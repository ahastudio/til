# Vinext 1.0 출시

원문: [Next.js applications, powered by Vite: introducing Vinext 1.0](https://blog.cloudflare.com/vinext-nextjs-on-vite/)

HN 토론: <https://news.ycombinator.com/item?id=49882760> (4점, 1개 댓글)

## 요약

2026년 9월 28일 Cloudflare 블로그에 실린 글이다. 글에는 저자 이름이 본문에 없고 Cloudflare Birthday Week 태그가 붙어 있다.
Vinext는 2월에 한 엔지니어가 AI로 일주일 만에 Next.js를 Vite 위에 재현한 실험으로 시작했고, 글은 이 프로젝트가 7개월 사이 실험에서 프로덕션 수준의 프레임워크로 졸업했다고 밝힌다.
글에 따르면 그 사이 고객들이 트래픽이 많고 동적인 앱을 Vinext로 운영했고, 1.0은 Pages Router와 App Router로 만든 Next.js 앱을 Cloudflare Workers 무료 플랜, Netlify, AWS Lambda 같은 웹 플랫폼에 배포하게 해 준다.
이전은 `npx vinext check`와 `npx vinext init` 두 명령으로 한다.

글이 1.0에서 내세우는 항목은 다음과 같다.

- 호환성: 고객이 가장 많이 요청한 기능의 테스트 호환성이 캐시 컴포넌트(Cache Components)를 제외하고 99%를 넘는다고 한다. 앞서 App Router에 집중하던 것을 Pages Router로 넓혔고 장기 Pages Router 사용자의 복잡한 앱을 겨냥했다고 설명한다.
- 테스트: 두 라우터, 개발과 프로덕션 서버, Node.js와 Cloudflare Workers 대상에 걸친 수천 개의 집중 테스트가 있고, Next.js의 종단 간(end-to-end) 테스트 스위트를 매일 밤 Vinext에 돌린다.
- 지원 범위: App Router, Pages Router, 혼합 앱, React Server Components, 서버 액션, API 라우트, 라우트 핸들러, 미들웨어, 클라이언트 내비게이션이다. 페이지는 서버 렌더링, 빌드 시 사전 렌더링, 정적 내보내기, 페이지 단위 ISR로 낼 수 있고 백그라운드와 온디맨드 재검증이 모두 된다.
- 캐싱: 두 라우터와 지원 런타임이 공유하는 캐싱 함수 집합과 Cloudflare Workers Cache 지원 확대이다.
- 관측성: 두 라우터에서 Next.js와 호환되는 트레이싱을 제공해 기존 OpenTelemetry와 Sentry 설정이 계속 동작하고, Workers에서는 Workers Observability와도 연동된다.
- 생태계: `next/*` 공개 표면과 인증, MDX, 이미지 최적화, 글꼴, 메타데이터, 환경 변수 같은 흔한 패턴을 구현한다.
- Workers 런타임: 개발과 프로덕션에서 workerd 런타임으로 서버 코드를 돌리고 이미지 최적화와 Hyperdrive 같은 바인딩에 직접 접근한다.
- 한계: Next.js 16이 캐시 컴포넌트를 중심 방향으로 삼았으나 글이 만난 팀 대부분이 쓰지 않았고 전제 조건으로도 보지 않아, `"use cache"` 지시어는 제한적으로만 지원한다. 개선은 계속하되 위 핵심 항목보다 우선순위가 낮다고 한다.

사전 렌더링은 달라진 점이 크다.
처음 공개 때는 첫 요청 뒤의 ISR만 지원하고 빌드 중에는 페이지를 렌더링하지 않았다.
1.0은 빌드 시 `generateStaticParams()`와 `getStaticPaths()`로 두 라우터의 경로를 사전 렌더링해 페이지 단위 ISR로 내고, 경로나 태그로 무효화하며, `output: "export"`로 완전 정적 사이트도 만든다.
글은 빌드에서 꼭 렌더링해야 하느냐고 되묻는다. URL이 수만에서 수십만 개인 사이트는 트래픽이 적은 페이지 때문에 순차 빌드에 수 시간이 걸린다고 한다.
그래서 캐시 워밍(cache warming)은 사전 렌더링을 Cloudflare 네트워크로 옮긴다. 새 Worker 버전을 올려 프로덕션 트래픽 0%로 배포하고, 그 버전에 페이지를 요청해 캐시를 채운 뒤 배포를 승격한다.

이후 계획으로 글은 처음 실험이 일회성 「slopfork」였다고 쓰고, 지금은 매일 새 커밋이 들어가는 Next.js canary를 따라간다고 한다.
매일 아침 에이전트가 변경을 검토하고 diff를 가져와 영향 가능성이 있는 것에 추적 이슈를 열고, 매일 밤 Next.js 테스트 스위트를 Vinext에 돌려 호환성 표를 다시 만든다. 틈이 발견되면 에이전트가 양쪽 코드에서 변경을 찾아 재현을 만들고 관련 테스트를 옮기고 수정을 제안한다.
글은 이 검토가 빠진 경우와 안전하지 않은 캐싱 동작, 개발 서버와 프로덕션 서버의 차이를 잡아냈다고 하며, 오픈소스를 위한 소프트웨어 공장을 짓는 중이라고 쓴다.
시작은 `npm create vinext-app@latest my-app`, 기존 앱은 `npx vinext check && npx vinext init`, Cloudflare 배포는 `npx @vinext/cloudflare deploy --warm-cache`이다.

## 분석

### 중심 주장은 실험이 제품이 되었다는 것이다

글의 구조는 졸업(호환성과 테스트), 1.0의 내용, 사전 렌더링과 캐시 워밍, 앞으로의 운영이다.
호환성 수치와 테스트 규모, 고객의 프로덕션 사용이 졸업의 근거로 놓인다.
이는 글의 서술을 이 문서가 정리한 것이다.

### 가장 큰 변화는 빌드 시점 사전 렌더링의 부활과 캐시 워밍이다

앞선 문서에서 다룬 2월의 공개 때 빌드 시 정적 사전 렌더링은 지원하지 않는 제약이었다.
1.0은 이를 지원하면서도 사전 렌더링 위치를 빌드 머신에서 Cloudflare 네트워크로 옮긴다.
빌드를 가볍게 하고 프로덕션 트래픽을 받기 전에 캐시를 채운다는 설명이다. 이는 인프라 소유자가 렌더링 전략에 개입하는 구조라는 점에서 이 문서의 해석이다.

### 호환성을 Next.js의 테스트로 유지하는 운영이다

호환성의 근거가 Next.js 자체의 종단 간 테스트와 매일의 상류 추적이다.
에이전트가 상류 변경을 읽고 재현과 수정을 제안하는 운영은 Vinext의 정의(Next.js API 표면의 재구현)에 맞춘 유지 방법이다.
Next.js가 바뀔 때마다 따라가야 한다는 부담을 자동화로 줄이려는 시도로 읽힌다. 이는 이 문서의 해석이다.

## 비평

### 99%의 분모와 범위가 글에서 읽히지 않는다

글의 99%는 고객이 요청한 가장 중요한 기능에 한정되고 캐시 컴포넌트는 제외된다.
이전 홈페이지에서 보인 94%(Next.js 16 API 표면)와 어떻게 다른 범주인지는 글이 설명하지 않는다.
중요한 기능의 선정 기준과 제외 항목이 수치를 정하므로 비교 가능한 수치로 보기는 어렵다.

### 제외 항목이 최신 방향과 어긋난다

글은 캐시 컴포넌트가 Next.js 16의 중심 방향이지만 만난 팀들이 쓰지 않았다고 쓴다.
이 판단은 글이 말한 고객 표본에 기댄다. 표본의 크기와 성격은 글에 없다.
Next.js가 이 방향으로 가면 호환성 격차가 커질 수 있다는 점은 글의 낮은 우선순위 표현 속에서만 암시된다.

### 에이전트 운영의 근거가 일화이다

상류 검토에서 에이전트가 빠진 경우와 안전하지 않은 캐싱 동작을 잡았다고 하지만 건수나 사례는 없다.
자동 제안된 수정의 채택 비율이나 오류율도 글에서 알 수 없다.
캐싱은 잘못되면 보안 문제로 이어질 수 있는 영역이어서 이 서술을 독립적으로 확인하기 어렵다.

### 배포 중립성의 정도가 불분명하다

글은 Cloudflare Workers 무료 플랜, Netlify, AWS Lambda를 배포 대상으로 든다.
그러나 캐시 워밍과 Workers Cache 통합, 관측성 통합, 바인딩 접근은 Cloudflare 기능에 묶여 있다.
다른 플랫폼에서 같은 수준으로 되는지는 글에서 구분되지 않는다. 이는 이 문서가 확인하지 못한 점이다.

### 외부 반응

HN에는 이 글로 올라온 글이 두 건이고(4점에 댓글 1개, 1점에 댓글 없음), 댓글 하나는 제출자 본인의 것이다. 한 줄로 Vercel의 제품 비전과 어디에서 갈라서는지 보고 싶다고 썼다.
Lobste.rs에서는 `vinext` 검색 결과가 1건이었고 이 글이 아닌 LLM 바이브코딩 논의였다.
GeekNews에서는 `Vinext`로 검색했고 대조 쿼리는 정상이었으나 이 글의 토픽은 없었다. 있는 것은 2월 글(`/vinext/`)의 토픽이다.
그래서 이 글의 주장은 독자의 검토를 거의 거치지 않았다.

## 인사이트

### 가져갈 것은 호환성 계층의 유지를 테스트 상류 연결로 푸는 방식이다

다른 프로젝트의 API를 재구현하는 계층은 상류의 변화를 따라가는 비용이 계속 든다.
상류의 테스트 스위트를 매일 돌리고 차이를 자동으로 추적하는 구성은 그 비용을 줄이는 방법의 한 예이다. 이는 이 문서의 적용이다.

### 이전을 검토한다면 자기 앱의 사용 기능부터 센다

캐시 컴포넌트와 `"use cache"`를 쓰는 앱은 제한적 지원에 해당한다.
`npx vinext check`로 호환성을 먼저 점검하고, 자기 앱이 쓰는 기능이 글이 말한 핵심 범위 안인지 확인하는 순서가 낫다.

### 확인할 관찰

이 글의 주장을 가를 관찰은 세 가지이다.
99% 수치의 분모와 제외 항목,
캐시 워밍이 Cloudflare 밖의 플랫폼에서 동작하는지,
캐시 컴포넌트를 쓰는 앱이 늘 때 호환성 격차의 변화이다.
셋 모두 이 문서가 확인하지 못했다.
