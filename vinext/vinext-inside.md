# Vinext 내부 구조 해설

원문: [Inside Cloudflare Vinext, the ground-up Next.js reimplementation](https://ai.sulat.com/19b8a8a3e779)

## 요약

2026년 2월 25일 AI @ Sulat.com에 JP Caparas가 쓴 15분 분량의 글이다. 요약문은 Cloudflare가 App Router를 Vite 위에 처음부터 다시 만들어 빌드가 4.4배 빠르고 번들이 57% 작다고 소개한다.
글은 Vinext가 Next.js API 표면의 94%를 덮는다는 수치로 시작해, 이식성 문제, 작동 방식, 벤치마크, 비어 있는 6%, 트래픽 인식 사전 렌더링, 1,100달러 프레임워크의 의미, Vite로의 수렴을 차례로 다룬다.

- 이식성 문제: Next.js가 ISR, 미들웨어, 이미지 최적화 같은 기능으로 Vercel에 점점 묶여 왔다고 쓴다. Vercel의 어댑터 API는 2026년 2월 기준으로 진행 중이며 Cloudflare 블로그가 이를 이른 시도라고 부른다고 인용한다.
- 작동 방식: Vite 6이 정식화한 Environment API로 클라이언트, SSR, RSC의 세 모듈 그래프를 한 개발 서버에서 돌린다. RSC는 `@vitejs/plugin-rsc`가 맡는다. `next/image`, `next/link`, `next/navigation` 등 33개 이상의 모듈 심(shim)을 쓰고 Vitest 1,700개 이상과 Playwright 380개, tsgo 타입 검사, oxlint를 쓴다.
- 95/5 분할: 코드의 95%는 플랫폼 중립이고 5%가 Cloudflare 어댑터(KV 캐시 핸들러 등)이다. Vercel 배포 개념 증명이 30분 안에 끝났다는 것을 경계가 확실하다는 신호로 든다.
- OpenNext 비교: OpenNext는 `next build` 출력을 변환해 실제 Next.js를 쓰지만 그 출력은 안정된 공개 API가 아니라 상류가 바꾸면 깨진다. Vinext는 API 표면을 재구현해 상류 내부 변경에 영향받지 않지만 새 기능을 직접 다시 만들어야 한다. 글은 OpenNext는 Next.js가 빌드 방식을 바꿀 때, Vinext는 제공하는 것을 바꿀 때 문제가 생긴다고 정리한다.
- 벤치마크: 33개 라우트 앱, 모든 라우트 `force-dynamic`, 기준은 Turbopack의 Next.js 16.1.6이다. 빌드 시간은 Next.js 7.38초, Vinext(Vite 7, Rollup) 4.64초(약 1.6배), Vinext(Vite 8, Rolldown) 1.67초(약 4.4배). 클라이언트 번들(gzip)은 Next.js 168.9KB, Vinext(Rollup) 74.0KB(56% 작음), Vinext(Rolldown) 72.9KB(57% 작음)이다.
- 비어 있는 6%: `generateStaticParams`와 빌드 시 정적 사전 렌더링이 없고 모든 페이지가 요청 시 렌더링된 뒤 ISR로 캐시된다. 글은 대시보드나 개인화 앱에는 상관이 없고 마케팅 사이트, 전자상거래 카탈로그, 문서 사이트에는 큰 문제라고 쓴다.
- 트래픽 인식 사전 렌더링(TPR): 지난 24시간 Cloudflare 존 분석에서 트래픽 많은 페이지를 골라 KV 캐시에 사전 렌더링한다. 실험적 기능이고 Cloudflare 분석 API와 KV에 의존한다.
- 1,100달러: Cloudflare 엔지니어링 매니저 Steve Faulkner가 OpenCode에서 800개 이상의 세션으로 Claude를 이끌어 약 1주일에 만들었고 첫 커밋은 2월 13일이다. 글은 토큰 비용이 그의 경력과 플랫폼 지식과 구조적 결정을 담지 못한다고 단서를 붙인다.
- Vite 수렴: React Router, TanStack Start, SolidStart, SvelteKit, Nuxt가 모두 Vite를 쓰고 Next.js만 Turbopack을 쓴다고 쓴다.
- 이후 함의: CIO.gov가 프로덕션에서 쓴다고 하고, 마이그레이션 도우미로 `npx skills add cloudflare/vinext`를 소개한다.

## 분석

### 중심 주장은 DX와 구현을 분리할 수 있다는 것이다

글의 결론은 파일 시스템 라우팅, 레이아웃, 서버 컴포넌트, 스트리밍, 캐싱이 Next.js 코드 없이 재현될 수 있고 API 표면이 안정된 부분이라는 것이다.
둘이 불가분이라는 가정에 대한 반례로 Vinext를 내세운다.
이는 글의 서술을 이 문서가 정리한 것이다.

### 벤치마크를 분해해서 읽는다

글은 4.4배라는 수치를 Rolldown 덕이고 Rollup에서는 1.6배라고 분해하며, 번들 감소는 번들러에 상관없이 일정하다고 쓴다.
또 제1자 벤치마크이고 모든 라우트가 `force-dynamic`이라는 점을 단서로 단다.
수치의 한계를 본문에서 직접 적는 구성이다. 이는 이 문서의 관찰이다.

### OpenNext와의 위험 프로필 비교가 핵심 대조이다

글은 두 접근을 우열이 아니라 서로 다른 실패 방식으로 비교한다.
이 틀로 보면 두 선택은 상류의 어떤 변화에 더 취약한지의 선택이다.

## 비평

### 수치가 시점에 묶여 있다

글의 수치(4.4배, 57%, 94%)는 2026년 2월의 값이다.
Vinext 프로젝트 사이트의 현재 수치는 최대 2배, 약 23%(gzip 185KB에서 143KB)로 보고되어 있고[^vinext-site], 글이 다룬 벤치마크와 같은 조건인지는 확인하지 못했다.
글의 사전 렌더링 부재 서술도 1.0에서 달라졌다. 1.0은 `vinext/vinext-1-0.md`에 정리했다.

### 1,100달러 서사에 대한 단서와 이를 담는 틀

글은 토큰 비용 외의 전문성을 짚지만, 1,100달러라는 숫자를 제목급 사실로 올리고 그 의미를 해설하는 데 한 절을 쓴다.
비용에 담기지 않는 것을 말하는 것과 숫자를 부각하는 것 사이의 균형은 독자의 판단에 달려 있다.

### 일부 서술이 확인되지 않는다

CIO.gov의 프로덕션 사용, Steve Faulkner의 직함, Vercel 배포 개념 증명 30분은 글이 전하는 것이다.
Vite가 프런트엔드 빌드의 리눅스 커널이 되고 있다는 비유는 글 자신이 불완전하다고 인정하는 비유이다.

### 외부 반응

HN에는 이 글 주소로 올라온 글이 없었다. 같은 사이트의 다른 글만 있었다(대조 쿼리는 정상이었다).
Lobste.rs에는 `vinext` 검색 결과가 이 글이 아닌 다른 글 1건이었다.
GeekNews에는 Vinext 2월 글의 토픽만 있고 이 글의 토픽은 없었다.

## 인사이트

### 가져갈 것은 벤치마크의 변수를 분해하는 읽기이다

한 수치(4.4배)에 번들러, 비교 대상, 라우트 설정이 섞여 있으므로 변수를 나눠 보면 어디서 이득이 나오는지 보인다.
다른 성능 주장도 같은 방식으로 분해하는 습관의 예로 쓸 수 있다. 이는 이 문서의 적용이다.

### 재구현과 어댑터의 실패 방식을 구분한다

어댑터는 상류의 내부 변경에, 재구현은 상류의 새 기능에 취약하다.
자기 프로젝트가 상류의 어느 변화에 더 자주 영향받는지에 따라 고르는 기준이 된다.

### 확인할 관찰

이 글의 주장을 가를 관찰은 세 가지이다.
Rolldown 외 조건에서 독립적으로 잰 빌드 시간,
정적 사전 렌더링 도입 후 같은 벤치마크의 변화,
Vite가 주요 프레임워크의 기반이 된다는 주장의 지속성이다.
