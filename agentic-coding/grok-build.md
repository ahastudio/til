## 소개

SpaceXAI의 터미널 기반 AI 코딩 에이전트다. 저장소 설명은 코딩 에이전트 하네스이자 TUI이며 전체 화면이고 마우스로 조작 가능하고 확장 가능하다고 적는다.
전체 화면 TUI로 돌면서 코드베이스를 이해하고, 파일을 편집하고, 셸 명령을 실행하고, 웹을 검색하고, 오래 도는 작업을 관리한다.
실행 형태는 세 가지다. 대화형, 스크립트와 CI를 위한 헤드리스, 그리고 Agent Client Protocol(ACP)을 통해 편집기에 내장되는 형태다.

Rust로 작성되었고 Apache-2.0이다.
2026년 7월 14일에 만들어진 저장소이며 스타 26,822개, 포크 5,049개다. 열린 이슈는 0개인데, 그 이유는 아래에서 다룬다.

이 저장소는 SpaceXAI 모노레포에서 주기적으로 동기화된다.
루트의 작은 `SOURCE_REV` 파일이 이 트리에 담긴 코드 버전에 해당하는 모노레포 커밋 SHA 전체를 기록한다.

## 저장소 구조

크레이트 이름이 전부 `xai-grok-pager` 계열이고, 빌드 산출물의 이름도 `xai-grok-pager`다. 공식 설치본에서만 `grok`이라는 이름으로 배포된다.

| 경로                                          | 내용                                                       |
| --------------------------------------------- | ---------------------------------------------------------- |
| `crates/codegen/xai-grok-pager-bin`           | 구성 루트 패키지. `xai-grok-pager` 바이너리를 빌드한다     |
| `crates/codegen/xai-grok-pager`               | TUI. 스크롤백, 프롬프트, 모달, 렌더링                      |
| `crates/codegen/xai-grok-shell`               | 에이전트 런타임과 leader/stdio/headless 진입점             |
| `crates/codegen/xai-grok-tools`               | 도구 구현. 터미널, 파일 편집, 검색 등                      |
| `crates/codegen/xai-grok-workspace`           | 호스트 파일시스템, VCS, 실행, 체크포인트                   |
| `crates/codegen/...`                          | 나머지 CLI 크레이트 묶음. 설정, MCP, 마크다운, 샌드박스 등 |
| `crates/common/`, `crates/build/`, `prod/mc/` | 묶음이 끌어오는 작은 공용 리프 크레이트                    |
| `third_party/`                                | 벤더링된 상류 소스. Mermaid 다이어그램 스택                |

루트 `Cargo.toml`은 생성된 파일이므로 읽기 전용으로 다루라고 README가 강조한다.
워크스페이스 멤버, 의존성 버전, 린트, 프로파일이 모두 거기 들어가며, 고칠 일이 있으면 크레이트별 `Cargo.toml`을 건드리라고 안내한다.

## 설치하고 빌드하기

릴리스 바이너리는 macOS, Linux, Windows용으로 제공된다.

```sh
curl -fsSL https://x.ai/cli/install.sh | bash   # macOS / Linux / Git Bash
irm https://x.ai/cli/install.ps1 | iex          # Windows PowerShell
grok --version
```

소스에서 빌드하려면 Rust 외에 DotSlash가 필요하다.
`bin/` 아래의 hermetic 도구, 특히 `bin/protoc`가 그것을 통해 내려받아 실행되기 때문이다.
빌드 전에 설치해서 `dotslash`가 `PATH`에 있어야 한다.

```sh
cargo install dotslash
/usr/bin/env dotslash --help   # 설치 확인

cargo run -p xai-grok-pager-bin              # 빌드 후 TUI 실행
cargo build -p xai-grok-pager-bin --release  # 릴리스 바이너리
cargo check -p xai-grok-pager-bin            # 빠른 검증
```

Rust 툴체인은 `rust-toolchain.toml`에 고정되어 있고 `rustup`이 첫 빌드에서 자동으로 설치한다.
proto 코드 생성은 DotSlash로 `bin/protoc`를 찾고, 없으면 `PATH`나 `$PROTOC`의 `protoc`로 물러선다.
빌드 호스트는 macOS와 Linux가 지원되며, Windows 빌드는 최선 노력이고 이 트리에서는 현재 테스트되지 않는다.

개발 시 명령은 크레이트 단위를 겨냥하라고 안내한다. 전체 워크스페이스 빌드는 느리기 때문이다.

```sh
cargo check -p <crate>          # 항상 특정 크레이트를 지정
cargo test -p xai-grok-config   # 크레이트별 테스트
cargo clippy -p <crate>         # 린트 설정은 루트 clippy.toml
cargo fmt --all                 # 루트 rustfmt.toml
```

첫 실행 시 브라우저가 열려 인증을 진행한다.

## 이식된 코드

이 저장소에서 가장 주목할 부분은 라이선스 고지다.
`xai-grok-tools` 크레이트의 도구 구현 상당수가 다른 오픈소스 프로젝트에서 이식되었다고 명시되어 있다.

| 출처           | 이식된 도구                                                           | 라이선스   |
| -------------- | --------------------------------------------------------------------- | ---------- |
| `openai/codex` | `apply_patch`, `grep_files`, `list_dir`, `read_file`                  | Apache-2.0 |
| `sst/opencode` | `bash`, `edit`, `glob`, `grep`, `read`, `skill`, `todowrite`, `write` | MIT        |

고지 문서는 이식된 파일이 원본에서 수정되었다고 밝힌다. 언어 간 번역, 이 크레이트의 `Tool` 트레이트와 런타임에 맞춘 적응, 그리고 확장이다.
그리고 이 파일 자체가 Apache License 2.0 §4(b)가 요구하는 변경 사항의 눈에 띄는 고지라고 적는다.

`openai/codex`에서 온 것은 `codex-rs/core/src/tools/handlers/`의 구현이고, `sst/opencode`에서 온 것은 `packages/opencode/src/tool/`의 구현이다.
전자는 Rust에서 Rust로 온 것이고 후자는 TypeScript에서 Rust로 번역된 것이다.

## 트레이드오프

### 모노레포 동기화 미러라는 형태

이 저장소는 개발이 일어나는 곳이 아니라 개발 결과가 도착하는 곳이다.
`SOURCE_REV`가 모노레포 커밋 SHA를 기록한다는 것은, 이 트리의 상태를 내부 상태와 대응시킬 수 있게 해 두었다는 뜻이다.

이 방식이 회사 쪽에 주는 이점은 분명하다. 내부 개발 속도를 공개 저장소의 절차에 맞출 필요가 없고, 공개 범위도 파일 단위로 통제된다.
사용자 쪽에도 이점이 있다. 실제로 배포되는 바이너리의 소스를 읽을 수 있고, 빌드해서 비교할 수 있다.

대가는 커뮤니티가 형성되지 않는다는 것이다.
버그를 발견해도 고쳐서 보낼 수 없고, 이슈로 남길 수도 없으며, 포크 5,049개가 상류로 돌아갈 경로가 없다.
여기서 흔히 떠올리는 절충, 즉 이슈만 열어 두는 방식은 이 구조에서 오히려 나쁘다. 응답할 인력이 모노레포 쪽에 있고 여기에는 없기 때문에, 열어 두면 방치된 이슈 목록만 쌓인다.
아예 닫아 두는 편이 기대를 정확히 전달한다는 점에서 이 선택은 일관적이다.

그런데 이 저장소의 포크는 북마크에 그치지 않았다. Sajarin이 HN에서 정리한 목록이 그것을 보여 준다.[^Sajarin]
`thedavidweng/gork-build`는 이름을 gork으로 바꾸고 벤더 텔레메트리를 걷어내고 데이터 보존을 옵트아웃 전용으로 바꾸고 x.ai 자동 업데이트를 막은, 그가 VSCodium 식 프라이버시 포크라 부른 것이다.
`DigiGoon/digi-grok-build`는 여러 제공사를 쓰는 dgrok CLI이면서 x.ai CDN 대신 소스에서 빌드하고, `victor-software-house/open-grok`은 모든 제공사에 열었으며, `LukaMucko/grok-build`는 제공사별 요청 필드를 위한 `extra_body`를 더했다.
`RapidAI/grok-build-desktop`은 Tauri 데스크톱 GUI이고, `mazdak/grok-build`는 테마를 붙였으며, `thomas9120/grok-build-archival`은 Windows용 텔레메트리 비활성화 스크립트다.

이 목록이 말하는 것은 기여 창구가 닫히면 협업이 사라지는 것이 아니라 분기로 바뀐다는 것이다.
그리고 분기의 주제가 대부분 텔레메트리와 제공사 잠금 해제라는 점이 무엇이 닫혀 있었는지를 알려 준다.
상류에 보낼 수 없는 변경일수록 포크가 되고, 그 포크들은 서로 합쳐지지 않으므로 같은 작업이 여러 번 반복된다.

### 경쟁사 도구 구현을 이식한 결정

`apply_patch`는 OpenAI Codex의 것이고, `edit`과 `bash`를 비롯한 여덟 개는 opencode의 것이다.
라이선스상 문제는 없다. Apache-2.0과 MIT는 이런 사용을 허용하고, 고지도 요구 이상으로 성실하다.

이 선택이 얻는 것은 시간과 호환성이다.
도구 인터페이스는 모델이 학습한 표면이므로, 널리 쓰이는 구현과 같은 이름과 같은 인자를 쓰면 모델이 이미 아는 방식으로 호출한다.
`apply_patch`를 Codex에서 그대로 가져온 것은 Grok 계열 모델이 그 포맷에 맞춰 후처리 학습되었을 가능성을 감안하면 특히 합리적이다.

대가는 상한도 함께 물려받는다는 것이다.
`apply_patch`의 실패 모드도, `edit`의 정확 일치 요구도 함께 온다. 다른 하네스들이 그 지점에서 겪는 문제를 똑같이 겪게 된다.
그리고 이식본은 상류를 따라가지 않는다. opencode가 자기 `edit`을 개선해도 이 트리의 사본은 누가 다시 이식하기 전까지 그대로다.

여기서 빠져나갈 길이 마땅치 않다. 독자적인 도구 인터페이스를 만들면 모델이 덜 익숙해지고, 그대로 쓰면 개선도 남의 일정에 달린다.
현실적인 절충은 이름과 시그니처는 유지하되 구현은 갈아 끼우는 것인데, 그러려면 이식이 아니라 재구현이 되고 이 저장소는 이식을 택했다.

### DotSlash를 빌드 전제로 삼은 것

빌드에 `protoc`가 필요한데, 시스템에 설치된 것에 기대지 않고 DotSlash로 고정 버전을 내려받는다.
이 선택의 이유는 재현성이다. 코드 생성에 쓰이는 컴파일러 버전이 개발자 머신마다 다르면 생성물도 달라지고, 그 차이는 빌드가 아니라 런타임에 드러난다.

대가는 빌드에 네트워크가 필요해진다는 것이다.
그리고 의존성 하나가 아니라 전제 하나가 늘어난다. DotSlash를 먼저 설치해 `PATH`에 두어야 하며, README가 이것을 굵은 글씨로 강조한 것도 그래서다.
`PATH`나 `$PROTOC`의 `protoc`로 물러서는 경로를 남겨 둔 것이 완화책이지만, 그 경로를 타면 재현성이라는 원래 목적이 사라진다.

에어갭 환경이나 사내 미러만 쓰는 조직에서는 이 구조가 그대로 문제가 된다. DotSlash가 가리키는 원격지를 먼저 미러링해야 하기 때문이다.

### 생성된 루트 `Cargo.toml`

워크스페이스 멤버, 의존성 버전, 린트, 프로파일이 전부 생성된 파일에 들어간다.
이것은 모노레포 빌드 시스템이 진짜 정본이고 Cargo 워크스페이스는 그 투영이라는 뜻이다.

포크해서 쓰려는 사람에게 이 사실은 실질적인 제약이다.
의존성 하나를 올리거나 크레이트를 추가하려면 루트 파일을 고쳐야 하는데, 그 파일은 다음 동기화 때 덮어써진다.
크레이트별 `Cargo.toml`을 고치라는 안내는 이 범위 안에서만 유효하고, 워크스페이스 수준 변경은 상류에 요청할 수밖에 없는데 그 창구가 닫혀 있다.

## 함정

`x.ai/cli/install.sh`를 파이프로 셸에 넘기는 설치 방식은 공식 안내이지만, 조직에 따라 허용되지 않는 형태다.
릴리스 바이너리를 직접 받아 서명을 확인하는 경로가 README에 없다.

바이너리 이름이 두 개다. 빌드하면 `xai-grok-pager`가 나오고 공식 설치본은 `grok`이다.
소스에서 빌드해 쓰는 경우 문서와 명령 이름이 어긋나므로, 심볼릭 링크나 별칭을 직접 만들어야 한다.

Windows 빌드는 최선 노력이고 이 트리에서 테스트되지 않는다고 명시되어 있다.
릴리스 바이너리는 Windows용으로 제공되므로, 쓸 수 있다는 것과 소스에서 빌드할 수 있다는 것이 다르다.

첫 실행에서 브라우저 인증이 필요하다. 헤드리스나 CI 용도로 쓰려면 이 단계를 어떻게 우회하는지 인증 가이드를 먼저 읽어야 한다.
저장소가 헤드리스 실행을 주요 용도로 내세우는 것에 비해 이 부분이 README에 정리되어 있지 않다.

이 CLI가 무엇을 전송하는지에 대한 별도 조사가 공개되어 있다는 점도 알아 둘 만하다. 이 저장소의 코드로 그 조사를 직접 검증할 수 있다는 것이 소스 공개의 실질적 값이다.

코드를 읽는 것을 대신하지는 않지만 실행 환경을 좁히는 방법이 있다.
doringeman은 Docker Sandboxes로 돌리는 방법을 소개하면서, `sbx policy log`가 네트워크 정책이 막거나 허용한 모든 요청을 보여 주므로 명시적 허용 목록과 합치면 의미 있게 더 안전한 환경이 된다고 적었다.[^doringeman]
텔레메트리 우려가 있는 도구를 평가할 때 먼저 취할 자세이며, 이 저장소처럼 소스가 공개된 경우에는 로그와 코드를 대조까지 할 수 있다.

## 확인하기

이 저장소에서 가장 값진 읽을거리는 도구 구현 디렉터리다.

```sh
git clone https://github.com/xai-org/grok-build
cd grok-build/crates/codegen/xai-grok-tools/src/implementations
ls codex opencode           # 이식된 구현이 출처별로 나뉘어 있다
cat ../../THIRD_PARTY_NOTICES.md
```

출처별로 디렉터리가 나뉘어 있으므로, 어떤 도구가 어디서 왔고 무엇이 자체 구현인지를 목록으로 볼 수 있다.
그 목록이 이 하네스가 어디에 독자적인 노력을 들였는지를 알려 준다. 이식된 것은 파일 조작과 검색이고, 남은 것이 이 팀이 직접 만든 부분이다.

그리고 `SOURCE_REV`와 릴리스 바이너리 버전을 함께 보면 이 미러가 얼마나 자주 갱신되는지를 알 수 있다.
그 주기가 이 저장소를 신뢰할 수 있는 감사 대상으로 볼지, 홍보용 스냅숏으로 볼지를 가르는 기준이 된다.

## 체크리스트

- 설치 스크립트를 파이프로 실행하는 방식이 조직 정책상 허용되는가
- 소스 빌드라면 DotSlash를 먼저 설치해 `PATH`에 두었는가
- 빌드 산출물 이름이 `xai-grok-pager`라는 것을 알고 별칭을 준비했는가
- Windows에서 소스 빌드가 필요한가, 릴리스 바이너리로 충분한가
- 헤드리스 또는 CI 용도라면 브라우저 인증 우회 방법을 확인했는가
- 포크해서 수정할 계획이라면 루트 `Cargo.toml`이 생성 파일이라는 제약을 반영했는가
- 외부 기여가 불가능하다는 점을 감안해 의존 계획을 세웠는가

## 비평

### 오픈소스라는 표현이 이 저장소에는 절반만 맞는다

라이선스는 Apache-2.0이고 소스는 전부 읽을 수 있다. 그 점에서 오픈소스다.
그러나 오픈소스라는 말이 보통 함께 뜻하는 것들, 즉 기여할 수 있고 논의할 수 있고 방향에 영향을 줄 수 있다는 성질은 여기 없다.

이 구분이 사소하지 않은 이유는 사용자의 위험 계산이 달라지기 때문이다.
상류가 방향을 바꾸거나 기능을 빼면 사용자가 할 수 있는 일은 포크뿐인데, 루트 빌드 설정이 생성 파일이라 포크 유지 비용이 일반적인 경우보다 높다.
그리고 포크 5,049개라는 숫자가 이 사정을 가린다. 그 대부분은 협업이 아니라 북마크다.

더 정확한 표현은 소스 공개 미러다. 감사 가능하고 빌드 가능하지만 참여할 수 없다는 뜻이며, 실제로 README가 그 사실을 숨기지 않고 명시했다.
문제는 저장소 밖에서 이 제품이 언급될 때 그 단서가 함께 따라가지 않는다는 것이다.

공개의 시점도 함께 읽어야 한다.
이 저장소가 공개되기 며칠 전, 이 CLI가 작업 디렉터리 전체를 전송한다는 분석이 화제가 되었고 HN에서 539점에 228개 댓글이 달렸다.
loufe는 공개가 로드맵에 있었더라도 그 소동에 떠밀려 우선순위가 올라간 것 아니겠냐고 추측했고[^loufe], GodelNumbering은 더 단호하게 이것이 옳은 일이 아니라 전술적인 일이라고 적었다.[^GodelNumbering]
점유율이 1% 미만이고 평판이 나쁘며 사용자 데이터를 올리다 걸린 상황에서 남은 몇 안 되는 전술적 수라는 것이다.

ninjagoo는 신뢰 회복에 필요한 것을 구체적으로 짚었다.[^ninjagoo]
유출한 데이터를 삭제했거나 삭제할 것이라고 주장하지만, FTI Tech나 Kroll이나 Epiq나 HaystackID 같은 데이터 파기를 인증하는 독립 기관이 있고 그런 증명서는 제시되지 않았다는 것이다.
소스 공개는 앞으로 무엇을 보내는지를 확인할 수 있게 하지만 이미 보낸 것에 대해서는 아무것도 말해 주지 않는다. 두 문제를 구분하지 않으면 공개가 해명으로 오독된다.

### 이식 고지가 성실할수록 드러나는 것이 있다

`THIRD_PARTY_NOTICES.md`는 모범적이다. 어떤 파일이 어디서 왔는지, 어떤 디렉터리에 있는지, 무엇이 바뀌었는지를 적고 Apache §4(b) 고지임을 명시한다.
법적 의무를 넘어서는 수준이며, 이런 문서를 이만큼 쓰는 곳은 드물다.

그런데 그 성실함 덕분에 목록을 세어 볼 수 있게 된다.
파일 읽기, 쓰기, 편집, 검색, glob, bash 실행, 스킬, todo 관리가 전부 남의 구현이다.
코딩 에이전트가 환경과 맞닿는 표면이 사실상 통째로 이식된 셈이며, 남은 자체 구현은 TUI와 런타임과 워크스페이스 관리다.

이것을 흠으로 볼 일은 아니다. 표준화된 부분을 다시 만들지 않는 것은 합리적이고, 앞서 본 대로 모델 호환성이라는 이유도 있다.
다만 이 사실은 코딩 에이전트 시장에서 무엇이 차별화 요소인지를 말해 준다. 도구 구현은 이미 공용재가 되었다는 것이다.
그렇다면 하네스의 값은 도구가 아니라 루프와 컨텍스트 관리와 인터페이스에 있어야 하고, 그 부분에 대한 설명이 README에 거의 없다는 점이 아쉽다.

코드 자체에 대한 평가는 갈렸다.
simonw는 이 코드베이스에 놀라운 것들이 있다며, Mermaid 다이어그램을 유니코드 박스 문자로 터미널에 렌더링하는 자족적인 렌더러를 예로 들었다.[^simonw]
반면 phillipcarter는 제공하는 기능에 비해 코드 양이 엄청나다며 의도적으로 설계된 것 같지 않다고 적었다.[^phillipcarter]
두 평가는 모순되지 않는다. 터미널에서 Mermaid를 그리는 렌더러를 직접 넣었다는 사실이 바로 양쪽 판단의 근거이기 때문이다.

그 렌더러가 곧바로 재사용되었다는 점이 소스 공개의 값을 보여 준다.
simonw는 그 Rust 코드를 WebAssembly로 컴파일해 브라우저 플레이그라운드를 만들었고[^simonw-wasm], clkao은 자기 마크다운 리뷰 도구에서 Mermaid를 렌더링할 방법을 찾던 차에 같은 코드를 Go로 이식했다.[^clkao]
기여는 받지 않지만 코드는 흘러 나간다는 것이며, 앞서 본 포크 목록과 같은 현상의 다른 형태다.
이 방향의 흐름은 상류에 아무 부담도 지우지 않으므로, 기여를 닫아 둔 정책과 충돌하지 않고 오히려 잘 맞는다.

### 26,822개의 스타가 무엇을 뜻하는지 따져 볼 필요가 있다

두 달 만에 스타 26,822개는 큰 숫자다. 같은 기간 대부분의 개발자 도구가 받는 것보다 훨씬 많다.
그런데 이 저장소의 성격을 보면 그 숫자를 사용량으로 읽기 어렵다.

이슈가 0개인 것은 정책 때문이므로 사용 신호가 될 수 없고, 포크는 기여 경로가 없으니 협업 신호가 아니다.
소스 빌드에는 DotSlash와 Rust 툴체인과 protoc가 필요하고, 실제 사용에는 SpaceXAI 계정 인증이 필요하다.
즉 저장소를 스타한 사람과 도구를 쓰는 사람의 교집합이 얼마나 되는지 알 방법이 이 페이지에는 없다.

이 관찰이 중요한 이유는 코딩 에이전트 비교에서 스타 수가 자주 인용되기 때문이다.
개발이 모노레포에서 이루어지고 공개 트리는 미러인 구조에서는, GitHub 지표가 프로젝트 활동과 거의 무관해진다.
커밋 빈도도 동기화 주기를 반영할 뿐이고, 기여자 수도 내부 인원을 반영하지 않는다.
이런 저장소가 늘어날수록 GitHub 지표로 도구를 비교하는 관행 자체가 무의미해진다.

동기도 함께 봐야 한다. glasffordd는 선물처럼 보이는 것이 실은 주머니를 채운다고 지적했다.[^glasffordd]
에이전트는 무료지만 기본적으로 유료 모델 위에서 돌기 때문에, 이 도구가 하는 모든 작업이 그 회사의 토큰을 쓴다는 것이다.
drdrek은 같은 사실을 반대로 평가했다. 뒤처진 쪽인 Meta와 xAI의 전략이 선두의 해자를 오픈소스로 만드는 것이고, 그 덕에 모두가 이득을 보며 결국 선두와 후발 모두 덜 강력해지기를 바란다는 것이다.[^drdrek]
두 관점이 같이 성립한다. 하네스를 공짜로 푸는 것은 하네스가 해자가 아니라는 판단이자, 해자를 모델 쪽에 남겨 두겠다는 선언이기도 하다.

## 기억할 원칙

### 도구 구현은 공용재가 되었고 차별화는 그 위로 올라갔다

이 저장소가 무심코 기록한 사실 하나가 업계 전체에 대한 진술이다.
프런티어 연구소가 만든 코딩 에이전트의 파일 도구가 경쟁사 제품과 오픈소스 프로젝트에서 이식되었다는 것이다.

이 일이 가능해진 조건은 두 가지다.
하나는 도구 인터페이스가 사실상 표준화되었다는 것이고, 다른 하나는 그 표준이 모델 학습에 반영되어 있어 벗어날 유인이 적다는 것이다.
`read`, `write`, `edit`, `bash`, `grep`, `glob`이라는 집합은 이제 어느 하네스에서나 거의 같은 이름으로 존재한다.

여기서 나오는 실천적 함의는 자기 하네스를 만들 때 무엇을 직접 만들지에 대한 것이다.
도구 구현을 처음부터 쓰는 것은 대체로 낭비다. 검증된 이식본이 여러 라이선스로 공개되어 있고, 모델도 그 이름에 익숙하다.
직접 만들 값이 있는 곳은 그 위층, 즉 어떤 순서로 도구를 부를지, 무엇을 컨텍스트에 남길지, 실패를 어떻게 되돌릴지다.

이 저장소의 크레이트 분할이 그 판단을 그대로 보여 준다.
`xai-grok-tools`는 이식으로 채웠고, `xai-grok-shell`과 `xai-grok-workspace`는 직접 만들었다.
런타임과 체크포인트에 자체 노력을 집중했다는 뜻이며, 같은 것을 만드는 사람이 참고할 만한 자원 배분이다.
