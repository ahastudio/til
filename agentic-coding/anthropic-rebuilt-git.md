# Theo: Anthropic은 병목 끝에 git을 다시 만들었고, 많은 팀이 같은 곳에 이를 것이다

트윗: [Anthropic was so bottleneck'd by GitHub that they rebuilt git itself.](https://twitter.com/theo/status/2112020808478638468)

## 요약

Theo(@theo, t3.gg)는 2026년 10월 19일 트윗에서
Anthropic이 GitHub 때문에 병목에 걸려 git 자체를 다시 만들었다고 썼다.
이것이 무모해 보일 수 있지만 우리 중 많은 사람이 지금의 Anthropic과 같은 곳에
이르게 될 것이라고 덧붙였다.
트윗에는 Anthropic의 10월 14일 트윗이 인용되어 있고,
인용문은 엔지니어링 블로그의 사내 소스 관리 글을 소개한다.

인용된 Anthropic 트윗은 숫자 둘을 든다.
5월에는 하루 약 2,500건의 코드 변경을 병합했고
9월에는 하루 3만 건 넘게 병합했다는 것이다.
그 결과 사람이 아니라 에이전트의 규모에 맞지 않는
개발자 인프라가 병목이 되었다고 한다.
트윗의 인용 카드에는 영상이 붙어 있고 본문은 줄여서 보인다.

이 글이 다루는 것은 Theo의 두 문장이다.
첫 문장은 원인을 GitHub에 돌리는 서술이고,
둘째 문장은 Anthropic의 경험이 곧 다수의 미래라는 일반화다.
Anthropic 원글의 세부는 이 글의 범위가 아니고,
원글과 대조해 이 두 문장이 얼마나 성립하는지만 따진다.

## 분석

### 트윗은 두 개의 서로 다른 주장을 한 호흡에 묶는다

첫 주장은 사실에 대한 서술이다.
병목의 원인이 GitHub이었고 그 결과 git을 다시 만들었다는 것이다.
둘째 주장은 예측이다.
다른 조직도 같은 상황에 놓일 것이라는 말이다.
앞의 것은 원글과 대조해 확인할 수 있고,
뒤의 것은 조건을 붙여야 검증할 수 있다.

트윗이 설득력을 갖는 이유는 숫자의 크기에 있다.
하루 2,500건에서 3만 건 넘게로 넉 달 사이 12배 남짓 늘었다.[^anthropic]
단순 계산으로 하루를 균등하게 나누면 3만 건은 3초에 한 건꼴의 병합이다.
이 속도라면 사람 규모로 설계된 절차가 버틸 수 없다는 직관이 곧바로 선다.

### 병합 하나가 일으키는 부하가 숫자로 드러난다

원글은 병합 수 말고도 규모를 보여 주는 숫자를 준다.
main 브랜치 한 줄기의 이력이 약 100GB이고 압축한 작업 사본이 25GB를 넘으며,
CI에서만 하루 약 2,500만 번 코드를 체크아웃한다.
그대로 가져오면 하루에 600PB가 넘는 git 트래픽이라고 한다.[^anthropic]

이 숫자를 병합 수와 나누면 이 글의 계산으로 병합 한 건당 체크아웃 약 800번이다.
2,500만을 3만으로 나눈 값이고,
병합과 체크아웃의 기간이 정확히 겹친다고 가정한 대략적 비율이다.
핵심은 비율의 크기보다 구조다.
코드 변경 하나가 수많은 CI 작업과 에이전트 샌드박스의 체크아웃으로 증폭된다.

### 원글이 말하는 병목은 사람 규모의 개발 인프라 전체다

Anthropic은 병목을 소스 관리, 빌드, CI를 아우르는
사람 규모로 만들어진 개발자 인프라라고 설명한다.[^anthropic]
git의 분산 설계, 곧 모든 클론이 완전한 저장소라는 성질이
클라이언트 대부분이 항상 온라인인 에이전트와 작업일 때는 비용이 되었다는 것이다.
그래서 서버가 중심이고 클라이언트는 필요한 데이터만 가져오는
Scion을 만들었다고 한다.

## 비평

### 병목의 원인을 GitHub이라고 부르는 것은 원글과 맞지 않는다

트윗은 GitHub 때문에 병목이 생겼다고 쓴다.
그런데 원글이 설명하는 병목은 git이라는 도구의 설계와
그 위에 쌓은 자체 운영, 곧 한때 수백 대에 이른 사내 git 미러다.[^anthropic]
미러와 저장소 스냅샷(seed)은 큰 모노레포를 다루는 표준 대응이고
이를 직접 운영하는 부담이 커졌다는 이야기다.

GitHub이라는 이름은 원글에서 해결해야 할 대상이 아니라
협력하고 싶은 상대로 나온다.
Anthropic은 자신들의 기여가 아주 좁다고 말하면서
GitHub, GitLab, 오픈 소스 커뮤니티와 함께
개발자의 변하는 요구를 지원하고 싶다고 쓴다.[^anthropic]
도구인 git과 서비스인 GitHub을 한 단어로 섞으면
무엇을 바꿔야 하는지에 대한 결론이 달라진다.
GitHub이 병목이었다면 벤더를 바꾸는 것이 답이지만,
원글의 진단은 소스 관리 모델 자체를 서버 중심으로 바꾸라는 것이다.

### 일반화는 Anthropic 스스로 한 단서와 엇갈린다

둘째 문장은 우리 중 많은 사람이 같은 곳에 이를 것이라고 단정한다.
원글은 이보다 조심스럽다.
Anthropic은 거의 모든 회사보다 Claude로 소프트웨어를 많이 쓰기 때문에
사람 규모용 도구가 먼저 무너지는 것을 먼저 본다고 하면서,
가까운 시일 안에 많은 조직이 이런 문제를 겪으리라고는 기대하지 않는다고 쓴다.
다만 머지않아 다른 곳도 같은 압력을 받을 것이라고
짐작한다고 덧붙인다.[^anthropic]

여기서 갈리는 것은 시간 척도다.
Theo는 많은 사람이 곧 그렇게 된다는 인상을 주고,
원문은 가까운 시일에는 아니고 머지않아라는 단서를 붙인다.
어느 규모부터 그렇게 되는지도 트윗에는 없다.
병합이 하루 몇 건, 저장소가 몇 GB일 때 같은 문제가 시작되는지를
말하지 않으면 예측은 검증할 수 없는 주장으로 남는다.

### 다시 만들었다는 표현이 작업의 성격을 줄여 버린다

트윗은 git 자체를 다시 만들었다고 쓴다.
원글에서 Scion은 git을 재구현한 것이 아니라
서버가 모든 연산을 수행하고
클라이언트는 얇은 캐시를 두는 별개의 시스템이다.[^anthropic]
원글은 대형 모노레포를 위한 선행 사례로 Google의 Piper와 Meta의 Sapling을 든다.
같은 문제에 한 번 이상 답한 선행 설계가 있었다는 뜻이다.

또 이 작업은 소스 관리만이 아니었다.
코드 리뷰 화면, 코드 검색, 소스 관리용 권한 체계를 같은 기간에 함께 만들었고
전체 이전은 다섯 달이 걸렸다고 한다.[^anthropic]
다시 만드는 일이 쉬웠다는 인상은
Claude가 코드를 대신 쓰는 조직의 사정에서 나온다.
원글도 Claude의 코드 작성 능력이 이 상황을 낳았고
동시에 해결도 가능하게 했다고 적는다.

## 인사이트

### 병목을 풀수록 수요가 늘어나는 구조에서는 용량 계획이 무의미해진다

원글은 병합 코드에 대한 잠재 수요가 사실상 무한하고
병목 하나를 없앨 때마다 코드 생산이 곧바로 더 늘어난다고 쓴다.[^anthropic]
이것은 도로를 넓히면 교통량이 늘어난다는 유발 수요와 같은 구조다.
여유 용량을 계산해 증설하는 방식은
수요가 용량에 반응하는 순간 따라잡히지 못한다.

이차 효과는 병목이 계속 하류로 옮겨 간다는 점이다.
소스 관리를 고치면 CI가, CI를 고치면 리뷰가 다음 병목이 된다.
Anthropic이 소스 관리와 같은 기간에
코드 리뷰 화면과 코드 검색까지 만든 것이 이를 보여 준다.[^anthropic]
따라서 병목을 하나 해결했다는 선언은
다음 병목의 위치를 알려 주는 것으로 읽어야 한다.

### 곧 그렇게 된다는 예측은 자체 구축이 아니라 벤더에 대한 요구로 이어질 가능성이 크다

Theo의 문장을 우리 중 많은 사람이
git을 다시 만들게 된다는 뜻으로 읽을 필요는 없다.
Anthropic이 다섯 달 만에 이전을 마칠 수 있었던 것은
자사의 코드 생산 능력이 압도적이어서인데,
이 조건은 대부분의 팀에 없다.
Anthropic 스스로 GitHub과 GitLab과 협력하고 싶다고 말하는 이유도
여기에 있을 것이다.

더 개연성 있는 결과는 에이전트 규모의 병합과 체크아웃 부하를 감당하는 기능이
벤더에게 요구사항으로 올라가는 것이다.
이 글은 이를 추론으로 표시한다.
원글이 직접 예측한 것은 아니다.
실무에서는 지금부터 병합당 체크아웃 수 같은 증폭 비율을 재 두면
그 요구가 언제 현실이 되는지 알 수 있다.

### 큰 회사의 인프라를 앞서 따라 하는 일은 반복되어 온 실수다

Anthropic은 다른 회사가 아직 겪지 않는 문제를 먼저 본다고 스스로 말한다.
이런 이야기가 소셜 미디어에서 우리도 거기 이를 것이라는 문장으로 압축되면
앞서 따라 하려는 압력이 생긴다.
작은 팀이 Google 규모에 맞춘 인프라나 마이크로서비스를
일찍 도입했다가 비용을 치른 일이 이미 여러 번 있었다.

차이를 가르는 기준은 이미 측정된 병목이다.
병합 수, 저장소 크기, 체크아웃 시간 중 어느 것이 실제로 한계에 닿았는지를
숫자로 보여 줄 수 없다면 이 이야기는 아직 남의 일이다.
트윗이 맞다면 그 숫자가 언젠가 나타나겠지만,
그때까지 따라 할 이유는 측정에서 나와야 한다.
