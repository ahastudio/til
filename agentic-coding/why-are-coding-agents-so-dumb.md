# 코딩 에이전트는 왜 이렇게 멍청한가: 병목은 모델이 아니라 에이전트다

원문: [Why Are Coding Agents So Dumb? · mtlynch.io](https://mtlynch.io/why-are-coding-agents-so-dumb/)

## 요약

Michael Lynch가 2026년 10월 9일 자신의 블로그에 쓴 글이다.
그가 처음 코딩 에이전트를 쓴 것은 2025년 2월이었다.
IDE와 AI 채팅 창 사이에서 코드를 복사해 붙이던 시절이라,
에이전트가 파일을 직접 고치고 자기 오류를 실시간으로 바로잡는 모습에 빠져들었다.
며칠 뒤 신혼기가 끝났다.
에이전트는 재시작하기 전까지 응답을 멈추곤 했고,
개발 흐름은 답답할 만큼 원시적이었으며,
작업을 거의 시작하지도 않고 끝났다고 선언하는 일이 잦았다.
그는 6개월이면 에이전트가 기반 LLM만큼 인상적인 수준에 이를 것이라 예상했지만,
에이전트는 그냥 나쁜 상태로 남았다고 말한다.
AI 지원 개발은 분명 발전했지만 무거운 일은 모델이 하고 있고,
에이전트가 병목이라는 것이 글의 출발점이다.

저자는 먼저 용어를 나눈다.
모델은 GPT Astra, Claude Sonnet, GLM-5.3 같은 LLM으로,
텍스트와 이미지와 꽤 괜찮은 코드를 생성한다.
에이전트는 Claude Code나 Codex처럼
모델을 코드베이스와 컴퓨터 시스템에 연결하는 소프트웨어다.
모델이 두뇌라면 에이전트는 몸이며,
모델이 내놓는 텍스트를 시스템의
올바른 명령과 파일에 꽂아 주는 접착제라는 비유다.

### 저자가 꼽은 여섯 가지 결함

| 결함                        | 저자가 든 사례                                                                                        |
| --------------------------- | ----------------------------------------------------------------------------------------------------- |
| 작업을 관리하지 못한다      | OpenCode가 약 1.5k줄짜리 PicoShare 암호 문구 기능을 하위 작업 10개로 나눈 뒤 하나씩 순서대로 처리했다 |
| 위임하지 못한다             | 5만 줄에서 패턴을 찾는 일에도 비싼 모델을 계속 쓰고, 반대로 더 똑똑한 모델을 부르지도 않는다          |
| 자기 자신을 모른다          | Claude Code에 Claude Code 사용법을 물으면 온라인 검색부터 한다                                        |
| 계획을 전달하지 못한다      | Codex와 GPT-6 Astra가 낸 계획은 저수준 설계 결정을 뒤섞어 나열한 목록이었다                           |
| 핑계만 있으면 일을 멈춘다   | 밤새 돌리려던 작업이 2분 만에 git 브랜치 이름을 묻느라 멈춰 아침까지 기다렸다                         |
| 위험을 감수해야만 쓸모 있다 | 읽지 말라고 부탁한 파일을 무시하고 비공개 애플리케이션 키를 OpenAI와 Anthropic으로 보냈다             |

작업 관리 항목에서 그는 컴퓨터는 멀티태스킹을 잘하라고
CPU 코어를 계속 늘려 주는 존재인데,
왜 쉽게 병렬화할 수 있는 작업을 하나씩 하느냐고 묻는다.
Claude Code는 하위 에이전트를 한두 개 띄우긴 하지만 전부 끝날 때까지 기다린다.
하루에도 여러 번 Claude Code가 종단 간 테스트를 몇 분씩 기다린 뒤에야
커밋 메시지 관례를 알아보려고 git 이력을 보기 시작하는 장면을 본다고 적었다.

위임 항목에서는 하위 작업마다 모델과 추론 수준을 직접 바꿀 수는 있지만
그것이 왜 사람의 일이냐고 따진다.
작업의 난이도를 매기고
거기에 맞는 모델을 고르는 일에 능한 기술이 바로 LLM이라는 것이다.
95%가 단순 노동인 작업도 쪼개서 위임하는 데 드는 시간이 아까워
결국 가장 똑똑한 모델에 통째로 맡긴다고 했다.

자기 인식 항목에서는 사용자가 쓴 적도 없는 기능을 위해 13GB를 내려받으면서
자기 기능을 설명하는 gzip 50KB 텍스트는 설치 패키지에 넣지 않느냐고 꼬집는다.
검색해 온 지침이 설치된 버전과 맞는지도 보장되지 않는다.

계획 항목에서 그는 한때 Plan 모드와 Execute 모드의 분리를 좋아했다고 말한다.
복잡한 작업은 계획을 받아 검토하고 고친 뒤
더 빠르고 싼 에이전트에 실행을 맡겼다.
그러다 계획 읽기가 싫어져 검토를 건너뛰게 되었는데,
게을러진 것이 아니라 계획이 읽기 괴로울 만큼
형편없이 전달되기 때문이었다고 결론짓는다.
유능한 개발자라면 UI 변경의 큰 그림에서 아래로 내려가거나,
데이터 모델 변경에서 위로 올라가며 계획을 설명했을 것이다.

위험 항목에서 그는
에이전트를 처음 쓸 때 파일 접근을 제한하는 설정부터 찾았다고 한다.
그러나 문서는 특정 파일이나 디렉터리를 읽지 말아 달라는
정중한 편지를 LLM에 쓰라고 권했고,
에이전트는 그 요청을 곧바로 무시했다.
지금도 에이전트는 모든 것에 접근 권한을 줄 때만 쓸 만하고,
공급사 자체 샌드박스를 우회하는 일도 흔하다.
대안은 하루 500번 Allow를 누르는 것인데 언젠가는 잘못 누르게 된다.
10년 넘게 샌드박스 도구가 있었다는 점이 그를 화나게 하며,
그는 에이전트가 저장소 디렉터리 밖을 보지 못하게 하는
샌드박스 llm-sandbox를 직접 만들어 쓴다.

### 기본 상태에서 갖춰야 할 것

저자는 무작위 git 저장소의 스킬 파일 20만 줄을 깔거나
숨은 기능 플래그를 켜면 된다는 반론을 예상하고,
자신이 말하는 것은 플러그인이나 몇 시간의 설정 없이
기본 상태에서 해야 할 일이라고 분명히 한다.
그가 2026년 코딩 에이전트의 기본기로 꼽은 목록은 다음과 같다.

- 요청을 여러 작업으로 나누고 각 작업에 맞는 모델을 배정하며,
  비용·속도·정확성을 최적화하되 사용자가 작업별로 조절할 수 있다.
- 사람이 이해하기 좋은 계획을 쓴다.
  높은 추상화 수준에서 시작해 세부로 내려가고 UI 목업, 데이터 흐름도, 의사결정 트리를 만든다.
- 실제 샌드박스 안에서 돈다.
  OS 수준 보안 기능으로 파일시스템과 네트워크 경계를 만들고,
  접근 제어는 에이전트가 무시해도 되는 부탁이 아니라 결정적인 코드여야 한다.
  bash 명령에 대한 정규식 목록이 샌드박스냐고 물으면 아니라고 답해야 한다.
- 기본 접근 범위는 저장소나 디렉터리 하나이고,
  세션마다 다른 저장소에 읽기 전용 또는 읽기·쓰기 권한을 줄 수 있다.
- 자기 자신에 대한 전문가여서, 작업이나 흐름을 어떻게 표현해야 하는지 검색 없이 답한다.
- 무제한 요금제를 포함해 어떤 LLM 공급자든 쓸 수 있고, 에이전트 자체는 오픈소스다.
- Execute 모드에서 질문에 답이 없고 30분 동안 세션에 상호작용이 없으면 스스로 결정하며,
  그 대기도 건너뛰는 AFK 모드를 둔다.
- 하위 에이전트 세션에도 사용자가 들어가 조종하거나 일찍 끝내라고 할 수 있다.

이어서 개인 작업 흐름에 치우쳤을 수 있다고 인정하며 더 큰 꿈도 적는다.
모든 세션을 한눈에 보여 주는 로컬 웹 인터페이스,
에이전트와 하위 에이전트가 계속 갱신하고 과거 정확도로 보정하는 완료 예상 시간,
20GB 로그를 임시 명령으로 파싱하느라 닷새 동안 하루 1,000달러를 쓴 것을
스스로 알아채고 전용 도구를 만드는 식의 자기 세션 검토,
언어를 이해하는 diff 화면,
자격 증명을 다른 호스트로 빼돌릴 수 없게 요청에 비밀을 넣어 주는 프록시,
주간 한도가 3시간 뒤 초기화되는데 90%가 남아 있으면
비용 최적화를 멈추는 식의 한도 인식 모델 선택,
일정 복잡도 이상의 작업에 다른 모델의 코드 리뷰를 붙여
수정안에 합의할 때까지 반복하는 기능이다.

### 왜 이렇게 되었는가

저자는 만족스러운 답이 없다고 먼저 인정한다.
가장 그럴듯한 가설은 주인-대리인 문제(principal-agent problem)다.
AI 도구의 방향을 정하는 사람은 Anthropic, OpenAI, Google의 경영진인데,
이들은 매일 코딩 에이전트를 쓰는 일선 개발자와 떨어져 있고,
상당수는 인간 개발자를 완전히 자동화하는 미래를 꿈꾼다.
경영진과 대형 고객과 주주는 화려한 데모와 벤치마크 점수처럼
자신에게 읽히는 지표를 보는데,
보안과 개발자 시간의 효율은 데모와 무관하고,
그가 본 벤치마크는 거의 에이전트가 아니라 기반 모델을 잰다.
다만 Claude와 Codex에 매달 많은 기능이 추가되는 것을 보면
회사들이 에이전트에 조금은 신경을 쓰므로 이 가설도 충분하지 않다고 덧붙인다.
그 기능 중 마지막으로 자기 삶을
낫게 한 것이 언제였는지는 기억나지 않는다고 했다.

그가 써 본 에이전트는 Claude, Codex, OpenCode, Cline, Pi이고,
매일 쓰는 것은 OpenCode와 Claude Code다.
더 나은 에이전트를 추천해 달라고 부탁하고,
상상 속 에이전트를 500억 달러에 사겠다면
언제든 VS Code를 포크할 준비가 되어 있다는 농담으로 글을 맺는다.

## 분석

### 모델과 에이전트를 나누는 것이 글 전체의 지렛대다

이 글에서 가장 중요한 문장은 불만 목록이 아니라 모델은 두뇌,
에이전트는 몸이라는 구분이다.
이 구분이 있어야 모델이 매달 좋아지는데
체감은 그만큼 좋아지지 않는다는 경험을 설명할 수 있다.
저자가 든 여섯 결함은 모두 모델의 지능이 아니라
모델 바깥에서 실행을 조직하는 코드의 결함으로 분류된다.
작업을 병렬로 띄우는 일, 모델을 고르는 일, 문서를 함께 배포하는 일,
일정 시간 뒤 스스로 결정하는 규칙,
파일시스템 경계는 모두 결정적인 소프트웨어로 짤 수 있는 것들이다.

그래서 이 글의 주장은 AI가 멍청하다는 흔한 불평과 다르다.
Lobste.rs의 dlisboa는 소망 목록이
70년치 컴퓨터 과학과 초인적 지능을 요구한다고 비판했다[^dlisboa].
저자는 이에 모델은 이미 할 수 있는데
에이전트가 활용하지 못하는 항목들이라고 답했다[^mtlynch-lobsters-2].
이 답이 글의 핵심 논리를 가장 짧게 요약한다.
요구는 더 똑똑한 모델이 아니라 이미 있는 모델을 제대로 부리는 소프트웨어다.

같은 관점은 이 저장소의 `agentic-coding/harness-tax.md`가 다룬
측정 연구와도 맞닿는다.
같은 모델이라도 하네스에 따라 비용과 성적이 달라진다는 실험 결과는,
저자가 말하는 병목이 기분 탓이 아니라 측정 가능한 영역이라는 근거가 된다.

### 기준은 동료 개발자이고, 그래서 결함이 무례로 느껴진다

저자는 결함마다 사람 동료와 비교한다.
코드 리뷰가 무엇인지 매번 검색하는 동료,
사소한 질문 하나 때문에 근무 시간 내내 놀았다는 직원,
요점 없이 사실을 늘어놓는 개발자의 계획이다.
이 비유가 글의 감정적 동력이지만 동시에 기대치를 정하는 장치이기도 하다.
에이전트를 도구로 보면 결함은 기능 부재지만,
동료로 보면 결함은 판단력 부재이고 그래서 훨씬 더 짜증스럽다.

Lobste.rs에서 zem은 글 전체에서 에이전트라는 말을 도구나 코드 생성기로 바꾸면
인지 부조화가 대부분 사라지고 실제로 쓰기도 훨씬 덜 괴롭다고 적었다[^zem].
janxdevil은 직원이라면 바로 해고하겠다는 대목을 인용하며
문제의 뿌리를 찾은 것 같다고 짧게 적었다[^janxdevil].
두 반응은 같은 지점을 가리킨다.
저자의 불만 상당 부분은 에이전트가 동료처럼 팔리고 있다는 데서
생기는 기대 격차다.

### 기본값을 문제 삼는 글이다

HN에서 가장 많이 나온 반론은 이미 다 해결되었다는 것이었다.
johnfn은 하위 에이전트를 쓰라고 말하면 되고,
Haiku나 Sonnet을 하위 에이전트로 지정하면 되고, 멈추는 문제는 `/loop`로,
샌드박스는 수많은 스타트업 제품으로 풀린다고 항목마다 답했다[^johnfn].
그러면서 계획 전달은 개선될 여지가 있다고 인정했는데,
greggoB는 다 해결되었다면서 하나는 아니라는 것은 모순이라고 짚었다[^greggoB].

저자의 답은 일관되었다.
에이전트를 확장하고 고칠 수 있다는 것은 인정하지만,
대부분이 원할 기능이 기본 표준으로 없다는 것이 어리석다는 것이다[^mtlynch-3].
그는 BeetleB가 든 메모리 관리와 C의 비유[^BeetleB-2] 대신,
Go에 패턴 매칭이 없다고 하자 Go를 직접 패치해
포크를 유지하라고 답하는 상황이 더 정확하다고 반박했다.
이 대화가 글의 성격을 드러낸다.
이 글은 무엇이 가능한가가 아니라 무엇이 기본값이어야 하는가에 대한 주장이고,
기본값은 대부분의 사용자가 실제로 겪는 경험을 정한다.

### 원인 진단은 개발 도구 시장의 오래된 구조를 다시 꺼낸다

마지막 절의 주인-대리인 가설은 데모와 벤치마크가 구매 결정을
끌고 가는 시장 구조에 대한 이야기다.
모델 벤치마크는 공개 순위표가 있고 언론이 받아쓰지만,
에이전트가 하루에 개발자 시간을 몇 분 아끼는지는 순위표에 오르지 않는다.
측정되지 않는 품질에는 투자가 덜 간다는 것은
소프트웨어 산업에서 반복된 패턴이다.

Lobste.rs의 kornel은 다른 각도의 가설을 냈다.
최전선 연구소들은 하네스를 LLM과 bash를 잇는 어댑터로 보고,
하네스가 도울 수 있는 모든 것을 다음 모델에 강화학습으로 넣기를 바라므로
영리한 하네스 기능을 기대하기 어렵다는 것이다[^kornel].
hc도 비슷하게 큰 연구소들은 LLM이 계속 좋아질 테니
전통적 방식으로 에이전트를 짓는 것은 시간 낭비라는 가정을 하고,
모델이 몇 달마다 바뀌어 하네스가 매번 깨지는 현실도
지속 가능한 투자를 막는다고 적었다[^hc].
두 가설은 저자의 가설보다 구체적이다.
경영진이 개발자와 멀어서가 아니라,
모델에 걸린 투자가 하네스 투자를 일시적인 비용으로 보게 만든다는
설명이기 때문이다.

## 비평

### 사례 하나가 병렬화 주장을 약하게 만든다

저자가 병렬화 실패의 대표 사례로 든 OpenCode 화면은 반론에 취약하다.
HN의 eviks는 화면 속 작업 목록에
e2e 테스트 추가와 최종 검증 실행이 들어 있었다며,
최종 검증을 암호 문구 기능 추가와 병렬로 돌리는 것이
무슨 의미냐고 꼬집었다[^eviks].
10개 하위 작업 중 몇 개는 앞선 작업의 결과에 의존하는 것이 당연하다.
저자가 쉽게 병렬화할 수 있다고 부른
작업 목록이 정말 독립적이었는지 글은 보여 주지 않는다.

병렬화의 비용도 글에서는 거의 다뤄지지 않는다.
Lobste.rs의 kingmob은 하네스가 자동으로 병렬화하지 않는 이유로
세션 한도에 걸리기 쉽고, 메시지 전달과 조율과 충돌 해결에 순차 실행보다
토큰이 더 든다는 점을 들었다[^kingmob].
저자는 하나의 문맥에서 10개를 처리하는 쪽이
오히려 토큰을 더 쓰지 않느냐고 되물었고,
한도에 잘 걸리지 않는 자신 같은 사용자는 토큰을 더 쓰고
실제 시간을 줄이는 쪽을 기꺼이 택할 것이라고 답했다[^mtlynch-lobsters].
hyperpape는 그 답이 하위 에이전트에 의미 있는 문맥을
얼마나 잘 넘기느냐에 달려 있고,
주 에이전트가 이미 알아낸 것을 다시 찾아내는 일이 생기면
결과가 엇갈린다고 받았다[^hyperpape].
병렬화는 공짜 개선이 아니라 문맥 분할이라는 어려운 설계 문제이고,
글은 그 어려움을 단순한 게으름처럼 묘사한다.

### 모델 선택은 저자가 말하는 만큼 쉬운 문제가 아니다

저자는 작업 난이도를 매겨 모델을 고르는 일이야말로 LLM이 잘하는 일이라고 말한다.
HN의 hbrn은 작업이 얼마나 어려울지는 미리 알기 거의 불가능하고,
사람에게 쉬워 보이는 것도 모델에 없는 맥락을
사람이 갖고 있기 때문인 경우가 많다고 반박했다[^hbrn].
잘못 추측하면 하위 에이전트를 안 쓴 경우 문맥이 썩고, 쓴 경우 실행이 느려진다.
추측을 정확하게 하려고 작업마다 사전 조사를 시키면 더 느려진다.

여기에 신뢰 문제가 겹친다.
TeMPOraL은 공급사가 고른 모델을 믿을 수 있느냐,
공급사가 자기 부하 분산을 먼저 고려하지 않겠느냐고 물었다[^TeMPOraL].
자동 모델 선택은 비용을 줄이는 기능인 동시에,
공급사가 사용자 모르게 더 싼 모델로 바꿀 수 있는 손잡이이기도 하다.
저자가 바라는 대로
사용자가 비용과 속도와 정확성의 다이얼을 조절할 수 있어야 한다는 조건은 맞지만,
그 다이얼이 실제로 무엇을 바꾸는지 사용자가 검증할 방법이 없다면
자동화는 불신을 키운다.
ghboo0927은 난이도를 작업마다 추측하는 대신
역할별로 모델을 미리 정하는 편이 낫다고 제안했는데[^ghboo0927],
이것이 지금 기술로 가능한 현실적 절충에 더 가까워 보인다.

### 샌드박스 비판은 시점이 섞여 있다

글에서 가장 무거운 주장은 보안 쪽인데, 서술의 시점이 흐릿하다.
문서가 정중한 편지를 쓰라고 권했고
에이전트가 키를 유출했다는 이야기는 처음 에이전트를 쓰던 때의 일이다.
Lobste.rs의 codekobold는 Claude가 bubblewrap으로 OS 수준 샌드박스를 지원한다며
이 부분이 사실과 다르다고 지적했다[^codekobold].
저자는 그 인용문이 처음 에이전트를 쓴 2년 전 상황이지
지금을 묘사한 것이 아니라고 답했다[^mtlynch-lobsters-4].
본문에서 그는 첫 사용을 2025년 2월로 적었으므로 실제로는 2년이 채 안 된 일이다.

그러나 독자가 글을 읽으며 그 구분을 알아차리기는 어렵다.
같은 절에서 곧바로 지금도 에이전트는 모든 접근을 줘야 쓸 만하다고 쓰기 때문이다.
저자의 실제 현재 주장은 더 좁고 더 단단하다.
Claude Code의 샌드박스는 기본으로 꺼져 있고,
켜도 시스템 전체 읽기 권한을 갖고 시작해
읽지 말아야 할 경로를 사용자가
하나하나 나열해야 하며,
현재 디렉터리만 읽게 하는 설정조차
문서에서 찾기 어렵다는 것이다[^mtlynch-lobsters-3].
기본값이 최소 권한이 아니라는 이 주장만 본문에 남겼다면
반론의 여지가 훨씬 적었을 것이다.

샌드박스 경계 자체도 저자가 쓴 것보다 넓게 생각해야 한다.
HN의 dare944는 `.git` 디렉터리에 악성 스크립트를 떨어뜨리면 다음에
샌드박스 밖에서 git을 실행할 때 무슨 일이 생기는지 물어보라고 했다[^dare944].
그는 결국 에이전트에 `.git`을 읽기 전용으로만 준다고 적었다[^dare944-2].
저자의 샌드박스는 저장소 디렉터리 하나로 접근을 제한하지만,
공격 표면은 그 디렉터리 안에서 사람이 나중에 실행할 파일까지 포함한다.

### 소망 목록은 기본값의 범위를 스스로 넘는다

저자는 기본 상태에서의 동작을 요구한다고 분명히 했지만,
그 목록에는 서로 충돌하는 요구가 함께 들어 있다.
30분 동안 답이 없으면 스스로 결정하라는 요구와,
위험을 사람 손으로 통제하고 싶다는 보안 요구는
같은 에이전트 안에서 긴장 관계에 있다.
스스로 결정하는 에이전트가 어디까지 결정해도 되는지는
샌드박스 경계만으로 정해지지 않는다.
브랜치 이름은 혼자 정해도 되지만,
데이터 마이그레이션 방식은 혼자 정하면 안 될 수 있다.

HN의 athrowaway3z[^athrowaway3z]와 BeetleB[^BeetleB],
Lobste.rs의 abarbu는 Pi의 확장으로 목록 대부분이 이미 존재한다고 반박했다.
abarbu는 목표 모드, 상태 UI, 도커 샌드박스, 환경 변수 기반 비밀 프록시,
한도와 비용 기반 모델 라우팅 확장을 하나씩 링크하고,
빠진 것은 자기 세션을 돌아보는 기능 정도라고 적었다[^abarbu].
저자는 Pi가 기본으로 맞추는 것은
자기 기능을 아는 것 하나뿐이라고 답했다[^mtlynch-2].
이 논쟁은 결론이 나지 않았지만, 저자의 기본값 요구가 얼마나 넓은지 보여 준다.
오픈소스이고, 모든 공급자를 지원하고,
한도와 ETA와 비용을 모두 관리하는 에이전트를 기본 설정 그대로 원한다면,
그것은 기본값이 아니라 의견이 강한 하나의 제품이다.
그리고 의견이 강한 제품은 다른 사람의 흐름에는 맞지 않을 가능성이 크다.

## 인사이트

### 에이전트가 병렬화를 배우면 비용은 공유 자원으로 옮겨 간다

저자는 에이전트가 병렬로 일하기를 바라지만,
그 바람이 이루어졌을 때 무슨 일이 생기는지는 HN의 kgeist가 실제로 겪었다.
그는 사무실에서 Qwen 3.6을 돌리는 LLM 서버를 서너 명이 함께 쓰는데,
가끔 요청 대기열이 넘쳐 20~30분 동안 아무것도 못 하는 일이 생겼다.
원인을 찾아보니 한 직원이 쓰던 QwenCode가
같은 모델로 하위 에이전트를 6개쯤 동시에 띄우고 있었고,
OpenCode는 같은 모델로 기본적으로 순차 TODO 목록을 썼다.
결국 서버 쪽에서 QwenCode를 감지해
병렬 요청을 하나의 대기열로 직렬화해야 했다[^kgeist].

이 사례는 저자의 소망이 개인 사용자의 관점이라는 점을 드러낸다.
구독 한도 안에서 토큰을 더 써 시간을 줄이는 것은 개인에게 합리적이지만,
연산 자원이 공유되는 순간 한 사용자의 병렬화는 다른 사용자의 대기 시간이 된다.
과거 공유 서버에서 `make -j`의 값을 놓고 벌어지던 갈등과 같은 구조다.
에이전트의 기본값이 병렬로 바뀌면,
그 비용은 조직 단위의 할당량과 대기열 정책으로 옮겨 간다.
공급사가 병렬화를 기본값으로 두지 않는 이유 중 하나는
바로 자기 서버가 그 공유 자원이기 때문일 수 있다.
이것은 원문에 없는 해석이다.

### 모델이 자기 하네스를 모르는 것은 구조적이다

자기 기능을 모른다는 불만에 대한 HN의 반응은 두 갈래였다.
jwstillwater는 Claude Code 사용법을 묻는 질문이
시스템 프롬프트의 Academy 스킬을 호출해
문서를 가져오도록 되어 있어 의도된 동작이며,
웹 접근을 끄면 Claude도 내부 지식으로 답한다고 설명했다[^jwstillwater].
jaggederest는 모델의 학습 시점이 하네스보다 최소 몇 달 늦으므로
모델이 자기 하네스를 아는 것은 정의상 불가능하다고 적었다[^jaggederest].
저자는 모델이 최신 기능을 학습하길 기대하는 것이 아니라,
하네스가 자기 문서를 함께 배포해 로컬에서
빠르게 찾고 버전이 맞도록 하라는 것이라고 답했다[^mtlynch].
그리고 이것은 자기 불만 중 가장 사소한 것이라고 덧붙였다[^mtlynch-4].

이 교환은 모델과 하네스의 출시 주기가 다르다는 구조적 사실을 보여 준다.
하네스는 매주 바뀌고 모델은 몇 달에 한 번 바뀐다.
그러면 하네스에 대한 지식은 학습이 아니라 실행 시점의 문맥으로만 전달될 수 있고,
그 문맥을 무엇으로 채울지가 하네스 설계의 일이 된다.
운영체제가 `man` 페이지를 바이너리와 함께 배포해 온 이유와 같다.
문서를 원격에 두면 항상 최신이지만 설치된 버전과 어긋나고,
로컬에 두면 버전은 맞지만 공급사가 문서 갱신 주기를 배포 주기에 묶어야 한다.
jonaustin이 지적했듯 Pi는 처음부터 문서를 함께 담았다[^jonaustin].
저자의 요구는 작지만,
그것이 표준이 되지 않은 이유는 공급사가 문서를
제품의 일부가 아니라 웹사이트의 일부로 보기 때문이라고 해석할 수 있다.

### 경험의 격차는 모델 세대만큼 하네스 버전에서도 생긴다

HN에서 mstank는 이 글에 꽤 공감했지만 최근 3~4개월은 그렇지 않았다며,
최신 모델들이 여러 작업을 다루고 위임도 잘한다고 적었다[^mstank].
361994752는 같은 OpenCode를 쓰는데
하위 에이전트를 병렬로 띄우는 기능이 이미 있다고 했고,
저자는 자신의 OpenCode에서는 2~3개를 띄우고 다 끝날 때까지 기다리며,
하위 에이전트가 죽으면 정보를 가져오지 못한다고 답했다[^mtlynch-5].
그러자 361994752는 자신이 OpenCode v2를 쓴다고 밝혔고[^361994752],
lloeki는 v2가 백그라운드 셸과 하위 에이전트 관리가 훨씬 나아져
비동기로 띄우고 대화를 막지 않는다고 거들었다[^lloeki].

같은 이름의 에이전트를 쓰면서도
버전과 모델 조합에 따라 정반대의 경험을 하는 셈이다.
이것은 이 분야의 평가가 왜 그렇게 극단으로 갈리는지를 설명한다.
누군가의 불만 글과 누군가의 반박은
서로 다른 제품을 놓고 이야기하고 있을 가능성이 크다.
에이전트에 대한 글을 읽을 때는 모델 이름뿐 아니라 하네스 이름과 버전,
그리고 사용자가 어떤 설정을 기본으로 여기는지를 함께 확인해야 한다.
저자의 글도 날짜가 붙은 관찰 기록으로 읽을 때 가장 정확하다.

### 계획 문서의 품질은 모델이 아니라 출력 계약의 문제다

저자가 계획을 읽지 않게 된 이유를 게으름이 아니라
계획의 전달 방식에서 찾은 것은 이 글에서 가장 날카로운 관찰이다.
에이전트가 쓰는 계획은 사람을 위한 문서가 아니라
자기 실행을 위한 작업 메모에 가깝다.
그래서 결정 사항이 중요도 순서 없이 나열되고, 큰 그림이 빠진다.
이 저장소의 `agentic-coding/plan-mode-is-dead.md`가
계획하기와 계획서는 다른 것이었다고 정리한 것도 같은 지점이다.

HN의 cbrake는 계획보다 문서를 먼저 고친다고 했다.
에이전트와 함께 사용자 문서를 먼저 수정하면
변경이 사용자에게 어떻게 보일지 구현 전에 알 수 있다는 것이다[^cbrake].
Lobste.rs의 laurentbroy는 반대 방향의 문제를 짚었다.
에이전트에 메모를 파일로 남기게 하면 메모 품질이 낮고,
한 세션이 쓴 나쁜 형식을 다음 세션이 관례라며 그대로 따라 해
오류가 쌓인다는 것이다[^laurentbroy].
두 반응을 합치면 원칙이 하나 보인다.
에이전트가 쓰는 텍스트는 독자가 누구인지 정해 주지 않으면
자기 자신을 독자로 삼는다.
사람이 읽을 계획이 필요하다면 그것은 기본값이 저절로 고쳐 줄 문제가 아니라,
UI 변경부터 쓰라거나 데이터 모델부터
쓰라는 식으로 출력 형식을 계약으로 정해야 하는 문제다.
저자가 소망 목록에 넣은 UI 목업과 데이터 흐름도와 의사결정 트리는
바로 그 계약의 후보들이다.
