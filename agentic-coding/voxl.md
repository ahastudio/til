# voxl: GPU 없는 VM과 샌드박스의 데스크톱을 브라우저 탭으로 60 FPS에 보내는 Rust 서버

<https://github.com/tembo/voxl>

HN 토론: <https://news.ycombinator.com/item?id=50356056> (5점, 0개 댓글)

GN 토론: <https://news.hada.io/topic?id=36682>

## 소개

voxl은 tembo 조직이 공개한 Rust 원격 데스크톱 스트리밍 서버다.
저장소 설명은 극도로 빠른 웹 원격 데스크톱 스트리밍이라고 한다.
X11 디스플레이, Mac 화면, Windows 데스크톱을 H.264로 인코딩해
WebSocket 하나로 보내고, 작은 웹 클라이언트가 WebCodecs로 디코딩한다.
입력, 클립보드, 오디오, 마이크, 파일과 폴더 전송, 동적 해상도를 지원한다.

2026년 11월 6일 기준 GitHub 정보는 다음과 같다.
MIT 라이선스이고 2026년 6월 18일에 만들어졌으며
스타 1,216개, 포크 60개, 열린 이슈 16개다.
마지막 푸시가 이 날짜의 오전이라 개발이 계속 움직이고 있다.
토픽에 `ai-agents`, `computer-use`, `sandbox`, `software-factory`가 있다.
crates.io에는 `voxl-server`라는 이름으로 올라 있고 바이너리 이름은 `voxl`이다.

목표 사용처는 README의 비교 설명에서 읽힌다.
개발사는 GPU 없이 Xvfb 위에서 도는 헤드리스 VM과 샌드박스,
즉 CI와 컴퓨터 사용(computer-use) 에이전트를 위한 도구라고 말한다.
게임용 GPU 머신을 위한 Moonlight와 Sunshine,
자기 컴퓨터에 닿기 위한 RustDesk와는 용도가 다르다는 것이다.

## 빠르게 띄워 보기

Linux에서는 X 디스플레이 번호만 주면 된다.

```sh
cargo install voxl-server   # x264, libyuv, Opus, PulseAudio, esbuild 필요
DISPLAY=:1 voxl             # :1 을 스트리밍하고 로그인 링크를 출력
```

출력되는 링크를 열면 비밀번호가 토큰으로 들어 있어 바로 로그인된다.
Mac과 Windows에서는 `DISPLAY` 없이 그 기계의 화면을 스트리밍한다.
README는 `nix-shell`이 빌드 의존성을 모두 제공한다고 한다.
부드러운 스크롤을 원하면 Xvfb를 `-shmem`으로 띄우고
저장소가 제공하는 패치된 Xvfb를 쓰라고 한다.

## 개발사가 내놓은 벤치마크

개발사는 모든 테스트에서 voxl이 평균 60 FPS를 내고
지연 중앙값이 12~99 ms라고 한다.
같은 조건의 noVNC는 평균 8 FPS 미만이라고 한다.
환경은 GPU 없는 16 vCPU AMD EPYC 9334 VM이고
데스크톱은 2560x1600 Xvfb다.
각 스트림을 네이티브 클라이언트로 디코딩하면서
화면에 그린 픽셀 표식을 읽어 지연을 잰다.
지연은 내용이 그려진 순간부터 프레임이 디코딩된 순간까지이고
셀은 FPS(최악의 1초)와 지연 p50/p99다.
README는 voxl 열이 각 테스트에서 가장 좋았던 실행이라고 밝힌다.

아래는 일곱 개 테스트 중 네 개를 골라 다섯 제품만 옮긴 것이다.

| 테스트                         | voxl            | selkies         | KasmVNC          | Sunshine, tuned  | noVNC           |
| ------------------------------ | --------------- | --------------- | ---------------- | ---------------- | --------------- |
| Chromium 스크롤, LAN           | 60.1, 55/60 ms  | 56.8, 85/106 ms | 51.7, 99/135 ms  | 48.5, 94/117 ms  | 6.7, 198/301 ms |
| 스크롤, 5 Mbps / 60 ms RTT     | 60.1, 99/109 ms | 27.9, 2.7/3.7 s | 4.9, 306/415 ms  | 44.5, 164/191 ms | 1.6, 637/937 ms |
| 1080p 애니메이션, LAN          | 60.1, 12/16 ms  | 58.7, 31/48 ms  | 56.7, 51/82 ms   | 45.6, 42/57 ms   | 7.7, 149/210 ms |
| 애니메이션, 5 Mbps / 60 ms RTT | 60.0, 66/92 ms  | 18.4, 2.2/4.3 s | 34.1, 104/156 ms | 45.5, 114/131 ms | 5.1, 174/240 ms |

서버 CPU는 X 서버와 스트리머를 합쳐 코어 단위로 잰다.
voxl은 화면이 멈춰 있으면 0.00 코어이고,
1080p 애니메이션 1.39, 스크롤 1.33, 전체 화면 1.68 코어를 쓴다.
Sunshine tuned는 같은 세 작업에서 3.07, 3.14, 3.22 코어를 쓰고
화면이 멈춰 있어도 2.84 코어를 쓴다.
다만 README 자신이 밝히듯 Sunshine의 CPU는 나중 세션에서 쟀고,
그 세션에서 voxl은 같은 작업에 1.74, 1.65, 1.99 코어를 썼다.

## 동작 방식과 설계 선택

README의 FAQ가 이 서버의 설계 선택을 직접 설명한다.

WebSocket을 쓰는 첫째 이유는 도달 범위다.
WebSocket 하나는 리버스 프록시, 터널, 샌드박스 미리보기 URL을 통과하고
TURN 서버나 UDP 포트를 열 필요가 없다.
둘째 이유는 지연이다.
브라우저가 프레임을 받는 즉시 WebCodecs로 디코딩해
WebRTC의 지터 버퍼를 거치지 않고, 속도 제어(rate control)도 직접 한다.
개발사가 인정하는 대가는 TCP다.
패킷이 유실되는 링크에서는 앞선 패킷 하나가 뒤따르는 프레임을 붙잡아 두고,
WebRTC는 건너뛸 수 있다.

기본 인코딩은 CPU의 x264이고 프리셋은 `ultrafast`, 기본 품질은 `--crf=24`다.
비트레이트는 2,000~30,000 kbps 사이에서 적응한다.
화면이 멈추면 `--paintover-crf=16`으로 다시 선명하게 그린다.
GPU 인코딩은 아직 없고 macOS용 하드웨어 인코딩이 진행 중이라고 한다.
화면 변경 영역은 XDamage(Linux), ScreenCaptureKit(Mac),
DXGI(Windows)가 알려 주며,
그래서 정지한 화면은 CPU를 쓰지 않는다.
Wayland는 아직 지원하지 않고 작업 중이라고 한다.

## 에이전트와 스크립트용 API

일반 원격 데스크톱과 다른 부분이 이 인터페이스다.
`VOXL_PASSWORD`를 설정하고 HTTP로 접근한다.

```sh
# 현재 화면을 PNG로
curl -u ":$VOXL_PASSWORD" -o shot.png localhost:6901/screenshot
# 앞으로 10초를 MP4로
curl -u ":$VOXL_PASSWORD" -o clip.mp4 "localhost:6901/record?seconds=10"
# 화면이 300 ms 동안 변하지 않을 때까지 기다림
curl -u ":$VOXL_PASSWORD" localhost:6901/wait
# 직전 스크린샷 이후의 첫 변화를 기다림
curl -u ":$VOXL_PASSWORD" "localhost:6901/wait?change&since=812"
```

녹화는 뷰어에게 이미 보내는 H.264를 다시 인코딩하지 않고 MP4로 담으므로
추가 CPU가 들지 않는다.
커서는 뷰어가 그리기 때문에 녹화에 없고, 해상도가 바뀌면 녹화가 끝난다.

`/wait`는 에이전트가 동작마다 얼마나 기다릴지 추측하지 않게 하려는 것이다.
`idle`은 화면이 가만히 있어야 하는 시간(기본 300 ms),
`timeout`은 포기 시점(기본 10,000 ms)이고,
`region=x,y,w,h`는 16픽셀 블록 단위로 사각형만 지켜본다.
`since`에 이전 `/wait`의 `seq`나 스크린샷의 `X-Voxl-Seq` 헤더 값을 주면
요청보다 먼저 일어난 변화도 놓치지 않는다.
깜빡이는 텍스트 커서는 초당 두 번쯤 화면을 다시 그리므로
`idle`을 500 ms 아래로 두거나 커서를 `region` 밖에 둬야 한다.

## 운영 체제별 차이와 제약

README가 밝힌 조건을 표로 모으면 다음과 같다.

| 항목      | 내용                                                                     |
| --------- | ------------------------------------------------------------------------ |
| Linux     | X11만 지원한다. Xvfb 포함. Wayland는 아직이다.                           |
| macOS     | ScreenCaptureKit, CGEvent 사용. 화면 기록과 손쉬운 사용 권한을 요구한다. |
| Windows   | 10 이상. DXGI 캡처. 서비스가 아니라 사용자 세션에서 실행해야 한다.       |
| 마이크    | Mac은 loopback 장치(BlackHole), Windows는 가상 오디오 케이블이 필요하다. |
| 브라우저  | WebCodecs가 있어야 한다. Android용 Firefox는 안 된다.                    |
| 접속 주소 | WebCodecs는 HTTPS 페이지나 localhost에서만 열린다.                       |

다른 기계에서 보려면 TLS 프록시(Caddy, Cloudflare Tunnel,
`tailscale serve`) 뒤에 두고
`--allowed-hosts`로 호스트 이름을 알려 주거나,
SSH로 포트를 전달해 localhost로 연다.
Mac과 Windows에서는 화면 전체가 노출되므로 기본 수신 주소가 `127.0.0.1`이다.
라이선스는 코드가 MIT지만 GPL-2.0인 x264를 링크하므로,
voxl 바이너리와 그것을 포함하는 모든 것은 GPL로 배포된다고 한다.

## 비평

### 벤치마크의 비교 조건은 개발사가 정했다

모든 실행과 설정을 개발사가 했고, voxl 열은 최고 실행값이다.
다른 제품이 몇 번 실행되어 어느 값이 표에 올랐는지는 본문에 없다.
Sunshine은 GPU 캡처와 인코딩을 전제로 만들어졌는데 GPU 없는 VM에서 쟀고,
개발사도 이 수치가 게임용 PC에서의 성능이 아니라고 적었다.
Neko와 Sunshine은 자기 설정을 voxl과 비슷하게 맞춘 tuned 열을 따로 두었고
이는 공정하게 보이려는 노력이다.
그래도 비교 대상의 튜닝은 voxl을 만든 쪽의 지식 범위 안에서 이루어졌다.
README가 Sunshine CPU를 나중 세션에서 쟀고 그때 voxl 수치가 높았다고 밝힌 것은
정직한 공개지만, 표의 voxl 숫자가 가장 좋은 쪽이라는 뜻이기도 하다.
같은 세션 수치로 보면 voxl 1.74 대 Sunshine tuned 3.07 코어로 격차는 여전하지만
좁아진다.

### 패킷 유실이 없는 링크만 쟀다

느린 링크 테스트는 대역폭과 지연만 바꾸고 패킷을 버리지 않는다.
README의 설명으로는 UDP 기반 제품이 오류 정정으로 유리해질 조건을 뺀 것이다.
그런데 개발사 스스로 FAQ에서 TCP 기반 WebSocket의 약점을 유실 링크로 꼽는다.
불안정한 Wi-Fi나 약한 모바일 신호에서 60 FPS가 유지되는지는
이 벤치마크로는 알 수 없다.
이 문서의 해석으로는, 사람이 모바일에서 샌드박스를 들여다보는 사용에서는
이 빠진 조건이 오히려 중요할 수 있다.

### 측정하지 않은 것이 결론에 닿아 있다

측정값은 FPS와 지연뿐이다.
화면의 선명도는 비교하지 않았다.
voxl은 `crf` 24에 멈춘 화면을 `crf` 16으로 다듬는 설정을 쓰고,
KasmVNC는 JPEG/WebP 품질 8~9를 쓴다.
같은 FPS와 지연에서 화질이 다르면 다른 비용을 치르는 것이다.
지연은 내용이 그려진 뒤 프레임이 디코딩될 때까지이므로
이 문서가 읽은 바로는 입력을 누른 순간부터 화면에 반영될 때까지의 지연이 아니다.
작업도 스크롤과 애니메이션이라는 합성 부하이고 글자를 치는 상황은 없다.

### 기본값의 노출 범위가 넓다

README 기준 기본값은 비밀번호 로그인이 켜져 있고
파일 업로드와 다운로드가 모두 허용되며,
`--files-root`는 사용자의 홈 폴더이고 업로드 크기 제한이 없으며,
서버는 평문 HTTP로 서비스한다.
README는 localhost를 벗어나면 TLS 뒤에 두라고 하고 SECURITY.md를 안내한다.
이 문서는 SECURITY.md와 소스를 열어 보지 않았으므로
위협 모델이 충분한지는 판단하지 못한다.
확인할 수 있는 것은 처음 띄운 사람이 로그인 링크와 홈 폴더 접근을
함께 얻는다는 사실이다.

### 아직 어린 프로젝트다

저장소는 4개월 남짓 되었고 `--stripes`는 실험적 기능이라고 표시되어 있다.
GPU 인코딩, Wayland, Android Firefox는 지원하지 않는다.
이 문서는 코드를 실행해 보지 않았고,
위 수치는 모두 개발사의 보고다.

## 인사이트

### 이 서버의 새로움은 화면을 이벤트 스트림으로 다룬다는 데 있다

일반 컴퓨터 사용 에이전트 루프는 동작한 뒤 얼마간 기다리고 스크린샷을 찍는다.
기다리는 시간은 대개 추측이다.
voxl은 이미 보내고 있는 화면 변경 정보로 `/wait`를 제공한다.
같은 신호가 정지 화면의 CPU 0.00 코어를 만들고 에이전트의 대기 신호도 만든다.
`since`로 순번을 넘기면 동작 직전과 직후의 경합까지 닫힌다.
이 문서의 해석으로는 관찰, 동작, `wait(since=seq)`가 하나의 루프이고,
지연 단축보다 이 대기 단위의 신뢰성이 에이전트에게는 더 큰 가치일 수 있다.

### 선택의 핵심은 화질이 아니라 도달 범위다

README가 WebSocket을 고른 첫째 이유는 지연이 아니라
프록시와 미리보기 URL을 통과한다는 점이다.
샌드박스가 클라우드 공급자의 미리보기 프록시 뒤에 있으면
UDP와 TURN을 쓰는 방식은 배포 자체가 어렵다.
그러므로 WebRTC 제품 대비 이점이 평가되어야 하는 곳은
FPS 표보다 배포 환경이다.
반대로 운영자가 UDP를 열 수 있는 사내망이라면 이 이점은 줄어든다.

### 결론을 바꿀 관찰

패킷을 2~5% 버리는 링크에서 voxl과 WebRTC 계열을 같은 부하로 비교한
결과가 나오면
TCP 선택의 대가가 드러난다.
`bench/`를 내 VM에서 재현했을 때 voxl 열의 최고 실행값과 중앙 실행값이
크게 다르면
표의 신뢰도는 낮아진다.
SECURITY.md가 홈 폴더 노출 기본값을 어떻게 설명하는지도 아직 열어 보지 않았다.
