# Cursor의 에이전트 하네스 개선법: 두 겹의 측정, 오류 분류, 모델별 맞춤 설정

원문: [에이전트 하네스를 지속적으로 개선하기 · Cursor](https://cursor.com/ko/blog/continually-improving-agent-harness)

HN 토론: <https://news.ycombinator.com/item?id=48017596> (3점, 0개 댓글)

## 요약

Cursor의 Stefan Heule과 Jediah Katz가 2026년 4월 30일에 쓴 9분 분량의 조사
글이다.
Cursor는 에이전트 하네스를 다른 야심 찬 소프트웨어 제품과 같은 방식으로 만든다고
한다.
이상적인 에이전트 경험이 어때야 하는지의 비전에서 출발해 가설을 세우고, 실험으로
검증하고, eval과 실제 사용량의 정량 신호와 정성 신호로 반복 개선하는데, 이는
온라인과 오프라인 계측에 달려 있다.
새 모델의 early access를 받으면 몇 주에 걸쳐 모델의 강점에 맞게 하네스를 맞춤
설정하고, 때로 도약적 개선을 발견하지만 대부분은 작은 최적화를 집요하게 쌓는
일이라고 한다.

컨텍스트 윈도우 관리는 크게 변했다.
2024년 말 처음 코딩 에이전트를 만들 때는 모델이 스스로 알맞은 컨텍스트를 고르는
능력이 훨씬 약했다.
그래서 수정할 때마다 lint와 타입 오류를 보여 주고, 너무 적은 줄만 요청하면 파일
읽기 요청을 다시 구성하고, 한 턴에 부를 수 있는 도구 수에 상한을 두었으며, 세션
시작 때 코드베이스의 폴더 배치와 의미적으로 맞는 코드 조각과 사용자가 붙인
파일의 압축본 같은 정적 컨텍스트를 줬다.
이런 방식은 대부분 사라졌고 지금은 운영 체제, git 상태, 현재 파일과 최근 본 파일
같은 정적 컨텍스트만 남겼으며, 모델 성능이 높아지면서 가드레일은 줄이고
에이전트가 작업 중에 가져올 동적 컨텍스트를 늘렸다.

변경의 평가는 두 가지다.
공개 벤치마크와 자체 eval 스위트 CursorBench로 빠르고 표준화된 품질을 보고, 실제
사용 환경에서 둘 이상의 하네스 변형을 나란히 배포해 A/B 테스트한다.
온라인 지표는 지연 시간, 토큰 효율, 도구 호출 횟수, 캐시 적중률이 명확한 편이고,
일을 잘했는지는 두 방식으로 잰다.
하나는 에이전트가 제안한 코드 변경 가운데 일정 시간 뒤에도 사용자의 코드베이스에
그대로 남은 비율인 Keep Rate이고, 다른 하나는 언어 모델로 에이전트의 초기 출력에
대한 사용자의 반응을 읽어 의미적 만족을 잡는 것이다.
사용자가 다음 기능으로 넘어가면 제 역할을 한 신호이고 스택 트레이스를 붙여
넣으면 그렇지 않은 신호다.
컨텍스트 요약에 더 비싼 모델을 시도했지만 눈에 띄는 차이가 없어 접은 사례가
소개된다.

성능 저하의 추적은 도구 호출 오류 관리다.
도구 호출 오류는 컨텍스트에 남아 토큰을 낭비하고, 누적된 실수가 이후 판단 품질을
떨어뜨리는 컨텍스트 부패를 일으킨다.
원인을 알 수 없는 오류는 모두 하네스의 bug로 취급하고, 예상된 오류는 원인별로
분류한다.
InvalidArguments와 UnexpectedEnvironment는 모델의 실수와 컨텍스트 안의 모순을,
ProviderError는 GenerateImage나 WebSearch 같은 도구의 벤더 장애를, 그 밖에
UserAborted와 Timeout 등이 있다.
도구별로 unknown error rate가 고정된 임계값을 넘으면 경보를 내고, 예상된 오류가
도구별 모델별 기준선을 크게 웃돌면 이상 탐지 경보가 울린다.
주간 자동화는 스킬을 가진 모델이 로그를 검색해 새로 생기거나 급증한 문제를 찾아
백로그 티켓을 만들거나 갱신하고, 클라우드 에이전트로 많은 수정을 한꺼번에
시작하며 Linear에서 직접 트리거할 수도 있다.
올해 초의 집중 스프린트에서 예상치 못한 도구 호출 오류를 한 자릿수 규모만큼
줄였다고 한다.

하네스의 모든 추상화는 특정 모델에 종속되지 않고 각 모델에 맞게 맞춤 설정한다.
OpenAI 모델은 패치 기반 형식으로 파일을 고치도록 학습되었고 Anthropic 모델은
문자열 교체 방식으로 학습되어서, 익숙하지 않은 도구는 추가 reasoning 토큰과
실수를 부르므로 각 모델이 학습한 도구 형식을 제공한다.
OpenAI 모델은 지시를 더 문자 그대로 정밀하게 따르고 Claude는 더 직관적이어서
불명확한 지시에도 유연하다고 한다.
한 모델에서는 컨텍스트가 차오를수록 작업을 거부하고 과제가 너무 크다며
머뭇거리는 context anxiety가 보였고 프롬프트 조정으로 줄였다.
채팅 도중 모델을 바꾸면 다른 모델이 만든 대화 기록(자신의 분포 밖)을 이어받는
문제와, 캐시가 프로바이더와 모델마다 달라 첫 턴이 느려지고 비싸지는 문제가
생긴다.
전환 시점에 대화를 요약하는 방식을 실험했지만 깊은 작업에서는 중요한 정보가 빠질
수 있어, 특별한 이유가 없다면 같은 모델을 계속 쓰기를 권한다.
대안은 새 컨텍스트 윈도우에서 시작하는 하위 에이전트이고, 사용자가 특정 모델로
하위 에이전트를 직접 실행해 달라고 요청하는 기능을 추가했다.
글은 AI 지원 소프트웨어 엔지니어링의 미래가 멀티 에이전트이고, 어떤 에이전트를
투입하고 작업을 어떻게 구성하고 결과를 일관된 워크플로로 엮을지의 조율이
하네스의 과제라고 맺는다.

## 분석

### 글의 핵심 주장은 하네스가 모델과 함께 성능을 좌우하는 제품이라는 것이다

글은 하네스를 모델 주변의 얇은 포장이 아니라 계측과 실험으로 개선하는 소프트웨어
제품으로 다룬다.
같은 모델이 특별히 튜닝된 하네스 안에서 더 빠르고 똑똑하고 효율적으로 작동한다는
서술이 이 입장을 요약한다.
도약적 개선은 가끔이고 대부분은 작은 최적화의 누적이라는 인정도 이 입장의
일부다.
이는 모델 중심의 논의에서 하네스의 몫을 분리해서 보게 하는 주장이다.

### 가드레일을 줄이고 동적 컨텍스트를 늘린 방향이 모델 능력에 따라 움직인다

2024년 말의 가드레일(오류 표시, 읽기 요청 재구성, 도구 수 상한)과 정적
컨텍스트가 대부분 사라졌다는 서술은 하네스의 구조가 모델 능력에 종속된다는
뜻이다.
모델이 스스로 컨텍스트를 고를 수 있게 되자 하네스가 대신 고르던 것을 거두었다.
Cursor의 하네스 역사는 규칙이 모델이 약할 때 필요했다가 강해지면 짐이 된다는
사례다.
이는 이 문서의 해석이다.

### 평가의 두 겹이 서로의 맹점을 가린다

벤치마크는 빠르지만 실제 사용의 근사일 뿐이고, 온라인 A/B는 실제를 보지만 지표가
모호하다.
Keep Rate와 언어 모델의 만족 판독은 이 모호함을 메우는 장치다.
각 장치의 약점(Keep Rate는 사용자가 다른 이유로 코드를 지울 수 있고, 만족 판독은
모델의 해석에 달려 있음)은 글이 다루지 않는다.

## 비평

### 개선의 증거는 서술이고 수치는 거의 없다

글은 오류를 한 자릿수 규모만큼 줄였다고 하지만 비율이 아니라 규모의 서술이어서
줄어든 정도를 알 수 없다.
같은 하네스에서 모델이 눈에 띄게 낫다는 주장과 도약적 개선도 근거가 되는 수치나
도표가 없다.
CursorBench의 구성과 Keep Rate의 값, A/B의 효과 크기는 이 문서가 읽은 범위에서
공개되지 않았다.
이는 제품 개선 글의 일반적 한계지만 독자는 이 글에서 방법의 구조를 배울 수
있어도 효과의 크기를 배울 수는 없다.

### 모델별 맞춤 설정의 비용이 이야기되지 않는다

모든 지원 모델에 맞춰 도구 형식과 프롬프트와 모델 버전별 지침을 따로 두는 일은
모델 수와 버전 수에 곱해지는 유지 비용이다.
새 모델을 몇 주 동안 튜닝한다는 서술은 이 비용이 인력과 시간임을 시사한다.
작은 팀이 같은 방식을 따를 수 있는지, 어디까지 줄여도 효과가 남는지는 글에 없다.

### 모델 제작사의 학습 형식에 하네스가 묶이는 것을 장점으로만 서술한다

OpenAI 모델에는 패치 형식을, Anthropic 모델에는 문자열 교체 형식을 주는 것은
학습 분포에 맞추는 합리적 선택이다.
그러나 이 선택은 하네스가 제작사의 학습 방식 변화에 따라 계속 바뀌어야 함을
뜻하고, 제작사가 도구 형식을 바꾸면 하네스의 최적점도 이동한다.
글은 이 의존의 위험을 말하지 않는다.

### 모델 전환의 권고가 자기 기능의 가치와 어긋난다

글은 채팅 도중 모델을 바꾸는 기능을 지원하지만 특별한 이유가 없다면 같은 모델을
계속 쓰라고 권한다.
전환은 캐시 미스와 요약 손실을 부르기 때문이다.
기능을 지원하면서 그 기능을 쓰지 말라고 하는 것은 솔직하지만, 사용자에게는
기능의 적절한 사용 시점이 불분명하다.
하위 에이전트로 우회하는 안이 대안으로 제시되지만 그 비용과 효과는 다루지
않는다.

## 인사이트

### 하네스의 품질은 오류를 분류하는 어휘에서 갈린다

Cursor는 오류를 원인을 알 수 없는 것과 예상된 것으로 나누고, 예상된 오류를
InvalidArguments, UnexpectedEnvironment, ProviderError, UserAborted, Timeout으로
나눈다.
이 분류는 이 오류가 하네스의 bug인지 모델의 실수인지 벤더의 장애인지를 가르는
어휘이고, 어떤 경보가 사람을 깨울지를 정한다.
오류 분류가 없으면 모든 오류가 같은 소음이고, 있으면 기준선에서 벗어난 것만
신호가 된다.
에이전트 제품에서 가장 먼저 만들어야 할 것이 오류의 어휘라는 점이 이 글의 가장
이식 가능한 교훈이다.
이는 이 문서의 해석이다.

### 에이전트의 개선 루프를 에이전트에게 맡기는 구조가 소프트웨어 공장이다

주간 자동화가 로그를 검색해 새 문제를 찾고 티켓을 만들고 클라우드 에이전트가
수정을 시작하는 흐름은 하네스 개선을 에이전트가 돕는 구조다.
글이 이를 자동화된 소프트웨어 공장이라 부르는 것은 개선의 병목이 발견과 분류에서
수정의 승인으로 옮겨 간다는 뜻이다.
사람의 몫은 어떤 수정을 받아들일지의 판단이고, 앞의 오류 분류가 그 판단의 근거가
된다.

### 컨텍스트 부패라는 이름이 도구 오류의 비용을 설명한다

글은 도구 호출 오류가 컨텍스트에 남아 토큰을 낭비하고 누적된 실수가 이후 판단
품질을 떨어뜨린다고 설명한다.
같은 주에 나온 Drew Breunig의 컨텍스트 관성과 오염 이야기와 맞닿는다.
오류가 일시적 실패가 아니라 이후 모든 단계에 영향을 주는 오염이라면, 오류율은
비용 지표 이상의 품질 지표다.
이 연결은 이 문서의 해석이며, 두 글은 서로를 인용하지 않는다.

### 하네스가 오케스트레이션을 맡는다는 전망은 모델이 아닌 조율의 가치를 키운다

글은 멀티 에이전트의 조율, 곧 어떤 에이전트를 투입하고 작업을 어떻게 구성하고
결과를 어떻게 엮을지가 하네스의 과제라고 한다.
모델이 서로 비슷해질수록 차별점은 이 조율에 옮겨 간다는 뜻이다.
그러나 조율의 품질을 평가하는 지표는 아직 이 글에 없다.
Keep Rate는 개별 변경 단위의 지표이고 워크플로 단위의 지표가 필요하다.

### 이 글을 읽는 방법

이 문서는 Cursor의 한국어 블로그 글 본문을 읽고 정리했다.
글이 언급하는 이전 게시물과 CursorBench는 열어 보지 못했다.
HN 스레드(3점, 댓글 없음)에는 인용할 반응이 없었고 Lobste.rs와 GeekNews에서도 이
글의 스레드는 찾지 못했다.
판단을 가를 관찰은 둘이다.
하나는 하네스 변형 A/B에서 Keep Rate와 만족 판독이 CursorBench 점수와 같은
방향으로 움직이는지다.
다른 하나는 모델 전환 때 요약을 쓴 경우와 쓰지 않은 경우의 이후 Keep Rate
차이다.
둘 다 이 문서가 확인하지 못했다.
