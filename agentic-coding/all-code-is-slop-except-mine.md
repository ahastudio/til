# 에이전트 코드를 믿게 만드는 린트와 검증

영상: [All Code Is Slop (Except Mine) — Lauren Tan, SpaceXSI](https://www.youtube.com/watch?v=O_zcc6Xl12g)

## 요약

AI Engineer 채널에 2026년 11월 14일 올라온 약 17분 발표이다.
영상의 화면(슬라이드, 코드, 짧은 시연 영상)은 보지 않았고, 자동 자막의 고유명사는 영상 설명과 대조해 확인한 것만 썼다.
발표자는 영상 설명에서 poteto로 소개되며 SpaceXSI의 Grok Bot 팀에서 일한다.
숫자와 사례는 모두 발표자의 보고이다.

발표의 논지는 이렇다.
소프트웨어 엔지니어의 일은 생산성을 크게 올리면서 코드 품질을 유지하거나 높이는 방법을 찾는 것이고, 이를 소프트웨어 공장이라 부르기도 하지만 발표자는 신뢰의 문제로 본다는 것이다. 맹목적인 신뢰가 아니라 에이전트의 환경에 투자해 에이전트가 옳은 일을 하리라고 믿을 수 있게 만드는 것이다.
발표자는 그 지점에 이르는 데 6개월이 걸렸고 지금은 수천 개의 PR을 내며 상당수를 잠든 사이에 낸다고 하며, 다른 사람은 이보다 훨씬 짧게 걸릴 것이라고 말한다. 지난달 자신이 PR 3,000개를 운영에 반영했다고도 한다.

논증은 뒤집힌 피라미드로 설명된다.
시간을 쓸 곳의 순서는 이렇다.

- 위의 두 층은 결정적(deterministic)이다. 좋은 API 설계와 아키텍처와 리팩터링, 린트 규칙과 타입 시스템과 컴파일러와 여러 종류의 테스트로, 에이전트가 할 수 있는 일을 제한하고 기본값으로 옳은 일을 하게 만든다.
- 그다음은 검증이다. 런타임 검증과 형식 검증으로 시스템이 지켜야 할 성질을 점검하고 에이전트가 목표와 의도를 이해했는지 확인한다.
- 마지막이 산문이다. 규칙, 스킬, agents.md처럼 판단이 필요한 것이다.

핵심 비유는 정원이다.
에이전트의 입력 중 가장 큰 것이 코드베이스여서, 우회책이나 안티패턴이나 폐기 코드나 기술 부채가 다음 에이전트에게 정립된 패턴으로 보여 복사된다. 잡초가 정원 전체로 번지는 것과 같다는 것이다. 발표자는 2024년에 동료가 쓴 PR 3개를 검토하던 시절과 달리 지금은 300개쯤이 오고, 엔지니어 한 명이 수백에서 수천 에이전트의 팀이라고 한다.
그래서 에이전트를 교정할 때는 규칙 파일에 한 줄을 더하지 말고 결정적 검사로 만들라고 한다. 코드로 된 규칙이 더 재현 가능하기 때문이다.

사례는 다음과 같다.

- Dune: Grok Bot용 클라이언트 프레임워크로, 발표자는 Electron 앱용 Next.js 같은 것이라고 설명한다. 기술적으로 흥미로운 것은 제약과 린트 규칙이다. 미묘한 판단이 필요한 것은 슬롭을 낳는다는 교훈에서 React의 useEffect를 제품 코드에서 금지하고 프레임워크의 API 안에서만 쓰게 했다. 그 결과 이 문제를 코드 리뷰에서 다시 잡을 필요가 없어졌다고 한다.
- 디렉터리 구조로 맥락 주기: Cursor(Electron 앱)에서 에이전트가 메인 스레드 코드를 렌더러 스레드로 가져와 긴 작업과 끊김을 일으켰다. 그래서 두 최상위 디렉터리(Electron renderer와 main)를 두고 둘 사이의 import를 의존성 그래프 분석기와 린트 규칙으로 막았다.
- 주석 대신 린트: Cursor에서 에이전트가 setTimeout과 requestAnimationFrame 같은 명령형 타이머를 임시방편으로 즐겨 썼고(VS Code의 명령형 스타일과 React의 선언형 스타일의 충돌을 덮은 것), 정당화하는 주석을 길게 달아 타이머가 퍼져 성능이 나빠졌다고 한다. Grok Bot에서는 주석의 99%를 금지했다. 주석은 낡기 쉽고 사람이 읽지 않으며 에이전트에게 어려운 일을 안 할 변명 거리를 주고 강제할 수 없기 때문이다. 대신 린트 규칙이 근본 원인을 고치라는 도움이 되는 오류 메시지를 낸다. 에이전트를 교정할 때마다 결정적 검사나 API와 아키텍처의 개선으로 바꾸다 보면 코드 리뷰에서 볼 것이 줄고, 어느 시점에 에이전트가 자기 PR 대부분을 스스로 머지하게 된다고 한다.
- 검증: 코드 리뷰가 영상, 스크린샷, 다이어그램, 형식 검증 같은 검증 산출물을 보는 쪽으로 줄었다. 런타임 검증은 에이전트가 직접 코드를 실행하게 하는 것이고 Chrome DevTools 프로토콜 같은 도구를 쓴다. 기능 지도(feature map)는 사용자 관점에서 앱의 모든 기능을 담은 사이트맵으로, 에이전트와 공유 어휘를 준다. 스킬 안의 자체 CLI는 토큰 사용을 줄이고 시험할 수 있게 한다. 형식 검증에는 TLA+로 여러 기기와 플랫폼에 걸친 알림 같은 주요 사용자 흐름을 모델 검사하고, Lean으로 자체 가상화 라이브러리의 깜빡임과 떨림이 없음을 증명한다. 이미 여러 버그를 찾았으나 만능은 아니며 실험 중이라고 한다. UI에는 속성 기반 테스트를 쓰고 Bombadil이라는 라이브러리가 몇 개의 UI 버그를 잡았다고 한다.
- 토큰 사용: 한 개발자의 트윗을 인용해 6개월 전에는 에이전트가 머지한 미묘한 버그 때문에 신뢰하지 못했는데 지금은 하루 토큰의 70%를 검증에 쓴다고 하며, 발표자도 비슷하다고 한다. 검증 기법은 새롭지 않고 비용이 너무 커서 못 쓰던 것을 에이전트가 싸게 만들었다는 설명이다. pstack 플러그인에 사용자 관점의 상태 기계를 시각화하는 state chart 스킬을 만들었다고 한다.
- 결과: 지난달 팀이 PR 1만 1천 개를 운영에 반영했고, 클라이언트를 약 하루에 한 번 안정 버전으로 낸다. 10월에 PR을 하나 이상 낸 사람이 약 227명이다. 되돌려진 PR의 비율은 상대적으로 낮아져 약 0.5%로 안정적이고, 시작, 입력, 새 채팅 열기, 채팅 전환이 출시 때보다 빨라졌다고 한다. 앱은 아직 Electron이라 한계가 있다고 인정한다.
- 결론: 소프트웨어 공장을 짓기 전에 코드베이스와 검증이라는 기초부터 올리라는 것이다. 내부 코딩 루프가 슬롭을 내면 그 루프를 자동화해도 슬롭만 늘고 토큰이 더 든다. 기초가 서면 바깥 루프가 쉬워지고, Grok Bot의 연결 장치와 루틴과 프로젝트로 Cursor 클라우드 에이전트를 부릴 수 있다. 예로 릴리스마다 새 프로젝트가 빌드 전체를 사용자처럼 돌려 버그를 찾고 수정 PR을 열어 자동 머지한다고 한다. 코드베이스가 좋아 PR이 기본적으로 좋고 제품 코드 대부분이 깊은 사람의 리뷰가 필요 없다는 것이다.

## 분석

### 중심 주장은 교정을 문장이 아니라 장치로 옮기라는 것이다

발표의 가장 선명한 원칙은 에이전트를 고쳐야 할 때 규칙 파일에 문장을 더하지 말고 린트나 API 설계로 문제를 구조적으로 없애라는 것이다.
이유는 두 가지로 읽힌다. 코드로 된 검사는 재현 가능하고, 에이전트는 산문 규칙을 해석하거나 변명하는 데 쓸 수 있다는 것이다(주석과 마크다운에 정당화를 적는다는 관찰).
이 주장은 발표자의 경험에서 나온 일반화이다.

### 같은 코드베이스가 에이전트의 입력이라는 점이 이 논증의 전제이다

정원 비유의 실질은 에이전트가 기존 코드를 본보기로 복사한다는 관찰이다.
그러면 낡은 패턴을 지우고 새로운 위반을 막는 일이 품질 관리이면서 에이전트의 입력 관리가 된다. 발표자의 처방 순서(새 안티패턴을 막는 린트 규칙, 그다음 옛 패턴 정리)가 이에 맞는다.

## 비평

### 근거는 한 팀의 자기 보고이고 비교 대상이 없다

PR 1만 1천 개와 되돌림률 0.5%는 같은 팀이 낸 숫자이고, 이 기준이 무엇을 되돌림으로 세는지와 이전 기간의 값은 발표에서 제시되지 않는다.
되돌림률은 에이전트 PR의 품질을 재는 지표로 쓰기에는 한계가 있다.
되돌리지 않고 이어서 고치는 결함과 오래 뒤에 발견되는 결함은 보이지 않는다.
성능이 좋아졌다는 서술도 숫자 없이 방향만 말한다.

### 제품 코드에 사람의 깊은 리뷰가 필요 없다는 주장은 조건이 좁다

이 주장은 6개월의 투자와 높은 수준의 린트와 검증 기반을 전제로 하고, 대상이 Electron 클라이언트라는 한 종류의 제품이다.
형식 검증도 발표자가 실험 중이라고 하며 만능이 아니라고 밝힌다.
다른 규모와 도메인의 팀에서 같은 결과가 나오는지는 이 발표로 알 수 없다.

### 주석 99% 금지는 이 맥락에서 나온 규칙이다

주석이 낡고 아무도 읽지 않으며 변명 거리를 준다는 이유는 에이전트가 쓰는 주석에 대한 관찰이다.
사람이 쓰는 이유 설명 주석이나 외부 제약의 기록까지 같은 논리로 금지해도 되는지는 발표가 다루지 않는다.

### 외부 반응이 없다

HN에서 이 영상의 스레드는 검색되지 않았고, Lobste.rs에서는 `youtube.com` 도메인의 최근 350개 글(14쪽)에 이 영상이 없었으나 그 아래는 요청 제한(429)으로 보지 못했다. GeekNews에서는 영어 제목과 한국어 표현과 발표자 이름으로 검색한 세 번에서 이 영상의 토픽을 찾지 못했다.
그래서 이 발표의 주장은 독자의 검토를 거치지 않았다.

## 인사이트

### 가져갈 것은 교정의 기본 단위를 검사로 바꾸는 습관이다

에이전트가 같은 실수를 두 번 하면 규칙 문장을 더하기 전에 그것을 린트 규칙이나 구조(디렉터리, 의존성 금지)로 막을 수 있는지 먼저 묻는 것이다.
막는 규칙에는 근본 원인을 고치라는 안내를 오류 메시지에 담는 것이 발표의 방법이다.
이는 이 문서의 적용이고, 발표가 제시한 것은 Grok Bot과 Dune에서의 사례들이다.

### 토큰을 검증에 쓴다는 선택은 비용 구조를 바꾼다

발표는 비용이 컸던 검증이 에이전트 덕에 싸졌고 토큰의 큰 부분(발표자는 대부분, 인용된 개발자는 70%)을 검증에 쓴다고 말한다.
이는 생성보다 검증에 예산을 두는 쪽이 신뢰를 만든다는 주장이다. 이 비율이 다른 팀에도 맞는지는 알 수 없다.

### 확인할 관찰

이 발표의 주장을 가를 관찰은 세 가지이다.
되돌림률 외의 지표(운영 사고, 지연된 결함, 성능 수치)가 공개되는지,
린트와 검증 기반의 구축 비용과 시간이 다른 팀에서 6개월보다 짧은지,
제품 코드의 사람 리뷰 생략이 다른 종류의 제품에서도 유지되는지이다.
