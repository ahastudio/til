# SoL-Pi: 에이전트가 스스로 찾아낸 하네스 효율화 장치 네 개

<https://nvlabs.github.io/SoL-Pi/>

<https://github.com/NVlabs/SoL-Pi>

## 소개

NVIDIA 연구 조직이 공개한 코딩 에이전트 하네스 확장이다.
TypeScript로 작성됐고 MIT 라이선스이며,
2026년 9월 2일에 만들어져 확인 시점에 별 772개와 포크 56개를 기록하고 있다.

저장소는 첫머리에 성격을 분명히 해 둔다.
이것은 Pi의 오픈소스 확장이며 Pi의 공식 배포판이 아니라는 것이다.
Pi는 `earendil-works/pi`의 경량 확장형 코딩 에이전트 하네스이고,
SoL-Pi는 수정하지 않은 Pi 릴리스 위에 얹힌다.

한 줄 요약은 에이전트가 유용한 일을 덜 하게 만들지 않으면서
비용을 줄인다는 것이다.
반복되는 모델 턴, 컨텍스트 재생, 과대한 관찰 결과,
불필요한 긴 로그 읽기를 줄이되
과제를 끝내는 데 필요한 작업과 증거는 보존한다고 적는다.

모든 장치가 선택적이며 기본값은 비활성이다.

## 네 가지 장치

| 영역 | 장치 | 바뀌는 것 |
| ------ | ---------------------------- | ------------------------------------------------ |
| 도구 | Action Fusion | 편집이나 쓰기가 후속 검증 명령을 같은 도구 호출에서 실행 |
| 관찰 | ObservationPack | 반복되는 큰 텍스트 결과를 안정적 핸들로 바꾸고 정확한 쪽 단위 회수 |
| 위임 | Evidence-Preserving Reducer | 긴 진단 로그를 압축된 영수증으로 바꾸되 보존된 인용이 원본과 일치할 때만 |
| 컨텍스트 | Online Context Compact | 완료된 계획 단계를 Pi 기본 압축의 후보 지점으로 삼음 |

네 장치가 공유하는 규칙도 넷이다.
Pi를 패치하지 않고 공개 API만 가져다 쓰며 Pi 소스 트리를 벤더링하지 않는다.
설정이 없으면 모든 장치가 꺼진 채로 남는다.
원본 관찰 결과는 로컬에 남으며 축소기가 실패하면 원래 결과가 그대로 유지된다.
인증과 공급자 URL과 주 모델과 셸 동작은 Pi의 통제 아래 둔다.

### Action Fusion

파일을 편집한 뒤 그것을 시험하거나 빌드하거나
실행하는 명령이 뒤따르는 패턴이 반복된다는 관찰에서 나왔다.
Action Fusion은 그 순서를 하나의 도구 호출로 만든다.
편집을 적용하고 명령을 로컬에서 실행한 뒤,
모델을 한 번 더 거치지 않고 결합된 관찰 하나를 돌려준다.

연구 과정이 네 단계로 기록돼 있다.
사전 분석에서 인접한 편집·쓰기에서 명령으로 이어지는 후보가 전체 턴 전환의
12.3퍼센트였고,
관찰된 다음 동작의 85.1퍼센트가 Bash였다.
기준선 구축에서 적격 호출 중 87.7퍼센트 적용률과 잘못된 호출 0건을 확보했다.
프롬프트 최적화 10회 배치에서 실패한 변형을 제거하고 프롬프트와 스키마를 다듬어,
트리거율 100퍼센트와 과제 점수 87.0인 10회차를 선택했다.
마지막으로 독립 검증 두 번을 돌렸다.

효과 추정치도 제시한다.
관찰된 149개 후보가 모두 트리거됐다면 모델 턴이 1,386에서 1,237로 10.8퍼센트
줄고
총 토큰이 3,238만에서 2,864만으로 11.5퍼센트 줄었을 것이라는 계산이다.
이것이 궤적에서 도출한 반사실이지 실제 재실행이 아니라고 명시한다.

### ObservationPack

기본 Pi에서는 큰 파일이나 도구 결과가 이후 모든 요청에 다시 나타나 컨텍스트와
캐시를 차지한다.
ObservationPack은 페이로드를 로컬에 보관하고
컨텍스트에는 핸들과 짧은 발췌만 남긴 뒤, 필요할 때만 정확한 쪽을 회수한다.

이 장치의 연구 기록은 다른 형태다.
깨끗한 Pi에서 다시 구현하고, 315줄과 훅 두 개로 줄이며
실패 시 원본을 유지하는 계약을 두고,
투영 설정 8가지를 훑어 품질 기준 안에 든 유일한 구성을 골랐으며,
마지막으로 같은 클러스터에서 두 조건을 동시에 돌리는 짝 비교를 수행했다.

### Evidence-Preserving Reducer

긴 로그 읽기를 더 저렴한 에이전트에 위임하되, 결과 영수증을 보관된 로그에 묶고
인용된 모든 줄을 최전선 에이전트가 보기 전에 검증한다.
위임이 유창한 요약에 대한 신뢰를 요구하지 않게 된다는 것이 설계 의도다.

### Online Context Compact

KV 캐시 재사용 때문에 압축은 보통 실행 후반으로 밀린다.
이 장치는 다른 시계를 쓴다.
과제를 하위 과제로 나누고 하나가 끝날 때마다 압축을 재고하되,
앞으로의 절약이 재작성 비용을 갚을 수 있을 때만 실행한다.
압축에 성공하면 새 턴을 시작해 과제를 이어 간다.

## 설치와 설정

Node.js 22.19 이상과 npm, 그리고
`@earendil-works/pi-coding-agent` 0.84.2가 필요하다.

Pi를 설치한 뒤 `pi install git:github.com/NVlabs/SoL-Pi`로 붙인다.
프로젝트 범위로만 설치하려면 `--local --approve`를 붙인다.

설정은 `sol-pi.json` 하나로 한다.
신뢰된 프로젝트의 `.pi/sol-pi.json`을 먼저 찾고 없으면
`~/.pi/agent/sol-pi.json`을 쓰며,
둘을 병합하지 않는다.
전용 환경 변수는 쓰지 않는다.

README가 권하는 보수적 구성은 추가 모델 호출을 만들지 않고 진행 중인 실행을
멈추지 않는
로컬 장치 둘만 켜는 것이다.
`actionFusion`과 `observationPack`을 켜고 나머지 둘은 끈 상태다.

### 저장과 보안

ObservationPack과 Evidence-Preserving Reducer는 세션 디렉터리 아래에 보관물을
남긴다.
보관된 사본은 로컬에 남으며
Pi 세션이 끝나도 자동으로 삭제되지 않는다고 명시한다.

Evidence-Preserving Reducer는 적격한 진단 로그 내용을 설정된 축소기 모델로 보낼
수 있다.
로컬에 남아야 하는 로그에는 원격 축소를 켜지 말라고 적는다.

## 연구 방식과 결과

블로그는 이 저장소를 재귀적 자기 개선(RSI) 연구의 산출물로 소개한다.

문제 제기가 명확하다.
RSI 자체가 토큰 집약적이며
더 나은 시스템을 만들려는 모든 시도가 성공 여부와 무관하게 토큰을 쓴다는 것이다.
그래서
RSI를 확장하기 전에 AI에게 AI를 더 효율적으로 만들라고 먼저 물어야 하는 것
아니냐고 묻는다.

### 탐색 절차

에이전트가 공개 데이터와 공개 소프트웨어 환경에서 실행 가능한 환경을 구성하고,
다른 에이전트가 그 궤적 안에서 모델이 어떻게 탐색하는지 관찰한 뒤,
그 관찰을 효율 목표 아래 하네스를 개선하는 자동 연구 루프로 바꾼다.

제안 152개가 루프에 들어가 4개가 살아남았다.
탐색 목표는 제약된 효율이며, 미리 선언한 능력 보존 기준을 지키면서
비용이나 토큰을 줄이는 것이다.

각 루프에 수용 관문 두 개가 있다.
모든 능력 지표가 미리 선언한 허용 범위 안에 있어야 하고,
효율 지표 중 최소 하나가 개선돼야 한다.
일찍 멈추거나 필요한 검증을 건너뛰거나
과제 완수에 필요한 증거를 없애서 아끼는 후보는 탈락한다.

블로그는 이 관문이 한 번에 하나의 장치에만 적용되므로
허용된 작은 손실이 장치를 결합하면 누적된다고 적는다.
그 결과 조립된 하네스가 Pi 평균 점수의 약 94퍼센트를 유지한다.

### 측정 결과

EdgeBench는 51개 과제로 된 장기 실행 평가 모음이며,
과제와 검증기와 피드백을 최종 홀드아웃 평가용으로만 쓴다고 밝힌다.
모든 비교는 각 모델 백엔드를 이 평가에서 가장 높은 추론 노력 설정으로 돌렸다.

EdgeBench에서 SoL-Pi는 두 모델 백엔드 모두에서 Pi 평균 점수의 약 94퍼센트를
유지하고,
GPT-5.6 Sol에서는 해당 모델의 네이티브 Codex 하네스를 넘어선다.
효율 쪽 차이가 더 크다.
Pi 대비 토큰을 45~49퍼센트 덜 쓰고 비용이 약 3분의 1 낮으며,
모델 네이티브 하네스 대비 토큰을 35~64퍼센트 덜 쓰고 정가 기준 API 비용이
50~54퍼센트 낮다.

전문 연구자가 한 문제에 매달릴 때 기준으로,
네이티브 Codex 및 Claude Code 하네스 대비 시간당 8.75~13.50달러,
Pi 대비 시간당 4.36~5.71달러를 아낀다고 적는다.

Terminal-Bench 4의 CPU 전용 63개 과제 결과도 제시한다.

| 하네스 | 해결 | 총 모델 비용 | 해결 과제당 비용 |
| ------- | ----- | ----------- | -------------- |
| Codex | 18/63 | $272.35 | $15.13 |
| Pi | 18/63 | $286.45 | $15.91 |
| SoL-Pi | 15/63 | $211.12 | $14.07 |

GPU가 필요한 과제는 이 연구에 쓰인 내부 평가 인프라가 긴 실행을 지원하지 않아
제외했다고 밝힌다.

### 에이전트 군집 실험

효율적인 하네스가 집단 탐색도 더 경제적으로 만드는지 시험했다.
Anthropic의 원래 성능 과제인 커널 최적화를 시뮬레이션 사이클 수로 채점하는
방식이다.

Codex에서 도는 GPT-5.6 Sol 조율자 하나가 GPT-5.6 Luna 작업자 20개를 지휘한다.
작업자는 4개씩 다섯 무리로 나뉘고 각 무리가 독립 작업 공간과 지역 증거 게시판을
갖는다.
무리 안에서는 동료끼리 증거를 주고받고 무리 사이의 발견은 조율자가 압축해
전달한다.

같은 시작점에서 2시간짜리 독립 시행 세 번을 돌렸다.

| 구성 | 사이클 | 모델 비용 | 속도 기준 |
| ------------------ | ------ | -------- | -------- |
| Sol + SoL-Pi 20개 | 1,127 | $60.11 | 8/8 |
| 단일 Sol | 1,333 | $39.20 | 8/8 |
| Sol + 기본 Pi 20개 | 1,366 | $82.12 | 7/8 |

SoL-Pi 군집이 기본 Pi 군집보다 사이클을 17.5퍼센트 적게 쓰고 비용이 26.8퍼센트
낮았다.
단일 Sol이 39.20달러로 가장 저렴했지만 1,333 사이클에서 끝났고,
에이전트를 늘린다고 결과가 좋아지지는 않았다는 점도 적는다.
기본 Pi 군집은 단일 Sol보다 비싸면서 1,366 사이클로 끝났다.

블로그는 이것이 조건당 무작위화되지 않은 단일 시행이며,
SoL-Pi 시행이 네트워크와 인증 문제로 세 번 멈춘 반면
대조군은 수리된 구성에서 시작했고,
이런 차이와 반복 부재 때문에
SoL-Pi의 효과를 인과적으로 추정할 수 없다고 명시한다.

### 논의에서 밝힌 탐색의 성질

깊이 우선 탐색은 5~10회 반복 뒤 국소 분지에 갇혀 방향을 바꾸는 대신
같은 설계를 조금씩 조정하는 경향을 보였다.
너비 우선은 대부분 검증에 실패했지만
시작 아이디어의 다양성을 늘리면 드물게 특이한 후보가 드러났고,
그 도약이 이 프로젝트에서 가장 유용한 변경 일부를 만들었다.
전환율은 낮게 유지됐다.
시작 아이디어 약 40개 중 하나만 검증을 통과했다.

사람의 역할도 정리한다.
사람이 초기 사전 지식을 제공하고 탐색 가치가 낮은 방향을 걸러 냈으며,
아이디어가 루프에 들어간 뒤에는 연구와 검증이 사람 개입 없이 진행됐고,
후보가 살아남으면 사람이 돌아와 에이전트가 발견한 장치를 이해하고
깔끔한 구현으로 다시 썼다.

마지막으로 두 가지 전망을 제시한다.
하네스 사전 학습이라는 방향과,
더 효율적인 하네스가 다음 하네스를 찾는 연구 비용을 낮춘다는 효율의 효율이다.
후자는 이번 연구가 입증한 복리 효과가 아니라 장기 연구 비전이라고 단서를 단다.

## 분석

### 효율을 능력과 분리해서 측정하겠다는 선언이 이 연구의 뼈대다

이 작업에서 가장 방법론적으로 단단한 부분은 수용 관문이다.
미리 선언한 능력 허용 범위를 지키면서
효율 지표 하나 이상을 개선해야 후보가 살아남는다.

이 설계가 중요한 이유는 효율 개선의 흔한 속임수를 차단하기 때문이다.
일찍 멈추기, 검증 건너뛰기, 증거 없애기가 그것이며, 셋 다 토큰을 확실히 줄인다.
자동 탐색에 목적 함수를 토큰 감소로만 주면 탐색이 정확히 그 방향으로 간다.

그리고 이 관문이 실제로 작동했다는 증거가 결과에 남아 있다.
152개 제안 중 4개만 살아남았고,
시작 아이디어 40개 중 하나가 검증을 통과했다는 수치가 그것이다.
보통의 자동 최적화 논문이 성공 사례만 보고하는 것과 달리,
이 프로젝트는 탈락률을 전면에 내세운다.

다만 관문의 적용 단위가 문제를 남긴다.
블로그 자신이 관문이 한 번에 하나의 장치에만 적용되므로
허용된 작은 손실이 결합 시 누적된다고 적는다.
그래서 94퍼센트라는 수치가 나온다.
이것은 부작용이 아니라 설계된 결과이며,
6퍼센트의 능력을 비용과 맞바꾸기로 한 결정이다.

### 하네스를 RSI의 대상으로 고른 것이 이 연구의 실제 주장이다

블로그가 서두에 던지는 질문이 이 프로젝트의 위치를 정한다.
RSI를 확장하기 전에 AI에게 AI를 더 효율적으로 만들라고 먼저 물어야 하지 않느냐는
것이다.

이 선택이 영리한 이유는 검증 가능성 때문이다.
모델을 개선하는 자기 개선은 결과를 측정하기 어렵고 주기가 길며 비용이 막대하다.
하네스는 코드이고, 개선 여부를 토큰 수와 과제 점수로 즉시 잴 수 있으며,
실험 한 번이 몇 시간이면 끝난다.

그리고 하네스는 모델 제공자 바깥에 있다.
NVIDIA가 프런티어 모델을 직접 만들지 않으면서도 그 모델들의 사용 효율을 연구할
수 있는 자리가 여기다.
GPT-5.6과 Claude 계열을 백엔드로 쓰면서 그 위의 층을 최적화하는 구도이며,
연구 대상과 상업적 이해가 충돌하지 않는다.

이 구도에서 나오는 부수 효과가 하나 있다.
하네스 효율화는 추론 수요를 줄이는 방향이므로 모델 제공자의 매출에는 불리하고,
추론 하드웨어를 파는 쪽에도 직관적으로는 불리하다.
그런데 블로그의 논리는 반대다.
효율이 높아지면 같은 예산으로 더 많은 환경과 궤적과 연구 아이디어를 돌릴 수
있다는 것이며,
수요가 줄지 않고 이동한다는 주장이다.

### 네 장치가 전부 재료가 아니라 배관을 다룬다

살아남은 네 장치의 공통점이 있다.
어느 것도 모델이 무엇을 생각할지 바꾸지 않는다.

Action Fusion은 두 도구 호출을 하나로 합치고,
ObservationPack은 같은 내용을 반복 전송하지 않게 하며,
Reducer는 읽기를 싼 모델에 위임하고,
Online Context Compact는 압축 시점을 옮긴다.
전부 같은 작업을 더 적은 왕복으로 처리하는 문제이며,
프롬프트 개선이나 추론 전략과는 층이 다르다.

제안 목록에 남은 탈락 후보들을 보면 이 대비가 더 분명해진다.
few-shot이나 RAG나 키워드 게이트를 주된 지렛대로 쓰지 말 것,
추론 노력을 검증된 진척 신호로 라우팅할 것 같은
항목들이 프롬프트 층위에 있었고 살아남지 못했다.

이 결과가 시사하는 바가 있다.
프런티어 모델이 충분히 좋아진 조건에서 하네스가 낭비하는 것은 판단의 질이 아니라
같은 판단의 반복이라는 것이다.
그리고 반복 제거는 프롬프트 기교가 아니라 시스템 설계 문제다.
앞서 다룬 Shopify 사례에서 에이전트의 병목이 코드 생성이 아니라
검증 왕복이었던 것과 같은 구조가 여기서도 관찰된다.

## 비평

### 유일하게 해결 과제 수를 공개한 벤치마크에서 세 과제를 덜 풀었다

EdgeBench 결과는 평균 점수의 94퍼센트라는 비율로 제시된다.
비율은 손실의 크기를 추상화하며, 어떤 과제를 왜 놓쳤는지를 보이지 않는다.

Terminal-Bench 4 결과는 다르다.
63개 중 Codex가 18개, Pi가 18개, SoL-Pi가 15개를 풀었다.
같은 과제 집합에서 세 개를 덜 풀었고, 비율로는 17퍼센트 적다.

이 숫자가 헤드라인 주장과 어긋난다.
유용한 일을 덜 하게 만들지 않으면서
비용을 줄인다는 것이 이 프로젝트의 한 줄 요약인데,
공개된 두 벤치마크 중 해결 수를 셀 수 있는 쪽에서 유용한 일이 실제로 줄었다.

그리고 비용 이득도 이 각도에서 보면 작아진다.
총비용은 211.12달러로 Pi의 286.45달러보다 26퍼센트 낮지만,
해결 과제당 비용은 14.07달러 대 15.91달러로 12퍼센트 차이다.
Codex의 15.13달러와 비교하면 7퍼센트다.
50~54퍼센트라는 EdgeBench 기준 비용 절감과 자릿수가 다르다.

블로그가 해결 과제당 비용을 표에 넣어 둔 것은 정직하다.
그러나 그 수치를 결론에서 다시 언급하지 않고,
요약과 배지와 첫 문단에는 더 큰 비율들이 놓인다.
읽는 사람이 가장 먼저 보는 숫자와 가장 정확한 숫자가 다르다.

### 군집 실험이 자신의 결론을 지지하지 않는다

이 절의 질문은 효율적인 하네스가 집단 탐색도 경제적으로 만드는가다.
그런데 세 시행의 결과를 그대로 읽으면 답이 나오지 않는다.

가장 싼 것은 단일 에이전트였다.
39.20달러로 1,333 사이클에 도달했고 속도 기준 8개를 모두 통과했다.
SoL-Pi 군집은 60.11달러를 써서 1,127 사이클에 도달했다.
15퍼센트 더 좋은 결과에 53퍼센트 더 많은 비용을 썼다는 뜻이며,
군집 도입의 경제성 자체가 증명되지 않는다.

증명된 것은 좁다.
군집을 쓰기로 이미 정했다면 SoL-Pi 작업자가 기본 Pi 작업자보다 낫다는 것이다.
그리고 그 비교조차 블로그가 열거한 조건 차이 때문에 흔들린다.
SoL-Pi 시행이 네트워크와 인증 문제로 세 번 멈췄고,
대조군은 수리된 구성에서 시작했으며,
조건당 시행이 한 번이고 반복이 없다.

블로그가 이 한계를 스스로 길게 적었다는 점은 인정해야 한다.
인과 추정이 불가능하다고 명시하고, 승인된 개선 횟수와 제출 후보 수까지 공개한다.
그런데 그 정직함이 절 제목과 충돌한다.
제목은 더 낮은 비용의 검증된 프런티어이고,
본문의 마지막은 이 실험이 어느 장치가 이득을 냈는지 분리하지 못한다는 고백이다.

여기서 더 의문스러운 것은 조율자가 Codex로 남았다는 점이다.
SoL-Pi는 작업자 안에서만 돌고 조율자는 네이티브 Codex 에이전트다.
효율 하네스의 가치를 보이려는 실험에서 가장 많은 컨텍스트를 다루는 자리에 그것을
쓰지 않은 이유가 설명되지 않는다.

### 대표 수치가 실제 재실행이 아니라 궤적 반사실이다

Action Fusion 절의 가장 눈에 띄는 숫자는 모델 턴 10.8퍼센트 감소와 총 토큰
11.5퍼센트 감소다.
그리고 바로 다음 문장이 이것은 궤적에서 도출한 반사실이며
측정된 재실행이 아니라고 적는다.

이 단서가 붙어 있다는 점에서 이 문서는 정직하다.
다만 이런 숫자의 운명은 대체로 정해져 있다.
인용되고 옮겨지는 과정에서 단서가 먼저 떨어지고, 퍼센트만 남는다.

그리고 반사실의 가정이 강하다.
관찰된 149개 후보가 모두 트리거됐다면이라는 조건인데,
같은 문서가 트리거율이 탐색 과정에서 28.3퍼센트에서 100퍼센트까지 비단조적으로
움직였다고 적는다.
실제 배포에서 100퍼센트가 유지되는지가 이 수치의 전제이며,
그 전제는 별도로 검증되지 않았다.

더 근본적인 문제는 반사실이 이차 효과를 담지 못한다는 것이다.
편집과 검증을 한 호출로 합치면 중간 판단이 사라지는데,
그 판단이 때로 유용했을 수 있다.
편집 결과를 보고 명령을 바꾸거나 아예 실행하지 않기로 하는 경우이며,
합친 호출에서는 그 선택지가 없어진다.
이런 손실은 궤적 재계산으로 드러나지 않고 실제 재실행에서만 보인다.
Terminal-Bench에서 세 과제를 덜 푼 것이 그 손실의 한 형태일 수 있는데,
두 결과가 연결되지 않는다.

### 증거 보존을 내세우면서 데이터 이동과 잔존을 만든다

이 프로젝트가 반복해 강조하는 원칙이 증거 보존이다.
원본 관찰 결과는 로컬에 남고, 축소기가 실패하면 원래 결과가 유지되며,
인용된 모든 줄이 원본과 대조된다.

이 설계는 요약 위임의 고질적 문제를 실제로 겨냥한다.
싼 모델에게 긴 로그를 요약시키면 그럴듯하지만 틀린 문장이 돌아오고,
받는 쪽은 그것을 검증할 방법이 없다.
인용 대조를 강제하는 것은 그 문제에 대한 적절한 해법이다.

그런데 같은 설계가 두 가지 부작용을 만들고, README가 그것도 적어 둔다.
보관물이 세션 디렉터리에 남으며 Pi 세션이 끝나도 자동으로 삭제되지 않는다.
그리고 축소기는 적격한 진단 로그 내용을 설정된 축소기 모델로 보낼 수 있다.

즉 증거를 보존하기 위해 원본을 디스크에 남기고,
비용을 줄이기 위해 그 원본의 일부를 다른 모델로 보낸다.
전자는 장기적으로 쌓이는 민감 데이터이며 정리 정책이 사용자에게 맡겨져 있고,
후자는 로컬에 남아야 할 로그가 있는 환경에서 켜면 안 되는 기능이다.

문서가 이 둘을 숨기지 않은 것은 좋다.
다만 보수적 기본 구성이 이 둘을 끄는 이유로 제시된 것은 추가 모델 호출을 만들지
않고 실행을 멈추지 않는다는 운영상 이유뿐이며,
데이터 이동이 그 판단에 포함돼 있는지가 드러나지 않는다.
기본값의 근거를 성능이 아니라
데이터 경계로 설명하는 편이 사용자에게 더 유용했을 것이다.

## 인사이트

### 효율 주장은 분모를 바꾸는 순간 크기가 달라지며, 그 분모는 완료된 일이어야 한다

이 연구가 제시한 수치들은 분모에 따라 전혀 다른 이야기를 한다.
토큰을 분모로 하면 45~49퍼센트 절감이고, 시간을 분모로 하면 시간당 몇 달러이며,
해결한 과제를 분모로 하면 7~12퍼센트다.

셋 다 정직한 계산이지만 의사결정에 쓸 수 있는 것은 마지막 하나뿐이다.
조직이 사는 것은 토큰이 아니라 완료된 과제이고, 과제를 덜 풀면서
토큰을 아끼는 것은 절감이 아니라 축소다.

이 구분이 지금 특히 중요한 이유가 있다.
에이전트 도구 시장 전체가 토큰 절감을 경쟁 지표로 쓰고 있고,
그 지표는 측정하기 쉽다.
반면 완료된 과제를 세려면 벤치마크가 필요하고,
벤치마크는 만들기 어렵고 논쟁적이다.
측정하기 쉬운 지표가 측정해야 할 지표를 대체하는 익숙한 경로이며,
이 연구는 두 지표를 모두 공개했다는 점에서 예외적이다.

여기서 나오는 실무 기준은 하네스나 도구의 효율 주장을 볼 때 완료 단위당 비용을
스스로 계산해 보는 것이다.
대부분의 발표가 그 수치를 직접 주지 않지만,
총비용과 성공 수를 함께 제시했다면 나눗셈 한 번으로 나온다.
그리고 그 나눗셈 결과가 헤드라인 비율과 크게 다르다면,
차이의 원인이 능력 손실인지 확인해야 한다.

### 미리 선언한 능력 허용 범위라는 장치는 이 연구 바깥에서 더 쓸모가 있다

이 프로젝트에서 가장 이식 가능한 것은 네 개의 장치가 아니라 수용 관문의 형태다.
효율을 개선하려는 모든 변경에 대해,
능력 지표가 미리 선언한 허용 범위 안에 머무는지를 먼저 확인한다는 규칙이다.

이 형태가 유용한 이유는 사후 합리화를 막기 때문이다.
성능 최적화 작업에서 흔한 일이 결과를 본 뒤 허용 가능한 손실의 기준을 정하는
것이며,
그렇게 하면 어떤 손실이든 받아들일 이유를 찾을 수 있다.
허용 범위를 미리 적어 두면 그 여지가 사라진다.

같은 구조가 자동 탐색 바깥에서도 성립한다.
데이터베이스 인덱스를 줄여 쓰기 성능을 올릴 때, 캐시 TTL을 늘려 부하를 줄일 때,
이미지 품질을 낮춰 대역폭을 아낄 때가 전부 같은 형태의 결정이다.
그리고 대부분의 조직에서 이 결정의 능력 쪽 허용 범위가 문서화되지 않는다.

에이전트 도입에서는 이 문제가 더 커진다.
자동화가 만들어 내는 절감은 명확하고 즉시 보이는 반면,
그 대가로 놓치는 것은 흩어져 있고 나중에 나타난다.
미리 선언한 허용 범위는 그 비대칭을 다루는 몇 안 되는 실용적 장치이며,
이 연구가 그것을 자동 탐색의 정지 조건으로 구현했다는 점이 참고할 만하다.

다만 이 연구가 동시에 보여 준 한계도 함께 가져가야 한다.
관문이 변경 하나씩에만 적용되면 손실이 누적된다는 것이며, 그래서
결합된 시스템에 대한 별도 관문이 필요하다.
개별 최적화가 각각 허용 범위 안에 있는데 전체는 벗어나는 상황이 실제로 일어났고,
94퍼센트라는 숫자가 그 기록이다.

### 자동 연구의 실제 산출물은 장치가 아니라 낮은 생존율이라는 사실이다

152개에서 4개, 그리고
시작 아이디어 40개 중 하나라는 수치가 이 프로젝트에서 가장 오래 남을 정보다.
장치 네 개는 Pi에 묶여 있고 Pi 버전에 묶여 있으며,
하네스 설계가 바뀌면 의미를 잃는다.
생존율은 그렇지 않다.

이 수치가 말해 주는 것은 자동 연구의 비용 구조다.
쓸 만한 개선 하나를 얻으려면 실패한 탐색 서른아홉 개의 비용을 치러야 하며,
그 비용이 개선으로 아끼는 비용보다 클지 작을지가 이 접근의 성립 조건이다.
그리고
블로그가 제시한 효율의 효율이라는 전망은 정확히 이 비율이 개선되는 경우에만
성립한다.

깊이 우선 탐색이 5~10회 반복 뒤 국소 분지에 갇혔다는 관찰도 같은 맥락에서
읽힌다.
모델의 추론 능력을 최대로 올려도 같은 설계를 조금씩 고치는 쪽으로 수렴했다는
것이며,
이것은 모델의 한계가 아니라 탐색 절차의 한계다.
해법이 더 좋은 모델이 아니라 더 다양한 시작점이었다는 결론이 여기서 나온다.

이 관찰이 개인 작업에도 적용된다.
에이전트에게 한 방향을 계속 개선하라고 시키면 몇 번 만에 미세 조정으로 빠지며,
그 시점을 사람이 알아차리기 어렵다.
같은 예산으로 서로 다른 출발점 여럿을 짧게 돌리는 편이 나은 결과를 낼 가능성이
높고,
그것이 이 연구가 너비 우선 탐색에서 얻은 교훈이다.

### 하네스 개선을 확장이 아니라 포크로 하는 순간 이 연구는 재현 불가능해진다

이 저장소가 스스로에게 건 네 규칙 중 첫 번째가 Pi를 패치하지 않는다는 것이다.
공개 확장 API만 쓰고 Pi 소스 트리를 벤더링하지 않으며,
인증과 공급자와 주 모델과 셸 동작을 Pi에 맡긴다.

이 규율이 연구 결과보다 오래갈 수 있다.
하네스 개선을 발표하는 프로젝트 대부분이 포크로 배포되며,
포크는 상류가 움직이는 순간 가치가 줄기 시작한다.
확장으로 배포하면 상류의 개선을 계속 받으면서 자기 장치만 유지하면 된다.

그리고 이 선택이 연구 방법론과도 맞물린다.
자동 탐색이 찾아낸 변경을 상류에 적용할 수 없으면 그 변경은 그 시점의
코드베이스에만 유효한 발견이 된다.
공개 API 위에서만 작동하도록 제약을 걸면 살아남는 후보가 줄어드는 대신,
남은 것들이 버전 변화를 견딘다.
152개에서 4개로 줄어든 데는 이 제약도 기여했을 것이며, 그 대가가 이식성이다.

다만 이 규율이 완전하지는 않다.
설치 요구사항이 Pi 0.84.2로 고정돼 있고 개발 의존성도 그 버전에 고정돼 있으며,
호환성 문서와 `check-pi-compat.mjs` 스크립트가 따로 존재한다는 것이 확장 API가
아직 안정적이지 않다는 뜻이다.
확장으로 만들었으나 특정 버전에 묶여 있다면 포크의 문제가 형태만 바꿔 남은
것이다.

여기서 나오는 일반 원칙은 상류 프로젝트 위에 무언가를 얹을 때 확인해야 할 것이
배포 형태가 아니라
API 안정성 보장이라는 것이다.
확장이라는 형태 자체는 아무것도 보장하지 않으며,
상류가 확장 API를 계약으로 취급하는지가 실제 변수다.
Pi가 그것을 명시적으로 약속하고 있는지는 이 저장소의 문서에서 확인되지 않고,
고정된 버전 번호가 그 불확실성을 대신 말해 준다.
