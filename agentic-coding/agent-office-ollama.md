# Agent Office (Ollama 시뮬레이션)

<https://github.com/harishkotra/agent-office>

## 소개

harishkotra의 Agent Office는 사무실에서 AI 에이전트가 책상으로 걷고 생각하고 협업하고
인턴을 뽑고 서로에게 일을 맡기는 모습을 보여 주는 시뮬레이션이다.
같은 이름의 다른 저장소가 여럿 있어 이 문서는 harishkotra의 것만 다룬다.
Claude Code 같은 실제 세션을 관찰하는 도구가 아니라
서버가 직접 LLM 에이전트를 돌리는 독립 시뮬레이션이다.
MIT 라이선스, TypeScript이고 2026년 11월 25일 GitHub API로 본 별은 426개, 포크는 114개이다.
생성일은 2026년 2월 25일, 마지막 커밋은 9월 24일, 커밋은 18개이다.
별도 홈페이지는 없다.

저장소를 받아 코드를 읽었으며 설치하거나 실행하지 않았다.
서버, 코어, 어댑터, 저장소 계층과 Phaser 클라이언트의 핵심 파일은 이 문서가 직접 읽고 줄 단위로 확인했다.
UI의 React 패널 대부분과 `pixel-agents-repo/`의 내용은 읽지 못했다.

## 동작 방식

### 모듈 구성

| 위치                               | 줄 수 | 역할                                                  |
| ---------------------------------- | ----- | ----------------------------------------------------- |
| `server/src/rooms/OfficeRoom.ts`   | 767   | 시뮬레이션 루프, 메시지 처리, 고용, 관계, 혼돈 이벤트 |
| `server/src/tools/ToolExecutor.ts` | 137   | 도구 네 가지 실행                                     |
| `server/src/memory/MemoryStore.ts` | 198   | SQLite 기억, 작업, 배치, 임베딩                       |
| `server/src/index.ts`              | 48    | Express 경로 셋과 Colyseus 등록                       |
| `core/src/agent/Agent.ts`          | 228   | 프롬프트 생성, 결정 해석, 단기 기억                   |
| `adapters/src/OllamaAdapter.ts`    | 74    | `/api/chat` 호출                                      |
| `ui/src/game/Game.ts`              | 861   | Phaser 장면, 서버 상태 구독                           |

`core`의 `Office`, `Grid`, `TaskManager`, `MemoryManager`는 서버가 쓰지 않는다.
`Office`만 서버가 만들지만(82줄) 그 뒤로 읽는 곳이 없다.
의존성은 서버가 colyseus, express, sqlite3, `@tavily/core`이고 어댑터는 외부 패키지 없이 `fetch`만 쓴다.
UI는 Phaser, React, colyseus.js이다.

### 에이전트 루프

서버(`OfficeRoom.ts`)의 `update()`가 100ms 간격으로(198줄) 돌면서 에이전트마다 생각 루프를 시작한다.
에이전트별 잠금이 있어 한 번 생각을 끝내면 15초 뒤에(425줄) 잠금이 풀리므로
실제 주기는 추론 시간에 15초를 더한 값이다.
기본 주민은 Alice와 Bob이고, Ollama(`llama3.2:latest`, 주소 `http://localhost:11434`가 코드에 고정)에
프롬프트 하나를 보내 JSON 결정을 받는다.
프롬프트는 `Agent.ts`의 `think()`(144~167줄)가 만들고 응답은 탐욕적 정규식 `\{[\s\S]*\}`로 JSON을 뽑아 해석한다.
온도는 0.7이고 `thought`는 120자로 자른다.
도구 이름을 목록으로 알려 주지 않고 모델의 기본 도구 호출 기능도 쓰지 않는다.
`OfficeRoom.ts`가 에이전트마다 `capabilities`에 도구 이름과 설명을 적어 두지만
`think()`는 그 값을 프롬프트에 넣지 않는다.
따라서 모델이 도구 이름을 우연히 맞히거나 지어내야 도구가 불린다.
`PromptBuilder`는 도구 목록을 넣도록 만들어져 있으나 서버가 호출하지 않는다.
결정은 말하기, 작업 만들기, 에이전트 고용, 도구 호출로 바뀐다.

고용은 도구 `hire_agent`이고 `hireCount < 5` 조건(330줄)으로 최대 5명까지, 곧 7명까지 늘 수 있다.
고용된 에이전트는 문(20, 2)에서 나타나 자기 책상으로 걷는다.
기억을 불러오는 코드는 Alice와 Bob에게만 있다.
작업 배정은 화면의 `assign-task` 메시지나 에이전트의 `create_task` 호출로 문자열을 정하는 것이고
그 문자열은 다음 프롬프트에 들어갈 뿐 완료 경로가 없다.
에이전트 사이의 메시지는 편지함 구조로 오간다.

### 움직임은 결정과 따로이다

각 에이전트는 자기 책상 좌표로 걷고, 행동이 `talk`이면 가장 가까운 에이전트에게 걷는다.
이동은 500ms마다(5틱) 한 칸이고 x를 먼저 맞춘 뒤 y를 맞추며 2~36 범위로 자른다.
`talk`일 때 걸어가는 상대는 메시지의 대상이 아니라 맨해튼 거리가 가장 가까운 에이전트이다.
`furnitureTargets`의 커피 머신, 화이트보드 같은 항목은 `<id>-desk` 키로만 조회되어 쓰이지 않고 길찾기도 없다.
`Decision` 타입에는 `move`가 있지만 프롬프트가 알려 주지 않고 서버도 처리하지 않는다.
화면은 Phaser 3와 React이고 사무실을 Graphics로 그린다.
캐릭터 스프라이트는 16×32이며 `char_0`과 `char_1`만 불러온다.
클라이언트에 상태 기계가 없고 서버가 자유 문자열 `action`을 보내면
위치 변화로 걷는 방향을 고르고 이모트와 생각 말풍선을 띄운다.
`Game.ts`는 이름에 Bob이 들어가면 `char_1`, 나머지는 모두 `char_0`을 쓰므로 고용된 에이전트도 Alice와 같은 모습이다.
이모트는 3초, 생각 말풍선은 6초 뒤에 사라진다.
접속 주소는 저장된 값, 전역 변수 `__AGENT_OFFICE_WS_URL`, 현재 호스트의 3000번 포트 순으로 고른다.

### 서버와 저장

Express와 Colyseus가 3000번 포트에서 돌고 인증과 입력 검사는 없다.
SQLite(`./data/office-memory.db`)에 기억, 작업, 배치를 저장한다.
Redis와 `DATABASE_URL` 설정은 쓰이지 않고 `db.ts`는 죽은 코드이다.
임베딩은 저장하지만 `semanticSearch()`는 호출되지 않는다.

### 상태 동기화와 메시지

서버 상태는 Colyseus 스키마(`OfficeState.ts`)로 동기화되고 에이전트마다
좌표, `action`, `thought`, 기분, 평판, 위험, 추진력 네 수치를 가진다.
채팅, 하이라이트, 관계, 배치는 스키마가 아니라 `broadcast`로 보낸다.
클라이언트가 보내는 메시지는 `chat`, `start-scenario`, `trigger-chaos`, `assign-task`, `save-layout`이다.
어느 것도 보낸 사람을 확인하지 않으며 `chat`은 받은 텍스트를 그대로 모두에게 돌려보낸다.
HTTP로는 `POST /api/vote-chaos`와 `GET /api/episode-recap`이 있다.
투표는 같은 사건이 3표가 되거나 전체 표 수가 5의 배수가 되면 혼돈 이벤트를 일으키고
`voterId`는 기록만 할 뿐 중복을 막지 않는다.

### 기억과 임베딩

`Agent.addMemory()`는 50개를 넘으면 중요도 내림차순으로 정렬해 앞 50개만 남긴다.
이 정렬이 배열 순서를 바꾸므로 `getRecentMemories()`가 끝에서 고르는 항목은
최신이 아니라 중요도가 낮은 쪽이 된다.
이것은 코드를 읽고 내린 추론이며 실행해 보지 않았다.
저장은 결정마다 30% 확률로 최근 세 개(420줄)와 방 종료 시 전체(`onDispose`)로 나뉘어 중복 행이 생길 수 있다.
중요도 0.5 이상인 기억은 저장 전에 Ollama의 `/api/embeddings`를 `llama3.2:latest`로 호출한다.
주석은 비차단이라고 하지만 `await`하므로 그 호출이 끝날 때까지 저장이 기다린다.
불러올 때는 중요도 순 20개이며 임베딩은 쓰지 않는다.

### 에러 처리

Ollama 호출이 실패하거나 JSON 해석이 실패하면 `think()`가 오류를 기록하고
생각을 `Systems recovering...`, 행동을 `idle`로 돌려준다.
`fetch`에 시간 제한이 없어 Ollama가 응답하지 않으면 그 에이전트의 잠금이 풀리지 않는다.
`action` 값은 검증하지 않아 모델이 낸 임의 문자열이 그대로 클라이언트에 간다.

## 분석

### 관찰이 아니라 연극이다

이 프로젝트가 보여 주는 일은 실제 코딩이 아니라
LLM이 만든 텍스트와 몇 개의 실제 도구 호출이다.
화면의 “협업”은 모델이 고른 행동 이름이 걷기와 말풍선으로 번역된 것이다.
코드베이스에는 `jsonl`이나 `.claude`에 대한 참조가 없다.
Pixel Agents와 겹치는 것은 픽셀 사무실이라는 겉모양뿐이다.

## 비평

### “샌드박스” 코드 실행

`ToolExecutor.ts`의 `code_execute`는 모델이 만든 코드를
`exec(`node -e “...”`)`로 서버가 띄운 자식 프로세스에서 실행하고 큰따옴표만 이스케이프한다(60줄).
이 문서가 해당 줄을 직접 읽어 확인했다.
시간 제한은 코드 안의 5초 타이머와 `exec`의 6초 두 가지뿐이고
파일, 네트워크, 환경 변수를 막는 장치는 코드에 없다.
도구 문서는 파일과 네트워크 접근이 없다고 적지만 이 코드에서는 확인되지 않는다.
쉘 큰따옴표 안에서는 `$(...)`, 역따옴표, 역슬래시가 여전히 해석되므로
큰따옴표만 이스케이프하는 방식은 쉘 수준 주입을 막지 못한다고 읽힌다.
자식 프로세스가 서버 환경 변수를 물려받는다는 점은 Node의 기본 동작에 따른 추론이다.
인증 없는 서버와 합치면 프롬프트 주입이 원격 실행으로 이어질 가능성이 있다.
다만 프롬프트가 도구 이름을 알려 주지 않으므로 모델이 스스로 도구를 부르는 경로는 약하다.
`save-layout`과 `chat` 같은 열린 메시지가 직접 실행으로 이어지는 경로는 찾지 못했다.
이 문서는 그 연쇄를 실행해 시험하지 않았다.
`read_file`은 `..`과 맨 앞의 `/`만 걸러 내고 서버 작업 디렉터리 기준 상대 경로를 열어 500자를 돌려준다.
심볼릭 링크는 확인하지 않으며 읽은 결과는 기억(200자)과 채팅(100자)에 남는다.
`write_note`는 서버 로그에 출력할 뿐 파일에 쓰지 않는다.
`web_search`는 `TAVILY_API_KEY`가 있으면 Tavily, 없으면 DuckDuckGo 즉답 API로 나간다.

### 설명과 코드의 차이

- “OpenAI 호환 API로 바꿀 수 있다”는 설명과 달리 서버가 `OllamaAdapter`를 고정해서 쓴다.
  README의 교체 예시는 생성자 인자 순서와 `/v1` 중복이 틀렸다.
- 의미 검색, Redis, 고용한 에이전트의 저장은 실제로 쓰이거나 지속되지 않는다.
- 도커에서는 서버가 `localhost`로 Ollama를 부르므로 닿지 않는다.
- 레이아웃 편집기는 항목을 끌어 옮기고 저장하면 서버가 SQLite에 넣어 모든 클라이언트에 퍼뜨리지만
  에이전트의 걷는 목표에는 영향이 없다. CLI의 `add-agent`, `start`는 빈 구현이다.
- 도커 파일은 `package-lock.json`을 복사하는데 이 저장소에는 그 파일이 없다.
  이 문서는 빌드하지 않았으므로 실패 여부는 확인하지 못했다.
- 도커 구성의 `./data:/data` 볼륨과 달리 기억은 컨테이너의 `./data/`에 쓰이므로 지속되지 않는 것으로 읽힌다.
- README의 저장소 주소가 다른 사용자의 이름을 가리킨다.
- “바이럴 쇼러너” 층의 지표는 LLM이 아니라 난수 흔들림이다.

### 성숙도와 눈에 띄는 점

테스트는 파일 두 개에 각각 테스트 하나이고 서버가 쓰지 않는 모듈을 시험한다.
`TaskManager.test.ts`는 작업 생성 시 상태가 `pending`이고 배정하면 `in_progress`로 큐에 들어가는지 본다.
`PromptBuilder.test.ts`는 결과 문자열에 이름, 역할, 사무실 이름, 능력 문구가 들어 있는지만 본다.
서버, 도구 실행기, 저장소, 클라이언트에는 테스트가 없다.
CI는 없고 코드는 약 4,500줄이며 `package.json`은 1.0.0, 변경 기록은 0.0.2이다.
저장소에는 `pablodelucca/pixel-agents`의 전체 사본이 `pixel-agents-repo/` 아래
(파일 228개, 원 저자의 MIT `LICENSE` 포함)에 들어 있으나
작업 공간에 속하지 않고 아무것도 참조하지 않는다.
README는 마지막의 감사 문구에서만 이를 언급한다.
이 문서는 이미지의 출처를 확인하지 못했다.

## 인사이트

### 가져갈 것

LLM 에이전트끼리의 사회 시뮬레이션을 가볍게 시도해 보는 출발점으로는 읽을 만하다.
실제 코딩 에이전트의 감독 도구와는 목적이 다르다.
모델이 만든 코드를 서버 쉘에서 실행하는 도구는 격리 없이 인터넷에 열면 안 된다.

### 확인할 관찰

1. 코드 실행 도구가 컨테이너나 샌드박스로 격리되는지.
2. README의 교체 예시와 도커 설정이 고쳐지는지.
3. 저장소에 사본으로 들어 있는 원본의 라이선스 표기가 정리되는지.

위 셋 모두 이 문서가 확인하지 못했다.
