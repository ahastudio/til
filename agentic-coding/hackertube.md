# HackerTube: HN 댓글이 추천한 영상으로 하루 만에 만든 YouTube 대안

원문: [HackerTube](https://karpathy.bearblog.dev/hacker-tube/)

HN 토론: <https://news.ycombinator.com/item?id=50319510> (2143점, 498개 댓글)

GN 토론: <https://news.hada.io/topic?id=36351>

## 요약

Andrej Karpathy는 금요일 밤 11시에 YouTube를 열었다가 과장된 썸네일과 같은
주제의 반복 추천뿐인 화면을 봤다고 적었다.
알고리즘이 평균적인 사용자에게는 맞겠지만 자신에게는 맞지 않는다는
것이 출발점이다.
다음 날 아침 그는 Opus 5.5에게 Hacker News에서 추천된 영상으로 자기만의 YouTube
복제본을 만들라고 맡겼다.

Opus는 HN의 모든 댓글을 내려받아 걸러 냈다.
그다음 Claude Code의 Workflow 기능으로 Sonnet을 돌려 스팸을 지우고,
YouTube 영상을 추천하는 댓글 4만 개로 좁혔다.
결과는 2007년부터 2026년까지 몇 사람 이상이 추천한 영상 6,454개이고,
주제는 150개로 나뉜다.
이 위에 YouTube 모양의 화면을 얹고, 도메인을 사고,
VPS에 올려 보안과 최적화까지 마치는 데 약 2시간이 걸렸다고 한다.

사이트의 특징은 다섯 가지로 적혀 있다.
품질 좋은 콘텐츠, 업로드된 썸네일 대신 영상 중간 지점(50%) 장면을 쓰는 썸네일,
계정 없이 브라우저 세션에만 상태를 저장하는 맞춤 추천, 키보드 단축키,
그리고 자기 버전을 만들 수 있게 해 주는 데이터 내보내기다.

글 끝의 추가 설명에서 그는 작업 방식을 밝힌다.
Mac용 Claude Code 데스크톱 앱을 쓰고, 기본값은 Medium effort의 Opus 5.5다.
코드를 읽거나 터미널 명령을 직접 치는 전통적 엔지니어링은 하지 않고 Claude와
대화만 한다.
직접 한 일은 Google Cloud에서 YouTube 메타데이터 조회용 API 키를 만드는 것,
VPS를 띄우는 것, 도메인을 사는 것 세 가지다.
VPS가 뜬 뒤에는 IP만 알려 주고 업데이트, 배포, 보안 강화,
최적화를 맡겼다고 한다.

## 분석

### 이 프로젝트의 핵심은 사이트가 아니라 큐레이션(curation) 파이프라인이다

글이 내세우는 것은 YouTube 화면이지만, 실제로 만든 가치는 데이터를 거르는 앞
단계에 있다.
HN 댓글 전체에서 영상 추천이 담긴 댓글만 골라내고, 같은 영상을 서로 다른 사람이 추천했는지로 신뢰를 거르고, 주제를 150개로 나눈 과정이 그것이다.
화면은 이 데이터를 보여 주는 최소한의 표시 계층이다.

댓글을 읽은 사람 중에도 같은 지적이 있었다.
twalichiewicz는 가장 값진 부분이 큐레이션 파이프라인이므로,
별도 사이트를 쓰게 하지 말고 자동으로 갱신되는 재생목록을 YouTube 채널에 올리는
방식이 낫겠다고 제안했다.[^twalichiewicz]
데이터를 zip으로 공개한 이유도 여기서 읽힌다.
파이프라인의 산출물이 곧 제품이라는 판단이다.

### 비용 구조는 작은 모델 호출에 몰려 있다

비용은 글에 없고 HN 댓글에서 나왔다.
sc970이 토큰이 얼마나 드는지 묻자 Karpathy는 구독을 쓰고 있지만 Claude에게
합산을 시켰다며, 입력 5억 400만 토큰(90%가 캐시)과 출력 760만 토큰이라고 답했다.
그중 90% 이상은 댓글에 라벨을 붙이는 Sonnet 호출이었고,
앱과 배포를 포함한 실제 작업은 Opus 5.5의 약 100만 토큰이었다. 컨텍스트 압축은
한 번 했다.[^karpathy-tokens]

작업을 하는 모델이 쓴 토큰은 전체의 작은 부분이고,
대량의 분류가 대부분을 차지한다.
mips_avatar는 이 작은 데이터셋에 Sonnet 사용료가 약 300달러 든다고 어림하며,
Sonnet만큼 정확하면서 10배에서 100배 싼 분류용 모델이 있으면 좋겠다고
적었다.[^mips_avatar]
이 300달러는 댓글 작성자의 추정이다. 글이나 Karpathy의 답에는 금액이 없다.

### 서버 코드는 공개하지 않고 데이터만 공개했다

서버 코드는 어디 있느냐는 질문에 Karpathy는 바이브 코딩으로 만든 엉망진창이라
공개하지 않았다고 답했다.
대신 about 페이지의 zip을 Opus 5.5에게 주고 YouTube 같은 사이트를 만들라고 하면
거의 즉시 된다고 했다.
다만 YouTube 데이터는 배포할 수 없어서,
그 부분은 무료 API 키를 직접 만들어야 한다는 단서를 붙였다.[^karpathy-source]

여기서 공유의 단위가 바뀐다.
코드가 아니라 데이터와 그 데이터를 다시 만드는 지시가 배포 대상이 된다.

## 비평

### 2시간이라는 숫자는 숨은 전제를 지운다

글은 2시간이면 된다고 말하지만, 그 시간에는 Karpathy가 이미 가진 것들이
들어 있지 않다.
HN 전체 댓글을 내려받을 수 있는 공개 API가 있다는 점, 구독 한도 안에서 5억 토큰을 쓸 수 있다는 점, Claude Code와 Workflow를 이미 능숙하게 쓴다는 점이다.

댓글 중에도 같은 의문이 나왔다.
codingisfreedom은 같은 모델을 써도 자신은 이만큼 끈질긴 결과를 얻지 못한다며,
어떤 프롬프트가 에이전트를 깊이 파게 했는지 궁금해했다.[^codingisfreedom]
글은 이 질문에 답하지 않는다. 프롬프트와 중간 점검 방식은 공개되지 않았다.

HN의 공개 API에 대해서는 dang이 한 가지를 보탰다.
Firebase 기반 API로 댓글을 내려받기는 쉽지만,
누가 누구에게 답했는지 스레드를 복원하려면 번거롭다고 했다. 그래서 어떤 HN
URL이든 JSON으로 돌려주는 API를 직접 운영하는 방식으로 바꾸는 작업을 시작했다고
한다.[^dang]
이 프로젝트가 쉬웠던 이유의 일부는 HN이 데이터를 열어 둔 데 있다.
같은 방법을 데이터가 닫힌 플랫폼에 쓸 수는 없다.

### 신뢰 신호가 HN 사용자층에 맞춰져 있다는 점을 다루지 않는다

글은 알고리즘이 평균적인 사용자에게는 맞을 것이라고 짚고 넘어간다.
mwambua는 이 말이 인터넷 서비스 전반에서 반복된다며,
평균 사용자가 정말 더 나은 콘텐츠를 더 좋아할지,
그리고 좋아하지 않는다면 대중에게 질 낮은 콘텐츠를 계속 보여 주는 일의 윤리는
무엇인지 물었다.[^mwambua]
이 질문은 글의 전제를 건드린다.
HackerTube의 품질은 HN 사용자라는 좁고 취향이 비슷한 집단의 추천에서 오고,
그 집단은 평균과 다르다.

mi_lk는 더 직설적으로, 그럭저럭 괜찮은 편이지만 Karpathy라서 메인에 올랐을 뿐인
바이브 코딩 사이트라고 적었다.[^mi_lk]
이 평가는 거칠지만, 같은 결과물을 무명 개발자가 올렸다면 같은 관심을 얻었을지는
글이 알려 주지 않는다.
HN 점수 2143은 아이디어만큼이나 저자의 이름이 만든 숫자일 수 있다.

### 데이터의 신선도와 규모가 글과 댓글에서 어긋난다

글은 영상이 6,454개라고 적었다.
sixtyj는 재생목록으로 열리는 영상이 14,139개라고 댓글을 달았다.[^sixtyj]
같은 데이터를 다르게 센 것인지, 그 사이에 데이터가 늘었는지는 확인하지 못했다.
어느 쪽이든 글의 숫자는 글을 올린 시점의 값이고,
이후 사이트가 바뀌었다는 점은 읽을 때 감안해야 한다.

또 clydeiii는 가장 새로운 영상이 5개월 전 것인 이유를 물었다.[^clydeiii]
이 질문에 대한 답은 읽은 범위에 없었다.
추천 댓글이 쌓이려면 시간이 필요하다는 구조적 한계가 있을 수 있지만,
이는 추정이다.
추천이 누적되어야 올라오는 목록은 새 영상에 불리하다.

## 인사이트

### 추천 알고리즘의 목표는 시청 시간이고, 사용자가 원하는 것과 같지 않을 수 있다

글은 알고리즘이 자신에게 맞지 않는다고만 말한다.
왜 그런지는 댓글에서 갈렸다.
rileymat2는 개인화 알고리즘이 사용자가 보고 싶어 하는 것이 아니라 계속 보게
만드는 것을 따르는 것이고, 그것이 측정 가능한 KPI라고 적었다.[^rileymat2]

이 구분이 맞다면 HackerTube가 더 나아 보이는 이유는 개인화를 덜 해서가 아니라
목표 함수가 달라서다.
추천의 근거가 시청 지속이 아니라 사람들이 다른 사람에게 권한 사실이다.
ssl-3의 경험도 이를 뒷받침한다.
그는 오랫동안 좋은 영상에 시청과 추천 신호를 꾸준히 준 결과 자기 피드가
좋아졌다고 적었다.[^ssl-3]
알고리즘이 나쁘다기보다, 어떤 신호를 주느냐가 결과를 정한다는 이야기다.

### 직접 만드는 비용이 낮아지면 서비스가 지킬 수 있는 것은 데이터다

Karpathy는 서버 코드를 공개하지 않으면서도 누구나 같은 사이트를 만들 수
있다고 봤다.
데이터가 있으면 화면은 몇 분이면 나온다는 계산이다.
doginasuit의 지적처럼 로고 색이 YouTube와 비슷해서 상표 분쟁 소지가 있다는
문제도 있었고, Karpathy는 이를 받아들였다.[^doginasuit]

화면과 기능을 따라 만드는 비용이 0에 가까워지면 서비스에 남는 것은 데이터와 그
위의 신뢰뿐이다.
okdood64는 이 영상 대부분이 YouTube가 광고 수익으로 크리에이터에게 지급하는 돈이
없었다면 존재하지 않았을 것이라고 적었다.[^okdood64]
HackerTube는 YouTube가 키운 콘텐츠 위에 얹힌 선별 계층이고,
YouTube의 영상 호스팅에 의존한다.
선별 계층을 만들기는 쉬워졌지만 그 아래 콘텐츠를 만드는 비용 구조는 그대로다.

### 사용자의 요청이 들어올 때마다 제품이 바뀌는 속도가 새 기준이 된다

이 스레드에서 가장 눈에 띄는 장면은 제품이 댓글에 응답하며 바뀐 것이다.
업로드 날짜 정렬을 요청한 댓글에 Karpathy는 곧바로 추가하고 푸시했다고 답했다.
이어 날짜 필터, 길이와 유형 필터, 정렬 옵션이 들어갔다는 변경 목록을
올렸다.[^karpathy-changelog]

댓글 하나가 몇 분 안에 배포되는 속도는 이전에는 소규모 팀의 전용 능력이었다.
앞으로는 공개 직후의 피드백에 얼마나 빨리 반영하느냐가 인기 있는 개인 프로젝트의
기본 기대치가 될 수 있다.
다만 이것은 이 한 건의 관찰이다.
유지보수 주기가 길어졌을 때 같은 속도가 유지되는지는 이 스레드로는 알 수 없다.
