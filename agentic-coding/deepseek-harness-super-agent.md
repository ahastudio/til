# DeepSeek Harness의 슈퍼 에이전트 설계: 세션을 구현 세부로 숨기는 두 단계 구조

트윗: [Exploring Super-agent Design: Towards a More Autonomous Agent System](https://twitter.com/deepseekharness/status/2116857257245987236)

HN 토론: <https://news.ycombinator.com/item?id=50326523> (2점, 0개 댓글)

## 요약

DeepSeek Harness 계정이 2026년 11월 1일에 올린 Twitter Article이다.
원문은 중국어이고 올라온 영어판은 기계 번역이라고 글 맨 앞에 적혀 있다.
이 글은 구조에 대한 아이디어를 다루며 DeepSeek Harness의 기존 기능을 소개하는
글이 아니라는 단서도 붙어 있다.

문제 제기는 이렇다.
코딩 에이전트는 사람이 계속 지켜보지 않아도 도구로 복잡한 문제를 풀게 되었지만,
지금의 에이전트는 여전히 세션 하나를 작업의 기본 단위로 삼는다.
세션은 서로 고립되어 있어서, 여러 작업을 병렬로 돌리는 사용자는 세션을 손으로
오가며 각 세션의 내용을 기억해야 한다.
저자들의 경험으로는 사람이 한 번에 따라갈 수 있는 활성 세션은 3~5개이고,
그래서 한 작업의 한계는 모델 능력이지만 여러 작업의 한계는 사람의 주의력이다.

해법으로 저자들은 에이전트를 어느 한 세션에서 분리해,
세션이 바뀌어도 맥락을 유지하고 여러 복잡한 작업을 서로 간섭 없이 동시에
처리하는 하나의 지속적인 존재로 만들자고 한다.
이것을 슈퍼 에이전트(Super-agent)라 부르고 네 가지 특성을 든다.
Continuous는 IM과 GitHub 댓글처럼 사용자가 이미 일하는 곳에서 하나의
에이전트처럼 느껴지는 것이다.
Productive는 여러 복잡한 작업을 병렬로 높은 수준으로 처리하고 이전 명령이 끝나기
전에 다음 지시를 받는 것이다.
Proactive는 단계별 지시를 기다리지 않고 환경의 이벤트를 감시하다가 처리할 가치가
있는 것에만 움직이는 것이다.
Persistent는 항상 켜져 있고 이상 상태에서 스스로 복구하는 것이다.

이를 받치는 다섯 모듈이 이어진다.
둘째 절의 두 단계 구조는 오래 사는 Router 계층이 모든 사람과의 상호작용과 전체
조율을 맡고, 맥락이 격리된 Worker 계층이 작업을 동시에 실행하게 나눈다.
Router는 작업을 직접 실행하지 않으며 Bash 도구가 없어도 된다고 한다.
Worker는 사람과 직접 말하지 않고 상태를 Router에 보고하며,
Router가 모든 답을 한다.

셋째 절의 이벤트 기반 설계에서는 그룹 채팅, 이메일, 캘린더 알림, 코드 리뷰 댓글,
CI 결과가 Trigger가 된다.
Trigger는 결정적인 코드로 먼저 거르고(Fast Path) 의미 판단이 필요한 후보만
모델에 보낸다(Slow Path).
같은 PR이나 IM 주제에서 이어지는 이벤트의 묶음을 Thread라 하고,
Worker가 Thread를 구독하면 후속 이벤트는 Router를 거치지 않고 코드가 Worker에게
직접 전달한다(subscription과 pass-through).
컨텍스트 창은 캐시처럼 다룬다. Inline은 곧 필요할 정보를 창 안에 넣고,
Spill은 길거나 드물게 쓰이는 정보를 창 밖에 두고 참조만 남긴다.
객체마다 ID가 있고 각 객체가 이웃 객체의 ID를 inline하므로,
모델은 참조를 따라 맥락을 한 단계씩 되살린다(Chain of Recall).
투기적 실행(speculative execution)도 쓴다. 팀 내부 사용자 그룹에는 누가 문제를
알리면 에이전트가 백그라운드에서 재현하고 수정을 찾아보고,
문제를 확인하고 간단한 수정을 찾은 경우에만 결과를 내놓는 정책이 있다.

넷째 절은 동기 `run()` 호출 대신 비동기 `start()`와 `stop()`을 쓰는 비동기 ReAct
루프로 전이중(full-duplex) 대화를 만들고,
채널마다 응답의 상세 수준을 달리한다. IM에서는 답변을 100단어로 제한하는 규칙이
효과적이었다고 한다.
다섯째 절은 Agent Loop를 돌리는 계산을 상태 없는 클라우드 컨테이너에,
세션 상태를 데이터베이스에 두고, 실행 환경은 각 단말의 가벼운 데몬이 명령을
실행하고 결과를 돌려주는 방식으로 분리한다. 사용자의 개인 컴퓨터를 연결하는
BYOM(Bring Your Own Machine)도 지원한다.
여섯째 절의 Watchdog은 주기적 메시지로 구동되는 독립 세션으로,
인프라 장애뿐 아니라 Worker가 실질적 진전이 있는지 목표에서 벗어났는지도
모델로 판단한다.

일곱째 절은 예비 실험이다.
전체 시스템 실험에서 슈퍼 에이전트는 작업 완료 시간이 p50 12.4분,
p95 15.7분이었고, 중립 프롬프트의 단일 세션 구조는 20.4분과 29.5분이었다.
Router 단독 실험에서는 판단이 필요한 Trigger 도착률을 분당 약 1건에서 약
40건으로 올릴 때 평균 배치 크기가 1.0에서 2.8로 늘고,
판단 하나당 분할 상환 추론 시간이 6.4초에서 1.6초로 줄었다.
여덟째 절은 열린 문제로 확장, 세션 없는 에이전트와의 협업 방식,
맥락 경계와 A2A 통신, 보안과 프라이버시를 든다.

## 분석

### 세션이 하던 두 가지 일을 분리하는 것이 설계의 출발점이다

글은 기존 설계에서 세션이 두 가지 일을 한다고 짚는다.
하나는 모델의 컨텍스트를 관리하는 일이고,
다른 하나는 사용자의 프로젝트 관리 단위가 되는 일이다.
제품을 아래의 세션에서 분리하면 프로젝트 관리가 세션 경계를 따를 필요가
없어진다고 저자들은 말한다.

이 분리가 중요한 이유는 사람의 주의력이 문제의 중심에 놓이기 때문이다.
저자들은 사람이 3~5개 세션까지만 따라간다는 경험을 근거로,
여러 작업의 한계가 모델이 아니라 사람의 주의력이라고 본다.
그렇다면 해법은 모델을 더 좋게 만드는 것이 아니라 사람이 관리해야 하는 단위를
줄이는 것이다.
세션을 구현 세부로 숨기고 사용자에게는 하나의 에이전트만 보이게 하는 구조는 이
진단에서 나온다.

### 연속성과 처리량의 맞바꿈을 두 계층으로 나눠 푼다

글은 모든 이벤트를 한 세션에 보내면 맥락은 가장 연속적이지만 ReAct 루프가 한
번에 한 단계씩 돌아 처리량이 낮고 서로 다른 작업의 중간 내용이 한 컨텍스트에
섞여 결과가 나빠진다고 설명한다.
이벤트마다 새 세션을 주면 처리량은 최대가 되지만 작업이 완전히 독립이 아닐 때
결과가 따로 놀고 여러 세션이 사용자에게 따로 답해 혼란스럽다.
Router와 Worker로 나눈 것은 이 두 극단 사이의 절충이다.

Agent Team과의 차이도 글이 직접 설명한다.
Agent Team은 복잡한 작업 하나를 단계로 쪼개 역할을 조율하므로 리더가 작업을 깊이
이해하고 자주 조율해야 하지만, Router는 작업 사이의 관계만 높은 수준에서
추적하고 개별 작업은 분해하지 않는다.
그래서 Router의 일이 예상보다 단순하고 가벼운 모델로도 속도와 품질을 낼 수
있었다는 것이 저자들의 경험이다.

### 컴퓨터 시스템의 용어로 에이전트의 문제를 옮겨 적는다

글은 설계 곳곳에서 컴퓨터 시스템의 개념을 빌린다.
Fast Path와 Slow Path로 이벤트를 걸러 모델 호출을 줄이고,
컨텍스트 창을 캐시로 보고 Inline과 Spill로 넣고 뺄 정보를 정하고,
지역성(locality)으로 이웃 정보를 미리 넣고,
투기적 실행으로 사람이 기다리는 시간을 줄이고, 계산과 저장을 분리하고,
독립된 제어 루프로 감시한다.
Router를 전체의 순서를 정하는 지점(global sequence point)이자 조율점이고
기억이라고 부르는 것도 같은 어휘다.

이 번역의 이점은 문제를 이미 연구된 형태로 보게 한다는 것이다.
예를 들어 “컨텍스트 창을 낭비하면 모델의 지능을 낭비한다”는 문장은 창을 한정된
캐시로 보기 때문에 나온다.
다만 이 번역이 어디까지 맞는지는 비평에서 다룬다.

## 비평

### 실험은 합성 작업이고 기준선이 약해서 구조의 효과를 크게 보이게 한다

저자들 스스로 실험이 합성 부하와 단순화한 환경이며 설정이 더 엄밀할 수 있다고
적고, 결과는 참고용이라고 밝힌다.
전체 실험은 약 300개의 메시지 중 작업 요청이 약 20개이고,
코딩 작업은 시간을 소비하는 도구로 흉내 냈다.
따라서 이 실험은 스케줄링과 조율을 재는 것이고,
각 작업을 얼마나 잘 해내는지는 재지 않는다.
글이 내세우는 Productive의 정의, 곧 여러 복잡한 작업을 각각 높은 수준으로
완수하는 것은 이 실험으로 검증되지 않았다.

비교 대상인 단일 세션 구조도 한 가지 방식뿐이다.
중립 프롬프트에서는 다섯 번 모두 모델이 하위 에이전트를 부르지 않고 직접 일을
했고 p95가 29.5분까지 올랐다.
위임을 우선하라는 프롬프트에서는 다섯 번 중 네 번 위임했고 완료 시간이 줄었지만,
p95는 29.0분으로 거의 같았다.
단일 세션이 지는 이유로 글이 든 것은 프롬프트와 모델의 즉석 판단에
의존한다는 점이다.
이 결과는 두 단계 구조가 낫다는 증거이기도 하지만,
프롬프트만 바꾼 두 가지 설정이 단일 세션 구조의 가능한 설계를
대표하는지는 알 수 없다.
Router의 구조 없이 위임 규칙을 코드로 강제하는 단일 세션 같은 중간 설계는
비교되지 않았다.

비용도 같이 읽어야 한다.
슈퍼 에이전트는 실행당 캐시 읽기 토큰이 2,320만이고 중립 프롬프트 단일
세션은 610만이다.
글은 토큰을 시간과 맞바꿨다고 적지만, 이 맞바꿈이 금액으로 얼마인지는
제시하지 않는다.

### 사람의 주의력이 한계라는 전제는 Router의 응답으로 옮겨 간다

전제는 사람이 3~5개 세션을 따라갈 수 있다는 저자들의 경험이다.
이 숫자에 대한 측정이나 출처는 글에 없다.
그리고 해법은 세션 수를 줄여 보이게 하는 것이어서,
사람이 확인해야 할 것이 Router의 답변으로 모인다.

Router는 IM에서 100단어 이내로 짧게 답하고,
결정이나 승인이 필요할 때만 알리라고 한다.
그러면 사용자는 Worker의 추론이나 도구 호출을 보지 못하고 Router의 요약만 본다.
Worker가 어떤 근거로 무엇을 했는지 사용자가 확인하는 경로는 글에 나오지 않는다.
열린 문제 절에서 사용자가 중간에 개입하는 방식을 더 탐색할 만하다고
인정하는 데 그친다.
주의력 부담이 사라지는 것이 아니라 Router의 요약을 얼마나 신뢰하느냐의
문제로 바뀐다.

### Router가 가볍고 하나로 충분하다는 결론은 한 팀의 규모에서만 확인되었다

글은 Router의 일이 예상보다 단순하고 가벼운 모델로 충분하다고 하며,
단일 장기 세션이 지금 팀 규모에는 충분하다고 한다.
Router 실험은 실제 모델에 Worker는 모의 모델로 돌렸고,
Trigger 도착률은 분당 40건까지였다.
평균 배치 크기가 2.8까지 늘었고 요청당 시간은 2.5초에서 3.9초로 늘었다.

이 결과는 배치가 효과가 있다는 것을 보이지만,
Router가 오래 돌 때의 맥락 문제는 재지 않았다.
글 스스로 Router가 모든 작업의 전체 이력을 컨텍스트에 담을 수 없어 오래된 작업은
Chain of Recall로 되살린다고 설명하는데,
Chain of Recall이 얼마나 정확히 되살리는지에 대한 측정은 없다.
몇 달 단위의 운영에서는 장기 기억이 주된 병목이 된다고 저자들도 열린
문제에서 인정한다.
Router를 여러 세션으로 나누면 처리량은 늘지만 세션 사이에 공유되는 기억과 맥락은
줄어든다는 맞바꿈도 글이 직접 적는다.

### 이벤트로 구동되는 에이전트의 보안은 마지막 절로 미뤄져 있다

슈퍼 에이전트의 가치는 그룹 채팅, 이메일,
코드 리뷰 댓글처럼 신뢰할 수 없는 입력에 항상 반응하는 데서 나온다.
가장 눈에 띄는 사례는 아무도 @로 부르지 않았는데 공개 그룹 채팅에서 버그를 찾아
PR을 여는 동작이다.
글은 보안과 프라이버시를 여덟째 절에서 열린 문제로 다루며,
클라우드의 Agent Loop가 외부 이벤트를 계속 받는 동안 단말은 비공개 코드와 자격
증명을 가지고 있다고 인정한다.
서버 침입이나 프롬프트 주입으로 Agent Loop가 탈취되면 연결된 모든 단말이 장악될
수 있고, 자격 증명이 모델의 컨텍스트에 들어갈 수 있는 한 정상 실행만으로도
노출될 수 있다고 쓴다.

이 위험은 설계의 가운데 있는데 실험이나 완화책은 글에 없다.
Router에 Bash 도구를 주지 않는 것은 권한을 나누는 한 방법이지만,
글은 그 목적을 성능 병목을 피하는 것으로 설명한다.
Watchdog은 전체 도구를 가진 세션이 주 시스템의 프롬프트와 Trigger 규칙을 실행
중에 바꿀 수 있게 하므로 그 자체가 높은 권한의 에이전트다.
이 권한을 누가 어떻게 제한하는지는 글에 나오지 않는다.

## 인사이트

### 세션을 숨기면 제품의 단위가 대화창에서 작업이 일어나는 곳으로 옮겨 간다

글은 채팅 창이 상호작용의 중심이 된 것은 경로 의존의 영향이 크다고 보고,
더 많은 상호작용이 도메인 전용 인터페이스로 옮겨 갈 수 있다고 한다.
저자들의 인스턴스가 GitHub 이슈와 PR 안에서 바로 일하는 것이 그 예다.
같은 작업이 IM 그룹 채팅에서 시작해 GitHub PR 리뷰에서 이어지는 장면이
글의 데모다.

이것은 에이전트 제품의 경쟁 영역이 어디인지를 바꾼다.
세션이 단위이던 때에는 대화창이 곧 제품이었고,
세션이 구현 세부가 되면 사용자가 일하는 곳(이슈 트래커, 메신저,
이메일)에 얼마나 깊이 들어가 있느냐가 제품이 된다.
그 대가로 사용자는 에이전트의 중간 과정을 직접 볼 기회를 잃고,
어떤 채널에 어떤 수준으로 보고받을지를 정책으로 정해야 한다.
글은 프로젝트 관리와 상호작용이 사용자의 작업 영역과 스타일에 크게 의존하므로
최종 설계는 고도로 맞춤화될 것이라고 전망한다.

### 컴퓨터 시스템의 비유가 성립하지 않는 지점이 설계의 위험이 된다

캐시는 정확한 내용을 더 빨리 가져오는 장치이고,
캐시 적중과 실패는 결과의 정확성을 바꾸지 않는다.
컨텍스트 창을 캐시로 보는 비유에서 Spill은 내용을 요약이나 참조로 바꾸는 손실
있는 변환이다.
창 밖으로 나간 정보를 되살리는 일은 모델이 참조를 따라가기로 판단해야
일어나므로, 필요한 것을 놓치면 실패가 조용히 일어난다.
Chain of Recall은 모델이 다음 참조를 올바르게 고른다는 가정 위에 서 있다.

투기적 실행도 마찬가지다.
CPU의 투기적 실행은 틀린 가정의 결과를 폐기해도 부작용이 없게 설계된다.
에이전트가 사람의 확인 없이 PR을 열거나 메시지를 보내는 일은 되돌릴 수
없을 수 있다.
글의 사례는 문제를 확인하고 간단한 수정을 찾은 뒤에만 결과를 내놓는 정책이어서
이 위험을 의식하고 있지만, 그 정책이 모델의 판단에 달려 있다는 점은 같다.
비유가 주는 설계 어휘는 유용하지만, 정확성이 결정적인 시스템과 확률적인 모델
사이의 차이가 각 모듈에서 어떤 형태로 나타나는지 하나씩 확인해야 한다.

### 사람의 주의력을 아끼려고 토큰과 상시 가동을 쓰는 구조는 어디까지 값이 맞는지 묻게 한다

슈퍼 에이전트는 항상 켜져 있고, 이벤트마다 Router가 판단하고,
투기적 실행으로 쓰이지 않을 수도 있는 일을 미리 하고,
Watchdog이 주기적으로 깨어 Worker를 점검한다.
이 각각이 토큰과 계산을 쓴다.
실험에서도 슈퍼 에이전트의 캐시 읽기 토큰은 단일 세션보다 많았고,
글은 이를 더 짧고 안정적인 완료 시간과 맞바꾼 것이라고 설명한다.

이 맞바꿈이 성립하는 조건은 사람의 주의력이 토큰보다 훨씬 비싼 자원일 때다.
저자들의 팀처럼 에이전트로 개발 자체를 하는 팀에서는 그럴 수 있다.
하지만 이벤트가 적고 대부분의 일이 한 번에 하나씩 이루어지는 개인 사용자에게는
같은 구조가 토큰만 더 쓸 수 있다.
글도 구조가 필요한 때를 여러 작업을 병렬로 돌리는 사용자와 팀으로 한정해 말한다.
도입을 따질 때는 같은 시간에 병렬로 돌리는 작업이 몇 개인지와,
이벤트 중 에이전트가 움직일 가치가 있는 비율이 얼마인지가 먼저 나와야 한다.
