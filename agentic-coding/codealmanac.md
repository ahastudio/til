# CodeAlmanac - AI 코딩 에이전트를 위한 코드베이스 위키

<https://github.com/AlmanacCode/codealmanac>

HN 토론: <https://news.ycombinator.com/item?id=48995181> (60점, 21개 댓글)

## 소개

CodeAlmanac는 "AI 코딩 에이전트가 직접 관리하는, 코드베이스를 위한 살아있는
위키"를 표방하는 로컬 우선 마크다운 문서화 도구다.
소스 코드만으로는 전달할 수 없는 맥락, 즉 시스템이 왜 지금과 같은 구조로
설계되었는지, 과거에 어떤 실패가 있었는지, 어떤 불변 조건을 지켜야 하는지,
여러 파일에 걸친 작업 흐름은 무엇인지를 구조화된 문서로 남기는 것을
목표로 한다.
AI 에이전트가 매 세션마다 코드베이스를 처음부터 다시 파악하는 대신,
누적된 위키를 참조해 맥락을 빠르게 얻도록 하려는 문제의식에서 출발했다.

## 아키텍처

모든 위키 콘텐츠와 실행 상태는 사용자의 로컬 머신에만 존재한다.
위키 페이지 자체는 저장소 안의 `almanac/` 폴더에 마크다운으로 저장되고,
파생 인덱스와 작업 기록은 `~/.codealmanac/` 아래에 보관된다.
페이지는 의미 단위 폴더로 구성되며, 폴더 간 이동을 위한 `topics.yaml`
파일이 함께 관리된다.
AI 실행기(runner)로는 OpenAI Codex와 Anthropic Claude를 모두 지원하며,
이 경계는 `almanac-yoke`라는 SDK를 통해 추상화된다.

핵심 동작 주체는 세 가지 "라이프사이클 에이전트"다.

- Build: 초기 위키 구조를 생성한다.
- Ingest: 파일, Git diff, GitHub PR/이슈, URL, 에이전트 트랜스크립트 등에서
  지식을 추출해 위키에 반영한다.
- Garden: 오래된 페이지, 중복 콘텐츠, 깨진 링크, 약한 연결을 찾아내
  위키 품질을 유지·보수한다.

이 세 에이전트 위에 자동화 계층이 얹힌다.
기본값 기준으로 5시간마다 동작하는 Sync 작업은 에이전트 대화 트랜스크립트를
훑어 ingest 큐에 넣을 지식을 찾고, 24시간마다 동작하는 Garden 작업이
자동 정비를, 역시 24시간마다 동작하는 Update 작업이 CLI 자체를 최신
상태로 유지한다.
읽기 전용 로컬 뷰어도 제공되어 브라우저에서 페이지, 검색, 토픽, 백링크,
파일 참조를 확인할 수 있다.

## CLI

설치는 `uv tool install codealmanac@latest` 실행 후 `codealmanac setup`으로
진행한다.
과거 npm 패키지는 폐기되었고, 현재는 PyPI 배포만 유지된다.

자격 증명 없이 쓸 수 있는 읽기 명령으로 `codealmanac search "<query>"`,
`codealmanac show <page-name>`, `codealmanac serve`, `codealmanac topics`,
`codealmanac health`가 있다.
AI 제공자 인증이 필요한 쓰기 명령으로는 위키를 새로 만드는
`codealmanac init`, 소스에서 지식을 반영하는
`codealmanac ingest <source> --using [codex|claude]`, 정비를 수행하는
`codealmanac garden --using [codex|claude]`가 있다.
작업 관리용으로 `codealmanac jobs`, `codealmanac jobs show <run-id>`,
`codealmanac jobs attach <run-id>`가 제공되고, 설정 관리용으로
`codealmanac config set <key> <value>`, `codealmanac automation status`가
있다.

`setup` 명령은 대화형으로 진행되며, 선택한 AI 도구(Codex 또는 Claude)에
맞는 에이전트 지침을 설치하고, 자동화를 위한 macOS `launchd` 작업 세 개를
등록하며, 익명 원격 측정(telemetry) 활성화 여부와 자동화 주기를
사용자가 직접 정할 수 있게 한다.
설정값은 `~/.codealmanac/config.toml`에 저장되며 기본 AI 하네스, Git
변경사항 자동 커밋 여부, 자동화 스케줄 등을 담는다.

## 주요 기능

- 저장소 내부에 위치하는 로컬 마크다운 위키로, 별도 서버나 클라우드
  동기화 없이 동작한다.
- Codex/Claude 두 가지 코딩 에이전트를 모두 실행기로 지원한다.
- 대화 트랜스크립트에서 지식을 자동으로 추출해 위키에 반영하는 Sync
  파이프라인을 갖춘다.
- 위키 자체의 노후화·중복·깨진 링크를 찾아 정리하는 Garden 자동화를
  제공한다.

## 라이선스 및 상태

Apache-2.0 라이선스로 공개되어 있으며, 이 글 기준 GitHub 스타 675개를
받았고 Y Combinator S26 배치에 속한 스타트업이 개발하고 있다.
현재 계약(contract)은 로컬 전용 동작만 지원하며 호스팅 로그인이나
클라우드 동기화는 없고, 단일 저장소의 `almanac/` 위키 루트만 지원한다.
공개 SDK나 MCP(Model Context Protocol) 패키지는 아직 없고, 위키·코드·
프롬프트·트랜스크립트를 업로드하는 기능도 없다.
지원 환경은 macOS이며 Codex 또는 Claude Code CLI가 설치되어 있어야 한다.
라이프사이클 에이전트는 `almanac/` 디렉터리에 대해 넓은 파일시스템
권한을 갖고 샌드박스 없이 동작하므로, 위키 변경사항을 반영하기 전
Git diff를 검토하도록 안내하고 있다.

## 분석

### 코드가 아니라 "왜"를 저장한다는 발상

CodeAlmanac이 겨냥하는 문제는 코드 자체의 부족이 아니라 코드 주변
맥락의 휘발이다.
왜 이런 구조를 택했는지, 과거에 어떤 접근이 실패했는지, 어떤 불변
조건을 깨면 안 되는지는 커밋 메시지나 PR 설명, 사람의 기억 속에
흩어져 있다가 시간이 지나면 사라진다.
AI 에이전트가 매번 코드베이스를 처음부터 추론해서 재구성하는 대신
누적된 지식을 참조하게 만들겠다는 발상은, 결국 "에이전트에게도
조직의 암묵지가 필요하다"는 관찰에서 나온다.
이는 사람 개발자가 온보딩 문서나 아키텍처 결정 기록(ADR)을 필요로
하는 것과 본질적으로 같은 문제이며, CodeAlmanac은 그 역할을 사람이
아니라 에이전트가 스스로 작성·유지하도록 뒤집었다는 점에서
독특하다.

다만 Hacker News의 실제 제작자 설명을 보면 이 발상의 출발점은
더 구체적이다.
개발자가 Claude나 Codex와 나눈 대화 자체에 상당한 지식이 담겨
있는데, 이를 문서화하지 않으면 그냥 사라진다는 관찰에서
시작했고, 예전에는 `MANUAL.md`나 `DESIGN.md` 같은 파일을 직접
만들어 에이전트에게 갱신을 맡겼지만 금방 낡고 지저분해지는
문제를 겪었다고 밝힌다[^divitsheth].
즉 CodeAlmanac은 완전히 새로운 문제의식이라기보다, 많은 개발자가
이미 임시방편으로 해오던 작업을 자동화 파이프라인으로 정형화한
것에 가깝다.

### 세 에이전트 분업 구조가 노리는 것

Build/Ingest/Garden이라는 역할 분리는 단순히 기능을 나눈 것이
아니라, 위키가 시간이 지나며 겪는 세 가지 실패 양상에 각각
대응한다.
Build는 처음부터 다시 시작해야 하는 콜드 스타트 문제를, Ingest는
지속적으로 발생하는 신규 지식의 반영 문제를, Garden은 문서가
쌓이면서 필연적으로 발생하는 부패(stale, 중복, 깨진 링크) 문제를
맡는다.
이 구조는 소프트웨어 유지보수의 오래된 패턴, 즉 "생성-갱신-정리"
사이클을 에이전트 자동화로 옮긴 것에 가깝다.
다만 이 세 역할이 모두 자동화 스케줄(5시간/24시간/24시간)에 묶여
있다는 점은, 위키의 신뢰성이 결국 이 주기적 실행이 실제로 유의미한
품질의 변경을 만들어내는지에 달려 있다는 뜻이기도 하다.

### 로컬 우선 설계가 신뢰 모델을 대신한다

클라우드 동기화나 호스팅 로그인이 없는 로컬 전용 설계는 초기
채택 장벽을 낮추는 동시에, 신뢰 문제를 다른 방식으로 떠넘긴다.
위키와 상태가 전부 로컬에 있다는 것은 팀 단위 공유나 다인 협업이
기본적으로 지원되지 않는다는 뜻이며, 여러 개발자가 같은 위키를
갱신하려면 Git을 통한 커밋·리뷰 절차에 의존해야 한다.
README가 "review Git diffs before accepting wiki changes"라고
못박아 둔 것은 이 설계의 자연스러운 귀결이다.
라이프사이클 에이전트가 샌드박스 없이 넓은 파일시스템 권한으로
동작한다는 점과 합쳐 보면, CodeAlmanac은 자동화의 편의와 신뢰의
책임을 사용자에게 명시적으로 되돌려주는 쪽을 택한 셈이다.

## 비평

### 위키의 정확성을 검증할 장치가 약하다

Garden 에이전트가 오래된 페이지와 중복, 깨진 링크를 찾아낸다고
설명하지만, 이는 형식적 결함을 발견하는 것이지 내용의 사실성을
검증하는 것과는 다르다.
에이전트가 코드 diff를 잘못 해석해 틀린 설계 이유를 위키에 적어
넣으면, 이후 다른 에이전트는 그 틀린 서술을 "신뢰할 수 있는 맥락"
으로 받아들여 더 잘못된 결정을 내릴 위험이 있다.
소스 코드는 실행 가능하므로 최소한 컴파일이나 테스트로 오류가
드러나지만, 자연어로 적힌 위키 문서는 오류가 조용히 누적되어도
드러날 방법이 마땅치 않다.
README 어디에도 위키 내용에 대한 사실 검증이나 사람의 승인 절차가
필수 단계로 명시되어 있지 않다는 점은, "누적된 지식"이라는 가치
제안의 신뢰도를 스스로 갉아먹을 수 있는 지점이다.
실제로 R&D 분야에서 사람 주도로 Opus를 활용해 온 한 Hacker News
사용자는, 강한 가이드 없이 세션에서 재사용 가능한 지식을 잘
추출하는 AI를 본 적이 없다고 증언한다.
구체적인 것을 추상화하는 시도는 자주 틀리고, 결과물은 구현 세부
사항과 개념적 도약을 뒤섞어 잘못된 추상화 수준에서 글을 쓴다는
것이다[^ajrouvoet].
이 증언이 맞다면 Garden 에이전트가 형식적 결함을 아무리 잘
정리해도, 애초에 Ingest 단계에서 만들어지는 문장 자체의 품질이
낮을 수 있다는 뜻이 되어 문제의 근원이 한 단계 더 앞으로
이동한다.

### 자동 트랜스크립트 흡수는 노이즈 문제를 감춘다

Sync 작업이 에이전트 대화 트랜스크립트를 스캔해 지식을 자동으로
큐에 넣는다는 설명은 매력적이지만, 실제 개발 대화의 상당수는
시행착오와 막다른 시도로 이루어진다.
어떤 대화가 "위키에 남길 가치가 있는 지식"이고 어떤 대화가 그저
실패한 탐색인지 자동으로 구분하는 일은 코드 diff를 요약하는 것보다
훨씬 어려운 판단이다.
README는 이 선별 기준을 구체적으로 밝히지 않은 채 자동화의
편리함만 강조하는데, 선별이 느슨하면 위키는 빠르게 저품질 정보로
채워지고, 반대로 선별이 지나치게 보수적이면 자동화의 존재
의미 자체가 줄어드는 딜레마에 놓인다.

### 단일 저장소·macOS 전용이라는 제약이 확장성 주장과 충돌한다

CodeAlmanac은 스스로 "현재 계약"이라는 표현으로 단일 저장소의
`almanac/` 루트만 지원하고, macOS 환경에서만 동작한다는 점을
명시하고 있다.
그런데 코드베이스 맥락이 가장 절실하게 필요한 환경은 대개 여러
저장소가 얽힌 마이크로서비스나 모노레포, 그리고 macOS만이 아니라
Linux 기반 CI/배포 환경까지 포괄하는 조직 규모의 개발팀이다.
현재 버전이 겨냥하는 사용자층(개인 개발자, 단일 저장소, macOS
로컬 작업)과, 이 도구가 궁극적으로 해결하고자 하는 문제(대규모
코드베이스에서 에이전트가 맥락을 잃는 문제)의 규모 사이에는
간극이 있고, 이 간극을 얼마나 빨리 좁히느냐가 도구의 실질적
채택 여부를 가를 것이다.
Hacker News에서도 같은 지점이 곧바로 지적되었는데, macOS 전용
제약이 파일시스템 구조에 대한 내장 지식 때문인지 아니면 더 근본적인
Apple 전용 도구·환경 의존성 때문인지를 묻는 질문이 나왔다[^colinb].
이는 README가 명시적으로 답하지 않는 부분이라, 단순히 초기
구현의 편의 때문인지 아니면 구조적 제약인지가 불투명하다.

### 자동화의 신뢰 전제가 실제 사용자에게는 부담으로 돌아온다

라이프사이클 에이전트가 넓은 파일시스템 권한을 갖고 샌드박스 없이
동작한다는 설계는 README에서 "review Git diffs before accepting
wiki changes"라는 문장으로 사용자에게 검토 책임을 넘긴다.
그런데 비슷한 사내 도구를 이미 운영해 본 한 Hacker News 댓글은
이 검토 책임이 실제로는 감당하기 어려운 부담이 된다고 지적한다.
결국 한 사람이 리뷰·스킴 역할을 전담하다가 압도당했고, 목적 자체가
"사람이 읽는 문서"에서 "AI가 토큰을 아끼며 다른 에이전트를 효율적으로
스폰하기 위해 참조하는 지식 그래프"로 바뀌었다는 것이다[^tdu01].
같은 맥락에서 macOS의 `sandbox-exec` 같은 도구로 에이전트를
샌드박스할 계획이 있는지 묻는 질문도 나왔는데[^pseufaux], 이는
CodeAlmanac이 제시한 "신뢰된 로컬 에이전트"라는 전제가 실사용
단계에서는 그대로 받아들이기 부담스러운 가정이라는 점을 보여준다.

## 인사이트

### 위키 자체가 새로운 공격면이 된다

라이프사이클 에이전트가 샌드박스 없이 파일시스템에 넓은 권한을
갖고 동작한다는 설계는, 코드 저장소 안에 "에이전트가 스스로 쓰고
읽는 신뢰된 텍스트 영역"을 만든다는 뜻이다.
만약 ingest 대상에 외부에서 온 콘텐츠(예: GitHub 이슈나 PR 본문,
URL)가 포함된다면, 공격자가 이슈나 PR 설명에 프롬프트 인젝션을
심어 위키 내용을 조작하고, 그 조작된 위키가 이후 다른 에이전트의
판단 근거로 쓰이는 간접 경로가 생길 수 있다.
이는 원문이 다루지 않은 위험이지만, "에이전트가 읽고 쓰는 지속적
저장소"라는 패턴이 보편화될수록 반드시 짚어야 할 지점이다.

같은 범주의 더 직접적인 위험을 Hacker News 댓글이 이미 짚었다.
디버깅 과정에서 대화 트랜스크립트에는 API 키나 `.env` 값 같은
비밀 정보가 그대로 붙여넣어지는 경우가 흔한데, Sync 에이전트가
이런 트랜스크립트를 읽어 `almanac/` 페이지로 옮기고 그 페이지가
그대로 Git에 커밋되는 것을 막을 장치가 있는지를 묻는 질문이다
[^satoyoshidev].
이는 프롬프트 인젝션처럼 외부 공격자가 필요한 시나리오가 아니라,
정상적인 디버깅 습관만으로도 발생할 수 있는 위험이라는 점에서
더 시급하다.
자동 커밋 옵션까지 켜져 있다면 비밀 정보가 원격 저장소 히스토리에
영구히 남을 수도 있다.

### 위키는 "지금 유효한 결정"만 남기고 "폐기된 이유"를 잃기 쉽다

한 Hacker News 댓글은 어떤 결정이 나중에 뒤집혔을 때, 위키
페이지가 그 자리에서 계속 덮어써지기만 한다면 애초에 어떤 접근을
시도했다가 명시적으로 포기했다는 신호 자체가 사라지는 것은 아닌지
묻는다[^w4v3z].
이는 Garden 에이전트의 설계와 정면으로 부딪히는 질문이다.
Garden은 "오래된" 정보를 정리하는 역할을 맡는데, 정리의 기준이
단순히 최신성이라면 폐기된 접근에 대한 기록은 정확히 정리
대상이 되어 사라질 위험이 크다.
그러나 "왜 이렇게 안 했는가"라는 정보는 "왜 이렇게 했는가"만큼이나
후속 작업자에게 중요하다.
결국 CodeAlmanac이 정말 필요로 하는 것은 최신 상태를 보여주는
단일 진실 공급원이 아니라, 결정의 역사를 층층이 쌓아 보여주는
버전 관리에 가까운 구조일 수 있다.

### 문서의 반감기 문제를 자동화로 이긴다는 것은 검증되지 않은 도박이다

기술 문서는 코드보다 반감기가 훨씬 짧다는 것이 오랜 경험칙이다.
사람이 관리하는 위키조차 방치되면 몇 달 안에 신뢰할 수 없는
상태가 되는데, CodeAlmanac은 이 반감기 문제를 사람 대신 에이전트가
주기적으로 순찰하며 늦추겠다는 내기를 걸고 있다.
이 내기가 성립하려면 Garden 에이전트의 판단 품질이 사람 관리자의
판단 품질에 근접해야 하는데, 현재 시점에서는 그 품질을 객관적으로
측정할 지표가 공개되어 있지 않다.
만약 이 접근이 성공한다면 "자동으로 스스로를 정비하는 문서"라는
패턴은 위키를 넘어 API 문서, 런북, 온보딩 가이드 전반으로 번질
잠재력이 있고, 반대로 실패한다면 "저품질 문서가 자동으로,
그리고 대량으로 생산되는" 부작용을 남길 수 있다.

### 에이전트 제공자 중립을 표방하지만 실제로는 소수 생태계에 종속된다

Codex와 Claude를 모두 지원한다는 점은 특정 벤더 종속을 피하려는
설계처럼 보이지만, 실제로는 이 두 생태계의 CLI 도구 존재 여부와
동작 방식에 강하게 의존한다.
`almanac-yoke`라는 추상화 계층이 이 경계를 흡수한다고 하지만,
새로운 코딩 에이전트가 등장할 때마다 이 계층을 확장해야 하는
유지보수 부담은 CodeAlmanac 개발팀에게 고스란히 남는다.
결국 "여러 에이전트를 지원한다"는 주장은 현재 두 개의 지원
대상에서 멈춰 있으며, 이는 생태계 중립이라기보다 초기 시장에서
가장 큰 두 플레이어에 맞춘 전략적 선택에 가깝다.
