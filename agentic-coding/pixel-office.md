# 픽셀 오피스: 구독형 AI CLI를 연결해 팀처럼 일하게 하는 Windows 앱

<https://github.com/MaoEmong/pixel-office>

GN 토론: <https://news.hada.io/topic?id=36418>

## 소개

픽셀 오피스(Pixel Office)는 여러 AI에게 일을 나누고 진행 상황과 결과를 픽셀
사무실 화면에서 확인하는 Windows 앱이다.
README의 설명으로는 사용자가 부장 AI에게 목표를 전하면 부장이 팀을 구성하고
일을 나눈다.
누가 작업하는지, 누구의 결과를 기다리는지 화면에서 보고,
사용자에게 온 질문과 실행 허가는 내 책상에서 확인한다.

현재는 Windows 10·11 64비트용 시험판이고 최신 배포는 0.2.6이다.
사용할 AI 프로그램의 설치와 로그인은 따로 해야 하며, 지원하는 것은 Claude Code,
Codex, Antigravity다.
이용 요금과 사용 한도는 각 서비스의 조건을 따른다.
저장소 정보로는 MIT 라이선스이고 2026년 10월 18일에 만들어졌으며,
이 글을 쓸 때 별은 1개였다.[^api]
저장소에는 사용 안내, 스크린샷, 배포 설명만 있고 앱의 소스 코드는 없다. 검증
기록은 원본 TypeScript와 Dart, 소스맵, 개발 도구를 ZIP에 넣지 않았다고
밝힌다.[^verification]

## 사용 흐름

시작은 ZIP 전체를 새 폴더에 풀고 `pixel_office.exe`를 실행하는 것이다.
실행 파일만 따로 옮기지 말라고 README가 당부한다.
준비 상태 확인을 누르고, 부서 만들기에서 작업 폴더와 사용할 AI를 고르고,
처음에는 허가 방식을 전부 묻기로 유지하라고 한다.
첫 요청도 파일을 수정하지 말고 프로젝트 구조를 설명해 달라는 작은 작업을 권한다.

부장과의 대화에서 원하는 결과와 완료 기준을 정하고, 대화, 팀별 의견, 작업 계획,
완료한 단계 기록을 한 화면에서 볼 수 있다.
사무실 위에서는 담당자 사이의 대기 관계가 보이고,
캐릭터를 누르면 기다리는 결과와 결과가 도착한 뒤 할 일이 나온다.
README는 화면 표시의 뜻을 표로 정리한다. 검사나 명령 실행 중은 별도로 실행한
작업이 남아 있다는 뜻이며 검사 통과를 뜻하지 않고,
미완료 업무 있음은 완료 보고가 남았다는 뜻이며 실제 명령의 실행 여부는 따로
확인해야 한다.

진행·기록에서는 요청 하나를 펼쳐 작업 과정, 완료 보고, 바뀐 파일,
파일 저장 지점을 본다.
README는 검사 결과가 AI가 보고한 내용이며 실행 기록만으로 통과했다고 표시하지
않는다고 적는다.
파일 저장 지점은 PC 안에 따로 보관하고 원래 프로젝트의 변경 기록이나 온라인
저장소는 바꾸지 않으며, 대화, 외부 데이터베이스, 웹사이트,
온라인 전송까지 되돌리지는 않는다.
이 기능을 쓰려면 Git이 필요하다.

그 밖에 프로젝트 문서(Markdown과 텍스트)를 앱 안에서 읽고 고치는 화면,
AI 서비스별 사용량 표시, 실행 중인 웹페이지를 등록하는 웹 미리보기(Microsoft
Edge WebView2 Runtime 필요), 휴대폰 브라우저로 접속하는 원격 접속이 있다.
원격 접속은 작업 PC를 켜 둔 채 별도 연결 설정과 기기 승인을 거친다.

## 사용 한도와 재개

상단의 AI 사용량에서 서비스별 사용량과 마지막 확인 시각을 본다.
확인할 수 없는 수치는 미확인으로 표시한다.
사용 한도가 소진되면 해당 부서의 실행을 멈추고 기존 업무, 대화,
완료 단계와 파일을 보존한다.

재개 방법은 두 가지다.
다시 확인하고 기존 AI를 재개하면, 기존 구성의 AI가 모두 사용 가능할 때 같은 AI와
같은 대화로 이어 간다.
교체하고 계속하면, 사용자가 다른 AI를 직접 고르고 기존 대화는 남긴 채 새 AI에
진행 요약과 남은 업무를 전달한다.
한도 갱신 시각이 지났더라도 실제로 사용할 수 있는지 다시 확인해야 하고,
AI 선택 목록을 열거나 항목을 고르는 것만으로는 재개하지 않는다고 한다.

## 키와 허가

키 저장소는 현재 프로젝트가 쓸 API 키, 로그인 아이디,
비밀번호를 이름과 값으로 저장한다.
해당 프로젝트의 부장, 팀장, 팀원이 `secret_list`로 이름과 설명을 보고
`secret_get`으로 값을 조회한다.
값은 Windows 계정에 연결된 암호화로 앱 데이터 폴더의 `secrets.vault`에 저장되고,
평문 대체 방식은 없다.
앱의 작업 기록, 오류 설명, 서버 로그에서는 등록된 원문 값을 가리지만,
값을 AI에 넘기면 그 AI 서비스와 CLI의 대화와 터미널 기록에 포함될 수 있고 앱의
가림 처리가 그것을 지우지는 못한다고 문서가 직접 적는다.[^keys]

모든 권한 허용은 이해 확인에 체크해야만 켤 수 있다.
켜면 해당 프로젝트의 부장, 팀장, 팀원이 보낸 허가 요청을 자동으로 허용하며,
파일 삭제, 프로그램 설치, 명령 실행, 온라인 전송, 작업 폴더 밖 접근도 포함한다.
자동 허가의 이유는 기록에 남고 켜져 있는 동안 상단에 표시되며,
기본값은 전부 묻기다.[^keys]

## 분석

### 화면 표시가 무엇을 뜻하고 무엇을 뜻하지 않는지를 먼저 적는다

여러 AI의 작업을 한 화면에 모으면 표시가 사용자의 판단으로 직결된다.
README는 상태 표시마다 뜻과 함께 뜻하지 않는 것을 적는다.
검사 실행 중은 통과가 아니고, 미완료 업무 있음은 명령이 실행 중이라는 뜻이
아니며, 지시 접수 확인 필요는 AI가 지시를 받았는지 아직 확인되지
않았다는 뜻이다.

이 서술 방식은 보고된 결과와 확인된 결과를 나눈다.
진행·기록의 검사 결과에 대해서도 README는 AI가 보고한 내용이고 실행 기록만으로
통과했다고 표시하지 않는다고 말한다.
오케스트레이션 도구에서 가장 쉽게 생기는 오해는 에이전트의 완료 보고를 사실로
읽는 것인데, 표시의 의미를 문서에 분명히 적어 이를 줄이려 한 설계다.

### 사람의 개입 지점을 한곳으로 모은다

질문과 실행 허가가 내 책상 한곳에 모이고, 크게 보기에서 요청한 담당자,
작업 설명, 실제 실행 내용을 읽을 수 있다.
AI끼리 주고받는 질문은 상사의 답변 대기로 구분해 사용자의 책상에
섞이지 않게 한다.
여러 에이전트가 병렬로 일할 때 사람이 가장 부족한 자원이므로,
사람에게 오는 요청을 한곳에 모으고 AI 사이의 요청은 거르는 것은 맞는 방향이다.

다만 그 효과는 요청의 수가 사람이 읽을 수 있는 범위에 있을 때 성립한다.
README는 허가 요청이 얼마나 자주 올지, 많아졌을 때 어떻게 묶거나 줄이는지는
설명하지 않는다.
모든 권한 허용이라는 선택지가 있는 것은 이 문제를 사용자가 스스로 푸는
방법이기도 하다.

### 한도 소진을 장애의 한 종류로 다룬다

구독형 AI CLI를 묶는 도구에서는 사용 한도가 일상적인 중단 원인이다.
이 앱은 한도 소진을 오류가 아니라 정해진 상태로 다루고,
부서 단위로 실행을 멈추고 대화와 업무를 보존한 뒤 재개 경로를 둘로 나눈다.
같은 AI로 이어 가는 경로와 다른 AI로 갈아타는 경로를 사용자가 고르게 하고,
목록을 여는 것만으로는 재개하지 않는다.

이 설계는 자동 전환을 하지 않는다는 선택을 보여 준다.
다른 AI는 같은 대화의 맥락을 갖고 있지 않으므로 진행 요약과 남은 업무를 전달해야
하고, 그 요약의 품질이 갈아탄 뒤의 작업을 정한다.
README는 이 요약이 어떻게 만들어지는지는 설명하지 않는다.

## 비평

### 소스를 공개하지 않은 실행 파일에 키와 모든 권한을 맡기는 구조다

이 앱은 사용자의 작업 폴더에서 파일을 바꾸고 명령을 실행하는 AI를 지휘하며,
키 저장소에 API 키와 비밀번호를 보관하고,
모든 권한 허용을 켜면 삭제와 설치와 온라인 전송까지 자동으로 허가한다.
그런데 저장소에는 소스 코드가 없고 Windows 코드 서명도 없다. README가 서명이
아직 없다고 밝힌다.
검증 기록은 ZIP의 SHA256과 파일 수를 제시해 배포 파일이 같다는 것까지는 확인해
주지만,[^verification] 파일의 동작이 문서와 같다는 것은 독립적으로
확인할 수 없다.

README가 처음에는 전부 묻기로 쓰고 중요한 작업은 복사본으로 먼저 해 보라고
권하는 것은 이 한계를 아는 태도다.
그러나 키 저장소를 쓰는 순간 값은 AI 서비스의 기록에 남을 수 있고,
키를 지워도 외부 서비스의 키는 폐기되지 않는다는 것도 문서가 인정한다.[^keys]
소스를 읽을 수 없는 도구에 이런 권한을 맡길지는 사용자가 위험을 어떻게
보느냐에 달려 있다.

### 검증의 범위가 좁고, 팀 작업이 실제로 잘되는지는 보여 주지 않는다

0.2.6의 검증 기록에서 자동 검사는 서버 전체 1,669개가 통과하고 17개가 제외되었으며 실패는 0이다.[^verification]
실제 AI를 쓴 시험은 Codex 하나에, 파일을 읽고 합계를 묻는 질문 두
번이다.[^verification]
Claude Code와 Antigravity는 이번 변경의 공통 안내를 자동 검사한 범위에 그치고,
다른 PC의 최초 설치와 로그인은 검증하지 않았다고 기록이 밝힌다.[^verification]

README 자신도 화면 사진의 프로젝트, 대화, 검사 결과, 사용량,
로그인 상태가 소개용 예시이며 실제 AI의 작업 성과가 아니라고 적는다.
따라서 부장이 팀을 구성하고 일을 나누어 실제 코딩 작업을 끝낸 사례는 이
저장소에 없다.
검증 기록의 정직함은 장점이지만, 이 앱의 핵심 약속인 여러 AI의 협업이 얼마나 잘
동작하는지는 이 자료로 평가할 수 없다.

### 키 저장소의 조회 도구는 값을 AI에게 건네는 경로다

AI가 `secret_get`으로 값을 조회한다는 것은 값이 AI의 컨텍스트에
들어간다는 뜻이다.
문서는 AI가 값을 출력, 소스, Git에 복사하지 않도록 안내하지만 AI에게 공개한 값을
회수할 수는 없다고 말한다.[^keys]
이 구조에서는 안내를 따르지 않는 에이전트나,
에이전트가 읽은 외부 입력에 담긴 지시가 키를 노출시킬 가능성이 있다.
문서는 이 위험을 가림 처리와 기록 제외로 줄이려 하지만,
위험의 원천이 AI에게 값을 주는 것 자체에 있다는 점은 같은 문서가
인정한 그대로다.

## 인사이트

### 여러 AI를 묶을 때 병목은 사람의 확인이고, 화면은 그 확인을 줄이는 데 쓰여야 한다

이 앱의 핵심 화면은 사무실, 대기 관계, 내 책상이다.
세 가지는 모두 사람이 어디에서 확인해야 하는지를 보여 준다.
캐릭터가 걷고 앉는 연출은 장식이지만, 누가 누구의 결과를 기다리는지와 어느
요청이 나에게 온 것인지는 정보다.

에이전트의 수가 늘수록 사람은 모든 에이전트의 출력을 읽을 수 없고,
막힌 곳과 결정이 필요한 곳을 찾는 일이 일의 대부분이 된다.
이 관점에서 시각화의 평가 기준은 예쁜가가 아니라 사람이 개입해야 할 지점을
얼마나 빨리 찾게 하느냐다.
README의 표시 의미 표는 그 기준에 맞춘 시도지만,
에이전트가 수십 개로 늘었을 때의 화면은 이 자료에서 확인되지 않는다.

### 보고된 결과와 확인된 결과를 나누는 일이 오케스트레이션의 기본 요건이 된다

이 앱은 AI가 보고한 검사 결과를 통과로 표시하지 않는다.
이 문제를 푸는 방법은 하나가 아니다. 증거를 실제 로그와 코드 상태에 묶어
에이전트의 말이 아니라 도구가 확인한 사실만 남기는 방식도 가능하다.
픽셀 오피스는 거기까지 가지 않고 표시의 의미를 구분하는 데 그친다.

이 차이는 완료의 정의가 어디에 있는지를 가른다.
표시만 구분하면 사용자가 보고된 결과를 직접 확인해야 하고,
실행 증거에 묶으면 도구가 확인한다.
앞의 방식은 가볍고 뒤의 방식은 강하다. 팀 작업의 규모가 커질수록 사용자가 확인할
수 있는 양에 한계가 생기므로, 어느 쪽이 더 오래 버티는지는 사용
규모에 달려 있다.

### 구독형 CLI를 묶으면 한도와 세션이 새로운 장애 유형이 된다

API를 직접 호출하는 구조에서는 비용이 늘어나는 것이 위험이지만,
구독형 CLI를 묶는 구조에서는 한도에 걸려 중단되는 것이 위험이다.
이 앱이 한도 소진 시 대화와 업무를 보존하고 재개 방법을 사용자에게 고르게 하는
것은 이 유형의 장애를 설계에 넣었다는 뜻이다.
같은 대화로 이어 가는 것과 새 AI에게 요약을 넘기는 것은 맥락의 보존
정도가 다르다.

그래서 이런 도구를 쓰는 사용자의 실질적인 선택 기준은 기능 수보다 중단이
일어났을 때 무엇이 남는지다.
0.2.6의 변경 내역이 비정상 종료 뒤 같은 대화와 기존 업무를 보존하며 재연결을 시도하고 회복된 한도 기록의 재차 차단을 고친 것이 모두 이 영역이라는 점도 같은 흐름이다.
