# Happy — AI 코딩 세션을 위한 크로스 플랫폼 모바일/웹 클라이언트

<https://happy.engineering/>

<https://github.com/slopus/happy>

Claude Code와 Codex를 모바일·웹에서 원격 제어하는 오픈소스 클라이언트.
종단간 암호화(E2EE)로 코드를 보호하면서 어디서든 AI 코딩 에이전트의
작업을 모니터링하고 개입할 수 있다.

2026년 8월 기준 GitHub 스타 약 2만 3천 개, 포크 약 1,900개, 열린 이슈
937개다.
2025년 7월에 시작했으니 1년 남짓 된 프로젝트이고, 저장소는 여전히 매우
활발하다.
라이선스는 MIT다.

## 설치

### 패키지 이름이 `happy-coder`에서 `happy`로 바뀌었다

`happy` 이름을 기부받아 이전했고, 현재 배포되는 최신 버전은 `happy`
쪽에만 올라온다.

```bash
npm install -g happy
```

`happy-coder`는 2026년 5월 1.1.9에서 멈춰 있고 `happy`는 7월에 1.2.0이
나왔다.
예전 문서를 보고 `happy-coder`를 설치하면 몇 달치 수정이 빠진 버전을
쓰게 된다.
이미 설치했다면 옮기는 편이 좋다.

```bash
npm uninstall -g happy-coder
npm install -g happy
```

### Homebrew는 쓰지 않는 게 좋다

`happy-coder` formula는 0.13.0에서 멈춘 채 deprecated 처리되었다.
사유는 `uses non-FOSS @anthropic-ai/claude-agent-sdk since 1.1.5`로,
Homebrew 코어의 FOSS 정책에 걸린 것이다.
따라서 앞으로 갱신될 가능성도 없다.
`happy`라는 이름의 formula는 아예 존재하지 않는다.

npm의 1.2.0과 비교하면 메이저 버전 하나에 반년 이상 차이다.
설치되어 있다면 정리하는 편이 좋다.

```bash
brew uninstall happy-coder
npm install -g happy
```

## 사용법

`claude` 대신 `happy`를 쓴다.
인자 없이 `happy`를 실행하면 Claude Code 세션이 시작된다.
다른 에이전트는 하위 명령으로 지정한다.

```bash
# Claude Code (기본)
happy

# Codex
happy codex

# Antigravity (Google CLI)
happy agy

# 임의의 ACP 호환 에이전트
happy acp opencode
```

Claude의 모든 플래그를 그대로 넘길 수 있어서 `happy --resume` 같은
사용이 가능하다.

주요 하위 명령은 다음과 같다.

| 명령            | 역할                                             |
| --------------- | ------------------------------------------------ |
| `happy auth`    | Happy 계정 인증 관리                             |
| `happy resume`  | Happy 세션 ID로 이전 세션 재개                   |
| `happy connect` | AI 벤더 API 키 연결                              |
| `happy sandbox` | OS 수준 샌드박스 설정·관리                       |
| `happy daemon`  | 원격에서 새 세션을 띄우기 위한 백그라운드 서비스 |
| `happy notify`  | 푸시 알림 전송                                   |
| `happy doctor`  | 진단 및 문제 해결                                |

자주 쓰는 플래그로는 권한 확인을 건너뛰는 `--yolo`
(`--dangerously-skip-permissions`의 축약), 세션 단위로 샌드박스를 끄는
`--no-sandbox`, Chrome 접근을 켜고 끄는 `--chrome` / `--no-chrome`이
있다.

### 벤더 인증 (`happy connect`)

원격 디바이스에서 세션을 시작하려면 AI 벤더의 자격증명이 필요하다.
`happy connect`는 이 키를 Happy 클라우드에 암호화해 저장한다.
사전에 `happy auth login`으로 Happy 계정에 로그인해야 한다.

```bash
happy connect claude
happy connect codex
happy connect gemini
happy connect status
```

로컬에서 시작한 세션과 모바일에서 시작한 세션은 인증 경로가 다르다.

| 시작 방식                       | 사용 인증                   |
| ------------------------------- | --------------------------- |
| 로컬 (`happy`)                  | 머신의 로컬 Anthropic 계정  |
| 원격 (모바일 Start New Session) | `happy connect` 클라우드 키 |

## 자동 진행이 잘 안 되는 이유

실사용에서 가장 자주 부딪히는 불만이 “자동으로 쭉쭉 진행되지 않는다”인데,
이것은 설정 문제가 아니라 상당 부분 알려진 결함이다.

### 서브에이전트가 도는 동안 세션이 끝난 것으로 보인다

CLI는 SDK가 `result`를 내보내는 시점에 턴이 끝났다고 판단한다.
그런데 이 이벤트는 메인 스레드가 서브에이전트에게 일을 넘기는 순간
발생한다.
그래서 서브에이전트가 몇 분씩 일하는 동안 앱은 세션을 유휴로 표시하고
완료 푸시까지 보낸다.
저장소에 올라온 실제 타임라인은 이렇다.

```text
15:58:36  서브에이전트에 턴 위임
15:58:52  thinking -> false + PUSH kind=done   <-- 이제 막 시작했는데
16:04:42  thinking -> false + PUSH kind=done   <-- 여전히 실행 중
16:08:53  서브에이전트가 bash 호출             <-- 작업 진행 중
16:12:23  서브에이전트 종료
```

14분 동안 앱은 세션이 준비 상태라고 말했고, 거짓 완료 알림이 두 번
나갔다.
게다가 서브에이전트의 출력은 별도 파일에 쌓이는데 스캐너가 그 경로를
보지 않아서 채팅에도 아무것도 뜨지 않는다.
상태는 유휴, 채팅은 침묵, 그런데 작업은 한창 돌아가는 중이다.

### 세션 목록이 끝남과 백그라운드로 넘김을 구분하지 못한다

같은 문제의 다른 얼굴이다.
20분짜리 빌드나 워크플로가 돌고 있어도 턴이 끝나는 순간 세션은 대기로
떨어진다.
그래서 아직 일하는 중인 세션을 사용자가 끊어 버리는 일이 생긴다.

이 두 결함이 합쳐지면 체감은 정확히 “자동으로 진행이 안 된다”가 된다.
실제로는 에이전트가 일하고 있는데 화면이 멈춰 보이니, 사용자가 개입해서
진짜로 흐름을 끊게 되는 구조다.
두 건 모두 2026년 8월 초 기준 수정이 제안되었지만 아직 병합되지 않았다.

### 기본값이 `yolo`다

CLI 코드에는 `DEFAULT_CLAUDE_PERMISSION_MODE = 'yolo'`가 그대로 들어
있고, 이 값은 `bypassPermissions`로 매핑된다.
즉 Happy로 Claude를 띄우면 기본적으로 권한 확인을 건너뛴다.
자동 진행이 목적이라면 편하지만, 터미널에서 `claude`를 직접 쓸 때와
안전 수준이 달라진다는 뜻이다.
이 기본값 자체가 이슈로 제기되어 있다.

### 샌드박스 모드

권한을 건너뛰는 대신 OS 수준에서 막는 경로도 생겼다.
`happy sandbox configure`로 설정하면 Anthropic의 sandbox-runtime을 써서
파일시스템과 네트워크를 제한한다.
기본 차단 대상에 `~/.ssh`, `~/.aws`, `~/.gnupg`가 들어 있다.

```bash
happy sandbox configure
happy sandbox status
happy sandbox disable
```

다만 설계상 샌드박스를 켜면 권한 모드는 강제로 bypass가 된다.
OS가 막아 주니 에이전트의 확인 절차는 불필요한 마찰이라는 판단이다.
무인 자동 진행을 원한다면 샌드박스를 켜고 권한 확인을 넘기는 이 조합이
현재로서는 가장 합리적인 선택지다.

## 특장점

### 원격 모니터링과 제어

데스크톱에서 `happy`로 세션을 시작하면 모바일이나 웹에서 진행 상황을
실시간으로 확인할 수 있다.
에이전트가 권한을 요청하거나 오류가 발생하면 푸시 알림을 보낸다.

### 디바이스 전환

모바일에서 제어하다가 데스크톱 키보드의 아무 키나 누르면 즉시 데스크톱으로
제어권이 돌아온다.

### 병렬 세션 실행

여러 에이전트를 동시에 실행할 수 있다.
병렬 세션마다 별도 Git worktree를 할당하면 서로 간섭 없이 독립적으로
작업한다.

### 다중 에이전트 지원

Claude Code와 Codex 외에 Antigravity(agy)를 1급 에이전트로 지원하고,
범용 ACP 러너를 통해 OpenCode 같은 임의의 ACP 호환 에이전트도 붙일 수
있다.

### 오픈소스

MIT 라이선스.
텔레메트리나 추적 코드가 없고, 코드를 직접 감사할 수 있다.

## 아키텍처

pnpm 워크스페이스 기반 모노레포이며 7개 패키지로 구성된다.

- **happy-app**: 웹 UI와 모바일 클라이언트 (Expo 기반)
- **happy-cli**: 커맨드라인 래퍼
- **happy-agent**: 원격 세션 관리·모니터링
- **happy-server**: 암호화된 동기화 백엔드
- **happy-wire**: 클라이언트와 서비스가 공유하는 메시지 타입과 Zod 스키마
- **happy-app-logs**: 앱 로그 도구
- **codium**: Electron 기반 데스크톱 셸

## 분석

Happy가 풀고자 하는 문제는 **AI 코딩 에이전트의 비동기 감시**다.
Claude Code나 Codex 같은 터미널 기반 에이전트는 데스크톱에 묶여 있다.
에이전트가 긴 작업을 수행하는 동안 인간은 자리를 비울 수 있지만, 권한
요청이나 에러가 나면 돌아와야 한다.
Happy는 이 대기 시간을 모바일로 옮긴다.
[장기 실행 에이전트](long-running-agents.md)가 강조하는 “며칠 동안
실행되는 에이전트”의 현실은 곧 “데스크톱에 묶이지 않은 모니터링”의
필요로 이어진다.

아키텍처에서 주목할 점은 **래퍼 방식**이다.
에이전트 자체를 수정하지 않고 CLI를 감싸는 형태로 세션을 원격 동기화한다.
기존 도구 체인을 깨뜨리지 않으면서 기능을 확장하는 데코레이터 패턴의
적용이다.

종단간 암호화와 텔레메트리 없음 정책은 코드가 서버를 경유하더라도 평문으로
노출되지 않게 한다.
AI 코딩 에이전트가 접근하는 코드베이스에는 API 키, 인프라 설정, 비즈니스
로직이 포함될 수 있으므로 이 설계 결정은 필수적이다.

### 상태 추정이라는 구조적 부채

2026년의 이슈 목록을 읽으면 Happy가 겪는 문제가 한 종류로 수렴한다는
것이 보인다.
서브에이전트 실행 중 유휴 표시, 백그라운드 작업과 종료의 미구분, 거짓
완료 푸시, 재개 세션의 히스토리 중복 재생, 압축(compaction) 요약이 일반
메시지로 표시되는 문제.
전부 **에이전트의 실제 상태를 외부에서 추정해야 한다**는 하나의 뿌리에서
나온다.

래퍼는 에이전트 내부를 볼 수 없다.
스트림에 흐르는 이벤트와 파일시스템에 남는 흔적으로 지금 무슨 상태인지를
역산할 뿐이다.
그런데 SDK의 `result` 이벤트는 “턴이 끝났다”는 뜻이지 “일이 끝났다”는
뜻이 아니다.
이 둘의 차이가 서브에이전트와 백그라운드 작업이 보편화되면서 벌어졌고,
추정 기반 상태 표시는 그만큼 어긋나기 시작했다.

주목할 점은 제안된 해법의 방향이다.
개발자들은 SDK 스트림을 더 정교하게 해석하는 대신, Claude Code가 이미
`Stop` 훅으로 내보내는 `background_tasks` 배열을 그대로 읽는 쪽을 택했다.
추정을 버리고 에이전트가 스스로 보고하는 사실을 쓰겠다는 것이다.
래퍼가 성숙하는 전형적인 경로이기도 하다.
바깥에서 관찰하다가 결국 안쪽이 제공하는 공식 통로에 의존하게 된다.

### 다중 에이전트 지원은 방어 전략이다

Happy는 Claude Code로 시작했지만 Codex, Antigravity, 범용 ACP 러너까지
지원 범위를 넓혔다.
이것을 단순한 기능 확장으로 읽으면 요점을 놓친다.

래퍼의 생존을 위협하는 가장 큰 변수는 감싸고 있는 플랫폼이 그 기능을
직접 제공하는 것이다.
Anthropic이 공식 모바일 경험을 강화할수록 Claude Code 전용 래퍼의 존재
이유는 줄어든다.
반면 여러 에이전트를 하나의 화면에서 감시하는 계층은 어느 한 벤더도
제공할 유인이 없다.
경쟁사의 에이전트까지 잘 보여주는 일은 벤더의 이해와 어긋나기 때문이다.

즉 다중 에이전트 지원은 기능이 아니라 위치 선정이다.
Happy가 장기적으로 살아남는다면 그 이유는 Claude Code를 잘 감싸서가
아니라, 어떤 벤더도 만들지 않을 중립 지대를 차지해서일 것이다.

이 중립 지대에 수요가 있다는 근거는 에이전트들의 성격이 실제로 다르다는
데 있다.
[Claude Code vs Codex](claude-code-vs-codex.md) 비교는 Claude Code가
빠르지만 지시를 흘리고 작업을 미완으로 남기는 반면, Codex는 3~4배
느려도 가이드라인을 지키고 체계적으로 움직인다고 정리한다.
성격이 이렇게 다르면 하나로 수렴하지 않고 작업에 따라 나눠 쓰게 되고,
그 순간 서로 다른 에이전트를 한 화면에서 감시할 필요가 생긴다.
감시 계층의 시장은 에이전트가 통합되지 않는 한 사라지지 않는다.

## 비평

### 1인칭 클라이언트와 3인칭 클라이언트의 격차

Claude 모바일 앱에서 Claude Code를 쓰는 경험과 비교하면 Happy의 한계가
가장 선명해진다.
두 도구는 겉보기에 같은 일을 하지만 상태를 아는 방식이 근본적으로 다르다.

Claude 앱은 에이전트를 실행하는 주체가 직접 만든 클라이언트다.
세션이 지금 무엇을 하고 있는지, 서브에이전트가 몇 개 돌고 있는지,
백그라운드 작업이 남았는지를 **추정할 필요가 없다.**
런타임이 그 사실을 알고 있고 클라이언트는 전달받기만 하면 된다.
반면 Happy는 바깥에서 관찰한다.
앞서 본 14분짜리 오탐은 이 차이의 직접적 산물이다.

이 격차는 UI 완성도로 메울 수 있는 종류가 아니다.
리퀴드 글래스를 입히고 사이드 챗을 붙여도, 세션이 일하는 중인지 끝났는지를
틀리게 말하면 신뢰가 서지 않는다.
원격 감시 도구의 핵심 가치는 안 봐도 된다는 확신인데, 상태 표시가 틀리는
도구는 오히려 더 자주 보게 만든다.
기능이 많아질수록 이 신뢰 문제는 가려지는 게 아니라 더 도드라진다.

그래서 Happy가 Claude 앱에 준하는 경험을 주려면 필요한 것은 기능 추가가
아니라 상태 정보의 출처를 바꾸는 일이다.
`Stop` 훅의 `background_tasks`를 읽겠다는 최근 제안이 정확히 그 방향이고,
이 작업이 실제로 병합되어 안정화되는지가 이 도구를 다시 평가할 기준이
된다.
다만 그 경로 역시 Anthropic이 제공하는 훅의 모양에 의존하므로, 3인칭
클라이언트의 숙명 자체가 사라지지는 않는다.

### 기본값이 안전하지 않다

CLI가 기본으로 `yolo`를 쓴다는 사실은 문서 어디에도 눈에 띄게 적혀 있지
않다.
터미널에서 `claude`를 실행할 때는 권한 확인이 기본인데, `happy`로 바꾸는
순간 그 확인이 사라진다.
명령어 하나를 바꿨을 뿐인데 안전 모델이 달라지는 것이다.

편의를 위한 선택이라는 점은 이해할 수 있다.
모바일에서 매번 승인을 누르게 하면 원격 감시의 의미가 줄어든다.
문제는 이 전환이 사용자에게 명시적으로 제시되지 않는다는 데 있다.
안전한 기본값에서 편한 기본값으로 옮기는 결정은 사용자가 내려야지 도구가
대신 내릴 일이 아니다.

샌드박스 모드가 이 문제의 답이 될 수 있지만 현재는 별도로 설정해야 하는
선택 기능이다.
순서가 뒤집혀 있는 셈이다.
권한 확인을 건너뛰는 것이 기본이고 그것을 상쇄할 격리는 옵션이라면,
대다수 사용자는 상쇄 없는 상태로 쓰게 된다.

### 열린 이슈 937개가 말해 주는 것

스타 2만 3천 개에 열린 이슈 937개는 흔한 비율이 아니다.
저장소가 활발하다는 사실과 이슈가 잘 정리된다는 사실은 다른 얘기다.
2025년 9월에 열린 “Claude Code v2.0.0 지원” 이슈가 댓글 23개를 달고 아직
열려 있고, “셀프호스팅이 완전히 망가졌다”, “Docker 배포 튜토리얼이
필요하다” 같은 이슈도 오래 남아 있다.

이 패턴은 우선순위의 문제로 읽힌다.
개발은 앱 UI와 신규 에이전트 지원 쪽으로 빠르게 움직이는데, 인프라와
자체 호스팅 경로는 뒤처진다.
문제는 이 도구가 다루는 대상이 코드베이스라는 점이다.
E2EE를 신뢰의 근거로 내세우면서 자체 호스팅이 오래 깨져 있는 상태는,
가장 보안에 민감한 사용자층이 실질적으로 선택지를 갖지 못한다는 뜻이다.

빠른 기능 개발과 미해결 이슈 누적은 초기 오픈소스 프로젝트에서 흔한
조합이고 그 자체가 결함은 아니다.
다만 도입을 검토한다면 봐야 할 것은 최근 커밋 빈도가 아니라, 자신에게
중요한 영역의 이슈가 실제로 닫히고 있는지다.

### 모바일에서의 코드 리뷰 한계

코드는 본질적으로 넓은 화면과 정밀한 입력을 요구하는 매체다.
모바일에서 에이전트의 작업 결과를 확인하는 것은 가능하지만, 의미 있는
검토를 하기에는 화면 크기와 입력 방식의 제약이 크다.
Happy가 푸는 문제의 본질이 알림과 간단한 승인이라면 모바일이 적합하지만,
심층 리뷰까지 확장하려 하면 사용자 경험이 나빠질 가능성이 높다.

이 한계는 앞의 상태 표시 문제와 맞물릴 때 특히 나빠진다.
화면에서 판단에 필요한 정보를 충분히 얻지 못하는 상황에서, 그 정보마저
부정확하다면 사용자가 할 수 있는 합리적 행동은 승인 버튼을 습관적으로
누르는 것뿐이다.

## 인사이트

### 에이전트 런타임의 물리적 탈결합

전통적으로 개발 도구는 IDE라는 단일 환경에 결합되어 있었다.
에디터, 터미널, 디버거, 버전 관리가 하나의 화면에 공존했다.
AI 코딩 에이전트는 이 결합을 처음으로 의미 있게 풀어낸다.
에이전트가 자율적으로 작업하는 동안 인간은 **물리적으로 다른 장소에서
다른 디바이스로** 작업을 감시할 수 있다.

이것은 제조업의 SCADA 시스템과 구조적으로 유사하다.
공장의 기계가 자동으로 돌아가는 동안 관리자는 중앙 통제실이나 모바일
단말에서 상태를 보고 이상이 생기면 개입한다.
Happy는 소프트웨어 개발에서 이 패턴을 재현한다.
에이전트가 기계이고, 개발자가 관리자이며, 모바일 앱이 원격 단말이다.

이 탈결합은 작업 패턴을 바꾼다.
기존에는 에이전트를 실행하고 결과를 기다리는 동안 같은 화면 앞에 앉아
있거나, 자리를 비우면 진행 상황을 알 수 없었다.
Happy 같은 도구는 실행하고 자리를 비웠다가 알림을 받고 필요할 때만
복귀하는 흐름을 가능하게 한다.

그러나 물리적 탈결합이 **인지적 탈결합**으로 이어지면 위험하다.
모바일 알림으로 상태를 파편적으로 확인하는 것은 전체 맥락을 유지한 채
판단하는 것과 질적으로 다르다.
승인 요청에 빠르게 허용을 누르는 습관이 생기면, 에이전트의 잘못된 판단을
걸러내는 인간의 게이트키핑이 약해진다.
SCADA 비유를 끝까지 밀고 가면 이 지점도 함께 따라온다.
산업 자동화에서 반복적으로 확인된 것이 자동화 안주(automation
complacency)이고, 감시자가 개입할 일이 드물수록 정작 개입해야 할 때의
판단력이 떨어진다.

### 상태 표시의 정확도가 신뢰의 상한을 정한다

Happy의 사례에서 일반화할 수 있는 원칙이 있다.
비동기 감시 도구의 가치는 기능의 수가 아니라 상태 표시의 정확도가
결정한다는 것이다.

거짓 완료 알림이 몇 번 반복되면 사용자는 알림을 믿지 않게 된다.
알림을 믿지 않으면 앱을 열어 직접 확인하고, 직접 확인할 거라면 애초에
자리를 비우지 않는다.
이 연쇄의 끝에서 도구는 사용되지 않는다.
기능이 아무리 늘어도 이 연쇄를 되돌리지 못한다.

거짓 양성(false positive)보다 거짓 음성(false negative)이 더 나쁘다는
점도 중요하다.
“아직 일하는 중”이라고 잘못 말하면 사용자는 조금 더 기다릴 뿐이지만,
“끝났다”고 잘못 말하면 사용자가 개입해서 실제 작업을 끊는다.
Happy가 겪은 문제가 정확히 후자다.
감시 도구를 설계할 때 두 오류의 비용은 대칭이 아니며, 불확실할 때는
아직 진행 중이라고 말하는 쪽이 안전하다.

이 기준은 도구 선택에도 적용된다.
비동기 감시 도구를 평가할 때 물어야 할 첫 질문은 어떤 기능이 있는지가
아니라, 상태를 어디서 가져오는지다.
런타임이 직접 보고하는가, 아니면 바깥에서 추정하는가.
답이 후자라면 정확도의 상한이 이미 정해져 있다.

같은 문제를 반대편에서 푸는 접근도 있다.
[re_gent](regent.md)는 에이전트의 행위를 Step 단위로 기록해 어떤
프롬프트가 이 줄을 만들었는지까지 되짚을 수 있게 한다.
실시간 상태를 추정하는 대신 사후에 정확한 기록을 남기는 쪽이다.
자리를 비운 동안 무슨 일이 있었는지 알아야 한다는 필요는 같은데,
한쪽은 지금 무엇을 하고 있는지를, 다른 쪽은 무엇을 했는지를 답한다.
에이전트의 자율성이 높아질수록 후자의 비중이 커진다는 점에서 두 계층은
언젠가 합쳐질 가능성이 높다.

### 래퍼는 결국 프로토콜을 요구하게 된다

Happy가 `Stop` 훅의 `background_tasks`를 읽기로 한 결정은 작은 구현
선택처럼 보이지만, 래퍼 생태계 전반이 지나가는 경로를 보여준다.

초기 래퍼는 관찰에 의존한다.
출력을 파싱하고, 파일시스템을 감시하고, 이벤트 타이밍으로 상태를
추론한다.
이 방식은 플랫폼의 협조 없이 즉시 작동한다는 점에서 강력하고, 그래서
생태계 초기에 폭발적으로 늘어난다.
하지만 관찰 대상이 복잡해지면 추론은 반드시 어긋난다.
서브에이전트와 백그라운드 작업이 그 임계점이었다.

다음 단계에서 래퍼는 플랫폼에 공식 통로를 요구한다.
훅, 이벤트 스트림, 구조화된 상태 보고 같은 것들이다.
브라우저 확장이 DOM 스크래핑에서 확장 API로, 에디터 플러그인이 텍스트
파싱에서 언어 서버 프로토콜로 옮겨간 것과 같은 경로다.
LSP가 특히 좋은 비유인데, 처음에는 에디터마다 각 언어를 따로 지원하다가
결국 중립적 프로토콜로 수렴했다.

에이전트 생태계도 같은 지점을 향해 가고 있다.
ACP(Agent Client Protocol)가 이미 그 시도이고, Happy가 범용 ACP 러너를
제공하는 것은 이 흐름에 올라탄 것이다.
여기서 나오는 예측은 이렇다.
에이전트 감시·제어 계층의 승부는 어느 래퍼가 더 잘 만들어졌는지가 아니라,
어떤 프로토콜이 표준이 되고 누가 그 표준에 먼저 자리잡는지에서 갈린다.
Happy의 다중 에이전트 지원이 의미 있는 이유도 기능이 많아서가 아니라
그 자리를 미리 잡는 행위이기 때문이다.
