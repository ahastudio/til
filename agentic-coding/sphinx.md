## 소개

Sphinx는 에이전트가 거드는 개발을 위한 Git 훅이다.
보호된 브랜치로 푸시하면 Git이 멈추고,
변경이 실제로 무엇을 하는지 묻는 질문이 먼저 나온다.
`git push`를 사람이 실행했든 코딩 에이전트가 실행했든 똑같이
동작한다. npm 패키지 이름은 `sphinx-understand`이고 MIT 라이선스다.
Node.js 22.19 이상이 필요하고 macOS, Linux, WSL에서 동작하며,
네이티브 Windows는 아직 지원하지 않는다.
이후 GitHub API로 확인한 값은 저장소 생성일이 2026년 10월 14일, 별 383개, 마지막
푸시가 10월 25일이다.

홈페이지의 표어는 사고는 맡길 수 있어도 이해는 맡길 수 없다는 문장이다.
홈페이지는 이 문장을 손자(Sun Tzu)의 말로 소개하지만 출처를 달지 않았다.
이 문서도 이 문장이 정말 손자의 말인지 확인하지 못했다.
HN에서도 Crowberry가 인용을 지어낸 것이 아니냐며 출처를 물었다.[^Crowberry]
Claude Code, Codex, Cursor, OpenCode, Pi와 일반 Git에서 쓸 수 있다고 한다.
답변은 코딩 에이전트에 전달되지 않고,
`.env` 파일과 키는 열지 않는다고 설명한다.

## 동작 방식

### 질문은 대화를 보지 않은 별도 모델이 만든다

푸시가 일어나면 별도의 검토 모델이 커밋된 변경을 읽기 전용 Git 도구로 읽는다.
이 모델은 코드를 만든 대화를 보지 못한다.
질문은 파일 이름이나 함수 이름이 아니라
동작, 실패 상황, 불변 조건을 다룬다.
홈페이지의 예시는 이런 식이다.
웹훅 핸들러가 이벤트 ID를 먼저 저장하고 결제를 호출하는데,
Stripe가 시간 초과로 같은 이벤트를 다시 보내면
재시도에서 무슨 일이 생기느냐는 질문이다.

답이 틀리면 이유를 설명하고 새로운 시나리오를 준다.
맞으면 멈춰 있던 푸시가 이어진다.
같은 변경을 다시 푸시해도 다시 묻지 않으며,
코드, 대상, 정책이 바뀌지 않는 한 통과는 24시간 유효하다.
시험은 오픈북이다.
답하는 동안 코드를 읽거나 에이전트에게 보여 달라고 해도 된다.

### 질문 수와 깊이는 변경 크기와 설정이 정한다

기본 깊이에서 작은 변경은 질문이 최대 한 개이고 문서나 사소한 수정에는 없다.
큰 변경은 최대 세 개다.
검토 모델이 거치는 경로도 변경 크기에 따라 작은 경로,
중간 경로, 큰 경로로 나뉜다.
`distance`가 `high`이면 변경이 무엇을 하고 무엇에 영향을 주는지를 묻고,
`low`이면 구체적인 로직과 조건과 경계 사례를 묻는다.
기본값은 둘을 섞은 `mixed`다.
커밋 뒤에 질문을 백그라운드에서 미리 만들어 두므로
푸시할 때쯤 질문이 이미 준비된 경우가 많다고 한다.

### 건너뛰기와 중단은 기록으로 남는다

기다림은 최대 25분이다.
창을 닫아도 Git은 계속 기다리고 같은 주소가 마감까지 유효하다.
이번만 건너뛰기를 누르면 푸시는 즉시 통과하지만
검사를 통과한 것으로 치지 않는다.
`sphinx yolo`는 저장소 안에서 실행하면 현재 저장소의 검사를,
저장소 밖에서 실행하면 전역으로 검사를 끈다.
모든 건너뛰기와 yolo 전환은 이유와 함께 기록되고 `sphinx status`로 볼 수 있다.

## 설치하고 설정하기

설치는 두 단계이고 저장소마다 한 단계가 더 있다.

```sh
npm install -g sphinx-understand
sphinx install            # 전역 Git 훅과 에이전트 연동 설치
cd your-repo
sphinx init               # .sphinxconfig, .sphinxignore, .sphinxcontext.md 생성
sphinx doctor             # 설정이 맞는지 확인
git push origin main      # 질문이 뜨고 Git이 기다린다
```

`sphinx install`은 전역 Git `core.hooksPath`를 설정한다.
기존 훅은 먼저 실행되고,
설치 직후에는 어느 저장소든 `main`과 `master`로의 푸시가 검사 대상이 된다.
`sphinx init`이 만드는 파일은 세 개다.
`.sphinxconfig`는 저장소의 정책, `.sphinxignore`는 읽지 않을 경로,
`.sphinxcontext.md`는 프로젝트가 하는 일과 깨지면
안 되는 것을 짧게 설명한 파일이다.
저장소 정책의 예는 이렇다.

```json
{
  "version": 1,
  "events": ["pre-push"],
  "branches": ["main", "release/*"],
  "remotes": ["*"],
  "level": "standard",
  "distance": "mixed",
  "exclude": ["vendor/**"]
}
```

검토 모델은 프리셋으로 고른다.
Claude Code 요금제를 쓰는 `claude-economy`, Codex 요금제를 쓰는 `codex-economy`,
유료 OpenRouter 크레딧을 쓰는 `openrouter-value`(`--allow-paid` 필요),
무료이지만 느리고 속도 제한이 있는 `openrouter-free`가 있다.
OpenAI 호환 엔드포인트라면
OpenAI, Groq, Together, Ollama, LM Studio, vLLM도 쓸 수 있다.
Sphinx에는 자체 계정이나 호스팅 서비스가 없다.

## 연동과 범위

### 터미널 모드와 GitHub 연동

SSH처럼 브라우저를 백그라운드로 열 수 없는 곳에서는 `git push`를 실행한 터미널에
질문이 바로 나온다.
`/hint`, `/learn`, `/dispute <이유>`, `/skip`, `/stop`을 입력하고, 통과한 뒤에는
`continue`나 `stop`을 쓴다.
`sphinx config --interface terminal`로 항상 터미널을 쓰게 할 수 있고,
`sphinx check`는 같은 검사를 터미널에서 실행한다.
GitHub CLI(`gh`)로 로그인되어 있으면 통과한 커밋에 도장이 찍힌다.
풀 리퀘스트 브랜치로 푸시하면 질문 요약과 첫 시도 결과를 풀 리퀘스트에 댓글로
남길지 묻고, `sphinx init --github-check`로 Sphinx Action을 더하면 풀 리퀘스트에
Sphinx 검사가 표시된다.
README는 이 중 어느 것도 푸시를 막지 않는다고 적는다.

### 버전 0.1이 다루지 않는 것

README는 버전 0.1이 로컬 커밋과 푸시만 검사한다고 밝힌다.
웹에서의 병합, CI에서 요구하는 검사, 배포는 다루지 않고, 바이너리 파일의 내용은
읽지 못한다.
이 도구는 이해를 시험할 뿐 코드를 감사하지 않는다.
평가 결과 문서는 합성 변경에서 질문의 질과 채점 오류와 비용을 기록한 것이고
임의의 저장소를 보증하지 않는다고 한다.
검토 모델 호출 수는 `sphinx config --max-model-calls`로 검사당 1~100회까지
제한할 수 있고, 컨텍스트 크기와 출력 토큰과 검토 시간은 항상 상한이 있다.
공급자의 일시 오류는 최대 세 번 다시 시도하며, 그래도 채점하지 못한 답은 재개할
때를 위해 저장된다.

### 명령

README의 명령은 열두 개다.
`install`(머신 전체 Git 훅과 에이전트 연동 설치), `init`(저장소 정책과 무시와
맥락 파일 생성), `doctor`(훅과 연동 범위 확인), `status`(정책, 대기 중인 검사,
최근 건너뛰기), `check`(터미널에서 검사 시작이나 재개), `pending`(끝나지 않은
검사 목록), `yolo`, `config`(검토 모델과 한도), `auth`(OpenRouter 키나 호환
엔드포인트 저장), `prepare`(백그라운드 준비, 실패 뒤 `--retry`),
`activate`(재설치 없이 에이전트 열기), `uninstall`이다.

## 분석

### 푸시라는 지점을 고른 이유

Sphinx가 개입하는 지점은 코드를 쓰는 순간도 병합하는 순간도 아니고 푸시다.
푸시는 로컬 작업이 공유 상태로 넘어가는 첫 지점이며,
사람이 실행하든 에이전트가 실행하든 Git이 거치는 길목이다.
훅을 쓰면 별도의 에이전트 연동 없이도 양쪽을 모두 잡는다.
README가 에이전트 쪽 연동을 두는 이유는
푸시가 막혔을 때 에이전트가 기다려야 한다는 것을 알려 주기 위해서다.

이 선택은 이해를 코드 리뷰 이전의 문제로 다룬다는 선언이기도 하다.
기존 리뷰는 작성자가 자기 변경을 이해한다는 가정 위에서 돌아간다.
에이전트가 쓴 변경이 늘면 이 가정이 깨지기 쉬우므로,
리뷰어가 보기 전에 작성자가 이해했는지를 먼저 확인하는 구조다.

### 시험관은 대화를 모르는 독립 모델이다

질문을 만드는 모델은 코드를 만든 대화를 보지 못하고 커밋된 변경만 읽는다.
이 독립성이 설계의 핵심이다.
같은 에이전트가 자기 코드로 문제를 내면
그 에이전트가 가진 가정이 그대로 질문에 들어간다.
대화를 모르는 독립 모델은 작성자와 에이전트가 함께 놓친 시나리오를 물을 수 있다.

대신 이 독립성에는 비용이 따른다.
검토 모델은 프로젝트의 의도를 모르므로
`.sphinxcontext.md`로 무엇이 깨지면 안 되는지를 알려 주어야 한다.
README의 예는 예약이 겹치면 안 된다는 식의 한 줄이다.
이 파일은 모든 검토 요청에 함께 전달되며 16KB 이하로, 비밀 없이 쓰라고 한다.

### 마찰은 정책 값으로 조정한다

Sphinx는 마찰을 하나의 스위치가 아니라 여러 값으로 나눈다.
검사할 브랜치와 이벤트, 질문 수(`level`), 질문의 거리(`distance`),
통과 유효 시간, 모델 호출 상한(`--max-model-calls`, 1~100)이 있다.
모델 호출에는 기본 상한이 없고 한 번의 검사에 보통 5~8번 호출하며,
답변마다 한 번쯤 더 요청한다고 한다.
비용 상한은 사용자가 직접 정해야 한다.

## 비평

### 통과는 이해의 증거가 아니라고 README가 먼저 말한다

README의 한계 목록은 솔직하다.
이 도구는 연습이지 보안 게이트가 아니고,
코딩 에이전트를 포함해 로컬 접근이 있는 누구든
훅을 우회하거나 외부 도움을 받을 수 있다고 적는다.
통과가 누가 코드를 썼는지도, 도움 없이 이해했는지도 증명하지 못하며
시험관이 LLM이라 틀릴 수 있다고도 한다.

그렇다면 도구의 효과는 사용자의 선의에 기댄다.
시험이 오픈북이어서
에이전트에게 질문을 그대로 붙여 넣고 답을 받아 적어도 통과할 수 있다.
이해를 키우려는 사람에게는 도움이 되고,
이해를 피하려는 사람은 마찰만 느낀다.
도구가 가장 필요한 사람이 가장 쉽게 우회할 수 있는 구조다.

HN에서도 같은 약점이 거론되었다. lecarore는 게으른 사람이 질문을 에이전트에게
그대로 붙여 넣는 것을 막을 방법이 없어서 문지기로 효과적일지 모르겠다고
했다.[^lecarore] zapkyeskrill은 답변이 AI가 생성한 것인지도 확인하느냐고
물었다.[^zapkyeskrill]
README가 스스로 인정한 한계가 사용자들의 첫 의문으로 나온 셈이다.

### 채점도 LLM이고 평가는 아직 통제된 시험이 아니다

저장소의 평가 결과는 개발 중에 합성 저장소 다섯 개로 측정한 것이다.
최근 결과에서는 생성된 질문에 대한 판정 검사 열네 건 중 열두 건이 일치했다.
저장소 스스로 이를 모든 항목이 통과한 의미 평가가 아니라고 말하고,
충분한 설명이 구체적인 코드 조건을 말하지 않았다는 이유로 거부된 사례를 남겼다.
단위 테스트 560개가 통과했다는 사실은 채점의 공정성과는 별개라고도 적는다.

이 솔직함은 믿을 만하지만 결론은 분명하다.
오답이 정답으로, 정답이 오답으로 처리될 수 있고,
그 비율은 임의의 저장소와 답변에 대해 알려져 있지 않다.
README는 잘못된 질문에 이의를 제기하면 그 개념은 통과로 치지 않고
질문이 고쳐질 때까지 막는다고 설명한다.
이의 제기 경로를 둔 것 자체가 틀린 질문이 나올 수 있음을 전제로 한다.

jan_m_savage는 AI가 대부분 만든 도구가 다른 AI가 썼을 코드를 검사한다는 점을
짚고, 검사 도중에 AI가 환각하면 어떻게 되느냐고
물었다.[^jan_m_savage] hatch_q는 검토까지 AI가 하면
모두가 같은 환각을 해야 통과되는데,
그렇다면 애초의 요구사항이 틀렸다는 뜻이라고 답했다.[^hatch_q]
이 답은 검토와 구현이 같은 방향으로 틀리는 경우만 말한다.
시험관만 틀리고 사용자가 맞았을 때 생기는 마찰은 다루지 않는다.

### 기본 설치 범위가 넓고 코드가 밖으로 나간다

`sphinx install`은 이 컴퓨터 전체의 Git 훅을 바꾼다.
설치 직후 어느 저장소든 `main`으로의 푸시가 검사받는다.
검토 모델 제공자는 변경된 코드와 관련 파일, 답변, `.sphinxcontext.md`를 받는다.
무시 규칙은 경로에만 적용되므로
일반 소스에 붙여 넣은 비밀은 걸러지지 않는다고 README가 인정한다.

따라서 도입 전에 `.sphinxignore`를 먼저 손봐야 한다.
README도 첫 검사 전에 편집하라고 적었다.
이 부담은 개인 취향이 아니라 조직의 정책이 정해야 할 사항이다.

### 푸시는 이해를 확인하기에 늦은 지점일 수 있다

fwlr는 이 도구가 푸시 전이 아니라
다른 사람의 시간이나 주의를 요청하기 전에 개입하면 크게 퍼질 것이라고 했다.
PR을 올리거나 갱신하는 버튼을 막으면
낭비를 많이 줄인다는 것이다.[^fwlr] reddmachine은 한 걸음 더 나아가
코드를 쓰기 전에 개입해야 하며 푸시 전에 확인하는 것은 이상하다고 했다.
비슷한 도구를 구현해 본 경험에서 객관식은
이해 없이 찍게 만든다는 말도 덧붙였다.[^reddmachine]

rDr4g0n은 같은 효과를 PR 설명을 쓰며 얻는다고 했다.
무엇을 왜 하는지, 어떻게 하는지를 압축해 쓰려면 이해가 필요하고,
그 과정에서 LLM이 내린 숨은 결정과 가끔은 버그가 드러난다는 것이다.[^rDr4g0n]
세 의견은 시점이 서로 다르지만
푸시가 이해를 확인하는 최적의 지점이 아니라고 보는 점은 같다.

## 인사이트

### 이해를 확인하는 단계가 리뷰의 병목을 작성자 쪽으로 옮긴다

기존 코드 리뷰의 병목은 리뷰어의 시간이었다.
작성자가 이해하고 있다는 전제 아래 리뷰어가 바깥에서 검증했다.
에이전트가 코드를 쓰면 작성자가 이해한다는 전제가 빠지고,
리뷰어는 작성자가 모르는 코드를 대신 이해해야 하는 부담을 진다.

Sphinx는 이 비용을 작성자에게 돌려 준다.
리뷰어에게 변경을 넘기기 전에 작성자가 스스로 이해를 보여야 한다.
이 구조는 항공 관제의 복창(read-back)과 닮았다.
조종사가 지시를 되풀이해 말해 이해했음을 확인하는 절차다.
다만 복창은 글자 그대로의 일치를 확인하지만
Sphinx는 의미의 이해를 확인해야 하고, 여기서 어려움이 생긴다.
의미는 일치 여부를 기계적으로 재기 어렵기 때문에 채점이 LLM에 맡겨진다.

HN에서는
이 병목 진단을 뒷받침하는 의견이 나왔다. 0c3ca83은
코드를 내보내는 일의 병목이 학습이라고 했다.
머릿속에 모델을 만들고 경계 사례와 시스템 상호작용을 가늠하는 일이 병목이고
타이핑은 작은 부분이므로, LLM으로 속도를 올린다면
속도의 대부분은 학습을 줄이는 데서
나온다는 것이다.[^0c3ca83] maximg68은 비슷한 기능을 직접 만들어 쓰며
에이전트가 계획 단계에서 놓친 시나리오를 짚어 주어 순이익이 있었다고 밝혔다.
동료들은 미리 꼼꼼히 계획하니 이해 수준이 같다고 반박했다고 한다.[^maximg68]

반응은 도구의 방향 자체를 두고도 갈렸다. nkmnz는
부정적인 댓글이 슬롭이 나쁘다는 식으로 일축한다고 꼬집었다.
그리고 이런 도구가 5~10년 전 이해하지 못한 코드를 스택오버플로에서
복사하지 말라던 경고의 역할을 이어받는다고
평가했다.[^nkmnz] rglover는 이해를 피하려는 시도일 뿐이며 제대로 배우라고
반박했고,[^rglover] dzogchen은 상사가 정한 마감 앞에서
여섯 달을 더 달라고 할 수 있느냐고 되물었다.[^dzogchen]
이 논쟁의 답은 이해에 드는 시간을 비용으로 인정하는 조직인지에 따라 달라진다.

### 통과가 목표가 되는 순간 질문은 시험 대비의 대상이 된다

굿하트의 법칙은 측정이 목표가 되면 좋은 측정이 아니게 된다고 말한다.
Sphinx에서 측정은 질문 통과이고,
통과는 24시간 유효하며 같은 변경에는 다시 묻지 않는다.
사용자는 어떤 질문이 나오고 어떻게 채점되는지를 익힐 수 있고,
이해가 아니라 통과를 위한 답 쓰기를 배울 수 있다.

이 위험을 줄이는 요소는 새로운 시나리오다.
틀리면 같은 개념에서 다른 시나리오가 나오므로
답을 외우는 방식은 통하지 않는다.
하지만 이는 개념 단위의 방어이고,
시험관이 같은 방식으로 묻는 한 사용자는 질문의 형식을 익힌다.
이해 확인이 오래 유지되려면
질문 생성의 다양성이 사용자의 학습 속도보다 빨라야 한다.

jamienk는 확인 피로(Confirmation Fatigue)를 기억하느냐며
곧 Sphinx와 대신 상호작용하는 에이전트가 등장할 것이라고 내다봤다.[^jamienk]
통과가 목표가 되는 구조에서는 자연스러운 다음 단계다.

### 개인의 규율로 설계된 도구가 팀의 문지기가 되면 성격이 바뀐다

Sphinx는 사용자가 스스로에게 거는 규율로 설명되고,
`sphinx yolo`처럼 스스로 끄는 탈출구를 둔다.
그러나 `.sphinxconfig`를 커밋해 정책을 공유할 수 있다는 점은
이 도구가 팀에 도입될 수 있음을 뜻한다.
이때 질문을 받는 사람과 설정을 정한 사람이 다르다.

팀이 이를 강제하면 우회 수단은 정책 위반이 되고,
README가 인정한 대로 로컬 접근이 있으면 우회는 쉽다.
그래서 이 도구는 개인이 쓸 때와 팀이 쓸 때 역할이 다르다.
개인에게는 학습 보조이고, 팀에게는 신뢰에 기대는 약한 문지기다.
팀에 도입한다면 훅을 쓰는 로컬 검사가 아니라
병합 단계의 검사로 보강해야 하는데,
버전 0.1은 웹 병합과 CI 필수 검사와 배포를 다루지 않는다고 명시한다.

sshah03은 PR의 시각적 요약과 퀴즈를 주는 오픈 소스 앱을 두고
게이트로 강제하기보다 이해하고 싶은 사람이 고르는 선택 기능으로 두기로 했다.
AI가 만든 PR의 양이 그 정도도
감당하기 어려울 만큼 늘고 있다는 이유였다.[^sshah03]
선택 사항이면 우회가 문제가 되지 않고,
강제하면 우회가 곧 정책 위반이 된다는 앞의 구분과 이어진다.
