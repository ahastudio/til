# Codex Harness: Claude Code용 하네스를 Codex로 옮기며 무엇이 달라졌는가

<https://github.com/revfactory/codex-harness>

## 소개

프로젝트를 살펴보고 작은 팀을 설계한 뒤 Codex 네이티브 에이전트와 재사용 가능한 스킬을 만들어 주는 프로젝트 범위 하네스 공장이다.
부모 오케스트레이터가 독립적인 작업을 병렬로 배치하고 결과를 통합하며 최종 검증을 책임진다.

Python으로 쓰였고 Apache 2.0 라이선스이며, 2026년 9월 7일에 만들어졌다.
별 43개, 포크 13개, 미해결 이슈 1개로 아직 작은 저장소다.
README는 영어, 한국어, 일본어로 제공된다.

정체성을 스스로 명확히 규정한다.
`revfactory/harness`를 상류 커밋 `cceac68` 기준으로 독립 이식한 프로젝트이며,
원본의 팀 설계 워크플로와 여섯 가지 아키텍처 패턴을 Codex에 맞춘 것이다.
그리고 상류의 Claude Code 벤치마크는 이 이식판의 성능을 보증하지 않는다고 첫 화면에서 적는다.

여섯 가지 설계 패턴은 파이프라인, 팬아웃/팬인, 전문가 풀, 생산자/리뷰어, 감독자, 계층적 분해다.
이 중 계층적 분해는 Codex로 옮겨 오면서 부모가 관리하는 의존성 그래프로 바뀌었고, 재귀적 에이전트 생성을 요구하지 않는다.

## 팀 구성

기본 팀은 부모 세션과 다섯 개의 시드 에이전트로 이루어진다.

| 역할                | 책임                                                 | 설정된 샌드박스 |
| ------------------- | ---------------------------------------------------- | --------------- |
| 부모 세션           | 일정 조율, 공유 인터페이스, 통합, 최종 수용 판정     | 현재 세션       |
| `harness_explorer`  | 관련 코드를 훑고 출처가 붙은 근거를 돌려줌           | 읽기 전용       |
| `harness_architect` | 경계와 의존성과 수용 기준을 응답 안에서 계획함       | 읽기 전용       |
| `harness_worker`    | 명시적으로 소유한 파일 안에서 구현함                 | 작업공간 쓰기   |
| `harness_reviewer`  | 수정 없이 실행 가능한 결함을 보고함                  | 읽기 전용       |
| `harness_qa`        | 검사를 실행하고 배정된 테스트와 검증 산출물을 작성함 | 작업공간 쓰기   |

부모는 각 작업에 목표, 소유 파일, 의존성, 수용 기준을 배정한다.
작업자들은 작업공간을 공유하되 서로의 수정을 보존하고 근거를 돌려준다.
공유 파일에는 소유자가 하나뿐이고, 의존하는 작업은 입력이 준비될 때까지 기다린다.

프로젝트 설정은 네이티브 서브에이전트를 켜고 동시 서브에이전트 스레드를 최대 셋으로 요청한다.
모델과 추론 강도는 부모에서 상속되고, 자식 에이전트는 기본적으로 재귀적으로 위임하지 않는다.
QA가 제품 코드를 고치지 않는다는 제약은 샌드박스 수준의 강제가 아니라 쓰기 권한 안에서의 지시 경계라고 명시한다.

## 설치

권장 경로는 플러그인 설치이며 저장소를 복제하거나 Python 설치 스크립트를 돌릴 필요가 없다.

```bash
codex plugin marketplace add https://github.com/revfactory/codex-harness.git
codex plugin add codex-harness@codex-harness
```

대상 프로젝트를 새 Codex 세션에서 연 뒤 `$harness`로 시작하는 요청을 보내면 된다.
한국어 요청도 동작한다고 적혀 있다.

```text
$harness Build a harness for this project. Use subagents in parallel for independent tasks.
```

플러그인만 설치하면 `harness` 스킬과 참조 자료와 보조 스크립트가 들어온다.
미리 정의된 5인 팀과 프로젝트 설정까지 넣으려면 별도의 프로젝트 설치 스크립트를 돌려야 한다.

```bash
python3 scripts/install.py --target /absolute/path/to/project --dry-run
python3 scripts/install.py --target /absolute/path/to/project
python3 scripts/validate.py --project /absolute/path/to/project
```

설치기는 표준 `harness` 스킬과 다섯 개의 시드 에이전트를 복사하고,
지원되는 프로젝트 설정 형식과 `AGENTS.md` 포인터를 기존 내용을 보존하며 병합한다.
개인 Codex 설정은 건드리지 않는다.

설정 병합에서 한 가지 제약이 문서화되어 있다.
인라인 `agents = { ... }` 테이블에 설치기가 넣어야 할 기본값이 빠져 있으면 파일을 쓰기 전에 진단과 함께 실패한다.
사용자가 값을 보존하며 `[agents]` 형태로 펼친 뒤 다시 실행해야 한다.

## 실행 상태와 에이전트 간 통신

부모는 실제 프로젝트 계획에서 실행을 초기화하고 네이티브 에이전트 ID를 기록하며,
각 자식에게 프로젝트 루트와 안정적인 입력 지문과 결정 사항과 스킬과 소유권과 의존성과 수용 기준을 담은 갱신된 패킷을 준다.

```bash
python3 .agents/skills/harness/scripts/run.py --project . init \
  --plan-file /absolute/path/to/project-plan.json --run-id project-v1
python3 .agents/skills/harness/scripts/run.py --project . ready --run project-v1
python3 .agents/skills/harness/scripts/run.py --project . status --run project-v1
```

중요한 메시지는 `_workspace/communications/<run-id>.jsonl`에 명시적으로 기록된다.
기록 절차가 세 단계로 규정되어 있다.
나가는 이벤트를 기록하고, 실제 네이티브 메시징 도구를 사용하고, 그 전달 결과를 기록해 답신과 연결한다.
읽기 전용 역할은 자기 메시지를 부모에게 기록과 전달을 요청한다.

이 로그의 한계도 같은 문단에 적혀 있다.
로컬 로깅은 메시지를 보내지 않으며 Codex 내부 동작을 자동으로 잡아내지도 않는다.

재개 규칙이 꽤 구체적이다.
입력 파일 내용만 바뀌었으면 보통의 `resume`을 쓴다.
결정 사항, 소유권, 수용 기준, 목표가 바뀌었거나 작업이 추가·삭제되었으면
이전 실행 원장을 수정하지 않고 새 실행으로 갈라서 수정된 계획 템플릿을 넣는다.

```bash
python3 .agents/skills/harness/scripts/run.py --project . resume \
  --run project-v1 --new-run project-v2 \
  --plan-file /absolute/path/to/revised-project-plan.json
```

바뀐 계약과 그 영향을 받는 하위 작업은 대기 상태로 되돌아가고, 바뀌지 않은 채 수용된 작업은 재사용된다.
쓰기 소유권을 넘기기 전에 부모가 이전 에이전트의 정지나 유휴 상태를 확인한다는 규칙도 있다.
작업 완료와 네이티브 세션의 유휴·종료는 별개라는 점을 명시하기 위한 것이다.

## 검증 기록

저장소는 검증 내역을 별도 문서로 분리해 두었고, 무엇이 확인되었고 무엇이 확인되지 않았는지를 항목마다 구분한다.

자동 검사 쪽은 오프라인이다.
94개 테스트 통과, 저장소 검증 5개 에이전트와 1개 스킬에 오류 0건, 예제 프로젝트 검증 통과, `git diff --check` 통과이며,
GitHub Actions가 Ubuntu에서 Python 3.11과 3.13으로 첫 공개 이식 커밋을 통과시켰다.
테스트가 다루는 범위에는 설치 보존과 멱등성, 심볼릭 링크 대상, 롤백, 유니코드 TOML 왕복, 작업 의존성 순환,
동시 쓰기 소유권 충돌, 24개 동시 작성 프로세스에서의 통신 로그, 손상된 꼬리 보존이 들어간다.

인증이 필요한 라이브 회귀 테스트는 CI 밖에 있다.

```bash
python3 scripts/live_smoke.py run --target _workspace/live-tests/NEW_ID
```

이 스크립트는 네이티브 커스텀 작업자 둘, 차단된 작업과 완료 검사 실패,
입력 수정 후 재개와 변경되지 않은 결과의 재사용, 그리고 QA 단언 둘을 실행한다.
최대 1,200초를 허용하며, README는 이 명령 자체가 기록된 통과가 아니므로 실제 기록과 파일과 검사 결과를 직접 확인하라고 적는다.

호환성 문서의 단서들이 이 프로젝트의 태도를 잘 보여 준다.
샌드박스 선언은 의도한 정책의 표현이며, 부모 세션의 런타임 재정의와 플랫폼 제약이 실효 샌드박스를 바꿀 수 있다.
소유권 지시는 파일 단위 접근 제어를 만들지 않는다.
역할이 발견되고 서브에이전트 도구가 노출된다는 것이 현재 세션에서 네이티브 생성이 동작한다는 근거는 아니다.

이슈 1번 재확인 기록도 같은 방식으로 쓰였다.
CLI가 0으로 종료하고 자식 ID와 준비 응답을 보고했지만, 기록된 JSONL에 배치를 독립적으로 확인해 줄 생성 메타데이터가 없었다.
그래서 이것은 보고된 성공이며 CLI 버전이 고쳐졌다는 증명도, 네이티브 병렬성의 증명도, 완전한 워크플로의 증명도 아니라고 적는다.

## 분석

### 이식판이 상류의 신뢰를 물려받지 않겠다고 선언했다

포크나 이식 프로젝트가 흔히 하는 일은 원본의 평판을 그대로 가져오는 것이다.
README 상단에 원본의 벤치마크와 별 수를 적고, 달라진 부분만 아래에 덧붙인다.

이 저장소는 반대로 한다.
상류 커밋 해시를 명시해 어느 시점의 이식인지 고정하고,
바로 다음 문장에서 상류의 Claude Code 벤치마크가 이 이식판의 성능을 보증하지 않는다고 적는다.
라이선스 절에서도 이식판의 Codex 동작과 검증 상태를 상류 릴리스와 별도로 문서화한다고 다시 확인한다.

이 선택이 실무적으로 의미가 있는 이유는 하네스가 런타임에 강하게 결합된 물건이기 때문이다.
같은 팀 설계와 같은 프롬프트라도 에이전트 생성 방식, 동시성 한도, 샌드박스 강제 수준, 세션 수명이 다르면 결과가 달라진다.
계층적 분해 패턴이 재귀 생성에서 부모 관리 의존성 그래프로 바뀐 것이 그 결합의 구체적인 증거다.
패턴 이름은 같지만 실행 구조가 다르므로, 상류의 측정값을 가져오는 것은 이름만 옮기는 일이 된다.

### 조정 문제를 소유권과 의존성으로 환원했다

이 하네스가 다중 에이전트에서 실제로 푸는 문제는 모델의 능력이 아니라 충돌이다.
설계가 그 점을 드러낸다.

공유 파일에 소유자를 하나만 두는 규칙, 의존 작업이 입력을 기다리는 규칙,
쓰기 소유권을 넘기기 전에 이전 에이전트의 정지를 확인하는 규칙이 모두 같은 문제를 겨냥한다.
두 에이전트가 같은 파일을 동시에 고쳐 서로의 수정을 덮는 상황이다.

작업 패킷의 구성도 같은 방향이다.
목표, 소유 파일, 의존성, 수용 기준 네 가지인데, 이 중 셋이 조정에 관한 것이고 하나만 내용에 관한 것이다.
에이전트에게 무엇을 할지 알려 주는 것보다 무엇을 건드리지 말지 알려 주는 데 더 많은 구조를 쓴 셈이다.

읽기 전용 역할을 셋이나 둔 것도 같은 맥락에서 읽힌다.
탐색, 설계, 리뷰는 쓰기가 필요 없으므로 쓰기를 주지 않았고, 그만큼 충돌 가능 지점이 줄어든다.
쓰기 권한을 가진 역할은 작업자와 QA 둘뿐이며, 그중 QA는 제품 코드를 고치지 않는다는 지시 경계를 추가로 받는다.

### 문서가 보고된 것과 증명된 것을 어휘로 구분한다

검증 문서의 가장 특징적인 점은 결과를 적는 방식이다.
CLI가 0으로 종료하고 자식 ID를 돌려준 사건을 성공이라 부르지 않고 보고된 성공이라 부른다.
근거는 기록된 JSONL에 배치를 독립적으로 확인해 줄 생성 메타데이터가 없었다는 것이다.

이 구분이 다중 에이전트 시스템에서 특히 필요하다.
에이전트가 작업이 끝났다고 말하는 것과 작업이 실제로 끝난 것은 다른 사건이고,
그 둘 사이의 간격이 이런 시스템의 주된 실패 지점이기 때문이다.
로컬 통신 로그가 메시지를 보내지 않으며 Codex 내부를 자동으로 잡아내지 않는다고 분명히 한 것도 같은 구분이다.
로그에 기록이 있다는 사실은 기록이 있다는 사실일 뿐 전달의 증거가 아니다.

이 저장소에 정리된 다른 하네스 논의들이 같은 지점에서 만난다.
자기 개선 하네스를 다룬 쪽은 시스템 프롬프트와 도구 설명과 미들웨어를 파일 시스템에 드러내 관찰 가능하게 만드는 것을 핵심으로 삼았고,
하네스의 비용 차이를 측정한 쪽은 같은 모델이 하네스에 따라 토큰 비용이 몇 배 차이 난다는 것을 보였다.
관찰 가능성이 이 분야에서 반복해 핵심으로 지목된다.

### 재개 규칙이 캐시 무효화 문제를 그대로 닮았다

재개 설계는 단순한 이어하기가 아니라 무효화 규칙이다.
입력 파일 내용만 바뀌면 보통의 재개, 계약이 바뀌면 새 실행으로 분기하고 영향받는 하위 작업을 대기로 되돌린다.

이 구조는 빌드 시스템의 의존성 그래프와 같은 문제를 푼다.
무엇이 바뀌었을 때 무엇을 다시 해야 하는가다.
입력 지문을 안정적으로 유지한다고 적은 것이 그 열쇠이고,
바뀌지 않은 채 수용된 작업을 재사용한다는 규칙이 재실행 비용을 줄인다.

에이전트 작업에서 이 절약이 특히 크다.
빌드에서 재실행되는 것은 CPU 시간이지만, 여기서 재실행되는 것은 모델 호출이므로 금액과 지연이 함께 든다.
이전 실행 원장을 수정하지 않고 새 실행으로 가른다는 규칙은 그 재사용 판단의 근거를 보존하기 위한 것이다.

## 비평

### 이 프로젝트가 무엇을 개선했는지 재는 척도가 없다

문서에 숫자가 풍부하다.
94개 테스트, 5개 에이전트, 오류 0건, 24개 동시 작성 프로세스, 1,200초 제한이다.
그런데 이 숫자들은 전부 구조와 절차가 의도대로 동작하는지에 대한 것이고, 하네스를 썼을 때 결과가 나아지는지에 대한 것은 하나도 없다.

상류 벤치마크가 이 이식판을 보증하지 않는다고 밝힌 것은 정직하다.
문제는 그 자리를 대신할 측정이 제공되지 않는다는 점이다.
그러면 독자에게 남는 질문이 그대로 남는다.
5인 팀으로 병렬 처리하는 것이 단일 세션보다 나은가, 낫다면 어떤 종류의 작업에서 얼마나 나은가.

이 질문에 답하기 어렵다는 것은 사실이다.
같은 작업을 두 구성으로 돌려 비교하려면 작업 집합과 성공 기준과 반복 횟수가 필요하고, 모델 비결정성 때문에 반복이 여러 번 필요하다.
그러나 어렵다는 것이 답할 필요가 없다는 뜻은 아니며,
94개 테스트가 통과했다는 문장이 그 자리를 채우면 독자는 검증된 프로젝트라는 인상을 근거 없이 받게 된다.

### 조정 규칙의 대부분이 강제되지 않는 지시다

이 하네스의 안전성은 소유권 규칙에 얹혀 있는데, 문서 스스로 그 규칙이 강제되지 않는다고 여러 곳에서 인정한다.
소유권 지시는 파일 단위 접근 제어를 만들지 않고, QA의 제품 수정 금지는 쓰기 권한 안에서의 지시 경계이며,
샌드박스 선언은 의도의 표현이고 실효 정책은 런타임이 정한다.

정직한 서술이지만, 정직함이 문제를 없애지는 않는다.
모델이 지시를 어기는 것은 드문 사건이 아니라 이 분야의 기본 실패 모드이고,
작업자 둘이 같은 파일을 고치는 사고가 정확히 그 실패 모드에서 나온다.
문서는 그 사고가 일어났을 때 어떻게 감지되는지, 감지 후 부모가 무엇을 하는지를 설명하지 않는다.

테스트 목록에 동시 쓰기 소유권 항목이 있지만, 이것은 계획 검증 단계에서 두 작업이 같은 파일을 소유하도록 선언된 경우를 잡는 검사로 읽힌다.
선언을 어기고 실제로 쓰는 경우와는 다른 사건이다.
기술적으로 가능한 방어가 없는 것도 아니다.
작업 전후의 파일 해시를 비교해 소유하지 않은 파일의 변경을 검출하는 사후 검사는 샌드박스 지원 없이도 구현할 수 있다.

### 핵심 기능이 인증된 수동 테스트 뒤에 있다

가장 중요한 동작, 즉 네이티브 서브에이전트가 실제로 병렬로 생성되어 일하는지는 CI에서 검증되지 않는다.
CI가 돌리는 것은 오프라인 테스트이고, 라이브 회귀는 인증된 클라이언트가 있어야 하며 최대 20분이 걸리고 기본 CI에서 제외되어 있다.

그래서 이 저장소의 상태를 확인하는 유일한 방법이 사용자가 자기 환경에서 직접 돌려 보는 것이다.
README도 그렇게 하라고 적는다.
합리적인 요구이지만, 결과적으로 이 프로젝트의 핵심 주장은 어떤 커밋에서도 자동으로 검증된 적이 없다.

이슈 1번 재확인 기록이 그 취약함을 보여 준다.
0.153.4에서 관측된 실패가 있었고, 0.154.0에서 성공이 보고되었지만 생성 메타데이터가 없어 확정할 수 없었다.
즉 이 프로젝트의 동작 여부가 Codex CLI의 마이너 버전에 따라 달라지며, 그 변화를 잡아내는 자동 장치가 없다.
CLI가 조용히 바뀌면 사용자가 실패로 먼저 알게 된다.

### 세 개의 문서가 같은 단서를 반복하며 실제 경계를 흐린다

README, 호환성 문서, 검증 문서가 모두 같은 종류의 유보를 반복한다.
문서 호환성 목표이지 모든 클라이언트를 시험했다는 주장이 아니라는 것,
CLI 인터페이스를 기술한 것이지 최소 지원 버전이 아니라는 것,
역할 발견이 네이티브 생성의 근거가 아니라는 것이다.

각각은 정확한 진술이다.
그러나 겹쳐 놓고 보면 독자가 실제로 무엇을 기대해도 되는지가 흐려진다.
어느 버전에서 어떤 구성으로 무엇이 동작하는 것이 확인되었는지를 한 표로 모아 주면 될 일인데,
그 정보가 세 문서의 문단 사이에 흩어져 있고 각 문단이 유보로 끝난다.

설치 경로가 둘로 갈린 것도 같은 문제를 만든다.
플러그인 설치는 스킬만 주고 프로젝트 에이전트와 설정과 `AGENTS.md`는 만들지 않는데,
README의 예제 명령은 프로젝트 설치를 전제한 경로를 쓴다.
권장 경로를 따른 사용자가 문서의 명령을 그대로 복사하면 동작하지 않는 구성이며, 그 사실은 각주 한 줄로만 안내된다.

## 인사이트

### 하네스는 런타임과 결합되어 있으므로 이식은 번역이 아니라 재설계다

이 저장소에서 가장 이전 가능한 관찰은 계층적 분해 패턴의 처리 방식이다.
같은 이름의 패턴이 Claude Code에서는 재귀적 에이전트 생성으로, Codex에서는 부모가 관리하는 의존성 그래프로 구현된다.
이름이 남고 구현이 바뀐 것이 아니라, 런타임이 재귀 생성을 기본으로 지원하지 않기 때문에 같은 목표를 다른 기계로 달성한 것이다.

이 관찰을 일반화하면 하네스 설계의 이식성 한계가 보인다.
하네스는 프롬프트의 모음이 아니라 에이전트 생성, 동시성 제어, 샌드박스, 세션 수명, 메시징이라는 런타임 원시 기능 위에 세운 구조물이다.
프롬프트는 복사되지만 그 원시 기능은 복사되지 않으므로, 옮길 때 실제로 옮기는 것은 설계 의도뿐이다.

그래서 하네스를 여러 런타임에서 쓰려는 팀이 먼저 해야 할 일이 있다.
자기 설계가 어떤 원시 기능에 의존하는지 목록으로 적는 것이다.
재귀 생성이 필요한가, 동시 스레드가 몇 개 필요한가, 샌드박스가 강제되어야 하는가, 자식이 부모에게 메시지를 보낼 수 있어야 하는가.
그 목록이 이식 가능성의 실제 척도이고, 목록에 없는 것은 어느 런타임에서든 옮겨진다.

### 지시로 만든 경계는 검출 장치와 함께 가야 경계가 된다

이 프로젝트는 소유권, 역할 분리, QA의 수정 금지를 모두 지시로 구현하고, 그것이 강제가 아님을 정직하게 밝힌다.
그 정직함에서 끌어낼 실천은 다른 데 있다.
강제할 수 없는 경계는 검출할 수 있어야 한다는 것이다.

강제와 검출은 비용이 다르다.
강제는 런타임 지원을 요구하고 대개 구현할 수 없지만, 검출은 대부분 사후 비교로 가능하다.
작업 시작 시점의 파일 해시 목록과 종료 시점의 목록을 비교하면 소유하지 않은 파일이 바뀌었는지 알 수 있고,
그 검사는 모델의 협조를 전혀 필요로 하지 않는다.

이 구분이 중요한 이유는 다중 에이전트 시스템의 실패가 조용하기 때문이다.
에이전트가 지시를 어겨도 오류를 내지 않고, 결과가 그럴듯하게 돌아오며, 문제는 나중에 다른 작업이 깨질 때 드러난다.
검출 장치가 없으면 그 시점에 원인을 되짚을 근거도 남지 않는다.
경계를 선언하는 문장을 쓸 때마다 그 경계가 깨졌음을 알아차릴 방법을 함께 적는 것이 실질적인 규율이 된다.

### 테스트 개수는 구조의 건강을 재지 작업의 품질을 재지 않는다

94개 테스트 통과라는 문장은 강한 인상을 주지만, 이 저장소의 테스트가 무엇을 다루는지 목록을 보면 성격이 분명해진다.
설치 보존과 멱등성, 심볼릭 링크 대상, TOML 왕복, 의존성 순환, 통신 로그의 동시 작성이다.
전부 도구 자체의 정합성이고, 이 도구로 만든 코드가 좋아지는지는 하나도 다루지 않는다.

이것은 결함이 아니라 범주의 차이다.
문제는 두 범주가 같은 자리에 나란히 제시될 때 독자가 구분하지 않는다는 데 있다.
에이전트 도구를 평가할 때 이 구분을 먼저 하는 것이 유용하다.
제시된 증거가 도구가 의도대로 동작한다는 증거인가, 도구를 쓴 결과가 나아진다는 증거인가.

두 번째 종류의 증거는 거의 항상 비싸고, 그래서 거의 항상 빠져 있다.
도입을 검토하는 쪽에서는 그 공백을 스스로 메워야 한다는 뜻이다.
자기 저장소의 실제 작업 대여섯 개를 골라 하네스를 쓴 경우와 쓰지 않은 경우를 각각 몇 번씩 돌려 보는 것이
저장소의 어떤 문서보다 빠르게 답을 준다.

### 상속하지 않겠다는 선언이 포크의 가장 유용한 문서다

포크와 이식이 흔해진 환경에서 이 저장소가 보여 준 가장 이전 가능한 관행은 기술이 아니라 문장이다.
상류 커밋 해시를 고정하고, 상류의 측정값이 이쪽을 보증하지 않는다고 적고, 검증 상태를 별도로 문서화하겠다고 선언한 것이다.

이 선언의 가치는 이 프로젝트를 쓰는 사람보다 이 프로젝트를 평가하는 사람에게 크다.
포크를 만났을 때 가장 알기 어려운 것이 어디까지가 원본의 성질이고 어디부터가 이쪽의 성질인지인데,
커밋 해시 하나와 보증하지 않는다는 문장 하나가 그 경계를 정확히 그어 준다.

반대 사례를 떠올려 보면 차이가 분명해진다.
원본의 별 수와 벤치마크를 README 상단에 그대로 둔 포크는 독자가 그 숫자의 출처를 추적할 수 없고,
원본이 나중에 바뀌어도 포크의 설명은 갱신되지 않는다.
포크를 공개할 때 상류 리비전과 상속하지 않는 주장 목록을 적는 것은 비용이 거의 들지 않으면서
이후 모든 평가의 출발점을 제공하는 드문 종류의 문서다.
