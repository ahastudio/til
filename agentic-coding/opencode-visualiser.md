# OpenCode Visualizer

<https://github.com/psinetron/opencode-visualiser>

## 소개

OpenCode Visualizer는 OpenCode의 실행 상황을 픽셀아트 사무실의 캐릭터로 보여 주는 플러그인이다.
저장소 설명은 “원시 터미널 로그를 아늑한 2D 픽셀 사무실로 바꾼다”이다.
이 문서가 코드를 읽어 확인한 바로는 로그를 읽는 도구가 아니라
OpenCode 프로세스 안에서 돌며 이벤트를 받는 플러그인이다.
npm 패키지 이름은 `psinetron-opencode-visualizer`이고 MIT 라이선스이다.
2026년 11월 25일 GitHub API로 본 별은 193개, 포크는 16개이고
저장소는 2026년 6월 1일에 만들어졌다.
커밋은 17개이며 main의 마지막 커밋은 2026년 10월 5일이다.
저장소의 홈페이지 항목은 별도 사이트가 아니라 저장소 안의 README를 가리킨다.

이 문서는 저장소의 커밋을 받아 소스를 읽고 썼으며 설치하거나 실행하지 않았다.
파일 경로와 줄 번호는 받은 저장소 기준이다.

## 동작 방식

### 모듈 구성

| 파일                                       | 줄 수 | 역할                                                     |
| ------------------------------------------ | ----- | -------------------------------------------------------- |
| `index.ts`                                 | 184   | 플러그인 진입점, 훅 세 개, 소켓 클라이언트, 서버 승계    |
| `visualizer/ocv-server.ts`                 | 202   | `Bun.serve`로 정적 파일과 WebSocket 중계                 |
| `visualizer/index.html`                    | 883   | Canvas 그리기, 캐릭터 상태 기계, 소켓 수신               |
| `tui.ts`                                   | 39    | `/visualizer` 명령이 주소를 토스트로 알리는 TUI 플러그인 |
| `opencode.json`                            | 6     | 저장소 자체에서 `./index.ts`를 플러그인으로 등록         |
| `visualizer/person1`~`person5`, `textures` | PNG   | 외형별 프레임 이미지와 배경, 책상, 커피 테이블           |

### 이벤트는 플러그인 훅으로 들어온다

OpenCode 플러그인 API(`@opencode-ai/plugin`)의 훅 세 개를 쓴다.
`event`, `tool.execute.before`, `tool.execute.after`이다(`index.ts` 167~179줄).
파일을 읽거나 표준 입력을 가로채거나 정규식으로 해석하는 코드는 없다.
`event` 훅은 이벤트 이름이 허용 목록에 있을 때만 보낸다.
허용 목록은 `session.status`, `session.created`, `session.deleted`, `session.idle`,
`session.error`, `session.diff`, `message.updated`, `todo.updated`이다(155~164줄).
도구 훅은 도구 이름만 보낸다.

### 서버는 먼저 포트를 잡은 인스턴스가 된다

OpenCode를 띄운 프로세스마다 플러그인이 하나씩 돌고,
모두 5173번 포트를 잡으려 시도한다.
포트를 잡은 쪽이 HTTP와 WebSocket을 한 포트에서 함께 제공하는 서버가 되고
나머지는 그 서버에 클라이언트로 접속한다(`index.ts` 22~35줄, `ocv-server.ts` 103~107줄).
서버가 있던 인스턴스가 닫히면 1초에 0~500ms의 임의 지연을 더해 기다린 뒤
남은 인스턴스가 포트를 이어받는다(`index.ts` 94~111줄).
클라이언트가 등록되거나 떠날 때마다 300초 타이머를 다시 걸고,
만료 시점에 플러그인과 프런트엔드 연결이 모두 0이면 서버가 멈춘다(`ocv-server.ts` 83~96줄).
서버를 잡은 프로세스의 플러그인도 자기 서버에 클라이언트로 붙으므로,
그 프로세스가 살아 있는 동안은 연결이 0이 되지 않는다.
이 경로로 서버가 멈추는 경우는 스탠드얼론으로 띄웠을 때를 빼면 드물 것으로 보이며,
시험해 보지는 않았다.
서버 코드는 `Bun.serve`, `Bun.spawn`, `Bun.file`을 직접 쓰므로 Bun 실행 환경이 전제이다.
페이지는 첫 플러그인이 등록되고 3초 뒤에 브라우저로 자동으로 열린다.
이미 열린 화면이 있으면 열지 않는다.

### 접속과 재시도

`index.ts`의 플러그인 함수는 로그 경로를 만들고 외형을 정한 뒤 서버를 시도하고,
최대 20번까지 WebSocket 접속을 시도한다(131~153줄).
시도마다 3초 제한이 있고 실패하면 300ms를 쉰다.
접속에 성공하면 `register` 메시지로 `instanceId`, `process.cwd()`, 외형을 보낸다(69~85줄).
`instanceId`는 `oc-` 뒤에 프로세스 ID와 무작위 문자열을 붙인 값이다(58줄).
외형 파일과 로그는 훅이 받은 `directory`를 쓰고 화면에 보내는 경로는 `process.cwd()`라서
두 값이 다르면 서로 다른 폴더를 가리킬 수 있다.
접속이 닫힐 때마다 `onclose`가 1초 뒤 재접속 타이머를 거는데(94~112줄),
이 핸들러는 초기 접속이 실패한 경우에도 불리므로 앞의 20회 반복과 겹쳐 돈다.
겹쳐서 연결이 이중으로 생기는지는 시험하지 않았다.
서버가 보낸 메시지는 `socket.onmessage = () => {}`로 버린다(114줄).
플러그인은 서버에서 아무것도 읽지 않고 보내기만 한다.

### 서버가 처리하는 메시지

서버는 메시지 `type` 세 가지만 처리하고 나머지는 무시한다(`ocv-server.ts` 131~161줄).

| 받는 메시지         | 서버 동작                                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| `register`          | 플러그인 목록에 넣고 `instance.added`를 방송한 뒤 `registered`로 답하고 브라우저 열기와 종료 타이머를 건다 |
| `frontend.register` | 프런트엔드 목록에 넣고 현재 인스턴스 목록을 `state.sync`로 보낸다                                          |
| `event`             | 내용을 보지 않고 `instance.event`로 프런트엔드 모두에게 방송한다                                           |

소켓이 닫히면 플러그인 목록에서 지우고 `instance.removed`를 방송한다(163~178줄).
`event`를 보낸 소켓이 먼저 `register`를 했는지 검사하는 코드는 없다.
JSON 해석에 실패한 메시지는 조용히 버린다(129줄).
HTTP 쪽은 `visualizer/` 폴더의 파일을 `Cache-Control: no-store` 헤더로 내주고
없으면 404, 예외가 나면 500을 돌려준다(106~124줄).

### 브라우저 열기

브라우저 실행은 운영체제별로 고정된 인자 배열을 `Bun.spawn`에 넘긴다(46~78줄).
macOS는 `open -n -a "Google Chrome" --args --app=<주소> --window-size=1024,768`,
Windows는 `cmd.exe /c start chrome ...`, 그 밖은 `google-chrome`을 먼저 시도한다.
`trySpawn`은 프로세스를 만드는 데 성공하면 참을 돌려주고 종료 코드는 보지 않는다(33~42줄).
`Bun.spawn`은 실행 파일이 없을 때 예외를 던지므로
Linux에서는 Chrome이 없을 때 Chromium, `xdg-open` 순으로 넘어간다.
macOS의 `open`과 Windows의 `cmd.exe`는 항상 존재하므로
Chrome이 없어도 첫 시도가 성공으로 처리되어 뒤의 대체 경로는 쓰이지 않는 것으로 읽힌다.
이것은 코드에서 읽은 추론이고 실행해 확인하지는 않았다.
서버를 승계받은 인스턴스는 `browserLaunched`를 거짓으로 되돌린 새 서버이므로
프런트엔드가 3초 안에 다시 붙지 못하면 창이 한 번 더 열릴 수 있다(88~91, 52~56줄).

### 화면은 한 장짜리 캔버스 페이지이다

`visualizer/index.html`(883줄)은 프레임워크도 빌드 단계도 없는 Canvas 2D 페이지이다.
논리 해상도는 640×480이고 스프라이트는 초당 6프레임, 걸음 속도는 초당 80픽셀이다.
OpenCode 인스턴스 하나가 캐릭터 하나이고 최대 다섯 명, 책상도 다섯 개이다.
여섯 번째 인스턴스는 조용히 그려지지 않는다(253줄).

캐릭터의 상태는 등장, 휴게 구역에서 대기, 책상으로 걷기, 앉기, 일하기, 오류,
일어서기, 커피 자리로 걷기, 커피 마시기, 퇴장이다(366~554줄).

- `session.status`가 `busy`나 `retry`이면 책상을 예약하고 걸어가 앉은 뒤 일한다(792~795줄).
  도구 훅은 캐릭터가 대기, 커피, 걷는 중일 때만 같은 일을 시킨다(842~848줄).
  일하는 동안 3~10초마다 긁거나 하품하는 동작이 끼어든다(283, 439줄).
- `busy`와 `retry`가 아닌 `session.status`와 `session.idle`은
  일하던 캐릭터를 일으켜 세운 뒤 빈 커피 자리로 보낸다(796~834줄).
- `session.error`는 일하는 중일 때만 오류 동작을 낸다(835~841줄).
- 프런트엔드가 서버와 끊어지면 10초 뒤 모든 캐릭터를 내보낸다.

프런트엔드가 실제로 쓰는 이벤트는 `session.status`, `session.idle`, `session.error`,
도구 훅뿐이다(787~851줄). `session.created`, `session.deleted`, `message.updated`,
`todo.updated`는 서버까지 전달되지만 화면 코드에 해당 분기가 없다.

### 프런트엔드의 판정과 이동

외형은 플러그인이 보낸 값을 쓰되 이미 다른 캐릭터가 쓰는 외형이면
남은 외형 중 첫 번째로 바꾼다(255~264줄).
그래서 두 프로젝트가 우연히 같은 외형을 저장해 두면 한쪽은 화면에서 다른 모습이 된다.
`localStorage`에 `viz-last-skin`을 쓰지만 읽는 곳은 없다(265줄).
책상 다섯 개 중 빈 것을 번호 순으로 받고(235~241줄),
책상에서 일어나도 책상 번호는 풀지 않는다.
번호는 대기 구역으로 돌아가는 경로를 고를 때 쓴다.
0~2번 책상은 `VERT_CORRIDORS`인 x=220 통로에서 대기 구역을 거쳐 커피 자리로 간다(356줄).
person1만 책상 앞 위치 `agentX`에 앉고 나머지는 `deskX`에 앉는다(331줄).
길찾기는 장애물 판정 없이 두 개의 세로 통로(x=220, x=450)를 거쳐
가로와 세로로만 꺾어 가는 점 목록을 만든다(178~218줄).
캐릭터는 초당 80픽셀로 걷고 상태마다 애니메이션 프레임을 따로 관리한다(570, 616~625줄).
등장과 퇴장은 투명도를 초당 2씩 올리고 내린다(370, 547줄).
커피를 마실 때는 프레임을 앞으로 갔다가 뒤로 돌리고 2초 쉬는 동작을 되풀이한다(510~544줄).
오류 동작 정의가 없는 외형은 오류 상태에 들어가는 즉시 일하기로 돌아가므로(467줄)
person2~5는 오류 때 눈에 보이는 반응이 없다.
스프라이트는 2배로 확대하여 그리고 `imageSmoothingEnabled`를 꺼서 도트를 유지한다(644, 650줄).
책상 앞에는 작업 폴더의 마지막 경로 조각을 최대 두 줄로 적는다(692~720줄).
이 조각은 `/`로만 나누므로 Windows 경로는 전체 경로가 잘려 적힐 것으로 읽힌다.
이벤트의 `sessionID`는 프런트엔드가 읽지 않는다.
한 OpenCode 인스턴스 안에서 여러 세션의 상태가 오가면
캐릭터 하나의 상태를 서로 덮어쓸 수 있다는 것이 코드에서 읽히는 결론이다.
하위 세션 이벤트가 같은 훅으로 오는지는 확인하지 못했다.

### 디스크와 프로세스

프로젝트 폴더에 `.opencode/viz-skin.json`(임의로 고른 외형)과
`.opencode/ocv-debug.log`(추가만 하는 로그)를 쓴다.
로그는 크기 제한이나 회전이 없다.
다만 로그에 쓰는 곳은 `index.ts`의 `log()` 호출 여섯 곳이고
서버 시작과 접속 성공 여부, 접속 실패 오류만 적는다(26~32, 142~152줄).
이벤트 내용이나 도구 이름은 로그에 쓰지 않는다.
서버 쪽 `serverLog`는 스탠드얼론으로 띄웠을 때만 콘솔에 찍는다(190~195줄).
브라우저는 고정된 인자로 직접 띄우며 셸 문자열을 조립하지 않는다.
`--app=` 창을 쓰지만 별도 `--user-data-dir`이 없어 사용자의 기본 프로필로 열린다.

### 의존성과 테스트

런타임에서 가져오는 외부 패키지는 없다.
`index.ts`는 `@opencode-ai/plugin`을 `import type`으로만 가져오므로 실행 시에는 지워진다.
`tui.ts`는 필요한 인터페이스를 파일 안에 직접 선언하고 아무것도 가져오지 않는다.
`index.ts`의 `existsSync`, `project`, `client`, `$`, `worktree`는 쓰이지 않는다.
`package-lock.json`은 `@opencode-ai/plugin` 1.18.34로 고정되어 있고
`package.json`은 `>=1.16.0`이다.
개발 의존성은 `typescript`와 `@types/node`인데 `tsconfig`도 스크립트도 없다.
`.github`에는 npm 의존성을 주 1회 확인하는 `dependabot.yml`과 후원 설정만 있고
테스트나 워크플로 파일은 없다.
따라서 이 저장소에는 시험하는 코드가 없고 동작은 코드 읽기로만 확인했다.
`node_modules`가 없어 `@opencode-ai/plugin`의 이벤트 타입은 읽지 못했다.

## 분석

### 무엇을 보여 주고 무엇을 보여 주지 않는가

Pixel Agents가 한 에이전트의 도구 하나하나를 읽어 캐릭터 동작에 옮기는 것과 달리
이 도구는 OpenCode 인스턴스마다 바쁨, 쉼, 오류 정도의 거친 상태 하나만 보여 준다.
서브 에이전트나 세션, 도구 종류는 모델링되어 있지 않다.
코드가 파일을 읽지 않고 플러그인이 받는 이벤트만 쓰므로
대화 기록 형식에 기대지 않는다는 장점이 있고,
그 대가로 플러그인 API가 주는 정보 밖의 활동은 볼 수 없다.

### 형식이 바뀔 때의 동작

허용 목록에 없는 이벤트는 버려지고,
`session.status`의 모양이 바뀌면 프런트엔드가 바쁨이 아닌 것으로 보아 쉼으로 처리한다.
버전 확인이나 스키마 검증, 경고는 없다.
플러그인의 의존성은 `@opencode-ai/plugin >=1.16.0`으로 상한 없이 열려 있어
호환되지 않는 변경이 와도 조용히 어긋난다(`package.json` 18~20줄).
다만 이 패키지는 형식만 가져오므로 실행 시 호환을 보장하는 것은 훅 이름과 이벤트 모양뿐이다.
이것은 이 문서가 코드에서 읽은 구성이며, 실제로 OpenCode가 이벤트를 바꿨는지는 확인하지 못했다.

## 비평

### 설명과 코드가 다른 부분

README의 문구와 코드를 맞춰 보면 다음이 확인되지 않았다.

- “원시 터미널 로그”: 로그를 읽는 코드가 없다. 쓰는 것은 플러그인 이벤트이다.
- “Explore, Scout 같은 여러 에이전트를 보여 준다”: 캐릭터는 OpenCode 프로세스 단위이고
  서브 에이전트는 모델링되어 있지 않다.
- “성공을 축하한다”: 성공을 따로 다루는 상태가 없다.
- 캐릭터별 반응 동작: 오류 동작은 다섯 외형 중 `person1`에만 있고
  나머지는 오류에서 아무 반응 없이 일하기로 돌아간다.
- “격리된 Chrome 창”: 별도 프로필 옵션이 없다.
- “의존성 설치가 필요 없다”: `package.json`에 의존성이 하나 선언되어 있으나
  코드가 형식만 가져오므로 실행에는 영향이 없다.
- “실시간으로 도구를 실행하고 파일을 검색한다”: 도구는 이름이 오지만
  화면은 도구 종류를 구분하지 않는다.
- 외형이 에이전트마다 저장된다는 설명: 저장은 프로젝트 폴더 단위이다.

반대로 서버를 잡은 인스턴스가 닫히면 다른 인스턴스가 이어받는다는 설명은 코드에서 확인된다.

### 인증 없는 로컬 WebSocket

서버는 `127.0.0.1:5173`에만 붙지만 토큰도 Origin 검사도 없다(`ocv-server.ts` 106~107, 125~162줄).
저장소의 `SECURITY.md`도 클라이언트를 인증하지 않는다고 적는다.
그래서 같은 컴퓨터의 어떤 프로세스나 브라우저 탭이든 소켓에 접속해
작업 경로와 전달되는 이벤트 내용을 받을 수 있고,
가짜 이벤트를 보내 캐릭터를 움직이거나 추가할 수도 있다.
서버는 `Origin` 헤더를 보지 않고 `upgrade`를 받아 주므로(107줄)
브라우저에서 열린 임의의 웹 페이지도 로컬 포트로 소켓을 열 수 있는 구조이다.
브라우저가 실제로 이를 허용하는지는 시험하지 않았다.
`index.ts`는 `event.properties`를 통째로 보낸다(169줄).
`message.updated`와 `session.diff` 속성에 어떤 내용이 들어 있는지는
플러그인 패키지를 읽지 못해 확인하지 못했다.
프런트엔드는 `register`가 보낸 외형 값을 `SKINS[skin]`으로 조회하는데
`Object.prototype`에 있는 이름도 참으로 판정된다(257줄).
`__proto__` 같은 이름이 들어오면 `SKINS[a.skinId].anims`가 비어 있어
첫 프레임 갱신에서 예외가 난다(617줄).
이 예외는 `loop`의 `requestAnimationFrame` 호출보다 앞에서 나므로(740~742줄)
화면 갱신이 멈출 것으로 읽힌다.
이는 코드 읽기에서 나온 추론이며 실행해 보지는 않았다.
화면에 그리는 문자열은 `fillText`뿐이어서 `innerHTML`로 들어가는 경로는 없다.
정적 파일은 `new URL`이 정리한 경로를 `join`해서 내주므로(109~111줄)
`..`는 URL 해석 단계에서 걸러질 것으로 보이나 시험하지 않았다.
포트 5173은 세 곳에 고정되어 있어 바꿀 수 없고, 많은 개발 서버의 기본 포트와 겹친다.

### 성숙도

테스트도 CI도 빌드 단계도 없고 TypeScript 원본을 Bun이 그대로 실행한다.
코드는 `index.ts`, `ocv-server.ts`, `index.html`, `tui.ts`를 합쳐 약 1,300줄이다.
개발자는 한 사람이고 README에는 다른 프로젝트의 이름과 데모 주석이 남아 있다.
`/visualizer` 토스트 명령(`tui.ts`)은 README에 없고 `opencode.json`에도 등록되어 있지 않다.

## 인사이트

### 가져갈 것

OpenCode를 여러 프로젝트에서 동시에 돌린다면
어느 인스턴스가 일하고 쉬는지 한눈에 보는 용도로는 이 구조가 충분하다.
이벤트 구독형 플러그인은 대화 기록 형식에 기대지 않아 형식 변경에 덜 민감하지만
도구 단위의 세밀한 활동은 보이지 않는다.
설치하기 전에 로컬 소켓에 인증이 없다는 점과 `.opencode/` 아래에 로그 파일이 생긴다는 점을
알고 있어야 한다.
로그에는 시작과 접속 기록만 남고 이벤트 내용은 남지 않는다.

### 확인할 관찰

1. 플러그인이 OpenCode의 새 버전에서도 같은 이벤트를 받는지.
2. 소켓에 인증이 더해지는지, 포트를 바꿀 수 있게 되는지.
3. 서브 에이전트나 도구 수준의 상태가 추가되는지.

위 셋 모두 이 문서가 확인하지 못했다.
