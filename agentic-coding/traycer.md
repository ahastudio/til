# Traycer: 이미 낸 구독 위에서 여러 코딩 에이전트를 한 작업 공간으로 묶는 앱

<https://traycer.ai>

<https://github.com/traycerai/traycer>

GN 토론: <https://news.hada.io/topic?id=34575>

## 소개

Traycer는 README가 에이전트 오케스트레이션을 위한 오픈소스 AI 앱이라고 소개하는 데스크톱 앱이다.
이미 내고 있는 공급자 구독을 그대로 가져와 여러 에이전트를 병렬로 돌리고, 모든 모델과 공급자에 걸친 공유 메모리로 문맥을 잃지 않게 한다는 것이 핵심 약속이다.
macOS, Linux, Windows용 설치 파일을 배포하고, 저장소는 MIT 라이선스의 TypeScript 모노레포다.
2026년 10월 1일 기준 GitHub 별 1,540개, 포크 207개이고, 같은 날 Desktop, Host, CLI 1.4.2가 함께 나왔다.

저장소는 2024년 5월에 만들어졌다.
Traycer는 원래 VS Code 확장으로 시작해, 계획을 세우고 단계별로 실행하고 검증하는 도구로 알려졌고, 문서에도 확장 사용자를 위한 별도 섹션이 남아 있다.
지금의 데스크톱 앱은 그 계획 도구를 여러 에이전트를 담는 작업 공간으로 넓힌 것이다.

README가 꼽는 기능은 다섯 가지다.

| 기능                 | README의 설명                                                      |
| -------------------- | ------------------------------------------------------------------ |
| Bring Your Own Agent | 기존 코딩 에이전트를 이중 결제 없이 연결하거나 Traycer 추론을 쓴다 |
| Unified Context      | 같은 에이전트 안에서 모델을 즉시 바꾸고 문맥을 공유한다            |
| Agent-to-Agent       | 에이전트끼리 대화하며 설계를 토론하거나 코드를 리뷰하게 한다       |
| Collaboration        | 공유 보드, 실시간 편집, 티켓 할당                                  |
| Cross-Device Sync    | 어느 기기에서든 같은 에이전트 상태를 유지한다                      |

## 구조

### Task, 에이전트, 산출물

문서의 정신 모델은 Task가 맨 위에 있는 구조다.
Task 안에서 에이전트를 만들고, Chat이나 Terminal 인터페이스로 일하며, 파일, git diff, 그리고 spec, ticket, story, review 같은 영속 산출물을 함께 다룬다.
에이전트가 일할 위치는 작업 공간 폴더, 새 worktree, 기존 worktree 중에서 고른다.

지원하는 코딩 에이전트는 21개다.
Claude Code, Codex, OpenCode, Cursor, Grok, Qwen Code, Kiro, Droid, Kimi, Copilot, Kilo Code, OpenRouter, Amp, Devin, Pi, Hermes Agent, Oh My Pi, Hugging Face, Reasonix, Antigravity, 그리고 Traycer 자체 추론이다.
모두 Chat 인터페이스로 쓸 수 있지만, Terminal 인터페이스는 Claude Code, Codex, OpenCode만 지원한다.
Claude Code와 Codex는 기본으로 켜져 있고, 나머지는 자격 증명을 확인한 뒤 켜지며, 대부분의 CLI는 Traycer가 내려받고 갱신한다.

### Host가 실제 작업을 쥔다

Host는 각 기계에서 작업 공간 폴더, 파일, 터미널, git 상태, 코딩 에이전트에 연결하는 Traycer 프로세스다.
클라우드 동기화가 Task와 기록을 기기 사이에 옮기지만, 살아 있는 작업은 시작한 Host에서 계속 돈다.
노트북과 워크스테이션에 각각 Host를 두고, 활성 Host에 닿지 않으면 다른 Host로 자동 전환했다가 원래 Host가 20초쯤 안정되면 돌아온다.
Chat 에이전트는 다른 Host로 복제할 수 있지만 원본은 남고, Terminal 에이전트와 터미널은 옮길 수 없다.

### 에이전트 사이의 세 가지 능력

에이전트는 자식 에이전트를 만들고, 다른 에이전트에게 답장을 요청하거나 일방향으로 메시지를 보내고, 다른 에이전트의 기록을 읽고, 멈추거나 포크할 수 있다.
문서는 참조, 기록 읽기, 메시지 받기가 서로 다른 능력이라고 분명히 나눈다.
참조는 같은 Task 안이면 언제나 되고, 기록은 자기 에이전트와 공유 Task의 다른 사용자 Chat 에이전트만 읽을 수 있으며, 메시지는 inbox가 있는 자기 에이전트만 받는다.

| 코딩 에이전트 | Chat 보내기 | Chat 받기 | Terminal 보내기 | Terminal 받기 |
| ------------- | ----------- | --------- | --------------- | ------------- |
| Claude Code   | 예          | 예        | 예              | 예            |
| Codex         | 예          | 예        | 예              | 아니요        |
| OpenCode      | 예          | 예        | 예              | 아니요        |
| 그 밖의 모두  | 예          | 예        | 없음            | 없음          |

그래서 Codex나 OpenCode Terminal 에이전트는 답장을 요청할 수 없고, 다른 에이전트가 그런 에이전트를 만들 수도 없다.
메시지는 받는 쪽에 inbox가 없거나, 다른 사용자의 에이전트이거나, 16MB를 넘으면 큐에 넣지 않고 거부된다.
다른 Host로 가는 메시지는 클라우드를 거쳐 전달된다.

### 권한과 판정 모델

권한 모드는 네 가지다.

| 모드              | 묻지 않고 실행하는 것                    |
| ----------------- | ---------------------------------------- |
| Supervised        | 읽기와 검색                              |
| Auto-accept edits | 읽기, 검색, 파일 편집                    |
| Auto              | 위에 더해 판정 모델(judge)이 승인한 명령 |
| Full access       | 모든 것, 검토 없음                       |

새 대화의 기본값은 Full access이고, CLI나 다른 에이전트가 만든 에이전트도 `--permission-mode`를 주지 않으면 Full access로 시작한다.
Auto 모드는 실험 기능이며, 판정 모델이 볼 수 없는 파일, 즉 git hook, CI 워크플로, `package.json`이나 `Makefile`, 에이전트 설정, `.traycer/auto-policy.md` 같은 파일 편집은 여전히 사람에게 묻는다.
저장소는 `.traycer/auto-policy.md`로 규칙을 더할 수 있지만, 제한을 더하는 Ask first와 Never allow만 적용된다.
판정 결정은 Host에 최근 200개까지 남는다.

### 사용량 한도와 자동 라우팅

Traycer는 Claude Code의 세션과 주간 한도, Codex의 한도와 수동 리셋, Cursor의 청구 주기 사용량처럼 공급자가 보고하는 한도를 읽어 상태 표시줄에 보여 준다.
자동 라우팅을 켜면 막힌 대화를 같은 공급자의 다른 계정, 다른 공급자의 동등한 모델, 리셋 대기, 알림 순서로 처리한다.
기본은 꺼져 있고, Chat 에이전트에만 적용되며, 전환하면 대화 기록에서 새 에이전트 세션을 시작해 막힌 메시지를 다시 보낸다.

## 분석

### 모델이 아니라 구독을 엮는 계층이다

Traycer가 기존 오케스트레이터와 다른 점은 무엇을 추상화하느냐다.
대부분의 멀티 에이전트 도구는 API 키를 받아 모델을 부르지만, Traycer는 Claude Code, Codex, Cursor 같은 에이전트 제품의 구독 자체를 연결 단위로 삼는다.
사용량 한도 표시, 계정 프로필, Codex 수동 리셋 버튼, 한도에 걸리면 다른 계정으로 넘어가는 라우팅은 모두 구독이라는 단위를 다루는 기능이다.

이 설계는 2026년의 가격 구조에 맞춘 것이다.
구독 요금제가 같은 토큰을 API보다 훨씬 싸게 주는 동안, 개발자는 여러 구독을 동시에 들고 한도를 돌려 가며 쓴다.
Traycer는 그 관리 작업을 제품으로 만들었고, 무료 요금제에 토큰 계량이 없다는 점은 자기 마진을 추론이 아니라 협업 기능에서 찾겠다는 선언이다.

### 같은 범주의 도구들과 갈라지는 지점

저장소의 비슷한 도구들과 비교하면 Traycer의 위치가 선명해진다.
`agentic-coding/claude-squad.md`가 다룬 Claude Squad는 tmux와 worktree로 터미널 에이전트를 나란히 돌리는 데 집중하고, `agentic-coding/herdr.md`와 `agentic-coding/paseo.md`도 에이전트 세션을 다루는 도구다.
Traycer는 여기에 세 가지를 더한다.
spec과 ticket 같은 산출물, 여러 기계에 걸친 Host, 그리고 에이전트 사이의 메시지다.

그중 산출물이 Traycer의 출신을 드러낸다.
VS Code 확장 시절의 계획, 단계, 검증 기능이 데스크톱 앱의 artifact 워크플로로 이어졌고, 에이전트 기록이 아니라 결정과 작업 항목을 영속시키는 것을 핵심으로 둔다.
여러 에이전트를 돌리는 도구는 많지만, 그 에이전트들이 무엇을 하기로 했는지를 문서로 남기는 도구는 드물다.

### 문서가 능력의 경계를 정직하게 적는다

README는 에이전트끼리 토론하고 리뷰하는 자동 루프를 약속하지만, 바로 같은 문장에서 기록 읽기와 메시지 전달은 사용자, Host, 런타임에 따라 좁아진다고 덧붙이고 능력 매트릭스로 연결한다.
문서는 참조, 기록, 메시지가 다른 능력이며 하나는 되고 다른 것은 안 되는 상태가 오류가 아니라 정상이라고 쓴다.

이 정직함은 구조에서 나온다.
Traycer는 21개 에이전트의 CLI를 감싸므로, 각 CLI가 외부에서 메시지를 받을 통로가 있느냐에 능력이 달려 있다.
Terminal 인터페이스에서 inbox를 가진 것이 Claude Code뿐이라는 사실은, 오케스트레이터의 능력이 결국 감싸는 대상의 확장점을 넘지 못한다는 것을 보여 준다.

## 비평

### 통합 문맥이라는 말은 기능보다 크다

README는 같은 에이전트 안에서 모델을 즉시 바꾸고, 문맥 창이 모든 공급자에 걸쳐 매끄럽게 공유된다고 쓴다.
그런데 사용량 한도와 라우팅 문서는 계정이나 모델을 바꾸면 대화 기록에서 새 에이전트 세션을 시작하고 막힌 메시지를 다시 보낸다고 설명한다.
문맥이 공유된다기보다, 대화 기록이 새 세션에 다시 주입되는 것이다.

이 차이는 작지 않다.
Claude Code와 Codex는 각자 도구 호출 형식, 시스템 프롬프트, 프롬프트 캐시를 가진다.
한쪽의 기록을 다른 쪽에 넣으면 캐시는 처음부터 다시 쌓이고, 도구 결과의 형식이 달라 모델이 앞선 작업을 다르게 해석할 수 있다.
문서가 라우팅을 설명하며 쓴 새 세션에서 다시 실행된다는 말이 정확하고, README의 매끄럽게 공유된다는 말은 그 정확함을 덮는다.

### 기본값이 Full access인 오케스트레이터

권한 설정의 기본값은 Full access이고, CLI나 다른 에이전트가 만든 에이전트도 따로 지정하지 않으면 Full access로 시작한다.
Auto 모드는 실험 기능이고, 가장 안전한 Supervised는 모든 명령과 편집을 묻는다.
에이전트가 에이전트를 만들고 메시지를 주고받게 하는 도구에서, 자식 에이전트의 기본 권한이 검토 없음이라는 것은 위험의 증폭기다.

한 에이전트가 읽은 웹 페이지나 이슈에 숨은 지시가 있으면, 그 에이전트는 Full access 자식 에이전트를 만들어 일을 맡길 수 있다.
판정 모델이 볼 수 없는 파일을 막는 Auto 모드의 규칙은 잘 설계되어 있지만, 기본값이 아니라면 대부분의 사용자는 그 보호를 받지 못한다.
문서는 기본값의 이유를 설명하지 않는다.

### 무료와 오픈소스 뒤에 남는 의존

Traycer는 MIT 라이선스이고 무료 요금제에 토큰 계량이 없다.
하지만 여러 기계에 걸친 Task 동기화, 다른 Host로의 메시지 전달, 공유와 팀 기능은 Traycer의 클라우드를 거친다.
Auto 모드 판정 모델의 기본값도 Traycer의 호스팅 모델이며 크레딧을 쓴다.

즉 오픈소스는 클라이언트와 Host의 코드이고, 이 도구를 오케스트레이터로 만드는 연결 계층은 서비스다.
README의 개인정보 설명도 Privacy Mode가 개인에게는 직접 켜야 하는 선택이고, 끄면 프롬프트가 기록될 수 있다고 적는다.
자기 구독을 가져온다는 약속은 모델 비용을 이중으로 내지 않는다는 뜻이지, 작업 문맥이 자기 기계에만 머문다는 뜻은 아니다.

## 인사이트

### 오케스트레이터의 상한은 감싸는 CLI의 확장점이 정한다

Traycer의 능력 매트릭스는 이 범주의 도구들이 부딪칠 구조적 한계를 보여 준다.
에이전트 사이 메시지는 받는 쪽 CLI가 외부 입력 통로를 열어 줄 때만 가능하고, 실행 중 조종(steer mid-turn)도, 권한 모드도, 사용량 보고도 각 CLI가 무엇을 노출하느냐에 달려 있다.
21개를 지원한다는 숫자보다, 그중 몇 개가 모든 능력을 다 쓰느냐가 실제 가치다.

이는 초기 데스크톱 통합 환경이 겪은 일과 비슷하다.
여러 도구를 한 창에 모은 IDE는 결국 언어 서버 프로토콜 같은 공통 확장점이 생기고서야 각 언어를 깊이 지원할 수 있었다.
에이전트 오케스트레이터도 비슷한 공통 프로토콜, 예를 들어 에이전트 inbox나 세션 이식의 표준이 생기기 전까지는 가장 잘 열린 한두 CLI 중심으로 기울 것이다.
지금 Claude Code가 모든 칸을 채운 유일한 에이전트라는 사실이 그 기울기를 보여 준다.

### 구독을 돌려 쓰는 기능은 공급자 정책 하나로 사라질 수 있다

Traycer의 라우팅은 한 계정이 한도에 걸리면 같은 공급자의 다른 계정으로 넘어간다.
이 기능의 가치는 구독 요금제가 API보다 싸다는 가격 차이에서 나온다.
그 차이는 공급자가 정한 것이고, 공급자는 이를 다시 정할 수 있다.

구독을 제3자 도구에서 쓰는 것을 공급자가 제한한 사례는 이미 있었다(`claude/third-party-subscription-block.md`).
여러 계정을 돌려 쓰는 패턴은 공급자 입장에서 한도 우회로 보일 수 있고, 약관이 바뀌거나 CLI 인증 방식이 바뀌면 이 계층 전체가 흔들린다.
Traycer가 자체 추론 크레딧을 함께 파는 것은 그 위험에 대한 보험으로 읽힌다.
구독 위의 오케스트레이터는 기술 위험보다 정책 위험이 더 크다.

### 산출물이 에이전트 기록보다 오래 산다

Traycer가 spec, ticket, review를 영속 산출물로 두는 설계는 멀티 에이전트 작업의 진짜 병목을 짚는다.
에이전트 여럿이 병렬로 일하면 기록은 빠르게 늘어나고, 사람이 그 기록을 다 읽을 수 없다.
남아야 하는 것은 대화가 아니라 결정이다.

이는 소프트웨어 팀이 회의록 대신 설계 문서와 티켓을 남기는 이유와 같다.
에이전트의 모델이 바뀌고, 세션이 새로 시작되고, 다른 공급자로 라우팅되더라도, 산출물은 다음 에이전트에게 넘겨줄 수 있는 유일하게 안정된 문맥이다.
그렇게 보면 README가 강조한 통합 문맥보다, 문서가 조용히 설명하는 artifact 워크플로가 이 도구의 더 오래갈 기여일 수 있다.
