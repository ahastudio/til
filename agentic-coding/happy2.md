# Happy (2): 사람과 코딩 에이전트가 함께 쓰는 자체 호스팅 슬랙

<https://happy.engineering/happy2/>

<https://github.com/slopus/happy2>

## 소개

Happy를 만든 팀(slopus)이 내놓은 다음 세대 제품이다.
저장소 한 줄 소개는 “사람과 코딩 에이전트가 함께 만들어 가는, 자체 호스팅
슬랙 같은 작업 공간”이고, GitHub 조직 목록의 설명은 더 직설적이다.
**“에이전트가 먼저 있었다면 슬랙은 어떤 모습이었을까?”**

전작과의 관계를 README가 명시한다.
[Happy](happy.md)의 성공에 이어, 코딩 에이전트를 실제 일상 업무에 들여오면서
배운 것을 바탕으로 바닥부터 새로 쓴 다음 장(next chapter)이라는 것이다.
대화, 파일, 작업 공간, 코딩 에이전트를 하나의 웹·데스크톱 앱에 모은다.

문제 정의가 분명하다.
지금 작업이 채팅 창과 터미널과 파일 브라우저와 일회성 대시보드로 흩어져 있는데,
팀과 코딩 에이전트에게 공유된 집을 주겠다는 것이다.

2026년 7월 11일에 만들어진 저장소이고 MIT 라이선스다.
8월 초 기준 스타 34개, 열린 이슈 5개로 아직 초기 단계다.
전작 `slopus/happy`가 스타 2만 3천 개, 이슈 940개인 것과 대비된다.

`happy.engineering/happy2/`는 읽을거리가 아니라 이 데스크톱 앱을 여는 진입점이며,
로컬 인스턴스에 연결되지 않으면 “CONNECTION NEEDED”만 표시된다.

## 사용법

Node.js 24 이상이 필요하고, 명령 하나로 전체 앱이 뜬다.

```sh
npx happy2
```

`http://127.0.0.1:3000`을 열면 된다.
데이터베이스, 파일, 생성된 시크릿, 에이전트 작업 공간, 비공개 Rig 런타임이
실행한 디렉터리 아래 `.happy2`에 저장된다.

운영체제 서비스를 설치하지 않고 백그라운드로 돌리는 방법과, 재부팅 후에도
유지되게 하는 방법이 나뉘어 있다.

```sh
npx happy2 daemon start     # 데몬. .happy2에 pid와 로그 저장
npx happy2 daemon stop

npx happy2 service start    # 재부팅 후에도 유지
npx happy2 service stop
```

`service` 쪽 처리가 세심하다.
macOS에서는 `sudo` 없이 사용자별 LaunchAgent를 설치해 로그인 시 시작한다.
Linux에서는 `./happy2.service` 파일을 쓰고 출력한 뒤, 시스템 전역 systemd 유닛으로
설치·시작하는 `sudo` 명령을 **보여주기만** 한다. 직접 `sudo`를 실행하지 않는다.
`service stop`도 마찬가지로 제거 명령을 출력만 한다.
생성된 파일은 현재 디렉터리에 남아 검토하거나 다시 설치할 수 있다.

`npx`로 시작한 경우 생성되는 서비스가 `npx --yes happy2`를 실행하도록 되어 있다.
축출될 수 있는 `_npx` 캐시 경로에 의존하지 않기 위해서다.

## 설정

설정 우선순위가 명확히 정의돼 있다.

1. `--config /path/to/happy2.toml`
2. `HAPPY2_CONFIG=/path/to/happy2.toml`
3. `./.happy2/happy2.toml` (존재할 때)
4. 내장 기본값

TOML은 부분 설정이다. 준 필드만 내장 기본값 위에 재귀적으로 병합되므로, 공개
리스너를 여는 데는 이 정도면 된다.

```toml
[server]
host = "0.0.0.0"
```

경로 해석 규칙에 함정이 하나 있고 README가 이를 명시한다.
데이터베이스·파일·플러그인·키·에이전트의 상대 경로가 **TOML 파일이 있는
디렉터리가 아니라 Happy (2)를 시작한 작업 디렉터리** 기준으로 해석된다.

서버 역할은 세 가지로 나뉜다.

| `role` | 의미                       |
| ------ | -------------------------- |
| `all`  | 인증 + 제품 API            |
| `auth` | 인증만                     |
| `api`  | 검증만                     |

파일 처리 설정에는 서명 URL 만료(기본 300초), 최대 업로드 크기(512MB), 재개 가능
청크 크기(8MB), 사용자별·서버 전체 할당량(0이면 비활성), 미완료 업로드 만료,
격리 보관 기간이 있다.
악성코드 검사기를 외부 명령으로 붙일 수 있고, 검사 실패 시 동작을 `deny`와
`allow` 중에 고를 수 있다. 기본값은 `deny`다.

## 아키텍처

제품 경계를 명시적으로 나눈 것이 이 프로젝트의 특징이다.

| 패키지          | 역할                                                       |
| --------------- | ---------------------------------------------------------- |
| `happy2-server` | 인증, 영속성, 파일, 협업, 에이전트 실행                    |
| `happy2-state`  | 인증된 HTTP·실시간 전송을 불변 서피스 스토어로 변환        |
| `happy2-ui`     | 재사용 가능한 디자인 시스템과 크로스 브라우저 커버리지     |
| `happy2-app`    | 웹과 Electron 양쪽을 위한 상태·UI 조합                     |
| `happy2-web`    | 브라우저 진입점과 프로덕션 웹 빌드                         |
| `happy2-desktop`| macOS Electron 앱                                          |
| `happy2-gym`    | 격리된 블랙박스 서버·상태·브라우저 테스트 환경             |

같은 React 애플리케이션이 브라우저와 Electron에서 함께 돈다.
작은 Fastify 서버가 인증, 지속적 협업 상태, 파일, 실시간 업데이트, 에이전트
실행을 제공한다.
서버와 웹 앱 전체가 `happy2` 패키지 하나로 묶여 배포된다.

데스크톱 앱에는 시작 모드가 둘 있다.
이 컴퓨터에서 도는 **비공개 Rig 관리형 Happy 서버**를 쓰거나, 기존 클라우드 Happy
인스턴스에 붙는 **얇은 HTTPS 클라이언트**로 동작하는 것이다.
자식 프로세스를 감독하고, 자격 증명을 암호화된 Keychain에 보관하며, 서명된 GitHub
Releases로 업데이트를 배포한다.

에이전트 실행 기반은 같은 팀의 [Rig](https://github.com/slopus/rig)다.
Pi 위에 만든 오픈소스 코딩 에이전트 하네스로, Pi·Codex·Claude Code·Kimi Code·Grok
Build의 장점을 하나로 모으는 것을 표방한다.
자체 계정이나 구독을 추가하지 않고, 제공자 접근을 모아 되팔지 않으며, 제공자의
약관과 한도를 그대로 둔다고 명시한다.

## 분석

### 제품 범주가 바뀌었지 개선된 것이 아니다

이름이 “Happy 2”라서 후속 버전으로 읽히지만, 두 제품이 푸는 문제는 다르다.

[Happy 1](happy.md)은 원격 제어 도구다.
자기 컴퓨터에서 도는 Claude Code나 Codex를 휴대폰과 웹에서 조종하는 것이고,
핵심 가치는 “자리를 비워도 에이전트가 멈추지 않는다”였다.
홈페이지 문구도 “Leave your desk. Keep your agents moving.”다.

Happy 2는 작업 공간이다.
대화, 스레드, 파일, 승인, 에이전트 활동이 한곳에 모인다.
슬랙과 비교되는 것에서 알 수 있듯 대상이 개인이 아니라 팀이다.

이 차이가 기술 스택 선택에도 그대로 나타난다.
Happy 1은 Expo 기반 모바일 앱이 중심이고 종단간 암호화가 핵심 설계 제약이었다.
Happy 2는 웹과 Electron이 중심이고 자체 호스팅이 핵심 제약이다.
모바일이 목록에서 빠졌고, E2EE도 전면에 없다.

즉 “2”는 버전 번호가 아니라 새 제품 계열의 이름에 가깝다.
그리고 전작이 스타 2만 3천 개를 모은 상태에서 새 제품을 같은 브랜드로 내는 것은
그 인지도를 옮겨오려는 선택이다.

### 자체 호스팅이 E2EE를 대체했다

두 제품의 신뢰 모델을 비교하면 흥미로운 교체가 보인다.

Happy 1의 약속은 종단간 암호화였다.
백엔드는 불투명한 암호문만 저장하고 중계하며, 키를 받지 않으므로 프롬프트도
응답도 코드도 세션 맥락도 복호화할 수 없다는 것이다.
서버를 운영하는 회사를 신뢰하지 않아도 되게 만드는 설계다.

Happy 2는 다른 방식으로 같은 문제를 푼다. 서버 자체를 사용자가 돌린다.
데이터베이스, 파일, 시크릿, 에이전트 작업 공간, Rig 런타임이 전부 `.happy2` 아래
로컬에 있다.
신뢰해야 할 제3자가 아예 없으므로 암호화로 보호할 대상도 없어진다.

이 교체가 자연스러운 이유는 제품 성격 때문이다.
휴대폰에서 데스크톱 세션을 보려면 둘 사이에 중계 서버가 반드시 있어야 하고, 그
서버를 신뢰하지 않으려면 E2EE가 필요했다.
팀이 자기 서버 하나에 모이는 구조에서는 중계가 필요 없다.

다만 이 교체에는 대가가 있다. 아무나 쓸 수 없게 된다는 것이다.
Happy 1은 앱을 받고 `npm install -g happy`만 하면 됐다. Happy 2는 누군가 서버를
띄우고 유지해야 한다.
`npx happy2` 한 줄로 시작되게 만든 것, 데몬과 서비스 설치를 CLI에 넣은 것은 그
문턱을 낮추려는 노력이다.

### 스스로를 채택해 진화한다는 개발 방식

README가 “adopting itself”라는 표현을 두 번 쓴다.
자체 서버, 상태 계층, 컴포넌트 워크벤치, 브라우저 테스트, 코딩 에이전트 워크플로가
제품 개발 루프의 일부라는 것이다.

`happy2-gym`이라는 별도 패키지가 이 주장의 실물이다.
격리된 블랙박스 환경에서 서버와 상태와 브라우저를 테스트하는 전용 패키지를
따로 뒀다.
`happy2-ui`에 컴포넌트 워크벤치와 크로스 브라우저 시각 커버리지가 포함된 것도
같은 맥락이다.

이 구조가 중요한 이유는 앞서 [Karpathy의 펠리컨](../ai/karpathy-pelican.md)에서
나온 문제 — 에이전트가 자기 결과물을 검수하지 못한다 — 와 직접 관련되기 때문이다.
에이전트가 이 제품을 개발하게 하려면 에이전트가 결과를 확인할 수 있어야 하고,
그러려면 블랙박스 테스트 환경과 시각 회귀 검사가 제품 안에 있어야 한다.
`happy2-gym`은 사람을 위한 테스트 도구가 아니라 에이전트를 위한 관찰 층으로
읽는 편이 정확하다.

패키지 경계를 네 층으로 명시적으로 나눈 것도 같은 목적에 봉사한다.
서버, 상태, UI, 조합이 분리돼 있으면 에이전트에게 한 층만 맡길 수 있고, 변경의
영향 범위가 좁아진다.
사람 협업을 위한 모듈화와 에이전트 작업을 위한 모듈화가 같은 방향을 가리키는
사례다.

## 비평

### 슬랙 비유가 이 제품의 가장 큰 위험을 감춘다

“에이전트가 먼저 있었다면 슬랙은 어떤 모습이었을까”는 좋은 질문이고 마케팅
문구로도 강력하다.
그런데 이 비유를 진지하게 받으면 곧바로 불편한 사실이 따라온다. 슬랙은 팀 협업
도구 중에서도 **가장 대체하기 어려운** 범주에 속한다.

이유는 기능이 아니라 네트워크 효과다.
채팅 도구의 가치는 그 안에 누가 있느냐에서 나오고, 팀 전체가 동시에 옮기지 않으면
쓸모가 없다.
Slack을 대체하려던 시도들 — Mattermost, Rocket.Chat, Zulip — 은 기능적으로 충분했고
자체 호스팅도 됐지만 대부분 특수한 요구(보안 규정, 비용)가 있는 조직에만 안착했다.

Happy 2는 여기에 더 어려운 조건을 얹는다.
자체 호스팅이라 누군가 서버를 운영해야 하고, 대화만이 아니라 파일과 작업 공간과
에이전트 실행까지 옮겨야 하며, 팀 전체가 동시에 이동해야 한다.
전환 비용이 Slack 대체보다 크고, 그 대가로 얻는 것은 “에이전트가 같은 공간에
있다”는 것 하나다.

README는 이 문제를 다루지 않는다.
“흩어진 도구 더미 대신 공유된 집”이라는 서술은 통합의 이점만 말하고, 통합을
달성하기까지 넘어야 할 조직적 문턱은 언급하지 않는다.
슬랙과 비교되기를 선택한 순간 슬랙이 가진 해자도 함께 상대해야 하는데, 그 계산이
보이지 않는다.

### 자체 호스팅을 표방하면서 운영 부담을 과소평가한다

`npx happy2` 한 줄로 시작된다는 것은 인상적인 온보딩이다.
그런데 README의 설정 절을 읽어 보면 이것이 개인 실험용 기본값이라는 것이 드러난다.

기본 host는 `127.0.0.1`이고 데이터베이스는 로컬 SQLite 파일이다.
팀이 쓰려면 `host` 값을 `0.0.0.0`으로 열어야 하는데, README는 그 한 줄만 보여주고
그다음에 필요한 것들 — TLS, 인증 경계, 백업, 업그레이드 — 은 서버 문서로 넘긴다.

특히 눈에 띄는 것은 `trusted_proxy_hops` 설정이다.
Happy (2) 바깥의 신뢰할 수 있는 프록시 수이며 직접 연결이면 0을 유지하라고 되어
있다.
이 설정이 있다는 것은 리버스 프록시 뒤에 두는 것이 정상 배포라는 뜻이고, 그렇다면
`npx happy2`와 실제 팀 배포 사이의 거리가 상당하다는 뜻이기도 하다.

악성코드 검사 설정도 같은 성격이다.
외부 검사기 명령을 붙일 수 있고 실패 시 `deny`가 기본이지만, 검사기를 설정하지
않으면 어떻게 되는지는 명시되지 않는다.
팀이 파일을 올리는 공유 공간을 자체 호스팅한다는 것은 이런 결정을 전부 운영자가
지게 된다는 의미다.

문제는 이 부담을 질 사람이 누구인가다.
자체 호스팅의 이점은 데이터 통제인데, 그것을 가장 원하는 조직은 대체로 전담
인프라 인력이 있는 곳이다.
그런 조직은 `npx` 한 줄로 시작하지 않고, `npx` 한 줄에 매력을 느끼는 개인은 팀
서버를 운영하지 않는다.
온보딩의 간편함과 실제 목표 사용자가 어긋나 있다.

### 전작의 미해결 부채를 안고 새 제품을 시작했다

숫자를 나란히 놓으면 불편한 그림이 나온다.

`slopus/happy`는 스타 2만 3천 개에 **열린 이슈가 940개**다.
2025년 7월에 시작해 1년 남짓 된 프로젝트에서 이 정도 이슈가 쌓였다는 것은 사용자가
많고 문제도 많다는 뜻이다.
그 상태에서 같은 팀이 2026년 7월에 새 저장소를 만들어 바닥부터 다시 쓰기 시작했다.

README는 이를 “실제 일상 업무에 코딩 에이전트를 들여오며 배운 것을 바탕으로 한
바닥부터의 다음 장”이라고 설명한다.
배움을 반영하려면 새로 써야 했다는 논리인데, 이 논리는 검증하기 어렵고 소프트웨어
역사에서 반복적으로 문제가 됐던 선택이기도 하다.

더 구체적인 신호가 조직 저장소 목록에 있다.
`happy-cli`(스타 558)와 `happy-server`(스타 367)의 마지막 푸시가 2026년 2월 14일에
멈춰 있다. 반년 가까이 손이 닿지 않았다.
같은 기간에 `happy2`, `rig`, `murmur`는 8월 3일까지 활발하다.
본체 `happy`는 8월 1일에 푸시됐지만, CLI와 서버 컴포넌트가 정지한 상태에서
본체만 움직이는 것이 무엇을 의미하는지는 분명하지 않다.

사용자 입장에서 판단해야 할 것은 명확하다.
2만 3천 스타짜리 도구를 쓰고 있는데 만든 팀이 다른 제품에 자원을 옮기고 있다면,
그 도구의 유지보수가 어떻게 될 것인가.
Happy 2 README는 전작과의 관계를 “다음 장”이라고만 표현하고, 전작이 어떻게 되는지에
대해서는 한 줄도 쓰지 않는다.

### 한 팀이 동시에 네 개의 야심찬 제품을 만들고 있다

조직 저장소 목록을 보면 최근 활동이 여러 갈래로 뻗어 있다.

`happy2`(자체 호스팅 협업 공간), `rig`(코딩 에이전트 하네스, Pi·Codex·Claude
Code·Kimi Code·Grok Build 통합), `murmur`(에이전트와 사람을 위한 P2P 암호화
메시징), `happy`(기존 원격 제어 클라이언트)가 전부 8월 초에 푸시됐다.
팀 소개 페이지에 이름이 올라온 사람은 세 명이다.

각각이 독립적으로도 충분히 큰 프로젝트다.
Rig 하나만 봐도 다섯 개 코딩 에이전트의 모델 네이티브 프롬프트와 도구를 통합
하네스에서 재현하겠다는 것이고, 각 제공자가 계속 바뀌는 상황에서 유지보수 부담이
크다.

그리고 이 제품들이 서로 의존한다.
Happy 2의 에이전트 실행 기반이 Rig이고, 데스크톱 앱은 “비공개 Rig 관리형 서버”를
띄운다.
Rig가 흔들리면 Happy 2도 흔들리는 구조인데, Rig 자체가 아직 스타 10개인 초기
프로젝트다.

세 명이 네 개의 제품을 만들면서 그중 하나는 2만 3천 스타에 940개 이슈를 안고
있다는 조합은, 어느 것도 충분한 손을 받지 못할 위험을 시사한다.
Happy 2를 도입 검토하는 입장에서 이건 기능 목록보다 중요한 정보인데, README에는
당연히 나오지 않는다.

## 인사이트

### 에이전트 협업 도구의 진짜 설계 문제는 승인 흐름이다

Happy 2가 나열한 것들 — 대화, 스레드, 파일, **승인(approvals)**, 에이전트 활동 —
중에서 기존 협업 도구에 없던 항목은 승인 하나다.
나머지는 슬랙에 다 있다.

승인이 왜 새로운 문제인지 보려면 에이전트 작업의 성질을 봐야 한다.
사람 사이의 협업에서 승인은 비동기적이고 지연에 관대하다. PR 리뷰가 하루 늦어도
대체로 괜찮다.
에이전트는 다르다. Happy 1 홈페이지가 정확히 이 문제를 문제 정의로 삼았다.
한 시간 걸릴 작업이 5분 만에 권한이나 질문이나 오류로 멈춘다는 것이다.

즉 에이전트 협업 도구에서 승인은 알림 기능이 아니라 **처리량을 결정하는 병목**이다.
승인 대기 시간이 실제 작업 시간보다 길어지는 것이 기본 상태이고, 그 비율을 줄이는
것이 이 범주 제품의 핵심 가치가 된다.

여기서 설계 문제가 갈라진다.
승인을 빠르게 만들려면 사람이 적게 보고 빠르게 판단해야 하는데, 그러면 승인이
형식화된다.
반대로 제대로 검토하게 하면 병목이 유지된다.
[TokenPhage](../ai-tool/tokenphage.md)에서 다룬 증거 과잉 문제와 같은 구조다.
검토 대상의 양이 임계를 넘으면 검토 자체가 의례가 된다.

Happy 2 README는 승인을 목록의 한 항목으로만 언급하고 이 긴장을 다루지 않는다.
그런데 슬랙과 다른 것을 만들겠다면 결국 승부는 이 지점에서 난다.
대화와 파일은 이미 잘 풀린 문제이고, 여러 에이전트의 승인 요청을 사람 한 명이
감당 가능한 형태로 배열하는 것은 아무도 풀지 않은 문제다.

### 자체 호스팅은 프라이버시 요구가 아니라 에이전트 실행 요구에서 온다

Happy 2가 자체 호스팅인 이유를 프라이버시로 읽기 쉽다. 실제로 README도 “데이터베이스,
파일, 시크릿, 에이전트 작업 공간, Rig 런타임을 당신의 통제 아래 둔다”고 쓴다.

그런데 목록의 마지막 두 항목이 다른 이야기를 한다.
에이전트 작업 공간과 Rig 런타임은 프라이버시 대상이 아니라 **실행 환경**이다.
코딩 에이전트가 실제로 일하려면 코드가 있는 파일 시스템과 실행 가능한 셸과
설치된 도구 체인이 필요하고, 그것들은 개발자의 기계에 있다.

이 제약이 클라우드 SaaS 형태를 원천적으로 어렵게 만든다.
슬랙은 클라우드에서 돌아도 된다. 메시지만 다루기 때문이다.
에이전트가 코드를 고치고 테스트를 돌려야 한다면 그 실행은 코드가 있는 곳에서
일어나야 하고, 그러면 제품이 사용자 기계 쪽으로 끌려온다.

이 관점에서 보면 Happy 1과 Happy 2가 같은 제약의 다른 해법이다.
Happy 1은 실행을 사용자 기계에 두고 UI만 원격으로 뺐다. 그래서 중계 서버가 필요했고
E2EE가 붙었다.
Happy 2는 UI까지 사용자 쪽으로 가져왔다. 그래서 중계가 사라졌고 자체 호스팅이 됐다.

여기서 예측되는 것이 있다.
에이전트 협업 도구 범주 전체가 클라우드 SaaS로 수렴하지 않고 자체 호스팅이나
하이브리드로 갈라질 가능성이 크다는 것이다.
실행 위치가 아키텍처를 결정하고, 실행은 코드 옆에서 일어나기 때문이다.
클라우드 개발 환경이 이 제약을 푸는 대안이지만, 그건 개발 환경 전체를 옮기는
훨씬 큰 결정이다.
그래서 이 범주에서는 SaaS의 배포 편의성이라는 통상적 우위가 작동하지 않고,
경쟁 축이 다른 곳으로 옮겨간다.

### 브랜드 재사용은 인지도를 옮기는 동시에 신뢰를 담보로 잡는다

전작이 2만 3천 스타를 모은 상태에서 새 제품에 “Happy (2)”라는 이름을 붙인 것은
분명한 선택이다.
새 이름으로 시작하면 처음부터 알려야 하고, 기존 이름을 쓰면 관심이 따라온다.

실제로 효과가 있다. 홈페이지 내비게이션에 “Happy (2) NEW”가 걸려 있고, 전작을
쓰던 사람들이 자연스럽게 들여다보게 된다.
스타 34개짜리 신생 저장소가 얻기 어려운 종류의 노출이다.

대가는 기대의 이전이다.
“Happy 2”라는 이름은 Happy 1을 쓰던 사람에게 “내가 쓰던 것의 개선판”이라는 신호를
보낸다.
실제로는 제품 범주가 다르고, 모바일이 빠졌고, E2EE가 전면에서 내려갔고, 자체 서버
운영이 필요하다.
이름이 약속한 연속성과 실물의 불연속이 어긋나면 그 실망은 전작의 평판에도 얹힌다.

역사적 사례가 여럿이다.
Netscape 4에서 6으로 넘어가며 코드베이스를 새로 쓴 것, Perl 6이 다른 언어가 되면서
결국 Raku로 개명한 것, Angular 1에서 2로 넘어가며 호환성을 버린 것.
공통점은 버전 번호가 연속성을 약속했는데 실물이 그렇지 않았고, 그 간극이 기존
사용자의 이탈로 이어졌다는 점이다.
Perl 6은 결국 이름을 바꿔서야 그 부채를 정리했다.

Happy 2에서 특히 위험한 것은 두 제품이 동시에 유지된다는 점이다.
Perl 5와 6이 그랬듯 같은 이름을 공유하는 두 제품이 병존하면 사용자는 어느 것을
쓸지 매번 판단해야 하고, 커뮤니티와 문서와 이슈가 분산된다.
`happy-cli`와 `happy-server`가 반년째 멈춰 있는 상황은 그 분산이 이미 시작됐음을
시사한다.
이름을 재사용해 얻은 초기 관심의 대가를, 전작 사용자들이 유지보수 불확실성으로
치르고 있는 셈이다.

### 자기 자신으로 개발하는 구조는 검증 도구를 제품에 편입시킨다

“스스로를 채택해 진화한다”는 서술과 `happy2-gym`이라는 전용 테스트 패키지의 조합은
이 프로젝트에서 가장 앞서 있는 부분일 수 있다.

에이전트에게 개발을 맡기려는 프로젝트가 마주하는 문제는 일관되다.
에이전트가 코드를 쓸 수는 있는데 그것이 실제로 동작하는지 확인시킬 방법이 없다는
것이다.
[agent-device](../ai-tool/agent-device.md)가 모바일 앱에서, Karpathy의 실험이 3D
렌더링에서 부딪힌 것과 같은 벽이다.

Happy 2의 접근은 그 확인 층을 제품 패키지의 하나로 만든 것이다.
`happy2-gym`은 격리된 블랙박스 환경에서 서버와 상태와 브라우저를 함께 검증하고,
`happy2-ui`는 컴포넌트 워크벤치와 크로스 브라우저 시각 커버리지를 갖는다.
사람이 쓰기 위한 테스트 인프라와 에이전트가 쓰기 위한 관찰 인프라가 같은 것이라는
판단이 깔려 있다.

이 판단이 맞다면 함의가 크다.
지금까지 테스트는 제품의 부속물이었고, 커버리지는 품질 지표였다.
에이전트가 주된 작성자가 되면 테스트는 부속물이 아니라 **에이전트의 감각 기관**이
되고, 커버리지는 품질 지표가 아니라 에이전트가 얼마나 자율적으로 일할 수 있는지의
상한이 된다.
테스트가 없는 영역은 에이전트가 눈을 감고 작업하는 영역이다.

그러면 아키텍처 판단 기준도 바뀐다.
“이 모듈을 어떻게 나눌 것인가”에 “에이전트가 이 경계에서 결과를 관찰할 수 있는가”가
추가된다.
Happy 2가 서버·상태·UI·조합을 네 층으로 명시적으로 분리하고 각각에 검증 수단을
붙인 것은 이 기준을 따른 결과로 읽힌다.

다만 이 구조가 실제로 작동하는지는 아직 알 수 없다.
스타 34개, 이슈 5개인 저장소에서 “스스로를 채택해 진화한다”는 것은 검증된 방법론이
아니라 선언이다.
이 주장이 확인되려면 이 프로젝트가 상당한 규모로 자라면서도 세 명이 유지할 수
있음을 보여야 하고, 그건 앞서 지적한 자원 분산 문제와 정면으로 부딪힌다.
