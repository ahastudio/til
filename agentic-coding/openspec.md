# OpenSpec: 코딩 에이전트와 구현 전에 명세를 맞추는 프레임워크

<https://openspec.dev/>

<https://github.com/Fission-AI/OpenSpec>

HN 토론: <https://news.ycombinator.com/item?id=49734264> (200점, 99개 댓글)

GN 토론: <https://news.hada.io/topic?id=33841>

## 소개

소프트웨어 명세를 만들고 관리하는 가볍고 설정 가능한 프레임워크다.
만들고 싶은 것을 명세에 담아 두고, 작업이 진행되는 동안 팀과 코딩 에이전트를 같은 곳에 맞춰 둔다는 것이 내세우는 목표다.
요구사항을 다듬고, 그것이 옳은 것을 서술하는지 검증하고, 구현이 그것과 맞는지 확인하는 세 가지를 돕는다고 밝힌다.
한 문장으로는 옳은 것을 만들고 그것을 옳게 만들도록 돕는다고 정리한다.

철학은 다섯 줄로 제시된다.

```text
→ 경직되지 않고 유연하게
→ 폭포수가 아니라 반복적으로
→ 복잡하지 않고 쉽게
→ 신규 프로젝트만이 아니라 기존 코드베이스를 위해
→ 개인 프로젝트에서 엔터프라이즈까지 확장되도록
```

네 번째 항목이 이 프로젝트의 위치를 정한다.
명세 기반 개발 도구 대부분이 빈 저장소에서 시작하는 것을 전제하는데, 여기서는 이미 있는 코드베이스를 명시적으로 대상에 넣었다.

GitHub 스타 68.0k개, 월 265,000명 이상의 개발자가 쓰며 2초마다 새 명세가 하나씩 만들어진다고 밝힌다.
MIT 라이선스이고 npm에 올라온 최신 버전은 v1.13.1이다.

## 워크플로

다섯 개의 슬래시 명령이 전부이고, 각각이 작업의 한 단계에 대응한다.

| 명령            | 하는 일                                     |
| --------------- | ------------------------------------------- |
| `/opsx:explore` | 문제를 파악하고 코드베이스를 이해한다       |
| `/opsx:propose` | 제안서, 명세, 설계 문서, 작업 목록을 만든다 |
| `/opsx:apply`   | 명세에 적힌 작업을 구현한다                 |
| `/opsx:verify`  | 구현이 명세와 맞는지 확인한다               |
| `/opsx:archive` | 완료된 변경을 보관한다                      |

README의 예시가 이 흐름을 그대로 보여 준다.

```text
You: /opsx:explore
AI:  무엇을 살펴볼까요?
You: 다크 모드를 넣고 싶은데 어떻게 깔끔하게 할지 모르겠어요.
AI:  스타일 설정을 보겠습니다...
     가장 깔끔한 경로는 CSS 변수와 작은 테마 컨텍스트,
     그리고 시스템 설정 감지입니다. 새 의존성은 없습니다. 범위를 잡을까요?
You: 네, 그렇게 하죠.

You: /opsx:propose add-dark-mode
AI:  openspec/changes/add-dark-mode/ 를 만들었습니다
     ✓ proposal.md — 왜 하는지, 무엇이 바뀌는지
     ✓ specs/       — 요구사항과 시나리오
     ✓ design.md    — 기술적 접근
     ✓ tasks.md     — 구현 체크리스트

You: /opsx:apply
AI:  작업을 구현합니다...
     ✓ 1.1 테마 컨텍스트 제공자 추가
     ✓ 1.2 토글 컴포넌트 생성
     ✓ 2.1 CSS 변수 추가
     ✓ 2.2 localStorage 연결

You: /opsx:archive
AI:  openspec/changes/archive/2025-01-23-add-dark-mode/ 로 보관했습니다
```

`/opsx:explore`가 먼저 있다는 점이 설계 의도를 드러낸다.
무엇을 만들지 정하지 않은 상태를 별도 단계로 두었고, 그 단계에서는 코드를 쓰지 않는다.

## 명세의 모양

배울 문법이 없다는 것이 이 프로젝트의 주장이다.
명세는 평범한 마크다운이며, 요구사항과 구체적인 시나리오로 이루어진다.

```markdown
## ADDED Requirements

### Requirement: Theme selection
The app SHALL let users switch between light and dark themes,
defaulting to the system preference.

#### Scenario: User toggles dark mode
- **WHEN** the user clicks the theme toggle
- **THEN** the app switches to dark mode and persists the choice
```

`SHALL`과 `WHEN`/`THEN`은 요구사항 명세의 오랜 관용이며, 새로 만든 문법이 아니다.
이 명세는 AI가 쓰고 사람이 검토한다고 README가 명시한다.
코드가 한 줄이라도 쓰이기 전에 계획을 검토하는 것이 이 도구가 파는 것이다.

OpenSpec 자체가 OpenSpec으로 만들어지고 있으며, 저장소의 `openspec/specs`와 `openspec/changes`에서 실제 사례를 볼 수 있다고 밝힌다.

그리고 이 도그푸딩은 권고가 아니라 기여 규칙이다.
기여 안내는 핵심 설계 변경이면 토론을, 그 밖에는 이슈를 PR보다 먼저 열고 PR에서 그것을 링크하라고 요구한다.
새 기능과 중요한 리팩터링과 구조 변경은 OpenSpec 변경 제안서를 먼저 거쳐야 한다고 명시한다.
즉 이 저장소에 기능을 보내려면 이 도구의 워크플로를 실제로 통과해야 한다.

## 설치하기

Node.js 20.19.0 이상이 필요하다.

```bash
npm install -g @fission-ai/openspec@latest
cd your-project
openspec init
```

`openspec init`이 선택한 도구에 맞는 명령 형태를 출력한다.
정규 이름은 `/opsx:propose`이지만 도구마다 표기가 다르다.
Cursor와 GitHub Copilot에서는 `/opsx-propose`, Amazon Q에서는 `@opsx-propose`, Codex에서는 `$openspec-propose`다.

기본 프로필에는 `explore`와 `propose`만 들어 있다.
확장 워크플로(`/opsx:new`, `/opsx:continue`, `/opsx:ff`, `/opsx:verify`, `/opsx:bulk-archive`, `/opsx:onboard`)가 필요하면 프로필을 바꾼다.

```bash
openspec config profile
openspec update
```

지원 도구는 30개가 넘는다고 밝히며, 홈페이지에 Claude Code, Codex, Cursor, GitHub Copilot, Gemini CLI, Zed 등이 나열되어 있다.

README가 사용상 권장 두 가지를 따로 적어 둔다.

하나는 모델 선택이다.
OpenSpec은 추론 능력이 높은 모델에서 가장 잘 동작한다고 하며,
계획과 구현 양쪽에 상위 모델을 권한다.
이것이 단순한 권고가 아닌 이유는 이 도구가 만드는 산출물의 성격 때문이다.
제안서와 명세와 설계 문서를 모델이 쓰므로, 모델이 약하면 사람이 읽어야 할 분량만 늘고 내용은 얕아진다.

다른 하나는 컨텍스트 위생이다.
깨끗한 컨텍스트 창에서 이득을 보므로 구현을 시작하기 전에 컨텍스트를 비우고
세션 내내 관리하라고 적는다.
이것은 이 도구의 구조가 만드는 요구이기도 하다.
계획 단계에서 탐색과 논의로 컨텍스트를 채운 뒤 같은 세션에서 구현으로 넘어가면,
방금 만든 명세가 대화 이력에 묻힌다.
명세를 파일로 남기는 것의 값이 바로 컨텍스트를 비워도 계획이 남는다는 데 있으므로,
비우지 않으면 이 도구를 쓰는 이유의 절반이 사라진다.

원격 수집도 알아 둘 필요가 있다.
익명 사용 통계를 수집하며 명령 이름과 버전만 보내고
인자와 경로와 내용과 개인 식별 정보는 보내지 않는다고 밝힌다.
CI에서는 자동으로 꺼진다.
끄는 방법은 세 가지이고 하나만 해도 된다.

```bash
openspec config set telemetry.enabled false  # 전역 설정, 값이 없으면 켜진 상태
export OPENSPEC_TELEMETRY=0                  # 환경 변수가 설정보다 우선한다
export DO_NOT_TRACK=1                        # 표준 opt-out 변수도 인식한다
```

기본값이 켜짐이라는 점이 중요하다.
사내 정책상 도구의 외부 통신을 통제해야 하는 환경이라면 설치 직후에 꺼야 한다.

## Stores: 저장소를 넘는 계획

혼자 쓸 때는 한 저장소 안에서 자신과 AI를 정직하게 유지하는 것이 전부지만, 팀에서는 어려운 지점이 옮겨 간다고 README가 짚는다.
기능 하나가 API 서버와 웹 앱과 공유 라이브러리에 걸치고, 요구사항은 한 팀이 소유하며 다른 팀이 소비하고, 계획은 코드가 존재하기 전에 시작된다.

Stores가 그 답으로 제시된다.
계획을 자기만의 저장소에 두되, 이미 아는 `openspec/` 구조(명세와 변경)를 그대로 쓰고 `git push`로 공유한다.

- 저장소를 넘는 기능: 코드가 세 저장소에 떨어져도 변경 하나, 계획 하나
- 공유 요구사항: 플랫폼 팀이 명세를 소유하고, 제품 팀이 읽기 전용으로 참조한다. 표류하는 위키가 없다
- 코드보다 앞선 계획: 지금 스토어에 계획을 담고, 코드 저장소가 나중에 따라온다

Stores는 베타다.

## 다른 도구와의 대비

README가 경쟁 도구를 직접 지목해 비교한다.
이런 비교는 대개 자기 위치를 설명하는 수사이므로, 무엇을 골랐는지를 읽는 자료로 쓰는 편이 낫다.

GitHub의 Spec Kit에 대해서는 철저하지만 무겁다고 평한다.
경직된 단계 관문과 많은 마크다운과 Python 설치가 든다는 것이며,
OpenSpec은 더 가볍고 자유롭게 반복할 수 있다고 적는다.

AWS의 Kiro에 대해서는 강력하지만 그들의 IDE에 묶이고 특정 모델 계열로 제한된다고 적는다.
OpenSpec은 이미 쓰는 도구에서 동작한다는 것이다.

그리고 아무것도 쓰지 않는 경우와도 비교한다.
명세 없는 AI 코딩은 모호한 프롬프트와 예측 불가능한 결과를 뜻하며,
OpenSpec은 의례 없이 예측 가능성을 준다는 것이다.

이 세 비교의 축이 각각 다르다는 점이 눈에 띈다.
Spec Kit과는 무게를, Kiro와는 종속을, 아무것도 없는 경우와는 예측 가능성을 두고 견준다.
즉 이 도구가 스스로 정의하는 자리는 가장 기능이 많은 곳도 가장 단순한 곳도 아니고,
단계 강제를 빼되 산출물은 남기는 지점이다.
철학 다섯 줄 중 앞의 세 줄이 정확히 그 선택을 적어 놓은 것이다.

확장 방식에서도 같은 태도가 보인다.
서드파티 스키마 묶음을 별도 저장소로 배포하는 공동체 스키마 개념이 있고,
README 스스로 이것이 Spec Kit의 확장 카탈로그가 도구 통합을 다루는 방식과 비슷하다고 밝힌다.
핵심을 얇게 두고 의견이 담긴 워크플로는 바깥으로 빼는 구조이며,
앞서 본 프로필 분리와 같은 방향이다.

## 트레이드오프

### 명세가 오래 살아남지 못한다

HN 토론에서 가장 많은 반응을 모은 것은 사용 후기였고, 그 후기는 이 도구의 절반을 버렸다는 내용이었다.

`mafro`는 6~9개월 동안 혼자 개발한 대형 소프트웨어 두 개에 OpenSpec을 적극적으로 썼지만 최근 명세 부분을 완전히 버렸다고 적었다.
장기적으로 유용하지 않았고, LLM으로 코드가 명세와 맞는지 그리고 명세가 코드와 맞는지를 양방향으로 점검하니 두 프로젝트 모두 크게 어긋나 있었다는 것이다.
결국 코드가 곧 명세라는 오래된 이론이 맞는 셈이라고 정리했다.[^mafro]

그런데 같은 글에서 그가 유지한 것이 있다.
제안서를 만들고, 검토하고, 구현하고, 코드를 검토하는 과정의 흐름이다.
그리고 단위 테스트로 동작을 검증할 수 없는 곳을 위한 ADR과 불변 조건 기록도 유용했다고 덧붙였다.

`mactavish88`이 이 구분을 더 분명하게 말했다.
저장소에 오래 남는 명세는 쓸모없지만, 하나의 복잡한 기능을 큰 코드베이스에서 개발하는 동안 에이전트를 궤도에 유지하는 변경 절차는 대단히 값지다는 것이다.[^mactavish88]

여기서 나오는 판단은 이 도구의 두 부분을 나눠서 평가해야 한다는 것이다.
변경 단위의 작업물(제안서, 작업 목록)은 수명이 그 작업의 길이와 같으므로 낡을 시간이 없다.
반면 저장소 전체의 동작을 서술하는 명세 말뭉치는 코드가 바뀔 때마다 낡고, 그것을 맞추는 비용이 계속 발생한다.
OpenSpec은 둘을 하나의 흐름으로 묶어 팔지만, 사용자들의 보고는 전자만 남기고 후자를 버리는 쪽으로 수렴한다.

반론도 있다.
`p_kuni`는 왜 표류가 생기느냐고 물으면서, 자기 팀은 AI 리뷰가 기존 명세와 현재 구현을 대조하고 충돌이 있으면 PR 리뷰에 기록되어 고칠 수 있게 한다고 적었다.[^p_kuni]
`polycaster`는 코드가 명세의 일부일 뿐이라고 반박했다.
코드는 구현의 이유를 말하지만 요구사항 자체의 근거는 말하지 않는다는 것이다.[^polycaster]

`cherry_tree`가 이 논쟁을 정리하는 질문을 던졌다.
저장소 전체에 대한 하나의 장수 명세를 유지하려는 것인지, 작업 단위마다 명세를 만드는 것인지 묻고,
전자를 시도하는 사람들에게서 무너진다는 말을 흔히 듣는다고 했다.[^cherry_tree]
이 질문이 이 도구를 도입할 때 먼저 정해야 할 것이다.

### 산출물이 많아지고 전부 검토 대상이 된다

두 번째로 자주 나온 불만은 문서의 양이다.

`open-paren`은 자기 조직이 OpenSpec을 도입했는데 강하게 싫어한다고 적었다.
중간 크기 이상의 변경마다 검토가 필요한 마크다운 문서 여러 개가 생기고, 그것들은 손으로 쓰이지 않으며 AI 글쓰기의 온갖 흔적이 담긴 슬롭이라는 것이다.
작고 사람이 쓴 명세가 이 큰 명세 문서들보다 훨씬 효과적이라고 보았고, 산문이 코드에 요구되는 모든 동작을 열거할 수 없으며 그래서도 안 된다고 했다.[^open-paren]

`QwenGlazer9000`도 자기 조직이 도입했고 워크플로가 크게 나빠졌으며 모든 변경이 훨씬 번거로워졌다고 적었다.[^QwenGlazer9000]
`whinvik`은 링크를 열자마자 얼마나 많은 파일을 만드는지 보였다며,
요구사항 프롬프트 하나에서 이 많은 명세 파일로 가는 것이 목적인지, 그 명세들이 요구사항을 반영하는지 어떻게 아는지 물었다.[^whinvik]

유지보수자 `TabishB`가 이 비판에 직접 답했다.
명세에 생각이나 노력이 들어가지 않으면 읽을 수 없는 슬롭이 될 수 있다는 데 동의하며,
품질과 가독성은 여전히 사람에게 달려 있지만 더 간결하고 반복적으로 만들도록 경험을 개선하겠다고 했다.[^TabishB]

이 응답이 문제의 구조를 드러낸다.
도구는 사람이 명세를 검토한다는 전제 위에 서 있는데, 검토 부담이 커지면 검토가 형식이 되고, 그러면 전제가 무너진다.
그리고 문서가 AI가 쓴 것이라면 검토자는 자기가 쓰지 않은 긴 산문을 읽어야 하며, 이것은 코드 리뷰보다 즐겁지 않은 일이다.

`nonethewiser`가 이것을 통제의 환상이라고 불렀다.
에이전트 워크플로에 이런 구조를 부과하면 일이 늘고 품질이 떨어진다는 것이다.[^nonethewiser]
이 주장을 그대로 받아들이지 않더라도, 검토 부담이 실제로 줄어드는지를 도입 전에 확인해야 한다는 점은 남는다.

### 최신 모델이 계획을 잘하면 이 층이 필요한가

`sheepscreek`은 이런 것들을 이미 지나오지 않았느냐고 물었다.
최근 LLM들은 긴 맥락 작업으로 충분히 학습되어 계획을 꽤 잘하게 되었고, Codex나 Claude Code를 쓴다면 굳이 쓰지 않겠다는 것이다.[^sheepscreek]

이 물음에 대한 답들이 이 도구의 실제 가치가 어디 있는지를 보여 준다.

`scosman`은 계획할 수 있다는 것과 원하는 것을 내놓는다는 것은 다르며, 대개 일의 대부분은 무엇을 만들지 합의하는 것이라고 했다.[^scosman]
`virgil_disgr4ce`는 한 줄로 잘랐다. 명세하는 것은 계획하는 것이 아니다.[^virgil_disgr4ce]
`crossroadsguy`는 다른 각도를 댔다.
이런 도구를 쓰는 이유 중 하나는 자신과 LLM 모두에게 규율을 강제하는 것이며, 그러지 않으면 자주 제자리를 맴돌고 토큰도 더 든다는 것이다.
LLM만으로도 할 수 있지만 매우 지저분했다고 덧붙였다.[^crossroadsguy]

`alexjplant`의 보고가 가장 구체적이다.
OpenSpec 같은 것으로 명시적으로 조사하고 범위를 잡고 저장한 뒤 새 맥락에서 구현하지 않으면 Claude Code가 엉뚱한 짓을 한다는 것이다.
Docker 컨테이너를 띄우라는 요청에 손을 들어 버리거나, 명시한 아키텍처 지시를 무시하거나, 부정확한 내용이 가득한 장황한 문서를 쓴다고 했다.[^alexjplant]

`philipp-gayret`은 취향의 문제로 보았다.
해법을 만드는 자신이나 조직의 취향이 LLM의 기본값과 크게 다를 수 있고, 명세로 그 취향을 담는다는 것이다.
예로 LLM들이 만든 것뿐 아니라 만들지 않은 것까지 문서화하기 좋아하는 습관을 들었다.[^philipp-gayret]

반대쪽도 분명하다.
`loveparade`는 speckit을 꽤 써 봤지만 결과가 잘해야 반반이었다며, 모호함과 코드 리뷰를 한 곳에서 다른 곳으로 옮길 뿐 실질적으로 얻는 것이 없다고 적었다.[^loveparade]

이 대립의 결론은 이 층이 모델 능력의 함수가 아니라 조직 규율의 함수라는 것이다.
계획을 잘하는 모델이 나와도 무엇을 만들지 합의하는 일은 사라지지 않고, 그 합의를 기록으로 남길지 말지는 여전히 선택이다.
그래서 모델이 좋아진다고 이 도구가 불필요해지지는 않지만, 규율이 이미 있는 팀에는 층이 하나 더 생기는 것일 수 있다.

### 1990년대 UML 코드 생성과 무엇이 다른가

`twen_ty`가 던진 질문이 이 분야 전체를 겨냥한다.
1990년대에 UML로 코드를 생성하자던 것과 무엇이 다르고, 왜 같은 식으로 실패하지 않겠느냐는 것이다.
자기 경험으로는 명세 표류가 이런 도구들이 작동하지 않는 주된 이유이며,
단발성 신규 기능 생성에는 통할지 몰라도 크고 여러 개발자가 오래 유지하는 코드베이스에서는 명세가 썩어 값어치보다 고통이 커진다고 했다.[^twen_ty]

`wyum`의 답이 가장 구조적이다.
코드 생성을 위한 모델링 언어들은 표현력이 부족해서 결국 프로그래밍 언어가 되어야 하고 그 사용자도 프로그래머가 되어야 하므로 실패했으며, 이 흐름이 명세가 곧 코드라는 결론으로 이어진다는 것이다.
AI와 함께라면 다른 이유는 자연어가 충분히 표현력이 있고 팀이 이미 그 수준에서 협업하며, LLM이 빈틈을 메우고 불일치를 지적하며 자연어를 코드로 안정적으로 대응시킬 수 있다는 점이다.[^wyum]

`spinningslate`는 UML 실패의 다른 원인을 짚었다.
명세와 동작하는 코드 사이에 닫힌 고리가 없었다는 것이다.
Rational Unified Process는 심하게 비효율적이고 대부분 수작업이었으며, 산출물 사이의 대응이 수동이고 휴리스틱에 기댔다고 했다.[^spinningslate]

이 진단이 맞는다면 이 세대 도구의 승부처는 표현력이 아니라 고리를 닫는 비용이다.
`/opsx:verify`가 존재하는 이유가 그것이고, 앞서 본 `mafro`의 보고, 즉 양방향 점검에서 크게 어긋나 있었다는 결과가 그 고리가 실제로 닫히는지에 대한 첫 번째 증거다.
도구가 검증 명령을 제공한다는 것과, 그 검증을 통과하도록 유지하는 비용을 팀이 감당한다는 것은 다른 문제다.

## 함정

명세는 오래 두면 낡는다. 변경 단위 작업물과 저장소 전체 명세 말뭉치를 구분하고, 후자를 유지할 비용을 감당할지 먼저 정해야 한다.

문서 검토가 병목이 될 수 있다. 변경마다 여러 개의 마크다운이 생기고 그것을 사람이 읽어야 하므로, 검토가 형식이 되는 순간 이 도구의 전제가 무너진다.

명세를 AI가 쓴다. 자기가 쓰지 않은 긴 산문을 검토하는 일이며, 코드 리뷰와 다른 종류의 피로가 생긴다.

Node.js 20.19.0 이상이 필요하고 전역 설치를 요구한다. 독립 실행 바이너리를 원하는 요청이 있으나 아직 없다.

슬래시 명령의 표기가 도구마다 다르다. `openspec init`이 출력하는 형태를 확인해야 한다.

기본 프로필에는 `explore`와 `propose`만 있다. `verify`를 비롯한 나머지는 프로필을 바꿔야 나온다.

Stores는 베타다. 팀 단위 도입의 핵심 기능이 아직 안정 단계가 아니라는 뜻이다.

원격 수집이 기본으로 켜져 있다. 명령 이름과 버전만 보낸다고 밝히지만, 끄려면 설정이나 환경 변수를 직접 건드려야 한다.

상위 추론 모델을 권장한다. 계획과 구현 양쪽에 쓰면 변경 하나의 비용이 그만큼 올라가고, 이 도구가 더하는 문서 작업이 그 비용 위에 얹힌다.

같은 분야에 SpecKit, SpecDD, GSD 등 여러 도구가 있고 접근이 상당히 다르다. 명세 기반 개발이라는 말 자체가 가리키는 범위가 넓다.

## 확인하기

주장을 검증하는 가장 빠른 방법은 기존 코드베이스에 붙여 한 기능을 끝까지 돌려 보는 것이다.

```bash
npm install -g @fission-ai/openspec@latest
cd your-project
openspec init
```

그다음 실제 작업 하나를 `/opsx:explore`부터 `/opsx:archive`까지 통과시키고, 생성된 파일을 전부 읽는다.
읽는 데 걸린 시간이 이 도구의 실제 비용이다.

그리고 몇 주 뒤에 같은 영역을 손댈 때 `/opsx:verify`를 돌려 본다.
앞서 본 보고들이 갈린 지점이 정확히 여기이므로, 자기 코드베이스에서 고리가 닫히는지가 도입 여부를 정한다.

저장소 자체가 OpenSpec으로 관리되므로 `openspec/specs`와 `openspec/changes`를 읽는 것이 규모 있는 실제 사례를 보는 가장 빠른 길이다.

## 체크리스트

- 변경 단위 작업물만 쓸 것인지, 저장소 전체 명세 말뭉치까지 유지할 것인지 정했는가
- 생성된 문서를 실제로 읽고 검토할 사람이 있는가
- 몇 주 뒤 `/opsx:verify`를 돌렸을 때 어긋남이 관리 가능한 수준인가
- Node.js 20.19.0 이상이고 전역 설치가 허용되는 환경인가
- 쓰는 코딩 도구의 슬래시 명령 표기를 확인했는가
- `verify`가 필요하면 확장 프로필로 바꿨는가
- 팀 단위로 쓸 계획이라면 Stores가 베타라는 점을 반영했는가
- 이미 규율이 있는 팀이라면 이 층이 무엇을 더해 주는지 말할 수 있는가
- 원격 수집을 끌 필요가 있는 환경인가, 끈다면 설치 직후에 껐는가
- 계획과 구현에 쓸 모델을 정했고 변경당 비용을 계산해 봤는가
- 구현을 시작하기 전에 컨텍스트를 비우는 절차가 습관으로 잡혔는가

## 기억할 원칙

### 과정의 산출물과 상태의 기록은 수명이 다르므로 따로 다뤄야 한다

이 도구에 대한 사용 후기들이 거의 같은 지점에서 갈렸다.
제안서와 작업 목록은 유용했고, 저장소 전체의 동작을 서술하는 명세는 버렸다는 것이다.

이 갈림은 우연이 아니라 두 종류의 문서가 가진 수명 차이에서 나온다.
과정의 산출물은 그 작업이 끝나면 역할이 끝나므로 낡을 시간이 없다.
상태의 기록은 대상이 계속 변하므로 갱신하지 않으면 즉시 틀린 것이 되고, 갱신 비용은 영원히 발생한다.

같은 구분이 다른 곳에도 있다.
PR 설명과 아키텍처 문서, 회의록과 운영 매뉴얼, 마이그레이션 스크립트와 스키마 문서가 각각 같은 쌍이다.
앞의 것은 쓰고 잊어도 되고, 뒤의 것은 쓰는 순간부터 유지보수 대상이 된다.

여기서 나오는 규칙은 두 가지다.
문서를 만들 때 그것이 과정의 산출물인지 상태의 기록인지 먼저 정하고, 상태의 기록에는 갱신 책임자와 갱신 시점을 함께 정해야 한다.
그리고 상태의 기록은 코드에서 생성할 수 있으면 생성하는 편이 낫다.
`nullbio`가 명세를 실시간으로 LLM에게 코드에서 읽어 내게 할 것이라고 본 이유가 그것이며,
코드에서 표류할 수 있는 모든 것이 부채이고 유지보수 부담이라는 그의 진단은 이 구분을 다른 말로 한 것이다.[^nullbio]

### 도구가 강제하는 규율은 규율이 없는 조직에만 값을 만든다

이 도구를 둘러싼 평가가 정반대로 갈린 것이 흥미롭다.
한쪽은 이것 없이는 에이전트가 엉뚱한 짓을 한다고 했고, 다른 쪽은 조직에 도입되자 모든 작업이 번거로워졌다고 했다.

두 보고가 모두 참일 수 있다.
전자는 규율을 도구로 들여온 경우이고, 후자는 이미 있던 규율 위에 도구를 얹은 경우이기 때문이다.
`crossroadsguy`가 LLM만으로도 할 수 있지만 지저분했다고 적은 것이 전자의 자리이고,
`esafak`이 OpenSpec조차 자신에게는 무겁다며 계획 세션 뒤 파일 하나를 만든다고 한 것이 후자의 자리다.
중요한 것은 리뷰어가 코드를 대조할 수 있는 파일이 있다는 것이라고 그는 정리했다.[^esafak]

여기서 일반화할 수 있는 판단 기준이 있다.
프로세스 도구를 평가할 때 그 도구가 무엇을 하는지보다, 그것이 강제하는 규율이 지금 없는 것인지를 먼저 물어야 한다.
없다면 도구가 그것을 들여오는 값이 비용보다 클 가능성이 높다.
이미 있다면 도구는 같은 일에 형식을 더하는 것이고, 그 형식이 만드는 산출물은 순수한 추가 비용이 된다.

이 기준은 도입 결정을 조직 단위가 아니라 팀 단위로 내려야 한다는 결론으로 이어진다.
같은 회사 안에서도 규율의 수준이 다르고, 그래서 한 팀에 도움이 된 도구가 옆 팀에는 번거로움만 될 수 있다.
`TabishB`가 채택이 주로 엔지니어 주도의 상향식이었다고 밝힌 것이 이 구조와 맞아떨어진다.[^TabishB-adoption]
위에서 일괄 도입한 조직에서 나온 불만이 가장 강했다는 사실도 같은 것을 가리킨다.
