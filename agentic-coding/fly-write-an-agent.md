## 소개

Fly.io의 Thomas Ptacek(@tqbf)이 2025년 11월 6일 Fly 블로그에 올린 글이다.
LLM 에이전트는 자전거와 같아서 추상적으로 이해하기는 쉬워 보이지만
직접 페달을 밟아 봐야 이해된다는 것이 출발점이다.
글쓴이는 에이전트를 좋아하는 쪽이든 싫어하는 쪽이든 그것에 대해 맞게 알아야
한다고 말한다.
에이전트가 허풍이든 아니든 큰 개념이므로 가장 잘 아는 안티(hater)나
팬(stan)이 되려면
만들어 봐야 한다는 것이다.

더 설득력 있는 이유는 에이전트가 놀랄 만큼 쉽다는 점이다.
글은 에이전트가 무엇인지 설명하지 않고 바로 코드로 들어간다.
OpenAI의 Responses API를 쓰는 15줄짜리 대화 엔진에서 시작해
대화 기록을 쌓는 방식을 보이고,
글이 According To Simon이라고 부르는 정의, 곧 에이전트는 도구를 쓰면서 루프로
도는 LLM이라는 정의를 인용한 뒤
`ping` 도구 하나를 붙여 도구 호출을 보여 준다.
모델에게 호스트에 핑을 보낼 권한만 주었는데,
모델이 여러 구글 주소를 스스로 골라 핑을 보내고 결과를 요약했다는 것이다.

글은 여기서 몇 가지 주장을 끌어낸다.
컨텍스트 윈도우는 문자열 리스트일 뿐이고 LLM 자체는 상태가 없는 블랙박스이며
우리가 나누는 대화는 스스로에게 거는 환상이다.
MCP는 근본적인 기술이 아니라 Claude Code와 Cursor에 자기 도구를 넣는 플러그인
인터페이스일 뿐이며,
직접 에이전트를 짜서 플러그인이 아니라 API를 다루라고 권한다.
컨텍스트 엔지니어링은 실제로 있는 문제이고, 읽기 쉬운 프로그래밍 문제다.
서브 에이전트는 새 컨텍스트 배열과 모델 호출 한 번이면 구현된다.
글은 에이전트 설계가 풀리지 않은 소프트웨어 공학 문제들과 닿아 있다며
네 가지를 든다.
예측 불가능성과 구조화된 프로그래밍의 균형, 에이전트를 실제 검증 가능한 근거에
잇는 방법,
여러 단계 작업을 잇는 중간 형식, 토큰 배분과 비용 통제다.
각 반복에 드는 시간이 30분 수준이어서 이 문제들이 누군가의 지하실에서 풀릴 수
있다고도 한다.

## 동작 방식

### 모델은 기억하지 않고 우리가 쌓는다

글의 가장 쓸모 있는 통찰은 대화가 환상이라는 것이다.
LLM 호출은 요청마다 독립이어서, 이전 대화를 기억하는 것은 모델이 아니라
우리 코드가 쌓은 리스트다.
호출 때마다 지금까지의 모든 사용자 입력과 모델 출력을 다시 보낸다.
컨텍스트 윈도우가 문자열 리스트일 뿐이라는 말은
컨텍스트를 우리가 편집하고, 나누고, 되돌릴 수 있다는 뜻이기도 하다.
HN의 aaronblohowiak은 매번 컨텍스트 전체를 보낸다는 데 놀라며,
정정 메시지를 보내는 것보다 되돌리는 편이 낫지 않겠느냐고
물었다.[^aaronblohowiak]
michaelanckaert는 매번 전체를 보내는 것이 곧 모델이 대화에 대해 기억하는
전부이며
모델은 완전히 상태가 없다고 답했다.[^michaelanckaert]
그는 에이전트가 궤도를 벗어나면 감독 에이전트가 그 지점의 메시지를 컨텍스트에서
지우거나 올바른 정보로 고치게 하는 에이전트를 짜 봤다고
적었다.[^michaelanckaert]

Lobste.rs의 equeue는 챗봇이 LLM에 사후에 덧씌운 상호작용 방식이라는 것을
알고 놀라는 사람이 많다고 적었다.[^equeue]
markerz는 사람들이 모델이 저장된 상태를 가진다고 믿지만
실제로는 새 메시지마다 이전 대화를 처음부터 다시 겪는 것이라고
말했다.[^markerz-state]
글쓴이는 직접 에이전트를 짜기 전에는 이를 알지 못했다고 답했다.[^tptacek-state]
대화를 추적하는 API 기능을 찾아 헤맸는데 그런 기능은 실제로 있었고,
처음에는 어리석다고 느꼈지만 그것으로 할 수 있는 일이 많았다는
것이다.[^tptacek-state]

### 도구 호출은 모델이 코드를 부르게 하는 약속이다

도구는 이름, 설명, 매개변수 스키마로 정의되고 모델을 부를 때마다 목록으로 함께
보낸다.
프롬프트가 도구 호출이 필요하다고 모델이 판단하면
모델은 도구를 부르라는 특별한 응답을 낸다.
우리 루프는 그 응답을 읽어 도구를 실행하고 결과를 컨텍스트에 넣어 다시 모델을
부른다.
글의 `handle_tools`가 하는 일이 이것이다.
호출할 도구를 여러 번 고르는 반복은 우리가 짠 루프가 아니라
모델이 결정한 것이라는 점이 글이 놀라는 대목이다.

### 서브 에이전트와 컨텍스트 엔지니어링은 같은 배열 조작이다

글은 고정된 토큰 한도에서 입력, 저장한 출력, 도구 설명, 도구 출력이 모두 공간을
차지하고
임계점을 넘으면 시스템이 비결정적으로 멍청해진다고 말한다.
서브 에이전트는 이 배열을 새로 만들고 모델을 한 번 더 부르는 것이며,
서로 요약하고 합치고 트리를 이루게 할 수 있다.
요약을 되먹여 즉석에서 압축하는 것도 가능하다.

## 구현하기

글의 코드는 OpenAI API 키가 있어야 실행된다.
아래는 같은 구조를 키 없이 실행해 볼 수 있게 줄인 것이다.
모델은 넘겨받은 컨텍스트만 보고 답하는 가짜 함수이고,
에이전트와 서브 에이전트가 모두 컨텍스트 배열 하나라는 점과
요약으로 컨텍스트를 줄이면 모델이 앞의 질문을 잃는다는 점을 보인다.

```python
def count_tokens(messages):
    """토큰 수를 단어 수로 어림한다. 실제로는 모델의 토크나이저를 쓴다."""
    return sum(len(m["content"].split()) for m in messages)


def fake_llm(context):
    """상태가 없는 블랙박스를 흉내 낸다. 넘겨받은 context만 보고 답한다."""
    questions = [m["content"] for m in context if m["role"] == "user"]
    return f"받은 메시지 {len(context)}개, 지금까지 질문 {len(questions)}개, 마지막 질문: {questions[-1]}"


class Agent:
    def __init__(self, system):
        # 대화는 모델이 기억하는 것이 아니라 우리가 쌓는 리스트다
        self.context = [{"role": "system", "content": system}]

    def process(self, line):
        self.context.append({"role": "user", "content": line})
        answer = fake_llm(self.context)  # 호출마다 리스트 전체를 다시 보낸다
        self.context.append({"role": "assistant", "content": answer})
        return answer


def compress(agent, summarizer):
    """서브 에이전트도 컨텍스트 배열 하나와 호출 한 번일 뿐이다.
    요약 담당에게 지금까지의 대화를 맡기고, 본 컨텍스트를 요약으로 바꾼다."""
    before = count_tokens(agent.context)
    transcript = " ".join(m["content"] for m in agent.context[1:])
    summary = summarizer.process(transcript)
    short = f"요약: 지금까지 {len(agent.context) - 1}개 메시지를 주고받았다"
    agent.context = [agent.context[0], {"role": "assistant", "content": short}]
    return before, count_tokens(agent.context), summary


if __name__ == "__main__":
    main = Agent("너는 도우미다")
    main.process("안녕")
    print(main.process("2+2는?"))
    summarizer = Agent("너는 요약 담당이다")  # 새 배열을 만들었을 뿐이다
    before, after, _ = compress(main, summarizer)
    print(f"압축 전 {before}토큰, 압축 후 {after}토큰")
    print(main.process("다시 물을게, 2+2는?"))
```

도구를 붙이는 부분은 글이 `ping`으로 보인 구조를 따르면 된다.
도구마다 이름, 설명, 매개변수 스키마를 정의해 매 호출에 함께 보내고,
응답에 도구 호출이 있으면 실행해 결과를 컨텍스트에 넣고 다시 호출하는
루프를 둔다.
모델이 더 이상 도구를 부르지 않을 때 루프가 끝난다.

## 트레이드오프

### 루프를 명시할수록 놀랄 일이 줄지만 문제를 푸는 힘도 줄어든다

글은 이를 다이얼로 설명한다.
어떤 루프는 우리가 명시적으로 쓰고, 어떤 루프는 모델의 추론에서 불러낸다.
너무 명시적이면 에이전트가 놀라게 하는 일이 없고,
다이얼을 끝까지 돌리면 놀라서 죽을 만큼 놀라게 한다.
취약점 스캐너의 예가 이 선택을 보여 준다.
저장소의 각 파일을 모델에 한 번씩 먹이는 루프를 쓸 수도 있고,
모델이 어떤 파일을 볼지 스스로 정하게 할 수도 있다.
OWASP Top 10 전부를 검사하는 에이전트와
DOM 무결성, SQL 인젝션, 권한 검사에 각각 루프를 둔 구성도 선택지다.

명시적 루프는 재현성과 비용 예측을 주지만 처음 설계한 분기 밖의 문제를 풀지
못한다.
모델에게 맡기면 예상치 못한 해법이 나오지만 같은 입력에서 다른 길을 갈 수 있고
토큰 비용이 늘어난다.
글이 어느 지점이 최선인지는 만들어 보기 전에는 모른다고 말하는 이유다.
HN에서 글쓴이 tptacek은 이 선택을 겪은 사례를 들려주었다.
2021년경 함대의 DNS 라우팅을 보려고 Vultr에 외부 DNS 탐침을 깔았는데
지표를 정하고 그 데이터를 읽을 수 있게 만드는 일이 번거롭고 오류가 잦았다고
한다.[^tptacek-fleet]
그런데 ping, dig, traceroute 같은 기본 네트워크 도구를 에이전트에 주고
깔끔한 신호를 요청하면 그럭저럭 해낸다는 것이다.[^tptacek-fleet]
에이전트가 잘 만든 하드코딩 텔레메트리보다 낫다는 말은 아니고
지금은 이런 일에 에이전트를 쓰지 않지만,
이런 문제에서 유용성 90% 문턱을 넘는 일은 좋은 텔레메트리를 만드는 일보다 훨씬
쉽다고 했다.[^tptacek-fleet]
그 글에 riskable은 이 방식이 한 가지 일만 잘하는 유닉스식 도구를 만들고 싶게
한다고 적었다.[^riskable]

Lobste.rs의 asb는 SWE-bench 저자들이 만든 mini-swe-agent를 소개했다.[^asb]
더 복잡한 하네스의 결과가 더 낫지만,
LLM이 bash를 생성하고 그것을 실행하는 단순한 방식도 꽤 잘 동작한다는
것이다.[^asb]

### 하나의 컨텍스트에 도구를 많이 넣으면 작업할 공간이 줄어든다

글은 한 컨텍스트 윈도우에 도구 설명을 가득 넣으면 일할 토큰 공간이 남지 않아
일부 초기 사용자가 도구에 비관적이 되었다고 전한다.
그런데 왜 한 컨텍스트에 모든 도구를 넣느냐고 되묻는다.
도구마다 컨텍스트를 나눈 서브 에이전트를 두면 도구 설명이 서로의 공간을 먹지
않는다.

그 대가는 에이전트 사이의 통신이다.
서브 에이전트가 많아지면 결과를 어떤 중간
형식(JSON, SQL 데이터베이스, 마크다운 요약)으로
넘길지, 어디서 정보를 잃을지가 설계 문제가 된다.
글이 이를 풀리지 않은 문제로 꼽는 것도 그래서다.

### MCP를 쓰면 코드를 줄이지만 에이전트 구조를 다듬을 자유를 잃는다

글의 주장은 MCP가 단일 컨텍스트 코딩 에이전트를 고객 응대 질의 같은 일에 끌고
가는 데
수십 줄을 아껴 줄 뿐, 에이전트 구조를 다듬을 기회를 빼앗는다는 것이다.
직접 에이전트를 짜는 사람에게는 맞는 말이다.
그러나 에이전트를 직접 짜지 않는 사람이 이미 있는 코딩 에이전트에
도구를 붙이는 방법은 플러그인 인터페이스뿐이다.
이 논리는 누가 독자인가에 따라 갈린다.
HN의 robot-wrangler는 에이전트 하나, 언어 하나, 프레임워크 하나를 만들 때는
MCP가 필요 없지만 우리가 원하는 개방형 코딩·조사 도우미는 여럿으로 구성될
것이라며,
MCP가 API를 쓰고 격리되고 재현 가능한 맥락에서 시험하는 쪽으로 가는 유일한
흐름이라고 반박했다.[^robot-wrangler]
글쓴이는 MCP의 가장 큰 문제가 Claude Code의 맥락 구조,
곧 하나의 컨텍스트 윈도우(어쩌면 서브 에이전트와 함께)와 하나의 도구 모음을
전제로 에이전트가 만들어질 것이라는 암묵적 가정이라고 답했다.[^tptacek-mcp]
MCP는 어떤 에이전트 구조에도 쓸 수 있음을 알지만,
직접 짜는 경우에도 남이 만든 도구 정의를 쓰려면 MCP 도구 호출 기능을 넣을 수
있다고 인정하며,
다만 직접 짠다면 Claude Code의 스킬 패턴을 구현하는 편이 나을 것이라고
했다.[^tptacek-mcp]
qwertox는 MCP 서버를 만들어 Claude에서 쓰는 편이 훨씬 유용했다고
적었고,[^qwertox]
글쓴이는 그렇게 할 수는 있지만 배우는 것이 적고 시간을 많이 아끼지 못하며
Claude Code의 맥락 구조에 묶인다고 답했다.[^tptacek-claudecode]

## 비평

### 쉽다는 말은 장난감 에이전트에 대한 것이다

글은 이것이 장난감 예제임을 스스로 인정한다.
모든 에이전트가 장난감일 수 있다고도 말한다.
핑 도구를 가진 15줄에서 코딩 에이전트까지의 거리가 가깝다는 주장은
bash를 주면 10분 안에 알 수 있다는 한 문장으로 뒷받침된다.

그러나 이 사이에 있는 일이 글에서 빠져 있다.
도구 실행의 오류와 재시도, 모델이 같은 도구를 무한히 부르는 루프의 한도,
비용 상한, 잘못된 도구 호출을 되돌리는 방법이 그것이다.
글이 마지막에 꼽은 풀리지 않은 문제 네 가지는 바로 이 영역이지만,
그 어려움이 처음 주장인 놀랄 만큼 쉽다와 어떻게 이어지는지는 설명하지 않는다.
쉽다는 것은 첫 시작이 쉽다는 뜻으로만 성립한다.
HN의 teiferer는 `client = OpenAI()`를 부르고 나서 에이전트가 쉽다고 하는 것은
웹 서버를 직접 만들라면서 `http` 패키지를 가져다 쓰는 것과 같다며,
그것이 98%를 해 주지 않느냐고 물었다.[^teiferer]
글쓴이는 `OpenAI()`가 단일 HTTP 엔드포인트인
`POST https://api.openai.com/v1/responses`에 대한 얇은 래퍼일 뿐이라고
답했다.[^tptacek-openai]
rbren은 압축(compaction), 보안, 샌드박싱, 계획, 맞춤 도구가 모두 제대로 하기
어렵다며
쉽지 않다고 했고,[^rbren]
olingern은 이 글이 프로덕션 수준의 에이전트를 쓰는 글이 아니므로
그만큼 쉬운 것이 맞다고 반박했다.[^olingern]
Lobste.rs의 jrgtt는 글머리의 비유가 좋지 않다며
끓는 물과 AWS S3 API를 든 것을 이상하게 여겼고,
자전거를 못 타는 사람도 작동 원리를 꽤 짐작할 수 있다고 적었다.[^jrgtt]
기술 내용은 괜찮지만 새로운 것은 없다고 평했다.[^jrgtt]

### 한 번의 출력으로 작동한다고 판단한다

핑 예제에서 글은 출력 한 번을 보이고 이것이 작동했다고 한다.
모델이 핑을 세 번 보내고 결과를 요약하는 것은 실제로 인상적이지만
이는 한 번의 실행이다.
같은 요청을 여러 번 보내 도구 호출이 일관되는지,
핑 결과를 잘못 요약하는 경우가 있는지는 확인하지 않았다.

글은 에이전트가 거짓을 말해 루프를 일찍 끝내지 못하게 에이전트를 근거에
잇는 것이
풀리지 않은 문제라고 쓴다.
그렇다면 이 예제에서 요약이 실제 핑 결과와 맞는지를 확인하는 장치가 없다는 점은
글의 가장 약한 부분이다.
이 주장을 가장 강하게 세우려면 같은 요청을 여러 번 돌려 도구 호출의 분포와
요약의 정확도를 보여야 한다.
HN의 wayy는 에이전트를 만드는 일은 누구나 좋아하지만 디버깅은 아무도 좋아하지
않는다며,
처음에는 마법 같다가 17단계, 41단계, 9단계에서 실패하는데
확률적이어서 재현할 수 없고 한 단계에 0.5초씩 걸려 10~20분을 기다리게 된다고
적었다.[^wayy]
furyofantares는 그래서 고치려는 컨텍스트에 대해 변경을 수백 번 병렬로 돌리고
과거 시나리오 수백 개를 병렬로 다시 돌려 아무것도 깨지지 않는지 확인하는 도구를
만든다고 답했다.[^furyofantares]

### 도구 권한과 보안을 한 문단으로 넘긴다

글은 bash를 주면 코딩 에이전트에 가까워진다고 말한다.
bash를 모델에 주는 것은 모델이 시스템에서 임의 명령을 실행하게 하는 일이다.
글쓴이는 보안이 복잡하다고 인정하고 분리된 컨텍스트와 도구로 흥미로운 문제를
만들 수 있다고만 말한다.
자신이 취약점 연구자여서 흥미롭다는 것에서 물러서는 것이 합리적이라는 농담으로
마무리한다.

그러나 이 글을 읽고 따라 하는 독자는 대부분 취약점 연구자가 아니다.
도구에 어떤 권한을 주고 모델이 읽는 외부 텍스트가 도구 호출을 유도할 수 있는지는
에이전트를 만드는 사람이 가장 먼저 부딪히는 문제다.
글은 MCP에 관한 보안 괴담을 읽으면 먼저 왜 MCP가 끼어들었는지 물으라고 하지만,
직접 짠 에이전트가 같은 위험을 피한다는 근거는 제시하지 않는다.
HN의 zahlman은 bash를 주라는 말에 원격 서비스가 `rm -rf /`를 부르는 호출을
보내지 않으리라고 믿어야 하느냐고 물었다.[^zahlman]
글쓴이는 그런 걱정이 매우 합리적이며,
`rm -rf`가 실제 문제를 일으킬 수 있는 환경에서는 돌리지 말라고
답했다.[^tptacek-rm]

## 함정

글의 코드에서 보이는 함정이 있다.
`handle_tools`는 응답의 첫 출력이 추론(reasoning) 항목이면 그것을 컨텍스트에
넣는다.
글의 코드가 이 항목을 따로 처리한다는 점은 이 API가 그 항목을 요구한다는 뜻으로
읽힌다.
이 문서는 이를 API 문서로 확인하지 않았다.
다른 모델 제공자로 옮기면 이 부분을 다시 맞춰야 한다.
글이 말하는 직접 짜면 이해된다는 것은 모델 API의 세부를 이해한다는 뜻을
포함한다.

모델이 같은 도구를 계속 호출하면 루프가 끝나지 않는다.
글의 `process`는 `while handle_tools(...)`로 도구 호출이 없을 때까지 돈다.
단계 수나 비용의 한도가 없으므로 실제 서비스에서는 한도를 직접 넣어야 한다.

컨텍스트가 길어지면 모델이 비결정적으로 나빠진다는 글의 경고도 함정이다.
도구 설명, 도구 출력, 대화가 모두 공간을 차지하므로
어느 지점에서 성능이 떨어지는지 측정하지 않으면 알 수 없다.
요약으로 컨텍스트를 줄이면 위의 예제처럼 모델이 앞의 질문을 잃는다.

## 확인하기

위 코드를 `demo.py`로 저장하고 실행하면 세 줄이 나와야 한다.

```text
받은 메시지 4개, 지금까지 질문 2개, 마지막 질문: 2+2는?
압축 전 22토큰, 압축 후 7토큰
받은 메시지 3개, 지금까지 질문 1개, 마지막 질문: 다시 물을게, 2+2는?
```

첫 줄에서 모델이 받은 메시지는 시스템, 사용자 둘, 모델 하나, 곧 4개다.
세 번째 줄은 압축 뒤에 컨텍스트가 시스템, 요약, 새 질문의 3개로 줄어
모델이 질문 한 개만 아는 상태가 됨을 보인다.
글의 핵심인 컨텍스트가 우리가 관리하는 리스트이고, 줄이는 순간 모델이
잊는다는 점을
눈으로 확인하는 실험이다.

## 체크리스트

- 에이전트의 컨텍스트가 호출마다 통째로 다시 전송되는 배열임을 알고 있는가?
- 도구마다 이름, 설명, 매개변수 스키마가 있고 설명이 토큰을 얼마나 쓰는지 아는가?
- 도구 호출 루프에 단계 수 한도와 비용 한도가 있는가?
- 도구 호출 하나하나를 기록해 모델이 무엇을 불렀는지 되짚을 수 있는가?
- 요약이나 서브 에이전트로 컨텍스트를 줄일 때 잃는 정보를 확인했는가?
- 에이전트가 거짓으로 끝내지 못하도록 결과를 실제 근거와 대조하는가?
- 도구에 준 권한이 필요한 최소한인가?
- 같은 요청을 여러 번 돌려 결과가 일관된지 확인했는가?

## 기억할 원칙

### 직접 짜 보면 에이전트가 신비한 것이 아님을 알게 된다

글의 가장 단단한 주장은 에이전트가 모델 호출, 문자열 배열, 도구 호출 루프로
이루어진다는 것이다.
이를 직접 짜 보면 MCP나 서브 에이전트나 컨텍스트 엔지니어링이라는 용어가
각각 어떤 코드에 해당하는지가 보인다.
이 이해가 있어야 에이전트에 대한 주장, 낙관이든 비판이든,
어느 부분을 근거로 하는지 따져 볼 수 있다.
HN의 MinimalAction은 우리를 대체할 수도 있는 도구를 만드는 일을 왜 권하느냐고
물었다.[^MinimalAction]
글쓴이는 그것이 어떻게 동작하는지 모르는 사람의 수사에 넘어가지 않고
더 날카롭게 비판하기 위해서라고 답했다.[^tptacek-why]
그 지점까지 가는 데는 노력이 거의 들지 않는다고 덧붙였다.[^tptacek-why]
Lobste.rs의 carlana는 같은 말을 정적 사이트 생성기를 직접 만드는 일에도 할 수 있다고 적었다.[^carlana]
도구 몇 개를 이어 붙이는 사소한 과정이지만
다른 도구에서 무엇을 원해야 하는지에 대한 감각을 준다는 것이다.[^carlana]
markerz는 자체 호스팅과 같다며 인터넷 기반 시설과 소프트웨어 배포에 대해 많이
배우게 된다고 덧붙였다.[^markerz]

### 쉬운 시작이 쉬운 운영을 뜻하지는 않는다

15줄로 동작하는 에이전트는 시작이 쉽다는 증거일 뿐이다.
글이 꼽은 풀리지 않은 문제, 곧 비결정성과 구조의 균형, 근거에 잇기,
중간 형식, 비용은 시작 뒤에 오는 문제다.
따라서 만들어 보는 일은 이해의 출발점이지 운영 준비의 증거가 아니다.
