# 엔터프라이즈 AI의 과제는 모델 선택이 아니라 신원·컨텍스트·하네스로 이루어진 실행 제어 평면이다

원문: [AX 필수 요소 - AI 에이전트 신원, 컨텍스트 플랫폼, 그리고 에이전트 하네스](https://axonn.wikidocs.net/blog/34202)

## 요약

Modern IT Insights 블로그의 2026년 10월 22일 글입니다.
글은 가트너(Gartner)의 '2027년 10대 전략 기술 트렌드'가 엔터프라이즈 AI의 핵심
과제를 파운데이션 모델의 벤치마크 경쟁에서 실행 환경 통제(Execution Control
Plane)로 옮겼다고 주장합니다.
글이 옮겨 적은 10대 기술은 대규모 정량 모델, 음성 추론 모델, 월드 모델,
AI 컨텍스트 플랫폼, AI 코딩 에이전트 하네스, AI 에이전트 신원, 자율형 노출 개선,
소버린 테크, 일회성 애플리케이션, 서비스형 웻웨어입니다.
이 중 글쓴이는 아키텍처 관점에서 AI 에이전트 신원, AI 컨텍스트 플랫폼,
AI 코딩 에이전트 하네스 세 가지를 고릅니다.

- **AI 에이전트 신원**: 글은 가트너 전망으로 2028년까지 기업 보안 침해 사고의 25%가 관리되지 않는 머신 권한과 기존 자격 증명 관행에 따른 AI 에이전트 오용에서 비롯된다고 전합니다. 대응책으로 영구 API 키 대신 작업 단위로 최소 권한을 임시 발급하고 끝나면 파기하는 동적 JIT(Just-In-Time) 권한 제어를 듭니다.
- **AI 컨텍스트 플랫폼**: 글은 가트너 전망으로 2027년까지 시맨틱 체계를 우선하는 기업이 에이전틱 AI 정확도를 최대 80% 높이고 비용을 최대 60% 줄인다고 전합니다. 파편화된 데이터와 비즈니스 규칙을 정형화된 온톨로지(ontology)로 묶고, 민감 정보를 마스킹하며 권한 범위에 따라 데이터를 걸러 주는 계층이라고 설명합니다.
- **AI 코딩 에이전트 하네스**: 글은 AI가 코드를 만드는 속도가 사람의 검토 한계를 넘어서 관리되지 않는 자격 증명 경로와 취약점이 쌓인다고 말합니다. 해법으로 격리 샌드박스, 정적 분석(SAST)·린트·단위 테스트의 폐루프(closed-loop) 검증, 검증을 통과한 결과물만 올리는 배포 게이트웨이를 듭니다.

결론에서 글은 세 계층을 세 질문으로 요약합니다.
어떤 에이전트가 어떤 범위의 인프라 접근 권한을 갖는가(신원),
어떤 맥락과 데이터 제약 아래에서 판단하는가(컨텍스트 플랫폼),
실행 결과물이 시스템의 안전성과 무결성을 해치지 않는가(하네스)입니다.
그리고 제어 평면의 성숙도가 자율형 엔터프라이즈로 전환하는 핵심 척도가 된다고
맺습니다.

## 분석

### 세 계층은 서로 다른 시점에 개입한다

글의 세 질문은 에이전트 실행의 서로 다른 시점에 대응합니다.

| 계층            | 개입 시점                | 통제 대상                   | 글이 제시한 수단                       |
| --------------- | ------------------------ | --------------------------- | -------------------------------------- |
| 신원            | 시스템에 접근할 때       | 권한의 범위와 수명          | 동적 JIT 최소 권한                     |
| 컨텍스트 플랫폼 | 판단에 쓸 자료를 받을 때 | 입력 데이터의 범위와 정확성 | 온톨로지, 마스킹, 동적 필터링          |
| 하네스          | 결과물을 내보낼 때       | 산출물의 안전성             | 샌드박스, 폐루프 검증, 배포 게이트웨이 |

이렇게 놓으면 세 계층은 서로를 대신하지 못합니다.
권한을 줄여도 잘못된 데이터를 받은 에이전트는 잘못 판단하고,
데이터를 걸러도 만들어진 코드가 검증 없이 배포되면 위험은 남습니다.
이 구분이 글에서 가장 쓸모 있는 부분입니다.

### 같은 위험이 세 곳에서 다른 모습으로 나타난다

글은 세 항목 모두에서 '관리되지 않는 권한이나 데이터가 에이전트의 속도에 실려
퍼진다'는 같은 문제를 말합니다.
신원에서는 정적 서비스 계정과 영구 API 키가 프롬프트 주입(prompt injection)이나
로직 오류 때 곧바로 인프라 침해가 된다고 합니다.
컨텍스트에서는 벡터 검색(RAG)으로 광범위한 데이터를 주입하면 권한 초과 노출,
환각에 따른 컴플라이언스 위반, 토큰 비용 상승을 피할 수 없다고 합니다.
하네스에서는 사람의 수동 코드 리뷰만으로는 검토 병목이 생겨 에이전트 도입의
생산성 이점이 상쇄된다고 합니다.

### 하네스 항목이 다루는 병목은 사람의 검토 속도다

세 항목 중 하네스만 보안이 아니라 속도의 불균형에서 출발합니다.
글은 생성 속도가 검토 속도를 넘는 상황에서 사람 검토를 자동 검증으로 바꾸는 것을
해법으로 둡니다.
다만 글이 열거한 SAST, 린트, 단위 테스트가 사람 검토를 어디까지 대신하는지는
글에 나오지 않습니다.

## 비평

### 수치의 출처가 글 안에서 확인되지 않는다

글에는 링크가 하나도 없습니다.
25%, 80%, 60%라는 세 수치는 모두 가트너 전망으로 소개되지만 가트너 페이지로
이어지는 주소도, 산출 근거도 없습니다.
이 문서를 쓰는 동안 가트너 보도자료 주소를 직접 열어 보려 했으나 접속 확인
단계에서 막혀 읽지 못했습니다.
따라서 이 문서의 수치는 모두 글이 전한 그대로이며,
가트너 원문과 대조한 값이 아닙니다.

### 가트너의 말과 글쓴이의 해석이 섞여 있다

글은 첫 문단에서 가트너 발표가 '실행 환경 통제로의 완전한 전환'을 보여
준다고 씁니다.
그러나 이 표현이 가트너의 분류인지, 열 개 가운데 세 개를 고른 글쓴이의
해석인지는 글만으로 가릴 수 없습니다.
글이 가트너 발언으로 명시한 것은 두 개의 전망 수치와 'AI가 소프트웨어를 만드는
속도가 인간의 검토 한계를 넘는다'는 언급뿐입니다.
JIT 권한, 온톨로지, 마스킹, SAST와 배포 게이트웨이 같은 구체적 구성은 글쓴이의
설계 제안으로 읽는 편이 안전합니다.

### 수치의 조건이 글에서 느슨하다

'최대 80%', '최대 60%'는 상한이며 평균이나 중앙값이 아닙니다.
글은 이 수치가 어떤 비교 대상에 대한 것인지,
시맨틱 체계를 우선한다는 것이 무엇을 뜻하는지 밝히지 않습니다.
25%도 '침해 사고의 25%가 에이전트 오용에서 비롯된다'는 한 문장이며,
어떤 집단의 침해를 세는지는 나오지 않습니다.

### 구현 사례와 비용이 없다

세 계층을 모두 갖추는 데 드는 비용, 순서,
기존 IAM 체계와의 연결 방법은 다루지 않습니다.
글이 말하는 온톨로지 구축이 데이터 팀에게 얼마나 큰 일인지도 없습니다.
하나만 먼저 도입한다면 무엇부터인지에 대한 판단이 빠져 있어 실행 계획으로 쓰기는
어렵습니다.

## 인사이트

### 1. 세 질문을 점검표로 쓸 수 있다

글의 가장 재사용하기 좋은 부분은 세 질문입니다.
에이전트를 운영하는 팀은 각 에이전트에 대해 이 세 질문에 한 문장씩 답해 볼 수
있습니다.
답이 비어 있는 칸이 그 에이전트의 통제 공백입니다.

### 2. 가장 먼저 볼 곳은 에이전트가 쥔 영구 자격 증명이다

글이 위험의 직접 경로로 꼽은 것은 광범위한 권한의 정적 서비스 계정과 영구 API
키입니다.
이 점검은 가트너 수치의 진위와 상관없이 지금 확인할 수 있습니다.
에이전트에 발급된 키 중 만료가 없거나 작업 범위보다 넓은 것이 있다면,
글의 논리에서 이것이 가장 먼저 고칠 항목입니다.

### 3. 결론이 바뀔 관찰

글의 중심 주장은 모델 선택보다 제어 평면의 성숙도가 중요하다는 것입니다.
같은 모델을 쓰는 두 조직이 제어 계층의 유무에 따라 사고율이나 비용에서 뚜렷하게
갈린다는 측정이 나오면 이 주장은 강해집니다.
반대로 제어 계층을 갖춘 조직에서도 사고율이 비슷하다면,
글이 말한 '핵심 척도'라는 평가는 약해집니다.
글은 이런 비교 자료를 제시하지 않으므로,
현재 이 주장은 근거가 아니라 제안으로 받아들이는 것이 맞습니다.
