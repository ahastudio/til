# 프롬프트가 아니라 환경을 고친다: 에이전트가 무너지지 않게 하는 하네스 설계 열아홉 항목

트윗: [Harness Engineering: The Complete Guide to Building AI Agents That Don't Fall Apart](https://twitter.com/LunarResearcher/status/2096570562625655088)

## 소개

Lunar(`@LunarResearcher`)가 2026년 9월 6일에 올린 Twitter Article이다.
읽는 데 9분이 걸린다고 표시되고, 조회수는 150만 회,
저자의 프로필은 AI engineer로 되어 있다.
글은 에이전트가 실패할 때 사람들이 프롬프트를 고치고, 모델을 바꾸고,
도구와 컨텍스트 창을 늘리는 것이 틀린 층을 만지는 일이라고 말한다.
많은 실패가 추론이 아니라 환경의 실패라는 것이다.
어떤 파일이 중요한지 몰랐고, 도구를 엉뚱한 곳에 썼으며,
지난 세션의 결정을 잃었고, 검사를 돌리지 않고 성공을 주장했고,
부분 실패 뒤에 같은 동작을 반복했고, 승인이 필요한 일을 할 권한이
있었다는 식이다.

글은 모델을 둘러싼 이 시스템을 하네스(harness)라고 부르고,
하네스 엔지니어링을 모델의 지능을 믿을 만한 작업으로 바꾸는 환경을 짓는
일이라고 정의한다.
프롬프트는 한 번의 시도를 바꾸고 하네스는 모든 시도를 바꾼다는 문장이
글의 핵심이다.
글은 이를 열아홉 항목으로 나누어 설명한다.
이 문서는 그 항목을 작업 순서에 맞게 다시 묶고,
구현 코드와 점검 방법을 더한 실무 노트다.
글의 주장과 이 문서의 해석을 구분하기 위해,
해석에는 “이 문서의 해석”이라고 적는다.

글이 제시하는 하네스의 구성 요소는 계약, 컨텍스트, 정책, 도구, 상태, 검사,
트레이스, 복구다.
모델은 이 안쪽의 추론 엔진이고, 하네스는 추론을 작동하게 만드는 나머지
전부라는 설명이다.
목표는 모델에서 불확실성을 없애는 것이 아니라 불확실성을 관찰하고 검증하고
복구할 수 있는 시스템 안에 가두는 것이다.

## 동작 방식

글의 항목을 한 번의 실행 순서로 늘어놓으면 흐름이 보인다.
이 순서는 글이 직접 제시한 것이 아니라 이 문서가 항목을 재배열한 것이다.

| 순서 | 단계      | 하네스가 하는 일                                | 글의 항목 |
| ---- | --------- | ----------------------------------------------- | --------- |
| 1    | 계약      | 모호한 요청을 범위, 제약, 수용 증거로 바꾼다    | 2         |
| 2    | 컨텍스트  | 작은 지도를 주고 필요할 때 세부를 가져오게 한다 | 3         |
| 3    | 행동      | 도구 게이트웨이가 인자와 경로를 검증한다        | 4, 9      |
| 4    | 상태      | 사실, 결정, 진행, 교훈을 명시적 상태로 저장한다 | 5, 6      |
| 5    | 검사      | 싼 결정론적 검사부터 돌리고 결과를 공격한다     | 7, 8      |
| 6    | 실패 처리 | 실패 종류를 분류하고 상한 안에서 복구한다       | 10        |
| 7    | 기록      | 트레이스와 변경 영수증을 남긴다                 | 12, 13    |
| 8    | 개선      | 실패를 센서, 규칙, 지도, 테스트로 바꾼다        | 11, 14    |

예시 하나로 흐름을 따라가 본다.
요청이 “온보딩 흐름을 개선해 줘”라면, 계약 단계가 이를 목표(이탈률 감소),
범위(가입 흐름과 분석), 제약(인증 변경 금지), 수용 조건(테스트 통과,
분석 이벤트 발생, 화면 캡처), 승인 필요 행동(프로덕션 배포,
마이그레이션)으로 바꾼다.
이 변환 뒤에 에이전트의 질문은 “다음에 무엇을 할까”에서 “계약한 결과 쪽으로
환경을 움직이는 행동은 무엇인가”로 바뀐다.
글은 계약이 없으면 에이전트가 그럴듯한 활동을 최적화하고,
계약이 있으면 검증된 완료를 최적화한다고 말한다.

컨텍스트는 한꺼번에 쏟아 붓는 대신 점진적으로 공개한다.
작업에서 프로젝트 지도, 관련 하위 시스템, 정확한 파일,
지역 지시 순으로 좁혀 간다.
글은 컨텍스트 컴파일러가 항상 필요한 것, 나중에 가져올 것, 낡은 것, 요약할 것,
원문 그대로 둘 것을 가려야 한다고 하며,
목표는 최대 컨텍스트가 아니라 토큰당 최대 신호라고 한다.

행동은 모델이 의도를 정하고, 게이트웨이가 행동을 검증하고, 도구가 환경을 바꾸고,
센서가 결과를 관찰하는 네 갈래로 나뉜다.
글은 모델이 행동을 제안할 수는 있지만 실행해도 될 만큼 유효한지는 게이트웨이가
정한다고 한다.
상태 쪽에서는 대화 기록이 믿을 만한 메모리가 아니라 이벤트 스트림이라는
점이 출발점이다.
유용한 기억은 사실, 결정, 진행, 교훈 네 범주의 명시적 상태로 바뀌어야 하고,
원문 기록은 감사용으로, 컴파일된 상태는 실행용으로 따로 둔다.

검사는 완료의 정의를 모델의 말에서 환경의 변화로 옮긴다.
“버그가 고쳐졌다”는 실패하던 테스트가 통과하는 것,
“페이지가 동작한다”는 브라우저 흐름이 끝까지 도는 것,
“마이그레이션이 안전하다”는 드라이런과 롤백이 통과하는 것이 증거다.
글은 문법, 타입, 집중 테스트, 통합 테스트, 시각 또는 의미 검토,
사람 승인의 순서로 싼 것부터 돌리라고 한다.
컴파일러, 스키마, 체크섬, 쿼리, 테스트로 답할 수 있는 곳에는 다른 모델을 쓰지
말라는 규칙도 있다.

## 구현하기

글은 개념과 명세 양식만 주고 실행 코드는 주지 않는다.
아래는 이 문서가 글의 계약, 게이트웨이,
정책 항목을 최소한으로 구현한 파이썬 예시다.
글의 코드가 아니며, 구조만 글을 따른다.

### 작업 계약 검사

계약의 다섯 질문에 답이 비어 있으면 에이전트를 시작하지 않는다.

```python
from dataclasses import dataclass, field

@dataclass
class TaskContract:
    objective: str = ""
    scope: list[str] = field(default_factory=list)
    constraints: list[str] = field(default_factory=list)
    acceptance: list[str] = field(default_factory=list)
    approval_required: list[str] = field(default_factory=list)

    def missing(self) -> list[str]:
        # 수용 증거가 없으면 완료를 판정할 수 없으므로 반드시 요구한다
        gaps = []
        if not self.objective:
            gaps.append("objective")
        if not self.scope:
            gaps.append("scope")
        if not self.acceptance:
            gaps.append("acceptance")
        return gaps

contract = TaskContract(
    objective="reduce onboarding drop-off",
    scope=["signup flow", "onboarding analytics"],
    constraints=["do not change authentication"],
    acceptance=["tests pass", "analytics event is emitted"],
    approval_required=["production deployment", "database migration"],
)
assert contract.missing() == [], contract.missing()
```

### 도구 게이트웨이와 정책

글의 네 위험 등급(낮음, 되돌릴 수 있음, 외부 영향,
되돌릴 수 없거나 민감함)을 코드로 옮긴다.
정책은 모델의 기억에 기대지 않도록 추론 루프 밖에 둔다.

```python
from pathlib import Path

WORKSPACE = Path("/work/project").resolve()
RISK = {
    "read_file": "low",
    "edit_file": "reversible",
    "run_tests": "reversible",
    "deploy": "external",
    "delete_data": "irreversible",
}

def authorize(tool: str, args: dict, approved: set[str]) -> tuple[bool, str]:
    risk = RISK.get(tool)
    if risk is None:
        return False, f"unknown tool: {tool}"
    path = args.get("path")
    if path is not None:
        # 작업 공간 밖 쓰기는 도구 계약의 사전 조건으로 막는다
        resolved = (WORKSPACE / path).resolve()
        if not resolved.is_relative_to(WORKSPACE):
            return False, "path outside workspace"
    if risk == "irreversible":
        return False, "hard gate: a person must run this"
    if risk == "external" and tool not in approved:
        return False, "approval required"
    return True, "ok"

print(authorize("edit_file", {"path": "src/a.py"}, set()))
print(authorize("edit_file", {"path": "../etc/passwd"}, set()))
print(authorize("deploy", {}, set()))
print(authorize("deploy", {}, {"deploy"}))
```

### 지속 상태와 변경 영수증

상태는 사실, 결정, 진행, 교훈의 네 칸으로 저장하고,
실행 끝에 시스템이 증명할 수 있는 것만 영수증으로 낸다.

```python
import json
from pathlib import Path

def save_state(path: str, facts, decisions, progress, lessons) -> None:
    Path(path).write_text(json.dumps({
        "facts": facts,
        "decisions": decisions,
        "progress": progress,
        "lessons": lessons,
    }, ensure_ascii=False, indent=2))

def receipt(objective, changed, verified, not_verified, risks) -> str:
    # 모델이 한 말이 아니라 실행된 검사의 결과만 VERIFIED에 넣는다
    lines = [f"OBJECTIVE\n{objective}", "CHANGED"]
    lines += [f"- {c}" for c in changed]
    lines.append("VERIFIED")
    lines += [f"- {v}" for v in verified]
    lines.append("NOT VERIFIED")
    lines += [f"- {n}" for n in not_verified]
    lines.append("RISKS")
    lines += [f"- {r}" for r in risks]
    return "\n".join(lines)

print(receipt(
    "Fix duplicate coupon application",
    ["checkout validation", "regression test"],
    ["unit tests passed"],
    ["production payment provider"],
    ["legacy mobile client unavailable locally"],
))
```

### 실패 종류별 복구

글은 재시도가 관련 조건을 하나라도 바꾸지 않으면 같은 실패를 비용을 내고
재현하는 것이라고 한다.
아래 표를 코드의 분기로 옮기면 된다.

| 실패 종류           | 다음 행동                   |
| ------------------- | --------------------------- |
| 도구 시간 초과      | 백오프 후 재시도            |
| 잘못된 인자         | 도구 호출을 고쳐 재시도     |
| 컨텍스트 부족       | 특정 출처를 가져온다        |
| 테스트 실패         | 실패한 동작을 조사한다      |
| 권한 거부           | 승인을 요청하거나 안전한 길 |
| 모순된 요구         | 사람에게 올린다             |
| 변화 없는 반복 실패 | 루프를 멈춘다               |

모든 루프에는 최대 시도 횟수, 최대 시간, 최대 비용, 최대 파괴 범위,
상위 보고 조건이라는 다섯 상한을 둔다.

## 값 정하기

글은 숫자를 하나도 주지 않는다.
다섯 상한과 점검 지표의 시작값은 독자가 정해야 하며,
아래는 이 문서가 제안하는 출발점이다.
근거는 각 값이 막으려는 실패이고, 측정 결과로 고쳐야 하는 가정이다.

| 값                 | 시작값                        | 근거와 조정 신호                                            |
| ------------------ | ----------------------------- | ----------------------------------------------------------- |
| 최대 시도 횟수     | 같은 실패 종류당 3회          | 변화 없는 반복을 멈추기 위한 값이며, 복구율이 낮으면 줄인다 |
| 최대 시간          | 작업 유형의 평소 소요의 3배   | 평소 소요를 먼저 측정해야 정할 수 있다                      |
| 최대 비용          | 사람이 한 번 검토할 가치 이하 | 검토 시간보다 비싼 실행은 이득이 없다                       |
| 자동 승인 등급     | 낮음, 되돌릴 수 있음          | 외부 영향부터 승인을 요구하며, 사고가 없으면 조정한다       |
| 컨텍스트 지도 크기 | 한 화면 분량                  | 지도가 길어지면 지도가 아니라 매뉴얼이 된다                 |

글이 권하는 지표는 수용된 산출물을 사람의 검토 시간과 실행 비용의 합으로
나눈 값이다.
함께 볼 것은 첫 시도 수용률, 도구 실패 뒤 복구율, 반복 실패율, 작업당 사람 개입,
근거 없는 완료 주장, 요청에서 검증된 결과까지의 시간,
구성 요소별 하네스 오버헤드다.
이 지표가 필요한 이유는 에이전트가 많이 활동해도 비싼 검토 작업만 만들어 낼 수
있기 때문이다.

## 트레이드오프

### 계약은 모호함을 없애지 않고 앞으로 옮긴다

계약을 쓰면 에이전트가 엉뚱한 곳으로 가는 일이 줄지만,
계약을 쓰는 비용이 사람에게 넘어온다.
수용 증거를 적으려면 과제를 이해하고 있어야 하며,
테스트로 옮길 수 없는 요구는 계약의 수용 칸에 들어가지 못한다.
“사용자가 덜 헷갈리게”처럼 판단이 핵심인 과제는 계약을 쓰는 순간
정의가 흔들린다.
이 문서의 해석으로는, 이런 과제에서는 수용 증거를 사람의 검토로 두고 그 사실을
계약에 적는 것이 정직한 선택이다.
얻는 것은 완료의 정의이고, 잃는 것은 착수 속도이며,
끝까지 남는 어려움은 판단이 필요한 과제를 기계적 검사로 바꿀 수 없다는 점이다.

### 하네스의 가드는 속도와 자유도를 비용으로 치른다

게이트웨이가 인자를 검증하고, 정책이 승인을 요구하고,
검사가 매 단계에 끼면 안전은 늘지만 실행은 느려지고 에이전트가 쓸 수 있는
전략은 줄어든다.
글은 이를 하네스 부패(harness decay)로 다루며,
지난 모델의 한계를 우회하려고 만든 장치가 모델이 나아진 뒤에도 남아 더 나은
전략을 막는다고 말한다.
처방은 각 구성 요소를 프로덕션 코드처럼 다루는 것이다.
어떤 실패를 막는지, 그 실패가 지금도 얼마나 자주 일어나는지,
지연과 복잡도를 얼마나 더하는지, 빼면 무엇이 일어나는지를 묻는다.
쉽게 놓치는 점은 가드를 뺀 실험이 가드가 있을 때보다 더 위험하다는 것이다.
그래서 빼는 실험은 되돌릴 수 있는 작업에서 먼저 하고,
가드의 필요를 보이는 지표(반복 실패율 등)를 미리 정해 둬야 한다.

### 적대적 검증은 비용을 두 배로 쓰고도 독립성을 보장하지 못한다

글은 같은 에이전트에게 같은 컨텍스트에서 다시 확인하라고 시키면 실수를 낳은
가정이 그대로 남는다고 하며, 검증자에게 거절 기준,
산출물과 수용 계약에 대한 접근, 필요하면 독립된 도구나 새 컨텍스트,
고치지 않고 거절할 권한을 주라고 한다.
이 설계는 효과가 있지만 두 가지 비용이 따른다.
검증자가 같은 모델이면 같은 맹점을 공유할 수 있고,
검증이 매번 도는 만큼 비용과 시간이 늘어난다.
그래서 결정론적 검사가 답할 수 있는 질문에는 검증자를 쓰지 않고,
모호함이 남는 부분에만 쓰는 것이 이 글의 규칙과 맞다.
검증자의 거절이 수용을 못 하게 만드는 순환(검증자가 계속 거절)을 막으려면 다섯 상한에 검증 라운드의 횟수도 넣어야 한다.

## 함정

### 지도가 매뉴얼이 된다

글은 작은 지도를 주라고 하지만, 지도에 항목을 하나씩 더하다 보면 어느새
컨텍스트를 쏟아 붓는 문서가 된다.
각 줄이 “이 작업에서 어디를 열어야 하는가”에 답하는지를 기준으로 줄을 지우는
점검이 필요하다.

### 영수증이 모델의 말을 옮겨 적는다

변경 영수증의 VERIFIED 칸에 모델이 한 말을 그대로 넣으면 영수증은 요약이 아니라
자기 보고가 된다.
이 칸은 하네스가 실행하고 결과를 본 검사만 채워야 하며,
모델이 쓴 항목은 NOT VERIFIED로 보내야 한다.
이 문서의 해석으로는 영수증을 코드가 만들고 모델은 RISKS와 DECISIONS 칸만 쓰게
하는 분업이 안전하다.

### 교훈이 쌓이기만 한다

글의 하네스 플라이휠은 실패를 센서, 규칙, 지도, 테스트,
도구 계약으로 바꿔 남긴다.
그런데 추가는 쉽고 삭제는 어려워서, 규칙이 늘어나면 시스템은 느려지고 경직된다.
글의 15번 항목이 이 문제의 해독제이며, 각 규칙에 막으려던 실패와 추가한 날짜를
적어 두면 삭제의 근거가 생긴다.

### 정책을 프롬프트에 두고 정책이라 부른다

글은 비밀을 노출하지 않기, 작업 공간 밖에 쓰지 않기, 비용 상한을 넘지 않기,
실행하지 않은 테스트를 통과로 표시하지 않기를 프롬프트 제안이 아니라
정책이라고 한다.
프롬프트에 적은 규칙은 정책이 아니라 바람이므로,
위반이 코드에서 불가능해야 정책이다.
점검 방법은 규칙을 어기라는 지시를 일부러 주고 시스템이 막는지 보는 것이다.

## 확인하기

글의 열일곱 번째 항목이 주는 하네스 명세 양식을 빈칸 점검에 쓸 수 있다.
명세는 계약, 컨텍스트, 도구, 상태, 정책, 검증, 복구,
관찰 가능성의 여덟 묶음이며, 비어 있는 칸이 있으면 에이전트는 자율적인 것이
아니라 즉흥으로 움직인다는 것이 글의 판정이다.

아래 스크립트는 명세 파일에서 빈 칸을 찾는 이 문서의 도구다.

```python
import re
import sys

SECTIONS = ["CONTRACT", "CONTEXT", "TOOLS", "STATE",
            "POLICY", "VERIFICATION", "RECOVERY", "OBSERVABILITY"]

def empty_fields(text: str) -> list[str]:
    empties = []
    section = ""
    for line in text.splitlines():
        head = re.match(r"\d+\.\s+([A-Z]+)", line.strip())
        if head and head.group(1) in SECTIONS:
            section = head.group(1)
            continue
        field = re.match(r"([a-z ,-]+):\s*$", line.strip())
        if field and section:
            empties.append(f"{section}.{field.group(1)}")
    return empties

if __name__ == "__main__":
    text = open(sys.argv[1]).read()
    gaps = empty_fields(text)
    print("OK" if not gaps else "EMPTY: " + ", ".join(gaps))
```

실제 효과는 다음 순서로 잰다.
먼저 하네스 없는 상태에서 같은 과제 열 개를 돌려 첫 시도 수용률과 사람의 검토
시간을 기록한다.
다음에 한 번에 한 구성 요소(계약, 게이트웨이,
검사 중 하나)만 더해 같은 열 개를 다시 돌린다.
구성 요소별 오버헤드를 함께 기록해야 15번 항목의 “빼면 무엇이 일어나는가”에
답할 수 있다.

## 비평

### 글은 실행 결과를 하나도 보여주지 않는다

글 전체가 개념 목록과 예시 조각이다.
쿠폰 중복 적용 예시도 영수증 양식을 보이기 위한 것이지,
실제 실행의 기록이 아니다.
첫 시도 수용률이 얼마나 올랐는지, 하네스를 더하기 전과 후의 반복 실패율이
어땠는지, 하네스가 지연을 얼마나 더했는지가 어디에도 없다.
글이 하네스 부패를 경고하며 구성 요소가 실제로 도움이 되는지 측정하라고 하는데,
정작 글의 열아홉 항목은 어느 것도 측정으로 뒷받침되지 않는다.
이 열아홉 항목이 서로 대체되는지, 어느 것부터 도입해야 효과가 큰지도 글은
말하지 않는다.

### 하네스의 정의가 너무 넓어 반증할 수 없다

글은 하네스를 모델을 둘러싼 계약, 컨텍스트, 정책, 도구, 상태, 검사, 트레이스,
복구라고 정의한다.
모델 밖의 거의 모든 것이 이 안에 들어가기 때문에,
어떤 실패도 하네스의 결함으로 설명할 수 있다.
모델이 정말 추론에 실패한 경우도 “하네스가 이를 감지하고 복구하지 못했다”로
읽을 수 있다.
글의 첫 단락이 많은 실패가 환경의 실패라고 하는데,
그 “많은”이 어느 정도인지는 제시되지 않는다.
이 주장이 틀렸음을 보이는 관찰은, 하네스를 충분히 갖춘 상태에서도 반복되는 추론
실패의 비율일 것이다.

### 글의 처방은 소규모 작업에 과하고 큰 작업에는 얇다

글은 마지막에 가벼운 프롬프트로 충분한 경우와 하네스가 필요한 경우를 구분한다.
그런데 열아홉 항목 대부분은 후자를 전제로 쓰여 있고,
최소 하네스의 여섯 단계도 각각이 얼마나 걸리는지 말하지 않는다.
반대로 큰 작업에서는 핵심 난제가 글에 없다.
여러 에이전트가 같은 상태를 쓰는 동시성, 상태 저장소 자체의 신뢰성,
검증자가 같은 모델일 때의 독립성은 다루지 않는다.
이 글의 하네스는 한 에이전트가 한 작업을 순서대로 하는 장면에 맞춰져 있다.

### 홍보와 저장 유도가 근거의 자리를 차지한다

글은 도입부에 Substack 구독 요청을 넣고, 끝에도 북마크, 팔로우, 구독,
공유 요청을 넣는다.
도입부의 안내는 “AI alpha”와 “글이 나오기 전에” 같은 표현으로 독자를 모으는
말투를 쓴다.
조회수 150만 회와 북마크 수는 글이 널리 읽혔다는 신호이지 이 항목들이 작동했다는
증거가 아니다.
글을 근거로 조직의 하네스를 바꾸려는 사람은 위의 측정 절차로 자기 환경에서
확인해야 한다.

## 체크리스트

- 에이전트를 시작하기 전에 목표, 범위, 제약, 수용 증거, 승인 필요 행동이 적혀 있는가.
- 수용 증거가 모델의 말이 아니라 환경에서 관찰되는 변화인가.
- 컨텍스트 지도의 모든 줄이 어디를 열어야 하는지에 답하는가.
- 도구마다 사전 조건, 성공 증거, 실패 시 동작, 위험 등급이 정해져 있는가.
- 작업 공간 밖 쓰기를 거부하는 검사가 도구 쪽 코드에 있는가.
- 승인이 필요한 행동을 모델이 건너뛰려 할 때 코드가 막는가.
- 사실, 결정, 진행, 교훈이 대화 기록과 따로 저장되는가.
- 싼 결정론적 검사가 모델 검증보다 먼저 도는가.
- 검증자가 거절만 하고 고치지 않을 권한을 갖는가.
- 재시도가 조건을 하나라도 바꾸는가, 변화 없는 반복 실패에서 루프가 멈추는가.
- 최대 시도, 시간, 비용, 파괴 범위, 상위 보고 조건이 모두 정해져 있는가.
- 변경 영수증의 VERIFIED 칸이 실행된 검사만 담는가.
- 하네스의 각 구성 요소가 막는 실패와 추가한 날짜가 기록되어 있는가.
- 수용된 산출물당 사람의 검토 시간과 실행 비용을 측정하고 있는가.

## 기억할 원칙

### 프롬프트는 판단을 설명하고 하네스는 불변 조건을 강제한다

글의 열한 번째 항목이 말하는 지시의 사다리는 설명, 체크리스트, 템플릿,
자동 검사, 강제 정책의 순서다.
반복해서 중요한 규칙은 가능한 한 아래로 내려야 한다.
“포매터를 쓰라”는 지시는 포매터를 자동으로 돌리는 것으로,
“계층을 넘어 import하지 말라”는 아키텍처 테스트로 바꾼다.
이렇게 내려간 규칙은 모델이 기억하는지에 의존하지 않으므로,
프롬프트에는 판단에 필요한 지역의 사정만 남는다.

### 복잡도는 관찰된 실패로 얻는다

글의 최소 하네스는 한정된 과제, 읽기 쉬운 환경, 통제된 행동, 지속 실행, 증거,
복구와 학습의 여섯 단계이며, 지금 겪는 실패를 없애는 가장 작은 층만 짓는다.
한 프롬프트에 가끔 설명이 필요하다는 이유로 멀티 에이전트 구조부터 시작하지
말라는 말이다.
각 층이 막는 실패를 이름으로 적어 두면,
그 실패가 사라졌을 때 층을 지울 근거도 같이 생긴다.
