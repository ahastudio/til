# 에이전트 AI로 돈을 버는 여섯 단계: 루프, 도구, 메모리를 갖춘 시스템을 측정 가능한 약속으로 판다

트윗: [AGENTES IA: LA GUÍA COMPLETA (monetiza hoy)](https://twitter.com/silvanrec/status/2090280285623464099)

## 소개

silvan(@silvanrec)이 2026년 8월 20일 Twitter에 올린 스페인어 장문 글이다.
10분 분량이며 조회수는 250만으로 표시된다.
같은 달에 에이전트 AI를 알게 된 두 사람을 대비하며 시작한다.
한 사람은 몇 주 동안 데모와 스레드만 보다가 마케팅 층에서 벗어나지 못한다.
다른 한 사람은 에이전트가 기술적으로는 도구와 상태를 가진 추론 루프임을 이해하고
첫 주부터 이를 인프라로 팔기 시작한다.
글은 둘의 차이가 재능이 아니라 구조를 이해하는 정도라고 말한다.

글이 약속하는 것은 지도다.
복잡도가 낮은 순서의 여섯 단계(Nivel 0에서 5)와 흔한 기술 오류, 범주별 도구
목록이다.
핵심 주장은 몇 줄로 줄일 수 있다.
에이전트는 LLM, 도구 호출(tool calling), 실행 루프, 메모리와 상태의 합이다.
이 넷이 없으면 긴 프롬프트가 붙은 챗봇이다.
처음에는 결정적(deterministic) 자동화에 LLM 호출을 하나만 넣어 팔고,
완전 자율 에이전트로 시작하지 말라고 권한다.
판매할 것은 GPT나 Claude를 붙였다는 사실이 아니라
응답 시간, 해결률, 주당 절감된 사람 시간 같은 서비스 수준 계약(SLA)이다.
관측 가능성(logs, tracing, evals)이 없는 에이전트는 제품이 아니라 데모이고,
가장 높은 가격은 다중 에이전트와 레거시 시스템 통합에 있다고 한다.

이 문서는 글의 주장을 그대로 따르지 않고,
글이 가르치는 작업을 따라 할 수 있게 정리하면서 근거가 부족한 곳을 짚는다.
글이 제시하는 금액이나 매출 수치는 없다는 점을 먼저 밝혀 둔다.

## 동작 방식

### 루프가 에이전트를 챗봇과 가른다

글은 에이전트를 인식, 추론, 행동, 관찰이 목표를 달성하거나 단계 한도에
닿을 때까지
반복되는 순환으로 정의한다.
모델이 어떤 도구를 부를지 정하고, 도구가 결과를 돌려주고,
모델이 다음 단계를 정한다.
이 반복이 없으면 한 번 답하고 끝나는 챗봇이다.

글이 강조하는 한도는 코드로 쓰면 이렇다.
아래 예는 실제 모델 호출 자리를 가짜 함수로 두어 그대로 실행되며,
단계 한도와 비용 한도, 실행 기록이라는 글의 세 권고를 담았다.

```python
import json

# 도구는 이름, 설명, 실행 함수를 한곳에 모은다.
# 모델은 설명을 보고 어떤 도구를 부를지 정한다.
TOOLS = {
    "lookup_order": {
        "description": "주문 번호로 배송 상태를 조회한다",
        "fn": lambda order_id: {"order_id": order_id, "status": "shipped"},
    },
}


def fake_model(messages):
    """실제 LLM 호출을 흉내 낸다.
    사용자 질문만 있으면 도구를 부르고, 도구 결과가 있으면 답한다."""
    last = messages[-1]
    if last["role"] == "user":
        return {"tool": "lookup_order", "args": {"order_id": "A-1001"}, "cost": 0.002}
    status = json.loads(last["content"])["status"]
    return {"answer": f"주문 상태: {status}", "cost": 0.001}


def run_agent(question, max_steps=5, max_cost=0.05, log_path="agent_trace.jsonl"):
    messages = [{"role": "user", "content": question}]
    spent = 0.0
    with open(log_path, "a", encoding="utf-8") as log:
        for step in range(1, max_steps + 1):  # 단계 한도: 무한 루프를 막는다
            out = fake_model(messages)
            spent += out["cost"]
            # 모든 단계를 남긴다. 실패해도 무슨 일이 있었는지 추적할 수 있다.
            log.write(json.dumps({"step": step, "out": out, "spent": spent},
                                 ensure_ascii=False) + "\n")
            if spent > max_cost:  # 비용 한도: 청구서가 오기 전에 멈춘다
                return {"status": "stopped", "reason": "cost_limit", "spent": spent}
            if "answer" in out:
                return {"status": "done", "answer": out["answer"],
                        "steps": step, "spent": spent}
            result = TOOLS[out["tool"]]["fn"](**out["args"])
            messages.append({"role": "tool", "content": json.dumps(result)})
    return {"status": "stopped", "reason": "step_limit", "spent": spent}


if __name__ == "__main__":
    print(run_agent("A-1001 주문은 어디까지 왔나요?"))
```

### 도구, 프로토콜, 메모리, 검색 증강이 나머지 부품이다

글은 도구 호출을 모델이 실제 코드를 실행하는 수단으로 설명한다.
각 도구는 이름, 매개변수, 설명으로 된 스키마를 가지고,
모델이 이를 보고 언제 어떻게 부를지 정한다.
위 코드의 `TOOLS`가 그 구조의 가장 작은 형태다.

MCP(Model Context Protocol)는 글이 도구와 데이터 원천을 모델에 균일하게 노출하는
개방형 표준으로 소개한다.
글은 Anthropic, Google, OpenAI가 이를 채택하고 있다고 쓰는데,
이 문서는 그 채택 상황을 따로 확인하지 않았고 글쓴이의 주장으로 남긴다.
핵심 논리는 자기 도구를 MCP로 노출해 두면 모델이나 고객이 바뀌어도
통합을 다시 쓰지 않는다는 것이다.

메모리는 둘로 나뉜다.
대화 안의 단기 메모리와, 특정 사용자의 과거 상호작용을 기억하는 장기 메모리다.
장기 메모리는 보통 벡터 저장소나 키-값 저장소에 둔다.
글은 메모리가 없는 에이전트가 세션마다 같은 질문을 되풀이하는 것을
최종 사용자의 첫째 불만으로 꼽는다.
검색 증강 생성(RAG)은 고객의 문서를 색인해 두고
질문마다 관련 조각을 모델의 컨텍스트에 넣는 방식이다.
글은 나쁜 청킹이나 임베딩이 기술적으로는 돌아가는 에이전트를 망친다고 경고한다.

## 구현하기

글의 여섯 단계를 만드는 것과 파는 방식으로 나누면 이렇다.

| 단계    | 만드는 것                                               | 파는 방식                      |
| ------- | ------------------------------------------------------- | ------------------------------ |
| Nivel 0 | 구조 이해, 도메인 이점이 있는 사례 선택, 측정 목표 정의 | 첫 고객부터 유료               |
| Nivel 1 | 결정적 자동화에 LLM 호출 하나를 넣은 흐름               | 월 구독과 응답 시간 SLA        |
| Nivel 2 | 흐름 템플릿, 도메인별 프롬프트와 스키마 묶음, 색인 구조 | 제품 판매와 소규모 교육        |
| Nivel 3 | 스스로 도는 모니터링과 알림, 조사 자동화                | 구독                           |
| Nivel 4 | 레거시 연동, 다중 에이전트, 성숙도 진단, 관측 서비스    | 고액 프로젝트와 정기 유지 보수 |
| Nivel 5 | 버전 관리, 도메인별 템플릿 틀, 원가 측정                | 가격 인상과 복제 가능한 구조   |

Nivel 1의 사례는 글이 구체적으로 든다.
웹훅으로 받은 메시지를 LLM이 의도(가격 문의, 주문 상태, 불만)로 분류하고,
분류에 따라 결정적 흐름이 동작하거나 사람에게 넘기는 일차 상담 봇이 첫째다.
둘째는 문서를 색인해 출처를 인용하며 답하는 조사 요약 에이전트다.
셋째는 채팅으로 서너 가지를 묻고 구조화된 출력으로 예산과 긴급도를 뽑아
점수로 영업 인력에게 넘길지 정하는 리드 선별이며,
넷째는 CRM의 상태를 읽고 알림을 보내는 후속 에이전트다.
글은 이 단계를 이번 주에 돈을 받을 수 있는 것이라고 부른다.

첫 고객을 얻는 방법은 에이전트 AI를 파는 것이 아니라
측정 가능한 병목을 진단해 그것을 푸는 흐름을 제안하는 것이다.
응답 시간, 이탈률, 반복 업무에 쓰는 사람 시간이 병목의 예다.

## 값 정하기

글은 무엇을 팔지 말하면서도 얼마를 받을지는 한 번도 숫자로 말하지 않는다.
가격에 대한 문장은 SLA로 팔라는 것,
용량 포화를 느끼기 전에 가격을 올리라는 것,
고객별 원가(토큰, 유지 보수 시간, 사고)를 매출과 견주라는 것뿐이다.

가격의 근거가 될 지표는 글이 이미 가리킨다.
아래 표는 글의 지표에 이 문서가 측정 방법을 덧붙인 것이다.

| 지표                  | 측정 방법                                 | 가격에 쓰는 법                              |
| --------------------- | ----------------------------------------- | ------------------------------------------- |
| 첫 응답 시간          | 요청 수신과 첫 응답 사이의 시간을 기록    | 도입 전후 차이를 보고 SLA 수준을 정함       |
| 해결률                | 사람에게 넘기지 않고 끝난 요청의 비율     | 비율이 낮으면 구독가를 낮추거나 범위를 줄임 |
| 주당 절감된 사람 시간 | 도입 전 반복 업무 시간에서 도입 후를 뺌   | 절감 시간에 시간당 비용을 곱해 상한을 잡음  |
| 고객별 원가           | 토큰 비용, 유지 보수 시간, 사고 처리 시간 | 매출에서 빼서 남는지 확인                   |

가격의 상한을 고객이 절감한 비용으로 잡고 그 일부를 받는다는 기준은
글이 제시한 것이 아니라 이 문서의 제안이다.
도입 전 기준 시간을 받아 두지 않으면 절감 시간을 증명할 수 없으므로,
첫 주에 기준값을 기록하는 일이 가격 협상의 전제가 된다.

## 트레이드오프

### 결정적 흐름에 모델 호출 하나를 넣는 쪽이 안전하지만 한계가 있다

글은 처음에는 결정적 자동화에 LLM 호출 하나를 넣으라고 한다.
오류가 날 수 있는 면이 작고 팔기 쉽기 때문이다.
이 선택은 얻는 것이 분명하다.
어디서 틀렸는지 추적할 수 있고, 모델이 틀려도 분류 한 곳에서만 틀린다.

그러나 얻지 못하는 것도 있다.
결정적 흐름은 처음 설계한 분기 밖의 상황을 처리하지 못한다.
고객 요청이 분류 체계에 들어맞지 않을 때 흐름은 사람에게 넘기는 것밖에 할
수 없다.
그래서 해결률이 어느 수준에서 막히는데,
그 한계를 넘으려면 자율성을 늘려야 하고 그때 오류의 면이 넓어진다.
이 둘 사이를 오가는 지점이 이 글이 가르치는 설계의 핵심이다.

### 다중 에이전트는 가격이 높은 대신 실패가 부분적으로 일어난다

글은 가장 높은 가격이 다중 에이전트와 레거시 통합에 있다고 한다.
이유는 이 영역에서 노코드 도구와 경쟁하지 않기 때문이다.
그러나 에이전트가 여럿이면 일부만 실패하는 상황이 생긴다.
데이터를 조회하는 에이전트는 성공했는데 검증하는 에이전트가 실패하면
이미 한 일을 되돌릴지 이어 갈지를 설계해야 한다.

글도 이 부분이 비싸게 지불되는 지점이라고 인정한다.
그러므로 비용이 높은 것은 에이전트의 수 때문이 아니라
부분 실패를 다루는 설계가 어렵기 때문이다.

### MCP로 도구를 노출하면 이식성을 얻는 대신 표준에 의존한다

자기 도구를 MCP로 노출하면 모델을 바꿀 때 통합을 다시 쓰지 않는다.
대신 표준이 바뀌거나 고객의 모델 제공자가 이를 지원하지 않으면 그 이점이
사라진다.
글은 MCP를 배우는 것이 현실의 경쟁 우위라고 하지만,
이 우위가 얼마나 오래 가는지는 표준의 채택에 달려 있다.

## 비평

### 수익을 약속하는 제목에 수익을 보이는 숫자가 없다

제목은 오늘 돈을 번다고 하고 도입부는 무엇을 얼마에 받는지 지도를 주겠다고 한다.
그러나 본문에는 가격, 월 구독료, 고객 수, 매출이 하나도 없다.
있는 숫자는 응답 시간을 4시간에서 2분으로 줄인다는 가상의 예와
RAG가 에이전트 유용성의 80%라는 문장이다.

80%의 근거는 제시되지 않는다.
기준이 무엇이고 누가 어떻게 측정했는지 알 수 없는 수치다.
Nivel 4에서 고객 한 명이 Nivel 1의 열 명만큼의 가치가 있다는 문장도 같다.
이 주장을 가장 강하게 세우려면 단계별로 실제 계약 금액과 고객당 투입 시간을
보여야 하는데, 글에는 그것이 없다.
글을 따라 했을 때 수익이 난다는 증거는 이 글 안에 없다.

### 도구의 권한과 안전은 다루지 않는다

글의 오류 목록은 한도 없는 루프, 관측 부재, 부적절한 청킹, 버전 관리 부재,
과한 아키텍처다.
여기에 에이전트가 어떤 권한으로 도구를 부르는지는 빠져 있다.
Nivel 4에서 에이전트를 고객의 ERP나 CRM에 연결하라고 하면서
쓰기 권한을 어디까지 줄지, 잘못된 호출을 어떻게 되돌릴지는 말하지 않는다.

외부 문서를 읽어 도구를 부르는 에이전트는 문서 안에 숨은 지시에 속을 수 있다.
이 위험은 글의 RAG 설명과 에이전트가 메일을 보내는 도구를 부르는 예가 만나는
자리에 있다.
이 위험이 글에서 빠진 것은 이 문서의 판단이며,
글쓴이가 다루지 않았다는 사실 이상은 주장하지 않는다.

### 시장성과 도메인 이점을 한 문장으로 가른다

글은 사례를 시장 잠재력이 아니라 도메인 이점으로 고르라고 권한다.
조언 자체는 합리적이지만 근거가 없다.
도메인을 아는 사람이 더 좋은 에이전트를 설계한다는 것과
그 사람이 수익을 낸다는 것은 다른 이야기다.
도메인 이점이 있는 분야의 시장이 작으면 이 조언은 고객 수에서 막힌다.
글은 이 가능성을 다루지 않는다.

## 함정

글이 직접 꼽는 실수 여섯 가지는 이렇다.

1. 긴 프롬프트를 에이전트로 착각한다. 도구 호출과 결정 루프가 없으면
자율성이 없다.
2. 단계와 비용의 한도를 두지 않는다. 에이전트가 루프에 빠지면 청구서가 오기
전까지 아무도 모른다.
3. 관측성을 고객이 불평한 뒤로 미룬다. 로그가 없으면 운영 중 오류를 추측으로
고쳐야 한다.
4. 맥락 구조가 중요한 법률, 의료, 기술 문서에 일반적인 청킹을 쓴다.
5. 프롬프트와 흐름을 코드가 아닌 버릴 설정으로 다룬다.
6. 결정적 자동화로 풀리는 문제에 복잡한 다중 에이전트를 쓴다.

여기에 글이 한 줄로만 언급하는 함정이 있다.
첫 고객에게 에이전트를 무료로 주면 데모 피드백만 얻는다는 것이다.
이는 가격보다 피드백의 질에 관한 말이다.

## 확인하기

위의 코드를 `agent.py`로 저장하고 실행하면 `status`가 `done`인 결과가 나오고
같은 디렉터리에 `agent_trace.jsonl`이 생긴다.
기록 파일의 각 줄이 한 단계이며, 비용이 누적되는 것을 볼 수 있다.

한도가 작동하는지는 `max_cost`를 `0.001`로 낮춰 실행해 확인한다.
첫 단계의 비용이 한도를 넘으므로 `reason`이 `cost_limit`인 결과가 나와야 한다.
`max_steps`를 `1`로 낮추면 도구 호출 뒤 답하기 전에 `step_limit`으로 멈춘다.
기록 파일에서 멈춘 단계가 보이는지가 관측성의 가장 작은 시험이다.

## 체크리스트

- 고객에게 약속하는 지표가 숫자(응답 시간, 해결률, 절감 시간)로 적혀 있는가?
- 도입 전 기준값을 첫 주에 기록했는가?
- 에이전트 실행에 단계 한도와 비용 한도가 있는가?
- 모든 단계가 기록 파일에 남고, 실패가 알림으로 나에게 먼저 오는가?
- 프롬프트, 함수 스키마, 흐름이 git으로 버전 관리되는가?
- 결정적 자동화로 풀리는 부분과 모델이 필요한 부분이 나뉘어 있는가?
- 에이전트가 도구를 부를 때 쓰는 권한이 최소로 제한되어 있는가?
- 고객별 원가(토큰, 유지 보수 시간, 사고)가 매출과 따로 계산되는가?

## 기억할 원칙

### 판매하는 것은 모델이 아니라 측정된 결과다

글의 가장 단단한 문장은 GPT나 Claude를 붙였다고 팔지 말고 SLA를 팔라는 것이다.
모델은 바뀌지만 약속한 지표는 고객과의 관계에서 유지된다.
지표가 없으면 가격을 정할 근거도, 개선했는지 증명할 방법도 없다.
따라서 어떤 단계에서 시작하든 첫 주에 기준값을 기록하는 것이 먼저다.

### 관측할 수 없는 에이전트는 운영할 수 없다

한도, 기록, 알림은 글이 반복해서 강조하는 세 가지다.
위의 짧은 코드에도 이 셋이 들어간다.
이 셋이 없으면 에이전트가 실패했을 때 고객이 먼저 알게 되고,
그때부터는 기술의 문제가 아니라 신뢰의 문제다.
