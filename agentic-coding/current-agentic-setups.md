# 2026년 11월의 에이전트 환경: 기본 도구에 머무는 쪽과 직접 만드는 쪽으로 갈린다

Ask HN: [Ask HN: What's your current AI agentic setup?](https://news.ycombinator.com/item?id=50366117)

GN 토론: <https://news.hada.io/topic?id=36636>

## 요약

2026년 11월 4일 Hacker News에 올라온 이 질문은 이 문서를 쓴 시점에 390점,
440개 댓글을 받았다.
질문자 eggbrain은 사람들이 AI를 하루하루 어떻게 쓰는지 궁금하다며 질문 다섯
개를 적었다.
어떤 AI 구독을 직접 결제하는지, 구독 밖의 모델(종량제 API, OpenRouter,
로컬 모델)을 쓰는지,
어떤 코딩용 harness와 인터페이스를 쓰는지,
agent orchestration이나 swarm 도구를 쓰는지,
OpenClaw, Hermes Agent, Grok Bot, Dots,
Muse 같은 범용 에이전트 플랫폼을 쓰는지다.
모든 질문에 답할 필요는 없고 지금의 스냅샷을 보고 싶다고 했다.
내려받은 댓글 트리에서 질문자 본인의 댓글은 없었다.

답은 번호를 붙여 다섯 칸을 채우는 형식부터 장문의 설계 설명까지 다양하다.
스레드 전체에서 가장 자주 나오는 이름은 Claude(댓글 433개 중 208개)와
Codex(101개)다.
그다음으로 Pi 계열 harness(68개), OpenCode(64개),
DeepSeek(62개)가 많이 언급된다.
이 숫자는 API로 내려받은 댓글 트리(433개,
위의 댓글 수와 다른 이유는 확인하지 못했다)에서
이름을 글자로 검색해 센 값이며,
같은 댓글이 여러 이름을 함께 말하므로 합산할 수 없다.
orchestration이나 swarm이라는 단어가 든 댓글은 78개인데,
그중 상당수는 쓰지 않는다는 답이어서 사용자 수의 근거가 되지 못한다.

구독 쪽에서는 월 100~200달러의 Claude와 Codex 상위 요금제를 겹쳐 쓰는 답이 많다.
반대편에는 월 10달러 안팎의 OpenCode Go나 DeepSeek Flash 종량제로
충분하다는 답과,
구독을 끊고 로컬 모델만 쓴다는 답이 있다.
병렬로 돌리는 세션의 수는 하나(사람의 처리량이 한도라는 이유)부터
카드 200장을 20대에 나눠 돌리는 구성까지 벌어져 있다.
AI를 쓰지 않는다는 답도 여러 개 있다.

## 분석

### 기본 도구를 쓰는 쪽은 설정을 줄이는 방향으로 움직였다

스레드 맨 위에 놓인 답은 설정을 늘리는 대신 줄인 경험이다.
thefourthchime은 Cursor와 Codex를 거쳐 지금은 Claude Code 데스크톱만 쓰며,
skills를 모두 지우고 추론 강도를 medium으로 둔다고 적었다.
요구는 막연하되 높은 수준으로 말하고,
가장 큰 요령은 끝난 상태가 어떤 모습인지 구체적으로 알려 주는 것이라고 했다.
서브에이전트(subagent)는 에이전트가 알아서 만들어 주므로 직접 관리하지 않는다고
한다.[^thefourthchime]

l9o도 같은 방향이다.
l9o는 복잡한 orchestration 도구나 OpenClaw,
Hermes 같은 플랫폼의 필요를 느끼지 못했다고 했다.
에이전트끼리 서로 메시지를 보낼 수 있게 되었으므로,
컨텍스트 창이 큰 Opus 세션 하나와 대화하고 그 세션이 나머지 세션과 이야기하게
둔다는 것이다.
Codex를 직접 쓰는 일은 줄었고, 대부분 Claude가 Codex를 대신 호출하며,
이 위임은 이제 주로 토큰 사용량을 나누려는 목적이라고 했다.[^l9o]

이 두 증언에서 공통으로 읽히는 것은 orchestration을 사람이 설계하는 층이 아니라
모델과 기본 도구가 흡수하는 기능으로 본다는 점이다.
이것은 두 사람의 보고이고, 모든 작업에 해당한다는 근거는 아니다.

### 직접 만드는 쪽은 통제와 차별성을 이유로 든다

반대편은 기성 도구로는 부족하다고 보고 harness를 직접 만든 사람들이다.
Fordec은 Rust 중심의 자체 harness를 쓴다고 했다.
이 harness는 프로덕션 엔지니어링 관문(gate)을 두고 컨텍스트를 그래프 네트워크로
제어한다.
이유로는 취향(taste)이 중요해지는 시대라면 코드 생성에도 자기만의 취향이
있어야 하고,
누구나 내려받을 수 있는 도구만 쓰면 같은 도구를 가진 누구로든 대체될 수 있다는
점을 들었다.
최종 목표는 harness 요금이 API 요금에 가까워질 때 Claude Code를 버리는 것이고,
그때까지는 자동화할 수 있는 일을 전통적이고 효율적인 코드로 바꿔 통제권을
넓힌다고 했다.[^Fordec]

glennfiedler의 구성은 규모가 가장 크다.
Claude Ultra 구독 여러 개, 월 500달러 Codex 구독 여러 개,
Antigravity와 종량제 DeepSeek 등을 섞어 쓰고,
Redis 기반의 단순한 메시지 버스 nova-bus로 모델과 harness 사이를 조율한다.
일이 그 이상 늘면 스프린트 카드 체계를 쓰며,
카드 200장을 tailscale과 ssh로 묶은 20대에서 병렬로 돌린다고 했다.
처리량은 높지만 서로 격리되어 일한 모델들의 결과물이 이것저것 섞인 모음
같아지므로,
마지막에 사람이 모델과 직접 작업해 정리하고 보강해야 한다고도 적었다.
반면 여러 모델과 harness가 코드베이스를 검토하게 하면 서로 다른 것을 잡아내
품질이 크게 오른다고 했다.[^glennfiedler]

기본 도구 쪽과 직접 만드는 쪽의 차이는 설정의 양보다
병렬 작업을 누가 감당하느냐에서 갈린다.
기본 도구 쪽은 한 사람이 감당할 수 있는 만큼만 돌리고,
직접 만드는 쪽은 사람이 감당하지 못하는 부분을 도구가 맡도록 만든다.

### 병렬이 늘면 병목은 모델이 아니라 읽는 사람으로 옮겨 간다

teekert는 Claude Code Pro로 Opus와 함께 데이터 모델과 역할 기반 접근 제어를
설계하고 있다고 했다.
속도와 코드 품질은 놀랍지만 끊임없는 결정과 장단점을 적은 긴 글을 처리해야 해서,
몰입해 직접 코드를 쓸 때보다 즐겁지 않고 에이전트 수십 개를 돌리는 모습은
상상하기 어렵다고 했다.
스스로 무엇이 틀렸는지, 시스템을 더 믿어야 하는지 물었다.[^teekert]

laurasg는 틀리지 않았고 압도적인 것이 당연하다고 답했다.
시스템을 더 믿는다고 해결되지 않으며,
지금의 코딩은 핵심 인프라를 유지하는 일에 가까워서 에이전트가 내리는
임의의 결정이
돈과 보안에 미칠 영향을 계속 지켜봐야 한다고 했다.
Claude가 몰래 내린 결정이 우연히 토큰도 더 쓰게 만든 사례를 여러 번 봤다고
적었다.[^laurasg]

이 대화는 같은 스레드에서 월 수백 달러를 쓰는 답들과 대조된다.
teekert는 월 수백 달러를 쓰는 사람들은 이미 채워진 백로그가 있어서 결정의 부담을
덜 느끼는 것일지도 모른다고 추측했다.
이 추측은 검증되지 않았다.
다만 병렬 규모가 사람이 처리하는 결정의 수에 묶인다는 점은 teekert와 laurasg의
답에서 공통으로 확인된다.

## 비평

### 이 스레드는 많이 쓰는 사람의 표본이라 보통 사용자를 대표하지 못한다

글을 올린 사람들은 자기 구성을 설명하고 싶은 사람들이다.
여러 구독을 겹쳐 쓰거나 harness를 직접 만든 사람은 길게 쓰고,
기본 도구만 쓰는 사람이나 쓰지 않는 사람은 한 줄로 답하거나 아예 답하지 않는다.
따라서 앞에서 센 언급 횟수는 사용자 분포가 아니라 쓰고 싶은 사람의
분포에 가깝다.
질문 자체도 OpenCode, Pi, Muse Code, Gas Town 같은 비주류 이름을 예로 들어
이미 이 도구들을 아는 독자를 불러 모았을 가능성이 있다.

이 표본에서 말할 수 있는 것은 이 정도다.
이 커뮤니티에서 병렬 작업과 harness 직접 제작이 드물지 않게 관찰된다는 것,
그리고 가격에 민감한 선택지(DeepSeek, OpenCode Go,
로컬 모델)가 널리 퍼져 있다는 것이다.
그 이상을 일반 개발자 전체로 확장하는 것은 근거 없는 일반화다.

### 구성 목록은 결과가 아니라 선택을 보여 준다

질문은 무엇을 쓰는지 물었지, 무엇을 얻었는지 묻지 않았다.
그래서 답의 다수는 효과를 확인할 수 없는 자기 보고다.
saulpw는 많은 사람과 회사가 토큰을 열 배 쓰고 개선은 10퍼센트 정도만 얻고 있다고
짐작하면서,
에이전트가 하는 일을 조금 들여다볼 의지가 있다면
Opus와 가끔 쓰는 Fable만으로 최대 요금제 하나가 아주 효과적이라고 했다.[^saulpw]
이 말은 스레드의 많은 구성을 낭비로 본다는 뜻이지만,
열 배와 10퍼센트라는 수치의 출처는 밝히지 않았다.
같은 이유로 saulpw의 말도 하나의 주장이지 측정이 아니다.

OSaMaBiNLoGiN의 답은 더 극단적이다.
그는 컴퓨터에 일을 시키고 하루 종일 비디오 게임을 한다고 적었다.
에이전트 구성을 다듬는 일은 0.5~1퍼센트의 개선을 좇는 곁가지
논쟁(bikeshedding)이라고 짐작했다.
또 10대부터 15년 넘게 몰두한 방식의 일이 더는 요구되지 않아 계속 매달릴 이유를
찾지 못한다고 했다.[^OSaMaBiNLoGiN]
이 답에는 반론이 달렸다.
다른 댓글은 Opus 5.5가 만든 풀 리퀘스트를 오전 내내 고쳤는데 요구 사항을 일부
따르지 않고 의존성을 무시한 채 많은 것을 처음부터 새로 만들었다고 답했다.
결국 같은 도구에 대한 평가가 정반대로 나오고,
그 차이를 가르는 기준은 스레드 안에서 확인되지 않는다.

### 모델 세대가 바뀌면 이 목록의 유효기간도 끝난다

스레드의 구성은 특정 모델과 요금제를 전제로 한다.
Opus 5.5, GPT 5.6 계열, DeepSeek 4.1 Flash 같은 이름이 곳곳에 나오고,
요금제 한도가 줄었다는 불만도 여러 답에 나온다.
이 문서가 기록하는 것은 2026년 11월 초 하루의 스냅샷이며,
같은 질문을 석 달 뒤에 하면 결과가 달라질 가능성이 높다.
개별 제품 이름보다 그 구성이 왜 그렇게 정해졌는지가 오래 남는 정보다.

## 인사이트

### 설정이 쓸모를 유지하는 기간은 모델 세대보다 짧다

Aozora7은 덜 알려진 도구를 골라 깊이 설정하지 않는다고 했다.
지능의 대부분이 모델에 있고 모델이 빠르게 좋아져서,
복잡한 설정은 몇 달 안에 쓸모없어지며
유용한 동작은 결국 모델에 학습되고 유용한 기능은 모든 harness에 빠르게
들어간다는 이유였다.[^Aozora7]
thefourthchime이 skills를 지운 것도 같은 현상으로 읽힌다.

여기서 이끌어 낼 수 있는 결과는 설정이 한 번 만들면 계속 쓰는 자산이 아니라
모델이 좋아질 때마다 쓸모가 줄어드는 비용이라는 점이다.
같은 스레드의 Fordec은 반대로 자체 harness가 차별성의 원천이라고 했다.
두 입장이 모두 맞을 수 있는 조건은 설정의 종류에 있다.
모델이 대신 해 주기 시작하는 일(skills, 프롬프트 요령)은 쓸모가 빨리 줄고,
모델 밖에 있는 일(회사의 검증 절차, 권한 경계, 작업 기록)은 오래 남는다.
이것은 이 글의 추론이고 스레드가 직접 검증한 것은 아니다.

권고는 설정을 추가하기 전에 그것이 모델이 곧 흡수할 종류인지 모델 밖에 있어야
하는 종류인지 먼저 분류하라는 것이다.
앞의 종류는 가볍게 쓰고 버리며, 뒤의 종류만 투자한다.

### 맥락을 도구에 보관할지 사람 머릿속에 둘지는 품질 관리 방식의 선택이다

한 댓글은 몇 달 뒤 AI가 만든 코드를 다시 열 때 맥락을 어떻게
유지하느냐고 물었고,
여러 답이 HANDOFF 파일이나 작업 일지처럼 기록을 에이전트에게 쓰게 하는 방법을
내놓았다.
hypfer는 그렇게 하지 않는다고 했다.
맥락은 코드 자체에서 드러나야 하고, 그렇지 않다면 사람의 머릿속에 있어야 하며
잊었을 때 다시 적어야 한다는 것이다.
LLM에게 다시 설명해야 하는 일은 오히려 좋은데,
구조와 선택과 한계를 스스로 생각하게 되기 때문이라고 했다.[^hypfer]

두 접근은 같은 문제의 반대편 비용을 선택한다.
기록을 맡기면 재개 비용이 줄지만 사람이 코드의 이유를 잊을 위험이 생기고,
기억을 사람에게 두면 재개 비용이 늘지만 이해가 유지된다.
teekert와 laurasg가 말한 결정의 과부하를 함께 놓고 보면,
병렬 작업이 늘수록 기록을 맡기는 쪽으로 기울게 되고 그만큼 이해는 얕아지리라고
추론할 수 있다.
이 긴장은 스레드의 어느 답도 해소하지 못했다.
개인의 판단으로는 사람이 직접 책임지는 영역(보안,
데이터 모델)에만 사람의 기억을 고집하고,
나머지는 기록에 맡기는 구분이 현실적인 절충으로 보인다.

### 처리량이 검토 능력을 넘으면 품질 관리는 모델 사이로 옮겨 간다

glennfiedler는 높은 처리량이 대가로 모델 간 일관성 부족을 낳는다고 했고,
같은 사람이 여러 모델에 같은 코드를 읽히면 서로 다른 것을 잡아낸다고도 했다.
teekert는 사람의 처리량이 한도라고 했고,
laurasg는 에이전트의 몰래 한 결정을 걱정했다.
세 증언을 이으면 다음과 같이 읽을 수 있다.
