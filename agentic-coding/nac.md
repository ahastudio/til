# nac는 계획만 하는 오케스트레이터와 일하는 스레드, 구조화된 에피소드로 오래 걸리는 에이전트 작업의 맥락을 지키는 오픈소스 하니스이다

<https://github.com/arcee-ai/nac>

## 소개

nac는 Arcee가 공개한 Apache-2.0 라이선스의 에이전트 하니스(harness)이다.
Rust로 쓰였고 웹 클라이언트를 함께 제공하며, 저장소는 2026년 3월 28일에 만들어졌고 이
문서가 읽은 2026년 11월 13일에 별 303개와 포크 32개였다.
기본 브랜치는 `dev`이고, 안정 릴리스는 2026년 8월 27일의 v0.1.4이다.
설명은 오래 걸리는 야심 찬 일(실험, 훈련 실행, 인프라, 의도에서 벗어나면 안 되는 프로토타입)에
쓰는 하니스이다.

핵심 구조는 스레드와 에피소드이다.
중앙 오케스트레이터가 일을 계획하고 쪼개지만 명령을 실행하거나 파일을 고칠 수 없다.
할 수 있는 일은 스레드를 띄우는 것뿐이고, 스레드는 자기가 한 일의 구조화된 요약인
에피소드를 돌려준다.
README는 이 구조가 Random Labs의 Slate에서 영감을 받았고 nanocode와 pi에서도 아이디어를
얻었다고 밝힌다.
기술 설명은 Arcee 블로그 글(2026년 8월 13일)에 있다.[^blog]

### 설치와 시작

한 줄 설치 스크립트가 `nac-web`을 `$HOME/.local/bin`에 넣고, `nac-web`을 실행하면 기본
주소 `http://127.0.0.1:3210`에서 대시보드가 열린다.
에이전트에게 맡기는 방법도 있다.
이식 가능한 온보딩 스킬과 MCP 연동을 제공하므로, 설치 스크립트로 스킬을 설치한 뒤 에이전트에게
`nac-onboarding`을 읽고 설치와 설정과 MCP 연결을 안내하게 할 수 있다.
업그레이드는 `nac-web upgrade`이고 야간 후보는 `--pre-release`로 받는다.
모델 인증은 세 가지이다.
Arcee 기기 코드 로그인(권장), ChatGPT 계정 OAuth, 그리고 DeepSeek, Fireworks, Together,
OpenAI, Anthropic 등 카탈로그의 제공자용 API 키 환경 변수이다.
PR을 보내려면 CLA에 서명해야 한다.

## 동작 방식

### 스레드와 에피소드

블로그의 설명은 이렇다.[^blog]
오케스트레이터가 스레드에 구체적인 작업을 배정하면 새 워커가 시작된다.
워커는 새 프로세스와 새 모델 컨텍스트로, 워커 시스템 프롬프트와 요청된 작업, 도구,
프로젝트나 스킬의 지침을 받는다.
별도의 요약 단계는 없다.
워커 시스템 프롬프트가 모델의 마지막 응답을 다음 작업을 위한 간결한 인계(handoff)로
쓰게 지시하고, 도구 호출이 없는 응답이 나오면 그것이 에피소드이다.
이 시점에서 워커의 실행 컨텍스트는 버려져 모델 컨텍스트로 다시 쓰이지 않는다.
환경에 가한 변경은 남지만 작업의 영속적 표현은 에피소드이다.
스레드는 에피소드를 순서대로 모은 이름 붙은 집합일 뿐이다.

같은 스레드에 새 작업이 배정되면 새 워커가 시스템 프롬프트와 요청된 작업과 그 스레드에 이미
저장된 에피소드를 모두 받는다.
오케스트레이터는 다른 스레드의 에피소드도 컨텍스트로 줄 수 있다(Slate가 말하는 스레드
엮기, thread weaving).
nac는 이를 이름 붙인 원본 스레드의 가장 최근 에피소드로 풀이하고, 그 에피소드는 이번 작업의
컨텍스트로만 쓰일 뿐 대상 스레드에 들어가지 않는다.[^blog]

### 한 배치의 호출과 의존 그래프

오케스트레이터가 일을 내보낼 때는 턴을 끝내면서 스레드 호출의 배치를 낸다.
호출마다 필수 항목은 스레드 이름(`name`)과 자유 형식 지시(`action`, 한 가지로 한정된
행동을 서술하도록 의도됨)이고, 선택 항목은 원본 스레드(`threads`), 미리 불러올 스킬
(`skills`), 실행 시간 제한(`timeout`)이다.
같은 배치 안의 원본 스레드는 의존 간선을 만들어 먼저 실행되어야 한다.
nac는 중복 대상을 거부하고 실행 전에 그래프에 순환이 없는지 검증하며 순환이면 배치를 오류로
돌려준다.
독립적인 워커는 동시에 돌 수 있지만 오케스트레이터는 배치가 끝날 때까지 기다린 뒤 다시
계획한다.
성공한 스레드의 에피소드와 실패한 스레드의 오류가 오케스트레이터에 돌아가고, 원본이 실패한
의존 호출은 건너뛴다.
사용자의 조종 지시는 큐에 쌓여 오케스트레이터의 다음 모델 호출 때 전달되고, 진행 중인 호출이나
워커 배치를 중단하지 않는다.[^blog]

### 세 가지 세션 동작과 안전 계약

저장소의 `AGENTS.md`는 세션의 불변 동작 세 가지를 적는다.
기존의 오케스트레이터와 워커 구조(`orchestrator`), 지속되는 직접 코딩 에이전트와 전통적인
자식 세션(`direct`), 별도의 관리형 오케스트레이터 세션을 띄울 수 있는 직접 에이전트
(`direct-with-orchestrator`)이다.[^agents]
의존 방향은 안쪽을 향한다.
React 클라이언트 → HTTP/OpenAPI/MCP 전달(`nac-server`) → 응용 서비스 → 영속 하니스(`nac-core`)
순이고, 도메인 계약은 Axum이나 React나 제공자 와이어 타입에 의존하지 않는다.[^agents]
안전 계약으로 권한 평가의 순서, 강한 거부, 정규화된 리소스 결합, 헤드리스에서 닫히는 실패를
꼽고, 도구가 보이는 것은 권한이 아니라고 적는다.
로컬, SSH, 선택적 Podman 중 어느 실행 백엔드를 쓸지는 구성할 때 정해지며 승인이 백엔드를
바꾸거나 샌드박스를 벗어나게 하지 않는다.[^agents]

### 샌드박스

샌드박스 모드는 Podman이 필요하다.
현재 디렉터리가 git 저장소에 속하면 살아 있는 체크아웃 대신 `HEAD`에서 갈라낸 세션별 임시 git
worktree를 컨테이너의 `/workspace`에 마운트한다.
worktree는 nac 홈 아래 `worktrees/<세션 키>`에 있고 `nac/<세션 키>` 브랜치에서 돌며 세션을
지우면 함께 지워진다.
세션이 커밋하면 브랜치는 남는다.
저장소의 공유 git 디렉터리는 읽기 전용으로 마운트하고 세션의 worktree 메타데이터와 느슨한
ref와 객체 저장소만 읽기·쓰기로 덮어쓴다.
호스트의 git 설정과 훅은 읽기 전용이고, worktree는 `--no-checkout`으로 등록해 커밋된 파일을
Podman 안에서 펼치므로 호스트의 git 필터와 체크아웃 훅이 실행되지 않는다.[^sandbox]
worktree를 만들 수 없으면 살아 있는 쓰기 가능한 마운트로 폴백하면서 서버 stderr에 경고를
남기고, git의 쓰기 가능한 관리 경로에 심볼릭 링크가 있는 것처럼 검증할 수 없는 경우에는
폴백하지 않고 실행을 거부한다.[^sandbox]

### 모델 요청 보안

모든 모델 추론 클라이언트는 HTTP 리다이렉트를 끄고, 추가 헤더가 `Host`, `Authorization`,
`Proxy-Authorization`, `x-api-key`를 어떤 대소문자로도 덮어쓰지 못하게 한다.
사용자 정의 API 키 엔드포인트는 호스트 허용 목록 없이 모든 공개 HTTPS 기본 URL을 받아들이되
URL에 내장된 사용자 정보는 거부한다.
평문 HTTP는 루프백, 사설망, 링크 로컬 주소에만 기본으로 허용하고, 공개 HTTP는
`allow_insecure_http = true`로 명시해야 하며 문서가 의도적으로 위험하다고 적는다.[^model-req]

## 분석

### 중심 주장은 임시 컨텍스트와 영속 상태를 분리하자는 것이다

블로그는 에이전트가 수만 토큰을 읽고 고치며 디버깅하다 보면 사용자가 초기에 말한 세부를
잊거나 의도하지 않은 방식으로 일을 마칠 수 있다고 진단한다.
조사, 도구 출력, 실패한 시도, 변하는 계획, 큰 작업의 상태가 한 기록에 쌓이는 것은 해롭고,
긴 과제에서 모델 성능이 떨어지는 컨텍스트 부패(context rot)도 이 때문이라고 본다.
압축(compaction)은 과제 구조가 아니라 토큰 압력에 따라 일어나 중요한 세부를 버릴 수 있다고도
한다.[^blog]
nac의 해법은 둘을 나누는 것이다.
행동에 필요한 임시 컨텍스트는 워커가 쓰고 버리며, 작업 흐름을 이어 가는 데 필요한
영속 상태는 에피소드로만 남긴다.

### 오케스트레이터가 직접 일하지 못하게 해서 위임을 강제한다

오케스트레이터는 판단하고 길만 정하며 행동하지 않고, 워커는 행동하되 오케스트레이션 그래프를
넓히지 않는다는 분업이다.[^blog]
이 제약의 효과는 오케스트레이터의 컨텍스트가 계획에 쓰이는 정보로 유지된다는 것이다.
블로그의 예는 웹 앱의 성능을 최적화하는 일이다.
스레드 여럿이 코드베이스의 다른 부분을 병렬로 탐색하고 다른 스레드가 환경을 준비하면
오케스트레이터는 패키지 관리자 재시도 같은 실행 세부 없이 에피소드만 받는다.[^blog]
이것은 블로그의 설명이고 이 문서가 같은 과제로 비교한 것은 아니다.

### 하니스가 추론 런타임이 되고 있다는 시각

블로그는 하니스를 두 축(컨텍스트 풍부화와 행동 공간 확장)으로 진화해 왔다고 정리하고,
nac의 요소를 런타임 용어로 대응시킨다.
워커 호출은 추론 연산, 스레드는 영속 프로그램 상태, 에피소드는 커밋된 작업 흐름 갱신,
원본 스레드는 데이터 의존, 디스패치 배치는 동적 실행 그래프이다.
판단은 토큰에 두고 불변 조건은 런타임에 둔다는 문장으로 정리한다.[^blog]
이 대응은 저자의 개념 틀이고 설계의 일관성을 설명하는 데 쓸 수 있다.
예를 들어 DAG 검증과 순환 거부는 런타임이 지키는 불변 조건이다.

## 비평

### 효과를 보여 주는 측정이 없다

블로그와 README에는 nac를 쓴 작업과 단일 에이전트의 작업을 비교한 벤치마크나 사례 수치가
없다.
출시 글은 내부에서 실험과 훈련 감독과 인프라 작업에 쓰며 몇 시간에서 며칠에 이르는 세션이
있다고 하고, 타임랩스 영상을 보여 준다.[^blog]
근거로 든 것은 컨텍스트 부패에 대한 외부 보고서와 다른 하니스의 사례이고 nac 자체의 측정이
아니다.
이 문서가 읽은 범위에서 오케스트레이터와 스레드 분리가 토큰, 시간, 결함 중 무엇을 얼마나
줄이는지는 알 수 없다.

### 에피소드는 손실 요약이라서 보고의 정확성에 기댄다

워커의 컨텍스트가 버려지고 에피소드가 영속 표현이므로, 오케스트레이터는 워커가 마지막에 쓴
요약만 본다.
별도의 요약 단계가 없어서 에피소드의 질은 워커가 마지막 응답을 얼마나 정확히 쓰는지에
달려 있다.[^blog]
워커가 한 일을 과장하거나 빠뜨리면 이후 계획이 그 위에 쌓인다.
블로그가 인정한 한계도 있다.
워커의 실패는 트랜잭션이 아니어서 워커가 환경을 바꾼 뒤 최종 응답을 내기 전에 끝나면 변경은
남고 새 에피소드는 없으므로, 오류가 돌아왔다는 것은 환경이 영속 기록보다 앞서 있을 수 있다는
뜻이다.[^blog]
오케스트레이터에게 작업을 한정하라고 프롬프트로 요청하지만 런타임이 범위를 강제하지는
않는다.[^blog]
이 한계들은 블로그에 적혀 있다.
이 문서는 에피소드 정확성을 점검하는 장치가 하니스에 있는지는 확인하지 못했다.

### 단일 작업에는 오히려 느리고 도입 조건이 까다롭다

블로그는 하나의 집중된 변경에는 직접 하는 편이 더 간단하고 빠르다고 인정한다.
오케스트레이터가 직접 일할 수 없어서 스레드로 위임해야 하는 오버헤드가 있기 때문이다.[^blog]
nac가 잘 맞는 작업의 조건으로 의미 있는 상위 목표, 앞서 정한 경계와 안전 제약, 확인할 수 있는
완료의 정의, 병렬화할 만큼의 독립 작업, 하니스가 분해를 스스로 정할 자유를 든다.[^blog]
조건이 채워지지 않는 일에는 이득이 없거나 손해라는 뜻이다.

### 샌드박스의 폴백은 조용히 열린다

worktree 격리가 이 하니스의 중요한 안전 장치이지만 문서는 worktree를 만들지 못하면 살아 있는
체크아웃을 쓰기 가능으로 마운트하는 폴백이 있다고 적는다.
경고가 서버 stderr에 남을 뿐이라서 대시보드만 보는 사용자는 격리가 꺼진 것을 모를 수 있다.
문서도 이 경고를 고친 뒤에 worktree 격리를 믿으라고 말한다.[^sandbox]
또 Podman 경로는 선택 사항이고 MVP 한계가 있다.
프로세스가 컨테이너 ID 게시 직전에 죽으면 시작 복구가 소유권을 추측하지 않고 비공개 기록을
남기며, 이 충돌 구간은 결정적 기록 경계 시험은 있지만 실제 Podman에서 검증하지 않았다고
문서가 밝힌다.[^sandbox]

### 성숙도와 벤더 종속

안정 릴리스는 v0.1.4이고 후보와 야간 빌드가 계속 나온다.
블로그는 설치 스크립트가 현재의 에지(edge) 빌드를 설치한다고 적는다.[^blog]
권장 인증은 Arcee 로그인이고 PR은 CLA 서명이 필요하다.
다른 제공자의 API 키와 ChatGPT 로그인도 쓸 수 있으므로 종속이 강제는 아니지만 기본 경로가
Arcee의 모델 API이다.
이 문서는 설치하거나 실행해 보지 않았다.

## 인사이트

### 도입 판단은 작업의 모양으로 한다

블로그가 든 지표를 도입 전 질문으로 바꿀 수 있다.
이 일에 확인할 수 있는 완료의 정의가 있는가, 독립적으로 나눌 부분이 둘 이상인가,
안전 제약을 앞서 말할 수 있는가, 하니스가 분해를 정해도 되는가.
네 가지에 모두 그렇다고 답하면 nac류의 오케스트레이션을 시험할 만하고, 하나라도 아니면
직접 에이전트가 더 낫다.[^blog]
이 질문 목록은 블로그의 지표를 정리한 이 문서의 제안이다.

### 에피소드 형식을 내 에이전트 작업에도 가져다 쓴다

nac를 쓰지 않아도 아이디어는 옮길 수 있다.
하위 에이전트나 긴 세션을 끝낼 때 마지막 응답을 자유 형식 요약이 아니라 고정된 인계 형식으로
쓰게 하는 것이다.
이 문서의 제안은 항목을 다음 다섯으로 두는 것이다.
한 일, 바꾼 파일과 환경, 확인한 증거(명령과 출력), 확인하지 않은 것, 다음에 할 일이다.
이것은 이 문서의 제안이고 nac의 에피소드 스키마가 아니다.
이 문서는 nac의 실제 스키마를 확인하지 못했다.

### 오케스트레이터 아래의 환경은 worktree로 가둔다

에이전트가 쓰는 환경을 임시 worktree에 가두는 방식은 nac 밖에서도 쓸 수 있다.
호스트의 git 설정과 훅을 읽기 전용으로 두고 체크아웃을 컨테이너 안에서 펼치는 방법은 에이전트가
호스트의 훅을 실행하는 길을 막는다는 점에서 참고할 만하다.[^sandbox]
다만 폴백이 열려 있는지 확인하는 것이 먼저이다.

### 효과를 확인하는 관찰

같은 과제를 단일 세션과 오케스트레이션으로 번갈아 돌려 토큰, 소요 시간, 완료 기준 통과율,
에피소드와 실제 환경의 불일치 횟수를 비교하면 이 구조의 주장을 확인할 수 있다.
불일치가 잦으면 에피소드가 영속 상태로 믿을 만하지 않다는 뜻이고, 통과율이 같은데 토큰이
줄면 분리의 이득이 있다는 뜻이다.
이 비교는 이 문서의 제안이고 블로그가 제시한 것이 아니다.
