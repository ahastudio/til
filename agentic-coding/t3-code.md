## 소개

T3 Code는 스스로를
에이전트 하네스 제어판(agent harness control surface)이라고 부른다.
내 컴퓨터에 설치된 코딩 에이전트를 모바일 앱(iOS, Android)과 웹 앱,
Electron 기반 데스크톱 앱에서 조종하게 해 준다.
Claude Code, Codex, Cursor, Grok Build, OpenCode, Google Antigravity를
지원하고(README는 여기에 Kiro, Pi, Muse Code, fx와 ACP 에이전트를 더한다),
T3 Code 자신은 API 키를 받아 모델을 직접 호출하지 않고,
사용자의 컴퓨터에서 이미 로그인된 채로 실행 중인 에이전트 프로그램을
원격으로 조종할 뿐이다.
그래서 API 종량제 요금이 아니라 그 에이전트가 쓰던 구독 플랜의
사용량을 그대로 쓴다.

README는 무엇을 파는 것이냐는 물음에 아무것도 팔지 않는다고 답한다.
Codex 데스크톱 앱, Conductor, Claude Desktop, Cursor Glass 같은 기존 도구에서
영감을 받았지만 어느 것도 기준에 못 미쳐서 직접 만들었다는 설명이다.
원하는 것은 빠르고 원격에서 쓸 수 있고 진짜로 열려 있는 도구이며,
방향이 틀어지면 누구든 포크해서 원하는 편집기를 만들 수 있게 하겠다고 한다.

## 동작 방식

### 실행은 작업 공간이 있는 환경에 있고 클라이언트는 조종만 한다

문서의 아키텍처 개요는 핵심 설계를 한 문단으로 밝힌다.
실행은 작업 공간을 가진 환경이 맡고, 웹과 데스크톱,
모바일 클라이언트는 인증된 RPC로 그것을 조종한다.
에이전트 프로세스, 터미널, Git, 프로젝트 파일은 모두 서버의 것이고,
원격 클라이언트가 자기 파일 시스템이나 인증 정보나
기계 상태로 환경의 것을 대신해서는 안 된다고 분명히 한다.
데스크톱 앱도 서버를 내장하지만 화면은 같은 경계를 따른다.

이 구조 덕분에 폰은 아무것도 실행하지 않는다.
폰은 집이나 회사에 켜 둔 컴퓨터에서 에이전트가 하는 일을 화면으로 볼 뿐이고,
그 컴퓨터는 작업이 끝날 때까지 켜져서 접속 가능한 상태여야 한다.
원격 접근 문서도 첫 문장에서 같은 조건을 건다.

### 에이전트마다 다른 점은 어댑터 뒤에 숨긴다

오케스트레이션은 정규화된 명령과 이벤트만 다루고
제공자별 동작은 어댑터 뒤에 둔다는 것이 설계 원칙이다.
그래서 새 제공자를 더해도 도메인 코드와 클라이언트 곳곳에 분기를 넣지 않아도
된다고 한다.
다만 권한 문서를 보면 이 추상화가 완전하지는 않다.
자동(Auto) 모드는 Codex, Claude, Cursor, Grok에서만 제공자의 자동 검토를 쓰고
OpenCode와 Antigravity는 그냥 묻는 쪽으로 돌아가며,
Grok에는 편집 자동 승인 모드가 아예 없다.

### 의도는 이벤트로 기록하고 부작용은 나중에 처리한다

서버는 명령을 직렬로 처리해 이벤트를 결정하고,
제공자나 파일 시스템 작업은 그 결정에서 하지 않는다.
이벤트와 투영(projection), 접수한 명령의 영수증, 부작용 대기열(outbox)을
한 데이터베이스 트랜잭션으로 저장한 뒤 별도의 작업자가 부작용을 실행하고
결과를 다시 오케스트레이션에 넣는다.
그래서 명령에 대한 응답은 의도가 기록되었다는 뜻이지
에이전트나 체크포인트 작업이 끝났다는 뜻이 아니라고 문서가 분명히 한다.

다만 이벤트 로그가 영구히 보존되는 진실은 아니다.
현재 구조 문서는 로그가 재접속 재생과 명령 재시도에 필요한 하루 안팎만 남기고,
투영이 적용한 오래된 이벤트는 지우므로 로그로 투영을 다시 만들 수 없다고 적는다.
원천은 투영이고, 로그는 짧게 남는 전달 장치다.
이 문서의 이전 판은 이 부분을 로그가 진실이라고 요약했는데
현재 문서와 맞지 않아 고쳤다.

체크포인트는 사용자 브랜치에 커밋을 더하지 않고
숨은 Git 참조로 작업 공간 상태를 저장한다.
되돌리기는 작업 공간과 에이전트 대화를 함께 맞춰야 하므로,
대화를 되돌릴 수 없는 제공자는 파일 시스템을 바꾸기 전에 되돌리기를 거부한다.
파일은 돌아갔는데 에이전트는 이전 변경을 그대로 기억하는 상태를
막으려는 순서다.

## 코드 분석

이 절은 2026년 11월 20일에 받은 저장소(커밋 `4d5bf2d`)를 읽은 결과다.
코드는 읽기만 했고 빌드하거나 실행하지 않았다.
아래 수치와 구조는 파일 이름, 줄 수, 소스와
`docs/`, `SECURITY.md`의 서술에서 읽은 것이며
동작을 재현해 확인한 것이 아니다.

`packages/`에는 다음 묶음이 있다.

| 소스 컨트롤 | GitHub, GitLab, Bitbucket, Azure DevOps, Forgejo, GitCafe용 패키지                                                                                                                | PR 연결과 정의가 서비스별 패키지로 나뉘어 있다                                                               |

저장소의 나머지 디렉터리는 다음과 같다.

- `native/`: Rust로 만든 `resource-monitor`와 리눅스 스냅샷 보조 도구
- `infra/relay`: T3 Connect 중계 서버의 코드
- `evals/`: PR 내용 생성, 스레드 제목, 음성 정리, MCP 도구 사용 같은 평가 묶음

서버 의존성에는 다음이 들어 있다.

- Claude Agent SDK(`@anthropic-ai/claude-agent-sdk`)
- `@cursor/sdk`
- `node-pty`
- `playwright-core`
- 음성 인식용 `transcribe-cpp`

서버 전반은 Effect 프레임워크로 쓰였다.

### 오케스트레이터는 명령 직렬화와 한 트랜잭션 쓰기로 이루어진다

`EventSink`의 쓰기 함수 이름과 인자는
(`writeWithEffects`에 이벤트와 효과 목록을 함께 넘긴다)
앞 절에서 설명한 한 트랜잭션 저장과 맞는다.
`CommandReceiptStore`가 명령 ID를 기록해 재시도를 한 번만 실행되게 하고,
`EffectWorker`가 부작용을 따로 실행한다.
제공자가 죽으면 그 프로세스에 묶인 효과는 다시 재생하지 않고
새 일을 받기 전에 정리한다고 문서가 적는다.

버전 2 전환의 비용도 문서에 드러난다.
첫 실행에서 `state.sqlite`를 `statev2.sqlite`로 복사하고 복사본에만 새
마이그레이션을 적용한다.
스레드 대화는 읽거나 이어 갈 때 가져오며, 다음은 가져오지 않는다.

- 제공자 세션 정체성
- 체크포인트
- 도구 호출
- 승인
- 제안된 계획

가져온 스레드를 처음 이어 갈 때는 새 제공자 세션을 만들고
최근 대화를 32,000자 안에서 잘라 넘긴다.

클라이언트와 서버의 프로토콜 버전(현재 2)이 다르면 `/ws`가 HTTP 426으로
거부한다.
마이그레이션 ID는 이름이 아니라 번호만 비교하므로,
포크가 같은 번호를 쓰면 이후 업스트림 마이그레이션이 영원히 건너뛰어진다고
문서가 경고한다.
포크의 스키마 변경은 별도 테이블에 두라는 것이 문서의 결론이다.

이 마지막 항목은 이 프로젝트가 내세우는 포크 가능성의 실무적인 한계다.
홈페이지의 포크 안내는 개인 빌드를 만드는 데는 맞으나,
업스트림 업데이트를 계속 받는 포크는 데이터베이스 스키마에서 제약을 받는다.

### 제공자 차이는 기능 선언으로 다룬다

앞서 어댑터가 차이를 숨긴다고 썼으나 코드의 모양은 숨기기보다 선언하기에 가깝다.
`CommandPolicy.ts`는 다음을 능력(capability)으로 나열한다.

- `queued_messages`
- `active_steering`
- `interrupt`
- `interrupt_restart_steering`
- `native_fork`
- `fork_from_turn`
- `rollback`
- `rollback_snapshot`
- `context_handoff`
- `strong_terminal_status`

제공자가 만족하지 못하면 `CommandPolicyCapabilityUnsupportedError`로 명령을
거부한다.
어댑터는 `ProviderAdapter.ts`에 정의된 이벤트를
(세션, 스레드, 턴, 노드, 하위 에이전트, 메시지, 턴 항목, 조종 갱신)
내보내는 방식으로 실행 그래프를 채운다.

`providers.md`는 제공자마다 다른 위험을 구체적으로 적는다.
같은 드라이버라도 인스턴스별로 계정과 상태를 분리한다.
OpenCode 2.x는 인스턴스당 서버 하나를 쓰고 스레드마다 `t3-code-<thread>`라는
MCP 항목을 등록하며, 세션 권한 규칙이 다른 스레드의 항목을 막는다.
OpenCode가 “항상 허용”을 프로젝트 전체에 저장하므로,
자동 승인은 `once`로만 답해서 감독 스레드의 권한이 넓어지지 않게 한다.

Antigravity는 인스턴스별 프로필을 두고 파일 기반 자격 증명을 강제한다.
macOS 키체인 항목이 인스턴스끼리 공유되는 것을 피하려는 것이다.
텍스트 생성 보조는 도구 요청을 거부하지만,
프롬프트 지시와 도구 거부가 네이티브 샌드박스를 만들지는 않는다고
문서가 스스로 적는다.

### 보안 모델은 환경이 샌드박스가 아니라는 전제에서 출발한다

루트의 `SECURITY.md`는 첫 문단에서 환경(서버)이 샌드박스가 아니고
서버를 실행한 운영체제 사용자의 권한으로
에이전트와 터미널을 의도적으로 실행한다고 분명히 적는다.
전체 권한 세션은 그 사용자의 셸과 같다고 하며,
보안 작업의 범위를 다음 세 질문으로 한정한다.

- 누가 세션을 얻는가
- 세션 종류마다 닿는 범위는 어디까지인가
- 폐기와 상한이 지켜지는가

주체는 다음과 같이 나뉜다.

| 주체                          | 얻는 경로                 | 할 수 있는 일                              |
| ----------------------------- | ------------------------- | ------------------------------------------ |
| 포트에 닿는 누구나            | 네트워크                  | 환경 설명 읽기, 일회용 자격으로 짝짓기     |
| 전체 권한 클라이언트          | 짝짓기, 토큰 교환         | 서버 사용자가 할 수 있는 모든 일 (기본값)  |
| 좁은 클라이언트               | 범위를 지정한 짝짓기 링크 | 허용된 RPC와 경로만, 스스로 넓힐 수 없음   |
| MCP 클라이언트(외부 에이전트) | `/mcp`의 OAuth            | `/mcp`만, 읽기 전용 또는 실행 모드 상한 안 |
| T3가 실행한 에이전트          | 스레드의 실행 모드        | 그 모드와 관리 정책과 도구별 접근 선언 안  |
| 게스트 링크                   | 공유 하나의 HMAC 토큰     | 스레드 하나 읽기와 메시지 제안만           |

기본 짝짓기 권한이 전체 범위인 이유를 문서는 직접 설명한다.
`terminal:operate`는 서버 사용자의 셸이고
`orchestration:operate`는 전체 권한 에이전트를 띄울 수 있어서,
둘 중 하나만 있어도 모든 범위의 세션을 만들 수 있으므로
기본값에서 관리 권한을 빼는 것은 경계가 되지 못한다는 것이다.
이 문서의 해석으로는 앞 절의 Full access 기본값과 같은 사고방식이다.
편의를 위해 신뢰를 한 단계로 합치고, 좁히는 일은 사용자에게 맡긴다.

코드에서 확인한 것은 두 가지다.
하나는 새 스레드의 기본 실행 모드로,
`packages/contracts/src/providerPolicy.ts`의
`DEFAULT_RUNTIME_MODE = "full-access"`이고, 모드 순서는
`approval-required` < `auto-accept-edits` < `auto` < `full-access`다.
다른 하나는 RPC 메서드마다 필요한 범위가 `RpcAuthorization.ts`의 표로 선언되어
있다는 점이다.
그래서 소켓 인증이 모든 메서드의 권한을 뜻하지는 않는다.

MCP 접근은 사용자가 범위 목록이 아니라
읽기 전용 또는 실행 모드 상한을 고르게 한다.
MCP 도구는 모두 오케스트레이션이어서 `orchestration:operate` 하나만 줘도
에이전트가 전체 권한 스레드를 시작할 수 있기 때문이다.
`McpToolAccess.ts`는
모든 도구가 누가 호출할 수 있는지 선언해야 컴파일되게 만들어
이 규칙을 타입으로 강제한다고 문서가 설명한다.

T3 Connect의 신뢰 가정은 문서가 직접 밝힌다.
중계(relay)는 신뢰하는 중개자이고, 환경 세션 토큰은 중계가 받지 않는다.
클라이언트가 자신의 DPoP 키로 환경과 직접 교환한다.
그러나 중계가 일회용 부트스트랩 자격을 요청하는 서명 권한을 쥐고 있으며,
DPoP는 정직한 교환에서 자격 재사용을 막을 뿐
중계의 서명 키가 탈취된 경우를 무해하게 만들지는 않는다고 명시한다.

장치 승인(`requireConnectDeviceApproval`)이 이 위험을 줄이지만
코드의 기본값은 `false`다.
문서에 따르면 꺼져 있는 동안에는 교환을 마친 모든 키가 신뢰 장치로 기록된다.
관리형 터널은 서버 자신의 루프백 HTTP 출처만 노출하고,
중계는 호출자가 준 URL이 아니라 자기 할당 정보에서 엔드포인트를 찾는다.
같은 호스트의 다른 서비스가 터널로 열리지 않게 하려는 것이다.

### 텔레메트리는 기본으로 켜져 있다

서버 코드의 `T3CODE_TELEMETRY_ENABLED`는 `Config.withDefault(true)`다.
사용자 문서에 따르면 제품 사용 이벤트는
`ingest.t3.codes`로 가고 PostHog로 전달된다.
이벤트에는 제공자, 모델, 추론 강도, 권한 모드, 턴 결과, 시간, 토큰 수가 들어가고
프롬프트, 응답, 파일 내용, 인증 토큰, 대화 ID는 들어가지 않는다고 한다.
설치 수를 세려고 T3 Connect 계정, 로그인한 OpenAI와 Claude 계정,
기기별 임의 식별자를 해시해서 보낸다.
이 단락은 이 문서를 쓴 시점의 서버 코드 기준이며,
로그인한 OpenAI와 Claude 계정을 쓰는 부분은 11월 24일에 바뀌었다(아래).

끄는 범위는 하나가 아니다.
아래 표는 범위마다 무엇으로 끄고 무엇이 남는지를 정리한 것이다.

| 범위               | 끄는 방법                                                                  | 꺼지는 것                 | 남는 것                                                                                            |
| ------------------ | -------------------------------------------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------- |
| 서버               | 환경 변수 `T3CODE_TELEMETRY_ENABLED=false`, 관리 정책의 `telemetry: false` | 제품 이벤트와 릴레이 추적 | -                                                                                                  |
| 브라우저 웹 앱     | 서버의 환경 변수를 읽지 않으므로 해당 없음                                 | -                         | 빌드에 릴레이 추적이 설정되어 있으면 서버가 옵트아웃해도 자체 연결 추적을 보낸다                   |

브라우저 웹 앱은 서버 설정과 별개로 동작하므로
서버에서 옵트아웃해도 이 경로까지 막히지는 않는다.
에이전트 활동 게시도 텔레메트리와 다른 기능이어서
옵트아웃과 상관없이 따로 확인해야 한다.

README의 요약은 API 요금을 따로 받지 않고
사용자가 구독 중인 플랜을 그대로 쓰게 할 뿐 아무것도 팔지 않는다는 것인데,

## 설치하기

가장 짧은 경로는 셸 스크립트다.

```bash
curl -fsSL https://t3.codes/install.sh | sh
t3
```

Windows에서는 PowerShell에서 `irm https://t3.codes/install.ps1 | iex`를 쓴다.
`t3`가 서버를 띄우고 로컬 웹 앱을 연다.
`t3 service install`은 서버를 백그라운드 서비스로 계속 돌리고
`t3 update`는 새 릴리스로 옮긴다.
설치 없이 한 번만 써 보려면 `npx t3@latest`를 쓴다.

데스크톱 앱은 GitHub Releases에서 받거나 패키지 관리자로 설치한다.
Windows는 `winget install T3Tools.T3Code`나 `scoop install extras/t3code`,
macOS는 `brew install --cask t3-code`,
Arch는 AUR의 `t3code-bin`과 nightly용 `t3code-nightly-bin`이다.
Debian 계열은 릴리스의 `.deb`를 `sudo apt install ./T3-Code-*.deb`로 설치한다.

어느 경로로 설치하든 먼저 지원 에이전트 가운데 하나 이상을 설치하고
로그인해야 한다.
Codex는 `codex login`, Claude는 `claude auth login`, Cursor는 `agent login`,
Grok Build는 `grok login`, OpenCode는 `opencode auth login`이고,
Antigravity는 설정에서 켜고 구글로 로그인하며 CLI가 필요 없다.
T3 Code는 이 로그인을 그대로 이어받아 동작하므로
에이전트가 로그인되어 있지 않으면 할 일이 없다.

## 연결 경로 정하기

원격 접근 문서는 한 컴퓨터에 닿는 길을 여러 가지로 나눈다.

| 경로            | 방법                                                                 | 맞는 상황                                    |
| --------------- | -------------------------------------------------------------------- | -------------------------------------------- |
| T3 Connect      | 호스트에서 로그인하고 켜면 공유기 포워딩 없이 다른 기기에서 접속     | 집 밖에서 쓰거나 호스팅 에이전트가 접속할 때 |
| LAN 또는 사설망 | `t3 serve --host <사설 IP>`로 열고 `t3 pair`의 QR 또는 링크로 짝짓기 | 같은 네트워크나 Tailscale 안에서만 쓸 때     |
| 기타            | Tailscale, 다른 VPN, 공개 URL, SSH                                   | 이미 쓰는 네트워크 구성이 있을 때            |

한 컴퓨터에 경로가 여럿이면 속도순으로 정렬해 첫 번째로 응답하는 경로로
연결하고,
우선순위가 더 높은 경로가 살아나는지 1분마다 다시 확인해 그쪽으로 되돌아간다.
집에서는 LAN으로, 밖에서는 T3 Connect로 자동으로 바뀐다.
`127.0.0.1` 주소는 링크를 연 기기에서만 닿으므로
폰용 페어링 링크에는 쓸 수 없다.

CLI만 있는 호스트의 로그인은 SSH 안에서도 된다.
CLI가 브라우저 링크와 짧은 코드를 출력하고 아무 기기에서
링크를 열어 코드가 일치하는지 확인해 승인하면 CLI가 알아서 이어 간다.
OAuth 콜백 포트를 포워딩할 필요가 없어서 서버 위에서 쓰기 편하다.

## 값 정하기

### 권한 모드

권한 모드는 대화 입력창에서 고르고 그 스레드에 적용된다.

| 모드                  | 동작                                                           |
| --------------------- | -------------------------------------------------------------- |
| **Supervised**        | 명령과 파일 변경마다 승인을 요청한다.                          |
| **Auto-accept edits** | 파일 편집은 자동 승인하고 나머지는 승인이 필요할 수 있다.      |
| **Auto**              | 제공자의 자동 검토가 일상적인 동작을 승인하고 나머지는 묻는다. |
| **Full access**       | 승인 없이 명령과 편집을 허용한다.                              |

문서에 따르면 새 스레드의 기본값은 Full access다.
기본 설정을 바꾸려면 설정의 새 스레드 권한 항목에서
정하고 프로젝트별로 덮어쓸 수 있다.
이 문서는 처음 쓸 때 Supervised나 Auto로 바꾸고 시작하기를 권한다.
폰에서 승인할 수 있는 도구에 일부러 승인 없는 기본값이 켜져 있기 때문이다.

### 이어서 실행

설정의 재시작 뒤 스레드 이어 가기는 기본으로 켜져 있다.
업데이트, 충돌, 기계 재시작 뒤에 지원되는 활성 스레드를 다시 이어 간다.
T3 Code가 다시 시작해야 하며 이 설정이 자동 시작을 켜 주지는 않는다.
승인이나 답변이나 비밀 값을 기다리는 스레드,
보관하거나 미룬 스레드는 이어 가지 않고,
연속 자동 재개가 세 번 지나면 다음 메시지를 기다린다.

## 트레이드오프

### 편리한 원격 접속은 열린 문의 개수와 같다

T3 Connect는 포워딩 없이 접속할 길을 열어 주고,
LAN 페어링은 문을 열지 않는 대신 같은 망에서만 쓸 수 있다.
저장소 문서에 따르면 T3 Connect의 신원은 Clerk가 맡고
앱 트래픽은 호스트에서 도는 `cloudflared`의 터널로 가며,
중계는 링크를 설정할 뿐 HTTP와 WebSocket 세션을 대신 전달하지 않는다.
자동화 웹훅만 예외적으로 중계를 거친다.
중계가 쥔 서명 권한과 장치 승인 기본값은 앞의 코드 분석 절에 정리했다.
코드와 프롬프트가 중계를 지나는 것이 문제라면
`t3 serve --host <사설 IP>`와 Tailscale 같은 직접 경로로 한정하는 것이 선택지다.
그 경우 집 밖의 폰에서는 VPN을 따로 켜야 한다는 불편이 따른다.

### 외부 에이전트에게 열어 주는 MCP는 권한 모델이 전부다

T3 Code는 MCP 서버도 제공해서 터미널의 Claude Code나 Codex,
ChatGPT 같은 외부 에이전트가 프로젝트와 스레드를 읽고
새 스레드를 시작하게 할 수 있다.
접근은 읽기 전용이 기본이고, Supervised에서 Full access까지 고르면
스레드를 시작하고 메시지를 보내고 멈추는 권한이 모든 프로젝트에 생긴다.
에이전트가 시작하거나 조종하는 스레드는
사용자가 고른 모드보다 높은 권한으로 돌 수 없다.
호스팅 에이전트에게 승인하는 로그인은 그 서비스를 운영하는 쪽이 접근을 갖는다고
문서가 직접 경고한다.
승인은 방금 시작한 로그인에만 하고,
로그인은 30일 뒤 만료되며 설정에서 즉시 취소할 수 있다.

### 서버와 앱이 따로 업데이트된다

앱과 서버는 다른 컴퓨터에서 따로 업그레이드되므로
둘의 오케스트레이션 프로토콜이 다르면 연결을 거부한다.
앱이 서버보다 새로우면 연결 전에 막고
서버가 앱보다 새로워도 업데이트 안내와 함께 거부한다.
그래서 집 컴퓨터를 켜 두고 폰 앱만 자동 업데이트에 맡기면
어느 날 폰이 연결되지 않는 일이 생길 수 있다.
사이드바의 업데이트 버튼은 제공자, 서버,
지금 쓰는 데스크톱 앱 순서로 한꺼번에 올리지만,
서버 업데이트는 npm에 새 버전이 올라간 뒤에만 나타난다.
서버 업데이트는 실행 중인 에이전트와 터미널 명령을 끊을 수 있으므로
중요한 일을 하는 중에는 미루는 편이 안전하다.

### 차별점은 아직 분명하지 않고 대안은 이미 있다

HN의 짧은 스레드 두 개가 이 도구를 보는 시선을 보여 준다.
hyperultra는 에이전트 메타 하네스에 T3라는 이름을 붙여 쓰게 만드는 것이
강력한 브랜딩이라고 평했고,[^hyperultra]
awaseem은 역시 오픈소스인 Superset과 어떻게 다르냐고 물었지만
스레드에는 답이 달리지 않았다.[^awaseem]
GN에서도 비슷한 대안이 거론되었다.
3ae3ae는 같은 목적에는 paseo가 아주 마음에 들었다고 적었다.[^3ae3ae]
click은 이 도구가 에이전트마다 따로 지원을 만들어야 하는 개발 방식이
아쉬워 쓰지 않고 있다고 했다.[^click]
지원 목록에 pi가 없다는 점과, 서버로 동작하는 컴퓨터에서
SFTP 브라우저나 파일 처리 기능을 찾지 못했다는 점도 짚었다.
데이터를 넣어 줄 때, 마크다운 파일을 직접 볼 때,
서버에서 만든 실행 파일을 가져와 확인할 때 쓸모가 있었을 기능이라는 것이다.
첫 번째 지적은 앞에서 본 어댑터 구조의 대가이기도 하다.
제공자별 차이를 어댑터 뒤에 숨기면 새 에이전트마다 어댑터가 필요하고,
그 어댑터가 없으면 그 에이전트는 이 제어판에서 쓸 수 없다.

### 써 본 사람들의 평가는 UX에 모인다

HN에서 T3 Code가 널리 쓰이느냐고 묻자 두 사람이 사용 경험을 적었다.
viraptor는 PR 미리보기와 git push처럼 흔한 일이 빨라지고,
네임스페이스가 붙은 worktree를 기본으로 만들어 주고,
메시지를 끼워 넣는(steer) 동작과 대기열에 쌓는(queue) 동작이 쓸모 있으며,
다른 스레드를 참조하고 특정 작업자를 띄우는 기능과 받은편지함 같은 스레드 처리가
좋다고 했다.
웹 작업이 많다면 내장 미니 브라우저가 지금까지 본 것 가운데 가장 낫고,
cmux에서 t3code로 옮겨 후회가 없다고 했다.[^viraptor]
joshka는 개발자에게 필요한 UX 면에서 Claude와 Codex의 공식 앱보다 훨씬 강하고,
이슈 트래커가 블랙홀 같지 않으며 릴리스 노트가 실제 PR 링크라고 했다.
Codex와 Claude 모델을 섞어 쓰며 하위 에이전트를 서로 넘긴다고 하면서,
자신은 OpenAI에서 Codex의 TUI 쪽 일을 했으므로 Codex가 더 익숙하다는 편향을
스스로 밝혔다.[^joshka]
두 증언은 이 문서의 앞부분이 다룬 구조(서버, 어댑터)가 아니라
화면과 작업 흐름의 완성도를 장점으로 꼽는다는 점이 같고,
README만 읽어서는 확인할 수 없는 부분이다.
다만 둘 다 자발적으로 쓴 댓글 두 개이며 대조군이 없다.

이 글은 저장소가 GitHub와 GitCafe 사이에서 동기화된다는 소식을 전하는
스레드였다.
동기화를 맡은 versecafe는
PR 약 1만 8천 개, 이슈 약 4천 개, 체크와 댓글과 리뷰까지 20만 개가 넘는 항목을
동기화하는 것으로 알고 있으며,
이것이 GitHub와 다른 플랫폼 사이에서 동기화된 공개 저장소 가운데
가장 큰 규모라고 적었다.[^versecafe]
preommr는 Git 저장소를 여러 곳에 두는 일은 흔하다고 반박했고,
versecafe는 Git 미러링은 쉽고 어려운 것은 PR과 이슈와 리뷰와 댓글 같은
메타데이터라고 답했다.[^preommr]

### 홈페이지의 수치와 후기는 선별된 홍보 문구다

홈페이지는 T3 Code를 코딩 에이전트를 위한 오픈소스 제어 평면(control
plane)이라고 소개한다.
Claude Code, Codex, Antigravity, OpenCode, Cursor, Grok을 한 화면에서 조종하고,
구독은 각자 가져오며, 전체를 포크할 수 있다는 것이 첫 문장이다.
README가 말한 에이전트 하네스 제어판과 같은 내용을
다른 이름으로 부르는 셈이고,
지원 목록과 모바일 앱(iOS, Android)도 README와 같다.

그 아래에는 홍보 수치와 후기 모음이 있다.
GitHub 스타는 이제 6만 6천 개 이상이라고 적혀 있고
GitHub API의 66,501개와 맞는다.
이전 판에서 홈페이지의 스타 수가 갱신되지 않은 것으로 보인다고 적은 지적은
2026년 11월 20일 기준으로는 해소되었다.
개발자 50만 명 이상이 쓴다는 문구는 근거나 집계 방식이 페이지에 없고,
저장소의 `AGENTS.md`도 같은 숫자를 사용자 수로 적을 뿐 출처를 달지 않는다.
후기는 서로 다른 트윗 20개를 인용하며(페이지 소스의 트윗 주소 기준),
휴가지에서 폰으로 iOS 개발을 했다거나
비행기 안에서도 LAN처럼 쓸 수 있었다는 식의 원격 사용 경험과
Electron 앱치고 가볍다는 평가가 많다.
어떤 기준으로 골랐는지 밝히지 않은 선별 후기이므로 만족도의 증거가 아니라
운영자가 내세우려는 장점의 목록으로 읽어야 한다.
위의 HN 댓글 두 개가 UX를 장점으로 꼽은 것과 방향이 같다는 점이 유일한 교차
확인이다.

## 함정

기본 권한이 Full access라는 점이 가장 먼저 눈에 띈다.
폰에서 스레드를 시작하면 에이전트가 컴퓨터에서
승인 없이 명령을 실행할 수 있으니,
처음에는 모드를 바꾸고 시작하는 편이 안전하다.

모든 에이전트에서 같은 권한 모드가 같은 뜻을 갖지는 않는다.
Auto는 제공자마다 다르게 동작하고,
Muse Code는 Supervised와 Full access만 제공하며,
Grok의 명령 승인에는 세션 전체 허용이 없다.
Antigravity는 Full access에서도 자체 승인 요청을 보낼 수 있다.

호스트 컴퓨터가 잠들거나 꺼지면 폰에서 할 수 있는 일이 없다.
백그라운드 서비스(`t3 service install`)로 돌리고
슬립을 막는 것은 사용자의 몫이다.

하나의 T3 홈 디렉터리는 서버 하나에만 쓸 수 있다.
다른 서버가 이미 쓰고 있다는 안내가 뜨면
그 서버를 멈추거나, 별도 홈 디렉터리를 만들어 실행 중인 서버에 짝지어야 한다.

`curl | sh`로 설치하는 방식은 편하지만 스크립트를 받아서 바로 실행하는 것이므로,
안심이 안 된다면 스크립트를 먼저 내려받아 읽어 보거나 패키지 관리자 경로를 쓴다.

텔레메트리가 기본으로 켜져 있고 끄는 방법이 클라이언트마다 다르다.
서버 환경 변수는 브라우저 웹 앱의 연결 추적을 끄지 못하고,
모바일 앱의 릴레이 추적과 호스트의 에이전트 활동 게시는 별도 설정이다.
상세는 코드 분석 절에 정리했고,
논란의 경과와 이후 변화는
[T3 Code 텔레메트리 소스 조사](t3-code-telemetry.md)에 있다.

T3 Connect를 쓴다면
장치 승인(`requireConnectDeviceApproval`)의 기본값이 꺼져 있다.
공유 컴퓨터나 민감한 코드에서는 켜고 시작한다.

## 확인하기

설치 없이 동작을 보려면 `npx t3@latest`를 실행하고
열린 로컬 웹 앱에서 프로젝트 하나를 추가한다.
권한 모드를 Supervised로 두고 에이전트에게 파일 하나를 고치게 한 뒤,
승인 요청이 대화에 뜨는지 확인한다.
그다음 같은 네트워크의 폰에서 `t3 serve --host <사설 IP>`로 열고
`t3 pair`의 QR로 짝지어,
폰에서 같은 스레드가 보이는지와 승인을 폰에서 처리할 수 있는지 본다.
마지막으로 `t3 update`를 한 번 실행해 앱과 서버 버전 불일치 안내가
어떻게 나오는지 확인해 두면 실제 업그레이드 때 놀라지 않는다.

## 체크리스트

- 지원 에이전트 가운데 하나 이상이 컴퓨터에 설치되고 로그인되어 있는가.
- 새 스레드의 기본 권한을 Full access에서 바꿨는가.
- 외부 에이전트에 MCP를 열 때 읽기 전용에서 시작했는가.
- 호스팅 에이전트에 승인하는 로그인이 방금 내가 시작한 것인가.
- 폰 접속 경로가 T3 Connect인지 사설망인지 알고 있는가.
- 호스트가 잠들지 않고 백그라운드 서비스로 돌아가는가.
- 앱과 서버를 같은 버전으로 올릴 방법을 알고 있는가.
- 텔레메트리를 끌 범위(서버, 브라우저, 모바일, 에이전트 활동 게시)를 정했는가.
- T3 Connect를 쓴다면 장치 승인을 켰는가.

## 기억할 원칙

### 제어판이 쉬워지면 권한 설정이 제품의 핵심이 된다

에이전트를 폰에서 조종할 수 있다는 것은
승인 버튼을 늘 손에 쥐고 다닌다는 뜻이다.
이 편의가 안전해지려면 기본값이 보수적이어야 하는데,
T3 Code의 문서화된 기본값은 반대다.
이 문서의 해석으로는 이 도구를 쓰는 사람이 첫 설정에서
해야 하는 일은 연결을 만드는 것이 아니라 권한 기본값을 바꾸는 것이다.
