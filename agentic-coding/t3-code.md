## 소개

T3 Code는 스스로를 에이전트 하네스 제어
화면(agent harness control surface)이라고 부른다.
내 컴퓨터에 설치된 코딩 에이전트를 모바일 앱(iOS,
Android)과 웹 앱, Electron 기반 데스크톱 앱에서 조종하게 해 준다.
Claude Code, Codex, Cursor, Grok Build, OpenCode, Google Antigravity를 지원하고,
이미 컴퓨터에 설치해 로그인해 둔 구독을 그대로 쓴다.
T3 Code는 모델을 팔거나 대신 호출하지 않고
이미 있는 에이전트 프로그램을 감싸 조종한다.

README는 무엇을 파는 것이냐는 물음에 아무것도 팔지 않는다고 답한다.
Codex 데스크톱 앱, Conductor, Claude Desktop, Cursor Glass 같은 기존 도구에서
영감을 받았지만 어느 것도 기준에 못 미쳐서 직접 만들었다는 설명이다.
원하는 것은 빠르고 원격에서 쓸 수 있고 진짜로 열려 있는 도구이며,
방향이 틀어지면 누구든 포크해서 원하는 편집기를 만들 수 있게 하겠다고 한다.

## 동작 방식

### 실행은 작업 공간이 있는 환경에 있고 클라이언트는 조종만 한다

핵심 설계는 문서의 아키텍처 개요가 한 문단으로 밝힌다.
실행은 작업 공간을 가진 환경이 맡고, 웹과 데스크톱,
모바일 클라이언트는 인증된 RPC로 그것을 조종한다.
에이전트 프로세스, 터미널, Git, 프로젝트 파일은 모두 서버의 것이고,
원격 클라이언트가 자기 파일 시스템이나 인증 정보나
기계 상태로 환경의 것을 대신해서는 안 된다고 분명히 한다.
데스크톱 앱도 서버를 내장하지만 화면은 같은 경계를 따른다.

이 구조 덕분에 폰은 아무것도 실행하지 않는다.
폰이 보는 것은 집이나 회사에 켜 둔 컴퓨터의 에이전트가 하는 일이고,
그 컴퓨터는 작업 내내 켜져 있고 닿을 수 있어야 한다.
원격 접근 문서도 첫 문장에서 같은 조건을 건다.

### 에이전트마다 다른 점은 어댑터 뒤에 숨긴다

오케스트레이션은 정규화된 명령과 이벤트로만 일하고
제공자별 동작은 어댑터 뒤에 둔다는 것이 설계 원칙이다.
그래서 새 제공자를 더해도 도메인 코드와 클라이언트 곳곳에 분기를 넣지 않아도
된다고 한다.
다만 권한 문서를 보면 이 추상화가 완전하지는 않다.
자동(Auto) 모드는 Codex, Claude, Cursor, Grok에서만 제공자의 자동 검토를 쓰고
OpenCode와 Antigravity는 그냥 묻는 쪽으로 돌아가며,
Grok에는 편집 자동 승인 모드가 아예 없다.

### 이벤트 로그가 진실이고 부작용은 나중에 처리한다

서버는 이벤트 로그를 오케스트레이션 상태의 원천으로 삼는다.
명령은 직렬로 처리해 이벤트를 결정하고
제공자나 파일 시스템 작업은 그 결정에서 하지 않는다.
이벤트와 투영, 명령 접수 기록,
부작용 대기열을 한 데이터베이스 트랜잭션으로 저장한 뒤 별도의
작업자가 부작용을 실행하고 결과를 다시 오케스트레이션에 넣는다.
그래서
명령에 대한 응답은 의도가 기록되었다는 뜻이지 에이전트나
체크포인트 작업이 끝났다는 뜻이 아니라고 문서가 분명히 한다.

체크포인트는 사용자 브랜치에 커밋을 더하지 않고
숨은 Git 참조로 작업 공간 상태를 저장한다.
되돌리기는 작업 공간과 에이전트 대화를 함께 맞춰야 하므로,
대화를 되돌릴 수 없는 제공자는 파일 시스템을 바꾸기 전에 되돌리기를 거부한다.
이 순서는 파일은 돌아갔는데
에이전트는 이전 변경을 기억하는 상태를 막으려는 것이다.

## 설치하기

가장 짧은 경로는 셸 스크립트다.

```bash
curl -fsSL https://t3.codes/install.sh | sh
t3
```

Windows에서는 PowerShell에서 `irm https://t3.codes/install.ps1 | iex`를 쓴다.
`t3`가 서버를 띄우고 로컬 웹 앱을 연다.
`t3 service install`은 서버를 백그라운드 서비스로 계속 돌리고
`t3 update`는 새 릴리스로 옮긴다.
설치 없이 한 번만 써 보려면 `npx t3@latest`를 쓴다.

데스크톱 앱은 GitHub Releases에서 받거나 패키지 관리자로 설치한다.
Windows는 `winget install T3Tools.T3Code`나 `scoop install extras/t3code`,
macOS는 `brew install --cask t3-code`,
Arch는 AUR의 `t3code-bin`과 nightly용 `t3code-nightly-bin`이다.
Debian 계열은 릴리스의 `.deb`를 `sudo apt install ./T3-Code-*.deb`로 설치한다.

어느 경로로 설치하든 먼저 지원 에이전트 가운데 하나 이상을 설치하고
로그인해야 한다.
Codex는 `codex login`, Claude는 `claude auth login`, Cursor는 `agent login`,
Grok Build는 `grok login`, OpenCode는 `opencode auth login`이고,
Antigravity는 설정에서 켜고 구글로 로그인하며 CLI가 필요 없다.
T3 Code는 이 로그인에 얹혀 동작하므로
에이전트가 로그인되어 있지 않으면 할 일이 없다.

## 연결 경로 정하기

원격 접근 문서는 한 컴퓨터에 닿는 길을 여러 가지로 나눈다.

| 경로            | 방법                                                                 | 맞는 상황                                    |
| --------------- | -------------------------------------------------------------------- | -------------------------------------------- |
| T3 Connect      | 호스트에서 로그인하고 켜면 공유기 포워딩 없이 다른 기기에서 접속     | 집 밖에서 쓰거나 호스팅 에이전트가 접속할 때 |
| LAN 또는 사설망 | `t3 serve --host <사설 IP>`로 열고 `t3 pair`의 QR 또는 링크로 짝짓기 | 같은 네트워크나 Tailscale 안에서만 쓸 때     |
| 기타            | Tailscale, 다른 VPN, 공개 URL, SSH                                   | 이미 쓰는 네트워크 구성이 있을 때            |

한 컴퓨터에 경로가 여럿이면 속도순으로 정렬해 첫 번째로 응답하는 경로로 연결하고
앞선 경로를 1분마다 다시 확인해 되돌아간다.
집에서는 LAN으로, 밖에서는 T3 Connect로 자동으로 바뀐다.
`127.0.0.1` 주소는 링크를 연 기기에서만 닿으므로
폰용 페어링 링크에는 쓸 수 없다.

CLI만 있는 호스트의 로그인은 SSH 안에서도 된다.
CLI가 브라우저 링크와 짧은 코드를 출력하고 아무 기기에서
링크를 열어 코드가 일치하는지 확인해 승인하면 CLI가 알아서 이어 간다.
OAuth 콜백 포트를 포워딩할 필요가 없어서 서버 위에서 쓰기 편하다.

## 값 정하기

### 권한 모드

권한 모드는 대화 입력창에서 고르고 그 스레드에 적용된다.

| 모드                  | 동작                                                           |
| --------------------- | -------------------------------------------------------------- |
| **Supervised**        | 명령과 파일 변경마다 승인을 요청한다.                          |
| **Auto-accept edits** | 파일 편집은 자동 승인하고 나머지는 승인이 필요할 수 있다.      |
| **Auto**              | 제공자의 자동 검토가 일상적인 동작을 승인하고 나머지는 묻는다. |
| **Full access**       | 승인 없이 명령과 편집을 허용한다.                              |

문서에 따르면 새 스레드의 기본값은 Full access다.
기본 설정을 바꾸려면 설정의 새 스레드 권한 항목에서
정하고 프로젝트별로 덮어쓸 수 있다.
이 문서는 처음 쓸 때 Supervised나 Auto로 바꾸고 시작하기를 권한다.
폰에서 승인할 수 있는 도구에 일부러 승인 없는 기본값이 켜져 있기 때문이다.

### 이어서 실행

설정의 재시작 뒤 스레드 이어 가기는 기본으로 켜져 있다.
업데이트, 충돌, 기계 재시작 뒤에 지원되는 활성 스레드를 다시 이어 간다.
T3 Code가 다시 시작해야 하며 이 설정이 자동 시작을 켜 주지는 않는다.
승인이나 답변이나 비밀 값을 기다리는 스레드,
보관하거나 미룬 스레드는 이어 가지 않고,
연속 자동 재개가 세 번 지나면 다음 메시지를 기다린다.

## 트레이드오프

### 편리한 원격 접속은 열린 문의 개수와 같다

T3 Connect는 포워딩 없이 접속할 길을 열어 주고,
LAN 페어링은 문을 열지 않는 대신 같은 망에서만 쓸 수 있다.
T3 Connect의 로그인 계정과 중계가 어떻게 동작하는지 문서가 자세히 밝히지는
않으므로, 어떤 데이터가 그 경로를 지나는지는 이 문서가 확인하지 못했다.
코드와 프롬프트가 중계를 지나는 것이 문제라면
`t3 serve --host <사설 IP>`와 Tailscale 같은 직접 경로로 한정하는 것이 선택지다.
그 경우 집 밖의 폰에서는 VPN을 따로 켜야 한다는 불편이 따른다.

### 외부 에이전트에게 열어 주는 MCP는 권한 모델이 전부다

T3 Code는 MCP 서버도 제공해서 터미널의 Claude Code나 Codex,
ChatGPT 같은 외부 에이전트가 프로젝트와 스레드를 읽고
새 스레드를 시작하게 할 수 있다.
접근은 읽기 전용이 기본이고, Supervised에서 Full access까지 고르면
스레드를 시작하고 메시지를 보내고 멈추는 권한이 모든 프로젝트에 생긴다.
에이전트가 시작하거나 조종하는 스레드는
사용자가 고른 모드보다 높은 권한으로 돌 수 없다.
호스팅 에이전트에게 승인하는 로그인은 그 서비스를 운영하는 쪽이 접근을 갖는다고
문서가 직접 경고한다.
승인은 방금 시작한 로그인에만 하고,
로그인은 30일 뒤 만료되며 설정에서 즉시 취소할 수 있다.

### 서버와 앱이 따로 업데이트된다

앱과 서버는 다른 컴퓨터에서 따로 업그레이드되므로
둘의 오케스트레이션 프로토콜이 다르면 연결을 거부한다.
앱이 서버보다 새로우면 연결 전에 막고
서버가 앱보다 새로워도 업데이트 안내와 함께 거부한다.
그래서 집 컴퓨터를 켜 두고 폰 앱만 자동 업데이트에 맡기면
어느 날 폰이 연결되지 않는 일이 생길 수 있다.
사이드바의 업데이트 버튼은 제공자, 서버,
지금 쓰는 데스크톱 앱 순서로 한꺼번에 올리지만,
서버 업데이트는 npm에 새 버전이 올라간 뒤에만 나타난다.
서버 업데이트는 실행 중인 에이전트와 터미널 명령을 끊을 수 있으므로
중요한 일을 하는 중에는 미루는 편이 안전하다.

### 차별점은 아직 분명하지 않고 대안은 이미 있다

HN의 짧은 스레드 두 개가 이 도구를 보는 시선을 보여 준다. hyperultra는 T3라는
이름을 붙여 에이전트 메타 하네스를 쓰게 만드는 것이 강력한 브랜드의 힘이라고
평했고,[^hyperultra] awaseem은 역시 오픈소스인 Superset과 어떻게 다르냐고
물었지만 스레드에는 답이 달리지 않았다.[^awaseem]
이 문서가 읽은 README와 문서만으로 가를 수 있는 차이는 이미 로그인된 구독을
그대로 쓰는 점, 폰과 웹과 데스크톱을 같은 서버에 붙이는 점,
외부 에이전트가 MCP로 들어올 수 있는 점이다.
GN에서도 비슷한 대안이 거론되었다. 3ae3ae는 같은 목적에는 paseo가 아주 마음에
들었다고
적었다.[^3ae3ae] click은 이 도구의 개발 방식상 각 에이전트를 T3
Code가 따로 지원해야 하는 점이 아쉬워 쓰지 않고 있다고 했다.[^click]
지원 목록에 pi가 없다는 점과, 서버로 동작하는 컴퓨터에서
SFTP 브라우저나 파일 처리 기능을 찾지 못했다는 점도 짚었다.
데이터를 넣어 줄 때, 마크다운 파일을 직접 볼 때,
서버에서 만든 실행 파일을 가져와 확인할 때 쓸모가 있었을 기능이라는 것이다.
첫 번째 지적은 앞에서 본 어댑터 구조의 대가이기도 하다.
제공자별 차이를 어댑터 뒤에 숨기면 새 에이전트마다 어댑터가 필요하고,
그 어댑터가 없으면 그 에이전트는 이 제어판에서 쓸 수 없다.
Superset과 직접 비교한 자료는 확인하지 못했으므로,
경쟁 도구와의 우열은 이 문서가 판단하지 않는다.

## 함정

기본 권한이 Full access라는 점이 가장 먼저 걸린다.
폰에서 스레드를 시작하면 에이전트가 컴퓨터에서
승인 없이 명령을 실행할 수 있으니,
처음에는 모드를 바꾸고 시작하는 편이 안전하다.

모든 에이전트에서 같은 권한 모드가 같은 뜻을 갖지는 않는다.
Auto는 제공자마다 다르게 동작하고,
Muse Code는 Supervised와 Full access만 제공하며,
Grok의 명령 승인에는 세션 전체 허용이 없다.
Antigravity는 Full access에서도 자체 승인 요청을 보낼 수 있다.

호스트 컴퓨터가 잠들거나 꺼지면 폰에서 할 수 있는 일이 없다.
백그라운드 서비스(`t3 service install`)로 돌리고
슬립을 막는 것은 사용자의 몫이다.

하나의 T3 홈 디렉터리는 한 서버만 쓸 수 있다.
다른 서버가 이미 점유하고 있다고 나오면
그 서버를 멈추거나 별도 홈 디렉터리를 쓰고 실행 중인 서버에 짝짓기해야 한다.

`curl | sh`로 설치하는 방식은 편하지만 스크립트를 받아 바로 실행하는 것이므로,
신경 쓰이면 스크립트를 먼저 내려받아 읽거나 패키지 관리자 경로를 쓴다.

## 확인하기

설치 없이 동작을 보려면 `npx t3@latest`를 실행하고
열린 로컬 웹 앱에서 프로젝트 하나를 추가한다.
권한 모드를 Supervised로 두고 에이전트에게 파일 하나를 고치게 한 뒤,
승인 요청이 대화에 뜨는지 확인한다.
그다음 같은 네트워크의 폰에서 `t3 serve --host <사설 IP>`로 열고
`t3 pair`의 QR로 짝지어,
폰에서 같은 스레드가 보이는지와 승인을 폰에서 처리할 수 있는지 본다.
마지막으로 `t3 update`를 한 번 실행해 앱과 서버 버전 불일치 안내가
어떻게 나오는지 확인해 두면 실제 업그레이드 때 놀라지 않는다.

## 체크리스트

- 지원 에이전트 가운데 하나 이상이 컴퓨터에 설치되고 로그인되어 있는가.
- 새 스레드의 기본 권한을 Full access에서 바꿨는가.
- 외부 에이전트에 MCP를 열 때 읽기 전용에서 시작했는가.
- 호스팅 에이전트에 승인하는 로그인이 방금 내가 시작한 것인가.
- 폰 접속 경로가 T3 Connect인지 사설망인지 알고 있는가.
- 호스트가 잠들지 않고 백그라운드 서비스로 돌아가는가.
- 앱과 서버를 같은 버전으로 올릴 방법을 알고 있는가.

## 기억할 원칙

### 제어판이 쉬워지면 권한 설정이 제품의 핵심이 된다

에이전트를 폰에서 조종할 수 있다는 것은 승인 한 번이 주머니 안에 있다는 뜻이다.
이 편의가 안전해지려면 기본값이 보수적이어야 하는데,
T3 Code의 문서화된 기본값은 반대다.
이 문서의 해석으로는 이 도구를 쓰는 사람이 첫 설정에서
해야 하는 일은 연결을 만드는 것이 아니라 권한 기본값을 바꾸는 것이다.
