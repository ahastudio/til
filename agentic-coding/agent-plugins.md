# Agent Plugins: 한 번 패키징해 모든 클라이언트에 보내는 벤더 중립 확장 표준

원문: [AWS Supports Agent Plugins: An Open Standard for Portable Agent Extensions](https://aws.amazon.com/blogs/opensource/aws-supports-agent-plugins-an-open-standard-for-portable-agent-extensions/)

## 요약

AWS의 Libby Clark와 James Ward가 2026년 8월 6일에 공개한 글로, Agent Plugins 1.0.0이라는
벤더 중립 명세를 소개한다.
AI 에이전트 확장을 어떻게 패키징하는지 표준화하는 것으로, 한 번 패키징해 어떤 클라이언트에든
보낼 수 있는 공통 패키징 형식을 제공한다.

해결하려는 문제는 파편화다.
이 표준 이전에는 확장 제작자가 한 클라이언트에 맞추고, 다른 클라이언트에 다시 쓰고, 모든
도구에 대해 그것을 반복해야 했다.
글은 이것을 패키지 매니저 이전의 JavaScript나 컨테이너 표준화 이전의 시대 — 개발자가 호환되지
않는 시스템 전반에서 의존성을 수동으로 관리하던 — 에 비유한다.

작동은 디렉터리 구조와 JSON 매니페스트로 이뤄진다.
매니페스트가 정체성과 진입점을 선언하고, 클라이언트는 폴더를 스캔해 컴포넌트를 발견한다 —
`skills/` 폴더가 있으면 스킬을 로드하고, MCP 설정이 있으면 그 서버에 연결한다.
Model Context Protocol(MCP)과의 관계는 보완이다 — MCP는 도구 연결성을 다루고 Agent Plugins는
확장 패키징을 표준화하며, 둘은 더 넓은 생태계 안에서 함께 작동한다.

“이식 가능한 에이전트 확장(portable agent extensions)”은 스킬·MCP 서버·훅·서브에이전트 같은
재사용 컴포넌트를 벤더 잠금 없이 여러 도구에 걸쳐 쓰는 것을 뜻한다.
같은 패키지가 Kiro, VS Code, Cursor 또는 호환 플랫폼에서 동작한다.
AWS는 Cursor, Microsoft, OpenAI, Vercel과 함께 기술 운영 위원회(Technical Steering Committee)의
창립 멤버이며, 거버넌스 구조는 한 회사의 제품 로드맵이 형식의 방향을 지시하지 못하게 한다.
1.0.0은 Agent Skills와 MCP 서버를 표준화하고, 훅과 커스텀 에이전트는 향후 버전으로 계획되어
있다.

## 분석

### 이 표준의 진짜 겨냥은 MCP가 남긴 빈칸이다

MCP가 “에이전트가 도구에 연결하는 방법”을 표준화했다면, Agent Plugins는 “그 도구와 스킬을
어떻게 묶어 배포하는가”를 표준화한다.
글이 둘을 보완으로 규정한 것이 정확하다 — MCP는 연결 프로토콜이고 Agent Plugins는 패키징
형식이다.

이 구별이 중요한 이유는 두 문제가 다른 층위이기 때문이다.
MCP가 있어도 여전히 스킬과 훅과 서브에이전트를 각 클라이언트의 형식으로 따로 만들어야 했고,
그 파편화가 확장 생태계의 성장을 막았다.
같은 스킬을 Claude Code용, Cursor용, VS Code용으로 세 번 만들어야 한다면 확장 제작자는 하나만
지원하거나 아무것도 안 만든다.
Agent Plugins는 그 반복을 없애 “한 번 만들어 모든 곳에”를 목표로 하며, 이것이 확장 생태계의
임계 질량을 만드는 조건이다.

이 접근이 앞서 여러 문서에서 본 패턴과 이어진다.
DeepSeek Harness의 “모든 것이 플러그인”[^ref-deepseek]과 Kiro Crew의 확장성이 각자의 플러그인
생태계를 만들었는데, Agent Plugins는 그 생태계들을 가로지르는 공통 형식을 겨냥한다.
개별 하네스가 자기 플러그인 시스템을 갖는 것과, 그 플러그인이 하네스를 가로질러 이식 가능한
것은 다른 문제이며, 후자가 이 표준의 값이다.

### 다섯 경쟁사의 공동 거버넌스가 이 표준의 성패를 가른다

Agent Plugins의 가장 눈에 띄는 특징은 기술적 설계가 아니라 거버넌스다.
AWS, Cursor, Microsoft, OpenAI, Vercel이 함께 창립 위원회 멤버라는 것은, 서로 경쟁하는 회사들이
하나의 형식에 합의했다는 뜻이다.

이 공동 거버넌스가 결정적인 이유는 표준의 채택이 중립성에 달려 있기 때문이다.
한 회사가 만든 형식은 그 회사의 이익에 종속된다는 의심을 받아 경쟁사가 채택하지 않는다.
글이 “한 회사의 제품 로드맵이 형식의 방향을 지시하지 못한다”고 명시한 것은, 이 표준이 특정
벤더의 전략 도구가 아님을 보증하려는 것이다.
OpenAI와 Microsoft와 AWS가 같은 위원회에 있다는 것 자체가, 어느 한 곳도 이 형식을 독점할 수
없다는 구조적 보증이다.

그러나 이 다자 거버넌스에는 대가가 있다.
경쟁사들의 합의로 움직이는 표준은 느리고, 각 회사의 이해가 충돌할 때 진전이 막힌다.
1.0.0이 Agent Skills와 MCP 서버만 표준화하고 훅과 커스텀 에이전트를 미룬 것이 그 신중함의
흔적일 수 있다 — 가장 논쟁 없는 부분부터 합의하고 어려운 부분을 뒤로 미룬 것이다.
다자 표준의 역사가 보여주듯, 위원회의 합의가 빠른 혁신을 따라잡지 못하면 표준이 현실보다
뒤처진다.

### 패키지 매니저 비유가 이 표준의 야심과 위험을 동시에 드러낸다

글이 든 비유 — 패키지 매니저 이전의 JavaScript, 컨테이너 표준화 이전의 시대 — 는 이 표준의
야심을 명확히 한다.
npm이 JavaScript 생태계를, Docker가 배포를 바꾼 것처럼, Agent Plugins가 에이전트 확장 생태계를
바꾸겠다는 것이다.

이 비유가 야심을 드러내는 이유는 그 선례들의 영향력 때문이다.
npm 이전에는 JavaScript 라이브러리를 수동으로 관리했고, npm 이후에는 의존성 설치가 한 줄이
됐으며, 그 편의가 JavaScript 생태계를 폭발시켰다.
Agent Plugins가 그 역할을 에이전트 확장에서 하겠다는 것은, 확장 설치를 표준화해 생태계의
성장을 촉발하겠다는 것이다.
스킬 하나를 만들면 모든 클라이언트에서 쓸 수 있다면, 확장 제작의 인센티브가 근본적으로 커진다.

그러나 같은 비유가 위험도 드러낸다.
npm은 편의를 준 대신 의존성 지옥, 공급망 공격, 좌파드(left-pad) 사건 같은 문제를 낳았다.
Agent Plugins가 확장 설치를 쉽게 만들면, 같은 문제 — 신뢰할 수 없는 확장의 확산, 공급망 공격,
버려진 확장에 대한 의존 — 가 에이전트 생태계에 온다.
앞서 DeepSeek Harness 문서에서 `invaliduser`가 “플러그인 피로”를 경고한 것[^ref-deepseek]이
정확히 이 위험이며, 표준화가 그 위험을 생태계 규모로 확대한다.

## 비평

### “벤더 중립”이 실제로는 “대형 벤더들의 카르텔”일 수 있다

Agent Plugins의 거버넌스가 벤더 중립을 표방하지만, 창립 위원회가 AWS, Cursor, Microsoft, OpenAI,
Vercel이라는 사실은 중립의 성격을 다시 보게 만든다.
이들은 서로 경쟁하지만 모두 대형 상용 플레이어이며, 소규모 오픈소스 하네스나 독립 개발자는
위원회에 없다.

이 구성이 문제인 이유는 표준이 누구의 필요를 반영하느냐를 결정하기 때문이다.
다섯 대형 회사가 합의한 형식은 그들의 공통 이해 — 각자의 플랫폼에서 확장이 돌게 하는 것 —
를 반영하지만, 그것이 반드시 확장 제작자나 사용자의 이해와 일치하지는 않는다.
예컨대 확장의 수익화, 검증, 신뢰 모델처럼 대형 벤더에게 유리하고 독립 제작자에게 불리할 수
있는 결정들이, 이 위원회의 합의로 정해진다.
“한 회사가 방향을 지시하지 못한다”는 보증은 독점을 막지만, 다섯 회사의 카르텔이 방향을
지시하는 것은 막지 못한다.

이 구조가 앞서 여러 표준의 역사와 이어진다.
웹 표준이 브라우저 벤더들의 합의로 움직이면서 그 벤더들의 이해를 반영했듯이, Agent Plugins도
대형 에이전트 플랫폼들의 이해를 반영할 것이다.
진짜 벤더 중립이라면 위원회에 독립 하네스(Zed, Aider), 오픈소스 프로젝트, 확장 제작자 대표가
있어야 하는데, 현재 구성은 상용 플랫폼에 편중되어 있다.
이 편중이 1.0.0에서 무엇을 표준화하고 무엇을 미뤘는지 — 스킬과 MCP는 넣고 수익화와 검증은
빠진 — 에 이미 반영되어 있을 수 있다.

### 폴더 스캔 기반 발견이 보안과 확장성에서 약하다

기술 설계 — 디렉터리를 스캔해 `skills/` 폴더나 MCP 설정을 발견하는 것 — 는 단순해서 매력적이지만,
그 단순함이 보안과 확장성의 약점을 만든다.
클라이언트가 폴더를 스캔해 자동으로 컴포넌트를 로드한다는 것은, 그 폴더에 무엇이 들어오는지에
대한 통제가 느슨하다는 뜻이다.

이 설계가 보안에서 위험한 이유는 자동 로딩 때문이다.
`skills/` 폴더가 있으면 스킬을 로드하고 MCP 설정이 있으면 서버에 연결한다면, 악의적 패키지가
그 규약을 이용해 원치 않는 스킬이나 서버를 주입할 수 있다.
앞서 Dogwood 문서에서 본 “도구 호출 경계의 통제”[^ref-dogwood]가 필요한 이유가 여기 있는데,
Agent Plugins의 발견 메커니즘은 그 경계 이전에 무엇이 로드되는지를 폴더 구조에 맡긴다.
서명, 검증, 권한 선언 같은 보안 장치가 1.0.0 명세에 어떻게 들어가는지가 이 표준의 안전성을
결정하는데, 발표는 그것을 다루지 않는다.

확장성에서도 폴더 스캔은 한계가 있다.
컴포넌트 유형이 늘어날수록(1.0.0의 스킬·MCP에서 향후 훅·커스텀 에이전트로) 스캔할 폴더 규약이
늘고, 그 규약들의 상호작용 — 훅이 스킬을 수정하거나 서브에이전트가 MCP를 쓰는 — 이 복잡해진다.
단순한 폴더 스캔은 평면적 컴포넌트에는 맞지만, 컴포넌트 간 의존과 순서가 필요한 복잡한 확장에는
표현력이 부족하다.
npm의 `package.json`이 단순한 폴더 규약을 넘어 정교한 의존성 그래프를 표현하게 진화한 것처럼,
Agent Plugins도 폴더 스캔을 넘어서야 할 텐데 그 진화의 경로가 아직 없다.

### 표준이 파편화를 없애는 것이 아니라 한 층 위로 옮길 수 있다

Agent Plugins의 약속 — 한 번 패키징해 모든 클라이언트에 — 는 파편화를 없애는 것처럼 보이지만,
실제로는 파편화를 패키징 층에서 실행 층으로 옮길 위험이 있다.
같은 형식으로 패키징해도, 각 클라이언트가 스킬과 MCP 서버를 다르게 해석하고 실행하면 “이식
가능”은 명목뿐이다.

이 위험이 실질적인 이유는 컴포넌트의 의미가 실행 환경에 의존하기 때문이다.
스킬이 Kiro에서 접근하는 도구와 Cursor에서 접근하는 도구가 다르면, 같은 스킬 패키지가 두
클라이언트에서 다르게 동작한다.
포장은 표준화됐지만 내용물의 실행은 표준화되지 않았다면, 확장 제작자는 여전히 각 클라이언트에서
테스트하고 조정해야 한다.
앞서 SDUI 문서에서 본 “표준화됐지만 각 렌더러가 다르게 해석하면 이식성은 명목뿐”이라는
문제가[^ref-sdui] 여기 그대로 적용된다.

이 문제가 다자 거버넌스와 결합되면 더 심각해진다.
패키징 형식은 다섯 회사가 합의했지만, 각 회사가 그 패키지의 컴포넌트를 자기 플랫폼에서 어떻게
실행할지는 각자의 결정이다.
표준이 “무엇을 담는가”를 정하고 “어떻게 실행하는가”를 각 벤더에 맡기면, 벤더들은 그 실행에서
차별화하려 할 것이고 그것이 미묘한 비호환을 만든다.
진짜 이식성은 패키징뿐 아니라 실행 의미론까지 표준화해야 하는데, 그것은 각 벤더의 차별화 여지를
없애므로 다자 합의가 가장 어려운 부분이다.
1.0.0이 그 부분을 다루지 않았다면, “이식 가능”이라는 약속은 아직 절반이다.

## 인사이트

### 경쟁사들의 공동 표준은 시장이 성숙 단계에 들어섰다는 신호다

AWS, OpenAI, Microsoft, Cursor, Vercel이 하나의 형식에 합의한 것은 에이전트 도구 시장의 국면
전환을 보여준다.
경쟁이 치열한 초기 시장에서는 각자 자기 형식으로 차별화하려 하고, 성숙한 시장에서는 공통
표준으로 생태계를 키우려 한다.

이 전환이 구조적인 이유는 표준의 값이 시장 크기에 비례하기 때문이다.
시장이 작을 때는 자기 형식을 고수해 사용자를 잠그는 것이 이득이지만, 시장이 커지면 파편화가
전체 생태계의 성장을 막아 모두가 손해를 본다.
확장 제작자가 다섯 형식을 각각 지원할 수 없어 하나만 지원하거나 포기하면, 어느 플랫폼도 풍부한
확장 생태계를 갖지 못한다.
다섯 회사가 공동 표준에 합의한 것은, 파편화의 비용이 잠금의 이득을 넘어섰다는 판단이다.

이 관점의 2차 효과는 경쟁 축의 이동이다.
확장 형식이 표준화되면 경쟁은 “누가 더 많은 확장을 가졌는가”에서 “누가 표준 확장을 더 잘
실행하는가”로 옮겨 간다.
앞서 grok-4-6 문서에서 본 “모델이 수렴하면 경쟁이 인프라와 비용으로 이동한다”는 패턴이[^ref-grok]
확장 생태계에도 적용된다 — 형식이 공통이 되면 차별화는 실행 품질, 성능, 통합 깊이로 이동한다.
이 표준의 성공은 역설적으로 이 다섯 회사가 확장 자체로는 더 이상 차별화하지 못하게 만드는
것이며, 그것이 그들이 이 합의를 감수한 이유이자 이 표준의 진짜 무게다.

### 패키징 표준이 “좋은 확장”이 아니라 “많은 확장”을 만든다

Agent Plugins가 npm을 모델로 삼은 것은 확장의 양적 폭발을 겨냥한 것이지만, npm의 역사가 보여주듯
패키징의 쉬움은 품질을 보증하지 않는다.
설치가 한 줄이 되면 확장은 늘지만, 그 확장의 신뢰성과 유지보수는 별개의 문제로 남는다.

이 구별이 중요한 이유는 확장 생태계의 진짜 병목이 제작이 아니라 신뢰이기 때문이다.
표준이 제작과 배포를 쉽게 만들면 수천 개의 확장이 생기지만, 그중 어느 것을 신뢰할 수 있는지,
어느 것이 유지보수되는지, 어느 것이 안전한지를 판별하는 문제가 그만큼 커진다.
앞서 여러 문서에서 “스타 수는 신뢰의 근거가 아니다”라고 했는데[^ref-jolt], 확장 생태계에서는
그 신뢰 판별이 사용자마다 반복되어야 하는 부담이 된다.
npm의 공급망 공격, 타이포스쿼팅, 버려진 패키지 문제가 에이전트 확장에서 반복될 것이며, 그
문제들은 패키징 표준이 아니라 별도의 신뢰 인프라 — 서명, 감사, 평판 — 를 요구한다.

이 통찰의 실무적 함의는 표준의 다음 과제가 신뢰라는 것이다.
Agent Plugins 1.0.0이 스킬과 MCP의 패키징을 표준화했다면, 2.0의 진짜 과제는 훅과 커스텀 에이전트를
더하는 것이 아니라 그 확장들을 신뢰할 수 있게 만드는 메커니즘이다.
서명된 패키지, 권한 선언, 검증된 레지스트리가 없으면, 이식 가능성은 악의적 확장의 이식 가능성이기도
하다.
앞서 Dogwood가 도구 호출 경계에서 에이전트를 통제하려 한 것처럼[^ref-dogwood], 확장 생태계도
설치 경계에서 신뢰를 통제해야 하며, 그것이 이 표준이 아직 다루지 않은 절반이다.

### 다자 거버넌스가 혁신 속도와 안정성을 맞바꾼다

다섯 경쟁사의 공동 위원회로 움직이는 표준은 안정성을 주는 대신 속도를 희생하며, 이 트레이드오프가
에이전트 도구처럼 빠르게 진화하는 분야에서 특히 첨예하다.
1.0.0이 가장 논쟁 없는 부분(스킬, MCP)만 표준화한 것이 이 신중함의 흔적이다.

이 트레이드오프가 근본적인 이유는 표준화의 대상이 움직이는 표적이기 때문이다.
에이전트 확장의 형태 — 스킬이 무엇이고 훅이 어떻게 작동하고 서브에이전트가 무엇을 하는지 —
가 아직 빠르게 변하는데, 그것을 다섯 회사의 합의로 표준화하면 그 합의가 이뤄질 때쯤 형태가
이미 바뀌어 있을 수 있다.
빠른 단일 벤더 표준(예: Anthropic의 MCP)은 현실을 앞서갈 수 있지만, 다자 표준은 현실을 뒤따르며
합의된 부분만 안정화한다.

이 통찰은 표준의 역할에 대한 재평가로 이어진다.
Agent Plugins의 값은 최신 혁신을 표준화하는 것이 아니라, 이미 안정된 부분(스킬, MCP)을 이식
가능하게 만들어 그 위에서 각 벤더가 혁신하게 하는 것이다.
안정된 하부를 표준화하고 불안정한 상부를 벤더에 맡기는 이 구조는, 앞서 여러 문서에서 본
“안정된 코어와 혁신하는 셸”의 또 다른 형태다.
이 표준이 성공하려면 무엇을 표준화하지 않을지 — 아직 변하는 부분을 강제로 굳히지 않는 것 —
를 아는 규율이 필요하며, 1.0.0의 좁은 범위가 그 규율의 초기 신호일 수 있다.
다자 표준의 지혜는 빠르게 많이 표준화하는 것이 아니라, 늦더라도 안정된 것만 표준화하는 데 있다.
