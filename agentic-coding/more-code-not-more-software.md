# 코드는 30% 늘었지만 소프트웨어는 늘지 않았다: 코드 리뷰라는 병목

원문: [AI coding agents generate more code, but not more software - Ars Technica](https://arstechnica.com/ai/2026/10/ai-coding-agents-generate-more-code-but-not-more-software/)

HN 토론: <https://news.ycombinator.com/item?id=50059523> (314점, 275개 댓글)

GN 토론: <https://news.hada.io/topic?id=35257>

## 요약

Ars Technica의 Kyle Orland가 2026년 10월 9일 쓴 기사로,
하버드대 Fiona Chen과 James Stratton의 구직 논문(job market paper)
「Artificial Intelligence in the Firm: Bottlenecks in Software Production」을
소개한다.
기사의 요지는 AI 코딩 에이전트가 코드를 훨씬 많이 만들지만,
사람의 코드 리뷰가 병목이 되어 기업 단위의
소프트웨어 산출과 고용은 거의 바뀌지 않았다는 것이다.
논문은 코딩 단계의 효율 향상이 생산 과정 하류의 제약에 “흡수”된다고 표현한다.

연구는 엔지니어링 분석 플랫폼 Jellyfish의 집계 데이터를 썼다.
2021년 1월부터 2026년 3월까지 718개 기업, 70만 명 넘는 직원의
커밋과 풀 리퀘스트 같은 “작업 이벤트” 약 3억 건과 Jira 이슈,
Google Calendar 일정이 들어 있다.
GitHub Copilot, Cursor, Claude Code 사용 데이터와 GitHub 활동으로
각 기업이 AI 코딩 보조 도구(사람이 쓰는 코드를 자동 완성)와
AI 코딩 에이전트(프롬프트로 코드를 대체로 자율 작성·제출)를
언제 도입했는지 판정하고,
도입 시점 차이를 이용한
이중차분(difference-in-differences) 회귀로 효과를 추정했다.

코드 양의 변화는 분명했다.
에이전트를 도입한 기업에서 코드 줄 수는 30%,
커밋은 20%, 풀 리퀘스트는 23% 늘었다.
보조 도구는 각각 12%, 9%, 5% 늘었지만 커밋만 통계적으로 유의했다.
그러나 Jira 이슈와 에픽(기능 단위 작업)의 해결 건수는
도입 전후로 통계적으로 유의한 변화가 없었다.
에이전트의 경우 산출 증가가 기준치의 12%를 넘지 않는다고 배제할 수 있었고,
이는 개인 수준의 30% 생산성 향상보다 훨씬 낮다.
이슈의 크기나 복잡도가 바뀌었을 가능성은
머신러닝으로 이슈 해결 예상 시간을 추정해 확인했고 변화가 없었다.
고용도 AI 탓으로 돌릴 만한 변화가 없었다.
LinkedIn 기준 전체 고용은 2.9% 넘는 감소를, Jellyfish 기준 엔지니어 고용은
13.8% 넘는 감소를 배제할 수 있었다.

차이는 코드 리뷰에서 나왔다.
에이전트 도입 후 풀 리퀘스트 제출부터 병합까지의 리뷰 시간은 평균 49% 늘었고,
변경 요청을 받는 풀 리퀘스트 비율은 거의 두 배가 되었으며,
풀 리퀘스트당 댓글은 35% 늘었다.
기업들은 리뷰에 인력을 돌려 코드 리뷰를 하는 직원 비율이 14% 늘었다.
2026년 3월까지 측정 기업의 80%가 어떤 형태로든 AI 코드 리뷰를 썼지만,
AI 에이전트가 단 리뷰 댓글은 23.3%, 연 풀 리퀘스트는 10.8%에 그쳐
리뷰 대부분은 여전히 사람이 했다.
논문은 Prolific 엔지니어 100명 설문으로 엔지니어가
시간의 30~40%만 코드 작성에 쓴다는 추정을 검증했고,
AI가 코드의 양과 함께 리뷰에 들어오는 초안의 품질을 바꿔
리뷰 수요를 키우는 생산 모형을 제시한다.

기사는 데이터가 2026년 3월에 끝났고 그 뒤 에이전트가 크게 발전했으며,
연구 대상 기업의 95%가 에이전트를 도입한 지
얼마 되지 않아 학습 과정에 있다는 단서를 단다.
그러면서 지금으로서는 AI에게 코드를 맡기는 것이
코딩 속도 증가가 비슷한 크기의
리뷰 부담 증가로 상쇄되는 양날의 검으로 보인다고 맺는다.

## 분석

### 개인 생산성과 기업 산출 사이의 “전달률”을 잰 연구다

이 연구의 가치는 측정 단위에 있다.
AI 코딩 도구의 효과를 다룬 기존 연구 대부분은 개인의 과제 단위 생산성을 쟀다.
이 논문은 기업 단위 도입을 처리 변수로 삼고,
코드 작성이라는 중간 산출에서 이슈 해결이라는 최종 산출,
그리고 고용까지 이어지는 사슬 전체를 같은 데이터로 본다.
그래서 “개인이 30% 더 많이 쓴다”와 “회사가 30% 더 많이 출시한다” 사이의 간극,
즉 생산성 향상의 전달률(pass-through)을 직접 잴 수 있다.

같은 결론은 다른 데이터에서도 나왔다.
GitHub 개발자 10만 명을 본 [NBER 논문](../ai/writing-code-vs-shipping-code.md)은
에이전트가 코드 줄 수를 여덟 배로 늘렸지만
릴리스는 30% 늘었을 뿐이라고 보고했고,
Narayanan과 Kapoor는 이를 근거로
[결정-실행-제공 샌드위치](../ai/why-ai-wont-replace-software-engineers.md)를 제시했다.
측정 방법이 다른 두 연구가 같은 방향을 가리킨다는 점이 이 결과를 무겁게 만든다.

### 병목 이론의 교과서적 사례다

논문이 기대는 이론은 경제학의 병목 모형이다.
생산이 여러 보완적 단계로 이루어지면 한 단계의 생산성이 아무리 올라도
다른 단계가 전체 산출을 묶는다.
HN의 pjmorris는 이를 Amdahl의 법칙으로 요약했다.[^pjmorris]
시스템 한 부분을 최적화해서 얻는 성능 향상은
그 부분이 실제로 쓰이는 시간 비율로 제한된다는 것이다.
blauditore는 경주용 자동차의 엔진이 아무리 강해져도
타이어가 접지력을 제한하면 차는 거의 빨라지지 않는다고 비유했다.[^blauditore]

논문이 한 걸음 더 나간 부분은 AI가 리뷰 단계에 두 가지로 영향을 준다는 모형이다.
코드 양이 늘어 리뷰할 것이 많아지고,
초안의 품질이 바뀌어 단위 코드당 리뷰 노력이 달라진다.
변경 요청 비율이 두 배가 되고 댓글이 35% 늘었다는 것은
두 번째 경로, 즉 품질 쪽이 리뷰 부담을 키웠다는 증거다.

### 고용에 대한 함의가 엇갈린다는 점을 모형이 드러낸다

논문 모형에서 두 경로는 노동 수요에 반대 방향으로 작용한다.
산출이 고정되어 있다면 코딩 생산성 향상은 필요한 코딩 노동을 줄이지만,
초안 품질 저하는 검증 노동 수요를 늘린다.
리뷰하는 직원 비율이 14% 늘었다는 결과는 노동이 사라지기보다
리뷰 쪽으로 재배치되고 있음을 보여 준다.

## 비평

### 데이터 시점이 결론의 수명을 짧게 만든다

기사도 인정하듯 데이터는 2026년 3월에 끝나고,
본 분석에 쓰인 에이전트는 그보다 이른 시기의 모델이다.
HN의 jefftk는 주 에이전트 결과에 쓰인 모델이 Claude 3.5부터 Sonnet 4.5,
GPT-4.1부터 GPT-5, Gemini 2.5 수준이라며
2025년의 그림을 현재 뉴스처럼 보도한다고 지적했다.[^jefftk]
geraneum은 논문이 두 번 갱신되었고 마지막은
2026년 8월이라고 반박했고,[^geraneum]
archagon은 그런 논리라면 LLM을 쓴 작업에 대한
연구는 아예 불가능하다고 받았다.[^archagon]

둘 다 맞다.
연구는 늦을 수밖에 없지만,
그렇다고 이 결과가 지금의 도구에도 그대로 적용된다는 뜻은 아니다.
특히 리뷰 병목은 AI 리뷰 도구의 성능에 크게 좌우되고,
그 도구는 데이터 이후에 빠르게 바뀌었다.
연구가 보여 준 것은 병목이 생긴다는 구조이지 병목의 크기는 아니다.

### “소프트웨어”를 Jira 티켓으로 정의했다

dcre는 이 연구가 “더 많은 소프트웨어”를
“더 많이 닫힌 티켓”으로 정의했다는 점을 짚었다.[^dcre]
저자들은 티켓 범위가 바뀌지 않았으니 좋은 척도라고 주장하지만,
에이전트 덕분에 더 쓰게 된 테스트가 티켓에 잡히느냐는 질문이 남는다.
keithnz는 자기 팀은 더 많은 소프트웨어를 만들고 더 야심 찬 것을 개발하며,
제품을 직접 써 보고 다듬는 데 훨씬 많은 시간을 쓴다고 반박했다.[^keithnz]
티켓 수가 그대로여도 각 티켓의 완성도가 올랐다면 연구는 그것을 보지 못한다.

dolebirchwood와 joshheitzman은 표본 자체를
문제 삼았다.[^dolebirchwood][^joshheitzman]
Jellyfish를 쓰는 기업은 엔지니어링 활동을 분석 플랫폼으로 관리할 만큼
절차가 갖춰진 회사이고, 그런 절차가 바로 병목의 원천일 수 있다.
KumaBear는 개인용 소프트웨어는 폭발적으로 늘었다고 했다.[^KumaBear]
이 연구가 보여 주는 것은 “기업이 정한 절차 안에서의” 소프트웨어 산출이고,
그 바깥에서 늘어난 소프트웨어는 처음부터 측정 대상이 아니었다.

### 리뷰를 줄이면 된다는 반론은 리뷰의 기능을 좁게 본다

기사의 결론에 대해 HN에서는 리뷰 자체를 바꾸자는 의견이 많았다.
staminade는 시니어 엔지니어들이 에이전트가 얼마나 좋아졌든
한 줄씩 보는 리뷰를 포기하지 못한다고 했다.[^staminade]
sroerick은 코드 리뷰가 한 줄 단위로 버그를 잡으리라 기대한 적이 있느냐며,
자신에게 리뷰는 기본 점검과 모범 사례 전파,
신입 교육의 기회였다고 말했다.[^sroerick]
cobbal은 한 줄씩 리뷰하며 소프트웨어의
정신 모형을 만들고 중요한 버그를 많이 찾는다고 반박했다.[^cobbal]

zmmmmm은 논의에서 빠진 차원을 짚었다.[^zmmmmm]
코드 리뷰는 품질만이 아니라 책임과 보안의 장치라는 것이다.
자동 리뷰는 코드가 의도대로 동작하는지는
확인하지만 의도 자체가 옳았는지는 확인하지 못하고,
백도어를 넣거나 테스트를 우회하는 일은 자동 리뷰로 잡히지 않는다.
fasterik은 API 설계와 테스트에 사람의 책임을 두고
구현 코드의 한 줄씩 리뷰는 줄이자는 대안을 냈다.[^fasterik]
리뷰를 줄여 병목을 없앤다는 처방은
리뷰가 지금까지 맡아 온 책임을 어디로 옮길지 답해야 성립한다.

## 인사이트

### 병목은 사라지지 않고 위로 이동한다

리뷰가 병목이라면 다음 단계는 리뷰를 자동화하는 것이다.
그러나 cyb_는 병목이 리뷰가 아니라 원래부터 품질이었다고 고쳐 말했다.[^cyb_]
리뷰는 설계와 코드 품질의 문제가 드러나는 장소일 뿐이라는 것이다.
jmward01은 병목이 언제나 제품을 함께 발전시키는 팀 전체였고,
분명하고 실행 가능한 비전을 갖고
올바른 다음 걸음을 고르는 것이 늘 문제였다고 했다.[^jmward01]
matsemann은 자기 팀이 더 많은 유용한 기능을 내놓지 못했고,
오히려 잘못된 방향으로 더 빨리 달리거나
범위가 끝없이 늘어난다고 적었다.[^matsemann]

이 증언들은 병목의 이동 경로를 보여 준다.
코딩이 빨라지면 리뷰가 막히고, 리뷰를 자동화하면 그다음은
무엇을 만들지 정하는 결정과 방향 설정이 막힌다.
mohamedkoubaa의 말처럼 방향이 틀린 로켓은 화성에 가지 못하며,
코드 리뷰의 다음 진화는 조향일 것이다.[^mohamedkoubaa]

### 리뷰 노동은 새로운 소진의 원천이 된다

PacificSpecific은 친구가 일의 80%가 Claude가 낸 코드를 리뷰하는 것이라
처음으로 회사를 그만뒀다고 전했다.[^PacificSpecific]
atleastoptimal은 하루 1,000줄 리뷰하던 것을 이제 10,000줄 “리뷰”한다며,
뇌가 열 배 빨라지지 않았으니 시간을 열 배 쓰든지
문제의 복잡도를 보고 AI가 맞을 거라고
받아들이든지 해야 한다고 적었다.[^atleastoptimal]

논문이 측정한 리뷰 시간 49% 증가와 리뷰어 비율 14% 증가는
이 경험을 숫자로 옮긴 것이다.
코드를 쓰는 일은 창작이지만 남이 쓴 코드를
검토하는 일은 주의력을 소모하는 감시다.
일의 구성이 작성에서 검토로 바뀌면
같은 시간을 일해도 일의 질감이 달라지고,
그 차이는 생산성 통계가 아니라 이직률에서 먼저 드러날 것이다.

### 이해하지 못한 코드가 레거시 부채로 쌓인다

jack_sunsetless는 코드가 늘어난 대가로 그 안에 무엇이 있는지 아는 사람이 줄고
버그가 늘어난다며,
기록적인 속도로 레거시 코드를 만들고 있는 것 같다고 했다.[^jack_sunsetless]
jacquesm은 에이전트가 반복적인 코드를 만들고 추출과 리팩터링 기회를 놓쳐
부풀고 읽기 어려운 코드가 된다고 지적했다.[^jacquesm]

리뷰 병목은 단기적으로는 속도를 늦추지만
장기적으로는 이 부채를 막는 마지막 장치이기도 하다.
리뷰를 줄여 병목을 풀면 출시 속도는 오르지만,
아무도 이해하지 못하는 코드의 비율도 함께 오른다.
기업이 선택하는 것은 지금의 속도와 몇 년 뒤의 유지보수 비용 사이의 교환이고,
이 연구는 그 교환이 시작되는 지점을 기록한 셈이다.
