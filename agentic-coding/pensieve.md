# Pensieve: 에이전트에게 grep 대신 로컬 색인을 쥐여 주는 Mac 앱

<https://tedhaley.ca/pensieve/>

<https://github.com/TedHaley/pensieve>

HN 토론: <https://news.ycombinator.com/item?id=50049508> (97점, 30개 댓글)

## 소개

Pensieve는 Ted Haley가 만든 Mac용 로컬 검색 앱이다.
문서와 폴더, git 저장소, Claude Code·Codex·Qwen Code의 에이전트 세션을
한 색인에 모아, 사람은 단축키로 띄우는 검색 패널로 쓰고
코딩 에이전트는 MCP로 같은 색인을 조회한다.
MIT 라이선스이고, 앱은 Apple Silicon과 macOS 14 이상이 필요하다.
저장소는 2026년 10월 8일에 만들어졌고, 이 노트를 쓸 때의 버전은 0.5.9다.

### 동작 방식

텍스트는 `Qwen3-Embedding-0.6B`로 임베딩해 SQLite에 저장하고,
정확한 문자열 검색을 위한 트라이그램 전문 색인과
turbovec 벡터 색인을 함께 둔다.
검색 문법은 의미 검색과 정확한 구절 검색을 섞을 수 있다.
따옴표는 정확히 일치하는 구절, 빼기 기호는 제외,
`kind:code`, `ext:pdf`, `in:` 같은 필터로 범위를 좁힌다.

색인은 FSEvents로 폴더, 저장소, 워크트리, 에이전트 대화 기록을 지켜보다가
마지막 저장 후 약 0.5초 뒤에 다시 색인한다.
커밋하지 않은 수정도 포함되고, 연결된 워크트리는
메인 체크아웃과 다른 파일만 브랜치 이름을 달고 색인된다.
검색 직전에 대기 중인 변경을 먼저 색인하고,
결과를 디스크의 파일과 비교해 바뀌었으면 다시 색인한 뒤 검색을 반복한다.
검색은 3만 5천 파일 저장소에서도 0.1~0.2초가 걸리고,
첫 색인은 Apple Silicon에서 분당 코드 파일 약 500개 속도라
3만 5천 파일 저장소는 한 시간 남짓 걸린다.

### 에이전트 연결

`pensieve mcp`로 stdio, 또는 HTTP로 붙는다.
기본으로 노출되는 MCP 도구는 `search`, `read`, `similar`, `who_knows`,
`knowledge_gaps`, `list_repos`, `team`, `unexplored`, `open`,
`current_scope`, `index_path` 열한 개다.
도구 설명이 매 턴 에이전트에게 전달되므로
기본 목록을 이렇게 줄였다고 README는 설명한다.

에이전트가 보는 범위는 스코프로 정한다.
기본값인 `auto`는 에이전트의 작업 폴더를 보고
그 저장소와 워크트리, 그 저장소에서 돌린 세션만 보여 주며,
색인되지 않은 저장소에서는 grep을 쓰라고 안내한다.

`pensieve integrate recommended`는 설치된 에이전트들에 MCP를 연결하고,
Claude Code·Codex·Gemini CLI의 지침 파일에
“grep하기 전에 검색하라”는 블록을 넣는다.
Claude Code에는 검색 스킬과 두 개의 훅도 추가한다.
편집 후 바뀐 경로를 Pensieve에 알리는 `PostToolUse` 훅(편집마다 약 50ms 추가)과,
색인되지 않은 저장소에서 세션이 시작되면
색인할지 한 번 묻는 `SessionStart` 훅이다.
설치는 홈페이지가 제공하는 프롬프트를 코딩 에이전트에 붙여 넣어
에이전트가 `curl | sh` 설치 스크립트를 실행하게 하는 방식이다.

### 벤치마크

Pensieve는 `bench/`에 공개된 스크립트로 Claude Code 자체를 측정한다.
색인된 코드에서 과제를 생성하고(설명, 정의한 이름, 에러 문자열, 혼합),
Claude Sonnet을 헤드리스로 돌려 정답 파일을 찾는지 본다.
504, 1,783, 2,383, 34,847개 파일의 네 저장소에서
조정에 쓰지 않은 72개 과제를 두 번씩, 한 배치로 돌린 결과는 다음과 같다.

| 항목             | Grep, Glob, Read | Pensieve와 지침 블록 |
| ---------------- | ---------------- | -------------------- |
| 해결한 과제      | 123/144 (85%)    | 131/144 (91%)        |
| 조회당 도구 호출 | 3.44             | 1.97 (−43%)          |
| 조회당 비용      | 0.050달러        | 0.041달러 (−18%)     |
| 조회당 토큰      | 67k              | 57k (−16%)           |
| 조회당 시간      | 10.9초           | 8.6초 (−21%)         |

비용 절감은 저장소별로 6~28%였고 가장 큰 모노레포에서 가장 컸다.
144번 중 82번은 검색 한 번 만에 답했다.
검색만 따로 보면 정답 파일이 첫 결과로 오는 비율이
이름 94%, 에러 문자열 88%, 이름과 설명 혼합 74%, 설명 58%였고,
grep 한 번은 각각 54%, 92%, 0%, 0%였다.
비용은 Claude 프롬프트 캐시 상태에 좌우되므로
같은 배치 안에서만 비교하라고 적혀 있다.

### 그 밖의 기능과 개인정보

git blame으로 영역마다 누가 남은 코드를 썼는지 보여 주고,
주제를 물으면 그 분야를 가장 많이 아는 사람을 찾아 준다.
코드를 쓴 사람들이 더 이상 활동하지 않는 영역은 지식 공백으로 표시한다.
색인과 검색은 모두 로컬에서 돌고 계정이 없다.
비밀번호 관리자 내보내기, 키, `.env`,
자격 증명처럼 보이는 파일은 색인하지 않는다.
요약과 인사이트는 선택이며, 내장 Qwen 3.5 9B, LM Studio,
Claude Code나 Codex(이 경우 클라우드로 전송) 중에서 고른다.

## 분석

### 작성자의 진단은 grep이 아니라 grep의 반복을 겨냥한다

작성자 TedHaley는 HN 첫 댓글에서 문제를 두 가지로 정리했다.
에이전트는 grep으로 정확한 문자열을 찾고, 결과 몇 개를 읽고,
다시 grep하는 순환을 돌며 그때마다 토큰과 시간을 쓴다.
그리고 grep은 이미 이름을 아는 것만 찾을 수 있어서,
“결제 공급자의 rate limit을 처리하는 곳” 같은 질문에는
첫 시도 정답률이 0%라는 것이다.[^TedHaley]
에이전트가 코드를 많이 쓸수록 저장소가 커지고
grep 한 번의 비용도 지난달보다 비싸진다는 지적도 덧붙였다.

벤치마크 설계가 이 진단을 그대로 반영한다.
비교 대상은 “grep보다 똑똑한 검색”이 아니라
“Grep, Glob, Read를 여러 번 반복하는 에이전트”이고,
지표도 정답률보다 도구 호출 수와 조회당 비용이 앞에 놓인다.
즉 Pensieve가 파는 것은 검색 품질보다 에이전트의 탐색 경로를 짧게 만드는 일이다.

### 하이브리드 검색은 grep을 대체하지 않고 grep의 빈칸을 메운다

첫 결과 정확도 표는 Pensieve의 위치를 정직하게 보여 준다.
에러 문자열에서는 grep 한 번이 92%로 Pensieve의 88%보다 낫다.
이름 검색에서는 Pensieve가 94%로 grep의 54%를 크게 앞선다.
grep이 0%인 설명과 혼합 질의에서 Pensieve가 58~74%를 내는 부분이
의미 검색이 실제로 더하는 몫이다.

그래서 정확 일치용 트라이그램 색인과 벡터 색인을 함께 두는 설계가 중요하다.
따옴표 구절을 의미로 순위를 매기는 혼합 검색은
에이전트가 이미 쓰는 “정확한 식별자 찾기”를 버리지 않으면서
“이름을 모르는 것 찾기”를 추가하는 구조다.

### 에이전트가 도구를 쓰게 만드는 일이 도구를 만드는 일만큼 크다

FAQ의 한 문장이 이 프로젝트의 숨은 핵심을 말한다.
에이전트는 습관적으로 grep을 쓴다.
그래서 Pensieve는 MCP 서버만 제공하지 않고,
에이전트 지침 파일에 “grep하기 전에 검색하라”는 블록을 넣고
스킬과 훅까지 설치한다.
그렇게 해서 최신 벤치마크의 144번 실행 모두에서
에이전트가 Pensieve를 썼다고 한다.

벤치마크의 비교 대상 이름도 “Pensieve와 지침 블록”이다.
측정된 개선은 색인과 행동 유도가 합쳐진 결과이고,
둘을 분리한 수치는 공개되어 있지 않다.
MCP 도구가 아무리 좋아도 에이전트가 부르지 않으면 소용없다는 사실이
도구 설계의 절반을 프롬프트 설계로 만든다.

## 비평

### 벤치마크의 개선 폭은 헤드라인보다 좁다

해결률 차이는 123/144와 131/144, 즉 8번의 실행이다.
과제 72개를 두 번씩 돌린 것이라 독립 표본은 더 작고,
이 차이가 우연을 넘는지는 수치만으로 판단하기 어렵다.
비용 18% 절감도 Pensieve 스스로 프롬프트 캐시 상태에 따라 달라진다고 인정한다.

과제 생성 방식도 Pensieve에 유리할 수 있다.
과제는 색인된 코드 조각을 평이한 말로 설명하거나,
그 조각이 정의한 이름이나 에러 문자열을 써서 만든다.
조각 단위로 임베딩하는 검색기는 조각 단위로 만든 질문에 강할 수밖에 없다.
실제 작업에서 에이전트가 묻는 것은 여러 파일에 걸친 동작이나
아직 존재하지 않는 코드를 어디에 넣을지인 경우가 많다.

bjornroberg가 제안한 실험이 빠진 축을 짚는다.
품질이 다른 코드베이스에서 grep과 의미 검색의 토큰 비용을 비교하고,
올바른 네임스페이스의 같은 이름 심볼을
찾았는지까지 봐야 한다는 것이다.[^bjornroberg]
네 저장소의 평균만으로는 어떤 코드베이스에서 이 도구가 필요하고
어떤 곳에서 필요 없는지 알 수 없다.

### 색인은 뿌리 원인을 덮는 벽지일 수 있다

가장 강한 반론은 tinthedev에게서 나왔다.
grep으로 찾기에 저장소가 너무 크고,
`hard_decline`을 “카드 재시도”로 바꿔 말해야 찾을 수 있으며,
에이전트의 무작정 검색 순환을 줄여야 한다는 문제 자체가
코드베이스 위생이 나쁘다는 증상이라는 것이다.
관심사를 나누고 설계 단계를 조금만 신경 써도
grep이 병목이 되는 일은 드물다고 그는 주장했다.[^tinthedev]

반박도 있었다.
CharlieDigital은 도서관 목록과 마트 진열대처럼 색인은 어디에나 있고,
잘 정리된 코드베이스도 폴더 구조와 이름 규칙이라는 색인이라고 답했다.
문제는 에이전트 하네스가 처음부터 색인을 염두에 두고
설계되지 않았다는 점이라는 것이다.[^CharlieDigital]
cyanydeez는 대부분의 개발자가
자기가 일하는 코드베이스를 통제할 수 없다고 지적했다.[^cyanydeez]

두 입장은 모두 맞다.
다만 Pensieve의 홈페이지가 보여 주는 예시가 그 긴장을 드러낸다.
“카드 재시도가 왜 멈추는가”라는 질문에 답하는 것은
`hard_decline`이라는 이름과 사고 검토 문서를 이어 주는 색인이다.
코드의 이름이 도메인 언어와 어긋나 있다는 사실은 그대로 남고,
색인은 그 어긋남을 매번 메워 줄 뿐 고치지는 않는다.

### 같은 시도는 이미 여러 번 있었고 일부는 물러났다

sheo는 이런 도구를 스무 개쯤 봤고 매달 새 것이 나오며,
Cursor는 한때 비슷한 기능을 가졌다가 없앴다고 적었다.[^sheo]
boyter는 업계가 사전 색인을 하지 않는 쪽으로 수렴했고,
에이전트 작업에는 BM25에 약간의 손질을 더한 방식이 좋다고 봤다.[^boyter]
victorbjorklund는 실제로는 AI에게 grep을 쓰게 두는 편이
더 나은 결과를 냈다는 것이 흔한 설명이라고 덧붙였다.[^victorbjorklund]

TowerTall의 증언은 색인의 대가를 구체적으로 보여 준다.
Cursor는 로컬 색인을 없앴다고 하지만 실제로는 `.git` 아래에 숨겨 두었고,
그 색인이 자주 낡아서 파일을 많이 바꿀 때마다 폴더를 지워야 했으며,
낡았는지 알리는 스크립트까지 따로 돌렸다는 것이다.[^TowerTall]
Pensieve가 파일 감시, 검색 직전 색인, 결과와 디스크 비교라는
세 겹의 장치를 둔 것은 바로 이 문제에 대한 답이다.
그러나 ProblemExplorer가 물었듯,
같은 개념의 구현 세 개를 세 브랜치에서 탐색할 때
어느 것이 “낡은 맥락”인지는 정의되어 있지 않다.[^ProblemExplorer]
워크트리마다 브랜치 이름을 붙이는 방식은 출처를 알려 줄 뿐
어느 쪽을 믿어야 하는지는 알려 주지 않는다.

### 설치 경로가 도구의 신뢰를 깎는다

Pensieve는 에이전트에게 설치 프롬프트를 붙여 넣으면
에이전트가 `curl | sh`를 실행하고, 지침 파일과 훅을 고치고,
색인할 소스를 사용자에게 묻도록 설계되어 있다.
pcthrowaway는 이것이 “스크립트를 curl해서 bash로 넘기라”는 오래된 관행의
새 버전이냐고 물었고,[^pcthrowaway]
swiftcoder는 최근 몇 주 사이 바이브 코딩된 도구 사이트에서
이 방식을 여섯 번 넘게 봤다고 답했다.[^swiftcoder]

이 설치는 단순한 실행 파일 하나가 아니다.
`~/.claude/settings.json`에 편집마다 실행되는 훅을 넣고,
여러 에이전트의 지침 파일에 행동 규칙을 추가한다.
앱은 아직 공증(notarization)되지 않아
macOS 보안 설정에서 직접 열기를 허용해야 한다.
코드와 세션 전체를 색인하는 도구라면
설치 단계부터 무엇을 바꾸는지 사람이 검토하기 쉬워야 하는데,
에이전트에게 맡기는 설치는 그 검토를 건너뛰게 만든다.

## 인사이트

### 도구의 고객이 사람에서 에이전트로 바뀌면 홈페이지도 에이전트를 설득하게 된다

bentt는 이런 도구 소개 페이지가 언젠가 에이전트가 직접 설치 여부를 판단하도록
최적화될 것이라고 내다봤다.
사람은 “비용을 줄여 줘”라고만 말하고,
에이전트가 이런 도구를 찾아
사람이 알지도 못하는 사이에 쓰기 시작한다는 것이다.[^bentt]
david-gpu는 사람도 광고와 선전에 넘어간다고 받았다.[^david-gpu]

Pensieve는 이미 그 방향에 반쯤 와 있다.
설치 안내는 사람이 아니라 에이전트에게 읽히는 프롬프트이고,
설치가 끝나면 에이전트의 지침 파일에 “grep하기 전에 검색하라”는 규칙이 들어간다.
도구가 에이전트의 습관 자체를 바꾸도록 설계되면,
도구 사이의 경쟁은 기능이 아니라 지침 파일의 자리를 놓고 벌어진다.
여러 도구가 각자 “나를 먼저 써라”는 규칙을 넣기 시작하면
에이전트의 지침 파일은 광고판이 된다.

이 변화에서 사람이 지켜야 할 경계는 지침 파일과 훅 설정이다.
어떤 도구가 그 파일을 바꿨는지 추적하지 않으면,
에이전트가 왜 특정 도구를 먼저 부르는지 설명할 수 없게 된다.

### 코드 검색은 결국 조직의 기억 문제로 커진다

Pensieve가 코드 검색에 git blame 기반의
소유권과 지식 공백을 붙인 것은 우연이 아니다.
“이 코드가 어디 있나”라는 질문은 곧 “왜 이렇게 되었나”와
“누구에게 물어야 하나”로 이어진다.
홈페이지 예시가 코드 위치와 함께 사고 검토 문서와 담당자 이름을 돌려주는 것이
이 확장을 보여 준다.

이 흐름은 과거 사내 위키와 전문가 찾기 시스템이 걸어간 길과 닮았다.
2000년대 기업들은 문서 검색을 넘어 “누가 무엇을 아는가”를 찾는
전문가 디렉터리에 투자했고, 대부분은 정보가 낡으면서 버려졌다.
git blame은 사람이 손으로 갱신할 필요가 없다는 점에서 그보다 유리하지만,
코드를 마지막으로 만진 사람이 그 맥락을 아는 사람이라는 가정은
에이전트가 코드를 대량으로 쓰는 환경에서 약해진다.
에이전트가 쓴 줄은 커밋한 사람의 이름으로 남기 때문이다.

throwaway219450의 지적도 같은 지점을 가리킨다.
에이전트 기억이 쉬운 문제였다면 모델 회사들이 이미 하네스에 넣었을 것이고,
에이전트가 커밋 해시와 대화 ID를 적어 두는 평문 일지는
사람도 읽을 수 있고 모델이 바뀌어도 쓸 수 있다는 것이다.[^throwaway219450]
색인과 일지 중 어느 쪽이 조직의 기억이 될지는 아직 정해지지 않았다.

### 토큰 비용 절감 경쟁은 에이전트 하네스가 흡수할 가능성이 크다

Pensieve가 보여 준 18% 비용 절감은 실재하지만,
그 가치는 하네스가 같은 기능을 기본으로 넣는 순간 사라진다.
Cursor가 로컬 색인을 넣었다 빼고, 다시 숨겨서 쓰고 있다는 증언은
하네스 제작사도 이 문제와 씨름하고 있다는 뜻이다.
ryuuseijin의 slopdex처럼 비슷한 도구가 계속 나오고,
그중 일부는 중복 코드 탐지 같은 다른 문제로 범위를 넓히고 있다.[^ryuuseijin]

이런 시장에서 독립 도구가 살아남는 길은 하네스가 하기 어려운 일을 하는 것이다.
Pensieve의 경우 그것은 여러 에이전트와 여러 저장소, 문서와 세션을
한 색인으로 묶는 기능이다.
하네스는 자기 세션과 자기 작업 폴더만 보지만,
사용자는 Claude Code와 Codex를 오가며 같은 문제를 다룬다.
에이전트를 가로지르는 기억 계층이라는 위치는
특정 하네스가 흡수하기 어렵다.

그 대신 이 위치는
모든 에이전트의 대화 기록과 모든 저장소를 한곳에 모은다는 뜻이기도 하다.
로컬에서만 돈다는 약속이 그래서 이 도구의 가장 중요한 기능이 된다.
선택 사항인 클라우드 인사이트를 켜는 순간
그 약속의 범위가 바뀐다는 점을 사용자가 분명히 알 수 있어야 한다.
