# Apache Maka: 주장 대신 측정치로 말하는 에이전트 워크스페이스

<https://maka.apache.org/>

<https://github.com/apache/maka>

## 소개

Apache Maka(Incubating)는 “자신이 한 모든 일의 완전한 기록을
유지하는 고성능 에이전트 워크스페이스”를 표방하는 프로젝트다.
모델 메시지, 도구 호출, 권한 결정, 종료까지 모든 것을 append-only
런타임 이벤트로 기록한다.
핵심 지향점은 주장이 아니라 측정이다.
같은 모델을 쓰는 다른 에이전트 하네스와의 비교 결과를 공식
검증기(verifier)를 기준으로 벤치마킹하고, 작업 단위(per-task)
결과를 `docs/eval/`에 공개한다.

Maka는 로컬 우선(local-first) 설계를 취한다.
세션, 설정, 실행 기록은 사용자의 기기에 남으며, 모델은 클라우드
API, 로컬 모델, 호환 게이트웨이 중 사용자가 직접 선택해 붙인다.
데스크톱 앱, 터미널 UI(TUI), CLI라는 세 가지 인터페이스는 모두
하나의 실행 권위(Runtime Host)에 대한 얇은 클라이언트로만
동작하며, 평가(Eval) 시스템은 별도로 실험과 채점만 담당한다.

## 아키텍처

시스템은 다음과 같은 계층 구조를 따른다.

```text
Desktop / TUI / CLI → Runtime Host → SessionManager → AgentRun
                              ↓
              Model + Tool Runtime → Runtime Event Log
                              ↓
               Context / Session / UI projections
```

하위 계층에는 Experiment → Cells → Attempts → Results로 이어지는
평가 파이프라인이 있으며, Runtime Host가 이 실험 대상(subject)들을
실제로 실행한다.

주요 패키지 구성은 다음과 같다.

- `packages/runtime`: AgentRun, 모델 어댑터, 도구, 컨텍스트,
  복구 로직
- `packages/runtime-host`: Runtime Host의 생명주기와 프로토콜
- `packages/eval`: 셀·시도·결과로 구성된 실험 프레임워크
- `packages/mcp`: Model Context Protocol 클라이언트 통합
- `packages/storage`: 상태와 설정을 위한 SQLite 저장소
- `native/`: Rust로 작성된 네이티브 컴포넌트(peer addon, gitoxide
  헬퍼)

## 사용법

요구 사항은 Node.js 22.19 이상, npm, Git, ripgrep이다.
개발 빌드는 다음과 같이 실행한다.

```bash
npm ci
npm run dev
```

최초 실행 시에는 Settings → Models 메뉴에서 API 연결이나 로컬
모델, 계정 중 하나를 먼저 추가해야 작업을 시작할 수 있다.
CLI 사용 예시는 다음과 같다.

```bash
npm run cli:dev -- run "Task description"
npm run cli:dev -- run --graph "Multi-step task"
```

`--graph` 옵션은 복잡한 작업을 독립적인 조각(slice)으로 나눠
그래프 기반으로 실행하고, 그 결과를 감독하에 통합하는 기능을
지원한다.

워크스페이스 데이터는 Electron의 userData 디렉터리 아래
`workspaces/default/`에 저장되며, 여기에는 실시간 기록인
`runtime.sqlite`, 로컬 평문 비밀 값을 담은
`credential-vault.json`, `settings.json`, 아티팩트 폴더가
포함된다.
안전 재개(safe resume) 기능은 기본적으로 꺼져 있으며,
`MAKA_RUNTIME_SAFE_BOUNDARY_RESUME=1` 환경 변수로 활성화할 수
있다.

개발 기여 시에는 타입 체크, 빌드, 그리고 변경 규모에 비례하는
테스트가 요구된다.

```bash
npm run typecheck
npm run build
npm test
npm run check:release
```

모델 메타데이터는 `npm run refresh:model-metadata`로 최신
카탈로그를 받아 TypeScript 파일을 재생성한다.

## 분석

### “측정”을 프로젝트 정체성의 핵심으로 삼는 선택이 갖는 의미

에이전트 코딩 도구 시장은 각 프로젝트가 자신의 성능을 주장하는
방식으로 경쟁해 왔다.
Maka가 “주장 대신 측정”을 표방하고 공식 검증기 기준의 작업 단위
결과를 `docs/eval/`에 공개하는 것은, 이 시장의 신뢰 구조 자체를
겨냥한 설계 결정이다.
벤치마크 결과를 공개하는 것 자체는 드물지 않지만, 그 결과를
저장소 구조 안에 지속적으로 갱신되는 형태로 통합하고 다른
하네스와의 비교를 프로젝트 정체성의 일부로 삼는 것은 다른
층위의 약속이다.
이는 이 프로젝트가 Apache Software Foundation이라는 중립적
거버넌스 아래 들어가려는 이유와도 연결된다.
특정 기업의 마케팅 주장이 아니라 검증 가능한 수치로 신뢰를
쌓겠다는 방향은 재단 산하 프로젝트의 성격과 자연스럽게
맞아떨어진다.

### 이벤트 소싱이 “완전한 기록”이라는 약속의 기술적 근거가 된다

Maka의 핵심 설계는 현재 상태만 저장하는 대신 모델 메시지, 도구
호출, 권한 결정, 종료까지 모든 것을 append-only 이벤트로 남기는
이벤트 소싱(event sourcing) 패턴이다.
이 설계가 중요한 이유는, “완전한 기록을 유지한다”는 주장이
말뿐이 아니라 아키텍처 수준에서 강제된다는 데 있다.
현재 상태만 저장하는 시스템은 언제든 그 상태에 이르는 과정을
사후에 재구성할 수 없지만, append-only 로그는 원리적으로 그
로그 자체가 유일한 권위 있는 실행 기록(authoritative runtime
record)이 된다.
이는 감사 추적(audit trail)이 필요한 에이전트 실행 환경에서
특히 중요한데, 에이전트가 어떤 판단으로 어떤 도구를 호출했는지
사후에 정확히 재구성할 수 있어야 문제가 생겼을 때 원인을 추적할
수 있기 때문이다.

### 세 가지 인터페이스와 하나의 실행 권위라는 분리가 유지보수 부담을 낮춘다

데스크톱, TUI, CLI가 모두 하나의 Runtime Host에 대한 “얇은
클라이언트”로 설계된 것은, 여러 인터페이스를 지원하는 도구가
흔히 겪는 문제(각 인터페이스마다 로직이 중복되거나 미묘하게
어긋나는 문제)를 구조적으로 방지하려는 시도다.
Eval 시스템이 별도로 분리돼 실험과 채점만 담당한다는 것도 같은
원칙의 연장이다.
실행(Runtime Host)과 평가(Eval)라는 두 관심사를 명확히 나누면,
평가 로직의 변경이 실제 실행 경로에 영향을 주지 않는다는
보장을 얻을 수 있다.

## 비평

### 로컬 우선을 표방하면서도 비밀 값을 평문으로 저장하는 것은 그 원칙과 긴장 관계에 있다

`credential-vault.json`이 “로컬 평문 비밀 값(local plaintext
secrets)”을 저장한다는 설명은, 프로젝트가 강조하는 로컬 우선
설계와 미묘하게 충돌한다.
로컬 우선이라는 원칙은 흔히 “데이터가 사용자의 기기를 벗어나지
않는다”는 프라이버시 측면의 신뢰를 함의하는데, 그 데이터가 평문
형태로 저장된다면 그 기기 자체가 침해됐을 때의 노출 범위가
크게 넓어진다.
API 키나 인증 토큰 같은 값이 포함될 credential-vault가 암호화
없이 평문으로 남는다면, 이는 로컬 우선이라는 슬로건이 실제
보안 실천으로 완전히 이어지지 않았다는 것을 보여주는 구체적
사례다.

### “측정을 통한 신뢰”라는 약속이 검증기 자체의 신뢰성에 의존한다는 순환을 다루지 않는다

Maka는 “공식 검증기(official verifiers)”를 기준으로 성능을
측정한다고 강조하지만, 그 검증기 자체가 얼마나 신뢰할 만한지,
누가 그 기준을 정의했는지에 대한 설명은 README 수준에서
확인되지 않는다.
측정을 통한 신뢰라는 전략은, 측정 도구 자체에 대한 신뢰가
선행돼야 성립하는 순환 구조를 갖는다.
검증기가 특정 유형의 작업에 편향돼 있거나, 검증 방식 자체가
게임화(gaming)될 수 있다면, “주장 대신 측정”이라는 원칙은
검증기의 결함을 감추는 새로운 형태의 주장으로 전락할 위험이
있다.

### 인큐베이팅 상태와 “활발한 변경 가능성”의 조합이 실사용자에게 안정성 리스크를 전가한다

프로젝트가 스스로 “데이터 형식, CLI 명령, 실험적 기능이 여전히
바뀔 수 있다”고 명시하는 것은 정직한 태도이지만, 동시에 이는
지금 이 도구에 의존해 실제 작업 기록을 쌓는 사용자가 그 기록의
장기적 접근 가능성을 보장받지 못한다는 뜻이기도 하다.
`runtime.sqlite`에 쌓인 이벤트 로그가 “완전한 기록”으로서
가치를 가지려면, 그 데이터 형식이 미래 버전에서도 읽을 수 있어야
한다.
데이터 형식이 계속 바뀔 수 있는 인큐베이팅 단계의 프로젝트에서
장기 감사 추적이라는 가치 제안을 함께 내세우는 것은, 그 가치가
실제로 실현되는 시점을 프로젝트가 안정화된 이후로 미뤄야 한다는
암묵적 전제를 깔고 있다.

## 인사이트

### 에이전트 도구 시장의 다음 경쟁축은 기능이 아니라 검증 가능성이 될 수 있다

Maka가 측정과 감사 추적을 정체성의 핵심으로 삼은 것은, 에이전트
코딩 도구 시장이 “더 많은 기능”에서 “그 기능이 실제로 작동했다는
것을 얼마나 신뢰할 수 있게 보여주는가”로 경쟁축이 옮겨가고 있다는
신호로 읽을 수 있다.
초기 시장에서는 새로운 기능(더 긴 컨텍스트, 더 많은 도구 통합)이
차별화 요소였지만, 시장이 성숙하면서 사용자는 “이 도구가 실제로
얼마나 잘 작동하는지”를 검증 가능한 형태로 알고 싶어 한다.
이런 흐름이 계속되면, 앞으로 새로 등장하는 에이전트 도구들은
자체 벤치마크 공개를 기본 관행으로 채택할 가능성이 크고, 그
결과 벤치마크 자체의 신뢰성과 재현 가능성이 다음 경쟁 지점이
될 수 있다.

### 이벤트 소싱의 감사 가능성은 규제 산업으로의 확장 가능성을 시사한다

모든 결정을 append-only 이벤트로 남기는 설계는, 이 도구가 단순한
개발자 생산성 도구를 넘어 규제가 엄격한 산업(금융, 의료, 법률)에서
AI 에이전트를 도입할 때 요구되는 감사 요건과 자연스럽게 맞물릴
수 있다.
회계 시스템이 복식부기로 모든 거래를 추적 가능하게 만든 것과
유사하게, 에이전트의 모든 행동을 이벤트로 기록하는 것은
“이 에이전트가 왜 이런 결정을 내렸는가”를 사후에 재구성해야
하는 규제 요구를 충족시키는 기반이 될 수 있다.
이는 지금은 개발자 도구로 시작한 이 프로젝트가, 장기적으로는
AI 에이전트의 행동을 법적으로 추적 가능해야 하는 산업의 표준
인프라로 확장될 잠재력을 갖고 있음을 시사한다.

### Apache 재단 산하로 들어가는 것은 특정 기업 종속을 우려하는 사용자에게 다른 신뢰 근거를 제공한다

에이전트 코딩 도구 대부분은 특정 기업(스타트업이나 대형 테크
기업)이 소유하고 그 기업의 사업 전략에 따라 방향과 지속 가능성이
좌우된다.
Maka가 Apache Software Foundation의 인큐베이팅 프로젝트로
출발한 것은, 이 도구의 장기적 존속과 거버넌스가 단일 기업의
이해관계에 종속되지 않는다는 다른 종류의 신뢰 근거를 제공한다.
이는 특히 로컬 우선, 감사 추적, 측정 가능한 신뢰라는 이 프로젝트의
다른 가치들과 결합했을 때 일관된 그림을 만든다.
데이터 주권과 검증 가능성을 중시하는 조직이 에이전트 도구를
채택할 때, 특정 기업이 아니라 재단이 관리하는 프로젝트라는 점이
채택 결정에서 실질적인 차별화 요소로 작용할 수 있다.
