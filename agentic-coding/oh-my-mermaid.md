# oh-my-mermaid: 코딩 에이전트가 코드베이스를 훑어 Mermaid 아키텍처 문서를 쓰게 하는 도구

<https://ohmymermaid.com/>

<https://github.com/oh-my-mermaid/oh-my-mermaid>

## 소개

oh-my-mermaid(줄여서 omm)는 코딩 에이전트가 코드베이스를 읽고 아키텍처를 Mermaid
다이어그램과 Markdown 문서로 남기게 하는 CLI와 스킬 묶음이다.
README는 AI가 코드를 몇 초 만에 쓰지만 사람이 이해하는 데는 몇 시간이 걸리고,
이해를 건너뛰면 자기 코드베이스도 블랙박스가 된다는 문제에서 출발한다.
그 간극을 AI가 사람을 위해 쓰는 아키텍처 문서로 메우겠다는 것이 목표다.
홈페이지는 이를 바이브 코딩을 위한 아키텍처 거울(Architecture mirror for vibe
coding)이라고 부른다.

저장소는 2026년 3월 22일에 만들어졌고 MIT 라이선스이며,
2026년 10월 기준으로 별 2,773개, 포크 219개를 받았다.
TypeScript로 쓰였고 런타임 의존성은 `yaml` 하나뿐이다.
npm 패키지는 3월 21일 0.1.0부터 3월 25일 0.2.0까지 아홉 번 배포되었고,
그 뒤로 새 버전은 없다.
저장소의 마지막 커밋은 4월 7일이며,
커밋 17개 중 14개는 김승진(hitkoo) 한 사람이 올렸다.
설계 문서인 `PLAN.md`는 한국어로 쓰여 있다.

이 글은 저장소의 소스, 스킬 정의, 저장소에 함께 들어 있는 자체 스캔 결과,
릴리스와 이슈를 읽고 정리한 것이며, 도구를 직접 설치하거나 실행하지는 않았다.

## 동작 방식

### 역할 분리: 에이전트가 분석하고 CLI가 파일을 쓴다

omm의 핵심 설계는 `PLAN.md`의 한 문장에 담겨 있다.
CLI가 `.omm/` 파일을 결정적으로 관리하고,
스킬이 AI 분석 뒤에 CLI를 호출하는 구조라는 것이다.
홈페이지도 같은 내용을 AI가 다이어그램을 쓰고 CLI가 파일을 소유한다고 표현한다.

실제 코드도 그렇게 나뉘어 있다.
CLI(`omm`)에는 코드를 분석하는 로직이 전혀 없다.
`omm write <경로> <필드> -`는 표준 입력을 받아 정해진 파일에 쓰고,
`meta.yaml`에 갱신 시각과 횟수를 남길 뿐이다.
코드베이스를 읽고 무엇을 그릴지 정하는 일은 전부 `/omm-scan` 스킬의 프롬프트를
받은 에이전트가 한다.
즉 다이어그램의 품질은 omm이 아니라 그 스킬을 실행하는 모델과 프롬프트가
정한다.

### `/omm-scan` 스킬이 시키는 일

`skills/omm-scan/SKILL.md`는 에이전트에게 다음 순서를 지시한다.

1. `omm config language`로 문서 언어를 확인한다. 기본은 영어이고, ID와 디렉터리 이름은 언제나 영어 kebab-case다.
2. Glob과 Read로 `package.json` 같은 매니페스트, 최상위 디렉터리, 진입점, 라우트와 DB 연결을 살핀다.
3. 관점(perspective) 목록에서 이 코드베이스에 맞는 것을 고른다.
4. 관점마다 다이어그램과 나머지 필드를 쓰고, 다이어그램의 모든 노드를 재귀적으로 분석한다.
5. 만든 것을 요약하고 `omm view`를 권한다.

관점 목록은 12개이며, 그중 `overall-architecture`만 항상 만들고 나머지는 해당할
때만 만든다.

| 관점                    | 만드는 조건                 |
| ----------------------- | --------------------------- |
| `overall-architecture`  | 항상                        |
| `request-lifecycle`     | 서버나 API가 있을 때        |
| `data-flow`             | 데이터 처리나 DB가 있을 때  |
| `dependency-map`        | 모듈 그래프가 복잡할 때     |
| `external-integrations` | 외부 API나 서비스가 있을 때 |
| `state-transitions`     | 상태가 있는 기능이 있을 때  |
| `route-page-map`        | 라우팅이 있는 프런트엔드    |
| `command-surface`       | CLI 도구                    |
| `extension-points`      | 플러그인·확장 시스템        |
| `pipeline`              | ML·데이터 파이프라인        |
| `orchestration`         | 이벤트·큐 기반 시스템       |
| `storage`               | 저장소가 둘 이상일 때       |

재귀 규칙은 단순하다.
다이어그램의 모든 노드에 대해 해당 코드를 읽고, 예외 없이 `description`을 쓴다.
안에 뚜렷한 하위 구성 요소가 있으면 그 노드의 다이어그램을 쓰고 다시
내려가며(그룹), 단일 파일이나 얇은 래퍼, 외부 시스템이면 거기서 멈춘다(리프).
다이어그램 규칙도 정해져 있다.
노드 ID는 하위 디렉터리 이름과 같아야 하고,
라벨은 이름과 파일 경로를 `\n`으로 나눈 두 줄이며,
모든 간선에는 왜 연결되는지 설명하는 라벨이 붙어야 한다.
외부 서비스, 위험 요소, 진입점, 저장소에는 정해진 색의 `classDef`를 쓴다.
스킬은 `omm write`를 필드마다 별도의 Bash 도구 호출로 실행하라고 요구한다.

### 출력 형식: 파일 시스템이 곧 트리다

결과는 프로젝트 루트의 `.omm/` 디렉터리에 쌓인다.

```text
.omm/
├── config.yaml                  # 언어, 클라우드 slug
├── overall-architecture/        # 관점
│   ├── description.md
│   ├── diagram.mmd
│   ├── context.md
│   ├── constraint.md
│   ├── meta.yaml                # 자동 관리
│   ├── commands/                # 하위 요소(그룹)
│   │   ├── description.md
│   │   ├── diagram.mmd
│   │   └── local-ops/           # 리프
│   │       └── description.md
│   └── store/
│       └── description.md
└── data-flow/
```

요소 하나는 최대 일곱 개 필드를 가진다.

| 필드          | 파일             | 용도               |
| ------------- | ---------------- | ------------------ |
| `description` | `description.md` | 무엇을 하는지      |
| `diagram`     | `diagram.mmd`    | Mermaid 다이어그램 |
| `context`     | `context.md`     | 배경과 결정 근거   |
| `constraint`  | `constraint.md`  | 지켜야 할 규칙     |
| `concern`     | `concern.md`     | 위험, 기술 부채    |
| `todo`        | `todo.md`        | 할 일              |
| `note`        | `note.md`        | 기타               |

`meta.yaml`은 CLI가 관리한다.
생성·갱신 시각, 갱신 횟수, 마지막으로 쓴 필드, 하위 요소 목록이 들어가고,
최상위 관점에는 그 시점의 git 커밋과 브랜치도 기록된다.
다이어그램을 덮어쓸 때는 직전 내용을 `prev_diagram`에 보관하는데,
`omm diff`가 비교하는 대상이 이것이다.
보관하는 것은 바로 앞 버전 하나뿐이다.

### 저장소에 들어 있는 자체 스캔 결과

저장소의 `.omm/`에는 omm이 자기 자신을 스캔한 결과가 커밋되어 있어,
출력이 실제로 어떻게 생겼는지 볼 수 있다.
관점은 `overall-architecture`, `data-flow`, `command-surface` 세 개이고,
요소 디렉터리가 62개, 필드 파일이 70개, 그중 다이어그램은 6개다.
대부분의 요소는 `description.md` 하나만 가진 리프이며,
`concern`, `todo`, `note` 파일은 하나도 없다.
`meta.yaml`의 생성 시각은 2026년 3월 25일 12시 24분 32초부터 12시 32분 2초에
걸쳐 있어, 이 규모의 저장소를 한 번 스캔하는 데 약 7분 반이 걸렸다.

`overall-architecture` 다이어그램은 CLI, 명령, 저장소 계층, 클라우드 클라이언트,
diff 엔진, 웹 뷰어 등 12개 노드와 라벨이 붙은 간선으로 구성되어 있다.
소스와 맞춰 보면 대체로 정확하다.
다만 `command-surface` 다이어그램에는 `read`, `write`, `tree`, `config` 명령이
없다.
메타에 기록된 커밋은 `2fb887a`인데, 이 네 명령은 그다음 커밋 `a9cc5c3`에서
추가되었다.
같은 릴리스(v0.2.0)에 들어간 기능이 그 릴리스에 함께 커밋된 아키텍처 문서에는
빠져 있는 셈이다.

### 웹 뷰어

`omm view`는 Node 내장 `http` 모듈로 기본 3000번 포트에 서버를 띄우고,
포트가 사용 중이면 다음 번호로 넘어간다.
`fs.watch`로 `.omm/`을 감시하다가 바뀌면 SSE(Server-Sent Events)로 브라우저에
알려 화면을 갱신한다.

이름과 달리 뷰어는 mermaid.js로 그리지 않는다.
`viewer.html`(1,562줄)은 자체 정규식 파서 `parseFlowchart`로 `graph`/`flowchart`
문법의 노드와 간선만 뽑아내고, dagre로 배치를 계산해 SVG를 직접 그린다.
하위 요소에 다이어그램이 있으면 그 노드를 펼칠 수 있는 그룹 상자로 그리며,
확대 비율이 일정 이하로 내려가면 그룹 내부를 흐리게 처리한다.
사이드바는 각 필드를 marked로 HTML로 바꿔 보여 준다.
`subgraph`, `classDef` 정의 줄, `style` 줄은 건너뛰며,
시퀀스 다이어그램 같은 다른 Mermaid 다이어그램은 이 파서가 다루지 않는다.

## 설치와 사용

README의 빠른 시작은 세 단계다.

```bash
# CLI 설치와 AI 도구에 스킬 등록
npm install -g oh-my-mermaid && omm setup

# 문서 언어를 한국어로 (선택)
omm config language ko

# 에이전트 안에서 /omm-scan 실행 뒤, 터미널에서 뷰어 열기
omm view
```

`omm setup`은 설치된 도구를 감지해 각자의 방식으로 스킬을 등록한다.

| 도구        | 감지 방법                     | 등록 방식                                                          |
| ----------- | ----------------------------- | ------------------------------------------------------------------ |
| Claude Code | `claude` 명령 존재            | `claude plugin marketplace add` 뒤 `claude plugin install`         |
| Codex       | `codex` 명령 존재             | `~/.agents/skills/oh-my-mermaid`에 심볼릭 링크                     |
| Cursor      | `cursor` 명령 또는 `.cursor/` | 현재 프로젝트의 `.cursor-plugin/`에 스킬 복사와 `plugin.json` 생성 |
| OpenClaw    | `openclaw` 명령 존재          | `~/.openclaw/skills/oh-my-mermaid`에 심볼릭 링크                   |
| Antigravity | `antigravity` 명령 존재       | `~/.gemini/antigravity/skills/oh-my-mermaid`에 심볼릭 링크         |

Claude Code와 Cursor는 설치된 플러그인 버전을 패키지 버전과 비교해 다르면
다시 설치하고, 나머지 셋은 링크가 있으면 설정된 것으로 본다.
`omm setup --list`는 감지 결과를, `omm setup --teardown`은 등록 해제를 한다.
`omm update`는 `npm update -g`를 돌린 뒤 `omm setup`을 다시 실행한다.

스킬은 세 개다.

| 스킬        | 하는 일                                                |
| ----------- | ------------------------------------------------------ |
| `/omm-scan` | 코드베이스를 분석해 `.omm/` 생성·갱신                  |
| `/omm-view` | `omm list`로 문서가 있는지 확인한 뒤 `omm view` 실행   |
| `/omm-push` | 로그인, 프로젝트 연결, 클라우드 업로드를 순서대로 진행 |

CLI에는 이 밖에 `list`, `tree`, `show`, `read`, `write`, `delete`, `status`,
`diff`, `refs`, `validate`가 있다.
`omm validate`는 다이어그램이 `graph LR` 같은 방향 선언으로 시작하는지,
괄호 짝이 맞는지, 간선에 라벨이 있는지, `classDef` 이름과 색이 정해진 팔레트와
같은지, 노드 수가 권장 범위인 5~15개 안인지를 검사한다.
`omm refs`는 다이어그램 안의 `@관점-이름` 표기로 관점 사이의 참조를 찾는다.

## 클라우드

`omm login`, `omm link`, `omm push`로 `.omm/`을 ohmymermaid.com에 올릴 수 있다.
로그인은 로컬에 임시 HTTP 서버를 띄우고 브라우저로 GitHub OAuth를 거친 뒤,
콜백으로 받은 토큰을 `~/.omm/credentials.json`에 권한 `0600`으로 저장한다.
`omm push`는 `.omm/` 아래 모든 파일을 읽어 현재 git 커밋과 함께 한 번의 JSON
요청으로 보낸다.
`omm pull`은 서버가 준 경로가 `.omm/` 밖을 가리키면 거부하는데,
이 경로 검사는 0.1.6 릴리스에서 추가되었다.

가격 페이지의 요금제는 다음과 같다.

| 요금제   | 가격   | 내용                                                     |
| -------- | ------ | -------------------------------------------------------- |
| Free     | $0     | 프로젝트 1개, 푸시 이력 5개, 비공개 보기만               |
| Personal | $10/월 | 프로젝트 5개, 이력 무제한, 공개 공유 링크                |
| Team     | $30/월 | 프로젝트 무제한, 조직 내 공유, 편집자 4명 포함(추가 $10) |

모든 요금제에 로컬 CLI 사용이 포함되고, 보기 전용 좌석은 언제나 무료다.

## 트레이드오프

### 결정적인 것은 파일 쓰기뿐이고, 내용은 매번 새로 생성된다

CLI가 파일을 결정적으로 관리한다는 설계는 저장 형식의 일관성을 보장한다.
경로 규칙, 필드 이름, 메타 기록은 모델이 바뀌어도 같다.
그러나 다이어그램에 어떤 노드가 들어가고 어디서 재귀를 멈출지는 매번 에이전트가
판단한다.
같은 코드베이스를 두 번 스캔하면 다른 트리가 나올 수 있고,
`omm diff`가 보여 주는 변화가 코드의 변화인지 모델 판단의 변화인지 구분할
방법이 없다.

CodeBoarding(`agentic-coding/codeboarding.md`)처럼 LSP 기반 정적 분석으로 구조를
먼저 뽑고 LLM이 의미를 붙이는 도구와 비교하면 차이가 분명하다.
omm은 구조 추출까지 전부 에이전트의 Glob과 Read에 맡긴다.
그 덕분에 언어별 분석기 없이 어떤 저장소에도 쓸 수 있지만,
호출 그래프나 의존성처럼 기계적으로 확인할 수 있는 사실도 모델이 읽은 범위
안에서만 그려진다.
간선 라벨은 모델이 코드를 읽고 쓴 설명이지 검증된 호출 관계가 아니다.

### 다시 스캔하는 비용이 문서의 신선도를 정한다

스킬에는 바뀌지 않은 요소는 다시 쓰지 말라는 규칙이 있지만,
무엇이 바뀌었는지 알아낼 장치는 없다.
요소와 소스 파일을 잇는 기록이 없으므로 에이전트는 다시 코드를 읽어야 한다.
자체 스캔 기준으로 이 작은 저장소 하나에도 7분 반이 걸렸고,
필드 하나마다 Bash 호출을 하나씩 쓰라는 규칙 때문에 수십 번의 도구 호출이
필요하다.

이슈 #20은 바로 이 문제를 지적했다.
스캔이 매번 전체를 분석해 토큰 비용이 크고, 어떤 파일 변경이 어떤 요소에
영향을 주는지 알 수 없어, 결국 문서가 낡는다는 것이다.
제안자는 소스 파일과 요소를 잇는 `manifest.json`,
파일 쓰기 뒤에 해당 요소만 다시 분석하는 Claude Code 훅,
구현 대신 `.d.ts` 선언만 읽혀 토큰을 줄이는 방법을 제시했다.
로드맵에도 증분 분석과 관점별 병렬 서브에이전트가 계획으로 올라 있지만,
3월 이후 구현된 것은 없다.
앞에서 본 `command-surface`의 누락도 이 비용 구조가 만든 결과로 보인다.
코드를 바꾼 사람이 스캔을 다시 돌리지 않으면 문서는 조용히 뒤처진다.

### 일곱 필드는 구조를 주지만 잘 채워지지 않는다

`PLAN.md`는 메모를 `constraint`, `concern`, `context`, `todo`, `note`로 나눈
이유를 AI 분석 품질 향상이라고 설명한다.
필드를 나누면 모델이 위험과 결정 근거를 따로 생각하게 만들 수 있다.
그러나 자체 스캔에서 위험(`concern`)과 할 일(`todo`)은 한 번도 채워지지
않았다.
다이어그램 아래 노드는 대부분 `description` 한 줄짜리 리프로 끝난다.
스킬이 리프에서 나머지 필드를 선택 사항으로 두기 때문이다.
사람이 이 문서에서 가장 얻고 싶은 것이 아키텍처의 위험이라면,
그 칸은 기본 설정으로는 비어 있다고 보는 편이 맞다.

### 자체 렌더러는 단순하지만 Mermaid의 일부만 이해한다

뷰어가 mermaid.js 대신 자체 파서와 dagre를 쓰는 덕분에 중첩 그룹을 펼치고
접는 탐색, 확대 비율에 따른 표시 조절 같은 기능을 직접 구현할 수 있었다.
대가는 지원 문법의 폭이다.
`subgraph`는 무시되고, 한 줄에 `A --> B --> C`처럼 간선을 이어 쓰면 파서는 첫
간선만 읽는다.
스킬이 `graph LR`/`graph TD`만 쓰게 하고 `validate`가 방향 선언을 강제하는
것도 이 제약과 맞물려 있다.
거꾸로 사람이 `.mmd`에 Mermaid의 다른 문법을 써 넣으면,
다른 Mermaid 렌더러에서는 보이는 내용이 omm 뷰어에서는 빠질 수 있다.

## 함정

- npm에 올라간 최신판 0.2.0은 도구 감지에 `which`만 쓴다. Windows의 cmd나 PowerShell에서는 Claude Code가 설치되어 있어도 `No supported AI coding tools detected`가 나온다(이슈 #24). `where`를 쓰도록 고친 PR #22는 4월 7일 `main`에 합쳐졌지만 그 뒤 배포가 없어, 이슈에서는 Git Bash에서 `omm setup`을 실행하는 우회법이 공유되었다.
- 저장소는 4월 이후 사실상 멈춰 있다. 플랫폼 추가와 뷰어 개선을 담은 외부 PR #30은 검토할 메인테이너가 없다며 작성자가 닫았고, PNG·Mermaid 내보내기(#26, #28), Gemini CLI 지원(#27) 요청에도 메인테이너의 답이 없다.
- 홈페이지는 Windsurf, GitHub Copilot, 모든 MCP 클라이언트와 함께 동작한다고 적지만, 코드가 지원하는 것은 Claude Code, Codex, Cursor, OpenClaw, Antigravity 다섯 가지이고 MCP 서버는 없다. CLI 도움말은 로그인 대상을 omm.dev라고 적지만 실제 기본 API 주소는 `https://ohmymermaid.com`이다.
- `omm view`는 `server.listen(port)`에 호스트를 지정하지 않아 모든 네트워크 인터페이스에서 받으며, API 응답에 `Access-Control-Allow-Origin: *`를 붙인다. 같은 네트워크의 다른 기기에서 아키텍처 문서를 읽을 수 있다는 뜻이므로 공용 네트워크에서는 조심해야 한다.
- 사이드바는 필드의 Markdown을 marked로 변환해 그대로 `innerHTML`에 넣고, 버전을 고정하지 않은 CDN의 marked를 불러온다. 문서는 에이전트가 코드와 주석을 읽고 쓴 것이므로, 신뢰하지 않는 저장소를 스캔한 결과를 열 때는 이 점을 기억해야 한다.
- 인자 없이 실행한 `omm validate`는 최상위 관점의 다이어그램만 검사하고, 뷰어의 diff API도 최상위 관점만 받는다. 하위 요소는 경로를 직접 넘겨야 하며, `omm diff`의 비교 기준은 직전 버전 하나뿐이다. 변경 이력이 필요하면 `.omm/`을 git에 커밋하는 편이 낫다.
- `omm push`는 `meta.yaml`의 `prev_diagram`까지 포함해 `.omm/` 전체를 올린다. 무료 요금제는 프로젝트 하나만 허용하며, `/omm-push` 스킬은 403 응답을 이 한도로 안내한다.
- Cursor 연동은 전역이 아니라 현재 프로젝트에 `.cursor-plugin/`을 만든다. 프로젝트마다 `omm setup`을 다시 해야 하고, 이 디렉터리를 커밋할지 정해야 한다.
- `omm login`은 macOS의 `open` 명령으로 브라우저를 연다. 다른 운영체제에서는 터미널에 출력된 주소를 직접 열어야 하고, 60초 안에 로그인을 끝내지 않으면 시간이 초과된다.

## 기억할 원칙

### 생성된 아키텍처 문서는 생성한 시점의 스냅숏이다

omm은 에이전트가 쓴 코드를 에이전트가 다시 설명하게 해서 이해의 간극을
메우려 한다.
그러나 저장소에 들어 있는 자체 스캔이 보여 주듯,
그 설명은 스캔한 커밋에서 멈추고 코드는 계속 움직인다.
`meta.yaml`이 git 커밋을 기록하는 것은 그 점에서 가장 중요한 필드다.
다이어그램을 읽을 때는 먼저 그 커밋과 지금 `HEAD`의 거리를 확인하고,
거리가 멀면 다이어그램을 지도가 아니라 과거의 기록으로 읽어야 한다.

### 무엇을 기계가 확인했고 무엇을 모델이 추론했는지 구분한다

omm이 남기는 문서에서 기계가 보장하는 것은 파일 경로, 필드 이름,
타임스탬프뿐이다.
노드의 경계, 간선의 의미, 재귀를 멈춘 지점은 모두 모델의 판단이다.
이런 문서를 리뷰나 온보딩에 쓰려면, 적어도 최상위 다이어그램의 간선 몇 개는
사람이 코드에서 직접 확인해 보고 신뢰 수준을 정해야 한다.
설명을 생성하는 비용이 거의 사라졌다고 해서 설명을 검증하는 비용까지 사라진
것은 아니다.
