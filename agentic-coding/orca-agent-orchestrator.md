# Orca — 병렬 코딩 에이전트 오케스트레이터

<https://www.onOrca.dev/>

<https://github.com/stablyai/orca>

HN 토론: <https://news.ycombinator.com/item?id=47549197> (21점, 10개 댓글)

## 소개

Orca는 Stably AI가 만든 에이전트 개발 환경(ADE, Agent Development Environment)이다.
“100x 빌더를 위한 AI 오케스트레이터”를 표방하며,
여러 AI 코딩 에이전트를 격리된 git worktree에서 병렬로 실행하고
결과를 나란히 비교·병합하는 데스크톱 앱이다.
MIT 라이선스 오픈소스이고, 2026년 8월 기준 GitHub 스타 39.8k, 포크 2.8k, 커밋 8,169개다.
README가 중국어·일본어·한국어·스페인어·프랑스어·포르투갈어로 번역되어 있다.

핵심 워크플로는 단순하다.
프롬프트를 한 번 입력하면 Orca가 이를 여러 에이전트에 동시에 배포하고,
각 에이전트는 자기만의 worktree에서 독립적으로 작업한다.
사용자는 통합 인터페이스에서 각 결과를 비교한 뒤 마음에 드는 쪽을 병합한다.
지원 에이전트 목록은 Claude Code, Codex, Grok, Cursor, GitHub Copilot, OpenCode,
MiMo Code, Amp, OpenClaude, Antigravity, Pi, oh-my-pi, Hermes Agent, Devin, Goose,
Auggie, Autohand Code, Charm, Cline, Codebuff, Command Code, Continue, Droid,
Kilocode, Kimi, Kiro, Mistral Vibe, Qwen Code, Rovo Dev로 이어지고,
마지막 항목이 “그 외 모든 CLI 에이전트”다 — 문서의 표현은
“터미널에서 돌면 Orca에서 돈다”이다.

## 주요 기능

- 에이전트별 격리 git worktree와 병렬 실행(fan-out)
- 결과 나란히 비교 및 병합, AI diff 주석·리뷰
- WebGL 렌더링 터미널과 무제한 분할
- Chromium 기반 Design Mode로 UI 요소 검사
- GitHub·Linear 태스크 연동, SSH 원격 worktree
- iOS·Android 컴패니언 앱으로 원격 모니터링과 조종(steering)
- worktree·파일 통합 검색(quick open), 계정 전환과 사용량 추적
- 워크플로 스크립팅용 CLI(`orca worktree create`, `snapshot`, `click`, `fill`)
- 에이전트에 파일·이미지를 끌어다 놓는 VS Code 기반 에디터와 전역 자동 저장
- Markdown·이미지·PDF·저장소 문서 미리보기, 데스크톱 앱 제어용 Computer Use
- 에이전트 완료·주의 필요 알림과 스레드 읽지 않음 표시

설치는 macOS·Windows·Linux 데스크톱은 onorca.dev/download 직접 다운로드,
Homebrew는 `brew install --cask stablyai/orca/orca`,
Arch Linux는 `yay -S stably-orca-bin`으로 한다.
기술 스택은 Electron 기반 데스크톱에 TypeScript/Node.js(pnpm 워크스페이스)이며,
익명 사용량 텔레메트리는 옵트아웃할 수 있다.
헤드리스 리눅스 서버에서는 `orca serve`로 띄우는 별도 가이드가 있고,
모바일 컴패니언은 iOS App Store와 TestFlight, Android는 APK 직접 배포다.
Windows 코드 서명은 SignPath.io가 후원하고 SignPath Foundation이 인증서를 제공한다.
저장소 최상단에는 `orca.yaml`과 `AGENTS.md`, `CLAUDE.md`가 함께 놓여 있고,
`skills/`, `skill-guides/`, `skill-stubs/`, `examples/plugins/` 디렉터리가 따로 있다.

## 분석

### “에이전트를 잘 쓰는 도구”에서 “에이전트들을 관리하는 도구”로

Orca의 핵심 전제는 코딩 에이전트가 이미 상품화(commoditize)됐다는 것이다.
Claude Code든 Codex든 개별 에이전트의 성능 차이는 줄어들고 있으니,
경쟁력은 어느 에이전트를 쓰느냐가 아니라
여러 에이전트를 어떻게 굴리느냐에서 나온다는 판단이다.
그래서 Orca는 에이전트를 직접 만들지 않고
30개가 넘는 서드파티 에이전트의 상위 관리 계층을 자처한다.

이 위치 선정은 IDE 전쟁의 구도를 한 단계 끌어올린다.
Cursor가 “에디터 안의 에이전트”였다면
Orca는 “에이전트들 위의 관제탑”이다.
개발자의 단위 작업이 코드 편집에서 에이전트 감독으로 옮겨간다는
업계 서사를 제품 구조로 그대로 옮긴 셈이다.

### 병렬 실행은 비결정성에 대한 공학적 대응이다

같은 프롬프트를 여러 에이전트에 뿌리고 결과를 고르는 방식은
LLM의 비결정성을 결점이 아니라 탐색 수단으로 뒤집는 전략이다.
한 번의 시도가 확률적으로 실패할 수 있다면,
n번을 병렬로 시도하고 최선을 고르는 편이 기대 품질을 올린다.
이는 추론 시점 스케일링(best-of-n sampling)을
개발 워크플로 수준으로 끌어올린 것과 같다.

격리 worktree는 이 전략의 전제 조건이다.
같은 저장소에서 여러 에이전트가 동시에 파일을 고치면 충돌하므로,
git worktree로 각자의 사본을 주고 결과만 병합 지점에서 수렴시킨다.
이 패턴은 Claude Code의 worktree 격리 옵션이나
tmux 기반 병렬 에이전트 운용 같은 수작업 관행을
제품 기능으로 정식화한 것이다.

터미널 구현도 같은 맥락의 실용주의를 보여준다.
HN에서 Ghostty의 WASM 포팅인 ghostty-web으로 교체하라는 제안이 나오자[^theturtletalks],
개발자는 이미 검토했지만 이슈 수와 멈춘 릴리스 때문에
xterm.js를 유지했다고 답했다[^nwparker-ghostty].
“Ghostty급” 터미널이라는 소개 문구와 달리
실제 구현은 검증된 기존 라이브러리 위에 서 있는 셈이다.

### 모바일 앱은 감독 노동의 성격 변화를 보여준다

iOS·Android 컴패니언 앱으로 에이전트를 원격 모니터링하고 조종한다는 기능은
단순한 편의 기능이 아니다.
에이전트가 수십 분씩 혼자 도는 시대에는
개발자가 화면 앞에 붙어 있을 이유가 없고,
필요한 것은 “막혔을 때 알림 받고 방향만 잡아주는” 개입 채널이다.
Orca는 이 감독 노동을 모바일 알림 수준으로 가볍게 만들려 한다.

이는 개발이 동기적 작업에서 비동기적 관리로 바뀐다는 신호다.
코드 리뷰 대기열을 관리하듯 에이전트 대기열을 관리하고,
출퇴근길에 진행 상황을 확인하는 그림이다.

### 같은 문제에 대한 반대 방향의 해법이 나란히 존재한다

이 범주에서 Orca와 가장 직접 비교되는 것이 [Paseo](paseo.md)다.
둘 다 여러 코딩 에이전트를 관리하는 데스크톱 앱이고, 모바일 컴패니언이 있고, CLI를 제공한다.
그런데 강조점이 반대다.

Orca는 팬아웃을 중심에 둔다 — 하나의 프롬프트를 여러 에이전트에 뿌리고
각자 격리된 worktree에서 돌린 뒤 비교해 승자를 병합한다.
Paseo는 역할 분담을 중심에 둔다 — 제공하는 스킬 네 개가
인계(handoff), 반복 루프(loop), 조언자(advisor), 위원회(committee)이고
같은 작업을 여러 에이전트에 동시에 시키는 패턴은 목록에 없다.

나머지 축도 대체로 반대다.
라이선스는 MIT 대 AGPL-3.0이고, 텔레메트리는 옵트아웃 가능한 익명 수집 대 아예 없음이며,
지원 에이전트는 30개 가까이 나열 대 다섯 개 명시다.
스타 수는 39.8k 대 12.7k로 세 배 차이가 난다.

이 대비가 알려주는 것은 이 시장이 아직 하나의 축으로 정렬되지 않았다는 사실이다.
넓게 지원하고 빠르게 출시하며 사용 데이터를 모으는 쪽과,
좁게 지원하고 통제권과 프라이버시를 파는 쪽이 동시에 성장하고 있다.
그리고 어느 쪽이 우세해질지는 이 도구들이 개인의 취미 환경으로 남는지
팀의 표준 도구가 되는지에 달려 있다 — 후자로 가면 라이선스와 텔레메트리 정책이
기능보다 먼저 심사 대상이 되기 때문이다.

## 비평

### 병렬 실행의 비용 구조를 말하지 않는다

프롬프트 하나를 에이전트 다섯에 뿌리면 토큰 비용도 대략 다섯 배다.
best-of-n의 기대 품질 향상이 n배 비용을 정당화하는지는
작업 난이도에 따라 크게 달라지는데,
Orca의 소개 자료는 이 비용-편익 계산을 전혀 다루지 않는다.
“100x 빌더”라는 구호 뒤에는 n배 청구서가 따라온다.

더 근본적으로, 병렬 결과 중 최선을 고르는 판단 자체가 비싸다.
다섯 개의 diff를 제대로 비교 검토하는 일은
diff 하나를 리뷰하는 것보다 다섯 배 이상 힘들 수 있다.
결과가 서로 다른 접근을 택했다면 단순 비교가 아니라
설계 판단이 필요해지기 때문이다.
AI diff 주석 기능이 이를 돕는다고 하지만,
“AI가 만든 것을 AI가 요약해 주는” 구조는
검증 부담을 줄이는 게 아니라 한 겹 더 숨길 위험이 있다.

### 병합이라는 가장 어려운 문제를 UI 뒤로 숨긴다

여러 worktree의 결과를 “비교하고 병합한다”는 문장은 간단해 보이지만,
서로 다른 에이전트가 같은 문제를 다르게 푼 코드를 병합하는 일은
git 충돌 해소보다 훨씬 어려운 의미론적 병합이다.
A안의 자료 구조와 B안의 에러 처리를 섞으면
어느 쪽 테스트도 통과하지 않는 제3의 코드가 나오기 쉽다.
실질적으로는 “하나를 통째로 고르는” 선택이 대부분일 텐데,
그렇다면 나머지 n-1개의 실행은 순수 탐색 비용이 된다.

### 오케스트레이터 계층은 구조적으로 취약한 위치다

Orca의 가치는 전적으로 하위 에이전트들에 의존한다.
Anthropic이나 OpenAI가 자사 에이전트에 병렬 실행·worktree 격리·
모바일 모니터링을 내장하면 — 실제로 Claude Code는 이미
worktree 격리와 백그라운드 에이전트를 지원한다 —
관리 계층의 존재 이유는 빠르게 얇아진다.
플랫폼 위의 애그리게이터가 플랫폼의 기능 흡수에 밀려나는 패턴은
트위터 클라이언트, 클라우드 관리 도구 등에서 반복돼 왔다.
멀티 벤더 중립성이 방어막이 될 수 있지만,
그 방어막은 사용자가 실제로 여러 에이전트를 섞어 쓸 때만 유효하다.

HN 스레드는 이 취약성을 다른 각도에서도 보여준다.
같은 자리를 노리는 cmux를 이미 쓰고 있다는 사용자가
차이가 무엇이냐고 묻자[^bartwaardenburg],
개발자는 탭 배치 방식, GitHub 네이티브 연동, 비포커스 창의 AI 상태 표시,
내장 diff 뷰어 같은 것들을 들며
“결국 작은 것들의 축적”이라고 답했다[^nwparker].
솔직한 답이지만, 차별화가 작은 UX 디테일의 합이라는 것은
이 계층의 진입 장벽이 낮고 대체가 쉽다는 방증이기도 하다.
실제로 그 답변만 듣고 갈아타 보겠다는 반응이 바로 달렸다[^virtu].

또한 30개 이상 에이전트와의 통합은 유지보수 표면적이 그만큼 넓다는 뜻이다.
각 에이전트의 CLI 인터페이스, 권한 모델, 세션 형식이 제각각 바뀌는데
1.2k의 열린 이슈는 이 통합 비용이 이미 현실임을 시사한다.

## 인사이트

### best-of-n은 검증 병목을 해결하는 게 아니라 증폭한다

에이전트 시대의 병목이 코드 생성이 아니라 검증이라는 지적은 이제 상식이다.
그런데 병렬 오케스트레이션은 생성량을 n배로 늘리는 도구다.
생성이 병목일 때는 훌륭한 해법이지만,
검증이 병목인 세계에서는 병목 앞의 재고만 쌓는 셈이 된다.
검증 부채(verification debt)의 관점으로 보면
Orca는 부채 발생 속도를 높이는 장치일 수 있다.

이 긴장은 도구 설계로 일부 완화할 수 있다.
결과를 사람이 고르는 대신 테스트 스위트가 고르게 하면
best-of-n은 검증 자동화와 결합해 실제 품질 향상이 된다.
결국 병렬 오케스트레이터의 가치는
사용자가 얼마나 강한 자동 검증 기준(스펙, 테스트)을 가졌느냐에 비례한다.
스펙 없이 쓰면 n개의 그럴듯한 쓰레기 중 하나를 고르는 도구가 되고,
스펙과 함께 쓰면 탐색 폭을 넓히는 도구가 된다.

### 오케스트레이터 경쟁의 승부처는 UI가 아니라 병합 의미론이다

지금의 오케스트레이터들은 터미널 분할, 알림, 모바일 앱 같은
관제 UI로 경쟁하고 있다.
하지만 병렬 실행이 보편화되면 차별화 지점은
“여러 결과를 어떻게 의미 있게 수렴시키는가”로 옮겨갈 것이다.
diff 수준 병합이 아니라,
각 시도에서 얻은 통찰을 추출해 다음 시도의 프롬프트에 반영하는
반복 수렴 루프를 가진 쪽이 이긴다.
이는 유전 알고리즘의 교차(crossover)와 닮은 구조로,
현재의 “나란히 놓고 사람이 고르기”는 그 원시적 초기 형태다.

역사적 유비로 CI 시스템의 진화가 있다.
초기 CI는 “빌드를 병렬로 돌리고 결과를 보여주는” 도구였지만,
성숙기의 가치는 병렬성 자체가 아니라
실패를 어느 커밋으로 좁히는가(bisect), 어떤 테스트를 먼저 돌리는가 같은
수렴의 지능에서 나왔다.
에이전트 오케스트레이터도 같은 경로를 밟을 가능성이 크다.

### 멀티 에이전트 상시 비교는 에이전트 벤더에 대한 실사용 평가 시장을 만든다

여러 에이전트에 같은 작업을 상시로 뿌리는 사용자는
자연스럽게 벤더별 실전 성능 데이터를 축적하게 된다.
합성 벤치마크가 아니라 자기 코드베이스, 자기 작업 분포에서의
승률 데이터다.
Orca 같은 도구가 계정 전환과 사용량 추적을 내장한 것은
이 비교 구매(comparison shopping) 행태를 이미 전제하고 있다.

이는 에이전트 벤더에게 이중의 압력이 된다.
성능이 상시 비교당하므로 마케팅으로 가릴 여지가 줄고,
오케스트레이터가 사용자 접점을 쥐면 벤더는 교체 가능한 부품이 된다.
항공권 메타서치가 항공사를 가격 비교의 대상으로 끌어내렸듯,
오케스트레이터는 에이전트를 승률 비교의 대상으로 끌어내린다.
벤더들이 자사 락인 기능(세션 이어가기, 메모리, 저장소 특화 학습)을
강화하는 방향으로 대응할 것이라 예상할 수 있고,
그 락인이 강해질수록 역설적으로 오케스트레이터의 중립성 가치도 커진다.

### 감독 부하의 상한이 병렬도의 실질 상한이다

worktree 격리와 모바일 조종이 아무리 매끄러워도,
사람 하나가 유의미하게 감독할 수 있는 동시 에이전트 수에는 상한이 있다.
관제 업무 연구에서 반복 확인되듯
감독자는 대상이 늘수록 개별 대상에 대한 상황 인식을 잃고,
“이상 없음” 신호를 확인 없이 승인하는 자동화 안주(automation complacency)에 빠진다.
병렬도를 높이는 도구는 이 상한을 올려주는 게 아니라
상한에 더 빨리 도달하게 해 준다.

따라서 이런 도구의 실질 효용 곡선은 병렬도에 선형으로 오르지 않고
낮은 n에서 일찍 꺾일 가능성이 크다.
개인 개발자에게 최적 병렬도는 아마 2~3 수준이고,
그 이상은 조직적 장치(에이전트 결과를 리뷰하는 별도 역할, 자동 게이트)가
받쳐줄 때만 의미가 있다.
“100x”라는 수사와 실제 감독 가능 범위 사이의 간극이
이 제품군 전체가 부딪힐 벽이다.
