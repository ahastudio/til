# 자기 LLM 프록시를 직접 운영해야 토큰이 어디로 새는지 보인다

원문: [If you don't run your own LLM proxy, how the fuck do you even know whats going on?](https://jrdsgl.com/if-you-dont-run-your-own-llm-proxy-how-the-fuck-do-you-even-know-whats-going-on/)

HN 토론: <https://news.ycombinator.com/item?id=50145507> (292점, 209개 댓글)

GN 토론: <https://news.hada.io/topic?id=35631>

## 요약

jrdsgl이 2026년 10월 18일 올린 이 글은 제목이 주장을 다 말한다고
하면서 시작한다.
LLM 제공자의 구독에 묶인 프런트엔드로 일하는 사람들은 자기 데이터가 들어가고
제공자의 데이터가 돌아오는 것만 볼 뿐,
그 사이에서 무슨 일이 일어나는지는 모른다는 것이다.
제공자가 보여 주는 사용량 화면은 일하는 증거로 보여 주는 것일 뿐 엔지니어를 위한
시계열 토큰 사용 통계가 아니라서 그것으로는 결정을 내릴 수 없다고 저자는 쓴다.
OpenTelemetry(OTel) 내보내기가 있다는 반박에는 좋다고 하면서
이것이 하나의 이유일 뿐이라며
직접 운영하는 프록시를 쓸 이유를 다섯 가지 더 든다.

다섯 가지 이유는 이렇다.
하나의 엔드포인트에서 여러 제공자와 모델을 쓸 수 있고,
어떤 키가 어떤 클라이언트로 어떤 모델을 몇 시에 불렀고
상태가 어땠는지 로그가 남는다.
가상 API 키로 하나뿐인 주 키를 작업과 에이전트와 하네스에 뿌리지 않아도 되고,
인프라를 직접 통제하며,
모델과 제공자를 처음부터 다시 설정하지 않고 빠르게 바꿀 수 있다.
저자는 특정 프록시를 권하지 않고 어디서든 직접 통제할 수 있는 곳에서
운영하되 필요에 맞게 고쳐 쓰라고 한다.
자신은 더 나은 가시성과 맞춤 MCP 서버 엔드포인트와 추가 기능을 위해 고쳐서
쓴다고 밝힌다.

글이 드는 실제 이득은 캐시 미스다.
코딩 세션에서 캐시 미스가 보이면 손으로 20초 안에 원인을 짚을 수 있고,
자동화하지는 않았지만 쓰는 프록시에 API가 있어서 자동화도 가능하다고 한다.
글은 인프라와 애플리케이션 가시성, 데이터 경로,
저장소를 직접 가지라는 말로 맺는다.
집에서는 재미있어서 하고, 직장에서는 하지 않으면
일을 제대로 하는 것이 아니라서 한다는 이유를 든다.
대규모 언어 모델이 어떻게 동작하는지 면접에서
칠판에 그릴 만큼 이해하지 못할 수는 있어도,
추론을 서빙하는 동안 계측되어 있도록 만들 수는 있다는 말이다.

## 분석

### 제공자의 사용량 화면은 청구서의 일부이지 계측이 아니다

글의 출발점은 제공자의 분석 화면이 엔지니어가
결정을 내릴 자료를 주지 않는다는 불만이다.
시계열 토큰 사용 통계가 아니라 일이 되고 있다는 증거로 보이는 화면이라고 한다.
제공자의 입장에서는 이해되는 설계다.
제공자는 사용량과 청구를 보여 주려는 것이지
사용자의 워크플로를 디버깅하게 하려는 것이 아니다.

프록시가 주는 것은 호출 단위의 기록이다.
어떤 키가 어떤 클라이언트로 어떤 모델을 불렀는지가 남으면
비용과 지연과 실패를 호출 단위로 쪼갤 수 있다.
글이 든 캐시 미스의 20초 진단이 이 차이를 보여 주는 예다.

### 프록시는 관측과 제어를 한 지점에 모은다

글의 다섯 가지 이유 가운데 관측에 속하는 것은 로그와 직접 통제하는 인프라이고,
제어에 속하는 것은 가상 키와 제공자 교체다.
프록시가 두 가지를 겸하는 것은 모든 호출이 그 지점을 지나기 때문이다.

HN에서 hoppp는 샌드박스에서
에이전트를 돌리는 데 LiteLLM 프록시가 필요하다고 했다.
가상 키를 발급해 제공자의 API 키가 샌드박스 근처에 가지 않게 하고,
모든 것을 볼 수 있으며, 가드레일을 걸 수 있다는 이유다.[^hoppp]
글의 가상 키 항목이 에이전트 격리 문제로 이어지는 예다.
관측 하나만이면 OTel이 대신할 수 있지만 제어까지 하려면
호출 경로 위에 있어야 한다는 구분이 여기서 나온다.

## 비평

### 구독 사용자의 대부분에게 이 조언은 전제가 맞지 않는다

글은 API 키를 쓰는 사람을 전제로 한다.
HN에서
NeutralWanted는 20배 Claude Max 구독(월 200달러)으로 매주 한도에 가깝게 쓰는데
API 키로 바꾸면 2~3일 만에 200달러를 쓴다고 하면서
API 키 비용을 어떻게 정당화하느냐고
물었다.[^NeutralWanted] dcss_gardener는 구독이 크게 보조받고 있고
요즘의 flash 모델은 저렴하다고
답했고,[^dcss_gardener] denkmoon은 마약상이 공짜로 한 번 주는 것은 장기적으로
중독이 이득이 되기 때문이라고
비유했다.[^denkmoon] jakozaur는 프록시는 API 가격을 낼 때 좋고,
구독에서는 `~/.claude/projects/` 같은 폴더의 JSONL 파일을 모으는 쪽이 더 쉽고
서브에이전트처럼 프록시가 못 보는 구조도 담긴다고
했다.[^jakozaur] variety8675는 100달러 구독이 집에서 쓰기에
사실상 무한하게 느껴져서 이렇게까지 감시할 필요를 모르겠다고 했고,
TuxedoBuddy는 ISP 라우터로 충분한 사람도 있고 내부를 보려고
pfSense를 쓰는 사람도 있다고 답했다.[^variety8675][^TuxedoBuddy]

이 교환들을 보면 글의 주장은 쓰는 방식에 따라 다르게 성립한다.
API 요금을 내고
에이전트를 많이 돌리는 사람에게는 프록시의 계측이 곧 비용 통제이고,
정액 구독으로 개인이 쓰는 사람에게는 같은 가치가 훨씬 작다.
글은 이 구분을 하지 않고 모두에게 필요하다고 말한다.

### OTel로 충분하다는 반론에 글은 답하지 않는다

HN에서 CharlieDigital은 프록시가 필요 없고 쓰지 않는 편이 낫다고 주장했다.
프록시는 생산성의 직선 경로에 단일 장애점을 만들고,
Codex와 Claude Code는 OTel 트레이스를 내보내며,
OTel 방출과 수집은 최선 노력이라 일부를 잃어도
생산성이 줄지 않는다는 것이다.[^CharlieDigital]
ProjectBarks는 OTel로는 하네스가 보여 주려는 것만 볼 수 있다고 반박했다.
Z.ai와 ByteDance Trae와 Alibaba Qwen이 그들이 가져가지 말아야 할 데이터를
색인했다는 논란을 거론하며 모든 하네스를 네트워크 로깅이 켜진 VM에서
돌리라는 대안을 냈다.[^ProjectBarks] pavelmelnichuk는 OTel은 프록시가 해결하는
것의 4분의 1이고, 에이전트가 막다른 길로 가서
100달러를 태우는 것을 알아채기 전에 막는 것은 프록시뿐이라고
했다.[^pavelmelnichuk]

글은 OTel 내보내기가 있다는 반론을 한 줄로 넘기고
프록시를 쓸 이유를 다섯 가지 더 든다.
그 가운데 OTel로 가능한 것(로그)과 불가능한 것(가상 키,
제공자 교체, 호출 차단)이 섞여 있다.
이 문서의 판단으로는 글이 가장 설득력 있는 곳은 가상 키와 제공자 교체이고
가장 약한 곳은 로그다.

### 어떤 프록시를 쓰는지 말하지 않아서 실행 가능한 조언이 되지 않는다

글은 특정 프록시를 권하지 않는다고 하고 자신이 쓰는 것도 밝히지 않는다.
HN에서 jFriedensreich는 이를 이상하게 여겼다.[^jFriedensreich]
댓글이 채운 것은 LiteLLM, Bifrost, GoModel,
Tailscale의 Aperture 같은 이름들이다.[^hoppp][^hoss1474489][^verdverm][^passive]
jubilanti는 LiteLLM을 비롯한 이런 도구들이 버그 많은 바이브 코딩 덩어리가 아닌
세상을 상상해 보자고 하면서 업데이트 속도로 보아 취약점이 있을 것 같다고
걱정했다.[^jubilanti] hoss1474489는 Bifrost가 일부 셰어웨어인 점은 있지만
괜찮았다고 답했다.[^hoss1474489]

프록시를 직접 운영하라는 조언의 보안 이득은 프록시 자체가 안전할 때만 성립한다.
모든 키와 모든 프롬프트가 지나가는 지점이므로
이 지점의 취약점은 가장 큰 사고의 입구다.
글은 이 위험을 다루지 않는다.

## 인사이트

### 프록시는 제3자에 대한 의존을 제어 지점으로 바꾸는 장치다

글의 다섯 번째 이유인 제공자 교체의 속도는 관측만큼 중요한 이득이다.
엔드포인트를 하나로 두면
모델과 제공자를 바꿀 때 하네스와 에이전트의 설정을 다시 만지지 않아도 된다.
이는 제공자 종속에서 벗어나는 수단이기도 하다.

HN의 andai는 같은 문제의 더 낮은 형태를 보여 준다.
LLM은 JSON API로 동작하므로 요청을 가로채 파일에 덤프하면
모델이 무엇을 보는지 알 수 있고, API 주소를 로컬 스크립트로 바꾸고
요청을 전달하며 파일에 쓰는 20줄짜리 파이썬 스크립트만으로 된다고 했다.[^andai]
다른 사람의 하네스를 쓰면서
모델이 무엇을 보는지 알 수 없어 답답했다는 말이 이 글의 불만과 같다.
이 문서의 읽기로는 프록시의 핵심은 기능이 아니라 호출 경로 위에 서
있다는 위치이고, 20줄짜리 스크립트와 LiteLLM은 그 위치를 얼마나 쓰느냐만 다르다.

### 캐시의 가치가 커질수록 계측의 가치도 커진다

글이 드는 이득은 캐시 미스를 20초 안에 짚는 것이다.
HN의 viccis는 이것이 얼마나 비싼 문제인지 보여 준다.
Claude 구독에서
서브에이전트의 캐시 TTL은 5분이어서 10분짜리 테스트를 기다리는 동안 캐시가
만료되어 5시간 사용량을 태웠고, 회사의 API에서는 모든 호출이 5분 TTL이어서
모니터링하지 않으면 회사 예산이 타 버린다고 했다.[^viccis]

이 경험이 맞다면 캐시 미스는 비용을 가장 크게 좌우하는 변수 가운데 하나이고,
제공자의 사용량 화면은 그것을 보여 주지 않는다.
에이전트가 오래 일할수록 캐시 TTL과 대기 시간의 상호작용이 비용을 정하게 되고,
이 상호작용은 호출 단위의 시계열이 있어야 보인다.
이 추론은 이 문서의 것이고,
캐시 TTL의 구체적인 값은 댓글의 주장이라 확인하지 않았다.

### 모든 대화가 지나가는 지점은 개인정보가 모이는 지점이다

HN의 lionkor는 EU에서는 대화에 개인 식별 정보가 들어 있을 수 있다고 경고했다.
난독증이 있어서 미안하다는 한마디도 개인 정보이므로
대화는 코드가 아니라 대화로 다뤄야 한다는 것이다.[^lionkor] jakozaur도 조직
전체의 에이전트 세션을 모으는 것이 가장 큰 가치를 주지만
자격 증명을 지우고 보안을 처리해야 한다고 했다.[^jakozaur]

관측을 늘리면 보관해야 하는 민감한 데이터도 함께 는다.
직접 운영하는 프록시의 로그는 제공자가 아니라 자기가 책임지는 데이터이고,
이는 통제의 이득이면서 책임의 비용이다.
글은 이 비용을 다루지 않는다.
