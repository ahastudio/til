# Claude Code 레벨 0에서 999까지: 작은 작업 하나를 완성 조건과 함께 맡기고 직접 확인한다

트윗: [Claude Code最強チート攻略大全](https://twitter.com/29meat_ai/status/2117178315471770094)

## 소개

Twitter 사용자 にく(@29meat_ai)는 2026-11-02에 Twitter Article로 이 글을 올렸다.
글 아래에는 조회수 595.2K와 33분 분량이라는 표시가 있고,
작성자는 프로필에 제조업 18년 경력의 비개발자라고 적었다.
글의 대상은 Claude Code를 써 보고 싶지만 용어에 막혀 준비만 하다 지치는
비개발자다.

글의 중심 주장은 하나다.
작성자는 최강이 무엇이든 맡기는 사람이 아니라 무엇을 맡기고,
어디서 멈추고, 무엇을 보면 완성인지 아는 사람이라고 말한다.
그래서 매번 하는 귀찮은 작업을 하나 골라 Claude Code에게 완성시키고,
잘 되었는지를 스스로 확인하라고 권한다.
이 순서를 레벨 0부터 999까지 열네 단계로 풀어 쓰고,
독자가 자기 위치에서 읽도록 시작 레벨 안내표를 붙였다.

글은 마지막에 LINE 오픈 채팅 「にくのAI爆速攻略」에서 무료 특전 12점을 나눠
준다는 안내로 끝난다.

### 예제의 계산

Lv.2의 예제는 CSV 두 개로 일별 매출을 만드는 일이다.
첫째 파일은 2026-10-01에 노트 2개(단가 300엔)와 펜 3개(단가 100엔),
둘째 파일은 2026-10-02에 노트 1개와 펜 5개다.
글은 첫날 900엔, 둘째 날 800엔, 합계 1,700엔이 정답이라고 하고,
손으로 계산할 수 있다는 점이 요점이라고 말한다.
이 문서가 다시 계산했을 때 2×300+3×100=900,
1×300+5×100=800이므로 합계 1,700으로 맞았다.

### 완성 조건을 전달하는 틀

글이 마지막에 권하는 요청 틀을 한국어로 옮기면 다음과 같다.
번역은 이 문서가 했다.

```text
목적은 ○○입니다. 재료는 ○○에 있습니다.
완성 조건은 ○○입니다. 변경해서는 안 되는 것은 ○○입니다.
판단에 필요한 정보가 부족하면 추측으로 채우지 말고 확인하세요.
방침이 정해진 부분은 진행하고, 결과를 검증하세요.
마지막에 결과물, 실행한 확인, 확인하지 못한 것, 다음 사용법을 보여 주세요.
```

## 동작 방식

### 전달하는 것은 절차가 아니라 판정 조건이다

글이 Lv.2와 Lv.3에서 반복하는 구조는 같다.
코드를 어떻게 쓸지는 지정하지 않고, 원본 데이터를 바꾸지 않는다,
합계가 1,700엔이 된다, 다시 실행할 수 있다,
사용법을 알 수 있다 같은 판정 가능한 조건을 건넨다.
조건을 만족하는 방법은 Claude가 찾는다.
글은 절차를 세세히 지정했는데 그 절차가 틀리면 Claude가 돌아가게 된다는 점을
이유로 든다.

### 확인은 실행된 증거와 확인하지 못한 목록으로 받는다

완성 보고에는 결과물의 위치, 실제로 한 확인,
확인하지 못한 것의 세 가지를 붙이게 한다.
확인용 입력으로는 수량이 빈 행, 단가에 「불명」이라고 쓴 행,
필요한 열이 없는 파일, 파일이 하나도 없는 폴더를 일부러 준다.
판단할 수 없는 행이 조용히 사라지지 않고 이유와 함께 남는지를 본다.
글은 코드를 읽은 것과 화면을 만져 본 것을 별개의 보고로 취급하라고도 한다.

### 고정된 계산은 스크립트에, 상황에 맞는 설명은 Claude에게

Lv.6은 계산 규칙이 정해져 있다면 Claude에게 모든 행을 읽히지 말고 Claude가 만든
스크립트로 처리하라고 한다.
결과를 보고 달라진 점을 설명하거나 처리하지 못한 이유를 읽고 대응안을 내는 일은
계속 Claude의 몫으로 둔다.
반복하는 요청의 절차는 `.claude/skills/weekly-report/SKILL.md` 같은 Skill로
저장하고, 사람이 부를 때만 쓰게 하려면 `disable-model-invocation: true`를 둔다.
글은 이 설정이 붙은 Skill을 그대로 정기 실행에 쓸 수 있다고는 할 수 없다고
경고한다.

### 자동 실행의 위치에 따라 조건이 달라진다

Lv.9는 세 가지 실행 위치를 구분한다.
`/loop`는 열려 있는 세션 안에서 반복하며 PC를 닫으면 멈춘다.
데스크톱의 로컬 정기 작업은 손에 있는 파일을 쓸 수 있지만 PC가 켜져 있고 앱이
열려 있어야 한다.
클라우드의 정기 작업은 PC를 닫아도 돌지만 손에 있는 파일을 그대로 읽지 못한다.
글은 `/schedule`이 확인한 시점에는 연구 프리뷰였다고 쓰고,
대상 요금제와 관리자 제한과 사용량 한도를 확인하라고 한다.

### 확인하는 사람을 구조로 분리한다

Lv.100은 Claude Code를 만드는 사람들의 방식을 네 가지로 소개한다.
작업 중의 대화를 보지 않은 별도의 Claude에게 변경을 확인시키고,
확인 쪽에는 이미 잘 고쳐졌다는 평가를 미리 알리지 않는다.
고치는 왕복은 횟수로 멈추며, 같은 불량을 두 번 고쳐도 해결되지 않으면 더 고치지
않고 시도한 것과 남은 증상과 사람이 정할 것을 정리하게 한다.
보안 지적은 고치거나 오탐이라고 이유를 적어 물리칠 때까지 다음 단계로 가지
못하게 한다.
돈, 로그인, 개인정보, 삭제, 공개는 Claude의 확인과 별도로 사람이 직접 확인하고,
그 뒤에 Claude가 다시 바꾸면 다시 확인한다.

## 도입 전에 정할 것

| 결정      | 선택지                                 | 판단 근거                                                                                         |
| --------- | -------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 시작 작업 | 정답을 아는 작은 작업 / 모호한 큰 작업 | 글이 말하는 확인(손계산 1,700엔)은 정답을 스스로 낼 수 있는 작업에서만 성립한다                   |
| 작업 장소 | 연습용 폴더 / 데스크톱 전체            | 범위가 작을수록 어떤 파일을 건드리는지 추적하기 쉽다. 단 폴더 선택이 PC 전체 접근을 막지는 않는다 |
| effort    | medium에서 시작 / 처음부터 MAX         | 글은 막히면 올리라고 하고, 설정을 만지기 전에 재료와 완성 조건을 점검하라고 한다                  |
| 권한 확인 | 의미를 알고 승인 / 전부 허용           | 글은 허용 요청이 귀찮아 전부 허용하는 일을 하지 말라고 한다                                       |
| 병렬 실행 | 하나로 끝까지 가는 작업이 있을 때만    | 확인하는 사람이 자기 혼자면 에이전트를 늘려도 확인 부담은 그대로다                                |
| 자동 실행 | 손으로 몇 번 통과한 뒤                 | 정기 실행은 실행 위치마다 읽을 수 있는 파일과 필요한 상태가 다르다                                |

effort의 기본값에 대해서는 이 문서가 따로 확인했다.
Search Engine Journal은 Opus 5.5가 기본으로 medium effort로 돌며,
Opus 5에서 쓰던 설정이 아직 맞는다고 가정하지 말라는 Anthropic의 권고를
전했다.[^sej]

## 비평

### 확인 방법이 성립하는 범위가 좁다

글의 방법은 사용자가 정답을 따로 가진 작업에서 가장 잘 작동한다.
1,700엔은 사람이 다른 방식으로 확인한 답이어서,
만든 쪽과 확인하는 쪽이 같은 착각을 해도 잡아낸다는 것이 글의 논거다.
그러나 글이 대상으로 삼는 독자는 코드를 읽지 못하는 사람이고,
이들이 정답을 미리 아는 작업은 합계 계산 같은 일부에 한정된다.
자료 조사에서는 출처 페이지를 열어 보라는 처방이 나오지만,
글은 읽고 판단하는 능력이 없는 경우에 무엇으로 확인할지는 말하지 않는다.

Lv.7의 처방에는 순환이 있다.
모르는 허용 요청이 나오면 Claude에게 이 조작이 무엇을 하는지,
바꾸는 파일과 외부 통신과 요금과 되돌릴 범위를 설명하라고 묻는다.
설명하는 쪽이 조작을 제안한 같은 에이전트이므로,
외부 문서에 심어 둔 지시를 따른 상태라면 설명도 영향을 받을 수 있다.
글은 같은 Lv.7에서 외부 문서의 지시를 따르지 말라고 쓰므로 이 위험을 알고
있지만, 그 처방을 설명 요청에 적용하지는 않았다.
이 위험이 실제로 일어난 사례를 이 문서가 찾은 것은 아니고,
처방의 구조에서 나오는 판단이다.

### Claude Code 내부에 대한 주장은 근거가 연결되지 않는다

Lv.100과 Lv.999는 Claude Code 자체의 코드 약 90%를 Claude가 쓴다는 것,
쓰는 Claude와 확인하는 Claude의 왕복이 하룻밤에 50번 넘게 이어진 적이 있다는 것,
Claude Code의 기본 지시문이 새 모델용으로 80% 이상 줄었다는 것,
Anthropic이 서브에이전트를 늘리지 않는 쪽을 권한다는 것을 전한다.
글에서 이 주장들 옆에 링크나 출처 표기는 없다.
Lv.5는 원래 글이 대화를 작업 책상에 비유한다고 쓰지만 그 글이 무엇인지도 밝히지
않는다.
이 문서는 effort 기본값만 별도로 확인했고, 나머지 주장은 확인하지 못했다.
권고 자체는 이 주장들이 사실이 아니어도 성립한다(확인을 구조로 만들고 규칙을
줄이라는 것은 그 자체로 합리적이다).
다만 주장이 권고에 권위를 더하는 역할을 하므로,
이 숫자들은 작성자가 전한 말로만 읽어야 한다.

### 단계 번호가 난이도의 순서를 말하지 않는다

글은 레벨 0에서 999까지라고 하지만 번호는 0에서 10, 50, 100, 999로 건너뛴다.
번호에서 읽히는 것은 순서이지 난이도나 필요한 지식의 양이 아니다.
예를 들어 Lv.999가 요구하는 것은 규칙과 도구를 덜어 내는 점검이어서,
새로운 기술이 필요한 단계가 아니다.
글은 마지막에 최강의 사람이 하는 일은 레벨 0과 같다고 결론짓는데,
이는 구조로서는 매끄럽지만 Lv.50과 Lv.100의 병렬 실행, 별도 확인자,
보안 게이트가 레벨 0과 같은 일이라는 증거는 아니다.
읽는 사람은 번호를 수준 평가가 아니라 항목 색인으로 쓰는 것이 낫다.

## 확인하기

글의 Lv.2 예제는 그대로 따라 해 볼 수 있다.

- 연습용 폴더를 만들고 안에 `input/`을 만든다.
- 위의 CSV 두 개를 Claude에게 만들게 하고 내용을 직접 열어 본다.
- 일별 매출 집계를 요청하되, 원본 변경 금지와 `output/daily_sales.csv` 저장과 완성 조건(900엔, 800엔, 1,700엔)을 함께 적는다.
- 결과 파일을 직접 열어 세 숫자가 맞는지, `input/`의 원본이 그대로인지 확인한다.
- 수량이 빈 행, 단가가 「불명」인 행을 넣어 이 행들이 0으로 처리되지 않고 이유와 함께 따로 남는지 본다.
- 같은 처리를 다시 실행해서 이중 집계가 생기지 않는지 확인한다.

이 확인에서 한 가지라도 통과하지 못하면 자동 실행이나 병렬 실행으로 넘어가지
않는다.

## 기억할 원칙

### 맡기기 전에 합격 조건을 정한다

글이 처음부터 끝까지 반복하는 질문은 무엇이 되면 완성인가다.
조건이 판정 가능하지 않으면 Claude가 한 보고를 사람이 평가할 수 없고,
확인이 점점 어려워진다.
조건을 쓰는 데 필요한 것은 코딩 지식이 아니라 자기 일의 재료와 현장의 함정을
아는 것이라는 점이 글의 결론이다.

### 확인하는 사람은 만든 쪽과 다른 쪽이어야 한다

글의 Lv.4와 Lv.100은 같은 이유를 다른 규모로 말한다.
만든 쪽에게 되었는지 물으면 대체로 되었다는 답이 돌아오므로,
확인은 정답을 가진 사람이나 작업 과정을 보지 않은 다른 세션이 맡는다.
이 원칙은 도구가 바뀌어도 유지된다.
