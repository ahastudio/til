# Graphify

<https://graphify.com/>

<https://github.com/Graphify-Labs/graphify>

## 소개

홈페이지는 이 도구를 한 줄로 소개한다.

> Graphify · the code knowledge graph for AI coding assistants

Graphify는 코드, DB 스키마, 인프라 설정, 문서, 이미지, 영상까지
프로젝트 폴더 전체를 지식 그래프로 변환하는 도구다.
AI 코딩 어시스턴트에서 `/graphify`를 입력하면
프로젝트를 그래프로 매핑하고,
이후에는 파일을 grep으로 뒤지는 대신 그래프에 질의할 수 있다.

핵심 설계는 두 단계로 나뉜다.
코드는 tree-sitter AST로 로컬에서 파싱되며,
결정적(deterministic)이고 LLM 호출이 없으며 아무것도 기기 밖으로 나가지 않는다.
반면 문서, PDF, 이미지, 영상 같은 비정형 자료는
설정된 AI 모델을 이용한 시맨틱 추출을 거치는데,
이 단계는 선택적이며 명시적으로 활성화했을 때만 동작한다.
결과물은 `graph.html`(인터랙티브 시각화),
`GRAPH_REPORT.md`(주요 발견과 제안 질의 목록),
`graph.json`(질의 가능한 전체 그래프 데이터) 세 가지로 출력된다.

그래프 내부에서는 `calls`, `imports`, `inherits`, `mixes_in` 같은
관계 유형이 식별되고,
각 엣지는 소스에 명시된 관계인 `EXTRACTED`와
분석으로 추론된 관계인 `INFERRED`로 구분해 태그된다.
또한 Leiden 알고리즘으로 커뮤니티를 탐지해
LLM 없이도 하위 시스템을 나누고 “god node”(과도하게 연결된 개념)를 찾아낸다.
질의는 `graphify query`, `graphify path`, `graphify explain` 세 명령으로 이루어지며,
Claude Code, Cursor, GitHub Copilot, Gemini CLI 등
20개 이상의 AI 코딩 어시스턴트를 지원한다.
네이티브 MCP 서버로 그래프를 노출해 팀 전체가 반복적으로 도구를 호출하며
접근할 수도 있다.

이후 저장소는 규모와 채택 지표를 크게 키웠다.
GitHub 별 11만 8천 개, 포크 1만 9백 개를 기록하고,
Y Combinator S26 배치 회사(graphify.com)로 소개되며
정식 v1 전에 app.graphify.com 얼리 액세스를 예고한다.
라이선스는 Apache-2.0과 MIT 이중 라이선스이고,
코드는 37개의 tree-sitter 문법으로 파싱하며
패키지명은 `graphifyy`(y 두 개), 명령은 `graphify`다.
지원 어시스턴트도 넓어져 Claude Code와 Cursor 외에
OpenClaw, Google Antigravity, Factory Droid, Kimi Code, Amp,
Devin CLI, Pi 코딩 에이전트, Hermes, Trae 등이 목록에 올랐다.
`graphify hook install`로 커밋마다 자동 재구축을 걸고,
`graphify export callflow-html`로 아키텍처 다이어그램을 뽑는 명령도 추가되었다.
벤치마크(BENCHMARKS.md)도 비교군을 붙여, LOCOMO recall@10 0.497(경쟁 도구 0.048~0.149),
LOCOMO QA 정확도 45.3%(supermemory 49.7%, mem0 27.3%),
LongMemEval-S QA 76%(밀집 RAG와 동률),
코드 추출 시 토큰당 LLM 크레딧 0을 제시한다.

## 사용법

패키지를 설치한 뒤 `graphify install`로 AI 어시스턴트에 스킬을 등록한다.

```bash
uv tool install graphifyy
graphify install
```

어시스턴트에서 `/graphify .`를 실행하면 앞서 말한 세 가지 산출물이 생긴다.
그다음부터는 파일을 다시 읽지 않고 그래프에 바로 질의한다.

```bash
graphify query "what connects auth to database?"
graphify path "ServiceA" "ServiceB"
```

플랫폼별로 상시 활성 모드를 설치할 수도 있다.

```bash
graphify claude install
```

이 명령을 실행하면 어시스턴트가 파일을 grep으로 뒤지는 대신 그래프 질의를 기본으로 택하게 된다.
주석과 문서에 적힌 설계 의도도 그래프의 일급 노드로 추출된다.
텔레메트리나 추적은 없고, 원하면 `~/.cache/graphify-queries.log`에 질의 로그를 남길 수 있다.

## 분석

### RAG의 벡터 임베딩을 그래프 구조로 대체하는 선택

Graphify가 내세우는 가장 뚜렷한 차별점은 임베딩을 쓰지 않는다는 점이다.
대부분의 코드베이스 이해 도구는 청크를 나누고 벡터로 임베딩한 뒤
유사도 검색으로 관련 코드를 찾는 RAG 방식을 취한다.
이 방식은 구현이 쉽지만 “의미적으로 비슷해 보이는 것”과
“실제로 연결된 것”을 혼동하기 쉽고,
임베딩 모델이 바뀌면 검색 결과도 따라 흔들리는 드리프트 문제를 안고 있다.

Graphify는 대신 tree-sitter AST로 코드를 파싱해
호출, 임포트, 상속 같은 관계를 결정적으로 추출한다.
이는 코드 구조를 그대로 반영하는 그래프이므로
“왜 이 두 노드가 연결되었는가”를 설명할 수 있다는 장점이 있다.
`EXTRACTED`와 `INFERRED`를 구분해 태그하는 설계는
이 설명 가능성을 한층 강화한다.
사용자는 어떤 관계가 소스 코드에서 직접 읽힌 것이고
어떤 관계가 도구의 추론을 거친 것인지 구분할 수 있다.
이는 에이전트가 그래프를 근거로 코드를 수정할 때
잘못된 추론에 기반한 결정을 내릴 위험을 낮추는 장치로 볼 수 있다.

다만 이 접근은 코드처럼 명시적 구조가 있는 자료에서는 강력하지만,
문서나 이미지처럼 구조가 암묵적인 자료에서는 결국 LLM에 의존할 수밖에 없다.
결과적으로 Graphify는 순수한 결정적 도구라기보다
“구조화 가능한 부분은 결정적으로, 나머지는 선택적으로 LLM에 위임하는” 혼합 설계에 가깝다.

두 접근의 실용적 차이는 질문의 종류에서 갈린다.
“이 함수와 비슷한 것을 찾아 달라”는 질문에는 임베딩이 자연스럽다.
반면 “인증 모듈에서 데이터베이스까지 실제 호출 경로를 보여 달라”나 “이 클래스를 직간접으로 쓰는 파일을 모두 찾아 달라”는 질문에는 그래프가 훨씬 정확하다.
Graphify가 노리는 것은 뒤쪽의 구조적 질문이다.

### 컨텍스트 창의 선택 문제를 미리 구조화한다

AI 코딩 어시스턴트의 근본적인 병목은 컨텍스트 창 한계다.
코드베이스가 수만 개 파일로 이루어져 있으면, 어시스턴트는 어떤 파일을 컨텍스트에 넣을지 매번 골라야 하고 잘못 고르면 정확도가 급격히 떨어진다.
Graphify의 그래프는 이 선택 문제를 미리 구조화해 둔다.
특정 함수나 모듈에 대한 질문을 받으면 파일 전체를 읽는 대신 관련 노드와 엣지만 조회해 필요한 최소한의 컨텍스트를 꾸릴 수 있다.
grep 기반 검색과 달리, 이렇게 꾸린 컨텍스트에는 의존성 맥락이 함께 따라온다.

### 로컬 처리와 선택적 클라우드 호출을 분리한 프라이버시 경계

코드 파싱은 로컬에서 완결되고 아무것도 외부로 전송되지 않는다는 점은
기업 코드베이스를 다루는 도구로서 중요한 신뢰 요소다.
반면 문서·이미지·영상의 시맨틱 추출은 Anthropic, OpenAI, Gemini, Ollama,
AWS Bedrock 등 다양한 백엔드를 선택적으로 호출한다.

이 경계 설정은 “가장 민감한 자산인 소스 코드는 로컬에 남기고,
상대적으로 덜 민감하거나 이미 공개된 문서류만 외부로 내보낸다”는
전략적 판단으로 읽힌다.
Ollama 같은 로컬 모델 백엔드를 지원하는 것도
같은 맥락에서 완전한 로컬 파이프라인을 구성하려는 사용자를 겨냥한 선택이다.
다만 이 구분이 실제로 얼마나 엄격하게 지켜지는지는
사용자가 어떤 백엔드를 설정하느냐에 달려 있어,
설계 의도와 실제 운영 사이에는 사용자 책임으로 남는 여지가 있다.

### 팀 협업을 위한 그래프 버전 관리 장치

Graphify는 `graphify-out/` 디렉터리를 git으로 커밋하도록 설계했고,
post-commit 훅으로 그래프를 증분 재구축하며,
병합 시 충돌하는 `graph.json`을 자동으로 union-merge하는
전용 병합 드라이버까지 제공한다.
이는 그래프를 “한 번 만들고 끝나는 산출물”이 아니라
코드베이스와 함께 진화하는 살아있는 자산으로 다루겠다는 의도를 보여준다.

이 설계는 팀이 매번 그래프를 처음부터 재구축하는 비용을 없애고,
누구나 최신 그래프를 pull 한 번으로 받아볼 수 있게 한다는 점에서 실용적이다.
동시에 이는 그래프 자체가 코드베이스만큼 자주 바뀌는 아티팩트가 되었을 때,
git 히스토리에 반복적으로 큰 JSON diff가 쌓이는 부담을 감수하겠다는
선택이기도 하다.

### 대규모 그래프에서 시각화가 질의로 무게중심을 옮기는 지점

README는 노드 수가 약 5000개를 넘으면 HTML 시각화가 다루기 어려워지고,
사용자가 JSON 질의로 전환하게 된다고 명시한다.
이는 Graphify의 세 가지 산출물 중 `graph.html`이
작은 프로젝트나 하위 모듈 탐색용 보조 도구이며,
실질적인 작업 도구는 결국 `graphify query`, `graphify path`,
`graphify explain` 같은 명령형 질의라는 점을 시사한다.

즉 시각화는 사람이 그래프의 전체 형태를 처음 이해할 때 유용하지만,
에이전트가 반복적으로 정보를 가져오는 실제 워크플로에서는
구조화된 질의 인터페이스가 중심이 된다.
이 설계는 Graphify가 “사람이 보는 지도”와
“기계가 읽는 질의 대상”이라는 두 가지 사용 맥락을 동시에 만족시키려 한
결과로 볼 수 있다.

## 비평

### “그래프면 다 설명 가능하다”는 전제는 지나치게 낙관적이다

`EXTRACTED`와 `INFERRED`를 구분하는 설계는 분명 신뢰도를 높이는 장치이지만,
`INFERRED` 관계가 어떤 알고리즘으로, 어느 정도의 확신을 갖고 도출되었는지에 대한
구체적인 신뢰도 수치나 검증 방법은 README에서 드러나지 않는다.
“추론되었다”는 이진 표시만으로는
그 추론이 얼마나 신뢰할 만한지 사용자가 판단하기 어렵다.
그래프 기반 도구가 벡터 검색보다 설명 가능하다는 주장은
관계의 존재 여부를 보여준다는 점에서는 사실이지만,
그 관계의 정확도까지 보장한다는 뜻은 아니다.
결과적으로 “결정적이라 신뢰할 수 있다”는 인상과
“실제로 얼마나 정확한가”라는 질문 사이에는 간극이 남는다.

### tree-sitter의 결정성은 동적 언어의 런타임 관계를 보지 못한다

Graphify는 tree-sitter AST를 결정적 파싱의 근거로 내세운다.
그러나 이 주장은 정적 분석이 런타임 동작을 잡아내지 못한다는 한계를 뒤로 미룬다.
Python의 동적 임포트, JavaScript의 런타임 의존성 주입, 메타프로그래밍, 런타임에 생성되는 클래스 같은 패턴에서 AST 기반 파싱은 실제 의존 관계를 놓친다.

이 한계는 현대 코드베이스에서 점점 더 무거워진다.
의존성 주입 프레임워크, 데코레이터 패턴, 런타임 플러그인 시스템은 정적 분석으로는 추출할 수 없는 관계를 만든다.
Graphify는 이것을 `INFERRED` 태그로 일부 처리하려 하지만, 잘못 추론된 관계가 그래프를 오염시킬 때 태그만으로는 막을 수 없다.
결정적인 부분이 결정적으로 틀릴 수 있다는 점이 이 설계에서 가장 덜 드러난 위험이다.

### 주석에서 설계 의도를 뽑는다는 주장은 검증되지 않았다

주석과 문서에서 설계 의도를 추출해 그래프 노드로 만든다는 기능은 매력적이지만, 그 과정을 얼마나 믿을 수 있는지 문서는 검증하지 않는다.
코드 주석은 오래된 정보를 담고 있는 경우가 흔하고, 의도가 아니라 무엇을 하는지만 설명하는 주석도 많다.
AI로 주석에서 의도를 뽑는 과정은 모델의 한계를 그대로 물려받는다.
도메인 지식이 없으면 주석의 맥락을 잘못 읽을 수 있고, 그렇게 잘못 추출된 의도 노드가 그래프에 들어가면 질의 결과에 근거 없는 확신을 얹게 된다.

### 벤치마크가 정작 코드 이해가 아니라 메모리 과제를 측정한다

이후 BENCHMARKS.md는 비교군을 붙여 수치를 보강했다.
LOCOMO recall@10 0.497을 경쟁 도구 0.048~0.149와 나란히 놓고,
LOCOMO QA 정확도 45.3%를 supermemory 49.7%, mem0 27.3%와 비교하며,
LongMemEval-S QA 76%가 밀집 RAG와 동률이라고 제시한다.
비교군이 생긴 것은 진전이지만, 더 근본적인 문제가 남는다.
LOCOMO와 LongMemEval은 대화 메모리와 장기 기억 질의응답 벤치마크이지
코드베이스 이해 벤치마크가 아니다.
Graphify가 파는 것은 코드·스키마·설정을 그래프로 만들어
에이전트가 질의하게 하는 것인데,
그 핵심 사용 사례를 재는 벤치마크는 제시되지 않는다.
QA 정확도에서는 supermemory에 뒤지고(45.3% 대 49.7%),
LongMemEval에서는 밀집 RAG와 동률인데,
동률이라는 것은 임베딩을 버린 대가로 얻은 우위가 없다는 뜻이기도 하다.
그러면 이 수치들은 “그래프가 벡터보다 낫다”를 증명하지 못하고,
오히려 코드 이해가 아닌 다른 과제에서 대등하거나 뒤처짐을 보여 준다.
자체 벤치마크가 비교군을 갖추었어도,
그것이 도구의 실제 목적과 어긋난 과제를 재면
재현 가능성 문제 이전에 측정 대상의 적절성 문제가 남는다.

### 별 11만 8천이 조직적 채택이 아니라 신호의 붕괴일 수 있다

이 저장소는 GitHub 별 11만 8천 개를 내세운다.
이 수치가 사실이라면 Graphify는 전체 GitHub에서
가장 많은 별을 받은 저장소 열 손가락 안에 드는,
React Native나 VS Code에 필적하는 프로젝트가 된다.
그러나 그 규모에 걸맞은 유기적 논의의 흔적이 없다.
Hacker News에 이 저장소가 여러 번 제출되었지만
모두 2~3점에 댓글 0개로 묻혔고, Lobste.rs에는 스레드조차 없다.
11만 8천 개의 별과 사실상 0에 가까운 토론이 공존하는 것이다.

이 불일치가 중요한 이유는 그것이 별이라는 신호의 신뢰성을 무너뜨리기 때문이다.
진짜로 폭발적으로 채택된 개발 도구는
그 채택에 비례하는 논의를 남긴다.
100만 줄의 코드를 그래프로 만드는 도구가 실제로 그만큼 쓰인다면,
사용 후기와 비교와 반론이 여러 커뮤니티에 쌓여야 정상이다.
그 논의가 없는데 별만 11만이라면,
그 별은 채택의 증거가 아니라 채택으로 보이려는 신호일 가능성이 높다.
이것은 이 저장소의 다른 노트가 다룬 품질 신호의 죽음과 정확히 이어진다.
매끈한 README와 인상적인 별 수가 실력과 채택을 가리키던 시대는 끝났고,
이제 더 완벽해 보일수록 더 의심스럽다.
Graphify의 기술이 나쁘다는 뜻이 아니라,
11만 8천이라는 숫자가 그 기술의 실제 가치를 판단하는 데
아무 도움이 되지 않는다는 뜻이다.
별을 신뢰 신호로 읽는 습관 자체가 이 사례에서 시험대에 오른다.

### 팀 단위로 그래프를 커밋하는 관행은 저장소 위생을 해칠 소지가 있다

`graphify-out/`을 git에 커밋하고 자동 병합 드라이버로 관리하게 만드는 설계는
편의성을 위해 저장소의 성격을 바꾸는 결정이다.
큰 코드베이스일수록 `graph.json`은 상당한 크기로 자라날 수 있고,
매 커밋마다 갱신되는 대용량 바이너리성 아티팩트는
git 히스토리를 무겁게 만들고 클론 속도를 늦추는 전형적인 안티패턴에 가깝다.
자동 union-merge가 실제 충돌 상황에서 항상 의미적으로 올바른 그래프를 만들어내는지도
검증하기 쉽지 않은 부분이다.
편의를 위해 파생 산출물을 소스 트리에 영구히 남기는 선택은
장기적으로 저장소 관리 부채로 돌아올 가능성이 있다.

### 20개 이상의 통합을 지원한다는 주장은 유지보수 부담을 감춘다

Claude Code, Cursor, GitHub Copilot, Gemini CLI, Codex 등
수많은 AI 어시스턴트와 MCP, 여러 LLM 백엔드, 여러 출력 포맷을
동시에 지원한다는 것은 사용자 입장에서는 매력적이지만,
프로젝트 관리 관점에서는 각 통합이 개별적으로 깨질 수 있는
표면적을 그만큼 넓힌다는 뜻이다.
신생 프로젝트가 이렇게 폭넓은 통합 매트릭스를 유지보수 리소스와 함께
지속적으로 감당할 수 있을지는 스타 수나 초기 인기와는 별개의 문제다.
넓은 통합 범위는 초기 채택을 끌어내는 데는 효과적이지만,
장기적으로 품질을 고르게 유지하기 어려운 구조를 스스로 만든다.

## 인사이트

### 코딩 에이전트의 등장이 “정적 분석”을 다시 인프라의 중심으로 불러왔다

지난 수년간 정적 분석 도구는 IDE의 부속 기능 정도로 취급되어 왔다.
하지만 코딩 에이전트가 방대한 컨텍스트 없이도 코드베이스를 이해해야 하는 상황이 되면서,
tree-sitter 기반의 결정적 구조 추출이 다시 핵심 인프라로 떠오르고 있다.
Graphify는 이 흐름의 한 사례로 볼 수 있다.
에이전트가 파일을 하나씩 열어 컨텍스트 윈도우를 소모하는 대신
미리 구축된 그래프에 질의해 필요한 정보만 가져오게 하는 방식은,
에이전트 시대에 “코드 이해”라는 오래된 문제가
새로운 형태의 인프라 계층으로 재조립되고 있음을 보여준다.

이는 2차 효과로 이어질 가능성이 크다.
그래프가 코드베이스를 이해하는 표준 인터페이스로 자리 잡으면,
에이전트의 성능은 점점 더 그 프로젝트에 얼마나 좋은 그래프가
미리 구축되어 있는지에 좌우될 수 있다.
즉 “에이전트 친화적인 코드베이스”의 기준이
코드 스타일이나 문서화 수준을 넘어
그래프 추출이 얼마나 깔끔하게 되는가로 옮겨갈 여지가 있다.

### 검색 엔진의 색인 구축 역사가 지식 그래프 도구의 미래를 예고한다

Graphify가 그래프를 미리 만들고 git으로 공유하는 방식은
검색 엔진이 크롤링과 색인을 분리해온 역사와 구조적으로 닮았다.
초기 웹 검색이 매 질의마다 문서를 다시 훑는 대신
미리 만든 역색인(inverted index)에 질의하는 방식으로 전환하며 속도와 품질을 얻었듯,
Graphify는 매번 파일을 훑는 대신 미리 만든 그래프에 질의하게 한다.

이 유비가 흥미로운 지점은 색인의 역사가 결국
“색인을 최신 상태로 유지하는 문제”로 수렴했다는 데 있다.
검색 엔진은 이를 위해 증분 크롤링, 캐시 무효화, 우선순위 재색인 같은
정교한 인프라를 발전시켰다.
Graphify의 post-commit 훅과 자동 병합 드라이버는
이 문제의 초기 형태에 대한 대응으로 보이며,
프로젝트가 성장한다면 결국 더 정교한 증분 갱신 전략을 요구받을 가능성이 높다.
지금의 “커밋마다 전체 재구축”에 가까운 단순한 방식은
소규모 코드베이스에서는 문제가 없지만,
대규모 모노레포로 갈수록 검색 엔진이 겪었던 것과 같은
확장성 압박에 부딪힐 것으로 보인다.

### 결정성과 포괄성은 근본적으로 맞바꿔야 하는 관계다

Graphify가 강조하는 “LLM 없이 결정적으로 추출한다”는 특징은
코드처럼 형식 문법이 있는 자료에서만 온전히 성립한다.
문서, 이미지, 영상처럼 형식이 느슨한 자료를 그래프에 편입시키려는 순간
필연적으로 LLM의 확률적 판단이 개입하게 되고,
그 순간 결정성이라는 장점은 부분적으로 희석된다.

이는 명시적으로 다뤄지지 않는 트레이드오프다.
README는 “코드는 결정적이고 로컬”이라는 점과
“문서와 이미지까지 그래프로 만든다”는 두 가지 장점을 나란히 내세우지만,
두 장점이 사실은 같은 축의 양 끝에 있다는 점은 강조되지 않는다.
포괄성을 넓힐수록 결정성은 낮아지고,
결정성을 지키려면 다룰 수 있는 자료의 범위는 좁아질 수밖에 없다.
Graphify가 실제로 유용한 도구가 되려면
이 경계선에서 사용자가 어디까지를 “믿을 수 있는 그래프”로 취급하고
어디부터를 “참고용 추정”으로 취급해야 하는지에 대한
더 명시적인 안내가 필요해 보인다.

### 코드 이해의 병목은 검색이 아니라 구조화에 있다

AI 코딩 어시스턴트 시대에 코드 검색은 어느 정도 해결된 문제다.
grep, 시맨틱 검색, 파일 트리 탐색은 이 코드가 어디 있느냐는 질문에 대부분 답한다.
진짜 병목은 이 코드가 전체 시스템에서 어떤 역할을 하느냐는 구조적 이해다.

Graphify는 스스로를 검색 도구가 아니라 구조화 도구로 정의한다.
지금의 어시스턴트가 이 파일을 읽고 저 파일을 읽기를 반복하는 방식은 사람이 처음 코드베이스를 파악할 때 하는 일과 같다.
지식 그래프는 이 과정을 한 번으로 줄여, 어시스턴트가 파일 단위 검색을 넘어 시스템 전체의 의존성 맥락을 갖추도록 돕는다.

### 로컬 우선 아키텍처가 기업 도입의 열쇠가 된다

벡터 임베딩 기반 코드 검색 도구가 부딪히는 가장 큰 도입 장벽은 코드를 외부 서버로 보내야 한다는 점이다.
기업 보안 정책, 지적재산 보호, 데이터 거버넌스 요구가 모두 이 모델과 충돌한다.
Graphify의 로컬 우선 아키텍처는 이 장벽을 구조적으로 없앤다.

이것은 기능상의 이점을 넘어 영업 전략의 의미를 가진다.
금융, 의료, 방산, 정부처럼 보안에 민감한 시장에서 코드가 로컬을 벗어나지 않는다는 보장은 의사결정 구조를 단순하게 만든다.
GitHub Copilot의 기업용 버전이 프라이빗 배포 선택지를 강조하는 것도 같은 이유다.
Graphify가 이 시장에서 성공한다면 기술적 우수성보다 로컬 처리라는 아키텍처 선택이 더 큰 몫을 할 가능성이 있다.
다만 앞서 짚었듯 문서와 이미지의 시맨틱 추출은 외부 모델을 부를 수 있으므로, 기업이 사는 것은 도구가 아니라 그 경계를 어떻게 설정하느냐는 운영 정책이다.

### 어시스턴트의 슬래시 명령이 새로운 배포 채널이 되고 있다

Graphify가 `/graphify` 슬래시 명령으로 어시스턴트에 붙는 방식은 더 큰 흐름의 일부다.
AI 어시스턴트가 단일 모델에서 도구 오케스트레이터로 바뀌면서, 어시스턴트의 역량은 내장된 지식보다 어떤 도구를 부르느냐에 좌우된다.

과거에는 IDE 플러그인 마켓플레이스에 올라가는 것이 개발 도구 생태계의 진입점이었다.
지금은 Claude Code, Cursor, Gemini CLI 같은 어시스턴트의 도구 계층에 올라타는 것이 그 역할을 대신한다.
Graphify가 20개가 넘는 플랫폼과의 통합을 앞세우는 것도 이 흐름을 반영한다.
이 계층이 성숙하면 IDE 플러그인 시장과는 다른 구조의 경쟁이 펼쳐질 것이고, 앞서 비평한 통합 매트릭스의 유지보수 부담은 그 경쟁의 입장료가 된다.
