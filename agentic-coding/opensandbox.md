# OpenSandbox: AI 에이전트용 샌드박스를 표준 인프라로 만들려는 Alibaba의 런타임

<https://open-sandbox.ai/>

<https://github.com/opensandbox-group/OpenSandbox>

GN 토론: <https://news.hada.io/topic?id=32685>

## 소개

OpenSandbox는 AI 애플리케이션을 위한 범용 샌드박스 플랫폼이다.
자기소개는 안전하고 빠르며 확장 가능한 AI 에이전트용 샌드박스 런타임이다.
Apache-2.0 라이선스이며 주로 Python으로 작성되었고,
2025년 12월에 만들어졌고, 2026년 9월 23일 기준 스타 15,477개, 포크 1,419개다.
Java 패키지 이름(`com.alibaba.opensandbox`)과
npm 패키지(`@alibaba-group/opensandbox`),
Alibaba Cloud 레지스트리에서 드러나듯 Alibaba가 뒷받침한다.
CNCF Landscape에 등재되어 있고 OpenSSF Best Practices 배지를 달았다.

대상 시나리오가 넓다.
코딩 에이전트, GUI 에이전트, 에이전트 평가,
AI 코드 실행, 강화학습(RL) 훈련을 든다.
이것들을 위해 여러 언어 SDK와 통합된 샌드박스 API,
Docker와 Kubernetes 런타임을 제공한다.
SDK는 Python, Java/Kotlin, JavaScript/TypeScript, C#/.NET, Go를 지원하고,
`osb`라는 터미널 CLI와 MCP 서버 통합도 있다.

주요 기능이 일곱 갈래로 제시된다.
샌드박스 프로토콜은 수명 주기 관리 API와 실행 API를 정의해
커스텀 런타임을 확장하게 한다.
샌드박스 런타임은 Docker와 고성능 Kubernetes를 지원해
로컬 실행과 대규모 분산 스케줄링을 모두 가능하게 한다.
샌드박스 환경으로 Command, Filesystem, Code Interpreter 구현이 내장되어 있고,
예제가 코딩 에이전트(Claude Code),
브라우저 자동화(Chrome, Playwright),
데스크톱 환경(VNC, VS Code)을 다룬다.
네트워크 정책은 통합 인그레스 게이트웨이와
샌드박스별 이그레스 통제를 제공한다.
자격 증명 볼트는 실제 비밀을 워크로드에 노출하지 않고
샌드박스의 외부 요청에 안전하게 주입한다.
강한 격리는 gVisor, Kata Containers, Firecracker microVM 같은
보안 컨테이너 런타임을 지원해
샌드박스 워크로드와 호스트 사이의 격리를 강화한다.
릴리스 이미지는 Cosign으로 키리스 서명되고 프로버넌스 증명을 포함하며,
프로덕션 이미지는 다이제스트로 고정하고 검증하도록 안내한다.

저장소 경로는 `alibaba/OpenSandbox`에서 `opensandbox-group/OpenSandbox`로 옮겨졌고, 이전 주소는 리다이렉트된다.
격리된 환경에서 코드를 실행하고 파일을 조작하며 네트워크를 제어할 수 있도록 멀티 언어 SDK, 통합 API, Docker와 Kubernetes 런타임을 제공한다.

## 핵심 아키텍처: 두 API 레이어 분리

OpenSandbox의 가장 중요한 설계 결정은 API를 두 레이어로 분리한 것이다.

```text
[외부 클라이언트]
       │
       ▼
[Lifecycle API] ← 샌드박스 생성/삭제/일시정지/재개
       │          (컨테이너 오케스트레이션 레이어)
       ▼
[컨테이너 런타임] Docker / Kubernetes
       │
       ▼
[execd 데몬] ← 컨테이너 내부에서 실행
       │
       ▼
[Execd API] ← 코드 실행/명령어/파일 조작
              (샌드박스 실행 레이어)
```

이 분리를 통해 런타임이 바뀌어도(Docker → Kubernetes)
실행 API는 동일하게 유지된다. 인프라 교체 비용이 0이다.

### Lifecycle API

샌드박스의 외부 생애주기를 관리한다.

| 엔드포인트                              | 역할                   |
| --------------------------------------- | ---------------------- |
| `POST /sandboxes`                       | 컨테이너 이미지로 생성 |
| `DELETE /sandboxes/{id}`                | 종료                   |
| `POST /sandboxes/{id}/pause`            | 상태 보존하며 일시정지 |
| `POST /sandboxes/{id}/resume`           | 재개                   |
| `POST /sandboxes/{id}/renew-expiration` | 만료 시간 연장         |
| `GET /sandboxes/{id}/endpoints/{port}`  | 서비스 접근 URL        |

인증: `OPEN-SANDBOX-API-KEY` 헤더

### Execd API

컨테이너 내부의 execd 데몬이 처리한다.

| 엔드포인트            | 역할                      |
| --------------------- | ------------------------- |
| `POST /code`          | Jupyter 커널로 코드 실행  |
| `POST /code/context`  | 실행 컨텍스트(세션) 생성  |
| `GET /code/contexts`  | 활성 컨텍스트 목록        |
| `POST /command`       | 셸 명령어 실행            |
| `GET /files/download` | 파일 다운로드             |
| `POST /files/upload`  | 파일 업로드               |
| `POST /files/replace` | 배치 텍스트 치환          |
| `GET /files/search`   | 글로브 패턴으로 파일 검색 |

인증: `X-EXECD-ACCESS-TOKEN` 헤더


## 샌드박스 상태 머신

```text
Pending → Running → Pausing → Paused
                 ↘           ↙
                  Stopping → Terminated
                  ↕
                 Failed
```

Pause/Resume은 컨테이너를 종료하지 않고 상태를 보존한다.
RL 학습처럼 장시간 실행되는 작업에서 핵심 기능이다.

## SDK 설계: API-First 멀티 언어

OpenAPI 명세에서 4개 언어 SDK를 파생한다.
명세가 진실의 단일 원천(Single Source of Truth)이다.

지원 언어: Python, JavaScript/TypeScript, Java/Kotlin, C#/.NET (Go 계획 중)

### Python SDK 예시

```python
import asyncio
from opensandbox.sandbox import Sandbox
from opensandbox.config import ConnectionConfig

async def main():
    config = ConnectionConfig(
        domain="api.opensandbox.io",
        api_key="your-api-key"
    )
    sandbox = await Sandbox.create(
        "ubuntu",
        connection_config=config
    )
    async with sandbox:
        result = await sandbox.commands.run(
            "echo 'Hello Sandbox!'"
        )
        print(result.logs.stdout[0].text)
        await sandbox.kill()

asyncio.run(main())
```

동기(`SandboxSync`)와 비동기(`Sandbox`) API를 모두 제공한다.
`async with` 컨텍스트 매니저로 자원 정리를 보장한다.

## Kubernetes BatchSandbox: O(1) 배치 생성

일반적으로 N개 샌드박스를 생성하려면 N번의 API 호출이 필요하다.
`BatchSandbox` CRD는 단일 리소스 생성으로 N개를 일괄 프로비저닝한다.
대규모 병렬 에이전트 실행(예: 에이전트 평가, RL 훈련)에서 핵심 차별점이다.

`Pool` CRD도 제공한다.
사전 워밍된 컨테이너 풀에서 꺼내오는 방식으로 샌드박스 생성 지연을 제거한다.


## Egress: DNS + nftables 이중 방어

단순 IP 필터링이나 DNS 필터링 중 하나만 쓰지 않는다.
두 레이어를 조합한다.

```text
컨테이너 DNS 요청
       │
       ▼
[DNS 프록시 (127.0.0.1:15353)]
  ├─ 허용 도메인 → NXDOMAIN이 아닌 정상 응답
  │               + 해석된 IP를 nftables에 동적 등록
  └─ 거부 도메인 → NXDOMAIN 반환
       │
       ▼
[nftables IP 필터]
  ├─ 등록된 IP → 통과 (TTL 기반 자동 만료)
  └─ 미등록 IP → 차단 (기본 거부)
```

DNS TTL이 만료되면 nftables 규칙도 자동으로 제거된다.
DNS 레이어만으로는 막을 수 없는 직접 IP 접근을 nftables가 차단하고,
nftables만으로는 표현하기 어려운 도메인 정책을 DNS가 처리한다.

## OSEP: 설계 방향을 보여주는 제안서

OpenSandbox Enhancement Proposals(OSEP)가 공개되어 있다.

| OSEP | 제목                              | 상태      |
| ---- | --------------------------------- | --------- |
| 0001 | FQDN 기반 이그레스 제어           | 구현 완료 |
| 0002 | Kubernetes SIGs 에이전트 샌드박스 | 계획      |
| 0003 | 볼륨·볼륨 바인딩 지원             | 계획      |
| 0004 | 보안 컨테이너 런타임              | 계획      |

OSEP-0004(보안 컨테이너 런타임)는 gVisor, Kata Containers 같은
강화된 격리 레이어를 추가하는 방향으로 추측된다.
현재 Docker 컨테이너보다 강한 격리가 필요한 시나리오를 목표로 한다.

그 제안은 이후 실현됐다.
README의 기능 목록에 gVisor와 Kata Containers와 Firecracker microVM 지원이
올라와 있으므로 위 표의 0004는 계획이 아니라 반영된 상태로 읽어야 한다.


## 분석

### 이 프로젝트는 샌드박스를 기능이 아니라 표준 인프라 계층으로 규정한다

OpenSandbox의 핵심 주장은 범용이라는 단어에 있다.
특정 에이전트를 위한 샌드박스가 아니라
모든 AI 애플리케이션을 위한 샌드박스 플랫폼이라는 것이다.
코딩 에이전트부터 GUI 에이전트,
평가와 RL 훈련까지 하나의 샌드박스 계층으로 묶는다.
이것은 샌드박스를 각 도구가 알아서 만드는 부품이 아니라
그 위에 여러 도구가 서는 표준 인프라로 보는 관점이다.

이 관점이 지금 나오는 이유는 에이전트가 코드를 실행하기 때문이다.
에이전트가 자율적으로 명령을 돌리고 파일을 바꾸고
브라우저를 조작하면,
그것을 격리된 환경에서 해야 한다.
격리되지 않으면 에이전트의 실수나 악용이
호스트를 망가뜨리기 때문이다.
그런데 지금까지는 각 에이전트 도구가
자기 샌드박스를 따로 만들었다.
Claude Code가 자기 방식으로,
다른 에이전트가 또 다른 방식으로 격리를 구현했다.
OpenSandbox는 그 중복을 하나의 계층으로 흡수하려 한다.

이 프로젝트를 이 저장소의 다른 문서들과 이으면 흐름이 보인다.
Poke가 사용자 생성 코드마다 데이터베이스를 격리하고,
key-amnesia가 에이전트에게서 비밀을 격리하고,
OpenSandbox가 에이전트의 실행 환경을 격리한다.
전부 에이전트가 신뢰할 수 없는 코드를 만들거나 실행하므로
그것을 담을 격리된 단위가 필요하다는 같은 원리다.
OpenSandbox는 그 격리 단위를 실행 환경 수준에서 표준화하려는 시도이며,
샌드박스가 예외적 방어에서 기본 인프라로 옮겨 가는 흐름의 한 사례다.

### 프로토콜과 다언어 SDK가 이 프로젝트의 야심을 드러낸다

OpenSandbox가 단순한 샌드박스 도구가 아니라는 신호가
프로토콜과 SDK의 폭에 있다.
샌드박스 수명 주기와 실행을 API로 정의하고,
Python부터 Go까지 다섯 언어 SDK를 제공하며,
Docker와 Kubernetes 런타임을 모두 지원한다.
이것은 도구가 아니라 표준을 만들려는 구조다.

프로토콜을 정의한다는 것이 특히 중요하다.
프로토콜이 있으면 OpenSandbox의 구현에 묶이지 않고,
누구나 그 프로토콜을 따르는 커스텀 런타임을 만들 수 있다.
이것은 특정 제품을 파는 것이 아니라
샌드박스를 다루는 공통 언어를 제안하는 것이다.
MCP 서버 통합도 같은 방향이다.
에이전트가 표준화된 방식으로 샌드박스를 다루게 하려는 것이며,
그 표준의 자리를 OpenSandbox가 차지하려 한다.

이 야심이 다언어 SDK의 이유도 설명한다.
하나의 언어만 지원하면 그 언어 생태계의 도구로 남지만,
다섯 언어를 지원하면 언어를 가로지르는 인프라가 된다.
Alibaba가 이 폭을 감당할 수 있는 것은
그럴 자원이 있기 때문이며,
14,000개가 넘는 스타는 그 야심이 관심을 받고 있다는 증거다.
그러나 프로토콜과 표준을 제안하는 것과
그것이 실제 표준이 되는 것은 다른 문제이며,
그 간극이 뒤에서 다룰 비평의 핵심이다.

### 격리 수준의 선택지가 이 프로젝트의 실용적 깊이를 보여 준다

기능 목록에서 가장 실질적인 부분이 격리 옵션이다.
gVisor, Kata Containers, Firecracker microVM을 지원한다.
이것들은 각각 다른 격리 강도와 성능 교환을 갖는 실제 기술이며,
이 선택지를 제공한다는 것이
이 프로젝트가 마케팅이 아니라 실용을 겨냥한다는 신호다.

이 선택지가 필요한 이유는 격리에 정답이 없기 때문이다.
평범한 컨테이너는 빠르지만 격리가 약해,
커널을 공유하므로 탈출 위험이 있다.
gVisor는 사용자 공간에서 시스템 콜을 가로채 격리를 높이지만 오버헤드가 있고,
Kata와 Firecracker는 경량 VM으로 강한 격리를 주지만 더 무겁다.
에이전트가 도는 코드의 신뢰 수준과
요구되는 성능에 따라 이 중 무엇이 맞는지가 달라진다.
OpenSandbox가 셋을 다 지원한다는 것은
사용자가 그 교환을 스스로 고르게 한다는 뜻이다.

여기에 자격 증명 볼트가 더해지는 것이 눈에 띈다.
실제 비밀을 워크로드에 노출하지 않고
샌드박스의 외부 요청에 주입한다는 것이,
바로 앞 문서에서 본 key-amnesia와 같은 아이디어다.
서로 다른 프로젝트가 독립적으로 같은 결론,
곧 비밀을 실행 환경에서 떼어 놓아야 한다는 결론에 도달한 것이다.
이 수렴이 이 문제가 에이전트 인프라의 공통 과제임을 보여 주며,
OpenSandbox가 그것을 플랫폼 기능으로 통합한 것은
샌드박스와 비밀 관리가 한 계층으로 묶이는 방향을 가리킨다.

### 두 API 레이어의 분리가 구현이 아니라 규격을 겨냥한 것이었음이 확인된다

처음 정리할 때 두 API 레이어 분리는 런타임 교체를 위한 내부 설계로 읽혔다.
지금 README는 그것을 샌드박스 프로토콜이라고 부르고,
라이프사이클 관리 API와 실행 API를 정의해
커스텀 샌드박스 런타임을 확장할 수 있게 한다고 적으며 별도의 API 명세를 둔다.

그 규격 주장의 첫 증명이 강한 격리 항목이다.
gVisor와 Kata Containers와 Firecracker microVM을 지원한다는 것은
격리 수준이 다른 세 런타임 아래에서 같은 API가 유지된다는 뜻이며,
이것이 성립하면 사용자 코드는 격리 강도를 설정으로 고를 수 있게 된다.
Docker에서 Kubernetes로 가는 경로에 이어 두 번째 축이 열린 것이다.

이 방향이 프로젝트의 위치도 정한다.
LangGraph와 Google ADK 연동이 있고 벤더 CLI 실행 예제가 있다는 것은
자기를 에이전트 프레임워크의 경쟁자가 아니라 그 아래 계층으로 규정한다는 뜻이며,
프레임워크가 무엇이든 실행 환경은 하나면 된다는 주장이다.

### Credential Vault가 격리의 문제 정의를 바꾼다

기존 이그레스 제어는 “밖으로 나가지 못하게” 하는 문제였다.
DNS와 nftables 이중 방어가 그 구현이고, 목표는 차단이다.

Credential Vault는 반대 방향의 문제를 다룬다 —
나가게 하되 비밀은 주지 않는 것이다.
에이전트가 실제로 일을 하려면 API 키가 필요하고,
키를 워크로드 안에 넣으면 격리의 의미가 크게 줄어든다.
샌드박스가 아웃바운드 요청에 자격 증명을 대신 주입하면
워크로드는 키를 본 적이 없는 상태로 인증된 요청을 보낼 수 있다.

이 패턴 자체는 새롭지 않다 — 프록시가 대신 서명하는 방식이며
서비스 메시와 API 게이트웨이가 오래 써 온 구조다.
새로운 것은 샌드박스 런타임이 그것을 내장 기능으로 올렸다는 사실이고,
그 선택이 대상 워크로드를 알려 준다.
사람이 쓰는 개발 환경이라면 키를 넣어 주는 것으로 끝나지만,
[에이전트가 위임자의 권한을 넘지 못하게 해야 하는 문제](../business/k-skill-blue-ribbon.md)에서는
키를 주지 않는 것이 유일한 해법이다.

### 9개월에 스타 15,477개가 만든 상태

저장소가 2025년 12월에 만들어졌고 2026년 9월 23일 기준 스타 15,477개에 포크 1,419개,
PR을 포함한 열린 이슈 137개다.
이 범주에서 가장 빠르게 커진 프로젝트 중 하나이며,
그 속도가 기능 목록의 성격을 설명한다.

기능이 축적되는 방향이 넓이 쪽이다 —
런타임 세 종류, SDK 다섯 언어, CLI, MCP, 인그레스, 이그레스, 자격 증명 보관소,
그리고 코딩 에이전트와 브라우저 자동화와 데스크톱 예제다.
좁고 깊은 도구가 아니라 플랫폼을 표방하는 목록이고,
열린 이슈 수가 그 넓이의 유지 비용으로 보인다.


## 비평

### 범용이라는 폭이 어느 용도에도 최적이 아닐 위험

OpenSandbox는 코딩 에이전트부터 RL 훈련까지
아주 넓은 시나리오를 하나의 플랫폼으로 다룬다.
이 폭이 인상적이지만,
동시에 이 프로젝트의 근본적 위험이다.
모든 것을 위한 도구는 대체로 어느 것에도 최적이 아니다.

용도마다 샌드박스에 요구하는 것이 다르기 때문이다.
코딩 에이전트는 빠른 시작과 파일시스템 접근이 중요하고,
GUI 에이전트는 디스플레이와 브라우저 자동화가 중요하고,
RL 훈련은 대규모 병렬 실행과 결정론적 재현이 중요하다.
이 요구들은 서로 충돌하기도 한다.
빠른 시작을 위한 경량 격리와
강한 격리를 위한 무거운 VM이 다른 방향이듯,
범용 플랫폼은 이 충돌하는 요구들 사이에서 타협해야 한다.
그러면 각 용도에 특화된 도구,
예컨대 코드 실행만 파는 E2B 같은 것보다
특정 용도에서 뒤처질 수 있다.

이 위험이 채택에서 드러난다.
특화된 도구는 하나를 아주 잘해서 그 용도의 사용자를 얻는데,
범용 플랫폼은 무엇이든 되지만 무엇도 가장 낫지 않아서
선택의 이유가 약할 수 있다.
14,000개의 스타가 관심을 보이지만,
스타는 채택이 아니라 주목이며,
실제로 프로덕션에서 이 넓은 플랫폼을 쓰는지는 다른 문제다.
범용을 표방하는 인프라 프로젝트가 흔히 겪는 것,
곧 데모는 인상적인데 실제 사용은 특화 도구로 흩어지는 결말을
이 프로젝트가 피할 수 있는지는 폭이 아니라
각 용도의 깊이로 판정되어야 한다.

### Alibaba 배경이 채택의 지정학적 변수를 만든다

OpenSandbox는 오픈소스이고 Apache-2.0이지만,
Alibaba가 뒷받침한다는 사실이 곳곳에 있다.
패키지 이름, 레지스트리, 후원 조직이 그것을 드러낸다.
이 배경은 자원과 신뢰의 근거이자
동시에 채택의 장벽이 된다.

이 장벽이 실질적인 이유는 인프라의 신뢰가
코드만으로 정해지지 않기 때문이다.
샌드박스는 에이전트의 실행 환경을 통제하고
비밀을 다루고 네트워크를 라우팅하는,
보안의 핵심에 있는 계층이다.
그 계층을 특정 대기업이,
특히 지정학적 긴장의 대상인 국가의 대기업이 주도하면,
서방 기업의 일부는 그것을 프로덕션에 쓰기를 주저한다.
코드가 오픈소스여도,
프로젝트의 방향과 우선순위와 장기 지원이
그 회사의 이해에 묶여 있다는 우려가 남는다.

그러면 이 프로젝트의 채택이 기술이 아니라
신뢰의 지리로 갈릴 수 있다.
중국 생태계에서는 자연스럽게 쓰이지만,
서방에서는 E2B나 Daytona 같은 대안을 선호할 수 있다.
CNCF Landscape 등재와 OpenSSF 배지와 Cosign 서명은
그 신뢰를 쌓으려는 노력이지만,
이런 인증이 지정학적 우려를 완전히 해소하지는 못한다.
표준을 지향하는 프로젝트에게 이 분열은 특히 치명적이다.
표준은 널리 쓰여야 표준인데,
지리적으로 분열된 채택은
OpenSandbox가 겨냥하는 보편적 표준의 자리를
얻지 못하게 만들 수 있다.

### 셀프 호스팅 인프라의 운영 부담이 이 플랫폼의 진짜 비용이다

OpenSandbox는 Kubernetes 런타임과 대규모 분산 스케줄링을 내세운다.
이것은 강력하지만,
그 강력함이 곧 운영 부담이다.
gVisor나 Firecracker 같은 보안 런타임을 Kubernetes 위에 올리고,
인그레스 게이트웨이와 이그레스 통제와 자격 증명 볼트를 운영하는 것은
상당한 인프라 전문성을 요구한다.

이 부담이 문제인 이유는 대상 사용자와의 불일치에 있다.
에이전트를 만드는 많은 팀은
인프라가 아니라 에이전트 자체에 집중하고 싶어 한다.
그들에게 샌드박스는 알아서 돌아가야 하는 것이지
Kubernetes 클러스터에서 관리해야 하는 것이 아니다.
그래서 많은 에이전트 팀이
샌드박스를 관리형 서비스로 사는 쪽을 택한다.
OpenSandbox가 셀프 호스팅 오픈소스라는 것은
통제와 비용 절감을 주지만,
그 대가로 운영 부담을 사용자에게 지운다.

그러면 이 프로젝트가 실제로 맞는 사용자가 좁아진다.
자기 인프라를 통제해야 하는 이유가 분명하고,
그것을 운영할 팀이 있는 조직,
곧 대규모로 에이전트를 돌리거나
데이터 주권이 중요한 곳이다.
그 밖의 대다수 팀에게는
관리형 샌드박스 서비스가 더 나은 선택이며,
OpenSandbox의 넓은 기능은
오히려 감당해야 할 복잡성으로 보인다.
오픈소스 셀프 호스팅과 관리형 서비스 사이의 이 교환을
README는 기능의 풍부함으로 그리지만,
사용자에게는 그 풍부함이 운영 비용의 목록이기도 하다.

### 조직 이름은 중립화됐는데 소유의 표시는 그대로 남아 있다

저장소 경로가 `alibaba/OpenSandbox`에서
`opensandbox-group/OpenSandbox`로 옮겨졌다.
새 이름은 회사가 아니라 프로젝트 이름을 딴 중립적 형태이고,
이런 이동은 통상 재단 이관이나 거버넌스 개방의 신호로 읽힌다.

그런데 패키지 좌표는 전부 그대로다.
Maven 그룹 ID가 `com.alibaba.opensandbox`이고
npm 스코프가 `@alibaba-group`이며 NuGet 패키지가 `Alibaba.OpenSandbox`이고,
Go 모듈 경로는 여전히 `github.com/alibaba/OpenSandbox`를 가리킨다.
즉 이동은 저장소 URL에서 일어났고 배포 아티팩트에서는 일어나지 않았다.

이 상태가 중립적이지 않은 이유는 채택 결정에 필요한 정보가 빠져 있기 때문이다.
사용자가 알고 싶은 것은 이름이 아니라 거버넌스다 —
릴리스 권한이 누구에게 있는지, CLA를 요구하는지,
로드맵을 정하는 주체가 회사인지 위원회인지다.
새 조직 이름은 그 질문에 답하지 않으면서 답한 것처럼 보이게 만든다.

GN 댓글의 반응 — 이제 ‘오픈’이라는 단어에 염증을 느낀다는 것[^heim2] — 이
정확히 이 지점을 겨냥한 것으로 읽힌다.
짧은 냉소이지만 근거가 있다.
저장소 어디에도 이 이동이 브랜딩인지 거버넌스 변화인지가 적혀 있지 않고,
패키지 이름은 전자라고 말한다.
한 줄의 설명이면 해소되는 오해이며, 그 한 줄이 없는 것이 선택으로 읽힌다.

### 세 격리 런타임을 한 줄에 나열하고 검증 조합을 밝히지 않는다

강한 격리 항목은 gVisor와 Kata Containers와 Firecracker microVM을 함께 든다.
셋은 격리 방식과 성숙도와 제약이 서로 다르다 —
gVisor는 시스템 콜을 사용자 공간에서 가로채므로
커버리지 밖의 호출에서 문제가 생기고,
Kata는 경량 VM이므로 오버헤드와 커널 관리가 따라오고,
Firecracker는 microVM이라 컨테이너 이미지와 디바이스 호환성이 별도 과제다.

이 프로젝트의 다른 기능들이 그 제약과 정면으로 만난다.
Code Interpreter는 Jupyter 커널을 띄우고,
데스크톱 예제는 VNC와 VS Code Web을 돌리며,
브라우저 자동화 예제는 Chrome과 Playwright를 실행한다.
셋 다 시스템 콜과 디바이스 요구가 큰 워크로드이므로,
“지원한다”가 어느 조합에서 검증됐는지가 실무 질문이 된다.

필요한 것은 런타임과 환경의 교차표 한 개다.
어느 격리 런타임에서 어느 예제가 검증됐고 무엇이 미지원인지를 표로 두면
사용자가 자기 워크로드에 맞는 격리 강도를 고를 수 있다.
지금은 목록만 있어서 선택의 근거가 문서 밖에 있다.

### 범용을 표방하면서 예제가 벤더 CLI의 약관 위에 서 있다

연동 예제에 Claude Code와 Gemini CLI와 Codex CLI 실행이 포함된다.
샌드박스 안에서 벤더 CLI를 돌리는 것은 실용적이고 수요가 분명한 시나리오다.

그런데 그 CLI들은 각자 계정 인증을 요구하고 약관이 다르다.
샌드박스 안에서 어떤 계정으로 로그인할지,
그 계정을 여러 샌드박스가 공유해도 되는지,
자동화된 다수 실행이 각 벤더의 이용 조건에 맞는지가 사용자에게 남는 질문이다.
그리고 Credential Vault가 있으므로 기술적으로는
자격 증명 공유가 아주 쉬워졌다 — 그 편의가 정확히 위험이 되는 자리다.

[한 사람의 구독 권한을 여러 사람의 것으로 바꾼 프록시가
문제가 된 사례](../business/k-skill-blue-ribbon.md)와 같은 구조이며,
차이는 여기서는 그 기능이 제품에 내장되어 있다는 점이다.
예제 문서에 “벤더 계정 자격 증명을 여러 샌드박스에 공유하는 것은
각 벤더 약관의 문제이며 이 예제는 개인 사용을 전제한다”는 한 줄이 있으면
사용자가 조직 단위로 그것을 돌릴 때의 판단이 달라진다.
지금은 편의만 제공되고 경계는 언급되지 않는다.


## 인사이트

### 샌드박스가 에이전트 인프라의 표준 계층으로 상품화되고 있다

OpenSandbox의 등장은 개별 프로젝트의 사건이 아니라
샌드박스가 상품화되는 흐름의 한 지점이다.
불과 얼마 전까지 에이전트의 격리는
각 도구가 자기 방식으로 푸는 문제였는데,
이제 그것을 표준 계층으로 만들려는 프로젝트가
여럿 경쟁하고 있다.
OpenSandbox, E2B, Daytona가 모두 같은 자리를 노린다.

이 상품화의 동력은 격리가 공통 과제가 되었다는 데 있다.
에이전트가 코드를 실행하는 한 격리가 필요하고,
그 격리는 어느 에이전트에나 비슷한 요구를 갖는다.
빠른 시작, 강한 격리, 파일시스템, 네트워크 통제,
비밀 관리가 모든 에이전트에 공통으로 필요하다.
공통된 것은 표준화되고 상품화된다.
각 도구가 따로 만들던 것이
하나의 인프라 계층으로 추출되는 것이며,
이것은 소프트웨어 역사에서 반복된 패턴이다.
웹 서버, 데이터베이스, 컨테이너가 모두
각자 만들던 것에서 표준 계층으로 굳었다.

그러면 이차 효과가 예측된다.
샌드박스가 표준 계층이 되면
에이전트 도구는 그것을 직접 만들 이유가 없어지고,
자기 차별화를 다른 곳,
곧 에이전트의 능력과 사용 경험에 집중하게 된다.
그리고 표준 계층의 자리는 승자 독식에 가까워진다.
가장 널리 쓰이는 샌드박스가
가장 많은 통합과 도구를 얻어 더 널리 쓰이는 것이다.
지금 여러 프로젝트가 그 자리를 두고 경쟁하는 것은
그 자리가 에이전트 인프라의 핵심 병목이 될 것을 알기 때문이며,
OpenSandbox의 넓은 야심도 그 병목을 차지하려는 시도다.

### 격리가 기본값이 되면 신뢰의 단위가 프로세스에서 샌드박스로 바뀐다

OpenSandbox가 여러 격리 런타임을 지원하는 것은
격리가 이제 선택이 아니라 기본이라는 신호다.
에이전트가 도는 모든 것을 격리한다는 전제가
이 플랫폼의 설계에 깔려 있다.
이것은 컴퓨팅의 신뢰 단위가 바뀌는 것을 의미한다.

전통적으로 신뢰의 단위는 프로세스나 사용자였다.
같은 사용자로 도는 프로세스들은 서로 신뢰했고,
격리는 사용자 사이나 기계 사이에 있었다.
그런데 에이전트가 만든 코드는
같은 사용자로 돌아도 신뢰할 수 없다.
그러면 격리의 경계가 사용자보다 아래,
곧 각 에이전트 작업 단위로 내려와야 한다.
샌드박스가 그 새로운 단위다.
작업 하나,
에이전트 세션 하나,
심지어 명령 하나가 자기 샌드박스를 갖는다.

이 변화가 인프라 전반을 재편한다.
격리가 사용자 수준에 있을 때는
샌드박스가 드물고 무거워도 되었지만,
격리가 작업 수준으로 내려오면
샌드박스가 수천 개씩 빠르게 뜨고 사라져야 한다.
OpenSandbox가 고성능 Kubernetes 스케줄링과
경량 격리 런타임을 강조하는 것이 그 요구의 반영이다.
Poke가 작업마다 데이터베이스를 격리한 것과 같은 원리가
실행 환경 전체로 확장되는 것이며,
에이전트 시대의 인프라는
격리를 값싸고 빠르게 대량 생성하는 능력으로 재정의된다.
신뢰의 단위가 작아질수록 그 단위의 생성 비용이 관건이 되고,
그 비용을 낮추는 것이 이런 플랫폼의 진짜 경쟁이다.

### 오픈소스 인프라의 표준 경쟁은 코드가 아니라 생태계와 신뢰로 판가름난다

OpenSandbox는 14,000개가 넘는 스타와
넓은 기능과 다언어 SDK를 갖췄지만,
표준이 되는 것은 이 자산들만으로 정해지지 않는다.
인프라의 표준 경쟁은
가장 좋은 코드가 이기는 것이 아니라
가장 널리 통합되고 가장 신뢰받는 것이 이기기 때문이다.

역사가 이것을 반복해 보여 준다.
기술적으로 더 나은 것이 표준이 된 경우는 드물고,
먼저 자리 잡거나,
더 널리 통합되거나,
중립적으로 신뢰받은 것이 표준이 되었다.
컨테이너 표준이 Docker에서 OCI로 간 것,
쿠버네티스가 경쟁 오케스트레이터를 이긴 것이
전부 코드의 우열이 아니라
생태계와 거버넌스와 중립성의 문제였다.
CNCF 같은 중립 재단이 그 신뢰를 만드는 자리였다.

그러면 OpenSandbox의 진짜 과제가 보인다.
기능을 더 늘리는 것이 아니라,
특정 회사의 프로젝트에서
중립적 표준으로 인식되게 하는 것이다.
CNCF Landscape 등재와 오픈 거버넌스를 향한 움직임이
그 방향의 시작이지만,
Alibaba의 프로젝트라는 인식이 강한 한
서방과 중국으로 갈린 채택을 통합하기 어렵다.
표준은 경계를 넘어야 표준인데,
지정학이 그 경계를 굳히고 있다.
그러면 에이전트 샌드박스의 진짜 표준은
가장 뛰어난 프로젝트가 아니라
가장 중립적으로 신뢰받는 프로젝트가 될 것이며,
그 중립성을 확보하는 것이
코드의 품질보다 이 경쟁의 결과를 더 크게 좌우한다.
OpenSandbox가 기술로는 앞서도 그 신뢰의 지리를 넘지 못하면,
표준의 자리는 더 중립적으로 보이는 대안에게 갈 수 있다.

### 두 API 분리가 만드는 유연성

대부분의 샌드박스 솔루션은 실행 환경과 오케스트레이션을 하나로 묶는다.
OpenSandbox는 이를 분리해서 런타임을 교체해도 코드가 바뀌지 않는다.
Docker에서 시작해 Kubernetes로 확장하는
전형적인 성장 경로를 마찰 없이 지원한다.

### execd 데몬 패턴

컨테이너 내부에 항상 실행 중인 데몬을 둔다.
이 데몬이 외부 API 호출을 받아 명령을 실행하고 결과를 반환한다.
단순하지만 강력하다.
어떤 베이스 이미지도 execd만 포함하면 OpenSandbox 호환 환경이 된다.

### Code Interpreter = Jupyter-as-a-Service

`POST /code`는 Jupyter 커널을 호출하며 SSE(Server-Sent Events)로
실시간 스트리밍한다.
컨텍스트(세션)가 지속되므로 이전 실행의 변수와 상태를 유지한다.
`import numpy as np` 같은 초기화 비용을 한 번만 지불하고
이후 실행에서 재사용한다.
단발성 스크립트 실행이 아닌 대화형 REPL 환경을 API로 노출한 것이다.

### Pause/Resume = 비용 최적화

컨테이너를 종료하지 않고 일시정지하면
재시작 비용(이미지 풀, 의존성 설치)이 없다.
RL 학습처럼 중단점이 필요한 작업에서
Pause → 체크포인트 저장 → Resume 패턴으로 비용을 절감한다.

### MCP가 뒤집는 통합 방향

기존: 에이전트 코드 안에 샌드박스 SDK를 임포트.
MCP: 샌드박스가 도구를 에이전트에 노출.

에이전트가 샌드박스를 소유하는 게 아니라,
샌드박스가 도구로서 에이전트에 등록된다.
에이전트 코드 변경 없이 샌드박스 교체가 가능하다.

### Egress 제어 = 진짜 격리

네트워크 접근을 샌드박스 단위로 제어한다.
AI 에이전트가 임의의 외부 서버와 통신하는 것을 막을 수 있다.
보안 규정이 엄격한 환경(금융, 의료)에서 에이전트를 운용하는 핵심 요건이다.

### 커스텀 헬스 체크 주입

기본 헬스 체크는 execd의 `/ping` 응답 여부만 확인한다.
VS Code Web이나 Playwright처럼 내부 서비스 준비가 필요한 경우
커스텀 함수를 주입해 실제 레디니스를 표현한다.

```python
async def wait_for_vscode(sandbox):
    endpoint = await sandbox.get_endpoint(8443)
    resp = await http_get(endpoint)
    return resp.status_code == 200

await sandbox.check_ready(
    timeout=60,
    health_check=wait_for_vscode
)
```

“컨테이너 실행 중” 이상의 레디니스 개념을 API 수준에서 표현하는 패턴이다.

### 에이전트 샌드박스의 경쟁축이 격리에서 자격 증명으로 이동한다

Credential Vault가 기능 목록에 오른 것은
이 범주의 무게 중심이 옮겨 가는 신호다.
격리 자체는 상품화되는 중이다 — gVisor와 Kata와 Firecracker가 이미 있고,
어느 프로젝트든 그것을 가져다 쓰면 되므로 차별점이 되지 못한다.

남는 문제는 격리된 워크로드가 실제로 일을 하게 만드는 것이다.
에이전트는 저장소에 푸시하고 API를 호출하고 결제를 조회해야 하는데,
그러려면 자격 증명이 필요하고 자격 증명을 넣는 순간 격리의 값이 줄어든다.
이 긴장을 푸는 유일한 방향이 워크로드가 비밀을 보지 못한 채
인증된 요청을 보내게 하는 것이며, 그것이 곧 프록시 계층이다.

여기서 따라오는 2차 효과가 위치의 집중이다.
샌드박스가 자격 증명을 주입하려면 모든 아웃바운드 요청이 그것을 지나야 하고,
그러면 샌드박스는 실행 환경이면서 동시에 네트워크 게이트웨이가 된다.
그 위치는 감사 지점으로서 값이 크지만 —
어느 에이전트가 무엇에 접근했는지가 한곳에 남는다 —
동시에 단일 실패점이며 침해 시 피해 범위가 가장 넓은 지점이다.

그러므로 이 범주를 평가하는 질문이 바뀐다.
얼마나 강하게 격리하는지가 아니라
자격 증명 주입의 범위와 감사 기록과 폐기 절차가 어떻게 되어 있는지이며,
[제어면과 실행면의 소유가 다르면 능력은 제어면에 있다는 관찰](../github/github-is-not-just-git.md)이
여기서도 그대로 적용된다.

### 중립적 조직 이름은 거버넌스의 대리 지표로 쓸 수 없다

기업이 후원하는 오픈소스 프로젝트가
회사 조직에서 중립적 이름의 조직으로 옮기는 일은 늘고 있다.
채택 장벽을 낮추는 알려진 수단이고, 재단 이관의 준비 단계이기도 하다.
문제는 같은 동작이 브랜딩만으로도 가능하다는 것이다.

구별할 수 있는 지표가 몇 개 있고 전부 확인 가능하다.
배포 아티팩트의 이름 공간, 기여자 라이선스 동의 요구 여부,
커밋 작성자 이메일 도메인의 분포, 릴리스 태그를 만들 권한을 가진 계정,
그리고 로드맵과 제안 절차를 누가 승인하는지다.
이 프로젝트의 경우 첫 번째 지표가 이동이 아직 표면적임을 알려 준다.

이것이 흠이라는 뜻은 아니다.
회사가 만들고 회사가 유지하는 프로젝트는 정당하며,
Apache-2.0에 API 명세와 제안서 절차까지 공개한 상태는 오히려 성실한 편이다.
문제는 이름이 주는 인상과 실제 상태가 다를 때 생기는 오해이고,
그 오해를 프로젝트가 아니라 사용자가 부담한다는 점이다.

그러므로 이런 이동을 만나면 이름을 신호로 읽지 않는 습관이 필요하다.
`pip install`과 `go get`에 적히는 문자열이 조직도보다 정확하며,
[저장소 이름과 검색 단위가 발견 가능성을 정한다는 관찰](../architecture/system-design-notes.md)의
반대편에서 같은 원리가 작동한다 — 이름은 값싸게 바꿀 수 있고,
그래서 정보량이 적다.
