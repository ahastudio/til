# Flue — 에이전트 하네스 프레임워크

> Flue — The Open Agent Framework

<https://flueframework.com/>

<https://github.com/withastro/flue>

## 소개

Flue는 Astro 팀(withastro)이 만든 TypeScript 기반 에이전트 하네스 프레임워크다.
“또 하나의 SDK가 아니다(Not another SDK)”라는 슬로건 아래,
자율 에이전트가 실제로 작동하는 데 필요한 환경 전체 — 세션, 도구, 스킬,
지시, 파일시스템 접근, 보안 샌드박스 — 를 제공하는 것을 목표로 한다.

7,000개 이상의 별을 받았으며 코드베이스의 91.1%가 TypeScript로 작성되어 있다.
라이선스는 Apache 2.0이다.

이 문서를 갱신하는 시점의 저장소 상태는 별 7,971개, 포크 468개, 열린 이슈 35개이며
2026년 2월 7일에 만들어졌다.
저장소 설명은 그사이 “샌드박스 에이전트 프레임워크”로 바뀌었고,
홈페이지 상단은 Flue 2.0과 Agent Hooks 발표를 알린다.

하네스를 직접 만들지 않았다는 점도 첫 화면에 적혀 있다.
Flue는 Pi가 구동하며, Pi는 OpenClaw가 쓰고 전 세계에서 쓰이는
믿을 수 있는 에이전트 하네스라고 소개한다.
Pi를 중심으로 Durable Streams와 Vite와 유연한 샌드박스 API가
하나의 열린 기술 묶음을 이룬다고 설명한다.

## 주요 기능

### 에이전트와 워크플로

1.0에서 에이전트는 `defineAgent` 함수로 정의했다.
모델, 도구 배열, 스킬, 샌드박스 설정, 지시를 명세하면
프레임워크가 세션과 컨텍스트를 관리하며 자율 실행을 이어갔다.
워크플로는 `defineWorkflow()`로 기술하는 별도의 구조였다.

2.0에서 이 두 API가 모두 없어졌다.
에이전트는 훅을 호출하고 지시문을 반환하는 평범한 함수가 되었고,
워크플로는 에이전트를 실행하는 아무 스크립트를 뜻하게 되었다.
자세한 내용은 아래 Flue 2.0 절에 있다.

### 샌드박스와 내구성 실행(Durable Execution)

에이전트는 로컬, 가상, 원격 컨테이너 중 하나의 샌드박스에서 도구를 실행하고
파일을 수정한다.
내구성 실행은 장애나 재시작이 발생해도 진행 상태를 보존하므로
장시간 실행 작업에서 처음부터 다시 시작하지 않아도 된다.

### 스킬과 도구

스킬은 마크다운 파일로 패키징된 재사용 가능한 전문성이다.
에이전트가 실행 시점에 동적으로 불러오며,
도메인 특화 지식이나 행동 지침을 코드와 분리해 관리할 수 있다.
도구는 타입 안전한 API 호출 및 제어된 애플리케이션 변경을 정의한다.

### 서브에이전트와 채널

서브에이전트는 상위 에이전트로부터 위임받은 특정 역할을 수행하며,
복잡한 작업을 전문화된 단위로 분해할 수 있다.
채널은 Slack, Teams, Discord, GitHub에서 검증된 이벤트를 수신하는 통합 지점이다.

### 관측성과 배포

OpenTelemetry, Braintrust, Sentry를 통한 텔레메트리를 지원한다.
배포 타깃은 Node.js, Cloudflare Workers, GitHub Actions,
GitLab CI/CD, Daytona, Render다.

## Flue 2.0과 Agent Hooks

2.0의 발표문은 프레임워크를 훅 기반 API로 다시 만들었다고 적는다.
훅은 에이전트가 자기 상태를 관리하고 수명 주기 이벤트를 듣고
실행 시점에 자원과 능력을 붙여 스스로를 강화하게 만드는 토대다.

같은 에이전트를 두 API로 쓴 예가 발표문에 나란히 있다.
1.0에서는 모델과 도구와 스킬과 샌드박스와 지시를 객체로 넘겼고,
2.0에서는 `useModel()`과 `useTool()`과 `useSkill()`과 `useSandbox()`를 호출하고
지시문을 문자열로 반환한다.

동기는 자기 API의 실패에서 나왔다고 적는다.
1.0 베타를 실제 개발자들과 함께 써 봤더니
정적 에이전트 방식이 단순한 용도에서는 잘 동작했지만
복잡한 에이전트와 다단계 워크플로에서 무너졌다는 것이다.
그리고 그 문제가 OpenAI SDK와 Anthropic SDK와 Cursor SDK와 Eve와 Mastra를 비롯한
다른 프레임워크에도 있을 것이라고 덧붙인다.

2.0에 담긴 것은 내장 훅 16개, 사용자 정의 훅,
터미널과 CI에서 `flue run`으로 도는 새 CLI,
호스팅 에이전트를 Vite로 직접 빌드하는 새 구조,
내장 상태 없는 MCP, 그리고 200개 이상의 수정이다.
발표문은 이것이 첫 안정 릴리스라고 적는다.

동적 에이전트의 예로 두 가지가 제시된다.
하나는 스스로를 승격시키는 에이전트다 —
`usePersistentState`로 강화 여부를 저장하고
`enhance`라는 도구를 주어 에이전트가 그 값을 켤 수 있게 하고,
켜지면 더 큰 모델과 원격 샌드박스와 추가 도구를 붙인다.
다른 하나는 상태 기계 형태의 워크플로다 —
현재 단계를 지속 상태에 두고
`reproduce`·`diagnose`·`report` 각 단계마다 다른 모델과 스킬과 도구를 붙이며,
각 단계의 도구가 다음 단계로 넘긴다.

사용자 정의 훅은 npm으로 공유할 수 있다.
`useLinear(apiKey)`가 `useMcpConnection`을 감싸는 예가 제시되고,
그것을 `useGitHub`와 `useBrowser`와 함께 호출하는 에이전트가 이어진다.

주변 변경이 이 릴리스의 성격을 더 잘 보여 준다.
`flue dev`와 `flue build`가 없어졌고
Flue 앱은 `vite.config.ts`에 `flue()` 플러그인을 넣은 평범한 Vite 프로젝트이며,
`app.ts`의 Hono 앱이 에이전트 경로를 명시적으로 마운트한다.
`defineWorkflow()`는 내구성이 그것을 불필요하게 만들었기 때문에 없어졌다 —
에이전트가 받은 모든 메시지가 크래시와 재시작과 재배포를 거쳐
정확히 한 번 정산되므로 별도 워크플로 개념이 필요 없다는 설명이다.
에이전트 안에서 체크포인트가 필요한 부작용은
도구가 `durable: true`를 선택하고 `step.do()`로 진행을 기록한다.

SDK는 대화 단위로 좁아졌다.
대화마다 URL이 있고 `@flue/sdk` 클라이언트가 그중 하나를 감싸며
`send()`·`read()`·`observe()`·`abort()`를 제공한다.
메시지에 `purpose`와 `display` 메타데이터가 붙어서
클라이언트가 사용자 대화와 내부 활동을 구분할 수 있다.
프런트엔드에서는 `@flue/react`의 `useFlueAgent({ url })`이 같은 대화를 스트리밍한다.

Cloudflare에 배포하면 Workers Traces를 켜는 것만으로
대화 내용과 메타데이터와 토큰 비용이 계측 코드 없이 추적된다.

## 분석

### “SDK가 아닌 하네스”라는 포지셔닝의 의미

Flue가 스스로를 “SDK가 아닌 하네스”로 규정하는 것은 단순한 마케팅 문구가 아니다.
이 구분은 에이전트 프레임워크 시장의 현재 분열을 정확히 짚는다.
LangChain, CrewAI, AutoGPT 등 대부분의 기존 프레임워크는 LLM API 호출을
추상화하고 체인과 파이프라인을 구성하는 SDK로 출발했다.
에이전트가 실제로 작업하는 환경 — 세션 상태, 파일시스템, 샌드박스, 이벤트 채널 —
은 사용자가 직접 구성해야 했다.

Flue는 그 환경 자체를 프레임워크의 핵심으로 가져온다.
[하네스 엔지니어링](./harness-engineering.md)이 개념으로 제시한
“에이전트가 아니라 에이전트를 둘러싼 시스템이 성패를 결정한다”는 명제를
프레임워크 수준에서 구현하려는 시도다.

### 스킬의 마크다운 패키징이 갖는 구조적 함의

스킬을 마크다운 파일로 패키징하는 설계는 표면적으로는 단순해 보이지만
깊은 아키텍처적 판단을 담고 있다.
코드가 아닌 텍스트로 전문성을 표현함으로써,
스킬이 에이전트 프레임워크에 종속되지 않고 모델과 직접 소통하는 구조가 된다.
프레임워크가 교체되어도 스킬은 재사용 가능하며,
도메인 전문가가 코드 없이 에이전트 행동을 정의할 수 있다.

이 패턴은 이미 Claude Code의 CLAUDE.md, Codex의 AGENTS.md,
그리고 이 TIL 저장소의 `.claude/skills/` 구조에서 검증되고 있다.
Flue는 이 패턴을 프레임워크 수준의 공식 추상화로 격상시킨다.

### Withastro의 선택이 신호하는 것

Astro는 웹 프레임워크로 알려진 팀이다.
아일랜드 아키텍처(Islands Architecture), 정적 사이트 생성, 멀티프레임워크 컴포넌트 지원으로
프론트엔드 개발자 생태계에서 신뢰를 쌓았다.
그 팀이 에이전트 하네스 프레임워크를 만든다는 것은 하나의 신호다.

웹 프레임워크 팀이 공통으로 직면하는 문제 — 배포 환경 추상화,
빌드 도구 통합, 개발자 경험 — 는 에이전트 하네스가 해결해야 할 문제와 구조적으로 닮아 있다.
Cloudflare Workers와 Node.js 양쪽에 동일한 에이전트를 배포하는 문제는
동일한 컴포넌트를 React, Svelte, Vue에서 동작시키는 문제와 같은 층위의 도전이다.
이 팀의 진입이 다른 AI 네이티브 스타트업과 다른 각도의 해법을 가져올 가능성이 있다.

### 내구성 실행이 에이전트 신뢰성의 핵심이 되는 이유

내구성 실행(Durable Execution)은 Temporal과 Cloudflare Durable Objects가
분산 시스템에서 확립한 패턴이다.
이 패턴이 에이전트 하네스에서 특히 중요한 이유는
에이전트 작업의 특성 때문이다.

파일 수정, API 호출, 서브에이전트 위임이 복잡하게 얽힌 장시간 작업에서
중간 실패는 불가피하다.
내구성 실행 없이는 실패 지점부터 재시작하는 것이 아니라 처음부터 다시 시작해야 하며,
이 과정에서 부수 효과(side effect)가 중복 실행될 위험이 있다.
Flue가 이를 프레임워크 수준에서 제공한다는 것은 에이전트의 신뢰성을
애플리케이션 코드가 아닌 인프라가 보장한다는 의미다.

### 프레임워크가 자기 표면을 지우는 방향으로 갔다

2.0의 변경 목록을 기능 추가로 읽으면 요점을 놓친다.
`flue dev`와 `flue build`가 없어졌고 `defineWorkflow()`가 없어졌으며
빌드는 Vite가, 라우팅은 Hono가, 모델 제공자는 Pi가 갖는다.
발표문 자신이 그것을 이 릴리스의 주제로 정리한다 —
생태계에 더 나은 것이 이미 있는 곳에서는 Flue가 자기 표면을 지운다는 것이다.

이 방향은 에이전트 프레임워크의 통상적 경로와 반대다.
이 범주의 프레임워크들은 대체로 표면을 늘리는 쪽으로 갔다.
자기 CLI와 자기 빌드와 자기 서버와 자기 관측성을 갖추고
그 전체를 하나의 제품으로 판다.
그렇게 하면 시작이 쉬워지지만 탈출이 어려워지고,
프레임워크가 유행을 잃을 때 그 안의 코드가 함께 묶여 있게 된다.

표면을 지우는 선택의 값은 대체 가능성에 있다.
Vite 프로젝트에 플러그인이 하나 붙어 있는 형태라면
빌드 문제는 Vite 생태계의 문제로 환원되고,
Hono 앱이 경로를 명시적으로 마운트한다면
그 앱은 Flue와 무관한 엔드포인트도 함께 가질 수 있다.
이 문서의 마지막 절에서 다루는 관찰 — 프레임워크가 사라져도 스킬은 남는다는 것 — 이
코드 층까지 확장된 형태다.

다만 이 선택에는 대가가 있다.
2.0으로 올라가는 사용자는 프레임워크 API만 바꾸는 것이 아니라
빌드 도구와 서버 프레임워크의 개념을 새로 알아야 한다.
`flue dev` 한 줄이면 됐던 것이
`vite.config.ts`와 `app.ts`와 플러그인 등록으로 늘어났고,
그것이 첫 안정 릴리스에서 함께 일어났다.

### React 훅에서 가져온 것은 모양이고 규칙은 가져오지 않았다

발표문은 영감을 숨기지 않는다.
지난주에 “에이전트를 위한 React라면?”이라고 농담처럼 던졌다고 적고,
React Hooks가 풀려고 만든 문제 — 가장 낮고 근본적인 수준에서
기능을 어떻게 합성하는가 — 가 에이전트에도 그대로 적용된다고 설명한다.

합성이라는 목표는 실제로 이식된다.
`useLinear`가 `useMcpConnection`을 감싸고
`useGitHub`와 `useBrowser`와 나란히 호출되는 예는
React의 사용자 정의 훅과 형태가 같고,
npm으로 공유한다는 계획도 같다.

그런데 결정적인 부분이 다르다.
React에서 훅은 조건문이나 반복문 안에서 호출할 수 없다.
호출 순서로 상태를 식별하기 때문이며,
그것이 훅 규칙이라는 이름으로 강제되고 린트 규칙으로 검사된다.
Flue 2.0의 대표 예제는 정확히 그 금지를 한다 —
`if (isEnhanced)` 안에서 `useModel`과 `useSandbox`와 `useTool`을 호출하고,
`if (step === 'reproduce')` 안에서 `useSkill`과 `useTool`을 호출한다.

이 차이는 버그가 아니라 설계다.
Flue의 훅에서 조건부 호출은 금지가 아니라 핵심 기능이며,
단계에 따라 다른 능력을 붙이는 것이 동적 에이전트의 정의다.
그것을 가능하게 하려면 상태 식별을 호출 순서가 아니라
`usePersistentState('step', ...)`처럼 키로 해야 하고,
실제로 그 API가 키를 받는다.

문제는 이 차이가 문서에서 강조되지 않는다는 점이다.
“익숙한 API”라는 표현으로 소개하면
읽는 사람은 자기가 아는 규칙을 함께 가져온다.
그리고 이 경우 가져온 규칙이 틀렸다는 것을 알려 주는 것은
린트 오류가 아니라 예제 코드뿐이다.

## 비평

### “SDK가 아니다”는 주장이 SDK인 것을 감춘다

Flue는 스스로를 “하네스”로 규정하며 SDK와 선을 긋지만,
`defineAgent`, `@flue/runtime`, `@flue/sdk`라는 명칭들은
이 프레임워크가 여전히 SDK 계층임을 드러낸다.
샌드박스와 세션 관리가 내장된다는 점에서 기존 SDK보다 두텁기는 하지만,
사용자 입장에서는 결국 패키지를 설치하고, API를 호출하며, 추상화에 의존한다.

“하네스”와 “SDK”를 가르는 기준이 무엇인지 문서는 명확히 하지 않는다.
포지셔닝 자체가 마케팅 언어인지 아키텍처적 구분인지 불분명한 상태에서,
이 주장은 경쟁 프레임워크들과 달리 보이고 싶은 욕구의 표현에 더 가깝다.

### 스킬의 마크다운 설계가 규모 확장에서 갖는 문제

스킬을 마크다운으로 관리하는 설계는 소규모에서 우아하지만,
수십, 수백 개의 스킬이 쌓이는 환경에서 취약점이 생긴다.
스킬 간 충돌을 어떻게 감지하는가, 스킬의 버전 관리는 어떻게 하는가,
모순되는 지시를 담은 두 스킬을 동시에 로드하면 에이전트 행동이 어떻게 결정되는가.

타입 시스템으로 잡을 수 없는 텍스트 기반 계약의 한계다.
코드에서는 컴파일러가 인터페이스 충돌을 잡아주지만,
마크다운 스킬 간의 의미론적 충돌을 잡아주는 장치가 없다.
이 문제를 어떻게 해결할 것인지에 대한 설계가 공개되지 않은 상태다.

### 관측성 지원이 표면적 통합에 그칠 위험

OpenTelemetry, Braintrust, Sentry를 지원한다는 것은 강점으로 나열되어 있지만,
에이전트 시스템의 관측성은 웹 서비스의 관측성과 본질적으로 다르다.
요청-응답 추적은 잘 작동하지만, 에이전트가 왜 그 결정을 내렸는가,
어떤 스킬이 어떤 행동에 영향을 미쳤는가, 실패의 근본 원인이
모델 때문인지 하네스 설정 때문인지를 구분하는 것은
표준 텔레메트리 도구가 설계된 문제가 아니다.

`@flue/opentelemetry`가 이 간극을 어떻게 메우는지는 공개된 정보로 확인하기 어렵다.
기존 관측성 도구를 “지원”한다는 것이 에이전트 특유의 가시성을 제공한다는 의미인지,
아니면 단순히 스팬(span)을 내보낸다는 의미인지 명확하지 않다.

### Withastro의 AI 에이전트 영역 신뢰성은 아직 검증 전이다

Astro 팀이 웹 프레임워크에서 쌓은 신뢰는 에이전트 하네스 도메인으로
자동 이전되지 않는다.
웹 프레임워크의 경쟁 우위 — 빌드 속도, 정적 생성, 하이드레이션 전략 —
는 에이전트 하네스의 핵심 문제 — 모델 통합의 깊이, 샌드박스 보안, 내구성 실행의 신뢰성 —
와 겹치는 부분이 적다.
7,000개의 별은 기대의 크기를 보여주지만,
프로덕션 에이전트 시스템을 실제로 운영한 사례가 공개되기 전까지는
이 프레임워크의 실전 신뢰성은 미지수다.

### 첫 안정 릴리스가 이전 API를 폐기하면서 나왔다

발표문은 2.0을 첫 안정 릴리스라고 부른다.
같은 문서가 1.0 API의 `defineAgent`와 `defineWorkflow`가 없어졌고
`flue dev`와 `flue build`도 없어졌다고 적으며,
기존 프로젝트를 올리려면 마이그레이션 가이드를 보라고 안내한다.

이 조합이 이례적이다.
안정 릴리스라는 표현은 통상 API가 굳었다는 선언인데,
여기서는 API를 바꾼 릴리스에 그 이름이 붙었다.
1.0을 베타로 재분류하는 방식으로 정합성을 맞췄지만 —
발표문이 그것을 “Flue 1.0 베타”로 부른다 —
1.0이라는 번호를 붙여 배포한 것을 나중에 베타로 부르는 것은
사용자가 그 번호를 보고 한 판단을 사후에 무효로 만드는 일이다.

깨는 변경을 지금 하기로 한 판단 자체는 옹호할 수 있다.
발표문의 논리는 명확하다 — 아직 이르므로 지금이 적기라는 것이다.
정적 에이전트의 한계를 실사용에서 확인했고,
같은 문제가 다른 프레임워크에도 있을 것이라고 봤으며,
그렇다면 늦게 고치는 비용이 더 크다.
이 판단은 합리적이고 오히려 정직하다.

그러나 그 정직함이 버전 이름에서는 유지되지 않는다.
정확한 서술은 2.0이 첫 안정 API라는 것이고,
그러면 1.0 사용자에게 무엇이 깨지는지가 먼저 와야 한다.
지금 발표문의 순서는 새 API의 매력이 먼저이고
마이그레이션 가이드 링크가 한 줄로 뒤에 있다.
프레임워크의 신뢰는 기능이 아니라 이런 순서에서 쌓인다.

### 하네스를 남의 것으로 쓰면서 프레임워크의 차별점을 하네스에서 찾는다

첫 화면의 두 번째 절은 이 프레임워크가 Pi로 구동된다는 선언이다.
Pi가 진짜 에이전트 자율성을 열어 주는 도구를 제공하며
단순한 챗봇을 넘어서게 한다고 적고,
Pi가 모델 제공자를 소유한다고 2.0 발표문이 명시한다.

그런데 이 문서의 앞부분이 정리한 이 프레임워크의 포지셔닝은
SDK가 아니라 하네스라는 것이었다.
하네스를 남의 것으로 쓰면서 하네스라는 이름으로 자기를 규정하면
차별점의 위치가 모호해진다.
Pi 위에 무엇을 얹었는지가 답이어야 하고,
2.0에서 그 답은 훅 API와 내구성 실행과 배포 통합인데
첫 화면은 여전히 하네스라는 단어를 앞세운다.

이 모호함이 실질적 문제가 되는 이유는 선택의 대안 때문이다.
Pi를 직접 쓰는 것도 가능하고,
Pi가 OpenClaw에서 쓰이고 있다면 그쪽 사용 예도 참고할 수 있다.
그렇다면 구매자가 물어야 할 질문은
Flue와 다른 프레임워크의 차이가 아니라
Flue와 Pi 직접 사용의 차이이며,
그 비교가 사이트에 없다.

의존의 방향도 확인해 둘 만하다.
Pi가 만들어 배포하는 TUI 패키지는 다른 프로젝트들도 쓰고 있고,
[Kimi Code CLI의 TUI](../ai-tool/kimi-code.md)가 같은 뿌리를 인용한다.
같은 하부 계층 위에 여러 상부 제품이 올라가는 구도이며,
그 구도에서 상부 제품의 차별점은 시간이 갈수록
하부 계층이 하지 않기로 한 일에 국한된다.
Pi가 훅 같은 합성 API를 직접 제공하기로 하면
이 프레임워크의 가장 큰 차별점이 하루아침에 사라진다.

## 인사이트

### 에이전트 프레임워크 전쟁의 새로운 전선

에이전트 프레임워크 경쟁은 지금까지 AI 네이티브 스타트업들 사이에서 벌어졌다.
LangChain, CrewAI, AutoGPT — 모두 LLM 등장 이후 만들어진 조직들이다.
Flue는 이 경쟁에 기존 개발 도구 생태계가 진입하는 것을 상징한다.

이 전환의 의미는 크다.
기존 도구 생태계는 개발자 경험, 빌드 시스템 통합, 배포 파이프라인에서
AI 네이티브 스타트업보다 수년의 노하우를 갖고 있다.
에이전트가 프로덕션 시스템에 통합되는 단계로 넘어갈수록,
이 노하우의 가치는 모델 추상화 능력보다 더 크게 작용할 수 있다.
Withastro의 진입은 이 전환의 신호탄일 수 있다.

### 스킬 마켓플레이스가 다음 경쟁 축이 될 것이다

마크다운 기반 스킬 설계가 성숙하면, 자연스럽게 스킬 공유와 재사용 생태계가 형성된다.
npm이 JavaScript 모듈의, Homebrew가 macOS 도구의 공유 생태계를 만든 것처럼,
에이전트 스킬의 공유 생태계가 등장할 조건이 마련되고 있다.

이 생태계에서 경쟁 우위는 특정 프레임워크를 채택하게 만드는 가장 강력한 유인 중 하나가 된다.
“X 서비스를 위한 스킬 패키지”가 Flue 생태계에서만 작동한다면,
그 스킬들이 사용자를 묶어두는 락인(lock-in) 메커니즘이 된다.
마크다운이 이식성을 높인다는 장점을 가지면서도,
실제로 성숙한 생태계에서는 프레임워크 특화 관례가 쌓이며 이식성을 침식할 것이다.

### Cloudflare Workers 타깃이 에이전트 아키텍처를 바꾼다

Flue가 Cloudflare Workers를 일급 배포 타깃으로 지원한다는 사실은
에지(edge) 컴퓨팅과 에이전트의 결합이 진지하게 고려되고 있음을 시사한다.

전통적인 에이전트 배포는 중앙화된 서버를 전제했다.
에지에서 동작하는 에이전트는 다른 제약과 가능성을 갖는다.
레이턴시가 낮아지고 데이터가 처리되는 위치가 사용자와 가까워지지만,
상태 관리와 내구성 실행의 구현이 훨씬 복잡해진다.
Cloudflare Durable Objects가 이 문제를 해결하는 인프라를 제공하며,
Flue가 이를 프레임워크 수준에서 추상화하려 한다면
에이전트 인프라의 지형을 바꿀 수 있는 조합이다.

### 프레임워크가 사라지면 스킬은 살아남는다

에이전트 프레임워크 생태계는 아직 초기다.
오늘의 선두 주자가 2년 후에도 선두인 보장이 없다.
이 불확실성에서 스킬의 마크다운 기반 설계는 역설적인 보험이 된다.

Flue가 경쟁에서 패하더라도, 마크다운으로 작성된 스킬 라이브러리는
다른 프레임워크로 이식될 수 있다.
CLAUDE.md와 AGENTS.md가 특정 AI 모델에 종속되지 않듯이,
텍스트로 표현된 전문성은 프레임워크 교체 비용을 낮춘다.
이것은 프레임워크가 아닌 스킬에 투자하는 것이
장기적으로 더 안전한 선택일 수 있음을 의미한다.
오늘 Flue를 선택하더라도, 진짜 자산은 Flue 코드가 아닌 마크다운 스킬들이다.

### 에이전트가 자기 능력을 바꿀 수 있으면 비용과 권한의 상한이 코드에서 사라진다

2.0의 대표 예제는 스스로를 승격시키는 에이전트다.
`enhance`라는 도구를 갖고 있고 그것을 호출하면
지속 상태가 켜지면서 더 큰 모델과 원격 샌드박스와 추가 도구가 붙는다.
발표문은 이것을 고객이 인증되면 새 도구를 얻고
일이 어려워지면 더 큰 모델로 올라가는 예로 설명한다.

이 설계가 실제로 편리한 이유는 분명하다.
정적 정의에서는 최악의 경우를 기준으로 모델과 샌드박스를 골라야 하므로
쉬운 대화에도 비싼 모델이 붙는다.
동적으로 올릴 수 있으면 평소에는 싼 모델을 쓰고
필요할 때만 비싼 쪽으로 간다.
비용 구조가 사용량에 맞게 굽는다.

그런데 승격의 방아쇠를 에이전트 자신이 갖고 있다는 점이 남는다.
`enhance`는 도구이고 도구는 모델이 호출한다.
그러면 어떤 대화가 비싼 모델로 올라가는지를 결정하는 것은
사람의 정책이 아니라 모델의 판단이며,
그 판단은 비결정적이고 프롬프트로 유도될 수 있다.
샌드박스가 로컬에서 원격 컨테이너로 바뀌는 승격이라면
비용뿐 아니라 실행 경계도 함께 움직인다.

이 문제는 새로운 것이 아니고 이미 알려진 형태를 갖는다.
권한 상승을 요청할 수 있는 프로세스에게
그 요청의 승인 기준을 함께 주면 안 된다는 것이 오래된 원칙이며,
그래서 운영체제는 권한 상승을 커널이 판정한다.
훅 API는 그 판정을 에이전트 함수 안에 두었고,
`if (isEnhanced)` 한 줄이 정책 지점이 된다.

그러므로 이 API를 쓰는 팀이 먼저 만들어야 하는 것은 훅이 아니라 한도다.
승격 도구에 사람의 승인을 요구하는 경로,
대화별 누적 비용의 상한,
그리고 승격이 일어난 횟수를 세는 계측이며,
셋 다 훅으로 표현할 수 있지만 기본값으로 제공되지는 않는다.
프레임워크가 능력의 동적 부착을 일급 기능으로 만들었다면
그 능력의 한도도 일급 기능이어야 하고,
지금은 전자만 있다.
