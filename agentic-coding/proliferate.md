# Proliferate: 여러 코딩 에이전트를 워크트리 단위로 병렬 실행하는 오픈소스 IDE

> Proliferate | Run a team of coding agents

<https://proliferate.com/>

<https://proliferate.com/docs>

<https://github.com/proliferate-ai/proliferate>

HN 토론: <https://news.ycombinator.com/item?id=49390739> (46점, 16개 댓글)

## 소개

Proliferate는 “오픈소스 AI IDE”를 표방하는 macOS 데스크톱 애플리케이션이다.
저장소 설명은 “Claude Code, Codex, OpenCode 등을 위한 오픈소스 AI IDE.
에이전트를 로컬이나 클라우드에서 병렬로 실행하고 재사용 가능한 워크플로를 만든다”이다.
TypeScript가 주 언어이고 라이선스는 AGPL-3.0이며,
2026년 4월 30일에 만들어져 확인 시점 기준 별 478개, 포크 78개다.

README의 한 줄 요약은 이렇다 —
Claude Code, Codex, OpenCode, Grok, 그 밖의 어떤 코딩 에이전트든
하나의 워크스페이스에서 병렬로 실행하며,
각 작업(task)은 자기 브랜치, 터미널, 대화, 리뷰 상태를 담을
격리된 git 워크트리를 받는다.

### 기능

README가 제시하는 기능은 여섯 가지다.

네이티브 하네스(Native harnesses)는 Claude Code, Codex, OpenCode, Cursor, Grok 등을
각자의 고유 하네스를 통해 실행한다는 것이다.
워크트리 워크스페이스는 모든 작업마다 격리된 브랜치와 작업 디렉터리를 둔다.
병렬 에이전트는 같은 워크스페이스 안에서 에이전트를 나란히 돌리되
각자 자기 작업을 맡게 한다.
서브에이전트는 에이전트가 범위가 정해진 일을 자식 에이전트에게 위임하고
끝나면 결과를 다시 받아 오는 구조다.
통합(Integrations)은 MCP, 스킬, Computer Use, Browser Use, 커스텀 도구를
한 번 설정해 모든 에이전트가 공유하게 한다.
워크플로는 반복 실행과 이벤트 기반 실행을 다루며,
예시로 야간 리뷰 패스, 알림 발생 시 분류, 의존성 업데이트가 제시된다.

지원 에이전트 표에는 Claude, Codex, OpenCode, Cursor, Grok 다섯이 아이콘과 함께 실려 있고,
“Proliferate는 각 에이전트를 그 네이티브 하네스를 통해 실행한다”는 문장이 붙는다.

### 셀프 호스팅과 개발 환경

Proliferate 컨트롤 플레인 전체가 셀프 호스팅 가능하다고 명시한다.
배포 문서가 Docker, AWS, GCP, Azure, 쿠버네티스, 그리고 에어갭 운영을 다룬다.
Docker Compose 경로는 Caddy, Postgres, API를 부트스트랩·업데이트 스크립트와 함께 띄우고,
AWS 원클릭 경로는 EC2에 스택을 프로비저닝하는 CloudFormation 래퍼다.
설정 항목은 `server/deploy/.env.production.example`에 필수·선택 항목이 모두 문서화돼 있다고 한다.
데스크톱 앱은 별도 문서를 따라 자기 컨트롤 플레인을 바라보게 설정한다.

소스에서 실행하려면 Rust stable, Node.js 22 이상, pnpm이 필요하다.
번들된 로컬 AnyHarness 런타임으로 데스크톱 앱을 돌리는 명령은
`make install`과 `make dev-local`이다.
로컬 풀스택 개발에는 Python 3.12 이상, `uv`,
그리고 로컬 컨트롤 플레인 데이터베이스를 위한 Docker가 추가로 필요하다.
여러 워크트리를 동시에 돌릴 때는 이름 붙은 dev 프로파일을 쓰라고 안내하며,
`make server-install`, `make setup PROFILE=main`, `make build`,
`make dev-list`, `make run PROFILE=main` 순서를 제시한다.

커뮤니티는 Discord이고, 기여 안내는 `CONTRIBUTING.md`,
취약점 신고는 `SECURITY.md`로 연결된다.

## 분석

### 워크트리를 단위로 삼은 것이 이 프로젝트의 실질적 설계 결정이다

README에서 가장 구체적인 문장은 기능 목록이 아니라
“각 작업은 자기 브랜치, 터미널, 대화, 리뷰 상태를 담을 격리된 git 워크트리를 받는다”이다.
이 한 문장이 나머지 기능들의 전제를 정한다.

에이전트를 병렬로 돌릴 때 가장 먼저 부딪히는 문제는 파일 시스템 충돌이다.
두 에이전트가 같은 작업 디렉터리에서 동시에 편집하면
서로의 변경을 덮어쓰거나, 테스트가 다른 에이전트의 중간 상태를 읽거나,
빌드 산출물이 섞인다.
이 문제의 해법은 몇 가지가 있는데 —
컨테이너로 격리하거나, 저장소를 복제하거나, 순차 실행으로 회피하거나 —
git 워크트리는 그중 가장 가벼운 선택이다.
`.git` 디렉터리를 공유하면서 작업 디렉터리만 분리하므로
복제보다 디스크와 시간이 적게 들고, 컨테이너보다 도구 체인 설정이 단순하다.

동시에 이 선택은 제약도 함께 들여온다.
워크트리는 같은 머신의 같은 파일 시스템을 공유하므로
포트 충돌, 전역 캐시 경합, `node_modules` 재설치 비용이 그대로 남는다.
README가 “여러 워크트리가 동시에 돌 때는 이름 붙은 dev 프로파일을 쓰라”고
자기 개발 환경에 대해 안내하는 것이 그 증거다.
자기 프로젝트를 개발하면서 겪은 문제를 해결한 장치가 문서에 남아 있는데,
그 문제는 이 도구의 사용자도 똑같이 겪을 문제다.

### 하네스를 대체하지 않고 감싸겠다는 선택이 경쟁 구도를 정한다

“각 에이전트를 그 네이티브 하네스를 통해 실행한다”는 문장은
이 프로젝트가 무엇을 하지 않는지를 선언한다.
Claude Code의 프롬프트 처리나 Codex의 도구 호출을 자기 방식으로 다시 구현하지 않고,
공식 CLI나 런타임을 그대로 띄운 뒤 그 바깥을 관리한다는 것이다.

이 결정의 이점은 명확하다.
각 하네스가 업데이트되면 그 개선이 자동으로 따라오고,
벤더가 모델을 바꾸거나 도구를 추가해도 어댑터를 다시 쓸 필요가 없으며,
“내 Claude Code 설정 그대로”라는 신뢰를 준다.
에이전트 CLI가 빠르게 바뀌는 지금 시점에서
재구현을 택한 프로젝트가 유지보수 부담으로 무너지는 일은 흔하다.

비용은 통제력이다.
하네스를 감싸기만 하면 내부 상태에 접근할 수 없으므로
토큰 사용량 집계, 중간 단계 개입, 실패 지점의 정밀한 진단이 제한된다.
그리고 하네스마다 대화 형식, 세션 저장 방식, 승인 모델이 다르므로
“모든 에이전트가 공유하는 통합”이라는 약속을 지키려면
결국 각 하네스에 대한 개별 대응이 필요해진다.
README가 MCP, 스킬, Computer Use, Browser Use를
“한 번 설정해 모든 에이전트가 공유”한다고 적은 부분이
가장 검증이 필요한 대목인 이유가 여기 있다 —
이 도구들의 지원 여부와 방식은 하네스마다 다르다.

### 셀프 호스팅 분량이 이 프로젝트의 실제 판매 대상을 드러낸다

README에서 기능 목록은 여섯 줄인데 셀프 호스팅 절은 그보다 길다.
Docker, AWS, GCP, Azure, 쿠버네티스, 에어갭 운영이 나열되고,
CloudFormation 래퍼와 환경 변수 예제 파일 경로까지 적힌다.
개인 개발자용 도구의 README에 들어가는 분량이 아니다.

이 배치는 대상 고객이 기업이라는 신호다.
에어갭 운영을 명시한다는 것은 인터넷이 차단된 환경을 상정한다는 뜻이고,
그런 요구를 하는 조직은 금융, 방위, 규제 산업이다.
그리고 AGPL-3.0이라는 라이선스 선택이 이 그림을 완성한다 —
AGPL은 네트워크 서비스로 제공할 때도 소스 공개를 요구하므로
경쟁자가 이 코드로 SaaS를 만드는 것을 막고,
동시에 그 조항이 부담스러운 기업에게 상용 라이선스를 팔 여지를 남긴다.

즉 이 프로젝트의 구조는 오픈코어에 가깝다.
데스크톱 앱과 컨트롤 플레인을 공개하고,
셀프 호스팅 경로를 성실하게 문서화해 신뢰를 얻은 뒤,
운영을 직접 하고 싶지 않은 조직에게 호스팅과 지원을 파는 것이다.
`proliferate.com`이 문서와 다운로드와 체인지로그를 모두 들고 있고
README의 첫 행동 유도가 “Download for macOS”인 것도 같은 방향이다.

### 워크플로 절이 이 도구를 IDE에서 자동화 플랫폼으로 밀어낸다

기능 목록의 마지막 항목인 워크플로는 다른 다섯과 성격이 다르다.
앞의 다섯이 “사람이 에이전트를 돌리는 환경”에 관한 것이라면,
워크플로는 “사람 없이 에이전트가 돌아가는 일정”에 관한 것이다.
예시로 든 야간 리뷰 패스, 알림 기반 분류, 의존성 업데이트는
모두 사람이 자리에 없을 때 실행되는 작업이다.

이 항목이 들어감으로써 제품의 정체성이 이중화된다.
IDE는 사람의 편집 세션을 중심에 두는 도구이고,
반복·이벤트 기반 실행은 CI나 잡 스케줄러의 영역이다.
둘을 한 제품에 넣으면 “내 노트북이 꺼져 있을 때도 도는가”라는 질문이 즉시 따라오고,
README가 “로컬이나 클라우드에서”라고 적은 것이 그 답의 자리다.

이 이중성이 앞서 본 셀프 호스팅 분량과 맞물린다.
데스크톱 앱만 있으면 컨트롤 플레인이 필요 없는데,
Postgres와 API를 갖춘 서버가 필요한 이유가 바로 이 워크플로다.
그러니 이 제품의 구조는 “데스크톱 IDE에 서버가 딸린 것”이 아니라
“에이전트 실행 플랫폼에 데스크톱 클라이언트가 딸린 것”에 가까우며,
README의 첫 소개가 전자로 읽히게 쓰여 있다는 점이 이 문서의 특징이다.

## 비평

### 병렬 실행이 왜 좋은지에 대한 논증이 README에 없다

이 프로젝트의 핵심 판매 문구는 “병렬”이다.
제목에도, 저장소 설명에도, 기능 목록에도 들어 있다.
그런데 왜 에이전트를 병렬로 돌려야 하는지,
그것이 순차 실행보다 무엇을 더 주는지에 대한 설명은 한 줄도 없다.

이 공백이 문제인 이유는 병렬 실행의 이득이 자명하지 않기 때문이다.
사람이 에이전트를 감독해야 한다면 병렬성의 상한은 사람의 주의력이고,
그 상한은 대개 둘을 넘기 어렵다.
세 개의 에이전트가 동시에 세 개의 브랜치를 만들면
검토해야 할 diff가 세 배가 되고, 그 검토는 병렬화되지 않는다.
에이전트 코딩에서 실제 병목이 생성이 아니라 검증이라는 것은
이 분야에서 반복적으로 보고돼 온 관찰이며,
그렇다면 생성을 병렬화하는 도구는 병목을 옮길 뿐 줄이지 못한다.

README가 이 질문에 답할 재료를 실제로 갖고 있다는 점이 아쉽다.
서브에이전트 항목은 “위임하고 결과를 다시 받아 온다”고 적혀 있는데,
이것이 병렬성의 진짜 사용법일 가능성이 높다 —
사람이 세 개를 보는 것이 아니라 에이전트 하나가 세 개를 관리하는 구조다.
그리고 워크플로 항목은 사람이 자고 있는 동안 도는 실행을 다룬다.
두 항목 모두 “사람의 주의력이 상한이 아닌 경우”를 만드는 장치인데,
README는 이들을 병렬성과 연결하지 않고 별개 기능으로 나열한다.

### “모든 에이전트가 공유하는 통합”이라는 약속이 가장 검증되지 않은 부분이다

통합 항목은 MCP, 스킬, Computer Use, Browser Use, 커스텀 도구를
한 번 설정하면 모든 에이전트가 공유한다고 적는다.
이것이 사실이라면 이 제품의 가장 큰 가치일 것이다.
문제는 이 네 가지가 벤더마다 전혀 다른 것을 가리킨다는 점이다.

MCP는 그나마 공통 규격에 가깝지만
승인 흐름과 서버 수명 관리 방식이 하네스마다 다르다.
스킬은 Claude 진영의 개념이고 다른 하네스에 대응물이 없거나 형식이 다르다.
Computer Use와 Browser Use는 벤더별 구현이 별개이며
같은 이름으로 부를 수 있는 표준이 아직 없다.
그렇다면 “한 번 설정”이 실제로 뜻하는 것은
Proliferate가 각 하네스의 설정 파일을 대신 써 준다는 정도일 가능성이 높고,
그 경우 공유되는 것은 설정이지 동작이 아니다.

이 차이는 사용자에게 중요하다.
같은 MCP 서버를 붙였는데 Claude Code에서는 되고 Codex에서는 안 되는 상황이 생기면,
문제의 원인이 Proliferate인지 하네스인지 서버인지 구분하기 어렵다.
앞서 본 “네이티브 하네스” 전략이 여기서 대가를 치른다 —
감싸기만 하는 계층은 문제가 생겼을 때 진단할 정보를 갖고 있지 않다.
README는 이 한계를 언급하지 않고, 지원 범위를 기능별·하네스별로 정리한 표도 없다.

### README가 광고하는 플랫폼과 실제로 존재하는 빌드가 어긋난다

README는 다운로드 버튼에 "Download for macOS"라고만 적는다.
다른 플랫폼 언급은 없다.
반면 셀프 호스팅 절은 Docker, AWS, GCP, Azure, 쿠버네티스, 에어갭을 나열한다.
문서만 보면 서버는 어디서나 돌지만 클라이언트는 맥에서만 도는 구성으로 읽힌다.

그런데 실제로는 그렇지 않다.
Show HN 스레드에서 shukantpal이 "윈도우 exe에 코드 서명을 해 달라"고 요청했고,
메인테이너 pablo24602는 진행 중이라며 그동안의 나쁜 윈도우 경험을 사과했다.[^shukantpal]
즉 윈도우 빌드는 존재하되 서명되지 않은 상태이고,
README는 그 사실을 아예 적지 않는다.
모바일도 마찬가지다 — pablo24602는 모바일 접근이 아직 1급 기능이 아니며
베타 버전은 있지만 Codex와 Claude 수준의 안정성에 도달하기 전에는
정식 출시하지 않겠다고 밝혔다.[^pablo-mobile]

이 어긋남이 문제인 이유는 README가 플랫폼 지원을 과소 표기하는 방향이라는 점이다.
과대 표기보다 정직해 보이지만 실질적 결과는 나쁘다.
윈도우 사용자는 이 도구를 후보에서 지우고,
지우지 않고 시도한 사용자는 서명되지 않은 실행 파일을 만나게 된다.
그리고 에어갭 쿠버네티스를 운영하는 조직에 전원이 맥을 쓰는 경우는 드물다 —
서버 쪽 요구가 가장 까다로운 고객이 클라이언트 쪽 정보 부족에 가장 취약한 구조다.
셀프 호스팅에 이만큼 분량을 쓰면서
클라이언트 플랫폼의 현재 상태에 한 줄도 쓰지 않은 것은 균형이 맞지 않는다.

### 4개월 된 프로젝트가 에어갭 운영을 문서화하는 것은 성숙도 신호를 앞당겨 쓴다

저장소는 2026년 4월 30일에 만들어졌고 이 문서를 쓰는 시점 기준 약 4개월 됐다.
그 기간에 데스크톱 앱, 컨트롤 플레인, 다섯 개 하네스 통합,
워크플로 스케줄러, 그리고 여섯 가지 배포 경로가 만들어졌다는 것이 README의 주장이다.

이 속도 자체가 의심스럽다는 뜻은 아니다.
에이전트로 개발한 에이전트 도구라면 그럴 수 있고,
실제로 이 분야의 프로젝트들이 그런 속도를 보인다.
문제는 문서가 제시하는 성숙도 신호와 프로젝트 나이 사이의 간극이다.
에어갭 운영, 쿠버네티스 배포, CloudFormation 원클릭은
보통 여러 고객의 실제 도입을 거치며 다듬어지는 항목이고,
문서에 존재한다는 것과 프로덕션에서 검증됐다는 것은 다르다.

이 간극은 추측이 아니라 실사용 보고로도 확인된다.
kgrax01은 몇 주 동안 오픈소스·셀프 호스팅 Cursor를 찾아
Proliferate, OpenHands, Opencode Manager, Paseo를 모두 시도했다고 적는다.[^kgrax01]
Proliferate는 PC에서 돌리고 맥과 아이폰에서 제어하는 구성을 끝내 만들지 못했고,
설정이 답답했으며 문서가 혼란스러웠다는 것이다.
반면 Paseo는 아주 쉽게 작동했고 문서도 명확했다며 그쪽을 강력히 추천한다.
이 증언은 프로젝트와 무관한 사용자의 것이라고 본인이 명시했다.

이 간극은 도입 검토자에게 실질적 위험이다.
배포 문서가 상세하면 검토자는 그 경로가 검증됐다고 가정하게 되는데,
4개월 된 프로젝트에서 그 가정은 위험하다.
README가 “이 경로들 중 무엇이 실제 운영 중인지”를 구분해 주지 않으므로
검토자는 직접 시도해 보는 수밖에 없다.
Discord와 이슈 트래커로 안내하는 것이 그 자리를 대신하는데,
그것은 지원 채널이지 성숙도 증거가 아니다.

## 인사이트

### 에이전트 도구의 경쟁은 모델이 아니라 격리 단위에서 벌어진다

에이전트 코딩 도구를 비교할 때 흔히 보는 축은 지원 모델과 프롬프트 품질이다.
그런데 실제로 사용 경험을 가르는 것은 그보다 아래층에 있다 —
에이전트가 무엇을 단위로 격리되는가다.

가능한 단위는 여러 층이다.
프로세스, 컨테이너, git 워크트리, 저장소 복제, 가상 머신, 원격 샌드박스.
각 단위는 격리 강도와 설정 비용의 교환이며,
그 선택이 병렬성의 상한, 실패의 파급 범위, 상태 복원 방식을 전부 결정한다.
Proliferate가 워크트리를 고른 것은 로컬 개발 경험을 우선한 선택이고,
클라우드 실행을 파는 경쟁 제품들이 컨테이너나 원격 샌드박스를 고르는 것은
격리 강도와 확장성을 우선한 선택이다.

이 관점에서 보면 “어떤 에이전트를 지원하는가”는 표면적 차별점이다.
하네스는 CLI를 실행하면 되는 일이고 목록은 시간이 지나면 수렴한다.
반면 격리 단위는 바꾸기 어렵다 —
제품의 데이터 모델, UI 구조, 배포 방식이 전부 그 위에 세워지기 때문이다.
Proliferate의 “작업 = 워크트리 = 브랜치 = 대화 = 리뷰 상태”라는 대응은
바로 그 데이터 모델의 선언이며,
이 대응이 무너지는 상황 — 하나의 작업이 여러 저장소에 걸치거나,
브랜치 없이 실험만 하고 싶거나, 같은 브랜치에서 두 에이전트를 돌리고 싶은 경우 —
에서 제품이 어떻게 대응하는지가 장기 경쟁력을 정한다.

역사적 유비가 있다.
버전 관리 도구의 경쟁도 결국 명령어 집합이 아니라
“변경의 단위가 무엇인가”에서 갈렸다 —
파일 단위였던 CVS, 커밋 단위였던 Subversion, 스냅샷과 DAG였던 git.
사용자가 체감한 것은 명령어의 편의였지만
승패를 정한 것은 모델이었다.

### 병렬 에이전트의 병목은 생성이 아니라 리뷰이며, 그 사실이 UI 설계를 규정한다

README는 “각 작업이 자기 리뷰 상태를 받는다”고 적으면서
리뷰를 워크트리에 딸린 속성으로 다룬다.
그런데 병렬 실행이 실제로 만드는 문제는 리뷰가 병렬화되지 않는다는 것이다.
에이전트 셋이 각자 브랜치를 만들면 검토 대상이 셋이 되고,
사람은 그것을 순차로 읽는다.

이 비대칭이 누적되면 도구의 가치가 뒤집힌다.
생성 속도가 리뷰 속도를 넘어서는 순간
쌓이는 것은 완성된 작업이 아니라 미검토 브랜치이고,
미검토 브랜치는 시간이 지나면 베이스와 벌어져 가치가 떨어진다.
즉 병렬성을 높일수록 폐기되는 작업의 비율이 올라가는 구간이 존재한다.

그렇다면 이런 도구가 실제로 풀어야 할 문제는 실행 관리가 아니라 리뷰 처리량이다.
방향은 몇 가지다 —
에이전트가 서로의 결과를 먼저 검토하게 하거나(서브에이전트 항목이 그 씨앗이다),
자동 검증을 통과한 것만 사람에게 올리거나,
여러 브랜치의 diff를 한 화면에서 비교 가능한 형태로 합치거나.
README의 기능 목록에는 이 중 어느 것도 명시적으로 들어 있지 않고,
“리뷰 상태”라는 단어만 워크스페이스 속성으로 한 번 등장한다.

이 관찰은 이 제품에만 해당하지 않는다.
지난 2년간 나온 에이전트 오케스트레이션 도구 대다수가
실행을 병렬화하는 데 집중하고 검토를 병렬화하지 못했으며,
그래서 실제 사용에서는 동시에 돌리는 에이전트 수가
사람 하나당 한둘로 수렴하는 경향이 관찰된다.
도구가 이 수렴을 깨려면 사람의 검토를 대체할 신뢰 장치가 필요하고,
그 장치는 UI가 아니라 테스트, 정적 분석, 그리고 실패 시 되돌리기 비용의 문제다.

### AGPL과 완전한 셀프 호스팅을 함께 내건 것은 신뢰를 담보로 잡는 전략이다

이 프로젝트는 AGPL-3.0을 택하면서 컨트롤 플레인 전체를 셀프 호스팅 가능하게 열었다.
두 결정을 함께 보면 겨냥하는 심리가 보인다.
에이전트 코딩 도구는 소스 코드 전체를 읽고 쓰는 권한을 갖는 소프트웨어이므로
도입 검토에서 가장 먼저 나오는 질문이 “우리 코드가 어디로 가는가”다.

셀프 호스팅은 그 질문에 대한 가장 강한 답이다.
“우리 서버에서 돌리면 된다”는 것보다 안심시키는 문장은 없고,
에어갭 운영까지 문서화했다는 것은 그 답을 극단까지 밀었다는 뜻이다.
AGPL은 그 답의 진정성을 보증하는 장치다 —
소스가 공개되어 있으므로 무엇이 어디로 나가는지 감사할 수 있다.

동시에 이 조합은 사업적으로 계산된 것이기도 하다.
AGPL은 경쟁 SaaS를 막고, 셀프 호스팅 문서는 도입 장벽을 낮추며,
막상 운영해 보면 Postgres와 Caddy와 API를 직접 돌리는 부담이 드러나
결국 호스팅 제안으로 돌아오게 된다.
오픈소스 인프라 회사들이 반복해 온 경로이고,
GitLab과 Sentry와 Mattermost가 각자의 방식으로 지나온 길이다.

여기서 이 전략의 취약점이 하나 나온다.
이 경로가 작동하려면 셀프 호스팅이 “가능하지만 귀찮은” 지점에 있어야 하는데,
에이전트 도구에서는 그 균형이 맞추기 어렵다.
컨트롤 플레인이 하는 일은 결국 작업 스케줄링과 상태 저장이고,
그 정도는 조직 내부에서 이미 잘 돌아가는 인프라 위에 얹기 쉽다.
반대로 진짜 비싼 것은 모델 API 비용인데 그것은 이 제품이 중개하지 않는다.
그렇다면 유료 전환의 근거는 편의가 아니라
지원, 감사 대응, 그리고 규정 준수 문서가 되며,
그것은 4개월 된 프로젝트가 아직 갖추기 어려운 자산이다.

### 하네스를 감싸는 도구는 하네스가 같은 기능을 내장하는 순간 존재 이유를 다시 증명해야 한다

이 제품이 제공하는 것 — 워크트리 격리, 병렬 실행, 서브에이전트 위임,
설정 공유, 예약 실행 — 은 모두 하네스 바깥에서 하네스를 조작하는 일이다.
그리고 이 목록은 하네스 제작사들이 자기 제품에 넣고 있는 목록과 겹친다.

이런 구도에서 감싸는 쪽의 수명은 두 조건에 달려 있다.
하나는 감싸는 대상이 여럿이라는 사실 자체의 가치이고,
다른 하나는 감싸는 계층에서만 가능한 기능이 있느냐다.
전자는 실재한다 — Claude Code와 Codex를 함께 쓰는 조직에게
두 도구의 워크트리와 설정을 한 곳에서 관리하는 가치는 하네스가 줄 수 없다.
후자가 더 어렵다.
지금 목록에서 하네스가 스스로 할 수 없는 것은 사실상 “여러 하네스를 가로지르는 것”뿐이다.

역사적으로 이 자리에 있던 도구들의 결말은 갈렸다.
여러 클라우드를 가로지르던 도구 중 일부는 표준이 됐고(Terraform),
일부는 각 클라우드가 자기 도구를 개선하면서 밀려났다.
갈림길은 대체로 하나였다 —
가로지르는 계층이 자기만의 추상을 만들어 냈는가,
아니면 아래 계층의 기능을 중계하기만 했는가.

Proliferate가 만들 수 있는 자기 추상의 후보는 “작업(task)”이다.
브랜치, 터미널, 대화, 리뷰 상태를 하나로 묶은 단위는
어느 하네스에도 없는 개념이고,
그것이 하네스를 갈아 끼워도 유지되는 조직의 자산이 된다면
이 계층은 중계가 아니라 기록의 층이 된다.
README가 이 개념을 기능 목록의 한 줄로만 두고
제품의 중심 개념으로 내세우지 않은 것이,
지금 시점에서 이 프로젝트가 자기 위치를 어떻게 보고 있는지를 보여준다.
