# Ace는 팀 구성원과 에이전트가 각자의 컴퓨터에서 같은 채널에 모여 일하는 도구이고, 신뢰의 경계를 Tailscale 네트워크에 맡긴다

<https://ace.githubnext.com/>

<https://github.com/githubnext/ace>

HN 토론: <https://news.ycombinator.com/item?id=50409162> (3점, 2개 댓글)

GN 토론: <https://news.hada.io/topic?id=37137>

## 소개

Ace는 GitHub Next가 공개한 협업 코딩 환경이다.
저장소 설명은 팀과 함께 로컬에서 소프트웨어를 만드는 도구라고 한다.
저장소는 2026년 10월 2일에 만들어졌고 MIT 라이선스이며 TypeScript로 쓰였다.
2026년 11월 14일에 읽은 값으로 별 93개, 포크 12개, 열린 이슈 72개이다.
홈페이지는 이것을 GitHub Next의 실험이라고 밝히고 거친 부분이 있을 것이라고 예고한다.
이 문서는 홈페이지와 README와 용어집과 아키텍처 문서를 읽은 것이며 Ace를 설치하거나 실행해 보지는 않았다.

## 구조

### 용어

Ace는 용어를 구속력 있는 문서로 정의한다.
채널(channel)은 사이드바의 지속적인 단위로, 하나 이상의 대화(chat)를 담고 호스트 위에서 하나의 작업 프로세스로 돈다.
대화는 채널 안의 하나의 대화 기록이고, 부모 대화를 죽이면 자식 대화도 죽는다.
레인(lane)은 한 단위 작업을 위한 격리된 Git worktree와 브랜치이며, 한 번에 하나의 대화만 쓰고, 풀 리퀘스트로 반영된다.
호스트(host)는 Ace의 호스트 프로세스를 돌리는 한 대의 기계이다.
팀은 같은 Tailscale 네트워크(tailnet)에 있는 사람과 기계이다.
디렉터리(directory)는 팀의 프로젝트와 호스트와 채널 위치의 공유 목록이며 팀 자신의 계정에 배포된다.
클라우드 채널은 베타이고 선택 사항으로, 팀의 계정에 있는 리눅스 컨테이너에서 도구가 돌아 모든 노트북을 닫아도 계속 일한다.

### 동작 방식

사용자는 Tailscale을 먼저 켜고, 설정에서 Anthropic이나 OpenAI의 모델 키를 넣고, 팀 디렉터리에 가입하고, 폴더를 프로젝트로 열어 채널을 시작한다.
채널에서 사람과 에이전트가 같은 대화를 보며 일한다.
홈페이지의 시연은 한 사람이 다크 모드가 필요하다고 말하고 다른 사람들이 의견을 더하면 `@ace do it`으로 에이전트가 파일을 읽고 고치고 앱을 다시 띄운다는 식이다.
에이전트가 채널에 질문하면 답을 아는 사람이 대답하고 이어서 일한다.
채널에 없던 사이에 일어난 일은 “While you were away” 요약으로 알려 준다.
다른 사람이 내 에이전트를 부릴 수 있는 것은 내가 에이전트 접근을 켰을 때뿐이고, 기본은 꺼져 있다.
호스트의 CLI도 있어서 `ace new`로 채널을 만들고 `ace ask`로 질문한다.

내부는 채널 하나가 pi라는 지속 세션(durable session) 하나를 소유하는 구조이다.
로컬 채널은 하나의 SQLite 파일 위에서 하나의 작업 프로세스로 돌고, 충돌하면 마지막 체크포인트에서 이어 간다.
아키텍처 문서는 이전 버전의 Ace가 채널마다 클라우드 VM 안에서 프로세스를 돌렸는데 고통의 대부분은 VM과 클라우드 인프라에서 왔다며 프로세스는 유지하고 인프라는 버렸다고 설명한다.
또 Ace가 호스팅 서비스를 운영하지 않고 팀이 직접 복제해 운영하는 오픈소스라고 밝힌다.

### 보안 모델

README의 첫 경고는 이렇다.
Ace는 에이전트를 호스트를 실행하는 사용자의 권한으로 돌린다.
에이전트는 임의의 셸 명령을 실행하고 프로젝트 디렉터리 밖의 파일도 읽고 바꾸고 지울 수 있으며, 채널과 레인은 보안 샌드박스가 아니다.
팀 구성원 자격과 협업 접근의 유일한 권한은 tailnet이고, Ace에는 별도의 계정이나 초대나 접근 제어가 없다.
그래서 호스트에 접근할 수 있게 해도 되는 신뢰하는 사람과 기계만 tailnet을 통해 Ace에 닿게 하라고 한다.

접근은 프로젝트 단위로 나뉜다.
GitHub 프로젝트는 GitHub 로그인이 읽을 수 있는 저장소에 대해, 로컬 폴더는 자기 호스트에 대해 직접 접근이 있고, 나머지는 공유(share)가 필요하다.
호스트는 `tailscale whois`로 호출자를 확인하고 접근 없는 호출자를 거절한다.
문서는 알려진 한계도 적는다.
프로젝트 접근은 협조적이어서, 수정하지 않은 Ace를 돌리는 호스트 사이에서만 유지되고 자기 호스트를 변조한 팀원에게는 소용이 없다.
팀 서비스가 `ACE_SECRET`에서 파생한 하나의 자격 증명을 받아들이고 모든 호스트가 이를 가지므로, 이 비밀을 가진 사람은 모든 목록을 읽고 어떤 로비에든 들어가며 호스팅 채널에서 보고 글을 쓸 수 있다.
호스트가 보고하는 GitHub 로그인도 검증되지 않은 주장이다.
채널 소유자가 협력자의 에이전트 호출을 켜면 팀원이 소유자로서 이 호스트에서 명령을 실행할 수 있음을 문서가 명시한다.

## 분석

### 중심 주장은 클라우드를 빼고 팀의 기계를 작업장으로 삼는다는 것이다

Ace의 설계 결정은 이전의 클라우드 VM 구조를 버리고 사람들의 노트북과 데스크톱을 작업의 장소로 삼는 것이다.
이득은 분명하다. 코드와 에이전트의 실행이 팀 소유 기계에 남고, 모델 키는 키체인에 있으며, 호스팅 서비스의 운영 책임이 없다.
대가도 분명하다. 에이전트가 사용자 권한으로 돌아가므로 사고의 영향 범위가 사용자의 기계 전체이고, 신뢰 모델이 팀원 모두를 신뢰한다는 가정에 기댄다.
이 구조는 작은 팀이 서로를 알 때에는 마찰이 적고, 신뢰 경계가 흐린 팀에는 맞지 않는다.

### 팀원은 곧 tailnet이라는 선택은 단순함과 위험을 함께 준다

별도 계정이나 역할이 없다는 선택은 설정이 단순하다는 장점이 있다.
Tailscale이 이미 팀의 신원과 접근 규칙을 관리하므로 Ace가 다시 만들 필요가 없다.
그러나 문서가 인정하듯 tailnet에 들어온 사람은 모두 팀이고, 프로젝트 단위의 접근 제한은 협조적이다.
비밀 하나를 가진 호스트는 모든 팀 서비스를 읽을 수 있다.
문서는 이를 알려진 한계로 적고 호스트별 자격 증명이 이를 해결할 것이라는 이슈를 가리킨다.
이 문서는 그 이슈를 열어 보지 않았다.

## 비평

### 에이전트가 사용자 권한으로 돈다는 점이 가장 큰 위험이다

README의 경고는 에이전트와 샌드박스에 대한 가장 솔직한 서술이다.
다른 사람이 내 에이전트를 부를 수 있게 켜면 그 사람이 소유자로서 이 호스트에서 명령을 실행하는 것과 같다.
이 설계에서 에이전트 접근을 켜는 것은 사실상 셸 접근을 주는 일이다.
HN의 한 댓글은 이 도구를 보안 악몽이자 또 하나의 새 IDE로 보고 거부했다.[^verdverm]
이 평가는 근거를 풀어 쓰지 않은 짧은 반응이지만, 문서가 스스로 적은 한계와 방향이 같다.
기본이 꺼져 있다는 점과 켤 때 경고한다는 점은 위험을 줄이지만 없애지는 않는다.

### 성숙도와 채택의 근거가 약하다

홈페이지가 실험이고 거친 부분이 있다고 밝히는 점은 정직하다.
그러나 별 93개와 열린 이슈 72개, 공개한 지 6주 남짓이라는 사실은 이 도구가 어느 정도 쓰이는지에 대한 증거가 부족하다는 뜻이다.
HN에서도 이 도구는 3점과 2개 댓글에 그쳤다.
반응의 규모만으로 도구의 가치를 판단할 수 없지만, 팀 단위로 도입한 사례를 이 문서는 찾지 못했다.

### 협업의 이점이 에이전트 시대의 병목과 맞는지는 열려 있다

Ace는 같은 채널에서 사람들이 에이전트를 함께 이끄는 협업(멀티플레이어)을 내세운다.
이 저장소에 정리된 다른 글들에서는 에이전트 개발의 병목이 코드 작성이 아니라 검토와 이해라는 논의가 반복된다.
채널에서 여럿이 같은 대화를 보며 에이전트를 이끄는 방식이 검토의 병목을 줄이는지는 이 문서가 판단할 수 없다.
HN 스레드에서도 이 점을 다룬 반응은 없었다.

## 인사이트

### 신뢰 경계를 어디에 두는지가 이 도구를 쓸 수 있는 팀을 정한다

Ace가 가장 분명하게 보여 주는 것은 신뢰 모델을 문서의 맨 앞에 둔 방식이다.
팀원 모두가 서로의 기계에서 명령을 실행할 수 있어도 되는 조건이 도입의 전제이다.
도입 전에 점검할 질문은 세 가지로 정리된다.
tailnet에 들어오는 모든 사람과 기계를 서로 신뢰하는가,
에이전트의 파일 접근 범위(프로젝트 밖)가 문제 되는 자료가 호스트에 있는가,
모델 키와 팀 비밀(`ACE_SECRET`)의 관리 책임을 누가 지는가이다.
이 질문들은 Ace에 한정되지 않고 에이전트에게 팀 공유 환경을 주는 모든 도구에 적용된다.

### 협조적 접근 제어는 신뢰가 있는 팀에서만 안전하다

문서가 “프로젝트 접근은 협조적”이라고 한 문장은 보안 설계에서 가치 있는 정직이다.
접근 제어가 수정하지 않은 클라이언트 사이에서만 유지된다는 것은 악의가 있으면 뚫린다는 뜻이다.
도구가 이 한계를 명시한 덕분에 사용자는 자기 팀에 이 가정이 맞는지 따질 수 있다.
도구를 평가할 때는 기능 목록보다 알려진 한계 문서가 있는지를 먼저 보는 것이 좋다.
이는 이 문서의 평가 기준이다.

### 확인할 관찰

이 도구의 방향을 가를 관찰은 세 가지이다.
호스트별 자격 증명 이슈가 해결되는지,
실제 팀 도입 사례와 사고 보고가 나오는지,
일정 기간 뒤에도 유지되는지 아니면 방향이 바뀌거나 보관되는지이다.
셋 모두 이 문서가 확인하지 못했다.
