# Claude Code를 은퇴시키고 Pi로 옮긴 이유는 작은 불만의 누적과 방향 없는 기능 추가다

원문: [Goodbye Claude, Hello Pi](https://caleb.software/posts/claude-to-pi.html)

HN 토론: <https://news.ycombinator.com/item?id=50410107> (705점, 437개 댓글)

GN 토론: <https://news.hada.io/topic?id=36795>

## 요약

caleb.software의 블로그 글로, 2026년 9월 21일에 올라왔고 11월 7일에 갱신되었다고
표시되어 있다.
글쓴이는 Claude Pro 구독에 Claude Code가 들어온 지 1년이 넘은 시점부터 쓴
오래된 사용자였다.
처음 쓴 날 한 번의 프롬프트로 주말 프로젝트용 파이썬 코드가 쏟아져 나오던 것이
설렜고, 몇 년 뒤에는 이 도구의 출시가 소프트웨어 개발의 새 시대를 이끈 큰
요인으로 기억될 것이라고 확신한다고 쓴다.
그런데도 작은 불만이 쌓여 Claude Code를 주 코딩 하니스(harness)에서 내리고
Pi로 옮기기로 했다고 한다.
결정한 지 하루 뒤 Anthropic이 Claude Code의 AGENTS.md 지원을 발표했지만
글쓴이에게는 너무 늦은 조치였다고 말한다.

불만은 세 갈래다.
첫째는 AGENTS.md다.
CLAUDE.md 파일을 흩어 놓는 것이 취미 저장소에 좋은 게릴라 마케팅일 수는
있어도, 사용자는 두 형식 사이에서 복사하거나 심볼릭 링크를 걸어야 한다는
것이다.
둘째는 IDE 연동이다.
글쓴이는 코드를 커밋 전에 대부분 직접 검토하는 편이라 VSCode 안에서 Claude Code를
쓰고, 파일에서 글을 선택하면 질문이나 수정 요청의 맥락에 자동으로 들어가는
기능을 좋아한다.
하지만 IDE에 연결되는 세션이 한 번에 하나뿐이어서 탭을 하나 더 열면 두 번째
세션은 선택 이벤트를 받지 못한다.
이 문제는 2025년 12월에 이미 보고되었는데 관계없는 다른 버그의 중복으로 닫혔다고
한다.
공식 VSCode GUI 확장은 탭을 여러 개 열 수 있지만 내장 슬래시 명령의 절반이
동작하지 않고, 사용자 지정 상태 줄을 지원하지 않으며, 하위 에이전트의 출력이
시간순으로 주 대화에 섞여 여럿이 돌 때 읽기 어렵다는 불만이다.
셋째는 변경의 속도와 방식이다.
동적 워크플로, 에이전트 팀, 울트라리뷰 같은 기능은 기업 고객이 매일 더 많은
토큰을 태우게 하는 방법일 뿐 자신이 원하는 것은 아니라고 한다.
글을 쓰던 시점에 올해 Claude Code 릴리스가 244번 있었고 그중 4분의 3 넘게
시스템 프롬프트나 도구 설명을 바꾸었는데, 그것이 사용자의 지시나 저장소 규칙과
충돌하면 LLM의 성능이 크게 달라질 수 있다는 것이다.
시스템 프롬프트의 80%를 줄였는데도 Pi보다 오버헤드가 훨씬 크다고 하고,
기본 Bash 도구의 설명은 약 3,000토큰이며 대부분이 git과 GitHub PR 사용법이라고
한다.

글쓴이는 이 글이 불평이 많았다고 사과하며, 새 분야의 선구자가 되는 일은
어렵고 자신이 더 잘했으리라고 생각하지 않는다고 덧붙인다.
Claude Code가 강한 비전이 없는 제품처럼 느껴지며, 열정적인 엔지니어와 PM이
각자의 작업 방식에 맞는 기능을 붙이고 다른 사용자에게 미칠 영향은 살피지
않는 것 같다고 평가한다.
요청에 단호하게 아니라고 말하는 것이 직무인 사람이 위에 없는 듯하다는 것이다.
Pi로 옮긴 뒤 처음 며칠은 손볼 곳이 있었으나 이후 순조로웠고, 안정성과 미니멀한
접근과 극단적인 맞춤 가능성이 마음에 든다고 한다.
이미 자신의 용도에 맞는 확장을 몇 개 썼고 정리해서 공개할 계획이라고 한다.

## 분석

### 불만의 공통점은 기능이 아니라 통제권이다

세 불만은 서로 달라 보이지만 한 가지로 모인다.
도구가 사용자의 환경에 어떻게 들어오고 어떻게 바뀌는지를 사용자가 통제하지
못한다는 것이다.
AGENTS.md는 사용자의 파일 형식 선택권, IDE 연동은 사용자의 작업 흐름,
시스템 프롬프트의 잦은 변경은 사용자가 쌓아 둔 설정의 안정성에 해당한다.
글쓴이가 Pi에서 얻었다고 말하는 것도 새 기능이 아니라 안정성과 맞춤 가능성이다.
이는 이 글을 해석한 것이다.

### 시스템 프롬프트의 변경은 사실상 사용자 설정을 깨는 호환성 문제다

글이 가장 구체적으로 말하는 것은 릴리스 244번 중 4분의 3 넘게 시스템 프롬프트나
도구 설명이 바뀌었다는 수치다.
프롬프트는 사용자가 쓴 지시와 같은 곳에서 모델에 읽히므로, 도구의 지시가
바뀌면 사용자 지시와의 상호작용이 달라질 수 있다.
소프트웨어에서 API가 바뀌면 호환성 문제로 다루지만 프롬프트 변경은 같은 수준의
공지를 받지 못한다는 것이 글의 문제 제기다.
글쓴이가 각주에서 지적한 Bash 도구 설명도 이 관점에서 읽힌다.
도구 설명이 약 3,000토큰이고 대부분이 모델이 이미 아는 git과 PR 사용법이라는
것은 모든 요청에 반복되는 고정 비용이라는 지적이다.
글은 백만 일일 사용자와 하루 1억 요청을 가정해 이 설명에서 1,000토큰만 줄여도
연간 수백만 달러의 추론 비용을 아낄 수 있다고 추산한다.

HN의 fwlr는 이 각주를 두고, 토큰을 1,000개 줄이면 추론 비용을 아끼는 것이 아니라
추론 매출을 잃는 것이므로 그것이 줄지 않는 이유가 설명된다고 비꼬았다.[^fwlr]
글의 비용 계산이 누구의 비용이냐에 따라 부호가 달라진다는 지적이다.

### 선택지가 오픈소스 하니스라는 점이 결론을 만든다

글쓴이는 Pi를 후발 주자가 선구자의 경험에서 핵심 기능과 잘라 낼 기능을 구분할
수 있는 이점을 가진 도구로 본다.
그러므로 이 글은 한 제품의 결함을 주장하기보다 규모가 커지는 제품과 작게
유지되는 도구의 차이를 말하는 글이다.
요청을 거절하는 사람이 없다는 진단도 이 맥락에서 나온다.

## 비평

### 수치의 의미가 글에서 정해지지 않았다

릴리스 244번은 올해 Claude Code의 변경이 많았다는 것은 보여 주지만,
그중 3/4이 프롬프트나 도구 설명을 바꾸었다는 것이 얼마나 나쁜지는 보여 주지
않는다.
작은 문구 수정과 행동을 바꾸는 수정이 같은 한 번으로 세어졌을 가능성이 있고,
글은 어떻게 셌는지 밝히지 않는다.
같은 기간 Pi의 릴리스와 변경 빈도와의 비교도 없다.
그래서 Claude Code가 불안정하다는 판단은 숫자가 아니라 글쓴이의 경험에 기대고
있다.

HN의 zmmmmm은 글이 일관되지 않다고 평했다.
Claude Code에 대한 불만 대부분이 Pi가 애초에 지원하지 않는 기능에 관한 것이고,
불안정이라고 부른 빠른 개발 속도는 Pi도 같거나 더 빠르며, 확장 생태계가 더
안정적이리라고 암묵적으로 가정한다는 것이다.[^zmmmmm]
AGENTS.md를 두고 ftchd는 Claude가 이미 오래전부터 그 파일을 읽어 왔다면 결정의
근거가 사실과 다르지 않느냐고 물었고, artdigital은 그것이 최근에 추가된
기능이며 전에는 심볼릭 링크나 `@AGENTS.md` 포함이 필요했다고 바로잡았다.[^ftchd][^artdigital]
이 바로잡음은 글의 서술과 맞는다.

### 비교가 한쪽에만 구체적이다

Claude Code의 문제는 시점과 개수로 적었지만 Pi가 오버헤드가 적다는 말에는
숫자가 없다.
Claude Code가 시스템 프롬프트의 80%를 줄이고도 오버헤드가 훨씬 크다는
문장도 이전과 현재의 크기, Pi의 크기를 말하지 않는다.
Bash 도구 설명이 약 3,000토큰이라는 수치도 어느 버전 기준인지 적지 않았다.
글은 안정성이 장점이라고 하면서 Pi로 옮긴 지 며칠 뒤의 경험만 근거로 든다.

### 옮기는 비용 중 구독 조건이 글에 없다

글은 Pi를 어떤 모델과 어떤 요금으로 쓰는지 밝히지 않는다.
HN에서 leobuskin은 Pi가 좋은 하니스이지만 Anthropic 구독과는 맞지 않고,
약관 위반으로 인한 차단 가능성, 맞춤 헤더와 문서화되지 않은 API 기능을 따라가지
못하는 점, Claude Code의 더 나은 압축, 캐시의 미묘한 문제 같은 이유를
들었다.[^leobuskin]
eli는 Agent SDK로 Anthropic에 연결하는 것은 공식 지원 방식이어서 차단 위험이
없다고 바로잡았다.[^eli]
edweis는 Anthropic 구독이 API 사용량 대비 꽤 이득이라는 계산을 내놓으며 Pi로
옮기면 토큰 오버헤드를 줄여서 이 계산이 달라지느냐고 물었다.[^edweis]
글이 말한 오버헤드 절감이 사용자에게 실제 비용이 되는지는 요금 방식에 달려
있고, 글은 그것을 말하지 않는다.

### 글쓴이의 해법은 유지 책임을 자신에게 옮긴다

글쓴이는 Pi 설치 뒤 여러 탭에서 같은 기능을 처리하는 확장을 20분 만에 썼다고
각주에 적는다.
이는 확장성의 이점이지만 동시에 자기 환경을 책임지는 일을 사용자가 떠안는다는
뜻이다.
Pi가 바뀌거나 확장이 깨질 때의 비용은 글에서 다루지 않는다.
IDE에서 검토하는 흐름이 중요하다고 했던 사용자에게 이 비용이 허용될 만한지도
알 수 없다.

HN의 giladd는 Pi를 써 보니 상쾌했지만 위험한 동작을 막는 자동 모드 같은 기본
기능을 넣지 않고 검증 절차가 없는 서드파티 모듈에 맡기는 태도 때문에 Claude
Code로 돌아왔다고 썼다.[^giladd]
mpern은 자동 모드를 애초에 믿지 않으며 에이전트를 샌드박스에 넣고 검사 없이
돌리면 권한 피로와 플러그인 신뢰 문제가 모두 사라진다고 답했다.[^mpern]
둘 중 어느 쪽이 맞는지는 사용자의 위험 감수에 달려 있고, 확장을 직접 쓴다는
글쓴이의 선택은 이 책임도 함께 받는다는 뜻이다.

### 방향 부재라는 진단은 외부에서 본 추정이다

글쓴이는 Anthropic 내부에 요청을 거절하는 사람이 없는 듯하다고 말한다.
이것은 릴리스 내용과 기능 목록에서 이끌어 낸 추정이며, 기능이 많고 빨리
추가된다는 사실이 방향이 없다는 증거는 아니다.
글쓴이도 자신이 더 잘했으리라고 확신하지 않는다고 인정한다.

## 인사이트

### 하니스는 모델이 아니라 환경의 일부이므로 변경 통제가 선택 기준이 된다

사용자가 지시, 설정, 확장을 쌓는 순간 하니스는 도구가 아니라 환경이 된다.
환경에서는 기능의 풍부함보다 변경이 예측 가능한지가 중요해진다.
글쓴이가 Pi에서 안정성과 미니멀함을 같이 말하는 이유다.
릴리스마다 프롬프트가 바뀌는 도구는 사용자의 환경을 매번 다시 시험해야 하는
도구다.
이 해석은 글에 직접 나오지 않으며 이 문서의 추론이다.

HN의 epolanski는 Codex와 Claude에 불만인 이유가 나쁜 소프트웨어여서가 아니라
통제권이 없어서이며, 비결정적인 LLM에 매일 바뀌는 하니스까지 겹치는 것을 못
견디겠다고 썼다.
몇 버전마다 도구 사용 방식과 스킬을 읽거나 무시하는 방식이 달라지고, 갑자기
워크트리를 만들거나 백그라운드 작업을 띄워 놓는다는 것이다.[^epolanski]
이는 글쓴이의 불만이 한 사람의 취향이 아니라는 증언이지만 한 사용자의 경험이다.

### 도구 설명의 크기는 비용이면서 행동의 편향이다

글이 지적한 3,000토큰짜리 Bash 설명은 토큰 비용이기도 하지만 모델에게 git과
PR 사용을 특정한 방식으로 하라는 지시이기도 하다.
글은 각주에서 그 설명이 안내하는 명령 형식이 자동 모드가 널리 배포되기 전에는
기존 git 명령 허용 목록과 상관없이 늘 수동 검토 규칙에 걸렸다고 말한다.
도구 설명이 사용자 설정과 충돌하는 사례가 비용 문제와 같은 원인에서 나온다는
것이다.
설명이 길수록 충돌 표면도 커진다.
이 역시 이 문서의 해석이다.

### 하니스 이동의 비용이 낮을수록 하니스 사이의 경쟁은 변경 통제로 일어난다

AGENTS.md는 하니스 사이에서 설정 파일을 공유하는 공통 형식이다.
형식이 공통이면 사용자는 불만이 쌓일 때 옮길 수 있고, 하니스는 옮기지 않게 할
이유를 기능이 아니라 신뢰에서 찾아야 한다.
글쓴이가 결정한 지 하루 뒤의 발표를 너무 늦었다고 말하는 것도 같은 맥락이다.
이동 비용이 낮아진 시장에서는 변경의 예측 가능성이 유지의 조건이 된다.
이는 이 문서의 추론이며 이 글 하나로 검증되지 않는다.
