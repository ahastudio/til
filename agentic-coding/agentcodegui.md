# AgentCodeGUI: IDE를 버리고 에이전트를 감싼 Windows 데스크톱 앱

<https://github.com/UnrealFactory/AgentCodeGUI>

Show GN: [Claude Code와 Codex CLI를 위한 올인원 에이전트 앱 대화로 코딩하고, 그 자리에서 읽고 고칩니다.](https://news.hada.io/topic?id=31980)

## 소개

만든 사람이 GeekNews에 올린 소개글의 출발점은 IDE가 필요 없어졌다는 판단이다.
사람은 코드를 읽고 판단만 하면 되고 작업은 에이전트가 하므로,
그 판단 하나 하자고 무겁고 복잡한 IDE를 통째로 켜 둘 이유가 없다는 것이다.
그렇다고 Claude Code를 터미널로만 쓰기에는 직관성이 낮아서
지금 무엇을 어디까지 하는지 한눈에 보이지 않는다고 적는다.

그래서 만든 것이 Claude Code와 Codex CLI를 GUI로 감싼 Windows 앱이다.
가볍게 만드는 데 공을 들인 이유도 밝혀 두었다 —
Rider에 언리얼 프로젝트를 여러 개 띄우는 일이 잦아서
여기에 더 얹을 무거운 도구는 쓰고 싶지 않았다는 것이다.
다계정으로 Claude Code나 Codex를 쓰는 사람이 많다는 관찰도 설계에 들어갔다.

저장소는 `UnrealFactory/AgentCodeGUI`이고 MIT 라이선스다.
2026년 6월 14일에 만들어졌고 TypeScript로 작성된 Electron 앱이며,
별 71개, 포크 6개, 열린 이슈 0개다.

## 기능

기능 목록의 축이 셋이다 — 대화, 코드 읽기, 그리고 여러 에이전트를 동시에 굴리는 것이다.

대화 쪽에는 스트리밍 응답과 도구 호출 로그와 승인·질문 카드가 있고,
실행 중에도 메시지를 예약해 둘 수 있다.
`Ctrl+F` 대화 검색, 이미지·텍스트 첨부, `/` 명령과 스킬, `@` 파일 멘션,
`↑`·`↓`로 보낸 메시지 되불러오기가 들어 있다.
오른쪽 버튼 드래그 제스처로 스크롤과 파일 이동과 창 제어까지 한다.

코드 읽기 쪽이 이 앱의 중심이다.
자체 탐색기와 LSP 코드 뷰어가 TS·JS·Python·C#·C/C++·Unreal Verse를 지원하고,
`F12` 정의 이동과 의미 기반 색상과 구조화된 호버 카드를 제공한다.
JetBrains 색 스킴을 쓰고 C#은 어셈블리 심볼을 `F12`에서 디컴파일한다.
언리얼 C++와 Verse 공식 API 문서의 호버를 한국어로 번역해 보여 준다.
diff 뷰어에서 추가는 녹색 행이고 삭제는 빨간 고스트 줄이며,
에이전트가 건드린 파일에 색과 배지가 붙는다.

동시 실행 쪽은 최대 6개 패널이며 각 패널이 자기 폴더와 모델과 계정을 갖는다.
`Ctrl+Shift+N`으로 독립 OS 창을 띄워 코드 옆에 두는 별도 대화도 있다.
Claude Code의 Workflow 도구가 그대로 동작하는데,
터미널과 달리 턴이 끝난 뒤에도 워크플로가 백그라운드에서 완주하고
끝나면 마무리 답변을 스스로 올린다.
하단 알약을 누르면 단계 레일과 에이전트 보드가 펼쳐지고
에이전트별 모델과 토큰과 도구 호출 수가 실시간으로 표시된다.
개발 서버 같은 셸과 서브에이전트도 턴보다 오래 살아남는다.

Git 화면이 따로 있다.
변경 파일 체크리스트에서 커밋에 넣을 것을 고르고 파일을 눌러 diff를 보며,
버튼 하나로 스테이징된 변경에서 커밋 메시지를 초안한다.
당겨오기·푸시·히스토리·브랜치 전환이 들어 있고
중첩 저장소를 3단계까지 자동으로 찾아 각각 카드로 만든다.

## 모델과 계정

엔진별로 구독 계정 또는 API 키를 쓴다.

| 엔진        | 모델                                       | 과금                               |
| ----------- | ------------------------------------------ | ---------------------------------- |
| Claude Code | Fable 5 · Opus 5 · Sonnet 5 · Haiku 4.5    | Claude 구독(Pro/Max) 또는 API 키   |
| Codex CLI   | GPT-5.6-Sol · GPT-5.6-Terra · GPT-5.6-Luna | ChatGPT 구독(Plus/Pro) 또는 API 키 |

모델 목록을 설치된 엔진에서 실시간으로 읽어 오므로
새 모델이 나오면 선택기에 그냥 나타난다고 적는다.
엔진과 모델과 추론 강도와 권한 모드를 대화마다 고른다.

계정 관리가 이 앱의 별도 기능이다.
설정의 계정 항목에서 엔진별로 구독 계정을 여러 개 등록해 두고
아무 대화나 아무 계정에 연결할 수 있으며,
연결하지 않은 대화는 기본 계정을 쓴다.
각 계정에 남은 한도 게이지가 5시간·주간·Fable 단위로 표시되어
여유가 있는 쪽으로 옮겨 갈 수 있다고 설명한다.

자격 증명은 DPAPI로 암호화해 `~/.agentcodegui`에 저장하며
터미널 쪽의 `~/.claude`와 `~/.codex` 로그인과 완전히 분리되어
서로 영향을 주지 않는다고 적는다.

## 배포와 릴리스

배포 형태는 Windows 10/11용 NSIS 설치 파일 하나다.
릴리스에서 `AgentCodeGUI-Setup-<버전>.exe`를 받아 실행하고,
첫 실행에 엔진이 자동으로 설치되며 시스템 전역 터미널 설정은 건드리지 않는다.
새 버전은 자동 업데이트되고 사이드바에 배지가 뜨면 한 번 눌러 조용히 설치된다.

릴리스 속도가 눈에 띈다.
2026년 6월 14일 `v1.0.0`부터 8월 20일 `v2.6.1`까지 두 달여에 71개 릴리스이고,
누적 다운로드가 31,746건이다.
같은 시점의 별 개수가 71개다.

개발 환경은 `electron-vite`이며 `npm run dev`로 HMR을 쓰고
`npm run typecheck`가 메인과 렌더러를 각각 검사한다.
소스는 Electron 메인(엔진 어댑터·LSP·영속화), React 렌더러,
그리고 메인과 렌더러의 IPC 계약을 담은 공유 층으로 나뉘어 있다.

## 분석

### IDE를 버린다는 주장의 실제 내용은 IDE의 절반만 남긴다는 것이다

소개글의 주장은 강하다 — 이제 IDE가 굳이 필요 없다는 것이다.
그런데 앱의 기능 목록에서 가장 두꺼운 항목이 코드 읽기이고,
거기에 LSP 뷰어와 정의 이동과 의미 기반 색상과 디컴파일과 호버 카드가 들어 있다.
JetBrains 색 스킴을 쓰고 C#은 어셈블리를 풀어 보여 준다.
이것은 IDE를 버린 것이 아니라 IDE에서 편집기를 뺀 것이다.

이 구분이 중요한 이유는 무엇을 절약했는지가 거기서 정해지기 때문이다.
편집을 뺐다는 것은 자동 완성 후보 생성과 리팩터링 엔진과 저장 시 검사와
빌드 통합과 디버거를 뺐다는 뜻이고,
무거움의 대부분이 실제로 그 계층에 있다.
읽기만 남기면 색을 칠하고 심볼을 해석하는 일만 하므로 가벼워진다.

그러면 이 앱의 실제 명제는 다르게 읽힌다 —
에이전트가 쓰는 시대에 사람이 IDE에서 쓰는 기능은 읽기 쪽에 몰려 있고,
그 절반만 따로 떼면 훨씬 가벼운 도구가 된다는 것이다.
이 명제는 검증 가능하고 이 앱이 그 증거인데,
소개글의 “IDE가 필요 없다”는 표현은 그보다 넓어서
편집기를 아예 쓰지 않는다는 주장으로 읽힌다.
Git 화면에 커밋 전 diff 검토가 들어 있는 것도 같은 방향이다 —
사람이 하는 일이 작성에서 검토로 옮겨 갔다는 관찰의 결과다.

### 같은 문제에 대한 답이 세 방향으로 갈렸다

터미널 코딩 에이전트의 화면이 부족하다는 문제는 널리 공유된 것이고,
이 저장소에 그 답이 이미 여러 개 기록되어 있다.

한쪽 극단은 화면을 더 줄이는 방향이다.
[코딩 에이전트를 IDE가 아니라 Unix 명령으로 되돌린 6MB 바이너리](fx.md)가
그 답이며, 파이프와 표준 입출력으로 조합하는 것을 값으로 삼는다.
다른 쪽 극단은 화면을 터미널 안으로 끌어들이는 방향이다 —
[IDE를 통째로 끌어들인 터미널 코딩 에이전트](omp.md)가 그 답이고,
셸을 떠나지 않은 채 파일 트리와 diff를 얻는다.
세 번째가 이 앱이며, 방향이 반대다 — 데스크톱 앱을 만들고 에이전트를 그 안에 넣는다.

세 답이 갈리는 지점은 어느 쪽이 주인인지에 대한 판단이다.
Unix 명령 방향은 에이전트를 도구 하나로 보고 조합 가능성을 지키며,
터미널 UI 방향은 셸이 작업 환경이라는 전제를 지킨다.
데스크톱 앱 방향은 그 둘을 포기하고 대신 창과 탭과 제스처를 얻는다.
여섯 패널 동시 실행과 독립 OS 창은 터미널에서도 가능하지만
탭 매니저나 tmux 설정을 사람이 해야 하고,
여기서는 앱이 그것을 기본값으로 제공한다.

그래서 이 세 답은 경쟁이 아니라 사용자 층의 분화로 읽힌다.
만든 사람이 언리얼과 Rider를 쓴다고 밝혔다는 점이 그 분화를 설명한다 —
게임 개발자의 기본 작업 환경은 셸이 아니라 무거운 IDE와 에디터이고,
그 환경에 tmux를 얹는 것은 자연스러운 선택지가 아니다.
Windows 10/11 전용이라는 제약도 여기서 나온다.
[Workflow 도구](claude-code-dynamic-workflows.md)를 백그라운드에서 완주시키는 기능이
이 앱의 차별점 중 하나인 이유도 같다 —
터미널을 계속 열어 두는 습관이 없는 사용자에게
턴이 끝나면 사라지는 오케스트레이션은 쓸 수 없는 기능이다.

### 다운로드가 별의 447배라는 비율이 이 프로젝트의 성격을 말한다

숫자를 나란히 놓으면 이례적이다.
별이 71개이고 누적 다운로드가 31,746건이므로 별 하나당 447건이다.
보통의 오픈소스 저장소에서 이 비율은 훨씬 낮고,
특히 소스를 받아 빌드하는 개발자 도구라면 별이 더 많은 편이다.

이 비율이 생기는 조건은 두 가지다.
첫째, 사용자가 GitHub 계정으로 저장소를 방문하는 사람이 아니라
설치 파일을 받아 쓰는 사람이라는 것이다.
릴리스 자산이 `.exe` 하나이고 자동 업데이트가 붙어 있으므로
한 사용자가 여러 번 다운로드에 계상되지만,
71개 릴리스 중 최신 두 개에만 655건이 몰려 있으므로
활성 사용자 규모가 별 개수보다 훨씬 크다는 결론은 유지된다.

둘째, 유입 경로가 GitHub이 아니라는 것이다.
GeekNews 소개글이 스타를 부탁하는 문장으로 끝나고,
유일한 댓글이 만든 사람 본인의 것인데
댓글은 달아 주지 않지만 스타는 많이 눌러 줘서 고맙다는 내용이다[^asdsa112].
스타 71개 중 상당수가 그 글에서 왔다는 뜻이고,
다운로드 31,746건은 다른 곳에서 왔다는 뜻이다.

이 격차가 개발자에게 실질적 문제를 만든다.
피드백 경로가 없다 — 열린 이슈가 0개이고 포크가 6개다.
3만 건의 다운로드가 있는데 이슈가 0개라는 조합은
사용자가 문제를 겪지 않는다는 뜻보다
문제를 보고할 곳을 모르거나 보고할 습관이 없다는 뜻일 가능성이 크다.
두 달에 71개 릴리스라는 속도가 그 공백을 혼자 메우는 방식으로 읽히고,
그 속도가 지속 가능한지가 이 프로젝트의 실제 위험이다.

## 비평

### 계정 여러 개를 한도 게이지와 함께 관리하는 기능은 약관 쪽 설명이 필요하다

이 앱의 차별 기능 중 하나가 계정 관리다.
엔진별로 구독 계정을 여러 개 등록하고 대화마다 계정을 지정하며,
각 계정의 남은 한도를 5시간·주간·Fable 단위 게이지로 보여 준다.
그리고 문서가 그 용도를 명시한다 — 여유가 있는 쪽으로 옮겨 가라는 것이다.
만든 사람이 이 앱을 Hacker News에 올릴 때 쓴 제목도
Claude Code와 Codex를 위한 다계정 데스크톱 GUI였으므로,
계정 관리가 부가 기능이 아니라 이 앱의 첫 소개 문구다.

기술적으로 이 기능은 정직하게 만들어졌다.
자격 증명을 DPAPI로 암호화해 저장하고 터미널 쪽 로그인과 분리하며,
시스템 전역 설정을 건드리지 않는다.
API 키 과금도 지원하므로 구독 계정만을 위한 기능도 아니다.
여러 계정을 정당하게 갖는 상황도 흔하다 —
개인 계정과 회사 계정, 프로젝트별로 분리된 조직 계정이다.

문제는 게이지의 설명 방식이다.
남은 한도를 보여 주는 것은 계정 관리이고,
여유가 있는 쪽으로 옮겨 가라고 안내하는 것은 한도 운용이다.
구독 요금제의 한도는 그 계정의 사용량 상한이고,
계정을 갈아타며 상한을 이어 붙이는 사용은 요금제의 전제와 어긋난다.
문서 어디에도 이 사용이 각 엔진의 약관에서 허용되는지에 대한 언급이 없고,
게이지가 다섯 시간 단위로 표시된다는 사실 자체가
이 기능이 어떤 사용 패턴을 겨냥하는지 알려 준다.

이 공백이 아쉬운 이유는 메우는 비용이 작다는 데 있다.
계정 전환이 조직 분리나 프로젝트 분리를 위한 것이라고 적고
같은 사람이 여러 구독을 한도 확장 목적으로 쓰는 것은
각 서비스 약관을 확인하라고 한 줄 덧붙이면 된다.
지금은 그 판단이 전적으로 사용자에게 있고,
앱은 판단에 필요한 숫자만 예쁘게 보여 준다.

README의 설치 절차 2번은 이렇다 —

“추가 정보 → 실행”으로 계속하라는 것이다.
같은 문서의 몇 줄 아래에 코드 서명 항목이 있고,
SignPath.io가 무료 코드 서명을 제공하고
인증서는 SignPath Foundation이 발급했다고 적혀 있다.

두 문단이 서로를 무효로 만든다.
서명을 받았으면 SmartScreen 경고를 우회하라는 안내가 불필요하고,
그 안내가 필요하면 서명이 실제 설치 파일에 적용되지 않은 것이다.
어느 쪽이 최신인지 읽는 사람은 알 수 없다.

이 어긋남이 사소하지 않은 이유는 이 항목이 신뢰의 문제이기 때문이다.
이 앱은 Claude와 ChatGPT 구독 계정의 OAuth 자격 증명을 다루고,
그것을 로컬에 암호화해 저장하며,
사용자의 소스 코드 전체에 접근한다.
그런 프로그램의 설치 파일에서 서명 경고를 무시하라고 안내하는 것은
사용자가 위조된 설치 파일을 구분할 방법을 없애는 것과 같다.
두 달에 71개 릴리스가 나오고 자동 업데이트가 붙어 있으므로
서명의 값은 오히려 이런 프로젝트에서 더 크다.

수정 방향은 명확하다.
서명이 적용된 릴리스가 어느 버전부터인지 적고
설치 절차의 경고 우회 안내를 지우면 된다.
서명이 아직 파이프라인에 붙지 않았다면
코드 서명 문단이 계획이라는 것을 밝히면 된다.
지금 상태는 둘 중 어느 것도 아니어서,
가장 확인이 필요한 항목이 가장 모호하게 남아 있다.

### 자기 저장소의 이슈가 0개라는 사실을 다루지 않는다

이 프로젝트에는 3만 건이 넘는 다운로드와 0개의 열린 이슈가 있다.
README에는 기여 안내도 없고 버그 신고 경로에 대한 문단도 없다.
GeekNews 글의 마지막 요청은 스타이고,
유일한 댓글에서 만든 사람이 아쉬워하는 것도 댓글이 없다는 점이다[^asdsa112].

이 상태를 그대로 두면 개발의 근거가 사라진다.
두 달에 71개 릴리스를 내는 속도는 무엇을 고칠지 알고 있어야 나오는데,
그 정보의 출처가 문서에 없다.
만든 사람이 자기 작업 환경에서 쓰면서 발견한 문제를 고치는 것이라면
그것은 1인 사용자를 위한 최적화이고,
3만 다운로드가 만드는 사용 패턴의 다양성과는 관계가 멀어진다.

이 프로젝트의 구조가 그 격차를 키운다.
LSP 뷰어가 TS·JS·Python·C#·C/C++·Unreal Verse를 지원하고,
언리얼 C++와 Verse 문서의 호버를 한국어로 번역하며,
C#은 어셈블리를 디컴파일한다.
이 조합은 특정한 한 사람의 작업 환경을 정확히 반영한 목록이고,
그것이 이 앱의 강점이기도 하다.
다만 그 목록 밖의 사용자가 다수가 되면
어떤 순서로 넓힐지 정할 근거가 필요해진다.

가장 값싼 장치가 이미 앱 안에 있다.
설정 화면에 오류를 보고하는 버튼과
사용 중인 언어를 알려 주는 항목을 두면
저장소로 오지 않는 사용자의 정보가 개발자에게 도달한다.
[에이전트가 붙은 도구에서 이런 계측이 표준이 되어 가는 흐름](harness-engineering.md)이
있으므로 새로운 요구도 아니다.
지금은 3만 건의 사용이 아무 신호도 남기지 않는다.

## 인사이트

### 에이전트 시대의 IDE 해체는 편집기부터가 아니라 편집기만 남기고 시작된다

이 앱이 보여 주는 것은 IDE의 해체 순서다.
가장 먼저 빠진 것이 편집기이고 가장 굳게 남은 것이 코드 읽기다.
탐색기, 심볼 해석, 정의 이동, 색상, 호버, diff가 전부 남았고
자동 완성과 리팩터링과 빌드와 디버거가 사라졌다.

이 순서가 직관과 반대다.
IDE의 정체성은 편집기였고 나머지는 편집기를 돕는 장치였는데,
작성이 에이전트에게 넘어가자 돕는 장치가 본체가 되었다.
그러면 이 도구 범주의 이름도 바뀌어야 한다 —
통합 개발 환경이 아니라 통합 검토 환경이다.

이 재배치가 만드는 2차 효과는 성능 요구의 이동이다.
편집기의 성능 요구는 입력 지연이었고 밀리초 단위였다.
검토 도구의 성능 요구는 다르다 —
에이전트가 스무 개 파일을 바꿨을 때 그 스무 개의 diff를
사람이 훑는 동안 끊기지 않는 것이며,
단위는 밀리초가 아니라 한 화면에 담기는 정보량이다.
이 앱이 변경 파일 체크리스트와 색·배지와 폴더 우클릭 수집을 만든 이유가 거기 있다.

그리고 이 이동이 오래된 도구들에 불리하게 작용한다.
기존 IDE는 편집기를 중심으로 20년간 최적화된 구조여서
읽기 전용 사용에서 그 구조의 대부분이 낭비로 남는다.
읽기만 하는 도구를 새로 만드는 쪽이 훨씬 가볍다는 사실이
이 앱의 존재 이유이고,
같은 논리가 앞으로 여러 개의 비슷한 도구를 만들어 낼 것이다.

### 백그라운드 완주가 오케스트레이션의 실사용 조건이었다

이 앱이 조용히 해결한 문제가 하나 있다.
터미널에서 여러 에이전트를 조율하는 워크플로를 돌리면
턴이 끝날 때 그 실행도 끝나는데,
이 앱에서는 워크플로가 백그라운드에서 완주하고 스스로 마무리 답변을 올린다.
개발 서버 같은 셸과 서브에이전트도 턴보다 오래 산다.

이것이 편의 기능으로 보이지만 실은 사용 가능성의 조건이다.
여러 에이전트를 병렬로 돌리는 이유는 시간을 절약하려는 것이고,
그 시간에 사람이 다른 일을 하려는 것이다.
그런데 사람이 다른 일을 하는 순간 세션이 끝나면
병렬 실행의 이점이 사라지고 사람이 대기하는 시간만 남는다.
[오케스트레이션을 스크립트로 기술하는 방식](claude-code-dynamic-workflows.md)이
표현력을 준다면, 백그라운드 완주는 그 표현력을 쓸 수 있게 만든다.

여기서 따라오는 것은 실행 소유권의 이동이다.
지금까지 코딩 에이전트의 실행 단위는 대화 세션이었고
세션의 수명은 사람이 그 창을 보고 있는 시간이었다.
실행이 세션보다 오래 살면 그 실행을 소유하는 것은 앱이 되고,
앱은 진행 상태와 결과와 실패를 보관할 책임을 갖는다.
알약과 단계 레일과 에이전트 보드가 그 책임의 UI이며,
토큰과 도구 호출 수를 에이전트별로 실시간 표시하는 것은
장시간 실행을 사람이 감시할 수 있게 만드는 최소 장치다.

그리고 이 이동이 다음 문제를 만든다.
실행이 사람의 주의보다 오래 살면 비용도 주의보다 오래 발생하고,
승인 카드가 필요한 순간에 사람이 화면을 보고 있지 않을 수 있다.
남은 한도 게이지가 이 앱에 있는 이유가 그 문제의 절반이며,
나머지 절반 — 자동 승인의 범위와 예산 상한 — 은
기능 목록에 권한 모드가 대화마다 지정된다는 한 줄로만 존재한다.
장시간 백그라운드 실행이 기본이 되면 그 한 줄이 가장 중요한 설정이 된다.

### 1인 개발자가 만든 랩퍼가 플랫폼 위험을 그대로 상속한다

이 앱의 구조는 명확한 랩퍼다.
Claude Code와 Codex CLI를 자동으로 설치하고,
설치된 엔진에서 모델 목록을 실시간으로 읽고,
그 엔진의 OAuth 로그인을 재사용한다.
새 모델이 나오면 선택기에 그냥 나타난다는 설명이 그 설계의 요약이다.

이 설계가 주는 이점은 유지 비용이다.
모델이 바뀌어도 코드를 고칠 필요가 없고,
엔진의 새 기능이 대체로 그대로 들어온다 —
Workflow 도구가 앱 안에서 그대로 동작한다는 문장이 그 증거다.
1인 개발자가 두 달에 71개 릴리스를 낼 수 있는 이유도 여기 있다.
어려운 부분을 만들지 않았기 때문이다.

그런데 같은 설계가 위험도 그대로 상속한다.
엔진의 CLI 인터페이스가 바뀌면 어댑터가 깨지고,
OAuth 재사용 방식이 막히면 계정 기능 전체가 무효가 되며,
구독 계정으로 서드파티 앱을 구동하는 것에 제약이 생기면
이 앱의 핵심 판매점인 API 키 불필요가 사라진다.
셋 다 이 개발자가 통제할 수 없고 예고 없이 일어날 수 있다.

역사적으로 이 위치의 도구들은 두 갈래로 갈렸다.
플랫폼이 그 기능을 흡수해 랩퍼가 불필요해지거나,
플랫폼이 공식 확장 지점을 열어 랩퍼가 그 위로 옮겨 갔다.
전자의 예가 많고 후자가 더 나은 결말인데,
후자로 가려면 랩퍼가 대체 불가능한 무엇을 갖고 있어야 한다.
이 앱에서 그것은 엔진 연동이 아니라
LSP 뷰어와 언리얼 문서 한국어 호버와 여섯 패널 관리다 —
엔진 제공자가 만들 이유가 없는 부분이며,
그래서 이 프로젝트가 오래 살려면 그쪽이 두꺼워져야 한다.

### 사용자가 3만 명인데 신호가 스타 71개뿐인 상태는 배포 방식이 만든다

이 프로젝트의 가장 특이한 숫자는 기능이 아니라 비율이다.
다운로드 31,746건, 스타 71개, 열린 이슈 0개, 포크 6개, 워처 0명이다.
소스가 공개된 MIT 프로젝트인데 관측되는 커뮤니티가 거의 없다.

이 상태를 만든 것은 배포 형태다.
릴리스 자산이 `.exe` 하나이고 자동 업데이트가 붙어 있으므로
사용자가 저장소를 두 번 방문할 이유가 없다.
소스를 읽을 이유도 없다 — 빌드해서 쓰는 것이 아니라 설치해서 쓴다.
오픈소스로 공개했지만 유통은 상용 데스크톱 앱의 방식이며,
그러면 커뮤니티 지표는 상용 앱처럼 0에 가까워진다.

이 조합이 흔해지는 흐름 안에 있다는 점이 중요하다.
Electron으로 만들고 GitHub Releases로 배포하고 자동 업데이트를 붙이는 구성은
1인 개발자가 데스크톱 앱을 유통하는 표준 경로가 되었고,
그 경로에서 GitHub은 배포 CDN 역할만 한다.
그러면 별과 이슈와 포크가 프로젝트의 건강을 나타낸다는
오랜 관행이 이 범주에서는 무의미해진다.

그래서 이런 프로젝트를 평가할 때 봐야 할 지표가 바뀐다.
릴리스 자산의 다운로드 수, 릴리스 간격, 최신 두 릴리스의 다운로드 비중이며,
셋 다 GitHub API로 얻어진다.
이 프로젝트의 경우 최신 릴리스가 하루도 안 되어 603건을 기록했으므로
자동 업데이트가 실제로 도는 활성 사용자 기반이 있다는 뜻이고,
그 사실이 스타 71개보다 훨씬 많은 것을 말해 준다.
같은 계산을 스타 수천 개짜리 저장소에 적용하면
반대 결과가 나오는 경우가 흔하며,
그 대조가 이 지표 전환의 값이다.
