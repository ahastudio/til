## 소개

REA(Reverse Engineer Anything)는 코딩 에이전트가 소스 코드 없이
프로그램을 들여다보게 해 주는 MCP 서버이자 CLI다.
README의 첫 문장은 앱에서 마음에 드는 기능을 보면
그것이 어떻게 동작하는지 바이너리 수준까지 이해하라는 것이다.
에이전트에게 다른 앱의 기능을 조사하게 하면 REA가 증거를 모아 주고,
에이전트는 그 증거로 동작을 설명하거나
자기 프로젝트에 비슷한 기능을 만든다는 구성이다.

저장소는 `morluto` 계정이 운영하며 TypeScript로 작성되었고 라이선스는 MIT다.
npm 패키지 이름은 `rea-agents`이고,
2026년 10월 11일에 나온 6.4.0이 최신 릴리스다.
변경 이력의 첫 항목인 0.2.0은 2026년 7월 12일이므로,
3개월 만에 메이저 버전을 여섯 번 올린 셈이다.
10월에 들어서는 4.0.0(10월 5일)부터 6.4.0(10월 11일)까지
일주일 사이에 릴리스가 아홉 번 나왔다.
6.4.0 한 번에만 336개 커밋과 163개 병합 PR이 들어갔다.

GitHub API 기준으로 10월 11일 현재 스타는 78,171개, 포크는 16,790개다.
README는 6만 스타 돌파를 감사하는 문구를 달았고,
한국어를 포함해 18개 언어 번역본을 둔다.
홈페이지 rea.tools는 설치 안내, 대상별 가이드, 사례 연구, FAQ,
블로그를 갖춘 별도 사이트다.
사례 연구와 블로그 글 상당수는 기여자 N0zoM1z0가 쓴 것으로,
그는 Touhou 시리즈 게임을 에이전트로 재구성하는 작업을 해 왔다.

## 동작 방식

### 에이전트, MCP 서버, 분석 엔진의 세 층

REA는 디컴파일러를 직접 만들지 않는다.
에이전트가 MCP로 REA를 부르면,
REA는 대상의 종류에 맞는 분석 엔진을 띄워 결과를 정리해 돌려준다.
네이티브 바이너리는 Hopper, Ghidra, IDA 중 하나를 쓰고,
Android APK는 헤드리스 JADX, 펌웨어는 Binwalk와 Unblob,
웹페이지는 Chrome 계열 브라우저의 DevTools Protocol을 쓴다.
JavaScript/Electron 앱과 .NET 어셈블리는
외부 엔진 없이 REA가 직접 정적 분석한다.
같은 기능을 `rea` CLI로도 쓸 수 있어서,
에이전트 없이 터미널에서 결과 JSON을 받아 볼 수 있다.

README가 정리한 분석 대상은 다음과 같다.

| 대상                 | REA가 돌려주는 것                                   | 필요한 것                   |
| -------------------- | --------------------------------------------------- | --------------------------- |
| 네이티브 바이너리    | 의사 코드, 어셈블리, 문자열, 심볼, 호출과 참조      | Hopper, Ghidra, IDA 중 하나 |
| JavaScript/Electron  | 모듈, import, 소스 맵, 라우트, IPC, 네이티브 애드온 | Node.js와 npm               |
| 웹사이트             | 페이지 구조, 스크립트, 네트워크 관찰, 스크린숏      | Chrome 계열 브라우저        |
| 저장된 네트워크 캡처 | 요청, 응답, 노출된 페이로드                         | HAR, Linux에서는 mitmdump   |
| .NET 어셈블리        | 메타데이터, CIL 명령어, 네이티브 의존성             | 없음(정적 분석만)           |
| Android APK와 기기   | 매니페스트, 클래스, 디컴파일된 메서드, 로그, 화면   | JADX와 JDK, adb             |
| 펌웨어               | 영역, 추출 결과, 네이티브 분석으로 넘길 대상        | Linux의 Binwalk/Unblob      |
| EVM 바이트코드       | 디스패치 셀렉터, 추정 인자, 상태 변경 여부          | Linux x64                   |
| 기록된 Linux 크래시  | 노트, 스레드별 레지스터와 시그널                    | pwntools, 선택적으로 GDB    |
| 프로세스 동작        | 터미널 출력, 상호작용, 종료, 파일 시스템 관찰       | Linux/macOS의 네이티브 PTY  |

REA 자체는 Node.js 22.19 이상, 24.11 이상 또는 26 이상을 요구한다.
이슈 #1554에 따르면 당시 소스 빌드 기준으로
MCP 도구의 입력 스키마는 139개였다.

### 스킬이 대상별 첫 도구를 고른다

설치하면 MCP 서버 등록과 함께 `reverse-engineer-anything` 스킬이 깔린다.
이 스킬은 도구 사용 설명서라기보다 조사 절차서에 가깝다.
첫 규칙은 소스 저장소 전체를 이미 가지고 있다면
REA를 쓰지 말고 평범한 저장소 도구를 쓰라는 것이다.
REA는 출하된 바이너리나 패키지, 디컴파일,
실행 중 관찰이 필요한 주장에만 쓴다.

그다음 스킬은 사용자가 준 대상에 따라 첫 도구를 정한다.
ASAR나 압축을 푼 Electron 앱이면 `analyze_javascript_application`,
APK면 `inspect_android_package`,
관리 코드 PE면 `inspect_managed_artifact`를 쓴다.
네이티브 실행 파일이면 `open_binary`로 세션을 연 뒤
`analyze_function` 같은 집중 도구로 들어간다.
사용자가 이름 없이 내 앱이라고만 하면 어떤 앱인지 먼저 묻고,
예제 앱을 사용자 대신 고르지 말라는 규칙도 들어 있다.

### 증거 원장과 요약 우선 조회

REA의 결과는 모두 Evidence라는 기록으로 남고,
각 기록에는 Evidence ID가 붙는다.
스킬은 모든 결론에서 관찰한 것, 추론한 것, 모르는 것을 구분하고
Evidence ID를 인용하라고 요구한다.
정적 분석으로 실행을 관찰한 것처럼 말하지 말라는 문장도 따로 있다.

큰 JavaScript 앱이나 ELF는 `"detail": "summary"`로 먼저 요약을 받고,
원장에 남은 부모 Evidence ID로 `inspect_analysis_view`를 불러
필요한 부분만 펼친다.
MCP 응답이 너무 커서 전송 제한에 걸려도 분석은 원장에 다 남아 있다.
그러니 같은 분석을 다시 돌리지 말고 뷰를 좁히거나
`export_evidence_bundle`로 파일에 쓰라는 것이 스킬의 지시다.
클라이언트가 결과를 잘라서 보여 주면
그 미리보기를 정식 JSON으로 파싱하지 말라는 경고도 있다.
에이전트의 컨텍스트 창이 한정되어 있다는 사실을
도구 설계 단계에서 다룬 셈이다.

여러 기능에 걸친 조사는 질문 목록을 먼저 만들고,
질문마다 필요한 증거 종류를 정하고,
끝날 때 각 질문을 답함, 부분적으로 답함, 미해결로 표시하게 한다.
독립된 질문은 병렬 작업자에게 나눠 주라는 지시도 들어 있다.

## 설치하기

기본 설치는 에이전트 설정까지 한 번에 하는 대화형 명령이다.

```bash
# 에이전트를 고르고, 변경 계획을 확인한 뒤 승인한다
npx rea-agents@latest setup

# 쓰기 없이 계획만 JSON으로 본다
npx rea-agents@latest setup --client claude_code --dry-run --json

# 특정 에이전트 등록이나 분석 엔진 하나만 점검한다
npx -y rea-agents@latest doctor --client claude_code --json
npx -y rea-agents@latest doctor --provider ghidra --json
```

설정 단계는 감지된 에이전트를 보여 주되,
새로 감지된 클라이언트는 기본으로 선택하지 않는다.
감지는 맥락일 뿐 등록 허가가 아니라는 것이 문서의 설명이다.
에이전트 설정 파일을 고치기 전에 백업을 만들고 원자적으로 교체하며,
기존 설정이 깨져 있으면 아무것도 쓰지 않고 전체 작업을 멈춘다.
MCP 등록은 설정을 실행한 정확한 버전에 고정되므로,
새 릴리스를 받으려면 설정을 다시 돌려야 한다.
Claude Code, Codex, Cursor, Gemini CLI, Windsurf, Devin, OpenCode,
GitHub Copilot CLI, Qwen Code 등 17개 클라이언트 ID를 지원한다.

분석 엔진 없이 바로 써 볼 수 있는 것은 JavaScript/Electron 정적 분석이다.

```bash
# 압축을 푼 앱 디렉터리나 .asar 파일을 넣는다
npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json
```

skills.sh에서 스킬만 받는 경로도 있다.

```bash
npx skills add morluto/rea --skill reverse-engineer-anything
```

이 경로는 지침만 설치하고 MCP 서버는 등록하지 않는다.
또 skills.sh는 저장소 main의 최신 지침을 가져오므로,
이미 등록된 서버에 없는 기능을 설명할 수 있다.
그래서 스킬도 실제로 연결된 서버의 도구 목록과 스키마를
기준으로 삼으라고 적는다.

네이티브 분석 엔진 중 Hopper는 별도 상용 소프트웨어다.
설정 단계에서 승인하면 공식 패키지를 내려받아 설치하고,
무료 데모 모드에는 제조사가 정한 제한이 있다.
Ghidra와 IDA는 이미 설치된 것을 연결만 하며,
REA는 Ghidra나 Java를 설치하거나 고치지 않는다.

이 문서를 쓰면서 REA를 직접 설치하거나 실행하지는 않았다.

## 사례

### Windows 계산기의 % 버튼

홈페이지의 첫 예제는 Windows 계산기에서
200 + 10%가 왜 220이 되는지 묻는 것이다.
REA는 설치된 계산기 DLL에서 % 처리 함수의 명령어와 디컴파일 코드를 돌려준다.
명령어는 연산자 값을 `0x5c`, `0x5b`와 비교해 분기하고 `0x64`, 곧 100을 쓴다.
Microsoft 공개 소스에서 `0x5c`는 곱셈(`IDC_MUL`),
`0x5b`는 나눗셈(`IDC_DIV`)이다.
곱셈과 나눗셈 뒤에서는 `current / 100`을,
그 밖에서는 `current * previous / 100`을 쓰므로,
덧셈 뒤의 10%는 200의 10%인 20이 된다.
검사는 REA 4.1.0과 Windows Calculator 11.2508.4.0 x64로 했다고 밝힌다.

### 공룡 게임과 DX-Ball

Chrome 공룡 게임 예제에서는
브라우저의 로컬 디버깅 연결로 실제 로드된 `index.js`를 받는다.
그 안에서 속도가 6에서 시작해 갱신마다 0.001씩 늘고
13에서 멈춘다는 규칙을 찾는다.
원래 갱신 함수를 통제된 브라우저에서 4,000번 부르면 속도 10.0,
10,000번 부르면 13.0이 되는 것까지 확인했다.

DX-Ball 사례는 1996년 Windows 게임을 실행 파일에서 C로 재구성하는 프로젝트다.
벽돌이 깨질 때 소리를 좌우로 나누는 함수에서
디컴파일러는 입력 없는 `__ftol()` 호출만 보여 줬다.
에이전트는 명령어 뷰에서 `[EBP+8]` 입력을 찾고,
호출자를 따라가 그 값이 `20 + 30 × tile_x`라는 화면 좌표임을 알아냈다.
이어서 `read_bytes`로 상수 1.5625와 500.0을 읽어 C 함수를 만들었다.
10월 7일 기준으로 C 함수 55개, 원본과의 비교 45,380건,
컴파일 바이트가 일치하는 함수 33개를 기록했다.

### Touhou 재구성과 검증 오라클

블로그 글 The industrial revolution in reverse engineering에서
N0zoM1z0는 TH08, TH095, TH04 재구성 경험을 적는다.
TH095는 8월 29일 확인된 함수 0개로 시작해
9월 7일 697개 함수 전부의 소스를 갖췄고,
9월 10일 Windows i386 재구성이 플레이 가능한 상태가 되었다.
그는 에이전트에게 조사의 자율을 주되 목표와 합격 기준은 사람이 정하고,
저장소와 Git을 작업 기억으로 쓰라고 정리한다.

이 글에서 가장 쓸모 있는 부분은 검사 도구 자체가 틀린 사례다.
TH08의 아이템 자동 수집 조건에서
원본은 최대 파워 128.0과 비교하는데 재구성 소스는 0.0과 비교했다.
그런데 이 함수는 이미 원본과 정확히 일치한다는 비교를 통과한 상태였다.
비교 도구가 주소 차이를 보정하면서
그 주소에 담긴 부동소수점 값은 확인하지 않았기 때문이다.
이후 부동소수점 리터럴 참조 1,548개를 감사해,
이미 통과한 함수 다섯 개에서 잘못된 참조 열두 개를 더 찾았다.

HN에서 InvisibleUp은 TH04 디컴파일 결과가
지금까지 본 AI 디컴파일보다 품질이 훨씬 좋다고 평가하면서도,
파일 구조가 원 개발자의 의도보다 AI 작업에 맞춰져 있다고 지적했다.[^InvisibleUp]

### 한글과 Word를 합친 워드프로세서

국내에서도 REA를 쓴 사례가 나왔다.
Threads 사용자 aijossi는 2026년 10월 14일 REA의 실제 활용 사례라며
한글 2022와 MS Word에 AI 자동 작성 에이전트를 합친
“탄글2026”이라는 프로그램을 소개했다.
그는 이 프로그램을 개인용, 교육용으로 만들었고,
기존 프로그램의 소스 코드를 한 줄도 가져오지 않고
REA를 활용해 Rust로 빌드했다고 밝혔다.
나쁜 사람 손에 들어가면 안 될 것 같다는 소감도 덧붙였다.[^aijossi]
프로그램 자체는 공개되지 않아 동작 범위나 완성도는 확인할 수 없다.

반응은 신기하다는 쪽과 무섭다는 쪽으로 나뉘었다.
왜 무서운지 묻는 cjg7670에게 j.wo_on은
REA를 쓰면 기존 프로그램을 비슷하게 복사할 수 있다고 답했다.[^cjg7670][^j-wo-on]
이 문답이 아래 법적 논점의 핵심을 그대로 보여 준다.
소스 코드를 옮기지 않았다는 말과
바이너리를 분석해 동작을 다시 만들었다는 말은 서로 다른 주장이고,
echelon이 말한 클린룸 구현은 앞의 것만으로는 성립하지 않는다.

## 트레이드오프

### 법적 판단은 전부 사용자에게 넘어간다

README의 면책 문구는 REA가 합법적인 역공학 연구, 분석, 재구성을 위한 도구이며,
필요한 허가를 얻고 법을 지키는 책임은 사용자에게 있다고 적는다.
도구가 하는 일은 그게 전부다.
설치 과정이나 스킬 어디에도 대상의 라이선스나 이용 약관을 확인하는 단계는 없다.
홈페이지가 내세우는 사용법은 남의 앱에서 본 기능을 내 제품에 만드는 것이다.
가장 위험한 판단을 도구가 가장 덜 돕는 구조다.

HN에서 jasomill은 역공학에는 보안과 무관한 이유가 수없이 많고
법이 명시적으로 허용하는 경우도 있다고 했다.
그러면서 상용 소프트웨어 역공학은 대개 라이선스 계약 위반이라,
계약 위반과 저작권 청구에 노출될 수 있다고 짚었다.[^jasomill]
Photoshop, Word 같은 앱을 모델로 한 오픈소스 앱을 만드는 echelon은
자신들은 바이너리를 디컴파일하지 않고 클린룸으로만 만든다고 밝혔다.
그는 이렇게 눈에 띄는 작업에 REA를 쓰면 소송을 부를 가능성이 높다고 봤다.
결과를 공개했는데 증거 개시 과정에서 원본을 디컴파일한 사실이 드러나면
곤란해질 것이라며,
REA는 개인용 앱이나 버려진 소프트웨어에 어울린다고 했다.[^echelon]
그 회사의 앱 하나는 이 저장소의 `design/photocraft.md`에서 다룬다.

Retr0id는 DRM 해제에 대해서는 긍정적이라고 했다.
DMCA 때문에 해제 작업을 공유하기 어려웠지만,
이제는 누구나 에이전트에게 처음부터 다시 하라고 시킬 수 있으니
공유할 필요 자체가 사라진다는 것이다.[^Retr0id]
이것은 법이 막던 지점을 도구가 돌아가는 방식으로 읽힐 수 있고,
그 결과 생기는 책임은 여전히 개인에게 남는다는 것이 이 문서의 해석이다.

모델 쪽 제약도 있다.
Scaevolus는 지금 모델들이 역공학과 디컴파일 자체는 막지 않지만,
버그를 찾으라고 하면 거절될 가능성이 높다고 했다.[^Scaevolus]
Retr0id는 게임에서는 Opus 5.5가 문제없지만,
DRM과 라이선스 검사에서는 이전 모델로 내려가야 한다고 적었다.[^Retr0id-2]
도구의 경계가 아니라 모델 제공자의 정책이 실제 사용 범위를 정하고,
그 정책은 예고 없이 바뀐다.

### 실행과 파싱을 감싸는 샌드박스가 없다

REA는 한때 권한 장치를 키웠다가 걷어 냈다.
이슈 #96은 한 번 허용, 세션 동안 허용, 프로젝트에 기억, 거부의
네 단계로 범위를 정해 허가하는 체계를 제안했고,
2.1.0(7월 18일)에서 프로세스 캡처에 MCP elicitation 기반 허가가 들어갔다.
그러나 4.0.0(10월 5일)에서 권한 설정과 정책 명령, 승인 필드,
파일 시스템 범위 입력을 모두 제거했고,
프로세스 캡처는 호스트 환경을 그대로 물려받게 되었다.
지금 스킬은 REA가 권한 부여나 호출별 승인을 요구하지 않으며,
승인은 에이전트 클라이언트가 따로 할 수 있다고 적는다.

SECURITY.md는 경계를 분명히 밝힌다.
분석 엔진 브리지 세션은 무작위 토큰과 현재 사용자 전용 Unix 소켓으로 인증한다.
그러나 이것은 샌드박스가 아니며,
같은 사용자로 이미 돌고 있는 악성 프로세스는 막지 못한다.
신뢰할 수 없는 바이너리를 열면
그 파싱과 분석은 사용자 권한으로 도는 분석 엔진에 그대로 맡겨진다.
Ghidra 세션은 격리된 임시 프로젝트와 별도 홈, 캐시 디렉터리를 쓰지만
이것도 샌드박스는 아니라고 적는다.
프로세스 캡처 문서 역시 명령이 현재 사용자 권한으로 실행된다고 밝힌다.
관찰 경로는 무엇을 스냅숏할지 정할 뿐,
프로세스가 읽고 쓰는 범위를 제한하지 않는다.

이 구조에서 에이전트에게 바이너리를 맡길 때의 위험은 두 겹이다.
하나는 의심스러운 바이너리를 열거나 실행하는 행위 자체이고,
다른 하나는 바이너리에 담긴 문자열과 코드가
도구 결과로 에이전트의 컨텍스트에 들어간다는 점이다.
README와 SECURITY.md는 앞의 것은 다루지만,
분석 대상이 에이전트에게 지시처럼 읽히는 뒤의 문제는 다루지 않는다.
악성코드나 출처를 모르는 실행 파일은 VM 안에서 다루는 편이 맞고,
에이전트에게 VM을 따로 주는 방식은 `mac/vmpal.md`에서 볼 수 있다.

### 분석은 로컬이어도 결과는 모델 제공자에게 간다

FAQ는 REA가 대상을 사용자 컴퓨터에서 분석한다고 답하면서,
에이전트가 받는 결과에는 모델 제공자의 데이터 정책이 적용된다고 덧붙인다.
디컴파일한 의사 코드, 문자열, 네트워크 캡처의 페이로드가
모두 모델 API로 넘어간다는 뜻이다.
회사 내부 바이너리나 고객 데이터가 담긴 캡처를 분석할 때는
앱을 올리지 않는다는 말만 보고 안심할 수 없다.
브라우저 관찰 도구가 쿠키와 authorization 헤더를 보관하지 않는 것처럼
일부 출력은 걸러지지만,
걸러지는 범위는 도구마다 문서를 확인해야 한다.

### 설치를 에이전트에게 맡기는 방식

홈페이지는 설치 명령을 에이전트에 붙여 넣을 문장으로 제시한다.
`npx rea-agents@latest setup`으로 설치하고,
설정 계획을 보여 주고 승인받은 뒤 검증하라는 내용이다.
HN에서 mb7733은 이것을 `curl | bash`의 다음 진화라고 비꼬았고,[^mb7733]
OptionX도 가장 나쁜 의미에서 `wget X | bash`의 진화라고 했다.[^OptionX]

REA 쪽 안전장치는 사람이 보는 계획과 승인이다.
다만 에이전트에게 설치를 시키면 그 계획을 읽는 주체가 에이전트가 되기 쉽다.
Hopper 설치 경로에도 남은 구멍이 있다.
SECURITY.md는 Linux에서 Hopper가 공개한 SHA-1 값으로 다운로드를 비교하지만,
이것은 손상 검사일 뿐 현대적인 패키지 서명이 아니라고 인정한다.
macOS 설치 과정이 내려받은 앱의 서명자가 누구인지 고정하지 않는다는 문제는
이슈 #1681에서 아직 논의 중이다.

### 빠른 릴리스는 계약을 자주 깬다

README는 REA가 빠르게 바뀌고 버그 수정이 잦으니 계속 업데이트하라고 권한다.
깨지는 변경이 6.3.0에 여덟 항목, 6.4.0에 아홉 항목이다.
그중 여럿은 이전에 저장한 Evidence가
새 스키마에서 더 이상 검증되지 않는다는 내용이다.
조사 결과를 오래 보관하며 다시 열어 볼 생각이라면,
버전을 고정하거나 원래 캡처를 따로 보관해야 한다.

MCP 등록이 버전에 고정되는 것은 이 속도를 감당하기 위한 장치다.
그러나 스킬은 저장소 main을, 서버는 고정 버전을 따르는 식으로
둘이 어긋날 수 있다.
6.3.0에서는 문서에 적힌 일부 클라이언트 설정이 npm 패키지에 빠져 있었다.
이 문제는 이슈 #1650에서 추적했다.

### 도구 카탈로그가 컨텍스트를 차지한다

REA는 사용할 수 없는 도구까지 포함해 전체 카탈로그를 항상 노출한다.
이슈 #1554는 GitHub Copilot CLI에서 `gpt-4.1` 메타데이터로 설정했을 때,
REA를 켜기만 해도 정적 시스템 메시지와 도구 정의가
모델의 컨텍스트 예산을 넘겨 평범한 대화조차 실패한다고 보고했다.
6.4.0은 Kimi/Moonshot처럼 크기 제한이 있는 클라이언트를 위해
`REA_MCP_INPUT_SCHEMA_PROFILE=compact`를 추가했다.
작은 모델이나 로컬 모델로 쓸 계획이라면 이 설정부터 확인해야 한다.

### 검증 오라클도 틀린다

TH08 사례가 보여 주듯, 에이전트가 만든 결과를 믿는 근거는 결국 검사 도구다.
N0zoM1z0는 사람 한 명이 에이전트와 일하는 팀에서는
모든 줄을 직접 볼 수 없으므로 신뢰의 상당 부분이 검사에 달려 있다고 적는다.
그래서 검사 도구가 놓치는 것이 있으면 그 결함이 수백 개 함수로 퍼진다.
그의 처방은 오라클에도 일부러 틀린 값을 넣어 거부되는지 시험하고,
결함을 찾으면 그 검사를 통과했던 이전 결과를 다시 보는 것이다.

REA 자체가 이 오라클을 제공하지는 않는다.
REA는 명령어, 의사 코드, 바이트를 돌려줄 뿐이고,
원본과의 비교, 당시 컴파일러로의 빌드,
실행 테스트는 재구성 프로젝트 쪽이 갖춰야 한다.
DX-Ball의 45,380건 비교도 REA가 아니라 재구성 저장소의 테스트다.

N0zoM1z0는 그 노력을 존중한다고 하면서도,

그 LLM에 대한 접근이 독점 소프트웨어보다 더 불공평하게 나뉠 수도 있다고
적었다.[^elliotmorris]

## 기억할 원칙

### 도구가 넘겨준 책임은 사용자 쪽에서 다시 세워야 한다

REA는 권한 확인을 걷어 내고 승인을 에이전트 클라이언트에 맡겼으며,
법적 판단은 면책 문구 한 단락으로 사용자에게 넘겼다.
도구의 마찰을 줄이는 선택으로는 이해할 수 있지만,
그만큼 사라진 확인 단계는 사용자가 다시 만들어야 한다.
격리된 실행 환경, 대상별 법적 검토, 모델에 보낼 데이터의 선별은
REA가 대신해 주지 않는다.

### 에이전트를 믿는 근거는 검사이고, 검사도 검사해야 한다

역공학에서 에이전트가 빠른 이유는
가설을 세우고 실패하고 다시 시도하는 고리를
사람이 붙잡고 있지 않아도 되기 때문이다.
그 고리가 믿을 만한지는 비교와 실행 테스트가 정한다.
TH08의 128.0 사례처럼 검사가 놓치는 것은 통과한 결과 전체에 조용히 퍼지므로,
검사 도구에도 일부러 틀린 입력을 넣어 보는 습관이 필요하다.
