# Claude Code 팀이 검증을 생각하는 방식

원문: [How the Claude Code team thinks about verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

HN 토론: <https://news.ycombinator.com/item?id=50529612> (280점, 224개 댓글)

GN 토론: <https://news.hada.io/topic?id=37359>

## 요약

claude.dev 블로그의 2026년 11월 16일 엔지니어링 글이다. 필자는 Addy Osmani이다.
이 문서는 본문 전체를 읽었다. 글이 가리키는 다른 글(코드 리뷰 글)과 영상은 열지 않았다.
모든 내용은 필자와 Claude Code 팀의 자기 보고이며 내부 수치는 이 문서가 확인하지 못했다.
같은 블로그의 코드 리뷰 글을 다룬 문서가 따로 있고, 이 글은 그 글이 가리키는 후속 글이다.

글의 전제는 이렇다.
Claude Code 팀의 코드는 약 90%를 Claude가 쓰고 검토한다고 한다.
이 규모에서는 에이전트가 증거와 함께 자기 작업을 검증하게 하는 방법이 중요하고,
검증 루프가 있어야 한 번에 한두 개가 아니라 수십, 수백 개의 Claude를 병렬로 돌릴 수 있다고 한다.
내부 시험에서 구조화된 파일 생성 과제에 별도의 채점자가 루브릭으로 확인하게 하자 일반 프롬프트 루프보다 성공률이 최대 10포인트 올랐고, 어려운 문제에서 효과가 컸다고 한다.

글은 어떤 테스트에 투자할지 세 가지를 든다.

- E2E 테스트: 하나만 고르라면 이것이다. 실제 사용자 흐름(장바구니, 결제, 확인 화면)을 재현해 기능이 전체로 동작하는지 속이기 어렵게 판정한다. 단위 테스트는 빠르고 덜 불안정하지만 통과하고도 기능이 깨질 수 있다. 에이전트에게 CDP, 시뮬레이터, API 하네스로 앱을 띄우고 조작하고 살펴보는 스킬을 주라고 한다.
- 속성 테스트(property test): fast-check, Hypothesis, proptest 같은 라이브러리로 깨질 수 없다고 믿는 문장에 대한 반례를 수천 개 생성한다. 왕복 인코딩, 불변식, 멱등성, 최적화 코드와 단순 정답 코드의 동등성이 예이다. 에이전트가 쓴 코드와 같은 편향 없이 만든 경계 사례로 에이전트를 감시하는 방법이다.
- 차분 테스트(differential test): 옛 시스템을 정답 기준(oracle)으로 같은 입력을 두 시스템에 넣어 결과를 비교한다. 대규모 이전에 효과적이고, 무작위 입력이나 운영 트래픽 표본을 쓰며 공백 같은 무관한 요소를 정규화하고 승인된 차이 목록을 둔다.
- 피할 실패: 불안정한 테스트는 에이전트에게 코드를 고치는 대신 다시 돌리는 습관을 가르치고, 느린 테스트는 에이전트가 적게 돌리게 만든다.

Claude Code 팀의 실천은 다음과 같다.

- 검증은 변경을 실행하는 것이다: 웹은 Chrome 확장, 모바일은 iOS나 Android MCP, 데스크톱은 컴퓨터 사용, 백엔드는 로컬 실행으로 확인한다. `verify`라는 스킬을 저장소 `.claude/skills/`에 두고, 관련 코드에 가깝게 여러 개를 두며, 빠르고 안정적으로 만들라고 한다.
- 실패한 테스트가 사람의 주의를 부른다: 세 번 시도해도 실패하면 Claude가 멈추고 사람을 부른다.
- 코드 소유자가 검사를 쓴다: 소유자가 표시했을 것을 표시할 때까지 다듬고, 검사가 리뷰어를 부를 때는 이유를 적는다.
- 신뢰성 체크리스트: 39개 항목이 각각 diff에서 읽을 수 있는 트리거, 검사, 근거가 된 사고나 PR을 가진다. Claude가 diff를 읽고 트리거가 맞는 항목(보통 3개에서 10개)만 검사한다.
- 리뷰어는 하나, 여러 라운드: 리뷰어를 더 쌓기보다 주 리뷰어를 조정하고, `REVIEW.md`에 이 코드에서 주의할 점을 적고, 라운드마다 앞선 맥락과 과거 실패를 가리킨다.
- 변경이 자기 검사를 고칠 수 없다: Code Review는 `REVIEW.md`를 PR이 아니라 기준 브랜치에서 읽는다. 오래된 커밋에서의 통과는 의미가 없다. 값싼 검사(테스트, 빌드, 린터)를 먼저 돌린다.
- 새 게이트는 관찰 모드로 시작: 각 커밋에 어떻게 검증했는지 도장을 찍고(없음 포함), `/code-review`나 `/verify`가 세션에 없으면 막는 게이트를 off, observe, enforce 모드로 운영한다. 세션에서 두 번 막히면 다음은 통과시켜 Claude가 갇히지 않게 한다.
- 검사 자체를 평가한다: 되돌려진 병합 변경 수, 병합 전 유지보수자가 거부한 변경 수, 크기를 맞춘 깨끗한 대조군을 추적한다. 과거 사고와 되돌림으로 평가 세트를 만들고 한 문장짜리 정답 키로 버그를 정확히 서술한 발견만 점수로 쳤고, 튜닝 세트와 고정 시험 세트를 나눴고, 원시 발견, 검증 뒤, 최종 리뷰의 재현율을 따로 잰다. 중요도는 Important, Nit, Pre-existing으로 나눈다.
- 놓친 것을 규칙으로: 사람의 리뷰 댓글과 되돌림에서 두 개 이상의 PR에 나오고 diff로 식별되는 패턴을 뽑아 에이전트 셋이 반증을 시도한 뒤 사람이 승인한다. 알려진 사고 PR에 버그 탐지기 셋을 재생해 둘 이상이 찾으면 탐지 가능한 버그로 본다. 불안정한 테스트는 건너뛰기, sleep, 재시도로 통과시킬 수 없고, 원인을 못 찾으면 삭제하고 이유를 적는다. 규칙도 주기적으로 정리한다.

결론은 검증 계층을 다른 시스템처럼 다루라는 것이다. 판정 대상인 변경이 건드릴 수 없는 곳에 두고, 실제 중요했던 버그로 채점하고, 놓친 것은 교훈으로 적고, 교훈을 정리하라고 한다.

## 분석

### 중심 주장은 검증이 위임의 전제 조건이라는 것이다

글은 검증 루프를 사람이 모든 것을 확인해야 하는 한계를 풀어 주는 구성 요소로 놓는다.
사람의 일이 diff를 읽는 것에서 완료의 기준을 정하고 증거를 검토하는 것으로 옮겨 간다는 서술이다.
이는 글의 서술을 이 문서가 압축한 것이다.

### 실천 대부분이 검증을 에이전트로부터 분리하는 설계이다

기준 브랜치에서 읽는 `REVIEW.md`, 변경이 자기 검사를 고칠 수 없다는 규칙, 속성 테스트의 편향 없는 입력, 차분 테스트의 옛 시스템 정답 기준은 모두 판정하는 쪽과 판정받는 쪽을 가르는 장치이다.
글은 판정자가 피판정자의 영향을 받으면 검사가 망가진다고 한다.
이 묶음은 이 문서의 분류이다.

### 도입은 단계적이다

게이트를 관찰 모드에서 시작해 거짓 양성을 먼저 보고, 두 번 막히면 통과시켜 에이전트가 갇히지 않게 하는 점은 현실적인 설계이다.
글은 Claude Code가 완벽하지 않다고 스스로 쓴다.

## 비평

### 비용 서술이 빠져 있다

HN에서 가장 많은 반응을 얻은 지적은 이 글이 무제한 토큰을 가진 쪽의 글처럼 읽힌다는 것이었다.
한 사용자는 변경마다 스킬 파일로 검증하고 Chrome 도구로 회귀를 보는 방식이 비싼데 거의 공짜인 방법(정적 분석 같은 값싼 결정적 검사를 먼저)이 같거나 나은 결과를 낸다고 했다.[^othershrezzing]
다른 사용자는 같은 취지의 강연을 소개하며 값싼 결정적 검사를 첫 단계로 두라는 요지를 전했다.[^xnorswap]
또 다른 사용자는 이런 글이 거리가 먼 고객의 결과를 높이면서 토큰 사용을 늘려 매출을 키우는 마케팅이라고 주장했다.[^svnt]
이 주장은 동기에 대한 추측이다. 글의 사실 서술이 틀렸다는 근거로 제시된 것은 아니다.
글은 병렬 수십, 수백 개의 에이전트를 말하지만 그 비용은 말하지 않는다. 한 사용자는 한두 에이전트만으로 한 달에 2,000달러를 쓴다고 했다.[^girvo]

### 모든 변경을 읽는 것이 불가능하다는 전제가 논쟁적이다

글은 아무도 모든 변경을 읽을 수 없으므로 실패를 사람 개입의 기준으로 쓴다고 한다.
HN에서 한 사용자는 사람이 모든 diff를 검토할지는 프로젝트 차원의 의식적 결정이고, 변경을 충분히 작게 쪼개면 가능하다고 반박했다.[^koolba]
다른 사용자는 코드는 만들기 싸고 유지보수가 비싸다는 점을 잊고 있다고 했다.[^thefunnyman]
글의 전제는 이 팀의 규모에서 나온 것이고, 다른 팀의 선택지는 다를 수 있다.

### 결정적 검증과 에이전트 검증의 경계

한 사용자는 에이전트에게 테스트용 스킬을 달아 주는 대신 직접 돌릴 수 있는 스크립트를 만들게 하라고 했다. 알고리즘이 에이전트보다 낫다는 주장이다.[^titzer]
다른 사용자는 스크립트는 토큰을 쓰지 않으므로 업체가 장려할 유인이 없다고 했다.[^duskdozer]
글도 속성 테스트와 차분 테스트, 린터 같은 결정적 검사를 권하므로 이 논쟁은 비중의 문제에 가깝다.
글에서 에이전트에게 조작하게 하는 E2E 검증과 스크립트로 굳힌 검증 사이의 균형이 명시되지는 않는다.

### 자사 제품의 신뢰성에 대한 반응

한 사용자는 Claude Code가 이제 신뢰할 만한 소프트웨어인지 물었고, 한 사용자는 파일 브라우저와 diff 뷰어 같은 주변 기능이 불안정하다고 답했으며,[^tshaddox][^kevincox] 다른 사용자는 데스크톱 앱이 이제 훌륭하다고 했다.[^jrflo]
제품의 열린 이슈가 1만 6천 개라는 지적에는 닫힌 이슈가 9만 개라는 반박이 달렸다.[^dotdi][^laichzeit0]
이 수치들은 댓글 작성자가 말한 것이며 이 문서가 확인하지 못했다.
글의 주장(검증으로 품질을 올린다)을 제품 품질로 직접 확인하는 방법은 글에 없다.

### 에이전트가 쓰는 테스트의 질 문제

HN에서 여러 사용자가 Claude가 쓰는 테스트가 쓸모없다고 불평했다. 구조체의 필드 읽고 쓰기만 확인하거나, 모든 함수를 모킹하거나, 오류 문자열을 검사한다는 것이다.[^anshumankmr][^bmitc]
이는 글의 속성 테스트와 E2E 권고가 가리키는 문제와 같은 쪽이다. 에이전트가 쓴 테스트를 누가 검증하느냐는 질문은 글에서 직접 답하지 않는다.
글은 불안정한 테스트와 낡은 규칙을 정리하라고 말할 뿐이다.

### 외부 반응

HN 스레드는 280점 224개 댓글이다.
톤이 냉소적인 댓글이 많았다. 팀이 무엇을 생각하느냐는 말장난이나 이 팀이 아무것도 생각하지 않는다는 단정은 근거가 없어 이 문서는 다루지 않았다.
Lobste.rs에서는 `claude.dev` 도메인에 코드 리뷰 글 하나만 올라왔고 이 글은 없다.
GeekNews에는 같은 글의 토픽이 있으나 댓글이 하나이고, 그것도 HN 댓글을 다시 모은 GN⁺ 계정의 요약이라 GeekNews 이용자의 반응은 없다.

## 인사이트

### 가져갈 것은 검증을 판정받는 쪽이 건드릴 수 없는 곳에 두는 원칙이다

자기 팀에서 바로 옮길 수 있는 것은 세 가지이다.
검사 설정(규칙 파일, 평가 기준)을 변경이 아니라 기준 브랜치에서 읽게 하고,
새 게이트는 관찰 모드로 켜서 거짓 양성을 본 뒤 강제로 올리고,
검증 결과(어떻게 확인했는지, 없음 포함)를 커밋에 기록하는 것이다.
이는 이 문서의 적용이며 이 문서가 시험하지 못했다.

### 값싼 결정적 검사를 앞에 둔다

HN의 비용 지적을 받아들이면 순서는 정적 분석과 타입, 린터, 속성 테스트 같은 값싼 결정적 검사 다음에 에이전트가 앱을 직접 조작하는 E2E 검증이다.
글도 값싼 검사를 먼저 돌리라고 하지만 비중이 에이전트 조작 쪽으로 기운다.
어디에 비용을 쓰는지는 팀의 토큰 예산과 변경의 위험에 달려 있다.

### 확인할 관찰

이 글의 주장을 가를 관찰은 세 가지이다.
검증 루프가 있는 팀과 없는 팀의 결함률과 되돌림 비율의 비교(글의 10포인트는 내부 시험의 구조화 파일 생성 과제 하나이다),
이런 검증 구성이 병렬 수십 개 에이전트를 돌릴 때의 총비용,
에이전트가 쓴 테스트의 질을 측정하는 방법이다.
셋 모두 이 문서가 확인하지 못했다.
