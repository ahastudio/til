# 에이전트에게 필요한 것은 메모리가 아니라 문서다

원문: [Agents Don't Need Memory. They Need Documentation. | Kevin Liao](https://liao.gg/blog/agents-dont-need-memory)

HN 토론: <https://news.ycombinator.com/item?id=49945933> (354점, 248개 댓글)

GN 토론: <https://news.hada.io/topic?id=34750>

## 요약

Kevin Liao가 2026년 10월 3일 블로그에 쓴 글이다.
글은 메모리 플러그인이 하는 일을 묘사하며 시작한다.
대화를 분석해 서로 떨어진 조각 1,000개를 만들어 벡터 데이터베이스에 넣고,
프롬프트마다 가장 비슷한 조각 다섯 개를 붙이며,
에이전트가 헷갈리면 직접 더 검색하게 한다.
저자는 사용자가 원하는 것은 에이전트가 프로젝트를 이해하는 것,
즉 기능이 어디 있고 왜 만들었고 무엇에 합의했고
무엇을 중요하게 여기는지 아는 것인데,
받는 것은 RAG 조각의 복권 추첨이라고 쓴다.
그래서 메모리 플러그인 생태계 전체가 잘못된 문제를 풀고 있으며,
에이전트에게 필요한 것은 메모리가 아니라 문서라고 주장한다.

저자에 따르면 시중의 메모리 플러그인은 모두 같은 구조다.
세션 기록을 훑고, 기억 조각을 만들어 RAG 데이터베이스에 넣고,
프롬프트마다 상위 다섯 개를 꺼내 주입하고,
더 필요하면 에이전트에게 검색 도구를 준다.
과거 기록을 글자 그대로 검색하게 하거나, 단기와 장기 메모리를 나누거나,
기억을 검토하고 합치고 중복을 없애는 백그라운드 데몬,
밤새 기억을 고쳐 쓰는 “Dreamer”, 지속적인 컨텍스트 압축,
리랭커(reranker)를 더하는 변형이 있지만,
모두 같은 결함 있는 구조 위에 토큰을 태우는 기능을 얹을 뿐이라고 한다.

글은 이 구조의 문제를 다섯 가지로 든다.
기억은 유사도로만 떠오르기 때문에 무엇이 맞고, 최신이고, 빠졌는지 알 수 없다.
조각에는 맥락, 동기, 교훈, 환경이 담기지 않는다.
과거를 진실로 취급하지만 코드베이스는 매일 바뀌어서,
인증에 관한 조각 500개가 각각 얼마나 정확한지 알 수 없다.
에이전트는 자신이 모르는 것을 검색할 수 없다.
SQLite 안의 임베딩 10,000개는 감사할 수 없어서,
어떤 기억이 낡았고 한 번도 쓰이지 않았고
몰래 에이전트를 잘못 이끄는지 알 수 없다.
저자는 이 문제들의 뿌리가
에이전트가 잊는 것이 문제이니 더 잘 기억하면 된다는 가정이라고 본다.
아무도 기능의 제약을 떠올리려고 3년 전 팀 회의를 다시 보지 않고,
사람은 적어 두고 그 기록을 쓴다는 비유가 뒤따른다.

대안으로 저자는 문서 기반 메모리를 제시한다.
AGENTS.md는 에이전트가 코드베이스에 눈을 감고 뛰어들지 않게 하려고 생겼고
효과도 있지만, 많은 경우 그 파일 하나가 프로젝트의 유일한 문서다.
저자는 파일 하나로는 부족하고 에이전트에게 지시, 명세, 결정, 조사, 색인을
요청 없이도 기록할 수 있는 구조화된 작업 공간, 곧 “brain”이 필요하다고 쓴다.
에이전트는 작업 전에 이 공간에서 관련 문서를 읽고,
작업 후에 전체 그림이 아직 컨텍스트에 있을 때
낡은 문서를 고치고 새 문서를 더한다.
그러면 루프가 prompt → build → forget에서
prompt → consult → build → update로 바뀐다는 것이다.

저자는 1년여 전 AI로 프로그래밍을 시작하면서
`internal/` 폴더를 만들고 에이전트에게 명세, 계획, 색인을 모두 적게 했고,
작업 전에 문서와 색인을 읽고 작업 후에 갱신하게 했다고 밝힌다.
이 지시가 정식 시스템을 거쳐 Operator Memory라는 플러그인이 되었다.
Operator Memory는 벡터 데이터베이스, 임베딩,
요약기나 Dreamer 같은 백그라운드 데몬 없이 모든 것을
읽고 고치고 커밋하고 팀과 공유할 수 있는 평범한 Markdown 문서로 둔다고 소개하며,
무료 오픈소스라는 말과 저장소 링크로 글이 끝난다.
나는 이 플러그인을 직접 설치하거나 실행해 보지 않았다.

## 분석

### 문제를 회상에서 큐레이션으로 옮긴다

글의 핵심 이동은 기억의 문제를 검색 품질이 아니라 무엇을
남길지의 문제로 바꾸는 것이다.
메모리 플러그인은 모든 대화를 원료로 삼고 꺼낼 때 골라내려 하지만,
저자의 문서 모델은 쓸 때 고르고 꺼낼 때는 그냥 읽는다.
HN의 zahrevsky는 이 차이를 더 정확히 짚었다.
메모리 조각은 사실 회의 후 적는 메모에 가깝기 때문에
3년 전 회의를 다시 본다는 비유는 맞지 않고,
진짜 문제는 문장마다 메모를 하나씩 써서 5,000개의 메모로 일하려는 데 있으며,
중요한 것만 골라 쓰면 그것이 곧 문서라고 했다.[^zahrevsky]
그는 메모리 조각이 불변이고 추가만 되며 구조가 거의 없다는 점도 들었다.

이렇게 보면 글의 주장은 저장 매체의 대결이 아니다.
조각을 독립적으로 쌓는 추가 전용 저장소와,
덮어쓰고 지우고 다시 묶을 수 있는 가변 문서의 대결이다.
문서가 더 나은 이유는 Markdown이어서가 아니라 고쳐 쓸 수 있는 단위이기
때문이라는 것이 이 글에서 끌어낼 수 있는 해석이다.

### 감사 가능성이 가장 단단한 근거다

다섯 가지 문제 가운데 다른 반론에도 살아남는 것은 감사 가능성이다.
임베딩 10,000개는 사람이 열어 볼 수 없지만
Markdown 파일은 diff로 검토하고 커밋하고 되돌릴 수 있다.
에이전트의 행동을 바꾸는 입력이 사람이 읽을 수 있는 곳에 있어야 한다는 원칙은
이 저장소가 지시를 메모리 대신 AGENTS.md에 두는 방식과도 같다.
HN의 CapitalistCartr도 글 전체에 비판적이면서
감사 가능성에 대해서는 저자가 전적으로 옳다고 인정했다.[^CapitalistCartr]

### 문서 공간의 구조가 기존 관행을 다시 묶는다

저자가 brain에 넣으라는 것은 지시, 명세, 결정, 조사, 색인이다.
이는 ADR, CONTRIBUTING 문서, 설계 문서 같은 오래된 관행과 겹친다.
gregwebs는 에이전트 전용 문서를 따로 두고 싶지 않다며,
ADR, CONTRIBUTING.md, CODING_STANDARDS.md, README, 아키텍처 문서,
커밋 메시지만으로도 에이전트가 문서를 찾고 최신으로 유지한다고 썼다.[^gregwebs]
글은 이 관행들과 자신의 brain이 어떻게 다른지 설명하지 않으므로,
새로운 것은 문서의 종류가 아니라 에이전트가 읽고 쓰는 루프를 강제하는
지시에 있다고 읽는 편이 맞다.

## 비평

### 비판한 문제가 해법에도 그대로 남는다

글은 RAG의 가장 날카로운 결함으로 에이전트가 모르는 것을 검색할 수 없다는 점을
드는데, Markdown brain도 같은 문제를 진다.
CapitalistCartr는 에이전트가 시작 전에 어떤 문서가 관련 있는지 어떻게 아느냐고
물으며, 임베딩 대신 에이전트가 색인 파일을 보고 고르는 방식도 이 문제를
벗어나지 못한다고 지적했다.[^CapitalistCartr]
그는 낡음도 마찬가지라고 했다.
기억 시스템이 과거를 진실로 취급한다고 비판하지만 문서도 자주 낡고,
에이전트에게 낡은 문서를 고치게 하는 해법은 저자가 조롱한 Dreamer와
백그라운드 데몬이 하던 일과 같다는 것이다.
다만 그는 저장소를 읽어 보니
범위마다 문서별로 다루는 내용과 열 시점을 적은 카탈로그가 있고,
색인 문서마다 짧은 설명과 `read_if` 조건이 있어
글보다 저장소가 낫다고 덧붙였다.
즉 해법의 실질은 글이 아니라 구현에 있고,
글은 그 구현이 모르는 것을 찾는 문제를 어떻게 줄이는지 설명하지 않는다.

### 시험했다는 소제목 아래에 시험이 없다

“Putting It to the Test”라는 소제목 아래에 있는 것은
저자가 1년 넘게 써 왔다는 경험담과 플러그인 소개뿐이다.
비교 대상, 작업, 지표가 없다.
CapitalistCartr는 시험이 어디 있느냐고 물었고,[^CapitalistCartr]
stbenjam은 에이전트가 만든 Markdown 문서 저장소가
수 메가바이트에 이르는 경우를 보지만,
그것이 성능을 의미 있게 높이고 썩지 않는다는 증거는
아직 보지 못했다고 썼다.[^stbenjam]
그는 에이전트에게 필요한 것을 세 가지로 줄였다.
드러나지 않은 정보를 찾는 길(더 좁은 문서를 가리키는 최소한의 AGENTS.md),
작업이 맞는지 확인하는 분명한 방법,
프로젝트 고유의 취향에 대한 약간의 안내이며 나머지는 소음이라는 것이다.
“모든 메모리 플러그인이 같은 방식으로 작동한다”는 일반화도 근거 없이 선언된다.
CapitalistCartr는 Claude가 쓰는 메모리는 그냥 읽을 수 있는 Markdown
파일이라며 이 일반화에 반례를 들었다.

### 문서가 썩는 속도를 과소평가한다

글은 작업 직후 에이전트가 문서를 갱신하면 최신성이 유지된다고 가정한다.
kaydub는 정반대 경험을 적었다.
여러 프로젝트에서 Markdown 문서와 결정 문서를 잔뜩 쌓았는데
낡으면서 문제가 되었고, 문서를 맞추는 세션을 따로 열어도 LLM이 혼란스러워했다며
코드가 곧 문서라고 했다.[^kaydub]
pornel은 에이전트가 사람의 승인 없이 쓴 명세를 믿지 않는다며, 요청하지 않은
추정 세부와 있으면 좋을 기능이 ADR에 들어가 부메랑처럼 돌아온다고 했다.[^pornel]
글이 메모리 조각의 결함으로 든 낡음과 출처 불명은 에이전트가 쓴 문서에서도
생기며, 글은 누가 문서를 승인하는지에 대해 말하지 않는다.

반대 경험도 있다.
crazygringo는 사람이 문서를 관리할 때의 문제이고
에이전트가 갱신을 맡으면 AGENTS.md 지시를 몇 번 다듬은 뒤로는
문서가 흩어지거나 낡는 일이 사라졌다고 했다.[^crazygringo]
그는 코드가 문서라는 방식도 결국 “왜”를 설명하는 주석이 필요하고 그 주석이
낡기 때문에 같은 문제가 남는다고 반박했다.
두 경험의 차이는 팀원 모두가 에이전트를 쓰는지에 달려 있다고
그 자신이 조건을 달았다.
smokel도 코드는 “무엇”과 “어떻게”를 담지만 “왜”는
잘 담지 않는다고 짚었다.[^smokel]
그러니 문서가 효과 있는지는 문서 형식이 아니라 갱신 규율이 지켜지는 조건에
달려 있고, 글은 그 조건을 성공 사례 하나로 대신한다.

### 로컬 코딩 에이전트만 상정한다

nijave는 글이 기억의 수명 주기를 무시한다고 지적했다.
이주 작업 중에만 유효한 기억처럼 한 주나 한 달만 의미 있는 정보가 있는데,
이 해법에는 시간이나 조정(reconciliation)의 개념이
일급으로 없다는 것이다.[^nijave]
그는 여러 사람이 같은 에이전트와 일할 때 선호와 사실을 구분할 방법이 없다는 점,
서버의 이벤트 기반 에이전트나 샌드박스의 챗 에이전트처럼
파일 시스템이 하나가 아니거나 여러 에이전트가 동시에 편집하면 깨지는 환경을
고려하지 않는다는 점도 들었다.
글의 대안은 로컬 저장소에서 혼자 일하는 CLI 코딩 에이전트에서 가장 잘 맞고,
메모리 플러그인 생태계 전체가 틀렸다는 결론은 그 범위를 넘어선다.

## 인사이트

### 메모리와 문서의 경계는 쓰는 시점의 판단 하나로 갈린다

ravenstine은 문서가 존재하고 현실을 가장 정확히 반영해야 한다는 전제가 깨지면
어떤 형태든 기억이 필요해지며,
에이전트가 기억으로 문서를 쓰는 것도 그 일부라고 했다.[^ravenstine]
이 지적과 zahrevsky의 관찰을 합치면, 메모리와 문서는 다른 범주가 아니라
기록 시점에 얼마나 골라내고 고쳐 쓰는지의 정도 차이로 보인다.
Operator Memory도 에이전트가 요청 없이 쓰는 기억 시스템이라는 점에서,
글의 제목은 메모리를 거부한다기보다
큐레이션 없는 메모리를 거부한다고 읽어야 한다.
이 해석이 맞다면 앞으로의 경쟁은 저장 방식이 아니라 무엇을 버릴지 정하는
정책에서 일어날 것이다.

### 문서가 많아질수록 RAG 문제가 다시 돌아온다

글의 해법은 문서 수가 적을 때 성립한다.
색인 하나로 전체를 내다볼 수 있는 동안에는 에이전트가 고를 수 있지만,
문서가 수백 개가 되면 색인 자체가 길어지고 하위 색인이 필요해진다.
그 시점에 에이전트가 하는 일은 설명문을 읽고 관련성을 판단하는 검색이며,
임베딩을 쓰지 않을 뿐 구조는 RAG와 같아진다.
이는 해석이지만, 위키가 커지면 결국 검색창이 필요해진 역사와 같은 경로다.
결국 문서 기반 메모리가 RAG보다 나은 구간은
사람이 전체 구조를 머리에 둘 수 있는 규모까지이고,
 그 너머에서는 문서를 줄이는 비용이 새 핵심 비용이 된다.

### 문서는 이론을 옮기는 도구로는 한계가 있다

jdw64는 Peter Naur의 「Programming as Theory Building」을 들어,
문서만으로는 프로그램 뒤의 정신적 모델을 다 담을 수 없다는
논지를 상기시켰다.[^jdw64]
그는 AI는 작업 맥락의 훨씬 많은 부분이 명시되어야 하므로
프로그램의 모델을 유지하는 방식이 근본적으로 다를 수 있다고 덧붙였다.
Naur의 관점에서 보면
글이 원하는 “프로젝트를 이해하는 에이전트”는 문서로 완성되지 않는다.
문서는 이론의 흔적이고, 이론은 문서를 읽고 코드를 고치고 결과를 확인하는
반복 속에서만 다시 세워진다.
그렇다면 문서보다 더 중요한 것은 stbenjam이 말한 확인 수단,
곧 에이전트가 자신의 이해가 틀렸을 때
그것을 알게 해 주는 테스트와 피드백일 수 있다.

### 자율적으로 쓰는 문서와 사람이 승인하는 문서를 나눠야 한다

글은 에이전트가 요청 없이 무엇이든 기록하라고 권하지만,
pornel의 경험은 승인 없는 기록이 부풀어 오른다는 것을 보여 준다.
이 긴장을 푸는 현실적인 방법은 두 층을 나누는 것이다.
작업 메모와 인계처럼 에이전트가 자유롭게 쓰고 버리는 층과,
결정과 원칙처럼 사람이 확인해야만 들어가는 층이다.
에이전트에게 자율을 주는 범위를 기록의 영속성과 연결하면,
낡은 기록이 쌓이는 비용은 버릴 수 있는 층에 머물고
에이전트의 행동을 오래 바꾸는 입력은 사람이 승인한 것만 남는다.
이는 에이전트에게 어디까지 자율을 줄지에 대한 일반 원칙,
즉 되돌리기 어려운 것일수록 사람이 개입해야 한다는 원칙을 기록에 적용한 것이다.
