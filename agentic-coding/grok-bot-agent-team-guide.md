# Grok Bot으로 에이전트 팀 만들기

트윗: [How to build an agent team in Grok Bot with Opus 5.5 + GitHub (Lauren Tan’s Method)](https://twitter.com/0xchonsy/status/2115445646169694321)

## 소개

콘텐츠 제작자 Chonsy(@0xChonsy)가 2026년 10월 28일 Twitter에 올린 약 9분 분량의 긴 글(Twitter Article)이다. 조회수 19만 1천 회로 표시되어 있다.
이 문서는 글 전문을 읽었다. 글이 설명하는 Grok Bot, Cursor 클라우드 에이전트, pstack은 직접 써 보지 않았고 코드와 설정의 동작은 확인하지 못했다. 글의 예제 저장소(Cypress Real-World App)와 도구 문서도 열지 않았다.

글의 주장은 이렇다.
Grok Bot과 Opus 5.5로 GitHub 저장소를 위한 에이전트 팀을 만들 수 있고, 리드 봇 하나가 일을 나누고 범위가 정해진 작업을 위임하며 검증 결과가 붙은 PR을 모은다는 것이다. 방법은 Lauren Tan이 말한 pstack 작업 방식을 따른다고 한다. 글은 도입부에서 Lauren Tan이 한 달에 PR 2,500개를 운영에 반영했다는 그의 트윗을 인용하고, 에이전트의 변경을 손으로 시험하면 에이전트 열 개가 리뷰 대기 PR 열 개를 남긴다는 문제를 든다.

## 구성

글은 세 구성 요소의 역할을 나눈다.

- Grok Bot: 요청을 받고 작업을 조율한다.
- Cursor 클라우드 에이전트: 코드를 돌리고 변경을 별도 환경에서 만든다.
- GitHub: 이슈와 브랜치, PR, CI 결과를 보관한다.

Grok Bot의 봇들은 계정 하나에 딸린 한 컴퓨터를 공유하고, Cursor 클라우드 에이전트는 각각 별도 VM에서 돈다. 여러 에이전트가 동시에 빌드하고 시험해야 할 때 이 차이가 중요하다고 글은 설명한다.
글은 Grok Bot이 백엔드 모델을 스스로 고르므로 Opus 5.5를 강제하거나 개별 요청 뒤의 모델을 확인할 수 없다고 밝힌다. 모델을 명시하려면 클라우드 코딩 에이전트의 설정을 쓰고 계정에서 Opus 5.5를 쓸 수 있는지 확인하라고 한다.

## 설정하기

글의 여섯 단계는 다음과 같다.

1. 준비(저장소 연결과 첫 실행): Grok Bot을 설치하고 첫 봇을 Chief라는 이름으로 만든다. 양쪽(Grok Bot의 앱 연결, Cursor 클라우드 에이전트)에서 GitHub를 연결하고 저장소를 골라 환경 설정을 끝낸다. 예제로 Cypress Real-World App(프런트엔드, API, 시드 데이터, 사용자 흐름 테스트가 있음)을 내 계정에 복사해 쓴다. 첫 작업은 개발 환경 확인으로, 저장소와 커밋, 서비스 준비 상태, 타입 검사와 인증 테스트 결과를 보고하게 한다. 실패하면 그 오류를 기준선으로 남겨 나중에 회귀와 구분한다. 성공한 실행이 Opus 5.5가 쓰였다는 뜻은 아니므로 모델 선택은 따로 보고하게 한다.
2. 검증(에이전트가 앱을 직접 시험하게 함): 타입 검사가 통과해도 브라우저에서 로그인이 실패할 수 있다. Lauren Tan의 pstack에 들어 있는 create-verification-skill이 저장소를 읽고 새 세션의 다른 에이전트가 따를 지침을 만든다. 생성되는 스킬은 실행(Launch), 진단(Doctor, 올바른 인스턴스인지와 환경 사용 가능 여부), 조작(Drive, 기능을 움직이는 브라우저 동작이나 기존 테스트), 증거(Evidence, 결과 저장 위치), 정리(Cleanup, 이 실행이 만든 프로세스만 정리)의 다섯 가지를 설명해야 한다. 첫 기능은 잘못된 자격 증명의 로그인이다. 기능 지도(feature map)에 시작 상태, 경로, 선택자, 동작, 기대 결과와 실패 조건을 적는다. 생성된 스킬의 PR은 실행 증거를 확인한 뒤 병합하고, 저장소 안의 스킬은 이후 클라우드 에이전트 실행에서 재사용된다.
3. 팀(역할 배정): 봇 셋을 더해 Chief(요청 접수와 추적), Lead(요청을 완료 기준이 있는 계획으로), Builder(구현 관리), Reviewer(원래 요구사항에 비춘 검토)로 나눈다. 각 역할 지침은 YAML 형식의 프롬프트로 제시된다. Chief는 병합 권한이 사람에게만 있고, Lead는 계획 전에 코드를 읽고 독립적인 작업만 병렬화하며 한 브랜치에 쓰는 사람은 하나로 한다. Builder는 별도 작업 브랜치에서 일하고 병합과 기본 브랜치 푸시가 금지된다. Reviewer는 PR의 정확한 헤드 커밋을 받아 검증을 다시 돌리고 PASS, FAIL, BLOCKED 판정을 내리며, 새 커밋이 오면 이전 판정은 무효이다. 증거가 없으면 BLOCKED이다. 네 봇을 그룹 채팅 Engineering에 넣고 모든 인계가 이슈, 현재 담당, 관련 커밋, 증거, 다음 행동을 밝히게 한다.
4. 이슈에서 PR까지: 첫 일은 로그인 실패 뒤 재시도 성공을 확인하는 회귀 테스트 추가이다. 완료 기준(오류가 나타남, 두 필드를 지우고 올바른 값을 입력, 새로고침 없이 다시 제출해 인증되고 오류가 사라짐, 기존 인증 테스트가 통과)을 이슈에 적는다. Lead가 기존 테스트가 이미 같은 범위를 덮는지 먼저 확인하고, 중복이면 링크만 걸고 새 테스트를 만들지 않는다. Builder는 별도 브랜치에서 새 스펙을 만들고, 이 앱이 인증 테스트마다 데이터베이스를 다시 시드하므로 병렬 실행에는 격리된 데이터가 필요하다고 글은 쓴다. Reviewer는 PR 헤드 커밋에서 같은 검사를 반복하고, 실패는 명령과 오류와 재현 절차와 함께 Builder에게 돌려보내며 환경이 없으면 BLOCKED이다. PR 설명에는 변경, 검증(명령과 종료 코드와 시험한 커밋), 증거, 한계를 담는다.
5. 품질(수정을 검사로): Reviewer가 잡은 실수는 다음에 무엇이 잡을지를 정해 구조 제약, 타입 오류, 린트 규칙, 회귀 테스트로 바꾼다. Lauren Tan의 /correct 흐름도 가장 강한 실행 수단부터 쓰고 남는 것을 문서화하는 순서라고 한다. 구체적으로는 모든 PR에서 도는 GitHub Actions 워크플로(auth-verification)를 추가해 체크아웃, 노드 설정, 의존성 설치, 타입 검사, Cypress 인증 테스트, 브라우저 증거 업로드를 하게 하고, 기본 브랜치 보호 설정에서 이 검사를 병합 필수 조건으로 건다. Reviewer의 PASS는 별도 보고이므로 병합 전에 검토한 SHA와 PR의 현재 헤드를 비교한다. 명확한 범위와 완료 기준이 있는 이슈에만 agent-ready 라벨을 달고, Chief에게 평일 오전 9시에 가장 오래된 해당 이슈 하나를 골라 진행 중이 아닌지 확인하고 담당을 기록한 뒤 Lead에게 보내는 루틴을 만들게 한다. 수정 라운드는 두 번까지이고 병합과 범위 확대는 사람의 승인이 필요하다.
6. 실행과 측정: 작은 이슈 하나로 한 주기를 돌리고 네 가지(사람 검토 시간, 수정 라운드 수, 완료 기준 충족, 사용량이나 비용)를 기록한다. 막혔을 때의 대응도 적는다. 앱이 시작되지 않으면 환경과 설정 로그를 보고 제품 코드를 바꾸기 전에 재현한다. 두 실행이 같은 일을 건드리면 Chief가 담당을 정하고 중복을 멈춘다. Reviewer가 필수 검사를 돌리지 못하면 BLOCKED로 두고 빠진 의존성이나 권한을 기록한다. PASS 뒤 새 커밋이 오면 그 SHA를 다시 검토시킨다. 몇 번 돌린 뒤 비슷한 작업을 비교하고, 병렬 작업을 하나 더해 보되 별도 브랜치와 환경을 주고 검토 시간이 급증하면 느린 인계나 빠진 검사를 찾으라고 한다.

## 분석

### 중심 주장은 에이전트 팀의 핵심이 역할이 아니라 증거를 붙인 인계라는 것이다

글에서 반복되는 요소는 역할 이름보다 인계의 규칙이다. 이슈, 담당, 커밋, 증거, 다음 행동이 빠지면 BLOCKED이고, 새 커밋이 오면 이전 판정이 무효가 되며, 병합은 사람만 한다.
이는 에이전트를 믿게 만드는 장치를 인계 단계마다 심는 구조이다. 이 문서의 해석이다.

### 저장소 안의 검증 스킬이 팀의 공통 기반이다

검증 스킬(Launch, Doctor, Drive, Evidence, Cleanup)을 저장소에 두면 다음 에이전트가 같은 길을 따라간다는 점이 설계의 핵심이다.
Builder와 Reviewer와 CI가 같은 검증 지침을 공유하므로 사람이 매번 설명할 일이 줄어든다.

## 비평

### 모델 선택에 대해 제목이 약속하는 것과 본문이 인정하는 것이 다르다

제목은 Opus 5.5를 내세우지만 본문은 Grok Bot이 백엔드 모델을 스스로 고르고 개별 요청 뒤의 모델을 확인할 수 없다고 인정한다.
모델을 명시할 수 있는 것은 Cursor 클라우드 에이전트 쪽이다. 따라서 Grok Bot의 조율 계층과 코딩을 실제로 하는 계층이 서로 다른 모델일 수 있다.

### 글의 YAML은 검증되지 않은 프롬프트 형식이다

역할 지침과 작업 지시가 YAML처럼 쓰여 있으나 이는 봇에게 보내는 자연어 프롬프트이고 도구가 읽는 정해진 스키마가 아니다. 글도 이를 루틴을 만들라는 프롬프트라고 쓴다.
그래서 키 이름(예: stop_if_unavailable, report_if_hidden)이 실제로 어떻게 해석되는지는 봇의 구현에 달렸다. 이 문서는 이를 확인하지 못했다.

### 성과를 보여 주는 실행 결과가 없다

글은 방법을 설명할 뿐 이 방법으로 실제 이슈를 돌린 결과(소요 시간, 수정 라운드, 비용)를 제시하지 않는다. 측정은 독자의 숙제로 남는다.
도입부의 2,500 PR은 Lauren Tan의 경험이고 이 팀 구성으로 얻은 수치가 아니다.

### 제시된 CI 설정은 가변 태그에 의존한다

글의 워크플로는 액션을 `@v7` 같은 태그로 지정한다. 태그는 사후에 바뀔 수 있어서 이 저장소의 CI 시장 문서(`devops/ci-market-split-into-three.md`)가 다룬 tj-actions 사건 같은 경로가 열린다. 에이전트가 만드는 워크플로에 같은 설정을 그대로 쓰기 전에 커밋 해시로 고정하는 점검이 필요하다.
이는 이 문서의 관찰이고 글에는 이 논점이 없다. 글이 쓴 액션 버전이 실제로 존재하는지도 이 문서는 확인하지 못했다.

### 비용과 보안에 대한 서술이 얕다

루틴이 실행될 때마다 사용량이 든다고 한 줄 적을 뿐이고, 에이전트에 GitHub 접근과 클라우드 환경 권한을 주는 위험(토큰 범위, 비밀 노출)은 다루지 않는다.

### 외부 반응

HN에서는 이 트윗의 스레드가 검색되지 않았고, Lobste.rs의 twitter.com 도메인 최근 150개 글(429로 이후 확인 불가)에도 없었다. GeekNews는 제목과 필자 이름과 주제 검색에서 이 글의 토픽을 찾지 못했다.
그래서 이 글의 주장은 독자의 검토를 거의 거치지 않았다.

## 인사이트

### 가져갈 것은 인계마다 증거와 판정을 규칙으로 두는 것이다

에이전트를 여럿 쓸 때의 병목은 만드는 속도가 아니라 사람이 결과를 재구성하는 시간이므로, 인계마다 증거와 판정과 무효 조건을 규칙으로 정해 두어야 한다.

### 따라 하기 전에 확인할 것

확인할 것은 네 가지이다.
어떤 모델이 어느 계층에서 일하는지 확인할 수 있는지,
검증 스킬을 저장소에 두고 모든 단계가 같은 것을 쓰는지,
CI의 필수 검사와 Reviewer의 판정이 같은 SHA를 가리키는지,
에이전트에 준 권한과 CI 설정(액션 고정 포함)을 점검했는지이다.
