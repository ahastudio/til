# Paseo: 자체 호스팅으로 여러 코딩 에이전트를 한 인터페이스에서 돌린다

<https://paseo.sh/>

<https://github.com/getpaseo/paseo>

HN 토론: <https://news.ycombinator.com/item?id=48377250> (92점, 54개 댓글)

## 소개

Paseo는 Claude Code, Codex, Copilot, OpenCode, Pi를 하나의 인터페이스에서 다루는 오픈소스 도구다.
저장소 설명은 “데스크톱과 모바일에서 여러 코딩 에이전트를 오케스트레이션”이고, 한 줄 소개는 “자기 기계에서 에이전트를 병렬로 돌리고, 폰에서든 책상에서든 배포하라”다.
라이선스는 AGPL-3.0이고, 스타 12.7k, 포크 1.3k, 커밋 4,788개다.
README가 영어·중국어 간체·일본어·한국어로 제공된다.

내세우는 다섯 가지는 이렇다.

- **자체 호스팅** — 에이전트가 자기 기계에서 전체 개발 환경을 그대로 쓰고 돌아간다. 자기 도구, 자기 설정, 자기 스킬을 쓴다.
- **멀티 프로바이더** — Claude Code, Codex, Copilot, OpenCode, Pi를 같은 인터페이스로 다루며 작업마다 맞는 모델을 고른다.
- **음성 제어** — 음성 모드로 작업을 받아쓰게 하거나 문제를 말로 풀어 갈 수 있다.
- **크로스 디바이스** — iOS, Android, 데스크톱, 웹, CLI. 책상에서 시작하고 폰에서 확인하고 터미널에서 스크립트로 돌린다.
- **프라이버시 우선** — 텔레메트리도, 추적도, 강제 로그인도 없다.

## 구조와 설치

Paseo는 코딩 에이전트를 관리하는 로컬 서버(데몬)를 돌리고, 데스크톱 앱·모바일 앱·웹 앱·CLI 같은 클라이언트가 거기에 붙는 구조다.
전제 조건은 에이전트 CLI를 최소 하나 설치하고 자격 증명을 설정해 두는 것이다.

데스크톱 앱이 권장 경로다 — 앱을 열면 데몬이 자동으로 시작하고 그 외에 설치할 것이 없다.
폰에서 붙으려면 설정 → 호스트 → Pair Device로 간다.

CLI/헤드리스 경로는 이렇다.

```bash
npm install -g @getpaseo/cli
paseo
```

Paseo가 로컬에서 시작한 뒤 기기 페어링을 위한 종단 간 암호화 릴레이를 켤지 묻는다.
거절하면 TCP나 Tailscale이나 다른 VPN으로 직접 연결한다 — 서버와 원격 머신에 유용한 경로다.

Docker로 데몬과 자체 호스팅 웹 UI를 함께 띄울 수도 있다.

```bash
docker run -d --name paseo \
  -p 6767:6767 \
  -e PASEO_PASSWORD=change-me \
  -v "$PWD/paseo-home:/home/paseo" \
  -v "$PWD:/workspace" \
  ghcr.io/getpaseo/paseo:latest
```

기동 후 `http://localhost:6767`을 연다.
베이스 이미지를 자기가 쓰는 에이전트 CLI로 확장하고, 자격 증명은 환경 변수나 영속 `/home/paseo` 볼륨으로 넘긴다.

## CLI

앱에서 할 수 있는 모든 것을 터미널에서 할 수 있다는 것이 문서의 주장이다.

```bash
paseo run --provider claude/opus-4.6 "implement user authentication"
paseo run --provider codex/gpt-5.4 --worktree feature-x "implement feature X"

paseo ls                              # 실행 중인 에이전트 목록
paseo attach abc123                   # 실시간 출력 스트리밍
paseo send abc123 "also add tests"    # 후속 작업 전달

paseo --host workstation.local:6767 run "run the full test suite"
```

## 스킬

Paseo는 에이전트가 Paseo를 써서 다른 에이전트를 오케스트레이션하도록 가르치는 스킬 묶음을 제공한다.

```bash
npx skills add getpaseo/paseo
```

- `/paseo-handoff` — 에이전트 사이에 작업을 인계한다. 관리자는 Claude로 계획하고 Codex로 구현을 넘기는 데 쓴다고 밝힌다.
- `/paseo-loop` — 명확한 인수 조건에 대해 에이전트를 반복 실행한다(이른바 Ralph 루프). 선택적으로 검증자를 붙인다.
- `/paseo-advisor` — 작업을 위임하지 않고 두 번째 의견을 얻기 위해 에이전트 하나를 조언자로 띄운다.
- `/paseo-committee` — 대비되는 두 에이전트로 위원회를 구성해 한 발 물러서서 근본 원인을 분석하고 계획을 만든다.

모노레포 구성은 `packages/server`(데몬 — 에이전트 프로세스 오케스트레이션, WebSocket API, MCP 서버), `packages/app`(Expo 클라이언트), `packages/cli`, `packages/desktop`(Electron), `packages/relay`(릴레이 전송과 암호화), `packages/website`다.
관련 프로젝트로 Elixir로 작성된 공식 분산 릴레이 `paseo-relay`, 커뮤니티 테마 모음 `paseo-skins`, VS Code 확장 `paseo-vscode`가 있다.

## 분석

### 이 도구가 파는 것은 오케스트레이션이 아니라 접근 경로다

Paseo의 기능 목록을 보면 오케스트레이션 도구처럼 보인다 — 여러 에이전트, 병렬 실행, 위임 스킬.
그런데 아키텍처를 보면 다른 것이 중심에 있다.

데몬이 로컬에서 돌고, 클라이언트가 거기에 붙고, 릴레이는 기기 페어링을 위한 것이며, 릴레이를 거절하면 TCP나 Tailscale로 직접 붙는다.
즉 이 제품의 핵심 문제는 “여러 에이전트를 어떻게 조율할까”가 아니라 “내 개발 환경에서 도는 에이전트에 다른 기기에서 어떻게 닿을까”다.

이 구분이 중요한 이유는 경쟁 지형이 달라지기 때문이다.
오케스트레이션 도구라면 병합 품질과 비교 UI가 승부처다.
접근 경로 도구라면 연결의 신뢰성, 지연, 보안, 그리고 무엇보다 “설정하지 않아도 되는 정도”가 승부처다.
그리고 Paseo가 실제로 공들인 것은 후자다 — 데스크톱 앱을 열면 데몬이 자동으로 뜨고, 페어링은 설정 메뉴 세 단계이며, 릴레이는 종단 간 암호화이고 거절할 수 있다.

이 관점에서 보면 “자체 호스팅”과 “프라이버시 우선”이 마케팅 문구가 아니라 아키텍처의 필연이다.
에이전트가 내 기계에서 내 전체 개발 환경으로 도는 것이 전제라면, 클라우드에서 돌리는 경쟁자와 달리 원격 접근 문제를 스스로 풀어야 한다.
그리고 그 문제를 푸는 과정에서 만들어진 릴레이가 이 프로젝트의 가장 특이한 자산이 되었다 — 별도 저장소로 Elixir로 작성되었다는 사실이 그 무게를 보여준다.

### 스킬 네 개가 이 도구의 실제 사용 모델을 드러낸다

기능 목록보다 스킬 목록이 더 많은 것을 알려준다.
`handoff`, `loop`, `advisor`, `committee`.

이 넷은 서로 다른 협업 패턴이다.
인계는 순차적 분업이고, 루프는 수렴할 때까지의 반복이고, 조언자는 위임 없는 참조이고, 위원회는 대비되는 관점의 병치다.
그리고 이 목록에 없는 것이 눈에 띈다 — 같은 작업을 여러 에이전트에게 동시에 시키고 결과를 비교하는 패턴.

이 부재가 Paseo의 위치를 설명한다.
같은 범주의 다른 도구들이 팬아웃과 비교를 전면에 내세우는 데 반해, Paseo의 스킬은 전부 “역할을 나눈다”는 발상 위에 서 있다.
관리자가 직접 설명한 사용 방식 — Claude로 계획하고 Codex로 구현을 넘긴다 — 이 그 발상의 전형이다.

그리고 이 선택에는 근거가 있다.
같은 작업을 다섯 번 돌려 비교하는 것은 토큰 비용이 다섯 배이고 검토 부담도 다섯 배다.
역할을 나누면 비용은 한 배에 가깝게 유지되면서 각 단계에서 모델의 강점을 쓸 수 있다.
`/paseo-advisor`가 “작업을 위임하지 않고” 의견만 구한다고 명시한 것도 같은 절약의 논리다.

### AGPL 선택이 이 프로젝트의 사업 모델을 사실상 결정한다

라이선스가 AGPL-3.0이다.
경쟁 도구 중 다수가 MIT를 택하는 것과 대비된다.

AGPL은 네트워크를 통해 소프트웨어를 제공하는 경우에도 소스 공개 의무를 발생시킨다.
그리고 이 제품은 정확히 그 형태로 쓰일 수 있다 — 데몬을 서버에 띄우고 웹 UI를 여럿이 쓰는 방식.
Docker 실행 예시가 그 시나리오를 명시적으로 지원한다.

즉 AGPL은 “우리 코드로 호스팅 서비스를 만들어 팔지 말라”는 신호다.
그리고 이 선택은 프라이버시 우선이라는 포지셔닝과 정합적이다 — 텔레메트리도 강제 로그인도 없는 도구를 만들면서 누군가 그것을 SaaS로 재포장하는 것을 막는 것.

동시에 이 선택은 기업 채택에 마찰을 만든다.
많은 기업이 AGPL 소프트웨어를 내부에서라도 쓰는 것을 정책으로 금지한다.
개인 개발자를 대상으로 하는 도구라면 문제가 적지만, 팀 단위 채택을 노린다면 이 마찰이 실질적이다.
Docker와 헤드리스 서버 경로를 문서화해 둔 것이 팀 사용을 상정한 것이라면, 라이선스와 대상 사용자 사이에 긴장이 있다.

### 모바일이 이 도구의 정체성이면서 가장 논쟁적인 지점이다

“폰에서든 책상에서든 배포하라”가 저장소 첫 문장에 있고, HN 스레드에서 가장 격한 반응을 얻은 것도 그 문장이다.

keyle이 정면으로 반대했다 — “이동 중에 배포”라는 것이 자기에게는 말이 안 되며, 서서 소변을 보면서 폰을 꺼내는 사람이나 횡단보도 신호가 빨간불일 때 폰을 꺼내야 하는 것과 같다는 것이다.
한 번에 하나만 하고 삶을 살라며, 폰에서 코드를 배포하는 것이 자랑이 아니라 우울이라고 했다[^keyle].

관리자 boudra의 답이 이 제품의 설계 의도를 가장 명확히 설명한다.
그 우려를 이해하지만 자기 경험은 그렇지 않았다는 것이다.
모바일 쪽을 온전한 근무 시간 위에 폰으로 계속 일하는 방법으로 생각하지 않으며, 그렇게 쓰일 수 있다는 것은 인정한다.
오히려 책상에서 물러나되 작업에 대한 접근을 잃지 않는 것에 가깝다는 설명이다[^boudra-mobile].

이 답변이 앞의 분석 — 이 도구가 파는 것은 접근 경로다 — 를 확인해 준다.
그리고 이 차이가 실제로 중요하다.
“폰에서 코딩하기”와 “자리를 비운 동안 돌아가는 것을 확인하기”는 다른 제품이고, 전자는 대부분의 사람에게 나쁜 아이디어이며 후자는 에이전트가 오래 도는 환경에서 자연스러운 요구다.
저장소 첫 문장이 전자로 읽히게 쓰여 있다는 것이 마케팅의 문제이지 제품의 문제는 아닐 수 있다.

## 비평

### “아름다운”이라는 형용사가 이 프로젝트에서 가장 많이 반박된 단어다

Show HN 제목이 “Paseo – Beautiful open-source coding agent interface”였고, 스레드의 첫 실질 비판이 그 단어를 겨냥했다.

jjcm이 정확히 지적했다 — 오픈소스라는 점을 깎아내리려는 것은 아니지만 무엇이 이것을 “아름답다”고 만드는가, 디자인 관점에서 이것은 기본 Tailwind이고 그중에서도 중립 회색 Tailwind에 Lucide 아이콘이라는 것이다.
그것들이 잘못되었다는 것은 아니지만 “의견 없는(unopinionated) 디자인”이라고 말하는 편이 더 적절하며, 디자인 의도가 나중 문제이고 기능에 집중할 때 나오는 기본 선택이라고 했다[^jjcm].
mutant도 같은 판정을 짧게 내렸다 — 아름답다는 것은 과장이며 전형적인 축이고, 다만 잘 동작하니 원 게시자가 엉뚱한 품질을 자랑한 것이라는 것이다[^mutant].

elicash가 변호했다 — 그림이나 그랜드캐니언이나 오로라나 부모의 사랑에 비교한다면 아름답지 않겠지만 오픈소스 프로젝트치고는 아주 좋으며, 웹사이트 마케팅 자료 어디에도 그 단어가 쓰이지 않은 것 같다고 덧붙였다[^elicash].

이 논쟁이 사소해 보이지만 한 가지를 드러낸다.
이 범주의 도구들이 전부 비슷한 스택으로 비슷한 인터페이스를 만들고 있고, 그래서 시각적 차별화가 거의 없다.
tao_oat이 그 상황을 직접 언급했다 — Conductor, Superconductor, cmux를 비롯해 비슷한 인터페이스를 주는 앱을 여섯 개 넘게 써 봤으며, Paseo 웹사이트에 최소한 그중 몇 개와의 비교가 있으면 좋겠다는 것이다[^tao_oat].
boudra는 Conductor 비교 페이지만 있다고 답하면서, 모두가 비슷한 인터페이스로 수렴하고 있지만 차이는 있다며 FOSS·로컬 우선·자체 호스팅 가능·텔레메트리와 강제 로그인 없음·macOS와 Windows와 Linux 지원을 들었다[^boudra-compare].

차별점이 전부 라이선스와 배포 정책이라는 사실이 이 범주의 현재 상태를 요약한다 — 기능은 수렴했고, 남은 것은 신뢰와 통제권이다.

### 비용과 컨텍스트 관리에 대한 질문에 제품이 답을 갖고 있지 않다

이 스레드에서 가장 기술적으로 날카로운 지적은 eugeneonai의 것이다.
README가 작업별 모델 선택을 내세우지만 컨텍스트 관리에 대해서는 별로 말하지 않는다는 것이다.
코딩 에이전트 루프에서는 전체 시스템 프롬프트와 도구 명세가 매 단계 다시 전송되므로 30단계 작업은 입력 비용을 30번 낸다.
프롬프트 캐시 헤더가 정적 접두부를 잡아 주지만 단계별 차이 — 파일 diff, 관측 토큰 — 는 캐시되지 않고 그것이 대개 입력의 대부분이다.
오래된 궤적을 상태 벡터로 자동 요약하면 자기가 본 워크로드에서 입력 토큰을 40~60% 절약했으며, 사용자가 각 에이전트의 내부에 손을 넣지 않을 것이므로 데몬 쪽 관심사로 유용할 수 있다는 제안이다[^eugeneonai].

이 지적이 중요한 이유는 그것이 오케스트레이터 계층의 존재 이유를 건드리기 때문이다.
여러 에이전트를 한 인터페이스에 모으는 것만으로는 각 에이전트가 개별적으로 하던 것을 그대로 하게 될 뿐이다.
데몬이 중간에 앉아 있다는 사실이 값을 갖게 하려면 개별 에이전트가 못 하는 것을 해야 하고, 크로스 에이전트 컨텍스트 관리가 정확히 그 후보다.

notenkidev도 인접한 질문을 했다 — Claude Code용 토큰 사용량 대시보드를 만들고 있는데 Paseo가 토큰이나 비용 가시성을 제공하는지 궁금하다는 것이다[^notenkidev].
timhigins가 다른 프로젝트를 추천하는 것으로 답이 대신되었다[^timhigins].
즉 두 질문 모두 제품 안의 답을 얻지 못했다.

여러 에이전트를 병렬로 돌리게 하면서 비용을 보여주지 않는 것은 구조적 공백이다.
사용자가 병렬도를 올릴 유인은 도구가 제공하고, 그 비용은 다른 곳에서 청구되기 때문이다.

### 자체 호스팅을 내세우면서 자체 호스팅 문서가 없었다

akoumjian이 웹 앱 인터페이스를 자체 호스팅할 방법이 있는지 물었다[^akoumjian].
boudra의 답이 현실을 드러낸다 — 웹 앱은 정적 Expo 내보내기이므로 `packages/app`을 빌드해 생성된 `dist/`를 아무 정적 HTTP 서버로 서빙하는 것이 가장 단순한 경로이고, 데몬 자체는 npm에 `@getpaseo/cli`로 배포된다는 것이다.
그리고 덧붙인다 — 이에 대한 문서가 현재 없으며 아마 이 모든 것을 Docker 이미지로 패키징해야 할 것 같아서 오늘 그렇게 하겠다는 것이다[^boudra-selfhost].

지금 README에 Docker 실행 예시가 있는 것을 보면 그 약속은 지켜졌다.
그러나 이 교환이 보여주는 것은 “자체 호스팅”이 첫 번째 셀링 포인트인 제품이 출시 시점에 자체 호스팅 문서를 갖고 있지 않았다는 사실이다.

이것은 이 범주 전반의 패턴이기도 하다.
포지셔닝은 통제권과 프라이버시로 잡고, 실제 개발 우선순위는 사용 경험에 가 있다.
그리고 통제권을 원하는 사용자는 대체로 문서를 읽고 직접 설정하려는 사용자이므로, 문서의 부재가 바로 그 사용자층을 걸러낸다.

### 이 범주가 이미 포화 상태이고 그 사실이 스레드에 그대로 나타난다

54개 댓글 중 상당수가 대안 언급이다.

navs는 몇 달째 openchamber를 쓰고 있고 만족한다며 그쪽도 웹 기반 PWA와 로컬 CLI로 비슷하다고 했고[^navs], T1ny도 같은 사용자라며 경쟁과 선택지가 늘어나는 것이 좋다고 덧붙였다[^T1ny].
tao_oat은 Conductor, Superconductor, cmux를 포함해 여섯 개 넘게 써 봤다고 했다.
betaout은 conductor.build를 무겁게 쓰다가 Paseo로 완전히 갈아탔다고 감사를 표했다[^betaout].
rcarmo는 자기가 만드는 비슷한 프로젝트를 소개했고[^rcarmo], yoavshai는 며칠 전에 OrbStack과 JJ로 더 조악한 버전을 만들었다고 했다[^yoavshai].
fadilf는 자기용으로 꽤 비슷한 프로젝트를 만들어 왔다고 했다[^fadilf].
txhwind는 이것을 Codex Remote Control의 오픈소스 대안으로 위치시켰다[^txhwind].

즉 한 스레드 안에 최소 열 개의 유사 프로젝트가 등장한다.
그리고 arcastroe는 전혀 다른 접근을 제시했다 — 자기는 Gitea 자체를 코딩 에이전트 인터페이스로 쓰며, 이슈에 `@codex`나 `@claude`를 태그해 PR을 열게 하거나 댓글 스레드에 답하게 한다는 것이다.
Gitea 인터페이스가 이미 어떤 기기의 어떤 브라우저에서도 접근 가능한 꽤 좋은 인터페이스라는 것이다[^arcastroe].

이 마지막 지적이 이 범주 전체에 대한 가장 강한 반론이다.
전용 앱이 해결하는 문제 — 어디서든 접근, 상태 확인, 후속 지시 — 를 이슈 트래커가 이미 해결하고 있다면, 새 클라이언트를 설치할 이유가 줄어든다.
그리고 이슈 트래커 쪽에는 전용 앱에 없는 것이 있다 — 팀이 이미 거기 있고, 기록이 남고, 권한 체계가 있다.

## 인사이트

### 자체 호스팅 에이전트 도구의 진짜 제품은 네트워킹이다

Paseo의 구성 요소를 값의 순서로 다시 정렬하면 예상과 다른 결과가 나온다.
에이전트 실행은 각 CLI가 한다.
UI는 이 범주에서 수렴했고 차별화되지 않는다.
남는 것은 데몬과 릴레이 — 내 기계에서 도는 프로세스에 외부 기기가 안전하게 붙게 하는 부분이다.

그리고 이것이 어려운 문제다.
NAT 뒤에 있고, 방화벽이 있고, 주소가 바뀌고, 종단 간 암호화가 필요하고, 신뢰할 수 있는 페어링 절차가 필요하다.
Tailscale이 회사가 될 만큼 어려운 문제이고, Paseo가 그 일부를 다시 풀고 있다.

이 관점에서 보면 릴레이를 Elixir로 별도 저장소에 만든 결정이 설명된다.
많은 장기 연결을 유지하는 서버는 BEAM이 잘하는 일이고, 그 선택은 이 컴포넌트를 진지하게 다룬다는 뜻이다.

그리고 여기서 예측 하나가 나온다.
이 범주의 통합은 UI 경쟁이 아니라 연결 계층에서 일어날 가능성이 높다.
기존 VPN이나 원격 접속 제품이 에이전트 세션 관리를 붙이는 것이, 에이전트 UI 제품이 신뢰할 만한 연결 계층을 만드는 것보다 쉽기 때문이다.
Paseo가 “릴레이를 거절하고 Tailscale로 붙어도 된다”고 안내하는 것은 정직하지만, 동시에 자기 핵심 자산의 대체 가능성을 인정하는 것이기도 하다.

### 스킬이 도구를 확장하는 것이 아니라 도구를 에이전트에게 노출하는 방향으로 쓰인다

`npx skills add getpaseo/paseo`로 설치하는 스킬 넷의 성격이 특이하다.
문서의 표현이 정확하다 — “스킬은 당신의 에이전트에게 Paseo를 써서 다른 에이전트를 오케스트레이션하도록 가르친다.”

즉 사용자가 UI에서 오케스트레이션하는 것이 아니라, 에이전트가 CLI를 통해 오케스트레이션한다.
그리고 이것은 아키텍처의 필연적 귀결이다 — CLI가 앱과 동등한 기능을 갖고 있고 데몬이 MCP 서버를 제공한다면, 에이전트가 그것을 호출하지 못할 이유가 없다.

이 구조가 만드는 것은 재귀다.
에이전트가 다른 에이전트를 띄우고, 그 에이전트도 같은 스킬을 갖고 있으며, 원리상 깊이 제한이 없다.
그리고 이 재귀에는 비용과 안전 양쪽에서 자연스러운 제동 장치가 없다.

여기서 나오는 실무적 관찰은 오케스트레이션 도구의 다음 필수 기능이 무엇인지에 관한 것이다.
지금까지 이 범주의 기능 경쟁은 무엇을 더 할 수 있는가였다.
에이전트가 도구를 직접 부르기 시작하면 경쟁 축이 바뀐다 — 무엇을 못 하게 막을 수 있는가, 예산 상한과 깊이 제한과 승인 게이트를 어디에 둘 수 있는가.
Paseo의 스킬 중 `/paseo-advisor`가 “작업을 위임하지 않고”라고 명시한 것이 그 방향의 원시적 형태이고, 아직 그것은 규칙이 아니라 관례다.

### 프라이버시 우선이 기능이 아니라 진입 조건이 되는 시점

“텔레메트리도, 추적도, 강제 로그인도 없다”는 문구가 다섯 셀링 포인트 중 하나로 올라와 있다.
그리고 boudra가 경쟁 도구와의 차별점으로 든 목록도 대부분 같은 성격이다.

이 현상 자체가 이 범주의 상태를 알려준다.
기능이 수렴하면 남는 차별점은 신뢰이고, 신뢰는 기능 목록에 넣을 수 없으므로 정책으로 표현된다.
텔레메트리 없음, 로그인 없음, 자체 호스팅, 오픈소스 라이선스.

그런데 이 차별화 방식에는 수명이 있다.
경쟁자가 같은 정책을 채택하는 데 드는 비용이 낮기 때문이다 — 텔레메트리를 끄고 로그인을 선택으로 바꾸는 것은 기능 개발보다 쉽다.
그러면 정책은 차별점에서 진입 조건으로 이동하고, 다시 다른 축에서 경쟁해야 한다.

같은 일이 다른 범주에서 이미 일어났다.
브라우저에서 프라이버시가 차별점이었다가 기본값이 되었고, 메신저에서 종단 간 암호화가 그랬다.
그리고 그 전환 뒤에 남은 승부처는 성능과 통합이었다.
이 범주에서 그 다음 축이 무엇일지가 지금 열려 있고, eugeneonai가 제기한 컨텍스트·비용 관리가 유력한 후보다 — 정책과 달리 그것은 구현이 어렵고 따라 하기도 어렵기 때문이다.

### 같은 문제에 대한 두 개의 해법이 정반대 방향으로 갈라졌다

이 도구를 [Orca](orca-agent-orchestrator.md)와 나란히 놓으면 대비가 선명하다.
둘 다 여러 코딩 에이전트를 관리하는 데스크톱 앱이고, 둘 다 모바일 동반 앱이 있고, 둘 다 CLI를 제공한다.
그런데 강조점이 반대다.

Orca는 팬아웃을 중심에 둔다 — 하나의 프롬프트를 다섯 에이전트에 뿌리고 각자 격리된 worktree에서 돌린 뒤 비교해 승자를 병합한다.
Paseo는 역할 분담을 중심에 둔다 — 계획은 이 에이전트, 구현은 저 에이전트, 조언은 또 다른 에이전트.

라이선스도 반대다 — Orca는 MIT, Paseo는 AGPL.
텔레메트리도 반대다 — Orca는 익명 사용 데이터를 수집하고 옵트아웃을 제공하며, Paseo는 아예 없다고 선언한다.
지원 에이전트 범위도 반대다 — Orca는 30개 넘게 나열하며 “터미널에서 돌면 Orca에서 돈다”고 하고, Paseo는 다섯 개를 명시한다.
스타 수도 39.8k 대 12.7k로 세 배 차이다.

이 대비가 흥미로운 이유는 두 전략이 같은 시장에서 서로 다른 사용자를 겨냥하고 있음을 보여주기 때문이다.
넓게 지원하고 빠르게 출시하며 통계를 수집하는 쪽과, 좁게 지원하고 통제권을 팔며 아무것도 수집하지 않는 쪽.
그리고 각각의 위험도 다르다 — 전자는 기능 목록이 계속 길어지며 초점을 잃을 위험이 있고, 후자는 지원 범위가 좁아 밀려날 위험이 있다.

여기서 관찰할 수 있는 일반 원리가 있다.
도구 범주가 형성되는 초기에는 “무엇을 지원하는가”가 승부처로 보이고, 실제로 초기 스타 수는 그 축을 따른다.
그러나 그 범주가 인프라가 되면 축이 바뀐다 — 무엇을 지원하는지가 아니라 어떤 약속을 지키는지가 된다.
어느 축이 언제 우세해질지는 이 도구들이 취미 프로젝트로 남는지 팀의 표준 도구가 되는지에 달려 있고, 그 분기점에서 AGPL과 MIT라는 선택이 다시 결정적으로 작용할 것이다.
