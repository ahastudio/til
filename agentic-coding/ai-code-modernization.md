# AI 코드 현대화를 준비하는 여섯 단계: 병목은 변경을 만드는 일에서 조직을 움직이는 일로 옮겨 간다

원문: [How to prepare for AI-driven code modernization projects  | Claude by Anthropic](https://claude.com/blog/how-to-prepare-for-ai-driven-code-modernization-projects)

## 소개

Anthropic의 Jonah Ezekiel과 Lexie Tonelli가 2026년 9월 23일 Claude 블로그의 “Notes from the Field” 시리즈에 쓴 글이다.
이 시리즈는 Anthropic의 포워드 디플로이드 엔지니어(FDE)가 실제 고객 배포에서 얻은 모범 사례를 나누며, 이번 글은 대규모 코드 현대화 프로젝트를 관리한 경험을 다룬다.

글의 출발점은 이렇다.
예전에는 여러 해에 걸친 전사적 작업으로 잡히던 코드 현대화가 이제 몇 달, 때로는 몇 주에 끝날 수 있지만, 그 앞뒤의 조직적 작업은 대개 그대로다.
중요한 은행 시스템의 모든 변경은 변경 관리, 검토, 승인을 거쳐야 하고, 그 과정은 규제 기관과 감사인과 사업이 요구하기 때문에 견고하다.
그런데 그 과정은 사람이 변경을 쓰고 사람이 diff를 검토한다는 가정 위에 세워졌다.
에이전트가 변경 작성을 빠르게 하면, 병목은 변경을 만드는 일에서 그 변경을 중심으로 조직을 움직이는 일로 옮겨 간다.

그래서 글은 현대화를 실행하기 전에 기업이 해야 할 일을 여섯 단계로 나눈다.

1. 목표 정하기: 현대화된 코드가 가져야 할 기술 스택과 동작.
2. 인증서(certificate) 만들기: 변경이 목표 상태에서 옳다고 여겨지려면 충족해야 할 조건.
3. 승격 정책(promotion policy) 정하기: 인증된 변경이 만들어지는 속도로 프로덕션에 들어가는 경로.
4. 전제 조건 갖추기: 환경, CI/CD, 검토 역량, 승인.
5. 에이전트 워크플로 만들고 다듬기: 현대화를 여러 작은 병렬 하위 에이전트 작업으로 나누는 맞춤형 Claude Code 다이나믹 워크플로.
6. 현대화 실행하기: 코드베이스의 작은 부분에서 처음부터 끝까지 증명한 뒤 규모를 키우기.

## 동작 방식

### 1단계: 목표를 정하면 현대화의 종류가 정해진다

| 종류     | 무엇인가                                                  | 고르는 때                                                         | 목표에 필요한 것                                                    |
| -------- | --------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------- |
| 업리프트 | 같은 스택의 버전 올리기(예: C++11 → C++20)                | 스택은 괜찮지만 버전이 뒤처짐: 수명 끝난 런타임, 미패치 보안 문제 | 런타임 버전과 패키지 집합                                           |
| 트랜스폼 | 동작은 그대로 두고 스택을 바꾸는 재작성(예: COBOL → Java) | 스택이 문제이고 동작은 신뢰함                                     | 업리프트의 모든 것과 새 코드가 따를 언어, 프레임워크, 아키텍처 관례 |
| 리이매진 | 동작을 바꾸며 새 아키텍처로 새로 만들기                   | 코드와 함께 동작도 바꿔야 함                                      | 트랜스폼의 모든 것과 새 시스템의 서면 동작 명세                     |

어느 쪽으로 갈지는 조직 안에서 자주 논쟁이 된다.
글에 따르면 프로덕션에 가장 가까운 사람들은 위험을 가두려고 동작은 그대로 두고 스택만 바꾸기를 원하고, 코드베이스와 함께 살아온 엔지니어와 사업 쪽 이해관계자는 기술 부채를 갚고 새 요구 사항을 넣고 싶어 한다.
두 입장 모두 합리적이지만, 결론을 내지 않으면 나중에 특정 변경이 “옳은지”를 두고 다시 다투게 된다.

현재 시스템을 이해하는 것이 좋은 첫걸음이다.
Claude는 의존성을 지도로 그리고 아무도 만든 기억이 없는 작업 흐름을 문서로 만들며, 코드 현대화 플러그인의 `assess`, `map`, `extract-rules` 명령은 소스 인용과 함께 비즈니스 규칙을 캐내 엔지니어가 검토하게 한다.
그러나 Claude의 탐색만으로는 레거시 시스템의 동작을 다 담지 못할 수 있으니, 사업 사용자와 개발자 인터뷰와 내부 문서로 빈칸을 채워야 한다.
글은 비용 절감이 대부분의 현대화를 이끈 목표가 아니었고, 가장 중요한 이점은 위험 감소, 곧 미패치 취약점, 지원이 끝난 런타임, 줄어드는 전문가 풀의 위험을 줄이는 것이라고 말한다.

### 2단계: 인증서는 사람 없이 확인할 수 있는 조건의 묶음이다

인증서는 모든 현대화 변경이 충족해야 할 조건이나 테스트의 집합이다.
각 조건은 사람이 루프에 없어도 확인할 수 있어야, 에이전트 워크플로가 변경이 인증서를 충족할 때까지 반복하거나 충족하지 못하면 사람의 검토로 넘길 수 있다.
글이 드는 후보는 다음과 같다.

- 원래 테스트 모음 통과
- 현대화 중 Claude가 쓴 테스트 통과
- 합의한 테스트 커버리지 기준 충족
- 성능 벤치마크가 합의한 범위 안
- 매번 새 컨텍스트 창에서 하는 Claude의 독립적 적대적 검토에서 막는 문제 없음
- 사용자 인터페이스라면 Claude의 컴퓨터 사용으로 회귀 없음
- 같은 입력에서 현재 판과 목표 판이 같은 출력(실제, 기록된, 또는 Claude가 만든 입력)
- 저장된 상태와 전송 형식이 두 판 사이에서 왕복 가능
- 합의한 기간 동안 스테이징에서 오류율, 지연, 경보에 회귀 없음
- 정적 분석과 보안 검사에서 새 발견 없음
- 컴파일 대상이라면 깨끗한 빌드와 타입 검사 통과

인증서는 변경을 검토하고 프로덕션으로 올릴 사람들과 함께 써야 한다.
글이 제시하는 좋은 확인법은, 그 사람들이 인증서의 증거만으로 병합하는 것을 편하게 느끼겠느냐는 것이다.
업리프트는 원래 코드베이스와의 동등성을 원래 테스트 모음으로 확인할 수 있지만, 트랜스폼은 원래 테스트가 새 스택에서 거의 돌지 않아 프로덕션 트래픽 재생, 구판과 신판의 차등 테스트, 프로덕션 병행 배포가 대부분의 일을 한다.
리이매진은 동작 명세에 기대므로 가장 어렵고, 명세가 기존 시스템보다 덜 객관적이라 모델의 판단이 더 많이 들어가 결과의 편차가 커질 수 있다.
오래된 시스템은 테스트 커버리지가 얇고, 테스트가 불안정하며, 원격 측정이 거의 없기 쉬우니, 강한 인증서를 세우기 어렵다면 Claude로 프로덕션 병행 환경, 재생 하네스, 추가 테스트 같은 빠진 증거부터 만드는 것이 이 단계에서 가장 쓸모 있는 일이다.

### 3단계: 승격 정책은 사람의 검토 깊이를 미리 정한다

에이전트는 어떤 사람 팀이 diff 하나하나를 검토하는 것보다 훨씬 빨리 변경을 만든다.
승격 정책은 미리 적고 합의한 계층형 검토 경로로, 변경마다 사람의 검토 깊이를 정해 현대화가 받아들일 만한 일정에 끝나게 한다.
글이 어디서나 통한다고 보는 규칙은 네 가지다.

- 영향 범위와 에이전트 확신도로 변경을 계층화하고, 조직의 기존 변경이나 위험 분류가 있으면 그것을 쓴다. 핵심 경로는 사람이 전부 검토한다.
- 반복되는 플래그는 원인에서 고친다. 같은 종류의 플래그가 계속 나오면 하나씩 검토하지 말고 워크플로나 인증서를 고친다.
- 출력 형식을 검토자와 함께 설계한다. 어떤 정보와 형식이 검토를 가장 빠르게 하는지 합의하고, 5단계의 초기 샘플을 검토하게 한다.
- 전문가(SME)의 시간을 효율적으로 배분한다. SME는 모든 diff를 읽지 않지만, 그들의 판단이 여전히 가장 희소한 입력이니, 가장 위험한 계층의 변경과 그 안에서 플래그가 붙은 에이전트의 결정으로 곧장 가게 한다.

마감이 급한 현대화, 예를 들어 런타임 지원이 끝나는 경우는 더 가벼운 사람 검토와 변경당 더 많은 위험을 받아들이는 명시적 합의가 필요하고, 일정이 긴 현대화는 더 깊은 검토와 느린 전환을 감당할 수 있다.
규제 환경에서는 개별 승인자가 나쁜 변경의 위험을 지기 때문에 가벼운 검토 경로를 불편해하는데, 글은 승격 정책의 지시가 조직의 맨 위에서 나오고 미리 합의돼야 프로덕션에 간 버그의 책임이 승인한 사람 한 명에게 씌워지지 않고 공유된다고 말한다.

### 4단계: 전제 조건은 다른 팀의 대기열을 거친다

이 단계의 많은 일은 현대화 팀 밖, 곧 호스트를 맡는 플랫폼이나 인프라 팀, 테스트 역량을 맡는 QA나 릴리스 엔지니어링 팀, 승인을 맡는 보안과 컴플라이언스 팀을 거친다.
각 팀은 자기 대기열과 승인 절차가 있으니, 요구 사항이 보이는 즉시, 흔히 1~3단계가 진행되는 동안 대화를 시작해야 한다.

| 영역                | 준비할 것                                                                                                                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 환경                | 워크플로를 돌릴 전용 원격 호스트, 인증서가 요구하는 테스트 역량, 원격 측정이나 프로덕션 병행 환경이나 재생용 데이터                                                                                         |
| 코드베이스와 CI/CD  | 빌드 로그, 임포트 분석, 런타임 추적에 근거한 의존성 지도, 의존성 처리 계획, 호환성 검사, 코드 동결 정책, 개발자 대상 공지 계획                                                                              |
| 팀과 검토           | 의존하는 다른 팀의 참여 방식 합의와 검토자 시간 확보                                                                                                                                                        |
| 보안과 컴플라이언스 | 소스 코드에 승인된 모델 접근 경로, 최소 권한(현대화 브랜치에만 쓰기, 프로덕션 자격 증명 없음), 비밀과 개인정보 마스킹, 변경마다 에이전트 기록과 인증서 증거에 연결된 PR, 새 의존성의 라이선스와 취약점 검사 |

### 5단계와 6단계: 워크플로를 고치고, 작게 증명한 뒤 키운다

Claude Code로 코드베이스를 현대화할 맞춤형 다이나믹 워크플로([[dynamic-workflows]])를 만든다.
글은 코드 현대화 플러그인에서 시작하고, 목표, 인증서, 승격 정책, 코드베이스, 문서, 인증서가 요구하는 데이터 원천과 도구를 모두 파일 시스템이나 MCP로 Claude가 닿을 수 있는 곳에 두라고 권하며, 이 글 자체를 Claude에게 맥락으로 줘도 된다고 한다.
그것이 갖춰지면 워크플로를 만드는 일은 쉬운 부분이라는 것이다.
코드베이스의 작은 부분에 적용해 SME가 변경, 에이전트의 과정, 인증서 충족의 증거를 검토하게 하고, 문제가 드러나면 각 변경이 아니라 워크플로를 고친다.

실행은 코드베이스의 작은 부분에서 승격 정책을 거쳐 변경을 착지시키는 데까지 처음부터 끝까지 해 보는 것으로 시작한다.
싸게 고칠 수 있을 때 고치고, 확신이 설 때까지 반복한 뒤 전체로 넓힌다.
트랜스폼과 리이매진은 기존 시스템 옆에 목표를 만들고 완성되면 전환하지만, 업리프트는 개발이 계속되는 살아 있는 코드베이스를 그 자리에서 현대화하는 선택지도 있다.
그 경우 잎에서 안쪽으로 논리적 구획을 나누고, 한 구획씩 동결해 현대화하며, 현대화된 구획을 새 커밋이 되돌리지 못하게 CI/CD로 막는 방식이 통했다고 한다.

## 값 정하기

### 비용은 파일럿에서 재고, 파일럿이 볼 수 없던 것은 미지수로 둔다

글은 토큰 비용의 주요 요인을 네 가지로 든다.

| 요인                                           | 왜 비용을 키우는가                                           |
| ---------------------------------------------- | ------------------------------------------------------------ |
| 읽어야 할 코드와 바꿔야 할 코드의 비율         | 바꾸지 않을 코드도 이해하려면 읽어야 한다                    |
| 인증서가 얼마나 복잡한가                       | 규제 환경에서는 변경을 쓰는 것보다 검증이 대개 더 큰 몫이다  |
| 인증서가 요구하는 새 테스트와 테스트 수리의 양 | 얇은 테스트 커버리지를 채우는 일이 곧 비용이다               |
| 실행 중 다른 팀의 병합에서 오는 조정 작업      | 살아 있는 코드베이스에서는 현대화하는 동안에도 코드가 바뀐다 |

작은 부분의 현대화에서 토큰 사용량을 재 나머지를 외삽하되, 살아 있는 코드베이스의 조정처럼 파일럿이 볼 수 없던 것은 미지수로 두면 전체 현대화의 비용 하한을 추정할 수 있다.
파일럿 측정은 어디를 최적화할지도 보여 준다.
가장 많은 토큰을 쓴 부분을 찾고, 계산이 무거운 검증 신호는 더 싼 관문 뒤에 둬 쉬운 검사가 통과한 뒤에만 돌게 한다.
인증서가 완전히 확인하는 기계적이고 양 많은 일에는 Sonnet처럼 비용과 능력의 균형을 잡은 모델을 쓰고, 어려운 변환과 정확성을 검증하는 적대적 검토에는 더 똑똑한 모델을 둔다.
싼 모델이 인증서를 충족하지 못할 때 비싼 모델로 올릴 수도 있지만, 싼 시도 여러 번이 비싼 시도 한 번보다 더 들 수 있으니 파일럿에서 재시도율을 꼼꼼히 봐야 한다.

## 함정

### 현대화 종류를 정하지 않으면 “옳음”의 논쟁이 변경마다 되살아난다

글이 가장 먼저 경고하는 것은 목표의 모호함이다.
트랜스폼과 리이매진 사이에서 결론을 내지 않으면, 동작이 조금 달라진 변경마다 그것이 버그인지 개선인지를 두고 다투게 된다.
인증서가 무엇과 비교할지, 곧 기존 코드와 비교할지 동작 명세와 비교할지가 목표에 달려 있으므로, 이 결정이 흔들리면 인증서도 함께 흔들린다.

### 리이매진은 인증서가 가장 약한 곳에서 가장 많은 판단을 요구한다

리이매진은 기존 시스템이라는 객관적 기준이 없어 동작 명세에 기대야 하고, 모델의 판단이 더 많이 들어가 결과의 편차가 크다.
글은 명세가 분명해지면서 인증서를 고치게 될 것이고, 명세의 빈틈이 여기서 가장 먼저 드러난다고 말한다.
동작을 바꾸고 싶다는 욕심이 가장 큰 곳이, 검증이 가장 어려운 곳이다.

### 승인자 개인에게 책임이 남으면 가벼운 검토 경로는 작동하지 않는다

승격 정책이 아무리 잘 설계돼도, 나쁜 변경의 책임이 그것을 승인한 사람에게 돌아간다면 승인자는 모든 변경을 깊이 검토하려 할 것이다.
그러면 에이전트가 만든 속도는 검토에서 다시 막힌다.
글이 승격 정책의 지시를 조직의 맨 위에서 내리고 미리 합의하라고 하는 이유가 이것이다.

## 체크리스트

- 업리프트, 트랜스폼, 리이매진 중 무엇인지 이해관계자가 합의했는가?
- 리이매진이라면 사용자 그룹과 합의한 서면 동작 명세가 있는가?
- 인증서의 모든 조건을 사람 없이 확인할 수 있는가?
- 검토자들이 인증서의 증거만으로 병합하는 것을 편하게 여기는가?
- 승격 정책이 영향 범위와 에이전트 확신도로 계층을 나누고, 핵심 경로를 사람이 전부 검토하게 하는가?
- 승격 정책이 조직의 맨 위에서 승인됐고 책임 공유가 문서로 합의됐는가?
- 워크플로가 현대화 브랜치에만 쓸 수 있고 프로덕션 자격 증명이 없는가?
- 모든 변경의 PR이 에이전트 기록과 인증서 증거에 연결되는가?
- 작은 구획에서 승격 정책을 거쳐 프로덕션까지 한 번 끝까지 가 봤는가?
- 파일럿의 토큰 사용량과 재시도율을 재서 전체 비용 하한을 추정했는가?

## 기억할 원칙

### 속도가 오르면 검증과 합의가 먼저 준비돼 있어야 한다

이 글의 여섯 단계 가운데 에이전트가 코드를 쓰는 단계는 다섯 번째이고, 글 스스로 그것을 쉬운 부분이라고 부른다.
나머지 단계는 모두 무엇이 옳은지, 그것을 어떻게 증명하는지, 누가 얼마나 검토하는지, 어떤 권한으로 돌리는지를 정하는 일이다.
에이전트가 변경을 만드는 속도가 빨라질수록, 그 변경을 받아들이는 조직의 기준이 미리 정해져 있지 않으면 속도는 검토 대기열에서 사라진다.

### 검토는 끝이 아니라 처음에 몰아서 한다

글이 강조하는 반전은 SME의 시간을 프로젝트의 끝이 아니라 처음에 쓰게 하는 것이다.
전통적인 방식에서는 변경이 다 만들어진 뒤에 검토가 몰리지만, 여기서는 SME가 인증서와 워크플로와 초기 샘플을 먼저 검토하고, 그 서명이 이후의 가벼운 검토 경로를 정당화한다.
희소한 전문가의 판단을 개별 diff가 아니라 diff를 만드는 규칙에 쓰면, 적은 시간으로 훨씬 많은 변경을 덮을 수 있다.
