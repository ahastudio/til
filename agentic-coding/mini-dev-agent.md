# mini-dev-agent: 3B 로컬 모델로 에이전트를 직접 만들어 보는 PyCon 튜토리얼

<https://github.com/charsyam/pycon2026-tutorial-ai-agents>

## 소개

`mini-dev-agent`는 PyCon Korea 튜토리얼용 저장소다.
부제는 “로컬 LLM으로 AI 에이전트 직접 구현하기”이고 별명은 “나만의 가재”다.
목표를 README가 한 문장으로 밝힌다 — “LLM을 쓰는 개발자”가 아니라 “LLM 도구를 만드는 개발자”가
되는 것이다.
Claude Code·Cursor·Codex류 도구의 핵심 구조를 소형 모델 하나로 직접 만들어 이해하게 한다.

요구 환경이 낮다.
Python 3.10 이상과 OpenAI 호환 로컬 LLM 서버(llama.cpp·Ollama·vLLM 등)만 있으면 되고, GPU는
필요 없으며 Qwen2.5-3B-Instruct 같은 소형 모델로 동작한다.
저장소는 Python으로 작성됐고 2026년 8월 15일에 만들어져 8월 17일에 마지막으로 푸시됐으며, 공개
시점 스타는 3개다.
라이선스 파일은 없다.

구성은 다섯 단계 실습 폴더와 완성본 하나다.

| 폴더          | 내용                                              |
| ------------- | ------------------------------------------------- |
| `tutorial-1/` | `ask_llm` 하나만 채운다                           |
| `tutorial-2/` | Agent Loop — 1단계가 완성된 상태에서 시작         |
| `tutorial-3/` | 도구 상자 — 1·2단계가 완성된 상태                 |
| `tutorial-4/` | 가드레일 — 1~3단계가 완성된 상태                  |
| `tutorial-5/` | 재고 감시봇(응용)                                 |
| `final/`      | 완성본 — 도구 15개, Plan→Execute→Verify, RAG      |

다섯 단계의 흐름은 이렇게 요약돼 있다 — 대화(LLM에 말 걸고 한계를 만나기), Agent Loop(LLM이
도구를 부르는 루프), 도구 상자(“함수 + 맵 한 줄 + 스키마 한 칸”), 가드레일(workspace 격리와 검증
모델, “사실은 코드가 책임진다”), 감시봇(“어디에 LLM을 **안** 쓸지 배우기”).
저장소 루트에는 `ask.sh`도 있는데, `curl` 한 번으로 LLM에 물어보게 해서 “LLM 서버는 그냥 HTTP
서버다”를 눈으로 확인시키는 스크립트다.

모든 폴더는 같은 방식으로 돌아간다 — `run.sh.example`을 `run.sh`로 복사해 `LLM_BASE_URL`·`LLM_MODEL`·`LLM_API_KEY`를
채우면 된다.
`run.sh`는 `.gitignore`에 있어 키를 넣어도 커밋되지 않는다.
4단계의 검증 모델은 기본 모델과 다른 모델을 쓰며 기본값은 `unsloth/Qwen3-1.7B`다.

## 각 단계가 가르치는 것

### 1단계 — LLM이 무엇을 모르는지 눈으로 보게 만든다

1단계에서 채울 것은 `llm.py`의 `ask_llm` 하나뿐이고, 실제로 쓸 줄은 두 줄이다 —
`client.chat.completions.create(...)`를 부르고 `response.choices[0].message.content or ""`를
반환하는 것이다.
`or ""`를 붙이는 이유까지 README가 설명한다 — `content`가 `None`일 수 있고, 나중에 도구를 부를
때가 그렇다는 것이다(“답 대신 ‘이걸 불러줘’가 오거든요”).

그다음이 이 단계의 핵심이다.
질문 두 개를 나란히 보낸다 — “파이썬에서 리스트와 튜플의 차이가 뭐야?”는 3B 모델도 잘 답하고,
“오늘 날짜와 지금 시각을 YYYY-MM-DD HH:MM 형식으로만 답해”는 `2023-10-05 13:23` 같은 값을
지어낸다.
README는 “틀렸다고 말해주지도 않습니다, 그냥 그럴듯하게 지어냅니다”라고 적는다.
그리고 ②가 ①보다 어려워서 틀린 게 아니라 오히려 반대 — ①은 개념 설명이라 어려운 질문이고 ②는
초등학생도 아는 것 — 이라는 대비를 표로 정리한다.

접힌 상세 블록에는 예상 질문에 대한 답이 준비돼 있다.
“ChatGPT는 날짜 잘 맞히던데요?”에 대해, ChatGPT·Claude 같은 서비스는 시스템 프롬프트에 오늘
날짜를 넣어 주므로 모델이 아는 게 아니라 서비스가 매번 알려주는 것이며, 시각은 초 단위로 흐르니
그렇게 못 메운다고 설명한다.
형식을 지정해 묻는 이유도 밝힌다 — 열어놓고 물으면 대체로 “알 수 없다”고 거절해서 지어내는 걸
못 보게 된다는 것이다.

이 단계는 “기억”에 대한 관찰로 끝난다.
멀티턴 대화가 되는데도 기억을 따로 만들지 않았고, `history` 리스트에 dict를 쌓아 매번 통째로
보냈을 뿐이며 그게 곧 기억이라는 것이다.

### 2단계 — 루프의 정체는 왕복이다

`agent.py`의 주석이 이 단계를 세 문장으로 정리한다 — LLM은 도구를 실행하지 못하고 “이걸 불러줘”라고
말할 뿐이며, 실행하는 건 우리 Python 코드고, 결과를 다시 넣고 또 물어보는 그 왕복이 루프다.

채울 TODO는 둘이다.
도구를 부르지 않았을 때 `message.content`를 `assistant`로 `history`에 넣고 반환하는 것(2-1), 그리고
도구 결과를 `{"role": "tool", "tool_call_id": call.id, "content": result}`로 넣는 것(2-2)이다.
코드 주석이 실무에서 실제로 틀리는 지점들을 미리 짚는다 — LLM이 “이 도구를 불러줘”라고 한 말도
대화에 남겨야 하며 이게 빠지면 다음 요청에서 `tool` 결과가 짝을 잃는다는 OpenAI 규약, 그리고
`arguments`가 dict가 아니라 문자열로 오므로 파싱해야 한다는 점이다.
무한 루프는 `MAX_TOOL_CALLS = 8`로 끊고, 한계에 닿으면 `[중단] 도구 호출 한계(8회) 도달`을
답변으로 넣는다.

### 4단계와 완성본 — 가드레일은 두 갈래다

첫째 갈래는 코드로 막는 것이다.
`final/tools/safety.py`의 `safe_path()`가 입력 경로를 `workspace/` 안의 절대경로로 정규화하고,
`os.path.commonpath([candidate, WORKSPACE]) != WORKSPACE`이면 `SafetyError`를 던진다.
여기에 파일 크기 제한 `MAX_FILE_SIZE = 100_000`바이트와 검색 결과 제한 `MAX_SEARCH_HITS = 50`이
붙는다.

둘째 갈래는 두 번째 모델로 검증하는 것이다.
`final/verifier.py`의 `verify(request, source, final)`은 원래 요청·도구가 반환한 원본 데이터·최종
답을 받아 `{"ok": bool|None, "reason": str}`을 돌려준다.
시스템 프롬프트가 통과·실패 기준을 구체적으로 나눈다 — 종목코드(삼성전자=005930.KS)나 도시명,
단위 변환처럼 같은 대상을 다르게 표기한 것은 환각이 아니라 통과이고, 원본이 비었거나 오류·스텁·미설치인데
답이 사실을 지어냈거나 원본에 전혀 없는 숫자를 만들어냈거나 요청한 동작이 실제로 수행되지 않은
경우만 실패다.
docstring은 이 검증의 한계를 스스로 밝힌다 — 작은 모델은 거친 오류(빈 결과·오류·스텁·근거 없는
환각)는 잡지만 미세한 사실 오류는 놓칠 수 있어 “큰 그림 검증” 용도라는 것이다.

구현 세부에 실전에서 얻은 흔적이 남아 있다.
`max_tokens`를 4096으로 크게 잡는 이유를 주석이 설명하는데, 검증 모델 Qwen3가 reasoning 모델이라
답을 내기 전에 생각을 토큰으로 먼저 쓰므로 기본값 512로는 생각하다 잘려서 본문이 빈 문자열로
돌아오고 검증이 매번 파싱 실패가 된다는 것이다.
검증 모델 호출이 실패하면 `ok`가 `None`이 되고 “가드레일만 비활성, 본체는 계속 간다”는 주석이
붙는다.

완성본의 도구 인프라는 `final/tools/registry.py`에 있고 “openclaw 류 실전 패턴의 축소판”이라고
자칭한다.
함수 시그니처와 타입힌트, docstring에서 OpenAI 도구 스키마를 자동 생성하고, `@tool` 데코레이터가
`{name, func, schema}`로 묶어 등록하며, 모든 도구 호출 앞뒤로 가로채는 before·after 훅으로 승인·로깅·차단을
건다.
도구 추가는 “함수 1개 + `@tool`”이다.
실제로 등록된 도구는 15개다 — `get_datetime`, `list_files`, `read_file`, `write_file`,
`search_text`, `web_search`, `get_weather`, `get_news`, `get_stock`, `get_today_schedule`,
`find_places`, `check_stock`, `speak`, `send_slack`, `send_discord`.

RAG도 최소 구현이다.
`final/rag.py`는 임베딩과 벡터 DB 없이 동작하며, 문서를 500자 단위로 자르고(문단 경계는 단순화를
위해 무시) 키워드 겹침 점수로 상위 3개 chunk를 골라 프롬프트에 끼워 넣는다.

완성본은 작은 모델을 위해 루프를 아예 분해한다.
`final/mini_agent.py`의 주석이 이유를 밝힌다 — 작은 모델은 “계획하며 동시에 실행”하는 뒤엉킨
루프에 약하므로 Planner(요청을 JSON 작업 큐로 한 번에 분해), Executor(큐를 하나씩 pop하고 `$N`을
앞 결과로 치환해 실행), Verifier(판정)로 단계를 나누면 각 단계가 “작은 모델이 잘하는 단발 작업”이
되어 1.7B에서도 동작한다는 것이다.

### 5단계 — 어디에 LLM을 쓰지 않을지

5단계는 닌텐도 스위치 재고를 지켜보다 뜨면 디스코드·슬랙으로 알리는 감시봇이다.
흐름이 명확히 갈린다 — `fetch_page`가 증거를 뽑고, `decide_stock`이 코드로 판정하며, `in_stock`이면
알리고 `sold_out`이면 조용히 있고 `unknown`일 때만 `diagnose_page`가 LLM을 부른다.

이 배분의 근거가 이 단계의 요점이다.
가장 순진한 감시봇은 `if "품절" not in html: 알림()`인데, ‘품절’이 안 보이는 이유는 세 가지 —
진짜 재고, 페이지가 깨짐, 엉뚱한 페이지 — 라는 것이다.
README가 이것을 한 문장으로 단언한다 — “‘품절’이 없다는 건 재고가 있다는 뜻이 아니다, 내가
보려던 페이지를 못 보고 있다는 뜻일 수도 있다.”
그래서 재고 판정은 규칙이 명확하니 코드가, 페이지 진단은 규칙으로 못 적으니 LLM이 맡는다.

`decide_stock`의 실제 구현이 이 원칙을 세 값 논리로 표현한다.
오류나 200이 아닌 상태 코드면 `unknown`, HTML이 너무 짧으면(껍데기·차단 페이지) `unknown`, 기대한
문구가 제목에 없으면(홈으로 리다이렉트된 경우) `unknown`, 재고 영역 자체가 없으면 `unknown`이다.
세 번째 검사에 붙은 주석이 이유를 밝힌다 — 이게 없으면 홈페이지의 ‘품절’을 보고 정상 품절이라
착각한 채 영원히 조용히 있게 되며, 그것은 “헛알람보다 더 위험한 ‘조용한 실패’”라는 것이다.

운영 방식도 두 갈래로 비교한다.
`while True + sleep`은 바로 보이지만 터미널을 닫으면 죽고 재부팅하면 끝이며, `--once` + cron은
로그로 보고 터미널을 닫아도 살고 재부팅하면 다시 뜬다.
README의 결론은 “죽지 않는 프로그램을 만들려 애쓰지 말고, 죽어도 되는 프로그램을 만들고 되살리는
건 OS에게 맡긴다”이며, cron으로 돌리면 프로세스가 매번 새로 뜨므로 “이미 알렸다”를 `.watch_state.json`에
저장한다 — “루프를 밖으로 빼면 기억도 밖으로”다.

마지막에 “매너” 절이 있다.
`SLEEP_SECONDS`는 60초 이상 유지하고(초 단위 조회는 차단당한다), 대상 사이트의 `robots.txt`와
이용약관을 확인하며, 구매 자동화가 아니라 알림까지만 — “그게 이 예제의 선이다”.

## 분석

### 이 튜토리얼의 실제 교재는 코드가 아니라 실패 장면이다

에이전트 튜토리얼의 표준 구성은 “프레임워크를 설치하고 에이전트를 만든다”이다.
이 저장소는 그 순서를 버리고 1단계 전체를 “LLM이 지금 몇 시인지 지어내는 장면”에 쓴다.
채울 코드는 두 줄인데 README는 7,347바이트에 이르며 그 대부분이 왜 이 질문을 이렇게 물어야
하는지에 대한 설명이다.

이 배분이 의도적이라는 증거는 접힌 상세 블록에 있다.
“그냥 ‘지금 몇 시야?’라고 열어놓고 물으면 모델이 거절하기도 한다, 형식을 주면 빈칸을 채우려
들면서 학습 시점의 값을 그대로 뱉는다” — 저자는 실패를 재현하기 위해 질문을 설계했고, 재현이
실패하는 경우까지 미리 안내한다.
학습자가 “나는 이 장면을 못 봤다”고 헤매지 않게 하려는 배려이며, 동시에 이 장면을 보는 것이 이
단계의 유일한 목표라는 선언이다.

같은 설계가 5단계에서 반복된다.
`./run.sh demo`가 네 가지 상황을 비교해 보여 주고, 홈페이지가 HTTP 200에 `stock` 블록에 ‘품절’까지
갖고도 왜 위험한지를 직접 목격시킨다.
결론을 문장으로 주는 대신 오판이 일어나는 순간을 재현하는 것 — 이것이 이 저장소가 일관되게 쓰는
교수법이다.
그리고 이 교수법은 에이전트라는 주제에 특히 잘 맞는다.
에이전트의 실패는 예외를 던지지 않고 그럴듯한 답으로 나타나므로, 실패를 “설명”받은 학습자는
현장에서 그것을 알아보지 못한다.

### 소형 모델을 고른 것은 접근성 때문만이 아니다

“GPU 불필요, Qwen2.5-3B로 동작”은 표면적으로 워크숍 물류 문제의 해법이다.
참가자 수십 명이 각자 노트북에서 돌려야 하니 큰 모델을 전제할 수 없다.

그러나 이 선택이 교육적으로 하는 일이 더 크다.
3B 모델은 잘 실패하고, 그 실패가 눈에 보이며, 무엇보다 프롬프트로 덮이지 않는다.
큰 모델로 같은 튜토리얼을 만들면 1단계의 핵심 장면 — 시각을 지어내는 것 — 부터 재현되지 않을
수 있고(서비스가 시스템 프롬프트로 날짜를 넣어 준다는 그 설명이 정확히 이 문제다), 도구 없이도
어지간한 답이 나와서 “왜 도구가 필요한가”라는 질문 자체가 서지 않는다.
약한 모델은 아키텍처를 드러내는 조명이다.

완성본의 구조가 이 논리의 귀결이다.
`mini_agent.py`가 Plan→Execute→Verify로 루프를 분해한 이유는 우아함이 아니라 “작은 모델은
계획하며 동시에 실행하는 뒤엉킨 루프에 약하다”는 제약이다.
제약이 아키텍처를 낳고, 그 아키텍처가 하필 현재 실무에서도 유효한 패턴이라는 것 — 큰 모델에서도
계획과 실행의 분리는 신뢰성을 올린다 — 이 이 튜토리얼이 3B로 가르치고도 전이 가능한 것을
가르치는 이유다.

### 역할 배분이 이 저장소의 진짜 주장이다

다섯 단계를 관통하는 문장은 두 개다 — 4단계의 “사실은 코드가 책임진다”와 5단계의 “어디에 LLM을
**안** 쓸지 배우기”다.
이 둘은 같은 주장의 앞뒷면이며, 저장소의 코드가 실제로 그 주장을 따른다.

`decide_stock`이 순수 코드이고 LLM은 `unknown`일 때만 호출되는 구조는 이 주장의 가장 선명한
구현이다.
판정 기준이 명확한 일(HTTP 200인가, HTML이 충분히 긴가, 제목에 기대 문구가 있는가)은 코드가
결정론적으로 처리하고, 규칙으로 적을 수 없는 일(왜 이 페이지를 못 봤는가)만 LLM에 넘긴다.
`safe_path`가 `commonpath` 비교로 경로 탈출을 막는 것도 같은 원리다 — 샌드박스 경계를 프롬프트로
부탁하지 않고 코드로 강제한다.

이 배분 원칙이 지금 유의미한 이유는 반대 방향의 압력이 강하기 때문이다.
프레임워크와 제품은 LLM이 더 많은 결정을 내리게 만드는 쪽으로 경쟁하고, 그것이 자율성으로
홍보된다.
이 저장소는 초급 튜토리얼의 형식으로 정반대의 규율을 가르친다 — 앞서 이 저장소의 다른 노트들이
정리한 “자율성을 높일수록 검증이 느슨해진다”는 관찰[^ref-ralph]과 정확히 같은 판단이며, 그것을
입문자에게 먼저 가르치는 순서를 택한 점이 드물다.

## 비평

### 루트 README의 약속과 실제 폴더가 어긋나며, 어긋난 자리가 가장 어려운 단계다

루트 README는 “각 단계 폴더의 `README.md`에 그 단계의 과제·힌트가 들어 있습니다”라고 명시한다.
실제로는 `tutorial-1/`과 `tutorial-5/`에만 README가 있고 `tutorial-2/`·`tutorial-3/`·`tutorial-4/`에는
없다.

빠진 자리가 하필 개념적 도약이 가장 큰 세 단계다.
2단계는 tool calling 규약 — assistant의 도구 요청 메시지를 history에 남겨야 하고 `tool_call_id`로
짝을 맞춰야 한다는, 처음 하는 사람이 반드시 틀리는 부분 — 을 다루고, 3단계는 도구 조합을,
4단계는 가드레일과 검증 모델을 다룬다.
1단계에 7,347바이트를 쓴 저자가 이 세 단계를 코드 주석만으로 남긴 것은 분량 판단이 아니라 미완이다.
`tutorial-2/agent.py`의 주석이 뛰어난 것은 사실이지만, 주석은 코드를 여는 사람만 읽고 README는
폴더에 들어서는 모든 사람이 읽는다.

정답 제공도 고르지 않다.
`tutorial-5/`에는 `ANSWERS.md`가 있는데 1단계는 “정답은 `../final/`”이라고만 안내한다.
`final/`은 15개 도구와 Plan→Execute→Verify가 얽힌 완성본이므로, 1단계에서 막힌 학습자가 두 줄의
정답을 찾으러 그곳을 열면 필요한 것보다 훨씬 복잡한 코드를 만난다.
단계별 정답을 단계별로 두지 않은 것은 실습 저장소의 구조적 결함이며, 강의장에서 강사가 메울 수
있는 종류의 결함이지만 이 저장소를 나중에 혼자 따라가는 사람에게는 메워지지 않는다.

`tutorial-2/`에 vim 스왑 파일 `.tools.py.swp`가 16KB로 커밋돼 있는 것도 같은 미완의 흔적이다.
`.gitignore`가 `run.sh`는 챙기면서 `*.swp`는 놓쳤다.

### 완성본 문서가 완성본 코드를 설명하지 않는다

`final/README.md`의 파일 표는 `tools.py` 하나가 `list_files`, `read_file`, `search_text`와
Safety를 담당한다고 적는다.
실제 `final/tools/`는 `registry.py`·`safety.py`·`files.py`·`web.py`·`output.py`·`places.py`·`schedule.py`·`watch.py`·`info.py`로
쪼개진 패키지이고, 등록된 도구는 셋이 아니라 15개다.

더 문제인 것은 안전장치 절이다.
“쓰기 도구는 기본 미포함(Future Extension에서 승인 모델과 함께 추가)”이라고 적혀 있는데, 실제로
`final/tools/files.py`에는 `write_file`이 `@tool`로 등록돼 있고 `_write_approval_hook`과
`_default_approval`이 함께 구현돼 있다.
즉 “나중에 추가할 것”으로 적힌 기능이 이미 들어 있다.
문서가 낡은 것이지 코드가 틀린 것은 아니지만, 이 문서는 “안전장치”를 설명하는 절이라 낡음의 비용이
크다 — 학습자가 “쓰기 도구는 없으니 안심”이라고 읽고 넘어갈 수 있는 위치다.

이 불일치가 우연이 아니라는 신호가 하나 더 있다.
`final/README.md`는 각 파일에 `Part 2`, `Part 3`, `Part 4/6/8`, `Part 5`, `Part 7`이라는 번호를
붙이는데, 루트 README와 실습 폴더는 1~5단계 체계를 쓴다.
두 개의 서로 다른 목차 체계가 한 저장소에 남아 있고, `final/README.md` 쪽이 더 이른 설계의
유물이다.
튜토리얼 저장소에서 완성본 문서는 학습자가 마지막에 읽고 오래 참조하는 문서인데, 그 문서가
이전 버전을 서술하고 있다.

### 라이선스 없는 교재는 참가자가 가져갈 수 없는 교재다

이 저장소에는 라이선스 파일이 없다.
GitHub API가 `license: null`을 돌려준다.

라이선스 부재는 많은 개인 저장소에서 관행이지만, 이 저장소에서는 성격이 다르다.
이것은 컨퍼런스 튜토리얼 교재이고, 존재 목적 자체가 참가자들이 클론해서 고치고 자기 것으로 만들어
가져가는 것이다.
README의 목표 문장 — “LLM 도구를 만드는 개발자가 된다” — 은 참가자가 이 골격을 자기 프로젝트에
쓰는 것을 전제한다.
그런데 라이선스가 없으면 기본값은 저작권 전면 보유이며, 참가자가 `registry.py`의 `@tool` 패턴이나
`safe_path` 구현을 자기 회사 코드에 옮겨도 되는지가 법적으로 불분명해진다.

이 문제는 고치기가 사소하다는 점에서 더 눈에 띈다.
MIT 파일 하나면 끝난다.
교육 목적으로 만든 코드에 라이선스를 붙이지 않는 것은 “가져가서 쓰라”는 메시지와 “쓸 권리를 주지
않았다”는 법적 상태를 동시에 두는 것이며, 튜토리얼의 목표와 저장소의 상태가 어긋나는 지점이다.

### 4단계의 가드레일은 저장소 자신이 5단계에서 가르치는 원칙을 지키지 않는다

4단계의 표제 원칙은 “사실은 코드가 책임진다”이고, 5단계는 판정을 코드에 맡기고 LLM을 `unknown`
분기로만 좁혀 그 원칙을 구현한다.
그런데 4단계가 실제로 도입한 가드레일의 절반은 LLM 검증기다.

이 검증기의 성질을 코드 자신이 밝힌다.
작은 모델은 거친 오류만 잡고 미세한 사실 오류는 놓치며, 검증 모델 호출이 실패하면 `ok`가 `None`이
되고 본체는 계속 간다.
즉 이 가드레일은 최선 노력(best-effort)이고 실패 시 열린다(fail-open).
방화벽으로 치면 규칙 서버가 죽으면 전면 허용으로 바뀌는 설계이며, `safe_path`가 예외를 던져
동작을 멈추는 것과 성질이 정반대다.

같은 저장소 안에 강한 버전과 약한 버전이 함께 있는데 둘의 등급이 명시되지 않은 것이 문제다.
`safe_path`는 결정론적이고 우회 불가능한 경계이고, `verify`는 확률적이고 실패 시 사라지는
권고다.
둘 다 “가드레일”이라는 한 단어로 4단계에 묶여 소개되므로, 학습자는 두 번째 모델을 붙이는 것이
첫 번째와 같은 종류의 보호라고 배울 위험이 있다.
앞서 이 저장소의 다른 노트가 정리한 대로 검증의 일부 증거는 시스템 바깥에서 와야 하는데[^ref-evals],
같은 계열의 더 작은 모델을 붙이는 것은 그 조건을 만족하지 않는다.

`mini_agent.py`의 Planner 프롬프트가 이 문제의 규모를 보여 준다.
그 프롬프트에는 “티커를 외워서 쓰지 마라”, “예시에 나온 종목으로 바꿔치기하지 마라”, “결과가
‘[확인 필요]’로 오면 지어내지 말고 그 문장을 그대로 전해라” 같은 방어 지시가 줄줄이 들어 있다.
정직한 실전 흔적이지만, 동시에 이 층에서 신뢰성을 확보하려면 프롬프트에 패치를 계속 쌓아야 한다는
증거다.
그리고 그 패치들은 3B·1.7B 모델에 특화된 것이라 학습자가 다른 모델로 옮기면 대부분 무의미해진다 —
5단계의 코드 판정은 어떤 모델에서도 그대로 유효한데, 4단계의 프롬프트 방어는 그렇지 않다.

## 인사이트

### 이 튜토리얼이 실제로 파는 것은 에이전트 구현법이 아니라 LLM을 쓰지 않을 자리를 알아보는 감각이다

다섯 단계를 다 지나면 학습자가 손에 쥐는 기술은 소박하다 — HTTP 요청 하나, 왕복 루프 하나, 함수에
데코레이터 붙이기, 경로 검사, 세 값 논리.
정작 값진 것은 그 과정에서 형성되는 판단이다 — 이 결정은 코드가 해야 하고 저 결정만 LLM에
넘긴다는 감각이다.

이 감각이 희소한 이유는 생태계가 반대 방향으로 최적화돼 있기 때문이다.
에이전트 프레임워크의 경쟁축은 “LLM이 더 많이 결정하게 하기”이고, 그것이 자율성·범용성으로
홍보된다.
프레임워크의 튜토리얼은 도구를 등록하고 LLM에게 알아서 하라고 맡기는 것을 성공으로 보여 주며,
`decide_stock`처럼 판정을 코드로 되찾아오는 예제는 거의 없다.
그래서 이 튜토리얼을 마친 학습자는 다음에 만나는 프레임워크에서 자기가 배운 규율을 지지받지 못한다.

2차 효과가 여기서 생긴다.
좋은 판단을 먼저 배운 사람이 그 판단을 실행할 도구를 찾지 못하면, 판단은 개인의 취향으로
남고 팀의 관행이 되지 못한다.
`decide_stock` 같은 코드는 프레임워크 안에서 “도구 하나”로 표현될 뿐이고, “이 판정은 절대 LLM에
맡기지 않는다”는 의도는 코드 어디에도 기록되지 않는다.
이 규율을 팀 자산으로 만들려면 프레임워크가 주지 않는 것을 스스로 만들어야 한다 — 어떤 결정이
결정론적이어야 하는지를 명시하는 문서나 검사 말이다.
튜토리얼의 성과가 개인에서 조직으로 넘어가지 못하는 지점이 정확히 여기이며, 이것은 저장소가 다룰
범위 밖이지만 이 튜토리얼을 사내 교육에 쓰려는 사람이 바로 마주칠 문제다.

### 이것은 “직접 만들어 보는 Redis·Git·Lisp” 장르가 에이전트에 도착한 사건이다

“작은 X를 처음부터 만들어 보기”는 오래된 장르다.
직접 만드는 Lisp, 직접 만드는 Git, 직접 만드는 데이터베이스, 직접 만드는 Redis가 모두 같은
형식이다 — 겉보기 복잡도는 크고 본질적 복잡도는 작은 대상을 골라, 후자를 드러내는 것이다.

이 장르가 성립하는 조건이 있다.
대상의 핵심이 몇백 줄로 재현 가능하고, 그 핵심이 상용 구현에서도 여전히 같은 모양이어야 한다.
Git이 그랬고 Redis가 그랬다.
이 튜토리얼은 에이전트가 그 조건에 도달했다고 주장한다 — Claude Code·Cursor·Codex의 핵심 구조가
`while` 루프 하나와 도구 맵 하나와 경로 검사 하나로 재현된다는 것이며, `tutorial-2/agent.py`의
전체 길이가 3.5KB라는 사실이 그 주장의 증거다.

이 관점이 예측하는 것이 있다.
어떤 기술이 이 장르에 편입되는 시점은 그 기술의 골격이 표준화되고 차별화가 다른 층으로 옮겨가는
시점이다.
Git 내부를 직접 만들어 보는 글이 쏟아질 때 Git 자체의 경쟁은 이미 끝나 있었고, 경쟁은 호스팅과
워크플로로 올라가 있었다.
같은 논리를 적용하면 에이전트 루프 자체는 이미 상품이 아니며, 남는 경쟁은 도구의 폭과 질, 컨텍스트
관리, 그리고 검증이다 — 이 저장소가 15개 도구와 Plan→Execute→Verify에 대부분의 코드를 쓴 배분이
공교롭게 그 판단과 일치한다.
루프는 3.5KB이고 도구는 그 몇 배다.

### 검증을 두 번째 모델에 맡기는 방식은 규모가 커질수록 코드 검증에 밀려난다

4단계의 검증 모델은 매 턴에 추가 추론 한 번을 붙인다.
그리고 그 추론은 reasoning 모델이라 `max_tokens` 4096을 잡아야 한다 — 생각에 쓰는 토큰이 답보다
많다는 뜻이다.
저장소가 이 값을 512에서 4096으로 올려야 했던 경위를 주석으로 남긴 것은, 검증 비용이 생성 비용의
부수 항목이 아니라 같은 자리를 다투는 항목이라는 사실의 기록이다.

이 비용 구조가 규모에서 하는 일은 분명하다.
호출당 검증 추론이 붙으면 지연과 비용이 배로 가까워지고, 그 대가로 얻는 것은 거친 오류만 잡는
확률적 보호이며 검증 모델이 죽으면 그 보호마저 사라진다.
반대로 `decide_stock` 방식의 코드 검증은 비용이 사실상 0이고 결정론적이며 죽지 않는다.
운영 규모가 커지면 이 비교는 한쪽으로 기울며, 실제로 이미 기울어 있다 — 프로덕션 에이전트의
신뢰성 확보가 “LLM으로 LLM을 검증”에서 “스키마·타입·테스트·권한으로 막기”로 옮겨온 흐름이 그것이다.

여기서 이 저장소의 단계 순서가 뜻하지 않은 것을 보여 준다.
4단계가 LLM 검증기이고 5단계가 코드 판정인데, 값의 순서로 보면 거꾸로다 — 나중에 배우는 것이 더
값지고 더 오래 유효하다.
난이도로 보면 이 순서가 맞다(LLM 검증기는 붙이기 쉽고, 무엇을 코드로 판정할지 결정하는 일은
어렵다).
그러나 이 순서는 산업이 실제로 겪은 학습 곡선을 재현하는 것이기도 하다 — 먼저 LLM으로 LLM을
감시하려 해 보고, 그것이 부족하다는 것을 겪은 뒤에 결정론적 검증으로 돌아오는 경로다.
튜토리얼이 두 단계를 다 담았으니 학습자는 그 곡선을 압축해 통과하는 셈인데, 다만 저장소가 둘의
등급을 명시하지 않았으므로 압축의 이득은 강사의 설명에 달려 있다.

### `unknown`이라는 세 번째 값이 이 저장소에서 가장 전이력이 높은 아이디어다

`decide_stock`이 돌려주는 값은 둘이 아니라 셋이다 — `in_stock`, `sold_out`, `unknown`.
그리고 구현의 대부분이 `unknown`으로 가는 경로다.
오류·비200, 너무 짧은 HTML, 제목 불일치, 재고 영역 부재가 모두 “모른다”로 수렴하고, 정상 판정은
그 관문을 다 통과한 뒤에야 내려진다.

이 설계가 값진 이유는 그것이 감시라는 문제의 본질을 정확히 표현하기 때문이다.
감시봇의 실패는 두 종류인데 비용이 대칭이 아니다 — 헛알람은 시끄럽고 즉시 발견되지만, 조용한
실패는 발견되지 않은 채 “정상 작동 중”으로 보인다.
저장소의 주석이 그것을 “헛알람보다 더 위험한 조용한 실패”라고 부른 것은 이 비대칭의 정확한
진술이다.
`unknown`은 조용한 실패를 시끄러운 무지로 바꾸는 장치다.

이 아이디어가 에이전트 전반으로 전이되는데, 정작 대부분의 도구와 프레임워크가 이것을 제공하지
않는다.
도구 호출의 반환은 관행적으로 성공값 아니면 예외이고, “실행은 됐지만 결과를 신뢰할 수 없다”는
제3의 상태를 표현할 자리가 없다.
그래서 에이전트는 빈 검색 결과와 검색 실패를 같은 문자열로 받고, 로그인 페이지로 리다이렉트된
HTML을 정상 콘텐츠로 받는다.
이 저장소의 `verify`가 `ok`에 `True`·`False` 외에 `None`을 두고 그것을 “검증 불가”로 쓴 것은 같은
발상을 검증 층에도 적용한 것이며, 두 곳에서 반복되는 이 패턴이 이 튜토리얼이 남기는 가장 오래
쓰일 자산이다.
도구를 만들 때 반환 타입에 “모른다”를 넣는 습관 하나가, 프레임워크를 바꾸고 모델을 바꾸어도
그대로 유효하다.
