# AI 네이티브 SDLC: 코드가 병목이 아니게 된 뒤 개발 과정 전체를 다시 짜기

원문: [The AI-native SDLC playbook | Claude by Anthropic](https://claude.com/blog/the-ai-native-sdlc-playbook)

HN 토론: <https://news.ycombinator.com/item?id=49420088> (6점, 4개 댓글)

## 요약

Anthropic의 Louis Claxton이 2026년 8월 21일 Claude 블로그에 올린 플레이북이다.
Applied AI 팀이 고객과 일하며 쓰는 모범 사례를
소프트웨어 개발 생명주기(SDLC)의 여섯 단계에 맞춰 정리했다고 밝힌다.
출발점은 코드가 더 이상 병목이 아니라는 진단이다.
조직은 1년 전에는 상상하기 어려웠던 속도로 AI에게 코드를 쓰게 하지만, 승인 관문,
리뷰, 인수인계, 정책은 그대로여서 Claude Code 같은 에이전트형 코딩 도구의
생산성 이득이 막힌다는 것이다.

글에 따르면 전통적인 SDLC는 기획, 설계,
구현, 테스트, 배포, 유지보수의 여섯 단계를 서로 다른 역할이 나눠 맡고,
작업은 문서와 티켓과 서명으로 단계 사이를 옮겨 다닌다.
이 구조는 코드 작성이 가장 비싸고 오래 걸리던 시대에 효율을 높이려고 만든
것이고, PRD, 추정 의식, 보안 리뷰는 몇 주에서 몇 분기에 이르는 개발 기간 동안
합의를 강제하려고 존재했다고 본다.
구현이 몇 시간으로 줄면 세 가지가 사실이 된다고 한다.
병목이 구현의 앞뒤인 기획, 리뷰와 테스트, 배포로 옮겨 가고,
사람이 모든 줄을 손으로 리뷰하는 통제는
에이전트가 diff 대부분을 쓰는 순간 따라가지 못하며,
예외가 매주나 매달 열리는 위원회를 거치므로 거버넌스 비용이 오른다.
보안 팀이 사람의 산출량에 맞춰 꾸려져 있으니 리뷰 대기열이 쌓이거나 덜 리뷰된
코드가 나가는데, 규제 산업은 둘 다 받아들일 수 없다는 예도 든다.

AI 네이티브 SDLC는 옛 통제 목표를 새로운 집행 방식과 묶은 과정이라고 정의한다.
선형 흐름 대신 루프가 되고, 각 단계는 버전 관리에 산출물 하나를 커밋하며 끝나고
다음 단계는 그것을 읽으며 시작한다.
산출물은 `intent.md`, `spec.md`, `plan.md`, diff와 테스트,
리뷰 결과가 담긴 PR, 장애 기록이다.
초기 단계에서 마크다운이 주된 형식인 이유는 제품 책임자와 에이전트가 같은 파일을
읽고 다룰 수 있기 때문이고, 커밋의 사슬이 누가 무엇을 요청했고 에이전트가 무엇을
만들었고 누가 승인했는지를 보여 주는 감사 기록이 된다고 한다.
각 플레이는 무엇이 바뀌는지, 시작하는 법, 구체적 단계, 거버넌스 고려 사항,
측정 방법으로 이루어지고, 선행 조건을 적어 채택 순서를 정한다.

### 기획과 설계

기획 단계에서는 아이디어를 낸 사람이 Claude와 브레인스토밍해
그 결과를 원래 표현 그대로 `intent.md`로 남긴다.
문제, 기대 결과, 영향받는 사용자와 시스템, 제약, 열린 질문을 담고,
제품 책임자가 검토하고 고친 뒤에 커밋한다.
엔지니어가 아닌 사람은 claude.ai나 Cowork에서 VCS 커넥터를 통해 git을 직접
쓰지 않고도 커밋할 수 있다.
저장소가 하나라면 제품 저장소의 `intent/` 폴더가 가장 단순한 보관처라고 권한다.
측정 지표로는 첫 대화부터 `intent.md` 커밋까지의 시간을 들고, 몇 주짜리
요구사항 도출 주기가 몇 시간으로 줄 것으로 기대한다.

설계 단계에서는 요구사항과 설계가 한 세션으로 합쳐진다.
Claude가 승인된 `intent.md`를 읽고 브랜드,
보안, 규정 준수, UX 스킬의 제약을 받으며 `spec.md`를 쓰고,
정책끼리 충돌해 만족시킬 수 없는 부분을 우려 사항으로 표시한다.
제품 책임자는 스펙을 쓰지 않고 검토하며,
프런트엔드라면 Claude Design(베타)으로 목업을 만들어 Claude Code로 넘긴다.
처음엔 손으로 돌리고, 나중에는 `intent.md`가 머지되면 비대화형 작업이 돌아
`spec.md`를 PR로 올리게 하라고 한다.

### 구현

구현의 기본 출발점은 Claude Code의 플랜 모드다.
엔지니어는 `spec.md`를 주고, 바뀌는 파일, 작업 순서,
증명할 테스트를 담은 계획을 받아 무엇이 깨질 수 있는지 캐묻는다.
대화를 본 적 없는 엔지니어도 계획만으로 구현할 수 있을 때까지 다듬고
`plan.md`로 커밋한다.
계획이 탄탄하면 구현이 한 번에 끝나는 경우가 많고, 구현이 계획에서 벗어나면 같은
커밋에서 `plan.md`를 고치며 훅으로 동기화를 강제하는 방안도 제안한다.
가드레일이 성숙하면 일상 작업에서는 편집마다 묻지 않는
자동 모드가 기본이 된다고 한다.

`CLAUDE.md`는 신규 입사자에게 필요한 맥락을 담는 파일로,
`/init`으로 만든 뒤 첫날 필요한 것만 남기고 한 페이지 이하로 유지하라고 권한다.
Claude가 같은 실수를 두 번 하면
그 교정을 `CLAUDE.md`에 넣는다는 규칙도 제시한다.
스킬은 일관되게 적용해야 하는 조직 지식을 실행 가능하게 만드는 수단인데,
글은 스킬이 권고형 통제일 뿐 세션이 따르도록 강제하지는 못한다고 분명히 적는다.
반드시 지켜야 하는 정책은 결정적인 훅이나 PR 단계의 재검사가 뒷받침해야 하며,
스킬은 위반을 드물게 하고 훅은 거의 불가능하게 한다는 구분이다.
구현 단계의 훅은 보호 경로 편집 차단, 편집 뒤 포매터와 린터 실행,
자격 증명 유출 방지를 맡고, 사람의 승인을 묻는 훅은 병렬 세션 전체의 임계 경로에
사람을 다시 세우므로 배포 단계에 두라고 한다.

병렬 세션은 각자 git worktree에서 도는 별도의 Claude Code 인스턴스이고,
서브에이전트는 한 세션 안에서 자기 컨텍스트와 도구 제한을 갖는 보조자다.
두세 개 세션으로 시작하고,
리뷰가 따라가는 동안에만 세션을 늘리라는 것이 실용적 상한으로 제시된다.

### 테스트

Claude에게 항상 스스로 작업을 검증할 피드백 루프를 주라고 한다.
테스트, 빌드, 스크린숏 비교를 한 명령으로 감싸고, 정량적인 목표를 주며,
버그 수정이라면 실패하는 테스트를 먼저 커밋한 뒤 테스트를 고치지 않고
통과시키게 한다.
고치는 에이전트가 자기 코드의 검사를 약하게 만들 수 없도록,
수정 작업 중 테스트 파일 편집을 막는 훅으로 루프 자체를 보호하라고 한다.
지속적 평가(eval)는 단계 관문형 QA의 AI 네이티브 대응물로,
최근 작업에서 실제 과제 20~50개를 모아 `CLAUDE.md`, 스킬,
훅이 바뀔 때마다 CI에서 돌리고, 모든 프로덕션 장애를 eval로 남기라고 권한다.

### 배포

Claude는 PR 리뷰를 하기도 하고 받기도 한다.
기술 리더가 저장소 루트의 `REVIEW.md`에 버그, 보안,
스펙과 계획 준수의 세 패스와 Important와 Nit의 기준을 적고, 리뷰 결과만으로는
승인도 차단도 하지 않으며 브랜치 보호가 여전히 코드 소유자의 승인을 요구한다.
코드를 쓴 에이전트가 승인할 길이 없으므로 직무 분리가 유지된다는 논리다.
훅은 허용, 질문, 차단을 고를 수 있어 릴리스 승인 관문이 되고,
꺼서는 안 되는 훅은 엔지니어가 끌 수 없는 관리형 설정(managed settings)에 둔다.
규제 산업용 예시로 비밀 파일 읽기와 네트워크 도구를 막고,
OS 수준 샌드박스와 도메인 허용 목록을 켜고,
관리형 훅과 MCP 서버와 승인된 플러그인 마켓플레이스만 허용하는 설정을 보이며,
그대로 복사할 권장안이 아니라 출발점이라고 덧붙인다.
CI/CD에서는 읽기 전용 판단 작업부터 `claude -p`로 시작하고,
에이전트가 쓰는 모든 것은 PR로 들어오며,
배포와 롤백은 환경별로 범위를 정한 MCP 도구로 노출한다.
에이전트는 프로덕션 관문 직전까지 모든 일을 하고 그 너머는 하지 않는다는 것이
이 단계의 원칙이다.

### 유지보수와 루프 닫기

마지막 단계에서 루프가 닫힌다.
결정적인 스크립트가 지표의 이동 기준선을 감시하다가 1σ에서는 기록만 하고,
2σ에서는 Claude를 읽기 전용으로 불러 진단하게 하며,
3σ에서는 PR을 열거나 사전 승인된 런북을 실행하게 한다.
탐지에는 모델을 쓰지 않고,
Claude는 진단을 1단계 형식의 `intent.md`로 써서 루프에 다시 넣는다.
정기 보안 스캔은 Claude Security가 Claude Mythos 5로 맡고, 보안 스캔은 코드와
모델이라는 두 축에서 모두 낡는다는 이유로 일정에 따라 반복하라고 한다.
Claude Tag는 Slack 채널에서 장애의 첫 대응자가 되고,
채널 자체가 감사 기록이 된다고 소개한다.
글은 루프는 계속 돌고 사람의 판단은 그 위에 남는다는 문장으로 끝난다.

## 분석

### 플레이북의 중심은 단계가 아니라 커밋된 산출물이다

여섯 단계의 이름은 전통적 SDLC와 똑같다.
바뀐 것은 단계 사이를 잇는 매체다.
전통적 SDLC에서는 회의, 티켓, 서명이 단계를 이었고,
그 매체는 사람만 읽을 수 있었다.
이 글은 그 자리에 `intent.md`, `spec.md`, `plan.md`처럼
 사람과 에이전트가 함께 읽는 마크다운 파일을 놓는다.
그래서 인수인계가 사람 사이의 해석에서 파일 읽기로 바뀌고,
다음 단계를 사람이 시작하는 대신 커밋이 트리거가 될 수 있다.

이 설계가 노리는 것은 속도만이 아니다.
글은 커밋의 사슬이 곧 감사 기록이라고 반복한다.
규제 산업이 사람의 서명과 회의록으로 증명하던 통제 목표를 git 기록의 작성자,
타임스탬프, 머지 결정으로 대체하려는 것이다.
측정 지표도 대부분 두 커밋 사이의 시간이나 특정 파일의 커밋 횟수처럼
git 기록에서 바로 읽을 수 있게 짜여 있다.
이 일관성이 글의 가장 단단한 부분이다.

### 통제를 권고, 결정, 승인의 세 층으로 나눈다

글에서 가장 정교한 부분은 통제의 강도를 구분하는 방식이다.
스킬은 권고형 통제여서 위반을 드물게 할 뿐이고,
훅은 결정적이어서 위반을 거의 불가능하게 하며,
질문하는 훅과 브랜치 보호는 특정한 사람의 승인을 요구한다.
같은 정책도 얼마나 반드시 지켜야 하는지에 따라 어느 층에 둘지가 달라진다.

이 구분은 사람이 개입하는 위치를 정하는 원칙이기도 하다.
구현 단계에서 승인을 묻는 훅을 쓰지 말라는 조언은 병렬 세션 여럿이 한 사람의
응답을 기다리게 되는 구조적 비용을 정확히 짚는다.
사람의 판단은 흐름 중간에 흩어 두지 않고 관문에 모은다.
그 관문은 `intent.md` 승인, `spec.md` 승인, `plan.md` 승인, PR 승인,
프로덕션 릴리스 승인으로 정해져 있다.
에이전트는 프로덕션 관문 직전까지 다 하고 그 너머는 하지 않는다는
원칙이 이 배치를 요약한다.

### 탐지는 결정적으로, 해석은 모델로 맡긴다

유지보수 단계의 시그마 등급 설계는 이 글이 모델을 어디에 쓰고
어디에 쓰지 않는지를 가장 분명히 보여 준다.
이상 탐지는 이동 평균과 표준편차,
Western Electric 규칙으로 하고 모델을 넣지 않는다.
모델은 기준이 깨진 뒤에만 불리고, 깨진 정도에 따라 기록, 읽기 전용 진단,
게이트를 거친 행동으로 권한이 커진다.
Claude Security를 소개하면서도 결정적 검사는 CI에 남기고,
모델 기반 스캔은 그 검사가 찾지 못하는
맥락 의존적 취약점을 맡는다고 선을 긋는다.

이 구조는 모델을 판단이 필요한 좁은 구간에만 넣고,
그 앞뒤를 재현 가능한 장치로 감싸는 패턴이다.
CI/CD 플레이가 결정적 스크립트로 돌던 파이프라인에서 판단이 필요한 단계,
예를 들어 불안정한 테스트 분류나 빌드 실패 원인 추정만 `claude -p`로
바꾸라는 것도 같은 생각이다.

### 이 글은 엔터프라이즈 도입 안내서이기도 하다

글은 방법론처럼 읽히지만 거의 모든 플레이가 특정 제품에 대응한다.
Cowork, Claude Design, 플랜 모드, 자동 모드, Code Review, `claude-code-action`,
관리형 설정, Claude Security, Claude Tag가 차례로 등장하고,
끝의 참고 자료는 플랫폼 팀이 이 통제를 켜는 순서대로
Claude Code 문서를 나열한다.
Claude Security의 인프라 조건에는 Claude Enterprise, Extra Usage와 지출 한도,
프리미엄 좌석이 적혀 있다.

이것이 글의 가치를 깎지는 않는다.
선행 조건 그래프와 측정 지표는 다른 도구로 옮겨도 성립하는 부분이 많다.
다만 독자는 무엇이 원리이고 무엇이 제품 배치인지 스스로 갈라 읽어야 한다.
`intent.md`에서 `plan.md`로 이어지는 산출물 사슬과 권고, 결정,
승인의 통제 층은 원리에 속하고, 어떤 스캔을 어떤 모델로 돌릴지는 배치에 속한다.

## 비평

### 병목이 사람의 리뷰로 옮겨 간다는 사실을 인정하고도 처리량을 계산하지 않는다

글은 병목이 구현의 앞뒤로 옮겨 간다고 스스로 진단한다.
그런데 제시하는 해법의 상당 부분은 사람의 검토 지점을 늘린다.
제품 책임자는 모든 `intent.md`와 `spec.md`를 검토하고,
엔지니어는 `plan.md`를 승인하고, 코드 소유자는 모든 PR을 승인하며,
서비스 책임자는 자동으로 생긴 `intent.md` 대기열을 분류한다.
각 관문의 검토는 처음부터 쓰는 것보다 가볍다는 것이 글의 전제지만,
얼마나 가벼운지는 어디서도 수치로 보이지 않는다.

병렬 세션 플레이에서 글은 실용적 상한이 한 사람이 제대로 리뷰할 수 있는
흐름의 수라고 정직하게 적는다.
같은 제약이 기획과 설계, 유지보수 단계에도 그대로 적용되어야 하는데,
그쪽에서는 말하지 않는다.
특히 6단계가 사람 없이 `intent.md`를 만들어 내기 시작하면
제품 책임자의 검토 대기열이 새로운 병목이 된다.
보안 팀이 사람의 산출량에 맞춰 꾸려져 있다는 첫 장의 문제 제기가 제품 책임자에게
고스란히 옮겨 오는 셈이고, 글은 이 대칭을 다루지 않는다.

### 측정 지표가 개선을 증명하기보다 활동을 기록한다

플레이마다 선행 지표와 후행 지표가 붙어 있지만,
상당수는 무엇이 빨라졌는지를 재고 무엇이 좋아졌는지는 재지 않는다.
첫 대화부터 `intent.md` 커밋까지의 시간이나
`intent.md`와 `spec.md` 커밋 사이의 시간은
 에이전트가 문서를 빨리 쓰면 줄어들 수밖에 없는 수치다.
몇 주짜리 도출 주기가 몇 시간으로 줄 것이라는 기대는 이 지표로는
거의 자동으로 달성된다.

더 어려운 질문은 빨리 쓰인 `intent.md`가 옛 PRD만큼 쓸모 있는가이다.
글이 이 질문에 가장 가까이 가는 지표는 제품 책임자가
받아들인 비율과 `spec.md` 이후의 `intent.md` 변경 횟수인데,
받아들인 비율은 검토자가 바쁠수록 올라가는 지표이기도 하다.
검토를 덜 꼼꼼히 할수록 좋아 보이는 지표는 관문이 무너지는 것을
개선으로 기록할 수 있다.
DORA 지표나 변경 실패율 같은 결과 지표가 일부 플레이에만
붙어 있다는 점도 아쉽다.

### 제품 성숙도에 기대는 플레이는 글이 인정하는 것보다 위험하다

HN에서 elpakal은 글이 Claude Design으로 진지한 설계 작업도 처리할 수 있다고 암시하지만,
베타로 표시된 점을 감안해도 자기 팀 경험으로는
이런 흐름에 쓰기에는 아직 멀었다고 적었다.[^elpakal]
글은 Claude Design, Code Review, Claude Tag, Claude Security에 각각 베타,
연구 미리보기, 공개 베타라는 표시를 붙여 두었다.
그런데 표시는 붙이면서 그 성숙도가 플레이의 위험에 어떤 영향을
주는지는 따지지 않는다.

설계 플레이의 목표는 제품 책임자가 스펙을 쓰지 않고 검토만 하는 것이다.
도구가 기대만큼 작동하지 않으면 그 검토는 사실상 다시 쓰기가 되고,
시간 지표는 개선된 것처럼 보이는데 실제 작업은 옮겨 갔을 뿐인 상황이 생긴다.
규제 산업을 주된 독자로 상정한 글이라면,
베타 제품에 기대는 플레이와
일반 공개된 기능만으로 되는 플레이를 구분해 채택 순서에 반영했어야 한다.

### 실천 가능한 안내서라는 주장과 글의 형식이 어긋난다

글 머리에는 읽는 시간 5분이라고 적혀 있지만,
본문은 여섯 단계의 플레이마다 선행 조건, 인프라, 실행 단계, 예시 파일, 거버넌스,
지표를 담고 있어 실제 분량은 그보다 훨씬 길다.
HN에서 siva7은 블로그 글이 언제부터 한 시간짜리 읽을거리가
되었느냐고 탄식했다.[^siva7]
t_tsonev는 글의 본문이 iPhone 화면에 들어가지도 않는데 코드는
이미 해결된 문제라고 한다며 비꼬았고,[^t_tsonev]
harshalizee는 사소한 트집인 줄 알았는데
Safari에서 실제로 오른쪽이 잘려 볼 방법이 없다고 확인했다.[^harshalizee]
dwrodri도 같은 지점을 두고 Anthropic의 엔지니어링 팀이 iPhone 화면에서
사이트를 테스트하지 않는 것 같다고 꼬집었다.[^dwrodri]

반응 자체는 가벼운 농담이지만, 글의 주장과 맞닿는 지점이 있다.
이 플레이북은 모든 세션이 스스로 작업을 검증할 피드백 루프를 가져야 하고,
UI 작업이라면 스크린숏으로 결과를 확인하라고 권한다.
그 권고를 담은 페이지가 흔한 모바일 화면에서 잘렸다는 것은 피드백 루프가
검증하는 범위가 목표로 정한 것에 한정된다는 점을 보여 준다.
목업과 일치하는지만 확인하는 루프는 목업에 없는 화면 크기를 보지 못하고,
이 한계는 글의 테스트 단계 어디에서도 다루지 않는다.

## 인사이트

### 산출물 사슬이 자동화될수록 사람의 승인은 서명으로 축소되기 쉽다

이 플레이북은 사람의 판단을 관문에 모으면 판단의 질이 오른다고 가정한다.
그런데 관문이 다섯 개가 되고 각 관문에 에이전트가 쓴 문서가 쉼 없이 들어오면,
관문의 승인은 판단보다 처리에 가까워진다.
`intent.md`가 승인되면 `spec.md`가 PR로 올라오고,
그것이 승인되면 플랜 모드가 시작되는 연쇄에서
한 관문을 대충 통과시키는 비용은 당장 보이지 않는다.
다음 관문이 잡아 줄 것이라는 기대가 각 관문에 생기기 때문이다.

이것은 다중 승인 체계에서 오래 관찰된 책임 분산과 같은 구조라고 해석할 수 있다.
결재란이 많은 문서일수록 각 결재자는 앞사람이 봤으리라 믿고 덜 본다.
글의 감사 기록은 누가 승인했는지는 남기지만 얼마나 들여다봤는지는 남기지 않는다.
그래서 규제 기관이 보기에는 통제가 완비된 것 같은데,
실제 판단은 어느 관문에서도 일어나지 않는 상태가 가능하다.

대응은 관문의 수를 늘리는 것이 아니라 관문마다 검토의 깊이를
다르게 정하는 것이다.
글이 이미 시도한 위험 등급에 따른 승인자 분리를 모든 관문으로 넓히고,
일정 비율의 승인 건을 무작위로 골라 재검토하는 표본 감사를 두면
도장만 찍는 승인을 지표로 드러낼 수 있다.
글의 지표 체계에는 이런 검토 품질 지표가 빠져 있다.

### `CLAUDE.md`와 스킬은 조직 지식의 위키가 걸었던 길을 다시 걷는다

글은 사람의 머리와 위키에 있던 지식이 에이전트가 매 세션
읽는 파일이 된다고 쓴다.
위키가 실패한 이유는 아무도 읽지 않아서 낡았기 때문인데,
에이전트는 매번 읽으니 이번에는 다르다는 것이 이 글의 숨은 논리라고 볼 수 있다.
실제로 에이전트가 읽는다는 점은 큰 차이다.
낡은 규칙은 이제 무시되는 대신 잘못된 행동으로 곧바로 나타난다.

그러나 이것은 양날이다.
위키의 낡은 문서는 해를 덜 끼쳤지만,
낡은 `CLAUDE.md`나 스킬은 모든 세션의 행동을 같은 방향으로 틀리게 만든다.
같은 실수가 두 번 나오면 교정을 `CLAUDE.md`에 넣으라는 규칙은
파일을 계속 자라게 하고,
한 페이지 이하로 유지하라는 다른 규칙과 시간이 갈수록 부딪친다.
글은 스킬이 정책에서 멀어지면 PR 리뷰 지적이 0으로 내려가지 않는다는 신호로
알아챌 수 있다고 하지만, 그 신호는 사후적이다.

그래서 이 파일들은 코드처럼 리뷰할 뿐 아니라 코드처럼 지워야 한다.
글이 지속적 평가를 `CLAUDE.md`, 스킬, 훅의 변경에도 돌리라고 한 것은
올바른 방향이며,
여기에 규칙 하나를 지웠을 때 평가 점수가 그대로인지 확인하는 삭제 시험을
 더하면 규칙이 쌓이기만 하는 문제를 막을 수 있다.
이것은 원문에 없는 해석이다.

### 루프가 스스로 일을 만들기 시작하면 무엇을 하지 않을지가 새로운 결정이 된다

6단계의 핵심은 사람이 일을 시작하지 않아도 된다는 것이다.
지표가 기준을 벗어나면, 스캔이 취약점을 찾으면,
Slack에 요청이 오면 `intent.md`가 생긴다.
전통적 SDLC에서 백로그가 쌓이는 것은 실패의 신호였지만,
이 루프에서는 일을 만드는 비용이 0에 가까워지므로
백로그가 쌓이는 것이 정상 상태가 된다.

이때 희소한 자원은 구현 능력이 아니라 무엇을 하지 않을지 정하는 판단이다.
글은 분류 담당자가 지금 고치기, 일정 잡기, 기각 중 하나를 고르고,
기각이 기준선을 조정해 소음을 줄인다고만 적는다.
그러나 에이전트가 고칠 수 있는 작은 문제가 끝없이 생기는 환경에서는,
모든 문제를 고치는 것이 제품을 나쁘게 만들 수도 있다.
작은 수정 PR이 쌓이면 리뷰 대기열을 점유하고 코드베이스의 변경 빈도를
높여 다른 위험을 키운다.

글이 PR 주기 시간을 감시 지표의 예로 든 것은 의미심장하다.
루프가 자기 자신이 만든 부하를 감시하는 지표를 갖게 되면,
사람의 역할은 개별 수정을 승인하는 것에서
루프가 만들어도 되는 일의 총량을 정하는 것으로 바뀐다.
이것은 글이 말하는 사람의 판단이 루프 위에 남는다는 문장의 구체적인
뜻이 될 수 있다고 본다.

### 결정적 장치와 모델의 경계는 시간이 지나며 움직이므로 경계 자체를 관리해야 한다

글은 탐지는 결정적으로, 해석은 모델로 한다는 선을 분명히 긋는다.
동시에 보안 스캔은 모델 세대마다 이전 세대가 놓친 취약점을
찾으므로 낡는다고 말한다.
이 두 문장을 겹치면, 모델이 맡는 구간과 결정적 장치가 맡는 구간의 경계가
모델 세대와 함께 움직인다는 결론이 나온다.

예를 들어 지금은 모델에게 맡긴 불안정한 테스트 분류도 패턴이 쌓이면
결정적 규칙으로 내려올 수 있고,
반대로 지금 결정적 규칙으로 하는 일부 검사는
더 나은 모델이 더 정확히 할 수 있다.
글의 지속적 평가 플레이가 모델이 바뀔 때 에이전트가 같은 기준으로 일하는지
확인하라고 하는 것은 이 이동을 감지하는 장치다.
하지만 평가는 모델이 맡은 구간 안에서만 돌고,
경계를 옮겨야 하는지는 묻지 않는다.

따라서 AI 네이티브 SDLC를 운영하는 조직은
어떤 판단을 모델에 맡기고 어떤 판단을 스크립트로 고정했는지의 목록을
하나의 산출물로 관리해야 한다고 본다.
이 목록은 글의 관리형 설정처럼 버전 관리되고,
모델이 바뀔 때마다 평가와 함께 다시 검토되어야 한다.
권고, 결정, 승인으로 나눈 통제의 층이 고정된 구조가 아니라
주기적으로 다시 그려야 하는 지도라는 뜻이다.
