# omp — IDE를 통째로 끌어들인 터미널 코딩 에이전트

<https://omp.sh/>

<https://github.com/can1357/oh-my-pi>

HN 토론: <https://news.ycombinator.com/item?id=48994611> (39점, 15개 댓글)

GN 토론: <https://news.hada.io/topic?id=31744>

## 소개

omp("Oh My Pi")는 Mario Zechner의 Pi를 포크해서 코딩 전용 표면으로 다시 쓴 터미널 코딩 에이전트다.
MIT 라이선스이며 macOS, Linux, Windows에서 동작한다.
Windows는 WSL 없이 네이티브로 돌아간다.
bun 1.3.14 이상을 요구한다.

```bash
curl -fsSL https://omp.sh/install | sh
```

내세우는 숫자는 프로바이더 40개 이상, 내장 도구 32개, LSP 연산 14개, DAP 연산 28개,
그리고 10만 줄 이상의 Rust 코어다.
"기본 상태로 완결된, 타협 없이 네이티브인" 에이전트를 표방한다.

## Pi에 더한 것들

프로젝트가 스스로 정리한 핵심 추가 기능은 열여섯 가지다.
그중 성격이 뚜렷한 것들을 추린다.

**LSP 연동.** 이름 변경을 요청하면 실제로 이름 변경이 일어난다.
호출이 `workspace/willRenameFiles`를 거치므로
재수출, 배럴 파일, 별칭 임포트가 파일이 이동하기 전에 갱신된다.
53개 언어 서버를 지원하고 저장 시점에 `textDocument/formatting`으로 포맷팅한다.

**DAP 연동.** 실제 디버거를 조작한다.
C 바이너리가 세그폴트를 내면 에이전트가 lldb를 붙여 잘못된 포인터까지 스텝을 밟고 프레임을 읽는다.
Go 서비스가 멈추면 dlv를 붙여 고루틴을 훑고, Python 프로세스가 걸리면 debugpy로 일시 정지 후 검사한다.
lldb-dap, dlv, debugpy를 포함해 14개 어댑터를 번들로 제공한다.

**Hashline 편집.** 모델이 바꾸고 싶은 줄을 다시 타이핑하는 대신 앵커를 가리킨다.
xxHash32로 만든 4자리 16진 태그를 쓰며, 오래된 파일을 편집하면 앵커가 어긋나 패치가 거부된다.
16개 모델, 180개 과제, 3회 반복 벤치마크에서
Grok Code Fast 1의 pass@1이 6.7%에서 68.3%로 올랐고,
Grok 4 Fast는 출력 토큰을 61% 덜 썼다.

**TTSR(Time-traveling stream rules).** 규칙이 평소에는 잠들어 있다가
정규식이 걸리면 스트림을 토큰 중간에 중단하고 규칙을 시스템 리마인더로 주입한 뒤 같은 지점에서 재시도한다.
매 턴 컨텍스트 비용을 내지 않고 궤도를 수정하는 방식이며, 주입은 압축을 견딘다.
`/omfg <불만>`을 입력하면 잘못된 대화에서 규칙 초안을 만들고
그 규칙이 실제로 발동했을지를 같은 트랜스크립트로 검증한 뒤 `.omp/rules/`에 등록한다.

**Advisor.** 리뷰어 모델을 `advisor` 역할에 붙이면
메인 에이전트의 모든 턴을 읽고 인라인으로 메모를 넣는다.
심각도는 aside, concern, blocker 세 단계다.
자체 컨텍스트와 자체 모델로 돌아가므로 실행자가 서둘러 지나친 것을 잡아낸다.

**Snapcompact.** 컨텍스트 압축을 모델 호출 없이 처리한다.
창이 차면 히스토리를 픽셀 폰트 PNG로 결정론적으로 렌더링해서 이미지로 돌려준다.
1568×1568 프레임 하나가 6×10 픽셀 폰트로 약 4만 자,
텍스트 기준 약 1만 토큰을 담고 Anthropic 픽셀 공식으로 3,279 이미지 토큰에 과금된다.
SQuAD v1.1 F1 기준으로 원문이 0.90일 때 이미지 방식이 0.88을 냈고,
같은 조건에서 산문 요약 방식은 Gemini가 240문항 전부, Opus가 240문항 중 209문항을 UNREADABLE로 답했다.

**모든 표면이 URL.** `pr://`, `issue://`, `agent://`, `skill://`, `rule://` 등 12개 내부 스킴이
파일시스템 형태의 모든 도구 안에서 투명하게 해석된다.
`read pr://1428`이 `read src/foo.ts`와 같은 형태를 돌려준다.
`gh view`도, `skill show`도, `agent get`도 없다.
URL 공간이 변형을 흡수하므로 도구 개수가 늘지 않는다.

**Collab.** `/collab`이 세션을 릴레이에 올리고 링크와 QR을 돌려준다.
동료는 `omp join`으로 다른 터미널에서 들어오거나 브라우저로 연다.
AES-256-GCM으로 클라이언트에서 봉인하고 키는 URL 프래그먼트에만 담기므로 릴레이는 내용을 보지 못한다.
읽기 전용 링크도 발급할 수 있다.

**네이티브 Rust 엔진.** 다른 에이전트가 `rg`, `grep`, `find`, `bash`를 셸로 넘기는 것과 달리
ripgrep, glob, find를 프로세스 안에 링크한다.
bash 자리에는 brush를 쓰며 세션이 호출 사이에 유지된다.
셸 3만 1천 줄, coreutils 2만 8천 줄, 출력 최소화기 2만 3천 줄 등으로 구성된다.

**기존 설정 상속.** 첫 실행 시 디스크에 이미 있는 여덟 가지 형식을 원래 모양 그대로 읽는다.
Cursor MDC, Cline `.clinerules`, Codex `AGENTS.md`, Copilot `applyTo` 등이다.
마이그레이션 스크립트도, YAML을 TOML로 옮기는 작업도 없다.

## 진입점

같은 엔진에 네 가지 껍데기가 붙어 있다.
`omp`는 TUI를 띄우고, `omp -p`는 프롬프트 하나에 답하고 종료한다.
Node SDK(`@oh-my-pi/pi-coding-agent`)는 세션을 호스트 프로세스에 내장한다.
`omp --mode rpc`는 NDJSON으로 stdio를 통해 다른 프로그램에 제어권을 넘기고,
`omp acp`는 Agent Client Protocol로 Zed 같은 에디터에 붙는다.
ACP 모드에서는 `bash`가 `terminal/create`로, `read`가 `fs/read_text_file`로 라우팅되고
쓰기는 `session/request_permission`으로 게이트된다.

## 분석

### 이 프로젝트의 논지는 "셸 아웃을 없애면 이긴다"이다

omp의 설계 결정 대부분이 하나의 명제로 수렴한다.
에이전트가 외부 프로세스에 위임하던 것을 안으로 끌어들이면 더 낫다는 것이다.
grep을 셸로 부르는 대신 ripgrep을 링크하고,
`gh` CLI를 부르는 대신 `pr://`을 read에 태우고,
디버거 대신 print 문을 뿌리는 대신 DAP를 직접 조작하고,
요약 모델을 부르는 대신 PNG를 렌더링한다.

이 명제의 근거는 두 가지다.
성능 측면에서는 fork-exec 왕복 비용이 사라진다.
정확성 측면에서는 도구가 자기 상태를 알게 된다.
이름 변경 예시가 이 두 번째를 잘 보여준다.
`sed`로 문자열을 바꾸면 배럴 파일이 깨지지만 LSP를 통하면 깨지지 않는다.
차이는 속도가 아니라 도구가 코드 구조를 이해하느냐다.

### 벤치마크 수치가 무엇을 측정한 것인지 봐야 한다

Grok Code Fast 1의 6.7% → 68.3%는 10배가 넘는 개선처럼 보이지만
이것은 모델 성능이 아니라 편집 형식의 성능이다.
프로젝트도 이 점을 명시한다.
"편집 형식이 모델을 산 채로 잡아먹는 것을 멈추는 순간"의 상승이라는 표현이다.

즉 6.7%라는 기저값은 해당 모델이 코딩을 못한다는 뜻이 아니라
`str_replace` 형식에서 문자열 매칭에 실패해 재시도 루프에 빠졌다는 뜻이다.
같은 논리로 Grok 4 Fast의 출력 토큰 61% 감소도 "잘못된 diff에 대한 재시도 루프가 사라져서"라고 설명된다.
이 수치들이 보여주는 것은 omp가 모델을 똑똑하게 만든다는 것이 아니라,
약한 모델일수록 편집 형식의 개선으로 얻는 이득이 크다는 사실이다.
Gemini 3 Flash의 +5pp가 상대적으로 작은 것도 같은 맥락에서 읽힌다.

### Snapcompact가 컨텍스트 압축의 전제를 바꾼다

컨텍스트 압축은 지금까지 "모델에게 요약을 시킨다"는 전제 위에 있었다.
그 결과 압축은 느리고, 비싸고, 무엇이 살아남을지 모델이 결정한다.
omp는 압축을 렌더링 문제로 재정의한다.
텍스트를 픽셀 폰트로 그려서 이미지로 되돌려주면
모델은 그것을 거의 원문 그대로 읽어 낸다.

프로젝트가 인용한 대조 실험이 인상적이다.
산문 요약으로 압축한 컨텍스트에 대해 Gemini는 240문항 전부를 UNREADABLE로 답했다.
요약이 답에 필요한 사실을 이미 버렸다는 뜻이다.
반면 이미지 방식은 F1 0.88로 원문 0.90에 근접했다.
"PNG는 당신의 컨텍스트를 찍은 사진이 아니라, 당신의 컨텍스트로 수렴한다"는 프로젝트의 표현이
과장이 아닐 수 있음을 시사한다.

다만 이 방식은 비전 모델을 요구한다.
텍스트 전용 모델은 `context-full`로 되돌아간다고 명시돼 있다.
40개가 넘는 프로바이더를 지원한다는 강점이
정작 핵심 기능 하나에서는 절반쯤 무력해지는 구조다.

### GeekNews 반응이 UI로 좁혀진 이유

GeekNews에 이 프로젝트를 올린 click은 소개 이유를 한 줄로 적었다.
에이전트가 어떤 작업을 진행 중인지 확인하는 UI가 꽤 좋다는 것이었다.[^click]

기능 목록이 열여섯 개인 프로젝트에서 소개자가 고른 지점이 TUI라는 사실은 시사적이다.
LSP, DAP, snapcompact, hashline은 모두 벤치마크로 증명해야 하는 주장이지만
"진행 상황이 보인다"는 즉시 확인 가능한 경험이다.
코딩 에이전트를 실제로 쓸 때 가장 자주 부딪히는 불편이
성능이 아니라 "지금 뭘 하고 있는지 모르겠다"는 데 있다는 방증이기도 하다.

## 비평

### 열여섯 개 기능을 나열하는 것 자체가 위험 신호다

omp의 홍보 페이지는 "Pi에 없는 것을 모두 더했다"는 구조로 짜여 있다.
eval, LSP, DAP, TTSR, subagents, advisor, collab, web, native-rs, review, hashline,
github-fs, memory, ACP, discovery, commit.
각각이 독립적인 하위 시스템이다.

이 폭은 강점으로 제시되지만 유지보수 관점에서는 부채다.
DAP 어댑터 14개, LSP 서버 53개, 프로바이더 40개, 검색 백엔드 14개.
이 조합의 곱만큼 회귀 가능성이 있고, 각 외부 시스템은 독립적으로 버전이 올라간다.
"기본 상태로 완결"이라는 표방이 유지되려면
이 표면 전체를 지속적으로 따라가야 하는데,
그것이 가능한 규모의 프로젝트인지는 페이지에서 드러나지 않는다.

실제로 GeekNews 본문 요약에도 기존 Pi 익스텐션과의 호환성 문제와
CommonJS 의존성 관련 버그가 언급돼 있다.
포크가 상류와 벌어지면서 생기는 전형적인 비용이다.

다만 첫 실행 경험에 대한 평가는 좋은 편이다.
explodes는 Z.ai와 함께 OpenCode 대신 써 봤는데 시작하기가 아주 간단했다고 전했다.[^explodes]
전반적으로 만족스러웠고, "TUI 에이전트의 파워 유저 에디션" 같은 느낌인데도
쓸 모델을 지정하는 것 외에 별도 조정 없이 돌아갔다는 것이다.
기능 표면이 넓은 도구가 기본 설정으로 바로 동작한다는 것은 쉽지 않은 성취다.

### 구독 계정 로그인이 계정 정지 위험을 안고 있다

hahn-kev는 실사용에서 걸린 문제를 보고했다.[^hahn-kev]
여러 계정으로 OAuth 로그인을 시도했는데 전부
해당 업체의 공식 도구에서 오는 로그인만 허용한다는 응답을 받았고,
그래서 자기 구독으로 이것을 쓰면 계정이 정지될 것 같다는 우려다.

이 지적은 프로바이더 40개 이상이라는 홍보 문구의 실질을 건드린다.
"지원한다"는 것이 기술적으로 연결된다는 뜻인지,
약관상 허용된다는 뜻인지가 사용자에게는 전혀 다른 문제다.
`/login`이 Cursor, GitHub Copilot, Kimi Code, GLM Coding Plan 같은
구독 기반 서비스를 나열하지만,
그 구독의 이용 약관이 서드파티 클라이언트를 허용하는지는 별개다.
API 키로 직접 결제하는 경우와 달리 구독 라우팅은 이 위험을 사용자가 떠안는 구조다.

### 벤치마크가 자체 측정이고 방법론이 요약 수준으로만 공개된다

"16 모델 · 180 과제 · 3회 반복 · React 픽스처"라는 서술이 방법론의 전부다.
과제가 무엇인지, React 픽스처가 어떤 성격인지, 비교 대상 도구의 설정이 어땠는지가 없다.
`/scripts/session-stats`와 "같은 방법 · 다른 도구"라는 링크가 있지만
페이지 자체에서는 검증할 수 없다.

편집 형식의 개선이 실제 효과를 낸다는 것은 그럴듯한 주장이고
6.7% → 68.3% 같은 극적인 수치도 재시도 루프 붕괴로 설명 가능하다.
문제는 이 수치가 도구 제작자가 자기 도구를 유리하게 만드는 조건에서 측정됐을 가능성을
독자가 배제할 방법이 없다는 점이다.
React 픽스처 하나에 특화된 결과일 수도 있다.

### 브라우저 도구가 Slack DM을 읽는다는 홍보가 불편하다

브라우저 절의 문구는 이렇다.
스텔스가 기본으로 켜져 있어서 페이지가 헤드리스 봇 대신 정상 사용자로 인식하며,
같은 API로 Electron 앱을 조작할 수 있어서 Slack을 가리키면
에이전트가 웹을 읽듯 당신의 DM을 읽는다는 것이다.

기능 자체는 정당한 쓰임이 있다.
문제는 이것이 "역량"으로 자랑되는 방식이다.
스텔스 기본값은 봇 탐지 우회를 기본 동작으로 삼겠다는 선언이고,
이는 대상 사이트의 이용 약관과 충돌할 소지가 크다.
Slack DM 읽기는 그 대화에 참여한 상대방의 동의 범위를 벗어난다.
에이전트에게 어디까지 권한을 줄 것인가를 사용자가 판단하도록 돕는 대신,
가장 넓은 권한을 기본값이자 세일즈 포인트로 제시하는 태도다.

### "benchmaxxed"라는 자기 규정이 솔직하지만 그래서 문제다

프로젝트는 2번 절의 제목을 "Every tool, benchmaxxed"로 달았다.
벤치마크 점수를 목표로 도구를 조정했다는 뜻을 스스로 밝힌 것이다.
"각 모델마다 집요하게 조정된 프롬프트"라는 설명도 같은 맥락이다.

이 솔직함은 평가할 만하지만, 동시에 일반화 가능성에 대한 경고이기도 하다.
180개 과제에 맞춰 조정된 프롬프트가 사용자의 실제 코드베이스에서도 같은 이득을 낸다는 보장은 없다.
벤치마크 최적화와 실사용 성능이 갈라지는 것은 이 분야에서 반복돼 온 패턴이다.
프로젝트가 "실사용으로 지속적으로 튜닝된다"고도 말하지만,
공개된 수치는 전부 벤치마크 쪽이다.

elikoga는 이 지점을 다른 각도에서 짚었다.
쓰는 것은 마음에 들지만 제작자가 CI에서 벤치맥싱을 제대로 하고 있지 않다는 느낌이 든다는 것이다.[^elikoga]
표현이 역설적인데, 벤치마크 최적화를 비판하는 것이 아니라
그것을 지속적 통합에 넣어 자동으로 돌리고 있지 않은 것 같다는 지적이다.

이것이 실질적인 문제다.
"benchmaxxed"를 표방하려면 그 수치가 매 커밋마다 재측정돼야 한다.
한 번 측정해서 랜딩 페이지에 올려 둔 숫자는 그 시점의 스냅숏일 뿐이고,
기능이 열여섯 개씩 추가되는 속도라면 회귀가 조용히 들어올 여지가 크다.
`/scripts/session-stats` 같은 도구를 갖췄다고 밝히면서도
그 결과가 지속적으로 공개되지 않는다는 점이 이 인상을 뒷받침한다.

## 인사이트

### 도구 개수를 늘리지 않고 표현력을 늘리는 방법

omp가 `gh_issue_view`, `gh_pr_view`, `gh_search` 같은 도구를 만드는 대신
`pr://`, `issue://` 스킴을 기존 `read`에 태운 결정은 일반화할 가치가 있다.
도구를 추가하면 모델이 학습해야 할 인터페이스가 늘고, 도구 정의가 컨텍스트를 먹고,
제작자가 유지해야 할 표면이 넓어진다.

주소 공간에 변형을 실으면 이 셋이 모두 억제된다.
모델은 이미 `read`를 안다.
새 스킴은 인자 스키마가 아니라 문자열 규칙일 뿐이다.
`pr://1428/diff/2:50-100`처럼 셀렉터가 합성되는 것도 파일 경로 문법을 그대로 재사용한 결과다.

이 원리는 omp 밖에서도 쓸 수 있다.
MCP 서버나 자체 에이전트 도구를 설계할 때
"동작마다 도구 하나"와 "도구 하나에 주소 공간"을 비교해 볼 만하다.
후자가 도구 목록의 인지 부하를 낮추고, 조합 가능성을 열어 준다.

### 규칙을 상시 로드하지 않고 위반 시점에 주입한다

TTSR의 발상은 프롬프트 엔지니어링의 비용 구조를 바꾼다.
지금까지 규칙은 시스템 프롬프트나 `CLAUDE.md`에 상주하며 매 턴 토큰을 소비했다.
규칙이 늘수록 비용이 선형으로 늘고, 정작 대부분의 턴에서는 그 규칙이 관련되지 않는다.

TTSR은 규칙을 정규식 트리거로 바꾸고 매칭될 때만 주입한다.
매칭 전 비용이 0이라는 서술이 핵심이다.
스트림을 토큰 중간에 끊고 같은 지점에서 재시도한다는 점도 중요하다.
턴이 끝난 뒤 고치는 것이 아니라 잘못이 발생하는 순간에 개입한다.

`/omfg`가 이 구조를 사용자 인터페이스로 완성한다.
불만을 입력하면 그 대화에서 규칙을 만들고,
같은 트랜스크립트로 "이 규칙이 그때 발동했을까"를 검증한다.
규칙을 쓰는 사람이 규칙의 효과를 사후에 확인할 수 있다는 뜻이다.
프롬프트 규칙이 실제로 작동하는지 알 수 없다는 오래된 문제에 대한 구체적인 답이다.

### 압축은 요약이 아니라 인코딩 문제일 수 있다

Snapcompact가 던지는 질문은 omp를 쓰지 않더라도 유효하다.
컨텍스트가 넘칠 때 우리가 하려는 일은 무엇인가.
정보를 버리는 것인가, 같은 정보를 더 싼 표현으로 옮기는 것인가.

산문 요약은 전자다.
모델이 중요하다고 판단한 것만 남기고 나머지를 버린다.
그래서 나중에 필요해진 사실이 이미 사라져 있는 일이 생긴다.
Gemini가 240문항 전부를 UNREADABLE로 답한 결과가 이 실패를 보여준다.

픽셀 렌더링은 후자다.
정보를 하나도 버리지 않고 토큰당 비용이 더 싼 매체로 옮긴다.
이미지 토큰이 텍스트 토큰의 약 3분의 1 가격이라는 것이 이 방식이 성립하는 조건이다.
이 아이디어가 일반화되면 압축 전략의 설계 축이 달라진다.
"무엇을 버릴까"가 아니라 "어떤 매체가 가장 조밀한가"가 질문이 된다.

### 기존 설정을 원래 형태로 읽는 것이 이주 비용을 없앤다

omp가 Cursor MDC, `.clinerules`, `AGENTS.md`, Copilot `applyTo`를
변환 없이 원래 모양으로 읽는다는 결정은 사소해 보이지만 채택 곡선을 바꾼다.
새 에이전트 도구를 시도할 때 가장 큰 장벽은 성능이 아니라
팀이 지난 분기에 쌓아 둔 설정을 다시 만들어야 한다는 사실이다.

"임포터를 제공하고 변환을 기대하는" 접근과
"이미 디스크에 있는 것을 그대로 읽는" 접근은 사용자 입장에서 완전히 다르다.
전자는 되돌리기 어려운 결정이고 후자는 그냥 실행해 보는 일이다.
`_source`, `_shadowed`, 우선순위 속성으로 어느 파일에서 온 설정인지 추적한다는 점도
여러 도구를 병행하는 실무 상황을 전제한 설계다.
도구 경쟁이 치열한 영역에서는 이주 비용을 0으로 만드는 것이
기능 하나를 더 넣는 것보다 큰 차이를 만들 수 있다.
