# 모델은 요청하고 하네스는 실행한다: 하네스 엔지니어링을 처음부터

트윗: [Harness Engineering: explicado desde cero](https://twitter.com/santtiagom_/status/2098782814837543075)

## 요약

santi(@santtiagom_)가 2026년 9월 12일 스페인어로 쓴 Twitter Article이다.
10월 6일 기준 조회수는 76만 1,900회, 북마크는 3,400회다.
글은 1년 전만 해도 에이전트를 개선하는 방법을 물으면 다른 모델을 써
보거나 프롬프트를 더 잘 쓰라는 답이 대부분이었지만,
그것은 일부일 뿐이라는 문장으로 시작한다.

저자는 세 가지 사례를 든다.
OpenAI는 사람이 한 줄도 쓰지 않고 100만 줄,
1,500개 풀 리퀘스트 규모의 내부 제품을 만들었다.
LangChain은 Terminal Bench 2.0에서 30위이던 자사 코딩 에이전트를 모델을 바꾸지
않고 상위 5위로 올렸다.
Anthropic은 같은 모델이라도 구성에 따라 보기에는 멀쩡하지만 동작하지 않는 앱이
나오기도 하고, 제대로 동작하는 앱이 나오기도 한다는 것을 기록했다.
셋 다 모델을 바꾸지 않았고, 모델을 둘러싼 시스템에 투자했으며,
그것을 하네스 엔지니어링이라 부르기 시작했다는 것이 저자의 정리다.

글의 중심 문장은 모델이 아닌 모든 것이 하네스라는 정의다.
모델은 텍스트를 받아 텍스트를 돌려줄 뿐이고, 파일을 열지도,
명령을 실행하지도, 기억하지도 않는다.
하네스는 모델이 읽을 것을 조립하고, 응답을 해석하고, 요청한 행동을 실행하고,
일어난 일을 저장하고, 작업이 끝났는지 판단한다.
Claude Code를 쓰면 모델은 Claude이고 Claude Code가 하네스이며,
Codex에서는 Codex가 하네스이고 Sol이 모델이라고 저자는 설명한다.

저자는 게시물에 좋아요 버튼을 추가해 달라는 요청 하나를 예로 들어,
텍스트만 돌려주는 모델에 부품을 하나씩 더하며 하네스를 쌓는다.
부품은 아홉 개이고 두 무리로 나뉜다.

| 무리                      | 부품        | 없으면 생기는 일                         |
| ------------------------- | ----------- | ---------------------------------------- |
| 하네스가 모델에게 주는 것 | 도구(tools) | 모델이 저장소에 아무것도 할 수 없다      |
|                           | 루프        | 요청 하나, 응답 하나로 끝난다            |
|                           | 메모리      | 호출 사이에 모든 것을 잊는다             |
|                           | 컨텍스트    | 너무 많이 보내 잡음이 늘거나 창을 넘는다 |
|                           | 작업 공간   | 실수가 사용자 컴퓨터에서 일어난다        |
|                           | 목표와 검증 | 끝났다는 말만 있고 끝났다는 증거가 없다  |
| 하네스가 사람에게 주는 것 | 권한과 한계 | 하면 안 되는 일을 한다                   |
|                           | 관측 가능성 | 왜 실패했는지 알 수 없다                 |
|                           | 평가(evals) | 개선했는지 망가뜨렸는지 알 수 없다       |

도구 부분에서 저자는 도구를 어떻게 설계하느냐가 에이전트의
행동을 바꾼다고 강조한다.
`editar_archivo`가 그냥 오류만 돌려주는 것과, Post.tsx에서 그 텍스트를 찾지
못했지만 42행에 들여쓰기만 다른 비슷한 부분이 있다고 돌려주는 것은 다르다.
OpenAI는 에이전트가 읽을 것을 염두에 두고 린터 오류 메시지를 썼다고 덧붙인다.
루프는 ReAct 패턴, 즉 추론하고 행동하고 결과를 관찰한 뒤 다시 추론하는 순환으로
설명하고, LangChain의 공식인 에이전트는 모델 더하기 하네스라는 문장을 인용한다.

메모리는 모델이 상태를 갖지 않으므로 하네스가 상태를 밖에 저장하고 매
호출에 다시 넘기는 것이다.
긴 작업에서는 세션 사이의 연속성도 필요한데, Anthropic은 각 세션이 진행 파일과
명확한 커밋을 남기게 해 다음 세션이 이어받게 했다고 소개한다.
컨텍스트는 프로젝트 전체 대신 지도를 주고,
나머지는 필요할 때 가져오는 점진적 공개(progressive disclosure)로 다룬다.
저자는 컨텍스트 창이 Sol은 약 100만 토큰이고 Claude도
비슷하지만, 큰 코드베이스는 그보다 클 수 있고 더 많은 컨텍스트가 더 좋은
컨텍스트는 아니라고 말한다.
이미 처리한 내용을 하네스가 고쳐 쓰면 그 지점부터 캐시가 깨진다는 비용도 짚고,
길어진 대화는 압축(compaction)하거나 새 세션으로 넘긴다고 설명한다.

작업 공간 부분은 샌드박스를 다룬다.
저자에 따르면 Codex는 운영체제 샌드박스 안에서 명령을 실행하며 읽기 전용,
프로젝트 폴더 쓰기, 전체 접근 세 단계를 고르게 하고,
기본값은 가운데이며 네트워크는 꺼져 있다.
샌드박스는 프로젝트 밖으로 새는 파괴적 명령,
요청하지 않은 연결, 에이전트가 읽는 자료에 숨은 지시라는 세 가지에서 보호하지만,
보장이 아니라 층 하나라고 저자는 덧붙인다.
목표와 검증 부분은 좋아요 버튼 요청을 목표, 제약, 수락 기준으로 바꾸는 과정이다.
모델이 다 됐다고 말하는 것은 모델이 일어났다고 믿는 것이지 실제로 일어난 일이
아니므로, 검증은 모델 바깥에서 증거를 찾아야 한다.
Anthropic이 만드는 쪽을 생성기(generator),
검사하는 쪽을 평가기(evaluator)라 부르며 역할을 나눈 것도 소개한다.

사람에게 주는 세 부품 중 권한에서 저자가 가장 강조하는 문장은 중요한 한계는
지시문이 아니라 권한 시스템에 있어야 한다는 것이다.
아무것도 지우지 말라는 지시는 모델이 매 순간 제대로 해석해야 하지만,
삭제 도구가 아예 없으면 해석할 것이 없다.
재시도 횟수, 시간, 비용에 상한을 두고, 같은 테스트를 다섯 번 고치려다 실패하면
실행을 멈추고 사람에게 결정을 넘기라고 권한다.
관측 가능성은 모델이 받은 컨텍스트, 고른 도구,
매개변수, 결과, 방향을 바꾼 지점을 추적으로 남기는 것이고,
평가는 같은 작업 묶음을 바꾸기 전과 후에 돌려 비교하는 것이다.
주변 파일까지 컨텍스트에 넣는 변경이 복잡한 작업에서는
좋아졌지만 단순한 작업에서는 엉뚱한 파일을 고치게 만든 예를 들어,
작업 하나로 시험해서는 이런 퇴행을 볼 수 없다고 설명한다.

마지막 부분은 스킬, MCP, 서브에이전트,
장기 메모리를 새 메커니즘이 아니라 앞의 부품을 확장한 것으로 정리한다.
스킬은 컨텍스트를 다루는 더 정돈된 방법이고,
MCP는 도구를 더하는 표준이며, 서브에이전트는 조율된 여러 루프이고,
장기 메모리는 작업을 넘어 살아남는 상태라는 것이다.
저자는 하네스라는 말이 소프트웨어에서 오래전부터 테스트
대상을 둘러싸고 입력을 넣고 결과를 확인하는 테스트 하네스를 뜻해 왔다고 짚고,
하네스 엔지니어링을 모델이 실제 작업을 끝내게 하는 시스템을 설계하고 측정하고
개선하는 일이라고 정의한다.
또 Claude Code와 Codex는 하네스를
끼운 채 모델을 사후 학습하므로 도구 로직을 바꾸면 성능이 떨어질 수 있지만,
LangChain이 Opus 4.6을 Claude Code와 다른 하네스에서 비교했을 때 Claude Code에서
점수가 꽤 낮았다며 기본 하네스가 늘 최선은 아니라고 덧붙인다.

## 분석

### 이 글은 개념서이지 실험 보고서가 아니다

글의 가치는 새 사실이 아니라 정리 방식에 있다.
첫머리의 OpenAI, LangChain, Anthropic 사례는 모두 다른 곳에서 나온 이야기를 한
문장씩 옮긴 것이고, 본문은 그 사례를 검증하지 않는다.
대신 좋아요 버튼이라는 하나의 작업을 끝까지 들고 가며 부품이 하나 빠질 때마다
무엇이 실패하는지 보여 준다.
이 구성은 각 부품을 기능 목록이 아니라 결핍으로 정의한다는 점에서 효과적이다.

이 저장소에는 하네스를 다룬 문서가 이미 많다.
`agentic-coding/harness-engineering.md`, `agentic-coding/what-is-a-harness.md`,
`agentic-coding/harness-is-the-company.md`가 각각 정의, 소유권,
회사 전략의 관점에서 같은 주제를 다룬다.
이 글은 그중 가장 입문에 가까운 자리, 즉 모델과 하네스의 경계를
처음 긋는 자리에 놓인다.
스페인어권 독자를 위해 처음부터 다시 설명했다는 점에서, 하네스 엔지니어링이라는
말이 영어권 업계 용어에서 일반 개발자 교육 용어로 퍼지고 있다는 신호로도 읽힌다.

### 두 무리의 구분이 이 글의 진짜 기여다

아홉 부품을 모델에게 주는 여섯과 사람에게 주는 셋으로 나눈 것은
단순한 분류 이상이다.
앞의 여섯은 자율성을 늘리고, 뒤의 셋은 그 자율성을 통제한다.
에이전트 도구를 평가할 때 대부분의 비교가 앞의 여섯,
특히 컨텍스트와 도구에 몰리는 것을 생각하면, 권한, 관측,
평가를 별도 무리로 떼어 낸 것은 독자의 시선을 의도적으로 돌리는 장치다.
저자가 컨텍스트 엔지니어링을 하네스의 한 부품일 뿐이라고 굳이
말한 것도 같은 맥락이다.

### 지시가 아니라 구조로 막으라는 원칙

권한 부분의 핵심 문장은 이 글에서 가장 실용적인 주장이다.
삭제하지 말라는 지시는 확률적으로 지켜지고,
삭제 도구가 없는 구조는 결정적으로 지켜진다.
이 원칙은 샌드박스 부분의 숨은 지시(prompt injection) 이야기와 맞물린다.
모델이 문서 속 지시에 속더라도, 그 지시를 실행할 도구나 네트워크가 없으면
피해가 멀리 가지 못한다.

## 비평

### 근거 없는 수치가 도입부를 떠받친다

글은 OpenAI의 100만 줄과 1,500개 PR, LangChain의 30위에서 5위,
Opus 4.6이 Claude Code에서 더 낮게 나왔다는 측정을 근거처럼 든다.
그러나 본문 텍스트에는 각 수치가 어디서 나왔는지,
어떤 조건에서 측정했는지가 없다.
글 곳곳에 링크가 걸려 있지만 나는 그 링크를 따라가 확인하지 않았으므로, 이
문서도 저자의 주장으로만 옮겼다.
개념을 가르치는 글이라면 사례의 정확성이 덜 중요해 보일 수 있지만,
하네스가 모델보다 중요하다는 핵심 주장을 이 사례들이 떠받치고 있으므로 출처 없는
수치는 글 전체의 무게를 흔든다.

특히 Codex의 모델 이름을 Sol이라 하고 그 컨텍스트 창을 약 100만 토큰이라고
적은 부분, Codex 샌드박스의 기본값과 네트워크 설정을 단정한 부분은 제품
버전에 따라 바뀌는 정보다.
입문서가 특정 시점의 제품 설정을 일반 사실처럼 적으면, 몇 달 뒤
독자에게는 틀린 정보가 된다.

### 하네스가 모든 것을 설명한다는 정의는 반증할 수 없다

모델이 아닌 모든 것이 하네스라는 정의는 이해하기 쉽지만, 그만큼 넓다.
이 정의에서는 실패가 일어났을 때 그것을 언제나 하네스의 문제로
다시 설명할 수 있다.
도구 설명이 모호했거나, 컨텍스트가 부족했거나,
검증이 약했다고 말하면 되기 때문이다.
저자가 관측 가능성 부분에서 모델이 실패했다는 판단
대신 어느 부품을 고쳐야 할지 보라고 권하는 것은 실무적으로 맞지만,
모델 자체의 한계가 원인인 실패를 구분하는 방법은 제시하지 않는다.

같은 하네스에서 모델만 바꿔 평가를 돌리는 것이 그 구분의 방법일 텐데,
글은 평가를 하네스 변경 전후 비교로만 설명한다.
모델과 하네스를 각각 고정하고 다른 쪽을 바꾸는 이원 비교가 빠져 있어서,
하네스가 중요하다는 결론이 어느 정도까지 일반화되는지 독자가 판단하기 어렵다.

### 하네스와 모델의 결합을 언급하고 지나간다

글 끝부분에서 저자는 Claude Code와 Codex가 하네스를 끼운 채 모델을
사후 학습한다고 말한다.
이것은 모델과 하네스를 깔끔하게 나눈 글 전체의 전제를 흔드는 사실이다.
모델이 특정 하네스의 도구 형식에 맞춰 학습되었다면, 모델이 요청하고 하네스가
실행한다는 경계는 기술적으로는 맞아도 성능 면에서는 이미 섞여 있다.
저자는 이 긴장을 하네스 엔지니어링이 반복 작업이어야 하는 이유로만 쓰고,
독자가 자기 하네스를 만들 때 이 결합이 어떤 제약이 되는지는 다루지 않는다.

## 인사이트

### 도구 오류 메시지가 새로운 API 설계 표면이 된다

저자가 든 `editar_archivo` 예시는 작지만 파급이 크다.
사람을 위한 오류 메시지는 짧고 정중하면 충분했지만,
에이전트를 위한 오류 메시지는 다음 행동을 고를 수 있을 만큼 구체적이어야 한다.
OpenAI가 린터 메시지를 에이전트가 읽을 것을 염두에 두고 썼다는 일화는, 앞으로
라이브러리와 CLI가 사람과 에이전트라는 두 독자를 동시에 상대해야 한다는 뜻이다.
과거 웹 API가 사람이 읽는 HTML에서 기계가 읽는 JSON으로 옮겨 갔던 것처럼,
개발 도구의 출력도 에이전트가 소비하기 좋은 형태로 바뀔 가능성이 크다.
그 변화는 오류 메시지 품질이 곧 에이전트 성능 지표가 되는
방향으로 이어질 것이다.

### 하네스의 평가는 소프트웨어 테스트의 역사를 되풀이한다

저자는 하네스라는 단어를 테스트 하네스에서 가져왔다고 설명하는데, 그 연결은 어원
이상의 의미를 가진다.
작업 하나로 시험하면 퇴행을 볼 수 없고 같은 작업 스무 개를 전후로 돌려야 한다는
설명은, 단위 테스트와 회귀 테스트가 자리 잡던 과정과 같은 이야기다.
소프트웨어가 테스트 없이 커지다가 회귀 때문에 테스트 문화를 받아들였듯이,
에이전트 하네스도 평가 묶음 없이 기능을 더하다가 같은 벽에 부딪힐 것이다.
차이는 결과가 결정적이지 않다는 점이다.
같은 작업도 실행할 때마다 결과가 달라지므로,
하네스의 평가는 통과와 실패가 아니라 분포를 비교하는 통계 문제가 된다.

### 입문서의 확산은 하네스가 차별점에서 기본기로 내려온다는 신호다

76만 회가 넘는 조회수와 3,400개 북마크는 이 주제가 더 이상 연구소 내부 용어가
아니라는 것을 보여 준다.
하네스의 부품이 입문서로 정리될 만큼 표준화되면, 그 부품을 갖춘 것만으로는
차별점이 되지 않는다.
도구, 루프, 메모리, 샌드박스는 모든 코딩 에이전트가 갖추는 기본기가 되고,
경쟁은 평가 묶음의 질, 도구 설계의 세밀함,
모델과 하네스의 공동 학습처럼 입문서에 다 담기지 않는 부분으로 옮겨 간다.
저자가 마지막에 짧게 언급한 사후 학습의 결합이 바로 그 경쟁이 일어나는 자리다.
