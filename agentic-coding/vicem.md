# Vicem: 코딩 에이전트를 바꿀 때 작업 맥락을 BATON.md 한 파일로 넘기는 로컬 CLI

<https://rakkunn.github.io/vicem/>

<https://github.com/RAKKUNN/vicem>

Show GN: [Vicem - 로컬 AI 코딩 에이전트 간 작업 컨텍스트를 전달하는 CLI/GUI 도구](https://news.hada.io/topic?id=36286)

## 소개

Vicem은 Claude Code, Codex CLI, Cursor, Gemini CLI 같은 로컬 AI 코딩 에이전트를
번갈아 쓸 때 작업 맥락을 다음 에이전트로 넘겨 주는 Node.js 도구다.
현재 프로젝트의 Git 상태, 최근 실행 명령과 실패 로그,
직전 에이전트의 로컬 세션 기록에서 작업 목표를 읽어
`.vicem/BATON.md`라는 파일로 정리한다.
그리고 받을 에이전트가 시작할 때 그 파일을 읽도록
`CLAUDE.md`, `AGENTS.md`, `.cursor/rules/vicem-baton.mdc`, `GEMINI.md` 같은
규칙 파일에 표식 블록을 덧붙인다.

만든 사람은 GeekNews에 올린 소개글에서 동기를 이렇게 설명한다.
한 에이전트의 사용량 한도에 닿거나 막힌 문제에서 진전이 없을 때
다른 에이전트로 넘어가는데,
그때마다 지금까지 한 일과 남은 일을 다시 설명하는 것이 번거로웠다는 것이다.
저장소 README는 여기에 컨텍스트를 줄이는 기능을 앞세운다.
제목이 `Diet the Context, Pass the Baton`이다.

2026년 11월 6일 기준 GitHub 정보는 다음과 같다.
MIT 라이선스, JavaScript, 2026년 10월 24일 생성,
스타 5개, 포크 0개, 열린 이슈 0개이고 기여자는 작성자 한 명이다.
README의 배지는 v1.2.0을 가리키고,
npm 패키지는 `vicem-cli`와 `@rakkunn/vicem` 두 이름으로 안내된다.

## 쓰는 방법

외부 패키지 의존성 없이 Node.js 18 이상만 있으면 된다고 한다.
README의 명령은 다음과 같다.

```bash
# 로컬 웹 GUI: 원본 대화와 도착지를 고르고 바통을 미리 본 뒤 넘긴다
npx -y vicem-cli gui

# 현재 저장소에서 바통을 만들고 Codex로 한 번에 넘긴다
npx -y vicem-cli codex

# 전달 전에 내용만 확인한다(저장도 실행도 하지 않는다)
node vicem.mjs codex --preview

# 해당 인계가 바꾼 지침 파일만 되돌린다
node vicem.mjs undo <handoff-id>
```

GUI는 세 단계로 나뉜다.
원본 대화를 고르고 추출된 목표를 고치는 단계,
도착지 에이전트와 전달 방식(앱 열기, 터미널에서 열기,
인계 파일만 준비)을 고르는 단계,
`.vicem/BATON.md`의 실제 내용을 확인하고 넘기는 단계다.
자동 실행이 안 되면 인계 파일은 저장된 채 남고,
GUI가 명령과 시작 프롬프트를 복사할 수 있게 해 준다.

MCP 서버와 에이전트 스킬로도 설치할 수 있다.
Claude Code는 `claude mcp add vicem -- npx -y vicem-cli mcp`로,
Codex는 `codex mcp add vicem -- npx -y vicem-cli mcp`로 붙인다.

## 바통과 코드 골격화가 동작하는 방식

README가 설명하는 처리는 크게 두 갈래다.

첫째는 세션 수확이다.
현재 작업 디렉터리에 해당하는 세션 기록만 읽어
목표(Goal), 한 일(Done), 바로 다음 할 일(Immediate NEXT)과 `git diff`를
`BATON.md`로 만든다.
홈페이지는 이 수확이 Claude Code, Codex, Gemini CLI,
Cursor(SQLite 백업), Antigravity, Aider, OpenCode, Goose를 읽는다고 한다.
GeekNews 소개글은 이 과정에 LLM 요약 호출이 없고,
토큰과 API 키 패턴은 로컬 정규식으로 가린다고 말한다.

둘째는 코드 골격화(skeletonization)다.
임포트, 타입, 함수 시그니처는 그대로 두고
12줄 이상인 함수 본문을 `{ /* ... */ }`로 접어 `BATON.md`에 싣는다.
접힌 본문은 `.vicem/ledger.json`에 색인된다.
받는 에이전트가 함수를 고쳐야 할 때는
MCP 도구 `vicem_rehydrate("src/auth.ts", "verifySessionToken")`로 원문을
불러오고,
이때 Git HEAD와 파일의 SHA-256으로 낡은 데이터인지 확인한다고 한다.

README의 단계별 표는 처리 대상마다 줄이는 정도를 다르게 주장한다.

| 단계               | 처리                                      | 주장하는 절감        |
| ------------------ | ----------------------------------------- | -------------------- |
| 세션 인계          | Goal, Done, NEXT, `git diff` 추출         | 인계 3초 미만        |
| 코드 골격화        | 시그니처 유지, 본문은 ledger 색인         | 코드 토큰 80~90%     |
| 테스트와 로그      | 실패한 단언과 사용자 코드 스택 프레임 5개 | 로그 잡음 95%        |
| 데이터와 잡음 차단 | 락 파일 제외, 데이터는 스키마와 샘플 2행  | 데이터 부피 98%      |
| 안전 장치          | 비밀 값 가림, 골격 덮어쓰기 방지 가드     | 유출 0건, 의존성 0개 |

## 안전장치와 되돌리기

README는 인계가 보이지 않게 일어나지 않도록 몇 가지를 둔다.
`--preview`는 아무것도 저장하거나 실행하지 않고 내용만 보여 주며,
예전 `--dry-run`은 인계 파일을 쓰므로 `--preview`를 쓰라고 안내한다.
GUI는 검토한 뒤 내용이 바뀌면 인계를 거부한다.
`undo`는 그 인계가 바꾼 지침 파일만 복원하며,
그 사이 지침이 바뀌었으면 덮어쓰지 않고 거부한다.
에이전트가 소스 코드에 가한 수정은 되돌리지 않는다.

README가 스스로 밝히는 한계도 분명하다.
전달과 앱 실행은 에이전트가 그 맥락을 읽었다는 것을 증명하지 않는다.
미리보기 토큰은 인증이 아니라 일관성 확인용이다.
검증은 자동화된 단위·통합 테스트와 macOS 브라우저 확인까지이고,
Windows와 Linux의 실제 에이전트 실행과
도착지 에이전트가 실제로 읽는지는 이 테스트로 인증되지 않았다.
Windows CLI 동작은 Node 22와 24의 네이티브 CI에서 확인했다고 한다.

## 비평

### 수치는 예시이지 측정이 아니다

README와 홈페이지의 터미널 영수증은
184,200 토큰을 14,800 토큰으로, 91.9% 줄였다고 보여 준다.
같은 숫자가 홈페이지의 데모 화면에도 그대로 나오고,
어느 저장소에서 어떻게 쟀는지는 적혀 있지 않다.
단계별 표의 이전 값도 `~120,000 tok`처럼 근사치다.
홈페이지는 이 표에 측정된 기여라는 제목을 붙였으니,
이 문서는 이 수치를 예시 출력으로 읽는다.
또 머리말의 80~99%는 코드, 로그, 데이터 덤프라는
서로 다른 대상의 절감률을 한 범위로 묶은 것이어서
한 세션 전체의 절감률이 아니다.

### 토큰이 줄어도 일이 이어지는지는 재지 않았다

이 도구가 풀려는 문제는 맥락을 줄이는 것이 아니라
다음 에이전트가 같은 일을 계속하게 하는 것이다.
그런데 README의 어느 수치도 인계 뒤 작업이 성공했는지를 말하지 않는다.
바통으로 넘겼을 때와
처음부터 다시 설명했을 때와
에이전트 자체의 압축 기능을 썼을 때를 같은 과제로 비교한 결과가 없다.
아낀 토큰의 일부는 `vicem_rehydrate` 호출과 그 지연으로 되돌아온다.
이 되돌림이 얼마나 되는지도 숫자로 나와 있지 않다.

### 무손실은 저장에서만 성립한다

README는 골격화를 무손실이라 부르며,
요약이 형 계약을 잊는 것과 대비한다.
시그니처는 보존되니 형 정보에 대해서는 맞는 말이다.
이 문서의 해석으로는, 접힌 본문에 든 부수 효과와 암묵적 전제는
에이전트가 그 함수를 열어 보기로 하는 순간에만 돌아온다.
호출하는 쪽만 고치고 본문을 열지 않은 에이전트는
접힌 함수의 숨은 전제를 모른 채 수정한다.
무손실은 디스크의 정보에 대한 말이고,
받는 에이전트의 주의 속에서까지 성립한다는 보장은 아니다.

### 다른 도구의 비공개 저장소에 기대고 있다

수확 기능은 `~/.claude`, `~/.codex`, Cursor의 SQLite 같은
다른 도구의 로컬 기록 형식을 읽는다.
이 형식들은 대체로 공개된 계약이 아니라서 도구가 업데이트될 때 깨질 수 있다.
작성자도 macOS 중심으로 먼저 검증했고 Windows와 Linux는 보완 중이라고 밝혔다.
이 문서는 코드를 실행해 보지 않아서
여덟 개 에이전트 가운데 실제로 몇 개를 읽는지는 확인하지 못했다.

### 문서마다 이름과 버전이 다르다

GeekNews 소개글은 `npx @rakkunn/vicem@latest --to codex`, `--undo`, `--diet`,
MCP 도구 `vicem_expand_symbol`을 쓴다.
README는 `npx -y vicem-cli codex`, `undo <handoff-id>`,
`vicem_rehydrate`를 쓴다.
홈페이지는 아직 v1.0.0이라 적고 있다.
릴리스가 며칠 간격으로 나오는 초기 프로젝트에서 흔한 일이지만,
쓰려는 사람은 어느 문서가 현재 코드와 맞는지 직접 확인해야 한다.
README의 HOL Guard, Glama, mcpservers.org 배지는 제3자 평가를 암시하지만
이 문서는 그 페이지를 열지 않았다.

### 비밀 유출 0건이라는 표현이 너무 강하다

README는 비밀 값 가림의 결과를 유출 0건이라고 적는다.
가림은 공급자 키 패턴, PEM 블록, 엔트로피가 높은 대입문을 대상으로 하는
정규식 기반의 규칙이라서 규칙에 없는 형식은 지나갈 수 있다.
GeekNews 소개글의 표현도 패턴이 로컬에서 가려진다는 정도다.
따라서 이 문장은 보증이 아니라 목표로 읽는 편이 맞다.

## 인사이트

### 바통이 통하는 이유는 압축이 아니라 규칙 파일의 수렴이다

Vicem은 어느 에이전트에도 연동 코드를 넣지 않는다.
이미 모든 에이전트가 시작할 때 읽는
`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.cursor/rules`를 통로로 쓴다.
도구마다 제각각이던 지침 파일 관행이 이 통로를 만들었고,
이 도구는 그 공통 분모 위에서 인계를 구현한 것이다.
이 문서의 해석으로는 여기서 두 가지가 따라온다.
에이전트 제작사가 세션 내보내기를 직접 제공하면 이 중간 계층은 필요 없어진다.
반대로 규칙 파일이 공유되는 쓰기 가능한 통로가 되면 새로운 위험이 생긴다.
바통은 실패 로그와 직전 대화에서 뽑은 문장을 담는데,
그 안에는 웹 페이지나 도구 출력처럼 믿을 수 없는 텍스트가 섞일 수 있다.
다음 에이전트는 그 파일을 지침으로 읽는다.
README에는 이 경로에서의 지침 주입에 대한 언급이 없다.

### 골격과 본문의 관계는 캐시와 같아서 적중률로 평가해야 한다

골격은 색인이고 `vicem_rehydrate`는 캐시 채우기에 해당한다.
이 틀에서 보면 절감은 받는 에이전트가 읽기만 하는 파일과
고치는 파일의 비율에 달려 있다.
대부분의 작업이 본문을 건드린다면 접은 본문을 곧바로 다시 불러오게 되어
토큰은 아끼지 못하고 호출만 늘어난다.
그러므로 인계 도구의 성능 지표는 줄인 토큰 비율이 아니라
받는 에이전트가 접힌 본문을 필요로 한 횟수와 그때의 성공률이어야 한다.

### 결론을 바꿀 관찰

같은 저장소와 같은 과제로 바통 인계와 처음부터 재설명과 압축 기능을 비교해
완료율과 총 토큰을 보여 준 결과가 나오면 주장이 처음으로 검증된다.
`vicem_rehydrate` 호출 기록이 인계 한 번당 몇 번인지 공개되면
캐시 비유가 맞는지 판단할 수 있다.
Windows와 Linux에서 도착지 에이전트가 바통을 읽었다는 증거가 나오면
작성자가 밝힌 한계가 줄어든다.
