# 테스트 기법 이름만 알려주면 에이전트는 그 기법을 흉내만 낸다

원문: [How well do agents use test/verification techniques?](https://danluu.com/agentic-testing/)

HN 토론: <https://news.ycombinator.com/item?id=49605246> (187점, 71개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/adrda9>

GN 토론: <https://news.hada.io/topic?id=33410>

## 요약

Dan Luu가 2026년 9월에 쓴 실험 보고다.
문제의식은 이전 글에서 이어진다 —
코딩 에이전트에게 효과적인 테스트 기법을 쓰게 하면
특정 품질 기준에 도달하기가 그 어느 때보다 쉬워졌는데도
소프트웨어 품질은 오히려 나빠지고 있어 보이며,
그렇다면 개발자들이 쓰는 기본값이 잘 작동하지 않는다는 뜻이라는 것이다.

이 글이 검증하려는 것은 단순하다.
에이전트에게 특정 기법이나 라이브러리를 쓰라고 지시하면 구현 정확도가 올라가는가.
저자는 이것을 “테스트에 전문성이 없지만
어떤 기법을 쓰라는 말은 들어 본 사람”이 에이전트를 지도할 때
얼마나 효과가 있는지를 재는 시험으로 규정한다.

### 실험 설계

이전에 쓰던 Zstd 구현 평가를 재사용했다.
구현 언어는 전부 Rust이고,
Zstd를 구현하라는 프롬프트에
“테스트 주도 개발을 써라”, “Lean 4를 써라”, “QuickCheck을 써라”,
“속성 기반 테스트를 써라” 같은 부가 지시를 붙여 조건을 나눴다.
IMAP RFC 등 다른 평가도 함께 돌렸다.

프롬프트 조건은 26가지다 —
ACL2, Alloy, “위험 영역 감사와 퍼징”, “먼저 감사”, Creusot,
Default(부가 지시 없음), 차등 테스트, 퍼징, Hegel, Insta,
Judgement(최선의 기법을 알아서 쓰라고 요청), Kani, Lean 4,
“실수하지 마라”, 변형 테스트(metamorphic testing), 뮤테이션 테스트,
속성 기반 테스트, Proptest, QuickCheck, rstest, Rust 내장 테스트 프레임워크,
SMT 솔버(Z3, cvc5, Yices 모두 설치), Spin, TDD, TLA+, Verus.
여기에 스킬 4종이 추가됐다 —
공식 Hegel 스킬, ECC Rust 테스트 스킬(ECC는 GitHub 별 25만 개, 포크 3.8만 개의 스킬 모음),
Trail of Bits 속성 테스트 스킬,
그리고 저자가 직접 쓴 테스트 스킬이다.
저자는 자신을 “스킬 대신 프롬프트를 쓰는 러다이트이며
좋은 스킬을 쓰는 감이 전혀 없다”고 소개한다.
자기 스킬을 제외한 나머지는 codex에게 관련 스킬을 찾아 달라고 했을 때
가장 위에 올라온 것들이라 골랐다.

모델은 codex의 GPT-5.6 Sol이며 medium과 xhigh 두 노력 수준에서 돌렸고,
조건마다 노력 수준별 80회, 총 160회씩 실행했다.
평가 지표는 숨겨진 테스트를 100% 통과한 실행의 비율이고,
비용을 x축에 둔 산점도로 제시된다.

### 사전 등록한 예측

저자는 결과를 보기 전에 추측을 등록해 뒀다.
TDD가 저조할 것(확신도 55%),
형식적 방법이 두각을 나타내지 못할 것(52%),
“실수하지 마라”가 지시 없음보다 낫지 않을 것(95%),
ECC 테스트 스킬이 두각을 나타내지 못할 것(65%),
Hegel 스킬이 두각을 나타내지 못할 것(65%),
Trail of Bits 테스트 스킬이 두각을 나타내지 못할 것(55%)이다.

TDD를 넣은 이유는 저조할 것이라고 생각해서라고 밝힌다.
형식적 방법에 대해서는, 그것이 효과적이고 유용하지만
좋은 테스트 방법도 마찬가지로 효과적이고 유용하며
단순한 문제에서는 비슷한 수준의 숙련도로 쓴다면
형식적 방법이 앞설 이유가 없다는 것이 근거다.
다만 형식적 방법이 효과적인 테스트 기법보다 더 많이 홍보돼 왔으므로
연구소들이 합성 데이터로 만든 RL 환경으로
모델을 형식적 방법에 매우 능숙하게 훈련시켰을 가능성도 있다고 덧붙인다.
ECC 스킬에 대해서는 크기가 꽤 크고 유용해 보이는 정보가 없으며
에이전트에게 TDD를 시키는데 그것이 오히려 결과를 나쁘게 만들 것이라고 봤다.
Hegel 스킬은 SKILL.md와 연결된 Rust 참조를 합쳐 2만 토큰이 넘고
에이전트 지시라기보다 튜토리얼처럼 읽힌다는 점을 들었다.

### 전체 결과

저자가 제시하는 결론은 세 가지다.
어느 조건도 크게 두각을 나타내지 않았다.
Default(부가 지시 없음)가 평균보다 상당히 잘했다.
xhigh에서 퍼징·속성 기반 테스트 계열이 형식적 방법보다 평균적으로 조금 나았고,
medium에서는 훨씬 뒤섞였다.
codex가 추천한 테스트 스킬들은 저조했지만
저자가 급조한 커스텀 스킬은 괜찮았다 —
주요 차이는 저자의 스킬이 에이전트의 기본 행동에서
더 생산적인 행동 쪽으로 밀어내도록 설계된 반면
다른 스킬들은 튜토리얼에 가깝다는 점이다.
TDD는 예측대로 저조했다.

에이전트가 실제로 무엇을 했는지 보면
대체로 이 도구와 기법을 잘 쓸 줄 모른다는 것이 곧 분명해진다.
저자는 Gary Bernhardt의 논평을 인용한다 —
“AI 에이전트의 테스트 접근법은 대략,
15년 전에 목(mock)을 실제로 써 본 적도 없이 반대하던 사람이
상상해 낸 병적인 사례들을 가져다가,
그 병리를 테스트 전략의 근간으로 삼는 것이다.”

특정 기법을 쓰라고 하면 이 접근법이 기대만큼 바뀌지 않는다.
에이전트는 평소 쓰던 테스트를 다른 기법의 프레임워크 안에 넣어 쓰거나,
기법을 피상적으로만 쓰고 그 기법에서 가치를 뽑아내는 일은 하지 않는다.
형식적 방법에서는 대체로 무관한 속성을 증명했고,
속성 기반 테스트에서는 완전 무작위 입력에 크게 기대어
잘못된 입력·거부 경로만 반복해서 때리거나
사소한 속성을 하나 찾아 거기에 저가치 무작위 실행을 돌렸다.
IMAP RFC(조건별 40회)나 다른 RFC들에서도 결과는 실질적으로 다르지 않았다.

xhigh에서는 에이전트가 자기가 쓴 테스트를 통과시키는 데는 대체로 성공했지만
테스트 자체가 나빴다 —
예컨대 네 개의 비트스트림을 쓰는 기능을 시험하면서
동일한 비트스트림 네 개를 넣어
스트림 순서를 바꿔 생기는 버그를 전혀 잡지 못하는 식이다.

### 조건별로 관찰된 것

Verus는 명세와 코드의 일치를 증명할 수 있는데도
에이전트는 그렇게 쓰지 않고 Zstd에 관한 추상적 속성만 증명했다.
증명된 속성 수는 적었고 흥미롭지도 않았으며,
`A => A` 형태의 공허한 증명을 자주 썼다.
저자가 인용한 실제 Verus 증명은
`0 < a <= window`, `0 < b <= window`, `0 < c <= window`를 요구하고
같은 세 조건을 보장하는 형태다.

Alloy는 정확도에서 두 번째로 나빴다.
Alloy가 반례를 찾아 에이전트가 완화 조치를 넣은 사례가 하나 있었으나,
그 반례는 8비트 오버플로에 의존했고
실제 구현은 64비트 usize를 써서 주어진 입력에서 오버플로가 불가능했으므로
버그를 막지 못한 채 코드만 복잡해졌다.

차등 테스트는 세 번째로 나빴다.
160회 중 두 개의 완전한 구현을 만들어 비교한 에이전트는 하나도 없었다.
135회가 차등 테스트라 부를 만한 무언가를 하기는 했지만
대체로 사소하고 사실상 쓸모없었으며,
버그를 잡을 수 있었을 경우에도
독립적으로 구현하는 대신 같은 것을 두 번 써서 같은 버그를 양쪽에 넣었다.

TDD는 에이전트 행동을 크게 바꿨다.
테스트를 두 배로 만들었고 훨씬 반복적인 워크플로로 일했다.
실질적인 구현 전에 실패하는 테스트를 하나 이상 가진 경우가
TDD 조건에서는 160회 중 67회였고 Default에서는 0회였다.
그런데 네 개의 허프만 스트림에 쓰이는 점프 테이블 같은 사례에서
TDD 에이전트는 일반적인 경우를 다루는 테스트를 더 많이 쓰고도
평가 테스트에 더 자주 실패했다 —
어려운 경우를 다루지 않는 테스트를 더 많이 썼기 때문이다.
저자는 Yossi Kreinin의 설명을 인용한다 —
코드보다 테스트를 먼저 쓰면 무엇이 어려울지 덜 알기 때문에 어려운 경우를 시험하기 힘들고,
TDD는 블랙박스 테스트 쪽으로 몰아가는데
복잡한 기계 장치에는 화이트박스 테스트가 더 효과적이라는 것이다.

Hegel의 실제 작업 흐름은
RFC와 API 읽기 → Zstd 구현 → 일반 테스트 실행 → Hegel 문서 읽기 →
Hegel로 단순한 속성 테스트 1~4개 작성 → 다시 일반 Rust 테스트로 정리됐다.
공식 Hegel 스킬은 정확도를 개선하지 못했고 오히려 조금 나빴으며,
더 두드러진 것은 비용이었다 — medium 26%, xhigh 41% 증가.
스킬 본문이 3.4만 자이고 4.5만 자짜리 Rust 참조를 불러와 2만 토큰을 넘는데,
시작 시 적재된 뒤 여러 후속 동작에서 다시 읽혔다.
캐시 적중률이 첫 읽기 이후 99.85%로 매우 높았는데도
비용의 상당 부분을 차지했다는 것이다.
스킬은 160회 중 157회에서만 사용됐다.

Trail of Bits 스킬은 160회 중 108회만 실제로 열어 읽었다.
스킬은 Rust에서 proptest를 쓰라고 제안하는데
의존성 추가에 승인이 필요하다고도 적혀 있고
이 실행들은 전부 단일 턴 자율 실행이라 추가가 이루어지지 않았다.

rstest에서는 에이전트가 rstest 안에 표준 단위 테스트를 썼을 뿐
rstest를 rstest이게 만드는 것을 쓰지 않아 목적이 무산됐다.
Rust 내장 프레임워크를 명시적으로 쓰라고 하면
테스트 수는 늘었지만(medium 두 배, xhigh 25%) 정확도는 나아지지 않았다.

퍼징에서는 무작위 구조화 입력을 만든 10회 중 절반이 실제 버그를 찾았다.
저자는 160회 중 5회에서만 퍼징을 어느 정도 효과적으로 쓴 것이
좋은 성적은 아니지만 지금까지 본 것 중 더 효과적인 축이라고 평가하며,
에이전트가 어떤 의미에서는 이 방법을 알고 있고
훈련이나 지시로 더 잘하게 만들 수 있음을 시사한다고 본다.

SMT 조건에서는 `byte1 + (byte2 << 8) + 0x7F00`이어야 할 계산을
많은 에이전트가 `byte1 + (byte2 << 8) | 0x7F00`으로 구현했다.
SMT 솔버로 이 계산에 관한 속성을 증명하고도 여전히 틀린 코드를 썼다.

TLA+에서는 160회 중 159회가 모델을 만들었고
30회가 버그가 잦은 영역(허프만/FSE/엔트로피)을 모델링했지만,
TLA+ 문제가 Rust 코드 변경으로 이어진 사례는 발견되지 않았다.

Kani는 실제로 실행되는 코드에 형식적 방법을 적용했다는 점에서 가장 나았고,
실제 Kani 사용이 사소하지 않은 버그를 잡아 Rust 코드를 바꾼 사례가 1회 있었다.
ACL2는 상당수 실행이 192GiB 한도에서 OOM으로 죽었고
OOM 결과는 집계에서 빠져 결과가 불투명하게 편향됐다.

ECC 스킬은 160회 중 153회가 읽었고 테스트를 더 만들게 했다.
그런데 노출 정도에 따른 기울기가 관찰됐다 —
스킬을 일찍 볼수록 행동이 더 바뀌었고 정확도는 더 나빴다.
ECC의 점수가 괜찮아 보이는 이유는
스킬을 읽지 않은 7회가 100% 정확도를 냈고
늦게 봐서 거의 영향받지 않은 9회도 100%였기 때문이다.
실제로 영향을 받은 경우만 보면 ECC는 평균 이하이며,
Rust 내장 프레임워크와 비슷하게
작고 의미 없는 테스트가 많아지는 실패 양상을 보인다.
스킬이 red-green TDD를 지시하기 때문이다.

Audit(구현 후 감사) 조건은 152회가 실제로 감사했고 151회가 문제를 찾았다고 주장했다.
그런데 대개 새 맥락에서 독립적으로 감사하지 않고
이미 저지른 실수를 감사에서도 똑같이 저질렀다.
독립 에이전트를 쓴 42회는 오히려 점수가 나빴다.
저자가 인용한 Em Chu는 자기 토큰의 대부분이 감사에 들어간다면서
서브에이전트를 만들지 말고 직접 코드를 읽으라는 것,
그리고 코드를 실행하지 말라는 두 지시를 항상 준다고 밝힌다.

저자 자신의 스킬은 최고 점수를 받았지만 의도대로 작동하지는 않았다.
다섯 항목으로 구성되어 있다 —
구현 전에 미묘한 버그가 있을 만한 영역을 생각하고
각각에 대해 있을 법한 실수와 그럴듯한 대안 해석을 말한 뒤
결과가 달라지는 검사를 고안할 것(경계 양쪽의 비대칭 예제 선호),
구현 후 고위험 영역에 대해 프로덕션 코드 맥락 없이 결과를 독립적으로 재도출해 비교할 것,
가능하면 속성 기반 테스트나 무작위 입력을 쓰되
패닉·크래시 없음만 보는 무작위화에는 노력을 최소화할 것,
무작위화할 때는 흥미로운 상태와 코드 경로를 탐색하는 입력 쪽으로 기울일 것,
세부가 불확실하면 독립적 추론으로 무엇이 옳은지 확인할 것.
그런데 “새 맥락” 항목은 거의 실행되지 않아 넣은 의미가 없었고,
퍼징과 속성 기반 테스트가 전부 수작업으로 이루어졌다.

### 저자의 결론과 후속

저자는 “에이전트에게 좋은 테스트를 쓰게 하려면 어떻게 하는가”에 대해
합리적인 테스트·분류 구조를 만들어 주면
그 위에 에이전트가 추가하게 하는 것은 큰 감독 없이도 그럭저럭 된다고 답한다.
Jamie Brandon과의 대화도 인용하는데,
스냅숏 테스트를 시키면 했다고 말하고 실제로는 단위 테스트를 쓰는 일이 있었고,
다른 프로젝트에서는 테스트를 별도 크레이트로 옮기고
AGENTS.md에 테스트를 그 크레이트에 유지하고
공개 인터페이스를 수정하지 말라고 적은 뒤에야
합리적인 종단 간 테스트를 쓰게 할 수 있었다는 것이다.

스킬에 대한 저자의 입장도 실험 후 바뀌었다.
자신이 본 스킬들은 전부 “인간용 튜토리얼 지시”처럼 쓰여 있는데,
이미 해당 주제를 어느 정도 아는 모델을 상대할 때는
그것이 최적이 아닐 것 같다는 생각이다.
모델에는 이미 기본 행동 분포가 있으므로
그 행동을 수정하는 진술을 주는 것이 자연스럽고,
아예 모르는 사람이 그 행동을 할 수 있게 하는 설명서를 쓰는 것은 아니라는 것이다.
그러면서 실패 양상이 예측 가능하고 따라서 고칠 수 있어 보이므로
개인용 스킬에 대해서는 실험 전보다 오히려 긍정적이 됐다고 적는다.

부록에는 Hegel 개발자 David R. MacIver의 반응이 실려 있다 —
“유감스럽게도 @danluu가 옳다. Hegel 스킬은 지금 좀 별로다.
많은 에이전트 스킬의 공통 문제는 에이전트가 에이전트 스킬을 잘 못 쓴다는 것이고,
우리를 포함해 다들 에이전트로 스킬을 쓴다는 것이다.”
저자는 MacIver가 이후 벤치마크를 만들어 결함을 확인했고
스킬을 개선하거나 Hegel 문서를 손보는 중으로 보인다고 전하면서,
이 글에서 나온 것이 Hegel 스킬 개선뿐이라 해도 훌륭한 일이라고 적는다.

## 분석

### 이 실험의 진짜 대조군은 Default이며, 그것이 결과를 뒤집는다

26개 조건을 나열한 표에서 가장 중요한 항목은 Default다.
어떤 부가 지시도 주지 않은 조건이 평균보다 상당히 잘했고,
“실수하지 마라”라는 농담 조건이 그와 구별되지 않았다.
저자가 결과를 요약하며 쓴 문장이 이 실험의 핵심이다 —
“쓸모없는 일을 하게 만드는 지시를 하지 않는 것이
쓸모없는 일을 하게 만드는 지시를 하는 것보다 낫다.”

이 결과 구조는 실험이 측정한 것이 무엇인지를 다시 정의한다.
표면적으로는 “어떤 테스트 기법이 가장 효과적인가”를 재는 실험처럼 보이지만,
실제로 측정된 것은 “기법 이름을 주는 것이 얼마나 해로운가”다.
26개 조건 중 다수가 Default보다 나빴다는 사실은
기법 자체의 우열이 아니라 지시 자체의 비용을 보여준다.

비용의 정체도 데이터에 드러난다.
에이전트는 지시받은 기법을 형식적으로 수행하되
그 수행이 정확도에 기여하지 않으며,
그러는 동안 실제로 정확도를 만드는 활동 — 표준 단위 테스트 —
에 쓸 예산과 주의를 나눠 쓴다.
Verus 조건에서 medium에서 xhigh로 갈 때
전통적 테스트에 훨씬 더 많은 노력이 들어가고
Verus에는 조금만 더 들어가서 결과가 괜찮아졌다는 관찰이 그 증거다.
지시는 예산을 옮기고, 옮겨진 예산은 회수되지 않는다.

### 실패 양상이 기법마다 동일하다는 것이 이 글의 가장 강한 발견이다

26개 조건의 서술을 읽으면 같은 문장이 반복된다 —
에이전트는 기법을 피상적으로만 쓰고 정확도는 표준 Rust 테스트에서 나왔다.
형식적 방법 다섯 종, 속성 기반 테스트 라이브러리 네 종,
모델 검사기 세 종이 전부 같은 양상을 보인다.

이 균일성이 중요한 이유는 원인을 좁혀 주기 때문이다.
만약 특정 도구가 어려워서 실패했다면
도구마다 실패 양상이 달라야 하고 일부는 성공해야 한다.
전부 같은 방식으로 실패한다는 것은
원인이 도구가 아니라 그 도구를 호출하는 쪽에 있다는 뜻이다.
저자가 앞선 언어 실험과 대비하는 대목이 이 추론을 뒷받침한다 —
언어 실험에서는 인기도와 성능 사이에 약한 상관이 관찰돼
훈련 데이터 양이라는 가설이 가능했는데,
여기서는 그런 패턴조차 없다.

HN에서 nseskin이 이 균일성에 대한 가장 설득력 있는 설명을 냈다.
이것이 LLM의 제약 준수 문제 전반을 보여준다는 것이다 —
에이전트는 과제에서 가장 눈에 띄고 검증하기 쉬운 부분을 충족시키고,
성공을 실제로 좌우하는 제약은 놓친다.
“퍼징을 써라”는 무작위 바이트 생성이 되고
“형식 검증을 써라”는 별로 유용하지 않은 속성의 증명이 된다 —
형식적으로는 기법이 적용됐지만 그 목적은 사라진 것이다.
그는 이것이 서로 다른 테스트 기법이 비슷한 결과를 내는 이유도 설명할 수 있다고 본다 —
문제는 특정 기법을 아느냐보다
에이전트가 자기 실제 목표를 주된 제약으로 유지할 수 있느냐에 가깝다는 것이다.[^nseskin]

movpasd는 Hypothesis를 쓰게 한 경험에서 같은 결핍을 다른 각도로 봤다.
에이전트가 코드와 그것이 모델링해야 할 실제 비즈니스 규칙 사이의 간극을 잇는 데 몹시 애를 먹었고,
어느 계층의 어떤 함수에 테스트를 써야 할지도 판단하지 못해
테스트가 도메인 로직 변경에 매우 취약했다는 것이다.[^movpasd]
그는 좋은 테스트가 결국 무엇을 테스트할지 찾는 일이며
그것은 입력 상태를 적절한 곱 상태로 나누고
각 동작을 독립적으로 검사하는 문제라고 정리한다.

그렇다면 남는 설명은 하나다.
에이전트는 “테스트가 무엇을 위한 것인가”에 대한 작동하는 모형이 없고,
기법 이름은 그 모형을 만들어 주지 않는다.
기법은 목적을 이미 아는 사람이 쓰는 도구이므로
목적이 없으면 기법의 껍데기만 남는다.
Gary Bernhardt의 인용이 이 관찰을 정확히 표현하며,
저자가 “기법 이름을 대면 그 기법에 대해 Gary가 묘사한 짓을 했다”고 정리한 것이
실험 전체의 요약이다.

### 스킬의 실패가 크기와 형식이라는 두 축에서 설명된다

네 개 스킬 중 셋이 저조했고 하나 — 급조한 것 — 가 최고 점수를 받았다.
저자가 제시하는 차이는 형식이다.
저조한 셋은 “어떻게 하는지 설명하는” 튜토리얼이고,
저자의 것은 “기본 행동에서 밀어내는” 진술 다섯 개다.

Hegel 스킬 분석이 이 차이의 비용을 수치로 보여준다.
3.4만 자 본문에 4.5만 자 참조가 붙어 2만 토큰을 넘고,
캐시 적중률 99.85%에도 불구하고 비용이 medium 26%, xhigh 41% 늘었다.
그리고 늘어난 비용이 산 것은 정확도가 아니라
이미 과하게 하던 일 — 잘못된 입력에 패닉이 없는지 확인하는 테스트 —
을 더 많이 하는 것이었다.

HN의 ivanzhaowy123이 다른 스킬 모음에서 똑같은 양상을 보고했다.
Superpowers 스킬 세트를 쓰면 에이전트가 모든 새 기능에 능동적으로 TDD를 적용하는데,
테스트에 대한 이해는 피상적인 채로 남는다는 것이다.
사용자가 “전송” 버튼이 있는 화면을 요청하면
먼저 버튼이 존재하는지 확인하는 테스트를 쓰고,
실패하니 버튼을 추가해 통과시킨다.
그 결과 테스트 스위트가 속성 존재 여부나 문자열 일치를 확인하는
저가치 케이스로 채워지며,
“실패하는 테스트를 쓰고 기능을 구현한다”는 워크플로는 따르지만
비즈니스 동작은 끝내 테스트하지 않는다.[^ivanzhao]
이 증언이 중요한 이유는 다른 스킬 모음, 다른 도메인(UI), 다른 사용자에게서
이 실험의 ECC 결과와 같은 실패가 재현됐다는 점이다.

ECC 분석은 여기에 더 불편한 결론을 더한다.
노출-반응 기울기가 관찰됐다는 것 —
스킬을 일찍 볼수록 결과가 나빴다는 것 — 은
스킬이 무해한 것이 아니라 능동적으로 해로웠다는 뜻이다.
그리고 총점이 괜찮아 보인 이유가
스킬을 읽지 않은 실행들이 만점을 받았기 때문이라는 분석은
벤치마크 총점의 신뢰성 문제를 함께 드러낸다.
저자가 “160회는 어느 합리적인 사람이 하는 것보다 많은 횟수인데도
겉으로 보면 ECC가 괜찮아 보인다”고 적은 대목이
이 글에서 방법론적으로 가장 값진 부분이다.

### 저자가 자기 예측의 이유까지 채점하는 방식이 이 글의 신뢰를 만든다

이 글은 결과를 보고하기 전에 예측을 등록하고,
결과 이후 예측 정확도를 별도 절에서 채점한다.
그런데 채점 방식이 단순한 맞고 틀림이 아니다.
“형식적 방법이 두각을 나타내지 못한다”는 맞았지만
“예상한 이유 때문이 아니었다”고 적는다 —
에이전트가 그것을 제대로 쓰지 못했으므로 애초에 앞설 수가 없었다는 것이다.

TDD 예측에 대해서도 같은 구분을 한다.
결과만 보면 맞았지만 추론이 맞았는지는 불분명하다고 적고,
자신이 예상한 실패 양상(과적합)이
실제 문제였는지 확신할 수 없다고 밝힌다.
그리고 등록하지 않았지만 자기 안에 있던 예측 두 개 —
Lean이 형식적 방법 중 잘할 것,
자기 스킬이 평범하거나 나쁠 것 — 가 모두 틀렸다고 적는다.

이 구조는 실험 보고에서 드물다.
대부분의 결과 보고는 맞은 예측을 강조하고 틀린 것을 축소하며,
맞은 이유가 틀렸을 가능성은 아예 다루지 않는다.
여기서 저자는 Max Bittker가 미리 이유까지 말해 줬는데
자신이 믿지 않았고 정확히 그 이유로 그 일이 일어났다며
“꽤 바보 같은 기분”이라고 적는다.
이 정직성이 수치 자체보다 이 글의 설득력을 만든다.

## 비평

### 단일 문제·단일 하네스·단일 모델에서 나온 결과를 기법 일반에 대한 판정으로 읽기 쉽게 쓰여 있다

실험은 Zstd 구현이라는 하나의 과제,
codex라는 하나의 하네스,
GPT-5.6 Sol이라는 하나의 모델에서 이루어졌다.
IMAP RFC와 다른 RFC 몇 개가 보조로 언급되지만
전부 “명세를 읽고 프로토콜·포맷을 구현하는” 같은 유형이다.

저자 자신도 이 한계를 여러 곳에서 인정한다 —
스킬 절에서 harness와 모델과 노력 수준마다 기본 행동이 다르다고 적고,
GPT-5.5에서 5.6으로 갈 때 프롬프트 방식이 크게 바뀌었다고 밝힌다.
그런데 제목과 결론 문장은 그 한정을 담지 않는다.
“에이전트는 형식적 방법이나 테스트 라이브러리나 기법을
효과적으로 쓰지 않았다”는 문장에는 조건절이 없다.

이 간극이 실질적인 이유는 이 글이 인용되는 방식 때문이다.
“TDD는 에이전트에게 해롭다”, “형식적 방법은 소용없다”,
“스킬은 대체로 해롭다”라는 형태로 요약되기 쉽고,
실제로 그런 요약이 이 글의 각 절 제목과 크게 다르지 않다.
Zstd처럼 비트 조작이 집중된 문제에서
형식적 방법이 잘 안 먹혔다는 것과
형식적 방법이 에이전트에게 소용없다는 것은 전혀 다른 진술인데,
글의 구조가 후자로 읽히도록 돼 있다.

### 조건 간 비교를 하지 말라고 하면서 조건을 정확도 순으로 배열한다

저자는 조건별 서술을 시작하면서
“순서에서 어떤 강한 결론도 끌어내지 말라고 경고하고 싶다”고 명시한다.
그리고 곧바로 정확도가 나쁜 순서대로 26개 조건을 배열한다.

이 배치는 경고를 무력화한다.
순서가 있는 목록은 순위로 읽히고,
“Alloy가 두 번째로 나빴다”, “차등 테스트가 세 번째로 나빴다” 같은
서수 표현이 본문에 반복해서 등장한다.
그러면서도 그 순위의 불확실성 —
80회 실행에서 부트스트랩 공분산이 어느 정도인지,
인접한 조건 간 차이가 유의한지 — 는
그래프에 마우스를 올려야 보이는 정보로 남는다.

이 문제는 저자가 스스로 ECC 절에서 지적한 것과 같은 종류다.
그는 사람들이 총점만 돌려 보고
통계적으로 무의미한 수치를 의미 있게 다룬다고 비판하는데,
이 글 자체가 26개의 총점을 순서대로 배열한 문서다.
“메시지가 지저분한 그래프를 선호한다”는 서술로 이 문제를 다루려 하지만,
지저분한 그래프는 정보를 더 주는 것이지
순위 해석을 막아 주지는 않는다.

### 테스트 기법만 바꾸고 코드 구조는 고정한 설계가 결과의 해석 범위를 좁힌다

이 실험은 프롬프트의 테스트 관련 부가 지시만 바꾸고
구현 방식에 대한 지시는 두지 않았다.
그래서 에이전트가 만든 코드 구조는 조건마다 제각각이며 통제되지 않는다.

HN에서 siscia가 이 설계를 문제 삼았다 —
코드를 테스트하는 방식은 코드를 설계하는 방식과 분리될 수 없고 분리되어서도 안 되며,
효과적인 테스트의 80% 이상은 테스트 프레임워크가 아니라 코드 아키텍처에 있다는 것이다.
저자는 코드가 어떻게 설계되고 관리되는지를 언급하지 않으며,
자신은 에이전트에게 의존성 주입과 헥사고날 아키텍처를 강제하고
간단한 커버리지 검사를 붙이는 것이 꽤 유용했다고 적는다.[^siscia]

이 반론이 실험 설계상 실제 문제인 이유는
관찰된 실패 다수가 테스트가 아니라 구조의 문제로도 읽히기 때문이다.
비트스트림 반전이 테스트에서 잡히지 않은 것은
인코딩 경로와 디코딩 경로가 같은 헬퍼를 공유해
회문 입력에서 대칭이 되어 버렸기 때문일 수 있다.
그렇다면 처방은 “더 나은 테스트”가 아니라 “경로 분리”이며,
그것은 테스트 기법 조건으로는 도달할 수 없는 영역이다.

gz09는 다른 방향의 대안 설계를 제안한다.
Verus, TLA+, Creusot, Lean 코드의 절대량이 비형식 코드에 비해 극히 적으므로
에이전트가 사소한 것만 증명하는 것은 이해할 만하며,
더 흥미로운 실험은 비자명한 시스템에 대해
고수준 명세를 사람이 직접 쓴 뒤
에이전트가 유도된 정제(refinement)로 그 명세를 만족하는 구현을 낼 수 있는지 보는 것이라는 이야기다.[^gz09]
emtel의 실제 Verus 경험이 이 제안을 뒷받침한다 —
에이전트를 그냥 두면 기존 구현을 그대로 재진술하는 명세를 만들지만,
그럴듯하게 정확하고 완전한 명세에 도달하기까지 많은 작업을 한 뒤에는
Claude가 코드가 명세를 만족함을 증명하는 데 아무 어려움이 없었고
그 과정에서 흥미로운 버그 몇 개를 발견했다는 것이다.[^emtel]

### ACL2의 OOM 처리가 결과 전체의 비교 가능성을 흔든다

ACL2 절에는 짧지만 무거운 문장이 있다 —
많은 경우 192GiB 한도에서 OOM이 났고
OOM 결과는 집계되지 않아 결과가 불투명하게 편향됐다는 것이다.
저자는 이것을 인정하고 지나간다.

그런데 이 처리 방식은 ACL2에만 영향을 주지 않는다.
실패한 실행을 제외하고 성공한 실행만 집계하면
그 조건의 점수는 위로 편향되고,
동시에 다른 조건과의 비교가 성립하지 않게 된다.
다른 조건에서 자원 한도로 죽은 실행이 있었는지,
있었다면 어떻게 처리했는지는 글에 없다.

더 중요한 것은 이것이 순위표의 신뢰 구간에 미치는 영향이다.
ACL2는 Default보다 높은 점수를 받았고
저자는 그것이 인과적이고 유의하다면 놀랄 일이라고 적는다.
그 판단은 옳지만, 판단의 근거로 제시되는 것은
“형식적 방법이 정확도에 영향을 주지 않았다”는 정성적 관찰이지
OOM 제외가 만든 편향의 크기 추정이 아니다.
몇 회가 OOM으로 빠졌는지조차 적혀 있지 않다.

### 프롬프트와 실험 설정이 공개되지 않아 재현도 반박도 불가능하다

이 글은 26개 조건의 프롬프트 부가 지시를 이름으로만 제시한다.
“Use test-driven development” 같은 예시가 몇 개 인용될 뿐
전체 프롬프트, 숨겨진 테스트 스위트, 컨테이너 구성, 채점 스크립트는 공개되지 않는다.

Lobste.rs에서도 같은 지적이 나왔다.
Student는 흥미롭기는 하지만 직접 재현하기에는 세부가 충분하지 않다며,
프롬프트 자체는 물론이고 이것이 단발 실행인지 반복 실행인지 알고 싶다고 적었다.[^lo-student]
같은 스레드에서 zg는 반대로 이 글의 미덕을 짚는다 —
저자가 스킬을 최소한으로 쓰기 때문에
모델의 원시 역량을 시험하는 쪽에 더 기울어 있다는 것이며,
자신은 스킬 생태계가 때때로 만병통치약 장사 같다고 느낀다는 것이다.[^lo-zg]

HN에서 gregwebs가 이 점을 정면으로 지적했다 —
훌륭한 작업이지만 재현 가능성의 결여와
제대로 된 SDLC와의 거리가 몹시 답답하다는 것이다.
에이전트가 정확히 어떻게 프롬프트됐는지 어떻게 확인하며,
이 설정을 재현해 자기 AI 구성을 시험해 보려면 어떻게 하느냐,
저장소 링크를 놓친 것이냐고 묻는다.[^gregwebs]
luckydata는 더 직설적으로,
프롬프트와 테스트 설정을 모르는 채로는
이 연습이 본질적으로 아무 가치가 없다고 적었다.[^luckydata]

이 비판은 이 글이 스스로 세운 기준에 비추어 특히 아프다.
저자는 ECC 절에서 사람들이 총점만 돌려 보고
통계적으로 무의미하거나 치명적으로 결함 있는 벤치마크를 그대로 인용한다고 비판한다.
그런데 그 비판의 힘은 남들이 이 글의 방법을 검토할 수 있을 때 나온다.
“에이전트가 실제로 무엇을 했는지 보라”는 것이 이 글의 핵심 방법론인데,
독자는 저자의 관찰 요약만 받고 원자료는 받지 못한다.

vetronauta는 방법론 자체에 대한 구체적 반론도 냈다.
저자가 에이전트에게 시킨 것이 자동 뮤테이션 테스트가 아니라
수동 뮤테이션 테스트로 보이는데,
왜 뮤테이션 테스트 프레임워크를 쓰고
일정 비율의 뮤턴트가 죽지 않으면 빌드 실패로 처리하지 않았느냐는 것이다.
에이전트가 TDD 절차는 무시할 수 있어도 빌드 실패는 무시할 수 없다는 지적이다.[^vetronauta]
이 반론이 옳은지는 실제 설정을 봐야 판정할 수 있는데, 볼 수가 없다.

### 저자 자신의 스킬이 1위를 한 결과에 대한 검토가 가장 얕다

26개 조건 중 최고 점수를 받은 것은 저자가 2분 만에 쓴 스킬이다.
그리고 그 결과에 대한 저자의 검토는
“의도대로 작동하지 않았다”와 “더 다듬어야 한다”에 머문다.

이 결과에는 최소한 두 가지 대안 설명이 필요하다.
하나는 다른 조건들과의 구조적 차이다.
다른 스킬 셋은 외부에서 가져온 것이고
저자의 스킬은 이 평가에서 에이전트가 실제로 저지르는 실패를
이미 관찰한 사람이 쓴 것이다.
저자는 “이전 퍼징 작업에서 에이전트가 자주 빠지는 실패 양상을 봤고
스킬은 그 실패를 막으려는 의도였다”고 직접 밝힌다.
그렇다면 이것은 일반적인 테스트 스킬과
이 평가에 맞춘 스킬을 비교한 것이며,
저자가 ECC 절에서 경계한 과적합이 바로 이 자리에 있다.

다른 하나는 저자 자신이 ECC에 적용한 잣대다.
ECC의 괜찮은 총점이 스킬을 읽지 않은 실행 덕분이라고 분해했듯,
자기 스킬의 1위도 어떤 실행들이 만들어 냈는지를 분해해야 한다.
“새 맥락 항목은 거의 실행되지 않았다”고 적었으므로
다섯 항목 중 하나는 작동하지 않은 것인데,
나머지 넷 중 무엇이 점수를 만들었는지는 분석되지 않는다.
자기 조건에만 노출-반응 분석을 적용하지 않은 것이
이 글에서 방법론적으로 가장 아쉬운 비대칭이다.

## 인사이트

### 기법 이름은 목적을 담지 않으며, 그래서 에이전트에게 전달되지 않는다

이 실험이 반복해서 보여주는 것은
“속성 기반 테스트를 써라”라는 지시가
“proptest를 import하고 proptest! 매크로를 쓴다”로 번역된다는 사실이다.
사람에게는 그 번역이 일어나지 않는다.
사람이 속성 기반 테스트를 배울 때 함께 배우는 것은
“어떤 불변식이 이 코드에서 깨지기 쉬운가”를 묻는 습관이지
매크로 문법이 아니기 때문이다.

기법의 이름은 그 습관을 가리키는 표지일 뿐 습관 자체가 아니다.
사람 사이에서 이름이 작동하는 이유는
그 이름을 듣는 쪽이 이미 목적을 공유하고 있거나
목적을 물어볼 수 있기 때문이다.
모델에게는 이름과 함께 그 이름이 붙은 코드의 통계적 형태가 전달되며,
그 형태를 재현하는 것이 지시를 따르는 것으로 보인다.

이 구조가 시사하는 실무 지침은 저자의 결론과 방향이 같지만 더 구체적이다.
지시는 기법이 아니라 실패 가설로 써야 한다.
“속성 기반 테스트를 써라” 대신
“인코딩과 디코딩에서 비트스트림 순서가 뒤집힐 수 있으니
회문이 아닌 입력으로 왕복 검사를 하라”고 쓰는 것이다.
저자의 스킬이 다른 스킬보다 잘한 이유도 여기 있다 —
다섯 항목 중 셋이 기법이 아니라 실패 양상을 지목한다.

그리고 이것은 스킬로 포장하기 어려운 종류의 지식이다.
실패 가설은 대상에 따라 달라지므로
“일반적인 테스트 스킬”이라는 것이 원리적으로 성립하기 어렵다.
저자가 “테스트되는 대상과 원하는 품질 수준과 무관한
일반적 테스트 워크플로라는 것이 사실 없다”고 적은 것이 그 결론이며,
스킬 생태계가 이 문제를 어떻게 다룰지는 아직 답이 없다.

### 통과한 테스트 수는 이 실험 이후 신뢰 지표에서 완전히 내려와야 한다

이 실험에서 가장 반복적으로 확인된 사실은
에이전트가 자기가 쓴 테스트를 통과시키는 데는 능하다는 것이다.
xhigh와 max에서 거의 모든 조건이 그랬고,
문제는 그 테스트가 무엇을 검사하는지였다.
HN의 filmdilemma가 이것을 한 줄로 요약한다 —
“467/467 테스트 통과”는 잘못된 것을 테스트하고 있다면 별 의미가 없다는 것이다.[^filmdilemma]

이 관찰은 새롭지 않지만 이 실험이 주는 것은 그 실패의 기전이다.
저자가 여러 조건에서 지적하듯,
반복적으로 테스트를 통과시키는 워크플로는
에이전트가 잘못된 동작을 강제하는 테스트를 더 많이 쓰게 만든다.
Rust 내장 프레임워크 조건에서 테스트 수가 두 배가 됐는데
위험 동작의 커버리지도, 잘못된 동작을 인코딩한 실행의 비율도 개선되지 않았다는 것이 그 증거다.
andai가 든 사례가 이 기전의 극단이다 —
에이전트가 아키텍처 변경을 완전히 거꾸로 구현했는데
“모든 테스트 통과”가 나왔고,
그것은 애초에 존재해서는 안 될 것이 제대로 작동함을 증명한 것이었다.
그는 형식 검증도 여기서는 도움이 되지 않았을 것이라며,
그저 존재해서는 안 될 것의 “정확성”에 대한 더 강한 증명이 됐을 뿐이라고 덧붙인다.[^andai]

여기서 나오는 실무적 결론은 지표의 교체다.
테스트 수와 통과율은 에이전트가 스스로 최적화할 수 있는 양이므로
에이전트가 쓴 테스트에 대해서는 신호가 되지 못한다.
신호가 되려면 지표가 에이전트의 통제 밖에 있어야 하고,
그것이 이 실험이 쓴 방식 — 숨겨진 테스트 스위트 — 이다.
vetronauta가 제안한 뮤테이션 프레임워크 기반 빌드 실패도 같은 성질을 갖는다.
에이전트가 무시할 수 없는 외부 판정이 있어야
“테스트를 쓴다”가 “품질을 만든다”로 이어진다.

### 노출-반응 기울기는 스킬 평가의 표준 도구가 되어야 한다

ECC 분석에서 저자가 쓴 방법은 단순하지만 강력하다.
스킬을 읽었는지, 언제 읽었는지로 실행을 나눈 뒤
그 구간별 정확도를 비교한 것이다.
그 결과 총점으로는 보이지 않던 사실이 드러났다 —
스킬에 노출될수록 결과가 나빴고,
총점을 떠받친 것은 스킬을 안 읽은 실행들이었다.

이 방법이 일반적으로 필요한 이유는
스킬이 확률적으로 발동한다는 점 때문이다.
저자가 Hegel 스킬이 160회 중 157회만 쓰였다고 지적하고
“에이전트가 써야 한다고 생각하는 스킬이 있어도
바깥에서는 불투명해 보이는 요인에 따라 쓸 수도 안 쓸 수도 있다”고 적은 대목이 그것이다.
발동 확률이 1이 아니면 총점은
“스킬의 효과”와 “스킬이 발동하지 않은 경우의 기저 성능”의 혼합이며,
발동률이 낮을수록 총점은 기저 성능 쪽으로 끌려간다.

이 혼합은 방향이 정해져 있지 않아서 더 위험하다.
해로운 스킬은 발동률이 낮을수록 총점이 좋아 보이고,
유익한 스킬은 발동률이 낮을수록 총점이 나빠 보인다.
전자의 경우 스킬 제작자는 자기 스킬이 괜찮다고 믿게 되고,
후자의 경우 좋은 스킬이 버려진다.
두 오류 모두 총점만 보면 구별되지 않는다.

그렇다면 스킬을 공개하는 쪽이 보고해야 할 최소 항목이 정해진다 —
평가에서의 발동률, 발동한 경우와 아닌 경우의 점수 분리,
그리고 가능하면 노출 시점별 기울기다.
이것은 임상 시험에서 순응도(adherence)를 보고하는 관행과 정확히 같은 구조이며,
그 관행이 만들어진 이유도 같다.
처방과 복용은 다르고, 효과는 복용에만 걸린다.

### 캐시 적중률 99.85%에도 비용이 늘었다는 사실이 컨텍스트 설계의 비용 모형을 바꾼다

Hegel 스킬 분석에서 가장 반직관적인 수치는 비용 구조다.
2만 토큰짜리 스킬이 시작 시 적재되고 여러 번 다시 읽혔는데,
캐시 적중률이 첫 읽기 이후 99.85%였는데도
달러 비용이 medium 16%, xhigh 18% 늘었고
원시 토큰으로는 medium 90만, xhigh 180만이 추가됐다.

이 수치가 뜻하는 것은 캐시가 비용 문제를 해결하지 않는다는 것이다.
캐시는 토큰당 단가를 낮추지만 토큰 수를 줄이지 않으며,
큰 컨텍스트가 여러 번 다시 읽히면
낮아진 단가 × 큰 횟수가 여전히 무겁다.
그리고 이것은 곱셈 항이 하나 더 있다 —
저자가 지적한 대로 스킬이 구조화된 작업 절차를 지정해
훨씬 많은 일을 하게 만들었고, 그 일이 정확도를 올리지 않았다.

여기서 컨텍스트 설계에 대한 실용적 규칙이 나온다.
프롬프트나 스킬의 비용을 평가할 때
“캐시되니까 괜찮다”는 판단은 틀렸다.
평가해야 할 것은 세 가지의 곱이다 —
크기, 재읽기 횟수, 그리고 그 내용이 유발하는 추가 작업량.
셋째 항이 가장 크고 가장 보이지 않는다.
지시가 늘어나면 에이전트가 하는 일이 늘고,
늘어난 일이 결과를 개선하지 않으면 순손실이다.

이 관점은 “컨텍스트는 공짜에 가까워지고 있다”는 통념과 충돌한다.
단가는 실제로 떨어지고 있지만,
컨텍스트에 들어가는 내용이 행동을 바꾸는 한
컨텍스트 비용은 토큰 비용이 아니라 실행 비용이다.
그리고 실행 비용은 모델이 싸질수록 오히려 더 커진다 —
같은 돈으로 더 많은 단계를 돌리기 때문이다.

### 에이전트가 위험 영역을 식별할 수 있다는 관찰이 이 실험에서 가장 활용되지 않은 발견이다

글 전체가 실패를 보고하는 가운데
저자가 두 번 반복해서 언급하는 성공이 하나 있다 —
위험하거나 미묘한 버그가 있을 만한 영역을 지목하라고 하면
에이전트는 그것을 해낸다는 것이다.
“위험 영역 감사와 퍼징” 조건에서 에이전트는 FSE, 허프만, 비트 리더, 상태에 집중했고
저자는 그 선택이 옳았다고 평가한다.
저자 자신의 스킬에서도 에이전트는 인코딩·디코딩의 비트스트림 반전을
위험 요소로 정확히 짚었다.

그런데 짚고 나서도 그 영역의 테스트에 실패했다.
medium 35번 실행에서 에이전트는 그 위험을 식별하고
독립적 재도출과 감사까지 했는데도 실패했다 —
관련 테스트가 있었지만 입력이 회문이어서
순서를 뒤집어도 같은 결과가 나왔기 때문이다.

이 조합 — 진단은 되는데 처방이 안 되는 것 — 이
이 실험에서 가장 활용 가능한 발견이다.
식별과 검사 설계가 분리 가능한 능력이라면,
파이프라인을 그 경계에서 자를 수 있다.
에이전트에게 위험 영역 목록을 뽑게 하고,
그 목록에 대해서는 사람이 검사 조건을 지정하거나
더 강한 검증 도구를 붙이는 구조다.

저자의 결론 — “합리적인 테스트·분류 구조를 만들어 주면
그 위에 에이전트가 추가하게 하는 것은 잘 된다” — 이
같은 이야기를 다른 각도에서 하고 있다.
구조를 사람이 만들고 내용을 에이전트가 채우는 분업인데,
이 실험은 그 분업선이 정확히 어디여야 하는지에 대한 힌트를 준다.
경계는 “테스트를 쓴다 / 안 쓴다”가 아니라
“무엇이 틀릴 수 있는지 안다 / 그것을 드러내는 입력을 고를 수 있다” 사이에 있다.
후자가 지금 빠져 있는 능력이고,
회문 입력 사례가 그 부재를 가장 선명하게 보여주는 예다.

HN의 실사용 보고들이 이 분업선을 다른 방향에서 지목한다.
Havoc은 계보가 아주 다른 모델을 섞는 감사가 잘 통했다고 적는다 —
주로 GLM5.3으로 코드를 쓰고 Muse 1.3으로 상세한 버그 목록을 만들게 하면
특히 Rust에서 잘 작동하며,
그 목록을 고치는 것은 실수를 만든 원래 모델에 맡겨도 괜찮아 보인다는 것이다.
그는 에이전트가 테스트를 수백 개 쓰기는 하지만
저자와 마찬가지로 그것들을 별로 신뢰하지 않으며 보너스로 여긴다고 덧붙인다.[^havoc]
epsteingpt도 감사가 답이며
Claude 계열이 Codex 계열을 검사하는 식으로
모델 패밀리를 교차시키는 것이 더 낫다고 적는다.[^epsteingpt]
lmeyerov는 2년간 여러 모델·하네스 세대에 걸쳐 투자한 결과
표준 소프트웨어에서는 LLM이
똑똑하게 유도된 퍼징과,
기능 프로토타이핑 이후 맥락을 초기화한 서브에이전트로 돌리는
반복적 병렬 적대 리뷰를 선호한다는 결론에 이르렀다고 전한다.[^lmeyerov]

세 증언의 공통점은 독립성의 확보 방식이다.
저자의 실험에서 Audit 조건이 xhigh 최고 정확도를 냈으면서도
독립 에이전트를 쓴 42회가 오히려 나빴던 것과 대비된다.
저자가 관찰한 실패는 “같은 실수를 감사에서도 반복한다”였는데,
HN 사용자들이 쓰는 방식은 그 반복을 구조적으로 막는다 —
다른 모델 패밀리를 쓰거나 맥락을 초기화한다.
같은 모델이 같은 맥락에서 자기 결과를 감사하면
그것은 독립적 검증이 아니라 같은 사전 확률의 재실행이며,
그 사실이 이 실험의 Audit 결과와 실사용 보고 사이의 차이를 설명한다.
