# Agent-Native: 액션 하나를 UI와 에이전트가 함께 쓰는 프레임워크

<https://agent-native.com/>

<https://github.com/BuilderIO/agent-native>

GN 토론: <https://news.hada.io/topic?id=33920>

## 소개

Builder.io가 만든 오픈소스 TypeScript 프레임워크다.
자율적인 작업과 그 목적에 맞춰 만든 UI를 함께 갖춘 에이전트를 만들기 위한 것이라고 소개한다.

별 4,800개에 포크 458개이고 MIT 라이선스다.

계약이 한 문장으로 정리된다.
각 기능을 **액션(action)으로 한 번만 정의**하면, 에이전트는 그것을 도구로 쓰고 UI는 코드에서 호출한다는 것이다.

왜 에이전트에 UI가 필요한지에 대한 논거도 짧게 제시된다.
코딩 에이전트는 텍스트 상자 하나로 일하지 않으며, 그 환경이 맥락과 도구와 파일과 테스트와 미리보기를 제공해 능력과 결과를 눈에 보이게 만든다는 것이다.
지식 노동에도 같은 종류의 환경이 필요하며, UI가 에이전트가 무엇을 할 수 있는지 보여 주고 사람이 그 작업을 검토하고 편집하고 승인하고 공유할 익숙한 방법을 준다는 논리다.

```bash
npx --yes @agent-native/core@latest create my-agent --standalone --template chat
```

## 동작 방식

공유되는 것이 셋이라고 명시한다.

| 공유 대상         | 내용                                                                      |
| ----------------- | ------------------------------------------------------------------------- |
| 액션              | 에이전트가 도구로 호출하고 UI가 코드에서 호출한다. 같은 검증·권한·구현    |
| 데이터            | 에이전트가 한 작업이 UI에 나타나고, UI에서 한 작업을 에이전트가 쓴다      |
| 애플리케이션 상태 | 현재 페이지, 선택된 레코드, 활성 뷰 같은 관련 UI 상태를 에이전트가 받는다 |

이 설계에서 가장 중요한 문장이 그다음에 온다.

> 에이전트는 UI를 클릭하며 돌아다니지 않는다. UI와 같은 액션 계층을 통해 일한다.

이것이 브라우저 자동화 방식의 에이전트와 갈리는 지점이다.
화면을 보고 요소를 찾아 클릭하는 대신, UI가 쓰는 것과 같은 함수를 호출한다.

### 액션 하나가 여섯 표면을 덮는다

`actions/` 폴더에 두면 프레임워크가 자동으로 발견해 마운트하며 별도 등록이 필요 없다.

```ts
// actions/hello.ts
import { defineAction } from "@agent-native/core/action";
import { z } from "zod";

// 액션 하나가 UI, 에이전트, HTTP, MCP, A2A, CLI 전부를 덮는다.
export default defineAction({
  description: "Return a friendly greeting.",   // 에이전트가 읽는 도구 설명
  schema: z.object({
    name: z.string().default("world").describe("Name to greet"),
  }),
  http: { method: "GET" },                      // HTTP 표면에서의 메서드
  readOnly: true,                               // 변경 없음을 표시
  run: async ({ name }) => {
    return { message: `Hello, ${name}!` };
  },
});
```

| 표면     | 호출 방식                                                                          |
| -------- | ---------------------------------------------------------------------------------- |
| 에이전트 | `hello` 도구로 노출                                                                |
| React UI | `useActionQuery("hello", { name: "Alex" })`, `useActionMutation()`, `callAction()` |
| HTTP     | `/_agent-native/actions/<name>`에 자동 마운트                                      |
| MCP      | Claude, Claude Desktop, Cursor가 발견 가능                                         |
| A2A      | 다른 agent-native 앱이 호출 가능                                                   |
| CLI      | `pnpm action <name>`                                                               |

문서가 이 설계의 요점을 한 줄로 적는다.
UI와 에이전트가 정확히 같은 액션을 호출하므로 구현이 하나뿐이고, 버그가 숨을 곳도 한 군데뿐이라는 것이다.

`description`이 두 역할을 겸한다는 점을 눈여겨볼 만하다.
사람에게는 주석이고 에이전트에게는 도구 설명이다. 즉 이 문자열의 품질이 곧 에이전트의 도구 선택 품질이 된다.

`readOnly`도 단순한 메타데이터가 아니다.
변경이 없는 액션임을 표시하면 승인 흐름이나 재시도 정책을 다르게 가져갈 근거가 된다.

## 포함된 것

프레임워크가 기본 제공한다고 나열한 항목들이다.

| 항목              | 내용                                                         |
| ----------------- | ------------------------------------------------------------ |
| 에이전트 채팅     | 같은 UI에서 작업을 위임하고 질문하고 결과를 검토             |
| 인증과 권한       | 누가 공유 작업에 접근하고 바꿀 수 있는지 통제                |
| 스킬과 메모리     | 재사용 가능한 전문성과 지속되는 맥락                         |
| 자동화            | 일정이나 이벤트로 에이전트 작업 실행                         |
| 에이전트 팀       | 같은 워크스페이스나 연결된 에이전트에게 전문 작업 위임       |
| PostgreSQL 백엔드 | 프로덕션은 PostgreSQL, 로컬 개발은 PGlite. Nitro 호환 호스트 |

LLM과 SQL 데이터베이스와 도구와 인프라를 직접 가져오라고 하며, 만든 것은 전부 사용자 소유로 남는다고 적는다.

오픈소스 예제 앱도 여럿 제공한다.
Clips(회의·화면·음성 메모 기록), Design, Calendar, Mail, Assets, Content, Plans다.

## 트레이드오프

### 액션 계층이 UI와 에이전트를 묶는 대신 표면의 차이를 지운다

“한 번 정의하면 모든 곳에서 쓴다”는 약속이 이 프레임워크의 전부다.
그리고 그 약속이 성립하는 조건이 있다. 여섯 표면이 같은 계약으로 충분히 표현될 때다.

실제로는 표면마다 요구가 다르다.

UI에서 호출하는 함수는 인자가 이미 검증되어 있고 사용자가 화면에서 고른 값이다.
에이전트가 호출하는 도구는 자연어에서 유도된 값이고 틀릴 수 있다.
HTTP 엔드포인트는 외부에서 오며 인증과 속도 제한이 필요하다.
MCP로 노출되면 사용자가 설치한 다른 클라이언트가 호출한다.

같은 `run` 함수가 이 넷을 모두 받으면, 가장 위험한 호출자를 기준으로 방어해야 한다.
그러면 UI 경로에도 불필요한 검증이 붙고, 반대로 UI 기준으로 느슨하게 만들면 MCP 표면이 취약해진다.

프레임워크가 `readOnly`와 권한 체계를 주는 것이 이 문제에 대한 부분적 대응이다.
그러나 “누가 호출했는가”에 따라 동작을 다르게 하려면 결국 `run` 안에서 분기해야 하고, 그 순간 “구현이 하나뿐”이라는 약속이 흐려진다.

### UI를 클릭하지 않는다는 선택이 시나리오 범위를 정한다

에이전트가 액션 계층을 쓰고 UI를 조작하지 않는다는 것은 명확한 설계 결정이고, 얻는 것이 많다.
화면 렌더링을 기다릴 필요가 없고, DOM 구조가 바뀌어도 깨지지 않고, 실패가 예외로 드러난다.

대가는 액션으로 표현되지 않은 것을 에이전트가 할 수 없다는 점이다.

UI에만 있는 동작이 늘 있다. 드래그로 순서 바꾸기, 캔버스에서 위치 옮기기, 여러 항목을 선택해 일괄 처리하기 같은 것들이다.
이런 것들을 에이전트가 하려면 액션으로 다시 표현해야 하고, 그 작업이 UI 개발과 별개의 설계를 요구한다.

그리고 이 경계가 시간이 지나며 어긋난다.
프런트엔드 개발자가 컴포넌트 안에서 상태를 직접 조작하는 기능을 추가하면 그것은 에이전트에게 보이지 않는다.
“액션으로 정의하라”는 규약이 지켜지는지를 강제하는 장치가 없으면, 몇 달 뒤 에이전트가 할 수 있는 일과 UI가 할 수 있는 일이 벌어진다.

역방향 문제도 있다.
에이전트를 위해 만든 세밀한 액션들이 UI에서는 쓸 일이 없어 죽은 코드가 되거나, 반대로 UI 편의를 위한 복합 액션이 에이전트에게는 너무 굵은 도구가 된다.

### 스택을 통째로 받는 대신 선택지를 내준다

이 프레임워크는 인증, 권한, 데이터베이스, 에이전트 런타임, 자동화, 팀 기능을 함께 준다.
빠르게 시작할 수 있다는 뜻이고, 동시에 그 결정들이 이미 내려져 있다는 뜻이다.

명시된 제약이 몇 가지 있다.
React 기반 UI, PostgreSQL(로컬은 PGlite), Nitro 호환 호스팅이다.
LLM은 가져오라고 하지만 에이전트 런타임 자체는 프레임워크의 것이다.

이 묶음이 맞는 조직과 맞지 않는 조직이 갈린다.
새 제품을 처음부터 만든다면 이 결정들이 대부분 합리적이고 직접 고를 이유가 적다.
이미 프런트엔드 스택과 인증 체계와 데이터 계층이 있는 조직이라면, 액션 계층이라는 아이디어만 가져오고 나머지는 쓰지 않는 편이 나을 수 있다.

그런데 그 분리가 쉽지 않다는 것이 문제다.
액션이 프레임워크의 자동 발견과 마운트와 권한 체계에 묶여 있으므로, 액션만 떼어 내려면 사실상 같은 것을 다시 만들게 된다.

## 함정

`description`이 에이전트의 도구 설명이다. 사람 눈에 충분한 설명이 에이전트에게는 부족할 수 있고, 그 차이가 잘못된 도구 선택으로 나타난다.

액션이 MCP로 자동 노출된다. 내부용으로 만든 액션이 사용자가 연결한 외부 클라이언트에 보이는지 확인해야 한다.

`readOnly`를 표시하지 않으면 모든 액션이 변경 가능한 것으로 취급된다. 승인 흐름이 필요 이상으로 무거워진다.

UI에서만 가능한 동작은 에이전트가 할 수 없다. 기능을 추가할 때마다 액션으로 표현할지 결정해야 하고, 그 결정을 미루면 격차가 쌓인다.

에이전트가 받는 애플리케이션 상태에 민감한 정보가 들어갈 수 있다. 현재 선택된 레코드를 그대로 넘기는 편의가 곧 노출 경로다.

A2A로 다른 agent-native 앱이 액션을 호출할 수 있다. 어떤 앱이 연결되어 있고 무엇을 호출할 수 있는지가 권한 설계의 일부다.

`pnpm action <name>`으로 CLI에서도 실행된다. 로컬 개발 편의가 배포 환경에서도 열려 있는지 확인한다.

PGlite와 PostgreSQL의 동작 차이가 로컬과 프로덕션의 차이가 된다. 마이그레이션과 동시성 동작이 특히 그렇다.

## 확인하기

액션 하나를 만들고 여섯 표면이 정말 같은 구현을 쓰는지 확인하는 절차다.

```bash
# 1. 프로젝트를 만든다
npx --yes @agent-native/core@latest create my-agent --standalone --template chat
cd my-agent

# 2. 위의 hello 액션을 actions/hello.ts 로 저장한다

# 3. CLI 로 호출한다
pnpm action hello --name Alex

# 4. HTTP 로 호출한다. 자동 마운트 경로를 그대로 쓴다
curl "http://localhost:3000/_agent-native/actions/hello?name=Alex"

# 5. 에이전트 채팅에서 자연어로 시킨다
#    "Alex 에게 인사해 줘" → hello 도구가 호출되는지 본다

# 6. MCP 로 노출되는지 확인한다
#    Claude Desktop 등에 연결한 뒤 도구 목록에 hello 가 보이는지 본다
```

여기서 실제로 봐야 할 것은 동작이 아니라 **차이**다.

```bash
# 스키마 검증이 모든 표면에서 같은지 확인한다.
# 타입이 맞지 않는 인자를 각 경로로 보내 같은 오류가 나오는지 본다
pnpm action hello --name 123
curl "http://localhost:3000/_agent-native/actions/hello?name[]=a&name[]=b"
```

그리고 노출 범위를 반드시 확인한다.

```bash
# 어떤 액션이 어떤 표면에 노출되는지 전수 확인한다.
# 내부용으로 만든 액션이 HTTP 나 MCP 에 열려 있지 않은지가 핵심이다
curl "http://localhost:3000/_agent-native/actions" | python3 -m json.tool
```

## 체크리스트

- 각 액션의 `description`을 에이전트가 읽는다는 전제로 썼는가
- 변경이 없는 액션에 `readOnly`를 표시했는가
- 어떤 액션이 HTTP와 MCP와 A2A에 노출되는지 전수 확인했는가
- 내부용 액션이 외부 표면에 열려 있지 않은가
- 에이전트에게 전달되는 애플리케이션 상태에 민감 정보가 없는가
- UI에만 있는 동작을 목록으로 관리하고 있는가
- 새 기능을 추가할 때 액션으로 표현할지 결정하는 절차가 있는가
- 스키마 검증이 모든 표면에서 동일하게 동작하는지 확인했는가
- PGlite와 PostgreSQL의 동작 차이를 테스트로 덮었는가
- 프레임워크가 내린 결정(React, PostgreSQL, Nitro)이 조직 제약과 맞는가

## 비평

### “구현이 하나뿐”이라는 약속이 가장 강한 주장이면서 가장 검증이 어렵다

문서의 핵심 문장은 UI와 에이전트가 정확히 같은 액션을 호출하므로 버그가 숨을 곳이 한 군데뿐이라는 것이다.

이 주장이 참인 층위가 분명히 있다.
비즈니스 로직이 한 함수에 있고 스키마가 하나이므로, “UI에서는 되는데 API로는 안 된다”는 흔한 불일치가 구조적으로 사라진다.

그런데 버그가 숨을 곳이 정말 한 군데인지는 다른 문제다.
액션이 여섯 표면에 노출되면 표면마다 다른 호출 패턴과 다른 신뢰 수준이 생기고, 버그는 대개 그 경계에서 난다.
같은 `run`이 UI에서는 늘 유효한 ID를 받고 MCP에서는 임의의 문자열을 받는다면, 그 차이가 드러나는 곳은 `run` 안이 아니라 호출 경로다.

그리고 README가 그 경계를 다루지 않는다.
권한과 인증이 포함되어 있다고만 하고, 표면별로 권한을 다르게 줄 수 있는지, `readOnly`가 어느 표면에서 어떻게 해석되는지는 나오지 않는다.

이것이 큰 결함은 아니다. README의 분량 문제일 수 있다.
다만 이 프레임워크를 평가할 때 가장 먼저 봐야 할 것이 바로 그 부분이라는 점은 분명하다.

### 에이전트가 UI를 쓰지 않는다는 설계가 UI의 존재 이유를 약화시킬 수 있다

이 프레임워크의 출발점은 에이전트에 UI가 필요하다는 주장이다.
코딩 에이전트가 풍부한 환경을 갖는 것처럼 지식 노동 에이전트도 그런 환경이 필요하며, UI가 에이전트의 능력과 결과를 보이게 한다는 것이다.

그런데 동시에 에이전트는 UI를 통해 일하지 않는다고 못 붙인다.

둘을 합치면 UI의 역할이 좁아진다. 에이전트가 하는 일의 **관찰과 승인과 편집**이지 실행이 아니다.

이 좁힘 자체는 합리적이다. 실제로 사람이 필요한 지점이 거기이기 때문이다.
문제는 그렇다면 UI가 왜 액션을 코드에서 호출해야 하는지가 덜 분명해진다는 것이다.

관찰과 승인만 한다면 UI는 데이터를 읽고 상태를 바꾸는 얇은 층이면 되고, 액션을 공유할 필요가 크지 않다.
UI가 액션을 호출해야 하는 경우는 사람이 직접 작업을 실행할 때인데, 그것은 에이전트가 하려던 일을 사람이 대신 하는 상황이다.

그러면 이 프레임워크의 진짜 주장은 “에이전트와 사람이 같은 작업을 할 수 있어야 한다”이고, UI에 대한 논거보다 이쪽이 더 정확하다.
README가 앞의 프레임으로 설명하다 보니 왜 액션을 공유해야 하는지가 흐려진다.

### 예제 앱 목록이 프레임워크의 범위를 애매하게 만든다

Clips, Design, Calendar, Mail, Assets, Content, Plans가 오픈소스 앱으로 제시된다.
회의 기록, 디자인, 일정, 메일, 미디어, 콘텐츠, 기획이다.

이 목록이 두 가지로 읽힌다.

하나는 프레임워크의 범용성을 보이는 예제들이라는 읽기다. 서로 다른 도메인에서 같은 패턴이 통한다는 증거다.

다른 하나는 이것이 사실상 제품군이라는 읽기다.
Builder.io가 이 앱들을 직접 운영하거나 판매할 계획이라면, 프레임워크는 그 제품군의 공통 기반이고 오픈소스는 채택 전략이다.

어느 쪽인지가 중요한 이유는 프레임워크의 수명과 방향을 좌우하기 때문이다.
제품군의 기반이라면 그 제품들이 필요로 하는 기능이 우선되고, 다른 용도는 뒤로 밀린다.

README는 이 질문에 답하지 않는다.
“직접 만들 때의 출발점이나 예시로 쓰라”고만 적혀 있어, 이 앱들이 계속 유지될 예제인지 상용 제품인지가 불분명하다.

## 기억할 원칙

### 에이전트를 붙이는 방식은 세 층 중 어디를 고르느냐의 문제다

에이전트가 기존 소프트웨어와 만나는 지점은 대체로 셋이다.

| 층         | 방식                         | 깨지는 지점             |
| ---------- | ---------------------------- | ----------------------- |
| 화면       | 브라우저 자동화, 컴퓨터 사용 | DOM 변경, 렌더링 타이밍 |
| 인터페이스 | API, MCP, 액션 계층          | 계약 변경, 노출 범위    |
| 데이터     | 데이터베이스 직접 접근       | 불변식 위반, 권한 우회  |

Agent-Native는 두 번째를 고르고 그 계층을 UI와 공유하게 만든다.

층마다 얻는 것과 잃는 것이 정해져 있다.
화면 층은 기존 시스템을 고치지 않아도 되지만 깨지기 쉽고 느리다.
데이터 층은 빠르지만 애플리케이션이 지키던 규칙을 우회한다.
인터페이스 층은 그 둘의 중간이며, 대신 무엇을 노출할지를 **설계**해야 한다.

그래서 이 선택은 기술 취향이 아니라 조직 상황의 문제다.
기존 시스템을 고칠 수 없으면 화면 층 말고 답이 없고, 새로 만든다면 인터페이스 층이 거의 항상 낫다.

그리고 인터페이스 층을 골랐다면 따라오는 일이 하나 있다.
그 인터페이스의 목록을 관리하는 것이다. 무엇이 노출되어 있고 누가 호출할 수 있는지를 아는 것이 이 방식의 유지 비용이며, 그것이 화면 층에는 없던 새 작업이다.

### 같은 함수를 여러 호출자가 쓸 때 계약은 가장 약한 호출자를 기준으로 정해진다

“한 번 정의하고 모든 곳에서 쓴다”는 형태는 반복적으로 매력적이다.
GraphQL 스키마, tRPC 라우터, OpenAPI 명세, 그리고 여기서는 액션이다.

공통된 이득도 분명하다. 타입이 한 곳에 있고, 검증이 한 번 쓰이고, 불일치가 사라진다.

공통된 함정도 같다.
호출자가 늘어날수록 그 함수가 가정할 수 있는 것이 줄어든다.
내부에서만 부르던 함수를 외부에 열면, 인자가 신뢰할 수 없게 되고 오류 메시지가 정보 노출이 되고 호출 빈도가 통제를 벗어난다.

그래서 이런 구조를 쓸 때 물어야 할 질문이 정해진다.
이 함수의 호출자 중 가장 신뢰할 수 없는 쪽이 누구이고, 그 기준으로 작성해도 나머지 호출자에게 부담이 아닌가다.

부담이라면 계층을 나눠야 한다. 내부용 코어와 외부 표면을 분리하고, 표면마다 자기 검증과 권한을 갖게 하는 것이다.
그러면 “구현이 하나뿐”이라는 단순함은 잃지만, 잃은 자리에 명시적인 경계를 얻는다.
그 경계가 없으면 단순함은 유지되고 위험이 조용히 쌓인다.
