# 프롬프트에서 루프까지, 엔지니어링의 대상은 문장에서 사이클로 올라갔다

## 한눈에 보기

먼저 결론을 적는다.
새 용어가 나올 때마다 사람이 손보는 대상이
문장에서 토큰 구성으로, 실행 환경으로, 반복 사이클로 한 층씩 올라갔다.
이 결론은 출처에 적힌 말이 아니라 출처들을 겹쳐 보고
정리하는 쪽이 내린 추론이며, 근거는 아래 표와 본문에 있다.

아래 표는 다섯 개 용어의 등장 시점, 유행 시기,
대상, 장단점을 한 장으로 줄인 것이다.
날짜는 출처에서 확인되는 가장 이른 사례이고, 유행 시기는 지표가 아니라
출처들의 날짜를 보고 추정한 값이다.

| 용어                | 등장 시점                                               | 유행 시기(추정)                                          | 한 줄 특징                                           | 장점                                                           | 단점                                                        |
| ------------------- | ------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------- |
| 프롬프트 엔지니어링 | 2020년 few-shot,[^gpt3] 2022년 11월 이후 확산[^wiki]    | 2023년 절정[^wiki]                                       | 지시문을 다듬는다[^weng]                             | 가중치를 바꾸지 않고 행동을 조정한다[^weng]                    | 모델마다 효과가 달라 실험이 필요하다[^weng]                 |
| 컨텍스트 엔지니어링 | 2025년 6월 말[^willison][^lc-rise]                      | 2025년 6월 이후[^anth-ce]                                | 모델이 보는 토큰 전체를 큐레이션한다[^anth-ce]       | 실패 원인을 나눠 본다[^lc-rise]                                | 길수록 회상이 떨어진다[^anth-ce]                            |
| 하네스 엔지니어링   | 2026년 2월[^mitchell][^openai]                          | 2026년 2월부터 4월[^fowler]                              | 모델 밖의 환경, 규칙, 센서를 설계한다[^fowler]       | 사람이 코드를 쓰지 않고 약 100만 줄을 만들었다는 보고[^openai] | 구축 비용이 크고 일반화가 보장되지 않는다[^openai][^fowler] |
| 루프 엔지니어링     | 2025년 7월 Ralph,[^ralph] 이름은 2026년 6월[^addy-loop] | 2026년 6월부터 8월[^addy-loop][^addy-prac]               | 목표와 검증으로 에이전트를 반복 호출한다[^addy-loop] | 사람이 매 턴 프롬프트하지 않아도 된다[^addy-loop]              | 토큰 비용, 검증 부담, 이해 부채[^addy-loop]                 |
| 그래프 엔지니어링   | 2026년 7월[^bouchard]                                   | 2026년 7월, 글쓴이가 그 주 유행이라 부른 이름[^bouchard] | 루프를 병렬 분기와 핸드오프로 잇는다[^bouchard]      | 한 루프로 모자란 일을 나눈다[^bouchard]                        | 서로 검사해도 헛소리가 나올 수 있다[^bouchard]              |

두 번째 표는 용어끼리 어떻게 겹치는지, 어디서 갈리는지를 보여 준다.

| 용어     | 최적화하는 것              | 한 번의 단위                | 사람의 일                          | 실패했을 때 먼저 의심할 곳                 |
| -------- | -------------------------- | --------------------------- | ---------------------------------- | ------------------------------------------ |
| 프롬프트 | 지시문의 문장              | 모델 호출 한 번             | 지시와 예시를 쓴다                 | 지시가 모호하거나 예시가 나쁘다            |
| 컨텍스트 | 추론 시점의 토큰 구성      | 추론 한 단계                | 무엇을 넣고 뺄지 정한다            | 정보나 도구가 없거나 컨텍스트가 오염되었다 |
| 하네스   | 모델 바깥의 실행 환경      | 세션 하나, 풀 리퀘스트 하나 | 규칙, 도구, 센서를 설계한다        | 같은 실수가 반복된다                       |
| 루프     | 에이전트를 호출하는 사이클 | 여러 세션의 반복            | 목표, 정지 조건, 검증자를 설계한다 | 검증이 약하거나 정지하지 않는다            |
| 그래프   | 여러 루프의 연결           | 여러 에이전트               | 분기, 핸드오프, 거부권을 설계한다  | 외부 증거 없이 서로 동의한다               |

이 두 번째 표는 출처의 정의를 바탕으로 정리한 것이고,
`실패했을 때 먼저 의심할 곳` 열은 출처의 주장이 아니라 정리하는 쪽의 추론이다.

## 읽기 전에

이 문서는 열여섯 개의 출처(블로그 글, 논문, 위키 문서)를 읽고 썼다.
각 용어를 처음 쓴 사람을 가리는 일은 하지 않았고,
출처에서 확인되는 가장 이른 사례를 적었다.
모든 출처가 2026년 10월 20일 이전에 나왔으므로
이 용어들이 이후에도 이어지는지는 알 수 없다.
사실, 출처의 주장, 정리하는 쪽의 추론은 구분해서 적었다.

## 프롬프트 엔지니어링

### 등장

Lilian Weng은 2023년 3월 15일 글에서 프롬프트 엔지니어링을
모델 가중치를 바꾸지 않고 언어 모델의 행동을
원하는 쪽으로 이끄는 방법이라고 정의한다.
그는 이를 경험적 학문이라 부르고, 효과가 모델마다 크게 달라
실험과 휴리스틱이 많이 필요하다고 덧붙인다.[^weng]

기법의 대표 사례는 더 앞선다. 2020년 5월 28일 GPT-3 논문은 언어 모델을
1,750억 개 파라미터 모델로 키우면
예시 몇 개만으로 새 작업을 푸는 few-shot 성능이 크게 좋아진다는 점을 보여
주었다.[^gpt3] 2022년 1월 28일 논문은 chain-of-thought 프롬프트로 5,400억 개
파라미터 모델에 추론 예시 여덟 개를 주었을 때 수학 문제 벤치마크 GSM8K에서
당시 최고 정확도를 냈다고 보고했다.[^cot]
용어와 직무는 2022년 11월 ChatGPT 출시 이후에 퍼졌고,
기업들이 프롬프트 전담 엔지니어를 채용하기 시작했다.[^wiki]
이 용어를 처음 쓴 시점은 확인하지 못했다.

### 유행과 쇠퇴

Wikipedia는 The Wall Street Journal의 2025년 보도를 인용해
프롬프트 엔지니어는 2023년 가장 뜨거운 직무 중 하나였지만
모델이 사용자 의도를 더 잘 짐작하고 기업 내 교육이
생기면서 더는 쓸모가 없어졌다고 적는다.[^wiki]
정리하는 쪽의 해석으로는 직무 이름이 줄어든 것이지 기법이 사라진 것은 아니다.
같은 문서는 few-shot과 chain-of-thought를 대표 기법으로 든다.[^wiki]

Simon Willison은 2025년 6월 27일 글에서
이 용어가 흔히 챗봇에 글자를 입력하는 일을
거창하게 부르는 말로 읽힌다고 진단했다.
그는 사람들이 용어에서 추론하는 정의가 결국 살아남는다고 보았다.[^willison]
이 글은 용어를 바꾸자는 이유를
기술적 한계가 아니라 사람들이 받는 인상에서 찾는다.

### 특징과 장단점

프롬프트 엔지니어링의 단위는 한 번의 입력과 출력이고, 손질하는 대상은 문장이다.
장점은 모델을 학습시키지 않고도 행동이 달라지는 점이며,
chain-of-thought처럼 예시 몇 개로 성능이 크게 오른 사례도 있다.[^weng][^cot]

단점은 두 가지다.
하나는 효과가 모델에 묶여 있어 모델을 바꾸면 다시 실험해야 한다는 점이다.[^weng]
다른 하나는 에이전트가 여러 턴에 걸쳐 오래 일할 때 프롬프트
작성만으로는 관리해야 할 대상을 다 다루지 못한다는 점이다.
Anthropic은 에이전트가 여러 번 추론하며 긴 시간 범위에 걸쳐 일하게 되면서
시스템 지시문, 도구, 외부 데이터,
메시지 이력까지 전체 컨텍스트 상태를 관리하는 전략이 필요해졌다고
설명한다.[^anth-ce]

## 컨텍스트 엔지니어링

### 등장과 유행

2025년 6월 27일 Willison의 글은
컨텍스트 엔지니어링이 프롬프트 엔지니어링의 대안으로 힘을 얻고 있다고 적고,
Shopify CEO Tobi Lütke의 트윗과 Andrej Karpathy의 지지를 인용한다.
Karpathy는 컨텍스트 엔지니어링이 다음 단계에 알맞은 정보로 컨텍스트 창을 채우는
섬세한 기술이자 과학이라고 설명했고, 작업 설명, few-shot 예시, RAG,
다중 모달 데이터, 도구, 상태, 이력, compaction을 그 요소로 들었다.[^willison]

비슷한 시기인 2025년 6월 23일 Harrison Chase(LangChain)는
컨텍스트 엔지니어링을 모델이 과제를 해낼 수 있도록
알맞은 정보와 도구를 알맞은 형식으로 제공하는
동적 시스템을 만드는 일이라고 정의했다.
그는 이 정의가 Lütke, Ankur Goyal, Walden Yan의 최근 견해를 바탕으로 한다고
밝히고, 새로운 아이디어는 아니며
에이전트 개발자들이 한두 해 해 온 일에 이름이 붙은 것이라고
적었다.[^lc-rise] 2025년 9월 29일 Anthropic 응용 AI 팀은 이 용어가 새로 주목받고
있다고 소개하며 프롬프트 엔지니어링의 자연스러운 진전이라고 보았다.[^anth-ce]
유행의 시작은 6월 말이고,
9월에는 Anthropic이 이 용어를 주목받는 개념으로 다뤘다.

### 특징

핵심 차이는 대상이 문장에서 시스템으로 넓어졌다는 점이다.
Anthropic은 컨텍스트 엔지니어링을 프롬프트 밖에서
들어오는 정보까지 포함해 추론 중 모델에 들어가는 토큰 전체를 최적의 구성으로
유지하는 전략이라고 하며,
프롬프트 하나를 쓰는 일과 달리 무엇을 모델에 넘길지
정할 때마다 반복되는 과정이라고 설명한다.[^anth-ce]
Chase는 프롬프트 엔지니어링을 컨텍스트 엔지니어링의 부분집합이라고 본다.
단일한 입력 묶음에 맞춰 프롬프트를 짜는 것이 아니라
동적으로 들어오는 데이터를 알맞게 조립하는 것이 차이라는 설명이다.[^lc-rise]

대표 기법으로 Anthropic은 필요한 순간에 불러오는 검색(just-in-time),
대화를 요약해 새 창에서 이어 가는 compaction,
창 밖에 메모를 남기는 구조화된 노트,
깨끗한 창에서 일하고 요약만 돌려주는 서브에이전트를 든다.[^anth-ce]
LangChain은 단기 메모리와 장기 메모리, 도구 사용, 검색을 예로 든다.[^lc-rise]

### 장단점

Chase가 꼽는 장점은 실패 원인을 나눠 볼 수 있다는 점이다.
정보나 도구가 모자라서 실패했는지,
모두 있는데 모델이 틀렸는지에 따라 고치는 방법이 다르다.[^lc-rise]

단점은 컨텍스트가 유한한 자원이라는 점이다.
Anthropic은 토큰이 늘수록 정보를 정확히 떠올리는 능력이 떨어지는 context rot이
모든 모델에서 나타나며
모델에게 주의 예산(attention budget)이 있다고 설명한다.[^anth-ce]
같은 글은 compaction을 너무 공격적으로 하면
나중에야 중요해지는 미묘한 정보를 잃을 수 있고,
실행 중에 탐색하는 방식은 미리 계산한 데이터를 가져오는 것보다 느리며
도구와 휴리스틱을 신중히 설계해야 한다고 짚는다.[^anth-ce]
또한 모델이 똑똑해질수록 사람이 덜 규정해도 되고,
프롬프트 서식 같은 세부는 점점 덜 중요해질 것이라고 예상한다.[^anth-ce]

## 하네스 엔지니어링

### 등장

`harness`라는 말은 하네스 엔지니어링이라는 이름이 붙기 전에도 쓰였다.
Anthropic의 2025년 11월 26일 글이 확인된 이른 사례로,
이 글은 Claude Agent SDK를 범용 에이전트 하네스라고 부르며
여러 컨텍스트 창에 걸친 장기 작업의 문제를 다뤘다.
각 세션이 이전 기억 없이 시작하기 때문에
첫 세션에서 환경을 세팅하는 초기화 에이전트와
세션마다 조금씩 진행하는 코딩 에이전트로 나누고,
진행 기록 파일과 git 이력, 처음에는 모두 실패로 표시한
200개가 넘는 기능 목록을 남기게 했다.[^anth-harness]

하네스 엔지니어링이라는 이름은 2026년 2월 5일 Mitchell Hashimoto의 글에 나온다.
그는 에이전트가 실수할 때마다 같은 실수를 다시 하지 않도록 해법을 설계하는 일을
이렇게 부르기 시작했다고 적고,
업계에서 받아들여진 용어가 있는지는 모른다고 밝혔다.
해법은 두 형태로, 에이전트용 지침 파일(AGENTS.md)을 고치는 것과
스크린샷이나 필터링된 테스트 같은 실제 도구를 만드는 것이다.[^mitchell]
엿새 뒤인 2026년 2월 11일
OpenAI의 Ryan Lopopolo가 같은 이름으로 글을 냈고,[^openai]
2026년 4월 2일 Birgitta Böckeler(Thoughtworks)가
이를 코딩 에이전트 사용자 관점으로 정리했다.[^fowler]

### 특징

Böckeler는 하네스를 AI 에이전트에서 모델을 뺀 모든 것이라고 소개하고
에이전트는 모델에 하네스를 더한 것이라고 적는다.
사용자가 만드는 바깥 하네스는 두 종류의 통제로 이뤄진다.
에이전트가 행동하기 전에 이끄는 지침(feedforward)과
행동한 뒤 관찰하고 스스로 고치게 하는 센서(feedback)다.
이들은 다시 결정적으로 빠르게 도는 계산형(테스트, 린터, 타입 검사)과
의미를 판단하는 추론형(AI 코드 리뷰)으로 나뉜다.[^fowler]

OpenAI 글은 사람의 일이 코드를 쓰는 데서
환경을 설계하고, 의도를 지정하고, 에이전트가 믿을 만하게 일하도록
피드백 루프를 만드는 쪽으로 옮겨 갔다고 말한다.
그들은 거대한 AGENTS.md가 실패해 약 100줄짜리 목차로 바꾸고,
지식은 저장소 안의 구조화된 docs 디렉터리에 두었다.
계층 구조의 의존 방향은 맞춤 린터와 구조 테스트로 강제했고,
린터의 오류 메시지에 고치는 방법을 넣어 에이전트의 컨텍스트에 주입했다.[^openai]

### 장단점

장점의 근거는 OpenAI의 사례 보고다. 5개월간 직접 쓴 코드 없이 내부 베타 제품을
만들었고 약 100만 줄, 약 1,500개의 풀 리퀘스트,
엔지니어 한 명당 하루 평균 3.5개의 풀 리퀘스트,
사람이 직접 짰을 때의 약 10분의 1 시간이라는 추정을 내놓았다.[^openai]
이 수치는 당사자의 추정이고 독립적으로 검증된 값은 아니다.

단점도 같은 글에 있다.
에이전트가 저장소의 기존 패턴을 그대로 복제해 드리프트가 쌓이고,
팀은 금요일마다 일주일의 20%를 AI가 만든 찌꺼기를 치우는 데 썼다고 한다.
그래서 원칙을 저장소에 넣고 정기적으로 정리하는 에이전트를 돌렸다.
또한 이 구조에 투자하지 않은 저장소에서 같은 자율성이 나온다고
가정해서는 안 된다고 글이 직접 밝힌다.[^openai]
Böckeler는 하네스를 일관되게 유지하는 방법, 센서가 한 번도 울리지 않을 때
그것이 품질이 좋다는 뜻인지 탐지가 부족하다는 뜻인지,
하네스의 범위와 품질을 평가하는 방법이 아직 없다는 점을 열린 질문으로 남겼다.
그는 좋은 하네스가 사람의 개입을 없애기보다 사람의 입력이
가장 중요한 곳으로 향하게 해야 한다고 본다.[^fowler]

## 루프 엔지니어링

### 등장

루프의 원형은 2025년 7월의 Ralph다.
Geoffrey Huntley는 가장 순수한 형태의 Ralph가
프롬프트 파일을 에이전트에 계속 먹이는
bash 루프라고 소개했다.
그는 이 기법에 결함이 있지만 찾아서 고칠 수 있고,
비결정적인 세계에서 결정적으로 나쁜 기법이라고 표현했다.[^ralph]

이름은 2026년 6월 8일 Addy Osmani의 글이 널리 알렸다.
그는 Peter Steinberger가 코딩 에이전트에 더는 프롬프트하지 말고
에이전트에 프롬프트하는 루프를 설계하라고 했고,
Claude Code 책임자 Boris Cherny도 자신은 이제 Claude에 프롬프트하지 않고
루프가 프롬프트하게 하며 자기 일이 루프를
쓰는 것이라고 말했다고 전한다.[^addy-loop]
같은 달 16일 LangChain의 Sydney Runkle은 swyx의 loopcraft(루프를 쌓는 기술)를
인용해 에이전트 루프, 검증 루프, 이벤트 구동 루프,
개선(hill climbing) 루프의 네 단계로 정리했다.[^lc-loop] 8월 14일 후속 글에서
Osmani는 이전에는 손으로 bash 루프를 짰지만
이제 Claude Code와 Codex에 /goal과 /loop 같은 기본 도구가 들어왔다고
적었다.[^addy-prac]

### 특징

Osmani는 루프를 에이전트에 프롬프트하는 사람의
자리를 시스템이 대신하는 것이라고 정의한다.
이 시스템은 일을 찾고, 나눠 주고, 검사하고,
끝난 일을 기록하고, 다음 일을 정한다.
구성 요소는 일정에 따라 도는 자동화,
병렬 작업을 위한 worktree, 프로젝트 지식을 적은 skill,
도구를 잇는 플러그인, 작성자와 검사자를 나누는 서브에이전트이고
대화 밖에 상태를 남기는 메모리 파일이 따른다.[^addy-loop]
그는 루프가 하네스보다 한 층 위에 있다고 설명한다.[^addy-loop]
`/goal`은 조건이 참이 될 때까지 계속하고
별도의 작은 모델이 끝났는지 판정하며,
`/loop`는 정해진 주기로 다시 실행한다.[^addy-loop][^addy-prac]

### 장단점

장점은 사람이 매 턴 프롬프트하지 않아도 일이 진행된다는 점이다.[^addy-loop]
비용도 따른다.
Osmani는 토큰 비용을 조심하라고 하고,
감독 없이 도는 루프는 감독 없이 실수한다는 점,
빨리 쌓이는 코드에 대한 이해가 뒤처지는 이해 부채,
루프가 알아서 하리라 믿고 사람이 자기 의견을 갖지 않게 되는 위험을 짚는다.
그는 직접 리뷰하지 않고 자동 루프에만 기대면
제품 품질이 떨어질 것이라고 인정한다.[^addy-loop]
LangChain은 검증을 추가하면 실행당 지연과 비용이 늘어난다고 적는다.[^lc-loop]

### 그래프 엔지니어링: 루프 다음에 붙은 이름

Louis-François Bouchard는 2026년 7월 22일 글에서
Steinberger의 짧은 트윗이 조회수 260만에 이르렀고
Hamel Husain이 루프 엔지니어링은 죽었고 그래프 엔지니어링이 온다고
받아쳤다고 전하고 둘 다 농담이었다고 정리한다.[^bouchard]
그는 여러 에이전트 루프를 병렬 분기, 검증자, 핸드오프, 정지 조건으로 잇는 일에
그 주 유행한 이름이 붙은 것이 그래프 엔지니어링이라고 보고,
구조 자체는 워크플로 엔진이 십 년 전부터 그려 온 것이라고 지적한다.
달라진 것은 노드가 고정 규칙을 따르는 대신 과제를 해석한다는 점이다.[^bouchard]

주의점은 Carlos Perez의 말로 전해진다.
에이전트가 에이전트를 검사하는 그래프는 조직화된 헛소리를 대규모로 만들 수 있고
같은 모델 스무 개가 같은 결함 있는 컨텍스트를 읽으면 서로 동의한다.
그래서 증거의 일부는 실제로 실행된 테스트나 사람처럼 시스템 밖에서
와야 한다.[^bouchard]

## 차이점과 관계

### 포함 관계에 대한 서로 다른 설명

출처마다 용어의 관계를 다르게 그린다.
Chase는 프롬프트 엔지니어링이
컨텍스트 엔지니어링의 부분집합이라고 한다.[^lc-rise]
Anthropic은 컨텍스트 엔지니어링을
프롬프트 엔지니어링의 자연스러운 진전이라고 본다.[^anth-ce]
Böckeler는 사용자가 코딩 에이전트에 만드는 하네스가
컨텍스트 엔지니어링의 특정한 한 형태라고 적는다.[^fowler]
Osmani는 루프가 하네스보다 한 층 위라고 하고,[^addy-loop]
Bouchard는 그래프가 루프를 포함한다고 말한다.[^bouchard]

여기서 두 가지 해석이 갈린다.
용어를 층으로 쌓으면 하위 층은 상위 층의 일부가 된다.
반대로 Bouchard는 프롬프트에서 컨텍스트, 하네스, 루프로 이어진 이름들이
대체로 같은 뜻을 가리킨다고 본다.[^bouchard]
어느 쪽이 맞는지는 출처가 정하지 못한다.
정리하는 쪽은 대상과 단위가 다르다고 본 두 번째 표의 구분을 따르되,
경계가 겹치는 부분은 출처마다 다르게 그린다는 사실로 적어 둔다.

### 새 이름이 붙은 계기

출처가 설명하는 계기를 이어 보면
하위 층의 한계가 다음 이름을 불렀다는 패턴이 보인다.
이 패턴은 정리하는 쪽의 추론이다.

| 넘어간 지점             | 출처가 말하는 계기                                                                                               |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 프롬프트에서 컨텍스트로 | 에이전트가 여러 턴과 긴 시간 범위로 일하게 되어 시스템 지시문, 도구, 데이터, 이력 전체를 관리해야 했다[^anth-ce] |
| 컨텍스트에서 하네스로   | 코드 처리량이 늘자 병목이 사람의 시간과 주의가 되어, 앱 화면과 로그를 에이전트가 읽을 수 있게 만들었다[^openai]  |
| 하네스에서 루프로       | 루프는 사람이 보지 않는 동안 돌기 때문에 신뢰할 수 있는 검증자가 있어야 자리를 비울 수 있다[^addy-loop]          |
| 루프에서 그래프로       | 루프 하나로는 모자란 복잡한 작업에서 병렬 분기와 검증 구조가 필요해진다[^bouchard]                               |

### 계층이 올라갈수록 커지는 것

층이 올라갈수록 사람이 매 순간 보지 않는 시간이 길어진다.
프롬프트는 한 번의 응답을 보고, 컨텍스트는 한 단계의 입력을 정하고,
하네스는 세션 하나가 지킬 규칙을 정하고, 루프는 여러 세션을 이어 돌린다.
그만큼 틀린 결과가 사람의 눈에 띄지 않고 쌓일 가능성도 커진다.
이는 정리하는 쪽의 추론이며, Osmani가 루프에서
짚는 감독 없는 실수와 이해 부채,[^addy-loop]
Bouchard가 그래프에서 짚는 조직화된 헛소리[^bouchard]와 같은 방향이다.

## 쓰는 법

### 용어보다 실패를 먼저 분류한다

다음은 출처의 주장이 아니라 정리하는 쪽의 제안이다.
어떤 이름을 택할지가 아니라 지금 어떤 실패를 보고 있는지에서 출발한다.

| 보이는 실패                                                         | 먼저 손볼 층                              |
| ------------------------------------------------------------------- | ----------------------------------------- |
| 같은 입력에 응답이 모호하거나 엉뚱하다                              | 프롬프트: 지시와 예시를 다듬는다          |
| 모델이 필요한 정보를 모르거나 도구가 없다, 대화가 길어지며 흐려진다 | 컨텍스트: 정보, 도구, 요약을 손본다       |
| 같은 실수를 사람이 되풀이해서 고친다                                | 하네스: 규칙을 린터나 테스트로 코드화한다 |
| 사람이 매번 다음 일을 시켜야 한다                                   | 루프: 목표, 정지 조건, 검증자를 둔다      |
| 루프 하나로 모자라 병렬 작업이 필요하다                             | 그래프: 분기와 외부 증거를 설계한다       |

위쪽 층으로 올라가는 비용은 크다.
Anthropic은 단순한 것부터 시작하라는 조언이 앞으로도 유효하다고 보고,[^anth-ce]
Bouchard는 반복되는 작업 하나, 진짜 검증자,
들여다볼 수 있는 상태, 강제 정지에서 시작해
일이 요구할 때만 키우라고 한다.[^bouchard]

### 이름이 바뀌어도 남는 것

Bouchard는 시스템의 어느 부분에 확률적인 에이전트를 쓰고 어느 부분을 지루하고
결정적인 코드로 둘지 결정하는 일이 오래 남을 기술이라고 본다.[^bouchard]
다섯 용어를 한꺼번에 놓고 보면 공통 요소가 눈에 띈다.
모델 밖에 상태를 남기고, 모델 밖에서 결과를 검증하며,
사람의 판단이 필요한 곳을 정하는 일이다.
이 공통 요소는 출처가 말한 것이 아니라 정리하는 쪽이 모은 것이며,
모델이 똑똑해질수록 사람이 덜 규정해도
된다는 Anthropic의 예상[^anth-ce]이 맞다면
일부 층은 다시 얇아질 수 있다.
그 여부는 앞으로 나올 모델이
compaction과 외부 메모 없이 장기 작업을 해내는지로 가려진다.
