# GPT Image 2.5 프롬프트 가이드: 바꿀 것과 지킬 것을 나눠 적기

원문: [Image prompting | OpenAI API](https://developers.openai.com/api/docs/guides/image-prompting)

GN 토론: <https://news.hada.io/topic?id=33919>

## 소개

OpenAI의 이미지 생성 모델 프롬프트 가이드다.
모델을 고르고, 효과적인 프롬프트를 쓰고, 편집을 거치면서 디테일을 보존하는 방법을 다룬다.

문서가 제시하는 기본 절차가 한 문단에 있다.
필요한 이미지에서 출발해 대상과 구도와 스타일과 제약을 기술하고, 편집에서는 **무엇이 바뀌어야 하고 무엇이 그대로여야 하는지**를 식별하며, 한 번에 하나씩 다듬고 결과를 확인하라는 것이다.

GPT Image 2.5는 두 모델로 나뉜다.

| 모델                     | 성격       | 품질 기준                        |
| ------------------------ | ---------- | -------------------------------- |
| `gpt-image-2.5-flare`    | 소형, 속도 | GPT Image 2와 비슷한 이미지 품질 |
| `gpt-image-2.5-sunburst` | 기본, 품질 | GPT Image 2보다 높은 이미지 품질 |

둘 다 정밀한 편집과 대상 보존에서 개선이 있다고 적는다.

문서 자체가 유용한 팁을 하나 담고 있다.
문서 URL 뒤에 `.md`를 붙이면 마크다운 버전을 받을 수 있고, 전체 색인은 `llms.txt`에 있다는 것이다.
실제로 이 페이지는 HTML로 받으면 탐색 메뉴가 본문을 덮지만 `.md`로 받으면 내용만 나온다.

## 모델을 고르는 절차

문서가 취향이 아니라 절차로 제시한다.

새 워크플로라면 속도가 우선일 때 Flare로, 까다로운 품질 요구가 우선일 때 Sunburst로 시작한다.
그리고 출력이 요구를 충족하면 지연을 줄일 기회를 찾는다.

기존 워크플로를 옮기는 경우는 현재 이미지 품질을 출발점으로 삼는다.

| 현재 상황                                           | 먼저 시험할 것                                      |
| --------------------------------------------------- | --------------------------------------------------- |
| GPT Image 2 워크플로가 이미 품질 요구를 충족한다    | Flare. 품질을 유지하면서 지연을 줄일 수 있는지 확인 |
| 복잡한 사례에서 GPT Image 2가 품질 요구에 못 미친다 | Sunburst. 먼저 필요한 품질이 나오는지 확정          |

Sunburst가 요구를 충족하면 같은 프롬프트와 입력으로 Flare를 시험하고, Flare도 충족하면서 지연이 개선되면 그쪽으로 옮긴다.
Sunburst의 품질 우위가 그 워크플로에 필요할 때만 Sunburst를 유지한다.

측정에 대한 경고가 붙어 있다.
자기 워크로드에서 응답 시간과 품질을 재야 하며, 결과가 프롬프트와 참조 이미지와 출력 크기와 품질 설정에 달려 있으므로 한 워크로드에서의 속도 개선이 다른 워크로드의 고정된 개선을 뜻하지 않는다는 것이다.

## 파라미터

프롬프트와 API 파라미터를 분리해서 설정하라고 명시한다.

| 파라미터     | 값                                                    |
| ------------ | ----------------------------------------------------- |
| `model`      | `gpt-image-2.5-flare` 또는 `gpt-image-2.5-sunburst`   |
| `quality`    | `auto`(기본), `low`, `medium`, `high`, `xhigh`, `max` |
| `size`       | `auto` 또는 커스텀 해상도                             |
| `background` | `auto`, `opaque`, `transparent`                       |

흔히 쓰는 크기로 `1024x1024`, `1536x1024`, `1024x1536`, `2048x2048`, `2048x1152`, `3840x2160`, `2160x3840`을 든다.

커스텀 해상도의 제약이 넷이다.

```text
각 변은 3,840픽셀 이하
두 변 모두 16픽셀의 배수
긴 변 대 짧은 변의 비율이 3:1을 넘지 않을 것
총 픽셀 수가 655,360 이상 8,294,400 이하
```

총 픽셀 수가 3,686,400(`2560x1440`)을 넘는 출력은 실험적이라고 적는다.

`quality` 튜닝 순서도 정해져 있다.
먼저 위의 절차로 모델을 고르고, 첫 비교에서는 두 모델이 모두 지원하는 품질 설정을 명시적으로 고정한 채 프롬프트와 참조 이미지와 출력 크기도 그대로 둔다.
그리고 중요한 단서가 붙는다. **같은 품질 라벨이 모델 간에 같은 이미지 품질이나 응답 시간을 뜻하지 않는다**는 것이다.

출력이 모자라면 더 높은 설정을 시험하고, 요구를 충족하면 더 낮은 설정으로 내려가며 허용 가능한 품질을 유지하면서 지연이 주는지 본다.
`xhigh`나 `max`는 지연 예산 안에서 충족되지 않은 품질 요구를 개선할 때만 쓴다.
더 높은 설정이 모든 프롬프트에서 더 나은 결과를 보장하지 않는다고 못 붙인다.

투명 배경은 `background="transparent"`를 명시적으로 요청하고 PNG나 WebP를 쓴다.
그리고 디코딩한 이미지의 알파 채널을 머리카락과 유리와 그림자와 물체 가장자리까지 확인하라고 한다.
`output_compression`은 JPEG나 WebP에만 쓰고 PNG에는 쓰지 않는다.

## 프롬프트의 여덟 가지 기본

문서가 번호를 매겨 정리한 원칙이다.

| # | 원칙                          | 핵심                                                           |
| - | ----------------------------- | -------------------------------------------------------------- |
| 1 | 결과를 정의한다               | 대상과 용도를 이름 붙이고 구도·종횡비·배치 제약을 지정         |
| 2 | 유지보수 가능한 형식을 고른다 | 짧은 프롬프트, 서술 문단, JSON 유사 구조, 지시문, 태그 중 택일 |
| 3 | 보이는 디테일을 기술한다      | 재질, 조명, 색, 시각 매체를 이름 붙인다                        |
| 4 | 사람과 동작을 지정한다        | 신체 프레이밍, 상대적 크기, 시선, 사물과의 상호작용            |
| 5 | 정확한 텍스트를 지정한다      | 필요한 문구를 따옴표로 묶고 위치와 타이포그래피를 기술         |
| 6 | 변경과 제약을 분리한다        | “X만 바꿔라”와 보존할 디테일 목록                              |
| 7 | 참조에 역할을 부여한다        | 입력마다 번호와 용도를 식별한다                                |
| 8 | 의도적으로 반복한다           | 이전 출력을 다음 편집 입력으로 넘기고 한 번에 하나만 바꾼다    |

몇 가지는 부연이 필요하다.

2번의 요지는 특별한 문법에 기대지 말라는 것이다.
여러 형식이 같은 의도를 표현할 수 있으므로, 요구사항을 읽고 고치기 가장 쉬운 형식을 고르라는 것이다.

3번에는 중요한 단서가 붙는다.
사실적인 사진을 원하면 “photorealistic”이나 “real photograph”를 명시적으로 요청해야 하고, **카메라 사양은 외양에 대한 단서이지 정확한 물리 시뮬레이션의 보장이 아니다**.
넓거나 영화적이거나 저조도이거나 비 오거나 네온인 장면에서는 분위기를 나타내는 단어에만 기대지 말고 규모와 대기와 색을 지정하라고 한다.

5번은 이 가이드에서 가장 구체적이다.
필요한 문구를 따옴표로 묶고, 위치와 타이포그래피를 기술하고, 특이한 단어나 브랜드명은 필요하면 한 글자씩 철자를 적어 주고, 추가 텍스트를 넣지 말라고 요청한 다음 출력에서 철자와 가독성을 확인한다.
작은 글자나 밀도 높은 정보나 여러 폰트가 있으면 `medium`과 `high`를 비교하라고 한다.

## 편집: 바꿀 것과 지킬 것을 나눠 적기

이 가이드의 중심 기법이다. 생성보다 편집에서 훨씬 중요하다.

패턴이 단순하다. 바꿀 것을 한 문장으로 말하고, 지킬 것을 목록으로 나열한다.

의류 교체 예시가 그 구조를 잘 보여 준다.
사람의 얼굴, 이목구비, 피부톤, 체형, 자세, 정체성을 바꾸지 말라고 열거하고, 닮음과 표정과 머리 모양과 비율을 보존하라고 하고, 옷만 교체하되 기존 자세와 신체 구조에 자연스럽게 맞추라고 한다.
그리고 조명과 그림자와 색온도를 원본에 맞춰 붙여 놓은 것처럼 보이지 않게 하고, 배경과 카메라 각도와 프레이밍과 이미지 품질을 바꾸지 말고, 액세서리나 텍스트나 로고나 워터마크를 추가하지 말라고 한다.

같은 패턴이 제품에도 적용된다고 문서가 명시한다. 제품이나 물체가 알아볼 수 있게 남아야 하는 편집이다.

번역 편집은 더 짧다.
인포그래픽의 텍스트를 다른 언어로 바꾸되 이미지의 다른 어떤 측면도 바꾸지 말라고 하고, 번역과 함께 원래 언어로 남은 단어가 있는지 확인하라고 한다.

참조 이미지를 여럿 쓸 때는 번호로 역할을 부여한다.
어느 이미지의 무엇을 어디로 옮길지와 무엇이 그대로여야 하는지를 지정하는 방식이다.

스케치를 사실적 이미지로 바꾸는 작업에는 별도의 조언이 있다.
프롬프트를 명세서처럼 다루라는 것이다. 레이아웃과 비율과 원근을 보존한 뒤 그럴듯한 재질과 조명과 환경을 지정해 사실감을 **더하고**, 창의적 재해석을 막기 위해 “새 요소나 텍스트를 추가하지 마라”를 넣는다.

투명 배경 컷아웃에는 경고가 하나 더 붙는다.
프롬프트에서 분리된 대상을 요청하고 API에서 `background="transparent"`를 설정하며, PNG나 WebP를 쓰고 반환된 알파 채널을 보존하고 PNG에는 `output_compression`을 생략한다.
그리고 **그려진 체커보드는 투명이 아니다**. 이후 편집에서는 투명 배경 보존 요구를 다시 적어야 한다.

## 여러 턴에 걸쳐 다듬기

출력 하나로 시작해 검사하고 그것을 다음 입력으로 쓴다.
각 후속 요청을 좁게 유지해야 어떤 변경이 도움이 되었는지 알 수 있다는 것이다.

문서의 예시 흐름이 이렇다.

```text
1단계  제품 사진 → 빌보드 목업 생성
       "Fresh and clean" 을 정확히 한 번, 굵은 산세리프, 중앙 정렬로

2단계  1단계 출력을 입력으로 → "겨울 저녁에 눈이 내리는 것처럼 만들어 줘"
```

2단계 프롬프트가 한 문장뿐이라는 점이 요점이다. 조건을 하나만 바꾼다.

캐릭터 일관성은 별도의 패턴으로 다룬다.
여러 삽화가 있는 책이라면 재사용 가능한 캐릭터 참조를 만들어 장면과 자세와 페이지에 걸쳐 외양을 보존하게 한다.
환경과 이야기를 바꾸되 캐릭터를 정의하는 디테일을 반복해서 적는 방식이다.

그리고 이 절 전체에 걸린 경고가 문서 앞쪽에 있다.
반복된 편집이 보존하려던 디테일을 여전히 바꿀 수 있으며, 그 제약을 다시 적고 각 결과를 검사해야 한다는 것이다.
결정적인 문장이 그다음이다.

> 어떤 영역이 픽셀 단위로 동일해야 한다면, 프롬프트에 기대지 말고 승인된 편집을 원본 이미지에 합성하라.

## 마이그레이션 절차

기존 워크플로를 옮기는 여섯 단계를 문서가 제시한다.

| 단계 | 내용                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------- |
| 1    | 기준선 저장. 대표 프롬프트와 참조 이미지, 어려운 편집, 정확한 텍스트, 얼굴, 제품 기하, 투명 자산 포함 |
| 2    | 첫 후보 선택. 프롬프트·참조·크기·출력 형식을 그대로 둔 채 비교                                        |
| 3    | 전체 결과 확인. 지시 준수, 정체성·제품 보존, 텍스트 정확도, 원치 않은 변경, 투명도                    |
| 4    | 품질이 통과한 뒤 지연 이득을 시험                                                                     |
| 5    | 설정을 하나씩 조정. 프롬프트를 고쳐 쓰기 전에 품질 수준을 먼저 비교                                   |
| 6    | 워크플로 단위로 점진 배포. 이전 모델을 롤백용으로 유지                                                |

3단계에 중요한 항목이 있다. **요청을 반복해 일관성을 측정**하고, 편집 워크플로라면 개별 단계만이 아니라 편집의 전체 순서를 시험하라는 것이다.

5단계에는 비용에 대한 단서가 붙는다.
일반적 응답과 느린 응답, 실패, 재시도, 그리고 **수용된 이미지당 비용**을 측정하며, 더 빠른 모델이 더 싸다고 가정하지 말고 현재 가격을 확인하라는 것이다.

## 결과 확인하기

문서가 제시하는 검수 항목이다.

- 필요한 텍스트가 정확하고 읽을 수 있는가. 다이어그램 라벨과 관계가 맞는가
- 정체성, 제품 형태, 라벨, 참조 디테일이 온전한가
- 편집이 요청한 것만 바꿨는가
- 투명도가 필요하다면 파일에 알파 채널이 있는가, 칠해진 배경이 아니라

프롬프트나 모델을 바꿀 때는 대표 입력에서 품질과 지연과 비용을 비교하라고 한다.

이 목록을 자동화할 수 있는 부분이 있다. 투명도 확인이 그렇다.

```bash
# 알파 채널이 실제로 있는지 확인한다.
# "체커보드가 그려진 불투명 PNG"를 걸러 내는 검사다.
python3 - "$IMG" <<'PY'
import sys
from PIL import Image
im = Image.open(sys.argv[1])
print("mode:", im.mode)
if im.mode not in ("RGBA", "LA"):
    print("FAIL: 알파 채널이 없다"); sys.exit(1)
alpha = im.getchannel("A")
lo, hi = alpha.getextrema()
# 모든 픽셀이 불투명하면 투명 배경 요청이 반영되지 않은 것이다
print("alpha range:", lo, hi)
sys.exit(0 if lo < 255 else 1)
PY
```

텍스트 검수도 부분 자동화할 수 있다.

```bash
# 요청한 문구가 정확히 한 번 나타나는지 OCR 로 1차 확인한다.
# 최종 판단은 사람이 하되, 명백한 오타와 중복을 먼저 걸러 낸다.
tesseract "$IMG" - 2>/dev/null | grep -o "Fresh and clean" | wc -l
```

## 트레이드오프

### 품질 라벨이 모델 간에 같은 것을 뜻하지 않는다는 사실이 비교를 어렵게 만든다

문서가 이 점을 명시한다. 같은 품질 라벨이 모델 간에 같은 이미지 품질이나 응답 시간을 뜻하지 않는다는 것이다.

정직한 서술이지만 실무에는 부담이다.
모델을 바꿀 때 `quality="high"`를 그대로 두는 것이 공정한 비교인지 아닌지가 불분명해진다.

문서가 제시하는 절차는 첫 비교에서 설정을 고정하라는 것인데, 그것은 “같은 설정”의 비교이지 “같은 품질”의 비교가 아니다.
Flare의 `high`가 Sunburst의 `medium` 수준이라면, 설정을 고정한 비교는 Sunburst에 유리하게 기울어 있다.

그래서 실제로 필요한 비교는 다른 형태다.
각 모델에서 자기 품질 요구를 **간신히 충족하는 최저 설정**을 찾고, 그 지점에서의 지연과 비용을 비교하는 것이다.
문서의 절차가 결국 이것을 향하지만(먼저 품질을 확정하고 그다음 내려가며 시험한다), 그 순서를 지키지 않고 같은 라벨끼리 재면 잘못된 결론에 닿는다.

### 반복 편집이 보존을 보장하지 못한다는 것이 이 도구의 근본 한계다

문서가 이 한계를 두 번 적는다.
반복된 편집이 보존하려던 디테일을 여전히 바꿀 수 있다는 것과, 픽셀 단위로 동일해야 하는 영역은 합성하라는 것이다.

이것이 왜 근본적인지는 생성 모델의 성질에서 나온다.
편집이 마스크 기반이 아닌 한 모델은 이미지 전체를 다시 만들며, “바꾸지 마라”는 지시는 재생성의 방향을 편향시킬 뿐 그 영역을 건드리지 않게 만들지 않는다.

그래서 보존 요구의 강도에 따라 도구가 갈린다.

| 보존 요구            | 적절한 방법                   |
| -------------------- | ----------------------------- |
| 대체로 비슷하면 된다 | 프롬프트에 보존 목록을 적는다 |
| 특정 영역만 바꾼다   | 마스크 편집                   |
| 픽셀 단위로 동일해야 | 승인된 편집을 원본에 합성     |

문서가 마스크 편집을 별도 가이드로 링크만 하고 넘어가는데, 실무에서 가장 많이 필요한 것이 이 중간 단계다.
제품 사진에서 배경만 바꾸거나 라벨만 교체하는 작업이 전부 여기 속한다.

그리고 합성으로 가면 이미 이미지 편집 파이프라인을 별도로 갖춰야 한다는 뜻이다.
즉 이 모델이 워크플로 전체를 대체하는 것이 아니라 그 안의 한 단계라는 것이 문서의 실질적 결론이다.

### 프롬프트 형식의 자유가 재현성과 맞바꿔진다

두 번째 원칙이 형식을 자유롭게 고르라고 한다. 짧은 프롬프트, 서술 문단, JSON 유사 구조, 지시문, 태그가 모두 같은 의도를 표현할 수 있다는 것이다.

이 조언이 맞는 층위가 있다. 특별한 문법에 대한 미신을 걷어 내기 때문이다.

그런데 유지보수 관점에서는 형식이 중립적이지 않다.
긴 서술 문단은 읽기 좋지만 무엇이 요구사항이고 무엇이 분위기 묘사인지 구분되지 않고, 그래서 diff로 리뷰하기 어렵다.
JSON 유사 구조나 라벨이 붙은 섹션은 장황하지만 항목별로 바꾸고 되돌릴 수 있다.

문서 자신의 예시들이 이 차이를 보여 준다.
정확한 텍스트나 투명 배경처럼 검수 가능한 요구가 있는 프롬프트는 전부 항목이 줄바꿈으로 나뉘어 있고, 분위기가 중요한 사진 프롬프트는 문단이다.

실무 규칙은 여기서 나온다. **검수 항목이 될 요구는 한 줄씩 적는다.**
나중에 결과가 요구를 충족하지 못했을 때 어느 줄이 지켜지지 않았는지를 가리킬 수 있어야 하고, 문단 안에 묻힌 요구는 그것이 안 된다.

## 함정

같은 `quality` 라벨이 모델 간에 같은 품질이 아니다. 라벨을 고정한 비교는 공정한 비교가 아니다.

더 높은 품질 설정이 모든 프롬프트에서 더 나은 결과를 주지 않는다. 문서가 명시한다.

더 빠른 모델이 더 싸다고 가정하면 안 된다. 문서가 현재 가격을 확인하라고 못 붙인다.

그려진 체커보드는 투명이 아니다. 알파 채널을 직접 확인해야 한다.

PNG에 `output_compression`을 쓰면 안 된다.

커스텀 해상도에 네 가지 제약이 동시에 걸린다. 16의 배수라는 조건을 특히 놓치기 쉽다.

`2560x1440`을 넘는 출력은 실험적이다.

카메라 사양은 외양 단서이지 물리 시뮬레이션이 아니다. `50mm`라고 적는다고 그 렌즈의 왜곡이 재현되지는 않는다.

편집을 반복하면 보존하려던 것이 바뀐다. 매 턴 제약을 다시 적어야 한다.

투명 배경은 이후 편집마다 다시 요청해야 한다.

번역 편집 후 원래 언어로 남은 단어가 있는지 확인해야 한다.

## 확인하기

모델을 고르는 절차를 재현 가능한 실험으로 만들면 이렇게 된다.

```bash
# 1. 기준선을 고정한다. 대표 프롬프트와 입력을 파일로 둔다
mkdir -p baseline && cat > baseline/prompt.txt <<'TXT'
(대표 프롬프트)
TXT

# 2. 같은 설정으로 두 모델을 각각 N회 호출해 일관성을 본다.
#    1회 비교는 의미가 없다. 문서도 반복해서 재라고 한다
for model in gpt-image-2.5-flare gpt-image-2.5-sunburst; do
  for i in 1 2 3 4 5; do
    curl -s https://api.openai.com/v1/images/generations \
      -H "Authorization: Bearer $OPENAI_API_KEY" \
      -H "Content-Type: application/json" \
      -w '\n%{time_total}\n' \
      -d "{\"model\":\"$model\",\"quality\":\"medium\",\"size\":\"1024x1536\",\"prompt\":$(python3 -c 'import json,sys;print(json.dumps(open("baseline/prompt.txt").read()))')}" \
      > "out/${model}-${i}.json"
  done
done

# 3. 수용 가능한 결과의 비율과 그때의 지연을 함께 센다.
#    분모가 호출 수이고 분자가 사람이 통과시킨 수다
```

3번이 이 절차의 핵심이다.
평균 지연이 아니라 **수용된 이미지당 비용과 시간**을 봐야 하며, 재시도가 잦은 모델은 호출이 빨라도 총비용이 더 든다.
문서의 5단계가 정확히 이것을 요구한다.

편집 워크플로라면 단계별이 아니라 전체 시퀀스를 재야 한다.

```bash
# 편집을 3턴 이어 붙인 뒤 1턴 결과와 3턴 결과에서
# 보존하기로 한 영역이 얼마나 달라졌는지를 수치로 본다
python3 - <<'PY'
from PIL import Image, ImageChops
a = Image.open("turn1.png").convert("RGB")
b = Image.open("turn3.png").convert("RGB")
# 보존 영역만 잘라 비교한다. 좌표는 워크플로마다 정한다
box = (100, 100, 500, 500)
diff = ImageChops.difference(a.crop(box), b.crop(box))
print("bbox of change:", diff.getbbox())
PY
```

## 체크리스트

- 모델 선택을 절차로 돌렸는가(품질 확정 → 지연 시험 순서)
- 첫 비교에서 프롬프트·참조·크기·출력 형식을 고정했는가
- 같은 품질 라벨을 같은 품질로 취급하고 있지 않은가
- 각 모델에서 요구를 충족하는 최저 설정을 찾았는가
- 같은 요청을 반복해 일관성을 측정했는가
- 편집 워크플로라면 전체 시퀀스를 시험했는가
- 수용된 이미지당 비용과 시간을 측정했는가(재시도 포함)
- 편집 프롬프트에 바꿀 것과 지킬 것이 분리되어 있는가
- 픽셀 단위 동일성이 필요한 영역을 합성으로 처리하고 있는가
- 정확한 텍스트를 따옴표로 묶고 출현 횟수를 지정했는가
- 투명 배경이 필요하면 알파 채널을 실제로 검사했는가
- PNG에 `output_compression`을 쓰고 있지 않은가
- 커스텀 해상도가 네 제약을 모두 만족하는가
- 롤백을 위해 이전 모델을 남겨 두었는가

## 기억할 원칙

### 생성 모델의 편집에서 “바꾸지 마라”는 보장이 아니라 편향이다

이 가이드의 기법 대부분이 보존 목록을 길게 쓰는 것으로 수렴한다.
얼굴, 체형, 자세, 배경, 카메라 각도, 조명, 라벨을 바꾸지 말라고 열거하는 식이다.

그 기법이 효과가 있다는 것은 문서의 예시가 보여 준다.
그러나 왜 효과가 있는지를 알면 한계도 보인다. 그 문장들은 재생성의 분포를 원본 쪽으로 기울이는 것이지, 해당 픽셀을 잠그는 것이 아니다.

그래서 이 부류의 도구를 쓸 때 물어야 할 질문이 정해진다.
이 영역이 **조금 달라져도 되는가**다.

조금 달라져도 되면 프롬프트로 충분하고, 안 되면 도구가 바뀌어야 한다.
마스크든 합성이든, 보장이 필요한 곳에는 결정론적 연산을 써야 한다.

이 구분이 이미지에만 있는 것이 아니다.
LLM에게 “이 부분은 그대로 두고 고쳐 줘”라고 하는 것도 같은 성질이고, 그래서 코드 편집에서 전체 재생성보다 패치 적용이 안전하다.
확률적 생성기에 보존을 맡기는 순간, 보존은 요구가 아니라 선호가 된다.

### 검수 가능한 요구는 검수 가능한 형태로 적어야 한다

이 가이드가 반복적으로 권하는 것이 정확한 텍스트를 따옴표로 묶고, 출현 횟수를 지정하고, 보존 항목을 열거하고, 금지 항목을 명시하는 것이다.

이 권고들의 공통점은 **결과를 보고 지켜졌는지 판정할 수 있다**는 점이다.
“세련되게”는 판정할 수 없고 “태그라인이 정확히 한 번 나타난다”는 판정할 수 있다.

그리고 판정 가능한 요구만이 자동 검수로 넘어갈 수 있다.
텍스트 출현은 OCR로, 투명도는 알파 채널로, 크기는 메타데이터로, 보존 영역은 픽셀 차이로 확인할 수 있다.

그래서 프롬프트를 쓰는 작업이 사실 두 가지를 동시에 하는 일이 된다.
모델에게 무엇을 만들지 말하는 것과, 자기에게 무엇을 확인할지 말하는 것이다.
후자를 염두에 두고 쓰면 프롬프트의 각 줄이 나중에 테스트 케이스가 되고, 염두에 두지 않으면 결과가 마음에 드는지 아닌지만 남는다.

이 원칙이 프롬프트를 자산으로 만드는 조건이기도 하다.
검수 항목이 붙은 프롬프트는 모델이 바뀌어도 그대로 재사용해 회귀를 잡을 수 있고, 분위기만 적힌 프롬프트는 모델이 바뀔 때마다 처음부터 다시 다듬어야 한다.
