# Codex Security

<https://github.com/openai/codex-security>

HN 토론: <https://news.ycombinator.com/item?id=49089755> (356점, 106개 댓글)

## 소개

Codex Security는 OpenAI가 공개한 CLI 도구이자 TypeScript SDK로, 코드베이스에서
보안 취약점을 찾고 검증하고 수정하는 데 사용한다.
저장소를 스캔하고, 변경 사항(diff)을 리뷰하고, 발견된 이슈를 시간에 따라
추적하고, CI 파이프라인 안에서 보안 점검을 실행할 수 있다.
패키지명은 `@openai/codex-security`이며 Apache-2.0 라이선스로 배포된다.

실행하려면 Node.js 22 이상, Python 3.10 이상, 그리고 Codex Security 서비스
접근 권한이 필요하다.
인증은 ChatGPT 로그인과 API 키 두 가지 방식을 모두 지원하며, 대화형 스캔에서
두 인증 수단이 모두 사용 가능하면 어느 쪽을 쓸지 사용자에게 묻는다.
반면 CI처럼 비대화형 환경에서는 기존 API 키 우선순위를 그대로 유지한다.

## 사용법

```bash
npm install @openai/codex-security
npx codex-security login
npx codex-security scan .
```

CI 환경에서는 로그인 대신 `OPENAI_API_KEY` 환경 변수를 설정한다.
인증 수단을 명시적으로 지정하려면 다음과 같이 `--auth` 플래그를 쓴다.

```bash
npx codex-security scan . --auth chatgpt
npx codex-security scan . --auth api-key
```

ChatGPT 로그인을 기본 인증 수단으로 쓰고 싶다면 설정된 API 키를 해제하면
된다.

```bash
unset OPENAI_API_KEY CODEX_API_KEY
```

스캔 이력은 Codex Security 워크벤치 상태 디렉터리에 저장된다.
해당 디렉터리에 쓰기 권한이 없다면 `CODEX_SECURITY_STATE_DIR` 환경 변수로
저장소 바깥의 쓰기 가능한 디렉터리를 지정할 수 있다.

TypeScript SDK를 사용하면 스캔을 코드에서 직접 호출할 수 있다.

```typescript
import { CodexSecurity } from "@openai/codex-security";

const security = new CodexSecurity();
const result = await security.run(".");

console.log(result.reportPath);
```

## 분석

### CLI와 SDK를 함께 제공하는 것은 침투 지점을 이원화하는 전략이다

Codex Security는 CLI와 TypeScript SDK를 동시에 제공하는데, 이는 단순한
편의 기능이 아니라 두 가지 서로 다른 채택 경로를 동시에 겨냥한 설계다.
CLI는 개발자가 로컬에서 즉시 실행해 보는 진입점이고, SDK는 이미 구축된
CI/CD 파이프라인이나 사내 도구에 프로그래밍적으로 통합하는 진입점이다.
보안 도구가 개발자 워크플로에 실제로 정착하려면 “한 번 써보는 것”과
“자동화에 편입되는 것” 사이의 문턱을 모두 낮춰야 하는데, 이 도구는 그
두 문턱을 각각 다른 인터페이스로 낮추고 있다.

### 이중 인증 구조는 개인 사용자와 조직 워크플로를 동시에 겨냥한다

ChatGPT 로그인과 API 키를 모두 지원하면서 우선순위를 상황에 따라 다르게
가져가는 설계는, 이 도구가 두 종류의 사용자를 동시에 노리고 있다는 것을
보여준다. 개인 개발자는 이미 보유한 ChatGPT 계정으로 마찰 없이 로그인하고,
조직의 CI 시스템은 API 키 기반의 예측 가능한 인증을 그대로 사용한다.
대화형 환경에서는 사용자에게 선택권을 주고 비대화형 환경에서는 기존
관행을 존중하는 방식은, OpenAI가 소비자용 제품과 엔터프라이즈용 인프라
도구 사이의 경계를 흐리며 확장하고 있는 더 큰 흐름과 맞닿아 있다.

### 상태 디렉터리를 저장소 바깥으로 옮길 수 있게 한 이유

스캔 이력을 저장하는 위치를 환경 변수로 재지정할 수 있게 만든 것은
사소해 보이지만, 실제로는 CI 환경의 읽기 전용 파일시스템이나 컨테이너화된
빌드 환경을 염두에 둔 설계다. 많은 CI 러너가 체크아웃한 저장소 디렉터리를
매 실행마다 새로 만들거나 쓰기 권한을 제한하는데, 상태를 저장소 밖에 둘 수
있어야만 스캔 이력이 여러 실행에 걸쳐 누적될 수 있다. 이는 이 도구가
일회성 로컬 스캔 툴이 아니라 지속적인 보안 모니터링 도구로 설계됐다는
신호다.

### 실제 가치는 스캐너가 아니라 스킬 정의와 하니스에 있다

HN 스레드에서 여러 참여자가 지적한 것처럼, 이 저장소를 뜯어보면 핵심
가치는 탐지 알고리즘 자체가 아니라 LLM에게 "어떻게 점검할지"를 지시하는
영어로 작성된 스킬(skill) 정의에 있다는 것이 드러난다[^varenc].
이 스킬 정의는 저장소의 `sdk/typescript/_bundled_plugin/skills` 경로에
공개되어 있으며, OpenAI가 다양한 프롬프트를 실험할 수 있는 컴퓨팅
자원을 가진 만큼 상당히 다듬어진 결과물일 가능성이 높다는 평도
나왔다[^petesergeant]. 이는 곧 이 CLI의 본질이 새로운 탐지 엔진이
아니라, 기존 모델 위에 얹은 정교한 프롬프트 엔지니어링과 오케스트레이션
계층이라는 뜻이다. 실제로 한 참여자는 스캐너 자체는 이 제품에서
가장 흥미롭지 않은 부분이며, 여러 실행에 걸친 중복 제거, 오탐 추적,
예산 통제, CI 게이팅 같은 "하니스" 계층이야말로 앞으로 혁신이 집중될
지점이라고 진단했다[^knighthacker]. 이는 앞서 CI 게이팅 정책의 공백을
지적한 비평과 정확히 같은 결을 공유하는 관찰이다.

## 비평

### 서비스 의존성이 이 CLI를 진정한 오픈소스 도구와 구분한다

저장소는 Apache-2.0 라이선스로 공개되어 있지만, 실제 스캔 기능은 “Codex
Security 서비스 접근 권한”을 전제로 한다.
즉 클라이언트 코드는 공개되어 있어도 실질적인 탐지 로직이나 취약점
데이터베이스는 OpenAI가 운영하는 백엔드에 있을 가능성이 높다.
이는 오픈소스 라이선스가 주는 인상 — 누구나 자유롭게 가져다 자체
호스팅하거나 수정해 쓸 수 있다는 기대 — 과 실제 사용 조건 사이에 간극을
만든다. README만 보고는 이 도구가 셀프 호스팅 가능한 스캐너인지, 아니면
OpenAI API에 의존하는 클라이언트에 불과한지 명확히 판단하기 어렵다.
실제로 코드를 ChatGPT나 OpenAI 인프라로 업로드해 분석하는 구조인지,
사내 프로젝트에도 허용되는 방식인지를 묻는 질문이 스레드에서 여러 차례
제기됐고[^petilon], 코드가 클라우드로 전송된다는 점을 경계해야 한다는
반응도 나왔다[^halfax]. 한 참여자는 AI 기업이 만드는 보안 도구를 두고
"방화범이 운영하는 소방서" 같다고 표현하며, 유용하긴 해도 이 화재로부터
누가 이득을 보는지 의식하지 않을 수 없다고 꼬집었다[^luciana1u].

### CI 통합 예시가 구체적인 실패 처리 방식을 제시하지 않는다

README는 CI 파이프라인에서 `OPENAI_API_KEY`를 설정해 스캔을 실행하는
방법을 보여주지만, 스캔에서 취약점이 발견됐을 때 CI가 어떻게 실패
처리해야 하는지, 종료 코드나 심각도 등급에 따른 게이팅 정책을 어떻게
설정하는지는 다루지 않는다.
보안 스캐너가 CI에 통합될 때 실제로 마찰이 발생하는 지점은 “스캔을
실행하는 방법”이 아니라 “발견된 이슈를 어떤 기준으로 빌드를 막을지
정하는 방법”인데, 문서화된 예시 수준에서는 이 부분이 비어 있다.

### 실제 사용 경험은 예측 불가능한 실행 시간과 비용을 드러낸다

한 사용자는 작은 저장소에 대해 스캔을 실행했더니 거의 한 시간 동안
실행되다 중단됐고, Pro 플랜의 주간 사용량 절반을 소진했다고
보고했다[^gregwebs]. 실행 로그를 보면 최대 8개의 워커 슬롯을 병렬로
위임하는 구조인데도 52분이 지난 시점에 "스캔 도중 저장소 HEAD가
변경되어 결과를 저장할 수 없다"는 오류로 실패했다. 이는 README가
제시하는 `npx codex-security scan .`이라는 단순한 명령 뒤에, 실제로는
예측하기 어려운 실행 시간과 상당한 추론 비용이 숨어 있다는 것을
보여준다. 앞서 지적한 CI 게이팅 정책의 공백과 겹쳐 보면, 이 도구를
매 PR마다 자동 실행하는 CI 파이프라인에 무비판적으로 통합할 경우
비용과 실행 시간이 통제 불가능한 수준으로 불어날 위험이 있다.

## 인사이트

### 보안 스캐닝의 AI 벤더 종속이 새로운 형태의 공급망 리스크를 만든다

Codex Security가 스캔 로직 상당 부분을 클라우드 서비스에 의존한다면,
이는 조직의 보안 점검 파이프라인이 OpenAI의 서비스 가용성과 정책
변경에 종속된다는 뜻이다. 전통적인 정적 분석 도구(예: Semgrep, CodeQL)는
로컬에서 완결적으로 실행할 수 있었지만, LLM 기반 보안 스캐너는 구조적으로
외부 추론 서비스를 필요로 한다. 이는 보안 도구 체인에 새로운 종류의
공급망 의존성 — 코드가 아니라 추론 서비스에 대한 의존성 — 을 도입하는
것이며, 향후 이 서비스의 요금 정책이나 가용성이 바뀌면 조직의 보안
프로세스 자체가 영향을 받는 구조적 취약점이 될 수 있다.

### CI 게이팅 정책의 공백은 결국 오탐 처리 관행을 흉내 내게 될 것이다

정적 분석 도구 업계는 지난 수십 년간 오탐(false positive) 처리 문제와
씨름해왔고, 그 결과 억제 주석(suppression comment), 기준선(baseline)
파일, 심각도 등급별 게이팅 같은 관행이 표준으로 자리 잡았다.
Codex Security의 현재 문서가 이런 정책을 아직 구체화하지 않았다는 것은
이 도구가 아직 초기 단계에 있다는 뜻이지만, 결국 LLM 기반 스캐너 역시
동일한 오탐 문제에 부딪힐 수밖에 없다. 오히려 LLM 특유의 비결정적
판단 방식 때문에 동일한 코드에 대해 스캔마다 다른 결과가 나올 가능성이
있고, 이는 전통적인 정적 분석기보다 더 정교한 억제·기준선 메커니즘을
요구하게 될 가능성이 높다.

### 스캔 이력 추적 기능은 보안 점검을 시점이 아니라 궤적으로 재정의한다

발견된 취약점을 시간에 따라 추적하는 기능은 보안 점검을 “지금 이
코드가 안전한가”라는 단발성 질문에서 “이 코드베이스의 보안 상태가
개선되고 있는가”라는 궤적의 질문으로 전환시킨다. 이는 개별 커밋
단위의 게이팅보다 팀의 보안 성숙도를 추적하는 조직 차원의 지표로
확장될 가능성을 시사한다. 다만 이런 궤적 기반 지표는 측정 방식이
바뀌거나(예: 새로운 취약점 카테고리 추가) 스캐너 버전이 바뀌면 추세선이
왜곡될 위험이 있으며, 이는 코드 커버리지 지표가 오랫동안 겪어온 것과
동일한 함정이다.

### 이 도구는 기존 보안 스캐너 시장을 대체하기보다 재배치할 가능성이 높다

HN 코멘트 중에는 이런 도구가 Snyk 같은 기존 보안 스캐너 업체를 시장에서
밀어낼지 궁금해하는 반응이 있었다[^game_the0ry]. 그러나 앞서 분석한
것처럼 Codex Security의 핵심 가치가 탐지 알고리즘이 아니라 LLM에게
지시를 내리는 스킬 정의와 그 위의 오케스트레이션 하니스에 있다면, 이
도구가 대체하는 것은 전통적인 정적 분석 엔진이 아니라 그 결과를
해석하고 우선순위를 매기는 인간 분석가의 초기 트리아지 작업에
가깝다. 실제로 Alibaba가 거의 같은 시기에 유사한 오픈소스 코드
리뷰 도구를 공개한 것도[^moehm] 이 흐름이 특정 기업의 전략이 아니라
업계 전반에서 동시다발적으로 일어나는 재배치라는 것을 시사한다.
기존 스캐너 업체들은 사라지기보다 자신의 규칙 엔진과 취약점
데이터베이스를 LLM 오케스트레이션 계층 아래의 한 구성 요소로
재배치하는 방향으로 적응할 가능성이 높다. 이는 클라우드 컴퓨팅이
등장했을 때 온프레미스 인프라 업체들이 사라지지 않고 클라우드
위의 관리형 서비스로 재편됐던 패턴과 유사하다.
