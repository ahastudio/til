# Inferno: 런타임 성능만을 목표로 11년을 버틴 React 계열 라이브러리

<https://infernojs.org/>

<https://github.com/infernojs/inferno>

HN 토론: <https://news.ycombinator.com/item?id=13089258> (197점, 128개 댓글)

## 소개

클라이언트와 서버 양쪽에서 고성능 사용자 인터페이스를 만드는,
빠른 React 계열 라이브러리다.
프로젝트의 주 목표는 웹 애플리케이션에
가능한 최고의 **런타임** 성능을 제공하는 것이라고 README가 명시한다.
실시간 데이터 뷰나 큰 DOM 트리를 렌더링하는 데 특히 강하다고 밝힌다.

2015년 2월 1일에 만들어졌고 스타 16,455개, 포크 640개, 열린 이슈 40개다.
JavaScript로 작성되었고 MIT 라이선스이며 마지막 푸시는 2026년 8월 19일이다.
11년 넘게 유지되고 있다.

같은 저자가 만든 [Octane](octane.md)이 이제 스스로를 Inferno의 후속작이라고
소개한다는 점이 지금 이 저장소를 읽을 때의 맥락이다.

## 성능을 얻는 방법

README가 최적화를 구체적으로 열거한다.

첫째, 자체 JSX 컴파일러가 `createElement` 호출 대신
단형(monomorphic) `createVNode` 호출을 만든다.
SWC용 플러그인, Babel용 플러그인, TSC용 플러그인이 각각 제공되며
TSX와 JSX를 컴파일한다.

둘째, diff 과정이 비트 플래그로 객체의 모양을 메모화한다.

셋째, 자식 노드 정규화를 필요할 때만 한다.

넷째, 특별한 JSX 플래그로
애플리케이션 수준에서 런타임 성능을 컴파일 타임에최적화할 수 있다.

다섯째, 수많은 미세 최적화가 있다.

첫 번째 항목이 이 라이브러리의 설계 철학을 담고 있다.
컴파일 타임 최적화는 JSX에서만 가능하다고 못 붙여 두었다.
hyperscript나 `createElement`를 쓸 수도 있지만 그 경로에는 최적화가 없다.

## React와 다른 점

기능 목록에서 Inferno가 스스로 내세우는 차이는 이렇다.

| 항목                            | 내용                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------- |
| 부분 합성 이벤트 시스템         | 전면 재구현이 아니라 브라우저 호환을 위해 필요한 만큼만 정규화한다              |
| `linkEvent`                     | 화살표 함수나 콜백 바인딩 없이 이벤트에 데이터를 붙인다                         |
| 함수 컴포넌트의 생명주기 이벤트 | React와 Preact에는 없다                                                         |
| 제어 컴포넌트                   | Preact와 다른 React 계열 라이브러리와 달리 input·select·textarea를 제어한다     |
| `defaultHooks`                  | 함수 컴포넌트마다 생명주기를 다시 정의하지 않아도 된다                          |
| 문자열 스타일                   | `style="background-color: red"`를 그대로 쓴다. camelCase는 `inferno-compat`에서 |
| 폴리필 없는 구형 브라우저 지원  | 버전 4부터 폴리필 없이 테스트 스위트를 돌린다                                   |
| 애니메이션 콜백                 | v8의 `componentDidAppear`, `componentWillDisappear`, `componentWillMove`        |

`linkEvent`와 함수 컴포넌트 생명주기,
제어 컴포넌트가 이 라이브러리가 성능 외에도 내세우는 세 가지다.
그리고 문자열 스타일을 기본으로 둔 결정이 흥미롭다.
React가 객체 리터럴만 받는 것과 반대이며,
브라우저가 원래 받는 형식을 그대로 쓰겠다는 뜻이다.

## 쓰는 방법

```jsx
import { render } from 'inferno';

const message = "Hello world";

render(
  <MyComponent message={message} />,
  document.getElementById("app")
);
```

클래스 컴포넌트가 React와 같은 모양으로 있다.

```jsx
import { render, Component } from 'inferno';

class MyComponent extends Component {
  constructor(props) {
    super(props);
    this.state = { counter: 0 };
  }
  render() {
    return (
      <div>
        <h1>Header!</h1>
        <span>Counter is at: {this.state.counter}</span>
      </div>
    );
  }
}

render(<MyComponent />, document.getElementById("app"));
```

## ChildFlags로 정규화를 건너뛰기

이 라이브러리에서 가장 특징적인 최적화가 ChildFlags다. 개발자가 자식 노드의 모양을 컴파일 타임에 미리 선언하는 기능이다.

```jsx
import { render, Component } from 'inferno';

class MyComponent extends Component {
  constructor(props) {
    super(props);
    this.state = { counter: 0 };
  }

  _getText() {
    return 'Hello!';
  }

  render() {
    // span은 내용이 항상 텍스트뿐이므로 $HasTextChildren이 맞는다
    const node = this.state.counter > 0
      ? <div>0</div>
      : <span $HasTextChildren>{this._getText()}</span>;

    return (
      <div>
        <h1>Header!</h1>
        {/* node가 단일 요소 또는 컴포넌트 vNode뿐임을 컴파일러에 알린다 */}
        <div $HasVNodeChildren>{node}</div>
      </div>
    );
  }
}

render(<MyComponent />, document.getElementById("app"));
```

README의 설명이 이 기능의 성격을 정확히 밝힌다.
JavaScript의 동적 성질 때문에 `node` 변수는 무엇이든 될 수 있으므로, Inferno는 중첩 배열이나 잘못된 데이터가 없는지 확인하는 정규화 과정을 거쳐야 한다.
`$HasVNodeChildren`을 붙이면 런타임 정규화를 건너뛰고, 객체의 모양과 데이터의 정확성에 대한 개발자의 판단을 신뢰한다.

그리고 대가도 함께 적어 두었다. 이 계약이 지켜지지 않고 `node`가 선언한 모양에 맞지 않는 값(예컨대 `null`)을 담으면 애플리케이션이 런타임에 크래시한다.

## 정리하기

애플리케이션을 해제하려면 루트 요소에 `null`을 렌더링한다.

```jsx
import { render } from 'inferno';

const rootElement = document.getElementById("app");

render(<ExampleComponent />, rootElement);

// 해제: 전체 vDOM 트리의 언마운트 생명주기를 호출하고 전역 리스너를 제거한다
render(null, rootElement);
```

쓰지 않는 vNode 트리를 언마운트해 브라우저 메모리를 돌려주는 것이 중요하다고 README가 강조한다.
이 안내가 명시적으로 있는 것 자체가 이 라이브러리의 대상이 어디인지를 알려 준다. 페이지 전체를 한 번 렌더링하고 끝나는 앱이 아니라, 긴 시간 동안 뷰를 붙이고 떼는 앱이다.

## 실행 환경 요구사항

Inferno v9는 런타임에 다음 기능이 있어야 한다.

- `Promise`
- `String.prototype.includes()`
- `String.prototype.startsWith()`
- `Array.prototype.includes()`
- `Object.spread()`
- `for ... of`

버전 4부터 폴리필 없이 테스트 스위트를 돌리며, Saucelabs 오픈소스 프로그램을 통해 테스트를 실행한다.
그리고 테스트 프레임워크의 브라우저 지원이 제한적이라서 표에 없는 구형 브라우저에서도 잘 돌 수 있다고 덧붙인다.

## 트레이드오프

### 성능을 단일 목표로 삼은 것

주 목표가 가능한 최고의 런타임 성능이라고 첫 문단에 적어 둔 라이브러리는 드물다. 대개 개발 경험이나 생태계, 유연성을 함께 내세운다.

이 단일성이 주는 것은 결정의 일관성이다.
합성 이벤트를 부분만 구현한 것, 문자열 스타일을 기본으로 둔 것, hyperscript 경로에는 최적화를 주지 않은 것, ChildFlags로 안전 검사를 개발자에게 넘긴 것이 모두 같은 기준에서 나왔다.
그 기준이 명시되어 있으므로 각 결정을 따로 변호할 필요가 없다.

대가는 그 목표가 시장에서 차지하는 비중이다.
런타임 렌더링 성능이 병목인 애플리케이션은 존재하지만 다수가 아니다. 대부분의 앱에서 체감 성능을 정하는 것은 번들 크기와 네트워크, 초기 렌더링 시점이다.
그래서 이 라이브러리는 맞는 자리에서는 대안이 없고, 맞지 않는 자리에서는 React를 버릴 이유를 주지 못한다.

여기서 빠져나갈 길이 좁다. 목표를 넓히면 일관성이 사라지고, 좁게 두면 대상이 좁게 남는다.
11년 동안 스타 16,455개라는 숫자가 그 좁음의 크기를 보여 준다. 꾸준하지만 폭발하지 않았다.

### ChildFlags가 성능과 안전을 교환한다

`$HasVNodeChildren`을 붙이면 정규화를 건너뛰어 빨라지고, 선언이 틀리면 런타임에 크래시한다.
README가 이 위험을 숨기지 않고 `null`이라는 구체적인 예까지 들어 적어 둔 것은 좋다.

문제는 이 계약이 정적으로 검증되지 않는다는 점이다.
`$HasTextChildren`을 붙인 자리에 나중에 조건부 렌더링이 들어가면 타입 검사도 린터도 잡지 못하고, 그 분기가 실제로 실행될 때 비로소 터진다.
그리고 그 분기는 드물게 실행되는 쪽일 가능성이 높다. 흔한 경로였다면 개발 중에 발견되기 때문이다.

그래서 이 기능은 성능 측정으로 필요가 확인된 지점에만 붙이는 것이 맞고, 그러려면 어디가 정규화 비용을 쓰는지 먼저 재야 한다.
전역적으로 붙이는 것은 성능을 위해 프로덕션 크래시 가능성을 사는 거래이며, 이 라이브러리를 쓰는 앱이 실시간 데이터 뷰라면 그 크래시가 가장 나쁜 때에 일어난다.

### JSX만 최적화되는 구조

hyperscript와 `createElement` 경로를 제공하지만 컴파일 타임 최적화는 JSX에서만 된다고 명시한다.

이 선택은 합리적이다. 최적화의 근거가 컴파일 타임에 코드 모양을 아는 것이므로, 런타임에 함수를 호출해 노드를 만드는 경로에서는 같은 일을 할 수 없다.

대가는 선택지가 실질적으로 하나라는 것이다.
JSX를 쓰지 않으면 이 라이브러리를 쓸 이유의 대부분이 사라지고, 그렇다면 다른 경로를 제공하는 것이 무슨 뜻인지가 애매해진다.
호환을 위한 통로로는 값이 있지만, 그 통로로 들어온 코드는 이 라이브러리의 이점을 받지 못한다는 사실이 문서에 한 줄로만 적혀 있다.

### 11년째 유지되는 라이브러리의 이주 부담

마이그레이션 가이드가 v4와 v6용으로 두 개 있다. v9까지 왔으므로 주요 버전이 아홉 번 바뀌었다는 뜻이다.

오래 유지된다는 것은 채택에 유리한 사실이다. 2015년에 시작해 2026년에도 푸시가 있는 프런트엔드 라이브러리는 많지 않다.

그런데 가이드가 두 개뿐이라는 점이 함께 읽힌다. v7과 v8, v9의 이주 안내가 README에서 링크되지 않는다.
변경이 작아서일 수도 있고 문서가 다른 곳에 있을 수도 있지만, 버전을 올리려는 사람에게는 확인이 필요한 공백이다.

## 함정

ChildFlags 선언이 틀리면 런타임 크래시가 난다. 정적 검사로 잡히지 않으므로 선언을 바꿀 때 해당 자리의 모든 분기를 확인해야 한다.

컴파일 타임 최적화가 JSX 전용이다. hyperscript나 `createElement`로 쓰면 이 라이브러리의 이점이 대부분 사라진다.

스타일이 문자열 기반이다. React 코드를 옮길 때 camelCase 객체 리터럴을 쓰려면 `inferno-compat`이 필요하다.

애플리케이션을 떼어낼 때 루트에 `null`을 렌더링해야 한다. 잊으면 전역 이벤트 리스너와 vDOM 트리가 남는다.

v9는 `Object.spread()`를 비롯한 최신 기능을 요구한다. 폴리필 없이 구형 브라우저를 지원한다는 말은 v4 이후 테스트 정책을 뜻하며, v9의 요구사항 목록과 함께 읽어야 한다.

JSX 컴파일러가 세 종류(SWC·Babel·TSC 플러그인)이므로 빌드 도구에 맞는 것을 골라야 하고, 각 플러그인의 지원 범위가 다르다. SWC와 TSC 플러그인은 TSX와 JSX를, Babel 플러그인은 JSX를 컴파일한다고 적혀 있다.

v7 이후의 마이그레이션 가이드가 README에서 링크되지 않는다.

## 확인하기

이 라이브러리의 주장은 벤치마크로 검증되도록 만들어져 있고, README가 그 목록을 직접 준다.

| 벤치마크                    | 확인하는 것                    |
| --------------------------- | ------------------------------ |
| UI Bench                    | 다양한 갱신 패턴의 렌더링 성능 |
| dbmonster                   | 고빈도 실시간 데이터 뷰 갱신   |
| JS Web Frameworks Benchmark | 프레임워크 간 표준 비교        |
| Isomorphic-UI-Benchmark     | 서버 렌더링 포함 동형 성능     |
| 1k Components               | 대량 컴포넌트 트리             |

dbmonster와 1k Components가 이 라이브러리가 겨냥하는 워크로드에 가장 가깝다. 자기 앱이 그 모양이 아니라면 다른 벤치마크의 순위는 채택 근거가 되기 어렵다.

ChildFlags의 효과를 직접 재려면 같은 컴포넌트를 플래그 유무로 두 벌 만들어 갱신 빈도를 올려 보는 것이 가장 단순하다.
차이가 측정되지 않는다면 그 자리에는 붙일 이유가 없고, 앞서 본 크래시 위험만 남는다.

## 체크리스트

- 렌더링 성능이 실제 병목인지 측정으로 확인했는가
- JSX를 쓰는가, 그리고 빌드 도구에 맞는 컴파일러 플러그인이 있는가
- ChildFlags를 붙인 자리의 모든 분기가 선언한 모양을 지키는가
- 애플리케이션 해제 시 루트에 `null`을 렌더링하는가
- v9의 런타임 요구사항을 대상 브라우저가 만족하는가
- React 스타일 객체 리터럴이 필요하면 `inferno-compat`을 반영했는가
- 후속작인 [Octane](octane.md)과 이 라이브러리 중 어느 쪽을 쓸지 정했는가

## 비평

### 후속작이 발표된 라이브러리를 새로 채택하기는 어렵다

[Octane](octane.md)이 스스로를 Inferno의 후속작이라고 소개하고, 같은 저자가 만들었다.
그러면서 Inferno는 여전히 푸시가 있고 이슈가 열려 있다.

이 상태가 채택 결정을 어렵게 만든다.
지금 Inferno를 새로 고르는 것은 후속작이 있는 줄 알면서 고르는 일이고, 그렇다면 언제까지 유지될지를 물어야 한다.
반대로 Octane을 고르는 것은 베타를 고르는 일이다.

README가 이 물음에 답하지 않는다. Octane에 대한 언급이 없고, 유지보수 계획이나 지원 기간에 대한 진술도 없다.
Octane의 README는 Inferno를 후속 관계로 명시하지만, Inferno의 README는 그 관계를 인정하지 않는 비대칭이 있다.

이것이 사소한 문서 문제가 아닌 이유는 11년치 코드베이스를 가진 사용자가 존재하기 때문이다.
그들에게 필요한 것은 이주 경로이거나 계속 쓸 수 있다는 약속이고, 지금은 둘 다 없다.

### 성능 주장이 벤치마크 링크로 대체되어 있다

README는 최적화 기법을 다섯 가지 열거하고 벤치마크 다섯 개를 링크한다. 그런데 숫자는 하나도 없다.

링크로 미루는 것이 정직한 방식일 수는 있다. 벤치마크 결과는 버전과 환경에 따라 바뀌므로 README에 적으면 낡기 때문이다.

그러나 그 결과로 이 라이브러리가 얼마나 빠른지가 문서만 읽어서는 알 수 없다.
insanely fast라는 표현이 첫 문단에 있고 구체적인 수치는 없으며, 확인은 독자가 외부 사이트에서 해야 한다.
그리고 그 외부 사이트 중 일부는 이 프로젝트가 직접 호스팅하는 데모다.

더 아쉬운 것은 최적화 기법과 측정 결과가 연결되지 않는다는 점이다.
비트 플래그 메모화가 얼마를 벌어 주는지, 정규화 생략이 얼마를 벌어 주는지가 없으므로, ChildFlags처럼 위험을 감수하는 기능의 값을 판단할 근거가 문서에 없다.
그 판단을 하려면 앞서 말한 대로 사용자가 직접 재야 한다.

### React 계열이라는 위치가 약점이 되는 구간

React 계열 API를 쓴다는 것은 학습 비용을 없애지만, 동시에 비교 기준을 React로 고정한다.

지난 11년 동안 React는 훅과 서버 컴포넌트, 컴파일러로 옮겨 갔다.
이 저장소의 예제는 여전히 `class MyComponent extends Component`와 `this.state`다. 함수 컴포넌트의 생명주기를 지원한다고 기능 목록에 적혀 있지만, 훅에 대한 언급은 README에 없다.

그렇다면 이 라이브러리가 호환하는 React는 2015년부터 2018년 사이의 React에 가깝다.
그 시기의 코드베이스를 유지하는 곳에는 여전히 맞는 선택이고, 지금 새로 시작하는 곳에는 익숙한 API가 아니다.

이 관찰이 Octane이 왜 별도 프로젝트로 시작되었는지를 설명한다. 훅 기반 API로 옮기는 일은 호환 유지가 아니라 재설계였기 때문이다.
그러니 Inferno의 위치는 나빠진 것이 아니라 고정된 것이며, 고정된 위치의 크기가 얼마인지가 이 프로젝트의 수명을 정한다.

## 기억할 원칙

### 안전 검사를 끄는 기능은 측정이 먼저이고 문서가 함께 가야 한다

ChildFlags는 프레임워크가 개발자에게 안전 검사를 끌 권한을 주는 기능이고, 이런 기능은 드물지 않다.
`unsafe` 블록, 경계 검사 생략, 타입 단언, `as any`가 모두 같은 성격이다.

이 저장소가 잘한 것은 대가를 명시한 것이다. 계약이 깨지면 런타임 크래시가 난다고 적고 `null`이라는 구체적인 예를 들었다.
잘하지 못한 것은 이득을 명시하지 않은 것이다. 정규화를 건너뛰어 얼마를 버는지가 없으므로, 독자가 거래의 한쪽만 알고 결정하게 된다.

여기서 나오는 규칙은 두 가지다.
안전 검사를 끄는 옵션을 제공할 때는 그것이 버는 양을 함께 문서화해야 한다. 그러지 않으면 사용자는 위험만 알고 이득은 짐작하게 되며, 그 짐작은 대개 과대평가다.
그리고 그런 옵션은 기본이 아니어야 한다. Inferno가 플래그를 명시적으로 붙이게 만든 것은 옳은 설계다.

쓰는 쪽의 규칙도 같은 모양이다. 검사를 끄기 전에 그 검사가 실제로 비용을 쓰고 있는지를 측정하고, 끈 자리를 목록으로 남겨 두는 것이다.
그 목록이 있으면 나중에 그 자리의 코드를 고칠 때 계약이 있다는 사실을 알 수 있고, 없으면 몇 달 뒤의 자신이 조용히 계약을 깨뜨린다.
