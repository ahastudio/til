# Octane: React API를 그대로 쓰면서 가상 DOM을 컴파일로 없앤 프레임워크

<https://octanejs.dev/>

<https://github.com/octanejs/octane>

## 소개

빠른 JavaScript UI 프레임워크이며 [Inferno](inferno.md)의 후속작이다.
이미 아는 React API로 컴포넌트를 작성하면
컴파일러가 출하 전에 그것을 직접 DOM 코드로 바꾼다.
가상 DOM이 없고, 훅 규칙을 맞추는 부담이 없고,
의존성 배열을 손으로 관리하지 않는다.

만든 사람은 Dominic Gannaway(trueadm)이고,
Inferno를 만들었으며 React와 Lexical, Ripple, Svelte에서 일했다.
스타 1,412개, 포크 53개, 열린 이슈 23개다.
2026년 6월 22일에 만들어졌고 TypeScript로 작성되었으며 MIT 라이선스다.
상태는 베타다.

가장 짧은 예제가 이 프레임워크의 두 특징을 동시에 보여 준다.

```jsx
import { useState } from 'octane';

export function Counter() @{
	const [count, setCount] = useState(0);

	<button onClick={() => setCount(count + 1)}>
		{'Count: ' + count}
	</button>
}
```

`useState`는 React 그대로다.
함수 본문 뒤의 `@{ … }`가 새로운 것인데,
설정 코드와 출력을 나란히 두는 축약 표기이며 `return`이 없다.

## 두 방언

표준 JSX가 그대로 동작한다.
React 문서에서 컴포넌트를 복사해 `.tsx` 파일에 붙이면 돌아간다.
그리고 `.tsrx`라는 방언이 따로 있는데,
README는 이것을 JSX의 정신적 후속작이라 부른다.

`.tsrx`가 더 주는 것은 템플릿 지시자다.
`@if`, `@for`, `@switch`, `@try`가 있고 키가 붙은 빠른 경로로 컴파일된다.
그리고 앞서 본 `@{ … }` 축약이 여기 속한다.

두 방언을 한 앱에서 섞을 수 있고 경계를 넘어 임포트할 수 있다.
VS Code용 TSRX Syntax 확장이 구문 강조와 진단, 탐색, 자동 완성을 제공한다.

## 컴파일러가 대신하는 것

### 의존성 배열

`useEffect`와 `useMemo`, `useCallback` 계열에서 배열을 생략하면 컴파일러가 클로저가 실제로 캡처한 것에서 그것을 도출한다.
안정적인 setter와 dispatcher, ref, 상태 getter까지 포함해서 판정한다.

README는 이것을 시그널 프레임워크에서 연상되는 무관리 개발 경험이라고 설명하면서, 훅 모델을 떠나지 않고 그것을 얻는다고 주장한다.
명시적으로 배열을 적으면 React에서와 정확히 같은 뜻으로 동작한다. 즉 생략이 기본이 아니라 선택이다.

### 훅 규칙

훅이 호출 순서가 아니라 호출 지점으로 추적된다. 그래서 훅이 `if` 안에 있거나 이른 반환 뒤에 있어도 된다.

남은 규칙은 하나이고 그것은 컴파일러가 강제한다. 평범한 JS 루프 안의 훅은 컴파일 오류인데, 반복마다 하나의 호출 지점 슬롯을 공유하게 되기 때문이다.
대신 키가 붙은 `@for` 지시자를 쓰면 각 항목이 자기 훅 상태를 갖는다.

이 설명이 훅 규칙이 왜 존재했는지를 거꾸로 알려 준다. 호출 순서에 기대는 구현이었기 때문이며, 호출 지점을 식별할 수 있으면 규칙 대부분이 불필요해진다.

### 가상 DOM

컴포넌트는 React처럼 다시 렌더링되지만, 컴파일된 렌더 경로와 LIS 기반 키 재조정기가 런타임 오버헤드를 최소로 유지한다.

플랫폼을 다시 구현하지 않는다는 원칙도 함께 밝힌다.
실제 위임된 DOM 이벤트를 쓰고, 제어 폼 컴포넌트가 네이티브 이벤트 위에서 동작하며(React의 `value`/`checked` 의미를 유지하되 편집마다 `onInput`, 커밋에 네이티브 `onChange`), ref는 평범한 prop이다(`ref={cb}`, `ref={obj}`, `ref={[a, b]}`도 된다).
합성 이벤트 층이 브라우저를 다시 판단하는 일이 없다.

## 의도적으로 뺀 것

네이티브 렌더러는 React가 넓어진 곳에서 일부러 좁다.
클래스 컴포넌트가 없고, 서버 컴포넌트가 없고, 합성 이벤트 시스템이 없다.
README는 이것이 빈틈이 아니라 선택이라고 적고, 별도 문서에 적어 두었다고 밝힌다.

이 선언이 이 프로젝트를 평가하는 기준이 된다. React 호환을 목표로 하면서 무엇을 호환하지 않을지를 문서로 고정했기 때문이다.

## 그 밖에 들어 있는 것

| 기능                  | 내용                                                                                           |
| --------------------- | ---------------------------------------------------------------------------------------------- |
| `useLinkedState`      | 입력이 바뀌는 즉시 로컬 상태를 초기화하거나 조정한다. 이펙트도, 렌더 중 상태 갱신도 없다       |
| 렌더 중 프로미스      | `cache()` 래퍼 없이 `use()`에 들어가는 생성이 선언 위치에서 메모화된다                         |
| 스트리밍 SSR          | 바이트 단위로 안정적인 하이드레이션, Suspense 순서 밖 플러시, Node와 웹 스트림 모두            |
| `<Hydrate>`           | 서버 HTML을 보이게 두되 활성화할 값이 생길 때까지 비활성으로 유지하고, 자식을 별도 청크로 분리 |
| 동작 전용 루트        | 남이 소유한 DOM에 렌더링 없이 중단 가능한 동작과 위임 네이티브 이벤트만 붙인다                 |
| React 상호 운용       | `ReactCompat`으로 React를 Octane 안에, `OctaneCompat`으로 Octane을 React 앱에                  |
| `"use strong"`        | 순수 렌더를 단언하고 위반을 잡으며, 프로덕션 메모화가 목격된 입력으로 렌더 호출을 조건화한다   |
| `class` / `className` | clsx 식 합성이 모든 적용 지점에서 된다. `<style>` 블록은 형제 범위로 스코프된다                |
| 현재 상태 getter      | `useState`와 `useReducer`가 `[state, update, getState]`를 반환한다                             |

마지막 항목이 실무에서 자주 아쉬웠던 부분을 직접 겨냥한다.
지연된 콜백이 낡은 캡처 대신 최신 값을 읽을 수 있다는 것이며, React에서는 ref로 우회해야 했던 문제다.

## 설치하기

배포된 패키지는 Node.js 22.22.2 이상이 필요하다.

```bash
npm create octane my-app
cd my-app
npm run dev
```

`--template spa`는 클라이언트 전용 앱이고 `--template fullstack`은 라우팅과 스트리밍 SSR, 하이드레이션, 프로덕션 빌드를 더한다. 플래그를 빼면 물어본다.

기존 프로젝트에 붙이려면 CLI가 `.tsrx`에 필요한 TypeScript 설정까지 잡아 준다.

```bash
pnpm dlx @octanejs/cli init
```

손으로 하려면 이렇게 한다.

```bash
pnpm add octane @octanejs/vite-plugin
```

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import { octane } from '@octanejs/vite-plugin';

export default defineConfig({
	plugins: [octane()],
});
```

```ts
// main.ts
import { createRoot } from 'octane';
import { App } from './App.tsrx';

const root = createRoot(document.getElementById('root')!);
root.render(App, { title: 'Hello world!' });
```

Rspack과 Rsbuild도 지원한다.

## React와 섞어 쓰기

`octane/react`가 두 렌더러 각자에게 자기 컴포넌트 소유권을 남긴다.

| 경계           | 렌더하는 것                   | React 버전                            |
| -------------- | ----------------------------- | ------------------------------------- |
| `ReactCompat`  | Octane 앱 안의 실제 React     | React 19 계열의 React·React DOM 19.2+ |
| `OctaneCompat` | React 앱 안의 컴파일된 Octane | React 19                              |

```tsrx
// App.tsrx — Octane이 컴파일한다
import { ReactCompat } from 'octane/react';
import { Counter } from './Counter.react';

export function App() @{
	<ReactCompat><Counter start={3} /></ReactCompat>
}
```

```tsx
/** @jsxImportSource react */
// Counter.react.tsx — React의 JSX 변환으로 컴파일된다
import { useState } from 'react';

export function Counter({ start }: { start: number }) {
	const [count, setCount] = useState(start);
	return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

핵심 규칙이 주석 두 줄에 있다. 파일마다 어느 컴파일러가 소유하는지를 명시해야 하고, 섞인 빌드는 두 컴파일러 모두에 `requireDirective: true`를 쓰며, React를 Octane으로 별칭하지 말아야 한다.

`ReactCompat`은 React 상태와 이벤트, ref를 보존한다. 네이티브 컨텍스트를 React로 넘기려면 `bridgeReactContext(OctaneContext, ReactContext)`와 경계의 `contexts` prop을 써서 명시적으로 매핑한다.
그리고 `ReactCompat`은 Octane이 커밋한 뒤에 React 작업을 시작하거나 갱신하므로, Octane 트랜지션과 `flushSync()`가 React 루트를 동기적으로 커밋하지 않는다.

## 트레이드오프

### React API를 유지하면서 구현을 바꾼 선택

이 프로젝트의 전략은 명확하다. 배울 것을 늘리지 않고 성능과 개발 경험을 얻겠다는 것이다.
`useState`와 `useEffect`가 그대로 있으므로 이주 비용이 문법 학습이 아니라 빌드 설정과 미묘한 동작 차이로 옮겨 간다.

얻는 것은 채택 장벽이다. 기존 코드를 붙여 넣어 돌려 볼 수 있다는 점이 다른 프레임워크와 결정적으로 다르다.
그리고 React 생태계 라이브러리를 이식할 표적이 생긴다. `@octanejs/*` 아래에 zustand와 jotai, tanstack-query, radix, shadcn 같은 것들의 포트가 있는 이유다.

대가는 두 가지다.
하나는 호환의 상한이 남의 결정에 달린다는 것이다. React가 API를 바꾸면 따라갈지 말지를 매번 정해야 하고, 서버 컴포넌트처럼 이미 포기한 영역은 생태계가 그쪽으로 갈수록 격차가 벌어진다.
다른 하나는 호환이 검증 대상이 된다는 것이다. 같은 API가 같게 동작한다는 주장은 테스트로만 뒷받침되며, 그래서 3,900개가 넘는 동작 테스트와 별도의 패리티 보고서가 필요하다.

여기서 흔히 떠올리는 절충, 즉 React를 그대로 쓰면서 컴파일러만 붙이는 방식은 이미 React Compiler가 하고 있다.
이 프로젝트가 별도로 존재하는 이유는 가상 DOM 제거와 `.tsrx` 지시자처럼 React 위에서는 할 수 없는 것을 하려는 데 있으며, 그것이 곧 호환을 스스로 유지해야 하는 이유이기도 하다.

### 의존성 배열을 컴파일러가 도출하게 한 것

배열을 생략하면 컴파일러가 채운다는 것은 손으로 쓰는 실수를 없앤다.
빠뜨린 의존성으로 인한 낡은 값 버그와 불필요한 의존성으로 인한 과도한 재실행이 둘 다 사라진다.

대가는 무엇이 재실행을 유발하는지가 코드에 적혀 있지 않게 된다는 것이다.
배열은 성가시지만 동시에 문서였다. 이 이펙트가 무엇에 반응하는지를 읽는 사람이 한눈에 봤다.
도출된 의존성은 컴파일 결과에만 있으므로, 예상과 다르게 동작할 때 확인하려면 도구를 거쳐야 한다.

그래서 명시적 배열이 React와 똑같이 동작하도록 남겨 둔 결정이 중요하다. 의도를 고정하고 싶은 지점에서는 여전히 손으로 쓸 수 있다.
실무 규칙으로 옮기면, 성능이 걸린 이펙트와 외부 시스템을 건드리는 이펙트에는 배열을 적고 나머지는 생략하는 편이 균형에 맞는다.

### 새 파일 확장자를 도입한 것

`.tsrx`는 새 언어를 만드는 데 가까운 결정이다. 문법이 늘고 도구가 필요하며, VS Code 확장이 별도로 존재하는 이유가 그것이다.

얻는 것은 컴파일러가 알 수 있는 것이 늘어난다는 점이다.
`@for`가 키 있는 빠른 경로로 컴파일된다는 것은 일반적인 `map` 호출로는 알 수 없는 정보를 문법이 제공한다는 뜻이다. 앞서 본 루프 안 훅 문제도 `@for`가 있어서 해결된다.

대가는 생태계 전체가 그 확장자를 몰라도 되게 만들어야 한다는 것이다.
그래서 표준 JSX가 그대로 동작하고 두 방언을 섞을 수 있게 설계했으며, 이 결정이 없었다면 채택 전략 자체가 성립하지 않는다.
다만 섞을 수 있다는 것이 곧 섞어도 괜찮다는 뜻은 아니다. 파일마다 어느 컴파일러가 소유하는지를 사람이 관리해야 하고, 그 경계에서 나는 문제는 진단이 어렵다.

### 베타 상태와 이식된 바인딩

런타임과 컴파일러, SSR과 하이드레이션 경로가 모두 동작하지만 API는 아직 움직인다고 README가 밝힌다.
그리고 React 생태계 라이브러리들의 포트가 `@octanejs/*`로 제공되며, 각 패키지가 무엇을 이식했고 상류 버전이 무엇이고 알려진 차이가 무엇인지가 별도 문서에 정리되어 있다.

이 구조가 주는 것은 즉시 쓸 수 있음이다. 상태 관리와 데이터 페칭, UI 컴포넌트를 처음부터 만들지 않아도 된다.
대가는 유지보수 부담이 이 프로젝트에 집중된다는 것이다. 상류 라이브러리 스무 개 남짓의 변경을 한 팀이 따라가야 하고, 그 지연이 곧 알려진 차이의 목록이 된다.

바인딩 상태 문서가 존재한다는 사실 자체가 이 부담을 관리하려는 시도이며, 채택을 검토할 때 가장 먼저 읽어야 할 문서이기도 하다.

## 함정

`@{ … }` 안에서는 `return`을 쓰지 않는다. 표준 JSX 함수에서 옮겨 올 때 가장 먼저 걸리는 차이다.

평범한 JS 루프 안의 훅은 컴파일 오류다. React에서도 금지였지만 여기서는 빌드가 실패하므로, `map` 안에 훅이 있는 기존 코드를 옮기려면 `@for`로 바꿔야 한다.

클래스 컴포넌트와 서버 컴포넌트가 없다. 둘 중 하나를 쓰는 코드베이스는 이 프레임워크의 대상이 아니다.

Node.js 22.22.2 이상이 필요하다. 패치 버전까지 지정된 요구사항이므로 CI 이미지 확인이 필요하다.

React를 Octane으로 별칭하지 말라는 경고가 명시되어 있다. 다른 React 호환 라이브러리에서 흔히 쓰는 방법이 여기서는 금지다.

`ReactCompat`이 Octane 커밋 후에 React 작업을 시작하므로, `flushSync()`가 React 루트까지 동기 커밋하지 않는다. 두 렌더러가 섞인 곳에서 동기 갱신을 기대하는 코드가 어긋난다.

`<style>` 블록이 형제 범위로 스코프된다. 블록이 자기 형제와 그 아래를 스타일하고 부모는 건드리지 않는다는 규칙이며, CSS Modules나 styled-components의 범위 규칙과 다르다.

베타이고 API가 움직인다. 프로덕션 채택은 이 사실을 전제로 판단해야 한다.

## 확인하기

이 프레임워크의 주장을 검증하는 가장 빠른 방법은 두 가지다.

```bash
npm create octane my-app --template fullstack
cd my-app && npm run dev
```

먼저 React 문서의 컴포넌트를 `.tsx`로 붙여 넣어 그대로 도는지 본다. 붙여 넣기가 된다는 주장이 채택 전략의 전부이므로, 이것이 첫 시험이다.

그다음 같은 컴포넌트를 `.tsrx`로 옮겨 `@{ … }`와 `@for`로 다시 써 본다. 두 판본의 차이가 이 방언이 무엇을 위해 있는지를 알려 준다.

주장 자체를 확인하려면 저장소의 문서를 본다.

```bash
# 무엇을 호환하지 않는지
open docs/differences-from-react.md
# React에서 가져온 테스트가 실제로 얼마나 되는지
open docs/react-parity-coverage.md
# 각 바인딩이 상류 어느 버전을 이식했고 무엇이 다른지
open docs/bindings-status.md
```

세 번째가 실무 판단에 가장 직접 닿는다. 쓰려는 라이브러리의 포트가 얼마나 최신이고 어떤 차이가 알려져 있는지가 채택 가능 여부를 정한다.

## 체크리스트

- Node.js 22.22.2 이상인가
- 클래스 컴포넌트나 서버 컴포넌트를 쓰고 있지 않은가
- 쓰려는 React 라이브러리의 `@octanejs/*` 포트가 있고, 알려진 차이를 확인했는가
- React를 Octane으로 별칭하지 않았는가
- React와 섞는다면 파일별 컴파일러 소유권과 `requireDirective` 설정을 정했는가
- 성능이나 외부 시스템이 걸린 이펙트에는 의존성 배열을 명시했는가
- API가 움직이는 베타라는 점을 채택 결정에 반영했는가

## 비평

### 테스트 수를 앞세우면서 그 수가 무엇을 뜻하지 않는지도 함께 적었다

3,900개가 넘는 동작 테스트라는 수치를 내세우면서, README는 곧바로 단서를 붙인다.
이것은 Octane 자체의 테스트 수이고 모든 테스트가 React에서 이식되었다는 주장이 아니며, 고정된 스냅숏과 출처가 표시된 React 테스트 수는 별도 문서에 있다는 것이다.
그리고 프로덕션 컴파일러 경로로 같은 스위트를 다시 돌리는 프로젝트가 있지만 그것은 고유 테스트로 다시 세지 않는다고 적는다.

이 정직함은 드물다. 테스트 수는 부풀리기 쉬운 지표이고, 대개 부풀린 채로 제시된다.

그런데 이 정직함이 동시에 문제를 드러낸다. 테스트 수가 호환성의 증거가 될 수 없다는 사실을 작성자도 알고 있다는 것이다.
React 호환을 주장하는 프로젝트에서 필요한 수치는 테스트 개수가 아니라 React의 어떤 동작 집합 중 몇 퍼센트를 통과하는지다.
패리티 보고서가 그것을 담고 있을 수 있지만, README는 그 숫자를 본문으로 끌어올리지 않는다. 대신 세기 쉬운 쪽을 앞에 두었다.

### React 호환을 목표로 삼는 프로젝트의 구조적 위치

이 프로젝트가 감당하는 일은 React를 따라가면서 React보다 나은 구현을 유지하는 것이다. 그리고 두 목표는 같은 방향이 아니다.

React가 서버 컴포넌트로 옮겨 가는 동안 이 프레임워크는 그것을 지원하지 않기로 했다.
합성 이벤트를 버린 것도 같은 성격이다. React가 그 층 위에 쌓은 동작이 있다면 그것은 호환되지 않는다.
즉 의도적 차이 목록은 시간이 갈수록 길어지는 쪽으로만 움직인다.

여기서 나오는 물음은 이 프로젝트가 React 호환 프레임워크인가, 아니면 React를 닮은 다른 프레임워크인가 하는 것이다.
채택하는 쪽에서 이 구분이 중요하다. 전자라면 React로 돌아갈 길이 열려 있고, 후자라면 사실상 잠긴다.
`OctaneCompat`으로 React 앱 안에 넣을 수 있다는 점이 전자에 가깝게 만들지만, `.tsrx`로 쓴 컴포넌트는 되돌릴 수 없다.

[Inferno](inferno.md)의 이력이 이 물음에 자료를 준다. 같은 저자가 만든 React 호환 라이브러리이고, 성능 우위로 주목받았지만 React 생태계를 대체하지는 못했다.
이번에는 컴파일러와 새 방언으로 접근이 달라졌으나, 호환을 혼자 유지해야 하는 구조적 위치는 같다.

### 채택을 어렵게 만드는 것은 기술이 아니라 바인딩 유지보수다

이 프레임워크를 실제로 쓰려면 zustand나 tanstack-query 같은 라이브러리가 필요하고, 그것들이 `@octanejs/*` 포트로 제공된다.
포트가 있다는 사실이 채택을 가능하게 하는 동시에 가장 큰 위험이 된다.

포트는 상류를 따라가야 하고, 상류는 이 프로젝트를 고려하지 않고 움직인다.
바인딩이 스무 개 남짓이라면 상류 릴리스도 그만큼 자주 나온다는 뜻이고, 그 전부를 한 프로젝트가 추적해야 한다.
바인딩 상태 문서에 알려진 차이 항목이 있다는 것은 이미 지연이 존재한다는 뜻이다.

이 문제의 해법이 마땅치 않다.
라이브러리 저자들이 Octane을 직접 지원하게 만드는 것이 근본 해법인데, 그것은 채택률이 먼저 올라야 가능하고 채택률은 바인딩이 최신이어야 올라간다.
그래서 이 프로젝트의 실제 승부처는 컴파일러 성능이 아니라 바인딩을 얼마나 오래 따라갈 수 있느냐이며, 그 능력은 README가 보여 주는 어떤 수치로도 확인되지 않는다.

## 기억할 원칙

### 규칙을 문서로 가르치는 대신 컴파일러가 알게 만들 수 있다

훅 규칙은 지난 몇 년간 React 개발자가 외워야 했던 것이고, 린터가 도왔지만 근본적으로는 사람의 규율에 기댔다.
이 프로젝트는 그 규칙 대부분을 없앴는데, 방법이 규칙을 완화한 것이 아니라 구현을 바꾼 것이었다.
호출 순서 대신 호출 지점으로 훅을 추적하니 조건문 안의 훅이 가능해졌다.

같은 형태가 의존성 배열에서도 반복된다. 사람이 적던 정보를 컴파일러가 클로저에서 도출한다.

여기서 일반화할 수 있는 판단 기준이 있다.
어떤 규칙을 문서에 적어 가르치고 있다면, 그 규칙이 존재하는 이유가 구현의 편의인지 본질적 제약인지를 먼저 물어야 한다.
편의라면 구현을 바꿔 규칙을 없앨 수 있고, 본질이라면 규칙을 강제로 검사하게 만들 수 있다.
이 프로젝트가 루프 안 훅만 남기고 그것을 컴파일 오류로 만든 것이 후자의 예다. 남길 규칙과 없앨 규칙을 구분한 뒤, 남긴 것은 사람에게 맡기지 않았다.

실무에 옮기면 온보딩 문서에 적힌 주의사항 목록이 그 후보다.
그중 린트 규칙이나 타입으로 바꿀 수 있는 항목이 얼마나 되는지를 세어 보면, 문서가 짧아지고 위반이 줄어든다.
