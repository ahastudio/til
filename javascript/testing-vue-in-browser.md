# Node 없이 브라우저 탭 안에서 Vue 컴포넌트 테스트하기

원문: [Testing Vue components in the browser](https://jvns.ca/blog/2026/05/02/testing-vue-components-in-the-browser/)

HN 토론: <https://news.ycombinator.com/item?id=47990526> (3점, 0개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/pcrluk/testing_vue_components_browser> (6점, 0개 댓글)

## 요약

Julia Evans가 2026년 5월 2일에 쓴 실습 기록이다.

이 블로그의 장기 프로젝트 중 하나가 **Node나 다른 서버 JS 런타임 없이 프런트엔드 자바스크립트를 쓰는 법을 알아내는 것**이며, [빌드 시스템 없이 라이브러리 가져오기](import-without-build-system.md)가 그 연재의 일부다.

그런데 그 프로젝트들에서 자주 부딪히는 문제가 있다. **테스트를 어떻게 쓸지 모르겠다**는 것이다.

과거에 Playwright를 써 봤는데 **느리고 다루기 불편하게 느껴졌다**고 한다. 새 브라우저 프로세스를 계속 띄우는 것이 그렇고, **테스트를 조율하는 데 Node 코드가 좀 들어갔기 때문**이다.

결과가 이렇다. **그냥 프런트엔드 코드를 테스트하지 않게 되었고 그것이 좋게 느껴지지 않는다**는 것이다.
대개 프로젝트를 많이 갱신하지도 않아서 자주 문제가 되지는 않지만, **더 자신 있게 변경할 수 있으면 좋겠다**고 적는다.

### 발단

Alex Chan이 예전에 **“서드파티 프레임워크 없이 자바스크립트 테스트하기”**라는 글을 썼다고 소개한다. 이 연재의 앞선 글에 대한 응답이었고, **브라우저의 페이지 안에서 돌아가는 아주 작은 단위 테스트 프레임워크를 쓰는 법**을 설명했다는 것이다.

당시에 그 글을 정말 좋아했지만 **단위 테스트만 다뤘고**, 자기는 Vue 컴포넌트에 대한 **종단 간 통합 테스트**를 쓰고 싶었는데 방법을 몰랐다고 한다.

그러다 Marco와 이야기하다가 **“있잖아, Vue 컴포넌트 테스트를 그냥 브라우저에서 돌리면 돼”** 같은 말을 들었고, **다시 시도해 봐야겠다**고 생각했다는 것이다.

어제 다 한 것이라 개선할 것이 분명히 많지만 잊기 전에 적어 둔다고 밝힌다.

까다로웠던 이유도 짚는다.
**Vue 사이트가 대개 빌드 과정에 Node를 어떤 식으로든 쓴다고 전제하는데**(“1단계: `npm install THING`”이 많다), 자기는 Node나 Deno 등을 쓰고 싶지 않았다는 것이다.
그런데 **결과적으로 그렇게 복잡하지 않았다**고 한다.

대상은 2023년에 만든 진 피드백 사이트다.

## 절차

### 테스트 프레임워크: QUnit

QUnit을 썼고 잘 동작했다는 것이다. 어떻게 동작하는지에 대해 흥미롭게 할 말이 없어서 거기까지만 한다며, Alex의 “직접 테스트 프레임워크를 쓰라”는 접근도 통했을 것이라고 적는다.

다만 하나를 짚는다.
**QUnit에 테스트 하나만 다시 돌리는 “rerun test” 버튼이 있는 것이 좋았다**는 것이다.
**테스트에 네트워크 요청이 워낙 많아서 하나만 돌릴 방법이 있는 것이 디버깅의 혼란을 크게 줄여 준다**는 이유다.

### 1단계: 컴포넌트를 테스트용으로 준비하기

먼저 Vue 컴포넌트를 테스트 환경에 올려야 했다.

메인 앱을 고쳐 **모든 컴포넌트를 `window._components`에 넣었다**.

```javascript
const components = {
  'Feedback': FeedbackComponent,
  // ...
}
window._components = components;
```

그다음 `mountComponent` 함수를 쓸 수 있게 되었는데, **평소 메인 앱이 하는 것과 거의 똑같은 일**(쓰려는 컴포넌트로 아주 작은 템플릿을 렌더링)을 한다.

차이가 둘이다.
**props로 쓸 추가 데이터를 선택적으로 넘길 수 있고**, **테스트가 끝나면 DOM에서 제거되는 임시 비가시 div에 마운트한다**는 것이다. 그 div는 화면 밖에 놓여서(`position: absolute; top: -10000, ...`) 보이지 않는다.

```javascript
const {div} = mountComponent(
  '<Page :feedbacks="feedbacks" id=2 />',
  {feedbacks: [testFeedback]},
);
```

```javascript
function mountComponent(template, data) {
  const app = Vue.createApp({
    template: template,
    data: () => data,
  })
  for (const [c, v] of Object.entries(window._components)) {
    app.component(c, v);
  }
  const div = document.getElementById('qunit-fixture')
    .appendChild(document.createElement('div'));
  return div;
}
```

결과는 **프로그램으로 클릭하고 폼 데이터를 채우고 올바른 내용이 나타나는지 확인할 수 있는 div**다.

### 2단계: 픽스처 데이터 추가

클라이언트 JS가 서버와 제대로 동작하는지 확인하는 종단 간 통합 테스트를 쓰고 있었으므로 **데이터베이스에 테스트 데이터가 필요했다**.

그래서 **SQL 25줄쯤을 써서 테스트 데이터를 세팅하고, 개발 서버에 그 SQL을 돌려 테스트 데이터를 알려진 상태로 되돌리는 엔드포인트를 추가**했다.

```javascript
async function reset() {
  return fetch('/api/reset_test_data', {method: "POST"})
}
```

그리고 테스트 데이터가 필요한 테스트 앞에서 `await reset()`을 돌린다.

솔직한 단서가 붙는다. **이 `reset()` 함수가 사실 늘 전부를 되돌리지는 않아서 좀 안 좋은데, 시작하기에는 쓸 만했고 언제든 개선할 수 있다**는 것이다.

### 3단계: 기본 테스트

```javascript
QUnit.test('renders feedback content', async function (assert) {
  const {div} = mountComponent(
    '<Page :feedbacks="feedbacks" id=2 image=2 page_hash=2 />',
    {feedbacks: [testFeedback]},
  );
  assert.ok(div.textContent.includes('loved this section'));
})
```

**div를 렌더링하고 대충 맞는 데이터가 들어 있는지 확인하는 것**이 전부다.

## 마주친 문제들

### 페이지 일부가 렌더링되기를 기다리기

테스트에 네트워크 요청이 많고, **그것들이 끝나고 Vue가 결과로 할 일을 해서 DOM을 갱신하기까지 시간이 걸린다**.

그리고 원칙을 명시한다.
**테스트에 아무 `sleep()` 호출을 넣고 타이밍이 맞기를 바라는 것이 느리고 불안정하고 극도로 짜증스럽다는 것을 우리 모두 오래전에 배웠으므로** 다른 방법이 필요했다는 것이다.

정상적인 방법은 **DOM에서 진행해도 되는지 알아낼 방법을 찾는 것**으로 보인다고 적는다. “이 버튼이 보이면 진행해도 된다” 같은 식이다.

그래서 **20밀리초마다 조건이 끝났는지 폴링하고 2초 뒤 타임아웃하는 작은 `waitFor()` 함수**를 썼다.

```javascript
QUnit.test("click item", async function (assert) {
  const {div} = mountComponent(
    '<Feedback zine_id="test123" image_width="800px" />', {});
  const item = await waitFor(() => div.querySelector('.feedback-item'));
  item.click();
  // ...
})
```

이 개념의 구현이 많이 있고 **전부 자기 것보다 잘 생각된 것들**이라며 `qunit-wait-for`와 Playwright의 `expect.poll`을 든다.

### 무엇을 기다려야 하는지 알아내는 것이 간단하지 않다

이 절이 이 글에서 가장 값지다.

**DOM에서 기다릴 올바른 대상을 찾았다고 생각한 경우들이 있었는데**(“이 textarea가 나타나기를 기다리면 되겠지!”), **프로그램 내부 동작의 세부 때문에 사실은 나중의 다른 무언가를 기다려야 했고 그것을 짚어내기가 어려웠다**는 것이다.

그래서 **컴포넌트 하나를 고쳐 중요한 동작이 끝났을 때 DOM에 임의의 값을 넣게 했다**(`data-this-thing-is-ready=true` 같은 것). 그리고 **좋게 느껴지지 않았다**고 적는다.

그다음 문장이 이 글의 핵심 통찰이다.

**이런 테스트 문제를 고치는 올바른 방법이 앱을 사용자에게도 더 안정적으로 만드는 리팩터링일 것 같다**는 것이다.
**DOM에 있는데 사용자가 상호작용할 준비가 안 된 요소가 있다면, 어쩌면 그것을 아직 표시하지 말아야 하는 것 아닌가**라는 것이다.

### 요소를 찾으려고 CSS 클래스를 붙이기

테스트에서 찾아야 하는 HTML 요소에 클래스를 몇 개 추가했다고 한다. 클릭해야 하거나 DOM에 나타나기를 기다려야 해서다.

그런데 **나중에 이 접근을 바꾸고 싶을지도 모른다**고 적는다.
**프런트엔드 테스트 프레임워크들이 CSS 클래스를 쓰지 말고 `getByRole` 같은 것을, 최후의 수단으로 `data-testid` 같은 것을 쓰라고 권하는 것 같기 때문**이다.

그리고 여기서도 같은 감각을 적는다.
**앱을 더 접근성 있게 만들면서 동시에 테스트하기 쉽게 만드는 길이 있는 것 같다**는 것이다.

### 폼 채우기가 까다롭다

폼을 채우려면 **`value`만 설정해서는 안 되고 요소가 바뀌었다고 Vue에게 알리는 이벤트를 발송해야 한다**. 그리고 **`checkbox`와 `textarea`가 서로 다른 종류의 이벤트를 필요로 한다**.

```javascript
textarea.value = 'banana banana banana';
textarea.dispatchEvent(new Event('input'));

checkbox.checked = true;
checkbox.dispatchEvent(new Event('change'));
```

**좀 성가시고, 그래서 UI 테스트 라이브러리를 왜 쓰고 싶어질 수 있는지 알게 되었다**고 적는다.
Testing Library의 폼 작성 예제가 **자기가 하는 것과 극도로 달라 보이고**, Vue Test Utils의 폼 처리 절이 **이것을 많이 단순화해 주는 것 같다**는 것이다.

### 테스트 커버리지

커버리지를 알고 싶었는데 **Chrome에 JS와 CSS용 코드 커버리지 기능이 내장되어 있다**는 것을 알게 되었다고 한다.

JS가 esbuild로 `bundle.js`에 번들되므로 그 파일을 보고 어느 줄이 덮이지 않았는지 볼 수 있었다.

과정이 조금 까다로웠다는 단서를 단다. **Chrome 개발자 도구에서 소스맵을 꺼야 했고**, 커버리지 데이터를 보려면 **그다지 뻔하지 않은 특정 동작 순서**를 거쳐야 했다는 것이다.

### 남은 질문

Testing Library를 발견했는데 **자기 초기 발상과 아주 다른 테스트 작성 지침이 많다**고 한다. 전부 그것으로 다시 써 보는 실험을 했고 꽤 괜찮게 느껴졌다며, **Node 없이 동작하는 `.umd.js` 파일을 배포한다**는 점을 짚는다.

그리고 미해결 문제를 하나 남긴다.
**이 테스트를 명령줄에서 돌릴 방법이 전혀 없다는 것에 대해 어떻게 생각해야 할지 모르겠다**는 것이다.
**주로 브라우저에서 작업하면서 원할 때 CI에서도 돌릴 간단한 방법이 있을까**라고 묻는다.

## 분석

### 제약이 만든 선택이 독립적인 장점을 갖는다

이 글의 구성이 “Node를 안 쓰겠다”는 제약에서 출발한다. 그런데 그 제약을 지키려고 고른 방법이 **제약과 무관하게 좋은 성질**을 갖는다.

저자가 Playwright를 불편해한 이유가 **새 브라우저 프로세스를 계속 띄우는 것**이었다.

브라우저 탭 안에서 테스트를 돌리면 그 비용이 사라진다. 이미 떠 있는 탭에서 새로 고침만 하면 되기 때문이다.
그리고 QUnit의 “테스트 하나만 다시 돌리기” 버튼이 값진 이유도 같다. **피드백 루프가 초 단위가 아니라 밀리초 단위**가 된다.

더 중요한 것이 하나 있다.

**테스트가 실제 브라우저의 실제 DOM에서 돈다.** jsdom 같은 에뮬레이션 계층이 없다.

이것이 프런트엔드 단위 테스트의 고질적 문제를 없앤다. jsdom에서 통과하는데 브라우저에서 깨지거나 그 반대인 경우다. 레이아웃, `getBoundingClientRect`, CSS가 적용된 가시성 같은 것이 jsdom에는 제대로 없다.

그리고 디버깅 경험이 다르다. **테스트가 실패한 상태의 DOM을 개발자 도구로 그대로 들여다볼 수 있다.**
저자가 화면 밖에 숨긴 div를 쓴 것이 그 접근을 조금 어렵게 만들지만, 필요하면 `position`을 빼고 눈으로 볼 수 있다.

일반화하면, 어떤 제약을 지키려고 택한 우회로가 제약과 무관한 이점을 가질 때, **그 제약이 사라져도 그 방법을 유지할 이유가 생긴다**.

저자가 Node를 피하려는 동기와 무관하게 이 방식이 좋을 수 있다는 뜻이고, 실제로 최근 몇 년간 브라우저에서 직접 도는 테스트 러너(Vitest browser mode, Web Test Runner)가 늘어난 배경이기도 하다.

### 테스트가 어려운 지점이 설계 결함의 신호다

저자가 두 번 같은 구조의 관찰을 한다.

**무엇을 기다릴지 모르겠어서 `data-this-thing-is-ready=true`를 넣었는데 좋게 느껴지지 않았고**, 올바른 해법은 **DOM에 있으면서 아직 상호작용할 수 없는 요소를 애초에 표시하지 않는 리팩터링**일 것 같다는 것이다.

그리고 **CSS 클래스로 요소를 찾은 것에 대해서도**, `getByRole`을 쓰라는 권고를 떠올리며 **앱을 더 접근성 있게 만들면서 동시에 테스트하기 쉽게 만드는 길이 있는 것 같다**고 적는다.

두 관찰이 같은 원리의 두 사례다.

| 테스트에서 겪는 문제      | 사용자가 겪는 문제            |
| ------------------------- | ----------------------------- |
| 뭘 기다려야 할지 모르겠다 | 언제 눌러도 되는지 알 수 없다 |
| 요소를 식별할 방법이 없다 | 스크린 리더가 식별할 수 없다  |

**테스트 코드와 보조 기술이 같은 정보를 필요로 한다.** 둘 다 사람이 아니고, 둘 다 DOM만 보고 상태를 판단해야 한다.

그래서 이런 규칙이 나온다.
자동화로 다루기 어려운 UI는 대개 사람에게도 불친절하며, 테스트를 위해 추가하는 표식은 **그 불친절함을 가리는 반창고**인 경우가 많다.

`data-testid`가 “최후의 수단”으로 권장되는 이유가 그것이다. 그것을 붙이는 순간 **테스트만 아는 정보**가 생기고, 사용자는 여전히 모른다.

저자가 그 반창고를 붙이고 나서 “좋게 느껴지지 않았다”고 적은 것이 정확한 감각이다. 그리고 그 불편함을 설계 신호로 읽은 것이 이 글에서 가장 값진 부분이다.

다만 이 원칙에 한계도 있다.
**모든 테스트 어려움이 UX 결함인 것은 아니다.** 예를 들어 내부 캐시가 채워지기를 기다려야 하는 경우는 사용자에게 보일 이유가 없다.
그런 경우에는 **DOM이 아니라 프로그램의 약속을 기다리는 편**이 낫다. 컴포넌트가 프라미스를 노출하거나 이벤트를 발생시키게 하는 것이다.

### 이벤트 발송이 프레임워크 추상화의 누수다

폼을 채울 때 `value`만 바꾸면 안 되고 이벤트를 발송해야 한다는 부분이 사소해 보이지만 구조적이다.

왜 그런가.

Vue의 `v-model`이 **DOM 이벤트를 구독해서 반응형 상태를 갱신한다.** 그래서 이벤트 없이 `value`만 바꾸면 **DOM과 Vue의 상태가 어긋난다**.

그리고 어떤 이벤트인지가 요소마다 다르다.

| 요소                | 필요한 이벤트 |
| ------------------- | ------------- |
| `input`, `textarea` | `input`       |
| `checkbox`, `radio` | `change`      |
| `select`            | `change`      |

즉 테스트를 쓰려면 **프레임워크가 감춰 주기로 한 바로 그 세부를 알아야 한다**.

이것이 Testing Library 같은 라이브러리가 존재하는 이유다. `userEvent.type()`이 실제 사용자처럼 키 입력 이벤트를 순서대로 발송해 준다.

그리고 저자가 남긴 관찰 — **Testing Library의 예제가 자기가 하는 것과 극도로 달라 보인다** — 이 그 차이를 가리킨다.

저자의 코드는 “상태를 이렇게 만들어라”이고 **Testing Library는 “사용자가 이렇게 한다”**이다.

후자가 나은 이유는 편의 때문만이 아니다. 전자는 **프레임워크 구현에 의존**하므로 Vue가 이벤트 처리 방식을 바꾸면 테스트가 깨진다. 후자는 사용자 동작을 흉내 내므로 그 층에서 안정적이다.

Testing Library가 `.umd.js`를 배포한다는 저자의 발견이 실용적으로 중요한 이유가 그것이다. **Node 제약을 깨지 않고 이 층을 얻을 수 있다.**

## 비평

### 반응이 없었다는 사실 자체가 하나의 데이터다

이 글은 HN에 두 번 올라가 각각 3점에 **댓글 0개**였고, Lobste.rs에서도 6점에 **댓글 0개**였다.

같은 저자의 다른 글들과 대비가 크다. [터미널 불만 설문](../cli/terminal-frustrations.md)이 273점에 311댓글, [Django 입문](../django/starting-django.md)이 257점에 143댓글이었다.

왜 이 글만 조용한가.

주제의 교차점이 좁다. **Vue를 쓰면서 동시에 Node를 안 쓰는 사람**이 드물기 때문이다.
그리고 이 글이 논쟁거리를 제공하지 않는다. 주장이 아니라 작업 기록이다.

다만 그 좁음이 이 글의 결함은 아니다. 오히려 이 연재의 성격을 드러낸다.

저자가 스스로 적은 대로 **프런트엔드나 백엔드 개발자로 일해 본 적이 없고 계속 아주 기본적인 작업을 배우고 있다고 느낀다**는 것이다.
그런 기록은 같은 자리에 있는 사람에게만 정확히 유용하다.

그리고 그 사람 수가 적다는 것이 문제라기보다, **이런 조합을 시도한 기록이 달리 없다**는 점이 이 글의 값어치다.

### `mountComponent` 코드가 그대로 동작하지 않는다

글에 실린 코드 조각에 불일치가 있다.

`mountComponent`가 `return div`로 끝나는데 사용하는 쪽은 `const {div} = mountComponent(...)`로 구조 분해한다. **객체가 아니라 요소를 반환하므로 `div`가 `undefined`가 된다.**

그리고 더 중요하게, **`app.mount(div)`를 호출하는 줄이 없다.** 앱을 만들고 컴포넌트를 등록하고 div를 만들기만 하면 아무것도 렌더링되지 않는다.

저자가 실제 코드에서는 당연히 마운트하고 있을 것이므로 **글에 옮기면서 줄인 결과**로 보인다.

그래도 짚어 둘 만하다. 이 글의 성격이 **따라 해 볼 수 있는 안내**인데 그대로 복사하면 동작하지 않기 때문이다.

빠진 부분을 채우면 이렇게 된다.

```javascript
function mountComponent(template, data) {
  const app = Vue.createApp({
    template: template,
    data: () => data,
  });
  for (const [c, v] of Object.entries(window._components)) {
    app.component(c, v);
  }
  const div = document.getElementById('qunit-fixture')
    .appendChild(document.createElement('div'));
  app.mount(div);                 // 이 줄이 빠져 있다
  return {app, div};              // 구조 분해에 맞춰 객체로 반환한다
}
```

`app`도 함께 돌려주는 편이 낫다. **테스트가 끝날 때 `app.unmount()`를 호출해야** 컴포넌트가 등록한 타이머나 전역 이벤트 리스너가 남지 않기 때문이다.
QUnit의 `#qunit-fixture`가 테스트마다 DOM을 비우기는 하지만, **DOM에서 제거되는 것과 Vue 앱이 정리되는 것은 다른 일**이다.

이것이 실제로 문제가 되는 상황이 있다. 컴포넌트가 `setInterval`이나 `window` 이벤트 리스너를 걸어 두면 테스트가 끝나도 계속 돌고, **다음 테스트에서 예상 못 한 네트워크 요청이나 오류로 나타난다.**

### 명령줄에서 못 돌린다는 문제가 구조적이다

저자가 마지막에 남긴 질문 — **이 테스트를 명령줄에서 전혀 돌릴 수 없다는 것을 어떻게 생각해야 할지 모르겠다** — 이 이 접근의 가장 큰 실질적 한계다.

그리고 이 한계가 우연이 아니다.

CI가 필요로 하는 것이 **종료 코드**다. 테스트가 브라우저 탭 안에서만 존재하면 프로세스도 없고 종료 코드도 없다.

그런데 저자의 질문(“주로 브라우저에서 작업하면서 원할 때 CI에서도 돌릴 간단한 방법이 있을까”)에 대한 답이 실은 있다.

QUnit이 **결과를 전역 콜백으로 노출**한다. 그러면 헤드리스 브라우저가 그것을 읽어 종료 코드로 바꿀 수 있다.

```javascript
// 테스트 페이지에 추가
QUnit.done(function (details) {
  window.__qunit_results = details;   // {failed, passed, total, runtime}
});
```

```bash
# CI에서: 헤드리스 크롬으로 페이지를 열고 결과를 읽는다
# (Node를 쓰지 않으려면 CDP를 직접 두드리거나 아래처럼 작은 도구를 쓴다)
chromium --headless --dump-dom http://localhost:8000/tests.html
```

여기서 저자의 제약과 현실이 충돌한다.
브라우저를 자동으로 조종하는 도구가 **대개 Node 생태계에 있다**.

그렇다고 방법이 없지는 않다. 파이썬의 Playwright 바인딩이나 Selenium, 또는 `chromium --headless`에 CDP를 직접 쓰는 방식이 있다.

그래서 정확한 정리는 이렇다.
“Node 없이 테스트를 쓴다”는 목표는 달성되었고, **“Node 없이 테스트를 자동 실행한다”는 별개의 문제**이며 아직 안 풀렸다.

그리고 두 번째가 훨씬 덜 중요할 수도 있다. 저자의 프로젝트가 **자주 갱신되지 않는 개인 사이트**이므로, 배포 전에 탭을 새로 고쳐 초록불을 확인하는 것으로 충분할 수 있다.

**자동화의 값어치가 실행 빈도에 비례한다**는 점을 생각하면 그 판단이 합리적이다.

### 픽스처 리셋이 안고 있는 위험을 가볍게 넘겼다

저자가 `reset()` 함수에 대해 **사실 늘 전부를 되돌리지는 않아서 좀 안 좋은데 시작하기에는 쓸 만했다**고 적고 넘어간다.

시작 단계에서는 맞는 판단이다. 다만 이 종류의 부분 리셋이 **가장 찾기 어려운 테스트 실패를 만든다**는 점은 짚어 둘 만하다.

무엇이 문제인가.

리셋이 불완전하면 **테스트 사이에 상태가 샌다**. 그러면 테스트가 **실행 순서에 의존**하게 되고, 혼자 돌리면 통과하는데 전체를 돌리면 실패하거나 그 반대가 된다.

그리고 저자가 좋아한다고 한 QUnit의 “테스트 하나만 다시 돌리기” 기능이 **그 문제를 숨긴다**. 하나만 돌려 통과하는 것을 보고 고쳤다고 판단하기 쉽기 때문이다.

이것을 싸게 막는 방법이 있다.

```sql
-- 전체 삭제 후 삽입. 테이블이 몇 개뿐이면 이것이 가장 안전하다
DELETE FROM feedbacks;
DELETE FROM zines;
-- 그다음 픽스처 삽입
```

또는 SQLite를 쓰고 있다면 **테스트용 DB 파일을 통째로 복사해 두고 리셋 때 덮어쓰는 것**이 가장 확실하다.

```bash
# 개발 서버 시작 전에
cp test_fixture.sqlite test.sqlite
```

그리고 QUnit에 **테스트 순서를 무작위로 섞는 옵션**이 있다는 점도 유용하다. 순서 의존성이 있으면 빨리 드러난다.

```javascript
QUnit.config.reorder = false;   // 실패한 테스트를 먼저 돌리는 기본 동작을 끈다
```

## 체크리스트

- 테스트가 브라우저 탭에서 도는가? 아니면 에뮬레이션 계층(jsdom)을 거치는가
- 컴포넌트를 마운트한 뒤 테스트 끝에 `unmount()`를 부르는가? 타이머와 전역 리스너가 남지 않는가
- `sleep()` 대신 조건 폴링(`waitFor`)을 쓰는가
- 기다리는 대상이 **사용자에게도 의미 있는 상태**인가? 테스트만 아는 표식을 넣고 있지 않은가
- 요소를 찾을 때 `getByRole`처럼 접근성 정보를 쓸 수 있는가? CSS 클래스에 의존하고 있지 않은가
- 폼 입력에 이벤트를 발송하는가? 요소마다 필요한 이벤트가 다르다는 것을 아는가
- 픽스처 리셋이 정말 전부를 되돌리는가? 테스트 순서를 바꿔도 통과하는가
- 이 테스트를 CI에서 돌릴 필요가 실제로 있는가? 없다면 그 사실을 적어 두었는가

## 기억할 원칙

### 테스트하기 어렵다는 감각을 설계 피드백으로 읽는다

이 글에서 가장 오래 남을 것이 저자가 반창고를 붙이고 나서 한 생각이다.

DOM에 있는데 사용자가 상호작용할 준비가 안 된 요소가 있다면, **어쩌면 그것을 아직 표시하지 말아야 하는 것 아닌가**.

이 문장의 구조가 일반적이다. **“테스트를 쓰려니 X가 필요하다”를 “사용자도 X가 필요한 것 아닌가”로 바꿔 읽는 것**이다.

몇 가지로 번역된다.

무엇을 기다릴지 모르겠다면, 사용자도 **언제 눌러도 되는지 모른다**.
요소를 식별할 방법이 없다면, 보조 기술도 **식별할 수 없다**.
상태를 세팅하려고 내부를 건드려야 한다면, 그 상태에 도달하는 **정상 경로가 없거나 너무 길다**.
같은 동작을 검증하려고 여러 곳을 확인해야 한다면, 그 동작의 결과가 **한곳에 모여 있지 않다**.

그래서 테스트를 쓰는 일이 **설계 리뷰의 한 형태**가 된다.

다만 이 원칙을 기계적으로 적용하면 과해진다. 앞서 짚은 대로 **내부 캐시처럼 사용자와 무관한 상태**도 있고, 그런 경우 테스트용 후크가 정당하다.

구분하는 질문이 하나 있다.
이 표식이 없으면 **사용자가 곤란해지는가, 아니면 테스트만 곤란해지는가**.
전자면 UI를 고치고 후자면 후크를 붙이면 된다.

저자의 `data-this-thing-is-ready`는 전자에 가까웠고, 그래서 불편했던 것이다.

### 도구를 피하는 결정과 개념을 피하는 결정을 구분한다

이 연재의 전제가 **Node를 쓰지 않는 것**이다. 그런데 이 글에서 저자가 결국 마주친 것들이 Node와 무관하다.

기다림, 이벤트 발송, 픽스처 관리, 커버리지, CI 실행이다.

이것들은 **테스트라는 문제에 본래 있는 것**이고, Node를 쓰든 안 쓰든 나타난다.
Playwright가 그것들을 이미 풀어 두었기 때문에 Playwright를 쓰면 안 보일 뿐이다.

그러면 저자의 선택을 이렇게 볼 수 있다.
도구를 피한 대가로 그 도구가 풀어 둔 문제들을 하나씩 다시 만났고, 대신 **그 문제들이 무엇인지 알게 되었다**.

이것이 손해인지 이득인지는 목적에 달렸다.

제품을 빨리 내야 하면 손해다. `waitFor`를 직접 쓰는 것은 명백한 중복 노동이고, 저자 스스로 **기존 구현들이 전부 자기 것보다 잘 생각되었다**고 인정했다.

배우는 것이 목적이면 이득이다. 이제 저자는 `expect.poll`이 무엇을 해 주는지, 왜 `data-testid`가 최후의 수단인지를 **겪어서** 안다.

그리고 이 연재의 성격이 후자다. 저자가 **계속 아주 기본적인 작업을 배우고 있다고 느낀다**고 적은 그대로다.

일반화하면, 성숙한 도구를 의도적으로 피하는 것은 그 도구가 어떤 문제를 풀고 있었는지 배우는 방법이고, **그 배움이 끝나면 대개 도구로 돌아가는 것이 맞다**.

저자가 마지막에 Testing Library를 발견하고 **전부 다시 써 봤더니 꽤 괜찮게 느껴졌다**고 적은 것이 그 회귀의 시작으로 보인다.
그리고 그 라이브러리가 `.umd.js`를 배포한다는 사실을 확인한 것이 **제약을 지키면서 도구로 돌아갈 수 있는지**를 먼저 확인한 것이다.
