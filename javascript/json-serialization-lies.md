# JSON 직렬화는 값을 조용히 바꿔서 넘긴다

원문: [Your JSON Is Lying to You](https://blog.gaborkoos.com/posts/2026-08-03-Your-JSON-Is-Lying-to-You/)

Lobste.rs 토론: <https://lobste.rs/s/tjgemj/your_json_is_lying_you> (46점, 13개 댓글)

## 요약

저자는 브라우저 콘솔에서 바로 재현되는 두 예제로 글을 연다.
`{id: 9007199254740993}` 같은 큰 정수를 `JSON.stringify`에 넘기면
값이 조용히 `...992`로 바뀌어 나오고, 오류나 경고는 전혀 없다는 것이다.
두 번째 예제는 `id`, `missing: undefined`, `createdAt: new Date(...)`,
`score: NaN`을 담은 객체를
`JSON.parse(JSON.stringify(...))`로 왕복시킨 결과를 보여 준다.
정수는 반올림되고, `missing` 속성은 사라지고,
`Date`는 문자열로 바뀌고, `NaN`은 `null`이 된다.
JavaScript에서 가장 익숙한 직렬화 왕복이 원본과 다른 타입과 값을
가진 사본을 만들어 낸다는 것이 글 전체의 출발점이다.

이어서 JSON의 역사를 짚는다.
JSON은 2001년경 Douglas Crockford가 이름 붙이고 대중화했고,
RFC 4627이 2006년에, 현재 표준인 RFC 8259가 2017년에 명세했다.
당시 XML이 지배하던 데이터 교환 환경에서 JSON은
JavaScript 개발자에게 이미 익숙한 객체·배열 리터럴 문법을 기반으로
훨씬 작은 문법을 제공했다.
JSON은 문자열, 숫자, 불리언, `null`, 배열, 객체만 지원하며,
JavaScript가 가진 `undefined`, `BigInt`, 심볼, 특수 수치,
프로토타입을 가진 객체, 내부 상태를 가진 내장 컬렉션은
이 모델 밖에 있다.

본문은 이 격차를 다섯 갈래로 나눠 다룬다.
첫째, 정수는 `Number.MAX_SAFE_INTEGER`(2^53 - 1)를 넘어서면
`JSON.stringify`가 실행되기도 전에, 숫자 리터럴이 평가되는 시점에
이미 반올림된다는 것.
둘째, 속성이 아예 없는 것과 값이 `undefined`인 속성은
JavaScript에서는 `in` 연산자로 구분되지만
직렬화하면 객체에서는 속성이 통째로 사라지고 배열에서는 `null`이
되어 그 구분이 사라진다는 것.
셋째, `JSON.stringify`는 객체 속성 순서를 안정적으로 보존하지만
RFC 8259는 객체를 순서 없는 컬렉션으로 정의하므로,
Go의 `map[string]any`처럼 순서를 보장하지 않는 언어로 넘어가면
그 순서에 의미를 실었던 코드가 깨진다는 것.
넷째, `Date`, `Map`, `Set`, `RegExp`, `Error`, 타입드 배열,
클래스 인스턴스가 직렬화를 거치면 원래 타입 정보와 프로토타입,
비공개 상태를 모두 잃고 평범한 문자열이나 빈 객체로 바뀐다는 것.
다섯째, 직렬화 자체가 `toJSON()` 메서드, 게터, replacer 콜백을 통해
실제 코드를 실행하므로 값을 계산하거나 외부 상태에 접근하거나
예외를 던질 수 있다는 것이다.

글은 각 문제마다 구체적인 처방을 함께 제시한다.
큰 정수는 십진 문자열로 넘기고 스키마에 그렇게 명시할 것,
`undefined`가 아니라 생략과 `null`이라는 JSON이 실제로 표현할 수 있는
두 상태로 API 계약을 정의할 것, 순서에 의미가 있다면 객체 대신
배열로 표현할 것, 서명이나 해시나 캐시 키가 필요하다면 정준화
(canonicalization) 스킴을 따로 정의할 것, 그리고 모든 비-JSON 타입의
직렬화 형태를 양쪽이 합의한 계약으로 명시적으로 정의할 것을 권한다.

## 분석

### 이 글의 진짜 주제는 JSON이 아니라 암묵적 계약이다

표면적으로는 `JSON.stringify`의 변환 규칙을 나열하는 글처럼 보이지만,
본문 전체를 관통하는 주장은 하나다.
JavaScript 값과 JSON 사이의 변환이 개발자가 눈으로 확인하지 않은
암묵적 계약에 의존하고 있다는 것이다.
큰 정수, `undefined`, 객체 순서, `Date`, `Map` 각각의 사례는
전부 “JavaScript 안에서는 자연스럽게 성립하던 어떤 가정이
경계를 넘는 순간 근거를 잃는다”는 하나의 구조를 반복한다.
그래서 글의 결론이 항상 “이렇게 하지 마라”가 아니라
“이 상태를 스키마나 계약에 명시적으로 적어라”로 수렴한다.

### 왜 하필 지금 이 문제가 다시 불거지는가

JSON이 2001년에 나온 이래 이 변환 규칙 자체는 바뀐 적이 없다.
그런데 이 문제가 반복해서 회자되는 이유는 JSON이 다루는 값의 종류가
당시보다 훨씬 다양해졌기 때문이다.
마이크로서비스 아키텍처에서 서비스 간 경계를 넘는 페이로드가 늘고,
JavaScript 바깥의 언어(Go, Python, Rust)로 그 경계를 넘는 사례가
흔해지고, 데이터베이스 식별자가 64비트 정수로 발급되는 시스템이
늘면서, JSON이 처음 설계될 때는 드물었던 “안전한 정수 범위를 넘는
식별자”나 “타입이 살아있는 컬렉션을 그대로 넘기고 싶은 요구”가
일상적인 문제가 됐다.
즉 이 글이 다시 쓸모 있어진 것은 JSON이 변한 게 아니라
JSON이 짊어지는 데이터의 성격이 변했기 때문이다.

### 직렬화가 코드 실행이라는 재분류가 핵심이다

`toJSON()`, 게터, replacer를 다루는 절은 이 글에서 가장 중요한
전환점이다. 대부분의 개발자는 `JSON.stringify`를 순수한 데이터
변환 함수로 취급하지만, 저자는 이를 “임의의 JavaScript 코드를
실행하는 연산”으로 재분류한다.
게터가 예외를 던지면 직렬화가 실패하고, `toJSON()`이 부수 효과를
가지면 직렬화 횟수가 카운터를 바꾸며, replacer가 개입하면 출력이
눈에 보이는 필드만으로는 예측되지 않는다.
이 재분류가 중요한 이유는, 직렬화를 로깅이나 에러 리포팅 같은
“실패해서는 안 되는 안전한 경로”에 무심코 배치하는 실무 습관을
정면으로 반박하기 때문이다.

### 처방이 항상 명시적 계약으로 수렴하는 이유

다섯 가지 문제 각각에 대한 처방—정수는 문자열로, 순서는 배열로,
타입은 스키마로, 정준화는 별도 스킴으로—을 나란히 놓으면 공통된
설계 원칙이 보인다.
JSON의 관대함(무엇이든 일단 변환해서 유효한 텍스트를 만들어 낸다는
성질)을 프로그램이 신뢰해서는 안 되고, 대신 그 관대함이 삼켜버리는
정보를 애플리케이션 계층에서 명시적으로 다시 인코딩해야 한다는
것이다. 이는 결국 “포맷이 관대할수록 계약은 더 엄격해야 한다”는
일반 원칙의 특수 사례이며, 이 원칙은 JSON을 넘어 프로토콜 버퍼가
없는 대부분의 텍스트 기반 데이터 교환 형식에 그대로 적용된다.

## 비평

### 왕복 실패를 전부 같은 무게로 다룬다

글은 정수 반올림, `undefined` 소실, 순서 비보장, 타입 소실, 코드 실행이라는
다섯 문제를 구조적으로 병렬 배치하지만, 실제로 이들이 초래하는 피해의
크기는 서로 크게 다르다.
정수 반올림은 식별자를 다른 레코드로 오인시킬 수 있는 조용한 데이터
손상이고, 코드 실행 위험은 신뢰할 수 없는 객체를 직렬화할 때만
발현되는 조건부 위험이다.
반면 객체 순서 문제는 애초에 순서에 의미를 실은 설계 자체가 드물기 때문에
발생 빈도가 훨씬 낮다. 다섯 절을 같은 분량과 같은 어조로 배치하면
독자는 이들을 동등한 우선순위의 위험으로 받아들이기 쉽지만,
실무에서 정수 반올림 하나를 놓치는 사고와 순서 문제로 인한 사고의
발생 빈도와 파급력은 동급이 아니다.

### 처방의 비용을 이야기하지 않는다

“십진 문자열로 큰 정수를 넘겨라”, “타입을 스키마에 명시하라”는
처방은 옳지만, 그 처방을 실제로 적용하는 비용은 글에서 다뤄지지
않는다.
식별자를 문자열로 바꾸는 순간 그 값에 의존하는 모든 클라이언트
코드, 정렬 로직, 캐시 키 생성 로직을 함께 수정해야 하고, 이미
운영 중인 API의 응답 스키마를 바꾸는 것은 하위 호환성 문제를
동반한다.
글은 “이렇게 설계했어야 한다”는 사후적 관점에서만 서술하고,
이미 정수 ID로 설계된 기존 시스템을 어떻게 점진적으로 옮겨갈지에
대해서는 침묵한다.
이상적인 설계와 이미 존재하는 레거시 사이의 간극을 메우는 이야기가
빠져 있다.

### 제목이 JSON과 JavaScript의 책임을 뒤섞는다

Lobste.rs 토론에서 가장 많이 반복된 지적이 바로 이 지점이다.
byroot는 이 글이 다루는 문제 대부분이 JSON 포맷 자체가 아니라
JavaScript의 `JSON.stringify()` 명세가 내리는 결정이라고 짚었다.
`NaN`을 `null`로 바꾸는 것은 JSON의 제약이 아니라 JavaScript의
선택이며, Ruby는 같은 JSON을 통해 `BigInt`를 문제없이 왕복시킨다는
것이다.[^byroot]
noirscape도 비슷하게, JSON이 모든 부동소수점 값을 표현하지 못한다는
점을 빼면 나머지는 대부분 JavaScript 쪽의 놀라운 동작이라고
정리했다.[^noirscape]
글의 제목이 “JSON이 거짓말한다”고 말하지만, 실제로 거짓말을 하는
것은 JSON이라는 포맷이 아니라 그 포맷을 다루는 JavaScript의
구현 결정이라는 것이 이 비판의 핵심이다.
이 구분이 중요한 이유는, 문제의 소재를 포맷에 두느냐 언어 구현에
두느냐에 따라 처방이 완전히 달라지기 때문이다.
포맷의 문제라면 다른 포맷으로 옮겨야 하지만, 언어의 문제라면
같은 JSON을 Ruby나 Go처럼 다루는 다른 언어에서는 애초에 발생하지
않는다.

### 최신 JavaScript는 이미 일부 문제를 해결하고 있다

mitsuhiko는 이 글이 이미 시대에 뒤처졌다고 지적하며,
`JSON.parse`의 새 `context.source` 매개변수를 이용하면
안전한 정수 범위를 넘는 `BigInt`도 처리할 수 있음을 보여
줬다.[^mitsuhiko]
이 지적이 글의 논지를 완전히 무너뜨리지는 않지만,
“JSON은 원래 이런 것이다”라는 어조로 서술된 결함 중 일부가
사실은 플랫폼이 계속 메워 가고 있는 진행형 문제라는 점을
드러낸다.
글이 다섯 문제를 모두 영구적인 구조적 한계처럼 제시하는 것과
달리, 실제로는 그중 일부가 명세와 구현의 발전에 따라 이미
바뀌고 있거나 바뀔 수 있다.

### 대안 포맷과의 비교가 없다

글은 JSON의 결함을 촘촘히 나열하지만, 이 결함들 중 상당수가
이미 다른 직렬화 포맷(Protocol Buffers, MessagePack, CBOR)에서
스키마 기반으로 해결돼 있다는 사실은 언급하지 않는다.
큰 정수, 타입 보존, 순서 보장 문제는 애초에 스키마를 강제하는
포맷을 채택하면 상당 부분 사라진다.
글이 “JSON을 계속 쓰면서 계약을 명시하라”는 처방만 제시하고
“애초에 이 요구가 있다면 다른 포맷을 검토하라”는 선택지를 다루지
않는 것은, JSON을 기본값으로 고정한 채 문제를 완화하는 방법만
찾는 편향된 틀이다.

## 인사이트

### 왕복 손실은 스냅숏이라는 잘못된 기대에서 나온다

Lobste.rs의 fleebee는 이 모든 사례를 관통하는 한 문장을
남겼다. JSON을 JavaScript 상태의 무손실 스냅숏으로 취급하는 순간
문제가 시작되며, 서로 다른 데이터 모델 사이에는 항상 명시적
변환이 필요하다는 것이다.[^fleebee]
이 글이 나열한 다섯 가지 함정—정수, `undefined`, 순서, 타입,
코드 실행—은 사실 하나의 착각이 다섯 군데에서 드러난
증상이다.
JSON은 애초에 JavaScript의 상태를 그대로 보존하도록 설계된 적이
없는데, 개발자들이 `JSON.parse(JSON.stringify(x))`라는 왕복이
항등 함수처럼 동작하기를 기대하면서 이 착각이 반복된다.
이 인사이트가 유용한 이유는 다섯 개의 개별 사례를 외우는 대신
“경계를 넘는 모든 직렬화는 손실 변환이다”라는 단일한 정신 모델로
대체할 수 있게 해 주기 때문이다.

### 이 문제는 정적 타입 시스템으로도 완전히 막히지 않는다

TypeScript나 Zod 같은 런타임 검증 도구를 쓰는 팀은 이 문제가
자신과 무관하다고 생각하기 쉽지만 실제로는 그렇지 않다.
TypeScript의 타입은 컴파일 시점에만 존재하고 `JSON.stringify`가
실제로 무엇을 만들어 내는지를 검사하지 않으므로,
`interface User { createdAt: Date }`라고 선언해도 직렬화된 값은
여전히 문자열이고 타입 시스템은 이를 막지 못한다.
결국 이 문제는 타입 시스템의 표현력이 아니라 직렬화 경계에서
타입 정보 자체가 물리적으로 사라진다는 데서 온다.
즉 정적 타입은 컴파일 시점의 실수를 잡아 주지만, 런타임에 실제로
전선을 타고 넘어가는 바이트에 대해서는 아무 것도 보장하지 않는다는
것을 이 글이 반증한다.

### 이 함정은 관측 가능성 도구에도 그대로 상속된다

로깅, 트레이싱, 에러 리포팅 도구들은 대부분 객체를 JSON으로
직렬화해 저장하거나 전송하는데, 이는 곧 이 글이 지적한 모든 함정이
관측 가능성 파이프라인에도 그대로 나타난다는 뜻이다.
게터가 예외를 던지는 객체를 로그 페이로드에 넣으면 로깅 호출 자체가
실패해 정작 기록하려던 에러가 사라지고, 큰 정수 식별자가 로그
안에서 반올림되면 사고 조사 중에 실제와 다른 레코드를 추적하게
된다.
디버깅과 장애 대응이라는, 정확성이 가장 중요한 순간에 바로 이
직렬화 함정이 가장 자주 발동한다는 역설이 여기서 드러나며,
이는 글이 명시적으로 짚지 않은 이차적 파급 효과다.

### 스키마 진화의 역사가 이미 같은 문제를 겪었다

객체 순서, 타입 소실, 순환 참조라는 문제는 사실 JSON에 국한된
새로운 문제가 아니라, 프로토콜 버퍼 이전 세대의 직렬화
포맷(XML-RPC, SOAP)이 이미 한 번 겪고 스키마 강제라는 해법으로
수렴했던 문제의 재발이다.
XML 진영이 XSD로 타입과 순서를 명시적으로 강제하는 방향으로
진화했던 것과 마찬가지로, JSON 진영도 JSON Schema, Protocol
Buffers, 혹은 이 글이 권하는 “명시적 계약”으로 수렴하고 있다.
이는 데이터 교환 포맷이 성숙하는 경로가 대체로 “관대한 텍스트
포맷으로 시작해서 결국 스키마 강제로 회귀한다”는 구조적 패턴을
따른다는 것을 보여 주며, JSON은 그 순환의 또 다른 반복일 뿐이다.

### 큰 정수 함정은 앞으로 더 흔해질 것이다

64비트 스노우플레이크 ID, 블록체인 트랜잭션 해시, 타임스탬프
기반 마이크로초 단위 식별자처럼 안전한 정수 범위를 넘는 값을
발급하는 시스템이 늘어나는 추세를 감안하면, 이 글이 첫머리에
제시한 정수 반올림 함정은 앞으로 점점 더 자주 실무자를 덮칠
것이다.
문제는 이 함정이 개발 환경에서는 거의 재현되지 않는다는 점이다.
테스트 데이터의 ID는 대개 작은 정수이고, 안전한 정수 범위를 넘는
식별자는 프로덕션의 대규모 데이터에서만 자연스럽게 발생하기
때문에, 이 버그는 전형적으로 “로컬에서는 통과하고 운영에서만
간헐적으로 실패하는” 형태로 나타난다.
이는 이 함정이 단순한 지식 부족의 문제가 아니라, 테스트 환경과
운영 환경의 데이터 분포 차이가 만들어 내는 구조적 사각지대라는
뜻이다.
