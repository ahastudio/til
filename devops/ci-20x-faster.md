# CI를 20배 빠르게: 코딩 에이전트가 밀어 올리는 시대에 대기 시간부터 줄이는 아홉 가지

트윗: [How I made our CI 20x faster (steal this)](https://twitter.com/owengretzinger/status/2116291924219060319)

## 소개

Boardy의 엔지니어링 책임자 owen이 2026-10-31에 Twitter Article로 올린 글이다.
1년 전에는 풀 리퀘스트 하나가 CI를 기다리는 데 최대 40분이 걸렸고 지금은
2분이라고 한다.
이 일이 더 중요해진 이유는 모든 풀 리퀘스트를 코딩 에이전트가 쓰기 때문이다.
에이전트는 밀고, CI를 기다리고, 빨간 검사를 고치고,
다시 미는 일에 지치지 않는다.
코드를 쓰는 속도가 10배가 되었는데 CI가 그대로면 기다리는 대상은 CI가
된다는 논리이다.
글은 Amdahl의 법칙을 말하는 게시물을 끼워 넣어,
빠르게 만들지 않은 부분이 전체 속도의 상한을 정한다는 점을 보여 준다.

저자는 이 달에 CI를 제품처럼 다루었고, 작업의 대부분을 휴대폰으로 Slack의 사내
에이전트에게 시켜 했다고 한다.
글 앞부분에는 이 글을 에이전트에게 주고 같은 일을 시키라는 말이 있다.
이 문서는 그 글을 사람이 읽고 적용할 수 있는 순서로 다시 정리하고,
글에 없는 확인 방법과 반대 증거를 덧붙인다.
덧붙인 부분은 글이 아니라 필자의 것임을 구분해 적는다.

### 개선 내용

| 변경                                         | 전                                  | 후       |
| -------------------------------------------- | ----------------------------------- | -------- |
| GitHub 기본 러너 대신 다른 러너              | 기계를 얻는 데 최대 11분            | 8초      |
| ESLint 대신 Oxlint                           | 2분                                 | 5초      |
| tsc에서 TypeScript 7을 거쳐 bun check로      | 70초                                | 5초 미만 |
| 테스트 파일마다 워커를 따로 쓰던 것을 공유로 | 샤드당 100초                        | 35초     |
| 캐시를 main에서 미리 채움                    | 풀 리퀘스트 실행의 절반이 캐시 미스 | 1%       |

전체로는 러너 교체로 40분에서 약 10분이 되었고, 나머지는 아래의 변경이 줄였다.
비용은 월 230달러에서 4,300달러가 되었다고 한다.
시간은 40분에서 2분이므로 20배이고 비용은 약 18.7배이다.
뒤의 비율은 필자의 계산이며, 두 숫자가 같은 기준의 달인지는 글에 나와 있지 않다.

## 동작 방식

글의 구조는 대기, 준비, 실행 세 구간으로 나누어 각각을 줄이는 것이다.
기계를 기다리는 시간은 러너 교체가, 준비 시간은 캐시와 클론 방식과 설정 점검이,
실행 시간은 도구 교체와 샤딩과 병렬화와 변경분만 돌리기가 줄인다.
저자는 가장 눈에 띄지 않는 구간이 준비라고 말한다.
서버 테스트 job은 168초에서 74초가 되었는데 테스트 자체는 거의 바뀌지 않았고,
줄어든 것은 거의 전부 준비 시간이라는 것이다.

가장 큰 발견은 감사에서 나왔다.
최근 150번의 실행을 job별로 대기, 준비,
실행으로 나누게 했더니 테스트 job의 절반이 의존성 캐시를 못 쓰고 있었다.
GitHub는 풀 리퀘스트의 캐시를 그 브랜치 안으로만 한정하는데 main에서 미리 채워
두는 것이 없어서 대부분의 풀 리퀘스트가 차가운 상태로 시작했다.
이 문제는 1년 내내 있었지만, CI를 지켜보는 사람이 없었고 지켜보던 에이전트는
원인을 고치는 대신 재시도했다고 한다.

## 적용하기

### 1. 기본 러너를 벗어난다

GitHub의 호스팅 러너에서 기계를 얻는 데만 최대 11분이 걸렸다.
job마다 한 줄로 바꾸면 8초 안에 시작한다.

```yaml
runs-on: blacksmith-4vcpu-ubuntu-2204
```

저자는 Blacksmith를 쓰고 Vercel CI와 boat.dev 같은 대안도 있다고 한다.
가장 작은 job 두 개를 GitHub에 남겨 두었더니 그것들이 파이프라인에서 가장 느린
부분이 되었다.
5초짜리 job이 기계를 10분 기다리면 10분짜리 job이 되므로 작은 job도 모두
옮겨야 한다.

### 2. ESLint를 Oxlint로 바꾼다

린트가 2분에서 5초가 되었다.
에이전트는 엄격한 규칙에 짜증 내지 않으므로 켤 수 있는 규칙은 모두 켜라고 한다.

### 3. 더 빠른 타입 검사기가 나올 때마다 바꾼다

한 달 사이에 타입 검사기를 세 번 바꾸었다.
서버의 차가운 타입 검사는 tsc로 70초였고 TypeScript 7은 13초,
bun check는 5초 미만이라 CI는 bun check를 쓴다.
로컬에서는 tsrs가 0.6초라고 한다.
Slack의 사내 에이전트에 새 도구의 소식을 붙여 넣으면 6분 뒤에 저장소 기준의
벤치마크가 나오고, 20분 뒤에 병합되었다는 일화가 붙는다.

### 4. 테스트를 큰 기계에 샤딩한다

8분짜리 테스트 하나를 8 vCPU 기계 여섯 개의 샤드로 나누고 샤드마다 자기
데이터베이스를 준다.
샤드 수보다 기계의 크기가 더 중요했다.
각 샤드가 CPU 대부분을 모듈을 읽는 데 쓰고 테스트 실행에는 거의 쓰지 않았기
때문에, 샤드가 아니라 코어를 샀다.

### 5. 테스트 파일마다 앱을 다시 읽지 않는다

Vitest는 테스트 파일마다 새 워커를 주므로 파일마다 NestJS 앱 전체를
처음부터 읽었다.
`isolate: false`로 바꾸자 샤드마다 100초가 35초가 되었다.

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    isolate: false, // 파일끼리 모듈과 상태를 공유한다
  },
});
```

대가는 테스트가 서로 새는 것이다.
모든 파일 뒤에 상태를 초기화하는 훅을 넣고,
에이전트에게 테스트가 무엇을 정리해야 하는지 알려 주라고 한다.

### 6. 준비 단계를 고친다

세 가지가 더 있다.
`node_modules`를 캐시하면 복원이 13초이고 설치 33초를 대신한다.
얕은 클론이 아니라 `filter: blob:none`의 blobless 클론을 쓰는데,
얕은 클론은 git 기록을 읽는 것을 깨뜨린다.
체크아웃은 36초에서 12초가 되었다.
병렬도를 코어 수에 맞추는데, 4 vCPU job이 작업 8개를 동시에 돌리던 것을 절반으로
줄여도 빠르기가 같았고 불안정한 테스트 하나가 사라졌다.

### 7. 모든 검사를 동시에 돌린다

린트, 타입 검사, 빌드, 테스트를 한꺼번에 돌리면 풀 리퀘스트는 가장 느린
것만큼 걸린다.
그다음에는 가장 느린 job이 다른 일도 하고 있는지 본다.
첫 테스트 샤드가 마이그레이션 검사와 다른 앱의 테스트도 돌려서 늘 마지막에
끝났고, 그것을 별도 job으로 옮겨 2분을 줄였다.

### 8. 풀 리퀘스트가 건드린 것만 돌린다

`nx affected`로 바뀐 프로젝트만 테스트하고, main에서는 밤마다 전체를 돌린다.
건너뛰는 논리 자체도 시험해야 한다.
서버 변경을 일부러 Nx에게 숨겼더니 여섯 샤드가 모두 테스트를 건너뛰고 초록으로
보고했고, 이제는 그것이 실행 실패가 되게 했다.

### 9. 밀기 전에 검사한다

push 직전 훅이 바뀐 파일에 대해 포맷, 린트, 타입 검사를 9초 안에 돌린다.
에이전트가 타입 오류를 로컬에서 만나면 몇 초 안에 고친다.
AGENTS.md의 한 줄이 아니라 훅에 넣으라는 이유는 에이전트가 단계를
건너뛰기 때문이다.

## 트레이드오프

### 돈을 쓰는 방향으로 푼다

글은 비용을 숨기지 않는다.
월 230달러가 4,300달러가 되었지만 에이전트를 빠르게 만드는 데 쓰는 가장 싼
돈이라고 저자는 말한다.
글은 비슷한 처지의 두 사람의 게시물도 끼워 넣어,
CI 지출이 엔지니어링 팀의 병목이 되었다고 말한다.
이 방식은 팀이 CI 비용을 에이전트의 시간으로 환산할 수 있을 때 성립한다.
그렇지 않은 팀은 아래 항목, 곧 준비 단계의 점검부터 시작하는 것이 돈이 덜 든다.

### 캐시와 격리는 항상 이득이 아니다

저자는 `node_modules`를 캐시해 복원 13초로 설치 33초를 대신하게 했다.
반면 글이 인용하는 Linear의 글은 반대의 결론을 낸다.
복원이 약 28초 걸리는데 필터링한 설치는 약 7.5초여서 `node_modules` 캐시를
없앴다는 것이다.[^linear]
두 팀의 설치가 다르기 때문에 한쪽이 틀린 것이 아니라,
캐시 복원 시간과 설치 시간을 각자 재야 한다는 뜻이다.

`isolate: false`도 마찬가지이다.
저자는 이를 전역으로 바꾸고 모든 파일 뒤에 초기화 훅을 넣는다.
Linear는 이 변경이 가장 큰 단일 개선이었다고 하면서도,
파일마다 명시적인 옵트인 주석을 요구하고 가짜 타이머를 쓰거나 상태가 얽힌 파일은
격리된 프로젝트에 남겼다.[^linear]
Vitest 문서는 격리를 끄는 것이 부작용에 기대지 않는 코드에서만 안전하고,
일부 파일만 끄려면 프로젝트별로 설정하라고 안내한다.[^vitest]
전역으로 끄는 쪽이 간단하지만 새는 테스트를 찾는 비용이 뒤로 밀린다.

### 변경분만 돌리는 것은 검사를 건너뛰는 일이다

`nx affected`는 시간을 크게 줄이지만, 건너뛰는 논리가 틀리면 전부 초록으로
보고하는 사고가 난다.
저자는 그것을 직접 시험해 실패로 만들었다.
이 시험이 없으면 CI는 빠르지만 아무것도 검사하지 않는 상태가 된다.
밤마다 main에서 전체를 돌리는 것은 이 위험의 마지막 방어선이며,
그 사이에 머지된 변경의 오류는 하루 늦게 드러난다.

## 함정

- 가장 작은 job을 기본 러너에 남기면 그것이 파이프라인에서 가장 느려진다.
- 얕은 클론은 git 기록을 읽는 도구를 깨뜨린다.
- 에이전트는 CI를 지켜보다가 원인을 고치지 않고 재시도한다. 반복되는 실패는 사람이나 별도의 점검이 잡아야 한다.
- AGENTS.md에 적은 규칙은 에이전트가 건너뛴다. 지켜야 하는 단계는 훅으로 강제한다.
- 이 글의 러너 라벨은 특정 업체의 것이다. 그 업체를 쓰기 위한 사전 설정은 글에 나오지 않으므로 도입하기 전에 해당 업체의 안내를 따로 확인해야 한다.

## 확인하기

글의 감사, 곧 최근 실행을 대기와 준비와 실행으로 나누는 일은 직접 할 수 있다.
다음 스크립트는 `gh` CLI로 최근 실행의 job별 대기와 실행 시간의 중앙값,
가장 오래 걸리는 단계 열 개를 보여 준다.
이 스크립트는 필자가 쓴 것이고, 공개 저장소로 시험해 동작을 확인했다.
대기는 `started_at`에서 `created_at`을 뺀 값이고 실행은 `completed_at`에서
`started_at`을 뺀 값이다.

```python
#!/usr/bin/env python3
"""최근 워크플로 실행을 job별로 대기, 실행, 단계별 시간으로 나눠 보여 준다.

사용법: python3 ci_audit.py OWNER/REPO [실행 수=50] [워크플로 파일명]
필요: gh CLI(로그인 상태). 대기 = started_at - created_at, 실행 = completed_at - started_at.
"""
import json
import statistics
import subprocess
import sys
from collections import defaultdict
from datetime import datetime


def gh(path):
    out = subprocess.run(["gh", "api", path], capture_output=True, text=True, check=True).stdout
    return json.loads(out)


def ts(s):
    return datetime.fromisoformat(s.replace("Z", "+00:00"))


def main():
    repo = sys.argv[1]
    limit = int(sys.argv[2]) if len(sys.argv) > 2 else 50
    wf = sys.argv[3] if len(sys.argv) > 3 else None
    base = f"repos/{repo}/actions/" + (f"workflows/{wf}/runs" if wf else "runs")
    runs = gh(f"{base}?per_page={min(limit, 100)}&status=completed")["workflow_runs"][:limit]

    wait = defaultdict(list)   # job 이름 -> 기계를 기다린 초
    run = defaultdict(list)    # job 이름 -> 실제로 돈 초
    steps = defaultdict(list)  # (job, 단계) -> 초
    for r in runs:
        for j in gh(f"repos/{repo}/actions/runs/{r['id']}/jobs?per_page=100")["jobs"]:
            if not (j.get("started_at") and j.get("completed_at")):
                continue  # 건너뛰거나 취소된 job
            wait[j["name"]].append((ts(j["started_at"]) - ts(j["created_at"])).total_seconds())
            run[j["name"]].append((ts(j["completed_at"]) - ts(j["started_at"])).total_seconds())
            for s in j.get("steps", []):
                if s.get("started_at") and s.get("completed_at"):
                    steps[(j["name"], s["name"])].append((ts(s["completed_at"]) - ts(s["started_at"])).total_seconds())

    print(f"{len(runs)}개 실행, 값은 중앙값(초)")
    print(f"{'job':40} {'대기':>7} {'실행':>7} {'n':>4}")
    for name in sorted(run, key=lambda n: -statistics.median(run[n])):
        print(f"{name[:40]:40} {statistics.median(wait[name]):7.0f} {statistics.median(run[name]):7.0f} {len(run[name]):4}")
    print("\n가장 오래 걸리는 단계 10개")
    top = sorted(steps.items(), key=lambda kv: -statistics.median(kv[1]))[:10]
    for (job, step), v in top:
        print(f"{statistics.median(v):7.0f}  {job[:28]} / {step[:50]}")


main()
```

사용법은 `python3 ci_audit.py OWNER/REPO 150`이다.
대기가 큰 job은 러너를, 단계 목록에서 `Set up`, 체크아웃,
설치가 위에 있으면 준비를 의심한다.
캐시가 실제로 쓰이는지는 풀 리퀘스트 실행의 캐시 단계 로그에서 적중
여부로 확인한다.

## 체크리스트

- 풀 리퀘스트의 CI 대기 시간 중앙값을 지난 한 달 치로 알고 있는가.
- job의 대기, 준비, 실행을 따로 재어 보았는가.
- 가장 작은 job까지 모두 기본 러너 밖으로 옮겼는가.
- 의존성 캐시가 풀 리퀘스트 브랜치에서 적중하는지 확인했는가.
- 캐시 복원 시간이 설치 시간보다 짧은지 재어 보았는가.
- 린트, 타입 검사, 빌드, 테스트가 동시에 도는가.
- 건너뛰기 논리를 일부러 속여 보고 실패하는지 확인했는가.
- 반드시 지켜야 하는 검사가 AGENTS.md가 아니라 훅에 있는가.
- CI 비용의 한도와 그 근거가 있는가.

## 기억할 원칙

### 병목은 가장 보이지 않는 구간에 있다

저자의 가장 큰 발견은 새 도구가 아니라 측정이었다.
대기와 준비와 실행으로 나누자 1년 동안 있던 캐시 결함이 드러났고,
테스트 자체는 줄일 것이 거의 없었다.
20,000개의 테스트를 에이전트가 감사했지만 자를 만한 것이 거의 없었고 시간은
테스트에 있지 않았다는 것이다.
도구를 바꾸기 전에 시간이 어디에 쓰이는지부터 나누어 재는 것이 순서이다.

### 에이전트가 기다리는 곳에는 사람이 지켜봐야 한다

에이전트는 빨간 검사를 재시도로 넘기고, 규칙을 건너뛰고,
캐시 결함을 알아채지 못했다.
CI가 빨라져도 이 습관은 사라지지 않으므로,
반복되는 실패를 모으는 점검과 단계를 강제하는 훅이 사람의 눈을 대신해야 한다.
저자도 다음 병목을 병합 단추를 누르는 자신이라고 쓰는데,
같은 이유로 사람이 보는 구간은 마지막까지 남는다.
