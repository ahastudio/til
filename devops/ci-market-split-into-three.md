# CI 시장은 세 갈래로 나뉘었다

원문: [The CI market has split into three — Console Analysis](https://console.dev/analysis/the-ci-market-has-split-into-three)

GN 토론: <https://news.hada.io/topic?id=37320>

## 요약

개발자 도구 뉴스레터 Console의 분석 글로, 2026년 11월 9일에 올라왔다.
이 문서는 글 전문과, 글이 링크한 업체의 공식 자료 일부(아래 각주)를 읽었다. 업체 자료의 수치와 주장은 해당 업체가 말한 것이고 이 문서가 검증한 것이 아니다. 글이 말하는 48개 CI 업체의 전체 평가표는 열람이 일부(카테고리 페이지의 한 항목)에 그쳤다.

필자의 주장은 CI가 더는 하나의 시장이 아니고 세 하위 범주로 나뉘었다는 것이다.

- 범용 러너 인프라: 더 빠르거나 싼 GitHub Actions이다.
- 오케스트레이션 플랫폼: 제어판은 업체가 주고 컴퓨팅은 고객이 댄다.
- 코드와 빌드 엔지니어링 계층: CI 위에서 더 프로그래밍 가능한 빌드 파이프라인을 제공한다.

글의 전개는 이렇다.

- GitHub Actions가 중심이다. 생태계(커뮤니티 액션과 통합)가 압도적이고, 최고라서가 아니라 PR과 알림과 추적에 통합되어 있어 선택된다. 그러나 속도와 디버깅 용이성의 근본 문제와 2026년의 신뢰성 문제로 해자가 얇아지고 있다.
- 전환 비용이 GitHub를 지켜 왔지만 첫 번째 범주가 이를 깎는다. Blacksmith와 WarpBuild와 Depot와 Namespace는 모두 워크플로는 그대로 두고 러너만 바꾸라고 제안하며, YAML 형식이 표준이 되고 러너가 범용 상품이 되었다는 신호라고 한다. 차별화는 Blacksmith의 베어 메탈, Namespace의 NVMe 캐싱, Depot의 초 단위 과금이고 이 범주가 가장 붐빈다.
- 2026년 이전에는 이것으로 충분했으나 에이전트가 병목이 속도만이 아니라 디버깅 용이성임을 드러낸다. Actions는 이 점에서 약하다(act 같은 도구가 있어도). 새 액션은 푸시하고 기다리는 방식으로 만들게 된다. 흥미로운 기능은 원시 속도가 아니라 Buildkite의 불안정 테스트 음소거와 Test Engine, Depot의 디버깅 가능한 인스턴스, Nx의 자가 치유 CI, Dagger와 Nx가 같은 검사를 로컬에서 돌리는 것이다. 에이전트가 쓰면 CI의 지연과 불안정은 에이전트의 유휴 시간이고 실패한 빌드는 구조화된 맥락이 필요한 기계가 소비한다.
- 필자가 흥미롭게 보는 쪽은 Buildkite와 Dagger와 Nx이다. 진짜 빌드 구성 요소와 로컬 러너로 에이전트가 모든 것을 관리하고, CI는 테스트 러너에서 에이전트가 이미 로컬에서 다 돌린 뒤 운영 반영 전에 다시 확인하는 최종 관문이 되어야 한다고 한다.
- 이것은 러너와 짝이 되어야 한다. 현대적 패턴은 제어면과 데이터면의 분리로, 업체가 조율하고 컴퓨팅은 고객 클라우드에서 돈다(스폿 가격, VPC 접근, 맞춤 하드웨어, 자본 지출 선호). WarpBuild는 AWS와 Azure와 GCP에서, Depot는 AWS에서만 이를 한다.
- 보안도 구매 기준이 된다. Actions는 액션이 기본으로 고정되지 않고 권한이 넓고 비밀 범위가 느슨한 함정이 있어 Shai-Hulud의 확산과 tj-actions/changed-files 공격에 악용되었다.
- 필자의 내기는 러너 업체가 당분간 GitHub 난민을 흡수하지만 근본 문제를 풀지 못한다는 것이다. 진짜 해법은 에이전트 네이티브 CI이고 Dagger와 Nx와 Buildkite가 오래 살아남는다면 그쪽이거나 아직 없는 무언가라고 한다.
- 공시: Buildkite와 WarpBuild와 Depot가 Console 뉴스레터에 광고한 적이 있으나 이 분석을 후원하지 않았다고 한다.

## 세 범주를 업체 자료로 채우기

글은 범주 이름만 주고 각 업체가 무엇을 하는지는 링크로 넘긴다. 이 절은 링크된 공식 자료에서 확인한 내용을 범주별로 모았다.

### 범주 1: 러너는 왜 상품이 되었고 어디서 갈리나

Blacksmith는 자신을 CI 클라우드라고 부른다. 2026년 10월 21일 Sequoia가 이끄는 시리즈 C로 기업 가치 10억 달러에 누적 1억 2천 5백만 달러를 모았다고 발표하며 이렇게 쓴다. 1월 이후 주간 CI 작업이 500만 건에서 9,000만 건 넘게 늘었고 ARR이 17배 늘었으며, 미국과 유럽의 데이터센터에서 10MW 가까운 컴퓨팅을 운영하고 2027년에 5배로 늘릴 계획이다. CI는 한 고객의 수요가 0에서 수만 CPU로 뛰었다 돌아오는, 회사가 돌리는 가장 들쭉날쭉한 워크로드라고 한다. 이 글은 Anthropic이 지난달 CI 작업량이 6개월 사이 25배 늘었다고 썼다고 인용한다.[^blacksmith-c]
이 숫자들은 한 업체의 투자 유치 발표이고, 필자가 말한 소음이 큰 첫 범주(Blacksmith와 Depot가 개발자 커뮤니티 어디에나 있고 큰 투자를 받는다)를 업체 쪽에서 확인해 주는 자료이다.

Depot는 Docker 이미지 빌드의 느림(멀티 플랫폼 이미지 빌드가 GitHub Actions에서 45분)에서 출발해 5배 빠른 시제품으로 시작했다고 쓴다. 시리즈 A 발표(1천만 달러, Felicis와 Y Combinator와 Pioneer Fund)에서 병목이 코드 작성에서 통합으로 옮겨 갔다고 주장하고, 소스 컨트롤과 CI와 코드 리뷰와 코드가 쓰이는 곳과 격리된 맥락을 병목으로 든다. 러너와 로컬 빌드와 원격 캐시와 에이전트 샌드박스에 이어 자체 CI 시스템 Depot CI를 곧 낼 예정이라고 한다. GitHub Actions 워크플로를 그대로 가져와 더 빠르고 안정적으로 돌리지만 호환성은 여러 프런트엔드 중 하나라고 한다.[^depot-a]
글이 말한 러너 범주가 러너만으로 머물지 않고 위쪽(자체 CI 엔진)으로 올라가려는 움직임이 업체 자료에서 보인다. 이는 이 문서의 관찰이다.

### 범주 2: 제어면과 데이터면의 분리는 실제로 무엇인가

WarpBuild의 자체 클라우드 가져오기(BYOC) 문서는 세 단계를 적는다. 클라우드 계정을 연결해 필요한 권한의 IAM 역할을 만들고, 리전과 VPC와 네트워크 설정을 담은 스택을 만들고, 인스턴스 유형과 디스크와 IP 설정을 담은 커스텀 러너를 만든다. AWS, GCP, Azure를 지원하고 고정 IP와 대기 디스크와 커스텀 VM 이미지, 서비스 역할을 쓸 수 있다고 한다.[^warpbuild-byoc]
글이 말한 제어면과 데이터면의 분리가 문서에서는 고객 계정의 IAM 역할과 VPC에 러너를 두고 업체가 관리하는 구조로 나타난다. 이 구조의 비용과 위험(업체가 고객 클라우드에 갖는 권한)은 문서가 다루지 않는다.

### 범주 3: 빌드 계층이 말하는 에이전트 친화성

Dagger는 자신을 Jenkins와 GitHub Actions 다음의 3세대 CI라고 부른다. 모든 코드 변경(기계가 쓴 것이든 사람이 쓴 것이든)을 푸시 전이나 후에 같은 빌드와 테스트 파이프라인에 통과시키고, 툴체인을 감지해 공식 모듈을 권하며, 모듈이 고유 YAML 대신 프로젝트의 기본 설정을 읽는다. 결과물은 소스와 컨테이너와 바이너리와 테스트까지 타입이 있는 산출물로 발견되고, 필요할 때 늦게 계산되는 샌드박스 함수의 증분 DAG로 내 컴퓨터나 공유 원격 엔진에서 돈다. 샌드박스와 스케줄러와 컨테이너 런타임과 빌드 캐시와 추적이 하나의 실행과 데이터 모델을 공유해서 구성 요소가 각각 사일로인 2세대 CI보다 컴퓨트와 토큰 효율이 높다고 주장한다(문서는 1.0 베타 버전).[^dagger]

Buildkite의 Test Engine은 테스트 상태를 활성, 음소거, 건너뜀으로 관리한다. 음소거된 테스트는 계속 돌지만 실패가 빌드 결과에 영향을 주지 않고 실행 데이터를 계속 모아 다시 믿을 만해지는 때를 감지하므로 권장되고, 건너뜀은 실행 데이터가 없어 회복을 알 수 없어 꼭 필요할 때만 쓰라고 한다. 자동 격리는 Enterprise 플랜에서만 설정할 수 있고, 클라이언트 bktec이 격리된 테스트의 실패로 빌드를 실패시키지 않게 하거나 테스트를 제외한다.[^buildkite]
글이 말한 불안정 테스트 음소거가 실제로는 요금제에 따라 기능 범위가 갈리는 제품 기능임을 보여 준다.

Nx Cloud의 자가 치유 CI는 AI로 CI 실패를 감지하고 분석해 수정안을 제안한다. 프로젝트 그래프와 메타데이터로 작업 공간 구조를 이해하고, PR 댓글이나 편집기에서 알려 주며, GitHub와 GitLab과 Azure DevOps와 Bitbucket 연동이 필요하고 기존 CI 공급자 위에서 동작한다고 한다. 설정은 파이프라인 끝에서 `nx fix-ci`를 이전 단계가 실패해도 항상 실행하는 조건으로 돌리는 것이다.[^nx]
이는 글의 두 번째 범주와 세 번째 범주가 서로 배타적이지 않다는 점도 보여 준다. Nx는 기존 CI 러너 위에 얹는 계층이다.

### 범주 밖: 클라우드 사업자 제품

Console의 CI 카테고리 목록에서 열어 본 한 항목(AWS CodeBuild)은 AWS 신원과 VPC와 로깅에 연결되어 팀이 이미 운영하는 권한과 인프라 안에서 일하고, Lambda와 관리형 머신과 예약 EC2 같은 여러 실행 선택지가 있다고 한다. 단점은 AWS 자체로, 강력하지만 복잡하고 드롭인 러너 서비스보다 접근성이 낮으며, 이미 AWS에 배포하는 팀이 정당화하기 쉽다는 평이다. 이 평가는 Console의 것이다.[^console-cat]
세 범주의 분류에 클라우드 사업자의 빌드 서비스가 어디에 들어가는지는 글이 말하지 않는다.

## 보안 함정은 어떤 사건이었나

글은 Actions의 함정이 이미 악용되었다고 두 사건을 든다.

- tj-actions/changed-files 공격: GitHub 보안 권고에 따르면 2025년 3월 14~15일에 걸쳐 이 액션이 침해되어 2만 3천 개가 넘는 저장소에 영향을 주었다. 공격자가 여러 버전 태그가 악성 커밋을 가리키도록 사후에 바꿔, CI/CD 비밀이 워크플로 로그에 노출되었다. 패치된 버전은 46.0.1이다.[^tj-actions]
- Shai-Hulud: 글은 GitHub 블로그의 공급망 보안 글을 링크하나 이 문서는 그 글을 열지 못했다(내용 없이 로드됨).

두 사건이 가리키는 공통점은 가변 태그와 같은 참조 방식과 CI에 주어진 넓은 권한이다. 태그가 사후에 바뀔 수 있다는 점이 첫 사건의 핵심이었다. 글이 말한 액션이 기본으로 고정되지 않는다는 함정과 맞아떨어진다. 이는 이 문서의 연결이다.

## 분석

### 중심 주장은 러너가 범용 상품이 되었고 차별화가 다른 층으로 옮겨 간다는 것이다

워크플로 형식(YAML)이 표준이 되면 러너는 바꿔 끼울 수 있는 상품이 된다는 논리이다.
업체 자료가 이를 뒷받침하는 방식이 흥미롭다. 러너 업체인 Depot가 러너에서 자체 CI 엔진으로 올라가겠다고 밝혔고, Blacksmith는 CI 클라우드라는 이름으로 컴퓨팅 규모를 키운다. 러너 범주 안에서도 한쪽은 위로, 한쪽은 규모로 차별화한다.

### 에이전트가 CI의 요구를 바꾼다는 것이 글의 새로운 축이다

사람이 코드를 쓸 때는 CI의 지연이 사람의 대기 시간이었지만 에이전트가 쓰면 유휴 시간이고 실패 로그는 구조화된 맥락이 필요하다는 서술이다.
업체들의 서술도 같은 방향이다. Blacksmith는 CI 작업량의 폭증을, Depot는 병목이 통합으로 옮겨 갔다는 점을, Dagger는 에이전트의 속도에 맞춘 3세대 CI를 말한다. 이는 한 방향으로 모이는 마케팅 메시지이기도 해서 신호와 선전을 구분하기 어렵다.

### 이 저장소의 다른 문서와의 연결

이 저장소의 `devops/linear-ci-bottleneck.md`는 Linear가 에이전트 때문에 CI가 병목이 되어 직접 고친 사례를 다루고, `devops/ci-20x-faster.md`는 CI를 20배 빠르게 만든 방법을 다룬다.
둘 다 도구를 바꾸기보다 파이프라인 내부를 고친 사례이고, 이 글의 분류에서는 러너 교체(범주 1)가 아닌 다른 길이다.

## 비평

### 결론이 근거보다 앞서 있다

필자는 에이전트 네이티브 CI가 진짜 해법이라고 내기하지만 이를 지지하는 전환 사례나 비용과 실패율 데이터는 글에 없다.
러너 업체가 가장 많이 보이고 투자를 받는다는 관찰은 시장 점유가 아니라 소음에 근거한다고 필자 스스로 쓴다.
업체 자료도 이 문제를 풀어 주지 않는다. Blacksmith의 90배 성장 수치는 한 업체의 것이고, Dagger는 아직 1.0 베타이다.

### 범주의 경계가 겹친다

Depot는 러너(초 단위 과금)이면서 디버깅 가능한 인스턴스와 자체 CI 엔진과 AWS 자체 클라우드 쪽에도 나오고, Nx는 빌드 계층이면서 기존 CI 위에 얹는 자가 치유 서비스이고, Dagger는 빌드 계층이면서 스스로를 CI의 다음 세대라고 부른다.
세 범주가 서로 배타적이지 않은데 글은 한 업체가 여러 범주에 걸치는 경우를 정리하지 않는다.

### 이해 관계와 인용의 한계

필자는 Buildkite와 WarpBuild와 Depot가 Console에 광고한 적이 있다고 공시하나 독립적으로 썼다고 한다. 이 문서가 확인할 수 있는 것은 공시 문장뿐이다.
업체 자료는 모두 업체의 목소리이다. 이 문서의 보강 절은 이를 교차 검증하지 못했고 글이 링크한 GitHub의 2026년 8월 가용성 보고서는 열지 못했다(내용 없이 로드됨). 그래서 GitHub 신뢰성 문제의 정도는 확인하지 못했다.

### 외부 반응

HN에서는 글의 주소와 제목으로 스레드가 검색되지 않았고, Lobste.rs에서는 도메인(`console.dev`)에 이 글이 올라온 적이 없다(다른 글 하나만 있음).
GeekNews에는 토픽이 있으나 댓글이 없었다.
그래서 이 글의 주장은 독자의 검토를 거의 거치지 않았다.

## 인사이트

### 가져갈 것은 CI 도구를 고를 때의 질문이다

러너를 바꿀 것인지, 파이프라인을 로컬에서 같은 방식으로 돌릴 수 있게 바꿀 것인지, 아니면 기존 CI 위에 실패 처리를 얹을 것인지를 먼저 가르는 것이다.
전자는 비용과 속도를 줄이고, 두 번째는 에이전트와 사람이 푸시 없이 검증하는 비용을 줄이며, 세 번째는 실패 수정의 사람 개입을 줄인다. 세 선택은 서로 겹치므로 하나를 고르고 나머지를 포기하는 문제가 아니다.

### 제어면과 데이터면을 가를 때 따질 것

업체가 고객 계정에 갖는 IAM 권한의 범위, 러너가 도는 VPC의 네트워크 경계, 업체 장애 시 폴백이 무엇인지가 점검 항목이다.
스폿 가격이나 맞춤 하드웨어 이득은 이 위험을 감수할 때 얻는다는 점을 글은 이득만 적는다.

### 보안 점검 목록은 바로 쓸 수 있다

가변 태그 대신 커밋 해시로 액션을 고정하고, 워크플로 권한을 최소로 두고, 비밀의 범위를 좁히는 것은 어떤 러너를 쓰든 점검할 항목이다.
tj-actions 사건처럼 태그가 사후에 바뀌는 경로를 닫는다. 에이전트에게 더 많은 접근을 주기 전에 이를 점검하라는 요지이다.

### 확인할 관찰

이 글의 주장을 가를 관찰은 네 가지이다.
GitHub Actions에서 러너 업체로 옮기는 팀이 실제로 늘었는지(업체의 성장 수치 말고 이전 수),
Depot CI 같은 러너 업체의 자체 CI 엔진이 채택을 얻는지,
Dagger와 Nx와 Buildkite 같은 프로그래밍 가능한 빌드 계층이 에이전트 시대에 살아남는지,
에이전트가 로컬에서 돌린 결과를 CI가 최종 관문으로만 다루는 구성이 실제로 퍼지는지이다.
넷 모두 이 문서가 확인하지 못했다.
