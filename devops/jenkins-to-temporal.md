# Jenkins 배치 220개를 Temporal로 옮기며: 개발팀이 신경 쓰지 않아도 되는 것을 정하는 이관

원문: [Jenkins 배치 220개를 Temporal로 옮기며 고민한 것들](https://tech.inflab.com/20261009-jenkins-to-temporal/)

## 요약

인프랩(인프런)의 데브옵스 담당 제이스(Jace)가 2026년 10월 20일에 쓴 글이다.
계기는 Jenkins의 디스크가 가득 차 배치가 멈춘 사고다.
빌드 이력 보존 설정(`logRotator`)이 빠진 잡들의 이력이 쌓여 디스크가 찼고, 그 사이 큐에는 배치가 3,000건 가까이 밀렸다.
밀린 배치를 그대로 실행하면 사용자 알림이 엉뚱한 시점에 나갈 수 있어서, 큐를 전부 비우고 다시 돌려야 할 배치를 개발자들이 골라 수동으로 실행했다.

기존 구조는 서비스마다 개발과 운영 Jenkins를 하나씩 띄워 EC2 12대에서 각각 단독으로 돌리는 방식이었다.
잡 220개가 하루에 약 15,900번 실행됐고, Groovy로 쓴 잡이 배치 이미지를 `docker run`하거나 서비스의 배치용 API를 `curl`로 호출했다.
글은 문제를 세 가지로 나눈다.
한 번 멈추면 모든 배치가 멈추는 구조(거의 분기마다 디스크 문제, 2024년 10월에는 플러그인 의존성 충돌로 Jenkins가 아예 뜨지 않음), 실패해도 모르는 배치(알림을 잡마다 설정하다 보니 한 잡은 중간 단계가 계속 실패했는데 마지막 단계가 성공해 알림이 한 번도 오지 않음), 평소에는 놀고 몰리면 부족한 서버(호스트별 평균 CPU 사용률은 배치가 몰린 2대를 빼면 6% 미만)다.

대안으로는 Argo Workflows와 Temporal을 검토했다.
Argo Workflows는 개발팀이 YAML과 GitOps 저장소 방식을 새로 배워야 해서 Groovy를 벗어나려다 또 다른 DSL을 배우는 셈이라고 판단했다.
Temporal은 워크플로를 일반 프로그래밍 언어로 쓰고, 실행 상태와 이력이 DB에 기록되며, 기존 배치 이미지를 그대로 쓸 수 있다는 점에서 골랐다.
서버는 EKS에 직접 띄우고 상태 저장소는 기존 Aurora PostgreSQL에 DB를 추가해 별도 비용이 들지 않게 했다.

설계는 두 번 바뀌었다.
처음에는 서비스 저장소에 잡 정의 YAML만 두고 데브옵스팀이 운영하는 범용 워커가 읽어 실행하게 했지만, 새 흐름이 필요할 때마다 스키마를 늘려야 해서 또 하나의 DSL이 되었다.
그래서 각 서비스 저장소의 `batch/` 디렉터리에 서비스별 워커를 두고, 데브옵스팀은 공통 부품을 TypeScript 라이브러리로 제공하는 구조로 바꿨다.
라이브러리는 `defineSchedule`(스케줄을 코드로 정의하고 워커 기동 시 서버와 동기화), `runContainer`와 `runHttp`(배치 이미지를 Kubernetes Job으로 실행하거나 API 호출), `alertOnFailure`(최종 실패 시 Slack 알림)를 제공한다.

이관하면서 중요하게 본 것은 개발팀 작업 최소화, 실패 알림 보장, 중복 실행 방지, 멈춤 감지, 실행 추적이다.
알림 발송은 배치 실행과 분리된 별도 Activity라서 Slack이 잠시 응답하지 않아도 배치를 처음부터 다시 돌리지 않는다.
중복 실행은 Job 이름을 Run ID와 시도 번호로 만들고, 이전 시도의 Job이 돌고 있거나 성공했으면 새로 만들지 않고 이어서 감시하게 해서 막는다.
Kubernetes 쪽 재시도(`backoffLimit`)는 0으로 두어 시도 횟수를 Temporal에서만 관리한다.
멈춤은 모든 단계의 타임아웃과 heartbeat로 잡고, 워커가 모두 내려가 실행 자체가 없는 경우는 Temporal 메트릭에 알림을 걸어 본다.
서버가 멈췄다 뜬 뒤에는 기본값(1년 전 실행까지 따라잡기)을 쓰지 않고 예정 시각이 1시간 이내인 실행만 따라잡게 했다.
로그는 Datadog에 보내고, Job 파드의 `ad.datadoghq.com/tags` 애노테이션과 워커 로그 속성에 같은 실행 ID를 넣어 한 실행의 로그를 한 번에 찾게 했다.

이관은 Jenkins와 Temporal을 함께 운영하면서 서비스별 잡 단위로 진행한다.
서비스마다 Temporal namespace를 만들었고, 데브옵스팀은 이관 가이드와 복사해 쓸 예제를 만들었으며, 라이브러리 새 버전을 배포하면 사용하는 저장소마다 업데이트 PR이 자동으로 올라간다.
전환할 때 가장 조심한 것은 같은 배치가 양쪽에서 함께 도는 일이었고, 스케줄의 활성 상태를 코드로 관리하면 UI에서 멈춘 상태가 워커 재시작 때 되돌아가는 문제가 있어서 새 스케줄은 항상 일시정지로 등록하고 실행 여부는 Temporal UI에서만 정하도록 바꿨다.
이관 도중에는 Karpenter가 노드를 줄이며 배치 파드를 내보내 배치가 실패하는 일이 있었고, 배치 파드에 `karpenter.sh/do-not-disrupt` 표시를 붙여 해결했다.
글은 Jenkins EC2를 모두 내리면 배치 시스템 비용이 절반 넘게 줄고, 잡 정의가 코드가 되어 PR 리뷰와 롤백이 가능해지며, 실행 이력은 DB에 30일 보존된다고 정리한다.
대신 개발팀이 Temporal 개념과 Datadog 검색을 새로 익혀야 하고 구조는 더 복잡해졌다고 인정한다.

## 분석

### 선택보다 기본값이 이 글의 중심이다

글의 마지막 문단은 이번 이관에서 가장 오래 고민한 것이 Temporal을 고르는 일이 아니라 개발팀이 무엇을 신경 쓰지 않아도 되게 할지 정하는 일이었다고 말한다.
Jenkins에도 Slack 알림을 보내는 공용 Groovy 라이브러리가 있었지만, 언제 알림을 보낼지는 잡마다 직접 설정해야 했고 그래서 빠뜨린 잡이 생겼다.
라이브러리가 있었는데도 사고가 난 이유는 라이브러리가 선택 사항이었기 때문이다.
새 구조에서는 실행 함수가 알림, 취소 시 정리, 타임아웃과 heartbeat를 함께 가진다.
잡을 옮기면 이 보장이 따라오고, 빠뜨리려면 일부러 우회해야 한다.

이 구조가 바꾸는 것은 누가 책임을 지는가다.
220개 잡이 각자 알림을 설정할 때 알림 누락은 잡 담당자의 실수였지만, 라이브러리가 알림을 보장하면 누락은 라이브러리의 결함이 된다.
책임이 220곳에서 한 곳으로 모이는 만큼 그 한 곳의 품질이 전체를 결정한다.

### 또 하나의 DSL을 피하려는 과정이 세 번 나온다

글에서 같은 모양의 판단이 세 번 반복된다.
Argo Workflows는 Groovy를 벗어나려다 YAML이라는 또 다른 DSL을 배우게 된다는 이유로 접었다.
데브옵스팀이 YAML 스키마를 정의하고 범용 워커가 읽는 방식은 새 흐름이 필요할 때마다 스키마를 늘려야 해서 결국 또 하나의 DSL을 만드는 일이라고 판단해 접었다.
최종안은 서비스 저장소 안에 TypeScript 워커를 두는 것이다.

이 판단의 공통점은 설정 언어가 표현력을 조금씩 늘리다가 결국 프로그래밍 언어가 된다는 관찰이다.
처음부터 일반 프로그래밍 언어를 쓰면 표현력의 한계에 부딪히지 않지만, 그 대가로 잡마다 코드를 쓰는 부담이 개발팀에 돌아온다.
글은 이 부담을 라이브러리와 예제, 이관 가이드로 줄인다고 답한다.

### 재시도와 중복 실행을 한 층에서만 다룬다

배치는 두 번 돌면 안 되고 한 번도 안 돌면 안 되는데, 이 둘은 서로 반대 방향의 요구다.
글의 해법은 책임을 층별로 나누는 것이다.
시도 횟수의 권한은 Temporal에만 두고 Kubernetes `backoffLimit`은 0으로 둔다.
Job 이름을 실행 ID와 시도 번호로 만들어 같은 시도를 다시 만들 일이 없게 하고, 있으면 이어서 감시한다.
실행이 없는 상황은 워크플로 안에서 잡지 못하므로 서버 메트릭 알림으로 따로 본다.

각 방어는 다른 방어가 놓치는 틈을 메운다.
재시도 권한을 한 층에 두는 것은 재시도가 층마다 곱해져 시도 횟수가 예측 불가능해지는 일을 막는다.
이관 중 발생한 Karpenter 사건은 이 선택의 대가를 보여 준다.
Kubernetes 쪽 재시도를 0으로 두었기 때문에 노드 축소로 파드가 내보내지면 그 시도가 곧바로 실패였다.

### 스케줄의 상태를 누가 소유하는가

스케줄의 활성 상태를 코드에서 관리하면 UI에서 멈춘 상태가 워커 재시작 때 되돌아가고, UI 값을 우선하면 코드와 실제 상태가 어긋난다고 글은 설명한다.
두 가지 모두 한쪽이 상태를 소유해야 하는데 둘 다 소유하려 하면 충돌한다는 문제다.
최종 선택은 소유자를 나누는 것이다.
스케줄의 존재와 설정은 코드가, 실행 여부는 UI가 소유한다.
새 스케줄은 항상 일시정지로 등록되므로 배포가 곧바로 배치를 켜지 않는다.

이 선택은 전환기에 중요한 안전장치다.
같은 배치가 Jenkins와 Temporal에서 동시에 도는 일을 막으려면 켜는 행위가 배포와 분리되어야 한다.

## 비평

### 비용 절감은 아직 측정이 아니라 전망이다

글은 Jenkins EC2를 모두 내리면 배치 시스템 비용이 절반 넘게 줄어든다고 쓴다.
이 문장은 조건문이고, 글의 끝에서 아직 Jenkins에 남은 잡이 있어 모두 옮기면 EC2를 내릴 예정이라고 밝히므로 지금은 전망이다.
기준 금액도, 절감된 금액도 나오지 않는다.

비교 대상도 선택되어 있다.
Temporal 상태 저장소는 기존 Aurora PostgreSQL에 DB를 추가해 별도 비용이 들지 않는다고 하는데, 이는 이미 있는 데이터베이스에 부하와 용량을 얹는 것이므로 비용이 사라진 것이 아니라 다른 항목으로 옮겨 간 것이다.
데브옵스팀이 Temporal 서버를 직접 운영하고 라이브러리를 유지하는 시간도 비용에 들어 있지 않다.
절반이라는 숫자는 서버 비용만 본 것으로 읽어야 한다.

### 서비스 규모에 비해 무거운 해법인지 따져 보지 않았다

검토한 대안은 Argo Workflows와 Temporal 둘이다.
글이 소개하는 예제에서 Jenkins의 `docker run` 잡 대부분이 `containerOnly` 워크플로 하나로 옮겨진다고 한다.
컨테이너를 한 번 실행하고 실패하면 알리는 잡이 대부분이라면, 내구성 있는 실행이라는 Temporal의 핵심 장점이 쓰이는 잡이 얼마나 되는지 글에서 알 수 없다.

글이 라이브러리에서 직접 구현한 것들, 즉 이름으로 구분하는 Job 중복 방지, 재시도 권한 정리, heartbeat 기반 멈춤 감지는 모두 Temporal 위에서 필요해진 장치다.
Kubernetes의 CronJob이나 Argo의 CronWorkflow에 알림 계층을 붙이는 방법은 검토 대상에 없고, 왜 제외했는지도 적혀 있지 않다.
이는 Temporal이 틀린 선택이라는 뜻이 아니라, 선택의 근거가 두 후보 사이의 비교에 한정되어 있다는 뜻이다.

### 운영 책임의 이동이 한 줄로 지나간다

서버는 데브옵스팀이 운영하고 각 팀은 워커를 운영하면서 Temporal의 규칙을 지켜야 한다고 글은 쓴다.
Jenkins에서는 한 곳이 멈추면 서비스 전체 배치가 멈췄지만, 이제는 서비스 저장소마다 워커가 있고 워커가 내려가면 그 서비스의 배치가 시작되지 않는다.
이를 잡는 장치로 작업을 가져갈 워커가 없을 때 쌓이는 메트릭과 스케줄 실행 성공 횟수에 알림을 건다고 한다.

그러나 그 알림을 누가 받고 새벽에 누가 대응하는지는 글에 없다.
워커가 개발팀 저장소에 있다면 워커 장애의 첫 대응자는 개발팀이고, 그 팀이 Temporal을 새로 배우는 중이라는 점은 글이 스스로 인정한 부담이다.
책임의 경계를 라이브러리 버전 업데이트 PR로 관리한다는 설명만으로는 이 공백이 채워지지 않는다.

### 이관의 성공 기준이 보이지 않는다

글에는 이관한 잡이 몇 개인지, 이관한 뒤 실패 알림이 몇 건 왔고 그중 몇 건이 실제 장애였는지, 이관 전과 같은 결과를 냈는지 확인한 방법이 없다.
Jenkins 문제는 거의 분기마다 반복됐다고 하면서 Temporal 도입 후의 신뢰성은 수치로 제시하지 않는다.
이관 담당자가 환경 변수, IAM 권한, 잡 파라미터를 확인한다고 했지만 이는 점검 항목이지 성공 기준은 아니다.
이 글은 설계의 근거를 설명하는 글이므로 이를 요구하는 것이 과할 수도 있지만, 설계의 가치를 판단하려면 필요한 정보다.

## 인사이트

### 기본으로 보장하는 구조는 라이브러리를 단일 장애점이자 단일 통제점으로 만든다

알림, 멈춤 감지, 중복 방지, 로그 연결을 실행 경로 안에 넣으면 220개 잡이 같은 보장을 받는다.
같은 이유로 라이브러리의 결함이 220개 잡에 같은 방식으로 퍼진다.
`alertOnFailure`에 오류가 있으면 모든 잡의 알림이 같이 망가지고, 그것도 잡마다 알림을 설정하던 때와 달리 어느 잡에서도 이를 우회해 확인할 수 없다.

글이 소개한 라이브러리 새 버전 배포 시 업데이트 PR이 자동으로 올라가는 구조도 양면적이다.
이관 중 고친 내용이 각 팀에 빠르게 퍼지지만 결함도 그만큼 빠르게 퍼진다.
이런 구조를 안전하게 운영하려면 라이브러리 자체의 테스트와 단계적 배포가 필요하다.
서비스 개발 조직에서 흔히 말하는 골든 패스(권장 경로를 기본으로 제공하는 방식)가 같은 긴장을 안고 있다.
편한 경로를 만드는 일은 그 경로의 품질을 플랫폼 팀이 책임진다는 약속이기도 하다.

### 하위 계층의 재시도를 없애려면 하위 계층의 중단도 없애야 한다

Kubernetes 재시도를 0으로 둔 결정은 시도 횟수를 한 층에서만 관리하게 해 주지만, 하위 계층이 일으키는 중단을 상위 계층이 흡수할 수 없게 만든다.
Karpenter 사건은 그 직접적인 결과다.
해법으로 배치 파드에 `do-not-disrupt` 표시를 붙였다.

이 해법은 비용과 이어진다.
노드 통합과 축소는 Karpenter가 비용을 줄이는 핵심 수단인데, 장시간 배치 파드가 많아지면 해당 노드는 파드가 끝날 때까지 줄어들 수 없다.
글은 노드가 부족하면 평균 30초 정도에 준비된다고 하면서 배치가 몰리는 시간대에 서버를 늘리는 장점을 말하지만, 반대로 배치 파드가 노드를 붙잡는 시간이 비용에 미치는 영향은 다루지 않는다.
신뢰성을 위해 방어를 세우면 그 방어가 다른 곳의 비용 절감을 막는 경우가 많다.
절감액을 말하려면 이 상호작용을 포함한 측정이 필요하다.

### 이관은 상태 소유권을 넘기는 작업이고 UI에 둔 상태는 감사 대상에서 빠진다

스케줄의 실행 여부를 UI에서만 정하는 선택은 전환기의 안전장치로 합리적이다.
그러나 글이 이관 후의 장점으로 꼽은 것은 잡 추가와 스케줄 변경이 코드가 되어 PR 리뷰를 거치고 롤백으로 함께 되돌아간다는 점이다.
실행 여부가 UI에만 있으면 이 장점의 바깥에 남는다.

운영 중 누군가 스케줄을 멈추고 다시 켜지 않으면 그 배치는 조용히 멈추고, 그 변경은 코드 리뷰에도 롤백에도 남지 않는다.
이는 GitOps 환경에서 자동 복구 설정과 수동 변경이 충돌하는 문제와 같은 모양이다.
일시정지로 등록하는 규칙은 전환기에는 필요하지만, 이관이 끝난 뒤에는 일시정지 상태가 얼마나 오래 유지되는지를 점검하는 감시가 따로 필요하다.
글이 말하는 스케줄 실행 성공 횟수 알림이 이 역할의 일부를 맡을 수 있지만, 의도적으로 멈춘 스케줄과 의도치 않게 멈춘 스케줄을 구분하는 방법은 글에 없다.
