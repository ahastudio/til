# AI 코딩이 CI를 병목으로 만들었을 때 Linear가 한 일

원문: [AI coding has made CI a bottleneck, so we reworked ours to keep up](https://linear.app/now/ci-bottleneck-reworked)

HN 토론: <https://news.ycombinator.com/item?id=49792067> (300점, 367개 댓글)

GN 토론: <https://news.hada.io/topic?id=34105>

## 소개

Linear의 Mufeez Amjad가 2026년 9월 21일에 쓴 글이다.
올해 초 CTO가 CI 비용이 높다는 제목의 이슈를 자기에게 배정한 데서 시작했다고 적는다.
하는 김에 CI를 더 빠르게도 만들어 달라고 했다는 것이다.

문제 설정이 한 문단으로 제시된다.
에이전트가 코드를 내보내는 속도를 기하급수적으로 빠르게 만들었는데
그 변경을 검증하는 쪽은 같은 속도로 따라오지 못했다는 것이다.
모든 PR이 여전히 CI를 통과해야 하므로,
개발이 빨라질수록 CI가 병목이 되어 인프라 비용을 올리고
개발자와 에이전트를 더 오래 기다리게 만든다.

최적화의 목표를 두 축으로 잡았다고 밝힌다.
PR이 CI를 기다리는 시간과 러너 시간을 얼마나 쓰는지다.
결과는 이렇다.
연초 이후 테스트 묶음이 거의 네 배가 되었는데도
PR 대기 시간을 6분 넘던 것에서 5분 조금 넘는 수준으로 낮췄고,
테스트당 러너 시간은 대략 절반으로 줄였다는 것이다.

개선은 네 갈래로 이루어졌다.
인프라와 도구를 올리기, 다른 작업을 막고 있는 작업을 최적화하기,
반복되는 준비 작업을 줄이기, 테스트 실행을 효율적으로 만들기다.
코드베이스는 주로 TypeScript이지만 상당수 최적화가 다른 언어와 도구 사슬에도 적용된다고 밝힌다.

## 인프라와 도구 교체

가장 이른 성과 몇 가지는 CI 자체를 거의 손대지 않고 얻었다고 적는다.

작업을 GitHub Actions에서 제3자 러너로 옮긴 것이다.
CPU가 더 빠르고 저장 장치 성능이 높으며 캐시 기반이 나은 것들이다.
전환 전후 이틀을 같은 조건으로 비교했을 때 작업이 평균 34% 빨라졌고,
타입 검사 같은 일부 작업은 52% 줄었다.

도구 사슬 현대화도 성과를 냈다.
네이티브 TypeScript 컴파일러인 `tsgo`로 바꾸자
타입 검사의 주간 중앙값이 73% 줄었고,
그 폭이 충분히 커서 병목이 타입 검사에서 아예 벗어났다는 것이다.

### 린트에서 타입 검사기를 떼어 내기

린트가 이른 표적이었다.
자체 린트 규칙 몇 개가 TypeScript 타입 정보에 의존하고 있었다.
제약을 강제하거나 자동 수정을 적용하기 위해서였다.
그래서 린트를 돌릴 때마다 그 규칙들을 평가하기 전에 타입 그래프 전체를 만들어야 했고,
린트가 CI에서 메모리를 가장 많이 쓰는 작업 중 하나가 되었다.

규칙을 추상 구문 트리 위의 정적 분석으로 다시 썼다.
타입 정보 없이 함수 같은 구조와 가드 패턴을 식별하는 방식이다.
그 결과 ESLint가 TypeScript를 완전히 떼어 낼 수 있었고,
API 린트 시간이 68%, 저장소 전체 린트 시간이 55% 줄었다.
메모리 사용량도 크게 떨어졌다.

타입 정보 의존을 없앤 것이 나중에 Oxlint로 옮기는 일도 훨씬 쉽게 만들었다고 적는다.
문법만으로 동작하는 규칙은 옮기기가 간단하기 때문이다.
Oxlint 자체도 린트에 쓰는 CI 러너 시간을 줄였다.

## 다른 작업을 막고 있는 작업 최적화

기반과 개별 검사가 빨라진 뒤 CI를 하나의 체계로 놓고 보았다고 적는다.
그러자 모든 것 앞에 놓인 작은 작업들이 눈에 들어왔다.

모든 실행이 PR이 어떤 경로를 건드렸는지,
같은 입력에 대해 이 테스트가 이미 통과했는지를 확인하는 것으로 시작한다.
이 검사를 작업 수준에서 걸어 두어 건너뛴 작업이 러너를 잡지 않도록 했는데,
그것이 동시에 이 검사들을 임계 경로 위에 올려놓았다.
여덟 개의 API 테스트 샤드 중 어느 것도 이것이 끝나기 전에는 시작할 수 없으므로,
작은 지연도 불균형하게 중요해진다는 것이다.

### 각 작업에 필요한 것만 받아 오기

여러 워크플로가 변경 감지 작업으로 시작한다.
예를 들어 차이에 데이터베이스 마이그레이션이 들어 있는지 확인하고
관련 검사를 스케줄하는 데 쓰이는 신호를 출력한다.
이 작업들이 작업 트리의 아주 일부만 필요한데도 전체를 체크아웃하고 있었다.

세 가지를 적용했다.

| 조치                                                        | 효과                         |
| ----------------------------------------------------------- | ---------------------------- |
| 가져오기 깊이 제한                                          | 가장 느린 게이트 94초 → 20초 |
| 작업 트리가 필요 없는 작업에서 체크아웃 제거                | 27초 → 7초                   |
| 경로 비교가 필요한 경우 희소·블롭 없는 체크아웃에 이력 제한 | 약 11초 추가 절감            |

변경 감지 작업의 중앙값이 26초에서 8초로,
상위 90번째 백분위가 31초에서 12초로,
가장 느린 실행이 138초에서 37초로 떨어졌다.

### 체크아웃을 견고하게 만들기

러너 기반을 바꾼 뒤 체크아웃 시간이 길어지고 때로 멈추는 것을 발견했다고 적는다.
제3자 러너가 GitHub 네트워크 바깥에 있어 직접 IP 연결로 GitHub에 닿는데,
공급자가 그 연결의 간헐적 성능 저하를 원인으로 지목했다.
여러 워크플로가 체크아웃으로 시작하므로 멈춘 가져오기 하나가 CI 실행 전체를 지연시킬 수 있다.

표준 체크아웃 액션을 자체 복합 액션으로 바꿨다.
지수 후퇴로 재시도하고,
환경 변수를 설정해 멈춘 연결이 무한정 매달리는 대신 약 30초 뒤에 중단되게 하며,
고정 디스크에 영속 git 미러를 유지하는 체크아웃 캐시를 쓴다.

```bash
# 멈춘 연결이 30초 안에 실패하도록 하는 두 값
# 이 아래 속도로 이 시간만큼 지속되면 git이 중단한다
export GIT_HTTP_LOW_SPEED_LIMIT=1000   # 바이트/초 기준선
export GIT_HTTP_LOW_SPEED_TIME=30      # 유지 시간(초)
```

결과적으로 임계 경로의 작업이 체크아웃을 기다리며 놀고 있는 실행이 훨씬 줄었다.

### 임계 경로에서 뺄 수 있는 것 빼기

임계 경로에 있던 모든 작업이 거기 있어야 했던 것은 아니라고 적는다.
병합 직전 마지막 검사의 일부로 캐시 표식을 쓰고 있었는데,
그것 때문에 테스트가 통과한 뒤에도 PR이 병합 대기열에 앉아 있을 수 있었다.
그 쓰기를 테스트 샤드가 끝난 뒤 실행되면서 아무것도 막지 않는 작업으로 옮겼고,
모든 API PR과 병합 대기열 항목에서 병합 경로가 42초 줄었다.

이 변경들을 합쳐 캐시 미스 시 API PR의 필수 검사에서 대략 1분을 덜어 냈고 러너 시작 횟수도 줄였다.

## 반복되는 준비 작업 줄이기

모든 작업에서 반복되는 준비 비용을 다음 표적으로 삼았다고 적는다.
러너를 띄우고, 패키지를 설치하고, 빌드 의존성을 갖추는 일이다.
그 부담 때문에 실제로는 몇 초의 유용한 일만 하는 작업이 인프라 시간을 몇 분씩 쓰게 된다.

### 공유 의존성을 CI 이미지에 미리 넣기

API 테스트 샤드 각각이 실행마다 같은 PostgreSQL 클라이언트를 패키지 관리자로 설치하는 데 7~8초를 썼다.
Node와 그 클라이언트를 담은 작은 CI 기본 이미지로 옮겨
각 샤드가 바로 실행할 수 있는 환경에서 시작하게 했다.
나중에 필요한 네이티브 빌드 헤더도 이미지에 더했는데,
준비 과정에서 그것을 내려받다가 이따금 멈추는 것을 발견했기 때문이며 꼬리가 짧아졌다.

### 각 작업에 필요한 의존성만 설치하기

코드베이스는 pnpm 워크스페이스로 관리하는 모노레포다.
API 테스트 워크플로가 API 패키지와 그 의존성만 필요한데도 워크스페이스 전체를 설치하고 있었다.
설치를 API 패키지로 제한하자 `pnpm install`이 44~73초에서 16~18초로 줄었다.
같은 방식을 API 인접 작업들에도 적용했는데,
그것들도 저장소 전체를 설치하고
나중 실행이 거의 쓰지 않는 의존성 캐시를 올리고 있었다.

### 다시 만드는 편이 빠르면 캐시하지 않기

`node_modules` 캐시도 시험해 봤는데 다시 만드는 편이 빨랐다고 적는다.
캐시 키가 자주 바뀌는 잠금 파일에 달려 있었고,
캐시가 맞아도 복원에 약 28초가 걸린 반면 걸러 낸 설치는 대략 7.5초였다는 것이다.
캐시는 저장 시간과 변동성만 더하고 알아볼 만한 이점을 주지 않았다.

이 세 가지로 샤드당 준비 시간이 대략 44% 줄었다.
110~140초에서 67~73초가 되었다.

### 바뀌지 않은 준비 작업을 다시 하지 않기

어떤 준비 작업은 입력이 바뀔 때만 반복하면 된다고 적는다.
API 컨테이너가 PR이 스키마를 바꾸지 않았는데도 실행마다 마이그레이션 이력 전체를 다시 재생하고 있었다.
생성된 스키마 스냅숏과 부트스트랩 파일을 불러오는 방식으로 바꿔
컨테이너당 데이터베이스 준비를 약 12초에서 1~2초로 줄였다.

### 짧은 검사를 묶어 작업 수를 줄이기

일곱 개의 독립적인 검사가 각각 러너를 띄우고 저장소를 체크아웃하고 의존성을 설치한 뒤
몇 초짜리 유용한 일만 하고 있었다.
이것들을 두 개의 작업으로 합치고, 그 안에서 일곱 과제를 동시에 돌렸다.
같은 준비 부담을 치르는 횟수가 일곱에서 둘로 줄었다.
6월 사용량 기준으로 월 약 87,000 러너 분을 아꼈으며, 전체 CI 사용량의 11.8%에 해당한다.

## 테스트 실행 효율화

샤드당 고정 비용이 내려가자 API 묶음을 더 공격적으로 병렬화할 여유가 생겼다고 적는다.
가장 크고 가장 자주 실행되는 부분이므로 여기서의 개선이 병합 시간에 큰 영향을 준다.

### 테스트 러너가 보는 방식대로 일을 나누기

TypeScript 테스트에 쓰는 Vitest는 개별 테스트의 소요 시간이 아니라 파일 단위로 일을 분배한다.
그래서 유난히 큰 테스트 파일 몇 개가 한 샤드를 독차지하고
다른 샤드들이 훨씬 먼저 끝나는데도 묶음 전체의 완료를 붙잡을 수 있었다.

테스트의 구조는 유지하면서 큰 파일들을 더 작고 초점이 분명한 파일로 쪼갠 뒤
여러 샤드와 러너 구성을 평가했다.
연초에 이미 셋에서 넷으로 늘렸고, 여덟으로 옮기자
초기 벤치마크에서 임계 작업이 약 19% 빨라지고 19% 저렴해졌다.
변경 일주일 뒤 가장 느린 샤드가 5.25분에서 4.33분으로 떨어졌다.

### 엄격한 격리 규칙 아래에서만 모듈 상태 공유하기

Vitest는 보통 모든 테스트 파일을 격리하는데,
그것이 각 테스트 샤드에서 엔티티와 GraphQL과 데코레이터 그래프를 다시 만든다는 뜻이었다.
안전한 파일들이 워커 안에서 모듈 레지스트리를 공유할 수 있도록
격리를 끄는 별도 프로젝트를 만들어 선택적으로 들어오게 했다.

```ts
// vitest.config.ts — 격리를 끄는 별도 프로젝트를 둔다
// isolate: false 는 워커 안에서 모듈 레지스트리를 공유한다.
// 공유해도 안전한 파일만 include 로 골라 넣는 것이 이 설정의 핵심이다.
export default {
  test: {
    projects: [
      { test: { name: 'isolated' } },               // 기본값: 파일마다 격리
      { test: { name: 'shared', isolate: false } }, // 선택적으로만 들어오는 쪽
    ],
  },
}
```

이것이 단일 개선으로는 가장 컸다.
사용량 기준으로 월 약 17%의 절감에 해당하며,
가장 느린 샤드가 약 300~379초에서 약 195초로 떨어졌고
실행당 API 샤드 러너 시간 합계가 약 32.8분에서 22분으로 줄었다.

동시에 정확성 위험이 가장 큰 최적화이기도 했다고 적는다.
그래서 세 가지 장치를 두었다.
모든 파일에 선택 참여 주석을 달아 자격을 명시하게 했고,
공유 상태에 필요한 정리 코드를 더했으며,
가짜 타이머를 쓰거나 공유 상태를 안전하게 풀어낼 수 없는 방식으로 쓰는 파일 몇 개는 격리 프로젝트에 남겼다.
그리고 한 가지를 덧붙인다.
이제 테스트 대부분을 에이전트가 쓰므로
생성된 테스트가 기본적으로 같은 제약을 따르도록 에이전트 지침을 갱신했다는 것이다.

### 샤딩은 준비 부담이 정한다

샤딩을 더 늘리는 것은 샤드당 고정 비용이 낮을 때만 이득이라고 적는다.
샤드 수를 두 배로 늘리면 워크플로가 준비에 쓰는 시간도 두 배가 되기 때문이다.
앞의 준비 최적화가 여덟 샤드를 현실적으로 만든 것이다.

샤드당 110~140초였다면 여덟 샤드는 준비에만 15~19분의 러너 시간을 썼을 것이고, 테스트 자체보다 많다.
지금은 준비가 약 40초이므로,
여덟 샤드가 전에 네 샤드가 쓰던 것보다 적은 준비 시간을 쓰면서 테스트를 두 배로 병렬화한다.

## 값 정하기

이 글에서 뽑아낼 수 있는 판단 기준을 정리하면 이렇다.

| 결정 항목           | 이 글의 값                   | 그 값의 근거                                        | 무엇을 재야 하는가                        |
| ------------------- | ---------------------------- | --------------------------------------------------- | ----------------------------------------- |
| 샤드 수             | 8                            | 준비 비용이 약 40초로 내려간 뒤에야 현실적이 되었다 | 샤드당 준비 시간 × 샤드 수 대 테스트 시간 |
| 체크아웃 깊이       | 제한, 필요 없으면 아예 제거  | 변경 감지 작업은 작업 트리가 거의 필요 없다         | 작업별로 실제 읽는 파일 범위              |
| `node_modules` 캐시 | 쓰지 않음                    | 복원 28초 대 걸러 낸 설치 7.5초                     | 캐시 적중 시 복원 시간 대 재설치 시간     |
| 멈춤 감지 시간      | 약 30초                      | 네트워크 저하로 체크아웃이 무한정 매달렸다          | 체크아웃 소요 시간의 꼬리 분포            |

여기서 눈여겨볼 것은 캐시하지 않기로 한 결정이다.
캐시는 대개 기본으로 켜는 것으로 여겨지는데, 이 팀은 재 보고 껐다.
그 판단의 근거가 두 숫자의 비교이며, 그 비교를 하지 않으면 캐시는 언제나 옳아 보인다.

## 트레이드오프

### 격리를 끄면 가장 크게 절감되고 가장 크게 깨진다

이 글이 스스로 밝힌 가장 큰 교환이다.
단일 개선으로 절감이 가장 컸고 정확성 위험도 가장 높았다.

얻는 것은 분명하다.
테스트 파일마다 다시 만들던 무거운 그래프를 워커 안에서 한 번만 만든다.
공유 그래프가 클수록 이득이 커지므로,
의존성 주입이나 스키마 생성처럼 초기화가 무거운 구조를 가진 코드베이스에서 특히 크다.

잃는 것은 테스트의 독립성이다.
그리고 이 상실은 즉시 드러나지 않는다.
공유 상태를 건드린 테스트가 다른 테스트의 결과를 바꾸는데,
그 조합은 실행 순서에 따라 달라지므로 재현되지 않는 실패로 나타난다.
이런 실패는 대개 재실행으로 넘어가고, 그러면 원인이 영원히 발견되지 않는다.

그리고 여전히 어려운 것이 남는다.
어떤 파일이 안전한지를 판정하는 일이다.
이 팀은 그것을 자동으로 판정하려 하지 않고 선택 참여 주석으로 사람이 선언하게 했다.
가짜 타이머를 쓰거나 공유 상태를 안전하게 풀 수 없는 파일 몇 개는 그냥 격리 쪽에 남겼다고 적는다.
즉 이 최적화는 전면 적용이 불가능하고, 영구적으로 두 종류의 테스트를 관리하게 된다.

그래서 이 교환의 진짜 비용은 성능이 아니라 분류의 유지다.
새 테스트가 들어올 때마다 어느 쪽인지 정해야 하고,
그 판정이 틀리면 간헐적 실패가 생긴다.
이 팀이 에이전트 지침을 갱신했다고 적은 이유가 여기에 있다.
테스트를 사람이 쓰지 않는다면 그 판정 규칙도 사람이 아니라 지침이 지켜야 한다.

### 캐시하지 않는 선택은 캐시 키가 자주 바뀔 때만 옳다

`node_modules`를 캐시하지 않기로 한 판단은 보편적인 조언처럼 읽히기 쉬운데 그렇지 않다.

이 팀의 근거는 두 가지였다.
캐시 키가 자주 바뀌는 잠금 파일에 달려 있었다는 것과,
적중해도 복원이 28초 걸렸다는 것이다.
앞의 조건은 적중률을 낮추고, 뒤의 조건은 적중했을 때의 이득을 낮춘다.
둘 다 성립해야 캐시를 버리는 것이 이득이다.

잠금 파일이 드물게 바뀌는 저장소라면 적중률이 높으므로 결론이 뒤집힌다.
설치가 원래 오래 걸리는 생태계라면 복원 28초가 여전히 이득이므로 또 뒤집힌다.
이 글의 7.5초라는 숫자는 설치를 API 패키지로 제한한 뒤의 값이므로,
앞 단계의 최적화가 없었다면 이 판단 자체가 성립하지 않는다.

여기서 나오는 어려움은 두 최적화가 서로의 전제라는 점이다.
설치 범위를 줄였기 때문에 캐시를 버릴 수 있었고,
캐시를 버렸기 때문에 변동성이 줄었다.
그래서 이 조합을 따라 할 때 하나만 가져오면 손해가 날 수 있으며,
어느 쪽을 먼저 할지는 각자의 숫자를 재 봐야 정해진다.

### 임계 경로를 줄이는 일은 총 작업량을 늘린다

이 글의 여러 조치가 같은 형태를 갖는다.
캐시 표식 쓰기를 아무것도 막지 않는 별도 작업으로 옮겼고,
짧은 검사 일곱 개를 두 작업으로 합쳤으며,
샤드를 넷에서 여덟으로 늘렸다.

앞의 둘은 총 작업량을 줄이지만 마지막은 늘린다.
샤딩은 대기 시간을 줄이는 대신 러너 시간을 더 쓰는 교환이고,
글에 실린 그래프 설명이 그것을 명시한다.
테스트당 기계 시간이 샤드를 더할 때 치솟았다는 것이다.

그래서 이 두 축은 함께 최적화할 수 없고 우선순위를 정해야 한다.
이 팀은 대기 시간을 우선했고, 그 비용을 준비 최적화로 되찾는 방식을 택했다.
비용을 우선하는 조직이라면 샤드를 줄이고 대기 시간을 감수하는 반대 선택이 맞는다.
글이 두 축을 모두 개선했다고 보고하지만,
그것은 준비 비용이라는 제3의 항목이 크게 남아 있었기 때문에 가능했다.
그 여지가 없는 조직에서는 둘 중 하나를 골라야 한다.

## 함정

임계 경로 위의 작은 작업이 가장 비싸다.
몇 초짜리 검사라도 그것이 여덟 개의 샤드를 막고 있으면 그 지연이 여덟 배로 증폭된다.
실행 시간이 긴 작업부터 손대는 본능이 여기서는 틀린다.

제3자 러너는 네트워크 경계를 하나 더 만든다.
GitHub 바깥에 있으므로 체크아웃이 그 링크에 의존하게 되고,
이 팀이 겪은 것처럼 간헐적 성능 저하가 CI 전체의 멈춤으로 나타난다.
속도만 보고 옮기면 이 항목이 뒤늦게 청구된다.

기본값으로 무한정 매달리는 동작이 곳곳에 있다.
체크아웃도, 패키지 설치 중 헤더 내려받기도 그랬다.
멈춤을 감지해 실패시키는 값을 명시하지 않으면 꼬리 분포가 통제되지 않는다.

캐시가 항상 이득이라는 가정이 비싸다.
적중률과 복원 시간을 재지 않으면 캐시는 저장 시간과 변동성만 더할 수 있다.

테스트 러너의 분배 단위를 모르면 샤딩이 기대만큼 듣지 않는다.
파일 단위로 나누는 러너에서는 큰 파일 하나가 샤드를 독차지한다.
샤드 수를 늘리기 전에 파일 크기 분포를 먼저 봐야 한다.

테스트를 에이전트가 쓰기 시작하면 성능 규칙도 지침에 들어가야 한다.
사람에게만 공지한 규칙은 생성된 코드에 적용되지 않는다.

## 확인하기

자기 CI에서 같은 진단을 해 보는 순서는 이 글의 구조를 그대로 따르면 된다.

```bash
# 1) 임계 경로 파악: 각 작업의 시작 시각과 소요 시간을 뽑는다
gh run view <RUN_ID> --json jobs \
  --jq '.jobs[] | {name, startedAt, completedAt, conclusion}'

# 2) 무엇이 무엇을 막는지 확인: needs 관계를 워크플로에서 읽는다
grep -n "needs:" .github/workflows/*.yml

# 3) 준비와 실제 작업의 비율: 한 작업 안의 단계별 시간을 본다
gh run view --job <JOB_ID> --log | head -50
```

그다음 두 숫자를 직접 재 본다.
캐시 복원 시간과 걸러 낸 설치 시간이다.

```bash
# 캐시 없이 필요한 패키지만 설치했을 때
time pnpm install --filter <패키지명>...
```

테스트 쪽은 파일 크기 분포를 먼저 본다.

```bash
# 테스트 파일별 소요 시간을 뽑아 상위 몇 개가 전체를 지배하는지 확인한다
npx vitest run --reporter=json --outputFile=/tmp/vitest.json
python3 -c "
import json
d = json.load(open('/tmp/vitest.json'))
rows = sorted(((r['endTime'] - r['startTime'], r['name']) for r in d['testResults']), reverse=True)
total = sum(t for t, _ in rows)
for t, name in rows[:10]:
    print(f'{t/1000:7.1f}s  {100*t/total:5.1f}%  {name}')
"
```

상위 몇 개 파일이 전체의 큰 비중을 차지한다면 샤드를 늘리기 전에 그 파일부터 쪼개야 한다.

## 체크리스트

- 임계 경로 위에 있는 작업을 나열했고, 그중 거기 있을 필요가 없는 것을 골라냈는가
- 각 작업이 실제로 필요한 파일 범위를 확인했고, 체크아웃을 그에 맞게 줄였는가
- 체크아웃과 패키지 설치에 멈춤 감지 시간이 설정되어 있는가
- 캐시 복원 시간과 재설치 시간을 실제로 재 봤는가
- 테스트 파일별 소요 시간 분포를 봤고, 소수 파일이 지배하지 않는가
- 샤드당 준비 시간 × 샤드 수가 테스트 시간보다 작은가
- 격리를 끈 테스트가 있다면 어느 파일이 해당되는지 파일 안에 선언되어 있는가
- 그 규칙이 사람 공지가 아니라 에이전트 지침에도 들어가 있는가
- 대기 시간과 러너 비용 중 무엇을 우선할지 정해 두었는가

## 비평

### 검증이 병목이라는 진단이 테스트의 가치를 묻지 않는다

이 글의 전제는 에이전트가 코드를 빨리 내놓으니 검증이 따라가야 한다는 것이다.
그런데 글타래에서 가장 많이 나온 반응은 그 전제 자체를 되묻는 것이었다.

saagarjha가 가장 짧게 묻는다.[^saagarjha]
테스트 묶음이 연초 이후 거의 네 배가 되었다는 서술을 인용하며,
그 테스트들이 네 배의 가치를 냈느냐는 것이다.

dgroshev가 그 의심에 구조를 준다.[^dgroshev]
상당 부분이 쓸모없는 테스트의 홍수 때문이라고 본다는 것이다.
아직 PR을 검토한다면, 마지막으로 테스트를 건너뛰지 않고 읽은 것이 언제였느냐고 묻는다.
그리고 언어 모델이 많이 관여한 PR의 테스트를 본 적이 있다면,
그중 몇 개가 내장 기능이나 사소한 동작이 아니라 실제로 유용한 것을 시험했느냐고 묻는다.
업계가 언어 모델이 업무 로직에 상용구를 많이 만들어 낸다는 것은 어느 정도 인식하고 있는데,
테스트 안에 그것이 얼마나 많은지는 훨씬 덜 인식하고 있는 것 같다고 적는다.

이 지적이 글의 논지와 정면으로 만난다.
이 글은 네 배가 된 테스트를 주어진 조건으로 놓고 그것을 빨리 돌리는 방법을 다룬다.
그런데 네 배 중 상당수가 가치를 더하지 않는다면,
가장 큰 최적화는 샤딩이나 격리 해제가 아니라 삭제다.
그리고 글에는 어떤 테스트를 지웠다는 서술이 없다.

이 팀이 그 판단을 하지 않은 데 이유가 있을 수는 있다.
CI 비용을 줄이라는 이슈를 받은 사람이 테스트의 가치를 판정할 위치에 있지 않을 가능성이 크다.
그러나 글이 주 2000개씩 테스트가 늘고 있다고 밝히면서
그 증가를 검토 대상이 아니라 배경으로만 다루므로, 이 질문이 남는다.

### 최적화 이후 병목이 어디로 갔는지가 없다

글의 마지막 절은 개선이 없었다면 지금 테스트가 약 11분 걸렸을 것이라고 적으며,
코드베이스가 계속 커지므로 노력이 이어질 것이라고 맺는다.
그런데 CI가 더 이상 병목이 아니라면 무엇이 병목인지는 말하지 않는다.

aliclark가 자기 경우를 든다.[^aliclark]
자기에게 병목은 CI가 아니라 사람이 하는 시험이라는 것이다.
작동하느냐는 확인되지만, 그것이 우리가 원하는 일을 하느냐,
그리고 더 중요하게는 고객이 이해하고 실제로 좋아할 방식으로 하느냐가 문제라는 것이다.

pushpendraw는 다음 병목의 위치를 예측한다.[^pushpendraw]
CI를 빠르게 하면 다음 병목이 배포와 롤백으로 옮겨 가는데,
그것들은 같은 방식으로 확장되지 않는다는 것이다.

두 지적이 같은 것을 가리킨다.
병목은 옮겨 다니는 것이므로, 한 단계를 최적화한 글은
그 단계가 더 이상 병목이 아니게 되었는지를 보고해야 논지가 닫힌다.
이 글은 개선 수치를 충분히 제시하지만
PR이 만들어져 배포되기까지의 전체 시간에서 CI가 차지하는 비중이 얼마나 줄었는지는 말하지 않는다.
그래서 이 작업이 실제로 무엇을 바꿨는지는 글 안에서 확인할 수 없다.

### 이 처방의 전제 조건이 드러나 있지 않다

이 글은 기법 목록으로 읽히지만, 그 기법들이 성립하는 조건이 상당히 특수하다.

## 기억할 원칙

### 고정 비용을 먼저 낮춰야 병렬화가 이득이 된다

이 글에서 가장 이식성이 높은 것은 특정 도구 설정이 아니라 두 최적화의 순서다.

샤드를 넷에서 여덟으로 늘리는 것은 그 자체로는 이득이 아니다.
글이 계산해 보인 대로, 샤드당 준비가 110~140초였다면
여덟 샤드는 준비에만 15~19분을 써서 테스트 자체보다 많았을 것이다.
준비를 약 40초로 내린 뒤에야 여덟 샤드가 전에 네 샤드가 쓰던 것보다 적은 준비 시간을 쓰게 되었다.

이 구조는 병렬화 일반에 적용된다.
작업을 n개로 나누면 고정 비용이 n배가 되고 가변 비용이 1/n이 된다.
그러므로 고정 비용이 가변 비용에 비해 크면 나눌수록 손해다.
그리고 사람들은 대개 가변 비용만 보고 나눈다.
테스트가 오래 걸리니 나누자는 판단이 그것이다.

여기서 나오는 순서가 있다.
병렬화를 고려하기 전에 한 조각의 고정 비용을 먼저 재고, 그것을 낮출 수 있는 만큼 낮춘다.
그다음 고정 비용 × 조각 수가 전체 가변 비용보다 작은 범위 안에서 조각 수를 정한다.
이 계산을 하지 않으면 병렬화는 대기 시간을 조금 줄이고 비용을 크게 늘리는 선택이 된다.

같은 계산이 컨테이너 기동, 람다 찬 시작, 배치 작업 분할, 워커 풀 크기 결정에 그대로 적용된다.
전부 조각마다 치르는 고정 비용이 있고, 그 값이 나눌 수 있는 한계를 정한다.

### 기본값은 재 보기 전까지 근거가 아니다

이 글에서 가장 반직관적인 결정이 캐시를 쓰지 않기로 한 것이다.
그리고 그 결정의 근거가 두 숫자의 비교였다.
복원 28초 대 걸러 낸 설치 7.5초다.

이 사례가 가치 있는 이유는 캐시가 거의 언제나 옳다고 여겨지기 때문이다.
그래서 대부분의 파이프라인이 캐시를 켜 두고, 그것이 이득인지 확인하지 않는다.
확인하지 않는 이유는 켜 두어도 눈에 띄는 손해가 없기 때문이며,
손해가 눈에 띄지 않는 이유는 그것이 전체 시간에 섞여 있기 때문이다.

같은 구조의 기본값이 곳곳에 있다.
재시도를 켜 두는 것, 타임아웃을 넉넉히 잡는 것, 로그 수준을 높게 두는 것,
테스트를 격리하는 것이 전부 안전한 쪽으로 보이는 기본값이다.
그리고 각각에 대해 이 글과 같은 질문을 던질 수 있다.
이것을 껐을 때 무엇이 나빠지는지 실제로 재 봤는가다.

여기서 중요한 것은 기본값을 의심하라는 조언이 아니라, 의심의 비용이 낮다는 사실이다.
캐시를 끄고 한 주 돌려 보는 것은 되돌리기 쉽고, 그 결과가 숫자로 남는다.
되돌리기 쉬운 실험은 확신 없이도 해 볼 수 있으며,
이 팀이 한 일의 상당수가 그런 실험이었다.

### 자동화가 코드를 쓰기 시작하면 규칙도 자동화 쪽에 두어야 한다

글의 마지막 기술적 서술이 이 문서에서 가장 조용하면서 중요한 대목이다.
격리를 끈 프로젝트에 파일을 넣으려면 선택 참여 주석이 필요한데,
이제 테스트 대부분을 에이전트가 쓰므로 에이전트 지침을 갱신해
생성된 테스트가 기본적으로 같은 제약을 따르게 했다는 것이다.

이 조치가 필요한 이유는 규칙이 지켜지는 경로가 바뀌었기 때문이다.
사람이 코드를 쓸 때 규칙은 문서와 코드 리뷰로 지켜진다.
생성기가 코드를 쓰면 문서를 읽는 것은 생성기이고, 리뷰는 대개 형식이 된다.
그러므로 규칙을 사람용 문서에만 두면 그 규칙은 적용되지 않는다.

여기서 나오는 일반 규칙이 있다.
어떤 제약을 새로 만들 때, 그 제약을 지켜야 하는 주체가 누구인지 먼저 정하고
그 주체가 읽는 곳에 적어야 한다는 것이다.
지금 그 주체는 셋이다.
사람, 생성기, 그리고 검사 도구다.
가장 튼튼한 것은 세 번째이므로,
주석 선언 같은 규칙은 결국 린트 규칙이나 CI 검사로 내려가는 것이 자연스러운 다음 단계다.

그리고 이 사례는 더 넓은 변화를 가리킨다.
성능 최적화가 코딩 규칙이 되고, 코딩 규칙이 에이전트 지침이 된다.
그러면 에이전트 지침 파일이 사실상 팀의 코딩 표준이 되며,
그 파일의 품질이 코드베이스의 품질을 직접 정하게 된다.
CI 비용을 줄이라는 이슈에서 시작한 작업이 거기까지 간 것이 이 글에서 가장 눈여겨볼 궤적이다.
