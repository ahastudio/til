# Aven: 내 서버에 설치하는 Railway 스타일 배포 플랫폼

<https://github.com/turin-dev/aven>

GN 토론: <https://news.hada.io/topic?id=36386>

## 소개

Aven은 자기 Docker 호스트에서 애플리케이션을 배포하고 운영하는 셀프
호스팅 플랫폼이다.
README의 첫 문장은 Railway처럼 쓰되 자기 서버에서,
사용량 기반 요금 없이 쓴다는 것이다.
`aven-server` 프로세스 하나가 Docker 옆에서 돌고,
서버를 더 붙이려면 `aven-agent`를 설치한다. 운영할 Kubernetes 클러스터는 없다.

저장소 정보로는 Go로 쓰였고 AGPL-3.0이며,
저장소는 2026년 10월 25일에 만들어졌다.
이 글을 쓸 때 별은 1개였다.[^api]
README는 이 프로젝트가 이전 프로젝트 Keel의 연속이며,
공개 저장소는 첫 Aven 릴리스(2026-10-25)에서 시작하고 Keel의 기록은 포함하지
않는다고 밝힌다.
또 개발에 AI 코딩 에이전트를 상당히 썼고 변경은 사람의 검토와 테스트를
거쳤다고 적는다.

README에는 독립 프로젝트라는 고지가 맨 위에 있다.
저장소에 Railway의 소스 코드는 없고, 캔버스와 서비스 작업 흐름은 Railway를
따르며, `railway.json`과 `railway.toml`을 읽고 Railway 모양의 GraphQL 질의에
응답해서 프로젝트를 옮길 수 있게 한다고 설명한다.
Dockerfile 없는 빌드는 Railway가 공개한 오픈소스 빌더 Railpack을 별도
프로그램으로 실행한다.

## 설치와 시작

요구 사항은 systemd와 Docker가 있는 Linux 서버(amd64 또는 arm64)이고 80번과
443번 포트가 비어 있어야 한다.
대시보드용 DNS 이름이 필요하고, 서비스 도메인을 자동으로 만들려면 와일드카드
이름(`*.apps.example.com`)이 필요하다.
서버를 여러 대 쓸 때는 Tailscale이나 WireGuard 같은 사설 네트워크로 서로
닿아야 한다.

```bash
curl -fsSL https://raw.githubusercontent.com/turin-dev/aven/main/install-server.sh | sh
```

README에 따르면 스크립트는 터미널에서 대시보드 URL, 서비스 기본 도메인,
Let's Encrypt 이메일, 관리자 비밀번호를 묻고 요약을 보여 준 뒤 확인을
받아 설치한다.
릴리스 체크섬을 검증하고, `aven-server`와 CLI, Railpack을 설치하고,
`/etc/aven/aven.env`를 쓰고, 서비스를 시작한 다음 로그인 정보와 만들어야 할 DNS
레코드를 출력한다.
이후에는 프로젝트를 열어 캔버스에서 Add를 누르고 첫 서비스를 배포한다.

저장소는 소스에서 빌드하는 방법도 적는다. Go 1.26 이상과 Node.js 20.9 이상이
필요하고 `make all`로 웹 UI, 서버, 에이전트, CLI 바이너리를 만든다.
README의 경고문은 Aven이 아직 젊고 빠르게 바뀌므로 업그레이드 전에 릴리스 노트를
읽고 데이터 디렉터리(`/var/lib/aven`)를 백업하라는 것이다.
이 디렉터리에는 데이터베이스와 비밀 값을 암호화하는 키가 들어 있다고 한다.

## 구조

`aven-server`는 대시보드가 내장된 단일 Go 바이너리다.
상태는 SQLite에 저장하고, Docker와 Railpack으로 이미지를 빌드하고,
Docker API로 컨테이너를 실행한다.
`aven-proxy`는 Aven이 설정하는 Caddy 컨테이너로 TLS 종료와 도메인 라우팅,
엣지 기능을 맡는다.
`aven-agent`는 추가 서버에서 돌며 인증서로 서버에 연결해 같은 Docker 작업을
수행하고, 서로 다른 노드의 서비스는 사용자가 준 사설 주소 위의 mTLS
메시로 통신한다.

README가 나열한 기능은 넓다.
GitHub push 배포와 풀 리퀘스트 미리보기 환경, Postgres, MySQL, Redis,
MongoDB와 S3 호환 버킷의 원클릭 생성, Postgres WAL과 MySQL binlog 기반 시점
복구, 자동 TLS와 경로 규칙, 엣지 캐시와 WAF 규칙,
여러 서버에 걸친 복제와 오토스케일링이 들어 있다.
팀 기능으로 워크스페이스와 역할, SAML SSO, 패스키, TOTP,
OAuth 2.0 / OpenID Connect 공급자가 같은 코어에 포함된다.
자동화 쪽으로는 CLI, REST와 GraphQL API, MCP 서버, 인프라 코드,
그리고 `aven import dokploy`가 있다.

## 기능 안정성 표시

README는 기능마다 Stable 또는 Experimental 표시를 붙인다.
Stable은 운영자를 위한 설명이 저장소에 있고 전용 테스트가 있다는 뜻이며,
지원 약속이 아니라고 적는다.
Experimental로 표시된 것은 다섯 가지다. Cloudflare Tunnel 인그레스(터널을 실제로
시작하는 테스트가 없음), 앱 슬리핑(유휴 상태에서 잠들고 깨어나는 경로를 시험하는
테스트가 없음), 크론 일정(예약된 실행이 실제로 발화하는 테스트를 찾지 못함),
AI 어시스턴트(로그가 가공 없이 모델로 전송되는 한계 등이 문서화됨),
그리고 웹 대시보드(`web/`에 자동화된 컴포넌트나 종단 간 테스트가 없음)다.

## 분석

### 비교표는 기준 날짜와 확인 방식을 밝혀서 주장의 강도를 정한다

README의 비교표는 Railway, Coolify, Dokploy와 Aven을 열세 항목으로 견준다.
Aven 칸은 이 저장소의 코드와 문서에서, 경쟁 제품 칸은 공식 페이지에서 가져왔고,
확인일은 2026-10-27이라고 적는다.
“문서화되지 않음”은 그 페이지가 기능을 설명하지 않았다는 뜻이지 기능이 없다는
주장이 아니라고 따로 밝힌다.

이 방식은 비교표가 흔히 저지르는 오류를 줄인다.
예를 들어 Railway의 자체 서버 설치기는 문서에 없다고 쓸 뿐이며 없다고
단언하지 않는다.
표의 각 칸에는 각주가 달려 있어서 독자가 근거 페이지를 따라갈 수 있다.
다만 이 글은 그 경쟁 제품 페이지를 직접 열어 보지 않았으므로,
표의 경쟁 제품 칸은 README의 주장으로 읽어야 한다.

### SSO와 패스키를 코어에 넣은 것이 가격 대신 내세우는 차별점이다

README의 표에서 SSO 항목의 서술은 이렇다.
Aven은 SAML SSO가 코어에 있고, Railway는 Free 플랜에서 제공하지 않으며
Enterprise와 약정 지출에 표시되어 있고, Dokploy는 Enterprise에서만 제공하고,
Coolify는 셀프 호스팅 무료판에서 v4.3.0부터 제공한다고 적는다.
README는 이 소프트웨어에 유료 기능 단계가 없다고도 말한다.

이 선택은 AGPL 라이선스와 맞물린다.
README의 FAQ는 AGPL을 고른 이유를 호스팅된 Aven의 개선이 공개 상태로 남게 하려는
것이라고 설명한다.
보안 기능을 유료 단계로 가르지 않으면 기능 격차로 돈을 받는 모델이 없어진다.
다만 이 프로젝트가 어떻게 유지될지는 README에 적혀 있지 않다.

### 이전 프로젝트의 호환을 유지하는 복잡도가 이름에 남아 있다

Keel에서 업그레이드한 설치는 `KEEL_*` 설정, `/var/lib/keel`, `keel-proxy`,
`keel.*` 레이블을 계속 읽는다.
기존 세션과 `keel_` API 토큰도 계속 작동하고,
사설 주소는 `<service>.<env>.keel.internal`로 유지되며,
업그레이드 뒤 배포된 컨테이너는 `.aven.internal`에도 응답한다.
새 설치는 Aven 이름을 쓰고 옛 설치는 옛 이름을 쓰므로,
같은 소프트웨어가 설치 시점에 따라 다른 경로와 이름을 가진다.
README는 두 서버(`keel-server`와 `aven-server`)를 같은 데이터 디렉터리에 함께
실행하지 말라고 경고한다.

## 비평

### 안정성 표시는 테스트의 존재를 말하지, 테스트가 충분함을 말하지 않는다

Stable의 기준은 운영자용 문서가 있고 전용 테스트가 있다는 것이다.
이것은 테스트 파일이 존재한다는 뜻이고 테스트가 기능을 충분히 덮는다는
뜻이 아니다.
표의 근거 열이 테스트 파일 이름만 나열하므로,
독자는 파일 이름을 보고 범위를 짐작해야 한다.

그리고 이 표가 Stable로 부르는 기능이 많다.
저장소는 만들어진 지 며칠밖에 되지 않았는데 Stable로 표시된 기능이 27개이고
Experimental은 5개다.
같은 README가 이 소프트웨어를 젊고 거친 부분이 있을 것이라고 쓰므로,
Stable이라는 단어는 성숙도보다 테스트 유무를 가리키는 것으로 읽어야 한다.
README는 Stable인 기능도 릴리스 사이에 바뀔 수 있다고 직접 적는다.

### 이름과 화면의 유사성은 사용자에게 오해의 여지를 남긴다

Aven의 제목은 Railway 스타일이고, 캔버스와 서비스 패널,
설정이 Railway의 대시보드를 따른다.
README는 상표 고지와 독립 프로젝트 고지를 앞쪽에 두어 이 문제를 의식하고
있음을 보여 준다.
그러나 GraphQL 엔드포인트가 Railway의 공개 API 모양을 따르는 부분은
성격이 다르다.
Railway가 API를 바꾸면 호환이 깨질 수 있고,
그 호환은 Railway가 약속한 것이 아니다.
README는 이 의존의 위험을 FAQ나 호환 설명에서 다루지 않는다.

### 단일 서버 SQLite 상태 저장소의 한계가 FAQ에 없다

`aven-server`는 상태를 SQLite에 저장한다.
이는 설치를 단순하게 하지만, 서버를 여러 대 붙이는 구조에서 제어 평면이 서버 한
대에 있다는 뜻이기도 하다.
README는 서버 데이터베이스의 백업은 설명하지만(자체 SQLite 데이터베이스의
복사본을 만든다고 비교표에 적음), 제어 서버가 죽었을 때 에이전트 쪽 서비스가
어떻게 되는지는 설명하지 않는다.
Postgres에는 고가용성 클러스터가 있다고 하지만 이는 사용자의 데이터베이스에 관한
것이고 Aven 자체의 가용성과는 다른 문제다.
이 항목은 README에서 확인하지 못했다.

## 인사이트

### 셀프 호스팅 PaaS의 경쟁은 가격이 아니라 신뢰할 수 있는 기능 범위에서 갈린다

비교표에서 Aven과 Coolify와 Dokploy는 모두 셀프 호스팅이 무료다.
그러면 가격은 차별점이 되지 못하고, 남는 질문은 어느 쪽이 더 많은 기능을 믿을
만하게 제공하느냐다.
Aven은 SSO, 패스키, PITR, 데이터 브라우저,
WAF 규칙까지 코어에 넣고 그 근거를 테스트 파일로 보여 주는 방식을 택했다.

이 방식은 기능 목록의 폭이 신뢰를 대신하지 않도록 만든다.
다만 기능 하나하나의 운영 경험은 시간이 지나야 쌓인다.
저장소 생성 일주일 차의 Stable 표시는 기능이 어떻게 테스트되는지를 알려 줄
뿐이고, 몇 달 동안 실제 부하를 견딘 기록은 아니다.
따라서 도입을 검토한다면 README의 Experimental 네 항목보다 Stable 항목 중 자신의
운영에 핵심인 것 몇 개를 골라 직접 시험하는 편이 정보가 많다.

### AI 에이전트로 만든 프로젝트는 출처와 검증 방식을 먼저 밝히는 쪽이 신뢰를 얻는다

README는 개발에 AI 코딩 에이전트를 상당히 썼고 사람의 검토와 테스트를 거쳤다고
한 문장으로 밝힌다.
이 문장은 짧지만 이 프로젝트를 평가하는 방식을 바꾼다.
독자는 사람이 손으로 쓴 코드를 평가하는 기준 대신 테스트 근거를 확인하려 하고,
Stable 표의 구조는 그 확인을 쉽게 만든다.

Experimental 항목의 사유가 구체적인 점도 같은 맥락이다.
테스트가 터널을 시작하지 않는다거나 예약 실행이 발화하는 테스트를 찾지 못했다는
설명은 무엇이 검증되지 않았는지를 말해 준다.
검증되지 않은 부분을 구체적으로 적는 것은,
AI가 만든 큰 코드베이스에서 독자가 가장 알고 싶은 정보다.
