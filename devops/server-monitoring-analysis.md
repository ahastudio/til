# 서버 모니터링 대시보드를 읽는 법: 증상에서 원인으로

원문: [서버 모니터링 분석 가이드 | kciter.so](https://kciter.so/posts/server-monitoring-analysis-guide/)

GN 토론: <https://news.hada.io/topic?id=34478>

## 소개

kciter(이선협)가 2026년 7월 20일에 쓴 글이다.
대시보드를 설치하고 만드는 가이드는 많지만, 만든 대시보드를 읽고 문제를 진단하는 가이드는 드물다는 문제의식에서 출발한다.
그래서 이 글은 도구 설정이 아니라 그래프를 읽는 순서와 패턴을 다룬다.
원문은 그래프 모양을 애니메이션으로 보여 주는데, 이 노트는 그 애니메이션이 말하는 판단 규칙을 글로 옮긴다.

뼈대는 두 가지다.
하나는 Google SRE가 말하는 네 가지 황금 신호, 즉 트래픽, 지연 시간, 에러, 포화도다.
다른 하나는 지표를 증상과 원인으로 나누는 관점이다.
지연과 에러는 사용자가 실제로 겪는 증상이고, CPU와 메모리와 풀 같은 리소스 지표는 원인 쪽이다.
분석은 언제나 증상에서 시작해 원인으로 범인을 좁히고, 알람도 원칙적으로 증상에 건다.

CPU가 90%여도 응답이 빠르면 당장 사람을 깨울 일은 아니고, CPU가 20%여도 응답이 느리면 문제다.
순간적인 CPU 80% 알람은 새벽에 사람을 깨우고 아무 일도 아닌 경우가 많지만, 에러율 알람이 울렸다면 누군가 실제로 문제를 겪고 있다.

## 동작 방식

### 증상 1: 트래픽은 모양과 분모로 읽는다

트래픽 그래프에서 먼저 익힐 것은 이상 패턴이 아니라 평소 모양이다.
평소의 절반이라면 정상 범위 안이어도 무언가 잘못된 것이다.

| 모양                   | 의미                                              |
| ---------------------- | ------------------------------------------------- |
| 수직 하락              | 서버가 한가한 게 아니라 요청이 도달하지 못하는 것 |
| 수직 상승              | 바이럴, 크롤러, 공격                              |
| 새벽마다 규칙적 급등   | 배치 작업이나 크론                                |
| 장애 중 서버 지표 평온 | LB, DNS, 게이트웨이 같은 앞단 문제일 가능성       |

트래픽은 분모이기도 하다.
같은 에러 500건도 분당 요청이 백만 건일 때와 천 건일 때 심각도가 전혀 다르다.
에러든 슬로 쿼리든 개수를 보면 반드시 트래픽으로 나눠 비율로 읽는다.

### 증상 2: 지연은 평균이 아니라 백분위로 읽는다

모든 요청이 100ms 근처인 서버와, 대부분 30ms인데 일부가 900ms씩 걸리는 서버의 평균은 똑같이 100ms일 수 있다.
평균은 분포의 모양을 지운다.
그래서 지연은 P50, P95, P99로 읽는다.

글은 P99의 1%를 무시하면 안 되는 이유를 두 가지 든다.
초당 1,000건이면 매초 10명, 하루 86만 건이 P99를 맞는다.
그리고 화면 하나에 API를 40번 호출하면 모든 호출이 P99를 피할 확률은 0.99의 40제곱, 약 67%다.
사용자 셋 중 하나는 화면 어딘가에서 꼬리 지연을 겪는다.
게다가 꼬리에 걸리는 사용자는 무작위가 아니라, 데이터가 많아 무거운 쿼리를 만드는 헤비 유저일 가능성이 높다.

기준은 이렇게 잡는다.
사용자 경험의 대푯값은 P50, 알람과 성능 목표는 P95나 P99다.
장애의 전조는 거의 항상 P99에 먼저 나타난다.

### 증상 3: 에러는 종류와 실패 속도로 읽는다

에러율이 뛰면 첫 질문은 몇 퍼센트인가가 아니라 어떤 에러인가다.
5xx는 언제나 우리 문제다.
4xx는 명세상 클라이언트 잘못이지만, 배포 직후 400이나 401이 급증했다면 우리가 API 계약을 깨뜨렸을 가능성이 높다.

다음은 실패하는 속도다.
타임아웃은 몇 초씩 스레드와 커넥션을 붙잡다가 실패하므로 에러와 포화를 동시에 일으킨다.
커넥션 거부나 널 참조는 밀리초 안에 5xx를 내므로 자원은 오히려 여유로워진다.

| 에러율 | P99            | 해석                             |
| ------ | -------------- | -------------------------------- |
| 상승   | 상승           | 어딘가가 느려지며 죽어 가고 있음 |
| 상승   | 정상 또는 개선 | 무언가가 즉시 실패하고 있음      |

두 번째 줄이 함정이다.
즉시 실패한 요청은 지연 분포에서 빠지거나 밀리초짜리 표본으로 섞이므로, 장애가 심해질수록 P99가 좋아 보일 수 있다.
에러율은 최악인데 응답 시간이 평소보다 좋다면 회복이 아니라 생존자 편향을 의심한다.

### 원인 1: CPU는 응답 시간과 겹쳐서만 읽는다

리소스 지표는 혼자 읽으면 거짓말을 한다.
CPU 90%가 문제인지는 CPU 그래프가 아니라 응답 시간이 말해 준다.

| CPU              | 응답 시간 | 진단                                                     |
| ---------------- | --------- | -------------------------------------------------------- |
| 트래픽 따라 완만 | 낮고 안정 | 건강                                                     |
| 20~30%로 한가    | 폭증      | 스레드가 무언가를 기다림(DB, 락, 풀 고갈, 외부 API)      |
| 100% 직선        | 폭증      | 트래픽도 올랐으면 용량 부족, 트래픽이 그대로면 코드 문제 |

두 번째 줄이 가장 헷갈린다.
CPU가 놀고 있으니 서버는 괜찮다고 결론 내리고 싶지만, 대부분은 정반대다.
이 패턴에서는 CPU 그래프를 넘어가고 I/O와 풀 지표를 본다.

컨테이너 환경이라면 CPU limit 스로틀링을 확인한다.
Kubernetes의 CPU limit은 리눅스 CFS 할당량으로 구현되어, 기본 100ms 주기마다 정해진 CPU 시간만 쓰고 다 쓰면 주기가 끝날 때까지 멈춘다.
500m이면 주기당 50ms, 2코어면 200ms다.
할당량은 CPU 시간이라 스레드가 나눠 쓰므로, 2코어 limit에서 스레드 8개가 동시에 돌면 25ms 만에 200ms를 소진하고 남은 75ms 동안 통째로 멈춘다.
CPU 사용률은 쓴 시간의 기록이라 기다린 시간은 남지 않는다.
그래서 CPU 사용률 옆에 스로틀 지표를 두고, P99가 튈 때 스로틀 횟수도 오르는지 본다.

### 원인 2: 메모리는 봉우리가 아니라 바닥을 본다

JVM이나 Node.js의 메모리 그래프가 차오르다 뚝 떨어지기를 반복하는 톱니 모양은 GC가 일하는 정상 신호다.
누수는 톱니의 최저점으로 알아본다.
건강한 서버의 최저점은 수평이고, 누수가 있으면 최저점이 계단처럼 올라간다.

최저점이 우상향하면 힙 한계에 가까워질수록 GC가 잦아지며 응답 시간이 먼저 나빠지고, 결국 OOM으로 죽는다.
그 자리에서 원인을 찾지 말고 힙 덤프를 남긴 뒤 재시작으로 시간을 번다.

톱니 위에서 메모리가 수직으로 뛰는 계단은 대량 데이터를 한 번에 올리는 요청이다.
전체 조회, 대용량 파일 처리, 엑셀 다운로드가 단골이다.
계단이 찍힌 시각과 액세스 로그를 대조하면 범인 요청이 나온다.

### 원인 3: 풀은 리틀의 법칙으로 읽는다

동시에 처리 중인 요청 수는 초당 유입량에 평균 처리 시간을 곱한 값이다.
초당 1,000건에 평균 50ms면 동시 요청은 50개라서 Tomcat 기본 스레드 200개로 여유롭다.
그런데 슬로 쿼리로 평균 처리 시간이 2초가 되면, 트래픽이 그대로여도 동시 요청은 2,000개가 된다.
스레드 200개는 순식간에 마르고 1,800개가 큐에 쌓인다.

여기서 연쇄 장애가 시작된다.
스레드가 전부 DB 대기에 묶이면 로드 밸런서 헬스 체크도 처리되지 못하고, LB는 그 서버를 빼고, 남은 서버가 더 빨리 마른다.
재시작해도 같은 DB에 물리는 순간 다시 쓰러지고, 클라이언트와 게이트웨이의 재시도가 트래픽을 두세 배로 불린다.
장애 이후 트래픽이 오히려 치솟았다면 사용자가 늘어난 게 아니라 같은 사용자가 여러 번 두드리는 것이다.

그래서 스레드 풀 지표는 사용률의 절댓값보다 기울기를 본다.
P99가 서서히가 아니라 수직으로 뛰었다면 어딘가의 풀이 방금 말랐을 가능성이 높다.

커넥션 풀은 같은 수학을 더 작은 숫자로 겪는다.
HikariCP 기본 풀 크기는 10개라서, 스레드 200개가 커넥션 10개를 나눠 쓰면 커넥션 풀이 먼저 마른다.
이때 반사적으로 풀 크기를 늘리면 느린 DB 앞에 줄을 더 길게 세울 뿐이고, DB는 동시 세션이 늘어 더 느려질 수 있다.
올바른 질문은 풀이 작은가가 아니라 왜 반납이 느려졌는가다.

### 원인 4: 이벤트 루프 서버는 루프 지연과 프로세스 단위로 읽는다

Node.js나 Netty 기반 서버에는 요청을 전담하는 스레드 풀이 없다.
스레드 하나가 이벤트 루프를 돌리므로, CPU를 오래 쓰는 작업 하나가 루프를 잡는 순간 그 프로세스의 모든 요청이 멈춘다.
핵심 지표는 루프가 한 바퀴 도는 데 예정보다 얼마나 늦어지는가, 즉 이벤트 루프 지연이다.

이 지표는 평균이 아니라 최대치나 높은 백분위로 본다.
밀리초 샘플 수천 개 사이에 1초짜리 정지 한 번이 끼면 평균은 거의 움직이지 않는다.
절대 기준 대신 평소 값 대비 수십 ms 이상 높은 상태가 지속되는지를 본다.
원인은 대개 커진 JSON 직렬화, 백트래킹이 폭발하는 정규식, 루프 위의 암호화 연산이다.
같은 원리를 브라우저 쪽에서 다룬 글이 같은 저자의 비싼 메인 스레드다(`frontend/main-thread-is-expensive.md`).

Node는 스레드 대신 프로세스를 늘리므로 지표도 프로세스 단위로 쪼갠다.
프로세스 여덟 개의 평균 CPU 40%는 일곱 개가 25%이고 하나가 100%에 붙어 죽어 가는 상황을 숨긴다.

### 겹쳐 읽기: 병목, 큐, 캐시, 타임아웃

병목 앞에는 대기가 쌓이고 뒤는 한가하다.
전체 처리량은 가장 좁은 단이 정하므로, 병목이 아닌 곳을 증설해도 전체는 빨라지지 않는다.

대기는 사용률에 비례해서 늘지 않는다.
사용률 50%의 대기를 1이라 하면 80%에서 4배, 90%에서 9배, 95%에서 19배다.
이 숫자는 단일 서버 큐의 대기가 사용률 ρ에 대해 ρ/(1−ρ)로 늘어나는 모양에서 나온다.
오토스케일 임계값 80%는 곡선이 꺾이는 이 지점에서 얻은 휴리스틱이다.
P99가 트래픽 증가보다 가파르게 나빠지기 시작하면, 병목을 손볼 마지막 여유 구간에 들어선 것이다.

큐는 공짜가 아니다.
처리량보다 유입이 지속적으로 많으면 자라나는 큐는 모두의 대기 시간을 늘리는 부채가 되고, 대기가 클라이언트 타임아웃을 넘으면 아무도 받지 않는 응답을 만들다 OOM으로 끝난다.
해법은 큐에 상한을 두고 넘치면 429로 즉시 거부하는 로드 셰딩이다.
건강한 큐 그래프는 출렁여도 반드시 평형으로 돌아오고, 우상향을 멈추지 않으면 흐름 제어가 없거나 부족하다.

캐시 히트율 97%는 DB가 트래픽의 3%에 맞춰져 있다는 뜻이다.
인기 키의 TTL이 만료되는 캐시 스탬피드 순간, DB는 평소에 받지 않던 일을 받는다.
DB 부하가 튀면 DB를 파기 전에 히트율 그래프가 같은 시각에 떨어졌는지 본다.

게이트웨이 타임아웃이 3초인데 백엔드 쿼리가 5초면, 사용자는 3초 만에 504를 받고 백엔드는 5초 뒤 성공을 기록한다.
백엔드 지표에는 실패가 없고 게이트웨이 지표에는 성공이 없는 모순이 생긴다.
안쪽 계층의 타임아웃을 바깥보다 짧게, 예를 들어 게이트웨이 3초에 DB 2.5초로 잡는 타임아웃 예산이 해법이다.

## 진단 순서

### 증상 조합에서 용의자로

글이 정리한 조합을 그대로 옮긴다.

| 조합                             | 먼저 볼 곳               | 가능한 원인                      |
| -------------------------------- | ------------------------ | -------------------------------- |
| P99 급증 + CPU 급증              | 트래픽                   | 용량 초과, 코드 문제             |
| P99 급증 + CPU 한가              | DB 응답 시간, 풀 대기    | I/O 병목, 락 경합, 풀 고갈       |
| 모든 API가 동시에 느림           | DB, 캐시, 공용 풀        | 공유 자원                        |
| 특정 API만 느림                  | 그 API의 쿼리, 외부 호출 | 그 API의 코드                    |
| 에러율 급증 + P99 정상 또는 개선 | 배포 이력, 의존 서비스   | 즉시 실패하는 버그나 의존성 다운 |
| 한 계층은 에러, 다른 계층은 성공 | 계층별 타임아웃          | 조율되지 않은 타임아웃           |

전부 느린가 일부만 느린가라는 판단 하나로 용의선상이 절반으로 준다.

### 시점마다 다른 질문

같은 대시보드에 평시, 장애 중, 장애 후는 서로 다른 질문을 던지고, 셋을 섞는 것이 가장 흔한 실수다.

평시에는 하루 5분씩 대시보드를 돌며 평소 모양을 눈에 익히고, 그 기준선으로 알람을 설계한다.
서서히 나빠지는 것은 알람이 잡지 못하므로, 오늘 P99 위에 지난주 같은 요일 P99를 겹친 주간 비교 패널을 둔다.

배포 직후 30분이 가장 위험하다.
원문은 SRE 책을 인용해 장애의 약 70%가 실행 중인 시스템에 대한 변경에서 온다고 쓴다.
배포 시각을 그래프에 마커로 남기는 것이 비용 대비 효과가 가장 큰 개선이다.
배포 직후 P99가 두세 배 뛰는 것은 JIT, 빈 로컬 캐시, 새 커넥션 때문에 정상일 수 있고, 구분은 값이 아니라 방향으로 한다.
몇 분에 걸쳐 우하향하면 워밍업이고, 내려오지 않으면 롤백을 고려한다.

장애 중에는 영향 범위 확인(트리아지), 최근 변경 확인, 복구 우선, 그다음에야 가설 기반 진단 순서로 간다.
그래프 스무 개를 띄워 튀는 게 없나 훑지 말고, 커넥션 대기가 올랐을 것이라는 식의 가설을 세운 뒤 그래프 하나로 채택하거나 버린다.

장애 후에는 첫 흔적, 알람, 대응 시작, 복구라는 네 시각을 찍어 감지의 공백과 대응의 속도를 본다.
원인은 표면에서 한 겹 더 들어가 적고, 사람 이름은 원인 칸에 넣지 않는다.

## 함정

### 대시보드가 평온한 것이 가장 큰 이상 신호일 수 있다

앞단에서 요청이 막히면 뒷단 서버 그래프는 오히려 평화로워진다.
에러율 급증과 P99 개선이 함께 오는 생존자 편향도 같은 부류다.
지표가 좋아졌다는 사실만으로 회복을 판단하지 않는다.

### 풀 크기를 늘리는 반사 행동

connection timeout 로그는 풀을 키우라는 신호처럼 보인다.
하지만 반납이 느려진 원인이 DB라면, 풀을 키우는 것은 DB에 동시 부하를 더 얹는 일이다.
풀 크기를 바꾸기 전에 커넥션 대기 시간과 슬로 쿼리 로그를 나란히 본다.

### 평균으로 집계된 모든 것

지연의 평균, 이벤트 루프 지연의 평균, 프로세스 여러 개의 평균 CPU는 모두 최악의 한 곳을 희석한다.
집계 함수가 평균인 패널은 최댓값이나 백분위 패널로 바꿀 수 있는지 먼저 본다.

### 재시도가 장애를 키운다

재시도에 지수 백오프와 지터가 없고 재시도 총량에 예산이 없으면, 일시 장애가 재시도 폭풍으로 커진다.
장애 이후 트래픽 급증은 사용자 증가가 아니라 재시도로 읽는다.

## 체크리스트

- 알람이 CPU 같은 원인 지표가 아니라 에러율과 P99 같은 증상 지표에 걸려 있는가?
- 에러와 슬로 쿼리를 개수가 아니라 트래픽 대비 비율로 보고 있는가?
- 지연 패널에 평균 대신 P50, P95, P99가 있는가?
- 에러율 패널이 4xx와 5xx로 나뉘어 있는가?
- 컨테이너 환경에서 CPU 사용률 옆에 스로틀 지표가 있는가?
- 메모리 패널에서 GC 이후 최저점의 추세를 볼 수 있는가?
- 스레드 풀과 커넥션 풀의 활성 수와 대기 시간이 대시보드에 있는가?
- Node 서버라면 프로세스별 이벤트 루프 지연을 최대치나 백분위로 보고 있는가?
- 캐시 히트율과 DB 부하가 같은 시간축에 있는가?
- 안쪽 계층의 타임아웃이 바깥 계층보다 짧은가?
- 배포 시각이 그래프에 마커로 표시되는가?
- 배포 후 롤백 기준이 숫자로 미리 합의되어 있는가?
- 지난주 같은 요일과 겹쳐 보는 비교 패널이 있는가?

## 기억할 원칙

### 리소스 지표는 증상과 겹쳤을 때만 의미를 가진다

이 글의 거의 모든 패턴은 같은 모양이다.
CPU 20%는 응답 시간이 폭증할 때만 대기 문제를 뜻하고, 메모리 계단은 액세스 로그와 겹칠 때만 범인을 가리키고, DB 부하는 히트율과 겹칠 때만 캐시 문제로 읽힌다.
그래프 하나를 보고 결론을 내리고 싶어질 때, 같은 시각의 증상 그래프를 옆에 놓는 것이 첫 동작이다.

### 평소를 모르면 이상도 모른다

트래픽의 평소 모양, P99의 평상시 값, 루프 지연의 기준선, 배포 때 출렁이는 폭까지, 이 글이 요구하는 판단은 대부분 평소 값을 알고 있다는 전제 위에 있다.
그 전제는 장애 중에 만들 수 없다.
하루 5분의 평시 관찰이 장애 한복판의 판단 속도를 정한다.
