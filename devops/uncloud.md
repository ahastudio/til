# Uncloud: 컨트롤 플레인 없는 여러 서버용 Docker Compose

<https://uncloud.run/>

<https://github.com/psviderski/uncloud>

HN 토론: <https://news.ycombinator.com/item?id=46144275> (403점, 181개 댓글)

GN 토론: <https://news.hada.io/topic?id=24862>

## 소개

Uncloud는 여러 서버에 컨테이너화된 웹 애플리케이션을 배포하고 확장하는 오픈소스 도구다.
홈페이지가 스스로를 **“프로덕션용 멀티 노드 Docker Compose”**라고 소개한다.

핵심 주장이 부제에 다 들어 있다.
클러스터 관리 오버헤드 없이 클라우드 서버나 자체 하드웨어에 웹 앱을 배포한다는 것이다.
Docker 호스트들을 안전한 WireGuard 네트워크로 연결해 **호스트 간 통신, 무중단 배포, HTTPS를 기본 제공**한다.

스스로를 Kubernetes, Swarm, Nomad, Kamal의 더 단순한 대안이라고 명시한다.

홈페이지에 적힌 수치는 GitHub 스타 5.2K 이상, 다운로드 21K 이상, Hacker News 프런트 페이지 2회, Discord 팬 390명 이상이다.

가장 눈에 띄는 인용은 CoreDNS 제작자이자 전 Google SRE인 Miek Gieben의 것이다.
Radboud 대학에서 **300개 이상의 웹사이트를 열 몇 대의 Uncloud 머신으로 옮기는 중**이며, 각 소유자가 자기 머신을 받아 필요한 것을 직접 돌리게 한다는 내용이다.

제작자 Pasha Sviderski가 HN 스레드에서 만든 동기를 직접 밝혔다.[^psviderski]
소규모 환경과 유니콘 기업 양쪽에서 Kubernetes를 운영해 온 끝에, 팀들이 K8s를 꺼내 드는 상황이 사실은 **몇 대의 머신에서 컨테이너를 돌리고 네트워킹과 롤아웃과 HTTPS만 필요한 경우**라는 것을 반복해서 봤다는 것이다.
필요한 것에 비해 K8s의 운영 오버헤드가 가혹하다고 적었다.

## 동작 방식

### 컨트롤 플레인이 없다

이것이 이 도구의 정체성이다.

각 머신이 클러스터 상태의 사본을 p2p로 동기화한다. 유지해야 할 쿼럼이 없다.
상태 복제는 Fly.io의 **Corrosion**을 쓴다. CRDT와 가십 프로토콜 기반이다.[^jabr-corrosion]

FAQ가 Swarm과의 차이를 직접 설명한다.
Swarm은 매니저 노드의 Raft 쿼럼이 필요하고 수년째 유지보수 모드인데, Uncloud에는 컨트롤 플레인이 아예 없다는 것이다.
머신들이 상태를 피어 투 피어로 동기화하므로 **어떤 부분집합이든 계속 동작한다**.

제작자가 이 설계의 이점을 더 구체적으로 답했다.[^psviderski-cp]
모든 머신이 동등한 네트워크로 연결되는 훨씬 단순한 모델이라는 것이다.
HA 3노드 중앙 “클러스터 두뇌”를 걱정할 필요가 없고, **etcd 쿼럼을 잃으면 클러스터를 쓸 수 없게 되는** 상황이 아예 생기지 않는다.

그리고 네트워크가 분단되어도 각 파티션이 계속 동작해 앱을 개별적으로 배포하고 업데이트할 수 있다고 덧붙였다.
본질적으로 **k8s 이전 시대에 Chef와 Ansible로 하던 일을, 보일러플레이트 없이 k8s에서 배운 것을 적용해 하는 것**이라는 정리다.

### 머신을 연결한다

SSH만 있으면 된다.

```bash
# 첫 머신으로 클러스터를 초기화한다. Docker와 데몬을 알아서 설치한다
uc machine init --name prod-1 root@152.67.101.197

# 두 번째 머신을 붙인다
uc machine add --name prod-2 root@65.21.45.67

uc machine ls
```

출력은 이런 모양이다.

```text
NAME    STATE  ADDRESS        PUBLIC IP      WIREGUARD ENDPOINTS
prod-1  Up     10.210.0.1/24  137.123.45.67  10.0.0.95:51820, 137.123.45.67:51820
prod-2  Up     10.210.1.1/24  65.21.45.67    192.168.40.243:51820, 65.21.45.67:51820
```

각 머신이 WireGuard 메시에 참여해 자동으로 피어를 찾고 NAT 트래버설을 수행한다.
클라우드 VM과 베어메탈을 섞을 수 있고, NAT 뒤의 라즈베리 파이까지 붙는다고 제작자가 적었다.
메모리 사용량은 150MB 미만이다.

### 배포한다

표준 `compose.yaml`을 그대로 쓴다.

```bash
uc deploy
```

이 한 명령이 이미지를 빌드하고, 머신으로 곧장 푸시하고(없는 레이어만 전송), 무엇이 바뀔지 계획을 보여 준다.
확인하면 무중단으로 롤아웃한다.

레지스트리가 필요 없는 부분은 제작자의 다른 프로젝트 **Unregistry**가 담당한다.
설정하거나 비용을 내거나 인증할 레지스트리가 없다는 뜻이다.

계획 출력이 Terraform을 닮았다.

```text
Deployment plan
~ update service web
│ ~ image: app/web:2026-04-10-070838.07e380b → app/web:2026-04-23-053642.833b6c1
│   replicas: 2
├── +/- replace container web/2de0ebf7eld5 on prod-1
╰── +/- replace container web/4c908f74ced5 on prod-2
───────────────────────────────────────────
2 replace (start-first) · across 2 machines
Proceed with deployment? [y/N]
```

### 연결하고 공개한다

서로 다른 머신의 서비스들이 비공개 WireGuard 메시 위에서 이름으로 서로를 찾는다.
데이터베이스는 **공개 포트를 열 필요가 없다**.

```yaml
services:
  web:
    build: .
    environment:
      # 다른 머신의 db에 서비스 이름으로 접근한다
      DATABASE_URL: postgres://db:5432/app
    # Caddy 인그레스로 공개하는 Uncloud 전용 확장
    x-ports:
      - app.example.com:8080/https
    scale: 2

  db:
    image: postgres:18
    volumes:
      - db-data:/var/lib/postgresql
```

내장 Caddy가 컨테이너 변경이 있을 때마다 설정을 갱신하고, Let's Encrypt 인증서를 발급하고 갱신한다.

DNS에는 `nearest.` 접두사가 있다.
같은 머신에서 도는 인스턴스를 우선 쓰게 하는 기능으로, 한 사용자가 전역 복제된 NATS 서비스를 `nearest.nats.internal`로 접속해 쓴다고 전했다.[^jabr]
`compose.yaml`에서 서비스를 어느 머신에 배포할지 지정할 수도 있으므로, 데이터베이스와 웹 앱을 같은 머신에 모으는 것도 가능하다.

### 스케일링은 자동이 아니다

이 부분이 명시적인 설계 결정이다.

복제본을 여러 머신에 퍼뜨려 가용성을 높이고, 용량이 필요하면 머신을 추가하고, 물릴 머신은 제거하고 재배포한다.

스스로 스케일하거나 재스케줄하는 것은 **아무것도 없다**.
홈페이지가 이것을 “예측 가능하고 지루한 인프라”라고 부른다.

FAQ가 머신이 죽었을 때를 설명한다.
잃을 컨트롤 플레인이 없고 다른 머신의 건강한 복제본이 계속 트래픽을 처리한다.
Uncloud는 **의도적으로 컨테이너를 자동 재스케줄하지 않는다**. 머신을 언제 교체하고 재배포할지는 사용자가 정한다.

오토스케일링 질문에 제작자는 없으며 적어도 당장은 범위 밖이라고 답했다.[^DeathArrow-reply]

### 문제를 찾는다

밑에 있는 것이 Docker와 WireGuard와 Caddy뿐이다.

```bash
uc logs -f web              # 머신·컨테이너 표시가 붙은 로그
uc caddy config             # 실제 적용 중인 Caddy 설정
uc exec web -- ping -c1 db  # 컨테이너 사이 연결 확인
uc wg show --machine prod-1 # WireGuard 피어와 핸드셰이크 상태
```

한 사용자가 이 점을 가장 높이 평가했다.
단순하고 익숙한 기술 위에 만들어져서 **뭔가 잘못되면 스스로 디버깅할 수 있다는 확신**이 들며, SwarmKit이나 etcd에 대해서는 같은 말을 할 수 없다는 것이다.

## 분석

### 반대한 것은 Kubernetes가 아니라 컨트롤 플레인이다

이 프로젝트를 “K8s는 무겁다”는 흔한 불만의 또 다른 표현으로 읽으면 요점을 놓친다.

경량 K8s는 이미 많다. k3s가 대표적이고, HN 스레드에서도 여러 번 언급되었다.
그러니 “무게”가 문제라면 Uncloud를 만들 이유가 없다.

Uncloud가 제거한 것은 크기가 아니라 **상태를 합의로 유지하는 구조 자체**다.

이 차이가 실패 모드를 바꾼다.
쿼럼 기반 시스템에서는 과반을 잃으면 애플리케이션이 멀쩡히 돌아도 클러스터를 조작할 수 없다. 배포도 롤백도 막힌다.
p2p 동기화 시스템에서는 그런 전역 상태가 없으므로 남은 머신들에 대한 조작이 그대로 가능하다.

제작자가 네트워크 분단 시 각 파티션이 독립적으로 배포를 계속할 수 있다고 말한 것이 이 지점이다.
이것은 성능 최적화가 아니라 **일관성을 가용성과 교환한 선택**이다.

HN에서 JohnMakin이 정면으로 물었다.[^JohnMakin]
컨트롤 플레인이야말로 Kubernetes의 핵심 기능이고 없이 지내고 싶지 않다는 것이다.
수백 노드와 1만 컨테이너를 운영하지만 1년에 한 번 업데이트하면 관리형 클러스터가 알아서 이미지와 버전을 올려 준다며, 이 고통이 **자체 호스팅하는 경우에서 오는 것이냐**고 물었다.

정확한 질문이다. 그리고 답은 그렇다는 쪽이다.

관리형 K8s를 쓰면 컨트롤 플레인의 운영 부담이 클라우드 제공자에게 넘어가므로 이 프로젝트가 푸는 문제 자체가 존재하지 않는다.
제작자도 그 점을 인정하면서, 자체 호스팅에서는 가용성을 스스로 걱정해야 한다고 답했다.

### 문제를 푼 게 아니라 다시 정의했다

kelnos가 규모 감각의 차이를 짚었다.[^kelnos]
수백 노드와 1만 컨테이너가 “상대적으로 작다”는 표현에 동의하지 않으며, 자기는 노드 2대에 컨테이너 10개 정도이고 잘되면 5~7대에 30개쯤 될 것 같다는 것이다.
이 정도 규모의 소규모 사업체가 **아주 많을 것 같다**고 덧붙였다.

이 대비가 이 도구의 시장을 정확히 그린다.

Uncloud는 K8s와 경쟁하지 않는다. K8s를 쓸 이유가 없는데 대안이 마땅치 않아 쓰던 사람들을 데려가려는 것이다.
sergioisidoro가 그 자리를 잘 표현했다. Docker Swarm을 써 왔지만 정체되어 간다는 느낌이 커지는데 Dokku는 너무 가볍고 K8s는 너무 무거워서, 이 제안이 **딱 맞는 지점을 친다**는 것이다.[^sergioisidoro]

기존 Compose 선언을 그대로 유지한다는 점을 특히 짚었다.
raphinou도 Swarm 사용자로서 처음으로 흥미로워 보이는 대안이라고 적었다.[^raphinou]

여기에 Dokku 메인테이너 josegonzalez가 직접 등장해 Dokku의 어떤 점이 “가볍다”고 느끼는지 피드백을 듣고 싶다고 답했다.[^josegonzalez]
이 짧은 교환이 이 영역이 얼마나 촘촘하게 붐비는지를 보여 준다.

### 익숙함이 진입 장벽을 결정한다

Nomad는 왜 안 되느냐는 질문이 나왔다.[^stevefan1999]

두 가지 답이 붙었다.
tontony는 Nomad에도 실질적인 학습 곡선이 있는데 Docker와 Compose를 이미 아는 사용자에게 Uncloud의 학습 곡선은 거의 없다고 답했다.[^tontony-nomad]
m1keil은 더 짧게 정리했다. **Nomad도 결국 컨트롤 플레인이 남는다**는 것이다.[^m1keil]

이 두 답이 이 프로젝트의 차별점을 그대로 요약한다. 새 DSL이 없다는 것과 컨트롤 플레인이 없다는 것이다.

k3s와의 비교 질문에는 tontony가 Uncloud가 Kubernetes 배포판이 아니고 K8s 프리미티브를 쓰지도 않으며, 서비스를 선언하고 관리하는 방식에서 **Compose/Swarm에 더 가깝다**고 답했다.[^tontony-k3s]

Coolify 사용자 scottydelta의 질문에 대한 답이 계층을 명확히 한다.[^scottydelta]
제작자는 Uncloud가 더 낮은 계층이고 CLI 전용이며 중앙 서버가 없다고 설명했다.[^psviderski-coolify]
그리고 현재의 Uncloud를 **Coolify 같은 상위 PaaS를 만드는 데 쓸 수 있는 프리미티브와 기반**이라고 표현했다.

Dokploy와의 비교에서도 같은 구도가 나온다. Dokploy는 Swarm 위의 웹 UI PaaS이고 Uncloud는 Swarm과 같은 계층이되 운영 모델이 단순하다는 것이다.[^psviderski-dokploy]

## 비평

### 설치 방식이 신뢰 모델을 망친다

이 스레드에서 가장 날카로운 비판이 여기에 있다.

tex0가 좋은 도구이고 아이디어도 마음에 들지만 `uc machine init`이 내부에서 동작하는 방식이 정말 무섭다고 적었다.[^tex0]
**root로 실행되는 `curl | bash`가 많다**는 것이다. 써 보고 싶지만 어떤 머신에도 돌리지 않을 것이라고 했다.

sigmonsays는 더 강하게 말했다.[^sigmonsays]
애플리케이션의 상태를 반드시 밝혀야 하며 실제 코드에서 `curl | bash`를 파이프하는 것이 터무니없다는 것이다.
**이런 투명성 부족으로 다리를 태우게 될 것**이며, 의도는 좋아하지만 구현이 너무 나빠서 아마 다시 보지 않을 것이라고 적었다.

이 비판이 특별히 아픈 이유는 이 프로젝트의 판매 논리와 정면으로 충돌하기 때문이다.

Uncloud는 “내 서버를 내가 통제한다”를 팔고 있다. 벤더 종속이 없고 표준 SSH 도구로 디버깅할 수 있다는 것이다.
그런데 그 통제를 시작하는 첫 명령이 원격 스크립트를 받아 root로 실행한다.

제어권을 되찾으려고 쓰는 도구가 첫 단계에서 **가장 큰 신뢰를 요구하는** 모양이다.

홈페이지는 이 문제를 전혀 언급하지 않는다. `uc machine init` 한 줄이 Docker를 설치하고 데몬을 띄우는 것을 편의로만 제시한다.

### 자동 재스케줄이 없다는 것을 기능으로 팔지만 비용이 있다

홈페이지가 “스스로 스케일하거나 재스케줄하는 것은 아무것도 없다”를 안심의 근거로 제시한다. 예측 가능하고 지루한 인프라라는 것이다.

이 프레이밍이 절반만 정직하다.

자동 재스케줄이 없다는 것은 **머신이 죽으면 그 위의 컨테이너가 돌아오지 않는다**는 뜻이다.
복제본을 여러 머신에 미리 퍼뜨려 두었다면 남은 복제본이 버티지만, 복제본이 1개인 서비스는 사람이 개입할 때까지 내려가 있다.

그리고 대부분의 소규모 배포에서 데이터베이스는 복제본이 1개다.

즉 이 설계는 **상태가 없는 웹 계층에는 잘 맞고 상태가 있는 계층에는 그대로 노출**된다.
홈페이지의 예제 `compose.yaml`이 정확히 그 구성이다. `web`은 `scale: 2`인데 `db`는 단일 인스턴스에 로컬 볼륨이다.

여기에 오토스케일링이 범위 밖이라는 답이 겹치면, 트래픽이 튀는 워크로드는 이 도구의 대상이 아니라는 결론이 나온다.
그것 자체는 정당한 선택이지만, 홈페이지가 “마음의 평화”라는 표현으로 **트레이드오프를 이점으로만 제시**하는 것은 아니다.

### 격리가 없는 상태로 여러 팀을 태울 수 있다고 말한다

홈페이지의 대표 인용이 Radboud 대학 사례다. 각 소유자가 자기 머신을 받아 필요한 것을 돌린다는 구성이다.
그리고 다른 문구는 “팀이나 프로젝트나 고객마다 클러스터를 하나씩 돌릴 만큼 싸다”고 말한다.

그런데 HN에서 raphinou가 물었다. Compose 스택 2개를 배포하면 **한 스택의 컨테이너가 다른 스택의 컨테이너에 모두 접근할 수 있느냐**는 것이다.

제작자의 답은 그렇다는 것이었다.[^psviderski-isolation]
현재 서로 다른 서비스와 스택의 컨테이너 사이에 **네트워크 격리가 없다**.

이것이 홈페이지의 판매 문구와 어긋난다.
“클러스터를 하나씩 돌릴 만큼 싸다”는 말은 격리가 필요하면 클러스터를 나누라는 뜻이니 기술적으로는 일관된다.
하지만 홈페이지는 그것을 비용 이점으로만 제시하고, **격리를 원하면 그 방법밖에 없다는 사실은 말하지 않는다**.

시크릿도 아직 없다.[^tontony-secrets]
Compose config로 주입할 수는 있지만 저장 시 암호화가 없으므로 모두에게 적합하지는 않다는 답이다.

여러 팀이나 고객을 태우겠다는 구성에서 격리와 시크릿이 둘 다 없다는 것은 작은 공백이 아니다.

### 표준을 벗어나는 비용을 다루지 않는다

raw_anon_1111이 조직 관점의 반대를 명확히 적었다.[^raw_anon_1111]
구현 리드로서 **업계 표준이 아니고 클라우드 제공자가 지원하지 않는 것**을 양심상 허용할 수 없다는 것이다.
이력서에 “K8s로 이걸 했다”고 쓰는 편이 낫고, 신입에게 “우리는 K8s를 쓴다”고 말하면 새로 배울 것이 없다는 논리다.
업계에 속해 있다면 그냥 참고 Kubernetes를 배우라고 적었다.

이 댓글에 두 개의 반박이 붙었다.

codegeek은 그런 논리라면 새로운 시도가 아예 없을 것이며, 이것은 누군가 만든 제품의 Show HN이지 모든 기업에 K8s를 대체하라고 요구하는 것이 아니라고 답했다.[^codegeek]

제작자 본인의 답이 더 흥미롭다.[^psviderski-standard]
커리어와 온보딩 측면의 지적이 타당하며 “모두가 안다”는 논리에 반론하기 어렵다고 인정한 다음, 그 사고방식이면 무엇도 도전할 수 없다고 적었다.
**COBOL도 한때 업계 표준이었고**, 베어메탈 서버나 컨테이너 없는 뚱뚱한 VM도 그랬다는 것이다.
누군가는 “이건 필요 이상으로 고통스럽다, 할 수 있으니 다른 걸 해 보고 싶다”고 말해야 했다는 정리다.

그리고 Docker가 처음 나왔을 때의 즐거움을 기억한다며, **k8s 커뮤니티는 시도조차 하지 않는 것 같다**고 덧붙였다.

이 교환 자체는 훌륭하지만, 홈페이지가 이 문제를 전혀 다루지 않는다는 사실은 남는다.
FAQ가 Swarm, 머신 다운, CI/CD, Hub 필요 여부를 다루면서 **채용과 지식 이전이라는 가장 현실적인 반대**는 빠져 있다.

vanillax의 한 줄짜리 반대도 같은 방향이다. Kubernetes는 어렵지 않고, 대부분의 사람에게 어려운 것은 **설명서를 읽는 데 시간을 쓰는 일**이라는 것이다.[^vanillax]

## 인사이트

### 컨트롤 플레인을 없애는 것은 조율을 사람에게 옮기는 일이다

이 프로젝트의 설계를 한 문장으로 요약하면 **자동 조율을 제거하고 그 자리를 사람이 채우게 한 것**이다.

컨트롤 플레인이 하는 일은 상태를 저장하는 것만이 아니다. 원하는 상태와 실제 상태의 차이를 계속 좁히는 일이다.
그 루프를 없애면 차이가 생겼을 때 아무도 좁히지 않는다.

Uncloud는 이것을 “예측 가능함”이라고 부르고, 실제로 그 말이 맞다. 예측 불가능한 재스케줄이 새벽에 일어나지 않는다.

그런데 예측 가능한 것과 대응되는 것은 다르다.

머신이 죽었을 때 Kubernetes는 밤에 알아서 컨테이너를 옮기고 아침에 사람이 확인한다.
Uncloud는 밤에 아무것도 하지 않고 아침에 사람이 옮긴다.

이 차이가 감당 가능한지는 **대응 인력이 있는지**에 달렸다. 머신 수가 아니라.

그래서 이 도구의 진짜 적합 조건은 홈페이지가 말하는 “몇 대의 머신”이 아니다.
**서비스가 몇 시간 내려가도 되는가**, 혹은 **누군가 항상 대응할 수 있는가**다.

Radboud 대학 사례가 이 조건에 잘 맞는다. 각 사이트 소유자가 자기 머신을 갖고 자기가 책임진다.
반면 24시간 SLA가 걸린 단일 서비스라면, 자동 재스케줄이 없다는 것은 사람이 항상 대기해야 한다는 뜻이다.

일반화하면 이렇다.
인프라 도구가 자동화를 줄여 단순해졌다고 말할 때, 줄어든 자동화는 사라진 것이 아니라 **운영자에게 이전된 것이다**.
그 이전이 이득인지는 운영자가 누구인지에 달렸고, 도구는 그것을 알 수 없다.

### 새 오케스트레이터의 진짜 경쟁자는 K8s가 아니라 서로다

이 스레드에서 언급된 이름들을 세어 보면 인상적이다.
Docker Swarm, Nomad, Kamal, Dokku, Dokploy, Coolify, Kubero, k3s, 그리고 직접 조합한 Swarm + Tailscale까지 나왔다.[^c0_0p_]

wg0이 목록을 나열하며 더 추가해 달라고 했고,[^wg0] strzibny는 서버에서 아무것도 돌지 않는 더 단순한 것으로 Kamal을 권했다.[^strzibny]
Kamal에 대해 그가 좋아하는 점이 흥미롭다. **실제로 K8s와 클라우드를 완전히 떠난 회사가 뒷받침하므로 모든 릴리스가 먼저 실전 검증된다**는 것이다.

이 밀도가 의미하는 바가 있다.

“K8s는 과하다”는 진단은 이미 합의되었다. 경쟁은 진단이 아니라 **대안들 사이**에서 벌어진다.

그리고 이 영역에서 승부를 가르는 것은 기능이 아니다.
HisNameIsTor의 한 줄이 그것을 보여 준다. 3개월 전에 이게 있었다면 선택했을 텐데 이제는 Kubernetes를 헛배운 것 같다는 농담이다.[^HisNameIsTor]

즉 이 시장의 진입 장벽은 기술이 아니라 **이미 배운 것을 버리는 비용**이다.

그래서 Uncloud가 Compose 스펙을 그대로 쓰기로 한 결정이 기능 목록에서 가장 중요한 항목이다. 새 DSL이 없다는 것은 버릴 것이 없다는 뜻이다.
반대로 raw_anon_1111의 반대가 강력한 이유도 같다. K8s를 아는 것이 이미 자산이 된 사람에게는 **버릴 것이 많다**.

역사적으로 이 패턴은 반복된다.
새 기술이 이긴 경우는 대체로 더 나았기 때문이 아니라 기존 지식을 덜 버리게 했기 때문이다.
Docker가 LXC를 이긴 것도, Git이 이긴 것도 그런 면이 있었다.

Uncloud의 승부처는 컨트롤 플레인 유무가 아니라 **Compose를 아는 사람의 수**일 가능성이 높다.

### p2p 상태 동기화가 인프라 도구의 기본 부품이 되어 간다

Uncloud가 상태 복제에 Fly.io의 Corrosion을 쓴다는 사실이 이 프로젝트 자체보다 넓은 의미가 있다.

몇 년 전이었다면 이 프로젝트는 Raft를 직접 구현하거나 etcd를 번들해야 했다.
지금은 CRDT와 가십 기반 동기화가 **가져다 쓰는 부품**이 되었다.

같은 스레드에서 Ey7NFZ3P0nzAe가 edgevpn과 iroh를 p2p 구성 요소로 언급했다.[^Ey7NFZ3P0nzAe]
[iroh](../network/iroh-v1-release.md)가 v1을 낸 것도 이 흐름의 일부다. 직접 연결과 NAT 트래버설이 라이브러리로 제공된다.

이것이 왜 중요한가.

분산 시스템에서 가장 어려운 두 가지가 **합의**와 **연결성**이었다.
합의는 CRDT로 우회할 수 있게 되었고(순서가 중요하지 않은 상태에 한해), 연결성은 WireGuard와 NAT 트래버설 라이브러리로 해결되었다.

그 결과 한 사람이 만드는 프로젝트가 **멀티 클라우드 메시 네트워크에 걸친 오케스트레이터**를 내놓을 수 있게 되었다.
Uncloud의 메모리 사용량이 150MB 미만이라는 것도 이 부품들이 가볍기 때문이다.

두 번째 효과가 더 흥미롭다.
이 부품들이 흔해지면 **중앙 집중이 기본값이었던 이유가 사라진다**.
Kubernetes가 etcd를 중심에 둔 것은 2014년에 그것이 가장 검증된 선택이었기 때문이지, 중앙 집중이 본질적으로 옳아서가 아니었다.

앞으로 나올 인프라 도구들이 컨트롤 플레인 없이 설계되는 경우가 늘어날 것이라고 보는 근거가 이것이다.
[Tailscale이나 WireGuard 기반 메시](../vpn/wireguard.md)가 이미 그렇게 쓰이고 있다.

다만 CRDT가 모든 것을 대체하지는 못한다는 점은 남는다.
“두 머신이 동시에 같은 포트를 잡으려 하면 누가 이기는가” 같은 질문에는 **결국 순서가 필요하다**.
Uncloud가 자동 재스케줄을 하지 않기로 한 것이 우연이 아닐 수 있다. 재스케줄은 정확히 그런 결정을 요구하는 기능이다.

즉 컨트롤 플레인을 없앤 대가로 포기한 기능 목록과, CRDT로 표현할 수 없는 결정의 목록이 상당 부분 겹친다.
이 도구가 무엇을 하지 않는지를 보면 그 경계가 보인다.
