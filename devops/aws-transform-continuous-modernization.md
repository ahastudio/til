# AWS Transform이 기술 부채를 상시 스캔해 PR로 고친다

원문: [AWS Transform continuous modernization is now generally available](https://aws.amazon.com/about-aws/whats-new/2026/7/aws-transform-continuous-general-available/)

## 요약

AWS가 2026년 8월 3일 AWS Transform의 상시 현대화(continuous modernization) 기능을 정식 출시
(GA)했다.
엔지니어링 팀이 코드 저장소 전반의 기술 부채를 대규모로 식별하고 해결하게 하는 서비스이며,
AWS Transform이 지원되는 모든 AWS 리전에서 제공된다.

핵심 기능은 다섯 가지다.
소스 코드 통합으로 GitHub 조직, GitLab 그룹, Bitbucket 워크스페이스를 연결하고, 분석을 온디맨드나
정기 일정으로 돌린다.
우선순위 지정은 기술 부채, 보안, 에이전트 준비성(agentic readiness), 현대화 준비성, 커스텀 분석
기준에 걸쳐 발견을 정렬한다.
자동 개선(remediation)은 적격 발견에 대해 브랜치를 만들고 검증된 코드 변경을 담은 풀 리퀘스트나
머지 리퀘스트를 연다.
접근은 AWS Transform 웹 애플리케이션, CLI 도구, IDE 통합(Kiro Power와 agent plugins), 클라우드
컴퓨트 옵션으로 이뤄진다.

기술적 특성으로는 데이터 통제가 강조된다.
분석과 개선이 사용자의 자격 증명으로 사용자의 AWS 계정 안에서 이뤄지고, 소스 코드는 사용자의
통제 아래 남는다.
로컬 분석과 Amazon EC2 또는 AWS Batch를 이용한 원격 분석을 모두 지원한다.

## 분석

### 이 서비스의 핵심 전환은 “일회성 마이그레이션”에서 “상시 스캔”으로다

AWS Transform은 원래 특정 마이그레이션 — .NET 이식, Java 업그레이드 — 을 돕는 일회성 도구였는데,
이 GA는 “continuous(상시)”라는 단어로 그 성격을 바꾼다.
마이그레이션이 이벤트에서 프로세스로, 프로젝트에서 파이프라인으로 이동한다.

이 전환이 중요한 이유는 기술 부채의 성격 때문이다.
기술 부채는 한 번 갚고 끝나는 것이 아니라 계속 쌓이는 것이므로, 일회성 마이그레이션은 그
쌓임을 따라잡지 못한다.
정기 일정으로 저장소를 스캔하고 발견을 PR로 고치는 상시 모델은, 부채를 이벤트가 아니라
지속적 유지보수의 대상으로 다룬다.
CI가 매 커밋에서 테스트를 돌리듯, AWS Transform Continuous는 매 주기에서 부채를 스캔한다.

이 전환이 에이전트 시대와 맞물린다.
“에이전트 준비성(agentic readiness)”이 우선순위 기준의 하나로 들어간 것이 그 신호다 — 코드가
AI 에이전트가 다루기 좋은 상태인지를 부채의 한 종류로 본다.
앞서 여러 문서에서 “AI가 생성 비용을 낮춰 부채가 빠르게 쌓인다”고 했는데[^ref-middle], AWS
Transform Continuous는 그 빠르게 쌓이는 부채를 자동으로 스캔하고 고치는 반대 방향의 힘을
제공한다.

### “검증된 코드 변경”이라는 주장이 이 서비스의 신뢰를 좌우한다

자동 개선의 핵심은 “검증된(validated) 코드 변경을 담은 PR을 연다”는 것이며, 이 “검증됨”이 이
서비스의 값과 위험을 동시에 결정한다.
자동으로 생성된 코드 변경이 실제로 검증됐다면 값이 크고, 검증이 명목뿐이라면 사람의 리뷰
부담만 늘린다.

이 주장이 중요한 이유는 자동 개선의 고전적 함정 때문이다.
정적 분석 도구가 문제를 찾는 것은 쉽지만, 그것을 자동으로 고치는 것은 어렵다 — 수정이 다른
곳을 깨뜨리거나 의도를 오해하거나 표면만 고칠 수 있다.
“검증됨”이 컴파일 통과나 기존 테스트 통과를 뜻한다면 그것은 필요조건이지 충분조건이 아니며,
발표는 그 검증이 무엇을 확인하는지 명시하지 않는다.

이 검증의 성격이 앞서 코드 리뷰 논문에서 본 것과 이어진다.
그 논문에서 “채택된 AI 제안조차 복잡도를 늘린다”고 했는데[^ref-synergy], 자동 개선 PR도 같은
위험을 갖는다 — 부채를 고친다는 PR이 기존 추상을 재사용하는 대신 새 코드를 더해 다른 종류의
부채를 만들 수 있다.
“검증된 코드 변경”이 정말 부채를 줄이는지, 아니면 부채의 형태만 바꾸는지가 이 서비스의 실제
값을 결정하며, 발표는 그 구별을 다루지 않는다.

### 사용자 계정 안에서 실행한다는 설계가 엔터프라이즈 도입의 전제다

기술적 특성 중 “분석과 개선이 사용자의 AWS 계정 안에서 사용자의 자격 증명으로 이뤄지고 소스
코드가 사용자 통제 아래 남는다”는 대목이, 이 서비스의 진짜 설계 판단이다.
코드를 외부로 보내지 않고 사용자 인프라에서 처리하는 것은 엔터프라이즈 도입의 필수 조건이다.

이 설계가 중요한 이유는 소스 코드가 가장 민감한 자산이기 때문이다.
많은 조직이 코드를 외부 서비스로 보내는 것을 정책으로 금지하며, 그 금지가 AI 코드 도구 도입의
가장 큰 장벽이었다.
AWS Transform이 사용자 계정 안에서 EC2나 Batch로 분석을 돌리는 것은, 그 장벽을 우회한다 —
코드는 사용자의 경계를 벗어나지 않고, AWS는 실행 환경만 제공한다.
앞서 uBlock 문서에서 본 “로컬 우선 도구의 시장이 규제에서 나온다”는 관찰이[^ref-ublock] 여기
엔터프라이즈 버전으로 나타난다.

이 설계는 AWS의 구조적 우위를 활용한다.
코드가 이미 AWS 계정에 있고 인프라가 AWS라면, 그 경계 안에서 분석을 돌리는 것은 자연스럽다.
독립 코드 분석 서비스는 코드를 자기 서버로 가져와야 하므로 이 신뢰 장벽에 걸리는데, AWS는
사용자가 이미 신뢰하는 경계 안에서 작동해 그 장벽을 피한다.
이것이 클라우드 제공자가 자기 플랫폼 위에서 개발 도구를 낼 때의 고유한 이점이며, AWS Transform
Continuous는 그 이점을 기술 부채 관리에 적용한다.

## 비평

### 다섯 개의 우선순위 기준을 하나의 서비스로 묶은 것이 각각을 얕게 만든다

발표는 기술 부채, 보안, 에이전트 준비성, 현대화 준비성, 커스텀 기준을 하나의 우선순위 체계로
묶는데, 이 통합이 각 영역의 깊이를 희생할 위험이 있다.
이 다섯은 서로 다른 전문성을 요구하는 영역이다.

이 묶음이 문제인 이유는 각 영역에 이미 전문 도구가 있기 때문이다.
보안에는 SAST/DAST 전문 도구가, 기술 부채에는 SonarQube 같은 도구가, 현대화에는 언어별 마이그레이션
도구가 있고, 각각 깊이 파고든다.
AWS Transform이 이 다섯을 하나로 묶으면 편의는 있지만, 각 영역에서 전문 도구만큼 깊지 못할
가능성이 높다.
“하나의 서비스로 다섯 영역”은 통합의 값을 팔지만, 그 값이 각 영역의 얕음을 정당화하는지는
사용자가 자기 워크로드로 판단해야 하며, 발표는 각 영역의 깊이를 보여주지 않는다.

이 문제가 앞서 xberg 문서에서 본 “101개 포맷을 하나로”와 같은 계열이다[^ref-xberg].
넓이를 파는 도구는 통합의 편의를 주지만, 각 항목의 품질을 보증하지 않는다.
다섯 우선순위 기준의 각각에서 AWS Transform이 얼마나 정확히 발견하고 고치는지 — 보안 취약점의
탐지율, 기술 부채 식별의 정밀도 — 가 도입 판단의 핵심인데, 발표는 그것을 다섯 개의 이름으로만
제시한다.
특히 “에이전트 준비성”과 “현대화 준비성”처럼 새롭고 정의가 모호한 기준은, 무엇을 측정하는지가
불분명해 그 발견을 신뢰하기 어렵다.

### 자동 PR 생성이 리뷰 병목을 만든다는 것을 발표가 다루지 않는다

“브랜치를 만들고 검증된 코드 변경을 담은 PR을 연다”는 자동 개선은 매력적이지만, 그 PR들을
누가 검토하는지가 이 서비스의 실제 부담을 결정한다.
상시 스캔이 정기적으로 PR을 쏟아내면, 그 PR을 검토하는 것이 새로운 병목이 된다.

이 병목이 근본적인 이유는 생성과 검토의 비대칭 때문이다.
자동화는 PR을 병렬로 대량 생성하지만 사람은 순차로 검토하며, 상시 스캔이 그 생성을 지속적으로
만들면 검토 부담이 누적된다.
앞서 middle-class-engineering 문서에서 본 “나쁜 결정 하나를 풀어내는 동안 다섯 개가 더 병합된다”는
관찰이[^ref-middle] 자동 개선 PR에서 반복된다 — 부채를 고치는 PR을 검토하는 동안 새 스캔이 더
많은 PR을 연다.
자동으로 열린 PR을 자동으로 병합하면 검증 없는 변경이 쌓이고, 사람이 검토하면 그 검토가
병목이 된다.

이 문제가 앞서 코드 리뷰 문서들과 정확히 이어진다.
AI가 생성한 변경을 사람이 검토하는 부담이 리뷰의 새 병목이라는 것이 반복된 주제였는데[^ref-synergy],
AWS Transform Continuous는 그 부담을 기술 부채 관리에 도입한다.
“상시 현대화”가 값을 내려면 그 자동 PR의 검증이 실제로 신뢰할 만해서 검토를 최소화할 수 있어야
하는데, 그 신뢰가 “검증됨”이라는 한 단어에 걸려 있고 발표는 그 단어의 내용을 밝히지 않는다.
자동 개선의 진짜 시험은 얼마나 많은 부채를 찾는가가 아니라, 그 PR을 얼마나 안심하고 병합할 수
있는가다.

### “상시”가 만드는 지속적 변경이 코드베이스의 안정성과 긴장한다

상시 스캔과 자동 개선이 만드는 지속적 변경 흐름은, 코드베이스의 안정성과 근본적으로 긴장한다.
정기적으로 부채를 고치는 PR이 열린다는 것은, 코드베이스가 계속 변한다는 뜻이다.

이 긴장이 문제인 이유는 변경 자체가 위험이기 때문이다.
동작하는 코드를 “현대화”하려 바꾸는 것은 새 버그를 넣을 위험을 감수하는 것이고, 그 위험이 고치는
부채의 값보다 클 수 있다.
앞서 SQLite WAL-Reset 문서에서 본 “되돌릴 수 없는 결정이 쌓이는 속도가 조직의 수명을 결정한다”는
관찰이[^ref-sqlite] 여기 적용된다 — 상시 자동 변경은 가역적인 것과 비가역적인 것을 구별하지
않고 지속적으로 코드를 바꾼다.
“에이전트 준비성”을 위한 리팩터링이나 “현대화”를 위한 업그레이드가 안정적으로 돌던 코드를
흔들 수 있으며, 그 흔듦의 누적이 새 부채가 된다.

이 통찰의 실무적 함의는 “언제 고치지 않을지”의 판단이다.
모든 부채를 고치는 것이 아니라 고칠 값이 있는 부채만 고르는 것이 핵심인데, 상시 자동화는 그
선별을 우선순위 알고리즘에 위임한다.
그 알고리즘이 “동작하는 것을 건드리지 말라”는 규율을 얼마나 반영하는지가 이 서비스의 안전성을
결정하며, 발표는 발견을 정렬한다고만 하고 “고치지 않기로 하는” 판단을 다루지 않는다.
자동 개선의 성숙도는 무엇을 고칠 수 있는가가 아니라 무엇을 고치지 말아야 하는지를 아는 데
있으며, 그 판단이 알고리즘에 없으면 “상시 현대화”는 상시 불안정이 된다.

## 인사이트

### 클라우드 제공자가 개발 도구로 확장하며 “신뢰 경계”를 무기로 쓴다

AWS Transform Continuous의 “사용자 계정 안에서 실행”은 이 제품 하나를 넘어 클라우드 제공자의
전략을 드러낸다 — 이미 소유한 신뢰 경계를 개발 도구 시장의 진입 무기로 쓰는 것이다.

이 전략이 강력한 이유는 코드 도구의 가장 큰 장벽이 신뢰이기 때문이다.
독립 코드 분석 서비스는 코드를 자기 서버로 가져와야 하고, 그것이 엔터프라이즈의 보안 정책에
걸린다.
AWS는 사용자의 코드가 이미 자기 클라우드에 있으므로 그 경계 안에서 도구를 돌릴 수 있고, 이는
독립 도구가 복제할 수 없는 구조적 이점이다.
앞서 DynamoDB 문서에서 본 “이미 운영 중인 도구가 벡터 검색을 흡수한다”는 전략이[^ref-ddb]
여기서 “이미 코드를 가진 클라우드가 코드 도구를 흡수한다”로 나타난다.

이 관점의 2차 효과는 독립 개발 도구 시장의 압박이다.
SonarQube, Snyk 같은 독립 코드 분석 도구가 신뢰 경계 밖에서 작동하는 동안, 클라우드 제공자는
경계 안에서 “충분히 좋은” 대안을 제공한다.
전용 도구가 더 깊을 수 있지만, 신뢰 경계 안의 편의가 그 깊이의 값을 상쇄한다.
앞서 SDUI와 벡터 검색 문서에서 본 “기능이지 제품이 아니다” 논쟁이[^ref-ddb] 코드 분석에도
적용되며, 클라우드 제공자가 그 기능을 플랫폼에 흡수하는 것이 독립 도구를 극단으로 밀어낸다.
개발 도구 시장의 다음 경쟁은 기능의 깊이가 아니라 신뢰 경계의 소유이며, 클라우드 제공자가 그
경계를 가졌다.

### 기술 부채의 자동화가 “부채란 무엇인가”라는 정의 문제를 드러낸다

AWS Transform Continuous가 다섯 가지 우선순위 기준으로 부채를 정의하는 것은, 기술 부채가 객관적
사실이 아니라 판단이라는 점을 드러낸다.
무엇이 부채이고 무엇이 정당한 트레이드오프인지는 맥락에 의존한다.

이 정의 문제가 근본적인 이유는 자동화가 정의를 고정하기 때문이다.
사람이 부채를 판단할 때는 “이건 지금 고칠 값이 있고 저건 아니다”라는 맥락적 판단이 개입하는데,
자동 스캔은 미리 정한 기준으로 부채를 식별한다.
그 기준이 “오래된 라이브러리”나 “복잡도 임계 초과”처럼 기계적이면, 정당한 이유로 그 상태인
코드까지 부채로 표시한다.
앞서 코드 리뷰 논문에서 본 “스멜 정의가 특정 규범에서 왔다”는 관찰이[^ref-synergy] 여기 적용된다 —
부채의 정의가 도구에 내장되면, 그 정의가 조직의 실제 우선순위와 어긋날 수 있다.

이 통찰의 함의는 자동 부채 관리의 진짜 과제가 탐지가 아니라 정의라는 것이다.
부채를 찾는 것은 쉽지만, 조직의 맥락에서 무엇이 고칠 값이 있는 부채인지 정하는 것은 어렵다.
“에이전트 준비성”이라는 새 기준이 특히 그렇다 — 코드가 AI가 다루기 좋은 상태여야 한다는 것이
정당한 목표인지, 아니면 도구가 만든 새 부채 범주인지가 불분명하다.
AWS Transform이 다섯 기준으로 부채를 정의하는 순간, 그 정의가 조직의 우선순위를 대체할 위험이
있으며, 커스텀 기준을 허용한 것이 그 위험을 완화하려는 장치다.
자동 부채 관리의 성숙도는 얼마나 많은 부채를 찾는가가 아니라, 조직이 자기 부채 정의를 얼마나
반영할 수 있는가에 있다.

### 상시 현대화가 “현대화가 끝나지 않는다”는 새로운 상태를 만든다

“상시(continuous)”라는 단어가 마이그레이션의 성격을 근본적으로 바꾼다 — 현대화가 도달하는
목표에서 유지하는 상태로 이동한다.
이 전환이 조직의 코드베이스 관계를 바꾼다.

이 변화가 구조적인 이유는 “현대적”의 정의가 계속 움직이기 때문이다.
일회성 마이그레이션은 “X 버전으로 올린다”는 명확한 목표가 있지만, 상시 현대화는 목표가 계속
뒤로 물러난다 — 오늘 현대적인 것이 6개월 뒤 부채가 된다.
CI/CD가 배포를 이벤트에서 상태로 바꿨듯이, 상시 현대화는 부채 관리를 프로젝트에서 상태로
바꾼다.
이는 조직이 “현대화를 끝냈다”고 말할 수 있는 시점이 사라진다는 뜻이다.

이 통찰의 양면성이 중요하다.
긍정적으로는, 상시 현대화가 부채의 누적을 막아 코드베이스를 지속적으로 건강하게 유지한다 —
앞서 여러 문서에서 본 “AI가 부채를 빠르게 쌓는다”는 문제의[^ref-middle] 대응책이다.
부정적으로는, 끝나지 않는 현대화가 지속적 변경의 피로와 불안정을 만들고, 조직이 “충분히 좋음”에
안착하지 못하게 한다.
앞서 choose-boring-technology의 정신 — 검증된 안정적 기술에 안착하는 것 — 과 상시 현대화의
지속적 변경은 긴장한다.
이 서비스가 값을 내려면 “언제 현대화를 멈추고 안정에 안착할지”를 판단하는 규율이 필요하며,
그 규율 없는 상시 현대화는 안정성을 현대성과 맞바꾸는 끝없는 거래가 된다.
상시성의 진짜 지혜는 계속 바꾸는 것이 아니라, 바꿀 값이 있을 때만 바꾸는 절제에 있다.
