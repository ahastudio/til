# Openship - 내장 CI/CD 배포 플랫폼

> Openship - Open Source, Self-Hostable Deployment Platform

<https://openship.io/>

<https://github.com/oblien/openship>

## 소개

Openship은 애플리케이션 배포를 직접 운영하려는 팀을 위한 오픈소스 셀프호스팅
배포 플랫폼이다. 빌드, 배포, 라우팅, TLS 종료를 통한 보안까지 자동화하는 것을
목표로 한다.

## 주요 기능

- 푸시-투-디플로이(GitHub 웹훅 기반)
- Node, Python, Go, Rust, PHP, Ruby, Java, .NET, Docker 등 모든 기술 스택 지원
- 내장 데이터베이스, Let's Encrypt 기반 자동 SSL, CDN 연동, SMTP 메일 서버
- 예약 백업, 실시간 모니터링, 오토스케일링

## 아키텍처

세 가지 컨트롤 플레인 방식으로 배포할 수 있다.

1. **데스크톱 앱**: 1인 개발자를 위한 GUI. SSH로 로컬에서 원격 서버를 제어한다.
2. **셀프호스팅 서버**: 로그인이 필요한 상시 구동형. Docker/엣지를 쓰는
   Compose 모드와 내장 데이터베이스를 쓰는 bare 모드를 지원한다.
3. **Openship Cloud**: 별도 설정 없이 바로 쓰는 매니지드 옵션.

파이프라인은 `package.json`, 락파일, 프레임워크 설정 파일을 읽어 스택과 빌드
명령을 자동 감지하고, Docker 이미지 또는 릴리스를 빌드해 컨테이너로 실행한
뒤 라우팅과 SSL을 관리한다.

## 설치

배포 방식에 따라 설치 경로가 다르다. 데스크톱 앱은 릴리스 페이지에서 내려받고,
CLI는 `curl -fsSL https://get.openship.io | sh`로 설치하며, 셀프호스팅 인스턴스는
`openship up` 명령으로 안내형 설정을 진행한다.

## 라이선스 및 상태

Apache License 2.0으로 배포되는 오픈소스 소프트웨어로, 상용·비공개 파생물
사용도 라이선스 조건 안에서 허용된다.

## 분석

### PaaS의 개발자 경험과 셀프호스팅의 비용 구조 사이를 겨냥한다

Openship이 겨냥하는 지점은 Vercel·Render 같은 매니지드 PaaS와 Coolify·
Dokku 같은 기존 셀프호스팅 도구 사이다. 스택 자동 감지와 웹훅 기반
푸시-투-디플로이로 매니지드 PaaS의 개발자 경험을 재현하면서도, 데스크톱 앱을
통한 로컬 SSH 제어라는 독특한 배포 경로를 추가로 제공한다. 매니지드 PaaS는
사용량이 늘수록 비용이 선형 이상으로 증가하는 구조인 반면, 셀프호스팅은
초기 설정 부담이 크다는 것이 전통적인 트레이드오프였다. Openship은 이 둘
사이의 간극을, 설정 자동화로 셀프호스팅의 진입 장벽을 낮추는 방식으로
메우려 한다.

### 컨트롤 플레인을 세 갈래로 나눈 설계는 사용자층을 명시적으로 구분한다

데스크톱 앱, 셀프호스팅 서버, 매니지드 클라우드라는 세 가지 배포 경로는
단순한 기능 다양화가 아니라 서로 다른 사용자 페르소나를 겨냥한 구조로
읽힌다. 데스크톱 앱은 서버에 상시 프로세스를 두지 않고 SSH로만 제어하므로
1인 개발자가 사이드 프로젝트에 가볍게 붙이기 좋고, 로그인이 필요한
상시 구동형 서버는 여러 인원이 공유하는 소규모 팀에 맞는다. 매니지드
클라우드는 이 모든 운영 부담 자체를 지고 싶지 않은 사용자를 위한
탈출구다. 이는 클라우드 비용을 피하려는 1인 개발자나 소규모 팀이 별도
서버 관리 지식 없이도 자체 인프라를 운영할 수 있게 하려는 설계로
보이며, 하나의 제품이 성장 단계가 다른 사용자를 단계적으로 흡수하도록
설계됐다는 뜻이기도 하다.

### 자동 감지가 실제 도입 난이도를 결정하는 핵심 변수다

`package.json`, 락파일, 프레임워크 설정 파일을 읽어 스택과 빌드 명령을
자동 감지한다는 서술은 짧지만, 이 부분이야말로 제품의 실질적인 완성도를
가른다. "Node, Python, Go, Rust 등 모든 스택을 지원한다"는 주장은 지원
목록의 나열일 뿐이고, 실제로 사용자가 아무 설정 없이 배포에 성공하는지는
감지 로직이 각 언어·프레임워크의 관례를 얼마나 정확히 인식하는지에
달려 있다. monorepo, 커스텀 빌드 스크립트, 여러 언어가 섞인 프로젝트처럼
관례에서 벗어난 구성일수록 자동 감지의 한계가 먼저 드러난다.

## 비평

### "모든 스택 지원"이라는 주장은 검증 불가능한 형태로 제시된다

README가 나열하는 지원 스택 목록은 실제 사용 경험을 재현할 수 있는
근거를 전혀 동반하지 않는다. 어떤 프레임워크의 어떤 버전까지 자동
감지가 검증됐는지, monorepo나 다중 언어 프로젝트 같은 예외 케이스는
어떻게 처리되는지에 대한 정보가 없다. 셀프호스팅 배포 도구의 실제
가치는 지원 언어의 폭이 아니라 예외 상황에서 얼마나 매끄럽게 동작하는지에
있는데, 이 문서는 그 부분을 검증할 수단을 전혀 제공하지 않는다.

### 세 가지 배포 경로의 기능 격차가 불명확하다

데스크톱 앱, 셀프호스팅 서버, 클라우드라는 세 경로가 정확히 같은
기능 집합을 제공하는지, 아니면 일부 기능이 특정 경로에서만 동작하는지가
명확하지 않다. 예를 들어 오토스케일링이나 CDN 연동 같은 기능이 1인
개발자용 데스크톱 앱에서도 완전히 동작하는지, 아니면 사실상 셀프호스팅
서버나 클라우드 전용 기능인지 문서만으로는 판단하기 어렵다. 이런 정보
비대칭은 사용자가 가벼운 용도로 데스크톱 앱을 선택했다가 나중에 필요한
기능이 다른 배포 경로에만 있다는 사실을 뒤늦게 발견하게 만들 위험이
있다.

### 신생 프로젝트의 신뢰도를 판단할 근거가 부족하다

Apache License 2.0이라는 라이선스 정보 외에, 이 프로젝트가 얼마나
활발히 유지보수되고 있는지, 프로덕션에서 실제로 쓰이고 있는 사례가
있는지에 대한 정보는 README 범위 밖에 있다. 배포 플랫폼은 도입
실패 시 되돌리기 어려운 인프라 종속을 만드는 도구인 만큼, 실제 채택
전에는 GitHub 저장소의 커밋 빈도, 이슈 대응 속도, 프로덕션 사용 사례
같은 별도 검증이 필요하다.

## 인사이트

### SSH 기반 제어는 상시 에이전트 없는 배포의 절충안이다

데스크톱 앱이 SSH로 원격 서버를 제어하는 방식은 서버에 상시 실행되는
에이전트를 두지 않아도 되므로, 공격 표면을 줄이면서도 GUI 편의성을
제공하는 절충안으로 눈여겨볼 만하다. 대부분의 PaaS형 배포 도구는 서버에
데몬이나 에이전트를 상주시켜 중앙 제어판과 통신하는데, 이 상주
프로세스 자체가 취약점의 표적이 될 수 있다. SSH는 이미 검증된 인증·
암호화 체계를 그대로 재사용하므로, 새로운 공격 표면을 최소화하면서도
원격 제어라는 목적은 달성한다. 다만 이 방식은 매 명령마다 SSH 세션을
오가야 하므로 실시간성이 필요한 기능(라이브 로그 스트리밍 등)에는
적합하지 않을 수 있고, 그 한계가 이 도구가 데스크톱 앱을 "1인 개발자용"
경로로 한정한 이유일 가능성이 있다.

### 자동 감지 범위가 지원 스택 목록보다 신뢰할 만한 지표다

셀프호스팅 배포 도구를 비교할 때 "얼마나 많은 스택을 지원하는가"보다
"설정 파일에서 자동 감지되는 범위가 어디까지인가"가 실제 도입 난이도를
더 잘 예측하는 지표다. 지원 스택 목록은 마케팅 문구로 쉽게 부풀릴 수
있지만, 자동 감지 로직의 정교함은 실제로 그 도구를 써보지 않는 한
드러나지 않는다. 이는 "몇 개 언어를 지원하는가"를 내세우는 다른
개발자 도구(코드 포매터, 린터, CI 템플릿 등)를 평가할 때도 동일하게
적용되는 원칙이다. 목록의 길이보다 각 항목의 처리 깊이를 확인하는
습관이 도구 선택의 실패를 줄인다.

### 셀프호스팅 배포 도구의 경쟁은 결국 "예외 처리의 완성도" 싸움으로 수렴한다

Coolify, Dokku, CapRover 같은 기존 셀프호스팅 배포 도구들도 이미
스택 자동 감지와 웹훅 배포를 제공해 왔다. Openship이 이 경쟁에서
차별화될 수 있는 지점은 새로운 기능의 존재가 아니라, 기존 도구들이
자동 감지에 실패하는 예외 케이스를 얼마나 더 잘 처리하느냐에 있을
가능성이 크다. 이는 이미 성숙한 카테고리의 신규 진입자가 흔히 마주치는
구조적 문제이기도 하다. 핵심 기능 목록으로는 차별화가 어렵고, 결국
디테일—에러 메시지의 명확성, 실패 시 롤백 동작, 흔치 않은 프로젝트
구조에 대한 대응—에서 우위를 만들어야 하는데, 이런 디테일은 README
수준의 소개 문서로는 절대 검증되지 않는다.
