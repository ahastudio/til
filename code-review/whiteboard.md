# Whiteboard: 에이전트가 그린 다이어그램으로 변경을 이해하는 리뷰 캔버스

<https://whiteboard.dev.fast/>

<https://github.com/devdotfast/whiteboard>

HN 토론: <https://news.ycombinator.com/item?id=49833867> (258점, 97개 댓글)

GN 토론: <https://news.hada.io/topic?id=34245>

## 소개

Whiteboard는 “신중한 소프트웨어 설계를 위한 오픈 소스 캔버스”를 표방하는 데스크톱 앱이다.
사람과 에이전트가 같은 작업 공간에서 함께 소프트웨어를 설계하게 하며, Claude Code나 Codex 같은 기존 도구에 붙어 에이전트에게 앱 안의 캔버스에 그림을 그릴 SDK를 준다.
에이전트는 그 캔버스에 자기가 한 일을 다이어그램으로 설명한다.
MIT 라이선스이고 TypeScript로 작성됐으며, 2026년 8월 18일에 저장소가 만들어져 9월 25일 기준 스타 643개, 포크 27개다.
HN 제출 제목에 따르면 YC W26 회사가 만든다.

빠른 시작은 세 단계다.
앱을 내려받아 열고, 첫 화면에서 Claude Code나 Codex 같은 코딩 에이전트를 연결하고, 에이전트에게 현재 브랜치를 최신 main과 비교해 검토한 결과를 Whiteboard에서 열라고 요청한다.
README는 지능과 비용과 속도의 균형 때문에 GPT-6 Sol과 Claude Opus 5.5 같은 모델에서 가장 잘 동작한다고 적는다.
macOS와 Fedora용 설치 파일이 있다.

## 주요 기능

### 코드로 이어지는 다이어그램

README는 순수 HTML 도구로는 명세나 다이어그램을 코드에 연결하기 어렵다는 문제에서 출발한다.
절충점은 구현을 한 번 해 본 뒤에야 드러나는 경우가 많기 때문에 이 연결이 특히 중요하다는 것이다.
Whiteboard에서는 시퀀스 다이어그램이나 개체 관계 다이어그램이나 에이전트 추적의 인용문을 누르면 그 밑의 코드로 바로 간다.
코드를 탐색할 때는 VS Code의 키 바인딩과 LSP가 그대로 딸려 온다.

### 의미 단위 diff 뷰어

날것의 diff는 잡음이 많으므로, AST를 이해하는 의미 단위 diff 뷰어를 Rust로 만들어 관련 있는 변경만 보게 한다.
기본값으로 새로 추가된 큰 함수는 의사 코드로 요약되고, 단위 테스트와 문서 변경은 접히거나 숨겨진다.
이 동작은 WASM 기반 플러그인으로 바꿀 수 있다.

### 결정 기록

에이전트가 스스로 내린 결정과 그것이 변경에 미친 영향을 파악하기 어려웠다는 경험에서, 에이전트가 자기 추적을 질의하고 캔버스에 연결하는 도구를 만들었다.
사용자는 자기가 정한 요구 사항, 그것이 어떻게 구현됐는지, 에이전트가 자율적으로 내린 결정이 무엇인지를 한 화면에서 본다.

### 알려진 한계

README는 세 가지 한계를 밝힌다.
Whiteboard 안에서는 파일을 편집할 수 없다.
한 리뷰에서 여러 저장소의 파일을 오가는 것은 잘 지원되지 않는다.
공유 버튼으로 리뷰를 다른 기기와 나눌 수 있지만, 공유한 뒤의 변경은 다른 사람에게 보이지 않아 다시 공유해야 한다.

## 사용법

README는 두 가지 프롬프트 예시를 든다.
새 API 변경을 설명받을 때는 커밋 묶음이 어떤 API로 무엇을 하려는 것인지 밝히고, 제안된 API, 예시, 동기를 먼저 본 뒤 구현으로 들어가자고 요청한다.
텔레메트리 변경을 설명받을 때는 특정 커밋을 가리키며 무엇을 추적하는지, 대시보드를 어떻게 만들지, 멈춤과 오류와 크래시를 어떻게 다루는지를 Whiteboard로 설명하라고 요청한다.
그린 결과가 마음에 들지 않으면 그 부분을 클립보드에 담아 에이전트에게 주면 다시 그린다.

로컬 체크아웃을 대상으로 돌며, 팀용 호스팅 제품이 계획되어 있지만 모든 것은 계속 자체 호스팅할 수 있게 하겠다고 한다.
익명 텔레메트리는 코드, diff, Whiteboard 텍스트, 프롬프트, 모델 출력을 담지 않으며 언제든 끌 수 있다.

## 설계 선택

Whiteboard는 Code OSS를 패치로 유지하는 대신 통째로 들여와(vendoring) 쓴다.
README의 설명은 이렇다.
모두가 전용 에이전트 TUI와 데스크톱 앱을 쓰면서 텍스트 편집기는 이제 한 줄씩 diff를 리뷰하는 데만 쓰이니, 리뷰를 위한 텍스트 편집기를 만들고 가장 성공한 오픈 소스 편집기에서 출발하자는 것이다.
패치 방식을 쓰지 않는 이유는 코딩 에이전트가 패치를 다루기 어려워하고, 요즘 기본 VS Code 코드의 약 45%가 Copilot이라 필요 없는 부분이 많기 때문이다.
보안 패치와 기능 패치는 상위 Code OSS를 지켜보며 정기적으로 합친다고 한다.

README가 밝힌 영향은 Geoffrey Litt의 “이해가 새로운 병목이다”, Maggie Appleton과 Val Town이 AI가 만든 코드를 2025년 이전의 소프트웨어 공학 개념에 끼워 맞춘 글들, 그리고 에이전트에 대한 Karpathy의 트윗들이다.

## 분석

### 병목을 “이해”로 본 도구다

Whiteboard가 풀려는 문제는 코드를 쓰는 속도가 아니라 에이전트가 쓴 코드를 사람이 이해하는 속도다.
README가 첫 영향으로 “이해가 새로운 병목이다”를 든 것이 그 출발점을 보여 준다.
에이전트가 한 번에 수백 줄을 바꾸면, 사람은 diff를 한 줄씩 읽는 대신 그 변경이 시스템에서 무엇을 바꿨는지를 먼저 알고 싶어진다.

HN에서 2001zhaozhao는 우리가 이제 에이전트와 아키텍처 수준에서 일하는 경우가 많고, 코딩 에이전트의 Plan Mode보다 더 시각적이고 에이전트와 점진적으로 주고받을 수 있는 대안이 필요하다는 점을 이 도구가 제대로 짚었다고 평가했다.[^2001zhaozhao]
nickosh는 요즘 코드를 많이 리뷰하는데 깊은 분석이나 AI 세션 없이는 무엇이 왜 바뀌었는지 이해하기 어렵다며, 아키텍처와 설계 수준에서 무엇이 있는지 빠르게 확인하는 시각적 방법을 반겼다.[^nickosh]
cannonpalms는 에이전트로 개발할 때 코드의 모양을 머릿속에 “보는” 능력이 가장 아쉽고, 정보가 너무 많이 쏟아져 코드가 어떤 모양인지 따라가지 못한다고 적었다.[^cannonpalms]
세 사람 모두 같은 공백을 가리킨다.

### 편집을 뺀 것은 한계가 아니라 정체성이다

README는 파일을 편집할 수 없다는 것을 알려진 한계의 첫 항목에 두지만, 설계 선택 절의 설명과 함께 읽으면 이것은 의도에 가깝다.
편집기는 이제 diff를 리뷰하는 데만 쓰이니 리뷰를 위한 편집기를 만들겠다는 것이 출발점이기 때문이다.
이 저장소의 [[px0]]이 쓰기 가능한 버퍼를 위험으로 보고 읽기 전용 IDE를 만든 것과 같은 판단이다.

HN에서 icar와 cjmcqueen은 편집할 수 없는데 IDE라고 부를 수 있느냐고 물었고[^icar][^cjmcqueen], 작성자 sidharthkmenon은 IDE라는 말이 잘못된 표현이며 에이전트가 구현과 절충을 이해시키는 데 쓰는 캔버스에 가깝다고 인정했다.[^sidharthkmenon-ide]
이 대화는 도구의 범주가 아직 이름을 갖지 못했다는 것을 보여 준다.
쓰기 도구는 에이전트 쪽으로 옮겨 갔고, 사람 쪽에 남은 도구는 읽고 이해하고 판단하는 도구인데, 우리는 아직 그것을 부를 말로 “IDE”밖에 갖고 있지 않다.

## 비평

### 다이어그램의 정확성을 보증하는 장치가 설명되지 않는다

이 도구의 가치는 에이전트가 그린 다이어그램이 코드와 맞을 때만 성립한다.
HN에서 8organicbits는 README의 예시 GIF에서 “no” 분기 뒤에 “wait for release”라는 전이가 세션 서비스로 돌아가는데, 보여 준 diff에는 그런 것이 없고 코드상으로는 컨텍스트가 만료된 경우라 기다릴 것이 아니라 멈춰야 한다고 지적했다.[^8organicbits]
작성자는 그 GIF가 디자인용으로 쓰던 가상의 예시였고 업데이트하는 것을 잊었으며, 실제 다이어그램은 모두 코드에 연결되어 있어 실제로는 환각이 거의 일어나지 않는다고 답했다.[^sidharthkmenon-gif]

이 답은 두 가지를 남긴다.
첫째, 제품의 첫인상을 결정하는 데모가 정확성이 핵심인 도구에서 틀린 다이어그램을 보여 줬다.
둘째, “코드에 연결되어 있으니 환각이 거의 없다”는 말은 연결이 있다는 것과 연결된 설명이 맞다는 것을 섞는다.
다이어그램의 노드가 실제 함수를 가리키더라도, 노드 사이의 화살표와 그 위의 레이블은 여전히 모델이 쓴 문장이다.
README는 다이어그램이 코드와 어긋날 때 그것을 사람에게 어떻게 알리는지, 에이전트가 그린 관계를 코드의 실제 호출 관계와 대조하는 장치가 있는지를 설명하지 않는다.

### 또 하나의 진실 공급원을 만든다는 문제에 아직 답이 없다

HN에서 asdev는 이런 제품의 문제가 팀의 다른 도구들 옆에 N+1번째 진실 공급원을 만드는 것이라고 지적했다.
프로젝트가 진행되면 본질적으로 낡을 것이고, 에이전트가 변경에 맞춰 갱신하게 하면 설계 문서가 알아볼 수 없는 찌꺼기가 되어 나중에 쓸모가 없어질 것이라는 것이다.[^asdev]
팀원 milanb는 이 지적이 정확하다고 인정하며, 앞으로 호스팅 제품으로 이 문제를 다루겠다고 답했다.[^milanb]

지금의 답은 계획이다.
README의 공유 기능조차 공유 뒤의 변경이 반영되지 않는다고 밝히고 있으니, 현재의 Whiteboard는 한 사람이 한 변경을 이해하는 순간을 위한 도구이지 팀이 오래 참조하는 설계 문서가 아니다.
cannonpalms가 이것을 일회성으로 쓰거나 스크린숏을 기존 문서에 붙여 한 곳에서 함께 썩게 하겠다고 한 것[^cannonpalms]이 현실적인 쓰임새다.
“신중한 소프트웨어 설계를 위한 캔버스”라는 표어는 오래 남는 설계를 암시하지만, 도구가 지금 제공하는 것은 금방 사라지는 이해다.

### 새 앱이 필요하냐는 질문을 가볍게 넘긴다

HN에서 nnevatie는 이것을 위해 새 IDE가 정말 필요하냐고 물었다.
마크다운에 Mermaid 같은 것을 곁들이면 문서와 계획을 위한 공유 캔버스로 충분하지 않겠느냐는 것이다.[^nnevatie]
factorialboy는 macOS에서 앱 크기가 736MB라고 지적했고[^factorialboy], 작성자는 코드 탐색 경험을 위해 VS Code 위에 만든 결과이며 나중에 완전히 네이티브로 다시 쓰겠다고 답했다.[^sidharthkmenon-size]

Code OSS를 통째로 들여온 선택은 LSP와 키 바인딩을 공짜로 얻게 해 주지만, 편집 기능을 뺀 리뷰 도구에 편집기 전체의 무게를 지운다.
그리고 정기적으로 상위의 보안 패치를 합친다는 약속은, 패치가 아니라 통째로 들여온 코드베이스에서는 합칠 때마다 충돌을 해결하는 비용이 된다.
Windows를 지원하지 않는다는 요청이 여러 번 나온 것[^gusmally]도 같은 비용의 다른 모습이다.

## 인사이트

### 에이전트의 결정 기록이 리뷰의 새 단위가 된다

Whiteboard의 세 기능 중 가장 오래 남을 것은 결정 기록이다.
다이어그램과 의미 단위 diff는 코드를 더 보기 좋게 보여 주는 도구이지만, 결정 기록은 코드에 없는 정보, 곧 에이전트가 무엇을 스스로 판단했는지를 보여 준다.

사람이 쓴 코드를 리뷰할 때는 작성자에게 물어볼 수 있었다.
왜 이렇게 했는지, 다른 방법은 생각해 봤는지를 물으면 답이 돌아왔다.
에이전트가 쓴 코드에서 그 대화의 상대는 세션이 끝나면 사라지고, 남는 것은 추적 기록뿐이다.
그 기록에서 자율적으로 내린 결정만 골라 요구 사항과 나란히 보여 주는 것은, 리뷰의 대상이 코드에서 결정으로 옮겨 가는 전조다.

### 이해 도구의 수요는 에이전트가 쓴 코드의 양에 비례해 커진다

HN의 반응 중 여럿은 비슷한 것을 직접 만들고 있다거나 만들었다고 말했다.
syl5x는 같은 생각을 흐름과 관련 코드를 담은 웹사이트를 만드는 스킬로 구현하던 참이었다고 했고[^syl5x], pftburger는 비슷한 것을 만들고 있어 긴장된다고 했으며[^pftburger], itissid는 2026년 상반기에 모두가 이런 내부 도구를 어떤 식으로든 만들었다고 적었다.[^itissid]

이 동시다발성은 수요의 크기를 말해 준다.
에이전트가 쓰는 코드가 늘어날수록 사람이 이해해야 할 코드도 늘고, 그 간극을 메우는 도구가 저마다의 팀에서 따로 만들어진다.
metanonsense가 코드베이스와 소프트웨어 설계를 이해하는 일이 곧 완전히 새로운 산업이 될 것이라고 쓴 것[^metanonsense]은 과장이 아니다.
다만 그 산업의 승자는 가장 예쁜 다이어그램을 그리는 쪽이 아니라, 다이어그램이 코드와 어긋나지 않는다는 것을 가장 잘 보증하는 쪽이 될 것이다.
