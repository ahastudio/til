# px0: 코드를 쓰는 IDE가 아니라 에이전트가 쓴 코드를 읽는 IDE

<https://px0.ai/>

<https://github.com/px0-ai/px0>

HN 토론: <https://news.ycombinator.com/item?id=49683668> (7점, 0개 댓글)

GN 토론: <https://news.hada.io/topic?id=33964>

## 소개

px0는 빠른 코드 리뷰에 맞춘 “사람과 AI를 위한 IDE”다.
브라우저를 지연 없는 콘솔로 바꾸고, Git과 GitHub를 기본으로 연동하며, 거대한 코드베이스를 즉시 검색하고, 로컬 AI 코딩 하네스로 작업을 넘긴다.
MIT 라이선스이며 Go로 작성됐고, Arpit Bhayani가 만들었다.
2026년 6월 24일에 저장소가 만들어졌고 9월 24일 기준 스타 1,506개, 포크 184개다.

README가 내세우는 전제는 한 문장이다.
AI 에이전트가 터미널에서 코드를 직접 쓰는 일이 늘면서 생산성을 제약하는 것은 타이핑 속도가 아니라 변경을 얼마나 빨리 리뷰하고 탐색하고 검증하느냐라는 것이다.
px0는 수 GB짜리 편집 도구 대신 이 리뷰 루프만을 위한 가볍고 산만하지 않은 환경을 준다고 말한다.

README가 제시하는 수치는 다음과 같다.

| 항목        | px0                                       | 비교 대상                   |
| ----------- | ----------------------------------------- | --------------------------- |
| 콜드 스타트 | 1ms 미만                                  | 전통적 IDE는 수 초          |
| 상주 메모리 | 약 20MB                                   | VS Code 약 1,440MB          |
| 실행 파일   | Go 정적 바이너리 하나, 런타임 의존성 없음 | Electron, Node, Chromium 등 |
| 언어 토큰화 | Chroma로 약 280개 언어                    | 해당 없음                   |

출시 글 “IDEs are dead, long live the IDE”는 Linux 커널(파일 9만 5천 개)을 370ms에 색인한다는 수치와, 전통적 IDE가 Node.js와 Electron 프로세스를 15개 넘게 띄운다는 대비를 더한다.

## 주요 기능

### GitHub PR 리뷰와 Git 패널

`px0 <pr-url>`로 풀 리퀘스트를 바로 연다.
머지 베이스 기준의 범위가 정해진 diff를 보고, 인라인 리뷰 댓글을 쓰고, 브라우저에서 스테이징과 커밋과 푸시까지 할 수 있다.
출시 글의 예시 화면에는 PR을 12ms에 열고 임시 워크트리를 준비한 뒤, 인라인 댓글 두 개를 쓰고 Approve로 제출하는 흐름이 나온다.
`Ctrl+D`로 HEAD 대비 분할 또는 통합 diff를 본다.

### AI 코딩 하네스로 넘기기

Claude Code, Gemini CLI, Cursor Agent, Antigravity, OpenCode, Codex, Aider, Goose로 수정을 바로 보내고, 에이전트가 바꾼 내용을 실시간으로 다시 불러온다.
출시 글은 px0에서의 편집이 한 글자씩 버퍼를 고치는 방식이 아니라 코드를 고르고 `Alt+E`로 지시와 의도를 내리면 에이전트가 뒤에서 변경을 적용하는 방식이라고 설명한다.

### 탐색과 렌더링

퍼지 파일 검색, 심볼 개요, 작업 공간 전체의 정규식 검색이 밀리초 단위로 돈다.
보이는 행만 마운트하는 가상 렌더링으로 40만 줄짜리 파일도 부드럽게 열고, 15초 동안 쓰지 않으면 메모리를 OS에 돌려준다.
테마 14개, 렌더링된 마크다운 미리 보기, 이미지 검사기가 있고, 설정 없이 켜는 LSP로 정의로 가기와 호버를 선택적으로 지원한다.

### 원격 우선

원격 서버, VM, 컨테이너에서 px0를 돌리고 로컬 브라우저로 본다.
README는 이것을 SSH 키 설정이나 원격 데몬 없이 할 수 있다고 소개한다.

## 사용법

macOS, Linux, BSD에서는 설치 스크립트 하나로 설치한다.

```bash
curl -fsSL https://px0.ai/install.sh | sh
```

소스에서 빌드하려면 Go 1.24 이상과 Node.js 또는 Bun이 필요하다.

```bash
git clone https://github.com/px0-ai/px0.git
cd px0
make build
install -d ~/.local/bin && install px0 ~/.local/bin/
```

기본 사용은 디렉터리나 파일, PR URL을 인자로 주는 것이다.

```bash
px0                                            # 현재 디렉터리
px0 ~/workspace/project                        # 특정 디렉터리
px0 main.go:42                                 # 특정 파일의 특정 줄
px0 https://github.com/owner/repo/pull/123     # GitHub PR 리뷰
px0 -host 0.0.0.0 -port 7777 ~/workspace       # 원격·헤드리스 서버 모드
px0 -base-path /rev-123/ -host 0.0.0.0 -port 7777 ~/workspace  # 리버스 프록시 하위 경로
px0 --update                                   # 업데이트
```

저장소에는 Linux, Kubernetes, TypeScript 등 약 3GB의 벤치마크 코퍼스를 받아 돌리는 `benchmark.sh`가 들어 있고, `--vscode` 옵션으로 현재 작업 공간에서 VS Code와 직접 비교할 수 있다.

## 분석

### 에이전트 시대의 병목을 “검사 지연”으로 정의했다

출시 글의 가장 강한 주장은 소프트웨어 공학의 주된 병목이 더 이상 타이핑 속도가 아니라 검사 지연(inspection latency)이라는 것이다.
개발 루프가 에이전트가 변경을 만들고, 개발자가 감사하고 탐색하고, 피드백이나 다음 프롬프트를 주는 순환으로 바뀌었다고 본다.
그러면 사람의 일은 파일을 가로지르는 심볼 정의와 참조를 따라가고, HEAD 대비 diff를 감사하고, 아키텍처의 건전성과 보안 불변식을 확인하고, 생성된 문서와 명세를 읽는 것이 된다.

이 정의는 이 저장소의 다른 노트들이 반복해 온 관찰과 같은 곳을 가리킨다.
에이전트가 코드를 쓰는 속도가 사람이 검증하는 속도를 넘어서면서, 리뷰가 새 병목이 됐다는 것이다.
px0의 특징은 이 병목을 조직이나 프로세스의 문제가 아니라 도구의 문제로 다룬다는 데 있다.
검증이 느린 이유 중 하나가 무거운 편집기를 여는 데 드는 몇 초와 수 GB라면, 그것만큼은 도구로 줄일 수 있다.

### 쓰기 가능한 버퍼를 위험으로 본 것이 설계의 핵심이다

출시 글은 에이전트가 터미널에서 파일 12개를 고치는 동안 무거운 IDE를 열어 들여다보다가, 무심코 누른 키 하나가 열린 버퍼를 더럽혀 에이전트의 git 패치와 충돌하고 컴파일러 캐시를 무효화하는 장면을 든다.
일반 편집기가 읽기·쓰기 버퍼를 유지하는 것은 사람이 타이핑한다고 가정하기 때문이며, 에이전트 흐름에서는 그 쓰기 가능한 버퍼가 부채라는 것이다.

이 관찰이 px0의 설계를 결정한다.
저장 버튼도 없고, 키 입력이 작업 트리를 덮어쓸 위험도 없다.
편집은 에이전트에게 의도를 넘기는 것으로 대체된다.
HN 제출 제목이 px0를 “읽기 전용 IDE”라고 부른 것도 같은 성격을 짚는다.
그러면 IDE의 경계가 바뀐다.
IDE는 사람이 코드를 쓰는 곳이 아니라 사람이 에이전트의 작업을 보고 방향을 정하는 곳이 되고, 실제 쓰기는 에이전트 하네스가 맡는다.

## 비평

### 비교 대상이 가장 무거운 편집기 하나로 고정되어 있다

README와 출시 글의 수치는 모두 VS Code, 또는 “전통적 IDE”와의 비교다.
약 20MB 대 약 1,440MB, 1ms 미만 대 수 초라는 숫자는 인상적이지만, 비교 대상이 Electron 위에 확장 호스트를 얹은 편집기다.
Vim, Neovim, Helix처럼 터미널에서 즉시 뜨는 편집기나, Zed처럼 네이티브로 빠른 편집기와의 비교는 없다.
에이전트가 터미널에서 일하는 동안 같은 터미널에서 `nvim`으로 diff를 보는 개발자에게, px0의 속도 이점은 VS Code 사용자에게만큼 크지 않다.

벤치마크 스크립트가 VS Code 비교 옵션만 제공하는 것도 같은 방향이다.
읽기 전용 검사 도구와 범용 편집기의 메모리를 비교하면 결과는 처음부터 정해져 있다.
더 공정한 질문은 같은 작업, 곧 PR 하나를 열어 diff를 보고 심볼을 따라가고 댓글을 다는 데 걸리는 시간을 다른 리뷰 도구와 비교하는 것이다.

### 원격 공개 모드의 보안 경계가 README에 없다

README는 원격 서버에서 px0를 돌리고 SSH 키 설정이나 원격 데몬 없이 로컬 브라우저로 볼 수 있다는 것을 장점으로 소개하고, 예시로 `-host 0.0.0.0`을 쓴다.
출시 글도 SSH 터널 없이 단일 포트로 원격 코드베이스를 본다고 설명한다.
그런데 px0는 코드를 보여 주는 데서 그치지 않고 스테이징, 커밋, 푸시, 그리고 에이전트 하네스로의 수정 지시까지 브라우저에서 할 수 있다.

모든 인터페이스에 바인딩한 이 서버에 누가 접근할 수 있는지, 인증이나 접근 통제가 있는지는 README와 출시 글 어디에도 나오지 않는다.
SSH가 번거로운 이유는 바로 그것이 인증과 암호화를 제공하기 때문이다.
SSH 없이 편하다는 것을 장점으로 내세우려면, SSH가 하던 일을 무엇이 대신하는지를 함께 밝혀야 한다.
리버스 프록시 하위 경로 옵션이 있다는 것은 앞단 프록시에서 인증을 처리하라는 뜻일 수 있지만, 그렇다면 그것을 문서에 적어야 한다.

### 설치 방식이 신뢰를 요구하는 방식이다

기본 설치는 `curl -fsSL https://px0.ai/install.sh | sh`다.
원격 스크립트를 셸에 바로 넘기는 방식은 흔하지만, 이 도구는 코드베이스 전체를 읽고 Git에 쓰고 GitHub에 리뷰를 제출하며 에이전트 하네스를 조종하는 권한을 갖는다.
Go 정적 바이너리 하나라는 성질은 서명된 릴리스 바이너리와 체크섬을 배포하기에 가장 좋은 형태인데, README는 그 경로보다 파이프 설치를 먼저 안내한다.
검증을 위한 도구라는 정체성과 설치 과정의 검증 부재가 어긋난다.

## 인사이트

### 편집기 시장이 쓰기 도구와 읽기 도구로 갈라지고 있다

px0의 가장 흥미로운 점은 기능이 아니라 범주다.
지난 30년 동안 IDE는 코드를 쓰고 읽고 디버그하고 실행하는 모든 일을 한 창에 모았다.
px0는 그중 읽기만 떼어 내고, 쓰기는 에이전트에게 넘긴다.

이 분리가 퍼지면 도구의 최적화 목표가 둘로 갈린다.
쓰기 도구는 에이전트 하네스로 옮겨 가 컨텍스트 관리와 도구 호출과 권한을 최적화한다.
읽기 도구는 사람 쪽에 남아 탐색 속도와 diff의 가독성과 리뷰 흐름을 최적화한다.
한때 편집기와 디버거와 버전 관리 도구가 따로 있다가 IDE로 합쳐졌던 흐름이, 에이전트를 계기로 다시 풀리는 것이다.

### 리뷰 도구의 진짜 경쟁 상대는 편집기가 아니라 리뷰를 건너뛰는 습관이다

px0가 풀려는 문제는 무거운 편집기를 여는 데 드는 몇 초다.
그러나 에이전트 흐름에서 리뷰가 부실해지는 더 큰 이유는 도구가 느려서가 아니라, 변경이 너무 많아서 사람이 리뷰를 건너뛰기 때문이다.
에이전트가 하루에 수천 줄을 바꾸면, 그것을 1ms에 열 수 있어도 사람은 다 읽지 못한다.

그러면 리뷰 도구의 가치는 여는 속도보다 무엇을 읽어야 하는지 골라 주는 능력에서 나온다.
touched-file 필터와 머지 베이스 기준 diff는 그 방향의 첫걸음이지만, 어떤 변경이 위험하고 어떤 변경이 기계적인지를 구분해 주는 것은 아직 사람의 몫이다.
속도는 리뷰를 가능하게 만들 뿐, 리뷰가 일어나게 만들지는 않는다.

### 원격 우선 설계는 에이전트가 사는 곳이 로컬이 아니라는 가정 위에 서 있다

SSH 없이 원격 머신의 코드를 브라우저로 본다는 기능은, 에이전트가 개발자의 노트북이 아니라 클라우드 VM이나 GPU 인스턴스나 CI 러너에서 일한다는 가정을 반영한다.
에이전트가 원격에서 코드를 바꾸고 사람은 그것을 로컬 브라우저에서 확인하는 구조다.

이 가정이 맞다면 리뷰 도구는 점점 네트워크 서비스가 된다.
그리고 네트워크 서비스가 되는 순간 인증, 권한, 감사 로그가 도구의 핵심 기능으로 올라온다.
px0가 지금 SSH 없는 편리함으로 내세우는 것은 한 사람이 한 원격 머신을 볼 때는 장점이지만, 여러 사람이 여러 에이전트의 작업을 함께 리뷰하는 팀 환경에서는 가장 먼저 설계해야 할 부분이 된다.
디자인 파트너를 10명 이상의 팀이나 에이전트 흐름을 운영하는 팀으로 한정한 것은, 그 전환이 이미 다음 과제로 보이고 있다는 뜻일 것이다.
