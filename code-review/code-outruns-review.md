# 코드가 리뷰를 앞질렀다: 사라지는 것은 코드 리뷰가 아니라 모든 변경을 같게 읽던 관행

GeekNews Article: [코드는 다 읽을 수 없고, 코드 리뷰가 맡아온 책임은 사라지지 않는다](https://news.hada.io/article/code-outruns-review)

## 요약

GeekNews가 직접 쓴 아티클이다.
지난 몇 년간 GeekNews에 올라온 코드 리뷰 글 열아홉 편과
최근의 대규모 연구를 묶어 하나의 논지로 정리한다.

문제 정의부터 시작한다.
AI가 만든 가장 큰 변화는 코드를 더 잘 쓰게 된 것이 아니라
사람이 코드를 읽고 검토할 수 있는 속도보다 코드가 만들어지는 속도가 빨라진 것이며,
그 격차가 가장 먼저 드러나는 곳이 코드 리뷰라는 것이다.
Faros AI가 4,000개 팀 22,000명의 2년치 텔레메트리를 분석한 결과로
AI 도입도가 낮은 팀에서 높은 팀으로 갈수록
중앙값 리뷰 소요 시간이 441.5% 증가하고 리뷰 없이 머지된 PR이 31.3% 증가했다고 인용한다.
다만 이것이 AI 도입이 변화를 직접 일으켰다고 입증한 실험이 아니라
생산성 분석 업체가 수집한 관찰 데이터라는 단서를 바로 붙인다.

그리고 흔들리는 원칙을 한 줄로 제시한다 —
코드를 만든 사람이 전부 읽고 다른 사람이 다시 읽은 뒤에야 머지한다는 것이다.
이 원칙을 계속 지킬 수 있는지, 지킬 수 없다면 리뷰를 없애야 하는지,
AI가 작성한 코드를 다른 AI가 검토하면 되는지를 묻고,
이 문제가 사람과 AI 중 누가 더 잘 리뷰하는가의 대결이 아니라
하나의 PR에 뒤섞여 있던 검증과 이해와 지식 전달과 승인과 책임을
누구에게 어떻게 나눌 것인가의 문제에 가깝다고 정리한다.

그 재정의를 위해 리뷰의 역할을 다섯 가지로 분해한다.

| 역할            | 내용                                             |
| --------------- | ------------------------------------------------ |
| 검증            | 변경에서 결함을 찾는 일                          |
| 유지보수성 확인 | 다른 사람이 코드를 이해할 수 있는지 보는 일      |
| 지식 공유       | 프로젝트의 관례와 과거 결정을 전달하는 일        |
| 게이트키핑      | 무엇을 코드베이스에 받아들일지 정하는 일         |
| 책임 분산       | 문제 발생 시 판단을 한 사람에게만 맡기지 않는 일 |

기존 코드 리뷰는 이 다섯을 모두 사람이 diff를 읽으며 처리해 온 것이라고 적는다.

이어서 병목의 위치를 다시 짚는다.
개발의 병목은 원래부터 타이핑이 아니라 리뷰와 테스트와 디버깅과 지식 이전과 협업에 있었고,
코드 생성이 쉬워질수록 이해와 검증 비용이 오히려 선명해진다는 것이다.
GitClear 데이터에서 AI를 매일 쓰는 개발자는 비사용자보다 약 4배의 원시 산출량을 냈지만
1년 전 자신과 비교한 생산성 향상은 약 12%였다고 인용하면서,
원래 생산성이 높은 개발자가 AI 사용 집단에 더 많이 포함됐을 가능성 때문에
이 수치에도 선택 편향이 남아 있다고 덧붙인다.
그리고 코드를 빨리 만들었다는 것은 일을 끝낸 것이 아니라
그 코드가 작동한다는 증거를 만드는 단계로 일을 넘긴 것에 가깝다는
입증 책임의 프레임을 제시한다.

AI를 하나 더 붙이는 접근의 현재 상태도 정리한다.
Anthropic 내부 측정에서 실질적인 리뷰를 받는 PR 비율이 16%에서 54%로 늘었고
GitHub 발표 기준으로 플랫폼 리뷰 5건 중 1건 이상에 에이전트가 관여한다 —
리뷰를 없애는 대신 AI로 1차 리뷰의 처리량을 늘리는 단계가 시작됐다는 것이다.

두 편의 대규모 연구가 사람과 AI의 차이를 보여 준다.
300개 오픈소스 프로젝트의 PR 54,330개와 인라인 리뷰 대화 278,790개를 분석한 연구에서는
전체 리뷰의 55.7%를 AI 에이전트가 시작했고,
AI 리뷰 코멘트의 95% 이상이 코드 개선과 결함 탐지에 집중한 반면
인간은 구현 의도를 묻고 테스트 방식을 확인하고 저장소 관례와 과거 결정을 대화로 가져왔다.
AI는 코드 안에서 답을 찾으려 했고 인간은 코드 밖의 맥락을 가져왔다는 것이다.
수정안 채택률은 AI가 16.6%, 인간이 56.5%였고,
AI가 시작한 리뷰의 85% 이상은 첫 코멘트 뒤 추가 응답 없이 종료됐으며,
인간이 에이전트 계정이 작성한 코드를 리뷰하면 대화가 평균 11.8% 길어졌다.
실제로 반영된 AI 수정안은 인간 수정안보다 코드 크기와 분기 복잡도를 더 많이 늘리는 경향을 보였고,
그래서 AI 리뷰는 판결보다 결함 후보를 넓게 탐지하는 센서에 가깝다고 해석한다.

207개 프로젝트의 102만 개 PR을 시기별로 나눈 다른 연구는 속도와 품질을 분리한다.
AI 리뷰어를 점진적으로 도입한 프로젝트에서는 리뷰 결정이 빨라졌지만
초기 LLM 리뷰어를 대부분의 PR에 일괄 적용한 프로젝트에서는 속도 개선이 없었고
리뷰 안티패턴이 오히려 늘었다.
빠르게 결론을 낸 프로젝트에서도 연구가 사용한 품질 대리 지표는 함께 좋아지지 않았다.
LLM이 참여한 프로젝트에서는 같은 리뷰어 조합이 반복되는 비율이 평균 60%로
사람만 참여한 경우의 약 16%보다 높았다 —
모든 PR에 같은 모델을 붙이면 리뷰어 수는 늘어난 것처럼 보여도 관점은 하나로 고정될 수 있다는 것이다.
두 연구가 모두 관찰 연구이며 실제 장애나 결함 발생률 대신 대리 지표를 썼고
인과관계를 입증하지 않았다고 다시 명시한다.

다음으로 ‘사라진 의도’ 문제를 제기한다.
사람이 코드를 쓰면 검토하고 버린 대안이 작성자 머릿속에 남아 있어
리뷰는 그 판단을 점검하는 일이었는데,
에이전트가 만든 diff에는 무엇을 시도했고 왜 버렸는지가 남지 않는 경우가 많아
리뷰어가 기록되지 않은 의도를 다시 구성해야 한다.
리뷰어가 왜 이 라이브러리를 선택했는지 물으면
개발자가 AI에게 다시 물어 답변을 전달하고 사람이 작성자가 아니라 중개인이 되는 장면도 인용한다.
해법은 모델의 내부 사고 과정을 보관하는 것이 아니라
에이전트가 수행한 도구 호출과 검토한 대안과 테스트 결과와 최종 판단 근거를
외부에서 검증 가능한 결정 로그로 남기는 것이며,
리뷰어가 “왜 이렇게 했나”라고 물어야 한다면
의사결정 로그에 빈 부분이 있다는 신호로 볼 수 있다고 적는다.

읽기를 완전히 대체할 수 없다는 반론도 함께 놓는다.
더 나은 테스트와 기능 플래그와 가드레일과 관측 가능성은 불안을 줄이지만
팀이 변경을 함께 이해하는 일까지 대신하지는 못하며,
리뷰어가 이해하지 못한 코드는 미래의 유지보수자도 이해하기 어려울 가능성이 크다는 것이다.
읽기는 무결성을 증명하는 행위가 아니라
다른 사람이 이 변경을 이해하고 이어받을 수 있는지 확인하는 행위라고 정리한다.
그리고 최신 LLM 리뷰가 놓치고 사람이 발견한 세 사례를 든다 —
여러 프로세스가 `~/.gitconfig`를 동시에 수정할 때의 잠금 충돌,
CI에 설치된 오래된 AWS CLI의 버전 호환성 문제,
tarball과 checksum을 따로 갱신할 때 생기는 비원자적 상태다.
세 문제 모두 현재 diff 바깥의 기억이 필요했고,
세 사례 중 두 개는 해당 코드를 잘 알던 개발자의 PR이었다.
다만 필요한 사실이 반드시 저장소에 없었던 것은 아니며
리뷰 시점에 모델이 그 컨텍스트에 접근하거나 현재 변경과 연결하지 못했을 가능성도 있다고 유보를 단다.

결론 부분에서 하나였던 리뷰를 다섯 단계로 나눈다.

| 시점         | 무엇을 하는가                                                          |
| ------------ | ---------------------------------------------------------------------- |
| 코드 생성 전 | 스펙·설계·데이터 모델·성능 목표·보안 경계·수용 기준을 사람이 검토      |
| 생성 중      | 타입 검사·린트·테스트·정적 분석·보안 스캔 자동화, 명령과 결과를 증거로 |
| PR 시점      | AI를 센서로 써서 결함 후보·중복·누락된 테스트를 선별                   |
| 머지 전      | 틀렸을 때의 비용으로 리뷰 강도를 결정                                  |
| 배포 후      | 기능 플래그·점진적 배포·관측 가능성·빠른 롤백                          |

머지 전 단계의 기준을 구체화한다 —
일회성 스크립트와 낮은 위험의 변경은 테스트와 AI 리뷰 중심,
오래 유지할 핵심 로직은 설계와 유지보수성까지 사람 검토,
인증과 결제와 권한과 데이터 삭제와 인프라는 시스템 소유자가 직접 확인이며,
작성자가 사람인지 AI인지보다 잘못됐을 때 어떤 일이 생기는지가 리뷰 수준을 결정한다.
테스트가 많이 수정된 diff에서는 새 동작에 맞춰 assertion까지 바꿨는지부터 확인하라고 덧붙인다.

마지막으로 사람이 최종적으로 소유해야 할 것을 네 가지로 제시한다 —
올바른 문제를 풀고 있는지(의도), 코드 밖의 제약과 과거 결정을 반영했는지(맥락),
실제로 작동하고 실패에 대비했는지(증거),
문제가 생겼을 때 이 변경을 설명하고 되돌릴 수 있는지(책임)다.
모델은 온콜 담당자가 되어 장애 호출을 받을 수도,
사용자에게 결정을 설명하거나 그 결과를 책임질 수도 없다고 적는다.
맺음 문장이 논지를 압축한다 —
사라지는 것은 코드 리뷰가 아니라 모든 변경을 같은 사람이 같은 방식으로 읽던 관행이며,
코드 리뷰는 코드에 대한 승인 절차에서
변경을 이해하고 검증하고 책임지는 시스템으로 바뀌고 있다는 것이다.

본문에 GeekNews 댓글 두 개가 인용되어 있다.
코드 리뷰를 굉장히 좋아하는 편이었는데
에이전트가 쏟아내는 방대한 코드를 리뷰하는 데 지쳐 간다는 것,
그리고 과거 PR은 내가 만든 결과물을 내가 책임진다는 느낌이 있었지만
바이브 코더의 PR은 “내가 뭘 만들었는지도 모르겠고
어쨌든 결과물은 있으니 니가 평가해서 문제점을 찾아라” 같다는 것이다.

그러므로 이 글의 값은 자료가 아니라 질문의 형태에 있다.
흔한 질문은 “AI가 사람보다 리뷰를 잘하는가”이고,
그 질문은 답이 무엇이든 실행 지침으로 바뀌지 않는다 —
잘한다면 맡기고 못한다면 안 맡긴다는 이항 선택만 남는다.
이 글은 그것을 “하나의 PR에 뒤섞여 있던 다섯 책임을 어떻게 나눌까”로 바꾼다.

이 전환이 결론을 가능하게 한다.
다섯 역할을 분리해 두면 각각이 다른 주체와 다른 시점에 배치될 수 있고,
그러면 “리뷰를 없앤다”와 “리뷰를 유지한다”가 아니라
“어느 역할을 어디로 옮긴다”가 논의 대상이 된다.
맺음의 문장 — 사라지는 것은 리뷰가 아니라 모든 변경을 같게 읽던 관행 — 은
그 분해 없이는 말할 수 없는 문장이다.

### 인용한 모든 연구에 유보를 붙인 절제가 결론을 인과에서 떼어 놓는다

이 글은 숫자를 많이 쓴다.
441.5%와 31.3%, 4배와 12%, 16%에서 54%, 55.7%, 16.6% 대 56.5%, 60% 대 16%다.
그리고 거의 모든 숫자 뒤에 성격을 표시한다.

Faros 데이터는 실험이 아니라 관찰 데이터라고 적고,
GitClear 수치에는 선택 편향이 남아 있다고 적고,
두 대규모 연구는 관찰 연구이며 대리 지표를 썼고 인과를 입증하지 않았다고 적고,
54,330개 PR 연구의 ‘AI 작성 코드’가 에이전트 계정이 만든 PR을 뜻하므로
사람이 AI 도구로 쓴 모든 코드로 확대할 수 없다고 적고,
세 실패 사례에 대해서도 모델이 컨텍스트에 접근하지 못했을 가능성을 남긴다.

이 절제가 논증 설계의 결과다.
결론이 “AI 때문에 리뷰가 무너진다”라면 인과 입증이 필요하지만,
이 글의 결론은 “읽는 속도가 생성 속도를 따라가지 못하면
읽히지 않은 코드가 머지된다”이고 그것은 산술이다.
그래서 어느 숫자가 나중에 뒤집혀도 처방이 유효하다.
[GitHub 장애를 다룬 같은 편집의 아티클](../github/github-is-not-just-git.md)이
AI를 원인으로 단정하지 않으면서 의존성 분리를 정당화한 것과 같은 구조다.

### ‘사라진 의도’가 이 글에서 가장 새로운 개념이다

다섯 역할 분해와 다섯 단계 배치는 여러 곳에서 변형이 논의된 형태인데,
사라진 의도는 이 글이 인용 자료들을 합쳐 만든 개념에 가깝다.

관찰의 내용이 정확하다.
사람이 쓴 diff에는 보이지 않는 것이 함께 딸려 온다 —
작성자가 검토하고 버린 대안이 그의 머릿속에 있고,
리뷰는 결과물뿐 아니라 그 선택을 점검하는 대화였다.
“왜 이 라이브러리를 골랐나”라는 질문이 성립했던 이유가 그것이다.
에이전트가 만든 diff에는 그 대안 집합이 어디에도 없고,
그래서 개발자가 답을 알지 못한 채 AI에게 다시 물어 전달하는 중개인이 된다.

처방의 방향도 정확하다.
모델의 내부 사고를 보관하는 것이 아니라
도구 호출과 검토한 대안과 테스트 결과와 판단 근거를
외부에서 검증 가능한 로그로 남기라는 것이다.
사고 과정 보관은 검증할 수 없고 분량만 늘리는데,
실행한 명령과 그 결과는 재현할 수 있다.
같은 구분이 생성 중 단계의 지침에도 있다 —
AI의 설명보다 실제 명령과 결과를 증거로 남기라는 문장이다.

### AI 리뷰를 센서로 규정한 것이 비유가 아니라 데이터의 요약이다

“판결보다 결함 후보를 넓게 탐지하는 센서”라는 표현은
수사처럼 보이지만 네 개의 수치가 같은 방향을 가리킨 결과다.

수정안 채택률 16.6%는 정밀도가 낮다는 뜻이고,
AI가 시작한 리뷰의 85% 이상이 첫 코멘트 뒤 종료된다는 것은 대화로 발전하지 않는다는 뜻이며,
반영된 AI 수정안이 코드 크기와 분기 복잡도를 더 늘린다는 것은
제안의 방향이 국소 최적화에 치우친다는 뜻이고,
리뷰어 조합 반복 60%는 관점의 다양성이 없다는 뜻이다.
넷을 합치면 “많이 찾지만 어느 것이 중요한지 정하지 못하는 장치”가 되고,
그것이 센서의 정의다.

이 규정이 실무적으로 유용한 이유는 실패 모드를 예측하게 하기 때문이다.
센서를 판결자로 쓰면 두 가지가 생긴다 —
낮은 정밀도가 경고 피로를 만들고, 국소 최적화 제안이 누적되어 복잡도를 올린다.
102만 개 PR 연구에서 일괄 적용 그룹의 안티패턴이 늘었다는 발견이
그 예측과 정확히 맞는다.

## 비평

### 다섯 단계 분해가 전제하는 조직 규모를 밝히지 않는다

결론의 다섯 단계는 각각 다른 인프라를 요구한다.
생성 전 단계는 스펙과 설계와 수용 기준을 검토할 사람과 절차,
생성 중 단계는 타입 검사와 정적 분석과 보안 스캔이 붙은 CI,
PR 단계는 AI 리뷰어 도구,
머지 전 단계는 시스템 소유자가 지정된 조직도,
배포 후 단계는 기능 플래그와 관측 스택과 롤백 경로다.

이 목록은 플랫폼 팀이 있는 조직의 목록이다.
세 명이 일하는 팀에서는 다섯 단계의 주체가 전부 같은 사람이고,
단계를 나눈다는 것이 곧 같은 사람이 다섯 번 맥락을 바꾼다는 뜻이 된다.
그 경우 분해가 비용을 줄이지 않고 늘린다.

그리고 문제 쪽은 규모와 무관하다.
코드 생성 속도가 읽기 속도를 앞지르는 현상은
개인 프로젝트에서도 똑같이 일어나며, 오히려 리뷰어가 없으므로 더 심하다.
즉 진단의 적용 범위가 처방의 적용 범위보다 넓고,
글이 그 차이를 표시하지 않는다.

작은 팀을 위한 축약형이 있었다면 이 글의 실용성이 크게 올라간다.
다섯 단계 중 무엇을 먼저 버려도 되는지 —
아마 PR 단계의 AI 센서와 배포 후 단계가 마지막에 오고
생성 전 단계의 수용 기준이 첫 번째일 것이다 — 를 한 줄로 적는 일이며,
이 글이 가진 자료로 충분히 판단할 수 있는 내용이다.

### 리뷰 강도를 위험으로 정하라는 규칙이 위험 추정 방법을 남기지 않는다

머지 전 단계의 기준이 이 글의 가장 실행 가능한 조언이다 —
작성자가 사람인지 AI인지보다
잘못됐을 때 어떤 일이 생기는지가 리뷰 수준을 결정한다는 것이다.

그런데 그 판단이 리뷰 이전에 필요하다.
어떤 변경이 위험한지 알려면 변경의 영향 범위를 알아야 하고,
영향 범위를 알려면 변경을 이해해야 하며, 이해가 곧 리뷰다.
읽지 않고 위험을 판정하는 방법이 필요한데 글에 그 방법이 없다.

실무에서 이 순환을 끊는 장치는 이미 있다.
경로 기반 규칙이다 — `CODEOWNERS`로 디렉터리마다 필수 리뷰어를 걸고,
결제나 인증 모듈에는 다른 정책을 적용하는 방식이며,
변경 내용을 읽지 않고도 파일 목록만으로 강도가 결정된다.
이 글은 인증과 결제와 권한과 데이터 삭제와 인프라를 나열해
사실상 그 근사를 제시하는데, 그것을 방법으로 승격하지 않고 예시로 둔다.

목록에서 방법으로 올리는 데 필요한 것은 한 문장이다 —
위험을 변경마다 판정하지 말고 코드베이스의 영역마다 미리 판정해 두라는 것이다.
그러면 위험 추정이 리뷰의 선행 조건이 아니라 저장소 설정이 되고,
순환이 사라진다.

### 결정 로그 처방이 해결하려는 문제를 다시 만든다

사라진 의도에 대한 처방은 결정 로그를 남기는 것이다 —
도구 호출과 검토한 대안과 테스트 결과와 판단 근거다.
그런데 이 글이 해결하려는 문제가 읽을 것이 너무 많다는 것이었다.

에이전트가 한 시간 동안 수십 번의 도구 호출과 여러 대안 검토를 거쳤다면
그 로그는 diff보다 길어질 수 있다.
그러면 리뷰어는 300줄 diff 대신 300줄 diff와 800줄 로그를 받는다.
읽기 대상을 바꾼 것이지 줄인 것이 아니며,
글이 그 분량 문제를 언급하지 않는다.

판정 기준도 사후적이다.
“리뷰어가 왜 이렇게 했나라고 물어야 한다면 로그에 빈 부분이 있다는 신호”는
질문이 나온 뒤에만 작동하고, 그때는 이미 리뷰 시간이 소비됐다.
같은 형태의 문제를 [KRP의 4년 회고](../architecture/krp-tree-rings.md)에서도 봤는데 —
“명확한 이유가 있을 때만 변경했다”가 변경 시점에는 항상 참인 것과 같다 —
사후에만 참·거짓이 정해지는 기준은 개선 지표로 쓸 수 없다.

쓸 수 있는 형태로 바꾸는 방법이 있다.
로그의 항목을 미리 정해 두고 빈 칸이 있는지 기계가 검사하는 것이다 —
어떤 대안을 검토했는지, 어떤 테스트를 실행했는지,
어떤 제약을 확인했는지를 필수 필드로 두면 사전에 판정된다.
그렇게 하면 로그가 자유 서술이 아니라 양식이 되고 분량 문제도 함께 줄어든다.

### 대규모 연구에는 유보를 달고 댓글 두 개에는 달지 않는다

이 글의 서술 태도에서 가장 눈에 걸리는 비대칭이 여기다.
22,000명의 텔레메트리와 102만 개 PR 연구에는
관찰 데이터이고 대리 지표이며 인과가 아니라는 단서를 꼼꼼히 붙인다.
반면 본문에 인용된 GeekNews 댓글 두 개에는 아무 표시가 없다.

두 댓글이 논증에서 하는 역할이 작지 않다.
첫 번째는 문제의 실재성을 보여 주는 장면으로 쓰이고,
두 번째 — 바이브 코더의 PR이 “내가 뭘 만들었는지도 모르겠고
어쨌든 결과물은 있으니 니가 평가해서 문제점을 찾아라” 같다는 것 — 은
책임 소재의 변화를 압축한 인용으로 결론 직전에 배치된다.
강한 문장이고 기억에 남는 문장인데, 한 사람의 경험이라는 표시가 없다.

이 비대칭이 문제인 이유는 이 글이 스스로 세운 기준 때문이다.
숫자의 성격을 밝히는 것이 이 글의 미덕인데,
그 기준을 정성 자료에는 적용하지 않으면 기준이 선택적으로 쓰인 것이 된다.
그리고 정성 자료가 결론 근처에 배치될 때 더 큰 무게를 갖는다 —
독자가 마지막에 읽은 문장을 기억하기 때문이다.

고치는 비용은 거의 없다.
“한 개발자의 경험이지만 여러 곳에서 반복되는 형태”라는 한 구절이면 되고,
그 구절이 있으면 오히려 인용의 설득력이 올라간다 —
자기 자료의 한계를 아는 글이 더 신뢰받는다는 것이
이 글이 숫자에서 이미 증명한 바다.

## 인사이트

### 다섯 역할 중 무엇이 옮겨지는지는 “코드 안에 답이 있는가”가 정한다

이 글은 역할을 다섯으로 나누고 단계를 다섯으로 나누는데,
둘 사이의 대응은 명시하지 않는다.
그 대응을 정하는 축이 인용된 연구 안에 이미 있다 —
AI 코멘트의 95% 이상이 코드 개선과 결함 탐지에 집중하고
인간은 의도와 테스트 방식과 관례와 과거 결정을 가져왔다는 관찰이다.

이 기준으로 다섯 역할을 나누면 결과가 선명하다.
검증은 코드 안에 답이 있으므로 옮겨진다.
유지보수성 확인은 절반만 옮겨진다 — 복잡도는 측정되지만
“다음 사람이 이해할 수 있는가”는 다음 사람이 누구인지에 달려 있다.
지식 공유와 게이트키핑과 책임 분산은 답이 코드 밖에 있으므로 옮겨지지 않는다.

여기서 조직이 잃는 순서가 예측된다.
검증이 자동화되면 리뷰의 정당성을 검증으로 설명해 온 팀은
리뷰를 축소할 근거를 얻는다 — 도구가 결함을 더 많이 찾으니까.
그리고 남은 세 역할은 대개 이름이 붙어 있지 않다.
리뷰 정책 문서에 “결함 발견”은 적혀 있지만
“신입이 코드베이스의 관례를 배우는 자리”는 적혀 있지 않으므로,
방어할 근거가 없어서 함께 사라진다.

그러므로 이 글의 다섯 역할 분해는 분석 도구가 아니라 방어 장치로 쓰는 것이 낫다.
리뷰 정책에 다섯 역할을 명시적으로 적어 두면
검증이 자동화되어도 나머지 넷이 자동으로 폐기되지 않는다.
이름이 있는 것만 예산과 시간을 배정받는다는 규칙이 여기서도 작동한다.

### ‘사라진 의도’는 새 문제가 아니라 오래된 문제가 임계를 넘은 것이다

diff에 왜가 남지 않는다는 문제는 에이전트가 만든 것이 아니다.
커밋 메시지가 “fix”뿐인 저장소, 문서 없는 레거시,
떠난 사람이 남긴 모듈이 모두 같은 문제였고 수십 년간 있었다.

달라진 것은 두 가지다.
규모가 커졌고 — 하루에 생성되는 코드가 늘었으므로 —
그리고 시간이 사라졌다.
과거의 사라진 의도는 사람이 떠난 뒤에 문제가 되었으므로 몇 년의 완충이 있었고,
그 사이에 코드가 안정되거나 대체되었다.
에이전트 diff의 사라진 의도는 리뷰 시점에, 즉 몇 분 뒤에 문제가 된다.

과거에 이 문제를 부분적으로 풀었던 장치들이 형태가 같다.
커밋 메시지 규약, 이슈 링크,
[아키텍처 결정 기록](../architecture/adr.md)이 전부
“왜”를 코드 밖에 남기는 형식이었다.
그러므로 결정 로그는 발명이 아니라 ADR의 자동 생성판이며,
ADR이 왜 널리 정착하지 못했는지가 결정 로그의 성패를 예측한다.

ADR이 실패한 이유는 쓰는 사람과 읽는 사람이 달랐기 때문이다.
지금 결정하는 사람에게는 이미 아는 내용이고,
필요한 사람은 몇 년 뒤에 오므로 쓸 동기가 약했다.
에이전트가 로그를 쓰면 그 비대칭이 해소된다 —
쓰는 비용이 사람에게 부과되지 않기 때문이다.
그것이 이번 국면의 실제 새로움이며,
동시에 이 처방이 성공할 가능성을 이전 시도보다 높게 보는 근거다.

### 같은 모델을 모든 PR에 붙이면 리뷰어 수가 아니라 상관관계가 늘어난다

102만 개 PR 연구의 발견 중 가장 실무적인 것은
리뷰어 조합 반복 비율이 60% 대 16%라는 숫자다.
그리고 그 숫자가 안티패턴 증가와 같은 그룹에서 나왔다.

메커니즘은 통계 쪽 언어로 정확히 기술된다.
여러 리뷰어를 두는 것의 값은 그들의 오류가 독립적이라는 데서 나온다 —
A가 놓친 것을 B가 잡을 확률은 두 사람의 관점이 다를 때만 높다.
같은 모델을 모든 PR에 붙이면 판정자 수는 늘지만 오류가 완전히 상관되므로,
검토 횟수가 늘어도 발견되는 문제의 집합은 커지지 않는다.

같은 구조가 다른 분야에서 이미 사고를 만들었다.
금융 리스크 모델이 같은 가정을 공유해 위험이 분산된 것처럼 보였던 국면,
신용평가에서 여러 기관이 같은 방법론을 써서 등급이 동시에 틀린 사례,
채용 스크리닝에서 여러 회사가 같은 필터를 써서 같은 후보군을 놓친 경우다.
공통점은 독립적으로 보이는 판정자들이 같은 모델을 공유하면
개별 정확도와 무관하게 시스템 위험이 커진다는 것이다.

실무적 함의는 우선순위의 역전이다.
AI 리뷰를 도입하는 팀이 먼저 하는 일은 대개 더 좋은 모델을 고르는 것인데,
이 발견에 따르면 관점의 분산이 정확도보다 먼저다.
같은 예산이라면 한 모델의 성능을 올리는 것보다
서로 다른 모델을 섞거나 프롬프트로 관점을 나누는 것 —
하나는 보안, 하나는 성능, 하나는 유지보수성 — 이 낫고,
연구가 말하는 “점진적 도입”이 잘 작동한 이유도
결과적으로 리뷰어 조합의 다양성이 유지됐기 때문으로 읽을 수 있다.

### 코드를 다 읽지 않는 상태는 예외가 아니라 소프트웨어의 정상이었다

“코드를 전부 읽을 수 없다”가 위기처럼 들리는 이유는
우리가 읽는 것을 기본값으로 여기기 때문인데, 그 기본값은 좁은 범위에만 적용돼 왔다.

우리는 이미 대부분의 코드를 읽지 않는다.
의존성으로 끌어온 라이브러리의 소스를 읽지 않고 버전과 테스트와 평판을 신뢰하며,
컴파일러가 만든 기계어를 검토하지 않고,
데이터베이스 엔진의 쿼리 실행 계획 구현을 확인하지 않는다.
읽지 않는 것이 정상인 영역이 압도적으로 넓고,
직접 쓴 코드만 예외적으로 전수 검토해 왔다.

그렇다면 질문은 “읽지 않아도 되는가”가 아니라
“읽지 않아도 되는 조건이 무엇인가”가 된다.
위 사례들에서 그 조건은 세 가지로 공통된다 —
경계가 명확해서 무엇이 들어오고 나가는지 알 수 있고,
실패가 관측되고, 문제가 생기면 대체할 수 있다는 것이다.
라이브러리를 믿는 근거가 코드 품질이 아니라 이 셋이다.

이 글의 결론 네 항목 — 의도와 맥락과 증거와 책임 — 이
사실상 같은 조건을 변경 단위에 적용한 것이다.
그리고 여기서 따라오는 함의가 이 글의 범위를 넘어선다.
읽지 않아도 되는 조건을 만드는 일은 리뷰 프로세스의 일이 아니라 설계의 일이다 —
배포 단위를 작게 쪼개고, 되돌릴 수 있게 만들고, 계약을 관측 가능하게 하는 작업이며,
그것을 해 두지 않은 코드베이스에서는 어떤 리뷰 체계를 붙여도 읽기를 줄일 수 없다.

그러므로 이 논의의 다음 무대는 코드 리뷰 도구가 아니라 가역성 설계다.
[KRP 회고에서 되돌릴 수 없는 변경이 일곱 중 하나였다는 사실](../architecture/krp-tree-rings.md)이
같은 축을 가리킨다 —
가역적인 변경은 덜 읽어도 되고,
비가역적인 변경은 얼마나 읽어도 부족하다.
리뷰 강도를 위험으로 정하라는 이 글의 조언을 한 단계 더 밀면,
위험을 낮추는 것이 리뷰를 잘하는 것보다 값이 크다는 결론이 나온다.
