# Claude Code 팀은 코드 리뷰를 어떻게 하는가: 읽기는 기계에게, 결정은 사람에게

## 요약

Addy Osmani, Morgan Westlee Lunt, Qing Wang은 2026년 10월 15일
Claude Code 팀의 코드 리뷰 흐름을 공개했다.
Claude Code 코드의 약 90%를 Claude가 쓰는 상황에서,
에이전트가 만드는 양만큼의 코드를 어떻게 리뷰하느냐는 질문에 대한 답이다.
6월부터 9월 사이 Claude Code 저장소에 병합된 PR은 두 배 넘게 늘었지만,
되돌려야 했던 PR의 비율은 40% 넘게 줄었다.
저자들은 리뷰를 없앤 것이 아니라 읽기의 대부분을 기계로 옮기고,
사람의 시간과 주의를 아끼는 쪽으로 최적화하고,
실수를 빠르고 쉽게 되돌리는 데 크게 투자했다고 설명한다.

### 리뷰의 목적과 목표

에이전트가 코드를 쓰면 변경의 수가 빠르게 늘어난다.
Anthropic 모노레포에 하루 들어오는 변경은 5월 약 2,500개에서
9월 3만 개 이상으로 늘었다.
Claude Code는 모노레포와 분리된 자기 저장소에 있지만 같은 압박을 받는다.
이 속도에서 한 줄씩 읽는 리뷰는 불가능에 가깝다.

저자들은 코드 리뷰가 두 가지 일을 한다고 본다.
출시 전에 문제를 찾아 고치는 일과,
팀 전체에 코드베이스에 대한 맥락과 이해를 퍼뜨리는 일이다.
그리고 “사람이 코드를 읽었는가”는
“이 변경에서 무엇이 잘못될 수 있고,
자동이든 사람이든 어떤 검사가 그것을 잡아야 하는가”를
부정확하게 대신하는 지표라고 말한다.
이 질문은 리뷰의 시점도 바꿨다.
예전의 리뷰는 코드를 쓰고 PR을 열고 동료를 기다리는 길 끝의 관문이었지만,
이제는 글을 쓰는 동안 계속 작동하는 맞춤법 검사에 가깝다.
대부분의 변경은 사람이 보기 전에 Claude가 적어도 한 번 리뷰하고 고친다.

희소한 자원은 사람의 시간과 주의다.
여기서 사람의 시간은 리뷰하는 데 쓰는 시간과
나쁜 코드가 깨뜨린 것을 고치는 데 쓰는 시간을 함께 가리킨다.
목표는 CLI, 데스크톱과 웹, 모바일 앱을 아우르는
Claude Code 저장소의 PR 대부분이
작성자를 포함해 많아야 한 사람의 개입으로 병합되면서도
되돌림과 장애가 늘지 않는 것이다.
사람의 시간은 PR당 사람의 승인 수(중앙값과 95번째 백분위),
사람의 댓글, PR이 사람을 기다린 시간으로 잰다.
되돌림과 장애 비율은 안전장치다.
그 수치가 오르면 사람의 시간을 아낀 것이 아니라 옮긴 것일 뿐이다.

### 변경 하나가 지나는 일곱 겹

| 단계                       | 내용                                                         |
| -------------------------- | ------------------------------------------------------------ |
| PR 전 검증                 | 테스트, 빌드, 린터 실행 뒤 서브에이전트가 새 컨텍스트로 리뷰 |
| AI 리뷰                    | 여러 에이전트가 병렬로 찾고, 투표를 통과한 지적만 게시       |
| 보안 리뷰                  | 별도 자동 리뷰, 열린 지적이 있으면 병합 불가                 |
| 필수 CI                    | 린트, 타입, 플랫폼별 테스트, 빌드와 패키징                   |
| 위험 기반 승인             | 분류기가 정한 등급에 따라 사람 0명, 1명, 2명                 |
| 병합 큐, 플래그, 단계 출시 | 최신 main에서 재검사, 사내 사용 먼저, latest 뒤에 stable     |
| 빠른 감지와 되돌림         | 플래그 끄기, 되돌림, 주간 온콜, 장애 리뷰                    |

PR을 열기 전 단계에서는 Claude에게 테스트, 빌드,
디자인과 비교할 스크린샷처럼 실행할 수 있는 것을 주고
다 됐다고 말하는 대신 출력을 보이게 한다.
그다음 서브에이전트가 새 컨텍스트에서 diff를 리뷰한다.
많은 팀원이 PR 전에 사내 스킬 몇 개를 더 돌린다.
버그를 찾는 스킬, diff를 단순하게 만드는 스킬,
동작을 처음부터 끝까지 확인하는 스킬이며,
UI 변경은 디자인 가이드라인과 대조한다.
Claude Code를 만든 Boris Cherny는
Claude에게 자기 작업을 검증할 방법을 주는 것이
좋은 결과를 얻는 데 아마 가장 중요하며,
최종 결과를 2~3배 낫게 한다고 추정했다.

자동 리뷰어가 같은 것을 계속 지적하면 근원에서 고친다.
스킬, 린트 규칙, 또는 `CLAUDE.md`와 `REVIEW.md` 같은 지시 파일이다.
`CLAUDE.md`는 스택, 관례, 목표와 비목표를 알려 준다.
모든 리뷰가 이 파일을 읽으므로 큰 코드베이스에서는 짧게 두고
다른 문서를 가리키게 하며,
리뷰어는 이 파일의 관례를 어긴 코드와
이 파일을 낡게 만드는 변경을 지적한다.
`REVIEW.md`는 코드 소유자가 쓴다.
좋은 `REVIEW.md`는 짧고, 그 저장소에서 실패가 어떤 모습인지 말한다.
문서라면 “거짓말한다”, 설정이라면 “잘못 라우팅한다”이다.
사소한 지적에 상한을 두고, 건너뛸 경로를 나열하고,
이름에서 짐작하지 말고 파일과 줄을 근거로 대라고 요구한다.
요약은 지적 개수로 시작하고 고칠 것이 없으면 없다고 분명히 말하게 한다.
리뷰어가 이 파일을 실제로 따르는지는 따로 확인한다.

모든 PR은 사람이 보기 전에 Claude의 리뷰를 받는다.
리뷰어는 diff를 저장소 전체, 그리고 PR이 밝힌 의도와 대조해 읽고,
변경이 제 문제를 푸는지, 시스템에 맞는지, 다른 것을 깨뜨리는지 묻는다.
버그 수정이라면 근본 원인을 찾는다.
리서치 프리뷰를 내놓았을 때 의미 있는 리뷰 댓글을 받은 사내 PR 비율은
16%에서 54%로 올랐다.
1,000줄이 넘는 PR은 대부분 지적을 받고, 작은 PR은 대부분 깨끗하게 돌아온다.
관리자는 저장소마다 Quick, Standard, Deep 중 하나를 고르며,
Deep은 버그 하나를 놓치는 비용이 추가 리뷰 시간보다 클 때 쓸 만하다.
스타일, 진단, 정리에 관한 지적은 버리는데,
이 필터는 사내 PR에서 A/B 테스트를 거친 뒤에 남겼다.
남은 지적은 심각도 순의 인라인 댓글이 되고,
Important, Nit, Pre-existing 태그가 붙어
PR이 만들지 않은 버그가 작성자 탓처럼 보이지 않게 한다.
모든 지적에는 답해야 하며, 고치거나 이유를 달아 스레드를 닫는다.
에이전트가 밤사이 수정을 맡는 경우가 많아,
작성자가 돌아오면 PR이 이미 한 라운드를 더 거친 상태다.
보안 리뷰의 지적은 이후 커밋이 문제를 고치면 저절로 사라진다.
PR 템플릿은 어떻게 테스트했고 어떻게 되돌리는지 묻는다.
Claude가 채울 수는 있지만 변경을 요청한 사람이 서명한다.

사람의 승인은 위험 등급에 따라 달라진다.

| 위험 | 예                                                   | 사람 승인 |
| ---- | ---------------------------------------------------- | --------- |
| 낮음 | 문서, 문구, 사내 전용 기능, 플래그 뒤의 추가 변경    | 필요 없음 |
| 중간 | 일반 제품 변경, 캐시, 자동 업데이트, 시스템 프롬프트 | 1명       |
| 높음 | 가장 위험한 코드와 항상 두 사람이 필요한 일부 경로   | 2명       |

등급은 작성자가 아니라 변경이 정한다.
한 분류기가 등급을 고르고,
다른 분류기가 등급과 상관없이 이 변경에 사람이 더 필요한지 묻는다.
소유자가 민감하다고 지정한 경로와
모든 CI 워크플로 파일은 항상 사람을 요구한다.
가벼운 경로는 저장소의 신뢰 목록에 있는 작성자,
주로 그 저장소를 맡은 팀에게만 열린다.
에이전트의 승인은 사람의 승인으로 치지 않는다.
에이전트가 쓴 PR에서는 에이전트를 지휘한 사람이
직접 타이핑한 것처럼 필수 리뷰어 가운데 하나가 된다.
승인은 특정 커밋에만 유효해서,
에이전트가 새로 푸시하거나 사람이 손으로 충돌을 해결하면 다시 승인해야 한다.

병합 큐는 변경을 적용한 최신 main에서 모든 검사를 다시 돌려,
따로는 통과한 두 PR이 합쳐져 main을 깨뜨리는 일을 막는다.
새 동작은 대개 플래그 뒤에서 Anthropic 직원에게 먼저 나가고,
공개 릴리스는 latest 채널에 먼저, stable 채널은 그 뒤에 나간다.
플래그는 배포 없이 끌 수 있고,
장애 리뷰는 어느 층이 잡았어야 했는지 묻는다.
한 동료는 속도를 늦추면 오류율이 낮아지기는 하지만
대체로 모든 일을 덜 하기 때문이라고 했고,
팀은 늦추기보다 문제를 알아차리고 고치는 속도를 높이는 쪽을 택했다.

### 리뷰어를 개선하는 고리

팀은 장애를 일으킨 과거 PR을 수정 커밋, 되돌림과 함께 모으고,
그 코드를 아는 엔지니어에게 각 버그와 위치를 확인하게 해 평가 세트를 만들었다.
리뷰어는 매일 이 세트로 평가되고,
프롬프트, 도구, 모델을 바꿀 때마다 점수가 오른 경우에만 변경을 유지한다.

잡음은 사람들이 댓글에 어떻게 반응했는지로 잰다.
고쳤는지, 틀렸다고 했는지, 의도된 동작이라고 했는지,
중요하지 않다고 했는지를 분류하고,
문제가 없다고 아는 PR에 리뷰어를 돌려
해로운 수정을 부를 지적을 얼마나 하는지도 센다.
글로 정해 둔 우선순위는 실제 버그를 잡는 것이 먼저이고
리뷰 라운드를 줄이는 것이 그다음이다.
작성자가 에이전트라면 잡음의 비용이 더 크다.
사람은 사소한 지적을 몇 초 만에 넘기지만,
에이전트는 그것을 고치고 또 한 번 리뷰를 부른다.

리뷰는 수렴해야 한다.
한 CLI PR은 작성자가 멈추기 전까지 밤사이 50번 넘게 리뷰와 수정을 오갔다.
리뷰어가 계속 지적한 것에 `git blame`을 돌려 보니
약 59%가 리뷰어의 첫 번째 패스 때부터 있던 코드였다.
새 버그를 찾은 것이 아니라 라운드마다 오래된 버그를 몇 개씩 더 찾아낸 셈이다.
저자들은 이 문제를 스스로 키웠다고 인정한다.
패스마다 새로운 것을 잡으니 여러 라운드를 기본으로 돌리는 데 익숙해졌는데,
위험한 변경에는 그럴 가치가 있어도 모든 PR에 그럴 필요는 없었다.
팀은 재현율과 함께 통과까지의 라운드를 추적하기 시작했고,
세 라운드 뒤에는 접근 방식을 다시 생각하라고 요청하는 상한,
처음 몇 번 뒤에는 새 diff만 보는 재리뷰,
한 줄이 아니라 버그의 부류를 지적하기,
이미 단 지적을 반복하지 않기를 도입했다.
리뷰 에이전트는 밤마다 기존 코드도 훑어
오래된 버그가 다른 곳에서 드러나기 전에 잡는다.

| 지표                         | 전   | 후   |
| ---------------------------- | ---- | ---- |
| 한 번의 리뷰와 수정으로 통과 | 65%  | 78%  |
| 다섯 라운드 이상 필요        | 8.9% | 1.5% |
| 통과까지 평균 리뷰 횟수      | 2.08 | 1.32 |

### 사람이 남는 자리

시니어 엔지니어를 깊은 작업에서 꺼내 흔한 실수를 잡게 하는 비용은
자동 리뷰보다 훨씬 크다.
그래서 사람의 일은 모든 diff를 읽는 것에서 기계가 못하는 결정으로 옮겨 갔다.
이것을 만들어야 하는가라는 방향, 취향, 범위의 판단,
결제와 자동 업데이트와 CI 워크플로 같은 위험한 코드,
남들이 따라 할 패턴을 정하는 아키텍처,
테스트 출력과 실행한 명령과 스크린샷 같은 증거 읽기,
그리고 누가 타이핑했든 출시되는 모든 변경에 대한 책임이다.
리뷰 병목을 해결했다고 선언한 한 팀도
팀 밖에서 온 변경에는 사람의 리뷰를 남겨
누군가 “이걸 해야 하나?”를 묻게 했다.
증거를 읽을 때 검사가 무엇을 놓칠지 말할 수 없다면
빠른 승인 대신 제대로 된 리뷰를 요청하라고 한다.

리뷰의 두 번째 일인 맥락 공유에는 공식 절차가 없다.
팀에서 Claude Code 전체의 정신 모델을 가진 사람은 없고,
누구도 그럴 필요가 없다고 본다.
어떤 부분을 이해하고 싶으면 Claude에게 정확히 그 조각의 설명서를 쓰게 한다.
몇 분이면 되고 오늘의 코드를 반영한다.
어떤 이는 그 부분을 시각화해 자기가 배우는 방식대로 가르쳐 주는
작은 아티팩트를 만들게 한다.
한 줄짜리 문구 수정은 거의 아무것도 가르쳐 주지 않지만,
곧 바꿀 모듈의 설명서는 많은 것을 가르쳐 준다는 판단이다.
열린 Slack 채널에서 일하는 문화도
다른 사람이 만드는 것을 만드는 동안 보게 해 준다.

팀 규범은 “병합한 사람이 책임진다”이다.
변경은 작아서 리뷰하고 디버깅하고 되돌리기 쉽고,
플래그와 되돌림과 단계적 출시가 대부분의 실수를 몇 분 안에 무르며,
위험 반경에 따라 사람과 검사의 수가 정해지고,
텔레메트리와 사내 사용이 회귀를 빨리 드러내며,
장애 리뷰는 사람이 아니라 시스템을 본다.
소유권도 공유된다.
누구나 다른 사람이 만드는 것을 보고
스레드를 이어받거나 빈틈에 Claude를 보낼 수 있고,
코드 소유자가 아닌 사람에게서도 피드백이 온다.
저자들은 이 개방성이 모든 줄에 관문을 두지 않고도
품질을 지키는 큰 이유라고 본다.

에이전트 덕에 일을 시작하기가 싸졌으니 병합하지 말아야 할 작업도 생긴다.
보통 채널에서 누군가 왜 하느냐고 묻거나, 이전 결정을 가리키거나,
더 단순한 길을 제안하면 작성자가 PR을 닫거나 고친다.
코드를 빨리 썼으니 PR을 닫아도 손실처럼 느껴지지 않는다.
요령은 다른 방향을 완성된 PR의 차단 댓글이 아니라
스레드 초반에 꺼내는 것이다.

### 도입 안내와 남은 과제

글은 대부분의 구성 요소가 이미 있다며 도입 순서를 안내한다.
PR 전에는 에이전트가 돌릴 검사를 짧은 `CLAUDE.md`에 적고,
포매터와 린터를 훅으로 돌리고,
`/code-review`와 `/security-review`나 새 컨텍스트의 서브에이전트 리뷰를 쓰고,
`REVIEW.md`를 만들어 반복되는 리뷰 댓글을 옮긴다.
PR에서는 CI를 필수로 하고
PR 템플릿에 “Testing”, “Risk”, “How to revert”를 넣고,
AI 리뷰어를 저장소 하나에 붙여 몇 주간 `REVIEW.md`를 다듬은 뒤 넓히고,
자동 보안 리뷰를 더해 모든 스레드가 해결되어야 병합되게 하고,
리뷰 깊이를 위험에 맞추고 라운드에 상한을 둔다.
승인에서는 위험 등급을 변경 기준으로 글로 적고
엄격하게 시작해 근거로 풀고,
가벼운 경로는 신뢰하는 작성자에게만 열고,
CODEOWNERS와 브랜치 보호로 인증, 결제, CI와 릴리스 워크플로,
설치 프로그램이 항상 사람을 거치게 하고,
봇의 승인으로 사람을 대신하지 않으며 새 커밋에는 승인을 무효로 한다.
병합 뒤에는 병합 큐, 기능 플래그, 사내 우선 사용, 단계적 출시,
한 단계 되돌림을 갖추고, 장애와 되돌림을 평가 세트로 만들고,
사람의 시간을 재되 되돌림과 장애 비율을 안전장치로 둔다.

Code Review 제품 발표는 PR 승인이 여전히 사람의 몫이라고 했고,
제품은 승인이 아니라 지적만 게시한다.
팀 자신의 저장소는 한 걸음 더 나아가,
어떤 저위험 변경을 자동 검사만으로 병합할지 소유자가 정하게 한다.
리뷰가 무언가를 놓치면 모델 앞에 무엇이 없었는지 묻고
그 답을 `CLAUDE.md`, 스킬, 새 검사로 옮긴다.
저자들은 되돌림과 장애 수치가 움직일 때
승인 기준을 자동으로 조이는 서킷 브레이커(circuit breaker)가 아직 없으며,
엔지니어들은 사람 없이 병합되는 코드가 더 늘기 전에
그것이 갖춰지기를 원한다고 밝힌다.

## 분석

### “누가 읽었나”를 “어떤 검사가 잡나”로 바꾸면 리뷰는 설계 문제가 된다

이 글의 가장 중요한 문장은 사람이 읽었느냐는 기준이
무엇이 잘못될 수 있고 어떤 검사가 그것을 잡아야 하느냐를
부정확하게 대신한다는 말이다.
전통적인 리뷰는 승인 버튼을 누른 사람이 있다는 사실로 품질을 보증했다.
그러나 피곤한 리뷰어의 승인이나 2,000줄짜리 PR의 형식적인 승인은
읽었다는 기록만 남기고 위험을 다뤘다는 증거는 남기지 않는다.

질문을 바꾸면 리뷰는 변경마다 가능한 실패와 그것을 잡을 검사를 짝짓는 일이 된다.
서식은 훅이, 타입은 CI가, 흔한 버그는 AI 리뷰어가,
두 PR의 충돌은 병합 큐가,
사용자가 보는 회귀는 사내 사용과 플래그가 맡는다.
사람의 리뷰는 그 목록의 한 항목이고,
가장 비싸고 느린 검사이므로 다른 검사가 못 잡는 실패에만 쓰는 것이 맞다.
원문의 그림이 리뷰를 관문 하나가 아니라
일부를 잡고 일부를 놓치는 여러 겹으로 그리는 것도 같은 생각에서 나온다.
어느 층도 완벽할 필요가 없고, 모든 층을 통과한 것은 되돌림이 처리한다.

이 전환은 리뷰를 관문에서 과정으로 옮긴다.
원문이 맞춤법 검사에 빗댄 것처럼 같은 종류의 검사가
PR 전 로컬, PR, 병합 큐, 병합 뒤 밤마다의 전체 코드 점검에서 되풀이된다.
한 번의 관문이 모든 것을 잡아야 한다는 부담이 사라지면
각 시점의 검사를 가볍게 만들 수 있고, 사람의 리뷰도 그 부담에서 풀려난다.
사람 리뷰를 줄일 수 있었던 이유는 리뷰어가 좋아져서만이 아니라
사람 리뷰가 혼자 책임지지 않아도 되는 구조를 먼저 만들었기 때문이다.

### 최적화 대상과 안전장치를 함께 정해야 비용이 숨지 않는다

원문의 목표 문장에는 최적화 대상과 제약이 함께 들어 있다.
사람의 시간을 줄이되 되돌림과 장애는 늘지 않아야 한다.
여기서 사람의 시간은 리뷰하는 시간과 나쁜 코드를 고치는 시간을 모두 가리킨다.
리뷰 자동화의 성과를 리뷰 시간 감소로만 보고하는 팀은
이 등식의 절반만 본다.
리뷰를 덜 하고 장애 대응을 더 하면 시간은 줄지 않고 옮겨 갈 뿐이며,
옮겨 간 시간은 대개 더 비싼 사람의 더 급한 시간이다.

지표를 분포로 잡은 것도 눈여겨볼 만하다.
PR당 사람 승인 수를 평균이 아니라 중앙값과 95번째 백분위로 본다.
대부분의 PR이 빨리 지나가도 몇 개가 며칠씩 사람을 기다리면
팀의 체감은 그 꼬리가 정한다.
PR이 사람을 기다린 시간을 따로 재는 것도 같은 이유다.
리뷰에 쓴 시간보다 기다린 시간이 작업의 흐름을 더 크게 끊는다.

되돌림과 장애 비율을 목표가 아니라 안전장치로 둔 것은 의도된 설계다.
안전장치는 사람의 시간을 아꼈다는 주장이 사실인지 확인하는 경보다.
경보를 목표로 바꾸면 굿하트의 법칙이 작동한다.
되돌리지 않고 고쳐 나가는 쪽을 택하면
되돌림 비율은 좋아 보이지만 회귀는 그대로다.
그래서 안전장치 지표는 체계를 조정하는 데 쓰고,
사람이나 팀을 평가하는 기준으로는 쓰지 않는 편이 안전하다.

목표끼리 부딪힐 때를 대비해 우선순위를 글로 적어 둔 점도 배울 만하다.
실제 버그를 잡는 것이 먼저이고 리뷰 라운드를 줄이는 것이 그다음이다.
라운드를 줄이려고 리뷰어를 조용하게 만들면 버그를 놓치고,
버그를 더 잡으려고 민감하게 만들면 라운드가 늘어난다.
어느 쪽을 택할지 미리 정해 두지 않으면
튜닝할 때마다 같은 논쟁을 되풀이한다.

### 검증은 완료 선언 대신 출력을 요구하는 데서 시작한다

원문은 리뷰의 대부분이 이제 PR이 생기기 전에 일어난다고 말한다.
그 출발점은 에이전트에게 실행할 수 있는 것을 주고
다 됐다는 말 대신 출력을 보이게 하는 습관이다.
에이전트의 완료 선언은 주장이고, 명령의 출력은 증거다.
Boris Cherny가 이것을 결과를 2~3배 낫게 하는 가장 중요한 일로 꼽은 이유도
여기에 있다.
뒤의 모든 층은 이 단계가 걸러 낸 나머지를 다루므로,
이 단계가 약하면 뒤의 층이 그만큼 무거워진다.

검증 수단은 영역마다 달라야 한다.
Cherny는 bash 명령 하나일 수도, 테스트 스위트일 수도,
브라우저나 휴대폰 시뮬레이터에서 앱을 시험하는 것일 수도 있다고 했다.
원문의 팀은 UI 변경을 스크린샷과 디자인 가이드라인으로 확인한다.
이 목록을 영역마다 정해 두지 않으면 에이전트는 가장 쉬운 검증,
대개 단위 테스트만 돌리고 끝낸다.
따라 하는 팀이라면 저장소의 영역마다
이 영역의 변경이 맞다는 것을 무엇으로 보일지
한 줄씩 적어 두는 것이 첫걸음이다.

새 컨텍스트의 서브에이전트에게 diff를 다시 보게 하는 것도 같은 원리다.
코드를 쓴 에이전트는 자기가 내린 결정의 이유를 컨텍스트에 갖고 있어
같은 실수를 실수로 보지 못한다.
새 컨텍스트의 리뷰어는 결과물만 보고 판단하므로
작성 과정의 합리화에 끌려가지 않는다.
사람 사이의 리뷰를 작성자가 아닌 사람에게 맡기는 것과 같은 이유다.

PR 전에 diff를 단순하게 만드는 스킬을 따로 둔다는 점도 흥미롭다.
에이전트가 쓴 코드는 필요한 것보다 길어지기 쉽고,
그 길이는 이후 모든 리뷰와 유지보수의 비용이 된다.
1,000줄이 넘는 PR은 대부분 지적을 받고 작은 PR은 대부분 깨끗하다는 관찰도
같은 방향을 가리킨다.
PR을 작게, diff를 짧게 만드는 것이 리뷰 비용을 줄이는 가장 싼 방법이다.
포매터와 린터를 훅으로 돌리라는 도입 안내도 같은 원리다.
기계적으로 정할 수 있는 것은 리뷰가 시작되기 전에 기계가 끝내야 한다.

### 반복되는 지적은 고칠 대상이 아니라 시스템의 결함 신호다

원문에서 가장 옮겨 쓰기 쉬운 습관은 같은 지적이 되풀이되면
PR에서 고치는 대신 근원에서 고치는 것이다.
같은 지적이 세 번 나왔다면 세 번 고친 것이 아니라
같은 비용을 세 번 낸 것이다.
원문이 든 근원은 스킬, 린트 규칙, `CLAUDE.md`, `REVIEW.md`이고,
어디에 고칠지는 지적의 성격이 정한다.
기계적으로 판정할 수 있으면 린트 규칙,
작성 단계에서 에이전트가 알아야 하면 `CLAUDE.md`,
특정 영역에서만 중요하면 `REVIEW.md`,
여러 단계를 거쳐야 확인할 수 있으면 스킬이다.

`CLAUDE.md`를 짧게 두라는 조언에는 비용 계산이 깔려 있다.
모든 리뷰가 이 파일을 읽으므로
한 줄을 더할 때마다 모든 리뷰가 그 줄을 읽는다.
더 중요한 것은 리뷰어가 이 파일을 낡게 만드는 변경을 지적한다는 점이다.
지시 파일이 코드와 어긋나 낡는 것은
지시 파일을 쓰는 팀이 가장 흔히 겪는 실패다.
이 팀은 그것을 리뷰 항목으로 만들어 문서의 유지보수를 리뷰어에게 맡겼다.

`REVIEW.md`에서 가장 쓸모 있는 장치는 실패의 모습을 한 단어로 적는 것이다.
리뷰어에게 버그를 찾으라고만 하면 모든 것을 본다.
이 디렉터리의 문서는 사실과 다를 때 실패한다고 알려 주면
리뷰어는 문서의 주장을 코드와 대조하는 데 집중한다.
코드 소유자가 이 파일을 쓰게 한 것도 같은 이유다.
무엇이 실패인지는 그 코드를 아는 사람만 정할 수 있다.
요약을 지적 개수로 시작하고 고칠 것이 없으면 없다고 쓰게 한 것은
읽는 사람이 첫 줄에서 판단하게 하려는 장치다.

그러나 지시 파일을 써 둔 것과 그것이 지켜지는 것은 다르다.
원문이 리뷰어가 `REVIEW.md`를 실제로 따르는지 따로 확인한다고 굳이 적은 것은
이 차이를 알기 때문이다.
지시를 더할 때마다 그 지시가 바꿔야 할 행동이 실제로 바뀌었는지
몇 개의 PR로 확인해야 한다.
리뷰가 무언가를 놓쳤을 때 모델 탓을 하지 않고
모델 앞에 무엇이 없었는지 묻는 원칙도 같은 고리에 있다.
모델 탓으로 돌리면 다음 모델을 기다리는 것밖에 할 일이 없지만,
입력의 문제로 보면 오늘 고칠 수 있다.

### 리뷰어의 잡음은 에이전트에게 더 비싸고, 수렴은 설계해야 생긴다

원문의 AI 리뷰는 찾는 에이전트와 거르는 에이전트를 나눈다.
여러 에이전트가 넓게 찾고,
다른 무리가 투표해 충분히 동의한 것만 게시한다.
한 에이전트에게 많이 찾으면서 틀리지도 말라고 하면 둘 다 어중간해진다.
버리는 범주인 스타일, 진단, 정리 지적의 필터 자체를
A/B 테스트로 검증한 뒤에 남겼다는 점도 배울 만하다.
필터를 감으로 정하면 중요한 지적이 그 범주에 섞여 사라져도 알 수 없다.

Important, Nit, Pre-existing 태그는 작은 장치지만
리뷰 문화에 미치는 영향이 크다.
AI 리뷰어는 diff 주변의 오래된 버그까지 찾아내므로,
태그가 없으면 작성자는 자기가 만들지 않은 문제로
PR이 막히는 경험을 되풀이한다.
그 경험이 쌓이면 사람들은 리뷰어를 끄거나 무시하게 된다.
모든 지적에 답하되 고치거나 이유를 달아 닫는 두 길만 둔 규칙은
읽지 않고 병합하는 길을 막는다.
닫을 때 남긴 이유는 그대로 리뷰어를 개선하는 데이터가 된다.

수렴 문제는 에이전트끼리의 리뷰에서 새로 생긴 문제다.
사람끼리의 리뷰에는 피로라는 자연스러운 멈춤 장치가 있었지만,
에이전트 작성자와 에이전트 리뷰어는 밤새 50번도 오갈 수 있다.
원문의 진단 방법은 그대로 가져다 쓸 수 있다.
라운드가 길어지면 지적 대상 줄에 `git blame`을 돌려
새로 생긴 줄인지 처음부터 있던 줄인지 가른다.
이 팀에서는 약 59%가 첫 패스 때부터 있던 코드였고,
문제는 작성자가 아니라 한 번에 다 말하지 않는 리뷰어에 있었다.

도입한 네 규칙은 각자 다른 실패를 막는다.
세 라운드 상한은 단순한 차단이 아니라 접근을 다시 생각하라는 요청이며,
세 번 고쳐도 통과하지 못하는 변경은 대개 세부가 아니라 방향이 틀렸다.
새 diff만 다시 보는 재리뷰는
같은 코드에서 오래된 버그를 조금씩 꺼내는 일을 막고,
버그의 부류를 지적하는 규칙은
한 줄만 고쳐 같은 버그가 다른 곳에 남는 일을 막으며,
반복 금지는 같은 논쟁의 되풀이를 막는다.
HN의 zeroonetwothree는 대부분 바이브 코딩으로 만든
약 1,000만 줄 규모의 프로젝트에서
에이전트가 버그를 말한 그 한 곳만 고치고
같은 버그가 다른 곳에 남는 일을 겪는다고 했다.[^zeroonetwothree]
버그의 부류를 지적하라는 규칙이 바로 이 습관을 겨냥한다.

여러 라운드를 기본값으로 돌리던 관행을 스스로 키운 문제라고 인정한 대목은
조직이 실패를 다루는 방식으로도 읽을 만하다.
한 번 효과를 본 관행이 기본값이 되면,
그 관행이 비용을 낼 때도 아무도 다시 묻지 않는다.
이 팀은 재현율과 라운드를 함께 재기 시작하면서 그 비용을 볼 수 있게 되었다.
라운드만 보면 리뷰어를 조용하게 만드는 쪽으로,
재현율만 보면 시끄럽게 만드는 쪽으로 튜닝이 쏠린다.

### 리뷰어를 바꾸는 일도 코드 변경처럼 검증한다

이 체계에서 다른 팀이 가장 먼저 시작해야 할 장치는 장애 기반 평가 세트다.
장애를 일으킨 PR을 모아 그 코드를 아는 엔지니어가 버그와 위치를 확인하고,
리뷰어의 프롬프트, 도구, 모델을 바꿀 때마다 그 세트 전체로 다시 채점해
점수가 오를 때만 변경을 남긴다.
일반적인 버그 벤치마크는 그 팀이 실제로 겪는 실패와 다르지만,
자기 장애 이력으로 만든 세트는
우리를 아프게 했던 종류의 버그를 잡는지 직접 묻는다.
데이터가 쌓이는 데 시간이 걸리므로
도입 순서상 가장 먼저 모으기 시작해야 한다.

잡음을 사람의 반응으로 재는 방식도 정교하다.
리뷰어의 댓글을 고쳤다, 틀렸다, 의도된 동작이다, 중요하지 않다로 나누면
네 범주가 서로 다른 개선 방향을 가리킨다.
틀렸다가 많으면 리뷰어가 코드를 잘못 읽고,
의도된 동작이 많으면 리뷰어가 맥락을 모르며,
중요하지 않다가 많으면 리뷰어의 기준이 팀과 어긋난다.
앞의 둘은 지시 파일을, 마지막은 필터를 고칠 신호다.

깨끗하다고 아는 PR에 리뷰어를 돌려 해로운 지적을 세는 것은
안전 점검에 가깝다.
에이전트가 지적을 성실히 고치는 환경에서
틀린 지적은 무시되지 않고 버그가 된다.
사람이 작성자일 때 잡음은 짜증이지만,
에이전트가 작성자일 때 잡음은 결함의 원천이다.
장애가 날 때마다 평가 세트에 사례가 하나씩 더해지고,
장애 리뷰가 어느 층이 잡았어야 했는지 물어 그 층을 강화하므로,
실패 하나가 검사 하나와 평가 사례 하나로 바뀌는 고리가 완성된다.

### 승인은 사람이 아니라 변경과 커밋에 묶인다

위험 등급을 작성자가 아니라 변경이 정한다는 원칙은
신뢰가 검사를 대신하지 못하게 한다.
시니어가 쓴 결제 코드도 위험하고, 신입이 쓴 문서 수정도 안전하다.
다만 가벼운 경로를 쓸 자격은 작성자에게 걸려 있어,
신뢰 목록에 있는 사람이 낮은 등급의 변경을 낼 때만
사람 없는 병합이 열린다.
변경의 위험과 작성자의 신뢰라는 두 조건이 함께 걸리는 구조다.

분류기를 둘 둔 것은 등급표의 한계를 인정한 설계다.
등급표는 아무리 잘 만들어도 예외를 다 담지 못하므로,
두 번째 분류기가 등급과 무관하게 이 변경에 사람이 더 필요한지 따로 묻는다.
그래도 분류기에 맡기지 않는 경로가 있다.
소유자가 민감하다고 지정한 경로와 모든 CI 워크플로 파일이다.
CI 워크플로가 이 목록에 있다는 점이 중요하다.
검사 체계 자체를 바꾸는 변경은 그 체계가 검사할 수 없고,
검사를 끄는 PR이 검사를 통과하는 일은 막아야 한다.

봇의 승인을 사람의 승인으로 치지 않는다는 규칙은
“사람 한 명 필수”가 “리뷰어 한 명 필수”로 미끄러지는 것을 막는다.
그 구분이 흐려지면 결국 봇 둘이 서로를 승인하는 구조가 된다.
에이전트를 지휘한 사람을 필수 리뷰어로 센다는 규칙은
반대 방향의 빈틈을 막는다.
에이전트에게 맡겼다는 이유로 책임이 비지 않게 하는 것이다.
따라서 이 체계에서 “작성자를 포함해 많아야 한 사람”은
대개 에이전트를 지휘한 그 사람을 가리킨다.

승인을 커밋에 묶은 규칙은 에이전트 시대에 특히 중요하다.
에이전트는 승인을 받은 뒤에도 쉬지 않고 PR을 고친다.
승인을 PR에 묶으면 사람이 본 적 없는 코드가 승인된 채로 병합된다.
사람이 손으로 충돌을 해결한 병합도 새 커밋으로 보는 것은,
시스템이 보증할 수 없는 변경이라면 누가 만들었든 다시 보겠다는 뜻이다.
도입 안내가 위험 등급을 엄격하게 시작해 근거로 풀라고 한 것도 같은 맥락이다.
느슨하게 시작해 장애가 나면 조이는 방식은 조이는 시점이 늘 장애 뒤다.

### 되돌릴 수 있어야 리뷰를 가볍게 할 수 있다

이 체계에서 리뷰의 무게는 되돌리기 쉬운 정도에 반비례한다.
플래그 뒤의 사내 전용 기능이 사람 승인 없이 병합될 수 있는 것은
그것이 몇 분 안에 꺼질 수 있기 때문이다.
되돌리기 어려운 변경일수록 앞쪽 리뷰가 무거워지고, 쉬우면 가벼워진다.
그래서 리뷰를 줄이려는 팀은 리뷰보다 되돌림 수단을 먼저 갖춰야 한다.
병합 큐, 기능 플래그, 사내 우선 사용,
latest와 stable 채널의 단계적 출시, 한 단계 되돌림이 그것이다.

병합 큐의 역할은 속도와 함께 커진다.
병합이 빨라질수록 PR이 만들어진 시점의 main과
병합되는 시점의 main은 멀어지고,
따로는 통과한 두 PR이 합쳐져 main을 깨뜨릴 가능성도 커진다.
사내 사용은 리뷰가 놓친 것을 사용자 앞에서 잡는 마지막 기회다.
원문은 사내의 많은 사용이 사용자보다 먼저 회귀를 드러낸다고 말한다.
이 층은 자기 제품을 매일 쓰는 회사에서 특히 강하게 작동한다.

“병합한 사람이 책임진다”는 규범이 처벌이 되지 않는 것도
이 안전망 덕분이다.
원문이 든 전제는 작은 변경, 되돌릴 수 있는 구조,
위험 반경에 비례한 기준, 빠른 회귀 발견, 비난 없는 장애 리뷰다.
되돌리기 어려운 환경에서 네가 병합했으니 네가 책임지라고 하면
사람들은 병합을 피할 뿐이다.
소유권을 공유한다는 대목도 이 규범을 보완한다.
개인의 책임은 수정을 맡기고, 팀의 소유권은 관찰과 피드백의 기회를 나눈다.

늦추기보다 빨리 알아차리겠다는 선택은
리뷰를 무겁게 해서 실패를 막는 전략과
실패의 비용을 줄이는 전략 사이의 선택이다.
앞의 전략은 처리량을 희생하고, 뒤의 전략은 감지와 복구에 투자한다.
다만 원문은 이 선택의 다음 단계가 아직 비어 있다고 인정한다.
지표가 나빠질 때 승인 기준을 자동으로 조이는 서킷 브레이커가 없고,
지금은 나쁜 병합을 알아차리는 일이 작성자와 온콜,
되돌림과 장애 대시보드에 달려 있다.
사람 없는 병합을 늘리는 다음 단계의 전제가
더 좋은 리뷰어가 아니라 자동으로 조이는 장치라는 판단은
이 체계에서 가장 정직한 부분이다.

### 스펙 문서가 없는 대신 방향은 의도, 헌장, 대화로 잡는다

원문에는 스펙 문서를 쓰거나 검증 기준으로 삼는다는 대목이 없다.
대신 방향을 잡는 장치가 네 곳에 흩어져 있다.
변경 단위에서는 PR이 밝힌 의도다.
AI 리뷰어는 diff를 저장소 전체와 함께 이 의도에 대조해 읽는다.
프로젝트 단위에서는 `CLAUDE.md`의 목표와 비목표이고,
모든 리뷰가 이것을 읽는다.
그 위에서 이것을 만들어야 하는가라는 방향, 취향, 범위의 판단은 사람이 맡고,
열린 채널에서 누군가 이전 결정이나 더 단순한 길을 꺼내 PR의 방향을 바꾼다.

검증 기준도 문서와의 일치가 아니라 실행이다.
테스트, 빌드, 스크린샷, 디자인 가이드라인,
처음부터 끝까지의 동작 확인이고,
사람이 읽는 증거도 테스트 출력, 실행한 명령과 결과, 스크린샷이다.
이 체계는 스펙에 맞는지 묻는 대신
실행해서 확인되는지, 되돌릴 수 있는지를 묻는다.

이 대체가 통하는 조건은 이 팀이 자기 제품의 사용자라는 데 있다.
새 동작은 사내에서 먼저 쓰이므로
의도대로 동작하는지를 매일의 사용이 확인한다.
사용자와 개발자가 다른 조직,
외부 요구사항이나 규제를 지켜야 하는 조직에서는
이 대체가 그대로 성립하지 않고, 스펙 문서의 역할이 여전히 남는다.

HN에서는 의도를 어디에 둘지에 대한 다른 해법도 나왔다.
visarga는 의도가 어긋나지 않도록 에이전트에게
그 프로젝트에서 사용자가 남긴 메시지 전체를 다시 읽게 하고,
그렇게 다시 끌어낸 의도로 코드와 테스트를 점검한다고 했다.
긴 작업은 프로젝트 안에 할 일 목록 문서로 남기고,
구현 전과 후에 한 번씩 리뷰한다고 한다.[^visarga]
alasano는 원하는 제품 동작을 정하고 기술 구현을 미리 논의한 뒤
그것을 스펙으로 남기고,
여러 모델의 여러 에이전트가 스펙에 맞을 때까지
리뷰와 수정을 되풀이하게 한다고 했다.[^alasano]
ithkuil은 설계는 자기가 쥐고 구현은 에이전트에게 맡기는 방식을 익히는 중이며,
과제는 자기와 에이전트가 함께 이해하고 합의할 수 있는 형태로
아키텍처를 적어 두는 것이라고 했다.[^ithkuil]
Claude Code 팀이 대화와 사내 사용으로 의도를 확인한다면,
이들은 의도를 문서로 고정해 에이전트의 검증 기준으로 쓴다.

### 제품의 현재 모양은 한 문서가 아니라 여러 장치에 나뉘어 있다

PR 설명이 밝힌 의도는 변경 하나의 수명만큼만 유효하다.
병합되고 나면 그 설명은 그 시점의 판단을 담은 기록이 되고,
뒤의 변경이 같은 동작을 다시 바꾸면 두 설명은 서로 모순된다.
수만 개의 PR 설명을 모아도 지금 제품이 어떤 모양인지는 나오지 않는다.
오래 유지되는 스펙 문서가 하는 일은
이렇게 쌓이는 변경 기록과 달리 현재의 모양을 한곳에 담는 것이다.

원문에서 이 역할에 가장 가까운 것은 `CLAUDE.md`다.
이 파일은 스택, 관례, 목표와 비목표를 적고, 모든 리뷰가 읽으며,
큰 코드베이스에서는 짧게 두고 다른 문서를 가리킨다.
리뷰어는 이 파일의 관례를 어기는 코드뿐 아니라
이 파일의 한 줄을 낡게 만드는 변경도 지적한다.
PR 설명은 쌓이지만 이 파일은 덮어써지고,
리뷰가 이 파일이 늘 현재를 말하도록 강제하는 셈이다.
나머지 현재는 실행할 수 있는 형태로 흩어져 있다.
테스트와 빌드, 디자인과 비교하는 스크린샷,
UI 변경을 대조하는 디자인 가이드라인,
코드 소유자가 쓰는 `REVIEW.md`가 그것이다.
`REVIEW.md`에 문서의 실패를 “거짓말한다”로 적으라는 조언은
문서도 코드와 같은 리뷰 대상이라는 뜻이다.

원문이 밝히는 범위는 여기까지다.

### 사람의 일은 좁아지는 대신 무거워진다

원문이 사람에게 남긴 다섯 가지는 범위가 좁지만 하나하나가 무겁다.
이것을 만들어야 하는가, 위험한 코드, 남들이 따라 할 아키텍처,
증거 읽기, 그리고 결과에 대한 책임이다.
아키텍처가 이 목록에 있는 이유는 그 코드가 버그를 내서가 아니라
에이전트와 사람이 그 패턴을 복제하기 때문이다.
에이전트는 저장소의 기존 코드를 보고 배우므로
나쁜 패턴 하나가 빠르게 퍼진다.

증거를 읽을 때 검사가 무엇을 놓칠지 말할 수 없다면
빠른 승인 대신 제대로 된 리뷰를 요청하라는 조언은
빠른 승인의 자격 조건이다.
검사의 범위를 아는 사람만 검사를 믿고 빨리 승인할 수 있다.
리뷰 병목을 해결했다고 선언한 팀도
팀 밖에서 온 변경에 사람을 남긴 것은,
버그는 기계가 잡아도 다른 팀이 이 저장소의 방향을 바꾸려 하는지는
저장소 소유자가 판단해야 하기 때문이다.

방향을 일찍 제안하라는 요령에는 비용 계산이 깔려 있다.
에이전트 덕에 작성 비용이 낮아지면 PR을 버리는 비용도 낮아진다.
그러면 방향 논의의 최적 시점은 코드가 생긴 뒤가 아니라 생기기 전이나 직후다.
완성된 PR에 차단 댓글을 다는 것은
작성 비용이 높던 시대의 관행이 남긴 가장 비싼 형태의 리뷰다.

맥락 공유의 해법도 사람의 일이 바뀐 방식을 보여 준다.
리뷰로 배우는 방식은 무작위로 들어오는 diff에 기대지만,
필요한 조각의 설명서를 그때그때 만드는 방식은
지금 필요한 곳을 고를 수 있다.
사람이 쓴 설계 문서는 쓴 날의 코드를 설명하고 곧 낡지만,
생성한 설명서는 그날의 코드를 설명한다.
배우는 방식에 맞춘 시각화 아티팩트는 이전에는 없던 선택지다.
다만 이 방식이 맥락 공유를 정말 대신하는지는 비평에서 다룬다.

사내 직원이 먼저 쓰며 회귀를 잡아 주는 대규모 내부 사용,
몇 분 안에 끌 수 있는 플래그 체계, 주간 온콜,
장애 평가 세트를 만들 만한 장애 이력,
그리고 자기 제품을 리뷰어로 쓰는 회사라는 조건이다.
특히 위험 분류기와 장애 기반 평가 세트는
상당한 양의 과거 데이터와 그것을 검증할 전문가의 시간을 전제로 한다.
작은 팀이 사람 승인 없는 병합을 따라 하면서 이 안전망을 갖추지 못하면,
절약한 리뷰 시간이 장애 대응 시간으로 옮겨 갈 뿐이다.
저자들이 경고한 바로 그 상황이다.

HN의 avinoth는 이 글을 Google 인프라 블로그에 빗대며,
작은 팀이 “Google이 그렇게 한다”는 이유로 따라 하다 쓴 교훈을 얻었듯
토큰을 사실상 무제한으로 쓰는 연구소의 방식을
그대로 따라 해서는 안 된다고 했다.[^avinoth]
chris_money202는 이런 글이 피곤한 이유로 스택의 단순함을 들었다.
자기 프로젝트는 컴파일 언어라 빌드가 오래 걸리고,
200GB 가까운 툴체인 의존성과 서드파티 라이선스 서버가 필요하며,
64코어 128GB 가상 머신 여러 대로도 통합 테스트가 몇 시간씩 걸린다.
그래서 단위 테스트 밖에서는
빠르게 병합하고 높은 확신으로 시험할 수 없다고 했다.[^chris_money202]
PR 전에 에이전트가 모든 것을 검증한다는 첫 번째 층은
검증이 몇 분 안에 끝나는 스택에서만 싸다.

반대쪽 경험도 있다.
NorthSouthNorth는 자체 호스팅 러너에서
데이터베이스와 시드 파일까지 개발자 환경과 똑같이 갖춘
맞춤 GitHub Action으로 Codex 리뷰를 돌리며,
반나절 만에 구성했고 구독 요금 안에서 거의 공짜로 쓴다고 했다.[^NorthSouthNorth]
AI 리뷰어 하나를 붙이는 것은 작은 팀에게도 어렵지 않다.
어려운 것은 그 뒤의 위험 분류, 평가 세트, 되돌림 체계다.

규제의 문제도 남는다.
gaal_dornick은 작성자 한 사람만 개입해 병합할 수 있다는 구조가
모든 코드를 다른 사람이 적어도 한 명 리뷰해야 한다는 SOC 2 요건과
어떻게 양립하느냐고 물었다.[^gaal_dornick]
c0rruptbytes는 SOC 2가 사람의 변경에 대한 감사 가능성을 묻는 것이고
기계는 스스로 동작하는 시스템으로 볼 수도 있다고 추측했다.[^c0rruptbytes]
drdexebtjl은 상장하고 나면 감사인이
재무 데이터를 건드리는 모든 코드에
사람의 서명을 요구할 것이라고 했다.[^drdexebtjl]
규제 산업의 팀에게는 이 질문이 도입 여부를 가르는 첫 관문이 된다.
비용도 문제다.
rileymichael은 Claude Code 리뷰 제품이 처음에 리뷰 한 번에
15~25달러라고 안내했다가 문서에서 그 문구를 뺐다고 전했다.[^rileymichael]

### 스타일 지적을 버리는 필터는 줄 단위 리뷰가 잡던 것도 버린다

이 체계는 스타일, 진단, 정리에 관한 지적을 걸러 내고
리뷰어가 버그에 집중하게 한다.
그러나 사람이 줄 단위로 읽으며 잡던 것은 버그만이 아니었다.
HN의 dylanhouli는 줄 단위 리뷰를 멈출 수 없는 이유로
중복 코드, 불필요한 코드, 지나치게 복잡한 아키텍처를 들며
그것을 보고도 넘기는 것은 부주의라고 했다.[^dylanhouli]
이런 문제는 되돌림이나 장애로 드러나지 않으므로,
이 체계의 안전장치 지표에도 잡히지 않는다.

bpeng2000은 이 문제가 어떻게 쌓이는지 구체적으로 설명했다.
큰 코드베이스에서 AI는 새 기능마다 바퀴를 새로 만드는 경향이 있다.
기존 코드를 찾아 이해하고 일반화해 통합하면 기존 기능이 깨질 수 있고,
구현과 테스트에 노력과 토큰이 더 들기 때문이다.
사람 리뷰어도 이런 코드를 좋아한다.
깔끔하고 리뷰하기 쉽고 일을 해내기 때문이며,
특히 기존 코드베이스를 잘 모를 때 그렇다.
문제는 이런 바퀴가 쌓이고 얽힌다는 것이다.
상위 명세가 바뀌거나 여러 기능에 걸친 새 기능이 들어오면
그 바퀴를 모두 다시 봐야 하지만,
새 테스트가 모든 경로를 덮지 못해 대개 그냥 남는다.[^bpeng2000]
버그 중심의 리뷰어와 깨끗한 diff를 반기는 승인자는
둘 다 이 축적을 보지 못한다.

검증 단계도 원문만큼 믿음직하지 않다.
nathanqueme는 API 문서와 대조해
Claude Code의 작업을 확인하는 라이브러리를 만들고
테스트를 많이 쓰게 했지만,
Claude Code가 문서를 바꿔 말하며 어긋났고
자기 스모크 테스트는 통과하면서 실제 API에서는 실패했다고 전했다.[^nathanqueme]
에이전트가 스스로 만든 검증은 에이전트의 오해를 그대로 물려받을 수 있다.
출력을 보이라는 원칙은 강력하지만,
그 출력을 만드는 검사가 무엇을 확인하는지는 여전히 누군가 판단해야 한다.

### 사람의 승인이 형식으로만 남을 위험을 다루지 않는다

이 체계는 위험한 변경에 사람의 승인을 남긴다.
그러나 그 사람이 무엇을 근거로 승인하는지는 깊이 다루지 않는다.
HN의 mahogany는 이 점을 신랄하게 짚었다.
지난주 이후 PR 12개를 거쳐 열두 번 바뀐 “중요한” 코드의 diff를
사람이 본들 무슨 일이 일어나는지 알 리 없고,
결국 사람도 다른 승인자처럼 Claude에게 회귀가 없는지 확인하라고 시킨 뒤
깨끗하다는 답을 보고 승인을 누를 것이라는 것이다.
그는 그런 과정에서 사람이 무슨 목적으로 있는지 모르겠다고 했다.[^mahogany]

원문에도 이 위험을 막는 장치는 있다.
검사가 무엇을 놓칠지 말할 수 없다면
빠른 승인 대신 제대로 된 리뷰를 요청하라는 조언이다.
그러나 이것은 규범이지 측정이 아니다.
이 팀은 리뷰어의 잡음은 사람의 반응으로 정교하게 재면서도,
사람의 승인이 실제로 무엇을 잡았는지,
사람이 반려한 비율이 얼마인지는 밝히지 않는다.
사람의 승인이 실질적인 검사인지 형식인지 알 수 없다면,
위험 등급의 “1명”과 “2명”이 무엇을 보증하는지도 알 수 없다.

책임 규범의 비대칭도 같은 곳에서 생긴다.
squidlib은 AI가 코딩 시간을 줄여 주지만 책임은 100% 사람에게 남아,
생성에 든 시간에 비해
이해하고 고치는 데 불균형하게 많은 시간을 쓰게 된다고 했다.[^squidlib]
“병합한 사람이 책임진다”는 규범은
그 사람이 코드를 충분히 이해한다는 전제 위에 서 있는데,
이 체계는 바로 그 이해를 줄이는 방향으로 움직인다.
책임과 이해가 갈라지면 책임은 서명만 남는다.

### 변경의 기록은 쌓이지만 제품의 현재 모양을 지키는 장치는 약하다

원문의 AI 리뷰어는 diff를 저장소 전체와 PR이 밝힌 의도에 대조해 읽는다.
이 구조는 변경이 자기 문제를 푸는지, 시스템에 맞는지,
다른 것을 깨는지를 묻는다.
그러나 변경이 제품 전체가 지향하는 모양에 맞는지는
`CLAUDE.md`의 목표와 비목표 몇 줄로만 묻는다.
하루에 수많은 PR이 각자의 의도를 내걸고 병합되면
하나하나는 옳아도 합친 결과가 한 제품처럼 보이지 않을 수 있다.
그 판단은 사람에게 남겨 두었지만,
사람이 기댈 현재의 그림은 원문 어디에도 문서로 나오지 않는다.

앞에서 본 UI 불만은 이 공백이 밖으로 드러난 모습이다.
andrekandre는 고객이 익숙해진 작업 흐름의 큰 변화를 싫어한다고 했다.
기능이나 버튼, 메뉴 항목 하나를 더하는 것은 괜찮지만
배치를 자주 바꾸면 무작위처럼 느껴지고,
고객을 존중하지 않는다는 인상과 함께
일관된 제품 설계가 없다는 신호를 준다는 것이다.[^andrekandre]
_verandaguy는 하루에도 여러 번 쓰는 제품이
발밑에서 계속 바뀌기를 원하지 않는다며,
속도는 제품이 아니라고 했다.[^verandaguy]
Rapzid는 너무 빨리 움직이면 처음부터 제대로 만들 가능성이 줄어
설계가 계속 뒤집히고,
몇 주 만에 다섯 번째로 기능을 갈아엎는 일을
참아 줄 사용자는 많지 않다고 덧붙였다.[^Rapzid]
반대 평가도 있다.
enraged_camel은 지난 6개월 동안 UI가 크게 나아졌다고 했다.
새 기능은 눈에 띄게 두고 덜 쓰는 기능은 덜 드러내거나 없앴으며,
모든 제품이 겪는 진화가 이 속도에서 더 잘 보일 뿐이라는 것이다.[^enraged_camel]
같은 변화를 두고 평가가 이렇게 갈리는 데에는
어떤 변화가 의도된 방향인지 판단할 기준이
바깥에서 보이지 않는다는 이유도 있다.

코드를 현재의 유일한 출처로 삼는 방식에는 더 근본적인 약점이 있다.
원문은 Claude가 쓴 설명서가 오늘의 코드를 반영한다고 하지만,
코드에서 뽑은 설명은 코드가 하는 일을 말할 뿐
코드가 해야 하는 일을 말하지 않는다.
기준이 코드뿐이면 버그도 명세가 된다.
앞서 본 marcindulak의 사례가 그렇고,
chrisjj도 LLM에게 코드 해설을 쓰게 했더니
코드를 직접 확인하지 않았다면 믿었을 만큼
분명하고 틀린 지어낸 내용이 가득했다고 했다.[^chrisjj]
sadengineer22는 Anthropic에서 일하는 사람에게 들은 이야기라며,
장애 회고가 “내 Claude는 X라는데”와 “내 Claude는 Y라는데”의
대립으로 흐르기도 한다고 전했다.[^sadengineer22]
전해 들은 이야기라 확인할 수는 없지만,
현재를 정하는 기준 문서가 없을 때 어떤 일이 생기는지는 잘 보여 준다.

문서를 에이전트에게 맡기면 반대 방향의 문제도 생긴다.
현재를 담아야 할 문서가 과거의 퇴적층이 되는 것이다.
therealdrag0은 바이브 코딩 프로젝트의 설계 문서를 AI로 정리해
3만 단어, 약 50%를 덜어 냈다고 했다.
AI와 논의한 모든 것이 열 배 길이로 문서가 되고,
이후의 결정 하나하나가 다섯 곳에 기록된다는 것이다.[^therealdrag0]
같은 결정이 다섯 곳에 있으면
그중 하나만 고쳐져도 문서끼리 모순된다.
bulbar는 Claude가 2년 전에 고친 버그처럼
이제는 상관없는 내용을 코드 주석에 남긴다고 했고,[^bulbar]
elondaits는 맥락상 당연한 것을 귀한 깨달음처럼
README와 주석과 커밋 메시지에 모두 넣는다고 했다.[^elondaits]
meheleventyone은 Claude가 자기 맥락을 암묵적인 가정으로
문서에 흘려 넣는다고 지적했다.[^meheleventyone]
PR 설명의 문제, 곧 그 시점의 사정이 현재의 사실처럼 남는 문제가
현재를 담아야 할 문서 안에서 되풀이되는 셈이다.

원문의 위험 등급도 이 문제를 키울 수 있다.
문서는 문구, 사내 전용 기능과 함께 낮음 등급에 들어 있어
자동 리뷰와 보안 검사가 통과하면 사람의 승인이 필요 없다.
koolba는 LLM이 쓴 문서를 아무도 읽지 않는다니 제정신이 아니라고 했고,[^koolba]
brational은 다른 에이전트를 위한 문서이니 당연하다고 비꼬았다.[^brational]
문구 수정과 제품의 현재 모양을 정하는 스펙 문서는 위험이 다르다.
에이전트가 다음 변경의 기준으로 읽는 문서라면
그 문서의 변경은 코드 변경보다 영향 범위가 넓다.

## 인사이트

### 코드 작성이 생산 라인에 오르면 리뷰는 공정 관리가 된다

HN의 cadamsdotcom은 반복적인 부분이 코드를 출시하는 일에서
코드를 만드는 일로 옮겨 가고 있다고 했다.
소프트웨어 제작이 산업 공정에 가까워지고,
장인의 일은 만드는 것이 필요한 것과 맞는지 맞추는 일과
제작 공정 자체를 만들고 조율하는 일로 옮겨 간다는 것이다.[^cadamsdotcom]
Claude Code 팀의 체계는 이 관점으로 읽으면 잘 맞는다.
평가 세트는 품질 기준이고, 잡음 측정은 검사 장비의 오검출률이며,
라운드 상한은 공정의 사이클 타임 관리다.

그러나 공장의 비유에는 분명한 한계가 있다.
fipar는 제조 품질 관리에서는 시스템이 극소수 종류를 아주 많이 찍어 내므로
표본 검사가 통하지만, 코드는 모든 산출물이 서로 다르다고 지적했다.[^fipar]
제조 공정의 통계적 품질 관리는 산출물의 분산이 작다는 전제에 기댄다.
코드에는 그 전제가 없으므로,
이 체계가 통계적 지표로 품질을 관리하는 방식은
변경 하나하나의 특이성을 놓칠 수 있다.

이 긴장은 앞으로 더 커진다.
리뷰를 공정 관리로 다룰수록 개별 변경은 평균의 일부가 되고,
특이한 변경은 분류기와 평가 세트의 바깥에서 들어온다.
위험 등급을 두 번째 분류기로 보완하고
일부 경로를 사람에게 고정한 것은 그 바깥을 인정한 장치다.
공정 관리를 들여오는 팀은 공정이 다루지 못하는 변경을 알아보는 사람을
어디에 둘지 함께 정해야 한다.

### 승인의 단위가 사람에서 커밋과 증거로 바뀐다

이 글의 규칙 가운데 오래 남을 것은 승인이 특정 커밋에만 유효하다는 점이다.
에이전트가 승인 뒤에 푸시하면 승인은 무효가 되고,
사람이 손으로 충돌을 해결한 병합도 마찬가지다.
에이전트가 PR을 계속 고치는 환경에서는
“승인된 PR”이라는 개념이 더는 성립하지 않는다.

앞으로 코드 리뷰 도구의 기본 단위는
PR이 아니라 커밋과 그 커밋에 딸린 증거가 될 것이다.
어떤 검사가 어떤 커밋을 통과시켰는지,
누가 어떤 증거를 읽고 서명했는지,
그 이후 무엇이 바뀌었는지를 추적하는 것이 승인 버튼 하나보다 중요해진다.
SOC 2 같은 감사 요건과의 충돌도 이 방향에서 풀릴 가능성이 크다.
사람이 읽었다는 기록 대신,
어떤 검사와 어떤 사람이 어떤 커밋을 보증했는지의 기록이 감사의 대상이 된다.

### 리뷰어의 민감도와 출처는 작성자에 따라 달라야 한다

사람은 사소한 지적을 무시할 수 있지만 에이전트는 성실하게 고친다.
이 비대칭은 AI 리뷰어를 튜닝하는 기준을 바꾼다.
사람이 작성자일 때는 조금 시끄러워도 많이 잡는 리뷰어가 나을 수 있지만,
에이전트가 작성자일 때는
잡음 하나가 커밋 하나, 리뷰 라운드 하나로 증폭된다.
작성자가 사람인지 에이전트인지에 따라 리뷰어의 민감도를 다르게 두는 설정이
곧 필요해질 것이다.
같은 리뷰어를 양쪽에 똑같이 쓰면 에이전트 쪽에서 비용이 조용히 쌓인다.

리뷰어의 출처도 변수가 된다.
HN의 walthamstow는
코드를 작성한 모델과 다른 연구소의 모델로 리뷰하게 한다고 했다.[^walthamstow]
같은 모델 계열이 쓰고 리뷰하면 같은 맹점을 공유할 수 있다.
Claude Code 팀의 체계는 쓰는 쪽도 리뷰하는 쪽도 Claude이며,
투표하는 검증 에이전트도 같은 계열이다.
에이전트 리뷰에서 다양성은
사람 리뷰에서 여러 리뷰어를 두던 이유와 같은 역할을 한다.

### 리뷰의 병목이 “만들어야 하는가”로 앞당겨진다

에이전트 덕에 시작이 싸지면서
병합하지 말아야 할 작업도 늘었다고 저자들은 말한다.
코드 품질 검사가 자동화될수록 남는 사람의 일은
이 변경이 애초에 필요한지를 판단하는 것이다.
그 판단은 PR이 열린 뒤가 아니라 작업이 시작되기 전,
또는 스레드 초반에 내려져야 비용이 적다.

이는 코드 리뷰가 설계 리뷰와 제품 결정 쪽으로 앞당겨진다는 뜻이다.
에이전트가 PR을 쉽게 만들수록 팀이 투자해야 할 곳은
PR을 더 잘 읽는 능력이 아니라
PR이 열리기 전에 방향을 정하는 의사결정 구조다.
그런데 원문에서 그 구조는 가장 비공식적인 부분이다.
채널에서 누군가 이전 결정을 가리킨다고 하지만,
그 결정이 어디에 기록되는지는 말하지 않는다.
정신 모델을 가진 사람이 없다고 한 체계에서 결정의 기록이 대화뿐이라면,
그 결정을 기억하는 사람이 떠날 때 함께 사라진다.
리뷰의 병목이 방향 결정으로 옮겨 가는 만큼,
결정 기록은 코드 리뷰가 하던 맥락 보존의 일을 물려받아야 한다.

### 현재를 담는 문서는 변경 기록과 나누고, 리뷰의 대상으로 둔다

원문과 HN 반응을 합치면,
장기 스펙의 역할을 에이전트 시대에 맞게 유지하는 방법이 몇 가지 보인다.
아래는 원문이 직접 권하는 것과 이 문서가 넓혀 적용한 것을 구분해 적는다.

첫째, 두 종류의 문서를 나눈다.
하나는 덮어쓰는 문서다.
제품이 지금 어떻게 동작하는지, 아키텍처의 경계가 어디인지,
무엇을 하지 않기로 했는지를 적고, 늘 현재 시제로 고친다.
다른 하나는 쌓이는 기록이다.
PR 설명과 커밋 메시지, 결정 기록이 여기에 들어가며,
왜 그렇게 바뀌었는지를 그 시점의 사정과 함께 남긴다.
쌓이는 기록은 현재를 묻는 질문에 답으로 쓰지 않는다.
결정 기록을 남긴다면
뒤의 결정이 앞의 결정을 대체했다고 표시해,
모순이 기록 안에서 풀리게 한다.
원문의 `CLAUDE.md`는 앞의 것이고 PR 설명은 뒤의 것이다.
이 구분을 기능 명세와 설계 문서까지 넓히는 것은 이 문서의 제안이다.

둘째, 동작을 바꾸는 PR이 현재 문서도 함께 고치게 한다.
원문의 리뷰어는 `CLAUDE.md`의 한 줄을 낡게 만드는 변경을 지적한다.
같은 규칙을 기능 명세에 적용하면,
리뷰어는 diff가 명세와 어긋나는지,
명세를 고쳐야 하는데 고치지 않았는지를 함께 본다.
`REVIEW.md`에 문서의 실패를 “거짓말한다”로 적으라는 원문의 조언이
이 검사의 출발점이 된다.
a3nz3g처럼 사용자 경험이 바뀌는 변경은
사람에게 알리게 하면,
현재 문서가 바뀌는 순간이 곧 사람이 제품의 모양을 판단하는 순간이 된다.[^a3nz3g]

셋째, 현재 문서의 변경은 낮은 위험 등급에서 뺀다.
원문은 CODEOWNERS와 브랜치 보호로 인증, 결제, CI 워크플로가
항상 사람을 거치게 하라고 권한다.
에이전트가 기준으로 읽는 스펙 문서도 같은 경로에 두는 것이 맞다.
제품의 모양을 정하는 판단은 원문 스스로 사람의 몫이라고 했으므로,
그 판단이 기록되는 문서의 변경에도 사람이 서명해야 앞뒤가 맞는다.

넷째, 기준을 실행할 수 있는 형태로 옮길 수 있는 만큼 옮긴다.
테스트, 디자인과 비교하는 스크린샷, 린트 규칙은
낡으면 실패하므로 스스로 갱신을 요구한다.
hnedeotes의 경험처럼 테스트는 코드의 의미를 굳히고,[^hnedeotes]
cadamsdotcom의 방식처럼
하네스가 그 테스트를 완료 조건으로 강제할 수 있다.[^cadamsdotcom-tdd]
다만 무엇을 테스트할지는 여전히 산문으로 된 현재 문서가 정한다.

다섯째, 문서와 코드를 정기적으로 대조한다.
원문의 리뷰 에이전트는 밤마다 기존 코드를 훑어 오래된 버그를 찾는다.
같은 순회를 문서에 돌리면 낡은 문장을 찾을 수 있다.
jt2190은 개발자들이 코드를 읽지 않고도 안다고 여기는 것이 문제라며,
AI가 여러 문서를 소스와 대조해 사실을 확인하게 하면
크게 도움이 될 것이라고 했다.[^jt2190]
suttontom은 LLM이 쓴 설명서를 다른 세션의 다른 LLM에게 확인시키라고 했다.
맞는 정보를 얻을 뿐 아니라,
그럴듯하고 자신 있는 답에 자기가 얼마나 쉽게 속는지도
알게 된다는 것이다.[^suttontom]
작성한 모델과 다른 모델로 대조하라는 walthamstow의 조언도
문서 검증에 그대로 쓸 수 있다.[^walthamstow]

여섯째, 짧게 쓰고 한 곳에만 쓴다.
원문이 `CLAUDE.md`를 짧게 두고 다른 문서를 가리키라고 한 것은
비용 때문이기도 하지만, 같은 사실을 한 곳에만 두는 효과도 있다.
therealdrag0이 겪은 것처럼 결정 하나가 다섯 곳에 기록되면,[^therealdrag0]
현재를 담으려던 문서가 모순의 원천이 된다.
에이전트에게 문서를 고치게 할 때는 내용을 더하기 전에
그 사실이 이미 어디에 있는지 찾아 그곳을 고치게 해야 한다.

이 대응법이 필요 없는 조건도 분명하다.
원문의 팀처럼 개발자가 곧 사용자이고,
사내 사용이 매일 제품의 모양을 확인해 주며,
되돌림이 몇 분이면 끝나는 환경에서는
대화와 사용이 스펙 문서의 일을 상당 부분 대신한다.
반대로 사용자와 개발자가 다르거나,
여러 팀이 한 제품을 나눠 만들거나,
규제나 계약이 동작을 고정하는 환경이라면
현재를 담는 문서 없이 PR 설명만으로 제품의 모양을 지킬 수는 없다.
지금 우리 팀의 제품이 어떻게 동작해야 하는지를
코드와 PR을 뒤지지 않고 한 문서에서 답할 수 없다면,
그 문서를 만드는 일이 리뷰 자동화보다 먼저다.
