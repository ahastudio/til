# Claude Code 팀은 코드 리뷰를 어떻게 하는가: 읽기는 기계에게, 결정은 사람에게

원문: [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)

HN 토론: <https://news.ycombinator.com/item?id=50122951> (273점, 255개 댓글)

## 요약

Addy Osmani, Morgan Westlee Lunt, Qing Wang은 2026년 10월 15일,
Claude Code 팀의 코드 리뷰 흐름을 공개했다.
Claude Code 코드의 약 90%를 Claude가 쓰는 상황에서,
생산하는 만큼의 코드를 어떻게 리뷰하느냐는 질문에 대한 답이다.
6월부터 9월 사이 Claude Code 저장소에 병합된 PR은 두 배 넘게 늘었지만,
되돌려야 했던 PR의 비율은 40% 넘게 줄었다.
리뷰를 없앤 것이 아니라 읽기의 대부분을 기계로 옮기고,
사람의 시간과 주의를 아끼며, 실수를 빠르고 쉽게 되돌리는 데 투자했다는 것이다.

### 리뷰의 목적을 다시 정하다

Anthropic 모노레포에 하루 들어오는 변경은 5월 약 2,500개였다가
9월에는 3만 개를 넘었다.
이 속도에서 한 줄씩 읽는 리뷰는 거의 불가능하다.
저자들은 코드 리뷰가 두 가지 일을 한다고 본다.
출시 전에 문제를 찾아 고치는 일과,
팀 전체에 코드베이스에 대한 맥락을 퍼뜨리는 일이다.
그리고 “사람이 코드를 읽었는가”는
“이 변경에서 무엇이 잘못될 수 있고,
자동이든 사람이든 어떤 검사가 그것을 잡아야 하는가”를
부정확하게 대신하는 지표라고 말한다.

리뷰의 시점도 바뀌었다.
예전에는 코드를 쓰고 PR을 열고 동료를 기다리는 길 끝의 관문이었다면,
이제는 글을 쓰는 동안 계속 작동하는 맞춤법 검사에 가깝다.
대부분의 변경은 사람이 보기 전에 Claude가 적어도 한 번 리뷰하고 고친다.

### 희소한 자원은 사람의 시간이다

목표는 CLI, 데스크톱과 웹, 모바일 앱을 아우르는 Claude Code 저장소의 PR 대부분이
작성자를 포함해 많아야 한 사람의 개입으로 병합되면서도,
되돌림과 장애가 늘지 않는 것이다.
사람의 시간은 PR당 사람의 승인 수(중앙값과 95번째 백분위), 사람의 댓글,
PR이 사람을 기다린 시간으로 잰다.
되돌림과 장애 비율은 안전장치다.
그 수치가 오르면 사람의 시간을 아낀 것이 아니라 다른 곳으로 옮긴 것일 뿐이다.

### 일곱 겹의 검사

| 단계                       | 내용                                                                             |
| -------------------------- | -------------------------------------------------------------------------------- |
| PR 전 검증                 | Claude가 테스트, 빌드, 린터를 돌리고 다른 에이전트가 새 컨텍스트에서 diff를 리뷰 |
| AI 리뷰                    | 여러 에이전트가 병렬로 버그를 찾고, 검증 에이전트가 투표해 살아남은 것만 게시    |
| 보안 리뷰                  | 별도 자동 리뷰, 열린 지적이 있으면 병합 불가                                     |
| 필수 CI                    | 린트, 타입, 플랫폼별 테스트, 빌드와 패키징                                       |
| 위험 기반 승인             | 분류기가 변경의 위험 등급을 정해 사람 0명, 1명, 2명 중 하나를 요구               |
| 병합 큐, 플래그, 단계 출시 | 최신 main에 다시 검사, 사내 사용 먼저, latest 채널 뒤에 stable 채널              |
| 빠른 감지와 되돌림         | 플래그 끄기, 되돌림, 주간 온콜, 장애 리뷰                                        |

PR 전 검증에서는 Claude에게 실행할 수 있는 것을 주고
“다 됐다”는 말 대신 출력을 보이게 한다.
Boris Cherny는 Claude가 자기 작업을 검증할 방법을 주는 것이
좋은 결과를 얻는 데 아마 가장 중요하며, 최종 결과를 2~3배 낫게 한다고 추정했다.
자동 리뷰어가 같은 지적을 반복하면 근원에서 고친다.
스킬, 린트 규칙, 또는 `CLAUDE.md`와 `REVIEW.md` 같은 지시 파일이다.
`REVIEW.md`는 코드 소유자가 쓰며, 그 저장소에서 실패가 어떤 모습인지
(문서라면 “거짓말한다”, 설정이라면 “잘못 라우팅한다”) 적고,
사소한 지적에 상한을 두고,
이름만 보고 짐작하지 말고 파일과 줄을 근거로 대라고 요구한다.

AI 리뷰 연구 프리뷰를 내놓았을 때 의미 있는 리뷰 댓글을 받은 사내 PR 비율은
16%에서 54%로 올랐다.
1,000줄이 넘는 PR은 대부분 지적을 받고, 작은 PR은 대부분 깨끗하게 돌아온다.
지적은 Important, Nit, Pre-existing으로 태그되어,
PR이 만든 것이 아닌 버그가 작성자 탓처럼 보이지 않게 한다.
모든 지적에는 답해야 하며, 고치거나 이유를 달아 스레드를 닫아야 한다.

위험 등급은 다음과 같다.

| 위험 | 예                                                   | 사람 승인 |
| ---- | ---------------------------------------------------- | --------- |
| 낮음 | 문서, 문구, 사내 전용 기능, 플래그 뒤의 추가 변경    | 필요 없음 |
| 중간 | 일반 제품 변경, 캐시, 자동 업데이트, 시스템 프롬프트 | 1명       |
| 높음 | 가장 위험한 코드와 항상 두 사람이 필요한 일부 경로   | 2명       |

등급은 작성자가 아니라 변경이 정한다.
한 분류기가 등급을 고르고, 다른 분류기가 등급과 상관없이
이 변경에 사람이 더 필요한지 묻는다.
가벼운 경로는 신뢰 목록에 있는 작성자에게만 열리고,
에이전트의 승인은 사람의 승인으로 치지 않는다.
에이전트가 쓴 PR에서는 에이전트를 지휘한 사람이 필수 리뷰어 중 하나가 된다.
승인은 특정 커밋에 대해서만 유효해서,
에이전트가 새로 푸시하거나 사람이 손으로 충돌을 해결하면 다시 승인해야 한다.

### 리뷰어를 개선하는 고리

과거 장애를 일으킨 PR을 모아,
그 코드를 아는 엔지니어가 버그와 위치를 확인한 평가 세트를 만들었다.
리뷰어는 이 세트로 매일 평가되고,
리뷰어의 프롬프트, 도구,
모델을 바꿀 때마다 점수가 오른 경우에만 변경을 유지한다.
잡음은 사람들이 댓글에 어떻게 반응했는지로 잰다.
고쳤는지, 틀렸다고 했는지, 의도된 동작이라고 했는지,
중요하지 않다고 했는지를 분류하고,
문제가 없는 PR에 리뷰어를 실행해
해로운 수정을 유도할 지적을 얼마나 하는지도 센다.
작성자가 에이전트라면 잡음의 비용이 더 크다.
사람은 사소한 지적을 몇 초 만에 넘기지만,
에이전트는 그것을 고치고 또 한 번 리뷰를 부른다.

리뷰는 수렴해야 한다.
한 CLI PR은 작성자가 멈추기 전까지 밤사이 50번 넘게 리뷰와 수정을 오갔다.
리뷰어가 계속 지적한 것에 `git blame`을 실행해 보니 약 59%가
리뷰어의 첫 번째 패스 때부터 있던 코드였다.
새 버그를 찾은 것이 아니라
라운드마다 오래된 버그를 몇 개씩 더 찾아낸 셈이다.
팀은 세 라운드 뒤에는 접근 방식을 다시 생각하라고 요청하는 상한,
처음 몇 번 뒤에는 새 diff만 보는 재리뷰,
한 줄이 아니라 버그의 부류를 지적하기, 이미 단 지적을 반복하지 않기를 도입했다.

| 지표                         | 전   | 후   |
| ---------------------------- | ---- | ---- |
| 한 번의 리뷰와 수정으로 통과 | 65%  | 78%  |
| 다섯 라운드 이상 필요        | 8.9% | 1.5% |
| 통과까지 평균 리뷰 횟수      | 2.08 | 1.32 |

### 사람이 남는 자리와 맥락 공유

사람의 일은 모든 diff를 읽는 것에서 기계가 못하는 결정으로 옮겨 갔다.
이것을 만들어야 하는가, 결제와 자동 업데이트와 CI 워크플로 같은 위험한 코드,
다른 사람이 따라 할 패턴을 정하는 아키텍처,
테스트 출력과 실행한 명령과 스크린샷 같은 증거 읽기,
그리고 누가 작성했든 출시되는 모든 변경에 대한 책임이다.

리뷰의 두 번째 일인 맥락 공유에는 공식 절차가 없다.
팀에서 Claude Code 전체의 정신 모델을 가진 사람은 없고,
필요하다고 생각하지도 않는다.
어떤 부분을 이해하고 싶으면 Claude에게 그 부분만의 설명서를 쓰게 하고,
어떤 이는 그 부분을 시각화해
자기에게 맞는 방식으로 가르쳐 주는 작은 아티팩트를 만들게 한다.
한 줄짜리 문구 수정을 읽는 것보다
곧 바꿀 모듈의 설명서를 읽는 것이 훨씬 많은 것을 가르쳐 준다는 판단이다.

팀 규범은 “병합한 사람이 책임진다”이다.
작은 변경, 되돌릴 수 있는 구조, 위험 반경에 따른 기준, 빠른 회귀 발견,
비난 없는 장애 리뷰가 이 규범을 뒷받침한다.
에이전트 덕에 시작이 싸졌으니 병합하지 말아야 할 작업도 생기는데,
코드를 빨리 썼으니 PR을 닫아도 손실처럼 느껴지지 않는다.
요령은 다른 방향을 제안할 때
완성된 PR에 차단 댓글을 달지 말고 스레드 초반에 꺼내는 것이다.

저자들은 되돌림과 장애 수치가 움직일 때
승인 기준을 자동으로 강화하는 서킷 브레이커(circuit breaker)가 아직 없으며,
엔지니어들은 사람 없이 병합되는 코드가 더 늘기 전에
그것이 갖춰지기를 원한다고 밝힌다.

## 분석

### “사람이 읽었는가”를 지표에서 내린 것이 핵심 전환이다

이 글의 가장 중요한 문장은,
사람이 읽었느냐는 기준이
무엇이 잘못될 수 있고 어떤 검사가 그것을 잡아야 하느냐를
부정확하게 대신하는 지표라는 말이다.
전통적 코드 리뷰는 승인 버튼을 누른 사람이 있다는 사실로 품질을 보증했다.
Claude Code 팀은 그 보증을 위험 등급, 검사 계층, 되돌림 비율로 분해했다.

이 분해 덕분에 리뷰는 측정 가능한 공학 문제가 된다.
사람의 시간은 승인 수와 대기 시간으로, 품질은 되돌림과 장애 비율로 잰다.
둘을 함께 보는 것은 한쪽만 최적화하면 비용이 다른 쪽으로 옮겨 갈 뿐이라는
인식에서 나온다.

### 에이전트 리뷰어의 문제는 재현율이 아니라 수렴이다

AI 리뷰를 처음 도입하는 팀은 대개 더 많은 버그를 잡는 데 집중한다.
이 글이 드러낸 것은 그 다음 단계의 문제다.
에이전트 작성자와 에이전트 리뷰어는 서로를 끝없이 바쁘게 만들 수 있고,
한 PR이 밤새 50번 넘게 오간 사례가 그것을 보여 준다.
59%가 첫 패스 때부터 있던 코드였다는 분석은
리뷰어가 한 번에 다 말하지 않고 조금씩 나눠 내놓는다는 뜻이다.

라운드 상한, diff 전용 재리뷰, 버그 부류 지적, 반복 금지는
모두 리뷰어가 한 번에 완결된 판단을 하도록 압박하는 장치다.
그 결과 한 번에 통과하는 비율이 65%에서 78%로,
다섯 라운드 이상 걸리는 비율이 8.9%에서 1.5%로 바뀌었다.

### 장애를 평가 세트로 바꾸는 고리가 체계 전체를 뒷받침한다

이 체계에서 다른 팀이 가장 가져다 쓰기 쉬운 장치는 장애 기반 평가 세트다.
장애를 일으킨 PR을 모아 전문가가 확인하고,
리뷰어를 바꿀 때마다 그 세트 전체로 다시 채점한다.
리뷰어의 품질이 감이 아니라 과거 실제 실패를 얼마나 잡는지로 정해지고,
장애가 날 때마다 평가 세트가 자란다.

장애 리뷰가 “어느 층이 이것을 잡았어야 했는가”를 묻는 것과 맞물려,
실패 하나가 검사 계층 하나를 강화하는 데 바로 쓰인다.
리뷰가 놓친 것을 모델 탓으로 돌리지 않고
모델 앞에 무엇이 없었는지를 물어 `CLAUDE.md`, 스킬,
새 검사로 옮긴다는 원칙도 같은 고리다.

## 비평

### 성과 지표가 원인을 분리하지 않는다

병합 PR이 두 배 넘게 늘고 되돌림 비율이 40% 넘게 줄었다는 수치는 인상적이다.
그러나 같은 기간 모델이 바뀌었는지, 팀 구성과 작업 종류가 바뀌었는지,
작은 PR의 비중이 늘었는지는 말하지 않는다.
되돌림 “비율”이 줄어도 PR 수가 두 배라면
되돌림의 절대 건수는 크게 줄지 않았을 수 있다.

수렴 개선 표도 마찬가지다.
라운드 상한을 두면 다섯 라운드 이상 걸리는 비율이 줄어드는 것은 정의상 당연하다.
중요한 것은 상한 때문에 놓친 버그가 늘었는지인데,
그 수치는 공개되지 않았다.
저자들이 재현율과 통과 라운드를 함께 본다고 했으니
그 재현율 변화도 함께 보여 주었어야 했다.

HN의 ativzzz는 되돌림과 장애를 측정하다 그것이 목표가 되었으니
굿하트의 법칙이 작동하는 것 아니냐고 물었고,[^ativzzz]
senderista는 되돌림과 장애 비율만 보면 나쁜 아키텍처 결정이 쌓여 생기는
누적 복잡도를 놓친다고 지적했다.[^senderista]
crooked-v는 이슈 5,000개가 쌓인 Claude Code GitHub 저장소를 들며
그중 3분의 1쯤은 예전 동작이 되돌아간 회귀일 것이라고 했다.[^crooked-v]
되돌릴 만큼 크지는 않은 회귀는 되돌림 비율에 잡히지 않는다.

### 맥락 공유를 설명서로 대신할 수 있다는 가정은 검증되지 않았다

글은 누구도 Claude Code 전체의 정신 모델을 가질 필요가 없다고 말한다.
필요할 때 Claude에게 그 부분의 설명서를 쓰게 하면 된다는 것이다.
그러나 코드 리뷰를 통한 맥락 공유의 가치는
필요할 때 찾아 읽는 지식이 아니라,
자기 일과 관계없어 보이던 변경을 우연히 보며 쌓이는 감각에 있었다.

무엇을 물어야 할지 아는 사람에게 설명서는 훌륭하지만,
무엇을 모르는지 모르는 사람에게는 질문할 계기가 없다.
저자들도 이 부분에는 공식 절차가 없다고 인정한다.
열린 Slack 채널이 그 공백을 일부 메운다고 하지만,
이것이 장기적으로 아키텍처 판단의 질에 어떤 영향을 주는지는
아직 측정된 바가 없다.

HN의 RGS1811은
손으로 익힌 이해가 수동 코드 리뷰 능력의 직접적인 전제가 아니냐며,
Claude가 쓴 설명서로는 복잡한 diff를 자신 있게 평가할 수준에 이르지 못하고,
그 diff를 이미 리뷰하고 승인한 바로 그 시스템에서
사전 지식을 얻게 된다고 했다.[^RGS1811]
jazzyjackson은 코드가 아니라 코드가 무엇을 하는지 알고 바꿀 줄 아는 사람이
자산이라던 말을 떠올리며,
설계와 리뷰 역량을 빠르다는 이유로 외주로 넘기고 있다고 했다.[^jazzyjackson]

### 이 체계의 전제 조건은 대부분의 팀에게 없다

글은 마지막에 대부분의 구성 요소가 오늘 이미 있다며 도입 방법을 안내한다.
그러나 이 체계를 뒷받침하는 것은 도구보다 환경이다.
사내 직원이 먼저 쓰며 회귀를 잡아 주는 대규모 내부 사용,
몇 분 안에 끌 수 있는 플래그 체계, 주간 온콜,
장애 평가 세트를 만들 만한 장애 이력,
그리고 자기 제품을 리뷰어로 쓰는 회사라는 조건이다.

특히 위험 분류기와 장애 기반 평가 세트는
상당한 양의 과거 데이터와 그것을 검증할 전문가의 시간을 전제로 한다.
작은 팀이 “사람 승인 없이 병합”을 따라 하면서 이 안전망을 갖추지 못하면,
절약한 리뷰 시간이 장애 대응 시간으로 옮겨 갈 뿐이다.
저자들이 경고한 바로 그 상황이다.

HN의 avinoth는 이 글을 Google 인프라 블로그에 빗대며,
작은 팀이 “Google이 그렇게 한다”는 이유로 따라 하다 쓴 교훈을 얻었듯
토큰을 사실상 무제한으로 쓰는 연구소의 방식을
그대로 따라 해서는 안 된다고 했다.[^avinoth]
gaal_dornick은 작성자 한 사람만 개입해 병합할 수 있다는 구조가
모든 코드를 다른 사람이 적어도 한 명 리뷰해야 한다는 SOC 2 요건과
어떻게 양립하느냐고 물었다.[^gaal_dornick]
c0rruptbytes는 SOC 2가 사람의 변경에 대한 감사 가능성을 묻는 것이고
기계는 스스로 동작하는 시스템으로 볼 수도 있다고 추측했다.[^c0rruptbytes]
규제 산업의 팀에게는 이 질문이 도입 여부를 가르는 첫 관문이 된다.
rileymichael은 Claude Code 리뷰 제품이 처음에 리뷰 한 번에
15~25달러라고 안내했다가
문서에서 그 문구를 뺐다고 전했다.[^rileymichael]

## 인사이트

### 승인의 단위가 사람에서 커밋으로 바뀐다

이 글의 규칙 가운데 눈에 띄는 것은 승인이 특정 커밋에만 유효하다는 점이다.
에이전트가 사람의 승인 뒤에 푸시하면 승인은 무효가 된다.
사람이 손으로 충돌을 해결한 병합도 마찬가지다.
이는 에이전트가 PR을 계속 고치는 환경에서
“승인된 PR”이라는 개념이 더는 성립하지 않는다는 인식이다.

앞으로 코드 리뷰 도구의 기본 단위는
PR이 아니라 커밋과 그 커밋에 딸린 증거가 될 것이다.
어떤 검사가 어떤 커밋을 통과시켰는지,
그리고 그 이후 무엇이 바뀌었는지를 추적하는 것이
승인 버튼 하나보다 중요해진다.

### 리뷰어 잡음은 사람보다 에이전트에게 더 비싸다

사람은 사소한 지적을 무시할 수 있지만 에이전트는 성실하게 고친다.
이 비대칭은 AI 리뷰어를 튜닝하는 기준을 바꾼다.
사람이 작성자일 때는 조금 시끄러워도 많이 잡는 리뷰어가 나을 수 있지만,
에이전트가 작성자일 때는 잡음 하나가 커밋 하나, 리뷰 라운드 하나로 증폭된다.

작성자가 사람인지 에이전트인지에 따라 리뷰어의 민감도를 다르게 두는 설정이
곧 필요해질 것이다.
같은 리뷰어를 양쪽에 똑같이 쓰면, 에이전트 쪽에서 비용이 조용히 쌓인다.

HN의 walthamstow는
코드를 작성한 모델과 다른 연구소의 모델로 리뷰하게 한다고 했다.[^walthamstow]
같은 모델 계열이 쓰고 리뷰하면 같은 맹점을 공유할 수 있으니,
리뷰어의 민감도뿐 아니라 리뷰어의 출처를 다르게 두는 것도 선택지다.

### 리뷰 병목이 “만들어야 하는가”로 옮겨 간다

에이전트 덕에 시작이 싸지면서 병합하지 말아야 할 작업도 늘었다고
저자들은 말한다.
코드 품질 검사가 자동화될수록,
남는 사람의 일은 이 변경이 애초에 필요한지를 판단하는 것이다.
그 판단은 PR이 열린 뒤가 아니라 작업이 시작되기 전,
또는 스레드 초반에 내려져야 비용이 적다.

이는 코드 리뷰가 설계 리뷰와 제품 결정 쪽으로 앞당겨진다는 뜻이다.
에이전트가 PR을 쉽게 만들수록, 팀이 투자해야 할 곳은
PR을 더 잘 읽는 능력이 아니라 PR이 열리기 전에 방향을 정하는 의사결정 구조다.
