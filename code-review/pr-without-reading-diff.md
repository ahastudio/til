# Diff를 읽지 않는 PR 머지 사례

원문: [어느 순간부터 저는 PR의 Diff를 읽지 않고 머지합니다](https://yozm.wishket.com/magazine/detail/4051/)

## 요약

요즘IT에 2026년 11월 26일 실린 글이다.
필자 핸디는 프론트엔드 개발자이고, PR의 Diff를 한 줄씩 읽지 않고
머지하게 된 과정을 정리했다.
글의 중심은 질문의 교체다.
“이 코드가 맞는지 내가 읽어서 알 수 있는가”가 아니라
“틀렸다면 시스템이 알려주는가”를 묻는다는 것이다.

글의 흐름은 이렇다.
필자는 2020년 초 신입 때 띄어쓰기 한 칸을 사람이 리뷰로 잡는 방식에 부딪혀
팀을 옮겼다고 회상한다.
Prettier나 lint가 없던 환경에서 스타일을 사람이 지적하는 일이었다.
2026년 9월에 이직 1년을 맞은 필자는 10명 규모 프론트엔드팀에서
자신이 PR 리뷰의 병목이었다고 돌아본다.
AI가 코드를 많이 쓰자 AI에게 리뷰를 맡기는 분위기가 퍼졌고,
사내에서는 받아들이자는 쪽과 사람 리뷰가 필요하다는 쪽의 논쟁이 있었으나
결론은 나지 않았다고 한다.

계기는 Cursor와 xAI에서 에이전트 환경을 만드는 Lauren Tan의 발표 영상이다.
필자는 발표의 요지를, 사람이 모든 줄을 읽는 방식은 확장되지 않으니
검증 장치를 겹겹이 쌓아 에이전트가 기본값으로 올바른 코드를 쓰게 하라는 것으로
옮긴다.
그 뒤 필자가 쌓은 검증 장치는 네 가지다.

| 장치           | 글이 설명하는 내용                                                           |
| -------------- | ---------------------------------------------------------------------------- |
| 테스트         | 구현보다 테스트를 먼저 보고, 특히 `it` 줄(요구사항 명세)에 집중한다          |
| 타입과 린트    | 커밋과 푸시 단계에서 Oxlint, 포맷터, `tsc --noEmit`, 빌드, 테스트를 강제한다 |
| 작은 PR        | PR 제목을 한 문장으로 설명할 수 없으면 쪼갠다                                |
| 화면 직접 확인 | 어드민의 플로우 페이지에서 Figma, 모바일 웹, 앱 화면을 카드로 나란히 본다    |

필자가 든 수치는 다음과 같다.
사이드 프로젝트에 Vitest 단위·통합 테스트 300개 이상과
Playwright E2E 스펙 16개가 있고, 매일 새벽 개발 환경에 스모크 테스트가 돈다.
2026년 10월 26일부터 11월 1일까지 한 주에 PR 136개가 열리고 134개가
머지되었으며 같은 기간 커밋은 158개였다.
회사에서는 타입스크립트 마이그레이션으로 Jira 티켓 48개를 만들어
Diff도 스크린샷도 보지 않고 머지했다고 한다.

필자는 완전히 자동화된 것은 아니라고 인정한다.
테스트는 통과했지만 화면이 이상했던 일이 여러 번 있었다.
특정 조건에서만 보이는 UI를 재현하지 못해 통과시킨 경우와
사람이 보면 바로 잘못이 보이는데 AI는 통과시킨 경우다.
그래서 데이터가 없으면 API 스펙으로 Mock 데이터를 만들어 검증하게 하고,
PR에 Before/After 스크린샷을 붙이게 했다.
필자는 처음부터 Diff를 보지 않고 머지하지 말고
테스트 하나와 규칙 문서 한 장에서 시작하라고 권한다.

## 분석

### 읽기와 검증을 떼어 놓은 질문

글의 가장 단단한 주장은 읽기가 검증의 유일한 수단이 아니라는 점이다.
코드를 읽는 일과 코드가 맞다는 확신을 얻는 일은 한때 같은 말이었다.
코드 생산량이 읽는 속도를 넘어서자 둘을 나눠 보게 되었다고 필자는 쓴다.
질문이 “읽어서 알 수 있는가”에서 “틀리면 알려 주는가”로 바뀌면
해야 할 일도 바뀐다.
코드를 더 빨리 읽는 방법을 찾는 대신, 틀림을 알리는 장치를 짓게 된다.

### 층마다 다른 종류의 오류를 맡는다

네 장치는 같은 일을 겹쳐 하는 것이 아니라 서로 다른 오류를 맡는다.
타입과 린트는 기계가 결정적으로 판정하는 오류, 곧 안 쓰는 변수나 경계 위반을
맡는다.
테스트는 의도와 구현의 어긋남을 맡고, 작은 PR은 한 번에 확인할 범위를 줄인다.
화면 확인은 앞의 셋이 볼 수 없는 결과물의 모양을 맡는다.
필자가 기계로 걸러진 뒤에만 자기 눈을 쓴다고 하는 것은 이 순서 때문이다.
싼 장치가 먼저 걸러내고 비싼 눈이 마지막에 남는다.

### 신입 때 일화와 규칙화의 연결

글머리의 띄어쓰기 일화는 장식이 아니라 같은 논지의 앞부분이다.
반복되는 지적은 사람이 아니라 규칙이 맡아야 한다는 힌트라고 필자는 되짚는다.
이 생각이 Oxlint의 함수 길이, 복잡도, 중첩 깊이 같은 규칙과
Knip, Archlint로 이어진다.
같은 코멘트를 반복해야 하는 일이 생기면 린트 룰로 옮긴다는 원칙이다.
기계가 잡기 애매한 기준은 `AGENTS.md`에 적고,
가능하면 나중에 정적 린트 룰로 옮긴다고 한다.

### 규칙 문서도 낡는다

필자는 규칙 문서가 쓰는 순간부터 낡는다는 경험을 적는다.
서비스가 모노레포로 커지고 린터가 Biome에서 Oxlint로 바뀌었는데
`CLAUDE.md`와 `AGENTS.md`가 따로 놀아서 에이전트가 옛 명령어를 실행했다.
결국 `CLAUDE.md`를 지우고 `AGENTS.md` 하나로 합쳤다고 한다.
검증 구조는 한 번 짓고 끝나는 것이 아니라 코드처럼 유지보수해야 한다는 뜻이다.

## 비평

### 구현과 테스트를 같은 AI가 쓴다

필자는 AI가 구현과 테스트를 동시에 쓰게 하고,
사람은 `it` 줄만 보고 그 아래 검증 코드는 AI가 더 정확히 썼으리라 믿는다.
이 믿음이 글의 핵심 장치를 받치고 있다.
같은 모델이 만든 구현과 테스트는 같은 오해를 공유할 수 있고,
그러면 테스트는 통과하면서 틀린 동작이 굳어진다.
글은 동어반복 테스트를 금지하는 규칙을 한 줄 언급할 뿐,
이 순환을 어떻게 끊는지는 설명하지 않는다.
요구사항 명세인 `it` 줄이 틀렸다면 그것도 AI가 쓴 것이므로 사람이 읽어야 한다.

### 수치는 산출량이지 품질이 아니다

PR 134개 머지와 하루 PR 10개는 많이 만든다는 증거다.
머지된 변경이 얼마나 옳았는지, 되돌린 PR이 몇 개인지,
운영에서 발견된 결함이 몇 건인지는 글에 없다.
필자는 코드를 안 보고 머지했다가 낚인 적이 여러 번이라고 쓰지만
횟수와 피해는 적지 않는다.
따라서 이 방식이 읽기보다 낫다는 비교 근거는 글 안에서 확인되지 않는다.

### 사이드 프로젝트와 사내 상황이 섞여 있다

사례 수치의 상당수는 필자의 사이드 프로젝트에서 나왔다.
사내 사례인 Jira 티켓 48개는 필자 스스로 단순한 타입스크립트 변경이라서
가능했다고 말한다.
사내 논쟁은 결론이 나지 않았다고 했으므로,
팀 단위에서 Diff를 안 읽는 합의가 어떤 조건에서 가능한지는 이 글로 알 수 없다.
사이드 프로젝트는 혼자 책임지는 구조여서 같은 방식이 팀에서 같은 결과를 낼지
따로 검증해야 한다.

### 프론트엔드 화면 중심의 한계

네 번째 장치인 화면 확인은 UI 결과물이 있는 변경에 맞는 장치다.
보안 변경, 동시성, 데이터 마이그레이션, 성능처럼
화면에 드러나지 않는 변경이 이 구조에서 어떻게 걸러지는지는 다루지 않는다.
테스트가 이 영역을 맡을 수 있으나, 테스트가 못 보는 결함은
Diff를 읽어야만 드러나는 경우가 있다.

### 코드를 읽는 일의 다른 쓸모

글은 읽기를 확신을 얻는 여러 수단 가운데 하나로만 본다.
그러나 리뷰에는 변경 내용을 팀이 함께 알게 하고
코드베이스에 대한 이해를 유지하는 기능도 있다.
Diff를 읽지 않으면 이 기능은 누가 맡는지에 대한 답이 글에 없다.
필자는 시스템이 믿을 만한지를 사람이 보면 된다고 하지만,
그 판단에 필요한 코드 이해가 어디서 쌓이는지는 말하지 않는다.

## 인사이트

### 변경마다 틀리면 무엇이 알려주는지 적어 보기

글에서 옮겨 쓸 수 있는 가장 작은 단위는 질문이다.
PR을 열 때 이 변경이 틀렸다면 어느 장치가 알려 주는지를 한 줄로 적어 본다.
답이 없는 변경은 읽어야 하는 변경이고,
답이 있는 변경만 읽기를 줄일 수 있다.
같은 이유로 검증 장치가 없는 영역에서는 이 방식을 쓰지 않는 편이 맞다.

### 반복되는 코멘트는 규칙의 후보

같은 리뷰 코멘트가 두 번 나오면 린트 룰이나 규칙 문서로 옮길 후보다.
필자의 띄어쓰기 일화가 보여 주듯 이 일은 사람이 맡을수록 비싸다.
다만 규칙 문서는 낡으므로, 가능하면 사람이 읽는 문서보다
도구가 실행하는 규칙으로 옮기는 편이 유지 비용이 낮다.

### 사고를 새 조건으로 바꾸는 습관

필자는 낚였을 때 눈을 더 갈아 넣는 대신 다음에 어떤 장치를 추가할지 묻는다.
이 글에서는 그 결과가 Mock 데이터 검증과 Before/After 스크린샷이었다.
사고를 한 번의 반성으로 끝내지 않고 PR 조건으로 남기는 방식이다.
관련 흐름은 [코드가 리뷰를 앞질렀다](code-outruns-review.md)와
[AI가 코드 작성과 리뷰의 비율을 깨뜨렸다는 주장](review-ratio-broken.md)에서
다른 시각으로 다룬다.
기준을 통과한 PR을 사람 없이 승인하는 시도는
[small-change](small-change.md)에 정리되어 있다.

### 확인할 것

머지된 PR 중 되돌려진 것의 비율과 머지 뒤 발견된 결함 수를 알아야
이 방식과 Diff 읽기를 비교할 수 있다.
구현과 테스트를 같은 모델이 쓸 때 테스트가 놓치는 오류의 유형도 확인이 필요하다.
글이 인용한 Lauren Tan의 발표와 요즘IT의 정리 기사는 이 문서가 열어 보지 않았다.
