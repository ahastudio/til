# OpenQodex: 코딩 에이전트가 쓴 변경을 별도 리뷰어가 푸시 전에 검토하는 도구

<https://github.com/openqodex/openqodex>

GN 토론: <https://news.hada.io/topic?id=36426>

## 소개

OpenQodex는 코딩 에이전트가 쓴 변경을 푸시하기 전에 별도의 리뷰어가 검토하게
하는 오픈 소스 도구다.
Qodex가 만들었고, Qodex는 풀 리퀘스트용 호스팅 리뷰 서비스도 따로 운영한다고
README는 밝힌다.
라이선스는 Apache 2.0이고 TypeScript로 작성되었다.
저장소는 2026년 10월 2일에 만들어졌고, 가장 최근 릴리스는 10월
28일의 0.16.0이다.
조회 시점의 GitHub 별은 1,104개였다.
README는 1.0을 향해 가는 중이며 명령, 플래그,
설정 파일이 마이너 릴리스 사이에 바뀔 수 있다고 적는다.

리뷰 대상은 아직 푸시하지 않은 커밋과 커밋하지 않은 변경 전부다.
Claude Code, Codex, Cursor, Cline에서 쓸 수 있고,
설치는 터미널에서 `npx openqodex init` 한 줄이다.
설치 뒤에는 에이전트에게 openqodex로 변경을 리뷰하라고 말하면 된다.
도구 자체는 계정이나 API 키를 요구하지 않는다.

## 동작 방식

리뷰는 두 단계로 진행된다.

첫 단계는 모델을 쓰지 않는 스캐너다.
스캐너(scanner)는 gitleaks나 semgrep처럼 모델 없이 코드를 검사하는 프로그램이며,
내장 스캐너는 22개다.
변경한 파일에 맞는 스캐너만 돌고, 결과 가운데 변경한 줄에 있는 것만 남긴다.
테스트 픽스처에서 나온 결과와 사용자가 끈 규칙의 결과는 버린다.
지원하는 모든 락파일은 리뷰와 스캔 때마다 osv.dev와 대조한다.
변경한 줄 밖의 취약점 공지는 보여 주되 개수에는 넣지 않고 리뷰어에게 주는
요약에서도 뺀다.

두 번째 단계는 리뷰어(reviewer)다.
리뷰어는 사용자의 로그인으로 실행되는 별도의 Claude Code 또는 Codex 프로세스다.
기본값에서는 코드를 쓴 에이전트가 리뷰하지 않는다.
파인더(finder) 세션이 변경의 각 부분과 그것을 호출하는 코드를 읽고,
근거가 되는 줄을 인용한 후보를 낸다.
스크립트가 모든 인용이 실제 코드에 있는지 대조한다.
이어 베리파이어(verifier) 세션이 후보와 스캐너 결과를 하나씩 코드와 비교해
확인하거나 부정하고, 이유를 달아야 한다.
스크립트는 모든 스캐너 결과에 답이 달렸는지,
변경된 모든 줄이 리뷰어에게 전달됐는지도 검사한다.
스타일과 이름에 관한 지적은 관찰로만 표시되고 푸시를 막지 않는다.
마지막에 어떤 결과를 에이전트가 고칠지는 사용자가 고른다.

## 설치와 사용

| 에이전트    | 리뷰 시작 | 리뷰어가 될 수 있음 | 푸시 게이트                    |
| ----------- | --------- | ------------------- | ------------------------------ |
| Claude Code | 가능      | 가능                | 가능                           |
| Codex CLI   | 가능      | 가능                | 가능, Codex에서 훅을 신뢰한 뒤 |
| Cursor      | 가능      | 불가                | 없음, 규칙으로 리뷰를 요청     |
| Cline       | 가능      | 불가                | 없음, 규칙으로 리뷰를 요청     |

요구 사항은 Node 22 이상과 git이고, macOS나 Linux에서 쓴다.
CI는 Node 22, macOS, Ubuntu에서 게이트를 돌리며 Windows와 WSL에서는 시험하지
않는다고 README는 적는다.
전체 리뷰에는 로그인된 Claude Code나 Codex가 필요하다.
OpenQodex 자체는 사용 데이터를 수집하지 않고,
내장 스캐너도 코드를 보내지 않는다.
다만 리뷰어는 변경 내용을 사용자의 Claude Code나 Codex 로그인에 연결된 모델
서비스로 보낸다.

주요 명령은 이렇다.

| 명령                 | 하는 일                                               |
| -------------------- | ----------------------------------------------------- |
| `openqodex review`   | 현재 변경을 한 번에 리뷰하고 요약(receipt)을 출력한다 |
| `review --all`       | 저장소 전체를 리뷰한다                                |
| `review <branch>`    | 브랜치를 리뷰한다                                     |
| `review '#42'`       | 풀 리퀘스트를 리뷰한다                                |
| `openqodex graph`    | 함수를 누가 호출하는지 같은 코드 질문에 답한다        |
| `openqodex trust`    | 설정에 추가한 커스텀 스캐너를 승인한다                |
| `npx openqodex demo` | 버그를 심은 작은 저장소를 만들어 스캔한다             |

리뷰 결과는 `report.html`, `report.md`, `report.json`,
`report.sarif`로 저장된다.
모든 단계가 돌아야 리뷰가 완료된 것이고,
아니면 Review incomplete와 빠진 단계를 출력하고 종료 코드 2로 끝난다.
푸시 게이트는 에이전트 안의 훅으로, 평범한 `git push`에서는 현재 작업에 통과한
리뷰가 있는지 묻는다.
`init`이 추가하는 git pre-push 훅은 푸시가 실제로 보내는 커밋을 검사하며,
`git push --no-verify`는 이 훅을 건너뛴다.
두 게이트는 기본값에서 경고만 하고, 설정 파일의 `review.block_on_severity`를
지정해야 막는다.
GitHub Action은 워크플로가 Anthropic API 키를 줄 때만 전체 리뷰를 돌리고,
키가 없으면 스캐너만 돈다.

## 제작사가 밝힌 한계

README는 아직 하지 못하는 일을 따로 나열한다.
Claude Code나 Codex가 아닌 리뷰어는 없다.
Cursor는 읽기만 하도록 제한할 방법이 없어서 리뷰어가 될 수 없다.
Codex 샌드박스 안에서는 두 번째 Codex 프로세스가 시작되지 않아 Codex가
리뷰어가 될 수 없다.
사용자 본인의 API 키로 하는 리뷰는 GitHub Action 말고는 없다.
취약점 데이터베이스의 오프라인 사본도 없고, 설치는 npm으로만 된다.
어떤 리뷰도 모든 문제를 찾아내지는 못하며,
돌지 못한 단계는 보고서에 적힌다고 README는 말한다.

## 벤치마크

README는 두 종류의 벤치마크를 싣는다.
하나는 버그를 심은 사례 모음의 개발(dev) 분할이다.
이 표에서 Claude Code(claude-opus-5-5)는 심은 문제 153개 가운데 150개를 찾아
재현율 98.0%였고, 리뷰 한 번당 비용은 0.4371달러였다.
같은 모델의 다른 설정은 129/153(84.3%)에 리뷰당 0.0870달러였다.
Codex(gpt-6.1-sol)는 115/153(75.2%)이었고 비용은 측정하지 않았다.
스캐너만 쓴 경우는 51개 중 32개(62.7%)였다.
정밀도는 하한과 상한 두 값으로 적혀 있고, 예를 들어 첫 행은 84.4%에서 100.0%다.

다른 하나는 실제 풀 리퀘스트 모음인 AACR-Bench이며,
이 벤치마크 자체의 평가기가 낸 수치다.
Library(gpt-6.1-sol) 행은 의미 정밀도(semantic precision) 22.8%,
의미 재현율 5.2%, 의미 F1 8.5%, 노이즈 비율 77.2%이고 리뷰당 비용은
0.0839달러다.
이 행의 이슈 재현율은 아직 판정하지 않았다고 되어 있다.

## 분석

### 모델의 판단을 스크립트가 감싸는 구조다

이 도구의 설계에서 눈에 띄는 것은 모델이 하는 일과 스크립트가 확인하는 일을
나눈 점이다.
모델은 후보를 내고 판정한다.
스크립트는 인용한 줄이 코드에 실제로 있는지, 모든 스캐너 결과에 답이 달렸는지,
모든 변경 줄이 누군가에게 전달됐는지만 센다.
이 확인들은 모델이 할 수 있는 실수 가운데 세 가지를 기계적으로 막는다.
없는 코드를 있다고 인용하는 것, 스캐너 결과를 조용히 건너뛰는 것,
일부 파일을 읽지 않고 통과시키는 것이다.
모델이 코드를 잘못 이해해서 틀린 판정을 내리는 경우는 스크립트가 막지 못한다.

### 코드를 쓴 쪽과 검토하는 쪽을 가르는 것이 기본값이다

기본값에서 코드를 쓴 에이전트는 리뷰하지 않는다.
같은 에이전트가 자기 변경을 검토하면 같은 맹점을 공유하기 쉽다는 전제에서 나온
설계로 보인다.
README는 이 전제를 직접 밝히지는 않으므로 이것은 설계에서 읽어 낸 추정이다.
이 분리가 실제로 맹점을 줄이는지는 README의 벤치마크로 확인되지 않는다.
벤치마크 표는 리뷰어의 종류별 수치이지,
작성자와 리뷰어가 같을 때와 다를 때를 비교한 표가 아니기 때문이다.

### 스캐너를 앞에 두어 확정적인 바닥을 만든다

스캐너가 먼저 돌고 그 결과를 베리파이어가 모두 판정하므로,
모델이 놓치더라도 스캐너가 잡은 문제는 보고서에 남는다.
README가 싣는 스캐너 단독 결과는 62.7%이고 모델을 더한 설정은 75%에서 98%다.
스캐너가 이미 잡는 범주가 큰 몫을 차지하고,
모델은 그 위에 얹히는 부분을 채운다는 구성이다.

## 비평

### 정밀한 수치는 제작사가 심은 버그에서 나온 것이다

98.0%라는 재현율은 심은 문제 153개에 대한 것이다.
누가 어떤 기준으로 심었는지는 README의 표만으로 알 수 없고,
분할 이름이 개발 분할이라는 점으로 보아 도구를 다듬는 데 쓰인 사례일
가능성이 있다.
이것은 추정이며, 그 경우 이 수치는 도구가 이미 본 유형의 문제에서의 성능이다.
실제 풀 리퀘스트 모음에서는 수치가 크게 달라진다.
AACR-Bench 행의 의미 F1은 8.5%이고 노이즈 비율은 77.2%다.
두 수치를 같은 표로 읽으면 안 된다.
모델이 다르고(claude-opus-5-5와 gpt-6.1-sol), 측정 지표도 다르며,
AACR-Bench 행은 개발 노트북 부분집합이다.
그래도 심은 버그에서 높은 재현율을 보인 도구가 실제 풀 리퀘스트에서는 지적의
상당수를 노이즈로 낸다는 읽기는 README의 수치 안에서 가능하다.

### 정밀도가 구간으로 적혀 있어 하나의 값으로 읽을 수 없다

첫 행의 정밀도는 249/295(84.4%)에서 295/295(100.0%)까지다.
구간의 양 끝이 무엇을 뜻하는지는 이 표에서 설명되지 않는다.
설명은 README가 링크한 별도 문서에 있다고 하는데, 이 글은 그 문서를 열지 않았다.
따라서 이 구간을 정밀도가 84%에서 100% 사이라고 단순하게 요약하는 것은 위험하다.

### 게이트는 기본값에서 막지 않고, 막더라도 우회할 수 있다

푸시 게이트는 기본값에서 경고만 한다.
막으려면 설정 파일에 `review.block_on_severity`를 직접 지정해야 한다.
막도록 설정해도 `git push --no-verify`는 git 훅을 건너뛴다.
에이전트 안의 게이트는 푸시 명령이 무엇을 보내는지 모르고,
평범한 `git push`가 아니면 판단할 수 없다고 답한다.
그러므로 이 도구는 지켜야 할 절차를 강제하는 장치가 아니라 실수를 줄이는 보조
장치로 읽어야 한다.

### 계정이 필요 없다는 말은 모델 서비스를 쓰지 않는다는 뜻이 아니다

OpenQodex는 자체 계정과 키를 요구하지 않는다.
하지만 전체 리뷰에는 로그인된 Claude Code나 Codex가 필수이고,
변경 내용은 그 서비스로 전달된다.
Cursor와 Cline 사용자는 리뷰어가 될 수 없으므로,
이 도구를 쓰려면 Claude Code나 Codex를 따로 설치해야 한다.
Windows에서는 시험하지 않았으므로 해당 환경에서 동작을 기대하기 어렵다.

## 인사이트

### 검토를 사람이 아니라 다른 에이전트에게 넘기면 검토의 부담이 옮겨 간다

에이전트가 코드를 쓰는 속도가 빨라지면 사람의 검토가 부족해진다.
OpenQodex는 이 문제를 다른 에이전트에게 검토를 맡겨 풀려 한다.
그러면 부족한 것이 검토 시간에서 검토 결과를 믿을 근거로 옮겨 간다.
사람은 이제 변경을 읽는 대신 리뷰어의 보고서를 읽고,
그 보고서가 믿을 만한지 판단해야 한다.
이 판단에는 위에서 본 벤치마크의 구간 정밀도, 노이즈 비율 같은 수치가 필요한데,
그 수치가 사용자의 코드베이스에서도 성립하는지는 직접 재 보기 전에는 알 수 없다.

### 도입은 푸시 단위로 하고, 자기 저장소의 사례로 정밀도를 먼저 재야 한다

리뷰 한 번에 모델 비용이 들고, README의 표에서 리뷰당 비용은 설정에 따라
0.09달러에서 0.44달러였다.
에이전트가 편집할 때마다 돌리면 비용이 쌓이므로,
푸시 직전에 한 번 돌리는 것이 이 도구의 설계와도 맞는다.
처음 몇 주는 막지 않는 기본값으로 쓰면서,
보고서의 지적 중 실제로 고친 것과 무시한 것의 비율을 기록하는 것이 좋다.
무시한 비율이 높으면 AACR-Bench의 노이즈 비율이 실제 환경에서도 나타나는 것이고,
그때는 `block_on_severity`를 켜지 않는 쪽이 낫다.

### 확정적 검사와 모델 판단의 비율이 이 범주 도구의 품질을 가른다

이 도구는 스캐너, 스크립트 검증, 모델 판단을 겹쳐 쌓았다.
모델의 판단이 틀릴 가능성을 앞뒤의 확정적 검사가 줄이는 구조다.
같은 구조는 컴파일러의 경고 위에 린터를 얹고 그 위에 사람이 리뷰하던 기존
관행과 닮았다.
다만 여기서는 가장 위층이 사람이 아니라 모델이어서,
위층의 오류를 더 위에서 잡아 줄 층이 없다.
그 빈자리를 채우는 것이 사용자가 고를 결과를 직접 지정하는 마지막 단계이고,
이 단계를 건너뛰고 모두 고치라고 하면 구조의 마지막 확인 단계가 사라진다.
