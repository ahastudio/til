# 크래시 리포터를 달자 나온 것: 오래된 Android WebView에서 부팅을 죽인 웹 표준 세 개

원문: [Our crash reporter's first day: three web standards that killed boot on old Android WebViews - DEV Community](https://dev.to/dumbgamelab/our-crash-reporters-first-day-three-web-standards-that-killed-boot-on-old-android-webviews-2a9d)

GN 토론: <https://news.hada.io/topic?id=36085>

## 소개

Dumb Game Lab이 열두 개쯤 되는 작은 HTML5 게임을 Android 앱으로 감싸 배포하면서
처음으로 크래시 리포터를 넣은 첫날의 기록이다.
리포터는 `<head>` 맨 위에 두는 작은 스크립트로, 잡히지 않은 오류를 자기 워커로
보낸다.
첫날 데이터에서 가장 많은 부팅 크래시는 게임 코드의 버그가 아니라 오래된 Android
WebView에 존재하지 않는 표준 함수였다.

세 가지가 문제였다.
`CanvasRenderingContext2D.roundRect`는 집게 게임에서 둥근 버튼과 공유 카드에
쓰다가 부팅을 죽였다.
`Array.prototype.at`은 `arr.at(-1)`이 편해서 열두 군데쯤에 번졌다.
`structuredClone`은 두 타이쿤 게임이 저장 데이터를 복사하는 데 썼다.
셋 다 최근 몇 년 사이의 폰에서는 동작해서 자체 테스트로는 잡히지 않았고, 아직
WebView가 Chrome 90 안팎인 구형 기기의 플레이어는 흰 화면을 보고 떠났다.
리뷰도 신고도 없이 떠나서, 리포터가 처음으로 그 사실을 보여 주었다고 한다.

## 동작 방식

### 왜 개발자의 폰에서는 보이지 않았나

WebView는 앱이 아니라 기기의 시스템 구성요소여서 사용자의 기기마다 엔진 버전이
다르다.
앱 안에 번들한 브라우저가 아니므로 개발 중인 최신 기기에서 동작해도 가장 오래된
사용자 기기에서는 표준 함수가 없을 수 있다.
글의 결론이 이를 요약한다.
WebView에 게임을 싣는다면 최소 지원 브라우저는 내 폰이 아니라 플레이어 기반에서
가장 오래된 폰이다.

### 실패가 보이지 않는 이유

부팅 시점의 `TypeError`는 게임이 화면을 그리기 전에 스크립트를 멈추므로 사용자는
흰 화면을 본다.
스토어에는 앱이 켜지지 않는다는 평가가 남지 않고, 사용자는 조용히 삭제한다.
이 실패는 크래시 리포터가 없으면 존재 자체가 드러나지 않는다.
글이 리포터를 가장 먼저 달 만한 이유로 꼽는 것이 이것이다.

## 구현하기

글의 해법은 게임마다 고치지 않고 호환 파일 하나를 만들어 리포터가 들어가는 같은
자리, 곧 어떤 게임 스크립트보다 먼저 실행되는 곳에 주입하는 것이다.
저자의 규칙은 세 가지다.
보고된 오류가 이 함수는 함수가 아니다이고 그 함수가 웹 표준이라면, 수정은 게임이
아니라 호환 파일에 넣는다.
그러면 다음 게임이 공짜로 혜택을 본다.
roundRect를 지운 캔버스 컨텍스트를 만들어 호환 코드가 채워 넣는지 확인하는 자체
시험을 다른 점검과 함께 돌린다.
호환 코드는 스토어 빌드에만 싣고 개발 서버에는 싣지 않는다.
개발 중에는 문제를 스스로 가리지 않기 위해서다.

아래는 이 접근을 다시 쓴 예다.
`Array.prototype.at`과 `String.prototype.at`을 없을 때만 정의하고,
`structuredClone`은 JSON 왕복으로 대체한다.

```javascript
(function () {
  // 이미 있으면 건드리지 않는다: 최신 WebView의 동작을 덮어쓰지 않기 위해서다.
  function define(target, name, value) {
    if (target && !target[name]) {
      Object.defineProperty(target, name, {
        value: value,
        writable: true,
        configurable: true,
      });
    }
  }

  // at(): 음수 인덱스는 끝에서부터 센다. 범위를 벗어나면 undefined.
  function at(index) {
    var n = Math.trunc(index) || 0;
    if (n < 0) n += this.length;
    return n < 0 || n >= this.length ? undefined : this[n];
  }
  define(Array.prototype, 'at', at);
  define(String.prototype, 'at', at);

  // structuredClone(): 손실이 있다. Map, Date, 순환 참조를 복사하지 못한다.
  // 저장 데이터가 순수 JSON일 때만 안전하다.
  if (typeof structuredClone === 'undefined') {
    window.structuredClone = function (value) {
      return value === undefined ? value : JSON.parse(JSON.stringify(value));
    };
  }
})();
```

roundRect는 `moveTo`, `lineTo`, `arcTo`로 모서리를 그리고 반지름을 짧은 변의
절반으로 제한하는 식으로 채워 `CanvasRenderingContext2D`,
`OffscreenCanvasRenderingContext2D`, `Path2D`에 설치한다고 글은 설명한다.
이 문서는 그 구현을 따로 쓰지 않았다.

## 트레이드오프

### 호환 파일 하나로 모으면 게임마다 고치는 비용은 줄지만 숨은 의존이 생긴다

한 파일에 모으면 다음 게임이 공짜로 혜택을 보고 같은 오류를 다시 고치지 않는다.
대신 호환 파일을 지나치게 믿어서 코드 작성자가 지원되지 않는 API를 모르고 쓰게
될 수 있다.
글은 이를 규칙(웹 표준이면 호환 파일에 넣는다)으로 관리하지만, 호환 파일이
커질수록 무엇을 채우고 있는지 파악하기 어려워진다.
이는 이 문서의 해석이다.

### 손실이 있는 대체 구현은 용도를 좁혀서만 안전하다

`structuredClone`의 JSON 대체는 Map, Date, 순환 참조를 복사하지 못한다.
글의 저장 데이터는 순수 JSON이어서 괜찮다고 저자가 밝히면서 복사해 쓰기 전에
자기 것을 확인하라고 경고한다.
같은 이름의 함수가 다른 의미로 동작하므로, 나중에 Map을 저장 데이터에 넣으면
구형 기기에서만 조용히 데이터가 달라진다.
이 실패는 호환 코드를 넣은 사람이 아니라 한참 뒤 데이터 모양을 바꾼 사람에게
돌아온다.

### 폴리필 대신 문법과 빌드로 낮추는 방법은 이 글에서 다루지 않았다

글의 해법은 런타임에서 없는 함수를 채우는 것이다.
다른 방법, 곧 빌드 시점에 코드를 낮추거나 최소 지원 버전을 올리는 것은 글에
나오지 않는다.
구형 기기의 비중이 작아지면 최소 지원 기준을 올려 호환 파일을 없애는 선택도
가능하지만, 글은 그 판단 기준을 주지 않는다.

## 함정

- 호환 파일이 게임 스크립트보다 뒤에 실행되면 의미가 없다. 가장 앞에 두어야
한다.
- 개발 서버에도 호환 코드를 넣으면 최신 기기에서는 문제가 드러나지 않는다. 글이
스토어 빌드에만 싣는 이유다.
- `structuredClone` 대체를 그대로 복사하면 Map이나 Date가 든 데이터가 조용히
깨진다.
- 호환 코드가 이미 있는 구현을 덮어쓰면 최신 WebView의 더 정확한 동작이
사라진다. 없을 때만 정의해야 한다.
- 리포터 자체가 구형 기기에서 실행되지 않는 문법을 쓰면 가장 필요한 곳에서
침묵한다. 리포터는 가장 낮은 기준의 문법으로 써야 한다. 이는 이 문서의 추가
주의이며 글에는 없다.

## 확인하기

글이 제시한 자체 시험은 roundRect를 제거한 캔버스 컨텍스트를 만들어 호환 코드가
이를 채우는지 확인하는 것이다.
같은 방식으로 `at`과 `structuredClone`도 시험할 수 있다.
가장 직접적인 확인은 구형 WebView(Chrome 90 안팎)가 든 에뮬레이터나 기기에서
앱이 흰 화면 없이 부팅되는지 보는 것이다.
이 문서는 이 시험을 실행하지 못했다.

## 체크리스트

- 크래시 리포터가 `<head>` 맨 위에서 게임 스크립트보다 먼저 실행되는가.
- 보고된 오류 가운데 웹 표준 함수가 없다는 종류를 따로 모아 보는가.
- 호환 코드는 스토어 빌드에만 들어가고 개발 빌드에는 들어가지 않는가.
- 호환 코드는 대상이 없을 때만 정의하는가.
- 대체 구현의 손실(Map, Date, 순환 참조)을 데이터 모양과 대조했는가.
- 최소 지원 WebView 버전을 사용자 분포에서 정했고, 그 버전의 기기에서 부팅을
시험했는가.

## 기억할 원칙

### 최소 지원 환경은 내 기기가 아니라 가장 오래된 사용자의 기기다

글이 말하는 교훈은 실패가 보이지 않는 곳에서 사용자가 조용히 떠난다는 것이다.
개발자의 기기에서 동작하는 것과 사용자의 기기에서 동작하는 것은 다르고, 그
차이를 측정하는 유일한 방법은 사용자의 기기에서 오류를 받아 보는 것이다.
작은 리포터 하나가 첫날부터 값을 한 이유가 이것이다.
