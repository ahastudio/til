## 소개

Jolt는 Scheme 위에서 도는 자기 호스팅(self-hosted) Clojure 구현이다.
Chez Scheme에서 네이티브로 돌고, JavaScript가 필요할 때는 Gambit 백엔드를 쓴다.
JVM도 빌드 단계도 없으며, 대부분의 이식 가능한(portable) Clojure 코드가 수정 없이
돌아간다고 소개한다.

컴파일러는 Clojure로 작성되어 자기 자신을 컴파일한다.
Clojure를 읽어 호스트 중립 IR로 분석하고 Scheme을 내보낸 뒤 실행하는 구조이며, 그
Scheme이 Chez이거나 JavaScript로 컴파일된 Gambit이다.
저장소는 2026년 6월 1일에 만들어졌고, 라이선스는 `LICENSE` 파일 기준 Eclipse Public
License 2.0이다.
공개 시점 기준 스타 225개, 포크 17개이며, 기본 브랜치 커밋은 약 2,300건으로 대부분이
`yogthos`(Dmitri Sotnikov)의 것이고 외부 기여자 네 명이 소수의 커밋을 더했다.

## 주요 기능

홈페이지가 내세우는 축은 여섯 가지다.

자기 호스팅 컴파일러는 위에서 말한 대로 Clojure로 쓰여 자신을 컴파일한다.
`jolt build`는 런타임과 표준 라이브러리, 애플리케이션과 그 의존성을 미리 컴파일해 하나의
자기 완결 실행 파일로 만든다 — 실행에는 Chez도 JVM도 소스도 필요하지 않다.

동시성은 흉내가 아니라 OS 스레드 위에서 돈다.
`future`/`promise`/`agent`/`pmap`이 공유 힙 위의 OS 스레드에서 실행되어 JVM 의미론과
맞고, `core.async`가 채널과 go 블록을 제공한다.

수 체계는 온전한 numeric tower다.
정확한 정수와 bignum, 정확한 유리수(`(/ 1 2)` ⇒ `1/2`), 그리고 flonum double을 갖는다.
`=`는 범주를 의식하고 `==`는 값 동등성을 본다.

영속 자료구조는 32-way 트라이 기반 불변 벡터, cons 리스트, HAMT 맵/집합으로 Clojure의
값 의미론을 따르며, transient는 진짜 가변 스크래치 컬렉션이다.
그 밖에 지연·무한 시퀀스, transducer, 구조 분해, 멀티메서드, 프로토콜과 레코드,
메타데이터, 네임스페이스, 런타임 `eval`, 완전한 리더를 지원한다고 적는다.

## 사용법

설치는 자기 완결 바이너리 하나로 끝난다 — 런타임과 컴파일러와 표준 라이브러리가 함께
들어 있다.

```sh
brew install jolt-lang/jolt/jolt
# 또는 설치 스크립트 (Linux / macOS)
curl -sL https://raw.githubusercontent.com/jolt-lang/jolt/main/install | bash

jolt -e '(+ 1 2)'        # => 3
```

클론에서 바로 돌릴 수도 있다.
이때는 Chez Scheme이 필요하지만 부트스트랩 시드가 저장소에 포함되어 있어 빌드 단계가
없다.

```sh
git clone --recurse-submodules https://github.com/jolt-lang/jolt.git
cd jolt
bin/jolt -e '(+ 1 2)'
```

프로젝트 실행과 빌드, nREPL은 다음과 같다.

```sh
bin/jolt run -m myapp.core        # deps.edn 해석 후 -main 실행
bin/jolt -M:test [args]           # 별칭의 :main-opts 실행
bin/jolt path                     # 해석된 소스 루트 출력

bin/jolt build -m myapp.core -o myapp   # 단일 실행 파일 (--opt / --dev)
./myapp arg1 arg2

bin/jolt --nrepl-server           # deps.edn 자동 해석, .nrepl-port 기록
```

`.nrepl-port` 파일로 CIDER나 Calva, Cursive를 붙이면 var를 재정의한 뒤 다음 호출이
그것을 보므로 재시작이 필요하지 않다.

## Clojure와 다른 점

홈페이지가 밝히는 진짜 분기는 셋이다.

| 항목         | 차이                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| Java interop | JVM이 없으므로 일반 Java interop과 reflection, `gen-class`/`proxy`가 없다. `java.*`의 shim된 부분집합과 C FFI를 제공한다 |
| BigDecimal   | 제공하지 않는다(`decimal?`은 항상 false). 나머지 수 체계는 JVM과 일치한다                                                |
| Regex        | `java.util.regex`가 아니라 irregex로 컴파일한다. 흔한 패턴은 동작하지만 Java 고유 기능은 다르다                          |

문서에는 하나가 더 있다.
`.printStackTrace`는 실제 백트레이스를 출력하지만 `.getStackTrace`는 빈 배열을 준다 —
꼬리 호출 최적화(tail-call optimization) 때문에 프레임별 배열을 충실히 돌려줄 수 없기
때문이다.
STM(`ref`/`dosync`/`alter`/`commute`/`ref-set`/`ensure`)은 제공된다.

## 분석

### 이 프로젝트의 설계 핵심은 언어가 아니라 shim 계층이다

Clojure를 다른 런타임에 올리는 시도에서 어려운 부분은 문법이나 자료구조가 아니다.
persistent vector와 lazy seq는 알려진 알고리즘이고, 리더와 매크로도 명세가 분명하다.
실제 장벽은 생태계가 `java.*`에 얼마나 닿아 있는지이며, Jolt의 답은 그 표면을 골라
Chez 위에 흉내 내는 것이다.

저자 본인이 스레드에서 목표를 명시했다 — jank와 목표가 다르며, 기존 Clojure
라이브러리를 지원하는 런타임을 제공하는 것이 목적이라는 것이다.
인기 라이브러리가 사용하는 Java 표준 라이브러리 API를 시간을 들여 지도로 만들고 Chez
위에 shim을 만들어 그것들이 매끄럽게 돌게 했으며, 공식적으로 테스트되고 지원되는
라이브러리 목록을 문서로 공개했다고 밝혔다.
나아가 shim을 만드는 API를 사용자 공간에 노출해 각자 필요한 라이브러리용 shim을 추가할
수 있게 했고, 자신도 그 기능으로 JDBC 계층이나 암호 관련 라이브러리를 시스템 공유
라이브러리에 FFI로 붙여 만들었다고 적었다[^yogthos-goal].

`didibus`의 정리가 이 구조를 외부에서 명확하게 요약했다 — jank는 C++/LLVM에 호스팅되어
C/C++ 라이브러리를 직접 import해 쓰는 반면, Jolt는 Scheme으로 컴파일하지만 아직 Scheme
interop이 없어 오히려 “순수 Clojure” 런타임에 가깝고, 대부분 다른 Clojure 라이브러리를
쓰는 데 의존하며 ClojureJVM에서 interop으로 하던 흔한 I/O·스레딩 작업을 위해 Java의
부분집합을 제공해 ring, reitit, integrant, malli, hiccup 같은 라이브러리가 돌게 한다는
것이다[^didibus].

즉 Jolt의 호환성은 언어 사양의 함수가 아니라 `java.*` 표면적의 함수다.
이 선택은 작업 범위를 명확하게 만들지만 동시에 끝이 없는 목록을 만든다 — 새 라이브러리를
지원하려면 그 라이브러리가 닿는 Java API를 또 shim해야 한다.

### jank와 Jolt는 경쟁이 아니라 재사용 대상의 다른 선택이다

같은 스레드에서 jank의 제작자 `Jeaye`가 직접 답했다.
jank의 핵심 차별점은 매끄러운 C++ interop이며, 이는 범위와 복잡도 때문에 많은 사람이
손대려 하지 않는 문제라는 것이다.
임의의 C++ 라이브러리를 Clojure 코드와 함께 JIT·AOT로 지원하고, 네이티브 의존성을
프로그램과 함께 빌드하거나 설치된 시스템에서 찾아 주는 Cargo 영향을 받은 빌드 시스템까지
포함한다고 설명했다.
그리고 어떤 사람들에게는 또 하나의 차별점이 AI 생성 코드의 양이라고 덧붙였다[^Jeaye].

두 프로젝트를 나란히 놓으면 갈림길이 선명하다.
jank는 호스트 생태계(C++)를 재사용하려 하고, Jolt는 Clojure 생태계를 재사용하려 한다.
전자는 새로운 능력을 얻는 대신 Clojure 라이브러리 호환에 별도의 노력이 필요하고, 후자는
기존 코드를 그대로 돌리는 대신 호스트 쪽 생태계가 거의 없다 — Scheme에는 큰 라이브러리
생태계가 없기 때문이다.

이 구도에서 사용자의 선택 기준도 갈린다.
네이티브 라이브러리와 붙어야 하는 작업이면 jank가, 기존 Clojure 코드베이스를 JVM 없이
배포하고 싶으면 Jolt가 맞는다.
`saityi`가 babashka와 비교해 물은 것도 이 축의 질문이며[^saityi], 답은 Jolt가 스크립트
실행 속도가 아니라 프로젝트를 단일 바이너리로 굽는 쪽을 겨냥한다는 데 있다.

### JVM을 떠나며 얻은 가장 큰 것이 정작 마케팅되지 않았다

Clojure의 가장 유명한 제약은 JVM이 일반 꼬리 호출 최적화를 하지 않는다는 것이고, 그래서
Clojure에는 `recur`라는 우회로가 있다.
호스트를 Chez로 바꾸면 이 제약이 사라진다 — 문서의 Scheme 백엔드 요구사항 목록에
`syntax-rules` 매크로, `call/cc`, 완전한 수 체계와 함께 “proper tail calls”가 하드
요구사항으로 올라 있다.

그런데 홈페이지의 기능 목록 어디에도 이것이 없다.
문서에서 꼬리 호출이 등장하는 곳은 두 군데인데, 하나는 위처럼 호스트가 제공해야 하는
조건으로서이고 다른 하나는 `.getStackTrace`가 빈 배열인 이유 — 꼬리 호출 최적화 때문에
프레임별 배열을 충실히 만들 수 없다 — 로서다.
즉 이득은 요구사항 목록에, 대가는 제약 목록에 적혀 있고, 사용자가 얻는 것으로는 어디에도
정리되어 있지 않다.

`nemoniac`이 정확히 이 공백에 걸렸다.
꼬리 호출 최적화가 있는지 문서를 훑어봤지만 언급을 찾지 못했다며, Chez를 기반으로 하면
JVM의 제약이 사라질 것으로 보이는데 그것이 흥미로운 판매 포인트가 될 수 있겠다고
적었다[^nemoniac].
정보가 없는 것이 아니라 사용자가 찾을 자리에 없는 것이며, 이는 기술 문서에서 흔한 실패
방식이다.

저자 자신은 이것을 판매 포인트로 이해하고 있다 — 다만 홈페이지가 아니라 다른 곳에서
말한다.
Lobste.rs 스레드에서 `Yogthos`는 제대로 된 TCO가 단순한 성능 최적화가 아니라고 적었다.
JVM에서는 스택을 소진하지 않으려고 트램폴린을 써야 하므로 상호 재귀 알고리즘을 표현하는
것이 고통스러운데, 제대로 된 TCO가 있으면 그 경우를 훨씬 깔끔하게 표현할 수 있다는
것이다[^yogthos-tco].
표현력에 관한 이 설명이 기능 목록에 한 줄로 들어가 있었다면 `nemoniac`의 질문은 애초에
나오지 않았을 것이다.

### 저자가 밝힌 속도의 원천이 이 프로젝트의 성격을 규정한다

2026년 6월에 시작한 저장소가 두 달 만에 nREPL과 라이브러리 지원 목록과 문서 사이트를
갖췄다는 사실이 스레드의 큰 논점이었고, 저자가 직접 답했다.
빠르게 움직일 수 있는 이유는 기존 언어를 새 런타임에 이식하는 작업이기 때문이며, 어려운
작업과 해먹에서의 사유는 이미 Clojure 코어 팀과 커뮤니티가 지불했다는 것이다.
바퀴를 다시 발명하려는 것이 아니고, 20년 가까이 Clojure로 일해 왔으므로 언어가 무엇을
하는지와 호스트 플랫폼에 무엇을 구현해야 하는지를 잘 알고 있으며, 기본이 부트스트랩된
뒤에는 테스트를 통과시키고 점점 더 많은 라이브러리를 돌려 그 라이브러리의 테스트를
실행시키는 문제였다고 적었다 — 명세가 매우 잘 정의된 이상적인 상황이었다는
것이다[^yogthos-speed].

`xedrac`도 같은 판단을 밖에서 내렸다.
저자가 LLM 사용에 대해 매우 개방적이었고, 자신은 LLM 슬롭을 경계하지만 이것은 LLM을
최대로 활용하는 것이 완전히 합당한 사례 — 참조할 Clojure 구현이 이미 있고 동작을
검증할 테스트 케이스가 산더미처럼 있는 — 라는 것이다[^xedrac].

두 진술을 합치면 이 프로젝트가 무엇인지 정확해진다.
Jolt는 새로운 언어 설계가 아니라 잘 정의된 명세를 향한 대규모 이식 작업이며, 명세와
검증 수단이 모두 외부에 존재하는 이 조건이 속도의 원인이다.
그리고 이 조건은 우연이 아니라 Clojure가 20년간 축적한 자산이다.

## 비평

### 홈페이지와 저장소의 라이선스 표기가 다르다

홈페이지 푸터는 Jolt가 Eclipse Public License 1.0으로 공개된 오픈소스라고 적는다.
그런데 저장소의 `LICENSE` 파일은 Eclipse Public License 2.0이고, GitHub이 인식한
라이선스도 EPL-2.0이다.

이것을 사소한 오기로 넘길 수 없는 이유가 둘 있다.
첫째, 두 버전은 같은 이름을 공유하지만 조항이 다르다 — EPL-2.0은 특허 조항과 GPL
호환 옵션(보조 라이선스 지정)에서 1.0과 갈린다.
법무 검토가 필요한 조직에서는 어느 쪽인지가 도입 가능 여부를 가르는 정보다.
둘째, 라이선스는 프로젝트가 독자에게 제공하는 가장 기본적인 사실이며, 그것이 두 곳에서
다르게 적혀 있다는 것은 다른 서술도 한 곳만 보고 믿기 어렵다는 신호가 된다.

오기의 경로도 짐작할 수 있다 — Clojure 본체가 EPL 1.0이므로 그 문장을 그대로 옮겨
왔을 가능성이 높다.
Clojure 호환을 목표로 하는 프로젝트가 Clojure의 라이선스 표기까지 함께 복사했다는 것은
이 프로젝트의 성격에 대한 우연한 은유이기도 하다.

### 속도가 신뢰의 근거를 대체하지 못한다

스레드의 가장 긴 분기는 기능이 아니라 이 프로젝트를 믿을 수 있는지였다.
`phforms`는 중립적 관찰이라고 전제하면서, 저장소 커밋으로 판단할 때 2~3개월 개발한
시점에 이미 기능이 완결되고 다듬어진(어쩌면 성숙하기까지 한) Clojure 방언으로, JVM
Clojure에서 이식된 여러 라이브러리와 FFI와 Fibers를 갖추고 전문적이고 마케팅 지향적인
웹사이트와 상세한 문서와 nREPL 지원까지 함께 소통되고 있다는 점이 이 시대의 징후처럼
보인다고 적었다 — 이런 초기 단계에 주로 한 사람이 개발한 언어에서 기대하지 않을
것들이라는 것이다[^phforms].
`davexunit`은 더 직접적으로, 6월 1일부터 단일 저자의 커밋 2천 건과 아주 긴 커밋 메시지와
소스 주석으로 보아 vibecoded인데 그렇다고 공개되지 않은 것 같다고 적고, 이어 매우 긴
블로그 글의 끝부분에 LLM으로 만들었다는 언급이 있다는 것을 찾아 추가했다[^davexunit].

이 지적의 핵심은 “LLM을 썼다”가 아니라 그 사실이 어디에 적혀 있느냐다.
공개는 존재했지만 홈페이지와 저장소 표면이 아니라 긴 블로그 글의 끝에 있었고, 그래서
프로젝트를 평가하려는 사람이 먼저 만나는 정보에는 없었다.
`Jeaye`가 어떤 사람들에게는 AI 생성 코드의 양이 차별점이라고 언급한 것도 이 정보가 도입
판단의 입력이라는 뜻이다.

옹호 쪽의 논리에도 약점이 있다.
`iLemming`은 저자가 Clojure 책을 출간한 사람이며 네브래스카 어딘가의 무명 AI 사용
십대가 아니므로 자기가 무엇을 하는지 알 것이라고 적었고[^iLemming], `rahen`도 슬롭이
아니며 주 개발자가 Clojure 씬에 오래 있던 Dmitri Sotnikov라고 확인하면서 다만 개발 속도가
정말 빠르다는 지적은 맞다고 인정했다 — 자신도 기계학습용 Clojure 컴파일러를 만들고
있는데 9개월이 지나도 프로덕션 준비와는 아주 멀다는 것이다[^rahen].
그러나 저자 평판은 사람에 대한 신뢰이고 코드에 대한 증거가 아니다.

역설적인 것은 이 프로젝트에 필요한 증거가 실제로 있다는 점이다.
공식적으로 테스트되고 지원되는 라이브러리 목록 페이지가 그것이며, 상류 라이브러리의
테스트 스위트를 통과시켰다는 사실은 저자 이력보다 훨씬 강한 근거다.
그것을 홈페이지 앞면이 아니라 문서 하위 페이지와 스레드 답변에 둔 것은 커뮤니케이션의
선택 실수다.

### 벤치마크 서술이 기대를 왜곡하는 방향으로 요약되어 있다

Lobste.rs 스레드에서 `gasche`는 이 시도가 훌륭하고 흥미롭다고 전제한 뒤 벤치마크 결과의
서술이 거슬린다고 적었다 — 오해를 유발하고 기대를 왜곡할 것이라는 것이다.
문제 삼은 문장은 실제 성능에서 Jolt가 여러 벤치마크에서 JVM Clojure와 비교할 만하며
대부분에서 동등하거나 2배 정도 느리고 몇몇 경우에만 7배 정도 나쁘다는 요약이었다.
링크된 결과를 따라가 보면 전부 마이크로벤치마크라는 것이 드러난다는 지적이다[^gasche].

이 비판이 유효한 이유는 요약의 형태가 최악값을 주변화하기 때문이다.
“대부분 2배 이내, 몇몇만 7배”라는 서술은 분포를 말하지만 가중치를 말하지 않는다.
실제 프로그램에서 자주 밟는 경로가 7배 느린 쪽에 있으면 체감은 7배에 가깝고, 그 판정은
벤치마크 개수가 아니라 워크로드가 결정한다.
마이크로벤치마크만 있는 상태에서 “JVM Clojure와 비교할 만하다”는 결론을 내리는 것은
측정한 것보다 넓은 주장이다.

저자의 답이 이 지점에서 정직했다는 점은 기록해 둘 만하다.
`Yogthos`는 벤치마크를 프로그램 유형별 영향도로 분류하지 않았다는 것을 인정하며, 느린
경로가 전형적인 프로그램에서 더 자주 밟힌다면 결과가 최악값 쪽으로 기울 것이라는 지적이
맞다고 답했다.
다만 Clojure 프로그래밍이 데이터 지향적이어서 많은 애플리케이션이 원시 데이터 처리에
집중하므로 컬렉션과 함수 호출이 가장 중요한 벤치마크라고 판단했다고 설명하고, 벤치마크를
확장할 계획이라고 덧붙였다[^yogthos-bench].
그러나 이 교환이 스레드에 남아 있는 동안 홈페이지와 블로그의 요약 문장은 그대로이며,
성능은 대체 런타임 도입의 1차 판단 기준이므로 이 간극은 라이선스 오기보다 실무 영향이
크다.

### “대부분의 이식 가능한 Clojure가 수정 없이 돈다”는 검증할 수 없는 형태의 주장이다

홈페이지의 첫 문단이 내세우는 약속인데, “이식 가능한”의 경계가 정의되지 않았다.
Clojure 코드가 이식 가능한지는 그 코드가 닿는 Java API의 집합에 달려 있고, 그 집합은
Jolt가 shim한 부분집합과 비교해야만 판정된다.
독자는 자기 코드가 그 안에 있는지 알 방법이 없다.

`saityi`의 시도가 그 경계를 실물로 보여준다.
JVM·CLR·JS를 모두 대상으로 하는 크로스 플랫폼 Clojure 프로젝트를 돌려 봤는데 JVM의
`System/in`을 로드하려다 실패했고, 이어 Jolt가 리더 조건절(reader conditional)을
처리하는지, 항상 `:clj` 분기를 따를 의도인지 아니면 `:cljolt` 같은 것을 계획하는지
물었다[^saityi].

이 질문이 중요한 이유는 답이 생태계 전체에 영향을 주기 때문이다.
`:clj`를 따른다면 JVM 전용 코드가 그대로 들어와 실패하고, 새 키워드를 만든다면 모든
크로스 플랫폼 라이브러리가 분기를 하나 더 관리해야 한다.
어느 쪽도 홈페이지에는 없으며, “대부분 수정 없이 돈다”는 문장은 정확히 이 결정을
가리는 자리에 놓여 있다.
호환성을 주장하려면 통과한 테스트 스위트의 목록이 필요하고, 실패를 예고하려면 리더 조건절
정책이 필요하다.

### 첫 화면의 데모가 저자 스스로 권하지 않는 경로다

홈페이지 상단에는 브라우저에서 라이브로 평가되는 REPL이 있고, 그것이 Gambit 백엔드로
JavaScript로 컴파일된 jolt 자신이라고 설명한다.
다운로드 크기를 줄이려고 축소 빌드를 썼기 때문에 정규식이 빠져 있고 그것을 쓰려 하면
그렇다고 말한다는 안내까지 붙어 있다.
소개 문단도 “Chez는 네이티브, Gambit은 JavaScript용”이라고 적어 두 백엔드를 병렬로
제시한다.

그런데 저자의 입장은 다르다.
`kccqzy`가 JVM을 원하지 않는 사람이 있다는 것은 이해하지만 브라우저에서 돌리는
경우라면 Gambit 위의 Jolt가 순수 ClojureScript에 비해 무엇을 제공하느냐고
물었고[^kccqzy], `yogthos`는 브라우저에서 돌리려면 ClojureScript나 Squint를 확실히
권하겠다고 답했다.
Gambit으로 JS로 컴파일한 것은 Jolt에 완전히 다른 Scheme 백엔드로 컴파일될 수 있는
이식 계층이 있다는 점을 보여주는 예시였을 뿐이며, 기존 프런트엔드 솔루션과 경쟁할
의도가 없다고 밝혔다 — 방언을 가볍게 유지해야 크기와 기존 JS 생태계와의 마찰을
최소화할 수 있기 때문이라는 것이다[^yogthos-js].

그렇다면 홈페이지의 배치가 잘못되어 있다.
첫인상을 만드는 데모가 저자가 권하지 않는 사용처이고, 그 결과 방문자는 이 프로젝트의
용도를 “브라우저에서 도는 Clojure”로 오해할 수 있다.
같은 데모를 “이식 계층의 증명”으로 이름 붙이고 실제 권장 경로(단일 바이너리 빌드)를
앞세우는 편이 프로젝트의 목적과 맞는다.

## 인사이트

### 이식은 에이전트 시대에 값이 가장 크게 떨어진 노동이다

이 프로젝트가 두 달 만에 도달한 상태를 설명하는 것은 도구의 마법이 아니라 작업의 성격
이다.
언어 이식에는 세 가지가 모두 갖춰져 있다 — 참조 구현이라는 명세, 상류의 방대한 테스트
스위트라는 검증 수단, 그리고 라이브러리 테스트 통과라는 판정 기준.
저자가 스레드에서 밝힌 이유가 정확히 이 세 조건이었고, 이는 에이전트에게 가장 잘 맞는
작업 형태의 정의이기도 하다.

Lobste.rs에서 `sanxiyn`이 이것을 한 문단으로 요약했다.
코딩 에이전트가 생겼으니 사람들이 그것으로 무엇을 만드는지 궁금했는데 바로 이런 것 —
Java 표준 라이브러리의 상당 부분을 Scheme으로 재구현하는 일 — 이며, 명백히 가능하지만
예전에는 엄두를 내기 어려울 만큼 노동집약적이었던 작업이 이제 가능해졌다는 것이다.
코딩 에이전트에 정말 완벽한 사용 사례라고 그는 적었다[^sanxiyn].
저자의 답이 여기에 결정적인 한 마디를 더했다 — 손으로 해도 어렵지는 않았겠지만 순전한
고역(pure drudgery)이었을 것이고, 그래서 아마 아무도 전에 하지 않았을 것이라는 것이다.
다른 런타임에 방언을 구현할 때는 기존 라이브러리를 돌릴 수 없으니 만들 이유가 적다는
닭과 달걀 문제가 늘 있었다고 그는 덧붙였다[^yogthos-drudgery].

이 진술이 중요한 이유는 사라진 장벽의 정체를 특정하기 때문이다.
막고 있던 것은 난이도가 아니라 지루함이었고, 지루한 대량 작업의 비용이 떨어지면 “가능
하지만 아무도 하지 않던” 프로젝트 범주가 한꺼번에 열린다.
`near`가 Clojure를 새 호스트로 이식하는 일이 이렇게 인기 있어진 것이 흥미롭다며 let-go와
jank, 그 전의 babashka와 ClojureScript를 열거하고 자신은 이런 일이 벌어질 것이라 예상하지
못했다고 적은 것이 그 열림을 밖에서 관측한 기록이다[^near].

이 관찰의 2차 효과는 런타임 다양성의 급증이다.
과거에 언어를 다른 호스트에 재구현하는 일은 수년짜리 프로젝트였고, 그래서 생태계는
하나의 호스트에 묶여 있었다 — Clojure는 JVM에, Ruby는 MRI에, Python은 CPython에.
그 비용이 몇 달로 떨어지면 “이 언어를 이 런타임에” 조합이 저렴해지고, 같은 스레드에서
언급된 jank, Glojure, let-go, Jerboa처럼 방언이 동시에 여러 갈래로 늘어난다.

이득과 부담이 함께 온다.
선택지가 늘어나는 것은 배포 형태의 자유를 뜻하지만, 라이브러리 저자에게는 지원해야 하는
대상이 늘어나는 것을 뜻한다.
그래서 다음 단계의 병목은 구현이 아니라 조율 — 리더 조건절 키워드, 호환성 등급 표기,
공식 지원 목록 같은 생태계 규약 — 이 될 가능성이 높다.
`saityi`의 질문이 그 병목의 첫 신호였다.

### 신뢰의 근거는 사람에서 산출물로 이동해야 한다

이 스레드에서 가장 많이 소비된 논증은 “저자가 누구인가”였다.
Clojure 책을 쓴 사람이고, 20년 경력이고, 무명이 아니다 — 옹호도 이 축이고, 의심도
같은 축의 반대편(단일 저자, 2천 커밋, 최근 만들어진 조직의 19개 프로젝트)이었다.

이 축이 더 이상 작동하지 않는다는 것이 이 사례의 교훈이다.
코드 생산량이 저자의 시간에 비례하던 시절에는 커밋 수와 완성도가 곧 투입의 증거였고,
평판은 그 투입의 누적이었다.
생산량이 시간과 분리되면 두 신호가 모두 정보를 잃는다.
같은 스레드에서 `JerboaScheme`이 자기 프로젝트를 “882만 줄의 100% 바이브 코딩된
코드”라고 소개한 것은 이 신호 붕괴의 극단적 예시다[^JerboaScheme].

그래서 필요한 것은 새로운 종류의 신뢰 인프라이며, 그것은 평판이 아니라 검증 산출물이다.
어떤 상류 테스트 스위트를 어느 버전에서 통과했는지, 무엇이 미구현인지, 회귀 스위트가
무엇인지가 프로젝트 표면에 있어야 한다.
Jolt는 그 재료를 실제로 갖고 있으므로 — 지원 라이브러리 목록과 그 테스트 통과 —
이 사례는 결핍의 예가 아니라 배치의 예다.
앞으로 새 프로젝트를 평가할 때 물어야 할 것은 “누가 썼는가”가 아니라 “무엇으로
확인했는가”이며, 이는 언어 구현만의 이야기가 아니다.

### 호스트를 바꾸는 것은 제약을 없애는 일이 아니라 교환하는 일이다

Jolt는 JVM의 가장 유명한 제약 하나를 없앤다 — 일반 꼬리 호출 최적화의 부재.
그 대가로 무엇을 잃는지는 문서 여러 곳에 흩어져 있다.
`.getStackTrace`가 빈 배열이 되고, `BigDecimal`이 없어지고, 정규식이 다른 엔진의
방언이 되고, reflection과 `gen-class`/`proxy`가 사라진다.

잃는 항목의 공통점이 눈에 띈다.
전부 개발 초기에는 드러나지 않고 나중에 발견되는 영역이다 — 스택 트레이스는 장애가
났을 때, `BigDecimal`은 금액 계산을 정확히 해야 할 때, 정규식 방언 차이는 이미 있던
패턴을 옮길 때 문제가 된다.
반대로 얻는 항목(단일 바이너리, 빠른 시작, 꼬리 호출)은 첫날에 체감된다.
그래서 대체 런타임의 평가는 체감 시점이 다른 두 목록을 나란히 놓고 해야 하며, 기능
비교표는 구조적으로 얻는 쪽에 유리하게 기울어 있다.

실무 지침으로 옮기면 이렇다 — 대체 런타임을 검토할 때 물어야 할 질문은 “무엇을 지원
하는가”가 아니라 “무엇이 조용히 달라지는가”다.
Jolt의 문서가 이 점에서는 정직하다.
차이 항목을 세 줄로 명시하고 `.getStackTrace`의 이유까지 적어 두었으므로, 남은 문제는
그 정직함이 홈페이지의 약속 문장과 같은 자리에 놓여 있지 않다는 것뿐이다.

### Clojure 생태계의 진짜 자산은 JVM이 아니라 라이브러리의 호스트 의존도가 낮았다는 사실이다

Jolt가 ring, reitit, integrant, malli, hiccup을 돌릴 수 있는 이유는 Chez가 강력해서가
아니라 그 라이브러리들이 Java 표면을 얇게만 쓰기 때문이다.
Clojure 커뮤니티가 오랫동안 순수 함수와 데이터 지향 설계를 강조하고 interop을 필요한
곳에만 좁게 둔 관행이, 20년 뒤에 이식성이라는 형태로 환급된 셈이다.

이 패턴은 Jolt에만 해당하지 않는다.
babashka가 빠른 시작을 위해 GraalVM으로 갈 수 있었던 것, ClojureScript가 브라우저로
갈 수 있었던 것, jank가 C++로 갈 수 있는 것 모두 같은 자산에 기대고 있다.
호스트에 덜 의존한 라이브러리가 많은 생태계는 호스트를 갈아탈 수 있고, 그러지 못한
생태계는 호스트와 함께 늙는다.

여기서 지금 코드를 쓰는 사람에게 옮길 수 있는 판단이 나온다.
라이브러리를 만들 때 플랫폼 API 사용을 좁은 경계 안에 모아 두는 것은 추상화 취향의
문제가 아니라 미래의 이식 옵션을 만드는 일이다.
그 경계가 흐릿한 코드베이스는 새 런타임이 등장했을 때 선택지가 없고, 명확한 코드베이스는
누군가 shim 계층 하나를 만들어 주면 따라갈 수 있다.
이식 비용이 떨어진 시대에 이 차이는 전보다 훨씬 큰 값이 된다 — 이식하는 쪽은 저렴해졌는데
이식되지 못하는 코드는 여전히 이식되지 못하기 때문이다.
