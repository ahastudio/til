# 휠에서 컨테이너로: AI 가속기 변형 선택을 표준화하려는 시도

원문: [\[PyCon KR 2026\] More Variants, More Diversity for AI Accelerators](https://speakerdeck.com/achimnol/pycon-kr-2026-more-variants-more-diversity-for-ai-accelerators)

## 요약

Lablup의 CTO 김준기(`achimnol`)가 PyCon KR 2026에서 발표한 19장짜리 슬라이드이며
2026년 8월 15일에 공개됐다.
자기 소개 슬라이드가 배경을 밝힌다 — 2016년부터 Lablup CTO로
Backend.AI 코어 플랫폼과 분할 GPU 가상화 기술 개발을 이끌고 있고,
2015년부터 PyCon에서 발표해 왔으며,
`aio-libs` 컨트리뷰터로 `aiodocker`와 `aiomonitor`를 유지하고
`aiotools`와 `Callosum`을 작성했고,
KAIST에서 이종 가속기용 고성능 패킷 처리 프레임워크로 박사를 받았다.

목차가 발표의 구조를 정한다.
PEP 817과 825 휠 변형(Wheel Variants) 리캡은 2025년 발표의 후속이고,
이번 발표의 질문은 같은 아이디어를 컨테이너 세계로 가져올 수 있는지이며,
실험과 응용으로 Docker variant 플러그인과 Backend.AI 통합을 다룬다.

문제 정의는 두 줄이다.
플랫폼 태그는 OS 종류와 CPU 아키텍처와 glibc 버전(manylinux)만 다룰 수 있고,
가속기 벤더가 여러 곳이며 그 수가 늘어나는데
각 벤더가 자기만의 독특한 호환성 표와 규칙을 가질 수 있다는 것이다.
그래서 `pip install torch`를 그냥 할 수 없다.

PEP 817과 825의 2025년에서 2026년 사이 주요 변경도 표로 정리한다.
변형 ID에 `_upper_bound` 접미사가 붙었고,
속성이 0개인 경우를 `00000000` 변형으로 표현했던 것이
`null`로 바뀌면서 변형이 아닌 일반 휠보다 명시적으로 높은 우선순위를 갖게 됐다.
없었던 변형별 의존성이 도입되어 `dep1; "nvidia" in variant_namespace` 형태로
요구사항에 쓸 수 있고 `pylock.toml`과 통합된다.
ABI 지원도 새로 들어와 `abi_dependency` 예약 네임스페이스가 생겼으며
`abi_dependency :: torch :: 2.9` 같은 형태를 쓴다.

Packaging Summit 2026 소개가 이어진다.
Python 패키징 이해관계자 모임이며 `setuptools`·pip·conda·poetry·uv 같은 도구 개발자와
numpy·torch·xgboost처럼 배포하기 어려운 라이브러리의 관리자,
리눅스 배포판의 하류 패키지 관리자, 관심 있는 모든 사용자가 대상이다.
형식은 반일 워크숍으로 선정 주제 발표 3~4개 뒤에
라이트닝 토크와 라운드테이블 토론이 붙으며,
언급된 이름은 Pradyun Gedam과 Jannis Leidel과 C.A.M. Gerlach다.
발췌로 Emma Smith의 “Wheel 2.0과 더 나은 압축 재검토”를 소개한다 —
포맷을 바꾸면서 기존 CI/CD를 깨지 않는 방법으로
PEP 777을 통한 최소 변경과 개별 변경마다 서브 PEP를 두는 방식,
그리고 인덱스 제공자가 전환 시점을 정할 수 있는 하위 호환성을 든다.
Zstandard 채택의 기대 효과는 상위 1,000개 프로젝트의 크기 25% 감소와
트래픽 100PB, 압축 해제 지연 36년치 절감이고,
pip 같은 도구가 C 확장 추가를 꺼린다는 난점은
Python 3.14가 zstd를 표준 라이브러리에 포함하면서 풀렸다고 적는다.
제안은 ZIP 안에 `tar.zst`를 비압축으로 저장해 하위 호환을 지키는 것이다.

컨테이너 쪽 현황 진단이 이 발표의 전환점이다.
OCI 이미지 인덱스의 플랫폼 변형은 Go의 빌드 타깃 변형 표현을 차용했고
사양 확장 논의가 있지만 가속기에 대한 고려가 없다.
Backend.AI도 다른 많은 시스템처럼 커스텀 태그 규칙을 채택했는데,
`pytorch:2.12.0-ubuntu24.04-py312`와 `pytorch:2.12.0-ubuntu24.04-cuda13-py312`와
`pytorch:2.12.0-ubuntu22.04-atom-py313` 같은 형태다.
불만도 세 줄로 적어 둔다 — 클라이언트가 수동으로 선택해야 하고,
벤더 간 태그 명명 표준이 없고,
여러 기능에 호환되는 이미지는 태그가 너무 길어진다는 것이다.
최신 기술로는 쿠버네티스의 DRA(Dynamic Resource Allocation)를 든다.
v1.35에서 안정화됐고 Prioritized List도 v1.35에서 안정,
`DRAListTypeAttributes`는 v1.36에서 알파이며
CEL 표현식으로 매칭 조건을 일반화하고 타입 있는 값을 도입했다.
그러나 복잡성이 여전히 사용자에게 남는다고 평가한다 — 수동 CEL 작성이다.

핵심 유추는 두 장에 걸쳐 제시된다.
패키지 인덱스가 변형 속성을 갖고, 클라이언트가 로컬 변형 공급자에서
호스트의 CPU·GPU·NPU 기능을 받아 맞는 휠을 내려받는 그림에
컨테이너 레지스트리를 나란히 덧붙여 같은 구조를 보여 준다.
속성 예시가 구체적이다 — `x86_64 :: level :: v3`,
`nvidia :: cuda_version :: 12.8`, `nvidia :: sm_arch :: 120_real`,
`rebellions :: arch :: atom_max`, `furiosa :: arch :: renegade`,
`hyperaccel :: arch :: bertha`다.

실험은 `lablup/docker-variant`다.
두 구성 요소로 되어 있는데 클라이언트 쪽 `docker variant` CLI 플러그인과
`/v2/<name>/_variants/<version>` API를 추가하는 서버 쪽 레지스트리 프록시이며,
프록시는 `variant-proxy --upstream registry.internal:5000` 형태로 띄운다.
구현된 공급자 플러그인은 `nvidia-smi` CLI 기반의 nvidia와
`golang.org/x/sys/cpu`의 기능 감지기에 기반한 x86_64와 aarch64다.
변형별 이미지를 만들 때는 Dockerfile에 라벨을 붙인다.

```dockerfile
LABEL dev.pep817.variant-label="cu128" \
      dev.pep817.variant.nvidia.cuda_version_lower_bound="12.8"
```

`ARG` 지시자로 라벨과 빌드 단계를 파라미터화할 수 있고,
`docker variant push`로 올린 뒤 `docker variant pull`로 받으면
변형이 선택되고 원래 태그와 변형 태그가 함께 붙는다.

응용의 동기는 Backend.AI의 스케줄링 문제다.
주어진 워크로드에 호환되는 가속기를 가진 노드를 골라야 하는데,
GPU 세대마다 컴퓨트 능력과 SM 아키텍처가 다르고
워크로드 호환성은 컨테이너 이미지의 CUDA 런타임 버전에서 온다.
그리고 멀티노드 작업, 즉 갱 스케줄링을 지원해야 한다 —
`cuda.device`나 `cuda.shares` 같은 단일 리소스 슬롯으로는
장치별·워크로드별 변형을 구분할 수 없고,
하나의 워크로드에 속한 모든 서브 컨테이너가
여러 노드에 걸쳐 동일하거나 호환되는 하드웨어 조합을 가져야 한다.

정리 슬라이드가 세 줄과 향후 과제를 남긴다.
휠 변형은 플랫폼 태그를 다벤더 가속기 변형으로 확장하며 사양이 활발히 갱신 중이고
2026년 판에는 변형별 의존성 같은 실용적 확장이 들어왔다.
Docker variant 플러그인은 기존 컨테이너 생태계에 대한 단순한 확장이며,
Backend.AI는 에이전트-디바이스 레지스트리 테이블에서 변형 데이터 모델을 재사용한다.
향후 과제는 변형을 인식하는 컨테이너 이미지를 만들고 배포하는 것 —
괄호로 라벨링을 자동화할 수 있을지 묻는다 — 그리고
AI 칩 벤더의 공급자 참여를 찾고 있다는 것이다.

발표에 인용된 외부 사실은 확인된다.
PEP 777은 “How to Re-invent the Wheel”, PEP 817은 “Wheel Variants: Beyond Platform Tags”,
PEP 825는 “Wheel Variants: Package Format”이고,
Python 3.14의 zstd 편입은 PEP 784로 이뤄져 `compression.zstd` 모듈이 문서에 있다.
OCI 사양 논의는 `opencontainers/image-spec#1216`
“Identifying Platform-Specific OCI Artifacts”이며 아직 열려 있다.
`lablup/docker-variant`는 Go로 작성된 Apache-2.0 저장소이고
2026년 7월 27일에 만들어져 8월 9일에 마지막으로 푸시됐으며 스타는 1개다.
19장 중 세 장은 그림뿐이어서 텍스트가 추출되지 않는다.

## 분석

### 문제를 감지의 문제가 아니라 표현력의 문제로 정의한 것이 이 발표의 축이다

첫 문제 슬라이드의 두 문장이 이후 모든 설계를 결정한다.
플랫폼 태그가 OS와 CPU 아키텍처와 glibc까지만 표현할 수 있다는 것,
그리고 가속기 벤더마다 호환성 표와 규칙이 다르다는 것이다.
이것은 하드웨어를 알아내지 못하는 문제가 아니라 알아낸 것을 적을 칸이 없는 문제다.

이 구분이 해법의 모양을 정한다.
감지의 문제라면 답은 더 나은 탐지 코드이고,
표현력의 문제라면 답은 표기 체계다.
그래서 이 발표의 산출물이 감지기가 아니라
네임스페이스와 속성과 값의 세 칸으로 된 문법이며 —
`nvidia :: sm_arch :: 120_real` — 감지는 공급자 플러그인에 위임된다.

대조 사례가 이 선택의 의미를 분명히 한다.
NumPy는 여러 CPU 패밀리용으로 코드를 여러 번 컴파일해
런타임에 디스패치하는 방식으로 같은 문제를 우회했고,
[그 우회가 왜 필요했는지는 앞선 논의에서 다뤄졌다](../python/pip-install-torch.md).
런타임 디스패치는 배포물 하나에 모든 경우를 넣는 방식이고,
변형은 선택 시점을 설치·풀 시점으로 옮긴다.
벤더가 두세 곳일 때는 전자가 단순하지만,
벤더 수가 늘고 각자 축이 다르면 조합이 곱셈으로 늘어나
하나의 배포물에 담는 것이 물리적으로 불가능해진다.
1GB짜리 PyTorch 휠이 그 곱셈의 중간 결과다.

### 두 생태계에서 같은 구조를 발견한 것이 실제 기여다

슬라이드 13과 14의 관계가 이 발표에서 가장 정보량이 많은 부분이다.
13장은 패키지 인덱스와 클라이언트와 로컬 변형 공급자로 된 그림이고,
14장은 같은 그림 옆에 컨테이너 레지스트리를 그대로 복사해 붙인다.
바뀐 것은 명사뿐이다 — 인덱스가 레지스트리로, `pip install`이 `docker pull`로.

이 동형성이 우연이 아닌 이유가 있다.
두 생태계 모두 원격 저장소가 여러 후보를 갖고 있고,
클라이언트만이 자기 하드웨어를 알고,
그 둘을 잇는 매칭 규칙이 필요하다는 구조를 공유한다.
그리고 두 생태계 모두 지금까지 그 매칭을 문자열 관행으로 처리해 왔다 —
휠은 플랫폼 태그, 컨테이너는 이미지 태그다.

구조가 같으면 해법도 옮길 수 있다는 것이 이 발표의 주장이며,
그 주장은 라벨 네임스페이스에서 문자 그대로 구현된다.
컨테이너 라벨의 접두사가 `dev.pep817.variant`다 —
Python 패키징 PEP의 번호가 OCI 라벨 키에 들어가 있다.
표준 하나를 두 생태계가 공유한다는 의도를 이보다 직접적으로 표시할 방법은 없고,
동시에 그 의도가 아직 어느 쪽에서도 승인되지 않았다는 사실도 함께 드러낸다.

### OCI와 DRA를 서로 다른 이유로 기각한 것이 설계 제약을 만든다

기존 대안 두 개에 대한 평가가 각각 다른 축에서 내려진다.
OCI의 플랫폼 변형은 Go 빌드 타깃 표현을 차용했으므로
가속기를 표현할 어휘가 없다 — 표현력의 부족이다.
쿠버네티스 DRA는 CEL 표현식으로 조건을 일반화할 수 있으므로 표현력은 충분한데,
복잡성이 사용자에게 남는다고 평가한다 — 사용성의 부족이다.

두 기각을 합치면 요구사항이 나온다.
가속기를 표현할 수 있어야 하고, 사용자가 식을 쓰지 않아야 한다.
`docker-variant`의 설계가 정확히 그 두 조건을 겨냥한다 —
어휘는 벤더 네임스페이스로 열어 두고,
값은 공급자 플러그인이 `nvidia-smi`와 CPU 기능 감지기로 자동 수집하며,
사용자가 하는 일은 `docker variant pull` 한 줄이다.

이 구성은 DRA를 대체하지 않고 다른 층에 놓인다는 점도 봐야 한다.
DRA는 스케줄러가 노드를 고르는 문제를 다루고,
변형은 고른 노드에서 어떤 이미지를 받을지를 다룬다.
발표가 둘을 나란히 비교한 것은 같은 문제를 푸는 경쟁자로 봤기 때문인데,
실제로는 보완 관계일 가능성이 높고 그 관계가 명시되지 않는다.

### 자사 제품의 관행을 문제의 증거로 내놓는 구성이 논증의 신뢰를 만든다

컨테이너 쪽 현황을 진단하는 슬라이드에서
저자는 Backend.AI가 다른 많은 시스템처럼 커스텀 태그 규칙을 채택했다고 적는다.
`pytorch:2.12.0-ubuntu22.04-atom-py313` 같은 태그를 예시로 들고,
수동 선택과 표준 부재와 과도한 태그 길이라는 세 가지 불만을 자기 이름으로 나열한다.

이 배치가 발표의 성격을 정한다.
벤더 소속 발표자가 표준을 제안할 때 흔한 형태는
자기 제품이 이미 잘 풀었다고 말하고 그 방식의 표준화를 권하는 것이다.
여기서는 반대로 자기 제품의 현재 방식이 우회이며 불만스럽다고 먼저 인정한다.

그 인정이 뒤의 요청을 가능하게 한다.
마지막 슬라이드가 AI 칩 벤더의 공급자 참여를 구하는 것으로 끝나는데,
자기 우회 방법을 표준으로 밀지 않았기 때문에
다른 벤더에게 하는 요청이 자사 규격 채택 요구로 읽히지 않는다.
`dev.pep817` 접두사를 쓴 것도 같은 성격의 선택이다 —
소유권을 Lablup이 아니라 Python 패키징 PEP에 둔 표기다.

## 비평

### 설계는 다벤더를 전제하는데 구현은 단일 벤더와 CPU에 머물러 있다

슬라이드 13과 14의 속성 예시에는 다섯 개 벤더 네임스페이스가 등장한다 —
nvidia와 rebellions와 furiosa와 hyperaccel과 x86_64다.
그런데 구현된 공급자 플러그인은 nvidia와 x86_64·aarch64뿐이다.
Rebellions와 FuriosaAI와 HyperAccel은 그림에만 있다.

이 격차가 이 제안의 실제 위험이 있는 자리다.
변형 체계의 값은 벤더가 자기 하드웨어의 속성을 기계가 읽을 수 있게 내놓는 데서 나오고,
그것이 없으면 남는 것은 nvidia 하나를 위한 태그 자동화다.
그 경우 문제 정의 — 벤더가 여러 곳이고 늘어난다 — 가 무효화되지는 않지만,
해법의 값이 크게 줄어든다.

그리고 참여의 유인이 논의되지 않는다.
공급자 플러그인을 만든다는 것은 자기 칩의 세대별 호환성 규칙을
공개된 어휘로 기술하는 일이며, 그 표가 경쟁 정보일 수 있다.
NVIDIA에게는 이미 `nvidia-smi`로 노출된 정보이므로 비용이 없지만,
후발 벤더에게는 아직 정리되지 않았거나 공개하고 싶지 않은 정보일 수 있다.
“벤더 참여를 찾고 있다”는 한 줄이 마지막 슬라이드에 있는데,
왜 참여하는 것이 그들에게 이득인지에 대한 논거는 어디에도 없다.

가장 설득력 있는 논거가 이미 발표 안에 있다는 점이 아쉽다.
표기 체계에 이름이 없으면 사용자가 그 하드웨어를 고를 방법도 없으므로,
참여는 호의가 아니라 유통 채널 확보다.
그 문장이 요청 슬라이드에 있었다면 요청의 성격이 달라진다.

### “라벨링을 자동화할 수 있을까”가 향후 과제가 아니라 채택 조건이다

정리 슬라이드의 향후 과제에 괄호로 들어간 질문이
실은 이 제안의 가장 어려운 부분이다.
지금 구조에서 변형 라벨은 이미지를 만드는 사람이 Dockerfile에 손으로 적는다 —
`dev.pep817.variant.nvidia.cuda_version_lower_bound="12.8"`이다.

휠과 컨테이너의 비대칭이 여기서 나타난다.
휠은 빌드 시스템이 컴파일 플래그와 링크된 라이브러리를 알고 있으므로
변형 속성을 산출물에서 추론할 여지가 있다.
컨테이너 이미지의 호환성은 이미지 안에 설치된 수십 개 패키지의 조합에서 나오고,
그 조합을 이미지 빌드가 끝난 뒤에 역산하는 것은 훨씬 어렵다.
CUDA 12.8 런타임이 들어 있다는 사실을 적는 것과
그 이미지가 실제로 `sm_120`에서 도는지는 다른 질문이다.

수동 라벨의 위험이 태그의 위험보다 크다는 점이 더 중요하다.
`ubuntu22.04-atom-py313`이라는 태그가 틀렸으면 사람이 읽다가 의심하고 확인한다.
라벨은 기계가 신뢰하고 자동으로 고르는 값이므로,
틀린 라벨은 조용히 잘못된 이미지를 배포한다.
발표가 태그 방식의 문제로 “수동 클라이언트 선택”을 들었는데,
새 방식은 선택을 자동화하는 대신 신고를 수동으로 남겨 둔 셈이다.

최소한 필요한 것은 라벨의 검증 경로다.
빌드 시점에 라벨이 주장하는 호환성을 실제로 확인하는 단계 —
선언한 하한 버전에서 임포트 테스트를 돌리는 정도 — 가 있어야
자동 선택이 신뢰를 얻는다.
발표에는 라벨을 붙이는 방법만 있고 라벨이 맞는지 확인하는 방법이 없다.

### 갱 스케줄링 요구가 1:1 매칭 모델로는 풀리지 않는다

응용 동기 슬라이드는 요구를 정확하게 적어 두었다.
하나의 워크로드에 속한 모든 서브 컨테이너가
여러 노드에 걸쳐 동일하거나 호환되는 하드웨어 조합을 가져야 한다는 것이다.

그런데 변형 선택 모델은 클라이언트와 호스트의 1:1 매칭이다.
그림에서도 클라이언트 하나가 자기 호스트의 속성을 읽어
자기에게 맞는 변형을 받는 구조이며, 그것이 이 설계의 단순함의 원천이다.
노드 A가 `sm_120`이고 노드 B가 `sm_90`인 클러스터에서
각 노드가 자기에게 맞는 변형을 고르면 서로 다른 이미지가 실행되고,
그것은 갱 요구의 정반대다.

필요한 것은 집합 제약 충족이다 —
노드 집합 전체에 공통으로 맞는 변형 하나를 고르는 문제이며,
경우에 따라 어느 노드에서는 차선의 변형을 받아들여야 한다.
그 계산은 풀 시점의 클라이언트가 할 수 없고 스케줄러가 해야 한다.
발표는 Backend.AI가 에이전트-디바이스 레지스트리 테이블에서
변형 데이터 모델을 재사용한다고 적어 이 문제를 인식하고 있음을 보이지만,
어떻게 집합 제약을 푸는지는 나오지 않는다 —
그리고 그 응용 부분의 슬라이드가 텍스트 없이 그림만 있는 세 장 중 하나다.

이 공백이 중요한 이유는 여기가 변형과 DRA의 관계가 정해지는 자리이기 때문이다.
집합 제약은 DRA의 CEL 표현식이 다루려는 문제와 같은 성격이고,
발표는 DRA를 복잡성 때문에 기각했다.
그러면 그 복잡성을 어디서 감당할지가 남는데,
플랫폼이 대신 감당한다는 것이 실질적인 답으로 보이며 그 답이 명시되지 않았다.

### 레지스트리 프록시라는 선택이 표준화 경로와 어긋날 수 있다

`variant-proxy`는 업스트림 레지스트리 앞에 서서
`/v2/<name>/_variants/<version>`라는 새 엔드포인트를 제공한다.
실험 구현으로는 영리한 우회다 —
레지스트리 구현체를 고치지 않고도 변형 목록 조회가 가능해진다.

그런데 이 선택에는 대가가 있다.
표준이 되려면 결국 레지스트리들이 그 API를 받아들여야 하는데,
프록시가 동작하는 동안에는 받아들일 압력이 생기지 않는다.
프록시를 세운 조직 안에서만 작동하고,
공용 레지스트리에서 변형 이미지를 받는 경로는 열리지 않는다.
발표가 “기존 컨테이너 생태계에 대한 단순한 확장”이라고 자평하는데,
단순함의 근거가 표준을 건드리지 않은 것이라면
그 단순함이 곧 확산의 상한이 된다.

대안의 트레이드오프가 다뤄지지 않은 것도 아쉽다.
라벨 자체는 이미 OCI 표준의 일부이므로,
클라이언트가 매니페스트를 훑어 라벨을 읽고 고르는 방식도 원리적으로 가능하다.
그 경로는 프록시가 필요 없는 대신 조회가 느리고 요청 수가 늘어난다.
어느 쪽이 왜 나은지는 실험의 핵심 판단인데,
슬라이드에는 프록시 구조도만 있고 그 선택의 이유가 없다.

## 인사이트

### 가속기 다양성의 해법은 감지에서 표기로, 다시 협상으로 이동한다

이 문제의 대응 방식에 세 단계가 있고 발표는 두 번째 단계에 있다.
첫 단계는 런타임 감지와 디스패치로, NumPy가 여러 CPU 패밀리용 코드를
하나의 바이너리에 넣고 실행 시점에 고르는 방식이다.
두 번째는 배포 시점 표기와 매칭이며, 변형이 그것이다.

세 번째 단계가 필요해지는 조건이 이미 이 발표 안에 있다.
갱 스케줄링 요구가 그것이며, 하나의 호스트가 아니라
호스트 집합에 공통으로 맞는 것을 골라야 하는 순간
문제는 매칭이 아니라 협상이 된다.
같은 이동이 다른 곳에서 이미 일어났다 —
HTTP는 확장자에서 `Accept` 헤더 기반 콘텐츠 협상으로 갔고,
TLS는 고정 알고리즘에서 사이퍼 스위트 협상으로 갔고,
패키지 관리는 버전 지정에서 의존성 해결기로 갔다.

그리고 그 이동에는 정해진 대가가 따른다.
협상 단계에 들어가면 해결기가 생기고, 해결기는 느려지고,
결과가 왜 그렇게 나왔는지 설명하기 어려워진다.
pip의 의존성 해결기가 겪은 일이 그것이며,
변형에도 같은 순서가 올 것으로 보인다 —
변형별 의존성이 2026년 판에 들어왔다는 사실이
이미 그 방향의 첫 걸음이다.
속성 매칭에 의존성 그래프가 얹히면 그것은 정의상 제약 충족 문제다.

그러므로 이 표준의 장기 설계에서 가장 중요한 결정은 어휘가 아니라
해결 실패를 어떻게 설명할지다.
맞는 변형이 없을 때 사용자가 받는 메시지가
“호환되는 변형이 없습니다”인지
“`nvidia :: cuda_version`이 12.8 이상이어야 하는데 12.4입니다”인지가
채택률을 정한다.

### 한국 칩 벤더 세 곳이 예시 속성에 등장한 것은 문서상의 사건이 아니다

슬라이드의 속성 예시에 `rebellions :: arch :: atom_max`와
`furiosa :: arch :: renegade`와 `hyperaccel :: arch :: bertha`가 있다.
표준 초안의 예시에 이름이 오르는 일은 사소해 보이지만
표준의 역사에서 예시는 특별한 위치를 갖는다.

예시는 구현의 첫 테스트 케이스가 되고, 문서의 기본 어휘가 되고,
나중에 참여하는 사람이 복사하는 원형이 된다.
문자 인코딩 표준에서 예시로 든 문자가 폰트 지원의 우선순위가 됐고,
HTTP 명세의 예시 헤더가 구현체의 기본 처리 경로가 됐다.
표기 체계가 시장 접근을 매개하는 구조에서
표기에 이름이 없다는 것은 사용자가 그 하드웨어를 고를 수 없다는 뜻이며,
그것은 성능이나 가격과 무관한 유통의 문제다.

이 관점에서 이 발표는 앞선 논의의 공백을 메우는 시도로 읽힌다.
[Wheel Next를 다룬 문서의 비평 중 하나가
한국 AI 생태계의 참여 부재였는데](../python/pip-install-torch.md),
이 발표는 한국 기업의 CTO가 컨테이너 쪽 확장을 직접 구현해
국내 NPU 세 곳의 네임스페이스를 예시에 넣은 것이다.

다만 예시에 이름이 오른 것과 벤더가 공급자 플러그인을 유지하는 것은 다르다.
플러그인은 칩 세대가 나올 때마다 갱신해야 하는 지속 노동이고,
그 노동을 누가 지는지가 정해지지 않으면 예시는 예시로 남는다.
그래서 이 시도의 다음 단계는 표준 논의가 아니라
벤더 세 곳 중 한 곳이 자기 플러그인을 자기 저장소에서 유지하기 시작하는 것이며,
그 한 건이 생기면 나머지의 비용 계산이 바뀐다.

### 컨테이너 태그는 타입 없는 문자열이었고, 그 사실이 이제 비용으로 청구된다

`pytorch:2.12.0-ubuntu22.04-atom-py313`을 보면 네 가지 사실이 하이픈으로 이어져 있다.
프레임워크 버전과 배포판과 가속기와 파이썬 버전이며,
순서와 구분자와 생략 규칙은 조직마다 다르고 아무도 검증하지 않는다.
사실상 타입 없는 문자열에 여러 차원을 인코딩한 것이다.

변형 라벨이 하는 일은 그 문자열을 구조화된 데이터로 바꾸는 것이다.
`(네임스페이스, 속성, 값)` 세 칸으로 나누고,
`_lower_bound`와 `_upper_bound` 같은 비교 의미를 붙이고,
`DRAListTypeAttributes`가 도입한 것처럼 값에 타입을 준다.
같은 전환이 파일 확장자에서 MIME 타입으로,
`User-Agent` 문자열 파싱에서 Client Hints로 가는 경로에서 반복됐다.

그 전환들에서 공통으로 관찰되는 것이 비용과 이득의 비대칭이다.
구조를 도입하는 비용은 생산자가 지고 —
이미지를 만드는 사람이 라벨을 정확히 붙여야 한다 —
이득은 소비자가 받는다.
그래서 이 전환은 항상 늦게 오고,
소비자 쪽 도구가 구조를 요구하기 시작한 뒤에야 생산자가 움직인다.
`User-Agent`가 20년 넘게 문자열 파싱으로 버틴 이유가 그것이다.

이 비대칭이 이 제안의 채택 순서를 예측하게 한다.
개별 이미지 제작자가 자발적으로 라벨을 붙이는 일은 늦게 오고,
먼저 움직이는 것은 이미지를 대량으로 만드는 주체다 —
프레임워크 공식 이미지, 클라우드의 관리형 이미지,
그리고 Backend.AI처럼 플랫폼이 사내에서 이미지를 생성하는 경우다.
발표의 응용 절이 자사 플랫폼인 것이 우연이 아니라
이 순서에서 가장 앞에 올 수 있는 자리이기 때문이다.

### 이 제안의 성공 조건은 표준 통과가 아니라 기본 동작이 되는 것이다

컨테이너 태그 관행은 어떤 표준 기구도 승인하지 않았는데 모두가 쓴다.
이유는 하나다 — `docker pull nginx:latest`가 아무 설정 없이 동작하기 때문이다.
관행이 표준을 이긴 사례이며, 이 발표가 상대하는 것이 그 관행이다.

그런데 지금 제안의 진입점은 `docker variant pull`이라는 별도 명령이다.
별도 명령은 아는 사람만 쓰고, 아는 사람만 쓰는 기능은
이미지 제작자에게 라벨을 붙일 이유를 주지 못한다.
라벨이 없으면 명령이 쓸 곳이 없고 명령을 안 쓰면 라벨이 붙지 않는 순환이며,
플러그인 저장소의 스타가 1개라는 사실이 그 순환의 현재 위치를 보여 준다.

휠 쪽은 이 문제를 다른 경로로 풀고 있다.
PEP를 통해 pip 자체의 동작에 변형 선택을 넣으려는 것이며,
그러면 사용자가 아무것도 배우지 않아도 `pip install torch`가 맞는 것을 받는다.
컨테이너 쪽에는 그에 해당하는 경로가 없다 —
CLI 플러그인은 정의상 선택적이고, OCI 사양 논의는 아직 열려 있는 이슈다.

그러면 현실적인 채택 경로가 둘로 좁혀진다.
하나는 Docker나 containerd 상류에 들어가 `docker pull`의 기본 동작이 되는 것이고,
다른 하나는 플랫폼이 사용자를 대신해 고르는 것이다.
후자는 사용자가 변형의 존재를 모르는 채 이득을 보는 구조이며,
Backend.AI 통합이 사실상 그 답이다.
그렇다면 이 발표의 제목이 약속하는 것 —
가속기를 위한 더 많은 다양성 — 이 실현되는 첫 장소는
공용 레지스트리가 아니라 관리형 플랫폼 안쪽이고,
표준화는 그 뒤에 따라오는 순서가 된다.
