# Replit이 샌드박스 엔진을 컨테이너에서 microVM으로 다시 쓰며 격리 경계를 커널 아래로 옮겼다

원문: [Inside Replit’s New Sandbox Engine, Part 1: The Path to MicroVMs](https://frontier.replit.com/sandbox-engine-microvms-part-1/)

HN 토론: <https://news.ycombinator.com/item?id=50396834> (97점, 38개 댓글)

GN 토론: <https://news.hada.io/topic?id=36828>

## 요약

Replit의 Compute Platform 팀이 2026년 11월 4일에 낸 엔지니어링 글이다.
Connor Brewster, Jason Dellaluce, Adnan Abdulhussein, Luis Hector Chavez와 팀이
썼고, 2부에서 쿠버네티스 위에서 수만 개의 microVM을 다루는 방법을 다룬다고
예고한다.
이 문서는 글만 읽고 정리했으며 글이 인용한 사고나 보고서, CVE 문서는 열어 보지
못했다.
성능과 보안에 관한 수치는 모두 Replit이 자사 시스템에 대해 한 주장이다.

Replit은 10년 가까이 샌드박스를 운영해 왔고, 에이전트가 코딩 없이 앱을
만들도록 같은 샌드박스를 쓴다고 한다.
최근 몇 달 사이 샌드박스 엔진을 통째로 다시 써서 보안, 기능, 클라우드 간
이식성을 높였고, 고객의 AWS, Google Cloud, Azure에 Replit을 설치하는 고객
클라우드 사용 상품(Bring Your Own Cloud)도 이 엔진 위에 있다고 한다.
수억 개의 프로젝트를 데이터 손실 없이 옮겼다고 주장한다.
2025년 11월에 재작성을 시작해 이듬해 2월부터 내부에서 썼고, 이후 몇 달 동안
다듬고 배포했다는 일정이다.

옛 엔진은 Google Compute Engine VM에 퍼진 Docker 안의 상태 없는 코드 실행이었고,
여기에 영구 작업 공간, 공개 엔드포인트, 캐시된 Nix 패키지, 지역 클러스터,
디스크를 즉시 복제하는 무한 저장소가 쌓였다.
도커에서 microVM으로 포팅하기보다 처음부터 다시 만드는 쪽이 쉽다고 판단했다.
새 샌드박스는 KVM으로 호스트와 다른 고객의 작업에서 격리된 microVM이고,
그 안에서 runc 컨테이너가 프로세스를 나눈다.
가상 머신 모니터(VMM)는 Cloud Hypervisor를 골랐다.
Firecracker와 rust-vmm 구성 요소를 공유하면서 virtiofs, 투명 거대 페이지,
장치 핫플러그, 라이브 마이그레이션을 갖추었고, 중첩 가상화로 개발 환경 안에서
VM을 띄우는 일도 된다는 이유다.
핫플러그와 메모리 스냅숏으로 예열된 VM에 고객 디스크를 그때그때 붙이고,
스냅숏의 이식성을 높이려고 Cloud Hypervisor를 자체 패치했다고 한다.
microVM 안의 최소 init이 컨테이너를 시작하고 감시하며, 호스트는 IP 네트워크
없이 vsock 위의 gRPC로 이와 통신한다.

보안 설계의 이유는 최근 1년 사이 리눅스 커널의 지역 권한 상승(LPE) CVE가
많았다는 것이다.
글은 Copy Fail, Dirty Frag 두 종류, Fragnesia 같은 이름을 나열하며 AI가 발견
속도를 높였다고 말한다.
옛 런타임은 호스트 커널을 공유해서 도달 가능한 취약점 하나가 컨테이너 탈출로
이어질 수 있었고, microVM에서는 게스트 커널이 뚫려도 가상화 경계를 따로
넘어야 한다는 설명이다.
각자의 커널이 있으니 공유 커널에서는 안전하게 줄 수 없던 권한을 요구하는
도커도 지원한다.

글이 설명하는 방어층은 다음과 같다.

- 권한과 커널 표면: 역할별로 네임스페이스, seccomp, 장치 접근, capability를 설정한다. VMM은 capability가 없는 비특권 신원으로 돈다. 게스트 커널은 tinyconfig에서 시작해 Bluetooth, 무선, USB, 디스플레이 드라이버를 뺐고, 필요한 드라이버는 내장하며 게스트 초기화 때 모듈 로딩을 끈다.
- 커널 CVE 감사: 2026년 6월 1일부터 11월 4일 사이 공개된 Linux CNA CVE 6,211개를 감사해 5,969개(96.1%)를 피했다고 한다. 4,375개(70.4%)는 공개 전에 수정을 반영했고 676개(10.9%)는 설정으로 해당 코드를 제외했다. 적어도 15개는 Linux CNA나 Red Hat이 LPE를 가능하게 한다고 명시한 것이라고 한다.
- 실행 중 감시: eBPF가 프로세스 실행, 파일 접근, 네트워크 활동을 관찰하고 LSM 훅이 금지 동작을 막는다. 샌드박스마다 호스트와 게스트 양쪽에서 도는 보안 감시기가 있고, 변경이 병합된 뒤 15분 안에 모든 운영 샌드박스에 핫리로드된다고 한다.
- 네트워크: 샌드박스마다 자체 네트워크 네임스페이스와 라우팅 표가 있고 VRF가 겹치는 사설 주소를 나눈다. 이그레스 정책은 게스트 밖의 호스트 쪽 프록시가 집행하며 TLS 핸드셰이크의 호스트 이름만 보고 페이로드는 복호화하지 않는다. 가상 NIC 속도 제한도 게스트 밖에서 건다.
- 자격 증명과 공급망: 자격 증명 중개자가 요청을 전달하며 업스트림 자격 증명을 붙여서 작업이 계정 API 키를 직접 받지 않는다. npm과 pip 요청은 레지스트리 방화벽을 지나며 알려진 악성 의존성은 즉시 차단된다.

저장소는 원격 블록 저장 서비스가 요구 시 데이터를 가져오므로 큰 작업 공간을
시작해도 전체 파일시스템을 내려받지 않는다.
이를 위해 vhost-user virtio-blk 백엔드를 직접 짰고, 한 호스트 커널에서
수백 개의 네트워크 블록 장치를 관리하며 겪은 교착과 노드 장애를 피한다고
한다.
이 컴포넌트는 Claude Sonnet 4 시절 AI가 전부 쓴 첫 컴포넌트 중 하나로
다섯에서 일곱 번의 반복을 거쳤다고 밝힌다.
샌드박스 하나를 얻는 데 약 500ms가 걸리며 디스크를 붙이고 마운트하고 보조
서비스를 병렬로 구성하는 것까지 포함한 수치이고, 빈 VM을 부팅하는 것은 훨씬
짧다고 한다.
시스템은 몇 달 동안 운영에서 건강하게 돌았다고 한다.

## 분석

### 격리 경계를 옮긴 이유는 공유 커널이라는 한 가지 전제에 있다

글의 논증은 한 문장으로 줄일 수 있다.
컨테이너는 호스트 커널을 공유하므로 커널 취약점 하나가 탈출로 이어질 수
있고, microVM은 그 공유를 없앤다는 것이다.
이 주장은 새롭지 않지만 글은 시기와 연결한다.
LPE CVE가 많은 해이고, 발견 속도가 AI로 빨라졌으며, 에이전트가 자율적으로 코드를
실행하는 환경이 늘었다는 세 가지가 겹쳐 공유 커널의 위험이 커졌다고 본다.
글이 경계를 옮기고도 컨테이너를 microVM 안에 그대로 둔 것은 역할별 권한 분리가
여전히 필요하기 때문이라는 설명이다.

HN에서 schainks는 이것이 OTP의 감독 트리와 프로세스 격리를 가장 아래의 가상화
계층까지 밀어 넣은 것이냐고 물었다.[^schainks]
tptacek은 그것은 과한 해석이라며 이야기는 단순하다고 답했다.
대부분의 네오클라우드 업체처럼 Docker나 리눅스 컨테이너를 격리 수단으로 썼고
그것은 안전한 적이 없었으며, 이제 실제 KVM 격리를 사용자 규모로 확장하는 법을
찾았다는 것이다.[^tptacek-shared]
그는 클라우드 업체를 고를 때 내 워크로드가 믿지 못할 다른 테넌트와 커널을
공유하는 모드가 있느냐고 묻고, 그렇다는 답이 나오면 탈락시키라고 권했다.

### 이 설계는 격리를 한 겹이 아니라 여러 겹으로 쌓는 방식이다

글이 나열한 방어는 하나의 보안 기능이 아니라 서로 다른 층이다.
게스트 안에서 권한을 최소화하고, 게스트 커널을 줄이고, VMM을 비특권으로
돌리고, 게스트 밖에서 네트워크와 자격 증명을 통제한다.
핵심은 규칙을 게스트 밖에 둔다는 점이다.
이그레스 정책과 속도 제한, 자격 증명 주입이 호스트 쪽에서 일어나므로 게스트가
뚫려도 그 규칙을 끌 수 없다고 글은 말한다.
다만 이 문서는 구현을 확인하지 못했고 글의 설명이 사실이라는 전제 위에서만
이 구조가 성립한다.

### 속도는 예열 풀과 지연 가져오기로 지켰다고 주장한다

microVM의 부팅 비용을 숨기는 방식은 두 가지다.
예열된 VM 풀에 고객 디스크를 핫플러그로 붙이는 것과, 원격 블록 저장이 요구 시
데이터를 가져와 큰 작업 공간도 즉시 시작하게 하는 것이다.
복사 후 쓰기 방식의 저장은 포크를 값싸게 만든다.
약 500ms라는 숫자는 이 과정을 거친 뒤 디스크가 붙은 상태의 인수 시간이고,
이전 시스템과의 비교는 없다.

## 비평

### 96.1%라는 숫자가 보여 주는 것과 보여 주지 않는 것

글은 6,211개 CVE 중 5,969개를 피했다고 하지만 이 숫자는 위험이 줄었다는
증거로는 약하다.
CVE의 상당수는 드라이버나 하위 시스템이 설정에 없으면 애초에 영향을 주지 않는다.
따라서 많이 피했다는 사실은 게스트 커널이 작다는 것을 보여 줄 뿐,
실제로 위협이 될 수 있었던 것 중 얼마나 막았는지를 보여 주지는 않는다.
수치를 더하면 공개 전 수정 4,375개와 설정 제외 676개를 합쳐 5,051개이고,
나머지 918개(약 14.8%)가 어떻게 피해졌는지는 글에 없다.
피하지 못한 242개(약 3.9%)가 무엇이고 어떤 위험인지도 말하지 않는다.
이 계산은 이 문서가 한 것이다.
또한 감사의 방법과 기준이 자사의 서술이어서 독립적으로 검증되지 않았다.

### 이 글은 보안 주장과 홍보를 같은 어조로 말한다

글은 보안과 격리가 AI 업계의 가장 뜨거운 주제라는 서두로 시작해 OpenAI의
Hugging Face 사고와 Anthropic의 평가 사고, NIST의 이니셔티브, 투자 유치 규모를
나열한다.
이 사례들은 샌드박스 수요를 설명하는 맥락이지만 Replit 설계가 그 위험을 막는
다는 증거는 아니다.
끝은 Replit에서 무언가 만들어 보라는 권유와 채용 공고다.
기술 설명 자체는 구체적이지만 비용, 한계, 실패 사례, 포기한 선택의 대가는
거의 없다.
각 컴포넌트에 microVM을 따로 두지 않기로 한 판단도 오버헤드가 그만한 가치가
없다는 한 문장이 전부다.
HN의 doomspork는 비영리 단체를 Replit에서 옮기는 일을 돕고 있는데, 같은
프롬프트에서 Replit의 LLM이 Claude Code나 Codex보다 나쁜 코드를 내고 토큰으로
돈을 뽑아내는 것 같다고 썼다.[^doomspork]
robgough는 Replit을 쓰는 사람이 많지만 대개 소프트웨어 공학 배경이 없는
창업가형 사용자라서 개발자 커뮤니티에서 보이지 않는다고 했다.[^robgough]
둘 다 개인의 경험이고 샌드박스 엔진의 품질과는 별개의 이야기다.

### 가상화 경계도 만능이 아니다

글은 microVM에서는 게스트 커널이 뚫려도 호스트가 곧바로 뚫리지는 않는다고
말한다.
옳은 설명이지만 가상화 경계 자체의 취약점, VMM의 버그, 게스트와 호스트가
공유하는 장치 경로는 글에서 다뤄지지 않는다.
글이 VMM을 비특권으로 돌리고 보안 감시기를 둔 것은 그 위험을 이미 인정한
설계로 읽히지만, 가상화 계층에서 어떤 위협을 가정했는지는 밝히지 않는다.
글이 고른 Cloud Hypervisor는 패치까지 했다고 하는데, 그 패치가 보안 표면에
미친 영향의 평가도 없다.
HN의 clhodapp은 하드웨어 격리가 에이전트에게 뚫리면 gVisor 같은 패치 가능한
소프트웨어 격리로 옮겨 갈지 물었다.[^clhodapp]
tptacek은 보안 실무자들 사이에서 gVisor와 Firecracker, Cloud Hypervisor가
비슷하다는 분위기이며, 핵심은 하드웨어 대 소프트웨어가 아니라 공유 커널과
게스트 커널의 구분이라고 답했다.
AMD-V나 VT-x 같은 하드웨어 격리는 거의 20년을 버텼고, 내기를 건다면 소프트웨어
격리보다 먼저 뚫리는 쪽에 걸지는 않겠다고 했다.[^tptacek-gvisor]
이 평가는 한 실무자의 인상이며 글의 설계 선택을 직접 시험한 것이 아니다.

### 이전의 성공을 확인할 수 없다

수억 개의 프로젝트를 문제없이 옮겼다는 서술에는 수치가 없다.
데이터 손실이 없었다는 주장은 확인 방법이 없고, 부팅이 빨라졌다는 말도 이전과
이후의 숫자가 없다.
엔지니어링 글로서 가장 가치 있었을 이 이전의 어려움과 실패한 시도가 글에서
거의 보이지 않는다.

## 인사이트

### 규칙을 게스트 밖에 둔다는 원칙은 컨테이너에서도 작동한다

글의 가장 이식 가능한 생각은 정책을 집행하는 지점을 정책의 대상 밖에 두라는
것이다.
이그레스 필터, 속도 제한, 자격 증명 주입이 모두 게스트가 바꿀 수 없는 호스트
쪽에서 일어난다.
이는 microVM이 아니어도 컨테이너 앞에 프록시를 두는 방식으로 일부 적용할 수
있다.
다만 이 문서의 해석으로, 이 원칙의 가치는 격리 기술이 아니라 신뢰 경계를
어디에 긋느냐에 있다.
에이전트가 자율적으로 코드를 실행하는 환경일수록 작업 환경 안의 어떤 설정도
신뢰하지 않는 구조가 중요해진다.

### 에이전트가 쓰는 샌드박스는 사람이 쓰던 샌드박스와 위협 모델이 다르다

글은 에이전트가 자율적으로 늘수록 환경도 달라져야 한다고 말한다.
사람이 개발하는 환경에서는 악의적인 행위자를 가정하지만, 에이전트가 도는
환경에서는 악의 없는 실수나 프롬프트 주입이 같은 결과를 낼 수 있다.
그래서 이그레스 통제와 자격 증명 중개자 같은 장치가 격리 기술만큼 중요해진다.
이는 이 문서의 추론이며 글이 이를 이론으로 설명하지는 않는다.

### 커널 CVE의 증가는 최소 커널을 선택이 아니라 기본값으로 만든다

글이 말하는 CVE 증가가 사실이라면 커널을 줄이는 일은 최적화가 아니라 방어의
기본이 된다.
불필요한 하위 시스템을 빼고 모듈 로딩을 끄는 것은 작은 비용으로 공격 표면을
줄이는 방법이다.
다만 이는 게스트가 단일 용도일 때 쉬운 일이고, 개발자가 임의의 도구와
드라이버를 요구하는 범용 환경에서는 어디까지 뺄 수 있는지가 문제가 된다.
글은 도커를 게스트 안에서 지원한다고 하지만 그에 필요한 커널 기능과 최소
커널의 균형은 설명하지 않는다.
