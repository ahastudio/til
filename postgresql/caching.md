# PostgreSQL 캐싱: 이미 캐시하는 것과 결과 캐시를 더해야 할 때

원문: [PostgreSQL Caching: What It Does and What to Add - PgCache](https://www.pgcache.com/blog/postgresql-caching/)

GN 토론: <https://news.hada.io/topic?id=34016>

## 요약

PgCache의 Philip이 2026년 9월 9일에 쓴 22분 분량의 안내서다.
“PostgreSQL 캐시”라는 말이 두 가지를 뒤섞어 쓴다는 지적에서 출발한다.
하나는 데이터를 메모리에 두어 읽기가 디스크를 피하게 하는 것이고, 다른 하나는 결과를 재사용해 반복 질의가 실행 자체를 피하게 하는 것이다.
둘을 섞으면 `shared_buffers`와 아무 상관없는 CPU 문제를 고치려고 `shared_buffers`를 한참 튜닝하게 된다고 적는다.

글은 세 가지를 다룬다.
Postgres가 이미 캐시하는 것, 실제로 어떤 문제를 겪고 있는지 알아내는 법, 결과 캐시가 필요할 때의 선택지다.
저자는 세 번째 선택지 중 하나를 자기 회사가 만든다고 처음부터 밝히고, 장단점을 공정하게 쓰려 했다고 덧붙인다.

## 동작 방식

### Postgres가 이미 캐시하는 것

`shared_buffers`는 최근 접근한 8KB 페이지를 담는 RAM 영역이다.
기본값은 128MB로 일부러 작게 잡혀 있고, 전용 서버에서는 시스템 RAM의 25%가 관례적인 출발점이며 바꾸려면 재시작해야 한다.
RDS나 Cloud SQL 같은 관리형 서비스는 이미 적당한 값으로 맞춰 두었으므로, 이것은 직접 운영하는 서버를 위한 조언이다.
교체 정책은 LRU를 근사한 clock-sweep으로, 페이지마다 최대 5까지 오르는 사용 횟수가 스윕이 지날 때마다 줄어든다.
`shared_buffers`의 4분의 1보다 큰 테이블을 순차 스캔하면 약 256KB의 작은 링 버퍼를 거치므로 뜨거운 페이지를 밀어내지 않는다.
RAM의 40%를 넘기는 것은 대개 가치가 없는데, 모든 페이지가 OS 캐시도 거치기 때문에 같은 데이터를 두 번 저장하게 되기 때문이다.
`pg_prewarm`으로 재시작 뒤 버퍼 풀을 자동으로 다시 채울 수 있다.

Postgres는 버퍼링된 I/O를 쓰므로 `shared_buffers`를 놓친 페이지도 OS 페이지 캐시에서 RAM으로 돌아오는 경우가 많다.
그래서 Postgres 통계의 “디스크 읽기”가 실제로 디스크에 닿지 않는 일이 흔하다.
`effective_cache_size`는 여기서 사람들이 가장 자주 헷갈리는 설정이다.
아무것도 할당하지 않는 플래너 힌트이며, 인덱스 스캔이 기대할 수 있는 전체 캐시 크기의 추정치일 뿐이다.

계획 캐시는 세션 단위이고 요청했을 때만 생긴다.
준비된 문장(prepared statement)은 첫 다섯 번은 매번 맞춤 계획을 세운 뒤, 그 평균 비용을 일반 계획과 비교해 일반 계획을 재사용할지 정한다.
버전 12부터는 `plan_cache_mode`로 어느 쪽이든 강제할 수 있다.
계획은 연결과 함께 살고 죽으므로 운영 환경은 대부분 커넥션 풀러를 쓴다.

연결마다 relcache와 syscache라는 카탈로그 캐시도 따로 둔다.
직접 튜닝하는 대상은 아니지만, 새 연결이 따뜻한 연결보다 느린 이유와 수만 개의 릴레이션을 건드리는 오래된 연결이 메모리를 키우는 이유를 설명해 준다.

### Postgres에 질의 캐시가 없는 이유

MySQL은 SELECT의 결과를 질의 문자열을 키로 저장하는 질의 캐시를 내장하고 있었지만, 5.7에서 사용 중단되고 8.0에서 제거됐다.
테이블에 쓰기가 한 번 일어나면 그 테이블을 건드린 모든 캐시 결과가 무효화되어, 실제 쓰기 부하에서는 캐시가 계속 갈아엎히기만 했다.
모든 질의가 단일 뮤텍스 뒤에서 캐시를 먼저 확인해야 했으므로 그것이 확장성의 천장이 됐다.
Postgres 개발자들은 이 과정을 지켜보고 질의 캐시를 만들지 않았으며, 공유 결과 캐시는 핵심 실행 경로에 속하지 않고 생태계의 몫이라는 입장을 메일링 리스트에서 되풀이해 왔다.

## 진단하기

결과 캐시를 더하기 전에 시간이 어디로 가는지부터 확인해야 한다.
숫자 두 개면 대부분 알 수 있다.

첫째는 캐시 적중률이다.

```sql
SELECT sum(blks_hit) * 100.0 / nullif(sum(blks_hit + blks_read), 0) AS cache_hit_pct
FROM pg_stat_database;
```

일반적인 OLTP 부하라면 99% 이상이어야 한다.
다만 `blks_read`는 `shared_buffers`에 없었다는 뜻일 뿐 OS 캐시에서 채워졌을 수 있으므로, 실제 I/O를 보려면 Postgres 16에 들어온 `pg_stat_io`를 쓴다.
어느 테이블이 문제인지 보려면 테이블별로 나눈다.

```sql
SELECT relname, heap_blks_read, heap_blks_hit,
       round(heap_blks_hit * 100.0 / nullif(heap_blks_hit + heap_blks_read, 0), 1) AS hit_pct
FROM pg_statio_user_tables
ORDER BY heap_blks_read DESC
LIMIT 10;
```

둘째는 실행 시간의 분포다.
`pg_stat_statements`는 Postgres에 들어 있지만 `shared_preload_libraries`로 켜야 하고 재시작이 필요하며, 관리형 서비스는 대개 이미 켜 두었다.

```sql
SELECT calls,
       round(total_exec_time::numeric) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

질의 하나를 볼 때는 `EXPLAIN (ANALYZE, BUFFERS)`가 계획 노드마다 `Buffers: shared hit=4098 read=512` 같은 분할을 보여 준다.
`ANALYZE`는 질의를 실제로 실행하므로 단순한 SELECT가 아니면 `BEGIN ... ROLLBACK`으로 감싸야 한다.

결과는 두 경우로 갈린다.

| 경우           | 증상                                                     | 먼저 할 일              |
| -------------- | -------------------------------------------------------- | ----------------------- |
| 작업 집합 초과 | 적중률 낮음, 디스크 읽기 많음                            | RAM과 `shared_buffers`  |
| 빈도 병목      | 적중률 100% 근처, CPU 포화, 빠른 질의가 수백만 번 호출됨 | 결과 캐시나 외부 완화책 |

두 번째 경우가 놓치기 쉽다.
반복 질의가 대시보드에서는 “캐시됨”으로 보이지만, 캐시된 읽기도 매번 파싱, 계획, 스캔, 가시성 검사, 결과 직렬화 비용을 치르기 때문이다.

## 선택지

### 데이터베이스 안에서

구체화된 뷰(materialized view)는 질의 결과를 미리 계산해 인덱스를 걸 수 있는 테이블로 저장한다.
비싸고 지연을 견딜 수 있는 질의 몇 개가 부하를 지배할 때 빛난다.
입력이 바뀌면 `REFRESH MATERIALIZED VIEW`로 처음부터 다시 계산해야 하고, 코어에는 점진 유지 기능이 없어 `pg_ivm` 확장이 제한적으로 그것을 더한다.
일반 새로 고침은 실행하는 동안 읽기를 막으므로, 운영 환경은 고유 인덱스가 필요한 `REFRESH ... CONCURRENTLY`를 쓴다.

Postgres 자체를 Redis처럼 쓸 수도 있다.
`UNLOGGED` 테이블은 WAL을 건너뛰어 쓰기가 크게 싸지고, 키에 인덱스를 걸고 만료된 항목을 주기적으로 지우면 서비스 하나를 스택에서 뺄 수 있다.
다만 캐시 트래픽이 여전히 데이터베이스로 가므로 CPU에 여유가 있을 때만 통하고, 크래시 뒤에는 테이블이 비워지며 스탠바이로 복제되지 않는다.

### 애플리케이션에서

Redis, Valkey, memcached 같은 애플리케이션 쪽 캐시가 업계 기본값이다.
적중하면 데이터베이스에 닿지 않고 1밀리초 훨씬 아래로 돌아온다.
대신 데이터 정확성의 부담이 데이터베이스에서 애플리케이션 코드로 옮겨 간다.
가장 쉬운 길은 TTL이고, 최신성이 중요하면 무효화를 직접 짜야 하는데 거기서 네 가지 문제가 생긴다.

- 무효화 누락: 마이그레이션, 대량 가져오기, 관리 도구, 같은 데이터베이스를 쓰는 다른 서비스 중 하나라도 키를 빠뜨리면 오래된 데이터가 나간다.
- 이중 쓰기: 데이터베이스 쓰기와 캐시 삭제는 트랜잭션을 공유하지 않는다.
- 파생 키: 사용자 하나를 바꾸면 그 사용자를 포함한 목록, 개수, 집계 중 어떤 것을 지워야 하는지 추적해야 한다.
- 스탬피드: 자주 쓰이는 키가 만료되는 순간 수천 개의 동시 요청이 한꺼번에 놓치고 Postgres로 몰려 데이터베이스 자체를 쓰러뜨릴 수 있다.

그래서 대부분의 팀은 결국 30초 같은 짧은 TTL로 오래됨의 상한을 정하고 받아들이며, 저자는 많은 경우 합리적인 타협이라고 본다.

### 프록시와 복제본

pgpool-II는 SELECT 결과를 공유 메모리나 memcached에 캐시할 수 있어, Postgres 세계에서 MySQL식 질의 캐시에 가장 가깝다.
무효화도 똑같이 테이블 단위라서 한 행을 UPDATE하면 그 테이블을 건드린 모든 결과가 날아가고, pgpool을 거치지 않은 쓰기는 보이지 않는다.

읽기 복제본은 키도 TTL도 없는 평범한 Postgres라 비용과 규모를 예측하기 쉽다.
그러나 순진하게 구성하면 데이터베이스 전체를 복사하므로 저장소를 두 번 내고, 전체 크기의 인스턴스를 따뜻하게 유지하며, 데이터 전송 비용까지 낸다.
대부분의 부하에서는 데이터 일부가 거의 모든 읽기를 받으므로, 차가운 대다수를 두 곳에 두는 비용을 내는 셈이다.
복제 지연은 TTL보다 짧지만 여전히 지연이므로 결과적 일관성이다.

### CDC 기반 캐시

앞의 모든 결과 캐시는 캐시된 결과가 언제 더 이상 참이 아닌지를 추측한다.
Postgres의 논리 복제 스트림은 모든 행 단위 변경을 순서대로 내보내므로, 이것을 구독하는 캐시는 추측할 필요 없이 무엇이 바뀌었는지 전달받아 그 행에 의존하던 항목만 갱신하거나 버릴 수 있다.

저자가 아는 두 프로젝트는 Readyset과 PgCache다.
Readyset은 MySQL과 PostgreSQL 모두와 와이어 호환되며 점진 뷰 유지 엔진으로 결과를 유지하고, 가속할 질의마다 `CREATE CACHE`로 선언해야 하며 메모리 예산을 계획해야 한다.
PgCache는 선언이 필요 없고 실시간 트래픽이 무엇을 캐시할지 정한다.
행 단위로 무효화하고, 읽힌 것만 담으므로 데이터베이스 전체가 아니라 트래픽의 복제본 모양이 되며, 그래서 “똑똑한 읽기 복제본”이라 부른다.

PgCache가 스스로 밝힌 제약도 있다.
SELECT 목록 밖의 `now()`, `random()` 같은 불변이 아닌 함수, LATERAL 서브쿼리, 재귀 CTE는 원본으로 넘긴다.
행 수준 보안(RLS)은 아직 지원하지 않고 4분기에 지원할 계획이다.
트랜잭션 안의 질의는 모두 원본으로 가므로 세션은 자기 쓰기를 읽고, 트랜잭션 밖에서는 복제 지연이 적용된다.
논리 복제 클라이언트로서 일관성이 복제 스트림에 묶이고, 일부 경우 삭제된 테이블을 놓칠 수 있으며, 복제 슬롯을 방치하면 WAL이 쌓일 위험이 있다.
PostgreSQL 16, 17, 18에서 동작한다.

## 값 정하기

| 증상                                                 | 선택                   | 근거                                             |
| ---------------------------------------------------- | ---------------------- | ------------------------------------------------ |
| 적중률이 약 99% 아래이고 디스크 읽기가 많다          | RAM과 `shared_buffers` | 결과 캐시는 작업 집합 문제를 풀지 않는다         |
| 적중률은 괜찮은데 반복 읽기로 CPU가 포화됐다         | 결과 캐시              | 반복 실행 비용 자체를 없애야 한다                |
| 비싼 집계 몇 개가 지배하고 오래됨을 견딘다           | 구체화된 뷰            | 설계와 새로 고침을 감당할 만한 소수의 질의다     |
| 서로 다른 뜨거운 질의가 있고 팀이 무효화를 책임진다  | Redis, Valkey          | 가장 빠르고 유연하지만 정확성 부담을 코드가 진다 |
| 뜨거운 질의가 많고 아무도 무효화를 책임지기 싫어한다 | PgCache, Readyset      | 무효화를 복제 스트림에 맡긴다                    |
| 읽기를 늘려야 하는데 결과 캐시는 선택지가 아니다     | 읽기 복제본            | 단순하고 예측 가능하지만 전체 복사 비용을 낸다   |
| 쓰기가 병목이다                                      | 이 중 무엇도 아니다    | 캐시는 쓰기를 돕지 않는다                        |

`shared_buffers`는 RAM의 25%에서 시작하고 40%를 넘기지 않는다.
OLTP 적중률은 99%를 기준으로 삼되 그것 하나에 의존하지 않는다.
짧은 TTL을 고를 때는 30초처럼 오래됨의 상한을 사업 요구에 맞춰 정한다.

## 함정

### 캐시가 틀린 답인 경우

저자는 캐시를 아예 건너뛰어야 할 경우를 네 가지로 든다.
데이터베이스가 RAM에 들어가고 CPU가 한가하다면 층을 더하지 말아야 한다.
질의가 거의 반복되지 않는 임시 분석이나 검색 같은 부하는 결과 캐시에서 얻는 것이 거의 없다.
쓰기가 뜨거운 테이블은 채우는 속도만큼 무효화되어 오버헤드만 남는다.
출금 전 잔액 확인이나 판매 전 재고 확인처럼 갱신을 놓치면 안 되는 읽기는 복제본을 포함한 모든 캐시가 어딘가에서 결과적으로 일관적이므로 원본으로 보내야 한다.

그리고 지루한 해결책을 먼저 다 써 봐야 한다.
`EXPLAIN ANALYZE` 세션이 새 인덱스로 끝난다면, 큰 테이블의 쓰기를 막지 않도록 `CONCURRENTLY`로 만든 그 인덱스가 이 글의 어떤 해결책보다 싸고 쉽다.

### 적중률 99%가 CPU 포화를 가린다

빈도 병목은 대시보드에서 정상으로 보인다.
적중률이 높고 디스크 I/O가 낮으니 캐시가 잘 동작한다고 판단하기 쉽지만, 같은 질의를 수백만 번 실행하는 비용은 적중률에 나타나지 않는다.
`pg_stat_statements`를 `total_exec_time`으로 정렬해 상위에 빠른 질의가 몰려 있는지 봐야 이 경우를 알아볼 수 있다.

### 캐시가 있는 한 결과적 일관성에서 벗어날 수 없다

애플리케이션 캐시는 TTL만큼, 복제본은 복제 지연만큼, CDC 캐시도 복제 지연만큼 오래된 데이터를 낸다.
어떤 선택지를 고르든 “반드시 최신이어야 하는 읽기”의 목록을 먼저 만들고 그것을 캐시 밖으로 돌리는 경로를 설계해야 한다.
PgCache가 트랜잭션 안의 질의를 원본으로 보내는 것은 이 경로를 트랜잭션 경계로 표현하는 방식이며, 애플리케이션이 그 경계를 의도대로 쓰고 있는지가 곧 정확성을 결정한다.

## 비평

### 선택지 비교가 판매하는 제품을 향해 기울어 있다

저자는 자기 회사가 선택지 하나를 만든다고 처음부터 밝혔고, 장단점을 공정하게 쓰려 했다고 했다.
실제로 PgCache의 제약을 상당히 솔직하게 적었다.
그러나 글의 구조는 공정하지 않다.

앞의 선택지들은 모두 약점과 함께 소개된다.
Redis는 무효화 누락, 이중 쓰기, 파생 키, 스탬피드라는 네 가지 문제로 설명되고, 복제본은 전체 복사 비용으로 설명되며, pgpool은 테이블 단위 무효화의 무딘 칼로 설명된다.
그 뒤에 CDC 기반 캐시가 이 문제들을 푸는 “세 번째 길”로 등장한다.
같은 방식으로 CDC 캐시의 문제, 곧 지원하지 않는 질의 모양, RLS 미지원, 복제 슬롯 방치 시 WAL 누적을 네 문단의 위험으로 먼저 늘어놓았다면 독자의 인상은 달랐을 것이다.

“덮인 질의(covered queries)” 설명이 대표적이다.
저자는 질의가 거의 반복되지 않는 부하에는 결과 캐시가 쓸모없다고 쓴 바로 그 문단에서, 괄호를 열고 PgCache는 예외라고 덧붙인다.
캐시를 건너뛰어야 할 경우를 설명하는 절에서조차 자사 제품이 예외로 들어가 있다.

### Readyset과의 비교가 한쪽 방향으로만 서술된다

Readyset은 가속할 질의마다 `CREATE CACHE`로 선언해야 하고 메모리 예산을 계획해야 한다고 소개된다.
PgCache는 선언이 필요 없고 트래픽이 알아서 정한다고 소개된다.
이 비교에서 선언은 부담으로만 그려진다.

그러나 선언은 통제이기도 하다.
어떤 질의가 캐시에서 나가는지 명시적으로 알면, 반드시 최신이어야 하는 읽기가 실수로 캐시되는 일을 막기 쉽다.
트래픽이 캐시 대상을 정하는 방식에서는 출금 전 잔액 확인 같은 질의가 트랜잭션 밖에서 실행되는 순간 캐시될 수 있고, 그것을 막는 책임은 애플리케이션이 트랜잭션 경계를 정확히 쓰는 데로 넘어간다.
저자가 앞에서 강조한 “갱신을 놓치면 안 되는 읽기는 원본으로 보내라”는 조언이 선언 없는 캐시에서는 더 지키기 어렵다는 점은 다뤄지지 않는다.

### 복제본 비용 비판은 가장 순진한 구성을 기준으로 삼는다

읽기 복제본의 경제성 비판은 전체 데이터베이스를 복사하는 가장 순진한 구성을 전제로 한다.
저자도 논리 복제로 특정 테이블만 복사하는 방법을 언급하지만, 고급 지식이 필요하고 흔하지 않은 것 같다며 한 문단으로 넘긴다.

그런데 저자의 제품도 바로 그 논리 복제 스트림 위에 서 있다.
논리 복제를 운영하는 데 필요한 지식, 곧 복제 슬롯 관리와 WAL 누적 감시와 삭제된 테이블 같은 가장자리 경우는 PgCache를 쓰는 팀도 똑같이 알아야 한다.
저자 스스로 이것들을 PgCache가 물려받는 주의 사항으로 적었다.
그렇다면 부분 복제본이 어렵다는 이유와 PgCache가 쉽다는 이유는 같은 지식을 서로 다르게 셈한 결과다.

## 기억할 원칙

### 캐시를 고르기 전에 무엇이 반복되는지 먼저 센다

이 글의 진단 절은 판매 목적과 상관없이 그대로 쓸 만하다.
캐시는 같은 일을 두 번 하지 않게 해 주는 장치이므로, 무엇이 얼마나 반복되는지 모르면 어떤 캐시도 정당화할 수 없다.
적중률은 메모리 문제를, `pg_stat_statements`는 반복 실행 문제를 보여 주며, 둘은 서로 다른 해결책을 가리킨다.
증상과 해결책의 층을 맞추는 것이 튜닝의 대부분이다.

### 최신성이 필요한 읽기를 먼저 목록으로 만든다

모든 결과 캐시와 복제본은 어딘가에서 결과적으로 일관적이다.
그러므로 어떤 캐시를 들이든 첫 작업은 캐시를 켜는 것이 아니라, 캐시에서 절대 나가면 안 되는 읽기를 목록으로 만들고 그것을 원본으로 보내는 경로를 확보하는 일이다.
이 목록이 없으면 캐시의 성능 이득은 언젠가 틀린 잔액 하나로 모두 상쇄된다.
