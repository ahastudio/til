# PostgreSQL 무중단 마이그레이션: 확장-축소로 스키마를 바꾸는 법

원문: [Zero-Downtime PostgreSQL Migrations: A Production Playbook for Safe Schema Changes](https://boundlayer.io/blog/zero-downtime-postgresql-migrations)

GN 토론: <https://news.hada.io/topic?id=35501>

## 소개

BoundLayer 엔지니어링 팀이 2026년 10월 8일에 올린 이 글은
운영 중인 PostgreSQL의 스키마를
서비스 중단 없이 바꾸는 절차를 정리한 실무 지침이다.
개발자 노트북에서 순식간에 끝나는 마이그레이션도
운영 환경에서는 시스템을 멈출 수 있다.
SQL이 옳아도 큰 테이블, 오래 실행되는 트랜잭션, 락 대기열, 복제본,
동시에 실행되는 여러 애플리케이션 버전,
커넥션 풀, 백그라운드 작업이 위험을 만든다.

글의 핵심 주장은 이렇다.
무중단 마이그레이션은 특정 명령이나 프레임워크 기능이 아니라,
스키마와 데이터가 통제된 중간 상태를 거치는 동안
옛 애플리케이션과 새 애플리케이션이 함께 동작하도록 유지하는
릴리스 규율이다.

### 무중단의 정의

“데이터베이스가 살아 있었다”는 충분한 정의가 아니다.
PostgreSQL은 기술적으로 살아 있어도 API 요청이 락 뒤에서 기다리고,
커넥션 풀이 차고, 복제본이 밀리고, 고객이 오류를 받을 수 있다.
글은 성공을 서비스 수준의 결과로 정의한다.

- 요청 오류율이 의미 있게 늘지 않는다.
- p95, p99 지연 시간이 합의한 범위 안에 있다.
- 핵심 흐름의 쓰기가 계속된다.
- 복제 지연이 제한된다.
- 데이터가 유실되거나 중복되거나 잘못 변환되지 않는다.
- 배포 중에 옛 버전과 새 버전이 모두 유효하다.
- 즉흥적인 대응 없이 멈추거나 되돌릴 수 있다.

어떤 스키마 작업은 짧은 락이 필요하므로,
목표는 문자 그대로 락이 없는 것이 아니라 락을 빨리 얻고,
그 영향을 제한하고, 제한적인 락을 쥔 채 긴 작업을 하지 않는 것이다.

## 동작 방식

### 위험은 락 대기열에서 온다

많은 `ALTER TABLE`은
일반 읽기와 쓰기와 충돌하는 `ACCESS EXCLUSIVE` 락을 요청한다.
진짜 위험은 그 락을 기다리는 동안 생긴다.

1. 오래 실행 중인 트랜잭션 A가 테이블에 락을 쥐고 있다.
2. 마이그레이션이 `ACCESS EXCLUSIVE`를 요청하고 A를 기다린다.
3. 그 뒤에 들어오는 평범한 애플리케이션 쿼리가 마이그레이션 뒤에 줄을 선다.
4. 시작도 하지 않은 스키마 변경 때문에 장애가 번진다.

그래서 마이그레이션은 오래 기다리기보다 빨리 실패해야 한다.

### 확장-축소 패턴

확장-축소(expand-contract)는 병렬 변경이라고도 부르며,
옛 계약을 한 번에 바꾸지 않고 다섯 단계로 옮겨 가는 방법이다.

| 단계 | 하는 일                                 |
| ---- | --------------------------------------- |
| 확장 | 옛 코드를 깨지 않는 새 스키마 추가      |
| 이전 | 데이터를 채우고 두 표현을 모두 지원     |
| 전환 | 읽기와 쓰기를 새 표현으로 이동          |
| 검증 | 정확성을 입증하고 운영 기간 전체를 관찰 |
| 축소 | 옛 코드, 열, 인덱스, 호환 경로 제거     |

단계마다 따로 배포하고 관찰한다.
축소 단계에는 담당자와 날짜가 있어야 하며,
그렇지 않으면 임시 열과 이중 쓰기와 안 쓰는 인덱스가 영구 복잡도로 쌓인다.

## 구현하기

### 락 획득에 시간 제한을 둔다

```sql
SET lock_timeout = '2s';
SET statement_timeout = '15s';

ALTER TABLE accounts
  ADD COLUMN risk_tier text;
```

`lock_timeout`은 락을 안전하게 얻지 못한 경우를,
`statement_timeout`은 시작한 작업이 너무 오래 걸리는 경우를 구분한다.
값은 작업 부하에 따라 다르다.
실패하면 통제된 시간대에 간격을 두고 다시 시도하되,
제한 시간을 계속 늘리다가 결국 운영을 막는 일은 피한다.
설정이 다른 작업에 영향을 주지 않게 별도 세션과 명시적 트랜잭션 범위를 쓴다.

재시도 전에 누가 막고 있는지 본다.

```sql
SELECT pid,
       pg_blocking_pids(pid) AS blocked_by,
       state,
       now() - xact_start AS xact_age,
       left(query, 80) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0
   OR state = 'idle in transaction'
ORDER BY xact_start;
```

글은 오래된 `idle in transaction` 세션이 실제 결함일 수 있다고 지적한다.

### 열을 추가한다

휘발성 기본값이 없는 nullable 열 추가는
최신 PostgreSQL에서 대개 빠른 메타데이터 작업이다.
공식 문서에 따르면 비휘발성 `DEFAULT`를 주어도 값이 메타데이터에 저장되어
큰 테이블에서도 `ALTER TABLE`이 매우 빠르다.[^pg-alter]
그래도 락은 필요하다.

나중에 필수가 될 열은 단계를 나눈다.

1. nullable 열을 추가한다.
2. 옛 행을 읽고 새 필드를 쓰는 코드를 배포한다.
3. 기존 행을 작은 배치로 채운다.
4. NULL이 남지 않았는지 확인한다.
5. 같은 의미의 CHECK 제약을 추가하고 검증한다.
6. `NOT NULL`을 적용한다.
7. 임시 호환 로직을 나중에 지운다.

5단계가 중요한 이유는,
공식 문서가 NULL이 없음을 증명하는 유효한 CHECK 제약이 있으면
`SET NOT NULL`의 전체 테이블 검사를 건너뛴다고 밝히기 때문이다.[^pg-alter]
스키마 확장, 전체 채우기, 제약 적용을 한 트랜잭션에 묶지 않는다.

기본값의 의미도 확인해야 한다.
데이터베이스 기본값은 열을 생략했을 때 적용되며,
애플리케이션이 명시적으로 NULL을 쓰는 경우에는 적용되지 않는다.

### 제약을 오래 막지 않고 추가한다

```sql
ALTER TABLE payments
  ADD CONSTRAINT payments_amount_positive
  CHECK (amount_minor >= 0) NOT VALID;

-- 과거 위반을 고친 뒤, 별도 트랜잭션에서
ALTER TABLE payments
  VALIDATE CONSTRAINT payments_amount_positive;
```

`NOT VALID`는 새로 쓰거나 바뀌는 행에만 제약을 적용하고
과거 데이터는 바로 검사하지 않는다.
검증은 덜 제한적인 락으로 따로 한다.
두 명령을 한 트랜잭션에 넣으면 첫 락이 커밋까지 유지되어 이점이 대부분 사라진다.

### 인덱스를 동시에 만든다

```sql
CREATE INDEX CONCURRENTLY idx_orders_customer_created
  ON orders (customer_id, created_at DESC);
```

일반 `CREATE INDEX`는 빌드 동안 쓰기를 막는다.
`CONCURRENTLY`는 쓰기를 허용하지만 더 오래 걸리고,
일반 트랜잭션 블록 안에서 실행할 수 없으며,
I/O, CPU, WAL, 복제 지연을 늘린다.
실패하면 무효 인덱스가 남을 수 있으므로 찾아서 지운 뒤 다시 만든다.
고유 제약이나 기본 키는 동시에 만든 고유 인덱스를
`ADD CONSTRAINT ... USING INDEX`로 붙일 수 있다.

### 열 이름을 여러 릴리스에 걸쳐 바꾼다

`users.name`을 `display_name`으로 바꾸는 경우다.

| 릴리스     | 하는 일                                                    |
| ---------- | ---------------------------------------------------------- |
| 1          | `display_name`을 nullable로 추가, `name`은 그대로          |
| 2          | 모든 변경에서 두 열에 함께 쓰고, 읽기는 `name` 또는 대체값 |
| 백그라운드 | 옛 값을 제한된 배치로 복사하고 진행 상황 기록              |
| 3          | `display_name`에서 읽고, 비교와 대체값은 잠시 유지         |
| 4          | 새 열을 기준으로 삼고 옛 쓰기를 멈춘 뒤 관찰               |
| 5          | `name`에 대한 의존을 지우고 전용 마이그레이션으로 삭제     |

이중 쓰기를 애플리케이션에 둘지 임시 트리거에 둘지도 정해야 한다.
애플리케이션 쓰기는 이해하기 쉽지만 모든 작성자를 고쳐야 하고,
트리거는 알 수 없는 작성자까지 덮지만 숨은 동작이 된다.

### 데이터를 채운다

```sql
WITH batch AS (
  SELECT id
  FROM accounts
  WHERE risk_tier IS NULL
  ORDER BY id
  LIMIT 1000
  FOR UPDATE SKIP LOCKED
)
UPDATE accounts AS a
SET risk_tier = derive_risk_tier(a)
FROM batch
WHERE a.id = batch.id;
```

채우기도 운영 작업 부하다.
배치마다 커밋하고, 멱등하게 만들고, 체크포인트를 남기고,
배치 사이에 속도를 조절하고, 서비스 지표가 나빠지면 자동으로 멈춘다.
WAL, 복제 지연, 죽은 튜플, vacuum을 보고,
남은 행과 실패한 행을 드러낸다.
OFFSET 페이지네이션은 동시 변경과 큰 오프셋 때문에 진행을 믿을 수 없으니
키 범위나 커서를 쓴다.

## 값 정하기

| 값                  | 글의 예시 | 근거와 조정 기준                                             |
| ------------------- | --------- | ------------------------------------------------------------ |
| `lock_timeout`      | 2초       | 곧바로 락을 얻어야 하는 작업용, 사용자 요청 지연 예산 안에서 |
| `statement_timeout` | 15초      | 메타데이터 작업의 예상 시간보다 넉넉히, 채우기에는 따로      |
| 채우기 배치 크기    | 1,000행   | 배치당 커밋 시간과 복제 지연을 보며 조정                     |
| 축소 단계 대기 기간 | 미정      | 대표적인 트래픽과 운영 주기 하나를 다 지날 만큼              |

글은 값이 작업 부하마다 다르다고만 하고 구체적인 기준은 주지 않는다.
측정해야 할 것은 락 획득 시간과 작업 시간을 따로 잰 값,
배치당 WAL 생성량과 복제 지연, p99 지연 시간의 변화다.

## 트레이드오프

### 이중 쓰기는 일관성을 보장하지 않는다

한 트랜잭션 안에서 두 열에 쓰는 것은 다룰 만하다.
그러나 PostgreSQL과 별도 서비스나 브로커에 함께 쓰면 분산 일관성 문제가 된다.
글은 트랜잭셔널 아웃박스나 로그 기반 CDC를 권하고,
옛 값과 새 값의 불일치, 한쪽만 채워진 행, 옛 버전에서 오는 쓰기,
채우기가 새 값을 덮어쓴 경우, 옛 스키마를 여전히 읽는 소비자를 계측하라고 한다.
불일치가 0이 되거나 모든 예외를 이해하기 전에는 축소하지 않는다.

### 되돌리기는 단계마다 비용이 다르다

확장 단계에서는 옛 스키마가 남아 있어 애플리케이션 되돌리기가 쉽다.
이중 쓰기 동안 되돌리기가 필요하다면 옛 표현에도 유효한 값이 계속 들어가야 한다.
축소 뒤에는 열을 다시 만들어도 데이터가 돌아오지 않고,
전체 백업 복원은 새 운영 쓰기를 날릴 수 있다.
그래서 글은 쉽게 되돌아갈 수 없는 지점을 문서로 남기고
그 지점을 넘기 전에 명시적 승인을 받으라고 한다.
기능 플래그로 새 읽기 경로를 끄기, 채우기 멈추기, 호환 수정 배포 같은
되돌리지 않고 앞으로 고쳐 나가는 방법이
맹목적인 down 마이그레이션보다 안전한 경우가 많다.

### 확장-축소는 속도를 내주고 안전을 얻는다

이름 바꾸기 하나가 다섯 번의 릴리스가 된다.
롤링 배포, 되돌리기, 검증을 지원하는 대가다.
작은 팀이나 트래픽이 적은 서비스라면 짧은 점검 시간에 한 번에 바꾸는 편이
전체 비용이 더 낮을 수 있다.
글은 이 선택지를 다루지 않는다.

## 함정

- 애플리케이션 시작 시 DDL을 자동 실행하면 여러 복제본이 경쟁하고,
  위험한 마이그레이션이 서비스 복구와 묶인다.
- 모든 단계를 한 트랜잭션에 넣으면 긴 채우기와 제약 검증이 락을 쥐고 진행이 전부 아니면 전무가 된다.
- 락 타임아웃이 없으면 마이그레이션이 운영 트래픽 뒤에서 기다리며 락 대기열을 만든다.
- 바쁜 테이블에 일반 인덱스를 만들면 빌드 동안 쓰기가 멈춘다.
- 같은 배포에서 이름을 바꾸면 롤링 배포 중 옛 인스턴스와 백그라운드 작업이 실패한다.
- 남은 행이 0이 되었다고 성공을 선언하면 잘못 변환된 값을 놓친다.
  업무 불변식으로 대조해야 한다.
- 축소 단계를 하지 않으면 임시 호환 코드가 영구 구조가 된다.
- 열을 지워도 디스크 공간은 이후 행 재작성이나 유지보수 전까지 돌아오지 않을 수 있다.

## 확인하기

CI에서 다음 순서로 호환성을 시험하면,
마이그레이션과 애플리케이션이 동시에 배포될 때만 동작하는 흔한 오류를 잡는다.

1. 옛 애플리케이션과 옛 스키마
2. 옛 애플리케이션과 확장된 스키마
3. 새 애플리케이션과 확장된 스키마
4. 이중 쓰기 동안 함께 실행되는 옛 애플리케이션과 새 애플리케이션
5. 채우기 뒤의 새 애플리케이션
6. 축소 뒤의 새 애플리케이션

리허설은 빈 데이터베이스가 아니라 운영 규모의 데이터,
동시 읽기와 쓰기, 긴 트랜잭션, 복제본, 제한된 디스크 여유에서 한다.
락 획득 시간과 작업 시간을 따로 잰다.

## 체크리스트

- 이 작업이 요청하는 락 모드를 운영 버전의 문서로 확인했는가?
- 테이블을 스캔하거나 다시 쓰는가?
- 운영 환경에서 대상 객체의 크기를 알고 있는가?
- 버전 N과 N+1이 함께 실행될 때 스키마가 둘 다 지원하는가?
- 뷰, 함수, 트리거, 외래 키, ETL, CDC 커넥터, BI 도구 의존을 확인했는가?
- 락 대기, 지연, 오류, 복제 지연에 대한 중단 기준과 중단 권한자가 정해져 있는가?
- `lock_timeout`과 `statement_timeout`을 설정했는가?
- 채우기 작업이 멱등하고 재개 가능하며 속도를 조절하는가?
- 축소 단계의 담당자와 날짜가 정해져 있는가?
- 쉽게 되돌아갈 수 없는 지점이 문서로 남아 있는가?

## 비평

### 버전별 차이를 “확인하라”로 넘긴다

글은 여러 곳에서 정확한 동작은 배포된 PostgreSQL 버전에서 확인하라고 한다.
옳은 조언이지만, 이 글이 실무 지침을 표방한다면
어느 버전부터 무엇이 바뀌었는지 정도는 적었어야 했다.
예컨대 NULL이 없음을 증명하는 유효한 CHECK 제약이 있으면
`SET NOT NULL`이 전체 검사를 건너뛴다는 내용은
현재 공식 문서에 명시되어 있는데,[^pg-alter]
글은 이를 “최적화 동작을 확인하라”는 문장으로만 다룬다.
독자가 가장 알고 싶은 것은 확인해야 한다는 사실이 아니라 무엇을 확인할지다.

글이 컨설팅 회사의 홍보 글이라는 점도 함께 읽어야 한다.
마지막 절은 회사가 도울 수 있는 일을 길게 나열한다.
내용 자체는 업계에서 널리 쓰이는 확장-축소 원칙을 충실히 정리했지만,
측정값이나 실제 사고 사례는 없다.
같은 원칙을 사례와 숫자로 뒷받침한 자료와 함께 보는 편이 좋다.

## 기억할 원칙

### 마이그레이션은 SQL이 끝날 때가 아니라 검증이 끝날 때 끝난다

글은 SQL 명령보다 릴리스 순서가 더 중요하다는 문장으로 끝난다.
마이그레이션의 성공은 명령의 종료 코드가 아니라
애플리케이션 동작과 데이터 정확성이 검증되었는지로 판정한다.
그래서 모든 지표를 마이그레이션 단계와 릴리스 버전에 연결해 보고,
각 단계로 넘어가기 전에 필요한 증거를 미리 정해 둔다.
