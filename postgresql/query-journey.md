## 동작 방식

### 쿼리는 파서, 옵티마이저, 실행 엔진을 차례로 거친다

영상이 그리는 전체 지도는 다섯 단계이다.

| 단계        | 하는 일                                                                                |
| ----------- | -------------------------------------------------------------------------------------- |
| 파서        | 문법을 검사하고 쿼리를 나무 모양 구조로 바꾼다                                         |
| 옵티마이저  | 통계를 보고 같은 답에 이르는 여러 길 가운데 가장 싼 길을 골라 실행 계획으로 확정한다   |
| 실행 엔진   | 확정된 계획대로 실제로 움직인다                                                        |
| 데이터 접근 | 버퍼 풀(메모리)에서 먼저 찾고, 인덱스로 행의 위치를 알아낸 뒤 테이블에서 행을 가져온다 |
| 쓰기        | 바꾸기 전에 WAL(write-ahead log)에 먼저 적어 둔다                                      |

모인 결과가 클라이언트로 돌아가면 여정이 끝난다.
이 지도에서 기억할 것은 계획을 짜는 쪽(옵티마이저)과 계획을 실행하는 쪽(실행
엔진)이 나뉘어 있다는 점이다.
같은 쿼리라도 계획이 달라질 수 있고, 계획은 통계에 달려 있다.

### 인덱스는 B+트리이고 읽기 속도를 쓰기 비용과 바꾼다

인덱스가 없으면 선택지는 하나, 처음부터 끝까지 한 줄씩 읽는 풀
스캔(full scan)이다.
100만 줄에서 한 줄을 찾으려면 100만 줄을 읽어야 하고,
찾을 때마다 같은 일을 반복하니 테이블이 커질수록 그대로 느려진다.

인덱스는 미리 만들어 둔 지도이고 구조는 B+트리이다.
맨 위 루트에는 구간을 가르는 기준 값이 있고,
기준과 비교하며 브랜치 노드를 타고 리프까지 내려간다.
노드 하나에 키가 수백 개 들어가서 서너 단의 높이로 수백만 행을 가리킨다고
영상은 말한다.

리프에 무엇이 들었는지로 종류가 갈린다.

| 종류              | 리프의 내용      | 조회의 끝                                            |
| ----------------- | ---------------- | ---------------------------------------------------- |
| 클러스터드 인덱스 | 행 데이터 자체   | 기본 키 조회라면 리프에 닿는 순간 끝                 |
| 세컨더리 인덱스   | 행이 있는 자리만 | 리프에서 자리를 확인하고 힙에서 행을 한 번 더 가져옴 |

PostgreSQL에는 클러스터드 인덱스가 없고 전부 세컨더리 방식이라고 영상은 말한다.
인덱스를 찾았는데도 한 번 더 찾아가는 이유가 이것이다.

리프끼리는 옆으로 링크가 이어져 있어서 시작점을 찾으면 옆으로 훑으면 된다.
가격이 5만 원에서 10만 원 사이라는 범위 검색이 빠른 이유이고 정렬된
결과도 따라온다.
필요한 열이 전부 인덱스 안에 있으면 힙에 가지 않고 끝나는데,
이것이 커버링 인덱스(covering index)이고 실행 계획에는 Index Only
Scan으로 찍힌다.

대가는 쓰기에 있다.
행을 쓸 때마다 걸린 인덱스도 전부 고쳐야 한다.
인덱스가 다섯 개면 쓰기 한 번이 여섯 번의 일로 늘어난다.
영상의 결론은 자주 읽는 길목에만 인덱스를 거는 것이 좋은 설계라는 것이다.

### MVCC는 덮어쓰지 않고 새 버전을 쌓는다

출발점은 잃어버린 갱신(lost update)이다.
트랜잭션 A와 B가 같은 계좌 행을 읽는다(잔액 100).
A는 입금을 반영해 120으로, B는 출금을 반영해 80으로 고친다.
둘 다 커밋하면 최종 잔액은 80이고 A의 입금 20은 흔적 없이 사라진다.

MVCC(다중 버전 동시성 제어)의 해법은 덮어쓰지 않는 것이다.
A가 값을 바꾸면 이전 행은 남겨 두고 새 버전을 만든다.
각 트랜잭션은 시작하는 순간 스냅샷을 받고 자기 스냅샷에 있는 버전을 읽는다.
A가 커밋해도 B가 보는 세상은 바뀌지 않으므로 읽기는 쓰기를 막지 않고 쓰기도
읽기를 막지 않는다.

격리 수준은 스냅샷을 언제 찍느냐로 갈린다.

| 격리 수준       | 스냅샷을 찍는 시점      | 같은 트랜잭션에서 두 번 읽으면                                             |
| --------------- | ----------------------- | -------------------------------------------------------------------------- |
| Read Committed  | 문장을 실행할 때마다    | 중간에 커밋된 값이 보인다                                                  |
| Repeatable Read | 처음 한 번, 끝까지 사용 | 결과가 같고 중간에 누가 세 행을 넣어도 나타나지 않는다(팬텀이 갈리는 지점) |

MVCC에는 대가가 둘 있다.
첫째는 남겨진 옛 버전이다.
아무도 읽지 않는 버전이 쌓이면 테이블만 비대해지므로 VACUUM이 치운다.
둘째는 버전으로 풀리지 않는 대기이다.
A가 첫째 행을, B가 둘째 행을 잡은 채 서로의 행을 기다리면 기다림이 원으로 닫히는
데드락(deadlock)이 되고,
데이터베이스가 한쪽을 포기시켜 원을 깬다.

### 옵티마이저는 통계로 비용을 매기고 조인은 세 가지다

옵티마이저는 테이블마다 미리 모아 둔 통계(행 수, 값의 분포)를 보고
방법마다 비용을 매겨 가장 싼 계획을 확정한다.
확정된 계획은 EXPLAIN으로 들여다본다.
처음부터 끝까지 훑는 Seq Scan과 인덱스로 바로 찾는 Index Scan이 갈리고,
계획의 cost는 예상 비용, rows는 예상 행 수이다.
영상은 둘 다 실측이 아니라 통계로 계산한 추정치라고 짚는다.

조인(join) 세 방식은 이렇다.

| 방식        | 동작                                            | 유리한 경우                          |
| ----------- | ----------------------------------------------- | ------------------------------------ |
| Nested Loop | 작은 쪽을 한 줄씩 돌며 큰 쪽을 인덱스로 찾는다  | 행이 적을 때                         |
| Hash Join   | 한쪽 전체를 해시 테이블로 만들어 두고 맞춰 본다 | 큰 조인                              |
| Merge Join  | 양쪽을 정렬한 뒤 나란히 훑으며 병합한다         | 이미 정렬돼 있어 정렬 비용이 빠질 때 |

이 계산은 통계가 맞아야 성립한다.
데이터가 크게 바뀐 뒤 통계가 낡으면 행 수 추정이 틀어지고 비싼 계획을 고른다.
그래서 ANALYZE로 통계를 새로 모아 줘야 한다.
영상의 정리는 계획이 이상하면 EXPLAIN을 열고 통계부터 의심하라는 것이다.

## 비평

### cost 수치는 시간이 아니다

설명란의 1편 수치는 cost 13,081.15에서 12.46으로 줄었다는 것이다.
이 값은 약 1,000배의 차이로 읽히지만, 영상이 3편에서 스스로 말하듯 cost는 통계로
계산한 예상 비용이다.
cost의 단위는 시간이 아니므로 이 비율이 실행 시간의 비율이라는 뜻은 아니다.
설명란은 인덱스 전후의 실행 시간(EXPLAIN ANALYZE의 실측)을 적지 않았다.
계획이 바뀌었다는 증거로는 충분하지만 얼마나 빨라졌는지의 증거로는 부족하다.

### 잃어버린 갱신의 해법은 격리 수준에 따라 다르게 나타난다

영상은 잃어버린 갱신을 MVCC의 출발점으로 세우고 해법이 새 버전을 쌓는
것이라고 말한다.
그러나 같은 시나리오를 두 격리 수준에서 돌렸을 때 결과가 어떻게 다른지는
영상에 없다.
스냅샷을 쌓는 것만으로는 두 트랜잭션이 같은 행을 쓰는 충돌이 풀리지 않는다.
서로 다른 버전을 읽은 쓰기끼리 만났을 때 무엇이 일어나는지가 잃어버린
갱신의 핵심인데,
영상이 이 부분을 데드락 설명으로 넘기므로 두 장면이 이어지지 않는다.
또 영상은 Read Committed와 Repeatable Read 둘만 다루고 Serializable은
말하지 않는다.

### 인덱스는 읽는 길목에만 건다는 기준이 구체적이지 않다

영상은 인덱스가 다섯 개면 쓰기가 여섯 번의 일이 된다는 계산을 쓰기
비용으로 든다.
그러나 어떤 읽기 빈도와 쓰기 빈도에서 인덱스를 거는 것이 이득인지의 기준은 없다.
읽기와 쓰기의 비율, 테이블의 크기, 쿼리의 선택도가 모두 이 판단에 들어가는데,
영상의 결론은 자주 읽는 길목이라는 한 줄이다.
EXPLAIN으로 인덱스 전후를 비교해 보라는 안내가 있었다면 이 한 줄을
검증할 수 있었다.

### 7분 46초에 네 주제를 싣는 구조의 한계

각 편은 약 1분 40초에서 2분 15초이다.
이 길이는 개념의 이름과 순서를 익히기에는 맞고, 판단을 내리기에는 짧다.
예를 들어 3편은 통계가 낡으면 계획이 어긋난다고 말하지만 어느 정도의 변화에서
ANALYZE가 필요한지,
자동으로 도는 기능이 있는지는 말하지 않는다.
영상은 오버뷰와 입문의 역할을 하므로 결함이라기보다 범위이며,
이 문서를 읽은 독자는 확인하기의 실험으로 빈자리를 직접 채워야 한다.

## 확인하기

아래는 영상의 주장을 로컬 PostgreSQL에서 확인하는 SQL이다.
이 문서가 실행해 보지는 못했으므로 출력은 환경에 따라 다를 수 있다.

### 인덱스 전후의 계획을 비교한다

```sql
CREATE TABLE products AS
SELECT g AS id, 'item-' || g AS name, (random() * 100000)::int AS price
FROM generate_series(1, 1000000) AS g;
ANALYZE products;

-- 인덱스 전: Seq Scan 계열이 나온다
EXPLAIN ANALYZE SELECT * FROM products WHERE id = 777777;

CREATE INDEX products_id_idx ON products (id);
ANALYZE products;

-- 인덱스 후: Index Scan이 나온다. cost와 함께 실제 시간(actual time)을 본다
EXPLAIN ANALYZE SELECT * FROM products WHERE id = 777777;

-- 열이 모두 인덱스 안에 있는 조회. VACUUM 뒤에 Index Only Scan이 나오는지 본다
VACUUM products;
EXPLAIN SELECT id FROM products WHERE id BETWEEN 1 AND 100;
```

### 격리 수준에 따라 같은 읽기가 달라지는지 본다

```sql
CREATE TABLE account (id int PRIMARY KEY, balance int);
INSERT INTO account VALUES (1, 100);

-- 세션 A: 격리 수준을 바꿔 가며 두 번 실행한다
BEGIN ISOLATION LEVEL READ COMMITTED;  -- 두 번째 실험에서는 REPEATABLE READ
SELECT balance FROM account WHERE id = 1;

-- 세션 B
UPDATE account SET balance = 120 WHERE id = 1;

-- 세션 A: 같은 트랜잭션 안에서 다시 읽는다
SELECT balance FROM account WHERE id = 1;
COMMIT;
```

READ COMMITTED에서는 두 번째 읽기가 120,
REPEATABLE READ에서는 100이 나오는지 확인한다.

### 데드락을 만든다

```sql
CREATE TABLE rows_for_lock (id int PRIMARY KEY, v int);
INSERT INTO rows_for_lock VALUES (1, 0), (2, 0);

-- 세션 A
BEGIN;
UPDATE rows_for_lock SET v = 1 WHERE id = 1;

-- 세션 B
BEGIN;
UPDATE rows_for_lock SET v = 1 WHERE id = 2;

-- 세션 A: 둘째 행을 기다린다
UPDATE rows_for_lock SET v = 2 WHERE id = 2;

-- 세션 B: 첫째 행을 기다리면 원이 닫힌다. 한쪽이 포기되는지 본다
UPDATE rows_for_lock SET v = 2 WHERE id = 1;
```

### 조인 방식이 데이터 크기에 따라 바뀌는지 본다

```sql
CREATE TABLE customers AS
SELECT g AS id, 'customer-' || g AS name
FROM generate_series(1, 100000) AS g;

CREATE TABLE orders AS
SELECT g AS id, (random() * 99999 + 1)::int AS customer_id, (random() * 1000)::int AS amount
FROM generate_series(1, 500000) AS g;

ANALYZE customers;
ANALYZE orders;

-- 조건을 바꿔 가며 Nested Loop, Hash Join, Merge Join이 나오는지 본다
EXPLAIN SELECT c.name, o.amount
FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE c.id < 50;

EXPLAIN SELECT c.name, o.amount
FROM customers c JOIN orders o ON o.customer_id = c.id;
```

대량 입력 뒤 ANALYZE를 빼고 같은 EXPLAIN을 돌려 보면,
통계가 낡았을 때 rows 추정이 틀어지는지 볼 수 있다.

## 체크리스트

- EXPLAIN에서 cost와 실제 시간(EXPLAIN ANALYZE의 actual time)을 구분해서 읽는가?
- 새로 거는 인덱스마다 그 인덱스를 쓰는 쿼리가 EXPLAIN에서 실제로 인덱스를 쓰는지 확인했는가?
- 테이블에 걸린 인덱스 수와 쓰기 빈도를 함께 보았는가?
- 같은 트랜잭션에서 값을 두 번 읽는 코드가 있다면 어느 격리 수준에서 도는지 알고 있는가?
- 읽은 값에 기대어 쓰는 코드(잔액을 읽고 계산해 쓰는 식)가 동시 실행에서 안전한지 확인했는가?
- 여러 행을 갱신하는 트랜잭션이 같은 순서로 행을 잡는가?
- 대량 입력이나 삭제 뒤에 ANALYZE를 돌렸는가?
- 계획이 이상할 때 통계부터 확인하는 순서를 지키는가?

## 기억할 원칙

### 계획을 의심할 때는 통계부터 본다

옵티마이저는 통계로 비용을 계산하고 계획은 그 계산의 결과이다.
계획이 이상한 것은 대부분 계산의 입력인 통계가 현실과 어긋났기 때문이라는 것이
영상의 순서이다.
쿼리를 고치거나 인덱스를 거는 일은 그 뒤이다.
EXPLAIN의 rows 추정과 실제 행 수를 비교하는 것이 첫 확인이다.

### 읽기와 쓰기가 서로 막지 않는 값을 청소로 치른다

MVCC는 덮어쓰지 않아서 읽기와 쓰기가 막히지 않게 하고,
그 대가로 옛 버전을 청소해야 한다.
이 구조는 인덱스에도 같은 모양으로 나타난다.
읽기를 빠르게 하는 장치는 쓰기에서 비용을 받는다.
성능 문제를 볼 때는 어느 쪽이 이득을 보고 어느 쪽이 값을 치르는지를
먼저 적어 본다.
