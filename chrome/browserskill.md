# BrowserSkill: 에이전트에게 내 로그인 상태를 빌려주는 브라우저 브리지

<https://github.com/Tencent/BrowserSkill>

## 소개

BrowserSkill은 Tencent가 MIT 라이선스로 공개한 브라우저 자동화 브리지다.
Cursor, Claude Code, Codex, OpenClaw, CodeBuddy, WorkBuddy, Pi, Hermes Agent,
DeepSeek Harness 등 셸을 호출할 수 있는 모든 에이전트를 사용자가 **이미
로그인해 둔** 브라우저에 연결한다.

이 프로젝트가 내거는 계약은 두 가지 축으로 되어 있다.
첫째, 에이전트는 별도의 테스트 계정 없이 사용자의 실제 세션을 그대로 쓴다.
둘째, 그 대가로 에이전트는 사용자의 브라우저를 마음대로 건드리지 못한다.
에이전트의 작업은 별도의 **Agent Window**에서 돌아가고, 사용자가 이미 열어 둔
탭을 만지려면 명시적으로 빌려야(borrow) 하며, 일이 끝나면 돌려줘야 한다.

경계도 분명하다.
런타임은 `bsk` CLI/데몬과 브라우저 확장 두 조각이며, 지원 대상은 macOS
(Apple Silicon·Intel), Linux(x64·ARM64), Windows x64와 Chrome·Microsoft Edge다.
다른 Chromium 계열 브라우저는 확장을 설치할 수 있으면 동작할 것으로 보지만
보장하지는 않으며, Firefox는 계획 단계다.
스킬 문서는 자격 증명, 쿠키, 토큰 등 비밀 정보를 추출하지 말라고 못박는다.

## 동작 방식

핵심은 에이전트가 브라우저와 **직접 말하지 않는다**는 것이다.
경로는 다음과 같이 네 단계를 거친다.

```text
Agent Harness  --(shell: bsk ...)-->  bsk CLI
bsk CLI        --(local IPC)------->  bsk daemon
bsk daemon     --(WebSocket, 127.0.0.1)-->  Browser Extension
Extension      --(automates)-------->  Agent Window
Extension      --(빌렸을 때만)------>  사용자의 일반 창
```

모든 통신이 로컬호스트에서 일어나고, 자동화의 실제 실행 주체는 브라우저 확장이다.
에이전트는 요청을 넣을 뿐이고 확장이 사용자의 설정을 근거로 그 요청을 허용하거나
거부한다.
DeepSeek Harness 플러그인도 같은 경로를 탄다.
에이전트가 주입된 `browser_*` 도구를 호출하면 플러그인이 대신 `bsk`를 실행한다.

이 구조가 중요한 이유는 권한의 위치 때문이다.
CDP(Chrome DevTools Protocol)를 직접 붙이는 방식은 에이전트가 디버깅 포트를 잡는
순간 브라우저 전체를 얻는다.
BrowserSkill은 그 권한을 확장 쪽에 두고, 에이전트에게는 요청권만 준다.
뒤에서 다룰 `--unattended` 플래그의 무력화도 이 설계의 직접적인 귀결이다.

### 세션이 작업의 단위다

`bsk`의 거의 모든 명령은 `--session <id>`를 요구한다.
작업은 `bsk session start --json`으로 시작해 `session_id`를 얻고,
`bsk session stop <id>`로 끝낸다.
`session stop`만 ID를 위치 인자로 받는다는 점이 예외다.

세션 종료는 선택이 아니라 정리 책임이다.
성공하든 실패하든 종료해야 하고, 그래야 빌린 탭이 사용자에게 돌아간다.
돌려준 탭은 닫히지 않고 사용자의 창에 그대로 남는다.
유휴 정리(idle cleanup)에 기대거나, 공유 데몬을 재시작해서 작업을 마무리하는 것은
금지된 우회다.

### 관찰과 참조(ref)의 수명

읽기의 기본 도구는 `bsk observe`다.
텍스트, 조작 가능한 컨트롤, 그리고 `@e3` 형태의 참조를 함께 돌려준다.
상호작용은 항상 “관찰해서 얻은 신선한 ref”로만 한다.

ref는 쉽게 썩는다.
페이지 이동은 ref를 무조건 무효화하고, 큰 DOM 변경도 무효화할 수 있다.
그래서 이동하거나 페이지가 크게 바뀌었으면 다시 관찰해야 한다.
반대로 성공이 눈에 보이면 거기서 멈춰야 하며, 확인을 위해 새로고침을 반복하는 것은
명시적으로 말리는 행동이다.

읽기 도구는 용도별로 갈린다.
`observe`는 평범한 컨트롤 찾기, `snapshot`은 정적 접근성 트리,
`get-html`은 정확한 마크업이나 숨은 메타데이터, `screenshot`은 시각적 내용이다.
평범한 버튼을 찾겠다고 HTML이나 이미지부터 뒤지는 것은 권장되지 않는다.

## 설치하기

가장 짧은 경로는 에이전트에게 설치를 시키는 것이다.

```text
Set up browser-skill on this machine by following https://raw.githubusercontent.com/Tencent/BrowserSkill/main/AGENT_INSTALL.md
```

수동 설치는 네 단계다.

```bash
# 1. CLI 설치 (~/.local/bin)
curl -fsSL https://raw.githubusercontent.com/Tencent/BrowserSkill/main/install.sh | sh
export PATH="${BSK_INSTALL_DIR:-$HOME/.local/bin}:$PATH"

# 2. 브라우저 확장은 Chrome 웹 스토어 / Edge 애드온에서 설치

# 3. 하네스에 스킬 설치 (대화형: Space로 선택, Enter로 설치)
bsk install-skill

# 비대화형으로 특정 하네스를 지정할 때
bsk install-skill --harness cursor --json

# 4. 연결 확인
bsk doctor
bsk --version
```

Windows는 PowerShell에서 `irm https://raw.githubusercontent.com/Tencent/BrowserSkill/main/install.ps1 | iex`를
쓴다.

`export PATH`는 지금 셸에만 적용된다는 점을 유의해야 한다.
에이전트는 명령마다 새 셸을 띄우는 경우가 많아서, 같은 PATH 설정을 매번 넣거나
설치된 바이너리의 절대 경로를 써야 한다.
설치 후에도 에이전트가 예전 PATH를 들고 있으면 에이전트를 재시작한다.

`bsk doctor`는 스킬이 설치되지 않은 상태에서도 통과(`N/A`)할 수 있으므로,
스킬이 하네스에서 실제로 보이는지는 따로 확인해야 한다.

### 스킬 파일의 소유권 모델

`bsk install-skill`이 설치한 `SKILL.md`는 자동 갱신 대상이지만, 조건이 붙는다.
데몬 시작, `session start`, `doctor` 시점에 동기화가 일어나되
**파일 내용이 마지막으로 설치한 버전과 여전히 같을 때만** 갱신한다.
사용자가 손댔으면 그 편집을 보존하고 자동 갱신을 멈춘다.

직접 쓴 지시문을 명시적 커스텀으로 못박으려면 `--source`를 쓴다.

```bash
# 내 지시문을 커스텀으로 고정 (내용이 번들 스킬과 같아도 커스텀으로 유지된다)
bsk install-skill --harness cursor --source ./SKILL.md --force

# 번들 스킬로 되돌리고 자동 갱신 재개 (기존 지시문을 덮어쓴다)
bsk install-skill --harness cursor --force
```

내용이 다른 과거 파일이나 알 수 없는 소스 마커가 발견되면 `doctor`가 `WARN`과
복구 방법을 보여준다.
이 경고는 헬스 체크를 실패시키지 않는다. `--json`에서 `status: "warn"`이지만
`ok: true`다.

## 조작 명령

관찰에서 실제로 나온 ref만 쓴다는 전제로:

| 필요한 동작        | 명령                                              |
| ------------------ | ------------------------------------------------- |
| 클릭               | `bsk click @e3 --session <id>`                    |
| 입력               | `bsk fill @e3 --value "text" --session <id>`      |
| 옵션 선택          | `bsk select @e3 --value "option-value" --session <id>` |
| 키 입력            | `bsk press Enter --ref @e3 --session <id>`        |
| 호버 메뉴 펼치기   | `bsk hover @e3 --session <id>`                    |
| 요소를 화면에 노출 | `bsk scroll-to @e3 --session <id>`                |
| 휠 스크롤          | `bsk wheel --delta-y 600 --session <id>`          |
| 포커스 / 해제      | `bsk focus @e3` / `bsk blur @e3`                  |

`select`는 보이는 레이블이 아니라 옵션의 `value`를 받는다.
`scroll-to`는 최상위 뷰포트 CSS 픽셀 기준의 조상 클리핑 경계를 돌려주며,
일부만 보여도 성공으로 친다. 다만 가려짐(occlusion)은 검사하지 않는다.
`wheel`은 부호 있는 델타를 보낼 뿐, 실제로 얼마나 스크롤될지는 보장하지 않는다.
어느 쪽이든 결과는 다시 관찰해서 확인해야 한다.

호버 메뉴에는 별도의 규약이 있다.
관찰 결과에 `[hover first: Shoes | Bags]`, `[has-submenu]`, `[expanded]` 같은
마커가 붙어 있으면 그 요소가 트리거다.
트리거를 호버하고, 다시 관찰하고, 그때 드러난 항목의 ref를 쓴다.
마커에 나열된 레이블은 ref가 아니다.
기대한 컨트롤이 없고 트리거를 식별할 마커도 없을 때만 `observe --probe-hover`를
한 번 시도한다. 이건 실제 페이지를 건드리고 수 초가 드는 비싼 동작이다.

### 큰 페이지를 나눠 읽기

기본 토큰 상한은 없다.
`observe --max-tokens <n>`을 쓰면 `next_cursor` 또는 `@more`가 돌아오고,
관련 내용이 남았을 때 이어 읽는다.

```bash
bsk observe --cursor <token> --session <id>
```

이어 읽기에는 함정이 하나 있다.
각 페이지는 ref 맵을 **교체**하므로, 이전 페이지의 ref를 재사용하면 안 된다.
또 이어 읽기는 같은 캡처를 읽을 뿐 새로고침이나 호버를 하지 않으므로,
깊이 변경이나 호버 프로빙과 섞으면 안 된다.
새 `observe`/`snapshot`을 하거나 페이지 정체성이 바뀌면 커서는 무효가 된다.

## 탭 빌리기

사용자 탭을 만지는 유일한 합법 경로다.

```bash
bsk tab list --scope user --session <id>
bsk tab borrow <tab-id> --session <id>
bsk tab return <tab-id> --session <id>
```

탭 ID를 지어내지 않고, 관계없는 작업 사이에 사용자 탭을 붙들고 있지 않는다.
대기 중이거나 거절됐거나 타임아웃된 빌리기를 반복하지 않는다.
`borrow_outcome_unknown`이 오면 재시도가 아니라 탭/세션 상태부터 확인한다.
탭이 이미 옮겨졌을 수 있기 때문이다.

`bsk tab borrow --timeout 120s`는 **확인을 기다리는 시간**만 바꾼다.
확인 자체를 없애지 못한다. 기본값은 60초이며, 커스텀 대기 시간은 데몬과 확장이
모두 프로토콜 1.2 이상이어야 한다.

Agent Window 안에 있더라도 소유하지 않은 탭(페이지가 스스로 연 팝업 등)은
자동으로 제어권이 생기지 않는다. 사용자가 그 탭을 자기 창으로 옮긴 뒤에야
빌릴 수 있다.

## 사람에게 넘기기

로그인, CAPTCHA, OTP, 결제 확인, 동의 절차처럼 사람만 할 수 있는 단계,
또는 두 번 시도해도 진전이 없을 때 사람을 호출한다.

```bash
bsk request-help --session <id> --prompt "Please complete sign-in" --target @e3
```

| 결과                      | 다음 행동                                              |
| ------------------------- | ------------------------------------------------------ |
| `continued` / `completed` | 다시 관찰하고 새 ref로 재개한다                        |
| `cancelled` / `timed_out` | 거절이나 차단을 존중한다. 같은 요청을 반복하지 않는다  |
| `disabled`                | 사람이 아무 것도 하지 않았다. 아래 규칙을 따른다       |
| 썩은 ref                  | 관찰 후 의도했던 동작을 한 번만 재시도한다             |
| 모르는 탭/세션            | 목록을 조회한다. ID를 추측하거나 남의 세션을 쓰지 않는다 |
| 타임아웃 / 효과 불명      | 재시도 전에 현재 상태를 확인한다. 이미 일어났을 수 있다 |
| `fill_value_mismatch`     | 필드를 읽는다. 포맷팅 차이일 수 있으니 무작정 다시 채우지 않는다 |

여기서 놓치기 쉬운 규칙이 있다.
**이동(navigation)만으로는 완료가 아니다.**
페이지가 바뀌었다는 사실은 목표 달성의 증거가 아니라는 뜻이다.

도움이 비활성화된 경우의 규칙은 더 엄격하다.
도움을 요청하지도, 다시 켜지도 않는다.
비활성화는 권한을 추가해 주지 않으며, 탭 빌리기 확인이나 호스트 제한을 없애지도
않는다.
권한이 허락되면 비전 모델이 그래픽 검증을 시도할 수는 있지만,
휴대폰 QR 스캔, 얼굴 인증, 받을 수 없는 SMS 코드, 텍스트 전용 모델에게 주어진
이미지 CAPTCHA는 그대로 막힌 채 남는다.
같은 실패를 반복하거나 제한을 우회하려고 다른 백엔드로 갈아타는 것은 금지된다.

## 스크린샷과 Canvas

```bash
bsk screenshot --session <id> --out viewport.png
bsk screenshot --session <id> --ref @e3 --out element.png --json
bsk screenshot --session <id> --full-page --out page.png
bsk screenshot --session <id> --full-page --scope current --out loaded.png
```

`--ref`와 `--full-page`는 함께 쓸 수 없다.
`--out`은 기존 파일을 덮어쓰고, 생략하면 임시 경로를 쓴다.
`--json`은 크기와 바이트 수를 함께 돌려준다.

전체 페이지 캡처의 `--scope`는 의미가 크게 다르다.

| `--scope` | 동작                                                         |
| --------- | ------------------------------------------------------------ |
| `follow`  | 기본값. 스크롤하면서 추가로 붙는 콘텐츠까지 따라간다         |
| `current` | 최초 문서 높이에서 멈춘다. 로딩 표시가 남아 있어도 거기까지다 |

`current`로 찍었으면 그 아래 콘텐츠는 빠져 있으므로,
“피드 전체를 불러왔다”고 말하면 안 되고 캡처한 범위를 그대로 보고해야 한다.

Canvas는 별도 규약이 있다.
`@eN canvas [visual:screenshot]`로 표시된 요소는 관찰이 픽셀이 아니라 텍스트를
돌려준다. 내용이 중요하면 그 ref를 스크린샷으로 찍어야 하고,
주변 레이블을 보고 Canvas 안의 컨트롤을 추측해서는 안 된다.
이미지에서 본 좌표를 클릭하려면 그 스크린샷의 `capture_id`를 들고 있어야 한다.

```bash
bsk click @e3 --capture <capture-id> --image-x <x> --image-y <y> --session <id>
```

좌표는 리사이즈된 표시 픽셀이 아니라 **원본 PNG 좌표계**를 쓴다.
캡처는 일회용이고 2분 뒤 만료되며, ref가 교체되거나 그 ref의 새 스크린샷을
찍으면 무효가 된다.
Canvas에서 클릭·버튼·수식어 키는 동작하지만, 채우기, IME, 드래그, 호버,
HTML 추출은 동작하지 않는다.

## 트레이드오프

### 실제 로그인 세션을 쓰면 실수의 비용이 실제가 된다

BrowserSkill이 파는 가치는 “별도 테스트 계정이 필요 없다”는 것이고,
그 값은 “실패가 테스트 데이터가 아니라 진짜 계정에서 일어난다”는 것이다.
헤드리스 브라우저가 더미 계정으로 잘못된 폼을 제출하면 로그 한 줄이 남지만,
같은 실수를 내 로그인 세션으로 하면 실제 주문이 들어가고 실제 메일이 나간다.

명백해 보이는 해법인 “읽기 전용 모드”는 이 문제를 풀지 못한다.
읽기와 쓰기의 경계가 HTTP 메서드에 있지 않기 때문이다.
“확인” 버튼을 눌러야 다음 페이지가 보이는 흐름, 검색 결과를 얻으려면 폼을 제출해야
하는 사이트에서 클릭은 읽기 수단이면서 동시에 쓰기다.
BrowserSkill이 이 문제를 해결하지 않고 **사람에게 밀어둔** 것은 정직한 선택이지만,
해결한 것은 아니다.

남는 어려움은 확인 피로다.
탭 빌리기 확인을 켜 두면 안전하지만 매번 눌러야 하고,
반복적으로 누르다 보면 내용을 읽지 않고 누르게 된다.
끄면 편하지만, 정확히 그 순간 방어선이 사라진다.
어느 쪽도 “안전하면서 편한” 지점이 아니다.

### 확장에 권한을 두면 에이전트가 우회할 수 없지만, 스크립트도 못 한다

0.3.0에서 `--unattended`, `tab borrow --no-confirm`, `BSK_REQUEST_HELP=off`가
확인을 건너뛰지 못하게 바뀐 것은 이 설계의 핵심 결정이다.
이 세 입력은 호환성을 위해 여전히 받아들여지지만 deprecated이고,
확장의 저장된 설정을 이길 수 없다.
CLI는 이런 입력이 쓰이면 알림 로그를 남기고, 데몬도 상속받은 환경 설정에 대해
같은 로그를 남긴다.

에이전트 관점에서 이건 좋은 소식이다.
에이전트가 자기 명령줄에 플래그를 하나 더 붙여서 사용자의 방어선을 내릴 수 없다.
스킬 문서가 “확인을 우회하려고 브라우저 저장소나 설정을 바꾸지 말라”고 따로
적어 둔 것도 같은 맥락이다.

대가는 CI와 스크립트 쪽에서 나온다.
이제 무인 운영을 하려면 사람이 브라우저 확장 팝업에서 토글을 꺼야 한다.
그 설정은 브라우저 프로필에 저장되고 모든 세션에 적용된다.
즉 “이 한 번의 실행만 무인으로”가 불가능해졌고, 무인 실행을 원하면
그 프로필 전체를 상시 무방비 상태로 두는 수밖에 없다.
세밀한 제어를 포기하고 우회 불가능성을 산 것이다.

### 프로토콜 버전이 세 조각으로 쪼개져 있다

CLI, 데몬, 확장이 각각 따로 업데이트되고 각자 프로토콜 버전을 가진다.
프로토콜 1.3은 1.0~1.2와 연결 호환성을 유지하므로 평범한 세션과 기본 탭 빌리기는
버전이 어긋나도 계속 동작한다.
하지만 기능별로 요구 버전이 다르다.

| 기능                      | 요구 사항                    |
| ------------------------- | ---------------------------- |
| 일반 세션, 기본 탭 빌리기 | 1.0 이상                     |
| 커스텀 빌리기 대기 시간   | 데몬과 확장 모두 1.2 이상    |
| `request-help`            | 데몬 프로토콜 1.3            |
| 전체 페이지 스크린샷      | CLI와 확장 빌드가 서로 맞아야 |

`request-help`가 1.3을 요구하는 이유가 흥미롭다.
옛 데몬은 브라우저에 묻지 않고 **로컬에서 스스로 답할 수 있기** 때문이다.
즉 버전 요구는 기능 부족이 아니라 보안 경계를 지키기 위한 것이다.

여기서 잘 알려지지 않은 함정이 하나 나온다.
확장만 업데이트해서는 이 문제를 못 고친다.
옛 CLI는 `BSK_REQUEST_HELP=off`를 보고 데몬에 연락하기도 전에 로컬에서 종료할 수
있고, 혼합 버전 설치는 그 레거시 동작을 그대로 유지한다.
확장 스토어 배포가 CLI 릴리스보다 늦을 수 있다는 점도 겹친다.
결국 설정을 온전히 강제하려면 CLI, 실행 중인 데몬, 확장을 **모두** 올려야 한다.

## 함정

### 샌드박스가 데몬을 죽인다

명령마다 백그라운드 프로세스를 정리하는 에이전트 샌드박스에서는 자동 시작이
작동하지 않는다.
데몬은 지속되는 호스트 환경에 따로 띄우고, 샌드박스 안의 **모든** 명령에
공유 `BSK_HOME`과 `BSK_AUTO_START=0`을 넘겨야 한다.
`export`가 셸 호출 사이에 남지 않을 수 있으므로 매 명령에 붙이는 편이 안전하다.

데몬이 없을 때의 올바른 대응은 호스트 쪽 기동이다.
자동 시작을 반복하거나, 홈 경로를 추측하거나, 런타임 파일을 지우거나,
공유 데몬을 재시작하는 것은 모두 잘못된 대응이다.

### 실패했는데 종료 코드가 0이다

`bsk evaluate`는 최후의 수단이며, 스크립트 예외가 발생해도 CLI 종료 코드가 0일 수
있다. 반드시 JSON의 `.ok`를 확인해야 한다.
셸 종료 코드만 보고 성공으로 판단하는 스크립트는 여기서 조용히 틀린다.

### 전체 페이지 캡처가 안 되는 페이지들

브라우저 내부 페이지, 웹 스토어, 중첩 스크롤 패널, 가상화 리스트는 지원하지 않는다.
캡처 탭은 보이는 상태로 유지해야 하고, 뷰포트도 안정적이어야 한다.
캡처와 인코딩 기본 제한은 2분이고 `--timeout 5m`은 전체 페이지 모드에서만 늘린다.

`loading_stalled` 오류는 30초 동안 높이가 자라지 않은 채 로딩 표시만 남았다는 뜻이다.
이때 마감 시간을 늘리는 것은 해법이 아니라고 문서가 직접 말한다.
실패한 전체 페이지 캡처는 부분 이미지를 남기지 않으며,
페이지를 편집하거나 스크린샷을 이어 붙이는 식으로 우회해서도 안 된다.
`page_hidden`은 환경 방해이고 `user_cancelled`는 사용자 입력에 의한 중단으로,
둘은 다른 상황이다.

### 업로드는 자동 대체 경로가 없다

기본 업로드는 업로드 버튼이나 레이블을 클릭해서 파일 선택 대화상자를 가로챈다.
`reason=file_input_not_activated`이고 `effect_state=none`이면 다시 관찰하고,
드롭 존이나 작성기처럼 명확한 첨부 대상일 때만 `--mode drop`을 **한 번** 시도한다.
빈 공간이나 모호한 컨테이너에는 쓰지 않는다.
메커니즘 사이의 자동 대체는 없다.

`effect_state=unknown`이나 `committed`일 때는 재시도도 모드 전환도 하지 않는다.
드롭이 성공했다는 것은 이벤트가 전달됐다는 뜻일 뿐 사이트가 받아들였다는 뜻이
아니므로, 첨부 여부는 관찰로 확인해야 한다.
다운로드는 기본적으로 덮어쓰기를 거부하며, 교체가 의도일 때만 `--overwrite`를 붙인다.

### 기록 기능은 민감한 페이지를 그대로 담는다

`bsk record start`는 사용자 동작을 캡처한다.
문서는 은행, SSO, 비밀번호 관리자 페이지에서는 절대 기록하지 말라고 명시한다.
이 경고가 필요하다는 사실 자체가, 이 도구가 다루는 세션의 성격을 말해 준다.

## 체크리스트

- 작업 시작 시 `bsk session start --json`으로 `session_id`를 확보했는가?
- 성공·실패와 무관하게 `bsk session stop <id>`를 호출하는 경로가 있는가?
- 모든 상호작용이 직전 `observe`에서 나온 ref를 쓰는가?
- 페이지 이동이나 큰 DOM 변경 후에 다시 관찰하는가?
- 사용자 탭을 만질 때 `tab list` → `tab borrow` → `tab return`을 거치는가?
- 자동화 설정 두 토글의 현재 값을 `session start --json`의 `interaction`으로
  확인했는가?
- `evaluate` 결과를 종료 코드가 아니라 JSON `.ok`로 판정하는가?
- 전체 페이지 캡처의 `--scope`가 `current`라면 보고 문구가 그 범위를 밝히는가?
- 샌드박스 환경이라면 모든 명령에 `BSK_HOME`과 `BSK_AUTO_START=0`이 붙는가?
- CLI, 데몬, 확장 버전을 `bsk --version`과 `bsk status`로 함께 확인했는가?

## 기억할 원칙

### 권한은 요청하는 쪽이 아니라 승인하는 쪽에 두어야 한다

BrowserSkill의 0.3.0 변경은 작은 플래그 정리처럼 보이지만 설계 원칙의 선언이다.
에이전트가 자기 명령줄에 붙이는 어떤 입력도 사용자의 저장된 설정을 이길 수 없게
만든 것은, 권한의 소재를 요청자에서 승인자로 옮긴 것이다.

이 원칙은 브라우저 자동화에만 적용되지 않는다.
에이전트에게 도구를 주는 모든 설계에서 같은 질문이 반복된다.
“이 안전장치를 끄는 스위치는 누가 들고 있는가?”
스위치가 에이전트의 인자나 환경 변수에 있으면, 그 안전장치는 에이전트가
자기 판단으로 끌 수 있는 것이고 따라서 안전장치가 아니다.

BrowserSkill은 그 스위치를 브라우저 확장 팝업으로 옮겼다.
에이전트가 닿을 수 없는 곳이다.
대신 그 대가로 세밀한 제어와 프로그래밍 가능성을 잃었다.
이 교환이 옳은지는 맥락에 달렸지만, 교환이 무엇이었는지는 분명하다.

### 상태를 관찰로만 알 수 있으면, 관찰하지 않은 것은 모르는 것이다

이 스킬 문서에 반복적으로 나오는 지시는 한 문장으로 요약된다.
“행동했으면 다시 관찰하라. 이동은 완료가 아니다.
드롭 성공은 수용이 아니다. 효과 불명이면 재시도가 아니라 조회다.”

이것은 브라우저의 특수성이 아니라 부작용이 있는 모든 원격 시스템의 성질이다.
명령을 보냈다는 사실과 원하는 상태에 도달했다는 사실은 다른 명제이고,
둘 사이를 잇는 것은 관찰뿐이다.
에이전트가 가장 자주 저지르는 오류가 바로 이 둘을 등치시키는 것이며,
`effect_state=unknown`일 때 재시도를 금지하는 규칙은 그 오류의 비용
— 같은 주문을 두 번 넣는 것 — 을 막기 위해 존재한다.
