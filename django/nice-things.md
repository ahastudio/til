# 2010년식으로 웹을 만들어 보니: Django에서 좋았던 것과 막힌 것

원문: [Some more things about Django I've been enjoying](https://jvns.ca/blog/2026/07/21/more-nice-django-things/)

HN 토론: <https://news.ycombinator.com/item?id=48997828> (174점, 126개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/x5ewgv> (17점, 3개 댓글)

## 요약

Julia Evans가 2026년 7월 21일에 쓴 글이다.
SQL 데이터베이스를 두고 백엔드에서 HTML을 렌더링하는, 이른바 2010년식으로 웹사이트 만드는 법을 배우는 중이라는 이야기로 시작한다.

그 방식이 자기에게 쉽게 느껴지지는 않는다고 적는다. 2000년대나 2010년대에 그렇게 만드는 법을 배운 적이 없고 배울 것이 많다는 것이다.
이 글은 Go 표준 라이브러리나 Flask로 시도하다 실패했을 때보다 이런 사이트를 만드는 일을 해낼 만하게 느끼게 해 준 Django 기능들과, 겪은 몇 가지 문제를 다룬다.

왜 2010년식으로 배우려 하는지에 대한 설명이 흥미롭다.
이전까지 자신 있던 도구는 정적 사이트 생성기, JavaScript로 재미있는 일을 하는 정적 사이트, 그리고 Lambda나 Go 백엔드를 붙인 단순한 Vue.js 단일 페이지 앱이었다.
아주 단순한 애플리케이션에는 프런트엔드 중심 접근이 정말 좋았지만, 페이지가 하나가 아니라 여럿인 무언가를 생각하기 시작하니 프런트엔드 코드가 많이 드는 선택지들이 그리 내키지 않았다는 것이다.

그리고 두 접근이 사실 같은 동기라고 적는다.
JS를 최대한 적게 쓰는 백엔드 중심 사이트를 쓰는 것과 백엔드에서 최대한 적게 하는 단일 페이지 사이트를 쓰는 것이 정반대로 보이지만, 두 경우 모두 로직을 최대한 한곳에 모으려는 것이라는 설명이다.

좋았던 기능은 넷이다.

첫째는 쿼리 빌더다. Django에서 쿼리셋 클래스를 정의하고 쓰고 싶은 `WHERE` 조건들을 메서드로 만들어 둘 수 있다는 것을 배웠다고 한다.

```python
Events.objects.approved()
  .for_tab(tab)
  .with_festivals(tab_params.festival_slugs)
  .is_free(tab_params.free)
  .is_outdoors(tab_params.outdoors)
```

```python
class EventQuerySet(SearchableQuerySetMixin, models.QuerySet):
    def approved(self):
        return self.filter(approved_at__isnull=False)

    def future(self):
        today = timezone.localdate()
        return self.filter(end__gt=self._midnight(today))

    def with_tags(self, tags):
        if tags:
            return self.filter(tags__name__in=tags).distinct()
        return self
```

필터를 정의하는 문법이 제일 마음에 드는 것은 아니지만 대부분의 시간은 그냥 메서드를 쓰는 데 보내게 되고, 읽기 좋고 쓰기 좋아서 다른 쿼리 빌더 라이브러리도 살펴보고 싶어진다고 적는다.
과거에는 “나는 SQL을 아는데 쿼리 빌더가 왜 필요한가”라고 생각했다는 고백도 덧붙인다.

둘째는 템플릿 필터다.
평문 URL을 링크로 바꾸고 줄바꿈을 `<br>`로 바꾸는 `{{ event.description|urlize|linebreaksbr }}`, 날짜 형식을 맞추는 `{{ row.date|date:"M j" }}`, 그리고 파이썬 딕셔너리를 JSON으로 바꿔 안전한 방식으로 `<script>` 태그에 넣어 주는 `json_script`를 써 봤다고 한다.
개별로는 다 작은 것들이지만 그냥 준비되어 있다는 사실이 왠지 큰 차이를 만든다는 평이다.

가장 좋아하는 필터는 `querystring`이다. 같은 쿼리 스트링에서 한 항목만 바꾼 링크를 만들어 준다.

```html
<a href="{% querystring date=nav.prev_date %}">
<a href="{% querystring outdoors=None %}">
```

셋째는 자동 마이그레이션이다.
모델을 고치기만 하면 Django가 마이그레이션을 자동 생성하는 것이 여전히 정말 좋다고 적는다.
지금까지 19번의 마이그레이션을 했고 앞으로도 더 있을 것 같은데, 문제에 대한 이해가 바뀔 때마다 데이터베이스를 쉽게 바꿀 수 있다는 점이 큰 차이를 만든다는 것이다.

넷째는 상속을 쓰지 않기로 한 결정이다.
Django 문서가 때때로 클래스 기반 뷰와 상속으로 뷰 코드를 정리하는 선택지를 제시하며, 코드를 많이 공유하는 뷰가 넷 있어서 부모 클래스를 만들고 상속시킬 수도 있었다고 한다.
시도해 봤지만 뷰 사이에 코드를 공유하는 데 상속을 쓰는 경험이 즐겁지 않았고, 함수를 쓰는 쪽으로 바꾸니 훨씬 단순했다는 것이다.
다만 Django 자신이 제공하는 인터페이스를 쓰기 위한 상속은 개의치 않는다고 덧붙인다. 쿼리셋을 정의하려면 `class EventQuerySet(SearchableQuerySetMixin, models.QuerySet)`처럼 써야 하는데 깊이 생각하지 않고 잘 동작한다는 것이다.

메타 코멘트도 붙는다.
자기 프로그래밍 의견을 “X가 나에게 좋게 느껴지지 않아서 대신 Y를 선호한다”고만 말하는 연습을 하고 있다는 것이다.
링크한 글은 함수 기반 뷰가 “옳은 방법”이라고 하지만, 자기는 그것이 옳은지에 별로 관심이 없고 다만 다른 사람들도 상속에 대해 비슷하게 느낀다는 것을 아는 게 힘이 된다고 적는다.

문제는 성능이다.
어느 시점에 LLM 스크레이퍼가 사이트를 발견해 초당 10건 정도를 보내기 시작했고, 차단해서 지금은 괜찮지만 사이트의 용량이 얼마인지 생각하게 되었다고 한다.
`ab -n 1000 -c 1`로 가볍게 부하를 줘 보니 월 10달러짜리 VM에서 초당 2~3건을 처리하는 수준이었다.
Go 백엔드는 성능 상황이 꽤 단순한데(대개 그냥 충분히 빠르다) Django 사이트는 매우 다르다는 것이다.

프로파일링 토끼굴로 들어가고 싶은 유혹이 있지만, Django 사이트에서 무엇을 기대해야 하고 더 높은 수준에서 어떻게 생각해야 하는지를 정말 모르겠다고 적는다.
아직 못 정한 것으로 넷을 든다. 간헐적 트래픽 폭증이 있는 사이트라면 스케일 업을 할 수 있어야 하는가, 캐시가 가능하도록 설계해야 하는가(그리고 정말 그래야 하는가, 캐시는 제대로 하기가 너무 성가시다), 성능 문서가 Jinja가 더 빠르다는데 템플릿 시스템 교체를 고민해야 하는가, 같은 문서가 `{% block %}`이 `{% include %}`보다 빠르다는데 차이가 큰지 그렇다면 왜인지다.

그리고 실제 원인 하나를 찾는다.
Django 성능 문서에서 캐시된 템플릿 로더를 켜면 매번 템플릿을 컴파일하지 않아도 되어 성능이 크게 개선되는 경우가 많다는 문구를 봤고, CPU 프로파일에서 템플릿 렌더링에 많은 시간을 쓰고 있었다는 것을 떠올린 것이다.
링크를 따라가 보니 캐시된 템플릿 로더는 기본으로 켜져 있어야 하는 것이었는데, 다른 일을 하다가 실수로 꺼 놓았던 것이었다.
Django 설정 파일이 여전히 꽤 혼란스럽고 어렵다고 느끼는 예라고 적는다.

템플릿 캐싱을 켠 뒤에는 CPU를 다 쓰지 않고도 초당 12건 정도를 무리 없이 처리하는 것 같다고 한다. 전후를 꼼꼼히 벤치마크하지는 않았다고 덧붙인다.

마지막 관찰이 실용적이다.
“성능 문제가 있으면 데이터베이스 쿼리를 확인하고 인덱스를 추가하라”는 조언을 늘 들어 왔는데, 이번 템플릿 캐싱처럼 느린 쿼리 때문이 아닌 성능 문제를 여럿 겪었다는 것이다.
그래서 지금까지는 CPU 프로파일부터 돌리는 쪽이 더 유용했고, SQLite를 쓰고 있으니 느린 쿼리 문제도 어차피 CPU 프로파일에 드러난다고 적는다.

## 분석

### 이 글은 프레임워크 리뷰가 아니라 학습 기록이다

제목이 Django에 대한 것이지만 내용의 축은 저자의 학습 곡선이다.
좋았던 기능 넷은 전부 “몰랐다가 알게 된 것”이고, 막힌 것 하나는 “아직 모르는 것”이다.

이 구조가 글의 신뢰성을 결정한다.
쿼리셋 메서드가 좋다는 말은 Django 경험자에게 새롭지 않지만, SQL을 잘 아는 사람이 쿼리 빌더를 왜 쓰게 되는지에 대한 기록으로는 값지다.
“나는 SQL을 아는데 쿼리 빌더가 왜 필요한가”라고 생각했었다는 문장이 그 전환의 축이고, 그 전환이 문법이 아니라 재사용 가능한 이름 때문에 일어났다는 것이 관찰의 핵심이다.

성능 절이 같은 구조의 반대 면이다.
아직 모른다고 명시하고, 모르는 것을 네 개의 구체적 질문으로 적는다.
프레임워크 리뷰라면 “Django는 느리다” 또는 “충분히 빠르다”로 결론을 냈을 자리에서, 이 글은 결론 대신 질문을 남긴다.

그래서 이 글을 읽는 방법도 정해진다. Django를 평가하는 자료가 아니라, 프런트엔드 중심으로 일해 온 사람이 백엔드 렌더링으로 옮겨 갈 때 무엇이 걸리는지를 보여 주는 자료다.

### 두 접근이 같은 동기라는 관찰이 글 전체를 지탱한다

JS를 최소화한 백엔드 사이트와 백엔드를 최소화한 SPA가 정반대로 보이지만 둘 다 로직을 한곳에 모으려는 것이라는 문단이, 이 글에서 가장 일반화 가치가 높다.

이 관찰이 맞다면 프런트엔드냐 백엔드냐는 근본적인 선택이 아니다. 근본적인 것은 로직이 몇 군데에 흩어지느냐다.
그리고 최악은 양쪽 다 무겁게 만드는 것이며, 실제로 많은 프로젝트가 거기서 고통받는다. 검증 로직이 프런트와 백엔드에 각각 있고, 상태가 브라우저와 서버에 각각 있는 형태다.

저자가 방향을 바꾼 계기도 이 틀 안에서 설명된다.
페이지가 하나일 때는 프런트엔드에 전부 모으는 것이 자연스럽고, 페이지가 여럿이 되는 순간 그 통일성을 유지하는 비용이 급격히 오른다.
라우팅, 페이지별 데이터 로딩, 뒤로 가기, 딥 링크가 전부 직접 다뤄야 할 문제가 되기 때문이다.

Lobste.rs에서 twotwotwo가 같은 지점을 프레임워크 쪽에서 짚었다.
Django나 Rails 같은 프레임워크가 옳게 느껴지는 점은 명사(타입), 관계, 동사(목록·검색·추가·편집)를 두고 그 주위에 좋은 도구 모음을 만들면 꽤 멀리 갈 수 있다는 것이라고 적었다.[^twotwotwo]
Pydantic처럼 스키마를 정의하는 현대적 도구가 있지만, Django는 스키마 선언부터 쿼리와 마이그레이션, 관리자 폼 렌더링까지 모든 계층에 걸쳐 있다는 점에서 이득을 얻는다는 것이다.
그리고 Django를 쓰기 전에는 CRUD라고 생각하지 않았을 작업들이, 익숙해지고 나면 잘 들어맞더라는 관찰을 덧붙였다.
문제가 관계형 모델이 아니라 보일러플레이트였던 경우가 그 예라는 것이다.

### 자동 마이그레이션에 대한 평가가 도구 선택의 진짜 기준을 드러낸다

19번의 마이그레이션이라는 숫자가 이 절의 핵심이다.
저자가 강조하는 것은 마이그레이션이 정확하다는 것이 아니라, 문제에 대한 이해가 바뀔 때마다 데이터베이스를 쉽게 바꿀 수 있다는 점이다.

이 기준이 도구 평가의 축을 옮긴다.
보통 ORM과 마이그레이션 도구는 정확성과 제어권으로 평가된다. 생성된 SQL이 맞는가, 원할 때 손으로 쓸 수 있는가다.
저자의 기준은 다르다. 스키마를 바꾸는 데 드는 마찰이 얼마나 낮은가이며, 그 마찰이 낮으면 설계를 일찍 확정하지 않아도 된다.

HN에서 ranedk가 이 가치를 더 극단적인 형태로 증언했다.
0.95 버전부터 Django를 써 왔고, 지난 10년간 Go 스택이나 Java 스택에서 일할 때도 모델과 마이그레이션에는 여전히 Django를 쓴다는 것이다.[^ranedk]
Django 모델로부터 Gorm DAO나 Hibernate 클래스를 생성하는 도구까지 만들어 두었고, Go 진영의 Atlas나 sqlx나 sqlc 같은 것들이 Django만큼 마이그레이션을 해내지는 못한다고 적었다.

반대편 의견도 있다.
dnautics는 자동 마이그레이션이 무섭다며 Elixir와 Ecto를 쓰고 그냥 마이그레이션을 직접 쓴다고 했다.[^dnautics]
게다가 같은 DB 테이블에 스키마가 둘 이상 필요할 때가 있다는 점을 들었다. 메뉴나 드롭다운을 위한 최소 정보 스키마와 전체 CRUD를 위한 전체 정보 스키마 같은 경우다.

두 입장의 차이는 프로젝트가 어느 단계에 있느냐다.
설계가 아직 흔들리는 단계에서는 자동 생성의 마찰 감소가 압도적이고, 스키마가 안정되고 운영 중인 단계에서는 명시적 마이그레이션의 통제력이 더 중요해진다.
저자가 19번을 자랑스럽게 말할 수 있는 것은 아직 전자에 있기 때문이다.

### 상속을 거부하면서 프레임워크의 상속은 받아들이는 구분이 정확하다

뷰 사이 코드 공유에는 상속을 쓰지 않고, `models.QuerySet`을 상속하는 것은 개의치 않는다는 구분이 이 글에서 가장 정교한 판단이다.

두 상속은 이름만 같지 하는 일이 다르다.
후자는 프레임워크가 정한 인터페이스를 구현하는 것이며, 상속이 사실상 유일한 등록 방법이다. 선택의 여지가 없고 계층도 한 단계다.
전자는 내 코드끼리의 중복을 없애기 위해 계층을 새로 만드는 것이며, 그 계층은 내가 유지해야 하고 깊어질 수 있다.

클래스 기반 뷰가 비판받는 이유가 정확히 여기 있다.
Django의 제네릭 뷰는 여러 믹스인이 메서드 해석 순서로 얽혀 동작하고, 어떤 메서드를 재정의해야 하는지 알려면 그 순서를 머릿속에 그려야 한다.
함수 하나로 쓰면 읽는 사람이 위에서 아래로 따라갈 수 있고, 중복은 평범한 헬퍼 함수로 줄인다.

sakjur가 이 글의 태도 자체를 평했다.
Julia의 글과 진이 하나의 관점을 밀기보다 호기심을 북돋우는 방식으로 소프트웨어를 탐구한다는 점을 존경한다는 것이다.[^sakjur]
“옳은 방법”이라는 표현에 거리를 두고 “나에게 좋게 느껴지지 않았다”로 말하는 선택이, 이 상속 논쟁처럼 오래된 주제에서 특히 유효하게 작동한다.

## 비평

### 초당 2~3건이라는 수치는 Django의 성능이 아니라 설정의 결과일 가능성이 높다

이 글에서 가장 널리 반박된 부분이다.
저자는 이 수치를 Django 사이트의 성능 특성을 이해하지 못하겠다는 근거로 제시하는데, 댓글 다수가 그 수치 자체가 잘못된 조건에서 나왔다고 지적했다.

echoangle은 그 숫자가 말이 안 될 정도로 낮으며 다른 무언가가 있을 것이라고 적었다.[^echoangle]
imperio59는 원인을 구체적으로 짚었다. 프로덕션에서 개발용 HTTP 서버를 쓰면 안 되며, 자기도 성능 좋은 머신에서 처리량이 믿을 수 없이 낮았던 적이 있는데 개발 서버 구현이 단일 스레드이고 동시성을 전혀 다루지 않기 때문이었다는 것이다.[^imperio59]
lazyant은 필요한 구성을 나열했다. nginx가 정적 자산을 서빙하고 그 뒤에 gunicorn과 Django를 두는 배치, SQLite에 적절한 PRAGMA, 일반 콘텐츠에 대한 캐싱을 갖추면 RPS가 한두 자릿수 규모로 개선된다는 것이다.[^lazyant]
sgt은 15년 전 아주 기본적인 하드웨어에서 템플릿을 렌더링하고 제법 복잡한 UI를 처리하면서도 그보다 훨씬 많이 냈다고 적었다.[^sgt]

Lobste.rs의 zipy124가 가장 구체적인 반례를 냈다.
성능 문제가 Django의 결과라고 보지 않으며, 디버그 모드로 `runserver`만 써도 자기 업무 저장소에서 초당 60건 정도가 나온다는 것이다.[^zipy124]
그리고 문제의 일부는 `-c 1`이라는 선택이라고 짚었다. 동시성 1은 웹 워크로드를 제대로 대표하지 못한다는 것이다.
프로덕션 설정에서 동시성을 올리면 11, 23, 54, 95, 153, 165, 177, 192로 올라간다는 측정을 덧붙였다.

이 반론들이 글의 논지를 흔드는 이유는 저자가 이 수치 위에 고민을 쌓았기 때문이다.
스케일 업을 해야 하는가, 캐시 설계를 해야 하는가, Jinja로 옮겨야 하는가라는 네 질문은 전부 “지금 너무 느리다”를 전제로 한다.
전제가 측정 오류라면 네 질문의 우선순위가 전부 달라진다. 템플릿 엔진 교체를 고민하기 전에 WSGI 서버를 붙이는 것이 먼저다.

다만 저자가 “제대로 벤치마크하지 않았다”고 여러 번 밝힌 점은 짚어 둘 필요가 있다.
글의 잘못은 측정이 틀렸다는 것이 아니라, 틀렸을 수 있는 측정 위에 프레임워크 수준의 질문을 세웠다는 데 있다.

### 설정 파일이 어렵다는 진단이 원인을 잘못 짚는다

캐시된 템플릿 로더를 실수로 꺼 놓았던 일화를, 저자는 프레임워크이기 때문에 잘못 설정하기 쉽다는 예로 제시한다.
그리고 Django 설정 파일이 여전히 혼란스럽고 어려우니 조심해야겠다고 결론을 낸다.

이 진단이 문제를 개인의 부주의로 되돌린다.
실제 문제는 설정 파일의 난이도가 아니라, 잘못된 설정이 아무 신호도 내지 않는다는 데 있다.
템플릿 로더를 껐을 때 사이트는 정상 동작하고, 응답도 정확하며, 단지 느릴 뿐이다. 그 느림을 성능 문제로 인지하고 프로파일을 돌리고 문서를 읽기 전까지 아무도 알려 주지 않는다.

이런 종류의 실패는 “조심하기”로 막을 수 없다.
막는 방법은 설정을 검사하는 장치다. Django에는 실제로 `manage.py check --deploy`가 있고, 프로덕션 배포 시 흔한 실수를 지적한다.
저자가 그 명령을 언급하지 않는다는 것은 몰랐다는 뜻이고, 그렇다면 문제는 설정 파일이 어렵다는 것이 아니라 그 도구가 발견되지 않는다는 것이다.

stuaxo가 성능을 생각할 때 가장 먼저 할 일로 Django debug toolbar를 설치해 뷰와 그 뷰가 유발하는 쿼리를 확인하는 것을 들었다.[^stuaxo]
이것도 같은 성질의 지적이다. 프레임워크에는 이런 상황을 위한 도구가 이미 있는데, 그 존재가 사용자에게 도달하지 않는다.

즉 이 일화가 드러내는 것은 설정의 복잡도가 아니라 발견 가능성의 문제이며, 글은 그 구분을 하지 않는다.

### 좋았던 기능 목록이 Django 고유의 것인지 검증되지 않는다

글이 좋다고 꼽은 넷 중 셋은 Django만의 것이 아니다.
체이닝 가능한 쿼리 빌더는 SQLAlchemy부터 Ecto까지 흔하고, 템플릿 필터는 Jinja와 Liquid와 ERB 헬퍼에 다 있으며, 자동 마이그레이션 생성은 Alembic과 Ecto와 Rails에도 있다.

이것이 글의 결함인 이유는 저자가 비교 대상을 명시했기 때문이다.
Go 표준 라이브러리나 Flask로 시도하다 실패했던 것과 대비해 Django가 해낼 만하게 느껴졌다고 썼다.
그런데 그 대비의 어느 정도가 Django의 설계 덕이고 어느 정도가 배터리 포함 여부 덕인지가 구분되지 않는다.

실제로 이 목록을 관통하는 공통점은 개별 기능의 우수함이 아니라 함께 있다는 사실이다.
저자 자신이 템플릿 필터에 대해 “개별로는 다 작은 것들이지만 그냥 준비되어 있다는 사실이 왠지 큰 차이를 만든다”고 정확히 그렇게 적는다.
그렇다면 글의 결론은 “Django의 이 기능들이 좋다”가 아니라 “통합된 프레임워크가 조립된 라이브러리보다 배우기 쉽다”여야 한다.

그리고 그 결론에는 반대급부가 있는데 글이 다루지 않는다.
melodyogonna는 Django가 좋지만 너무 커서 프로젝트를 Go로 옮기고 있다고 적었다. 문서를 소화하는 것 자체가 일이고 PDF가 3,000쪽이며, 모든 부분이 머릿속에 들어오는 도구로 일하는 것을 좋아한다는 것이다.[^melodyogonna]
seanwilson은 더 구체적인 대가를 나열했다. 기본 템플릿 언어에서 `{% if a and (b or c) %}` 같은 괄호가 안 되고, `{{ x * 2 }}` 같은 기본 산술이 안 되면서 `{{ x|add:"2" }}`는 되며, 표현식을 변수에 넣을 수 없어 반복해야 하고, 템플릿이 만든 HTML을 변수에 담아 슬롯 형태로 넘길 수 없고, 모델 메서드에 인자를 넘길 수 없다는 것이다.[^seanwilson]
템플릿에 복잡한 로직이 없어야 한다는 철학은 이해하지만 위의 제약들은 꽤 자의적이며 유지보수가 더 어려운 코드로 이어진다는 평이다.

BrenBarn은 필터의 이중 밑줄 문법이 칠판을 손톱으로 긁는 느낌이라며, 연산자 오버로딩으로 진짜 쿼리 표현식 언어를 만들지 않은 것이 이해가 안 된다고 적었다.[^BrenBarn]
저자가 “필터를 정의하는 문법이 제일 마음에 드는 것은 아니다”라고 한 문장을 지나친 것을, 이 댓글이 정면으로 받는다.

### 규모가 커진 뒤의 비용이 시야에 없다

19번의 마이그레이션은 시작 단계의 숫자다.
자동 마이그레이션의 마찰 없음이 유지되는 구간이 얼마나 되는지를 글은 묻지 않는다.

a_c가 수천 개의 마이그레이션과 수십 개의 앱으로 Django 애플리케이션을 운영한 경험을 적었다.[^a_c]
모델이 얽힌 테스트가 느리다는 것이 첫 번째다. 모든 마이그레이션을 실행하기 때문이며, 모델이 없는 함수 테스트는 파이썬 기본 `unittest`로 빠르게 돌아간다는 것이다.
비즈니스 로직에 권장되는 패턴이 액티브 레코드라서 모델에 대한 함수를 모델 옆에 두게 되는데, 깨끗한 경우에는 좋지만 여러 모델이 얽힌 작업에는 잘 맞지 않는다는 점도 들었다.
데이터 마이그레이션은 통화 목록처럼 열거형 같은 데이터를 팀 전체에 공유할 때 편리하다고 했다.
그리고 새 팀원이 Django 앱을 새로 만들고 싶어 하는 유혹이 크다는 점을 짚었다. 기존 비즈니스 맥락을 신경 쓰지 않고 새로 시작하는 느낌이 들기 때문인데, 앱 사이의 개념적 경계를 설계하는 일이 매우 중요하다는 것이다.

이 목록이 저자의 글과 정확히 반대 방향을 가리킨다.
저자에게 자동 마이그레이션은 스키마를 자유롭게 바꾸게 해 주는 것이고, a_c에게는 테스트를 느리게 만드는 누적된 이력이다.
액티브 레코드도 마찬가지다. 모델 옆에 로직을 두는 것은 모델이 적을 때 자연스럽고, 많아지면 경계 문제가 된다.

글이 초기 단계의 기록이므로 이 비용을 다루지 않는 것이 잘못은 아니다.
다만 “여전히 정말 좋다”는 평가가 시간 축을 갖지 않은 채로 제시되면, 읽는 사람은 그것이 전 구간에 걸친 평가라고 받아들이기 쉽다.

## 인사이트

### 프로파일부터 돌린다는 습관이 조언보다 나은 이유는 병목이 계층을 가리지 않기 때문이다

글의 마지막 관찰이 가장 실용적이다.
“성능 문제면 쿼리를 보라”는 조언을 늘 들었지만, 실제로 겪은 문제들은 느린 쿼리가 아니었고 그래서 CPU 프로파일부터 돌리는 쪽이 유용했다는 것이다.

이 조언이 왜 자주 빗나가는지에는 역사적 이유가 있다.
쿼리를 먼저 보라는 규칙이 자리 잡은 시기의 전형적 웹 애플리케이션은 데이터베이스가 별도 머신에 있고, 네트워크 왕복이 있고, N+1 쿼리 한 번이 수백 밀리초를 먹는 구조였다.
그 환경에서는 병목이 거의 항상 DB였고, 프로파일링은 비싸고 번거로운 작업이었다.

지금의 조건이 다르다.
SQLite를 같은 프로세스에서 쓰면 쿼리 비용이 CPU 시간으로 나타나고, 저자가 정확히 짚은 대로 어차피 CPU 프로파일에 드러난다.
그리고 py-spy 같은 도구는 코드를 바꾸지 않고 실행 중인 프로세스에 붙을 수 있어서, 프로파일링의 비용이 조언이 만들어지던 시절보다 훨씬 싸다.

일반화하면 규칙이 나온다. 병목의 위치를 미리 가정하는 조언은 그 조언이 만들어진 아키텍처에 묶여 있다.
계층을 가리지 않고 측정하는 도구가 싸졌다면, 가정을 버리고 측정부터 하는 것이 항상 옳다.
그리고 이 원칙은 다음번 조언에도 적용된다. 오늘 “먼저 프로파일하라”가 옳은 이유도 영원한 진리라서가 아니라 지금 프로파일링이 싸기 때문이다.

### 프레임워크의 기본값이 성능 계약의 일부라는 점이 잘 인지되지 않는다

캐시된 템플릿 로더 일화에서 가장 중요한 사실은 그것이 기본으로 켜져 있었다는 점이다.
즉 Django는 성능에 중요한 결정을 이미 내려 두었고, 사용자는 그것을 모른 채 누리고 있었다.

이 구조가 만드는 함정이 있다.
설정 파일을 만지는 이유는 대개 다른 목적이고, 그 과정에서 관련 없어 보이는 기본값이 함께 날아간다.
저자의 경우 `TEMPLATES` 설정에서 로더를 직접 지정하는 순간 기본으로 딸려 있던 `cached.Loader` 래핑이 사라진 것이다.
이것은 부주의가 아니라 설계의 결과다. 설정을 일부만 재정의할 방법이 없고 통째로 교체하게 되어 있으면 이런 일이 반드시 일어난다.

더 일반적으로 말하면, 프레임워크의 기본값은 문서화된 계약의 일부가 아니라 암묵적 계약이다.
API 시그니처는 바뀌면 컴파일이 깨지거나 테스트가 실패하지만, 기본값이 바뀌거나 사라지면 아무 일도 일어나지 않고 그냥 느려지거나 덜 안전해진다.

그래서 프레임워크를 쓰는 쪽이 가져야 할 습관이 하나 정해진다.
설정 블록을 통째로 재정의할 때는, 재정의하기 전의 기본값이 무엇이었는지를 먼저 확인하는 것이다.
Django라면 `django/conf/global_settings.py`를 열어 보는 일이고, 어느 프레임워크든 그에 해당하는 파일이 있다.
이 한 단계가 저자가 겪은 종류의 문제를 대부분 막는다.

### 학습자가 프레임워크에서 얻는 것은 기능이 아니라 어휘다

이 글의 좋았던 기능 목록을 다시 보면, 저자가 실제로 얻은 것은 코드를 줄여 주는 기능이 아니라 문제를 부르는 이름들이다.

쿼리셋 메서드가 그 예다. `approved()`나 `is_free()`는 SQL로 쓰면 한 줄이고, 절약되는 타이핑은 미미하다.
얻는 것은 “승인된 이벤트”라는 개념에 이름이 붙고, 그 이름이 코드 곳곳에서 같은 의미로 쓰인다는 사실이다.
저자가 “읽기 좋고 쓰기 좋다”고 한 것이 정확히 이 효과이며, SQL을 아는 사람이 쿼리 빌더로 전향하는 이유도 성능이나 안전성이 아니라 이 어휘화다.

`querystring` 태그가 더 선명한 사례다.
현재 쿼리 스트링에서 한 항목만 바꾼 링크를 만드는 일은 직접 짜면 열 줄쯤 되는데, 그보다 중요한 것은 그 작업에 이름이 있다는 것이다.
이름이 없으면 매번 새로 발명하고, 발명할 때마다 인코딩이나 빈 값 처리에서 조금씩 다르게 틀린다.

이 관점이 프레임워크 선택 기준을 바꾼다.
비교해야 할 것은 기능 목록의 길이가 아니라, 그 프레임워크가 내 문제 영역의 개념들에 이름을 붙여 주는가다.
Django가 CRUD 웹앱에서 강한 것도 그 영역의 개념 대부분에 이름이 이미 붙어 있기 때문이고, 그 영역을 벗어나면 같은 강점이 사라진다.

그리고 어휘가 많다는 것은 배울 것이 많다는 뜻이기도 하다.
melodyogonna가 3,000쪽 문서를 이유로 떠난 것과, 저자가 같은 프레임워크 덕분에 해낼 만해졌다고 느끼는 것이 모순이 아닌 이유가 여기 있다.
어휘는 배우기 전까지는 장벽이고 배운 뒤에는 지렛대이며, 그 전환점이 어디인지는 프로젝트의 수명과 개인의 체류 기간이 정한다.

### 동기적 프레임워크의 부활은 비동기의 복잡도가 드러난 결과다

이 글은 언급하지 않지만, 2010년식으로 돌아간다는 이 실험이 개인적 취향에 그치지 않는 흐름 위에 있다.

CraigJPerry가 그 배경을 정리했다.
비동기 파이썬에 함정이 아주 많은데도 현대 파이썬 웹의 시대정신을 가져갔으며, 동기적 Django에는 칭찬할 점이 많다는 것이다.[^CraigJPerry]
워커와 캐싱 리버스 프록시 뒤에 합리적으로 배포하면 부하 상황에서도 운영하기 쉽고, 오래 유지되는 웹소켓 연결에는 맞지 않지만 CRUD성 애플리케이션이나 기업용 앱에는 대개 매우 생산적이라는 평이다.
함정의 예로 든 것이 구체적이다. 무제한 큐로 인한 버퍼 블로트, `asyncio.gather`로 인한 무제한 동시성, `requests.get`을 그냥 불러서 이벤트 루프를 막는 것이다.
이벤트 루프 지연을 재는 별도 태스크를 두고 알림을 걸 수는 있지만, 이런 것은 튜토리얼에 절대 나오지 않고 직접 겪어 봐야 알게 된다는 말이 핵심이다.

이 목록이 말해 주는 것은 비동기의 비용이 코드가 아니라 운영 지식에 있다는 점이다.
동기 코드에서 요청 하나가 느려지면 그 요청만 느리다. 비동기에서 이벤트 루프를 막으면 전부 느려지고, 그 인과를 추적하려면 새로운 도구와 새로운 직관이 필요하다.

그래서 저자가 “Go 백엔드는 성능 상황이 꽤 단순하다”고 한 말의 의미도 다시 읽힌다.
Go가 빠르기 때문만이 아니라 고루틴 모델이 동기적 코드를 쓰면서 동시성을 얻게 해 주기 때문이며, 파이썬에서 그 조합을 얻는 방법이 async가 아니라 프로세스 기반 워커, 즉 gunicorn 배치인 것이다.
댓글들이 한목소리로 WSGI 서버 얘기를 한 것이 단지 설정 실수 지적이 아니라 이 구조적 사실을 가리킨다.
