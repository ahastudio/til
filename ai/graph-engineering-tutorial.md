# 그래프 엔지니어링 따라하기: LangGraph로 AI 작업 경로를 코드로 통제하는 교재

<https://wikidocs.net/book/20829>

이창근이 위키독스에 쓴 LangGraph 실습 교재를 정리한 노트다.
부제는 “AI 협업 조직도를 설계하고 에이전트 경로를 제어하는 실무 가이드”이고, 1~8장과 부록은
온라인에 무료로 공개돼 있으며 9장(배포·서비스화)과 10장(서브그래프·슈퍼바이저)은 전자책
특별판(7,000원)에 수록돼 있다.
Claude Code를 활용해 집필했다고 밝히며, 각 페이지 상단에 검증 상태를 표시한다 — `[검증]`은 해당
버전에서 직접 실행해 확인한 내용, `[참고]`는 공식 문서 대조만 한 내용이다.
기준 버전은 Python 3.12, LangGraph 1.2.10, LangChain 1.3.14, Langfuse 4.14.3이며 실습 코드는
`graph-engineering-tutorial` 저장소(MIT)로 공개돼 있다.

## 이 정리의 범위

원문 사이트가 봇 차단 뒤에 있어 Playwright로 브라우저를 띄워 읽었다.
개념·설계·운영·적용에 해당하는 19개 절(01-1~01-4, 03-1, 04-1, 04-3, 05-1, 05-3~05-7, 06-1,
06-3, 07-3, 08-1, 부록B, 부록C)의 본문을 확보해 그 근거로 정리했다.
설치 절차(2장), 실습 절(각 장의 마지막 절), 08-2~08-7의 단계별 상세, 부록A·D·E는 확보하지
않았으므로 아래에서 다루지 않는다.
9·10장은 유료 구간이라 미리보기 제목 외에는 확인할 수 없다.

## 다섯 계층: 프롬프트에서 그래프까지

책의 출발점은 AI를 통제해 온 방식을 다섯 계층으로 세운 지도다.
계층마다 개발자가 통제하는 대상이 다르고, 통제에 실패했을 때 나타나는 증상도 다르다.

| 계층       | 통제 단위          | 핵심 질문              | 대표 실패 증상                        |
| ---------- | ------------------ | ---------------------- | ------------------------------------- |
| 프롬프트   | 모델 호출 한 번    | 무엇을 말할 것인가     | 모호한 지시로 인한 환각, 들쭉날쭉한 출력 |
| 컨텍스트   | 컨텍스트 윈도우    | 무엇을 알게 할 것인가  | 정보 과부하로 중요한 조건을 놓침      |
| 하네스     | 에이전트 실행 환경 | 무엇을 쓰게 할 것인가  | 작업 이탈을 감지 못함, 허용 밖 행동   |
| 루프       | 행동 반복 주기     | 어떻게 반복할 것인가   | 멈추지 못하는 반복, 컨텍스트 오염     |
| 그래프     | 다중 작업 워크플로우 | 어떻게 경로를 분배할 것인가 | 상태 전파 오류, 과도한 분기 설계  |

책이 강조하는 것은 이 계층이 교체되는 것이 아니라 포개진다는 점이다.
그래프를 도입해도 프롬프트가 사라지지 않고, 그래프의 노드 하나하나 안에
프롬프트·컨텍스트·하네스·루프가 부품으로 들어가며 노드 하나가 그 자체로 작은 루프를 돌리는
에이전트일 수도 있다.
하위 계층이 부실하면 정교한 그래프도 부실한 부품으로 지은 건물이 된다.
컨텍스트 계층에 대한 경고가 특히 명확하다 — “많이 넣을수록 좋다”는 오해이며 컨텍스트는 채우는
기술이 아니라 골라내는 기술이라는 것이다.

고객 문의 자동 응답 시스템 하나에 다섯 계층이 전부 들어간다는 예시가 이 지도를 꿴다.
프롬프트 계층에서 “정중하게, 세 문단 이내로, 환불 규정을 인용해”를 다듬고, 컨텍스트 계층에서
사내 문서 수백 건 중 관련 FAQ 두 개와 주문 내역만 고르고, 하네스 계층에서 주문 조회 도구를
읽기 권한만으로 연결하고 호출을 기록하고, 루프 계층에서 초안을 만들고 규정 위반을 자체 점검해
고치는 주기를 만들고, 그래프 계층에서 “분류 → 조회 → 작성 → 검증 → (금액이 크면) 사람 승인”이라는
경로 전체를 설계한다.

## 루프 엔지니어링의 세 한계

그래프가 등장한 배경으로 책은 단일 루프의 한계 세 가지를 든다.
그리고 뒤에서 배울 그래프의 장치가 전부 이 세 문제에 대한 대답이라고 예고한다.

첫째는 컨텍스트 오염이다.
루프가 수십 바퀴 돌면 이전 시도의 실패 로그와 도구 호출 결과와 중복된 대화가 하나의 컨텍스트
윈도우에 누적되는데, 문제는 이 기록이 자리만 차지하는 것이 아니라 판단을 적극적으로 방해한다는
점이다.
쌓인 노이즈가 주의를 분산시켜 처음 합의한 제약을 잊게 만들거나 앞서 실패한 접근을 다시 꺼내
들게 만든다.
책의 비유가 정확하다 — 40번째 반복쯤 된 코딩 에이전트가 초반에 정한 아키텍처 규칙을 어기기
시작하는 것은 모델이 멍청해서가 아니라 책상 위에 실패한 서류가 너무 많이 쌓였기 때문이다.

둘째는 정지 조건이다.
루프는 “다 됐는지”를 스스로 판단해야 멈출 수 있는데 그 판단을 하는 것이 결과물을 만든 바로 그
모델이므로, 자기가 쓴 코드를 자기가 채점하면 후한 점수가 나온다.
반대 방향의 실패도 있다 — “성능을 개선하라”처럼 끝이 열린 작업은 어디까지가 끝인지 증명할 방법이
루프 안에 없어 멈추지 못하고 토큰만 소진한다.
관대해서 일찍 멈추거나 기준이 없어서 못 멈추거나, 단일 루프의 정지 조건은 양쪽 모두에서 취약하다.

셋째는 병렬화와 전문화의 어려움이다.
루프는 요구사항 분석부터 보안 검수까지 성격이 다른 영역을 에이전트 한 명이 순서대로 처리하게
만들므로 서로 의존하지 않는 작업조차 한 줄로 세운다.
더 심각한 것은 권한이다 — 한 에이전트가 전부 하려면 모든 권한을 줘야 하므로 조사만 하면 되는
단계에서도 배포 권한을 쥐고 있게 된다.
책은 이것을 “직원이 한 명뿐이라 그 사람에게 금고 열쇠까지 다 맡긴 상황”이라고 부른다.

세 한계를 관통하는 공통점이 블랙박스라는 진단이다.
별도의 관측 장치 없이 만든 루프는 40바퀴를 돌았어도 밖에서 보이는 것이 최초 입력과 최종
출력뿐이며, 그래프는 단계가 1급 요소로 드러나 있어 이 상자를 유리로 바꾸기 쉬운 구조를 준다.

| 관점       | 단순 단일 루프 구현        | 그래프 구조                        |
| ---------- | -------------------------- | ---------------------------------- |
| 투명성     | 어디서 왜 틀렸는지 모른다  | 노드 단위로 입력·출력·경로가 남는다 |
| 오류 수정  | 대개 처음부터 전체 재실행  | 실패한 노드만 고쳐서 재시도        |
| 전문성     | 만능 에이전트 한 명        | 역할별로 지침·모델·도구를 특화     |
| 거버넌스   | 전부 아니면 전무의 권한    | 노드마다 필요한 권한만 부여        |

그리고 세 한계가 각각 그래프의 장치 하나와 짝을 이룬다 — 컨텍스트 오염은 노드별 격리로, 정지
조건은 스테이트 기반 종료로, 병렬·전문화 불가는 팬아웃과 권한 분리로 풀린다.
다만 노드별 격리에 붙은 단서가 중요하다 — 나누는 것만으로 저절로 격리되지 않고 노드에 무엇을
넘길지(스테이트와 프롬프트)를 설계해야 실제 격리가 된다.
루프가 사라지는 것도 아니다 — 잘 만든 루프는 그래프의 노드 안으로 들어가 통제된 범위에서 계속
일한다.

## 정의와 조직도 비유

책의 한 문장 정의는 이렇다 — 그래프 엔지니어링이란 AI 작업 흐름을 노드·엣지·스테이트·컨디션의
명시적인 그래프로 설계하고, 에이전트가 어느 경로로 일할지를 코드로 통제하는 방법이다.

이 정의가 결합하는 두 세계가 명확하다.
언어 모델은 같은 질문에도 매번 조금씩 다르게 답하는 비결정론적 존재이고 업무 프로세스는 정해진
절차를 정확히 밟아야 하는 결정론적 세계인데, 그래프 엔지니어링은 개별 노드 안에서는 모델의
유연함을 활용하되 노드 사이의 이동은 개발자가 코드로 정한 경로만 허용한다.
책의 표현으로는 “모델의 창의성은 방 안에서만 발휘되고, 방과 방 사이의 복도는 설계도를 따른다”다.

책 전체를 이끄는 비유는 조직도다.
루프 엔지니어링이 유능한 직원 한 명에게 모든 업무를 욱여넣는 방식이라면 그래프 엔지니어링은
회사의 조직도 자체를 설계하는 일이며, 견적 업무를 예로 들면 접수 담당자가 빠진 항목을 확인하고,
분류 담당자가 종류를 판단해 부서로 넘기고, 계산 담당자가 단가표대로 금액을 내고, 작성 담당자가
견적서를 쓰고, 검토자가 규정 위반을 확인한 뒤 대표가 승인하면 발송된다.
담당자가 노드, 서류가 넘어가는 순서가 엣지, 서류철이 스테이트, “금액이 기준 이상이면 대표
승인으로”가 컨디션이다.

구성원이 전부 AI일 필요가 없다는 점을 책은 반복해서 강조한다.
코드는 명확한 규칙과 계산을, AI는 정답이 없는 판단과 생성을, 사람은 전략적 결정과 최종 승인을
맡는다.

여기서 한 겹 더 들어간 구분이 실무에서 유용하다 — 수명이 다른 두 개의 구조가 공존한다는 것이다.

| 구분        | 조직 그래프 (Who)                    | 작업 그래프 (What)                  |
| ----------- | ------------------------------------ | ----------------------------------- |
| 정하는 것   | 누가 있고, 무슨 도구와 권한을 갖는가 | 이번 일이 어떤 순서와 분기로 흐르는가 |
| 수명        | 배포 시 확정되어 오래 유지           | 요청마다 만들어지고 끝나면 소멸     |
| 바뀌는 시점 | 코드 수정·권한 정책 변경 때          | 실행 중 컨디션이 평가될 때          |

조직 그래프는 조직도와 직무 권한 규정이고 작업 그래프는 오늘 들어온 안건 하나가 실제로 밟아 가는
결재 경로다.
8장에서 “먼저 조직을 고정하고, 경로는 입력에 따라 달라지게” 하는 설계 원칙으로 다시 등장한다.

## 그래프로 만들지 말아야 할 때

책이 1장에서 가장 실용적일 수 있다고 스스로 지목한 절이다.
“망치를 들면 모든 것이 못으로 보인다”로 시작하며, 그래프는 공짜가 아니라 노드가 늘 때마다 호출
비용과 관리할 코드와 디버깅 표면적이 늘어난다고 못을 지른다.

판정은 두 질문이면 끝난다.

```text
질문 1. 한 번의 호출로 끝나는 단발성 작업인가?
        예 → 프롬프트(+컨텍스트)로 충분. 그래프 불필요.
        아니오 ↓
질문 2. 다음 중 둘 이상이 필요한가?
        조건 분기 / 병렬 처리 / 중간 검증과 재작업 / 사람 승인
        예 → 그래프 후보.
        아니오 → 순차 함수 호출이나 단일 루프로 충분.
```

질문 2의 네 항목이 곧 5장의 다섯 설계 패턴이며, 그래프가 아니면 구현하기 고통스러운 것들이다.
거꾸로 이것들이 필요 없는 작업에 그래프를 쓰면 고통만 남는다.
판정이 틀릴까 걱정할 필요는 없다는 조언이 붙는다 — 프롬프트로 시작했다가 그래프로 옮기는 비용은
크지 않지만 잘못 그린 그래프를 걷어내는 일은 훨씬 번거롭기 때문이다.

그래프가 과한 경우로 네 가지를 든다.
한 번 호출로 끝나는 작업(노드 하나짜리 그래프는 포장만 늘린 프롬프트), 분기도 재시도도 없이 항상
같은 순서로 흐르는 두세 단계, 단계 구분 자체가 흔들리는 프로토타입 단계, 그리고 유지보수할 사람이
없는 경우다.
마지막 항목의 이유가 서늘하다 — 그래프는 만드는 것보다 고치며 운영하는 기간이 길어서, 분기 조건과
스테이트 스키마를 이해하고 손볼 사람이 없으면 잘 만든 그래프도 몇 달 뒤에는 아무도 못 건드리는
블랙박스가 된다.

반대로 값어치를 하는 신호는 다섯이다.
중간 결과를 검증하고 기준 미달이면 재작업시켜야 할 때, 입력에 따라 처리 경로가 갈라질 때, 서로
독립인 작업이 여러 개일 때, 사람의 승인이 중간에 필요할 때, 그리고 실패 시 어디서부터 다시 할지가
중요할 때다.
마지막 항목의 근거가 구체적이다 — 30분짜리 파이프라인이 마지막 단계에서 실패했을 때 처음부터
다시 돌리는 것과 실패한 노드만 다시 돌리는 것의 차이는 비용 그 자체다.

책이 반대편 주장까지 소개하는 것도 눈에 띈다.
모델 성능이 좋아질수록 잘 쓴 단일 프롬프트와 좋은 모델의 조합이 어설프게 쪼갠 그래프보다 낫다는
견해가 있고, 단순하고 절차가 뻔한 작업에서는 단계를 잘게 나누는 것이 나누는 과정에서 맥락을
조각내 품질을 떨어뜨리기도 한다는 것이다.
책의 입장은 “그래프는 규모와 신뢰성의 문제를 푸는 도구이지 품질을 자동으로 올려 주는 마법이
아니다”이며, 다섯 계층의 아래쪽을 먼저 다진 뒤 검증·분기·병렬·승인이 필요한 핵심 업무부터 올리라고
권한다.

## 네 요소와 코드 대응

정의에 등장한 네 요소는 은유가 아니라 LangGraph API 이름 그대로다.
노드는 고유한 책임 하나를 맡은 작업 단위이고, 엣지는 다음 노드로 가는 연결선이며, 스테이트는 노드
사이를 오가며 결과가 쌓이는 데이터 구조이고, 컨디션은 갈림길의 판단 규칙이다.
노드의 “속”이 순수 파이썬 함수든 LLM 호출이든 사람 입력을 기다리는 정지점이든 겉에서 보면 모두
같은 노드이며, 그래프는 속을 가리지 않고 연결한다 — 이 성질이 코드·AI·사람 노드의 역할 분담을
가능하게 한다.

스테이트에는 두 규칙이 있다.
어떤 항목이 들어갈지 미리 스키마로 선언하는 것(서류철의 칸막이를 먼저 정하는 것), 그리고 각
노드가 서류철 전체를 새로 쓰지 않고 자기가 채울 칸만 갱신하는 것이다.

| 개념           | LangGraph 코드                          |
| -------------- | --------------------------------------- |
| 스테이트 스키마 | `class State(TypedDict)`                |
| 노드           | 함수 정의 + `add_node("이름", 함수)`    |
| 엣지           | `add_edge("research", "summarize")`     |
| 입구·출구      | `add_edge(START, ...)` / `add_edge(..., END)` |
| 컨디션         | `add_conditional_edges(...)`            |

개념과 코드가 일대일이라는 것이 저자가 LangGraph를 교재의 도구로 고른 이유 중 하나다.

## 노드 설계: 계약과 쪼개기

노드 크기를 재는 가장 빠른 방법은 이름을 지어 보는 것이다.
“자료 수집”, “형식 검증”, “보고서 작성”처럼 두세 단어로 떨어지면 적정 크기이고, “자료를 수집하고
검증해서 요약하는 노드”처럼 이름에 ‘하고’가 들어가면 일이 많은 것이다 — 경험칙으로 이름에 동사가
두 개면 나눌지 먼저 검토한다.
이름은 장식이 아니다 — 노드 이름이 실행 로그와 Langfuse 추적 화면에 그대로 나타나므로 이름이 하는
일을 정확히 말해야 실패한 스팬을 봤을 때 어디를 고칠지 바로 안다.

노드를 만들기 전에 세 줄짜리 계약을 쓴다 — 입력(스테이트의 어떤 필드를 읽는가), 수행 작업(서너
문장 이내), 출력(스테이트의 어떤 필드를 채우는가)이다.
계약이 문서로 남으면 구현을 다른 사람이나 AI에게 맡길 수 있고, 구현을 통째로 갈아 끼워도 계약만
대조하면 그래프가 깨지는지 알 수 있다.
계약이 확정되면 노드 세 개를 세 사람이 동시에 구현해도 서로를 기다릴 필요가 없으며, AI 코딩 도구에
맡길 때도 계약 세 줄이 그대로 작업 지시서가 된다 — 조직도 비유로는 직무 기술서다.

수행 작업의 분량이 곧 진단이다.
서너 문장으로 정리되지 않는 노드는 일이 많은 노드이며, 지침 수십 개를 든 만능 에이전트가 그중
몇 개를 반드시 흘리는 것과 같은 이유로 노드 하나가 감당할 지시가 서너 문장을 넘으면 모델이 흘리는
지시가 생긴다.

쪼개기를 검토할 신호는 다섯이다 — 이름에 ‘하고’·‘그리고’가 들어간다, 수행 지침이 다섯 문장을
넘는다, 프롬프트에 서로 다른 종류의 요구(수집 + 검증 + 형식)가 섞여 있다, 실패했을 때 어느 부분이
실패했는지 말할 수 없다, 출력 필드가 서너 개를 넘는다.
반대 방향의 경고도 붙는다 — “문장 끝에 마침표 붙이기”처럼 코드 한 줄이면 되는 일을 노드로 만들면
관리 비용만 늘어난다.
쪼개는 이유는 잘게 만들기 위해서가 아니라 실패 지점을 분리하고 책임을 명확히 하기 위해서다.

계약 템플릿에서 가장 중요한 줄은 마지막이다.

```text
노드 이름: collect (자료 수집)
입력:     topic
수행 작업: 주제에 대한 핵심 사실 7개를 수집한다.
          각 사실은 40자 이내 한 문장으로 쓴다.
          근거 유형(연구/사례/통계)을 함께 표시한다.
출력:     facts
실패 정의: JSON 파싱 불가, 또는 사실 7개 미만
```

무엇이 실패인지 미리 적어 두면 그것이 곧 검증 규칙이 되고 조건 분기의 판정 기준이 된다 — 계약
한 장이 설계 문서이자 테스트 명세가 되는 셈이다.

## 코드·AI·사람 노드의 역할 배분

이 절이 교재에서 실측으로 가장 인상적인 부분이다.
“수집된 항목이 10개 이상인가?”라는 판정을 코드와 AI로 각각 구현해 돌린 결과다(항목 8건, 정답은
미달).

```text
[코드 판정]  결과: 미달
             소요: 0.0006ms / 비용: $0 / 같은 입력엔 항상 같은 답

[AI 판정]    결과: 미달
             소요: 1.05초 / 토큰: 입력 153 출력 6 / 실행마다 흔들릴 수 있음
```

둘 다 정답을 냈지만 실행 시간 차이는 밀리초의 천분의 일 대 1초였고 AI 쪽은 토큰 159개의 비용이
들었다.
그리고 결정적으로 코드는 규칙이 제대로 구현돼 있다면 같은 입력에 항상 같은 답을 내지만 AI의 정답은
확률이며, 목록이 수백 개로 늘거나 표현이 애매해지면 AI의 개수 세기는 틀리기 시작한다.

저자가 이 수치에 규모를 곱해 본 대목이 이 절의 핵심이다.
판정 1회에 약 1초와 토큰 159개가 들었으니 하루 1만 건을 처리하는 그래프라면 이 판정 하나가 매일
약 2.8시간의 누적 모델 호출 시간과 159만 토큰을 만든다 — 코드로 내리면 전부 사라지는 비용이다.
동시 처리를 하면 체감 경과 시간은 짧아지지만 지불하는 시간과 토큰의 총량은 그대로라는 단서까지
붙는다.

배분은 위에서부터 순서대로 묻는다.

| 질문                                      | 예라면                                    |
| ----------------------------------------- | ----------------------------------------- |
| 판정 규칙을 코드로 쓸 수 있는가?          | 코드 노드 — 빠르고 LLM 비용이 없으며 결정론적 |
| 규칙은 못 쓰지만 AI가 판단·생성할 수 있는가? | AI 노드 — 프롬프트에 규칙 명시            |
| 책임·전략이 걸려 기계에 맡길 수 없는가?   | 사람 노드 — 정지점 배치                   |

순서가 중요하다 — 코드가 가능한지 먼저 묻고 안 될 때만 AI로 내려간다.
반대로 “일단 AI로” 시작하면 그래프의 모든 노드가 느리고 비싸고 불확실해진다.
그리고 비용만의 문제가 아니다 — AI 노드는 실패 처리(재시도·타임아웃)도 함께 설계해야 하므로
유지보수 비용이 코드 노드보다 훨씬 크며, 저자의 결론은 “AI 노드 수를 줄일수록 시스템이
단단해진다”다.

## 다섯 가지 경로 제어 패턴

### 패턴 1: 라우터 — 조건 분기

고정 엣지가 “끝나면 무조건 저기로”라면 조건부 엣지는 “끝나면 상태를 보고 갈 곳을 정한다”다.
구조가 셋으로 나뉜다 — 판단하는 노드(AI), 경로를 정하는 라우팅 함수(코드), 갈래를 선언하는 매핑이다.
분류 노드가 문의 유형을 판단해 스테이트에 적으면 라우팅 함수가 그 값을 보고 다음 노드 이름을
반환하며, 라우팅 함수는 노드가 아니므로 스테이트를 갱신하지 않는다.

역할 분담이 앞 절의 원칙 그대로다 — 애매한 판단은 AI에게, “이 레이블이면 이 노드”라는 명확한 규칙은
코드에게다.
매핑을 명시하면 그래프 그림(`draw_mermaid`)에 갈래가 전부 점선으로 그려져 설계를 눈으로 검증할 수
있고, 라우팅 함수의 반환 타입(`Literal[...]`)과 매핑이 서로를 검증하는 문서가 된다.
저자가 직접 실험한 사실이 하나 붙는다 — 라우팅 함수가 매핑에 없는 값을 반환하면 그래프는 실행
시점에 `KeyError`를 내며 죽는다.

실행 결과에서 주목할 것은 마지막 건이다.
“혹시 오늘 우주 날씨는 어떤가요?”라는 문의가 세 분류 어디에도 속하지 않는데 그래프가 죽지 않고
`기타` → 사람 검토대로 안착했다 — Fallback 경로의 값이 이 한 줄에 있다.

### 패턴 2: 병렬 실행 — 팬아웃과 팬인

기준은 하나, 의존성이다.
시장·기술·규제 조사는 서로의 결과를 필요로 하지 않으므로 동시에 돌릴 수 있고, 조사 → 요약은
요약이 조사 결과를 읽어야 하므로 병렬이 불가능하다.
병렬 실행에 특별한 API는 필요 없다 — 한 지점에서 여러 노드로 엣지를 이으면 팬아웃, 여러 노드가 한
노드로 모이면 팬인이며, 팬인 노드는 자신을 향한 엣지의 출발 노드들이 전부 끝날 때까지 실행되지
않는다.

병렬에서 유일하게 조심할 것은 스테이트다.
리듀서 없이 두 노드가 같은 필드에 쓰면 실제로 이런 오류가 난다.

```text
InvalidUpdateError: At key 'items': Can receive only one value per step.
Use an Annotated key to handle multiple values.
```

한 단계에 한 필드는 한 번만 갱신될 수 있다는 원칙 때문이며, 해결책은 여러 값이 들어오면 어떻게
합칠지를 스키마에 선언하는 것 — `Annotated[list[str], operator.add]`가 리듀서다.

실측이 기대와 다르다는 점이 중요하다.

```text
순차 실행: 33.81초 / 조사 3건
병렬 실행: 19.13초 / 조사 3건
단축 배율: 1.77배
```

이론상 3배가 아니라 1.77배에 그친 이유를 저자가 밝힌다 — 팬아웃·팬인과 스케줄링 오버헤드가
더해진 값이 실제 성적이고, API 동시 호출 한도에 걸리면 갈래들이 줄을 서게 되어 이득이 더 줄어든다.
그리고 결정적 단서가 붙는다 — 병렬이 줄여 주는 것은 벽시계 시간이지 토큰이 아니다.
순차든 병렬이든 호출은 세 번이고 비용은 같으며, 오히려 갈래를 늘리기 쉬워져 “일단 열 갈래로
조사”처럼 호출 수를 늘리는 설계를 하기 쉽다.
병렬은 속도의 도구이지 절약의 도구가 아니다.

### 패턴 3: 오케스트레이터-워커 — 동적 작업 분할

설계 시점에 갈래 수를 알 수 없는 업무를 위한 패턴이다.
계획을 세우는 노드가 실행 시점에 작업 목록을 만들고 목록의 항목 수만큼 워커에게 위임하며, 동적
팬아웃의 도구가 `Send`다.

여기서 가장 중요한 한 줄은 플래너 코드의 마지막 슬라이싱이다 — 워커 수를 정하는 것은 AI지만 상한을
정하는 것은 코드이며(`[:MAX_WORKERS]`), 플래너가 폭주해 하위 주제를 서른 개 만들어도 비용이 서른
배가 되지 않도록 구조가 막는다.

실측에서 무거운 주제(사내 문서 검색 챗봇 도입)에는 워커 5명, 가벼운 주제(점심 메뉴 추천)에는 4명이
붙었고 그래프 코드는 한 글자도 바뀌지 않았다 — 조직 그래프와 작업 그래프의 구분이 실행으로 확인되는
지점이다.

| 항목        | 병렬 실행 (패턴 2)      | 오케스트레이터-워커        |
| ----------- | ----------------------- | -------------------------- |
| 갈래 수     | 설계 시점에 고정        | 실행 시점에 결정           |
| 갈래 정의   | 노드를 각각 등록        | 워커 노드 하나 + Send 목록 |
| 적합한 업무 | 관점이 정해진 정형 조사 | 입력마다 쪼개짐이 다른 업무 |
| 비용 예측   | 정확 (갈래 수 고정)     | 상한으로 통제 (MAX_WORKERS) |

고정 갈래로 충분하면 병렬 실행이 낫다 — 더 단순하고 비용도 예측 가능하다.
오케스트레이터-워커는 유연함의 대가로 비용 변동성을 안는 패턴이므로 반드시 워커 상한과 함께 쓴다.

### 패턴 4: 생성자-평가자 루프

01-2에서 진단한 “자기가 만든 것을 자기가 검사하는” 관대함의 처방이다.
작성자와 검수자를 서로 다른 노드로 두면 작성자는 검수 결과에 영향을 줄 수 없고 검수자는 자기가 쓴
글이 아니므로 관대할 이유가 없다.

평가 기준은 검증 가능한 규칙으로 서면화한다 — 예제의 검수자는 필수 단어 포함과 길이 제한을
검사하는 코드 노드이며 LLM을 쓰지 않는다.
되돌아갈 때 빈손으로 보내지 않는 것이 품질을 좌우한다 — 반려 사유(“길이 초과: 170자”)가 다음 시도의
프롬프트에 들어가므로 매 바퀴가 이전 바퀴보다 정확히 한 걸음 나아간다.
단일 루프에서는 이 피드백이 수십 바퀴의 노이즈에 섞여 흐려지지만 여기서는 스테이트의 `feedback`
필드 하나로 깨끗하게 전달된다.

평가자를 코드로 둘지 AI로 둘지는 앞의 판단표가 그대로 적용된다.
기준이 “문체가 공지문답게 정중한가”처럼 규칙으로 쓸 수 없는 것이면 평가자도 AI가 되어야 하는데,
이때는 생성자와 다른 프롬프트(가능하면 다른 관점)를 주어 자기 채점의 관대함이 되살아나지 않게 해야
한다 — 실무에서는 코드 검사를 먼저 통과시킨 뒤 AI 검사를 거치는 이중 구조도 흔하다.

실측에서는 첫 초안이 170자로 길이 기준을 넘겨 반려되고 두 번째도 근소하게 넘겨 반려된 뒤 세 번째에
148자로 통과했다 — 이 과정에 사람이 전혀 개입하지 않았고, 기준을 서면화해 둔 덕분에 반려·재작성·통과가
전부 그래프 안에서 자동으로 돌았다.

### 루프 제어: 이 교재에서 가장 값진 실측

되돌아가는 엣지를 만드는 순간 무한 루프의 가능성이 생긴다.
항상 반려하는 평가자를 두고 상한 없이 실행한 결과가 이렇다.

```text
=== 1. 재시도 상한 없음 ===
GraphRecursionError 발생: Recursion limit of 10007 reached without hitting a stop condition.
```

여기에 반드시 알아야 할 실측 사실이 붙는다 — LangGraph v1.2의 기본 재귀 한도는 10007단계다.
예전 자료에는 기본값 25로 소개돼 있는데 저자가 이 버전에서 직접 확인한 값은 10007이며, 이 차이는
심각하다.
이 실험의 노드는 LLM을 부르지 않는 코드였으니 순식간에 1만 번을 돌고 끝났지, LLM 노드였다면 오류로
죽기 전에 수천 번을 호출하며 비용을 태웠을 것이다.
재귀 한도는 최후의 안전망이지 루프 제어 수단이 아니다.

처방은 재시도 횟수를 스테이트에 기록하고 상한을 두는 것이다.

```python
def route_after_check(state: State) -> Literal["publish", "escalate", "maker"]:
    if state["approved"]:
        return "publish"
    if state["attempts"] >= MAX_ATTEMPTS:
        return "escalate"  # 상한 도달 — 무한 루프 대신 사람에게
    return "maker"         # 반려 사유를 들고 생성자로 되돌아간다
```

같은 무한 반려 상황을 상한 3회로 다시 돌리면 오류가 아니라 설계된 경로로 조용히 빠져나온다 —
“에이전트의 자율 판단이 아니라 구조가 종료를 강제한다”의 실체가 이 라우팅 함수 다섯 줄이다.

상한 초과의 목적지는 업무 성격에 따라 셋 중 하나다 — 사람에게 에스컬레이션(기본값, 반려 사유와
마지막 초안을 함께 넘겨야 이어받을 수 있다), 미달인 채로 표시하고 진행(품질보다 처리량이 중요한
업무, 반드시 “검증 미통과” 표식을 남긴다), 작업 폐기와 기록(스팸 처리처럼 버려도 되는 업무)이다.
공통 원칙은 조용히 사라지지 않게 하는 것이다.

종료 조건 설계 체크리스트는 되돌아가는 엣지를 그릴 때마다 확인한다 — 루프 횟수가 스테이트에
기록되는가, 상한과 상한 도달 시의 목적지가 명시적 노드로 존재하는가, 반려 사유가 다음 시도에
전달되는가(사유 없는 재시도는 같은 실패의 반복이다), 성공 조건이 코드로 판정 가능한가(“충분히
좋아지면”은 종료 조건이 아니다), 상한이 재귀 한도보다 훨씬 작은가.

### 패턴 5: 사람 승인 (Human-in-the-loop)

모든 단계에 승인을 두면 자동화의 의미가 없고 하나도 없으면 사고가 났을 때 책임질 수 없다.
기준은 되돌리기 어려움과 책임이다 — 고객에게 발송되는 것, 돈이 나가는 것, 외부에 공개되는 것처럼
되돌릴 수 없는 행동의 직전이 사람의 자리이며, 내부 초안 생성이나 중간 검증에는 승인을 두지 않는다.

구현은 노드 안에서 `interrupt`를 호출해 그래프를 그 자리에서 멈추는 것이다.

```python
result = graph.invoke({"item": "사내 문서 검색 챗봇"}, config)   # 멈춤
pending = result["__interrupt__"][0].value                      # 사람에게 보여줄 내용
result = graph.invoke(Command(resume="승인"), config)            # 멈춘 곳부터 재개
```

`resume`에 넣은 값이 `interrupt` 호출의 반환값이 되어 노드가 이어서 실행되고, 그 뒤는 평범한 조건부
엣지다 — 승인이면 발송 노드로, 반려면 재작성 대기로.
정지 상태를 유지하려면 체크포인터가 필요하다.

실무적으로 중요한 것은 정지와 재개가 분리되어 있다는 점이다.
멈춘 그래프는 몇 초 뒤에 재개될 수도, 결재권자가 휴가에서 돌아온 사흘 뒤에 재개될 수도 있으며 그
사이 상태는 체크포인터에 안전하게 잠들어 있다.

## 스테이트와 체크포인트

스테이트를 보는 관점은 컨베이어 벨트다.
그래프 없이 LLM을 여러 번 호출하면 결과물이 지역 변수와 f-문자열 사이를 떠돌아다니고, 어느 시점에
무엇이 있었는지는 코드를 추적해야만 알 수 있으며 중간에 프로세스가 죽으면 전부 사라진다.
스테이트는 이 떠돌이 데이터를 하나의 벨트에 올려 어느 시점에 무엇이 실려 있는지를 항상 명확하게
만든다.

벨트 관점이 주는 실용적 이득은 프롬프트의 다이어트다.
그래프에서는 노드가 스테이트에서 필요한 필드만 꺼내 쓰므로 요약 노드는 조사 결과만 받으면 되고
원래 요청문이나 중간 로그까지 받을 필요가 없다.
저자가 남긴 감각이 이것이다 — 벨트에 올린 것은 언젠가 누군가의 토큰 비용이 된다.

담을 것과 담지 않을 것의 기준이 분명하다.
담는 것은 두 개 이상의 노드가 주고받는 작업 데이터, 경로 결정에 쓰이는 값(`passed`, `category`,
`attempts`), 실패 시 이어받기에 필요한 최소 맥락(반려 사유)이다.
담지 않는 것은 한 노드 안에서만 쓰는 중간 계산값(함수의 지역 변수로), 다시 만들 수 있는 파생
데이터(필요한 노드가 그때 계산), 그리고 원문 전체가 필요 없는 대용량 데이터(파일이나 DB에 두고
스테이트에는 경로·ID만)다.
세 번째가 실무에서 가장 중요하다 — 100페이지 계약서를 검토하는 그래프라면 스테이트에는 파일 경로와
검토 대상 조항 목록을 싣고 각 노드가 필요한 부분만 읽어 온다.
“벨트에는 상자를 올리는 게 아니라 상자의 위치표를 올린다.”

스테이트가 비대해질 때 셋이 함께 나빠진다 — 토큰 비용(비대한 필드가 프롬프트에 들어가는 순간 매
호출이 비싸진다), 추적 난도(어떤 노드가 어떤 필드에 의존하는지 흐려져 필드 하나를 고치면 어디가
깨질지 모른다), 저장 비용(체크포인터가 노드마다 스냅샷을 저장하므로 스테이트 크기가 곧 저장소 증가
속도다).
잘 설계된 스테이트의 모습은 “모든 필드에 올리는 노드와 내리는 노드가 있고 아무도 안 쓰는 필드가
없는” 상태다.

체크포인터는 노드가 하나 끝날 때마다 스테이트 스냅샷을 기록하는 장치다 — 벨트를 매 공정마다 사진
찍어 앨범에 꽂아 두는 것이며, 이 앨범이 정지와 재개, 실행 경로의 사후 추적, 되감아 다시 실행을
가능하게 한다.
로컬에서 가장 간단한 선택은 SQLite 파일이고, 바뀌는 것은 `compile`의 인자 하나뿐이다.

```python
conn = sqlite3.connect("checkpoints.sqlite", check_same_thread=False)
graph = builder.compile(checkpointer=SqliteSaver(conn))
```

노드 코드도 엣지도 그대로이며, 이 저장소를 PostgreSQL로 바꾸는 것도 같은 방식이다 — 체크포인터
교체가 그래프 코드에 영향을 주지 않는다는 것이 이 설계의 장점이다.
실행 건은 `thread_id`로 구분하고, 같은 `thread_id`로 다시 호출하면 이어서 실행되고 새 값을 쓰면 새
건이 시작된다 — 실무에서는 견적 건번호나 티켓 ID처럼 업무의 자연스러운 단위를 쓴다.

`get_state_history`로 매 단계의 스냅샷을 되짚을 수 있다.

```text
== 실행 이력 (최신 → 과거) ==
step 3: 다음 실행 노드 = ('끝',) / 채워진 필드 = ['topic', 'collected', 'checked', 'summary']
step 2: 다음 실행 노드 = ('summarize',) / 채워진 필드 = ['topic', 'collected', 'checked']
step 1: 다음 실행 노드 = ('verify',) / 채워진 필드 = ['topic', 'collected']
step 0: 다음 실행 노드 = ('collect',) / 채워진 필드 = ['topic']
step -1: 다음 실행 노드 = ('__start__',) / 채워진 필드 = []
```

## 노드마다 다른 모델 쓰기

그래프의 숨은 장점은 노드가 곧 모델 선택의 단위라는 것이다.
단일 에이전트는 “제일 어려운 작업”에 맞춰 비싼 모델 하나를 골라야 하고 그 모델이 쉬운 작업까지
처리하며 비용을 태우지만, 그래프에서는 노드마다 LLM 인스턴스를 따로 만들면 그만이다.

고객 문의를 분류하고 답변을 작성하는 2노드 파이프라인을 두 구성으로 돌린 실측에서, 분류 노드의
모델만 상위 티어에서 최소 티어로 바꿨을 때 비용은 약 10분의 1, 지연은 절반이 됐고 분류 결과는
동일했다.
“버그신고/기능요청/결제문의 중 하나 고르기”에는 최소 모델의 능력으로 충분하기 때문이며, 반면
고객에게 나가는 답변 작성은 문장 품질이 곧 서비스 품질이므로 상위 모델을 유지했다.

배분 사다리가 앞의 판단표에 한 칸 늘어난다 — 코드로 판정 가능한가를 먼저 묻고, AI가 필요하면
그다음 “선택지 고르기인가 품질이 가치인 생성인가”를 물어 티어를 정한다.
저자가 던지라고 권하는 질문이 날카롭다 — “이 노드의 프롬프트가 사실상 `if`문 아닌가?”
의외로 많은 분류·판정 노드가 키워드 매칭이나 정규식으로 내려간다.

중복 호출을 줄이는 것도 비용 설계의 절반이다.
체크포인트가 이미 절반을 해결한다 — 실패 시 전체 재실행 대신 실패 지점부터 재개하면 성공한 노드의
호출이 반복되지 않는다.
나머지 절반은 설계다 — 재사용되는 데이터는 스테이트에 실어 뒤 노드들이 다시 조사하지 않게 하고,
자주 반복되는 동일 질문이 있으면 노드 캐시(`add_node`의 `cache_policy`)를 검토한다.

## 기업 업무 적용: 1단계 적합성 판정

프로젝트의 성패는 첫 대상 업무를 무엇으로 고르느냐에서 절반이 결정된다.
이상적인 첫 대상은 네 가지를 갖춘 업무다 — 반복적이다(월 몇 건 이상 꾸준히 발생해야 투자가
회수된다), 절차가 어느 정도 명문화되어 있다(담당자마다 처리 방식이 완전히 다르면 노드로 나누기 전에
절차 정리부터 필요하다), 실패해도 치명적이지 않다(첫 프로젝트는 반드시 시행착오를 겪는다), 결과를
측정할 수 있다.

후보가 여러 개라면 우선순위는 “발생 빈도 × 담당자의 고통 × 실패 시 위험의 역수”로 매긴다.
그리고 후보 선정 단계부터 담당자를 참여시키라는 조언이 붙는다 — 그래프는 담당자를 대체하는 것이
아니라 반복 노동을 덜어내는 것이고 숨은 규칙의 원천도 결국 담당자이며, 담당자가 반기지 않는 자동화
프로젝트는 시범 운영 단계에서 조용히 좌초된다.

적합성 판정 질문지는 다섯이다 — 한 번의 호출로 끝나는가(예라면 종료), 조건 분기·병렬·중간 검증·사람
승인 중 둘 이상이 필요한가(핵심 관문), 입력과 출력이 명확히 정의되는가, 판단에 필요한
데이터(단가표·규정·이력)에 시스템이 접근할 수 있는가, 규칙을 답해 줄 담당자가 있는가.
저자는 4번에서 자주 걸린다고 적는다 — 단가표가 담당자 개인의 엑셀에만 있다면 그래프 이전에 데이터
정리가 선행 과제다.

그래프를 만들기 전에 현재 방식의 성적표를 남기라는 것이 이 절의 실무적 핵심이다.
건당 처리 시간, 월 건수, 오류·반려율, 담당자 투입 시간을 재 두지 않으면 시범 운영에서 “좋아진 것
같다”는 인상 외에 보고할 것이 없고, 기준선이 있으면 “건당 40분 → 8분, 반려율 15% → 4%” 같은 문장이
나와 확대 승인의 근거가 된다.

탈락도 결과다 — 단발성 작업이면 프롬프트로 충분하고, 절차가 명문화되지 않았다면 절차 정리 후 재판정
대상이며, 업무 전체는 부적합해도 일부 구간은 적합할 수 있으므로 “전부 아니면 전무”로 판정하지 말고
구간 단위로 다시 본다.

## 도입 전 체크리스트

부록B가 본문에 흩어진 점검표를 모아 둔 것이고, 그중 실제로 옮겨 쓸 만한 세 묶음이다.

적합성 판정은 여덟 항목이다 — 한 번의 호출로 끝나는가, 분기·병렬·검증·승인 중 둘 이상이 필요한가,
업무가 반복적이고 절차가 명문화되어 있고 실패가 치명적이지 않은가, 입력과 출력이 명확한가, 필요한
데이터에 시스템이 접근할 수 있는가, 규칙을 답해 줄 담당자가 참여하는가, 기준선을 측정해 두었는가,
유지보수할 사람이 팀에 있는가.

노드 분해 검토는 여덟 항목이다 — 모든 노드 이름이 두세 단어이고 ‘하고’가 없는가, 수행 지침이 서너
문장 이내인가, AI 노드마다 “코드로는 정말 안 되는가”를 물었는가, AI 노드의 모델 티어를 정했는가,
각 노드의 출력을 읽는 노드가 존재하는가, 스테이트 필드마다 채우는 노드가 하나로 특정되는가, 여러
노드가 쓰는 필드는 리듀서 여부를 결정했는가, 두 개 이상의 노드가 주고받는 데이터만 스테이트에
담았는가.

경로 설계 점검은 아홉 항목이다 — 노드마다 “끝나면 언제 어디로”가 문장으로 적혀 있는가, 라우팅
함수의 모든 반환값이 매핑에 선언되어 있는가(빠지면 실행 중 `KeyError`), “어디에도 해당 없음”의
Fallback 경로가 존재하고 사유가 스테이트에 실리는가, 되돌아가는 엣지마다 재시도 횟수가 기록되고
상한이 있는가, 상한 도달 시의 목적지가 명시적 노드로 존재하는가, 반려 사유가 다음 시도에
전달되는가, 병렬 구간의 스테이트 충돌을 확인했는가, 고립 노드·막다른 노드가 없는가, 그래프
그림이 설계 의도와 일치하는가.

노드 계약 템플릿은 노드 하나마다 한 장씩 쓴다.

```text
노드 이름:  (두세 단어)
종류:      코드 / AI(모델명) / 사람
입력:      (읽는 스테이트 필드)
수행 작업:  (서너 문장 이내)
규칙:      (검증 가능한 형태로 — "정확히 N개", "OO 포함")
출력:      (채우는 스테이트 필드)
실패 정의:  (무엇이 실패인가 — 검증 코드와 재시도 판정의 기준)
```

## 용어 혼동: 세 갈래의 “그래프”

부록C가 이 교재에서 가장 실용적인 부록이다.
저자가 실측한 사실 하나가 그 필요를 증명한다 — 기준 모델에게 “그래프 엔지니어링을 설명하라”고
물으면 이 책의 의미가 아니라 그래프 데이터베이스 쪽 의미로 답하며, 두 번 물어도 같은 방향이었다.
용어가 아직 젊어서 모델의 지식 속에서도 데이터 진영의 용법이 우세한 것이다.

| 비교 항목   | 그래프 엔지니어링         | 그래프 데이터베이스    | Graph RAG            |
| ----------- | ------------------------- | ---------------------- | -------------------- |
| 시스템 계층 | 오케스트레이션·프로세스 제어 | 데이터 저장소          | 정보 검색·컨텍스트 증강 |
| 노드        | 작업 (조사·검증·승인)     | 개체 (고객·상품)       | 문서 속 개체         |
| 엣지        | 실행 순서·조건 분기       | 개체 간 관계           | 개체 간 의미 관계    |

부속 어휘도 진영이 갈린다 — Neo4j·Cypher·GQL·지식 그래프·트리플·온톨로지는 데이터 진영의 말이고,
StateGraph·조건부 엣지·체크포인터·`interrupt`는 이 책 진영의 말이다.
검색하다 Neo4j나 GraphRAG 자료를 만나면 다른 분야라고 생각하면 된다.
