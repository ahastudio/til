# Cerebras가 사내 지식 베이스를 구축한 방법

원문: <https://twitter.com/cerebras/status/2077822555159945507>

블로그 원문: <https://www.cerebras.ai/blog/how-we-built-our-knowledge-base>

GN 토론: <https://news.hada.io/topic?id=31850>

## 요약

저자는 Isaac Tai, Daniel Kim, Mike Gao다.
Cerebras 직원들은 사내 지식 베이스 "Cerebras Knowledge"에 하루
15,000건 이상의 질문을 던진다.
출시 3개월 만에 회사에서 가장 널리 쓰이는 사내 도구 중 하나가 되었으며,
사람뿐 아니라 자동화 스크립트와 에이전트도 이 시스템을 사용한다.

Cerebras는 데이터 센터 운영, 칩 설계, 하드웨어, 트레이닝, 추론, 클라우드
플랫폼 등 여러 팀으로 구성되어 있고, 매년 많은 신규 입사자가 합류한다.
그 결과 "이거 어디 있어?", "이 분야 전문가가 누구야?", "이게 뭐야?" 같은
질문이 사내 커뮤니케이션 채널에 반복적으로 쌓이는 문제를 겪었다.

지식 베이스는 세 가지 구성 요소로 이루어진다.
사내 데이터를 수집하고 저장하는 플랫폼, 그 데이터를 질의하는 플랫폼,
그리고 인증·인가·감사·분석을 담당하는 계층이다.
핵심에는 여러 소스의 임베딩과 원본 요약, 메타데이터를 담는 단일
Postgres 테이블(pgvector, 3072차원, HNSW 인덱스)이 있으며, Slack
스레드부터 회로 설계 파일(netlist)까지 모든 소스가 하나의 커넥터를
거쳐 같은 테이블에 들어가고 동일한 인터페이스로 질의된다.

Slack 처리에는 전문 검색·임베딩·IDF·시간 가중치를 결합한 하이브리드
검색, LLM이 스레드를 질문·요약·해결책·참조 시스템으로 구조화하는
"증류(distillation)", 같은 작성자의 연속 메시지를 묶어 별도로
임베딩하는 "버스팅(bursting)" 기법이 쓰인다.
코드 저장소는 CocoIndex 프레임워크로 언어별 경계(클래스 → 메서드 →
블록)를 따라 재귀적으로 청크를 나누고, 변경분만 재임베딩하는 증분
방식으로 40GB가 넘는 저장소를 최신 상태로 유지한다.
질의 시점에는 LLM 플래너가 어떤 도구(subsystem_index, search,
search_slack, search_code, recent_prs, who_knows)를 쓸지 먼저 결정하고
병렬로 실행한 뒤, 여러 검색 결과를 RRF(Reciprocal Rank Fusion, k=60)로
융합하고 소형 리랭커 모델로 상위 10개를 추린다.
MCP를 통해서는 이 검색 도구들을 LLM 없이 직접 호출 가능한 원시 도구로
노출해 Claude Code 같은 에이전트가 오케스트레이션을 맡도록 하고, 웹
UI에서는 플래너 → 실행기 → 합성기 파이프라인이 자동으로 돌아간다.
검색 범위는 "프로젝트" 단위로 Slack 채널·저장소·문서를 묶어 스코핑할
수 있고, 사용자는 온보딩 시 기본 프로젝트를 지정해 자신과 무관한
팀의 결과가 섞이지 않도록 한다.

## 분석

### 통합이 아니라 연결을 선택한 이유

Cerebras의 설계에서 가장 두드러지는 결정은 "하나의 도구로 통합"하지 않고
"기존 소스를 연결"하는 쪽을 택했다는 점이다.
원문은 이를 "모든 정보를 하나의 플랫폼에 기록하자"는 제안이 분기마다
반복되지만 실제로는 거의 성공하지 못하는 "단일 진실 공급원(single
source of truth)의 꿈"이라고 표현한다.
문서의 제안 편집, Slack 스레드, GitHub의 코드 참조, Jira의 상태
메타데이터는 각각 그 도메인에 맞게 수년간 다듬어진 도구이며, PR을
Google Docs에서 논의하는 것이 끔찍한 경험이 되듯 도구를 옮기는 순간
워크플로의 품질이 떨어진다.
그래서 Cerebras Knowledge는 기존 동작을 최소한으로만 바꾸도록
설계되었고, 데이터 수집은 각 플랫폼에서 직접 추출하는 방식을 택했다.

### 단일 임베딩 테이블과 커넥터라는 단순한 인터페이스

Cerebras는 Slack 스레드부터 netlist까지 성격이 전혀 다른 데이터를
하나의 Postgres 임베딩 테이블(문서, 임베딩, 메타데이터, 소스와
타임스탬프)로 정규화하는 구조를 선택했다.
소스별로 정의하는 것은 "데이터가 무엇인지, 어떻게 연결하는지, 얼마나
자주 가져올지"뿐이며, 결과 레코드는 어느 소스에서 왔든 동일한
인터페이스를 따른다.
이 단순함 덕분에 사내 다른 팀 개발자가 직접 커넥터를 작성해 새로운
데이터 소스를 추가할 수 있고, 커스텀 데이터베이스를 가진 팀도 작은
Python 스크립트 하나로 같은 스키마의 행을 내보내기만 하면 나머지
스택은 그대로 동작한다.

### Slack을 위한 4중 하이브리드 검색

Slack 메시지는 정보 밀도 편차가 크고("hey yeah sure mike"와 상세한
커널 설명이 똑같이 하나의 메시지다), 메시지 길이가 짧을수록 코사인
유사도에서 오히려 유리해지는 역설이 있으며, 의미가 주변 대화 맥락에
크게 의존한다.
Cerebras는 이 문제를 해결하기 위해 임베딩 단독이 아니라 네 가지 신호를
결합한다.
전문 검색(full-text)은 에러 문자열이나 플래그 이름처럼 임베딩이
뭉개버리는 정확한 토큰을 잡아내고, 임베딩 검색은 어휘가 전혀 다른
질문과 답변을 의미로 연결하며, IDF는 희귀한 토큰이 담긴 짧은 메시지가
"sounds good, thanks!" 같은 필러보다 높은 순위를 받도록 하고, 시간
가중치는 같은 질문에 대한 답이 여러 개일 때 이미 사라진 인프라를
설명하는 6개월 전 스레드보다 최근 스레드가 이기도록 만든다.
각 기법은 독립적인 랭킹 뷰를 만들고, 이 뷰들은 질의 시점에 RRF로
융합된다.

### 실시간 수집과 스레드 단위 재수집

Slack 봇은 Socket Mode로 워크스페이스에 설치되어 모든 메시지 이벤트를
지속적인 웹소켓으로 실시간 수신하며, Web API를 폴링하지 않아 레이트
리밋 소모가 없다.
이벤트가 도착하면 즉시 확인 응답을 보내고 이벤트 ID로 중복을
제거한다.
중요한 설계는 새 메시지 하나만 저장하는 것이 아니라, 그 메시지가
속한 스레드 전체(부모와 모든 답글)를 Slack API에서 다시 가져와 하나의
행으로 다시 쓰는 방식이다.
즉 답글 하나가 달릴 때마다 스레드 전체가 재수집되어, 저장된 내용과
참여자 목록, 마지막 활동 시각이 항상 전체 대화를 반영한다.
채널마다 별도의 데이터 소스로 취급되므로, 인시던트 채널처럼 활발한
채널은 더 자주 수집하도록 팀별로 신선도를 조정할 수 있다.

### 스레드 증류와 버스팅

Postgres GIN 인덱스로 원문 텍스트는 즉시 키워드 검색이 가능하지만,
유용한 벡터 검색을 위해서는 추가 처리가 필요하다.
증류 단계에서 LLM은 전체 스레드에서 "엔지니어가 실제로 검색할 법한
한 줄짜리 질문", 짧은 요약, 해결책, 언급된 시스템과 코드 참조를
구조화된 형태로 추출한다.
Cerebras는 원본 대화 전문을 직접 임베딩하지 않고 이렇게 정규화된
형태를 임베딩했을 때 정확도가 크게 올랐다고 밝힌다.
그럼에도 긴 스레드 안에서 중요한 개별 메시지가 스레드 수준 요약에
반영되지 않는 문제가 남았고, 이를 보완하기 위해 같은 작성자가 연속으로
남긴 메시지 묶음("burst")에 스레드 주제를 앞에 붙여 별도로
임베딩한다.
모든 버스트를 임베딩하면 저품질 데이터가 쌓이므로, IDF 4.0 이상의
희귀 토큰 포함 여부, 200자 이상의 길이, 이모지 반응 여부라는 세 가지
신호를 가중 결합해 임계값을 넘는 버스트만 데이터베이스에 넣는다.

### CocoIndex 기반 언어 인식 코드 청킹과 증분 임베딩

Cerebras는 처음에는 "grep만 있으면 충분하다"는 관점에서 코드
임베딩의 필요성 자체를 논쟁했으나, 업계 동향과 Cursor의 대규모
코드베이스 시맨틱 검색 사례를 검토한 뒤 시도하기로 했다.
40GB가 넘는 저장소를 포함한 여러 사내 저장소를 다루기 위해 CocoIndex를
채택했고, 언어별 정규식 경계를 굵은 단위에서 세밀한 단위 순서로
적용하는 재귀적 청킹을 쓴다.
분할기는 먼저 클래스 같은 상위 경계를 시도하고, 청크가 여전히 크면
메서드 경계로, 그다음 더 작은 블록으로 내려간다.
파일 하나가 파일 수준과 함수 수준처럼 서로 다른 구체성의 임베딩을
여러 개 만들어낼 수 있다.
CocoIndex는 동기화 메타데이터를 Postgres에 함께 저장하기 때문에,
커밋이 있을 때마다 저장소 전체가 아니라 변경된 청크만 재임베딩하고
재수출한다.

### LLM 쿼리 플래너와 RRF 기반 융합, 리랭킹

모든 질의는 먼저 짧은 플래닝 단계를 거친다.
LLM이 subsystem_index(파일별 요약), search(Slack·위키·코드 등을
아우르는 통합 벡터 파이프라인), search_slack, search_code(ripgrep),
recent_prs, who_knows(주제별 전문가) 중 어떤 도구가 관련 있을지
결정한다.
플래너는 어떤 프로젝트가 존재하고 각 프로젝트에 어떤 소스가 있으며
각 소스가 무엇에 강한지에 대한 압축된 설명을 참고해 도구를
선택하고, 실행기가 이를 병렬로 팬아웃한 뒤 공통 증거 포맷으로
정규화해 최종 합성 LLM에 전달한다.
서로 다른 검색기의 결과 목록은 RRF(가중치 1.0, 평활 상수 k=60)로
융합되는데, 이 상수는 여러 검색기에서 골고루 상위권에 오른 문서가
단 하나의 검색기에서만 1위인 문서를 이기게 만든다.
융합 후에는 중복 청크를 소스 단위로 병합하고 파일당 기여 개수를
제한해 상위 20개의 다양성을 확보한 다음, 원 질의와 함께 소형 리랭커
모델에 보내 0~10점을 매기고 상위 10개만 남긴다.
최종 승자에게는 위키 섹션을 매칭했을 때 인접한 두 섹션을 함께
가져오는 식으로 청킹 과정에서 잘려나간 맥락을 다시 붙여준다.

### MCP와 웹 UI의 서로 다른 오케스트레이션 책임

MCP 통합에서는 검색 기능을 "질문에 답하라"는 단일 엔드포인트 뒤에
숨기지 않고, search_slack이나 search_code 같은 원시 검색 도구를
그대로 노출한다.
이 도구들은 의도적으로 단순하고 LLM에 최대한 의존하지 않도록
만들어져 있어, Claude Code 같은 MCP 호환 에이전트가 어떤 도구를
어떤 순서로 부를지 스스로 오케스트레이션한다.
반대로 웹 UI에서는 같은 도구들이 완전한 파이프라인 뒤에 있으며, UI
에이전트가 플래너·실행기·합성기 전 단계를 직접 소유해 사용자에게는
"질문하면 답이 나온다"는 경험만 남는다.

### 프로젝트 단위 스코핑으로 관련성 확보

말뭉치가 커지면서 "모든 것을 검색"하는 방식은 빠르게 쓸모를
잃었고, 컴파일러 팀은 자신의 결과에 인프라 런북이 섞이는 것을
원하지 않았다.
Cerebras는 특정 팀이나 이니셔티브에 관련된 Slack 채널, 코드 저장소,
내부 데이터베이스, 문서 공간을 이름 붙인 묶음으로 "프로젝트"를
도입했고, 공유 인시던트 채널처럼 같은 소스를 여러 프로젝트가
중복 없이 참조할 수 있게 했다.
온보딩 과정에서 사용자는 자신의 업무에 맞는 기본 프로젝트를
선택하며, 이 기본값이 프로필에 저장되어 이후 질의 범위를 자동으로
좁혀준다.

## 비평

### "3개월 만에 15,000건"이 증명하는 것은 채택이지 정확도가 아니다

원문이 성공의 증거로 제시하는 지표는 질의량뿐이다.
하루 15,000건이라는 숫자는 시스템이 자주 호출된다는 사실을 보여줄 뿐,
답변의 정확도나 유용성, 혹은 잘못된 답변으로 인한 비용은 전혀 드러내지
않는다.
자동화 스크립트와 에이전트가 질의 주체에 포함된다는 서술은 특히 주의가
필요한데, 에이전트가 반복적으로 같은 질의를 자동 생성하는 경우 질의량은
쉽게 부풀려질 수 있다.
채택 지표와 품질 지표를 구분하지 않고 하나의 숫자로 성공을 서술하는 것은,
사내 도구 홍보 글에서 흔히 나타나는 과장이며 이 글도 예외가 아니다.

### 권한(auth) 계층의 실제 동작이 가장 짧게 다뤄진다

원문은 "인증과 인가를 담당하는 계층"이 세 가지 핵심 구성 요소 중
하나라고 명시하지만, Slack 비공개 채널, 특정 팀만 접근 가능한
저장소, 민감한 커스텀 데이터베이스가 하나의 공유 임베딩 테이블에
섞여 있는 상황에서 질의 시점에 권한 필터링이 정확히 어떻게
이루어지는지는 설명하지 않는다.
프로젝트 단위 스코핑이 소개되지만, 이는 관련성을 높이기 위한
장치로 서술될 뿐 접근 권한 통제 장치로 명시되지는 않는다.
공유 테이블 설계상 권한 검증은 임베딩 단계가 아니라 매 질의·응답
단계에서 재확인되어야 하는데, 이 부분이 구현의 핵심 난이도임에도
가장 짧게 언급되고 넘어간다.

### 커넥터 확장 구조의 품질 관리가 생략되어 있다

다른 팀 개발자와 커스텀 데이터 소스 팀이 직접 커넥터나 Python
스크립트를 작성해 데이터를 추가할 수 있다는 서술은 확장성 측면에서는
매력적이지만, 그렇게 추가된 커넥터가 얼마나 정확하게 데이터를
요약하고 임베딩하는지에 대한 품질 기준은 언급되지 않는다.
소스가 늘어날수록 팀마다 검색 품질 편차가 커질 가능성이 높은데, 원문은
이 편차를 어떻게 검증하고 관리하는지 설명하지 않는다.

### 리랭커와 합성 LLM의 실패 모드가 다뤄지지 않는다

RRF 융합 이후 소형 리랭커 모델이 0~10점을 매겨 상위 10개를
추리고, 최종 합성 LLM이 답변과 인용을 생성하는 구조는 두 개의 LLM
호출이 검증 없이 순차적으로 최종 답변에 영향을 미친다는 뜻이다.
원문은 이 리랭커나 합성 단계가 잘못된 점수를 매기거나 근거 없는
답을 합성했을 때 이를 어떻게 감지하고 되돌리는지에 대해서는
다루지 않는다.

## 인사이트

### 통합 대신 연결을 택하는 설계는 조직의 정치적 마찰을 줄이는 전략이기도 하다

Cerebras의 접근은 기술적 선택이면서 동시에 조직 관리의 선택이다.
새 도구로 데이터를 이전하라고 요구하면 각 팀은 자신들의 워크플로가
침해당한다고 느끼고 저항하지만, 기존 도구는 그대로 두고 인덱스만
추가하면 어떤 팀도 도구를 바꿀 필요가 없다.
이는 사내 소프트웨어 도입에서 반복적으로 관찰되는 패턴으로, 기술적으로
더 우아한 통합보다 정치적으로 마찰이 적은 연결이 실제 채택률에서
승리하는 경우가 많다.

### 소스별 맞춤 파이프라인은 검색 시스템을 소프트웨어 유지보수 문제로 되돌린다

RAG를 "임베딩하고 검색하면 끝"이라는 단순 모델로 접근하는 조직이
여전히 많은 가운데, Cerebras의 사례는 실제 성과를 내려면 소스마다
별도의 전처리 로직—Slack의 증류와 버스팅, 코드의 언어 인식 청킹과
증분 임베딩—이 필요하다는 것을 보여준다.
이는 검색 시스템의 문제를 모델링 문제에서 전통적인 소프트웨어
엔지니어링 문제로 되돌린다는 의미이며, 지식 베이스의 품질은 최신
임베딩 모델이 아니라 소스별 파이프라인을 얼마나 꾸준히 유지보수하는
팀 역량에 달려 있다는 결론으로 이어진다.

### MCP 도구를 얇게 유지하는 선택은 오케스트레이션 책임을 클라이언트로 넘기는 결정이다

Cerebras는 MCP에서 검색 도구를 의도적으로 LLM 없이 작동하도록
단순하게 유지하고, Claude Code 같은 에이전트가 오케스트레이션을
맡도록 설계했다.
이는 검색 인프라 자체는 어떤 LLM의 판단에도 의존하지 않고 안정적으로
동작해야 하며, 그 위에서 무엇을 언제 호출할지 결정하는 판단은
호출하는 에이전트의 책임으로 넘긴다는 아키텍처 원칙을 보여준다.
검색 계층과 추론 계층을 분리하면 검색 계층의 신뢰성을 독립적으로
검증할 수 있다는 장점이 있지만, 동시에 에이전트가 도구를 잘못
조합해 호출하는 오류는 오롯이 에이전트 쪽 문제로 남는다는 뜻이기도
하다.

### 질의 주체에 에이전트를 포함시키는 순간, 지식 베이스는 사람이 아니라 다른 소프트웨어를 위한 인프라가 된다

하루 15,000건의 질의 중 상당수가 자동화 스크립트와 에이전트에서
나온다는 서술은, 이 시스템의 진짜 소비자가 이미 사람에서 소프트웨어로
옮겨가고 있다는 신호다.
에이전트가 스스로 지식 베이스에 질의해 코드를 작성하거나 의사결정을
내리는 구조가 되면, 검색 결과의 오류가 사람의 검토 없이 곧바로 다음
행동으로 이어질 위험이 커진다.
이는 사내 지식 베이스의 설계 기준이 "사람이 읽고 판단하는 참고 자료"에서
"기계가 즉시 신뢰하고 실행하는 입력값"으로 이동하고 있음을 뜻하며,
검색 정확도에 대한 요구 수준 자체가 근본적으로 달라져야 한다는 것을
시사한다.
이 전환은 Cerebras만의 특수한 상황이 아니라, 에이전트를 사내 워크플로에
투입하는 모든 조직이 곧 마주할 구조적 변화다.
