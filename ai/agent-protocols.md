# AI 에이전트 프로토콜 여섯 개, 각각 무엇을 푸는가

원문: [Developer's Guide to AI Agent Protocols](https://developers.googleblog.com/developers-guide-to-ai-agent-protocols/)

HN 토론: <https://news.ycombinator.com/item?id=47473721> (2점, 1개 댓글)

## 요약

Google의 시니어 AI 프로덕트 매니저 Shubham Saboo와 개발자 관계 엔지니어 Kristopher Overholt가 2026년 3월 18일에 Google 개발자 블로그에 쓴 글이다.
MCP, A2A, UCP, AP2, A2UI, AG-UI라는 여섯 개 프로토콜 약어가 각각 어떤 가치를 주는지를, ADK(Agent Development Kit)로 레스토랑 공급망 에이전트를 단계적으로 만들어 가며 보여준다.
시나리오는 도매 식자재 주문, 재고 데이터베이스 조회, 원격 공급사 에이전트와의 통신, 안전한 거래 실행, 대화형 대시보드 렌더링이며, 모든 것을 환각하는 맨몸 LLM에서 시작해 실제 재고를 확인하고 전문가 견적을 받고 주문을 넣고 결제를 승인하고 스트리밍 대시보드를 그리는 에이전트까지 진행한다.

### MCP — 도구와 데이터 연결

시스템과 데이터에 접근하는 에이전트를 만들려면 보통 API마다 맞춤 통합 코드가 필요하다.
MCP(Model Context Protocol)는 수백 개 서버에 대한 단일 표준 연결 패턴을 제공해 이를 없앤다 — 서버가 자기 도구를 광고하고 에이전트가 자동으로 발견한다.
MCP 서버는 그 시스템을 만든 팀이 유지하므로, 통합 코드를 수동으로 갱신하지 않아도 에이전트는 항상 최신 도구 정의를 받는다.

ADK는 `McpToolset`으로 MCP를 일급 지원한다.
주방 매니저 에이전트는 MCP Toolbox for Databases로 PostgreSQL을 읽고, Notion MCP로 레시피를 조회하고, Mailgun MCP로 공급사에 메일을 보낸다.

```python
inventory_tools = ToolboxToolset(server_url=TOOLBOX_URL)

notion_tools = McpToolset(connection_params=StdioConnectionParams(
    server_params=StdioServerParameters(
        command="npx", args=["-y", "@notionhq/notion-mcp-server"],
        env={"NOTION_TOKEN": NOTION_TOKEN}),
    timeout=30))

kitchen_agent = Agent(
    model="gemini-3-flash-preview",
    name="kitchen_manager",
    instruction="You manage a restaurant kitchen. Check inventory, look up recipes, email suppliers.",
    tools=[inventory_tools, notion_tools, mailgun_tools],
)
```

### A2A — 에이전트 간 통신

MCP가 데이터 접근을 처리하면 다음 과제는 전문성이다.
주방 매니저는 재고는 확인할 수 있지만 현재 도매가, 공급사 품질 등급, 배송 시간대는 모를 수 있고, 그 지식은 다른 팀이 다른 프레임워크로 다른 서버에 올린 원격 에이전트에 있다.

A2A(Agent2Agent) 프로토콜은 에이전트가 서로를 발견하고 통신하는 방식을 표준화한다.
각 A2A 에이전트는 잘 알려진 URL(`/.well-known/agent-card.json`)에 이름·역량·엔드포인트를 기술한 Agent Card를 게시한다.
주방 매니저는 이 카드들을 가져와 각 원격 에이전트가 무엇을 하는지 배우고 런타임에 적절한 쪽으로 질의를 라우팅하며, 새 원격 에이전트를 추가하려면 URL만 추가하면 되고 수동 코드 변경이나 재배포가 필요 없다.

ADK의 `RemoteA2aAgent`는 턴당 원격 에이전트 하나로 라우팅하므로, 가격·품질·배송을 동시에 확인하는 것처럼 질의가 여러 원격 에이전트에 걸치면 `a2a-sdk`를 직접 쓴다.

```python
# EXPOSE
app = to_a2a(pricing_agent, port=8001)

# DISCOVER
client = await ClientFactory.connect("http://pricing-agent:8001")
card = await client.get_card()

# CALL
msg = create_text_message_object(content="What's today's wholesale price for salmon?")
async for response in client.send_message(msg):
    ...
```

### UCP — 상거래 표준화

공급사를 발견하고 견적을 받을 수 있게 되었지만 실제 주문 단계에서는 공급사마다 API가 다르다 — 도매상 다섯 곳을 통합하면 체크아웃 흐름을 다섯 개 만들어야 한다.

UCP(Universal Commerce Protocol)는 쇼핑 생애주기를 모듈형 역량으로 표준화하며, 강한 타입의 요청·응답 스키마가 하부 전송 방식과 무관하게 일관되게 유지된다.
에이전트는 REST, MCP, A2A, 또는 브라우저 기반 흐름을 위한 EP(Embedded Protocols)를 통해 통일된 패턴으로 상호작용한다.
A2A에서 본 것과 같은 잘 알려진 URL 패턴(`/.well-known/ucp`)으로 공급사 카탈로그를 발견한 뒤 타입이 정해진 체크아웃 요청을 구성해 주문을 완료하며, 표준 REST API도 지원해 독점 SDK 없이 아무 HTTP 클라이언트로도 동작한다.

```python
profile = UcpDiscoveryProfile.model_validate(
    (await c.get("http://example-wholesale:8182/.well-known/ucp")).json())

checkout_req = CheckoutCreateRequest(
    currency="USD",
    line_items=[
        LineItemCreateRequest(quantity=10, item=ItemCreateRequest(id="salmon")),
        LineItemCreateRequest(quantity=3,  item=ItemCreateRequest(id="olive_oil")),
    ],
    payment=PaymentCreateRequest(),
)

headers = {"UCP-Agent": 'profile="https://kitchen.example/agent"',
           "Idempotency-Key": str(uuid.uuid4()), "Request-Id": str(uuid.uuid4())}
```

작업마다 새 `Idempotency-Key`를 쓰는 점이 예제에 명시되어 있다.

### AP2 — 결제 권한

주문을 넣을 수 있게 되었지만 그 지출을 누가 승인했는지는 남지 않는다 — 어떤 한도가 설정되었는지, 어떤 판매자가 승인되었는지, 권한이 언제 만료되는지에 대한 기록이 없다.

AP2(Agent Payments Protocol)는 타입이 정해진 맨데이트(mandate)로 그 층을 채운다.
의도에 대한 부인 불가능한 증명을 제공하고 모든 거래에 설정 가능한 가드레일을 강제한다.
UCP가 무엇을 누구에게 주문하는지를 다룬다면 AP2는 누가 그 구매를 승인했는지와 감사 추적을 다루며, AP2가 UCP의 확장으로 꽂혀 체크아웃 흐름에 암호학적 인가 증명을 더한다.

`IntentMandate`가 허용 판매자와 자동 승인 지출 한도를 정하고, 에이전트가 특정 장바구니와 금액에 묶인 `PaymentMandate`를 생성하며, 주문이 한도를 넘으면 매니저가 명시적으로 승인할 때까지 맨데이트는 서명되지 않은 채 남고, `PaymentReceipt`가 감사 추적을 닫는다.

```python
intent = IntentMandate(
    natural_language_description="10 lbs salmon, 3 bottles olive oil",
    merchants=["Example Wholesale"],
    requires_refundability=True,
    user_cart_confirmation_required=False,
    intent_expiry="2026-02-23T20:00:00Z",
)
```

글은 AP2가 v0.1이고 타입이 ADK 코어에 내장되지 않은 별도 패키지로 제공된다고 밝힌다.

### A2UI — 무엇을 그릴지

모든 결과가 평문으로 돌아오는데, 재고 대시보드나 주문 양식이나 공급사 비교를 보여주려면 보통 별도 프론트엔드 컴포넌트가 필요하고 새 UI 요구마다 코드가 늘어난다.

A2UI(Agent-to-User Interface Protocol)는 에이전트가 고정된 카탈로그에서 새 레이아웃을 동적으로 조합하게 한다.
행, 열, 텍스트 필드 같은 안전한 컴포넌트 프리미티브 18개로 구성된 선언적 JSON 형식이다.
A2UI는 UI 구조와 데이터를 분리한다 — 에이전트가 ID로 서로를 참조하는 평평한 컴포넌트 목록을 보내고 이어서 별도의 데이터 페이로드를 보내면, 클라이언트의 렌더러가 이 JSON을 Lit·Flutter·Angular 같은 프레임워크로 네이티브 UI로 바꾼다.

```python
a2ui_messages = [
    {"beginRendering": {"surfaceId": "default", "root": "card"}},
    {"surfaceUpdate": {"surfaceId": "default", "components": [
        {"id": "card", "component": {"Card": {"child": "col"}}},
        {"id": "col", "component": {"Column": {"children": {"explicitList": ["title", "price", "buy"]}}}},
        {"id": "title", "component": {"Text": {"usageHint": "h3", "text": {"path": "name"}}}},
    ]}},
    {"dataModelUpdate": {"surfaceId": "default", "contents": [
        {"key": "name",  "valueString": "Fresh Atlantic Salmon"},
        {"key": "price", "valueString": "$24.00/lb"},
    ]}},
]
```

같은 에이전트에 세 번 프롬프트하면 `CheckBox`, `TextField`, `DateTimeInput`, `Card` 같은 컴포넌트로 재고 체크리스트, 주문 양식, 공급사 비교라는 전혀 다른 인터페이스가 프론트엔드 코드 추가 없이 나온다.
개발 중에는 ADK 웹 인터페이스(`adk web`)가 A2UI 컴포넌트를 네이티브로 렌더링해 준다.

### AG-UI — 어떻게 스트리밍할지

전통적 REST API는 응답을 돌려주고 끝나지만 에이전트는 다르다 — 텍스트를 점진적으로 스트리밍하고, 응답 중간에 도구를 호출하고, 때로는 사람 입력을 기다리며 멈춘다.
ADK는 이벤트를 직접 스트리밍하는 `/run_sse` 엔드포인트를 제공하고 프론트엔드 코드 수십 줄이면 스트림을 파싱해 도구 호출을 그릴 수 있지만, 그 파싱 코드는 상투적이고 이벤트 형식이 바뀔 때마다 깨진다.

AG-UI(Agent-User Interaction Protocol)는 그 상투적 코드를 없앤다.
프레임워크의 원시 이벤트를 표준화된 SSE 스트림으로 번역하는 미들웨어이며, 프론트엔드는 어떤 에이전트 프레임워크가 만들었는지 신경 쓰지 않고 `TEXT_MESSAGE_CONTENT`나 `TOOL_CALL_START` 같은 타입 이벤트를 듣는다.

```python
ag_ui_agent = ADKAgent(adk_agent=kitchen_mgr, app_name="kitchen", user_id="chef")
app = FastAPI()
add_adk_fastapi_endpoint(app, ag_ui_agent, path="/")

# RUN_STARTED / TOOL_CALL_START / TOOL_CALL_RESULT / TOOL_CALL_END
# TEXT_MESSAGE_CONTENT ... / RUN_FINISHED
```

### 전부 합치면

여섯 프로토콜이 모두 들어가면 처음의 맨몸 LLM이 실제 재고를 확인하고 공급사를 발견하고 주문을 넣고 결제를 승인하고 대화형 대시보드를 스트리밍하는 수준이 된다.
연어 재고를 확인하고, 오늘 도매가와 품질 등급을 받고, 부족하면 Example Wholesale에서 10파운드를 주문하고 결제를 승인하라는 요청 하나가 세 단계로 처리된다.
① 정보 수집 — MCP가 재고 DB에 연어를 질의하고(`check_inventory`), A2A가 원격 가격·품질 에이전트에 질의한다(`ask_agent`).
② 거래 완료 — UCP가 Example Wholesale에 체크아웃 요청을 보내고(`place_order`), AP2가 설정된 가드레일 안에서 결제 맨데이트로 주문을 보증한다(`authorize_payment`).
③ 결과 제시 — A2UI가 결과에서 대화형 위젯을 조합하고, AG-UI가 도구 호출과 텍스트 응답을 실시간으로 프론트엔드에 전달한다.

마지막 조언은 네 가지다 — 각 프로토콜이 어떤 문제를 푸는지 알고 그 경계를 지켜 아키텍처를 깨끗하게 유지할 것, 첫날부터 여섯 개가 다 필요하지는 않으니 대부분 MCP로 시작해 필요할 때 해당 프로토콜을 들일 것, 프로토콜이 빠르게 움직이므로 직접 구현하기 전에 ADK 통합·공식 SDK·샘플 코드를 확인할 것, 이 프로토콜들이 아직 성숙 중이지만 잘 알려진 URL을 통한 발견·타입이 정해진 요청/응답 스키마·표준 이벤트 스트림이라는 패턴이 생태계 호환성을 만들어 주므로 표준을 일찍 채택할 것.

## 분석

### 여섯 프로토콜을 하나의 서사에 꿴 방식이 이 글의 실제 기여다

각 프로토콜을 따로 설명하는 문서는 이미 각 프로토콜의 공식 사이트에 있다.
이 글이 더한 것은 순서다 — 맨몸 LLM에서 시작해 각 단계에서 무엇이 부족한지 보여주고 그 부족을 메우는 프로토콜을 하나씩 들인다.

이 구성이 효과적인 이유는 각 프로토콜의 존재 이유가 앞 프로토콜의 한계에서 자연스럽게 나오기 때문이다.
MCP로 재고는 알지만 시세는 모른다 → A2A.
견적은 받았지만 주문 API가 제각각이다 → UCP.
주문은 넣었지만 누가 승인했는지 기록이 없다 → AP2.
결과가 전부 평문이다 → A2UI.
스트리밍 파싱 코드가 계속 깨진다 → AG-UI.

동시에 이 서사는 설득 장치이기도 하다.
각 단계의 결핍이 실제 제품에서 그 순서로 나타나는지는 별개 문제이고, 뒤에서 다루겠지만 특히 UCP와 AP2는 대부분의 에이전트가 도달하지 않는 지점이다.
서사의 매끄러움이 필요성의 증거처럼 읽히게 만드는 것이 이 글의 수사적 구조다.

### 여섯 프로토콜이 실은 세 쌍이다

목록은 여섯이지만 구조를 보면 세 개의 짝이다.
MCP와 A2A는 에이전트가 바깥으로 나가는 통로이고 — 하나는 도구로, 하나는 다른 에이전트로 — 발견 방식도 같은 형태다.
UCP와 AP2는 상거래 한 쌍이며, 글 자신이 AP2가 UCP의 확장으로 꽂힌다고 명시한다.
A2UI와 AG-UI는 사용자 인터페이스 한 쌍으로, 하나는 무엇을 그릴지를 다른 하나는 어떻게 전달할지를 정한다.

이 짝 구조가 드러나면 목록의 위압감이 줄어든다.
실제로 배워야 할 개념은 세 가지 — 바깥과 연결하기, 돈이 오가는 거래 다루기, 사람에게 보여주기 — 이고 각각에 두 층이 있을 뿐이다.
글의 마지막 조언인 필요할 때 들이라도 이 구조에서 자동으로 나온다 — 세 영역 중 자기 제품에 해당하는 것만 들이면 된다.

그런데 글은 이 짝 구조를 명시적으로 정리하지 않고 1번부터 6번까지 평평하게 나열한다.
그 결과 여섯 개를 다 알아야 할 것 같은 인상이 남고, 정작 각 짝 안에서 두 층이 왜 분리되어야 하는지 — 특히 A2UI와 AG-UI가 왜 하나가 아닌지 — 는 설명되지 않는다.

### 공통 설계 어휘가 반복해서 나타난다

여섯 프로토콜을 관통하는 패턴이 몇 개 있고, 글도 마지막에 이를 요약한다 — 잘 알려진 URL을 통한 발견, 타입이 정해진 요청/응답 스키마, 표준 이벤트 스트림이다.

가장 눈에 띄는 것은 `/.well-known/` 경로의 재사용이다.
A2A는 `/.well-known/agent-card.json`, UCP는 `/.well-known/ucp`를 쓴다.
이는 RFC 8615가 정한 오래된 관례이고, `robots.txt`나 `security.txt`, ACME 도전 응답이 같은 자리를 쓴다.
새 프로토콜들이 발견 메커니즘을 새로 발명하지 않고 웹의 기존 규약에 얹었다는 점은 이 생태계가 웹 인프라 위에서 자라고 있음을 보여준다.

두 번째 패턴은 구조와 데이터의 분리다.
A2UI가 컴포넌트 트리와 데이터 모델을 따로 보내는 설계가 대표적인데, 이는 데이터만 갱신할 때 컴포넌트를 다시 보내지 않아도 되게 한다.
같은 발상이 UCP의 타입 스키마와 전송 방식 분리에도 있다 — 스키마는 REST든 MCP든 A2A든 그대로 유지된다.
LLM이 만들어내는 출력을 다루는 프로토콜이 왜 이런 분리를 필요로 하는지는 글이 설명하지 않지만, 토큰 비용과 스트리밍 특성을 생각하면 이유는 분명하다.

## 비평

### 글은 프로토콜을 소개하는 문서가 아니라 ADK 채택을 위한 문서다

모든 코드 예제가 ADK를 쓰고, 맺음말은 첫 에이전트를 세우고 MCP 서버에 연결한 뒤 거기서부터 프로토콜을 추가하라고 권한다.
이는 잘못이 아니라 Google 개발자 블로그의 당연한 성격이지만, 그 성격이 내용 선택을 왜곡하는 지점이 있다.

가장 뚜렷한 것은 각 프로토콜의 성숙도와 채택 현황이 거의 다뤄지지 않는다는 점이다.
MCP는 이미 광범위하게 채택되었고, A2A는 Google이 주도해 리눅스 재단으로 넘긴 상태이며, UCP·AP2·A2UI는 훨씬 초기다.
AP2에 대해서만 v0.1이라는 단서가 붙고 나머지에 대해서는 그런 표시가 없다.

이 차이는 실무 결정에 결정적이다.
성숙한 표준을 채택하는 것과 v0.1 명세에 코드를 맞추는 것은 완전히 다른 위험이고, 후자는 명세가 바뀔 때마다 재작업을 요구한다.
글은 이 프로토콜들이 빠르게 움직인다고 한 번 언급하고 표준을 일찍 채택하라고 권하는데, 빠르게 움직인다와 일찍 채택하라는 조합은 그 재작업 비용을 독자에게 조용히 넘긴다.

HN에 달린 유일한 댓글이 이 공백을 정확히 겨눈다 — wxw는 흥미롭다면서 MCP 말고 나머지는 얼마나 채택되었느냐고 묻는다.[^wxw]
이 글을 읽은 사람이 가장 먼저 갖는 질문이 그것이고, 글은 그 답을 주지 않는다.
반응 자체가 2점 1댓글에 그쳤다는 사실도 같은 방향을 가리킨다 — 여섯 개를 한 스택으로 묶은 서사가 아직 독자의 현실과 맞물리지 않았다는 신호다.

### 여섯 개가 필요한 예제를 고른 것 자체가 논증의 순환이다

레스토랑 공급망 시나리오는 여섯 프로토콜이 모두 등장하도록 설계되었다.
재고 DB가 있으니 MCP가 필요하고, 원격 전문가 에이전트가 있으니 A2A가 필요하고, 실제 구매가 있으니 UCP와 AP2가 필요하고, 대시보드를 보여주니 A2UI와 AG-UI가 필요하다.

문제는 이 시나리오가 얼마나 대표적이냐다.
실제로 배포된 에이전트의 압도적 다수는 데이터를 읽고 텍스트로 답한다 — MCP 하나면 끝난다.
자율적으로 돈을 쓰는 에이전트는 극소수이고, 그것을 허용하는 조직은 더 적다.
글의 마지막 조언도 대부분 MCP로 시작한다고 인정하는데, 그렇다면 본문의 8할은 대부분의 독자에게 해당하지 않는 이야기다.

더 유용했을 구성은 각 프로토콜을 언제 도입하지 않아야 하는지를 함께 말하는 것이다.
공급사가 세 곳뿐이라면 UCP보다 각각의 REST API를 직접 부르는 편이 싸고, 프론트엔드가 하나뿐이라면 A2UI의 18개 프리미티브로 조합하는 것보다 그냥 컴포넌트를 만드는 편이 낫다.
표준의 이득은 N이 클 때 나오는데, 글은 N이 클 때만 가정하고 그 조건을 명시하지 않는다.

### A2UI가 푼다고 주장하는 문제와 실제로 만드는 문제가 다르다

A2UI의 설명은 프론트엔드 코드를 새 UI 요구마다 만들지 않아도 된다는 것이다.
그런데 이 주장은 절반만 맞다 — 렌더러는 여전히 만들어야 하고, 18개 프리미티브를 각 플랫폼에서 네이티브 UI로 바꾸는 그 렌더러가 사실상 디자인 시스템이다.

즉 A2UI는 프론트엔드 작업을 없애는 것이 아니라 옮긴다.
화면마다 컴포넌트를 만드는 일에서, 프리미티브 집합을 구현하고 유지하는 일로 바뀐다.
후자가 유리한 경우는 화면 종류가 아주 많고 미리 알 수 없을 때이며, 정확히 그것이 에이전트가 만드는 UI의 특성이므로 방향 자체는 옳다.

문제는 표현력의 상한이다.
18개 프리미티브로 조합할 수 있는 것은 폼과 카드와 목록이고, 그 밖의 것은 만들 수 없다.
글이 든 예시 — 재고 체크리스트, 주문 양식, 공급사 비교 — 가 모두 그 범위 안에 있다는 점이 이 한계를 역설적으로 보여준다.
그리고 사용자가 그 범위 밖을 원하면 결국 전용 컴포넌트를 만들어야 하는데, 그때 A2UI 렌더러와 기존 프론트엔드 두 벌을 유지하게 된다.
이 이중 유지 비용이 글에는 없다.

### 여섯 개를 조합했을 때 생기는 문제를 다루지 않는다

각 프로토콜은 개별적으로 설명되고 마지막에 하나의 요청이 세 단계로 흐르는 그림이 나온다.
그런데 그 흐름에서 실패하면 무슨 일이 일어나는지는 없다.

UCP 체크아웃은 성공했는데 AP2 서명이 실패하면 주문은 어떻게 되는가.
A2A로 물어본 가격이 UCP 체크아웃 시점에 바뀌어 있으면 누가 그것을 감지하는가.
`Idempotency-Key`가 예제에 등장하는 것을 보면 재시도가 전제되어 있는데, 재시도 중에 IntentMandate가 만료되면 어떻게 되는가.
여섯 프로토콜이 각각 자기 층에서 타입 안전을 보장하지만, 층 사이의 상태 일관성은 아무도 보장하지 않는다.

이는 분산 트랜잭션의 고전적 문제가 프로토콜 스택 형태로 다시 나타난 것이다.
그리고 이 문제는 프로토콜이 늘어날수록 조합적으로 커지므로, 여섯 개를 다 쓰는 시스템에서 가장 어려운 부분이 된다.
글은 여섯 프로토콜이 각각 다른 문제를 풀며 하나의 에이전트를 통해 함께 작동한다는 문장으로 끝나는데, 함께 작동한다는 그 지점이 실은 가장 설명이 필요한 곳이다.

## 인사이트

### 이 목록은 프로토콜 표준화가 아니라 표준 경쟁의 스냅숏이다

여섯 개 중 A2A, UCP, AP2, A2UI는 Google이 주도했거나 깊이 관여한 것이고, MCP는 Anthropic이 만들었으며, AG-UI는 별개 커뮤니티에서 나왔다.
Google 블로그가 이들을 하나의 스택으로 제시한다는 것은 서로 다른 출처의 명세를 자사 프레임워크 안에서 통합해 보이겠다는 위치 선점이다.

이 구도는 낯설지 않다.
웹 초기에 HTML·CSS·JS·HTTP가 각기 다른 주체에서 나왔고, 브라우저 벤더들이 그것들을 묶어 자기 플랫폼으로 제시했다.
그때 승부를 가른 것은 명세의 우수성이 아니라 어느 구현이 실제로 쓰였느냐였고, 표준화 기구는 사후에 현실을 추인했다.

지금 상황도 비슷하다면 예측 가능한 것이 몇 가지 있다.
겹치는 프로토콜은 통합되거나 하나가 사라진다 — A2UI와 AG-UI처럼 인접한 영역은 특히 그렇다.
채택률이 낮은 명세는 이름만 남고 실제 구현은 파편화된다.
그리고 프레임워크가 여러 프로토콜을 흡수하면서 프로토콜 자체보다 프레임워크가 사실상의 인터페이스가 된다 — 이 글의 모든 예제가 ADK인 것이 그 방향을 보여준다.

실무자가 지금 할 수 있는 방어는 프로토콜 경계를 코드 안에서 명확히 유지하는 것이다.
ADK의 `McpToolset`을 쓰더라도 그것이 MCP를 감싼 어댑터라는 사실을 코드 구조로 표현해 두면, 프레임워크를 바꾸거나 명세가 바뀔 때 교체 범위가 좁아진다.

### 결제 프로토콜의 진짜 어려움은 암호가 아니라 조직의 승인 절차다

AP2가 제공하는 것은 IntentMandate, PaymentMandate, PaymentReceipt라는 세 단계 감사 추적이다.
기술적으로는 명료하지만, 이 구조가 실제로 쓰이려면 조직이 답해야 할 질문이 먼저 있다.

누가 IntentMandate를 만들 권한을 갖는가.
한도는 누가 정하고 얼마나 자주 검토하는가.
한도를 넘어 사람 승인이 필요한 요청이 하루 수십 건 생기면 그것을 누가 처리하는가.
만료된 맨데이트로 실패한 주문은 누구에게 알려지는가.

이 질문들은 프로토콜이 답하지 않으며, 답이 없으면 두 가지 중 하나가 일어난다 — 한도를 아주 낮게 잡아 에이전트가 아무것도 못 하게 되거나, 아주 높게 잡아 가드레일이 형식이 되거나.
그리고 후자가 훨씬 흔하다.
승인 피로는 예측 가능한 실패 모드이고, 예제의 `user_cart_confirmation_required=False`가 그 유혹을 이미 보여준다.

여기서 파생되는 관찰이 하나 더 있다.
AP2의 감사 추적이 진짜로 가치를 갖는 시점은 사고가 난 뒤이며, 그때 필요한 것은 무엇이 승인되었는가만이 아니라 왜 그 판단이 나왔는가다.
`natural_language_description`에 담긴 자연어 한 줄이 그 역할을 하도록 설계되어 있는데, 에이전트가 스스로 작성한 자연어 설명이 사후 책임 판단의 근거가 될 수 있는지는 완전히 열린 문제다.
서명은 누가 승인했는지를 증명하지만 무엇을 이해하고 승인했는지는 증명하지 못한다.

### 프로토콜 표준화의 이득은 도구 제공자 쪽에 먼저 쌓인다

MCP의 설명에서 글은 중요한 사실을 한 줄로 지나간다 — MCP 서버는 그 시스템을 만든 팀이 유지하므로 에이전트는 항상 최신 도구 정의를 받는다는 것이다.

이 문장에는 비용의 이동이 담겨 있다.
표준 이전에는 에이전트를 만드는 쪽이 각 API에 대한 통합을 만들고 유지했다.
표준 이후에는 API를 제공하는 쪽이 MCP 서버를 만들고 유지한다.
전체 작업량은 M×N에서 M+N으로 줄지만, 남은 N의 부담은 도구 제공자에게 간다.

도구 제공자가 그 부담을 받아들이는 이유는 명확하다 — 에이전트가 자기 서비스를 쓰게 하려면 그래야 하기 때문이다.
즉 MCP 서버를 만드는 것은 호의가 아니라 유통 채널 확보이며, 이는 과거 모바일 앱 시대에 모두가 API를 공개했던 것과 같은 유인 구조다.

그런데 이 구조에는 뒤따르는 국면이 있다.
유통 채널이 충분히 중요해지면 제공자는 그 채널을 통제하려 한다 — 요금제를 나누고, 특정 에이전트만 허용하고, 사용량을 제한한다.
UCP의 `UCP-Agent` 헤더가 에이전트의 역량 프로필을 가리킨다는 사양은 이미 그 통제의 첫 단계다.
지금은 무료로 열려 있는 MCP 서버들이 몇 년 뒤에도 그럴 것이라 가정하고 아키텍처를 짜는 것은 위험하며, 도구 접근에 대한 대체 경로를 남겨두는 편이 안전하다.

### 여섯 개의 프로토콜은 결국 하나의 오래된 질문으로 수렴한다

MCP는 원격 프로시저 호출이고, A2A는 서비스 발견이며, UCP는 표준 주문 스키마이고, AP2는 전자 서명과 감사 로그이며, A2UI는 서버 주도 UI이고, AG-UI는 이벤트 스트리밍이다.
어느 것도 새로운 발상이 아니다 — CORBA와 SOAP, UDDI, EDI, PKI, 서버 주도 렌더링, SSE로 각각의 조상을 찾을 수 있다.

이 계보를 짚는 것은 냉소가 아니라 예측을 위해서다.
이전 세대들이 어디서 실패했는지 보면 지금 무엇을 주의할지 알 수 있다.
CORBA와 SOAP은 스펙이 너무 커져 구현마다 호환되지 않았고, UDDI는 아무도 레지스트리를 유지하지 않아 죽었으며, EDI는 표준이 있음에도 파트너마다 방언이 생겼다.

세 실패 모드가 지금 그대로 재현될 조건이 보인다.
스펙 비대화는 여섯 개가 서로 확장하기 시작하면서 이미 진행 중이고, 레지스트리 유지 문제는 `/.well-known/` 방식으로 분산해 피했지만 대신 발견의 신뢰성 문제를 낳았으며, 방언 문제는 UCP처럼 여러 전송 방식을 허용하는 설계에서 특히 나타나기 쉽다.

살아남은 이전 세대의 공통점도 있다 — HTTP, JSON, OAuth처럼 작고 한 가지만 하는 것들이다.
그 기준으로 보면 여섯 중 MCP와 AG-UI가 가장 유리하다.
둘 다 하는 일이 좁고, 명세를 다 읽는 데 오래 걸리지 않으며, 잘못 구현하기 어렵다.
반대로 상거래와 결제처럼 도메인 규칙이 두꺼운 영역의 프로토콜은 역사적으로 표준화가 가장 어려웠던 곳이고, UCP와 AP2가 그 자리에 있다.
