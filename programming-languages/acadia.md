원문: [Rethinking Database Programming | Acadia](https://acadia.engineering/blog/rethinking-database-programming)

## 요약

Elm을 만든 Evan Czaplicki가 Acadia의 퍼블릭 알파를 공개하며 쓴 글이다.
지난 몇 년간 “Elm 같은 언어”의 이점을 SQL로 가져오려 해 왔으며, SQLite부터 PostgreSQL까지 훌륭한
데이터베이스 구현이 있으니 그것을 현대 프로그래머에게 더 편리하게 만들고 싶었다고 밝힌다.

목표를 네 가지로 제시한다.

더 정밀한 타입 — 요즘 많은 언어가 커스텀 타입을 지원하는데 그것을 데이터베이스에 저장할 쉬운 방법이
없다.
Rust에는 Enum이, Elm에는 Custom Type이, Haskell에는 대수적 자료형이 있는데 왜 그 정밀하고 표현력
있는 타입을 손으로 이상한 바이너리 레이아웃이나 JSON이나 널 가능 컬럼의 조합으로 바꿔야 하느냐고
묻는다.

검증된 마이그레이션 — SQL 마이그레이션이 매우 무섭다고 적는다.
운영 데이터베이스에 들어갈 때면 몸이 경계 태세가 되고, 내가 실행하는 명령이 조금 어긋났으면 어쩌나,
스테이징 환경이 조금 달랐으면 어쩌나 싶어 재난 직전에 있는 느낌이라는 것이다.
컬럼 타입도 알고 원하는 타입도 아는데 왜 컴파일러가 마이그레이션을 미리 검증해 주지 않느냐고
반문한다.

친절한 오류 메시지 — Elm의 오류 메시지에 많은 공을 들였고 Rust 같은 언어의 비슷한 노력에 영감을
주었다며, 데이터베이스 쿼리에서도 그래야 한다고 말한다.

엔드투엔드 타입 — 클라이언트와 서버와 데이터베이스 사이에서 타입을 공유하고 싶고, 테이블 컬럼의
타입을 바꾸면 Elm 코드에서 높은 품질의 오류 메시지를 보고 싶다는 것이다.

### 코드가 어떻게 생겼나

테이블 정의는 이런 형태다.

```elm
type alias Food =
  { id : FoodID
  , name : String
  }

type FoodID = FoodID UInt64

foods : Table Security.Unrestricted Food
foods :=
  Table.table
    { primary = .id
    , security = Security.unrestricted
    , indexes = []
    , constraints = []
    }
```

기본 키와 행 수준 보안 정책, 그리고 강제하고 싶은 인덱스와 제약을 함께 지정한다.
쿼리는 함수형 프로그램처럼 `map`과 `filter`를 쓴다.

```elm
getFood : Cookies -> FoodID -> Transaction String
getFood _ id =
  access foods Security.Unrestricted
    |> filter (\f -> f.id == id)
    |> map .name
    |> select
```

이것이 컴파일 시점에 SQL로 내려간다.

```sql
SELECT f.name FROM "Foods.foods" AS f WHERE f.id = $1
```

생성되는 SQL의 품질에 많이 공을 들였고, Acadia가 실행하는 SQL을 출력하므로 직접 평가해 볼 수 있으며
컴파일러가 여러 최적화를 자동으로 한다고 밝힌다.

더 복잡한 트랜잭션은 “bind” 문법으로 쌓는데 `async`/`await`처럼 동작한다.
예로 든 것은 이 웹사이트의 비밀번호 재설정 흐름이다 — 새 UUID를 만들고 현재 시각을 얻어
`resetSessions` 테이블에 넣는다.

```elm
type EmailSecret = EmailSecret Uuid.Uuid

passwordResetInit : Cookies -> Email -> Purpose -> Transaction EmailSecret
passwordResetInit _ email purpose =
  let
    secret  := Uuid.generate EmailSecret
    created := Time.now

    () :=
      insert resetSessions (EmailInit email)
        { secret = secret
        , email = email
        , created = created
        , purpose = purpose
        }
  in
  Transaction.succeed secret
```

`:=`는 렛 바인딩이며 `Transaction`의 결과를 간결하게 꺼내 준다.
이 `let`의 결과는 모든 단계가 성공해야만 커밋되는 하나의 트랜잭션이고, 그래서 `secret` 같은 값을
여러 곳에서 쓰기가 훨씬 쉽다 — SQL에서 값을 넘기려면 `RETURNING`을 써야 하는 것과 대비된다고
덧붙인다.

현재 Elm과 Haskell 통합을 지원하며 언어를 추가하는 것은 꽤 쉬우니 원하는 언어가 있으면 알려 달라고,
퍼블릭 알파 동안의 피드백을 기준으로 우선순위를 정하겠다고 한다.

### 배경과 다음 단계

2017년에 Elm의 서버 사이드 렌더링 설계를 탐색하다 SQL 테이블과의 타입 불일치 때문에 모든 설계가
불만족스러웠다고 한다 — “데이터가 거기 있다는 것은 아는데 있다고 보장되지는 않는다”는 것이다.
2019년쯤부터 Elm을 쓰는 여러 회사에서 같은 피드백을 들었다 — Elm 코드는 대체로 괜찮은데 주요
엔지니어링 과제는 백엔드 코드에 있다는 것이었다.

2020년에 Tereza와 함께 “저장 프로시저”가 좋은 컴파일 대상일지 탐색하기 시작했다.
초기 설계는 현대적 타입 시스템을 얹은 SQL 문법에 가까웠고 다소 투박했는데, 초안을 본 Tereza가
“`map`과 `filter`가 있는 Elm처럼 생길 줄 알았는데”라고 곧바로 말했다고 한다 — 훨씬 우아한
설계였다는 것이다.

조용히 “대학원생처럼” 작업한 이유로 그것이 불가능할지도 모른다고 믿었다는 점을 든다.
마이그레이션은 어떻게 되는가, 1+N 쿼리는 어떻게 막는가, “재귀 함수 없는 함수형 언어”가 SQL에서 항상
분명한 의미를 가질 것인가, SQLite와 PostgreSQL에서 답이 다르지 않겠는가 같은 물음들이다.
결국 전부 가능했고 설계가 예상보다 훨씬 좋게 나왔다고 적는다.

다음 단계로는 1+N 쿼리를 어떻게 완전히 피하는지, 오래된 클라이언트가 있을 때 테이블 마이그레이션이
어떻게 되는지, ORM의 문제를 어떻게 피하는지(객체가 없다) 같은 주제로 별도 글을 쓸 계획이라고 한다.
퍼블릭 알파인 이유로 아직 추가하거나 개선할 기능이 많다는 점을 들고, 윈도 함수나 커스텀 집계 함수
같은 고급 기능은 최소 기능 제품에 들어가지 못했지만 내부는 그냥 평범한 SQLite이므로 필요하면 언제든
SQL로 내려갈 수 있다고 밝힌다.

마지막에 이렇게 적는다 — Elm의 2012~2014년 이후로 언어 작업에 이만큼 열정을 느껴 본 적이 없다.

## 라이선스

본문에 나오지 않지만 두 커뮤니티 토론에서 가장 큰 쟁점이 된 것이 라이선스다.

Lobste.rs에서 `intarga`가 가장 많은 표를 받은 댓글로 이것이 독점 소프트웨어이고 소스가 공개되지
않았다는 점이 더 눈에 띄게 언급되어야 한다고 지적했다.
유료 라이선스에도 소프트웨어의 수정이 엄격히 금지되며 디컴파일과 디스어셈블과 리버스 엔지니어링과
소스 코드를 유도하려는 시도가 불가하다는 조항이 있고, 구독 기반이라 활성 구독 기간에만 유효하다는
것이다[^intarga].

`callahad`은 라이선스 FAQ에 “결과 데이터베이스는 그냥 평범한 SQLite와 Postgres이므로 사용자는 언제든
Acadia에서 빠져나올 수 있다”는 문장이 있다는 점을 들며 그나마 견딜 만하다고 했고, Evan의 경제적
어려움에 대한 진단에는 크게 공감하지만 독점 도구에 대한 우려도 공유한다며 어려운 균형이라고
적었다[^callahad].

## 분석

### 네 가지 목표 중 세 번째와 네 번째가 이 프로젝트의 정체를 정한다

앞의 두 목표 — 정밀한 타입과 검증된 마이그레이션 — 는 이미 여러 생태계가 답을 갖고 있다.

Lobste.rs에서 `koreth`가 그 점을 짚었다.
jOOQ와 Flyway를 여러 해 써 온 사람으로서 정밀한 타입 매핑과 검증된 마이그레이션이 다른 코드
생태계에서는 기본 사양이 아니라는 것을 보는 것이 늘 좋은 현실 점검이 되며, 자기는 그 두 가지를
걱정해 본 지 오래됐다는 것이다[^koreth].

남는 것은 오류 메시지와 엔드투엔드 타입이다.
그리고 이 둘이 Evan의 이력과 정확히 겹친다 — Elm이 알려진 이유가 오류 메시지 품질이었고, Elm의
가장 큰 불편이 백엔드와의 경계였다.

그러므로 이것은 데이터베이스 프로젝트가 아니라 Elm 프로젝트의 연장이다.
본문의 배경 절이 그것을 그대로 말한다 — 2017년 Elm의 서버 사이드 렌더링을 설계하다 막혔고, 2019년에
Elm 사용 회사들에게서 백엔드가 문제라는 말을 들었다는 것이다.
`honungsburk`가 HN에서 이 글을 “Elm 저자가 만든 PostgreSQL과 SQLite용 새 함수형 쿼리 언어”라고 한
줄로 요약한 것[^honungsburk]이 커뮤니티의 첫인상이었다.

### 컴파일 결과를 출력한다는 선택이 신뢰 전략이다

생성되는 SQL의 품질에 공을 들였고 Acadia가 실행하는 SQL을 출력하니 직접 평가해 보라는 대목이 짧게
지나가지만 중요하다.

SQL을 생성하는 도구가 신뢰를 잃는 지점은 대개 성능이다.
개발자가 쿼리를 읽을 수 없으면 느릴 때 원인을 찾을 수 없고, 원인을 찾을 수 없으면 도구를 버린다.
ORM에 대한 오랜 불신의 상당 부분이 여기서 온다.

출력을 기본 동작으로 둔 것은 그 불신에 대한 답이다.
그리고 예시로 든 변환이 단순하다는 점도 의도적으로 보인다 — `filter`와 `map` 두 줄이
`SELECT ... WHERE ...` 한 줄이 되는 대응은 독자가 머릿속에서 검산할 수 있다.

`let_rec`는 이 구조를 다르게 정리했다.
이것은 `.db` 파일 안에 사는 Elm 같은 언어와, 그 언어를 대상 백엔드의 강타입 데이터베이스 프로시저로
바꾸는 컴파일러의 조합이며, ORM보다는 시맨틱 레이어에 가깝다는 것이다 — 얻는 것은 테이블 정의와
쿼리를 잇는 공유 언어라고 봤다[^let_rec].

### 행 수준 보안을 테이블 타입에 넣은 것이 가장 급진적인 부분이다

테이블 정의 예시에서 눈에 걸리는 것은 `Table Security.Unrestricted Food`라는 타입이다.
보안 정책이 설정이 아니라 타입 파라미터로 들어가 있고, 쿼리에서도 `access foods
Security.Unrestricted`처럼 명시적으로 요구된다.

`gampleman`이 HN에서 이 점을 흥미로운 기능으로 꼽았다.
합타입이 데이터베이스 데이터 모델링에서 오랫동안 빠져 있었으니 환영할 변화이고, 일급으로 강제되는
RLS는 안전과 보안 보장을 확보하는 훌륭한 방법으로 보인다는 것이다[^gampleman].

이 설계가 왜 급진적인지는 기존 방식과 비교하면 드러난다.
PostgreSQL의 RLS는 데이터베이스 쪽 정책이고 애플리케이션 코드는 그것을 모른 채 쿼리를 보낸다.
정책을 잘못 짜면 런타임에 행이 안 나오거나 나오지 말아야 할 행이 나오고, 그 사실을 컴파일 시점에
알 방법이 없다.
Acadia는 그 판정을 타입 검사로 옮긴다.

다만 `gampleman`은 같은 댓글에서 마이그레이션 전략이 합타입의 변종을 제거하는 경우 등에 어떻게
작동할지 분명하지 않다고 덧붙였다[^gampleman].
그리고 그것이 이 글이 다음 글로 미룬 주제 중 하나다.

## 비평

### 이 글에 라이선스가 한 글자도 없다

본문은 목표와 코드와 배경과 다음 단계를 다루고, 다운로드 링크와 문서와 Discord를 안내하며, 감사
인사로 끝난다.
이 소프트웨어가 독점이고 소스가 공개되지 않았으며 구독이 끊기면 라이선스가 만료된다는 사실은 어디에도
없다.

그리고 두 커뮤니티 모두에서 그것이 첫 번째 화제가 됐다.
Lobste.rs에서 최다 득표 댓글이 `intarga`의 지적이었고[^intarga], HN에서도 여러 갈래로 같은 이야기가
나왔다 — `tempaccount420`은 라이선스 FAQ 링크와 함께 이런 것들은 시간이 지나며 바뀌므로 아카이브
링크도 남긴다고 적었다[^tempaccount420].

이 누락이 단순한 편집 실수로 보이지 않는 이유가 있다.
글의 목적은 사람들이 시도해 보게 하는 것이고, 도입 결정에 가장 큰 영향을 주는 정보가 라이선스다.
`gbjcantab`은 Evan이 설계에 매우 사려 깊고 엄청난 노력을 쏟았다는 것을 알지만, 이런 제한적 라이선스의
비공개 소프트웨어를 애플리케이션의 일부로 채택하는 데는 매우 신중하겠다며 특히 Elm의 궤적이라는
맥락에서 그렇다고 적었다[^gbjcantab].

퍼블릭 알파 발표에서 시도를 권하면서 시도의 조건을 말하지 않은 것은, 독자가 스스로 FAQ를 찾아
읽었을 때 신뢰를 잃는 방식이다.

### 기존 도구와 무엇이 다른지를 논증하지 않는다

글은 네 가지 목표를 제시하고 그것을 달성했다고 말하는데, 같은 목표를 이미 달성했다고 주장하는
도구들과의 비교가 없다.

`jeremyjh`가 그 지적을 직접 했다.
특별한 것이 보이지 않으며 Haskell에는 이런 것이 10년 넘게 있었고 Selda가 아마 Acadia에 가장 가까울
것이라며, 주장과 달리 이것이 여러 언어의 ORM 플랫폼과 실질적으로 다르지 않다고 봤다[^jeremyjh].

글이 ORM을 언급하기는 한다 — 다음 글에서 ORM의 문제를 어떻게 피하는지 다루겠다며 “객체가 없다!”고
괄호를 친다.
그러나 괄호 안의 한마디는 논증이 아니다.
ORM의 문제로 지목되는 것들 — 1+N, 누출되는 추상, 성능 예측 불가 — 은 객체 때문이 아니라 매핑
계층이 존재하기 때문에 생기며, Acadia에도 매핑 계층은 있다.

`mike_hearn`의 지적이 그 매핑 계층의 한계를 구체화한다.
스키마를 SQL이 아닌 언어로 정의하면 언제나 하부 데이터베이스가 할 수 있는 것보다 뒤처지며, ORM 같은
프레임워크가 기본 키와 유일성 제약 정도는 정의할 수 있어도 파티셔닝 방식이나 압축 방법이나 더 고급
제약을 정의할 수 있느냐는 것이다[^mike_hearn].

글이 윈도 함수와 커스텀 집계 함수가 빠졌다고 스스로 밝힌 것이 이 지적의 사례다.
그리고 그 대응으로 제시한 것 — 필요하면 SQL로 내려가라 — 은 두 언어를 함께 쓰라는 뜻이며, 그러면
엔드투엔드 타입이라는 네 번째 목표가 그 경계에서 끊긴다.

### “SQL과 공존한다”는 주장이 저장 형식과 충돌한다

`dwohnitmok`이 가장 날카롭다.
데이터베이스를 소유하려는 언어를 경계하며, 특히 “SQL과 공존한다”는 주장이 의심스럽다는 것이다 —
합타입이 커스텀 바이너리 인코딩을 쓰므로 다른 언어에서 상호 운용하기가 어려울 것이고, 그렇다면
주장된 다른 언어와의 상호 운용은 완전한 Acadia로 가는 임시 정거장에 가깝다는
것이다[^dwohnitmok].

이 지적이 정확한 이유는 첫 번째 목표와 라이선스 FAQ의 탈출 조항이 서로를 잠식하기 때문이다.
첫 번째 목표는 정밀한 커스텀 타입을 데이터베이스에 저장하는 것이고, 탈출 조항은 결과 데이터베이스가
평범한 SQLite와 Postgres이니 언제든 나갈 수 있다는 것이다.

둘 다 참일 수는 있다 — 파일 포맷은 표준이니까.
그러나 그 안의 합타입 컬럼이 Acadia의 인코딩 규칙으로만 해석된다면, 나간 뒤에 남는 것은 읽을 수 있는
바이트이지 읽을 수 있는 데이터가 아니다.
`eeue56`이 전 Elm 코어 팀원으로서 데이터베이스 자체가 있으니 언제든 빠져나올 수 있다 해도 코드가
결정적이라고 지적한 것[^eeue56]이 같은 자리를 가리킨다.

이 문제는 문서로 해소할 수 있다 — 인코딩 규칙을 공개 사양으로 내놓으면 된다.
그런데 라이선스가 리버스 엔지니어링을 금지하고 있으므로 공개하지 않는 한 알아낼 방법이 없다.

### 자금 조달 문제를 라이선스로 푼 것이 이 프로젝트의 최대 리스크다

Evan이 본문에서 언급한 두 편의 글 — 프로그래밍 언어의 경제학과 채택 전략 재고 — 은 그가 오랫동안
씨름해 온 문제를 가리킨다.
Elm은 널리 쓰였지만 그 채택이 개발 자금으로 이어지지 않았다.

`happyraul`이 그 맥락을 옹호로 썼다.
Elm에서는 채택과 개발 자금 사이에 아무 상관관계가 없었는데 Acadia에서는 다른 자금 모델을 시도하고
있으니 Acadia와 Elm 양쪽에 더 나은 지원을 뜻할 수도 있다는 것이다[^happyraul].
`bbkane`은 새 자금 모델이 가장 기대된다며, 자기는 직장에서 Acadia를 쓸 수 없고 개인 프로젝트에 쓸
위험 감수 성향도 없지만 이 모델이 생계를 해결하는지 보고 싶다고 적었다 — 더 관대한 라이선스의
코드와 경쟁할 수 있겠느냐는 것이다[^bbkane].
`skatkov`은 반대편에서 물었다 — 개인 정보를 파는 회사나 끔찍한 광고의 지원을 받고 싶지 않은 독립
창작자의 작업을 가능하게 할 다른 방법이 무엇이 있느냐는 것이다[^skatkov].

문제는 선택한 형태다.
`hwj`는 JetBrains를 좋아하지는 않지만 영구 폴백 라이선스는 마음에 든다며, 구독이 끝나도 특정 버전을
무기한 쓸 수 있고 새 버전으로 올리려면 갱신이 필요한 방식을 들었다[^hwj].
그것이 존재한다는 사실이 지금 라이선스의 엄격함을 선택으로 만든다.

`intarga`가 이 노선의 종착점을 그렸다.
이 길의 끝이 독립 도구 제작자가 잘 지원되는 세상은 아닐 것이며, 이것을 정상화하면 고용주가 Oracle과
계약했다는 이유로 어떤 데이터베이스 드라이버를 쓸지 고르지 못하게 되고, 프로그래머는 업무 밖에서
자기 기술을 쓸 능력을 잃게 되는데 Oracle이 합리적 개인 사용에 예외를 두지 않기 때문이라는
것이다[^intarga-oracle].
그리고 지금 Acadia를 “400년 된 칼 대장간 가업”에 비유하는 것이 솔직하지 않다고 덧붙였다 — 칼 대장간이
칼을 산 뒤 개조를 금지하거나 돈을 계속 내지 않으면 칼을 회수하지는 않으며, 그것은 오히려 “현대 거대
기술 기업”에 가깝다는 것이다[^intarga-knife].

## 인사이트

### 데이터베이스를 소유하지 않으면서 타입을 소유하는 것은 불가능에 가깝다

이 프로젝트가 약속한 것 중 가장 매력적인 것은 합타입을 테이블에 그대로 저장하는 것이다.
그리고 그 약속이 지켜지는 순간 데이터베이스는 더 이상 중립적 저장소가 아니게 된다.

SQL 타입이 빈약한 것은 결함이면서 동시에 성질이다.
`INTEGER`와 `TEXT`와 `TIMESTAMP`만 있으면 어떤 언어에서도 같은 방식으로 읽히고, 그 최소 공통 분모가
데이터베이스를 여러 시스템의 접점으로 만든다.
분석 도구와 백업 스크립트와 다른 팀의 서비스가 같은 테이블을 읽을 수 있는 이유가 그것이다.

합타입을 저장하려면 그 최소 공통 분모를 벗어나야 하고, 벗어나는 순간 그 컬럼의 의미를 아는 것은
Acadia 컴파일러뿐이다.
`dwohnitmok`이 지적한 상호 운용 문제[^dwohnitmok]가 버그가 아니라 설계의 필연인 이유다.

여기서 나오는 일반적 교훈이 있다.
데이터베이스 위에 타입을 얹는 도구는 언제나 두 진영 중 하나를 골라야 한다 — 타입을 애플리케이션
경계에서만 유지하고 저장은 표준 형식으로 하거나(jOOQ, 대부분의 ORM), 저장까지 타입을 밀어 넣고 그
데이터의 유일한 해석자가 되거나.
전자는 표현력을 잃고 후자는 개방성을 잃으며, 중간은 없다.

Acadia는 후자를 골랐고 그 대가를 라이선스로 한 번 더 키웠다.
인코딩 사양이 공개되지 않은 채로 저장 형식을 소유하면, 데이터베이스 파일이 표준이라는 사실이 위안이
되지 못한다.

### 이 프로젝트의 진짜 실험은 언어가 아니라 자금 모델이다

HN과 Lobste.rs 두 스레드의 상위 댓글을 세면 기술보다 라이선스에 대한 이야기가 많다.
그리고 그것이 이 발표의 성격을 드러낸다.

Evan은 Elm으로 이미 기술적 성취를 증명했고, 그 성취가 지속 가능한 생계로 이어지지 않는다는 것도
증명했다.
Acadia는 그 두 번째 문제에 대한 시도이며, 그가 인용한 두 편의 글이 그 시도의 이론적 배경이다.

그래서 이 프로젝트의 결과를 판단할 지표가 둘로 나뉜다.
언어로서 성공했는지는 몇 년 뒤 사용 사례로 알 수 있고, 실험으로서 성공했는지는 훨씬 빨리 알 수
있다 — 구독 수익이 두 사람의 전업을 지탱하는가다.
`bbkane`이 가장 기대되는 것이 자금 모델이라고 한 것[^bbkane]이 그 관전 포인트를 정확히 짚었다.

그리고 이 실험에는 관찰자에게도 값이 있다.
독립 언어 제작자의 생계 문제는 오래된 것이고, 오픈소스 라이선스와 스폰서십과 컨설팅과 클라우드
호스팅이 차례로 시도됐으며 대부분 충분하지 않았다.
구독형 독점 컴파일러는 그중 시도된 적이 거의 없는 형태다.

다만 표본이 특수하다는 점을 짚어야 한다.
Evan에게는 Elm으로 쌓은 이름이 있고 그 이름이 유료 알파에 사람을 모은다.
이름이 없는 제작자가 같은 모델을 쓰면 어떻게 되는지는 이 실험이 답하지 못하며, 그렇다면 이것은
자금 모델의 검증이 아니라 특정 개인의 브랜드 가치 측정일 수 있다.

### 데이터베이스 도구에서 개방성은 기능이 아니라 보험이다

`eeue56`의 지적이 기업 도입의 실제 논리를 보여 준다.
전 Elm 코어 팀원으로서 이 시도가 어디서 나왔는지 이해하지만, 무료 대안이 많은데 구독형 컴파일러에
의존하는 것은 많은 회사에서 시작조차 불가능하며, 데이터베이스 자체는 갖고 있어서 언제든 빠져나올 수
있다 해도 코드가 결정적이므로 자원 측면에서도 법적으로도 벤더 종속의 위험이 높다는
것이다[^eeue56].

여기서 “코드가 결정적”이라는 부분이 핵심이다.
데이터를 꺼낼 수 있다는 것과 시스템을 계속 돌릴 수 있다는 것은 다르다.
Acadia로 쓴 엔드포인트 정의는 Acadia 컴파일러 없이 빌드되지 않으며, 구독이 끊기면 배포가 멈춘다.

이 위험의 성격이 일반 라이브러리와 다르다.
라이브러리는 포크하거나 벤더링하거나 최악의 경우 대체 구현을 쓸 수 있지만, 컴파일러는 그럴 수 없고
특히 리버스 엔지니어링이 금지되어 있으면 더 그렇다.
`intarga`가 인용한 수정 금지 조항[^intarga]이 그 차이를 만든다.

그래서 데이터베이스 계층 도구에서 오픈소스가 갖는 값은 커뮤니티 기여가 아니라 보험이다.
회사가 오픈소스를 고르는 이유의 상당 부분은 소스를 읽거나 고치기 위해서가 아니라, 공급자가 사라져도
계속 돌릴 수 있다는 사실 때문이다.
[Gitea에서 Forgejo로의 포크](../git/forgejo.md)가 코드가 거의 같은 상태에서도 일어난 이유가 같은
계산이었다.

Acadia의 FAQ가 제시한 탈출 경로 — 데이터베이스는 표준이니 언제든 나갈 수 있다 — 는 이 보험의 절반만
제공한다.
데이터는 남고 시스템은 남지 않으며, 실제 운영에서 문제가 되는 것은 후자다.
