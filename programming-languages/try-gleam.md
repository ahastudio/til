# Rust 사용자라면 Gleam을 써 볼 만하다: 단순한 함수형 문법에 BEAM의 동시성을 얹은 언어

원문: [You should try Gleam](https://nchagnet.eu/blog/you-should-try-gleam)

HN 토론: <https://news.ycombinator.com/item?id=50424366> (144점, 137개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/4yqgpu/you_should_try_gleam>

GN 토론: <https://news.hada.io/topic?id=36975>

## 요약

nchagnet은 Rust를 취미 프로젝트의 주력 언어로 써 왔는데, 최근 Gleam도 같은
즐거움을 준다고 말하며 글을 시작한다.
Gleam은 Erlang 가상 머신인 BEAM을 대상으로 하는 함수형 언어이고, JavaScript로도
컴파일된다.
글쓴이는 Rust에 익숙하다면 Gleam이 친숙할 것이며 자신이 쓰는 코드의 80%는 문법만
바꾸면 Rust로 컴파일될 것 같다고 느낀다고 적는다.
언어 전체를 소개하는 글은 아니라며 공식 대화형 투어를 권한다.

글은 Gleam의 홈페이지 문구인 “타입이 안전하고 확장되는 시스템을 만드는 친근한
언어”를 따라 좋은 점을 구성한다.

- **친근하다:** 문법이 아주 단순하고 변수는 변하지 않는다.
파이프 연산자 `|>`로 함수를 이어 붙이는데, 파이프로 넘기는 값은 첫 번째 인자가
  되어야 한다.
Rust처럼 오류는 `Result` 값이다.
Gleam의 타입에는 메서드가 없어서 메서드 체인 대신 파이프를 쓴다.
- **`use` 패턴:** 콜백을 마지막 인자로 받는 함수에서 `use param <-
  some_func(arg)` 한 줄로 콜백 들여쓰기가 겹겹이 쌓이는 것을 피한다.
파이프가 첫 인자를 채우는 것과 반대로 마지막 인자를 채운다.
- **꼬리 호출 최적화:** Gleam에는 반복문이 없고, 대부분의 반복은 리스트 순회
  함수로 하고 나머지는 재귀로 한다.
재귀 호출이 마지막 동작이면 스택 프레임을 재사용해 반복문에 가까운 성능이 난다.
글쓴이는 “98%의 경우”라는 수치가 지어낸 것이라고 각주로 밝힌다.
- **타입 안전:** Elixir가 아니라 Gleam을 쓰는 이유다.
Gleam의 타입은 Rust의 enum과 struct를 합친 대수적 데이터 타입이라 불가능한
  상태를 막을 수 있고, BEAM과 JavaScript 양쪽으로 컴파일되므로 웹 앱과 BEAM 앱이
  같은 타입 정의를 공유한다.
- **확장되는 시스템:** BEAM의 프로세스로 동시성을 다루는 두 예제를 보인다.
하나는 `process.spawn_unlinked`로 주문 처리 프로세스를 띄워 하나가 죽어도 부모와
  형제가 영향을 받지 않는 예이고, 다른 하나는 `Subject`로 메시지를 주고받는
  예다.
글쓴이는 첫 예제의 `process.sleep(10)`이 자식 프로세스를 기다리는
  임시방편(hack)이라고 직접 인정한다.

OTP(Open Telecom Platform) 절에서 글쓴이는 상태를 가진 가벼운 프로세스인 액터와,
죽은 액터를 다시 띄우는 감독자(supervisor)가 Kubernetes의 컨트롤러와 파드 구조와
비슷하다고 설명한다.
자기 팀이 Go로 직접 만든 작업 스케줄러, 워커, Node.js UI를 파드로 나누어
운영하는데, 이를 하나의 Gleam 애플리케이션으로 합치면 중복된 REST API를 줄일 수
있다고 구상한다.
이때 UI도 Gleam으로 써서 JavaScript로 컴파일하고, `Job` 같은 타입을 프런트엔드와
서버가 공유하는 코드 예를 든다.

“나쁜 점”으로는 세 가지를 꼽는다.
생태계가 작고(Gleam이 2016년에 만들어졌지만 1.0.0은 2024년이라는 각주를 단다),
언어가 너무 단순하다는 비판(매크로나 커링 같은 복잡한 기능이 없는 점)이 있으며,
BEAM이 특이한 대상이어서 Rust의 Mozilla나 Go의 Google처럼 밀어주는 대기업이
없다는 것이다.
글쓴이는 단순함은 자신이 좋아하는 점이라며 동의하지 않는다고 하고, 경험이 적어
편향된 평가이며 열광이 식은 뒤에 보일 결점을 놓쳤을 것이라고 덧붙인다.

## 분석

### 글의 논거는 “이식성이 아니라 이미 아는 것과의 닮음”이다

글은 Rust 사용자를 독자로 삼고, Rust 코드와 Gleam 코드를 나란히 놓는 방식으로
진행한다.
같은 일을 하는 문자열 파싱, `gcd`, enum 정의가 서로 대응한다는 점이 “친근하다”는
주장을 받친다.
이 논거가 말해 주는 것은 Gleam의 단순함이 Rust의 함수형 부분집합을 아는 사람에게
편하다는 것이지, 함수형 경험이 없는 사람에게도 쉽다는 것은 아니다.
글쓴이도 C 계열 명령형 세계에서 살아온 사람에게는 처음에 부담스러울 수 있다고
인정한다.
HN에서 isodev는 거대해진 현대 Swift를 쓰는 중이라 Gleam이 신선한 공기 같다고
썼고,[^isodev] 이는 닮음이 아니라 언어가 작다는 점에서 오는 편안함을 가리킨다.

### 이 언어의 값어치는 동시성보다 타입을 공유하는 데서 나온다

글의 가장 구체적인 설계 주장은 BEAM과 JavaScript 양쪽으로 컴파일되는 타입을
서버와 UI가 공유한다는 것이다.
HN의 subarctic은 프런트엔드와 백엔드 모두를 Gleam으로 쓰는 웹 앱을 꾸준히
개발하고 있으며, 코드를 공유하기 쉽고 TypeScript 전체 스택처럼 설정을 많이
맞추지 않아도 된다고 했다.[^subarctic]
다만 subarctic은 코드를 대부분 Claude가 쓰고 있고 직접 쓴다면 보일러플레이트가
꽤 있을 것이라고 덧붙였다.
이 증언은 글쓴이의 주장을 실제로 쓰는 사람의 경험으로 받쳐 주되, 그 사람이 직접
타이핑하지 않는다는 점에서 언어의 인체공학에 대한 근거는 아니다.

## 비평

### 감독자를 말하지만 보여 주는 코드에는 감독자가 없다

OTP 절의 핵심 주장은 감독자가 죽은 액터를 다시 띄워서 애플리케이션이 개별 액터의
고장에 견디게 만든다는 것이다.
그러나 글의 동시성 예제는 `process.spawn_unlinked`와 `Subject` 메시지 전달만
보여 주고, 감독자 트리나 재시작 전략은 보여 주지 않는다.
앞의 예제는 작업이 죽으면 그냥 사라지고, 글쓴이 스스로 `sleep(10)`이
임시방편이라고 적는다.
Kubernetes 대체 구상의 핵심이 감독자인데 그 부분은 설명만 있고 코드로 확인되지
않는다.
각주 6은 OTP에는 클러스터 스케줄러와 배치와 컨테이너 격리가 없어서 노드를 직접
배포하고 배치해야 한다고 인정한다.
이 각주는 본문의 “OTP가 Kubernetes의 흔한 대안”이라는 인상을 깎는 중요한
조건인데 각주에 묻혀 있다.

### 대안 구상의 근거는 글쓴이 팀 한 곳의 사례다

글쓴이는 자기 팀의 Go 스케줄러와 파드 구성을 Gleam 하나로 합친다는 구상을
들면서, 많은 Kubernetes 사용이 클러스터를 필요로 하지 않으며 비싸다고 말한다.
그러나 이 구상이 실제로 구현되었는지, 장애와 배포, 관측 가능성에서 어떤 대가가
있는지는 글에 없다.
주장은 설계 스케치이고 경험담이 아니다.
글쓴이는 자신이 언어 경험이 적다고 스스로 밝혔으므로, 이 구상은 시도해 볼 가설로
읽어야 한다.

### 커링 부재는 글이 가볍게 다룬 문제다

글은 “나쁜 점”에서 매크로나 커링 같은 복잡한 기능이 없다는 것을 “단순함을
좋아하는” 쪽으로 정리해 버린다.
그러나 HN에서 기술적으로 가장 길게 이어진 논쟁이 이것이었다.
adamddev1은 Gleam이 아주 즐거운 언어인데 커링이 없는 것이 비극이며 함수형
세계에서 한쪽 다리가 잘린 기분이라고 했다.[^adamddev1]
stiiv는 파이프 연산자와 함께 쓰는 것이 커링의 가장 큰 쓸모라며 이것이 결정적인
단점이라고 했다.[^stiiv]
반대로 kaoD는 커링이 읽기 어렵고 타입 오류도 따라가기 어려우며 인자 순서가
고정되어 융통성이 없다고 보고 부분 적용을 “슬롯”으로 하는 방식을 물었다.[^kaoD]
yladiz는 한 칸만 비워 두는 방식이 인자를 첫 번째나 마지막으로 넘기는 스레딩보다
낫고 커링보다 추론하기 쉬워서 좋은 절충이라고 답했다.[^yladiz]
논쟁은 취향 싸움처럼 보이지만 파이프라인 중심 언어에서 부분 적용이 어떻게
표현되는가라는 설계 질문이라서, 글이 이를 단순함이라는 하나의 이점으로 접은 것은
독자가 판단할 재료를 줄인다.

### 매크로와 트레이트가 없는 것은 결함이 아니라 의도적 선택이고, 비용은 도구가 진다

글은 “언어가 너무 단순하다”는 비판에 자신은 동의하지 않는다고만 적고, 무엇이
어떻게 대신되는지는 설명하지 않는다.
Lobste.rs의 gavinmorrow는 Rust에서 넘어왔고, 한동안 Gleam만 쓰다 돌아가니 다른
언어가 신경 쓰게 하는 무관한 것이 많다는 사실을 잊었던 것을 깨달았다며 방법이
하나뿐인 점이 가독성을 높인다고 썼다.[^gavinmorrow]
이에 rprospero는 매크로 없이는 풀 수 없는 용도가 아직 없다는 논리가 자기실현적
예언처럼 느껴지고, 직렬화와 역직렬화가 특히 걸린다고 반박했다.[^rprospero]
lpil은 언어 서버의 원클릭 생성 기능이 직접 쓸 작은 함수를 만들어 주는 방식이며
다른 아이디어에도 열려 있다고 답했고,[^lpil-gen] krig는 디코더와 JSON 인코더
생성기가 언어 서버에 내장되어 있어서 코드 생성기를 쓰라는 말이 생각만큼
불친절하지 않다고 보충했다.[^krig]
pushcx는 Gleam이 트레이트나 서브클래스에 가까운 것, 또는 리플렉션이나 매크로나
코드 생성 쪽을 일부러 두지 않았다는 이야기가 자주 나온다고 정리했다.[^pushcx]
이는 글의 “나쁜 점”을 “단순함은 장점”으로 접는 것보다 더 구체적인 쟁점이다.
단순함의 비용이 언어가 아니라 편집기 도구로 이전되었다는 뜻이고, 도구 지원이
없는 환경이나 생성된 코드를 사람이 읽고 유지해야 하는 상황에서는 같은 비용이
다시 드러날 수 있다.

### 생태계와 상호 운용의 한계가 “작다”는 한마디보다 구체적이다

글은 생태계가 작은 것을 어린 언어의 당연한 결과로 보고 외부 함수 호출로
보완된다고 한다.
HN에서 whalesalad는 Elixir 라이브러리와 쓰는 것이 처음부터 일급 기능이 아니라는
점이 언어 선택을 의심하게 한다며 Clojure와 Java의 관계를 비교했다.[^whalesalad]
Ndymium은 Elixir를 Gleam에서 쓰는 쪽은 외부 함수 하나로 쉽지만 Gleam을 Elixir
프로젝트에서 쓰는 쪽은 `mix_gleam`에 의존하고, Elixir에 Gleam 지원을 넣는 풀
리퀘스트는 아직 병합되지 않았다고 정리했다.[^Ndymium]
이 정리는 글의 “외부 함수로 쉽다”가 한 방향에서만 맞는다는 뜻이다.
이 두 댓글은 각각 사용자의 경험과 설명이며 현재 상태는 확인이 필요하다.

### 커뮤니티 논쟁은 글이 다루지 않은 선택 요인이다

글은 “나쁜 점”에 커뮤니티의 분위기를 포함하지 않았다.
HN에서 hmokiguess는 이 커뮤니티에 활동가적 태도의 이력이 있어서 떠난다고 하면서
작은 생태계라는 글의 지적에 덧붙였고,[^hmokiguess] 글쓴이는 어떤 종류인지
몰랐다며 되물었다.[^nchagnet-ask]
이어 행동 강령(code of conduct)을 둘러싼 긴 논쟁이 이어졌는데, surgical_fire는
언어를 쓰는 데 행동 강령을 따를 필요가 없다고 했고,[^surgical_fire] F3nd0는 공식
사이트가 아주 친근하게 보이려 하다가 곧바로 그 인상을 깬다는 점이 거슬린다고
했다.[^F3nd0]
이 논쟁은 언어의 기술적 장단점이 아니라 커뮤니티 취향에 관한 것이어서 이 문서는
어느 쪽이 옳은지 판단하지 않는다.
다만 도입을 고려하는 팀에는 사람이 고려 요소가 된다는 것을 보여 주는 사례다.

## 인사이트

### AI가 코드를 쓰는 시대에 언어의 인체공학은 다시 평가받는다

HN에서 mono442는 AI가 코드를 전부 쓴다면 더 대중적인 언어가 낫지 않냐고
물었다.[^mono442]
lpil은 프로그래밍 모델이 이미 특정 언어에 묶이지 않을 만큼 발전했고, 이는 특정
언어를 아는 초급 개발자와 일반적인 프로그래밍을 아는 중급 개발자의 차이와 같다고
답했다.[^lpil]
sczi는 덜 알려진 언어가 더 쉬운 문제를 받았다는 점을 들어 Elixir 쪽이 인용하는
연구가 주장을 받쳐 주지 못하고, 오히려 OpenAI의 SQLite 재구현 비교는 Python,
JavaScript, Java, C# 같은 인기 언어가 가장 잘하는 쪽으로 나왔다고 썼다.[^sczi]
ModernMech는 이에 맞서 대중 언어는 모든 면에서 최악을 타협한 결과이고, 네트워크
효과가 약해지면 비주류 언어의 이점을 취할 수 있다고 했다.[^ModernMech]
이 논쟁에서 확인된 것은 결론이 아니라 증거가 양쪽 모두 약하다는 점이다.
이 문서가 얻는 시사점은, Gleam을 도입하는 근거가 AI가 잘 쓴다는 것이면 먼저 자기
작업으로 측정하라는 것이다.
이는 이 문서의 제안이다.

### 반복자가 없는 선택은 파이프라인 중심 설계와 맞물려 있다

글은 Gleam에 반복문이 없다고 하면서 리스트를 순회하는 함수들로 대신한다고
설명한다.
Lobste.rs의 hawski는 Python의 반복자(iterator)를 좋아한다며 파이프라인 연산자와
어떻게 함께 쓸지 물었다.[^hawski]
lpil은 파이프라인에 반복자를 쓸 수는 있지만 반복자는 컴파일 모델이 실행 시점에
최적화로 없애 주지 않으면 아주 느려서 Gleam에서는 흔히 쓰지 않는다고
답했다.[^lpil-iter]
이 답은 언어의 단순함이 취향이 아니라 BEAM 위에서의 성능 판단에 기대고 있다는
단서다.

### 작은 언어의 “깔끔함”은 도구가 메운 틈 위에서 유지된다

HN 스레드에서 글쓴이는 도구가 꽤 완성도 있고 언어 서버가 작은 프로젝트로는
품질이 높다고 쓰면서, 테스트 하나만 실행하는 방법을 아직 못 찾았다고
한다.[^nchagnet-tooling]
이 사소해 보이는 틈은 작은 언어의 결점이 눈에 띄지 않다가 일상 작업에서 하나씩
드러나는 방식을 보여 준다.
글이 언급한 “열광이 식은 뒤”의 결점은 대개 이런 일상의 마찰이다.
언어를 평가할 때 문법 비교만이 아니라 테스트 실행, 디버깅, 배포를 한 번 끝까지
해 보는 것이 더 정직한 시험이다.

### 결론을 바꿀 관찰

- 글의 Kubernetes 대체 구상이 실제 서비스로 구현되어 감독자 재시작과 관측과 배포
  비용이 보고된다면, “OTP가 흔한 대안”이라는 인상이 근거를 얻는다.
- Elixir 쪽의 Gleam 내장 지원이 병합되어 양방향 상호 운용이 일급이 되면,
  생태계가 작다는 약점이 줄어든다.
- 커링이나 부분 적용 구문이 Gleam에 들어가거나 한 칸 비우기 방식이 불편하다는
  보고가 쌓이면, 단순함을 장점으로 삼는 글의 평가가 달라진다.
