# Goose: 힙 없이 데이터 스택만 쓰는 메모리 안전 시스템 언어

<https://aardappel.github.io/goose/>

<https://github.com/aardappel/goose>

HN 토론: <https://news.ycombinator.com/item?id=50224100> (304점, 187개 댓글)

GN 토론: <https://news.hada.io/topic?id=35942>

## 소개

Goose는 힙 할당기, 가비지 컬렉터, 수명 표기(lifetime annotation)가 없는 메모리
안전 시스템 언어다.
Wouter van Oortmerssen이 언어와 컴파일러를 설계했고, 컴파일러 구현과 벤치마크,
예제와 문서 작성은 Claude Fable이 맡았다고 페이지의 저자란에 적혀 있다.
Goose는 C로 컴파일되며 라이선스는 Apache 2.0이다.
페이지는 이 저장소의 벤치마크에서 Goose가 C++와 Rust보다 빠르고 메모리도 적게
쓴다고 주장한다.
그 수치는 저자 자신의 측정이다.

문법은 C와 Rust 프로그래머에게 익숙한 모양이지만 힙이 없다.
모든 동적 값은 컴파일러가 관리하는 데이터 스택에 인라인으로 놓인다.
커지면 포인터만 앞으로 옮기고, 스코프가 끝나면 메모리가 해제된다.
상태는 아직 새 프로젝트다.
컴파일러는 C++ 3만 줄쯤이고, 명세와 표준 라이브러리, 예제 31개, Windows와
macOS와 Linux에서 도는 테스트 모음이 있다.
이동(move) 의미론, 구조체 하나에 크기가 변하는 필드 여러 개, 이름 붙은 break는
일부러 범위 밖에 두었다.

## 동작 방식

### 하나의 메모리 모델은 스택과 스코프 끝의 해제다

프로그램은 네이티브 호출 스택, 정적 데이터, 그리고 컴파일러가 개수 N을 정하는
데이터 스택들로 이루어진다.
데이터 스택은 주소 공간을 크게 예약해 둔 영역과 증가용 포인터(bump pointer)다.
스택마다 크기가 변하는 값은 한 번에 하나만 살아 있고 항상 맨 위에 있으므로,
커져도 아무것도 옮겨지지 않고 용량 검사도 없다.
이 보장은 컴파일 시점에 증명되고, 실행 시점에는 포인터 위치만 추적한다.
스택 하나는 기본적으로 2GB의 주소 공간을 예약하고 쓰는 만큼만 실제로 확보한다.

```text
for round in 3 {
    var scratch: u8[>..] = [];        // 늘기만 하는 배열: 성장은 포인터 증가
    ...
}                                     // 해제: 스택 꼭대기에 값 하나 쓰기
```

위 코드는 페이지 예제를 줄인 것이며, 해제가 값 하나를 쓰는 일이라는 점을 보여
준다.
백만 개짜리 구조를 해제하는 비용도 중첩 깊이와 무관하게 같다고 페이지는 말한다.

### 성장해도 참조가 유지된다

아무것도 옮겨지지 않으므로 늘어나는 배열 안의 원소를 가리키는 참조는 배열이 사는
동안 유효하다.
`push`는 새 원소의 참조를 돌려주어 원소를 만들면서 서로 연결할 수 있다.
C++의 `vector`나 Rust의 `Vec`은 재할당할 수 있어 같은 보장을 못 준다는 것이
페이지의 설명이다.
작성자는 HN에서 이 설계가 64비트 주소 공간 덕분에 실용적이라고 설명했다.
거의 모든 현행 언어는 32비트의 제약을 염두에 두고 설계됐고, 배열마다 큰 주소
공간을 줄 수 있으면 재할당이 필요 없어 안정된 포인터와 다른 기능이 따라온다는
것이다.[^Aardappel-address]

### 참조의 안전은 표기 없이 컴파일러가 뿌리를 추적해서 얻는다

모든 참조와 슬라이스는 정적인 뿌리, 곧 대상의 수명을 정하는 변수를 가진다.
컴파일러가 뿌리를 추론하고 함수를 뿌리별로 특수화하므로 수명 표기가 없다.
별칭이나 배타성 규칙도, `unsafe`도 없다.
수명 검사가 실패하면 오류 메시지가 참조의 뿌리와 도착 지점을 이름으로 알려 준다.
작성자는 `unsafe` 기능과 정의되지 않은 동작이 없고 완전히 메모리 안전하다고
답했다.[^Aardappel-unsafe]

### 중첩 데이터는 포인터 없이 한 덩어리에 놓인다

배열 종류는 하나가 아니라 크기가 어떻게 되는지만 다른 가족이다.
고정 크기, 만들 때 정해지고 이후 고정, 용량 안에서 늘고 줄기, 늘기만
하기(`T[>..]`, 기본 일꾼), 늘고 줄기(스택, 큐, 힙용)가 있다.
문자열은 `u8` 배열이고, 크기가 변하는 필드를 가진 구조체도 필드가 선언 순서대로
인라인으로 놓인다.
주문 하나(고객 이름과 주문 항목 둘)가 페이지의 예에서 29바이트에 할당 0회이고,
같은 것을 C++로 만들면 160바이트에 1회, Rust로 만들면 153바이트에 4회라고 한다.
대가는 크기가 변하는 원소의 배열이 순차 접근만 된다는 것이다.
순회는 되지만 인덱싱은 안 되고, 인덱싱이 필요하면 참조 배열을 따로 둔다.

### 열거형은 두 가지 크기로 저장된다

대수적 데이터 타입(ADT)이 유일한 동적 다형성이고 상속과 vtable은 없다.
고정 모드는 가장 큰 변형에 맞춰 태그와 공간을 잡고, 인덱싱과 덮어쓰기가 된다.
가변 모드는 값마다 자기 변형의 크기만 차지하며, 배열은 순차 접근이 되고 값은
변형을 바꾸지 못하는 대신 페이로드 참조를 얻을 수 있다.
페이지는 이 모드가 Rust의 enum 대비 메모리 4분의 1, 속도 2배를 낸 벤치마크가
있다고 한다.

### 포인터보다 좁은 상대 링크와 파일 형식으로서의 데이터

`T&`는 8바이트 기계 주소이고 절대 dangling이 되지 않는다.
상대 참조 `T&<u32>`는 필드 자신에서 같은 배열 안 대상까지의 오프셋을 1, 2,
4바이트로 저장한 링크다.
그래서 구조가 위치와 무관하고, 저장은 바이트를 쓰는 일이고 불러오기는 읽은 뒤
검증하는 일이 된다.
`from_bytes`는 틀, 태그, 길이, 링크를 모두 검사하므로 손상되거나 악의적인 파일은
잘못된 참조가 아니라 `false`가 된다.
HN에서 한 댓글이 인용한 John Carmack의 평은 이 부분에 주목했다.
여러 데이터 스택과 크기 변하는 필드의 자동 분석이 많은 일을 이 방식으로 하게 해
주고, 상대 참조와 내장 이진 구조 검증 덕에 파일과 네트워크 데이터를 메모리에
바로 매핑해 쓸 수 있다는 내용이다.[^bobbydigitales]

### 제자리 생성, 여러 프레임 위로 오류 반환, 공유 없는 스레드

값은 최종 위치에서 만들어지며 호출 깊이와 무관하게 위쪽에서 아래로 전달된다.
그래서 `items.push(parse(line))`는 파싱한 레코드를 배열에 바로 쓰고, 증가 배열을
값으로 반환하는 일도 비용이 없다.
`return err from load`는 함수 `load`의 가장 안쪽 활성 호출의 결과로 오류를
돌려주며, 사이 함수의 시그니처는 평범한 채로 남는다.
정적으로 검사되고 unwinder도 `Result` 타입도 필요 없다.
스레드는 각 작업자를 별도 프로그램처럼 자기 메모리를 가진 채 컴파일하고, 값은
타입별 큐를 통해 `memcpy`로 건넨다.
작성자는 복사는 런타임이 하며 그 아래에서는 원자 연산을 쓰지만 사용자는 직접
쓰지 않고, 모델은 단일 프로세스 다중 스레드라고 설명했다.[^Aardappel-threads]

### 제네릭과 함수 블록, 그리고 C

타입을 쓰지 않은 매개변수는 제네릭이다.
함수 값은 컴파일 시점의 개체이므로 `xs.filter() { it > 0 }`는 보이는 그대로의
루프로 컴파일된다.
컴파일러는 C 파일 하나를 내놓고, `extern fn`으로 C를 직접 부른다.
번들된 TinyCC 백엔드는 프로세스 안에서 컴파일하고 실행한다.
작성자는 출시용 빌드는 최적화 C 컴파일러를 거치므로 컴파일 속도에 한계가 있고,
개발 중에는 libtcc 기반 JIT를 쓸 수 있으며 대신 실행이 3배쯤 느리다고
했다.[^Aardappel-jit]

## 함정

### 값이 어디에 사는지를 프로그래머가 정해야 한다

페이지가 직접 꼽는 비용은 이렇다.
누가 이 데이터를 갖고 스코프가 얼마나 가는지 생각해야 한다.
재귀 함수는 재귀 호출 너머로 증가하는 데이터를 들고 갈 수 없고, 호출 뒤까지
살아남는 데이터는 풀(pool)로 넘겨야 한다.
크기 변하는 원소의 배열은 인덱싱이 안 되고, 고정 모드 enum은 안을 가리킬 수
없고, 가변 모드 enum은 덮어쓸 수 없다.
이스케이프하는 클로저, 함수 포인터, ADT 태그 이상의 동적 디스패치도 없고
컴파일은 프로그램 전체 단위다.
풀에 돌려준 슬롯을 계속 이름으로 쓰면 다음 소유자가 넣은 값이 읽히는데, 논리
오류일 뿐 메모리 손상은 아니라고 한다.

### 무한히 커지는 구조와 임의 순서의 삭제가 어렵다

HN에서 malisper는 크기가 변하는 값을 임의 개수만큼 표현하는 방법을 물으며, 값이
문자열인 해시 테이블에서 무작위로 삽입과 삭제를 하는 경우를 예로
들었다.[^malisper]
작성자는 수명이 비슷한 것끼리 배열에 모으는 구조에서 이득이 가장 크고, 스택
순서가 아닌 임의 삭제가 필요하면 용량 있는 고정 배열이나 풀을 쓴다고
답했다.[^Aardappel-pools]
pradn은 가비지 컬렉션이 없으니 오래된 데이터가 쓸모없어져도 스택이 계속 커질 수
있다고 짚었다.[^pradn]
작성자는 만들 때만 늘거나 성장이 한계 안에 있는 구조는 늘기만 하는 배열로
충분하고, 끝없이 커질 수 있으면 풀이나 재구성 같은 다른 해법이 필요하다고
했다.[^Aardappel-unbounded]
그러면 이 언어의 이득은 문제가 이 모델에 맞게 짜일 때 나오고, 맞지 않으면 사실상
풀이라는 이름의 직접 만든 할당기를 쓰게 된다는 뜻이다.
이 해석은 이 문서의 것이다.

## 비평

### 속도 주장은 저자 측정이고 수치가 한 군데에서 일관되지 않는다

페이지 상단은 열여섯 벤치마크에서 관용적 C++ 대비 3.3배, 손으로 최적화한 C++
대비 1.16배, 가장 좋은 안전한 Rust 대비 1.12배이고 메모리는 각각 1.9배, 1.3배,
1.2배 적다고 쓴다.
같은 페이지의 표는 MSVC 백엔드에서 3.51배, 1.24배, 1.13배, clang 백엔드에서
3.54배, 1.26배, 1.19배, 메모리는 1.95배, 1.32배, 1.25배 적다고 한다.
두 값 사이의 차이가 어디서 오는지(측정 시점이나 집계 방식)는 페이지에 설명이
없다.
작성자는 HN에서 평균적으로 빠르다는 말이고 느린 알고리즘 예도 있지만 크게 느린
경우는 못 찾았다고 했고, 독립 벤치마크로 LangArena를
가리켰다.[^Aardappel-threads]
이 문서는 LangArena와 저장소의 벤치마크를 열어 보지 못했고 재현하지 못했다.

### 안전 주장은 새 컴파일러의 추론 정확성에 전적으로 기댄다

`unsafe`도 정의되지 않은 동작도 없다는 보증은 수명 검사 증명이 맞다는 전제 위에
선다.
컴파일러는 3만 줄쯤의 새 C++이고 구현은 AI가 했다고 페이지가 밝힌다.
저자는 검증 수단으로 테스트와 sanitizer 작업을 말하지만, 안전 증명을 독립적으로
검토했다는 언급은 페이지에 없다.
이 지적이 곧 안전하지 않다는 뜻은 아니며, 주장이 아직 컴파일러 자체의 검증을
받지 않았다는 말이다.
weinzierl이 Rust의 매력을 안전, 성능, 개발자 경험 순으로 꼽으며 Goose의 위치를
물은 것도 같은 맥락이다.[^weinzierl]
작성자의 답은 borrow checker와 싸울 일이 없고, Rust에서 인덱스를 써야 하던
알고리즘이 Goose에서는 강하게 타입 지정된 참조가 된다는
것이었다.[^Aardappel-unsafe]

### 64비트 주소 공간이라는 전제는 적용 범위를 좁힌다

설계는 큰 주소 공간을 예약하는 데 기댄다.
malkia는 wasm이 대개 32비트라 이 방식이 가능한지 물었고,[^malkia] kadw는
임베디드와 MCU에서 어떻게 맞는지 보고 싶다고 했다.[^kadw]
작성자는 실제 확보하는 메모리가 상대적으로 적어 임베디드에도 쓸 수 있지만 64비트
주소 공간이 필요하고 임베디드에서는 아직 흔하지 않다고
답했다.[^Aardappel-embedded]
따라서 이 언어가 닿는 곳은 64비트 환경으로 정해진다.
wasm 질문에는 작성자의 답을 확인하지 못했다.

### 첫 화면은 무엇을 위한 언어인지 알려 주지 않는다는 반응이 있었다

FrustratedMonky는 표지에 목적과 쓰임, 그리고 어떤 빈틈을 메우는지가 먼저 있어야
한다고 했다.[^FrustratedMonky]
wewewedxfgdf는 새로운 더 나은 것이 나올 때 중요한 질문은 단점이라고 했고,
작성자는 튜토리얼의 단점 목록을 가리켰다.[^wewewedxfgdf][^Aardappel-downsides]
이 문서가 읽은 페이지는 소개 문단에서 특징을 늘어놓은 뒤 “What it costs you”에서
단점을 적는다.
단점은 숨겨져 있지 않지만, 비용이 어떤 종류의 프로그램에서 특히 아픈지는
페이지에 구분이 없다.

## 인사이트

### 오래된 region 아이디어가 64비트 주소 공간에서 다시 가능해졌다

ebiederm은 ML 쪽에서 이 길을 갔고 region이라 불렀으며, 메모리 사용이 크게
늘어나는 프로그램이 있어 막다른 길로 여겨졌다고 기억한다고 했다.[^ebiederm]
작성자는 ML Kit의 region 추론이 가장 가까운 선행 연구라고 인정하면서, 당시에는
큰 64비트 주소 공간을 쓸 수 없어 메모리 블록의 사슬로 구현하고 대부분을 런타임에
추적했는데 Goose는 그 일을 컴파일 시점에 한다고 설명했다.[^Aardappel-ml]
이 대화가 보여 주는 것은 설계 아이디어의 성패가 하드웨어 가정에 달려 있었다는
점이다.
주소 공간이 부족하던 시절의 한계가 풀리면, 한 번 막다른 길이라 판단된 설계가
다시 열릴 수 있다.
이 해석은 이 문서의 것이다.

### 설계는 사람이 하고 구현은 AI가 하는 분업의 비용은 문서에서 드러난다

페이지의 마지막 절은 이 저장소가 거의 전부 AI로 만들어졌고 설계는 사람이 했다고
적는다.
작성자는 몇 년 전 설계해 두고 시간이 없어 구현하지 못하던 언어를 Fable이 나온 뒤
만들 수 있었고, 이전 컴파일러(Lobster)의 코드 스타일 가이드를 AI가 정리하게 한
뒤 그 스타일로 패스별로 쓰게 했다고 HN에서 설명했다.[^Aardappel-ai]
그 결과로 코드가 자기 것처럼 읽혀 검토가 쉬웠다고 한다.
반면 문서 쪽은 반응이 갈렸다.
IshKebab은 AI 특유의 문장을 없애고 다시 쓰라고 했고,[^IshKebab] cardanome은
설계가 괜찮아 보이는데 자기 말로 쓰지 않았다는 이유로 읽기를 그만둔다고
했다.[^cardanome]
작성자는 이미 많이 고쳤으나 사람들이 언어를 써 보는 것이 AI 특유의 표현을
걱정하는 것보다 낫다고 답했다.[^Aardappel-prose]
이 일이 보여 주는 것은 구현은 검증할 수 있는 코드로 신뢰를 얻을 수 있지만,
설명은 읽는 사람이 글에서 신뢰 신호를 읽는다는 점이다.
설계가 새롭다는 주장과 문서가 AI 문장처럼 읽힌다는 인상이 한 페이지에 함께
있으면, 앞의 주장이 뒤의 인상에 가려질 수 있다.
이 해석은 이 문서의 것이다.

### 이 글을 읽는 방법

이 페이지는 언어의 소개이자 저자 자신의 벤치마크 요약이고, 판단에 필요한 정보는
샘플 프로그램을 직접 짜 보는 데 있다.
오늘 할 일은 설치 없이 돌아가는 TinyCC 프로세스 내 실행으로 튜토리얼 예제를 몇
개 돌려 보고, 자신이 쓰는 데이터 구조(예: 해시 테이블이나 그래프)를 이 모델에서
어떻게 짤지 가늠해 보는 것이다.
이 주장을 가를 관찰은 두 가지다.
독립된 측정에서 같은 열여섯 벤치마크의 속도와 메모리가 페이지의 수치에 가깝게
나오는지, 그리고 수명이 서로 다른 객체가 섞인 실제 프로그램(예: 해시 테이블에
문자열을 임의로 넣고 빼는 서버)이 풀 없이 어느 정도까지 짜이는지다.
둘 다 이 문서는 직접 확인하지 못했다.
