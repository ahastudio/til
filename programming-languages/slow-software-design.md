# 소프트웨어가 느린 이유는 느린 언어가 아니라 나쁜 설계다

원문: [Software is slow because of bad design, not slow languages](https://www.seangoedecke.com/software-is-slow-because-of-bad-design-not-slow-languages/)

HN 토론: <https://news.ycombinator.com/item?id=50206715> (7점, 3개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/hd72yt/software_is_slow_because_bad_design_not> (38점, 44개 댓글)

GN 토론: <https://news.hada.io/topic?id=35893>

## 요약

Sean Goedecke가 쓴 짧은 블로그 글이다.
AI가 소프트웨어를 더 빠른 언어로 다시 써서 빠르게 만들 것이라는 말이 많은데,
대부분의 프로그램은 C나 Rust로 다시 써도 의미 있게 빨라지지 않는다는 것이
주장이다.
C는 Python보다 50배 빠를 수 있지만 그렇다고 Python 프로그램을 C로 옮기면 50배
빨라지지는 않는다.
이유는 세 가지다.

첫째, 대부분의 실제 프로그램은 I/O에 묶여 있다.
데이터베이스가 있는 단순한 CRUD 웹사이트에서 요청 시간의 50%가 데이터베이스
조회에 쓰인다면, C로 다시 써서 줄일 수 있는 것은 나머지 50%뿐이라 최대
2배(현실적으로는 1.5배 정도)가 상한이다.
외부 API 대기나 디스크 읽기와 쓰기도 마찬가지이며, curl의 코드를 100배 빠르게
만들어도 네트워크를 기다리는 시간이 대부분이라 알아차리기 어렵다고 쓴다.
둘째, 느린 언어는 이미 빠른 언어에 일을 넘긴다.
위키가 마크다운을 HTML로 바꿀 때 cmark-gfm 같은 라이브러리를 쓰고, Python은 행렬
곱셈이 GPU에서 최적화된 C나 어셈블리로 도는 기계 학습에서 경쟁력이 있다.
엔지니어링 관심을 받지 못한 프로그램에는 쉬운 개선점이 많겠지만 그런 프로그램은
대개 중요하지 않고, 중요했다면 AI 이전에 누군가 최적화했을 것이라고 한다.
셋째, 속도 개선은 보통 재설계다.

저자의 근거는 Bryan Cantrill의 2018년 글이다.
최적화된 C 프로그램을 Rust로 옮기려다 빌림 검사기와 설계가 맞지 않아 포기하고
단순하게 Rust로 썼는데 20% 이상 느려질 것이라는 예상과 달리 30% 빨랐고, 이유는
Rust의 기본 자료 구조가 캐시 효율이 좋은 B-트리라는 점이었다고 한다.
저자 본인의 큰 속도 개선도 거의 전부 일을 덜 하도록 바꾼 재설계였다.
느린 작업 캐싱(보통 외부 API 호출), 비동기 처리(백그라운드 작업), 순차 대신 병렬
실행, N+1 문제를 단일 SQL로 바꾸기, 느린 SQL을 빠른 SQL로 바꾸기, 불필요한 느린
작업 건너뛰기(페이지에 보이는 항목의 부가 데이터만 가져오기)가 예다.
그래서 AI 에이전트에게는 Rust로 다시 쓰라는 대신 프로파일링으로 병목을 찾고
프로그램이 하는 일을 어떻게 재설계할지 제안하게 하라는 것이 결론이다.
진짜 CPU에 묶인 병목이 있고 줄일 일이 없을 때만 그 부분을 빠른 언어로 다시 쓰면
된다고 한다.

글 끝에는 저자가 덧붙인 수정 문단이 있다.
Lobste.rs 댓글 대부분이 비판적이었다고 밝히고, CRUD가 I/O에 묶였다는 것에 반대하는 의견(데이터베이스 질의는 약 5ms인데 응답은 약 500ms)은 경험적 질문이며 자신의 판단은 수천 개의 Ruby 플레임그래프에서 나왔다고 답한다.
요청 하나가 수십에서 수백 개의 질의를 하거나 5ms보다 훨씬 느린 큰 질의나 내부
API 호출에 기대는 일이 드물지 않지만 자신이 프로파일링한 곳이 두어 회사뿐이라는
한계를 인정한다.
CPU에 묶인 프로그램(브라우저 레이아웃 엔진, 3D 렌더러, 워드 프로세서, 신경망)은
인정하되 CRUD 프로그램 수의 약 5% 정도이고 공개 논의의 50% 이상을 차지할
뿐이라고 추정한다.
언어의 생태계가 성능을 쉽게 또는 어렵게 한다는 지적은 설계에 속하는 일이라고
받아들인다.

## 분석

### 글의 중심 주장: 암달의 법칙이 언어 교체의 상한을 정한다

글의 논리는 암달의 법칙(각주에서 명시)이다.
전체 시간 중 언어 속도에 비례하는 부분이 작으면 그 부분을 아무리 빠르게 해도
전체는 거의 빨라지지 않는다.
50%라는 가정 비율이 이 논증을 정량으로 만들지만, 그 값은 저자의 경험(보통
인터프리트 언어 기준으로 그럴듯한 범위)이라고 각주에서 밝힌다.
이 논증은 비율이 맞는 프로그램에서는 정확하고, 비율이 다른 프로그램에서는
성립하지 않는다.

### 설계가 먼저라는 주장의 구조

저자가 드는 여섯 가지 속도 개선은 모두 할 일을 줄이거나 겹치게 하는 것이다.
캐싱과 건너뛰기는 일을 안 하고, 비동기와 병렬은 일을 겹치고, N+1 해소는 왕복을
줄인다.
이들은 언어와 독립적이라는 점이 핵심이다.
저자는 느린 고수준 언어가 오히려 최적화를 쉽게 한다고도 주장하는데, 프로그램이
하는 일이 한눈에 보여 N+1이나 API 호출 이동 같은 기회를 알아차리기 쉽기
때문이라는 설명이다.

### AI 시대에 이 글이 나온 맥락

이 글의 직접적인 표적은 에이전트에게 프로그램을 Rust나 C로 옮기라고 시키는
유행이다.
다시 쓰기가 싸졌기 때문에 시도가 늘었고 저자는 이를 재미는 있지만 진지한
최적화는 아니라고 평한다.
권고(프로파일링, 병목 식별, 재설계 제안)는 AI에게 시킬 일을 바꾸는 것이어서 도구
사용법으로도 읽힌다.

## 비평

### 서버 개발자의 시야로 프로그램 전체를 말한다

Lobste.rs의 snej는 CRUD 웹사이트를 실제 프로그램의 전형으로 삼은 것을 서버 개발자가 모든 실제 프로그램을 서버라고 생각하는 것이라고 비판했고, 브라우저 레이아웃 엔진, 3D 렌더러, 워드 프로세서, 신경망을 반례로 들었다.[^snej]
untitaker는 CLI에서는 `--help` 지연이 곧 사용자에게 보이므로 많은 느린 언어가
이미 졌다고 했고, 느린 언어가 빠른 언어에 일을 넘긴다는 주장에 대해서도 언어
사이 데이터 전달이 쉽지 않아 파일 형식 변환 같은 문자열 입출력이 아닌 문제에는
같은 방식이 통하지 않는다고 했다.[^untitaker]
저자는 수정 문단에서 이를 인정하되 이런 프로그램이 CRUD 프로그램 수의 약 5%
정도일 것이라고 추정했는데, 이 비율은 근거 없는 추정이며 저자도 틀렸을 수 있다고
쓴다.
논점은 이 글의 주장이 어느 모집단에 대한 것인지다.

### I/O에 묶였다는 전제가 경험적으로 다툼의 대상이다

dlisboa는 서버 쪽에서도 틀렸다고 했다.
DB 조회가 약 5ms인데 평균 응답이 약 500ms이므로 사람들이 당연하게 여기는 CPU
묶임의 작은 작업과 오버헤드가 많다는 것이다.[^dlisboa]
mpweiher는 SSD가 빨라서 서버에서도 한동안 사실이 아니고, `mkfile(8)`처럼 0만
디스크에 쓰는 프로그램도 macOS에서 시스템 호출 한도로 CPU에 묶인다고
했다.[^mpweiher]
저자의 답은 자신이 본 수천 개의 Ruby 플레임그래프에서 한 요청이 수십에서 수백
개의 질의를 한다는 것이다.
두 주장은 서로 다른 계측 환경에서 나온 것이며 이 글도, 이 문서도 어느 쪽이
일반적인지 확인하지 못했다.

### 언어의 속도라는 개념 자체를 문제 삼는 반론과 그 반응

singpolyma는 언어는 느리지 않고 느린 구현이 있을 뿐이며 시간이 지나면 더 빠른
구현으로 바뀔 수 있다고 했다.[^singpolyma]
nrposner는 구현 변화가 한 언어 안에서도 성능에 큰 효과가 있다며 CPython이 새
버전마다 빨라지고 Jython, IronPython, PyPy로 가면 성능이 달라진다고
반박했다.[^nrposner]
swaits는 Ruby, Lua, Perl, PHP, 대부분의 Python을 다른 언어로 다시 쓰면 훨씬
빨라질 것이며, 글이 이를 빼먹은 것이 아니라 적극적으로 피했다고
비판했다.[^swaits]
저자는 수정 문단에서 언어의 생태계가 설계에 속한다고 받아들였다.
이 논쟁에서 글의 가장 약한 부분은 언어 선택이 설계 선택의 폭을 넓히거나 좁힌다는
점을 별개로 취급한다는 것이다.

### 고수준 언어가 최적화를 쉽게 한다는 주장은 약하게 뒷받침된다

nrposner는 파이썬에서 최적화할 때 언어나 패키지와 씨름하게 되므로 한눈에
보인다는 주장에 동의하지 않는다고 했고,[^nrposner-opt] spc476은 언어와 무관하게
어디서 시간이 쓰이는지를 정확히 짚은 적이 없다고 했다.[^spc476]
sunshowers는 Rust보다 Python에서 허용 가능한 성능을 얻으려고 더 무리를 해야 했고
추상화를 없애고 코드를 복사하는 등 나쁜 엔지니어링을 해야 했다고
했다.[^sunshowers]
weberc2는 필요하면 느린 부분만 C나 Rust로 바꾸겠다며 Python을 고른 프로젝트들이
느린 부분을 명목상 빠르게 만들고 언어 사이 데이터 마샬링에 시간을 쓰게 되는
문제를 고쳤다고 했다.[^weberc2]
저자의 이 주장은 프로파일링이 아니라 경험에서 나온 것이며 반례가 많다.

## 인사이트

### 언어 교체와 재설계는 서로 다른 시점의 비용이다

두 편의 갈래가 같은 현상을 다르게 본다.
저자는 이미 있는 프로그램을 다시 쓰는 시점의 이득을 말하고, 반론자들은 처음부터
어떤 언어로 쓰느냐가 설계 선택지와 이후 최적화 비용을 정한다고 말한다.
Jackevansevo의 지적처럼 LLM이 서비스를 X로 다시 썼더니 빨라졌다는 사례가 많은
이유는 다시 쓰는 김에 설계를 다시 생각했기 때문이며 공정한 비교가 아닐 수
있다.[^jackevansevo]
이 구분을 하면 언어 교체의 이득이 순수한 언어 효과인지 설계를 다시 한 효과인지를
분리하는 실험(같은 설계를 두 언어로 구현)이 필요함을 알 수 있다.
글은 그런 비교를 제시하지 않으며 Cantrill의 사례가 가장 가까운 예다.

### 병목 계측이 선행되어야 어느 주장이 맞는지 안다

저자의 처방(프로파일링과 병목 식별)은 논쟁의 해결책이기도 하다.
I/O에 묶였는지 CPU에 묶였는지는 프로그램마다 측정으로 답할 수 있다.
저자도 반대편도 일반화된 비율을 주장하지만 실제로 필요한 것은 자기 프로그램의
플레임그래프다.
siru는 설계가 어려운 부분이고 문법을 쓰는 것은 어렵지 않았던 것 같다고
말했는데,[^siru] 에이전트가 문법 쓰기를 싸게 만들면서 남는 병목이 설계와
측정이라는 이 글의 암묵적 함의와 이어진다.
이 연결은 이 문서의 해석이다.

### 이 글을 읽는 방법

이 글은 에이전트에게 프로그램을 빠른 언어로 다시 쓰게 하려는 사람에게 먼저
측정하라는 경고로 쓸모 있다.
오늘 할 일은 느리다고 생각하는 서비스 하나의 요청을 프로파일링해서 I/O 대기와
CPU 시간의 비율, 질의 수, 직렬 호출을 세어 보는 것이다.
이 글의 주장을 가를 관찰은 두 가지다.
같은 서비스의 프로파일에서 CPU 시간이 요청 시간의 절반을 넘는지, 그리고 같은
설계를 다른 언어로 옮겼을 때와 설계를 바꿨을 때의 속도 개선 크기가 어느 쪽이
큰지다.
둘 다 이 글에는 없고, 저자가 인정한 대로 자신의 경험(몇몇 회사의 Rails 서비스)에
기댄다.
