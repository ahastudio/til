# Soppo: Go에 빠진 기능을 더한 언어

> Go, with the features it's missing.
>
> Type safety and ergonomics, with full interop.

<https://soppolang.dev/>

<https://github.com/halcyonnouveau/soppo>

Lobste.rs 토론: <https://lobste.rs/s/0ykmyt/soppo_go_with_features_it_s_missing> (82점, 33개 댓글)

## 소개

Soppo는 스스로를 “Go, with the features it's missing”이라고 소개한다.
부제는 “Type safety and ergonomics, with full interop”이며, 홈페이지 최상단이 투어
링크와 GitHub·Playground·Docs 링크로 구성된다.

핵심 전략은 문법 친화성이다.
가능한 모든 곳에서 Go 문법을 쓰므로 Go를 알면 Soppo의 대부분을 이미 아는 셈이고,
어떤 Go 라이브러리든 직접 쓸 수 있고, 기존 툴체인을 유지하며 기존 프로젝트에 점진적으로
도입할 수 있다고 밝힌다.
첫 예제 코드가 이 주장을 뒷받침한다 — `net/http`로 핸들러를 등록하고
`http.ListenAndServe(“:8080”, nil)`을 호출하는 코드가 Go와 문자 그대로 동일하다.

컴파일은 내부적으로 Go를 사용한다.
설치 권장 경로는 SOPMOD라는 버전 관리자이며, Soppo 버전 설치·갱신·전환을 처리하고
Soppo가 내부적으로 쓰는 Go도 함께 관리한다.

```bash
curl -fsSL https://soppolang.dev/install.sh | sh
export PATH="$HOME/.sopmod/bin:$PATH"
sopmod install sop latest
```

SOPMOD 없이 `sop` 바이너리만 설치하려면 Cargo를 쓸 수 있고, 이 경우 Rust와 Go가
모두 필요하다.

```bash
cargo install soppo
```

즉 툴체인은 Rust로 작성된 컴파일러가 Go 코드를 생성하고 Go 툴체인이 그것을 빌드하는
구조로 읽힌다.

## 주요 기능

### 열거형과 패턴 매칭

구조체 변종을 갖는 태그 유니온과, 모든 경우를 처리하도록 보장하는 패턴 매칭을
제공한다.
컴파일러가 실행 전에 빠진 분기를 잡아내므로 자신 있게 리팩터링할 수 있다는 것이
홈페이지의 설명이다.

```go
type Shape enum {
    Circle struct { radius float64 }
    Rectangle struct { width, height float64 }
}

func area(s Shape) float64 {
    match s {
    case Shape.Circle{radius: r}:
        return 3.14159 * r * r
    case Shape.Rectangle{width: w, height: h}:
        return w * h
    }
}
```

`enum` 키워드로 변종을 선언하고 `match`로 분해하는 형태이며, 변종 안에 이름 있는
필드를 두고 패턴에서 `{radius: r}`처럼 구조 분해한다.

### `?` 연산자를 통한 오류 처리

반복적인 `if err != nil` 블록을 없애는 것이 목표다.
`?` 연산자가 오류를 간결하게 전파하면서도 오류 처리를 명시적이고 눈에 보이게 유지하고,
필요할 때 맞춤 처리를 추가할 수 있다.

```go
func processFile(path string) error {
    // Propagate error directly
    data := os.ReadFile(path)?

    // Custom handling with named error
    result := parse(data)? err {
        return fmt.Errorf("parse failed: {err}")
    }

    fmt.Println("Processed {len(result)} items")
    return nil
}
```

`?` 뒤에 이름 있는 오류 변수와 블록을 붙여 맞춤 처리를 하는 문법이 특징이고,
문자열 안에 `{err}`, `{len(result)}`처럼 식을 넣는 보간(interpolation)도 함께
제공된다.

### nil 안전성

nil 포인터 역참조가 Go에서 런타임 패닉의 흔한 원인이라는 진단에서 출발한다.
Soppo는 nil 가능성을 컴파일 시점에 추적하므로 이 버그가 프로덕션에 도달하기 전에
잡을 수 있고, nil 검사 이후 타입이 자동으로 좁혀진다.

```go
func findUser(id int) ?*User {  // ? marks nilable
    if id == 0 {
        return nil
    }
    return &User{name: "Alice"}
}

func greet(id int) {
    user := findUser(id)

    if user != nil {
        // user is *User here, not ?*User
        fmt.Println("Hello {user.name}")
    }
}
```

`?*User`가 nil이 될 수 있는 포인터 타입이고, `if user != nil` 블록 안에서는
`*User`로 좁혀진다.

### 진단 메시지

무언가 잘못되면 정확히 무엇이 어디서 일어났는지 알려주는 것을 목표로 한다.
오류 메시지가 관련 코드를 보여주고 문제를 강조하고 고치는 방법을 제안하며, 디버깅이
추측 게임이 아니라 직관적이어야 한다는 것이다.

```text
× Non-exhaustive match
   ╭─[main.sop:11:5]
10 │     var message string
11 │ ╭─▶ match colour {
12 │ │    case Colour.Red:
13 │ │        message = "Stop"
14 │ │    case Colour.Yellow:
15 │ │        message = "Wait"
16 │ ├─▶ }
   · ╰──── missing variants: Green
17 │ }
   ╰────
help: Ensure all enum variants are handled, or add a `default` case
```

소스 파일 확장자가 `.sop`이며, 진단 형식은 Rust의 `miette`/`ariadne` 계열 렌더링과
같은 계보로 보인다.

## 분석

### 이 프로젝트의 실제 주장은 언어 설계가 아니라 마이그레이션 경로다

홈페이지가 나열하는 기능 — 합 타입, 패턴 매칭, `?` 오류 전파, nil 추적, 문자열 보간 —
은 그 자체로 새롭지 않다.
Rust와 Swift와 Kotlin에 다 있고, Go 커뮤니티에서 10년 넘게 요구되어 온 목록이기도
하다.
새로운 것은 그것들을 Go 문법 안에 담고 Go 라이브러리를 직접 쓰게 하고 기존 프로젝트에
점진적으로 넣을 수 있다고 주장하는 부분이다.

이 배치가 프로젝트의 성격을 결정한다.
언어를 파는 것이 아니라 이주 비용의 부재를 파는 것이며, 그래서 첫 번째 기능 섹션이
문법이나 타입 시스템이 아니라 “Familiar syntax”이고 그 예제가 순수한 Go 코드다.
Go 개발자에게 “아무것도 배우지 않아도 시작할 수 있다”를 먼저 보여주는 구성이다.

같은 계보의 선례를 보면 이 전략의 승률이 갈린다.
성공한 쪽은 기존 런타임과 생태계를 그대로 쓴 언어들이다 — Kotlin이 JVM에서, TypeScript가
JS에서, Scala가 초기에 JVM에서 그랬다.
실패한 쪽은 문법만 개선하고 생태계 통합이 얕았던 언어들이다.
Soppo가 Go로 컴파일하고 Go 라이브러리를 직접 쓴다는 설계는 전자에 속하려는 시도이며,
설치 과정이 Go 툴체인까지 함께 관리한다는 사실이 그 의존을 드러낸다.

### `?` 연산자와 명시적 오류 처리라는 두 목표를 동시에 주장하는 구조

오류 처리 섹션의 서술은 조심스럽게 균형을 잡는다 — 반복적인 `if err != nil`을 없애면서도
“오류 처리를 명시적이고 눈에 보이게 유지한다”는 것이다.
이 문장은 Go 커뮤니티의 오래된 논쟁에 대한 답으로 읽힌다.

Go 팀이 `try` 제안을 거부한 이유가 정확히 이 지점이었다.
`if err != nil`의 장황함은 대가이고, 그 대가로 얻는 것은 모든 오류 지점이 코드에
보인다는 것이다 — 예외가 있는 언어에서 어느 줄이 던질 수 있는지 알 수 없는 것과의
대조다.
Soppo의 `?`는 이 논쟁에서 Rust 쪽 답을 택했다 — 전파는 한 글자로 줄이되, 그 한 글자가
거기 있다는 사실 자체가 오류 지점의 표시가 된다.

여기에 Soppo가 추가한 것이 `? err { ... }` 형태의 맞춤 처리 블록이다.
Rust는 `?`와 `match`를 별도 문법으로 두는데, Soppo는 전파와 처리를 같은 위치에서
선택하게 만든다.
이 설계는 Go 코드의 흔한 패턴 — 오류를 감싸 문맥을 덧붙여 반환하는 것 — 을 한 표현에
담으려는 시도로 보이며, 실제로 예제가 `fmt.Errorf(“parse failed: {err}”)`를
보여준다.

그런데 Lobste.rs에서 이 문법이 충분히 짧지 않다는 반론이 최상위 댓글로 올라왔다.
문서의 맞춤 처리 예제가 통상적인 `if err != nil` 춤보다 거의 짧지 않아 완전히 잉여로
느껴지며, 진짜 유용한 해법은 `return fmt.Errorf(“{message}: %w”, err)`에 대한 축약이라는
것이다.[^nemin]
제안된 형태가 구체적이다 — `port := parsePort(config) ?? “port parsing failed”`가
오류를 `%w`로 감싸 반환하는 코드로 확장되고, `?? (“port parsing on %q failed”,
config.IPAddress)`처럼 포맷 인자를 받는 변종도 두는 것이다.
다른 참여자가 이 제안에 동의하면서 Go의 요점은 단순하고 명시적인 것이며 한두 줄
아끼는 데 가치가 없다고 하면서도, 진짜 짜증은 실패할 수 있는 동작마다 반복되는 세
줄이 고루틴·채널 의례에 소음을 더할 때 생긴다고 구별했다 — 그래서 합리적인 길은
오류 처리를 아예 바꾸지 않는 것과 일반적 경우를 아주 깔끔하게 만드는 한 줄짜리 문법
설탕뿐이라는 것이다.[^sylq]

반대로 `?`를 옹호하는 근거는 Go의 스코프 규칙에서 나왔다.
`port` 변수를 조건문 아래에서도 쓰이게 하면서 `err`가 검사 이후로 살아남지 않게
하려면 `var port PortType`을 먼저 선언하고 블록으로 감싸는 끔찍한 춤이 필요하며,
실무에서는 대개 `port, err := parsePort(config)`로 쓰고 `err`가 주 스코프로 새는
것을 감내한다는 설명이다.[^spillybones]
그 새어 나온 `err` 때문에 뒤이은 줄에서 `err := ...`를 쓰면 “no new variables on
left side of :=” 컴파일 오류가 난다는 것이 이 문제의 실질적 비용이다.
다른 참여자도 같은 이유로 `?`가 순수 Go의 대안보다 낫다고 인정했다 — 새 변수를 바깥
스코프에 두고 싶을 때 `if port, err := ...; err != nil` 형태는 `port`를 내부 스코프에
갇히게 만들기 때문이다.[^gerow]

Go 진영에서 같은 문법이 이미 검토되고 폐기되었다는 사실도 지적되었다.
후행 `?`와 오류 변수를 잡는 `?`에 대한 최근 GitHub 논의가 결국 폐기되었고, 불만
중 하나가 `?`를 놓치기 아주 쉬워 오류 경로와 정상 경로를 찾으려 할 때 코드가 훨씬
읽기 어려워진다는 것이었다.[^dfawcus]
그 댓글은 새 키워드 형태였던 이전의 `try`/`check` 제안이 읽고 발견하기 쉬워 더
맞았을 것이라고 보면서, 오류 처리 개선에 대해 고려할 만한 설계 제안 고고학이 상당히
쌓여 있으며 그것들이 검토되고 저울질되었는지 궁금하다고 덧붙였다.

### nil 안전성을 새 타입이 아니라 흐름 분석으로 푸는 선택

`?*User`라는 표기와 “nil 검사 이후 타입이 자동으로 좁혀진다”는 서술이 이 설계의
핵심이다.
`Option[T]` 같은 래퍼 타입을 도입하는 대신, 기존 포인터 타입에 nil 가능성 표시를
붙이고 제어 흐름 분석으로 좁힌다.

이 선택은 Go 상호운용성에서 직접 따라온다.
Go 라이브러리는 포인터를 반환하고 그것이 nil일 수 있다.
Soppo가 `Option`을 도입했다면 모든 Go 호출 경계에서 변환이 필요했을 것이고, “Go
라이브러리를 직접 쓴다”는 약속이 깨졌을 것이다.
반면 nil 가능성을 타입 수준 표시로 두면 Go 함수의 반환 타입을 `?*T`로 해석하는 것만으로
경계가 처리된다.

같은 접근을 택한 선례가 여럿이다 — TypeScript의 `strictNullChecks`와 좁히기,
Kotlin의 `?` 타입과 스마트 캐스트, C#의 nullable 참조 타입.
셋 다 기존 생태계와의 호환을 위해 래퍼 대신 표시와 흐름 분석을 골랐고, 같은 대가를
치렀다 — 좁히기가 통하지 않는 경우(별칭, 클로저 캡처, 필드 접근, 동시 수정)가 남고,
그때 사용자가 강제 단정을 쓰게 된다.
홈페이지에는 이 경계 사례가 나오지 않으며, 실사용 판단에 가장 필요한 정보가 빠진
셈이다.

Lobste.rs 최상위 댓글이 정확히 이 지점을 의심했다 — 매끄러운 상호운용과 nil 안전성을
동시에 가질 수 있는지 모르겠다는 것이다.[^nemin]
다른 참여자가 문서에서 답을 찾아 왔고, 그 답이 설계를 명확히 한다 — 외부 Go 패키지의
타입은 Go에 nil 가능성 주석이 없으므로 nilable로 가정되며, 비nilable 타입을 기대하는
Soppo 함수에 넘길 때는 nil 검사나 `.(!nil)`을 쓰라는 것이다.[^wezm]
즉 상호운용 경계에서 안전성은 보장되지 않고 사용자의 검사로 이전된다.
설계로서는 일관되지만 “full interop”이라는 부제와 “nil 안전성”을 나란히 내세운
홈페이지의 서술은 이 이전 비용을 보여주지 않는다.

## 비평

### 홈페이지가 “Go의 빠진 기능”이라고 부르는 것들은 Go 팀이 거부한 기능들이다

프로젝트의 한 줄 소개 — “Go, with the features it's missing” — 는 Go에 그 기능들이
없는 이유를 우연이나 미완성으로 전제한다.
그런데 나열된 항목 대부분은 Go 팀이 명시적으로 검토하고 거부한 것들이다.

합 타입은 Go 제안 목록에 오래 있었고, 오류 전파 문법(`try`)은 2019년에 제안되어
커뮤니티 반발 후 철회되었고, nil 추적은 하위 호환 파괴 없이는 어렵다는 이유로 진전이
없었다.
이 결정들의 공통 근거는 단순성 예산이었다 — Go는 기능을 더하지 않는 것을 설계 목표로
삼은 언어이며, 읽기 쉬움과 컴파일 속도와 학습 시간을 그 대가로 산다.

그러므로 “빠진 기능”이라는 프레임은 논쟁을 회피한다.
Soppo가 실제로 하는 주장은 “Go의 단순성 예산 배분이 잘못되었다”이고, 그것은 정당한
주장이지만 홈페이지는 그것을 논증하지 않는다.
기능 목록을 나열하는 형식은 “있으면 좋다”를 자명한 것으로 만들지만, 언어 설계에서
기능의 가치는 그것이 없을 때의 비용과 있을 때의 상호작용 복잡성을 함께 재야 판단할 수
있다.
이 홈페이지에는 후자에 대한 논의가 없다.

### 제로값 문제가 합 타입의 망라성 보장을 근본에서 깨뜨린다

Lobste.rs에서 가장 무거운 기술적 반박은 Go의 제로값 규칙을 겨눈 것이었다.
Go에 태그 유니온을 더하자는 제안이 나올 때마다 첫 질문은 모든 값이 기본 초기화된다는
사실을 어떻게 다루느냐는 것이며, Soppo는 이것을 실제로 다루지 않는 것으로 보인다는
지적이다.[^brendan]
제시된 반례가 간결하다 — `type Empty enum {}`처럼 변종이 하나도 없는 열거형을 선언한
뒤 그것을 필드로 가진 구조체를 `Foo{}`로 만들면 컴파일되고 `{<nil>}`이 출력된다.
이상적으로는 이 타입을 아예 구성할 수 없어야 하는데 그렇지 않다는 것이다.

이 문제가 치명적인 이유는 홈페이지가 내세운 두 약속을 동시에 무너뜨리기 때문이다.
“컴파일러가 빠진 분기를 실행 전에 잡아낸다”는 망라성 보장은 값이 항상 어떤 변종이라는
전제 위에 있다.
제로값이 어떤 변종도 아닌 상태로 존재할 수 있으면 `match`는 그 상태를 다루지 않고,
런타임에 nil로 새어 나온다.
같은 댓글이 지적한 대로 Go API에 기본값이 만연하다는 사실이 이것을 사소한 이론적
문제가 아니라 실질적 함정으로 만든다.

같은 참여자가 선택지를 정리한 것이 이 설계 공간을 잘 보여준다 — nil 안전성과 망라성
주장을 철회하거나, 열거형 `match`에서 기본(nil) 케이스 처리를 요구하거나, 변종을
하나 이상 요구하고 첫 변종을 기본값으로 삼거나, 기본 변종을 명시적으로 표시하게
하는 것이다.[^brendan-b]
Go 자체의 합 타입 제안이 택한 방향은 세 번째, 즉 첫 옵션을 제로값으로 삼는 가장
단순한 방식이며, 이것이 nilable 포인터를 바꾸는 것보다 추론하기 훨씬 쉽다는 지적도
나왔다.[^nposting]
그 댓글의 결론이 이 프로젝트에 대한 가장 공정한 요구다 — 제로값처럼 언어 전반에
함의가 있는 아주 핵심적인 부분을 건드리는 변경인데, 나머지 언어가 이 변경들을 어떻게
둘러싸도록 의도되었는지에 대한 설명을 듣지 못한 것이 놀랍다는 것이다.

트레이드오프에 대한 판단은 갈렸다.
한 참여자는 언어에서 제로값을 없애기 위해 기존 Go 코드 거의 전부를 다시 써야 하는
아주 다른 Go보다, 열거형 타입에 이상한 기본값 흠이 남고 나머지 Go가 그대로인 쪽을
훨씬 선호한다고 적었다 — nil 처리에 약간의 안전성만 있어도 큰 이득이라는
것이다.[^jitl]
이 입장은 실용적이지만, 그렇다면 홈페이지가 “컴파일러가 실행 전에 잡아낸다”를 조건
없이 주장하는 것은 정확하지 않은 서술이 된다.

### Go로 컴파일한다는 사실이 만드는 제약이 어디에도 언급되지 않는다

설치 안내에서 Go가 “Soppo가 내부적으로 컴파일에 사용하는” 것으로 한 번 언급되고
끝난다.
그런데 이 사실은 언어의 능력을 상당히 규정한다.

Go를 대상으로 코드를 생성하면 Go의 타입 시스템으로 표현할 수 없는 것을 런타임 표현으로
내려야 한다.
합 타입은 태그 필드가 있는 구조체나 인터페이스로, 패턴 매칭은 타입 스위치나 태그
비교로 컴파일된다.
그러면 두 가지가 따라온다 — 생성 코드의 성능 특성이 손으로 쓴 Go와 달라질 수 있고,
디버깅과 스택 트레이스와 프로파일링이 원본이 아닌 생성 코드를 가리킨다.
소스 맵이나 디버그 정보 대응에 대한 언급이 홈페이지에 없다.

상호운용의 방향성도 불분명하다.
“어떤 Go 라이브러리든 직접 쓸 수 있다”는 Soppo에서 Go를 부르는 방향이다.
반대 방향 — 기존 Go 코드베이스가 Soppo로 쓴 부분을 부르는 것 — 은 “기존 프로젝트에
점진적으로 도입”이라는 약속의 전제인데, 그 경우 Soppo의 합 타입과 nilable 타입이
Go 쪽에 어떤 모습으로 보이는지가 문제가 된다.
점진적 도입이 실제로 가능한지는 이 질문의 답에 달려 있고, 홈페이지는 답하지 않는다.

### 설치 경로가 두 개의 이질적 툴체인을 요구하는데 그것을 장점처럼 서술한다

권장 경로는 `curl | sh`로 SOPMOD를 받는 것이고, 대안은 Cargo로 설치하는 것인데 후자는
Rust와 Go가 모두 필요하다.
즉 이 언어를 쓰려면 Go 툴체인과, 컴파일러 자체가 Rust로 되어 있으므로 상황에 따라
Rust 툴체인까지 필요하다.

홈페이지는 이것을 유연성으로 제시한다 — SOPMOD가 버전 관리와 Go 관리를 다 해 준다는
것이다.
그러나 도입 결정을 하는 팀 관점에서 이것은 의존성 표면의 확장이다.
CI 이미지가 Go와 Soppo 컴파일러 배포를 함께 담아야 하고, 두 툴체인의 버전 호환
행렬이 생기고, 재현 가능한 빌드를 위해 SOPMOD 자체를 고정해야 한다.

`curl -fsSL ... | sh`를 권장 설치 경로로 제시하는 것도 기업 도입 관점에서는 마찰이다.
서명된 배포물, 패키지 관리자 등록, 체크섬, SBOM에 대한 언급이 없다.
“기존 툴체인을 유지한다”는 약속과 “새 버전 관리자를 설치하라”는 안내가 나란히 있는
것이 이 홈페이지의 긴장이다.

### 홈페이지가 보여주는 것과 판단에 필요한 것 사이의 간극

이 사이트는 잘 만들어졌고 예제가 짧고 명료하다.
그런데 언어 채택을 검토하는 사람에게 필요한 정보는 거의 없다.

빠진 항목을 열거하면 그 규모가 보인다 — 언어 명세나 안정성 정책, 버전 번호와 릴리스
이력, 하위 호환 약속, 제네릭 지원 여부와 형태, 동시성 모델(고루틴과 채널이 그대로
쓰이는지, 합 타입과 어떻게 상호작용하는지), 표준 라이브러리의 범위, 편집기·LSP 지원,
빌드 시간, 생성 코드의 성능 오버헤드, 라이선스, 유지 주체와 후원 여부.
Playground와 Docs 링크가 있으므로 일부는 그 안에 있을 수 있지만, 랜딩 페이지가
“이 언어를 지금 써도 되는가”에 대한 어떤 신호도 주지 않는다.

특히 성숙도 표시의 부재가 눈에 띈다.
알파인지 베타인지, 프로덕션 사용 사례가 있는지, 문법이 아직 바뀔 수 있는지에 대한
언급이 없다.
언어 프로젝트에서 이 정보는 겸손의 문제가 아니라 사용자 보호의 문제다 — 문법이 바뀔
수 있는 언어로 코드를 쓴 사람은 나중에 그 비용을 지불한다.
홈페이지가 “기존 프로젝트에 점진적으로 도입하라”고 권하면서 성숙도를 밝히지 않는
것은 그 비용을 계산하지 못하게 만든다.

## 인사이트

### Go를 겨눈 개선 언어들이 반복적으로 실패한 지점은 문법이 아니라 커뮤니티 규범이다

Go에 합 타입과 오류 전파를 더하려는 시도는 Soppo가 처음이 아니다.
트랜스파일러, 코드 생성기, 제안서, 실험 언어가 10년간 이어졌고 대부분 흔적을 남기지
못했다.
기술적 난이도가 아니라 채택 논리에서 막혔다는 점이 이 계보의 특징이다.

Go 사용자층의 상당 부분이 Go를 선택한 이유는 기능이 부족해서다.
팀이 커질 때 코드 스타일이 갈라지지 않고, 새 사람이 2주 만에 기여할 수 있고, 어떤
코드베이스를 열어도 같은 관용구가 나온다는 것이 그 선택의 실질적 이득이었다.
이 이득은 언어에 표현력을 더하면 그만큼 줄어든다 — 합 타입과 패턴 매칭이 있으면
같은 문제를 푸는 방식이 두 가지가 되고, 코드 리뷰에서 스타일 논쟁이 생긴다.

그러므로 Soppo가 부딪힐 문제는 “Go 개발자가 이 기능을 원하는가”가 아니라 “Go를
선택한 조직이 이 기능을 원하는가”다.
개인 개발자는 대체로 원하고, 조직은 대체로 원하지 않는다.
그리고 언어 채택 결정은 조직이 한다.

이 구조가 시사하는 것은 Soppo의 실제 시장이 Go 사용자 전체가 아니라 그 안의 특정
층이라는 것이다 — Go로 혼자 또는 소규모로 일하며 Go의 장황함을 비용으로만 느끼는
사람들, 그리고 Rust를 쓰고 싶지만 학습 곡선이나 컴파일 시간 때문에 못 쓰는 사람들.
이 층은 실재하지만 언어 생태계를 지탱하기에는 작을 수 있고, 그래서 이런 프로젝트들이
기술적으로 훌륭한 상태에서 유지보수가 멈추는 패턴이 반복된다.

Lobste.rs에서 이 우려가 그대로 표현되었다 — Go 팀이 그냥 이 변경들을 채택하면 좋겠고
Go가 완벽한 언어가 될 수 있는데, Soppo는 훌륭하지만 안타깝게도 널리 채택될 가능성이
꽤 낮으며 그것이 결국 이런 프로젝트를 죽인다는 것이다.[^zknd]
그런데 이 전제를 되물은 댓글이 더 흥미롭다 — Soppo가 읽을 수 있는 Go 코드를 뱉는
것처럼 보이는데 왜 널리 채택되어야 하느냐, 저자 자신의 도구로 남아도 저자에게는
여전히 유용할 수 있다는 것이다.[^jmiven]
이 반문이 정확한 이유는 트랜스파일러의 생존 조건이 일반 언어와 다르다는 데 있다 —
생성물이 대상 언어의 정상적인 코드이면 프로젝트가 멈춰도 만들어 놓은 코드는 계속
빌드되고, 최악의 경우 생성된 Go로 이주하면 된다.
즉 이 설계는 채택 실패의 비용까지 낮춰 놓았고, 그것이 “점진적 도입”이라는 약속의
숨은 절반이다.

같은 스레드에서 이 공간에 이미 여러 시도가 있다는 것도 드러났다 —
[Lisette](./lisette.md)가 나란히 언급되었고, 두 언어의 Go 개선이 문법만 다르고 거의
동일하다는 관찰이 붙었다.[^quad]
dingolang과의 유사성도 지적되었다.[^adaszko]
같은 문제를 같은 방식으로 푸는 프로젝트가 셋 이상 동시에 존재한다는 사실은 수요가
실재한다는 증거이면서, 동시에 그 수요가 하나로 모이지 못한다는 증거이기도 하다 —
한 참여자가 이 종류의 것에 대한 갈망이 상당히 많아 보이지만 모두가 하나의 노력으로
결집하려면 진짜 애를 써야 한다고 적은 것이 그 진단이다.[^Student]

### 에이전트가 코드를 쓰는 시대에 “장황함”의 비용 구조가 바뀐다

`if err != nil`을 없애자는 요구의 근거는 언제나 두 가지였다 — 쓰기 귀찮다는 것과 읽기
어렵다는 것이다.
전자가 훨씬 자주 인용되었고, Soppo 홈페이지의 “No more repetitive if err != nil
blocks”도 전자를 겨눈다.

그런데 코드 작성의 상당 부분이 에이전트로 옮겨 가면 전자의 비용이 사라진다.
반복적인 오류 검사 블록을 쓰는 것은 에이전트에게 부담이 아니고, 오히려 패턴이
규칙적이므로 정확하게 생성된다.
남는 것은 후자, 즉 읽기 비용이다.

그리고 읽기 비용에 대해서는 판단이 갈린다.
`if err != nil` 블록이 화면을 채우면 실제 로직의 밀도가 낮아져 읽기 어렵다는 주장이
있고, 반대로 오류 경로가 눈에 보여 검토하기 쉽다는 주장이 있다.
후자는 에이전트 시대에 오히려 강해진다 — 생성된 코드에서 확인해야 할 것이 정확성이고,
오류 처리 누락은 가장 흔한 결함 유형이기 때문이다.
`?` 한 글자로 압축된 전파는 쓰기에 편하지만 “이 오류를 여기서 삼켜야 했나”라는 질문을
덜 던지게 만든다.

이 재계산은 Soppo뿐 아니라 최근의 언어 설계 트렌드 전반에 적용된다.
지난 15년간 언어 개선의 지배적 방향은 보일러플레이트 제거였고, 그 가치는 사람이
타이핑한다는 전제에 걸려 있었다.
전제가 흔들리면 우선순위가 검증 가능성 — 명시성, 지역적 추론 가능성, 컴파일러가
잡아 주는 오류의 범위 — 으로 이동한다.
흥미롭게도 Soppo의 기능 목록 중 절반은 이 새 기준에서도 유리하다 — 망라적 패턴
매칭과 nil 추적은 컴파일러가 잡아 주는 오류를 늘린다.
반면 `?` 연산자와 문자열 보간은 타이핑을 줄이는 쪽이다.
같은 언어 안에 두 시대의 설계 논리가 섞여 있는 셈이다.

### 컴파일 대상이 다른 고수준 언어라는 선택은 이득을 앞당기고 비용을 뒤로 미룬다

Soppo는 Go로 컴파일한다.
이 결정 덕에 프로젝트는 백엔드, 최적화기, 가비지 컬렉터, 런타임, 표준 라이브러리,
크로스 컴파일, 플랫폼 지원을 전부 공짜로 얻는다.
1인 또는 소규모 팀이 언어를 만들 수 있게 하는 유일한 현실적 경로이기도 하다.

같은 전략의 역사는 길고 결말이 두 갈래다.
성공한 쪽은 대상 언어가 사실상 플랫폼이 된 경우다 — TypeScript는 JS로, Kotlin은
JVM 바이트코드로, Elixir는 BEAM으로 컴파일하면서도 일급 언어로 인정받았다.
막힌 쪽은 대상 언어의 의미론이 원본을 제약한 경우다 — CoffeeScript는 JS의 의미론을
넘을 수 없었고 TypeScript가 타입만 더하는 전략으로 이겼으며, C로 컴파일한 여러 언어는
디버깅 경험 때문에 채택이 정체되었다.

갈림길을 결정하는 것은 대상 언어가 표현할 수 없는 것을 언제 만나는지다.
Soppo의 현재 기능 목록은 Go로 표현 가능하다 — 합 타입은 태그 구조체로, 패턴 매칭은
분기로, nil 추적은 컴파일 시점 검사이므로 런타임 표현이 필요 없다.
문제는 다음 단계다 — 제네릭의 특수화, 꼬리 호출 최적화, 코루틴 이외의 동시성 모델,
효과 추적, 선형 타입 같은 것을 원하게 되면 Go가 벽이 된다.

그러므로 이 프로젝트의 장기 궤적을 예측하는 질문은 문법이 얼마나 좋은지가 아니라
야심의 상한이 어디인지다.
“Go에 빠진 기능을 더한다”로 범위를 유지하면 이 전략은 계속 유효하다.
독자적 언어로 자라려 하면 어느 시점에 백엔드를 다시 만들어야 하고, 그 비용은 지금
아낀 것보다 크다.
홈페이지의 겸손한 위치 설정 — 대체가 아니라 보완, 전환이 아니라 점진적 도입 — 이
전략적으로 정확한 이유가 여기 있다.

### 진단 메시지 품질이 언어 선택 기준으로 올라온 것은 최근 10년의 변화다

홈페이지가 별도 섹션을 할애해 오류 메시지 렌더링을 보여주는 것은 눈여겨볼 만하다.
소스 코드 인용, 문제 지점 표시, 누락된 변종의 명시, `help:` 제안까지 담긴 그 출력은
그 자체로 판매 논점으로 제시된다.

10년 전 언어 랜딩 페이지에서 이런 섹션은 상상하기 어려웠다.
당시의 판매 논점은 성능, 표현력, 안전성, 생태계였고 진단 품질은 구현 세부였다.
이 전환을 만든 것은 Rust와 Elm이다 — Elm이 친절한 오류 메시지를 정체성으로 삼았고,
Rust가 그것을 산업 규모로 증명하면서 “컴파일러가 가르쳐 준다”는 것이 채택 이유가
되었다.

이 변화의 함의는 언어의 학습 곡선이 문법의 함수가 아니라 도구의 함수라는 것이다.
같은 타입 시스템이라도 오류 메시지가 무엇을 어디서 어떻게 고치라고 알려주면 학습
비용이 크게 줄고, 그러지 않으면 표현력이 곧 진입 장벽이 된다.
Soppo가 Go의 단순성을 포기하고 표현력을 더하면서 진단 품질을 나란히 내세운 것은
이 계산을 의식한 배치로 읽힌다.

그런데 여기서 덜 논의되는 대칭이 있다.
좋은 진단 메시지는 사람의 학습 곡선을 낮추지만, 에이전트에게는 다른 방식으로 작동한다 —
구조화된 오류 출력은 에이전트가 스스로 고치는 루프의 품질을 직접 결정한다.
`missing variants: Green`처럼 무엇이 빠졌는지 기계가 파싱할 수 있게 알려주는 컴파일러는
에이전트의 수정 성공률을 올린다.
그러므로 진단 품질은 이제 두 종류의 사용자를 동시에 위한 기능이며, 앞으로의 언어
경쟁에서 사람이 읽기 좋은 형식과 기계가 읽기 좋은 형식(`--message-format=json`
같은 것)을 함께 제공하는지가 차별점이 될 것이다.
Soppo 홈페이지는 전자만 보여주고 후자에 대해서는 말하지 않는다.

문법의 사소해 보이는 선택이 오래 남는다는 것도 이 스레드가 보여주었다.
Lobste.rs 논의의 상당 부분이 문자열 보간 문법에 집중되었는데, 더 많은 언어가 백슬래시로
보간을 시작하면 좋겠다는 제안이 그 출발이었다 — Swift의 `“Time: \(t) seconds”`처럼
말이며, 맨 `{}`를 쓰면 `{}` 자체를 출력할 때 곤란하고 `{{`와 `}}`라는 새로운 이스케이프
종류가 생기는데 우리는 이미 백슬래시를 이스케이프용으로 예약해 두었으니 모든 것에
백슬래시를 쓰는 것이 더 일관적이라는 논지다.[^hmry]
Ninja에서 `$`를 보편 이스케이프 문자로 삼아 같은 문제를 해결했다는 응답이 이어졌고,
그 덕에 윈도우 경로의 백슬래시를 이스케이프할 필요가 없어졌다는 부수 효과까지
보고되었다.[^evmar]
반대편에서는 순수 포맷팅에서 `{}`가 `%`보다 나은 이유로 지정자 문법의 끝이 명확해
제약이 덜하다는 반론이 나왔다.[^foonathan]
최상위 댓글의 지적 — 문자열 보간이 선택이 아니라 보편적으로 켜져 있는 것이 짜증의
원인이 될 수 있다는 것 — 도 같은 축에 있다.[^nemin]
이 논쟁이 언어 설계 논의에서 반복적으로 큰 지면을 차지하는 이유는 문법 취향 때문이
아니라, 이스케이프 규칙이 한 번 정해지면 그 언어로 쓰인 모든 문자열에 영향을 주고
되돌릴 수 없기 때문이다.
