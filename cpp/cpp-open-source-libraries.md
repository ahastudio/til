# 오픈 소스 C++ 라이브러리 목록

원문: [C++ 오픈 소스 라이브러리 목록](https://ko.cppreference.com/cpp/links/libs)

GN 토론: <https://news.hada.io/topic?id=31933>

## 요약

cppreference.com 한국어판이 "특정 기능을 구현하기 위해 구글링하는 시간을
낭비하지 않도록" 취합한, 카테고리별 오픈소스 C++ 라이브러리 목록이다.
누구나 편집할 수 있는 위키 문서이며, 소스 형태로 내려받을 수 있다는 것
외에는 등재 조건이 없다고 밝히고 있다.

분류는 매우 세분화되어 있다. 범용 라이브러리(Boost, Folly, Dlib, JUCE),
통신·네트워킹(Boost.Asio, POCO, ZeroMQ, cpp-netlib, Apache Thrift), GUI
(Qt, GTK+, wxWidgets, FLTK), 멀티미디어·그래픽(SFML, SDL, OpenCV, Cairo),
3D 그래픽스(OpenGL, GLFW, GLM, Ogre3D, bgfx, Magnum)까지 이어진다.

수학·수치연산 쪽은 특히 두텁다. 선형대수(Eigen, Armadillo, Boost.uBLAS),
그래프 이론(Boost.Graph, LEMON), 기계학습(MLPACK, Shogun, liblinear),
계산기하(CGAL, PCL), 동시성·병렬 연산(Intel TBB, OpenMP, Thrust, HPX)까지
세부 분야별로 라이브러리를 나눠 놓았다.

그 외에도 컨테이너(Boost.Container류), 직렬화(protobuf, cereal, yaml-cpp),
테스팅(Google Test, Catch, cppunit), JSON(rapidjson, jsoncpp, nlohmann
계열 이전의 여러 구현체), 데이터베이스(libpqxx, SOCI, ODB), 암호화(OpenSSL,
Botan, Crypto++), 텍스트 파싱(PEGTL), 임베디드/실시간(FreeRTOS 핸들러,
ETL), 로그(spdlog, log4cpp, plog)까지 실무에서 마주치는 거의 모든 영역을
카테고리로 나눠 링크만 나열하는 형식이다. 각 항목에 짧은 한 줄 설명과
라이선스가 함께 표기된 경우도 있지만, 설명 없이 이름만 적힌 항목도 상당수다.

## 분석

### 이런 링크 모음의 가치는 내용이 아니라 "최신성"에 있다

이 문서는 위키미디어 기반이라는 형식 자체가 내용의 신뢰도를 좌우한다.
"페이지는 그냥 있는 그대로 제공된다"는 면책 문구가 위키 상단에 적혀 있듯,
편집자가 나타나지 않으면 그대로 방치된다. GeekNews에서 t7vonn은 "한국판은
마지막 업데이트가 16년 전이라 원문을 보는 것이 좋을 듯 하다"며 영어
원본(cppreference.com/cpp/links/libs)을 참고하라고 지적했다.[^t7vonn]
이는 번역·미러 사이트가 원본과 별개로 방치되기 쉬운 구조적 문제를 보여주는
사례로, C++ 생태계처럼 표준화 위원회 중심으로 느리지만 꾸준히 변화하는
분야에서도 참고 문서의 신선도는 별도로 검증해야 한다는 점을 시사한다.
dieafterwork는 이 지적에 "cppreference 한국 사이트가 있는지 이 글을 보고
처음 알아서 반가웠는데, 기존대로 영문 사이트를 이용해야겠다"고 답해,
한국어 미러의 존재 자체가 널리 알려져 있지 않았다는 점도 함께
드러났다.[^dieafterwork]

### 분류 체계 자체가 2000년대 C++ 생태계의 화석이다

목록의 카테고리 구성을 보면 이 문서가 만들어진 시대를 짐작할 수 있다.
JSON 파서만 십수 개가 나열되어 있는데(jsoncpp, rapidjson, jsoncons,
json11, jansson 등), 이는 C++11 전후 표준 라이브러리에 JSON 지원이
전무해 각자 바퀴를 재발명하던 시기의 흔적이다. 반대로 오늘날 사실상
표준처럼 쓰이는 nlohmann/json이나 simdjson은 목록에 없다. 마찬가지로
"임베디드 언어 바인딩"에 ChaiScript, AngelScript, Lua가 나란히 오르고
"동시성" 항목에 Boost.MPI, Boost.Context가 병렬로 걸려 있는 구성도,
C++11 표준 스레드 라이브러리가 막 자리잡기 시작하던 시절의 문제의식을
반영한다. 즉 이 목록은 특정 시점 C++ 생태계의 "지층"을 그대로 보존한
화석에 가깝고, 그 지층이 몇 년 치인지는 각 카테고리마다 다르다.

### 링크만 나열하는 형식은 선택의 부담을 독자에게 전가한다

같은 문제 영역에 여러 라이브러리가 설명 없이 나란히 걸려 있을 때(예:
JSON 파서 15종, XML 파서 5종), 독자는 이름만 보고는 어느 것을 골라야
할지 판단할 근거가 없다. 일부 항목에는 "부스트 라이선스", "GPL 라이선스"
같은 라이선스 정보나 한 줄 설명이 붙어 있지만, 대다수는 이름과 링크
뿐이다. 이는 "목록을 만드는 것"과 "선택을 돕는 것"이 서로 다른 작업이라는
점을 보여준다. 이 문서는 전자에만 충실하고 후자는 전혀 다루지 않는다.

## 비평

### "빠짐없이 모은다"는 목표와 "쓸모 있게 고른다"는 목표가 충돌한다

목록형 문서는 검색 편의성은 높지만, 어떤 라이브러리가 활발히 유지보수되고
있는지, 최근 C++20/23 기능과 얼마나 잘 통합되는지에 대한 정보가 빠져 있으면
오히려 오래된 선택을 유도할 위험이 있다. 특히 이 문서는 "삭제"보다
"추가"에 편향된 위키 구조를 갖고 있다. 새 라이브러리는 계속 추가되지만,
죽은 프로젝트나 후속 라이브러리에 밀린 항목을 걷어내는 작업은 거의
이뤄지지 않는다. 그 결과 시간이 지날수록 목록은 길어지지만 밀도는
낮아지는 방향으로만 움직인다. 링크 모음을 참고할 때는 각 라이브러리의
GitHub 저장소에서 최근 커밋·이슈 활동을 직접 확인하는 편이 안전하다.

### 일부 카테고리는 이미 표준 라이브러리에 흡수됐다는 사실을 반영하지 않는다

"컨테이너" 항목에 나열된 Boost.Any, Boost.Variant, Boost.Optional류는
각각 C++17의 std::any, std::variant, std::optional로 표준에 편입됐고,
"동시성" 항목의 std::thread·std::atomic도 이미 오래전에 표준화됐다.
그런데도 목록은 여전히 Boost 확장판을 마치 유일한 선택지처럼 나열한다.
표준에 흡수된 기능인지 여부를 표시하지 않는 것은 단순한 누락이 아니라,
독자에게 불필요한 외부 의존성을 추가하게 만들 수 있는 실질적인 위험이다.
C++ 표준 자체가 계속 라이브러리 기능을 흡수해 온 역사를 감안하면, 이런
목록은 "표준화되지 않은 것만" 걸러 보여주는 편이 훨씬 유용했을 것이다.

## 인사이트

### 위키형 목록은 "추가 편향"이라는 하나의 메커니즘으로 노화한다

이런 위키형 목록의 노화 방식은 무작위가 아니라 구조적으로 예측 가능하다.
새 라이브러리를 추가하는 행위는 편집자에게 성취감을 주는 긍정적 기여이지만,
죽은 프로젝트를 목록에서 걷어내는 행위는 아무 보상도 없는 궂은일이다.
이 비대칭은 위키피디아의 문서 비대화 현상이나 GitHub의 awesome-* 리스트가
시간이 지날수록 죽은 링크로 가득 차는 현상과 정확히 같은 메커니즘이다.
즉 "이 목록이 오래됐다"는 사실 자체는 예외가 아니라, 이런 형식의 문서가
반드시 도달하게 되는 정상 상태에 가깝다. 따라서 목록형 문서를 참고할 때는
개별 항목의 최신성을 매번 의심하기보다,애초에 "이 형식의 문서는 구조적으로
낡아간다"는 전제를 깔고 접근하는 편이 효율적이다.

### C++ 표준의 흡수 이력이 목록의 유효기간을 예측하는 단서가 된다

C++ 표준위원회는 검증된 서드파티 아이디어를 표준에 편입시켜 온 오랜
역사가 있다. Boost의 상당수 라이브러리(any, variant, optional, filesystem,
thread 일부)가 이후 표준에 흡수된 사례가 이를 보여준다. 이 흐름을
알고 있으면, "지금 존재하는 서드파티 라이브러리 카테고리 중 어느 것이
다음 표준에 흡수될 가능성이 높은가"를 역으로 추론할 수 있다. 예를 들어
JSON 파싱이나 네트워킹처럼 여러 라이브러리가 각자 표준화를 시도해 온
영역은, 표준 라이브러리가 결국 그 자리를 차지할 후보가 된다. 이런 관점을
가지면 목록에 오른 항목을 볼 때 "이게 얼마나 오래 유효할 도구인가"까지
가늠할 수 있어, 단순히 최신 버전을 확인하는 것보다 한 단계 더 나아간
판단이 가능해진다.

### 큐레이션 없는 목록은 결국 검색 엔진에 자리를 내준다

이 문서가 원래 해결하려던 문제는 "구글링하는 시간을 낭비하지 않도록"
하는 것이었지만, 역설적으로 오늘날에는 이런 목록보다 검색 엔진이나 LLM에
직접 물어보는 편이 더 최신 정보를 준다. 위키형 링크 모음이 가진 유일한
비교우위는 사람이 수작업으로 선별했다는 신뢰감이었는데, 선별 이후
갱신이 멈추면 그 비교우위마저 사라진다. 이는 사람이 큐레이션한 정적
콘텐츠가 동적으로 갱신되는 검색·생성형 도구에 자리를 내주는 더 큰
흐름의 축소판이며, 이런 목록이 살아남으려면 콘텐츠 자체보다 "누가,
얼마나 자주 갱신을 책임지는가"라는 운영 구조가 관건이라는 점을
보여준다.
