# Go url.Error의 쿼리 문자열 로그 누출 막기

원문: [Go url.Error가 쿼리 문자열을 로그에 남기는 경로와 마스킹 방법](https://velog.io/@commitlog/go-url-error-query-masking)

GN 토론: <https://news.hada.io/topic?id=37086>

## 요약

velog의 commitlog가 쓴 글이다.
날짜 표기가 엇갈려, velog 본문은 2026년 11월 7일이고 GeekNews 토픽은 발행일을 11월 13일로 적는다.
글은 외부 API 요청이 응답을 받기 전에 실패하면 Go의 `*url.Error`가 쿼리 문자열에 실린 계좌번호까지 로그에 남기는 문제와 그 마스킹 방법을 다룬다.
실제 계좌로 전환하기 전의 점검에서 한 로그 파일에 4,899줄이 나왔고 그것은 테스트용 계좌 두 개의 번호였다고 한다.

## 원인

기준은 Go 1.25와 `http.Client`의 `Timeout`이다.

- 계좌 조회가 GET이라 계좌번호가 쿼리 문자열에 실린다.
- `http.Client`는 응답 전 실패(timeout, connection refused)에서 `*url.Error`를 돌려주는데 `URL` 필드에 쿼리까지 들어 있다. 표준 라이브러리가 지우는 것은 URL 속 비밀번호뿐이다.
- 글쓴이는 이 에러를 감싸 경고 로그로 남기고 있었다. 로그에는 `account=...`가 든 요청 URL과 `context deadline exceeded (Client.Timeout exceeded while awaiting headers)`가 함께 찍혔다.
- 비밀 값을 가리는 함수는 이미 있었지만 메신저 알림 경로에만 붙어 있었고 가리는 대상도 봇 토큰 하나였다. 로그 파일로 가는 조회 실패 에러는 이 함수를 거치지 않았다.

## 해결

글의 선택은 가릴 파라미터 목록을 관리하지 않고 쿼리 문자열을 통째로 버리는 것이다. 목록은 새 파라미터가 생길 때마다 고쳐야 하고 한 번 빠뜨리면 다시 샌다는 이유이다. 대가는 다른 조회의 쿼리 조건도 로그에서 빠진다는 것이다.
에러를 문자열로 바꾸지 않고 같은 `*url.Error` 타입으로 다시 만들어 `Op`와 `Err`를 그대로 복사한다. 그래서 `errors.As`나 `Timeout()`으로 원인을 묻는 코드는 수정 전과 같은 값을 받는다.

글이 설명한 논리를 옮긴 예시는 다음과 같다. 함수 이름 `redactURLError`는 글이 쓴 것이다.

```go
func redactURLError(err error) error {
	var ue *url.Error
	if !errors.As(err, &ue) {
		return err
	}
	u := ue.URL
	if i := strings.IndexByte(u, '?'); i >= 0 {
		u = u[:i]
	}
	return &url.Error{Op: ue.Op, URL: u, Err: ue.Err}
}
```

`*url.Error`가 아니면 원래 에러를 그대로 돌려준다.
200이 아닌 응답은 같은 메시지에 body 전체가 실리고 있었다. 계좌번호가 돌아온 적은 없지만 응답이 보낸 값을 되돌려 줄 가능성을 배제하지 못해, 오류 코드 같은 진단 필드만 남기고 형식을 모르는 body는 길이만 기록한다.

## 테스트

수정 전에 실패하는 테스트 세 개를 만들었다. 연결 거부, 재시도 중 timeout, 서버가 계좌번호를 되돌려 주는 경우이다. 세 경우 모두 메시지에 계좌번호, 필드 이름, `?`가 없는지 확인한다.
없어야 할 것만 검사하면 전부 지우는 코드도 통과하므로, 연결 거부 경우는 경로와 원인이 남는지, 되돌려 주는 경우는 오류 코드가 남는지도 함께 확인한다.

## 남은 일

이 수정은 앞으로 새로 쌓이는 로그만 막는다. 이미 찍힌 줄의 처리는 따로 정하기로 했고 배포 뒤 줄 수가 늘었는지 다시 세겠다고 한다. 결론은 외부 호출 에러를 로그에 남기기 전에 URL을 통째로 들고 있는지 확인하라는 것이다. 글에는 같은 사례를 화면으로 따라가는 영상 링크도 있다.

## 비평

### 쿼리 전체 삭제의 대가가 크다

글도 인정하듯 쿼리를 통째로 버리면 장애 분석에 필요한 조건이 사라진다. GeekNews에서 한 이용자는 허용할 키만 남기는 방식을 제안했고 글쓴이는 다르게 처리한 경험을 듣고 싶다고 답했다.[^eggkmc3][^commitlog]
허용 목록 방식은 새 파라미터가 생길 때 빠뜨리지 않는 대신 목록 관리가 필요하다. 글은 두 방식을 비교하지 않는다.

### 원인의 범위가 좁게 서술된다

글의 경로는 `*url.Error`를 로그에 직접 남긴 경우이다.
같은 URL이 다른 경로로 새는 경우(요청 로깅 미들웨어, 트레이싱, 프록시 로그)는 글의 범위 밖이다.

### `errors.As`가 에러를 찾는 범위가 열려 있다

`errors.As`로 `*url.Error`를 찾는 방식은 에러가 다른 타입으로 한 번 더 감싸일 때 `Unwrap`이 이어지는지에 달려 있다.

### 외부 반응

GeekNews 토픽에는 위의 댓글 둘이 있다. HN에는 이 글 주소로 올라온 글이 없었다(대조 쿼리는 정상이었다). Lobste.rs의 `velog.io` 도메인에는 글이 없었다.

## 기억할 원칙

- 외부 호출 에러를 로그에 남기기 전에 URL과 쿼리, 요청 본문, 응답 본문이 들어 있는지 확인한다.
- 비밀 값 마스킹은 알림 경로와 로그 파일 경로를 모두 지나게 한다.
- 가릴 키 목록보다 통째로 버리거나 허용 목록으로 남기는 방식을 택한다. 대가가 장애 분석 정보임을 알고 선택한다.
- 에러를 문자열로 바꾸지 말고 같은 타입으로 다시 만들어 `errors.As`와 `Timeout()`이 유지되게 한다.
- 지워야 할 것이 지워졌는지와 남아야 할 것이 남았는지를 함께 시험한다.
