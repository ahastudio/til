# LLGo: Go를 C 생태계에 붙이려고 만든 LLVM 기반 컴파일러

<https://github.com/xgo-dev/llgo>

HN 토론: <https://news.ycombinator.com/item?id=49486828> (3점, 4개 댓글)

GN 토론: <https://news.hada.io/topic?id=33302>

## 소개

LLGo는 LLVM 기반의 Go 컴파일러다.
README의 첫 문장이 목적을 밝힌다 — Go를 C 생태계와 더 잘 통합하기 위한 것이고, 그 C 생태계에는 Python과 JavaScript가 포함된다.
XGo 프로젝트의 하위 프로젝트다.

프로젝트가 스스로를 요약하는 방식은 등식 하나다.

```text
LLGo := Go * C ecosystem
```

LLGo는 C의 애플리케이션 바이너리 인터페이스(ABI)를 통해 C 생태계와 호환되고, 소스 코드 수준에서 Go와 호환된다.
여기서 말하는 C 생태계는 C 호환 인터페이스를 노출하는 언어들 — C/C++, Python, JavaScript, Objective-C, Swift — 을 뜻한다.

넓히려는 경계로 게임 개발, AI와 데이터 과학, WebAssembly, 임베디드 개발을 든다.

2026년 9월 기준 별 750개, 포크 50개이고 라이선스는 Apache 2.0이다.
저장소는 원래 `goplus/llgo`였다가 `xgo-dev/llgo`로 옮겨졌다.
그리고 이름이 같은 옛 프로젝트가 따로 있다 — 2010년대 초 LLVM 하위 프로젝트였던 `axw/llgo`인데, 지금 이 프로젝트와는 관계가 없다.

## Go 호환성과 런타임

LLGo는 Go 1.20 이상 소스 코드와 호환되며 Go 1.27 언어 문법 전체와 `cgo`를 지원한다고 밝힌다.

컴파일러 호환성은 고정된 Go 1.27 툴체인으로 상위 `GOROOT/test` 케이스를 돌려 확인한다.
사용자 프로젝트와 `test/` 아래 패키지는 Go 1.20부터 1.27까지의 정확한 툴체인으로 추가 테스트한다.
남은 차이는 `xfail.yaml`에 기록되고, LLGo의 호환 목표 바깥에 있는 gc 특유의 메커니즘은 `notapplicable.yaml`에 문서화된다.

런타임은 표준 Go 툴체인과 다르다.
네이티브 고루틴이 OS 스레드에 1:1로 매핑되고 고정된 네이티브 스택을 쓴다.
그래서 C를 직접 호출할 때 Go에서 C로의 스택 전환이나 스케줄러 전환이 필요 없고, 표준 Go에서 잦은 C 호출을 비싸게 만드는 cgo 오버헤드를 피한다는 설명이다.

기본 가비지 컬렉터는 보수적(conservative) BDWGC(libgc)다.
베어메탈 임베디드 타깃에서는 TinyGo에서 파생된 보수적 mark-and-sweep 컬렉터를 쓴다.
`nogc` 빌드 태그로 가비지 컬렉션을 끌 수 있다.

```sh
llgo run -tags nogc .
```

표준 라이브러리는 지원되는 네이티브 플랫폼에서 완전히 지원된다고 밝힌다.
CI가 주 Go 툴체인의 모든 공개 패키지와 익스포트된 심볼에 대한 호환성 커버리지를 요구하며, 더 오래된 지원 툴체인마다 `test/std` 호환성 세트를 돌린다.

타깃별 커버리지는 표로 정리되어 있다.

| 타깃        | 현재 커버리지                                                                                                            |
| ----------- | ------------------------------------------------------------------------------------------------------------------------ |
| Native      | Linux amd64/arm64, macOS amd64/arm64, Windows amd64/arm64(MSVC·MinGW) 릴리스 빌드. 주 CI는 Linux amd64, macOS arm64, Windows |
| WebAssembly | `js/wasm`과 `wasip1/wasm` 빌드. WASI와 Emscripten CI 커버리지                                                             |
| Embedded    | 지원 보드와 MCU를 위한 `-target` 구성, 선택된 QEMU/에뮬레이터 스모크 테스트                                                |

WebAssembly 타깃 이름은 Go 소스 태그와 독립적으로 생태계 C ABI를 고른다.
`-target emscripten`은 ES 모듈과 그 짝인 wasm32 모듈을 내보내고, `-target emscripten-memory64`는 LP64 C 데이터 모델로 같은 쌍을 내보내며, `-target wasi`/`-target wasip1`은 WASI Preview 1 모듈을 내보낸다.
`GOOS=js/wasip1 GOARCH=wasm`은 표준 Go 플랫폼 ABI와의 수렴을 위해 남겨둔 별도 호환 경로다.

## C/C++ 연동

LLGo는 래퍼나 cgo 오버헤드 없이 C/C++ 라이브러리를 직접 임포트하고 호출할 수 있다고 밝힌다.

연동 메커니즘은 `go:linkname`으로 Go 선언을 C ABI 심볼에 직접 바인딩하는 것이다.

```go
package main

import _ "unsafe" // for go:linkname

//go:linkname Sqrt C.sqrt
func Sqrt(x float64) float64

func main() {
	println("sqrt(2) =", Sqrt(2))
}
```

C 호출이 C ABI에 대한 네이티브 호출로 컴파일되므로 Go-C 스택이나 스케줄러 전환이 없고, 그래서 잦은 C 호출도 싸다는 것이다.

Windows에서는 `WINAPI`나 `__stdcall`로 선언된 API를 `stdcall.` 네임스페이스로 바인딩한다.
이 규약은 386에서만 구별되고 Windows amd64와 arm64는 통합된 네이티브 C ABI를 쓴다.
`_MessageBoxW@16` 같은 명시적으로 장식된 386 이름도 받아들이며 64비트 타깃에서는 `MessageBoxW`로 정규화된다.

```go
//go:linkname MessageBoxW stdcall.MessageBoxW
func MessageBoxW(hwnd uintptr, text, caption *uint16, flags uint32) int32

//llgo:type stdcall
type Callback func(context uintptr) uintptr
```

`stdcall.` 선언과 `//llgo:type stdcall`은 가변 인자가 아닌 함수 타입에만 적용된다.
네이티브 콜백은 함수 포인터 하나이므로 Go 콜백은 직접 함수 참조여야 하며, 상태는 캡처하는 클로저가 아니라 명시적인 컨텍스트 포인터로 전달해야 한다.

C/C++ 표준 라이브러리 바인딩은 `c`, `c/syscall`, `c/sys`, `c/os`, `c/math`, `c/math/cmplx`, `c/math/rand`, `c/pthread`, `c/pthread/sync`, `c/sync/atomic`, `c/time`, `c/net`, `cpp/std`로 제공된다.

```go
package main

import "github.com/goplus/lib/c"

func main() {
	c.Printf(c.Str("Hello world\n"))
}
```

`c.Str`는 Go 문자열을 C 문자열로 바꾸는 런타임 변환이 아니라 `llgo`가 인식해 C 문자열 상수로 직접 컴파일하는 내장 명령이라고 밝힌다.

표준 라이브러리 너머의 바인딩도 있다 — `c/bdwgc`, `c/cjson`, `c/clang`, `c/ffi`, `c/libuv`, `c/llama2`, `c/lua`, `c/neco`, `c/openssl`, `c/raylib`, `c/sqlite`, `c/zlib`, `cpp/inih`, `cpp/llvm`.
다만 이 바인딩들은 현재 손으로 관리하고 있으며, Python 라이브러리 임포트에서 이미 하고 있는 것처럼 자동화하는 것이 향후 계획이라고 적는다.

이 바인딩들로 만든 예제로 Llama 2 추론(`llama2-c`), JSON 생성, SQLite 데모, raylib 기반 테트리스를 든다.

## Python 연동

LLGo에서 Python 라이브러리를 임포트할 수 있다.
`llpyg`라는 도구로 바인딩을 만들며, `py`(abi), `py/std`, `py/sys`, `py/os`, `py/math`, `py/json`, `py/inspect`, `py/statistics`, `py/numpy`, `py/pandas`, `py/torch`, `py/matplotlib`가 제공된다.
pandas나 PyTorch 같은 서드파티 라이브러리는 따로 설치해야 한다.

```go
package main

import (
	"github.com/goplus/lib/py"
	"github.com/goplus/lib/py/math"
	"github.com/goplus/lib/py/std"
)

func main() {
	x := math.Sqrt(py.Float(2))
	std.Print(py.Str("sqrt(2) ="), x)
}
```

이것이 Python의 `import math; x = math.sqrt(2); print("sqrt =", x)`와 같다고 설명한다.
numpy로 3x3 행렬 두 개를 더하는 예제도 함께 제시한다.

## 의존성과 설치

의존성 목록이 길다 — 빌드용 Go 1.27, LLVM 22, Clang 22, LLD 22, LLDB, pkg-config 0.29+, bdwgc/libgc 8.0+, libffi, OpenSSL 3.0+, zlib 1.2+, 그리고 선택적으로 Python 3.12+.

macOS에서는 Homebrew로 `llvm@22`, `lld@22`, `bdw-gc`, `openssl`, `cjson`, `libffi`, `libuv`, `pkg-config`를 설치한 뒤 `install.sh`를 실행한다.
Homebrew의 버전별 LLVM 22 포뮬러에는 LLDB가 없고 `lldb@22` 포뮬러도 없으므로, LLGo가 일반적인 Homebrew·시스템 위치를 확인한 뒤 `PATH`의 `lldb`를 찾으며 `LLGO_LLDB`나 `llgo lldb -lldb`로 명시할 수 있다고 안내한다.

Debian/Ubuntu는 apt.llvm.org 저장소를 추가하고, Alpine과 Fedora 44+ 안내도 별도로 있다.
Fedora 43은 LLVM 21을 쓰므로 이번 릴리스의 지원 기본 툴체인 환경이 아니라고 명시한다.

Windows는 릴리스 워크플로가 네 가지 통합 변형을 ZIP으로 빌드한다 — amd64/arm64 각각에 MSVC와 MinGW다.
MSVC 컴파일러는 LLVM을 정적 링크하고, MinGW 아카이브는 네이티브 LLVM과 C++ DLL 의존성을 `llgo.exe` 옆에 포함한다.
번들된 ESP Clang은 ARM64 아카이브에서도 x64 Windows 페이로드 그대로이며 Windows의 x64 에뮬레이션으로 돌아가고, `llgo.exe` 자체는 그 아카이브에서도 네이티브 ARM64라고 밝힌다.

## 분석

### 이 프로젝트가 파는 것은 언어가 아니라 ABI 경계의 제거다

LLGo는 새 언어를 만들지 않는다.
Go 1.27 문법 전체를 지원하고 표준 라이브러리도 지원한다고 말하므로, 언어 층에서 얻는 것은 없다.

얻는 것은 호출 규약이다.
표준 Go에서 C를 부르려면 cgo를 거쳐야 하고, cgo 호출은 고루틴 스택에서 시스템 스택으로 넘어가며 스케줄러에 이 스레드가 블로킹될 수 있음을 알린다.
그 전환이 호출당 수백 나노초 수준의 비용을 만들고, 그래서 Go에서는 “C 호출을 배치로 묶어라”가 일반적인 조언이 된다.

LLGo의 설계는 그 비용을 아예 없애는 쪽이다.
고루틴을 OS 스레드에 1:1로 매핑하고 고정 네이티브 스택을 쓰면 전환할 것이 없기 때문이다.
`c.Printf(c.Str("..."))`가 그냥 네이티브 호출로 컴파일된다는 것이 이 프로젝트의 실질이다.

그러니 이것은 컴파일러 프로젝트라기보다 런타임 교체 프로젝트다.
그리고 교체된 런타임이 무엇을 포기했는지가 이 프로젝트를 평가하는 핵심 축이 된다.

### 고루틴 1:1 매핑이 Go의 정체성을 포기하는 결정이다

README는 1:1 매핑을 cgo 오버헤드 회피의 근거로 짧게 언급하고 넘어가지만, 이것은 Go에서 가장 특징적인 설계를 되돌리는 일이다.

Go의 고루틴이 싼 이유는 M:N 스케줄링과 작게 시작해 자라는 스택 때문이다.
수십만 개를 띄워도 되는 것은 각각이 몇 KB로 시작하고 사용자 공간에서 스케줄링되기 때문이며, 그 성질 위에 Go의 동시성 관용구 전체가 서 있다 — 요청당 고루틴, 채널로 파이프라인 구성, 블로킹 호출을 고루틴으로 감싸기.

1:1 매핑에 고정 네이티브 스택이면 그 계산이 전부 달라진다.
고루틴 하나가 OS 스레드 하나이므로 생성 비용이 수천 배가 되고, 동시 실행 수의 상한이 커널 한계로 내려온다.
`go handleRequest(conn)`을 연결마다 부르는 서버 코드는 문법적으로 컴파일되지만 운영 특성은 전혀 다른 프로그램이 된다.

README가 “Go 1.27 문법 전체 지원”과 “표준 라이브러리 완전 지원”을 앞세우면서 이 차이를 런타임 절의 한 문장으로 처리한 것이 이 문서의 가장 큰 균형 문제다.
소스 호환성과 동작 호환성은 다르고, 동시성이 핵심인 Go에서 그 차이가 특히 크다.

### 보수적 GC 선택이 대상 사용자를 규정한다

기본 가비지 컬렉터가 BDWGC라는 것도 같은 성격의 결정이다.
표준 Go는 정확한(precise) GC를 쓰고, 보수적 GC는 스택과 레지스터의 값이 포인터인지 정수인지 알 수 없으므로 포인터처럼 보이는 값을 전부 포인터로 취급한다.

결과는 두 가지다.
객체가 예상보다 오래 살아남을 수 있고(false retention), 그래서 메모리 사용이 예측하기 어려워진다.
그리고 객체를 옮길 수 없으므로 압축(compaction)이 불가능하고 단편화가 쌓인다.

이 선택이 불가피했던 이유는 짐작할 수 있다.
C ABI로 직접 넘어가는 포인터를 정확히 추적하려면 컴파일러가 모든 C 경계를 알아야 하는데, `go:linkname`으로 임의의 C 심볼에 바인딩하는 설계에서는 그것이 불가능하다.
C와 섞으려면 보수적 GC로 갈 수밖에 없다.

그래서 `nogc` 태그가 존재하는 것으로 보인다.
GC를 끄고 쓰라는 것은 사실상 수동 메모리 관리로 가라는 뜻이고, 그것을 감수할 사용자는 임베디드나 짧게 살다 끝나는 프로세스를 만드는 사람들이다.
README가 든 용도 — 게임, 임베디드, WebAssembly — 가 정확히 그 집합이다.

### 손으로 만든 바인딩이 이 접근의 실제 병목이다

C/C++ 바인딩 목록은 열네 개이고, 그 아래에 한 문장이 붙어 있다 — 바인딩은 현재 손으로 관리하며 자동화는 향후 계획이라는 것이다.

이 문장이 프로젝트의 현재 위치를 정확히 말해준다.
“C 생태계 전체를 쓸 수 있다”는 약속과 “쓸 수 있게 준비된 것은 열네 개”라는 현실 사이의 거리가 여기 있다.

Python 쪽과 대비하면 차이가 뚜렷하다.
Python 바인딩은 `llpyg`라는 도구로 생성하고, 그래서 numpy·pandas·torch·matplotlib까지 목록에 있다.
C 쪽에는 그런 도구가 아직 없다.

이 비대칭이 흥미로운 이유는 난이도가 반대일 것 같기 때문이다.
Python은 동적 타입이라 시그니처를 정적으로 뽑기 어렵고, C는 헤더 파일에 타입이 다 적혀 있다.
그럼에도 Python 쪽이 먼저 자동화된 것은, C 헤더에서 Go 바인딩을 만드는 일이 매크로·조건부 컴파일·플랫폼별 타입 때문에 실제로는 더 지저분하기 때문일 것이다.
`c/clang` 바인딩이 목록에 있는 것이 그 자동화를 준비하는 재료로 읽힌다.

## 비평

### “Go 호환”이라는 표현이 소스 호환만을 뜻하는데 그렇게 읽히지 않는다

README는 Go 1.20+ 소스 코드와 호환되고 Go 1.27 문법 전체를 지원하며 표준 라이브러리를 완전히 지원한다고 반복해서 밝힌다.
그리고 그 주장을 뒷받침하는 절차도 상세하다 — `GOROOT/test` 케이스, 툴체인별 테스트, `xfail.yaml`과 `notapplicable.yaml`.

문제는 이 검증이 컴파일과 통과 여부를 확인한다는 점이다.
같은 코드가 같은 성능 특성으로 돌아가는지는 다른 문제이고, 앞서 본 1:1 고루틴 매핑과 보수적 GC는 그 특성을 크게 바꾼다.

구체적인 예를 들면 이렇다.
`sync.WaitGroup`으로 고루틴 만 개를 띄우는 테스트는 두 런타임 모두에서 통과하지만, 하나는 몇 MB를 쓰고 다른 하나는 OS 스레드 만 개를 만든다.
채널로 파이프라인을 구성한 코드도 컴파일되지만, 고루틴 전환이 커널 문맥 교환이 되므로 처리량이 자릿수 단위로 달라질 수 있다.

`notapplicable.yaml`이라는 파일이 존재한다는 것은 저자들이 이 구분을 알고 있다는 뜻이다.
다만 그것이 “LLGo의 호환성 목표 바깥에 있는 gc 특유의 메커니즘”으로 서술되어 있어, 성능 특성의 차이가 아니라 기능의 차이로만 읽힌다.
런타임 절 첫머리에 “동시성 성능 특성이 표준 Go와 다르다”는 문장이 하나 있었다면 이 문서의 정직성이 훨씬 높아졌을 것이다.

### 벤치마크 배지는 있는데 숫자는 README에 없다

상단 배지 줄에 “benchmark: LLGo vs Go”가 있고 외부 사이트로 링크된다.
그런데 README 본문에는 성능 수치가 한 줄도 없다.

이것이 아쉬운 이유는 이 프로젝트의 존재 이유가 성능이기 때문이다.
cgo 오버헤드를 없앤다는 것이 핵심 주장인데, 없앤 결과가 얼마인지 — C 호출 하나가 표준 Go 대비 몇 배 빠른지 — 가 문서에 없다.

그리고 그 숫자가 특히 필요한 이유는 트레이드오프가 크기 때문이다.
C 호출이 10배 빨라지고 고루틴 생성이 100배 느려진다면, 그 교환이 유리한지는 프로그램의 성격에 달려 있다.
사용자가 그 판단을 하려면 양쪽 숫자가 다 있어야 하는데, 배지 하나로는 어느 쪽도 알 수 없다.

배지 링크를 따라가면 있을 수도 있다.
그러나 README에서 가장 반복되는 주장의 근거를 외부 링크에 두는 것은, 앞서 살펴본 여러 발표문에서 반복된 형태다 — 형용사는 본문에, 숫자는 클릭 뒤에.

### 의존성 목록의 길이가 채택 가능성을 결정한다

의존성 절에는 열한 개 항목이 있고 그중 넷이 LLVM 22 계열이다.
그리고 설치 안내가 macOS, Debian/Ubuntu, Alpine, Fedora, Windows(MSVC·MinGW)로 나뉘어 있으며 각각 다른 주의사항이 붙는다.

이 길이 자체가 이 프로젝트의 가장 큰 채택 장벽이다.
Go의 대표적 장점 중 하나가 툴체인 하나만 받으면 끝난다는 것인데, LLGo는 그 성질을 잃는다.

버전 고정도 부담이다.
LLVM 22를 요구하므로 Fedora 43은 지원 환경이 아니고, Homebrew에는 `lldb@22`가 없어 별도 안내가 필요하며, Alpine에서는 환경 변수 네 개를 손으로 설정해야 한다.
LLVM 메이저 버전은 반년 주기로 올라가므로 이 문서는 계속 갱신되어야 한다.

Windows 쪽 서술이 특히 그렇다.
네 가지 아카이브 변형이 있고, ARM64 아카이브에 x64 Clang이 들어 있어 에뮬레이션으로 돌며, MSVC는 정적 링크이고 MinGW는 DLL을 옆에 둔다는 설명이 이어진다.
정확한 문서화이지만, 이 정도의 설명이 필요하다는 사실 자체가 배포 복잡도의 지표다.

### 대안들과의 비교가 없다

Go 코드를 LLVM으로 컴파일하려는 시도는 처음이 아니다.
TinyGo가 같은 접근으로 임베디드와 WebAssembly를 겨냥해 오래 유지되어왔고, gccgo도 다른 백엔드로 같은 문제를 다룬다.

README는 TinyGo를 한 번 언급하는데, 임베디드 타깃의 GC가 TinyGo에서 파생되었다는 맥락에서다.
비교는 없다.

이 공백이 실무 판단을 어렵게 만든다.
임베디드나 WebAssembly가 목적이라면 TinyGo가 이미 성숙한 선택지이고, LLGo가 그 위에서 무엇을 더 주는지가 결정 요인이다.
답은 아마 C/C++/Python 상호운용의 폭일 텐데, 그렇다면 그것을 명시하고 TinyGo가 그 축에서 어디까지 되는지와 나란히 놓는 것이 독자에게 훨씬 유용하다.

별 750개라는 규모도 이 맥락에서 읽어야 한다.
TinyGo가 훨씬 큰 사용자 기반과 벤더 지원을 갖고 있으므로, LLGo를 고르는 것은 더 작은 생태계와 더 넓은 상호운용을 교환하는 선택이다.
그 교환을 명시하지 않으면 기능 목록만 보고 온 사람이 나중에 알게 된다.

HN에 달린 유일한 제3자 질문이 정확히 이 지점을 찌른다.
pancsta는 LLGo의 WASM 바이너리 크기가 어떻게 되는지 묻는다 — TinyGo는 표준 라이브러리에 의존하면 순전히 고통이기 때문이라는 것이다.[^pancsta]
WASI에서의 네트워킹도 되면 좋겠다고 덧붙이고, 한번 돌려보겠지만 GitHub에 정보가 없어 질문을 남겨둔다고 적는다.

이 질문이 README의 공백 두 개를 동시에 드러낸다.
하나는 바이너리 크기 수치가 없다는 것이고, 다른 하나는 TinyGo와의 비교가 없다는 것이다.
그리고 두 공백이 같은 뿌리에서 나온다 — WebAssembly 타깃에서 LLGo를 고를 이유가 무엇인지가 서술되지 않았다.

pancsta가 든 TinyGo의 약점 — 표준 라이브러리 의존 시의 고통 — 은 LLGo가 정확히 겨냥할 수 있는 자리다.
README가 표준 라이브러리 완전 지원을 반복해서 강조하므로, 그것을 WASM 맥락에서 수치로 보여주는 것이 가장 강한 논거가 되었을 것이다.
그 수치가 없어서 잠재 사용자가 직접 돌려보고 판단해야 하는 상태로 남아 있다.

## 인사이트

### cgo 비용은 언어 설계 결정의 청구서였고, LLGo는 그 결정을 되돌려 지불한다

Go에서 C 호출이 비싼 것은 구현의 게으름이 아니라 설계의 귀결이다.
경량 고루틴과 자라는 스택, 사용자 공간 스케줄러를 얻으려면 런타임이 스택 레이아웃과 실행 상태를 통제해야 하고, C는 그 통제 밖에 있다.
그래서 경계를 넘을 때마다 상태를 정리하고 스케줄러에 알려야 한다.

LLGo는 이 교환을 반대로 한다.
런타임의 통제를 포기하고 C와 같은 실행 모델을 쓰면 경계가 사라진다.

이 구조는 언어 런타임 일반에 적용되는 법칙에 가깝다.
호스트 언어가 실행 모델을 많이 통제할수록 그 언어 안에서 얻는 것이 많고 바깥으로 나가는 비용이 커진다.
JVM의 JNI, .NET의 P/Invoke, Python의 GIL과 확장 모듈이 전부 같은 곡선 위에 있다.

그렇다면 “FFI가 싼 언어”는 대개 런타임이 얇은 언어이고, 그 얇음은 다른 곳에서 대가를 치른다.
LLGo가 흥미로운 것은 같은 언어의 두 런타임을 나란히 제공해 그 대가를 사용자가 고를 수 있게 만든다는 점이다.
그리고 그 선택이 소스 코드 변경 없이 컴파일러 교체만으로 이루어진다는 것이 이 프로젝트의 실질적 기여다.

### 같은 문법 다른 런타임이라는 구성은 생태계를 조용히 쪼갠다

LLGo로 컴파일되는 코드는 표준 Go로도 컴파일된다.
이 성질은 채택에 유리하지만 라이브러리 생태계에는 새로운 문제를 만든다.

문제는 라이브러리가 자기 실행 환경을 가정한다는 데 있다.
고루틴을 수만 개 띄우는 워커 풀, 스택 크기를 전제한 재귀, GC 압력을 고려한 객체 재사용 패턴이 전부 표준 런타임의 특성 위에 최적화되어 있다.
그 라이브러리를 LLGo로 컴파일하면 컴파일은 되고 테스트도 통과하지만 운영 특성이 다르다.

그리고 이런 종류의 불일치는 문서화되지 않는다.
`go.mod`에는 언어 버전을 적는 자리는 있어도 런타임 가정을 적는 자리는 없다.
라이브러리 작성자가 “고루틴을 자유롭게 쓴다”고 명시할 이유도 없었다 — 지금까지는 그것이 기본값이었기 때문이다.

역사적 유비는 Python 2와 3이 아니라 CPython과 PyPy의 관계다.
문법은 같고 대부분의 코드가 양쪽에서 돌지만, C 확장 호환성과 성능 특성이 달라 사실상 다른 배포 대상이 되었다.
그리고 라이브러리들이 “PyPy 호환” 표시를 달기까지 오래 걸렸다.

LLGo가 널리 쓰이면 같은 표시가 Go 생태계에도 필요해진다.
지금은 그 필요가 보이지 않는데, 사용자가 적고 대부분 자기 코드만 컴파일하기 때문이다.

### 임베디드와 AI를 같은 도구의 용도로 묶은 것이 이 프로젝트의 구조적 약점이다

README가 나열한 용도 — 게임, AI와 데이터 과학, WebAssembly, 임베디드 — 는 공통점이 하나뿐이다.
C 라이브러리를 많이 쓴다는 것이다.

그러나 요구 사항은 정반대에 가깝다.
임베디드는 GC를 끄고 바이너리를 줄이고 결정론적 동작을 원한다.
AI와 데이터 과학은 Python 상호운용과 대용량 메모리, 그리고 대개 서버 환경을 전제한다.
WebAssembly는 또 다른 ABI와 샌드박스 제약을 갖는다.

이 셋을 하나의 컴파일러가 지원하려면 타깃별 런타임을 따로 유지해야 하고, README를 보면 실제로 그렇게 하고 있다 — 네이티브는 BDWGC, 임베디드는 TinyGo 파생 GC, WebAssembly는 별도 ABI 선택.
즉 이름은 하나지만 안에는 세 개의 제품이 있다.

이 구성이 유지 가능한지가 이 프로젝트의 장기 과제다.
LLVM 메이저 버전마다 세 갈래를 전부 따라가야 하고, 지원 플랫폼 표에 나온 조합 — Linux·macOS·Windows 각각 amd64/arm64, MSVC·MinGW, wasm 네 변형, 임베디드 보드들 — 을 CI로 유지해야 한다.
별 750개 규모의 프로젝트가 감당하기에 큰 표면적이다.

여기서 예상되는 경로는 집중이다.
셋 중 실제 사용자가 붙는 하나가 나오면 나머지는 유지보수 모드로 밀리고, 그때 README의 용도 목록도 줄어들 것이다.
Python 바인딩만 자동화되어 있다는 사실이 이미 어느 쪽에 힘이 실려 있는지 보여주는 신호일 수 있다.

### C ABI가 사실상의 언어 간 공용어로 다시 부상하고 있다

LLGo의 등식 — Go 곱하기 C 생태계 — 에서 곱해지는 대상이 C 자체가 아니라 “C 호환 인터페이스를 노출하는 언어들”이라는 점이 눈에 띈다.
README는 그 목록에 C/C++, Python, JavaScript, Objective-C, Swift를 넣는다.

이 목록이 시사하는 것은 C ABI의 위치 변화다.
한동안 언어 간 연동의 주류는 상위 계층이었다 — RPC, 직렬화 포맷, 프로세스 분리.
그 방식이 안전하고 언어 독립적이지만 호출당 비용이 크고, 그 비용이 문제가 되는 영역이 늘고 있다.

특히 AI 워크로드가 그렇다.
Python에서 텐서 연산을 부르는 것은 사실상 C ABI를 통해 네이티브 코드를 부르는 일이고, 그 경계를 넘는 횟수가 성능을 좌우한다.
LLGo가 Python 바인딩을 먼저 자동화한 것도 그 수요를 겨냥한 것으로 보인다.

역사적 유비는 1990년대 COM과 CORBA의 시대다.
그때도 언어 간 상호운용이 큰 주제였고, 정교한 객체 모델을 표준화하려는 시도가 여럿 있었으며, 결국 살아남은 것은 가장 단순한 계층 — C 함수 호출 규약 — 이었다.
WebAssembly Component Model 같은 현대적 시도가 다시 상위 추상을 세우려 하고 있는데, LLGo는 반대로 최하층에 붙는 쪽을 택했다.

어느 쪽이 이길지는 모르지만 한 가지는 분명하다.
C ABI는 1970년대에 정해진 규약이고, 그것이 반세기 뒤에도 언어 간 연동의 기준선으로 남아 있다는 사실이 이 층의 관성을 보여준다.
LLGo 같은 프로젝트가 계속 나오는 이유도 그 관성이 사라지지 않기 때문이다.
