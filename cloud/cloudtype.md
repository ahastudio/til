# 클라우드타입: Kubernetes를 감춘 국내 PaaS와 OpenClaw로 옮겨 간 간판

<https://cloudtype.io/>

Show GN: [클라우드타입 - Kubernetes기반 배포 플랫폼 | GeekNews](https://news.hada.io/topic?id=10479)

## 소개

클라우드타입은 GitHub 저장소의 소스 코드를 인프라 작업 없이 배포하고 운영하게 해 주는 국내 PaaS다.

[GN에 올라온 소개](https://news.hada.io/topic?id=10479)에서는 자기를 **Kubernetes 기반 배포 플랫폼**이라고 밝힌다.
서비스 개발자는 빠르게 개발 환경을 구성하고 인프라 엔지니어는 안정적인 리소스 할당과 제어가 가능하다는 것이다.

그런데 지금 홈페이지 첫 문장은 Kubernetes를 말하지 않는다.

> OpenClaw 를 사용하는 가장 간편한 방법

그 아래에 복잡한 클라우드 설정 없이 10분 만에 서비스를 배포하고 운영하라는 문구가 오고, 어떤 언어든 프레임워크든 코드만 준비하면 된다고 적는다.

실적으로 제시하는 수치는 **100개 이상의 템플릿과 45만 회 이상의 배포**다.

운영사는 주식회사 클라우드타입이고 대표는 조재욱, 주소는 경기도 고양시 덕양구 꽃마을로 64, 1022호(향동동, DMC스타허브플러스)다.
사업자등록번호는 `609-88-01541`, 통신판매업 신고번호는 `2023-고양덕양구-2952호`이며 문의는 `help@cloudtype.co.kr`이다.
인터페이스는 한국어와 일본어를 지원한다.

## 구성 개념

대시보드 화면이 계층을 드러낸다.

| 단위     | 역할                                                           |
| -------- | -------------------------------------------------------------- |
| 스페이스 | 최상위 소유 단위. 개인용과 팀용이 나뉘며 전환해 쓴다           |
| 프로젝트 | 스페이스 안의 묶음. 구독 등급과 자원 쿼터가 여기 붙는다        |
| 배포환경 | 프로젝트 안의 환경. 기본값이 `main`이고 새로 만들어 전환한다   |
| 서비스   | 실제 실행 단위. 애플리케이션과 데이터베이스가 모두 여기 속한다 |

이 구조에서 눈여겨볼 것이 **배포환경이 서비스보다 위에 있다**는 점이다.
스테이징과 프로덕션을 환경으로 나누면 그 안의 서비스 묶음이 통째로 복제되는 모양이 된다.

화면에는 `모두 시작`과 `모두 중지` 버튼, 그리고 `YAML 다운로드`가 함께 놓인다.
즉 화면에서 구성한 것을 선언 파일로 내보낼 수 있다.

예시 화면의 서비스 목록이 이 플랫폼의 범위를 잘 보여 준다.

```text
flask            python@3.10       중지됨
n8n-ce           n8n@1.27          실행 중(1/1)
api              node@22           중지됨
dockerfile       dockerfile        중지됨
java-springboot  java@17           실행 중(1/1)
mariadb          mariadb@10.5      실행 중(1/1)
```

언어 런타임과 오픈소스 앱(n8n)과 데이터베이스와 커스텀 Dockerfile이 같은 목록에 섞여 있다.
**서비스 종류를 구분하지 않고 같은 단위로 다루는 것**이 이 제품의 기본 발상이다.

## 배포 방식

네 가지 경로가 제시된다.

### 내장 빌더

`Dockerfile` 작성 방법을 몰라도 Git 저장소의 소스 코드를 즉시 빌드하고 배포한다는 것이다.
화면에서 언어와 버전(`node@22` 같은)이 자동 감지된 형태로 표시된다.

### Dockerfile 배포

빌드를 사용자 정의하고 애플리케이션을 독립적으로 배포하려면 `Dockerfile`을 쓴다.

두 경로가 공존하는 것이 중요하다.
내장 빌더는 편의를 주지만 빌드 과정을 감추므로, 시스템 패키지가 필요하거나 멀티스테이지 빌드가 필요하면 막힌다.
그때 `Dockerfile`로 내려갈 수 있어야 제품이 성립한다.

### 데이터베이스와 오픈소스 템플릿

클릭 한 번으로 데이터베이스를 만든다. 예시로 `mariadb@11.7`, `mongo@5.0`, `postgres`가 나온다.
독립 구동되고 **프라이빗 네트워크로 연결**된다고 명시한다.

오픈소스 소프트웨어도 원클릭 설치를 지원하며, 앞서 본 `n8n-ce`가 그 사례다.

### GitHub Actions와 CLI

GitHub Actions를 통해 더 다양한 배포 방식과 자동화를 지원한다고 적는다.

CLI는 선언 파일 기반이다.

```bash
# YAML로 정의한 앱을 배포환경에 적용한다
ctype apply -f myapp.yaml

# 현재 배포환경의 앱 목록을 확인한다
ctype ls
```

출력 예시가 이렇다.

```text
$ ctype apply -f myapp.yaml
1 apps deployed to @demo/myproject
 └ app "myapp" deployed to main

$ ctype ls
@demo/myproject:main
NAME    APP      CREATED              UPDATED
myapp   node@22  2025-01-11 03:57:37  2025-02-04 20:35:56
```

`@스페이스/프로젝트:배포환경` 표기가 앞서 본 계층을 그대로 반영한다.

## 운영 기능

### HTTPS 자동 발급

도메인을 연결하면 무료 HTTPS(TLS) 인증서가 자동 발급된다.

### 리소스 조정

CPU, 메모리, 디스크, 레플리카를 화면에서 바꾼다. 화면에 보이는 선택 범위는 이렇다.

| 항목     | 가용 한도 | 선택 단계                                  |
| -------- | --------- | ------------------------------------------ |
| CPU      | 8 vCPU    | Minimum, 0.5부터 4 vCPU까지 0.5 단위       |
| RAM      | 16GB      | 0.5GB부터 8GB까지 0.5GB 단위               |
| Disk     | 1TB       | 1GB, 10GB, 50GB, 이후 100GB부터 1000GB까지 |
| Replicas | 7         | 1부터 10까지                               |

기본값은 Minimum vCPU, 0.5GB RAM, 레플리카 1개다.

여기서 눈에 띄는 것이 **가용 한도와 선택 단계가 어긋난다**는 점이다.
CPU 가용이 8 vCPU인데 선택지는 4 vCPU까지이고, RAM 가용이 16GB인데 선택지는 8GB까지이며, 레플리카 가용이 7인데 선택지는 10까지다.
가용 한도가 프로젝트 전체 쿼터이고 선택지가 서비스당 상한이라고 읽으면 앞의 둘은 설명되지만, 레플리카는 반대 방향이라 화면만으로는 확정할 수 없다.

### 터미널과 로그 뷰어

대시보드에서 직접 컨테이너 터미널에 접속하고 실시간 로그를 본다.

로그 뷰어 예시 화면에 담긴 내용이 흥미롭다.

```text
2025-02-07 11:33:07 [1] [INFO] Starting gunicorn 19.9.0
2025-02-07 11:33:07 [1] [INFO] Listening at: http://0.0.0.0:80 (1)
2025-02-07 11:33:07 [1] [INFO] Using worker: gevent
2025-02-07 11:33:07 [9] [INFO] Booting worker with pid: 9
2025-02-10 13:37:54 [1] [CRITICAL] WORKER TIMEOUT (pid:9)
2025-02-10 13:37:55 [9] [INFO] Worker exiting (pid: 9)
2025-02-10 13:37:56 [11] [INFO] Booting worker with pid: 11
2025-02-10 19:27:00 [1] [CRITICAL] WORKER TIMEOUT (pid:11)
```

마케팅 화면에 **워커 타임아웃이 반복되는 실제 장애 로그**가 실려 있다.
꾸미지 않은 화면이라는 점에서 정직하지만, 기능 소개로는 묘한 선택이다.

한편 이 로그가 알려 주는 실무 정보도 있다. gunicorn 기본 타임아웃(30초)에 걸리는 워커가 있으면 이 플랫폼에서도 똑같이 죽는다는 것이다.

### 보안

운영자 대시보드에서 모든 자격증명과 시크릿과 배포 세부 사항을 **개발자에게 노출하지 않고** 체계적으로 관리한다고 적는다.
그리고 모든 개발자 활동과 감사 로그를 빠르게 검토하고 검색할 수 있다는 것이다.

이 절만 영문으로 적혀 있다는 점이 눈에 띈다. 기업 고객이나 해외 시장을 겨냥한 문구로 보인다.

## 트레이드오프

### Kubernetes를 감추는 대가로 Kubernetes의 표현력을 잃는다

이 제품의 근본 거래가 여기 있다.

GN 소개문은 자기를 Kubernetes 기반이라고 밝히고, 지원 기능에 **Kubernetes 연결 기능**까지 포함한다고 적는다.
반면 홈페이지는 Kubernetes를 한 번도 언급하지 않는다. 대신 “복잡한 클라우드 설정 없이”라고 쓴다.

같은 제품이 대상 독자에 따라 정반대로 소개된다.

이 이중성이 우연이 아니다. PaaS의 가치 제안이 원래 그렇게 생겼기 때문이다.
개발자에게는 Kubernetes를 몰라도 된다고 말해야 하고, 인프라 담당자에게는 Kubernetes 위에 있어서 통제 가능하다고 말해야 한다.

문제는 그 둘이 동시에 참이기 어렵다는 점이다.

화면에서 조절 가능한 것이 CPU, 메모리, 디스크, 레플리카 넷이다.
Kubernetes에서 실제로 필요한 것들 — 파드 안티어피니티, 토폴로지 분산, PodDisruptionBudget, 리소스 요청과 한도의 분리, HPA 지표 선택, 초기화 컨테이너, 사이드카 — 이 화면에 없다.

그러면 두 갈래가 된다.
그것들이 필요 없는 워크로드라면 이 제품이 잘 맞고, 필요해지는 순간 **화면 밖으로 나가야 한다**.

GN 소개문의 “Kubernetes 연결 기능”이 그 탈출구로 보이지만, 홈페이지에는 그 기능에 대한 설명이 없다.
즉 탈출구의 존재는 알 수 있어도 그 폭은 알 수 없다.

### 원클릭 데이터베이스가 운영 책임의 경계를 흐린다

클릭 한 번으로 만드는 데이터베이스가 이 제품의 강한 편의 기능이다.
독립 구동되고 프라이빗 네트워크로 연결된다는 설명도 명확하다.

그런데 화면에 보이는 것이 거기까지다.

운영 데이터베이스에서 실제로 중요한 것들이 홈페이지에 없다.
백업 주기와 보관 기간, 시점 복구(PITR) 가능 여부, 장애 조치와 복제 구성, 버전 업그레이드 시 다운타임, 스냅샷 내보내기 경로다.

이것이 왜 위험한가 하면, **클릭 한 번으로 만들어지는 것은 클릭 한 번으로 만들어졌다는 인상을 준다**는 점 때문이다.
개발 단계에서 편하게 띄운 데이터베이스가 그대로 프로덕션이 되는 경로가 너무 짧다.

애플리케이션은 코드가 Git에 있으므로 어디서든 다시 띄울 수 있다. 데이터는 그렇지 않다.
그래서 이 플랫폼에서 가장 이전하기 어려운 자산이 데이터베이스이고, 정확히 그것이 가장 쉽게 만들어진다.

실무 규칙으로 바꾸면 이렇다.
원클릭 데이터베이스는 개발과 스테이징에 쓰고, 프로덕션 데이터는 **백업과 복구 경로를 확인한 뒤에만 올린다**.
확인이 안 되면 외부 관리형 데이터베이스를 쓰고 애플리케이션만 여기 두는 편이 낫다.

### 국내 PaaS라는 위치가 이점이자 제약이다

이 제품이 해외 경쟁자(Railway, Render, Fly.io)와 갈리는 지점이 기술이 아니라 위치다.

이점이 실재한다.
한국어 인터페이스와 한국어 문서와 디스코드 커뮤니티가 있고, 국내 법인이므로 세금계산서와 계약과 개인정보 처리 측면에서 국내 기업에 맞다.
지연 시간도 국내 사용자 대상 서비스라면 유리할 수 있다.

제약도 실재한다.
생태계 규모가 작으므로 문제를 만났을 때 검색으로 나오는 사례가 적고, 템플릿 100개는 해외 플랫폼의 커뮤니티 템플릿 수와 비교하기 어렵다.
그리고 45만 회 배포라는 수치가 규모를 말하지만, 그것이 활성 프로젝트 수인지 누적 배포 횟수인지에 따라 의미가 크게 달라진다. 홈페이지는 누적 배포로 적고 있다.

더 구조적인 문제도 있다. **단일 사업자 의존**이다.
해외 대형 PaaS도 서비스를 접지만, 그때 이주 대상 플랫폼과 이주 가이드가 커뮤니티에 쌓인다.
국내 중소 PaaS에서 같은 일이 생기면 이주 경로를 스스로 만들어야 한다.

그래서 이 제품을 쓸 때의 실질적 방어가 하나 있다. **`Dockerfile` 경로로 배포하는 것**이다.
내장 빌더로 배포하면 빌드 규칙이 플랫폼 안에 있고, `Dockerfile`로 배포하면 그 규칙이 저장소에 남는다.
같은 이미지를 다른 곳에서 띄울 수 있다는 차이가 이전 비용을 크게 가른다.

## 함정

### 무료 등급의 CPU 표기가 실제 한도를 드러낸다

대시보드 예시 화면의 프리티어 쿼터가 이렇게 적혀 있다.

```text
구독        프리티어
CPU        0 of 0 vCPU
메모리      1.75GB of 5GB
디스크      2GB of 2GB
서비스      5 / 14
```

메모리와 디스크는 숫자가 있는데 **CPU가 `0 of 0 vCPU`**다.

이것을 읽는 방법이 둘이다.
무료 등급에 전용 vCPU 할당이 없어 공유 또는 버스트로만 돈다는 뜻이거나, 표기가 비어 있는 것이다.

어느 쪽이든 실무에서 의미하는 바는 같다. 무료 등급에서 **CPU 성능을 예측하지 말아야 한다**.
빌드 시간이나 응답 지연을 무료 등급에서 측정해 유료 등급을 추정하면 어긋난다.

디스크가 `2GB of 2GB`로 가득 찬 것도 눈여겨볼 만하다. 예시 화면이지만, 디스크 한도가 작아 금방 차는 등급이라는 점은 사실이다.

### 배포환경 복제가 데이터까지 복제하지는 않는다

배포환경을 새로 만들어 전환할 수 있다는 기능이 스테이징 구성에 편리해 보인다.

그런데 서비스 목록에 데이터베이스가 함께 들어 있다는 점이 함정을 만든다.

애플리케이션은 같은 이미지를 띄우면 동등해지지만, 데이터베이스는 스키마와 데이터가 있어야 동등해진다.
배포환경을 복제해도 데이터가 따라오지 않으면 스테이징에서 통과한 것이 프로덕션에서 깨진다.

그리고 반대 방향이 더 위험하다. 프로덕션 데이터를 스테이징에 복사하면 개인정보가 통제 밖으로 나간다.

홈페이지는 이 문제를 다루지 않는다. 마이그레이션 실행 시점과 방식에 대한 언급도 없다.

실무에서는 이렇게 다룬다.
**스키마 변경을 애플리케이션 배포와 분리해 명시적 단계로 두고**, 그 단계를 CLI나 GitHub Actions에서 실행한다.
`ctype apply`가 선언 파일을 적용하는 명령이므로, 마이그레이션은 그 앞뒤에 별도 잡으로 두는 편이 안전하다.

### 터미널 접속이 편리한 만큼 상태가 새기 쉽다

대시보드에서 바로 컨테이너 터미널에 접속하는 기능이 디버깅에 좋다.

그런데 이 편리함이 **컨테이너 안에서 손으로 고치는 습관**을 만든다.
패키지를 하나 설치하거나 설정 파일을 수정해 문제를 넘기면, 그 변경이 다음 배포에서 사라진다.

플랫폼이 재시작하거나 레플리카를 늘리면 즉시 드러나지만, 그 사이에 원인을 찾기 어려운 불일치가 생긴다.

같은 문제가 디스크에도 있다. 디스크를 붙일 수 있으므로 컨테이너 안에 상태를 둘 수 있는데, 레플리카를 1보다 크게 잡는 순간 그 상태가 인스턴스마다 갈린다.

레플리카 선택지가 1부터 10까지 화면에 노출되어 있고, 상태를 가진 서비스에서 그것을 올리면 안 된다는 경고는 없다.

## 체크리스트

- 이 서비스를 `Dockerfile`로 배포했는가, 내장 빌더에 의존하는가? 이전 가능성이 여기서 갈린다.
- 데이터베이스의 백업 주기와 복구 절차를 확인했는가? 확인 못 했다면 프로덕션 데이터를 올리지 않았는가?
- 레플리카를 1보다 크게 잡은 서비스가 상태를 로컬 디스크에 두고 있지 않은가?
- 스키마 마이그레이션이 애플리케이션 배포와 분리된 명시적 단계로 있는가?
- 무료 등급에서 측정한 성능 수치를 유료 등급 추정에 쓰고 있지 않은가?
- 터미널로 컨테이너 안에서 고친 것이 저장소에도 반영되었는가?
- `YAML 다운로드`로 구성을 내보내 저장소에 넣어 두었는가?
- 서비스 간 연결에 프라이빗 네트워크 주소를 쓰고 있는가, 공개 도메인을 경유하고 있는가?

## 기억할 원칙

### 추상화 계층을 고를 때는 탈출구의 폭을 먼저 본다

PaaS 선택의 핵심 질문은 “얼마나 편한가”가 아니라 “막혔을 때 어디로 나가는가”다.

클라우드타입은 이 점에서 답을 여럿 갖고 있다.
`Dockerfile`로 빌드를 직접 정의할 수 있고, CLI와 YAML로 구성을 코드화할 수 있으며, GitHub Actions로 파이프라인을 밖으로 뺄 수 있고, GN 소개문에 따르면 Kubernetes 연결도 있다.

이것들이 각각 다른 깊이의 탈출구다.
`Dockerfile`은 빌드 재현성을 저장소로 옮기고, YAML은 구성을 옮기며, Kubernetes 연결은 실행 기반 자체를 옮긴다.

일반화하면, 관리형 플랫폼의 성숙도는 기본 경로가 얼마나 편한가가 아니라 **기본 경로를 벗어나는 단계가 몇 개인가**로 재는 것이 낫다.
단계가 하나뿐이면 편의와 통제 사이에서 절벽을 만나고, 여러 개면 필요한 만큼만 내려갈 수 있다.

그리고 이 기준은 도입 시점이 아니라 **도입 6개월 뒤**에 값을 드러낸다.
처음에는 기본 경로만 쓰고, 요구가 늘어나면서 하나씩 내려가게 되기 때문이다.

### 간판 문구의 변화가 제품의 방향을 알려 준다

이 홈페이지에서 가장 정보량이 큰 한 줄이 기능 설명이 아니라 첫 문장이다.

GN에 올라올 때는 “Kubernetes 기반 배포 플랫폼”이었고, 지금은 **“OpenClaw 를 사용하는 가장 간편한 방법”**이다.

범용 PaaS가 특정 도구의 배포 창구를 전면에 내세우는 것은 큰 전환이다.
대상 사용자가 “배포할 앱이 있는 개발자”에서 “[OpenClaw](../openclaw/build-your-own-openclaw.md)를 돌리고 싶은 사람”으로 좁아지기 때문이다.

이 선택에 합리적 근거가 있다.
범용 PaaS 시장에서 국내 사업자가 해외 플랫폼과 기능으로 겨루기는 어렵고, 특정 워크로드에서 “가장 쉬운 경로”가 되는 편이 유입에 유리하다.
그리고 에이전트 도구는 셀프호스팅 수요가 크면서 배포 난이도가 높아 PaaS와 궁합이 좋다.

다만 이 전환에 따르는 위험도 분명하다.
**특정 오픈소스의 인기에 유입이 묶인다.** 그 프로젝트가 호스팅 정책을 바꾸거나 인기가 식으면 간판을 다시 갈아야 한다.

여기서 나오는 읽기 방법이 있다.
어떤 플랫폼의 홈페이지 헤드라인이 기술 스택에서 특정 애플리케이션으로 바뀌었다면, 그것은 대체로 **일반 유입이 정체되어 특정 수요에 올라타는 국면**이라는 신호다.
사용자 입장에서 나쁜 소식은 아니지만, 그 특정 수요에 속하지 않는다면 로드맵이 자기 쪽을 향하지 않을 수 있다는 것을 감안해야 한다.
