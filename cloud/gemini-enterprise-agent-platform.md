# Gemini Enterprise Agent Platform: Google Cloud의 AI 에이전트 거버넌스 스택

원문: <https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform>

트윗: [The Agent Governance Stack: Treat Your AI Agent Fleet Like Your Engineering Org](https://twitter.com/GoogleCloudTech/status/2047120160100860290)

HN 토론: <https://news.ycombinator.com/item?id=47863364> (3점, 2개 댓글)

## 요약

Google Cloud가 Cloud Next '26(2026년 4월 23일)에서
Gemini Enterprise Agent Platform을 발표했다.
AI 에이전트를 빌드·확장·거버넌스·최적화하는 통합 플랫폼으로,
Vertex AI의 모든 서비스와 로드맵을 이 플랫폼으로 통합하겠다고 선언했다.

거버넌스 레이어가 핵심이다.
에이전트 플릿을 엔지니어링 조직처럼 관리한다는 개념 하에,
에이전트 신원 부여, 접근 제어, 정책 집행, 행위 모니터링, 감사 기능을 제공한다.
거버넌스 스택은 Agent Identity, Agent Registry, Agent Gateway,
이상 및 위협 탐지, Agent Security Dashboard의 5계층으로 구성된다.

플랫폼은 거버넌스 외에도 개발(Agent ADK, Agent Studio, Agent Garden),
실행(Agent Runtime, Agent Sandbox, Agent Memory Bank, Agent Sessions),
최적화(Agent Simulation, Agent Evaluation, Agent Observability, Agent Optimizer)
기능을 포함한다.
현재 Burns & McDonnell, Comcast, PayPal, L'Oréal 등
주요 기업이 이미 에이전트 플랫폼을 활용 중이라고 밝혔다.

모델 가든을 통해 Gemini 3.1 Pro, Gemma 4와 함께
Anthropic Claude Opus/Sonnet/Haiku도 지원한다.

### Google Cloud Tech가 정리한 다섯 계층

같은 날 Google Cloud Tech 계정이 Addy Osmani와 Shubham Saboo의 이름으로
이 거버넌스 스택을 계층별로 설명한 장문의 트윗을 올렸다.
출발점은 위험의 성격 구분이다 —
잘못 설정된 SaaS 도구는 수동적으로 데이터를 흘리지만
잘못 설정된 에이전트는 능동적으로 나쁜 행동을 한다는 것이다.
2015년 섀도 IT에서 본 패턴이 AI 에이전트에서 반복되고 있으며,
에이전트가 프로덕션 데이터베이스와 고객 PII와 금융 시스템에 접근하는데도
고유 신원, 범위가 정해진 권한, 행위 모니터링이 없을 수 있다고 지적한다.
엔지니어링 팀을 그렇게 운영하지 않을 텐데 에이전트 플릿은 왜 그렇게 운영하느냐는 것이 논지다.

1계층 신원에서는 공유 자격 증명 문제를 구체적으로 든다.
대부분의 에이전트 배포가 이 단계를 통째로 건너뛰고
`agent-service@project.iam.gserviceaccount.com` 하나가 조직의 모든 에이전트를 뒷받침한다.
에이전트가 접근하면 안 되는 데이터에 접근하거나 범위 밖 행동을 했을 때
감사 추적이 공유 자격 증명으로 이어지면서 조사가 멈춘다 —
에이전트가 했다는 것은 알지만 어느 에이전트인지는 모른다.
Agent Identity는 모든 에이전트에 고유한 암호학적 ID와 명확히 정의된 인가 정책을 부여해
추적 가능하고 감사 가능하며 독립적으로 회수 가능하게 만든다.
세분성이 중요하다 — data-reader 같은 넓은 역할을 주는 것이 아니라
각 에이전트가 어떤 테이블, 어떤 버킷, 어떤 API 엔드포인트에 접근할 수 있는지를 정확히 정의한다.
Finance Agent는 급여 데이터를 읽을 수 있지만 직원 복리후생 정보는 볼 수 없고,
HR Agent는 복리후생 데이터를 읽지만 재무 기록에는 접근 권한이 전혀 없다.
프롬프트 인젝션 시도나 모델 업데이트로 인한 추론 변화로
Finance Agent의 행위가 예상 밖으로 바뀌면
플릿의 다른 에이전트에 영향을 주지 않고 그 신원만 회수한다.
신원이 1계층인 이유는 그 위의 모든 것이 그것에 의존하기 때문이다 —
에이전트에 구별되는 신원이 없으면 의미 있는 정책을 강제할 수 없고,
개별 에이전트의 행위 기준선을 잡을 수 없으면 이상을 탐지할 수 없다.

2계층 중앙 도구 거버넌스의 문제의식은 섀도 AI다.
엔지니어가 입사해도 프로덕션 서버에 아무 패키지나 설치하지 않고
승인된 의존성과 검증된 라이브러리와 검토된 설정이라는 절차가 있는데,
중앙 도구 거버넌스가 없으면 팀마다 자기 에이전트를 위한 도구를 각자 만들고 연결한다.
이는 섀도 IT의 에이전트 역량 판이며 중복과 보안 공백과 가시성 부재라는 같은 문제를 만든다.
Agent Registry는 조직 전체의 에이전트·MCP 도구·엔드포인트의 중앙 카탈로그이고,
Cloud API Registry와 통합되어 Apigee와 MCP 서버를 통해
관리형 API를 안전한 에이전트 접근 가능 도구로 노출할 수 있다 —
기존 API 거버넌스가 자연스럽게 에이전트 거버넌스로 확장된다는 것이다.
개발자는 필요한 도구를 무엇이든 만들 수 있지만
프로덕션 에이전트가 쓰려면 등록과 승인을 거쳐야 하며,
이것이 개발자의 속도·유연성과 플랫폼 팀의 가시성·통제 사이에 건강한 긴장을 만든다.
Registry는 발견 가능성 문제도 푼다 —
새 에이전트를 만들 때 네 번째 BigQuery 커넥터를 만드는 대신 카탈로그를 뒤진다.
모든 도구에는 어떤 데이터에 접근하는지, 어떤 권한이 필요한지,
어떤 속도 제한이 걸려 있는지, 현재 어떤 에이전트가 쓰는지가 메타데이터로 붙어 있어서
도구의 취약점을 고칠 때 어떤 에이전트가 영향받는지 정확히 알 수 있다.

3계층 정책 집행은 현재 관행의 반대를 지적한다.
대부분의 에이전트 배포는 보안 규칙을 각 에이전트의 시스템 프롬프트나 애플리케이션 로직에 하드코딩한다.
고객 PII를 드러내지 못하게 하는 정책을 새로 추가하려면 모든 에이전트를 개별로 고쳐야 하고,
에이전트가 50개면 50번의 코드 변경, 50번의 배포, 50번의 테스트 주기,
그리고 하나를 빠뜨릴 50번의 기회가 생긴다.
Agent Gateway는 이를 뒤집는다 —
자연어로 보안 정책을 정의하는 중앙 집행 지점이고,
정책을 평이한 영어로 한 번 쓰면 게이트웨이를 지나는 모든 에이전트에 전역으로 적용된다.
정책을 추가하면 게이트웨이가 관장하는 모든 에이전트가 즉시 강제하고,
정책을 바꾸면 변경이 즉시 전파되며, 배포 주기도 에이전트별 코드 변경도
에이전트를 빠뜨릴 위험도 없다.
Gateway는 Model Armor도 통합해 프롬프트 인젝션과 민감 데이터 유출을 기본 방어한다 —
정책이 예상하지 못한 공격을 잡는 심층 방어 계층이며,
에이전트 행위를 조작하도록 설계된 적대적 입력, 학습 데이터 추출 시도,
접근 통제를 우회하려는 사회공학 공격이 그 대상이다.
알려진 위험에 대한 자연어 정책과 알려지지 않은 공격에 대한 Model Armor의 조합이
모든 개발 팀에 보안 전문성을 요구하지 않으면서 포괄적 보호를 제공한다는 주장이다.

4계층 행위 이상 탐지는 두 가지 상호보완적 접근을 쓴다.
통계 모델이 각 에이전트의 정상 행위 기준선을 세운다 —
전형적인 응답 시간, 흔한 도구 호출 패턴, 예상되는 데이터 접근량, 표준적인 추론 사슬 길이다.
에이전트가 기준선에서 크게 벗어나면 검토 대상으로 표시된다.
두 번째 접근은 LLM-as-a-judge 프레임워크로,
별도 모델이 에이전트의 추론 사슬을 검토해
증거에서 논리적으로 따라 나오지 않는 결론,
에이전트가 명시한 목표와 모순되는 권고,
에이전트의 정의된 범위 밖 요인에 영향받은 것으로 보이는 결정을 표시한다.
Agent Threat Detection은 악의적 활동에 특화된 별도 계층을 더한다 —
이상 탐지가 우발적 오설정과 행위 표류를 잡는다면
Threat Detection은 리버스 셸, 알려진 악성 IP 연결, 권한 상승 시도 같은
의도적 공격과 침해 지표를 감시한다.
둘 다 Security Command Center와 통합되어 통합 알림과 사고 대응으로 이어진다.

5계층 통합 보안 태세는 Security Command Center 기반의 Agent Security Dashboard다.
보안 팀은 여기서 어떤 에이전트가 어떤 모델을 쓰고 그 사이에 어떤 데이터가 흐르는지 관계를 매핑하고,
새 에이전트가 배포되면 자동으로 인벤토리에 잡히고 평가되며,
하부 운영체제와 언어 패키지의 취약점을 스캔해
에이전트가 쓰는 Python 의존성에 알려진 CVE가 있으면 표시하고,
다섯 계층 전체의 신호를 상관 분석한다 —
한 에이전트의 이상과 다른 에이전트의 정책 위반이 겹치면 조율된 공격을 의미할 수 있다는 것이다.
이 통합 뷰가 모든 CISO가 묻는 질문, 즉 지금 AI 에이전트로부터의 전체 위험이 무엇이냐에 답한다고 말한다.

맺음말의 논지는 복리다.
신원 → 레지스트리 → 게이트웨이 → 탐지 → 통합 태세 순서로 구현하면
가장 강한 기반이 되며, 이 스택을 일찍 구현한 팀은 복리로 쌓이는 이점을 얻는다 —
새 에이전트마다 신원 모델과 정책 프레임워크와 모니터링 인프라를 자동으로 물려받으므로
50번째 에이전트를 추가하는 한계 비용이 거의 0에 가깝다.
기다린 팀은 섀도 IT에서 본 것을 겪는다 —
관리되지 않는 에이전트가 늘 때마다 공격 표면과 감사 복잡도와
결국 치를 이관 비용이 점점 나빠지는 상황이다.
트윗은 6주짜리 글로벌 챌린지 홍보로 끝난다 —
클라우드 크레딧 500달러, Gemini Enterprise Agent Platform 전체 접근권,
9만 달러 상금 풀이 걸려 있다.

## 분석

### 5계층 거버넌스 스택

```text
[Agent Security Dashboard]  ← 통합 가시성
[Anomaly & Threat Detection] ← 행위 모니터링
[Agent Gateway]              ← 정책 집행 레이어
[Agent Registry]             ← 승인된 에이전트 카탈로그
[Agent Identity]             ← 암호화 신원
```

각 계층의 역할:

- **Agent Identity**: 에이전트마다 고유한 암호화 ID를 부여하여
  최소 권한 원칙에 기반한 접근 제어와 감사 추적을 가능하게 한다.

- **Agent Registry**: 조직 내 모든 에이전트, MCP 도구, 엔드포인트의
  중앙 카탈로그. 사내 npm 레포지터리처럼 플랫폼 팀이 승인한
  에셋만 프로덕션에서 사용할 수 있게 통제한다.

- **Agent Gateway**: 자연어로 작성된 보안 정책을 모든 에이전트에
  즉시 적용하는 “에이전트 생태계의 항공 교통 관제소”.
  MCP, A2A 같은 에이전트 프로토콜을 이해하고,
  Model Armor로 프롬프트 인젝션과 데이터 유출을 방어한다.

- **이상 및 위협 탐지**: 통계 기준선으로 행위 이상을 탐지하고,
  별도의 LLM 판사(LLM-as-a-judge)가 추론 패턴을 감사한다.
  리버스 셸, 악성 IP 연결 등 위협 활동도 실시간 탐지한다.

- **Agent Security Dashboard**: Security Command Center 기반의
  통합 시각화. 에이전트-모델 관계 매핑, 취약점 스캔,
  계층 간 신호 상관관계를 제공한다.

### 에이전트를 “조직원”처럼 관리한다는 발상

Google Cloud의 거버넌스 프레임워크는 에이전트에 인간 직원에 준하는
신원, 권한, 감사 체계를 부여한다.
이것은 단순한 기술적 추상화가 아니다.
에이전트가 기업 시스템에 접근하고, 외부 서비스를 호출하고,
다른 에이전트를 오케스트레이션하는 세계에서
“이 행동을 한 에이전트가 누구인가”를 추적하는 것은
법적 책임, 규정 준수, 사고 대응의 기반이 된다.
IAM이 클라우드 리소스에 적용한 것을 에이전트에 적용하는 논리다.

트윗은 이 비유를 문서 전체의 뼈대로 쓴다.
각 계층이 엔지니어링 조직의 대응물로 먼저 소개되고 —
신원은 사원증, 도구 거버넌스는 승인된 의존성 목록,
정책은 회사 규정, 이상 탐지는 보안 팀의 눈, 통합 태세는 대시보드 —
그다음에 제품 이름이 붙는다.
이 순서가 설득력의 원천이다.
독자가 이미 옳다고 믿는 관행을 먼저 확인시키고
그것이 에이전트에는 없다는 사실을 보여준 뒤 제품을 내놓기 때문에,
제품의 필요성을 따로 논증할 필요가 없어진다.

### 위험의 성격이 다르다는 첫 문장이 논의의 틀을 정한다

잘못 설정된 SaaS 도구는 수동적으로 데이터를 흘리지만
잘못 설정된 에이전트는 능동적으로 나쁜 행동을 한다는 대비는
이 글에서 가장 밀도 높은 한 문장이다.

기존 보안 모델은 대체로 누출을 막는 데 최적화되어 있다 —
접근 통제, 암호화, 데이터 분류, DLP가 모두 잘못된 사람이 데이터를 보게 되는 것을 겨냥한다.
에이전트는 데이터를 보는 데서 멈추지 않고 그것으로 무언가를 한다.
송금하고, 레코드를 지우고, 메일을 보내고, 배포를 트리거한다.
그러면 사고의 형태가 유출에서 행위로 바뀌고,
탐지 시점의 의미도 달라진다 —
유출은 사후에 발견해도 피해 범위를 산정할 수 있지만
행위는 사후에 발견하면 이미 되돌릴 수 없는 것이 있다.

이 구분이 4계층에 이상 탐지를 넣는 근거가 된다.
정책이 정의한 금지를 어기지 않았는데도 이상한 일이 벌어질 수 있고,
그것을 잡으려면 규칙이 아니라 기준선이 필요하다.
다만 트윗은 탐지 이후를 말하지 않는다 —
이상이 표시된 에이전트를 자동으로 멈추는지, 사람이 검토할 때까지 계속 도는지,
되돌릴 수 없는 행동을 하기 전에 개입할 수 있는지가 모두 비어 있다.

### Vertex AI의 완전한 흡수

“모든 Vertex AI 서비스와 로드맵이 Agent Platform을 통해 제공될 것”이라는 선언은
Google Cloud의 AI 전략 전환점을 의미한다.
Vertex AI는 더 이상 독립 서비스가 아니라 Agent Platform의 하부 레이어가 된다.
이는 클라우드 AI 서비스의 단위가 “모델”에서 “에이전트”로 이동했음을
플랫폼 아키텍처 수준에서 공식화한 것이다.

## 비평

### 엔지니어링 조직 비유는 설득력의 원천이자 논증의 사각지대다

에이전트를 직원처럼 다루라는 비유는 다섯 계층을 한 번에 이해시키는 데 탁월하지만,
정확히 그 매끄러움 때문에 비유가 깨지는 지점을 검토하지 않고 넘어간다.

엔지니어는 복제되지 않는다.
채용에는 몇 주가 걸리고 그 마찰 자체가 통제 장치로 작동한다 —
사람을 뽑는 속도가 조직이 감당할 수 있는 신원 관리의 상한을 자연스럽게 정한다.
에이전트는 API 호출 한 번으로 늘어나며 50번째 에이전트의 한계 비용이 0에 가깝다는 것이
트윗 자신의 자랑이다.
같은 문장이 거버넌스 쪽에서는 경고가 되어야 한다 —
생성 비용이 0에 가까운 주체에 대해 신원과 권한을 사람이 정의하는 모델은
에이전트 수가 늘수록 유지되지 않는다.
각 에이전트가 어떤 테이블과 어떤 버킷에 접근하는지 정확히 정의하라는 요구는
에이전트가 50개일 때는 규율이지만 5,000개가 되면 그 자체가 병목이다.

두 번째로 엔지니어는 자기 권한이 부족하면 말한다.
에이전트는 권한이 부족하면 실패하거나, 더 나쁘게는 우회 경로를 찾는다.
최소 권한을 세밀하게 적용할수록 권한 부족으로 인한 실패가 늘고,
그 실패를 줄이려는 압력이 권한을 조용히 넓히는 방향으로 작동한다.
이 되먹임은 사람 조직에는 없는 것인데 비유가 그것을 가린다.

세 번째로 조직은 신뢰를 시간에 따라 쌓는다.
수습 기간이 있고, 권한이 단계적으로 늘고, 평판이 축적된다.
트윗의 모델에는 시간 축이 없다 —
에이전트는 배포되는 순간 정해진 권한을 전부 갖는다.
새 에이전트에 제한된 권한으로 시작해 실적에 따라 넓히는 개념이 없다는 것은,
비유를 끝까지 밀지 않았다는 뜻이다.

### 자연어 정책의 즉시 전역 적용은 같은 크기의 위험을 만든다

정책을 평이한 영어로 한 번 쓰면 전역으로 적용되고 변경이 즉시 전파된다는 것이
Agent Gateway의 핵심 판매 논리다.
배포 주기도 없고, 에이전트별 코드 변경도 없고, 빠뜨릴 위험도 없다는 것이다.

그런데 배포 주기가 없다는 것은 카나리도 없고 단계적 롤아웃도 없다는 뜻이다.
50개 에이전트를 개별로 고치는 방식이 느린 이유는 각 변경이 검토와 테스트를 거치기 때문이고,
그 느림이 잘못된 정책이 전체에 퍼지는 것을 막아준다.
문장 하나를 잘못 써서 모든 에이전트가 동시에 멈추거나
반대로 모든 에이전트가 동시에 허용해서는 안 될 것을 허용하게 되는 시나리오를
트윗은 전혀 다루지 않는다.

자연어라는 선택은 이 위험을 키운다.
평이한 영어로 쓴 정책은 사람이 읽기 쉽지만 두 사람이 다르게 읽을 수 있고,
집행하는 것은 사람이 아니라 모델이다.
그러면 정책의 실제 의미는 그것을 해석하는 모델의 현재 버전이 정하며,
모델이 업데이트되면 같은 정책 문장의 집행 결과가 달라질 수 있다.
정책 문장은 그대로인데 동작이 바뀌는 이 상황은 감사 관점에서 최악이다 —
무엇이 언제부터 달라졌는지 diff로 확인할 수 없기 때문이다.
정책 충돌 해소 규칙, 우선순위, 예외 처리, 테스트 방법이 모두 언급되지 않는다는 점도 같은 공백에 속한다.

Model Armor를 알려지지 않은 공격에 대한 심층 방어로 배치한 구성도 다시 볼 필요가 있다.
알려진 위험은 자연어 정책이, 알려지지 않은 공격은 Model Armor가 맡는다는 분업은 깔끔하지만,
두 층 모두 모델이 판단한다는 점에서 독립적이지 않다.
프롬프트 인젝션이 정책 해석기와 Model Armor를 동시에 속이는 입력을 찾는 것은
서로 다른 원리의 두 방어를 뚫는 것보다 쉽다.

### 섀도 IT 비유는 이 스택 자체에도 겨눠진다

트윗의 프레임은 관리되지 않는 에이전트가 2015년의 섀도 IT라는 것이다.
그런데 섀도 IT가 왜 생겼는지를 함께 봐야 이 비유가 완성된다 —
공식 IT가 너무 느리고 까다로워서 사람들이 우회했기 때문이다.

트윗은 이 위험을 절반만 인식한다.
개발자가 도구를 무엇이든 만들 수 있지만 프로덕션에 쓰려면 등록과 승인을 거쳐야 한다는 구조를
건강한 긴장이라고 부르는 대목이 그것이다.
긴장이 건강하려면 승인이 빨라야 하는데, 승인 절차의 처리 시간이나 담당 주체나
거절 시 이의 제기 경로에 대한 언급이 없다.
승인이 느려지는 순간 개발자는 게이트웨이를 지나지 않는 경로를 찾을 것이고,
그것이 정확히 이 스택이 막으려 한다는 섀도 AI다.

즉 이 거버넌스 스택의 성패는 다섯 계층의 기술적 완성도가 아니라
승인 대기 시간이라는 하나의 운영 지표에 달려 있다.
그리고 그 지표는 제품이 아니라 조직이 만든다.
Google Cloud가 팔 수 있는 것은 통제 지점이고,
그 지점이 병목이 되지 않게 하는 일은 구매자의 몫인데
트윗은 이 비대칭을 언급하지 않는다.

### 발표 시점의 정보 공백과 판매 문맥

발표 수준에서 구체적인 구현 세부사항과 가격 정보가 공개되지 않았다.
자연어 정책이 즉시 적용된다는 주장은 매력적이지만
자연어의 모호성이 실제 보안 정책에서 어떻게 처리되는지,
정책 충돌은 어떻게 해소되는지에 대한 설명이 없다.
또한 Google Cloud의 에이전트 생태계에 종속(vendor lock-in)되는 위험도 존재한다.
Agent Identity, Agent Registry가 Google Cloud 인프라에 종속된다면
멀티클라우드 에이전트 환경을 구축하는 것이 어려워진다.

트윗은 이 종속을 오히려 이점으로 서술한다 —
새 에이전트마다 신원 모델과 정책 프레임워크와 모니터링을 자동으로 물려받으므로
50번째 에이전트의 한계 비용이 거의 0이라는 복리 논증이다.
이 논증은 참이지만 방향이 양쪽이다.
같은 복리가 이탈 비용에도 작동한다 —
50개 에이전트가 모두 한 신원 체계와 한 정책 프레임워크에 묶여 있으면
플랫폼을 바꾸는 비용도 에이전트 수에 비례해 커진다.
일찍 채택한 팀이 얻는 복리 이점과 나중에 겪을 이관 비용은 같은 곡선의 두 이름이고,
트윗은 후자를 기다린 팀의 문제로만 배치한다.

같은 게시물이 9만 달러 상금과 500달러 크레딧이 걸린 6주 챌린지 홍보로 끝난다는 점도
읽는 방식에 영향을 준다.
다섯 계층의 분석은 그 자체로 유용하지만,
이것이 채택을 앞당기기 위한 문서라는 사실은 무엇이 강조되고 무엇이 빠졌는지를 설명한다.
빠진 것 — 승인 지연, 정책 오작동, 이관 비용, 탐지 이후의 대응 — 은
모두 구매 결정을 늦출 수 있는 항목이다.

HN에 달린 반응은 짧지만 이 문제를 세는 것으로 보여준다.
Jayakumark는 이 블로그 글 하나에 agent라는 단어가 142번 나온다며 지나치다고 적었고,[^Jayakumark]
upstreamutopia는 다른 에이전트 플랫폼보다 더 에이전트다워 보이려는 시도로 읽히며
유용한 것이라기보다 과장에 가깝다고 동의했다.[^upstreamutopia]
3점 2댓글이라는 반응 크기 자체가 발표의 무게와 개발자 커뮤니티의 관심 사이 간격을 보여준다.
다섯 계층 프레임이 실제로 유용한 사고 도구라는 점과
그 프레임이 제품 이름 다섯 개를 감싸고 있다는 점이 동시에 참이며,
독자가 해야 할 일은 전자를 가져가되 후자와 분리하는 것이다.

## 인사이트

### 에이전트 거버넌스는 IAM의 진화다

클라우드 시대 초기에 “누가 어떤 리소스에 접근할 수 있는가”를 정의하는
IAM(Identity and Access Management)은 보안의 중심축이 되었다.
에이전트 시대에 같은 질문이 반복된다:
“어떤 에이전트가 어떤 도구를, 어떤 조건에서 사용할 수 있는가.”
Google Cloud의 거버넌스 스택은 IAM이 수행한 역할을 에이전트 레이어에서 재수행한다.
이 유사성은 우연이 아니다.
에이전트는 사실상 자율적으로 행동하는 새로운 종류의 “주체(principal)”이며,
모든 보안 아키텍처는 새로운 주체가 등장할 때마다 재설계 압력을 받는다.

흥미로운 점은 에이전트 거버넌스가 단순히 IAM을 확장하는 것이 아니라
새로운 차원을 추가한다는 것이다.
인간 사용자는 의도를 갖고 행동하며 그 의도를 언어로 설명할 수 있지만,
에이전트의 “추론 패턴”은 외부에서 완전히 관찰하기 어렵다.
LLM-as-a-judge로 에이전트의 추론을 감사한다는 접근은
이 문제에 대한 초기 시도이지만, 감사자 자신이 LLM이라는 재귀적 문제를 내포한다.
“누가 감시자를 감시하는가”라는 고전적 질문이 AI 거버넌스에서도 되풀이된다.

트윗이 밝힌 판정 기준을 보면 이 재귀 문제의 크기가 더 분명해진다.
LLM 판사가 표시하는 것은 증거에서 논리적으로 따라 나오지 않는 결론,
명시한 목표와 모순되는 권고, 정의된 범위 밖 요인에 영향받은 결정이다.
셋 다 판정 자체가 추론을 요구하는 항목이고,
그 추론을 하는 모델이 피감사 모델과 같은 종류의 실패에 노출된다.
그리고 프롬프트 인젝션이 에이전트의 추론 사슬을 오염시켰다면
그 사슬을 읽는 판사도 같은 텍스트를 읽게 된다.
통계 기준선 쪽이 이 문제에서 자유롭다는 점이 오히려 눈에 띈다 —
응답 시간과 도구 호출 패턴과 데이터 접근량은 언어로 속일 수 없는 신호다.

### 에이전트 레지스트리는 기업 AI의 새로운 패키지 관리자다

Agent Registry를 “사내 npm 레포지터리”에 비유한 것은 정확한 유추다.
npm이 JavaScript 생태계에서 “신뢰할 수 있는 패키지”의 관문 역할을 하듯,
Agent Registry는 기업 내에서 “승인된 에이전트와 도구”의 관문이 된다.
이 유추는 기회와 위험을 동시에 시사한다.
npm이 공급망 공격의 표적이 된 것처럼,
Agent Registry도 승인된 에이전트로 위장한 악성 에이전트의 잠재적 표적이 된다.
에이전트가 다른 에이전트를 실행하고 도구를 호출하는 체인에서
하나의 타협된 에이전트가 전체 워크플로를 오염시킬 수 있다.
에이전트 공급망 보안(agent supply chain security)은
소프트웨어 공급망 보안과 같은 수준의 주의가 필요한 문제가 될 것이다.

트윗이 언급한 도구 메타데이터가 이 방향에서 가장 실용적인 부분이다.
각 도구가 어떤 데이터에 접근하고, 어떤 권한을 요구하고,
어떤 속도 제한이 걸려 있고, 현재 어떤 에이전트가 쓰는지를 기록해 두면
취약점이 발견되었을 때 영향 범위를 즉시 산정할 수 있다.
이것은 SBOM(소프트웨어 자재 명세서)이 공급망 보안에서 한 역할과 정확히 같으며,
에이전트판 SBOM이라 부를 만하다.
그리고 SBOM의 역사가 보여주듯 이 목록의 가치는 완전성에 달려 있다 —
등록되지 않은 도구가 하나라도 프로덕션에 있으면 영향 범위 산정은 틀린 답을 준다.

### 신원을 1계층에 둔 것은 순서가 아니라 관측 가능성의 전제 조건이다

트윗은 신원이 1계층인 이유를 위의 모든 것이 그것에 의존하기 때문이라고 설명하고,
구별되는 신원이 없으면 정책을 강제할 수 없고 기준선을 잡을 수 없다고 덧붙인다.
두 번째 이유가 더 중요한데 글은 그것을 지나가듯 말한다.

정책 강제는 사실 신원 없이도 부분적으로 가능하다 —
게이트웨이가 요청 내용만 보고 PII 유출을 막을 수 있다.
그러나 이상 탐지는 다르다.
기준선은 정의상 개체별로 세워지며,
모든 에이전트가 하나의 서비스 계정을 공유하면
그 계정의 행위는 50개 에이전트 행위의 합이 되고 개별 이상은 평균에 묻힌다.
에이전트가 늘수록 이 희석은 심해지므로,
공유 자격 증명 환경에서는 에이전트를 많이 배포할수록 탐지 능력이 떨어진다.

이 관찰은 도입 순서에 실질적 의미를 준다.
신원을 나중에 하면 되는 기반 작업으로 미루는 조직이 흔한데,
신원이 없는 기간 동안 쌓이는 것은 기술 부채만이 아니라 관측 데이터의 공백이다.
나중에 신원을 도입해도 그 이전 기간의 기준선은 만들어지지 않으며,
정상 행위가 무엇이었는지 알 수 없는 상태에서 이상 탐지를 켜면
초기 몇 주는 오탐으로 가득 찬다.

같은 논리가 회수 가능성에도 적용된다.
트윗은 문제가 생긴 에이전트의 신원만 회수해 나머지에 영향을 주지 않는다는 점을 강조하는데,
공유 자격 증명에서는 회수가 전면 중단을 뜻한다.
사고 대응 시 선택지가 아무것도 안 하기와 전부 멈추기 둘뿐인 상태가 되고,
그러면 실무에서는 대개 전자를 고르게 된다 —
멈추는 비용이 너무 커서 위험을 감수하는 쪽으로 기울기 때문이다.
신원 세분화의 진짜 가치는 감사 추적보다 이 선택지의 확보에 있다.

### 능동적으로 행동하는 주체를 다루려면 탐지가 아니라 되돌리기가 필요하다

트윗의 첫 문장은 수동적 유출과 능동적 행동을 구분하며 시작하는데,
다섯 계층의 대응은 모두 탐지와 예방에 머문다.
행동이 이미 일어난 뒤에 대한 이야기가 없다.

이 공백은 구조적이다.
보안 스택은 전통적으로 막기와 알기로 구성되어 왔고,
되돌리기는 애플리케이션과 데이터 계층의 책임이었다.
그런데 에이전트가 자율적으로 여러 시스템에 걸쳐 행동하면
그 행동의 되돌리기도 여러 시스템에 걸치게 되고,
어느 한 계층도 그것을 책임지지 않는다.
Finance Agent가 잘못된 송금을 실행하고, 확인 메일을 보내고, 원장을 갱신했다면
신원을 회수해도 세 결과는 남는다.

여기서 필요한 것은 새로운 계층이다 —
에이전트의 모든 부작용 있는 행동을 보상 트랜잭션과 함께 기록하고,
사고 시 그 역순으로 실행할 수 있게 하는 층이다.
분산 시스템에서 사가(saga) 패턴이 하는 일이고,
개념적으로는 이미 잘 알려져 있지만 에이전트 도구 호출에 적용된 사례는 드물다.
Agent Registry가 각 도구의 메타데이터를 갖는다는 점을 생각하면
그 메타데이터에 이 도구의 보상 동작이라는 항목을 더하는 것이 자연스러운 확장이다.

이 계층이 없는 동안 조직이 취할 수 있는 현실적 대응은 두 가지다.
되돌릴 수 없는 행동을 하는 도구를 아예 등록하지 않거나,
그런 도구만 사람 승인을 강제하는 것이다.
전자가 안전하고 후자가 유용하며, 대부분의 조직은 후자로 갈 것이다.
그렇다면 승인 대기열이 다시 병목이 되고, 앞서 지적한 승인 지연 문제로 돌아온다 —
이 스택의 모든 미해결 문제가 결국 사람이 얼마나 빨리 판단할 수 있느냐 하나로 수렴한다는 점이
이 아키텍처가 아직 답하지 않은 가장 큰 질문이다.
