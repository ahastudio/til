# 1024바이트로 만든 파이썬 인터프리터

원문: [Making a Python interpreter in 1024 bytes](https://austinhenley.com/blog/python1024.html)

HN 토론: <https://news.ycombinator.com/item?id=49591876> (310점, 106개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/n0zgj1/making_python_interpreter_1024_bytes>

GN 토론: <https://news.hada.io/topic?id=33329>

## 요약

Austin Z. Henley가 2026년 9월 6일에 쓴 글이다.
저자는 정확히 1024바이트의 C 코드로 파이썬 인터프리터를
만든 과정을 설명한다.
가독성 있게 작성한 원본 버전은 4800바이트가 넘지만, 코드
골프 기법을 적용해 최종적으로 1024바이트까지 줄였다.

이 인터프리터가 지원하는 기능은 다음과 같다.
한 글자짜리 정수 변수와 리터럴, 우선순위가 적용된 산술
연산자(`+`, `-`, `*`, `%`), 비교 연산자(`<`, `>`, `<=`,
`>=`, `==`), 제어 흐름(`if`/`else`, `while` 루프,
`for`-`in`-`range` 루프), 함수 정의와 재귀 호출, 들여쓰기
기반 코드 블록, 문자열과 정수 표현식을 위한 `print`문,
그리고 주석이다.

기술적 접근 방식은 CPython의 모델을 따르지 않는다.
중간 표현(intermediate representation)을 생성하지 않고
파싱과 동시에 직접 실행하는 방식이다.
저자는 “아무것도 컴파일되지 않으므로, 루프는 뒤로
점프해서 매 반복마다 소스를 다시 파싱하는 방식으로
작동한다”고 설명한다.
제어 흐름은 재귀를 처리하기 위해 C의 콜 스택에 의존하고,
루프는 다시 파싱할 수 있도록 소스 위치 참조를 유지한다.

축소(minification) 과정에는 여러 전략이 동원됐다.
한 글자 이름 짓기, 임시 저장을 위한 전역 변수 사용, 논리
연산자 대신 비트 연산자 사용, 문자 리터럴 대신 ASCII 값
대입 등이다.

## 분석

### 파싱과 실행을 분리하지 않는 결정이 크기 제약과 정확히 맞물린다

일반적인 인터프리터는 소스를 토큰화하고 파스 트리나
바이트코드 같은 중간 표현으로 변환한 뒤 그것을 실행한다.
이 인터프리터는 그 중간 단계를 통째로 생략하고 파싱하는
동안 곧바로 실행한다.
이 설계는 우연한 단순화가 아니라 1024바이트라는 제약이
강제한 선택이다.
중간 표현을 만들려면 그 표현을 저장할 자료구조와 그것을
순회할 코드가 따로 필요한데, 그럴 여유가 없는 크기
제약에서는 “매번 다시 읽는” 비효율을 감수하는 대신 코드
자체의 크기를 줄이는 쪽을 택하는 것이 합리적이다.
루프가 실행될 때마다 소스를 재파싱하는 것은 CPU 시간을
낭비하지만, 그 낭비되는 시간은 1024바이트 제약이 요구하지
않는 유일한 자원이다.

### C의 콜 스택을 재귀 처리기로 재활용하는 것은 자원 제약 하의 위임 전략이다

재귀 함수 호출을 지원하기 위해 별도의 호출 스택 자료구조를
구현하는 대신 C 언어 자체의 콜 스택을 그대로 활용한 것은,
이미 존재하는 인프라를 다시 만들지 않고 위임하는 전략이다.
이는 “최소한의 코드로 최대한의 기능을 구현한다”는 코드
골프의 일반 원칙을 넘어, 언어 구현체를 만들 때 호스트
언어가 이미 제공하는 메커니즘을 얼마나 적극적으로 재사용할
수 있는지를 보여주는 사례다.
파이썬 자체의 재귀 깊이 제한이 실제로는 C 스택 크기에
의해 결정된다는 사실을 생각하면, 이 선택은 오히려 원본
CPython의 재귀 구현 방식과 원리적으로 크게 다르지 않다.

### 코드 골프 기법의 목록이 “가독성 대 크기”라는 트레이드오프를 명시적으로 드러낸다

한 글자 변수명, 전역 변수 재사용, 비트 연산자 대체, ASCII
값 직접 대입 같은 기법들은 모두 코드의 가독성을 희생해
바이트 수를 줄이는 결정이다.
가독성 있는 버전이 4800바이트가 넘고 최종본이 1024바이트라는
것은, 이 프로젝트에서 실제 “압축”된 것이 논리 자체가
아니라 그 논리를 사람이 이해할 수 있게 표현하는 데
들어가는 여분의 바이트라는 것을 보여준다.
이는 프로그램의 본질적 복잡도(어떤 기능을 구현하는가)와
우연적 복잡도(그것을 어떻게 표기하는가)를 분리해서 볼 수
있게 하는 좋은 사례다.

## 비평

### “파이썬 인터프리터”라는 이름이 실제 지원 범위를 과장할 위험이 있다

이 프로젝트가 지원하는 기능은 한 글자 정수 변수, 기본
산술과 비교 연산자, 제어 흐름, 함수 정의와 재귀뿐이다.
실제 파이썬이 가진 문자열 조작, 리스트와 딕셔너리 같은
자료구조, 클래스, 예외 처리, 표준 라이브러리 등은 전혀
다루지 않는다.
“파이썬 인터프리터”라는 제목은 이 프로젝트가 파이썬
문법의 아주 좁은 부분집합(subset)만 구현했다는 것을
명확히 전달하지 못하며, 독자가 실제 지원 범위를 확인하기
전까지는 훨씬 더 완전한 구현으로 오해할 여지가 있다.

이 비판은 HN과 Lobste.rs 양쪽에서 정확히 같은 지점을
겨냥해 제기됐다.
HN의 Scubabear68은 “이것이 진짜 ‘해석’하고 있는 것은
작게 지어낸 언어일 뿐이며, 파이썬은커녕 파이썬의 세 자릿수
배수 범위 안에도 들지 못한다”고 실망감을 표했다.[^scubabear68]
jrdres는 더 구체적으로 파고들어, 이 구현이 오류 검사를
수행하는 C4(작지만 완전한 C 컴파일러)와도 다르고, 모든
것을 그냥 넘겨짚는 Sector C보다도 거칠다고 지적했다.
`f`는 무조건 `for [x] in range[y]` 하나만을 뜻하고, `w`는
무조건 `while`, `i`는 무조건 `if`, `d`는 무조건 `def`,
`p`는 무조건 `print(`로 취급하는 식이어서, 키워드 자체가
아니라 첫 글자만으로 문법을 결정한다는 것이다.
그는 이 구현이 “Tiny Python”이라 부르기에는 조금 지나치게
단순하다며, 몇 킬로바이트만 더 허용한다면 리스트와 딕셔너리
정도는 보고 싶다고 덧붙였다(Lisp는 그 정도면 해낸다는
것이다).[^jrdres]
Lobste.rs의 mdaniel도 같은 맥락에서 “클릭베이트를 좀
자제하라”며, 제목을 “나는 코드 인터프리터를 코드
골프했다”로 썼어야 한다고 꼬집었다.[^mdaniel]
세 반응을 종합하면, 이 글의 비평이 지적한 “이름과 실제
범위 사이의 간극”이 단순한 우려가 아니라 실제 독자들이
가장 먼저 걸려 넘어진 지점이었다는 것을 확인할 수 있다.

### 매 반복마다 소스를 재파싱하는 방식의 성능 비용이 다뤄지지 않는다

루프가 실행될 때마다 소스 코드를 다시 파싱한다는 설계는
크기 제약 하에서는 합리적이지만, 이 결정이 실제 실행
속도에 미치는 영향은 이 글에서 전혀 정량화되지 않는다.
반복 횟수가 많은 루프에서는 매번 같은 텍스트를 문자
단위로 다시 훑는 비용이 누적될 것이 분명한데, 어느 정도
규모의 반복에서 이 비효율이 실질적으로 체감되는지에 대한
벤치마크나 언급이 없다.
이는 이 프로젝트가 “작동하는가”를 보여주는 데는 충분하지만
“얼마나 느린가”에 대한 정보는 주지 않는다는 뜻이다.

HN의 userbinator는 이 설계를 정확히 짚으며 중요한 정정을
덧붙였다.
1024바이트는 C 소스 코드의 크기이지 컴파일된 바이너리의
크기가 아니며, 실제 바이너리는 그보다 몇 배 더 크다는
것이다.
그는 “뒤로 점프해서 매 반복마다 소스를 재파싱한다”는
설계가 사실 DOS의 `.bat` 파일 처리 방식과 동일한 원리라고
짚었다(유닉스 계열 셸도 같은 방식인지는 써 볼 필요가
없었다며 확언하지 않았다).
같은 밀도로 유명한 다른 사례로 J Incunabulum(의도적으로
골프하지는 않았지만 극도로 조밀한 배열 프로그래밍 언어
구현체)을 들며, 배열 프로그래밍 문화권에서는 이 정도의
코드 밀도가 오히려 표준으로 여겨진다고 덧붙였다.[^userbinator]
이 지적은 본문의 비평이 요구했던 정량적 성능 정보를 채워주지는
않지만, 적어도 “1024바이트”라는 수치가 정확히 무엇을
가리키는지, 그리고 이런 재파싱 방식이 이 프로젝트만의
기이한 발명이 아니라 자원 제약 환경에서 반복적으로
재발명돼 온 패턴이라는 역사적 맥락을 보충한다.

### 코드 골프 프로젝트의 교육적 가치와 실용적 가치가 구분되지 않은 채 서술된다

이 글은 축소 기법들을 나열하지만, 이 프로젝트가 실제로
누구에게 어떤 가치가 있는지는 명시하지 않는다.
1024바이트라는 제약 자체는 실용적 필요에서 나온 것이
아니라 인위적으로 설정한 도전 과제이며, 이런 종류의 코드
골프 프로젝트가 주는 가치는 대체로 실용성이 아니라
교육적 통찰(파서와 인터프리터의 최소 요건이 무엇인지 보여주는
것)에 있다.
글이 이 구분을 명시적으로 하지 않으면, 독자는 이 코드가
실무에 응용할 만한 패턴인지 아니면 순전히 지적 유희인지를
헷갈릴 수 있다.

## 인사이트

### 극단적 제약은 구현의 본질을 드러내는 진단 도구가 된다

1024바이트라는 인위적 제약을 통해 이 프로젝트는 “파이썬
인터프리터를 만드는 데 최소한 무엇이 필요한가”라는 질문에
실증적으로 답한다.
이는 일반적인 소프트웨어 개발에서는 좀처럼 얻기 어려운
종류의 통찰이다.
프로덕션 코드에서는 항상 견고성, 유지보수성, 확장성 같은
부가 요구사항이 최소 구현 위에 계속 쌓이기 때문에, 어떤
기능이 정말 “핵심”이고 어떤 것이 편의를 위한 부가 장치인지
구분하기 어렵다.
극단적인 크기 제약은 이 군더더기를 강제로 제거해, 언어
구현의 최소 골격이 무엇인지를 드러내는 일종의 진단 도구로
기능한다.

### 코드 골프 문화는 컴파일러 이론 교육의 실습판이다

파싱과 실행을 분리하지 않는 이 인터프리터의 설계는, 학부
컴파일러 수업에서 배우는 “인터프리터 대 컴파일러”라는
전통적 구분을 극단적으로 단순화된 형태로 체험하게 해준다.
정규 교육 과정에서는 렉서, 파서, AST, 바이트코드 생성 같은
각 단계를 순서대로 배우지만, 이 프로젝트처럼 그 모든
단계를 생략하고 “파싱하면서 바로 실행한다”는 가장 원시적인
형태의 인터프리터를 직접 눈으로 보는 경험은 각 단계가
왜 필요한지를 역설적으로 더 선명하게 이해시킨다.
이는 코드 골프라는 취미 문화가 단순한 유희를 넘어, 정규
교육이 추상화 계층으로 감춰 놓은 개념을 다시 드러내는
비공식적 학습 도구로 기능한다는 것을 보여준다.

### 극소 크기 소프트웨어의 전통은 자원 제약이 사라진 시대에도 계속 재발명된다

메모리와 저장 공간이 사실상 무한대로 여겨지는 지금 시대에,
1024바이트짜리 인터프리터를 만드는 시도는 실용적 필요와
무관하게 계속 등장한다.
이는 1980~90년대 데모씬(demoscene)의 극소 용량 실행 파일
전통이나, IOCCC(International Obfuscated C Code Contest)
같은 대회 문화와 같은 계보에 있다.
하드웨어 자원 제약이 실질적으로 해소된 이후에도 이런
극단적 최소화 시도가 계속되는 이유는, 그것이 더 이상
경제적 필요가 아니라 순수한 지적 도전과 자기 과시의
영역으로 옮겨갔기 때문이다.
이는 기술적 제약이 사라져도 그 제약이 만들어냈던 창의성의
형식 자체는 문화적 관성으로 살아남는다는 것을 보여주는
사례이며, 앞으로도 새로운 언어나 새로운 도전 과제(예:
LLM 토큰 예산 안에서 실행되는 인터프리터)를 대상으로 같은
전통이 반복될 가능성이 크다.

Lobste.rs의 fanf는 이 계보를 실제 하드웨어 역사로
뒷받침한다.
매 반복마다 소스를 재파싱하는 이런 저메모리 제어 흐름
방식은 매우 느리다는 단점에도 불구하고 오래된 컴퓨터에서
상당히 흔한 방식이었다는 것이다.[^fanf]
이는 이 인터프리터의 설계가 새로운 발명이 아니라, 메모리가
실제로 희소했던 시절에 널리 쓰이던 실용적 타협을 지금의
인위적 제약 아래서 다시 불러온 것에 가깝다는 것을 보여준다.
한편 HN의 teddyh는 이런 초경량 언어 구현이 순전히 취미의
영역만은 아니라는 것을 보여주는 실제 프로덕션 사례를
언급했다.
Snek이라는 언어는 “겨우 수 킬로바이트의 플래시와 RAM만
가진 프로세서를 대상으로 하는 초소형 임베더블 언어”로
실제 임베디드 환경에 배포되고 있다는 것이다.[^teddyh]
이는 이 글이 다루는 종류의 극단적 최소화가 데모씬이나
코드 골프 같은 순수 취미의 영역에만 머무르지 않고, 지금도
자원이 진짜로 희소한 임베디드 하드웨어에서는 여전히 실용적
필요로 존재한다는 것을 보여준다.
