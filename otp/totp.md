# TOTP: 공유한 비밀 키와 시계만으로 30초마다 바뀌는 인증 코드를 만드는 방법

원문: [RFC 6238: TOTP: Time-Based One-Time Password Algorithm](https://www.rfc-editor.org/rfc/rfc6238)

HN 토론: <https://news.ycombinator.com/item?id=20132477> (2점, 2개 댓글)

## 소개

TOTP(Time-Based One-Time Password)는 사용자의 기기와 서버가 같은 비밀 키와 같은
시계를 가지고, 서로 통신하지 않고도 같은 6자리 코드를 계산하게 하는 방식이다.
2011년 5월에 나온 RFC 6238(정보용 문서)이 정의하고,
계산의 핵심은 2005년 12월의 RFC 4226(HOTP)에 있다.
TOTP는 HOTP의 카운터를 “시간 단계 번호”로 바꾼 것이다.
`T = floor((현재 Unix 시각 − T0) / X)`이고, 기본값은 X가 30초,
T0가 Unix 기점(0)이다.
시각이 59초면 T는 1이고 60초면 T는 2다.

이 문서가 다루는 범위는 알고리즘, 서버가 정해야 할 값, 흔한 구현 실수다.
비밀 키를 사용자에게 건네는 과정(QR 코드 등)은 RFC 6238이 범위 밖이라고 밝히고
RFC 6030을 가리킨다.

## 동작 방식

### 코드가 만들어지는 세 단계

서버와 기기는 같은 비밀 키 K와 같은 T를 넣어 같은 계산을 한다.
1단계로 `HMAC(K, T)`를 계산한다. 기본은 SHA-1이고 결과는 20바이트다.
2단계는 동적 절삭(dynamic truncation)이다. 결과의 마지막 바이트의 아래 4비트를
위치(offset)로 삼아 거기서 4바이트를 꺼내고, 부호 문제를 없애려고
최상위 비트를 지운다.[^rfc4226]
3단계로 그 정수를 `10^자릿수`로 나눈 나머지를 취하고 앞을 0으로 채운다.

기기와 서버가 통신하지 않는 이유는 입력이 T와 K뿐이기 때문이다.
T는 현재 시각만 알면 계산되므로(요구 사항 R1), 둘이 같은 30초 구간 안에 있으면
같은 코드가 나온다.

### 같은 구간의 코드는 같다

RFC는 같은 시간 단계 안에서 만든 코드가 모두 같다고 짚는다.
그래서 서버가 코드를 받은 시각과 기기가 만든 시각이 다른 구간에 놓일 수 있고,
서버는 받은 시각의 코드뿐 아니라 직전 구간의 코드도 비교해야 한다.
RFC는 전송 지연으로 허용하는 구간을 최대 한 단계로 권고한다.

## 구현하기

아래 코드는 RFC의 규칙을 그대로 옮긴 Python 구현이다.
`verify`는 맞은 단계 번호를 돌려주고,
호출하는 쪽이 그 번호를 저장해 두었다가 다음 검증에 `last_used_step`으로 넘겨야
같은 코드를 두 번 받지 않는다.

```python
import hashlib
import hmac
import struct
import time


def hotp(key: bytes, counter: int, digits: int = 6, algo=hashlib.sha1) -> str:
    # 1단계: HMAC(key, 카운터 8바이트, 빅 엔디언)
    mac = hmac.new(key, struct.pack(">Q", counter), algo).digest()
    # 2단계: 마지막 바이트의 아래 4비트가 가리키는 위치에서 4바이트를 꺼낸다
    offset = mac[-1] & 0x0F
    # 3단계: 최상위 비트를 지워 부호 문제를 없애고, 자릿수만큼 나머지를 취한다
    code = struct.unpack(">I", mac[offset:offset + 4])[0] & 0x7FFFFFFF
    return str(code % 10**digits).zfill(digits)


def totp(key: bytes, at: float | None = None, step: int = 30, t0: int = 0,
         digits: int = 6, algo=hashlib.sha1) -> str:
    now = time.time() if at is None else at
    return hotp(key, int((now - t0) // step), digits, algo)


def verify(key: bytes, code: str, last_used_step: int, step: int = 30,
           window: int = 1, digits: int = 6, at: float | None = None):
    """맞으면 사용한 시간 단계(step 번호)를, 틀리거나 재사용이면 None을 돌려준다."""
    now_step = int((time.time() if at is None else at) // step)
    for s in range(now_step - window, now_step + window + 1):
        if s <= last_used_step:  # 이미 쓴 단계와 그 이전은 받지 않는다
            continue
        if hmac.compare_digest(hotp(key, s, digits), code):
            return s
    return None


if __name__ == "__main__":
    # RFC 6238 부록 B의 시험 값(SHA-1, 8자리)
    key = b"12345678901234567890"
    vectors = {59: "94287082", 1111111109: "07081804", 1111111111: "14050471",
               1234567890: "89005924", 2000000000: "69279037"}
    for t, want in vectors.items():
        got = totp(key, at=t, digits=8)
        print(t, got, want, "OK" if got == want else "MISMATCH")
    first = verify(key, totp(key, at=100), last_used_step=0, at=100)
    print("처음 입력:", first, "| 같은 코드 다시:", verify(key, totp(key, at=100), first, at=100))
    print("시계가 30초 앞선 기기:", verify(key, totp(key, at=130), 0, at=100) is not None,
          "| 90초 앞선 기기:", verify(key, totp(key, at=190), 0, at=100) is not None)
```

## 값 정하기

| 값              | 시작 값                          | 근거                                                                                               |
| --------------- | -------------------------------- | -------------------------------------------------------------------------------------------------- |
| 시간 단계(X)    | 30초                             | RFC 6238이 보안과 사용성의 균형으로 권고하는 기본값이다.                                           |
| 허용 창(window) | 앞뒤 1단계                       | RFC는 네트워크 지연으로 허용하는 것을 최대 한 단계로 권고한다. 창이 넓을수록 공격 구간도 넓어진다. |
| 자릿수          | 6                                | RFC 4226은 최소 6자리를 요구하고 7자리 이상을 보안 요구에 따라 고려하라고 한다.[^rfc4226]          |
| 비밀 키 길이    | 해시 출력 길이(SHA-1은 20바이트) | RFC 6238은 해시 출력 길이를 권고하고, RFC 4226은 최소 128비트, 권고 160비트를 요구한다.[^rfc4226]  |
| 시도 제한(T)    | 가능한 한 낮게                   | RFC 4226은 실패 횟수 상한을 두라고 권고하고, 사용성을 해치지 않는 한 낮게 두라고 한다.[^rfc4226]   |

값을 바꿀 때 측정할 것은 정상 사용자의 실패율이다.
허용 창을 줄였을 때 시계가 어긋난 기기의 로그인 실패가 늘어나는지 보고, 늘어나면
창이 아니라 기기 시계 문제로 다룬다.

## 트레이드오프

### 시간 단계의 길이

단계가 길수록 사용자가 코드를 옮겨 적을 여유가 생기지만,
코드가 노출된 뒤 쓸 수 있는 시간이 길어진다.
RFC는 코드가 제3자에게 노출되면 그 사람이 같은 구간 안에 코드를 쓸 수 있다고
명시한다.
반대쪽 비용도 있다.
한 번 성공한 뒤 다음 코드를 받으려면 다음 구간까지 기다려야 하므로,
10분 같은 너무 긴 구간은 일반적인 로그인에 맞지 않는다고 RFC는 말한다.

### 6자리의 한계

6자리는 가능한 값이 100만 개이고,
RFC 4226은 HMAC을 짧게 자르는 순간 무차별 대입이 가능해진다고
인정한다.[^rfc4226]
그래서 문서의 해법은 자릿수가 아니라 서버의 시도 제한이다.
자릿수를 늘리면 사용자가 옮겨 적기 어려워지므로, 제한이 없는 서버에서
자릿수만 늘리는 것은 순서가 거꾸로다.

### 서버가 키를 복호화할 수 있어야 한다

비밀번호와 달리 TOTP 키는 해시로 저장할 수 없다.
서버가 매번 HMAC을 계산해야 하기 때문이다.
RFC는 키를 검증 시스템에 안전하게 저장하고, 가능하면
변조 방지 하드웨어로 암호화하고, 검증할 때만 복호화해 곧바로 다시 암호화하며,
접근을 검증 프로세스로 한정하라고 권고한다.
이것이 서버 쪽에서 TOTP를 도입하는 비용이다.

## 함정

### 같은 코드를 두 번 받는 서버

한 구간 안에서는 코드가 같으므로,
한 번 성공한 코드를 다시 보내도 계산상으로는 맞다.
RFC는 이미 성공한 코드의 두 번째 시도를 검증자가 받으면 안 된다고 명시한다.
구현에서는 맞은 단계 번호를 저장하고 그 이하를 거부하는 것이 방법이며,
위 코드의 `last_used_step`이 그것이다.
저장 없이 `window`만 두면 같은 코드로 두 번 로그인된다.

### 시계가 틀린 기기

TOTP의 모든 값은 Unix 시각에서 나오므로 기기 시계가 틀리면 코드가 맞지 않는다.
RFC 6238은 6장에서 자동 재동기화가 안 되는 경우 기기와 서버의 시계 오차를
명시적으로 맞추는 방법을 따로 다룬다.
시간대는 무관하고 틀리는 것은 절대 시각이다.
HN의 Cypher는 비밀번호를 아는 사람이 시계를 조작하면
막을 수 없는지 물었다.[^cypher]
이 질문에는 스레드에 답이 없어 내 설명을 적는다.
검증은 서버의 시계로 하므로 사용자 기기의 시계를 바꾸면
그 기기가 만드는 코드가 서버가 기대하는 코드와 어긋날 뿐이고,
과거 구간의 코드는 허용 창과 재사용 거부로 막힌다.

### 2038년

알고리즘 구현은 T가 32비트 정수를 넘는 2038년 이후에도 동작해야 한다고
RFC가 명시한다.
시각을 32비트 정수로 다루는 언어와 라이브러리를 쓰면 이 조건을 어긴다.

### 시도 제한이 세션마다만 걸리는 경우

RFC 4226은 지연이나 잠금 방식이 로그인 세션을 가로질러 적용되어야 한다고 한다.
세션마다 따로 세면 여러 세션을 병렬로 열어 시도를 늘리는 공격이
가능하다.[^rfc4226]

## 확인하기

위 코드를 파일로 저장해 실행하면 RFC 부록 B의 시험 값 5개가 모두 `OK`로 나온다.
이 문서를 쓰면서 같은 구현으로 RFC의 시험 표 전체(SHA-1, SHA-256,
SHA-512 각 6개 시각, 총 18개)를 확인했고 모두 일치했다.
SHA-256과 SHA-512는 키 길이를 각각 32바이트와 64바이트로 늘린 ASCII
문자열(`1234567890`의 반복)을 쓴다.

```text
59 94287082 94287082 OK
1111111109 07081804 07081804 OK
1111111111 14050471 14050471 OK
1234567890 89005924 89005924 OK
2000000000 69279037 69279037 OK
처음 입력: 3 | 같은 코드 다시: None
시계가 30초 앞선 기기: True | 90초 앞선 기기: False
```

마지막 두 줄은 재사용 방지와 허용 창의 동작을 보여 준다.
같은 코드를 다시 넣으면 `None`이고, 시계가 한 단계 앞선 기기는 받아들여지고
세 단계 앞선 기기는 거부된다.

## 체크리스트

- 비밀 키를 암호학적 난수로 사용자마다 따로 만들었는가?
- 키 길이가 128비트 이상(권고 160비트)인가?
- 성공한 단계 번호를 저장하고 그 이하를 거부하는가?
- 허용 창이 앞뒤 한 단계를 넘지 않는가?
- 실패 횟수 제한이 로그인 세션을 가로질러 적용되는가?
- 키를 평문이 아니라 암호화해서 저장하는가?
- 시각을 32비트 정수에 담지 않는가?
- 코드 비교에 상수 시간 비교(`hmac.compare_digest` 등)를 쓰는가?

## 기억할 원칙

### 코드는 시간이 만든 암호화 해시의 일부다

TOTP의 보안은 알고리즘이 아니라 비밀 키가 새지 않는 데서 나온다.
코드 6자리는 HMAC 출력의 일부를 잘라 낸 것이어서
그것만으로 키를 되짚을 수 없지만, 키가 새면 모든 코드를 미리 계산할 수 있다.
그래서 키를 어디에 두고 누가 읽을 수 있는지가 설계의 중심이다.

### 서버가 지켜야 하는 것은 계산이 아니라 횟수와 재사용이다

알고리즘은 라이브러리 한 줄이면 되지만,
틀린 코드를 몇 번 받을지와 맞은 코드를 다시 받지 않는 일은 서버가 직접 구현해야
한다.
RFC의 두 MUST(재사용 거부, 세션을 가로지르는 제한)가 모두 이 부분에 있다.
