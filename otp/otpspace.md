# OTP Space: WABA 없이 보내는 인도네시아용 WhatsApp OTP API

<https://www.otpspace.com/>

## 소개

OTP Space는 인도네시아 앱을 위한 WhatsApp OTP 발송·검증 API다.
홈페이지 문구는 WhatsApp OTP, 인도네시아를 위해 만들었다는 한 줄로 시작하고,
REST API 하나로 인도네시아의 모든 번호에 코드를 보내고 검증하며
API 호출 두 번이면 오늘 바로 서비스에 붙일 수 있다고 내세운다.
`/api` 페이지 제목은 WABA 설정도 Meta 승인도 필요 없다는 문장이다.
사이트는 인도네시아어가 기본이고 `/en/` 아래에 영어판이 있다.

운영 주체에 대해 사이트가 밝히는 정보는 적다.
블로그 글 네 편은 모두 Rahmad Nurhuda가 썼고,
저자 소개에 OTP Space 창업자라고 적혀 있다.
홈페이지가 연결하는 GitHub 계정 `rhmdnrhuda`의 프로필은 이름이 같고,
소속을 Astro의 시니어 백엔드 엔지니어, 위치를 인도네시아로 적었다.
이용약관, 개인정보 처리방침, SLA, DPA는 모두 2026년 7월 3일부터 시행이지만
어느 문서에도 법인명이나 주소가 없고, 바닥글은 © 2026 OTP Space뿐이다.
`llms.txt`는 2026년 인도네시아에서 세웠다고만 적는다.

바닥글의 Tentang(회사 소개) 링크와 `llms.txt`는 GitHub 저장소
`rhmdnrhuda/otp-space`를, Changelog 링크는 그 릴리스 페이지를 가리킨다.
2026년 10월 10일 확인 당시 둘 다 404였다.
비공개 저장소이거나 지워진 것으로 보이며, 어느 쪽인지는 확인하지 못했다.
바닥글의 Webhook과 Template 링크는 둘 다 `/docs`로 간다.
Status 링크는 상태 페이지가 아니라 `/health`로 가는데,
이 경로는 PostgreSQL과 Redis 상태, 배포 커밋 해시를 담은 JSON 한 줄을 돌려준다.

### 채널과 쓰임새

채널은 WhatsApp과 이메일 둘이다.
같은 API에 `channel` 값만 바꿔 쓰며, SMS는 `llms.txt`가 로드맵에 있다고 적는다.
홈페이지가 드는 쓰임새는 전자상거래 결제·로그인, 핀테크 KYC와 2단계 인증,
SaaS 가입·비밀번호 없는 로그인·계정 복구다.
지원 통신사로는 Telkomsel, Indosat, XL, Tri, Smartfren을 나열하는데,
WhatsApp으로 보내는 이상 통신사는 전달 경로와 무관하므로
이 목록은 SMS 사업자와 비교하는 문구에 가깝다.

OpenAPI 명세에는 OTP와 별개로 주문 알림, 공지 같은 비 OTP 메시지를 보내는
`/messages/send`도 있다.
화이트리스트에 든 계정만 쓸 수 있고, 다른 계정은 `403`을 받는다.

## 가격

### 표시 가격

WhatsApp OTP는 건당 Rp 100이고, `llms.txt`는 약 0.006달러로 환산한다.
홈페이지와 가격 페이지는 물량과 상관없는 단일 요율이며 등급도, 월 기본료도,
최소 약정도 없다고 강조한다.
이메일 OTP는 0.2크레딧, 즉 WhatsApp 요율의 5분의 1이며
영어 FAQ는 Rp 20부터라고 적는다.
가입하면 신용카드 없이 10건을 무료로 주고, 충전은 QRIS, 계좌이체, 카드로 한다.

과금 규칙은 문서마다 조금씩 다른 말로 같은 내용을 반복한다.
발송 요청이 접수될 때 크레딧을 차감하고, 전달에 실패하면 자동으로 돌려준다.
약관과 SLA는 제한 시간 안에 전달되지 않은 인증은 청구하지 않는다고 적는다.
`llms.txt`는 크레딧이 만료되지 않는다고 하지만,
약관은 산 크레딧은 법이 요구하는 경우를 빼고 환불하지 않는다고 정한다.
책임 한도는 사고 직전 3개월 동안 낸 금액이다.

### 단일 요율과 어긋나는 흔적

단일 요율이라는 주장과 맞지 않는 내용이 사이트 안에 남아 있다.
2026년 7월 2일 블로그 글 Berapa Biaya OTP di Indonesia?는
OTP Space 가격이 Rp 100에서 시작해 대량이면 Rp 70까지 내려간다고 쓰고,
월 1만 건이면 Scale 등급 요율 Rp 80이 적용된다고 계산한다.
같은 저자의 WABA 우회 글도 등급별 가격표를 보라며 가격 페이지로 연결한다.
API의 잔액 조회 응답에는 `tier` 필드가 있고, 값은 `starter`, `growth`,
`scale`, `business`, `enterprise` 중 하나다.
지금 가격 페이지에는 등급이 없으므로, 등급제에서 단일 요율로 바꾸면서
블로그와 API 응답을 정리하지 않은 것으로 읽힌다(해석).

### 경쟁사 비교

`/compare` 페이지는 인도네시아 번호로 WhatsApp 인증 한 건을 보내는 비용을
다음과 같이 비교한다.

| 사업자        | 건당 가격 | 청구 통화 | 페이지 설명                               |
| ------------- | --------- | --------- | ----------------------------------------- |
| OTP Space     | Rp 100    | IDR       | 단일 요율, 셀프서비스 키                  |
| Twilio Verify | ≈ Rp 800+ | USD       | 인증 수수료에 WhatsApp 메시지 요금이 붙음 |
| Vonage Verify | ≈ Rp 900+ | USD       | 실패한 시도에도 요금을 냄                 |
| Verihubs      | ≈ Rp 300+ | IDR       | 영업 주도 온보딩과 물량 약정              |
| Fazpass       | ≈ Rp 300+ | IDR       | 채널과 협상 물량에 따라 다름              |

각주는 2026년 7월 공개 가격표에서 가져온 참고치이며
달러는 약 Rp 16,000으로 환산했다고 밝힌다.
그런데 같은 각주에 운영자가 이 페이지를 완전히 공개하기 전에
숫자를 검증하는 중이라는 문장이 그대로 남아 있다.
FAQ는 Twilio, Vonage보다 약 8배 싸다고 하는데,
표의 Rp 800과 Rp 100을 나눈 값이다.

WABA 비교 글은 Meta가 2024년 11월 1일 월 1,000건 무료 대화를 없앴고,
2025년 7월 1일부터 대화 단위가 아닌 메시지 단위로 과금한다고 설명한다.
인도네시아 번호로 보내는 인증 메시지 요율을 국내 기업은 약 IDR 367,
해외 기업은 약 IDR 1,951로 제시하고,
OTP Space가 메시지당 약 3.7배 싸다고 계산한다.
이 숫자들은 블로그의 주장이며 Meta 요율표와 대조하지는 않았다.

## 동작 방식

### 인증과 기본 규칙

기본 URL은 `https://api.otpspace.com/v1`이다.
대시보드의 API Keys 화면에서 `CLIENT_ID`와 `CLIENT_SECRET`을 받고,
모든 요청에 `Authorization: Bearer sk_live_xxx` 형태로 client secret을 넣는다.
별도의 샌드박스 키는 없고, 무료 10건도 운영 키 `sk_live_*`로 쓴다.
번호는 `+6281234567890`, `6281234567890`, `081234567890`을 모두 받아
`6281234567890`으로 정규화한다.
요청 한도는 무료 체험 계정이 분당 10회, 유료 계정이 분당 60회이며
둘 다 계정 단위다.

OpenAPI 명세 기준 엔드포인트는 다음과 같다.

| 메서드 | 경로                  | 하는 일                               |
| ------ | --------------------- | ------------------------------------- |
| POST   | `/v1/otp/send`        | OTP 생성과 발송, `202`로 즉시 응답    |
| POST   | `/v1/otp/verify`      | 사용자가 입력한 코드 검증             |
| GET    | `/v1/otp/{otp_id}`    | OTP 한 건의 현재 상태                 |
| GET    | `/v1/otp/logs`        | 발송 이력, 필터와 페이지네이션        |
| GET    | `/v1/account/balance` | 남은 크레딧, 쓴 크레딧, 등급          |
| POST   | `/v1/messages/send`   | 비 OTP 메시지, 화이트리스트 계정 전용 |

### 발송

`/v1/otp/send`에는 목적지를 정확히 하나 준다.
WhatsApp이면 `phone`, 이메일이면 `email`이며,
`channel`을 비우면 값에 `@`가 있는지로 채널을 추정한다.
선택 필드는 다음과 같다.

| 필드             | 범위와 기본값           | 비고                                           |
| ---------------- | ----------------------- | ---------------------------------------------- |
| `template_id`    | 대시보드에서 만든 slug  | 없는 이름은 계정 기본 템플릿으로 조용히 대체됨 |
| `template`       | `template_id`의 옛 별칭 | `template_id`가 비었을 때만 씀                 |
| `app_name`       | 최대 50자, URL 금지     | 메시지의 `{app_name}`을 이번 발송만 바꿈       |
| `sender_name`    | `app_name`의 별칭       | `app_name`이 비었을 때만 씀                    |
| `otp_length`     | 4~8, 기본 6             |                                                |
| `expiry_seconds` | 60~900, 기본 300        | 기본 5분                                       |
| `metadata`       | 자유 키-값              | 2단계 웹훅에서 그대로 돌려준다고 함            |

응답은 `202`이고 `otp_id`, 가린 번호(`6281234***90`), 채널,
상태 `queued`, `expires_at`, `credits_remaining`을 담는다.
상태는 `queued`, `sending`, `delivered`, `verified`, `failed`, `expired` 중
하나이며, 홈페이지는 `queued`에서 `delivered`까지 약 6초가 걸린다고 표시한다.
크레딧이 모자라면 `402`(`insufficient credits`)를 받는다.

### 검증

검증 요청은 `otp_id`가 아니라 발송 때와 같은 `phone` 또는 `email`과
`code`를 보낸다.
번호마다 틀린 시도는 최대 5번이고, 넘으면 OTP가 잠긴다.
한 번 검증에 성공한 코드는 다시 쓸 수 없다.

| 상태  | 명세의 의미                             |
| ----- | --------------------------------------- |
| `200` | 코드가 맞음, `status: verified`         |
| `404` | 이 번호의 OTP가 없거나 다른 계정의 것   |
| `410` | 만료됨(`otp expired`)                   |
| `422` | 코드가 틀림(`invalid code`)             |
| `429` | 5번 넘게 틀려 잠김(`too many attempts`) |

### 만료와 재시도

만료는 `expiry_seconds`로 정하고 범위는 60~900초, 기본은 300초다.
같은 번호로 새 OTP를 보냈을 때 이전 OTP가 무효가 되는지,
검증이 가장 최근 OTP만 보는지는 어느 문서에도 적혀 있지 않다.
재발송 전용 엔드포인트도 없어서, 다시 보내기는 새 발송 요청이고
매번 1크레딧이 든다.
Flutter 연동 글은 재발송에 60초 대기 시간을 두라고 권한다.

서버 쪽 재시도 지침은 짧다.
문서의 오류 표는 `429`에 몇 초 뒤 다시 시도하라고, `500`에는
백오프로 다시 시도하고 계속되면 지원팀에 연락하라고만 적는다.
전달 쪽 재시도는 서비스가 맡는데, SLA는 전달 노드를 쓸 수 없으면
대체 경로로 보낸다고 하고, 홈페이지는 이를
자동 장애 조치(auto-failover)라 부른다.
전달 결과를 알려 주는 웹훅은 아직 없다.
문서는 웹훅을 2단계(Phase 2)에 나올 기능으로 적고,
그때 `delivered`, `verified`, `expired`, `failed` 이벤트를 보낸다고 한다.
그전까지 전달 여부는 `GET /v1/otp/{otp_id}`를 폴링하거나 대시보드에서 본다.

## 전달 경로

OTP Space가 WhatsApp 메시지를 어떤 계정으로 보내는지는 어디에도
직접 적혀 있지 않다.
OpenAPI 설명은 자체(proprietary) 인프라로 보낸다고만 하고,
`/api` 페이지는 우리가 WhatsApp 전달을 맡으니 고객은 Meta 비즈니스 인증,
WABA 번호, 템플릿 승인을 건드리지 않는다고 말한다.

창업자의 블로그 글 Cara Kirim OTP via WhatsApp tanpa WABA Business
Verification이 단서를 준다.
글은 세 가지 방법을 비교한다.
첫째는 whatsmeow나 Baileys 같은 오픈소스 라이브러리로 WhatsApp Web 프로토콜에
붙어 개인 번호로 보내는 방식으로, Fontte, Kirimin, Wablas 같은 인도네시아
게이트웨이가 쓰며 번호가 차단되기 쉽다고 적는다.
둘째가 OTP Space 같은 관리형 서비스인데,
직접 WhatsApp Web 자동화를 돌리는 것과 달리 발신 번호의 상태 관리와 교체가
제공자 몫이 되고, 모니터링과 번호·노드 사이의 장애 조치가 있어
번호 하나에 문제가 생겨도 발송이 멈추지 않는다고 설명한다.
셋째는 SMS다.
글의 비교표는 관리형 WhatsApp OTP의 차단 위험을 낮음으로 적는다.

비 OTP 메시지 API의 명세는 더 직접적이다.
`template_id`가 `order`이면 서버가 1~5 중 하나를 골라 `order_3` 같은 변형을
먼저 쓰는데, 명세는 이 규칙에 차단 방지(anti-ban)라는 이름을 붙이고
WhatsApp의 패턴 필터에 걸리지 않게 매번 다른 문구를 쓰기 위한 것이라고 설명한다.
같은 설명에는 템플릿을 OTP Space 팀이 SQL로 `message_templates` 테이블에 직접
넣는다는 내부 사정과 `MESSAGE_API_WHITELIST` 환경 변수 이름까지 나온다.

이 단서들을 합치면 OTP Space는 WABA 공식 템플릿이 아니라 여러 일반 WhatsApp
번호를 돌려 가며 보내는 구조로 보인다(해석).
공식 WABA로 보낸다면 번호 차단 위험이나 문구를 바꿔 패턴 필터를 피할 이유가
작고, Meta의 인증 템플릿 요율이 IDR 367이라고 스스로 쓴 회사가
건당 Rp 100에 팔기도 어렵다.
반면 약관은 고객에게 WhatsApp/Meta 서비스 약관을 어기는 용도를 금지한다.

## 함정

### 문서마다 다른 엔드포인트와 요청 형식

같은 사이트 안에서 API 형식이 세 가지로 나온다.

| 출처                         | 경로                             | 발송 본문                      | 검증 키         |
| ---------------------------- | -------------------------------- | ------------------------------ | --------------- |
| 홈페이지                     | `/v1/send`, `/v1/verify`         | `to`, `template`               | `id`, `code`    |
| `/api`, Go 연동, Flutter 글  | `/v1/send`, `/v1/verify`         | `phone`(`channel`, `template`) | `phone`, `code` |
| `/docs`, OpenAPI, `llms.txt` | `/v1/otp/send`, `/v1/otp/verify` | `phone`, `template_id` 등      | `phone`, `code` |

홈페이지 예시처럼 `otp_id`로 검증하는 방식은 명세에 없다.
명세의 발송 요청에는 `to` 필드도 없다.
인증 없이 `/v1/send`, `/v1/otp/send`, 존재하지 않는 `/v1/zzz-nonexistent`에
POST를 보내 보면 셋 다 `401 missing api key`를 돌려준다.
인증 검사가 라우팅보다 먼저 일어나므로, 어떤 경로가 실제로 살아 있는지는
키 없이 알 수 없다.
키를 받아 직접 호출해 보지 않았으므로 어느 형식이 동작하는지 확인하지 못했다.
연동은 OpenAPI 명세를 기준으로 하고, 첫 호출에서
경로와 필드를 확인하는 편이 안전하다.

### 같은 상태 코드, 다른 의미

`/docs`의 오류 표는 `422`를 WhatsApp 번호가 유효하지 않거나 활성 상태가 아님,
`429`를 요청 한도 초과로 설명한다.
OpenAPI의 검증 엔드포인트에서는 `422`가 틀린 코드, `429`가 5회 초과 잠금이다.
그래서 검증 응답의 `429`만 보고는 잠시 기다리면 되는지,
새 OTP를 보내야 하는지 구분할 수 없다.
분기는 상태 코드가 아니라 `error` 문자열(`too many attempts`,
`rate limit exceeded`)로 해야 한다.

만료 기본값도 엇갈린다.
명세는 300초인데 Flutter 글은 `410`을 설명하며 기본 10분이라고 적는다.
화면에 남은 시간을 표시한다면 `expires_at`을 읽어야 하고,
기본값을 가정하면 안 된다.

### 템플릿 이름 오타가 조용히 지나간다

`template_id`에 없는 이름을 주면 오류 없이 계정 기본 템플릿으로 바뀐다.
로그인용, 비밀번호 재설정용 문구를 따로 만들었다면 오타 하나로 사용자가
엉뚱한 문구를 받아도 API는 `202`를 돌려준다.
`/messages/send`는 모르는 `template_id`에 `400`을 주므로 두 엔드포인트의
동작도 다르다.

### 서버 위치와 보안 문구

홈페이지는 인도네시아 서버, 낮은 지연과 데이터 규제 준수를 위한 현지 인프라를
내세운다.
`llms.txt`는 인도네시아 사용자에게 지연이 낮도록 싱가포르(Oracle Cloud)에
호스팅한다고 적는다.
둘 중 하나는 틀렸고, 개인정보보호법 대응을 따지는 고객이라면 직접 물어야 한다.

홈페이지는 종단간 암호화(Enkripsi end-to-end)를 내세우지만 설명은 전송 중과
저장 시 암호화다.
개인정보 처리방침이 밝히는 실제 조치는 전화번호 저장 시 암호화,
OTP 코드 해시 저장, 서명된 세션, 관리자 접근 허용 목록,
운영 로그에 비밀값과 전체 번호를 남기지 않는 것이다.
OTP Space가 코드를 만들고 WhatsApp으로 보내므로 평문 코드는 서비스를 거친다.
종단간이라는 말은 이 구조에 맞지 않는다.

### 키를 앱에 넣으면 안 된다

샌드박스 키가 없으므로 테스트 키와 운영 키가 같다.
Flutter 연동 글은 `sk_live_*`를 앱에 넣지 말고 자체 백엔드를 거치라고
경고하면서도, 예제 코드는 앱에서 API를 직접 호출한다.
그대로 출시하면 APK에서 키를 꺼낸 누구나 고객 계정의 크레딧으로 임의 번호에
메시지를 보낼 수 있다.

## 트레이드오프

### 값싼 전달과 차단 위험

건당 Rp 100이라는 가격은 WABA 인증 템플릿 요율보다 낮다.
블로그의 설명대로라면 그 차이는 발신 번호 교체와 장애 조치로 메운다.
창업자 스스로 WhatsApp Web 자동화의 약점으로 번호 차단, 대량 발송 시 불안정한
전달률, 발신 번호가 막히면 모든 OTP가 실패하는 점을 꼽았다.
관리형 서비스는 이 위험을 고객에게서 제공자에게 옮길 뿐 없애지 못한다.
Meta가 이런 발송을 대규모로 막는 날에는 장애 조치할 번호 묶음 전체가 같은 이유로
막힐 수 있다(해석).

그래서 OTP Space를 쓰더라도 인증 흐름을 이 한 경로에만 걸어 두기는 어렵다.
전달 실패 시 이메일 OTP나 SMS로 넘어가는 대체 경로를 앱 쪽에 두어야 하고,
그 판단에는 웹훅이 아직 없으므로 상태 폴링이 필요하다.
실패 건은 환불되지만, 그동안 로그인하지 못한 사용자는 돌아오지 않는다.

### 셀프서비스의 낮은 진입 장벽

가입만 하면 키가 나오고, 신용카드도 사업자 등록번호도 필요 없다.
인도네시아 개인 개발자에게는 PT나 CV 법인과 NPWP, 몇 주의 Meta 심사를 건너뛸
수 있다는 점이 핵심 가치다.
같은 성질이 반대편에서는 약점이다.
누구든 무료 10건과 운영 키를 바로 받으므로 공급자 쪽 신원 확인이 약하고,
사기 업자도 같은 문턱으로 들어온다.

### 계정 단위 한도와 트래픽 부풀리기

요청 한도는 계정당 분당 60회이고, 번호별 발송 한도는 문서에 없다.
검증 시도는 번호당 5회로 막지만, 발송 쪽에서 같은 번호나 비슷한 번호대로
쏟아지는 요청을 막는 장치는 고객이 만들어야 한다.
SMS OTP에서 이 빈틈을 노리는 공격이
[AIT 사기](ait-fraud.md)에서 다룬 트래픽 부풀리기다.
SMS 펌핑은 통신사 착신 수익을 나누는 구조라 WhatsApp에는 그대로 옮겨지지
않지만, 가입 양식을 봇이 두드려 고객의 크레딧과 발신 번호의 평판을 태우는
피해는 똑같이 생긴다(해석).

비용을 아예 서비스 밖으로 빼는 방향도 있다.
[OCTOMO](octomo-mo-sms-auth.md)는 사용자가 직접 문자를 보내는 MO 방식으로
발송 비용과 펌핑 위험을 함께 없앤다.
OTP Space는 발송 방향은 그대로 두고 채널 단가만 낮춘 쪽이다.

## 비평

### 단일 요율과 투명성을 말하는 사이트가 스스로 어긋난다

OTP Space의 판매 문구는 간단함과 예측 가능성이다.
등급이 없고, 놀랄 일이 없고, 문서는 추측하지 않고 이해하도록 썼다고 한다.
그런데 사이트를 끝까지 읽으면 등급표가 있는 블로그, `tier`를 돌려주는 API,
세 가지 엔드포인트 형식, 의미가 다른 `422`와 `429`,
5분과 10분 두 개의 만료 기본값,
인도네시아와 싱가포르 두 개의 서버 위치가 나온다.
비교표 각주에는 운영자가 아직 숫자를 검증하는 중이라는 내부 메모가 남아 있다.

하나하나는 출시 초기 서비스에서 흔한 정리 누락이다.
문제는 이 서비스가 파는 것이 인증이라는 점이다.
인증 API의 고객은 오류 코드에 따라 사용자를 잠그거나 다시 보내는 분기를 짜는데,
그 분기의 기준이 문서마다 다르면 고객의 로그인 흐름이 틀린 가정 위에 선다.

### 핵심 질문에 답하지 않는 문서

고객이 가장 먼저 알아야 할 사실은 메시지가 어떤 WhatsApp 계정에서 나가는가다.
공식 WABA 발신이면 Meta 정책 안에 있고, 일반 번호 여러 개를 돌리는 방식이면
고객의 인증 흐름이 Meta의 차단 정책에 그대로 노출된다.
사이트는 이 질문을 proprietary 인프라, 전달 노드, 대체 경로 같은 말로 피해 가고,
답에 가장 가까운 내용은 비 OTP 메시지 API 명세의 anti-ban 설명에 묻혀 있다.

이 서비스와 비교할 대상은 사이트가 고른 Twilio나 Vonage가 아니다.
창업자가 블로그에서 직접 이름을 든 Fontte, Wablas 같은 WhatsApp Web 게이트웨이,
그리고 Verihubs, Fazpass 같은 현지 인증 사업자다.
그 비교를 하려면 발신 방식이 공개되어야 하는데,
비교 페이지는 그 축을 다루지 않는다.

### 운영 주체가 보이지 않는다

약관, 개인정보 처리방침, DPA는 OTP Space를 데이터 처리자로 정하지만
그 처리자가 어느 법인인지는 적지 않는다.
회사 소개 링크가 가리키는 GitHub 저장소는 404다.
고객 사용자의 전화번호를 맡기는 처리자 계약에서 상대방이 누구인지 알 수 없다면,
인도네시아 개인정보보호법상 책임을 물을 곳도 분명하지 않다.
블로그의 저자 소개와 GitHub 프로필이 개인 창업자를 가리키는 것이
지금 확인할 수 있는 전부다.

## 체크리스트

- 연동 코드가 OpenAPI 명세의 `/v1/otp/send`, `/v1/otp/verify` 형식을 따르고,
  첫 호출로 경로와 필드를 확인했는가?
- `sk_live_*` 키를 앱 번들이 아니라 서버에만 두었는가?
- 검증 응답의 `429`를 상태 코드가 아니라 `error` 문자열로 잠금과 한도 초과로
  나누어 처리하는가?
- 만료 시간을 기본값으로 가정하지 않고 `expires_at`이나 명시한
  `expiry_seconds`로 다루는가?
- `template_id`가 대시보드 slug와 맞는지 실제 수신 문구로 확인했는가?
- 같은 번호로 다시 보냈을 때 이전 코드가 통하는지 직접 시험해 보았는가?
- 번호별, IP별 발송 한도와 재발송 대기 시간을 자체 서버에 두었는가?
- WhatsApp 전달이 실패하거나 지연될 때 넘어갈 이메일이나 SMS 경로가 있는가?
- 웹훅 없이 전달 상태를 `GET /v1/otp/{otp_id}` 폴링으로 확인하는 흐름이 있는가?
- 운영 법인, 서버 위치, WhatsApp 발신 방식을 서면으로 확인했는가?

## 기억할 원칙

### 싼 OTP 채널은 전달 경로부터 묻는다

OTP 단가가 공식 채널 요율보다 낮다면 그 차이가 어디서 나오는지 먼저 물어야 한다.
OTP Space의 경우 답은 사이트에 직접 쓰여 있지 않고,
창업자의 블로그와 부수 API의 명세를 맞춰 보아야 겨우 드러난다.
인증은 실패하면 사용자가 서비스에 들어오지 못하는 경로이므로,
단가보다 전달 경로가 언제 어떤 이유로 끊길 수 있는지가 더 중요한 정보다.
