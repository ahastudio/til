# OTP.ID: 인도네시아 상점을 위한 다섯 채널 OTP 발송·검증 API

<https://otp.id/>

## 소개

OTP.ID는 인도네시아 상점(merchant)을 대상으로 한 OTP 발송·검증 API다.
홈페이지는 스스로를 “layanan API OTP Indonesia untuk login, registrasi,
dan verifikasi nomor pengguna”라고 소개한다.
로그인, 가입, 사용자 번호 확인에 쓰는 인도네시아 OTP API 서비스라는 뜻이다.
WhatsApp, SMS, 음성 통화(Voice), 이메일, 부재중 전화(Missed Call) 다섯 채널을
하나의 연동으로 묶었고,
월 이용료 없이 OTP 한 건마다 돈을 낸다는 점을
“tanpa biaya bulanan, bayar hanya per OTP”라는 문구로 앞세운다.
사이트와 문서는 인도네시아어가 기본이고, 개발자 문서(`docs.otp.id`)는 영어다.

운영 주체는 PT Aplikasi Kreasi Indonesia다.
소개 페이지(`/tentang`)는 OTP.ID를
이 회사가 소유하고 운영하는 서비스라고 밝힌다.
모회사 사이트에 따르면 이 회사는 2019년 리아우주 프칸바루(Pekanbaru)에서 세운
핀테크 회사로, 처음에는 휴대폰 충전(pulsa)과 PPOB(공과금 등 온라인 결제 대행)
사업자에게 디지털 상품을 공급하는 Bukakios 브랜드로 시작했다.
지금은 결제 플랫폼 Tokopay, 게임 충전 API Apigames,
고객 응대 AI CSKU.ai 등과 함께
OTP.ID를 사업부 목록에 올려 두고 있다.
API 문서의 Voice 예제에 `"brand": "Bukakios"`가 그대로 쓰인 것도
이 관계를 보여 준다.
문의 창구는 지원 이메일 하나와 상점 대시보드(`app.otp.id`)이고,
약관과 개인정보 처리방침은 모두 인도네시아 공화국 법을 준거법으로 둔다.

규모 수치는 페이지마다 다르다.
홈페이지는 발송 OTP 1.412.842건, 등록 상점 4.691곳을 표시하고,
소개 페이지는 활성 상점 2.000곳 이상, 발송 OTP 130만 건 이상이라고 적는다.
하나는 등록 상점, 다른 하나는 활성 상점이라 직접 모순은 아니지만,
둘 다 갱신 시점이 적혀 있지 않다.
블로그 글은 2026년 8월부터 올라오기 시작했고,
npm 레지스트리의 공식 Node SDK `@otp-id/sdk`는 2026년 8월 14일에 처음 등록되어
지금 최신 버전이 0.1.0이다.
개인정보 처리방침의 최종 갱신일은 2026년 8월 17일이다.
날짜로 보면 2026년 여름에 공개 API(V3)와 문서를 정비한 비교적 새 서비스다.

## 채널과 가격

가격 페이지(`/harga`)는 채널 계열을 다섯 개로 나누지만,
API에서는 WhatsApp이 발신(outbound)과 수신(inbound) 흐름으로 갈라지기 때문에
채널 모드가 여섯 개라고 설명한다.
발신 WhatsApp은 다시 Random Number와 Official OTP.ID 두 가지로 나뉜다.
공개 가격은 다음과 같다.

| 채널                     | API `channel` 값   | 공개 가격(OTP당) | 쓸 수 있는 엔드포인트     |
| ------------------------ | ------------------ | ---------------- | ------------------------- |
| WhatsApp Tap-to-Verify   | `whatsapp_inbound` | Rp120            | `/v3/request`만           |
| WhatsApp Random Number   | `whatsapp`         | Rp370            | `/v3/request`, `/v3/send` |
| WhatsApp Official OTP.ID | `whatsapp`         | Rp495            | `/v3/request`, `/v3/send` |
| SMS                      | `sms`              | Rp670            | `/v3/request`, `/v3/send` |
| Voice                    | `voice`            | Rp595            | `/v3/request`만           |
| Email                    | `email`            | Rp20             | `/v3/request`, `/v3/send` |
| Missed Call              | `misscall`         | Rp250            | `/v3/request`만           |

선불제다.
보증금(deposit)은 최소 Rp10.000부터 넣을 수 있고,
새 상점은 이메일 인증을 마치면 시험용 크레딧 Rp2.000을 받는다.
대량 발송은 가격을 협상할 수 있다고 적혀 있다.
크레딧 충전은 대시보드에서 하거나 `POST /v3/topups`로 결제 링크를 만들어서 한다.
충전 금액은 10000, 100000, 500000, 1000000,
2000000루피아 다섯 가지 패키지로 정해져 있고,
결제 링크는 3시간 뒤 만료되며,
QRIS와 가상계좌(Virtual Account) 안내가 OTP.ID 페이지 안에 표시된다.

Random Number와 Official OTP.ID가 각각 어떤 발신 번호를 뜻하는지는
공개 페이지에 설명이 없다.
이름으로 보면 전자는 무작위 일반 번호,
후자는 OTP.ID 공식 계정에서 보내는 방식으로 읽히지만,
이것은 이름에서 미루어 본 해석이다.

홈페이지의 Smart Channel은 WhatsApp 경로 사이에서만 자동으로 바꿔 주는 기능이다.
같은 번호로 짧은 시간 안에 다시 요청이 오면 다른 WhatsApp 경로로 돌린다.
홈페이지와 FAQ는 SMS, Voice, Email, Missed Call로 넘어가는 대체 발송은
없다고 여러 번 강조한다.
SMS 페이지 FAQ도 WhatsApp이 실패했을 때 SMS가 자동으로 쓰이지 않는다고 답한다.
Smart Channel 그림에는
“Diagram ini ilustrasi, bukan status produksi”라는 단서가 붙어 있다.
그림은 설명용이지 실제 운영 상태가 아니라는 뜻이다.

## 동작 방식

### 요청, 발송, 검증

기본 흐름은 요청 → 검증 두 단계다.
인증은 `Authorization: Bearer <api_key>` 헤더 하나로 하고,
기본 주소는 `https://api.otp.id`다.

```bash
curl -X POST https://api.otp.id/v3/request \
  -H "Authorization: Bearer <api_key>" \
  -H "Content-Type: application/json" \
  -d '{
    "channel": "whatsapp",
    "destination": "6281234567890",
    "brand": "TokoKita",
    "external_id": "login-7f3a"
  }'
```

`POST /v3/request`는 OTP.ID가 코드를 만들어 보내며, 코드는 응답에 담기지 않는다.
`POST /v3/send`는 상점이 만든 코드(`otp` 필드, 숫자 4~8자리)를 대신 보내 주며,
`whatsapp`, `sms`, `email`에서만 쓸 수 있다.
문서는 상점 서버가 코드를 볼 일이 없는 `/v3/request`를 권장한다.
전화번호는 `+` 없이 국가 번호부터 시작하는 숫자로, 10자리 이상이어야 한다.

발송은 동기식이다.
응답이 돌아올 때 이미 채널 공급자(vendor)를 호출한 결과가 `status`에 담겨 있다.
응답에는 거래 ID `otp_id`가 들어 있고,
형식은 `OTP` + 날짜(서인도네시아 시간, UTC+7) + 대문자 4자
+ 하루 단위 일련번호 6자리다.
사용자가 코드를 입력하면 `POST /v3/verify`에 `otp_id`와 코드를 보낸다.

```bash
curl -X POST https://api.otp.id/v3/verify \
  -H "Authorization: Bearer <api_key>" \
  -H "Content-Type: application/json" \
  -d '{"otp_id": "OTP20260811ABCD000001", "otp": "482913"}'
```

검증 결과는 HTTP 상태 코드만으로는 판단할 수 없다.
틀린 코드는 오류가 아니라 HTTP 200에 `verified: false`,
`reason: "mismatch"`로 돌아온다.
만료, 시도 횟수 초과, 이미 사용됨은 HTTP 422에 각각 `OTP_EXPIRED`,
`TOO_MANY_ATTEMPTS`, `ALREADY_USED` 오류 코드로 온다.
발송 실패도 HTTP 200에 `status: "failed"`로 오며,
`data.failure.code`가 이유를 알려 준다.
실패 사유는 `NUMBER_NOT_ON_WHATSAPP`, `TOO_FREQUENT`, `CHANNEL_UNAVAILABLE`,
`PROVIDER_UNAVAILABLE`, `DELIVERY_FAILED` 다섯 가지이고,
공급자의 원래 오류 메시지는 노출하지 않는다.

### 만료와 시도 횟수

| 값             | 범위                 | 기본값 | 범위를 벗어나면                  |
| -------------- | -------------------- | ------ | -------------------------------- |
| `ttl`          | 60~900초             | 300초  | 오류 없이 가까운 경계로 조정     |
| `otp_length`   | 4~8자리              | 6자리  | 오류 없이 가까운 경계로 조정     |
| 검증 실패 허용 | 일반 5회, 부재중 2회 | —      | 그 뒤 호출은 `TOO_MANY_ATTEMPTS` |

만료와 시도 초과는 상태 값이 아니다.
TTL이 지나거나 시도 횟수를 다 써도 저장된 `status`는 `sent`/`success`로 남고,
검증 호출이 422를 돌려줄 뿐이다.
상태를 조회(`GET /v3/otp/{otp_id}`)해서 이 상황을 알아내려면
`expires_at`과 `attempts`를 직접 비교해야 한다.
제한에 걸리게 되는 마지막 오답은 여전히 200 `mismatch`로 오고,
그다음 호출부터 422가 온다.
시각 필드는 모두 `YYYY-MM-DD HH:MM:SS` 형식의 서인도네시아 시간(WIB)이다.

### 채널별로 다른 점

Missed Call은 메시지 본문이 없다.
OTP.ID가 전화를 걸었다가 끊고,
사용자의 통화 기록에 남은 발신 번호의 끝자리가 코드가 된다.
응답의 `verification.prefix`(예: `628559263`)는 끝자리를 뺀 발신 번호이고,
`verification.otp_length`(현재 4)는 사용자가 채워야 할 자릿수다.
코드는 통신 공급자가 정하므로 `otp_length` 요청 값은 무시되고,
`brand`도 필요 없다.
문서는 일반 6자리 입력 화면을 쓰지 말고,
접두부를 보여 주고 끝자리 칸만 두는 전용 화면을 만들라고 권한다.

Voice는 브랜드 이름을 말한 다음 네 자리 숫자를 한 자리씩 읽어 준다.
문서의 예시 발화는 `Kode TokoKita 1 6 7 8`이다.
`brand`는 필수이고, `otp_length`를 보내도 항상 네 자리다.
상점 계정에서 Voice 채널을 따로 활성화해야 하며,
그렇지 않으면 `CHANNEL_UNAVAILABLE`이 돌아온다.
요청 응답은 사용자가 전화를 받았는지 확인해 주지 않는다.

Email은 제목이 `Kode verifikasi <brand>` 형식이고,
상점이 유효한 HTTPS 주소를 주면 로고도 넣을 수 있다.
Email 페이지 FAQ는 이메일이 프로모션함이나 스팸함으로 갈 수 있어
전화번호 채널보다 늦을 수 있다고 스스로 적는다.

### WhatsApp Tap-to-Verify

Tap-to-Verify(`whatsapp_inbound`)는 방향이 거꾸로다.
OTP.ID가 코드를 보내는 대신, `/v3/request`가 OTP.ID의 WhatsApp 번호, 보낼 문장,
`wa.me` 딥링크를 돌려준다.
문장은 다음과 같은 형태다.

```text
OTPID V-8FK2QN9P — verifikasi TokoKita. Kirim pesan ini tanpa mengubah isinya.
```

끝 문장은 내용을 바꾸지 말고 그대로 보내라는 안내다.
사용자가 이 문장을 보내면 OTP.ID가 토큰을 대조해 거래를 `verified`로 바꾸고,
상점은 `otp.verified` 웹훅을 받거나 상태 조회 엔드포인트를 폴링해 결과를 안다.
`/v3/verify`는 호출하지 않는다.
사용자가 WhatsApp에서 메시지를 보낸다는 점에서 사용자 발신(MO) 방식이고,
국내 SMS로 같은 일을 하는 사례는
[OCTOMO](octomo-mo-sms-auth.md) 문서에 정리되어 있다.

`destination`은 선택이다.
넣으면 그 번호에서 온 메시지만 인정하고,
빼면 일치하는 토큰을 보낸 어느 WhatsApp 번호든 인정한다.
상태 조회는 대기 중인 거래에 대해 같은 `verification` 블록을 다시 돌려주므로,
페이지를 새로 고쳐도 딥링크를 따로 저장할 필요가 없다.

## 재시도와 멱등성

`/v3/request`와 `/v3/send`는 `external_id`를 받는다.
같은 `external_id`가 24시간 안에 같은 파라미터로 다시 오면
OTP.ID는 새 거래를 만들지 않고 원래 거래를 돌려준다.
문서는 이를 재생(replay)이라 부르며,
메시지를 다시 보내지도 크레딧을 다시 빼지도 않는다.
비교하는 값은 `channel`, 정규화한 목적지, 그리고 `/v3/send`의 `otp`뿐이다.
`brand`, `ttl`, `otp_length`가 달라도 충돌로 보지 않고 무시한다.
같은 키로 비교 대상 값이 다르면 409 `DUPLICATE_EXTERNAL_ID`가 오고,
`error.details.existing_otp_id`에 원래 거래 ID가 담긴다.

재시도 정책은 오류 종류마다 다르다.

| 응답                           | 의미                       | 문서가 권하는 대응                           |
| ------------------------------ | -------------------------- | -------------------------------------------- |
| 429 `RATE_LIMITED`             | API 키당 초당 20건 초과    | 약 100ms부터 두 배씩, ±20% 지터, 최대 5회    |
| 429 `DESTINATION_RATE_LIMITED` | 같은 목적지 발송 한도 초과 | 자동 재시도 금지, 사용자에게 기다리라고 안내 |
| 402 `INSUFFICIENT_BALANCE`     | 크레딧 부족, 거래 미생성   | 반복 재시도 금지, 충전 후 다시 요청          |
| 503 `CHANNEL_UNAVAILABLE`      | 채널 또는 공급자 장애      | 지수 백오프, 길어지면 다른 채널 제안         |
| 500 `INTERNAL_ERROR`           | 서버 오류                  | 지수 백오프, 지속되면 ID와 시각으로 문의     |
| 200 `status: "failed"`         | 발송 실패, 과금 없음       | 사유를 보여 주고 새 요청이나 다른 채널       |

목적지 한도는 상점과 정규화한 목적지의 조합 단위로 센다.
`whatsapp`, `sms`, `email`은 10분에 5건, 1시간에 10건이고,
`misscall`은 10분에 2건, 1시간에 4건이다.
문서는 목적지 한도를 조정할 수 없다고 단언하고,
초당 20건 전역 한도는 지원팀과 상의해 올릴 수 있다고 한다.

## 웹훅

`otp.verified`는 `/v3/verify`가 성공했을 때와
Tap-to-Verify 토큰이 맞았을 때 나간다.
실패나 불일치에는 나가지 않는다.
웹훅 주소 등록과 `webhook_secret` 발급은 아직 OTP.ID 팀에 연락해서 해야 하고,
대시보드 셀프 설정은 곧 나온다고 적혀 있다.
주소가 없으면 이벤트는 조용히 버려진다.

서명은 `X-OTPID-Timestamp` 값과 마침표,
원본 본문을 이어 붙인 문자열의 HMAC-SHA256이고,
`X-OTPID-Signature` 헤더에 16진수로 온다.
본문에는 OTP 코드, 코드의 해시, 수신 토큰이 들어가지 않는다고 명시한다.
`external_id`를 항상 되돌려 주므로(보내지 않았으면 빈 문자열)
상점은 매핑 표 없이 자기 주문이나 세션에 이벤트를 붙일 수 있다.
실패하면 즉시, 1초 뒤, 2초 뒤 세 번까지만 시도하고 시도마다 제한 시간은 10초다.
세 번 모두 실패하면 이벤트는 버려진다.
같은 이벤트가 두 번 올 수 있으니 `otp_id`로 중복을 거르라고 권한다.

## 과금 규칙

크레딧은 공급자가 발송에 성공한 순간 원자적으로 차감된다.
발송 실패와 멱등성 재생은 차감되지 않는다.
예외는 Tap-to-Verify로,
보낼 발신 메시지가 없기 때문에 거래를 만드는 순간 요금이 빠지고,
사용자가 끝내 메시지를 보내지 않아도 돌려주지 않는다.

응답의 `price`는 이 거래에 매겨진(또는 성공했다면 매겨졌을) 크레딧이고,
`last_balance`는 거래 뒤 잔액이다.
문서는 계정마다 채널별 요율이 다를 수 있으니 실제 요율은 `price`를 보라고 한다.
그래서인지 문서 예제의 `price`는 공개 가격과 다르다.
WhatsApp 350, Missed Call 300, Voice 450, Tap-to-Verify 350으로,
공개 가격표의 370 또는 495, 250, 595, 120과 맞는 것이 하나도 없다.
크레딧 1이 1루피아인지도 문서에 명시되어 있지 않다.

API 키는 상점당 하나뿐인 UUID다.
교체하면 이전 키가 즉시 무효가 되고, 환경별 키 같은 것은 없어서
분리된 환경이 필요하면 상점 계정을 따로 만들라고 한다.
상점별 IP 허용 목록도 둘 수 있는데,
정확한 공인 IPv4·IPv6 주소만 받고 CIDR은 받지 않으며,
설정은 OTP.ID에 요청해서 한다.

## 함정

### 성공 응답 안에 실패가 들어 있다

발송 실패, 틀린 코드, 시도 마지막 오답이 모두 HTTP 200으로 온다.
HTTP 계층의 재시도 라이브러리나 모니터링이 200을 성공으로 세면,
발송 실패율과 오답률이 대시보드에서 사라진다.
`success`, `data.status`, `data.verified` 세 값을 모두 확인하는
한 겹의 처리층을 먼저 만드는 편이 안전하다.

만료와 시도 초과가 상태 값이 아니라는 점도 같은 종류의 함정이다.
상태 조회만 보는 화면은 이미 쓸 수 없는 거래를 `sent`로 보여 준다.

### 멱등성 키가 만료된 거래를 되살린다

`external_id`를 로그인 세션 ID처럼 오래 사는 값으로 정하면 문제가 생긴다.
OTP가 만료된 뒤 사용자가 다시 보내기를 눌러도,
24시간 안이라면 같은 키는 만료된 원래 거래를 재생한다.
새 코드는 나가지 않고, 사용자는 오지 않는 메시지를 기다린다.
문서도 이 점을 경고하며 키를 시도마다 새로 만들라고 한다.
재시도용 키와 상관관계용 키를 같은 값으로 쓰라는 권고와
시도마다 새 키를 쓰라는 권고가 함께 있으므로,
세션 ID에 시도 번호를 붙이는 식으로 둘을 모두 만족시켜야 한다.

`brand`, `ttl`, `otp_length` 차이가 무시된다는 점도 기억해야 한다.
TTL을 바꿔 다시 보냈는데 같은 키라면 이전 TTL의 거래가 그대로 돌아온다.

### 4자리 코드는 짧다

Missed Call은 접두부가 공개되고 끝 네 자리만 맞히면 된다.
경우의 수는 10,000이고 거래당 오답은 2회까지라,
무작위로 맞힐 확률은 거래당 0.02%다.
목적지당 1시간 4건 한도를 다 쓰면 시간당 8번 추측할 수 있어 약 0.08%가 된다.
이 수치는 문서의 한도로 직접 계산한 것이고, 문서가 이 확률을 말하지는 않는다.
문서는 4자리라 추측에 더 취약해서 한도를 더 엄격하게 둔다고만 설명한다.

Voice도 항상 네 자리지만 일반 채널과 같은 5회 오답 허용을 받으므로
거래당 0.05%다.
목적지 한도 표는 일반 채널을 `whatsapp`, `sms`, `email`로만 적고
`voice`를 넣지 않아서,
Voice의 시간당 한도는 문서만으로 알 수 없다.
가입 같은 낮은 위험 흐름이면 문제가 되지 않지만,
거래 승인이나 계정 복구에 4자리 채널을 쓰려면
상점 쪽에서 계정 단위 시도 제한을 덧붙여야 한다.

### 묶지 않은 Tap-to-Verify는 누구의 번호든 확인한다

`destination` 없이 만든 Tap-to-Verify 거래는
토큰이 맞는 메시지를 보낸 아무 번호로나 완료된다.
가입 시점에 번호를 아직 모를 때 쓰라는 용도이고,
그 경우 결과는 “누군가 이 토큰을 자기 WhatsApp에서 보냈다”는 사실이다.
상점은 웹훅이나 상태 조회의 `number`를 받아 그것을 사용자의 번호로 삼아야 하며,
사용자가 미리 입력한 번호와 비교하지 않으면
다른 사람의 휴대폰으로 확인을 끝내는 흐름이 열린다.
이것은 문서가 경고하는 내용이 아니라,
문서가 설명한 동작에서 따라 나오는 해석이다.

거래 생성 시 선과금되고 환불되지 않는다는 점은 남용 비용과 연결된다.
가입 화면에서 이 거래를 아무나 만들 수 있으면,
메시지를 보내지 않는 봇도 건당 요금을 쓰게 만든다.

### 펌핑 방어는 상점 몫이다

공개 문서에서 확인할 수 있는 남용 방어는 목적지별 발송 한도,
초당 20건 전역 한도, IP 허용 목록이다.
목적지별 한도는 번호 하나를 괴롭히는 것을 막을 뿐,
많은 번호로 퍼뜨리는 공격은 막지 못한다.
문서의 번호 규칙은 숫자 10자리 이상뿐이고, 국가 제한이나 접두번호 차단,
봇 판별에 대한 설명은 찾지 못했다.
약관은 스팸과 사기 목적 사용을 금지하고 남용 상점을 정지할 수 있다고 하지만,
상점의 가입 화면이 봇에게 털려서 생기는 비용을 누가 지는지는 말하지 않는다.
선불제에서는 그 비용이 상점 잔액에서 빠진다.
SMS OTP 엔드포인트를 노린 인위적 트래픽 사기의 구조는
[AIT 사기](ait-fraud.md) 문서에 정리되어 있다.
OTP.ID에서 SMS는 Rp670으로 가장 비싼 채널이므로, 같은 구조를 그대로 받는다.

### 상품 페이지와 API 문서가 어긋나는 곳

몇몇 설명은 홍보 페이지와 API 문서가 서로 다르다.

- WhatsApp 상품 페이지는 Tap-to-Verify에서 OTP.ID가 “isi pesan beserta hash-nya”, 즉 메시지 내용과 그 해시를 돌려준다고 적는다. API 문서에는 해시 필드가 없고, 웹훅 본문에는 해시가 들어가지 않는다고 명시한다.
- Tap-to-Verify 페이지는 상태를 `pending`, `waiting`, `invalid`, `expired`, `success`로 소개하지만, API 문서의 상태 값은 `pending`, `sent`/`success`, `failed`, `verified`이고 만료는 상태 값이 아니라고 한다.
- API 문서 소개 페이지와 `INVALID_CHANNEL` 오류 메시지는 채널을 다섯 개로 나열하며 `voice`를 빼놓았다. 채널 개념 문서와 요청 참조는 `voice`를 포함해 여섯 개를 말한다.
- 웹훅 참조는 `X-OTPID-Timestamp`가 너무 오래된(예: 5분 넘은) 요청을 거르는 것을 선택 사항으로 둔다. 재전송 공격을 막으려면 사실상 필수다.

구현할 때는 API 문서와 실제 응답을 기준으로 삼고,
상품 페이지 문구는 참고만 하는 편이 맞다.

## 체크리스트

- 모든 응답에서 `success`, `data.status`, `data.verified`를 확인하는가?
- `status: "failed"`일 때 `data.failure.code`로 사용자에게 다른 채널을 제안하는가?
- `external_id`를 OTP 시도마다 새로 만드는가?
- 409 응답에서 `existing_otp_id`로 원래 거래를 조회하는가?
- `DESTINATION_RATE_LIMITED`와 402를 자동 재시도에서 빼 두었는가?
- 검증 화면이 `expires_at`과 남은 시도 횟수를 따로 세는가?
- Missed Call에 접두부와 끝자리 칸만 있는 전용 화면을 쓰는가?
- 묶지 않은 Tap-to-Verify에서 확인된 `number`를 계정 번호로 저장하는가?
- 웹훅에서 원본 본문으로 서명을 검증하고, 타임스탬프 나이를 확인하고, `otp_id`로 중복을 거르는가?
- 웹훅이 세 번 만에 버려질 때를 대비해 상태 조회로 보충하는가?
- 가입·발송 화면에 상점 쪽 봇 차단과 국가 또는 번호 대역 제한을 두었는가?
- `last_balance`에 경보 임계값을 걸어 두었는가?
- API 키가 브라우저나 모바일 앱에 들어가지 않는가?

## 기억할 원칙

### 대행 API는 코드 생성보다 실패의 모양을 산다

OTP 코드를 만들고 비교하는 일은 몇 줄이면 된다.
OTP.ID 홈페이지에서 직접 만들기(Bangun sendiri)와
OTP.ID 쓰기(Pakai OTP.ID)를 비교한 표도
공급자 연동, 발신 번호와 템플릿 등록, 발송 기록을 먼저 내세운다.
상점이 실제로 사는 것은
공급자 장애와 번호 오류를 다섯 개의 안정된 실패 코드로 바꿔 주는 계약이다.
그 계약은 문서에 적힌 만큼만 유효하므로,
200 안에 숨은 실패와 상태 값이 아닌 만료처럼
계약의 경계에 있는 규칙을 먼저 읽어야 한다.

### 선불제는 남용 비용을 상점에게 넘긴다

건당 과금과 선불 잔액은 작은 상점에게 진입 장벽을 낮춘다.
같은 구조가 봇 트래픽의 비용을 그대로 상점 잔액에 떠넘긴다.
가장 싼 채널(Email Rp20)과 가장 비싼 채널(SMS Rp670)의 차이가 30배가 넘으므로,
기본 채널을 무엇으로 두고 어떤 조건에서 비싼 채널로 넘어갈지가
곧 보안 결정이자 비용 결정이다.
