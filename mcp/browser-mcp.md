# Browser MCP: AI 앱이 내 Chrome의 로그인된 탭을 조작하게 하는 MCP 서버

<https://browsermcp.io/>

<https://github.com/browsermcp/mcp>

HN 토론: <https://news.ycombinator.com/item?id=43613194> (616점, 217개 댓글)

GN 토론: <https://news.hada.io/topic?id=20209>

## 소개

Browser MCP는 Cursor, Claude, Windsurf, VS Code 같은 AI 애플리케이션을 사용자의 브라우저에 연결해, AI가 사용자를 대신해 웹 작업을 자동화하게 하는 MCP 서버와 Chrome 확장 프로그램의 조합이다.
홈페이지의 문제 설정은 단순하다.
폼을 반복해서 채우는 것 같은 웹사이트 작업을 자동화하고 싶어도 Cursor나 Claude 같은 AI 앱은 웹 브라우저에 접근하지 못하는데, Browser MCP가 그 연결을 만든다는 것이다.

홈페이지가 내세우는 쓰임새는 두 가지다.
하나는 AI 편집기가 코드를 끝에서 끝까지(end-to-end) 시험하게 하는 자동 테스트로, 사용자 흐름과 UI 요소를 확인한다.
다른 하나는 데이터 수집, 폼 채우기, 워크플로 자동화 같은 반복적인 웹 작업이다.

차별점으로는 네 가지를 든다.

| 특징                   | 홈페이지의 설명                                                         |
| ---------------------- | ----------------------------------------------------------------------- |
| 빠름(Fast)             | 자동화가 로컬에서 일어나 네트워크 지연이 없다                           |
| 비공개(Private)        | 브라우저 활동이 기기에 머물고 원격 서버로 가지 않는다                   |
| 로그인 유지(Logged In) | 기존 브라우저 프로필을 써서 모든 서비스에 로그인된 상태를 유지한다      |
| 은밀함(Stealth)        | 실제 브라우저 지문(fingerprint)을 써서 기본적인 봇 탐지와 캡차를 피한다 |

저장소 README는 Browser MCP가 Microsoft의 Playwright MCP 서버를 고쳐 만든 것이라고 밝힌다.
Playwright MCP가 새 브라우저 인스턴스를 띄우는 것과 달리, Browser MCP는 사용자의 기존 브라우저를 자동화해 로그인된 세션을 쓰고 자동화된 브라우저를 흔히 막는 봇 탐지를 피한다.
라이선스는 Apache-2.0이고, 2026년 9월 말 기준 GitHub 별 7,145개, 포크 584개, 열린 이슈 151개다.

## 동작 방식

### 세 조각의 연결

구성은 세 부분이다.
AI 애플리케이션이 MCP 클라이언트로서 로컬에서 `npx`로 띄운 Browser MCP 서버를 호출하고, 서버는 로컬 WebSocket 서버를 열어 Chrome 확장 프로그램의 연결을 기다린다.
확장 프로그램은 사용자가 “Connect”를 누른 탭 하나를 서버에 붙이고, 모든 브라우저 행동은 그 연결된 탭에서 일어난다.

저장소의 `src/ws.ts`는 WebSocket 서버를 만들기 전에 설정된 기본 포트를 점유한 프로세스를 종료하고, 포트가 빌 때까지 기다린 뒤 서버를 연다.
서버 패키지는 MCP SDK, `ws`, `zod`에 의존하는 작은 Node.js 프로그램이다.

확장 프로그램은 Chrome DevTools Protocol(CDP)로 브라우저를 자동화한다.
namuorg는 이 때문에 Chromium 계열 브라우저에서만 동작하며, Firefox는 확장 프로그램에 WebDriver BiDi를 노출하지 않아 지원하기 어렵다고 답했다.[^namuorg-firefox]
Chrome을 원격 디버깅 모드로 띄우게 하는 대신 확장 프로그램을 택한 이유로는, Chrome을 거의 항상 켜 두는 사용자에게 명령줄로 새 인스턴스를 띄우게 하는 것은 진입 장벽이 너무 높다고 설명했다.[^namuorg-extension]

### 제공하는 도구

홈페이지가 나열하는 브라우저 도구는 열두 가지다.

| 도구             | 하는 일                          |
| ---------------- | -------------------------------- |
| Navigate         | URL로 이동                       |
| Go Back          | 이전 페이지로                    |
| Go Forward       | 다음 페이지로                    |
| Wait             | 지정한 초만큼 대기               |
| Press Key        | 키보드 키 입력                   |
| Snapshot         | 현재 페이지의 접근성 스냅샷 캡처 |
| Click            | 웹 페이지 클릭                   |
| Drag & Drop      | 두 요소 사이 끌어 놓기           |
| Hover            | 요소 위에 마우스 올리기          |
| Type Text        | 편집 가능한 요소에 텍스트 입력   |
| Get Console Logs | 브라우저 콘솔 로그 가져오기      |
| Screenshot       | 현재 페이지 스크린샷             |

Snapshot이 접근성 트리를 돌려준다는 점은 Playwright MCP의 방식을 이어받은 것이다.
모델은 픽셀이 아니라 역할과 이름이 붙은 요소 목록을 보고 클릭할 대상을 고른다.

작성자 namuorg는 Show HN 스레드에서 Puppeteer MCP 서버는 CSS 선택자를 요구하는데 모델이 페이지를 읽지 않고 선택자를 지어내서 잘 안 된다고 설명했다.[^namuorg]
lxe는 이 방식이 YAML로 된 ARIA 스냅샷을 쓰므로 곧 컨텍스트 한도를 넘길 것이라고 지적했다.[^lxe]

### 한 번의 명령이 지나가는 길

문서의 첫 시험 명령은 google.com으로 가서 “Browser MCP”를 검색하라는 것이다.
이 명령에서 모델은 Navigate로 연결된 탭을 google.com으로 옮기고, Snapshot으로 검색창을 찾고, Type Text로 검색어를 넣고, Press Key로 Enter를 누른다.
각 단계는 MCP 도구 호출 하나이고, 서버는 그 호출을 WebSocket으로 확장 프로그램에 넘기며, 확장 프로그램이 실제 탭에서 실행한다.
사용자의 쿠키와 로그인 상태는 그 탭이 원래 가진 것이므로, 모델은 로그인 과정 없이 사용자가 로그인해 둔 서비스에 바로 닿는다.

## 설정하기

### 서버 등록

Node.js가 설치되어 있어야 한다.
MCP를 지원하는 AI 애플리케이션의 설정에 다음 서버 설정을 추가한다.

```json
{
  "mcpServers": {
    "browsermcp": {
      "command": "npx",
      "args": ["@browsermcp/mcp@latest"]
    }
  }
}
```

Cursor에서는 전체 설정의 Tools 탭에서 New MCP server를 누르고 위 설정을 넣은 뒤, `browsermcp` 옆의 새로 고침 버튼으로 설정을 다시 읽는다.
Claude Desktop, Windsurf, VS Code는 각 애플리케이션의 MCP 문서를 따른다.
문서는 Claude Desktop에 MCP 서버가 두 번 시작되는 버그가 있어 오류가 보이지만 동작은 한다고 적는다.

`@latest`를 붙이면 실행할 때마다 npm의 최신 버전을 가져온다.
공급망 관점에서는 버전을 고정하는 편이 안전하다.
npm 레지스트리의 현재 버전은 `0.1.3`이다.

```json
{
  "mcpServers": {
    "browsermcp": {
      "command": "npx",
      "args": ["@browsermcp/mcp@0.1.3"]
    }
  }
}
```

### 확장 프로그램 연결

Chrome 웹 스토어에서 Browser MCP 확장 프로그램을 설치하고 툴바에 고정한다.
자동화할 탭에서 확장 프로그램 아이콘을 누르고 “Connect”를 누른다.
이후 모든 행동은 그 탭에서 일어난다.

### 막혔을 때

문서가 꼽는 오류 원인은 두 가지다.
MCP 서버가 돌지 않거나, 브라우저가 서버에 연결되지 않은 경우다.
`Client closed` 메시지가 나오고 새로 고침으로 풀리지 않으면, 설정에서 `@latest`를 빼고 `@browsermcp/mcp`로 쓰라고 한다.

## 트레이드오프

### 로그인된 프로필은 편의이자 반경이다

Browser MCP의 핵심 가치는 사용자의 실제 프로필을 쓴다는 것이다.
새 브라우저를 띄우는 Playwright MCP에서는 로그인을 자동화하거나 테스트 계정을 따로 준비해야 하지만, Browser MCP에서는 사용자가 이미 로그인한 모든 서비스가 곧바로 쓸 수 있는 상태다.
사내 도구, 관리자 콘솔, 개인 메일이 모두 여기에 들어간다.

그 편의가 곧 위험의 반경이다.
모델이 연결된 탭에서 읽는 페이지에 숨은 지시가 있으면, 그 지시는 사용자의 모든 로그인 세션을 등에 업고 실행될 수 있다.
Browser MCP 자체에는 Claude in Chrome의 금지 행동 목록, 사이트 단위 권한, 행동 검사 분류기 같은 계층이 문서에 나오지 않는다.
어떤 행동을 허용할지는 MCP 클라이언트의 도구 승인 설정에 달려 있다.

그래서 연결 단위를 탭 하나로 둔 것은 중요한 설계다.
모델은 사용자가 Connect를 누른 탭에서만 움직인다.
하지만 Navigate는 그 탭을 어느 URL로든 옮길 수 있으므로, 탭 하나라는 제한은 화면의 경계일 뿐 로그인 세션의 경계는 아니다.

같은 효과를 얻는 다른 길도 있다.
cAtte\_는 Playwright에서도 `launchPersistentContext()`에 기존 Chrome 설치의 사용자 데이터 디렉터리를 넘기면 개인 맥락에 접근할 수 있다고 알려 줬다.[^cAtte_]

### 봇 탐지 회피는 기능이면서 약관 문제다

홈페이지는 실제 브라우저 지문으로 기본적인 봇 탐지와 캡차를 피한다는 것을 장점으로 내세운다.
자동 테스트에서 자기 앱을 시험할 때는 이것이 순수한 편의다.
하지만 다른 회사의 사이트에서 데이터를 모으거나 폼을 채울 때는, 그 사이트가 자동화 접근을 막으려고 둔 장치를 우회하는 일이 된다.

같은 문제를 Anthropic은 반대 방향으로 풀었다.
Claude in Chrome은 캡차 우회와 봇 인증 우회를 금지 행동으로 두고, 제3자 웹사이트의 자동화 접근 제한을 지키는 책임이 사용자에게 있다고 명시한다.
Browser MCP는 우회를 기능으로 광고하면서 그 책임에 대해서는 말하지 않는다.
사용자는 어느 사이트에서 이 기능을 써도 되는지 스스로 판단해야 한다.

회피가 광고만큼 통하는지도 의문이다.
bhouston은 자기가 만든 비슷한 도구로 로그인된 세션을 AI에게 조작시켰더니, 사람으로 쓰는 세션에서도 캡차가 뜨기 시작했고 결국 여러 사이트에서 차단당했다고 경고했다.[^bhouston]
그 사용을 멈추자 차단은 풀렸지만, 봇 탐지는 도구가 아니라 계정과 브라우저에 흔적을 남긴다는 뜻이다.
unixfox는 확장 프로그램이 브라우저 디버깅을 켜서 자동화 배너가 뜨고, 이것은 JavaScript로 탐지할 수 있다고 덧붙였다.[^unixfox]
xena는 관리자가 이 도구를 막을 수 있도록 robots.txt를 지키느냐고 물었지만, 스레드에서 작성자의 답은 없었다.[^xena]

### 로컬 처리는 비공개를 보장하지 않는다

홈페이지는 자동화가 로컬에서 일어나므로 브라우저 활동이 기기에 머문다고 말한다.
Browser MCP 서버와 확장 프로그램 사이의 통신은 로컬이 맞다.
그러나 Snapshot, Screenshot, Get Console Logs가 돌려주는 내용은 MCP 클라이언트를 거쳐 모델에게 간다.

Cursor나 Claude Desktop이 원격 모델을 쓴다면, 연결된 탭의 접근성 트리와 스크린샷과 콘솔 로그는 그 모델 제공자의 서버로 전송된다.
비공개라는 설명은 Browser MCP 자신의 서버를 두지 않는다는 뜻에 가깝고, 페이지 내용이 기기를 떠나지 않는다는 뜻은 아니다.

출시 당일 HN에서 johnpaulkiser가 바로 이 점을 물었다.[^johnpaulkiser]
namuorg는 AI 모델에 데이터가 가는 것은 당연하고, 비공개라는 말은 원격 브라우저로 자동화하는 서비스와 대비한 것이라고 답했다.[^namuorg-private]
원격 브라우저 서비스는 모든 브라우징 활동과 로그인 정보를 받지만, Browser MCP에서는 모델에 가는 도구 호출 결과 외에는 기기에 남는다는 것이다.
johnpaulkiser는 모델뿐 아니라 사용자가 허용한 다른 도구에도 브라우징 데이터가 노출될 수 있으므로, 비기술 사용자에게는 그 위험을 명시해야 한다고 재반박했다.[^johnpaulkiser-2]
민감한 페이지를 연결할지는 이 경로를 기준으로 판단해야 한다.

## 함정

### 유지보수가 멈춰 있다

저장소의 마지막 커밋은 2025년 4월 24일의 `0.1.3` 버전이고, 문서의 변경 기록은 2025년 5월 7일의 확장 프로그램 `v1.3.4`에서 끝난다.
2026년 9월 기준으로 약 1년 5개월 동안 저장소에 새 코드가 없고, 열린 이슈는 151개다.
MCP 명세와 클라이언트는 그동안 계속 바뀌었으므로, 설정이 맞는데도 연결이 안 되는 문제를 만나면 이 공백을 먼저 의심해야 한다.

### 저장소만으로는 빌드할 수 없다

README는 이 저장소에 핵심 MCP 코드가 있지만, 개발하는 모노레포의 유틸리티와 타입에 의존해 단독으로 빌드할 수 없다고 적는다.
실제로 `src/ws.ts`는 `@repo/config`와 `@repo/utils`를 가져오고, `package.json`의 개발 의존성에는 `workspace:*` 참조가 있다.
Apache-2.0 라이선스로 공개되어 있지만, 사용자가 코드를 읽고 직접 빌드해 npm 패키지와 같은지 확인하는 경로는 막혀 있다.
확장 프로그램의 코드는 이 저장소에 없다.

출시 당일 rmac은 확장 프로그램이 PostHog와 Amplitude로 텔레메트리를 보내고, 소스가 공개되지 않은 확장 프로그램이 playwright-crx를 출처 표시 없이 묶었을 가능성이 있다고 경고했다.[^rmac]
namuorg는 익명 기기 ID와 도구 호출 시 분석 이벤트를 보낸다는 것을 인정하면서, 개인 식별 정보는 전혀 보내지 않으니 네트워크 트래픽으로 확인할 수 있고 확장 프로그램은 전부 직접 작성했다고 답했다.[^namuorg-telemetry]
tomrod는 텔레메트리는 언제나 옵트인이어야 한다고 반박했다.[^tomrod]
홈페이지의 비공개라는 설명과 별개로, 사용량 이벤트는 기본값으로 외부 분석 서비스에 간다는 뜻이다.

### 서버가 포트를 쓰던 프로세스를 죽인다

`createWebSocketServer`는 기본 포트를 점유한 프로세스를 먼저 종료한다.
같은 포트를 우연히 쓰던 다른 개발 서버가 있으면 경고 없이 꺼진다.
이 동작의 이유는 작성자가 직접 설명했다.
Claude Desktop이 서버를 두 번 시작하는 버그가 있어서, 서버가 이전 실행의 프로세스를 죽이도록 만들었다는 것이다.[^namuorg-windows]
그 설명은 cadence-가 Windows에서 `netstat`과 `taskkill`로 9009번 포트를 정리하는 명령이 실패해 서버가 죽는 로그를 올린 데 대한 답이었고, 작성자는 오류를 더 잘 다루는 0.1.1을 바로 게시했다.[^cadence-]
클라이언트 버그를 피하려는 코드가 같은 포트를 쓰던 무관한 프로세스까지 종료하는 셈이다.

### `@latest`는 매번 새 코드를 실행한다

권장 설정의 `@browsermcp/mcp@latest`는 MCP 클라이언트가 서버를 띄울 때마다 npm의 최신 버전을 받아 실행한다.
유지보수가 멈춘 패키지의 게시 권한이 넘어가거나 탈취되면, 다음 실행에서 사용자의 로그인된 브라우저에 닿는 코드가 바뀐다.
버전을 고정하고, 바꿀 때는 변경 내용을 확인한다.

### 연결된 탭을 닫으면 조용히 끊긴다

변경 기록에는 연결된 탭을 닫거나 새 탭 같은 잘못된 URL을 연결한 뒤 연결 문제가 생기던 버그를 고쳤다는 항목이 있다.
연결 상태는 탭에 묶여 있으므로, 사용자가 작업 중에 그 탭을 닫거나 다른 탭으로 옮겨 가면 모델의 다음 도구 호출이 실패한다.

## 확인하기

로컬에서 동작과 경계를 확인하는 순서다.

1. MCP 클라이언트 설정에 버전을 고정한 서버 설정을 넣고 클라이언트를 다시 시작한다.
2. 로그인 세션이 없는 별도 Chrome 프로필을 만들고, 그 프로필에만 확장 프로그램을 설치한다.
3. 빈 테스트 페이지나 로컬 개발 서버의 탭에서 Connect를 누른다.
4. 문서의 시험 명령처럼 간단한 이동과 입력을 시켜 보고, 클라이언트에서 도구 호출이 어떻게 승인되는지 본다.
5. Snapshot과 Screenshot의 결과가 클라이언트 대화에 어떻게 들어가는지 확인한다. 이것이 모델에게 가는 내용이다.
6. 연결된 탭을 닫고 다음 명령이 어떻게 실패하는지 본다.

```bash
# 서버가 연 포트와 그 포트를 쓰는 프로세스를 확인한다(macOS, Linux)
lsof -nP -iTCP -sTCP:LISTEN | grep -i node
```

## 체크리스트

- 확장 프로그램을 민감한 계정에 로그인되지 않은 별도 프로필에 설치했는가?
- 서버 버전을 `@latest`가 아닌 특정 버전으로 고정했는가?
- MCP 클라이언트가 브라우저 도구 호출마다 승인을 요구하도록 설정되어 있는가?
- 연결한 탭이 신뢰할 수 없는 사용자 생성 콘텐츠를 보여 주지 않는가?
- 자동화 대상 사이트의 약관이 자동화 접근을 허용하는가?
- 원격 모델을 쓴다면, 연결된 탭의 내용이 모델 제공자에게 전송되어도 괜찮은가?
- 서버의 기본 포트를 다른 개발 도구가 쓰고 있지 않은가?

## 기억할 원칙

### 브라우저 에이전트의 안전은 어느 계층이 책임지는지로 판단한다

Browser MCP와 Claude in Chrome은 같은 일을 한다.
사용자의 로그인된 Chrome에서 AI가 클릭하고 입력하게 한다.
차이는 안전 계층이 어디에 있느냐다.

Claude in Chrome은 권한 모드, 사이트 단위 허용, 금지 행동 목록, 행동 검사 분류기를 제품 안에 둔다.
Browser MCP는 도구를 제공할 뿐이고, 승인과 거부는 MCP 클라이언트에 맡긴다.
어느 쪽이 더 안전한지는 도구가 정하지 않는다.
사용자의 클라이언트 설정과 프로필 격리가 그 계층을 채우느냐가 정한다.

그래서 MCP로 브라우저를 여는 도구를 쓸 때는, 그 도구가 무엇을 막아 주는지가 아니라 무엇을 막아 주지 않는지를 먼저 적어 두어야 한다.
그 목록이 곧 사용자가 직접 채워야 할 방어의 목록이다.
