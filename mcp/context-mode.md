## 소개

Context Mode는 AI 코딩 에이전트의 컨텍스트 윈도우 소비를 줄이는 MCP 서버다.
MCP 도구 호출 시 원시 데이터가 대화 컨텍스트에 직접 쌓이는 구조적 문제를
샌드박스 실행, 세션 지속성, 코드로 생각하기라는 세 가지 전략으로 해결하고,
네 번째 항목으로는 하지 않는 일 하나를 명시한다.
프로젝트가 제시하는 대표 수치는 “315 KB → 5.4 KB, 98% 절약”이다.

README가 여는 문제 서술은 구체적이다.
Playwright 스냅샷 하나가 56 KB, GitHub 이슈 20개가 59 KB,
접근 로그 하나가 45 KB이고, 30분이 지나면 컨텍스트의 40%가 사라진다는 것이다.
그리고 에이전트가 공간을 확보하려고 대화를 압축하면 자기가 어떤 파일을 고치고
있었는지, 어떤 작업이 진행 중인지, 사용자가 마지막에 무엇을 요청했는지를 잊는다.
저장소 설명은 이것을 “17개 플랫폼에 걸쳐 MCP와 훅으로 라우팅을 강제한다”고
요약하며, 여기에 OpenClaw 게이트웨이 통합이 별도로 붙는다.

저장소는 2026년 2월 23일에 만들어졌다.
이전 갱신 시점에는 GitHub 스타 19,813개, 포크 1,425개, 열린 이슈 146개였고,
2026년 10월 11일 GitHub API 기준으로는 스타 26,421개, 포크 1,903개이며
열린 이슈 173개와 열린 PR 169개를 합해 342건이 열려 있다.
언어는 TypeScript이고 라이선스는 Elastic License 2.0이다.
Hacker News에서 570점으로 1위에 올랐던 이력을 README 배지로 표시한다.
이 HN 스레드의 링크 대상은 저장소가 아니라 저자 블로그의 설명 글이며,
그 사흘 전에 저장소 자체를 올린 Show HN 글이 따로 있다.
README 상단의 users 배지는 저장소의 `stats.json`을 읽는데,
2026년 10월 11일 값은 667.7k+이고 그 안에서 npm이 623.3k+,
마켓플레이스가 44.3k+다.
곧 배지 이름은 사용자 수지만 실제로는 설치 횟수를 합한 값으로 보인다(해석).
그 아래에는 Microsoft, Google, Meta, Amazon, NVIDIA 등 18개 회사 로고를
“Used across teams at”이라는 문구와 함께 늘어놓았는데,
각 로고의 링크는 `#`이라 근거로 이어지지 않는다.

이 저장소는 이제 회사 제품군의 일부이기도 하다.
2026년 10월 11일 현재 `context-mode.com` 홈페이지가 주력으로 내세우는 것은
이 플러그인이 아니라 Claude Code와 Codex 앞에 두는 호스팅 게이트웨이이며,
이 저장소의 플러그인은 “Context Mode Engine”이라는 이름의
무료 제품으로 따로 소개된다.
자세한 내용은 아래 호스팅 게이트웨이 절에 정리한다.

## 핵심 전략

### 샌드박스 실행

`ctx_execute`를 비롯한 도구들이 코드를 격리된 서브프로세스에서 실행하고
stdout만 컨텍스트에 주입한다.
Playwright 스냅샷(56 KB), GitHub API 응답(59 KB), 접근 로그(45 KB) 같은
원시 데이터는 대화에 노출되지 않는다.

12개 언어 런타임을 제공한다.
JavaScript, TypeScript, Python, Shell, Ruby, Go, Rust, PHP, Perl, R, Elixir,
C#이며 JS/TS는 Bun이 감지되면 3~5배 빠르게 실행된다.
`gh`, `aws`, `gcloud`, `kubectl`, `docker` 같은 인증된 CLI는
자격 증명 통과 방식으로 환경 변수와 설정 경로를 물려받되
대화에는 노출되지 않는다.
출력이 5 KB를 넘고 `intent`가 주어지면 의도 기반 필터링으로 전환해,
전체 출력을 지식 베이스에 색인한 뒤 의도에 맞는 구간만 돌려준다.

### 세션 지속성

대화가 압축(compaction)되면 모델은 작업 중이던 파일, 열린 태스크, 미해결 오류를
잃는다.
Context Mode는 파일 수정, Git 작업, 태스크 상태, 오류, 사용자 결정을 SQLite에
기록하는데, 압축 시 그 데이터를 컨텍스트에 도로 쏟아붓지 않는다.
이벤트를 FTS5에 색인해 두고 BM25 검색으로 관련된 것만 꺼내 오는 방식이다.
`PreCompact`가 우선순위 계층으로 2 KB 이하의 XML 스냅샷을
만들어 `session_resume` 테이블에 저장하고,
`SessionStart`가 그것을 꺼내 15개 범주의 세션 가이드를
구성해 `<session_knowledge>` 지시문으로 주입한다.
2 KB 예산이 빠듯하면 의도나 MCP 도구 호출 수 같은 낮은 우선순위 항목부터 버리고
활성 파일과 태스크와 규칙과 결정은 언제나 보존한다.
포착 범주는 23개이며 파일과 태스크와 계획과 규칙과 사용자 프롬프트가
최상위 우선순위, Git과 오류와 오류 해결 쌍과 제약과 블로커와 거부된 접근과
환경과 반복 루프가 그다음이다.
다섯 개 훅(PreToolUse, PostToolUse, UserPromptSubmit, PreCompact,
SessionStart)이 협력해 상태를 보존하며, Stop을 포함하면 여섯 개다.
`--continue`를 쓰지 않으면 이전 세션 데이터는 즉시 삭제된다.
새 세션은 백지에서 시작한다는 원칙이다.

복원 경로는 압축만이 아니다.
README는 `--continue`, `--resume`, `/resume`으로
다시 이어 갈 때도 작업 상태를 다시 세운다고 적고,
`/resume`의 선택 목록에서 최신이 아닌 세션을 고르면 `SessionStart` 훅이
새 세션 id에 이벤트가 없음을 알아채고 그 프로젝트에서 아직 쓰지 않은
가장 최근 스냅샷으로 돌아간다고 설명한다.
압축 뒤 모델이 받는 세션 가이드는 마지막 요청, 태스크, 계획, 핵심 결정,
수정한 파일, 미해결 오류, 제약, 블로커, Git, 프로젝트 규칙 등으로 이루어진다.
README의 흐름도는 이것을 15개 범주라고 적지만 바로 아래 목록에는
19개 항목이 있다.

세션 복원이 온전히 되는지는 에이전트마다 다르다.
README의 호환표는 Claude Code와 OpenCode와 KiloCode를 Full로,
Gemini CLI와 VS Code Copilot과 JetBrains Copilot과 GitHub Copilot CLI와
OpenClaw와 Pi와 OMP를 High로, Cursor와 Codex CLI와 Antigravity CLI와 Kiro를
Partial로 표시하며, Antigravity IDE와 Zed에서는 세션 추적이 없다.
Gemini CLI와 VS Code Copilot처럼 `UserPromptSubmit`에 해당하는 훅이 없는
곳에서는 사용자의 결정과 정정이 기록되지 않는다.

### 코드로 생각하기

LLM이 50개 파일을 읽어 함수 수를 세는 대신, 분석 스크립트를 작성해 결과만
받는다.
10번의 도구 호출을 1번으로 줄이고 컨텍스트 사용량을 약 100배 절약한다.
README는 이것을 17개 클라이언트 전체에 걸친 필수 패러다임이라고 표현하며,
LLM을 데이터 처리기로 취급하지 말고 코드 생성기로 취급하라고 적는다.

```js
// Before: 47 × Read() = 700 KB.  After: 1 × ctx_execute() = 3.6 KB.
ctx_execute("javascript", `
  const files = fs.readdirSync('src').filter(f => f.endsWith('.ts'));
  files.forEach(f => console.log(f + ': ' + fs.readFileSync('src/'+f,'utf8').split('\n').length + ' lines'));
`);
```

### 문체를 강제하지 않는다

네 번째 항목은 기능이 아니라 하지 않기로 한 일이다.
Context Mode는 원시 데이터를 컨텍스트 밖에 두되 모델이 최종 답변을 어떻게
쓰는지는 지시하지 않는다는 것이다.
간결함이나 완결성이나 서식은 모델의 판단이거나 사용자가 자기 `CLAUDE.md`와
`AGENTS.md`로 정할 몫이라고 적는다.
근거로는 공격적인 간결성 프롬프트가 코딩과 추론 벤치마크 성능을 떨어뜨린다는
Moonshot AI의 `kimi-k2.5` 관련 보고를 든다.
라우팅 블록은 데이터가 어디로 가는지에 집중하며 모델이 어떻게 말하는지는 다루지
않는다는 것이다.

이 항목은 이전 판에서 뒤집힌 것이다.
과거 README는 응답에서 조사와 불필요한 수식어와 인사말을 제거해 출력 토큰을
65~75% 절약한다는 출력 압축을 네 번째 전략으로 내걸었다.
지금은 같은 자리에 정반대 원칙이 들어가 있다.

다만 그 흔적이 README에 남아 있다.
2026년 10월 11일 판 README의 문제 서술 절은 여전히 에이전트가 군말과 인사말과
장황한 설명에 출력 토큰을 낭비해 양쪽에서 컨텍스트를 태운다고 적고,
이어서 이 문제의 네 측면을 모두 푼다고 말한다.
그런데 바로 아래 네 번째 항목은 모델의 문체를 지시하지 않는다는 원칙이다.
문제 서술은 옛 판을, 해법 목록은 새 판을 따르고 있는 셈이다.

## 도구 목록

| 도구                  | 기능                                      | 절약 효과      |
| --------------------- | ----------------------------------------- | -------------- |
| `ctx_execute`         | 12개 언어로 코드 실행, stdout만 수집      | 56 KB → 299 B  |
| `ctx_batch_execute`   | 명령/쿼리 다중 실행                       | 986 KB → 62 KB |
| `ctx_execute_file`    | 파일을 샌드박스에서 처리                  | 45 KB → 155 B  |
| `ctx_index`           | 마크다운을 청크 분할 후 FTS5에 색인       | 60 KB → 40 B   |
| `ctx_search`          | BM25 랭킹으로 색인 내용 검색              | 온디맨드 조회  |
| `ctx_fetch_and_index` | URL 가져와 마크다운 변환 후 24시간 캐시   | 60 KB → 40 B   |
| `ctx_stats`           | 컨텍스트 절약량과 세션 지표 표시          | —              |
| `ctx_doctor`          | 설치, 런타임, FTS5 진단                   | —              |
| `ctx_upgrade`         | GitHub에서 최신 버전으로 업데이트         | —              |
| `ctx_purge`           | 색인된 콘텐츠 전체 삭제                   | —              |
| `ctx_insight`         | 호스팅 Insight 대시보드를 브라우저로 열기 | —              |

여섯 개 샌드박스 도구와 다섯 개 메타 도구를 합해 11개다.
`ctx_batch_execute`는 여러 명령과 여러 질의를 한 번의 호출로 묶고
I/O 위주 배치에서는 `concurrency: 1-8`을 선택적으로 쓴다.
`ctx_fetch_and_index`는 기본 24시간 TTL 캐시를 쓰며 호출마다 `ttl`을 덮어쓰거나
`ttl: 0` 또는 `force: true`로 우회할 수 있고, 14일이 지난 콘텐츠 데이터베이스는
시작 시 정리된다.
`ctx_insight`는 다른 도구들과 성격이 다르다.
`context-mode.com/insight`의 호스팅 대시보드를 브라우저로 여는 것이며,
README는 이것을 AI 지원 엔지니어링 팀을 위한 조직 분석이라고 소개한다.

`ctx_search`에는 점진적 제동이 걸려 있다.
1~3회 호출은 질의당 결과 2건을 정상 반환하고,
4~8회는 1건으로 줄이며 경고를 붙이고,
9회부터는 차단하고 `ctx_batch_execute`로 유도한다.

## 지식 베이스 아키텍처

SQLite FTS5에 BM25 랭킹을 적용하고 Porter 어근 분석으로
“running”, “runs”, “ran”을 동일 어근으로 처리한다.
헤딩에는 5배 가중치를 부여한다.

검색은 Porter 어근 색인과 트라이그램 부분 문자열 검색 결과를
Reciprocal Rank Fusion으로 병합한다.
다중 용어 쿼리는 용어가 인접한 단락을 더 높게 평가하는 근접 재랭킹을 적용한다.
오타 보정도 내장되어 있다(“kuberntes” → “kubernetes”).

## 설치

Claude Code에서는 플러그인 마켓플레이스로 설치할 수 있다.

```bash
/plugin marketplace add mksglu/context-mode
/plugin install context-mode@context-mode
```

훅이 런타임에 자동 주입되고 프로젝트에 파일이 기록되지 않는다.
라우팅 지시 파일을 첫 세션 시작 시 프로젝트 디렉터리에 자동으로 쓰던 동작은
git 트리를 더럽힌다는 이유로 비활성화되었다.
Gemini CLI, VS Code Copilot 등은 설정 파일을 별도로 작성해야 한다.
훅을 지원하지 않는 Zed와 Antigravity IDE는 라우팅 파일을 한 번 수동으로
복사한다.

2026년 10월 11일 판 README의 설치 절은 18개 항목을 다룬다.
Claude Code, Gemini CLI, VS Code Copilot, JetBrains Copilot, GitHub Copilot CLI,
Cursor, OpenCode, KiloCode, OpenClaw와 Pi Agent, Codex CLI, Kimi Code,
Qwen Code, Antigravity IDE, Antigravity CLI(`agy`), Kiro, Zed, Pi Coding Agent,
OMP(Oh My Pi)다.
홈페이지의 Engine 소개도 같은 맥락에서 18개 AI 코딩 도구라고 적는다.
Kimi Code는 Codex와 같은 JSON 훅 규약을 TOML 설정으로 쓰고,
Qwen Code는 Claude Code와 같은 훅 규약을 쓴다고 README는 설명한다.
Cursor 마켓플레이스 플러그인은 아직 Cursor 팀의 검토를 기다리는 중이어서
로컬 폴더에 복제해 넣는 방식이 안내된다.
슬래시 명령과 플러그인 마켓플레이스는 Claude Code에만 있고,
다른 에이전트에서는 대화창에 `ctx stats`나 `ctx doctor`처럼 입력하면 모델이
해당 MCP 도구를 부른다.

런타임 쪽에서는 Linux에서 Node.js 22.5 이상이면
네이티브 애드온인 `better-sqlite3` 대신 내장 `node:sqlite`를 자동으로 쓰며,
Linux에서 V8의 메모리 반환 동작이 애드온을 망가뜨려 생기던 간헐적 SIGSEGV를
피하려는 조치라고 README는 설명한다.
Linux에서 Node.js 22.5 미만은 지원하지 않고, Bun에서는 `bun:sqlite`를 쓴다.

라우팅 강제 수단에 따라 절약 효과가 갈린다.
훅이 있는 플랫폼은 약 98% 절약,
지시 파일만 있는 플랫폼은 약 60% 절약으로 표시된다.
README는 훅 없이는 라우팅되지 않은 `curl` 하나나 Playwright 스냅샷 하나가
56 KB를 컨텍스트에 부어 한 세션치 절약을 통째로 날릴 수 있다고 적는다.

Claude Code용 상태 표시줄은 플러그인 매니페스트로
선언할 수 없어 `~/.claude/settings.json`을 한 번 직접 고쳐야 하며,
이번 세션 절약액과 누적 절약액과 효율 비율을 달러로 보여 준다.

소스 코드는 공개되어 있지만 관리형 서비스로 재패키징하거나
라이선스 표시를 제거하는 것은 금지된다.
README는 MIT 대신 ELv2를 고른 이유를 명시하는데, MIT는 이 코드를 경쟁하는
폐쇄 소스 SaaS로 재포장하는 것을 허용하지만 ELv2는 소스를 모두에게 열어 둔 채
그것만 막는다는 것이다.

데이터는 로컬 SQLite에만 저장되고 외부로 전송되지 않는다.
`file://`, `gopher://`, `data://` 같은 위험 스킴과
AWS/GCP/Azure 메타데이터 엔드포인트(169.254.169.254)는
MCP 계층에서 차단된다.
이 차단은 `ctx_fetch_and_index`에 걸린 것으로,
호스트 이름이 그 주소로 풀리는 경우까지 막아 DNS 리바인딩을 방어한다.
반면 `localhost`와 사설망(RFC1918) 주소는 로컬 개발 서버를 위해 기본으로
허용되며, 공유 서비스나 CI처럼 이것까지 막아야 하면 `CTX_FETCH_STRICT=1`을 켠다.

권한 규칙은 Claude Code의 설정 형식을 그대로 빌린다.
`.claude/settings.json`에 `Bash(sudo *)` 같은 거부 규칙을 두면 그 규칙이
`ctx_execute`와 `ctx_execute_file`과 `ctx_batch_execute` 안에서도 적용되며,
README는 Gemini CLI나 OpenCode에서도 같은 형식을 읽는다고 적는다.
`&&`, `;`, `|`로 이은 명령은 조각마다 따로 검사하고, 거부가 허용보다 우선한다.

2026년 6월 22일의 v1.0.164에서는 `ctx_execute_file`이 프로젝트 루트 밖의 경로를
읽지 못하게 막혔다(#852).
호스트 샌드박스가 프로젝트 밖 읽기를 거부하자 에이전트가 MCP 샌드박스로
우회해 같은 파일을 읽을 수 있었고,
MCP 승인 창은 도구 인자를 보여 주지 않아 승인하는 사람이 그 우회를
볼 수 없었다는 것이 README의 설명이다.
README는 이 장치가 파일 읽기 도구를 위한 다층 방어일 뿐 완전한 OS 샌드박스가
아니며, `ctx_execute`와 `ctx_batch_execute`는 임의 코드를 실행하고 프로세스의
파일 시스템 접근을 그대로 물려받으므로 실행 도구를 승인하는 것은 임의
코드 실행을 승인하는 것으로 여기라고 적는다.
앞에서 쓴 “격리된 서브프로세스”는 프로세스 경계를 뜻할 뿐 파일 시스템 격리를
뜻하지는 않는다는 점을 함께 봐야 한다.
그 밖에 `mcp__*` 도구 호출의 인자는 세션 DB에 저장되기 전에 `authorization`,
`token`, `password`, `api_key` 같은 키의 값이 가려진다.

## 호스팅 게이트웨이

2026년 10월 11일 현재 홈페이지는 Context Mode를 코딩 에이전트와 모델 사이의
제어 평면이라고 소개한다.
제품은 셋이다.
주력인 Context Mode는 호스팅 게이트웨이이고,
Context Mode Engine은 이 저장소의 무료 플러그인이며,
Context Mode Insight는 Engine이 기록한 이벤트로 팀의 에이전트 사용을 보여 주는
대시보드다.
홈페이지 하단의 운영 주체는 영국 런던의 MKSF LTD다.

게이트웨이는 플러그인과 작동 위치가 다르다.
`npx @context-mode/cli`가 Claude Code의 `~/.claude/settings.json`에
`ANTHROPIC_BASE_URL`을 `https://gateway.context-mode.com`으로 바꾸는 항목과
장치 키 헤더를 쓰고, Codex의 `~/.codex/config.toml`에는 같은 주소를 쓰는
모델 제공자를 추가한다.
그러면 에이전트의 모든 모델 요청이 게이트웨이를 거쳐 사용자의 Anthropic 또는
OpenAI 계정으로 전달된다.
지원 에이전트는 Claude Code와 Codex 둘이고 OpenCode와 Pi는 예정으로 표시된다.
문서는 한계로 Cloudflare 위에서만 돌고 온프레미스 빌드가 없으며 SSO와 팀 역할이
아직 없다고 밝힌다.

기능은 세 묶음이다.
절약 쪽에는 테스트와 빌드와 로그 출력을 처음 볼 때 접어 넣는 Context Saving,
스크립트를 돌려 출력만 돌려주는 Thinking in Code, 스레드가 보낼 이력을 200K,
500K, 1M 중에서 고르는 Active Context가 있다.
기억 쪽에는 압축 없이 최근 작업과 오래된 작업의 색인만 보내고 원문은 보관소에서
id와 단어와 시간으로 찾아 읽게 하는 Recall,
사실마다 유효 시작과 끝이라는 두 시계를 붙여 값이 바뀌면 옛 값을 지우지 않고
닫는 Memory, GitHub에서 가져온 스킬 중 맞는 것을 골라 넣는 Skills,
세션 전체 검색인 Search, 다른 기계에서 세션을 이어 가는 Session resume이 있다.
통제 쪽에는 도구 호출을 이름이 아니라 하는 일로 읽어
`.env` 읽기나 보호 브랜치 push나 `rm -rf ~` 같은 호출을 실행 전에 막는
Protect와 상시 지시문인 Instructions가 있다.
Recall 보관소는 기본 90일 보관하며,
비밀 값과 이메일 주소는 저장 전에 가린다고 적는다.

요금은 요청 수로 매긴다.
Free는 계정당 한 번 1,000건, Pro는 월 49달러 또는 연 490달러에 월 50,000건,
Team은 좌석당 과금에 조직 단위 Protect 정책을 더하고,
Enterprise는 전용 인스턴스나 고객의 Cloudflare 계정 배포를 제공한다.
모델 비용은 사용자의 제공사 계정이 그대로 내며 토큰에 수수료를 붙이지 않는다고
하고, 요청이 바닥나면 에이전트가 끊기지 않고 모델로 직접 연결된다고 설명한다.

벤치마크는 플러그인 때와 단위가 다르다.
게이트웨이 문서는 바이트가 아니라 달러로 재며,
Claude Code 2.1.283과 Claude Opus 5.5로 같은 과제를 직접 연결과 게이트웨이
경유로 번갈아 돌린 사전 등록 짝 실험을 내세운다.
2026년 10월 3일의 30단계 긴 세션 4쌍에서 7.20달러가 2.49달러로 65.5% 줄었고,
2026년 9월 29일의 짧은 과제 168쌍에서는 155쌍이 더 쌌으며 과제 성공은 양쪽 모두
168건 전부였다고 적는다.
200K 창에서 Recall을 켠 3쌍에서는 비용이 37.6% 줄고
초기 세부 사항 질문 10개 중 정확한 답이 직접 연결 4개 대비 9개였으며,
직접 연결은 세 번 압축됐지만 게이트웨이 쪽은 한 번도 압축되지 않았다고 한다.
다만 같은 문서는 이 표가 비용이 낮아진 작업만 보여 주며 그렇지 않은 작업은
공개 파일에 넣지 않았고, 어떤 작업을 뺐는지는 사전 등록 문서에 표시했다고
밝힌다.
Codex에 대한 짝 실험은 아직 없다.

Insight로 무엇이 나가는지는 Insight 소개 페이지가 적는다.
`~/.context-mode/platform.json`에 Insight 키를 넣어야 전송이 시작되며,
보내는 것은 이벤트마다 종류, 도구 이름, 파일 경로, 명령 종류, 종료 코드, 시각,
프로젝트 이름과 본문 앞 200자이고,
여기에는 각 프롬프트의 앞부분이 가린 뒤 포함된다.
저장소의 `hooks/platform-bridge.mjs`도 이 설정 파일이 없으면 전송 루프가
돌지 않고, `ctxm_`로 시작하는 키와 플랫폼 주소가 있을 때만 보내며 필드를 200자로
자른다.

## 분석

### 컨텍스트 소비 문제의 구조적 접근

토큰 절약 도구들은 흔히 “압축”에 집중하지만, Context Mode는 애초에
데이터가 컨텍스트에 들어오지 않도록 막는 방향을 택한다.
샌드박스 실행이 핵심인 이유는 여기에 있다.
원시 데이터를 요약하거나 자르는 것보다 처음부터 컨텍스트 진입을 차단하는 것이
근본적으로 더 많은 공간을 확보한다.

### 프롬프트 캐시는 깨지지 않는다던 답의 이후

HN에서 esafak은 이 방식이 캐시를 깬다면 작은 것을 아끼고 큰 것을 잃는 셈이라고
물었다.
캐시된 전체 질의는 정보가 많고 값이 싸다는 것이다[^esafak].
저자는 원시 데이터가 대화 이력에 들어가지 않으니 무효화할 것이 없고,
더 작은 메시지를 덧붙일 뿐이라 캐시가 유지된다고 답했다[^mksglu-cache].
플러그인에 관해서는 맞는 설명이다.
플러그인은 이미 보낸 메시지를 고치지 않고 앞으로 들어갈 출력만 줄인다.

그런데 요청 경로 전체를 다루는 게이트웨이로 넘어가자 같은 질문이 정면으로
돌아왔다.
2026년 10월 9일자 블로그 글은 Opus 5.5에서 캐시 쓰기가 읽기의 40배 값이라
캐시를 깨는 변경은 아끼는 것보다 더 쓸 수 있다고 설명한다.
도구 정의 60개를 처음에 보내지 않고 검색하게 했더니 프롬프트 토큰이 39% 줄었는데
비용은 149.6% 올랐고, 그래서 도구를 빼지 않고 긴 설명만 매 턴 같은 바이트로
잘라 내는 방식을 택했다는 것이다.
2월의 답과 10월의 글을 겹쳐 보면,
컨텍스트 절약을 바이트로 재던 시기에는 보이지 않던 캐시가 달러로
재기 시작하자 설계의 일차 제약이 되었다(해석).

### FTS5와 BM25 조합의 실용성

LLM이 검색 레이어로 활용할 수 있는 SQLite FTS5는 외부 벡터 DB 없이
키워드 기반 검색을 구현한다.
BM25는 TF-IDF보다 문서 길이 정규화가 우수해 짧은 청크와 긴 청크가 혼재할 때
더 공정한 랭킹을 제공한다.
에이전트 실행 환경에서 외부 의존성을 최소화하는 설계 원칙과 일치한다.

### 세션 압축 문제에 대한 현실적 해결책

Claude Code의 `/compact` 기능이나 자동 압축은 현재 많은 에이전트 워크플로에서
“작업 맥락 소실”을 야기하는 실질적 문제다.
Context Mode의 SQLite 기반 스냅샷은 이 문제를 모델 수준이 아닌 인프라 수준에서
우회한다.
실제 효용은 세션 지속 시간이 30분에서 3시간으로 늘어난다는 벤치마크에서
드러난다.

### 출력 압축을 철회한 것이 이 프로젝트에서 가장 중요한 설계 변경이다

이전 판의 네 번째 전략은 출력 압축이었고 조사와 수식어와 인사말을
제거해 출력 토큰을 65~75% 절약한다고 내걸었다.
지금 같은 자리에는 문체를 강제하지 않는다는 정반대 원칙이 들어가 있고,
근거로 공격적인 간결성 프롬프트가 코딩과 추론 벤치마크를 떨어뜨린다는 보고를
인용한다.

이 철회가 중요한 이유는 두 전략이 서로 다른 것을 건드리기 때문이다.
샌드박스와 색인은 모델에게 무엇을 보여 줄지를 정하는 입력 쪽 개입이고,
문체 지시는 모델이 어떻게 생각할지를 건드리는 출력 쪽 개입이다.
출력 토큰은 대개 자기회귀적 추론의 흔적이기도 하므로 그것을 줄이라고 지시하면
절약되는 것은 토큰이지만 함께 줄어드는 것은 사고 과정이다.
곧 이 프로젝트는 토큰 절약이라는 같은 목표 아래 묶여 있던 두 개입 중 하나가
사실은 성능세였다는 것을 인정하고 걷어낸 셈이다.

그리고 이 변경은 이 부류 도구를 평가하는 기준을 하나 만들어 준다.
컨텍스트 절약을 내세우는 도구가 모델의 출력 형식까지 지시하고 있다면 그 부분은
절약이 아니라 품질 저하일 가능성이 높으며,
절약량 수치는 그 대가를 반영하지 않는다.
남은 세 전략은 모두 모델이 보는 것을 바꿀 뿐 모델이 하는 말을 바꾸지 않는다는
점에서 같은 층위에 있고, 그 정렬이 이번 판에서야 맞춰졌다.

### 진짜 98% 절약인가

[GeekNews 댓글](https://news.hada.io/topic?id=29106)에서 recast7838과
shakespeares는 “실질적으로 효과적일지 모르겠다”,
“한두 번 더 쓰면 토큰을 더 쓰지 않을까”라고 의문을 제기했다.
정당한 우려다.
`ctx_execute`로 도구를 호출하는 행위 자체가 추가 토큰을 소비하고,
SQLite 조회 결과를 컨텍스트에 주입할 때도 비용이 발생한다.
“315 KB → 5.4 KB”는 Playwright 스냅샷 전체를 직접 주입할 때와의 비교로,
에이전트가 항상 그런 원시 출력을 컨텍스트에 쏟아붓지는 않는다.
워크로드에 따라 절약 효과가 크게 달라질 수 있다.

Hacker News 토론에서 같은 의문이 더 정확한 형태로 제기됐고, 저자가 직접 답했다.

있느냐고 묻자[^nharada], 저자 mksglu는 이론대로 성립한다고 하면서도
답변 품질에 대한 정식 벤치마크는 아직 돌리지 않았고 주로 토큰 절약량을 재는
데 집중했다고 인정한다.

### 추출 스크립트가 틀리면 데이터가 사라진다

이 설계의 전제는 모델이 필요한 것을 정확히 뽑아내는 코드를 미리 쓸 수 있다는
것이다.
HN에서 hereme888이 이 전제를 정면으로 친다.
훅이 지나치게 공격적이라 `curl`과 `wget`과 WebFetch를 전부 막고 샌드박스로
몰아넣는데, 56 KB 스냅샷에는 좋지만 200바이트를 반환하는 헬스 체크 호출에는
아니라는 것이다.
그리고 153개 커밋을 107바이트로 줄인다는 것은 모델이 데이터를
보기 전에 완벽한 추출 스크립트를 써야 한다는 뜻이며,
특정 커밋 메시지가 필요했는데 `git log --oneline | wc -l`을 썼다면 그 정보는
사라진다고 적는다.
벤치마크는 모델이 언제나 올바른 요약 코드를 쓴다고 가정하지만 실제로는
그렇지 않다는 것이다[^hereme888].

startages도 같은 방향을 짚는다.
정확도를 희생하며 불완전한 데이터나 에이전트가 쓴 나쁜 추출 로직에서 환각이
늘어날 위험이 있고, 결국 이 MCP 전체가 Claude가 좋은 추출 스크립트를
쓸 만큼 똑똑하고 동시에 좋은 검색 질의를 만들 만큼 똑똑하다는 것을 전제한다는
것이다.
정보 보존이 실제 경험상 진짜 문제라고 덧붙인다[^startages].

저자의 반론은 아무것도 버려지지 않는다는 것이다.
전체 출력이 검색 가능한 FTS5 색인에 남아 있으므로 모델이 요약에서 놓친 세부가
필요하다고 깨달으면 검색하면 되고,
그래서 이것은 무엇이 중요한지 미리 정하는 방식이 아니라 지금은 요약을 받고
세부는 나중에 찾아오는 방식이라는 것이다[^mksglu-fts].
이 반론은 절반만 유효하다.
`ctx_execute`의 stdout은 색인되지 않고 사라지며,
색인되는 것은 `ctx_index`와 `ctx_fetch_and_index`가 다룬 콘텐츠와 5 KB를 넘고
`intent`가 주어진 경우의 출력이다.
hereme888이 든 예는 정확히 전자,
곧 모델이 직접 짠 스크립트의 출력이며 그 경로에는 되돌아갈 색인이 없다.

게다가 `ctx_search`에 걸린 점진적 제동이 이 반론을 더 약화시킨다.
검색으로 돌아와 세부를 찾는 것이 설계의 안전망인데,
그 안전망이 4회부터 결과를 줄이고 9회부터는 차단된다.
탐색이 많이 필요한 작업일수록 검색 횟수가 늘어나고,
검색 횟수가 늘어날수록 안전망이 좁아지는 구조다.
곧 이 도구는 잘 모르는 데이터를 다룰 때 가장 필요하지만 바로 그때 가장 제약이
세다.

### 지식 베이스가 어휘 검색만으로 도구 출력을 감당하는지가 미검증이다

이번 판은 검색 층이 눈에 띄게 정교해졌다.
Porter 어근 색인과 트라이그램 부분 문자열 검색을 병렬로
돌려 Reciprocal Rank Fusion으로 병합하고, 다중 용어 질의에는 근접 재랭킹을 걸며,
Levenshtein 거리로 오타를 고치고,
잘라내기 대신 질의어 주변 창을 뽑는 똑똑한 스니펫을 쓴다.
이전의 폭포식 대체, 곧 Porter가 아무것도 못 찾을 때만 트라이그램을 쓰던 방식을
대체한 것이다.

그런데 두 전략 모두 어휘 검색이다.
HN에서 blakec가 이 지점을 짚는다.
FTS5 색인 접근 자체는 옳지만 순수 BM25는 도구 출력에서 성능이 떨어지는데,
도구 출력이 JSON과 표와 설정 같은 구조화 데이터와 주석과 오류 메시지와
독스트링 같은 자연어가 섞인 것이라 구조화된 절반에서 키워드 매칭이 무너진다는
것이다.
자기는 15,800개 파일의 Obsidian 저장소를 색인하며 Model2Vec의 256차원 임베딩과
`sqlite-vec` 벡터 검색과 FTS5의 BM25를 RRF로 묶은 하이브리드 검색기를 만들었고,
그래야 식별자와 함수 이름에는 BM25의 정확 매칭이,
설명과 오류 맥락에는 벡터 검색의 의미 매칭이 함께 걸린다고 적는다[^blakec].

이 지적은 이 프로젝트가 이미 RRF를 도입했다는 사실과 충돌하지 않는다.
Context Mode의 RRF는 어근과 트라이그램이라는 두 어휘 전략을 합치는 것이고,
blakec가 말하는 RRF는 어휘와 의미라는 두 축을 합치는 것이다.
전자는 오타와 부분 문자열 문제를 풀고 후자는 표현이 다른 같은 개념 문제를 푼다.
그리고 세션 이벤트 색인처럼 사용자의 자연어 프롬프트와 도구 로그가 뒤섞이는
자료에서는 후자가 필요한 쪽에 가깝다.

thecopy가 덧붙인 실무 제약도 함께 볼 만하다.
많은 도구가 구조화된 응답을 돌려주는데 그것이 손대지 않은 채로 남는 것이 이
접근의 큰 주름이고, 이 프로젝트의 해법은 `execute` 메서드이지만 자기가 만드는
MCP 게이트웨이에는 그런 샌드박스 실행이 아직 없다는 것이다[^thecopy].
곧 샌드박스가 가능한 환경에서만 성립하는 해법이며,
MCP 생태계의 상당 부분은 그 조건 밖에 있다.

## 인사이트

### 컨텍스트 윈도우 경쟁의 역설

모델 제공사들은 컨텍스트 윈도우를 지속적으로 확장하고 있다.
그러나 Context Mode 같은 프로젝트가 존재한다는 것은 이 경쟁의 역설을 드러낸다.
컨텍스트가 클수록 유용하지만, 클수록 비용이 높고 추론 속도가 느리다.
“가능한 모든 것을 컨텍스트에 넣어라”는 naive한 접근은 실제 에이전트 워크플로에서
경제적으로 지속 불가능하다.

컨텍스트 최적화는 모델 성능 최적화와 별개의 엔지니어링 문제가 되고 있다.
하드웨어 세계에서 CPU가 빨라져도 캐시 계층 설계가 여전히 중요한 것처럼,
모델 컨텍스트가 커져도 무엇을 언제 컨텍스트에 넣을지 설계하는 일은
별도의 전문 영역이 된다.

이 최적화의 전문화는 하네스 엔지니어링이 독립적인 기술 스택으로 성장하는 한
신호다.
Context Mode는 그 스택에서 “컨텍스트 관리” 레이어를 담당하는
첫 세대 도구 중 하나다.

### 에이전트 인프라의 로컬 우선 원칙

Context Mode가 “아무것도 머신을 벗어나지 않는다”를 설계 원칙으로 명시한 것은
주목할 만하다.
AI 에이전트 시장에서 현재 지배적인 흐름은 클라우드 기반 오케스트레이션이다.
에이전트 실행 로그, 기억, 세션 상태를 클라우드에 저장하고 분석하는 서비스들이
등장하고 있다.

로컬 SQLite 기반 접근은 이 흐름에 대한 의식적인 대안이다.
기업 보안 요구사항, 개인정보 민감 워크로드, 네트워크 격리 환경에서
클라우드 기반 에이전트 인프라는 현실적으로 채택하기 어렵다.
Context Mode의 “로컬 우선” 설계는 이 시장 세그먼트를 겨냥한다.

장기적으로 에이전트 인프라는 클라우드와 로컬 양 극단에서 발전하고,
그 사이에서 하이브리드 아키텍처가 표준이 될 것이다.

그런데 이번 판에서 그 원칙에 균열이 생겼다.
README의 프라이버시 절은 여전히 아무것도 머신을 벗어나지 않으며 텔레메트리도
클라우드 동기화도 사용 추적도 계정도 없다고 적고,
이것이 빠진 기능이 아니라 의도적인 아키텍처 선택이며 컨텍스트 최적화는
좌석당 구독료를 받는 대시보드 뒤가 아니라 원천에서 일어나야 한다고 선언한다.
그런데 같은 README의 도구 목록에 `ctx_insight`가 있고,
그것은 `context-mode.com/insight`의 호스팅 대시보드를 여는 명령이며
AI 지원 엔지니어링 팀을 위한 조직 분석이라고 소개된다.

대시보드에 무엇이 어떻게 올라가는지는 README에 없다.
그러니 이것이 원칙의 위반인지 아닌지는 알 수 없고, 알 수 없다는 것이 문제다.
로컬 우선을 철학으로 내걸고 그것에서 모든 설계 결정이 따라 나온다고 적은 문서가
호스팅 서비스를 도구 목록에 넣으면서 데이터 흐름을 서술하지 않는 것은,
앞서 지적한 벤치마크 공백과 같은 종류의 공백이다.
주장은 강하고 확인 경로는 없다.

이 어긋남을 수익 모델의 관점에서 보면 오히려 자연스럽다.
ELv2로 관리형 서비스 재판매를 막아 둔 프로젝트가 자기 관리형 서비스를
하나 가지고 있고, 그것이 조직 단위 분석이다.
곧 무료로 배포되는 것은 개인의 컨텍스트 절약 도구이고 돈이 붙는 자리는 조직의
사용 현황 가시성이며, 이 배치는 개발자 도구에서 반복해 나타난 형태다.
문제는 그 배치 자체가 아니라 프라이버시를 철학으로 내건 문서가 그 배치를
설명하지 않는다는 데 있다.

2026년 10월 11일 기준으로 보면 이 공백 가운데 Insight 부분은 저장소 밖에서
메워졌다.
홈페이지의 Insight 페이지가 키를 넣어야 전송이 시작된다는 것과 보내는 필드와
프롬프트 앞부분 200자를 밝히고 전송 코드 파일까지 링크하며,
실제 코드도 설정 파일이 없으면 보내지 않는다.
Engine 페이지도 코드와 세션은 기계에 남는다면서 Insight를 연결하지 않는 한이라는
단서를 붙인다.
그러나 README의 프라이버시 절은 그대로 아무것도 머신을 벗어나지 않는다고 적고
있어, README만 읽는 사용자에게는 여전히 같은 공백이 남는다.

더 큰 변화는 수익 모델 쪽이다.
위에서 돈이 붙는 자리를 조직의 사용 현황 가시성이라고 보았는데,
지금 회사가 주력으로 파는 것은 모든 모델 요청이 지나가는 호스팅 게이트웨이다.
README가 컨텍스트 최적화는 좌석당 구독료를 받는 대시보드 뒤가 아니라 원천에서
일어나야 한다고 선언한 바로 그 자리에,
요청 수로 과금하는 클라우드 프록시가 들어선 셈이다.
게이트웨이 쪽은 접는 위치를 원천에서 경로로 옮김으로써 플러그인으로는
할 수 없던 일, 곧 이미 보낸 이력을 보관소로 빼고 색인만 남기는 Recall 같은
기능을 얻었다.
이것은 앞서 이 문서가 다음 축이라고 짚은 제거 시점의 관리와 같은 방향이다(해석).
대신 그 대가로 프롬프트와 도구 출력 전체가 제3자 클라우드를 지나간다.
로컬 우선과 원천에서의 최적화라는 두 원칙 중 후자를 위해 전자를 내려놓은
선택이며, 같은 이름 아래 두 제품이 정반대의 프라이버시 전제를 갖게 되었다는 점은
사용자가 구분해서 봐야 한다.

### 훅 기반 에이전트 인프라의 가능성

Context Mode의 세션 지속성은 다섯 개 훅이 없으면 구현할 수 없다.
Claude Code의 훅 시스템(PreToolUse, PostToolUse, PreCompact, SessionStart 등)은
에이전트 행동을 모델 외부에서 제어할 수 있는 강력한 확장점이다.

훅 기반 인프라의 핵심 가치는 “모델을 수정하지 않고 동작을 변경한다”는 것이다.
모델 파인튜닝이나 시스템 프롬프트 수정 없이도 에이전트의 컨텍스트 관리,
상태 저장, 보안 정책을 외부에서 주입할 수 있다.
이 패턴은 소프트웨어 공학의 미들웨어나 관점 지향 프로그래밍(AOP)과 유사하다.

Context Mode는 이 훅 시스템을 최대한 활용하는 예시를 통해,
에이전트 플랫폼이 훅 확장점을 얼마나 풍부하게 제공하는가가
생태계 경쟁력의 핵심 척도임을 보여준다.

다만 17개 플랫폼 호환표를 자세히 보면 이 확장점이 표준이 아니라는 사실이
드러난다.
같은 이름의 훅이 플랫폼마다 다른 것을 뜻한다.
Gemini CLI에서는 `BeforeTool`과 `AfterTool`과 `PreCompress`이고,
Copilot CLI에서는 낙타 표기의 `preToolUse`와 `userPromptSubmitted`와
`agentStop`이며, OpenCode와 KiloCode에서는 훅이
아니라 인프로세스 함수인 `tool.execute.before`와
`experimental.chat.system.transform`이다.
Cursor는 `sessionStart`를 문서화해 놓고도 검증기가 거부해 세션 복원이 안 되고,
Codex CLI는 `permissionDecision: "deny"`만 지원해 인자 수정이 불가능하며,
Antigravity IDE와 Zed는 훅 자체가 없다.

곧 이 프로젝트가 17개 플랫폼을 지원한다는 말의 실제 내용은 17개의 서로
다른 어댑터를 쓰고 유지한다는 뜻이다.
표에서 같은 기능 행이 Yes와 Plugin과 Bounded와 대시로 갈리는 것이 그 비용의
표시값이며, 이전 갱신 시점의 열린 이슈 146개 중 상당수가 여기서 나올 것이라고
짐작하기 어렵지 않다.
훅이 미들웨어 확장점이라는 관찰은 옳지만,
미들웨어가 성립하려면 인터페이스가 하나여야 한다는 조건이 아직 충족되지 않았다.

### 컨텍스트 관리의 다음 축은 추가 시점이 아니라 제거 시점이다

이 프로젝트가 다루는 것은 무엇을 컨텍스트에 넣을지다.
샌드박스는 넣지 않고, 색인은 나중에 넣고, 스냅샷은 압축 후에 다시 넣는다.
전부 추가 시점의 결정이며, 이 축에서는 이미 상당히 정교하다.

HN 토론에서 반복해 나온 다른 축은 제거다.
nr378은 컨텍스트 관리에 아직 손쉬운 열매가 많다며 되돌리기를 유망한 방향으로
든다.
모델이 몇 번의 시도 끝에 옳은 일을 해내면 실패한 시도들을 컨텍스트에서
잘라 내자는 것이다[^nr378].
elephanlemon은 이것을 더 밀고 나간다.
세션 중간에 디버깅에 시간을 쓴 뒤 버그를 고쳤다면 그 과정 전체를 컨텍스트에서
지우고 디버깅 전 상태로 이어 갈 수 있어야 하는데,
지금은 IDE에 따라 수동으로도 꽤 성가시고 그 뒤에 다른 작업을 했다면
잘라 낼 방법이 아예 없다는 것이다.
로그를 많이 뱉는 도구를 쓴 경우 그 로그가 한두 프롬프트 뒤에 자동으로
정리되어야 하며, 컨텍스트는 끝에서만 붙이고 뗄 수 있는 스택이 아니라 자유롭게
조작 가능한 것으로 생각해야 한다고 적는다[^elephanlemon].

이 두 축은 서로 배타적이지 않고 오히려 서로를 필요로 한다.
추가 시점 최적화만 하면 세션이 길어질수록 유효하지만 이미 낡은 정보가 컨텍스트에
계속 남는다.
Context Mode의 벤치마크가 자랑하는 세션 30분에서 3시간이라는 연장은 그 문제를
세 배로 키운다는 뜻이기도 하다.
3시간 전에 읽은 파일의 내용, 이미 해결된 오류,
폐기된 접근이 전부 컨텍스트 앞쪽에 남아 있고,
압축이 걸리기 전까지는 그것을 걷어낼 장치가 없다.

그리고 이 축에서 이 프로젝트는 이미 필요한 재료를 갖고 있다.
23개 범주로 이벤트를 분류하면서 해결된 오류와 거부된 접근과 반복 루프를
이미 식별하고 있기 때문이다.
어떤 오류가 언제 고쳐졌는지 아는 시스템은 원리적으로 그 오류와
관련된 대화 구간이 언제부터 쓸모없어졌는지도 안다.
지금 그 정보는 압축 후 복원용 스냅샷을 만드는 데만 쓰이는데,
같은 정보로 압축 전에 무엇을 먼저 버릴지 정할 수 있다.
곧 이 프로젝트의 자연스러운 다음 판본은 새 기능이 아니라 이미 수집한 신호를 반대
방향으로 쓰는 것이다.

### 도구 출력의 표현 형식 자체가 다음 경쟁 지점이 된다

이 프로젝트의 전제는 도구 출력이 텍스트라는 것이다.
그래서 해법이 텍스트를 어딘가에 숨기고 텍스트로 검색하는 형태를 띤다.
샌드박스도 stdout을 다루고 색인도 마크다운 청크를 다룬다.

HN에서 lmeyerov가 다른 층위의 답을 제시한다.
데이터베이스와 로그 시스템을 다루는 자기 제품에서는 질의 결과를 LLM에 돌려주는
대신 메모리 내 parquet에 가까운 데이터프레임을 만들고,
토큰 최적화된 요약 뷰와 함께 “…외 100만 행” 같은 힌트를 붙여 응답에 넣는다는
것이다.
그러면 LLM이 로그에 빠지지 않고 데이터프레임을 더 똑똑하게
파고들지 결정할 수 있으며, 운영 시스템에 반복 질의 압박이 줄고 에이전트 추론이
빠르고 싸지며 대화형 데이터 뷰가 담긴 노트북이 남는다.
그리고 MCP 프로토콜이 이론상 이진 같은 대체 콘텐츠 타입을 지원한다는 점을 들어,
MCP 세계의 데이터 쪽을 텍스트와 JSON에서 Apache Arrow로 옮기고 에이전트 하네스를
그것에 맞게 똑똑하게 만드는 방향에 관심이 간다고 적는다[^lmeyerov].

이 관점이 Context Mode의 접근을 다시 보게 만든다.
샌드박스가 하는 일은 결국 큰 텍스트를 작은 텍스트로 바꾸는 것이고,
그 변환을 매번 모델이 즉석에서 쓴 스크립트에 맡긴다.
앞서 hereme888과 startages가 지적한 취약함이 전부 그 즉석 변환에서 나온다.
반면 도구가 애초에 구조화된 핸들을 돌려주고 모델이 그 핸들을 질의하는 구조라면
변환 코드를 쓸 필요가 없고, 따라서 잘못 쓸 일도 없다.

여기서 나오는 이차 효과가 있다.
Context Mode 같은 도구가 널리 쓰일수록 그것이 해결하는 문제,
곧 도구가 원시 데이터를 쏟아붓는 관행이 정상으로 굳는다는 것이다.
MCP 서버를 만드는 쪽에서 보면 출력을 다듬을 유인이 줄어든다.
어차피 클라이언트 쪽에서 걸러지기 때문이다.
저자 자신도 이 문제를 알고 있어서,
사람들이 작업마다 MCP 서버 목록을 손으로 고르지 않고 5~6개를 설치해 80개 도구를
기본으로 띄운다는 현실을 인정하며 이 도구는 도구 정의 부풀림이라는
입력 쪽 문제는 풀지 않고 출력 쪽만 다룬다고 답한다[^mksglu-tools].
곧 이 도구는 생태계의 나쁜 기본값을 견딜 만하게 만들어 주는 완충재이며,
완충재가 잘 작동할수록 기본값을 고칠 압력은 줄어든다.
