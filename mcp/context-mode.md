# Context Mode

<https://context-mode.com/>

<https://github.com/mksglu/context-mode>

HN 토론: <https://news.ycombinator.com/item?id=47193064> (570점, 1위)

## 소개

Context Mode는 AI 코딩 에이전트의 컨텍스트 윈도우 소비를 줄이는 MCP 서버다.
MCP 도구 호출 시 원시 데이터가 대화 컨텍스트에 직접 쌓이는 구조적 문제를
샌드박스 실행, 세션 지속성, 코드로 생각하기라는 세 가지 전략으로 해결하고,
네 번째 항목으로는 하지 않는 일 하나를 명시한다.
프로젝트가 제시하는 대표 수치는 “315 KB → 5.4 KB, 98% 절약”이다.

README가 여는 문제 서술은 구체적이다.
Playwright 스냅샷 하나가 56 KB, GitHub 이슈 20개가 59 KB, 접근 로그 하나가 45 KB이고,
30분이 지나면 컨텍스트의 40%가 사라진다는 것이다.
그리고 에이전트가 공간을 확보하려고 대화를 압축하면 자기가 어떤 파일을 고치고 있었는지,
어떤 작업이 진행 중인지, 사용자가 마지막에 무엇을 요청했는지를 잊는다.
저장소 설명은 이것을 “17개 플랫폼에 걸쳐 MCP와 훅으로 라우팅을 강제한다”고 요약하며,
여기에 OpenClaw 게이트웨이 통합이 별도로 붙는다.

저장소는 2026년 2월 23일에 만들어졌고 이 문서 갱신 시점 기준 GitHub 스타 19,813개,
포크 1,425개, 열린 이슈 146개다.
언어는 TypeScript이고 라이선스는 Elastic License 2.0이다.
Hacker News에서 570점으로 1위에 올랐던 이력을 README 배지로 표시한다.

## 핵심 전략

### 샌드박스 실행

`ctx_execute`를 비롯한 도구들이 코드를 격리된 서브프로세스에서 실행하고
stdout만 컨텍스트에 주입한다.
Playwright 스냅샷(56 KB), GitHub API 응답(59 KB), 접근 로그(45 KB) 같은
원시 데이터는 대화에 노출되지 않는다.

12개 언어 런타임을 제공한다.
JavaScript, TypeScript, Python, Shell, Ruby, Go, Rust, PHP, Perl, R, Elixir, C#이며
JS/TS는 Bun이 감지되면 3~5배 빠르게 실행된다.
`gh`, `aws`, `gcloud`, `kubectl`, `docker` 같은 인증된 CLI는 자격 증명 통과 방식으로
환경 변수와 설정 경로를 물려받되 대화에는 노출되지 않는다.
출력이 5 KB를 넘고 `intent`가 주어지면 의도 기반 필터링으로 전환해,
전체 출력을 지식 베이스에 색인한 뒤 의도에 맞는 구간만 돌려준다.

### 세션 지속성

대화가 압축(compaction)되면 모델은 작업 중이던 파일, 열린 태스크, 미해결 오류를
잃는다.
Context Mode는 파일 수정, Git 작업, 태스크 상태, 오류, 사용자 결정을 SQLite에
기록하는데, 압축 시 그 데이터를 컨텍스트에 도로 쏟아붓지 않는다.
이벤트를 FTS5에 색인해 두고 BM25 검색으로 관련된 것만 꺼내 오는 방식이다.
`PreCompact`가 우선순위 계층으로 2 KB 이하의 XML 스냅샷을 만들어 `session_resume`
테이블에 저장하고, `SessionStart`가 그것을 꺼내 15개 범주의 세션 가이드를 구성해
`<session_knowledge>` 지시문으로 주입한다.
2 KB 예산이 빠듯하면 의도나 MCP 도구 호출 수 같은 낮은 우선순위 항목부터 버리고
활성 파일과 태스크와 규칙과 결정은 언제나 보존한다.
포착 범주는 23개이며 파일과 태스크와 계획과 규칙과 사용자 프롬프트가 최상위 우선순위,
Git과 오류와 오류 해결 쌍과 제약과 블로커와 거부된 접근과 환경과 반복 루프가
그다음이다.
다섯 개 훅(PreToolUse, PostToolUse, UserPromptSubmit, PreCompact, SessionStart)이
협력해 상태를 보존하며, Stop을 포함하면 여섯 개다.
`--continue`를 쓰지 않으면 이전 세션 데이터는 즉시 삭제된다.
새 세션은 백지에서 시작한다는 원칙이다.

### 코드로 생각하기

LLM이 50개 파일을 읽어 함수 수를 세는 대신, 분석 스크립트를 작성해 결과만
받는다.
10번의 도구 호출을 1번으로 줄이고 컨텍스트 사용량을 약 100배 절약한다.
README는 이것을 17개 클라이언트 전체에 걸친 필수 패러다임이라고 표현하며,
LLM을 데이터 처리기로 취급하지 말고 코드 생성기로 취급하라고 적는다.

```js
// Before: 47 × Read() = 700 KB.  After: 1 × ctx_execute() = 3.6 KB.
ctx_execute("javascript", `
  const files = fs.readdirSync('src').filter(f => f.endsWith('.ts'));
  files.forEach(f => console.log(f + ': ' + fs.readFileSync('src/'+f,'utf8').split('\n').length + ' lines'));
`);
```

### 문체를 강제하지 않는다

네 번째 항목은 기능이 아니라 하지 않기로 한 일이다.
Context Mode는 원시 데이터를 컨텍스트 밖에 두되 모델이 최종 답변을 어떻게 쓰는지는
지시하지 않는다는 것이다.
간결함이나 완결성이나 서식은 모델의 판단이거나 사용자가 자기 `CLAUDE.md`와
`AGENTS.md`로 정할 몫이라고 적는다.
근거로는 공격적인 간결성 프롬프트가 코딩과 추론 벤치마크 성능을 떨어뜨린다는
Moonshot AI의 `kimi-k2.5` 관련 보고를 든다.
라우팅 블록은 데이터가 어디로 가는지에 집중하며 모델이 어떻게 말하는지는 다루지
않는다는 것이다.

이 항목은 이전 판에서 뒤집힌 것이다.
과거 README는 응답에서 조사와 불필요한 수식어와 인사말을 제거해 출력 토큰을
65~75% 절약한다는 출력 압축을 네 번째 전략으로 내걸었다.
지금은 같은 자리에 정반대 원칙이 들어가 있다.

## 도구 목록

| 도구                  | 기능                                      | 절약 효과      |
| --------------------- | ----------------------------------------- | -------------- |
| `ctx_execute`         | 12개 언어로 코드 실행, stdout만 수집      | 56 KB → 299 B  |
| `ctx_batch_execute`   | 명령/쿼리 다중 실행                       | 986 KB → 62 KB |
| `ctx_execute_file`    | 파일을 샌드박스에서 처리                  | 45 KB → 155 B  |
| `ctx_index`           | 마크다운을 청크 분할 후 FTS5에 색인       | 60 KB → 40 B   |
| `ctx_search`          | BM25 랭킹으로 색인 내용 검색              | 온디맨드 조회  |
| `ctx_fetch_and_index` | URL 가져와 마크다운 변환 후 24시간 캐시   | 60 KB → 40 B   |
| `ctx_stats`           | 컨텍스트 절약량과 세션 지표 표시          | —              |
| `ctx_doctor`          | 설치, 런타임, FTS5 진단                   | —              |
| `ctx_upgrade`         | GitHub에서 최신 버전으로 업데이트         | —              |
| `ctx_purge`           | 색인된 콘텐츠 전체 삭제                   | —              |
| `ctx_insight`         | 호스팅 Insight 대시보드를 브라우저로 열기 | —              |

여섯 개 샌드박스 도구와 다섯 개 메타 도구를 합해 11개다.
`ctx_batch_execute`는 여러 명령과 여러 질의를 한 번의 호출로 묶고 I/O 위주 배치에서는
`concurrency: 1-8`을 선택적으로 쓴다.
`ctx_fetch_and_index`는 기본 24시간 TTL 캐시를 쓰며 호출마다 `ttl`을 덮어쓰거나
`ttl: 0` 또는 `force: true`로 우회할 수 있고, 14일이 지난 콘텐츠 데이터베이스는
시작 시 정리된다.
`ctx_insight`는 다른 도구들과 성격이 다르다.
`context-mode.com/insight`의 호스팅 대시보드를 브라우저로 여는 것이며,
README는 이것을 AI 지원 엔지니어링 팀을 위한 조직 분석이라고 소개한다.

`ctx_search`에는 점진적 제동이 걸려 있다.
1~3회 호출은 질의당 결과 2건을 정상 반환하고, 4~8회는 1건으로 줄이며 경고를 붙이고,
9회부터는 차단하고 `ctx_batch_execute`로 유도한다.

## 지식 베이스 아키텍처

SQLite FTS5에 BM25 랭킹을 적용하고 Porter 어근 분석으로
“running”, “runs”, “ran”을 동일 어근으로 처리한다.
헤딩에는 5배 가중치를 부여한다.

검색은 Porter 어근 색인과 트라이그램 부분 문자열 검색 결과를
Reciprocal Rank Fusion으로 병합한다.
다중 용어 쿼리는 용어가 인접한 단락을 더 높게 평가하는 근접 재랭킹을 적용한다.
오타 보정도 내장되어 있다(“kuberntes” → “kubernetes”).

## 설치

Claude Code에서는 플러그인 마켓플레이스로 설치할 수 있다.

```bash
/plugin marketplace add mksglu/context-mode
/plugin install context-mode@context-mode
```

훅이 런타임에 자동 주입되고 프로젝트에 파일이 기록되지 않는다.
라우팅 지시 파일을 첫 세션 시작 시 프로젝트 디렉터리에 자동으로 쓰던 동작은
git 트리를 더럽힌다는 이유로 비활성화되었다.
Gemini CLI, VS Code Copilot 등은 설정 파일을 별도로 작성해야 한다.
훅을 지원하지 않는 Zed와 Antigravity IDE는 라우팅 파일을 한 번 수동으로 복사한다.

라우팅 강제 수단에 따라 절약 효과가 갈린다.
훅이 있는 플랫폼은 약 98% 절약, 지시 파일만 있는 플랫폼은 약 60% 절약으로 표시된다.
README는 훅 없이는 라우팅되지 않은 `curl` 하나나 Playwright 스냅샷 하나가 56 KB를
컨텍스트에 부어 한 세션치 절약을 통째로 날릴 수 있다고 적는다.

Claude Code용 상태 표시줄은 플러그인 매니페스트로 선언할 수 없어 `~/.claude/settings.json`을
한 번 직접 고쳐야 하며, 이번 세션 절약액과 누적 절약액과 효율 비율을 달러로 보여 준다.

## 분석

### 컨텍스트 소비 문제의 구조적 접근

토큰 절약 도구들은 흔히 “압축”에 집중하지만, Context Mode는 애초에
데이터가 컨텍스트에 들어오지 않도록 막는 방향을 택한다.
샌드박스 실행이 핵심인 이유는 여기에 있다.
원시 데이터를 요약하거나 자르는 것보다 처음부터 컨텍스트 진입을 차단하는 것이
근본적으로 더 많은 공간을 확보한다.

### FTS5와 BM25 조합의 실용성

LLM이 검색 레이어로 활용할 수 있는 SQLite FTS5는 외부 벡터 DB 없이
키워드 기반 검색을 구현한다.
BM25는 TF-IDF보다 문서 길이 정규화가 우수해 짧은 청크와 긴 청크가 혼재할 때
더 공정한 랭킹을 제공한다.
에이전트 실행 환경에서 외부 의존성을 최소화하는 설계 원칙과 일치한다.

### 세션 압축 문제에 대한 현실적 해결책

Claude Code의 `/compact` 기능이나 자동 압축은 현재 많은 에이전트 워크플로에서
“작업 맥락 소실”을 야기하는 실질적 문제다.
Context Mode의 SQLite 기반 스냅샷은 이 문제를 모델 수준이 아닌 인프라 수준에서
우회한다.
실제 효용은 세션 지속 시간이 30분에서 3시간으로 늘어난다는 벤치마크에서 드러난다.

### 출력 압축을 철회한 것이 이 프로젝트에서 가장 중요한 설계 변경이다

이전 판의 네 번째 전략은 출력 압축이었고 조사와 수식어와 인사말을 제거해 출력 토큰을
65~75% 절약한다고 내걸었다.
지금 같은 자리에는 문체를 강제하지 않는다는 정반대 원칙이 들어가 있고,
근거로 공격적인 간결성 프롬프트가 코딩과 추론 벤치마크를 떨어뜨린다는 보고를 인용한다.

이 철회가 중요한 이유는 두 전략이 서로 다른 것을 건드리기 때문이다.
샌드박스와 색인은 모델에게 무엇을 보여 줄지를 정하는 입력 쪽 개입이고,
문체 지시는 모델이 어떻게 생각할지를 건드리는 출력 쪽 개입이다.
출력 토큰은 대개 자기회귀적 추론의 흔적이기도 하므로 그것을 줄이라고 지시하면
절약되는 것은 토큰이지만 함께 줄어드는 것은 사고 과정이다.
곧 이 프로젝트는 토큰 절약이라는 같은 목표 아래 묶여 있던 두 개입 중 하나가
사실은 성능세였다는 것을 인정하고 걷어낸 셈이다.

그리고 이 변경은 이 부류 도구를 평가하는 기준을 하나 만들어 준다.
컨텍스트 절약을 내세우는 도구가 모델의 출력 형식까지 지시하고 있다면 그 부분은
절약이 아니라 품질 저하일 가능성이 높으며, 절약량 수치는 그 대가를 반영하지 않는다.
남은 세 전략은 모두 모델이 보는 것을 바꿀 뿐 모델이 하는 말을 바꾸지 않는다는 점에서
같은 층위에 있고, 그 정렬이 이번 판에서야 맞춰졌다.

## 비평

### 진짜 98% 절약인가

[GeekNews 댓글](https://news.hada.io/topic?id=29106)에서 recast7838과 shakespeares는
“실질적으로 효과적일지 모르겠다”, “한두 번 더 쓰면 토큰을 더 쓰지 않을까”라고
의문을 제기했다.
정당한 우려다.
`ctx_execute`로 도구를 호출하는 행위 자체가 추가 토큰을 소비하고,
SQLite 조회 결과를 컨텍스트에 주입할 때도 비용이 발생한다.
“315 KB → 5.4 KB”는 Playwright 스냅샷 전체를 직접 주입할 때와의 비교로,
에이전트가 항상 그런 원시 출력을 컨텍스트에 쏟아붓지는 않는다.
워크로드에 따라 절약 효과가 크게 달라질 수 있다.

Hacker News 토론에서 같은 의문이 더 정확한 형태로 제기됐고, 저자가 직접 답했다.
nharada가 질적으로는 성능 저하가 없었던 것 같은데 벤치마크나 평가로 검증한 적이 있느냐고
묻자[^nharada], 저자 mksglu는 이론대로 성립한다고 하면서도 답변 품질에 대한 정식
벤치마크는 아직 돌리지 않았고 주로 토큰 절약량을 재는 데 집중했다고 인정한다.
일화적으로 가장 큰 이득은 압축이 걸리기 전까지 세션이 더 오래 간다는 것이고
그래서 모델이 대화 이력을 온전히 유지해 맥락 소실로 인한 실수가 줄어든다는 것이다[^mksglu-bench].

clouedoc은 이 공백을 더 강하게 친다.
주장하는 98% 컨텍스트 절약은 컨텍스트 모드를 켰을 때와 껐을 때의 하네스 성능 벤치마크가
없으면 잡음이며, 이런 문제를 다루는 사람이 있는 것은 반갑지만 진지한 해법으로는 느껴지지
않는다는 것이다[^clouedoc].
같은 댓글에서 Bun이 JS/TS 실행을 3~5배 빠르게 한다는 문구를 두고, 병목은 JS 인터프리터가
아니라 LLM이므로 그 주장이 사실이어도 의미가 없다고 지적한다.

이 지적들이 겹쳐 드러내는 것은 이 프로젝트가 재는 것과 팔려는 것이 다르다는 사실이다.
벤치마크 표의 여덟 항목은 전부 바이트 수 비교이고, 팔려는 것은 에이전트가 일을 더 잘한다는
결과다.
둘을 잇는 다리가 세션이 오래 간다는 일화 하나뿐이며, 그 다리가 검증되기 전까지
98%라는 숫자는 절약률이지 개선률이 아니다.

### 추출 스크립트가 틀리면 데이터가 사라진다

이 설계의 전제는 모델이 필요한 것을 정확히 뽑아내는 코드를 미리 쓸 수 있다는 것이다.
HN에서 hereme888이 이 전제를 정면으로 친다.
훅이 지나치게 공격적이라 `curl`과 `wget`과 WebFetch를 전부 막고 샌드박스로 몰아넣는데,
56 KB 스냅샷에는 좋지만 200바이트를 반환하는 헬스 체크 호출에는 아니라는 것이다.
그리고 153개 커밋을 107바이트로 줄인다는 것은 모델이 데이터를 보기 전에 완벽한 추출
스크립트를 써야 한다는 뜻이며, 특정 커밋 메시지가 필요했는데
`git log --oneline | wc -l`을 썼다면 그 정보는 사라진다고 적는다.
벤치마크는 모델이 언제나 올바른 요약 코드를 쓴다고 가정하지만 실제로는 그렇지 않다는
것이다[^hereme888].

startages도 같은 방향을 짚는다.
정확도를 희생하며 불완전한 데이터나 에이전트가 쓴 나쁜 추출 로직에서 환각이 늘어날
위험이 있고, 결국 이 MCP 전체가 Claude가 좋은 추출 스크립트를 쓸 만큼 똑똑하고
동시에 좋은 검색 질의를 만들 만큼 똑똑하다는 것을 전제한다는 것이다.
정보 보존이 실제 경험상 진짜 문제라고 덧붙인다[^startages].

저자의 반론은 아무것도 버려지지 않는다는 것이다.
전체 출력이 검색 가능한 FTS5 색인에 남아 있으므로 모델이 요약에서 놓친 세부가 필요하다고
깨달으면 검색하면 되고, 그래서 이것은 무엇이 중요한지 미리 정하는 방식이 아니라
지금은 요약을 받고 세부는 나중에 찾아오는 방식이라는 것이다[^mksglu-fts].
이 반론은 절반만 유효하다.
`ctx_execute`의 stdout은 색인되지 않고 사라지며, 색인되는 것은 `ctx_index`와
`ctx_fetch_and_index`가 다룬 콘텐츠와 5 KB를 넘고 `intent`가 주어진 경우의 출력이다.
hereme888이 든 예는 정확히 전자, 곧 모델이 직접 짠 스크립트의 출력이며 그 경로에는
되돌아갈 색인이 없다.

게다가 `ctx_search`에 걸린 점진적 제동이 이 반론을 더 약화시킨다.
검색으로 돌아와 세부를 찾는 것이 설계의 안전망인데, 그 안전망이 4회부터 결과를 줄이고
9회부터는 차단된다.
탐색이 많이 필요한 작업일수록 검색 횟수가 늘어나고, 검색 횟수가 늘어날수록 안전망이
좁아지는 구조다.
곧 이 도구는 잘 모르는 데이터를 다룰 때 가장 필요하지만 바로 그때 가장 제약이 세다.

### 지식 베이스가 어휘 검색만으로 도구 출력을 감당하는지가 미검증이다

이번 판은 검색 층이 눈에 띄게 정교해졌다.
Porter 어근 색인과 트라이그램 부분 문자열 검색을 병렬로 돌려 Reciprocal Rank Fusion으로
병합하고, 다중 용어 질의에는 근접 재랭킹을 걸며, Levenshtein 거리로 오타를 고치고,
잘라내기 대신 질의어 주변 창을 뽑는 똑똑한 스니펫을 쓴다.
이전의 폭포식 대체, 곧 Porter가 아무것도 못 찾을 때만 트라이그램을 쓰던 방식을 대체한
것이다.

그런데 두 전략 모두 어휘 검색이다.
HN에서 blakec가 이 지점을 짚는다.
FTS5 색인 접근 자체는 옳지만 순수 BM25는 도구 출력에서 성능이 떨어지는데,
도구 출력이 JSON과 표와 설정 같은 구조화 데이터와 주석과 오류 메시지와 독스트링 같은
자연어가 섞인 것이라 구조화된 절반에서 키워드 매칭이 무너진다는 것이다.
자기는 15,800개 파일의 Obsidian 저장소를 색인하며 Model2Vec의 256차원 임베딩과
`sqlite-vec` 벡터 검색과 FTS5의 BM25를 RRF로 묶은 하이브리드 검색기를 만들었고,
그래야 식별자와 함수 이름에는 BM25의 정확 매칭이, 설명과 오류 맥락에는 벡터 검색의
의미 매칭이 함께 걸린다고 적는다[^blakec].

이 지적은 이 프로젝트가 이미 RRF를 도입했다는 사실과 충돌하지 않는다.
Context Mode의 RRF는 어근과 트라이그램이라는 두 어휘 전략을 합치는 것이고,
blakec가 말하는 RRF는 어휘와 의미라는 두 축을 합치는 것이다.
전자는 오타와 부분 문자열 문제를 풀고 후자는 표현이 다른 같은 개념 문제를 푼다.
그리고 세션 이벤트 색인처럼 사용자의 자연어 프롬프트와 도구 로그가 뒤섞이는 자료에서는
후자가 필요한 쪽에 가깝다.

thecopy가 덧붙인 실무 제약도 함께 볼 만하다.
많은 도구가 구조화된 응답을 돌려주는데 그것이 손대지 않은 채로 남는 것이 이 접근의
큰 주름이고, 이 프로젝트의 해법은 `execute` 메서드이지만 자기가 만드는 MCP 게이트웨이에는
그런 샌드박스 실행이 아직 없다는 것이다[^thecopy].
곧 샌드박스가 가능한 환경에서만 성립하는 해법이며, MCP 생태계의 상당 부분은 그 조건 밖에
있다.

## 인사이트

### 컨텍스트 윈도우 경쟁의 역설

모델 제공사들은 컨텍스트 윈도우를 지속적으로 확장하고 있다.
그러나 Context Mode 같은 프로젝트가 존재한다는 것은 이 경쟁의 역설을 드러낸다.
컨텍스트가 클수록 유용하지만, 클수록 비용이 높고 추론 속도가 느리다.
“가능한 모든 것을 컨텍스트에 넣어라”는 naive한 접근은 실제 에이전트 워크플로에서
경제적으로 지속 불가능하다.

컨텍스트 최적화는 모델 성능 최적화와 별개의 엔지니어링 문제가 되고 있다.
하드웨어 세계에서 CPU가 빨라져도 캐시 계층 설계가 여전히 중요한 것처럼,
모델 컨텍스트가 커져도 무엇을 언제 컨텍스트에 넣을지 설계하는 일은
별도의 전문 영역이 된다.

이 최적화의 전문화는 하네스 엔지니어링이 독립적인 기술 스택으로 성장하는 한
신호다.
Context Mode는 그 스택에서 “컨텍스트 관리” 레이어를 담당하는 첫 세대 도구 중 하나다.

### 에이전트 인프라의 로컬 우선 원칙

Context Mode가 “아무것도 머신을 벗어나지 않는다”를 설계 원칙으로 명시한 것은
주목할 만하다.
AI 에이전트 시장에서 현재 지배적인 흐름은 클라우드 기반 오케스트레이션이다.
에이전트 실행 로그, 기억, 세션 상태를 클라우드에 저장하고 분석하는 서비스들이
등장하고 있다.

로컬 SQLite 기반 접근은 이 흐름에 대한 의식적인 대안이다.
기업 보안 요구사항, 개인정보 민감 워크로드, 네트워크 격리 환경에서
클라우드 기반 에이전트 인프라는 현실적으로 채택하기 어렵다.
Context Mode의 “로컬 우선” 설계는 이 시장 세그먼트를 겨냥한다.

장기적으로 에이전트 인프라는 클라우드와 로컬 양 극단에서 발전하고,
그 사이에서 하이브리드 아키텍처가 표준이 될 것이다.

그런데 이번 판에서 그 원칙에 균열이 생겼다.
README의 프라이버시 절은 여전히 아무것도 머신을 벗어나지 않으며 텔레메트리도
클라우드 동기화도 사용 추적도 계정도 없다고 적고, 이것이 빠진 기능이 아니라 의도적인
아키텍처 선택이며 컨텍스트 최적화는 좌석당 구독료를 받는 대시보드 뒤가 아니라
원천에서 일어나야 한다고 선언한다.
그런데 같은 README의 도구 목록에 `ctx_insight`가 있고, 그것은
`context-mode.com/insight`의 호스팅 대시보드를 여는 명령이며 AI 지원 엔지니어링 팀을
위한 조직 분석이라고 소개된다.

대시보드에 무엇이 어떻게 올라가는지는 README에 없다.
그러니 이것이 원칙의 위반인지 아닌지는 알 수 없고, 알 수 없다는 것이 문제다.
로컬 우선을 철학으로 내걸고 그것에서 모든 설계 결정이 따라 나온다고 적은 문서가
호스팅 서비스를 도구 목록에 넣으면서 데이터 흐름을 서술하지 않는 것은,
앞서 지적한 벤치마크 공백과 같은 종류의 공백이다.
주장은 강하고 확인 경로는 없다.

이 어긋남을 수익 모델의 관점에서 보면 오히려 자연스럽다.
ELv2로 관리형 서비스 재판매를 막아 둔 프로젝트가 자기 관리형 서비스를 하나 가지고 있고,
그것이 조직 단위 분석이다.
곧 무료로 배포되는 것은 개인의 컨텍스트 절약 도구이고 돈이 붙는 자리는 조직의
사용 현황 가시성이며, 이 배치는 개발자 도구에서 반복해 나타난 형태다.
문제는 그 배치 자체가 아니라 프라이버시를 철학으로 내건 문서가 그 배치를 설명하지
않는다는 데 있다.

### 훅 기반 에이전트 인프라의 가능성

Context Mode의 세션 지속성은 다섯 개 훅이 없으면 구현할 수 없다.
Claude Code의 훅 시스템(PreToolUse, PostToolUse, PreCompact, SessionStart 등)은
에이전트 행동을 모델 외부에서 제어할 수 있는 강력한 확장점이다.

훅 기반 인프라의 핵심 가치는 “모델을 수정하지 않고 동작을 변경한다”는 것이다.
모델 파인튜닝이나 시스템 프롬프트 수정 없이도 에이전트의 컨텍스트 관리,
상태 저장, 보안 정책을 외부에서 주입할 수 있다.
이 패턴은 소프트웨어 공학의 미들웨어나 관점 지향 프로그래밍(AOP)과 유사하다.

Context Mode는 이 훅 시스템을 최대한 활용하는 예시를 통해,
에이전트 플랫폼이 훅 확장점을 얼마나 풍부하게 제공하는가가
생태계 경쟁력의 핵심 척도임을 보여준다.

다만 17개 플랫폼 호환표를 자세히 보면 이 확장점이 표준이 아니라는 사실이 드러난다.
같은 이름의 훅이 플랫폼마다 다른 것을 뜻한다.
Gemini CLI에서는 `BeforeTool`과 `AfterTool`과 `PreCompress`이고, Copilot CLI에서는
낙타 표기의 `preToolUse`와 `userPromptSubmitted`와 `agentStop`이며, OpenCode와
KiloCode에서는 훅이 아니라 인프로세스 함수인 `tool.execute.before`와
`experimental.chat.system.transform`이다.
Cursor는 `sessionStart`를 문서화해 놓고도 검증기가 거부해 세션 복원이 안 되고,
Codex CLI는 `permissionDecision: “deny”`만 지원해 인자 수정이 불가능하며,
Antigravity IDE와 Zed는 훅 자체가 없다.

곧 이 프로젝트가 17개 플랫폼을 지원한다는 말의 실제 내용은 17개의 서로 다른 어댑터를
쓰고 유지한다는 뜻이다.
표에서 같은 기능 행이 Yes와 Plugin과 Bounded와 대시로 갈리는 것이 그 비용의 표시값이며,
열린 이슈 146개 중 상당수가 여기서 나올 것이라고 짐작하기 어렵지 않다.
훅이 미들웨어 확장점이라는 관찰은 옳지만, 미들웨어가 성립하려면 인터페이스가 하나여야
한다는 조건이 아직 충족되지 않았다.

### 컨텍스트 관리의 다음 축은 추가 시점이 아니라 제거 시점이다

이 프로젝트가 다루는 것은 무엇을 컨텍스트에 넣을지다.
샌드박스는 넣지 않고, 색인은 나중에 넣고, 스냅샷은 압축 후에 다시 넣는다.
전부 추가 시점의 결정이며, 이 축에서는 이미 상당히 정교하다.

HN 토론에서 반복해 나온 다른 축은 제거다.
nr378은 컨텍스트 관리에 아직 손쉬운 열매가 많다며 되돌리기를 유망한 방향으로 든다.
모델이 몇 번의 시도 끝에 옳은 일을 해내면 실패한 시도들을 컨텍스트에서 잘라 내자는
것이다[^nr378].
elephanlemon은 이것을 더 밀고 나간다.
세션 중간에 디버깅에 시간을 쓴 뒤 버그를 고쳤다면 그 과정 전체를 컨텍스트에서 지우고
디버깅 전 상태로 이어 갈 수 있어야 하는데, 지금은 IDE에 따라 수동으로도 꽤 성가시고
그 뒤에 다른 작업을 했다면 잘라 낼 방법이 아예 없다는 것이다.
로그를 많이 뱉는 도구를 쓴 경우 그 로그가 한두 프롬프트 뒤에 자동으로 정리되어야 하며,
컨텍스트는 끝에서만 붙이고 뗄 수 있는 스택이 아니라 자유롭게 조작 가능한 것으로
생각해야 한다고 적는다[^elephanlemon].

이 두 축은 서로 배타적이지 않고 오히려 서로를 필요로 한다.
추가 시점 최적화만 하면 세션이 길어질수록 유효하지만 이미 낡은 정보가 컨텍스트에
계속 남는다.
Context Mode의 벤치마크가 자랑하는 세션 30분에서 3시간이라는 연장은 그 문제를 세 배로
키운다는 뜻이기도 하다.
3시간 전에 읽은 파일의 내용, 이미 해결된 오류, 폐기된 접근이 전부 컨텍스트 앞쪽에
남아 있고, 압축이 걸리기 전까지는 그것을 걷어낼 장치가 없다.

그리고 이 축에서 이 프로젝트는 이미 필요한 재료를 갖고 있다.
23개 범주로 이벤트를 분류하면서 해결된 오류와 거부된 접근과 반복 루프를 이미 식별하고
있기 때문이다.
어떤 오류가 언제 고쳐졌는지 아는 시스템은 원리적으로 그 오류와 관련된 대화 구간이
언제부터 쓸모없어졌는지도 안다.
지금 그 정보는 압축 후 복원용 스냅샷을 만드는 데만 쓰이는데, 같은 정보로 압축 전에
무엇을 먼저 버릴지 정할 수 있다.
곧 이 프로젝트의 자연스러운 다음 판본은 새 기능이 아니라 이미 수집한 신호를 반대
방향으로 쓰는 것이다.

### 도구 출력의 표현 형식 자체가 다음 경쟁 지점이 된다

이 프로젝트의 전제는 도구 출력이 텍스트라는 것이다.
그래서 해법이 텍스트를 어딘가에 숨기고 텍스트로 검색하는 형태를 띤다.
샌드박스도 stdout을 다루고 색인도 마크다운 청크를 다룬다.

HN에서 lmeyerov가 다른 층위의 답을 제시한다.
데이터베이스와 로그 시스템을 다루는 자기 제품에서는 질의 결과를 LLM에 돌려주는 대신
메모리 내 parquet에 가까운 데이터프레임을 만들고, 토큰 최적화된 요약 뷰와 함께
“…외 100만 행” 같은 힌트를 붙여 응답에 넣는다는 것이다.
그러면 LLM이 로그에 빠지지 않고 데이터프레임을 더 똑똑하게 파고들지 결정할 수 있으며,
운영 시스템에 반복 질의 압박이 줄고 에이전트 추론이 빠르고 싸지며 대화형 데이터 뷰가
담긴 노트북이 남는다.
그리고 MCP 프로토콜이 이론상 이진 같은 대체 콘텐츠 타입을 지원한다는 점을 들어,
MCP 세계의 데이터 쪽을 텍스트와 JSON에서 Apache Arrow로 옮기고 에이전트 하네스를
그것에 맞게 똑똑하게 만드는 방향에 관심이 간다고 적는다[^lmeyerov].

이 관점이 Context Mode의 접근을 다시 보게 만든다.
샌드박스가 하는 일은 결국 큰 텍스트를 작은 텍스트로 바꾸는 것이고, 그 변환을 매번
모델이 즉석에서 쓴 스크립트에 맡긴다.
앞서 hereme888과 startages가 지적한 취약함이 전부 그 즉석 변환에서 나온다.
반면 도구가 애초에 구조화된 핸들을 돌려주고 모델이 그 핸들을 질의하는 구조라면
변환 코드를 쓸 필요가 없고, 따라서 잘못 쓸 일도 없다.

여기서 나오는 이차 효과가 있다.
Context Mode 같은 도구가 널리 쓰일수록 그것이 해결하는 문제, 곧 도구가 원시 데이터를
쏟아붓는 관행이 정상으로 굳는다는 것이다.
MCP 서버를 만드는 쪽에서 보면 출력을 다듬을 유인이 줄어든다.
어차피 클라이언트 쪽에서 걸러지기 때문이다.
저자 자신도 이 문제를 알고 있어서, 사람들이 작업마다 MCP 서버 목록을 손으로 고르지
않고 5~6개를 설치해 80개 도구를 기본으로 띄운다는 현실을 인정하며 이 도구는
도구 정의 부풀림이라는 입력 쪽 문제는 풀지 않고 출력 쪽만 다룬다고 답한다[^mksglu-tools].
곧 이 도구는 생태계의 나쁜 기본값을 견딜 만하게 만들어 주는 완충재이며,
완충재가 잘 작동할수록 기본값을 고칠 압력은 줄어든다.
