# APIANT의 MCP 서버 기능: 통합 자동화를 MCP 도구로 게시하기

<https://apiant.com/mcp-servers>

## 소개

APIANT는 SaaS 회사, 시스템 통합 업체, 기업을 대상으로
API 통합 자동화를 만드는 플랫폼이다.
자동화 편집기, Assembly Editor와 AI Co-Pilot, 관리 콘솔, 챗봇, 폼 앱 같은
여러 기능을 갖추고 있고, MCP 서버는 그중 하나다.
이 문서는 플랫폼 전체가 아니라 MCP 서버 기능만 다룬다.

MCP 서버 소개 페이지는 APIANT 엔지니어링 팀 명의로 2026년 2월 19일 게시되었고
4월 22일 마지막으로 고쳐졌다.

이 기능의 요지는 한 문장이다.
APIANT에서 MCP 서버는 내려받아 쓰는 것이 아니라 만드는 것이며,
어떤 API든 자동화로 감싸고 필요한 로직을 더해 MCP로 노출하면
사용자와 고객이 자기 AI를 연결해 도구처럼 호출한다는 것이다.
페이지는 이를 “AI를 위한 웹 서비스”라고 부른다.

페이지 상단에는 차세대 제품 APIANT.AI도 소개한다.
Claude, Codex, Cursor처럼 원격 MCP 서버를 받는 클라이언트에
`https://mcp.apiant.ai`를 연결하고 필요한 통합을 요청하면
AI 에이전트가 그 통합을 만들고 시험하고 실행한다는 것이다.
설치가 필요 없고 무료로 시작할 수 있다고 한다.

## 동작 방식

### MCP 도구 하나는 자동화 하나다

APIANT에서 MCP 도구 하나는 플랫폼에서 만든 자동화 하나에 대응한다.
자동화의 깊이는 만드는 사람이 정한다.
엔드포인트 하나를 그대로 넘기는 얇은 도구일 수도 있고,
여러 시스템을 거치며 데이터를 변환하고 비즈니스 규칙을 적용해
정리된 결과만 돌려주는 다단계 자동화일 수도 있다.

페이지의 예시는 고객의 AI 에이전트가 `tools/list`로
`check_order_status`, `create_support_ticket`, `get_account_summary`
세 도구를 발견하고, 그중 주문 상태 도구를 주문 번호 하나로 부르는 장면이다.
`check_order_status`의 설명은 “ERP와 3PL에 걸쳐 주문을 조회”이고,
결과로 배송 상태, 운송사, 도착 예정일, 마지막 스캔 위치가 돌아온다.
에이전트는 그 뒤에 있는 ERP와 물류 API를 직접 만지지 않는다.
인증, 속도 제한, 오류 처리, 여러 시스템에 걸친 로직, 데이터 변환은
도구 뒤의 자동화가 맡는다.

### 용도

페이지가 제시하는 용도는 네 가지다.

| 용도             | 내용                                                        |
| ---------------- | ----------------------------------------------------------- |
| 제품 도구 서버   | 고객의 AI 에이전트가 고객 대신 내 제품 안에서 동작하게 한다 |
| 통합 데이터 서버 | CRM, 결제, 지원 시스템을 묶은 통합 조회를 도구 하나로 준다  |
| 다중 시스템 도구 | 여러 API를 거치는 다단계 자동화를 도구 하나 뒤에 둔다       |
| 내부 AI 도구     | 자사 에이전트에 통합 코드 없이 통제된 접근을 준다           |

### 플랫폼 안에서의 위치

MCP 서버는 APIANT AI 스택의 한 부분이다.
Assembly Editor와 AI Co-Pilot으로 자동화를 만들고,
AI Agents와 Chatbot을 그 위에서 돌리며,
MCP 서버는 그 모든 것을 외부 AI에 넘기는 출구다.

## 트레이드오프

### 얇은 래퍼 대신 작업 단위 도구

엔드포인트 하나를 도구 하나로 옮기는 직접 래핑은
[기존 REST API에 MCP 엔드포인트를 붙이는 방식](mcp-api-wrapper.md)처럼
코드 몇 줄로 끝난다.
그러나 모델은 잘게 쪼개진 도구를 여러 번 조합해야 하는 작업에서 자주 실패한다.
APIANT가 내세우는 “여러 시스템을 거치는 도구 하나”는
조합의 책임을 모델에서 자동화로 옮긴다는 점에서 설계상 맞는 방향이다.

대가는 도구가 무엇을 하는지가 자동화 안에 숨는다는 점이다.
모델은 설명 한 줄만 보고 도구를 고르는데,
그 뒤에서 세 시스템에 쓰기가 일어나는지 읽기만 하는지는
설명에 적지 않는 한 모른다.
작업 단위가 커질수록 설명과 부작용 표기가 더 중요해진다.

### 코드 없는 통합의 비용

통합 코드를 쓰지 않아도 된다는 것은 장점이지만,
도구의 로직이 APIANT의 자동화 형식 안에 저장된다는 뜻이기도 하다.
같은 기능을 직접 운영하는 서버로 옮기려면 자동화를 코드로 다시 써야 한다.
Uber처럼 사내에 [MCP 게이트웨이](uber-mcp-gateway.md)를 두는 조직이라면
이 종속이 감당할 만한지 따져 봐야 한다.

## 함정

- 페이지는 마케팅 소개다.
  가격, 지원하는 인증 방식(OAuth 여부), 속도 제한 값,
  호출 기록을 어디서 보는지 같은 운영 정보는 없다.
  도입 전에 설명서와 영업 문의로 따로 확인해야 한다.
- 예시의 응답 형식은 MCP의 `content` 배열이 아니라 단순화된 객체로 그려져 있다.
  실제 프로토콜 메시지 모양으로 읽으면 안 된다.
- APIANT.AI는 에이전트가 통합을 만들고 실행까지 한다고 소개한다.
  외부 AI 클라이언트가 내 계정의 자동화를 만들고 돌릴 수 있다면
  그 권한 범위와 승인 절차를 먼저 확인해야 한다.
- 문의 양식은 회사 웹사이트를 분석하고, 전화번호를 인증하고,
  “Alex”라는 통합 전문가와 음성 통화로 연결하는 흐름이다.
  상대가 사람인지 AI 음성 에이전트인지는 페이지에 명시되어 있지 않다.

## 기억할 원칙

### MCP 서버의 가치는 프로토콜이 아니라 뒤에 있는 작업에 있다

MCP는 모델이 도구를 발견하고 호출하는 방법을 표준화할 뿐이다.
같은 프로토콜 위에서 엔드포인트를 그대로 넘기는 서버와
여러 시스템의 작업을 하나로 묶어 정리된 결과를 돌려주는 서버는
모델에게 전혀 다른 도구다.

그래서 MCP 서버를 만드는 일의 핵심은 프로토콜 구현이 아니라
모델이 한 번에 성공할 수 있는 작업 단위를 정하는 일이다.
APIANT 같은 플랫폼은 그 작업 단위를 자동화로 만들게 하고,
직접 만드는 쪽은 같은 결정을 코드로 내린다.
어느 쪽이든 도구 목록을 API 목록이 아니라 사용자의 할 일 목록에서 출발해야 한다.

## 도구 계약을 검토하는 기준

도구를 공개하기 전에 호출의 결과를 세 범주로 나눈다.
읽기 전용 조회, 되돌릴 수 있는 변경,
외부에 금전·권한·업무 영향을 남기는 실행이다.
마지막 범주일수록 권한을 좁히고
사용자 확인과 감사 기록을 더 강하게 요구해야 한다.

도구 설명에는 이름과 입력값뿐 아니라
언제 호출하는지, 어떤 시스템을 바꾸는지,
실패하거나 두 번 호출했을 때 어떻게 되는지를 적는다.
자동화가 여러 API를 묶을수록 일부 단계만 성공하는 경우도 생긴다.
그때 재개 가능한지, 전체를 되돌릴 수 있는지,
운영자가 어느 실행 기록을 보고 복구할지까지 시험한다.

도입 평가는 성공한 데모 횟수로 끝내지 않는다.
모델이 엉뚱한 도구를 고르는 비율,
재시도에 따른 중복 실행,
사람이 개입해 해결한 실패를 일정 기간 기록해야
작업 단위로 묶은 자동화가 실제로 운영 부담을 줄였는지 알 수 있다.
