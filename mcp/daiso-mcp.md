# Daiso MCP: 한국 로컬 리테일·생활·영화관 데이터를 API 키 없이 AI에 연결하다

<https://github.com/hmmhmmhm/daiso-mcp>

<https://mcp.aka.page>

## 소개

Daiso MCP는 한국의 로컬 리테일·생활 정보·영화관 조회를 MCP, CLI, Codex Skill로 AI에 연결하는
오픈소스 도구다.
hmmhmmhm이 만들었고 TypeScript로 작성됐으며 MIT 라이선스, Cloudflare Workers 위에서 돌아간다.
이름은 “다이소”에서 왔지만 실제 지원 범위는 훨씬 넓다 — 다이소·올리브영·롯데마트의 상품/매장/재고,
GS25·세븐일레븐·CU·이마트24 편의점의 상품/매장/재고/인기검색어/카탈로그, CGV·메가박스·롯데시네마의
극장/영화/시간표/잔여 좌석, 네이버 지역 검색(음식점·카페), 오피넷 유가/주유소까지 아우른다.

핵심 특징은 “사용자가 별도 API 키를 준비하지 않고 바로 사용할 수 있다”는 것이다.
연결은 세 경로다 — MCP 서버 `https://mcp.aka.page`, CLI `npx daiso`, Codex Skill `clawhub install
daiso-cli`.
ChatGPT, Claude, Home Assistant, Grok 같은 AI 앱에서 바로 연결하며, Home Assistant Core
2026.7.1에서 MCP 도구 40개를 모두 정상 로드하는 것을 확인했다고 한다.
MCP 도구 응답은 각 서비스의 원본 필드를 유지하면서 클라이언트가 공통 UI를 만들 수 있도록
`standard` 필드를 함께 제공한다.

기술적으로 이 프로젝트의 데이터는 대부분 비공식 API를 역설계해 얻는다.
저장소 문서에는 스크래핑 플레이북, mitmproxy 가이드, 그리고 다이소·CU 등 각 브랜드의 “네트워크
분석 결과”, Playwright 네트워크 분석, 세션 리플레이 테스트 스크립트가 공개돼 있다.
공공데이터인 오피넷은 한국석유공사 무료 API(1일 1,500 call 한도)를 쓰고 응답에 출처와 `fetchedAt`을
포함하며 Cloudflare Edge Cache(예: 평균 유가 60분 캐시, 30분 stale-while-revalidate)로 원본 호출을
줄인다.
AI 에이전트가 오류·개선·신규 기능 요청을 개발자에게 바로 전달하는 `submit_developer_request` 도구는
Supabase `agent_requests` 테이블에 저장된다.

운영 측면에서 이 프로젝트는 이미 부하 문제에 직면했다.
2026년 7월 18일부터 올리브영·CGV·CU·GS25·롯데마트의 검색을 포함한 공개 GET API에 IP당 하루
합산 3,000회(KST 기준) 호출 제한을 적용했고, 한도를 넘는 사용이 필요하면 오픈소스이므로 저장소를
직접 배포하라고 안내한다.
100% 코드 커버리지 배지와 Better Stack 실시간 상태 페이지, Cloudflare Workers 30일 호출량 그래프를
README에 노출하며, `daiso_get_display_location`(다이소 진열 위치)이나 CGV 프로바이더 같은 기능은
외부 기여자들이 구현했다.

## 분석

### 이 프로젝트의 핵심은 “공식 API가 없는 데이터를 MCP로 감싼다”이다

Daiso MCP의 본질은 다이소라는 브랜드가 아니라, 공식 API가 존재하지 않는 한국 로컬 데이터를
AI가 쓸 수 있는 형태로 바꾸는 것이다.
편의점 재고, 다이소 진열 위치, 영화관 잔여 좌석 같은 정보는 각 기업이 자사 앱에서만 쓰라고
만든 비공식 엔드포인트이며, 이 프로젝트는 그것을 역설계해 표준 MCP 도구로 노출한다.

이 접근이 중요한 이유는 그것이 MCP의 진짜 쓸모를 드러내기 때문이다.
MCP는 LLM을 외부 도구에 연결하는 프로토콜이지만, 공식 API가 잘 갖춰진 서비스(예: GitHub,
Slack)라면 MCP 없이도 연결은 쉽다.
Daiso MCP의 값은 정확히 그 반대편 — 공식 API가 없어 AI가 닿을 수 없던 “현실 세계의 지저분한
데이터 층”을 메우는 데 있다.
저장소가 스크래핑 플레이북과 mitmproxy 가이드, 브랜드별 네트워크 분석 문서를 공개한 것은, 이
프로젝트의 핵심 노동이 프로토콜 구현이 아니라 비공식 엔드포인트의 역설계임을 정직하게 드러낸다.

이 관점이 MCP 생태계에서 이 프로젝트의 위치를 규정한다.
대부분의 MCP 서버가 이미 API를 가진 서비스의 얇은 래퍼인 반면, Daiso MCP는 API가 없는 곳에서
데이터를 캐내는 두꺼운 작업을 한다.
`standard` 필드를 원본 필드와 함께 제공해 클라이언트가 공통 UI를 만들게 한 것은, 열두 개가
넘는 이질적 브랜드의 제각각인 응답을 하나의 일관된 형태로 정규화하려는 시도다.
즉 이 프로젝트의 진짜 아키텍처는 “역설계 + 정규화 + MCP 노출”이며, MCP는 그 마지막 얇은 층일
뿐이다.

### “API 키 불필요”가 이 프로젝트의 설계 전체를 결정한다

Daiso MCP가 반복 강조하는 “사용자가 API 키 없이 바로 쓸 수 있다”는 것은 편의 기능이 아니라
아키텍처의 근본 결정이다.
이 결정이 공개 중앙 서버, Cloudflare Workers, 호출 제한, 캐싱 정책을 모두 낳는다.

이 결정이 중요한 이유는 그것이 인증 부담의 위치를 옮기기 때문이다.
사용자가 API 키를 준비하지 않는다는 것은, 그 데이터에 접근하는 부담 — 비공식 엔드포인트를
호출하고 세션을 관리하고 차단을 피하는 — 을 공개 서버가 대신 진다는 뜻이다.
그래서 `mcp.aka.page`라는 단일 공개 서버가 모든 사용자의 트래픽을 흡수하고, 그 집중이 Cloudflare
Workers의 엣지 배포와 캐싱을 필수로 만든다.
오피넷처럼 공식 무료 API가 있는 경우에도 1일 1,500 call 한도가 있어, 공개 서버는 캐싱으로 원본
호출을 줄여야 한다.

이 결정이 프로젝트의 지속 가능성을 직접 위협한다.
저자가 2026년 7월 18일부터 IP당 하루 3,000회 제한을 걸어야 했던 것은, “API 키 불필요”의 편의가
곧 남용과 부하로 돌아왔음을 보여준다.
그 대안으로 “오픈소스이니 직접 배포하라”고 안내한 것은, 편의의 부담을 다시 사용자에게 되돌리는
탈출구다.
결국 이 프로젝트는 “아무 준비 없이 바로 쓰는 공개 서비스”와 “각자 배포해 부담을 나누는 오픈소스”
사이에서 진동하며, 그 진동이 “API 키 불필요”라는 단일 설계 결정에서 비롯된다.

### 외부 기여와 100% 커버리지가 신뢰의 서사를 만든다

Daiso MCP가 100% 코드 커버리지 배지, 실시간 상태 페이지, 호출량 그래프, 외부 기여자 목록을
전면에 내세우는 것은, 비공식 데이터에 기반한 프로젝트가 겪는 신뢰 문제를 상쇄하려는 서사다.
검증 가능한 지표로 “이것은 신뢰할 수 있는 인프라”라는 인상을 만든다.

이 서사가 필요한 이유는 역설계 기반 프로젝트의 태생적 불안정성 때문이다.
비공식 API는 언제든 바뀌거나 막힐 수 있어, 이런 프로젝트는 “오늘 작동하지만 내일은 모른다”는
의심을 산다.
100% 커버리지와 상태 모니터링은 “우리는 이 불안정성을 체계적으로 관리한다”는 신호이며,
`daiso_get_display_location`이나 CGV 프로바이더를 외부 기여자가 구현했다는 것은 “한 사람의
취미가 아니라 커뮤니티 프로젝트”라는 인상을 더한다.
이 지표들은 기술적 사실이면서 동시에 신뢰를 사기 위한 마케팅이다.

이 서사가 앞서 여러 문서에서 본 패턴과 이어진다.
Jolt 문서에서 본 “스타 수가 신뢰의 근거가 아니다”[^ref-jolt], celld 문서에서 본 “100% 커버리지
같은 지표가 상류 안정성을 보장하지 않는다”는 관찰이 여기 적용된다.
Daiso MCP의 100% 커버리지는 자기 코드가 올바름을 재지, 다이소 서버가 응답 형식을 바꾸지 않음을
보장하지 않는다.
지표의 서사가 정교할수록 사용자는 그것이 재는 것(자기 코드 품질)과 재지 못하는 것(비공식 엔드포인트의
지속성)을 혼동하기 쉬우며, 이 프로젝트의 신뢰 서사는 바로 그 혼동 위에서 작동한다.

## 비평

### 비공식 API 역설계의 법적·윤리적 회색지대를 정면으로 다루지 않는다

이 프로젝트는 스크래핑 플레이북과 네트워크 분석 문서를 자랑스럽게 공개하지만, 그 데이터 수집이
각 기업의 이용약관과 어떤 관계인지는 다루지 않는다.
이 침묵이 프로젝트의 가장 큰 취약점이다.

이 공백이 문제인 이유는 역설계된 데이터가 무료가 아니기 때문이다.
편의점 재고, 다이소 진열 위치, 영화관 좌석 정보는 각 기업이 자사 앱 사용자에게 제공하려고 만든
것이지, 제3자가 대량으로 수집해 재배포하라고 연 것이 아니다.
mitmproxy로 앱 트래픽을 가로채 비공식 엔드포인트를 알아내고 세션을 리플레이하는 것은 기술적으로는
영리하지만, 대부분의 이용약관이 금지하는 자동화된 접근에 해당할 수 있다.
저자가 오피넷(공공데이터)에는 출처와 `fetchedAt`을 성실히 붙이면서도, 민간 기업의 비공식 API에는
그런 법적 근거 표시가 없다는 대비가 이 회색지대를 드러낸다.

이 문제가 프로젝트의 지속 가능성을 직접 위협한다.
이미 부하로 호출 제한을 걸어야 했다는 것은, 이 서비스가 대상 기업들의 서버에 실질적 트래픽을
가하고 있다는 뜻이다.
기업이 이를 인지하면 엔드포인트를 바꾸거나 차단하거나 법적 조치를 취할 수 있고, 그러면 40개
도구의 상당수가 하루아침에 멈춘다.
프로젝트가 “오픈소스이니 직접 배포하라”고 안내하는 것은 부하 분산책이지만, 동시에 법적 책임을
분산시키는 효과 — 각자 배포한 인스턴스가 각자 위험을 진다 — 도 갖는다.
역설계를 프로젝트의 핵심 노동으로 삼으면서 그 행위의 법적·윤리적 지위를 다루지 않는 것은, 사용자가
알아야 할 가장 중요한 위험을 문서에서 지운 것이다.

### “API 키 불필요”의 편의가 중앙 서버를 단일 실패·남용 지점으로 만든다

프로젝트가 자랑하는 “API 키 없이 바로 사용”은 사용자 편의이지만, 그것이 만드는 중앙 집중이
프로젝트의 구조적 취약점이라는 점을 README는 인정하지 않는다.

이 취약점이 근본적인 이유는 편의와 집중이 같은 동전의 양면이기 때문이다.
사용자가 자기 자격증명 없이 쓴다는 것은 모든 트래픽이 `mcp.aka.page`라는 단일 공개 서버를 통과한다는
뜻이고, 그 집중이 정확히 2026년 7월의 호출 제한을 강제했다.
분산된 API 키 모델이라면 각 사용자의 사용량이 각자의 키에 귀속되어 남용이 자연히 격리되지만,
공개 서버 모델은 한 명의 남용이 전체 서비스의 한도를 소진시킨다.
저자가 IP당 3,000회 제한을 걸어야 했던 것은 이 집중의 필연적 귀결이며, “API 키 불필요”의 편의가
곧 “한 명의 남용이 모두를 막는” 취약성으로 전환됐다.

이 취약점이 프로젝트가 제시한 해법에서 오히려 심화된다.
“한도를 넘으면 직접 배포하라”는 안내는, 편의로 사용자를 끌어들인 뒤 진지한 사용자에게는 그
편의를 거두어들이는 것이다.
직접 배포하려면 결국 각 브랜드의 세션·인증을 스스로 관리해야 하는데, 그것이 바로 “API 키 불필요”가
숨겨 둔 진짜 복잡도다.
즉 이 프로젝트는 복잡도를 없앤 것이 아니라 공개 서버 뒤에 숨겼을 뿐이며, 그 서버가 부하나 차단으로
무너지면 숨겨졌던 복잡도가 고스란히 사용자에게 돌아온다.
편의를 핵심 가치로 내세우면서 그 편의가 만드는 중앙 집중의 위험을 다루지 않은 것은, 사용자가
이 서비스에 얼마나 의존해도 되는지를 오판하게 만든다.

### 이름과 실제 범위의 불일치가 프로젝트의 정체성을 흐린다

“Daiso MCP”라는 이름은 다이소 하나를 가리키지만 실제로는 열두 개가 넘는 브랜드를 아우르며,
이 불일치는 단순한 명명 문제를 넘어 프로젝트의 초점과 유지보수 부담을 드러낸다.

이 불일치가 문제인 이유는 그것이 범위의 무한 확장을 시사하기 때문이다.
다이소로 시작한 프로젝트가 편의점 넷, 마트, 올리브영, 영화관 셋, 유가, 지역 검색으로 번진 것은,
“한국 로컬 데이터”라는 경계 없는 목표를 향해 계속 팽창하고 있음을 보여준다.
각 브랜드가 자기 비공식 API를 갖고 그것들이 제각기 바뀌므로, 지원 브랜드가 늘수록 유지보수 부담은
선형이 아니라 그 이상으로 증가한다.
40개 도구가 열두 개 브랜드에 걸쳐 있다는 것은, 어느 하나의 엔드포인트가 바뀌어도 그 브랜드의
도구들이 조용히 실패할 수 있다는 뜻이다.

이 확장이 신뢰 서사와 충돌한다.
100% 커버리지는 코드가 자기 로직대로 작동함을 보장하지만, 열두 개 브랜드의 비공식 API가 모두
살아 있음을 보장하지 않는다.
외부 기여자가 CGV 프로바이더나 다이소 진열 위치 도구를 구현했다는 것은 커뮤니티의 활력을 보여주지만,
동시에 그 기여자가 떠나면 그 브랜드의 유지보수가 공백이 될 위험을 뜻한다.
이름이 “다이소”에 묶여 있는데 실제로는 “한국 로컬 데이터 전체”를 지향하는 이 프로젝트는, 초점의
부재로 인해 어느 브랜드도 깊이 신뢰하기 어려운 상태 — 모두를 얕게 지원하되 어느 것도 보장하지
못하는 — 에 놓일 수 있다.
범위를 좁혀 소수 브랜드를 견고히 하는 것과 범위를 넓혀 “한국의 모든 것”을 얕게 다루는 것 사이의
선택을, 프로젝트는 후자로 기울면서도 그 대가를 명시하지 않는다.

## 인사이트

### MCP의 진짜 전선은 공식 API가 없는 회색 데이터이며, 이것이 에이전트 시대의 스크래핑 군비 경쟁을 부른다

Daiso MCP가 드러내는 가장 깊은 사실은, MCP의 실질적 가치가 이미 API를 가진 서비스가 아니라
API가 없는 데이터에 있다는 것이다.
그리고 그 데이터를 캐내는 역설계가 에이전트 시대에 새로운 규모의 스크래핑 군비 경쟁을 촉발한다.

이 통찰이 근본적인 이유는 그것이 데이터 접근의 권력 구조를 건드리기 때문이다.
공식 API를 가진 대기업은 자기 데이터의 접근을 통제하지만, 다이소·편의점·영화관처럼 공식 API가
없는 곳의 데이터는 “자사 앱 안에서만” 쓰이도록 갇혀 있었다.
Daiso MCP는 그 갇힌 데이터를 역설계로 해방해 AI가 쓸 수 있게 하며, 이는 uBlock 문서에서 본
“플랫폼이 자기 콘텐츠에 대한 사용자 통제를 파괴한다”는[^ref-ublock] 흐름의 반대편이다 — 여기서는
사용자(개발자)가 플랫폼의 통제를 우회해 데이터를 되찾는다.
그러나 이 해방은 대칭적 반작용을 부른다 — 기업이 비공식 API를 잠그면 역설계가 다시 뚫고, 그
순환이 스크래핑 군비 경쟁이 된다.

이 통찰의 2차 효과는 에이전트가 이 경쟁을 가속한다는 것이다.
LLM이 자연어로 “강남역 근처 제일 싼 주유소”나 “이 영화 잔여 좌석”을 물으면, 그 요청을 채우려면
누군가 그 데이터를 비공식 API에서 캐내야 한다.
에이전트가 현실 세계의 행동(예약, 구매, 조회)을 하려 할수록 공식 API가 없는 회색 데이터에 대한
수요가 폭증하고, Daiso MCP 같은 역설계 브리지가 그 수요를 메운다.
앞서 celld 문서에서 본 “독점 원시요소가 가치를 증명하면 상품화된다”는 패턴이[^ref-celld] 여기서
“갇힌 데이터가 가치를 증명하면 역설계된다”로 나타난다.
에이전트 시대의 진짜 병목은 모델의 지능이 아니라 현실 데이터에 대한 접근이며, 그 접근을 둘러싼
역설계와 차단의 군비 경쟁이 MCP 생태계의 가장 뜨거운 전선이 될 것이다.

### “API 키 불필요”의 공개 프록시는 반복적으로 죽는 역사적 패턴을 따른다

Daiso MCP의 “API 키 없이 바로 사용”이라는 공개 프록시 모델은 새롭지 않다.
그것은 지난 20년간 반복적으로 등장했다가 부하·차단·법적 압력으로 죽은 서비스 유형의 최신판이다.

이 패턴이 반복되는 이유는 편의와 지속 가능성의 근본적 상충 때문이다.
공개 프록시는 “아무 준비 없이 바로 쓴다”는 압도적 편의로 사용자를 끌지만, 그 편의가 트래픽을
단일 지점에 집중시켜 세 가지 죽음의 원인 — 부하, 대상 서비스의 차단, 법적 압력 — 에 노출된다.
RSS 브리지, 유튜브 다운로드 프록시, 트위터 nitter 인스턴스, 각종 공개 API 프록시가 모두 같은
궤적을 밟았다 — 인기를 얻고, 부하로 제한을 걸고, 대상이 차단하고, 결국 문을 닫거나 “직접 호스팅하라”로
후퇴했다.
Daiso MCP가 2026년 7월 호출 제한을 걸고 “직접 배포하라”고 안내한 것은 이 궤적의 초기 단계를
그대로 밟는 것이다.

이 통찰의 함의는 공개 프록시의 진짜 가치가 서비스가 아니라 코드에 있다는 것이다.
공개 인스턴스는 결국 죽지만, 오픈소스 코드와 역설계 문서(스크래핑 플레이북, 네트워크 분석)는
남아 각자 배포할 수 있게 한다.
앞서 Firefox·uBlock 문서에서 본 “자유가 소수의 수호자에 의존하면 그 수호자가 무너질 때 함께
무너진다”는[^ref-firefox] 원리가 여기 적용된다 — `mcp.aka.page`라는 단일 공개 서버에 의존하는
것은 취약하고, 진짜 회복력은 코드의 분산에서 온다.
Daiso MCP를 평가할 때 물어야 할 것은 “이 공개 서버가 얼마나 안정적인가”가 아니라 “이 서버가
죽어도 내가 직접 배포해 이어갈 수 있는가”이며, 이 프로젝트의 지속적 가치는 무료 서비스가 아니라
역설계 지식의 오픈소스화에 있다.

### 남의 API에 결합한 도구의 유지보수 경제학은 에이전트 시대에 더 취약해진다

Daiso MCP가 열두 개 브랜드의 비공식 API에 결합한 것은, 자기가 통제하지 못하는 인터페이스에
의존하는 도구의 근본적 취약성을 드러낸다.
그리고 이 취약성은 AI가 그 도구를 대량으로 호출하는 에이전트 시대에 오히려 증폭된다.

이 취약성이 구조적인 이유는 결합의 방향 때문이다.
Daiso MCP는 다이소·CU·CGV의 API를 소비하지만 그것들을 통제하지 못하므로, 상류가 바뀌면 하류가
조용히 깨진다.
공식 API라면 버전 관리와 폐기 공지가 있지만, 비공식 API는 아무 예고 없이 바뀌며, 그때 40개
도구 중 관련된 것들이 실패한다.
이것은 앞서 여러 문서에서 본 “의존성이 진짜일 때만 결합하라”는 원리의[^ref-bwsn] 반대 사례다 —
이 프로젝트는 통제할 수 없는 열두 개의 상류에 필연적으로 결합할 수밖에 없고, 그 결합이 유지보수
부담의 원천이다.

이 통찰의 2차 효과는 에이전트가 이 취약성을 증폭한다는 것이다.
사람이 이따금 조회하던 시절에는 비공식 API의 부하가 미미했지만, AI 에이전트가 자연어 요청마다
이 도구를 호출하면 트래픽이 폭증한다 — 정확히 Daiso MCP가 겪은 부하다.
증폭된 트래픽은 대상 기업의 주의를 끌어 차단을 앞당기고, 차단은 도구를 깨뜨리며, 그 결과 에이전트가
사용자에게 잘못된 정보(옛 캐시, 실패한 조회)를 줄 위험을 낳는다.
`submit_developer_request` 도구로 AI가 오류를 개발자에게 직접 보고하게 한 것은 이 취약성에 대한
영리한 완화책이지만, 근본 문제 — 통제 못 하는 API에 대한 의존 — 를 풀지는 못한다.
에이전트 시대에 “남의 API를 감싸는 도구”는 그 어느 때보다 유용하면서 동시에 그 어느 때보다
취약하며, 이 긴장이 Daiso MCP 같은 프로젝트의 장기적 운명을 결정한다 — 유용성은 채택을 부르고,
채택은 부하를 부르고, 부하는 차단을 부르는 순환 속에서, 이런 도구의 진짜 수명은 기술이 아니라
대상 기업의 관용에 달려 있다.
