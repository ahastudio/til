# MCP를 프로덕션에서 쓰는 사람들이 실제로 답한 것

Ask HN: [Ask HN: Who is using MCP in production?](https://news.ycombinator.com/item?id=49548600)

## 요약

`sukit`이 던진 Ask HN 질문에 185개의 댓글이 달렸고 162점을 받았다.
질문은 짧다 — MCP가 처음 나왔을 때부터 지켜봤고 초기에 많은 주목을
받았지만 프로덕션에서 쓰는 사람을 별로 못 봤다는 것이다.
그래서 쓰고 있다면 무엇에 쓰는지, 그리고 일반 API나 직접 도구 통합이나
그냥 CLI에 비해 어떤 이점을 찾았는지를 묻는다.

답변에서 가장 자주 반복된 이유는 성능이나 우아함이 아니라 사용자층이었다.
`cgarvis`는 MCP가 LLM 에이전트를 모는 최종 사용자가 비기술자일 때를 위한
것이라고 정리한다 — 대부분의 비기술자는 자기 컴퓨터에 CLI를 설치하지
않고 터미널로 에이전트를 몰지도 않는다는 것이다[^cgarvis].
그는 인증이 필요할 때도 유용하다며 CIMD를 쓴 MCP OAuth가 API 키를
생성하는 번거로운 과정 대신 손쉽게 만들어 준다고 덧붙이고, 이미 CLI를
쓰는 기술자라면 MCP가 별로 줄 것이 없다고 인정한다.
`div3rs3`는 질문의 대상 독자가 개발자일 테니 “그냥 CLI 쓰라”는 답이
많이 나올 것이라 전제한 뒤, 지금 MCP 서버의 주된 동인은 데이터 소스를
자기 AI 애플리케이션에 안전하게 연결하고 싶어 하는 비기술자라고
짚는다[^div3rs3].

두 번째로 많이 나온 것은 클라이언트를 자기가 통제하지 않는 상황이다.
`MitziMoto`는 고객 대면 음성 에이전트에 MCP를 쓰는데, 커스텀 MCP 서버가
예약을 잡거나 주문 상태를 확인하는 도구와 리소스를 정의해 두면
ElevenLabs든 vapi든 pipecat이든 어떤 음성 플랫폼을 골라도 그것을 가리키는
순간 사용 가능한 도구와 입력과 사용법을 즉시 이해한다고 적는다[^MitziMoto].
그는 HN이 옹호하는 CLI나 API 대안이 현실적으로 무엇인지 모르겠다고
되묻는다 — CLI를 패키징해 ElevenLabs에 배포하고 써 달라고 부탁해야 하는가,
전체 API 명세를 주고 구현해 달라고 해야 하는가.
`harijoe`는 MCP Apps가 Claude와 ChatGPT 앱 안에서 실제로 쓸 수 있는
커넥터를 만드는 유일한 방법이라며, 도구 결과와 함께 UI 조각을 반환하므로
CLI로는 같은 기능을 제공할 수 없다고 적는다[^harijoe].

인증과 배포의 편의도 반복된다.
`Eldodi`는 공식 SDK의 하루 다운로드가 1,700만 건으로 MCP 사용이 사상
최고라며, CRM·ATS·뱅킹·회계·Notion·Linear를 비롯한 거의 모든 SaaS와
인프라 제공자에 MCP를 쓰고 있고 구매 기준에서 “MCP 없으면 탈락”이 됐다고
적는다[^Eldodi].
이점으로는 직원 계정으로 그냥 동작하는 내장 인증과 Codex Plugins·Claude
Connectors의 원클릭 설치를 든다.
`946789987649`는 니치 CRM을 운영하는데 비기술 사용자가 자사 데이터를
Claude나 Copilot에 연결해 다른 MCP와 조합하는 것이 대단히 유용하다며,
자사 API 대비 이점을 네 가지로 정리한다 — 모든 도구와 파라미터에 LLM용
설명을 붙이기 훨씬 쉽고, 고객 중 누구도 CLI를 모르며, 같은 MCP를 자사
플랫폼의 에이전트에도 재사용하고, 애플리케이션 안에서 OAuth 전 과정을
처리해 준다는 것이다[^946789987649].
그러면서도 REST API와 매우 비슷하며 언젠가 합쳐질 수도 있겠다고 인정한다.

보안 경계를 좁히는 용도도 나온다.
`SegmentTree`는 보안과 촘촘한 권한 경계가 중요할 때 MCP를 쓴다며,
GitHub의 세분화된 토큰조차 충분히 세분화되지 않는 경우가 있는데 그럴
때는 원하는 작업만 정확히 노출하는 작은 MCP 서버를 만드는 것이
간단하다고 적는다[^SegmentTree].
에이전트가 호출할 수 있는 모든 GitHub CLI 조합을 일일이 감사하지 않고도
훨씬 작고 명시적인 공격 표면을 얻는다는 것이다.

여러 시스템을 가로지르는 집계도 반복 등장한다.
`5ersi`는 에이전트가 API와 CLI를 더 잘 쓰게 되면서 MCP의 가치가 다소
줄고 있다며 `gh` CLI를 이미 설치해 뒀으니 GitHub MCP 대신 그것을 쓴다고
적으면서도, 여러 소스를 가로질러 결과를 결합할 때는 큰 가치가 있을 수
있다고 말한다 — 사내에서 다섯 개의 서로 다른 레거시 시스템에 걸쳐
로그와 메트릭을 검색하는 MCP를 쓰는데 서로 다른 시스템의 이벤트 사이
상관관계를 몇 분 만에 찾아낸다는 것이다[^5ersi].
`jitl`은 자기 고용주인 Notion이 MCP를 제공하며 모노레포에 16개 이상의
MCP 설정이 있고 개발자가 선택적으로 활성화하는 플러그인도 많다며,
Slack·Honeycomb·incident.io·Materialize DB에 걸쳐 알림을 디버깅하도록
에이전트를 보내는 것을 특히 좋아한다고 적는다[^jitl].

실제 회사 사례도 여럿이다.
`josete89`는 Adidas에서 stdio와 remote 두 방식 모두를 프로덕션에서 쓰며
remote는 보안이 필요한 자율 에이전트나 에이전트 워크플로에, stdio는
로컬 개발에 쓴다고 적는다[^josete89].
`Aldipower`는 2026년 3월부터 지구력 스포츠 분석·계획 서비스에 쓰고
있는데 ChatGPT·Claude·Grok·Perplexity·Mistral 등 여러 채팅 인터페이스에
사용자가 직접 커스텀 MCP 서버를 추가하면 Claude로 훈련 계획을 만들어
Garmin 기기에 밀어 넣을 수 있다고 설명한다[^Aldipower].
그는 MCP가 제품의 등뼈이며 일반 사용자가 그것에 대해 아무것도 모른 채
일을 해내게 해 주므로, “MCP가 쓸모없는가” 논쟁은 일반 소비자 관점에서
완전히 무의미하다고 적는다.

문제점도 함께 보고된다.
`tasoeur`는 실시간 시각 효과 작업에서 앱 내 UI 갱신과 양방향 상태 질의,
프레임버퍼 캡처를 통한 폐루프 검증에 MCP를 널리 썼다면서도 흔한 함정에
당했다고 적는다 — 도구가 너무 많으면 컨텍스트가 빠르게 커지고, 일부
에이전트는 도구 목록 전체를 조회하지 않고 일부만 훑어 잘못된 동작을
한다는 것이다[^tasoeur].
`ByteOfWood`는 건설 설계 회사에서 PDF 마크업에 Bluebeam을 쓰는데,
적어도 Claude에서는 MCP로 데이터를 직접 파이프할 방법이 없어 에이전트가
모든 것을 스스로 출력해야 하므로 차라리 에이전트가 파이썬으로 MCP를
호출하거나 PDF를 직접 편집하는 편이 낫다고 적는다[^ByteOfWood].
그는 이 이유만으로도 대부분의 경우 커맨드라인 도구가 더 나은 길이라고
본다.
`patwolf`는 개인용으로는 MCP를 많이 쓰지 않지만 여러 에이전트를 뒤섞어
쓰는 비개발 팀에 도구를 배포하는 표준 메커니즘의 이점을 알게 됐다며,
스킬을 MCP로 전달할 수 있게 하는 SEP-2640 확장을 기대한다고 적는다 —
스킬 형식은 표준화됐지만 배포는 아직 그렇지 않다는 것이다[^patwolf].

## 분석

### 질문이 “왜 안 보이나”였는데 답은 “당신 눈에 안 보일 뿐”이었다

질문자의 전제는 MCP가 초기 주목에 비해 프로덕션 채택이 적다는 것이었다.
185개의 답변이 그 전제를 부정하지는 않았지만, 왜 그렇게 보이는지를
설명했다.

`Aldipower`의 문장이 이 구조를 압축한다 — MCP가 제품의 등뼈이고 일반
사용자는 그것에 대해 아무것도 모른 채 일을 해낸다는 것이다.
프로덕션 MCP는 개발자 도구가 아니라 제품 내부의 통합 계층으로 쓰이고
있으며, 그런 용도는 블로그 글이나 GitHub 스타로 드러나지 않는다.
HN에서 MCP가 화제가 될 때 거론되는 것은 개발자가 자기 에이전트에 붙이는
MCP이고, 그 층위에서는 실제로 CLI가 자주 더 낫다.

이 어긋남이 MCP 논쟁 전반의 형태를 설명한다.
“MCP는 죽었다, CLI 만세” 계열의 주장은 기술자가 자기 터미널에서 쓰는
경우를 근거로 삼고, 반대편은 비기술 사용자와 통제 불가능한 클라이언트를
근거로 삼는다.
둘 다 자기 층위에서 옳으며, 논쟁이 끝나지 않는 이유는 같은 단어로 다른
상황을 말하기 때문이다.

### 반복해서 나온 세 가지 이유는 모두 “내가 통제하지 못하는 쪽”에 관한 것이다

답변을 유형별로 묶으면 세 덩어리가 나온다 — 비기술 최종 사용자, 내가
만들지 않은 클라이언트, 그리고 인증.
겉보기에 별개지만 공통점이 있다.

셋 다 통합의 상대편을 내가 통제하지 못하는 상황이다.
비기술 사용자에게는 설치를 요구할 수 없고, ElevenLabs에게는 내 CLI를
탑재해 달라고 요구할 수 없으며, 사용자에게 API 키를 발급받아 오라고
요구할 수도 없다.
`MitziMoto`가 던진 반문 — CLI를 패키징해 배포하고 써 달라고 부탁해야
하는가 — 이 이 구조를 가장 선명하게 드러낸다.

이 관점에서 MCP는 프로토콜의 기술적 우수성 때문이 아니라 상대편이
이미 그것을 구현했기 때문에 선택된다.
`946789987649`가 “REST API와 매우 비슷하며 언젠가 합쳐질 수도 있겠다”고
인정한 것이 정직하다 — 차이는 스펙이 아니라 어느 쪽이 이미 지원하느냐다.
표준의 가치는 대체로 이런 형태이며, MCP의 채택 곡선도 기술 논쟁이 아니라
클라이언트 지원 현황을 따라간다.

### 도구 목록 자체가 새로운 병목이 되고 있다

여러 답변이 서로 다른 각도에서 같은 문제를 보고한다.
`tasoeur`는 도구가 많으면 컨텍스트가 커지고 일부 에이전트가 목록을
다 보지 않는다고 했고, `owaiswiz`는 수백에서 수천 개의 엔드포인트를
도구로 노출하는 대신 `list_resources`, `list_endpoints`,
`describe_endpoint`, `describe_ref`, `execute` 다섯 개로 감쌌다고
적는다[^owaiswiz].
`maxrev17`은 발품을 좀 팔면 컨텍스트를 오염시키지 않고도 수천 개의
도구를 둘 수 있다고 반박한다[^maxrev17].

이 논쟁의 실체는 MCP가 도구 목록을 선언적으로 전부 내려보내는 설계를
택했다는 데 있다.
그 설계는 클라이언트가 무엇을 할 수 있는지 즉시 알게 해 주지만, 목록이
커지면 그 자체가 컨텍스트 비용이 된다.
`owaiswiz`의 다섯 도구 패턴은 사실상 점진적 공개(progressive disclosure)를
손으로 구현한 것이고, `cagz`가 직접 API 호출의 문제로 “매번 API를 다시
이해해야 한다”를 든 것과 정확히 대칭을 이룬다[^cagz].

즉 MCP와 직접 API 호출은 컨텍스트 비용을 어디에 둘지가 다를 뿐 같은
문제를 다룬다.
MCP는 선불로 목록을 주고, 직접 호출은 사용할 때마다 명세를 다시 읽게
한다.
어느 쪽이 나은지는 도구 개수와 호출 빈도의 함수이며, 그래서 “MCP가
좋은가”라는 질문에 보편적 답이 없다.

## 비평

### 이 스레드는 표본이 아니라 자기 선택된 응답이다

Ask HN의 형식상 답하는 사람은 답할 것이 있는 사람이다.
“우리는 MCP를 검토했다가 버렸다”는 답은 쓸 동기가 약하고, 실제로 그런
답은 스레드에서 소수다.
그런데 질문자가 알고 싶었던 것은 정확히 채택률이었다.

이 구조에서 나오는 왜곡은 방향이 정해져 있다.
185개의 긍정적 사례가 나열되면 “MCP는 널리 쓰인다”는 인상이 남지만,
그것은 분모를 모른 채 분자만 센 것이다.
`kaydub`이 “프로덕션에서 쓴다는 게 무슨 뜻이냐”고 되물으며 고객 대면
앱 스택의 배포 구성 요소로는 안 쓰고 개발자들이 업무에 쓰는 것은
맞는다고 구분한 것이 이 문제를 드러낸다[^kaydub].
답변자마다 “프로덕션”의 정의가 다르며, 그 정의를 통일하지 않은 채 모은
목록은 채택률의 근거가 되지 못한다.

숫자가 하나 등장하지만 그것도 약하다.
`Eldodi`가 든 공식 SDK 하루 다운로드 1,700만 건은 인상적으로 들리지만,
SDK 다운로드는 CI 실행과 컨테이너 빌드에서 반복 발생하므로 사용자 수와
거리가 멀다.
같은 지표로 어떤 npm 패키지든 큰 숫자를 만들 수 있으며, 프로덕션 채택의
증거로 쓰기에는 부적절하다.

### 대부분의 답변이 대안과의 비교를 생략한다

질문은 두 부분이었다 — 무엇에 쓰는가, 그리고 일반 API나 CLI 대비 어떤
이점이 있는가.
답변의 다수가 첫 번째만 답하고 두 번째를 건너뛴다.

`peaxkl`이 정직한 예다 — 도움말 센터 재구성, 문서 작성과 이동과 게시에
쓰고 있으며 이 모든 경우에 API도 동작하겠지만 고객이 어차피 AI 도구를
쓰고 있으니 MCP가 그들에게 더 간단할 뿐이라고 적는다[^peaxkl].
“API도 되지만”이라는 단서가 붙은 사례가 여럿인데, 그렇다면 그것은 MCP의
이점이 아니라 배포 채널의 이점이다.
`earthdeity`가 Claude Code를 Jira와 Figma에 붙인 이야기를 하면서
“Jira에 대한 비난에 가깝다”고 자조하고 “API로 직접 붙이는 것보다 아주
조금 쉬워지는 정도”라고 적은 것이 그 온도를 보여 준다[^earthdeity].

비교를 실제로 수행한 소수의 답변이 훨씬 유용하다.
`cagz`는 직접 API 호출과 CLI를 각각 왜 배제했는지 조목조목 쓴다 —
직접 호출은 에이전트가 API 명세를 매번 다시 이해해야 하고 일반적인
OAS가 에이전트 친화적이지 않으며, CLI는 잘 문서화된 에이전트 친화적
CLI를 전제하는데 대부분의 CLI는 사람이나 CI/CD를 위해 설계됐다는 것이다.
이런 형태의 답이 열 개만 있었어도 스레드의 정보 가치가 크게 달라졌을
것이다.

### 성공 사례에 규모와 비용이 빠져 있다

프로덕션 사례를 묻는 질문에 대한 답으로서 이 스레드는 정성적 서술에
머문다.
얼마나 많은 호출이 오가는지, 지연이 얼마인지, 토큰 비용이 얼마나 드는지,
장애가 났을 때 무슨 일이 벌어지는지에 대한 언급이 사실상 없다.

`harijoe`가 유일하게 트래픽을 언급하는데 그것도 “아직 대단하지는 않지만
새 채널에 자리를 잡아 두는 비용이 적다”는 정도다.
Adidas와 Notion 같은 큰 이름이 등장하지만 규모는 나오지 않는다.
`mstade`는 여러 고객이 프로덕션 서비스에서 자사 MCP 서버를 쓴다며
플랫폼에서 매우 인기 있는 부분이라고 적지만 그 이상은 없다[^mstade].

이 공백이 중요한 이유는 MCP에 대한 회의가 주로 운영 측면에서 나오기
때문이다.
도구 호출 실패 시 재시도를 누가 하는지, 서버 버전이 올라갈 때 기존
에이전트가 깨지는지, 에이전트가 예상 밖의 순서로 도구를 부를 때 어떻게
되는지 — 프로덕션이라는 단어가 실제로 뜻하는 것은 이런 질문들이다.
“프로덕션에서 쓴다”는 답이 185개 모여도 이 질문에는 하나도 답하지
않는다.

## 인사이트

### MCP의 실제 경쟁 상대는 CLI가 아니라 각 플랫폼의 자체 확장 규격이다

이 스레드에서 반복된 CLI 대 MCP 논쟁은 사실 잘못된 대립이다.
답변자들이 MCP를 고른 상황을 보면 CLI가 후보였던 적이 거의 없다 —
ElevenLabs에 붙일 때, ChatGPT 앱 스토어에 올릴 때, 비기술 사용자가
OAuth로 연결할 때 CLI는 애초에 선택지가 아니다.

그 자리에 있던 진짜 대안은 각 플랫폼의 독자 규격이다.
ChatGPT 플러그인, Slack 앱, Zapier 통합, 각 음성 플랫폼의 커스텀 함수
정의가 그것이다.
MCP가 이긴 방식은 우월함이 아니라 그 규격들을 하나로 대체한 것이며,
`MitziMoto`가 “어떤 음성 플랫폼을 골라도 내 서버를 가리키면 즉시
이해한다”고 말한 것이 정확히 그 가치다.
N개의 플랫폼과 M개의 서비스를 잇는 N×M 통합 문제를 N+M으로 바꾸는
고전적 표준화이며, 이 관점에서 MCP는 프로토콜이라기보다 통합 시장의
정산 규격에 가깝다.

이 구조가 갖는 함의는 MCP의 운명이 기술적 개선이 아니라 플랫폼의
이해관계에 달려 있다는 것이다.
표준이 유지되려면 각 플랫폼이 독자 규격으로 되돌아가지 않아야 하는데,
그 유인은 차별화 압력과 반대 방향이다.
`Eldodi`가 “MCP 없으면 탈락”을 구매 기준으로 삼았다고 한 것이 이 표준을
지키는 실질적 힘이며, 구매자 쪽의 요구가 플랫폼의 이탈을 막는다.

역사적 유비가 도움이 된다.
ODBC가 데이터베이스 접근을, LSP가 편집기와 언어 도구를 같은 방식으로
바꿨고, 두 경우 모두 규격의 우아함보다 채택의 임계 질량이 결과를
결정했다.
LSP가 특히 가까운데, 처음에는 “그냥 각자 플러그인 쓰면 되지”라는 반응이
많았고 지금은 언어 도구가 LSP를 지원하지 않는 것이 상상하기 어렵다.

### 도구 목록의 크기가 MCP 설계의 다음 전장이다

스레드에서 가장 자주 반복된 실무적 불만은 컨텍스트 오염이었고, 그에
대한 대응으로 나온 것이 `owaiswiz`의 다섯 도구 패턴이다.
이 패턴이 널리 재발명되고 있다는 사실 자체가 프로토콜 수준의 공백을
가리킨다.

MCP는 서버가 자기 도구 전부를 선언하고 클라이언트가 그것을 컨텍스트에
싣는 구조로 출발했다.
도구가 열 개일 때는 자연스럽지만, 수백 개가 되면 목록 자체가 요청마다
반복되는 고정 비용이 된다.
그래서 사람들이 손으로 만드는 것이 검색 가능한 메타 도구층이며 —
“무슨 도구가 있는지 물어보는 도구” — 이것은 정적 선언에서 동적 발견으로의
이동이다.

이 이동은 다른 곳에서 이미 일어난 적이 있다.
SOAP의 WSDL은 서비스 전체를 선언했고, REST는 그것을 버리고 URL 탐색으로
갔으며, GraphQL은 다시 스키마를 선언하되 클라이언트가 필요한 것만 질의하게
했다.
매번의 이동을 만든 힘은 같다 — 선언의 크기가 사용의 크기를 압도하는
순간이다.
MCP도 같은 압력 아래 있고, `patwolf`가 언급한 SEP-2640 — 스킬을 MCP로
전달하는 확장 — 이 그 방향의 첫 신호일 수 있다.

여기서 나오는 예측은 MCP 서버의 좋은 설계 기준이 바뀐다는 것이다.
지금은 “얼마나 많은 기능을 노출하는가”가 성숙도의 지표처럼 쓰이지만,
곧 “노출하지 않고도 찾을 수 있게 하는가”가 그 자리를 대신할 것이다.
`owaiswiz`가 수천 개의 엔드포인트를 다섯 개로 감싼 것이 후진적 타협이
아니라 앞선 설계였다는 평가를 받게 될 가능성이 높다.

### 비기술 사용자를 위한 통합 계층이라는 정체성이 MCP를 보안 문제의 중심에 놓는다

스레드의 지배적 논거 — 비기술 사용자가 CLI를 설치하지 않으니 MCP가
필요하다 — 는 채택을 설명하지만 동시에 위험의 구조도 설명한다.

`cgarvis`와 `Eldodi`가 이점으로 든 것을 뒤집어 읽어 보자.
링크 하나를 눌러 OAuth 흐름을 거치면 인증이 끝나고, 원클릭으로 설치되며,
직원 계정으로 그냥 동작한다.
같은 문장이 “사용자가 자기 계정의 권한을 무엇에게 얼마나 위임했는지
모른 채 연결이 완료된다”로도 읽힌다.
`SegmentTree`가 GitHub 세분화 토큰조차 부족해 직접 MCP 서버를 만들었다고
한 것은 이 문제를 아는 사람의 대응이지만, 그런 대응을 할 수 있는 사람은
정의상 이 스레드가 말하는 비기술 사용자가 아니다.

`ma2kx`의 경고가 이 지점을 짚는다 — 일반적으로 MCP의 장점은 에이전트가
쓸 수 있는 도구를 세밀하게 통제할 가능성인데, 실제로는 직접 API 접근이나
CLI 통합보다도 나쁜 끔찍한 MCP 서버가 무수히 많다는 것이다[^ma2kx].
통제 가능성은 프로토콜이 주는 것이 아니라 서버 구현자가 주는 것이고,
사용자는 그 차이를 볼 수 없다.
`hkchad`가 “개발자 서클 밖에서 서비스를 채택시키는 데 좋다”고 한 것이
바로 그 사각지대다[^hkchad].

이 구조가 시간이 지나며 만들 결과는 예측 가능하다.
연결이 쉬울수록 연결이 많아지고, 많아진 연결은 감사되지 않으며,
사고는 프로토콜의 결함이 아니라 과다 권한 부여에서 나온다.
브라우저 확장, 모바일 앱 권한, OAuth 스코프가 모두 같은 곡선을 그렸고,
매번 해법은 프로토콜 수정이 아니라 권한 표시와 사후 감사 도구였다.
MCP에서 아직 비어 있는 것이 정확히 그 층이며, 다음 몇 년의 작업이
거기 몰릴 것이다.
