# Claude의 MCP 확장 지원 발표

원문: [MCP servers can now ship skills, run tasks, and more with Claude | Claude by Anthropic](https://claude.com/ko/resources/articles/skills-over-mcp-tasks-and-more)

HN 토론: <https://news.ycombinator.com/item?id=50632503> (4점, 0개 댓글)

## 요약

Anthropic은 2026년 11월 24일 Claude 리소스 페이지에 제품 업데이트 글을 올렸다.
핵심은 MCP(Model Context Protocol) 서버가 도구만 내놓는 데서 벗어나, 사용 지침과
장시간 작업과 사용자 입력과 파일까지 Claude와 주고받을 수 있게 되었다는 것이다.
글은 이를 두고 Claude가 서버를 다른 에이전트처럼 대하게 된다고 설명한다.
배우고, 일을 맡기고, 입력과 파일을 주고받는다는 뜻이다.

새 기능은 네 가지다.
첫째는 Skills over MCP다.
서버가 도구 옆에 스킬(skill)을 함께 게시하면 Claude는 필요할 때만 그 스킬을
불러온다.
스킬은 서버와 함께 갱신되므로 사용자가 따로 설치할 것이 없다고 글은 말한다.
스킬에는 모범 사례, 단계별 작업 절차, 계정이나 조직에 맞춘 지침을 담을 수 있다.

둘째는 Tasks다.
도구 호출이 끝나야 Claude가 다음으로 넘어가던 방식 대신, 서버가 시간이 걸리는
작업이나 에이전트 루프 전체를 맡아 돌리고 Claude는 그동안 다른 일을 한다.
셋째는 Elicitation이다.
서버가 호출 도중 멈추고 양식이나 링크로 사용자에게 입력을 요청한 뒤 이어서
진행한다.
넷째는 File Uploads다.
PDF, 스프레드시트, 이미지를 컨텍스트 창(context window)을 거치지 않고 서버로
보낸다.

글이 드는 사례는 다음과 같다.
Shopify는 온라인 스토어 설계와 갱신, HubSpot은 고객 온보딩, Atlassian은 조직
맥락을 활용한 분석에 스킬을 쓴다.
Carta는 업로드한 문서로 지분을 작성하고 발행하는 스킬을 곧 낼 예정이다.
ZoomInfo는 예전에는 여러 번의 프롬프트가 필요했던 계정과 연락처 조사를 Tasks로
돌린다.
Supabase는 유료 프로젝트를 만들기 전과 파괴적인 SQL을 실행하기 전에 비용을
확인하고, Railway는 서비스 삭제 같은 변경 전에 묻고, GitHub는 저장소를 삭제하기
전에 저장소 이름을 입력하게 한다.
이 셋은 모두 Elicitation 사례다.

제공 범위는 다음과 같이 적혀 있다.

| 기능            | 상태                           | 대상                                                                             |
| --------------- | ------------------------------ | -------------------------------------------------------------------------------- |
| Skills over MCP | Claude와 Claude Code 공개 베타 | Pro, Max, Ultra는 기본으로 켜짐, Team은 관리자가 켜면 사용, Enterprise는 곧 제공 |
| Tasks           | 정식 출시(GA)                  | Pro, Max, Ultra는 제공, Team과 Enterprise 조직에는 순차 제공                     |
| Elicitation     | 정식 출시(GA)                  | Pro, Max, Ultra는 제공, Team과 Enterprise 조직에는 순차 제공                     |
| File Uploads    | 곧 제공                        | Pro, Max, Ultra와 해당하는 Team, Enterprise 요금제                               |

글 후반부는 지난 1년의 변화를 네 가지로 정리한다.
도구 검색(tool search)은 여러 서버를 쓸 때 도구 정의가 차지하는 컨텍스트를 85%
넘게 줄일 수 있다고 한다.
최신 MCP 명세는 무상태(stateless)이고, Enterprise Managed Auth 확장은 관리자가
지원 서버를 한 번 승인하면 사용자가 자동으로 연결되게 한다.
MCP Apps 확장은 대화 옆이나 전체 화면에 인터페이스를 띄운다.
글은 MCP의 월간 SDK 다운로드가 7억 건을 넘고 Claude용 MCP 커넥터가 1만 개를
넘는다는 수치도 든다.
마지막으로 MCP가 Agentic AI Foundation이 호스팅하는 개방형 표준임을 밝히고
커뮤니티에 감사를 전한다.

## 분석

### 세 가지 부족을 한 번에 메우는 발표다

도구 이름과 설명은 서버가 무엇을 할 수 있는지만 알려 주고, 특정 사용 사례를
어떻게 처리할지는 알려 주지 않는다는 것이 글의 출발 진단이다.
Skills over MCP는 지식의 부족을 메운다.
Tasks는 시간의 부족을 메운다. 호출이 끝날 때까지 기다려야 한다는 제약이
사라진다.
Elicitation과 File Uploads는 입출력의 부족을 메운다. 사용자 결정과 파일이라는,
텍스트 인자로는 담기 어려운 것을 다룬다.

세 부족은 서로 다른 문제처럼 보이지만 공통 전제가 있다.
도구 하나를 호출하면 결과가 즉시 돌아오고 사람은 개입하지 않는다는 전제다.
이 전제는 조회성 도구에는 맞았지만 상점 설계나 지분 발행이나 계정 조사 같은
업무에는 맞지 않는다.
글이 사례로 든 서버들이 대부분 업무 도구(Shopify, HubSpot, Atlassian, Carta,
ZoomInfo)와 인프라 도구(Supabase, Railway, GitHub)인 것도 이 때문으로 읽힌다.

### Skills over MCP는 스킬 배포를 서버 쪽으로 옮긴다

MCP 쪽 문서는 Skills 확장을 다음과 같이 설명한다.
스킬은 `SKILL.md` 파일과 선택적 지원 파일로 이루어진 디렉터리이고, 서버는 기존
Resources 기본 요소(primitive)로 스킬을 노출한다.[^mcp-skills]
클라이언트는 `skills/list`로 스킬 목록과 메타데이터를 받고, 지침과 지원 파일은
실제로 필요할 때 읽는다.[^mcp-skills]
글이 말한 “필요할 때만 불러와 컨텍스트 사용을 낮춘다”는 설명은 이 설계를
가리키는 것으로 보인다.

이 문서에서 눈에 띄는 것은 무결성 장치다.
서버는 스킬의 모든 파일에 대해 URI, SHA-256 다이제스트, 바이트 크기를 담은
목록(manifest)을 내야 한다.[^mcp-skills]
호스트는 파일을 쓰기 전에 크기와 다이제스트를 검증해야 하고, 승인은 파일 URI와
다이제스트 전체 묶음에 묶여야 한다.[^mcp-skills]
파일이 바뀌거나 추가되거나 빠지면 승인은 취소되고 다시 받아야 한다.[^mcp-skills]
따라서 “스킬이 서버와 함께 갱신된다”는 글의 장점은 명세 쪽에서는 “갱신될 때마다
재승인이 필요할 수 있다”는 조건과 한 쌍이다.

### Tasks는 오래 걸리는 호출을 영속 핸들로 바꾼다

MCP의 Tasks 문서는 연결을 열어 둔 채 기다리는 방식이 안 되는 이유를 들어 이
확장을 설명한다.[^mcp-tasks]
많은 클라이언트와 전송 중개 계층에는 몇 초를 넘기면 곤란한 타임아웃이
있다.[^mcp-tasks]
서버는 최종 결과 대신 작업 ID(task ID)를 돌려주고, 클라이언트는 `tasks/get`으로
상태를 조회하며, 연결이 끊겼다 다시 이어져도 같은 ID로 조회를 재개할 수
있다.[^mcp-tasks]
상태는 `working`, `input_required`, `completed`, `failed`, `cancelled`로
나뉜다.[^mcp-tasks]

Tasks와 Elicitation은 Tasks 문서에서 서로 연결된다.
작업이 사용자 입력을 필요로 하면 `input_required` 상태가 되고, 클라이언트는
요청을 받아 `tasks/update`로 응답한다.[^mcp-tasks]
글에서는 두 기능이 따로 소개되지만, 장시간 작업 중에 사용자 확인을 받는 흐름은
두 기능이 함께 있어야 완성된다.

### File Uploads는 파일을 컨텍스트 밖으로 뺀다

글은 File Uploads가 PDF, 스프레드시트, 이미지를 컨텍스트 창을 거치지 않고 서버에
보낸다고 설명한다.
이 확장의 저장소 설명도 같은 방향이다. 파일 바이트가 모델 컨텍스트와 JSON-RPC
메시지 밖에 머물게 하는 것이 목적이다.[^mcp-files]
도구 검색이 도구 정의를, Skills가 지침을, File Uploads가 파일을 컨텍스트 밖으로
미루는 구도다.
세 가지가 모두 “필요할 때만 들여온다”는 원칙을 서로 다른 자원에 적용한 것이라고
볼 수 있다.

## 비평

### 호환성 주장과 명세 쪽 성숙도가 같은 속도로 읽히지 않는다

글은 이 기능들이 개방형 MCP 명세와 그 확장의 일부이므로 서버가 호환되는 어떤
클라이언트에서도 동작한다고 말한다.
그러나 MCP 쪽 Skills 문서는 Skills 확장이 최종(Final) 상태의 SEP-2640이라고
하면서도, SDK와 호스트 지원은 아직 구현 중이며 현황은 클라이언트 지원 표를
보라고 적는다.[^mcp-skills]
File Uploads 저장소는 한 걸음 더 나아간다.
이 확장은 실험적(experimental)이고, MCP 명세의 일부가 아니며, SEP로 제안된 적도
없고, 변경이 깨질 수 있다고 적는다.[^mcp-files]

원문의 문장은 이 둘을 구분하지 않는다.
“명세와 그 확장”이라는 표현은 문자 그대로는 틀리지 않지만, 읽는 사람은 네 기능이
모두 같은 성숙도라고 받아들이기 쉽다.
서버 개발자에게 실제로 중요한 질문은 “내 서버가 Claude 밖의 다른
클라이언트에서도 이 기능을 쓸 수 있는가”인데, 이 질문의 답은 기능마다 다르고
원문만으로는 알 수 없다.

### 신뢰 문제가 한 줄도 나오지 않는다

서버가 모델에게 지침을 배달하는 통로를 여는 일은 보안상 가볍지 않다.
MCP 쪽 문서는 스킬 내용을 신뢰할 수 없는 입력으로 취급하라고
요구한다.[^mcp-skills]
호스트 쪽 코드 실행과 `allowed-tools` 같은 권한 부여에는 스킬별 명시적 사용자
승인이 필요하다고 적는다.[^mcp-skills]
다이제스트는 서버 목록과의 일관성을 보증할 뿐 내용에 대한 신뢰를 보증하지
않는다는 주의도 있다.[^mcp-skills]
이름이 같은 스킬끼리 몰래 서로를 대체하지 못하게 하라는 요구도
있다.[^mcp-skills]

원문에는 이런 내용이 없다.
“기본으로 켜짐”과 “사용자가 따로 설치할 것이 없다”는 말은 편의를 강조하지만,
사용자가 무엇을 승인하고 무엇이 승인 없이 로드되는지는 말하지 않는다.
제품 소개 글이 보안 세부를 담지 않는 것은 자연스럽지만, 이 기능은 서버가 쓴
문서가 모델의 행동을 바꾸는 구조라서 그 세부가 사용자의 판단 재료가 된다.

### 사례와 수치의 근거가 글 안에 없다

ZoomInfo가 이전에 여러 번의 프롬프트가 필요했던 조사를 Tasks로 돌린다는 서술에는
소요 시간이나 품질 비교가 없다.
도구 검색이 컨텍스트를 85% 넘게 줄일 수 있다는 수치에는 “여러 서버를 쓰는
구성에서”라는 단서가 붙어 있을 뿐, 서버 수나 측정 방식이 없다.
월 7억 건의 SDK 다운로드와 1만 개의 커넥터도 정의가 없다.
다운로드 수가 자동화된 설치를 얼마나 포함하는지, 커넥터 1만 개가 활발히 쓰이는
것인지 등록된 것인지도 글만으로는 알 수 없다.
이런 수치는 글의 목적(생태계가 크다는 인상)에는 맞지만, 독자가 판단에 쓰려면
정의와 출처가 필요하다.

### 확인 절차의 품질은 서버 작성자에게 달려 있다

Elicitation 사례 세 가지는 모두 파괴적이거나 비용이 드는 행동 앞에서 확인을 받는
모습이다.
그러나 이 확인은 서버 작성자가 코드에 넣어야 존재한다.
Supabase와 Railway와 GitHub가 확인을 넣었다는 것은 그 서버들에 대한 사실이지,
모든 서버가 그렇다는 보증이 아니다.
글은 Elicitation을 사용자 동의를 받는 수단으로 소개하지만, 동의가 필요한 행동을
서버가 스스로 알아서 구분해 준다는 약속은 어디에도 없다.

## 인사이트

### 서버가 갱신될 때마다 모델의 행동도 바뀔 수 있다

이 아이디어는 이 문서의 해석이다.
도구는 이름과 입력 스키마가 바뀌면 호출 방식이 눈에 띄게 달라지지만, 스킬은
자연어 지침이어서 바뀌어도 겉으로는 같은 도구를 같은 방식으로 부르는 것처럼
보인다.
그런데 서버가 배포하는 스킬이 서버와 함께 갱신되면, 클라이언트 쪽에서는 아무것도
업데이트하지 않았는데 모델의 작업 순서와 판단 기준이 바뀐다.
명세가 승인을 파일 다이제스트 묶음에 묶고 변경 시 재승인을 요구하는 것은 이
위험을 의식한 설계로 보인다.[^mcp-skills]

여기서 긴장이 생긴다.
재승인을 엄격하게 요구할수록 서버 갱신이 잦은 서비스에서 사용자는 승인 요청에
시달린다.
느슨하게 하면 지침 변경이 눈에 띄지 않는다.
승인 요청이 잦아지면 사용자가 내용을 읽지 않고 승인하게 되는 문제와 구조가 같고,
이 기능의 사용성을 가를 부분이 될 수 있다.

### MCP 서버가 도구 상자에서 비동기 작업 서비스로 바뀐다

Tasks가 정의하는 흐름은 웹 API에서 오래 걸리는 요청에 쓰던 오랜 패턴과 닮았다.
요청을 받으면 즉시 작업 식별자를 돌려주고, 클라이언트가 상태를 조회하고, 입력이
필요하면 멈추고, 끝나면 결과를 가져가는 방식이다.
이 유사성은 이 문서의 비유이며, 명세가 그렇게 설명한 것은 아니다.

이 패턴이 MCP로 들어오면 서버의 성격이 바뀐다.
함수 모음이던 서버가 작업 큐를 가진 서비스가 되고, 글이 말한 “에이전트 루프
전체”를 서버 안에서 돌리는 것도 가능해진다.
이때 책임 소재가 달라진다.
작업이 Claude의 대화 바깥에서 오래 돌아가면, 결과가 틀렸을 때 어느 쪽의 판단이
틀렸는지를 대화 기록만으로는 추적하기 어렵다.
서버가 자체 에이전트를 돌린다면 그 에이전트의 모델과 지침은 사용자도 Claude도
보지 못하는 영역에 놓인다.

### 컨텍스트 절약이 탐색의 정확도 문제로 옮겨 간다

도구 검색, 스킬의 필요 시 로드, 파일의 컨텍스트 밖 전달은 모두 모델이 한꺼번에
보는 정보를 줄이는 방향이다.
이 방향의 대가는 “무엇을 불러올지 고르는” 단계가 중요해진다는 점이다.
MCP 쪽 문서에 따르면 호스트는 스킬을 이름과 설명으로 고르거나 사용자가
명시적으로 고르게 할 수 있다.[^mcp-skills]
커넥터가 1만 개에 이르고 서버마다 스킬을 낼 수 있게 되면, 이름과 설명이 비슷한
항목이 늘어난다.
이 상황에서 모델이 맞는 스킬을 고르지 못하면 컨텍스트를 아낀 이득이 틀린 선택의
비용으로 상쇄된다.

결국 서버 작성자의 일 가운데 설명 문장을 쓰는 일의 비중이 커진다.
스킬의 `description`이 사실상 검색 키워드이자 라우팅 규칙이 되기 때문이다.
이 기능을 평가하려면 컨텍스트가 얼마나 줄었는지보다 맞는 스킬이 얼마나 자주
선택되는지를 측정해야 하는데, 글은 이에 대한 수치를 내놓지 않는다.

### 확인의 위치가 모델 판단에서 서버 코드로 이동한다

Elicitation 사례에서 GitHub는 저장소를 삭제하기 전에 사용자가 저장소 이름을 직접
입력하게 한다.
이런 확인은 모델이 “정말 삭제할까요?”라고 되묻는 것과 성격이 다르다.
모델의 되묻기는 모델이 그 순간 필요하다고 판단해야 나오지만, 서버가 요청하는
양식은 서버 코드가 그 행동에 도달하면 반드시 나온다.
위험한 행동 직전의 확인을 결정적(deterministic)으로 만드는 방향이다.

다만 이 장점은 서버 작성자가 위험한 경로를 빠짐없이 짚었을 때만 성립한다.
파괴적 행동을 하는 서버를 쓰는 사람은 그 서버가 어떤 행동에 확인을 붙였는지를
도구 이름만으로는 알 수 없다.
도구별로 확인 여부를 표시하는 방법이 생기면 이 설계의 가치가 더 분명해질 것이다.
