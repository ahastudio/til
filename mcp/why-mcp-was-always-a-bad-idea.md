# MCP는 처음부터 잘못된 아이디어였다

원문: [Why MCP Was Always a Bad Idea](https://maharship.com/blog/why-mcp-was-always-a-bad-idea/)

HN 토론: <https://news.ycombinator.com/item?id=49779329> (321점, 317개 댓글)

GN 토론: <https://news.hada.io/topic?id=34059>

## 요약

Maharshi Patel이 2026년 9월 14일에 올린 짧은 의견 글이다.
최근 MCP 세계의 최신 동향을 다루는 종일 행사에 다녀왔는데, 발표자들은 모두 훌륭했고 자기 일에 열정이 있어 보였지만
솔직히 MCP에 지쳤다는 문장으로 시작한다.
LLM이 그리 똑똑하지 않던 시절을 위해 만들어진 형편없는 프로토콜이고 우리는 그것을 넘어섰다는 것이다.

역사 서술은 짧다.
MCP는 2024년 11월 Anthropic이 에이전트를 외부 서비스와 데이터 소스에 연결하기 위한 프로토콜로 내놓았다.
당시 모델은 지금에 비하면 원시적이었고 Claude Code조차 없었으며 범용 에이전트 작업 흐름은 훨씬 덜 믿을 만했다.
사용자들이 AI 모델에 외부 서비스 접근을 주는 것의 유용함을 보기 시작하면서 채택이 폭발했고,
경제 전반의 LLM 채택 증가와 나란히 갔다.
MCP는 Anthropic의 관리 아래 진화하다가 2025년 Linux Foundation 산하의 Agentic AI Foundation에 기증되었다.

그다음 절의 제목이 MCP 산업 복합체다.
채택이 늘면서 사용자들이 MCP 서버를 여럿 붙이기 시작했고 컨텍스트 팽창 문제에 부딪혔다.
서버마다 여러 도구가 딸려 오고 도구마다 자기 스키마가 있어서 모델의 컨텍스트를 과부하시켰다는 것이다.
하네스 개발자들은 우회법을 여럿 찾아냈고, Composio와 MintMCP와 Pipedream 같은 플랫폼이 제공하는
일반화된 검색 및 실행 패턴이 그중 하나다.
여러 외부 서비스의 자격 증명을 한곳에 두고, 컨텍스트 팽창을 줄이기 위해 에이전트에 최소한의 도구만 주어
그것들에 접근하게 하는 방식이다.
저자는 이것이 좋은 일이라고 분명히 해 두면서 단서를 붙인다.
단기적으로는 그렇다는 것이다.
MCP 주위에 쌓아 올린 이 모든 것에서 우리가 셈에 넣지 않았거나 어쩌면 무시한 것이 모델이 좋아지고 있다는 사실이며,
이제는 MCP 서버를 감시하고 응답이 괜찮은지 확인하고 에이전트가 도구에 쉽게 접근하게 하고
스키마를 알아내고 올바른 때에 올바른 호출을 하도록 무엇을 주어야 하는지 정하는 전용 시스템들까지 생겼다고 적는다.

전환점은 큰 연구소들이 옳았다는 절이다.
모델이 컴퓨터에서 코드를 실행하고 큰 코드베이스를 추론하고 훨씬 자율적으로 행동하게 되었다.
그 작업의 큰 부분이 코딩 목적의 스크립트를 쓰고 돌리는 것이었고, 그 부수 효과로 이제 API를 직접 잘 호출한다는 것이다.
괄호 안에 저자가 던지는 물음이 있다.
과연 부수 효과인가라는 것이다.
스크립트를 쓰고 여러 서비스를 조합하고 본 적 없는 API를 호출하는 일을 사용자의 최소한의 개입으로 해낸다고 적는다.
Cloudflare가 LLM에게 여러 호출을 스크립트로 조합해 샌드박스에서 실행하게 하는 Code Mode를 내놓은 것이 그 증거로 제시된다.
그리고 더 나아간 관찰이 이어진다.
LLM이 `--help` 명령으로 CLI를 발견하는 법을 알아냈으므로,
문서화된 API나 CLI로 제공되는 많은 서비스에 접근하는 데 더 이상 MCP 서버가 필요하지 않다는 것이다.
원격 서비스 MCP 서버 대부분이 결국 이미 존재하는 API를 감싼 것이라는 문장이 이 절을 닫는다.

그래서 무엇을 하느냐는 물음에 대한 저자의 답은 한 문장이다.
MCP 서버 대부분을 지우라는 것이다.
터미널 접근을 가진 에이전트가 MCP 서버 대부분을 대체할 수 있고 종종 더 유능하다고 말한다.
남는 문제도 인정한다.
CLI가 JSON이나 XML 같은 기계 판독 응답을 돌려주는데 그것이 매우 장황하고 토큰을 많이 쓴다는 것이며, 고칠 방법은 있다고 덧붙인다.
대안은 이미 대부분 존재한다는 것이 저자의 주장이다.
문서화된 HTTP API, 표준 콘텐츠 협상, 성숙한 인증 기제다.
그리고 에이전트가 HTTP API를 직접 쓰는 방식을 표준화하기 시작해야 한다고 제안한다.
에이전트 클라이언트가 자신이 에이전트임을 알리는 헤더를 붙이면, 서버가 HTML이나 장황한 JSON 대신
Markdown이나 텍스트로 응답 데이터를 자동으로 보낼 수 있다는 것이다.

실제 사례로 두 가지가 나온다.
하나는 `Accept: text/markdown` 헤더다.
LLM 친화적인 서버가 늘고 있고 특히 문서 사이트처럼 텍스트가 많은 곳이 이 헤더를 존중해
평소 보내던 HTML 대신 렌더링된 Markdown 파일을 보낼 수 있다.
미디어 타입 자체는 표준화되어 있고, 그것을 에이전트 대상 콘텐츠 협상에 쓰는 것이 채택을 얻고 있다는 서술이다.
다른 하나는 `Accept-Language` 헤더다.
Vercel의 한 엔지니어가 하네스들에게 클라이언트가 선호하는 프로그래밍 언어를 보내 달라고 요청했고,
그러면 문서 사이트가 더 구체적인 예제를 줄 수 있다는 것이다.
Python을 넣으면 일반적인 것 대신 Python SDK 문서를 우선할 수 있다는 예가 붙는다.
Shopify의 Tobi Lütke가 그 생각을 좋아해 Shopify 문서에 들어가게 되었다는 대화가 인용된다.

맺음말은 이렇다.
공통 프로토콜을 중심으로 표준화한 것이 인터넷을 오늘의 모습으로 키웠다.
MCP는 이제 지나간 시대의 프로토콜이다.
에이전트는 똑똑하고 스크립트를 쓸 수 있으며 원하는 것을 정확히 요구할 수 있다.
MCP라는 토끼굴을 계속 파는 대신, 이미 필요한 인터페이스를 제공하는 HTTP API와 CLI에 직접 의존하고
MCP는 수명을 끝낼 때라는 것이다.

## 분석

### 논증 전체가 밝혀지지 않은 하나의 전제 위에 서 있다

이 글의 주장은 조건부로 읽으면 대부분 옳고 무조건으로 읽으면 대부분 틀린다.
조건은 에이전트가 셸을 갖고 있고 인터넷에 제한 없이 접근한다는 것이다.
그 조건에서는 MCP 서버가 감싼 것이 어차피 HTTP API이므로 한 겹을 걷어 내는 것이 맞고,
`--help`로 CLI를 발견할 수 있다면 도구 스키마를 미리 컨텍스트에 올릴 이유도 줄어든다.

문제는 글이 그 조건을 한 번도 명시하지 않는다는 것이다.
저자가 든 사례는 전부 터미널 에이전트의 것이고, 결론은 프로토콜 전체의 수명 종료다.
HN 토론에서 가장 많이 읽힌 반응이 정확히 이 간격을 짚었다.
simonw는 글이 MCP가 오늘 제공하는 가치를 완전히 놓쳤다고 적으면서, 먼저 저자의 주장 절반을 인정한다.[^simonw]
인터넷에 제한 없이 접근하는 본격적인 터미널 에이전트를 돌린다면 API를 직접 호출하게 두면 되므로 MCP를 쓸 이유가 거의 없다는 것이다.
그러고 나서 그보다 덜 무모하게 운영하고 싶다면 필요해지는 것 네 가지를 든다.
어떤 외부 서비스에 접근할 수 있는지에 대한 정확한 통제,
에이전트가 API 키에 직접 닿지 않게 하는 인증 처리 방식,
사용자가 서비스를 연결하고 인증할 수 있는 합리적인 UI, 그리고 강력한 감사 로그다.
코딩 에이전트에게 필요 없다는 이유로 MCP가 낡았다고 보는 것은 우리가 만들고 싶을 다른 모든 것을 놓치는 일이라는 결론이다.

이 반응이 이 논쟁의 축을 정했다.
이후의 토론 대부분이 저 네 항목이 정말 MCP 고유의 것인지, 아니면 CLI와 API로도 되는지를 두고 갈린다.
그리고 그 축이 글에는 없다.

### 역사 서술이 능력 곡선 하나로 정리되어 있다

글의 역사 부분은 깔끔한 서사를 만든다.
모델이 약했을 때 MCP가 필요했고, 채택이 폭발하면서 컨텍스트 팽창이 생겼고,
그것을 메우려고 산업이 생겼고, 그러는 사이 모델이 좋아져 그 산업 전체가 불필요해졌다는 것이다.
큰 연구소들이 옳았다는 절 제목이 그 서사의 도덕이다.

이 서사에서 움직이는 변수는 하나뿐이다.
모델의 능력이다.
채택의 관성, 조직의 구매 절차, 비개발자 사용자층, 규제와 감사 요구, 기존 투자 같은 것들은 등장하지 않는다.
저자가 산업 복합체라는 이름을 붙인 것 자체가 그 축소를 드러낸다.
그 이름은 이해관계가 기술적 필요보다 오래 살아남는다는 함의를 담고 있는데,
글은 정작 그 이해관계가 어떻게 작동하는지는 다루지 않고 기술적 불필요만 논증한다.

능력 곡선 하나로 정리된 서술에는 반복되는 형태가 있다.
어떤 계층이 모델의 부족함을 메우려고 생겼다면 모델이 나아지면 사라진다는 것이다.
이 형태가 맞는 경우가 실제로 있다.
프롬프트 기법 상당수가 그렇게 사라졌고, 출력 형식을 강제하려던 여러 장치도 그랬다.
그러나 그 형태가 성립하려면 그 계층이 오직 모델의 부족함만 메우고 있었어야 한다.
MCP가 그런 계층인지가 이 글이 답해야 하는 질문인데, 글은 그것을 전제로 놓고 시작한다.

### 대안으로 제시된 것은 프로토콜의 부재가 아니라 다른 프로토콜이다

맺음말의 논리 구조를 그대로 따라가면 어긋남이 보인다.
공통 프로토콜을 중심으로 표준화한 것이 인터넷을 키웠다고 말하고,
그래서 MCP를 끝내고 HTTP API와 CLI에 직접 의존하자고 말한다.
그런데 그 직접 의존이 성립하려면 글이 제안한 것이 필요하다.
에이전트가 자신을 식별하는 헤더를 붙이고 서버가 그에 맞춰 Markdown을 보내는 관습이다.

즉 제안의 내용은 프로토콜을 없애는 것이 아니라 더 얇은 프로토콜로 바꾸는 것이다.
그리고 그 얇은 프로토콜도 양쪽의 합의가 있어야 작동한다.
글이 든 두 사례가 그 점을 보여 준다.
`Accept: text/markdown`은 미디어 타입이 이미 표준이므로 합의 비용이 낮고,
`Accept-Language`에 프로그래밍 언어를 넣자는 제안은 기존 헤더의 의미를 바꾸자는 것이므로 합의 비용이 높다.
후자가 성사된 경위로 글이 인용한 것은 표준 절차가 아니라 두 사람의 짧은 대화다.
Vercel 엔지니어가 요청했고 Shopify 창업자가 좋다고 답했다는 것이다.
MCP가 한 회사에서 시작해 재단으로 간 것과 절차상 크게 다르지 않은 경로다.

이 대목은 뒤의 비평에서 가장 강하게 반박받는 지점이기도 하다.
프로토콜 난립을 문제 삼는 글이 기존 표준 필드의 의미를 겹쳐 쓰자고 제안하기 때문이다.

### 이 논쟁은 실은 두 개의 다른 논쟁이다

토론 317건을 읽고 나면 사람들이 서로 다른 것을 이야기하고 있다는 것이 분명해진다.
한쪽 논쟁의 주제는 도구 호출의 효율이다.
스키마를 몇 개나 컨텍스트에 올려야 하는지, 응답이 얼마나 장황한지, 발견에 토큰이 얼마나 드는지다.
다른 쪽 논쟁의 주제는 통제 평면이다.
누가 무엇에 접근할 수 있는지, 자격 증명이 어디에 있는지, 무슨 일이 있었는지 어떻게 남기는지,
그리고 셸이 없는 사용자와 런타임에 어떻게 기능을 배포하는지다.

발언자의 처지가 어느 논쟁에 속하는지를 거의 결정한다.
`0x696C6961`는 사람들이 자기 로컬 Claude Code 작업 흐름이 유일한 MCP 사용 사례가 아니라는 것을 인정하지 못한다고 적었다.[^0x696C6961]
CharlieDigital은 더 구체적으로 나눈다.
많은 개발자가 혼자 일하는 방식으로 MCP를 오해하는데, 혼자일 때는 비밀 정보가 로컬에 있고 접근 감사를 신경 쓰지 않으며
인프라와 서드파티 비밀을 관리하는 IT 조직이 없고, 여러 하네스를 고려할 필요 없이 자기 하네스에 도구를 맞추면 되고,
팀원이 떠날 때 비밀을 회수하고 교체할 일을 생각하지 않으며, 여러 런타임과 스택에 기능을 전달할 필요가 없다는 것이다.[^CharlieDigital]
dmix는 한 줄로 같은 말을 한다.
이런 글들은 늘 MCP를 기술적인 사람들이 쓴다고 가정하는데,
MCP는 터미널이 무엇인지 모르는 기업의 일반 사용자들이 OpenAI와 Claude 마켓플레이스의 플러그인으로 쓴다는 것이다.[^dmix]
whazor는 그것이 승리의 이유라고 본다.
ChatGPT와 Claude 앱 안에 플러그인 스토어가 있고, 그 플러그인은 인증까지 지원하는 원클릭 설치 MCP 서버이며,
기업 사용자가 쓰는 것이 바로 그것이라는 것이다.[^whazor]

두 논쟁을 갈라 놓으면 이 글의 위치가 분명해진다.
첫 번째 논쟁에서는 글이 대체로 옳고, 두 번째 논쟁에서는 글이 참여하지 않았다.
그리고 글의 결론인 수명 종료는 두 번째 논쟁에서 이겨야 나올 수 있는 결론이다.

### 상태를 가진 프로토콜로 설계한 것이 실제 설계 실수로 지목된다

글은 MCP를 형편없는 프로토콜이라고 부르면서도 어디가 어떻게 잘못되었는지는 짚지 않는다.
컨텍스트 팽창은 사용 양상의 문제이고 감싸기라는 지적은 계층의 문제이므로, 둘 다 프로토콜 설계 자체에 대한 진단은 아니다.
토론에서는 그 빈자리를 메우는 구체적 지목이 나왔다.

miguelspizza는 글이 MCP의 핵심을 놓쳤다고 보면서도 어떤 면에서는 실수였다는 데 동의한다.[^miguelspizza]
그리고 실수의 내용을 한 곳으로 좁힌다.
MCP를 API와 별개의 프로세스에 두어야 하도록 만든 것이며,
MCP가 상태를 갖는다는 성질이 업계를 크게 우회시켜 앞으로 몇 년은 그 뒤처리를 하게 될 것이라는 것이다.
이제 MCP가 상태를 갖지 않게 되었으므로 실제로 유용한 것, 즉 에이전트를 위해 API를 확장하는 일을 시작할 수 있다고 적는다.
그러면서 오늘 MCP를 해야 하느냐는 질문에는 당연히 그렇다고 답하는데,
이유는 MCP의 OAuth 부분이 매우 좋고 모든 공개 API에 순이익이기 때문이라는 것이다.

cruffle_duffle는 같은 지점을 처음 서버를 만들 때의 반응으로 전한다.[^cruffle_duffle]
왜 이렇게 만들었는지, 어떤 사용 사례를 염두에 둔 것인지 의아했다는 것이다.
우리는 수십 년 동안 백엔드를 최대한 상태 없이 만들어 왔고,
상태를 갖게 만드는 것은 조금이라도 합리적인 확장성을 원한다면 비싸고 복잡하며,
2026년에 상태를 가진 서비스를 스케일 투 제로 서버리스 인프라에 올리는 것은 사실상 불가능하다고 적는다.
그리고 그 선택의 출처를 추측한다.
LLM 세션 자체가 캐싱을 위해 상태를 심하게 갖고 캐싱이 LLM을 경제적으로 확장하는 유일한 방법이므로,
연구소 입장에서는 상태성이 DNA에 가깝고 그래서 MCP도 백엔드에서 상태를 갖게 하는 것이 자연스러웠으리라는 것이다.

이 두 반응이 글에 없는 것을 제공한다.
글의 진단은 모델이 좋아졌으니 이 계층이 불필요해졌다는 시점의 문제이고,
이 진단은 프로토콜이 처음부터 잘못된 축을 골랐다는 설계의 문제다.
둘의 함의가 다르다는 점이 중요하다.
앞의 진단이 맞으면 MCP는 사라져야 하고, 뒤의 진단이 맞으면 MCP는 고쳐져야 한다.
그리고 miguelspizza의 보고에 따르면 지목된 결함은 이미 고쳐졌다.
`X-Prefers-Lang`을 표준화하자는 제안보다 이쪽이 글의 제목에 훨씬 가까운 논거인데, 글에는 없다.

angry_octet은 같은 문제를 더 오래된 이름으로 부른다.[^angry_octet]
MCP는 기본적으로 RPC이고 RPC 계열의 문제를 전부 물려받았다는 것이다.
긴 왕복 시간, 적지 않은 직렬화 비용, 호출자와 소비자의 결합, 버전 관리 문제가 그것이다.
그러면서 소멸이 아니라 진화를 예상한다.
왕복 지연을 줄이는 클라이언트 쪽 마이크로 모델과,
여러 로컬 모델이 질의를 밀어 넣고 작업을 계속하다가 여러 주제에 대한 갱신을 비동기로 받는 메시지 버스 구조로 갈 것이며,
그 채널이나 주제는 여러 로컬 에이전트가 함께 쓸 수 있고 도구 호출 결과도 그렇다는 것이다.
메시지 버스 시스템이 무작위한 CLI 도구와 웹 인터페이스보다 버전을 매기고 어댑터를 쓰고 디버깅하기 쉬우므로,
MCP 인터페이스는 사라지지 않고 진화한다고 맺는다.

## 비평

### 셸이 없는 에이전트에 대한 답이 글에 없다

글의 처방은 한 문장이다.
터미널 접근을 가진 에이전트가 MCP 서버 대부분을 대체할 수 있다는 것이다.
이 처방은 터미널 접근이 없는 에이전트에 대해 아무 말도 하지 않는다.

docheinestages가 이 공백을 정면으로 짚었다.[^docheinestages]
글의 전제는 Model Context Protocol이 현재 형태에서 비효율적이라는 것이고 거기에는 동의할 수 있다고 먼저 인정한다.
그러면서 묻는다.
그렇다고 해서 에이전트가 서버에 연결해 그 기능과 도구와 배포된 스킬을 발견하는 프로토콜이 필요 없다는 뜻이냐는 것이다.
그리고 터미널 접근이 없는 다른 모든 에이전트는 어떻게 해야 하느냐고 되묻는다.
viccis도 같은 지적을 한다.
MCP를 비판하는 사람 상당수가 배터리 포함형 코딩 하네스로만 LLM을 접해 봐서
어떤 종류의 도메인 특화 에이전트 시스템이 만들어지고 있는지 모른다는 것이며,
에이전트에 CLI 접근이 없으면 CLI 대 MCP라는 대립 자체가 아무 뜻도 없다고 적는다.[^viccis]

실물 조건을 드는 반응도 있다.
dnlosx는 CLI 도구가 항상 같은 환경을 쓸 때는 훌륭하지만 iPhone에서 써 보면 그냥 작동하지 않으며,
원격 MCP는 매끄럽게 작동한다고 적는다.[^dnlosx]
그리고 두 가지의 설계 목적이 다르다는 구분을 덧붙인다.
API는 예측 가능하고 일관되도록 설계되어 클라이언트가 응답 모양을 미리 알지만,
MCP는 동적으로 발견되도록 설계되어 에이전트가 새롭고 알려지지 않은 것에 연결할 수 있다는 것이다.
API에 추가 책임을 얹어 MCP를 대체하게 하는 것은 혼란만 키우며,
MCP 서버를 만들어 놓고 API라고 부르는 것과 같다고 정리한다.

이 반론들이 글의 범위를 좁힌다.
글이 실제로 논증한 것은 터미널 에이전트에게 MCP가 필요 없다는 것이고,
주장한 것은 MCP를 끝내자는 것이다.
그 사이의 거리를 메우는 논증이 글에 없다.

### 통제와 자격 증명과 감사를 CLI가 대신한다는 주장이 결론 나지 않았다

simonw가 든 네 항목은 이 논쟁에서 가장 길게 다투어졌고, 저자 본인이 직접 답했다는 점에서 특히 볼 만하다.
maharshi365는 네 가지에 차례로 반박한다.[^maharshi365]
통제는 CLI로 할 수 있고 API 키 기반 접근 제어는 우리가 늘 해 오던 것이며,
두 번째는 OAuth 기반 MCP에만 해당하고 많은 서버가 파일로 저장된 API 키 인증을 지원하므로 보안은 여전히 허술하며,
세 번째와 네 번째도 API와 CLI로 할 수 있고 MCP만의 것이 아니라는 것이다.
그리고 MCP가 본질적으로 이것을 더 쉽게 만들어 주지 않으며 여전히 엔지니어링 유지보수가 든다고 맺는다.

lelanthran은 그 반박을 자기 구현으로 구체화한다.[^lelanthran]
자기는 웹앱에 MCP가 아니라 CLI 인터페이스를 두었고, 접근 제어는 CLI가 아니라 웹앱에 들어 있다.
CLI는 환경에서 자격 증명을 받아 엔드포인트와 통신하며, 호출자가 환경을 설정한 뒤 CLI 프로그램을 부른다.
그래서 CLI에 입력을 보내는 쪽, 즉 모델이 환경 변수를 요청하거나 꺼낼 방법이 없다는 것이다.
MCP에 비해 유일한 이점으로 자신이 인정하는 것은 문법에 대한 합의된 관습이며 의미에 대한 것은 아니라고 적는다.

prescriptivist는 한 걸음 더 나아가 둘의 구분 자체를 흐린다.[^prescriptivist]
MCP는 결국 도구 사용이고, 터미널 에이전트에 내장된 웹 검색과 Bash와 Grep도 이름만 다른 MCP라는 것이다.
모델이 부르는 CLI는 Bash 도구 호출일 뿐이고, Bash 도구는 노출할 수 있는 가장 개방적이고 광범위한 MCP이며,
얻는 것은 컨텍스트 팽창의 감소이고 잃는 것은 에이전트에 대한 통제라고 정리한다.
그 통제는 Bash 도구에 엄격한 권한 체계를 세우기 전까지는 회복되지 않는다.
그리고 자기 사례를 든다.
샌드박스에 격리된 Claude Code 여러 대가 파일을 공유하는데, 파일은 AWS에 있지만 인스턴스들은 AWS에 접근할 수 없고
접근 키를 볼 수도 없으며 파일이 AWS에 있다는 사실조차 모른다는 것이다.
대신 목록과 업로드와 내려받기를 위한 MCP 도구 묶음을 갖는다.

반대 방향의 가장 강한 반론은 jimbokun에게서 나온다.[^jimbokun]
MCP를 통제 지점으로 삼는 것이 거짓된 안전감을 만든다는 것이다.
인증과 접근 제어는 셸을 완전히 가진 에이전트를 견딜 수 있어야 하고,
감사는 사람이든 에이전트든 모든 클라이언트의 활동 전체를 보여 주려면 서버 쪽에 있어야 한다.
에이전트를 영리한 사람처럼 다루고 그에 맞게 데이터 접근을 보호하고 감사해야 하며,
에이전트의 민감 정보 접근을 사람의 접근과 다르게 다룰 수 있다고 생각하던 시대는 끝났다는 것이다.
kaoD도 같은 방향에서 정리한다.
네 항목 중 1과 2와 4는 샌드박싱에 속하고 3은 샌드박스 UI에 속하며, 이상적으로는 차세대 운영체제에 들어가야 할 것들이고
MCP는 그 전부에 대해 잘못된 추상이라는 것이다.[^kaoD]

이 교환에서 결론이 나지 않았다는 사실 자체가 글에 대한 비평이 된다.
글은 이 네 항목을 아예 다루지 않았고, 다룬 사람들 사이에서도 답이 갈렸다.
그렇다면 수명을 끝내자는 결론은 이 논쟁이 끝난 뒤에나 나올 수 있는 것이다.

### 표준 헤더를 겹쳐 쓰자는 제안이 글의 자기 논지와 충돌한다

글이 든 두 사례 중 두 번째가 토론에서 가장 격한 반응을 얻었다.
`Accept-Language`에 프로그래밍 언어를 넣자는 제안이다.

well_ackshually는 Vercel이 수십 년간 쓰여 온 표준 헤더의 용법을 오용하자고 제안하는 것이며,
`X-Prefers-Lang` 같은 것을 표준화하자고 요청하기 귀찮아서 그러는 것이고,
Shopify도 거기에 동참하고 있다고 적었다.[^well_ackshually]
표현은 거칠지만 지적은 정확하다.
`Accept-Language`는 자연어 협상을 위한 필드이고, 프로그래밍 언어를 담으면
같은 필드가 두 가지 다른 축을 뜻하게 된다.

graypegg의 지적이 그 이유를 설명한다.[^graypegg]
자원이 완전히 달라질 것이라면 그것은 URL에 들어가야 한다는 것이다.
`Accept-Language`가 원래 조금 이상한 것도 같은 이유인데, 그 헤더의 의도는 자원 자체가 같은 것을 전달하려 한다는 데 있다.
Python SDK 문서와 일반 문서는 같은 자원의 두 표현이 아니라 다른 자원이므로,
콘텐츠 협상이 아니라 주소로 구분하는 것이 맞다는 논지다.

mbreese는 이 문제를 글 전체의 논지와 연결한다.[^mbreese]
API 접근이 없는 사설 자원으로 가는 관문으로서 MCP에 여전히 가치가 있다고 보면서도,
`Accept-Language`를 재정의하지는 말아 달라고 적는다.
이런 것들은 이유가 있어서 잘 정의되어 있고 재정의는 도움이 되지 않으며,
LLM을 위해 프로토콜을 즉석에서 만들어 내는 것이야말로 지금의 난장판을 만든 방식이라는 것이다.
W3C에 온갖 군더더기가 있어도 표준화 기구와 함께 일하는 것이 AI 벤더들에게 도움이 될 것이라고 맺는다.

이 반론의 힘은 글의 맺음말을 그대로 겨눈다는 데 있다.
글은 공통 프로토콜을 중심으로 표준화한 것이 인터넷을 키웠다는 문장으로 끝난다.
그런데 그 문장 바로 앞에 놓인 구체적 제안은 표준 절차를 거치지 않고 기존 필드의 의미를 겹쳐 쓰는 것이다.
MCP가 한 회사의 제안에서 출발했다는 사실을 문제 삼지 않으면서
두 사람의 대화로 정해지는 헤더 용법은 문제 삼지 않는 것이 이 글의 일관성 문제다.

### MCP가 만들어 낸 부수 효과를 계산에서 뺀다

글은 MCP의 가치를 도구 호출의 효율로만 잰다.
그런데 토론에서 반복해 나온 것은 MCP가 기술 외부에서 만든 결과들이었다.

thehamkercat는 MCP가 좋은 일 하나는 했다고 적는다.[^thehamkercat]
REST API를 제공할 생각조차 없던 수많은 웹사이트가 MCP가 인기를 얻자 MCP 서버를 노출하게 되었고,
LLM을 전혀 끼우지 않고도 그 서버를 써서 평범한 자동화를 짤 수 있다는 것이다.
jvanderbot는 같은 관찰을 자기 이해관계로 정리한다.[^jvanderbot]
MCP에 대한 기술적이고 깔끔함에 관한 반론은 타당하지만 자기가 신경 쓰는 것은 다른 것이라는 것이다.
많은 회사가 API를 갖고 있지 않았고 가질 이유도 못 느꼈는데,
틈새이거나 개발자 대상이거나 경쟁 프런트엔드를 낳을 수 있다는 이유였다.
그런데 이제 고객의 에이전트가 데이터에 접근하게 해 준다는 이유가 생겼고,
그 결과 더 많은 회사가 자기 데이터에 자기가 접근하도록 허용하게 되었으므로 순이익이라는 것이다.

가장 날카로운 관찰은 mikeocool에게서 나온다.[^mikeocool]
simonw가 든 네 가지 전부가 OpenAPI 명세를 갖춘 평범한 REST API와 표준 인증 옵션,
그리고 합리적인 API 요청 도구를 구현한 AI 클라이언트로 완벽히 가능하다고 먼저 적는다.
지금의 AI 클라이언트들이 MCP를 구현하는 것과 똑같이 말이다.
그리고 MCP의 진짜 가치는 다른 데 있었다고 말한다.
기업이 MCP 서버를 만들면서 우리는 AI를 하고 있다고 말할 수 있게 해 준 것이며,
우리 API를 쓰라는 말은 훨씬 덜 흥미로웠다는 것이다.
이름을 다르게 붙인 것이 비기술직 임원들이 API로 사용자 데이터를 여는 것은 원하지 않으면서
AI는 하고 싶어 하던 회사들에서 정치를 뚫는 데도 도움이 되었을 것이라고 덧붙인다.

이 관찰이 중요한 이유는 글의 비판이 닿지 않는 층위를 가리키기 때문이다.
어떤 프로토콜의 기능이 조직적인 것이라면, 기술적으로 불필요해졌다는 증명은 그것을 없애지 못한다.
글은 MCP가 감싸는 것이 결국 이미 존재하는 API라는 사실을 결정적 논거로 제시하는데,
mikeocool의 관찰이 맞다면 그 감싸기가 바로 존재 이유였다.
글이 산업 복합체라는 이름을 붙이면서도 그 복합체의 작동 방식을 분석하지 않은 대가가 여기서 나타난다.

### 지금 시점의 판단이 근거 없이 일반화된다

글은 모델이 이미 충분히 좋아졌다고 단정한다.
API를 직접 호출하고 본 적 없는 API도 다루며 최소한의 개입으로 작업 흐름을 만든다는 것이다.
토론에서 이 단정에 대한 실무 보고가 여러 방향에서 나왔다.

rimeice는 최전선 모델이 지금 API를 안다는 데 동의하지 않는다고 적는다.[^rimeice]
직접 해 보면 올바른 매개변수를 알아내려고 헤매면서 토큰을 태우고 컨텍스트를 부풀리는 일이 여전히 많으며,
실제 기업용 에이전트 작업에 쓰는 비용 효율적인 모델들은 확실히 추가적인 도움이 필요하고
적어도 앞으로 여섯 달은 그럴 것이라는 것이다.
여기서 나오는 구분이 중요하다.
글의 전제는 최전선 모델의 능력이고, 대부분의 생산 환경이 돌리는 것은 최전선 모델이 아니다.

cagz는 컨텍스트 논증 자체를 되돌린다.[^cagz]
MCP가 컨텍스트를 너무 쓴다고 말하지만, 에이전트가 `my_cli --help`로 시작해
스위치와 매개변수를 하나씩 따라 내려가며 CLI를 어떻게 불러야 하는지 알아내는 과정을 생각해 보라는 것이다.
잘 알려진 CLI라면 덜한 문제이지만, 대부분의 CLI는 사람이나 CI 파이프라인이 쓰도록 설계되었지 에이전트용이 아니다.
직접 접근도 마찬가지로 에이전트가 API 명세를 완전히 이해해야 하고,
점진적 공개로 컨텍스트를 아낄 수 있지만 그것은 쓸 때마다 매번 API를 다시 이해해야 한다는 뜻이라고 적는다.
그리고 API 호출에 미묘한 조건이 있을 때 그것을 어디에 적어야 하느냐고 묻는다.
OpenAPI 설명란에 넣으면 되긴 하지만 어설프다는 것이다.

LeonidBugaev의 사례가 이 논점을 완성한다.[^LeonidBugaev]
자기 앱은 도움말 페이지가 1,000개가 넘어서 그 전부를 컨텍스트에 올릴 방법이 없고 올리는 것 자체가 어리석다.
그래서 점진적 발견을 쓴다.
에이전트가 먼저 원래의 도움말 메시지를 읽어 지금 흐름의 어느 단계인지 파악하고,
오류 메시지와 여러 힌트를 통해 주제를 스스로 발견하며, 내부에 Elasticsearch 같은 검색이 있다는 것이다.
이것이 흥미로운 이유는 MCP 쪽 플랫폼들이 내놓은 검색 및 실행 패턴과 구조가 같기 때문이다.
글은 그 패턴을 MCP 산업 복합체의 증상으로 들었는데, CLI 경로에서도 같은 패턴이 다시 발명된다.

반대 경험도 기록해 둘 만하다.
doctaj는 Microsoft의 Power BI Authoring MCP로 SQL과 CSV에서 의미 모델을 만들었는데 마법 같았다고 적는다.[^doctaj]
Microsoft가 그 방법을 MCP에 정의해 두었고, 기계에 추가하는 것이 간단하며 실행이 믿을 만했다는 것이다.
대안은 모델이 문서 웹사이트에서 문서를 직접 가져오는 것으로 보이는데,
그렇다면 모든 것이 인터넷에서 특정 웹페이지를 찾는 데 달려 있게 되므로 모든 면에서 더 나빠 보인다고 적는다.

마지막으로 형식에 관한 지적 하나가 있다.
HN에 올라온 제목은 물음표로 끝나는데 원문에는 물음표가 없다.
bifftastic가 그 차이를 짚었다.[^bifftastic]
글이 단정으로 말한 것이 토론 마당에서는 질문으로 바뀌어 유통되었다는 뜻이고,
이 문서를 읽는 사람이 두 곳의 제목을 비교할 때 알아 둘 만한 사실이다.

### 최소 권한 원칙을 포기하자는 제안이라는 반론에 답이 없다

글의 처방은 MCP 서버 대부분을 지우고 터미널 접근을 가진 에이전트로 대체하라는 것이다.
이 처방에서 에이전트가 얻는 권한의 범위는 논의되지 않는다.

pixlmint가 그 점을 원칙의 이름으로 묻는다.[^pixlmint]
에이전트에 터미널 접근을 주고 싶지 않은 경우는 어떻게 하느냐는 것이며,
여기 있는 많은 사람이 작은 모델로 작업해 본 적이 없는 것 같다고 적는다.
작은 모델은 컨텍스트가 커지면 CLI 인자를 금방 혼동하고, 그러면 무슨 피해를 입힐지 알 수 없다는 것이다.
MCP를 쓰면 실제로 필요한 접근만 주게 되는데, 최소 권한 원칙은 이제 적용하고 싶지 않은 것이냐고 되묻는다.

butterNaN은 같은 것을 자기 사용법으로 보여 준다.[^butterNaN]
자기는 기존 도구를 감싸는 인가 통제 장치로 MCP를 직접 띄우며, 예를 들어 GET 요청만 할 수 있는 서버를 만든다는 것이다.
다른 방법으로도 같은 효과를 낼 수 있다는 것을 알지만 그것들은 모두 부드러운 통제로 느껴지고
단단한 제약이 하지 말라는 컨텍스트 한 줄보다 안심된다고 적는다.
그리고 글의 취지대로라면 CLI 감싸개를 쓰라고 할 수 있겠지만,
에이전트에서 도구로 바로 가는 경로보다 에이전트에서 MCP를 거쳐 도구로 가는 명시적 경로가 좋다고 말한다.
LLM이 더 똑똑해진 동시에 그 LLM을 쓰는 응용들이 사용자가 무엇을 허용하려는지를 더 많이 가정하게 되었고,
환각 한 번에 재앙이 오는 자리에 있고 싶지 않다는 것이다.

lowbloodsugar는 이 문제를 더 구체적인 결함으로 좁힌다.[^lowbloodsugar]
저자 본인이 MCP 인증도 안전하지 않다고 적은 데 대한 답인데,
그것이 대부분의 샌드박스가 가진 가장 큰 문제이고 어떤 사람들은 샌드박스조차 돌리지 않지만,
최선의 샌드박스에도 큰 문제가 있다는 것이다.
GET 동사가 쓰기 기능을 제공하는 API들이 그것이다.
MCP의 가치는 표면을 알려진 API로 최소화하고 읽기 전용과 변경을 구분해 신뢰하거나 승인하거나 차단할 수 있게 하는 데 있으며,
이 경우 MCP 서버는 읽기·쓰기나 셸이 볼 수 있는 환경에서 돌지 않는다고 적는다.

brabel은 전제 자체를 되돌린다.[^brabel]
도구가 없으면 LLM은 텍스트를 뱉는 것 말고 아무것도 못 하며,
셸 접근을 가진 하네스가 제공된다는 가정은 사용 사례에 따라 전혀 필수가 아니라는 것이다.
보안이 걱정된다면 터미널만큼의 힘을 가진 것은 주고 싶지 않고,
MCP 서버는 도구 호출 외에는 아무것도 할 수 없으므로 검토되고 감사되며 자격 증명이 LLM에 보이지 않게 보장되기에
통제된 힘을 안전하게 주기에 알맞다고 적는다.

이 반론들이 글의 처방에 가격을 붙인다.
글은 CLI 경로의 이득을 컨텍스트와 능력으로만 계산하고, 권한 범위가 넓어지는 것을 비용으로 세지 않는다.
barrkel은 그 맞교환을 명시적으로 인정하는 드문 경우다.[^barrkel]
샌드박스 없이 가는 것은 LLM의 손발을 묶어 두는 일이며, 환경을 주지 않는 것은 선택이고
멍청한 모델을 쓴다면 필요할 수 있지만 자기는 대개 그 맞교환이 값어치 있다고 보지 않는다고 적는다.
즉 이것은 답이 하나인 문제가 아니라 모델의 크기와 실패의 대가에 따라 갈리는 문제인데,
글은 한쪽 답만 제시하면서 다른 쪽 조건을 적지 않는다.

### CLI 경로가 실패할 때의 비용이 사례로 제시된다

글은 에이전트가 CLI와 API를 잘 다룬다고 단정한다.
잘 다루지 못할 때 무슨 일이 생기는지는 적지 않는다.
berkes가 그 빈자리에 실측값을 넣었다.[^berkes]

자기 MCP가 자기 실수로 내려가 있었고, 에이전트가 요청을 끝내려면 파이썬 스크립트를 만들어야 한다고 판단했다는 것이다.
그것을 리팩터링하고 디버깅한 뒤 써서 Joplin API로 자기 노트에 접근해 주간 갱신 Markdown을 쓰려 했고,
그 과정에서 400줄이 넘는 파이썬 도구와 파일 다섯 개가 나왔으며 어느 시점에는 그것을 git 저장소에 넣을까 고민하고
도커 컨테이너를 돌리는 곁가지 작업까지 갔다고 적는다.
MCP를 쓰면 이 작업은 보통 0.05달러에서 0.90달러가 드는데, 이번에는 17달러가 들고 30분 가까이 걸렸다는 것이다.
Joplin에 노트 하나 쓰는 데 말이다.

이 사례가 글의 논증을 정면으로 시험한다.
글이 제시한 대안은 에이전트가 필요할 때 스크립트를 써서 서비스를 조합하는 것이고, 그것이 정확히 여기서 일어난 일이다.
차이는 글이 그것을 능력의 증거로 들고, 이 사례는 같은 행동을 비용의 증거로 든다는 데 있다.
berkes가 끌어내는 원칙은 표준이 왜 필요한지에 대한 것이다.
대안이 매번 에이전트가 API와 CLI와 UI를 조사해 상호작용할 소프트웨어를 만들어 돌리는 것이라면,
그것은 매우 비효율적일 뿐 아니라 예측 불가능하고 종종 느리다는 것이다.

무작위성이 여기서 핵심이다.
MCP 경로의 비용은 알려진 범위 안에서 움직이고, 스크립트 작성 경로의 비용은 에이전트가 그때 무엇을 하기로 정하는지에 달린다.
한 번의 실행이 340배로 튀는 분산을 가진 경로를 생산 환경에 두는 것은 평균이 낮아도 받아들이기 어렵다.
글은 평균만 이야기하고 분산을 이야기하지 않는다.

### 제목이 물음표로 바뀐 것을 두고 책임 회피라는 지적이 나왔다

원문 제목에는 물음표가 없고 HN에 올라온 제목에는 있다는 사실은 이미 앞에서 적었다.
그 차이를 형식 문제로 넘기지 않은 반응이 있다.

yipinwong은 그것을 언론이 쓰는 장치와 같은 것으로 읽는다.[^yipinwong]
무언가를 질문으로 표현하면 사실로 주장하는 것이 아니게 되는 법적 허점이며,
어머니가 살인 용의자일 수 있느냐고 물으면 함의는 전달되지만 기술적으로는 그렇다고 말한 것이 아니라는 것이다.
그래서 언론사는 그런 제목으로 잘못된 정보에 대해 기소되지 않으며,
이 글도 같은 방식으로 질문의 틀을 씌워 저자가 함의하는 바를 자기 것으로 책임지지 않는다고 적는다.
완곡한 표현보다 더 나쁘다는 것이 결론이다.

이 지적의 사실관계는 정확하지 않다.
물음표를 붙인 것은 저자가 아니라 HN에 제출한 사람이거나 조정자이고, 원문은 단정형 제목을 그대로 쓴다.
다만 이 반응이 기록할 값이 있는 이유는 다른 데 있다.
같은 주장이 어느 마당에 놓이느냐에 따라 강도가 조정되고, 읽는 사람은 그 조정을 저자의 의도로 귀속한다는 것이다.
이 문서처럼 두 곳의 반응을 함께 다루는 글에서는 어느 제목을 인용하는지가 저자에 대한 평가를 바꾼다.

## 인사이트

### 능력이 오르면 설명 계층은 사라지지만 허가 계층은 사라지지 않는다

이 논쟁 전체에서 가장 재사용할 만한 구분이 여기 있다.
MCP는 실제로 두 가지 일을 함께 해 왔다.
하나는 모델에게 어떻게 부르는지를 알려 주는 일이고, 다른 하나는 불러도 되는지를 정하는 일이다.
스키마와 도구 설명과 발견 기제가 앞의 일이고, 자격 증명 격리와 접근 범위와 감사 기록이 뒤의 일이다.

모델의 능력이 오르면 앞의 일은 값이 떨어진다.
`--help`를 읽고 OpenAPI 명세를 해석하고 본 적 없는 API를 조합할 수 있게 되면
어떻게 부르는지를 미리 알려 주는 계층은 비용만 남는다.
글의 논증이 힘을 갖는 것이 정확히 이 지점이고, 그 부분은 옳다.

뒤의 일은 능력이 올라도 값이 떨어지지 않는다.
오히려 오른다.
더 유능한 에이전트는 더 많은 것을 할 수 있고, 할 수 있는 것이 많아질수록 해서는 안 되는 것의 목록이 중요해진다.
jimbokun의 지적이 여기서 다시 읽힌다.
접근 제어는 셸을 완전히 가진 에이전트를 견딜 수 있어야 한다는 것은,
허가 계층을 에이전트 쪽에 두면 안 된다는 뜻이지 허가 계층이 필요 없다는 뜻이 아니다.

그래서 이 논쟁의 올바른 형태는 MCP를 없앨 것이냐가 아니라 두 계층을 분리할 것이냐다.
설명 계층은 걷어 내고 허가 계층은 남기되, 그것을 프로토콜이 아니라 샌드박스와 자격 증명 브로커와 서버 측 감사로 구현하는 것이
kaoD가 말한 방향이다.
그리고 이 구분은 MCP 바깥에도 적용된다.
어떤 도구 계층이 사라질 것인지 판단할 때 물어야 할 것은 그것이 모델의 무지를 메우고 있는지,
아니면 사람의 결정을 담고 있는지다.
앞엣것은 시간이 지우고 뒤엣것은 지우지 않는다.

### 컨텍스트 예산은 사라지지 않고 자리를 옮긴다

MCP 비판의 실질적 출발점은 컨텍스트 팽창이었다.
서버를 여럿 붙이면 도구 스키마가 컨텍스트를 채운다는 것이다.
그런데 토론이 보여 준 것은 CLI 경로가 그 비용을 없애는 것이 아니라 다른 시점으로 옮긴다는 사실이다.

MCP에서는 비용이 세션 시작에 한 번 발생한다.
쓰든 쓰지 않든 도구 목록이 올라간다.
CLI에서는 비용이 사용할 때마다 발생한다.
`--help`를 읽고 하위 명령을 찾고 플래그를 확인하는 토큰이 매번 든다.
cagz가 짚은 것이 이것이고, LeonidBugaev가 만든 점진적 발견은 그 반복 비용을 줄이려는 장치다.
그리고 그 장치의 모양은 MCP 플랫폼들이 만든 검색 및 실행 패턴과 같다.

그렇다면 두 방식을 비교하는 올바른 단위는 시작 시점의 토큰 수가 아니라 완료된 작업당 총 토큰이다.
이 단위로 재면 답이 사용 양상에 따라 갈린다.
같은 도구를 한 세션에서 여러 번 쓰면 선불 비용이 분산되므로 MCP 쪽이 유리하고,
많은 도구 중 하나만 한 번 쓰면 필요할 때 발견하는 쪽이 유리하다.
글은 앞의 경우를 셈에 넣지 않고 뒤의 경우만으로 결론을 낸다.

응답 쪽의 비용도 같은 성질을 갖는다.
글 자신이 CLI가 돌려주는 기계 판독 응답이 장황하다는 것을 인정하고 고칠 방법이 있다고 넘어간다.
그 방법들이 토론에 실제로 나왔다.
tobyhinloopen는 무엇이든 출력을 붙잡아 두고 LLM이 나중에 질의하게 하는 도구 감싸개를 만들었다고 적는다.[^tobyhinloopen]
출력을 똑똑하게 잘라 내고 잘린 부분을 LLM이 펼칠 수 있게 하는 방식이며,
도구가 엄청난 양을 돌려주는 위험을 이것으로 해결한다는 것이다.
bob1029은 `curl`과 `jq`가 요즘 해법의 대부분이라고 본다.[^bob1029]
`jq` 출력에 크기 제한을 걸어 두면 에이전트가 간결한 뷰를 찾을 때까지 여러 필터로 반복하며,
이 동작을 프롬프트로 지시하거나 조율할 필요가 이제 없다는 것이다.

두 해법 모두 공통점이 있다.
장황함을 없애는 것이 아니라, 무엇을 볼지 에이전트가 정하게 만들어 비용을 요구 시점으로 미루는 것이다.
즉 컨텍스트 논쟁의 실제 내용은 총량이 아니라 지연 여부다.
어떤 계층을 평가할 때 그것이 비용을 없애는지 미루는지를 구분하면, 낡았다는 판정을 훨씬 정확하게 내릴 수 있다.

### 프로토콜의 수명은 기술적 우열이 아니라 그것이 해결한 조직 문제가 정한다

글의 결론은 수명 종료다.
그리고 토론에서 나온 가장 설득력 있는 반론은 기술적인 것이 아니었다.
mikeocool의 관찰, 즉 MCP의 진짜 가치가 기업이 AI를 하고 있다고 말할 수 있게 해 준 데 있었다는 것이다.

이 관찰을 진지하게 받아들이면 예측이 달라진다.
기술적으로 불필요해진 것이 사라지려면 그것이 맡고 있던 비기술적 기능이 다른 것으로 옮겨 가야 한다.
MCP의 경우 그 기능은 세 가지쯤으로 보인다.
비개발자에게 설치 가능한 단위를 주는 것, 조직 내부에서 데이터 개방을 정당화하는 이름을 주는 것,
그리고 벤더가 자기 서비스를 에이전트 생태계에 올리는 배포 경로를 주는 것이다.
whazor가 말한 플러그인 스토어가 첫 번째와 세 번째를 이미 맡고 있고,
kaoD가 예상한 스킬 마켓플레이스가 같은 자리를 노린다.

역사에도 같은 형태가 있다.
SOAP과 WS-* 계열이 REST에 밀린 것은 기술 논쟁에서 진 뒤가 아니라,
그 계열이 맡고 있던 기업 간 계약과 도구 지원과 조달 정당화의 기능을
다른 것들이 충분히 대신하게 된 뒤였다.
그 전까지는 더 단순한 방식이 있다는 사실이 여러 해 동안 알려져 있었는데도 바뀌지 않았다.
themythfable가 MCP를 JavaScript에 빗대며 때로는 근본보다 채택과 가용성이 중요하다고 적은 것이 같은 관찰이다.[^themythfable]

여기서 나오는 실무적 함의는 방향을 바꾼다.
어떤 기술을 걷어 내고 싶다면 그것이 기술적으로 열등하다는 논증은 거의 쓸모가 없다.
그것이 조직에서 무슨 일을 대신하고 있었는지를 먼저 찾아, 그 일을 다른 것이 더 잘하게 만들어야 한다.
이 글이 설득력 있는 기술 논증을 갖고도 수명 종료를 불러오지 못할 것이라 보는 이유가 이것이다.

### 응답 형식을 자유롭게 고르는 것이 컨텍스트 절약의 실질적 수단이다

컨텍스트 논쟁은 대개 도구 스키마의 개수를 두고 벌어진다.
그런데 토론에서 나온 가장 실용적인 절약 수단은 스키마가 아니라 응답 쪽에 있었다.

cruffle_duffle는 자기 MCP 서버들에서 CSV나 표 형태 데이터, 때로는 옛날식 평문 템플릿을 돌려주는 방식으로
토큰 수를 크게 줄였다고 적는다.[^cruffle_duffle-json]
JSON은 반복이 심해서 어떤 경우에는 응답 토큰의 30퍼센트 이상이 JSON 상용구였다는 것이다.
그리고 그 이유를 한 문장으로 정리한다.
LLM에게 JSON은 XML이나 Markdown이나 구두점 없는 의식의 흐름과 다를 바 없는 토큰의 흐름일 뿐이라는 것을 깨닫고 나면,
자기만의 이상한 형식을 만들지 않을 이유가 없다는 것을 알게 된다는 것이다.
MCP가 JSON이 아닌 것을 돌려줘도 LLM은 파싱 오류를 내지 않으며,
문법적으로 올바른 JSON을 돌려주는 것보다 도구 설명과 매개변수 설명이 무엇을 하고 무엇을 하지 않는지를
제대로 알리는 일이 훨씬 중요하다고 적는다.

이 관찰이 글의 한 대목을 되돌린다.
글은 CLI가 돌려주는 JSON이나 XML이 장황해서 토큰을 많이 쓴다는 것을 남은 문제로 인정하고 고칠 방법이 있다고 넘어갔다.
그 문제는 CLI 고유의 것이 아니라 기계 판독 형식 일반의 것이고,
apf6이 지적한 대로 MCP 쪽에서도 같은 방법으로 해결된다.[^apf6]
즉 이것은 두 방식을 가르는 축이 아니라 양쪽에 공통인 구현 품질의 문제다.

여기서 나오는 일반 원칙은 형식 선택의 자유를 어디까지 쓸 수 있는지에 대한 것이다.
사람과 기계가 함께 읽는 인터페이스에서는 형식이 계약이므로 바꿀 수 없다.
LLM만 읽는 인터페이스에서는 형식이 계약이 아니라 토큰 예산의 문제가 되고, 그러면 가장 짧게 뜻이 전달되는 형태가 최적이다.
cruffle_duffle가 버전 관리에 대해 덧붙인 말이 같은 논리의 연장이다.
도구 계약 수준에서 MCP에는 말할 만한 하위 호환성이 없고, 도구가 실제로 무엇을 하는지는 다른 층위의 문제라는 것이다.

### 에이전트를 위한 인터페이스는 새 프로토콜이 아니라 오래된 규율의 재발견으로 수렴한다

글의 제안은 에이전트가 HTTP API를 직접 쓰는 방식을 표준화하자는 것이다.
토론에서 여러 사람이 그 제안에 동의하면서, 그것이 새로운 것이 아니라는 점을 지적했다.

_heimdall은 그 지적을 가장 멀리 끌고 간다.[^_heimdall]
에이전트에게 필요한 것은 REST API이며, 20년 넘게 만들어 온 JSON RPC API가 아니라 진짜 REST라는 것이다.
REST를 버리지 않았다면 자기 문서화가 되고 타입과 스키마를 갖춘 API가 여전히 있었을 것이고,
브라우저가 XSLT를 계속 지원했다면 같은 API를 XML로 쓰고 시각적 표현이 필요한 브라우저만 HTML 템플릿을 불러오며
에이전트는 원시 XML을 쓸 수 있었을 것이라고 적는다.
이어지는 글에서 시점을 더 앞으로 옮긴다.[^_heimdall-soap]
MCP는 25년 전 REST API의 좋은 부분을 다시 만들려는 시도이며,
SOAP은 괴로웠고 XML을 싫어한 사람이 많았지만 그 계열이 정확히 이 문제들을 풀었다는 것이다.
지금은 그 기능들을 근본적으로 지원하지 않는 플랫폼에 억지로 얹고 있으며,
현대 웹 프레임워크가 RPC 호출을 빌드 단계에 넣고 상태와 렌더링을 클라이언트와 서버에 나누는 동안
에이전트를 위한 새 API 맥락을 세우고 새 기능마다 문서와 유지보수로 발을 맞춰야 하는 처지가 되었다고 적는다.

flohofwoe는 반대편 끝의 사례로 같은 결론에 닿는다.[^flohofwoe]
원격 제어 접근점이 아예 없는 UI 응용, 예를 들어 게임 엔진 에디터를 원격 제어하는 데는
MCP 서버가 여전히 많은 의미가 있지 않느냐고 묻는다.
AmigaOS 식의 스크립팅 포트도 똑같이 잘 작동할 것이고 MCP 서버가 본질적으로 그것,
즉 발견 가능한 명령 프로토콜을 구현한 소켓이라는 것이다.
그러면서 모든 응용과 서비스가 스크립팅과 원격 제어에 대한 표준에 합의하면 좋겠고,
AI 열풍이 거기에 도달하는 데 필요한 것이라면 그래도 좋다고 적는다.

이 두 방향이 같은 것을 가리킨다.
에이전트용 인터페이스에 요구되는 성질은 새로 발명된 것이 아니다.
자기 기술적이고, 발견 가능하고, 타입이 있고, 사람이 읽는 표현과 기계가 읽는 표현이 분리되어 있어야 한다는 것이며,
이것들은 REST와 SOAP과 스크립팅 포트가 각자의 방식으로 이미 풀었던 요구다.
그렇다면 지금 벌어지는 일의 이름은 새 프로토콜의 등장이 아니라 잊힌 규율의 재발견에 가깝고,
그 관점에서 보면 MCP와 글의 제안은 경쟁하는 두 진영이 아니라 같은 요구에 대한 두 개의 부분적 답이다.
앞의 통찰에서 적은 것처럼 어떤 계층이 사라질지를 판단하려면 그것이 무슨 요구를 맡고 있는지를 먼저 보아야 하는데,
이 요구들은 모델이 좋아진다고 사라지는 종류가 아니다.

### 에이전트를 겨냥해 새로 만든 CLI가 두 진영의 실질적 수렴점이다

논쟁은 MCP 대 CLI로 놓였지만, 토론에서 가장 자주 언급된 실제 해법은 제3의 것이었다.
에이전트를 염두에 두고 새로 설계한 CLI다.

wetpaste는 그것을 가장 흥미로운 중간 지대라고 부른다.[^wetpaste]
Grafana가 `grafanactl`을 대체한 `gcx`라는 새 CLI를 내놓았고,
자기는 원래 MCP 서버를 썼는데 컨텍스트 팽창과 MCP의 제약에 부딪힌 뒤 이것을 찾았으며
에이전트에게 훌륭한 인터페이스로 보이고 관측성 작업을 거침없이 해낸다는 것이다.
ex1fm3ta는 같은 판단을 자기 손으로 구현했다.[^ex1fm3ta]
Jira와 GitLab MCP가 토큰을 지나치게 쓰는 것을 보고 각각의 CLI를 설치했으며,
코딩 에이전트가 특정 작업 항목 필드를 가져오는 방법을 매번 다시 발견하느라 자원을 낭비하게 두는 대신
Claude에게 CLI에 재귀적으로 `--help`를 돌려 가능한 모든 동작을 별도 Markdown 파일로 저장하게 했다는 것이다.
그렇게 해서 MCP가 해야 할 일을 훨씬 적은 토큰으로 하는 가벼운 플러그인 둘을 만들어 공개했다고 적는다.

qalmakka는 이 수렴을 규범으로 바꾼다.[^qalmakka]
CLI의 가장 큰 장점은 사람도 쓸 수 있다는 것이며 그래서 범용 도구라는 것이다.
자기가 싫어하는 것은 사람들이 쓸만한 것에 MCP 서버만 쓰고 끝내는 일이며,
같은 Claude나 Codex 인스턴스에 같은 기능을 CLI로도 노출하라고 시키면 되지 않느냐고 적는다.

shibel의 사례는 이 수렴이 어디서 오는지를 보여 준다.[^shibel]
Linear MCP의 과도한 토큰 사용 때문에 CLI로 옮겼다고 적으면서,
컨텍스트 절약이 앞서 열거된 이점들을 Linear의 경우에는 능가한다고 본다.
그리고 곧바로 단서를 붙인다.
이것은 MCP 대 API/CLI 일반에 대해 아무것도 말해 주지 않으며 Linear의 나쁜 구현일 뿐이라는 것이다.
w0m은 반대 경험을 보고한다.[^w0m]
제대로 만든 효율적인 MCP로 훨씬 나은 토큰 사용량을 얻었고,
사용법을 깊이 정의한 스킬이 있어도 MCP 결과를 파싱하는 것이 CLI 결과를 파싱하는 것보다 대체로 효율적이었다는 것이며,
하네스 사용을 겨냥해 CLI 도구를 직접 쓴 경험과 같은 일에 MCP를 쓴 경험을 모두 가지고 하는 말이라고 적는다.
그러면서 더 나은 연구가 있으면 궁금하다고 맺는다.

세 보고를 나란히 놓으면 결론이 하나로 모인다.
측정된 차이는 프로토콜의 차이가 아니라 구현의 차이였다.
Linear MCP가 비싼 것은 MCP가 비싸기 때문이 아니고, `gcx`가 좋은 것은 CLI가 좋기 때문이 아니다.
양쪽 모두 에이전트가 무엇을 언제 필요로 하는지를 고려해 설계했는지가 비용을 정했다.
그렇다면 이 논쟁에서 실천으로 옮길 수 있는 문장은 어느 쪽을 지우라는 것이 아니라,
지금 쓰는 인터페이스가 사람을 위해 설계된 것인지 에이전트를 위해 설계된 것인지를 확인하라는 것이다.

### 표준을 우회하는 관습은 나중에 더 비싼 표준화를 부른다

글의 제안 중 하나는 성사되었고 하나는 논란이 되었다.
`Accept: text/markdown`은 이미 표준화된 미디어 타입을 그 용도대로 쓰는 것이므로 마찰이 없었고,
`Accept-Language`에 프로그래밍 언어를 넣자는 제안은 기존 필드에 새 축을 겹치는 것이므로 반발을 샀다.
이 대비 자체가 규칙을 준다.

콘텐츠 협상 필드가 여럿으로 나뉘어 있는 것은 축이 여럿이기 때문이다.
미디어 타입, 문자 집합, 인코딩, 자연어가 각각 다른 필드를 갖는 이유는
어느 하나가 바뀌어도 나머지의 의미가 흔들리지 않게 하려는 것이다.
한 필드에 두 축을 넣으면 그 필드를 해석하는 모든 중간 계층이 두 해석 중 하나를 골라야 하고,
캐시 키와 `Vary` 처리와 프록시 동작이 구현마다 갈린다.
`User-Agent` 문자열이 어떻게 되었는지가 그 결말의 잘 알려진 예다.
모두가 서로를 흉내 내다가 결국 아무 정보도 담지 못하는 문자열이 되었고,
그것을 정리하려는 시도가 20년 뒤에 훨씬 비싸게 시작되었다.

그래서 새로운 협상 축이 필요하다면 새 필드를 요청하는 것이 맞고,
그 절차가 느리다면 graypegg가 말한 대로 그동안은 URL에 두는 것이 맞다.
URL에 두면 자원이 다르다는 사실이 주소에 드러나고, 캐시와 링크와 북마크가 전부 정상 작동한다.
헤더로 숨기면 같은 주소가 클라이언트에 따라 다른 것을 돌려주는 상태가 되어, 디버깅과 캐싱이 모두 어려워진다.

이 원칙이 이 글의 논지와 만나는 지점이 있다.
MCP를 비판하는 근거 중 하나가 이미 있는 것 위에 새 층을 얹었다는 것이었다.
같은 기준을 제안에도 적용하면, 이미 있는 헤더의 의미를 늘리는 것도 같은 종류의 비용을 만든다.
프로토콜을 줄이자는 주장이 설득력을 가지려면 그 주장이 제안하는 것 역시 줄이는 쪽이어야 한다.
