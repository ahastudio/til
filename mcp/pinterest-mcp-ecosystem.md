# Pinterest가 사내에 MCP 생태계를 만든 방법

원문: [Building an MCP Ecosystem at Pinterest](https://medium.com/pinterest-engineering/building-an-mcp-ecosystem-at-pinterest-d881eb4c16f1)

## 요약

Pinterest의 Agent Foundations 소프트웨어 엔지니어 Tan Wang이 2026년 3월 19일에 Pinterest 엔지니어링 블로그에 쓴 글이다.
지난 1년 동안 MCP가 흥미로워 보인다는 단계에서 MCP 서버 생태계와 중앙 레지스트리, 그리고 IDE·사내 채팅·AI 에이전트에 들어간 프로덕션 통합까지 왔다고 정리한다.

MCP(Model Context Protocol)는 대규모 언어 모델이 모델마다 도구마다 일회성 통합을 만드는 대신 통일된 클라이언트-서버 프로토콜로 도구와 데이터 소스에 접근하게 해주는 오픈소스 표준이다.
Pinterest는 MCP를 질문에 답하는 수준이 아니라 엔지니어링 작업을 안전하게 자동화하는 AI 에이전트의 기반으로 쓴다 — 로그를 읽고 무엇이 잘못되었는지 말해달라는 것부터 버그 티켓을 조사해 수정 PR을 제안하는 것까지다.

### 초기 아키텍처

MCP는 노트북이나 개인 클라우드 개발 상자에서 stdio로 통신하는 로컬 서버를 지원하지만, Pinterest는 사내 라우팅과 보안 로직을 가장 잘 적용할 수 있는 사내 클라우드 호스팅 MCP 서버에 명시적으로 최적화했다.
로컬 서버는 실험용으로 여전히 가능하지만, 포장된 길(paved path)은 서버를 작성하고 클라우드 컴퓨트 환경에 배포한 뒤 레지스트리에 등록하는 것이다.

단일 거대 서버와 여러 도메인별 서버를 두고 논의한 끝에 후자를 골랐다 — Presto, Spark, Airflow처럼 각 MCP 서버가 작고 일관된 도구 집합을 소유하는 방식이다.
서버별로 다른 접근 통제를 적용할 수 있고 모델의 컨텍스트를 붐비게 하지 않는다는 것이 이유다.
초기에 받은 흔한 피드백은 새 MCP 서버를 띄우는 데 일이 너무 많다는 것이었다 — 비즈니스 로직을 쓰기도 전에 배포 파이프라인, 서비스 설정, 운영 준비가 필요했다.
그래서 모든 MCP 서버의 인프라를 처리하는 통합 배포 파이프라인을 만들었고, 팀이 도구를 정의하면 플랫폼이 배포와 확장을 맡아 도메인 전문가가 배포 메커니즘 대신 비즈니스 로직에 집중하게 했다.

MCP 레지스트리는 어떤 MCP 서버가 승인되었고 어떻게 연결하는지에 대한 단일 진실 공급원이며 두 청중을 상대한다.
웹 UI는 사람이 서버와 소유 팀, 대응하는 지원 채널, 보안 상태를 찾아보게 하고 서버의 실시간 상태와 노출된 도구도 보여준다.
API는 AI 클라이언트(사내 AI 채팅 플랫폼, 사내 커뮤니케이션 플랫폼의 AI 에이전트, IDE 통합)가 서버를 발견하고 검증하게 하며, 사내 서비스가 에이전트를 호출하기 전에 이 사용자가 서버 X를 써도 되는가를 묻게 한다.
이것이 거버넌스의 근간이기도 하다 — 여기 등록된 서버만 프로덕션 사용 승인으로 간주된다.

### 출시한 것들

실제 고충을 해결하는 소수의 고레버리지 MCP 서버를 먼저 심고 다른 팀이 그 위에 쌓게 했다.
사용량 기준 대표 사례는 세 가지다.
Presto MCP 서버는 일관되게 트래픽이 가장 많으며, 에이전트(AI 지원 IDE 포함)가 대시보드로 맥락을 전환하는 대신 Presto 기반 데이터를 즉시 워크플로 안으로 끌어오게 한다.
Spark MCP 서버는 AI Spark 디버깅 경험의 바탕으로, Spark 작업 실패를 진단하고 로그를 요약하고 구조화된 근본 원인 분석을 기록하도록 도와 시끄러운 운영 스레드를 재사용 가능한 지식으로 바꾼다.
Knowledge MCP 서버는 범용 지식 엔드포인트로, 사내 AI 봇이 회사 지식과 Q&A에 쓰고 다른 에이전트가 사내 여러 출처의 문서·디버깅 질문에 답하는 데 쓴다.

통합은 엔지니어가 이미 일하는 곳에 나타나야 했다.
대다수 Pinterest 직원이 매일 쓰는 사내 LLM 웹 채팅 인터페이스는 필요한 경우 OAuth 흐름을 자동으로 수행하고 현재 사용자가 쓸 수 있는 도구 목록을 보안 정책에 맞춰 돌려준다.
연결되면 AI 채팅 에이전트가 MCP 도구를 자기 도구 집합에 직접 묶으므로 MCP 호출이 다른 도구 호출과 다르지 않게 느껴진다.
사내 채팅 플랫폼에 들어간 AI 봇도 레지스트리 API로 인증·인가를 처리하며, 특정 MCP 도구를 특정 채널로 제한하는 기능도 지원한다 — 예를 들어 Spark MCP 도구는 Airflow 지원 채널에서만 쓸 수 있다.

### 보안과 거버넌스

AI 에이전트가 실제 시스템과 데이터를 건드리는 도구를 호출하게 하는 일에는 명백한 보안 질문이 따르므로, MCP를 처음부터 보안 팀과의 공동 프로젝트로 다뤘다.
전용 MCP 보안 표준을 정의했고, 일회성 실험이 아닌 모든 MCP 서버는 소유 팀이 있어야 하고 사내 레지스트리에 등재되어야 하며 리뷰를 거쳐야 한다 — 보안, 법무/프라이버시, 해당되는 경우 GenAI 리뷰 티켓이 생성되고 프로덕션 사용 전에 승인되어야 한다.
이 리뷰들이 서버 주변에 적용될 보안 정책, 예컨대 어떤 사용자 그룹으로 접근을 제한할지를 결정한다.

런타임에서 거의 모든 MCP 호출은 두 겹의 인증을 거친다 — 최종 사용자 JWT와 메시 아이덴티티다.
최종 사용자 흐름은 이렇다.
사용자가 웹 AI 채팅 인터페이스나 IDE 플러그인이나 AI 봇 같은 표면과 상호작용하면, 클라이언트가 사내 인증 스택에 OAuth 흐름을 수행하고 그 결과 JWT를 MCP 레지스트리와 대상 MCP 서버에 연결할 때 보낸다.
Envoy가 JWT를 검증해 `X-Forwarded-User`, `X-Forwarded-Groups` 등의 헤더로 매핑하고 거친 단위의 보안 정책을 강제한다 — 예를 들어 프로덕션의 AI 채팅 웹앱은 Presto MCP 서버와 통신할 수 있지만 dev 네임스페이스의 실험용 MCP 서버와는 안 된다는 식이다.
서버 안에서는 도구가 가벼운 `@authorize_tool(policy='…')` 데코레이터로 더 세밀한 규칙을 강제한다 — 서버 자체는 다른 조직에서 접근 가능하더라도 `get_revenue_metrics`는 광고 엔지니어링 그룹만 호출할 수 있게 하는 식이다.

Presto MCP 서버처럼 민감한 사내 데이터 시스템에 질의를 실행할 수 있는 서버에는 비즈니스 그룹 기반 접근 게이팅을 적용했다.
인증된 모든 Pinterest 직원과 계약자에게 접근을 주는 대신, 사용자 JWT에서 비즈니스 그룹 소속을 추출하고, 연결을 받아들이기 전에 승인된 그룹에 속하는지 검증하며(승인 그룹 목록은 초기 리뷰 단계에서 정해진다), 데이터 접근이 필요한 역할의 사용자에게만 선택적으로 기능을 활성화한다.
그 결과 Presto MCP 서버가 기술적으로는 LLM 웹 채팅 같은 넓은 표면에서 도달 가능하더라도 광고·재무·특정 인프라 팀처럼 승인된 비즈니스 그룹만 세션을 맺고 고권한 도구를 실행할 수 있다 — 강력하고 데이터가 많은 MCP 서버를 인기 있는 표면에 켠다고 해서 민감 데이터를 볼 수 있는 사람이 조용히 늘어나지 않는다는 것이다.
일부 서버는 도구 발견에도 유효한 JWT를 요구하는데, 그러면 모든 호출에 사용자 수준 귀속이 생겨 로그를 볼 때 누가 무엇을 했는지 따지기 깔끔해진다.

위험이 낮은 읽기 전용 시나리오에는 SPIFFE 기반 인증(메시 아이덴티티만)을 쓸 수 있다.
사내 서비스 메시가 여전히 보안 정책을 강제하지만 서버는 사람의 JWT 대신 호출 서비스의 메시 아이덴티티로 인가하며, 이 패턴은 최종 사용자가 개입하지 않고 폭발 반경이 좁게 제한된 경우로 한정한다.

MCP 명세는 사용자가 각 MCP 서버에 명시적으로 인증하는 OAuth 2.0 인가 흐름을 정의하며 보통 동의 화면과 서버별 토큰 관리를 수반한다.
Pinterest의 방식은 다르다 — 사용자는 AI 채팅 인터페이스 같은 표면을 열 때 이미 사내 인증 스택에 인증했으므로 그 기존 세션에 얹어 간다.
MCP 도구를 호출할 때 추가 로그인 프롬프트나 동의 대화상자가 없고, Envoy와 정책 데코레이터가 배후에서 투명하게 인가를 처리해 서버별 인가 흐름의 복잡성을 최종 사용자에게 드러내지 않으면서 누가 어떤 도구를 호출할 수 있는지를 세밀하게 통제한다.

MCP 서버가 자동화된 행동을 가능하게 하므로 사람이 직접 이 도구들을 다룰 때보다 폭발 반경이 크다.
그래서 에이전트 지침은 민감하거나 비싼 행동 전에 사람이 개입할 것을 의무화한다 — 에이전트가 MCP 도구로 행동을 제안하고 사람이 (선택적으로 일괄로) 승인하거나 거부한 뒤 실행한다.
위험한 행동은 elicitation으로 확인하며, 실제로는 테이블 데이터를 덮어쓰는 변경을 적용하기 전에 AI 에이전트가 확인을 요청하는 형태다.

### 관측과 성공 지표

MCP가 블랙박스가 되지 않도록 처음부터 측정되고 관측되도록 설계했다.
모든 MCP 서버는 입출력 로깅, 호출 횟수, 예외 추적, 영향 분석용 텔레메트리를 기본 제공하는 라이브러리 함수 집합을 쓴다.
생태계 수준에서는 등록된 MCP 서버와 도구의 수, 전체 서버의 호출 수, 서버 소유자가 메타데이터로 제공하는 호출당 예상 절감 시간을 측정한다.

이것들이 하나의 북극성 지표인 절감 시간으로 모인다.
각 도구에 대해 소유자가 호출당 절감 분(minutes saved per invocation)의 방향성 추정치를 가벼운 사용자 피드백과 이전 수동 워크플로 비교를 근거로 제공하고, 호출 수와 결합해 영향의 자릿수 수준 그림을 얻어 가치의 방향성 신호로 취급한다.
2025년 1월 기준 MCP 서버는 월 66,000회 호출, 월간 활성 사용자 844명까지 올라왔고, 이 추정치로 계산하면 MCP 도구가 월 7,000시간 수준을 절약하고 있다.

결론에서는 사내 클라우드 호스팅, 도메인별 다중 MCP 서버, 중앙 레지스트리라는 아키텍처를 명시적으로 선택해 AI 에이전트를 위한 유연하고 안전한 기반을 만들었다고 정리한다.
JWT와 메시 아이덴티티의 두 겹 인가 모델, 전용 MCP 보안 표준, Presto 같은 민감 서버의 비즈니스 그룹 기반 게이팅이 최소 권한과 완전한 감사 가능성을 보장한다고 말한다.
앞으로 MCP 서버를 더 늘리고 더 많은 엔지니어링 표면에 통합을 깊게 하며 거버넌스 모델을 다듬겠다는 계획으로 맺는다.

## 분석

### 이 글의 핵심 결정은 MCP 표준의 인가 모델을 버린 것이다

MCP 명세는 사용자가 각 서버에 OAuth로 인증하고 동의 화면을 보고 서버별 토큰을 관리하는 흐름을 정의한다.
Pinterest는 이를 쓰지 않고 기존 사내 세션에 얹었다.

이 결정이 글에서 가장 논쟁적인 부분이고, 동시에 가장 잘 설명된 부분이다.
사내 환경에서 서버별 동의 화면은 마찰이지 보안이 아니다 — 사용자는 이미 회사 SSO로 인증했고, 어떤 도구에 접근할 수 있는지는 사용자의 동의가 아니라 조직의 정책이 정한다.
동의 모델은 서로 신뢰하지 않는 당사자 사이에서 의미가 있는데, 사내에서는 그 전제가 성립하지 않는다.

그래서 인가가 Envoy(거친 단위)와 데코레이터(세밀한 단위)의 두 층으로 옮겨간다.
이 배치는 사내 마이크로서비스에서 이미 검증된 패턴이며, MCP를 위해 새로 발명한 것이 아니라 기존 인프라에 MCP를 끼워 넣은 것이다.
글이 명시하지 않는 함의는 이것이 이식 불가능하다는 점이다 — 서비스 메시와 사내 인증 스택과 Envoy 정책 계층이 이미 있는 조직만 이 길을 갈 수 있다.

### 레지스트리가 카탈로그가 아니라 정책 결정 지점이다

레지스트리는 흔히 검색용 목록으로 이해된다.
그런데 이 글에서 레지스트리는 사내 서비스가 이 사용자가 서버 X를 써도 되는가를 묻는 곳이고, 여기 등록된 서버만 프로덕션 사용 승인으로 간주된다.

즉 레지스트리는 조회 대상이면서 동시에 인가 판단의 근거이고, 등록 여부가 곧 승인 여부다.
이 이중 역할이 거버넌스를 단순하게 만든다 — 승인 절차와 발견 경로가 같은 시스템을 통과하므로, 승인받지 않은 서버는 발견되지도 않고 발견되지 않으면 호출되지도 않는다.

이 설계의 힘은 강제력이 자연스럽다는 데 있다.
별도의 감사나 정책 검사 없이 등록 절차를 통과하지 못한 서버는 생태계에 존재하지 않게 되고, 그러면 규칙을 어기는 것보다 지키는 것이 쉬워진다.
반대로 이 설계의 취약점도 같은 곳에 있다 — 레지스트리가 죽으면 도구 발견과 인가가 동시에 멈춘다.
글은 레지스트리의 가용성이나 캐싱 전략을 전혀 다루지 않는다.

### 여러 작은 서버를 고른 이유 중 하나는 모델의 한계다

단일 서버 대신 도메인별 다중 서버를 고른 이유로 글은 두 가지를 든다 — 서버별로 다른 접근 통제를 적용할 수 있다는 것과 모델의 컨텍스트를 붐비게 하지 않는다는 것이다.

두 번째 이유가 흥미롭다.
이는 소프트웨어 아키텍처의 근거가 아니라 모델 한계의 근거다.
도구 정의가 컨텍스트를 차지하고 도구가 많아지면 모델의 선택 정확도가 떨어지므로, 서버 분할이 사실상 컨텍스트 예산 관리 수단이 된 것이다.

이 근거는 시간이 지나면 약해질 수 있다.
컨텍스트 창이 커지고 도구 선택 능력이 개선되면 컨텍스트를 붐비게 한다는 이유는 사라지고, 접근 통제 이유만 남는다.
그러면 서버 경계가 조직 경계와 정확히 일치해야 할 이유도 약해지는데, 이미 배포된 수십 개 서버를 재구성하는 비용은 그때도 그대로다.
모델의 현재 한계에 맞춰 아키텍처를 나눈 결정은 그 한계가 사라진 뒤에도 남는다는 점을 글은 고려하지 않는다.

## 비평

### 북극성 지표가 소유자의 자기 신고 추정치다

절감 시간이라는 단일 지표는 각 도구 소유자가 제공하는 호출당 절감 분 추정치와 호출 수의 곱이다.
글은 이를 방향성 신호이자 자릿수 수준 그림이라고 신중하게 표현하지만, 결론에서는 월 7,000시간 절감이라는 수치를 성과로 제시한다.

이 지표의 문제는 조작 가능성이 아니라 구조에 있다.
추정치를 제공하는 사람이 그 도구의 성공으로 평가받는 사람과 같다.
그리고 호출 수는 자동 집계되므로 정확한데 절감 분은 추정이므로, 곱의 정밀도는 낮은 쪽에 지배되지만 결과는 정확한 숫자처럼 보인다.
월 7,000시간은 66,000회 호출에 호출당 약 6.4분을 곱한 값인데, 6.4분이라는 값이 어디서 왔는지는 검증 불가능하다.

더 근본적인 문제는 이 지표가 대체 시나리오를 가정한다는 점이다.
호출당 절감 분은 이전 수동 워크플로와의 비교인데, MCP가 없었다면 그 작업의 상당수는 아예 일어나지 않았을 가능성이 크다.
데이터를 쉽게 가져올 수 있게 되면 사람들은 예전에 하지 않던 조회를 하게 되고, 그 조회의 시간 절감은 0이 아니라 정의되지 않는다.
새로 생긴 수요를 절감으로 계산하면 지표는 도구가 쓰일수록 커지지만 그것이 조직의 산출을 늘렸다는 증거는 되지 못한다.

### 사용자 수와 호출 수의 규모가 결론의 크기와 맞지 않는다

월간 활성 사용자 844명, 월 66,000회 호출.
사용자당 월 78회, 근무일 기준 하루 4회 남짓이다.
글은 이를 프로덕션 준비된 견고한 생태계라 부르고 대다수 직원이 매일 쓰는 채팅 인터페이스에 통합되었다고 말한다.

두 서술이 어긋난다.
대다수 직원이 매일 쓰는 표면에 통합되어 있는데 MCP를 실제로 쓰는 사람은 844명이라면, 통합의 도달률과 채택률 사이에 큰 간격이 있다는 뜻이다.
그 간격이 왜 생기는지 — 접근 게이팅 때문인지, 도구가 유용하지 않아서인지, 사람들이 존재를 몰라서인지 — 가 이 글에서 가장 알고 싶은 정보인데 다루어지지 않는다.

날짜 표기도 혼란스럽다.
글은 2026년 3월에 발행되었는데 지표는 2025년 1월 기준이라고 적혀 있다.
1년 이상 지난 수치를 성과로 제시했거나 연도 오기이거나 둘 중 하나이며, 어느 쪽이든 이 글의 유일한 정량적 근거의 신뢰도를 떨어뜨린다.

### 사람 개입 의무화가 원칙으로만 서술된다

에이전트 지침이 민감하거나 비싼 행동 전에 사람 개입을 의무화한다고 하는데, 무엇이 민감하거나 비싼지를 누가 어떻게 정하는지가 없다.
도구 정의에 위험도 플래그가 있는지, 서버 소유자가 표시하는지, 리뷰에서 정해지는지, 아니면 에이전트의 판단에 맡기는지가 모두 열려 있다.

이 공백이 중요한 이유는 이 층이 마지막 방어선이기 때문이다.
Envoy와 데코레이터는 누가 무엇을 호출할 수 있는지를 통제하지만, 권한이 있는 사용자가 에이전트를 통해 파괴적인 작업을 하는 것은 막지 못한다.
테이블 데이터 덮어쓰기 전에 확인을 요청한다는 예시는 좋지만, 그 확인이 도구 수준의 선언인지 에이전트의 재량인지에 따라 보장의 성격이 완전히 달라진다.

그리고 일괄 승인(optionally in batches)이라는 표현은 이 방어선의 실효성을 스스로 약화시킨다.
사람이 개별 행동을 검토하는 것과 20개를 한 번에 승인하는 것은 다른 통제이고, 후자는 실무에서 빠르게 형식적 절차가 된다.
승인 피로는 예측 가능한 실패 모드인데 글에는 그에 대한 대비가 없다.

### 조직 구조를 전제로 한 해법이 표준의 문제로 서술된다

MCP 표준의 OAuth 흐름을 대체한 대목에서, 글은 자기 방식이 최종 사용자에게 복잡성을 드러내지 않는다는 점을 장점으로 든다.
그런데 이 비교는 공정하지 않다.

MCP의 OAuth 흐름은 서로 다른 조직이 운영하는 서버에 접속하는 상황을 위한 것이고, 사내 서버만 쓰는 환경을 위한 것이 아니다.
동의 화면이 존재하는 이유는 사용자가 자기 데이터에 대한 접근 권한을 제3자에게 위임한다는 사실을 알아야 하기 때문인데, 사내 도구에는 위임할 제3자가 없다.
즉 Pinterest가 발견한 것은 표준의 결함이 아니라 표준의 적용 범위 밖이었다는 사실이다.

이 구분이 중요한 이유는 다른 조직이 이 글을 읽고 표준 OAuth를 건너뛰어도 된다고 결론 내릴 수 있기 때문이다.
외부 MCP 서버를 하나라도 붙이는 순간 같은 논리는 성립하지 않고, 그때는 동의 흐름과 서버별 토큰 관리가 필요해진다.
그리고 사내 생태계가 커질수록 외부 서버를 붙이고 싶은 요구는 반드시 생긴다 — 글은 이 미래를 언급하지 않는다.

## 인사이트

### 도구 접근을 표준화하면 병목이 프로토콜에서 승인 절차로 옮겨간다

MCP의 약속은 M개 모델과 N개 도구의 조합 문제를 M+N으로 줄이는 것이다.
Pinterest는 그 약속을 실현했고, 그러자 새 병목이 드러났다 — 보안·법무/프라이버시·GenAI 세 종류의 리뷰 티켓이다.

통합 비용이 높을 때는 아무도 통합을 많이 만들지 않으므로 승인이 병목이 되지 않는다.
통합 비용이 0에 가까워지면 만들려는 서버가 급증하고, 그때 각 서버가 세 개의 리뷰를 통과해야 한다면 리뷰 대기열이 전체 속도를 정한다.
글이 배포 파이프라인을 통합해 배포 마찰을 없앤 것은 바로 이 문제 인식에서 나왔지만, 리뷰 쪽에 대해서는 같은 자동화를 하지 않았다.

이 관찰은 플랫폼 팀에게 순서를 제시한다.
기술적 마찰을 줄이기 전에 그 마찰이 사라졌을 때 무엇이 병목이 되는지 먼저 보라는 것이다.
그리고 그 병목이 사람의 판단이라면, 판단이 필요한 경우와 필요 없는 경우를 미리 분류해야 한다 — 읽기 전용이고 공개 데이터만 다루는 서버까지 세 개의 리뷰를 요구하면 승인 절차가 곧 새로운 배포 파이프라인이 된다.

### 사용자 수준 귀속이 감사가 아니라 학습 자산이 된다

일부 서버가 도구 발견에도 JWT를 요구하는 이유로 글은 누가 무엇을 했는지 따지기 깔끔해진다는 감사 목적을 든다.
그런데 이 데이터의 더 큰 가치는 다른 곳에 있다.

모든 호출에 사용자, 도구, 입력, 출력, 예외가 기록되면 그것은 에이전트가 실제로 어떤 도구를 어떤 순서로 쓰는지에 대한 완전한 기록이 된다.
어떤 도구가 자주 실패하는지, 어떤 도구 조합이 반복되는지, 어떤 질문이 도구 없이 끝나는지가 모두 보인다.
이는 다음 MCP 서버를 무엇으로 만들지 정하는 데 직접 쓰이는 정보이고, 도구 설명을 어떻게 고칠지에 대한 신호이기도 하다.

한 걸음 더 나아가면 이 로그는 평가 데이터셋이 된다.
실제 호출 이력에서 성공한 궤적과 실패한 궤적을 뽑으면 에이전트 변경의 회귀를 잡는 테스트가 만들어지고, 그것 없이는 프롬프트나 모델을 바꿀 때마다 무엇이 나빠졌는지 알 수 없다.
Pinterest가 관측을 처음부터 라이브러리로 강제한 것은 결과적으로 이 자산을 확보한 것인데, 글은 이를 지표 계산의 재료로만 다룬다.

### 도메인별 서버 분할은 컨텍스트 문제이자 조직 문제이며, 후자가 더 오래간다

서버를 나눈 이유로 접근 통제와 컨텍스트가 제시되었지만, 실제로 이 구조를 유지시키는 것은 세 번째 이유일 가능성이 높다 — 소유권이다.

레지스트리가 소유 팀과 지원 채널을 보여준다는 서술, Spark MCP 도구가 Airflow 지원 채널에서만 쓰인다는 설정, 도구를 정의하면 플랫폼이 배포를 맡는다는 파이프라인이 모두 같은 것을 가리킨다 — 각 서버는 그 도메인을 이미 소유한 팀의 산출물이다.
단일 거대 서버였다면 그 서버를 누가 소유하는가라는 질문에 답할 수 없었을 것이고, 답할 수 없으면 아무도 도구를 고치지 않는다.

이 관점은 사내 AI 도구 전략에 일반화된다.
에이전트가 쓸 도구의 품질은 그 도구를 만든 팀이 그 도메인의 실무를 아는지에 달려 있고, 중앙 플랫폼 팀이 모든 도구를 만들면 도구는 얇아진다.
그래서 중앙 팀이 해야 할 일은 도구를 만드는 것이 아니라 도구를 만들기 쉽게 만드는 것이며, Pinterest가 배포 파이프라인 통합을 가장 먼저 한 이유가 여기에 있다.

다만 이 구조에는 지속적인 세금이 붙는다.
서버가 늘수록 어떤 도구가 어디 있는지 아는 사람이 줄고, 도구 설명의 품질이 팀마다 달라지며, 같은 일을 하는 도구가 두 서버에 생긴다.
레지스트리가 발견을 돕지만 중복을 막지는 못하고, 글에는 도구 카탈로그의 품질을 관리하는 장치가 없다.

### 사내 표준을 만들면 외부 표준과의 간격이 시간이 갈수록 벌어진다

Pinterest는 MCP의 인가 흐름을 쓰지 않고, 전송을 사내 클라우드 호스팅으로 고정했으며, 자체 보안 표준과 레지스트리 API를 정의했다.
남은 것은 도구 정의와 호출 형식이라는 MCP의 핵심 부분이다.

이 선택은 지금 합리적이다 — 사내 요구에 맞고, 기존 인프라를 재사용하며, 사용자 경험이 좋다.
문제는 MCP 명세가 계속 진화한다는 점이다.
elicitation을 이미 쓰고 있다는 서술에서 보이듯 Pinterest는 명세의 새 기능을 채택하고 있는데, 그 기능들이 인가 모델을 전제하는 순간 사내 구현과 충돌한다.

시간이 지나면 세 가지 중 하나가 일어난다.
명세를 따라가느라 사내 구현을 계속 고치거나, 명세에서 멀어져 사실상 사내 프로토콜이 되거나, 외부 MCP 서버를 붙일 때마다 어댑터를 만들거나.
LinkedIn이 Kafka 브랜치에서 겪은 것과 같은 구조이며, 그 사례에서 배울 것은 이탈 항목에 만료 조건을 붙여 관리하라는 것이다.

여기서 실무적으로 가져갈 질문은 하나다 — 우리가 표준에서 벗어난 지점의 목록이 문서로 존재하는가.
존재하지 않으면 벗어남은 결정이 아니라 사고가 되고, 나중에 왜 이렇게 되어 있는지 아무도 설명하지 못한다.
Pinterest의 글은 그 목록을 사실상 공개한 문서이기도 하며, 그 점이 이 글의 가장 실용적인 기여다.
