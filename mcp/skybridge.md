# Skybridge: MCP 앱을 만드는 풀스택 React 프레임워크

<https://skybridge.tech>

<https://github.com/alpic-ai/skybridge>

## 소개

Alpic이 만들어 공개한 MCP 앱 및 MCP 서버용 풀스택 TypeScript 프레임워크다.
MIT 라이선스이며 2025년 10월 7일에 만들어졌고,
확인 시점에 별 1,998개와 포크 132개, 열린 이슈 49개를 기록하고 있다.

프로젝트가 스스로 설명하는 목적은 Claude와 ChatGPT를 비롯한 UI 지원 MCP
클라이언트를 위해
타입 안전한 MCP 앱을 만들도록 돕는 것이며,
사람과 에이전트 양쪽을 위한 도구 모음을 함께 제공한다고 밝힌다.

### MCP 앱이라는 범주

README는 왜 이 프레임워크가 필요한지를 두 단계로 설명한다.

첫째, MCP 앱은 Model Context Protocol을 확장해 MCP 서버가 렌더링하는 풍부하고
상호작용 가능한 UI 뷰를 얹는 것이다.
대화형 앱은 사용자와 UI와 모델 사이의 매끄러운 상호작용을 필요로 하며,
그것이 새로운 UX 패턴과 개발 도구와 추상화를 요구한다.

둘째, 원시 SDK가 저수준이라는 것이다.
훅도 없고 타입 안전성도 없고 핫 모듈 교체도 없다고 적는다.

### 세 행위자와 맥락 비대칭

아키텍처 문서가 이 프레임워크의 설계 관점을 가장 잘 보여 준다.

MCP 앱에는 세 행위자가 관여한다.
앱과 사용자와 모델이다.
그리고 이것이 맥락 비대칭을 만든다.
각 행위자가 시스템의 부분적 그림만 갖는다는 것이다.

모델은 UI를 보지 못한다.
명시적으로 되돌려 동기화하지 않는 한 화면도 사용자 조작도 볼 수 없다.
반대로 사용자는 아래에서 흐르는 도구 출력을 보지 못한다.

그래서 문서는 핵심 설계 과제가 레이아웃이나 스타일링이 아니라고 단언한다.
누가 무엇을 언제 보는지를 정하는 일이며,
모델이 무엇을 알아야 하는지, 무엇을 모델에게서 감춰야 하는지,
어디에서 자연어가 전통적 UI를 대체해야 하는지가 그 질문이라고 적는다.

### 용어와 생애 주기

문서가 정의하는 용어는 여덟이다.
호스트는 모델을 품고 앱을 실행하는 AI 클라이언트이고,
MCP 앱은 도구를 노출하는 서버에 선택적 뷰가 붙은 단위이며,
MCP 서버는 모델과 뷰에 노출되는 도구 집합이고,
도구는 모델이나 뷰가 호출할 수 있는 서버의 함수다.
뷰는 도구에 묶여 배포되고 호스트 안에서 렌더링되는 React 컴포넌트이고,
런타임은 서버 응답과 모델과 뷰 사이를 잇는 호스트의 다리이며,
뷰 인스턴스는 뷰가 마운트된 하나의 사례이고,
뷰 상태는 그 인스턴스에 붙은 상태다.

생애 주기는 세 단계다.

마운트 단계에서는 사용자가 모델과 대화하고 모델이 서버의 도구를 호출한다.
서버 응답에는 호스트가 뷰를 대화에 인라인으로 마운트하는 데 쓰는 뷰 참조와,
모델과 공유되면서 뷰에도 전달되는 출력이 들어 있다.
모델이 연결된 도구를 호출할 때마다 뷰의 새 인스턴스가 마운트된다.

여기서 이 프레임워크의 설계 결정 하나가 드러난다.
도구 출력의 형태가 각 데이터 조각을 특정 수신자에게 지정할 수 있게 한다는
것이다.
어떤 필드는 모델에만, 어떤 필드는 뷰에만, 어떤 필드는 양쪽에 보낼 수 있으며,
수신자를 고르는 것이 각 행위자가 어떤 맥락을 보는지 통제하는 설계 결정이라고
명시한다.

실행 단계에서 뷰는 사용자가 도구 호출과 상태 변경을 일으킬 수 있는 활성 표면이
된다.
상태는 뷰와 모델 양쪽에 공유되어 모델이 화면에서 벌어지는 일을 계속 인지한다.
다만 상태를 변경할 수 있는 것은 뷰뿐이며 각 뷰 인스턴스가 자기 상태를 갖는다.
뷰는 자신이 묶인 도구는 물론 다른 도구도 호출할 수 있는데,
뷰에서 시작한 도구 호출은 뷰를 마운트하지 않는다.

해체 단계는 대화가 닫힐 때다.
모든 뷰 인스턴스가 언마운트되고,
다음에 불러올 때 각자 자기 상태가 복원된 채로 다시 마운트된다.

### 기능

README가 내세우는 것은 여섯이다.

개발 환경 쪽에는 로컬 에뮬레이터를 갖춘 개발 서버와 핫 모듈 교체,
그리고 로컬 앱을 Claude와 ChatGPT에 연결하는 영구 터널이 있다.

한 번 쓰고 어디서나 돌린다는 항목은 프레임워크가 MCP 클라이언트 사이의 구현
차이를 추상화해
Claude와 ChatGPT와 VSCode를 비롯한 호환 클라이언트에서 앱이 그대로 돌아가게
한다는 것이다.

에이전트 대응 항목은 스킬과 CLI와 프로그래밍 방식 개발 도구 API를 제공해
코딩 에이전트가 MCP 앱을 처음부터 끝까지 만들 수 있게 한다는 것이다.

타입 안전성은 tRPC 방식의 추론으로 MCP 서버의 도구 정의에서 React 뷰까지
이어진다.
React 훅은 React Query 방식이며 고급 상태 관리를 포함한다고 적는다.
예제 라이브러리에는 전자상거래와 여행과 SaaS 등의 앱 예제가 들어 있다.

### 설치와 예제

설치 안내의 순서가 특이하다.
에이전트용이 먼저 나오고 사람용이 뒤에 온다.

에이전트용은 스킬을 설치하는 명령 한 줄이며,
설치한 뒤 에이전트에게 어떤 스킬이 있는지 물어 확인하고
새 MCP 앱 만들기나 기존 MCP 서버를 이 프레임워크로 옮기기나 새 뷰 추가하기를
시켜 보라고 안내한다.
사람용은 프로젝트를 새로 만드는 `npm create` 명령이다.

예제는 범주별로 정리돼 있다.
모든 훅과 기능을 보여 주는 종합 예제가 있고,
지도와 항공권 예약과 전자상거래 캐러셀과 추리 게임과 분석 대시보드와 단어 맞히기
게임과 AI 튜터가 사용 사례로 들어 있다.
인증 예제는 여섯 개 공급자에 대해 각각 준비돼 있고,
UI 컴포넌트 라이브러리 예제도 셋 있다.

### 배포와 상업 계층

배포는 Alpic에서 즉시 할 수 있다고 안내한다.
확장 가능한 호스팅과 MCP 전용 분석과 영구 터널링,
그리고 앱 스토어 규정 준수 감사와 제출 지원을 제공한다는 것이다.
Node.js 호환 플랫폼이라면 자체 호스팅도 가능하다고 덧붙인다.

사용자로는 Datadog과 Bitmovin과 Evaneos와 Touchstream과 Cottages.com이 로고로
제시된다.
관리자는 Harijoe와 Fred Barthelet과 Alpic 팀이다.

v1.0 릴리스에 대해 핵심 관리자 harijoe가 Hacker News에 남긴 설명에 따르면,
통합 터널과 새 개발자 도구, 그리고
ChatGPT와 Claude 스토어 제출을 준비하도록 돕는 감사 기능이 들어갔다.[^harijoe]

## 분석

### 이 프레임워크가 푸는 문제는 렌더링이 아니라 정보 라우팅이다

아키텍처 문서에서 가장 값 있는 문장은 핵심 설계 과제가 레이아웃이나 스타일링이
아니라는 선언이다.
누가 무엇을 언제 보는지를 정하는 것이라는 대목이며,
이것이 웹 프레임워크와의 결정적 차이를 만든다.

웹에서는 데이터의 수신자가 하나다.
서버가 응답을 보내고 브라우저가 그리고 사용자가 본다.
개발자가 고민하는 것은 무엇을 어떻게 보이게 할지이지 누구에게 보일지가 아니다.

MCP 앱에는 수신자가 둘이다.
같은 도구 호출의 결과를 모델도 받고 뷰도 받으며,
두 수신자가 필요로 하는 것이 다르다.
모델에게는 판단에 쓸 구조화된 사실이 필요하고 뷰에는 그릴 데이터가 필요하며,
겹치는 부분과 겹치지 않는 부분이 있다.

도구 출력의 필드마다 수신자를 지정할 수 있게 한 설계가 이 문제에 대한 답이다.
그리고 문서가 그것을 편의 기능이 아니라 설계 결정이라고 부른 것이 정확하다.
어떤 필드를 모델에 보내지 않기로 하면 모델은 그 정보에 대해 판단할 수 없고,
보내기로 하면 그것이 맥락을 차지한다.

### 맥락 비대칭이라는 개념이 이 프레임워크의 실제 기여다

세 행위자가 각각 부분적 그림만 본다는 정식화는 단순하지만 설계 어휘로 유용하다.

이 정식화가 유용한 이유는 버그의 위치를 알려 주기 때문이다.
대화형 앱의 흔한 실패는 모델이 화면에 있는 것을 모른 채 엉뚱한 조언을 하거나,
사용자가 모델이 무엇을 받았는지 몰라 예상과 다른 결과를 얻는 것이다.
둘 다 코드의 결함이 아니라 정보 흐름 설계의 결함이며,
비대칭이라는 이름이 그 범주를 만든다.

상태 설계도 같은 관점에서 나왔다.
상태가 뷰와 모델에 공유되어 모델이 화면 상황을 계속 인지하되 변경은 뷰만 할 수
있다는 규칙이다.
이것이 개인 쇼퍼 예제에서 작동하는 방식이 문서에 나온다.
뷰가 장바구니와 현재 표시 중인 상품을 들고 있고
모델이 그것을 읽어 대화에서 맥락에 맞는 조언을 한다는 것이다.

단방향 변경 규칙은 웹 프레임워크의 단방향 데이터 흐름과 형태가 같지만
이유가 다르다.
웹에서는 예측 가능성을 위해서이고
여기서는 모델이 상태를 임의로 바꾸면 사용자가 조작하지 않은 변화가 화면에 생기기
때문이다.

### 에이전트를 1차 사용자로 놓은 설치 안내가 위치 선언이다

README의 설치 절은 에이전트용을 먼저 놓고 사람용을 뒤에 놓는다.
그리고 에이전트용 안내가 더 길다.
스킬을 설치하고, 에이전트에게 어떤 스킬이 있는지 물어 확인하고,
세 가지 지시를 시켜 보라는 구성이다.

이 순서가 우연이 아니다.
기능 목록에도 에이전트 대응이 세 번째 항목으로 들어 있으며,
스킬과 CLI와 프로그래밍 방식 개발 도구 API를 함께 제공한다고 적는다.
즉 이 프레임워크는 사람이 쓰는 도구이면서
동시에 에이전트가 조작하는 대상으로 설계됐다.

이 설계가 합리적인 이유가 있다.
MCP 앱을 만들 사람의 상당수가 이미 코딩 에이전트를 쓰고 있고,
새 프레임워크의 가장 큰 장벽이 학습 비용인데 에이전트가 그 비용을 대신
치를 수 있다면 채택 곡선이 달라진다.

그리고 이것은 프레임워크 문서화의 성격을 바꾼다.
사람이 읽을 문서와 에이전트가 읽을 스킬이 별개의 산출물이 되며,
둘의 내용이 어긋날 여지가 생긴다.
아키텍처 문서가 스킬을 최고의 교사라고 부르며 설치를 권하는 대목이 그 분리를
보여 준다.

## 비평

### 한 번 쓰고 어디서나 돌린다는 약속이 이 프로젝트에서 가장 위험한 부분이다

기능 목록의 두 번째 항목은 프레임워크가 MCP 클라이언트 사이의 구현 차이를
추상화해
Claude와 ChatGPT와 VSCode에서 앱이 그대로 돌아가게 한다는 것이다.

이 약속의 구조적 문제는 추상화의 대상이 경쟁사 두 곳의 제품이라는 데 있다.
Claude와 ChatGPT는 같은 시장에서 다투고 있고,
각자 자기 앱 런타임과 스토어 규정을 갖고 있으며, 둘 다 빠르게 움직인다.
그리고
어느 쪽도 서드파티 프레임워크를 위해 자기 런타임의 계약을 고정해 주지 않는다.

추상화의 수명은 대상들이 얼마나 벌어지느냐의 함수이며,
이 경우 벌어질 유인이 양쪽에 있다.
차별화가 곧 경쟁 우위이므로
각자 자기 런타임에만 있는 기능을 만들 이유가 충분하다.
그때 프레임워크는 두 선택지만 갖는다.
최소 공통분모만 노출해 양쪽의 고급 기능을 포기하거나,
분기 코드를 늘려 한 번 쓴다는 약속을 깨는 것이다.

앞서 다룬 Shopify의 React Native 복귀 사례가 이 경로의 한 결말을 보여 준다.
크로스 플랫폼 추상화가 제공한 절감은 실현됐지만,
프레임워크와 플랫폼 사이의 간극을 메우는 데 지속적으로 인력이 들어갔다.
거기서는 대상이 Apple과 Google이었고 둘 다 안정된 플랫폼 계약을 문서로 제공한다.
Claude와 ChatGPT의 앱 런타임은 아직 그 단계가 아니며, 그만큼 유지 비용이 크다.

README가 이 비용을 언급하지 않는 것은 홍보 문서로서 자연스럽다.
다만 도입을 검토하는 쪽이 물어야 할 것은 기능 목록이 아니라
두 플랫폼이 갈라졌을 때 이 프로젝트가 어느 쪽을 따라가는지다.
그리고 그 답은 상업적 이해가 정한다.

### 상태가 모델 맥락에 들어간다는 사실이 설계 부담으로 제시되지 않는다

상태가 뷰와 모델에 공유되어 모델이 화면 상황을 인지한다는 설명은 기능으로
서술된다.
개인 쇼퍼 예제가 그 이점을 보여 준다.
모델이 장바구니를 읽고 화면에 있는 상품을 가리키며 조언한다는 것이다.

그런데 같은 메커니즘에 세 가지 대가가 붙는다.

첫째는 토큰이다.
뷰 상태가 모델 맥락으로 들어간다면 상태의 크기가 곧 비용이며,
상태가 갱신될 때마다 그 비용이 반복된다.
웹 개발에서 컴포넌트 상태의 크기를 걱정하는 습관은 거의 없고,
여기서는 그것이 직접적인 지출이 된다.

둘째는 프라이버시다.
사용자가 화면에서 입력한 것이 뷰 상태에 들어가면 모델 제공자에게 전송된다.
폼에 입력했지만 아직 제출하지 않은 값,
사용자가 선택했다가 취소한 항목이 여기 해당할 수 있다.
어떤 것을 상태에 둘지가 UI 편의 문제가 아니라 데이터 경계 결정이 된다는 뜻이다.

셋째는 맥락 오염이다.
모델이 화면 상황을 안다는 것은 좋지만,
그 정보가 모델의 판단을 의도치 않게 끌 수도 있다.
사용자가 장바구니에 넣었다가 뺀 상품이 상태 이력에 남아 있으면 모델이 그것을
선호 신호로 읽을 수 있다.

문서가 도구 출력의 수신자 지정에 대해서는 설계 결정이라고 명시하면서
상태에 대해서는 같은 경고를 하지 않는 것이 비대칭이다.
두 경로 모두 모델 맥락으로 들어가는 문인데 한쪽에만 안내판이 붙어 있다.

### 인증 예제를 여섯 개 만든 것이 입장의 부재를 가린다

예제 목록에서 가장 눈에 띄는 것은 인증이다.
Descope와 Clerk와 WorkOS와 Stytch와 Auth0와 Authplane에 대해 각각 예제가 있다.
설명은 여섯 개가 거의 같으며, 전부 OAuth 인증과 개인화된 커피숍 검색이다.

같은 예제를 공급자만 바꿔 여섯 번 만드는 것은 통합의 폭을 보여 주는 흔한
방식이다.
문제는 인증이 MCP에서 가장 덜 정착된 영역이라는 점이다.
누가 사용자를 인증하는지, 토큰을 누가 보관하는지,
호스트와 서버 사이에서 신원이 어떻게 전달되는지가 여전히 논쟁 중이다.

그 상황에서 프레임워크가 취할 수 있는 입장은 둘이다.
자기 추상화를 제시하고 공급자들을 그 뒤에 두거나,
추상화하지 않고 각 공급자의 방식을 그대로 노출하는 것이다.
전자는 위험하지만 프레임워크의 값어치이고 후자는 안전하지만 프레임워크가 아니라
예제 모음이다.

여섯 개의 병렬 예제는 후자에 가깝게 보인다.
그리고 그것이 나쁜 선택이 아닐 수 있다.
표준이 정해지지 않은 영역을 성급히 추상화하면
표준이 정해질 때 그 추상화가 부채가 된다.

다만 그렇다면 그 판단을 밝히는 편이 낫다.
지금은 인증에 대한 입장이 예제의 개수로 대체돼 있으며,
도입하는 쪽은 여섯 중 하나를 골랐을 때 나중에 다른 것으로 옮기는 비용이 얼마인지
알 수 없다.

### 스토어 제출 지원이 상업 계층에만 있다는 사실이 이 프로젝트의 실제 구조를 드러낸다

배포 절은 Alpic에서 즉시 배포할 수 있다고 안내하며 네 가지를 든다.
확장 가능한 호스팅과 MCP 전용 분석과 영구 터널링, 그리고
앱 스토어 규정 준수 감사와 제출 지원이다.
그리고 Node.js 호환 플랫폼이라면 자체 호스팅도 가능하다고 덧붙인다.

앞의 셋은 자체 호스팅으로 대체 가능하다.
호스팅은 어디서든 할 수 있고, 분석은 직접 붙일 수 있으며,
터널은 개발 단계의 편의다.

네 번째는 다르다.
스토어 규정 준수와 제출은 자체 호스팅으로 대체되지 않는 종류의 도움이며,
동시에 MCP 앱을 만드는 사람이 실제로 막히는 지점이기도 하다.
만드는 것과 배포되는 것 사이에 심사가 있고, 심사 기준은 플랫폼이 정하며
자주 바뀐다.

v1.0에 감사 기능이 들어갔다는 관리자의 설명이 이 구조를 확인해 준다.
프레임워크 안에 감사가 들어왔지만 제출 지원은 여전히 상업 계층에 있다.

이 배치 자체를 비난할 이유는 없다.
오픈소스 프레임워크와 상업 호스팅의 조합은 흔하고 정당한 사업 형태다.
짚어야 할 것은 무료 계층과 유료 계층의 경계가 기술적 편의가 아니라
유통 관문에 그어져 있다는 사실이다.
그리고 그 관문은 이 회사가 만든 것이 아니라 플랫폼이 만든 것이므로,
이 회사가 그것을 계속 통과시켜 줄 수 있는지는 플랫폼에 달려 있다.

## 인사이트

### 프로토콜이 저수준으로 나오면 DX 계층이 생기고, 플랫폼이 결국 그것을 흡수한다

이 프로젝트의 존재 이유가 README에 그대로 적혀 있다.
원시 SDK가 저수준이라 훅도 타입 안전성도 핫 리로드도 없다는 것이다.

이 진단은 정확하고, 동시에 잘 알려진 반복 패턴의 시작점이다.
플랫폼이 프로토콜과 최소 SDK를 내놓고,
서드파티가 개발자 경험 계층을 만들어 채택을 이끌고,
그 계층이 표준이 되면 플랫폼이 그 기능을 1차 도구로 흡수한다.

전례가 많다.
브라우저 API의 불일치를 메우던 라이브러리가 표준화 이후 역할을 잃은 일,
상태 관리 라이브러리의 핵심 개념이 프레임워크 기본 기능으로 들어간 일,
빌드 도구와 배포 계층이 프레임워크 본체에 흡수된 일이 모두 같은 궤적이다.

이 패턴에서 서드파티가 살아남는 경로는 둘이다.
흡수되지 않는 영역으로 이동하거나,
플랫폼이 직접 하기 어려운 교차 플랫폼 위치를 점유하는 것이다.
이 프로젝트는 후자를 택했다.
Claude와 ChatGPT를 동시에 지원한다는 것은 어느 한쪽이 자기 1차 도구로 대체할 수
없는 자리다.

다만 그 자리의 안정성은 두 플랫폼이 서로를 의식하는 정도에 달려 있다.
한쪽이 압도적이 되면 교차 플랫폼 가치가 사라지고, 둘이 비슷하게 유지되면
그 자리가 유지된다.
즉 이 프로젝트의 전략적 위치는 자기 실력이 아니라 시장 구조가 정하며,
그것이 이런 도구가 감수하는 구조적 조건이다.

### 맥락 비대칭은 MCP 바깥에서도 쓸 수 있는 설계 어휘다

세 행위자가 각각 부분적 그림만 본다는 정식화는 MCP 앱을 설명하려고 만들어졌지만
그 범위를 넘는다.

같은 구조가 나타나는 자리가 이미 여럿이다.
코딩 에이전트가 터미널에서 작업하는데 사용자는 편집기에서 파일을 보고 있을 때,
에이전트가 브라우저를 조작하는데 사용자는 그 화면을 보지 못할 때,
여러 에이전트가 협업하면서 각자 다른 맥락을 들고 있을 때가 전부 같은 비대칭이다.

이 어휘가 유용한 이유는 질문을 구체화하기 때문이다.
막연히 에이전트가 상황을 잘 모른다고 말하는 대신,
어느 행위자가 어떤 정보를 갖고 있지 않은지,
그 정보가 어느 경로로 전달될 수 있는지, 전달 비용이 얼마인지를 묻게 된다.

그리고 이 관점은 도구 설계의 우선순위를 바꾼다.
에이전트 도구를 만들 때 흔히 능력을 먼저 생각한다.
무엇을 할 수 있게 할지를 정하고 그것을 함수로 노출하는 것이다.
비대칭 관점에서는 반대로 시작한다.
이 도구를 쓴 뒤 각 행위자가 무엇을 알게 되고 무엇을 여전히 모르는지를 먼저 적고,
그 격차를 메울 경로를 설계에 넣는다.

앞서 다룬 SoL-Pi가 관찰 결과를 핸들로 바꾸면서
정확한 쪽 회수를 남긴 것도 같은 문제의 다른 해법이다.
거기서는 모델에게 전부 보내지 않으면서 필요할 때 찾아볼 수 있게 했고,
여기서는 필드마다 수신자를 지정하게 했다.
둘 다 무엇을 모델에게 보일지가 설계 대상이라는 인식에서 나왔으며,
이것이 에이전트 시대 도구 설계의 공통 축으로 굳어지고 있다.

### UI 상태에 토큰 가격이 붙는 것은 웹 개발에 없던 조건이다

이 프레임워크의 상태 모델은 웹 프레임워크와 형태가 거의 같다.
훅으로 읽고 쓰고, 인스턴스마다 격리되고, 단방향으로 변경된다.

그런데 하나가 다르다.
그 상태가 모델 맥락으로 흘러간다는 것이다.

이 차이가 개발 습관과 충돌한다.
웹에서 컴포넌트 상태에 무엇을 넣을지는 거의 비용 없는 결정이다.
필요하면 넣고, 안 쓰면 방치해도 사용자는 모른다.
여기서는 넣는 순간 토큰이 되고, 갱신할 때마다 다시 토큰이 되며,
대화가 길어질수록 누적된다.

그래서 이 환경에서는 상태 설계에 대한 새로운 규율이 필요해진다.
화면을 그리는 데만 필요한 것과 모델이 알아야 하는 것을 구분해 두 곳에 나눠 담는
것,
큰 목록을 통째로 상태에 두지 않고 식별자만 남기는 것,
사용자가 입력 중인 임시 값을 모델에 보이는 상태와 분리하는 것이 그 규율의 내용이
된다.

이것이 두 번째 효과로 이어진다.
비용이 보이지 않으면 절제가 생기지 않는다는 것이다.
현재 이 프레임워크의 문서에는 상태 크기가 맥락과 비용에 어떻게 반영되는지에 대한
안내가 보이지 않으며,
개발 도구가 그것을 보여 주는지도 명시되지 않는다.
개발 서버가 상태 갱신마다 추가되는 토큰을 표시해 준다면 그 규율이 저절로 생기고,
보여 주지 않으면 청구서에서만 드러난다.

역사적 유비로 모바일 데이터 사용량이 있다.
개발자들이 이미지 크기와 요청 횟수를 신경 쓰기 시작한 것은 원칙을 배워서가
아니라
도구가 그것을 눈에 보이게 만든 뒤였다.
에이전트 앱의 맥락 예산도 같은 경로를 밟을 것이며,
그 계기를 만드는 것은 프레임워크의 개발 도구다.

### 진짜 병목은 만드는 것이 아니라 승인받는 것이며 프레임워크는 그것을 고칠 수 없다

이 프로젝트가 해결하는 문제는 구축의 어려움이다.
훅이 없고 타입이 없고 핫 리로드가 없어서 MCP 앱을 만들기가 번거롭다는 것이며,
그 문제는 실재하고 이 프레임워크가 실제로 줄인다.

그런데 만든 뒤의 경로가 훨씬 불확실하다.
MCP 앱이 사용자에게 닿으려면 Claude나 ChatGPT의 앱 목록에 올라야 하고,
그 관문의 기준을 플랫폼이 정하며, 기준은 초기 단계라 자주 바뀐다.

상업 계층이 규정 준수 감사와 제출 지원을 파는 것이 이 사실의 증거다.
파는 쪽은 고객이 어디서 막히는지 알고 있으며, 그 지점이 코드가 아니라 심사다.

이 구조가 개발자에게 주는 함의는 도구 선택 기준이 달라진다는 것이다.
프레임워크를 고를 때 보통 개발 경험과 생태계와 성능을 본다.
여기서는 그 항목들 위에 하나가 더 얹힌다.
이 프레임워크로 만든 앱이 실제로 스토어를 통과한 사례가 있는지다.

그리고 이 조건은 프레임워크 경쟁의 성격을 바꾼다.
기술적 우열이 아니라 플랫폼과의 관계가 승부를 가르게 되며,
그것은 오픈소스 저장소에서 보이지 않는 변수다.
README에 기업 로고가 다섯 개 걸려 있는 것이 그 변수에 대한 유일한 신호이고,
그 로고들이 실제로 스토어에 앱을 올렸는지는 저장소에서 확인되지 않는다.

여기서 나오는 예측은 이 범주의 도구들이 결국 유통 대행 쪽으로 무게를 옮기리라는
것이다.
프레임워크는 복제 가능하고 스토어 통과 실적은 복제하기 어렵기 때문이다.
모바일 앱 초기에 빌드 도구를 만들던 회사들이 배포와 심사 대행과 분석으로
이동했던 것과 같은 경로이며,
이 저장소의 배포 절이 이미 그 방향을 가리키고 있다.
