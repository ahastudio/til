# 페이플 MCP: 결제 연동 문서를 AI가 찾아 읽게 하되 읽기와 원칙 전달에만 쓴다

<https://docs.payple.kr/v2/ref/for-ai>

<https://team.payple.kr/blog/payple-mcp>

Show GN: [페이플 MCP - AI 코딩 도구가 PG 결제 연동 문서를 직접 찾아 읽게 하기](https://news.hada.io/topic?id=36629)

## 소개

페이플(Payple)은 PG사이고, 개발자센터의 결제 연동 문서를 읽는 MCP 서버를
공개했다.
GeekNews의 Show GN 글은 2026년 11월 5일에 페이플이 직접 올렸다.
페이플은 MCP를 연결한 AI 코딩 도구가 개발자센터 문서를 스스로 찾아 읽고
그 문서를 근거로 결제 연동 코드를 쓴다고 설명한다.
로그인이나 키 없이 연결되며, 서버 주소는 `https://mcp.payple.kr/mcp`다.

페이플의 설명에 따르면 이전에는 이런 과정이 필요했다.
이번 달 개발자센터를 새로 단장하며 AI가 읽기 좋은 문서 목차(`llms.txt`)와
문서별 Markdown 복사 기능을 넣었지만,
그때는 개발자가 문서를 골라 AI에게 붙여 넣어야 했다.
MCP를 연결하면 개발자가 질문하는 것만으로 AI가 맞는 문서를 찾는다는 것이다.

다루는 문서는 22개이고 국내 카드와 계좌 결제, 정기(빌링) 결제, 링크결제,
해외카드 결제, 정산지급대행, 대사, 응답 코드 등이다.
이 문서는 페이플이 공개한 이 서버를 소개하는 글의 내용을 정리하며,
성능이나 정확성에 관한 서술은 모두 페이플의 주장으로 적는다.
MCP 서버를 직접 연결해 보지는 못했다.

## 동작 방식

### 서버는 도구 네 개로 문서를 찾고 읽는다

페이플의 개발자센터 안내에 나오는 도구는 네 가지다.

| 도구                  | 언제 쓰이는가                                             | 하는 일                                                |
| --------------------- | --------------------------------------------------------- | ------------------------------------------------------ |
| `search_api_doc`      | 연동 질문을 하면 (예: 빌링키로 정기결제를 승인하는 API)   | 관련 문서를 검색해 문서 제목과 절 주소를 근거로 받는다 |
| `list_available_apis` | 어떤 결제 방식 문서가 있는지 묻거나 검색 결과가 비었을 때 | 22개 문서의 id, 제목, 분류, 요약이 담긴 목차를 본다    |
| `get_api_details`     | 찾은 문서의 자세한 내용이 필요할 때                       | 그 절의 원문(파라미터 표, 예시, 응답 코드)을 읽는다    |
| `get_example_code`    | 코드만 필요할 때 (예: 빌링키 해지 요청 JSON 예시)         | 문서에 실린 코드 블록만 가져온다                       |

안내는 보통 `search_api_doc`으로 문서를 찾고,
받은 주소를 `get_api_details`에 넣어 원문을 읽은 뒤 답한다고 적는다.
긴 문서는 목차부터 받는다.
답에는 근거가 된 문서가 함께 나오므로 개발자가 원문을 바로 열어 확인할 수 있다고
블로그 글은 설명한다.

### 연결할 때 세 가지 원칙이 AI에게 함께 전달된다

페이플은 MCP가 연결될 때 AI에게 다음 원칙을 함께 건넨다고 쓴다.
첫째, 문서 하나를 기준으로 구현한다.
국내, 해외, 정산지급대행은 인증 방식, 키, 성공 응답 코드,
승인 절차가 서로 달라서
다른 서비스의 키나 응답 코드를 섞지 않는다.
둘째, 문서에 없는 파라미터나 값은 만들어 넣지 않고 확인이 필요하다고 알린다.
셋째, 외부에 드러나면 안 되는 키는 서버에서만 쓰고 테스트 키와 운영 키를 나눈다.
블로그 글은 여기에 결제 금액을 서버에서 다시 확인한다는 내용도 적는다.

같은 원칙은 `llms.txt`의 맨 앞에도 들어 있다.[^llms]
이 파일은 정기결제와 빌링이 같은 말이라는 것,
간편페이는 네이버페이나 카카오페이 같은
간편결제 서비스이며 페이플에 카드나 계좌를 등록해 비밀번호로 결제하는
비밀번호 간편결제와 다른 상품이라는 것도 먼저 밝힌다.[^llms]
원문을 열지 못하면 내용을 추측하지 말고 화면 주소를 사용자에게 알려 달라는
지시도 있다.[^llms]
따라서 MCP를 쓰지 않고 목차나 문서 원문을 붙여 넣어도 같은 원칙이 AI에게
전달된다.

### 서버는 읽기만 하고 결제를 요청하지 않는다

페이플은 이 MCP가 공개된 개발자센터 문서를 찾아 읽는 일만 한다고 밝힌다.
결제를 요청하거나 거래 내역을 조회하지 않고 결제 데이터나 키도 다루지 않는다.
개발자센터에는 화면 안에서 묻고 답하는 AI 도우미 지니봇이 따로 있고,
MCP는 개발자가 코드를 쓰는 AI 코딩 도구 안에서 문서를 쓰게 하는 것이라는 구분도
블로그 글이 적는다.

## 연결하기

Claude Code에서는 터미널에 다음 한 줄을 입력한다.
연결되었는지는 `/mcp`를 입력해 확인한다.

```bash
claude mcp add --transport http payple https://mcp.payple.kr/mcp
```

Cursor처럼 설정 파일(`mcp.json`)로 연결하는 도구는 서버 주소만 넣는다.

```json
{
  "mcpServers": {
    "payple": { "url": "https://mcp.payple.kr/mcp" }
  }
}
```

페이플의 안내는 Codex는 터미널 명령 한 줄로,
VS Code는 설정 파일에 추가해 연결한다고 설명한다.
Claude 앱(웹과 데스크톱)에서는 Customize > Connectors에서
Add custom connector로 이름과 주소를 넣고 로그인은 No sign-in으로 둔다.
Team과 Enterprise 요금제는 조직 관리자가 한 번 추가하면 구성원 모두 쓴다.
외부 도메인 접속을 막아 둔 환경에서는 연결할 수 없다고 안내가 적는다.

실제 결제를 받으려면 페이플 가입이 필요하다.
테스트 정보로는 계약 전에도 연동을 미리 해 볼 수 있고,
가입 문의는 접수 후 1영업일 안에 담당자가 연락한다고 한다.

## 한도와 오류

문서 검색에는 하루 한도가 있고 사무실처럼 여러 명이 같은 IP를 쓰면 함께 쓴다.
한도에 걸려도 문서 목차와 원문 읽기는 계속된다고 안내는 적는다.
연결이 안 될 때의 오류는 다음과 같이 나뉜다.

| 신호                       | 안내가 붙인 이름과 이 문서의 풀이           |
| -------------------------- | ------------------------------------------- |
| HTTP 429                   | 요청 과다(HTTP 표준 의미, 이 문서의 풀이)   |
| `CSAR0001`                 | 검색 분당 한도                              |
| `CSAR0002`                 | 검색 하루 한도                              |
| `CSAQ0001`                 | 검색이 몰려 자리를 얻지 못함                |
| `CSAT0001`, `CSAS0001`     | 검색 서버 지연 또는 장애                    |
| 근거 0건, `low_confidence` | 근거가 없거나 신뢰도가 낮음(이 문서의 풀이) |

오류 메시지에는 기다릴지 원문을 볼지가 함께 안내되어 AI가 읽고 판단한다고 한다.
해결되지 않으면 지니봇에 묻거나 페이플 지니 깃허브에 사용 중인 AI 도구,
오류 메시지, `request_id`를 남기라고 안내한다.

## 분석

### 쓰기가 아니라 읽기에 한정한 설계가 결제라는 영역에 맞는다

결제 연동 코드는 실제 돈이 오가는 코드라는 것이 페이플 안내의 첫 경고다.
되돌리기 어려운 부분, 곧 금액, 주문번호,
취소 처리는 테스트 환경에서 먼저 확인하라고 한다.
이 영역에서 MCP가 하는 일을 문서 검색과 읽기로 한정한 것은 합리적인 선택이다.
서버가 결제를 요청하거나 거래 내역을 조회하지 않으므로
AI가 잘못 판단해도 서버를 통해 결제가 일어날 길이 없다.

이 설계는 에이전트의 권한을 행동이 아니라 정보에 한정하는 방식이다.
같은 저장소의 [자율 에이전트를 위한 데이터
플랫폼](../data/data-platform-for-autonomous-agents.md)이
에이전트에게 줄 권한을 행동 단위로 나누자고 한 것과 방향이 같다.
다만 이 서버가 막는 것은 서버를 통한 행동이고,
AI가 쓴 코드가 나중에 실제 결제를 일으키는 경로는 서버 밖에 있다.

### 원칙을 서버와 문서 양쪽에 넣어 어느 경로로 써도 같은 규칙이 간다

페이플은 같은 세 원칙을 MCP가 연결될 때와 `llms.txt`와 문서 원문의 맨 앞에
모두 넣었다.
MCP를 쓰는 개발자도, 문서를 붙여 넣는 개발자도 AI가 같은 규칙을 받는다.
규칙이 한 경로에만 있으면 다른 경로로 쓰는 개발자는 규칙 없이 코드를 받게 된다.

이 구조에서 규칙은 서버의 기능이 아니라 문서의 일부다.
그래서 문서를 갱신하면 규칙도 함께 갱신되고,
AI 도구가 달라도 문서를 읽는 한 규칙은 따라온다.
다만 AI가 규칙을 따르는지는 전달만으로 보장되지 않는다.

### 용어 충돌을 문서 맨 앞에서 풀어 모델의 혼동을 줄인다

`llms.txt`의 첫머리에는 정기결제와 빌링이 같은 말이라는 것,
간편페이와 비밀번호 간편결제가 다른 상품이라는 것,
정산지급대행이 정산금 이체와 계좌조회로 나뉜다는 것이 있다.
사람은 문서를 읽다 보면 이런 구분을 알게 되지만 모델은 이름이 비슷한 항목을 섞을
수 있다.
같은 이름이 서로 다른 상품을 가리키거나 다른 이름이 같은 것을 가리키는 곳을
먼저 정리해 두는 방식이다.

## 비평

### 정확한 연동이라는 말에 측정이 붙어 있지 않다

페이플은 AI에게 맡겨도 정확한 결제 연동이라고 소개한다.
이 정확성이 어떻게 측정되었는지는 글에도 안내에도 없다.
질문 몇 건에 맞는 문서를 찾았는지, 틀린 값이 얼마나 나왔는지의 수치는 없다.
안내가 근거 0건이거나 `low_confidence`일 때를 오류 항목에 둔 것은
검색이 틀릴 수 있다는 점을 시스템이 알고 있다는 뜻이다.
페이플이 GeekNews 글에서 쓰는 도구에서 문서를 정확히 찾는지 의견을
달라고 한 것도
이 정확성이 아직 사용자 의견으로 확인되는 단계라는 신호다.[^payple]

### 원칙은 지시이고 강제가 아니다

세 원칙은 AI에게 전달되는 글이다.
서버가 AI의 코드를 검사하거나 막지 않는다.
금액을 서버에서 다시 확인하는 일, 키를 서버에서만 쓰는 일은
AI가 쓴 코드가 그렇게 되어 있어야 지켜진다.
페이플도 AI가 만든 코드를 반드시 확인하고 테스트 환경에서 먼저 돌려
보라고 적는다.
결제 연동의 안전은 결국 개발자의 검토에 놓이며,
MCP는 그 검토를 쉽게 하는 도구에 가깝다.
이 한계를 서버나 문서가 해결하지는 않는다.

### 서버가 AI의 컨텍스트에 지시를 넣을 수 있는 구조는 신뢰를 전제한다

이 MCP는 연결될 때 AI에게 원칙을 건넨다.
같은 경로로 다른 지시도 들어갈 수 있다는 것이 이런 구조의 일반적 성질이다.
페이플의 서버는 공개 문서만 읽고 로그인이 없으므로 사용자에게 닿는 위험이 작아
보이지만,
이 서버가 건네는 글의 내용을 사용자가 매번 확인하지는 않는다.
이는 이 문서의 추론이며, 페이플의 서버가 그런 일을 한다는 증거는 없다.
다만 외부 MCP 서버를 연결할 때는 건네받는 지시문도 신뢰의 대상이라는
점이 남는다.

### 문서 갱신과 서버의 동기화는 설명이 없다

문서가 바뀌면 서버가 읽는 내용도 바뀌어야 한다.
안내는 문서 22개를 다룬다고만 적고 갱신 주기나 색인 방식은 밝히지 않는다.
`llms.txt`에는 문서와 연동 스펙의 변경 이력을 담은 업데이트 노트 항목이
있다.[^llms]
서버가 이 변경을 얼마나 빨리 반영하는지가 틀린 코드를 막는 데 중요한데
설명이 없다.

### 댓글은 사용 후기가 아니라 추천이다

GeekNews에서 hmmhmmhm은 문서 MCP가 놀랍다고 짧게 반응했다.[^hmmhmmhm]
운영자 xguru는 자신들의 서비스 페어리에서 페이플을 잘 쓰고 있고
대응이 빨라서 좋다며 PG 서비스가 필요한 사람에게 추천한다고 적었다.[^xguru]
이 댓글은 MCP가 아니라 페이플이라는 PG사에 대한 추천이다.
또 [페어리](../current-affairs/fairy.md)는 GeekNews를 운영하는 Hada Studio가
만든 서비스이고
xguru는 그 사이트의 운영자이므로, 이 댓글은 고객이면서 호스팅 사이트 운영자의
의견이라는 점을 감안해 읽어야 한다.
이 MCP를 실제로 써 본 후기는 댓글에 없다.

## 인사이트

### 문서가 에이전트의 입력이 되면 문서 구성이 스펙만큼 중요해진다

`llms.txt`가 문서 목차 위에 원칙과 용어 정리를 얹고,
원문을 열지 못했을 때 추측하지 말고 사용자에게 알리라는 지시까지 적은 것은
문서가 사람을 위한 설명에서 에이전트를 위한 입력으로 바뀌었다는 뜻이다.
사람은 모호한 서술을 맥락으로 풀지만 에이전트는 그대로 코드로 옮긴다.

이 관점에서 개발자 문서의 점검 항목이 달라진다.
같은 이름이 서로 다른 것을 가리키는지, 서비스마다 키와 응답 코드가 다른지,
문서에 없는 값을 만들면 안 된다는 규칙이 문서 안에 있는지 확인하는 일이다.
이 점검은 MCP 서버 없이 `llms.txt`와 원문 Markdown만으로도 시작할 수 있다.

### 결제처럼 되돌리기 어려운 영역은 에이전트에게 읽기부터 맡긴다

이 서버가 결제를 요청하지 않고 문서만 읽게 한 것은
에이전트를 도입할 때의 순서에 시사점을 준다.
먼저 읽기와 검색에 맡겨 에이전트가 근거를 제시하는지 확인하고,
쓰기와 행동은 사람이 검토하는 경로에 남겨 두는 것이다.

결정 규칙은 단순하다.
에이전트가 낸 근거를 사람이 열어 볼 수 있어야 하고,
되돌리기 어려운 행동은 테스트 환경에서 사람이 확인한 뒤에만 운영으로 보낸다.
페이플 안내가 답에 근거 문서를 함께 보여 준다고 한 것은 이 첫 조건에 해당한다.

### 연결하기 전에 확인할 것이 세 가지 있다

이 서버를 쓰기로 했다면 확인할 것이 있다.
첫째, 사용하는 AI 도구가 원격 MCP 서버(HTTP)를 지원하고 외부 도메인 접속이
막혀 있지 않은지 본다.
둘째, 검색 하루 한도를 팀이 같은 IP로 함께 쓰는지 본다.
셋째, AI가 낸 답의 근거 문서를 열어 파라미터와 응답 코드를 대조하고,
테스트 키로 먼저 돌려 본다.
