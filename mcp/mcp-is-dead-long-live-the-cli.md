# MCP is dead. Long live the CLI

원문:
  <https://ejholmes.github.io/2026/02/28/mcp-is-dead-long-live-the-cli.html>

## 요약

이 글의 핵심 메시지는 명확하다.
“MCP를 부정”하는 것이 아니라, 실제 에이전트 제품 개발에서는
CLI가 더 강한 기본 인터페이스라는 주장이다.

MCP는 도구 연결 표준으로 유용하지만,
복잡한 상호작용(스트리밍, 승인, 장기 세션, 복구, 분기)까지
포괄하려고 하면 추상화가 빠르게 무거워진다.

반면 CLI는 운영체제의 프로세스 모델과 stdin/stdout,
exit code, 파이프라인 같은 검증된 구성 요소를 그대로 활용한다.
결과적으로 구현 난이도, 디버깅, 배포, 호환성에서 이점을 얻는다.

즉, 글의 메시지는 “표준 vs 비표준”의 이분법이 아니라,
“문제에 맞는 인터페이스 선택”에 가깝다.

## 분석

### 1) MCP의 문제라기보다, 책임 과적재의 문제

MCP 자체는 툴 디스커버리와 호출 계약에 강점이 있다.
문제는 팀이 MCP 하나로 에이전트 런타임의 모든 계층을
해결하려고 할 때 발생한다.

- 도구 호출 계약
- 세션/상태 지속성
- 사용자 승인 루프
- 스트리밍 UI 동기화
- 에러 복구와 재시도

이 다섯 책임은 결이 다르다.
하나의 프로토콜에 모두 얹으면 설계가 비대해지고,
경계가 흐려져 구현체마다 해석 차이가 커진다.

### 2) CLI는 “가난한 인터페이스”가 아니라 “강한 최소 코어”

CLI는 표현력 부족처럼 보이지만,
에이전트 시스템에서는 오히려 장점이 된다.

- 어디서나 실행 가능(로컬, CI, 컨테이너, 원격 SSH)
- 로깅/관찰 가능성 우수(텍스트 스트림 기반)
- 조합 용이(`|`, `xargs`, `jq`, 리다이렉션)
- 실패 모델 명확(exit code, 시그널)

즉 CLI는 기능이 적어서 약한 게 아니라,
운영 관점의 불확실성을 줄여서 강하다.

### 3) 제품 팀 관점: “통합 속도”가 아키텍처를 이긴다

에이전트 제품의 병목은 모델 성능만이 아니다.
현실의 병목은 통합과 운영이다.

- 기존 툴체인에 얼마나 빨리 붙는가
- 장애 시 누가 어디를 볼 수 있는가
- 팀 간 계약이 얼마나 단순한가

CLI 우선 전략은 이 병목을 줄인다.
특히 초기/성장 단계 제품에서 의사결정 속도를 높인다.

## 비평

### 제목이 논지보다 훨씬 강하다

제목은 MCP가 죽었다는 선언이고, 본문이 실제로 말하는 것은 MCP에 너무 많은 책임을 얹지 말라는 것이다.
이 문서 자신도 MCP를 부정하는 것이 아니라고 첫 문단에서 정정한다.

제목과 논지의 거리는 단순한 수사 문제가 아니다.
이런 제목은 프로토콜을 쓸지 말지의 이분법으로 논의를 끌어가고,
실제로 결정해야 할 질문인 어느 계층에 무엇을 둘지를 가린다.
읽지 않고 제목만 공유되는 환경에서는 그 왜곡이 그대로 굳는다.

기술 논쟁에서 이 패턴은 반복된다.
무엇이 죽었다는 형식의 제목은 거의 항상 그것이 만능이 아니라는 내용을 담고,
두 진술 사이의 거리만큼 논의가 거칠어진다.
같은 주장을 책임 과적재라는 자기 본문의 표현으로 제목에 옮겼다면
논지도 정확해지고 반박도 생산적이 되었을 것이다.

### CLI의 장점 목록이 비용을 세지 않는다

CLI가 강한 최소 코어라는 논증은 네 가지를 든다.
어디서나 실행 가능하고, 텍스트 스트림이라 관찰이 쉽고, 조합이 쉽고, 실패 모델이 명확하다는 것이다.

각 항목의 반대편이 언급되지 않는다.
어디서나 실행 가능하다는 것은 어디서나 실행된다는 뜻이기도 해서,
에이전트에게 CLI를 주는 순간 그 셸의 모든 권한을 함께 주게 된다.
텍스트 스트림은 관찰이 쉬운 대신 형식이 보장되지 않아,
출력 형식이 바뀌면 그것을 파싱하던 쪽이 조용히 깨진다.

조합 용이성도 양날이다.
파이프와 리다이렉션으로 무엇이든 이어 붙일 수 있다는 것은
모델이 만들어 낸 명령줄 한 줄이 의도하지 않은 일을 할 수 있다는 뜻이다.
MCP가 무거워 보이는 이유 중 하나가 도구 목록과 인자 스키마를 명시적으로 한정하기 때문인데,
그 한정이 곧 안전 장치라는 점이 이 비교에서 빠져 있다.

### 다섯 가지 책임이 CLI에서는 사라진다는 듯이 서술된다

논증의 중심은 도구 호출 계약, 세션 지속성, 승인 루프, 스트리밍 동기화, 에러 복구라는 다섯 책임이
한 프로토콜에 얹히면 설계가 비대해진다는 것이다.

옳은 지적이지만, 다음 문단에서 CLI로 넘어가면서 이 다섯이 어디로 갔는지가 설명되지 않는다.
CLI를 쓴다고 승인 루프가 없어지지 않고, 장기 세션이 필요 없어지지도 않는다.
다만 그 책임들이 프로토콜 밖으로 나가 각 팀의 자체 구현으로 흩어질 뿐이다.

흩어지는 것이 나은 경우와 나쁜 경우가 있다.
팀이 하나이고 도구도 자기 것뿐이면 자체 구현이 가볍고 빠르다.
여러 조직이 만든 도구를 한 에이전트가 함께 쓰는 상황이면
승인과 복구의 규약이 제각각이 되고, 그 불일치를 조정하는 비용이 프로토콜을 만든 이유로 되돌아온다.
문서가 통합 속도를 강조하면서 그 속도가 유리한 조건이 초기와 성장 단계라고 한 줄 적는데,
그 조건 밖에서 무엇이 달라지는지는 다루지 않는다.

### 실전 경험이라고 하면서 사례가 제시되지 않는다

논증의 권위는 실제 에이전트 제품 개발에서 그렇더라는 경험에 기대고 있다.
그런데 어떤 제품이었는지, 도구가 몇 개였는지, MCP로 만들었다가 CLI로 바꾼 것인지,
바꾼 뒤에 무엇이 얼마나 나아졌는지가 나오지 않는다.

이 정보들이 있으면 독자가 자기 상황과 대조할 수 있다.
도구가 다섯 개인 팀과 쉰 개인 팀에서 결론이 같을 이유가 없고,
사내 도구만 쓰는 경우와 외부 서비스를 붙이는 경우도 다르다.
통합 속도가 아키텍처를 이긴다는 명제는 통합 대상의 수와 이질성에 따라 뒤집히는 종류의 주장이다.

관찰 가능성을 CLI의 강점으로 꼽은 글이므로 더 아쉽다.
장애 시 누가 어디를 볼 수 있는지를 병목으로 지목했다면,
실제로 장애가 났을 때 CLI 기반 구성에서 원인을 찾는 데 걸린 시간 같은 것이
이 주장을 가장 잘 뒷받침했을 것이다.

## 인사이트

### 1) “MCP 종료”가 아니라 “MCP의 계층 재배치”가 본질이다

이 논쟁을 승패 프레임으로 보면 오판한다.
더 정확한 해석은 계층 분리다.

- 상위 계층: 에이전트 경험/세션/승인/워크플로우
- 하위 계층: 도구 호출 계약(MCP), 프로세스 실행(CLI)

즉 MCP는 사라지는 것이 아니라,
“도구 표준”이라는 제자리를 찾아가는 과정이다.

### 2) 2026년 에이전트 스택의 실전 패턴은 “CLI 퍼스트 + 선택적 MCP”가 될 가능성이 높다

운영 가능한 시스템은 대개 복잡도를 늦게 도입한다.
처음엔 CLI로 end-to-end를 고정하고,
필요한 지점에만 MCP를 얹는 방식이 생존 확률이 높다.

이 패턴의 장점:

- 초기 전달 속도 빠름
- 디버깅 단순
- 장애 격리 쉬움
- 팀 온보딩 비용 낮음

결국 “아름다운 표준”보다
“고장 나도 복구 가능한 파이프라인”이 이긴다.

### 3) 프로토콜 경쟁의 승부처는 기능이 아니라 “운영 인지부하(operational cognitive load)”다

엔지니어 조직이 감당하는 진짜 비용은
스펙 문서 분량이 아니라 운영 시 인지부하다.

- 이 문제가 누구 소유인지 즉시 아는가
- 로그 한 번으로 경로를 재구성할 수 있는가
- 재현 시나리오를 5분 안에 만들 수 있는가

CLI는 이 질문에 강하게 답한다.
“단순성”이 미학이 아니라, MTTR을 줄이는 실무 무기다.

### 4) Human-in-the-loop의 핵심은 UI가 아니라 경계 정의다

승인 UX를 화려하게 만드는 것보다 중요한 건
“어디서 자동화가 멈추고 사람이 결정하는지”를
명확히 선언하는 것이다.

CLI 중심 설계는 이 경계를 명령 단위로 드러낸다.
에이전트 동작을 작은 불변 계약으로 쪼개고,
위험 작업 앞에서 중단점을 강제하기 쉽다.

이는 보안/감사/컴플라이언스 요구가 있는 조직에서
특히 강력한 장점이 된다.

### 5) 장기적으로는 “CLI가 API를 이긴다”가 아니라 “CLI가 API 설계를 정련한다”가 맞다

초기에는 CLI가 빠르다.
하지만 규모가 커지면 API/프로토콜이 필요해진다.

중요한 점은 순서다.
CLI로 먼저 실전 워크플로우를 검증하면,
나중에 만드는 API는 “가정”이 아니라
“실측된 사용 패턴”을 반영한다.

즉 CLI 퍼스트는 종착지가 아니라,
더 좋은 프로토콜로 가는 압축 학습 단계다.

## 실무 적용 체크리스트

- 에이전트 핵심 루프를 먼저 CLI로 고정했는가?
- 실패 모델(exit code, timeout, retry)을 계약으로 문서화했는가?
- 승인 지점(human gate)을 명령 경계로 정의했는가?
- 로그/트레이스를 텍스트 기반으로 재현 가능하게 남기는가?
- MCP 도입 목적을 “표준 준수”가 아니라
  “명확한 통합 이득”으로 증명했는가?

위 다섯 질문에 “예”가 많을수록,
도구 유행과 무관하게 오래가는 에이전트 시스템이 된다.
