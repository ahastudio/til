# Uber MCP Gateway: 기존 API를 그대로 에이전트 도구로 바꾸는 중앙 관문

원문: [Designing MCP Gateway Uber's MCP Management Platform](https://www.uber.com/in/en/blog/designing-mcp-gateway/)

GN 토론: <https://news.hada.io/topic?id=35213>

## 요약

Uber 엔지니어링 블로그가 2026년 10월 1일에 공개한 글로,
Business Platform 조직의 Alok Srivastava, Deepanshu Mehndiratta, Gaurav Gill 등
여덟 명이 함께 썼다.
출발점은 사내 MCP 도입이 빨라지면서 생긴 파편화다.
팀마다 MCP 연동을 따로 만들다 보니 도구는 찾기 어렵고 안정적으로 운영하기도
힘들었으며,
특정 서비스나 특정 에이전트 구현에 단단히 묶여 있었다.
수백 개 팀이 에이전트 워크플로를 시도하기 시작하자 이 방식으로는 운영 복잡도와
보안 위험, 개발자 마찰이 함께 커질 수밖에 없었다고 한다.

해법은 모든 MCP 상호작용을 맡는 마이크로서비스 하나, MCP Gateway다.
제어 평면(control plane)인 MCP Registry가 서버와 도구의 목록, 소유권,
활성화 상태를 관리하고,
데이터 평면(data plane)인 Proxy Gateway가
MCP 호출을 HTTP, gRPC, TChannel 요청으로 바꿔 백엔드에 전달한 뒤
응답을 다시 MCP 결과로 돌려준다.
글을 쓴 시점에 이 게이트웨이는 800개가 넘는 MCP 서버와 5,000개가 넘는 도구를
호스팅한다.

도구는 사람이 직접 만들지 않고 AutoCrawler가 찾아낸다.
Cadence 워크플로로 돌아가는 AutoCrawler는 정해진 주기로 Uber의 IDL 레지스트리를
훑어 Protobuf와 Thrift 정의에서 메서드, 요청·응답 스키마, 문서 주석을 뽑고,
LLM으로 에이전트용 도구 설명을 생성한 뒤 스키마를 MCP의 JSON-RPC 2.0 형식으로
바꿔 등록한다.
사내 프레임워크 MCPFx로 만든 네이티브 MCP 서버는 하트비트 지표로 존재를 알리고,
AutoCrawler가 이를 보고 `listTools`를 호출해 가상 프록시 서버로 등록한다.
어느 경로든 새 서버와 도구는 비활성 상태로 들어간다.
글은 이를 “발견이 노출을 뜻하지 않는다”는 원칙으로 부르며,
소유 팀이 생성된 설명을 검토하고 다듬은 뒤에야 켤 수 있게 했다.
설명을 바꿀 때마다 설정 변경 diff가 생기고 서버 소유자가 승인해야 배포되며,
필요하면 이전 버전으로 되돌릴 수 있다.

데이터 평면은 제어 평면의 설정을 정해진 주기로 메모리에 다시 읽어 들여
재시작이나 재배포 없이 변경을 반영하고,
가상 서버마다 `/<service-name>/mcp` 엔드포인트 하나를 연다.
IDL 기반 도구는 JSON 페이로드를 Protobuf나 Thrift 바이트로 직렬화해
서비스 메시 사이드카 Muttley를 통해 보내므로,
기존 서비스 간 라우팅 기능을 그대로 물려받는다.
보안은 사내 접근 제어 시스템의 charter 정책을
호출 주체(사람, 서비스, 에이전트)에 따라 적용하되
서버 단위로 정하고 필요하면 도구 단위로 덮어쓰며,
도구 응답에서 개인정보와 민감 데이터를 기본으로 지운다.
Jira나 Google 같은 외부 MCP 서버는 게이트웨이가 호출자의 사용자 토큰을 넘기고,
별도의 Third-Party MCP Service가 그 토큰을 외부 서비스 토큰으로 바꿔 요청한다.

규모가 커지자 작은 규모에서는 없던 문제, 즉 컨텍스트 비대와 비용이 드러났다.
MCP에는 서버를 가로지르는 검색 개념이 없어서,
에이전트에 서버 수백 개의 URL과 자격 증명, 도구 목록을 일일이 연결하면
모델의 컨텍스트 한도를 다 써 버린다.
그래서 세 가지를 더했다.
Omni MCP는 `discover_server`, `discover_tools`, `get_tool_schema`,
`invoke_tool` 네 도구만 노출하는 단일 프록시로,
필요한 서버와 도구를 단계적으로 찾게 한다.
Response Projection은 도구 요청 스키마에 필드를 하나 더 넣어 LLM이 필요한 중첩
경로만 적게 하고, 게이트웨이가 응답에서 그 필드만 남기는 GraphQL 비슷한
방식이다.
Code Mode는 사내 에이전트용 CLI `aifx`의 `aifx mcp list`, `aifx mcp search`,
`aifx mcp call`로 MCP 서버를 설치하지 않고 게이트웨이를 호출하게 하며,
결과를 파일로 써서 에이전트가 필요한 부분만 grep하게 한다.
글에 따르면 Code Mode는 이제 사내 코딩 에이전트의 기본 MCP 사용 방식이다.
결론은 대규모 에이전트 시스템에서 가장 어려운 것은 AI가 아니라
발견, 보안, 신뢰성 같은 연결 조직이라는 문장이다.

## 분석

### 핵심 결정은 “기존 API가 곧 도구”라는 베팅이다

글이 결론에서 스스로 밝히듯 설계를 끌고 간 통찰은 하나다.
에이전트에게 도구를 주는 가장 빠른 길은 이미 있는 API라는 것이다.
그래서 서비스 팀에게 에이전트용 서버를 새로 쓰라고 요구하지 않고,
IDL을 기계적으로 번역해 도구를 만든다.
Muttley를 거쳐 호출하므로 하류 서비스는 아무것도 바꾸지 않아도 된다.

이 베팅은 MCP 커뮤니티에서 자주 나오는 조언과 정면으로 부딪힌다.
도구는 API를 얇게 감싼 것이 아니라 에이전트의 작업 단위에 맞춰 설계해야 한다는
조언이다.
Uber도 이 긴장을 알고 있다.
레지스트리에는 무코드로 감싼 도구와
MCPFx로 처음부터 에이전트에 맞춰 만든 네이티브 도구가 함께 있고,
글은 둘을 같은 레지스트리의 두 극단으로 설명한다.
다만 어느 쪽이 얼마나 쓰이는지,
래핑 도구로 시작했다가 네이티브로 옮겨 간 사례가 있는지는 말하지 않는다.

그래서 이 결정은 품질보다 범위를 먼저 고른 것으로 읽힌다.
수천 개 서비스를 한꺼번에 에이전트가 닿을 수 있게 만드는 것이 첫 목표였고,
도구 하나하나의 쓰기 좋음은 LLM이 생성한 설명과 소유 팀의 검토에 맡겼다.
뒤에서 다룰 컨텍스트 문제는 이 선택의 직접적인 대가다.

### 도구 설명이 소유자가 승인하는 설정이 되었다

“발견이 노출을 뜻하지 않는다”는 원칙은 소유권에 관한 결정이다.
AutoCrawler는 서비스 팀 모르게 도구를 만들 수 있지만,
켜는 권한은 서비스 팀에 남긴다.
기술적으로 만들 수 있는 것과 조직적으로 책임질 수 있는 것을 분리한 셈이다.

흥미로운 것은 그 대상이 코드가 아니라 도구 설명이라는 점이다.
LLM이 초안을 쓰고, 사람이 diff로 검토해 승인하고, 배포하고, 필요하면 되돌린다.
에이전트가 어떤 도구를 언제 고를지는 이 설명에 좌우되므로,
설명은 사실상 에이전트 행동을 바꾸는 프롬프트다.
Uber는 그 프롬프트를 설정 관리 체계 안에 넣었다.

### 컨텍스트 문제가 MCP의 기본 모델을 밀어냈다

글의 뒷부분은 MCP가 원래 상정한 사용 방식에서 점점 멀어지는 과정이다.
MCP의 기본 모델은 클라이언트가 서버를 연결하고 도구 목록을 받아 모델에게 보여
주는 것이다.
도구가 5,000개가 되자 이 모델이 깨졌다.
Omni MCP는 도구 목록 대신 “도구를 찾는 도구” 네 개만 보여 주고,
Code Mode는 아예 MCP 클라이언트를 거치지 않고 CLI로 검색하고 호출한다.

그리고 사내 코딩 에이전트의 기본값이 된 것은 Code Mode다.
즉 Uber 안에서 가장 많이 쓰일 경로에서 에이전트는 MCP 프로토콜을 직접 말하지
않는다.
MCP는 게이트웨이 안쪽의 표준 봉투, 다시 말해 등록과 권한과 번역을 위한 내부
형식으로 남고,
에이전트 쪽 인터페이스는 검색과 호출과 파일이라는 셸의 언어로 돌아갔다.
이 저장소의 「MCP is dead. Long live the CLI」 계열 글들이 주장한 방향을
가장 큰 MCP 운영자 중 하나가 실무에서 확인한 셈이다.

### 다른 회사들도 같은 모양으로 수렴하고 있다

이 저장소에는 Pinterest의 MCP 생태계와 DoorDash의 에이전트 게이트웨이를 다룬
문서가 있다.
세 회사의 설계는 놀랄 만큼 비슷하다.
중앙 레지스트리가 카탈로그이자 정책 결정 지점이 되고,
게이트웨이가 신원과 인가와 관측을 맡으며,
도구 목록을 그대로 모델에 보여 주는 대신 큐레이션하거나 검색하게 한다.

이 수렴은 MCP 명세가 비워 둔 층이 무엇인지를 보여 준다.
명세는 클라이언트와 서버 사이의 대화를 정의하지만,
수백 개 서버를 누가 소유하고 누가 켜고 누가 호출할 수 있는지는 정의하지 않는다.
기업들은 그 층을 각자 게이트웨이로 채우고 있고,
Uber 글은 그중에서도 기존 서비스 자산이 가장 큰 회사의 답이다.

## 비평

### 800개와 5,000개는 재고이지 성과가 아니다

글이 내세우는 숫자는 서버와 도구의 개수뿐이다.
그런데 AutoCrawler는 발견한 모든 것을 비활성 상태로 등록한다.
5,000개 가운데 실제로 켜진 도구가 몇 개인지,
켜진 도구 가운데 에이전트가 실제로 호출하는 도구가 몇 개인지는 나오지 않는다.
자동 수집으로 쌓은 목록의 크기는 크롤러의 성능을 보여 줄 뿐,
게이트웨이가 에이전트 작업을 얼마나 바꿨는지는 보여 주지 않는다.

결론은 팀이 몇 분 만에 연결할 수 있는 플랫폼이 되었다고 말하지만,
호출량, 오류율, 지연, 작업 성공률, 비용 절감 같은 지표는 하나도 없다.
특히 Response Projection과 Code Mode는 컨텍스트와 비용 문제를 풀려고 만든
기능인데,
토큰을 얼마나 줄였는지조차 밝히지 않는다.
설계를 공유한다는 글의 목적을 감안해도,
다른 회사가 이 설계를 따라 할지 판단하려면 바로 그 숫자가 필요하다.

### “실시간 반영”과 “정해진 주기”는 같은 말이 아니다

글은 데이터 평면이 설정을 정해진 주기로 다시 읽어 변경이 실시간으로 반영된다고
쓴다.
두 표현은 양립하지 않는다.
주기적 폴링은 최대 한 주기만큼 늦는 결과적 일관성이다.
평소 도구 설명을 고칠 때는 문제가 되지 않지만,
사고 중에 위험한 도구를 끌 때는 그 지연이 곧 노출 시간이다.

소유자가 승인하고 롤백할 수 있다는 절차는 잘 설계되어 있지만,
그 롤백이 언제 모든 게이트웨이 인스턴스에 닿는지,
긴급 차단용으로 주기를 건너뛰는 경로가 있는지는 나오지 않는다.
에이전트 시스템에서 비상 정지 장치의 지연은 부차적인 세부가 아니라 안전
속성이다.

### 보안 절은 가장 어려운 질문을 피한다

보안에 관한 설명은 두 문단이다.
도구 단위 인가와 개인정보 자동 제거가 있다는 것인데,
무엇을 기준으로 민감 데이터를 찾아내는지,
잘못 지워서 에이전트가 필요한 값을 잃는 경우를 어떻게 다루는지는 나오지 않는다.
정규식 기반이든 분류 모델 기반이든 제거는 확률적이고,
놓친 데이터는 그대로 모델 컨텍스트로 들어간다.

더 큰 공백은 위임된 신원이다.
charter 정책은 호출 주체를 사람, 서비스, 에이전트로 구분하지만,
에이전트가 사람을 대신해 호출할 때 권한이 누구 기준으로 정해지는지는 말하지
않는다.
외부 MCP 서버에서는 게이트웨이가 사용자 토큰을 그대로 넘기고 별도 서비스가
외부 토큰으로 바꾼다.
에이전트가 프롬프트 주입으로 조종당하면 그 사용자의 권한 전체가 외부 서비스로
흘러갈 수 있는데,
이른바 치명적 삼중 조합(lethal trifecta)이나 혼동된 대리인(confused deputy)
문제에 대한 언급은 없다.
같은 블로그가 2026년 8월에 에이전트 신원 문제를 따로 다룬 글을 냈으니
그쪽에 답이 있을 수 있지만,
이 글만으로는 게이트웨이가 무엇을 막고 무엇을 막지 못하는지 알 수 없다.

### Response Projection은 실패를 조용하게 만든다

Response Projection은 LLM에게 필요한 필드의 경로를 직접 적게 한다.
모델이 필요한 필드를 빠뜨리면 게이트웨이는 그 필드를 지운 응답을 정상 결과처럼
돌려준다.
모델은 데이터가 없다고 판단하고 다음 단계로 넘어갈 수 있고,
그 실수는 오류가 아니라 그럴듯한 오답으로 나타난다.

GraphQL에서는 클라이언트 코드가 스키마에 맞춰 필드를 고르고 타입 검사가 이를
잡아 준다.
여기서는 그 역할을 확률적인 모델이 맡는다.
글은 이 기능이 엔터프라이즈 수준의 API 스키마 호환성을 확장하게 해 주었다고만
말하고,
투영이 틀렸을 때 재요청하게 하는 장치나 정확도 측정은 언급하지 않는다.
비용을 줄이는 기능일수록 줄어든 정보가 무엇이었는지 기록해야 하는데,
그 부분이 빠져 있다.

## 인사이트

### 이 게이트웨이가 싼 이유는 10년 치 플랫폼 투자 위에 있기 때문이다

Uber의 설계가 매끄러워 보이는 것은 게이트웨이가 뛰어나서라기보다
그 아래에 이미 IDL 레지스트리, Cadence, Muttley, 사내 접근 제어 시스템이 있었기
때문이다.
모든 서비스의 인터페이스가 Protobuf나 Thrift로 기계가 읽을 수 있게 등록되어
있으니 크롤러가 도구를 만들 수 있고,
서비스 메시가 라우팅을 맡으니 게이트웨이는 번역만 하면 된다.

이것이 만드는 2차 효과는 MCP 도입 속도의 격차다.
스키마 관리가 엄격한 조직은 기존 API를 거의 공짜로 에이전트에게 열 수 있지만,
문서화되지 않은 REST 엔드포인트와 구전으로 전해지는 계약 위에서 돌아가는 조직은
도구 하나하나를 손으로 만들어야 한다.
에이전트 시대에 스키마 거버넌스는 위생 문제가 아니라 경쟁력이 되고,
이 글을 그대로 따라 하려는 회사가 먼저 확인해야 할 것은 게이트웨이 설계가 아니라
자기 IDL 레지스트리의 상태다.

### 중앙 번역 허브는 ESB가 걸었던 길을 다시 걸을 위험이 있다

여러 프로토콜을 하나의 중앙 계층에서 번역하고,
라우팅과 보안과 변환을 한곳에 모으는 구조는 처음이 아니다.
2000년대 SOA 시대의 엔터프라이즈 서비스 버스(ESB)가 정확히 그런 약속을 했다.
ESB는 결국 모든 변경이 거쳐 가는 병목이 되었고,
비즈니스 로직이 조금씩 버스 안으로 스며들면서 아무도 전체를 이해하지 못하는
중앙 서비스가 되었다.
마이크로서비스 운동이 “똑똑한 엔드포인트, 멍청한 파이프”를 외친 것이 그
반작용이었다.

MCP Gateway는 이미 번역만 하지 않는다.
개인정보 제거, 응답 투영, 단계적 발견, 사용자 토큰 교환이 모두 게이트웨이
안에 있다.
기능 하나하나는 타당하지만,
에이전트에 필요한 정책이 생길 때마다 게이트웨이에 넣는 것이 가장 쉬운 길이
되면 같은 일이 반복된다.
Uber가 이 계층을 얇게 유지할 수 있을지는 앞으로 무엇을 게이트웨이 밖에 두기로
결정하느냐에 달려 있다.

### 도구 설명을 승인하는 것과 도구 설명을 시험하는 것은 다르다

도구 설명에 diff 승인과 롤백을 붙인 것은 좋은 출발이지만,
코드 리뷰가 테스트를 대신하지 못하듯 설명 승인도 행동 검증을 대신하지 못한다.
설명 한 줄을 바꾸면 에이전트가 그 도구를 고르는 빈도와 상황이 바뀌고,
그 영향은 같은 레지스트리의 다른 도구 선택에까지 번진다.
5,000개 도구 사이의 선택 경쟁에서 한 설명의 변화는 다른 도구의 호출량을 빼앗는
변화이기도 하다.

이 지점에서 소유 모델에 긴장이 생긴다.
서비스 팀은 자기 도구 설명만 책임지지만,
에이전트의 선택 품질은 전체 설명 집합의 성질이다.
결국 누군가는 설명 변경마다 대표 작업 묶음을 다시 돌려 도구 선택이 나빠지지
않았는지 보는 평가 체계를 운영해야 하고,
그것은 개별 서비스 팀이 아니라 플랫폼 팀의 일이 될 수밖에 없다.

### 도구가 수천 개가 되면 에이전트의 능력은 검색 품질이 된다

Omni MCP의 `discover_server`는 질의 의도로 서버를 찾는다.
Code Mode의 `aifx mcp search`는 모든 서버를 가로질러 도구를 찾는다.
도구가 수천 개인 환경에서 에이전트가 무엇을 할 수 있는지는 모델의 추론 능력보다
이 검색이 올바른 도구를 상위에 올리느냐에 먼저 좌우된다.

이 사실은 실패의 모양을 바꾼다.
검색이 엉뚱한 도구를 돌려주면 에이전트는 잘못된 도구로 그럴듯하게 일을 끝내거나,
할 수 있는 일을 할 수 없다고 판단한다.
사용자는 이를 “모델이 멍청하다”고 경험하지만 원인은 정보 검색 문제다.
도구 플랫폼을 운영하는 팀은 이제 검색 엔진 팀이 다뤄 온 지표,
즉 재현율과 순위 품질과 질의 실패 분석을 자기 지표로 가져와야 한다.
5,000이라는 숫자는 그 일이 이미 시작되었다는 신호다.
