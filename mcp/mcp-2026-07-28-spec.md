# MCP가 무상태로 간다: 2026-07-28 스펙 릴리스 후보

원문: [The 2026-07-28 MCP Specification Release Candidate | Model Context Protocol Blog](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)

## 요약

MCP `2026-07-28` 릴리스 후보(RC)는 출시 이후 가장 큰 프로토콜 개정으로, 2026 로드맵을 구현한다.
네 가지 축이다 — 평범한 HTTP 인프라에서 확장되는 무상태 코어(stateless core), MCP Apps(서버
렌더링 UI)와 Tasks 확장 같은 확장(extensions), OAuth·OpenID Connect 배포와 더 밀착하는 인가(authorization),
그리고 만들어 둔 것을 깨지 않고 프로토콜을 진화시키는 공식 폐기 정책(deprecation policy)이다.
실무적 효과는 즉각적이다 — 예전에 sticky session, 공유 세션 저장소, 게이트웨이의 심층 패킷 검사가
필요하던 원격 MCP 서버가 이제 평범한 라운드로빈 로드밸런서 뒤에서 `Mcp-Method` 헤더로 라우팅되고,
클라이언트는 서버의 `ttlMs`가 허용하는 만큼 `tools/list` 응답을 캐시할 수 있다.

핵심 변화는 프로토콜 계층의 무상태화다.
`2025-11-25`에서는 도구 호출 전에 `initialize`로 세션을 맺고 서버가 발급한 `Mcp-Session-Id`를
이후 모든 요청이 지녀야 해서 클라이언트가 특정 인스턴스에 고정됐다.
`2026-07-28`에서는 `initialize`/`initialized` 핸드셰이크가 제거되고(SEP-2575), 프로토콜 버전·클라이언트
정보·기능이 매 요청의 `_meta`로 이동하며, `server/discover`로 필요할 때 서버 기능을 가져온다.
`Mcp-Session-Id` 헤더와 그에 딸린 세션도 제거되어(SEP-2567), 어떤 MCP 요청이든 어떤 서버 인스턴스에나
도착할 수 있게 됐다.

프로토콜이 무상태라고 애플리케이션이 무상태여야 하는 것은 아니다.
상태를 이어가야 하는 서버는 HTTP API가 늘 해 온 것을 하면 된다 — 도구에서 명시적 핸들(`basket_id`,
`browser_id`)을 발급하고 모델이 이후 호출에 일반 인자로 되돌려주게 하는 것이다.
MCP 팀은 이 패턴(모델이 식별자를 한 호출에서 다음으로 실로 꿰는 것)이 세션 상태의 대체물을
넘어 더 강력하다고 본다 — 모델이 핸들을 도구 간에 조합하고 추론하고 넘겨줄 수 있으며, 전송
메타데이터에 숨겨진 외부 관리 세션 상태로는 못 하던 것이다.
무상태 프로토콜이라도 서버가 처리 중에 클라이언트에 무언가를 요청(elicitation)할 수 있어야 하므로,
서버 개시 요청은 클라이언트 요청을 능동 처리하는 동안에만 허용되고(SEP-2260), SSE 스트림을 열어
두는 대신 `InputRequiredResult`를 반환하는 Multi Round-Trip 방식(SEP-2322)으로 재구성됐다.

나머지 변화도 크다.
MCP Apps(SEP-1865)는 서버가 상호작용 HTML을 샌드박스 iframe에 렌더링하게 하며, 도구가 UI
템플릿을 미리 선언해 호스트가 프리페치·캐시·보안 검토할 수 있다.
Tasks는 실험적 코어 기능에서 확장으로 졸업했고(무상태 모델에 맞춰 재설계), 인가는 6개 SEP로
강화되어 클라이언트가 RFC 9207에 따라 `iss`를 검증해야 하는 등 OAuth·OIDC 실전 배포에 밀착한다.
확장은 일급이 되어 reverse-DNS ID로 식별되고 `ext-*` 저장소에서 독립적으로 버전이 매겨지며(SEP-2133),
공식 폐기 정책도 도입됐다.
RC는 2026년 5월 21일에 잠겼고 최종 스펙은 7월 28일 발행되며, 이 10주는 SDK·클라이언트 구현자가
실제 워크로드로 검증하는 창이다 — 이 개정은 파괴적 변경(breaking changes)을 포함한다.

## 분석

### 이 개정의 핵심은 “상태를 전송 계층에서 애플리케이션으로 밀어낸다”이다

이 RC의 모든 변화는 하나의 결정에서 파생된다.
프로토콜이 관리하던 세션 상태를 없애고, 그 상태를 애플리케이션이 명시적 핸들로 다루게 한 것이다.

이 결정이 근본적인 이유는 그것이 확장성의 병목을 제거하기 때문이다.
`Mcp-Session-Id`가 클라이언트를 특정 인스턴스에 고정하면 수평 확장에 sticky routing과 공유 세션
저장소가 필요했다 — 이는 상태를 가진 시스템의 고전적 확장 비용이다.
핸드셰이크와 세션을 없애 모든 요청을 자기완결적으로 만들면, 어떤 요청이든 어떤 인스턴스에나
도착할 수 있어 평범한 라운드로빈 로드밸런서로 확장된다.
이것은 웹 아키텍처가 오래전에 배운 교훈 — 무상태 서버가 수평 확장을 가능하게 한다 — 을 MCP에
적용한 것이다.

이 결정이 앞서 여러 문서에서 본 패턴과 정확히 이어진다.
celld가 “상태를 노드에서 분리해 버킷에 두어 노드를 교체 가능하게” 만든 것[^ref-celld], session-token-economics에서
본 “핸드오프 브리핑으로 상태를 명시적으로 나른다”는 것이[^ref-session] 여기서 프로토콜 설계 원칙으로
나타난다.
특히 MCP의 “명시적 핸들” 패턴 — `basket_id`를 발급해 모델이 되돌려주게 하는 — 은 celld의 명시적
셀 이름과 구조적으로 동일하다.
무상태화는 MCP만의 발명이 아니라, 상태를 인프라에서 꺼내 명시적으로 다루는 분산 시스템의 보편적
성숙 궤적이다.

### “상태를 모델에게 보이게 한다”는 재프레임이 이 설계의 진짜 통찰이다

MCP 팀이 명시적 핸들 패턴을 “대체물이 아니라 더 강력한 것”이라 부른 것은, 무상태화를 단순한
확장성 트릭이 아니라 모델과의 협업 방식 개선으로 재프레임한다.
숨겨진 세션 상태를 모델이 볼 수 있는 명시적 인자로 바꾼 것이다.

이 재프레임이 중요한 이유는 그것이 LLM의 작동 방식에 맞기 때문이다.
전송 메타데이터에 숨겨진 세션 상태는 모델이 추론할 수 없지만, `basket_id`가 일반 인자로 대화에
드러나면 모델이 그것을 조합하고 추론하고 도구 간에 넘길 수 있다.
이것은 working-memory-advantage에서 본 “LLM의 기억은 컨텍스트에 드러난 토큰”이라는 관찰[^ref-wm]과
정확히 맞물린다 — 상태가 컨텍스트에 보여야 모델이 그것을 다룬다.
MCP 팀은 확장성 요구(무상태)와 LLM의 인지 특성(보이는 것만 추론)이 우연히 같은 방향 — 상태를
명시적으로 드러내기 — 을 가리킴을 발견한 것이다.

이 통찰이 프로토콜 설계의 일반 원칙을 시사한다.
LLM을 위한 프로토콜은 사람이나 전통적 클라이언트를 위한 것과 다르다 — 숨겨진 상태는 사람에겐
편의지만 모델에겐 장벽이다.
서버 개시 요청을 “클라이언트 요청을 처리하는 동안에만” 허용한 것(SEP-2260)도 같은 방향이다 —
“사용자가 난데없이 프롬프트받지 않고 모든 elicitation이 그들이 시작한 것으로 추적된다”는 것은,
상태와 인과를 명시적이고 추적 가능하게 만드는 설계 철학의 일관된 적용이다.
무상태화의 진짜 값은 서버 비용 절감이 아니라, 프로토콜을 LLM의 사고 방식에 맞게 재설계한 것이다.

### 확장·폐기 정책의 공식화가 프로토콜의 성숙을 알린다

이 RC에서 무상태화만큼 중요한 것은 확장을 일급으로 만들고 공식 폐기 정책을 도입한 것이다.
이것은 MCP가 실험적 프로토콜에서 장기 유지되는 표준으로 넘어가는 신호다.

이 공식화가 중요한 이유는 그것이 진화의 규율을 세우기 때문이다.
확장이 reverse-DNS ID로 식별되고 `ext-*` 저장소에서 독립적으로 버전이 매겨지는 것(SEP-2133)은,
코어를 얇게 유지하면서 실험을 주변부로 밀어내는 구조다 — Tasks가 코어에서 확장으로 “졸업”한
것이 이 구조의 첫 적용이다.
공식 폐기 정책은 “만들어 둔 것을 깨지 않고 진화한다”는 약속으로, 프로토콜이 프로덕션 의존성을
갖게 됐음을 인정하는 것이다.

이 성숙이 앞서 ActivityPub 문서에서 본 긴장과 이어진다.
ActivityPub가 “100개 이상의 구현과 수천만 사용자의 그래프를 백지 재작성으로 깨서는 안 된다”는
성숙의 부담을 진 것처럼[^ref-activitypub], MCP도 이제 파괴적 변경의 비용을 관리해야 한다.
RC를 5월에 잠그고 최종을 7월에 내는 10주 검증 창, Tier 1 SDK의 지원 기대는 이 부담을 제도화한
것이다.
확장·폐기 정책의 공식화는 화려하지 않지만, 프로토콜이 “빠르게 움직이며 깨뜨리는” 단계에서 “안정적으로
진화하는” 단계로 넘어가는 진짜 분기점이다.

## 비평

### “무상태 프로토콜, 상태적 애플리케이션”이 복잡도를 옮길 뿐 없애지 않는다

MCP 팀은 무상태화를 순전한 이득으로 그리지만, 상태 관리의 복잡도는 사라진 게 아니라 프로토콜에서
애플리케이션으로 옮겨졌을 뿐이다.

이 이동이 문제인 이유는 애플리케이션 개발자가 그 복잡도를 떠안기 때문이다.
예전에는 프로토콜이 세션을 관리해 줬지만, 이제 서버가 명시적 핸들을 발급·검증·만료·인가하는 로직을
직접 구현해야 한다.
`basket_id`를 발급하는 것은 쉬워 보이지만, 그 핸들의 수명·소유권·재사용 방지·권한 검사는 모두
애플리케이션의 몫이 된다 — 이것은 앞서 celld 문서에서 본 “API 키 불필요의 편의가 복잡도를 숨길
뿐”이라는 패턴[^ref-celld]과 같다.
MCP 팀이 “HTTP API가 늘 해 온 것”이라 한 것은 사실이지만, 그 “늘 해 온 것”이 바로 상태 관리의
어려움 그 자체다.

이 이동이 새로운 함정을 연다.
상태를 모델이 다루는 인자로 만들면, 모델이 핸들을 잘못 다룰 위험 — 만료된 핸들을 재사용하거나,
다른 세션의 핸들을 혼동하거나, 핸들을 노출해서는 안 될 곳에 노출하는 — 이 생긴다.
전송 계층의 세션은 최소한 프로토콜이 검증했지만, 모델이 실로 꿰는 핸들은 모델의 신뢰성에 의존한다.
MCP 팀은 “모델이 핸들을 조합하고 추론한다”를 강점으로 들지만, 앞서 여러 문서에서 본 “모델은
모호함 앞에서 대담하게 가정한다”는 위험[^ref-wm]이 여기서 “모델이 핸들을 잘못 조합한다”로 나타날
수 있다.
무상태화는 서버 확장을 쉽게 하지만, 그 대가로 상태 정합성의 책임을 프로토콜의 검증에서 모델의
판단과 애플리케이션의 구현으로 분산시킨다 — 이 트레이드오프를 RC 문서는 “더 강력하다”는 낙관으로만
서술한다.

### 파괴적 변경의 비용을 생태계 관점에서 충분히 다루지 않는다

RC 문서는 파괴적 변경을 “Release Timeline and Validation” 섹션 한 줄로 처리하지만, 갓 성장하는
MCP 생태계에서 파괴적 변경의 비용은 그보다 훨씬 크다.

이 과소평가가 문제인 이유는 MCP의 채택이 이제 막 확산됐기 때문이다.
`initialize` 핸드셰이크와 `Mcp-Session-Id`를 제거하는 것은 기존 모든 MCP 서버·클라이언트의 수정을
요구한다.
MCP가 “출시 이후 가장 큰 개정”이라는 것은 곧 “가장 많은 기존 구현을 깨뜨리는 개정”이라는 뜻이다.
10주 검증 창과 Tier 1 SDK 지원 기대는 대형 SDK에는 충분할지 몰라도, 수많은 소규모·독립 MCP
서버 구현자에게는 갑작스러운 부담이다 — 그들은 로드맵을 좇지 않고 한 번 만들어 둔 것을 쓰고
있었을 것이다.

이 문제가 프로토콜 성숙의 역설을 드러낸다.
MCP는 확장·폐기 정책을 공식화해 “안정적 진화”를 약속하는 바로 그 릴리스에서, 역사상 가장 큰
파괴적 변경을 낸다.
이것은 “다음부터는 안 깨뜨리겠다, 단 이번 한 번만”이라는 구조인데, 성장기 프로토콜에서 이런
대규모 파괴는 채택자의 신뢰를 시험한다.
앞서 ActivityPub 문서에서 본 “설치 기반이 실재하면 표준 진화가 어려워진다”는 긴장[^ref-activitypub]이
MCP에서는 아직 초기라 상대적으로 감당 가능하지만, 그렇다고 비용이 없는 것은 아니다.
RC 문서가 무상태화의 이득(확장성)은 상세히 그리면서 그 전환 비용(모든 기존 구현의 수정)은 타임라인
한 줄로 처리한 것은, 프로토콜 설계자의 관점과 구현자의 관점 사이의 비대칭을 드러낸다.

### MCP Apps의 샌드박스 iframe이 새로운 보안 표면을 연다

RC는 MCP Apps(서버 렌더링 HTML UI)를 확장의 대표 사례로 내세우지만, 서버가 클라이언트에서
UI를 렌더링하는 것이 여는 보안 표면을 충분히 다루지 않는다.

이 공백이 문제인 이유는 서버 렌더링 UI가 신뢰 경계를 넘기 때문이다.
MCP 서버는 종종 신뢰할 수 없는 제3자가 운영하는데, 그런 서버가 보낸 HTML을 호스트가 렌더링하면
— 아무리 샌드박스 iframe이라도 — 공격 표면이 생긴다.
RC는 “도구가 UI 템플릿을 미리 선언해 호스트가 프리페치·캐시·보안 검토할 수 있다”고 하지만,
“보안 검토할 수 있다”는 가능성이지 보장이 아니다.
앞서 daiso-mcp 문서에서 본 “MCP가 비공식·신뢰 불가 데이터를 감싼다”는 현실[^ref-daiso]을 생각하면,
그런 서버가 UI까지 렌더링하는 것은 데이터 노출을 넘어 능동적 공격(피싱 UI, 클릭재킹)의 가능성을
연다.

이 문제가 아키텍처적 긴장을 드러낸다.
MCP의 매력은 그것이 얇은 프로토콜 — 도구 호출과 JSON — 이라는 데 있었는데, MCP Apps는 그것을
UI 렌더링 플랫폼으로 확장한다.
프로토콜이 UI를 다루기 시작하면 웹 보안의 모든 문제 — XSS, CSRF, 클릭재킹, 데이터 유출 —
가 따라 들어온다.
RC가 이것을 “샌드박스 iframe”과 “보안 검토 가능”으로 처리한 것은, 브라우저 보안 역사가 보여준
“샌드박스는 반복적으로 뚫린다”는 교훈을 낙관적으로 지나친 것이다.
무상태화가 프로토콜을 단순하게 만드는 방향이라면, MCP Apps는 반대로 프로토콜의 책임을 UI로
넓히는 방향이며, 이 두 방향의 긴장 — 얇게 유지하기 대 기능 확장 — 을 RC는 조화롭게 그리지만
실제로는 상충한다.

## 인사이트

### 무상태화는 “LLM을 위한 프로토콜”이 사람을 위한 프로토콜과 다르게 진화함을 보여준다

이 RC의 가장 깊은 함의는 확장성 개선을 넘어, LLM이 소비자인 프로토콜이 독자적 설계 원칙을
갖기 시작했다는 것이다.
“상태를 모델이 볼 수 있게 하라”는 원칙은 사람을 위한 프로토콜에는 없던 것이다.

이 차이가 근본적인 이유는 소비자의 인지 구조가 다르기 때문이다.
전통적 클라이언트(브라우저, 앱)는 숨겨진 상태(쿠키, 세션)를 문제없이 다루지만, LLM은 컨텍스트에
보이는 것만 추론한다.
그래서 사람을 위해서는 상태를 숨기는 게 편의였지만, LLM을 위해서는 상태를 드러내는 게 필수가
된다.
MCP가 세션을 없애고 명시적 핸들로 간 것은 확장성 때문이기도 하지만, 동시에 LLM이 그 핸들을
추론할 수 있기 때문이다 — 두 요구가 우연히 같은 방향을 가리킨 것이 이 설계를 자연스럽게 만들었다.

이 통찰의 2차 효과는 프로토콜 설계의 새 분야다.
LLM이 API의 주 소비자가 되면, API 설계 자체가 “LLM이 추론 가능한가”를 기준으로 재편된다.
working-memory-advantage에서 본 “LLM의 이점은 외부화된 명시적 기억”[^ref-wm]이 여기서 “LLM을 위한
API는 상태를 명시적으로 노출해야 한다”는 설계 규범으로 확장된다.
숨겨진 상태, 암묵적 순서, 마법 같은 부수 효과 — 사람이나 전통 클라이언트에는 편의였던 것들 —
이 LLM 소비자 앞에서는 장벽이 된다.
MCP의 무상태화는 이 재편의 초기 사례이며, 앞으로 “LLM-friendly API 설계”가 REST·GraphQL에
이은 독자적 설계 패러다임으로 자리 잡을 것을 예고한다 — 그 핵심 원칙은 “모델이 볼 수 없는 상태는
모델이 다룰 수 없다”이다.

### 상태의 명시화는 확장성과 감사가능성을 동시에 주지만 모델 신뢰라는 새 의존을 만든다

MCP의 명시적 핸들 패턴은 확장성만이 아니라 감사가능성(auditability)이라는 뜻밖의 이득을 주지만,
그 대가로 상태 정합성을 모델의 신뢰성에 의존하게 만든다.
드러난 상태는 검사할 수 있지만, 그 상태를 실로 꿰는 것이 모델이라면 정합성은 모델에 달린다.

이 양면성이 구조적인 이유는 명시성이 양방향으로 작동하기 때문이다.
상태가 대화의 인자로 드러나면 — `basket_id`가 로그에 보이면 — 무슨 일이 일어났는지 추적·감사·디버깅이
쉬워진다.
이것은 숨겨진 전송 세션에서는 불가능하던 투명성이며, 앞서 handles 문서에서 본 “검사가 손잡이에서
서명으로, 결과에서 과정으로 옮겨간다”는[^ref-handles] 흐름과 같은 방향이다 — 상태가 보이면 책임도
추적된다.
그러나 그 상태를 다음 호출로 넘기는 주체가 모델이라면, 모델이 잘못된 핸들을 넘기거나 핸들을
누락하면 애플리케이션 상태가 조용히 어긋난다.

이 통찰의 함의는 신뢰 경계의 이동이다.
전통적 세션에서는 프로토콜이 상태 정합성을 보장했지만(서버가 세션 ID를 검증), 명시적 핸들에서는
모델이 그 정합성의 일부를 진다.
이것은 앞서 여러 문서에서 본 “되돌릴 수 없는 행위에 모델을 붙일 때의 위험”[^ref-celld]과 이어진다 —
금융 거래의 `basket_id`를 모델이 잘못 꿰면 그 결과는 실재한다.
MCP는 이를 완화하려 “서버 개시 요청은 처리 중에만, 모든 elicitation은 추적 가능하게”라는 규율을
두지만, 근본적으로 상태 정합성의 책임 일부를 확률적 모델에 넘긴 것은 사실이다.
명시적 상태의 진짜 트레이드오프는 “투명성을 얻는 대신 정합성을 모델에 의존한다”이며, 이것이
LLM 시대 프로토콜 설계의 핵심 긴장 — 모델을 신뢰할 수 있게 만드는 것과 모델에 의존하는 것의
경계 — 을 드러낸다.

### 얇은 코어와 두꺼운 확장의 분리가 프로토콜 거버넌스의 승부처가 된다

이 RC에서 코어를 무상태로 얇게 만들면서 UI·Tasks를 확장으로 밀어낸 것은, MCP의 장기적 성패가
기술이 아니라 확장 거버넌스에 달렸음을 시사한다.
얇은 코어는 합의하기 쉽지만, 두꺼운 확장 생태계는 파편화의 위험을 진다.

이 구조가 근본적인 이유는 확장이 상호운용성의 시험대이기 때문이다.
reverse-DNS ID로 식별되고 독립적으로 버전이 매겨지는 확장은 유연하지만, 동시에 “모두가 자기
확장을 만드는” 파편화를 부를 수 있다 — 앞서 Ralph 문서에서 본 “얇은 패턴이 수십 개 변종을
낳는다”는 현상[^ref-ralph]의 프로토콜판이다.
MCP Apps 하나만 봐도, 서로 다른 호스트가 서로 다른 방식으로 UI를 렌더링하면 “한 번 만들어
어디서나 도는” 상호운용성이 깨진다.
확장이 일급이 된다는 것은 코어의 안정성을 얻는 대신 확장 층의 파편화 위험을 지는 것이다.

이 통찰의 함의는 MCP의 진짜 경쟁이 코어 스펙이 아니라 확장 생태계에서 벌어진다는 것이다.
무상태 코어는 기술적으로 우아하고 합의 가능하지만, 그것만으로는 아무것도 흥미롭지 않다 — 가치는
MCP Apps, Tasks 같은 확장에 있다.
앞서 ActivityPub·celld 문서에서 본 “개방 표준의 성패는 조율 거버넌스에 달렸다”는 원리[^ref-activitypub]가
여기서 “확장 거버넌스가 MCP의 성패를 가른다”로 나타난다.
SEP 프로세스, Extensions Track, 위임된 유지관리자 — 이 거버넌스 장치들이 확장의 폭발적 다양성과
상호운용성의 붕괴 사이에서 균형을 잡을 수 있는가가 관건이다.
무상태화라는 기술적 성취는 이 거버넌스 시험의 전제일 뿐이며, MCP가 표준으로 살아남을지는 얇은
코어의 우아함이 아니라 두꺼운 확장 층을 파편화 없이 다스릴 수 있는가에 달렸다.
