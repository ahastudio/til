# DoorDash가 에이전트-도구 접근을 위한 중앙 게이트웨이를 만든 이유

원문: [How DoorDash Built a Centralized Gateway for AI Agent-Tool Access](https://careersatdoordash.com/blog/how-doordash-built-a-centralized-gateway-for-ai-agent-tool-access/)

## 요약

DoorDash의 Tech Lead Engineer인 Siddarth Kodwani와 Principal Engineer인 Vasily Vlasov가 2026년 7월 30일에 쓴 글이다.
AI 에이전트가 사내 API, 엔지니어링 시스템, 관측 플랫폼, 티켓 시스템, 지식 베이스, 서드파티 SaaS에 접근할 때 생기는 문제를 플랫폼 역량으로 해결한 Agent Gateway를 소개한다.

MCP(Model Context Protocol)는 에이전트와 서버가 역량을 기술하고 발견하고 호출하는 공통 방식을 제공해 도구 노출을 쉽게 만들었다.
그런데 에이전트가 실험에서 실제 워크플로로 옮겨가자 다른 문제가 나타났다 — MCP는 도구 호출의 모양은 표준화했지만 그 호출을 둘러싼 프로덕션 질문에는 답하지 않았다.
어떤 에이전트가 이 도구를 호출해도 되는가, 어떤 사용자·팀·서비스를 대신해 행동하는가, 어떤 자격 증명을 써야 하는가, 에이전트가 애초에 어떤 도구 부분집합을 봐야 하는가, 접근을 어떻게 회수하는가, 호출 후 무슨 일이 있었는지 어떻게 아는가.

이 질문들은 빠르게 커진다.
코딩 에이전트 하나가 GitHub, Jira, 코드 검색, CI, 관측, 문서를 필요로 할 수 있고, 서드파티 MCP 서버는 워크플로에 다섯 개만 필요한데 수백 개 도구를 노출할 수 있다.
사용자 대면 에이전트는 사용자의 OAuth 승인이 필요한 반면 팀 자동화는 비개인 서비스 주체를 써야 한다.
각 팀이 이 문제를 따로 풀면 에이전트-도구 짝마다 자체 인증 코드, OAuth 흐름, 비밀 처리, 도구 카탈로그, 속도 제한, 로그가 생긴다.

그래서 Agent Gateway를 만들었다.
에이전트가 도구를 발견하고 호출하는 단일한 통제된 진입점이며, 호출자를 인증하고, 인가를 확인하고, 승인된 도구 표면만 노출하고, 올바른 자격 증명을 주입하고, 하류 MCP 서버로 라우팅하고, 모든 호출에 대해 구조화된 사용 이벤트를 기록한다.
글은 이것이 단순한 프록시가 아니라 에이전트 생태계의 컨트롤 플레인이라고 강조한다.

### 문제의 세 부분

프로덕션에서 어려운 문제는 세 차원이라고 정리한다.
첫째는 접근이다 — 누가 호출하는지, 허용되는지, 어떤 자격 증명 모델이 적용되는지(사내 아이덴티티, 게이트웨이 보유 토큰, 사용자별 OAuth, 서비스 주체)를 플랫폼이 알아야 한다.
둘째는 도구 표면 큐레이션이다 — 에이전트가 하류 MCP 서버가 노출하는 모든 도구의 원본 덤프를 받아서는 안 되며, 더 작고 과업에 맞는 카탈로그가 안전성을 높이고 모델 혼란을 줄이고 운영을 쉽게 한다.
셋째는 운영이다 — 도구 호출에는 속도 제한, 트레이스, 지표, 사용 이벤트, 비용 귀속, 소유권 메타데이터, 프로덕션 가시성이 필요하다.

### 아키텍처

게이트웨이는 프록시와 레지스트리 두 조각으로 이루어진다.
프록시는 데이터 플레인으로 각 MCP 요청을 받아 호출자를 인증하고, 행동을 인가하고, 속도 제한을 적용하고, 자격 증명을 주입하고, 요청을 전달하고, 관측 데이터를 내보낸다.
레지스트리는 컨트롤 플레인의 단일 진실 공급원으로 에이전트, MCP 서버, 소유자, 전송 설정, 인증 모드, 정책, 발견된 도구 카탈로그, 도구 표면 설정을 저장한다.

이 분리가 점대점 통합으로는 얻기 어려운 성질을 준다 — 에이전트는 하류 서버마다 인증과 라우팅 모델을 배우는 대신 일관된 하나의 MCP 엔드포인트 패턴을 쓰고, 도구 소유자는 역량을 한 번 등록해 소유권과 정책을 붙이고 프로덕션 사용량을 보며, 보안 팀은 접근을 강제하고 승인을 회수하고 호출을 감사할 한 곳을 얻고, 플랫폼 팀은 공유 경로를 한 번 개선하면 모든 에이전트가 그 개선을 물려받는다.

내부와 외부 신뢰 경계는 분리해서 유지한다.
사내 DoorDash 워크플로와 외부 대면 에이전트 사용 사례는 공유 라이브러리와 레지스트리 개념을 쓰되 별도의 프록시 플레인에서 돈다 — 인터넷 대면 폭발 반경을 가두고 각 인증 모델이 독립적으로 진화하게 하기 위해서다.

### 아이덴티티, 인가, 비밀

모든 게이트웨이 요청은 호출자로 해석된다 — 사용자, 서비스, 또는 위임된 사용자 맥락으로 행동하는 에이전트다.
그 아이덴티티가 인가, 자격 증명 주입, 라우팅, 관측을 관통해 전달되므로 모든 하류 행동을 귀속시킬 수 있다.

인가 질문은 이 호출자가 이 서버에 접근할 수 있는가에서 멈추지 않는다.
이 에이전트가 이 서버에 접근할 수 있는가, 이 사용자가 이 에이전트를 통해 이 도구를 호출할 수 있는가, 이 도구가 이 환경에 노출될 수 있는가, 이 호출자가 쓰기 가능한 변형을 쓸 수 있는가 아니면 읽기 전용만인가, 이 워크플로가 팀 서비스 주체를 쓸 수 있는가 아니면 사용자별 OAuth가 필요한가.
정책이 게이트웨이에 살기 때문에 접근을 바꾸고 회수할 단일 지점이 생기고, 도구 소유자는 서버마다 인가를 다시 만들지 않아도 되며, 에이전트 개발자는 보안 결정을 프롬프트나 애플리케이션 코드에 넣지 않아도 된다.

자격 증명 처리는 네 가지 모드로 정리된다.

| 인증 모드           | 자격 증명 보유 주체        | 게이트웨이가 하는 일                                       |
| ------------------- | -------------------------- | ---------------------------------------------------------- |
| 사내 서비스 아이덴티티 | DoorDash 인프라            | 검증된 호출자 맥락을 사내 서비스로 전달                     |
| 게이트웨이 보유 토큰 | 게이트웨이 비밀 저장소     | 벤더나 서비스 토큰을 에이전트에 노출하지 않고 주입          |
| 사용자별 OAuth      | 암호화된 사용자별 승인 저장소 | 사용자 범위 행동을 위해 사용자 토큰을 주입하고 갱신         |
| 서비스 주체         | 게이트웨이 관리 팀 주체    | 수명이 짧은 비개인 자격 증명을 발급하거나 중개              |

에이전트는 벤더 API 키나 OAuth 리프레시 토큰, 팀 자동화를 위해 빌려온 사람의 승인 같은 원시 자격 증명을 보유해서는 안 되며, 게이트웨이가 그 경계를 명시적이고 감사 가능하게 유지한다.

### 에이전트 턴을 깨지 않는 사용자별 OAuth

사용자 범위 서드파티 도구는 사용자 인가가 필요하다 — 사용자의 문서를 읽거나 그 사용자 이름으로 티켓을 만들거나 SaaS 데이터를 대신 갱신하는 일은 공유 키로 안전하게 할 수 없다.
게이트웨이 도입 전에는 각 팀이 자체 OAuth 흐름과 토큰 저장과 먼저 연결하세요 경험을 만드는 경향이 있었다.

게이트웨이는 OAuth 승인을 중앙화한다.
접근 단위는 에이전트·사용자·서버로 범위가 정해지고, 인가가 필요한 첫 호출에서 게이트웨이가 제공자의 OAuth 흐름을 시작해 결과로 나온 액세스·리프레시 토큰을 암호화해 저장하고 이후 호출에서 사용자 토큰을 주입한다 — 에이전트는 원시 토큰을 결코 보지 못한다.
MCP elicitation을 지원하는 클라이언트에 대해서는 게이트웨이가 도구 호출을 일시 정지하고 클라이언트에 연결 프롬프트를 띄우게 한 뒤 사용자가 인가하면 원래 호출을 재개할 수 있다.
elicitation을 지원하지 않는 클라이언트에는 연결 URL이 담긴 구조화된 인가 필요 응답을 돌려준다.
이로써 연결이 실패한 턴이 아니라 도구 호출의 복구 가능한 일부가 된다.

### 큐레이션된 도구 표면

에이전트는 MCP 서버 단위로 생각하지 않고 과업 단위로 생각한다.
코딩 에이전트는 GitHub, Jira, 관측, 문서를 별도 설정 단계로 원하지 않으며, 이슈를 조사하고 코드를 수정하고 PR을 열고 CI를 확인하고 프로덕션 동작을 이해하는 데 필요한 도구 표면을 원한다.
동시에 대부분의 하류 MCP 서버는 어떤 에이전트가 써야 할 것보다 훨씬 많은 도구를 노출한다 — 서드파티 서버는 관리자 작업, 파괴적 작업, 과금 API, 제공자별 틈새 기능을 포함해 수백 개 오퍼레이션을 공개할 수 있는데 대부분의 워크플로는 승인된 작은 부분집합만 필요하다.

게이트웨이는 큐레이션된 도구 표면으로 두 문제를 함께 푼다.
번들(bundle)은 여러 MCP 서버의 도구를 하나의 논리적 MCP 엔드포인트로 묶고, 필터는 주어진 번들·에이전트·사용자 그룹·환경·청중에 대해 각 서버의 어떤 도구를 노출할지 결정한다.
예를 들어 개발자 도구 번들은 저장소와 PR 워크플로를 위한 선별된 GitHub 도구, 이슈 조회와 갱신을 위한 선별된 Jira 도구, 로그·지표·트레이스를 위한 선별된 관측 도구, 선별된 코드 검색과 문서 도구, 선별된 배포나 기능 플래그 도구를 포함할 수 있다.

에이전트는 개발자 도구 엔드포인트 같은 게이트웨이 URL 하나에 연결한다.
그 URL 뒤에서 게이트웨이는 번들에 속한 서버들에 `tools/list`를 팬아웃하고, 인가와 도구 필터를 적용하고, 필요한 곳에서 도구 이름에 네임스페이스를 붙이거나 별칭을 주고, 하나의 일관된 카탈로그를 돌려준다.
에이전트가 `tools/call`을 호출하면 게이트웨이가 정책을 다시 강제하고, 올바른 하류 서버로 라우팅하고, 그 서버의 자격 증명 모델을 적용한다.

이점은 네 가지로 정리된다 — 에이전트 설정이 여러 서버 엔드포인트 대신 게이트웨이 엔드포인트 하나로 단순해지고, 에이전트가 승인된 경계 안의 도구만 보므로 도구 발견이 안전해지고, 작은 카탈로그가 무관한 선택지와 도구 혼동을 줄여 모델 동작이 개선되고, 발견과 호출이 같은 정책을 강제하므로 인가가 중앙에 유지된다.
글은 큐레이션된 도구 표면이 올바른 도구를 고르는 에이전트와 지나치게 큰 API 카탈로그를 헤매는 에이전트의 차이를 만들 수 있다고 표현한다.

### 관측, 비용 귀속, 하류 보호

모든 호출이 게이트웨이를 지나므로 각 요청은 구조화된 이벤트를 낼 수 있다 — 서버·도구·번들·소유 팀, 호출에 관여한 사용자·에이전트·서비스·플랫폼, 인가 결과·상태 코드·오류 출처·지연 분해, 요청과 응답 크기, 가능한 경우 하류가 보고한 비용 메타데이터다.
게이트웨이는 요청량, 도구별 지연, 인가 결정, OAuth 갱신 결과, 속도 제한 결정, 스트리밍 연결, 상류 실패에 대한 지표도 내보내며, 트레이스 전파로 에이전트에서 게이트웨이를 거쳐 하류 서버까지 호출을 따라갈 수 있다.

같은 지점이 하류 시스템을 보호한다.
속도 제한은 서버·도구·호출자·사용자·번들·호출자 유형으로 범위를 정할 수 있고, 새 제한은 강제 전에 섀도 모드로 돌려 프로덕션 트래픽을 깨뜨리지 않으면서 무엇이 거절되었을지 보여줄 수 있다.
글은 이를 게이트웨이가 거버넌스를 데이터로 바꾼다고 표현한다 — 모든 팀이 올바른 필드를 로깅하고 올바른 제한을 강제하기를 기대하는 대신에 말이다.

### 셀프서비스 온보딩

게이트웨이는 팀이 우회하기보다 쓰기를 선호할 때만 작동하므로 등록, 발견, 필터링, 번들 관리가 모두 셀프서비스여야 한다.
컨트롤 플레인 UI와 API를 통해 팀은 MCP 서버와 에이전트를 등록하고, 인증을 설정하고, 도구를 발견하고, 소유권을 붙이고, 필터를 정의하고, 번들에 도구를 추가하고, 프로덕션 사용량을 점검할 수 있다.
온보딩 루프는 MCP 서버 등록 → `tools/list`로 원본 도구 카탈로그 발견 → 노출할 도구 선택·승인 → 인증 모드·소유권·정책 부착 → 승인된 도구를 하나 이상의 번들에 추가 → 트래픽·지연·오류·인가 결정·비용 관찰이다.
티켓을 요구하는 거버넌스는 확장되지 않으며, 포장된 길이 비밀을 에이전트에 복사해 서버에 직접 연결하는 것보다 쉬워야 한다고 단언한다.

### 채택 현황과 교훈

채택이 플랫폼의 진짜 시험이라며 수치를 제시한다.
200개가 넘는 MCP 서버가 게이트웨이 뒤에 등록되어 있고 함께 수천 개 도구를 원본 카탈로그가 아니라 승인되고 과업 범위로 정해진 부분집합으로 큐레이션해 노출한다.
30개가 넘는 에이전트와 서비스를 수천 명의 직원이 쓰며 그중 어느 것도 원시 자격 증명을 다루지 않는다.
매주 수백만 건의 도구 호출이 게이트웨이를 지나고 각각이 인증되고 인가되고 구조화된 사용 이벤트로 기록된다.
새 MCP 서버와 도구 등록은 몇 분이 걸리고 이미 등록된 도구에 에이전트를 붙이는 것은 더 빠르다.

교훈은 일곱 가지로 정리된다 — MCP는 호출을 풀지 거버넌스를 풀지 않으며 아이덴티티·정책·비밀·큐레이션·관측·회수가 어려운 부분이 된다, 발견된 도구 카탈로그는 인터페이스이므로 이름·설명·필터링·그룹화·청중이 중요하다, 번들이 워크플로의 올바른 단위이며 에이전트는 서버 목록이 아니라 과업 지향 툴킷을 필요로 한다, 도구 필터링은 더 작고 명확한 행동 집합을 노출해 보안과 에이전트 품질을 함께 개선한다, 자격 증명은 중앙에서 교체·감사·회수할 수 있는 게이트웨이에 있어야 한다, OAuth 승인 누락은 예외가 아니라 정상 상태이므로 연결을 프로토콜 안에서 처리해야 한다, 통제된 경로는 셀프서비스여야 하며 그렇지 않으면 팀은 직접 연결한다.

다음 투자는 더 강한 에이전트 아이덴티티와 사용자 위임이다.
목표 모델은 모든 에이전트에 암호학적 아이덴티티를 주고 게이트웨이가 사용자·에이전트·과업·대상 도구로 범위가 정해진 수명 짧은 위임 자격 증명을 발급하는 것이며, 그러면 감사 추적에 사용자와 에이전트라는 두 개의 진짜 주체가 남는다.
품질·보안 리포트 카드, 위험한 도구 설명 검사, 오류에서 비밀이나 개인식별정보 탐지, 서버 생성 스캐폴딩, 자동 등록, 동적 도구 발견, 분석과 컴플라이언스를 위한 마스킹된 도구 호출 이벤트 스트림 같은 개발자 도구에도 투자하고 있다.
동적 발견은 번들의 모든 도구를 주는 대신 과업 맥락과 정책과 사용 신호로 지금 작업에 유용할 도구만 노출하는 방향이다.

## 분석

### 게이트웨이는 MCP의 결함을 고치는 것이 아니라 MCP가 정의하지 않은 층을 채운다

글의 핵심 진술은 MCP는 호출을 풀지 거버넌스를 풀지 않는다는 문장이다.
이 진단이 정확한 이유는 MCP가 의도적으로 좁은 프로토콜이기 때문이다 — 도구를 기술하고 발견하고 호출하는 방법을 정하고 그 이상은 정하지 않는다.

좁은 프로토콜은 채택을 빠르게 하지만 운영 층을 각 조직에 떠넘긴다.
그래서 MCP를 프로덕션에 올리는 모든 조직이 같은 것을 만들게 된다 — 레지스트리, 인가 계층, 자격 증명 저장소, 사용량 로깅.
Pinterest도, DoorDash도 각각 독립적으로 같은 구조에 도달했고, 두 회사의 문서가 거의 같은 목차를 갖는다는 사실이 이 층의 필연성을 보여준다.

이 관찰은 프로토콜 설계 일반에 적용된다.
HTTP가 인증을 정의하지 않아 OAuth가 생기고, gRPC가 정책을 정의하지 않아 서비스 메시가 생긴 것과 같은 형태다.
좁은 코어와 그 위에 쌓이는 운영 층이라는 구조는 반복되며, 지금 MCP는 그 운영 층이 아직 표준화되지 않은 단계에 있다.

### 번들은 인가 단위이자 컨텍스트 예산 단위이자 제품 단위다

이 글에서 가장 잘 설계된 개념은 번들이다.
여러 서버의 도구를 하나의 논리적 엔드포인트로 묶고 필터로 노출 범위를 정하는 구조인데, 이 하나가 세 가지 문제를 동시에 푼다.

보안 측면에서 번들은 인가의 단위다 — 어떤 청중이 어떤 도구를 보는지가 번들 정의에 담긴다.
모델 측면에서 번들은 컨텍스트 예산의 단위다 — 수백 개 도구 정의를 다 넣지 않고 다섯 개만 넣는다.
개발자 경험 측면에서 번들은 제품의 단위다 — 에이전트 개발자가 여러 서버를 각각 붙이는 대신 개발자 도구 엔드포인트 하나를 가리킨다.

세 문제가 하나의 추상으로 풀린다는 것은 그 추상이 문제의 실제 구조와 맞는다는 신호다.
그리고 글이 발견된 도구 카탈로그는 인터페이스라고 정리한 것이 이 설계의 근거를 압축한다 — 도구 목록을 구현 세부가 아니라 사용자에게 보여줄 API로 취급하면 이름, 설명, 범위, 대상 청중이 모두 설계 대상이 된다.

### 채택 수치가 이 글의 논증 구조를 결정한다

글은 채택이 플랫폼의 진짜 시험이라며 수치를 제시하고, 셀프서비스가 아니면 팀이 직접 연결한다는 교훈으로 맺는다.
이 배치가 의도적이다 — 중앙 게이트웨이는 기술적으로는 쉽고 조직적으로는 어려운 종류의 프로젝트이기 때문이다.

중앙 통제 지점을 만드는 일의 실패 모드는 성능이나 안정성이 아니라 우회다.
팀들이 게이트웨이를 거치는 것이 번거롭다고 느끼면 서버에 직접 붙고, 그러면 거버넌스는 문서로만 남는다.
그래서 이 글의 절반은 기능 설명이 아니라 왜 우회하지 않는지에 대한 설명이다 — 등록이 몇 분이고, OAuth를 대신 처리해 주고, 하나의 엔드포인트로 여러 서버를 쓸 수 있고, 비밀을 관리하지 않아도 된다.

즉 이 게이트웨이의 설계 목표는 통제가 아니라 통제가 편의보다 매력적인 상태를 만드는 것이다.
포장된 길이 비밀을 복사하는 것보다 쉬워야 한다는 문장이 이 프로젝트의 진짜 사양이며, 나머지 기능은 그 사양을 만족시키기 위한 수단이다.

## 비평

### 큐레이션의 비용과 그 비용을 누가 치르는지가 빠져 있다

번들과 필터가 안전성과 모델 품질을 함께 개선한다는 주장은 설득력 있다.
그런데 누군가는 수백 개 도구 중 다섯 개를 골라야 하고, 그 선택이 틀리면 에이전트가 필요한 도구를 못 쓰게 된다.

이 선택 작업의 성격이 글에 나오지 않는다.
서버 소유자가 하는가, 번들 소유자가 하는가, 에이전트 개발자가 요청하는가.
서드파티 서버가 새 도구를 추가하면 누가 그것을 검토해 번들에 넣는가.
에이전트가 필터에 막혀 실패했을 때 그 신호가 큐레이터에게 어떻게 도달하는가.

이 질문들이 중요한 이유는 큐레이션이 일회성 작업이 아니라 지속적 유지보수이기 때문이다.
200개 서버와 수천 개 도구 규모에서 승인 목록을 최신으로 유지하는 일은 상당한 비용이고, 그 비용이 어디로 가는지가 이 모델의 지속 가능성을 결정한다.
글은 등록이 몇 분이라는 온보딩 속도만 말하고 등록 이후의 유지 비용은 다루지 않는다.

### 게이트웨이가 단일 장애점이 되는 문제를 언급하지 않는다

모든 에이전트의 모든 도구 호출이 하나의 프록시를 지난다.
그리고 그 프록시는 인증, 인가, 자격 증명 주입, 라우팅, 로깅을 모두 수행하며 레지스트리 조회에 의존한다.

이 구조에서 게이트웨이가 느려지면 모든 에이전트가 느려지고, 게이트웨이가 죽으면 사내의 모든 에이전트가 도구를 잃는다.
매주 수백만 건이 지나는 경로인데 글에는 가용성 목표, 다중화 구성, 레지스트리 캐싱, 저하 모드에 대한 서술이 전혀 없다.
내부와 외부 프록시 플레인을 분리했다는 서술이 폭발 반경 통제의 유일한 언급인데, 그것은 신뢰 경계 분리이지 가용성 대책이 아니다.

특히 문제가 되는 것은 인가 결정이 실시간 조회에 의존한다는 점이다.
레지스트리가 응답하지 않을 때 게이트웨이가 열어주는지 닫아주는지는 보안과 가용성이 정면으로 충돌하는 지점이고, 어느 쪽을 골랐는지가 이 시스템의 성격을 규정한다.
같은 질문을 Pinterest의 문서도 답하지 않았는데, 두 글이 함께 빠뜨렸다는 사실이 이 층의 성숙도를 보여준다.

### 사람 개입과 위험한 행동에 대한 통제가 이 문서에는 아예 없다

게이트웨이는 누가 어떤 도구를 호출할 수 있는지를 통제한다.
그런데 권한이 있는 에이전트가 파괴적인 도구를 호출하는 것은 막지 않는다.

글은 쓰기 가능한 변형인가 읽기 전용인가를 인가 질문 목록에 넣었고, 서드파티 서버가 파괴적 작업과 과금 API를 노출한다는 위험을 인식하고 있다.
그런데 대응은 그런 도구를 번들에서 빼는 것뿐이다.
번들에 포함된 쓰기 도구를 에이전트가 잘못 호출하는 경우 — 예를 들어 잘못된 이슈를 닫거나 잘못된 배포를 트리거하는 경우 — 에 대한 승인 흐름이나 확인 절차는 언급되지 않는다.

Pinterest의 같은 주제 문서가 사람 개입 의무화와 elicitation 기반 확인을 명시한 것과 대비된다.
DoorDash 문서에서 elicitation은 OAuth 연결에만 쓰이고 위험 확인에는 쓰이지 않는다.
게이트웨이가 모든 호출을 보고 있다는 점을 생각하면 이 위치는 위험도 기반 승인을 넣기에 가장 좋은 자리인데, 글은 그 가능성을 다루지 않고 다음 투자 목록에도 넣지 않았다.

### 도구 호출 수가 가치의 지표로 쓰이는 구조가 반복된다

채택 지표는 등록된 서버 200개 이상, 에이전트 30개 이상, 주간 수백만 호출이다.
이 수치들은 게이트웨이가 실제로 쓰인다는 것을 보여주지만 그것이 좋은 결과를 낳았는지는 말하지 않는다.

호출 수는 우회가 없다는 증거로는 훌륭하다 — 실제로 이 글의 맥락에서 채택률은 정확한 지표다.
문제는 결론이 그 이상을 주장할 때 생긴다.
큐레이션이 모델 동작을 개선한다는 주장은 이 글의 핵심 근거 중 하나인데, 그것을 뒷받침하는 측정은 없다 — 번들 도입 전후로 도구 선택 정확도가 어떻게 달라졌는지, 잘못된 도구 호출 비율이 얼마나 줄었는지에 대한 수치가 없다.

게이트웨이가 모든 호출의 인가 결과, 상태 코드, 오류 출처를 기록한다는 점을 생각하면 이 측정은 이미 가능한 상태다.
데이터가 있는데 제시하지 않았다는 것은, 이 글이 아키텍처 소개이지 효과 검증이 아니라는 뜻이다.
독자는 설계를 배우되 그 설계가 실제로 에이전트를 더 똑똑하게 만들었는지는 다른 근거로 판단해야 한다.

## 인사이트

### 도구 카탈로그를 인터페이스로 보면 API 설계의 규율이 그대로 적용된다

발견된 도구 카탈로그는 인터페이스라는 교훈은 짧지만 함의가 넓다.
API를 설계할 때 우리가 신경 쓰는 것들 — 이름의 일관성, 설명의 정확성, 버전 관리, 폐기 정책, 대상 청중별 노출 범위 — 이 도구 카탈로그에도 그대로 필요해진다.

그런데 결정적 차이가 하나 있다.
일반 API의 사용자는 문서를 읽고 시행착오를 거치는 사람이지만, 도구 카탈로그의 사용자는 설명 문자열만 읽고 즉시 선택하는 모델이다.
사람은 이름이 모호해도 문서를 더 읽어 보완하지만 모델은 주어진 설명이 전부이므로, 설명의 품질이 곧 동작의 품질이 된다.

이 차이가 새로운 규율을 요구한다.
도구 설명은 문서가 아니라 프롬프트의 일부이고, 따라서 변경할 때마다 회귀 시험이 필요하다.
DoorDash가 다음 투자로 위험한 도구 설명 검사를 넣은 것은 이 방향의 첫걸음인데, 더 나아가면 도구 설명 변경을 코드 변경처럼 리뷰하고 평가셋으로 검증하는 체계가 필요해진다.
그리고 그 체계가 없으면 서드파티 서버가 도구 설명을 바꾸는 것만으로 사내 에이전트의 동작이 조용히 달라진다.

### 게이트웨이는 접근 통제 장치이면서 동시에 협상 지렛대다

모든 도구 호출이 한 곳을 지나면 그 지점을 운영하는 팀이 특별한 지위를 갖는다.
어떤 도구가 얼마나 쓰이는지, 어떤 팀이 비용을 발생시키는지, 어떤 서버가 자주 실패하는지를 그 팀만 안다.

이 정보 비대칭은 플랫폼 팀에게 조직적 힘을 준다.
서드파티 SaaS 벤더와 계약을 갱신할 때 실제 사용량 데이터를 가진 쪽이 유리하고, 사내 팀에 도구 품질 개선을 요구할 때 오류율 데이터가 있는 쪽이 설득력을 갖는다.
DoorDash가 다음 투자로 품질·보안 리포트 카드를 넣은 것은 이 지렛대를 제도화하는 작업이다.

같은 구조는 비용 쪽에서도 작동한다.
글은 비용 귀속을 관측 항목으로 나열하지만, 비용이 팀별로 보이는 순간 그것은 회계가 아니라 정책 도구가 된다 — 어떤 에이전트가 얼마를 쓰는지 보이면 예산이 배정되고, 예산이 배정되면 팀이 스스로 최적화한다.
플랫폼 팀이 강제하지 않아도 행동이 바뀌는 이 경로가, 중앙 통제 지점을 만드는 일의 가장 큰 이득일 수 있다.

### OAuth 승인 누락을 정상 상태로 취급한 것이 이 설계에서 가장 이식성 높은 아이디어다

OAuth 승인 누락은 예외가 아니라 정상 상태라는 교훈은 작아 보이지만 프로토콜 설계의 핵심을 건드린다.
승인이 없는 상태를 오류로 다루면 에이전트 턴이 실패하고 사용자는 무슨 일이 일어났는지 모른 채 다시 시도한다.
승인이 없는 상태를 정상 상태로 다루면 그 상태에서 무엇을 해야 하는지가 응답에 담기고, 흐름이 이어진다.

이 전환은 에이전트 시스템 전반에 적용된다.
권한 부족, 자격 증명 만료, 승인 대기, 속도 제한 초과, 하류 서비스 점검 중 — 이 모든 것이 지금은 대개 오류로 처리되지만, 각각은 사람이라면 다음 행동을 알 수 있는 상태다.
그 다음 행동을 응답 구조에 담으면 에이전트가 스스로 복구할 수 있고, 담지 않으면 사람이 개입해야 한다.

여기서 elicitation의 역할이 드러난다.
elicitation은 도구 호출 중간에 사용자에게 물어볼 수 있게 하는 장치이고, 그것이 있으면 인가가 호출의 일부가 되어 턴이 끊기지 않는다.
DoorDash가 elicitation을 지원하는 클라이언트와 그렇지 않은 클라이언트에 각각 다른 경로를 만든 것은 실용적 타협인데, 시간이 지나 elicitation 지원이 보편화되면 후자의 구조화된 인가 필요 응답은 레거시가 된다.
지금 이 두 경로를 모두 유지하는 비용은, 프로토콜이 성숙하는 중간 단계에 있는 시스템이 치르는 전형적인 세금이다.

### 두 회사가 같은 결론에 독립적으로 도달했다는 사실이 이 층의 표준화를 예고한다

Pinterest의 MCP 생태계 문서와 이 글은 발행 시점이 4개월 차이인데 구조가 거의 같다 — 중앙 레지스트리, 도메인별 다중 서버, 두 겹 인가, 셀프서비스 온보딩, 사용량 지표, 도구 표면 제한.
두 팀이 서로를 참고했을 가능성은 낮고, 같은 문제에서 같은 형태가 나온 것으로 보는 편이 자연스럽다.

이런 수렴은 대개 표준화의 전조다.
서비스 메시가 그랬고 컨테이너 오케스트레이션이 그랬다 — 여러 회사가 각자 만든 내부 시스템이 비슷해지면, 곧 그것을 공통으로 만드는 오픈소스나 명세가 나온다.
MCP 명세 자체가 레지스트리와 인가 층을 흡수할 수도 있고, 별도의 게이트웨이 계층이 표준으로 자리 잡을 수도 있다.

지금 이 층을 자체 구축하는 조직에게 이는 두 가지를 시사한다.
첫째, 만든 것이 곧 표준과 겹치게 될 가능성이 높으므로 프로토콜 경계를 명확히 두어 나중에 교체 가능하게 해야 한다.
둘째, 두 문서가 공통으로 다루지 않은 부분 — 가용성, 위험도 기반 승인, 큐레이션 유지 비용 — 이 아직 아무도 풀지 않은 영역이며, 자체 구축한다면 그쪽에 시간을 쓰는 것이 차별적이다.
이미 두 회사가 같은 답을 낸 부분을 세 번째로 다시 만드는 것은 학습 외의 가치가 크지 않다.
