# Netflix의 사내 LLM 서빙 플랫폼

원문: [In-House LLM Serving at Netflix. By AI Platform’s Model Runtime team and… | by Netflix Technology Blog | Jul, 2026 | Netflix TechBlog](https://netflixtechblog.com/a5a8e799ea2c)

## 요약

대부분의 조직은 호스팅된 API를 통해 LLM을 소비하지만,
Netflix는 모델 배포부터 추론까지 전체 스택을 자체 프로덕션 환경 안에서
직접 운영하는 길을 선택했다.
이 글은 AI Platform 조직의 Model Runtime 팀과 Inference 팀이 작성했으며,
엔진 선택, 모델 패키징, API 표면 설계, 배포 전략, 출력 제약 강제라는
다섯 가지 핵심 의사결정과 그 과정에서 프로덕션이 드러낸
설계 단계의 예상치 못한 문제들을 다룬다.

Netflix의 멤버 규모 ML은 JVM 기반의 통합 서빙 시스템이 라우팅, A/B 테스트,
후보 생성, 피처 조회, 추론, 후처리, 로깅을 처리한다.
작은 CPU 모델은 인프로세스로 실행해 원격 호출 비용을 없애고,
GPU가 필요한 큰 모델은 Model Scoring Service(MSS)라는 공유 추론
백엔드로 위임한다.
MSS는 NVIDIA Triton Inference Server 위에서 XGBoost, TensorFlow,
PyTorch, LLM을 하나의 인터페이스로 통합해서 제공하며,
그 위에 배포·버전 관리·헬스 체크·오토스케일링·다중 리전 롤아웃을
담당하는 Java 컨트롤 플레인이 놓여 있다.

플랫폼은 원래 TensorRT-LLM 위에 구축됐지만,
2025년 여름까지 오픈소스 엔진들이 전용 스택과의 성능 격차를
상당 부분 좁혔고 워크로드도 임베딩 생성, prefill 전용 추론,
자기회귀 디코딩, 커스텀 제약 로직을 가진 모델까지 다양해졌다.
재벤치마크 결과 Netflix는 vLLM을 paved-path 엔진으로 채택했다.
커스텀 아키텍처를 다단계 컴파일 없이 로드할 수 있고,
커스텀 디코딩 로직을 위한 확장 훅이 있으며,
디버깅이 쉽고, 이미 연구 단계에서 vLLM을 쓰던 실무자가 많아
연구-프로덕션 전환 비용이 낮다는 점이 이유였다.

Triton에 vLLM을 통합하는 방식에는 Python 백엔드와 vLLM 백엔드
두 가지가 있는데, vLLM 백엔드는 배포 시점에 I/O 텐서 스펙을 동적으로
생성해 모델과 프런트엔드가 독립적으로 진화할 수 있게 해주는 쪽이라
아키텍처적으로 올바른 기본값으로 선택됐다.
다만 Triton과 vLLM의 버전 불일치로 백엔드가 아예 로드되지 않는
문제가 프로덕션에서 발생했고, 커스텀 전처리·후처리가 필요한 모델은
여전히 Python 백엔드라는 탈출구를 써야 했다.

API 표면 설계에서는 LLM 모델을 "특별한 존재"로 만들지 않는다는
목표 아래 gRPC를 기본으로 유지하면서, OpenAI 호환 API를 추가
프런트엔드로 노출했다.
구현은 NVIDIA Triton의 OpenAI 호환 프런트엔드를 재사용했는데,
`response_format` 파라미터가 스키마상으로는 허용되지만 실제로는
vLLM에 전달되지 않고 조용히 버려지는 문제를 발견해 프런트엔드를
직접 패치했다.

배포 전략은 Red-Black과 Versioned 두 가지를 제공한다.
Red-Black은 모델 인터페이스가 안정적일 때 쓰는 기본 전략이지만,
I/O 스키마가 바뀌는 배포에서는 소비자가 새 배포가 완전히
살아나기 전까지 설정을 갱신할 수 없어 "구" 요청이 "신" 배포로
전달되는 조정 문제가 있었다.
Versioned는 (modelId, modelVersion) 쌍마다 독립된 배포를 유지해
이 문제를 해결하지만, 전환 구간 동안 GPU 비용이 일시적으로 늘어난다.

운영 측면에서는 모델을 S3나 Hugging Face에서 직접 내려받는 대신
Amazon FSx에 미리 캐싱해 콜드 스타트 지연을 줄였고,
vLLM과 Triton이 각각 다른 방식으로 노출하는 메트릭을 하나의
`/metrics` 엔드포인트로 합치는 프록시를 추가했다.
가장 공을 들인 딥다이브는 제약 디코딩(constrained decoding)이다.
초기에는 vLLM V0에서 요청 단위로 순차 실행되는 순수 Python
구현을 썼는데, GIL 때문에 배치 크기가 커질수록 CPU 처리 시간이
선형으로 늘어나는 병목이 발생했다.
vLLM V1으로 옮기면서 로짓 프로세싱을 배치 단위로 재작성하고
C++과 멀티스레딩으로 GIL을 우회했으며,
그 과정에서 partial prefill과 preemption이라는 두 가지 새로운
상태 관리 문제를 추가로 처리해야 했다.

## 분석

### 이 글의 핵심 주장은 "자체 운영"이 아니라 "기존 인프라 재사용"이다

이 글의 표면적 주제는 LLM을 자체 호스팅하기로 한 결정처럼 보이지만,
실제로 반복해서 강조되는 것은 별도의 ML 실리콘을 새로 짓지 않고
기존 프로덕션 서빙 시스템에 LLM을 끼워 넣었다는 점이다.
"LLM 모델은 특별한 존재가 되어서는 안 된다"는 문장이 그 축약본이다.
XGBoost 앙상블이든 대형 LLM이든 같은 gRPC 호출로 스코어링하고,
같은 클라이언트 라이브러리와 헬스 체크, 배포 파이프라인을 재사용한다.

이 선택은 Netflix가 이미 오랫동안 축적해온 대규모 추천 시스템
인프라(MSS, Triton 기반 배치·오토스케일링·다중 리전 롤아웃)를
LLM 시대에도 그대로 상각하겠다는 뜻이다.
많은 기업이 LLM을 도입하며 벡터 DB, 오케스트레이션 레이어,
전용 게이트웨이 등 완전히 새로운 스택을 만드는 것과 대비된다.
Netflix의 선택은 조직 규모가 크고 기존 ML 인프라가 이미 성숙했을 때만
성립하는 전략이며, 이 글은 그 전제를 명시하지 않는다.

### vLLM 채택 시점은 "engine war"의 승자가 아니라 "격차가 좁아진 시점"을 포착한 것이다

TensorRT-LLM에서 vLLM으로의 전환 서술에서 흥미로운 지점은,
Netflix가 vLLM이 더 빠르다고 주장하지 않는다는 점이다.
대신 "오픈소스 엔진이 전용 스택과의 성능 격차를 상당 부분 좁혔다"는
표현을 쓴다.
즉 결정 기준은 최고 성능이 아니라 운영 적합성 — 커스텀 아키텍처
로딩 속도, 디버깅 편의성, 인력 친숙도 — 이었다.

이는 추론 엔진 선택이 순수 벤치마크 경쟁이 아니라 조직의 인력 구성과
반복 속도(iteration speed)에 의해 좌우된다는 점을 보여준다.
연구자들이 이미 vLLM을 쓰고 있었다는 사실이 "연구-프로덕션 전환 비용"을
낮추는 요인으로 명시적으로 언급된 것은, 오픈소스 생태계의 채택이
성능 곡선보다 먼저 조직의 의사결정을 굳힌다는 구조적 패턴을 보여준다.
TensorRT-LLM이 컴파일 파이프라인 때문에 반복 속도에서 밀렸다는 서술은
컴파일 기반 최적화 엔진들이 갖는 근본적인 트레이드오프이기도 하다.

### 프로덕션에서 드러난 문제들은 대부분 "경계 계층"에서 발생했다

이 글이 나열하는 실제 장애나 결함 — Triton/vLLM 버전 불일치,
`response_format`이 조용히 버려지는 문제, Red-Black 배포에서
신구 스키마가 충돌하는 문제, 메트릭이 두 시스템에 흩어지는 문제 —
는 모두 서로 다른 컴포넌트가 맞닿는 경계에서 발생한다.
단일 컴포넌트 내부 로직의 버그가 아니라, 두 개의 독립적으로
진화하는 시스템(Triton과 vLLM, 컨슈머와 모델 배포)의 인터페이스에서
암묵적 가정이 깨지는 패턴이다.

이는 오픈소스 컴포넌트를 조합해 플랫폼을 만드는 조직이라면 피하기
어려운 구조적 비용이다.
Triton과 vLLM은 각각 독립적인 릴리스 주기를 가지며, Netflix는
그 사이의 호환성을 스스로 검증하고 버전을 고정하는 책임을 떠안았다.
이는 "우리는 오픈소스를 조합해서 쓴다"는 선택이 실제로는
"두 오픈소스 프로젝트 사이의 통합 테스트를 우리가 대신 수행한다"는
숨은 비용을 동반한다는 사실을 보여주는 사례다.

### GIL과 배치 처리의 충돌은 Python 기반 추론 스택의 오래된 딜레마를 재현한다

제약 디코딩 딥다이브에서 드러나는 V0 → V1 전환은 사실 새로운 문제가
아니다.
GPU에서는 배치가 병렬로 처리되는데 CPU 쪽 후처리 로직이 GIL 때문에
요청 단위로 직렬화되는 구조는, Python이 프로덕션 추론 서빙의
핵심 경로에 남아 있는 한 반복해서 나타나는 병목이다.
Netflix의 해법 — 배치 수준 자료구조로 재설계하고 핫 패스를 C++로
다시 구현 — 은 결국 Python을 오케스트레이션 계층으로 남기고
연산 집약적인 부분을 네이티브 코드로 밀어내는, PyTorch나 NumPy가
오래전부터 써온 패턴의 반복이다.
"단일 요청 벤치마크에서는 보이지 않다가 실사용 동시성에서만
드러나는 병목"이라는 표현은, 이 문제가 설계 단계의 검증 방법론
자체의 한계에서 비롯됨을 시사한다.

## 비평

### "특별한 존재로 만들지 않는다"는 원칙은 커스텀 로직이 필요한 순간 스스로 깨진다

이 글은 LLM을 기존 서빙 인프라에 자연스럽게 편입시켰다는 점을
성과로 내세우지만, 정작 본문 곳곳에서 그 원칙이 유지되지 못하는
지점들을 스스로 드러낸다.
Python 백엔드라는 "탈출구"가 커스텀 전처리·후처리가 필요한 모델에는
여전히 필요하다고 인정하고, 제약 디코딩을 위해 vLLM의 로짓
프로세서 인터페이스를 C++까지 내려가서 다시 구현했다.
결국 LLM은 표준 경로로는 처리되지 않는 워크로드를 상당수 안고 있고,
"특별하지 않다"는 서술은 표준 스코어링 호출 경로에 한정된
절반의 진실에 가깝다.

이 균열은 사소하지 않다.
제약 디코딩처럼 토큰 단위로 상태를 추적해야 하는 워크로드는
XGBoost나 TensorFlow 모델과 근본적으로 다른 실행 모델을 요구하고,
partial prefill과 preemption에 대응하기 위해 엔진 내부 스케줄링
동작까지 추적해야 했다는 서술이 이를 뒷받침한다.
"같은 gRPC 호출, 같은 배포 파이프라인"이라는 표면적 통일성 아래에는
LLM 전용의 상당한 엔지니어링이 숨어 있으며, 글은 이 비대칭을
축소해서 서술한다.

### 버전 고정 전략의 지속가능성에 대한 질문이 빠져 있다

Triton과 vLLM의 버전 불일치 문제에 대한 해법은 "호환 버전을
서비스 이미지에 고정하고, 모델 작성자가 vLLM 버전을 임의로
바꾸지 못하게 막는다"는 것이다.
이는 당장의 장애를 막는 실용적 조치이지만, vLLM이 매우 빠른
주기로 릴리스되는 프로젝트라는 점을 고려하면 이 고정이 장기적으로
얼마나 자주 재검증되어야 하는지, 그 검증 비용을 누가 얼마나
자주 부담하는지에 대한 언급이 전혀 없다.

플랫폼 팀이 상류 프로젝트 두 개의 호환성 매트릭스를 계속 추적해야
한다면, 이는 일회성 수정이 아니라 지속적인 운영 부담이다.
글은 이를 "Triton 25.09가 vLLM 0.11.2에서 제거된 모듈을 임포트해
실패했다"는 하나의 사례로만 제시하고, 이런 종류의 사고가 얼마나
자주 재발했는지, 재발 방지를 위한 자동화된 호환성 테스트가
있는지는 말하지 않는다.
사후 대응 사례 하나로 구조적 리스크 관리 여부를 판단하기는 어렵다.

### Versioned 배포의 비용 증가가 구체적으로 얼마나 되는지 제시되지 않는다

Versioned 전략이 "전환 구간 동안 GPU 비용이 일시적으로 늘어난다"고만
서술하고, 그 정도를 정량화하지 않는다.
GPU 인스턴스는 CPU 인스턴스보다 단가가 훨씬 높고, LLM 서빙에서는
특히 그렇다.
"임시 증가"가 몇 퍼센트인지, 어느 정도 기간 지속되는지에 대한
데이터가 없으면 이 트레이드오프가 실제로 감내할 만한 수준인지
독자가 판단할 근거가 없다.

더 나아가 글은 "변수 설정을 모델에 넣어 버전에 무관하게 만들어
Red-Black을 쓰라"고 권장하면서도, 이 권장이 항상 가능한 것은
아니라는 점 — 즉 어떤 스키마 변경은 근본적으로 버전 비호환일 수밖에
없다는 점 — 을 인정한다.
그렇다면 실제로 Versioned를 얼마나 자주 써야 했는지, 그 빈도가
비용 예산에 어떤 영향을 주는지가 이 글에서 가장 궁금한 지점인데
빠져 있다.

## 인사이트

### 플랫폼 표준화는 비용을 없애는 것이 아니라 비용의 위치를 옮긴다

Netflix가 LLM을 기존 서빙 시스템에 통합한 것은 "LLM 전용 복잡도"를
없앤 것이 아니라, 그 복잡도를 표준 인터페이스 뒤로 옮겨서
플랫폼 팀이 흡수하는 구조다.
API를 사용하는 모델 개발자 입장에서는 XGBoost나 LLM이나 똑같은
gRPC 호출로 보이지만, 그 균일함을 유지하기 위해 플랫폼 팀은
Triton 프런트엔드를 직접 패치하고, 버전 호환성을 수동으로
관리하고, 로짓 프로세서를 C++로 재작성해야 했다.

이 패턴은 LLM 서빙에 국한되지 않는다.
클라우드 제공자가 "서버리스"를 내세울 때, 쿠버네티스가 "선언적
배포"를 내세울 때도 동일한 일이 벌어진다 — 사용자 쪽의 인지 부하는
줄어들지만, 그 부하는 사라지지 않고 플랫폼 운영자 쪽으로 집중된다.
조직이 이런 표준화 계층에 투자할 여력이 있는지가 실제로는
"자체 호스팅이 API 소비보다 나은가"라는 질문보다 더 중요한
결정 요인이며, Netflix 규모의 조직이 아니면 이 정도의 흡수 비용을
감당하기 어렵다.

### 오픈소스 엔진의 급속한 버전 교체는 "안정적인 프로덕션 인터페이스"라는 통념을 무너뜨린다

vLLM V0에서 V1으로의 전환에서 로짓 프로세서 인터페이스 자체가
바뀌어 상태 추적 방식을 다시 설계해야 했다는 서술은, 오픈소스
추론 엔진의 API가 전통적인 의미의 "안정적 인터페이스"가 아님을
보여준다.
전통적인 인프라 소프트웨어(데이터베이스, 웹 서버)는 메이저 버전
사이에서도 하위 호환성을 상당 기간 유지하는 문화가 있었지만,
LLM 추론 엔진 생태계는 아직 그런 규범이 자리 잡지 않았다.

이 격차는 LLM 인프라를 구축하는 모든 조직에 구조적인 함의를
가진다 — 엔진 버전을 고정하는 순간 최신 기능과 성능 개선에서
멀어지고, 최신 버전을 따라가는 순간 인터페이스 변경에 맞춰
자체 코드를 지속적으로 재작성해야 한다.
Netflix가 로짓 프로세서를 C++로 다시 구현한 것도 이 딜레마의
결과물이며, 이는 일회성 마이그레이션이 아니라 앞으로도 반복될
운영 패턴으로 봐야 한다.
즉 LLM 인프라 팀의 역량은 "얼마나 빨리 만드는가"가 아니라
"업스트림 변경을 얼마나 잘 흡수하는가"로 재정의되고 있다.

### 제약 디코딩을 인프라 계층으로 내리는 선택은 "정확성"과 "지연시간"의 경계를 재정의한다

Netflix가 출력 검증을 후처리 재시도 방식에서 디코딩 루프 내부의
상태 기계로 옮긴 것은 단순한 성능 최적화가 아니라, 정확성 보장의
책임 소재를 애플리케이션 계층에서 인프라 계층으로 옮기는
아키텍처적 선택이다.
전통적으로 "이 출력이 유효한 JSON인가"는 애플리케이션이 받은 뒤
검증할 문제였지만, 이제는 모델이 애초에 유효하지 않은 토큰을
생성할 수 없도록 인프라가 강제한다.

이 선택은 장기적으로 두 가지 긴장을 만든다.
첫째, 제약 로직이 인프라에 내려갈수록 애플리케이션 개발자는
그 제약이 어떻게 구현되는지 알 필요가 없어지지만, 동시에 제약을
바꾸려면 인프라 팀을 거쳐야 하는 결합이 생긴다.
둘째, 상태 기계가 preemption이나 partial prefill 같은 엔진 내부
스케줄링 이벤트에 의존하게 되면서, "정확성 보장 로직"이 스케줄러의
구현 세부사항과 강하게 결합된다.
이는 향후 vLLM의 스케줄링 방식이 다시 바뀔 때마다 제약 디코딩
로직도 함께 재검증해야 한다는 뜻이며, 글이 다음 투자 과제로 언급한
"GPU 커널로 완전히 이전"이 완료되기 전까지는 이 결합이 계속
유지보수 부담으로 남을 것이다.
