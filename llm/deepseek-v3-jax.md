## 소개

저장소는 DeepSeek-V3 기술 보고서의 구조를 순수 JAX 190줄로 구현하고, 공개 도메인 탐정 소설로 처음부터 사전 학습한 프로젝트이다.
2026년 11월 13일에 만들어졌고 MIT 라이선스이며 Python이다.
2026년 11월 15일에 읽은 값으로 별 167개, 포크 14개, 열린 이슈 0개이다.
Flax도 Equinox도 PyTorch도 쓰지 않고, 매개변수는 배열의 평범한 딕셔너리이며 모델의 모든 부분은 `deepseek_v3.py`에서 위에서 아래로 읽을 수 있는 함수이다.
README는 이것이 아키텍처 시연이지 강한 언어 모델이 아니라고 밝힌다.
이 문서는 README 전문과 저장소 파일 목록, HN 스레드를 읽었다.
코드를 실행하거나 글(vaibhaav.in)의 본문을 읽지는 않았다.

만든 사람은 HN 스레드에서 DeepSeek V3를 다르게 만드는 것을 이해하려고 세 가지 핵심 아이디어를 처음부터 다시 구현했다고 설명한다. 다중 헤드 잠재 어텐션(MLA), 보조 손실 대신 편향으로 부하를 맞추는 전문가 혼합(MoE), 다중 토큰 예측(MTP)이다.

저장소가 홈페이지로 등록한 주소는 vaibhaav.in이다.
읽은 시점(2026년 11월 18일)에 열어
첫 화면 제목이 “DeepSeek V3 in 190 lines of pure JAX · Vaibhaav Tiwari”임을 확인했다.
사이트 본문은 읽지 않았고, 사이트의 설명은 제작자의 주장이다.

## 구현한 것

README의 표에 따르면 190줄에 들어간 것은 다음과 같다.

- MLA: 키와 값 전체 대신 토큰당 작은 잠재 벡터 하나를 캐시한다. 이 구성에서 토큰·층당 480개 수가 144개로 줄어든다고 한다.
- 분리된 RoPE: 모든 헤드가 공유하는 회전 키 하나를 압축된 잠재 벡터 밖에 둔다.
- DeepSeekMoE: 항상 도는 공유 전문가 1개와 라우팅 전문가 16개, 토큰당 상위 4개이다.
- 보조 손실 없는 균형: 전문가별 편향이 라우팅을 놀고 있는 전문가 쪽으로 민다. 편향은 어떤 전문가가 뽑히는지만 바꾸고 가중치는 바꾸지 않는다.
- 시퀀스 단위 균형 손실: 논문의 작은 보완 손실(α = 1e-4)이다.
- MTP: 추가 모듈이 다음 다음 토큰도 예측하며 손실에서 λ = 0.3으로 가중한다.
- 학습과 생성: f32 마스터 가중치 위의 bf16 연산, MLA 캐시를 쓰는 프리필과 디코드이다.

“190줄”은 `deepseek_v3.py`의 docstring 뒤에서 빈 줄과 주석을 뺀 줄 수이고, README가 이를 세는 명령도 적는다.

## 결과

기본 설정으로 MacBook Air M5(24GB)에서 한 번 돌린 결과는 이렇다.

| 항목                   | 값                                                                           |
| ---------------------- | ---------------------------------------------------------------------------- |
| 모델                   | 파라미터 3,620만 개, 토큰당 활성 1,360만 개                                  |
| 데이터                 | 책 207권, 학습 토큰 2,170만 개(Hammett를 3번 반복), 검증은 따로 둔 범죄 소설 |
| 학습                   | 12,000 스텝, 약 9,800만 토큰(약 4.5 에폭), 약 2.6시간                        |
| 속도                   | 초당 약 1만 700토큰(중앙값)                                                  |
| 검증 손실              | 5.02(스텝 250)에서 3.51                                                      |
| 전문가 부하(편향 사용) | 전문가당 5.7~6.9%(균등은 6.25%), 스텝 2000                                   |
| 전문가 부하(편향 없음) | 전문가당 0.09~18.6%, 스텝 2000                                               |

균형 편향을 켜고 끈 두 실행의 스텝 2000 검증 손실은 같았고(3.921 대 3.923), README는 편향이 비용 없이 전문가를 고르게 하며 이는 논문의 주장이라고 쓴다.
프롬프트 “The fog came in off the”에서 모델이 쓴 문장도 보여 준다.

재현 안내가 자세하다. 학습 데이터를 직접 만드는 스크립트(`prepare_data.py`)와 게시한 실행의 정확한 체크포인트와 데이터가 있는 v1.0 릴리스가 있고, jax-metal 0.1.1은 `jax==0.4.34`에서만 동작한다고 밝힌다. 테스트는 39개이다.
CPU에서는 작은 설정(4층, 전문가 8개, 상위 2개, 문맥 128토큰)으로 돌릴 수 있고 끝까지 학습해 보지는 않았다고 한다. AMD GPU(ROCm)에서도 수정 없이 돌고 RX 7600 XT에서 전체 실행이 약 50분이며 검증 손실 3.527에 이른다고 한다.
체크포인트가 Python pickle이라 신뢰하는 출처에서만 불러오라는 경고도 있다.

## 단순화한 것

README가 스스로 적는 한계이다.

- MoE 연산이 밀집이다. 모든 전문가가 모든 토큰에서 돌고 고르지 않은 것은 0으로 만든다. 라우팅 수학은 정확하지만 희소 디스패치와 전문가 병렬성이 없다.
- MLA에 가중치 흡수가 없어 잠재 벡터를 명시적으로 풀며, 읽기는 쉽고 추론은 느리다.
- FP8 학습, DualPipe, 노드 제한 라우팅, YaRN 문맥 확장, 사후 학습은 빠졌다.
- 규모는 파라미터 3,620만 개 대 6,710억 개, 6층 대 61층, 문맥 256토큰 대 128K이다.

학습 텍스트는 미국 기준 공개 도메인이다. Standard Ebooks의 CC0판 Dashiell Hammett 작품과 Project Gutenberg의 탐정·범죄 소설 약 200권이고 출처 목록이 `sources.txt`에 있다. 미국 밖에서는 공개 도메인 여부가 다를 수 있다고 한다.

## 분석

### 중심 가치는 읽을 수 있는 크기의 참조 구현이다

DeepSeek-V3의 아이디어를 한 파일에서 위에서 아래로 읽을 수 있게 줄인 것이 가치이다.
README의 표가 논문의 아이디어와 코드 위치(`mla`, `route`, `update_bias` 등)를 짝지어 준다.
HN 스레드에서도 이 점이 반응의 중심이었다. 한 댓글은 모델을 기본 원리부터 다시 만드는 것만 한 학습이 없다고 했다.[^armcat]
다른 댓글은 이런 글이 추론이 어떻게 작동하는지 배우고 싶게 만든다며 Java와 Python에 익숙한 일반 개발자의 로드맵을 물었다.[^mattfrommars]
답글들은 3Blue1Brown과 Welch Labs 영상, Karpathy의 강의, jaxformer.com과 nanochat, Stanford CS336을 제안했다.[^rhdunn][^jbits][^vaibhaav-cs336]

### 균형 편향의 결과는 작은 규모에서의 확인이다

편향을 쓰면 전문가 부하가 5.7~6.9%로 고르고 쓰지 않으면 0.09~18.6%로 치우치는데, 검증 손실은 같았다는 결과는 논문의 주장을 작은 모델에서 재현한 것이다.
다만 6개 층과 16개 전문가에서의 2,000스텝 결과이고, 규모가 클 때의 거동은 보여 주지 않는다. README도 규모 차이를 한계로 적는다.

## 비평

### 아키텍처 시연이므로 성능 평가는 범위 밖이다

3,620만 개 모델이 탐정 소설 말투의 문장을 만든다는 것이 결과의 전부이고, 표준 벤치마크와의 비교가 없다.
한 댓글은 다른 사람이 쓴 데이터셋을 쓰면 결과를 직접 비교할 수 있다고 지적했고, 만든 사람은 비교가 목표일 때는 표준 데이터를 쓰겠지만 탐정 소설은 재미로 고른 것이라고 답했다.[^nico][^vaibhaav-nico]
README의 문장 예시도 선택된 하나이다.

### 단순화가 효율 평가를 가린다

MoE가 밀집으로 계산되고 MLA에 가중치 흡수가 없으므로, 이 구현의 속도와 메모리는 DeepSeek-V3의 설계 이점인 희소 연산과 압축 캐시의 효율을 측정하지 않는다.
토큰당 캐시 수가 480에서 144로 준다는 것은 캐시 크기의 계산 결과이고 속도 이득의 증거가 아니다.
이 문서는 코드를 읽어 이 계산을 확인하지는 못했다.

### 하드웨어 지원의 한계가 반응으로 드러났다

한 사용자는 Fedora와 ROCm의 RX 7600 XT 16GB에서 이 프로젝트가 처음으로 끝까지 돌았고, 환경 변수 두 개(`HSA_OVERRIDE_GFX_VERSION`과 Triton GEMM 비활성)가 필요했다고 보고했다.[^joebarbere]
만든 사람은 그 변경을 받아 병합했고 AMD 카드가 없어 시험하지는 못했다고 답했다.[^vaibhaav-joe]
다른 댓글은 AMD의 소프트웨어 지원이 비데이터센터 하드웨어에서 여전히 형편없다고 비판했다.[^kouteiheika]
이는 개인 경험과 의견이고, README의 ROCm 안내가 이 기여에서 나온 것인지는 이 문서가 확인하지 못했다.

## 인사이트

### 학습용 구현을 고르는 기준

이 저장소가 학습 자료로 좋은 이유는 읽는 순서가 정해져 있고 단순화 목록이 있고 테스트가 있다는 것이다.
테스트 39개는 인과 마스킹, 캐시와 전체 순전파의 일치, 라우팅, 균형, MTP 목표, NaN 처리, bf16 마스터 가중치 같은 점을 확인한다고 한다.
구현을 읽을 때 “무엇을 일부러 뺐는가”가 적혀 있는지가 자료의 신뢰를 가른다.

### 다음 구조로의 확장 요청

한 댓글은 같은 방식으로 V4.1을 만들 수 있느냐고 물었고, 만든 사람은 작은 규모로 가능하다고 했다. V4가 MLA를 두 가지 압축 어텐션의 혼합으로 바꾸고 잔차 연결을 바꾸며 MoE는 유지한다고 이해하지만 아키텍처를 깊이 보지는 않았다고 덧붙였다.[^try-working][^vaibhaav-v4]
이 서술은 작성자의 이해이고 이 문서가 확인하지 못했다.

### 확인할 관찰

이 프로젝트의 가치를 가를 관찰은 세 가지이다.
표준 데이터셋으로 같은 구조의 결과가 비교되는지,
희소 디스패치와 가중치 흡수를 넣은 판이 속도와 메모리에서 어떤 차이를 보이는지,
다른 하드웨어(AMD, CPU)에서의 재현 결과가 쌓이는지이다.
셋 모두 이 문서가 확인하지 못했다.
