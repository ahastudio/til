# Qwen3.8-Omni-Flash: 옴니모달이 이해에서 실행으로 넘어간다는 선언

원문: [Qwen3.8-Omni-Flash: Omni Senses. Agentic Delivery.](https://qwen.ai/blog?id=qwen3.8-omni-flash)

HN 토론: <https://news.ycombinator.com/item?id=49747925> (330점, 129개 댓글)

GN 토론: <https://news.hada.io/topic?id=33884>

## 요약

Qwen 팀이 2026년 9월에 공개한 차세대 네이티브 옴니모달 모델 발표문이다.

핵심 목표를 명시한다. 실제 생산성 시나리오에서 에이전트 역량을 강화하는 것이며, 옴니모달 모델을 “옴니모달 콘텐츠를 이해하는” 단계에서 “작업을 계획하고, 도구를 호출하고, 창작을 완성하는” 단계로 밀어 올리는 것이다.

코딩·텍스트 기반 지식 노동·GUI 조작에서의 일반 에이전트 역량 위에, 오디오와 비디오를 중심으로 한 에이전트 응용을 확장했다고 적는다.
영상 편집, 뮤직비디오 제작, 영화 제작과 해설, 시청각 요약, 실시간 대화가 그 예다.

### 발표된 수치

텍스트·이미지·오디오·비디오 입력을 받고 **1M 토큰 컨텍스트**를 지원한다.
같은 규모의 텍스트 전용 모델에 준하는 텍스트 성능을 유지하면서 옴니모달 역량을 크게 올렸다는 주장이다.

29개 평가에서 평균 점수가 Qwen3.5-Omni-Plus 대비 25% 이상 개선되었다.
API 가격에서는 오디오 입력 시간당 단가가 98% 이상, 시청각 입력 시간당 단가가 93% 이상 낮아졌다.

에이전트 쪽 수치가 특히 크게 움직였다.
WildClawBench-MM에서 36.5점, AgenticVBench에서 22.3점 올랐고, UniClawBench에서 69.6을 기록했다.

핵심 역량 개선도 나열한다.
LongAudioSpan에서 8.3점, OmniVideoBench에서 9.6점 상승했다.
OmniCap-IF의 CSR과 ISR이 각각 8.5점, 14.1점 올랐다.
AliMeeting의 DER과 cpWER은 88.11 / 89.61에서 **3.35 / 17.18**로 떨어졌다.

종합 평가는 이렇다. 시청각 성능은 Gemini 3.8 Flash에 근접했고, 전반적인 오디오 성능은 Gemini 3.8 Flash를 넘어섰다는 것이다.

가격 산정 방식도 각주로 밝힌다.
시간당 오디오/시청각 입력 가격은 2분 분량 원본의 입력 비용에 30을 곱해 추정했고, 시청각 입력은 720p 1fps 기준이다.
Gemini 3.8 Flash는 `media_resolution=high`, Seed 2.0 Lite는 `max_frame_tokens=384`를 쓰고 나머지 API 파라미터는 기본값이다.
텍스트 입출력 가격은 1M 토큰당 CNY이며, Gemini와 Muse 가격은 1 USD = 6.7191 CNY로 환산했다.

### 문제 정의와 해법 구성

오디오와 비디오가 에이전트를 실제 생산성 시나리오로 끌어들이는 중요한 매체이지만 시스템 차원의 새로운 문제를 들여온다고 짚는다.

긴 오디오와 비디오는 저장·전송·다회차 추론에 비용이 크고, 기존 에이전트 하네스 프레임워크가 이 양식을 기본 지원하지 않으며, 옴니모달 이해와 종단 간 작업 실행을 잇는 워크플로가 아직 초기 단계라는 것이다.
그래서 모델과 하네스 도구와 런타임 환경이 함께 진화해야 한다고 적는다.

### 에이전트형 이해가 토큰을 절반 가까이 줄였다

발표문에서 가장 구체적으로 검증 가능한 주장이 여기에 있다.

몇 시간짜리 영상에서 기존 방식은 답이 몇 분 분량에만 있어도 전체를 처음부터 끝까지 처리해야 했다.

### 응용 사례

발표문의 절반가량이 워크플로 시연이다.

**제어 가능한 시청각 캡셔닝**은 “모델이 본 것”을 답하던 것에서 “사용자가 알고 싶은 것”을 이해하는 쪽으로 옮겼다는 설명이다.
주제, 시간 범위, 상세도, 출력 형식을 자유롭게 지정할 수 있고, 같은 영상에 대해 개요를 줄 수도 핵심 구간을 짚을 수도 인물 동작·카메라 샷·조명·소리를 깊이 분석할 수도 있다.

**긴 회의**에서는 오디오와 비디오를 가로질러 화자를 함께 인식하며 최대 1시간 분량의 시청각 입력을 기본 지원한다.
화자 분할, 내용 전사, 신원 정렬을 종단 간으로 수행하고, 시각 정보로 오디오의 지시 대상과 개체 모호성을 해소한다.
도구 사용과 결합하면 이메일을 보내고 작업을 정리하고 회의 요구사항에 따라 코딩을 시작할 수도 있다고 적는다.

**Music2MV**, **단편 드라마 번역**, **장편 영화 해설**이 제작 쪽 사례다.
영화 해설의 경우 장편 영상 이해, 핵심 플롯 추출, 해설 기획, 나레이션과 음악 제작, 편집, 렌더링, 최종 품질 검수까지 한 문장의 요구로 수행한다는 주장이다.

**Video2Note**와 **Omni Skill Creator**는 Qwen-MM-Plugins에 오픈소스로 공개했다.
후자는 시연에서 표준 작업 절차(SOP)를 추출해 재사용 가능한 자동화 작업을 만들거나, 전문가 설명에서 도구 사용법·판단 기준·핵심 통찰을 배운다.
시연 하나가 검증과 평가를 거친 에이전트 스킬이 된다.

### 모델이 모델을 개선한 실험

발표문에서 가장 흥미로운 절이다.

Qwen3.8-Omni-Flash에 과제를 줬다. **12시간 안에 Qwen2.5-Omni-3B의 쓰촨 방언 음성 인식을 개선해 쓸 만한 모델을 내놓으라**는 것이다.

모델이 스스로 WenetSpeech-Chuan 평가셋을 골랐고, 평가 기준을 고정했으며, 기준선을 세웠다.
그다음 오디오 샘플을 직접 듣고 인식 결과로 문제를 진단해 표적 학습 데이터를 만들었다.

네 차례 연속 실험에서 에이전트는 3,413개의 학습 예제를 만들었고, 평가 피드백에 따라 접근을 조정했으며, 효과가 있던 개선은 유지하고 실패한 시도는 되돌렸다.
같은 평가셋에서 문자 오류율이 25.79%에서 15.30%로 떨어졌다. 상대 감소 약 40.7%다.

### 지원 언어

음성 인식이 74개 언어와 39개 중국어 방언을, 음성 생성이 29개 언어와 7개 방언을 지원한다.
FLEURS 계열 평가는 60개 언어를 다룬다.

### 사용법

`reasoning_effort`로 추론 깊이와 비용을 조절한다. `xhigh`(기본값), `medium`, `low` 세 단계다.
`preserve_thinking`은 모든 시나리오에서 기본 활성화되어 있다.

OpenAI 호환 Chat Completions와 Responses API를 지원한다.

```python
completion = client.chat.completions.create(
    model="qwen3.8-omni-flash",
    messages=messages,
    extra_body={"enable_thinking": True},
    reasoning_effort="xhigh",  # xhigh, medium, low
    stream=True,
)
```

Qwen-MM-Plugins는 Codex, Claude Code, Qwen Code, Gemini CLI, Qoder, CodeBuddy, OpenClaw를 지원한다.

```bash
curl -fsSL https://raw.githubusercontent.com/QwenLM/Qwen-MM-Plugins/main/install.sh | bash
```

Qwen-Live Harness는 npm으로 설치한다.

```bash
npm install -g qwen-live-harness
qwen-live-harness init
```

## 분석

### 벤치마크 표보다 가격 표가 이 발표의 중심이다

발표문은 성능 개선을 앞세우지만, 실제로 판세를 바꿀 수 있는 숫자는 성능이 아니라 가격이다.

오디오 입력 시간당 98% 인하, 시청각 입력 시간당 93% 인하라는 수치가 그것이다.
그리고 성능 쪽 주장은 대부분 “Gemini 3.8 Flash에 근접” 또는 “일부 항목에서 상회”다.

이 조합이 전형적인 추격자 포지셔닝이다.
성능에서 동급임을 보이고 가격에서 한 자릿수 배수의 차이를 내는 것이다.

HN에서 `_ache_`가 이 계산을 직접 했다.[^ache]
성능이 비슷하고 아니라는 증거가 없다면, 입출력 단가가 Gemini 1.5 / 9.0 대 Qwen 3.8 0.15 / 0.47이므로 막대한 비용 절감이라는 것이다.

다만 이 계산에 즉시 반론이 달렸다.
killingtime74는 토큰당 단가만 볼 수 없고 작업 하나를 해내는 데 평균 몇 토큰이 드는지를 봐야 하며 그 차이가 막대할 수 있다고 적었다.[^killingtime74]

이 반론이 이 발표문 안에서 이미 증명되어 있다는 점이 흥미롭다.
에이전트형 이해가 질의당 토큰을 145,736에서 79,117로 줄였다는 표가 바로 그 이야기다.
같은 모델, 같은 벤치마크에서 운용 방식만 바꿔 토큰이 절반 가까이 움직인다면, 모델 간 단가 비교는 그보다 훨씬 큰 분산 위에 놓인 숫자다.

즉 이 발표문은 “단가를 낮췄다”고 광고하면서 동시에 “단가는 비용의 일부일 뿐”이라는 증거를 스스로 제시한다.

### 하네스를 제품의 일부로 내놓은 것이 이번 발표의 실질적 변화다

모델 하나가 아니라 네 개가 함께 나왔다는 점이 구조적으로 중요하다.

이유가 발표문에 적혀 있다.
기존 에이전트 하네스 프레임워크가 오디오·비디오를 기본 지원하지 않는다는 것이고, 그래서 모델·하네스 도구·런타임이 함께 진화해야 한다는 것이다.

이 진단이 정확하다.
텍스트 에이전트에서 도구 호출의 단위는 명령어와 파일이고 그 결과가 곧 컨텍스트에 들어간다.
영상에서는 그렇지 않다. 2시간짜리 영상을 컨텍스트에 넣는 것은 가능하더라도 비싸고, 대부분의 질문에 불필요하다.
그래서 “어느 구간을 볼지 정하는 도구”가 먼저 있어야 모델이 의미 있게 쓰인다.

Qwen-MM-Plugins의 플러그인 목록이 그 판단을 그대로 반영한다.
`core`가 프레임과 문서를 읽고, `api`가 전사와 화자 분할과 이벤트 분석을 하고, `omni-memory`가 긴 영상에서 사람·대화·소리·사건의 기억을 만든다.
모델이 아니라 이 도구들이 영상을 탐색 가능한 자료로 바꾼다.

그리고 이것이 벤치마크 표의 해석을 바꾼다.
하네스별 비교 표에서 Gemini 3.8 Flash도 Qwen Code를 쓰면 점수가 오른다.
LVOmniBench에서만 예외인데, Omni-Flash는 63.3에서 73.6으로 10.3점 오르고 Gemini는 70.7에서 70.7로 제자리다.

이 한 칸이 발표문의 논리를 지탱한다.
하네스를 붙였을 때 더 많이 얻는 모델이 있다는 주장이고, 그것이 “에이전트 친화적으로 훈련했다”는 말의 측정 가능한 형태다.
다른 두 벤치마크에서는 Gemini가 여전히 앞서므로, 이 주장은 특정 과제 유형에 한정된다.

### 모델이 모델을 튜닝한 실험이 이 발표문에서 가장 새로운 부분이다

쓰촨 방언 실험은 벤치마크가 아니라 작업 방식에 대한 주장이다.

구조를 보면 이렇다.
큰 범용 멀티모달 모델이 데이터를 이해하고 실험을 계획하고 반복을 주도하며, 작은 모델이 특정 응용의 전문 역량을 획득한다.

여기서 결정적인 조건이 하나 있다. **평가가 자동이고 빠르다**는 것이다.
문자 오류율은 기계가 즉시 계산하고, 개선 여부에 해석의 여지가 없다.
그래서 네 차례 실험을 돌리고 효과 있는 것을 남기고 없는 것을 되돌리는 루프가 성립한다.

이 조건이 실험의 일반화 범위를 정한다.
음성 인식, 번역, 분류처럼 지표가 단일하고 자동 계산되는 과제에서는 이 방식이 바로 작동한다.
반면 요약 품질이나 대화 자연스러움처럼 평가 자체가 모델이나 사람의 판단인 과제에서는 같은 루프가 자기 판단을 자기가 채점하는 구조가 된다.

그럼에도 이 절이 값진 이유는 옴니모달이어야만 가능한 단계가 들어 있기 때문이다.
에이전트가 오디오 샘플을 직접 듣고 인식 결과와 대조해 문제를 진단했다는 대목이다.
텍스트 모델이라면 전사 결과만 보고 추측해야 하는 구간을 원본 신호로 확인한 것이고, 이것이 “옴니모달 모델이 연구개발을 주도한다”는 주장의 가장 구체적인 근거다.

### 오픈 웨이트 계보에서 이탈하는 흐름이 배경에 있다

발표문 어디에도 가중치 공개 언급이 없다. Qianwen AI Platform의 API로만 제공된다.

HN에서 andy_ppp가 이 점을 짚었다.[^andy_ppp]
Qwen이 과거에도 Omni 모델을 오픈 웨이트로 공개하지 않았으며, 이번에는 어떻게 할지 알면 좋겠다는 것이다.

`_ache_`가 더 단정적으로 답했다.[^ache-open]
Qwen3.8-Omni-X가 공개되는 일은 없을 것 같고, 마지막으로 공개된 것이 Qwen3-Omni-30B-A3B였으며, Qwen4도 공개되지 않을지 모르고 Qwen3.8은 27B와 거의 쓸 수 없는 125B만 나왔다는 것이다. 오픈 웨이트 공개 속도가 확실히 느려지고 있다고 적었다.

이 관찰이 맞다면 이번 발표의 의미가 달라진다.
Qwen의 시장 위치는 오랫동안 “성능이 준수하면서 가중치가 공개된 모델”이었고, 그것이 로컬 배포와 파인튜닝 생태계를 만들었다.
옴니모달과 실시간 쪽이 API 전용으로 간다면, Qwen은 그 영역에서 Gemini와 같은 종류의 제품이 되고 차별점은 가격만 남는다.

그리고 이 흐름이 오픈소스로 공개된 구성 요소의 성격과도 맞아떨어진다.
공개된 것은 Qwen-Live Harness와 Qwen-MM-Plugins, 즉 **모델을 호출하는 쪽**이다.
하네스를 열어 생태계를 키우고 모델은 닫아 두는 구성이며, 이것이 최근 몇 년간 여러 곳에서 반복된 형태다.

## 비평

### 기준선이 유리하게 선택된 흔적이 표 안에 있다

AliMeeting의 DER/cpWER이 88.11 / 89.61에서 3.35 / 17.18로 떨어졌다는 수치가 발표문 앞부분에서 가장 극적인 숫자로 제시된다.

그런데 벤치마크 표를 보면 Qwen3.5-Omni-Plus의 AISHELL-4 점수가 **100.0 / 100.0**이다.
DER이 100이라는 것은 화자 분할이 전혀 작동하지 않았다는 뜻이다.
MagicData-RAMC도 98.4 / 97.1이다.

즉 이전 세대 모델은 다화자 ASR을 사실상 수행하지 못했다.
그 상태에서 3.4 / 11.2로 간 것은 큰 개선이 맞지만, “88.11에서 3.35로”라는 서술이 암시하는 점진적 향상과는 다른 종류의 사건이다.
없던 기능이 생긴 것에 가깝다.

경쟁 모델과의 비교에서도 같은 문제가 있다.
AliMeeting cpWER에서 Qwen은 17.2이고 Gemini 3.8 Flash는 53.1인데, MagicData-RAMC에서는 Qwen 14.1, Gemini 33.8이지만 MLC-SLM (en)에서는 Qwen 14.2, **Gemini 26.6**으로 격차가 좁고, DER에서는 Qwen이 압도적이다.

DER과 cpWER의 격차가 이렇게 크게 벌어진다는 것 자체가 읽을 거리다.
Qwen은 화자를 나누는 일(DER 3.4)은 매우 잘하는데 그 위에서 무엇을 말했는지 맞히는 일(cpWER 17.2)은 상대적으로 덜 잘한다.
발표문은 두 숫자를 나란히 놓기만 하고 이 비대칭을 설명하지 않는다.

그리고 AliMeeting과 AISHELL-4는 중국어 회의 데이터셋이다. 이 계열에서의 우위가 다른 언어로 이전되는지에 대한 근거는 표에 없다.

### 가격 비교 방법론이 자사에 유리한 가정을 담고 있다

각주에 적힌 산정 방식이 투명한 것은 좋지만, 그 안에 선택이 들어 있다.

시청각 입력을 720p 1fps로 잡았다.
Gemini 3.8 Flash는 `media_resolution=high`로, Seed 2.0 Lite는 `max_frame_tokens=384`로 평가했다.

이 설정들이 각 모델에서 같은 수준의 품질을 내는 조건인지는 밝혀지지 않는다.
경쟁 모델을 고해상도 설정으로 돌리고 자사 모델을 1fps로 돌린 뒤 시간당 단가를 비교하면, 비교되는 것은 가격이 아니라 설정이다.

98%라는 인하율이 특히 그렇다.
2분 분량의 입력 비용에 30을 곱해 시간당 가격을 추정한다는 방식은 캐싱이나 청크 재사용을 전혀 반영하지 않으며, 실제 워크로드에서 한 시간짜리 오디오를 한 번에 밀어 넣는 경우가 얼마나 되는지도 다루지 않는다.

이 지점이 앞서 나온 에이전트형 이해 표와 다시 충돌한다.
발표문 자신이 “전체를 처리하지 말고 필요한 구간만 보라”고 권하는데, 가격 비교는 전체를 처리하는 시나리오를 기준으로 삼고 있다.

### 시연이 많고 검증 가능한 것은 적다

발표문의 상당 부분이 영상 데모다.
뮤직비디오 제작, 단편 드라마 번역, 장편 영화 해설, Video2Note가 각각 여러 개의 데모와 워크플로 도식을 갖고 있다.

이 사례들에 대해 제시된 정량 수치가 없다.
영화 해설이 얼마나 걸렸는지, 몇 번의 실패가 있었는지, 결과물이 사람이 만든 것과 비교해 어떤 수준인지가 전부 영상으로만 제시된다.

HN의 반응이 이 점에 냉정했다.
esquire_900은 블로그 글 자체가 기술적으로 인상적이지 않고 슬롭의 미래 같다고 적었다.[^esquire_900]
Firefox에서 스크롤이 악몽이고 콘솔이 경고와 디버그 데이터로 가득하며, 영상들은 화려하지만 짧은 문단으로 말할 수 있는 것 이상을 전달하지 못하고 스톡 음악이 끔찍하며, 첫 그림은 너무 작아 읽을 수 없고 확대도 되지 않는다는 것이다.

zepearl은 더 구체적인 문제를 보고했다. 그 페이지가 자동으로 **441MiB의 mp4 파일**을 내려받는다는 것이다.[^zepearl]

이 비판이 사소해 보이지만 그렇지 않다.
이 발표문의 주제가 “시청각 워크플로를 효율적으로 다루는 법”인데, 발표문 자체가 시청각 자산을 가장 비효율적인 방식으로 전달하고 있다.
에이전트형 이해가 토큰을 45% 줄였다고 자랑하는 페이지가 방문자에게 441MiB를 강제로 다운로드시키는 구성이다.

그리고 lxe와 syntaxing이 하네스 저장소 링크가 404라고 보고했다.[^lxe][^syntaxing]
오픈소스로 공개했다는 두 구성 요소 중 하나가 발표 시점에 접근되지 않았다는 뜻이다.

### 모델 이름 체계가 사용자의 선택을 돕지 않는다

podocarp가 HN에서 직설적으로 물었다. Flash, Pro, Ultra 같은 것들이 도대체 뭐며 semver 같은 것을 쓸 수 없느냐는 것이다.[^podocarp]

mavamaarten이 제기한 더 근본적인 문제가 여기에 닿는다.[^mavamaarten]
쏟아지는 모델 중에서 용도와 비용에 맞는 것을 골라 주는 도구가 있느냐는 것이며, 자기 사용 사례를 설명하면 시도해 볼 만한 모델 몇 개를 추천받고 싶다는 것이다.
스팸함을 정리하는 도구를 만들었는데 지금은 싸고 충분히 좋으며 네덜란드어와 프랑스어도 어느 정도 되는 `google/gemma-4-31b`를 쓰고 있지만, 모든 모델을 현실적으로 시험해 볼 수는 없다고 적었다.

Systemerror7A69의 답이 실용적이다.[^Systemerror7A69]
전부 시험하지 않는 것이 자기 접근이며, 쓰는 모델이 문제를 만족스럽게 풀고 있다면 금전적 이유가 아닌 한 다른 모델을 시험할 필요가 없다는 것이다.
싼 모델로 시작해 해내는 한 바꾸지 않고, 못 하는 것이 있으면 모델을 바꾸기 전에 도구를 더 주거나 맥락을 개선하거나 다른 접근을 시도한다고 적었다.
그 작업은 나중에 모델을 바꾸더라도 쓸모가 있다는 것이다.

이 교환이 발표문의 벤치마크 표 전체를 상대화한다.
29개 평가에서 25% 개선이라는 수치가 의미 있는 독자는 모델을 고르는 위치에 있는 사람인데, 실제 사용자 다수는 이미 쓰는 모델이 작동하는 한 표를 읽지 않는다.

## 인사이트

### 컨텍스트 절약 기법이 모델 경쟁의 새 축으로 올라왔다

에이전트형 이해가 토큰을 145,736에서 79,117로 줄였다는 표가 이 발표문에서 가장 오래갈 숫자다.

이 숫자가 말하는 것은 성능이 아니라 **비용 구조**다.
같은 모델이 같은 벤치마크에서 운용 방식만 바꿔 비용을 절반으로 줄이면서 정확도를 올렸다.

여기서 나오는 함의가 두 가지다.

첫째, 모델 가격 비교의 유효기간이 짧아진다.
토큰당 단가 차이가 5배여도 운용 방식이 토큰 수를 2배로 바꾸면 순서가 뒤집힐 수 있다.
killingtime74가 단가만 보면 안 된다고 한 지적이 여기서 정확해진다.

둘째, 모델 제공자가 하네스를 함께 내놓는 유인이 커진다.
자사 모델이 자사 하네스에서 가장 잘 동작한다면, 벤치마크 비교의 조건 자체를 자기 쪽으로 가져올 수 있다.
실제로 이 발표문은 Gemini를 Qwen Code 하네스에 넣고 비교했는데, 이 비교가 공정해 보이면서도 미묘하다.
경쟁 모델을 자사 하네스로 평가하는 것은 자사 하네스가 그 모델에 최적화되지 않았다는 조건 아래의 측정이다.

그리고 이 축이 열리면 “어느 모델이 더 좋은가”라는 질문이 점점 답하기 어려워진다.
모델·하네스·프롬프트·도구 구성의 조합이 결과를 지배하는데, 벤치마크는 그중 하나만 바꾸고 나머지를 고정한다.
발표문이 제시한 하네스별 비교 표가 그 복잡성을 드러내는 첫 형태이고, 앞으로 이런 표가 표준이 될 것이다.

### 소리로 위치를 찾는 능력이 로봇공학 쪽으로 향하는 신호다

공간 음향 인지가 발표문에서 가장 조용히 지나가지만 함의가 가장 먼 기능이다.

“이리 와” 또는 “저 소리 뭔지 보고 와” 같은 지시를 받아 환경 소음에서 표적 소리를 분리하고 주변 공간에 접지한 뒤 위치 추정과 경로 계획과 내비게이션을 수행한다는 서술은, 영상 편집이나 회의 요약과 같은 범주의 기능이 아니다.

이것은 **물리적 에이전트의 인지 스택**이다.
카메라만으로는 시야 밖의 사건을 모르고, 마이크만으로는 방향을 알아도 장면을 모른다.
둘을 하나의 모델에서 함께 처리하면 시야 밖에서 난 소리 쪽으로 이동해 확인하는 행동이 가능해진다.

발표문의 벤치마크 표에 ERQA(체화 지능)가 포함되어 있는 것이 우연이 아니다.
Qwen3.8-Omni-Flash가 71.0, Claude-Opus-4.6 (Max)가 40.8이다.

그리고 실시간 지연 수치가 이 방향과 맞물린다.
시청각 20초 입력에서 첫 오디오 패킷까지 1,350ms이고 RTF가 0.153이다.
사람 대화에는 느리지만 “소리가 난 쪽을 확인하러 간다”는 행동에는 충분하다.

여기서 나오는 예측이 하나 있다.
옴니모달 모델의 다음 경쟁 지표는 벤치마크 정확도가 아니라 **인지에서 행동까지의 지연**이 될 것이다.
지금은 모델이 얼마나 잘 이해하는지를 재는데, 물리적 작업에서는 얼마나 빨리 반응하는지가 성패를 가른다.

### 큰 모델이 작은 모델을 튜닝하는 구조가 파인튜닝 서비스의 형태를 바꾼다

쓰촨 방언 실험이 제시하는 작업 흐름을 일반화하면 이렇게 된다.
평가셋 선정 → 기준선 측정 → 원본 데이터 직접 검토 → 오류 진단 → 표적 데이터 생성 → 학습 → 평가 → 유지 또는 롤백.

이 루프의 각 단계가 지금까지 사람의 전문성을 요구했고, 그래서 도메인 특화 모델을 만드는 일이 비쌌다.

여기서 비용이 떨어지면 시장의 모양이 바뀐다.
지금 파인튜닝 서비스의 가치 제안은 대체로 “학습 인프라를 대신 운영해 준다”인데, 실제 병목은 인프라가 아니라 **무엇을 어떻게 고칠지 판단하는 일**이었다.
그 판단이 자동화되면 서비스의 경계가 인프라에서 진단 루프로 옮겨 간다.

그리고 이 구조가 오픈 웨이트 논쟁과 교차한다.
큰 모델이 API 전용이고 작은 모델이 공개 가중치라면, 이 루프는 “닫힌 모델이 열린 모델을 개선한다”는 형태가 된다.
개선된 작은 모델은 로컬에서 돌릴 수 있지만, 그것을 만드는 과정은 API 호출에 의존한다.

`_ache_`가 관찰한 오픈 웨이트 공개 둔화가 이 구도에서 다르게 읽힌다.[^ache-open]
공개를 줄이는 것이 단순한 폐쇄 전환이 아니라, 큰 모델을 닫고 그것을 도구로 쓰는 작은 모델 생태계를 여는 배치일 수 있다.
그 배치에서 실질적 통제력은 여전히 큰 모델 쪽에 남는다.

testaburger가 HN에서 Gemini 3.8 Flash가 아마도 이들의 증류 대상일 것이라고 짧게 적은 것도 같은 층위의 이야기다.[^testaburger]
누가 누구를 개선의 재료로 쓰는가가 모델 공개 정책의 실제 쟁점이라는 것이다.

### 유럽 부재론에 대한 반론이 더 정확한 질문을 만든다

andy_ppp가 왜 중국은 모델을 만드는데 유럽은 못 하느냐고 물었다.[^andy_ppp]
알고리즘이 그렇게 복잡하지 않은데 에너지 비용인지, 데이터 확보의 불법성과 어려움인지, 문샷 연구소를 세울 자본의 부족인지, 낙관의 부족인지 묻고, 중국은 미국과 유럽이 살 수 있는 GPU 근처에도 못 가면서 해내는 것 같다고 적었다.

두 갈래의 답이 달렸다.

EagnaIonat은 사실을 바로잡았다.[^EagnaIonat]
Mistral이 있고, EU는 범용 LLM보다 특화 모델에서 앞서 있으며, Flux3, Kyutai, H Company, LightOn, AMD Silo(핀란드), OpenEuroLLM과 EuroLLM이 있고 더 있을 것이라고 나열했다.

zipy124는 질문의 전제를 바꿨다.[^zipy124]
못 하는 것이 아니라 굳이 할 이유가 없다는 것이며, 상품화 측면에서 바닥을 향한 경쟁이므로 Legora나 Lovable처럼 모델 계층 위에 짓는 편이 훨씬 똑똑하다는 것이다.

이 반론이 이번 발표문과 겹쳐 읽힌다.
Qwen이 시간당 단가를 98% 낮췄다는 것은 정확히 zipy124가 말한 바닥을 향한 경쟁의 모습이다.
그리고 같은 발표문에서 오픈소스로 내놓은 것이 모델이 아니라 하네스와 플러그인, 즉 **모델 계층 위의 것들**이다.

그래서 흥미로운 질문은 누가 모델을 만드느냐가 아니라, 모델 제공자 자신이 모델 계층 위로 올라가고 있다는 사실이다.
Qwen-MM-Plugins가 Codex와 Claude Code와 Gemini CLI를 지원한다는 문장이 그 증거다.
경쟁사 하네스에 자사 플러그인을 심는 것은 모델 판매가 아니라 워크플로 점유를 노리는 움직임이고, 마진이 사라지는 계층에서 사라지지 않는 계층으로 이동하는 표준적인 경로다.

conception이 Qwen을 “구식 믿을 만한” 모델로 고르겠다고 하면서 RL로 망가뜨리지 않기를 바란다고 적은 것이[^conception] 이 이동의 반대편에 있는 정서다.
사용자가 원하는 것은 예측 가능한 도구인데, 제공자가 워크플로 점유로 가면 모델은 점점 제품의 일부가 되고 단독으로 예측 가능하기를 멈춘다.
