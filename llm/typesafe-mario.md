# TypeSafe Mario: 스크린샷 없이 구조화된 상태만으로 마리오를 플레이하는 에이전트

> An experimental controller that lets TypeSafe's Jev model directly choose
> NES controller inputs for the original Super Mario Bros.

<https://github.com/fhshaik/typesafe-mario>

## 소개

TypeSafe의 Jev 모델이 원작 Super Mario Bros.의 NES 컨트롤러 입력을 직접 고르게 하는 실험적 컨트롤러다.
2026년 9월 16일에 만들어진 저장소이며 Python으로 작성됐다. 스타 212개, 포크 21개, 열린 이슈 0개이고 라이선스는 지정되어 있지 않다.

이 프로젝트가 내세우는 계약은 한 문장에 담긴다. 모델은 스크린샷을 받지 않는다는 것이다.
하네스가 에뮬레이터 텔레메트리와 RAM을 마리오의 움직임, 점프 궤적, 다가오는 적, 지형, 측정된 응답 지연, 최근 조작 결과, 에피소드 진행을 담은 간결한 객체 중심 JSON으로 번역한다.
Jev는 합법적인 컨트롤러 동작 중 하나를 고르고, 에뮬레이터가 몇 프레임을 진행하고, 이 루프가 반복된다.
원시 로컬 타일 격자는 디버그 로그와 UI에서 여전히 볼 수 있지만 모델 입력에는 중복해서 넣지 않는다.

저장소에는 닌텐도 ROM이나 저작권이 있는 게임 데이터가 들어 있지 않으며, 에뮬레이터와 게임 파일을 합법적으로 구하고 쓰는 것은 사용자 책임이라고 명시한다.

이 문서는 Jev 모델 자체를 다루지 않는다. 그쪽은 `jev`를 참고하면 되고, 여기서는 그 모델을 실제 제어 루프에 물렸을 때 무엇을 만들어야 하는지를 본다.

## 아키텍처

파이프라인은 한 줄로 요약되어 있다.

```text
NES emulator -> telemetry/RAM parser -> structured JSON -> Jev Choice -> controller input
```

초기 동작 집합은 의도적으로 작게 잡혀 있고, `gym_super_mario_bros`의 `SIMPLE_MOVEMENT` 인덱스와 그대로 대응된다.

| 동작             | 인덱스 | 설명                                                              |
| ---------------- | ------ | ----------------------------------------------------------------- |
| `noop`           | 0      | 조작을 놓고 현재 관성을 유지한다                                  |
| `right`          | 1      | 점프 없이 보통 속도로 오른쪽 이동                                 |
| `right_jump`     | 2      | 통제된 전진 점프를 시작하거나, 상승 중 점프를 계속 눌러 높이 유지 |
| `right_run`      | 3      | 신뢰 가능한 지형이 비어 있고 takeoff 마감이 아닐 때만 달리기      |
| `right_run_jump` | 4      | 달리기 점프. takeoff 마감일 때 우선 선택                          |
| `jump`           | 5      | 제자리 점프. 전진이 위험할 때 상승 중 유지                        |
| `left`           | 6      | 위험 회피나 과주행 복구                                           |

점프 계열은 별도로 묶여 있고, 각 점프 동작에는 점프를 놓았을 때 이어질 동작이 짝지어져 있다.
`right_jump`는 `right`로, `right_run_jump`는 `right_run`으로, `jump`는 `noop`으로 풀린다.
점프를 누르고 있는 상태와 놓은 상태를 같은 어휘 안에서 표현하기 위한 장치다.

## 파서가 만드는 것

README가 밝히듯 TypeSafe는 JSON을 직접 받으므로 텔레메트리를 산문으로 평탄화할 필요가 없다.
모델을 향하는 객체는 관찰을 의미별로 묶는다.

| 키                | 담는 것                                                      |
| ----------------- | ------------------------------------------------------------ |
| `player`          | 위치, 속도, 접지 상태, 점프 단계, 파워업                     |
| `trajectory`      | 체공 시간, 이륙 이후 거리, 확정된 간극 횡단 여부             |
| `hazard`          | 적 최대 3기, 투영 위치, 접촉 시점, takeoff 마감              |
| `terrain`         | 장애물과 간극 기하, 관측 신뢰도, 마지막 접지 시점의 미리보기 |
| `reaction_timing` | 동작 지속 시간, 측정된 관측에서 행동까지의 지연              |
| `recent_control`  | 선택한 동작, 지속 시간, 얻은 진행, 관측된 결과               |
| `episode`         | 목숨, 시계, 진행, 정체, 사망, 스테이지 클리어                |

사람을 위해서는 더 풍부한 디버그 스냅숏을 간결한 텍스트로 렌더링할 수 있다.

```text
Goal: Reach the flag in World 1-1 without dying.
Mario: x=172 y=79, moving right, airborne=False, status=small
Progress: 172 (best 172), time=387, lives=2
Nearby enemies: goomba 42px ahead
Local grid (# solid, . empty, E enemy, M Mario):
...........
...........
...........
..M..E.....
###########
```

README는 이 관계를 명시한다. 구조화된 객체가 정본이고 텍스트 뷰는 디버깅과 UI 전용이다.

적은 RAM의 종류 ID로 식별되어 이름이 붙는다. `0x06`이 굼바, `0x05`가 해머 브로, `0x0E`가 치어치어, `0x12`가 뻐끔플라워, `0x2D`가 쿠파, `0x31`이 깃대다.
개별 적 관측은 상대 좌표와 상대 속도를 담고, 앞인지 뒤인지를 `horizontal_relation`으로 따로 표기한다. 모델이 부호를 해석하게 두지 않는다는 뜻이다.

## 세 가지 판정

매 요청은 같은 상태에 대해 세 개의 독립적인 판정을 평가한다.
`Choice`가 다음 컨트롤러 매크로를 고르고, `Noul`이 지금 전진 점프가 유용한지 추정하며, `Score`가 실시간 시각화를 위해 즉각적인 위험도를 잰다.

실제 호출부가 이 설계를 그대로 드러낸다.

```python
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()

questions = {
    # 선택지는 액션 이름 -> 설명 매핑으로 넘긴다. 모델이 자유 문자열을 만들 여지가 없다.
    "next_action": Choice(
        instructions={
            "question": "Which controller macro should Mario commit to next?",
            "goal": "Advance toward the stage flag while avoiding death.",
            "timing": "The selected action is held for at least 8 emulator frames.",
            # ... geometry / trajectory / stall / enemy_timing / delay 지침이 이어진다
        },
        criteria={action.value: ACTION_DESCRIPTIONS[action] for action in actions},
    ),
    "jump_needed": Noul(instructions="... 전진 점프를 시작하거나 유지해야 하는가?"),
    "danger": Score(
        instructions="How dangerous is Mario's immediate situation?",
        criteria=[
            "Safe open movement",
            "Potential obstacle or enemy soon",
            "Immediate collision, fall, or enemy threat",
        ],
    ),
}

response = client.system_one(state=snapshot.to_state(), questions=questions)
```

응답에서 꺼내는 값도 타입별로 나뉜다.
`Choice`에서는 선택된 동작과 전체 확률 분포와 신뢰도를, `Noul`에서는 확률 하나를, `Score`에서는 점수 하나를 꺼낸다.
코드는 `response.choices` 같은 타입별 컬렉션을 먼저 보고 없으면 `response.answers`로 물러서며, 둘 다 없으면 키 오류를 던진다. 빠진 답을 조용히 넘기지 않는다.

가장 중요한 설계 결정은 README의 마지막 문단에 있다.
정확한 타이밍 산술은 코드에 남는다는 것이다.
파서가 측정된 응답 지연, 적의 움직임, 동작 주기, 점프로 넘는 데 걸리는 시간을 합쳐 `jump_must_start_this_decision`이라는 타입이 지정된 사실 하나로 만든다.
Jev는 그 사실들을 해석하되 컨트롤러 선택은 여전히 자기가 갖고, 스크립트로 된 복구 동작 오버라이드는 없다.

## 실행하기

Windows PowerShell 기준 절차가 README에 있다. Python 3.13 이상과 `TYPESAFE_API_KEY`, 그리고 합법적인 로컬 Super Mario Bros. 구성이 필요하다.

```powershell
py -3.13 -m venv .venv
.venv\Scripts\python -m pip install -e ".[mario,dev]"
$env:TYPESAFE_API_KEY = "your-key"
```

게임을 띄우거나 API를 호출하지 않고, 실제로 전송될 JSON과 텍스트만 확인하는 명령이 따로 있다.

```powershell
.venv\Scripts\typesafe-mario state-demo
```

실제 플레이는 결정 간 프레임 수를 지정해 실행한다.

```powershell
.venv\Scripts\typesafe-mario play --env SuperMarioBros-1-1-v0 --frames-per-decision 8
```

기본 표시는 실시간 게임과 모델 텔레메트리를 함께 담은 녹화 가능한 창 하나다.
대시보드는 선택된 동작, 전체 `Choice` 확률 분포, 신뢰도, Jev 지연, 점프 확률, 위험 점수, 보상, 파싱된 게임 상태를 보여 준다.
`R`이나 Restart로 새 에피소드를 시작하고, 사망이나 클리어 후에도 대시보드는 열려 있으며, `Esc`나 `Q`로 종료한다.
`--display game`은 에뮬레이터 창만, `--display none`은 헤드리스 벤치마크용이다.

모든 결정은 `artifacts/run-<timestamp>.jsonl`에 기록된다.
지연, 동작 확률, 신뢰도, 정본 모델 상태, 원시 디버그 상태, 게임 결과가 들어가며, 실시간 오버레이나 소셜 클립 렌더링의 데이터가 된다.

## 값 정하기

| 값                      | 기본 | 근거와 조정 기준                                                                    |
| ----------------------- | ---- | ----------------------------------------------------------------------------------- |
| `--frames-per-decision` | 8    | 한 번의 API 호출이 커버하는 게임 시간. 낮추면 반응이 빨라지고 호출 수와 비용이 는다 |
| 동작 집합 크기          | 7    | `SIMPLE_MOVEMENT`와 1:1. 늘리면 표현력이 늘지만 `Choice` 확률이 분산된다            |
| `hazard` 적 수          | 3    | 뒤에 숨은 두 번째·세 번째 적을 보되 입력 크기는 묶어 두려는 절충                    |
| `--display`             | 기본 | 벤치마크를 돌릴 때는 `none`으로 두어야 렌더링 비용이 측정에서 빠진다                |

무엇을 측정해 이 값들을 고칠지가 저장소 구조에 이미 들어 있다.
`artifacts/*.jsonl`에 지연과 확률과 결과가 함께 남으므로, 결정 주기를 바꿔 가며 사망 지점과 지연 분포를 비교하면 된다.
특히 `--frames-per-decision`은 아래 트레이드오프에서 보듯 이 프로젝트의 중심 변수다.

## 트레이드오프

### 픽셀을 버리고 얻은 것과 잃은 것

스크린샷을 주지 않는 선택이 이 프로젝트의 정체성이다.
얻는 것은 세 가지다. 입력 토큰이 극적으로 줄고, 모델이 화면을 해석하다 틀릴 여지가 사라지며, 무엇을 근거로 판단했는지가 JSON 키로 남아 사후 분석이 가능해진다.
특히 마지막 것이 크다. 실패한 결정에 대해 그때 `terrain.observation_reliability`가 얼마였는지를 로그에서 바로 꺼낼 수 있다.

잃는 것은 파서가 모델링하지 않은 모든 것이다.
RAM에서 읽어 객체로 만들지 않은 현상은 모델에게 존재하지 않으며, 그것이 중요해지는 순간 모델은 실패하되 왜 실패했는지도 알 수 없다.
`ENEMY_NAMES`에 여덟 종류만 있다는 사실이 그 경계를 보여 준다. 목록에 없는 ID는 이름이 붙지 않은 채 들어가거나 빠진다.

여기서 흔히 떠올리는 해법이 통하지 않는다.
그럼 스크린샷도 같이 주면 되지 않느냐는 생각인데, 그러면 이 프로젝트가 증명하려던 것이 사라진다.
모델이 픽셀과 JSON 중 어느 쪽을 보고 판단했는지 구분할 수 없게 되고, 토큰 비용과 지연이라는 이점도 함께 사라진다.
둘 다 가질 수는 없고, 실제로 남는 선택은 파서를 계속 키우는 것뿐이다.

### 판단을 어디까지 코드로 옮길 것인가

README가 가장 힘주어 밝히는 경계가 이것이다. 정확한 타이밍 산술은 코드에 남고 모델은 그 사실들을 해석한다는 것이다.
`jump_must_start_this_decision`은 그 경계선 위에 놓인 값이다. 응답 지연과 적 속도와 점프 소요 프레임을 코드가 계산해 불리언 하나로 만든다.

이 선택의 이점은 분명하다. 산술은 결정론적이므로 코드가 하는 편이 정확하고 재현 가능하며 디버깅 가능하다.
그리고 모델에게는 계산이 아니라 판단만 남으므로, 같은 상태에서 다른 답이 나올 여지가 줄어든다.

대가는 그 불리언이 사실상 정책이 된다는 것이다.
`jump_must_start_this_decision`이 참일 때 전진 점프를 고르라고 `Choice` 지침이 명시하고, 같은 값이 참이면 `Noul`도 명백히 예라고 지침에 적혀 있다.
즉 이 한 값이 두 판정의 답을 거의 결정하며, 그 계산식이 틀리면 모델의 판단력과 무관하게 실패한다.
README가 스크립트로 된 복구 동작 오버라이드는 없다고 강조하지만, 오버라이드가 없을 뿐 유도는 강하다.

그렇다고 산술까지 모델에 넘기면 더 나빠진다. 프레임 단위 타이밍은 언어 모델이 안정적으로 하기 어려운 종류의 계산이고, 틀렸을 때 관측도 어렵다.
남는 현실적 절충은 경계를 옮기는 것이 아니라 경계에 놓인 값의 수를 줄이고 각각을 로그로 검증 가능하게 두는 것이다.

### 결정 주기 8프레임이라는 숫자

`--frames-per-decision 8`은 NTSC 기준 약 0.13초마다 한 번 결정한다는 뜻이다.
이 값이 낮아지면 반응이 빨라지지만 API 호출 수가 그만큼 늘고, 높아지면 비용이 줄지만 한 번의 잘못된 선택이 더 오래 유지된다.

이 구조에서 주기는 단순한 성능 손잡이가 아니라 상태 표현의 일부다.
`Choice` 지침이 선택된 동작이 최소 8 에뮬레이터 프레임 동안 유지된다고 모델에게 알려 주고, `reaction_timing`이 관측에서 행동까지의 지연을 실측해 넣는다.
즉 주기를 바꾸면 모델이 받는 설명도 함께 바뀌어야 하며, 숫자만 고치면 지침과 실제가 어긋난다.

여기에 이 방식이 감당하기 어려운 한계가 있다.
게임의 어떤 구간은 프레임 단위 정밀도를 요구하는데, 모델 왕복 지연이 결정 주기보다 길면 그 구간은 원리적으로 통과할 수 없다.
`reaction_timing`을 상태에 넣어 모델이 투영된 거리로 판단하게 한 것이 그 지연을 다루는 방식이지만, 지연을 보정하는 것과 지연을 없애는 것은 다르다.

### 세 판정을 나눈 구조

한 번의 요청에서 `Choice`, `Noul`, `Score`를 각각 받는 설계는 관심사를 분리한다.
동작 선택은 제어에, 점프 확률은 해석에, 위험 점수는 시각화에 쓰인다. 실제로 `Score`의 용도는 README에 실시간 시각화라고 명시되어 있다.

이 분리의 이점은 각 값이 독립적으로 검증 가능하다는 것이다.
점프 확률이 높았는데 점프를 고르지 않은 결정이 로그에 남으면 그 자체가 조사할 만한 신호가 된다.

대가는 세 답이 서로 모순될 수 있다는 것이고, 코드는 그 모순을 해소하지 않는다.
`Decision`은 세 값을 나란히 담을 뿐 `jump_needed_probability`가 높을 때 `action`을 바꾸지 않는다.
일관성 강제를 넣으면 모델의 선택을 덮어쓰게 되어 앞서 말한 오버라이드 없음 원칙과 충돌하고, 넣지 않으면 모순이 그대로 남는다.
이 프로젝트는 후자를 택했고, 그래서 모순의 빈도 자체가 측정 가능한 지표가 된다.

## 함정

액션 설명이 사실상 정책 문서다.
`ACTION_DESCRIPTIONS`의 `right_run` 항목은 신뢰 가능한 지형이 비어 있고 `hazard.jump_must_start_this_decision`이 거짓일 때만 달리라고 적혀 있다. 동작의 뜻이 아니라 언제 그것을 고르라는 조건이다.
동작 목록을 늘리거나 고칠 때 이 문자열이 정책의 일부라는 것을 잊으면, 프롬프트를 고치지 않고 정책을 바꾼 셈이 된다.

`terrain.observation_reliability`가 낮은 상태가 정상적으로 존재한다.
공중에 있을 때는 현재 기하보다 `terrain.last_grounded_preview`를 쓰라고 지침이 지시한다. 즉 파서가 항상 믿을 만한 지형을 주지는 않으며, 그 사실을 모델이 알아서 다뤄야 한다.
지형 관련 실패를 조사할 때 이 값을 먼저 봐야 하는 이유다.

로컬 격자는 모델 입력에 없다.
디버그 로그와 UI에는 보이므로 사람이 화면을 보며 왜 저걸 못 봤냐고 생각하기 쉬운데, 모델은 그 격자를 받지 않았다.
사람이 보는 것과 모델이 받는 것이 다르다는 사실이 이 프로젝트에서 가장 혼동을 일으킬 지점이다.

라이선스가 지정되어 있지 않다.
GitHub API 기준 license 필드가 비어 있으므로, 기본적으로는 저작권이 저자에게 유보된 상태다. 코드를 가져다 쓰려면 먼저 확인해야 한다.

저장소가 만들어진 날과 마지막 푸시가 같은 날이다.
2026년 9월 16일에 생성되어 같은 날 마지막으로 푸시됐다. 스타 212개는 그 이후에 붙은 것이며, 유지보수 이력이 아직 없는 프로젝트다.

실행 절차가 PowerShell 기준으로만 적혀 있다.
`py -3.13`과 `.venv\Scripts\`와 `$env:` 표기는 전부 Windows용이다. 다른 OS에서는 경로와 환경 변수 설정을 바꿔야 하고, `nes-py` 계열은 플랫폼마다 빌드 사정이 다르다.

## 확인하기

API 키 없이도 이 프로젝트의 핵심을 볼 수 있는 경로가 있다.

```powershell
.venv\Scripts\typesafe-mario state-demo
```

이 명령이 게임을 띄우지도 API를 부르지도 않고 전송될 JSON과 텍스트만 출력한다.
그 출력을 읽는 것이 이 저장소에서 가장 값진 학습이며, 확인할 것은 세 가지다.

첫째, 각 키가 원시 수치가 아니라 판정된 사실인지 본다.
`relative_x_pixels`처럼 수치가 그대로 있는 것과 `horizontal_relation`처럼 앞뒤가 이미 판정된 것이 섞여 있는데, 후자의 비율이 이 설계의 핵심이다.

둘째, 모델이 직접 계산해야 하는 것이 무엇이 남았는지 센다.
`jump_must_start_this_decision`처럼 코드가 끝내 준 것과, 여러 키를 조합해 모델이 판단해야 하는 것의 경계가 거기서 드러난다.

셋째, 같은 상태의 텍스트 뷰와 비교한다.
텍스트에는 로컬 격자가 있지만 모델 입력에는 없다는 차이가 눈으로 확인되며, 그것이 앞서 말한 혼동의 원인이다.

로컬에서 오프라인으로 루프 구조만 보고 싶다면 `HeuristicPolicy`가 있다.
코드 주석이 밝히듯 오프라인 스모크 테스트용이고 마리오 벤치마크의 기준선으로 의도된 것은 아니지만, API 없이 파이프라인이 도는지 확인하는 데는 쓸 수 있다.

## 비평

### 스크린샷을 주지 않은 것이 공정한 비교를 어렵게 만든다

이 저장소의 주장은 구조화된 상태만으로 게임을 제어할 수 있다는 것이고, 그것은 시연으로 성립한다.
그런데 이 결과를 픽셀 기반 에이전트와 비교해 무엇이 더 낫다고 말하려는 순간 문제가 생긴다.

파서가 하는 일의 상당 부분이 원래 인식(perception)의 영역이기 때문이다.
적의 종류를 RAM ID로 식별하고, 상대 속도를 계산하고, 접촉 시점을 투영하고, 지형의 신뢰도를 매기는 것은 픽셀 기반 에이전트라면 스스로 해내야 하는 일이다.
그 일을 사람이 쓴 코드가 대신하고 있으므로, 남은 과제는 결정이지 인식이 아니다.

그래서 이 프로젝트가 실제로 보여 주는 것은 모델이 마리오를 할 수 있다는 것이 아니라, 잘 설계된 상태 표현이 있으면 결정 모델이 제어 루프에 들어갈 수 있다는 것이다.
두 명제는 크게 다르고, 저장소 설명은 전자처럼 읽히기 쉽다.
README가 스크린샷을 받지 않는다는 사실을 굵은 글씨로 강조하면서 그 대신 무엇을 받는지는 아래에 길게 나열한 배치가 그 인상을 만든다.

### 지침의 양이 모델의 몫을 좁힌다

`Choice` 하나에 들어가는 지침을 세어 보면 question, goal, timing, geometry, trajectory, stall, enemy_timing, delay로 여덟 항목이다.
그중 enemy_timing 항목만 해도 네 개의 조건문을 담고 있다. `jump_must_start_this_decision`이 참이면 지금 전진 점프를 고르고, `contact_within_reaction_horizon`이 참이면 즉시 점프하고, `will_land_before_contact`가 참이면 이번 점프로는 못 넘으니 착지 후 다시 이륙해야 한다는 식이다.

이 지침들을 합치면 사실상 결정 트리 한 벌이 자연어로 적혀 있는 셈이다.
그렇다면 모델이 기여하는 부분이 어디인지가 흐려진다. 조건이 전부 만족될 때 무엇을 할지가 이미 문장으로 정해져 있기 때문이다.

이것은 결함이라기보다 이 계열 시스템의 구조적 성질이다.
결정 모델에게 안정적인 출력을 받으려면 지침을 촘촘히 써야 하고, 촘촘히 쓸수록 모델이 아니라 지침이 정책이 된다.
다만 그렇다면 평가의 대상도 달라져야 한다. 모델의 판단력이 아니라 지침의 품질을 평가해야 하는데, 저장소에는 지침을 바꿔 가며 비교한 흔적이 없다.

`HeuristicPolicy`가 그 빈자리를 드러낸다.
코드 주석이 스스로 밝히듯 오프라인 스모크 테스트용이고 벤치마크 기준선으로 의도된 것이 아니다.
즉 이 지침과 상태 표현으로 규칙 기반 정책을 제대로 짰을 때 어디까지 가는지가 비교되지 않았고, 그 비교가 없으면 모델이 얼마나 기여했는지 말할 수 없다.

### 하루 만에 만들어진 저장소가 받은 관심의 성격

생성일과 마지막 푸시가 같은 날이고, 그 상태로 스타 212개를 받았다.
이슈는 0개이고 라이선스는 없다.

이 숫자 조합이 말하는 것은 사용이 아니라 관심이다.
실행하려면 Python 3.13과 Windows 전제의 절차와 TypeSafe API 키와 합법적인 ROM이 필요한데, 이 네 가지를 모두 갖춘 사람의 수가 스타 수에 가까울 리 없다.
즉 대부분의 스타는 코드를 돌려 보고 붙인 것이 아니라 발상에 붙은 것이다.

이 구분이 중요한 이유는 저장소를 평가 자료로 쓸 때다.
스타 수는 이 접근이 실제로 잘 작동한다는 증거가 아니며, 이슈가 0개라는 것도 문제가 없다는 뜻이 아니라 아직 아무도 깊이 써 보지 않았다는 뜻에 가깝다.
데모가 설득하는 것과 시스템이 검증되는 것은 다른 일이고, 지금 이 저장소는 앞쪽에 있다.

## 체크리스트

- 에뮬레이터와 ROM을 합법적으로 확보했는가
- Python 3.13 이상인가
- `TYPESAFE_API_KEY`를 설정했는가
- API를 부르기 전에 `state-demo`로 전송될 JSON을 읽어 보았는가
- 모델 입력에 로컬 격자가 없다는 것을 인지하고 실패를 해석하고 있는가
- `--frames-per-decision`을 바꿨다면 `Choice` 지침의 프레임 수 설명도 함께 고쳤는가
- 벤치마크를 돌릴 때 `--display none`으로 렌더링 비용을 제외했는가
- `artifacts/*.jsonl`을 보존해 지연과 확률과 결과를 함께 분석할 수 있게 했는가
- 라이선스가 비어 있다는 것을 확인하고 재사용 여부를 판단했는가

## 기억할 원칙

### 상태 표현을 설계하는 일이 모델을 고르는 일보다 먼저다

이 저장소에서 가장 큰 파일은 모델을 호출하는 `policy.py`가 아니라 상태를 만드는 `state.py`다. 25KB 대 6.7KB로 거의 네 배다.
이 비율이 이런 종류의 시스템에서 실제 작업이 어디에 있는지를 정확히 말해 준다.

그리고 그 작업의 성격은 데이터 변환이 아니라 존재론 설계에 가깝다.
무엇을 하나의 객체로 볼 것인지, 어떤 수치를 판정된 사실로 바꿀 것인지, 무엇을 모델에게 숨길 것인지를 정하는 일이다.
적의 상대 x를 그대로 주면서 동시에 앞뒤 관계를 따로 판정해 넣은 결정이 그 예다. 같은 정보를 두 형태로 주되 해석 부담을 줄이겠다는 선택이며, 그런 결정 수백 개가 모여 `state.py`가 된다.

여기서 나오는 실천적 함의는 순서에 관한 것이다.
어떤 모델을 쓸지 정하기 전에, 이 도메인에서 하나의 결정을 내리는 데 필요한 사실이 무엇인지를 먼저 적어 보는 것이다.
그 목록이 만들어지면 모델 교체는 비교적 싼 작업이 되고, 목록 없이 모델부터 붙이면 프롬프트에 도메인 지식이 흩어져 교체가 불가능해진다.

이 프로젝트가 그 순서를 지켰다는 증거가 `state-demo` 명령이다.
게임도 API도 없이 전송될 상태만 출력하는 진입점을 따로 만들어 두었다는 것은, 상태 표현 자체를 독립적으로 들여다볼 대상으로 취급했다는 뜻이다.
같은 시스템을 만들 때 가장 먼저 만들어 둘 만한 것이기도 하다.
