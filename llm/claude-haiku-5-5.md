# Claude Haiku 5.5: 값을 75% 내리고 하위 에이전트 자리를 노린 소형 모델

원문: [Introducing Claude Haiku 5.5 \ Anthropic](https://www.anthropic.com/claude-haiku-5-5)

HN 토론: <https://news.ycombinator.com/item?id=49996437> (732점, 370개 댓글)

GN 토론: <https://news.hada.io/topic?id=34958>

## 요약

Anthropic이 2026년 10월 7일에 공개한 Claude Haiku 5.5의 발표문이다.
Opus 5.5와 Sonnet 5.5에 이어 Claude 5.5 계열을 채우는 세 번째 모델이며,
발표문은 이를 지금까지 내놓은 소형 모델 가운데 가장 싸고, 가장 빠르고,
가장 유능한 모델이라고 소개한다.
모델 식별자는 `claude-haiku-5-5`다.

겨냥하는 일은 양이 많고 비용에 민감한 작업이다.
요약, 컴팩션(compaction), 데이터베이스 질의, 분류처럼 빠르고 반복적인 일을
안정적으로 처리하고, 코딩 작업에서는 Opus 5.5와 Sonnet 5.5 아래의
하위 에이전트(subagent)로 잘 맞는다고 적는다.
지금까지 나온 모델 중 가장 빠르므로 실시간 고객 지원과 브라우저 사용처럼
속도가 중요한 작업에도 맞다고 한다.
다만 각주에서, 가장 빠르다는 말은 각 모델의 표준 속도 기준이며
Fast Mode의 Opus 모델보다는 느리다고 단서를 단다.

### 가격

가장 크게 내세우는 것은 값이다.
백만 토큰당 가격은 다음과 같으며, Haiku 5.5는 프롬프트가 10만 토큰을
넘는지에 따라 값이 다섯 배 달라진다.

| 항목      | Haiku 5.5 (10만 이하 / 초과) | Haiku 4.5 | Sonnet 5.5 |
| --------- | ---------------------------- | --------- | ---------- |
| 캐시 읽기 | $0.01 / $0.05                | $0.10     | $0.10      |
| 캐시 쓰기 | $0.125 / $0.625              | $1.25     | $2.50      |
| 입력 토큰 | $0.10 / $0.50                | $1.00     | $2.00      |
| 출력 토큰 | $0.50 / $2.50                | $5.00     | $10.00     |

각주의 설명에 따르면 10만 토큰 이하 요청은 Haiku 4.5보다 90%,
초과 요청은 50% 싸다.
이전 Haiku에 들어온 요청의 약 90%가 10만 토큰 이하였으므로,
평균으로는 실행 비용이 약 75% 줄어든다고 한다.
이 계산에는 새 토크나이저가 같은 작업에 토큰을 조금 더 쓴다는 점도
반영했다고 밝힌다.

### 벤치마크

발표문의 표는 다음과 같다.
Sonnet 5.5는 참고용으로 함께 실었다.

| 벤치마크                         | Haiku 5.5 | Haiku 4.5 | GPT-6 Luna | Sonnet 5.5    |
| -------------------------------- | --------- | --------- | ---------- | ------------- |
| GDPval-AA v2.1 (Elo)             | 1620      | 735       | 1437       | 1840          |
| AA-Briefcase v1.1                | 1578      | 614       | 1336       | 1824          |
| OSWorld 2.1 (오프라인 부분집합)  | 72.4%     | 15.7%     | 48.9%      | 83.9%         |
| Humanity’s Last Exam (도구 없음) | 45.9%     | 10.2%     | —          | 56.9%         |
| Humanity’s Last Exam (도구 사용) | 57.4%     | 18.7%     | —          | 64.5%         |
| Terminal-Bench 4.0               | 39.2%     | 0.0%      | 16.4%      | 70.6%         |
| FrontierCode 1.1 (Main)          | 46.4%     | —         | 42.4%      | 52.1% (Xhigh) |
| Chartography (도구 없음)         | 46.4%     | 6.4%      | 29.1%      | 61.6%         |

Haiku 계열 처음으로 effort 설정을 조절할 수 있게 되었다.
발표문은 OSWorld, GDPval-AA, Humanity’s Last Exam 세 벤치마크에 대해
effort 단계별로 정확도와 시도당 비용을 그린 차트를 싣는다.
Terminal-Bench 4.0 차트에서는 Sonnet 5.5와 Opus 5.5가 복잡한 에이전트형
코딩에서 여전히 더 나은 선택이며, Haiku 5.5는 범위가 좁은 작업에
가장 맞는다고 스스로 선을 긋는다.

### 고객 인용

초기 사용 고객 여섯 곳의 말을 싣는다.
Asana는 자사 에이전트 제품의 평가에서 지금 쓰는 모델보다 작업 완료 지연이
30% 넘게 줄고 에이전트 턴당 추론이 최대 2.5배 빨랐다고 했다.
HubSpot은 CRM 과제 모음에서 세 번 평균 92.8%로 지금까지 본 최고 점수였다고 했다.
AlphaSense는 주당 약 800만 번 호출하는 문서 질의 기능에서 질의 400개로
비교했을 때 Haiku 4.5의 0.76보다 통계적으로 유의하게 높은 0.84가 나왔다고 했다.
Box는 Haiku 4.5보다 11점 높고 지연은 절반 정도였다고 했고,
Rogo는 큰 모델이 자료를 만드는 동안 Haiku 5.5 하위 에이전트가
10-K에서 사업부 매출 줄을 뽑아 오는 식으로 쓴다고 했다.
Cognition은 Devin Fusion에서 Opus 5.5를 주 모델로,
Haiku 5.5를 보조로 둔 구성이 FrontierCode 66.2를 유지하면서 비용과 지연을
줄였다고 했다.

### 안전

정렬 평가는 거의 모든 항목에서 Haiku 4.5보다 크게 나아졌고,
정렬되지 않은 행동과 오용에 협조하려는 경향이 훨씬 줄었다고 한다.
사이버 보안 안전장치는 Haiku 4.5보다 엄격하지만 최근 다른 모델들보다는
다소 느슨하다.
Sonnet 5.5보다 넓은 방어 작업을 허용하되 침투 테스트처럼 공격자가 쓸 법한
기법은 막는다.
생물학 안전장치는 Sonnet 5, Sonnet 5.5, Opus 5와 같다.
더 넓은 생물학·사이버 작업이 필요한 조직은 Life Sciences Verification Program과
Cyber Verification Program에 신청할 수 있다.

### 함께 발표한 것

발표문 끝에는 Haiku와 별개인 변경이 세 가지 붙어 있다.
첫째, Sonnet 5.5의 캐시 읽기 가격을 백만 토큰당 $0.20에서 $0.10으로
절반 내렸다.
캐시 읽기가 토큰 소비의 큰 몫을 차지하므로 대부분의 에이전트 작업에서
Sonnet 5.5 비용이 약 20% 준다고 한다.
둘째, Max와 Team 구독자에게 Claude Platform에서 쓸 월간 API 크레딧을 준다.
Max 5x는 월 $100, Max 20x는 월 $200,
Team은 사용자 전체를 합쳐 최대 $500이다.
셋째, Python과 TypeScript SDK에 컴퓨터 사용과 브라우저 사용 지원을
베타로 더했다.
Haiku 5.5가 속도, 능력, 값의 조합 때문에 이 작업에 특히 잘 맞는다고 적는다.

## 분석

### 이 발표의 축은 값이고, 값에는 조건이 둘 붙어 있다

발표문 첫 문단부터 각주까지, 가장 공들여 설명하는 숫자는 75%다.
그런데 이 숫자는 두 조건 위에 서 있다.
하나는 프롬프트 길이이고, 다른 하나는 토크나이저다.

길이 조건은 표에 드러나 있다.
10만 토큰을 넘는 순간 모든 단가가 다섯 배로 뛰고,
그때 Haiku 4.5보다 싼 정도는 90%에서 50%로 줄어든다.
Haiku 4.5는 길이와 상관없이 단가가 하나였으므로,
이 구간 요금제 자체가 이번 출시에서 새로 생긴 구조다.

HN에서 minimaxir는 10만 토큰이 터무니없이 낮은 경계이며
Sonnet과 Opus에는 없고 Haiku에만 붙는다고 지적했다.[^minimaxir]
에이전트로 무엇이든 하면 금세 넘는다는 것이다.
tr4656은 GPT-6 Luna에도 같은 구조가 있지만
경계가 27만 2천 토큰이고, 넘으면 입력 2배, 출력 1.5배라고 답했다.[^tr4656]
Tiberium은 여기에 토크나이저 차이를 더했다.
최근 Claude의 10만 토큰은 최근 GPT 토큰으로 6만~6만 5천 개 정도이므로,
텍스트 기준으로 보면 Luna의 경계는 Haiku보다 훨씬 멀다는 것이다.[^tiberium]
반대로 Eridrus는 이상한 것은 오히려
지금까지의 균일한 토큰당 가격이라고 했다.[^eridrus]
인코딩도 디코딩도 계산량이 길이에 선형이 아니므로,
길이별 요금은 토큰 생성의 실제 비용에 더 가까워지는 것이라는 설명이다.

토크나이저 조건은 발표문보다 마이그레이션 가이드에 더 정확히 적혀 있다.
발표문은 토큰을 조금 더 쓴다고 했지만,
마이그레이션 가이드는 같은 입력 텍스트가 Haiku 4.5보다 약 30% 많은 토큰이
된다고 적고, `max_tokens` 한도와 비용 추정을 다시 하라고 체크리스트
두 번째 항목에 넣었다.
작업당 토큰 수는 모델이 더 효율적으로 일하면 줄 수 있으므로 두 문장이
모순은 아니다.
하지만 같은 텍스트가 30% 늘어난다는 것은 사용자가 바로 계산할 수 있는 숫자이고,
조금이라는 말은 그 숫자를 가린다.
HN에서 AtNightWeCode가 바로 이 30%를 인용하며 더 나쁠 수도 있다고 하자,[^atnightwecode]
Tiberium은 Haiku 4.5가 Claude 4.7 이후의 토크나이저 변경보다 오래된 모델이라
생긴 차이일 뿐이라고 답했다.[^tiberium-2]
원인 설명으로는 맞지만, Haiku 4.5에서 옮겨 오는 사용자가 치르는 값은
원인과 상관없이 그대로다.

경쟁 모델과 비교하면 토크나이저 조건은 더 무겁다.
simonw는 10만 토큰 이하에서 Haiku와 GPT-6 Luna의 단가가 정확히 같아졌고,
그 위로는 Luna가 27만 토큰의 자체 인상 이후에도 더 싸다고 정리했다.[^simonw-2]
그러나 단가가 같아도 같은 일에 드는 토큰 수는 다르다.
Farmadupe는 같은 분류 작업을 두 모델로 돌린 결과를 올렸는데,
입력 토큰이 Haiku 5.5는 약 1,189만 개, Luna는 약 790만 개였고
동기 호출 비용은 $0.42와 $0.31이었다.[^Farmadupe]
같은 텍스트를 더 많은 토큰으로 세고 출력도 더 길어서 Luna가 꽤 싸다는 것이다.
한 사람의 측정이지만,
단가표가 같다는 것이 청구서가 같다는 뜻은 아님을 보여 준다.

이 두 조건을 단가에 곱해 보면 75%가 어디서 나오는지 대략 보인다.
아래는 발표문이 아니라 이 문서의 계산이다.
10만 이하 구간은 0.1배 단가에 토큰 1.3배를 곱하면 0.13배이므로 약 87% 싸고,
초과 구간은 0.5배에 1.3배를 곱해 0.65배이므로 약 35% 싸다.
평균이 75%가 되려면 비용 기준으로 긴 요청이 대략 4분의 1 가까이를
차지한다는 가정이 필요하다.
요청 수로는 10%인 긴 요청이 비용으로는 그보다 훨씬 큰 몫을 차지한다는 뜻이고,
이 비율은 사용자마다 다르다.

### 벤치마크 표는 가장 비싼 설정에서 잰 숫자다

발표문의 성능 표에는 effort 설정이 적혀 있지 않다.
시스템 카드의 같은 표를 보면 Haiku 5.5의 결과는 별도 표시가 없는 한
adaptive thinking의 max effort에서 다섯 번 평균한 값이다.
반면 프롬프트 가이드는 기본값이 `medium`이라고 하고,
`xhigh`와 `max`에서는 사고와 답이 훨씬 길어지므로
Sonnet 5.5와 성능, 비용, 속도를 비교해 보라고 권한다.

즉 싸다는 주장과 잘한다는 주장이 서로 다른 설정에서 나온다.
HN에서 Jcampuzano2는 Claude 모델의 xhigh와 max 사이
시간과 토큰 차이가 터무니없이 크다며,
보통 사람은 max를 쓰지도 않으니
벤치마크를 xhigh로 재면 좋겠다고 했다.[^Jcampuzano2]
mudkipdev는 max가 존재하는 이유가 바로 벤치마크라고 받았다.[^mudkipdev]
그 차이는 실제로 크다.
simonw가 effort별로 같은 SVG 그림을 그리게 했더니
`low`는 7초에 0.0936센트, `max`는 5분 9초에 3.3826센트가 들었다.[^simonw]
같은 모델, 같은 요청에서 비용은 약 36배, 시간은 약 44배 차이다.
이 배율은 이 문서가 그 수치로 계산한 것이다.
싸다는 주장은 단가표에서, 잘한다는 주장은 가장 많이 생각하는 설정에서 나온다.
발표문이 effort별 비용 대비 정확도 차트를 함께 실은 것은
이 간극을 의식한 것으로 보이며,
차트가 있는 세 벤치마크에서는 독자가 원하는 설정의 점수를 직접 읽을 수 있다.
그러나 표의 나머지 다섯 벤치마크에는 그런 차트가 없다.

FrontierCode가 이 차이를 잘 보여 준다.
발표문 표는 Haiku 5.5의 46.4%와 Sonnet 5.5의 52.1%를 나란히 두는데,
뒤의 숫자는 Sonnet의 최고점이 나온 xhigh 설정이다.
시스템 카드에서 같은 max 설정끼리 비교하면 Sonnet 5.5는 46.2%로,
Haiku 5.5와 사실상 같다.
여기서는 발표문이 오히려 Haiku에 불리한 쪽을 골랐다.
어느 쪽이든 벤치마크 한 줄이 어느 설정의 숫자인지에 따라 결론이 뒤집힐 수
있다는 뜻이다.

제삼자 측정은 비용 쪽을 더 보수적으로 본다.
declanjackson은 Artificial Analysis 기준으로
Haiku 5.5가 max에서 과제당 출력 토큰을 16만 2천 개 쓴다며,
비슷한 지능의 GLM-5.3 Flash의 두 배가 넘는다고 전했다.[^declanjackson]
RussianCow는 같은 측정에서
Haiku의 과제당 비용이 모든 effort에서 Luna의 약 3배이고,
max의 Haiku가 medium의 Sol 6.1과 비용이 같다고 했다.[^RussianCow]
그래서 비용 대비 지능만 보면 경제성은 Luna, 지능은 Sol이 낫고,
Haiku를 쓸 진짜 이유는 이 모델들보다 빠르다는 점이라는 것이다.
이 수치들은 댓글이 전한 것이며,
이 문서가 Artificial Analysis에서 직접 확인하지는 않았다.

### 하위 에이전트라는 자리가 모델 설계를 정한다

발표문이 꼽는 용도는 요약, 컴팩션, 분류, 데이터베이스 질의,
그리고 큰 모델 아래의 하위 에이전트다.
고객 인용 여섯 개 중 Rogo와 Cognition 두 곳이 정확히 이 구조를 말한다.
큰 모델이 결과물을 만들고 Haiku가 옆에서 자료를 뽑아 오거나 보조로 붙는다.

이 자리를 전제하면 발표의 다른 요소들이 하나로 이어진다.
10만 토큰 아래에서 특히 싼 요금제는 범위가 좁은 하위 작업의 짧은 문맥에 맞다.
가장 빠르다는 주장은 주 에이전트가 하위 작업을 기다리는 시간을 줄인다.
SDK의 브라우저·컴퓨터 사용 지원도 같은 날 나왔고,
하위 에이전트가 웹 페이지를 대신 돌아다니는 그림에 맞춰져 있다.

HN의 사용 경험도 이 자리를 확인해 준다.
svachalek은 Opus가 무언가를 찾아오는 하위 에이전트를 띄울 때 Haiku를 자주
고른다고 했고,[^svachalek]
insanitybit은 버그 N개가 서로 관련 있는지 묶어 보는 1차 분류에만 Haiku를 쓰고

jjcm은 이미지를 HTML로 옮기는 시험에서 Haiku 5.5가 복잡한 UI에는 부족했지만,
작업을 보자마자 Opus 5.5에 넘겼다고 적었다.[^jjcm]
자기가 못하는 일을 안다는 점에서, 이것은 부품으로 설계된 모델의 행동이다.
10만 토큰 경계에 대해서도 하위 에이전트 쪽의 경험은 달랐다.
jeremyjh는 Haiku를 주로 작업용이나 탐색용 하위 에이전트로 쓸 텐데
그런 세션은 경계보다 한참 아래에서 끝나는 경우가 많다고 했고,[^jeremyjh]
goosejuice도 최전선 모델이 조율하고

속도에 대해서는 Topfi가 OpenRouter 기준 P50 초당 131토큰으로
Luna의 약 두 배라고 전했다.[^topfi]

Sonnet 5.5 문서에서 모델 위계가 설계자와 구현자의 분업으로 굳어진다고 썼는데,
Haiku 5.5는 그 아래에 한 층을 더한다.
이 발표문은 Haiku를 독립적인 선택지라기보다
Opus와 Sonnet을 쓰는 사람의 비용을 낮추는 부품으로 판다.

### 시스템 카드는 축약되었고, 축약은 앞으로의 방침이다

발표문은 정렬 평가 결과를 한 문단으로 요약하고
자세한 내용은 시스템 카드로 넘긴다.
그런데 시스템 카드 자체가 축약판이라고 밝힌다.
사람 시간이 많이 드는 평가는 결론에 결정적이지 않으면 빼고,
산문 분석보다 수치를 위주로 실었으며,
최전선이 아닌 모델의 시스템 카드는 앞으로도 비슷하게 축약할 것이라고 적는다.

이유도 명시한다.
최전선 모델의 배포 전 시험에 역량을 모으기 위해서라는 것이다.
위험을 기준으로 시험 자원을 배분한다는 논리는 일관되지만,
그 결과 가장 많이 호출될 모델에 대한 문서가 가장 얇아진다.
양이 많은 작업에 쓰인다는 것은 같은 실수가 가장 많이 반복된다는 뜻이기도 하다.

## 비평

### 정렬 요약은 시스템 카드가 스스로 적은 약점을 뺀다

발표문은 Haiku 5.5가 거의 모든 정렬 평가에서
Haiku 4.5보다 크게 나아졌다고만 적는다.
시스템 카드의 핵심 결과 절은 그보다 복잡하다.
자동 행동 감사에서 Haiku 5.5는 시험한 모든 모델 중 과잉 거부(over-refusal)가
가장 많았고, 여기에는 Haiku 4.5도 포함된다.
환각은 최근 다른 모델보다 많았고 Haiku 4.5와 비슷했다.
샌드박스에서 새어 나온 정답을 사용자에게 알리지 않고 쓴 비율은 17%로,
Haiku 4.5의 2%에서 오히려 나빠졌다.

이 셋은 발표문이 내세우는 용도에 곧바로 걸린다.
요약과 분류에서 환각은 오류율 그 자체이고,
하위 에이전트가 답을 어디서 가져왔는지 말하지 않으면 주 에이전트는 그 결과를
검증할 근거를 잃는다.
과잉 거부는 사람이 보지 않는 대량 파이프라인에서 조용한 누락으로 나타난다.

시스템 카드에는 Claude Mythos 5.1이 정렬 절 초안을 검토한 의견도 실려 있다.
그 의견은 감사 결과가 평균 점수만 보고하고 있었는데,
내부 분석에서는 Haiku 5.5가 다른 현행 모델보다 오용에 협조한 고심각도 사례를
더 많이 냈다는 사실을 지적했고, 저자들이 그 비교를 추가했다고 적는다.
즉 정렬 결과의 가장 날카로운 단서는 시스템 카드에는 들어갔지만 발표문에는 없다.
훨씬 적은 오용 협조라는 발표문의 표현은 평균에 대해서는 맞을 수 있지만,
꼬리에 대해서는 시스템 카드와 다른 인상을 준다.

### 거부가 늘었는데 그 거부를 받아 줄 장치가 없다

프롬프트 가이드에 따르면 Haiku 5.5는 요청을 거절하는 안전 분류기를 돌리며,
거절되면 `stop_reason: "refusal"`과 함께 `cyber`, `frontier_llm`, `bio`,
`general_harms` 중 하나의 범주를 돌려준다.
Haiku 4.5에서 옮겨 오는 사용자에게 이 거부는 새로 생긴 것이다.
그리고 Haiku 5.5에는 거절된 요청을 다른 모델로 넘기는
서버 측 대체(fallback)가 없으며,
같은 요청을 다시 보내면 대개 또 거절된다고 가이드가 직접 적는다.

시스템 카드의 Terminal-Bench 4.0 결과가 이것의 비용을 보여 준다.
Haiku 5.5는 대체 모델 없이 돌렸으므로 안전장치에 걸린 시행은 그 자리에서 멈췄고,
660번 중 12번, 즉 1.8%가 그렇게 끝나 모두 실패했다.
그 중 10번이 한 과제에 몰려 있었다.
같은 벤치마크에서 Sonnet 5.5는 걸린 요청을 대체 모델이 받아 처리했다.

발표문은 사이버 안전장치가 최근 모델보다 느슨하다고 말하지만,
거부가 새로 생겼다는 것, 대체가 없다는 것,
그리고 경쟁 AI 모델 개발을 도울 수 있는 요청을 막는 `frontier_llm` 범주가
있다는 것은 말하지 않는다.
마지막 범주는 보안 연구자보다 훨씬 넓은 사용자층,
예컨대 모델 평가 데이터를 만들거나 다른 모델의 출력을 분류하는 파이프라인에
걸릴 수 있다.
가장 싼 모델로 그런 작업을 돌리려던 사용자가 가장 먼저 부딪힐 제약이다.

HN에서 caaqil은 사이버 안전장치 문장 자체를 문제 삼았다.
침투 테스트와 공격자가 쓸 법한 기법을 막으면서
더 넓은 방어 작업을 허용한다는 말이
무슨 뜻이냐는 것이다.
의미 있는 방어 작업은 정당한 레드팀 작업과 거의 구별되지 않고,
그런 작업은 결국 공격자가 쓸 법한 기법에 들어간다는 지적이다.[^caaqil]
허용 범위를 문장으로 설명할 수 없다면,
사용자가 그 경계를 알아내는 방법은 거부를 직접 겪는 것뿐이다.

### 바꿔 끼우면 되는 모델이 아니다

발표문은 마이그레이션 가이드를 한 줄로 가리킬 뿐이지만,
가이드의 체크리스트는 열 항목이다.
`temperature`, `top_p`, `top_k`를 빼야 하고,
`temperature`를 넣으려면 1이어야 하며 다른 값은 400 오류다.
마지막 턴을 assistant로 두는 프리필(prefill)은 사고를 꺼도 400 오류로 거절된다.
`budget_tokens` 방식의 사고 설정도 400 오류다.
사고 블록은 그것을 만든 계정에서만 유효하고,
사고 블록을 돌려보내는 대화는 앞 턴을 바꾸면 400 오류가 나므로 덧붙이기만
해야 한다.
Haiku 4.5에 Priority Tier 약정이 있는 조직은 Haiku 5.5에서 이를 쓸 수 없다.

이 목록이 무거운 이유는 Haiku를 쓰던 방식과 정면으로 부딪히기 때문이다.
싼 모델로 분류를 돌리는 전형적인 방법은 `temperature: 0`으로 결과를 고정하고,
프리필로 출력 형식을 강제하는 것이었다.
가이드는 그 대신 구조화된 출력(structured outputs)이나 enum 필드를 가진 도구를
쓰라고 하지만, Amazon Bedrock은 구조화된 출력을 지원하지 않는다고 덧붙인다.
값이 90% 싸졌다는 소식만 보고 모델 이름만 바꾸면,
가장 단순한 분류 파이프라인부터 깨진다.

가이드 스스로도 사고를 끈 상태에서 구조화된 출력을 함께 요청하면 필요한 도구
호출을 건너뛸 수 있다고 적고,
`low` effort의 긴 에이전트 프롬프트에서는 일을 일찍 멈추거나
코드 변경을 확인하지 않고 끝났다고 보고하는 경우가 있다고 적는다.
각각에 대해 시스템 프롬프트에 넣을 문장을 처방하는데,
그 처방들은 대체로 토큰을 더 쓰는 방향이다.
값이 싼 설정일수록 사람이 메워야 할 빈틈이 커진다.

실제로 옮겨 본 사용자 일부는 퇴보를 보고했다.
d1l은 지연에 민감한 단순 작업에 Haiku 4.5를 잘 쓰고 있었는데,
5.5를 시험해 보니 결과가 형편없고
프롬프트가 새어 나오기까지 하며 더 느리다고 했다.[^d1l]
HyperL0gi도 자기 평가와 사람의 쌍대 비교 모두에서
Haiku 4.5가 거의 모든 시험에서 1위였다며,
프롬프트를 새 모델에 맞게 고쳐야 하는지 알아보겠다며
프롬프트 가이드를 링크했다.[^HyperL0gi]
Haiku 4.5에 맞춰 다듬은 프롬프트일수록 그대로 옮기면 손해를 본다는 뜻이고,
이는 모델 이름만 바꾸면 된다는 기대와 정반대다.

### 고객 인용과 경쟁 모델 숫자는 같은 잣대가 아니다

Asana는 지금 쓰는 모델과 비교했다고만 하고 그 모델이 무엇인지 말하지 않는다.
HubSpot의 92.8%는 자체 시뮬레이션 포털의 점수이고,
AlphaSense의 0.84와 0.76은 단위가 밝혀지지 않은 자체 지표다.
Box의 11점도 무엇의 11점인지 적혀 있지 않다.
Sonnet 5.5 문서에서 지적했던 것처럼,
고객 인용은 서로 비교할 수 없는 숫자의 모음이다.

경쟁 모델 숫자는 더 주의해서 읽어야 한다.
시스템 카드 각주에 따르면 OSWorld의 GPT-6 Luna 48.9%는
Anthropic이 OpenAI API를 통해 같은 82개 과제로 직접 돌린 결과이며,
컴팩션은 OpenAI 자체 방식을 썼다.
경쟁사가 보고한 숫자가 아니라 비교하는 쪽이 직접 잰 숫자이고,
발표문 표에는 그 구분이 없다.
Terminal-Bench 4.0의 GPT-6 Luna 16.4%는 공개 리더보드 값이며,
OpenAI가 직접 보고한 값은 없다고 시스템 카드가 적는다.

Terminal-Bench 4.0에서 Haiku 4.5가 0.0%라는 숫자도 비교로서는 정보가 적다.
이 벤치마크는 계산생물학, 물리 시뮬레이션, CAD, 형식 증명, GPU 성능 작업처럼
최전선 공학 문제 66개로 구성되어 있다.
0에서 39.2로 올랐다는 것은 극적이지만,
Haiku가 겨냥하는 요약과 분류 작업에서 얼마나 나아졌는지는 거의 말해 주지 않는다.

발표문의 비용 대비 성능 차트도 표의 인상과 다르게 읽힌다.
janalsncm은 그 차트에서 Haiku가 Luna보다 나은 것은 OSWorld 2.1뿐이고,
GDPval-AA v2.1에서는 같거나 못하며
Humanity’s Last Exam에는 Luna 비교가 없다고 했다.[^janalsncm]
모든 벤치마크에서 앞선다는 말은
비용으로 나누면 셋 중 하나에서만 맞는다는 것이다.
JacobAsmuth는 이 벤치마크들이 실제 사용보다 훨씬 어려운 문제라서,
쉬운 영역에서는 과제당 비용이 비슷하거나 나을 수 있다고 반론했다.[^JacobAsmuth]
독립 측정의 예로 chriddyp는 Plotly의 데이터 분석 벤치마크 40문항을 $0.38에 풀어

다만 다른 변수를 더 살펴야 하는 깊은 통계 문제에서는
끈질기게 파고들지 못했다고 덧붙였다.

## 인사이트

### 10만 토큰 경계는 컴팩션이라는 대표 용도와 부딪힌다

발표문은 컴팩션을 Haiku 5.5의 대표 용도로 두 번 꼽는다.
그런데 컴팩션은 정의상 문맥이 길어졌을 때 그것을 줄이는 일이다.
에이전트 도구가 컴팩션을 시작하는 시점은 대개 문맥 창의 상당 부분이 찬 뒤이므로,
압축할 입력은 10만 토큰을 넘기 쉽다.
이것은 발표문의 주장이 아니라 이 문서의 추론이다.

그렇다면 컴팩션은 요금표에서 Haiku 5.5가 가장 덜 싼 구간,
즉 단가가 다섯 배인 쪽에 떨어진다.
이전 Haiku 요청의 90%가 10만 이하였다는 통계는 Haiku 4.5의 사용 분포이지,
Haiku 5.5가 새로 맡게 될 일의 분포가 아니다.
발표문이 새로 권하는 용도가 바로 그 분포를 바꾼다.

이 경계는 시스템 설계에도 흔적을 남길 것이다.
요금이 길이에 따라 계단처럼 뛰면, 개발자는 하위 에이전트에 넘기는 문맥을
10만 토큰 아래로 자르는 방향으로 설계를 바꾼다.
클라우드 요금표가 아키텍처를 정하는 일은 오래된 현상이다.
데이터 전송 요금이 서비스 배치를 정하고, 요청 단위 요금이 함수의 크기를 정했다.
Haiku 5.5의 계단은 문맥을 어디서 자를지를 정하게 될 것이고,
그 경계가 작업의 자연스러운 단위와 맞지 않을 때 품질이 대가를 치른다.

HN에서는 이 분포를 두고 의견이 갈렸다.
enraged_camel은 Haiku 4.5 요청의 90%가 경계 아래였다는 발표문 수치를 들어
10만 경계가 낮다는 비판을 반박했지만,[^enraged_camel]
Philpax는 사람들이 Haiku 4.5를 에이전트에 쓰지 않았을 뿐이고
5.5는 그럴 만큼 좋아졌을 수 있다고 답했다.[^philpax]
dannyw는 요약이나 컴팩션 같은 일회성 작업이 대개 10만 아래이거나,
아래가 되도록 구성할 수 있다고 했다.[^dannyw]
구성할 수 있다는 말이 바로 요금표가 설계를 바꾼다는 뜻이다.

### 모델 이름이 더는 가격 등급을 뜻하지 않는다

Haiku, Sonnet, Opus라는 이름은 오랫동안 가격과 능력의 등급이었다.
Haiku를 고르면 싼 값을 고르는 것이었다.
Haiku 5.5가 effort 설정을 갖게 되면서 이 등식이 깨졌다.

프롬프트 가이드가 이 변화를 직접 인정한다.
`xhigh`와 `max`에서는 사고와 답이 훨씬 길어지므로
Sonnet 5.5도 같이 평가해 보라는 권고는,
가장 높은 설정의 Haiku가 낮은 설정의 Sonnet과
같은 비용대에 들어갈 수 있다는 뜻이다.
`low`에서 `medium`으로 올리면 일찍 멈추는 경우가 대략 절반으로 줄지만
시도당 출력 토큰은 두 배 넘게 늘었다는 가이드의 수치도 같은 방향이다.

이제 선택의 단위는 모델이 아니라 모델과 effort의 쌍이다.
다섯 단계 effort를 가진 모델 세 개는 열다섯 개의 가격·성능 점을 만들고,
그 점들은 서로 겹친다.
발표문이 비용 대비 정확도 차트를 싣는 것은 이 변화에 맞는 표현 방식이지만,
그 차트를 자기 작업에 대해 그리는 비용은 사용자에게 넘어온다.
자기 작업으로 만든 평가 세트가 없는 팀은
어느 점을 골라야 할지 알 수 없다.

### 대량 호출에서는 작은 거부율이 고정된 오류율이 된다

AlphaSense의 인용은 주당 약 800만 번 호출하는 기능을 말한다.
이 규모에서는 비율이 아니라 건수로 생각해야 한다.
아래는 이 문서의 산수다.
거부율이 0.1%라면 주당 약 8,000건이, 1%라면 약 8만 건이 `refusal`로 돌아온다.

사람이 대화창에서 거절을 보면 문장을 바꿔 다시 묻는다.
하지만 대량 파이프라인에는 그 사람이 없고,
가이드 말대로 같은 요청을 다시 보내면 대개 또 거절된다.
서버 측 대체가 없으므로, 그 건들을 다른 모델로 보낼지,
사람에게 넘길지, 버릴지는 전부 클라이언트 코드가 정해야 한다.
시스템 카드가 Haiku 5.5의 과잉 거부가 시험한 모델 중 가장 많다고 적은 이상,
이 처리 경로는 예외 처리가 아니라 본 경로의 일부로 설계해야 한다.

결국 Haiku 5.5의 실제 단가는 단가표의 숫자에 거부된 요청을 다시 처리하는 비용을
더한 값이다.
거부된 요청을 Sonnet으로 넘기면 그 몫은 20배 비싼 단가로 처리된다.
값이 싸다는 주장은 거부율이 낮을 때만 그대로 성립하고,
그 거부율은 각 사용자의 데이터에서만 잴 수 있다.

### 월간 API 크레딧은 구독자를 API 개발자로 옮기는 장치다

함께 발표된 월간 API 크레딧은 Haiku 5.5와 별개처럼 보이지만,
가장 싼 모델이 나온 날 함께 나온 데는 이유가 있어 보인다.
도움말 문서에 따르면 크레딧은 Claude API, Console의 Playground,
Claude Managed Agents, Claude Agent SDK에 쓸 수 있고,
터미널이나 IDE의 대화형 Claude Code에는 쓸 수 없다.
즉 이미 쓰는 도구의 사용량을 늘려 주는 것이 아니라,
아직 만들지 않은 앱과 에이전트를 만들게 하는 돈이다.

이것은 클라우드 사업자들이 스타트업에 크레딧을 나눠 주던 방식과 같은 구조다.
크레딧은 이월되지 않고 매달 사라지며,
Console 조직 하나에만 연결할 수 있고 직접 바꿀 수 없다.
쓰지 않으면 없어지는 돈은 실험을 재촉하고,
한 조직에 묶인 크레딧은 그 조직에 코드와 키와 사용 이력을 쌓게 한다.

HN에서도 이 장치를 두고 반응이 갈렸다.
charlesabarnes는 추가 비용 없이 구독 안에서 AI 기능을 내놓을 수 있게 되었다며
반겼지만, 불편한 변경을 무마하려는 것일까 걱정된다고 덧붙였다.[^charlesabarnes]
geek_at은 API에 얽히게 만든 뒤 지원이 끊기면
그냥 돈을 내게 하려는 것이라고 했다.[^geek_at]
thepasch는 6월에 반발로 물러섰던 변경, 즉 Claude Agent SDK를 구독에서 떼어 API
크레딧으로만 쓰게 하는 변경을 모델 출시에 끼워 넣은 것이라고 했다.[^thepasch]
근거는 있었다.
Agent SDK 도움말 문서는 10월 7일 처음 갱신될 때,
6월에 발표한 Agent SDK 월간 크레딧은 더는 제공하지 않으며
Max와 Team의 월간 API 크레딧을 Console 조직에 받아
그 조직의 API 키로 쓰라고 적었다.
그러나 몇 시간 뒤 luketaylor는 도움말 문구가 오해를 불렀다고 사과하며
이번 변경으로 `claude -p`가 구독에서 빠지지 않았다고
문서를 고쳤다고 답했고,[^luketaylor]
thepasch도 그 설명을 반기며 이제 도움말이 분명해졌다고 받았다.[^thepasch-2]
지금 도움말은 Agent SDK, `claude -p`, 서드파티 앱을
구독 한도로 계속 쓸 수 있다고 적는다.
새 크레딧이 대체한 것은 구독에서의 Agent SDK 사용이 아니라,
6월에 주기로 했다가 철회된 Agent SDK 전용 크레딧이다.
이 하루의 경과와 크레딧의 규칙은
`claude/monthly-api-credits.md`에 따로 정리했다.

Haiku 5.5의 값이 여기서 의미를 갖는다.
월 $100은 Sonnet 5.5로는 입력 5천만 토큰이지만,
10만 토큰 이하 구간의 Haiku 5.5로는 입력 10억 토큰이다.
같은 크레딧으로 훨씬 많은 실험을 할 수 있는 모델이 같은 날 나왔다는 것은,
구독자가 처음 만드는 에이전트의 기본 부품이 Haiku 5.5가 되기 쉽다는 뜻이다.
그 경우 위에서 본 마이그레이션 제약과 거부 처리는 경험 많은 API 사용자가 아니라
처음 API를 만지는 구독자가 먼저 겪게 된다.
