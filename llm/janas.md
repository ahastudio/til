# Janas: SSD에서 전문가를 읽어 RAM보다 큰 MoE 모델을 돌리는 C 추론 엔진

<https://github.com/prabanta-dev/janas>

HN 토론: <https://news.ycombinator.com/item?id=50063717> (220점, 94개 댓글)

GN 토론: <https://news.hada.io/topic?id=35298>

## 소개

Janas는 C 라이브러리 외에 의존성이 없는 순수 C로 작성된 AI 도구 모음이다.
첫 구성 요소인 Janas-LLM은 전문가 혼합(MoE, Mixture of Experts) 언어 모델을
GPU가 있든 없든 일반 PC에서 실행한다.
가중치는 디스크에 그대로 두고, 토큰마다 필요한 전문가만 NVMe SSD에서 읽으며,
반복해서 쓰이는 전문가는 메모리에 캐시한다.
README가 내세우는 대표 사례는 RAM 32GB 노트북에서
48.4GB짜리 Qwen3-Next-80B-A3B를 돌리는 것이다.

작성자는 Maurizio “camauri” Cammalleri이며,
저장소는 2026년 9월 20일에 만들어졌다.
2026년 10월 15일 기준 스타 408개, 포크 29개이고,
릴리스는 `v2026.10.14`처럼 날짜 형식 태그로 거의 매일 나온다.
라이선스는 GNU GPL 3 이상이다.
변환된 모델 파일(`.jns`)은
Janas가 아니라 원 모델의 파생물이므로 원 모델의 라이선스를 따른다.

README 첫머리의 경고는 분명하다.
이것은 제품이 아니라 실험이며, 공개 API와 명령줄은 예고 없이,
때로는 일주일에 여러 번 바뀐다.
예외는 모델 파일 형식으로,
Hugging Face에 올라간 형식 버전 2의 `.jns` 파일은
이후 모든 버전에서 읽을 수 있다고 약속한다.
개발과 측정은 모두 노트북 한 대에서 이루어졌고,
그 밖의 하드웨어는 검증되지 않았다.

## 동작 방식

### 전문가 스트리밍과 캐시

MoE 모델은 토큰마다 전체 가중치 중 일부 전문가만 계산에 참여시킨다.
Qwen3-Next-80B-A3B라면 파라미터는 800억 개지만
토큰당 활성화되는 것은 약 30억 개다.
Janas-LLM은 이 성질을 이용해 모델 전체를 메모리에 올리지 않는다.
모델을 열 때 비어 있는 메모리를 전문가 캐시로 채우고,
캐시에 없는 전문가는 `O_DIRECT`로 SSD에서 최대 속도로 읽는다.
대표 측정에서는 약 19GB의 전문가 캐시를 쓰고 나머지를 디스크에서 읽었다.

### 측정으로 정하는 실행 구성

스레드 구성은 고정값이 아니라 엔진이 실측해서 고른다.
프롬프트 처리, 단일 토큰 생성,
여러 토큰 동시 처리 같은 패스 종류마다 처음 몇 번은 모든 코어,
성능 코어당 스레드 하나, 성능 코어의 전체 스레드를 시험해 가장 빠른 것을 남긴다.
이후에도 가끔 다른 구성을 다시 시험해서,
기계가 달아오르며 판정이 바뀌는 경우를 반영한다.
README에 따르면 i9-14900HX에서는 모든 스레드를 쓴 구성이
성능 코어 16개 스레드보다 절반 이하 속도로 응답했다.
측정 결과는 `~/.cache/janas`에 저장되며,
엔진이 쓰는 곳은 여기와 사용자가 지정한 변환 모델 경로뿐이다.

### 초안 생성

`--mtp`로 켜는 초안 생성은 다음 토큰들을 미리 추측하고 모델이 검증하는 방식이다.
Qwen3.5, Qwen3.6, Qwen3-Next는 모델 자체의 예측 블록을,
Gemma 4는 별도의 작은 보조 모델을 초안으로 쓴다.
같은 텍스트를 더 빠르게 내는 것이 목적이며,
효과는 생성하는 텍스트에 따라 크게 달라진다.
영어 질문에서는 Qwen 모델과 Gemma의 큰 두 모델에서 초안이 74~89% 채택됐지만,
이탈리아어 산문에서 Qwen3.5-2B는 약 3분의 1만 채택되어 이득이 거의 없었다.

README는 이 열의 수치가 2026년 9월 26일까지 잘못되어 있었다고 스스로 밝힌다.
같은 문단이 반복되는 텍스트를 이어 쓰게 해서 측정했기 때문에,
초안이 거의 매번 맞아 Qwen3.5-2B가 107토큰/초로 나왔다.

## 성능

측정 기계는 Debian 13,
Intel Core Ultra 9 185H(성능 코어 6개, 효율 코어 8개, 저전력 코어 2개),
내장 Arc GPU, DDR5 32GB, 읽기 약 5.7GB/초의 1TB NVMe SSD다.
llama.cpp와의 비교는 2026년 10월 9~12일에 `llama-bench -p 1024 -n 16`과
`janas-bench --prompt 1024 --gen 16`으로 측정했으며,
생성 열은 양쪽 모두 초안 없이 잰 값이다.

| 모델                        | 프롬프트 Janas | 프롬프트 llama.cpp | 생성 Janas | 생성 llama.cpp |
| --------------------------- | -------------- | ------------------ | ---------- | -------------- |
| Qwen3-Next-80B-A3B (48.4GB) | 62             | 16                 | 24         | 2.8            |
| Qwen3-Coder-Next (48.4GB)   | 66             | 14                 | 22         | 2.2            |
| Qwen3.6-35B-A3B             | 104            | 79                 | 19         | 12             |
| Qwen3-30B-A3B               | 135            | 122                | 32         | 15             |
| Gemma-4-26B-A4B-it          | 84             | 76                 | 18         | 12             |
| Qwen3.8-27B (dense, 17.6GB) | 30.6           | 25.6               | 4.4        | 2.1            |
| Qwen3-4B                    | 193            | 164                | 27         | 18             |

단위는 모두 토큰/초이며, 표는 README의 14개 모델 중 일부다.
README는 비교한 모든 모델에서 Janas-LLM이 더 빨랐다고 적지만,
예외도 하나 밝힌다.
unsloth의 3비트 Qwen3-30B-A3B는 Q3_K 가중치가
아직 GPU의 빠른 프롬프트 경로로 가지 않아
프롬프트 처리에서 llama.cpp(112)보다 느렸다(100).

메모리보다 큰 Qwen3-Next-80B의 비교 조건은 따로 읽어야 한다.
llama.cpp의 일반 빌드는 GPU가 참여하자마자 메모리가 부족해졌다.
CPU 백엔드가 가중치를 재배치(repack)하려고 자체 메모리에 복사하고,
Vulkan 백엔드는 CPU에 남긴 가중치를 시스템이
회수할 수 없는 버퍼에 복사하기 때문이다.
그래서 `GGML_CPU_REPACK=OFF`로 빌드하고 `--no-host 1 -lm mmap`을 줘서
전문가를 파일에 남긴 채 페이지 캐시로 읽게 했다.
반면 Janas-LLM은 별도 옵션 없이 실행했다.
측정 방식도 완전히 같지 않은데,
`llama-bench`는 선행 프롬프트 없이 생성하고
`janas-bench`는 1,024토큰을 읽은 뒤 생성한다.

초안 생성을 켠 채팅에서는 Qwen3-Next-80B-A3B가 37토큰/초,
Qwen3.6-35B-A3B가 34토큰/초를 기록했다.
Windows 11에서도 같은 노트북으로 Linux와 비슷한 생성 속도가 나왔고,
밀집 모델 Qwen3-4B의 프롬프트 처리는
인텔 자체 드라이버 덕에 346토큰/초로 1.8배 빨랐다.

## 사용하기

Linux x86-64(Ubuntu 22.04, Debian 12 이상)에서는
릴리스 파일을 받아 바로 실행한다.

```bash
curl -LO https://github.com/prabanta-dev/janas/releases/latest/download/janas-linux-x86_64.tar.gz
tar xf janas-linux-x86_64.tar.gz && cd janas
./janas-chat   # 아는 모델 목록에서 고르면 내려받고 검증한다
```

Windows 10(1903 이상)과 11에서는 `janas-windows-x86_64.zip`을
풀고 `janas` 폴더에서 `.\janas-chat`을 실행한다.
소스에서 빌드하려면 `build-essential`과, GPU를 쓸 경우 `libvulkan-dev`,
`glslang-tools`, `vulkan-tools`를 설치하고 `./build.sh`를 실행한다.

모델은 `janas-get`으로 Hugging Face의 변환본을 받거나,
GGUF 파일을 `.jns` 형식으로 변환해서 쓴다.
구성 프로그램은 역할별로 나뉜다.

| 프로그램       | 역할                                                              |
| -------------- | ----------------------------------------------------------------- |
| `janas-chat`   | 터미널 채팅, 외부 MCP 서버의 도구 사용                            |
| `janas-server` | OpenAI 호환 HTTP API와 브라우저 채팅 페이지, 에디터 코드 자동완성 |
| `janas-mcp`    | 모델을 Claude Code 같은 MCP 클라이언트에 도구로 제공              |
| `janas-bench`  | 기계 성능 측정과 보고서 작성                                      |

코드 자동완성은 OpenAI의 `/v1/completions`(`suffix` 포함)와
llama.cpp의 `/infill`을 지원해서,
VS Code와 VSCodium의 llama.vscode나 Continue에서 쓸 수 있다.
키 입력마다 보내는 창을 고정해서 바뀐 부분만 다시 읽게 했고,
노트북에서 제안 하나에 1.5~2.2초가 걸린다.
창이 한 줄 밀리면 전체를 다시 읽느라 17초가 걸렸다고 한다.

문제가 생기면 `Ctrl-C`로 응답을 멈추고 `Ctrl-D`로 채팅을 끝낸다.
`--cache <GiB>`는 캐시가 쓰는 메모리에 상한을 두고,
`JANAS_GPU=0`은 GPU를 아예 쓰지 않게 한다.

## 트레이드오프

### 프롬프트 처리 속도는 여전히 병목이다

표의 수치는 로컬 모델로서 인상적이지만, 쓰임새에 따라 의미가 달라진다.
kolinko는 초당 60토큰이 단순 채팅에는 괜찮아도
입력 전처리나 에이전트 작업에는 부족하다고 지적했다.[^kolinko]
에이전트가 쓰는 토큰의 대부분은 문서, 도구 출력, 코드를 읽는 입력이고,
클라우드 모델의 입력 처리 속도는 초당 수천에서 수만 토큰이라
수백 배 차이가 난다는 것이다.[^kolinko-2]
Janas의 프롬프트 처리 62토큰/초로 수만 토큰짜리 컨텍스트를
읽으면 응답 전에 몇 분을 기다려야 한다.
결국 이 엔진이 잘 맞는 자리는 짧은 대화와 코드 자동완성이고,
긴 컨텍스트를 반복해서 읽는 에이전트 루프는 아니다.

### 기계를 독점하는 설계다

README는 엔진이 일부러 기계를 혹사한다고 적는다.
비어 있는 메모리를 전부 전문가 캐시로 채우고 디스크를 최대 속도로 읽기 때문에,
여유가 생각보다 적은 기계에서는 데스크톱이
스왑으로 밀려 느려지거나 멈출 수 있다.
브라우저와 에디터를 열어 둔 채 측정하자 같은 모델이
속도의 약 4분의 3을 유지했고 디스크 대기는 5배 늘었다고 한다.
LeoisNotAI는 RAM에 모델을 올리는 것은 첫 단계일 뿐이고,
그동안 브라우저나 VS Code 같은 기본 작업을
계속할 수 있느냐가 실용적인 질문이라고 했다.[^LeoisNotAI]
`--cache`로 상한을 두면 공존은 가능하지만,
캐시가 작아질수록 SSD 읽기가 늘어 대표 수치에서 멀어진다.

### 대역폭의 물리적 한계는 그대로다

SSD 스트리밍은 DRAM을 플래시로 대신하는 방식이고,
둘의 대역폭 차이는 소프트웨어로 메울 수 없다.
SlavikCA는 PCIe 5.0 x4 연결이 약 16GB/초이고 네 개를 RAID0로 묶어도 64GB/초인데,
RTX 5090의 1,792GB/초보다 100배 느리다고 계산했다.[^SlavikCA]
adrian_b는 4슬롯 M.2 카드 등을 조합하면 일반 메인보드에서도
88GB/초까지 가능하다고 반박했다.[^adrian_b-2]
Janas가 3B 활성 파라미터의 MoE에서 성과를 내는 것도
토큰당 읽어야 할 양이 작기 때문이며,
활성 파라미터가 큰 모델일수록 이 이점은 줄어든다.

### 캐시 전략은 모델마다 다시 풀어야 한다

Espressosaurus는 연구를 대략 살펴본 결과,
어떤 전문가를 붙잡아 둘지 정하는 캐싱 알고리즘이 결정적이면서도 자명하지 않고,
모델과 프롬프트에 따라 달라지며,
아직 풀린 문제가 아니라고 정리했다.[^Espressosaurus]
README가 다른 기계에서는 수치가 달라질 것이라 거듭 말하는 것도 같은 이유다.
캐시 적중률은 모델 크기와 남은 메모리의 비율, 그리고 입력 텍스트에 좌우된다.

## 함정

### 수치는 기계 한 대의 기록이다

README의 모든 수치는 Core Ultra 9 185H 노트북 한 대에서 나왔다.
AVX-VNNI가 없는 CPU, AMD CPU, 외장 GPU,
느린 SSD, 다른 메모리 용량은 시험한 적이 없다.
작성자도 다른 기계에서 돌렸다면 `janas-bench` 보고서를 보내 달라고 요청한다.
첫 실행에서는 캐시가 아직 차지 않아 수치가 더 낮게 나오므로,
측정은 유휴 상태의 기계에서 여러 번 해야 한다.

### llama.cpp가 못 하는 일은 아니다

jdb9001은 몇 주마다 누군가 llama.cpp에 수년 전부터 있던 기능을
다시 발견해 재구현한다고 꼬집었다.[^jdb9001]
hgoel은 범용 프로젝트에 기여하는 것이
자체 엔진을 유지하는 것보다 훨씬 어려워 최적화 도입이 느리고,
llama.cpp가 성능을 따라잡을 즈음엔 그 아키텍처가
이미 최신이 아니라고 답했다.[^hgoel]
adrian_b는 이 엔진이 SSD에서 가중치를 읽을 때 llama.cpp보다 몇 배 빠르고,
하드웨어 한계까지 SSD를 읽는 코드가 llama.cpp에
곧 들어갈 가능성은 낮다고 봤다.[^adrian_b]
llama.cpp도 `mmap`으로 메모리보다 큰 모델을 돌릴 수는 있으므로,
차이는 가능 여부가 아니라 SSD 읽기와 캐시를 얼마나 잘 다루느냐에 있다.
비교 표의 2.8토큰/초도 llama.cpp가 이 상황에 맞게 조정된 결과가 아니라,
메모리 부족을 피하려고 기능을 끈 구성이라는 점을 감안해야 한다.

### 지원 모델이 최신 흐름보다 한발 늦다

비교 대상의 중심은 Qwen3-Next-80B-A3B이며,
같은 분야의 Strata는 Qwen3.8-Flash-Next를 내세운다.
HN에서 왜 Qwen 3.8이 없느냐는 질문에 droidjj는 전체가 바이브 코딩된 티가 나니 에이전트가 학습 데이터에서 아는 모델만 골랐을 것이라고 추측했다.[^droidjj]
추측이긴 하지만,
하루에도 여러 번 바뀌는 API와 함께 보면
장기 의존 대상으로 삼기 전에 유지보수 방식을 확인할 이유는 된다.

### SSD 수명보다 발열을 걱정하라

sheepscreek이 SSD에 무리가 갈까 걱정하자,
unrented7977은 SSD 읽기는 수명을 소모하지 않는다고 답했다.[^unrented7977]
justsomehnguy는 QLC에서는 그렇지 않다고 덧붙였는데,
QLC는 읽기 교란을 막으려고 데이터를 주기적으로
다시 쓰기 때문으로 보인다.[^justsomehnguy]
고속 드라이브를 몇 시간씩 최대 속도로 읽으면
쓰기 마모보다 발열과 스로틀링이 먼저 문제가 된다.

## 기억할 원칙

### 모델 크기보다 토큰당 읽는 양이 실행 가능성을 정한다

Janas가 보여주는 것은 메모리보다 큰 모델도 돌릴 수 있다는 사실이 아니라,
활성 파라미터가 작은 MoE라면 SSD 대역폭으로도 쓸 만한 속도가 나온다는 사실이다.
로컬 모델을 고를 때는 전체 파라미터 수보다 토큰당 활성 파라미터와
캐시 적중률을 먼저 봐야 한다.
같은 80B라도 밀집 모델이었다면 이 방식은 성립하지 않는다.

자신의 수치가 틀렸던 이력까지 공개해서 수치를 검증할 여지를 남긴다.
