# Switchyard: 코드를 바꾸지 않고 LLM 호출을 최적 모델로 라우팅한다

<https://github.com/NVIDIA-NeMo/Switchyard>

## 소개

Switchyard는 LLM 애플리케이션이 여러 모델과 제공자에 트래픽을 라우팅하면서
OpenAI·Anthropic API 호환성을 그대로 유지하게 하는 도구다.
NVIDIA-NeMo가 만든 Rust 프로젝트(Python 바인딩 포함)이며
Apache 2.0 라이선스에 별 3.1천 개를 받았다.
유연한 모델 선택, 벤치마킹, 비용·성능 최적화를 목표로 한다.

핵심 기능은 각 LLM 호출을 어느 모델이 처리할지 고르는 것이다.
프로젝트의 표현으로, 각 LLM 호출을
그 일을 여전히 해낼 수 있는 가장 싼 모델로 고른다,
에이전트 코드를 한 줄도 바꾸지 않고서다.

세 가지 통합 경로를 제공한다.
NeMo Relay 플러그인은 기존 Relay 배포에 `routes.toml`을 로드한다.
임베디드 라이브러리는 자기 게이트웨이에 라우팅을 통합하며
모델 호출·자격 증명·재시도를 사용자가 소유한다.
독립 프록시는 내부 게이트웨이가 없는 에이전트를 위한
OpenAI·Anthropic 호환 서버다.

## 명세

구조적으로 요청은 설정 가능한 구성 요소를 거친다.
LLM 클라이언트(제공자 연결), 타깃(특정 모델),
라우트(둘 사이를 결정하는 라우팅 알고리즘)다.
클라이언트가 라우트로 요청을 보내면 라우트가 타깃을 고르고,
호출 하네스가 선택된 모델에 대해 실행한다.

주요 라우팅 알고리즘은 서로 다른 비용·정확도 트레이드오프를 갖는다.
역량/LLM 분류기는 첫 요청을 LLM이 판정한다(정확도 71.2%, $79.32).
스테이지 라우터는 도구 응답을 패턴 매칭 또는 LLM이 판정한다(72.7%, $68.19).
에스컬레이션은 효율적으로 시작해 응답을 LLM이 문제 여부로 판정한 뒤 격상한다
(75.7%, $85.00).
어드바이저 게이트는 한 모델이 모든 턴을 처리하고
더 강한 어드바이저가 검토해 승인하거나 격상한다.
서브에이전트 인식 라우터는 자식 에이전트에 별도 라우팅 로직을 위임하고,
랜덤 라우터는 균등·가중 무작위 선택을 기준선으로 제공한다.

벤치마크(Terminal-Bench 2.1)에서
Claude Opus 4.8 기준선(정확도 76.0%, $98.06)에 대해
에스컬레이션은 기준선 정확도의 99.6%를 13.3% 낮은 비용에 달성했고,
스테이지 라우팅은 95.7% 정확도를 30.5% 절감으로 달성했다.
핵심 구성 요소로는 커스텀 하네스용 임베디드 라우팅 `switchyard-libsy`(베타),
HTTP 호출·프로토콜 변환 `switchyard-llm-client`(알파),
다른 런타임 안에서 라우트를 돌리는 `switchyard-runner`(알파),
독립 프록시 `switchyard-server`(데모)가 있다.

## 분석

### 이 프로젝트의 전제는 대부분의 호출이 최고 모델을 필요로 하지 않는다는 것이다

Switchyard의 존재 이유는 하나의 관찰에 기댄다.
에이전트가 하는 대부분의 LLM 호출은
가장 비싸고 강한 모델을 필요로 하지 않는다는 것이다.
간단한 도구 응답 판정, 정형화된 변환, 반복적 단계는
훨씬 싼 모델로도 충분하다.
비싼 모델은 어렵고 애매한 소수의 호출에만 있으면 된다.

이 전제가 중요한 이유는 비용 구조를 근본적으로 바꾸기 때문이다.
벤치마크 숫자가 이를 뒷받침한다.
에스컬레이션 라우팅은 Opus 4.8 정확도의 99.6%를 유지하면서
비용을 13.3% 줄였고, 스테이지 라우팅은 정확도를 약간 낮추는 대신
30.5%를 절감했다.
이것은 대부분의 호출을 싼 모델이 처리하고
어려운 소수만 비싼 모델로 격상하면,
정확도를 거의 잃지 않고 비용을 크게 줄일 수 있음을 보인다.

이 접근은 앞선 personal-ai-router의 라우팅과 개념적으로 이어지지만 축이 다르다.
PAIR는 같은 로컬 네트워크의 여러 기기로 요청을 분산해 처리량을 늘렸다.
Switchyard는 여러 모델·제공자로 요청을 분산해 비용을 줄인다.
전자는 하드웨어 병렬화, 후자는 모델 계층화다.
둘 다 라우터라는 같은 은유를 쓰지만,
최적화하는 대상이 처리량이냐 비용이냐로 갈린다.

### API 호환성 유지가 채택의 핵심 열쇠다

Switchyard가 OpenAI·Anthropic API 호환성을 보존한다는 점은
반복 강조된다.
에이전트 코드를 한 줄도 바꾸지 않는다는 약속이 그것이다.
기존 코드가 OpenAI API를 호출하고 있었다면,
그 호출을 Switchyard로 돌리기만 하면 라우팅이 투명하게 끼어든다.

이 투명성이 중요한 이유는 라우팅의 채택 비용을 없애기 때문이다.
모델 선택 최적화의 이론적 이득이 아무리 커도,
그것을 쓰려고 에이전트를 재작성해야 한다면 대부분 도입하지 않는다.
Switchyard는 라우팅을 애플리케이션 바깥의 인프라 계층으로 밀어내
코드 변경 없이 이득만 취하게 한다.
이것은 personal-ai-router가 Ollama 기본 포트를 그대로 쓴 것과 같은 전략,
곧 기존 생태계에 투명하게 스며드는 설계다.

세 가지 통합 경로를 둔 것도 채택 마찰을 낮추려는 설계다.
이미 게이트웨이가 있는 팀은 라이브러리로 임베드하고,
없는 팀은 독립 프록시를 쓰고,
NeMo Relay 사용자는 플러그인을 쓴다.
같은 라우팅 엔진을 조직의 성숙도에 맞춰 여러 형태로 제공하는 것은
인프라 도구의 확산을 위한 현실적 선택이다.

## 비평

### 라우팅 판정 자체의 비용과 오류가 계산에서 빠져 있다

Switchyard의 라우팅 알고리즘 다수는 LLM으로 요청을 판정한다.
역량 분류기는 첫 요청을 LLM이 판정하고,
에스컬레이션은 응답을 LLM이 문제 여부로 판정한다.
그런데 이 판정 자체가 LLM 호출이므로 비용과 지연을 더한다.
벤치마크의 절감 숫자가 이 판정 비용을 순비용에 포함했는지는 불분명하다.

이 공백이 중요한 이유는 절감 효과의 실제 크기를 결정하기 때문이다.
매 요청마다 어느 모델로 보낼지를 또 다른 LLM이 판정한다면,
그 판정 호출이 쌓여 절감분을 잠식할 수 있다.
특히 스테이지 라우팅이 도구 응답을 매번 LLM으로 판정한다면,
호출 수가 두 배가 되는 셈이다.
프로젝트는 패턴 매칭이라는 더 싼 판정 대안을 제시하지만,
패턴 매칭의 정확도가 LLM 판정보다 낮으면
잘못된 라우팅으로 인한 재시도 비용이 발생한다.

더 근본적으로, 라우팅 판정의 오류는 이중 비용을 낳는다.
싼 모델로 잘못 보낸 어려운 요청은 실패하고,
그러면 격상해 비싼 모델로 재실행해야 하므로
싼 호출과 비싼 호출을 모두 지불한다.
정확도 71.2%인 분류기는 약 29%의 요청을 잘못 판정하며,
그 오판의 비용이 벤치마크의 평균 비용에 어떻게 반영되었는지가
프로젝트의 절감 주장을 검증하는 열쇠다.

### 벤치마크 하나로 일반화하기에는 조건 의존성이 크다

프로젝트의 인상적인 숫자는 모두 Terminal-Bench 2.1에서 나왔다.
그러나 라우팅의 이득은 워크로드의 난이도 분포에 강하게 의존한다.
쉬운 요청과 어려운 요청이 잘 섞인 워크로드에서는
계층화가 크게 이득이지만,
모든 요청이 어렵다면 결국 다 비싼 모델로 격상되어 절감이 사라진다.

이 조건 의존성이 중요한 이유는 실제 절감이 크게 달라지기 때문이다.
Terminal-Bench는 터미널 작업 벤치마크로 특정 난이도 분포를 가진다.
법률 문서 분석이나 코드 리뷰처럼
대부분의 호출이 높은 역량을 요구하는 도메인에서는
같은 라우팅이 거의 이득을 내지 못할 수 있다.
하나의 벤치마크 숫자를 모든 워크로드의 기대 절감으로 읽으면
실제 도입 후 실망할 위험이 있다.

또한 벤치마크가 Opus 4.8을 기준선으로 삼고
그 대비 절감을 보고하지만,
어떤 싼 모델들이 격상 대상이었는지,
그 모델 조합이 다른 제공자에서도 재현되는지는 명시되지 않는다.
라우팅의 이득은 사용 가능한 모델 계층의 다양성에 달려 있으며,
그 계층이 얇은 환경에서는 라우팅할 여지 자체가 줄어든다.

## 인사이트

### LLM 인프라의 다음 전장은 모델이 아니라 라우팅이다

Switchyard가 드러내는 가장 이전 가능한 통찰은
LLM 애플리케이션의 경쟁 우위가
어느 모델을 쓰느냐에서 어떻게 여러 모델을 조합하느냐로 옮겨 간다는 점이다.
단일 최고 모델에 모든 것을 맡기는 시대에서,
요청마다 최적 모델을 고르는 오케스트레이션의 시대로 이동한다.

이 이동이 중요한 이유는 비용이 규모의 병목이 되었기 때문이다.
에이전트가 수백 개의 호출을 하는 장기 실행 시대에는
호출당 비용이 전체 경제성을 좌우한다.
long-running-agents 문서가 지적한 비용 한계,
곧 프런티어 모델로 24시간을 돌리면 하루 만에 예산을 태운다는 문제에
Switchyard 같은 라우팅이 직접 답한다.
어려운 호출만 비싼 모델로 보내면 장기 실행의 경제성이 성립한다.

두 번째 차수의 효과는 이것이 모델 제공자의 협상력을 바꾼다는 점이다.
애플리케이션이 API 호환 라우터를 통해 여러 제공자를 투명하게 오간다면,
어느 한 제공자에 대한 종속이 약해진다.
Switchyard가 OpenAI·Anthropic 호환성을 보존하는 것은
바로 이 제공자 중립성을 가능하게 하며,
역설적으로 모델을 상품화(commoditize)하는 압력이 된다.
라우터가 흔해지면 개별 모델은 라우터가 고르는 후보 중 하나가 된다.

### 판정자를 두는 설계가 다시 자기 채점 문제로 돌아온다

Switchyard의 라우팅 알고리즘이 LLM으로 요청과 응답을 판정하는 구조는
앞선 문서들이 반복해 만난 문제와 같은 자리에 선다.
aligned-to-whom은 해킹 불가능한 채점기는 없다고 했고,
behavior-specs는 생성과 평가의 분리를 강조했다.
Switchyard의 판정 LLM도 결국 같은 채점기이며,
그 판정이 틀리면 라우팅 전체가 틀린다.

이 통찰이 새로운 프레임을 주는 이유는
라우팅 품질이 판정 품질에 갇힘을 드러내기 때문이다.
어느 모델이 이 요청을 해낼 수 있는가를 판정하는 것은
그 자체로 어려운 메타 판단이다.
그리고 그 판단을 LLM에 맡기면,
판정 LLM의 역량이 라우팅의 상한이 된다.
약한 판정자가 어려운 요청을 쉽다고 오판하면
싼 모델로 보내 실패하고,
강한 판정자를 쓰면 판정 비용이 커진다.
라우팅은 이 판정 비용과 판정 정확도의 트레이드오프에 갇혀 있다.

세 번째 차수의 효과는 라우팅이 결국 계층 구조를 낳는다는 점이다.
요청을 판정하는 판정자, 그 판정자를 검증하는 어드바이저,
서브에이전트에 위임하는 라우터가 쌓이면,
라우팅 자체가 또 하나의 에이전트 계층이 된다.
Switchyard의 어드바이저 게이트와 서브에이전트 인식 라우터가
이미 그 방향을 가리킨다.
비용을 줄이려는 라우팅이 복잡도를 늘리며,
그 복잡도의 관리가 다음 문제가 된다.
가장 싼 모델로 보내는 최적화가,
그 최적화를 운영하는 새로운 오버헤드를 만든다는 역설이 여기 있다.

### 코드를 바꾸지 않는다는 약속이 인프라의 권력을 재배치한다

Switchyard가 반복하는 약속, 곧 에이전트 코드를 한 줄도 바꾸지 않는다는 것은
단순한 편의 이상의 함의를 가진다.
라우팅이 애플리케이션 코드 바깥의 인프라 계층으로 완전히 빠지면,
모델 선택의 권한이 개발자에서 인프라 운영자로 이동한다.

이 이동이 중요한 이유는 조직 내 의사결정의 위치를 바꾸기 때문이다.
지금까지 어느 모델을 쓸지는 애플리케이션 코드에 하드코딩되었고,
그것을 바꾸려면 개발자가 코드를 고쳐야 했다.
라우팅이 `routes.toml` 같은 설정으로 빠지면,
플랫폼 팀이 코드 배포 없이 모델 정책을 바꿀 수 있다.
비용 절감 목표, 새 모델 도입, 제공자 교체가
애플리케이션 팀의 개입 없이 인프라 계층에서 이루어진다.

이 통찰의 함의는 라우팅이 새로운 통제점(control point)이 된다는 것이다.
personal-ai-router가 네트워크 계층에서 요청을 통제하듯,
Switchyard는 모델 선택 계층에서 정책을 통제한다.
그리고 통제점은 항상 권력의 자리다.

조직의 AI 비용과 품질을 좌우하게 되며,
그 파일을 누가 소유하느냐가
AI 인프라 거버넌스의 핵심 질문으로 떠오른다.
