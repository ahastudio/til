# AesCode: 이미지 생성 모델의 안목을 빌려 인포그래픽을 코드로 그리는 모델

<https://github.com/microsoft/AesCode>

## 소개

AesCode는 Microsoft가 공개한 연구 저장소이자 모델로,
슬라이드, 포스터, 대시보드 같은 정보 밀도 높은 시각물을 HTML과 CSS로 생성한다.
저장소는 2026년 7월에 만들어졌고 MIT 라이선스로 공개되었다.
모델 체크포인트는 Qwen3-VL을 백본으로 한 AesCode-8B와 AesCode-32B 두 가지이며,
체크포인트의 라이선스는 Qwen3-VL을 따른다.
논문은 인용 정보에 심사 중(Under review)으로만 적혀 있다.

### 풀려는 문제

시각물을 코드로 만들면 구조가 남고, 수정할 수 있고, 검증할 수 있다.
문제는 코드 모델이 자신이 고른 레이아웃, 위계, 색이
캔버스 위에서 어떻게 어우러지는지 보지 못한다는 점이다.
요구된 내용은 다 넣었는데 디자인은 낡거나 산만한 결과가 나온다.
이미지 생성 모델은 반대다.
보기 좋은 페이지를 구성하지만 글자, 숫자, 논리 관계를 자주 틀린다.

AesCode는 같은 프롬프트로 생성한 이미지를 코드 모델의 미적 참고 자료로 준다.
내용의 기준은 프롬프트이고,
참고 이미지는 가능한 레이아웃과 스타일 하나를 보여 줄 뿐이다.
저장소는 참고 이미지를 입력에 넣기만 해서는 부족하다고 강조한다.
기성 비전-언어 모델은
이미지 속 잘못된 내용을 베끼거나 레이아웃을 무시하기 때문이다.

### 학습 방법

학습은 세 단계로 설명된다.

1. 목표를 디자인 그래프로 표현한다.
   노드는 텍스트, 차트, 표, 카드, 영역, 이미지 자리이고,
   엣지는 포함, 정렬, 순서, 연결 관계다.
2. 속성마다 맞는 보상으로 보낸다.
   결정적 검증기 여섯 개가 실행 여부, 정확한 텍스트, 캔버스 경계, 표와 차트 데이터,
   의미 단위 레이아웃, 여백을 채점한다.
   나머지 시각 속성은 샘플별 Visual Graph Rubric이 그래프에 묶인 예/아니요 질문으로 평가한다.
3. 보상을 합치기 전에 채널마다 정규화한다.
   GDPO가 롤아웃 그룹 안에서 채널별로 정규화해,
   촘촘한 규칙 보상이 드문 시각 피드백을 덮어 버리지 않게 한다.

Visual Graph Rubric의 질문은 문자열이 무엇을 말하는지,
이미지가 무엇을 그리는지는 묻지 않는다.
그것은 텍스트 채널과 OCR이 이미 채점하고,
참고 이미지 생성기는 같은 자리에 다른 그림을 그려도 되기 때문이다.
질문은 가능하면 요소 하나가 아니라 집합 전체에 대해 묻는다.
요소 하나에 대한 질문은 거의 모든 시도가 통과해 보상에 정보가 없다는 이유다.

학습 데이터는 SFT 시연 3,000개, RL 프롬프트 7,408개, 검증용 300개다.
공개된 실행은 Python 3.10, CUDA 12.6, NVIDIA B200 8장짜리 노드 하나를 썼고,
8B와 32B 체크포인트는 각각 400스텝과 520스텝에서 골랐다.
데이터셋은 공개하지 않고 코드만 공개한다.

### 결과

평가는 인포그래픽 300개에서 한다.
Rule은 텍스트, 경계, 차트 검사의 평균이고,
Visual은 VLM 심사자가 렌더링 이미지만 보고 답하는
체크리스트의 내용, 레이아웃, 스타일 평균이다.
Overall은 둘의 평균이며, 프롬프트마다 세 번 생성한 평균이다.

| 모델            | 참고 이미지 | Rule  | Layout | Style | Visual | Overall |
| --------------- | ----------- | ----- | ------ | ----- | ------ | ------- |
| GPT-5.5         | 없음        | 85.90 | 68.09  | 52.80 | 66.72  | 76.31   |
| GPT-5.5         | 있음        | 85.80 | 89.93  | 57.91 | 76.76  | 81.28   |
| Claude Opus 4.8 | 없음        | 88.04 | 64.88  | 46.72 | 65.53  | 76.78   |
| Claude Opus 4.8 | 있음        | 83.55 | 89.76  | 55.51 | 77.23  | 80.39   |
| Qwen3-VL-32B    | 있음        | 67.19 | 64.59  | 38.43 | 55.02  | 61.10   |
| AesCode-8B      | 있음        | 90.07 | 87.80  | 53.21 | 75.80  | 82.94   |
| AesCode-32B     | 있음        | 94.33 | 90.58  | 55.99 | 77.44  | 85.89   |

저장소가 요약한 주장은 네 가지다.
생성 이미지는 정답이 되지 않고도 디자인을 가르칠 수 있다.
추론 때 참고 이미지를 빼도 AesCode-8B의 Visual은 1.0점만 떨어지지만,
백본은 19.6점 떨어진다.
그래프에 묶인 질문이 전체 인상을 묻는 VLM 채점보다 낫고,
채널별 정규화가 스칼라 GRPO보다 Visual을 5.12점 더 올린다.
AesCode-32B는 GDB/lica, SlidesBench, Design2Code의
14개 지표 모두에서 백본보다 낫다.

### 쓰는 방법

체크포인트를 vLLM으로 띄우고,
프롬프트와 요구 사항 파일, 참고 이미지를 함께 넣는다.

```bash
vllm serve microsoft/AesCode-32B \
  --port 8000 \
  --tensor-parallel-size 4 \
  --limit-mm-per-prompt image=2

python -m inference.generate \
  --provider openai \
  --model microsoft/AesCode-32B \
  --base-url http://127.0.0.1:8000/v1 \
  --spec-file examples/hospital_dashboard/sample.jsonl \
  --image examples/hospital_dashboard/reference.png \
  --out page.html
```

아이디어 한 줄에서 시작하는 `inference.from_idea`도 있다.
이미지 모델이 참고 이미지를 그리고,
비전 모델이 아이디어를 텍스트, 차트, 표 요구 사항이 담긴 프롬프트로 펼친다.
저장소의 실행에는 GPT-Image-2와 GPT-5.5가 쓰였다.
중간에 멈춰 `spec.json`의 문구와 차트 값을 사람이 고친 뒤
 생성을 이어 가게 되어 있다.
“그려진 이미지는 레이아웃을 주고, 사실은 사용자가 준다”는 것이
 이 파이프라인의 분업이다.

## 분석

### 핵심 아이디어는 취향과 사실을 다른 채널로 보내는 것이다

AesCode의 주장은 모델 크기나 데이터 양이 아니라 신호의 분리에 있다.
이미지 생성 모델은 구도와 색에 강하고 사실에 약하다.
코드 모델은 사실을 지키지만 구도를 보지 못한다.
둘을 한 모델에 합치는 대신,
이미지는 “이런 배치도 가능하다”는 힌트로만 쓰고
사실은 프롬프트에서 뽑은 검증 가능한 요구 사항으로 채점한다.

결과표가 이 분리가 왜 필요한지 보여 준다.
Claude Opus 4.8에 참고 이미지를 주면 Layout은 64.88에서 89.76으로 오르지만,
Chart는 87.69에서 73.75로 떨어진다.
참고 이미지 속의 틀린 차트 값을 베낀 것으로 읽힌다.
참고 이미지는 레이아웃에 약이고 데이터에는 독이며,
AesCode는 그 독을 보상 설계로 걸러 내려는 시도다.

### 보상을 쪼개는 일이 곧 디자인 지식을 명세로 바꾸는 일이다

“좋은 디자인”은 하나의 점수로 주기 어렵다.
AesCode는 이를 실행, 텍스트, 경계, 표와 차트, 레이아웃, 여백, 디자인 루브릭의
일곱 채널로 나누고, 각 채널을 따로 정규화한다.
학습 스크립트 `train_gdpo.sh`를 보면 표와 차트 채널의 가중치만 3.0이고
나머지는 1.0이다.
데이터 정확성을 가장 비싸게 치는 설계다.

Visual Graph Rubric은 디자인 감각을 체크리스트로 바꾸는 장치다.
“세 지표 블록이 한 열로 쌓이고 왼쪽 끝이 맞는가”,
“부서 이름이 줄바꿈 없이 한 줄에 들어가는가” 같은 질문은
디자이너가 리뷰에서 지적할 법한 항목을 예/아니요로 굳힌 것이다.
질문을 그래프의 노드에 묶어야
VLM 심사자의 답이 어느 요소의 문제인지 추적할 수 있고,
저장소는 이 귀속 가능성이 전체 인상 채점보다 낫다고 보고한다.

### 참고 이미지는 결국 학습 신호로 흡수된다

추론 때 참고 이미지를 빼도 AesCode-8B는 Visual이 1.0점만 떨어진다.
참고 이미지 없이 프롬프트만 받는 정책도
참고 이미지 기반 보상으로 학습하면 Visual이 25.17에서 69.71로 오른다.
이는 참고 이미지가 실행 시점의 입력이라기보다
학습 시점의 교사로서 더 중요하다는 뜻이다.

실용적으로는 의미가 크다.
배포 때마다 이미지 모델을 한 번 더 부르는 비용과 지연을 없앨 수 있기 때문이다.
이미지 모델의 안목이 코드 모델의 가중치 안으로 증류된 셈이다.

## 비평

### 이름은 미학인데 가장 크게 오른 것은 규칙 점수다

AesCode-32B가 백본보다 가장 크게 앞서는 지점은 Rule이다.
참고 이미지를 받은 Qwen3-VL-32B의 Rule이 67.19인데 AesCode-32B는 94.33이고,
특히 경계 검사(Bound)는 97.27로 모든 비교 모델 가운데 가장 높다.
반면 미학과 가장 가까운 Style에서 AesCode-32B는 55.99로,
참고 이미지를 받은 GPT-5.5의 57.91보다 낮다.
Content도 Claude Opus 4.8이 근소하게 앞선다.

즉 “참고 이미지를 받은 프런티어 모델”과 비교하면
AesCode의 우위는 레이아웃과 데이터 정확성,
캔버스 밖으로 넘치지 않는 규율에서 나오고,
스타일 자체는 아직 따라잡는 쪽이다.
이 결과는 충분히 가치 있지만 저장소 이름과 첫 문장이 주는 인상과는 다르다.
정확히 말하면 AesCode는 미적으로 더 뛰어난 모델이라기보다
프런티어 모델 수준의 시각 품질을 유지하면서 데이터를 틀리지 않는 작은 모델이다.

### 심사자가 비교 대상과 같은 계열이다

평가 문서에 따르면 Visual 점수의 심사자 기본값은 `gpt-5.5`이고,
`from_idea` 실행에서도 참고 이미지와 프롬프트 확장에 GPT 계열을 썼다.
같은 표에서 GPT-5.5는 비교 대상 모델이기도 하다.
심사 모델이 자기 계열의 출력 스타일을 선호하는지,
아니면 그 반대로 다른 계열에 관대한지는 이 표만으로 알 수 없다.

학습 보상과 평가 지표의 형태가 닮았다는 점도 걸린다.
학습의 디자인 보상은 VLM이 그래프에 묶인 예/아니요 질문에 답한 통과율이고,
평가의 Visual도 VLM이 체크리스트 질문에 답한 통과율이다.
평가 체크리스트는 참고 이미지 없이 프롬프트로 만든다는 차이가 있지만,
“VLM이 예/아니요로 답하기 쉬운 페이지”를 만드는 법을 학습했을 가능성은 남는다.
외부 벤치마크 세 곳에서 모두 백본보다 나았다는 보고가 이 우려를 덜어 주지만,
README에는 그 수치가 실려 있지 않아 독자가 크기를 확인할 수 없다.

### 재현의 문턱이 높고 데이터는 닫혀 있다

저장소는 코드만 공개하고 데이터셋은 공개하지 않는다.
평가 300개 샘플도 함께 오지 않으므로,
표의 숫자를 다시 내려면 같은 형식의 데이터를 직접 만들어야 한다.
학습에는 B200 8장 노드, 고정 커밋의 verl과 저장소가 제공하는 패치,
특정 버전의 PaddleOCR, Chromium 시스템 라이브러리,
호스팅된 VLM 엔드포인트가 모두 필요하다.

README는 이 의존성의 위험을 솔직하게 적는다.
Chromium이 뜨지 않으면 모든 페이지가 0점이 되고,
PaddleOCR이 없으면 레이아웃 채널이 기권하지 않고
0을 돌려 보상을 조용히 오염시킨다.
그런데 같은 종류의 조용한 실패가 보상 코드에도 있다.
`rl_verl/rewards.py`는 검증기를 불러오지 못하거나 실행 중 예외가 나면
디버그 수준의 로그만 남기고 `_html_quality`라는 휴리스틱 점수로 대체한다.
이 휴리스틱은 `<html>`, `<head>`, `<body>` 태그의 존재와
CSS 속성 개수 같은 것으로 점수를 매기므로,
검증기가 깨진 환경에서는 그럴듯한 HTML이면 높은 보상을 받는다.
재현하려는 사람은
학습 초반에 채널별 점수가 실제 검증기에서 나오는지 먼저 확인해야 한다.

### 고정 캔버스는 편집 가능한 코드의 장점을 절반만 쓴다

AesCode가 만드는 HTML은 포스터처럼 고정된 크기의 캔버스다.
평가 문서도 캔버스 밖으로 나간 내용은 잃은 것으로 친다고 명시한다.
경계 검사가 97점이라는 것은 이 고정 캔버스 안에 정확히 들어간다는 뜻이다.

코드로 생성하는 이유로 저장소가 든 것은 구조, 편집 가능성, 검증 가능성이다.
그런데 웹 코드의 가장 큰 장점인 반응형, 즉 화면 크기에 맞춰 다시 흐르는 성질은
이 설정에서 오히려 감점 요인이 될 수 있다.
결과물은 텍스트를 고칠 수 있는 이미지에 가깝고,
대시보드처럼 데이터가 바뀌거나 여러 기기에서 보는 산출물로 옮기려면
 별도의 작업이 필요하다.

## 인사이트

### 생성 모델은 정답 공급자에서 취향 공급자로 역할이 바뀐다

AesCode가 보여 주는 가장 중요한 변화는 생성 모델의 쓰임새다.
지금까지 합성 데이터는 대개 정답을 대신하는 용도였다.
더 큰 모델이 만든 출력을 작은 모델이 따라 하게 하는 증류가 대표적이다.
AesCode에서 이미지 모델의 출력은 정답이 아니다.
틀린 글자와 숫자가 섞여 있다는 것을 전제로,
배치와 색이라는 일부 속성만 신호로 쓰고 나머지는 버린다.

이 방식은 다른 분야로 쉽게 번진다.
예를 들어 음성 합성 모델이 만든 억양을 대본의 정확성과 분리해 쓰거나,
동영상 생성 모델이 만든 카메라 움직임만 3D 장면 코드의 참고로 쓰는 식이다.
공통 조건은 산출물을 검증 가능한 표현(코드, 그래프, 데이터)으로 만들 수 있고,
생성 모델의 출력에서 “믿을 속성”과 “버릴 속성”을 나눌 수 있는가다.
이 조건을 갖춘 영역에서는 생성 모델의 환각이 더 이상 치명적이지 않고,
오히려 값싼 안목의 원천이 된다.

### 인쇄 시대의 원고와 시안 분리가 모델 안으로 들어왔다

출판과 광고 디자인에는 오래된 분업이 있다.
편집자는 원고를 확정하고, 디자이너는 같은 원고로 시안을 여러 개 만든다.
시안의 더미 텍스트는 아무도 사실로 받아들이지 않고,
최종본은 확정 원고를 시안의 레이아웃에 흘려 넣어 만든다.
AesCode의 구조가 정확히 이 분업이다.
프롬프트와 요구 사항이 확정 원고이고,
참고 이미지가 더미 텍스트가 섞인 시안이다.

`from_idea` 파이프라인이 사람에게 `spec.json`의 사실을 고치게 하고
그림은 손대지 않게 한 것도 같은 분업을 사람과 모델 사이에 다시 그은 것이다.
이 비유가 시사하는 점은, 디자인 자동화의 다음 병목이
레이아웃 생성이 아니라 원고 확정, 즉 무엇이 사실인지 정하는 일이 된다는 것이다.
AesCode는 사실을 틀리지 않게 만드는 데 집중했지만,
그 사실을 누가 어떻게 확정하는지는 여전히 사람의 몫으로 남겨 두었다.

### 측정 가능한 채널이 측정 어려운 채널을 끌고 간다

AesCode의 학습 곡선 설명은 정직하다.
실행 채널은 SFT 직후 포화되고, 텍스트와 표·차트는 빠르게 오르며,
레이아웃, 여백, 디자인은 학습 내내 천천히 오른다.
여기에 표·차트 채널의 가중치가 3.0으로 다른 채널의 세 배다.
채널별 정규화가 규칙 보상의 독주를 막는다고 해도,
결과표에서 가장 큰 개선이 Rule에서 나온 것은 우연이 아니다.

이 긴장은 규모가 커질수록 중요해진다.
결정적 검증기로 잴 수 있는 속성은 빠르게 최적화되고 금방 천장에 닿는다.
그 뒤 남는 개선 여지는 모두 VLM 심사자가 판단하는 영역에 있고,
그 영역의 보상은 심사 모델의 취향과 질문 설계에 따라 흔들린다.
다음 세대 디자인 생성 모델의 경쟁은 모델 구조보다
“좋은 디자인”을 얼마나 많이, 얼마나 귀속 가능한 질문으로
명세할 수 있는가에서 갈릴 것이다.

### 작은 모델의 쓸모는 비용보다 신뢰 구간에 있다

AesCode-8B는 Overall 82.94로,
참고 이미지를 받은 GPT-5.5(81.28)와 Claude Opus 4.8(80.39)보다 높다.
비용 면에서 의미가 크지만, 더 중요한 차이는 오류의 종류다.
프런티어 모델은 참고 이미지를 받으면 차트 값을 틀리는 쪽으로 무너졌고,
AesCode는 차트와 경계 점수를 지키는 쪽으로 학습되었다.

보고서나 대시보드를 자동으로 만드는 실무에서는
조금 덜 세련된 페이지보다 숫자 하나가 틀린 페이지가 훨씬 비싸다.
그래서 이 결과는 “작은 모델도 큰 모델만큼 예쁘다”보다
“작은 모델이 틀리면 안 되는 곳을 더 잘 지킨다”로 읽는 편이 쓸모 있다.
특정 산출물 형식에 대해 검증기를 갖출 수 있는 조직이라면,
범용 프런티어 모델을 그대로 쓰는 것보다
이렇게 좁게 학습한 모델이 더 믿을 만한 선택이 될 수 있다.
