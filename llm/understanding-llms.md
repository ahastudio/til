## 소개

율무커피(@yulmu_coffee)가 2026-10-23에 올린 12분 분량의 Twitter 아티클이다.
“컨텍스트 윈도가 뭐예요?”, “토큰이 글자 수랑 같은 거예요?”, “캐시는 왜 할인해요?”라는 질문에 답하려고 썼다고 한다.
저자는 비유를 많이 쓰되, 비유가 오해를 부르는 곳에는 한계를 같이 적겠다고 약속한다.
목표는 채팅창에 질문을 입력한 뒤 일어나는 일을 머릿속에 그릴 수 있게 하는 것이다.

글은 14개 장으로 이어지고, 앞 장의 개념이 뒤 장의 이유가 되도록 짜여 있다.
다음 토큰 예측에서 시작해 토큰, 임베딩, 파라미터, 학습, 어텐션, 레이어를 거치고, 사전학습 이후의 단계, 추론의 두 박자, KV 캐시, 프롬프트 캐싱, 컨텍스트 윈도우, MoE로 끝난다.
이 노트는 14개 장을 그대로 옮기지 않고, 읽고 나서 실제로 판단에 쓸 수 있는 형태로 다시 묶는다.

이 글의 쓸모는 마지막 두 가지 질문, 곧 API 요금표의 캐시 할인과 긴 대화가 느려지는 이유에 가장 뚜렷하게 나타난다.
그 두 질문의 답이 앞의 모든 개념을 거쳐야 나오기 때문에, 순서대로 읽는 구성이 효과를 낸다.

## 동작 방식

### 한 번의 요청이 지나가는 길

저자가 마치며에서 정리한 흐름을 단계별로 풀면 다음과 같다.

| 단계 | 일어나는 일                                 | 비유            |
| ---- | ------------------------------------------- | --------------- |
| 1    | 질문이 토큰으로 잘리고 번호가 붙는다        | 글을 조각냄     |
| 2    | 토큰 번호가 임베딩 벡터가 된다              | 지도 위의 좌표  |
| 3    | 레이어마다 어텐션으로 서로의 문맥을 섞는다  | 회의실 대화     |
| 4    | 마지막 층이 다음 토큰의 확률표를 낸다       | 완제품          |
| 5    | 확률표에서 하나를 골라 붙이고 다시 예측한다 | 자동완성의 반복 |

3단계 전체가 프리필이고, 이때 KV 캐시가 만들어진다.
5단계의 반복이 디코딩이다.
저자는 이 모든 과정에서 파라미터가 대화 중에는 바뀌지 않는다는 점을 거듭 강조한다.

### 학습과 추론은 다른 일이다

학습은 순전파, 손실 계산, 역전파, 경사하강법을 되풀이해 다이얼을 맞추는 일이고, 끝나면 값이 고정된다.
추론은 고정된 값으로 순전파만 하는 일이다.
대화 중에 모델이 내 말을 기억하는 것처럼 보이는 것은 대화 전체가 매번 입력으로 다시 들어가기 때문이라고 저자는 설명한다.

### 프리필은 연산이 병목이고 디코딩은 메모리가 병목이다

프리필은 프롬프트 토큰이 이미 다 주어져 있어 한꺼번에 병렬로 처리한다.
저자는 vLLM 논문을 인용해, 디코딩은 토큰을 하나씩 만들어야 해서 행렬-벡터 곱 위주가 되고 메모리 병목이 된다고 적는다.
그래서 긴 문서를 붙여 넣으면 첫 글자가 나오기까지 멈칫하고, 그 뒤로는 일정한 속도로 흘러나온다.

### KV 캐시는 중복 계산을 메모리와 맞바꾼다

디코딩에서는 새 토큰을 만들 때마다 앞 토큰 전부의 Key와 Value가 필요하다.
이를 매번 다시 계산하는 것이 낭비라서, 한 번 계산한 값을 저장해 둔다.
대가는 메모리이고, 저자는 vLLM 논문의 수치로 130억 파라미터 OPT 모델이 토큰 하나당 800KB, 2,048토큰 요청 하나에 최대 1.6GB를 쓴다고 적는다.

### 프롬프트 캐싱은 요청이 끝난 뒤에도 KV 캐시를 남겨 둔다

보통 KV 캐시는 요청이 끝나면 버려진다.
그런데 시스템 프롬프트, 툴 정의, 참고 문서처럼 요청마다 똑같은 앞부분이 있으면, 그 부분의 KV 텐서를 보관했다가 다음 요청에서 꺼내 쓸 수 있다.
저자는 OpenAI가 저장하는 것은 토큰이 아니라 KV 텐서라고 명시한다고 전한다.
계산을 건너뛰었으니 값을 덜 받는다는 것이 할인의 이유이고, 첫 글자가 나오기까지의 시간도 줄어든다.

## 값 정하기

저자가 2026년 10월 기준이라고 밝힌 캐시 요금과 최소 길이는 다음과 같다.
이 표는 글의 서술을 옮긴 것이어서, 실제로 쓰기 전에 각 회사 문서에서 다시 확인해야 한다.

| 회사      | 캐시 읽기                  | 캐시 쓰기                           | 보관 시간           | 최소 길이                  |
| --------- | -------------------------- | ----------------------------------- | ------------------- | -------------------------- |
| OpenAI    | 0.1배 (GPT-6.1 Sol 0.05배) | 30분 보관 1.25배, 12시간 보관 2.5배 | 30분, 12시간        | 1,024토큰                  |
| Anthropic | 0.1배 (일부 0.05배)        | 5분 보관 1.25배, 1시간 보관 2배     | 기본 5분, 쓰면 갱신 | 모델에 따라 512~4,096      |
| Gemini    | 암묵적 캐싱 자동 반영      | 글에 수치 없음                      | 글에 수치 없음      | 2.5 세대 2,048, 이후 4,096 |

OpenAI의 쓰기 요금은 GPT-5.6 이후 모델에 해당하고, 이전 모델은 쓰기 추가 요금이 없다고 저자는 적는다.
Anthropic 열의 괄호 값은 일부 최신 모델에서 읽기 0.05배, 쓰기 쪽 0.025배라고 적힌 대목을 줄인 것이다.

값을 정하는 기준은 하나다.
고정된 앞부분의 길이와 요청 간격을 보고, 보관 시간 안에 같은 앞부분이 몇 번 다시 쓰이는지를 센다.
쓰기 할인이 없는 대신 읽기가 싼 구조라서, 한 번만 쓰고 말 접두부에는 오히려 쓰기 요금만 낸다.

## 트레이드오프

### 캐시 할인은 접두부가 바이트 단위로 같아야만 받는다

Anthropic은 캐시 지점까지의 텍스트와 이미지가 100% 같아야 한다고 쓰고, OpenAI도 렌더링된 접두부 전체가 일치해야 한다고 쓴다고 저자는 전한다.
노트가 첫 장부터 쌓이는 구조라서, 3쪽에서 한 글자가 바뀌면 3쪽 이후는 모두 쓸 수 없다.

그래서 에이전트에서 오래된 기록을 요약하거나 잘라내 비용을 줄이려는 직관적인 방법이 역효과를 낼 수 있다.
글에 임베드된 저자의 10월 23일 트윗은 이 문제를 다룬다.
긴 작업을 하는 에이전트는 비용 대부분이 KV 캐시 읽기에서 나오고, 앞부분을 바꾸면 뒤의 캐시가 전부 무효가 된다는 내용이다.
그 트윗이 인용한 논문의 수치는 전체 API 비용의 82.4%라고 한다.
이 수치는 글 안에 임베드된 트윗에서 읽은 것이고, 논문 원문은 열어 보지 않았다.

### 책상을 키우면 계산과 메모리가 함께 는다

컨텍스트 윈도우가 넓으면 자료를 많이 펼칠 수 있지만, 어텐션이 모든 토큰 쌍을 비교하므로 계산이 늘고 KV 캐시도 커진다.
긴 프롬프트의 프리필이 오래 걸리는 이유도 여기서 나온다.
넓은 윈도우의 대가는 속도와 메모리이고, 이것을 피하는 방법은 글에 없다.

### MoE는 대역폭을 아끼는 대신 용량을 쓴다

저자는 Mixtral 8x7B를 예로 든다.
전체 파라미터는 470억 개인데 토큰 하나에 쓰는 것은 130억 개다.
전문가를 전부 메모리에 올려야 해서 용량은 많이 필요하지만, 토큰마다 읽는 양이 적어 대역폭 부담은 작다.
메모리 용량이 모자란 환경에서는 이 이점이 사라진다는 점이 암묵적으로 따라온다.

## 함정

### 비유가 만드는 오해를 글이 직접 막는 곳

저자는 비유가 오해를 부를 수 있는 곳마다 주석을 달아 둔다.
임베딩의 지도는 2차원이 아니라 수천 차원이고, 축에 사람이 붙인 이름이 없다.
어텐션의 주목은 의도적 집중이 아니라 유사도 점수의 가중 평균이다.
MoE의 전문가는 의학이나 법률 같은 주제를 맡지 않고, Mixtral 논문은 문법적이고 구조적인 패턴과 더 관련 있어 보인다고 보고했다고 한다.

이 주석들은 읽는 사람이 건너뛰기 쉬운 자리에 있다.
비유만 기억하고 주석을 놓치면, 어텐션을 “사람처럼 집중하는 것”으로 되돌려 이해하게 된다.

### 접두부를 깨는 눈에 안 띄는 변경

글이 든 예는 시스템 프롬프트 맨 앞의 현재 시각 같은 값이다.
첫 줄이 매번 바뀌니 노트를 한 장도 못 쓴다.
OpenAI가 타임스탬프를 접두부 끝으로 옮기라고 권하고, Anthropic이 타임스탬프가 든 블록에 캐시 지점을 두면 쓰기 요금만 내고 읽기는 한 번도 못 한다고 경고한다고 저자는 전한다.

툴 정의의 순서나 스키마 변경, 일부 언어에서 JSON 키 순서가 무작위로 바뀌는 것도 같은 결과를 낳는다.
툴을 잠시 끄고 싶으면 정의를 지우지 말고 `tool_choice: "none"` 등으로 막으라는 것이 OpenAI의 권고라고 글은 적는다.

### 짧은 접두부는 오류 없이 캐싱이 꺼진다

Anthropic은 최소 길이보다 짧으면 `cache_control`을 붙여도 오류 없이 캐싱 없이 처리한다고 한다.
오류가 나지 않으니 캐싱이 적용되었다고 착각하기 쉽다.
응답에 캐시 읽기 토큰이 찍혔는지를 확인해야 한다는 점은 글에 명시되어 있지 않고, 이 노트가 덧붙인 판단이다.

### 수치와 모델명은 글이 쓰인 시점의 값이다

요금 배율, 최소 길이, 모델별 파라미터 수와 벡터 크기는 모두 2026년 10월 기준의 서술이다.
글은 한국어 토큰 비율이 토크나이저마다 크게 달라 직접 확인하라고 적어 두었다.
같은 태도로 이 노트의 모든 수치를 다룰 필요가 있다.

## 확인하기

글이 말하는 KV 캐시의 핵심 주장은 두 가지다.
캐시를 써도 결과는 같고, 대신 계산 횟수가 준다.
아래 코드는 외부 패키지 없이 이 주장을 그대로 시험한다.
토큰 6개로 어텐션을 캐시 없이 한 번, 캐시와 함께 한 번 계산해 결과를 비교한다.

```python
import math
import random

random.seed(0)
d, T = 4, 6                                   # 벡터 크기, 토큰 수


def mat(r, c):
    return [[random.gauss(0, 1) for _ in range(c)] for _ in range(r)]


def vec_mat(v, m):
    return [sum(v[i] * m[i][j] for i in range(len(v))) for j in range(len(m[0]))]


def softmax(s):
    mx = max(s)
    e = [math.exp(a - mx) for a in s]
    return [a / sum(e) for a in e]


def attend(q, ks, vs):
    s = [sum(a * b for a, b in zip(q, k)) / math.sqrt(d) for k in ks]
    w = softmax(s)
    return [sum(w[i] * vs[i][j] for i in range(len(vs))) for j in range(d)]


x = mat(T, d)                                 # 임베딩된 토큰 6개
Wq, Wk, Wv = mat(d, d), mat(d, d), mat(d, d)

# 1) 캐시 없이: 토큰마다 앞쪽 모든 토큰의 K, V를 처음부터 다시 계산한다
calls_plain, plain = 0, []
for t in range(T):
    ks = [vec_mat(x[i], Wk) for i in range(t + 1)]   # i <= t 만 보기: 마스킹
    vs = [vec_mat(x[i], Wv) for i in range(t + 1)]
    calls_plain += t + 1
    plain.append(attend(vec_mat(x[t], Wq), ks, vs))

# 2) KV 캐시: 새 토큰의 K, V만 계산해 덧붙인다
K, V, cached = [], [], []
for t in range(T):
    K.append(vec_mat(x[t], Wk))
    V.append(vec_mat(x[t], Wv))
    cached.append(attend(vec_mat(x[t], Wq), K, V))

diff = max(abs(a - b) for p, c in zip(plain, cached) for a, b in zip(p, c))
print("두 결과의 최대 차이:", diff)
print("K,V 계산 횟수 (캐시 없음):", calls_plain, "(캐시):", T)
print("bf16 27.78B 파라미터 GB:", 27.78e9 * 2 / 1e9)
print("KV 800KB x 2048 토큰 GB:", 800e3 * 2048 / 1e9)
```

이 코드를 실제로 실행한 출력은 다음과 같다.

```text
두 결과의 최대 차이: 0.0
K,V 계산 횟수 (캐시 없음): 21 (캐시): 6
bf16 27.78B 파라미터 GB: 55.56
KV 800KB x 2048 토큰 GB: 1.6384
```

결과가 완전히 같고 계산 횟수가 21회에서 6회로 줄었다.
토큰이 T개일 때 캐시 없이는 T(T+1)/2번, 캐시와 함께는 T번이므로, 길이가 늘수록 격차가 벌어진다.
이 실험은 어텐션 한 층의 계산 횟수만 센 것이어서, 실제 모델의 속도나 비용을 보여 주지는 않는다.

마지막 두 줄은 글의 산술을 검산한 것이다.
bf16에서 파라미터 하나는 2바이트이므로 277.8억 개는 약 55.6GB이고, 글이 말한 공식 체크포인트 크기와 맞는다.
토큰당 800KB에 2,048토큰을 곱하면 약 1.64GB이고, 글의 “최대 1.6GB”와 맞는다.
다만 Qwen의 공식 체크포인트 크기와 vLLM 논문의 800KB는 글의 서술을 그대로 쓴 것이고, 직접 확인하지 않았다.

## 체크리스트

- 시스템 프롬프트와 툴 정의가 요청에서 가장 앞에 있는가.
- 현재 시각이나 사용자별 값이 접두부 끝쪽으로 옮겨져 있는가.
- 툴 정의의 순서와 JSON 키 순서가 요청마다 같은가.
- 고정 접두부가 사용하는 모델의 최소 토큰 길이를 넘는가.
- 요청 간격이 보관 시간(Anthropic 기본 5분) 안에 들어오는가.
- 응답에 캐시 히트가 실제로 기록되는지 확인했는가.
- 오래된 기록을 요약하거나 자르는 처리가 접두부를 바꾸지 않는가.
- 쓰는 모델의 요금 배율을 글이 아닌 해당 회사 문서에서 확인했는가.

## 기억할 원칙

### 앞에는 바뀌지 않는 것만 둔다

저자가 한 줄로 줄인 것처럼, 안 바뀌는 것은 앞에 두고 한 글자도 건드리지 않는다.
캐시는 앞에서부터 순서대로 쌓이기 때문에, 앞쪽 한 군데의 변경이 그 뒤 전체를 무효로 만든다.
그래서 프롬프트를 짤 때는 무엇을 말할지보다 무엇이 요청마다 달라지는지를 먼저 가른다.

### 비유는 한 번 쓰고 주석으로 되돌아온다

이 글은 비유를 쓰는 즉시 한계를 적는 구조가 잘 작동한다.
지도, 다이얼, 노트, 책상은 모두 이해의 입구이고, 그 비유를 그대로 믿으면 어텐션이나 MoE를 잘못 상상하게 된다.
모델을 다룰 때도 비유로 감을 잡은 뒤, 수치로 검산하는 순서를 지키는 편이 안전하다.
