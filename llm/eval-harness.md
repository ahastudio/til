# Eval harness: 변경마다 무엇이 고쳐지고 무엇이 깨졌는지 알려주는 장치 만들기

트윗: [Build Your Eval Harness](https://twitter.com/tonycueva/status/2115089591824744957)

## 소개

Confident AI(YC W25)에서 GTM을 맡은 Tony가 2026년 10월 27일 올린 Twitter
Article이다.
조회수는 2만 1천 회가 넘고, 평가와 추적(evals and tracing) 가이드의 두
번째 편이다.
첫 편에서 만든 테스트 질문 몇 개로 버그 하나를 고쳤더니,
다른 버그를 고치려고 프롬프트를 바꾼 뒤에 무엇이 같이 깨졌는지 아무도 말하지
못하는 문제가 남았다는 데서 시작한다.

글이 내놓는 해법이 eval harness다.
모든 테스트 질문을 변경마다 다시 던지고,
고쳐진 것과 깨진 것을 목록으로 알려주는 설치다.
한 번 만들어 두면 모델 교체, 도구 추가,
프롬프트 수정이 모두 이 관문을 통과해야 배포된다.
글은 신발 가게 지원 봇 하나를 실제 서버에 올리고 실제 트래픽의 질문 20개를 세
번씩 던지는 예로 전 과정을 보여주며, 코드는 저자의 GitHub 저장소로
공개했다고 한다.

이 문서는 그 절차를 실무 순서로 다시 정리하고,
글의 숫자가 무엇을 증명하고 무엇을 증명하지 못하는지를 따진다.
글이 쓰는 도구는 Confident AI와 DeepEval이므로,
도구에 묶이지 않는 원리와 도구에 묶이는 부분을 나눠 적는다.

### 역할별로 하네스가 하는 일

글은 독자를 엔지니어, QA, PM 세 부류로 나눠 각자의 일을 다르게 정의한다.

| 역할     | 하네스가 되는 것                | 그 역할이 하는 결정                                                                 |
| -------- | ------------------------------- | ----------------------------------------------------------------------------------- |
| 엔지니어 | 프롬프트와 모델의 테스트 스위트 | 변경마다 질문을 세 번씩 돌리고, 항상 통과하던 질문이 깨지면 CI가 막는다             |
| QA       | AI를 위한 회귀 테스트           | 실제 트래픽에서 케이스를 고르고, 불안정한 케이스가 봇 탓인지 심판 탓인지 가른다     |
| PM       | 좋은 답의 기준이 담긴 합격률    | 질문마다 기대 답을 쓴다. 예를 들어 5주 전 구매는 35일이므로 30일 창 밖이라 거절이다 |

## 동작 방식

### 하네스라는 말의 두 층

글은 하네스를 모델을 둘러싼 코드로 정의한다.
Claude Code와 Codex가 그 예이고, 도구를 주고 과업이 끝날 때까지 반복 실행하는
층이라는 뜻이며 글은 이를 Agent = Model + Harness로 요약한다.
같은 모델이 하네스에 따라 결과가 달라진다는 근거로,
글은 OpenAI 연구자 @polynoamial이 포켓몬을 하는 모델들의 점수가 하네스가 달라
비교되지 않는다고 짚은 것을 든다.
그래서 벤치마크의 모델 점수는 내 앱의 점수가 아니고,
내 앱의 점수는 내 프롬프트와 내 데이터로 직접 재야 한다는 것이 글의 출발점이다.

eval harness는 그 점수를 내는 장치다.
글은 Anthropic의 에이전트 평가 가이드가 이를 평가를 처음부터 끝까지 실행하는
설치로 정의한다고 인용한다.
정의에서 중요한 것은 모델과 하네스를 함께,
사용자가 만나는 모습 그대로 잰다는 점이다.

### 한 번의 실행이 거치는 경로

글이 만든 하네스의 한 번의 실행은 이렇게 흐른다.
먼저 실제 트래픽에서 질문을 모아 골든(golden)을 만든다.
골든은 질문과 기대 답과 실패 유형이 붙은 테스트 케이스다.
하네스는 사용자가 부르는 것과 같은 HTTP API로 앱을 호출하고,
각 질문을 세 번 던져 답을 받는다.
답마다 메트릭이 점수를 매기고, 새 실행의 질문별 상태를 이전 실행과 비교해 고쳐진
것, 깨진 것, 불안정해진 것을 보고한다.
마지막으로 CI가 항상 통과하던 질문이 항상 실패로 바뀐 경우에만 변경을 막는다.

### 글의 출발점이 된 숫자

글이 첫 편에서 만든 봇은 다섯 개 질문으로 수정이 증명됐다.
그런데 같은 봇을 실제 서버에 올리고 실제 트래픽에서 고른 질문 20개를 세 번씩
던지자 60개 중 33개만 통과했다.
다섯 개 질문은 이미 알던 버그 하나만 덮고 있었다는 것이 글의 결론이다.

## 구현하기

글의 구성을 여섯 단계로 줄이면 아래와 같다.
코드는 글의 저장소를 그대로 옮긴 것이 아니라,
같은 구조를 이 문서가 다시 쓴 것이다.
DeepEval의 정확한 호출 방식은 글의 설명을 따르되,
이 문서는 그 API를 직접 실행해 보지 않았다.

### 1단계: 트래픽에서 시작하고 요청에 출처 태그를 단다

앱은 요청마다 `source`를 받아 추적(trace)에 태그로 남긴다.
기본값은 `customer`이고 하네스가 보내는 요청은 `harness`다.
이 태그가 있어야 나중에 실제 고객의 질문만 골라낼 수 있고,
테스트 트래픽이 실제 지표를 오염시키지 않는다.

글은 20개 질문을 모은 뒤 추적 API로 질문, 답,
검색 결과를 내려받아 한 줄씩 읽는다.
이 읽기에서 실패 유형이 나온다.
글의 봇에서는 날짜 계산 실패와 지어낸 답 두 가지가 보였다.
5주 전 구매를 30일 창 안으로 판단한 것이 앞의 것이고, 도움말에 없는 가격 맞춤,
아동화, PayPal, 파손 상품에 아는 듯 답한 것이 뒤의 것이다.
이 단계에는 오류 분석(error analysis)이라는 이름이 붙는다.
실제 답을 읽고, 무엇이 틀렸는지 적고, 유형으로 묶는 일이다.
유형이 무엇을 테스트할지를 정한다.

글이 짚은 한 가지 사실이 특히 쓸모 있다.
5주 질문의 검색 결과에는 30일 규칙 문서가 없었다.
프롬프트 문제처럼 보이던 버그의 첫 원인이 검색이었던 것이다.
나쁜 추적을 읽을 때는 LLM 호출보다 검색 호출을 먼저 보라는 조언이 여기서 나온다.

### 2단계: 골든을 만든다

골든마다 기대 답을 결정과 그 근거 규칙으로 쓴다.

```json
[
  {
    "input": "5주 전에 산 러닝화가 아파요. 반품할 수 있나요?",
    "expected_output": "아니요. 5주는 35일이고 반품은 배송 후 30일 이내입니다.",
    "failure_type": "date math"
  },
  {
    "input": "아동화도 파나요?",
    "expected_output": "도움말에 없다. 모른다고 답하고 상담원 연결을 제안한다.",
    "failure_type": "made up"
  }
]
```

실패한 질문만이 아니라 20개 전부를 넣어야 한다.
통과하는 질문이 있어야 한 가지를 고치다 다른 것이 깨졌다는 사실을 알 수
있기 때문이다.
기대 답은 판단 가능하게 써야 한다.
글은 35일이라는 숫자가 있는 문장은 심판이 검사할 수 있지만 봇이 정확하게
답한다는 문장은 너무 모호하다고 설명한다.

### 3단계: 앱을 사용자와 같은 경로로 호출한다

하네스는 봇 코드를 import하지 않고 사용자가 부르는 HTTP API를 부른다.
그래야 배포와 인증까지 테스트에 들어간다.

```python
import os
import time
import requests

URL = os.environ["APP_URL"]
HEADERS = {"Authorization": f"Bearer {os.environ['APP_API_TOKEN']}"}


def wake_up():
    # 무료 호스팅은 유휴 시 잠들므로 첫 요청 전에 깨운다
    requests.get(f"{URL}/health", timeout=120).raise_for_status()


def ask(question: str, source: str = "harness"):
    for attempt in range(3):
        r = requests.post(
            f"{URL}/chat",
            json={"question": question, "source": source},
            headers=HEADERS,
            timeout=120,
        )
        if r.status_code < 500:  # 서버 오류만 재시도한다
            break
        time.sleep(10 * (attempt + 1))
    r.raise_for_status()
    data = r.json()
    return data["answer"], data["sources"]
```

글은 이 재시도를 실제 실패 뒤에 넣었다고 밝힌다.
첫 기준선 실행에서 서버가 일부 요청에 오류를 냈고,
결과가 없는 케이스를 비교 스크립트가 통과로 센 것이다.

### 4단계: 실패 유형마다 메트릭을 하나 쓴다

첫 편의 두 메트릭, 답변 관련성(answer relevancy)과 충실도(faithfulness)는 5주
버그를 놓쳤다.
글에 따르면 첫 전체 실행에서 충실도는 60개 케이스를 모두 통과시켰고,
5주 질문에서 두 메트릭 모두 1.00이었다.
답이 주제에 맞았고 봇이 본 문서 세 개와도 일치했지만 틀린 답이었기 때문이다.

그래서 실패 유형마다 G-Eval 메트릭을 하나씩 만든다.
글이 든 두 메트릭은 이렇다.

| 메트릭         | 묻는 것                                                       | 받는 증거                                                         |
| -------------- | ------------------------------------------------------------- | ----------------------------------------------------------------- |
| Policy correct | 답의 결정이 기대 답과 같고, 숫자와 기간이 정책과 맞는가       | 질문, 답, 기대 답, 도움말 전체(CONTEXT)                           |
| Stays in docs  | 답의 모든 사실이 검색 결과에서 나왔고, 없으면 모른다고 했는가 | 질문, 답, 봇이 실제로 본 검색 결과와 도구 출력(RETRIEVAL_CONTEXT) |

두 메트릭이 서로 다른 증거를 받는다는 것이 이 단계의 핵심이다.
글의 첫 Stays in docs는 CONTEXT를 받았다가 주문 상태 질문 두 개를
잘못 실패시켰다.
주문 상태는 도구가 알려주는 사실이어서 도움말에 없었고,
심판이 도움말에 없는 사실을 지어낸 것으로 본 것이다.
RETRIEVAL_CONTEXT로 바꾸자 둘 다 통과했다.
글의 교훈은 실패를 믿기 전에 읽으라는 것이다.
앱의 버그도 있고 하네스의 버그도 있다.

### 5단계: 질문마다 세 번 돌리고 질문 단위로 비교한다

글의 하네스는 pytest 파일 하나다.
골든마다 도움말 전체를 컨텍스트로 붙이고, 앱을 호출하고,
네 메트릭으로 `assert_test`를 건다.
실행은 `deepeval test run test_harness.py -id <실행 이름> -r 3` 형식이며,
`-r 3`이 모든 케이스를 세 번 반복한다.
봇이 매번 다르게 답할 수 있고 심판도 매번 다르게 점수를 줄 수 있기 때문이다.

비교의 핵심은 합격률이 아니라 질문별 상태다.
세 번 모두 통과하면 항상 통과, 세 번 모두 실패하면 항상 실패, 섞이면 불안정이다.
결과가 세 개가 아니면 오류로 센다.
아래는 이 문서가 같은 논리를 다시 쓴 비교 스크립트다.
입력은 질문에서 반복별 통과 여부 목록으로 가는 JSON 한 쌍이며,
평가 도구의 출력을 이 형식으로 바꾸는 부분은 도구마다 다르다.

```python
import json
import sys

REPEATS = 3  # 평가를 돌릴 때 쓴 반복 횟수와 같아야 한다


def status(passes: list[bool]) -> str:
    if len(passes) != REPEATS:
        return "error"  # 앱 호출이 점수 전에 실패했다
    if all(passes):
        return "always pass"
    if not any(passes):
        return "always fail"
    return "flaky"


def main(old_path: str, new_path: str) -> int:
    old = {q: status(p) for q, p in json.load(open(old_path)).items()}
    new = {q: status(p) for q, p in json.load(open(new_path)).items()}

    groups = {
        "고쳐짐": lambda a, b: a != "always pass" and b == "always pass",
        "깨짐": lambda a, b: a == "always pass" and b == "always fail",
        "불안정해짐": lambda a, b: a == "always pass" and b == "flaky",
        "여전히 실패": lambda a, b: b == "always fail",
        "오류": lambda a, b: b == "error",
    }
    found = {name: [] for name in groups}
    for q, b in new.items():
        a = old.get(q, "error")  # 이전 실행에 없던 질문은 오류로 드러낸다
        for name, cond in groups.items():
            if cond(a, b):
                found[name].append(q)

    for name, qs in found.items():
        print(f"{name} ({len(qs)})")
        for q in qs:
            print(f"  {old.get(q, '-')} -> {new[q]}  {q}")

    # 항상 통과하던 질문이 항상 실패로 바뀌었거나 결과가 비었을 때만 막는다
    return 1 if found["깨짐"] or found["오류"] else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1], sys.argv[2]))
```

글은 이 보고를 아래에서 위로 읽으라고 권한다.
여전히 실패가 할 일 목록이고, 불안정해짐이 읽을 목록이며, 합격률은 마지막이다.

### 6단계: 변경마다 자동으로 돌린다

글의 GitHub Actions 파일은 봇이나 골든을 건드린 풀 리퀘스트마다 돈다.
CI 머신 안에서 풀 리퀘스트 버전의 봇을 띄우고, 하네스를 세 번 반복해 돌리고,
main에서 만든 기준선과 비교한다.
기준선은 저장소에 고정된 파일이므로 main이 좋아지면 main의 실행 결과를 같은
방식으로 저장해 기준선 파일을 덮어쓴다.
이 작업에서 알려진 실패 때문에 평가 단계가 멈추지 않도록 평가 명령에는 실패를
무시하는 처리를 두고, 판정은 비교 스크립트의 종료 코드에 맡긴다.

## 값 정하기

| 값             | 글의 시작점                  | 근거와 바꿀 때                                                                 |
| -------------- | ---------------------------- | ------------------------------------------------------------------------------ |
| 반복 횟수      | 질문당 3회                   | 봇과 심판의 변동을 가르는 최소선이다. 빠른 확인은 1회로 하되 힌트로만 읽는다   |
| 메트릭 임계값  | 0.7                          | 글이 모든 메트릭에 쓴 값이다. 심판 점수의 분포를 본 뒤 조정해야 한다           |
| 심판 모델      | 도구 기본값(글은 gpt-5.4)    | 비교할 모든 실행에서 같아야 한다. 바꾸면 비용과 점수가 함께 바뀐다             |
| 비용           | 3회 실행 한 번에 약 1.40달러 | 글의 20개 질문 기준이며 심판 호출 비용만이다. 글은 CI 전체가 8분 걸렸다고 한다 |
| CI의 차단 조건 | 항상 통과 → 항상 실패        | 세 번째 시도에서 정한 값이다. 이유는 아래 트레이드오프에 있다                  |
| 실행 이름      | 변경을 알려주는 이름         | 글은 `main-prompt-v2` 같은 이름을 쓴다. 비교 단계가 이름으로 실행을 찾는다     |

## 트레이드오프

### 한 번 돌릴까, 세 번 돌릴까

한 번 실행은 비용이 세 번의 약 3분의 1이다.
하지만 한 번의 결과로는 봇이 불안정한 것과 심판이 불안정한 것을 구별할 수 없다.
글의 사례가 이를 보여준다.
주문 4821 질문은 세 번 모두 같은 올바른 답을 받았는데, 심판의 점수는 실패,
실패, 통과였다.
봇은 그대로였고 심판이 흔들린 것이다.
이 구별이 있어야 고칠 대상이 봇인지 메트릭인지 정할 수 있다.

세 번으로 얻지 못하는 것도 있다.
표본이 세 개이므로 불안정하다는 판정은 거친 분류일 뿐 확률 추정이 아니다.
이 문서의 해석으로는, 한 질문의 합격 확률이 높은지 중간인지 낮은지를 가리는
용도로 삼아야 하고 비율 자체를 비교하는 용도로는 약하다.

### 게이트를 얼마나 엄격하게 둘까

글은 게이트를 세 번 만들었다.
첫째 안은 실패한 테스트가 하나라도 있으면 막는 것이었다.
main에도 실패하는 골든이 있어서 첫 풀 리퀘스트부터 빨갛게 되었고,
항상 빨간 검사는 사람들이 무시하게 된다.
둘째 안은 한 번의 실행에서 회귀가 있으면 막는 것이었다.
답은 맞았는데 정중한 마무리 문장 때문에 관련성 점수가 0.67이 된 질문이 있었고,
한 번의 실행이 심판의 잡음을 거짓 경보로 바꿨다.
셋째 안은 세 번 모두에서 항상 통과하던 질문이 항상 실패로 바뀐 경우에만
막는 것이다.

이 안의 대가도 있다.
항상 통과하던 질문이 불안정해지는 변화는 막지 않고 사람이 읽을 목록에
올릴 뿐이다.
품질이 서서히 떨어지는 변화를 게이트가 잡지 못할 수 있다는 뜻이다.
그래서 불안정해짐 목록을 읽는 사람과 시점이 정해져 있어야 이 설계가 성립한다.
이것은 글이 직접 말하는 내용이 아니라 이 문서의 추론이다.

### 메트릭에 어떤 증거를 줄까

메트릭마다 필요한 증거만 줘야 한다.
정답 판단에는 기대 답과 진짜 정책 전체를 주고,
지어낸 사실 검사에는 봇이 실제로 본 것만 준다.
증거가 틀리면 맞는 답을 틀렸다고 판정하며, 글의 첫 Stays in docs가 그랬다.
증거를 넉넉히 주는 쪽이 안전해 보이지만,
지어낸 사실 검사에 도움말 전체를 주면 봇이 보지 못한 문서로 정당화되는 답을
통과시킬 수 있다.
글이 이 가능성을 직접 다루지는 않으며, 이 문서가 두 메트릭의 증거 설계에서
이끌어낸 해석이다.

### 한 번에 하나만 바꿀까

글은 한 실행에 한 가지만 바꾸라고 한다.
프롬프트와 검색을 함께 바꿨다면 5주 질문의 수정이 검색에서 왔다는 사실을 알 수
없었을 것이다.
글의 흐름이 이를 보여준다.
프롬프트를 v3로 바꾸자 60개 중 41개가 통과하고 일곱 질문이 고쳐졌지만 5주 질문은
세 번 모두 여전히 실패했다.
이유는 검색이 키워드 일치였고, 고객이 쓴 send them back이 30일 규칙 문서와
공유하는 단어가 없었기 때문이다.
검색을 임베딩 기반 의미 일치로 바꾸자 54개가 통과했고 회귀는 없었다.

비용은 실행 횟수다.
변경을 하나씩 검증하면 실행이 늘고 그만큼 심판 호출 비용이 든다.
이 비용이 부담되면 변경 묶음을 한 번에 돌린 뒤 실패가 나올 때만 쪼개는 방법이
있지만, 그때는 원인을 되짚는 일이 사람 몫이 된다.

## 함정

### 결과가 없는 케이스가 통과로 센다

글이 실제로 겪은 일이다.
첫 기준선에서 서버가 일부 요청에 오류를 냈고,
결과가 없는 케이스를 비교 스크립트가 통과로 셌다.
점수가 없는 것과 점수가 높은 것은 다르므로,
질문마다 결과 개수를 확인해 세 개가 아니면 오류로 드러내야 한다.

### 한 번의 하락을 회귀로 부른다

글은 Confident AI의 회귀 화면이 테스트 케이스 세 개를 회귀로 표시했다고 한다.
그중 하나인 빠른 배송 요금 질문은 앞선 v3에서 이미 통과, 실패,
통과로 불안정했고, 새 실행에서는 실패, 통과, 통과였다.
한 번의 실행에서 보인 하락은 이전부터 불안정했던 질문의 잡음일 수 있다.
질문 단위로 세 번을 비교해야 가를 수 있다.

### 프롬프트를 고치기 전에 추적을 열지 않는다

5주 버그는 프롬프트 지시를 늘려도 고쳐지지 않았다.
추적을 열면 검색 결과에 규칙 문서가 없다는 것이 바로 보였다.
실패를 만나면 프롬프트를 다시 쓰기 전에 추적에서 검색 호출을 먼저 읽는
것이 순서다.

### 코드로 고칠 수 없는 실패를 코드로 고치려 한다

글의 마지막 실행에서도 파손 상품 질문은 세 번 모두 실패했다.
도움말에 해당 문서가 없었기 때문이다.
프롬프트나 검색으로는 고칠 수 없고 지원팀이 문서를 써야 한다.
이런 질문은 골든에 남겨 두면 문서가 올라간 날 다음 실행에서 자동으로 항상 실패
목록을 벗어난다.

### 기준선이 낡는다

CI는 고정된 기준선 파일과 비교한다.
main이 좋아졌는데 기준선을 갱신하지 않으면 새로 고쳐진 질문을 다시 깨뜨려도
게이트가 잡지 못한다.
이 문서의 지적으로는, 기준선 갱신을 누가 언제 하는지가 정해져 있어야 한다.

## 비평

### 수정을 확인한 질문 집합이 수정에 쓴 질문 집합과 같다

글의 33개에서 41개, 54개로 오르는 숫자는 모두 같은 질문 20개에 대한 것이다.
이 20개는 트래픽에서 골라 오류를 분석하고 실패 유형을 정하고 골든을 만든 바로
그 질문들이다.
즉 발견용 집합과 평가용 집합이 같다.
고친 것이 그 20개에는 듣지만 새 질문에서도 듣는지는 이 숫자로 알 수 없다.
검색을 임베딩으로 바꾼 일은 일반적인 개선일 가능성이 높지만,
프롬프트에 날짜 계산 지시를 넣은 것은 이 질문 유형에 맞춘 처방이므로 새로운 날짜
표현에서 어떻게 되는지는 확인되지 않았다.

이 주장을 뒤집을 관찰은 간단하다.
실제 트래픽에서 하네스에 넣지 않은 새 질문 20개를 따로 모아 같은 실행을 하고,
54에 해당하는 합격 수가 비슷하게 나오는지 보면 된다.
글은 이런 보류 집합을 언급하지 않는다.
이것은 작은 데모의 한계이기도 하므로 하네스 구조 자체를 흠잡는 것은 아니다.

### 심판의 신뢰성이 실제로 어떻게 점검되었는지 알 수 없다

글은 메트릭을 라벨이 있는 몇 개 케이스로 먼저 시험하라고 권하고,
그 덕분에 주문 질문의 거짓 실패 두 건을 찾았다고 한다.
하지만 심판이 사람의 판단과 얼마나 일치하는지,
일치율을 어떻게 재는지는 나오지 않는다.
메트릭 점수가 0.67인지 0.7인지에 따라 합격이 갈리는데, 임계값 0.7의 근거도 없다.
글 자체가 불안정한 케이스의 상당수를 심판 잡음으로 분류하므로,
합격률 숫자의 오차 범위가 얼마인지가 핵심 질문으로 남는다.

### 도구 판매를 겸한 글이다

저자는 Confident AI에서 GTM을 맡고 있고,
글은 Confident AI와 DeepEval을 쓰며 끝에서 가입과 온보딩 도구를 안내한다.
이것이 내용을 틀리게 만들지는 않는다.
하지만 하네스의 원리와 이 제품의 기능은 다른 것이다.
추적 수집, 실행 이름 붙이기, 회귀 화면은 다른 도구로 대체할 수 있고,
이 문서의 구현 절은 그 원리 부분을 도구와 분리해 적으려 했다.
글이 인용하는 외부 발언(Anthropic의 가이드,
업계 인물들의 말)은 이 문서가 원문을 열어 보지 않았고 글이 전하는 대로만 옮겼다.

### 비용과 속도 수치는 작은 앱의 값이다

세 번 실행 1.40달러와 CI 8분은 질문 20개, 메트릭 4개, 앱 하나의 값이다.
골든이 수백 개로 늘고 메트릭이 더 늘면 비용과 시간은 곱으로 커진다.
글은 이 증가를 다루지 않는다.
이 문서의 추정으로는 골든을 층으로 나눠 풀 리퀘스트마다 도는 핵심 집합과 밤에
도는 전체 집합을 구분해야 할 시점이 온다.

## 체크리스트

- 요청마다 출처 태그가 추적에 남고, 테스트 요청과 고객 요청이 갈라지는가
- 골든이 실패한 질문만이 아니라 통과하던 질문도 포함하는가
- 기대 답이 결정과 근거 규칙으로 쓰여 심판이 검사할 수 있는가
- 하네스가 사용자가 부르는 것과 같은 API를 같은 인증으로 부르는가
- 실패 유형마다 메트릭이 있고, 메트릭마다 필요한 증거만 받는가
- 새 메트릭을 이미 라벨을 붙인 좋은 케이스와 나쁜 케이스로 먼저 시험했는가
- 질문마다 세 번 이상 돌려 항상 통과, 항상 실패, 불안정으로 나누는가
- 결과가 비었거나 개수가 맞지 않는 질문을 오류로 드러내는가
- 한 실행에는 변경을 하나만 담았는가
- CI가 항상 통과하던 질문이 항상 실패로 바뀔 때만 막는가
- 불안정해짐 목록을 읽는 사람과 시점이 정해져 있는가
- 기준선을 갱신하는 사람과 시점이 정해져 있는가
- 발견에 쓰지 않은 새 질문 집합으로 수정을 확인했는가

## 기억할 원칙

### 합격률보다 질문별 상태를 먼저 읽는다

60개 중 몇 개가 통과했는지는 얼마나 움직였는지만 알려준다.
무엇이 움직였는지는 질문마다 세 번의 결과를 이전 실행과 비교해야 나온다.
고쳐짐, 깨짐, 불안정해짐, 여전히 실패라는 목록이 합격률보다 먼저 읽을 보고서다.

### 실패를 믿기 전에 먼저 읽는다

실패 점수는 앱의 버그일 수도, 메트릭의 버그일 수도, 심판의 잡음일 수도 있다.
글의 주문 질문 두 건은 답이 맞았는데 메트릭에 잘못된 증거를 준 탓에 실패했고,
한 질문은 답이 같은데 심판만 흔들렸다.
실패의 이유 문장을 읽고 세 번의 답을 나란히 놓으면 어디를 고칠지 가려진다.

관련 문서로는 오류 분석을 평가의 중심에 놓는 [LLM Eval의 핵심은 도구가 아니라
오류 분석이다](llm-evals.md), 대규모 평가를 정리한 [평가 주도
개발](eval-driven-development.md), 하네스의 정의를 다룬 [에이전트
하네스](../agentic-coding/what-is-a-harness.md)가 있다.
