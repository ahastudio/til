# Z80-μLM: 1976년 프로세서에서 도는 40KB 대화형 모델

<https://github.com/HarryR/z80ai>

HN 토론: <https://news.ycombinator.com/item?id=46417815> (514점, 122개 댓글)

GN 토론: <https://news.hada.io/topic?id=25430>

## 소개

Z80-μLM은 문자 단위로 짧은 시퀀스를 생성하는 '대화형 AI'이며, **양자화 인식 학습(QAT)**을 거쳐 64KB RAM의 Z80 프로세서에서 돈다.

프로젝트의 출발점이 된 질문이 README에 그대로 적혀 있다.
**개성을 유지하면서 얼마나 작게 갈 수 있는가, 그리고 쉽게 학습하거나 미세 조정할 수 있는가, 자체 호스팅 배포까지 쉽게 되는가**다.

답은 그렇다는 것이었다.
추론과 가중치와 채팅 스타일 UI를 전부 포함한 **40KB `.com` 바이너리**가 1976년산 4MHz 프로세서에서 돈다.

저자가 스스로 선을 긋는다. 튜링 테스트를 통과하지는 못하겠지만 **초록색 화면 앞에서 미소 짓게 만들 수는 있을 것**이라는 것이다.

예제 두 개가 들어 있다.

`tinychat`은 가벼운 문답 쌍으로 학습한 대화 챗봇이다.

```text
> hello
HI
> are you a robot
YES
> do you dream
MAYBE
```

`guess`는 모델이 비밀 주제를 알고 YES/NO/MAYBE로 답하는 스무고개 게임이다.
Ollama나 Claude API로 학습 데이터를 생성하고 클래스 분포를 맞추는 도구가 함께 들어 있다.

## 아키텍처

### 입력을 해석하지 않고 해시한다

이 프로젝트에서 가장 특이한 결정이 입력 처리다.

입력 텍스트를 **트라이그램 해시로 128개 버킷에 넣는다**.
그래서 오타에 관대하고 **어순과 무관**하다.

```text
"hello there"  →  [버킷 23: 64, 버킷 87: 32, ...]
"there hello"  →  [버킷 23: 64, 버킷 87: 32, ...]   (같다)
"helo ther"    →  [버킷 23: 32, 버킷 87: 32, ...]   (비슷하다 — 오타에 강함)
```

README의 표현이 정확하다. **모델은 정확한 단어가 아니라 입력의 “형태”에 반응한다.**

그리고 그 한계도 스스로 적어 둔다.
짧은 입력에서는 의미론적으로 강력하지만, 길거나 어순에 의존하는 문장은 개념들이 같은 버킷을 두고 경쟁하면서 뭉개진다는 것이다.
예로 든 것이 **“문을 열고 불을 켜라”와 “문을 켜고 불을 열어라”를 구분하지 못할 것**이라는 문장이다.

### 신경망 부분

| 구성      | 내용                                         |
| --------- | -------------------------------------------- |
| 입력      | 질의 트라이그램 버킷 128개 + 문맥 버킷 128개 |
| 은닉층    | 깊이·너비 가변. 예: 256 → 192 → 128          |
| 출력      | 문자 집합의 문자마다 뉴런 하나               |
| 활성 함수 | 은닉층 사이에 ReLU                           |

gwern이 HN에서 이 구조를 정확히 분류했다.
어텐션을 쓰지 않고 입력 전체를 하나의 임베딩으로 만들어 한 번에 처리한다면 **이것은 트랜스포머도 RNN도 아니고 그냥 MLP 아니냐**는 것이다.[^gwern]

맞는 지적이고, 그것이 이 프로젝트가 성립하는 이유이기도 하다.

### 2비트 가중치와 16비트 누산기

각 가중치는 `{-2, -1, 0, +1}` 네 값 중 하나이고 **한 바이트에 4개씩 채워 넣는다**.

Z80은 8비트 CPU이지만 16비트 레지스터 쌍(HL, DE, BC)을 활성값과 누산기에 쓴다.
16비트 누산기가 **입력 256개를 오버플로 없이 더할 수 있는 수치 안정성**을 주지만, 표현력은 여전히 2비트 가중치에 묶여 있고 QAT 없이 순진하게 학습하면 오버플로가 나거나 이상하게 동작한다.

부동소수점은 전혀 쓰지 않는다. 전부 고정소수점 스케일링을 쓴 정수 연산이다.

### 추론 루프 전체

이 저장소에서 가장 인상적인 부분이 어셈블리가 짧다는 것이다.

```z80
; 채워 넣은 바이트에서 2비트 가중치를 꺼낸다
ld a, (PACKED)
and 03h             ; 하위 2비트만 남긴다
sub 2               ; 0,1,2,3 → -2,-1,0,+1 로 옮긴다
ld (WEIGHT), a

; 다음 가중치를 위해 회전시킨다
ld a, (PACKED)
rrca
rrca
ld (PACKED), a
```

곱셈-누산은 네 가지 경우로 갈라진다. 값이 넷뿐이므로 **곱셈 명령이 아예 필요 없다**.

```z80
MULADD:
    or a
    jr z, DONE       ; 가중치 0: 통째로 건너뛴다
    jp m, NEG        ; 가중치 음수: 뺀다
    ; 가중치 +1: 활성값을 더한다
    ld hl, (ACC)
    add hl, de
    ld (ACC), hl
    ret
NEG:
    cp 0FFh
    jr z, NEG1       ; 가중치 -1
    ; 가중치 -2: 두 번 뺀다
    ld hl, (ACC)
    sbc hl, de
    sbc hl, de
    ld (ACC), hl
    ret
```

층마다 끝에서 산술 우측 시프트 2회로 오버플로를 막는다.

```z80
sra h        ; 부호를 보존하는 산술 우측 시프트
rr l
sra h
rr l         ; ACC = ACC / 4
```

README가 스스로 요약한다.
이것이 신경망의 전부다. 가중치를 꺼내고, 곱해서 더하고, 시프트한다. 문자 하나를 만들 때마다 **약 10만 번 반복한다**.

## 플랫폼

CP/M이 원래 표적이고 `buildz80com.py`로 `.COM` 파일을 만든다. CP/M의 TPA(Transient Program Area)에 들어가는 크기다.

ZX Spectrum 48K도 완전히 지원한다. `buildz80tap.py`로 `.TAP`을 만들고, ZX Spectrum ROM 루틴으로 입출력을 처리하며, 48K에 맞게 메모리를 최적화했다.

```bash
# CP/M
iz-cpm CHAT.COM

# ZX Spectrum
fuse --tape CHAT.TAP
# 그다음 LOAD "" CODE 와 RANDOMIZE USR 32768
```

라이선스는 MIT 또는 Apache-2.0 중 선택이다.

## 무엇이 되고 무엇이 안 되는가

README에 이 목록이 있다는 사실 자체가 드물다.

| 잘하는 것                             | 아닌 것                           |
| ------------------------------------- | --------------------------------- |
| 짧고 다양한 입력에 일관된 범주형 출력 | 새로운 문장을 생성하는 챗봇       |
| 퍼지 매칭(오타, 재표현, 어순)         | 여러 턴의 맥락을 깊이 추적하는 것 |
| 어휘 선택을 통한 개성                 | 문법을 이해하는 파서              |
| 제약된 8비트 하드웨어에서 실행        | 범용 지능에 근접한 무엇           |

그리고 짧은 응답이 왜 한계가 아닌지를 설명하는 대목이 이 프로젝트의 태도를 보여 준다.

`OK`는 인정과 중립, `WHY?`는 전제에 대한 의문, `R U?`는 실존적 의심 제기, `MAYBE`는 진짜 불확실, `AM I?`는 질문을 되돌려 주는 것이다.
“모델은 당신을 이해하지 못한다. **그런데 어쩐지 당신을 알아듣는다**”는 한 줄이 이 프로젝트의 자기 인식이다.

## 분석

### 2비트라는 선택이 곱셈을 없앴다

가중치를 `{-2, -1, 0, +1}`로 제한한 것은 크기를 줄이기 위한 결정처럼 보인다. 실제로 한 바이트에 4개가 들어간다.

그런데 더 중요한 효과가 어셈블리에 있다.

값이 네 개뿐이므로 **곱셈이 조건 분기로 대체된다**.
0이면 건너뛰고, +1이면 더하고, -1이면 빼고, -2면 두 번 뺀다. `add`와 `sbc`만으로 끝난다.

이것이 왜 결정적인가 하면, **Z80에는 곱셈 명령이 없기 때문**이다.
일반적인 8비트 CPU에서 16비트 곱셈은 시프트와 덧셈을 반복하는 서브루틴이고 수십 사이클이 든다.

즉 이 양자화는 모델을 작게 만든 것이 아니라 **그 하드웨어에서 실행 가능하게 만든 것**이다.
2비트가 아니었다면 40KB에 들어가더라도 돌지 않았을 것이다.

같은 논리가 현대 하드웨어에서도 반복된다.
[BitNet b1.58](bitnet-b1-58.md)이 삼항 `{-1, 0, 1}`을 택한 이유가 정확히 이것이다. 행렬 곱셈이 덧셈으로 바뀐다.
목표 하드웨어가 GPU냐 1976년 CPU냐만 다르고 **논리는 동일하다**.

그래서 이 프로젝트를 “레트로 장난”으로만 보면 놓치는 것이 있다.
**양자화의 진짜 이득은 저장 공간이 아니라 산술 연산의 제거**라는 원리를, 곱셈기가 아예 없는 하드웨어에서 극단적으로 보여 준 사례다.

### 이해하지 않는 것을 설계 원칙으로 삼았다

트라이그램 해시 인코딩은 토크나이저가 아니다. 어휘도 없고 순서도 없다.

이것이 태만한 선택이 아니라 제약에서 나온 정직한 설계다.
64KB 안에서는 임베딩 테이블을 가질 수 없고, 어텐션은 말할 것도 없다.

그런데 이 선택이 예상 밖의 성질을 낳았다.
**오타와 재표현에 강하다**는 것이다. 정확한 문자열 대신 형태에 반응하기 때문이다.

orbital-decay가 이 지점을 짚었다.
옛날 자유 입력 RPG들에 퍼지 매처가 있었으면 좋았을 것이라며, 그것들이 정확한 키워드 일치로 동작해서 어색했다는 것이다.[^orbital-decay]
임의의 텍스트로 NPC와 대화할 수 있던 마지막 게임이 아마 2001년의 Wizardry 8이었을 것이라고 덧붙였다.

이 관찰이 이 모델의 실제 쓰임을 정확히 가리킨다.
**생성기가 아니라 관대한 분류기**다. 짧은 자유 입력을 미리 정한 응답 범주로 보내는 일에 맞다.

Peteragain은 한 걸음 더 들어갔다.[^Peteragain]
여기서 두 가지가 동시에 일어나고 있다는 것이다. 큰 모델이 어떻게 작동하는지 생각하는 데 유용한 아주 작은 LLM 메커니즘이 하나이고, **흔히 “속임수”라고 무시되는 잘 알려진 현상 — 인간이 믿고 싶어 한다는 것** — 이 다른 하나다.
우리는 대화 상대가 말한 것을 이해하려고 열심히 애쓰며, 사용 중인 언어는 집단적 문화 구성물이라는 것이다.
그러므로 진짜 질문은 **왜 그리고 어떻게 인간이 어떤 발화를 특정한 방식으로 이해하는가**이며, Eliza와 Parry와 촘스키봇이 같은 원리로 동작한다고 정리했다.

### ELIZA와의 비교가 이 프로젝트를 정확히 위치시킨다

여러 댓글이 ELIZA를 떠올렸고, 그 비교가 유익했다.

gcanyon은 적절한 코드와 학습 인프라만 있었다면 **ELIZA가 당시에 훨씬 유능할 수 있었을 것**처럼 보인다고 적었다.[^gcanyon]

antonvs가 실제 수치로 답했다.[^antonvs]
원래 ELIZA는 1960년대 IBM 7094 메인프레임에서 돌았고, 그 기계는 36비트 워드 32K에 **바이트 연산을 지원하지 않았다**.
6비트 BCD 문자를 워드당 6개씩 담을 수는 있었지만 그것은 문자열 연산용이었고 산술이나 논리 연산은 되지 않았다.
그래서 40KB Z80 실행 파일을 직접 옮긴다면 **바이트가 아니라 워드로 세어 40K > 32K이므로 빠듯할 것**이라는 계산이다.
다만 그 대부분이 2비트 가중치 데이터라면 그렇게 나쁘지 않을 수도 있다고 덧붙였다.

rahen은 다른 각도에서 같은 이야기를 했다.[^rahen]
자기가 1960년대 천공 카드 기계용으로 Fortran IV MLP를 짠 적이 있어 이것이 남 일 같지 않다며, **어텐션 메커니즘이 없고 문맥이 마지막 문장의 트라이그램으로 제한되는데도 상호작용이 놀랍도록 괜찮다**고 평했다.
그리고 이것이 **60년대 하드웨어에서도 동작할 수 있었을 것이며 당시 세상과 공상과학을 완전히 바꿔 놓았을 것**이라고 적었다.

noosphr은 이 감각을 한 문장으로 요약했다. **“가지 않은 길”**이라는 것이다.[^noosphr]

이 비교들이 흥미로운 이유가 있다.
이 프로젝트가 증명한 것은 작은 모델이 유용하다는 것이 아니라, **지금 우리가 아는 방법을 과거 하드웨어에 적용하면 무엇이 가능했을지**다.
병목이 하드웨어가 아니라 방법이었던 구간이 실제로 있었다는 뜻이다.

## 비평

### 실제 하드웨어에서의 속도를 밝히지 않는다

README가 4MHz 프로세서에서 돈다고 말하지만 **얼마나 빨리 도는지는 어디에도 없다**.

그 공백을 jrdres가 채웠다.[^jrdres]

Omikron CP/M 매퍼를 쓴 TRS-80 Model I의 사이클 정확 에뮬레이터로 시험한 기록이다.
당시 대부분의 Z80 기계가 4MHz였는데 TRS-80은 **1.77MHz**뿐이었다.

| 단계                         | 시간           |
| ---------------------------- | -------------- |
| “Are you an animal?” 입력 후 | 25초           |
| `N` 출력 후                  | 20초           |
| `O` 출력 후                  | 23초           |
| **두 글자 답변까지 총합**    | **약 1분 9초** |

그리고 더 긴 답변은 비례해서 더 걸릴 것이라고 덧붙이며 이렇게 맺었다.
“잘한다는 것이 놀라운 게 아니라, **한다는 것 자체가 놀랍다**.”

이 수치가 README의 서술과 충돌하지는 않는다. 4MHz면 두 배 이상 빠를 것이다.
그러나 **문자당 10만 번의 곱셈-누산**이라는 README 자신의 서술에서 이 결과는 충분히 예측 가능했고, 그것을 독자가 직접 재 보고 나서야 알게 된다는 점이 문제다.

README에 “문자 하나에 N초”라는 한 줄이 있었다면 독자가 이것을 무엇에 쓸 수 있는지 훨씬 빨리 판단했을 것이다.

이 공백이 실질적인 결과도 낳았다. gp2000이 **약 9배 빠른 Z80 네트워크 평가 코드**를 직접 짜서 포크에 올렸고, 10% 정도 더 개선할 수 있을 것 같다고 적었다.[^gp2000]
성능 수치가 공개되어 있었다면 이 최적화가 더 일찍 나왔을 수 있다.

### 메모리 모델이 실제 8비트 기계와 어긋난다

플랫폼 지원 목록이 CP/M과 ZX Spectrum 48K인데, 두 경우 모두 **평탄한 64KB 주소 공간**을 전제한다.

그런데 실제 Z80 기계의 상당수가 그렇지 않다.

a_t48이 이 문제를 구체적으로 짚었다.[^a_t48]
게임보이 카트리지에는 들어가겠지만 **뱅크 스위칭 때문에 돌리기 아주 끔찍할 수 있다**는 것이다. 각 뱅크가 16K뿐이고, 여러 개를 가질 수 있지만 한 번에 하나(기술적으로는 항상 접근 가능한 뱅크 0까지 둘)만 쓸 수 있다.

anonzzzies도 MSX와 ZX와 Amstrad CPC를 다수 갖고 있고 멀티프로세서 Z80 CP/M 기계까지 있다면서, **뱅크 스위칭에서 얼마나 험할지 궁금하며 아마 좋지 않을 것**이라고 적었다.[^anonzzzies]

이것이 사소한 지적이 아니다.

40KB 가중치를 문자마다 10만 번 순회하는 구조에서 뱅크 경계를 넘을 때마다 뱅크 전환 비용이 붙는다.
접근 패턴이 순차적이라면 견딜 만하지만, 층 사이를 오가며 임의 접근한다면 감당하기 어렵다.

README가 “여러 Z80 기반 플랫폼에서 돈다”고 말할 때 그 목록이 평탄 주소 공간 기계로만 이루어져 있다는 사실은 적혀 있지 않다.

### 가중치에서 비밀을 추출할 수 있는가에 대한 답이 없다

vedmakk가 흥미로운 질문을 던졌다.[^vedmakk]

실제 비밀(예를 들어 암호 구절)을 이런 모델에 학습시켜 사용자가 올바른 질문을 던져 알아내야 하게 만든다면, **가중치에 접근할 수 있는 사람이 그 비밀을 쉽게 역공학으로 알아낼 수 있는가**, 아니면 올바른 질문을 통해서만 도달할 수 있다고 가정해도 되는가라는 것이다.

`guess` 예제가 정확히 그 구조이므로 실제적인 질문이다.

ronsor의 답이 명료했다. **이 정도로 작은 네트워크라면 가능하며, 더 일반적으로는 해석 가능성(interpretability)의 영역**이라는 것이다.[^ronsor]

Kiboneu는 다른 층위의 참고 문헌을 들었다. 탐지 불가능한 백도어를 머신러닝 모델에 심는 방법을 다룬 논문이다.[^Kiboneu]

이 교환이 남기는 함의가 있다.

모델이 작을수록 **비밀을 숨기기 어렵다**.
파라미터가 적으면 각 파라미터가 하는 일이 특정되기 쉽고, 출력 공간이 좁으면 전수 탐색도 가능하다.

`guess` 예제는 게임이므로 문제가 되지 않는다.
그러나 “작은 모델이라 안전하다”는 직관이 정반대라는 점은 온디바이스 모델 전반에 적용되는 이야기다.
[Needle](needle.md) 같은 모델을 제품에 넣을 때 그 안에 든 것이 무엇이든 **기기에 배포하는 순간 읽힐 수 있다고 가정해야 한다.**

## 인사이트

### 이 프로젝트가 증명한 것은 작음이 아니라 방법의 시차다

이 저장소를 보는 흔한 방식은 “얼마나 작게 갈 수 있는가”의 기록으로 읽는 것이다. README 자신이 그렇게 프레임을 잡는다.

그런데 HN 반응의 상당수가 다른 것에 반응했다.

rahen이 60년대 하드웨어에서도 됐을 것이고 **세상과 공상과학을 바꿨을 것**이라고 적은 것, noosphr이 “가지 않은 길”이라고 부른 것, gcanyon이 ELIZA가 훨씬 유능할 수 있었을 것이라고 한 것이 전부 같은 감각이다.

그 감각의 정체는 이렇다.
이 결과를 막고 있던 것은 하드웨어가 아니라 **우리가 아직 모르던 방법**이었다.

역전파는 1970년대에 이미 있었고 1986년에 널리 알려졌다. 양자화 인식 학습은 훨씬 나중이다.
Z80은 1976년에 나왔다. 즉 **하드웨어가 방법보다 먼저 있었고, 그 간격이 수십 년이었다**.

여기서 끌어낼 수 있는 일반화가 있다.
어떤 기술이 지금 불가능해 보일 때, 그것이 자원 부족 때문인지 방법 부재 때문인지 구분해야 한다.
전자는 기다리면 해결되고 **후자는 기다려도 해결되지 않는다**.

그리고 사후에 보면 둘은 잘 구분되지 않는다. 방법이 없던 시기의 사람들도 “하드웨어가 부족하다”고 말했기 때문이다.

그래서 이런 레트로 이식 프로젝트의 진짜 가치는 향수가 아니다.
**과거의 제약이 실제로 무엇이었는지를 사후에 측정하는 실험**이다.
40KB가 충분했다는 것이 밝혀졌다면, 당시의 병목은 메모리가 아니었다.

### 자원 절약의 대조군으로 쓰이는 것이 이 프로젝트의 또 다른 쓸모다

andrepd의 한 줄이 이 스레드에서 가장 많이 공감을 받은 종류의 반응이었다.
**Slack이나 Teams나 Jira 엔지니어가 텍스트 채팅이 시작하는 데 왜 1.5GB RAM이 필요한지 설명하려 할 때마다 이것을 보여 줘야 한다**는 것이다.[^andrepd]

농담이지만 여기에 실질이 있다.

소프트웨어 비대화를 비판할 때 가장 약한 지점이 **“그럼 얼마면 되는데”에 답하지 못한다는 것**이다.
비교 대상이 없으면 1.5GB가 많은지 적은지 말할 수 없고, 논쟁은 취향 싸움이 된다.

40KB에 추론과 가중치와 UI가 다 들어간 바이너리는 그 논쟁에 **절대적 하한**을 제공한다.
물론 기능이 전혀 다르므로 직접 비교는 성립하지 않는다. 하지만 하한이 있다는 것만으로 논의의 성격이 바뀐다.

jacquesm이 그 방향을 정확히 제안했다. 같은 원리를 노트북에 적용해 **1메가바이트 정도를 쓰게 하면 무엇이 되는지 보자**는 것이다.[^jacquesm]

이것이 실제로 흥미로운 질문이다.
Z80의 40KB에서 128버킷 트라이그램과 3층 MLP가 나왔다면, 1MB에서는 무엇이 나오는가.
[Needle이 8~29MB](needle.md)에서 도구 호출을 하고 있으니 그 사이 어딘가에 답이 있다.

일반화하면 이렇다.
극단적인 제약 아래의 구현은 그 자체로 유용하지 않아도 **척도를 만든다**.
그리고 척도가 있으면 “이 정도면 충분한가”라는 질문을 비로소 할 수 있게 된다.

vatary가 이 프로젝트를 LLM 압축과 실행의 스트레스 테스트로 읽으면서 **당장 실용적 쓸모는 많지 않지만 IoT 기기에 내장 LLM이 곧 올 것임을 보여 준다**고 정리한 것도 같은 맥락이다.[^vatary]
acosmism이 이것을 **“임신 테스트기에서 둠 돌리기” 같은 순간**이라고 부른 것도 그렇다.[^acosmism]
그런 프로젝트들의 공통점은 결과물이 아니라 **경계를 옮겨 놓았다는 사실**이 남는다는 것이다.

### 작은 모델의 질문은 “얼마나 똑똑한가”에서 “어디에 붙일 것인가”로 옮겨 간다

giancarlostoro가 던진 질문이 이 스레드에서 가장 진지한 것이었다.[^giancarlostoro]

간단한 대화를 할 수 있는 **“최소 실행 가능 LLM”**이 무엇인지 궁금하며, 다음 질문은 외부에서 데이터를 찾아보며 배우게 얼마나 밀어붙일 수 있는지, **아주 작은 모델에 터무니없이 큰 컨텍스트 창을 붙일 수 있는지**라는 것이다.
그리고 말하고 즉석에서 배우는 초소형 모델을 만들 수 있다면 Siri 같은 개인 비서를 완전히 로컬화한 셈이 된다고 정리했다.

andy12_가 이것이 Karpathy의 **“인지 코어(cognitive core)”** 아이디어와 매우 비슷하다고 답했다. 백과사전적 지식이 거의 0이고 기본적인 추론과 도구 사용 능력만 갖춘 극소형 모델이라는 것이다.[^andy12_]

이 교환이 온디바이스 모델 논의의 축이 어디로 옮겨 가고 있는지를 보여 준다.

Z80-μLM은 지식이 0이다. 트라이그램 버킷에 반응하는 분류기이므로 애초에 담을 자리가 없다.
[Needle](needle.md)도 세계 지식을 포기했고, 대신 인자를 **요청에서 복사**한다.

둘의 공통 전략이 같다. **모르는 것을 바깥에서 가져오고, 모델은 형태만 맡는다.**

그렇다면 작은 모델의 성능 질문이 달라진다.
“이 모델이 무엇을 아는가”가 아니라 **“이 모델이 무엇에 연결되어 있는가”**다.

그리고 이 축에서 Z80-μLM의 한계가 분명해진다. 연결할 것이 없다.
`guess` 예제가 게임인 이유도 그것이다. 외부 상태가 없는 폐쇄된 문제라야 이 크기로 완결된다.

MagicMoonlight가 원한 것 — **NPC마다 이런 작은 모델이 하나씩 있어서 실제로 말을 걸 수 있는 게임** — 이 정확히 이 조건에 맞는 응용이다.[^MagicMoonlight]
게임 안의 NPC는 알아야 할 세계가 좁고, 틀려도 손해가 없으며, 개성이 정확성보다 중요하다.

GN에서 crawler가 남긴 반응도 같은 방향의 상상이다.
최신 기술을 과거 하드웨어에서 돌린다는 것이 신기하다면서, **미래에 AGI가 나왔을 때 지금 지구에 있는 컴퓨팅 파워를 모두 모으면 돌릴 수 있을지** 궁금하다고 적었다.[^crawler]

이 질문이 이 프로젝트를 거꾸로 세운 것이라 흥미롭다.
Z80-μLM은 “가장 작은 하드웨어에 얼마나 큰 것을 넣을 수 있는가”를 물었고, crawler는 “가장 큰 하드웨어로 얼마나 먼 것에 닿을 수 있는가”를 물은 셈이다.

두 질문의 답이 같은 형태일 가능성이 있다.
한계를 정하는 것은 자원의 총량이 아니라 **그 자원으로 무엇을 하는지 아는가**다.
1976년에 40KB는 충분했고 방법이 없었다. 지금 우리에게 부족한 것이 무엇인지는 나중에야 알게 될 것이다.
