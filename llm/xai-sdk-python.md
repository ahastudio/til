# xai-sdk-python: gRPC 위에 올린 공식 Python SDK

<https://github.com/xai-org/xai-sdk-python>

HN 토론: <https://news.ycombinator.com/item?id=44471131> (2점, 0개 댓글)

## 소개

xAI API를 위한 공식 Python SDK다. gRPC 기반 라이브러리이며 Python 3.10 이상을 요구하고, 동기 클라이언트와 비동기 클라이언트를 모두 제공한다.
스타 575개, 포크 190개, 열린 이슈 46개다. 2025년 6월 9일에 만들어졌고 마지막 푸시는 2026년 8월 18일이다. 라이선스는 Apache-2.0이다.

gRPC를 쓴다는 점이 이 SDK의 가장 큰 특징이다.
대부분의 LLM SDK가 REST와 JSON 위에 올라가 있는데, 이 SDK는 프로토콜 버퍼와 gRPC를 쓴다.
그래서 오류가 HTTP 상태 코드가 아니라 gRPC 상태 코드로 오고, 재시도와 타임아웃이 라이브러리 자체 로직이 아니라 gRPC 채널 옵션으로 설정된다.
이 사실을 모르고 쓰면 예외 타입부터 낯설다.

```bash
pip install xai-sdk
# 또는
uv add xai-sdk
```

## 클라이언트 만들기

기본적으로 `XAI_API_KEY` 환경 변수를 찾는다. 설정되어 있으면 인자 없이 만들 수 있다.

```python
from xai_sdk import Client, AsyncClient

sync_client = Client()
async_client = AsyncClient()
```

명시적으로 넘기려면 `python-dotenv`로 `.env`에서 읽는 방식을 README가 권한다.

```python
import os
from dotenv import load_dotenv
from xai_sdk import Client, AsyncClient

load_dotenv()

api_key = os.getenv("XAI_API_KEY")
sync_client = Client(api_key=api_key)
async_client = AsyncClient(api_key=api_key)
```

동기와 비동기의 차이가 클래스 이름 하나뿐이라는 점이 이 SDK의 설계 원칙이다. 나머지 호출 모양은 같다.

## 대화 상태를 클라이언트가 들고 있다

이 SDK에서 가장 특징적인 API가 `chat` 객체다.
README가 밝히듯 하부 API는 여전히 무상태(stateless)인데, `append`로 메시지 이력을 쌓고 `sample`로 응답을 받는 방식으로 상태 관리를 감쌌다.

```python
from xai_sdk import Client
from xai_sdk.chat import system, user

client = Client()
chat = client.chat.create(
    model="grok-4.6",
    messages=[system("You are a pirate assistant.")]
)

while True:
    prompt = input("You: ")
    if prompt.lower() == "exit":
        break
    chat.append(user(prompt))      # 사용자 발화를 이력에 넣는다
    response = chat.sample()       # 이력 전체로 한 번 호출한다
    print(f"Grok: {response.content}")
    chat.append(response)          # 응답도 직접 이력에 넣어야 한다
```

마지막 줄이 중요하다. 응답을 `append`하지 않으면 다음 턴의 컨텍스트에서 모델의 직전 발화가 사라진다.
`sample`이 이력을 자동으로 갱신하지 않는다는 뜻이며, 상태 관리를 감쌌지만 절반만 감쌌다는 것이 이 설계의 정확한 성격이다.

비동기는 `AsyncClient`로 바꾸면 된다.

## 주요 기능

`examples/` 아래에 동기용 `sync/`와 비동기용 `aio/`가 같은 파일 이름으로 나란히 있다.

| 기능               | 예제 파일                | 요점                                                      |
| ------------------ | ------------------------ | --------------------------------------------------------- |
| 함수 호출          | `function_calling.py`    | 도구를 정의하고 모델이 호출하게 한다                      |
| 이미지 생성        | `image_generation.py`    | 이미지 생성 모델 사용                                     |
| 이미지 이해        | `image_understanding.py` | 비전 모델로 이미지 분석                                   |
| 비디오 생성        | `video_generation.py`    | `grok-imagine-video`로 텍스트·이미지·참조 이미지에서 생성 |
| 비디오 확장        | `video_extension.py`     | 기존 영상을 프롬프트로 이어 붙인다                        |
| 구조화된 출력      | `structured_outputs.py`  | Pydantic 모델로 응답을 받는다                             |
| 추론 모델          | `reasoning.py`           | 노력 수준을 설정할 수 있다                                |
| 지연 채팅          | `deferred_chat.py`       | 오래 도는 응답을 폴링으로 받는다                          |
| 토크나이저         | `tokenizer.py`           | 토크나이저 API                                            |
| 모델 정보          | `models.py`              | 이름, 별칭, 토큰 가격, 최대 프롬프트 길이 등              |
| 에이전틱 도구 호출 | `server_side_tools.py`   | Grok이 웹·𝕏 검색이나 코드 실행을 스스로 판단해 쓴다       |
| 텔레메트리         | `telemetry.py`           | OpenTelemetry 트레이스를 콘솔이나 OTLP로 내보낸다         |

`models.py`가 실무에서 특히 유용하다. 토큰 가격과 최대 프롬프트 길이를 API로 조회할 수 있으므로, 모델 이름을 코드에 고정하지 않고 런타임에 확인할 수 있다.

에이전틱 도구 호출은 서버 쪽에서 돈다. README의 예시가 명확하다. 아스날의 최근 경기 결과를 물으면 웹 검색이 자동으로 발동된다.
즉 도구 실행 루프를 클라이언트가 돌리지 않고 서버가 돌린다는 뜻이며, 이 경우 응답 시간이 길어지므로 뒤에 나오는 타임아웃 값이 그 사정을 설명한다.

## 값 정하기

| 값                    | 기본값        | 근거와 조정 기준                                                           |
| --------------------- | ------------- | -------------------------------------------------------------------------- |
| `timeout`             | 1620초(27분)  | 서버 쪽 에이전틱 실행과 영상 생성을 감당하려는 값. 채팅만 쓰면 크게 줄인다 |
| 재시도 최대 횟수      | 5             | `UNAVAILABLE`에만 적용된다                                                 |
| 초기 백오프           | 0.1초         | 첫 재시도까지의 대기                                                       |
| 최대 백오프           | 1초           | 상한이 낮아 5회가 1초 남짓에 끝난다                                        |
| 백오프 배수           | 2             | 0.1 → 0.2 → 0.4 → 0.8 → 1(상한)                                            |
| 재시도 대상 상태 코드 | `UNAVAILABLE` | `RESOURCE_EXHAUSTED`는 기본에 없다                                         |

타임아웃은 클라이언트 단위로만 설정된다. 개별 RPC나 메서드마다 지정하는 것은 현재 불가능하다고 README가 명시한다.

```python
from xai_sdk import Client

sync_client = Client(timeout=300)   # 5분
```

타임아웃이 걸리면 동기 클라이언트는 `grpc.RpcError`, 비동기는 `grpc.aio.AioRpcError`를 던지며 상태 코드는 `grpc.StatusCode.DEADLINE_EXCEEDED`다.

재시도를 끄려면 채널 옵션을 쓴다.

```python
from xai_sdk import Client

sync_client = Client(channel_options=[("grpc.enable_retries", 0)])
```

정책을 직접 정하려면 gRPC 서비스 설정 JSON을 넘긴다.

```python
import json
from xai_sdk import Client

custom_retry_policy = json.dumps({
    "methodConfig": [{
        "name": [{}],                 # 모든 메서드에 적용
        "retryPolicy": {
            "maxAttempts": 3,         # 시도 횟수를 줄인다
            "initialBackoff": "0.5s", # 첫 대기를 늘린다
            "maxBackoff": "2s",       # 상한을 늘린다
            "backoffMultiplier": 1.5, # 증가를 완만하게
            "retryableStatusCodes": ["UNAVAILABLE", "RESOURCE_EXHAUSTED"],
        },
    }]
})

sync_client = Client(channel_options=[("grpc.service_config", custom_retry_policy)])
```

이 예시에서 눈여겨볼 것은 `retryableStatusCodes`에 `RESOURCE_EXHAUSTED`를 추가한 부분이다.
기본 정책은 속도 제한을 재시도하지 않는다. 속도 제한에 걸리는 워크로드라면 이 설정이 사실상 필수다.

## 오류 코드

gRPC 상태 코드가 그대로 오므로, HTTP 코드에 익숙한 사람은 대응 표를 알아 두어야 한다.

| gRPC 상태 코드       | xAI API 맥락                                        |
| -------------------- | --------------------------------------------------- |
| `INVALID_ARGUMENT`   | 잘못된 인자나 형식이 어긋난 입력                    |
| `DEADLINE_EXCEEDED`  | 클라이언트 타임아웃 초과                            |
| `NOT_FOUND`          | 요청한 모델이나 리소스가 없음                       |
| `PERMISSION_DENIED`  | 키가 비활성·차단되었거나 해당 모델·기능 권한이 없음 |
| `UNAUTHENTICATED`    | 키가 없거나 잘못되었거나 만료됨                     |
| `RESOURCE_EXHAUSTED` | 사용 할당량이나 속도 제한 초과                      |
| `INTERNAL`           | xAI 쪽 내부 서버 오류                               |
| `UNAVAILABLE`        | 일시적 장애나 연결 문제. 기본 재시도 대상           |
| `DATA_LOSS`          | URL로 넘긴 이미지를 서버가 가져오지 못한 경우       |

마지막 줄이 특히 알아 두어야 할 항목이다.
`DATA_LOSS`는 보통 복구 불가능한 데이터 손실을 뜻하는 코드인데, 여기서는 사용자가 URL로 준 이미지를 서버가 가져오지 못했을 때 난다.
이름만 보고는 짐작할 수 없는 대응이므로, 이미지를 URL로 넘기는 코드에서 이 코드를 만나면 손상이 아니라 이미지 접근 실패를 의심해야 한다.

`PERMISSION_DENIED`와 `UNAUTHENTICATED`를 구분해 두는 것도 중요하다. 전자는 키가 유효하지만 권한이 없는 것이고 후자는 키 자체가 문제다.

## 텔레메트리

OpenTelemetry 트레이스를 콘솔이나 OTLP 호환 백엔드로 내보낼 수 있다. 기본은 꺼져 있고 코드에서 명시적으로 설정해야 켜진다.

```python
from xai_sdk.telemetry import Telemetry

telemetry = Telemetry()
telemetry.setup_console_exporter()   # 개발용: JSON으로 콘솔에 출력
```

켜면 API 호출마다 스팬이 생기고, 입력 프롬프트와 모델 응답과 토큰 사용량 통계가 속성으로 붙는다.
속성은 대체로 OpenTelemetry GenAI 시맨틱 컨벤션을 따르므로 Langfuse 같은 백엔드가 구조화해 보여 줄 수 있고, 대응 표준이 없는 경우에는 SDK 자체 속성을 덧붙인다고 밝힌다.

환경 변수 두 개가 중요하다.

| 환경 변수                                        | 효과                                                 |
| ------------------------------------------------ | ---------------------------------------------------- |
| `XAI_SDK_DISABLE_TRACING`                        | `1` 또는 `true`면 이 SDK의 트레이스만 끈다           |
| `XAI_SDK_DISABLE_SENSITIVE_TELEMETRY_ATTRIBUTES` | 트레이스는 수집하되 메시지·프롬프트·응답 내용은 뺀다 |

두 번째가 실무에서 자주 필요하다. 트레이스를 보려면 프롬프트와 응답이 관측 백엔드로 나가는데, 그것이 곧 사용자 데이터가 제3자 시스템에 저장된다는 뜻이기 때문이다.
이 변수를 쓰면 토큰 사용량과 지연 같은 지표는 유지하면서 내용은 남기지 않는다.

## 트레이드오프

### gRPC를 고른 결정

gRPC는 이 SDK의 성격을 거의 전부 결정한다.

얻는 것은 세 가지다.
하나는 스트리밍이 프로토콜 수준에서 지원되므로 SSE 파싱 같은 층이 필요 없다는 것이다.
둘은 재시도와 타임아웃이 채널 옵션이므로 표준화된 방식으로 설정되고, gRPC 서비스 설정 JSON이라는 기존 형식을 그대로 쓸 수 있다는 것이다.
셋은 스키마가 프로토콜 버퍼로 정의되므로 타입이 생성된다는 것이다. README가 하부 proto 객체에 접근하는 방법을 별도 절로 안내하는 것도 그래서다.

대가는 생태계 밖에 놓인다는 것이다.
OpenAI 호환 REST 인터페이스를 전제하는 도구와 프록시와 라이브러리가 지금 대다수인데, 그쪽과 바로 맞물리지 않는다.
브라우저에서 직접 호출할 수도 없고, 표준 HTTP 프록시나 방화벽 정책 아래에서 문제가 생길 수 있으며, `curl`로 눈으로 확인하는 방식이 통하지 않는다.

여기서 빠져나갈 길은 있지만 비용이 있다. xAI가 OpenAI 호환 REST 엔드포인트를 따로 제공하므로 그쪽을 쓰면 되지만, 그러면 이 SDK의 이점을 포기하는 것이다.
그리고 두 경로가 항상 같은 기능을 지원한다는 보장이 없으므로, 어느 쪽을 쓸지는 필요한 기능이 어디에 있느냐로 결정된다.

### 27분이라는 기본 타임아웃

1620초라는 기본값은 HTTP 클라이언트 기준으로 보면 터무니없이 길다. 보통 30초에서 60초를 쓴다.

이 값이 필요한 이유는 이 API가 무엇을 하는지에 있다.
영상 생성과 확장은 원래 오래 걸리고, 에이전틱 도구 호출은 서버가 웹 검색과 코드 실행을 여러 번 돌 수 있다.
그런 호출에 60초 타임아웃을 걸면 정상 작업이 끊긴다. 가장 오래 걸리는 용도를 기준으로 기본값을 잡은 것이다.

대가는 그 외 모든 용도에서 위험한 기본값이 된다는 것이다.
채팅 한 번을 부르는 코드가 27분간 매달려 있을 수 있고, 그 사이 스레드나 연결이 점유된다.
그리고 개별 RPC마다 타임아웃을 지정할 수 없다는 제약이 이 문제를 키운다. 같은 클라이언트로 채팅과 영상 생성을 모두 하려면 둘 중 하나에 맞지 않는 값을 골라야 한다.

실질적인 절충은 클라이언트를 용도별로 두는 것이다. 채팅용 짧은 타임아웃 클라이언트와 생성용 긴 타임아웃 클라이언트를 따로 만드는 것이며, 클라이언트 생성이 싸다면 이것이 가장 단순한 해법이다.

### 상태 관리를 절반만 감싼 `chat` 객체

`chat.append`와 `chat.sample`은 무상태 API 위에 이력을 얹는다. 편리하지만 경계가 애매하다.

편리한 쪽은 분명하다. 메시지 배열을 직접 관리하지 않아도 되고, 다중 턴 루프가 몇 줄로 끝난다.
애매한 쪽은 `sample`이 응답을 이력에 넣지 않는다는 점이다. 호출자가 `chat.append(response)`를 직접 해야 한다.

이 설계에는 이유가 있다. 응답을 이력에 넣을지 말지가 상황에 따라 다르기 때문이다.
여러 후보를 뽑아 하나만 고르는 경우, 응답을 검증한 뒤 버리는 경우, 재생성하는 경우에 자동으로 넣으면 이력이 오염된다.

그러나 기본 사용 경로에서 한 줄을 빠뜨리면 조용히 잘못 도는 결과가 나온다.
오류가 나지 않고 그냥 모델이 자기 직전 발화를 기억하지 못하는 상태가 되므로, 원인을 찾기 어려운 종류의 버그다.
`sample`이 넣고 넣지 않으려면 명시적으로 끄게 하는 쪽이 안전했겠지만, 그러면 이번엔 끄는 것을 잊는 실수가 생긴다. 어느 쪽이든 한쪽 실수는 남는다.

### 기본 재시도가 속도 제한을 다루지 않는다

기본 정책은 `UNAVAILABLE`만 재시도한다. `RESOURCE_EXHAUSTED`는 대상이 아니다.

이 선택이 옳은 이유가 있다. 속도 제한을 즉시 재시도하면 제한을 더 악화시키고, 적절한 대기 시간은 서버가 알려 주는 값에 따라야 한다.
그리고 0.1초에서 1초 사이의 백오프는 속도 제한 창을 넘기기에 턱없이 짧다. 그 정책으로 재시도하면 다섯 번 모두 실패하고 1초쯤 낭비한다.

대가는 사용자가 그 사실을 알아야 한다는 것이다.
속도 제한에 걸리는 워크로드에서 아무 설정도 하지 않으면 예외가 그대로 올라오고, README의 커스텀 정책 예시를 읽지 않은 사람은 SDK가 재시도해 준다고 믿고 있을 수 있다.
그리고 커스텀 정책으로 `RESOURCE_EXHAUSTED`를 추가하더라도 백오프 상한이 초 단위라면 제대로 대기하지 못한다. 속도 제한은 애플리케이션 수준에서 다뤄야 하는 문제로 남는다.

## 함정

기본 타임아웃이 27분이라는 것을 모르면 장애가 멈춤으로 나타난다. 프로덕션에 올리기 전에 용도에 맞는 값으로 바꾸는 편이 안전하다.

`chat.append(response)`를 빠뜨리면 다중 턴 대화에서 모델이 자기 직전 응답을 기억하지 못한다. 오류가 나지 않으므로 증상만 보고는 원인을 찾기 어렵다.

예외 타입이 `grpc.RpcError`와 `grpc.aio.AioRpcError`다. HTTP 예외를 잡는 기존 오류 처리 코드가 이것을 놓친다.

`DATA_LOSS`는 이미지 URL 가져오기 실패를 뜻한다. 이름과 실제 원인이 어긋나는 유일한 항목이다.

텔레메트리를 켜면 프롬프트와 응답 내용이 관측 백엔드로 나간다. `XAI_SDK_DISABLE_SENSITIVE_TELEMETRY_ATTRIBUTES`를 먼저 검토해야 한다.

버전 정책에 예외가 명시되어 있다. 주 버전에만 호환성 파괴를 두려 하지만 라이브러리 내부 구조에 대한 비호환 변경이 마이너나 패치에서 일어날 수 있다는 것이다.
하부 proto 객체에 직접 접근하는 코드는 이 예외의 대상이므로, 마이너 업데이트마다 릴리스 노트를 확인하라고 README가 권한다.

Python 3.10 이상이 필요하다.

## 확인하기

키 없이도 SDK 설치와 임포트는 확인할 수 있고, 키가 있으면 가장 싼 호출부터 시작한다.

```python
import xai_sdk
print(xai_sdk.__version__)

from xai_sdk import Client

client = Client(timeout=30)          # 기본 27분을 먼저 줄여 둔다
for m in client.models.list_language_models():
    print(m.name, m.aliases, m.max_prompt_length)
```

모델 목록 조회는 토큰을 쓰지 않으면서 인증과 연결을 동시에 확인한다.
그리고 반환값에 토큰 가격과 최대 프롬프트 길이가 들어 있으므로, 코드에 고정해 둔 모델 이름이 아직 유효한지와 비용 가정이 맞는지를 한 번에 점검할 수 있다.

오류 처리를 시험하려면 일부러 잘못된 모델 이름을 넣어 본다.

```python
import grpc
from xai_sdk import Client
from xai_sdk.chat import user

client = Client(timeout=30)
try:
    chat = client.chat.create(model="grok-does-not-exist", messages=[user("hi")])
    chat.sample()
except grpc.RpcError as e:
    print(e.code(), e.details())     # NOT_FOUND 를 확인한다
```

이 코드가 실제로 `grpc.RpcError`를 잡는지 확인하는 것이, 기존 오류 처리 코드를 고쳐야 하는지 판단하는 가장 빠른 방법이다.

## 체크리스트

- 기본 타임아웃 27분을 용도에 맞게 바꿨는가
- 채팅과 영상 생성처럼 소요 시간이 다른 호출을 같은 클라이언트로 쓰고 있지 않은가
- 다중 턴 루프에서 응답을 `chat.append`로 이력에 넣고 있는가
- 오류 처리가 `grpc.RpcError`와 `grpc.aio.AioRpcError`를 잡는가
- 속도 제한이 예상되는 워크로드라면 `RESOURCE_EXHAUSTED` 대응을 애플리케이션 수준에 두었는가
- 텔레메트리를 켠다면 민감 속성 비활성화 여부를 정했는가
- 하부 proto 객체에 접근하는 코드가 있다면 마이너 업데이트의 릴리스 노트를 확인하는가

## 비평

### REST를 쓰는 세계에서 gRPC SDK를 유지하는 부담이 사용자에게 넘어간다

이 SDK는 잘 만들어져 있다. 재시도와 타임아웃과 텔레메트리와 오류 코드를 문서에 정리해 둔 수준이 같은 종류의 라이브러리 중 상위에 든다.
문제는 그 설계가 주변 생태계와 맞물리지 않는다는 점이다.

지금 LLM 도구 생태계의 사실상 표준은 OpenAI 호환 REST다.
프록시, 게이트웨이, 관측 도구, 비용 추적기, 라우터, 캐시 계층이 그 인터페이스를 전제하고 만들어져 있다.
gRPC를 쓰면 그 층 전부를 쓸 수 없거나 별도 어댑터가 필요하다.

그래서 이 SDK를 고르는 결정은 라이브러리 선택이 아니라 아키텍처 결정이 된다.
영상 생성이나 서버 쪽 에이전틱 도구 호출처럼 이 SDK에만 있는 기능이 필요하다면 감당할 만하지만, 채팅만 쓴다면 OpenAI 호환 경로가 거의 항상 낫다.
README는 이 비교를 하지 않는다. gRPC 기반이라는 사실을 첫 문단에 적어 두지만, 그것이 무엇을 포기하는 선택인지는 독자가 알아내야 한다.

### 기본값들이 서로 다른 사용자를 가정한다

기본 타임아웃 27분은 영상 생성을 하는 사용자를 가정한다.
기본 재시도 정책의 1초 상한은 짧은 채팅 호출을 하는 사용자를 가정한다.
두 기본값이 같은 클라이언트에 들어 있다.

이 불일치가 드러나는 지점이 있다. 27분짜리 호출이 `UNAVAILABLE`로 실패하면 0.1초 뒤에 재시도하고, 그 재시도도 27분을 기다릴 수 있다.
다섯 번 시도하면 최악의 경우 두 시간이 넘는데, 백오프 총합은 1초 남짓이므로 재시도 정책은 이 시나리오를 전혀 고려하지 않은 값이다.

더 근본적인 문제는 개별 RPC 타임아웃을 지정할 수 없다는 제약이다.
README가 현재 불가능하다고 명시했으므로 알고 있는 한계이지만, 그 한계 때문에 사용자는 클라이언트를 여러 개 만드는 우회를 해야 한다.
그리고 그 우회 방법이 문서에 없다. 타임아웃 절은 값을 바꾸는 방법만 알려 주고, 용도가 섞였을 때 어떻게 하라는 안내는 하지 않는다.

### 상태 없는 API에 상태 있는 객체를 얹으면 경계를 문서화해야 한다

`chat` 객체의 설계 자체는 합리적이다. 하부 API가 무상태라는 사실을 README가 분명히 밝힌 것도 좋다.
그런데 그 경계에서 사용자가 책임지는 부분이 예제 코드의 마지막 한 줄로만 표현되어 있다.

`chat.append(response)`가 왜 필요한지, 넣지 않으면 어떻게 되는지, 어떤 경우에 일부러 넣지 않는지가 문서에 없다.
예제를 그대로 복사하는 사람은 문제가 없지만, 루프를 자기 구조에 맞게 고치는 사람은 그 줄을 빠뜨릴 수 있다.

이 종류의 실수가 위험한 이유는 실패가 조용하다는 것이다.
모델은 여전히 답하고 응답 형식도 정상이며, 다만 대화가 이어지지 않는다. 테스트로 잡기도 어렵다. 한 턴만 시험하면 통과하기 때문이다.

문서가 해야 할 일은 실수했을 때의 증상을 적어 두는 것이다.
모델이 직전 대화를 기억하지 못하는 것처럼 보이면 응답을 이력에 넣었는지 확인하라는 한 문장이 있으면, 이 버그를 겪는 사람의 시간이 크게 줄어든다.

## 기억할 원칙

### 기본값은 가장 흔한 용도에 맞추고, 극단적 용도는 문서로 안내한다

이 SDK의 27분 기본 타임아웃은 기본값 설정의 어려움을 잘 보여 주는 사례다.
가장 오래 걸리는 용도를 감당하게 잡으면 그 외 모든 용도에서 위험하고, 흔한 용도에 맞추면 긴 작업이 끊긴다.

원칙은 실패의 성질로 정하는 것이다.
값이 너무 작아 실패하면 오류가 나서 즉시 드러나고, 원인도 명확하며 고치는 방법도 문서에서 찾기 쉽다.
값이 너무 커서 실패하면 멈춤으로 나타나고, 자원이 조용히 점유되며, 프로덕션에서야 드러난다.

그러니 기본값은 시끄럽게 실패하는 쪽으로 잡고, 조용한 실패가 필요한 용도는 문서로 끌어올리는 편이 낫다.
이 SDK라면 기본을 60초쯤에 두고 영상 생성 예제 첫 줄에 타임아웃을 크게 준 클라이언트를 보여 주는 형태다.
지금 구조는 그 반대이며, 그 결과로 영상 생성을 하지 않는 대다수 사용자가 위험한 기본값을 물려받는다.

같은 원칙이 재시도에도 적용된다. 재시도 대상에서 `RESOURCE_EXHAUSTED`를 뺀 것은 조용히 상황을 악화시키지 않겠다는 선택이며, 방향이 옳다.
기본값을 정할 때 물어야 할 질문은 무엇이 가장 편리한가가 아니라, 틀렸을 때 어느 쪽이 더 빨리 드러나는가다.
