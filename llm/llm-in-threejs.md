# Three-LLM: 렌더링 라이브러리 Three.js로 브라우저에서 LLM 추론 그래프를 돌리다

원문: [Running LLMs in the Browser with Three.js](https://ben3d.ca/blog/running-llms-in-the-browser-with-threejs)

HN 토론: <https://news.ycombinator.com/item?id=49552740> (1점, 0개 댓글)

## 요약

Ben Houston이 2026년 9월 3일에 쓴 17분 분량의 글이다.
Three-LLM은 GPT-2, SmolLM2, Qwen, Phi 모델의 추론 그래프를 WebGPU 위의 Three.js TSL(Three.js Shading Language) 컴퓨트 셰이더로 바꿔 브라우저에서 로컬로 돌린다.
데모는 three-llm.ben3d.ca에 있고, npm 패키지 `three-llm`과 GitHub 소스가 공개되어 있다.

저자가 이 프로젝트로 시험하려던 것은 두 가지다.
Three.js와 WebGPU의 범용 연산 능력을 어디까지 밀어붙일 수 있는지, 그리고 오늘날의 작은 언어 모델이 브라우저에서 무엇을 할 수 있는지다.
Three.js는 렌더링 라이브러리로 알려져 있지만 WebGPU 렌더러는 스토리지 버퍼, 컴퓨트 디스패치, 워크그룹 메모리, 아토믹, GPU 읽기를 모두 노출한다.
언어 모델은 수백 번의 순서 있는 디스패치, 큰 행렬-벡터 곱, 리덕션, 지속되는 어텐션 상태나 순환 상태, 새 토큰마다 GPU와 JavaScript 사이를 오가는 좁은 루프를 요구하므로 이 기능을 전부 쓴다.

Three-LLM은 Hugging Face의 `config.json`, 토크나이저 파일, SafeTensors 체크포인트를 브라우저에서 그대로 읽는다.
재사용 가능한 TSL 컴퓨트 커널로 모델을 조립하고 사용자의 GPU에서 추론하며, 서버 쪽 추론 런타임도 모델별 WebAssembly 바이너리도 필요 없다.
검증용 CPU 참조 구현과 실사용용 GPU 구현이 함께 들어 있고, GPT-2, Llama 계열, Gemma 3, Phi, Qwen3.5 구조를 인식한다.
데모에서 고를 수 있는 체크포인트는 TinyStories GPT-2 3M, GPT-2 124M, SmolLM2 135M, Qwen3.5 0.8B, Phi-1.5 1.3B의 다섯 개다.
모델 파일은 15MB에서 2.8GB까지이고, Three-LLM이 가중치를 32비트 부동소수점으로 펼치기 전 크기다.
휴대폰에서는 TinyStories나 SmolLM2만 쓰라고 권하며, Qwen과 Phi는 메모리가 부족해 많은 모바일 기기에서 불러오지 못한다.

## 동작 방식

### 토큰 하나를 만드는 루프

LLM이 토큰 하나를 만드는 과정은 여섯 단계다.
토크나이저가 텍스트를 정수 토큰 ID 열로 바꾸고, 임베딩 표가 각 ID를 벡터로 바꾼다.
트랜스포머 블록 더미가 현재 토큰과 앞선 문맥으로 그 벡터를 갱신하고, 마지막 행렬 투영이 어휘의 모든 토큰에 로짓 하나씩을 낸다.
샘플링 규칙이 그중 하나를 고르고, 모델은 그 토큰을 붙여 다시 돈다.

주어진 프롬프트를 처리하는 단계가 프리필이고, 이어서 토큰을 하나씩 만드는 단계가 디코드다.
같은 모델을 쓰지만 성능 특성이 다르다.
프리필은 알려진 입력 토큰이 많아 한꺼번에 처리할 수 있고, 디코드는 한 단계에 새 토큰이 하나뿐이면서 모델 가중치 대부분을 매번 다시 읽어야 한다.

### 모델을 TSL 커널로 표현하기

Three-LLM은 모델 연산 하나하나를 작은 TSL 컴퓨트 커널로 표현하고, 러너가 모델 레시피가 요구하는 순서로 연결한다.
기본 부품은 행렬-벡터 곱의 `TSLLinear`, 정규화의 `TSLNormalize`와 `TSLRMSNorm`, 인과 어텐션의 `TSLAttention`, 피드포워드의 `TSLMLP`와 `TSLGatedMLP`, 잔차 연결의 `TSLAdd`, GPU에서 어휘 로짓을 줄이는 `TSLLogitSampler`다.

선형 계층은 GPU 호출 하나가 출력 원소 하나를 맡아 입력 벡터를 따라 도는 가장 단순한 형태로 쓰였다.
저자는 연산이 보이도록 일부러 평범하게 두었다고 밝힌다.
브라우저에서 읽을 수 있는 연산자를 만들면 TSL이 WebGPU 백엔드용 WGSL을 생성하며, 모델 컴파일러가 타일링된 행렬 커널을 미리 고르는 대신 이 일을 런타임에 한다.

GPU 어텐션은 계층마다 네 단계로 돈다.
새 키와 값을 캐시에 쓰고, 쿼리를 준비하고, 헤드와 캐시된 토큰마다 스케일된 쿼리-키 점수를 하나씩 계산하고, 안정된 소프트맥스로 캐시된 값들을 섞는다.
CPU 러너가 같은 연산을 TypeScript로 수행하며, 브라우저 체크포인트 테스트가 다섯 모델 모두에서 탐욕적 GPU 출력과 CPU 참조를 비교한다.
셰이더가 오류 없이 돌면서도 미묘하게 틀린 텍스트를 낼 수 있기 때문에 이 참조 경로가 필수였다고 저자는 적는다.

### 체크포인트를 런타임에 읽기

설정 파일이 레시피를 고르고, 레시피가 그래프 계열, 정규화, MLP 종류, 잔차 배치, 위치 인코딩, 헤드 수, 체크포인트 배치를 기술한다.
텐서 이름 별칭이 GPT-2의 `transformer.h.0.attn.c_attn.weight`나 Llama의 `model.layers.0.self_attn.q_proj.weight` 같은 이름을 러너가 기대하는 공통 필드로 연결한다.
그래서 오프라인 변환 단계 없이 모델 저자가 공개한 체크포인트를 그대로 쓴다.

### 모델 계열마다 다른 것

SmolLM2 135M은 매개변수 수는 GPT-2와 비슷하지만 Llama 계열 디코더 패턴을 쓴다.
평균을 빼지 않는 RMSNorm, 학습된 위치 벡터를 더하는 대신 쿼리와 키를 회전시키는 RoPE, 쿼리 헤드 여러 개가 더 적은 키·값 헤드를 공유해 KV 캐시를 줄이는 GQA, GPT-2의 GELU MLP를 대신하는 SwiGLU가 달라진 점이며, Three-LLM은 이것들을 별도 러너 없이 레시피 플래그와 재사용 커널로 처리한다.

Phi-1.5 1.3B는 쿼리와 키의 일부만 회전시키는 부분 RoPE를 쓰고, 어텐션과 MLP 가지를 같은 정규화 입력에서 병렬로 돌린다.
레시피에 `residual: 'parallel'`이 있으면 러너가 이 분기 그래프를 만든다.

Qwen3.5 0.8B가 가장 복잡하다.
Three-LLM은 텍스트 백본만 돌리고 비전 텐서는 건너뛴다.
이 모델은 게이트된 완전 어텐션 계층 하나마다 Gated DeltaNet 계층 셋을 두는 혼합 구조다.
완전 어텐션 계층은 KV 캐시를 유지해 특정한 앞 토큰을 찾을 수 있고, Gated DeltaNet 계층은 늘어나는 기록 대신 고정 크기의 순환 상태를 써서 토큰이 늘어도 메모리가 일정하다.
학습된 감쇠 게이트가 옛 상태가 얼마나 남을지 정하고, 델타 갱신이 현재 키에 대한 연결을 새 값 쪽으로 고친다.
Qwen은 전용 러너와 순환 상태 관리와 DeltaNet TSL 커널 전체를 따로 가졌고, 주변의 잔차와 게이트 MLP 구조는 다른 계열과 같은 연산자를 다시 쓴다.

## 효과가 있었던 최적화

저자가 측정한 이득의 대부분은 몇 가지 변경에서 나왔다.

| 변경                                 | 효과                                                         |
| ------------------------------------ | ------------------------------------------------------------ |
| 순전파 한 번을 한 번에 제출          | TinyStories 디코드 초당 약 120 → 566토큰, SmolLM2 약 34 → 75 |
| 쓰지 않는 프롬프트 로짓을 계산 안 함 | SmolLM2 첫 토큰까지 시간 약 760ms → 260ms (제출 변경과 합산) |
| 프롬프트 접두사 재사용               | 대화의 앞부분을 다시 프리필하지 않음                         |
| GPU에서 샘플링 리덕션                | 탐욕적 생성은 토큰 ID 4바이트만 읽음                         |
| GPU가 가중치를 잡은 뒤 CPU 사본 해제 | 대형 체크포인트 로딩 중 메모리 중복 제거                     |

첫 번째가 가장 컸다.
SmolLM2는 토큰 하나에 400번이 넘는 컴퓨트 디스패치를 실행하는데, 처음 구현은 디스패치마다 따로 제출했다.
순서 있는 노드들을 Three.js 컴퓨트 호출 하나에 기록하자 427번의 명령 제출이 한 번으로 줄었고, TinyStories가 4.7배, SmolLM2가 2.2배 빨라졌다.
작은 모델에서는 JavaScript에서 WebGPU로의 제출 오버헤드가 시간을 지배하고 있었다.
GPU는 여전히 디스패치마다 파이프라인을 바꾸고 중간 버퍼를 읽으므로, 셰이더를 합치는 것은 별개의 최적화다.

프롬프트의 마지막 토큰만 어휘 로짓이 필요하다.
앞 토큰들은 어텐션 캐시나 순환 상태만 갱신하면 되므로, 49,152개 토큰 어휘로 모두 투영하는 것은 결과를 버리는 일이다.
Three-LLM은 마지막 정규화와 어휘 투영 없이 프리필 경로를 기록하고 마지막 토큰에만 로짓을 계산한다.

측정으로 기각된 최적화도 있다.
공유 워크그룹 정규화와 넓은 `vec4` 행렬-벡터 커널은 대표적인 SmolLM2 처리량을 개선하지 못해, 복잡도만 늘리는 것으로 보고 빼 버렸다.

## 트레이드오프

### FP32 하나로 통일한 대가

Three-LLM은 모든 GPU 커널을 32비트 부동소수점 저장과 연산으로 돌린다.
체크포인트가 FP16이나 BF16으로 와도 임베딩이 아닌 텐서는 `Float32Array`로 펼치고, KV 캐시, 활성값, 로짓, Qwen의 순환 상태도 모두 FP32다.
WebGPU 어댑터 전반에서 하나의 단순한 기준선을 주는 대신 메모리와 대역폭 비용이 크다.
SmolLM2의 269MB BF16 체크포인트는 GPU 가중치로 대략 두 배가 되고, Qwen의 1.7GB와 Phi의 2.8GB 체크포인트에서는 문제가 훨씬 두드러진다.
자기회귀 디코드는 토큰마다 그 가중치 대부분을 다시 읽으므로, 저장 형식의 크기가 곧 속도의 천장이 된다.

이 선택이 어려운 이유는 반대편 선택지들이 모두 조건부이기 때문이다.
FP16은 WGSL `f16` 확장과 WebGPU `shader-f16` 기능이 있는 GPU에서만 되고, 양자화는 4개의 8비트 정수 쌍을 한 번에 곱하는 `packed_4x8_integer_dot_product` 확장 위에 가중치 형식, 블록별 스케일, 어댑터 기능 탐지, 역양자화 비용을 고려한 커널을 모두 따로 설계해야 한다.
저자는 두 확장을 TSL로 노출하는 작업을 하고 있다고 밝히지만, 어느 쪽을 택하든 “모든 어댑터에서 같은 결과”라는 FP32의 단순함은 잃는다.

### 런타임 조립과 사전 컴파일

비슷한 조건의 SmolLM2-135M 시험에서 FP32로 펼친 기본 체크포인트의 Three-LLM은 초당 약 78토큰, 양자화하지 않은 FP32 Instruct 체크포인트의 WebLLM은 약 80토큰이었다.
디코드만 보면 거의 같지만, 프롬프트 프리필과 더 큰 양자화 모델에서는 격차가 훨씬 컸다.
WebLLM은 모델별 커널을 미리 컴파일하고, 프리필과 디코드 프로그램을 따로 두며, 낮은 정밀도나 양자화된 가중치를 배포한다.
Three-LLM은 평범한 Hugging Face 체크포인트를 받아 일반 연산자를 런타임에 조립한다.

얻는 것은 범용성이다.
새 모델이 나와도 레시피와 텐서 이름 별칭만 있으면 오프라인 변환 없이 돌릴 수 있다.
잃는 것은 모델별 최적화다.
타일링된 행렬 커널, 합쳐진 셰이더, 배치된 프리필은 모두 특정 모델의 모양을 미리 알 때 쉽게 만들 수 있다.
두 설계는 서로 다른 목표를 최적화한다는 저자의 말은 공정하지만, 그 목표 중 하나가 사용자가 체감하는 속도라는 점에서 어느 쪽이 더 많이 쓰일지는 분명하다.

## 함정

### 셰이더는 오류 없이 틀린다

저자가 CPU 참조 구현을 필수라고 부른 이유가 가장 중요한 교훈이다.
GPU 커널은 인덱스를 잘못 계산하거나 정규화를 한 번 빠뜨려도 예외를 던지지 않고, 그럴듯하지만 미묘하게 틀린 텍스트를 낸다.
언어 모델의 출력은 원래 확률적이므로, 사람이 읽어서는 버그와 모델의 한계를 구별하기 어렵다.
탐욕적 디코딩으로 GPU와 CPU의 출력을 토큰 단위로 맞춰 보는 테스트가 없었다면, 이 프로젝트는 “돌긴 도는” 상태에서 멈췄을 것이다.

### 작은 모델의 병목은 GPU가 아니다

제출 횟수를 줄였더니 TinyStories가 4.7배 빨라졌다는 결과는, 작은 모델에서는 GPU 연산이 아니라 JavaScript와 WebGPU 사이의 명령 제출이 시간을 먹는다는 뜻이다.
직관적으로는 커널을 빠르게 만드는 데 먼저 손이 가지만, 이 경우 커널 최적화는 거의 효과가 없었을 것이다.
실제로 `vec4` 커널과 공유 워크그룹 정규화가 효과를 내지 못했다.
모델 크기가 커지면 병목은 다시 메모리 대역폭으로 옮겨 가므로, 어떤 최적화가 통하는지는 모델 크기와 함께 다시 재야 한다.

### 모바일에서는 불러오는 것부터 실패한다

Qwen과 Phi는 FP32로 펼치면 GPU 메모리에 수 GB가 필요하고, 많은 모바일 기기에서는 불러오기 단계에서 실패한다.
데스크톱에서 잘 도는 데모가 휴대폰에서 아무 말 없이 멈추는 경험은 사용자에게 버그로 보인다.
대형 파일을 여러 동시 요청으로 나눠 받는 프록시와 CPU 사본 해제가 도움이 되지만, FP32라는 기본 선택이 바뀌지 않는 한 모바일의 한계는 남는다.

## 비평

### “렌더러로 LLM을 돌린다”는 성과는 목적이 흐려진 시험이다

저자는 이 프로젝트를 Three.js 연산 능력의 시험이자 쓸 만한 추론 라이브러리로 소개한다.
두 목적은 서로 당긴다.
시험으로서는 성공이다.
토큰화부터 체크포인트 로딩, 여러 트랜스포머 계열, 순환 선형 어텐션, GPU 샘플링, 프롬프트 캐시까지 Three.js만으로 해냈다는 것은 TSL의 범용성을 강하게 보여 준다.

그러나 라이브러리로서는 비교 대상이 이미 있다.
WebLLM이 같은 규모에서 디코드는 비슷하고 프리필과 큰 모델에서는 앞선다면, 사용자가 Three-LLM을 고를 이유는 “이미 Three.js를 쓰고 있다”는 것뿐이다.
저자가 마지막에 같은 WebGPU 렌더러가 장면을 그리고 그 장면을 설명하는 언어 모델도 돌릴 수 있다고 쓴 것이 사실상 이 라이브러리의 자리를 말해 준다.
3D 장면과 언어 모델을 한 GPU 컨텍스트에서 함께 돌려야 하는 응용이 이 라이브러리의 과녁이고, 그 과녁은 좁다.

### 성능 비교가 한 모델 한 조건에 머문다

WebLLM과의 비교는 SmolLM2-135M 하나에서, “거의 맞춘” 조건으로 이루어졌다.
Three-LLM은 기본 체크포인트를, WebLLM은 Instruct 체크포인트를 썼다.
프리필과 큰 양자화 모델에서 격차가 “훨씬 컸다”고만 적고 숫자를 주지 않는다.
어느 GPU에서 쟀는지도 나오지 않는다.

이 정도 비교로는 독자가 자기 응용에 어느 쪽이 맞는지 판단할 수 없다.
디코드가 비슷하다는 한 줄은 인상적이지만, 사용자가 실제로 기다리는 시간은 대개 첫 토큰까지의 시간이고 그것은 프리필이 정한다.
가장 불리한 숫자를 빼고 가장 유리한 숫자만 남긴 인상을 주는 것은, 공정하게 쓰려 한 저자의 태도와 어울리지 않는다.

## 기억할 원칙

### 참조 구현 없는 GPU 코드는 검증되지 않은 코드다

확률적 출력을 내는 시스템을 GPU로 옮길 때는, 같은 연산을 느리지만 확실한 방식으로 수행하는 참조 구현을 먼저 만들고 결정적인 설정에서 출력을 비교해야 한다.
출력이 “그럴듯한지”로는 아무것도 알 수 없다.
이 원칙은 LLM 추론에만 해당하지 않고, 수치 계산을 가속기로 옮기는 모든 작업에 해당한다.

### 최적화의 순서는 측정이 정한다

이 글에서 가장 큰 이득은 커널이 아니라 명령 제출 횟수에서 나왔고, 그럴듯한 커널 최적화 두 개는 측정에서 기각됐다.
어디가 느린지는 추측이 아니라 측정으로 찾아야 하며, 병목은 모델 크기와 하드웨어에 따라 옮겨 다닌다.
효과가 없는 최적화를 빼 버린 저자의 선택이, 효과가 있는 최적화를 넣은 것만큼 중요하다.
