# xAI Cookbook: 노트북 여섯 개와 베타 테스팅 라이선스

<https://github.com/xai-org/xai-cookbook>

## 소개

xAI의 Grok API를 기초부터 고급까지 안내하는 실용 예제 모음이다.
스타 579개, 포크 193개, 열린 이슈 30개이고 주 언어는 TypeScript로 분류된다.
2025년 2월 23일에 만들어졌고 마지막 푸시는 2026년 4월 16일이다.

라이선스가 표준 오픈소스 라이선스가 아니다. Beta Testing License라는 이름의 자체 문서이며, GitHub도 이를 인식하지 못해 라이선스 식별자가 비어 있다.

실제로 제공되는 노트북은 `registry.yaml`에 등록된 여섯 개다.

| 제목                                                          | 경로                                              | 날짜       | 태그                                                |
| ------------------------------------------------------------- | ------------------------------------------------- | ---------- | --------------------------------------------------- |
| Seeing the World Through Language: Object Detection with Grok | `examples/multimodal/object_detection/`           | 2025-03-03 | vision, object-detection, multi-modal               |
| Extracting Structured Data from Fashion Images with Grok      | `examples/multimodal/structured_data_extraction/` | 2025-03-03 | vision, structured-outputs, multi-modal, e-commerce |
| Building a Unified Chat Experience with Grok                  | `examples/multi_turn_conversation/`               | 2025-04-07 | multi-turn, chatbot, streaming, function-calling    |
| Real Time Sentiment Analysis with Grok & 𝕏                    | `examples/sentiment_analysis_on_x/`               | 2025-04-10 | sentiment-analysis, real-time, reasoning            |

저자는 대부분 Omar Diab이고 Function Calling 101만 Zhaohan Dong이다.
저장소 루트에는 `Android`와 `iOS`, `voice-examples` 디렉터리도 있어서 노트북 밖의 예제가 별도로 존재한다.

모든 노트북은 셀 출력이 그대로 보존되어 있어, 직접 돌리지 않고 읽기만 해도 따라갈 수 있다고 README가 밝힌다.

## 설정하기

의존성 관리는 `uv`를 쓴다.

```bash
git clone https://github.com/xai-org/xai-cookbook.git
cd xai-cookbook

uv sync                      # 가상환경 생성과 의존성 설치
uv run pre-commit install    # 훅 설치
git lfs install              # 대용량 데이터 파일 추적용

cp .env.example .env         # 여기에 API 키를 넣는다
uv run jupyter notebook examples/
```

API 키는 [xAI Console](https://console.x.ai)에서 발급한다.
VS Code의 노트북 확장을 쓰려면 인터프리터를 `uv sync`가 만든 `.venv`로 지정하면 된다.

노트북에서 키를 읽는 방식도 README가 지정한다.

```python
from dotenv import load_dotenv
import os

load_dotenv()
XAI_API_KEY = os.getenv("XAI_API_KEY")
```

절대 키를 하드코딩하지 말라는 경고가 굵은 글씨로 붙어 있고, 개발 중에도 그렇게 하지 말라고 못 붙인다. 실수로 커밋될 위험 때문이다.

## 안전장치 세 겹

이 저장소가 예제 모음치고 공들인 부분이 키 유출 방지다.

첫째, `.env` 파일이 `.gitignore`에 들어 있어 커밋되지 않는다.
둘째, Gitleaks를 쓰는 pre-commit 훅이 API 키가 실수로 커밋되는 것을 막는다. 다만 완벽하지 않으므로 키를 커밋했다면 즉시 콘솔에서 폐기하고 새로 발급하라고 적어 둔다.
셋째, 노트북이 처음부터 끝까지 오류 없이 도는지 검증하는 pre-commit 훅이 따로 있다.

두 번째 훅과 세 번째 훅의 성격이 다르다는 점이 중요하다.
Gitleaks는 정적 검사이므로 공짜지만, 노트북 전체 실행 검증은 API를 실제로 호출하므로 크레딧을 쓴다.
README도 그 사정을 인정하며, 노트북이 xAI API를 자주 호출한다면 개발 중에는 `git commit --no-verify`로 훅을 건너뛰는 것이 크레딧을 아끼는 데 도움이 된다고 안내한다.
그러면서 PR을 올리기 전이나 열린 PR의 리뷰에 응답하기 전에는 적어도 한 번 훅을 켠 상태로 돌려 보라고 권한다.

특정 파일만 골라 훅을 돌리는 방법도 제시한다.

```bash
uv run pre-commit run --files examples/your_notebook.ipynb
```

## 트레이드오프

### 노트북 실행을 CI 대신 pre-commit에 둔 선택

노트북이 끝까지 도는지 검증하는 일은 본래 CI가 할 일이다. 그런데 이 저장소는 그것을 커밋 훅에 두었다.

이 선택이 얻는 것은 비용의 위치다. API 호출 비용이 저장소 소유자가 아니라 기여자의 크레딧에서 나간다.
외부 기여를 받는 예제 저장소에서 각 기여자가 자기 키로 자기 노트북을 검증하는 구조는 합리적이다. CI에 조직 키를 넣으면 PR 하나가 크레딧을 태울 수 있기 때문이다.

대가는 검증이 선택적이 된다는 것이다.
README가 직접 건너뛰는 방법과 그 정당한 이유를 안내하므로, 실제로 건너뛴 커밋이 들어올 가능성이 높다.
그리고 건너뛴 상태로 머지되면 그 노트북이 도는지 아무도 모르는 상태가 된다.

여기서 빠져나갈 길이 좁다. CI로 옮기면 비용이 조직에 몰리고, 훅에 두면 강제가 안 된다.
현실적인 절충은 머지 전에 유지보수자가 한 번 돌리는 것인데, 그 절차가 `CONTRIBUTING.md`에 있는지는 확인해야 한다.
그리고 이미 머지된 노트북이 지금도 도는지는 아무 장치도 보장하지 않는다. 노트북 날짜가 전부 2025년 1~4월이라는 사실이 그 문제의 크기를 알려 준다.

### 출력을 보존한 노트북

셀 출력을 남겨 두어 실행 없이 읽을 수 있게 한 것은 예제 저장소로서 옳은 선택이다.
API 키가 없는 사람, 크레딧을 쓰기 싫은 사람, 그냥 결과가 어떤 모양인지만 보려는 사람이 대부분이기 때문이다.

대가는 두 가지다.
하나는 저장소가 커진다는 것이고, 이미지가 포함된 멀티모달 예제 때문에 Git LFS를 도입한 것이 그 결과다.
다른 하나는 출력이 낡는다는 것이다. 보존된 출력은 2025년의 모델이 낸 응답이므로, 지금 같은 코드를 돌리면 다른 결과가 나온다.

이 두 번째가 더 성가시다. 코드가 낡으면 오류가 나서 알 수 있지만, 출력이 낡으면 그냥 다른 답일 뿐이라 알아차리기 어렵다.
읽기만 하는 독자는 보존된 출력을 현재 모델의 성능으로 오인할 수 있고, 그 오인은 어느 방향으로든 갈 수 있다.

### 라이선스가 아닌 라이선스

`LICENSE` 파일은 Beta Testing License라는 제목을 달고 있고 본문은 MIT와 거의 같다. 사용, 복사, 수정, 병합, 공개, 배포, 서브라이선스, 판매를 제한 없이 허용한다.
그런데 두 조항이 덧붙어 있다.

2번 조항은 베타 면책이다. 이 소프트웨어가 사전 공개 베타 형태이고 최종 제품이 아니며 버그와 오류와 미완성 기능을 포함할 수 있고 오직 테스트와 평가 목적으로만 제공된다는 것이다.
3번 조항은 지원 없음이다. 어떤 지원도 유지보수도 업데이트도 제공되지 않으며 사용은 전적으로 사용자 책임이라는 것이다.

이 두 조항이 실무에 닿는 부분은 오직 평가 목적이라는 문구다.
문자 그대로 읽으면 이 예제 코드를 프로덕션에 가져다 쓰는 것이 허용 범위 밖으로 보이는데, 권한 부여 문단은 제한 없이 허용한다고 적혀 있다. 두 부분이 서로 긴장한다.

같은 조직의 다른 저장소가 Apache-2.0이나 AGPL-3.0 같은 표준 라이선스를 쓴 것과 비교하면 이 선택은 의도적으로 보인다.
예제 코드에 법적 책임을 지지 않겠다는 뜻으로는 이해되지만, 그 목적이라면 표준 라이선스의 면책 조항으로도 충분하다.
결과적으로 얻은 것은 GitHub가 라이선스를 식별하지 못하는 상태이며, 사내 법무 검토가 필요한 조직에서는 이것이 그대로 마찰이 된다.

## 함정

노트북 날짜가 전부 2025년 1월부터 4월 사이다. 저장소 푸시는 2026년 4월까지 있지만 등록된 예제는 1년 이상 갱신되지 않았다.
그 사이 Grok 모델은 4와 4.1과 4.5 계열로 여러 번 바뀌었고, 예제가 지정하는 모델 이름이 지금도 유효한지 확인해야 한다.

열린 이슈가 30개다. 지원하지 않는다고 라이선스에 명시한 저장소이므로 이슈에 답이 오기를 기대하기 어렵다.

주 언어가 TypeScript로 분류되는데 README의 설정 절차는 전부 Python이다.
`Android`와 `iOS` 디렉터리가 그 불일치의 원인으로 보이며, 그 예제들에 대한 안내는 README에 없다.

Git LFS가 필요하다. 설치하지 않은 상태로 클론하면 대용량 파일이 포인터 텍스트로 받아지고, 멀티모달 예제가 이유를 알기 어려운 오류를 낸다.

`--no-verify`로 훅을 건너뛰는 것이 README에서 권장되므로, 이 저장소의 커밋 이력에 검증되지 않은 노트북이 섞여 있을 수 있다.

## 확인하기

API 키를 쓰기 전에 무엇이 들어 있는지부터 보는 편이 낫다.

```bash
git clone https://github.com/xai-org/xai-cookbook.git && cd xai-cookbook

# 등록된 예제 목록과 날짜를 한눈에 본다
grep -E '^- title|^  date' registry.yaml

# 예제가 어떤 모델 이름을 쓰는지 센다
grep -rho '"grok-[a-z0-9.-]*"' examples/ | sort | uniq -c
```

두 번째 명령이 핵심이다. 예제에 적혀 있는 모델 이름이 현재 API에서 유효한 것인지가 이 저장소를 쓸 수 있는지를 결정하고, 그 확인에는 키가 필요하지 않다.

키를 넣은 뒤에는 가장 짧은 예제부터 돌린다.

```bash
uv run pre-commit run --files examples/function_calling_101/guide.ipynb
```

`Function Calling 101`이 가장 오래된 동시에 가장 단순한 예제이므로, 이것이 도는지가 환경 설정이 맞는지에 대한 가장 싼 시험이다.

## 체크리스트

- Git LFS를 설치한 뒤에 클론했는가
- `.env`에 키를 넣었고 노트북에 하드코딩하지 않았는가
- 예제가 지정하는 모델 이름이 현재 API에서 유효한지 확인했는가
- 보존된 셀 출력이 2025년 모델의 응답이라는 점을 감안해 읽고 있는가
- Beta Testing License의 평가 목적 문구를 조직 기준으로 검토했는가
- 훅을 건너뛰고 커밋할 경우 PR 전에 최소 한 번은 켠 상태로 돌렸는가

## 비평

### 쿡북이라는 이름에 비해 요리법이 적다

여섯 개는 쿡북으로서 적다. 그리고 그 여섯 개의 주제 분포가 균일하지 않다.
멀티모달이 둘, 함수 호출이 둘(하나는 다중 턴 예제 안에 포함), 나머지가 X 감정 분석과 하이퍼 개인화 마케팅이다.

주제 선정이 이 회사의 차별점을 겨냥한다는 점은 이해할 만하다.
X 실시간 감정 분석은 다른 곳이 못 하는 것이고, 그것이 Grok API의 판매 논거다.
문제는 그것이 API를 처음 쓰는 사람에게 필요한 순서가 아니라는 점이다.

처음 쓰는 사람이 필요한 것은 오류 처리와 재시도, 속도 제한 대응, 토큰 계산과 비용 추정, 스트리밍 중단 처리, 구조화된 출력의 스키마 검증 실패 같은 것들이다.
이 목록 중 어느 것도 별도 예제로 있지 않다. 다중 턴 예제에 스트리밍과 구조화된 출력이 함께 들어가 있을 뿐이다.

그래서 이 저장소는 무엇이 가능한지를 보여 주는 쇼케이스이고, 실무에서 무엇이 어려운지를 다루는 쿡북은 아니다.
두 종류를 한 저장소가 다 할 필요는 없지만, 이름이 후자를 약속한다는 점에서 기대가 어긋난다.

### 지원하지 않겠다는 선언과 기여를 받겠다는 초대가 충돌한다

`CONTRIBUTING.md`가 있고 README가 노트북을 추가하고 싶으면 PR을 보내라고 초대한다.
같은 저장소의 라이선스는 어떤 지원도 유지보수도 업데이트도 제공되지 않는다고 적는다.

두 문서가 다른 것을 말하는 셈이다. 기여를 받는다는 것은 리뷰하고 머지한다는 뜻이고, 그것이 곧 유지보수다.
열린 이슈 30개와 1년 넘게 갱신되지 않은 예제 목록을 보면 실제로 어느 쪽이 지켜졌는지가 짐작된다.

이 불일치가 기여자에게 비용을 만든다.
노트북을 쓰고 훅을 돌리고 크레딧을 태워 검증한 뒤 PR을 올렸는데 답이 오지 않는 상황이 그것이다.
그리고 README가 열린 PR의 리뷰에 응답하기 전에 훅을 켜고 돌려 보라고 안내한다는 점이, 리뷰가 실제로 돌아가던 시기가 있었음을 짐작하게 만든다.

정직한 조치는 둘 중 하나다. 리뷰할 사람을 두거나, 기여를 닫고 아카이브로 표시하는 것이다.
같은 조직의 Grok Build 저장소가 외부 기여를 받지 않는다고 못 붙인 것과 비교하면, 이 저장소는 그 명확함이 없다.

### 키 유출 방지에 들인 공이 다른 곳에는 없다

이 저장소에서 가장 잘 설계된 부분이 API 키 보호다. `.gitignore`와 Gitleaks 훅과 `.gitleaks.toml`과 `SECURITY.md`까지 갖추고, 유출 시 즉시 폐기하라는 안내까지 있다.
예제 저장소에서 이 정도로 신경 쓴 곳은 드물다.

그런데 같은 수준의 주의가 다른 실패 모드에는 없다.
예제가 낡았는지 알려 주는 장치가 없고, 모델 이름이 폐기되었을 때 알려 주는 것도 없고, 보존된 출력이 언제 만들어진 것인지 노트북 안에 적혀 있지도 않다.

이 편중이 시사하는 바가 있다. 키 유출은 회사에게도 사고이고 사용자에게도 사고다. 낡은 예제는 사용자에게만 비용이다.
어느 쪽에 자동화된 방어가 붙었는지를 보면 그 저장소가 실제로 무엇을 지키려 했는지가 드러난다.

이것이 비난받을 일은 아니다. 다만 이 저장소를 쓰는 사람은 자기가 방어되지 않는 쪽의 위험을 스스로 감당해야 한다는 뜻이며, 앞의 확인하기 절에서 모델 이름부터 세어 보라고 적은 이유가 그것이다.

## 기억할 원칙

### 예제 저장소의 수명은 실행 검증을 누가 언제 하느냐로 정해진다

예제 코드는 쓰인 순간부터 낡기 시작하고, 낡았다는 사실은 누군가 돌려 보지 않으면 드러나지 않는다.
이 저장소는 그 검증을 기여자의 커밋 훅에 두었고, 그래서 기여가 멈춘 시점에 검증도 멈췄다.

여기서 나오는 규칙은 단순하다. 예제를 공개할 때 정해야 할 것은 예제의 내용이 아니라 그것을 언제 누가 다시 돌릴 것인지다.
비용이 드는 검증이라면 주기를 낮춰서라도 정기적으로 도는 자리에 두어야 하며, 커밋 훅은 그 자리가 아니다. 커밋이 없으면 돌지 않기 때문이다.

비용이 문제라면 규모를 줄이는 것이 답이다.
예제 여섯 개를 매달 한 번 돌리는 비용은 크지 않고, 그 결과를 배지로 노출하면 읽는 사람이 신뢰 여부를 판단할 수 있다.
반대로 검증할 계획이 없다면 작성 날짜와 그때의 모델 이름을 노트북 첫 셀에 적어 두는 것만으로도 많은 오인을 막는다.

이 저장소의 `registry.yaml`이 그 절반을 이미 하고 있다. 각 예제의 날짜가 거기 적혀 있기 때문이다.
남은 절반은 그 날짜를 노트북 안으로, 그리고 마지막으로 성공적으로 실행된 날짜로 바꾸는 일이다.
