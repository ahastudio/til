# PostHog의 의사결정 모델 활용

원문: [Not everything needs an LLM](https://newsletter.posthog.com/p/decision-models)

HN 토론: <https://news.ycombinator.com/item?id=50535740> (180점, 74개 댓글)

GN 토론: <https://news.hada.io/topic?id=37415>

## 요약

PostHog 뉴스레터에 Jina Yoon이 2026년 11월 9일 쓴 글(부제 「우리가 의사결정 모델을 쓰는 방법」)이다.
글은 의사결정 모델(decision model)이 「그때그때 다르다」는 장문의 답 대신 확률이 붙은 형식화된 답을 돌려준다고 설명하고 PostHog의 실험을 바탕으로 쓰는 때와 방법과 실수를 다룬다.
도구로는 TypeSafe AI의 「Jev」를 든다.
글이 링크한 TypeSafe의 블로그와 문서, 풀 리퀘스트, 저장소는 열지 못했다.
댓글 12개는 읽지 못했다.
수치와 모델 이름은 글에 나온 그대로이다.

설명의 예는 「고슴도치는 포유류인가?」에 「예, 0.99」, 「고슴도치의 보전 상태는?」에 「Least Concern, 0.77」이다. 보정된 모델의 0.8 답은 약 80%가 맞고 0.5는 동전 던지기라고 한다. 의사결정 모델은 최대 444.6배 저렴하고 193.6배 빠르다고 TypeSafe의 블로그를 인용한다.

글의 네 가지 용도와 요점은 다음과 같다.

- 비싼 LLM 호출의 문지기: PostHog의 세션 녹화 요약기(Replay Vision)는 개인정보를 두 질문 문지기로 거른다. 「실제 사람의 이름이 있는가」와 「연락처나 ID가 보이는가」를 묻고 둘 중 하나가 0.4 이상이면 Gemini가 요약을 다시 쓰고 다시 검사한다. 좁은 질문으로 나누자 하나의 넓은 질문일 때 거짓 경보가 약 10분의 1이 되었고 프로덕션에서 요약의 98.7%가 LLM 호출을 건너뛴다. 0.85점도 1,000번 중 약 150번은 틀리므로 거짓 음성이 비싼 곳(개인정보 저장)에서는 임계값을 낮게(0.4) 두고, 거짓 양성이 비싼 곳(Slack 봇이 태그 없는 질문에 답하는 경우)에서는 두 검사가 모두 0.85 이상일 때만 답한다.
- 모델 라우터: Slack 봇이 모델을 지정하지 않은 요청에 `choice` 질문 하나로 후보를 고른다. 지시문은 첫 시도에 일을 끝낼 가능성이 높은 가장 싼 선택지를 고르라는 것이고 실패한 실행이 더 똑똑한 선택지보다 비싸다고 덧붙인다. 후보는 상대 비용으로 Claude Sonnet 5.5(1배), Claude Opus 5.5(2배), Claude Fable 5.1(5배), GPT-6 Luna(0.05배), GPT-6 Sol(1배), GPT-6 Astra(5배)이다. 임계값은 작업과 모델마다 다르므로 오류 추적의 로그 병합 판정기는 v1과 v2 사이에 임계값을 바꿨고 프로젝트별로 나눠 수작업 라벨 데이터로 재보정하며 그림자 모드로 돌렸다. 그래서 모델을 바꾸고 시험하는 사내 AI 게이트웨이도 만들었다.
- 액면 검사: 맥락이 필요하거나 여러 단계 추론이 필요한 질문에는 약하다. 입력을 평평하게 만들어 액면으로 확인할 수 있을 때 쓴다. 세션 검색에서 임베딩으로 가까운 관찰 20개를 뽑고 결과마다 「이 요약이 검색이 찾는 세션과 맞는가」를 물어 예(yes) 확률로 다시 정렬했고 시험 질의 20개에서 순위 품질이 약 25% 좋아졌다. 반대로 「이 세션이 볼 만한가」에 이어 「왜」를 연쇄로 묻는 하이라이트 기능은 한 시간마다 세션 32개를 보내 요청이 모델 서버를 막아 다른 제품의 호출을 몇 시간 막았다.
- 과한 LLM 대신: SQL 결과에 차트를 고르는 규칙(날짜와 숫자 열이면 선 그래프 등)을 의사결정 모델로 바꿨다. 예는 브라우저별 페이지뷰로, 옛 규칙은 합계 선 그래프를, 의사결정 모델은 브라우저로 나눈 묶음 막대 그래프를 골랐다. 반대로 사내 PR 리뷰 에이전트의 발견을 다섯 개 좁은 질문으로 순위 매기는 시도는 AUC 0.52로 결론이 없었다. Jev는 큰 요청을 받지 못하고 긴 문맥 모드는 느리고 덜 정확하다(기본 요청당 64k 토큰, 질문당 32k, 옵트인으로 262k).
- 하이브리드: PostHog의 AI 연구 팀이 만든 Jeeves가 불확실할 때 판단 전에 추론하며, 모델을 지정하지 않은 PostHog의 의사결정 호출의 기본값이다. 이와 비슷한 다른 개발자의 프로젝트도 있다고 소개한다.
- 마무리 문장은 이 글이 두 달 안에 낡을 것이라 예상한다는 필자 표기이다.

## 분석

### 중심 주장은 LLM과 정규식 사이에 판정 모델 층이 있다는 것이다

글의 결론은 의사결정 모델이 LLM에는 너무 단순하고 정규식에는 너무 모호한 입력에 맞는다는 것이다. 문지기, 라우터, 액면 검사, 규칙 대체의 네 용도가 모두 「하나의 입력에 대한 한 번의 판정」이라는 공통점을 가진다. 이는 글의 서술을 이 문서가 정리한 것이다.

### 임계값과 비용을 한 번에 설계한다

글이 반복하는 점은 임계값이 어느 실수가 더 비싼지로 정해진다는 것이다. 이는 분류기를 운영하는 일반 원칙을 사례로 보여 준다.

### 실패한 시도를 같이 적는다

연쇄 추론이 서버를 막은 사례와 AUC 0.52의 실패를 적어 적용 범위의 경계를 구체로 보여 준다. 이는 이 문서의 관찰이다.

## 비평

### 근거가 PostHog 내부 사례이고 도구는 파트너의 것이다

444.6배와 193.6배는 TypeSafe의 수치를 인용한 것이다.
글은 Jev가 TypeSafe의 제품이라고 밝히지만 두 회사의 관계나 이해관계는 쓰지 않는다.

### 이것이 LLM이 아니라는 서술에 대한 반박이 있다

HN에서 한 사용자는 이 글이 하드코딩된 알고리즘을 정말로 LLM인 것으로 바꾸는 이야기이고 Jev 같은 의사결정 모델도 약간 다른 신경 구조의 대형 언어 모델이라고 했다.[^mike-hearn] 다른 사용자는 Strands Decider도 판별형 LLM이라고 짚었다.[^charlesw]
글의 제목(모든 작업에 LLM이 필요한 것은 아니다)이 가리키는 범위가 모호해진다.

### 라우터와 재순위에 대한 회의가 있다

한 사용자는 결정 모델이 라우터로 쓰이면 모델이 결정 모델보다 최신일 가능성이 높아 모델 능력에 대한 정보가 없다고 했고,[^throwawayffffas] 다른 사용자는 재순위기는 훈련이 쉬워졌고 이미 보정된 점수를 내는데 결정 모델은 더 크고 느리고 같은 곳에 있지 않다고 회의했다.[^nostrebored]
글은 임계값이 모델 사이에 넘어가지 않는다는 점은 인정하지만 이 비교는 다루지 않는다.

### 개인정보 처리의 우려가 있다

HN에서 한 사용자는 PostHog가 고객 데이터에 이를 쓰면 안 된다고 했고 다른 사용자도 데이터 수집 업체가 수집 방식을 보여 줄 때마다 불편하다고 했다.[^dzink][^jakeydus]
글은 개인정보를 거르는 문지기를 소개하지만 요약이 어떤 모델과 서비스를 거치는지, 고객 동의는 어떤지 다루지 않는다.

### 외부 반응

HN 글 제목은 「Not Everything Needs an LLM」이다. 한 사용자는 이미 OpenAI가 Luna 기반 의사결정 모델을 제공한다고 했고,[^simianwords] 다른 사용자는 Copilot Fusion이 비슷한 작업 분류와 모델 선택을 한다고 했다.[^npteljes]
Lobste.rs의 `newsletter.posthog.com` 도메인에는 글이 없었다.

## 인사이트

### 가져갈 것은 문지기와 라우터를 임계값 설계로 보는 관점이다

비싼 호출 앞에 싼 판정을 두고, 틀렸을 때 더 비싼 쪽(거짓 음성인지 양성인지)에 맞춰 임계값을 정한다. 좁은 질문으로 쪼개고 임계값은 작업과 모델별로 따로 보정하며 그림자 모드로 시험한다. 이는 이 문서의 적용이다.

### 연쇄와 대형 입력은 LLM에 둔다

여러 단계 추론과 큰 입력은 의사결정 모델의 약점이다. 호출 빈도가 높은 경로에는 연쇄를 넣지 않는다.

### 확인할 관찰

이 글의 주장을 가를 관찰은 세 가지이다.
같은 작업에서 보정된 일반 분류기나 재순위기와의 비교,
모델이 바뀐 뒤의 임계값 이동 폭,
문지기의 거짓 음성이 실제로 낸 사고이다.
