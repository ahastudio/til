# LLM 구조화 디코딩: 문법에 맞지 않는 토큰을 지우고 고르는 샘플링

원문: [How LLM Structured Decoding works](https://nishtahir.com/how-llm-structured-decoding-works/)

## 소개

Nish Tahir가 2025년 9월 13일에 쓴 글로,
LLM이 JSON을 안정적으로 내놓게 하려다 지시를 계속 무시당하던 대화에서 출발한다.
저자는 주요 벤더가 제공하는 “Structured Output” 기능, 즉 출력 스키마를 넘기는
방식을 해법으로 제시하고,
그것이 왜 그렇게 잘 동작하는지를 Phi-4-mini-instruct와 Hugging Face
`transformers` 코드로 보여 준다.

핵심 계약은 한 문장으로 정리된다.
모델은 다음 토큰마다 어휘 전체에 대한 확률 분포를 내놓을 뿐이고,
어느 토큰을 받아들일지는 샘플러가 정한다.
구조화 디코딩은 그 샘플러가 문법에 어긋나는 토큰을 후보에서 지운 뒤 남은
토큰 중에서만 고르는 것이다.
그래서 저자는 샘플링 과정에 버그가 없다면 출력이 스키마를 따르는 것이 보장된다고
말한다.

이 보장의 경계는 정확히 알아 둘 필요가 있다.
보장되는 것은 문법이고, 보장되지 않는 것은 내용이다.
그리고 아래에서 보듯 문법조차 생성이 끝까지 진행됐을 때만 보장된다.

## 동작 방식

### 모델은 문자가 아니라 어휘 위의 분포를 내놓는다

모든 언어 모델은 토큰 문자열과 토큰 ID를 잇는 어휘를 가진다.
원문은 Phi-4-mini-instruct 어휘의 한 조각을 보여 주는데,
`ĠNSError`, `Ġfiltro`, `-best`, `icester` 같은 조각이 85268번부터 차례로 번호를
받는다.
앞의 `Ġ`는 앞 공백을 나타내는 바이트 수준 BPE의 표기다.
프롬프트를 토크나이저에 넣으면 이런 번호의 열이 나온다.

모델에 이 열을 넣으면 마지막 위치의 로짓, 즉 어휘의 모든 토큰에 대한 점수가
나온다.
원문이 “Write a json object with the following keys: ...”라는 프롬프트로 다음
토큰을 뽑아 보니,
가장 확률이 높은 것은 326번 ` and`(0.19), 다음은 483번 ` with`(0.12)였다.
지시를 따르는 것이 아니라 문장을 이어 쓰려는 것이다.
채팅 템플릿 없이 맨 문장을 넣었으니 당연한 결과이기도 하다.

### 디코딩 한 스텝은 마스크 한 장이다

JSON 객체는 `{`로, 배열은 `[`로 시작해야 한다.
그러니 첫 토큰으로 올 수 있는 후보는 정해져 있다.
원문의 첫 예제는 로짓과 같은 모양의 텐서를 `-inf`로 채운 뒤,
`{`와 `[`에 해당하는 자리만 원래 로짓을 복사하고 `argmax`를 취한다.
` and`가 19%였든 `{`가 0.01%였든 상관없이 결과는 `{`가 된다.

이 과정은 세 단계로 반복된다.

1. 지금까지 만든 출력을 접두사로 두고 모델의 로짓을 얻는다.
2. 접두사에 후보 토큰을 붙였을 때 문법상 아직 유효한 토큰만 남긴다.
3. 남은 토큰 중에서 고르고 접두사에 붙인다.

### 문법은 “아직 망가지지 않았는가”를 묻는 부분 일치 검사다

둘째 단계의 질문은 “이 문자열이 올바른 JSON인가”가 아니라
“이 문자열을 이어 써서 올바른 JSON을 만들 수 있는가”다.
원문은 이를 Python `regex` 모듈의 `partial=True` 옵션으로 구현한다.
`{"te`는 완성된 객체가 아니지만 정규식에 부분적으로 일치하므로 통과하고,
`{"te"x`는 어떻게 이어 써도 일치할 수 없으므로 탈락한다.

저자는 각주에서 이것이 DFA나 다른 파싱 기법과 매우 닮은 것은 우연이 아니라고
말한다.
어휘소(lexeme)를 흘려보내면서 무엇이 맞고 무엇이 맞지 않는지 결정하는 일이기
때문이다.
실제 엔진은 이 검사를 매 토큰마다 정규식으로 돌리지 않는다.
원문이 예로 드는 vLLM은 llguidance를 쓰며,
이런 라이브러리는 문법을 오토마톤으로 컴파일해 상태별로 허용 토큰 집합을
빠르게 계산한다.

### 벤더 API는 스키마를 받고 내부에서 같은 일을 한다

원문은 Gemini, OpenAI, vLLM의 구조화 출력 문서를 각주로 단다.
대부분의 벤더는 JSON Schema를 받고,
더 정교한 API는 BNF 비슷한 표기나 정규식으로 출력 문법을 정하게 해 준다.
사용자 입장에서 스키마는 프롬프트의 일부처럼 보이지만,
실제로는 샘플러의 설정이다.
프롬프트는 모델에게 부탁하는 것이고, 스키마는 샘플러에게 명령하는 것이다.

## 구현하기

원문의 정규식 예제를 그대로 실행할 수 있는 함수로 다시 정리하면 아래와 같다.
원문과 달리 채팅 템플릿을 쓰고,
어휘 문자열을 미리 풀어 두며,
문법이 완성되면 멈추도록 했다.

```python
# pip install torch transformers regex
import regex
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

MODEL = "microsoft/Phi-4-mini-instruct"  # 원문과 같은 모델. 더 작은 모델로 바꿔도 된다.

tokenizer = AutoTokenizer.from_pretrained(MODEL)
model = AutoModelForCausalLM.from_pretrained(MODEL, torch_dtype=torch.bfloat16)
model.eval()

# 키 하나와 값 하나를 가진 JSON 객체만 허용한다.
# 값은 공백 없는 단어 하나이거나 true/false/null이다.
PATTERN = regex.compile(r'\{\s*"\w+"\s*:\s*(?:"\w+"|true|false|null)\s*\}')

# 어휘 전체를 한 번만 문자열로 풀어 둔다. 스텝마다 decode하면 너무 느리다.
VOCAB = [tokenizer.decode([i]) for i in range(len(tokenizer))]


def constrained_generate(prompt: str, max_new_tokens: int = 40) -> str:
    messages = [{"role": "user", "content": prompt}]
    prefix = tokenizer.apply_chat_template(
        messages, add_generation_prompt=True, return_tensors="pt"
    )
    generated: list[int] = []
    completion = ""

    for _ in range(max_new_tokens):
        # 문법이 완성되면 더 생성하지 않는다. 원문 예제에는 이 종료 조건이 없다.
        if PATTERN.fullmatch(completion):
            return completion

        ids = prefix
        if generated:
            ids = torch.cat([prefix, torch.tensor([generated])], dim=1)
        with torch.no_grad():
            logits = model(ids).logits[0, -1]

        # 이어 붙여도 아직 부분 일치하는 토큰만 남긴다.
        allowed = [
            i
            for i, piece in enumerate(VOCAB)
            if piece and PATTERN.fullmatch(completion + piece, partial=True)
        ]
        if not allowed:
            raise RuntimeError(f"막다른 상태: {completion!r}")

        masked = torch.full_like(logits, float("-inf"))
        masked[allowed] = logits[allowed]
        next_id = int(torch.argmax(masked))  # 탐욕 선택. 샘플링하려면 softmax 후 multinomial.

        generated.append(next_id)
        completion += VOCAB[next_id]

    # 토큰 예산을 다 쓰면 문법이 완성되지 않은 채로 끝난다.
    raise RuntimeError(f"토큰 예산 소진: {completion!r}")


if __name__ == "__main__":
    print(constrained_generate("Write a valid json object with a single test key and value"))
```

결정이 담긴 값은 세 가지다.

| 값               | 정하는 기준                                                      |
| ---------------- | ---------------------------------------------------------------- |
| `PATTERN`        | 받아야 할 구조의 최소한. 넓을수록 모델의 표현을 덜 깎는다        |
| `max_new_tokens` | 문법이 완성될 수 있는 최대 길이보다 넉넉해야 한다                |
| 선택 방식        | 추출·분류는 `argmax`, 다양성이 필요하면 마스크 뒤에서 샘플링한다 |

이 코드는 원리를 보이기 위한 것이라 실제 서비스에 쓰기에는 느리다.
스텝마다 프롬프트 전체를 다시 계산하고(KV 캐시를 쓰지 않는다),
어휘 전체에 정규식을 한 번씩 돌린다.
운영에서는 벤더 API의 스키마 옵션이나 vLLM 같은 서버의 구조화 출력 기능을 쓰는
편이 맞다.

## 트레이드오프

### 문법을 좁힐수록 내용이 깎인다

원문의 마지막 예제 출력이 이 비용을 직접 보여 준다.
모델은 `{ "test": "This` 까지 쓰고 닫는 따옴표와 `}`로 끝났다.
정규식이 값을 `\w+`, 즉 공백 없는 단어 하나로 제한했으므로,
모델이 “This is a test” 같은 문장을 쓰고 싶었더라도 첫 단어 뒤에는 공백 토큰이
모두 지워진다.
출력은 문법적으로 완벽하지만 모델이 하려던 말은 잘렸다.

마스크는 모델이 원하는 토큰을 지우고 차선책을 강요한다.
차선책이 의미상 비슷하면 문제가 없지만,
문법이 모델의 자연스러운 표현과 어긋날수록 차선책의 품질은 떨어진다.
형식 제약이 추론 성능을 떨어뜨린다는 연구와,
그것이 프롬프트와 스키마 설계의 문제라는 반론이 이후로도 오갔다.
분명한 것은 스키마가 너무 좁으면 모델이 정답을 표현할 길 자체가 사라진다는
점이다.

### 토큰 경계와 문법 경계가 맞지 않는다

문법은 문자 단위로 정의되지만 모델은 토큰 단위로 쓴다.
BPE 어휘에는 `":`나 `{"` 같은 여러 문자를 묶은 토큰이 흔하고,
같은 문자열을 만드는 토큰 분할이 여러 가지다.
마스크는 문법에 맞는 분할만 남기므로,
모델이 학습 중에 자주 본 분할이 지워지고 낯선 분할이 강요될 수 있다.
문법상으로는 같은 문자열인데 모델에게는 다른 입력이 되는 것이다.

이 문제를 피하는 쉬운 방법은 없다.
문법을 문자 단위로 쪼개 매 토큰을 검사하는 것이 정확성은 보장하지만,
그 대가로 모델의 토큰화 습관과 어긋나는 경로를 막을 수 없다.
실제 엔진은 토큰 경계를 문법 상태 전이와 함께 다루는 쪽으로 진화했고,
그만큼 구현이 복잡해졌다.

### 부분 일치는 막다른 길을 미리 보지 못한다

부분 일치 검사는 “이어 쓸 수 있는가”만 묻고 “이 모델이 실제로 이어 쓸 것인가”는
묻지 않는다.
문법상 열려 있지만 모델이 거기서 빠져나올 토큰을 낮은 확률로만 가진 상태로
들어가면,
생성은 반복 토큰이나 공백을 계속 쌓다가 예산을 다 쓴다.
JSON의 `\s*`가 대표적인 함정으로,
공백을 무제한 허용하는 문법에서는 모델이 줄바꿈과 공백만 내놓는 경우가 있다.

## 함정

### 보장은 생성이 끝났을 때만 성립한다

원문은 샘플링 버그가 없다면 출력이 스키마를 따르는 것이 보장된다고 말한다.
하지만 원문의 정규식 예제는 `range(20)`으로 20 토큰에서 멈추고,
문법이 완성됐는지 확인하는 종료 조건이 없다.
값이 길었다면 출력은 닫는 괄호 없이 잘렸을 것이다.
벤더 API에서도 최대 토큰 수에 걸리면 같은 일이 생긴다.
“스키마를 따른다”는 보장은 “끝까지 생성했다면”이라는 조건을 달고 있다.

### 문법은 내용의 정확성을 보장하지 않는다

스키마는 `age` 필드가 정수라는 것은 보장하지만 그 정수가 맞는지는 보장하지
않는다.
모델이 모르는 값을 요구하는 스키마는 그럴듯한 숫자를 만들어 내도록 강요한다.
자유 텍스트였다면 “모르겠다”고 썼을 모델이,
선택지가 숫자뿐인 문법에서는 숫자를 고를 수밖에 없다.
필수 필드에는 “알 수 없음”을 표현할 수 있는 값(null 허용 등)을 두는 편이
안전하다.

### 토큰을 하나씩 decode해서 이어 붙이면 원문과 달라질 수 있다

위 코드와 원문은 `tokenizer.decode([id])`로 풀어 둔 조각을 이어 붙인다.
Phi-4-mini처럼 바이트 수준 BPE를 쓰는 토크나이저에서는 대체로 맞지만,
SentencePiece 계열은 단독으로 decode할 때 앞 공백을 떨어뜨리기도 하고,
여러 바이트로 이루어진 문자가 두 토큰에 걸치면 단독 decode는 깨진 문자가 된다.
한글처럼 UTF-8로 3바이트인 문자가 섞이면 이 차이가 실제로 문제가 된다.
정확하게 하려면 접두사 전체를 decode한 결과에서 차이를 계산해야 한다.

### 스키마를 프롬프트에서 빼면 안 된다

마스크는 모델이 무엇을 써야 하는지 알려 주지 않고,
쓰면 안 되는 것만 막는다.
원문의 첫 실험에서 모델은 ` and`를 쓰려 했는데,
마스크로 `{`를 강제해도 그 다음에 무엇을 써야 할지는 모델이 프롬프트에서
알아내야 한다.
스키마의 필드 이름과 의미를 프롬프트에도 적어 두어야 모델의 확률 분포가
처음부터 문법 쪽으로 기운다.
그래야 마스크가 지우는 확률 질량이 줄고 품질 손실도 줄어든다.

## 확인하기

위 스크립트를 실행하면 `{"test": "..."}` 모양의 한 줄이 나온다.
마스크의 효과를 직접 보려면 두 가지를 바꿔 본다.

1. `PATTERN`의 값 부분을 `"(?:\w|\s)+"`처럼 공백을 허용하게 넓히고, 값이 단어 하나에서 문장으로 바뀌는지 본다.
2. `max_new_tokens`를 5로 줄이고, 문법이 완성되기 전에 “토큰 예산 소진” 예외가 나는지 본다.

첫 실험은 문법의 폭이 내용을 정한다는 것을,
둘째 실험은 보장이 생성 완료를 전제한다는 것을 보여 준다.

## 기억할 원칙

### 스키마는 부탁이 아니라 필터다

프롬프트에 “JSON으로 답하라”고 쓰는 것은 모델의 확률 분포를 조금 움직이는
일이고,
구조화 디코딩은 분포에서 문법에 어긋나는 부분을 잘라 내는 일이다.
둘은 대체재가 아니라 보완재다.
프롬프트로 분포를 문법 쪽으로 기울이고, 마스크로 남은 이탈을 막는다.
마스크만 쓰면 품질이 깎이고, 프롬프트만 쓰면 형식이 깨진다.

### 필터는 모양을 보장하고 내용은 보장하지 않는다

구조화 디코딩이 해결하는 문제는 파싱 실패다.
값이 맞는지, 모델이 그 값을 알고 있는지는 전혀 다른 문제로 남는다.
스키마를 설계할 때는 모델이 정직하게 답할 수 있는 출구,
즉 모름을 표현할 자리를 함께 설계해야 한다.
