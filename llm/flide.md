# Flide: 한 상태에서 여러 질문을 갈라 한 번에 답하는 결정 모델 추론 엔진

<https://flide.org/>

<https://github.com/OmniJev/Flide>

Show HN: [Show HN: Flide: Make Jev-like decision models up to 9.5x faster](https://news.ycombinator.com/item?id=50421155)

## 소개

Flide는 Jev 방식의 결정 모델(decision model)을 빠르게 서빙하는 추론 엔진이다.
README는 정확한 상태 분기(exact state forking)로 vLLM과 SGLang보다 최대 9.5배
빠르고 모든 답이 그 질문만 단독으로 물었을 때의 답과 같다고 소개한다.
`/v1/systemone` API를 제공한다.
논문 초록은 결정 모델을 LLM 에이전트 시스템에서
가벼운 범주형 추론으로 빠른 1단계
(System One) 실행을 맡는 패러다임으로 설명하고,
기존 생성 중심 추론 엔진이 접두사(prefix) 재계산 부담이나 왜곡된 출력 확률
때문에
이 작업에 맞지 않는다고 한다.[^paper]

저장소는 2026년 10월 24일에 만들어졌고 Apache-2.0 라이선스, Python이다.
2026년 11월 10일에 확인한 별은 283개, 포크 8개, 열린 이슈 1개다.
PyPI의 최신판은 0.1.11이고, README의 소식 목록은 10월 24일의 0.1.0부터
11월 10일의 0.1.11까지 17일 사이에 열한 번의 릴리스를 적는다.
논문은 2026년 10월 30일에 arXiv에 제출되었다.[^paper]

### 설치와 요청

```bash
uv venv -p 3.12 && source .venv/bin/activate
uv pip install flide torchvision
flide serve --model OmniJev/OneJev1.6-0.8B
```

Python 3.10 이상과 PyTorch 2.12 이상이 필요하고,
홈페이지는 커널이 A40, A10, RTX 30, H100, H200용으로 미리 빌드되어 있다고 한다.
`flide serve`는 기본으로 모든 인터페이스의 8000번 포트에서 듣는다.

요청은 하나의 상태(`state`)와 이름 붙은 여러 질문(`questions`)을 보낸다.
질문은 선택지가 있는 `choice`나 예, 아니오를 묻는 `noul` 같은 유형이고,
응답은 모든 선택지의 확률을 담아 임계값을 바로 적용할 수 있다.
README의 예는 환불 요청 한 건에 대해 무엇을 할지(환불, 교체, 사람에게 넘김)와
한 시간 안에 답해야 하는지를 한 번에 묻는다.

### 옵션

| 옵션                    | 하는 일                                                                   |
| ----------------------- | ------------------------------------------------------------------------- |
| `--session-cache-gb 40` | 이전 요청의 상태를 보관해 에이전트의 다음 단계가 새 부분만 읽는다         |
| `--batch-invariant`     | 어떻게 배치되든 요청에 같은 비트를 내며, 속도를 일부 잃는다               |
| `--quantize fp8`        | Ada, Hopper, Blackwell GPU에서 Qwen3.5를 FP8로 돌린다                     |
| `--frontends 2`         | HTTP, 렌더링, 토큰화를 별도 프로세스 둘에서 돌려 많은 클라이언트를 받는다 |

## 분석

### 질문 수가 많을수록 이득이 커지는 구조

속도 향상의 핵심은 상태를 한 번만 읽고 그것을 모든 질문으로 갈라 각 질문이
그 상태를 제자리에서 읽게 하는 것이다.
홈페이지는 이를 ForkAttention이라 부르고,
일반 어텐션과 순환(recurrent) 층인 게이트 델타넷(Gated DeltaNet)에서 모두
질문이 공유 맥락의 정확한 상태에서 출발하게 한다고 설명한다.
9.5배는 Qwen3.5-0.8B로 QuALITY의 긴 글 하나(평균 5.8k 토큰)와 그에 딸린 18개
질문을 처리한 경우라고 개발자가 HN에서 밝혔다.[^unikcc-9-5]
질문이 하나뿐이면 최대 3배이고 질문이 많을수록 이득이 커진다.[^unikcc-3x]
Show HN 스레드의 한 사용자도 논문을 읽고 같은 결론을 정리했다.[^tancop]

### 정확함을 파는 엔진이다

홈페이지는 Flide가 float32 기준 구현과의 거리를 0.1에서 1.1점으로 유지해
다른 엔진 중 가장 가깝고, 0.5 임계값에서 결정이 뒤집히는 비율이 최대 2.3%라고
말한다.
다중 항목 점수화(multi-item scoring) 방식은 같은 값이 0.9에서 14.8점,
0.8에서 28.9%라고 적는다.
확률을 임계값으로 자르는 결정 모델에서는 확률의 작은 왜곡이 결정을 뒤집으므로,
정확도가 곧 이 엔진의 쓸모를 정한다는 논리다.
`--batch-invariant`는 배치에 상관없이 같은 비트를 보장해 이 정확성을 한 걸음 더
밀어붙인다.

### 에이전트의 다음 단계가 이전 상태에서 이어진다

홈페이지가 소개하는 또 하나의 이득은 에이전트의 이력이 길어질 때다.
이전 패스에서 저장한 체크포인트에서 이어 가서 이력 1k 토큰당 단계마다 추가되는
시간이 Flide는 0.6에서 1.0ms이고 다른 엔진 둘은 11에서 15ms라고 한다.
반복되는 에이전트 루프에서 이 차이가 쌓인다.

### 데모의 성격

이메일 분류 데모는 H200 한 장에서 OneJev1.6-0.8B로 이메일 한 통을 10.0ms에,
10,000통에 질문 여덟 개씩을 28초에 답하며,
가장 빠른 다른 엔진보다 한 통은 3.5배, 전체는 4.1배 빠르다고 한다.
한 상태에 질문 여덟 개가 붙는 가장 유리한 모양의 작업이다.

## 비평

### 속도 비교의 기준선이 한결같지 않다

헤드라인의 9.5배는 vLLM과 SGLang을 상대로 한 값이다.
같은 README의 모델 표는 첫 두 열을 이렇게 설명한다.
채팅 모델은 vLLM과 SGLang 중 빠른 쪽과, OneJev는 Flide 이전에 쓰던 qev 엔진과,
다른 모델은 각 릴리스가 함께 내는 엔진과 비교한다.
표에는 Senova의 MultiRC가 28.1배, Sieve가 14.3배로 헤드라인의 9.5배를 넘고,
Clef나 Gemma 4의 일부 칸은 1.0배다.
공식 문서의 첫 장은 최대 9.4배라고 적고 README와 홈페이지는 9.5배라고 적어
같은 프로젝트 안에서도 숫자가 다르다.[^docs]
표의 수치는 모델마다 다른 기준선과 다른 워크로드의 한 조합이어서,
한 줄로 요약하기 어렵다.

### 엔진 개발자가 가장 큰 이득을 보는 모델도 낸다

저장소는 `OmniJev` 조직 아래에 있고, 이메일 데모와 설치 예제에 쓰는 OneJev
모델도 같은 조직의 것이다.
모델 표에서 OneJev는 이미지와 영상까지 읽는 모델로 DI 약 6.8배, MultiRC
7.3배, QuALITY 4.7배의 이득을 보인다.
엔진 제작자가 자기 모델에 맞춰 최적화하고
그 모델로 데모를 만드는 것은 자연스러우나,
외부 모델의 이득과 같은 수준으로 읽으면 안 된다.
논문과 README 모두 공개 모델에서의 평가를 말하지만 어떤 비교가 독립적으로
재현되었는지는 이번에 확인하지 못했다.

### 가장 흔한 사용 방식에서는 이득이 작다

HN에서 한 사용자는 같은 질문을 여러 입력에 던지는 반대의 경우가 실제로는 훨씬
유용하다고 지적했다.[^p-e-w]
개발자는 현재 설정으로는 크게 도움이 되지 않는다고 인정하며,
질문을 앞에 두고 상태가 뒤따르도록 동적으로 배치하는 확장을 생각하고 있다고
답했다.[^unikcc-question-first]
이메일 한 통에 스팸인지만 묻는 경우에도 최대 3배라는 답이 나왔다.[^unikcc-email]
이 엔진의 최대 이득은 질문이 많은 한 가지 작업 모양에 한정된다.

### 새 엔진이 필요한가라는 질문

HN의 다른 사용자는 vLLM을 수정해 같은 작업에서 비슷한 속도 향상을 얻었다고
했다.[^Tostino]
개발자는 전체 어텐션에서는 그것이 통하지만 Qwen3.5의 게이트 델타넷에서는 vLLM이
블록 경계에서만 캐시하므로 새 엔진이 필요했고,
CUDA 그래프 사용을 최적화했으며 부하에 상관없이 비트가 같은 답을 낸다고
답했다.[^unikcc-vllm]
이 주장이 얼마나 근거를 가지는지는 이 문서가 확인하지 못했고,
논문이 그 근거를 세운다.

### 실제 사용 환경의 범위가 좁다

개발자는 Linux에서만 시험했고 Windows에서는 WSL2가 필요할 수 있다고
했다.[^unikcc-linux]
6GB NVIDIA GPU 노트북에서는 0.8B 모델을 서빙할 수 있지만,
CPU만 있는 기기나 더 작은 GPU에서는 llama.cpp나 LM Studio가 낫다고
안내했다.[^unikcc-laptop]
GLiDE 9B+ 같은 양방향 어텐션 모델은 아직 지원하지 않고 이득도 작을 것이라고
했다.[^unikcc-glide]
다섯 가지 GPU용 사전 빌드 커널과 Linux라는 조건은 시험 범위가 아직 좁다는
뜻이다.

## 인사이트

### API의 모양이 구조를 엔진에 알려 주면 캐시 추정이 필요 없어진다

일반 서빙 엔진은 프롬프트 접두사가 같은지를 추정해 캐시를 재사용한다.
Flide의 요청은 상태와 이름 붙은 질문이 처음부터 분리되어 있어,
엔진이 어느 부분이 공유되는지를 추정하지 않고 안다.
이 분리가 가지치기(분기)를 정확하게 만들고, 질문 수와 이득의 관계를 직접
만든다.
작업의 구조를 인터페이스에 드러내는 설계가 엔진 쪽의 복잡한 휴리스틱보다
강하다는 것을 이 프로젝트가 보여 준다.
이것은 이 문서의 해석이다.

### 정확도가 속도와 한 묶음으로 팔린다

결정 모델은 확률을 임계값으로 자르므로 속도를 위해 확률을 약간 흩트리는
방식(다중 항목 점수화)은 결정을 뒤집는다.
Flide가 속도와 정확성을 같은 슬로건으로 내세우는 것은 이 작업에서 둘을 맞바꿀 수
없다는 것을 안다는 뜻이다.
`--batch-invariant`가 속도를 일부 잃더라도 같은 비트를 보장하는 선택지로
제공되는 것도 같은 맥락이다.
감사나 재현이 필요한 에이전트 시스템에서는 이 옵션이 기본값이 되어야 한다는
주장이 나올 수 있다.

### 엔진이 모델 생태계의 호환 계층이 되어 간다

README의 소식 목록은 거의 날마다 새 결정 모델 계열을 추가했다고 적는다.
2026년 10월 24일 0.1.0 이후 17일에 서른 개가 넘는 모델 계열이 표에 오른다.
엔진이 개별 모델의 서빙 방식(어댑터 병합, 양자화, 이미지 입력)의 차이를 감싸
같은 `/v1/systemone` API로 내놓는다.
이렇게 되면 엔진은 속도를 파는 도구이면서 서로 다른 모델 사이의 호환 계층이
된다.
그 대가로 엔진 쪽이 모든 모델의 특성(양방향 어텐션 등)을 따라가야 한다.
