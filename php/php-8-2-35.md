# PHP 8.2.35: 완전한 임시 완화책이 없는 보안 릴리스 대응법

원문: [PHP 8.2.35](https://github.com/php/php-src/releases/tag/php-8.2.35)

HN 토론: <https://news.ycombinator.com/item?id=50180873> (742점, 307개 댓글)

GN 토론: <https://news.hada.io/topic?id=35758>

## 요약

PHP 개발 팀이 2026년 10월 21일에 GitHub 릴리스 페이지로 PHP 8.2.35를 알렸다.
이 릴리스는 인증 없는 원격 코드 실행으로 이어질 수 있는 치명적 취약점 두 건,
`CVE-2026-109618`과 `CVE-2026-109619`를 고친다.
릴리스 노트는 PHP 8.2 사용자 모두에게 즉시 업데이트를 권한다.

노트는 완전한 임시 완화책이 없으며 업데이트만이 안전한 선택이라고 분명히 밝힌다.
자세한 내용은 php.net의 보안 권고(security advisory)를 보라고 안내한다.
또 PHP 8.2가 2026년 12월 31일에 지원이 끝나 그 뒤로는 보안 수정을 받지 못하므로,
지원되는 버전으로 올릴 계획을 세우라고 덧붙인다.

같은 날 PHP 8.5.12, 8.4.27, 8.3.36도 함께 나왔다.[^advisory]
릴리스 노트는 짧아서 이 글의 나머지는 노트가 가리키는 보안 권고를 바탕으로 한다.

## 동작 방식

두 취약점은 PHP 엔진이 요청을 처리하는 과정의 서로 다른 지점에 있다.
권고는 이를 각각 메모리 부족(out-of-memory) 처리와 요청 단위 전역 상태 처리의 문제로 설명한다.

### CVE-2026-109618: 메모리 부족 처리가 만든 손상

메모리 부족 처리가 요청의 내부 데이터를 일부만 초기화한 시점에 PHP 실행을 중단시킬 수 있다.
이후 요청 정리 과정이 그 유효하지 않은 데이터를 유효한 것으로 취급한다.[^advisory]
권고는 이를 `RCE via OOM corruption`이라고 부른다.[^advisory]

### CVE-2026-109619: 해제된 메모리에 남은 상태

요청이 소유한 내부 상태가 그것을 뒷받침하던 메모리가 해제된 뒤에도 남는다.
같은 워커가 처리하는 다음 요청이 정상 초기화로 그 상태가 지워지기 전에 이를 쓸 수 있다.[^advisory]
권고는 이를 `RCE via stale global state`라고 부른다.[^advisory]

### 영향받는 범위

영향받는 대상은 웹 요청을 처리하는 모든 PHP 설치다.
PHP-FPM, `mod_php`를 쓰는 Apache, `php-cgi`, FrankenPHP, LiteSpeed가 포함된다.
권고는 `mod_php`의 위험이 가장 높다고 본다.
인증 없는 요청 하나가 애플리케이션 코드가 실행되기도 전에 공격을 일으키는 익스플로잇이 시연되었기 때문이다.[^advisory]

## 업데이트하기

해야 할 일은 사용 중인 브랜치에 맞는 버전으로 올리는 것이다.
8.5는 8.5.12, 8.4는 8.4.27, 8.3은 8.3.36, 8.2는 8.2.35다.[^advisory]
소스 다운로드는 php.net 내려받기 페이지에 있고, Windows 소스와 바이너리도 같은 페이지에 있다.[^advisory]

### 배포판 패키지를 쓰는 경우

Linux 배포판과 LTS 공급업체는 패치를 미리 받았으므로, 업데이트는 해당 공급업체의 패키지로 한다.[^advisory]
패키지 관리자에서 버전 번호만 보지 말고 공급업체의 보안 공지로 수정 포함 여부를 확인해야 한다.
배포판은 백포트를 적용하면서 상위 버전 번호를 그대로 두는 경우가 많기 때문이다.

Remi가 자원봉사로 관리하는 `rpms.remirepo.net` 저장소를 쓰고 있다면, 권고는 배포판 패키지로 옮기거나 소스에서 빌드하라고 한다.
그 저장소는 당일에 업데이트가 없을 예정이었다.[^advisory]

HN 댓글을 보면 릴리스 당일 배포 경로마다 도착 시간이 달랐다.
dstu는 Ubuntu LTS가 `apt update`로 새 패키지를 가져오지 못하고, Laravel Forge는 업데이트하려는 사람들이 몰려 응답이 없다고 적었다.[^dstu]
Neil44는 자신의 Linode와 OVH 가상 머신이 Ubuntu 본 서버가 아닌 지역 미러를 바라보고 있어서 늦는 것 같다고 추측했다.[^Neil44]
같은 업데이트라도 어떤 미러와 어떤 관리 도구를 거치느냐에 따라 적용 시점이 갈린다는 뜻이다.

spenvo는 Docker의 공식 PHP 이미지가 릴리스 시각이 지나고 한참 뒤에도 준비되지 않았다고 불만을 적었다.
이후 갱신에서 amd64 이미지는 PHP 릴리스로부터 2시간 55분이 지나서야 올라왔고, 서버가 몰려 내려받기도 어렵다고 덧붙였다.[^spenvo]
asimovDev는 이미지가 레지스트리에 닿기까지 여러 빌드 단계를 거치는 긴 절차가 있다고 설명했다.[^asimovDev]
컨테이너 이미지로 PHP를 배포한다면 이미지가 올라오기 전까지는 직접 빌드하는 수밖에 없다.

배포판 패키지는 개인 관리자가 유지하는 저장소에도 의존한다.
cholmon은 deb.sury.org 저장소를 관리하는 Ondrej에게 후원을 권했고,[^cholmon]
jdhawk는 그가 5.6에서 8.0까지의 브랜치에도 수정을 백포트했으며 최신 5.6.40-104에 CVE 수정이 들어 있다고 알렸다.[^jdhawk]

### PHP 8.1 이하를 쓰는 경우

PHP 8.1 이하는 PHP 프로젝트의 업데이트가 끝났다.
일부 배포판과 LTS 공급업체가 백포트 수정을 제공하므로 공급업체에 문의하거나 지원되는 버전으로 올려야 한다.[^advisory]
소스에서 빌드하거나 LTS 공급업체를 쓸 수 없는 사람을 위해, PHP 보안 팀은 PHP 7.4, 8.0, 8.1용 최소한의 소스 백포트를 제공했다.[^advisory]

### 지금 바로 업데이트할 수 없는 경우

권고는 아래 조치가 특정 공격 경로의 노출을 줄일 뿐, 설치를 안전하게 만들지 않는다고 분명히 밝힌다.[^advisory]
다음 코드는 FPM 풀 설정에서 이 조치들을 애플리케이션이 되돌릴 수 없게 적용하는 예다.

```ini
; /etc/php/<버전>/fpm/pool.d/www.conf
; php_admin_*는 애플리케이션의 ini_set()으로 덮어쓸 수 없다.

; CVE-2026-109618: 통제 가능한 memory_limit 실패를 없앤다.
php_admin_value[memory_limit] = -1

; CVE-2026-109618: 업로드가 필요 없는 애플리케이션은 8M, 필요하면 32M.
php_admin_value[post_max_size] = 8M
; 항상 post_max_size보다 작게 둔다.
php_admin_value[upload_max_filesize] = 2M

; CVE-2026-109619: 확인된 세션 업로드 진행 경로를 막는다.
php_admin_flag[session.upload_progress.enabled] = off
```

설정을 바꾼 뒤에는 모든 워커를 재시작해야 한다.
권고는 `session.upload_progress.enabled=0`을 적용한 뒤 모든 워커를 재시작하라고 명시한다.[^advisory]

## 값 정하기

| 설정                                 | 시작 값                  | 근거                                                                                |
| ------------------------------------ | ------------------------ | ----------------------------------------------------------------------------------- |
| `memory_limit`                       | `-1`                     | 통제 가능한 메모리 제한 실패를 없앤다. 하부 할당 실패는 남는다.[^advisory]          |
| `post_max_size`                      | `8M` 또는 `32M`          | 업로드가 필요 없으면 8M, 필요하면 32M이다.[^advisory]                               |
| `upload_max_filesize`                | `post_max_size`보다 작게 | 권고가 지정한 관계다. 구체적인 값은 애플리케이션의 업로드 크기에 맞춘다.[^advisory] |
| `session.upload_progress.enabled`    | `0`                      | 확인된 세션 경로를 막는다. 다른 변형은 막지 못한다.[^advisory]                      |
| `fatal_error_backtraces` (PHP 8.5만) | `0`                      | 확인된 치명적 오류 백트레이스 경로만 막는다.[^advisory]                             |

`upload_max_filesize`의 구체적인 값은 권고에 없으므로 위 코드의 `2M`은 예시일 뿐이다.
애플리케이션이 받는 가장 큰 파일을 기준으로 직접 정해야 한다.

## 트레이드오프

### memory_limit을 풀면 다른 보호가 사라진다

`memory_limit=-1`은 공격자가 조절할 수 있는 실패 지점을 없애지만,
폭주하는 스크립트가 서버의 메모리를 다 쓰는 것도 막지 못하게 된다.
권고는 이를 컨테이너나 cgroup 제한으로 보완하라고 한다.
영향받은 워커만 죽이는 정책이 바람직하다는 조건이 붙는다.[^advisory]

겉으로 비슷해 보이는 `RLIMIT_AS`나 `RLIMIT_DATA`는 대체할 수 없다.
이 제한들이 오히려 취약한 할당 실패를 일으킬 수 있기 때문이다.[^advisory]
그래서 메모리를 제한하고 싶어도 PHP 프로세스 안쪽이 아니라 바깥의 cgroup에서 해야 한다.

### 완화책은 알려진 경로만 막는다

`session.upload_progress.enabled=0`은 확인된 세션 경로를 막지만 다른 변형은 막지 못한다.[^advisory]
`fatal_error_backtraces=0`도 확인된 백트레이스 경로 하나만 막는다.[^advisory]
공격자가 이 설정들이 닫지 않은 경로를 찾으면 설정은 소용이 없다.
따라서 완화책을 적용했다는 사실이 업데이트를 미룰 근거가 될 수 없다.

### 업로드를 줄이면 서비스가 줄어든다

`post_max_size`를 낮추거나 업로드 진행 표시를 끄면 정상 사용자도 영향을 받는다.
큰 파일 업로드나 진행률 표시줄이 필요한 서비스는 그 기능을 잃는다.
권고도 업로드가 필요하면 32M을 쓰라고 구분해 둔다.[^advisory]

### 웹 서버에서 멀티파트 요청을 막으면 업로드가 전부 깨진다

HN에서 bombcar는 배포판 패키지를 기다리는 동안 자신의 WordPress 서버에 적용한 조치를 정리했다.
PHP가 요청 본문을 파싱하기 전에 웹 서버에서 `multipart/form-data` 요청을 403으로 거절하는 방법이다.
bombcar는 모든 브라우저 업로드(미디어 라이브러리, 플러그인 압축 파일, 가져오기 도구)가 깨진다는 비용을 함께 적었다.
또 워커 하나가 요청을 하나만 처리하고 종료하도록 `pm.max_requests = 1`을 두면 오래된 상태를 이용하는 연쇄가 끊기지만, 요청마다 포크 비용이 든다고 했다.[^bombcar]
dwedge는 이 글이 Claude의 출력 같다며 직접 검증했는지 물었다.[^dwedge]
이 조치들은 권고에 없는 개인의 경험이므로, 적용하기 전에 자신의 환경에서 확인해야 한다.

## 함정

### 설정을 어디에 적용했는지에 따라 효과가 달라진다

권고는 `ini_set()`이나 FPM의 `.user.ini`에 의존하지 말라고 한다.
요청 파싱 전에 적용되는 `php.ini`, FPM 풀, 서버 설정에 넣어야 한다.[^advisory]
애플리케이션 안에서 값을 바꾸는 방식은 취약한 경로가 지나간 뒤에야 적용될 수 있다.

### 경고를 숨기는 것으로는 막히지 않는다

초기화 전에 진단 메시지를 내는 잘못되었거나 사용이 중단된 요청별 설정은 제거해야 한다.
`error_reporting`, `display_errors`, `@`로 진단 메시지를 숨겨도 도움이 되지 않는다.[^advisory]
메시지가 보이지 않게 되었을 뿐 그 처리 경로는 그대로 실행되기 때문이다.

### 공격자가 닿을 수 있는 치명적 오류를 고쳐야 한다

권고는 콜백, 업로드, 가져오기 처리, 정리 단계의 실패를 포함해
공격자가 닿을 수 있는 치명적 오류와 실행 시간 초과를 고치라고 한다.[^advisory]
이는 PHP를 업데이트해도 애플리케이션 코드의 책임이 사라지지 않음을 뜻한다.

### 8.2는 곧 지원이 끝난다

릴리스 노트가 밝힌 대로 8.2는 2026년 12월 31일 이후 보안 수정을 받지 못한다.
이날까지 두 달 남짓밖에 남지 않았으므로, 이번 업데이트를 마친 뒤에도 상위 버전으로의 이전 계획이 남는다.

### 수정이 넓게 퍼져 있어 빠진 곳이 있을 수 있다

dannyw는 패치가 `if (ZEND_HAS_OOM())` 검사를 코드 곳곳에 수천 번 넣는 방식이라 어딘가 빠뜨렸을 것 같다는 첫인상을 적었다.[^dannyw]
OscarCunningham은 두 번째 취약점이 있을 수 있다는 글을 링크했는데, 이 글에서는 그 내용을 확인하지 못했다.[^OscarCunningham]
둘 다 추측이나 미확인 주장이지만, 업데이트한 뒤에도 후속 보안 릴리스가 나올 가능성을 열어 두고 공지를 계속 확인해야 한다는 뜻이다.

### 공격 흔적이 보이지 않는다고 안전한 것이 아니다

tovve는 보안 업체 watchTowr가 실제 침해가 있었다고 보고했지만 어디인지는 밝히지 않았다고 전했다.[^tovve]
redox99는 공격 에이전트가 이미 수십만 개의 사이트를 뚫고 백도어를 설치한 뒤 취약점을 막아 다른 공격자를 막고 있을 것이며, 사이트를 변조하지 않으니 흔적도 없을 것이라고 예상했다.[^redox99]
이는 증명되지 않은 예측이다.
다만 업데이트가 끝난 서버라도 그 전에 요청을 받았다면, 업데이트가 침해 여부를 지워 주지는 않는다.

## 확인하기

적용한 설정이 실제 요청 처리에 쓰이는 값인지 확인한다.
명령줄 `php`의 설정은 FPM이나 Apache의 설정과 다를 수 있으므로 웹 환경에서 확인해야 한다.

```bash
# 설치된 버전과 배포판 패키지 변경 이력
php -v
# Debian/Ubuntu: 패키지 변경 로그에 CVE 번호가 있는지 확인한다.
apt changelog php8.2-common | grep -n "CVE-2026-10961"

# FPM 풀에 적용한 설정을 설정 파일에서 직접 확인한다.
grep -rn "php_admin_value\|php_admin_flag" /etc/php/*/fpm/pool.d/
```

배포판이 백포트를 적용했다면 `php -v`의 버전 번호가 8.2.35보다 낮아도 수정이 들어 있을 수 있다.
그 판단은 공급업체의 보안 공지로 하며 이 글의 명령만으로 단정할 수 없다.

- `rpms.remirepo.net`을 쓰고 있다면 배포판 패키지나 소스 빌드로 옮겼는가?
- PHP 8.1 이하라면 공급업체의 백포트를 받았거나 지원되는 버전으로 올렸는가?
- 임시 완화책을 쓴다면 `ini_set()`이나 `.user.ini`가 아니라 서버 설정에 넣었는가?
- 임시 완화책을 쓴다면 업데이트 일정을 함께 정했는가?
- 8.2를 쓴다면 2026년 12월 31일 전의 이전 일정이 있는가?

## 기억할 원칙

### 완화책은 업데이트가 끝날 때까지의 시간을 버는 수단이다

이 릴리스의 노트는 완전한 완화책이 없다고 직접 말하고, 권고는 각 완화책이 막는 경로를 하나씩 한정한다.
완화책이 막는 범위를 모르면 적용했다는 사실이 안전하다는 착각을 만든다.
완화책을 적용할 때는 무엇을 막고 무엇을 막지 못하는지를 같이 기록해 두어야 한다.

### 제한은 그 제한이 일으킬 수 있는 실패까지 살펴서 건다

`memory_limit`을 풀어야 하고 `RLIMIT_AS`는 쓰면 안 된다는 권고의 대비는,
같은 목적의 제한이라도 걸리는 위치에 따라 새 실패를 만든다는 것을 보여 준다.
자원 제한을 걸 때는 제한에 걸린 프로세스가 어떻게 실패하는지까지 확인해야 한다.
