# brewery: Homebrew 업데이트 세 줄을 버튼 하나로 바꾼 macOS 앱

<https://github.com/Devguru-J/brewery>

Show GN: [brewery - Homebrew 업데이트를 버튼 하나로 하는 macOS 앱](https://news.hada.io/topic?id=34258)

## 소개

brewery는 `brew update`, `brew upgrade`, `brew upgrade --greedy` 세 명령을 버튼 하나로 실행하는 macOS 네이티브 앱이다.
작성자는 매일 터미널을 열어 같은 세 줄을 치다가 이것을 버튼 하나로 바꾸려고 만들었다고 소개한다.
SwiftUI로 만들었고 외부 패키지 의존성이 없으며, 소스는 GitHub의 `Devguru-J/brewery` 저장소에 MIT 라이선스로 공개돼 있다.
저장소는 2026년 9월 13일에 만들어졌다.

설치는 작성자의 tap으로 한다.

```bash
brew install --cask devguru-j/tap/brewery
```

Developer ID로 서명하고 Apple 공증을 거친 빌드라 경고 없이 열리며, macOS 14 이상이 필요하다.

## 주요 기능

- 세 명령을 순서대로 실행하고, 한 단계라도 실패하면 거기서 멈춘다. 각 단계를 따로 실행하거나 중간에 중단할 수도 있고, brew 출력은 하단 로그 창에 실시간으로 나온다.
- 설치된 formula와 cask를 탭으로 나눠 보여 준다. cask는 실제 설치된 앱의 아이콘으로 표시하고, 업데이트가 있으면 `현재 → 새 버전`을 함께 보여 준다.
- 여러 항목을 골라 업그레이드하거나 삭제할 수 있다. 삭제는 항상 확인창을 거치고 강제 옵션 없이 실행되므로, 다른 패키지가 의존하는 formula는 brew가 거부한다.
- `brew search` 결과에서 바로 설치할 수 있다.
- 메뉴바의 맥주잔 아이콘에 업데이트 가능한 개수가 뜨고, 창을 닫아도 메뉴바에 남는다.
- 테마 3종(macOS 기본, 다크 터미널, 맥주집)과 7개 언어를 지원한다.

작성자가 밝힌 한계는 세 가지다.
관리자 비밀번호가 필요한 cask는 GUI에서 비밀번호를 받을 수 없어 실패로 표시되고, 그 항목만 터미널에서 실행해야 한다.
brew가 changelog를 주지 않아 변경 내역 대신 홈페이지 링크를 보여 준다.
샌드박스 안에서는 brew를 실행할 수 없어 Mac App Store에는 올릴 수 없다.

## 동작 방식

앱의 핵심은 `Sources/Engine` 아래 몇 개의 작은 타입이다.
`BrewLocator`는 `/opt/homebrew/bin/brew`와 `/usr/local/bin/brew`를 먼저 찾고, 없으면 `PATH`의 디렉터리를 차례로 뒤진다.
Apple Silicon과 Intel Mac의 기본 설치 경로를 모두 다루는 셈이다.

`BrewRunner`는 Foundation의 `Process`로 brew를 띄우고, 표준 출력과 표준 에러를 각각 `Pipe`로 받아 한 줄씩 로그로 흘려보낸다.
이때 표준 입력은 `FileHandle.nullDevice`로 막아 둔다.
`UpgradePipeline`은 실행할 때마다 다음 환경 변수를 넣는다.

```text
HOMEBREW_NO_AUTO_UPDATE=1
HOMEBREW_NO_ENV_HINTS=1
HOMEBREW_NO_COLOR=1
NO_COLOR=1
NONINTERACTIVE=1
```

`HOMEBREW_NO_AUTO_UPDATE`는 `brew upgrade`가 스스로 `brew update`를 다시 부르지 않게 한다.
앱이 update 단계를 따로 실행하므로 같은 일을 두 번 하지 않으려는 설정이다.
색 코드를 끄는 두 변수는 로그 창에 ANSI 이스케이프가 섞이지 않게 한다.

업데이트 가능 목록은 `brew outdated --json=v2 --greedy`의 JSON을 `BrewOutdatedParser`가 읽어 만든다.
이 파서는 `installed_versions`가 배열로 올 때와 문자열 하나로 올 때를 모두 받아들인다.
텍스트 출력을 정규식으로 긁는 대신 brew가 제공하는 구조화된 출력을 쓴 것이, 이 앱이 작은 코드로도 안정적일 수 있는 이유다.

## 분석

### 이 앱은 brew를 대신하지 않고, brew를 감싼다

Homebrew GUI는 이번이 처음이 아니다.
GeekNews에도 같은 Brewery라는 이름으로 Homebrew 패키지 관리 GUI를 소개한 글이 이미 있다.
그 앱은 대시보드, 의존성 태그, cask의 `--zap` 삭제, `brew info` 원본 출력 같은 “관리” 기능에 무게를 뒀다.

brewery는 출발점이 다르다.
작성자가 없애려 한 것은 패키지 관리의 복잡함이 아니라, 매일 치는 세 줄의 반복이다.
그래서 화면의 중심은 큰 버튼 하나와 단계별 상태 카드이고, 설치 목록과 검색은 그 주변 기능이다.

구현도 이 방향을 따른다.
앱은 brew의 내부 API나 formula 파일을 직접 읽지 않고, 사용자가 터미널에서 치던 명령을 같은 순서로 실행해 그 출력을 보여 줄 뿐이다.
Homebrew가 명령 체계를 바꾸지 않는 한 앱이 깨질 여지가 적고, 사용자는 로그를 보며 터미널에서와 똑같은 일이 일어났는지 확인할 수 있다.

### 한 단계라도 실패하면 멈추는 설계는 셸의 `&&`를 옮겨 온 것이다

세 명령을 이어 치는 사람은 대개 `brew update && brew upgrade && brew upgrade --greedy`처럼 쓴다.
앞 단계가 실패하면 뒤 단계를 건너뛰는 이 셸의 규칙을, brewery는 파이프라인의 상태로 바꿨다.
실패한 단계의 카드는 빨갛게 바뀌고, 남은 단계는 건너뜀으로 표시된다.

이 설계의 가치는 실패가 눈에 보인다는 데 있다.
터미널에서 세 줄을 이어 치면, 중간의 실패 메시지는 긴 출력 속에 묻히기 쉽다.
단계별 카드와 종료 코드를 보여 주는 화면은 어디서 멈췄는지를 한눈에 알려 준다.

## 비평

### 비밀번호 문제는 GUI의 한계라기보다 표준 입력을 막은 결과다

작성자는 관리자 비밀번호가 필요한 cask가 GUI에서 비밀번호를 받을 수 없어 실패한다고 적고, 괜찮은 처리 방법에 대한 피드백을 청했다.
코드를 보면 이 실패는 설계의 결과다.
`BrewRunner`는 표준 입력을 `nullDevice`로 막고 `NONINTERACTIVE=1`을 넣으므로, cask 설치 스크립트가 `sudo`로 비밀번호를 물으면 대답할 곳이 없다.

이 문제에는 macOS 앱이 흔히 쓰는 길이 있다.
`sudo`는 `SUDO_ASKPASS` 환경 변수가 가리키는 프로그램을 불러 비밀번호를 받을 수 있고, 이 프로그램이 GUI 대화상자를 띄우면 터미널 없이도 비밀번호를 받을 수 있다.
다만 이 길은 비밀번호를 다루는 코드를 앱이 떠안는다는 뜻이고, 서명된 앱이 관리자 권한 입력 창을 띄우는 것 자체가 신뢰의 문제가 된다.
지금처럼 실패로 표시하고 터미널로 넘기는 방식은 불편하지만, 가장 적은 권한만 가진 선택이기도 하다.

### `--greedy`를 기본 흐름에 넣는 것은 가볍지 않은 선택이다

`brew upgrade --greedy`는 스스로 업데이트하는 앱, 곧 `auto_updates true`로 표시된 cask나 버전이 `latest`인 cask까지 업그레이드한다.
이런 앱은 보통 자체 업데이트 기능을 갖고 있어서, Homebrew는 기본적으로 이들을 건너뛴다.
brewery는 이 단계를 기본 흐름의 세 번째 단계로 넣었고, 메뉴바의 업데이트 개수도 `--greedy` 기준으로 센다.

그 결과 메뉴바의 숫자는 앱이 스스로 알아서 올릴 항목까지 포함한다.
또 `--greedy`는 앱이 이미 스스로 업데이트했는데도 Homebrew의 기록과 어긋나 같은 앱을 다시 내려받게 하거나, 실행 중인 앱을 교체하는 일이 생길 수 있다.
작성자의 일상에서는 세 줄이 정답이었겠지만, 모든 사용자에게 `--greedy`가 기본값으로 맞는지는 다른 문제다.
이 단계를 켜고 끄는 설정이 있다면, 버튼 하나의 단순함을 해치지 않고도 이 차이를 사용자에게 맡길 수 있다.

### 예약 실행은 이 앱의 성격을 바꾼다

작성자는 다음 기능으로 예약 실행과 업데이트 알림을 생각하고 있다고 밝혔다.
알림은 지금의 메뉴바 숫자를 조금 더 적극적으로 만드는 기능이지만, 예약 실행은 다르다.
사람이 버튼을 누르는 순간을 없애면, 로그를 보며 무엇이 바뀌었는지 확인하는 이 앱의 장점도 함께 사라진다.

Homebrew 업그레이드는 가끔 설정 파일을 바꾸거나, 주요 버전을 올리거나, 실행 중인 서비스를 멈춘다.
이것을 사람이 보지 않는 시간에 자동으로 돌리면, 무엇이 깨졌는지 알아차리는 시점이 늦어진다.
예약 실행을 넣는다면 formula만 대상으로 하거나, 주요 버전 변경은 건너뛰는 식의 범위 제한이 함께 필요할 것이다.

## 인사이트

### 개인의 반복 작업을 앱으로 만드는 비용이 크게 떨어졌다

brewery는 한 사람의 하루 습관에서 나온 앱이다.
세 줄의 셸 명령을 버튼으로 바꾸기 위해 SwiftUI 앱, 7개 언어의 String Catalog, 테마 3종, 서명과 공증과 tap 배포 스크립트까지 갖췄다.
예전 같으면 셸 별칭 하나로 끝냈을 일에, 작은 제품 하나의 완결된 배포 체계가 붙었다.

이런 앱이 늘어나는 것은 네이티브 앱을 만들고 배포하는 비용이 떨어졌다는 신호다.
`xcodegen`으로 프로젝트 파일을 코드로 관리하고, 서명과 공증과 cask 갱신을 스크립트 세 줄로 돌리는 흐름은, 한 사람이 주말에 끝낼 수 있는 범위가 됐다.
그 결과 같은 문제를 푸는 비슷한 앱이 같은 이름으로 여러 번 나오는 일도 생긴다.

### App Store에 올릴 수 없는 개발자 도구는 Homebrew가 유통망이 된다

작성자는 샌드박스 안에서는 brew를 실행할 수 없어 App Store에 올릴 수 없다고 밝혔다.
이것은 brewery만의 사정이 아니라, 다른 프로세스를 실행하거나 시스템 전역 파일을 다루는 개발자 도구 대부분이 겪는 일이다.
그런 도구에게 남은 유통 경로가 Developer ID 서명과 공증, 그리고 Homebrew cask다.

그래서 Homebrew를 관리하는 앱이 Homebrew로 설치되는 순환이 생긴다.
이 순환은 편리하지만, 앱의 업데이트도 결국 자기 자신이 실행하는 `brew upgrade`를 통해 이뤄진다는 뜻이다.
업그레이드 도중 앱 자신이 교체되는 경우를 어떻게 다루는지는, 이런 종류의 도구가 언젠가 마주칠 문제다.

### 좋은 래퍼는 원래 도구의 출력을 숨기지 않는다

brewery가 신뢰를 얻는 방식은 로그 창에 있다.
사용자는 버튼을 눌러도 brew가 실제로 출력한 내용을 한 줄씩 볼 수 있고, 실패한 단계에서는 종료 코드를 확인할 수 있다.
래퍼가 원래 도구의 출력을 감추고 “완료”만 보여 주면, 문제가 생겼을 때 사용자는 다시 터미널로 돌아가 같은 명령을 쳐야 한다.

이 원칙은 GUI 래퍼 전반에 적용된다.
편의를 더하되 원래 도구의 동작을 그대로 비춰 주는 래퍼는, 사용자가 언제든 터미널로 돌아갈 수 있게 해 준다.
brewery가 비밀번호가 필요한 cask를 조용히 건너뛰지 않고 실패로 표시하며 로그에 안내를 남기는 것도, 같은 원칙에서 나온 선택이다.
