# 헤드리스 Chrome이 남긴 앱 복제본 3만 7천 개가 Mac 부팅을 40분 멈춘 사건

원문: [Mac 부팅이 5%에서 멈추는 문제 (헤드리스 Chrome 앱 복제본 누적)](https://velog.io/@milcho0604/mac-%EB%B6%80%ED%8C%85%EC%9D%B4-5-%EC%97%90%EC%84%9C-%EB%A9%88%EC%B6%94%EB%8A%94-%EB%AC%B8%EC%A0%9C-%ED%97%A4%EB%93%9C%EB%A6%AC%EC%8A%A4-chrome-%EC%95%B1-%EB%B3%B5%EC%A0%9C%EB%B3%B8-%EB%88%84%EC%A0%81)

GN 토론: <https://news.hada.io/topic?id=35839>

## 소개

백엔드 개발자 밀초(milcho0604)가 velog에 쓴 장애 분석이다.
Mac이 부팅 진행률 5% 근처에서 멈췄고, 원인은 작성자가 만든 MCP 서버의 헤드리스
Chrome 렌더러였다.
이 문서는 글의 사실을 정리하고, 같은 상황에서 확인하고 고치는 순서로 다시
배열한다.
글의 수치와 소스 코드 서술은 모두 작성자의 것이며, 이 문서가 직접 재현하지는
않았다.

글에 따르면 증상은 두 번 나왔다.
9월 30일 새벽에 재시동하자 진행 막대가 5%에서 멈췄고, 여섯 번 강제로 끄고 켰으며
가장 오래 기다린 시도는 2,382초(약 40분)였다.
macOS를 재설치한 뒤에야 부팅됐고, 10월 11일에 같은 증상이 다시 나왔다.

## 동작 방식

### 부팅이 멈춘 곳은 임시 폴더 정리다

부팅에 실패한 여덟 번의 진단 기록은 모두 같은 상태였다.
`launchd`가 `dirhelper`가 끝나기를 기다렸고, `dirhelper`는 파일과 폴더를 지우는
자식 프로세스가 끝나기를 기다렸다.
`dirhelper -machineBoot`는 부팅 초기에 `/var/folders/.../X/`를 비우는
프로세스이고, 이 폴더는 평소에는 청소하지 않고 부팅 때만 지운다.

그 폴더 안에 Chrome 앱 복제본이 쌓여 있었다.

```text
X/com.google.Chrome.code_sign_clone/
  code_sign_clone.yQsZl2/
  code_sign_clone.7i8xMR/
  ... (9월 28일 기준 37,856개)
```

복제본 하나에는 Chrome 앱 전체가 들어 있고, 현재 설치된 앱 기준으로 파일과
폴더가 1,340개다.
37,856개면 약 5천만 항목이고, 당시 앱 구조에 따라 2,800만에서 9,600만 사이로
추정했다고 한다.

### Chrome은 실행할 때 앱을 복제하고 정상 종료할 때만 지운다

작성자는 Chromium의 `code_sign_clone_manager.mm`을 읽고 다음과 같이 설명한다.
macOS의 Chrome은 브라우저 프로세스를 띄울 때마다 앱 전체를 `X/` 아래에 복제한다.
`clonefile`로 만들기 때문에 디스크를 실제로 두 배 쓰지는 않지만 파일과 폴더
항목은 그대로 생긴다.
복제본을 지우는 정리 프로세스는 `CodeSignCloneManager`의 소멸자에서만 뜨므로,
`SIGKILL`이나 크래시로 끝나면 소멸자가 실행되지 않아 복제본이 재부팅 때까지
남는다.
남은 복제본을 나중에 찾아 지우는 기능은 같은 파일에 `TODO`로만
있다(crbug.com/343784575).

GeekNews에서 skageektp가 왜 앱을 통째로 복제하느냐고 묻자 작성자가 직접 답했다.
Chrome이 켜져 있는 동안 업데이트가 준비되면 돌고 있는 버전의 코드 서명이 맞지
않게 되는 문제가 있어서, 켤 때 앱을 복제해 두고 그것을 붙잡고 있는 방식인 것
같다는 것이다.[^milcho0604]
질문한 쪽도 답한 쪽도 소스 주석을 근거로 하는 해석이며 Chrome 쪽 공식 설명은 이
문서가 확인하지 못했다.[^skageektp]

### 렌더러가 매번 SIGKILL로 끝냈다

문제의 렌더러는 7월 31일에 넣은 다이어그램 렌더러였다.
새 헤드리스 Chrome이 결과 파일을 만든 뒤에도 종료되지 않아서, 결과 파일이 생기면
기다리지 않고 `SIGKILL`로 끝내게 했고, 당시 커밋 메시지는 90초가 3.9초로
줄었다는 것이었다.
이 변경으로 렌더마다 복제본이 남았다.
8월 11일 이후 49.8일 동안 재부팅하지 않는 사이 복제본이 8월에는 하루 450개,
9월에는 하루 1,000개쯤 늘어 37,856개가 됐고, 다음 재부팅이 9월 30일이었다.
렌더러 테스트(`npm test`)는 Chrome을 여러 번 띄우고 매번 `SIGKILL`로 끝내므로 한
번에 복제본이 37개 남았다고 한다.

## 값 정하기

### 40분을 설명하는 데는 항목 수만으로 부족하다

Chromium 소스 주석에는 복제본 하나를 지우는 데 M1 Max에서 약 20ms가 걸린다고
적혀 있다.
항목당으로 환산하면 14~29µs이고, 5천만 항목이면 12~25분이면 끝났어야 한다는
계산이다.
작성자는 부팅 직후 캐시 상태나, 한 폴더에 3만 7천 개가 모여 있고 복제본끼리
데이터 블록을 공유하는 구조가 삭제를 느리게 했을 수 있다고 보지만 얼마나
느려졌는지는 측정하지 못했다고 밝힌다.
즉 40분의 원인 가운데 설명되지 않은 부분이 남아 있다.

### 재설치가 해결책이 아니었다

macOS를 재설치해도 `/var/folders`는 지워지지 않았다.
설치 로그에서 이전 도구가 기존 `nq/`, `zz/` 폴더의 이름만 바꿔 그대로 옮겼다.
작성자는 재설치가 문제를 푼 것이 아니라 부팅을 시도할 때마다 `dirhelper`가
일부를 지웠고, 여러 번 시도하는 사이 삭제가 끝난 것으로 본다.
그래서 같은 증상이 생기면 재설치 전에 수십 분 기다려 볼 것을 권한다.

## 함정

작성자의 해결은 Chrome 실행 인자에 `--disable-features=MacAppCodeSignClone`을
넣는 것이다.
Chrome 155로 종료 방법별 테스트를 했다.

| 종료 방법                | 남은 복제본 |
| ------------------------ | ----------- |
| 플래그 없이 `SIGKILL`    | 1           |
| 플래그 없이 `SIGTERM`    | 1           |
| 플래그 추가 후 `SIGKILL` | 0           |

헤드리스 Chrome은 `SIGTERM`으로 끝내도 복제본이 남았으므로 종료 방식을 바꾸는
것으로는 해결되지 않았다는 것이 작성자의 결론이다.
렌더러에는 이 플래그를 넣고, 테스트 뒤 복제본 수가 늘었는지 확인하는 검사를
추가했다.
플래그를 빼고 돌리면 테스트 한 번에 37개가 남아 검사가 실패하고, 플래그를 넣으면
0개다.

적용에는 함정이 있다고 작성자는 적는다.

- `--disable-features`를 두 번 넣으면 Chrome은 마지막 것만 쓴다.
  다른 기능도 끄고 있다면 쉼표로 합쳐 한 줄로 써야 한다.
- Playwright는 내부적으로 자체 `--disable-features` 목록을 넣는다.
설치된 Chrome을 쓰면서 이 플래그를 `args`로 추가하면 Playwright의 목록을
덮어쓴다.
- Playwright가 기본으로 받는 Chrome for Testing과 `chrome-headless-shell`은 이
기능이 빠진 빌드라 복제본을 만들지 않는다.
  `channel: 'chrome'`처럼 설치된 Google Chrome을 쓸 때가 문제다.
- Playwright는 먼저 정상 종료를 시도하지만 제한 시간 안에 끝나지 않으면 프로세스
그룹에 `SIGKILL`을 보낸다.
Playwright MCP 서버도 종료 신호를 받고 15초가 지나면 무조건 종료되는데, 그때
Chrome이 실행 중이면 `SIGKILL`로 같이 끝난다.

## 확인하기

내 Mac에 복제본이 쌓이는지는 아래 명령으로 센다.
작성자의 명령이며 이 문서가 실행해 보지는 않았다.

```bash
ls "$(dirname "$(getconf DARWIN_USER_TEMP_DIR)")/X/com.google.Chrome.code_sign_clone" | wc -l
```

실행 중인 Chrome 하나당 하나씩 있는 것은 정상이다.
수백, 수천 개가 나오면 헤드리스 Chrome을 띄우는 도구 중 하나가 강제 종료로
끝나고 있을 가능성이 크다고 한다.
지울 때는 Chrome을 모두 종료한 뒤에 지우는 편이 안전하다고 한다.
작성자는 이 렌더러가 `velog-mcp`에 있었고 0.9.6에서 고쳤다고 하며, 0.9.5 이하를
쓰면 올리라고 안내한다.

## 체크리스트

- 헤드리스 Chrome을 직접 띄우는 도구(스크립트, MCP 서버, 테스트 러너)를 쓰고
있는가.
- 그 도구가 Chrome을 `SIGKILL`로 끝내는가, 아니면 제한 시간 뒤에 강제로
끝내는가.
- 위 명령으로 센 복제본이 수백 개를 넘는가.
- 실행 인자에서 `--disable-features`가 한 번만, 쉼표로 합쳐져 있는가.
- Playwright에서 설치된 Chrome 채널을 쓰면서 `args`로 이 플래그를 넣었다면
Playwright의 기본 목록이 덮이지 않았는가.
- 몇 주 넘게 재부팅하지 않는 머신인가.

## 기억할 원칙

### 강제 종료는 정리 코드를 건너뛴다

이 사건의 구조는 단순하다.
정리를 소멸자에 맡긴 프로그램을 소멸자가 실행되지 않는 방식으로 끝내면 정리
대상이 쌓이고, 그 비용은 몇 주 뒤 부팅 때 한꺼번에 청구된다.
빠르게 끝내려는 최적화(90초를 3.9초로)가 그 비용을 장기로 미뤘다는 점이 이
글에서 가져갈 교훈이다.
같은 프로그램을 자동화에서 반복 실행한다면 한 번의 종료가 남기는 흔적을 세어
보고 그 개수를 검사에 넣는 것이 작성자가 택한 방어다.
