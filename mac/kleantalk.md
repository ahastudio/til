# KleanTalk: 맥용 카카오톡의 광고 자리를 빈 공간으로 바꾸는 macOS 앱

<https://emzlabs.com/kleantalk/>

<https://github.com/showmeyourway-sketch/KleanTalk>

## 소개

KleanTalk는 맥용 카카오톡(KakaoTalk for Mac)의 광고 자리를 카카오톡 창과 같은
색의 빈 공간으로 바꾸는 Swift 앱이다.
개발자는 카카오톡 앱 파일을 고치거나 다시 서명하지 않고,
대화 내용과 설정에도 손대지 않는다고 주장한다.
카카오와 관계없는 비공식 개인 프로젝트이며,
README는 카카오톡 이용약관과 맞지 않을 수 있으니 확인하고 쓰라고 적어 둔다.
라이선스는 MIT다.

저장소는 2026년 10월 27일에 만들어졌고,
같은 날부터 이틀 사이에 v1.1부터 v1.8까지 릴리스 8개가 나왔다.
별은 5개, 포크는 2개, `main`의 커밋은 17개다.
지원 환경은 macOS 12(Monterey) 이상의 Apple Silicon과 Intel 맥이고,
확인한 카카오톡 버전은 26.9.0이다.

릴리스 노트를 보면 지원 범위가 빠르게 넓어졌다.
v1.1은 macOS 14 이상의 Apple Silicon만 대상이었다.[^v11]
v1.2가 Intel 맥을 추가했고, v1.5가 macOS 12와 13으로 내려갔다.[^v12][^v15]

## 동작 방식

### 광고를 막기만 하면 안 되는 이유

개발 노트에 따르면 카카오톡은 광고 요청이 실패하면 앱 안에 들어 있는 홍보 배너를
대신 띄운다.[^dev]
그 문구는 카카오 서버가 보내 준다고 노트는 적는다.[^dev]
그래서 광고 주소를 막는 것으로는 광고 자리가 비지 않는다.
KleanTalk는 광고 요청을 성공시키되 내용만 비우는 쪽을 택했다.

### 네 단계

README가 설명하는 흐름은 다음과 같다.

1. `/etc/hosts`에서 광고 주소 `display.ad.daum.net`과 `analytics.ad.daum.net`을 막는다.
2. 카카오톡이 광고를 받아 오는 주소 `serv.ds.kakao.com`은 이 맥 안의 작은 서버로 돌린다.
3. 그 서버가 진짜 광고 서버와 같은 형식의 빈 광고를 돌려준다.
4. 진짜 광고 서버에는 연결하지 않으므로 광고 이미지, 추적 코드, 노출 집계도 오가지 않는다.

서버는 전용 루프백(loopback) 주소 `127.84.11.1`의 443 포트에서만 받는다.
`127.0.0.1:443`을 쓰는 Docker, 로컬 웹 서버,
mitmproxy와 부딪치지 않게 하려는 선택이라고 개발 노트는 설명한다.[^dev]
`serv.ds.kakao.com`의 IPv6 주소는 막아 두어서,
카카오톡이 곧바로 IPv4 전용 주소로 연결하게 한다.[^dev]

### 빈 광고의 응답 형식

개발자는 mitmproxy로 실제 응답을 확인했다고 적는다.[^dev]
응답은 `status`, `id`, `ads[]`, `options`로 된 JSON이고,
광고 하나에는 `content`(HTML), `mimeType`, `width`와 `height`, `feedback`,
`dspId`, `bidId`, `etxId`, `cid`와 `crid`와 `adid`, `type`이 들어 있다.[^dev]
`content`만 바꾸고 나머지 값도 진짜와 같은 모양으로 채워야 카카오톡이
받아들인다고 한다.[^dev]
비워 두면 카카오톡은 한 번 다시 요청한 뒤 광고 자리를 짙은 회색(`#1E1E1E`)으로
비워 둔다.[^dev]

광고 HTML과 앱 사이에도 신호가 있다.
원래 광고 HTML은 앱이 `ReadyToListen`을 보내면 `window.chrome.webview`로
`AdLoaded` 이벤트를 답한다.[^dev]
빈 광고 HTML도 같은 신호를 보낸다.[^dev]

### 색을 맞추는 방법

빈 광고의 색은 다크 모드에서 실측한 값이다.
사이드바는 폭 77px에 `#2D2D2D`, 구분선은 1px에 `#383838`,
목록은 `#222222`다.[^dev]
개발 노트는 이 값 덕분에 창과 픽셀 단위로 같다고 적는다.[^dev]
라이트 모드는 아직 실측하지 않았다.

## 설치와 제거

### 설치

1. 릴리스의 DMG를 받아 `KleanTalk.app`을 응용 프로그램 폴더로 옮긴다.
2. 앱은 Apple 공증을 받지 않았으므로 처음 열 때 경고가 뜬다. 시스템 설정의 개인정보 보호 및 보안에서 그래도 열기를 누른다.
3. 언어를 고르고 설치를 누른다. 암호를 두 번 묻는다.
4. 카카오톡이 자동으로 다시 시작되고 광고 자리가 비게 된다.

첫 번째 암호는 서버와 hosts를 설치하는 관리자 권한이고,
두 번째는 macOS가 인증서 신뢰 설정을 확인하는 단계다.
설치가 끝나면 로그인할 때 창 없이 실행되어 설정이 풀렸는지 가끔 확인한다.
개발 노트에 따르면 6시간마다 상태를 보고, 작동하지 않으면 창을 띄운다.[^dev]
상태는 카카오톡처럼 `https://serv.ds.kakao.com/sdk/banner`를 요청해 보고,
응답에 서버의 `X-KleanTalk: 1` 헤더가 있으면 작동 중으로 판단한다.[^dev]

### 이 맥에서 바뀌는 것

README는 바뀌는 항목을 표로 밝힌다.

| 항목              | 위치                                                            |
| ----------------- | --------------------------------------------------------------- |
| hosts             | `/etc/hosts`의 `KakaoAdBlock` 블록                              |
| 빈 광고 서버      | `/Library/Application Support/KleanTalk/AdServer/`              |
| 백그라운드 서비스 | `/Library/LaunchDaemons/com.myungchul.kleantalk.adserver.plist` |
| 루프백 주소       | `lo0`의 `127.84.11.1`                                           |
| 인증서 신뢰       | 사용자 신뢰 설정                                                |
| 로그인 시 실행    | `~/Library/LaunchAgents/com.myungchul.kleantalk.plist`          |

설치 스크립트를 읽으면 몇 가지가 더 보인다.
`/etc/hosts`는 처음 고치기 전에 `/etc/hosts.kakaoadblock.bak`으로
백업한다.[^script]
서버는 LaunchDaemon으로 등록되어 항상 실행되고(`RunAtLoad`, `KeepAlive`),
설치 끝에 DNS 캐시를 비우고 `mDNSResponder`를 다시 띄운다.[^script]

### 제거

앱의 제거 버튼이 서버, 인증서 신뢰, hosts 설정,
로그인 시 실행을 모두 되돌리고 앱을 휴지통으로 옮긴다고 README는 설명한다.
터미널로 서버만 설치하고 지우는 스크립트도 따로 있다.

## 신뢰와 권한 설계

광고 서버를 맥 안에서 흉내 내려면 카카오톡이 HTTPS로 접속하는 주소에서 유효한
인증서를 내놓아야 한다.
KleanTalk가 이 문제를 푸는 방식은 신뢰의 범위를 가능한 한 좁히는 것이다.

| 요소      | 설계                                                                                                  |
| --------- | ----------------------------------------------------------------------------------------------------- |
| 인증서    | `serv.ds.kakao.com` 한 이름에만 쓰는 일반 인증서(`CA:FALSE`), 용도는 서버 인증만, 유효 825일[^script] |
| 신뢰 등록 | 사용자 계정의 신뢰 설정에, 그 이름의 SSL 서버 인증에만 등록                                           |
| 키        | root만 읽을 수 있는 폴더의 `key.der`, 모드 600[^script]                                               |
| 서버 권한 | 443 포트를 연 뒤 `nobody`로 권한을 낮춤                                                               |
| 접속 범위 | 전용 루프백 주소에서만 받아 다른 기기가 접속할 수 없음                                                |

개발 노트가 밝히는 구현상의 제약도 있다.
자기 서명 인증서라서 신뢰는 `trustRoot`로 등록해야 하고,
`trustAsRoot`는 매개변수 오류가 난다고 한다.[^dev]
관리자 권한 스크립트 안에서 `security add-trusted-cert`를 쓰면 사용자 상호작용이
불가능하다는 이유로 거부된다.[^dev]
그래서 신뢰 등록은 앱이 사용자 권한으로 따로 한다.[^dev]
이것이 설치할 때 암호를 두 번 묻는 이유다.
다시 설치할 때 인증서가 30일 넘게 남아 있으면 그대로 써서 신뢰 확인 창이 다시
뜨지 않는다.[^dev]

## 업데이트와 배포

앱은 Sparkle 2.10.0을 넣어 하루에 한 번 새 버전을 확인한다.[^dev]
피드 주소는 저장소의 최신 릴리스에 있는 `appcast.xml`이다.[^dev]
앱은 ad-hoc 서명이라서 Sparkle은 코드 서명 대신 EdDSA 서명으로 업데이트를
확인한다고 노트는 설명한다.[^dev]
비공개 서명 키는 개발 맥의 로그인 키체인에 있고,
잃어버리면 업데이트를 서명할 수 없다.[^dev]
개발자는 로컬 시험에서 다운로드, 서명 확인, 교체,
재실행이 3초 안에 끝났다고 적는다.[^dev]

업데이트에 서버 변경이 들어 있으면 설치된 서버와 앱 안의 서버의
SHA-256이 달라진다.
그러면 상태 화면에 다시 설치 버튼이 나오고,
누르면 관리자 암호를 한 번 묻는다.[^dev]
v1.6은 카카오톡 창을 다시 클릭할 때 광고 자리가 잠깐 하얗게 깜빡이던 문제를
고치면서 이 재설치를 요구했다.[^v16]

| 한계             | 내용                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------- |
| 카카오의 변경    | 광고 주소, 응답 형식, 광고 HTML과 앱 사이의 신호가 바뀌면 동작하지 않을 수 있음             |
| 라이트 모드      | 빈 광고 색을 다크 모드에서만 실측했음                                                       |
| 인증서 기한      | 825일(macOS가 허용하는 최대)이며, 다가오면 상태가 작동하지 않음으로 바뀌어 다시 설치해야 함 |
| 시스템 전체 적용 | hosts는 맥 전체에 적용되어 브라우저에서도 위 카카오·다음 광고 주소가 막힘                   |
| 이용약관         | 카카오톡 이용약관과 맞지 않을 수 있다고 개발자 스스로 경고함                                |

개발 노트에는 이전 방식도 기록되어 있다.
처음에는 광고 자리 위에 같은 색의 창을 띄우는 가림판을 썼다.
창 순서, 데스크톱 전환, Mission Control 때마다 깜박임과 어긋남을 완전히 없앨 수
없어서 지금의 빈 광고 방식으로 바꿨다고 한다.[^dev]

## 분석

### 막는 대신 성공시키는 설계

이 프로젝트의 중심 판단은 광고 요청을 실패시키지 않고 성공시킨다는 것이다.
카카오톡이 요청 실패를 감지하면 내장 배너로 되돌아가는 구조이므로,
클라이언트가 기대하는 응답을 서버가 내놓는 쪽이 광고를 지우는 가장 직접적인
길이 된다.[^dev]
그 대가로 응답 형식을 정확히 알아야 한다.
개발 노트가 `dspId`, `bidId`, `etxId` 같은 필드까지 진짜와 같은 모양으로 채워야
한다고 적는 것은, 카카오톡이 응답의 일부 필드를 검증한다는 뜻이다.[^dev]
이 검증의 범위는 개발자가 관찰한 한도까지만 알려져 있고,
어떤 필드가 필수인지에 대한 공식 자료는 없다.

카카오톡 쪽에서 보면 이 설계가 합리적으로 보이는 이유도 있다.
프록시로 요청을 가로채는 광고 차단 도구가 카카오톡의 서비스 자체를 막아 버린다는
GeekNews 댓글이 있다.[^kang1027]
이 댓글은 다른 도구(Zen)에 대한 보고이므로 KleanTalk에 그대로 적용할 수는 없다.
다만 카카오톡이 광고 경로의 이상에 민감하게 반응할 수 있다는 정황이고,
실패 대신 정상 응답을 주는 편이 그 반응을 피하는 방법이라는 해석과 맞는다.

### 신뢰 범위를 좁히는 방식

로컬에서 TLS를 종단하는 도구는 신뢰 설정을 건드리므로,
실패했을 때의 피해가 얼마나 퍼지는지가 안전성을 가른다.
KleanTalk는 세 가지로 범위를 좁힌다.
인증서가 인증 기관이 아니라서 다른 이름의 인증서를 만들 수 없고,
신뢰가 그 호스트 이름의 서버 인증과 현재 사용자에게만 등록되며,
키가 root 전용이다.[^script]
이 설계가 의도대로 작동한다면 키가 유출되어도 공격자가 흉내 낼 수 있는 대상은
`serv.ds.kakao.com` 하나다.
그 이름이 가리키는 서비스가 카카오의 광고 서버라는 점이 피해 범위를 한정하는 두
번째 요인이다.

### 업데이트 경로의 위치

업데이트는 두 층으로 나뉜다.
앱 껍데기는 Sparkle이 사용자 권한으로 교체하고,
root 권한이 필요한 서버와 hosts 변경은 관리자 암호를 다시 묻는 재설치로만
바뀐다.[^dev]
그래서 자동 업데이트가 사용자 몰래 root 영역을 바꾸지는 못하는 구조다.
이 구조는 설계 문서의 설명과 설치 스크립트에서 확인되지만,
실제로 그렇게 동작하는지는 이 문서를 쓰면서 실행해 보지 않았다.

## 비평

### 신뢰의 뿌리가 개발자 개인의 키체인에 있다

앱은 공증을 받지 않았고 ad-hoc 서명이라 macOS의 서명 검증이 보증하는
것이 없다.[^dev]
그 빈자리를 채우는 것이 Sparkle의 EdDSA 서명이고,
서명 키는 개발자의 개발 맥 로그인 키체인에 있다.[^dev]
그러므로 업데이트를 믿는다는 것은 그 개발 맥의 보안과 개발자의 계정을
믿는다는 뜻이다.
또 이 앱은 root 권한의 LaunchDaemon과 hosts 수정과 인증서 신뢰 설정을 한
번에 요구한다.
요구하는 권한이 큰 도구일수록 사용자는 소스를 읽어야 하는데,
저장소는 만든 지 이틀이 지난 시점이고 별이 5개다.
이 숫자는 검증된 사용자 기반이 아직 없다는 사실만 말해 준다.
이 주장이 틀렸다고 판단할 수 있는 관찰은,
독립된 사람이 소스를 읽고 설치 스크립트의 동작을 확인했다는 기록이다.

### 지속 가능성이 가장 약한 지점은 카카오의 선택이다

동작 전체가 카카오톡의 광고 주소, 응답 형식,
광고 HTML과 앱 사이의 신호에 기댄다.[^dev]
이 중 어느 것도 공개된 인터페이스가 아니고,
개발 노트에 적힌 형식은 개발자가 mitmproxy로 관찰한 결과다.[^dev]
카카오톡이 업데이트되어 한 곳이라도 바뀌면 빈 광고가 거부되고,
앞서 본 대로 요청이 실패한 것으로 처리되어 홍보 배너가 돌아올 수 있다.
이틀 만에 릴리스가 8개 나온 것은 개발 속도를 보여 주지만,
릴리스 노트의 내용은 창 구성, 지원 환경, 업데이트와 신고 기능이 대부분이다.
핵심 방식이 카카오의 새 버전에서 얼마나 오래 버티는지는 아직 관찰되지 않았다.
확인된 카카오톡 버전이 26.9.0 하나라는 점이 이 불확실성의 크기를 말해 준다.

### 시스템 전체에 미치는 영향이 설치의 비용으로 충분히 드러나지 않는다

README는 hosts가 맥 전체에 적용되어 브라우저에서도 카카오·다음 광고 주소가
막힌다고 밝힌다.
이것은 숨기지 않은 부작용이지만, 설치 화면에서 사용자가 이 사실을 보는지는
확인하지 못했다.
또 `analytics.ad.daum.net`을 막는 일은 광고를 지우는 것을 넘어 카카오와 다음
쪽의 노출 집계를 끊는다.
개발자는 이를 추적 코드가 오가지 않는 장점으로 소개한다.
같은 사실이 광고 사업자에게는 계측 누락이므로,
개발자가 직접 경고한 이용약관 문제의 한 갈래가 된다.
이 문서는 카카오톡 이용약관의 실제 조항을 확인하지 않았으므로,
위반 여부는 판단하지 않는다.

## 인사이트

### 실패하는 경로를 막으면 대체 경로가 열린다

광고 요청을 막았더니 내장 배너가 나온다는 것이 이 프로젝트의 출발점이다.
이것은 클라이언트가 실패 경로에 대체 콘텐츠를 준비해 두었을 때 생기는
일반적인 형태다.
차단하는 쪽이 이기려면 실패시키지 않고 비어 있는 성공을 줘야 한다.
이 구조에서는 차단 도구가 클라이언트의 정상 응답 모양을 알고 있어야 하고,
클라이언트 제작자가 응답 형식을 조금만 바꿔도 차단 도구가 깨진다.
그래서 이런 도구의 수명은 기술적 완성도가 아니라 상대방이 형식을 바꾸는
빈도로 정해진다.
이 해석을 바꿀 관찰은 카카오톡이 여러 번 업데이트되는 동안 형식이 그대로
유지되는 것이다.

### 가림판에서 빈 응답으로 옮긴 것은 개입 지점의 이동이다

처음 방식은 화면 위에 같은 색의 창을 덮는 것이었고,
창 순서와 데스크톱 전환에서 깜박임을 없앨 수 없었다.[^dev]
지금 방식은 화면이 아니라 데이터를 바꾼다.
화면 계층에서 일하면 운영체제의 창 관리 규칙과 싸워야 하지만,
데이터 계층에서 일하면 상대의 응답 규칙을 알아야 한다.
어느 쪽이 더 안정적인지는 상대가 무엇을 자주 바꾸는지에 달려 있다.
운영체제의 창 관리는 연 단위로 바뀌고, 광고 서버의 응답은 광고 사업자의 사정에
따라 바뀐다.
선택의 기준을 이렇게 상대의 변경 빈도로 놓으면,
앞으로 이 프로젝트가 다시 방식을 바꿀 때 어떤 선택지로 갈지 예측하기 쉬워진다.

### 도구를 설치하는 일은 신뢰 범위를 얼마나 좁힐 수 있는지의 문제다

root 권한과 인증서 신뢰를 요구하는 도구를 쓰는 것이 합리적인지는 도구가 얼마나
좁은 권한을 쓰는지에 달려 있다.
KleanTalk는 인증서, 신뢰, 서버 접속 범위를 모두 한 호스트 이름과 한 루프백
주소로 좁힌 설계를 선택했다.[^script]
좁힌 범위를 사용자가 직접 확인할 수 있게 하는 방법이 있다.
설치 스크립트와 개발 노트를 공개하고, 바뀌는 항목을 표로 밝히고,
제거 버튼이 모두 되돌리게 하는 것이다.
이 세 가지는 이 저장소에 이미 있다.
남은 간극은 그 설명이 실제 동작과 일치하는지 제3자가 확인했다는 기록이다.
설치를 고민하는 사람이 할 수 있는 현실적인 확인은
`scripts/install-adserver.sh`를 먼저 읽고,
설치 전후로 `/etc/hosts`와 `/Library/LaunchDaemons/`를 비교해 보는 것이다.
