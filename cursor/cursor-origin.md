# Cursor · Origin: 에이전트 시대를 위한 Git 포지

> A git forge for the agentic era
>
> Code is moving faster than any infrastructure was built to handle.
>
> Origin was designed for this moment.

<https://cursor.com/origin>

## 출시 전: 트윗 하나와 웨이트리스트로 발표됐다

트윗: <https://twitter.com/cursor_ai/status/2067012220832329782>

발표 HN 토론: <https://news.ycombinator.com/item?id=48558605> (23점, 8개 댓글)

2026년 6월 16일, Cursor는 코드 스토리지와 git 호스팅 서비스 Origin을 발표했다.
발표 형식이 특이했다 — 기술 블로그 없이 트윗과 웨이트리스트뿐이었다.

배경에는 같은 날 열린 Cursor의 Compile 컨퍼런스가 있다.
HN에서 Graphite·Cursor 소속을 밝힌 gen220에[^gen220] 따르면 Origin은 Graphite 공동창업자 Tomas가
컨퍼런스 무대에서 직접 발표했으며, 컨퍼런스 발표가 언론 보도 역할을 대신한 셈이다.
Mattwmaster58도[^mattwmaster58] 컨퍼런스 무대에서 발표됐는데 블로그 포스트가 없었다고 맥락을
보충했다.

## 발표 당시 내세운 것

“에이전트 시대를 위한 git 포지(forge)”를 표방하며, 팀과 에이전트가 코드를 호스팅하고 리뷰하고
협업하는 장소를 제공한다고 했다.
출시는 2026년 가을 예정이었고 웨이트리스트를 운영했다.

기술적 기반은 Cursor의 2024년 Graphite 인수에서 비롯된다.
Graphite는 빠르게 움직이는 팀을 위한 스택형 풀 리퀘스트(stacked pull requests) 도구로 주목받았던
코드 리뷰 스타트업이고, Origin은 이 리뷰 인프라를 AI 에이전트 환경에 맞게 재설계한다는 것이었다.

데모에서 공개된 수치는 초당 22.6 커밋, 시간당 수십만 클론, 글로벌 동기화 레이턴시 400ms 이하다.
기술적 특징으로는 네 가지를 들었다.

- MCP 확장성 — 에이전트가 포지와 프로그래밍 방식으로 상호작용하는 인터페이스
- 자동화된 머지 컨플릭트 해소 — 에이전트가 충돌을 자율적으로 처리
- CI·빌드 실패 자동 복구
- NVMe와 S3를 결합한 하이브리드 스토리지로 무한 레플리카 지원

스택형 풀 리퀘스트는 Graphite에서 이어받은 핵심 기능으로 제시됐다.

## 같은 날 있었던 다른 두 발표

Origin이 발표된 날은 SpaceX의 나스닥 IPO 당일이자 SpaceX가 Cursor를 $600억에 인수한다고 선언한
당일이기도 하다.
이 겹침이 이후 모든 논의의 배경이 됐다 — Origin에 코드를 호스팅한다는 것은 SpaceX가 소유한
인프라에 코드를 맡기는 것이 되기 때문이다.

발표 시점에 데이터 처리 정책, 코드 소유권 조건, 훈련 데이터 활용 여부에 대한 공개 문서는 없었다.
Grok V9-Medium이 실제 Cursor 워크플로우 데이터로 훈련되었다는 점을 감안하면, Origin에 호스팅된
코드가 미래 SpaceX AI 모델의 훈련 자원이 될 가능성은 합리적 우려의 범위 안에 있었다.

## 발표 직후 반응: 정보가 없다는 불만

발표 HN 스레드는 23점 8개 댓글로 조용했고, 내용은 대체로 정보 부재에 대한 지적이었다.

jarbus는[^jarbus] “사이트가 고장난 건지, 아니면 HN 포스트 제목 외에 정보가 아예 없는 건지
모르겠다. 이렇게 정보가 없는 웨이트리스트는 처음 봤다”고 했다.
22.6 커밋/초라는 수치는 인상적이지만 그것은 성능 주장이지 설계 주장이며, GitHub도 적절한 분산
시스템 설계로 유사한 처리량을 달성할 수 있다.
“의미론적 diff”와 “기계 판독 가능한 머지 상태”가 실제로 어떻게 구현됐는지는 알려진 바가 없었고,
이 개념들은 수십 년간 연구돼 왔지만 완전히 해결된 문제가 아니다.

newaccountman2는[^newaccountman2] 더 근본적인 반론을 냈다.
“이 분야에서 좋은 것들은 대부분 LLM과 무관하다. LLM으로 많은 코드를 생성하는 것은 일반적인 PR과
PR 리뷰로 충분히 잘 맞아 들어간다”는 것이다.
이 주장은 Origin의 핵심 전제 — 에이전트 시대에 git 인프라의 전면 재설계가 필요하다 — 를 직접
부정한다.

## 출시 발표: 2026년 8월 체인지로그

체인지로그: [Origin Code Hosting · Cursor](https://cursor.com/changelog/origin-code-hosting)

출시 HN 토론: <https://news.ycombinator.com/item?id=49334209> (457점, 360개 댓글)

GitHub 장애 영향 HN 토론: <https://news.ycombinator.com/item?id=49336919> (66점, 27개 댓글)

GN 토론: <https://news.hada.io/topic?id=32621> (네이티브 댓글은 아래 “GN 반응” 절에 정리)

발표 두 달 뒤 Origin이 실제로 나왔고, 체인지로그의 첫 문장은 “Cursor can now host your code”다.
얼리 베타로 모든 유료 플랜에 당일부터 순차 적용되며, 예외는 관리자가 옵트아웃한 엔터프라이즈
조직뿐이다.
이번 범위를 “essentials, designed for agent scale”이라고 규정하며 저장소, 풀 리퀘스트, 코드
브라우징, GitHub 동기화 넷을 들고 “에이전트 네이티브 기능은 곧 출시된다”고 덧붙였다.

저장소는 새 Codebase 탭에서 만든다.
`+New`로 저장소를 만들면 CLI 설치 방법과 클론·푸시 명령이 안내되고, 푸시하면 코드가 Origin에
호스팅된다.
첫 저장소를 만들 때 정한 코드베이스 이름이 이후 모든 저장소 URL의 일부가 된다 —
`cursor.com/codebase/acme-corp` 형태다.

GitHub 저장소는 Origin이 호스팅하는 것과 나란히 놓인다.
GitHub를 연결하고 조직을 고르면 동기화 가능한 저장소 목록이 보이고, 선택하면 Cursor가 끌어온다.
무엇을 동기화할지 고를 수 있고 언제든 연결을 끊을 수 있으며, 동기화된 저장소에 읽기나 쓰기 권한이
있는 사람은 누구나 Cursor에서도 볼 수 있다.
동기화된 저장소는 실시간으로 갱신되고 Origin의 복사본에서 브라우징·검색·풀이 가능하지만, 푸시는
계속 GitHub로 가며 GitHub가 그쪽에서 시작된 것의 소스 오브 트루스로 남는다 — 저장소 이름 옆
아이콘이 Cursor 호스팅과 GitHub 출신을 구분한다.

풀 리퀘스트는 모든 저장소에 있고 타임라인·커밋·체크·변경 파일을 보여 준다.
동기화된 저장소의 PR은 양방향으로 동기화되어 Cursor에서 남긴 코멘트가 GitHub에 올라가고 GitHub의
반응이나 답글이 몇 초 안에 Cursor에 나타나며, GitHub에서 할당된 리뷰를 Cursor에서 검토하고 머지할
수 있다.
에이전트는 모든 저장소에 붙는다 — 브라우징 중인 코드에 질문하면 답하거나 변경하거나 PR을
갱신하거나 브랜치를 푸시한다.

앱 확장으로는 Vercel·Depot·Buildkite 통합이 제공된다.
저장소의 Apps 탭에서 Vercel을 연결하면 모든 PR에 프리뷰 배포가 붙고 머지하면 프로덕션으로 나가며,
CI는 Depot이나 Buildkite를 연결하는데 둘 다 기존 GitHub Actions 워크플로를 실행하고 Buildkite는
자체 파이프라인도 돌린다.
저장소별 설정에서 GitHub 동기화 상태, 접근 권한, 연결된 앱을 관리한다.

## 6월의 약속과 8월의 출시 사이

발표 때 내세운 것 — 초당 22.6 커밋, MCP 확장성, 자동 머지 컨플릭트 해소, CI 실패 자동 복구,
NVMe·S3 하이브리드 스토리지, 스택형 PR — 은 체인지로그에 하나도 없다.
실제로 나온 넷은 모두 2008년 GitHub의 기능 집합이며, 에이전트 규모가 실제로 요구하는 것 —
에이전트별 신원과 권한, 커밋 서명, 감사 로그, 동시 PR 충돌 처리, 호출량 상한 — 은 언급되지 않는다.
“Agent-native features ship soon”이라는 한 줄이 그 공백에 대한 자기 인정이다.

HN에서 이 격차가 곧바로 지적됐다.
GitHub 클론 이상을 기대했는데 실망스럽고 에이전틱 워크플로 시대의 협업과 형상 관리에는 혁신할 공간이
많다는 반응[^dutchCourage], 블로그만으로는 GitHub와 무엇이 다른지 알기 어려우며 PR을 보다가
에이전트에게 변경을 요청할 수 있다는 것이 전부인지, 워크트리 문제를 푸는 것 같은 근본적 차이도
있는지 묻는 질문[^jjcm-diff]이 그것이다.
GitHub식 작업 방식은 이미 구시대적이고 PR·이슈·CI는 전부 사라질 것이므로 Cursor라면 그것을 대체할
새 기본 요소를 이끌어야 한다는 요구도 나왔다[^hahahaa].

가장 실무적인 요청은 처리량이었다.
에이전트는 사람보다 훨씬 빠르게 움직이는데 SaaS는 높은 RPS를 감당하도록 설계돼 있지 않아 레이트
리밋이 낮고, 자기가 직접 호스팅하는 것이 상업 호스트보다 빠르며, 남의 불만에 시달리지 않고 자기
인스턴스를 마음껏 두드릴 수 있는 전용 테넌시를 원한다는 것이다[^arjie].
“agent scale”이라는 표현의 진짜 시험대가 이 요청이고, 체인지로그는 그것을 다루지 않는다.

## 프라이버시 모드를 낮추지 않으면 쓸 수 없다

발표 시점의 훈련 데이터 우려는 추론이었는데, 출시 후 제품의 설정 화면에서 확인됐다.

한 사용자가 보고한 문구가 이렇다 — “Legacy Privacy Mode에서는 코드 저장이 비활성화되므로
Codebase를 설정할 수 없습니다. 계속하려면 아래에서 다른 개인정보 보호 모드로 전환하세요.”
그리고 다른 선택지는 Cursor의 훈련을 위해 데이터를 공유하는 모드뿐이라는 것이며, 같은 사용자의
마무리 문장이 함의를 요약한다 — 결국 모든 코드베이스를 가져가겠다는 뜻이다[^real-hacker].

배포 정책과 함께 봐야 한다.
Origin은 옵트인이 아니라 모든 유료 플랜에 기본 적용이고 옵트아웃은 엔터프라이즈 관리자에게만
있으며, 출시 당일 닫기 옵션이 없는 “Try Origin” 모달이 떠서 프로세스를 강제 종료해야 했다는 보고도
나왔다[^TowerTall].
얼리 베타를 조직의 가장 민감한 자산에 기본 활성으로 밀어 넣은 것이고, 여기에 프라이버시 모드 전환
요구가 겹치면 “써 보라”는 권유와 “데이터를 넘겨라”는 요구가 같은 클릭에 담긴다.
동기화된 저장소에 GitHub 읽기·쓰기 권한자가 자동으로 열람 권한을 얻는다는 사양은 접근 통제 평면을
하나 늘린다 — 그 조직이 Cursor 계정 관리를 GitHub만큼 엄격히 운영하고 있는지는 별개 문제다.

이 구조의 유인을 한 참가자가 냉소로 정확히 짚었다 — 오히려 무료로 풀었으면 나중에 훈련 데이터로
값을 다 회수했을 텐데 유료 기능으로 한 것이 기회를 놓친 것이라는 관측이다[^whywhywhywhy].

## 소유 구조: 반발의 규모가 뒤집혔다

발표 때 23점 8개 댓글이던 반응이 출시 때 457점 360개 댓글이 됐고, 상위 댓글의 성격이 기능 논평이
아니라 소유 구조 거부다.

이 스레드에서 반드시 짚어야 할 것은 비판의 축이 제품이 아니라는 점이다.
상위 댓글 대부분은 Origin의 기능이 부족하다거나 GitHub보다 못하다고 말하지 않는다 — 소유자가
누구인지를 이유로 이 서비스를 쓰지 않겠다고 말한다.
기능 비판(“GitHub 클론이다”, “agent scale이 증명되지 않았다”)은 있지만 상위에 오른 것도, 반복된
것도, 절대 쓰지 않겠다는 결론으로 이어진 것도 소유 구조 쪽이다.
그리고 그 거부의 근거로 제시되는 것은 추상적 기업 리스크가 아니라 특정 인물의 행적 — 시민 데이터
확보 시도, 허가 없는 코드 업로드 적발, 그리고 뒤에서 다룰 콘텐츠 관련 사건 — 이다.
즉 이 발표에 대한 시장의 1차 반응은 “이 제품이 좋은가”가 아니라 “이 사람에게 우리 코드를 맡길
수 있는가”였다.

이것이 제품 평가에도 영향을 준다.
소유자 신뢰가 채택의 선행 조건이 되면 기능 개선으로는 해소되지 않으며, 기업 고객에게는 계약 조항과
감사 가능성의 문제로 넘어간다.
그러므로 이 절의 인용들은 감정적 반응의 기록이 아니라 채택 곡선을 실제로 결정할 변수의 기록으로
읽어야 한다.

가장 많이 반복된 논지는 하나다 — GitHub가 엉망이라고 해서 다른 방식으로 엉망인 머스크 소유 기업에
코드를 맡겨야 하느냐는 것이고, 차라리 둘 다 쓰지 않겠으며 이쯤 되면 Subversion을 계속 썼으면
싶다는 것이다[^cryo32].
Cursor가 이제 일론 소유이며 시민 데이터를 확보하려 온갖 시도를 했던 인물이 소유하고 있으므로 그가
Grok을 먹이는 데 쓸 것이라는 우려[^nikole9696], SpaceX 소유 서비스를 쓰는 것이 GitHub가 간간이
다운되는 것보다 더 큰 공급망 위험이라는 판단[^drusepth], x.ai가 여기 호스팅된 코드로 훈련할
것이라는 가정[^s09dfhks]이 이어졌다.
아직 Cursor로 브랜딩하는 것이 흥미롭고 SpaceXAI라고 하지 않은 이유가 궁금하다는 관찰도 있었다[^SoKamil].

더 정교한 추론도 나왔다.
코드의 전체 버전 이력을 볼 수 있으면 코드가 어떻게 생성되고 어떤 버그가 생기고 어떤 수정이 어떻게
구현되는지, 즉 인간과 기계의 코딩 피드백 루프 전체를 학습 자원으로 갖게 된다는 것이다[^viraj_shah].
AI 회사에 소스 코드를 호스팅하게 하는 것은 샌드박스를 깨고 나올 수도 있고 테스트 목적으로만 쓰이며
절대 비테스트 목적으로는 쓰이지 않을 것이 확실한 에이전트에게 코드를 주는 일이라는 비꼬기도
있었다[^colinrand].
일론이 우리 저장소를 모두 업로드하던 Google Cloud Storage 버킷의 리브랜딩이냐는 농담도
있었다[^grim_io].

## GN 반응: 다들 코드 저장소를 출시하는 이유

GeekNews의 반응은 한 줄이지만 HN의 360개 댓글이 돌아간 지점을 곧바로 찔렀다.

> 코드 학습을 위해서인지 다들 코드 저장소를 출시하네요
>
> — dhy0613[^dhy0613]

이 문장이 값진 이유는 개별 회사의 소유 구조가 아니라 패턴을 지목하기 때문이다.
Cursor만 코드 호스팅을 시작한 것이 아니고, 같은 시기 여러 곳이 같은 계층으로 내려오고 있다 — HN에서
GitHub 대안이 이미 너무 많고 도시(Dorsey)도 하나 만들고 있는데 왜 이것이 유행이 됐느냐는 물음이 나온
것이[^vivekyyy] 같은 관찰의 다른 표현이다.
AI 회사가 이것을 하기를 기다리고 있었고 지금 GitHub를 흔들 기회가 분명하다는 반응[^dmix]은 그
유행을 시장 기회로 읽지만, GN 댓글은 동기를 학습 데이터로 읽는다.

두 독해는 예측이 다르다.
시장 기회로 읽으면 경쟁의 승자는 개발자 경험이 가장 좋은 곳이 되고, 학습 데이터로 읽으면 승자는
가장 많은 코드가 지나가게 만든 곳이 된다 — 그리고 후자에서는 제품이 좋을 필요가 없고 기본값으로
켜져 있으면 된다.
Origin의 출시 방식이 그 예측과 맞아떨어진다는 점이 이 한 줄의 무게다.
유료 플랜에 기본 활성이고 엔터프라이즈만 옵트아웃이며, 앞서 본 대로 프라이버시 모드를 낮추지
않으면 기능 자체를 쓸 수 없다 — “가장 많은 코드가 지나가게 만드는 것”에 최적화된 배포 정책이다.
같은 스레드에서 오히려 무료로 풀었으면 훈련 데이터로 값을 다 회수했을 것이라는 냉소가 나온
것도[^whywhywhywhy] 이 독해 안에서 자연스럽다.

## 회사 측 응답: “무엇이든 답하겠다” 뒤에 답하지 않은 것들

Origin 개발자이자 Graphite 공동 창업자인 Tomas Reimers가 스레드 상단에 나서 “Origin이나 형상 관리에
대해 무엇이든 답하겠다”고 했다[^tomasreimers].

다섯 시간이 지난 뒤 한 참가자가 지적한 것은, 곤란하지 않은 질문 하나에만 답했다는 것이며 — 일주일
전 Claude Code 대신 Cursor를 택한 입장에서도 이것이 Origin과 팀 모두에 좋지 않게 보인다는
것이다[^guhcampos].
답을 받지 못한 것들은 이렇다 — Grok이 허가 없이 전체 코드베이스와 민감한 `.env` 파일을 업로드하다
적발된 상황에서 어떻게 신뢰할 수 있느냐[^dbbk], 일론이 민감 데이터 접근을 절대 악용하지 않으리라
전적으로 신뢰하느냐, 그의 데이터 탈취를 막는 보호 장치가 무엇이냐[^victorbjorklund]다.
답이 많지 않았지만 이 글을 올린 것 자체는 용감했다고 인정하는 반응도 있었다[^gtirloni].

발표 시점의 데이터 처리 불투명성이 채택 장벽이라는 것은 6월에도 지적됐다.
출시 시점의 이 침묵은 그 장벽이 두 달 동안 낮아지지 않았음을 보여 준다.

## GitHub 대안을 출시한 날 GitHub 장애가 Origin을 흔들었다

출시 직후 Cursor 상태 페이지에 사건이 올라왔다 — GitHub의 성능 저하가 Origin에 영향을 준다는
것이다.
HN의 반응이 아이러니를 한 문장으로 정리했다 — 사람들을 GitHub에서 떼어 오려고 이것을 발표했는데
그것 자체가 GitHub에 의존하고 있었다는 것이다[^techgnosis].

정확히 말하면 GitHub와 긴밀히 통합된 기능들이 영향을 받은 것이므로 예상 가능한 일이라는 정리도
같은 스레드에 있다[^tuananh].
그 “예상 가능함”이 제품 전략의 성질을 드러낸다 — Origin의 1일 차 핵심 기능이 GitHub 동기화이므로
GitHub가 흔들리면 Origin의 주된 사용 경로도 흔들린다.
체인지로그가 “푸시는 계속 GitHub로 가며 GitHub가 소스 오브 트루스로 남는다”고 명시한 것이 그
의존을 문서화한 문장이다.

같은 스레드에는 반대 방향의 관찰도 있었다 — GitHub 사례가 서비스 신뢰성이 과대평가돼 있음을 분명히
보여 주며, 신뢰성 때문에 GitHub를 진지하게 떠나는 사람은 없고 대부분의 회사는 그 논의조차 하지
않는다는 것이다[^deepsun].
Slack이 다운되면 그냥 기다리는 것과 같다는 비유가 붙었다.

## 이름: `origin`은 이미 git 원격의 이름이다

이름 자체가 마찰을 만든다.
`origin`은 git 원격의 기본 이름이라 “origin main에 푸시해 줘”가 두 가지 뜻을 갖게 되고, LLM이
사용자 모르게 코드를 새 제공업체로 푸시할 수도 있어 천재적 성장 전략과 도메인 타이포스쿼팅 사이의
아슬아슬한 선이라는 지적이다[^jjcm].

HN 스레드 제목 자체도 혼동을 낳았다 — “GitHub degradation affects Cursor Origin, its new Git
platform”이 Cursor Origin을 GitHub의 새 플랫폼처럼 읽히게 한다는 지적이다[^djfdat].
그리고 Git과 GitHub를 혼동하는 담론 자체에 대한 정리도 나왔다 — Git은 Subversion보다 객관적으로
낫지만 널리 쓰이는 호스팅 서비스와 기반 형상 관리 시스템을 혼동하는 것이 문제이며, Git을 잘 쓰는
데 GitHub는 필수가 아니라는 것이다.

## 락인은 호스팅이 아니라 워크플로 포맷에 있다

Origin이 대체하겠다는 것은 git 호스팅인데, CI 통합을 보면 Depot과 Buildkite가 “기존 GitHub Actions
워크플로를 실행한다”고 적혀 있다 — 저장소는 옮겨도 빌드 정의는 GitHub의 문법으로 남는다는 뜻이다.

이것이 이 발표에서 가장 조용하지만 중요한 사실이다.
GitHub의 해자를 저장소 호스팅이라고 보면 경쟁은 성능과 가격의 문제가 되지만, 해자가 워크플로
포맷이라면 경쟁은 이미 끝나 있다 — `.github/workflows`의 YAML은 사실상 산업 표준이 됐고 Origin은
그것을 대체하는 대신 실행해 주기로 했다.
같은 구조가 PR에도 있다 — 양방향 코멘트 동기화는 GitHub의 PR 모델을 정본으로 인정하고 그 위에
미러를 얹는 것이다.
한 참가자의 정리가 이 지점을 요약한다 — 진짜 해자는 생태계 락인이고 git 호스팅 자체는 쉽지만 모든
팀이 의존하는 통합을 대체하는 것이 어려운 부분이라는 것이다[^ferrule].

여기서 나오는 결과는 이전의 가역성이다.
호스팅을 옮겨도 워크플로가 그대로면 되돌아가기도 쉽고, 되돌아가기 쉬우면 조직은 결단을 내리지
않는다 — GitHub를 소스 오브 트루스로 두고 Origin을 브라우징·리뷰 레이어로 쓰는 상태가 안정
균형이 된다.
Origin에게 이 균형이 나쁜 소식은 아닐 수 있다(리뷰 화면을 차지하는 것이 목표라면 충분하다).
그러나 “GitHub 대안”이라는 프레이밍에는 나쁜 소식이다 — 대안이 아니라 부착물로 정착하는 경로이며,
GitHub 장애가 Origin의 주된 사용 경로를 흔든 사건이 그 정착의 결과를 미리 보여 줬다.
그러므로 Origin이 진짜로 이겨야 할 대상은 GitHub가 아니라 GitHub Actions YAML이다.

## 코드베이스 이름을 URL에 넣은 한 줄

체인지로그에서 눈에 덜 띄는 문장이 하나 있다 — 첫 저장소를 만들 때 정한 코드베이스 이름이 이후
모든 저장소 URL의 일부가 되며 `cursor.com/codebase/acme-corp` 형태가 된다는 것이다.

URL은 옮기기 가장 어려운 자산이다.
`github.com/<org>`가 15년 동안 해 온 일은 저장소를 담는 것이 아니라 링크와 문서와 README 배지와
이슈 참조와 채용 공고와 논문 각주의 앵커가 되는 것이었고, 그 앵커가 축적되면 이전 비용이 저장소
용량과 무관하게 커진다.
조직 네임스페이스를 자기 도메인 아래로 가져오는 것은 그 축적을 새로 시작하겠다는 선언이며, 기능
넷을 나열한 목록보다 이 한 줄이 더 긴 시간을 겨냥한다.

동시에 이 선택이 앞의 긴장을 키운다.
GitHub 동기화가 이전을 미루는 장치라면 URL 네임스페이스는 이전을 확정하려는 장치이고, 두 장치가
같은 제품에 있다 — 조직은 Cursor URL을 문서와 링크에 쓰기 시작하는 순간부터 GitHub를 정본으로 두는
구성과 어긋나기 시작한다.
그러므로 도입하는 조직이 초기에 정해야 할 것은 동기화 범위가 아니라 링크 정책이다 — 사내 문서와
이슈 참조에 어느 도메인의 URL을 쓸 것인지이며, 그 결정이 실질적인 이전 시점이다.

## 원래 논지: GitHub의 설계 가정이 에이전트 시대에 붕괴한다

Origin의 발표가 겨냥한 것은 GitHub의 데이터 모델이다.
라인 단위 unified diff, `<<<<<<<` 마커 기반 충돌 표시, 브라우저에서 사람이 읽는 diff 뷰어는 인간
읽기 속도를 전제로 한다 — 사람은 하루에 수 건의 PR을 처리하는데 에이전트는 초당 수십 건의 커밋을
생성하므로, 이 차이는 기능 추가가 아닌 아키텍처 재설계를 요구한다는 것이다.

제안된 대안은 의미론적(semantic) 표현이다.
라인 레벨 diff 대신 함수 시그니처, 인터페이스 변경, 의존성 변동, 테스트 커버리지 변화를 기계가
파싱 가능한 객체로 인코딩하고, 충돌도 “브랜치 A는 반환 타입을 Promise로 변경했고 브랜치 B는 동기
호출을 전제한다”처럼 의미론적으로 서술한다.
이 접근은 기계가 충돌의 의미를 이해하고 자율적으로 해소할 수 있는 기반이 된다.

더 중요한 변화로 제시된 것은 에이전트 감사 추적(audit trail)이다.
에이전트가 어떤 프롬프트를 받았는지, 어떤 코드베이스 상태를 추론했는지, 어떤 대안을 고려했는지를
캡처하는 것이며, 이것은 코드 변경 이력이 아니라 추론 과정 이력이다.
결과물이 아닌 과정을 추적할 수 있다면 인간 감독의 단위가 “이 코드는 맞는가”에서 “이 추론은
타당한가”로 이동할 수 있다.

## 수직 통합의 완성이라는 관점

2026년 중반 기준으로 Cursor의 스택은 단계별로 완성돼 왔다 — IDE에서 코드를 작성하고(Cursor
Editor), 에이전트를 병렬로 실행하고(Cursor Cloud), 스택형 워크플로우로 리뷰하고(Graphite 기반),
호스팅하고 머지한다(Origin).
이 파이프라인이 단일 제품 에코시스템에 들어오면 각 단계의 전환 비용이 사라지고 플랫폼 종속성이
강화된다.

경쟁 구도에서 타깃은 명확하다.
Microsoft는 GitHub(호스팅) + VS Code(편집기) + GitHub Copilot(AI 보조)을 결합한 유사한 수직 통합을
이미 운영하며, Origin은 이 스택에 대한 정면 응수다.
Cursor가 SpaceX에 인수됨으로써 이 대립은 SpaceX-Microsoft 구도이기도 하다.

Graphite 인수의 전략적 의미도 지금 더 선명하다.
Graphite가 스택형 PR을 개발한 이유는 빠르게 움직이는 인간 팀을 위해서였는데, 이 설계는 AI 에이전트의
병렬 작업 패턴과 구조적으로 일치한다 — 에이전트는 독립적이고 의존적인 변경을 동시에 만들어내고
스택형 PR은 그 의존 관계를 명시적으로 표현한다.
Graphite는 인간 팀을 위해 에이전트 시대를 미리 설계한 셈이다.

## 병목이 생성에서 검증으로 이동했다는 진단

에이전트 이전에 개발의 속도 제약은 코드 생성이었고 리뷰는 그보다 빠르게 처리할 수 있었다.
에이전트가 초당 수십 건의 커밋을 생성하면 이 관계가 역전된다.

이 병목에 대한 응답은 두 가지다 — 인간 리뷰를 자동화된 게이트로 대체하는 것과 에이전트의 생성
속도를 제한하는 것이다.
Origin은 전자를 택한다 — 리뷰 기준을 측정 가능한 게이트(요구사항 준수, 불변성 보존, 테스트 통과)로
전환해 자동화 가능하게 만드는 것이다.
이 선택은 코드 품질의 최종 판단자를 인간 리뷰어에서 프로그래밍된 검증 기준으로 옮긴다.

## 자동화된 리뷰 게이트는 누가 기준을 정하는가를 숨긴다

“요구사항 준수”는 요구사항이 명확히 정의돼 있을 때만 자동화 가능한데, 현실의 요구사항은 종종
암묵적이고 변동하며 이해관계자마다 다르게 해석된다.
“불변성 보존”은 모든 중요한 불변성이 코드로 표현돼 있을 때만 검증 가능한데, 시스템에서 가장 중요한
불변성 상당수는 코드가 아닌 팀의 공유된 이해 속에 있다.

위험은 게이트가 틀린 경우가 아니라 게이트가 검증하지 않는 것이 있는 경우다.
에이전트가 게이트를 통과하도록 최적화되기 시작하면 — RLHF 정렬 문제의 코드베이스 버전이다 —
게이트가 측정하는 것과 실제로 중요한 것 사이의 괴리가 벌어진다.

HN에서 bparanj는[^bparanj] 이 문제를 직접 물었다 — “이게 GitHub과 무엇이 다른가? AI가 기계 속도로
코드를 생성할 때 이것을 어떻게 다루는가? 인간이 여전히 AI 슬롭(slop) 리뷰 루프에 있는 건가?”
자동화된 게이트가 형식적 정확성은 검증할 수 있지만 에이전트가 생성한 코드가 실제로 의도한 것을
올바르게 구현했는지는 여전히 인간의 판단을 요구할 수 있으며, 이 질문에 답하지 않고 “기계 속도로의
전환”을 전제로 출발하는 것은 기술적 가능성을 사용 가능성과 혼동하는 오류다.

## 대안 지형: 탈중앙화와 자체 호스팅

출시 스레드에서 가장 많이 언급된 대안 논지는 중앙집중형 대안을 하나 더 만들 것이 아니라 탈중앙화
해법에 노력을 투자하는 편이 낫다는 것이었다 — Radicle이나 연합형(federated) Forgejo가 예로
꼽혔다[^xvilka].
sourcehut과 Codeberg가 함께 제시되기도 했고[^DrBenCarson], GitLab과 Gitea를 비롯해 더 성숙하고
오픈소스인 대안이 많은데 굳이 이것을 선택할 이유가 떠오르지 않으며 팀에 악영향을 줘도 책임지지 않는
관리자·임원·CTO를 겨냥한 듯하다는 평가도 있었다[^jjice].

Tangled에 대한 소개가 가장 구체적이었다[^LelouBil].
git 호스팅, 이슈와 풀 리퀘스트, CI를 각각 원한다면 직접 호스팅할 수 있고, 계정 하나로 모든 저장소를
팔로우하거나 별표를 달고 이슈와 PR을 추가하는 GitHub식 소셜 기능도 제공하며, ATProto 기반이라 회사가
사라져도 누구나 오픈소스 AppView를 운영해 연동 기능을 계속 쓸 수 있다는 것이다.

반대편 논지도 분명했다.
이 접근은 GitHub나 Origin의 가치를 완전히 놓치는 것이며, git 서버 호스팅 자체는 어렵지 않고 사용자
경험과 PR 기능도 이미 대안이 있는데 GitHub가 특별한 이유는 생태계와 연동 기능이라는 것이다 —
Sentry나 Linear 같은 수많은 도구가 GitHub에 특화된 경험을 제공하므로 중앙화 혹은 최소한 표준이
필요하다는 정리다.
탈중앙화 해법은 늘 소수 기술 애호가에게만 매력적이고 대중적 채택에는 이르지 못한다는 냉정한 관찰도
따라붙었다.
Forgejo에 프로젝트를 호스팅하고 GitHub는 노출과 기여 유입을 위한 미러로만 쓰는 절충안, 그리고
Forgejo 등을 설치하면 과거 Subversion과 Trac을 함께 쓰던 환경을 지금도 구축할 수 있다는 지적도
있었다.

## 시장 쪽에서 나온 관측

밸류에이션에 대한 지적이 상위에 올랐다 — Cursor가 $600억 가치라는데 그것은 수익성이 있고 매출
$1,440억인 메르세데스-벤츠 그룹의 시가총액보다 높은데, 웹사이트는 CPU를 100% 쓰고 이것은 GitHub
대안이 아니라 유료 플랜용 베타라는 것이다[^3182876].
그 밑에는 매출을 업종 간 비교하는 것이 타당하지 않고 메르세데스의 이익률은 약 5%이며 SaaS는 규모에서
훨씬 높은 이익률을 기대한다는 반박[^Eridrus], 그리고 부풀려진 SpaceX 밸류에이션에 기반한 부풀려진
인수 밸류에이션이라는 정리[^empath75]가 붙었다.

타이밍과 경쟁 공백에 대한 관측도 있었다.
AI 회사가 이것을 하기를 기다리고 있었고 지금 GitHub를 흔들 기회가 매우 분명하다는 반응[^dmix],
대형 GitHub 장애를 기다린 것이 아니냐는 농담[^vb-8448], 그리고 GitLab이 이 명백한 AI 시장 기회를
어떻게 놓쳤는지 궁금하다는 지적 — 자체 호스팅 코드 관리에서 좋은 위치에 있었으니 저장소 수준
에이전트와 조직 수준 에이전트만 더했으면 지금쯤 $500억 밸류에이션을 받았을 것이라는 것이다[^throwaw12].
GitHub 대안이 이미 너무 많고 도시(Dorsey)도 하나 만들고 있는데 왜 이것이 유행이 됐느냐는 물음도
나왔다[^vivekyyy].

Microsoft가 GitHub의 호의를 날려 버린 것이 놀랍다는 평가와 함께 지정학적 논지도 붙었다 — 러시아나
우크라이나(크림)나 이란의 개발자는 GitHub에 접근하지 못하는데 탈중앙화 저장소는 자기 나라의 문제가
자기 잘못이 아닌데도 금지된 국가 출신이라는 이유로 막히는 일 없이 접근할 수 있으므로 미래는
탈중앙화라는 것이다[^dzonga].

## 콘텐츠 윤리를 이유로 한 거부

소유 구조와 별개로 회사의 다른 제품을 이유로 거부하는 반응도 상위에 있었다.
아동 성착취물을 만드는 회사에 코드를 호스팅하지 않겠다며 워싱턴포스트와 KATV 기사를 링크한
댓글이다[^grandpajoey].

이 댓글에는 반론도 붙었다 — 인용된 기사에도 의붓아버지가 Grok으로 어린 시절 사진을 변환했다고
명시돼 있으므로 Stable Diffusion이나 1990년대의 Photoshop으로도 가능했던 일이며, 이 논리라면
인터넷을 없애거나 모든 기술에 보호 필터를 넣어야 한다는 것이다.
Claude가 명령을 거부할 때 불만을 말하면서 여기서는 개인의 책임을 부정하고 의심되면 차단하는 기술
정책을 지지하는 것이 모순이며 대상이 머스크라서 그러는 것이 아니냐는 지적도 있었다.
반대로 오랫동안 읽은 것 중 가장 슬픈 내용이며 이 호스팅 서비스도 절대 쓰지 않겠다는 반응, 그리고
그러면서 Flock에 자금을 대는 웹사이트에는 댓글을 쓰고 있다는 되돌리기까지 이어졌다.

## 에이전트 감사 추적이 코드보다 값진 자산이 된다

Origin에서 가장 과소평가된 기능은 코드 호스팅이 아니라 에이전트 감사 추적일 수 있다.
어떤 프롬프트를 받았고 어떤 코드베이스 상태를 추론했고 어떤 대안을 고려했는지를 보존하는 것은 코드
변경 이력과 다른 종류의 데이터다.

이 데이터는 세 방향에서 값지다.
규제 환경에서 에이전트의 결정 과정을 소급 검토하는 감사, 추론 과정이 담긴 데이터가 결과만 담긴
데이터보다 훨씬 유용한 모델 훈련, 그리고 어떤 문제에서 에이전트가 더 자주 실패하고 어떤 맥락에서
인간이 에이전트의 제안을 거부하는지가 보이는 조직 패턴 이해다.

SpaceX 인수 맥락에서 이 가치는 다른 함의를 갖는다.
Origin에 호스팅된 코드와 에이전트 추론 추적이 Grok 훈련에 기여한다면 Origin은 코드 호스팅 서비스가
아니라 데이터 수집 인프라가 되며, 이것이 기업 채택의 가장 큰 장벽이 될 수 있다.
앞서 본 프라이버시 모드 게이트와 “버전 이력 전체가 학습 자원이 된다”는 HN 추론이 이 우려를 추정에서
관측으로 옮겼다.

## 스택형 PR이 병렬성의 기본 단위가 된다

GitHub의 기본 단위는 단일 풀 리퀘스트이며, 이것은 인간이 하나의 작업을 마치고 리뷰를 요청하는
순차적 워크플로우에서 자연스럽다.
에이전트는 한 작업을 여러 개의 의존적 변경으로 분해해 병렬로 실행한다.

스택형 PR은 이 의존 관계를 명시적으로 표현한다 — “PR B는 PR A가 머지된 이후에만 유효하다”를 데이터
모델 수준에서 인코딩하는 것이다.
Graphite가 이 방식으로 인간 팀의 생산성을 높인 것처럼 Origin은 같은 방식으로 에이전트 팀의 병렬성을
조율한다는 구상이다(다만 8월 출시에는 스택형 PR이 포함되지 않았다).

두 번째 효과는 리뷰 인터페이스의 변화다.
단일 PR 리뷰에서 스택 전체를 이해하는 리뷰로 바뀌면 인간 리뷰어는 개별 변경이 아닌 변경의 그래프를
검토해야 하고, 이것은 더 높은 인지 부담을 요구하면서 동시에 에이전트에게 더 많은 자율성을 허용한다.
에이전트가 실수했을 때의 영향 범위도 단일 PR이 아니라 스택 전체로 확대된다.

## 진짜 경쟁자는 GitHub가 아니라 기업 내 자체 구축 인프라다

Origin은 “GitHub 경쟁자”로 포지셔닝되지만, 실제 전환 장벽이 높은 곳은 GitHub 공개 플랫폼보다 기업
내 자체 구축 git 인프라다.
많은 대기업은 GitLab Self-Managed 또는 Bitbucket Data Center를 내부에서 운영하며, 이 조직들이
Origin으로 이동하려면 데이터 프라이버시와 거버넌스와 규정 준수를 먼저 해결해야 한다.

역설적으로 이 기업들은 에이전트를 가장 적극적으로 도입하는 곳이기도 하다.
수백 명의 개발자가 수백 개의 에이전트와 함께 작업하면 기존 git 인프라의 한계가 가장 먼저 드러나므로,
에이전트 병렬성 문제가 가장 심각하게 나타나는 곳이 대규모 엔지니어링 조직이다.

그래서 Origin의 성공 조건은 이 기업 시장을 어떻게 설득하는가에 달려 있다.
“에이전트 시대를 위해 설계되었다”는 마케팅 프레이밍보다 “기존 self-managed 환경에서 Origin으로
마이그레이션하는 방법”이 더 중요한 문서이며, SpaceX 인수 이후 데이터 처리 투명성 문제가 해결되지
않는 한 Origin은 개발자 열의와 기업 채택 사이의 간극을 메우기 어려울 것이다.
그리고 프라이버시 모드를 낮추지 않으면 기능을 쓸 수 없다는 출시 시점의 제품 동작은 그 간극을 좁히는
방향이 아니다.

## 남은 질문

- “에이전트 네이티브 기능”이 언제 어떤 형태로 나오는지 — 6월에 약속한 자동 머지 컨플릭트 해소, CI 실패 자동 복구, MCP 확장성이 실제로 구현되는지
- 프라이버시 모드 하향 없이 Origin을 쓸 수 있는 경로가 생기는지, 엔터프라이즈 계약에서 훈련 데이터 제외가 보장되는지
- 에이전트 처리량 요구(높은 RPS, 전용 테넌시)에 대한 답이 나오는지
- 스택형 PR과 감사 추적이 출시되는지, 그리고 그것이 GitHub의 PR 모델을 미러링하는 현재 구조와 어떻게 공존하는지
- GitHub Actions 문법에 대한 의존을 언제 끊는지, 아니면 끊지 않기로 하는지
