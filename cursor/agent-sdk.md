# Cursor Agent SDK: 팀의 업무 방식에 맞춘 에이전트를 코드로 정의하고 한 명령으로 배포한다

원문: [Introducing the Agent SDK · Cursor](https://cursor.com/blog/agent-sdk)

HN 토론: <https://news.ycombinator.com/item?id=50273731> (122점, 119개 댓글)

GN 토론: <https://news.hada.io/topic?id=36138>

## 요약

Cursor가 2026년 10월 20일에 올린 제품 발표 글이다.
글은 소프트웨어 팀이 코드로 정의한 에이전트를 개발 수명 주기 전반의 반복 업무에
쓴다고 시작한다.
에이전트는 팀이 일하는 곳에 연결되어 관련 이벤트가 생기면 움직이고,
예로 든 일은 풀 리퀘스트 검토, 규정 준수 작업의 실행, 장애 조사이다.
글은 가장 쓸모 있는 에이전트가 팀의 일하는 방식에 맞춘 것이라고 보고,
지금까지는 남의 업무 방식에 맞춘 제품을 쓰거나 처음부터 만들어야 했다고 쓴다.

Agent SDK는 Cursor가 자사의 관리형 에이전트인 Bugbot, Security Reviewer,
Rollouts를 만드는 데 쓰는 프레임워크이고, 이제 일반 공개(GA)되었다.
에이전트를 코드로 정의해 다른 소프트웨어 프로젝트처럼 관리한다.
템플릿에서 시작하거나 코딩 에이전트에게 문서를 읽혀서 만들 수 있고,
준비가 되면 `agent-sdk deploy` 한 명령으로 Cursor의 인프라에 배포한다.
이 명령은 에이전트를 빌드하고 URL을 주고 시작한다고 글은 설명한다.

에이전트는 GitHub, GitLab, Bitbucket의 풀 리퀘스트 이벤트에 반응해
변경의 위험을 평가하고, 맞는 팀에 보내고, 정책에 맞는 변경을 승인할 수 있다.
예로 든 것은 Cursor 안의 한 팀이 교훈을 모은 지식 베이스를 모든 풀 리퀘스트와
대조하려고 약 하루 만에 만든 kb-reviewer이다.
기록된 교훈과 어긋나는 변경을 표시하고, 각 지적의 근거 노트를 인용하고,
엔지니어가 어긋남을 조정하도록 유도한다고 한다.
복잡한 작업에서는 에이전트가 다른 전문 에이전트에게 일을 넘기거나
하위 에이전트 여럿에게 일을 나눌 수 있다.
평가(evals)와 이벤트 재생(replay)이 기본 제공되고,
글은 PGA Tour가 이 SDK로 소프트웨어 공장을 구동하며 평가 덕분에
빠르게 움직인다고
적는다.

에이전트는 작은 소프트웨어 프로젝트처럼 구성된다.
지침, 도구 코드, 외부 서비스 연결, 시험용 평가가 한 곳에 있고,
프롬프트는 Markdown으로, 도구는 TypeScript 함수로 쓴다.
모든 것이 코드이므로 변경은 다른 소프트웨어와 같은 버전 관리와 검토를 거친다.
배포하면 비밀 값과 연동은 대시보드에서 관리하고 로컬과 같은 로그, 평가,
플레이그라운드를
쓴다.
자체 인프라에서도 돌릴 수 있고 각 에이전트는 컨테이너로 묶을 수 있는 단일 Node
프로세스이다.
글의 시작 예제는 `@cursor/agent-sdk`의 `defineAgent`로 이름, 모델
(`composer-2.5`, effort 높음, fast 켜짐), 로컬 작업 디렉터리를 정의한다.
글은 코딩 에이전트가 개발 과정을 따라가도록 안내하는 스킬(skills)도
함께 제공한다고
한다.

## 분석

### 이 SDK는 에이전트를 소프트웨어 프로젝트의 규율 안에 넣는다

글의 중심 문장은 에이전트를 코드로 정의해 다른 소프트웨어
프로젝트처럼 관리한다는
것이다.
이 선택이 가져오는 것은 세 가지이다.
지침이 저장소에 있으니 변경이 검토되고 되돌려질 수 있고,
평가가 시험처럼 붙어 있으니 변경의 효과가 측정될 수 있고,
배포가 한 명령이니 개발과 운영의 거리가 짧아진다.
이 문서의 해석으로는 이 구조의 가치는 에이전트의 능력이 아니라 에이전트의 변경
관리에 있다.
같은 모델로도 지침 한 줄이 동작을 바꾸므로,
그 한 줄을 코드 리뷰의 대상으로 만드는
것이 이 도구의 실질이다.

### 사례들은 사람의 판단이 가장 작은 자리를 가리킨다

글의 두 사례는 비슷한 모양이다.
kb-reviewer는 기록된 교훈과 어긋나는 변경을 표시하고,
코드 리뷰 에이전트는 위험을 평가해 맞는 팀에 보내고 정책에 맞는 변경을 승인한다.
둘 다 기준이 이미 글로 쓰여 있는 일이다.
교훈은 노트로 있고 정책은 문서로 있으며,
에이전트는 그 기준과 변경을 대조한다.
이 문서의 해석으로는 이 선택이 우연이 아니다.
기준이 없는 일은 평가를 만들 수 없고,
평가가 없으면 에이전트를 코드로 관리해도 개선의 방향을 알 수 없다.

### 배포 모델은 한 곳에서 시작하고 이전할 길을 남긴다

글은 Cursor의 인프라에 한 명령으로 배포하는 흐름을 중심에 두면서,
자체 인프라에서 돌릴 수 있다는 문장을 따로 둔다.
각 에이전트가 하나의 Node 프로세스이므로 컨테이너로 옮기는 비용이 작다.
이 이중 구조는 Cursor에 묶이는 우려를 줄이려는 장치로 읽힌다.
다만 글은 자체 인프라에서 돌 때 대시보드, 로그, 평가, 플레이그라운드 같은 관리형
기능이 어떻게 되는지 쓰지 않는다.

## 비평

### 모델과 요금과 한도가 글에 없다

글의 시작 예제에는 모델 하나(`composer-2.5`)가 나온다.
이 모델이 Cursor의 자체 모델인지, SDK가 다른 공급자의 모델도 받는지는 글에 없다.
요금, 사용량 한도, 지원하는 이벤트 원천의 전체 목록도 이 문서가 읽은
글에는 없다.
HN에서 verdverm은 2026년에 하네스를 고르는 주요 기준이 만든 회사의
모델만이 아니라
모든 모델 계열에 접근하게 해 주는지라고 썼다.[^verdverm]
pscanf는 OpenAI의 Agent API와 Anthropic의 Agent SDK 같은 대안이 기능이 비슷한데
특정 공급자에 앱을 묶는 것이 내키지 않는다며 표준이 생기기를 바란다고
했다.[^pscanf]
이 두 반응은 글이 모델 선택의 폭에 대해 아무 말도 하지 않은 데서 나온 질문이다.

### 증거는 한 사례의 일화와 한 문장의 추천이다

kb-reviewer는 Cursor 안의 팀이 약 하루 만에 만들었고 모든 풀
리퀘스트에서 돌고 있다고
한다.
이 서술에는 얼마나 많은 지적이 있었고 몇 퍼센트가 유용했는지의 수치가 없다.
PGA의 인용문은 SDK로 소프트웨어 공장의 모든 구성 요소를 Cursor의 인프라
위에 만들었고
평가 덕분에 빠르게 반복한다는 일반적인 칭찬이다.
인용 아래의 서명은 PGA America의 수석 엔지니어이고,
본문은 이 SDK를 쓰는 곳을 PGA Tour라고 쓴다.
두 이름이 같은 조직인지 글에서 알 수 없다.
이 문서는 둘을 확인하지 못했다.

### 이미 있는 Cursor의 SDK와의 관계가 설명되지 않는다

HN에서 randomblock1은 Cursor에 기존 TypeScript SDK가 있다고
알렸다.[^randomblock1]
글은 이 Agent SDK가 그것과 어떻게 다른지, 대체하는지,
위에 얹히는지를 쓰지 않는다.
scosman은 OpenAI와 Anthropic이 이미 Agent SDK라는 이름을 쓰고
Vercel은 AI SDK라고 부르는데 좋은 이름을 지어 달라고 했다.[^scosman]
이름과 계보의 모호함은 도입하려는 팀이 문서에서 실제로 확인해야 할 비용이다.

### 사람이 참여하는 흐름을 만드는 법이 없다

bob1029는 HN에서 이런 회사들이 어려운 부분을 제공하지 않는다고 썼다.
기업이 실제로 쓰는 웹 화면(채팅 UI)은 도메인에 맞게 바뀌어야 하는데,
기성 화면에 맞춤 설정을 얹는 시도가 처참하게 실패했고,
인라인 승인 흐름처럼 맞춤 요소와 컨트롤러 동작이 필요한 경우를 기성 플랫폼에
연결할 길이 없다는 것이다.[^bob1029]
이 글의 에이전트는 이벤트에 반응하고 승인까지 하는 쪽에 초점이 있어서,
사람이 승인하는 화면을 만드는 방법은 이 글에 없다.
이 지적은 글이 다루지 않은 범위이지 SDK에 그 기능이 없다는 증거가 아니다.

## 인사이트

### 지침이 코드가 되면 에이전트의 개선이 코드 리뷰의 일이 된다

인프라를 코드로 관리하는 흐름이 서버 설정을 저장소에 넣어 검토와
이력과 되돌리기를
가능하게 했던 것처럼, 에이전트의 지침을 코드로 두는 것도 같은 이득을 준다.
이 문서의 비유로는 이것이 인프라를 코드로 쓰는 일의 다음 단계이다.
그러나 차이가 있다.
인프라 코드는 같은 입력에 같은 결과를 내지만 에이전트의 지침은 같은 입력에도
결과가 달라질 수 있다.
그러면 변경의 검토는 코드를 읽는 일에서 평가를 돌려 결과의 분포를 보는
일로 옮겨 간다.
simianwords는 HN에서 에이전트 SDK의 API가 왜 도구를 가진 런타임이 실행하는
PROMPT.md 하나가 아니냐고 물었다.[^simianwords]
ashishmax31은 그 런타임이 바로 만드는 대상이며,
범용 하네스는 셸과 도구가 환경이지만 직접 만든 런타임에서는 도구를 코드로
정의해 권한 부여 같은 것을 통제할 수 있다고 답했다.[^ashishmax31]
zomtorg는 에이전트가 제약 없는 LLM을 풀어 놓아도 될 수준이 아니고,
워크플로의 부분마다 모델과 도구와 제약이 다를 수 있으며,
보안과 법무 팀에 데이터가 어떻게 다뤄지고 무엇이 기록되는지 설명하기가 쉽다고
했다.[^zomtorg]
이 문서의 해석으로는 이 답이 SDK의 존재 이유를 글보다 잘 말한다.
통제와 설명 가능성이다.

### 승인하는 에이전트는 책임을 어디에 둘지의 문제를 만든다

글은 에이전트가 정책에 맞는 변경을 승인할 수 있다고 적는다.
이 승인이 풀 리퀘스트의 병합 조건이 되는 순간 판단의 책임이 누구에게 있는지가
문제가 된다.
정책이 문서로 있다고 해서 정책을 해석한 에이전트의 판단을 정책 작성자가 책임지는
것은 아니다.
kb-reviewer는 지적하고 조정을 권하는 데서 멈추는 설계이고,
승인하는 에이전트는 그 선을 넘는다.
이 문서의 해석으로는 같은 SDK로 만든 두 에이전트가 서로 다른 위험 수준에 놓인다.
글은 둘을 같은 틀에서 소개하지만, 승인 권한을 어디까지 줄지는 팀이 정해야 하고
그 결정을 도울 평가 지표가 글에는 없다.
이 가설을 뒤집는 관측은 승인한 변경의 사후 결함률이 사람의 승인과 비슷하거나
낮게 공개되는 경우이다.

### 하네스의 경쟁은 도구가 아니라 구독의 경제와 전환 비용에서 갈린다

HN의 가장 긴 갈래는 오픈소스 하네스를 왜 안 쓰느냐는 h0rv의 질문이었다.
chrisvalleybay는 가장 좋은 모델이 Claude Code Max 구독으로 쓰는 것이 훨씬 싸서
오픈소스 하네스를 쓰려고 돈을 더 낼 이유가 없다고 답했다.[^chrisvalleybay]
sodacanner는 오픈소스 하네스에 구독을 갈아탈 만큼 놀라운 기능이 없고,
복잡한 기능은 생산성 연극이라고 의심한다고 했다.[^sodacanner]
Benjammer는 반대로 기본 부품이 단순하니 직접 하네스를 만들면 된다고
했다.[^Benjammer]
이 문서의 해석으로는 이 논쟁이 가리키는 것은 하네스의 우열이 아니라
어느 쪽의 비용 구조가 이기느냐이다.
Cursor가 Agent SDK로 파는 것은 하네스가 아니라 배포와 운영이고,
그 가치는 구독으로 모델을 쓰는 사람들이 갖지 못하는 부분(이벤트 연결,
평가, 호스팅)에
있다.
username_my1은 LLM 생태계가 JS 생태계처럼 끝없는 기술의 교체로 가고 있다고
했고,[^username_my1] gawacer는 AI 도구가 JS 프레임워크 교체의 시기에 들어섰다고
했다.[^gawacer]
교체가 빠를수록 코드로 정의한 에이전트의 이식성이 중요해지는데,
글은 그 이식성(다른 공급자의 모델과 하네스로 옮기는 길)을 말하지 않는다.
