# LivLiv Player: 의존성 없이 30KB로 2.5D 캐릭터를 웹에 올리고 립싱크와 얼굴 추적까지 붙이는 플레이어

<https://github.com/livliv-dev/player>

## 소개

LivLiv Player는 웹에서 2.5D 캐릭터를 재생하는 가벼운 플레이어이고,
저장소 설명은 립싱크(lip sync)와 웹캠 얼굴 추적(face tracking)이 붙어 있다고 한다.
README는 몇 줄의 코드로 캐릭터를 페이지, 방송 오버레이, 앱에 넣을 수 있다고 소개하고,
화풍이 서로 다른 추천 캐릭터 21개를 함께 넣었다고 한다.

2026년 11월 6일에 읽은 저장소 정보는 다음과 같다.
Apache-2.0 라이선스이고 스타는 452개, 포크는 49개, 커밋은 21개다.
열린 이슈와 풀 리퀘스트는 각각 1개다.
토픽은 `avatar`, `character`, `face-tracking`, `lip-sync`, `pngtuber`, `vrm`,
`vtuber`, `webgl2`이다.
릴리스는 11월 5일의 0.2.0이 첫 공개 릴리스이고,
11월 6일의 0.2.1이 최신이다.

README가 내세우는 특징은 네 가지다.

| 항목          | README의 설명                                                                |
| ------------- | ---------------------------------------------------------------------------- |
| 크기와 의존성 | WebGL2, 의존성 없음, 코어는 gzip으로 약 30KB                                 |
| 음성과 얼굴   | 마이크, 오디오, 비디오 립싱크와 MediaPipe 웹캠 얼굴 추적, 필요할 때만 불러옴 |
| 재생 대상     | LivLiv, VRM, PNGTuber 캐릭터를 같은 API로 재생                               |
| 캐릭터        | `characters/`에 바로 쓸 수 있는 추천 캐릭터 21개                             |

브라우저 지원은 WebGL2와 ES2023이 되는 Chrome과 Edge 97 이상,
Firefox 104 이상, Safari 15.4 이상이다.
README는 현재 데스크톱 브라우저에서 시험했고 휴대폰에서는 아직 시험하지 않았다고
밝힌다.

README는 이 플레이어와 `.livliv` 형식이 LivLiv의 자체 작업이며
Live2D 소프트웨어나 Cubism SDK를 쓰지 않고 `.moc3`나 `.cmo3` 파일을 읽지도 않는다고
적는다.
Live2D는 Live2D Inc.의 상표이고 LivLiv는 그 회사와 관계가 없다고도 적는다.

## 사용법

저장소는 아직 npm에 올라 있지 않다.
README는 저장소를 받아 직접 빌드한 뒤 `dist/index.js`를 가져다 쓰라고 안내한다.
기본 사용은 캔버스 하나에 `Player`를 만들고 캐릭터 폴더나 `.livliv` 파일을 읽는 것이다.

```js
import { Player } from '@livliv/player'

const player = new Player(document.querySelector('canvas'))
await player.load('characters/k01/')   // model.json과 textures/가 있는 폴더, 또는 .livliv 파일

player.setExpression('smile')          // id는 player.expressions에 있다
player.act('nod')
player.params.mouthOpen = 0.6          // 0..1
```

립싱크와 얼굴 추적은 별도 모듈로 나뉘어 있어서 쓸 때만 불러온다.

```js
import { createSpeech } from '@livliv/player/voice'
import { startFaceTracking } from '@livliv/player/tracking'   // @mediapipe/tasks-vision이 필요하다

const speech = createSpeech(player)
button.onclick = () => { speech.unlock(); speech.say('/reply.mp3') }

await startFaceTracking(player)
```

VRM과 PNGTuber는 같은 인터페이스를 가진 `BodyPlayer`에 몸체 클래스를 꽂아서 쓴다.
VRM은 `three`와 `@pixiv/three-vrm`이 필요하다.
PNGTuber는 입을 닫은 그림과 연 그림 두 장이면 되고,
눈을 감은 그림 두 장이 더 있으면 쓴다.

```js
import { BodyPlayer } from '@livliv/player/body'
import { VrmBody } from '@livliv/player/vrm'
import { PngBody } from '@livliv/player/png'

const vrm = new BodyPlayer(canvasA, new VrmBody())
await vrm.load('/avatars/me.vrm')
const png = new BodyPlayer(canvasB, new PngBody())
await png.load({ closed: 'me-closed.png', open: 'me-open.png' })
```

코드 없이 쓰는 길도 있다.
livliv.ai의 `/live/<id>` 페이지를 `iframe`으로 넣으면 되고,
같은 페이지는 배경이 투명해서 OBS 브라우저 소스로도 쓸 수 있다고 한다.
개발용 명령은 타입 검사 `npm run check`, 빌드 `npm run build`,
Node 22.18 이상에서 도는 단위와 퍼징 테스트 `npm test`,
추천 캐릭터를 전부 헤드리스 Chromium으로 그려 보는 `npm run test:browser`,
Firefox와 WebKit에서 표본을 돌리는 `npm run test:engines`이다.

## 얼굴 추적이 부르는 외부 호스트

README는 플레이어가 AI 서비스를 부르지 않고 지정한 파일만 읽으며
카메라 영상은 기기에 남는다고 한다.
API.md의 상세 설명은 이 말이 얼굴 추적의 기본 설정에서는 조건부임을 보여 준다.
기본 설정에서 얼굴 추적은 외부 호스트 세 곳과 통신한다.
MediaPipe의 런타임을 받는 jsDelivr, 얼굴 모델을 받는 Google의 모델 저장소,
그리고 MediaPipe의 사용 통계를 약 1분에 한 번 보내는 Google의
`odml.pa.googleapis.com`이다.
처음에는 약 8MB를 내려받는다.

세 호스트와 통신하지 않으려면 세 단계가 필요하다.
MediaPipe의 `wasm/` 폴더와 `face_landmarker.task`(3.6MB)를 자기 서버에 두고,
`startFaceTracking`에 `wasmUrl`과 `modelUrl`을 넘기고,
`connect-src 'self'` 같은 콘텐츠 보안 정책(Content Security Policy)으로 통계 전송을
막는다.
API.md는 MediaPipe에 통계를 끄는 옵션이 없고,
막아도 얼굴 추적은 똑같이 동작하며 브라우저가 분당 한 번 거부된 연결을 로그에 남긴다고
적는다.

## 믿을 수 없는 파일을 전제로 한 한도

API.md는 모델 패키지를 누구나 만들 수 있는 파일로 보고 GPU에 닿기 전에 검사한다고 한다.
`.livliv` 파일은 항목 2048개와 풀었을 때 256MB까지,
압축된 항목은 디렉터리가 알려 준 크기에서 풀기를 멈추어 ZIP 폭탄이 더 나가지 못하게
하고,
패키지 밖의 경로, 암호화, ZIP64는 받지 않는다.
`model.json`은 캔버스 한 변 8192px, 레이어 512개, 이미지 2048개까지,
이미지는 한 변 8192px에 전체 6400만 픽셀까지다.
VRM은 three.js의 glTF 로더가 읽기 전에 먼저 걸러지고,
바깥 URL을 이름으로 부르는 파일은 거부되어 페이지가 아무것도 가져오게 만들 수 없다.
검사에 걸리면 `load()`가 오류와 함께 거부되고 앞서 재생하던 캐릭터가 그대로 남는다.
LivLiv가 만든 가장 큰 모델도 이 한도의 10분의 1 이하를 쓴다고 한다.

## 코드와 캐릭터는 라이선스가 다르다

코드는 Apache License 2.0이고 NOTICE가 따로 있다.
추천 캐릭터는 Apache가 아니라 `characters/LICENSE.md`의 별도 라이선스를 따르고,
LivLiv라는 이름과 로고는 두 라이선스 어디에도 포함되지 않는다.

| 대상                 | 조건                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------- |
| LivLiv가 만든 캐릭터 | 비상업 용도에 무료, 크레딧 표기, 판매·상업 사용·AI 학습·정치 선전 등은 금지              |
| Nana                 | 위 조건에 더해 자신이나 다른 제품의 마스코트로 쓰거나 LivLiv의 보증을 암시하는 것을 금지 |
| Kujira, Kujira Q     | CC BY-NC-SA 4.0                                                                          |
| Pen                  | Apache도 LivLiv 캐릭터 라이선스도 해당하지 않음                                          |

LivLiv 캐릭터 라이선스는 개인 창작자의 방송과 영상이 플랫폼에서 광고 수익과 후원,
멤버십을 받아도 비상업으로 본다고 적는다.
회사나 단체가 광고, 제품 홍보, 유료 앱과 서비스, 굿즈에 쓰는 것은 상업 사용이고
먼저 이메일로 동의를 구하라고 한다.
위반하면 쓸 권리가 자동으로 끝난다.

Kujira와 Kujira Q는 중국 커뮤니티 캐릭터 고래 소녀를 바탕으로 하며,
원작자 두 사람의 크레딧을 CREDITS.md가 밝힌다.
LivLiv가 AI로 두 장의 기존 그림에서 레이어와 리깅이 된 모델로 만들었다고 한다.
Pen은 팬 캐릭터 咕咕嘎嘎를 바탕으로 한 것이고,
CREDITS.md는 LivLiv가 이 캐릭터에 어떤 권리도 갖지 않고 부여하지도 않으며
권리자가 이메일을 보내면 크레딧을 달거나 캐릭터를 내리겠다고 적는다.

## 비평

### 캐릭터 라이선스는 하루 만에 한 번 고쳐졌다

0.2.0은 11월 5일에, 0.2.1은 이튿날인 11월 6일에 나왔다.
0.2.1의 릴리스 노트는 추천 캐릭터 세 개의 출처와 조건을 바로잡았다고 쓰고,
Kujira와 Kujira Q를 CC BY-NC-SA 4.0으로 옮기고
Pen은 어느 쪽 라이선스도 해당하지 않는다고 적는다.
이 문서는 0.2.0의 라이선스 표기가 어땠는지 읽지 않았으므로 무엇이 틀렸는지는 알지 못한다.
확인되는 것은 첫 공개 이튿날 파생 캐릭터의 권리 정리가 바뀌었다는 사실이다.

그래서 Pen을 쓰려는 사람이 읽어야 할 곳은 이 저장소의 라이선스가 아니다.
저장소는 이 캐릭터에 어떤 권리도 부여하지 않는다고 밝힌다.
README가 추천 캐릭터가 바로 쓸 수 있다고 소개하는 것과,
그중 하나가 쓸 근거가 없는 것은 같은 목록 안에서 서로 다른 상태다.
예제에서 `?model=` 인자로 아무 캐릭터나 불러 볼 수 있는 구조에서,
데모에서 본 캐릭터를 그대로 자기 프로젝트에 가져가는 일이 가장 쉬운 오용이 된다.

### 코드의 Apache 라이선스는 캐릭터에 닿지 않는다

Apache-2.0 코드와 21개의 캐릭터가 한 저장소에 들어 있어서,
코드의 자유로움이 데모 자산에까지 미친다고 읽기 쉽다.
이 문서는 이 오해를 가장 먼저 짚어야 한다고 본다.
라이선스 문서는 상업적 사용을 법인이나 단체에 한정해 정의하고,
개인 창작자의 수익은 비상업으로 두는 비교적 관대한 선을 긋는다.
그러나 이 선은 LivLiv가 쓴 정의이고,
회사가 아닌 개인이 캐릭터가 나오는 유료 앱을 파는 경우가 어느 쪽인지는
문서가 정하지 않는다.
이런 경우에는 라이선스 문서가 안내하는 이메일로 먼저 물어야 한다.

### 얼굴 추적의 프라이버시 문구는 기본 설정에서 조건부다

README의 한 문장만 읽으면 얼굴 추적도 기기 안에서 끝난다고 읽힌다.
카메라 영상이 기기에 남는다는 말은 API.md가 뒷받침한다.
그러나 같은 문서가 기본 설정에서 외부 호스트 세 곳과의 통신이 일어나고
그중 하나가 MediaPipe의 사용 통계라고 밝힌다.
이 통계는 MediaPipe에 끄는 옵션이 없어서 이 라이브러리가 막을 수 없고,
페이지의 보안 정책으로만 막을 수 있다.
개인정보를 다루는 페이지에 이 플레이어를 넣는 쪽이 위 세 단계를 직접 해야 한다는 뜻이다.
저장소는 이 사정을 감추지 않고 문서화했지만,
통계가 나가는 사실은 README가 아니라 API.md의 하위 절까지 가야 보인다.

### 릴리스와 main이 어긋나 있다

최신 릴리스는 0.2.1이지만 main의 CHANGELOG.md에는 0.3.0 절이 있고,
이 절은 패키지가 npm에 오르기 전에 인터페이스를 굳히는 변경이라고 설명한다.
`act('away')`가 예외를 던지고, `player.puppet`이 타입에서 사라지고,
`load()`를 두 번 부르면 앞의 것이 `AbortError`로 거부되는 것이 그 예다.
README의 사용 예가 어느 버전을 기준으로 쓰였는지는 이 문서가 읽은 자료에서 구분되지 않았다.
0.2.1 릴리스를 받아 쓰는 사람과 main을 빌드하는 사람이 서로 다른 인터페이스를 만날 수 있다.
저장소가 아직 npm에 오르지 않았고 첫 릴리스가 나온 지 이틀이 안 되었다는 점에서,
이 불일치는 초기 프로젝트에서 자연스럽지만 도입을 결정할 때는 버전을 고정해야 한다.

### 이 문서는 플레이어를 실행해 보지 않았다

이 문서는 저장소를 빌드하거나 데모를 열거나 캐릭터를 불러 보지 않았다.
30KB라는 크기, 지원 브라우저, 한도의 숫자, 테스트 통과는 모두 저장소가 한 말이다.
`livliv.ai`의 서비스와 요금제도 읽지 않았고,
워터마크가 유료 요금제에서 사라진다는 서술도 API.md에서 읽은 것이다.

## 인사이트

### AI로 만들었다는 공개 의무와 AI 학습 금지가 한 쌍으로 묶여 있다

README는 LivLiv로 만든 캐릭터를 공개적으로 보일 때 AI를 썼다고 밝히고
손으로 그리거나 리깅한 것처럼 보이게 하지 말라고 요구한다.
같은 시기의 캐릭터 라이선스는 이 캐릭터로 AI 모델을 학습하거나 다른 캐릭터를 생성하는
것을 금지한다.
이 문서의 해석으로는 이 둘이 서로 다른 불신을 다룬다.
앞의 것은 시청자가 창작물의 출처를 오해하는 문제를 다루고,
뒤의 것은 AI가 만든 자산이 다시 AI의 재료가 되는 문제를 다룬다.
AI로 만든 결과물에 이런 조건을 거는 것이 유효한지는 이 문서가 판단할 수 없다.
다만 캐릭터를 만드는 쪽이 자기 결과물에 거는 조건을 후속 사용자에게도 적용하는 방식은
이 영역에서 앞으로 흔해질 가능성이 있다.

### 형식을 먼저 공개하고 플레이어를 오픈소스로 둔 것은 서비스의 유입 장치다

런타임이 livliv.ai의 렌더러와 같은 코드라는 점이 이 저장소의 성격을 정한다.
README는 `src/runtime/`이 livliv.ai가 돌리는 렌더러와 모션 코드이고
이 저장소가 거기서 게시된다고 밝힌다.
그리고 무료 요금제로 내보낸 패키지에는 플레이어가 캔버스에 LivLiv 로고를 그리고,
API.md는 이 표식이 패키지 라이선스의 일부이며 플레이어에 숨기는 스위치가 없다고 한다.
코드는 열고 표식은 패키지가 정하는 구조에서는
플레이어가 퍼질수록 서비스의 노출이 늘어난다.
이 문서는 이를 비판하지 않고 구조로 읽는다.
코드가 공개되어 있으므로 표식을 지우는 포크는 기술적으로 막을 수 없고,
그 포크가 라이선스를 어기는지는 별개의 문제다.

### 믿을 수 없는 파일을 전제로 한 플레이어가 캐릭터 시장의 형식을 바꾼다

모델 패키지를 누구나 만든 파일로 취급해 크기와 개수, 압축 폭탄을 미리 막는 설계는
캐릭터 파일을 사용자가 내려받는 방송 도구에서 중요한 안전 장치다.
VRM이 바깥 URL을 이름으로 부르면 거부하는 것도 같은 맥락이다.
캐릭터 파일이 마켓에서 거래되는 환경이라면 파일 자체가 공격 표면이 되기 때문이다.
이 한도는 저장소가 스스로 밝힌 것이고 이 문서는 퍼징 테스트의 범위나 결과를 읽지 않았다.
한도가 실제로 막아 주는지는 SECURITY.md와 테스트가 보여 줄 것이다.

### 결론을 바꿀 관찰

npm에 패키지가 올라가고 버전별 변경 기록이 안정되면 도입 위험이 줄어든다.
Pen을 포함한 캐릭터의 라이선스 정리가 더 이상 바뀌지 않으면
추천 캐릭터를 목록 그대로 믿어도 되는지가 가려진다.
휴대폰 브라우저에서의 시험 결과가 공개되면 방송 오버레이를 넘어선 용도가 열린다.
얼굴 추적의 통계 전송이 MediaPipe의 옵션으로 꺼지면
프라이버시 문구를 조건 없이 쓸 수 있게 된다.
