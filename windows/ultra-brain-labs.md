## 소개

Ultra-Brain-Labs는 Windows 시스템 엔지니어링 결과물을 공개하는 저장소이다.
저장소는 2026년 11월 12일에 만들어졌고 11월 14일에 마지막 변경이 있었으며 C로 쓰였다.
2026년 11월 15일에 읽은 값으로 별 1개, 포크 0개, 열린 이슈 0개이고, GitHub 정보에 라이선스 항목이 없다.
README는 세 도구가 모두 C11 파일 하나이고 C 런타임이 없으며 임포트 DLL이 `KERNEL32.dll` 하나라고 밝히고, 문서의 모든 수치에 출처(CI 실행 번호나 로컬 측정 조건)를 달았고 측정하지 않은 값은 적지 않았다고 쓴다.
현재 버전은 1.2.0이다.
이 문서는 README의 상당 부분(1~3절, 5절의 도구 표, 한계)과 Show GN 글 소개를 읽었다.
빌드하거나 실행하지 않았고 CI 기록도 열어 보지 않았다.

## 구성

| 파일                   | 역할                                                             |
| ---------------------- | ---------------------------------------------------------------- |
| `src/win_zero_cli.c`   | 무의존성 CLI 레퍼런스(`win_zero_cli.exe`, 5,120 B)               |
| `src/agent_wire_ipc.c` | Win32 named pipe 기반 로컬 에이전트 IPC                          |
| `src/agent_wire_mcp.c` | 위 파이프를 Claude Desktop과 Cursor에 잇는 MCP stdio 어댑터      |
| `build.cmd`            | clang+lld 또는 `msvc` 인자로 MSVC 빌드, 둘 다 경고를 오류로 처리 |
| `scripts/` `tests/`    | 파이프 시나리오, MCP Soak, Python 표준 라이브러리 시험           |

### 무의존성 CLI

README가 밝히는 원리는 세 가지이다.
C 런타임을 빼면 DLL 의존이 사라진다. 보통의 빌드가 끌어오는 `ucrtbase.dll`과 `vcruntime140.dll`이 “DLL 누락”의 정체이고, 진입점을 직접 쓰고 필요한 Win32 함수를 직접 선언하면 링커가 넣는 DLL이 `KERNEL32.dll`만 남는다.
인코딩은 시작 시 `SetConsoleOutputCP(65001)`로 UTF-8로 한 번 고정해 CP949 콘솔에서 한글이 깨지는 문제를 없앤다.
빌드 산출물이 아니라 소스를 배포해 받는 쪽이 자기 PC에서 구우면 내려받은 exe에 붙는 Mark-of-the-Web이 생기지 않는다.
다만 Smart App Control은 서명 없는 exe를 평판으로 차단할 수 있다고 직접 적는다.
실측으로 exe가 5,120 B(clang+lld)와 5,632 B(MSVC), 컴파일과 링크가 0.23초에서 0.38초, 힙이 없고 64 KiB 정적 아레나를 쓴다고 한다.

### 로컬 에이전트 IPC

같은 PC의 에이전트 둘이 상태를 주고받을 때 흔한 선택인 Slack 봇, 로컬 HTTP/WebSocket 서버, 파일 폴링은 토큰과 서버 프로세스와 포트와 방화벽 예외가 붙고 왕복이 수십에서 수백 밀리초라고 README는 쓴다.
대신 Win32 named pipe로 두 프로세스가 64바이트 패킷을 주고받는다.
파이프 이름은 `\\.\pipe\ultra_brain_agent_wire`, 메시지 모드, 원격 클라이언트 거부, 인스턴스 1개이다.
패킷은 64바이트 고정이고 매직(`WIRE`), 버전, opcode(PING, TASK, STATUS, 서버만 보내는 RECEIPT), 프로젝트 해시, 송수신 에이전트, 페이로드 길이(최대 40), FNV-1a 체크섬, 페이로드 40바이트로 이루어진다.
거부된 패킷에도 영수증이 돌아가고 세션은 유지된다.
벤치마크는 GitHub-hosted `windows-latest` 러너에서 1,000회 PING→RECEIPT 왕복의 평균이 clang 0.040밀리초와 MSVC 0.038밀리초이고 p99는 0.066과 0.063밀리초라고 한다.
README는 지시 사양이 0.4밀리초급이었으나 실측 평균은 그 10분의 1이며, 첫 왕복이 7.9~9.8밀리초로 워밍업 비용이라고 스스로 적는다.

### MCP 어댑터

어댑터는 위 파이프를 Claude Desktop과 Cursor에 잇는 stdio 도구이다.
툴 4개를 제공한다. `wire_status`(연결 상태와 왕복 시간), `wire_roundtrip`(1~16,384회 왕복과 영수증 검증), `wire_server_start`(같은 폴더의 `agent_wire_ipc.exe`를 창 없이 실행), `wire_close`(연결 양보)이다.
`wire_server_start`는 실행 파일 이름과 인자가 코드에 고정되어 임의 명령을 실행할 수 없고, 자식은 어댑터가 끝나면 함께 끝나는 job에 묶인다고 한다.

## 분석

### 중심 주장은 의존성을 줄이면 설치 문제가 사라진다는 것이다

문제를 네 가지(파이썬 가상환경 충돌, DLL 누락, Smart App Control 오탐, 안티바이러스 오인)로 좁히고, 그중 앞의 둘을 런타임 제거로 푸는 접근이다.
임포트가 `KERNEL32.dll` 하나라는 사실은 CI가 `dumpbin`과 `llvm-readobj`로 확인한다고 한다.
이 접근은 작은 도구에 맞고 큰 프로그램에는 비용이 크지만, 에이전트용 로컬 도구처럼 기능이 좁은 경우에는 일관된 선택이다.

### 서명 없는 바이너리는 풀지 못한 문제로 남는다

README가 가장 솔직한 부분이 한계 절이다.
바이너리가 서명되지 않았고 Smart App Control이 켜진 PC에서는 CI가 만든 exe도 로컬에서 직접 빌드한 exe도 차단될 수 있으며, 개발기에서 실제로 막혀 로컬 실행은 실행하지 못했다(NOT_RUN)고 적는다.
의존성 제거가 “설치 문제를 없앤다”는 서술은 이 한계 안에서만 맞다.

## 비평

### 수치의 출처가 모두 공유 CI 러너이다

벤치와 Soak 수치는 공유 CI 러너에서 구성당 1회 잰 값이고 하드웨어 보장치가 아니라고 README가 밝힌다.
로컬 개발기 실측은 없다.
그래서 “0.04밀리초”는 이 저장소의 CI 환경에서의 값이다.

### 검증의 범위가 프로토콜 수준에서 멈춘다

MCP 어댑터는 Claude Desktop, Cursor, Claude Code 실제 앱에서 시험하지 않았고 프로토콜 수준 검증만 했다고 한다.
최신 개정과 resources, prompts, logging, Streamable HTTP는 구현하지 않았다.
Soak는 30분을 넘지 않았고 메모리는 “증가 0 B”가 아니라 호출 수에 비례하는 증가가 측정되지 않았음까지 확인했다고 한다.
이 정직함은 장점이지만, 실제 클라이언트에서의 동작을 보증하지 않는다는 뜻이다.

### 문체와 성숙도

README의 제목들(“물리적 인증의 실체”, “길막 분쇄”, “AI 환각 방지 원샷 지휘문”)은 과장된 홍보 투이고, 내용의 절제(출처 표기, 한계 명시)와 어긋난다.
저장소는 만든 지 사흘이고 별 1개, 라이선스 표기가 없어서 재사용 조건이 불분명하다.
이 문서는 이 도구를 쓴 사례를 찾지 못했다.

### 반응이 없다

GeekNews에 자체 댓글이 없었고 HN과 Lobste.rs에도 이 저장소가 올라온 흔적이 없다.

## 인사이트

### 가져갈 것은 출처 표기 방식이다

수치마다 CI 실행 번호와 측정 조건을 달고, 측정하지 않은 것은 NOT_RUN이라고 쓰는 방식은 소규모 저장소가 신뢰를 얻는 좋은 방법이다.
“지시 사양 0.4밀리초, 실측 0.04밀리초”처럼 기대와 실측의 차이를 그대로 적는 것도 같은 태도이다.

### 로컬 에이전트 간 통신에 서버가 필요 없는 경우가 있다

같은 PC의 에이전트끼리라면 토큰도 포트도 없이 파이프로 충분하다는 것이 이 저장소의 요지이다.
이 판단은 보안 경계(같은 사용자 계정의 프로세스끼리)가 같다는 전제에서 성립한다.
이 문서는 파이프 접근 권한 설정을 확인하지 못했다. README는 원격 클라이언트를 거부한다고만 밝힌다.

### 확인할 관찰

이 저장소의 방향을 가를 관찰은 세 가지이다.
코드 서명이나 Smart App Control 환경에서의 실행 결과가 나오는지,
실제 MCP 클라이언트에서의 시험 결과가 추가되는지,
라이선스가 명시되는지이다.
셋 모두 이 문서가 확인하지 못했다.
