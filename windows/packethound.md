# PacketHound: Windows 방화벽을 나가는 연결마다 묻는 방화벽으로 바꾼다

<https://packethound.app/>

<https://github.com/packethound-app/packethound.app>

HN 토론: <https://news.ycombinator.com/item?id=50415135> (122점, 58개 댓글)

GN 토론: <https://news.hada.io/topic?id=36862>

## 소개

PacketHound는 Windows용 아웃바운드(outbound) 응용 프로그램 방화벽이다.
README는 Little Snitch의 정신을 따른다고 소개한다.
서드파티 앱이 처음으로 밖으로 나가는 연결을 시도하면 허용(Allow)과 차단(Block)을
묻고, 답을 일반 Windows 방화벽 규칙으로 저장한다.
Windows 자체의 구성 요소에는 묻지 않는다.
홈페이지의 표어는 어떤 앱이 집으로 전화를 거는지 알라는 것이다.

무료이고 체험판, 계정, 광고가 없다고 한다.
홈페이지가 적는 현재 버전은 1.3.0, 크기 68.2MB이고
Windows 10(1809 이상)과 Windows 11의 x64와 ARM64를 지원한다.
소스는 GitHub에 GNU 일반 공중 사용 허가서(GPL) 3판으로 공개되어 있다.
저장소는 C#으로 쓰였고 2026년 11월 5일에 만들어졌다.
2026년 11월 10일에 GitHub API로 확인한 별은 50개, 포크 2개, 열린 이슈 1개이고
마지막 푸시는 11월 9일이다.
닫힌 이슈 네 건은 모두 기능 요청(규칙 편집, 활동 로그에서 규칙 만들기, 결정 중
IP 복사, 다른 연결을 허용할 때 차단 연결을 지우지 않기)이고,
열린 한 건은 Windows on ARM64판 요청이다.

## 동작 방식

### 아웃바운드 기본값을 차단으로 바꾼다

PacketHound는 커널 드라이버를 쓰지 않고 Windows 방화벽 위에 얹힌다.
README가 말하는 흐름은 다음과 같다.

1. 세 방화벽 프로필(도메인, 개인, 공용) 모두에서 아웃바운드 기본값을 차단으로
   바꿔, 허용 규칙이 없는 프로그램은 막는다.
2. 필터링 플랫폼 연결의 실패 감사를 켜서 차단된 시도가 보안 로그에 이벤트 5157로
   남게 한다.
3. 규칙이 없는 프로그램의 5157 이벤트를 감시한다.
   Windows 구성 요소면 조용히 허용 규칙을 만들고,
   서드파티 앱이면 앱, 게시자, 목적지 호스트 이름 또는 IP, 포트,
프로토콜을 보이는
   창을 띄운다.
4. 답은 앱 전체, 특정 IP, 특정 호스트, 특정 도메인과 하위 도메인 가운데 하나를
   범위로 하는 규칙이 되고, 기간은 영구, 앱이 끝날 때까지, 한 시간, 오늘 하루
   중에서 고른다.

규칙은 `wf.msc`의 아웃바운드 규칙에 보이는 일반 방화벽 규칙이므로
PacketHound가 꺼져 있거나 제거된 뒤에도 계속 작동한다.
이 구조에서 첫 시도는 반드시 실패한다.
앱이 차단되어야 PacketHound가 알기 때문이고,
허용을 누른 뒤 앱이 다시 시도해야 한다.
홈페이지는 대부분의 앱이 자동으로 재시도하고 브라우저는 새로 고침이 필요하다고
설명한다.

### 무엇을 Windows로 볼 것인가

프로그램이 Windows로 취급되려면 세 조건을 모두 만족해야 한다.
Windows 위치(`%SystemRoot%`, `Program Files\Windows *`,
Defender 플랫폼 폴더)에 있고,
파일 소유자가 TrustedInstaller나 SYSTEM이며,
내장 또는 보안 카탈로그를 통한 유효한 Microsoft Windows 인증 코드(Authenticode)
서명이 있어야 한다.
WHQL 서명을 받은 벤더 도구(NVIDIA 유틸리티 등)는 System32에 있어도 Windows로
치지 않는다.
README는 작성자의 PC에서 System32의 659개 프로그램 중 625개가 Windows로
분류되었다고 적는다.
그런 구성 요소 중에서도 악성코드가 페이로드를 내려받는 데 자주 쓰는 PowerShell,
cmd, curl, certutil, bitsadmin, mshta, rundll32, regsvr32, wscript, msiexec, ssh
등은 기본으로 묻는다(설정에서 끌 수 있다).

### 갱신, 설치 프로그램, 조용 모드

일부 앱은 버전마다 새 폴더에 설치되므로 경로만 바뀐 경우 프롬프트가 갱신처럼
보인다고 알리고 같은 설정을 새 경로에 복사하는 버튼을 준다.
새 버전의 서명자가 다르면 이 버튼은 나오지 않고 다시 결정해야 한다.
`%TEMP%`에 매번 새 폴더로 풀리는 설치 프로그램에는 앱이 끝날 때까지만 유효한
규칙을 만들고, 유효한 서명이 있고 허용하면 같은 파일 이름과 같은 서명자의
이후 복사본은 묻지 않고 통과시킨다.
이 과정에서 바꿔치기를 막으려 서명 확인 뒤 앱이 끝날 때까지 파일을 열어
고정한다고 README가 설명하며, 그 부작용으로 설치 프로그램이 임시 폴더를
남길 수 있다고도 적는다.
결정을 미루면 앱은 차단된 채 대기 목록에 오르고 10분 뒤에 다시 묻는다.
조용 모드(30분, 1시간, 3시간 또는 끌 때까지)는 새 앱을 묻지 않고 차단한다.
보호를 5분, 15분, 한 시간, 또는 다시 켤 때까지 일시 중지할 수도 있다.

## 사용하기

설치 프로그램은 약 65MB이며 `C:\Program Files\PacketHound`에 설치된다.
README는 로그인 때 시작하는 작업이 관리자 권한으로 PacketHound를 돌리므로,
일반 사용자가 쓸 수 있는 폴더의 실행 파일이 바꿔치기되어 관리자 권한을
얻는 일을 막으려고 관리자만 바꿀 수 있는 경로에 둔다고 설명한다.
관리자 권한이 필요한 이유는 방화벽 설정을 바꾸고
보안 이벤트 로그를 읽기 때문이다.

소스에서 빌드하려면 .NET 10 SDK가 필요하다.

```powershell
.\build.ps1                  # publish\PacketHound.exe (약 750KB), .NET 10 Desktop Runtime 필요
.\build.ps1 -SelfContained   # 더 크고 .NET이 필요 없는 실행 파일
.\build.ps1 -Arch arm64      # Windows on ARM용
.\build.ps1 -Installer       # 설치 프로그램, Inno Setup 7 또는 6 필요
```

개인정보에 대해 홈페이지는 수집이나 분석이 없다고 한다.
다만 서버 이름을 보여 주려고 앱이 접속하려는 서버를 DNS로 조회하고,
일주일에 한 번 홈페이지에 새 버전이 있는지 묻는다.
이 요청에는 사용자나 PC에 관한 내용이 없으며 끌 수 있다고 한다.
Windows SmartScreen이 많이 받지 않은 프로그램이라고 경고하면
자세한 정보에서 실행을 누르고, 다운로드 페이지의 SHA-256 체크섬과 비교해
확인하라고 안내한다.
README는 코드 서명이 아직 준비되지 않았다고 적는다.

## 분석

### 이미 있는 정책 엔진 위에 대화형 층만 얹은 설계

PacketHound는 방화벽 엔진을 새로 만들지 않고 Windows 방화벽의 규칙과 감사 로그를
그대로 쓴다.
감시와 결정만 앱이 맡고, 시행은 운영체제가 한다.
이 구조의 좋은 점은 앱이 죽거나 제거되어도 이미 내린 결정이 유지된다는 것이고,
홈페이지도 이를 강조한다.
나쁜 점은 방화벽이 아는 것(경로와 IP)만 규칙으로 표현된다는 것이다.
호스트와 도메인 규칙은 이름의 IP 주소를 앱이 쓸 때마다 규칙에 더하는 방식으로
근사되고, CDN처럼 주소를 공유하는 사이트는 규칙도 공유한다고
홈페이지가 인정한다.

### 첫 시도를 실패시켜서 알아내는 방식

감사 이벤트로 알아내므로 규칙이 없는 앱은 반드시 한 번 막힌다.
이 비용은 설치 프로그램에서 가장 두드러져서,
PacketHound는 허용 뒤 5분 동안 보호를 멈추는 한 번의 클릭과 서명된 설치
프로그램의
기억, 임시 폴더 감시라는 보완책을 만들었다.
설계 전체의 복잡도 상당 부분이 이 첫 실패를 부드럽게 만드는 데 쓰인다는 점이
눈에 띈다.

### Windows 판정의 세 조건은 경로만 믿지 않으려는 방어다

경로, 소유자, 서명을 모두 요구하는 것은 System32에 악성코드를 복사해 넣어
자동 허용을 받는 길을 막으려는 설계다.
홈페이지가 이 점을 “Hard to fool”이라는 제목으로 내세운다.
같은 맥락에서 설치 프로그램 규칙이 서명을 확인한 뒤 파일을 열어 고정하는 것은
확인 시점과 사용 시점 사이의 바꿔치기를 막는 방어이고,
이 설계가 실제로 막는지는 이 문서가 확인하지 못했다.

## 비평

### Windows를 자동으로 믿는 기본값은 Little Snitch의 취지와 부딪친다

README는 Windows 자체에는 묻지 않는다고 하고,
홈페이지는 수백 개의 시스템 서비스에 대한 질문에 묻히지 않는다는 점을 장점으로
말한다.
HN에서 한 사용자는 이것이 반드시 좋은 일은 아니라고 지적했고,[^bad_username]
다른 사용자는 모든 트래픽을 아는 것이 Little Snitch의 핵심이라고
덧붙였다.[^dyauspitr]
또 다른 사용자는 Binisoft(Malwarebytes) Windows Firewall Control이
Windows 구성 요소의 차단을 허용하지만 문제가 생길 수 있다고
소개했다.[^TwoNineFive]
PacketHound의 선택은 소음을 줄이는 대신 Windows의 원격 측정(telemetry) 같은
트래픽을 보지 못하게 한다.
위험한 도구 목록만 예외로 두는 것은 타협이며,
그 목록 밖의 Windows 구성 요소가 나쁜 용도로 쓰이는 경우는 막지 못한다.

### 도구의 신뢰를 어디에서 구할 수 있는가

관리자 권한으로 방화벽을 바꾸는 도구는 그 자체가 높은 신뢰를 요구한다.
홈페이지는 소스가 공개되어 있고 직접 빌드할 수 있다고 하지만,
README는 코드 서명이 아직 준비되지 않았다고 적는다.
HN에서는 이 앱과 홈페이지가 전부 LLM이 만든 글이라는 반응이 여러 건 있었다.
한 사용자는 홈페이지 문구를 클로드 투(claudease)라고 비난했고,[^poszlem]
다른 사용자는 100% 바이브코딩한 보안 도구는 쓰지 않겠다고 했으며,[^Kwpolska]
또 다른 사용자는 코딩을 LLM이 했다고 판매를 못 하느냐고
반박했다.[^AltruisticGapHN]
이 문서는 저장소의 작성 방식을 확인하지 못했다.
작성 방식은 신뢰의 증거가 되지 못하고, 서명, 재현 가능한 빌드, 시험 같은
검증 가능한 신호가 신뢰의 근거가 된다.

### 기존 대안과의 차이를 문서가 설명하지 않는다

HN에서는 ZoneAlarm,[^Dwedit] simplewall,[^shrx] Fort Firewall,[^baal80spam]
Portmaster,[^s3p] Binisoft Windows Firewall Control 같은 기존 도구가
줄줄이 거론되었다.
한 사용자는 simplewall이 이름과 경로로 허용하는 규칙이 없어 수없이 묻는 점이
가장 큰 불만이라고 했다.[^underlines]
PacketHound가 갖춘 앱 경로와 서명 기반 규칙, 갱신 감지가 그 불만에 답하는
것으로 보이지만, 홈페이지와 README는 다른 도구와 비교하지 않는다.
홈페이지의 대부분의 방화벽이 들어오는 것만 본다는 말에는
20년 동안 아웃바운드를 보지 않는 방화벽을 쓴 적이 없다는 반박이 달렸다.[^avazhi]

### 첫 실패와 CDN 공유 규칙이 사용자 경험을 좌우한다

첫 연결이 실패하는 것은 구조의 결과이지만, 사용자는 앱이 고장 났다고 느낀다.
홈페이지는 이를 알려 주는 문단을 갖췄으나 모든 앱이 자동으로 재시도하지는
않는다.
CDN을 공유하는 사이트가 규칙을 공유한다는 점은 호스트 단위 허용이 생각보다
넓다는 뜻이다.
이 두 가지의 실제 빈도는 이번에 확인하지 못했다.

## 인사이트

### 허용 결정의 후속 비용이 이 제품의 실제 가치를 정한다

아웃바운드 방화벽의 한 번의 허용은 쉽지만 그 뒤에 비용이 따른다.
앱이 갱신되어 새 폴더에 설치되면 규칙이 깨지고,
설치 프로그램은 임시 경로에서 매번 새로 풀린다.
PacketHound가 갱신 감지, 같은 서명의 임시 설치 프로그램 기억, 조용 모드,
결정 보류를 갖춘 것은 질문의 수를 줄이는 데 설계가 쏠려 있다는 뜻이다.
질문이 너무 많으면 사용자가 모두 허용하게 되므로,
이 기능들이 보안의 질을 지키는 일이기도 하다.
이 관점은 이 문서의 해석이다.

### 정책을 운영체제에 두면 앱이 사라져도 안전한 방향으로 실패한다

규칙이 일반 Windows 방화벽 규칙이므로 PacketHound가 제거되어도 차단된 앱은
차단된 채 남고, 종료할 때 규칙이 없는 앱을 계속 막을지 묻는다.
제거하는 쪽도 원래 방화벽 설정으로 되돌린다고 홈페이지가 설명한다.
도구가 죽을 때 열린 문 쪽으로 실패하지 않고 닫힌 문 쪽으로 실패하게 하는
설계이며, 그 대가는 일상의 불편이다.

### 신뢰의 신호가 만든 이의 정체에서 검증 가능한 산출물로 옮겨 간다

HN 반응의 큰 가지가 이 앱이 LLM으로 만들어졌느냐에 쏠렸다.
보안 도구에서 이는 이해할 만한 걱정이지만, 사용자가 실제로 확인할 수 있는 것은
작성 방식이 아니라 서명, 소스, 빌드 재현성, 이슈 처리 기록이다.
저장소가 열린 지 닷새 만에 별 50개와 이슈 5건을 받고 그 가운데 네 건이 닫힌 것은
최소한 유지자가 요청에 반응하고 있다는 신호이고,
HN에서 한 사용자가 자신도 같은 종류의 도구를 1년 넘게 만들고 있다고 밝힌 것은
이 분야에 경쟁하는 개인 개발자가 있다는 신호다.[^Avicebron]
무엇이 충분한 신뢰의 근거인지는 이 문서가 확정하지 못한다.
