## 소개

OpenPencil은 ZSeven-W가 만든 MIT 라이선스의 벡터 디자인 도구다.
저장소 설명은 세계 최초의 오픈소스 AI 네이티브 벡터 디자인 도구이자 동시에
일하는 에이전트 팀(Agent Teams)을 갖춘 첫 도구라고 소개하고, 홈페이지는
`op.zseven.tech`다.
핵심 주장은 디자인을 코드처럼 다룬다는 것이다.
`.op` 파일은 사람이 읽을 수 있는 JSON이고 Git에서 비교할 수 있으며, 프롬프트가
라이브 캔버스에 곧바로 UI를 만든다.

이 저장소는 2026년 2월 17일에 생성됐고 2026년 10월 23일에도 푸시가 있었다.
스타 6,451, 포크 563이며 주 언어는 Rust이다(2026년 10월 23일 확인).
2026년 10월 28일에 다시 읽은 값은 스타 6,764, 포크 590이다.
최근 확인한 릴리스는 v0.8.4다.
이름이 비슷한 `open-pencil/open-pencil`(Figma 대체를 표방하는 다른 프로젝트)과는
별개의 저장소이다.
두 프로젝트의 비교는 아래 「오픈소스 디자인 도구의 사각 구도」와
`design-tool/open-pencil.md`, `design-tool/penpot.md`에 있다.

README는 기능을 열거한다.
- 프롬프트에서 캔버스로: 자연어로 UI를 설명하면 스트리밍 애니메이션과 함께 무한
캔버스에 나타나고, 요소를 고르고 채팅해 수정한다.
- 동시 에이전트 팀: 오케스트레이터가 복잡한 페이지를 공간 단위 하위 작업(히어로,
기능, 푸터)으로 나눠 여러 에이전트가 병렬로 그린다.
- 다중 모델 대응: Claude는 전체 프롬프트와 thinking을, GPT-4o와 Gemini는
thinking을 끄고, 더 작은 모델(MiniMax, Qwen, Llama)은 단순화된 프롬프트를
받는다.
- MCP 서버: Claude Code, Codex, OpenCode, Kiro, Copilot CLI에 한 번에 설치해
터미널에서 `.op` 파일을 읽고 고친다.
- 코드 내보내기: React + Tailwind, HTML + CSS, Vue, Svelte, Flutter, SwiftUI,
Jetpack Compose, React Native.
- 실시간 협업: 인증된 P2P 세션과 공개 릴레이, 10자 지역 태그 페어링 코드, 원격
커서, 충돌 패널.
- CLI `op`, 임베드용 웹 SDK(바닐라, React, Vue 어댑터), Git 연동(클론, 브랜치,
3방향 병합과 충돌 패널), `.fig` 가져오기, 프레젠테이션 덱(PDF, 슬라이드쇼 HTML,
PPTX 내보내기), Chrome 웹 캡처 확장이 있다.

## 동작 방식

### Rust 재작성이 현재 제품이다

README에 따르면 TypeScript와 Electron 편집기는 `v0.7.5`에서 퇴역했고, 지금의
제품은 Rust 워크스페이스다.
데스크톱 앱은 `winit`과 GPU Skia로 그리는 단일 네이티브 바이너리(55.5 MB)이고
브라우저 엔진이 없다.
웹은 8.2 MB의 wasm(전송 2.18 MB gzip)과 CanvasKit(WebGL2)으로 같은 그리기 코드를
쓴다.
저장소는 Rust 안에 편집기, CLI, MCP, AI, 코드 생성, Figma, Git을 모은 하나의
워크스페이스다.
수치 주장으로는 1만 노드 캔버스에서 패닉이 없고 유휴 CPU가 약 0%이며, 전체
레이아웃 스냅숏이 약 0.68초이고, 휠 줌 CPU를 약 69%에서 약 0%로 줄였다고 한다.
이 수치는 모두 README의 서술이며 이 문서가 측정하지 않았다.

### 설치는 패키지 관리자 경로가 있다

macOS는 Homebrew cask, Windows는 Scoop, Linux와 Windows는 GitHub Releases의
`.exe`, `.AppImage`, `.deb`이다.
Nix 플레이크는 `x86_64-linux`용으로 있고 `.deb`는 만들지 않는다.
CLI는 Homebrew 또는 설치 스크립트로 받는다.
소스에서 빌드하려면 서브모듈 세 개(`jian`, `casement`, `agent`)를 함께 받아야
하고 Rust 안정 버전이 필요하다.
웹 SDK 작업에만 Bun과 Node.js가 필요하다.

### 웹 호스트는 자격 증명 저장 위치가 기본값으로 브라우저다

브라우저에서 입력한 공급자 API 키 같은 자격 증명은 같은 출처의 `localStorage`에
기본으로 저장되고, 데몬은 이를 `settings.json`에 쓰지 않는다.
비공개 배포는 환경 변수로 서버 저장을 켤 수 있지만, README는 접근이 통제된 신뢰
배포, 관리자 프로필 하나, HTTPS 뒤에서만 켜라고 하고, 같은 출처의 스크립트가
읽을 수 있으므로 XSS로부터 출처를 보호해야 한다고 쓴다.
웹 호스트는 내장 API 키 에이전트만 지원하고 CLI·ACP 에이전트는 네이티브에서만
쓴다.

### 공식 홈페이지는 완성된 화면보다 편집 가능한 상태를 앞세운다

공식 홈페이지는 이 도구를 프롬프트에서 편집 가능한 제품 UI로 가는 길이라고
소개하고, 모바일과 데스크톱의 여러 화면을 라이브 캔버스에서 만든 뒤 레이어마다
AI로 다듬는다고 한다.
쇼케이스(Music Home, Marquee, Wander, Daybreak Coffee, Pulse)는 캔버스에서
생성한 실제 제품 화면이고 첫 결과 이후에도 텍스트와 이미지와 레이아웃과
컴포넌트를 수정할 수 있다고 설명한다.
시작 방식은 빈 캔버스가 아니라 의도, 즉 제품 설명이나 참고 이미지나 기존 `.op`
파일이다.
Agent Teams는 여러 화면의 제품을 공간 단위 작업으로 나눠 병렬로 만든다고 하며,
이는 README가 설명한 오케스트레이터 구조의 홍보 문구다.
홈페이지는 이어서 병렬 작업 뒤에 공유 내비게이션과 시각 언어를 다시 한곳에
모으고, 에이전트가 어디서 일하는지 표시기로 보여 주며,
고칠 부분만 다시 실행할 수 있다고 쓴다.
이 밖에 `.fig` 가져오기(레이아웃, 스타일, 컴포넌트, 텍스트, 이미지, 벡터),
PNG·JPEG·WebP·PDF와 코드 내보내기, 그리고 에이전트가 프로젝트의 색과 글꼴과
컴포넌트와 레이아웃 규칙을 따르도록 `design.md` 명세를 가져오고 내보내고
생성하는 기능이 있다.
코드 생성은 출력을 계획하고 집중된 조각으로 제출한 뒤 편집 가능한 `.op` 원본에서
조립하는 증분 방식이라고 한다.
지원 플랫폼은 macOS, Windows, Linux 세 가지, 인터페이스 언어는 15개, 라이선스는
MIT이며 설치는 Homebrew와 Scoop 또는 독립 `op` CLI로 한다.
홈페이지에는 후기나 성능 수치가 없고 쇼케이스 화면도 생성 과정(프롬프트와 편집
횟수)을 밝히지 않으므로, 결과물의 품질은 이 문서가 확인하지 못했다.

### 에이전트 팀은 오케스트레이터가 나눈 공간 단위 작업을 병렬로 맡는다

README는 AI 설계를 프롬프트에서 UI로 가는 흐름으로 소개한다.
텍스트로 페이지를 설명하면 SSE 스트리밍 애니메이션과 함께 캔버스에 생성되고,
요소를 고른 뒤 자연어로 수정을 요청할 수 있으며,
스크린샷이나 목업을 참조 이미지로 붙일 수 있다.
오케스트레이터는 복잡한 페이지를 공간 단위 하위 작업으로 쪼개고,
에이전트 팀은 위임 도구와 구성원별 캔버스 표시기,
대체 전략을 갖춘 동시 작업자들로 구성된다고 한다.
반복 생성의 획일화를 줄이려고 생성 사이의 다양성을 추적하는 anti-slop
기능도 둔다.

MCP 쪽에는 계층형 설계 흐름이 있다.
`design_skeleton`, `design_content`, `design_refine` 순서로 단계마다 집중된
프롬프트를 써서 여러 구역으로 된 설계의 충실도를 높인다는 것이다.
필요한 설계 지식(스키마, 레이아웃, 역할, 아이콘,
계획 등)만 골라 불러오는 분할 프롬프트 검색이 있고,
스타일 가이드는 태그 기반 퍼지 매칭으로 50가지 이상(글래스모피즘, 브루탈리스트,
레트로 등)을 계획과 생성에 연결한다고 한다.
모델마다 사고 모드, 노력 수준, 프롬프트 모양을 바꾸는 능력 프로필이 있어서
Claude는 전체 프롬프트와 사고 모드를, GPT-4o와 Gemini와 DeepSeek은 사고 모드를
끄고, MiniMax와 Qwen과 Llama는 단순화된 프롬프트를 받는다.
이 구분은 open-pencil의 호환성 표가 측정으로 다룬 문제,
곧 모델마다 도구 호출이 다르게 깨진다는 문제를 ZSeven이 설정으로 흡수하려는
접근이다.[^os-byok]

### MCP 서버와 `op` CLI는 Node.js 없이 데스크톱 바이너리에 들어 있다

MCP 서버는 `op-mcp` 크레이트로 내장되어 Claude Code, Codex, OpenCode, Kiro,
Copilot CLI에 한 번에 설치된다.
Node.js가 필요 없고, 데스크톱 바이너리의 `--mcp <path>`로 stdio 전송을 쓰며,
실행 중인 앱의 `127.0.0.1:<port>/mcp` HTTP 엔드포인트도 있다.
코드 생성은 증분 파이프라인으로 `codegen_plan`, `codegen_submit_chunk`,
`codegen_assemble`, `codegen_clean` 도구를 거친다.

`op` CLI는 `op start`, `op start --headless --file design.op`,
`op design @landing.txt`, `op design @ui.js`(반복문이 있는 샌드박스 JavaScript),
`op insert '{"type":"rectangle"}'`, `op import:figma design.fig`를 지원한다.
인자는 문자열, `@파일`, 표준 입력(`-`) 세 가지로 준다.
`op install`은 감지된 에이전트에 OpenPencil 스킬을 설치해 에이전트에게 `op`로
설계하는 법을 가르친다.
README는 에이전트 지원을 표로 정리한다.
Claude Code는 설정 없이 Claude Agent SDK와 로컬 OAuth를 쓰고,
Codex CLI와 OpenCode와 GitHub Copilot은 에이전트 설정에서 연결하고,
내장 경로는 9곳 이상의 공급자를 지역 전환기와 함께 제공한다.
Kimi, Zhipu, GLM, DouBao 같은 중국 LLM 공급자를 위한 Anthropic 형식
패스스루도 있다.

### Git과 `.op` JSON이 변경 검토를 만든다

`.op`가 JSON이라는 점은 Git 연동 기능으로 이어진다.
README는 SSH와 HTTPS 인증이 되는 클론 마법사,
브랜치 만들기와 전환과 삭제와 병합, 푸시와 풀의 재인증과 non-fast-forward
처리를 나열한다.
폴더 모드의 3방향 병합은 디스크의 `MERGE_HEAD` 상태를 추적하고,
충돌 패널은 노드별과 필드별 3방향 카드, 인라인 JSON 편집기, 일괄 동작,
인라인 diff 블록을 갖는다고 한다.
디자인 도구가 병합 충돌을 노드와 필드 단위로 푸는 UI를 갖는 것은 이 목록에서
가장 독특한 부분이다.
이 문서가 이 기능을 직접 시험하지는 못했다.

### 협업, 발표 덱, 템플릿과 웹 캡처가 제품의 폭을 넓힌다

협업은 인증된 P2P 세션에 공개 릴레이 대체 경로와 내장 지역 허브를 두고,
10자의 지역 태그 페어링 코드로 계정 없이 LAN 세션에 참여하게 한다.
원격 커서, 계정을 넘는 협업, 편집별 상세와 버려진 편집의 재생이 있는 충돌 패널,
`--serve-web` 데몬의 온라인 다중 테넌트 모드와 장치 로그인이 있다.
발표 덱은 16:9 템플릿 여섯 개와 프로젝터 크기의 AI 덱 계획을 갖고,
PDF와 자체 포함 슬라이드쇼 HTML과 편집 가능한 PowerPoint(`.pptx`)와 hyperframes
영상 구성으로 내보낸다.
장면 템플릿 센터에는 여섯 장면에 걸친 58개 템플릿이 있고,
Chrome 확장은 웹페이지를 충실한 HTML과 레이아웃으로 캡처해 OpenPencil로 보낸다.
이 목록은 디자인 도구라기보다 에이전트가 만드는 제품 화면의 제작 공정 전체를 한
저장소에 담으려는 시도로 읽힌다.

### 같은 저자의 순수 Rust 도구 가족에 속한다

README의 생태계 절은 OpenPencil이 ZSeven-W의 순수 Rust,
AI 네이티브 도구 가족의 일부라고 소개한다.
`jian`이 OpenPencil을 렌더링하고, `agent-rs`가 에이전트를 돌리고,
`noema`가 기억하고, `zode`가 터미널에서 설계한다는 설명이다.
빌드에 필요한 서브모듈 `jian`, `casement`, `agent`가 이 가족의 구성원이다.
이 구조는 편집기가 UI 프레임워크와 에이전트 런타임을 직접 소유한다는 뜻이고,
재작성의 이유이자 유지 부담의 출처다.

## 오픈소스 디자인 도구의 사각 구도

이 프로젝트는 혼자 서 있지 않다.
`design-tool/penpot.md`의 Penpot, `design-tool/open-pencil.md`의
open-pencil/open-pencil(이름이 같은 다른 프로젝트),
이전 이름이 Pencil이었던 pen.dev(`design-tool/pen-dev.md`)가 같은 시기에 같은
빈자리를 겨눈다.
네 도구의 전체 비교표와 파일 형식, 렌더러, 에이전트 면,
서버 문제의 정리는 `design-tool/open-pencil.md`의 「오픈소스 디자인 도구의 사각
구도」에 있다.
이 절은 ZSeven의 자리에서 보이는 모양을 적는다.

### ZSeven이 서로 다른 세 상대와 겹치고 갈리는 곳

| 항목          | ZSeven-W/openpencil                                 | open-pencil/open-pencil                              | Penpot                                            | pen.dev                                 |
| ------------- | --------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------- | --------------------------------------- |

표의 구현과 기능 칸은 각 프로젝트가 자기 문서에서 한 주장이고,
이 문서가 시험한 것이 아니다.
눈에 띄는 것은 ZSeven이 Git과 병합이라는 변경 검토에서 가장 앞서고,
Figma 충실도에서는 open-pencil에 뒤진다는 점이다.
README의 Figma 항목은 레이아웃, 채움, 선, 효과, 텍스트, 이미지,
벡터를 보존하며 가져온다고 적는 데 그친다.
open-pencil은 Figma 기능을 지원, 부분 지원, 왕복만 보존,
미지원으로 나눈 호환성 표를 공개한다.[^os-roadmap]

### 두 OpenPencil은 같은 문제에 반대 방향으로 내기를 건다

ZSeven은 TypeScript와 Electron으로 시작해 `v0.7.5`에서 그 편집기를 퇴역시키고
Rust 워크스페이스로 다시 썼다.
open-pencil은 반대로 TypeScript와 Vue를 유지하고 Skia를 WASM으로 부르며 Tauri로
데스크톱을 만든다.
open-pencil의 비교 페이지는 Penpot과 견주면서 TypeScript와 Vue를 택한 이유로
낮은 진입 장벽과 큰 인력 풀, 빠른 핫 리로드를 든다.[^os-compare]
ZSeven의 README는 같은 문제에서 가비지 컬렉션이 없는 예측 가능한 지연,
55.5MB의 단일 바이너리, 모든 대상에서 같은 GPU Skia 백엔드를 이유로 든다.
한쪽은 기여자와 개발 속도에, 다른 쪽은 런타임 성질과 단일 코어에 건 내기다.
이 문서의 해석으로는 어느 쪽이 옳은지는 이 문서의 자료로 판정할 수 없고,
두 프로젝트의 별 성장, 기여자 수, 릴리스 간격이 몇 달 뒤 쌓이면 알 수
있는 일이다.

두 프로젝트는 서로의 약점을 향해 움직이기도 한다.
open-pencil의 로드맵은 구조화된 노드 트리 diff를 UI, CLI, MCP, SDK,
CI 편집 전반에서 Git 친화적인 검토 산출물로 일급화하겠다고 적는다.[^os-roadmap]
이것은 ZSeven이 `.op`의 JSON으로 먼저 내세운 장점과 겹친다.
반대로 ZSeven은 `.fig` 가져오기를 이미 갖췄다.
README의 로드맵에서도 `.fig` 가져오기는 완료 항목이다.
차이는 앞으로 줄어들 수 있다.

### 돈의 축에서 ZSeven은 라이선스가 자유롭고 모델 비용만 사용자가 낸다

ZSeven은 MIT 라이선스이고 README에는 요금제가 없다.
돈이 들어가는 곳은 모델 비용이다.
README는 에이전트 지원을 표로 정리하는데,
Claude Code는 Claude Agent SDK와 로컬 OAuth로,
Codex CLI와 OpenCode와 GitHub Copilot은 각자의 구독 연결로,
내장 경로는 9곳 이상의 공급자 키로 쓴다고 한다.
이는 사용자가 이미 내고 있는 구독이나 키를 그대로 쓰는 구조여서,
도구 쪽에서 에이전트 사용량에 값을 매기지 않는다.
Anthropic이 서드파티 도구에서의 구독 사용을 막았다는 공지는
`claude/third-party-subscription-block.md`가 다룬다.
ZSeven이 Claude Agent SDK와 로컬 OAuth로 구독을 쓰는 경로가 그 범위에 걸리는지는
이 문서가 확인하지 못했으므로, 구독이 아니라 API 키로 쓰는 경우의 비용을 따로
계산해야 할 수 있다.
README 앞부분의 후원 배너는 두 API 중개 서비스를 소개하며 공식 가격의 10분의
1이나 최대 70% 절감을 내세우고, 이 비용 구조가 도구의 기본 경로가 아니라는 점은
앞의 비평에서 살폈다.

반면 같은 구도의 상용 쪽은 다르게 값을 매긴다.
pen.dev는 편집기와 CLI와 MCP 호출을 무료 단계에서 제한 없이 주지만 에이전트와
디자인하는 날을 월 5일로 막고, 자기 키를 연결해도 이 한도가 계속
계산된다.[^pen-pricing]
Figma는 MCP 호출을 무료 플랜에서 월 20회로 제한한다.[^figma-pricing]
ZSeven의 문서에서 이런 사용 일수나 호출 한도는 찾지 못했다.
이 문서의 해석으로는 모델 구독을 이미 가진 사용자에게 ZSeven은 추가 비용이 없는
도구이고, 병렬 에이전트 팀을 돌리는 만큼 모델 비용이 늘어나는 구조다.
에이전트 팀이 한 요청에 여러 에이전트를 동시에 부르므로,
사용량 기반 요금제의 모델을 쓰는 사람에게는 이 병렬도가 비용을 직접 키운다.
이 비용의 크기는 이 문서가 재지 못했다.

오픈소스냐, 무료냐, 유료냐, 비싸냐의 비교는 `design-tool/open-pencil.md`의 「돈과
라이선스가 갈리는 지점」에 다섯 도구(Figma, Penpot, open-pencil, ZSeven,
pen.dev)의 표로 정리했고, 열 명 기준의 한 달 정가는 `design-tool/pen-dev.md`에 있다.

### `.pen`은 두 OpenPencil을 잇는 접점이다

README는 ZSeven이 `.pen` 파일에서 UIKit를 가져오고 내보낸다고 적고,
open-pencil의 README는 지원되는 `.pen` 문서를 연다고 적는다.
pen.dev는 `.pen`을 에이전트가 바로 다루는 JSON 파일이고 스키마를 완전히
공개했다고 소개한다.[^pen-dev]
세 도구가 모두 같은 형식을 어느 정도 다룬다는 점은 `.pen`이 오픈소스 쪽에서
사실상의 교환 형식이 될 가능성을 보여 준다.
다만 ZSeven은 UIKit에, open-pencil은 지원되는 문서에 제한을 두고 있어 어느
범위까지 열리는지는 세 도구 모두 문서에서 정확히 적지 않는다.
open-pencil의 로드맵은 `.pen`을 가져오기 전용이 아니라 편집하고 저장할 수 있는
형식으로 만들겠다고 적는다.[^os-roadmap]

### Penpot의 자리에서는 ZSeven이 서버 문제를 건너뛴다

Penpot은 서버 협업과 접근 통제와 셀프 호스팅이 강점이다.
ZSeven은 서버 없이 P2P와 선택형 온라인 다중 테넌트 데몬으로 협업하고,
웹 호스트는 Docker 이미지로 띄운다고 README가 안내한다.
접근 통제와 영속성은 서버가 필요한 영역인데 ZSeven은 이를 다루는 방식이 다르다.
Penpot의 렌더러가 SVG에서 WebGL로 옮겨 가는 베타 단계에 있다는
점에서,[^penpot-webgl] ZSeven은 처음부터 GPU Skia를 쓴 선택의 이점을 갖는다.
그러나 Penpot에는 오래 쌓인 사용자와 플러그인과 라이브러리가 있고,
ZSeven에는 없다.
이 문서의 해석으로는 ZSeven은 Penpot의 시장을 직접 뺏기보다 에이전트가 화면을
처음부터 만드는 새 작업 방식에서 자리를 잡는 쪽이다.

## 비평

### 최초라는 주장은 검증되지 않았다

저장소 설명은 세계 최초의 오픈소스 AI 네이티브 벡터 디자인 도구이자 동시
에이전트 팀을 갖춘 첫 도구라고 한다.
이 문서가 살핀 범위에서 근거는 없다.
같은 시기에 비슷한 이름과 목표를 내세운 다른
프로젝트(`open-pencil/open-pencil`)도 있고, HN의 같은 검색 결과에서 그
프로젝트의 게시물이 더 높은 점수(17점)를 받았다.[^open-pencil-hn]
최초라는 표현은 마케팅 문구로 보고 기능 목록만 판단 대상으로 삼는 편이 낫다.

### 기능 목록이 길어서 어느 것이 실제로 성숙한지 알 수 없다

README는 AI 생성, 팀, 협업, Git, 덱, 템플릿 센터 58종, Chrome 확장까지 한 문서에
나열한다.
v0.8대 버전이고 TypeScript 편집기를 퇴역시킨 지 오래되지 않았으며, 기능마다
안정성이나 한계를 적지 않았다.
Rust 재작성 뒤 이전 편집기의 기능이 얼마나 옮겨졌는지, 각 기능의 완성도는
README만으로 알 수 없다.

### 후원 배너가 사용자의 모델 선택에 영향을 준다

README 앞부분의 큰 부분을 두 API 중개 서비스(Infistar.cc, Fluxion AI)의 후원
문구가 차지하고, 가입 링크에 추천 코드가 붙어 있다.
한 곳은 공식 가격의 10분의 1, 다른 한 곳은 최대 70% 절감을 내세운다.
중개 서비스가 요청과 응답을 거치는 구조라서, 디자인 파일과 프롬프트가 어디로
가는지는 사용자가 따로 확인해야 한다.
이 문서는 두 서비스를 확인하지 않았다.

### 단일 개발자의 홍보 방식에 대한 반응

HN에서 verdverm은 며칠 전의 제출과 달라진 점이 있느냐고, 이 링크를 세 번
올렸다며 HN이 주로 자기 홍보에 쓰는 것을 금지한다고 지적했다.[^verdverm]
제작자 finiking은 저장소에는 매일 커밋이 있었고 중복 제출은 처음 써 본 제출
시스템에서 생긴 실수였으며, 앞으로는 큰 버전이나 구조 변화에서만 올리겠다고
답했다.[^finiking-reply]
같은 제작자는 첫 글에서 GUI 시대의 디자인 도구가 final_v9.fig를 내려받고 손으로
요소를 고치는 일을 바꾸고 싶었다고 동기를 설명했다.[^finiking]

### 성능과 크기 수치는 README의 서술이고 측정 방법이 없다

README는 55.5MB의 데스크톱 바이너리, 8.2MB의 wasm(전송 2.18MB),
1만 노드 캔버스에서 패닉 없음과 유휴 CPU 약 0%, 전체 레이아웃 스냅숏 약 0.68초,
휠 줌 CPU를 약 69%에서 약 0%로 줄였다고 적는다.
모두 개선 전후의 한 줄 서술이고 하드웨어, 문서 구성, 측정 도구가 없다.
open-pencil의 비교 페이지도 같은 유형의 수치(시작 2초 미만,
지연 1ms 미만)를 측정 방법 없이 낸다.[^os-compare]
두 프로젝트의 수치는 서로 다른 지표라서 직접 비교할 수 없다.
같은 샘플 문서를 두 도구에 열어 재지 않는 한,
어느 쪽이 빠르다는 문장은 홍보 문구로 읽어야 한다.

### 설치 경로의 신뢰 비용이 사용자에게 넘어온다

README의 CLI 설치 안내는 원격 스크립트를 받아 바로 셸에 넘기는 `curl ... |
bash`와 PowerShell의 `irm ... | iex` 방식을 쓴다.
Windows 설치기가 백신에 걸린다는 안내도 README에 있고,
새로 나온 낮은 보급 릴리스에 대한 알려진 휴리스틱 오탐이며 다운로드를 검증하는
방법이 따로 있다고 적는다.
이 설명은 정직하지만, 보급이 적은 새 바이너리를 설치하는 사용자에게 검증의
부담이 넘어온다는 뜻이기도 하다.
같은 기능을 하는 Homebrew와 Scoop 경로가 있으므로 가능하면 패키지 관리자를
쓰는 편이 낫다.
이 문서는 스크립트의 내용을 읽지 않았다.

### 한 저장소의 가족 의존이 단일 실패 지점을 만든다

편집기가 UI 프레임워크 `jian`, 윈도 계층 `casement` 포크,
에이전트 런타임 `agent-rs`를 서브모듈로 직접 소유한다.
빌드하려면 세 서브모듈을 함께 받아야 한다.
외부 의존이 적다는 장점이 있지만, 같은 저자가 이 모두를 유지해야 한다는
뜻이기도 하다.
HN에서 verdverm이 지적한 홍보 방식의 문제와 별개로,
단일 개발자 프로젝트의 지속성은 저장소 바깥 사정에 좌우된다.
GitHub API로 2026년 10월 28일에 읽은 별은 6,764개, 포크는 590개,
열린 이슈는 23개다.
이 숫자는 건강도의 판정이 아니다.

### 에이전트 팀의 일관성 보증은 홈페이지에도 README에도 방법이 없다

홈페이지는 병렬 작업 뒤에 공유 내비게이션과 시각 언어를 다시 모은다고 하고,
README는 스타일 가이드와 anti-slop을 둔다.
그러나 구역마다 다른 에이전트가 낸 색, 간격,
문구가 충돌할 때 어떻게 조정하는지는 적혀 있지 않다.
이는 글의 핵심 약속인 한 번의 요청으로 일관된 여러 화면이 나온다는 주장에 직접
걸린 공백이다.
결과물의 품질을 보여 줄 사례로는 홈페이지의 쇼케이스 다섯 개가 전부이고,
생성 과정은 밝혀져 있지 않다.

## 인사이트

### 디자인 파일을 코드로 만드는 방향은 에이전트의 변경 확인을 풀어 준다

`.op`가 JSON이라 Git에서 비교할 수 있다는 점이 이 제품에서 가장 실용적인
부분이다.
에이전트가 디자인을 읽고 코드를 만든 뒤 디자인이 바뀌면, 바뀐 부분을 텍스트
차이로 확인할 수 있다.
에이전트가 디자인을 보고 구현한 뒤 디자인이 바뀌면 바뀐 부분을 확인할 수
있느냐는 질문에 대해, 텍스트로 비교되는 파일 형식은 하나의 실용적인 답이다.
다만 차이로 보이는 것은 노드와 속성의 변화이지 시각적 의미의 변화가 아니다.
자동 레이아웃이 바뀌면 JSON의 작은 수정이 화면에서는 큰 변화일 수 있고, 그
반대도 있다.

### 시각 도구의 동시 에이전트는 공간 분할을 전제로 한다

README의 에이전트 팀은 페이지를 히어로, 기능, 푸터처럼 공간 단위로 나눠 병렬로
만든다.
이 방식은 구역이 독립적일 때 빠르지만, 색과 간격과 문구의 일관성은 구역을
가로지르는 제약이다.
README가 반복 생성 사이의 다양성을 추적하는 anti-slop 기능을 별도로 두는 점은
병렬 생성이 닮은 결과를 낳는다는 문제의식이 있음을 보여 준다.
홈페이지는 병렬 작업 뒤에 공유 내비게이션과 시각 언어를 다시 모으고 스타일
가이드로 화면의 일관성을 유지한다고 밝힌다.
다만 모으는 방식과 구역 사이에 충돌이 날 때의 처리는 README와 홈페이지 어디에도
적혀 있지 않다.

### 이 글을 읽는 방법

도입을 검토한다면 먼저 로컬에서 데스크톱 앱과 `.op` 파일로 한 화면을 만들어
보고, 모델 연결은 직접 가진 키(또는 로컬 CLI 에이전트)로 하는 편이 안전하다.
후원 중개 서비스는 선택이며 README의 기본 경로가 아니다.
이 프로젝트의 주장을 가를 관찰은 두 가지다.
v0.8 이후에도 Rust 재작성 이전 기능의 이전이 마무리되는지, `.op`를 Git으로
관리하는 팀의 실제 사례가 나오는지다.
둘 다 확인되지 않으면 이 프로젝트는 기능이 많은 초기 단계 도구로 남는다.

### 변경 검토를 가진 쪽이 에이전트 시대의 디자인 도구에서 유리하다

에이전트가 디자인을 직접 고치게 되면 가장 먼저 필요한 것은 무엇이 바뀌었는지
사람이 확인하는 수단이다.
코드는 diff와 풀 리퀘스트가 그 수단이고,
디자인 도구는 지금까지 그 수단이 없었다.
ZSeven은 `.op`를 JSON으로 두어 Git의 3방향 병합과 노드와 필드 단위의 충돌
패널을 만들었다.
open-pencil의 로드맵은 구조 diff를 Git 친화적인 검토 산출물로 일급화한다고
적었고,[^os-roadmap] 이는 같은 필요를 다른 길에서 인식한 것이다.
이 문서의 해석으로는 이 경쟁에서 이기는 쪽은 에이전트가 만든 변경을 사람이 가장
빨리 승인하거나 되돌릴 수 있게 하는 도구다.
시험은 같은 수정을 에이전트에게 시키고 사람이 변경을 검토하는 데 걸린 시간을
재는 것이다.

다만 이 우위는 파일을 코드처럼 다루는 팀에게만 의미가 있다.
JSON 차이는 노드와 속성의 변화이지 화면의 변화가 아니다.
시각 diff와 구조 diff를 함께 보여 주는 도구가 이 구도에서 더 앞선다.
open-pencil의 로드맵이 시각 diff와 patch 도구를 개발 버전에 넣었다고 쓴 점도
이를 겨눈다.[^os-roadmap]

### 같은 이름의 두 프로젝트가 가르는 선택은 Figma 자산과 Git 습관 둘뿐이다

세 문서의 사실을 팀의 상황에 대어 보면 두 OpenPencil의 선택 기준은 두
질문으로 줄어든다.
이 기준은 이 문서의 해석이며 측정 결과가 아니다.

| 질문                                           | 답이 그렇다면 먼저 시험할 도구 |
| ---------------------------------------------- | ------------------------------ |
| 기존 `.fig` 자산을 계속 읽고 써야 하는가       | open-pencil                    |
| 디자인 변경을 Git에서 병합하고 검토하고 싶은가 | ZSeven-W/openpencil            |
| 서버 협업과 접근 통제가 필요한가               | Penpot                         |
| 에이전트가 처음부터 화면을 그리게 하고 싶은가  | ZSeven-W/openpencil, pen.dev   |

위 표에서 둘 이상에 해당하면 같은 샘플 화면으로 두 도구를 돌려 결과와 수정
횟수를 비교하는 것이 이 문서가 권하는 방법이다.
이 문서는 그 비교를 하지 못했다.
이 가설을 뒤집는 관측은 한쪽이 다른 쪽의 형식과 기능을 흡수해 격차가
사라지는 경우다.

### 재작성의 값은 몇 달 뒤 별이 아니라 이탈률로 나온다

TypeScript와 Electron 편집기를 접고 Rust 워크스페이스로 다시 쓴 결정은 어느
프로젝트에도 큰 내기다.
이전 편집기의 기능이 얼마나 옮겨졌는지,
사용자가 얼마나 남았는지는 별 수가 아니라 이슈와 릴리스 노트에서 읽을 수 있다.
README는 `v0.8`대의 개발 중인 제품이라고 밝힌다.
반면 open-pencil은 같은 시기에 v0.16.0까지 릴리스를 냈다.
버전 숫자는 서로 다른 체계라 비교할 수 없지만,
릴리스 간격과 변경 기록의 두께가 두 프로젝트의 속도를 가늠하는 단서다.
이 문서가 이를 정량으로 비교하지는 못했다.
판단을 가를 관찰은 `v0.8` 이후 재작성 이전 기능의 이전이 끝나는 시점과,
`.op`를 Git으로 관리하는 팀의 실제 사례가 나오는 시점이다.
