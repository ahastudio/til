# desigma: Figma 파일을 읽고 오프라인으로 돌아가는 Rust 네이티브 오픈소스 디자인 도구

<https://github.com/deepfounder-ai/desigma>

## 소개

desigma는 Rust로만 작성한 데스크톱 디자인 도구다.
GitHub 저장소의 설명은 “Free Figma alternative made on Rust”이고,
README는 자신을 독립적이고 로컬 우선이며 오픈소스인 인터페이스 디자인 도구라고
소개한다.
프레임, 오토 레이아웃, 컴포넌트와 변형(variant), 프로토타이핑, 실시간 협업,
키프레임 모션, 화이트보드, 발표 자료(deck), 벡터 편집,
실제 Figma 파일 가져오기를 한 앱에 담았다고 한다.
프로젝트는 무료이고 오프라인으로 동작하며 macOS, Windows, Linux에서
네이티브로 돈다고 말한다.

2026년 11월 11일에 GitHub에서 읽은 상태는 다음과 같다.

| 항목                  | 값                                           |
| --------------------- | -------------------------------------------- |
| 저장소 생성           | 2026년 10월 11일                             |
| 마지막 갱신           | 2026년 11월 9일                              |
| 별 / 포크 / 열린 이슈 | 1,197 / 119 / 12                             |
| 언어                  | Rust                                         |
| 최신 릴리스           | v0.1.0-alpha.18(2026년 11월 9일, 프리릴리스) |
| 커밋 수               | 389개                                        |
| 라이선스              | MIT 또는 Apache-2.0(사용자가 선택)           |

README 상단의 배지도 이 프로젝트의 상태를 “early alpha”라고 표시한다.
릴리스는 `.dmg`(macOS), 설치 프로그램과 휴대용 `.zip`(Windows),
`.tar.gz`(Linux)로 나온다.
릴리스 빌드는 아직 코드 서명이 되어 있지 않아 첫 실행에서 경고가 뜬다고
README가 밝힌다.

## 기능

README가 내세우는 기능을 묶으면 다음과 같다.

- 편집: 프레임, 섹션, 도형, 펜과 연필, 텍스트, 벡터 네트워크(점 편집,
페인트 버킷, 올가미 선택)와 도형 빌더, 윤곽선 변환,
평탄화 같은 벡터 연산을 갖춘다.
- 레이아웃: 방향, 줄바꿈, 간격, 여백, 정렬,
허그·채움·고정 크기를 지원하는 오토 레이아웃과 제약 조건, 그룹,
클리핑 프레임을 제공한다.
- 컴포넌트와 변수: 컴포넌트 세트와 변형, 인스턴스 오버라이드,
색·숫자·문자열·불리언 변수를 모드와 함께 다룬다.
공유 라이브러리는 컴포넌트와 스타일과 변수를 게시하고
새 버전에는 검토 단계가 있다.
- 프로토타입: 흐름 시작점과 연결선, 트리거와 액션과 오버레이, 이징과 스프링,
Smart Animate를 지원한다.
변수와 조건문(If/Else if/Else)으로 프로토타입을 제어하며 파일은 바뀌지 않는다.
- 모션(베타): 페이지를 타임라인으로 바꾼다.
키프레임, 이징과 스프링, 프리셋 41개, GIF·WebM·PNG 시퀀스 내보내기를 갖추고
Figma의 Motion 베타 모드 데이터를 가져온다.
- 협업(베타): 공유 링크로 계정 없이 함께 편집한다.
피어 투 피어 암호화 연결이고 속성 단위로 병합하며
각자의 되돌리기는 자기 편집만 되돌린다.
- 보드와 발표: 포스트잇, 연결선, 표, 코드 블록, 타이머와 투표를 갖춘 화이트보드,
슬라이드 정렬과 발표자 노트와 전체 화면 발표를 갖춘 덱이 있다.
- 개발자 인계: Dev 모드가 측정값과 CSS, Tailwind, SwiftUI, Jetpack Compose,
React 코드를 만든다.
- 파일 형식: 가져오기는 `.fig`(FigJam 보드와 Motion 데이터 포함),
Figma REST JSON, Pencil `.pen`, SVG, 자체 `.desigma`이고, 내보내기는 `.desigma`,
Figma REST JSON, PNG, JPG, SVG, PDF, 애니메이션 GIF·WebM이다.
- 에이전트: 로컬 MCP 서버가 16개 도구로 파일 가져오기, 레이어와 토큰 조회,
코드 생성, 되돌리기가 있는 편집을 맡는다.
편집기의 에이전트 브리지를 켜면 같은 도구가 화면에 열린 문서를 직접 편집하고
되돌리기를 공유한다.
- 플러그인: 매니페스트 URL을 붙여 넣어 설치하며,
스키마 2 플러그인은 브라우저에서 HTML 패널로 열린다.

## 구조

README가 설명하는 설계는 문서 모델 하나를 여러 크레이트가 공유하는 모양이다.
`desigma-doc`이 장면 그래프와 되돌리기 스택을 담고
모든 편집은 정확한 역연산이 있는 명령(Command)이다.
`desigma-render`는 tiny-skia로 CPU에서
그려 같은 입력이 바이트 단위로 같은 출력을 내도록 한다.
`desigma-gpu`는 CPU로 물러날 수 있는 wgpu 렌더러다.
UI는 egui로 만들고, Electron과 웹 뷰는 쓰지 않는다고 한다.
시각 회귀는 `desigma-diff`가 스크린샷을 안티에일리어싱 감지와 SSIM으로 비교해
HTML 보고서를 만든다.
협업은 `desigma-collab`(문서 차이 동기화와 충돌 규칙)과 `desigma-net`(iroh 기반
QUIC 전송)이 맡는다.

저장소의 `crates` 디렉터리에는 크레이트가 16개 있다.
README의 크레이트 표는 그 가운데 15개를 적는다.
표에 없는 `desigma-server`는 Cargo 설명에 “상시 켜져 있는 헤드리스 호스트로
.desigma 파일을 영구히 공유한다”고 적혀 있다.

## 시작하기

릴리스 페이지에서 플랫폼별 빌드를 받아 쓰거나 소스에서 빌드한다.

```sh
git clone https://github.com/deepfounder-ai/desigma
cd desigma
cargo run --release -p desigma-app               # 데모 문서가 열린 편집기
cargo run --release -p desigma-app -- file.fig   # Figma 파일 열기
cargo test --workspace                           # 테스트
```

리눅스에서는 창 시스템 헤더(`libxkbcommon-dev`, `libwayland-dev`,
`libx11-dev` 등)가 필요하다고 README가 적는다.
자동화를 위한 명령줄 옵션도 있다.

```sh
desigma --screenshot out.png --size 1600x1000 --select Card   # 프레임 하나를 그려 저장하고 종료
desigma --tab prototype --present                              # 프로토타입 발표 모드로 바로 열기
desigma-diff compare reference.png actual.png --out diff.png   # 이미지 두 장 비교
```

MCP 서버는 `cargo build --locked -p desigma-mcp`로 빌드하고
클라이언트가 `desigma-mcp --workspace /path/to/designs`를 실행하게 설정한다.
이 문서는 코드를 직접 빌드하거나 실행해 보지 않았고, 위 명령은 README에서
옮긴 것이다.

## 분석

### 이 저장소의 주장은 기능의 폭과 개발의 속도에 걸려 있다

README의 기능 목록은 디자인 편집기 하나가 아니라 편집, 프로토타이핑, 모션,
화이트보드, 발표, 협업, 코드 생성, 에이전트 연동,
플러그인을 한 저장소에 모은 것이다.
저장소는 2026년 10월 11일에 만들어졌고 11월 9일에 알파 18번째 릴리스가 나왔다.
이 문서의 계산으로 29일 동안 커밋이 389개이고 하루 평균 13개 남짓이다.
GitHub의 기여자 목록에서 한 계정이 약 86%의 커밋(326개)을 올렸다.

이 속도와 집중은 사실만 말해 준다.
README는 이 코드가 어떻게 작성되었는지,
곧 사람이 얼마나 직접 썼는지는 밝히지 않는다.
다만 짧은 기간에 넓은 기능이 쌓였다는 것이 알파라는 상태 표기와 함께 읽혀야
한다.

### 호환성은 한 방향이고 독립성을 강조한다

가져오기 형식이 많고 내보내기는 자체 형식과 범용 형식에 그친다.
`.fig`와 `.pen`은 가져오고 저장은 `.desigma`로 간다.
Motion 데이터도 `.fig` 파일에 되쓰지 못한다고 README가 밝힌다.
이는 Figma를 쓰던 사람이 파일을 잃지 않고 옮겨 올 길을 열면서,
다시 돌아가는 길은 열지 않는 구조다.

동시에 README와 저장소 문서는 독립성을 거듭 말한다.
Figma와 제휴하거나 보증받지 않았고,
Figma의 편집기 외관을 그대로 재현하는 것은 목표가 아니며,
파일 호환성과 익숙한 작업 흐름이 개발을 이끈다고 적는다.
`PLAN.md`도 같은 취지로 방향을 다시 썼다고 적고,
상표 정책 문서는 이름과 로고가 DeepFounder의 상표이며
포크는 다른 이름을 써야 한다고 정한다.
코드는 MIT 또는 Apache-2.0이지만 이름과 로고에는 라이선스가 미치지 않는다.

### 협업은 서버 없는 호스트 방식이다

공유 링크 하나로 계정 없이 함께 편집한다는 설계는 호스트의 앱이 세션을 맡는다는
뜻이다.
README는 세션이 호스트가 파일을 닫으면 끝나고 손님은 사본을 저장할 수 있다고
적는다.
편집은 속성 단위로 병합되어, 같은 레이어의 색과 위치를 두 사람이 바꾸면
둘 다 남고 같은 프레임에 넣은 삽입도 둘 다 남지만 삭제는 편집을 이긴다.
직접 연결이 불가능하면 공개 중계 서버를 거치되 종단 간 암호화가 유지된다고 한다.

이 구조에서 파일의 소유와 지속성은 호스트의 컴퓨터에 있다.
영구 공유를 원하면 상시 켜진 호스트가 필요하고,
저장소의 `desigma-server` 크레이트가 바로 그 일을 하는 것으로 보인다.
이는 이 문서의 추정이며 README는 이 크레이트를 설명하지 않는다.

## 비평

### 알파 선언과 기능 목록이 서로 어긋난다

README 가운데 상태 안내는 desigma가 초기 알파이고
전문가의 일상 작업을 대체하지 못하며 가장 큰 공백이 협업, 플러그인,
PDF 내보내기, 실제 `.fig` 파일에서 검증되지 않은 기능, 코드 서명이라고 적는다.
그러나 같은 README의 앞부분은 실시간 협업(베타), 네이티브 플러그인 설치,
PDF 내보내기(슬라이드와 덱)를 이미 기능으로 소개한다.
둘이 같은 시점의 서술이라면 기능이 있으나 아직 공백으로 남았다는 뜻이고,
다른 시점의 서술이라면 둘 중 하나가 낡았다는 뜻이다.

덱의 PDF 내보내기는 고해상도 래스터 페이지이며 텍스트를 선택할 수 없다고
README가 직접 적는다.
그러므로 PDF가 공백이라는 말은 벡터 PDF를 뜻하는 것으로 읽을 수 있다.
이는 이 문서의 해석이며 README가 그렇게 풀어 쓰지는 않는다.
독자가 상태를 판단하려면 이런 해석을 스스로 해야 한다는 점이 문제다.

### 성능과 품질의 수치는 재현 방법이 README에 없다

README는 5,000개 레이어 페이지에서 이동과 드래그가 한 프레임 안에 들어온다고
하고, 워크스페이스 전체에 테스트가 1,600개가 넘는다고 적는다.
프리셋 41개와 블렌드 모드 19개도 수로 적혀 있다.
이 가운데 기능의 수는 UI에서 셀 수 있지만
성능 주장과 테스트 수는 독자가 확인하려면 직접 빌드하고 돌려야 한다.
README는 성능을 재는 명령이나 측정 환경을 적지 않는다.

이 문서도 빌드와 측정을 하지 않았으므로 이 수치들은 프로젝트의 주장으로 남는다.
스크린샷은 모두 앱의 `--screenshot` 모드로 오프스크린에서 찍은 것이라고
README가 밝히는데, 이는 화면이 실제 앱의 출력이라는 근거이지 사용 중의 성능이나
안정성의 근거는 아니다.

### Figma 파일 가져오기의 신뢰도가 스스로 낮게 적혀 있다

헤드라인은 실제 Figma 파일 가져오기를 내세운다.
그러나 본문은 `.fig` 형식이 문서화되지 않았고
디코더가 커뮤니티의 역공학을 따르며
합성 파일로 시험했으므로 실제 파일에서는 빈틈이 있을 것이라고 밝힌다.
Motion 가져오기도 휜 모션 경로와 색·효과 트랙을 아직 가져오지 못한다.
가져오기가 가장 큰 차별점이라면 지원 범위가 가장 불확실한 부분이기도 하다.

이 정직한 서술은 장점이지만, 사용자가 자기 파일을 옮기기 전에 얼마나 깨지는지
가늠할 수단(호환성 표, 실제 파일 시험 결과)이 README에 없다.
이슈 보고를 요청하는 것이 현재의 유일한 피드백 경로다.

### 플러그인은 신뢰를 설치 시점에 요구한다

플러그인 패널은 브라우저에서 열리고,
문서에는 `document:insert-svg`와 `storage:local` 권한만 열려 있으며
플러그인이 문서를 읽거나 GitHub 자격 증명에 접근하지는 못한다고 한다.
README는 이것이 범용 JavaScript 샌드박스가 아니라 제한된 문서 연결이라고
솔직히 적는다.
브라우저의 자바스크립트는 평소의 브라우저 기능을 그대로 가진다.

설치 예시의 URL은 가변 브랜치인 `main`을 가리키는데, 바로 뒤에서
고정된 패키지 판을 원하면 `main` 대신 커밋 해시를 쓰라고 권한다.
기본 예시가 덜 안전한 쪽이라는 점이 눈에 띈다.
다운로드 한도(파일 16개, 파일당 2MiB,
합계 8MiB)와 리다이렉트 금지는 공격면을 줄이는 장치로 읽힌다.

### 기여가 한 계정에 몰려 있다

기여자 목록에서 가장 많은 계정이 커밋의 약 86%를 올렸고
나머지는 여섯 명이 20개 이하다.
알파 단계의 프로젝트로는 흔한 모양이지만,
상표와 이름의 통제권도 한 회사(DeepFounder)에 있다.
오픈소스 라이선스가 포크를 허용해도 이름과 로고를 쓸 수 없어서,
프로젝트가 멈추면 포크는 새 이름으로 시작해야 한다.
이는 흔한 정책이며 이 프로젝트만의 결함은 아니다.

## 인사이트

### 파일 호환성은 사용자의 이동 비용을 먼저 낮추는 전략이다

가져오기 형식이 많은 도구는 기능으로 이기기 전에 이동 비용으로 경쟁한다.
`.fig`, FigJam 보드, `.pen`, SVG를 열 수 있으면 사람들은 기존 자산을 버리지 않고
시험해 볼 수 있다.
반대 방향의 호환(되쓰기)이 없는 것은 이동을 한 방향으로 만들어,
시험이 곧 이주가 되게 한다.

이 구도는 사무용 소프트웨어에서 오래 있었던 문서 형식 호환 경쟁과 같은 모양이다.
다만 형식이 문서화되지 않았다는 점이 다르다.
상대 형식이 바뀔 때마다 역공학 디코더를 고쳐야 하므로 호환의 유지비는 시간이
갈수록 쌓인다.
그 부담을 소수의 기여자가 계속 질 수 있는지가 이 전략의 지속성을 정한다.
이는 이 문서의 해석이다.

### 되돌리기의 소유권이 협업과 에이전트에서 다르게 정해져 있다

README에서 협업 편집의 되돌리기는 자기 편집만 되돌린다.
반면 에이전트 브리지를 켜면 MCP 도구가 화면에 열린 문서를 편집하고
사용자의 되돌리기를 공유한다.
사람과 사람 사이에서는 편집의 주인이 구분되고,
사람과 에이전트 사이에서는 구분되지 않는다.

이 차이가 실무에서 중요한 이유는 에이전트가 한 번에 여러 변경을 가할 수 있기
때문이다.
사용자가 되돌리기를 누르면 어디까지가 한 단계인지,
그 전에 한 자기 작업을 건드리게 되는지가 문서에 적혀 있지 않다.
README는 에이전트의 편집이 같은 되돌리기를 공유한다고만 말한다.
디자인 도구가 에이전트로 조작되는 시대에는 편집의 단위와 소유를 사람과
에이전트에 대해 어떻게 나눌지가 인터페이스의 핵심 결정이 된다.
이는 이 문서의 관점이며 README가 다룬 문제가 아니다.

### 서버 없는 협업은 지속성을 요구하는 순간 서버로 돌아간다

링크 하나, 계정 없음, 서버 없음이라는 협업의 매력은 호스트가 켜져 있는 동안만
성립한다.
세션이 끝나면 파일의 정본이 어디 있는지,
호스트가 없을 때 변경을 누가 받는지가 문제가 된다.
저장소에 상시 켜진 호스트 크레이트가 있다는 사실은 피어 투 피어에서 중계로,
그리고 상시 호스트로 옮겨 가는 익숙한 경로를 가리킨다.

이는 프로젝트가 잘못 설계되었다는 뜻이 아니라 로컬 우선과 영구 공유 사이의
긴장이 설계에 드러난 것이다.
개인과 작은 팀에는 호스트 방식이 충분하고,
팀 단위의 영구 공유에는 상시 호스트가 필요하며,
그 둘 사이의 경계를 README가 아직 정리하지 않았다.

### 결론을 바꿀 관찰

- 실제 사용자 파일의 `.fig` 가져오기 결과를 모은 호환성 표나 이슈 통계가 나와서
대부분의 파일이 깨지지 않는다고 확인된다면, 가져오기에 대한 비평은 약해진다.
- 5,000개 레이어에서
프레임 안에 들어온다는 성능이 공개된 명령과 환경으로 재현된다면,
성능 수치가 주장에 머문다는 지적은 해소된다.
- 협업이 베타를 벗어나고 상시 호스트 방식이 문서화되며
되돌리기 규칙이 에이전트 편집에 대해 정리된다면,
위의 협업과 되돌리기에 대한 우려는 줄어든다.
