# 코드 마이그레이션은 손이 아니라 스크립트로 한다

원문: [Script Your Code Migrations](https://will-keleher.com/posts/script-your-code-migrations/)

## 소개

Will Keleher가 코드베이스 전체를 훑어 고치는 일을
허술한 스크립트로 처리하는 방법을 정리한 글이다.
주장의 핵심은 기술적 정교함이 아니라 기준의 조정에 있다.
코드를 고쳐 쓰는 스크립트는 가능한 모든 경우를 다룰 필요가 없고,
실제로 코드베이스에 존재하는 경우만 다루면 된다는 것이다.

## 작은 예: CSS 애니메이션 지연

출발점은 사소한 문제다.
CSS에는 여러 애니메이션의 `animation-delay`를 한꺼번에 비율로 조정하는 방법이 없다.
애니메이션이 두 배 빨라지면 어떨지 보고 싶다면 모든 줄을 손으로 고쳐야 한다.

```css
.component-1 {
    animation-delay: 1s;
}
.component-2 {
    animation-delay: 2s;
}
```

vim 한 줄로도 되겠지만, 어떤 언어로든 스크립트를 쓰는 편이 간단하다고 저자는 말한다.

```python
import sys

with open(sys.argv[1], "r") as infile:
    contents = infile.read()
with open(sys.argv[1], "w") as outfile:
    for line in contents.splitlines():
        if "animation-delay" in line:
            # "  animation-delay: 1.5s;" 를 콜론에서 갈라 숫자만 반으로 줄인다
            first, rest = line.replace("s;", "").split(":")
            line = f"{first}: {round(float(rest) / 2, 2)}s;"
        outfile.write(line)
        outfile.write("\n")
```

대부분은 복사해 붙일 수 있는 상용구이고,
실제 변환은 세 줄이다.
저자는 이것이 완벽한 변환이 아니지만 자기가 원한 방식으로 파일을 바꾸기에는 충분했다고 적는다.

범위를 좁히고 싶다면, 예컨대 특정 클래스의 타이밍만 바꾸고 싶다면 현재 선택자를 기억하면 된다.

```python
search_match = re.search(r'(.*)\s*\{', line)
if search_match:
    curr_selector = search_match.group(1)   # 여는 중괄호를 만나면 현재 선택자를 갱신한다
if ".my_class" in curr_selector and "animation-delay" in line:
    ...
```

저자의 평가가 이 글 전체의 태도를 압축한다.
한편으로 이것은 끔찍한 파서이며 대단히 취약하다.
그러나 결정적인 장점이 하나 있는데, 만드는 데 시간이 거의 들지 않았다는 것이다.

여기서 기준이 제시된다.
코드 파일을 고쳐 쓰는 스크립트는 코드베이스에 실제로 있는 경우만 다루면 되고,
그조차 전부 다룰 필요가 없다.
열 개 중 아홉 개 파일의 마이그레이션을 자동화할 수 있다면
그것만으로도 마이그레이션 전체를 해 볼 만하게 만드는 노력 절감이 된다.

## 실제 사례: 쿼리에 이름 붙이기

진짜 문제로 넘어간다.
애플리케이션이 돌리는 모든 쿼리에 고유한 이름을 붙여
슬로우 쿼리 로그에 나타나게 하면 대단히 유용하지만,
지금까지 이름을 붙여 오지 않았다면 그 이름들을 소급해 채워야 한다.
코드베이스에 쿼리가 수천 개라면 감당할 수 없는 작업량이다.
스크립트를 쓰지 않는 한 그렇다.

몇 해 전 저자는 다른 엔지니어와 한 시간 동안 짝을 지어
애플리케이션의 모든 쿼리에 이름을 붙이는 스크립트를 짰다.
영향력으로 따지면 그 조잡한 작은 NodeJS 스크립트가
회사에서 이룬 일 중 가장 중요한 축에 들었을 것이라고 적는다.

```typescript
// 고치기 전
async function findWidgetsByGroupId (groupId: Id) {
    return new WidgetQueryBuilder()
        .whereId("groupId", groupId)
        .findMultiple();
}

// 고친 뒤
async function findWidgetsByGroupId (groupId: Id) {
    return new WidgetQueryBuilder({ name: "findWidgetsByGroupId" })
        .whereId("groupId", groupId)
        .findMultiple();
}
```

CSS 파일 하나에 썼던 것과 정확히 같은 패턴이 코드베이스 전체에도 통한다.

```python
# 의사 코드
import sys
import re
import os
files = sys.argv[1:]   # uv run ./this_script.py $(rg QueryBuilder | grep .ts)

for file in files:
    with open(file, "r") as infile:
        file_contents = infile.read()
    with open(file, "w") as outfile:
        file_label = os.path.basename(file).split(".")[0]

        # 파서가 놓친 자리를 출력에서 바로 알아볼 수 있도록 눈에 띄는 기본값을 둔다
        curr_function = "unset: if you see this in output, my terrible parser didn't handle something properly"
        for line in file_contents.splitlines():
            if "function" in line:
                # 원문은 공백과 괄호를 제외한 문자 집합으로 이름을 잡는다.
                # 여기서는 같은 뜻을 단어 문자 집합으로 바꿔 적었다.
                curr_function = re.search(r"function (\w+)", line).group(1) or curr_function

            if "QueryBuilder()" in line:
                line = line.replace("QueryBuilder()", f"QueryBuilder({{ name: '{file_label}.{curr_function}' }})")
            outfile.write(line)
            outfile.write("\n")
```

기본값 문자열에 담긴 발상이 이 스크립트에서 가장 배울 만한 부분이다.
파서가 실패했을 때 조용히 잘못된 값을 넣는 대신
결과물 안에 눈에 띄는 문자열을 남겨, 검색 한 번으로 실패 지점을 전부 찾아낼 수 있게 한다.

저자는 이런 마이그레이션을 돌리기 전에 반드시 코드를 백업하라고 강조한다.
처음 돌릴 때는 거의 확실히 몇 가지 경우를 놓쳐서 전부 되돌려야 할 것이기 때문이다.

실제 스크립트는 글에서 다루지 않은 것들을 더 처리했다고 밝힌다.
중첩 함수, `QueryBuilder<TypeOverride>` 형태,
`const fnName = async () =>` 문법, 이미 생성자 인자가 있는 경우 등이다.
그 한 번 쓰고 버린 코드가 2,113개의 쓸 만한 쿼리 이름을 붙였고
시스템 전체의 관측 가능성을 크게 높였다.

## 코딩 에이전트가 있는데도 이 패턴이 중요한가

저자의 답은 그렇다는 것이다.

많은 팀이 AI 에이전트로 대규모 코드 마이그레이션을 자동화하는 데 들떠 있고
저자도 그것이 훌륭한 용도라고 본다.
코드 마이그레이션은 대체로 기계적이고, 검증하기 쉽고, 필요한 맥락이 제한적이기 때문이다.

그럼에도 스크립트를 아는 것이 중요한 이유가 셋 제시된다.

| 이유          | 설명                                                                       |
| ------------- | -------------------------------------------------------------------------- |
| 프롬프트의 질 | 이런 스크립트를 언제 쉽게 쓸 수 있는지 알면 적절한 지시를 줄 수 있다       |
| 오류 확률     | 에이전트가 써야 할 코드 줄이 많아질수록 실수할 기회도 늘어난다             |
| 검토 비용     | 수천 줄의 diff보다 짧은 스크립트의 논리와 테스트를 검토하는 편이 훨씬 쉽다 |

두 번째가 특히 구체적이다.
에이전트에게 손으로 하라고 시키면 실제로 손으로 한다.
파일 하나하나를 직접 고치는 방식은 변경 지점 수만큼 실수 기회를 만들지만,
스크립트를 쓰게 하면 논리는 한 곳에 모인다.

복잡도가 올라가면 코드를 더 잘 이해하는 도구로 옮겨 가라는 조언도 붙는다.
TypeScript 프로젝트에서는 `ts-morph`를 여러 번 써서 좋았다고 밝힌다.

결론은 이 기법이 더 값어치 있어졌다는 것이다.
AST를 이해하든 아니든 이런 스크립트를 만드는 일이 AI 에이전트로 더 쉬워졌고,
코드를 고치는 비용이 예전보다 싸졌으므로
한때 바꾸기에 너무 비싸 보였던 코드베이스의 패턴을 개선하고 싶을 때 이 방법을 떠올릴 만하다.

## 이 방식이 맞는 경우와 아닌 경우

| 상황                                 | 적합한 방법                |
| ------------------------------------ | -------------------------- |
| 변경이 줄 단위이고 패턴이 일정하다   | 문자열 치환 스크립트       |
| 범위를 알려면 주변 맥락이 필요하다   | 상태를 기억하는 한 줄 파서 |
| 타입이나 임포트 관계를 따라가야 한다 | `ts-morph` 같은 AST 도구   |
| 변경마다 판단이 필요하다             | 에이전트 또는 사람         |
| 일부만 자동화해도 이득이다           | 무엇이든, 나머지는 손으로  |

마지막 줄이 이 글의 실질적 주장이다.
자동화율 100퍼센트를 목표로 삼으면 도구 선택이 무거워지고 착수 자체가 미뤄지는데,
90퍼센트를 목표로 삼으면 한 시간짜리 스크립트로 끝난다.

## 함정

- 파일을 읽고 같은 경로에 쓰는 구조라 스크립트가 중간에 죽으면 파일이 잘린다. 저자의 백업 경고가 이것을 가리킨다.
- `if "function" in line` 같은 검사는 주석이나 문자열 안의 단어에도 걸린다. 실제 코드보다 주석이 먼저 잡히면 엉뚱한 이름이 붙는다.
- 여러 번 돌리면 이미 변환된 자리가 또 변환될 수 있다. 예시에서 `QueryBuilder()`만 찾는 것은 우연히 멱등성을 확보한 경우이며, 의도적으로 그렇게 설계해야 한다.
- 생성된 이름이 중복될 수 있다. 파일명과 함수명을 조합하는 방식은 같은 파일 안의 익명 함수 여럿에서 충돌한다.
- 한 번에 전부 돌리면 검토가 불가능하다. 디렉터리 단위로 쪼개 커밋을 나누면 diff가 읽을 만해진다.

## 비평

### 취약한 파서를 옹호하면서 그 실패를 어떻게 발견하는지는 한 줄뿐이다

이 글의 미덕은 완벽하지 않아도 된다는 허가에 있다.
그런데 완벽하지 않은 도구를 쓸 때 정말로 필요한 것은 실패를 탐지하는 방법이다.

글은 눈에 띄는 기본 문자열이라는 훌륭한 장치를 보여 주면서도 그것을 설명하지 않는다.
코드 블록 안에 그냥 놓여 있을 뿐이고,
이 값이 왜 중요한지, 스크립트를 돌린 뒤 무엇을 검색해야 하는지가 본문에 없다.
백업하라는 경고도 실패를 되돌리는 방법이지 발견하는 방법은 아니다.

실무에서 이 부분을 채우는 방법은 어렵지 않다.
변환한 줄 수와 건너뛴 줄 수를 출력하고,
변환하지 못했지만 대상으로 보이는 줄을 따로 기록하고,
변환 전후로 테스트나 타입 검사를 돌리는 것이다.
9할만 자동화해도 된다는 주장이 성립하려면
나머지 1할이 어디인지 알 수 있어야 하는데, 글은 그 연결을 하지 않는다.

### 에이전트 논의가 스크립트 대 에이전트 구도로 좁아져 있다

저자는 에이전트에게 손으로 시키지 말고 스크립트를 쓰게 하라고 말하며
검토 비용을 근거로 든다.
타당하지만 실제로 쓰이는 제3의 방식이 빠져 있다.
에이전트가 스크립트를 쓰고, 돌리고, 결과를 보고, 스크립트를 고치는 반복이다.

이 방식이 중요한 이유는 이 글이 제시한 9할 기준과 잘 맞기 때문이다.
첫 스크립트가 900개 파일을 고치고 100개를 놓치면,
놓친 100개의 패턴을 모아 스크립트에 조건을 더하는 작업은 정확히 에이전트가 잘하는 종류다.
사람이 직접 하면 지루해서 중간에 손으로 고치기 시작하는 구간이기도 하다.

검토 비용에 대한 주장도 한 겹 더 들어갈 여지가 있다.
스크립트의 논리를 검토하는 것이 diff 수천 줄을 검토하는 것보다 쉽다는 것은 맞지만,
스크립트가 옳다고 해서 결과가 옳은 것은 아니다.
결국 무작위 표본을 뽑아 결과를 확인해야 하며,
그 표본 검토와 스크립트 검토를 합친 비용이 실제 비용이다.

### 이름 생성 규칙의 품질 문제를 다루지 않는다

2,113개의 쓸 만한 이름이라는 성과는 인상적이지만,
쓸 만하다는 판정의 근거가 나오지 않는다.
생성 규칙은 파일명과 함수명을 이어 붙이는 것이고, 이것은 기계적으로는 잘 동작한다.

문제는 이 이름들이 나중에 읽히는 자리다.
저자의 다른 글이 설명하듯 이 이름은 슬로우 쿼리 로그에 나타나
어느 코드가 이 쿼리를 돌렸는지 되짚는 데 쓰인다.
그렇다면 함수 이름이 나쁜 코드에서는 쿼리 이름도 나쁘게 생성된다.
`utils.handler`나 `index.default` 같은 이름이 2천 개 중 몇 개나 있었는지,
그런 경우를 어떻게 처리했는지가 이 마이그레이션의 실제 품질을 정한다.

한 번 쓰고 버리는 스크립트라는 성격상 이름은 한 번 생성되면 그대로 코드에 남는다.
그러므로 이 마이그레이션의 진짜 산출물은 스크립트가 아니라 이름 2,113개이고,
그 품질에 대한 검토가 스크립트 검토보다 중요했을 것이다.

## 체크리스트

- 변환 대상 패턴이 코드베이스에 실제로 몇 가지 형태로 존재하는지 세어 봤는가?
- 스크립트가 처리하지 못한 자리를 결과물에서 검색으로 찾을 수 있는가?
- 변환한 줄 수와 건너뛴 줄 수를 출력하는가?
- 두 번 돌려도 결과가 같은가?
- 변환 전후로 테스트나 타입 검사를 돌렸는가?
- 커밋을 검토 가능한 크기로 쪼갤 계획이 있는가?
- 자동화하지 않기로 한 나머지 부분의 목록이 남아 있는가?
- 생성되는 값에 품질 문제가 있다면, 그것을 스크립트가 아니라 사람이 검토했는가?

## 기억할 원칙

### 일회용 코드의 품질 기준은 재사용 코드와 다르다

이 글이 반복해서 하는 말은 코드가 허술해도 된다는 것이 아니라
이 코드의 수명이 한 시간이라는 것이다.
수명이 짧으면 다뤄야 할 경우의 수가 코드베이스에 실제로 있는 것으로 한정되고,
예외 처리도 오류 메시지도 필요 없어진다.

같은 기준이 다른 곳에도 적용된다.
데이터 조사용 질의, 일회성 이관 도구, 실험용 프로토타입이 그렇다.
이런 코드를 재사용 코드의 기준으로 쓰기 시작하면 착수 비용이 올라가
결국 스크립트 대신 손으로 하게 되며, 그쪽이 훨씬 비싸다.
중요한 것은 두 종류의 코드를 구별하고 섞이지 않게 두는 것이다.

### 자동화율의 목표를 100퍼센트로 두지 않는다

열 개 중 아홉 개만 자동화해도 값어치가 있다는 기준이 이 글의 실질적 기여다.
완전 자동화를 목표로 삼는 순간 파서의 정확성, 예외 처리, 도구 선택이 전부 무거워지고,
그 무게 때문에 착수가 미뤄지다가 마이그레이션 자체가 취소된다.

이 기준이 성립하려면 조건이 하나 있다.
자동화되지 않은 나머지를 식별할 수 있어야 한다는 것이다.
식별할 수 있으면 9할 자동화는 1할의 수작업으로 끝나지만,
식별할 수 없으면 10할을 다시 검토해야 하므로 이득이 사라진다.
그러므로 부분 자동화를 택할 때 먼저 설계해야 할 것은 변환 로직이 아니라 실패 표시 방법이다.
