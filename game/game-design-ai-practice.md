혼자 만드는 개발자는 23부의 개인 게임 개발과 각 챕터의 1인 축소판을 따라갑니다.

도구를 만들게 하는 방법도 가장 쉬운 활용법으로 소개합니다.

## 책의 약속과 표기 방식

서문은 이 책이 세 번 쓰였다고 설명합니다.
처음은 사내 매뉴얼이었고, 두 번째 원고는 효과를 보이는 숫자가 많았으나 대부분
가공 수치였다고 합니다.
그래서 세 번째로 다시 쓰며 세 가지 원칙을 세웠습니다.

- 모든 챕터가 실제 세션을 끝까지 보여 줍니다. 입력 프롬프트 전문, AI의 날것 출력, 무엇을 거부했고 어떻게 다시 시켰는지를 담습니다.
- 숫자는 셋 중 하나입니다. 공개 표준(모델 토큰 단가, 접근성 가이드라인), 저자 시스템 코드에 실제로 입력된 상수, 또는 저자 추정이라고 명시한 값입니다.
- 6개월 운영한 시스템을 그대로 인용합니다. 서문은 304개의 결정 카드(atom), 48개의 도구(skill), 매 입력마다 관련 기억을 끌어오는 hook, 한 사람이 네 명분의 협업 맥락을 운영하는 메모리 구조를 듭니다.

'재구성'이라는 표기는 지어냈다는 뜻이 아니라 실제 세션을 편집했다는 뜻이라고
서문이 따로 약속합니다.
입력 프롬프트 전문, 출력의 구조와 실패, 코드·상수·검증값은 보존하고,
회사·프로젝트·팀원 고유명은 익명화하며, 길이와 조판은 지면에 맞춘다고 합니다.
실패한 출력을 성공으로 고쳐 쓴 곳은 없다고 밝힙니다.

## 읽은 장에서 뽑은 방법

### 환각은 0이 안 되므로 검증 게이트를 건다

22.2는 환각을 없애는 프롬프트는 없다고 전제하고,
LLM이 지어낼 수 있는 인용·수치·ID는 LLM이 아닌 곳에서 검증하라고 합니다.
검증의 출처는 코드, 원본 문서의 grep, 사람의 눈 셋 중 하나입니다.

| 작업               | 환각 위험 | 책이 제시한 게이트                 |
| ------------------ | --------- | ---------------------------------- |
| 수치 계산          | 매우 높음 | 계산은 코드로, LLM에는 시키지 않음 |
| 인용(회의·결정 ID) | 높음      | 원본 grep 대조                     |
| 분류               | 보통      | 결정론 비교                        |
| 요약·추론          | 보통      | 자기검증과 사람 게이트             |
| 창작               | 낮음      | 톤 검수                            |

장의 워크드 트랜스크립트는 회의록 한 건을 결정 카드로 요약시킵니다.
원본에는 '빙결 지속시간은 논의했으나 수치 미정'이라고만 적혀 있는데,
1차 출력은 '3초로 결정, 확정, 표준 기준 적용'이라고 썼습니다.
저자는 카드를 원본과 항목별로 대조해 일치, 생성,
누락으로 표시하게 하는 자기검증을 재요청하고,
AI가 3초는 자기가 추가한 값이라고 밝히며 카드를 미정으로 되돌립니다.
같은 대조에서 사람이 놓친 누락(다음 주 재논의 조건)도 드러났다고 합니다.
책은 자기검증이 만능이 아니라고 단서를 달고,
첫 단계일 뿐이며 결정론 게이트와 사람 게이트가 뒤따른다고 설명합니다.
게이트는 사람이 닿는 곳을 맨 앞(원본 투입)과 맨 뒤(자동 게이트가 못 잡는 판단)로
한정합니다.

### 비용은 매 호출에서 입력 토큰을 깎는 코드로 통제한다

22.3은 비용이 무서운 이유가 금액이 아니라 보이지 않는다는 데 있다고 말하고,
실무에서 청구서를 지배하는 항목은 입력 토큰이라고 봅니다.
공개 단가는 이 책 집필 시점 세대의 1M 토큰당 요금으로,
책은 적용 전에 현재 가격표를 확인하라고 따로 적습니다.
절감의 두 축은 모델 적정화와 캐싱입니다.

가장 조용히 쌓이는 비용은 매 호출에 자동으로 붙는 컨텍스트라고 합니다.
저자는 프롬프트를 칠 때마다 관련 메모리를 끼워 넣는 UserPromptSubmit
hook(`inject_memory.py`)의 비용 가드를 실제 상수로 보여 줍니다.

- 가드 A: 한 호출에 주입할 atom을 최대 3개로 제한(`max_matches = 3`)
- 가드 B: atom 본문을 6000자에서 절단(`max_atom_body = 6000`)
- 가드 C: score 내림차순으로 슬롯을 채워 가치 낮은 atom이 슬롯을 차지하지 못하게 함

이 상수를 정하는 과정도 트랜스크립트로 실려 있습니다.
AI가 제안한 6000자를 저자가 가장 긴 atom에서 직접 확인했더니 절단 지점이 표 행을
끊었습니다.
줄 경계 보정을 물었고, AI는 절단의 목적이 토큰 상한이지 표 무결성이 아니므로
보정하지 말라고 권해 단순 절단을 유지했습니다.
이 세션에서 AI가 6000이 최적값인지 모른다고 스스로 신고한 줄(확신도 낮음)도 책은
가장 가치 있는 부분으로 꼽습니다.

### 회의록에서 결정을 뽑는 파이프라인

17.2는 회의록 한 건이 양식 lint, 결정 네 필드 파서,
주인 없는 결정의 `[MISSING]` 표시, 후보 파일 생성,
일주일 뒤 검수와 승격을 거쳐 자동 주입되는 자산이 되는 흐름을 다룹니다.
사람의 손은 회의록을 쓰는 입구와 주 1회 검수하는 출구 둘뿐입니다.
책의 흔한 실패 처방은 lint를 커밋 훅으로 강제하고,
결정 슬롯에는 결정만 한 문장으로 쓰며, owner 빈칸은 반려하고,
pending 리뷰는 주간 회고에 고정 슬롯으로 두고, 폐기도 atom으로 남기는 것입니다.

측정 절은 표준 양식만 쓸 때와 파이프라인을 돌릴 때를 비교하지만,
책 스스로 정밀 계측이 아니라 체감한 방향과 대략의 비율이며 저자 추정(미검증)이
섞였다고 밝힙니다.

| 항목                           | 양식만(수동)   | 파이프라인   |
| ------------------------------ | -------------- | ------------ |
| 회의록에서 결정 추출 시간      | 회의당 20~30분 | 1분 미만     |
| 결정의 atom 승격 비율          | 5~10%          | 60~80%       |
| 재회의(“전에 결정 안 했었나?”) | 분기당 5~10건  | 분기당 0~2건 |

### 회고에서 나온 발화가 다음 세션부터 자동으로 작동해야 루프가 닫힌다

21.3은 같은 회고 항목이 6개월 뒤에도 토씨까지 같은 상황을 '루프가 닫히지
않았다'고 진단합니다.
도구 하나를 만들지 말지는 ROI로 정합니다.
산식은 '절약 시간 × 발동 빈도 × 운영 기간' 나누기 '제작 시간 + 유지보수
부담'이고, 결과가 10 이상이면 즉시 제작, 3~10이면 일주일 안에 제작,
1~3이면 한 달 보류, 1 미만이면 그 형태로는 폐기합니다.
통과선은 주 1회 이상 발동, 4주 이상 운영입니다.
만든 도구는 등록과 발동 검증을 거치고, 그 작동이 다시 회고로 측정되어 돌아와야
한다는 것이 장의 요지입니다.

### 도구 중립의 골격

부록 K는 책의 방식을 다섯 골격으로 요약하고 어느 것도 특정 제품 이름이 아니라고
주장합니다.

| 골격                      | 뜻                                                            |
| ------------------------- | ------------------------------------------------------------- |
| 표준, 템플릿, 검증 게이트 | 규칙을 틀로 굳히고 결과가 규칙을 지켰는지 자동으로 거름       |
| atom = 1결정 1파일        | 결정을 작은 파일 하나에 적어 필요할 때 꺼내고 그 한 칸만 고침 |
| JIT 주입                  | 지금 대화에 필요한 결정만 골라 모델에 넣음                    |
| 회고 루프                 | 일·주·월 단위 회고에서 반복 패턴을 다음 규칙으로 끌어올림     |
| 도구 차용 경계            | 골격만 가져오고 도메인 데이터는 두고 옴                       |

다른 도구로 옮길 때 잃는 것은 자동 실행의 매끄러움, 통합된 한 화면,
즉시 쓰는 스킬·명령 같은 편의이고 지키는 것은 위 골격이라고 적습니다.
부록 L은 도입 비용을 구독료 곱하기 인원으로만 보지 말고 도입 공수, 운영비,
보안·계정 관리로 나눠 팀 규모별 빈칸 워크시트를 채우라고 합니다.

## 비평

### 가장 강한 주장과 그 근거의 범위

이 책의 가장 강한 주장은 AI 활용의 가치가 효과를 과장하는 숫자가 아니라 실제
세션, 코드, 거부의 기록으로만 전달된다는 것입니다.
읽은 장에서 이 주장은 근거가 있습니다. 프롬프트 전문, 실패한 출력,
사람이 거부하고 재요청하는 단계가 실제로 실려 있습니다.
다만 근거는 읽은 아홉 개 장 안에서만 확인한 것이고,
100개 챕터 전체가 같은 수준인지는 이 문서가 확인하지 못했습니다.

### 숫자의 세 가지 지위가 섞여 있다

서문의 약속은 숫자가 공개 표준, 코드에 입력된 상수,
명시된 추정 중 하나라는 것입니다.
17.2.6의 표(수동 20~30분 대 1분 미만, 승격 5~10% 대 60~80%)는 세 번째,
즉 저자 추정(미검증)에 속하며 장이 스스로 그렇게 밝힙니다.
그래서 부제의 '지어낸 숫자는 한 개도 없다'는 숫자를 지어내지 않았다는 뜻이지
모든 숫자가 측정값이라는 뜻이 아닙니다.
독자는 표를 읽을 때 각 숫자가 셋 중 어느 지위인지 본문의 단서를 확인해야 합니다.

### 한 사람의 환경에서 나온 사례다

비용 가드의 상수(3개, 6000자)와 atom 17개짜리 라이브러리는 저자 개인 PC의 운영
코드입니다.

## 기억할 원칙

- AI가 지어낼 수 있는 것(인용, 수치, ID)은 AI가 아닌 곳(코드, 원본 grep, 사람)에서 검증합니다.
- 자기검증은 게이트의 첫 단계일 뿐이고, 결정론 게이트와 사람 게이트가 뒤따라야 합니다.
- 비용은 다짐이 아니라 호출마다 입력 토큰을 깎는 코드(개수 상한, 길이 상한, 우선순위)로 통제합니다.
- 사람의 손은 입구(원본을 넣는 곳)와 출구(자동 게이트가 못 잡는 판단)에 둡니다.
- 도구를 만들기 전에 ROI를 계산하고, 만든 뒤에는 발동 여부를 회고로 측정합니다.
- 책의 숫자는 지위(공개 표준, 상수, 추정)를 확인하고 읽습니다.
