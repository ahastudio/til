# SpriteCook의 스프라이트 스태킹 가이드

원문: [Sprite stacking for fake 3D pixel art cars and props](https://www.spritecook.ai/blog/sprite-stacking-pixel-art)

## 요약

SpriteCook가 2026년 11월 14일에 낸 기술 글이다.
SpriteCook는 코딩 에이전트가 2D 게임 에셋을 만들게 하는 서비스이고,
글은 이 서비스의 블로그에 올라왔다.
쓰는 사람의 목표는 위에서 내려다본 자동차 스프라이트 하나를
어느 방향으로든 돌려 보이게 하는 것이다.

문제는 이렇다.
위에서 본 자동차 스프라이트는 한 방향에서만 제대로 보인다.
방향마다 그림을 그리면 16방향으로 늘려도 레이싱 게임에서는 끊겨 보인다고
글은 말한다.
스프라이트 스태킹(sprite stacking)은 물체를 높이 1픽셀마다 한 장씩
평평한 층으로 잘라 두고, 그 층을 1픽셀씩 위로 올려 겹쳐 그려서 해결한다.
모든 층을 같은 각도로 돌리면 더미 전체가 3D 모델처럼 돌고, 화소는
선명하게 남는다.

글은 세 부분으로 이어진다.
층을 만드는 법(네 방향 그림에서 자르기), 그 층을 그리는 코드(Python과 Godot),
그리고 함정이다.
예로 든 자동차는 가로 24, 세로 43 화소짜리 층 15장이고 10배로 확대해 그린다.

## 동작 원리

각 층은 물체의 한 높이를 위에서 본 그림이다.
바퀴 바닥, 차체, 창, 지붕 순서로 올라간다.
바닥 층을 먼저 그리고 다음 층부터 1픽셀씩 높게 그리면
층을 벌려 놓았을 때는 겹이 보이지만 1픽셀 간격에서는 하나의 단단한 차로 읽힌다.

차를 돌릴 때는 모든 층을 같은 각도로 각자의 중심에서 돌린 뒤 위로 올린다.
다른 것은 바뀌지 않으므로 시트 하나가 모든 각도를 맡는다.
카메라가 비스듬히 내려다보는 경우에는
올리기 전에 각 층의 높이를 75%로 눌러 준다.
측면이 더 보이고 지붕이 덜 보이게 된다. 글의 영상은 0.75를 쓴다.

아래 코드도 이 순서를 따른다.
돌리기는 층의 중심 기준이고, 누르기는 올리기 전이며, 뒤의 층이 앞의 층을 덮는다.

## 네 방향 그림에서 층 만들기

층 15장을 손으로 그리는 것이 가장 느린 부분이다.
보통은 MagicaVoxel 같은 복셀 편집기로 물체를 만들어 층을 내보낸다.
단순하고 각진 물체라면 더 빠른 길이 있다고 글은 소개한다.
위, 옆, 앞, 뒤 네 방향의 평면 그림을 쓰는 방법이다.

원리는 세 그림이 동의하는 곳에만 화소가 있다는 것이다.
위 그림은 위에서 볼 때 차가 있는 곳을, 옆 그림은 길이 방향의 높이를,
앞 그림과 뒤 그림은 높이마다의 폭을 알려 준다.
그래서 옆 그림의 한 행이 층 한 장이 된다.
그 층은 위 그림을
그 높이에서 다른 그림들이 말하는 길이와 폭으로 잘라 낸 것이다.

색은 각 화소를 마주 보는 그림에서 가져온다.
모든 열의 윗면은 위 그림의 색을 쓰고,
각 층의 2픽셀 가장자리는 그 쪽을 향한 옆, 앞, 뒤 그림의 같은 행 색을 쓴다.
코드 없이 해 보려면 글이 안내하는 무료 스프라이트 스택 생성기(sprite stack
generator)에
네 그림을 넣으면 된다.
브라우저에서 층을 자르고 돌려 보게 하며,
층 또는 8, 16, 32방향 시트를 내려받을 수 있다고 한다.

### 네 방향 그림을 생성하는 프롬프트

글의 자동차는 Nano Banana Pro의 픽셀아트 모드에서 크기 32 x 32로
한 번 생성한 것이고, 16 크레딧이 든다고 한다.
프롬프트는 슬라이싱 코드가 기대하는 배치를 요구한다.
핵심은 2 x 2 격자의 모델 시트이다.

| 위치        | 그림           | 방향             |
| ----------- | -------------- | ---------------- |
| 왼쪽 위     | 위에서 본 그림 | 차가 아래를 향함 |
| 오른쪽 위   | 옆 그림        | 차가 왼쪽을 향함 |
| 왼쪽 아래   | 앞 그림        | -                |
| 오른쪽 아래 | 뒤 그림        | -                |

프롬프트는 이 밖에 원근과 기울기 없는 직교 투영, 모든 그림에서 같은 축척,
1픽셀 어두운 외곽선, 평평한 채색, 그림자와 글자와 격자선 없음을 요구한다.
차를 트럭, 탱크, 상자로 바꾸어도 배치 문장은 그대로 둔다고 글은 안내한다.

시트를 자르기 전에 눈으로 확인해야 한다.
글의 스크립트는 가장 키가 큰 그림을 위 그림으로,
가장 넓은 그림을 옆 그림으로 취급하고,
위 그림의 창이 옆 그림의 높은 부분 위에 오도록 돌린다.
옆 그림은 왼쪽을 향해야 하며, 오른쪽을 향하면 `--side-nose right`를 준다.
글의 첫 시도는 평평한 색과 외곽선 없음을 요구했다가
가장자리가 부드러운 회색이 되었고, 층이 돌면서 번졌다.
굵은 1픽셀 외곽선과 평평한 채색이 선명하게 남는다.

### 슬라이싱 코드가 하는 일

글이 싣는 Python 스크립트(`views_to_slices.py`, Pillow와 numpy 필요)는
시트에서 그림 네 장을 찾아 외곽선을 지우고 하나의 공유 팔레트(기본 24색)에 올린
뒤 층을 자른다.
출력은 한 줄짜리 층 시트이며 바닥 층이 왼쪽에 오고, 각 층은 위 그림의 크기이다.
인자 `--shade 0.25`는 옆면을 윗면보다 어둡게 칠하고, `--top-nose`로 위 그림의
방향을 직접 줄 수 있다.
같은 아이디어를 구현한 다른 스킬은
[sprite-stacking](../agent-skill/sprite-stacking.md)에 정리되어 있다.

## 층을 그리는 코드

글의 Godot 예제는 노드 하나에서 층마다 변환을 걸어 그린다.
Godot 4.6에서 시험했다고 하고, 프로젝트의 기본 텍스처 필터는 Nearest로 둔다.
차가 시트에서 아래를 향하므로 속도 벡터로 움직이는 차는
`turn = velocity.angle() - PI / 2`로 돌린다.
다른 엔진은 글이 시험하지 않았다.
Unity는 층마다 자식 `SpriteRenderer`를 두고 화면에서 1픽셀씩 올리며 정렬 순서를
아래에서 위로 유지하라고 하고, Phaser, Pygame, 자체 엔진은 최근접 필터로
층 이미지를 반복문에서 그리라고 안내한다.

글의 코드를 옮긴 것이 아니라 글이 설명한 순서를 따라 쓴 것이다.

```python
import math
import numpy as np
from PIL import Image

def render_stack(slices, turn=0.0, squash=0.75, spacing=1.0, scale=1):
    """RGBA 층(바닥 층이 먼저)을 겹쳐 한 장으로 그린다."""
    h, w = slices[0].shape[:2]
    radius = int(math.ceil(math.hypot(h, w) / 2)) + 1
    lift = int(round((len(slices) - 1) * spacing))
    out_w = 2 * radius
    out_h = int(math.ceil(2 * radius * squash)) + lift + 2
    canvas = np.zeros((out_h, out_w, 4), np.uint8)
    ys, xs = np.mgrid[0:out_h, 0:out_w]
    cos_t, sin_t = math.cos(turn), math.sin(turn)
    for z, piece in enumerate(slices):
        cy = out_h - 1 - radius * squash - round(z * spacing)
        dx = xs + 0.5 - out_w / 2
        dy = (ys + 0.5 - cy) / squash
        # 돌리고 누른 변환의 역변환으로 각 화면 화소가 층의 어느 화소인지 찾는다
        u = dx * cos_t + dy * sin_t + w / 2
        v = -dx * sin_t + dy * cos_t + h / 2
        ui, vi = np.floor(u).astype(int), np.floor(v).astype(int)
        inside = (ui >= 0) & (ui < w) & (vi >= 0) & (vi < h)
        px = np.zeros((out_h, out_w, 4), np.uint8)
        px[inside] = piece[vi[inside], ui[inside]]
        drawn = px[..., 3] > 0
        canvas[drawn] = px[drawn]          # 뒤의 층이 앞의 층을 덮는다
    if scale > 1:
        canvas = np.repeat(np.repeat(canvas, scale, 0), scale, 1)
    return canvas
```

층 6장짜리 12 x 8 상자로 시험하면 결과가 글의 측정 방식과 같은 방향으로 나온다.
squash 1, turn 0에서는 8 x 16 화소를 덮고, 90도 돌리면 12 x 12가 된다.
squash 0.75에서는 높이가 14로 줄고, spacing 2에서는 21로 늘어난다.
글이 자기 자동차로 보고하는 값(24 x 52, 41, 43, 50)과 같은 경향이다.
숫자가 다른 것은 층의 크기와 개수가 다르기 때문이다.

## 값 정하기

글과 글 끝의 에이전트용 지침에 나오는 수치는 다음과 같다.

| 값      | 기본        | 설명                                                                                |
| ------- | ----------- | ----------------------------------------------------------------------------------- |
| 층 간격 | 1 화면 픽셀 | 층 z의 높이는 z에 간격을 곱해 반올림한 값                                           |
| squash  | 0.75        | 1은 바로 위에서 보기, 낮을수록 카메라가 낮음. 0.6 아래에서는 지붕이 얇아진다고 한다 |
| 확대    | 10배        | 글의 영상은 화소 하나를 화면 10픽셀로 그린다                                        |
| 층 수   | 15          | 기준 자동차. 층은 24 x 43 화소                                                      |

차가 후진할 때는 속도가 아니라 진행 방향(heading)으로 돌려야 뒤집혀
보이지 않는다고
글 끝의 지침이 덧붙인다.

## 함정

### 돌릴 때 떨린다

최근접 보간 회전은 화소를 한 칸씩 건너뛰며 옮기는데 작은 스프라이트에서는 건너뛸
때마다 보인다.
크게 그리는 것이 처방이며 글의 영상은 10배로 그린다.
RotSprite 방식(각 층을 Scale2x로 8배 키워 돌린 뒤 8 x 8 블록의 가운데
화소를 취함)은
긴 가장자리를 안정시키지만 이 작은 차는 둥글게 깎아서 영상은 단순 최근접을
쓴다고 한다.

### 부드러운 그림은 번진다

부드러운 가장자리와 중간 색조는 층이 돌며 겹치면 흐려지고 가는 줄무늬는 끊긴다.
굵은 외곽선과 평평한 채색, 폭이 몇 화소인 줄무늬를 쓴다.

### 구멍은 메워진다

평면 그림에서 자른 층은 구멍이나 돌출부를 만들 수 없다.
트럭 짐칸, 아치, 트렁크 위의 스포일러는 속이 찬 덩어리로 나온다.
해당 층은 손으로 고친다.

### 정렬 단위는 더미 전체이다

다른 물체와 가릴 때는 더미 전체를 땅에 닿는 점 기준으로 정렬한다.
다른 물체의 층끼리 섞어 정렬하면 나무의 층이 차 안으로 들어간다.

### 외곽선은 완성된 더미에 한 번

층마다 외곽선을 두르면 차 한가운데로 선이 지나간다.
완성한 더미에 한 번만 외곽선을 둘러야 하며,
SubViewport에 그려 외곽선을 입히거나
필요한 각도를 외곽선 포함 시트로 미리 구워 둔다.

### 수백 개의 더미

더미마다 층 수만큼 그리기 호출이 든다.
몇 대의 차는 괜찮지만 돌지 않는 나무 숲은 불러올 때 한 번 그려 단순
스프라이트로 쓴다.

## 비평

### 시험이 글 안에서 닫혀 있다

글이 보고하는 Godot 시험은 같은 그림을 numpy로 그린 것과 화소 단위로 맞는지
보는 것이다.
수치도 한 대의 자동차 하나에서 측정한 값이고,
Python 도구의 층 15장이 영상의 층과 화소까지 같다는 것은
같은 글의 두 코드가 서로 맞는다는 뜻이다.
다른 모델이나 다른 엔진에서도 같은 결과가 나오는지는 글이 말하지 않는다.

### 방법의 범위가 좁다

글도 밝히듯 네 방향 그림에서 자르는 방법은 단순하고 각진 물체에 맞는다.
네 그림이 동의하는 곳에만 화소를 두는 구조에서는 오목한 모양을 표현할 수 없다.
구멍이 메워지는 함정이 이 한계의 결과로 보인다.
이는 이 문서의 해석이다.
사람이 어디를 고쳐야 하는지 미리 알려 주는 장치가 있는지는 글에 없다.

### 서비스와 얽힌 설명

글은 같은 서비스의 모델과 크레딧, 무료 생성기와 에이전트용 프롬프트로 이어진다.
슬라이싱 코드 자체는 어떤 도구의 네 방향 그림에도 쓸 수 있지만,
프롬프트의 구체적 비용(16 크레딧)과 설정은 이 서비스에 해당하는 정보이다.
다른 서비스에서 같은 배치를 얻는 데 필요한 노력은 글이 다루지 않는다.

### 주장의 근거

16방향으로 늘려도 레이싱 게임에서는 끊겨 보인다는 첫머리의 문장은
이 글에서 따로 보여 주지 않는다.

## 기억할 원칙

### 층의 수는 높이이다

층 하나는 높이 1화소이므로 키가 큰 물체는 층이 많아지고 그만큼 그리기
비용도 는다.
더미는 몇 개의 움직이는 물체에 쓰고 움직이지 않는 물체는 한 번 구워 둔다.

### 선명함은 그림에서 시작한다

부드러운 가장자리는 코드로 고칠 수 없다.
네 방향 그림은 굵은 외곽선과 평평한 채색으로 요구하고, 외곽선은 시트가 아니라
완성된 더미에 한 번 두른다.
