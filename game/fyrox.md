## 소개

Fyrox는 Rust로 작성한 2D·3D 범용 게임 엔진이다.
홈페이지는 Fyrox Game Engine이라는 제목 아래
Feature-rich Game Engine Written in Rust라는 부제를 걸고,
최신 빌드 내려받기와 데모 프로젝트 실행 버튼 두 개를 앞에 둔다.
사이트 설명문은 Fyrox를 기능이 풍부하고(feature-rich),
프로덕션에 쓸 수 있으며(production-ready),
오픈소스인 게임 엔진이라고 소개한다.
릴리스 글마다 반복되는 한 줄 요약은
네이티브 에디터로 2D와 3D 게임을 적은 노력으로 만들게 해 주는,
Rust로 된 Unity 같은 엔진이라는 것이다.

이 엔진의 이전 이름은 rg3d다.
저장소 README에도 Formerly known as rg3d라고 적혀 있고,
crates.io의 `rg3d` 크레이트는 0.24.0에서 멈췄고,
이후 버전은 `fyrox` 크레이트로 이어졌다.
GitHub 저장소는 2019년 3월 30일에 만들어졌고 라이선스는 MIT다.
책의 설계 철학 장에 따르면
개발은 2019년 초 Rust를 배우려는 취미 프로젝트로 시작했다.
처음에는 C로 작성한 엔진을 옮긴 것이었는데,
C에서 1년쯤 개발하다 메모리 손상과 누수를 고치는 데 지친 저자(@mrDIMAS)가
1년이 안 되어 Rust로 옮겼고, 이후 무작위 충돌이 사라졌다고 적는다.

2026년 3월 24일 블로그에 첫 안정판 1.0.0 발표 글이 올라왔다.
글은 7년 개발 끝에 나온 첫 안정판이라고 소개한다.
이 문서를 쓰는 2026년 10월 기준으로
crates.io의 최신 버전은 3월 28일에 나온 1.0.1이다.

## 주요 기능

### 홈페이지가 내세우는 12가지

홈페이지의 Features 블록은 열두 항목으로 엔진을 요약한다.

| 항목                      | 홈페이지 설명                                                                    |
| ------------------------- | -------------------------------------------------------------------------------- |
| Editor                    | 게임을 처음부터 끝까지 만드는 완전한 에디터                                      |
| Hot Reloading             | 네이티브 코드와 에셋의 핫 리로딩으로 빠른 프로토타이핑                           |
| First Class 2D/3D Support | 2D, 3D, 또는 둘을 섞은 게임                                                      |
| Flexible PBR Renderer     | 확장 가능한 PBR 렌더러                                                           |
| High Quality Audio System | 풍부한 사운드 환경을 만드는 오디오 시스템                                        |
| Powerful 2D/3D Physics    | 강체, 여러 콜라이더, 조인트, 레이 캐스팅                                         |
| Advanced User Interface   | 상상력이 한계인 UI 시스템                                                        |
| Powerful Animation System | 복잡한 애니메이션을 만드는 내장 애니메이션 시스템                                |
| Multiplatform             | PC(Windows, Linux, macOS), Web(WebAssembly), 모바일(Android, iOS)                |
| Plugins & Scripting       | 게임 전체를 Rust로 쓰면서 에디터 안에서 실행, 플러그인으로 엔진 확장             |
| Scene Graph               | 피벗, 카메라, 메시, 조명, 파티클, 스프라이트와 사용자 정의 노드를 담는 씬 그래프 |
| Documentation             | 엔진 사용법을 익히는 고품질 문서                                                 |

책의 소개 장에는 더 자세한 목록이 있다.
렌더링 기능으로는
지연 셰이딩, HDR, 톤 매핑, SSAO, 볼류메트릭 라이트, 라이트맵, 디칼이 있다.
씬 노드는 지형, 타일맵, 내비게이션 메시, 래그돌, 사운드 등을 포함한다.
사운드는 HRTF 기반 바이노럴 음향과 리버브를 지원한다.
애니메이션은 Unity의 Mecanim과 비슷한 애니메이션 블렌딩 상태 기계와
리타기팅, 블렌드 스페이스, 루트 모션을 지원한다.
AI 쪽에는 A* 경로 탐색, 내비메시, 행동 트리가 들어 있다.
물리는 rapier 물리 엔진 위에 만들었고,
UI는 32개가 넘는 위젯을 가진 메시지 전달 방식의 자체 라이브러리다.
에디터 FyroxEd도 이 자체 UI 라이브러리로 만들어졌다.

### ECS가 아닌 객체 지향 설계

Rust 게임 엔진 하면 흔히 ECS(Entity Component System)를 떠올리지만,
Fyrox는 ECS 기반이 아니다.
책의 FAQ는 이 엔진이 조합 기반 설계와 객체 지향 설계를 섞고 메시지 전달 등
작업에 맞는 방식을 고른다고 설명한다.
모든 것을 ECS로 하지 않는 이유는 실용성이며,
못을 두드리는 데 현미경을 쓰지 말라는 비유를 든다.
ECS를 쓰고 싶다면 쓸 수는 있지만,
엔티티 상태를 엔진 쪽 객체와 직접 동기화해야 한다.
GeekNews의 2020년 rg3d 소개 글에서도
shaha가 2022년에 가이드를 살펴보니 ECS가 아닌 OOP 구조라고 적었다.[^shaha]
같은 Rust 게임 엔진인 Bevy는 `game/bevy.md`에서 따로 다룬다.

### 설치와 프로젝트 구조

내려받기 페이지는 1.0.0 버전의 프로젝트 매니저를
Windows, macOS, Linux용 zip으로 제공한다.
설치 없이 압축을 풀어 실행하면 되고,
`cargo install fyrox-project-manager --version=1.0.0`으로 설치할 수도 있다.
Fyrox는 컴파일형 엔진이라 게임을 네이티브 코드로 빌드해야 하므로
Rust 툴체인이 필요하다.

프로젝트 매니저로 새 프로젝트를 만들면 여러 크레이트로 된 워크스페이스가 생긴다.

| 디렉터리                            | 역할                                             |
| ----------------------------------- | ------------------------------------------------ |
| `game`                              | 게임 코드                                        |
| `data`                              | 모든 에셋                                        |
| `editor`                            | 이 프로젝트 전용 에디터, 필요 없으면 지워도 된다 |
| `executor`                          | PC 진입점                                        |
| `executor-android`, `executor-wasm` | Android, WebAssembly 진입점                      |
| `export-cli`                        | 내보내기 기능의 명령줄 도구                      |
| `game-dylib`                        | 네이티브 코드 핫 리로딩을 위한 연결 고리         |

책은 모든 Fyrox 게임이 엔진과 에디터 양쪽의 플러그인이라고 설명한다.
그래서 게임을 에디터 안에서 실행하면서 게임 객체를 편집할 수 있고,
에디터 없이 게임만 실행할 수도 있다.
첫 빌드는 엔진 전체를 컴파일하므로 4코어 CPU에서 최대 10분,
8코어에서 5분쯤 걸리고, 그다음부터는 게임 코드만 몇 초 만에 다시 컴파일한다.

### 지원 플랫폼

책의 시스템 요구 사항 장은 엔진과 에디터의 지원 범위를 나눠 적는다.

| 플랫폼      | 엔진                           | 에디터 |
| ----------- | ------------------------------ | ------ |
| Windows     | 지원                           | 지원   |
| Linux       | 지원                           | 지원   |
| macOS       | 지원(Intel GPU 느림)           | 지원   |
| WebAssembly | 지원                           | 미지원 |
| Android     | 지원                           | 미지원 |
| iOS         | 컴파일은 될 것으로 보나 미검증 | 미지원 |

에디터가 PC에서만 도는 이유는 풍부한 파일 시스템 기능과 스레딩이 필요해서다.
그래픽 API는 PC에서 OpenGL 3.3, WebAssembly에서 OpenGL ES 3.0을 쓴다.
책은 가상 머신에서 엔진을 돌리지 말라고 경고하는데,
대부분의 가상 머신이 그래픽 API를 초보적으로만 지원하기 때문이다.

1.0의 날짜는 두 번 밀렸다.

RC2 글은 엔진의 일곱 번째 생일인 2026년 3월 19일로 다시 잡았으며,
실제 발표는 그로부터 닷새 뒤였다.

### RC1: 자산 체계와 렌더러를 다시 짰다

1.0의 실질적인 변화는 두 RC에 몰려 있다.
1.0 글도 0.36.2 이후 변경 사항은
사실상 두 RC의 릴리스 노트에 정리되어 있다고 안내한다.

RC1에서 PBR 파이프라인은
이미지 기반 조명(IBL), 환경 매핑, 반사 프로브까지 갖췄다.
전역 조명은 여전히 없고, 글은 이를 Fyrox 2.0쯤의 과제로 미룬다.
자산 시스템은 경로가 아니라 UUID로 자산을 참조하도록 바뀌었다.
덕분에 원본 파일 이름을 바꿔도 프로젝트 전체의 경로 참조를 고칠 필요가 없지만,
모든 자산 옆에 UUID를 담은 메타 파일이 붙어야 하고,
이 파일을 지우거나 따로 옮기면 안 된다.
네이티브 자산 형식은 협업 시 병합할 수 있도록 텍스트 기반으로 바뀌었고,
배포 빌드에서는 로딩 속도를 위해 바이너리로 변환된다.
RC1은 예전 자산과의 호환성을 유지하되 1.0에서는 이를 끊는다고 예고하고,
예전 형식의 자산을 일괄 변환하는 도구를 에디터에 넣었다.

씬과 UI 객체를 가리키는 핸들에도 타입이 붙었다.
이전에는 핸들에서 실제 노드 타입 정보가 사라져 직접 형변환을 해야 했는데,
이제 카메라 핸들은 카메라 핸들로 저장하고 꺼낼 수 있다.
UI는 화면 공간 정보를 매 프레임 모든 위젯에 대해 다시 계산하던 방식을
바뀐 위젯만 갱신하도록 고쳐 성능이 약 50% 올랐다.
글은 위젯이 15,000개가 넘는 에디터의 99.99%가 정적이라는 점을 그 근거로 든다.

### RC2: API를 굳혔다

RC2는 API 안정화에 집중했다.
플러그인과 스크립트의 거의 모든 메서드가 `GameResult`를 반환하게 되어
`?` 연산자로 오류를 넘길 수 있고,
엔진은 오류를 패닉 대신 로그에 남기고 실행을 이어 간다.
타입 있는 핸들 작업이 마무리되었고,
UI 메시지는 도우미 생성자 대신 열거형 변형을 직접 쓰도록 바뀌었다.
위젯이 시각적으로 바뀔 때만 다시 그리도록 해
에디터 성능이 거의 3배 빨라졌다는 내용과,
텍스트에 BBCode 마크업을 지원한다는 내용도 들어 있다.

### 1.0: 팀 개발을 위한 마무리

1.0 글의 첫 항목은 프로젝트 내보내기 CLI다.
프로젝트 매니저로 만든 모든 프로젝트에 `export-cli` 크레이트가 들어가,
에디터의 내보내기 기능을 명령줄에서 그대로 쓸 수 있다.
글은 이것이 여러 역할의 개발자가 함께 일하는 팀 개발에서 중요하다며,
작은 팀에서도 QA용 빌드를 CI/CD로 자동화할 수 있다고 설명한다.
대상 플랫폼은 `pc`, `android`, `wasm` 세 가지다.
이밖에 텍스트 말줄임, 입력 상자 위젯, 애니메이션 에디터의 키 일괄 기록,
비동기 작업 기반으로 다시 짠 씬 로딩이 들어갔다.
책도 1.0에 맞춰 스크린숏을 모두 새로 찍었고 거의 모든 장을 마쳤다고 한다.

글의 마지막 계획은 이례적으로 솔직하다.
1.0 출시가 매우 고되어 Fyrox 개발팀이 쉬어야 하므로,
버그 수정은 계속하지만 큰 신규 기능은 몇 달간 보류한다고 적었다.

### 후원

후원 페이지는 세 가지 경로를 제시한다.
Boosty를 가장 선호하고, 그다음이 Bitcoin 주소이며,
Patreon은 가장 덜 선호하는 방법이라고 적는다.
README는 Patreon으로 낸 돈은 언제 받을 수 있을지 모르는 상태로 묶여 있다며
저장소 이슈 #363으로 연결한다.

GitHub Sponsors는 원래 쓸 수 없었으며 PayPal이 러시아에서 막혀
그해 2월 이후로 한 푼도 받지 못했다고 밝혔다.

2026년 10월 현재 공개된 숫자는 작다.
Boosty의 Making Fyrox Game Engine 페이지는 구독자 33명이고,
등급은 50루블부터 10,000루블까지 열 단계다.
Patreon의 Creating Fyrox Game Engine 페이지 데이터에는
회원 26명 중 유료 회원 2명, 월 후원 합계 2,072센트(약 20달러)가 표시된다.
홈페이지 하단의 후원자 명단에는 48명의 이름이 있고,
README의 후원자 명단은 대부분 Patreon 프로필로 연결된다.
README는 JetBrains가 오픈소스 라이선스를 제공한다는 사실도 함께 적는다.

## 분석

### 엔진의 기능 목록은 저자가 만든 게임에서 나왔다

Fyrox의 기능 목록은 그래픽 기술 데모보다 게임 제작 도구 상자에 가깝다.
사운드, 애니메이션 상태 기계, 내비메시, 행동 트리, UI 위젯 32종,
저장과 불러오기가 렌더러와 같은 비중으로 나열된다.
이 구성은 저자가 엔진과 함께 게임을 만들어 온 방식에서 나온다.
2020년 rg3d가 HN에서 398점을 받았을 때,
저자는 이전에 다른 언어로 만든 엔진들이
메시와 조명 몇 개를 띄우는 데모만 있어서 실패했다고 돌아봤다.
어떤 기능이 필요한지는 그 기능이 필요해질 때까지 알 수 없고,
많은 엔진이 최고의 그래픽에 몰두하느라
사운드, 애니메이션, 물리, 자원 관리, 에디터를 소홀히 한다는 것이다.[^mrDIMAS-3]

예제 페이지가 보여 주는 게임 목록도 이 전략을 반영한다.
Dead Space 같은 공포 게임 Station Iapetus,
Quake 3 같은 아레나 슈터 rusty-shooter,
Fall Guys 같은 3D 플랫포머 Fish Folly가 앞에 있다.
책은 실험적인 코드 핫 리로딩을 Fish Folly와 Station Iapetus 두 대형 게임에서
시험했다고 적는다.
엔진의 품질 검증이 저자 자신의 게임에 크게 기대고 있다는 뜻이다.

### Rust로 Unity를 만든다는 말의 실제 의미

릴리스 글마다 반복되는 Unity 같지만 Rust로 된 엔진이라는 비유는
에디터 중심 작업 흐름을 가리킨다.
게임을 에디터 안에서 실행하고, 씬을 편집하고,
애니메이션 상태 기계를 그래프로 짠다.
HN에서 Animats는 Unreal Engine 힘의 상당 부분이 런타임이 아닌 에디터에 있다며,
에디터가 있기에 비프로그래머도 무언가 해낼 희망이 있다고 평가했다.[^Animats]
Unity와 Unreal의 잦은 충돌에 지쳤다는 damody는
Bevy나 Macroquad 같은 다른 Rust 엔진과 비교해
Fyrox가 프로그래밍 부담을 줄이려 많이 노력했다고 봤다.[^damody]

하지만 Unity와 다른 점이 하나 있다.
Unity는 엔진을 미리 빌드된 프로그램으로 배포하고
사용자는 C# 스크립트만 컴파일하지만,
Fyrox 프로젝트는 에디터 자체를 프로젝트 워크스페이스 안의 크레이트로 가진다.
게임 코드가 엔진과 에디터의 플러그인으로 정적 링크되므로,
첫 실행에서 엔진과 에디터를 소스부터 컴파일한다.
Unity의 경험을 Rust의 컴파일 모델 위에 다시 세운 셈이고,
그 비용은 첫 빌드 시간과
권장 개발 사양(6코어 3.6GHz CPU, 16GB RAM)으로 드러난다.

### 1.0은 기능보다 협업 가능성을 위한 릴리스다

RC1부터 1.0까지의 변경을 묶어 보면 방향이 보인다.
UUID 기반 자산 참조는 파일을 옮겨도 깨지지 않는 프로젝트를,
텍스트 자산 형식은 버전 관리에서 병합할 수 있는 씬을,
타입 있는 핸들과 `GameResult`는 실수하기 어려운 API를,
`export-cli`는 사람이 에디터를 열지 않아도 나오는 빌드를 만든다.
모두 혼자서는 덜 아프지만 여럿이 한 프로젝트를 만들 때 문제가 되는 부분이다.

1.0 글이 `export-cli`를 소개하며
팀 개발과 QA 자동화를 직접 언급한 것도 같은 맥락이다.
0.x 시절 Fyrox가 기능을 더하는 데 집중했다면,
1.0은 이 엔진을 개인의 실험장이 아니라 팀이 쓰는 도구로 바꾸려는 정리 작업이다.

## 비평

### 프로덕션 준비 완료라는 말을 뒷받침할 증거가 홈페이지에 없다

사이트 설명문은 Fyrox를 production-ready라고 부른다.
그러나 홈페이지와 예제 페이지가 보여 주는 게임은
저자의 프로젝트와 오픈소스 데모, 커뮤니티의 실험작이다.
상업적으로 출시된 게임이나 이를 쓰는 스튜디오의 사례는
이 사이트에서 찾을 수 없다.
책의 설계 철학 장은 Fyrox 위에 큰 프로젝트들이 만들어졌다며
검증되었다(battle-tested)고 하지만,
그 큰 프로젝트가 무엇인지는 말하지 않는다.

0.36 HN 스레드에서 martin-t는
순수 Rust 엔진을 찾는다면 이미 프로덕션에 쓸 만하다고 했다.
텍스트 상자 개선이나 멀티플레이 서버용 헤드리스 모드를 요청하자
빠르게 추가되었다는 증언도 덧붙였다.[^martin-t]
이 증언은 엔진이 쓸 만하다는 근거이면서 동시에 다른 사실도 보여 준다.
필요한 기능을 저자에게 요청하면 빨리 들어온다는 것은 작은 공동체의 장점이지만,
엔진의 완성도가 저자 한 사람의 응답 속도에 묶여 있다는 뜻이기도 하다.
2023년 0.29 스레드에서 hesdeadjim이 Rust 엔진을 쓰는 사람은 일정에 쫓기지 않는
취미 개발자와 인디 지망생뿐이라고 단언한 것을 반박하려면,
production-ready라는 형용사보다 출시된 게임 목록이 필요하다.[^hesdeadjim]

### 공식 문서끼리 서로 다른 말을 한다

같은 사이트와 책 안에서 사실관계가 어긋나는 곳이 여럿이다.
책의 FAQ는 OpenGL을 다른 API로 바꿀 필요가 없으며 현재 구현이 충분하다고 답한다.
그런데 RC1 글은 OpenGL이 여전히 돌아가긴 하지만 지저분하고 버그가 많다며,
앞으로 현대적인 그래픽 API로 옮기기 위해
OpenGL을 별도 크레이트로 격리했다고 적는다.
그리고 8월에는 wgpu 백엔드가 기능 플래그로 들어왔다.
FAQ가 한 시점의 입장을 그대로 남겨 둔 것으로 보인다.

시스템 요구 사항도 다르다.
내려받기 페이지는 VRAM 256MB 이상을, 책은 최소 128MB를 요구한다.
책은 macOS에서 M1 이후 칩은 잘 돌아간다고 하지만,
내려받기 페이지가 제공하는 macOS용 프로젝트 매니저 파일 이름은 `macos-x86_64`다.
Apple silicon용 빌드가 따로 있는지는 내려받기 페이지에서 확인되지 않는다.
홈페이지는 기능 목록 마지막에 고품질 문서를 내세우는데,
이런 어긋남은 1인 중심 프로젝트에서
문서가 코드를 따라가지 못하는 전형적인 모습이다.

### 핫 리로딩은 홈페이지와 책의 온도가 다르다

홈페이지는 Hot Reloading을 두 번째 기능으로 내세우며
네이티브 코드와 에셋의 빠른 프로토타이핑을 약속한다.
책의 해당 장은 훨씬 조심스럽다.
코드 핫 리로딩은 매우 새롭고 실험적인 기능이며,
극도로 안전하지 않은(wildly unsafe) 기능 위에 만들어져
메모리 손상과 미묘한 버그가 생길 수 있다고 경고한다.
트레잇 객체의 vtable 포인터가 플러그인을 내리면 무효가 될 수 있고,
엔진이 놓친 객체가 남으면 충돌이 날 수 있다는 한계도 적는다.

이 경고는 저자가 2022년 HN에서 한 말과 이어진다.
그는 게임 DLL과 엔진 사이에서 같은 타입의 `TypeId`가 맞지 않아
일주일을 씨름했고,
DLL 경계를 넘는 모든 것이 미정의 동작과 충돌의 원인이 될 수 있어
정적 링크를 택했다고 설명했다.[^mrDIMAS]
지금의 핫 리로딩은 그 위험을 리플렉션과 직렬화로 관리하며 다시 들인 것이다.
홈페이지의 한 줄만 보면 Unity의 스크립트 리로드 같은 안정적인 기능으로 읽히는데,
실제로는 문제가 생기면 정적 링크로 돌아가라는 조건이 붙은 실험 기능이다.

### 1.0의 호환성 약속이 보이지 않는다

1.0은 보통 이후 API를 함부로 깨지 않겠다는 약속으로 읽힌다.
그러나 1.0 글에는 앞으로의 호환성 정책이나 버전 관리 원칙에 대한 언급이 없다.
오히려 같은 글이 `AsyncSceneLoader`를 없애고 씬 로딩 방식을 바꾸는 등
안정판 직전까지 API를 고쳤다.
RC1은 1.0에서 예전 자산 형식과의 호환을 끊는다고 예고했다.

1.0 직후 큰 기능을 몇 달간 보류한다는 계획은 안정성 측면에서는 좋은 신호다.
하지만 그 이유가 팀의 휴식이라는 점,
그리고 이후 커밋 277개 중 271개가 한 사람의 것이라는 점을 보면,
1.0이 무엇을 보장하는지는 정책이 아니라 저자 개인의 판단에 달려 있다.

## 인사이트

### Rust의 ABI 불안정성이 게임 엔진의 반복 속도를 정한다

게임 개발에서 반복 속도는 언어 선택의 중심 문제다.
0.29 HN 스레드에서 Waterluvian은
Rust의 안전성과 속도는 잘못된 것을 최적화하는 것이며,
게임 개발자가 원하는 것은 단순하고 빠른 개발 루프라고 지적했다.
Lua가 게임 개발에서 사랑받고 자체 스크립트 언어가 많은 이유도
그것이라고 했다.[^Waterluvian]
2024년 홈페이지 스레드에서 logicprog는
Rust가 게임 로직에는 맞지 않지만 엔진에는 맞을 수 있다는
당시 HN의 결론에 동의했다.
그리고 Fyrox가 그 구분을 향한 한 걸음이라고 봤다.[^logicprog]

Fyrox가 겪은 일은 이 논쟁에 구체적인 답을 준다.
Rust는 크레이트 사이에 안정된 ABI를 보장하지 않으므로,
C++ 엔진처럼 게임 코드를 DLL로 갈아 끼우는 일이 언어 차원에서 막혀 있다.
Fyrox는 처음에 정적 링크로 안전을 택했다가,
반복 속도의 압력 때문에
리플렉션으로 객체를 추적하고 직렬화로 상태를 옮기는 장치를 만들어
핫 리로딩을 되살렸다.
안전을 내세운 언어 위에서 반복 속도를 얻으려면
결국 안전하지 않은 영역으로 들어가야 한다는 것이다.
해석하자면, Rust 게임 엔진의 경쟁력은
렌더러보다 이 경계를 얼마나 잘 관리하느냐에서 갈린다.

### 1인 중심 오픈소스는 지정학에도 노출된다

오픈소스 프로젝트의 버스 팩터는 보통 개발자가 지치거나 떠날 위험으로 이야기한다.
Fyrox는 다른 종류의 위험을 보여 준다.
저자는 2021년 HN에서
GitHub 후원이 자기 나라에서 지원되지 않아 Patreon만 쓸 수 있다고 했다.
Bitcoin 후원을 묻는 질문에는
자기 나라에서 Bitcoin이 금지되어 법정 화폐로 바꾸기 어렵다고 답했다.[^mrDIMAS-2]
2022년에는 PayPal이 막혀 Patreon 후원금을 받지 못한다고 밝혔고,
지금 후원 페이지는 루블로 등급을 매기는 Boosty를 가장 먼저 권한다.
그 사이 후원 페이지에는 Bitcoin 주소가 두 번째 선택지로 올라 있다.

코드의 91%를 쓴 한 사람에게 돈이 닿는 경로가 제재와 결제망 차단에 따라 바뀐다.
그리고 공개된 후원 규모는 Boosty 구독자 33명, Patreon 유료 회원 2명 수준이다.
1.0 글이 휴식을 이유로 신규 기능을 보류한 것은 이 구조에서 자연스러운 결과다.
이 엔진으로 장기 프로젝트를 고려하는 팀이라면
기능 목록보다 이 구조를 먼저 평가해야 한다.
MIT 라이선스는 코드를 포크할 권리를 보장하지만,
8,000개 가까운 커밋에 담긴 맥락을 이어받을 사람까지 보장하지는 않는다.

### 2019년의 OpenGL 선택은 7년에 걸친 빚이 되었다

FAQ는 OpenGL을 쓰는 이유를 역사적 배경으로 설명한다.
2018년 4분기에는 여러 플랫폼을 지원하는 좋은 대안이 없었고,
wgpu의 첫 버전은 2019년 1월에야 나왔다는 것이다.
엔진이 시작된 시점에는 합리적인 선택이었다.

HN의 Animats는 2024년에
Fyrox가 여전히 OpenGL이라는 점을 꽤 복고적이라고 지적했다.[^Animats]
Fyrox는 그 선택 덕분에 일찍부터 WebAssembly와 Android에서 돌았지만,
RC1 글 스스로 인정하듯 OpenGL 구현에는 버그가 쌓였다.
RC1의 OpenGL 격리와 8월의 wgpu PR은 7년 전 선택을 갚기 시작한 것이다.
wgpu PR을 소개한 HN 스레드에서 shelldon42는 OpenGL 경로를 기본으로 두고
wgpu를 기능 플래그 뒤에 넣은 것이
기존 사용자를 깨지 않는 올바른 방법이라고 평가했다.[^shelldon42]
다만 그 PR은 저자가 아닌 외부 기여자의 것이었고 알려진 버그를 안고 병합되었다.
1인 중심 프로젝트에서 가장 큰 구조 변경이 외부에서 들어왔다는 점은,
이 엔진의 다음 단계가 저자 한 사람의 속도를 넘어서는지 가늠하는 시험대가 된다.

### 이름보다 작업 흐름이 진입 장벽을 정한다

2022년 HN에서 erlend_sh는 0.25에서 에디터 안에서 게임을 실행할 수 있게 되자
Fyrox를 Godot lite라고 불렀다.[^erlend_sh]
Fyrox가 이후 4년 동안 다듬은 것은 대부분 이 작업 흐름이었다.
프로젝트 매니저, 에셋 브라우저, 인스펙터 복사와 붙여넣기, 내보내기 CLI가 그렇다.

그런데 1.0 Lobste.rs 스레드에 달린 유일한 댓글은
기능이 아니라 첫 경험에 대한 것이었다.
vaguelytagged는 게임 프로젝트를 만들 때 크레이트를 잔뜩 설치해야 했다며,
처음부터 모두 바이너리에 들어 있으면 좋겠다고 적었다.[^vaguelytagged]
2024년 홈페이지 스레드에서 logicprog가 Fyrox를 엔진이 별도 실행 파일이고
게임 로직을 플러그인으로 불러오는 구조로 이해한 것도 흥미롭다.[^logicprog]
실제로는 기본 설정에서 게임과 에디터를 함께 소스부터 컴파일한다.
에디터를 내세우는 엔진일수록
사용자는 Unity처럼 내려받아 바로 여는 경험을 기대하는데,
Rust 컴파일 모델은 그 기대와 첫 10분의 빌드 사이에 간극을 만든다.
Fyrox가 비 Rust 개발자에게 다가가려면
기능 추가보다 이 첫 경험의 비용을 줄이는 쪽이 더 큰 효과를 낼 것으로 보인다.
