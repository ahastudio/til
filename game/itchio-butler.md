# butler: 빌드를 차이만 올리는 itch.io 명령줄 도구

<https://github.com/itchio/butler>

## 소개

butler는 itch.io가 만든 명령줄 도구이다.
저장소는 2015-10-23에 만들어졌고, Go로 작성되었으며 MIT 라이선스이다.
확인한 시점에 별은 1,002개, 포크는 82개였고 마지막 푸시는 2026-10-29였다.
README는 사용처를 두 곳으로 적는다.
하나는 itch.io에서 빌드를 올리는 제작자이고, 다른 하나는 itch 앱이 네트워크,
파일 시스템, 패치 작업에 butler를 쓰는 경우이다.

`cmd/` 아래에서 등록된 명령은 55개이고, 그중 34개는 도움말에서 숨겨져 있다.
숨겨지지 않은 명령은 21개이다.
`push`, `push-preview`, `login`, `logout`, `status`, `upgrade`, `version`,
`which`, `diff`, `apply`, `verify`, `heal`, `sign` 등이다.
`daemon`, `steam-sync`, `steam-login` 같은 명령은 숨겨져 있다.

## 설치와 사용

설치 문서는 두 경로를 안내한다.
하나는 <https://itchio.itch.io/butler>에서 받는 방법이고, 다른 하나는 CI에 넣기
좋은 `broth.itch.zone/butler` 주소이다.
후자의 주소는 고정되어 있어서 스크립트에 그대로 넣을 수 있고, 최신 안정판은
`linux-amd64/LATEST/archive/default` 경로로 받는다.
압축 파일에는 실행 파일과 7-zip 관련 동적 라이브러리 두 개가 들어 있다.
문서는 이 라이브러리가 `butler push`에는 필수가 아니라고 적는다.
docs는 itch 앱 26.12.0부터 앱 안에서 butler로 빌드를 올리는 화면이 있고, 앱이
내장 butler를 직접 갱신한다고도 적는다.

가장 많이 쓰는 명령은 `push` 하나이다.

```bash
butler push 디렉터리 user/game:channel
```

- `디렉터리`는 올릴 폴더이며 .zip 파일도 받는다.
- `user/game`은 프로젝트이고, `channel`은 빌드가 들어갈 자리이다.
- 채널 이름에 `win`, `linux`, `mac`, `osx`, `android`가 들어 있으면 해당 플랫폼 태그가 붙는다.
- 직접 정한 버전 번호는 `--userversion` 또는 `--userversion-file`로 넘긴다.
- `--if-changed`는 변경이 없으면 올리지 않고, `--dry-run`은 올릴 파일 목록만 보여 준다.
- `--hidden`은 새 채널을 바로 내려받을 수 없게 만든다.

인증은 `butler login`을 쓰거나 `BUTLER_API_KEY` 환경 변수로 API 키를 넘긴다.
머리 없는(headless) 환경에서는 `BUTLER_MANUAL_OAUTH=1`로 복사해 붙이는 OAuth
흐름을 쓴다.
README는 이 밖에 SQL, HTTP, JSON-RPC 요청을 기록하는 `BUTLER_SQL_DEBUG`,
`BUTLER_HTTP_DEBUG`, `BUTLER_JSON_RPC_DEBUG`와 pprof 서버를 여는
`BUTLER_DEBUG_PORT`를 소개한다.

## 구성

README의 아키텍처 절은 butler가 하위 패키지 27개를 조합한 구조라고 설명한다.
핵심은 세 개이다.
wharf는 델타 패치와 이진 diff와 pwr 형식을 맡고, boar는 7z, RAR, ZIP 압축 해제를
맡고, hush는 설치 영수증과 매니페스트를 맡는다.
그 아래에서 savior가 압축 해제와 탐색을, httpkit이 HTTP 스트리밍을, go-itchio가
API 클라이언트를 맡는다.
7-zip과 RAR 해제는 libc7zip을 동적으로 불러 쓰며, 이 부분은 LGPL 2.1과 MPL 2.0
구성 요소를 포함한다고 README가 따로 적는다.
소스에서 빌드한 butler 자체는 전부 MIT이다.

`butlerd`는 butler를 JSON-RPC 데몬으로 띄우는 부분이다.
`daemon` 명령은 `--json`이 없으면 안내만 출력하고 종료하며, 전송 방식으로
`http`, `tcp`, `stdio`를 고를 수 있다.
`butlerd/types.go`의 `@name` 주석은 121개이고, 코드 생성기 `generous`가 이
주석에서 Go 핸들러, JSON 스펙, API 문서를 만든다.
README에 따르면 `generous`는 itch 앱용 TypeScript 바인딩과 Rust 클라이언트용
serde 바인딩도 만든다.

## 분석

### push는 빌드를 차이로 바꾸어 올린다

`cmd/push/push.go`를 따라가면 push는 다음 순서로 진행된다.
먼저 올릴 폴더를 걷는 작업을 인증과 동시에 시작한다.
그다음 itch.io에 빌드를 만들고, 같은 채널의 직전 빌드가 있으면 그
서명(signature)을 내려받는다.
서명은 직전 빌드의 블록 해시 목록이다.
butler는 새 폴더를 이 해시와 비교하여 이미 있는 블록은 재사용하고 새 데이터만
패치에 담는다.

패치는 Brotli 품질 1로 압축된다.
패치와 새 서명은 각각 따로 이어 올리기(resumable) 업로드로 동시에 올라가고,
끝나면 둘 다 확정(finalize)된다.
진행 표시는 읽은 바이트에서 패치에 쓰인 바이트를 뺀 값으로 남은 양을 추정한다.
그래서 변경이 적으면 진행률이 비교적 정확하다.

첫 빌드도 같은 경로를 탄다.
이때 비교 대상은 빈 컨테이너이다.
문서는 이 경우에도 압축 덕분에 300MB 빌드에서 120MB만 전송하는 정도의 절감이
있다고 적는다.
변경 비율은 문서가 일반적으로 5%에서 20%라고 말하며, 이는 제작자의 경험적 설명일
뿐이고 측정값으로 제시된 것은 아니다.

### 패치는 두 번 만들어진다

`docs/pushing.md`는 패치 생성을 두 단계로 나눈다.
첫 단계는 사용자 컴퓨터에서 일어난다.
rsync 방식의 고정 크기 블록 비교와 낮은 품질의 Brotli로 빠르고 메모리를 적게
쓰는 기본 패치를 만든다.
업로드가 끝나면 빌드는 바로 공개되고, 플레이어는 이 기본 패치로 갱신할 수 있다.

두 번째 단계는 itch.io 서버에서 일어난다.
서버는 bsdiff로 바이트 단위 차이를 다시 구하고 높은 품질의 Brotli로 재압축하여
더 작은 최적화 패치를 만든다.
큰 게임은 이 처리에 30분쯤 걸릴 수 있다고 문서는 적는다.
처리가 끝나면 최적화 패치가 기본 패치를 자동으로 대체한다.
CPU와 메모리가 많이 드는 작업을 사용자 기기에서 서버로 옮긴 설계이다.

### 실패한 빌드는 서버에 실패로 보고된다

`Do` 함수는 빌드 ID를 받은 뒤 오류로 끝나면 `reportBuildFailure`를 호출한다.
코드 주석은 이 호출이 없으면 빌드가 시작됨 상태로 영원히 남는다고 설명한다.
또 폴더 걷기 결과는 어떤 API 호출보다 먼저 받아 두어, 잘못된 경로 때문에 빌드가
만들어지자마자 실패 처리되는 일을 막는다.
`--dry-run`은 인증 전에 반환되므로 로그인하지 않아도 올릴 파일 목록을 볼
수 있다.

### 숨겨진 명령이 butler의 범위를 보여 준다

공개 도움말의 21개 명령은 제작자가 쓰는 부분이다.
숨겨진 34개에는 itch 앱이 쓰는 설치, 실행, 사전 요구 사항 검사 명령이 많다.
예를 들어 `launch`, `install-prereqs`, `msi-install`, `elfprops`,
`exeprops`가 있다.
`steam-sync`는 Steam 앱의 빌드를 플랫폼별 채널로 itch.io에 복사하는 명령이며
`--from-config`로 여러 앱을 한 번에 처리한다.
이 명령들이 숨겨져 있다는 사실은 CLI 도구와 앱의 백엔드가 하나의 바이너리라는
점을 보여 준다.

## 비평

### 이 도구는 itch.io 서버가 있어야 의미가 있다

butler의 이점은 서버가 직전 빌드의 서명을 갖고 있고 패치를 해석해 준다는 전제
위에 선다.
저장소만으로는 이 이점을 재현할 수 없다.
서버 쪽 최적화 패치 생성은 저장소에 코드가 없으므로, 문서의 설명을 코드로 검증할
수 없다.
이 문서도 그 부분은 문서의 주장으로만 적었다.

### 절감 수치는 사례가 없다

문서가 말하는 80%에서 95% 절감은 변경이 5%에서 20%일 때의 이야기이다.
저장소에는 이를 재현하는 측정이나 벤치마크가 보이지 않는다.
변경이 빌드 전체에 흩어지는 경우, 예를 들어 에셋이 하나의 큰 묶음 파일에
압축되어 있는 경우에는 블록 단위 재사용이 거의 작동하지 않을 수 있다.
이 추정은 블록 비교의 일반 성질에서 나온 것이며 butler로 확인한 것은 아니다.
직접 확인하려면 같은 빌드를 두 번 올려 보고, 묶음 파일 하나만 바꾼 빌드를 한 번
더 올려 `Re-used` 비율을 비교하면 된다.

### 도움말은 butler 기능의 일부만 보여 준다

README는 `daemon`을 butlerd로 소개할 뿐 숨겨진 명령 목록을 싣지 않고,
도움말은 21개만 보여 준다.
`steam-sync`처럼 기능이 큰 명령이 숨겨져 있어서 사용자가 존재를 알기 어렵다.
숨긴 이유는 저장소에서 확인하지 못했다.
의도된 비공개인지 아직 안정화되지 않았다는 뜻인지는 알 수 없다.

## 인사이트

### 업로드 비용을 서버로 옮기는 구조는 제작자의 CI 시간을 줄인다

제작자 입장에서 push가 끝나는 시점은 기본 패치 업로드가 끝난 때이다.
bsdiff와 고품질 압축은 그 뒤에 서버가 한다.
CI 파이프라인은 가장 느린 계산을 기다리지 않고 끝난다.
이 구조의 대가는 플레이어가 한동안 더 큰 기본 패치를 받을 수 있다는 점이다.
사용자 수가 적은 게임에서는 문제가 되지 않고, 출시 직후 접속이 몰리는 게임에서는
처리 시간 30분이 실제 전송량으로 바뀔 수 있다.

### 같은 바이너리가 CLI와 데몬을 겸하면 호환 범위가 넓어진다

butler는 제작자용 CLI와 앱용 JSON-RPC 데몬을 한 코드베이스에 둔다.
그 결과 Go 핸들러에서 TypeScript와 Rust 바인딩까지 한 번에 생성할 수 있다.
다른 언어의 클라이언트를 붙이려는 사람은 API 문서를 직접 쓰지 않고 `generous`의
출력을 쓰면 된다.
반대로 CLI 플래그와 데몬 API가 같은 내부 함수를 공유하므로, 한쪽의 동작 변경이
다른 쪽에 번진다.
`push.Do`가 `metadata`와 `hidden` 같은 인자를 데몬에서도 받는 이유가
여기에 있다.

### 서명 파일은 빌드 무결성 검사에도 쓰인다

push가 서명을 올리는 이유는 다음 push의 비교 기준을 만들기 위해서만은 아니다.
`verify`와 `heal` 명령은 서명을 기준으로 설치된 폴더가 손상되었는지 확인하고
고친다.
같은 서명 파일이 갱신, 검증, 복구에 모두 쓰이므로 서버가 서명을 보관하는 비용이
세 기능으로 나뉘어 회수된다.
이 연결은 명령 이름과 README의 패키지 설명에서 읽은 추정이며, `heal`의 동작은
실행해 보지 않았다.
