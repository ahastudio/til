# Little City

<https://littlecity.io/>

<https://github.com/yaoderek/littlecity.io>

## 소개

Little City는 Derek Yao가 만든 브라우저용 마을 짓기 게임이다.
README는 이를 손으로 그린 도시 건설 게임이라고 소개한다.
블록 몇 개를 놓으면 마을이 되고, 그 뒤에 사람들이 이사 와서 살기 시작한다.
무료이고 계정이 필요 없으며, 컴퓨터와 iPhone, iPad, Android에서 돌아간다고 한다.
README 끝에는 만든 사람으로 Derek Yao와 Nano-AI가 함께 적혀 있다.

프로젝트 사이트는 `https://littlecity.io/`이고,
GitHub API의 `homepage` 값도 같은 주소다.
저장소 `yaoderek/littlecity.io`는 사이트에 올라가는 빌드 결과만 담는다.
게임의 소스 코드는 별도 저장소 `yaoderek/littlecity`에 있다.

### 게임이 하는 일

| 항목        | 사이트와 README가 설명하는 내용                                       |
| ----------- | --------------------------------------------------------------------- |
| 건물 결정   | 메뉴에서 건물을 고르지 않고, 블록을 놓은 위치에 따라 건물이 정해진다  |
| 규칙 예시   | 높은 탑 옆의 집은 예배당이 되고, 바다 옆에 네 칸을 쌓으면 등대가 된다 |
| 마을의 생활 | 제분업자가 밀가루를 빵집에 나르고, 배가 고기잡이를 나간다             |
| 특별한 날   | 장날, 결혼식, 해변의 날, 눈 오는 날, 추수 만찬이 있다                 |
| 마을 키우기 | “Grow a town”이 새 섬에 마을 하나를 통째로 만든다                     |
| 저장과 공유 | 브라우저에 자동 저장되고, 링크나 엽서로 공유한다                      |

마을 유형은 항구 마을, 대리석 도시, 성 마을, 장터 마을, 강 마을, 농촌 마을,
언덕 마을, 정원 마을의 여덟 가지로 llms.txt에 적혀 있다.
게임 안내 페이지는 특별한 건물과 사건 102개와 얻는 방법을 나열한다.
README는 이것이 80개가 넘는다고 쓴다.
README는 마을에 쓰인 그림 파일이 없고 모든 선을 코드로 그린다고 말한다.

### 저장소와 기술

| 항목          | 내용                                                              |
| ------------- | ----------------------------------------------------------------- |
| 사이트 저장소 | 빌드 결과만 담고, 읽은 시점에 커밋이 하나(빌드 게시)였다          |
| 소스 저장소   | 읽은 시점에 커밋 972개, 생성일 2026-11-19, 마지막 푸시 2026-11-26 |
| 언어와 도구   | TypeScript, three.js, Vite, Vitest, Playwright                    |
| 요구 사항     | Node 22.12 이상                                                   |
| 라이선스      | MIT                                                               |
| 분석 도구     | posthog-js가 의존성에 있다                                        |

사이트 저장소는 별 129개, 포크 34개였고 소스 저장소는 별 5개였다.
빌드 결과에는 영어 외에 es, fr, ja, ko, pt, zh 번역 묶음 파일과
피아노 음악 mp3 세 곡이 들어 있다.
README는 직접 호스팅하는 경우 분석 키를 `.env.production`에 두고
littlecity.io로 링크를 걸어 달라고 부탁한다.

### 개발 기록

소스 저장소의 `docs/swarm/STATUS.md`는 이 게임을 만든 과정의 진행 일지다.[^status]
일지는 조정자 에이전트(orchestrator)가 쓴 것으로,
여러 에이전트가 각자의 작업 트리와 브랜치에서 병렬로 작업하고
조정자가 단계마다 합치는 방식을 기록한다.[^status]
첫 단계에서는 논리, 겉모습, 인터페이스 세 담당이 병렬로 일했고,
모델은 Opus 5.5와 Fable 5.2가 쓰였다고 적혀 있다.[^status]
같은 일지에 따르면 이 단계를 합친 시점의 테스트는 445개였고,
나중에 기록된 UFO 작업 검증에서는 2,502개가 통과했다.[^status]

## 분석

### 건물을 고르지 않고 규칙이 건물을 정한다

이 게임의 중심 설계는 플레이어가 건물을 고르지 않는다는 점이다.
게임 안내 페이지는 메뉴에서 건물을 고르는 일이 없고
블록을 놓으면 마을이 무엇이 될지 정한다고 설명한다.
그래서 모든 특별한 건물은 발견의 대상이 된다.
80개가 넘는다는 숫자는 기능 목록이 아니라 찾아낼 것의 수로 읽어야 한다.
게임 안내 페이지가 건물마다 얻는 방법을 적은 것도 이 구조 때문이다.

소스 저장소의 계약 문서는 이 구조의 개발 쪽 얼굴을 보여 준다.
목록을 고치지 않고 파일을 추가하는 방식으로 규칙을 발견하게 하고,
규칙 호출에 맥락(ctx)을 넘기는 형태를 쓴다고 적혀 있다.[^contracts][^status]
이런 구조에서는 새 건물 하나가 기존 코드의 수정이 아니라 파일 하나의 추가다.
여러 에이전트가 같은 저장소에서 동시에 일할 수 있었던 이유와 맞닿는다.

### 그림 파일 없이 코드로 그린 화면

README는 마을에 그림 파일이 없고 모든 선을 코드로 그린다고 말한다.
일지는 렌더러가 잉크와 종이 질감을 내며,
블록 2,000개를 그리는 데 그리기 호출이 11번이라고 기록한다.[^status]
카메라를 돌릴 때 생기는 깜박임은 별도 작업으로 다뤄져
깜박임 점수가 0.103에서 0.015로 내려갔다고 적혀 있다.[^status]

이 선택에서 얻는 것은 스타일의 일관성이다.
건물 조각이 모두 같은 규칙으로 그려지므로 새 건물이 어색하게 튀지 않는다.
치르는 값은 계산 비용과 튜닝이다.
일지에는 모양 결정 단계가 예산을 넘은 기록이 남아 있고,
뒤에 점진 계산을 넣는 개선이 합쳐졌다고 한다.[^status]

### 에이전트 여럿이 만든 프로젝트

일지는 개발이 에이전트 병렬 작업으로 진행됐음을 숨기지 않는다.
단계마다 담당이 정해지고, 합칠 때 전체 검사와 화면 캡처 확인을 거쳤다.[^status]
일지가 적은 어려움은 모델 사용 한도와 기계 부하였다.
한 번은 Fable 사용 한도에 걸려 돌던 에이전트 일곱 개가 한꺼번에 멈췄고,
작업 결과는 작업 트리에 남아 있었다.[^status]
그 뒤 Derek는 한도로 죽은 에이전트를 Opus 5.5로 같은 작업 트리에 다시 띄우고,
이후 새로 띄우는 에이전트는 모두 Opus 5.5를 쓰라고 지시했다고 적혀 있다.[^status]

사람의 역할은 방향과 취향의 판정으로 기록되어 있다.
요청은 Derek의 이름으로 하나씩 기록되고,
걷기 모드는 그가 직접 써 보고 승인하기 전에는 합치지도 게시하지도 않는 미리보기로 못박혔다.[^status]
UFO 광선 효과에 대해서는 그의 평가가 기록되었고,
조정자가 이를 바탕으로 다시 수정을 맡겼다.[^status]

### 사이트와 소스를 나눈 배포

사이트 저장소는 빌드 결과만 담는다.
소스 저장소의 일지는 GitHub Pages가 `gh-pages` 브랜치의 빌드된 파일만 서빙하도록
설정을 바꿨다고 적는다.[^status]
소스 저장소에는 `tools/deploy-pages.sh`가 있고, 사이트 저장소의 커밋 메시지는
소스 커밋 해시를 가리키는 빌드 게시 한 건이었다.
이 구조는 소스 이력과 공개 산출물을 분리하며,
공개 저장소만 보아서는 게임이 어떻게 만들어졌는지 알 수 없다.
일지의 도메인 이전 언급으로 보아 주소는 GitHub Pages 주소에서 옮겨졌다.[^status]

## 비평

### 규모를 말하는 숫자가 서로 다르다

README와 llms.txt는 특별한 건물과 사건이 80개가 넘는다고 쓰고,
게임 안내 페이지의 제목과 문구는 102개라고 쓴다.
일지의 안내 작업 기록에는 항목 44개와 자동 블록이 나온다.[^status]
같은 대상을 세는 기준이 다른 것으로 보이지만,
세는 단위가 문서에 정의되어 있지 않다.
독자는 세 숫자 가운데 어느 것이 건물이고 어느 것이 사건인지 알 수 없다.
이 문서는 숫자를 하나로 맞추지 않고 출처별로 적었다.

### 일지의 통과 기록과 남은 문제

일지는 전체 검사를 통과한 시점의 테스트 수를 거듭 적는다.
같은 일지에는 기계 부하 때문에 시간 초과가 나서 제한 시간을 늘린 일과
통과를 위해 단언 하나를 느슨하게 고친 일도 적혀 있다.[^status]
이 기록은 솔직하다는 장점이 있지만,
테스트 수가 늘었다는 사실이 화면 품질을 보증하지는 않는다.
일지가 직접 인정하듯 눈으로 확인하지 못한 효과도 목록에 남아 있다.[^status]

### 성능 주장의 근거가 부분적이다

일지의 측정에는 블록 2,000개 기준으로 모양 결정이 중앙값 12.8밀리초,
95번째 백분위 40밀리초라는 값이 있고 예산은 8밀리초였다.[^status]
측정은 기계 부하가 높은 상태에서 한 것으로 적혀 있다.
휴대폰 성능은 측정 도구가 있다는 사실만 확인했다.

### 라이선스와 요청의 구분

README는 MIT 라이선스를 밝히면서,
직접 호스팅할 때 분석 키를 유지하고 링크를 걸어 달라고 부탁한다.
MIT는 이 요청을 조건으로 요구하지 않는다.
요청이 법적 조건인지 부탁인지가 README에 구분되어 있지 않고,
분석 키를 유지하라는 부탁은 복제본의 방문 집계가 원작자에게 모이게 하자는 뜻으로 읽힌다.
이는 이 문서의 추정이며 README가 이유를 밝힌 것은 아니다.

## 인사이트

### 규칙마다 증명 테스트를 두는 안내서

일지는 안내 작업이 항목마다 그림과 한 줄 조리법을 만들고
조리법마다 증명 테스트를 두었다고 기록한다.[^status]
사용자에게 보이는 안내문이 코드로 검증되면, 설명과 구현이 어긋나는 일이 줄어든다.
규칙이 많은 게임이나 도구를 만들 때 문서를 테스트의 산출물로 두는 설계를 참고할 만하다.
다만 증명 테스트가 통과한다는 사실이 그 규칙이 재미있다는 뜻은 아니다.

### 에이전트 병렬 작업에서 먼저 닳는 것

이 일지에서 병목은 아이디어나 코드 품질이 아니라 사용 한도와 기계 부하였다.
에이전트 일곱 개가 한꺼번에 죽었을 때 작업이 살아남은 이유는
작업 트리와 커밋이 따로 있었기 때문이다.[^status]
복구 규칙(작업 트리 경로, 인계 메모, 커밋 습관)이 일지에 적혀 있다.
병렬 작업을 설계한다면 에이전트 수보다 중단 뒤 복구 절차를 먼저 정해 둘 만하다.
에이전트 작업을 다룬 다른 문서로 [49개 에이전트 게임 스튜디오 템플릿](claude-code-game-studios.md)이 있다.

### 사람이 맡는 일은 취향의 판정

이 프로젝트의 기록에서 사람이 한 일은 코드 작성이 아니라
무엇을 만들지 요청하고 결과를 보고 판정하는 일이었다.
UFO 효과처럼 점수로 잴 수 없는 항목은 그의 눈이 통과 기준이었다.
이 방식이 맞는지는 이 문서로 판단할 수 없고,
결과물을 직접 해 본 사람의 평가가 필요하다.
