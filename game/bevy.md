# Bevy: 에디터보다 코드가 먼저인 Rust 데이터 주도 게임 엔진

<https://bevy.org/>

<https://github.com/bevyengine/bevy>

HN 토론: <https://news.ycombinator.com/item?id=24334307> (96점, 42개 댓글)

## 소개

Bevy는 Rust로 만든 오픈소스 게임 엔진이다.
홈페이지는 스스로를 “상쾌할 만큼 단순한 데이터 주도 게임 엔진”이라고 소개하고,
바로 아래에 “영원히 무료이고 오픈소스”라는 문구를 단다.
라이선스는 MIT와 Apache 2.0 중 하나를 고르는 방식이며, 홈페이지는 계약도,
라이선스 비용도, 매출 수수료도 없다고 따로 적는다.
엔진과 게임 로직이 모두 Bevy ECS라는 자체 엔티티 컴포넌트 시스템
(Entity Component System) 위에서 돌아간다는 점이 가장 앞에 나온다.

GitHub 저장소는 2020년 1월 18일에 만들어졌고, 첫 공개 글 Introducing Bevy는
2020년 8월에 나왔다.
2026년 10월 8일에 GitHub API로 확인한 저장소의 별은 48,679개,
포크는 4,888개이고, 열린 이슈와 PR을 합한 수는 3,432개다.
crates.io의 `bevy` 크레이트 누적 다운로드는 7,830,085회이고,
최근 90일 다운로드는 1,636,079회다.
최신 안정판은 0.19.1이며,
0.20.0은 9월 28일에 두 번째 릴리스 후보(rc.2)가 태그된 상태다.

만든 사람은 Carter Anderson(`@cart`)이고, 지금도 프로젝트 리드다.
6년이 지난 지금도 버전 번호는 1.0에 닿지 않았다.
공식 소개 문서는 Bevy가 아직 개발 중이고 중요한 기능이 빠져 있으며,
대략 3개월마다 API를 깨는 새 버전이 나온다고 경고한다.
다음 대형 프로젝트에 쓸 엔진을 고르는 중이라면 기능이 훨씬 완성되고 안정적인
Godot을 먼저 보라고 권하는 문장도 그대로 남아 있다.

## 주요 기능

### 홈페이지가 내세우는 기능

| 항목        | 홈페이지 설명                                                           |
| ----------- | ----------------------------------------------------------------------- |
| ECS         | 컴포넌트는 Rust 구조체, 시스템은 Rust 함수, 락 없는 병렬 스케줄러       |
| 2D 렌더러   | 스프라이트 시트, 동적 텍스처 아틀라스, 카메라, 머티리얼, 커스텀 셰이더  |
| 3D 렌더러   | 조명, 그림자, 메시, 머티리얼, glTF 로딩, 커스텀 렌더 파이프라인         |
| 렌더 그래프 | 그래프로 렌더 파이프라인 조립, 자동 병렬 실행, 특정 그래픽 API에 비종속 |
| 애니메이션  | ECS 기반 골격 애니메이션, 블렌딩, 모프 타깃, glTF 애니메이션 가져오기   |
| 플랫폼      | Windows, macOS, Linux, Web, iOS, Android                                |
| Bevy UI     | ECS 위에 만든 자체 UI, flex box 레이아웃                                |
| 씬          | ECS 월드 저장과 로드, 엔티티 ID 보존, 씬 파일 핫 리로드                 |
| 핫 리로드   | 씬, 텍스처, 메시를 재시작이나 재컴파일 없이 반영                        |
| 컴파일 시간 | “fast compiles” 설정에서 0.8~3.0초                                      |

홈페이지는 다른 인기 Rust 게임 엔진이 줄바꿈 하나에 30초 넘게 컴파일한다고
비교하지만, 어떤 엔진인지는 밝히지 않는다.

### 데이터 주도 구조

Bevy에서 게임 오브젝트는 엔티티이고, 엔티티에 붙는 데이터가 컴포넌트이며,
그 데이터를 읽고 바꾸는 함수가 시스템이다.
사용자는 클래스 계층을 만드는 대신 평범한 Rust 구조체와 함수를 쓰고,
엔진은 시스템이 어떤 컴포넌트를 읽고 쓰는지 보고,
병렬로 실행할 수 있는 것을 골라 돌린다.
홈페이지가 말하는 “데이터 주도”와 “단순함”은 이 구조를 가리킨다.

Bevy 유지보수자인 james7132는 HN에서 이 설계가 Rust와 맞물리는 이유를
설명했다.[^james7132]
전통적인 엔진은 애니메이션 골격, 변환 계층, 물리, 렌더링, 스크립트가
서로를 가리키는 포인터 덩어리라서 Rust의 빌림 규칙으로 표현하기 어렵고,
결국 `unsafe`나 스크립트 런타임에 기대게 된다는 것이다.
Bevy ECS는 이런 관계를 평평하게 펴서, 시스템이 쿼리로 필요한 컴포넌트를 바로
가져오게 하고 그 빌림의 수명을 함수 안으로 묶는다.
그 결과 Bevy 크레이트 대부분이 `forbid(unsafe_code)`를 켤 수 있고,
위험한 코드는 `bevy_ecs` 한 크레이트에 모인다고 그는 적었다.

### 0.19: 차세대 씬 BSN

2026년 6월 19일에 나온 0.19는 기여자 261명, PR 1,185개로 만들어졌다.
가장 큰 변화는 BSN(Bevy Scene Notation)이라는 새 씬 시스템이다.
`bsn!` 매크로로 엔티티와 컴포넌트 계층을 선언적으로 적으면,
씬은 서로 조합되고 덧씌워지며 필요한 에셋과 의존성을 스스로 끌어온다.
다른 엔진이 프리팹이라고 부르는 것에 가깝다.
`.bsn` 파일 형식으로 에셋을 저장하고 읽는 기능은 아직 들어오지 않았고,
릴리스 노트는 이것을 다음 최우선 과제로 꼽았다.

```rust
fn button() -> impl Scene {
    bsn! {
        Button
        Node { width: px(200), height: px(100) }
        on(|activate: On<Activate>| {
            info!("Button activated!")
        })
    }
}
```

위 코드는 6번째 생일 글에 실린 예제로, 스타일 없는 기본 `Button` 위젯을 엔티티에
붙이고 활성화 이벤트를 관찰하는 씬을 만든다.
직접 실행해 보지는 않았다.

Lobste.rs에서 npiazza는 무언가 하나를 생성하려고 ECS의 여러 부분을
한 함수에 끌어와야 해서 걸려 넘어진 적이 셀 수 없이 많았다며,
BSN의 템플릿을 보고 멈춰 둔 프로젝트를 되살리겠다고 적었다.[^npiazza]
HN에서 CupricTea는 BSN이 6년 전 Bevy가 처음 발표됐을 때만큼 큰 소식이라고
했다.[^CupricTea]

### 0.19: 렌더링 성능과 UI

0.19 릴리스 노트는 큰 씬을 빠르게 그리는 데 집중했다고 밝히며 수치를 내놓았다.
모바일 RTX 4090 노트북에서 큐브 메시 엔티티 160만 개, 화면 안 116,000개를 그리는
`many_cubes` 예제가 0.18의 프레임당 49.47ms(21FPS)에서 18.77ms(53FPS)로 줄었고,
컬링을 끄고 160만 개를 모두 그리면 93.1ms에서 41.2ms가 됐다.
엔티티 55,000개로 도시를 만드는 새 예제 `bevy_city`는 정적인 경우 19.3ms에서
11.8ms로, 움직이는 경우 22.1ms에서 16.2ms로 빨라졌다.
배치 준비를 GPU로 옮기고, 깊이 프리패스를 묶고, 바뀐 메시 유니폼만 올리고,
조명 클러스터링을 GPU에서 하는 등의 변경이 모인 결과이며,
조명 클러스터링은 `many_lights` 벤치마크에서 약 20배 빨라졌다고 한다.

UI 쪽에서는 `EditableText` 컴포넌트로 텍스트 입력이 처음 엔진에 들어왔다.
폰트 패밀리와 가변 폰트 속성을 다루는 텍스트 기능,
파일에서 읽고 저장해 ECS 리소스로 노출하는 앱 설정 프레임워크,
비네트와 렌즈 왜곡 후처리, 접촉 그림자, 사각형 면광원도 추가됐다.
에디터용 위젯 모음인 Bevy Feathers는 위젯이 늘고 BSN으로 옮겨졌다.

### 개발 환경과 컴파일 시간

Bevy는 일반 Rust 의존성이라서 `cargo add bevy`로 시작한다.
최소 지원 Rust 버전은 “최신 안정판”이다.
빠른 시작 문서는 디버그 빌드가 느리다는 점을 먼저 짚고,
`Cargo.toml`에 다음 설정을 넣으라고 권한다.

```toml
# 내 코드에는 약간의 최적화만 걸어 재컴파일을 빠르게 유지한다.
[profile.dev]
opt-level = 1

# 의존성(Bevy 포함)은 한 번만 빌드되므로 최대로 최적화한다.
[profile.dev.package."*"]
opt-level = 3
```

반복 컴파일을 줄이는 선택지도 단계별로 나온다.
`bevy/dynamic_linking` 기능으로 Bevy를 동적 라이브러리로 빌드하면
매번 정적 링크하는 비용이 사라지지만, 배포할 때는 끄라고 한다.
Linux와 Windows에서는 LLD를, Linux에서는 LLD보다 최대 5배 빠르다는 mold를
쓸 수 있고, macOS는 기본 링커가 이미 빠르다.
나이틀리 컴파일러와 Cranelift 코드 생성기를 쓰면 LLVM보다 약 30% 빨리
컴파일된다고 적혀 있다.
홈페이지의 0.8~3.0초라는 수치는 이런 빠른 컴파일 설정을 갖춘 상태를 전제로 한다.

## 재단과 운영

### Bevy Foundation

Bevy Foundation은 2024년 3월 11일에 발표된 비영리 단체로,
미국 워싱턴주에 설립됐고 같은 해 9월 연방 501(c)(3) 공익 자선단체 지위를 받았다.
사명은 Bevy를 개발하고 사람들에게 쓰는 법을 가르치는 것이다.
기부금은 유지보수자 고용, 웹사이트와 CI 같은 인프라, 단체 운영비에 쓰인다.

이사회는 Carter Anderson(회장, 임시 재무), Alice Cecile(서기), François Mockers,
Robert Swain, James Liu 다섯 명이다.
현재 이사회는 합의로 유지보수자에게 이사 자리를 제안하는 관행을 따른다.
2024년 재단 발표 HN 스레드에서 weinzierl이 인용했듯,
이사 자리를 돈으로 살 방법은 없다는 것이 출범 당시의 원칙이었다.[^weinzierl]

2026년 10월 8일 기준 후원 페이지는 월 $15,606, 개인 후원자 217명,
기업 후원 3곳을 보여 준다.
개인 등급은 월 $5부터 $250까지, 기업 등급은 월 $500부터 $13,000까지 있다.
재단 페이지가 링크하는 예산 문서는 여전히 2024년 예산으로,
수입의 약 90%를 Alice Cecile을 목표 연봉 $150,000의 전업 유지보수자로 고용하는
데 쓰고 나머지 약 10%를 비상금으로 쌓겠다는 내용이다.

Carter Anderson은 매년 8월 10일 생일 글로 한 해를 돌아본다.
2026년 글의 주요 수치는 다음과 같다.

| ------------------ | -------------- | ------------- |
| GitHub 고유 기여자 | 1,527          | 1,291         |
| GitHub 별          | 47,529         | 40,900        |
| PR(병합)           | 16,415(12,501) | 12,928(9,795) |
| crates.io 다운로드 | 6,656,483      | 2,753,203     |
| Discord 회원       | 23,359         | 21,985        |
| Discord 메시지     | 3,751,524      | 2,836,825     |

한 해 동안 0.17, 0.18, 0.19가 나왔고, 커밋마다 런타임 성능, 컴파일 시간,
바이너리 크기를 기록하는 Bevy Metrics가 2025년 12월에 생겼다.
2026년 2월의 일곱 번째 Bevy Jam에는 310명이 참가해 64개 게임이 제출됐다.
Steam에 출시된 게임과 데모, 3D 시계열 데이터 시각화나 설계·시뮬레이션 플랫폼
같은 게임 외 응용도 소개된다.
Exofactory 개발자는 생성 코드를 BSN으로 옮기며 7,364줄을 줄였다고 한다.

같은 글은 문제도 숨기지 않는다.
재단은 여전히 자금이 부족하며, 지금 고용한 개발자에게 기준 연봉 대비 약 54% 깎인
급여를 주고 있다고 적었다.
모금이나 수익 사업은 엔진이 어느 수준까지 완성된 뒤에 하겠다고 밝혔다.

### 공식 에디터

Bevy에는 아직 공식 에디터가 없다.
생일 글에 따르면 지난 1년 동안 BSN, Bevy UI, Feathers, 원격 프로토콜 같은
토대가 갖춰졌다.
커뮤니티의 jbuehler23은 이 토대로 에디터 프로토타입 Jackdaw를 만들었고,
Jackdaw는 이미 시각적 씬 편집, ECS 검사, 되돌리기, 지형과 지오메트리 편집을
갖췄다.
에셋을 엔티티로 다루는 Assets as Entities와 `.bsn` 형식이 들어가면
에디터 워킹 그룹을 꾸려 공식 에디터를 만들겠다는 것이 다음 해 최우선 과제다.
Carter Anderson은 여러 해 동안 “에디터는 내년”이라고 말해 왔으니
이번에도 믿지 않는 편이 좋겠다고 스스로 덧붙였다.

### 프로젝트 목표와 AI 정책

Bevy 개발은 각자 원하는 일을 원할 때 하는 방식이었다.
그래서 몇 달 들인 작업이 방향이 틀렸다는 이유로 막히거나 리뷰를 받지 못하는 일이
잦았고, 로드맵을 묻는 질문에는 “없다”고 답해 왔다.
지난 1년 사이에 도입한 프로젝트 목표(Project Goals)는 크고 논쟁적인 작업을
GitHub의 `C-Goal` 이슈로 제안하고, 주제 전문가(SME)와 프로젝트 리드가 승인,
보류, 거절하며, 리더십이 직접 맡은 목표를 “staffed”로 표시하는 제도다.
생일 글은 처음 도입할 때의 문구가 독재적으로 느껴져 반발을 샀고, 지금은 승인된
목표라면 리더십이 맡지 않아도 워킹 그룹을 만들 수 있도록 완화했다고 밝혔다.

AI 정책도 한 해 내내 공동체를 흔들었다.
처음 도입한 엄격한 AI 금지 정책은 마녀사냥과 거짓말을 부추기고 집행이 거의
불가능했다고 생일 글은 평가했다.
지금 공개된 AI 정책은 생성형 AI로 만든 이미지, 3D 모델, 오디오 같은 미디어와
문서, 이슈, PR 설명, 릴리스 노트 같은 공개 문장,
사람과의 대화에 붙여 넣는 AI 출력,
AI를 커밋 작성자나 `Co-authored-by`로 올리는 것을 모두 금지한다.
코드 쪽에서는 사람이 주도하는 신중한 AI 사용을 용인하되,
사용 사실을 밝히고 제출한 모든 줄을 스스로 설명할 수 있어야 한다.
AI가 보조한 작업을 리뷰하지 않을 권리와, AI 사용 여부를 이유로 남을 괴롭히지
말라는 규정도 함께 들어 있다.

## 분석

### ECS는 Rust의 소유권 문제에 대한 구조적 답이다

Bevy가 ECS를 엔진의 중심에 둔 이유를 성능 유행으로만 읽으면 절반만 본 것이다.
james7132의 설명대로, 서로를 가리키는 객체 그래프는 Rust의 빌림 검사기와
정면으로 부딪힌다.[^james7132]
C++ 엔진은 그 그래프를 포인터로 감당하지만, Rust에서는 같은 구조가 `unsafe`
아니면 `Rc<RefCell<...>>`의 늪이 된다.
ECS는 관계를 데이터 테이블과 쿼리로 바꿔 이 충돌 자체를 피한다.

이 선택은 성능과 안전을 한 번에 얻는다.
시스템의 매개변수가 어떤 컴포넌트를 읽고 쓰는지 타입으로 드러나므로,
스케줄러가 락 없이 병렬 실행을 정할 수 있다.
홈페이지의 “락 없는 병렬 스케줄러”는 따로 붙인 기능이 아니라 이 구조에서
자연스럽게 나온 결과다.
동시에 위험한 코드가 `bevy_ecs`에 모이므로
메모리 안전을 검증할 범위가 한 크레이트로 줄어든다.

그래서 Bevy의 다른 기능은 모두 ECS로 수렴한다.
UI 위젯은 엔티티에 붙는 컴포넌트이고, 씬은 엔티티 계층의 템플릿이며,
렌더 그래프조차 0.19에서 ECS 스케줄 안의 시스템으로 바뀌었다.
앞으로 에셋까지 엔티티로 만들겠다는 계획은 이 수렴의 마지막 단계로 볼 수 있다.
“단순하다”는 홈페이지의 말은 개념의 수가 적다는 뜻이고,
모든 것을 하나의 모델로 표현한다는 약속이다.

### Bevy는 엔진이라기보다 코드로 쓰는 라이브러리로 자랐다

빠른 시작 문서는 Bevy를 “평범한 Rust 의존성”이라고 소개한다.
Unity나 Godot처럼 에디터를 내려받아 프로젝트를 여는 것이 아니라,
`cargo new`로 만든 프로그램에 크레이트를 추가하는 것으로 시작한다.
2024년 HN에서 llmblockchain은 Bevy가 엔진이라고 하지만 실제로는 라이브러리나
프레임워크에 가깝고 처음부터 해야 할 일이 많다며 Godot을 권했다.[^llmblockchain]

이 성격은 6년 동안 바뀌지 않았다.
2020년 홈페이지 HN 스레드에서 smt923은 Godot과 비교할 때 가장 큰 차이로
레벨 디자인과 배치를 위한 UI가 없다는 점을 들었고,[^smt923]
2024년에는 brundolf가 에디터 없이 Unity나 Godot의 영역을 가져오기는
어렵다고 물었다.[^brundolf]
pcwalton은 그때 서드파티 에디터를 쓰고 있으며 공식 에디터는 로드맵에 있다고
답했다.[^pcwalton]
2026년 0.19 Lobste.rs 스레드에서도 srcrip은 Bevy가 Godot이나 Unity 같은
에디터를 내놓으면 Godot이 긴장해야 할 것이라고 했고,[^srcrip]
viraptor는 Jackdaw를 가리키며 결국 나올 것이라고 답했다.[^viraptor]
같은 질문이 6년째 반복되고 있다.

다만 이것을 단순한 지연으로만 보기는 어렵다.
Bevy는 에디터를 엔진 위에 얹는 별도 프로그램이 아니라 Bevy UI와 BSN으로
만든 “평범한 Bevy 앱”으로 만들겠다고 정했고, 그러려면 씬 형식, UI, 위젯,
에셋 시스템이 먼저 있어야 했다.
에디터를 미룬 것은 에디터가 쓸 토대를 엔진 자체에 먼저 넣는 순서를 고른 결과다.
그 순서가 옳았는지는 공식 에디터가 실제로 나온 뒤에야 판단할 수 있다.

### 거버넌스는 한 사람의 취향에서 제도로 옮겨 가는 중이다

Bevy의 초기 개발 문화는 프로젝트 리드 한 사람이 큰 설계를 붙잡고 있는 구조였다.
Carter Anderson은 생일 글에서 BSN을 혼자 오래 다듬다가 몇 년을 끌었고,
그 사이 공동체에 실망이 쌓였다고 인정했다.
리더십이 문 앞에 떨어진 작업을 챙기느라 우선순위를 놓치고,
기여자는 리뷰 없이 방치된 작업에 배신감을 느끼는 악순환도 그가 직접 적었다.

프로젝트 목표, SME, 워킹 그룹, 재단 이사회는 이 문제를 제도로 풀려는 시도다.
리더십의 시간이 한정되어 있다는 사실을 숨기지 않고,
무엇을 맡고 무엇을 맡지 않는지를 공개 보드로 알리는 방식이다.
기여 문서는 목표 보드가 로드맵과 비슷한 역할을 한다고 소개하지만,
생일 글은 앞으로의 순서를 미리 계획하지 않으므로 로드맵은 아니라고 선을 긋는다.
현재 상태를 알리는 도구이지 약속이 아니라는 뜻이다.

AI 정책은 이 제도가 처음 맞은 큰 시험대였다.
정책 문구는 기술적 품질, 기여자의 성장, 공동체라는 세 가치에서 출발해,
미디어와 공개 문장은 막고 코드는 조건부로 허용하는 절충을 택했다.
게임 엔진은 프로그래머뿐 아니라 아티스트도 쓰는 도구라서,
생성형 AI가 아티스트에게 미치는 영향을 특히 우려한다는 문장이 정책에 들어 있다.

## 비평

### 홈페이지는 2020년의 엔진을 설명한다

홈페이지의 기능 목록은 지금의 Bevy를 거의 반영하지 않는다.
씬 항목은 “Bevy Scene format”과 핫 리로드를 말하지만,
0.19의 핵심인 BSN은 나오지 않는다.
최근 1년 사이 들어온 실시간 레이 트레이싱 렌더러 Solari, 가상 지오메트리,
DLSS도, GPU 주도 렌더링으로 수백만 엔티티를 그린다는 0.19의 성과도 없다.
더 어긋나는 것은 렌더 그래프 항목이다.
홈페이지는 그래프 구조로 렌더 파이프라인을 조립하는 것을 핵심 기능으로
소개하지만, 0.19 릴리스 노트는 `RenderGraph` 구조를 ECS 스케줄로 대체했고,
렌더 패스가 이제 평범한 시스템이라고 밝혔다.
대문이 이미 사라진 API를 광고하고 있는 셈이다.
사운드는 “오디오 파일을 불러와 재생한다”는 한 줄이고,
핫 리로드는 “현재 씬, 텍스처, 메시를 리로드할 수 있다”는 오래된 문장 그대로다.

컴파일 시간 문구는 더 문제가 크다.
0.8~3.0초라는 수치는 동적 링크와 대체 링커, 경우에 따라 나이틀리 컴파일러까지
갖춘 “fast compiles” 설정을 전제로 한다.
그런데 홈페이지는 어떤 하드웨어와 프로젝트 규모에서 잰 값인지 밝히지 않고,
비교 대상인 “다른 인기 Rust 게임 엔진”의 이름도 대지 않는다.
2026년 Lobste.rs 생일 글 스레드에서 ramones가 Bevy가 장기적으로 이기길 바라지만
컴파일 시간과 바이너리 크기는 개선이 필요하다고 적은 것을 보면,[^ramones]
홈페이지의 약속과 사용자의 체감 사이에는 여전히 거리가 있다.
반대로 hoistbypetard는 최근 게임 잼에서 증분 빌드가 빨랐고 첫 빌드만 몇 분
걸렸다고 했으니,[^hoistbypetard] 체감은 설정과 기대에 따라 크게 갈린다.
그렇다면 홈페이지가 할 일은 최선의 수치를 내세우는 것이 아니라
조건을 함께 적는 것이다.

릴리스 노트, 생일 글, 메트릭 사이트는 성실하게 갱신되는데 대문만 멈춰 있다.
Bevy Metrics가 커밋마다 컴파일 시간을 재고 있으니,
홈페이지의 수치를 그 측정에 연결하는 편이 훨씬 설득력 있을 것이다.

### “영원히 무료”라는 약속에 비해 재정 정보가 얇다

홈페이지 하단은 계약도, 라이선스 비용도, 매출 수수료도 없다는 문장으로
Unity식 가격 정책과 자신을 구분한다.
그러나 그 약속을 떠받치는 재단의 재정 정보는 생각보다 얇다.
재단 페이지가 링크하는 예산은 2024년 문서이고, 그 문서의 단 하나의 목표는
한 사람을 연봉 $150,000에 고용하는 것이었다.
2026년의 후원액은 월 $15,606, 연으로 환산하면 약 $187,000이며,
생일 글은 지금 고용한 개발자가 기준 대비 약 54% 깎인 급여를 받는다고 적었다.

이 숫자들을 나란히 놓으면, 2년이 지나도록 예산 문서를 갱신하지 않은 이유가
궁금해진다.
재단은 투명성을 내세우며 정관, 회의록, 예산을 공개한다고 밝히지만,
지금 몇 명에게 얼마를 주고 있는지는 생일 글의 비율 하나로만 알 수 있다.
미국 비영리 단체는 일반적으로 연간 신고를 하므로 정보 자체가 없지는 않을 것이다.
다만 후원을 호소하는 페이지에서 바로 찾을 수 없다는 점이 아쉽다.

더 근본적인 질문은 순서다.
Carter Anderson은 엔진이 충분히 완성되기 전에는 모금과 수익 사업에 나서지
않겠다고 했다.
하지만 자금이 부족해 전업 개발자를 늘리지 못하고,
개발자가 부족해 완성이 늦어지는 고리는 이 결정으로 끊기지 않는다.
완성이 먼저냐 돈이 먼저냐는 닭과 달걀 문제에서, 재단은 엔진 쪽에 걸었고
그 판단의 근거는 아직 보이지 않는다.

### 6년째 0.x라는 경고는 정직하지만 비용을 사용자에게 넘긴다

소개 문서가 Godot을 먼저 보라고 권하는 것은 드물게 정직한 태도다.
2020년 HN에서 bluejekyll이 인용한 경고도 거의 같은 문장이었다.[^bluejekyll]
그러나 같은 경고가 6년 동안 유지됐다는 것은 칭찬만 할 일이 아니다.
대략 3개월마다 깨지는 변경이 나오고, 마이그레이션 가이드가 있다 해도
쉬울 것이라고 보장하지 않는다는 문장은 사용자에게 비용을 넘기는 선언이기도 하다.

이 비용은 생태계에서 더 크게 드러난다.
2024년 HN에서 ajuc는 쓸 만한 라이브러리가 서로 다른 Bevy 버전에 의존해서
함께 쓸 수 없고, 비공식 문서인 Cheat Book에는 여러 버전 전에 바뀐 동작이
남아 있다고 지적했다.[^ajuc]
noelwelsh도 공식 Bevy Book이 금방 바닥나 예제와 Cheat Book을 뒤져야 한다고
했다.[^noelwelsh]
0.19 릴리스 노트가 Bevy Book을 크게 늘려 0.20 개발 주기 중에 내놓겠다고 밝힌
것은 이 문제를 리더십도 알고 있다는 뜻이다.

그렇다면 1.0의 조건이 무엇인지 공식적으로 밝혀야 한다.
에디터가 나와야 1.0인지, API 안정성 정책이 생겨야 1.0인지,
아니면 1.0이라는 개념 자체를 두지 않을 것인지를 알 수 없다.
사용자가 Bevy를 고를 때 가장 알고 싶은 것은 언제 깨지는 변경이 멈추느냐인데,
생일 글도 릴리스 노트도 이 질문에는 답하지 않는다.

### AI 정책의 문구와 과정 사이에 간극이 있다

정책 문구 자체는 균형 잡혀 보인다.
금지 대상이 구체적이고, AI를 쓰지 않을 권리와 쓰는 사람을 괴롭히지 말라는
규정이 나란히 있다.
그러나 이 정책을 만든 과정에 대한 평가는 생일 글과 크게 엇갈린다.

Bevy 기여자 fallible은 9월 9일 자신의 블로그(`blog.fallible.net`)에 올린 글
It Breaks a Village: Bevy's 6th Birthday에서 새 정책이 문구상으로는 괜찮지만,
SME들이 방향을 미리 정한 뒤에야 공개 토론을 열었고 AI 반대 논거는
사실상 무시됐다고 비판했다.
그는 이전 정책을 집행할 수 없다는 근거도 핑계처럼 읽혔고,
정책이 더 허용적인 방향으로 계속 움직일 것이라는 불신이 퍼졌다고 적었다.
몇 달째 Plugins API 개편을 하던 그 자신은 5주 가까이 Bevy 코드를 쓰지 못했다고
밝혔다.

생일 글은 엄격한 금지가 마녀사냥을 낳았다는 점을 개정의 이유로 들지만,
그 진단을 받아들이지 않는 기여자에게는 설명이 부족했던 셈이다.
프로젝트 목표 제도가 처음에 독재적으로 느껴졌다는 반성과 같은 패턴이
AI 정책에서도 되풀이됐다고 볼 수 있다.
결정의 내용보다 결정이 내려지는 방식이 신뢰를 좌우한다는 교훈을,
Bevy는 한 해에 두 번 배우고 있다.

## 인사이트

### 게임 엔진의 1.0은 API가 아니라 에디터가 결정한다

Bevy의 렌더러는 이미 레이 트레이싱과 가상 지오메트리를 다루고,
ECS는 Rust 생태계에서 가장 성숙한 구현 중 하나다.
그런데도 사람들이 Bevy를 Godot과 비교할 때 6년째 꺼내는 말은 에디터다.
엔진의 경쟁력은 런타임 기능보다
사람이 콘텐츠를 만드는 작업 화면에서 갈린다는 뜻이다.

이 관점에서 BSN의 의미는 문법 개선 이상이다.
BSN은 코드로 쓰는 씬과 에디터가 저장할 `.bsn` 파일을 같은 데이터 모델로 묶는다.
에디터가 만든 결과를 코드로 덧씌우고,
코드로 만든 씬을 에디터가 다시 열 수 있다면,
srcrip이 바란 “에디터를 쓰되 쓰지 않을 수도 있는 엔진”이 가능해진다.[^srcrip]
Godot에서 에디터 없이 게임을 만드는 것이 사실상 불가능하다는 그의 지적을
뒤집으면, Bevy의 기회는 에디터를 선택 사항으로 남기는 데 있다.

반대로 위험도 분명하다.
rafpast가 지적했듯 게임 개발의 많은 작업은 Rust의 문법이 편하지 않은 영역이라서
DSL이나 스크립트 언어가 필요하다.[^rafpast]
BSN이 그 DSL 역할을 하지만, 아티스트와 디자이너가 직접 다룰 수준이 되려면
에디터가 필수다.
결국 Bevy가 프로그래머의 라이브러리에 머물지, 창작 도구가 될지는
다음 1~2년의 에디터에 달려 있다.

### 안전하지 않은 코드를 한곳에 모으는 설계는 엔진 밖에서도 통한다

james7132가 설명한 구조는 Rust 표준 라이브러리의 방식과 같다.
`Vec`이나 `HashMap` 안에는 `unsafe` 코드가 가득하지만,
그것을 감싼 안전한 인터페이스 덕분에 사용자는 신경 쓰지 않아도 된다.
Bevy는 같은 전략을 게임 엔진 규모로 키워, 위험을 `bevy_ecs`에 모으고 나머지
수십 개 크레이트에서 `unsafe`를 아예 금지했다.

이 설계는 다른 영역에도 옮길 수 있는 교훈을 준다.
복잡한 객체 그래프를 다루는 GUI, 시뮬레이션, 에디터 같은 프로그램은
Rust에서 늘 소유권과 싸운다.
2024년 HN에서 tekacs가 게임이 아닌 작업이 Bevy ECS 없이는 훨씬 고통스러웠을
것이라며 개인 후원을 시작했다고 밝힌 것이나,[^tekacs]
생일 글이 소개한 데이터 시각화와 설계 플랫폼 사례는
Bevy ECS가 게임 엔진 밖에서도 독립된 가치를 갖는다는 신호다.

다만 이 구조에는 대가가 있다.
the__alchemist는 ECS를 이해하고 디버깅하기 어려워 자신의 계산화학 GUI
프로그램을 Bevy에서 WGPU 직접 사용으로 옮겼다고 했다.[^the__alchemist]
관계를 평평하게 편다는 것은 타입 시스템이 지켜 주던 구조를 런타임 쿼리로
옮긴다는 뜻이고, noelwelsh가 지적한 타입 안전성 손실과 엔티티 정리 문제도
여기서 나온다.[^noelwelsh]
안전한 메모리와 이해하기 쉬운 구조 사이의 교환이며,
어느 쪽을 택할지는 문제의 규모가 정한다.

### 오픈소스 엔진의 AI 정책은 누구를 위한 도구인지를 정하는 일이다

라이브러리 프로젝트에서 AI 정책은 대개 코드 품질과 저작권의 문제다.
게임 엔진은 다르다.
사용자 중에 아티스트, 작곡가, 디자이너가 있고, 생성형 AI는
바로 그들의 일과 겹친다.
Bevy 정책이 AI 생성 미디어를 코드보다 엄격하게 막는 이유가 여기에 있다.

이 차이는 이차 효과를 낳는다.
fallible의 글은 Discord의 쇼케이스 채널이 AI 기반 프로젝트로 채워지며
배움을 나누던 공간의 성격이 바뀌었다고 지적한다.
정책이 저장소에 들어오는 기여만 규정해도, 공동체가 무엇을 자랑하고
무엇을 칭찬하는지는 정책 밖에서 바뀐다.
그 변화가 아티스트를 밀어내면, 엔진은 결국 프로그래머만을 위한 도구가 된다.

이것은 앞의 에디터 문제와 같은 질문의 다른 얼굴이다.
에디터는 비프로그래머를 엔진으로 데려오는 문이고, AI 정책과 공동체 문화는
그들이 머물지를 정한다.
Bevy가 창작 도구가 되려면 기술적 토대와 함께,
창작자가 환영받는다고 느끼는 공간이 필요하다.

### 토론의 무게중심은 HN에서 Lobste.rs로 옮겨 갔다

Bevy 릴리스 글의 HN 반응은 대체로 작아졌다.
0.6은 399점, 0.12는 348점을 받았지만 0.17은 40점, 0.18은 18점,
0.19는 19점에 그쳤다.
같은 0.19가 Lobste.rs에서는 91점과 9개 댓글을 받았다.
관심이 줄었다고 단정하기보다는, 관심이 있는 사람들이 다른 곳에 모인다고 보는
편이 맞다.

이 변화는 Bevy만의 일이 아닐 가능성이 크다.
아래는 해석이다.
AI 정책을 두고 공동체가 갈라진 시기에 Bevy 관련 토론이 Lobste.rs 쪽에서 더 길게
이어진 것은, Rust와 오픈소스 개발자가 어디서 이야기할지를 고르는 기준이 바뀌고
있다는 신호로 읽힌다.
Bevy의 수치는 그 이동을 보여 주는 하나의 표본이다.

이것은 프로젝트가 성공을 측정하는 방식에도 영향을 준다.
HN 점수가 줄었다고 Bevy가 덜 쓰이는 것은 아니며,
crates.io 다운로드는 1년 사이 두 배 이상 늘었다.
반대로 GitHub 별이나 HN 점수 같은 눈에 띄는 지표만 보면 실제 사용과 엇갈린
판단을 하게 된다.
Bevy Metrics처럼 엔진 자체를 재는 도구를 만든 프로젝트라면, 공동체의 건강도
별의 수보다 기여자의 지속성과 리뷰 대기 시간 같은 지표로 재는 편이 낫다.
