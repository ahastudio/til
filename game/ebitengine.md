## 소개

Ebitengine은 Go 언어로 2D 게임을 만드는 오픈소스 게임 엔진이다.
홈페이지의 부제는 A dead simple 2D game engine for Go,
곧 Go를 위한 아주 단순한 2D 게임 엔진이다.
발음은 에-비-텐-진이고, 원래 이름은 Ebiten이었다.
2022년 5월 블로그 글은 엔진을 더 고유하게 만들려고 이름을 바꾼다고 알리며,
Ebitengine이 Ebiten과 Engine을 합친 말이라고 설명한다.
웹사이트 주소와 GitHub 저장소 이름은 바꾸지 않았고,
사용자는 소스 코드를 고칠 필요가 없었다.
FAQ는 이름의 유래를 묻는 질문에 에비텐(새우튀김)은 맛있다고만 답한다.

만든 사람은 도쿄의 개발자 호시 하지메(Hajime Hoshi)다.
첫 커밋은 2013년 6월 15일이고, 2023년에 10주년을 맞았다.
그는 같은 GitHub 계정에서 오디오 라이브러리 Oto, 순수 Go MP3 디코더 go-mp3,
WebAssembly 테스트 서버 wasmserve, GUI 프레임워크 Guigui도 만들었고,
Go, Go mobile, GopherJS, Chromium에 기여했다고 소개한다.
Ebitengine 기여로 Google Open Source Peer Bonus를 2023년과 2024년에 연달아
받았다.

## 주요 기능

### 모든 것이 이미지다

홈페이지가 내세우는 첫 특징은 단순함이다.
Ebitengine에서는 화면, 이미지 파일에서 읽은 데이터, 화면 밖 버퍼가 모두 이미지
객체이고, 대부분의 렌더링은 한 이미지를 다른 이미지 위에 그리는 일이다.
설치 문서의 Hello, World 예제는 이 계약을 그대로 보여 준다.

```go
package main

import (
	"log"

	"github.com/hajimehoshi/ebiten/v2"
	"github.com/hajimehoshi/ebiten/v2/ebitenutil"
)

type Game struct{}

// 게임 상태 갱신. 기본 60틱/초로 호출된다.
func (g *Game) Update() error {
	return nil
}

// screen도 그냥 *ebiten.Image다. 여기에 그린다.
func (g *Game) Draw(screen *ebiten.Image) {
	ebitenutil.DebugPrint(screen, "Hello, World!")
}

// 논리 화면 크기. 창 크기(640x480)와 분리되어 자동으로 확대된다.
func (g *Game) Layout(outsideWidth, outsideHeight int) (screenWidth, screenHeight int) {
	return 320, 240
}

func main() {
	ebiten.SetWindowSize(640, 480)
	ebiten.SetWindowTitle("Hello, World!")
	if err := ebiten.RunGame(&Game{}); err != nil {
		log.Fatal(err)
	}
}
```

게임은 `Update`, `Draw`, `Layout` 세 메서드를 가진 `ebiten.Game` 인터페이스를
구현하면 된다.
엔진은 일반 Go 라이브러리로 쓰이고, `go mod tidy`와 `go run .`이면 창이 뜬다.
장면 그래프, 엔티티 시스템, 에디터는 없다.
설치 문서는 환경 확인용으로
`go run github.com/hajimehoshi/ebiten/v2/examples/rotate@latest`를 제시한다.
(이 문서를 쓰면서 예제를 직접 실행하지는 않았다.)

단순한 API 뒤에서 성능을 챙기는 장치도 홈페이지가 밝힌다.
여러 이미지는 내부적으로 하나의 텍스처 아틀라스에 합쳐지고,
그리기 호출은 가능하면 자동으로 일괄 처리된다.
사용자는 이미지 단위로 생각하고, 엔진은 GPU가 좋아하는 형태로 바꾼다.

기능표 문서를 옮긴 것이다.
웹은 WebAssembly로 돌아가고, 모바일은 `ebitenmobile` 명령으로 Android용
`.aar`나 iOS용 `.xcframework`를 만들어 네이티브 앱의 뷰나 뷰 컨트롤러로 넣는
방식이다.
FreeBSD는 작성자가 충분히 테스트하지 못했다고 설치 문서가 경고한다.
기능표에는 없지만 홈페이지는 Nintendo Switch도 지원한다고 적고,
v2.5 릴리스 노트는 Xbox 지원을 알렸다(아래 콘솔 절).

### Kage 셰이더

1.12부터 사용자 정의 셰이더를 쓸 수 있다.
셰이더 언어는 Kage라는 자체 언어로, 문법은 Go와 같아서 `gofmt`까지 통하지만
문자열, 슬라이스, 포인터, 구조체, 채널 같은 Go 기능 다수는 없다.
작성한 프래그먼트 셰이더는 실행 시점에 컴파일되어 OpenGL, Metal, DirectX 등
환경마다 다른 그래픽 API에서 똑같이 동작한다.

### v2.10: 순수 Go 데스크톱, 애플리케이션 가상화, 셰이더 사전 컴파일

2026년 9월 8일 나온 v2.10은 최근 몇 년 중 변화가 큰 릴리스다.
네 가지 핵심 변화를 릴리스 노트에서 옮기면 다음과 같다.

| 변화                    | 내용                                                                         |
| ----------------------- | ---------------------------------------------------------------------------- |
| 데스크톱 순수 Go        | macOS, Linux/BSD에서 Cgo 제거. C 컴파일러와 개발 헤더 없이 교차 컴파일 가능  |
| 애플리케이션 가상화(VM) | 게임을 별도 프로세스의 게스트로 실행하고 호스트가 입력, 틱, 출력을 제어      |
| 셰이더 사전 컴파일      | 실험 패키지 `exp/shaderprecomp`로 런타임 셰이더 컴파일 작업과 로딩 시간 감소 |
| 컬러 이모지와 텍스트    | `text/v2`의 컬러 이모지, 양방향 텍스트 순서 수정, IME 입력 플랫폼 확대       |

순수 Go 전환은 `ebitengine` 조직의 PureGo로 OS API와 공유 라이브러리를
호출해 이뤄졌다.
Windows는 이미 Cgo 없이 동작했다.
다만 릴리스 노트는 Linux 같은 플랫폼에서 창 시스템, 그래픽, 오디오용 런타임
라이브러리가 여전히 필요하고, 모바일과 일부 콘솔 빌드는 Cgo가 여전히 필요하다고
분명히 적는다.
설치 문서도 X 서버(또는 XWayland)와 libX11, libGL 같은 런타임 라이브러리를
요구하며, 개발 패키지와 `pkg-config`만 필요 없어졌다고 설명한다.

애플리케이션 가상화는 게임을 게스트로, 다른 프로그램을 호스트로 나눈다.
호스트는 게스트에 입력을 보내고 언제 갱신하고 그릴지 정하며,
게스트는 그리기 명령을 호스트로 보내 호스트의 그래픽 백엔드에서 실행된다.
오디오는 플레이어별 스트림으로 받는다.
용도는 두 가지로, 게임 에디터 안에 다른 게임을 미리 보기로 넣는 것과,
프로그램이나 AI 에이전트가 입력을 넣고 틱을 진행시켜 렌더링과 오디오를 검증하는
자동 테스트다.
게스트가 되려면 `ebitenginevmguest` 빌드 태그나
`ebiten.RunGameOptions.VMGuestEndpoint`로 작성자가 명시적으로 허용해야 한다.
릴리스 노트는 외부 프로그램이 앱을 쉽게 조작할 수 있게 되므로
일부러 옵트인으로 만들었다고 밝힌다.
게스트는 데스크톱에서만 돌고, 호스트에는 여전히 GPU 환경이 필요하며,
GPU 없는 CI용 소프트웨어 렌더러는 없다.

같은 릴리스는 저장소에 AI 에이전트용 스킬 파일 두 개를 넣었다.
`run-ebitengine-app-headless`는 앱을 vmhost 게스트로 띄워 창 없이 틱을
실시간보다 빠르게 돌리고, 키보드·마우스·터치·게임패드 입력을 주입하고,
렌더링된 프레임을 PNG로 뽑거나 픽셀 단위로 검사하고, 앱이 재생한 소리를
플레이어별 PCM으로 관찰하는 절차를 담는다.
다른 하나는 Kage 셰이더 작성을 돕는 `writing-kage-shaders`다.

그 밖에 프레임버퍼 장치(fbdev)와 EGL로 X11이나 Wayland 없이 Linux에서 그리는
기능이 들어가 휴대용 게임기처럼 창 시스템이 없는 기기를 겨냥했고,
게임패드 진동, 시스템 라이트/다크 모드 조회, 창 숨김 실행이 추가되었다.
v2.10.1부터 v2.10.4까지 9월 한 달에 네 번의 수정 릴리스가 이어졌는데,
숨겨진 창에서 메모리가 끝없이 늘어나는 문제, macOS 13에서 실행되지 않는 문제,
macOS의 USB 게임패드 인식 문제 등을 고쳤다.

## 콘솔과 상용 게임

### Nintendo Switch로 가는 두 번의 길

2021년 6월 Ebiten은 Odencat의 협력으로 Nintendo Switch를 공식 지원한다고
발표했다.
Go로 쓴 Ebiten 게임이 거의 수정 없이 Switch에서 돌아간다고 했지만,
도구는 오픈소스가 아니며 쓰려면 Nintendo와 개발자 계약을 맺어야 한다고 함께
밝혔다.
그해 Odencat의 Bear's Restaurant가 Switch로 나왔다.

처음 방법은 Go 프로그램을 WebAssembly로 컴파일한 뒤 C++ 파일로 바꾸는 것이었다
(go2cpp).
2022년 1월 글에서 호시는 이 방식의 장점으로 낮은 불확실성, 낮은 유지 비용,
높은 이식성을 들고, 단점으로 느린 성능과 긴 컴파일 시간,
단일 스레드라 GC가 게임을 멈추는 문제를 들었다.
그래서 1년 가까이 틈틈이 실험해 Go 프로그램을 Switch용 네이티브 바이너리로
컴파일하는 데 성공했다.

방법은 런타임과 표준 라이브러리의 시스템 호출을 표준 C 함수와 pthread 호출로
바꾸는 것이다.
`go build -overlay`로 런타임 파일을 덮어쓰고, 이 오버레이 JSON을 만들어 주는
패키지 Hitsumabushi(장어덮밥 히쓰마부시)를 새로 만들었다.
Go 컴파일러는 그대로 쓰고 `GOOS=linux GOARCH=arm64 -buildmode=c-archive`로
만든 `.a` 파일을 Switch 컴파일러로 링크한다.
대가도 글에 그대로 적혀 있다.
시그널을 모두 무시하므로 nil 포인터 접근이 패닉 메시지 없이 프로그램을 죽이고,
`calloc`만 하고 `free`는 하지 않는 단순한 메모리 계층이라 메모리 사용량이
줄지 않고 늘기만 하며, `futex`를 pthread 조건 변수로 흉내 내느라 필요 없는
스레드까지 깨운다.
그 대신 C++ 프로젝트 전체 빌드가 5~10분에서 10초 미만으로 줄었고
GC로 인한 멈춤이 사라졌다.
새 Go 버전이 나올 때마다 갱신해야 하는 부담은 받아들일 만한 타협이라고 했다.
글은 공개된 정보만으로 작업했으니 Nintendo에 문의하지 말아 달라는 당부와 함께,
플랫폼 전용 API를 쓰지 않은 이유 중 하나가 그래야 오픈소스로 공개할 수 있기
때문이라고 각주로 밝힌다.

조회 시점 현재 후원자는 26명, 과거 후원자는 96명으로 표시된다.
후원금은 도메인과 서버 비용, 특정 GPU에서만 재현되는 버그를 잡기 위한 테스트
기기 구입 등에 쓴다고 밝힌다.
연례 회고 글은 매년 12월부터 11월까지의 후원자를 금액 순으로, 기여자를 커밋 수
순으로 나열하는데, 기여자 목록은 Ebitengine 본체 외에 PureGo와 Oto를 따로
나눈다.

연락처 페이지의 관리자는 호시 한 사람이다.
2025년 회고에서 그는 회사 업무 외에는 Guigui 개발에 집중했다고 적는다.
Ebitengine에 GUI와 에디터가 없다는 지적이 오래 있었고,
Odencat 사내에서 만들던 게임 에디터의 범용 부분을 떼어 낸 것이 Guigui다.
실제 에디터 개발에서 얻은 통찰로 Guigui와 Ebitengine을 고치고 다시 에디터에
반영하는 순환을 돌린다고 설명한다.

## 분석

### Go의 단순함을 게임 엔진의 설계 원칙으로 옮겼다

Ebitengine의 API는 Go 언어가 표준 라이브러리에서 보여 주는 태도를 닮았다.
작은 인터페이스 하나, 메서드 세 개, 모든 것을 같은 타입으로 다루는 일관성.
`image.Image`를 다루듯 화면을 다루게 한 결정은, 게임 엔진이 보통 제공하는
장면 그래프와 컴포넌트 체계를 의도적으로 빼고 그 자리를 사용자의 Go 코드에
맡긴 것이다.
2020년 HN 스레드에서 fredrikholm은 Ebiten이 아주 잘 돌고 때로는 스크립트를 쓰는
느낌이라고 평했다.[^fredrikholm]

이 선택은 Go 생태계 안에서 의미가 크다.
Go 사용자는 `go run` 한 번으로 실행되는 경험에 익숙하고,
Ebitengine은 그 경험을 게임으로 이어 준다.
2022년 Switch 글 스레드에서 djur는 게임은 자동화된 테스트를 쓰기 어려워 정적
타입의 가치가 크지만 단순한 게임 설계는 Rust나 Haskell의 강력한 타입 체계에서
얻을 게 별로 없으니, Go가 취미 게임 개발에 잘 맞고 여기서는 정말 더 나은 C처럼
느껴진다고 적었다.[^djur]
Ebitengine의 지지층은 이 감각을 공유하는 사람들이다.

같은 철학을 C로 구현한 raylib이 이 저장소의 `game/raylib.md`에 있다.
둘 다 에디터 없이 코드만으로 게임을 만들게 하고, 엔진보다 라이브러리에 가까운
위치를 택했다.
차이는 raylib이 C의 이식성에 기대는 반면 Ebitengine은 Go 툴체인과 런타임을
다른 플랫폼으로 끌고 가야 한다는 점이고, 이 차이가 엔진의 기술적 이력 대부분을
설명한다.

### 엔진의 역사는 Go 런타임을 낯선 땅으로 옮기는 역사다

블로그를 시간 순으로 읽으면 기능 추가보다 이식 작업이 더 두드러진다.
2016년에는 GopherJS로 브라우저에서 돌렸고, 2018년에 WebAssembly 실험 지원,
2019년 v1.9에서 Windows의 Cgo 제거, 2021년 Switch, 2023년 Xbox,
2026년 v2.10에서 모든 데스크톱의 Cgo 제거로 이어진다.
2020년 v2 스레드에서 oregontechninja는 Windows에서 C 컴파일러가 왜 필요 없는지
소스를 뒤져, GLFW를 DLL로 빌드해 Go 상수 바이트로 넣고 실행 시점에 불러온다는
것을 찾아냈다.[^oregontechninja]
v2.10의 PureGo는 그 우회를 모든 데스크톱으로 넓힌 일반화다.

이 작업이 가능한 이유는 저자가 게임 엔진 작성자이면서 Go 런타임과 툴체인
기여자이기 때문이다.
Hitsumabushi는 Go 컴파일러를 고치지 않고 런타임 파일만 덮어써 공식 지원하지
않는 플랫폼에 Go를 올린다.
엔진의 경쟁력이 렌더링 기법이 아니라 언어 런타임을 다루는 능력에서 나온다는
점이 Ebitengine을 다른 2D 엔진과 구별한다.

### 상용 스튜디오 한 곳이 엔진의 검증 환경이다

쇼케이스 열두 편 중 다섯 편, 홈페이지 Gold 후원사, Switch 지원의 협력사,
Xbox 첫 출시작, Guigui의 출발점이 된 사내 에디터가 모두 Odencat으로 모인다.
2024년 회고는 Odencat 대표 Daigo를 오프라인 행사의 게스트로 소개하고,
Switch 글은 그에게 감사를 전한다.
Ebitengine의 콘솔 지원과 실제 출시 경험은 이 관계 위에서 만들어졌다.

이는 오픈소스 엔진이 상용 품질을 얻는 한 가지 경로다.
엔진 사용자가 동시에 후원자이자 시험대가 되면,
출시 과정에서 나오는 버그가 곧바로 엔진으로 돌아온다.
v2.10의 VM 기능이 게임 에디터 안의 미리 보기를 첫 용도로 드는 것도,
Odencat 사내 에디터라는 구체적 수요를 생각하면 자연스럽다(해석).

### 성숙기에 들어선 엔진은 주변 도구와 검증 도구로 이동한다

2024년 회고는 커밋 수가 전년 1,028개에서 800개로 줄었고 엔진이 성숙 단계에
이르렀다고 적는다.
2025년 회고는 2024년까지 1년에 두 번 내던 마이너 릴리스가 2025년에는 v2.9 한
번뿐이었다고 밝힌다.
같은 시기 블로그는 DebugUI v0.1.0 출시를 알렸고,
저자의 관심은 Guigui 같은 주변 라이브러리로 옮겨 갔다.

v2.10은 이 흐름의 결과물로 읽힌다.
새 그리기 기능보다 빌드 장벽 제거, 외부 프로그램이 게임을 조작하는 인터페이스,
로딩 시간 단축, 텍스트 입력 같은 실제 출시에서 부딪치는 문제가 중심이다.
특히 AI 에이전트용 스킬 파일을 저장소에 공식으로 넣은 것은,
엔진의 다음 사용자가 사람만이 아니라는 판단을 보여 준다.

## 비평

### 단순하다는 말은 엔진이 하지 않는 일을 사용자에게 넘긴다

dead simple이라는 표어는 API의 표면에 대해서는 정확하다.
그러나 게임 하나를 끝내는 데 드는 일, 곧 장면 전환, UI, 충돌, 애니메이션 상태,
자산 파이프라인, 레벨 편집은 엔진 밖에 있다.
FAQ가 타일을 확대하거나 회전해 그리면 틈이 생기니 화면 밖 이미지에 먼저 그리라고
안내하는 것처럼, 단순한 모델의 경계에서 생기는 문제는 사용자가 알아서 피해야
한다.

저자 스스로 GUI와 에디터 부재가 오래 지적되었다고 인정한다.
그 답인 Guigui는 2025년 말 기준 알파이고 API가 안정되지 않았으며,
GitHub 스타 486개로 본체에 비하면 아직 작은 프로젝트다.
2020년 HN에서 philosopher1234가 바란 3D 지원도 범위 밖이다.[^philosopher1234]
결국 Ebitengine은 엔진이라기보다 잘 만든 2D 그래픽·입력·오디오 계층이고,
이름을 Ebiten에서 Ebitengine으로 바꾼 것이 성격까지 바꾸지는 않았다.
이 점을 알고 고르면 장점이지만, Godot 같은 통합 엔진과 같은 선상에서 비교하면
기대가 어긋난다.

### 순수 Go라는 표현은 의존성이 사라졌다는 뜻이 아니다

홈페이지는 v2.10부터 모든 데스크톱에서 순수 Go로 구현되어 C 컴파일러가 필요
없다고 적는다.
빌드 시점에 대해서는 맞는 말이다.
그러나 PureGo는 C 라이브러리를 없애는 것이 아니라 링크 대신 실행 시점에
`dlopen`으로 불러오는 방식이고, Linux에서는 여전히 libX11, libGL, 경우에 따라
ALSA 라이브러리가 있어야 실행된다.
2023년 PureGo 스레드에서 기여자 totallygamerjet은
PureGo가 C 호출 오버헤드를 줄이지 않으며
C 툴체인 없이 교차 컴파일하게 해 줄 뿐이라고 설명했고,[^totallygamerjet]
emidoots는 정적 바이너리를 만들 수 없다는 단점을 짚었다.[^emidoots]

즉 문제는 빌드 머신에서 실행 머신으로 옮겨 갔다.
교차 컴파일은 쉬워졌지만, 사용자 환경에 맞는 라이브러리가 없을 때의 실패는
링크 오류가 아니라 실행 시점 오류로 나타난다.
모바일과 일부 콘솔은 여전히 Cgo를 쓴다는 단서도 릴리스 노트에는 있지만
홈페이지 문장에는 없다.

### 콘솔 지원이라는 문구는 공개되지 않은 경로를 가리킨다

홈페이지는 Nintendo Switch도 지원한다고 짧게 적는다.
그러나 2021년 발표문에 따르면 도구는 오픈소스가 아니고 Nintendo와의 계약이
필요하며, 실제로 어떻게 그 도구를 얻는지는 사이트 어디에도 절차로 나와 있지
않다.
Xbox는 2023년에 일반 공개를 준비 중이라고 한 뒤 이 문서가 확인한 범위에서는
후속 공지가 없다.
기능표에도 콘솔 열은 없다.

Hitsumabushi 글 자체는 이례적으로 솔직하다.
메모리를 반환하지 않고, 시그널을 무시해 nil 접근이 조용히 죽으며,
Go 새 버전마다 패치를 갱신해야 한다고 다 밝혔다.
2022년 스레드에서 japhib은 공식 지원이 아니어서 Go 업데이트마다 깨질 것이니
작업이 헛될까 아쉽다고 했고,[^japhib] xiaq는 저자가 패치 형식까지 만들어 유지할
의지를 보였다고 반박했다.[^xiaq]
두 사람 모두 맞다.
콘솔 지원은 기술적으로는 성립하지만, 그 지속성은 저자 한 사람의 유지 의지와
Odencat과의 관계에 달려 있고, 이는 홈페이지의 한 문장에서 드러나지 않는다.

### 13년 된 엔진의 버스 팩터는 여전히 1이다

## 인사이트

### 게임을 VM 게스트로 돌리는 설계는 에이전트 시대의 테스트 인터페이스다

게임은 자동 테스트가 가장 어려운 소프트웨어 중 하나다.
출력이 픽셀과 소리이고, 상태가 시간에 따라 흐르며, 입력이 사람의 손에서 온다.
v2.10의 VM은 이 세 가지를 모두 프로그램이 다룰 수 있는 형태로 바꾼다.
틱을 원하는 만큼 빨리 돌리고, 입력을 주입하고, 프레임을 픽셀로 읽고,
소리를 플레이어별 PCM으로 받는다.

이것은 웹 개발에서 헤드리스 브라우저가 한 역할과 같다(해석).
헤드리스 Chrome이 E2E 테스트와 이후 브라우저 자동화 에이전트의 기반이 되었듯,
게임 엔진이 헤드리스 실행과 결정적 틱 제어를 공식 API로 내놓으면
에이전트가 게임을 직접 플레이하며 버그를 재현하고 고친 결과를 확인하는 순환이
가능해진다.
엔진이 스킬 파일을 저장소에 함께 둔 것은 그 사용자를 처음부터 상정했다는 뜻이다.
저자가 Show HN에서 v2.10을 요약하며 VM을 헤드리스 테스트와 게임 임베딩으로
정리한 것도 이 기능을 앞에 세운 것이다.[^hajimehoshi]

동시에 옵트인 빌드 태그라는 결정은 이 인터페이스가 곧 조작 인터페이스라는
사실을 인정한다.
테스트용 문이 치트와 봇용 문이기도 하다는 긴장은,
게임 엔진들이 같은 기능을 도입할수록 더 자주 마주칠 문제다.
릴리스 빌드에서 게스트 모드를 끄는 것이 기본이 되도록 하는 습관이 필요하다.

### GC 언어가 콘솔에 들어가는 길은 언어 팀이 아니라 런타임을 고쳐 쓰는 개인이 연다

2020년 HN에서 pjmlp는 Ebiten이 GC 언어를 주류 게임 개발로 밀어 넣는 또 하나의
프로젝트라며 Switch 지원이 채택을 도울 것이라고 했다.[^pjmlp]
그 뒤의 이력은 이 말이 절반만 맞았음을 보여 준다.
Go 팀은 Switch를 지원하지 않았고, 길은 호시 개인이 런타임을 덮어써서 열었다.

이 구조는 C#과 Unity의 역사와 닮았다(해석).
Unity가 C# 게임을 콘솔에 올리려고 결국 IL2CPP로 C#을 C++로 변환하는 길을 택한
것처럼, GC 언어의 콘솔 진출은 언어 팀보다 엔진 쪽의 런타임 작업에 기대 왔다.
Ebitengine의 첫 Switch 경로였던 go2cpp가 바로 그 방향이었고,
Hitsumabushi는 반대로 네이티브 런타임을 유지하는 쪽을 택했다.
어느 쪽이든 GC 언어로 콘솔에 가려면 누군가 언어 런타임의 가장 낮은 층을
책임져야 한다는 점은 같다.

그 대가는 Go 버전마다 반복되는 유지 비용이다.
Go 1.25를 요구하는 v2.10처럼 엔진이 최신 Go를 따라갈수록,
콘솔 패치도 같이 따라가야 한다.
GC 언어 게임 엔진의 콘솔 지원은 기능이 아니라 계속 내야 하는 구독료에 가깝다.

### 후원 등급표는 1인 오픈소스 유지의 실제 가격표다

GitHub Sponsors 등급은 이름 게재에서 시작해 예제 코드 작성 요청으로 올라간다.
돈으로 사는 것이 기능이나 우선 지원이 아니라 저자가 직접 쓰는 예제라는 점은,
이 프로젝트에서 가장 희소한 자원이 저자의 시간과 맥락 지식이라는 것을 정확히
드러낸다.
현재 후원자 26명이라는 숫자는 13,000개가 넘는 스타와 대비된다.

이 구조에서 상용 스튜디오의 후원은 사실상 보험료 역할을 한다(해석).
Odencat이 Gold 후원사로 있으면서 자기 게임을 출시하는 것은,
엔진이 계속 유지된다는 데 돈을 거는 일이다.
Ebitengine으로 상용 게임을 내려는 다른 팀도 같은 계산을 해야 한다.
엔진 비용이 무료라는 사실보다, 엔진이 멈췄을 때 직접 떠안을 비용과 지금 낼
후원금을 비교하는 것이 현실적인 판단이다.

### 브라우저에서 시작한 이식성이 결국 에이전트 친화성으로 이어졌다

2016년 첫 HN 스레드에서 사람들이 주목한 것은 GopherJS로 브라우저에서 돌린다는
점이었다.[^shurcooL]
그 뒤 엔진은 WebAssembly, 모바일, 콘솔, Cgo 없는 데스크톱, 창 없는 Linux,
그리고 창도 GPU도 쓰지 않는 VM 게스트로 이어졌다.
겉으로는 서로 다른 기능이지만, 모두 게임이 어디서 어떻게 실행되는지를 엔진이
추상화하는 작업이다.

모든 것을 이미지로 다루는 단순한 모델은 이 추상화를 쉽게 만든다(해석).
그리기 명령이 이미지 사이의 합성으로 정리되어 있으니,
그 명령을 다른 프로세스로 보내 대신 실행하게 하는 VM도 자연스럽게 따라 나온다.
초기의 단순함은 사용자를 위한 선택이었지만,
13년 뒤에는 이식과 자동화를 위한 기반으로 기능하고 있다.
API를 작게 유지하는 결정이 당장의 편의보다 장기적인 확장성에 더 크게 기여한다는
사례로 기억할 만하다.
