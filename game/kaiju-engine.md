# Kaiju Engine: 가비지 컬렉터가 있는 Go로도 빠른 게임 엔진을 만들 수 있다는 주장

<https://kaijuengine.com/>

<https://github.com/KaijuEngine/kaiju>

HN 토론: <https://news.ycombinator.com/item?id=46205519> (222점, 108개 댓글)

## 소개

Kaiju Engine은 Go로 작성하고 Vulkan으로 그리는
오픈소스 2D/3D 게임 엔진이자 에디터다.
홈페이지는 스스로를 Go로 작성하고 Vulkan이 뒷받침하는,
극도로 빠른 오픈소스 게임 엔진과 에디터라고 소개한다.
게임 로직도 엔진과 같은 Go로 짜며, 컴파일 언어의 성능과 현대적 문법의 단순함을
함께 얻는다는 것이 홈페이지의 설명이다.
만든 사람은 Brent Farris이고,
저장소의 `AUTHORS.md`는 그를 프로젝트 창립자로 적는다.
README에 따르면 그는 원래 C로 만든 게임 엔진을 Go로 옮겼다.
Go를 고른 이유로는 Ken Thompson이 Go 설계에 참여했다는 사실,
어셈블리를 쉽게 섞어 쓸 수 있다는 점,
다른 개발자가 배우기 쉽다는 점을 든다.

작업 방식은 두 가지다.
하나는 Kaiju Editor로
장면, 콘텐츠, 셰이더, 파티클, UI를 시각적으로 다루는 길이고,
다른 하나는 에디터 없이 Go 프로젝트에서 엔진을 직접 쓰는 길이다.
두 길 모두 같은 런타임을 쓴다.
설치는 필요 없고, 미리 빌드한 실행 파일을 받거나 소스에서 빌드한다.

이 저장소의 `game/raylib.md`가 C 쪽의 가벼운 게임 라이브러리를 다루고,
`game/cl-fast-ecs-tutorial.md`가 Common Lisp로 ECS를 만드는 과정을 다룬다.
Kaiju는 그 사이에서
가비지 컬렉터가 있는 언어로 에디터까지 갖춘 엔진을 만들겠다는 시도다.

### 문서와 에디터

문서 사이트는 MkDocs Material로 만들었고,
시작하기, 에디터, 엔진, API 항목으로 나뉜다.
에디터 문서는 고유한 용어를 정해 둔다.
Stage는 다른 엔진의 씬이나 레벨에 해당하며,
90년대 게임에서 맵을 부르던 말에서 따왔다.
Template은 다른 엔진의 프리팹이나 블루프린트에 해당하고,
고치면 모든 사용처가 함께 바뀐다.
Table of Contents는 콘텐츠 ID를 이름으로 묶어
코드에 문자열 상수를 늘어놓지 않게 하는 장치다.
F5는 디버그 빌드를 만들어 지금 열린 Stage에서 실행하고,
Ctrl+F5는 릴리스 빌드를 게임 진입점부터 실행한다.
에디터 사용법은 Sudoku를 옮기는 YouTube 연재로 배우라고 권한다.

에디터 없이 쓰는 경로는 `src/main.test.go`를 예제로 삼는다.
이 파일에는 `//go:build !editor` 제약이 있어서,
`editor` 태그 없이 빌드하면 회전하는 구 하나를 그리는 데모가 나온다.
게임은 `bootstrap.GameInterface`를 구현하는 타입 하나로 정의한다.
`PluginRegistry()`, `ContentDatabase()`, `Launch(host *engine.Host)`를 채우고,
매 프레임 호출할 함수를 `host.Updater`에 등록하는 구조다.
Go 모듈 경로는 `kaijuengine.com`이다.

```go
// 에디터 없이 빌드할 때 컴파일되는 예제 진입점의 골격 (문서 설명을 따름)
type Game struct {
	host *engine.Host
	ball *engine.Entity
}
```

빌드는 Go 빌드 태그로 갈래를 나눈다.
홈페이지가 보여 주는 명령은 다음과 같다.

```bash
cd src
go build -tags="debug,editor,filedrop" -o ../ ./
```

`debug` 태그를 넣으면 `-trace` 인자로 Go의 실행 추적을 남기고
Gotraceui로 열어 볼 수 있다.
문서는 디버그 빌드, 특히 추적을 켠 빌드가
릴리스 런타임보다 2배 이상 느리다고 적는다.
CGo를 쓰므로 C 컴파일러가 필요하고, 모든 플랫폼에서 Vulkan SDK가 필요하며,
macOS는 MoltenVK를 거쳐 Vulkan을 쓴다.

### 블로그로 본 최근 방향

블로그에는 2026년 1월부터 5월까지 글 네 편이 있다.
1월의 VFX 글은 파티클 시스템 구조를 설명하면서,
파티클을 아직 CPU에서만 갱신해서
불꽃놀이나 짙은 연기처럼 양이 많으면 병목이 된다고 스스로 밝힌다.
2월의 SIMD 글은 행렬 곱셈 세 함수를 AMD64와 ARM64 어셈블리로 다시 써서
AMD Ryzen 9 7900X에서 6.4~17.0배,
Apple M4에서 8.2~9.6배 빨라졌다는 벤치마크를 싣는다.
같은 달의 다른 글은 Go 표준 `gob` 인코더가
필드가 같은 두 구조체, 특히 빈 구조체 둘을 구별하지 못해 패닉을 일으키는 문제
때문에 직접 인코더를 만든 과정을 설명한다.

5월 글의 제목은 Making Kaiju More Than A Coder Tool이다.
저자는 오랫동안 코드와 성능, 프로그래머 경험에 집중했지만,
이제 아티스트와 디자이너를 위한 도구를 키우겠다고 쓴다.
이 글은 정점 스냅, 지형 편집기, 통합 테스트, 지역화 패키지를 소개하고,
Graviton이라는 이름의 멀티스레드 물리 엔진을 Go로 직접 만들어
Bullet3 의존성을 없앴다고 밝힌다.

## 분석

### 이 프로젝트의 진짜 논제는 엔진이 아니라 Go다

README에서 가장 긴 두 절은 기능 설명이 아니라
Why Go와 What about the Garbage Collector다.
저자는 Go를 말하면 가비지 컬렉터 질문을 받기 때문에 이 절을 만들었다고 쓴다.
그의 답은 세 갈래다.
Unity는 C#으로, Unreal은 자체 GC로, Godot은 C# 스크립트에서 GC를 쓰므로
공개 엔진에 GC는 이미 흔하다.
사람은 실수를 많이 하고 그 실수를 엔진 탓으로 돌리므로,
대중이 쓸 엔진에는 GC가 필요하다.
엔진 설계가 GC와 잘 맞아서 실행 중 힙 할당이 0이었고,
GC를 남용하지 않으면 체감하기 어렵다.

이 구조를 보면 Kaiju는 기능 경쟁보다 언어에 대한 통념을 반박하는 데 무게를 둔다.
홈페이지 첫 문장의 extremely fast와 README의 FPS 비교도 같은 맥락이다.
엔진이 무엇을 할 수 있는지보다
Go로도 이만큼 빠를 수 있다는 것을 먼저 보여 주려 한다.
게임 로직을 엔진과 같은 언어로 짠다는 설계도 이 논제에서 나온다.
엔진 코드와 다른 스크립트 언어를 두지 않으면,
엔진을 읽고 고치는 문턱이 게임 코드를 짜는 문턱과 같아진다.

HN에서도 토론의 상당 부분이 엔진이 아니라 GC를 두고 벌어졌다.
drnick1은 GC 언어는 게임 엔진에 쓸 수 없다는 것이
기초 상식이라고 했고,[^drnick1]
maccard는 Unreal로 만든 모든 게임에 GC가 붙어 있다고 반박했다.[^maccard]
mvdtnz는 GC에서 문제는 평균 FPS가 아니라 멈춤이며,
저자가 이 우려를 FPS 수치로 넘기려 한다고 지적했다.[^mvdtnz]
README의 GC 절은 이런 반응을 예상하고 쓴 글이지만,
토론의 쟁점이 프레임 시간의 꼬리에 있다는 점에는 직접 답하지 않는다.

### 에디터를 엔진 위의 게임으로 만든 선택

홈페이지는 에디터 자체가 엔진에서 돌아가는 게임이라는 점을
엔진의 유연성을 보여 주는 증거로 내세운다.
UI 시스템이 HTML/CSS 비슷한 마크업을 지원하는 것도
같은 시스템으로 게임 인터페이스와 엔진 도구를 함께 만들기 위해서다.
5월 블로그 글에서 에디터 UI 셰이더와 CSS 구현을 다듬고
`<kaiju-include>` 태그를 더한 것이 곧 게임 UI 기능의 개선이기도 하다.

이 선택에는 실용적인 이점이 있다.
에디터가 엔진의 가장 큰 사용자가 되므로,
엔진의 UI, 입력, 렌더링 결함이 에디터를 쓰는 동안 드러난다.
게임이 없는 엔진이라는 비판에 대해,
적어도 엔진 위에서 도는 복잡한 애플리케이션 하나는 존재한다는 답이 된다.
다만 에디터는 게임과 부하의 모양이 다르다.
에디터는 대부분 정적인 화면과 입력 처리이고,
게임은 수많은 엔티티 갱신과 물리, 파티클이 매 프레임 겹친다.
에디터가 잘 돈다는 사실이 게임 부하에서의 성능을 보증하지는 않는다.

### 빌드 태그와 CGo가 드러내는 Go 게임 엔진의 비용

Kaiju의 빌드 명령에는 `debug`, `editor`, `filedrop` 같은 태그가 붙는다.
같은 소스에서 에디터, 디버그, 배포용 바이너리를 골라 만드는 방식이고,
추적 코드는 배포 빌드에서 컴파일러가 제거한다고 문서는 설명한다.
Go의 빠른 컴파일과 단일 바이너리 배포가 개발 속도라는 홈페이지의 약속을 받친다.
HN에서 nullbyte808은 바이너리 컴파일 시간의 이점만으로도
유망한 에디터라고 평가했다.[^nullbyte808]

반대편에는 CGo가 있다.
Vulkan, SoLoud, 플랫폼 창 관리가 모두 C 쪽에 있으므로
C 컴파일러와 Vulkan SDK가 필요하고,
Windows에서는 MinGW, DirectX 런타임, 64비트 Go를 따로 맞춰야 한다.
README는 Windows에서 `libstdc++-6.dll`이 없다는 오류가 나면
MinGW를 설치하라고 안내한다.
순수 Go 프로젝트의 `go build` 한 번이라는 경험은 여기서 깨진다.
HN의 kunos는 Go로 3D를 해 본 경험상 FFI 오버헤드가 커서 실용적이지 않았고,
Vulkan을 호출할 때마다 성능을 잃을 것이라고 했다.[^kunos]
nish__는 C 호출은 프레임당 한 번이면 된다고 되물었다.[^nish__]
Graviton으로 Bullet3를 Go로 대체한 것은
이 경계를 줄이려는 흐름으로 읽을 수 있으며, 이것은 해석이다.

## 비평

### 성능 주장의 근거는 재현할 수 없는 스크린숏 하나다

README의 Why Kaiju 절은 같은 기계에서
Unity의 검은 배경과 큐브 하나가 약 1,600 FPS,
Kaiju의 같은 장면이 약 5,400 FPS로 돈다고 쓴다.
오디오, 커서, 실시간 PBR과 그림자, UI를 갖춘 완성된 게임이
디버그 모드에서 2,712 FPS라는 수치도 붙인다.
그 근거로 연결한 것은 2025년 7월 11일 저자의 트윗이다.
트윗 본문은 Unity에 큐브를 놓고 릴리스 모드로 빌드하니 650 FPS,
자기 엔진으로 게임 전체를 돌리니 2700 FPS라고 말하고, 스크린숏 두 장을 붙였다.

여기에는 벤치마크가 갖춰야 할 정보가 거의 없다.
CPU와 GPU, 해상도, 수직 동기화 여부, Unity 버전과 렌더 파이프라인,
측정 방법이 어디에도 적혀 있지 않다.
저장소에 이 비교를 재현할 Unity 프로젝트나 Kaiju 장면, 측정 스크립트도 없다.
README와 트윗의 Unity 수치도 서로 다르다.
README는 Unity 큐브를 약 1,600 FPS라고 하지만,
README가 근거로 연결한 트윗은 같은 장면을 650 FPS라고 한다.
기계나 설정이 다르다면 설명이 있어야 하고, 같다면 둘 중 하나는 틀렸다.

HN 게시 당시 README의 기능 목록에는
Unity보다 기본 상태에서 9배 빠르다는 괄호가 있었다.
1,600과 5,400의 비율은 약 3.4배이고, 650과 2,700의 비율은 약 4.2배여서
어느 쪽도 9배가 아니다.
현재 README에서는 이 괄호가 사라지고
다른 게임 엔진보다 성능이 낫다는 문장만 남았다.
과장된 숫자를 지운 것은 맞는 방향이지만,
근거를 보강하지 않은 채 범위를 모든 게임 엔진으로 넓힌 셈이다.

HN의 반응은 이 지점에 몰렸다.
MindSpunk는 빈 장면의 FPS는 `while (true) {}`로도 얻을 수 있는 숫자이고,
9배라는 수치는 출처의 맥락 없이 진지하게 받아들일 수 없다고 했다.[^MindSpunk]
johnnyanmac은 200 FPS는 5밀리초, 1,800 FPS는 0.5밀리초 남짓이어서,
실제 작업이 조금만 더해져도 되찾은 4.5밀리초는
금방 사라진다고 계산했다.[^johnnyanmac]
james2doyle은 그나마 맥락이 있는 비교로 저자의 트윗을 찾아 올렸지만,
그것도 9배는 아니며 오해를 부른다고 덧붙였다.[^james2doyle]
artur44는 빈 장면 벤치마크는 추상화 계층이 얼마나 얇은지를 잴 뿐이라며,
엔티티 갱신, 머티리얼, 배칭, 물리에 부하를 거는 데모를
보고 싶다고 했다.[^artur44]

같은 저자가 SIMD 글에서는 CPU 모델과 함수별 ns/op 표를 공개했고,
저장소에 벤치마크 테스트도 있다.
즉 이 프로젝트는 측정을 공개하는 방법을 알고 있다.
그 기준을 엔진 전체의 성능 주장에는 적용하지 않았다는 점이 문제다.
홈페이지 첫 문장이 극도로 빠르다는 말로 시작하는 만큼,
이 주장에는 재현 가능한 장면과 프레임 시간 분포가 따라야 한다.

### 엔진은 프로덕션 준비가 됐다는 말과 저장소의 상태가 맞지 않는다

README는 엔진은 프로덕션 준비가 됐고 에디터는 아니라고 쓴다.
그런데 같은 README의 기능 목록 마지막 줄은 작업 중이며 개발이 한창이라는 경고다.
릴리스는 nightly 189개뿐이고 정식 버전 번호가 붙은 것은 하나도 없다.
엔진 설계 목표를 설명해야 할 Design goals 문서는 곧 채우겠다는 안내만 있다.
프로덕션 준비라는 말을 뒷받침하려면
적어도 버전 정책과 호환성 약속이 필요한데, 둘 다 보이지 않는다.

문서끼리도 어긋난다.
에디터 없이 시작하기 문서는 Go 1.22 이상이면 된다고 하지만,
저장소의 `go.mod`는 `go 1.26.0`을 요구한다.
README는 서브모듈로 받으면
SoLoud와 Bullet3 라이브러리 빌드를 건너뛸 수 있다고 하지만,
5월 블로그는 Bullet3 의존성을 없앴다고 밝혔고,
현재 미리 빌드한 라이브러리 저장소에는 SoLoud 파일만 있다.
문서가 코드를 따라가지 못하는 것은 빠르게 움직이는 프로젝트에서 흔한 일이다.
하지만 처음 들어온 사람이 가장 먼저 읽는 두 문서에서 버전과 의존성이 틀리면,
프로덕션 준비라는 말의 신뢰도도 함께 떨어진다.

### 홈페이지는 게임을 보여 주지 않는다

홈페이지와 README에는 기능별 영상과 에디터 소개는 있지만,
Kaiju로 만든 게임 목록은 없다.
에디터 학습 자료도 Sudoku를 옮기는 연재다.
HN의 pants2는 10분을 뒤져 실제 게임 스크린숏 한 장을 겨우 찾았다며,
Unity 홈페이지는 데모로 시작하는데
Kaiju 홈페이지는 큐브를 Unity보다 빨리 그린다는 글로 시작한다고
꼬집었다.[^pants2]
groundzeros2015는 게임보다 엔진을 만드는 쪽이 늘 쉽고,
엔진은 게임을 만들어야 할 때 비로소
어려운 결정을 내리게 된다고 했다.[^groundzeros2015]

이 비판은 Kaiju만의 문제가 아니지만, Kaiju의 주장 구조 때문에 더 아프다.
성능을 앞세운 엔진은 성능이 게임 부하에서도 유지된다는 것을 보여 줘야 하고,
그 증거는 게임이다.
README가 근거로 연결한 트윗의 완성된 게임이 그 역할을 할 수 있는데,
그 게임이 무엇인지, 어디서 받을 수 있는지는 홈페이지에 나오지 않는다.
5월 블로그가 아티스트와 디자이너를 위한 도구로 방향을 넓힌 것은
이 공백을 인식한 결과로 보이며, 이것은 해석이다.

### 프레임 페이싱과 GC 멈춤에 대한 공개 자료가 없다

README의 GC 절은 실행 중 힙 할당이 0이었다고 하면서도,
다시 검토가 필요할 수 있다는 단서를 단다.
측정 방법이나 시점, 대상 장면은 밝히지 않는다.
게임에서 GC가 문제 되는 지점은 평균 처리량이 아니라 가끔 튀는 프레임이고,
그것을 보여 주는 자료는 프레임 시간 히스토그램이나 백분위 수치다.
Kaiju는 Gotraceui로 추적을 보는 방법은 문서화했지만,
그 도구로 측정한 결과는 공개하지 않았다.

HN의 charcircuit는
코드에서 `time.NewTicker`로 프레임률을 제한하는 부분을 짚었다.
Windows에서 이 타이머의 해상도는 약 0.5밀리초이고,
프레임을 제출해야 할 시점과 맞춰져 있지 않아서
타이머를 만든 시점에 따라 끊김이 생길 수 있다는 지적이다.[^charcircuit]
guywithahat은 고루틴과 채널은 게임에 쓰기에는 지연이 충분히 낮지 않으며,
Go의 대표적인 게임 엔진인 Ebitengine도
내부에서 고루틴을 쓰지 않는다고 했다.[^guywithahat]
이런 지적에 답하려면
FPS 하나보다 프레임 간격의 분포를 보여 주는 편이 훨씬 설득력 있다.

## 인사이트

### 언어 논쟁을 이기려는 벤치마크는 오히려 논쟁을 키운다

Kaiju의 FPS 비교는 Go로는 게임을 못 만든다는 통념을 반박하려고 만든 것이다.
그러나 HN 토론에서 이 수치는
엔진을 진지하게 볼 이유가 아니라 진지하게 보지 않을 이유가 됐다.
999900000999는 9배 빠르다는 터무니없고 근거 없는 주장 때문에
프로젝트를 진지하게 볼 가치가 없다고 여기겠다고 썼다.[^999900000999]
빈 장면 벤치마크가 반박하려던 통념을 오히려 강화하는 구조다.

이것은 언어 커뮤니티의 오래된 패턴과 닮았다.
어떤 언어가 느리다는 평판을 뒤집으려는 프로젝트는
대개 마이크로벤치마크를 들고 나오고,
반대편은 곧바로 그 벤치마크가 실제 부하를 대표하지 않는다는 점을 공격한다.
결국 평판을 바꾸는 것은 그 언어로 만든, 사람들이 실제로 쓰는 물건이다.
Java로는 게임을 만들 수 없다는 통념에 가장 강한 반례는
벤치마크가 아니라 Minecraft였고,
HN에서도 wredcoll은 한 단어로 Minecraft를 들었다.[^wredcoll]
Kaiju가 Go 게임 개발의 평판을 바꾸고 싶다면, 같은 길을 밟아야 한다.

### 1인 엔진의 성장은 문서 부채로 먼저 드러난다

HN 게시 뒤 열 달 동안 커밋은 두 배 가까이 늘었고, 별은 4,700개를 넘었다.
그 사이 물리 엔진을 Bullet3에서 자체 구현으로 바꾸고,
지형 편집기와 통합 테스트를 더했다.
그런데 Go 버전 요구 사항, Bullet3 빌드 안내,
Design goals 문서는 그 속도를 따라가지 못했다.
최근 커밋의 대부분을 한 사람이 쓰는 프로젝트에서는
코드를 쓰는 사람과 문서를 고치는 사람이 같고,
그 사람의 시간은 대개 코드 쪽으로 간다.

이 부채는 사용자 경험에서 가장 먼저 비용이 된다.
엔진을 처음 시험하는 사람은 홈페이지에서 시작하기 문서로 가고,
그 문서가 틀린 Go 버전을 알려 주면 첫 빌드부터 막힌다.
README 커밋 기록에는
외부 기여자가 문서 배치와 설치 안내를 정리한 PR도 섞여 있다.
이런 외부 기여를 문서 유지에 끌어들이는 구조를 만들지 못하면,
기능이 늘수록 첫인상은 오히려 나빠질 수 있다.

### 에디터를 엔진 위에 올리는 설계는 도그푸딩이면서 부하 왜곡이다

에디터를 엔진 위의 게임으로 만드는 방식은
Godot이 자기 에디터를 Godot로 만드는 것과 같은 계열이다.
엔진 개발자가 매일 자기 엔진을 쓰게 되므로
UI와 입력, 도구 쪽 결함은 빨리 고쳐진다.
Kaiju의 최근 블로그가
정점 스냅, 기즈모 단축키, 메뉴 동작 같은 에디터 사용성 이야기로 채워진 것도
이 구조의 결과다.

그러나 도그푸딩은 그 사용자의 부하에 맞춰 엔진을 다듬는다.
에디터는 엔티티가 많지 않고 화면 대부분이 UI이며,
프레임 시간보다 응답성이 중요하다.
게임 쪽의 약점,
예컨대 VFX 글이 인정한 CPU 파티클 병목이나 GC 멈춤 같은 문제는
에디터를 쓰는 동안 잘 드러나지 않는다.
엔진 위의 에디터라는 설계를 가진 프로젝트일수록,
에디터와 다른 모양의 부하를 거는 게임 하나가 따로 필요하다.

### Go 게임 엔진의 경쟁 상대는 Unity가 아니라 다른 Go 도구다

Kaiju는 스스로를 Unity와 비교하지만,
Unity를 쓰던 팀이 Go 엔진으로 옮길 이유는 성능 수치만으로 생기지 않는다.
HN의 eek2121은 Unity가 지형 편집기, 풍부한 교육 자료,
임시 에셋을 구할 에셋 스토어를 갖춰서 시제품을 만들기 쉽다고 했다.[^eek2121]
Kaiju를 실제로 고를 사람은 Go를 이미 좋아하고 게임도 Go로 짜고 싶은 개발자다.
HN의 liampulles는 Go가 그리워서 다른 엔진에서 멀어졌다며
반가워했다.[^liampulles]

그렇다면 Kaiju가 이겨야 할 비교 대상은 Ebitengine 같은 Go 2D 라이브러리,
또는 Go 바인딩을 거쳐 쓰는 raylib 같은 도구다.
그 비교에서 Kaiju의 강점은 에디터와 3D, Vulkan이고,
약점은 CGo 빌드 환경과 짧은 이력이다.
Unity보다 빠르다는 주장보다,
Go로 3D 게임과 에디터를 한 언어 안에서 다룰 수 있다는 점을 앞세우는 편이
실제 사용자층과 더 잘 맞는다.
이것은 홈페이지가 아니라 이 문서의 판단이다.
