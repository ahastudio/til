# Go와 SDL2로 혼자 짓는 2D MMO 엔진, 그리고 아직 증명되지 않은 수천 명

원문: [How I’m Building a 2D Game Engine for an MMO in Golang from Scratch | by Jose Castelli | Medium](https://josecastelli.medium.com/e4262775b61d)

## 요약

Jose Castelli가 2025년 6월 11일 Medium에 올린 글이다.
저자는 이 글을 쓰기까지 5년이 걸렸고 초안도 여러 번 버렸다고 말한다.
기술 해설이라기보다 게임 개발이라는 오랜 열정에 관한 개인 기록이며,
단계별 튜토리얼이나 소스 코드는 싣지 않았다고 처음부터 밝힌다.
본문에는 현재 프로젝트의 이미지와 영상이 들어 있고,
세부 기술은 후속 글로 미룬다.

### 엔진을 여러 번 다시 만든 이력

저자는 스스로를 전문가가 아니라
사물이 어떻게 동작하는지 끝없이 궁금해하는 사람이라고 소개한다.
그동안 VB6(DirectX 7/8), C++(DirectX 11과 SDL), JavaScript(Three.js),
그리고 최근에는 Go로 여러 게임 엔진을 만들었다.
처음 영감을 준 것은 Pablo Márquez와 Fernando Testa의 Argentum Online(VB6와
DirectX 7)과 Aaron Perkins의 ORE Engine 같은 오픈소스 프로젝트였다.
이 엔진들을 연구하고 처음부터 다시 만들어 보면서
어떻게 동작하는지뿐 아니라 왜 그렇게 동작하는지를 이해했다고 한다.
지금 Go로 만드는 MMO는 빌린 코드 없이 전부 직접 만들었다고 강조하며,
숙련된 게임 개발자에게는 비효율적이거나 잘못된 접근으로 보일 수 있다는 점도
인정한다.

17년 전 저자는 형의 YouTube 계정으로
자신이 호스팅한 개조 게임 서버 영상을 처음 올렸다.
그 서버는 동시 접속 40명 가까이까지 갔고,
당시 프로그래밍을 한 지 1년 반쯤 되던 때였다.
미리 만들어진 환경을 다루며 스프라이트, 맵, 인덱싱,
사운드 처리 같은 개념을 처음 접했다.
이후 여러 서버를 열었고 일부는 동시 접속 200명까지 갔지만, 낮은 코드 품질,
불안정한 네트워킹, 성능 병목이라는 같은 문제를 계속 만났다.
어떻게 하면 더 낫게 만들 수 있느냐는 질문이 지금까지 이어진다고 쓴다.

### Go와 Go-SDL2로 시작한 3년

약 3년 전 저자는 Go-SDL2를 써서 Go로 새 엔진을 시작했다.
늘 그렇듯 파티클과 조명부터 만들었고, 첫 기능들은 VB6.0과 DirectX 8로 작성된
Aaron Perkins의 ORE v0.5.0에서 본 파티클 운동, 광원 효과,
색 변화에서 영감을 받았다.
같은 원리를 Go와 SDL2로 다시 구현해 더 성능 좋고 확장 가능한 환경으로 옮겼다는
것이 저자의 설명이며, 베끼지 않고 실험으로 로직을 다시 만들었다고 덧붙인다.

진행은 주로 주말과 틈나는 시간에 이루어졌다.
게임 루프, 스프라이트 렌더링, 기본 상호작용을 갖춘 단순한 엔진을 만들었고,
초기 개발 속도를 높이려고 Argentum Online과 ORE 엔진의 맵, 스프라이트,
효과음을 임시 에셋으로 썼다.
그 과정에서 엔진에 맞춘 독자 맵 형식을 설계해 원래 형식보다 유연성과 성능을
높였다고 한다.
저자는 이 에셋들이 자기 것이 아니며 공개 출시 전 몇 달 안에 직접 만든 콘텐츠로
모두 바꿀 계획이라고 분명히 적는다.

### 화면, UI, 도구

데모는 동적 조명, 텍스트 오버레이, 파티클 궤적, 흉내 낸 시각적 깊이, 스크롤, UI,
네트워킹, 텍스트 렌더링 등을 보여 준다.
저자가 가장 흥미롭고도 어려웠다고 꼽는 부분은 외부 의존성 없이 UI 전체를 직접
만든 일이다.
마우스 상호작용, 버튼, 창과 중첩 창, 포커스 관리, 키보드 단축키, 리스트 박스,
선택, 창 전환을 모두 구현했고, 이를 운영체제가 입력과 상호작용을 다루는 방식을
이해하는 일에 견준다.
관심이 모이면 이 UI 프레임워크를 재사용 가능한 툴킷으로 오픈소스화할 수도 있다고
한다.
도구로는 인덱서와 파티클 에디터를 만들었고 맵 에디터는 아직 작업 중이며,
예전에 C++와 DirectX 11로도 비슷한 도구를 만든 적이 있다.

### 다섯 저장소와 AWS 인프라

시스템은 책임이 분명한 다섯 저장소로 나뉜다.

| 저장소         | 역할                                                                      |
| -------------- | ------------------------------------------------------------------------- |
| Client         | 게임 엔진, 클라이언트 네트워킹, 렌더링. 엔진은 아직 별도 저장소로 분리 전 |
| Server         | SOLID 원칙을 따르는 확장 가능한 핸들러로 핵심 게임 로직 처리              |
| Proto-Messages | 클라이언트와 서버 사이의 강타입 메시지 계약                               |
| Loader         | 프로젝트 전반의 에셋 로딩을 빠르고 일관되게, 중복을 줄여 관리             |
| Infra          | 하드코딩된 설정이나 환경 의존 없이 모듈화한 코드형 인프라                 |

Proto-Messages에 대해 저자는 대부분의 게임이 쓰는 저수준 바이트 패킹 대신
명확성과 안정성을 택했고, 조금 더 장황하더라도 버그가 줄고 장기 유지보수가
쉽다고 설명한다.
애플리케이션 스택 전체는 컨테이너로 묶여 Docker, AWS EC2, AWS RDS로 배포되며,
인프라 갱신은 AWS CDK로 자동화했다.
CDK 구성에는 퍼블릭·프라이빗 VPC, 가벼운 EC2 인스턴스, ECR 이미지 저장소,
기본 보안 규칙과 네트워킹, 계정과 캐릭터 데이터를 담는 DynamoDB,
모니터링과 기본 지표용 CloudWatch가 들어 있다.
비용을 낮추고 민첩성을 높이려고 일부러 최소한으로 구성했지만 게임이 커지면
확장할 수 있는 기반이라고 한다.

### 왜 MMO인가, 그리고 다음 단계

MMO를 택한 이유로 저자는 아키텍처가 이미 인프라뿐 아니라 코드 수준에서도
수천 명의 동시 접속을 지원하도록 설계되어 있다는 점을 든다.
네트워킹부터 메시지 처리까지 실시간 멀티플레이 트래픽을 효율적이고 안정적으로
처리하도록 만들었다는 것이다.
그러면서도 첫 공개 버전을 오프라인 모드만으로 낼지 고민 중이며,
그러면 멀티플레이 시스템을 계속 다듬으면서 빨리 출시하고 피드백을 받을 수 있다고
말한다.
멀티플레이 시스템은 이미 프로덕션 준비에 가깝다는 것이 저자의 평가다.

현재 본업 때문에 전업으로 매달릴 수는 없지만 첫 출시를 향해 집중하고 있다고
한다.
지금 갖춘 것으로는 핵심 효과와 리소스 로딩을 갖춘 2D 엔진,
필요한 메시지 패키지가 거의 다 정의된 네트워킹 프로토콜,
확장하기 쉬운 코드 구조, 어느 클라우드에서든 Docker 컨테이너를 빠르게 배포할
기본 인프라를 꼽는다.
앞으로 할 일은 임시 에셋 전면 교체, 검증된 표준에 가깝게 게임 메커니즘 확정,
안정성과 확장성을 갖춘 인프라 완성, 게임 이름 결정이다.
프로젝트는 여러 해 지속되는 것을 목표로 하며,
기여자가 장벽 없이 협업할 수 있는 커뮤니티를 지향한다고 밝히고,
Discord와 YouTube 채널을 안내하며 글을 맺는다.

## 분석

### 이 글은 엔진 설명이 아니라 계보 선언이다

글의 무게중심은 기술보다 계보에 있다.
17년 전의 개조 서버, VB6와 DirectX 시절의 Argentum Online과 ORE,
C++와 DirectX 11 도구, 그리고 지금의 Go 엔진이 한 줄로 이어진다.
저자가 반복해서 강조하는 것은 같은 대상을 다른 언어와 도구로 여러 번 다시
만들었다는 사실이며, 이번 엔진은 그 연장선의 최신판이다.

이 계보는 실제로 확인된다.
스페인어 Wikipedia는 Argentum Online을 Baronsoft가 만든 ORE(Online RPG Engine)
v0.4를 1999년 Pablo Ignacio Márquez와 Fernando Testa가 친구들과 함께 고친
게임으로 소개하고, 아르헨티나에서 태어난 첫 MMORPG로 꼽는다.
SourceForge의 oreproject 페이지는 ORE를 Aaron Perkins가 관리한 VB 프로젝트로
등록해 두었다.
즉 저자가 영감의 원천으로 든 두 프로젝트는 서로 독립된 것이 아니라 하나의
줄기이고, 저자는 그 줄기의 세 번째 세대를 자처하는 셈이다(해석).

그래서 이 글은 엔진 설계 문서라기보다,
VB6 시절 2D MMO 엔진을 공부하며 자란 개발자가
같은 장르를 현대 도구로 다시 쓰는 과정을 기록한 글로 읽는 편이 정확하다(해석).
새 엔진의 첫 기능을 ORE v0.5.0에서 본 파티클과 조명으로 정했다는 대목,
그리고 엔진과 함께 인덱서, 파티클 에디터, 맵 에디터를 따로 만든다는 대목은
옛 엔진의 구성 요소를 하나씩 현대 도구로 옮기는 작업 방식을 보여 준다.

### 전부 직접 만든다는 선택의 범위

저자는 빌린 코드가 없다는 점과
UI를 외부 의존성 없이 만들었다는 점을 내세운다.
하지만 실제 스택을 보면 직접 만든 범위는 꽤 정확하게 갈린다.
렌더링과 입력은 SDL2에, 그 바인딩은 Go-SDL2에, 배포는 Docker와 AWS CDK에,
데이터는 DynamoDB에 맡겼다.
직접 만든 것은 게임 루프, 파티클과 조명, UI 툴킷, 맵 형식, 에디터, 메시지 계약,
로더다.

이 경계 설정은 합리적이다.
그래픽 API와 창 관리처럼 플랫폼마다 다르고 재미없는 부분은 빌리고,
게임의 손맛을 정하는 부분은 직접 쥔다.
다만 이 구분은 “from scratch”라는 제목이 주는 인상과는 결이 다르며,
실제 의미는 상용 엔진이나 Go 게임 프레임워크를 쓰지 않았다는 쪽에 가깝다.

### 강타입 메시지 계약은 서버 운영 경험에서 나온 결정이다

다섯 저장소 가운데 가장 의미 있는 결정은 Proto-Messages를 따로 둔 일이다.
저자는 대부분의 게임이 쓰는 저수준 바이트 패킹 대신 강타입 메시지를 쓴다고 하고,
그 이유로 버그 감소와 장기 유지보수를 든다.
글이 Protocol Buffers라고 명시하지는 않지만 저장소 이름으로 보아 그 계열의
스키마 기반 직렬화일 가능성이 높다(추정).

이 선택은 저자가 어린 시절부터 겪었다는 불안정한 네트워킹 문제와 직접 맞닿는다.
클라이언트와 서버가 각자 바이트 순서를 손으로 맞추는 구조에서는 한쪽만 바뀌어도
조용히 깨지는데, 계약을 별도 저장소로 떼어 두면 그 변경이 양쪽에 동시에
드러난다.
같은 서버를 여러 번 운영하며 얻은 교훈이 아키텍처에 반영된 지점이라는 점에서,
글 전체에서 가장 경험에 뿌리를 둔 설계다(해석).

### 인프라 서술은 엔진보다 앞서 있다

흥미로운 점은 인프라가 게임보다 더 완성된 것처럼 서술된다는 것이다.
게임 이름도 없고, 메커니즘도 확정되지 않았고, 에셋은 전부 임시인데, CDK로 VPC,
ECR, CloudWatch까지 자동화되어 있다.
이는 저자의 본업 감각이 취미 프로젝트에 그대로 옮겨진 모습으로 보인다(해석).

이 순서는 양면적이다.
배포가 자동화되어 있으면 테스트 서버를 쉽게 열 수 있고 커뮤니티 피드백 루프를
빨리 돌릴 수 있다.
반대로 게임의 재미가 아직 검증되지 않은 단계에서 인프라에 들인 시간은 출시를
앞당기는 데 거의 기여하지 않으며, 저자 스스로 첫 버전을 오프라인 모드로 낼지
고민한다는 점이 그 긴장을 드러낸다.

## 비평

### 수천 명 동시 접속은 주장일 뿐 측정이 아니다

저자가 MMO를 택한 이유로 내세우는 핵심 문장은
아키텍처가 이미 수천 명의 동시 접속을 지원하도록 설계되었다는 것이다.
그러나 글에는 부하 시험 결과, 봇 수, 틱 주기, 패킷 크기,
대역폭 같은 근거가 하나도 없다.
설계 의도와 검증된 용량은 다른 말이며, 글은 둘을 같은 문장 안에서 섞는다.

같은 저장소의 `game/modak-online.md`가 좋은 대조군이다.
그 글의 저자는 Go 백엔드로 MMORPG 동시 접속 1,000명을 시험했는데,
실제 봇을 붙여 보니 약 300명에서 `TCP: out of memory`가 났고 병목은 CPU가 아니라
지속 아웃바운드 대역폭이었다.
코드 수준의 효율과 무관한 곳에서 한계가 왔다는 점이 핵심이다.
Castelli의 인프라가 가벼운 EC2 인스턴스 하나라는 점을 생각하면,
수천 명이라는 숫자는 측정되기 전까지 희망치로 읽어야 한다.

저자의 과거 경험도 이 숫자와 거리가 있다.
그가 운영한 서버의 최대치는 동시 접속 200명이었고,
그때 겪은 문제로 불안정한 네트워킹과 성능 병목을 직접 꼽는다.
200명에서 겪은 문제를 해결했다는 증거 없이
수천 명을 설계 목표로 말하는 것은 한 자릿수 이상의 비약이다.

글 안에서도 이 주장은 스스로 흔들린다.
멀티플레이 시스템이 프로덕션 준비에 가깝다고 하면서 동시에 첫 공개 버전은
오프라인 모드만으로 낼지 고민한다.
정말 수천 명을 감당할 준비가 되어 있다면 MMO의 첫 출시를 싱글 플레이로 미룰
이유가 줄어든다.

### 남의 에셋을 쓴다는 고백은 라이선스 질문을 열어 둔 채 끝난다

저자는 Argentum Online과 ORE의 맵, 스프라이트,
효과음을 임시로 썼고 자기 것이 아니라고 솔직하게 밝힌다.
이 솔직함은 미덕이지만, 어떤 라이선스 아래에서 썼는지는 말하지 않는다.

확인할 수 있는 범위에서 보면 두 프로젝트의 코드는 카피레프트다.
스페인어 Wikipedia는 AO가 ORE처럼 GNU GPL로 배포되었고 0.11 이후 GNU Affero
라이선스로 넘어갔다고 적고, `ao-libre/ao-cliente` 저장소의 LICENSE도
AGPL-3.0이다.
SourceForge의 ORE 프로젝트 페이지는 라이선스를 GPLv2와 LGPLv2로 표시한다.
하지만 이 라이선스가 그래픽과 사운드 에셋까지 덮는지,
에셋에 별도 저작권자가 있는지는 이번에 확인하지 못했다.

이 공백이 중요한 이유는 저자가 독자 맵 형식을 만들면서 원래 맵을 변환했다고
읽히기 때문이다.
맵 데이터가 GPL 계열로 배포된 것이라면 변환물의 배포 조건도 따져야 하고,
에셋이 별도 권리 아래 있다면 공개 데모 영상 자체가 문제의 소지가 된다.
출시 전 교체하겠다는 약속은 최종 배포물에 대한 답일 뿐,
이미 공개한 영상과 데모에 대한 답은 아니다.

빌린 코드가 없다는 강조와 남의 에셋을 쓴다는 고백이 한 글 안에 나란히 있다는
점도 짚어 둘 만하다.
코드는 직접 썼어도 화면에 보이는 게임의 인상 대부분은 AO와 ORE의 것이며,
독자가 데모 영상에서 보는 것도 결국 그 인상이다.
엔진의 성과를 평가하려면 이 둘을 분리해서 봐야 하는데 글은 그 분리를 독자에게
맡긴다.

### 인프라 서술은 서로 맞지 않는다

인프라 절은 짧은 분량 안에서 두 번 어긋난다.
먼저 배포 경로를 Docker, AWS EC2, AWS RDS라고 소개한 직후,
CDK 구성 목록에는 RDS가 없고 계정과 캐릭터 데이터 저장소로 DynamoDB가 나온다.
RDS를 다른 용도로 함께 쓰는 것인지, 초기에 RDS를 썼다가 DynamoDB로 옮긴 것인지,
단순한 서술 실수인지 글만으로는 알 수 없다.

관계형 데이터베이스와 키-값 저장소 중 무엇을 쓰느냐는 MMO에서 사소한 문제가
아니다.
인벤토리 거래, 길드, 경매처럼 여러 캐릭터에 걸친 원자적 갱신이 필요한 기능은
저장소 선택에 따라 구현 난이도가 크게 달라진다.
아직 게임 메커니즘이 확정되지 않았다는 저자의 말과 겹쳐 보면,
저장소 선택이 메커니즘보다 먼저 이루어졌을 가능성이 있다(해석).

다음으로 현재 갖춘 것을 정리하는 대목에서는
어느 클라우드에서든 Docker 컨테이너를 빠르게 배포할 인프라라고 하지만,
실제 구성은 AWS CDK, ECR, DynamoDB, CloudWatch로 AWS 고유 서비스에 묶여 있다.
컨테이너 이미지는 이식할 수 있어도
DynamoDB에 의존하는 서버 코드와 CDK로 정의한 네트워크는 그대로 옮겨지지 않는다.

### Go-SDL2 선택의 비용은 언급되지 않는다

저자는 Go와 SDL2를 더 성능 좋고 확장 가능한 환경이라고만 설명하고,
왜 Go를 택했는지와 Go-SDL2가 어떤 제약을 가져오는지는 다루지 않는다.
`veandco/go-sdl2`의 README는 크로스 컴파일 예시마다
`CGO_ENABLED=1`과 C 컴파일러를 요구하며, cgo 바인딩이라는 점을 분명히 보여 준다.
Go의 장점으로 흔히 꼽히는 단일 바이너리 크로스 컴파일이 클라이언트에서는 그만큼
약해진다는 뜻이다.

유지보수 상황도 고려할 만하다.
저장소는 보관(archive) 상태가 아니고 BSD 3-Clause 라이선스이지만,
릴리스 피드상 가장 최근 태그는 2024년 12월의 `v0.5.0-alpha.7`이고 커밋 피드의
최신 항목은 2025년 2월이다.
README 첫 줄은 SDL3가 필요하면 cgo 없이 코드 생성을 쓰는 다른 프로젝트
`JupiterRider/purego-sdl3`를 보라고 안내한다.
여러 해 지속되는 프로젝트를 목표로 한다면,
바인딩 계층을 언제 어떻게 바꿀지가 언젠가 엔진 전체의 질문이 된다.

UI를 외부 의존성 없이 만들었다는 자부심도 같은 맥락에서 읽어야 한다.
SDL2 위에 직접 만든 UI는 SDL 버전이나 바인딩이 바뀔 때 함께 옮겨야 하는
코드이며, 의존성을 줄인 대신 이식 부담을 스스로 떠안은 것이다.
저자가 엔진을 별도 저장소로 아직 분리하지 못했다고 밝힌 점을 보면,
그 경계가 실제로 얼마나 깨끗한지도 아직 검증되지 않았다.

## 인사이트

### 혼자 만드는 MMO의 첫 병목은 코드가 아니라 콘텐츠다

저자가 남은 일로 꼽은 네 가지 가운데 둘은 엔진과 무관하다.
에셋 전면 교체와 게임 이름 결정이다.
그리고 지금까지 엔진 작업을 가능하게 한 것은 AO와 ORE의 맵, 스프라이트,
효과음이었다.
즉 3년 동안 엔진이 자랄 수 있었던 조건 자체가 빌린 콘텐츠였다.

이 구조는 개인 MMO 프로젝트에서 반복된다.
엔진 개발자는 코드 문제를 풀 수 있는 사람이라 엔진이 먼저 자라고, 맵, 몬스터,
퀘스트, 밸런스 같은 콘텐츠는 뒤로 밀린다.
MMO는 플레이어가 오래 머무는 장르라 콘텐츠 소모 속도가 빠르고,
혼자서는 그 속도를 따라잡기 어렵다.
저자가 커뮤니티를 강조하는 것도 이 공백을 사람으로 메우려는 시도로 읽힌다(해석).

그렇다면 에셋 교체는 남은 일 목록의 한 줄이 아니라 프로젝트의 실제 임계 경로다.
지금까지의 데모가 보여 준 화면 인상이 대부분 AO에서 왔다면,
독자 에셋으로 바꾼 뒤의 게임은 사실상 처음 보는 게임이 되고,
그때 비로소 커뮤니티가 무엇에 반응하는지 알 수 있다.

### 같은 엔진을 언어를 바꿔 다시 쓰는 것은 학습 방식이지 제품 전략은 아니다

VB6, C++, JavaScript, Go로 이어진 재작성 이력은 강력한 학습 방법이다.
같은 문제를 다른 도구로 풀어 보면 무엇이 도구 탓이고 무엇이 설계 탓이었는지가
드러난다.
저자가 왜 그렇게 동작하는지를 이해했다고 말하는 것도 이 반복 덕분일 것이다.

하지만 제품을 내는 관점에서 재작성은 매번 출시 시계를 처음으로 되돌린다.
엔진을 만들다 게임을 끝내지 못한다는 개발자 사이의 오래된 통념이
정확히 이 지점을 가리킨다.
저자가 첫 공개 버전을 오프라인 모드로 낼지 고민하는 것은 이 위험을 본인도
감지하고 있다는 신호로 읽을 수 있다(해석).

이 저장소의 `game/open-mmo.md`가 다루는 OpenMMO는 반대 극단에 있다.
그쪽은 AI 도구로 빠르게 만들어 플레이 가능한 서버부터 열었다.
두 사례를 나란히 두면, 개인 MMO에서 손으로 다듬은 엔진과 빨리 열린 서버 중
무엇이 커뮤니티를 먼저 모으는지가 앞으로 지켜볼 질문이 된다.

### 오픈소스 계보에서 태어난 프로젝트는 오픈소스로 돌려줄 때 가장 큰 힘을 얻는다

Argentum Online이 오래 살아남은 이유 중 하나는
코드가 공개되어 수많은 파생 서버와 커뮤니티가 생겼기 때문이다.
스페인어 Wikipedia는 라이선스 변경 이후 수많은 AO 파생 프로젝트가 생겼고,
2005년 만들어진 GS-Zone 포럼이 그 코드들을 보존해 왔다고 적는다.
저자 자신도 공개된 AO와 ORE의 코드를 연구하고 다시 만들어 보며 엔진을 배웠다.

그런데 저자의 현재 프로젝트는 저장소가 다섯 개라고 말할 뿐 어느 것도 공개하지
않았고, UI 툴킷은 관심이 모이면 공개할 수도 있다는 조건부 약속에 머문다.
기여자가 장벽 없이 협업하는 커뮤니티를 지향한다는 결론과,
코드 없이 영상과 Discord로만 연결하는 현재 상태 사이에는 간격이 있다.

이 간격을 메우는 가장 짧은 길은 아마 엔진과 UI 툴킷을 게임과 분리해 먼저
공개하는 것이다.
저자가 엔진을 별도 저장소로 떼어 내려는 계획과도 맞고,
Go 생태계에 SDL2 기반 UI 툴킷이라는 구체적인 기여를 남긴다.
게임의 콘텐츠와 이름은 비공개로 두더라도 엔진을 열면,
저자가 AO에서 받은 것을 같은 방식으로 다음 세대에게 돌려주는 셈이 된다(해석).

### MMO라는 이름이 설계 결정을 먼저 끌어당긴다

MMO를 목표로 정하면 아직 필요 없는 결정들이 앞당겨진다.
강타입 메시지 계약, 클라우드 인프라, 확장 가능한 서버 구조 같은 것들이다.
이 글에서도 게임 이름과 메커니즘보다 VPC와 ECR이 먼저 정해졌다.

이 현상은 스타트업이 사용자 한 명 없이 쿠버네티스부터 구성하는 패턴과 닮았다.
확장성을 위한 결정은 대체로 되돌리기 어렵고,
실제 부하가 어디서 오는지 모르는 상태에서 내린 결정은
엉뚱한 곳을 단단하게 만든다.
`game/modak-online.md`의 사례처럼 실제 병목이 대역폭이었다면,
코드 수준의 확장성보다 패킷 설계와 전송 주기가 먼저였을 것이다.

저자가 오프라인 모드 우선 출시를 진지하게 고민한다면,
그것은 후퇴가 아니라 순서를 바로잡는 일일 수 있다.
게임이 재미있는지 먼저 확인하고,
그다음에 몇 명이 함께 즐길 수 있는지를 측정하는 순서다.
