# PS2 Web Recomp: 에뮬레이터 없이 PS2 게임을 WebAssembly로 미리 옮겨 브라우저에서 돌리는 프로젝트

<https://github.com/snuri00/ps2-web-recomp>

Show HN: [PS2 games statically recompiled to WebAssembly](https://news.ycombinator.com/item?id=50052251) (123점, 68개 댓글)

## 소개

PS2 Web Recomp는 PlayStation 2 게임을 에뮬레이터 없이 브라우저에서
실행하는 프로젝트다.
게임의 Emotion Engine 기계어를 미리 C++로 번역하고,
그것을 WebAssembly로 컴파일한 뒤,
PS2의 운영체제와 하드웨어를 재구현하고 WebGPU로 그리는 런타임에 링크한다.
저장소는 2026년 10월 8일에 만들어졌고 MIT 라이선스이며,
같은 저자의 psp-web-recomp와 같은 방법을 따른다.

### 지금까지 올라온 게임

첫 대상은 Gran Turismo 4다.
두 벡터 유닛을 모두 쓰고,
리플레이와 라이선스 시험이 정확한 부동소수점 동작에 기대며,
렌더링한 이미지를 다시 팔레트로 읽는 그래픽 기법까지 쓰는,
PS2에서 가장 까다로운 게임 중 하나라서 골랐다고 한다.
부팅부터 오프닝 영상, 메뉴, 레이스까지 음악과 효과음과 함께 돌아가고,
브라우저에 보관하는 메모리 카드에 저장된다.
노트북 내장 GPU의 Chrome에서 PS2 해상도의 두 배로
PAL판 기준 초당 50프레임을 낸다.

두 번째로 올린 God of War II는 게임 전용 코드 없이 같은 스크립트로 변환되었다.
대신 Gran Turismo 4가 건드리지 않았던 버그 두 개,
즉 재컴파일러 버그 하나와 벡터 유닛 타이밍 버그 하나를 드러냈고,
I/O 프로세서 쪽에서 빠진 부분 몇 가지도 채워야 했다.
지금은 메뉴에서 컷신을 거쳐 전투까지 진행되며,
PS2 해상도에서는 격한 전투에서도 초당 60프레임,
두 배 해상도에서는 48~60프레임을 낸다.

저장소에는 게임 데이터가 들어 있지 않다.
사용자가 가진 디스크 이미지를 넣으면
저장소의 스크립트가 자기 컴퓨터에서 웹 페이지로 바꾼다.

### 동작 방식

| 구성 요소         | 처리 방식                                                                                                |
| ----------------- | -------------------------------------------------------------------------------------------------------- |
| EE(R5900) 코드    | `eerecomp`가 제어 흐름을 따라 함수를 찾고 16KiB 단위로 C++ 생성                                          |
| EE 쪽 커널        | 스레드, 세마포어, 인터럽트 핸들러, SIF 채널을 고수준 에뮬레이션                                          |
| I/O 프로세서(IOP) | 디스크의 IRX 모듈은 R3000 인터프리터로, IOP 커널과 라이브러리는 C++ 재구현                               |
| 벡터 유닛 1(VU1)  | 테스트 실행에서 본 마이크로프로그램은 SIMD C++로 미리 컴파일, 처음 보는 것은 즉석에서 WebAssembly로 번역 |
| 그래픽(GS)        | 4MB 비디오 메모리를 GPU에 그대로 두고 WebGPU 컴퓨트 셰이더로 래스터화                                    |
| 소리와 영상       | SPU2 48보이스 재구현, AudioWorklet 출력, IPU(MPEG-2 디코더) 구현                                         |
| 디스크            | HTTP Range 요청으로 필요한 부분만 읽고 실행 파일만 먼저 내려받음                                         |

생성 코드는 R5900의 특이한 동작을 그대로 지킨다.
128비트 레지스터와 그 위의 멀티미디어 명령, 분기 지연 슬롯,
무한대와 비정규수가 없고 IEEE와 다르게 반올림하는 PS2 부동소수점,
코프로세서로 쓰는 벡터 유닛 0까지 포함한다.
단위 사이의 점프는 꼬리 호출이 되고,
스레드 전환은 호스트 스택을 풀고 게스트 주소에서 다시 시작하므로
게스트 스레드마다 스택을 둘 필요가 없다.

벡터 유닛 1의 마이크로프로그램은
PS2와 비트 단위로 같은 부동소수점 연산으로 돌고,
MAC, 상태, 클립 플래그의 파이프라인 지연까지 모델링한다.
게임이 그 지연에 맞춰 코드를 짜기 때문이다.
그래픽은 GS의 텍스처링, 팔레트, 알파 블렌딩, 깊이와 대상 알파 검사 규칙으로
타일 단위 래스터화를 하고,
GPU 출력과 비교할 기준으로 같은 GS의 소프트웨어 래스터라이저를 남겨 두었다.
에뮬레이션, 벡터 유닛 1, 페이지 스레드가 각각 다른 스레드에서 돈다.

### 빠르게 만든 과정

처음 레이스는 소프트웨어 래스터라이저와 벡터 유닛 인터프리터로
네이티브에서 초당 3프레임이었다.
GS를 WebGPU 컴퓨트 셰이더로 옮기고
벡터 유닛 프로그램을 컴파일해 약 70프레임이 되었고,
그 뒤의 작업은 대부분 에뮬레이션이 아니라
브라우저가 시간을 쓰는 곳을 줄이는 일이었다.

| 문제                                                              | 해결                                                                | 결과                        |
| ----------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------- |
| 텍스처 업로드마다 삼각형 묶음이 나뉘어 프레임당 약 650회 디스패치 | 의존하지 않는 삼각형 앞으로 업로드를 끌어올림                       | 약 80회                     |
| 레이스 중 매 프레임 같은 3MB 텍스처 업로드                        | GPU 쪽 16MB 최근 업로드 캐시                                        | 프레임당 전송량 약 60% 감소 |
| 3배 해상도에서 23프레임                                           | 삼각형 설정을 분기 밖에서 균일하게 읽고, 프레임 데이터를 한 번에 씀 | 48~50프레임                 |
| 중첩 `setTimeout`의 4ms 하한                                      | `MessageChannel`로 양보                                             | 루프 지연 제거              |
| 레이스가 40~50프레임 사이에서 흔들림                              | 에뮬레이션을 워커로 옮기고 페이지 스레드는 GPU만 담당               | 50프레임 고정               |

### 게임 하나를 직접 옮기기

git, CMake, Ninja, C++20 컴파일러(clang 우선), Python 3가 필요하고,
모든 작업은 x86-64 Linux에서 돌려 봤다.
첫 실행 때 Emscripten SDK와 헤드리스 테스트용 wgpu-native를 받는다.
게임 하나당 생성 코드와 빌드에 약 300MB가 든다.

```bash
git clone https://github.com/snuri00/ps2-web-recomp.git
cd ps2-web-recomp
scripts/port.sh mygame "My Game.iso"
python3 scripts/serve.py build/web-mygame games/mygame/disc.iso    # http://localhost:8620/
```

`port.sh`는 디스크의 `SYSTEM.CNF`가 가리키는 부팅 프로그램을 번역한 뒤
게임을 헤드리스로 여러 번 돌린다.
정적 분석으로는 함수 포인터로만 닿는 함수를 다 찾지 못하므로,
실행마다 찾지 못한 주소를 기록해 진입점으로 추가하고 다시 번역하며,
새 주소가 나오지 않을 때까지 반복한다.
같은 실행에서 게임이 올리는 벡터 유닛 마이크로프로그램도 기록해 미리 컴파일한다.
탐색 실행은 시작 버튼을 누른 뒤 5초마다 X 버튼을 눌러 타이틀 화면을 넘기고,
God of War II는 8코어 노트북에서 ISO부터 페이지까지 3분 30초가 걸린다.

README는 기대치를 낮춰 두라고 말한다.
지금까지 올라온 게임은 두 개이고,
다른 게임은 아직 아무도 구현하지 않은 시스템 콜이나 IOP 라이브러리 함수,
렌더러가 처리하지 못하는 GS 기능에서 멈출 가능성이 크다.

### 브라우저, 네이티브, 저장, 배포

페이지는 WebGPU가 필요하다.
Linux의 Chrome에서는 기본으로 꺼져 있어 플래그를 켜야 하고,
WebGPU가 없으면 소프트웨어 렌더러로 넘어가는데 3D에는 너무 느리다.
게임패드의 아날로그 트리거는 DualShock 2의 압력 감지 L2와 R2로 전달된다.

같은 빌드가 만드는 네이티브 실행 파일 `ps2run`은 SDL2가 있으면
창에서 게임을 돌린다.
Vulkan 위의 wgpu-native로 그리고,
에뮬레이션, 벡터 유닛 1, GS를 각각 스레드로 나누면
God of War II가 네이티브 해상도에서 43프레임에서 60프레임으로 오른다.

메모리 카드는 브라우저 저장소에 보관되고,
PCSX2와 같은 `.ps2` 형식으로 내보내고 가져올 수 있다.
페이지는 스레드에 SharedArrayBuffer를 쓰므로
`Cross-Origin-Opener-Policy`와 `Cross-Origin-Embedder-Policy` 헤더를 보내는
교차 출처 격리 환경에서 제공해야 하며, `scripts/serve.py`가 이를 처리한다.

### 법적 경계

저장소에는 원본 코드와 각자의 라이선스를 가진 서드파티 코드만 있다.
README는 생성된 C++와 빌드된 WebAssembly가 게임 실행 파일의 번역물이므로
게임 소유자에게 속한다고 명시하고,
자기 컴퓨터에만 두고 공개하지 말라고 한다.
서버에 접근할 수 있는 사람은 누구나 게임을 불러올 수 있으니
혼자만 쓰라는 경고도 있다.

## 분석

### 정적 재컴파일은 에뮬레이션의 비용을 실행 시점에서 빌드 시점으로 옮긴다

에뮬레이터는 게임을 실행하는 동안 매 명령을 해석하거나 그때그때 번역한다.
PS2 Web Recomp는 그 일을 실행 전에 끝낸다.
게임의 실행 파일을 미리 C++로 바꾸고,
C++ 컴파일러와 WebAssembly 엔진이라는
이미 고도로 최적화된 도구에 나머지를 맡긴다.
그래서 브라우저가 실제로 하는 일은 번역이 아니라 일반적인 WebAssembly 실행이다.

이 방식은 공짜가 아니다.
정적 분석으로는 함수 포인터로만 닿는 코드를 다 찾을 수 없어서,
`port.sh`는 게임을 여러 번 실제로 돌려 보며 빠진 진입점을 모은다.
벡터 유닛 마이크로프로그램은 실행 파일에 들어 있지 않고 게임이 DMA로 올리므로,
테스트 실행에서 본 것은 미리 컴파일하고 처음 보는 것은 페이지에서 즉석 번역한다.
결국 이 프로젝트는 “정적”이라는 이름과 달리
정적 번역, 동적 탐색, 소량의 JIT를 섞은 혼합 파이프라인이다.

저자 deadxwarrior는 HN에서 타이밍을 어떻게 다루느냐는 질문에
사이클 단위로 정확하지 않으며 지금까지는 그럴 필요가 없었다고
답했다.[^danxbuild][^deadxwarrior-timing]
번역된 각 블록이 자기 명령 수만큼 사이클 예산을 빼고,
인터럽트, 타이머, DMA, 수직 귀선 같은 사건은 하나의 가상 시계 위에서
블록 경계마다 전달된다.
대부분의 게임은 사이클 수가 아니라 인터럽트와 세마포어로 동기화하므로
순서만 맞으면 타이밍은 근사여도 된다는 것이다.
타이밍에 기대는 게임이 있으면 특정 버그로 드러나고,
NTSC 게임에 PAL 주기로 설정한 HBLANK 타이머가 그런 예였다.

### 두 번째 게임이 첫 번째 게임보다 더 많은 것을 알려 준다

README에서 가장 흥미로운 부분은 God of War II를 올린 과정이다.
게임 전용 코드는 하나도 필요하지 않았지만,
두 번째 게임은 첫 번째 게임이 우연히 피해 간 버그를 정확히 짚었다.
16KiB 단위의 마지막 명령이 분기일 때 분기하지 않는 경로가
지연 슬롯 다음이 아니라 지연 슬롯에서 이어져
명령을 두 번 실행하던 재컴파일러 버그,
그리고 `CLIP` 뒤 세 명령 만에 클립 플래그를 읽는 마이크로코드를
네 명령 뒤에야 보이게 만들던 벡터 유닛 모델 버그다.

이 경험은 호환성 계층을 만드는 일의 본질을 보여 준다.
테스트 대상 하나로는 구현이 맞는지 알 수 없고,
그 대상이 쓰지 않은 경로는 맞는지 틀린지조차 판단할 수 없다.
Gran Turismo 4는 마이크로코드가 늘 더 오래 기다렸기 때문에
틀린 지연 모델에서도 정상으로 보였다.
README가 기대치를 낮춰 두라고 경고하는 이유가 여기에 있다.

### 성능 작업의 대부분은 에뮬레이션이 아니라 브라우저와의 경계였다

초당 3프레임에서 70프레임까지는 에뮬레이션 자체를 바꾼 결과였지만,
그다음의 개선은 모두 경계에서 나왔다.
GPU 디스패치 수, WebAssembly와 GPU 사이의 전송량,
셰이더의 분기 발산, Chrome 페이지 스레드를 막는 업로드 크기,
`setTimeout`의 4ms 하한, 워커 분리가 그 목록이다.

이 목록은 웹을 실행 플랫폼으로 쓰는 다른 프로젝트에도 그대로 적용된다.
연산이 충분히 빨라진 뒤에는
호출 횟수와 복사량, 스레드 사이의 대기가 프레임 시간을 결정한다.
같은 폴더의 [demoscene-recomp](demoscene-recomp.md)가
DOS 데모의 타이밍을 보존하는 데 집중했다면,
PS2 Web Recomp는 같은 문제를 브라우저의 스케줄러와 GPU 큐까지 넓혀서 다룬다.

## 비평

### “에뮬레이터 없이”라는 문구는 절반만 참이다

README의 첫 문장은 “without an emulator”다.
그러나 같은 README가 설명하듯 I/O 프로세서는
디스크의 IRX 모듈을 R3000 인터프리터로 돌리고,
처음 보는 벡터 유닛 프로그램은 JIT로 번역하며,
GS, DMA, VIF, SPU2, CDVD 같은 하드웨어는 모두 런타임이 모델링한다.
HN에서 krystalgamer가
“핵심 시스템 구성 요소를 여전히 에뮬레이션하는 또 하나의 recomp”라고
꼬집은 것도 이 지점이다.[^krystalgamer]

저자는 IOP가 인터프리터로 돈다는 점을 인정하면서 근거를 댔다.
IOP는 PS1급 I/O CPU이고 여기서는 게임이 디스크에 싣고 온
사운드, 패드, 메모리 카드 드라이버 모듈만 돌리며,
IOP 커널과 Sony 핵심 라이브러리 20개는 네이티브로 재구현했다.
God of War II 전투에서 이 인터프리터는 CPU 시간의 약 2%여서
아직 재컴파일할 가치가 없었다는 것이다.
EE 게임 코드는 전부 AOT로 번역되어 인터프리터로 물러나는 경로가 없고,
하드웨어 모델링은 N64Recomp가 RDP에 RT64를 쓰듯
모든 recomp가 해야 하는 일이라고 덧붙였다.[^deadxwarrior-iop]

이 답은 기술적으로 타당하지만, 문구의 문제를 해결하지는 않는다.
정확한 표현은 “게임 코드는 재컴파일하고 시스템은 재구현했다”이며,
PCSX2와의 차이는 에뮬레이션의 유무가 아니라 어디에 번역 비용을 두느냐다.
popcar2는 실행 파일에 에뮬레이터를 넣고
“네이티브 이식”이라고 홍보하는 프로젝트가 늘어
진짜 재컴파일을 찾기 어려워졌다고 불평했다.[^popcar2]
이런 맥락에서는 경계를 정확히 말하는 것이 프로젝트의 신뢰를 지키는 일이다.

### 두 게임으로는 일반화 가능성을 말할 수 없다

README는 이 점을 스스로 인정하지만, 이 한계는 생각보다 크다.
God of War II 하나를 더 올리는 데 재컴파일러 버그, 벡터 유닛 타이밍 버그,
구현되지 않은 IOP 하드웨어 타이머, BIOS 같은 부팅 경로,
메모리에서 불러오는 모듈, 스크래치패드 DMA의 대상 체인 모드가 필요했다.
게임 하나가 버그 두 개와 빠진 기능 서너 개를 드러냈다면,
PS2 라이브러리 수천 개를 생각할 때 남은 작업량은 짐작하기 어렵다.

PCSX2가 20년 넘게 쌓은 호환성 목록은
바로 이런 게임별 차이를 하나씩 메운 결과다.
정적 재컴파일은 성능 면에서 유리하지만
호환성 문제를 피해 가지 못하며,
오히려 실행 전에 모든 경로를 찾아야 한다는 부담을 더한다.
`port.sh`의 탐색 실행은 시작 버튼과 X 버튼만 누르므로,
게임 후반부에서만 쓰이는 코드나 특정 모드의 마이크로프로그램은
실제 플레이 중에야 드러날 수 있다.

### 법적 경고는 개인 사용에서만 성립하는 배포 모델을 만든다

README는 생성된 코드가 게임 소유자에게 속하므로 공개하지 말고,
서버에 접근하는 누구나 게임을 불러올 수 있으니 혼자 쓰라고 경고한다.
HN에서 GitHub Pages로 바로 해 볼 수는 없느냐는 질문이 나오자
svantana와 rvz는 게임이 저작물이라 그런 페이지는 DMCA 요청을 받는다고
답했다.[^simonmales][^svantana][^rvz-dmca]

이 제약은 프로젝트의 가장 큰 매력,
즉 브라우저에서 바로 실행된다는 장점을 크게 줄인다.
사용자는 Linux 개발 환경을 갖추고, Emscripten을 받고,
게임당 300MB의 빌드를 직접 만든 뒤 로컬 서버를 띄워야 한다.
이 과정을 거칠 수 있는 사람이라면 대부분 PCSX2도 쓸 수 있다.
저자는 재컴파일러가 WebAssembly를 직접 내보내게 해서
사용자가 고른 ISO를
브라우저 안에서 변환하는 방향을 언급했지만,[^deadxwarrior-wasm]
지금 상태의 “브라우저에서 PS2 게임”은 개발자의 로컬 실험에 가깝다.

## 인사이트

### AI가 만든 재컴파일 프로젝트의 진짜 쟁점은 저작권보다 검증 가능성이다

HN 스레드에는 AI가 이런 recomp 프로젝트를 쏟아 내게 만들었다는 반응이 많았다.
xyzsparetimexyz는 이런 AI 프로젝트에 거짓말이 많다며
사람이 수정할 수 있는 100% 일치 디컴파일을 보고 싶다고 했고,[^xyzsparetimexyz]
rvz는 Claude를 쓰는 개발자 대부분이 코드도 README도 읽지 않는다는 증거라고
비꼬았다.[^rvz-ai]
Elizer0x0309는 쉽게 “훔쳐질” 수 있다면
게임 회사가 투자할 유인이 있느냐고 물었고,
treyd는 게임에서 어렵고 값진 부분은 코드 작성이 아니라 나머지 전부라며
“훔친다”는 표현에 반대했다.[^Elizer0x0309][^treyd]

그러나 이 프로젝트에서 눈여겨볼 점은 저작권보다 검증 장치다.
README는 GPU 렌더러와 비교할 기준으로 소프트웨어 래스터라이저를 남겨 두었고,
게임을 헤드리스로 여러 번 돌려 화면을 `shots` 폴더에 남기며,
버그를 하드웨어 와치포인트로 추적한 과정을 구체적으로 적었다.
AI가 코드를 빨리 쓰게 해 줄수록,
그 코드가 원래 하드웨어처럼 동작하는지 확인하는 장치의 비중이 커진다.
recomp 프로젝트의 품질은 앞으로 “얼마나 많은 게임이 도는가”보다
“어떻게 맞는지 확인하는가”로 갈릴 것이다.

### 재컴파일은 게임 보존을 에뮬레이터 중심에서 게임별 이식 중심으로 옮긴다

에뮬레이터는 플랫폼 하나를 한 번 구현해 모든 게임을 돌리려는 접근이다.
정적 재컴파일은 게임마다 별도의 산출물을 만든다.
N64Recomp로 시작된 흐름이 PSP, PS2, PS Vita로 번지면서,
보존의 단위가 플랫폼에서 개별 게임으로 바뀌고 있다.
HN에서 kodablah는 PS Vita용으로 ARM을 WebAssembly로 바꾸는 범용 트랜스파일러를
WebAssembly 안에서 돌리는 vitaslop을 소개했는데,[^kodablah]
이는 게임별 이식과 범용 에뮬레이터 사이의 중간 지점을 찾는 시도다.

이 변화의 2차 효과는 수정 가능성이다.
번역된 C++가 있으면 해상도, 프레임 제한, 입력 방식을 게임 단위로 고칠 수 있다.
easyThrowaway는 Gran Turismo를 압력 감지 버튼 없이 하면
비참하다고 했는데,[^easyThrowaway]
README는 이미 게임패드의 아날로그 트리거를
DualShock 2의 압력 감지 L2와 R2로 넘긴다.
에뮬레이터라면 범용 설정으로 풀어야 했을 문제를,
게임 단위 이식은 그 게임에 맞게 직접 해결할 수 있다.
반대로 게임마다 산출물이 따로 생기므로,
버그 수정이 모든 게임에 한 번에 퍼지는 에뮬레이터의 장점은 약해진다.

### 웹이 콘솔급 런타임이 되었다는 신호는 성능보다 스레드와 격리 요구에 있다

이 프로젝트가 브라우저에서 PS2 게임을 60프레임으로 돌린다는 사실은 인상적이지만,
더 의미 있는 신호는 요구 사항 목록이다.
SharedArrayBuffer를 쓰는 다중 스레드, AudioWorklet, WebGPU 컴퓨트 셰이더,
교차 출처 격리 헤더, 게임패드 진동 API까지 필요하다.
웹은 더 이상 문서 플랫폼이 아니라,
콘솔의 CPU, 벡터 유닛, GPU를 각각 다른 스레드로 나눠 돌리는 실행 환경이 되었다.

이 요구 사항은 배포 장벽이기도 하다.
교차 출처 격리를 하려면 서버가 특정 헤더를 보내야 하고,
Linux Chrome에서는 WebGPU를 플래그로 켜야 하며,
듀얼 GPU 노트북에서는 캔버스가 화면에 안 보이는 경우까지 대비해야 한다.
“링크 하나로 실행”이라는 웹의 약속은
고성능 애플리케이션에서는 서버 설정과
브라우저 지원이라는 조건부 약속으로 바뀌었다.
저자도 Steam Deck용으로는 네이티브 Linux 빌드를 쓰라고
권했는데,[^deadxwarrior-deck]
같은 코드가 웹과 네이티브 양쪽으로 빌드되는 구조가
결국 웹의 조건을 우회하는 탈출구 역할을 한다는 점이 이를 보여 준다.
