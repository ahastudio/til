# use cache 기본 메모리 제한 토론

원문: [Clarification on use cache default memory limits and cacheMaxMemorySize behavior](https://github.com/vercel/next.js/discussions/88078)

## 요약

2026년 1월 4일 vercel/next.js의 App Router 범주에 ale-grosselle이 올린 토론 #88078이다.

질문자는 `use cache`를 시험하며 기본 캐시 핸들러가 대규모 사용에서 메모리를 어떻게 다루는지 알고 싶다고 쓴다.
수백만 개 광고가 있는 마켓플레이스를 가정해 광고 상세 페이지 전체를 캐시하는 최소 재현과 배포 데모를 링크한다.
`NODE_OPTIONS=--max-old-space-size=200 next start`로 메모리를 제한하고 부하 시험을 돌리면 프로세스가 `FATAL ERROR: Ineffective mark-compacts near heap limit`와 `Allocation failed - JavaScript heap out of memory`로 죽고, 제한이 없으면 캐시가 프로세스 한도까지 계속 커진다고 한다.
질문은 네 가지이다. 기본 `cacheMaxMemorySize`는 얼마인가, 어떻게 정해지며 Node 힙 한도와 이어지는가, 힙 한도까지 커지는 것이 의도된 동작인가, 큰 규모의 캐싱에 맞는 전략은 무엇인가. 글에 Next.js 버전은 적혀 있지 않다.

답은 0xpourya가 1월 5일에 달았다(추천 1, 채택 표시 없음).

- 기본 한도는 고정값이 없다. `cacheMaxMemorySize`를 명시하지 않으면 기본 핸들러는 사실상 무제한이고 Node 힙, 운영체제나 컨테이너 메모리, 플랫폼 한도에만 제한된다.
- 힙의 비율로 정해지지 않고 Node 힙 한도와 이어지지 않는다. LRU 비슷한 메모리 저장소이며 `cacheMaxMemorySize`가 있을 때만 퇴출하고 `--max-old-space-size`를 무시하며 GC 압력에 반응하지 않는다.
- 힙 한도까지 커지는 것이 의도된 동작이고 글의 충돌은 예상된 것이다.
- `use cache`는 마켓플레이스 규모나 무제한이나 엔터티별 전체 페이지 캐싱을 위해 설계되지 않았다. 메모리에 두려면 `cacheMaxMemorySize`를 엄격한 바이트 한도로 두어 충돌 대신 결정적 퇴출을 얻으라고 권한다.

대화에서 질문자가 0xpourya에게 `use cache`를 만든 사람인지 묻자, 0xpourya는 Next.js 코어 팀이 아니고 `use cache`를 구현하지 않았으며 현재 소스를 읽고 로컬에서 재현하고 Node.js 메모리 경험으로 답했다고 밝혔다.
질문자가 프로세스 안 캐시가 인스턴스 사이에 공유되지 않고 영속적이지도 않고 메모리가 한정되지 않는데 실제 비용 절감이 있는지 묻자, 0xpourya는 AWS의 Redis 캐시가 들어오는 트래픽을 맡아 대부분의 요청이 계산 계층에 닿지 않게 하는 자신의 구성을 설명했다.

## 분석

### 쟁점은 기본값이 무엇이냐가 아니라 기본값이 없다는 것이다

질문의 첫 두 항목은 기본 한도의 값과 산출 방식이었고 답은 한도가 없다는 것이다.
따라서 이 토론이 알려 주는 핵심은 설정값이 아니라 기본 핸들러가 무한 성장 구조라는 점이다.
이는 토론의 서술을 이 문서가 정리한 것이다.

### 도구가 해결하는 문제와 질문자의 문제가 다르다

질문자는 대규모 전체 페이지 캐싱을 가정했고 답은 그것이 설계 범위 밖이라고 한다.
기본 핸들러는 프로세스 로컬 캐시이므로 큰 규모에는 외부 캐시 계층을 둔다는 것이 답변자의 해법이다. 이는 이 문서의 해석이다.

## 비평

### 답변이 공식 답이 아니다

답은 코어 팀이 아닌 사용자가 소스를 읽고 쓴 것이고 답 표시도 없다.

### 재현의 조건이 좁다

충돌은 힙을 200MB로 제한한 상태의 부하 시험에서 나온 것이다.
광고 수백만 개 규모라는 가정은 시험 스크립트로 흉내 낸 것이고 실제 서비스의 접근 분포는 아니다.

### 비용 절감의 질문이 열려 있다

프로세스 로컬 캐시가 여러 인스턴스에 공유되지 않는 구조에서 `use cache`가 비용을 얼마나 줄이는지에 대한 답은 Redis 같은 외부 계층을 쓰는 한 사용자의 구성 설명에 그친다.
`use cache`만으로의 효과는 토론에서 확인되지 않았다.

### 외부 반응

Lobste.rs에서는 `next.js memory` 검색이 14,308건의 관련 없는 결과를 돌려줘 이 토론의 유무를 판단하지 못했다. 이 문서는 Lobste.rs에 글이 없다고 단정하지 않는다.
GeekNews에서는 `cacheMaxMemorySize`와 `Next.js OOM Kubernetes`가 결과 없음이었고 대조 쿼리는 정상이었으며 이 토론의 토픽은 없었다.

## 인사이트

### 가져갈 것은 캐시에 한도를 명시하는 습관이다

프로세스 안 캐시는 한도를 정하지 않으면 사실상 무제한이다.
`cacheMaxMemorySize` 같은 한도를 바이트로 정하면 충돌 대신 퇴출이라는 예측 가능한 실패를 얻는다. 이는 이 문서의 적용이다.

### 규모가 크면 프로세스 밖 캐시를 둔다

여러 인스턴스와 영속성이 필요하면 프로세스 로컬 캐시보다 공유 캐시 계층이 맞다는 것이 토론의 방향이다.
같은 문제가 `nextjs/opennext.md`의 캐싱 논의와도 이어진다.

### 확인할 관찰

이 토론의 주장을 가를 관찰은 세 가지이다.
현재 버전의 기본 핸들러가 정말 무제한인지,
`cacheMaxMemorySize`를 둔 상태의 같은 부하에서의 동작,
외부 캐시 계층을 둔 구성에서의 비용 변화이다.
