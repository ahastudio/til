# Next.js 16 메모리 누수 OOM 토론

원문: [Memory Leak Issue in Next.js 16.1.0 Causing OOM Crashes in Docker/Kubernetes Environment](https://github.com/vercel/next.js/discussions/88603)

## 요약

2026년 1월 15일 vercel/next.js의 Help 범주에 rameesac이 올린 토론 #88603이다. 이 문서가 읽은 시점에는 열려 있고 채택된 답이 없으며 마지막 갱신은 2026년 9월 30일이다. API는 댓글 23개를 알리고 페이지는 댓글 8개와 답글 15개로 표시하며, 페이지에서 답글 9개가 접혀 있어 이 문서는 전체를 읽지 못했다.

제목은 16.1.0인데 본문의 버전 칸은 16.0.1이다. 질문자는 Docker 컨테이너를 Kubernetes에서 돌리는데 몇 시간에 걸쳐 메모리가 꾸준히 늘어 OOMKilled와 파드 재시작이 생긴다고 쓴다.
루트 서버 컴포넌트에서 `await connection()`으로 환경 변수를 불러 `EnvProvider`에 넘기고, 쿠버네티스 liveness probe가 10초마다 `GET /ready` API 라우트를 부른다. 다른 사람들도 16.x에서 겪는지, 디버깅 조언을 구한다. 메모리 그래프와 코드는 스크린샷이라 읽지 못했다.

이후 댓글을 시간순으로 정리하면 다음과 같다.

- ismaildasci(1월 17일): 루트 레이아웃의 `connection()`이 캐싱을 일으킬 수 있으니 환경 변수 로드를 미들웨어나 `next.config`로 옮기고, 프로바이더 값을 메모이즈하고, `/ready`를 단순하게 두고, `output: "standalone"`과 힙 스냅샷, `NODE_OPTIONS`로 힙 제한을 시도하라고 했다. 이 댓글은 비추천 반응 4를 받았다.
- icyJoseph(코어 협력자, 1월 27일): 진행 상황을 묻고 이미지 최적화 끄기, `--max-old-space-size` 조정(컨테이너 한도의 50에서 75%, AI 제안이라고 표시), 전역 데이터 유지 피하기, standalone, 최신 Node와 Next를 제안했다.
- blf885(2월 26일): 이미지 최적화를 끄고 힙을 6GB로 올려도 같은 증가가 있고 `cacheMaxMemorySize`를 0과 128MB로 둬도 효과가 없다고 했다. Node 22.14.0, Next 16.1.6이다. 이 댓글 아래 답글 14개 중 9개가 접혀 있다. 보이는 답글에서 hotrungnhan은 16.2.3과 16.2.1-canary.32에서도 지속된다고 했고, icyJoseph는 많은 OOM 보고가 지속적인 부하에서 GC가 돌지 않는 것이라며 재현 저장소를 요청했다. joshunger는 `--expose-gc`와 `app/api/gc` 라우트, 부하 시험을 제안했고 나중에 부하에서 `React.cache`를 의심한다고 했다. hotrungnhan은 `instrumentation.ts`에서 60초마다 GC를 돌리면 증가가 느려지지만 계속 오른다고 했다.
- PayteR(8월 25일): 16.2.3, App Router, 사용자 지정 Node 서버에서 요청당 약 0.5에서 1MB가 강제 GC 뒤에도 남는다고 했다. Node 22와 Bun, 16.3.3에서도 재현되고, 유지자 분석이 React 캐시의 모듈 범위 `Map`과 `WeakMap` 구조와 요청당 약 225개의 `AsyncLocalStorage` 항목을 가리킨다고 한다. 완화책은 RSS 감시자가 일찍 재시작하는 것이다. pkpio(8월 26일)도 같은 문제를 Next 프레임워크로 좁혔고 로드밸런서 뒤에서 감시자 재시작을 쓴다.
- FreQll(9월 7일): 같은 문제가 있다.
- mikeflame(9월 30일): 감시자 재시작이 누수를 고치지 못한다고 하며 종료 코드 134(V8 힙 한도), 137(cgroup OOMKilled), 143(Next SIGTERM 처리)을 구분한다. Node의 기본 힙은 cgroup 한도의 약 절반이고 2GB로 상한이 있다고 하며 `--max-old-space-size`를 컨테이너 한도의 약 70에서 75%로 권한다. 프로세스별로 무작위화한 RSS 임계값, 최대 가동 시간 교체, liveness에만 쓰는 감시자, 메모리와 무관한 readiness probe, 노드에 걸친 복제본 분산을 권하고 `topologySpreadConstraints`와 `preStop` 예를 든다. React 저장소의 열린 이슈를 링크한다.

## 분석

### 쟁점은 한도 구성이 아니라 요청당 남는 메모리이다

2023년의 토론(`nextjs/oom-kubernetes-discussion.md`)에서 질문자는 결국 한도 구성과 느긋한 GC를 원인으로 짚었다.
이 토론의 후반 댓글은 강제 GC 뒤에도 요청당 0.5에서 1MB가 남는다고 해서 단순한 한도 문제를 넘는 구조적 증상으로 읽힌다.
이는 댓글의 서술을 이 문서가 정리한 것이다.

### 작성자들의 진단이 서로 다른 층에 있다

원 글에는 `connection()`과 환경 변수 프로바이더, 한 댓글은 `React.cache`와 비동기 지역 저장소, 한 댓글은 쿠버네티스 한도 구성, 한 댓글은 GC 미작동을 든다.
어느 진단이 맞는지는 토론에서 확정되지 않았다. 이는 이 문서의 관찰이다.

## 비평

### 근거가 개인 보고와 스크린샷에 기댄다

댓글들의 수치(요청당 0.5에서 1MB, 225개 항목)는 보고자의 분석이고 이 문서가 재현하거나 확인하지 못했다.
원 글의 증거는 읽을 수 없는 스크린샷이다. 접힌 답글 9개의 내용은 알 수 없다.

### 완화책이 증상 관리에 머문다

RSS 감시자와 일찍 재시작, 가동 시간 교체는 증가를 막지 못하고 터지기 전에 죽이는 방법이다.
댓글 하나가 이를 직접 지적한다. 근본 원인의 수정은 이 토론에서 확인되지 않는다.

### AI 제안과 비추천을 받은 조언이 섞여 있다

협력자가 힙 비율 조언에 AI 제안이라고 표시한 점은 투명하지만 근거 수준을 낮춘다.
첫 댓글은 `connection()`이 캐싱할 수 있다는 가설을 세웠으나 비추천 4를 받았다. 비추천 이유는 토론에 적혀 있지 않다.

### 외부 반응

HN에는 이 토론 주소로 올라온 글이 없었다(대조 쿼리는 정상이었다).
Lobste.rs 검색은 소음이 커서 이 토론의 유무를 판단하지 못했다. 이 문서는 없다고 단정하지 않는다.
GeekNews에서는 `Next.js 메모리 누수`로 검색했고 대조 쿼리는 정상이었으나 이 토론의 토픽은 없었다. 결과는 Bun이나 Vercel Scriptc 같은 다른 글이었다.

## 인사이트

### 가져갈 것은 누수 의심 때 먼저 구분할 세 가지이다

종료 코드(134, 137, 143)를 보면 V8 힙 한도, 컨테이너 OOM, 정상 종료를 구분할 수 있다.
그 뒤에 힙 한도를 컨테이너 한도의 70에서 75% 안에서 정하고, 강제 GC 뒤에도 남는지로 누수와 GC 지연을 가른다. 이는 이 문서의 적용이다.

### 감시자 재시작은 임시 방편으로 쓴다

감시자는 장애 확산을 막지만 원인을 가린다.
RSS 임계값에 무작위성을 넣고 복제본을 분산해 동시에 재시작되는 것을 피하는 설계는 임시 방편에도 필요한 것이다.

### 확인할 관찰

이 토론의 주장을 가를 관찰은 세 가지이다.
요청당 남는 메모리의 원인(React 캐시 구조인지 다른 요인인지),
수정된 Next.js 버전이 나온 뒤의 증가 곡선,
최소 재현 저장소로 독립 확인된 여부이다.
셋 모두 이 문서가 확인하지 못했다.
