# 개인 사이트를 Next.js 대신 코딩 에이전트가 만든 5,000줄 프레임워크로 돌린다

원문: [thank u, next | Max Leiter](https://maxleiter.com/blog/thank-u-next)

HN 토론: <https://news.ycombinator.com/item?id=49523229> (4점, 1개 댓글)

## 요약

Max Leiter는 2026년 9월 1일부터 자신의 웹사이트가 Next.js 위에서 돌지
않는다고 밝힌다.
새 사이트는 Fable이 설계하고 Opus가 구현한 자체 제작(bespoke) 프레임워크로
만들어졌다.
사이트는 빌드 시점에 HTML로 컴파일하는 완전 정적 사이트이지만,
React를 많이 쓰고 MDX 같은 빌드 시점 처리도 적지 않다고 한다.
저자는 상업 프로젝트였다면 아마 Next.js에 남았을 것이라고 덧붙인다.

저자가 claude code CLI에서 Fable 5에게 준 지시는 대략 이렇다.
이 사이트 하나에 맞춘 프레임워크가 Next.js보다 빠를 수 있는지,
같은 기능을 지원하고 Vercel에 배포할 수 있는지 조사해 보라는 것이다.
가능하면 출시하겠다고 했고, 하위 에이전트는 모두 Opus로 조율하라고 했다.
저자는 약 3시간 뒤에 볼 만한 결과물이 나왔다고 적는다.

저자가 제시한 전후 비교는 아래와 같다.
모든 수치는 글의 표에서 가져온 것이다.

| 항목                  | Next.js                 | 자체 제작             | 글이 적은 변화      |
| --------------------- | ----------------------- | --------------------- | ------------------- |
| 홈페이지 HTML         | 24.7 KB                 | 16.3 KB               | -34%                |
| 홈페이지 eager JS     | 208 KB (파일 11개)      | 2.3 KB                | -99%                |
| 홈페이지 Lighthouse   | 98, LCP 2.4 s, 1,153 KB | 100, LCP 1.3 s, 78 KB | LCP -46%, 무게 -93% |
| 블로그 글 HTML        | 20.6 KB                 | 11.6 KB               | -44%                |
| 블로그 글 JS          | 200 KB (파일 11개)      | 2.3 KB                | -99%                |
| 블로그 글 Lighthouse  | 99, LCP 2.2 s, 405 KB   | 100, LCP 1.1 s, 57 KB | LCP -50%, 무게 -86% |
| 로컬 전체 빌드 (warm) | 2.4 s                   | 0.5 s                 | -79%                |
| Vercel 빌드 (평균)    | 28 s                    | 11 s                  | -61%                |
| lockfile의 패키지 수  | 706                     | 550                   | -22%                |

구조는 빌드 스크립트에 가깝다.
`build.ts`가 `posts/`를 읽어 모든 경로를 React 서버 렌더링으로 정적
`index.html`로 만들고,
Vercel Build Output 디렉터리를 쓴다.
MDX는 이전과 같은 remark, rehype 플러그인으로 파일마다 한 번 컴파일하고,
코드 강조는 shiki로 빌드 때 처리해 두 테마를 모두 HTML에 넣는다.
블로그 글에는 JavaScript가 없고, 테마 전환, Cmd+K,
아일랜드(islands) 지연 로딩을 맡는
2 KB짜리 인라인 스크립트만 있다.
데스크톱 창 관리자와 명령 팔레트는 Preact 컴포넌트이며 서버가 그린 마크업 위에서
하이드레이션(hydration)한다.
Preact는 React 호환 계층을 거쳐도 7 KB이고 React는 52 KB라고 한다.

저자는 Claude가 parity harness도 썼다고 적는다.
Next 사이트의 101개 경로를 스냅숏으로 저장하고,
변경할 때마다 head 태그, 눈에 보이는 본문,
코드 블록을 새 빌드와 비교하는 도구다.
이 도구가 비공개 글 8편의 RSS 피드 유출과 404가 나는 OG 이미지를 찾아
고쳤다고 한다.
세션 통계는 비용 $669.45, API 시간 8시간 27분, 실제 경과 1일 1시간 34분,
추가 20,914줄과 삭제 2,022줄이다.
저자는 이것이 Claude Code 20x 구독 사용량의 약 10%였다고 적는다.

단점은 글이 직접 나열한다.
Next.js가 처리하는 수많은 사소한 최적화를 LLM이 모르거나 재현하지 못할 수 있고,
일부 기능은 일부러 빼 두었으며,
교체 대상에 따라 상류(upstream)의 보안 수정을 놓칠 수 있고,
버그와 기능 요청이 이제 전부 저자의 몫이라는 것이다.
Claude가 부딪힌 브라우저 문제도 둘 적혀 있다.
Chrome은 도착 페이지의 head에 외부 module 스크립트가 있으면
문서 간 view transition의 진입 쪽 절반을 조용히 건너뛰고,
Safari는 speculation rules 지원 여부를 항상 true로 답하면서 prefetch만 구현한다.
전망은 조심스럽다.
저자는 벤더링(vendoring)과 에이전트를 이용한 재작성(slop forks)이 늘
것이라고 보고,
프레임워크가 사라진다는 말은 더 먼 이야기로 구분한다.

## 분석

### 가장 강한 형태의 주장은 요구가 고정된 사이트에서 프레임워크를 다시 만드는 값이 싸졌다는 것이다

글이 보여 주는 가장 강한 주장은 이렇게 정리할 수 있다.
필요한 기능이 작고 고정된 사이트라면,
코딩 에이전트가 몇 시간 안에 그 기능만 담은 프레임워크를 다시 만들 수 있고,
결과물은 더 작고 빠르며 소유자가 전부 읽을 수 있다.
저자가 새 프레임워크를 Next.js가 하던 일 가운데 이 사이트가 실제로 쓰는 부분만
가져온 것이라고
설명하는 것도 같은 뜻이다.

여기서 줄어든 것은 프레임워크의 기능이 아니라 요구 사항이다.
이 사이트는 완전 정적이다.
서버에서 요청마다 실행되는 코드가 없으므로,
라우팅은 빌드 때 만든 디렉터리가 되고,
이미지 최적화, 캐싱, 리디렉트, 분석은 Vercel의 Build Output API 설정이 맡는다.
저자가 5,000줄을 수십만 줄과 견주는 것도 같은 맥락이다.
이 비교는 5,000줄짜리 구현이 Next.js와 React를 대신한다는 뜻이 아니라,
이 사이트가 그 수십만 줄 가운데 5,000줄어치만 쓴다는 뜻으로 읽어야 한다.
이것은 글의 문장이 아니라 내 해석이다.

저자는 더 단순한 정적 사이트 생성기를 고르거나 Python으로 갈아타면 훨씬 간단했을
것이라는 반론을
스스로 꺼내고, 그 말이 대체로 맞다고 인정한다.
그러고 나서 이 글은 정적 사이트에 대한 이야기가 아니라 소프트웨어의 미래를
보이는 시연이라고 답한다.
따라서 글이 실제로 증명하려는 것은 자체 제작 프레임워크가 우월하다는
점이 아니라,
그런 프레임워크를 만드는 일이 이제 한 사람의 몇 시간 일이 되었다는 점이다.

### 수치 대부분은 클라이언트 JavaScript를 없앤 결과로 읽힌다

표에서 가장 큰 변화는 첫 로딩 때 즉시 받는 JavaScript(eager JavaScript)다.
홈페이지는 208 KB에서 2.3 KB로, 블로그 글은 200 KB에서 2.3 KB로 줄었다.
다만 -99%는 eager JavaScript에만 해당한다.
홈페이지에는 첫 페인트 뒤에 받는 10.6 KB(창 관리자)와
Cmd+K를 처음 누를 때 받는 1.8 KB(명령 팔레트)가 따로 있다.
이 셋을 모두 더하면 14.7 KB이고, 208 KB 대비 약 93% 감소다.
이 합산은 내 계산이다.

반면 Lighthouse 표의 무게 차이는 JavaScript만으로 설명되지 않는다.
홈페이지는 1,153 KB에서 78 KB로, 차이가 1,075 KB다.
eager JavaScript 감소분 208 KB는 그 가운데 약 19%다.
두 수치의 단위가 같다고 가정한 내 계산이다.
나머지 약 870 KB가 어디서 줄었는지 글은 적지 않는다.
이미지 최적화와 asset 캐싱을 Vercel 쪽이 맡는다고만 적었을 뿐,
Next.js 버전에서는 같은 기능을 쓰지 않았는지,
쓰고도 이만큼 무거웠는지는 밝히지 않는다.
나머지 감소분이 JavaScript가 아니라 이미지나 글꼴 같은 다른 자원에서 나왔다고
추정할 수는 있지만,
글만으로는 확인할 수 없다.

HTML 자체도 줄었다.
홈페이지는 24.7 KB에서 16.3 KB로, 블로그 글은 20.6 KB에서 11.6 KB로 줄었다.
Next.js가 HTML에 넣던 직렬화 데이터가 없어진 결과일 수 있다.
이것 역시 글이 설명하지 않는 부분이라 추정이다.
저자가 적은 Preact 7 KB 대 React 52 KB는 라이브러리 선택 하나가 번들 크기를
얼마나 좌우하는지 보여 주지만,
이 선택은 프레임워크를 다시 만들지 않고도 할 수 있는 종류의 변경이다.

### 작업은 설계, 구현, 동등성 검사 세 갈래로 나뉘어 있었다

글에 따르면 설계는 Fable이, 구현은 Opus 하위 에이전트들이 맡았다.
통계에서 Opus 비용은 $537.98, Fable은 $131.09다.
내 계산으로는 총액 $669.45 가운데 Opus가 약 80%, Fable이 약 20%다.
Fable의 입력은 57.4k 토큰이고 출력은 165.3k 토큰인 반면,
Opus는 입력 547.6k, 출력 2.0m 토큰이다.
메인 세션의 프롬프트 캐시는 입력 토큰의 95%를 캐시에서 읽었다고 한다.

세 번째 갈래가 parity harness다.
이 도구가 있었기에 저자는 Next.js 버전을 기준으로 삼아
101개 경로의 head 태그, 본문, 코드 블록이 바뀌었는지 변경마다 확인할 수 있었다.
글은 이 도구가 찾은 문제 두 가지를 적는다.
비공개 글 8편이 RSS 피드에 섞여 나가는 문제와 404가 나는 OG 이미지다.
글은 이 문제가 Next.js 쪽에 있었는지 새 빌드에 있었는지는 밝히지 않는다.

통계의 줄 수도 눈여겨볼 만하다.
세션에서 추가된 줄은 20,914줄이고, 프레임워크는 5,000줄이라고 한다.
내 계산으로 프레임워크는 추가된 줄의 약 24%이고,
나머지 약 76%가 무엇인지 글은 적지 않는다.
harness, 변환 스크립트, 콘텐츠 이동이 들어 있을 수 있지만 글에서 확인되는
사실은 아니다.

### 저자의 결론은 시연 부분보다 훨씬 조심스럽다

저자는 상업 프로젝트라면 아마 Next.js에 남았을 것이라고 적고,
그 문장에 붙인 각주에서 지금은 그렇다는 뜻이라고,
1년 뒤 의견은 모르겠다고 밝힌다.
단점 목록도 길다.
수백에서 수천 가지의 사소한 최적화를 놓칠 수 있고,
일부 기능은 일부러 뺐으며,
버그와 보안과 기능 요청이 모두 소유자 몫이 된다.

전망 부분에서는 말의 무게가 한 번 더 내려간다.
저자는 소프트웨어 공학의 미래를 점치는 것은 소용없다고 먼저 말하고,
그래도 벤더링과 slop forks가 늘 것이라고 본다.
글은 이미 보이는 사례로 Bun의 Zig에서 Rust로의 재작성과 Cloudflare의
Vinext를 든다.
이 두 사례는 글이 든 것이며 나는 따로 확인하지 않았다.
프레임워크가 사라진다는 이야기는 더 먼 전망으로 따로 분리하고,
프레임워크에 쌓인 지식은 skills나 어떤 미래의 표준으로 증류될 수 있다고 말한다.

정리하면 글의 증거는 사이트 하나의 한 번 이식이고,
글의 결론은 그보다 한 걸음 앞서 있다.
그 간격을 저자 자신이 의식하고 있다는 점이 글의 가장 믿을 만한 부분이다.

## 비평

### 공급망과 검토 가능성 논거는 글의 수치와 맞지 않는다

저자가 든 첫 이유는 이런 루프를 반복해 의존성 대부분을 교체하면 공급망 공격을
없앨 수 있다는 것이다.
그런데 이 실험의 결과는 lockfile이 706개에서 550개로 줄어든 것이다.
내 계산으로 156개가 줄었고 약 78%가 남았다.
남은 550개가 무엇인지 글은 적지 않는다.
Preact, shiki, MDX 계열 플러그인, React가 서버 렌더링에 쓰이고 있다는
사실만으로도
많은 패키지가 남았으리라고 짐작할 수 있다.
이 사이트에서 공급망 노출이 얼마나 줄었는지는 글에서 알 수 없다.

두 번째 이유는 프레임워크가 5,000줄이라 사람과 모델 모두 쉽게 검토할 수
있다는 것이다.
그러나 글은 저자가 그 5,000줄을 읽었는지 적지 않는다.
세션에서 추가된 줄은 20,914줄이므로, 검토 대상이 어디까지인지도 분명하지 않다.
모델이 모델의 결과물을 검토한다는 말은 같은 계열의 실수를 같은 방식으로 놓칠 수
있다는 뜻이기도 하다.
이 논거를 뒷받침하려면 저자가 직접 읽은 범위나,
다른 사람이나 다른 도구가 찾아낸 결함 수 같은 증거가 있어야 한다.

### 측정 조건이 적혀 있지 않아 LCP -46%와 -50%를 일반화할 수 없다

표에는 페이지가 둘뿐이다.
홈페이지와 블로그 글 하나다.
Lighthouse를 몇 번 돌렸는지, 중앙값인지 한 번의 값인지,
어떤 기기와 네트워크 조건이었는지 글은 말하지 않는다.
Vercel 빌드의 평균 28초와 11초가 몇 번의 빌드에서 나왔는지도 없다.
Lighthouse의 모바일 점수는 98과 99에서 100으로 올랐을 뿐이어서,
점수는 격차를 거의 보여 주지 못하고 LCP와 전송 무게가 그 일을 맡는다.

비교 대상도 따져 봐야 한다.
Next.js 버전은 완전 정적 사이트인데도 JavaScript 파일 11개와 208 KB를
처음부터 받았다.
이것이 Next.js를 정적 사이트에 맞게 최대한 다듬은 구성인지 글은 말하지 않는다.
저자 스스로 더 단순한 정적 사이트 생성기를 골랐으면 되었다고 인정하므로,
이 표가 말해 주는 것은 이 Next.js 구성과 이 결과물의 차이이지 Next.js 일반의
한계가 아니다.
결론을 바꿀 관찰은 구체적이다.
같은 페이지를 여러 번 측정한 중앙값과 분산,
실제 사용자 측정 데이터(field data),
클라이언트 컴포넌트를 최소로 줄인 Next.js 구성이나 기존 정적 사이트 생성기와의
비교가 그것이다.

### 3시간과 $669.45는 서로 다른 것을 센다

글은 약 3시간 뒤에 볼 만한 결과가 나왔다고 적고,
세션 통계에는 API 시간 8시간 27분과 경과 시간 1일 1시간 34분이 찍혀 있다.
저자는 경과 시간의 상당 부분이 노트북이 잠들어 있던 시간이라고 설명한다.
세 숫자는 각각 사람이 본 시간, 모델이 일한 시간, 달력 시간으로 기준이 다르다.
어느 것도 사람이 요구 사항을 정하고 결과를 확인하는 데 쓴 주의력을 따로
재지 않는다.

비용도 마찬가지다.
$669.45는 통계 화면에 나온 값이고, 저자가 실제로 낸 돈은 구독료다.
글은 구독 사용량의 약 10%라고 적는다.
통계를 낸 뒤에도 저자가 작은 수정을 계속했고,
통계가 작업의 95%를 담는다는 것은 저자의 추정이다.
그래서 이 숫자들로는 사람이 직접 이식했을 때와 비교한 손익분기를 계산할 수 없다.
결론을 바꿀 증거는 같은 방법으로 다른 사이트를 옮긴 기록과,
그때 사람이 쓴 시간의 실측이다.

### 프레임워크 지식이 중요하다는 증거를 들고도 확인 없이 넘어간다

두 브라우저 문제를 소개하면서 저자는 Next가 이를 처리할 것이라고 짐작한다.
그러나 Next.js 버전은 next.maxleiter.com에 그대로 남아 있다고 글이 밝히고
있으므로,
같은 조건에서 Next.js가 실제로 처리하는지 확인하는 일은 어렵지 않았을 것이다.
글은 확인 결과를 적지 않는다.
그러면 이 두 사례는 프레임워크에 지식이 쌓여 있다는 증거가 아니라,
이 사이트에서 Claude가 마주친 문제 두 개일 뿐이다.

결론의 마지막 주장, 즉 그 지식이 skills나 표준으로 증류될 수 있다는 말도
시험되지 않았다.
이 작업에서 skill이 만들어졌다는 언급은 없다.
Claude는 이 문제들을 skill이 아니라 두 페이지짜리 대조용 페이지로 이등분해
찾아냈다고 적혀 있다.
저자가 인정한 수백에서 수천 가지의 최적화 중 이 두 개는 우연히 드러난 것이다.
나머지가 몇 개이고 어떤 종류인지는 글의 관찰 범위 밖에 있다.

## 인사이트

### 이 결과는 새로 만든 것이 아니라 이미 있던 사이트를 다시 만든 것이어서 가능했다

글에서 가장 눈에 띄지 않지만 가장 중요한 장치는 Next.js 버전이 남아 있었다는
사실이다.
Claude는 그 사이트의 101개 경로를 스냅숏으로 떠 두고 새 빌드가 같은 head, 본문,
코드를 내는지 변경마다 비교했다.
기준이 되는 구현이 있었으므로 완성의 정의가 기계로 검사 가능했다.
이것은 명세에 맞춰 새로 쓰는 일과, 기존 구현과 똑같이 동작하도록 다시 쓰는
일의 차이다.
구현을 처음부터 쓰는 일이 아니라 이미 있는 구현의 출력을 목표로 삼는 일이었다.

이 구조는 기존 구현의 테스트 묶음을 통과하도록 새 구현을 만드는 흔한 재구현
작업과 같다.
그래서 이 방법이 다른 곳에서도 통할지는 프레임워크가 얼마나 작은지가 아니라
기존 동작을 얼마나 싸게 검사할 수 있는지에 달려 있다고 나는 판단한다.
정적 HTML처럼 출력이 문서인 경우에는 비교가 쉽다.
인증, 데이터베이스, 세션이 있는 서버 렌더링 앱은 출력이 요청마다 달라서 같은
도구를 만들기 어렵다.
이 판단을 바꿀 관찰은 그런 앱을 같은 방식으로 옮겨 보고 걸린 시간과 놓친 결함
수를 기록하는 것이다.

### 동등성 검사가 보는 면과 프레임워크 지식이 사는 면은 서로 다르다

글이 적은 parity harness는 head 태그, 눈에 보이는 본문, 코드 블록을 비교한다.
모두 정적으로 만들어진 문서의 내용이다.
반면 글이 소개한 두 브라우저 문제는 모두 실행 시점의 동작이다.
Chrome이 view transition의 한쪽 절반을 조용히 건너뛰는 경우에도 HTML은 한 글자도
달라지지 않는다.
그러니 이 harness로는 두 문제를 잡을 수 없었고,
글에 따르면 Claude가 직접 부딪혀 이분 탐색으로 원인을 찾았다.

이것은 프레임워크를 대체했을 때 잃는 것이 어떤 종류인지에 대한 단서다.
조용히 실패하는 동작은 비교 대상 출력에 흔적을 남기지 않는다.
게다가 Next.js를 쓰는 수많은 사이트가 같은 문제를 겪으면 보고가 쌓이고 수정이
상류에 반영되지만,
사용자가 한 명뿐인 자체 제작 프레임워크에서는 소유자 혼자가 유일한 탐지
수단이다.
옮기기 전에 실행 시점 검사, 곧 전환 애니메이션과 프리렌더 동작을 브라우저에서
확인하는 시험을
parity harness에 넣는 것이 최소한의 대응이라고 본다.

### 비용은 사라지지 않고 의존성 갱신에서 소유자의 주의력으로 옮겨 간다

글은 의존성을 줄이면 공급망 위험이 줄고 상류의 보안 수정이 필요
없어진다고 말한다.
다만 정적 사이트라서 보안 수정이 해당되지 않는다는 단서를 스스로 단다.
이 단서가 바로 자체 제작의 비용 구조를 보여 준다.
위험이 사라진 것이 아니라 이 사이트의 성격 덕분에 지금은 작을 뿐이다.

더 오래 남을 비용은 우회 코드의 수명이다.
Safari 문제를 피하는 두 조건 검사는 Safari가 지금 그렇게 동작하기 때문에
성립한다.
Safari가 바뀌면 이 검사는 불필요해지거나 틀려질 수 있고,
누구도 그 사실을 알려 주지 않는다.
프레임워크에 있었다면 그 수정은 유지보수자가 맡았을 일이다.
이제는 소유자가 직접 브라우저 동향을 추적하거나,
문제가 생길 때까지 모르고 지내야 한다.
이 비용을 재는 방법은 간단하다.
1년 동안 이 사이트의 변경 기록에서 외부 변화 때문에 생긴 수정이 몇 건이고 몇
시간이 들었는지 세 보면 된다.

### 프레임워크의 후속은 문서보다 실행 가능한 검사 묶음에 가까울 수 있다

저자는 프레임워크에 쌓인 지식이 skills나 미래의 표준으로 증류될 수 있다고 본다.
이 글 안에서 실제로 재사용 가능한 형태로 남은 것은 두 가지다.
하나는 기존 사이트를 기준으로 비교하는 parity harness이고,
다른 하나는 Chrome 문제를 재현한 두 페이지짜리 대조용 페이지다.
둘 다 읽는 문서가 아니라 돌리는 도구다.

이 차이는 중요하다.
외부 module 스크립트가 전환을 막는다는 문장은 브라우저가 고치는 순간 틀린
문장이 되지만,
아무도 그 사실을 알려 주지 않는다.
대조용 페이지는 지금도 그런지 직접 답한다.
따라서 프레임워크 지식을 전달하는 단위가 설명 글에서 검사 묶음으로 옮겨 간다면,
프레임워크가 하던 일 가운데 사라지는 것은 코드이고 남는 것은 검사일 것이라는
예상이 가능하다.
이것은 글에 없는 내 판단이다.
이 판단이 틀렸음을 보이려면, 검사 묶음 없이 prose로 된 skill만으로 같은 종류의
문제를 피한 사례가 있으면 된다.
