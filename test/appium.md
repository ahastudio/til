# Appium: 앱 UI 자동화 프레임워크

<https://appium.io/>

<https://github.com/appium/appium>

HN 토론: <https://news.ycombinator.com/item?id=5172747> (40점, 10개 댓글)

## 소개

Appium은 네이티브, 하이브리드, 모바일 웹, 데스크톱 앱을 W3C WebDriver 프로토콜 위에서 자동화하는 오픈소스 프레임워크이다.
저장소 설명은 모든 종류의 앱을 위한 크로스 플랫폼 자동화 프레임워크라고 적는다.
직접 설치해 써 보지 않았고 생태계 페이지(드라이버, 클라이언트, 플러그인)와 설치, CLI, 거버넌스 문서는 열지 못했다.
`appium.io`는 문서 사이트(`/docs/en/latest/`)로 이동한다.
설명은 모두 프로젝트의 주장이다.

GitHub API로 읽은 시점(2026년 11월 19일)의 수치는 별 22,241개, 포크 6,308개, 열린 이슈와 풀 리퀘스트 39개, 라이선스 Apache-2.0, 언어 TypeScript, 생성일 2013년 1월 9일, 마지막 푸시 2026년 11월 18일이다.

문서가 소개하는 구성은 다음과 같다.

- 범위: 모바일(iOS, Android, Tizen), 브라우저(Chrome, Firefox, Safari), 데스크톱(macOS, Windows), TV(Roku, tvOS, Android TV, Samsung) 자동화를 아우르는 프로젝트와 생태계라고 소개한다.
- 목표: 플랫폼별 자동화를 크로스 플랫폼 표준 API로 쓰게 하고, 어떤 프로그래밍 언어에서든 쓰게 하고, 공동체의 확장 도구를 제공하는 것이다.
- 서버: Node.js로 만든 HTTP 서버이며 WebDriver 프로토콜을 구현한다. 클라이언트와 서버는 다른 기계에 있어도 되고 클라우드 호스팅도 언급된다.
- 드라이버: 플랫폼별로 WebDriver 호출을 해당 자동화 라이브러리 호출로 바꾸는 Node.js 모듈이다. XCUITest 드라이버가 예이고, 공식 드라이버는 일부이고 나머지는 공동체의 것이며 중앙 권한이 없다고 한다. README는 `xcuitest`와 `uiautomator2`가 모바일 웹과 하이브리드 전환을 기본 지원한다고 적는다.
- 플러그인: 서버 코드를 고치지 않고 기능을 확장하며 드라이버와 달리 시작할 때 켜야 한다(`appium --use-plugins=<이름>`). 이미지 매칭용 images 플러그인이 예로 나온다.
- 클라이언트: 가벼운 HTTP 라이브러리이다. 공식 지원은 Java, Python, Ruby, .NET C#이고 나머지 언어는 외부 클라이언트이다.
- 설치: `npm i -g appium`이며 다른 패키지 관리자는 지원하지 않는다고 한다. 서버만으로는 아무것도 자동화하지 못해서 `appium driver install <드라이버>`로 드라이버를 설치한다. 실행은 `appium server`(기본 `0.0.0.0:4723`)이다. Appium 1에서 올릴 때는 먼저 `npm uninstall -g appium`을 하라고 한다.
- 주장: 앱을 다시 컴파일하거나 고칠 필요가 대체로 없고, 열린 웹 표준인 WebDriver에 투자해 독점 스택을 피한다고 한다. 지원은 가장 최근 버전에만 제공한다.
- 거버넌스: 문서 푸터에 OpenJS Foundation과 Appium 기여자의 저작권이 적혀 있다. 개발과 전략 파트너로 BrowserStack과 TestMu AI(옛 LambdaTest)가 README에 나온다.

## 분석

### 중심 주장은 하나의 표준 API로 여러 플랫폼을 다룬다는 것이다

Appium의 구조는 서버가 WebDriver를 받고 드라이버가 플랫폼 도구에 연결하는 중간 계층이다.
그래서 테스트 코드는 언어와 프레임워크를 고르는 데 자유롭고 플랫폼 차이는 드라이버가 흡수한다.
이는 문서의 서술을 이 문서가 정리한 것이다.

### 드라이버와 플러그인이 확장 지점이다

드라이버는 플랫폼을 추가하는 단위이고 플러그인은 서버 기능을 더하는 단위이다.
중앙 권한이 없고 드라이버 품질이 제각각이라는 문서의 서술은 확장성과 품질 편차가 한 쌍이라는 뜻으로 읽힌다. 이는 이 문서의 해석이다.

### 2013년부터 이어진 프로젝트이다

저장소는 2013년에 생겼고 지금도 매일 푸시가 있다.
HN의 2013년 글에서 한 Appium 커미터는 소스 코드를 고치거나 서드파티 라이브러리를 넣지 않고 테스트해야 한다는 것과 기존의 검증된 도구를 활용한다는 두 원칙을 밝혔다.[^jlipps]
오래된 글이라 지금의 구조와 같다고 보장되지 않는다.

## 비평

### 플랫폼 범위의 세부가 읽은 범위에 없다

Espresso와 Mac2 같은 드라이버 이름도 읽은 페이지에서 확인하지 못했다.

### 드라이버 품질이 공통으로 보장되지 않는다

README는 드라이버가 공동체가 만든 것이라 병렬 세션 지원 등이 다르니 각 드라이버 문서를 확인하라고 한다.
일부 WebDriver 명령은 플랫폼에 따라 지원되지 않는다(예: 네이티브 앱의 쿠키).
표준 API라는 주장은 이 예외를 감안해야 한다.

### 설정 부담이 외부에서 지적된다

이 저장소의 `mcp/mirroir-mcp.md`가 정리한 블로그 글은 Appium이 iPhone 제어에 WebDriverAgent와 개발자 모드가 필요하다고 비교한다.
지원이 최신 버전에만 제공된다는 점도 업그레이드를 강제하는 조건이다.

### 외부 반응

HN 헤더의 글은 2013년 공개 직후의 것으로 40점에 10개 댓글이 달렸고 지금의 평가가 아니다. 그 글에서 한 사용자는 단계마다 걸리는 시간이 시뮬레이터 때문인지 물었고, 다른 사용자는 Instruments에 내장된 지연이라고 답했다.[^maudineormsby]
Lobste.rs에는 `appium.io` 도메인의 글이 없었고 `appium` 검색 결과 23건은 다른 주제의 글이 언급한 것이었다.
GeekNews에서는 `Appium`으로 검색해 이 프로젝트의 토픽이 없었다. 같은 영역의 Maestro와 agent-device 토픽만 있었다(대조 쿼리는 정상이었다).

## 인사이트

### 가져갈 것은 서버와 드라이버를 나눈 구조이다

표준 프로토콜을 받는 서버와 플랫폼별 드라이버를 분리하면 새 플랫폼은 드라이버만 만들면 된다.
다른 자동화 도구를 설계하거나 고를 때 프로토콜 표준과 플러그인 지점이 어디에 있는지 보는 기준으로 쓸 수 있다. 이는 이 문서의 적용이다.

### 도입 전에 쓸 드라이버의 상태를 확인한다

Appium을 고른다는 것은 사실상 대상 플랫폼의 드라이버를 고르는 일이다.
드라이버 저장소의 유지 상태와 지원 버전을 먼저 보고, 그 위에 테스트를 쌓는다.

### 확인할 관찰

이 프로젝트의 주장을 가를 관찰은 세 가지이다.
쓰려는 드라이버의 안정성과 갱신 속도,
같은 시나리오에서 다른 도구(예: Maestro)와 비교한 설정과 실행 시간,
Appium 서버 최신 버전과 지원 정책이다.
