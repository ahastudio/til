# e2e의 Filters API: 작은 모델에게 PR마다 영향받는 테스트만 고르게 해 CI를 줄이는 방법

트윗: [How to make your CI 10x faster with e2e?](https://twitter.com/o_kwasniewski/status/2116237813582582072)

## 요약

TesterArmy의 공동창업자이자 CTO인 Oskar가 2026년 10월 31일에 올린 Twitter
Article이다.
CI에서 가장 느린 작업은 보통 end-to-end 테스트이고 불안정하다고 글은 말한다.
TesterArmy가 만든 오픈소스 테스트 프레임워크 e2e는 웹과 모바일 앱을 대상으로,
결정적 테스트와 에이전트 테스트를 하나의 API로 섞어 쓰게 해 준다.
저자는 첫 달에 GitHub 별 1만 2천 개와 npm 주간 다운로드 50만 회 이상을
얻었다고 적는다.

프레임워크 자체를 빠르게 만드는 데는 한계가 있으므로,
CI를 빠르게 하는 가장 좋은 방법은 중요한 테스트만 돌리는 것이라는 것이
글의 주장이다.
이를 위해 e2e에는 Filters API가 있다. PR에서 테스트를 실행하기 전에 걸러
내는 장치다.
내장 필터는 diff와 테스트 파일을 작은 판단용 모델에 보내고,
테스트마다 이 변경이 이 테스트에 영향을 줄 수 있느냐는 질문 하나를 던진다.
글의 예시는 `typesafe-ai/jev` 모델을 쓰지만 판단형 모델이면 무엇이든 쓸 수
있다고 한다.

설정은 `e2e.config.ts`의 `filters`에 `decisionFilter`를 넣고,
`@e2e-dev/decision`과 `ai` 패키지를 설치하고,
CI에서 `npx e2e run --changed-since origin/<base>`로 실행하는 것이다.
필터는 `--changed-since`를 줄 때만 동작하고,
병합 기준점과 diff를 뜨려면 `fetch-depth: 0`이 필요하다.
PR 예시 출력은 “테스트 77개 중 7개를 남기고 70개를 뺐다(호출 1번, 토큰 17.6k,
0.0007달러)”이고, 글은 이를 테스트가 11배 줄었는데 비용은 0.1센트
미만이라고 설명한다.

안전하다고 보는 근거는 네 가지다.
내장 필터는 모델이 확신하지 못하는 테스트는 돌리는 쪽으로 기운다.
영향받을 확률이 20% 미만이라고 모델이 평가한 테스트만 뺀다.
테스트 파일을 바꿨으면 그 테스트는 돌고,
e2e 설정이나 잠금 파일을 바꿨으면 전부 돈다.
diff가 60kB를 넘거나 파일이 너무 커서 보낼 수 없거나 호출이 실패하는 등 모델이
판단하지 못하면 그 테스트는 돈다.
저자는 최악의 경우가 필요한 것보다 더 많은 테스트를 돌리는 PR이라고 쓴다.
사용자 규칙으로 필터를 감쌀 수도 있다. 글의 예는 `infra/`가 바뀌면 전부 돌리고
`smoke` 태그 테스트는 항상 돌린다.

## 분석

### 이 글이 파는 것은 속도가 아니라 어떤 테스트를 건너뛰어도 되느냐는 판단이다

e2e 테스트의 실행 시간은 테스트 수에 거의 비례한다.
프레임워크를 최적화하면 단위 시간이 줄지만 한계가 있고,
건너뛰는 것은 한계가 없다는 것이 글의 논리다.
그래서 문제를 어떤 테스트가 이번 변경과 관련 있는가라는 분류 문제로 바꾼다.

분류 입력은 diff와 테스트 파일뿐이고, 출력은 테스트마다 영향받을 확률이다.
모델 호출은 PR 하나에 한 번이고 토큰은 1만 7천 개 안팎이다.
사람이 코드와 테스트의 관계를 읽고 판단하는 일을 모델 한 번의 호출로 바꾸었다.

### 안전장치는 모두 모델이 틀릴 수 있다는 전제에서 만들어졌다

글의 안전 규칙은 두 종류다.
하나는 모델의 판단을 믿지 않는 경우다. 확신이 없으면 돌리고,
판단하지 못하면 돌리고, 임계값은 20%로 낮게 둔다.
다른 하나는 모델이 볼 수 없는 영역에 대한 규칙이다. 설정 파일이나 잠금 파일이
바뀌면 전부 돌리고, 인프라 변경에는 사용자가 전부 돌리는 규칙을 둘 수 있다.

두 번째 종류가 이 설계에서 가장 정직한 부분이다.
모델에게 diff만 보여 주면 설정 의존이나 환경 의존의 영향은 알 수 없으므로,
그런 변경은 사람이 규칙으로 막아야 한다.
Filters API가 필터를 `{ name, filter }` 모양의 함수로 열어 둔 것도 이 때문이다.
사용자가 모델의 판단 앞뒤에 자기 규칙을 끼울 수 있다.

## 비평

### 최악의 경우가 더 많이 돌리는 것이라는 설명은 반대쪽 실패를 가린다

글은 최악의 경우를 필요 이상으로 많은 테스트를 돌리는 PR이라고 쓴다.
이것은 모델이 불확실할 때의 경우일 뿐이다.
모델이 확신을 가지고 틀리는 경우, 곧 영향받는 테스트를 영향 없다고 판단해 빼는
경우가 실제 최악이고, 그때는 회귀가 병합된 뒤에 발견된다.

글은 이 경우의 빈도를 말하지 않는다.
20%라는 임계값이 어떻게 정해졌는지, 영향받는 테스트를 빠뜨리지 않는
비율(재현율)이 얼마인지에 대한 측정도 없다.
예시 출력도 한 PR에서 77개 중 7개를 남겼다는 것뿐이어서,
남긴 7개가 맞는 7개였는지는 알 수 없다.
이 도구를 도입하려면 일정 기간 전체를 돌리면서 필터의 예측과 실제 실패를 비교해
재현율을 먼저 재야 한다. 이 방법은 글에 없다.

### 제목의 10배는 테스트 수의 비율이고 CI 시간의 비율이 아니다

글의 숫자는 테스트가 11배 줄었다는 것이다.
CI 전체 시간에는 의존성 설치, 빌드, 앱 기동 같은 고정 비용이 있고,
이 부분은 테스트를 걸러도 줄지 않는다.
글의 CI 예시도 체크아웃, 설치, 빌드, 앱 기동 뒤에 `npx e2e run`이 나온다.
테스트가 11배 줄어도 CI가 11배 빨라진다는 보장은 없고,
줄어드는 폭은 테스트 시간이 전체에서 차지하는 비중에 달려 있다.

### 필터의 판단 근거가 diff와 테스트 파일뿐이라는 한계가 있다

모델이 받는 입력은 diff와 테스트 파일이다.
테스트가 의존하는 공유 모듈, 서버 쪽 변경, 데이터 픽스처, 환경 변수,
의존성 버전 변경은 diff 안에 직접 보이지 않거나 파일이 너무 커서 모델에 전달되지
않을 수 있다.
글은 이런 경우에 파일이 너무 크면 돌린다는 규칙을 두지만,
diff에 보이지 않는 영향은 이 규칙이 잡지 못한다.
테스트와 코드의 의존 관계를 커버리지 기록으로 만드는 결정적 방식과 비교한
이야기도 글에는 없다.

### 글은 제품의 홍보를 겸한다

저자는 e2e를 만든 회사의 CTO이고, 글은 e2e의 별과 다운로드 수,
문서 링크와 `npx e2e init` 안내로 끝난다.
예시 모델은 Typesafe AI의 `jev`이고 어느 판단형 모델이든 쓸 수 있다고 하지만,
기본으로 소개된 것은 특정 모델이다.
이것이 문제는 아니지만, 이 글의 수치와 안전 주장은 모두 만든 사람의 서술이다.

## 인사이트

### 건너뛰기를 모델에 맡길 때는 건너뛴 것의 사후 검증이 설계의 일부여야 한다

CI에서 테스트를 거르는 결정은 비대칭이다.
돌린 테스트가 불필요했을 때의 비용은 시간이고,
빠뜨린 테스트가 필요했을 때의 비용은 회귀의 병합이다.
글의 안전 규칙은 모두 앞의 비용을 감수해 뒤의 비용을 줄이는 방향이다.

이 구조를 완성하려면 건너뛴 테스트를 나중에 따로 돌리는 경로가 필요하다.
예를 들어 병합 뒤나 야간에 전체 스위트를 돌려,
필터가 빠뜨린 실패를 모아 임계값을 조정하는 방식이다.
글에는 이 경로가 없다. 필터를 쓰는 팀이 스스로 만들어야 하는 부분이다.

### 모델은 제안하고 규칙이 거부권을 갖는 구조가 가장 단순한 안전 설계다

글의 사용자 정의 필터 예시는 이 구조를 그대로 보여 준다.
`infra/`가 바뀌면 모델을 부르지도 않고 전부 돌리고,
`smoke` 태그는 모델의 판단에서 아예 빼서 항상 돌린다.
결정적 규칙이 먼저 걸러 내고, 남은 것만 모델이 판단한다.

이 순서는 비용에도 이득이다. 규칙으로 정해지는 경우에는 모델 호출이 없다.
모델의 판단이 필요한 범위를 좁히는 것이므로,
모델을 믿지 못해서가 아니라 믿어도 되는 범위를 명시하는 방식이다.
같은 패턴은 테스트 선택뿐 아니라 코드 리뷰 대상 선정이나 배포 승인 같은 다른 CI
단계에도 적용할 수 있지만, 이 글이 그것까지 보여 주는 것은 아니다.

### 한 번의 호출에 모든 테스트의 판단을 맡기는 구조는 비용을 극단적으로 낮추는 대신 판단의 깊이를 포기한다

호출 1번, 토큰 1만 7천 개, 0.0007달러라는 숫자는 테스트마다 따로 깊이 읽지
않는다는 뜻이다.
모델은 diff와 테스트 파일을 한꺼번에 받아 77개 테스트 각각에 확률을 매긴다.
이는 필터가 싸고 빠르다는 장점의 원인이면서,
판단이 얕을 수 있다는 한계의 원인이다.

비용이 이렇게 낮으면 같은 입력을 여러 번 물어 합의를 보거나 더 큰 모델로
불확실한 테스트만 다시 판단하는 식의 보강이 값싸게 가능하다.
글은 이 방향을 말하지 않지만, 가격 구조가 그런 선택지를 열어 둔다는 점은 이
숫자에서 읽을 수 있다.
