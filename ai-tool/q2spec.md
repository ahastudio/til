# Q2Spec: 불완전한 문서와 사람의 지식에서 제품 명세를 복원하는 도구

<https://github.com/tipop/Q2Spec>

## 소개

Q2Spec은 팀이 가진 불완전한 문서와 구성원의 머릿속 지식에서 제품 명세를
복원하도록 돕는 도구다.
참고 자료를 읽고 간단한 객관식 질문을 던지며, 확인된 답을 Epic, Feature,
Requirement, Scenario(Gherkin)로 구성된 살아 있는 명세로 다시 쌓는다.
README가 가장 앞에 두는 원칙은 AI의 제안이 사람이 확인하기 전까지 잠정적이라는
것이다.
저장소는 2026년 8월 31일에 만들어졌고 라이선스는 MIT이며, GitHub API 기준 언어는
JavaScript, 별은 0개다.
README는 스스로를 초기 공개 프로젝트라고 부른다.

README가 소개하는 기능은 다음과 같다.
Word, PowerPoint, Excel, PDF 참고 자료를 받아 각 문서의 목적과 쓸 만한 근거를
파악한다.
세부 명세를 만들기 전에 제품 경계에 대한 질문을 먼저 한다.
Requirement는 Feature 하나씩 찾아낸다.
Scenario를 제안하기 전에 정상 경로(happy path), 예외 상황(edge case), 실패
상황(failure case)을 따로 묻는다.
확인된 답으로 Markdown과 Gherkin 명세를 만들고, 프로젝트를 로컬에 저장하며
브라우저를 새로고침해도 현재 질문을 되살린다.
선택한 코드베이스와 확인된 Scenario를 읽기 전용으로 비교하는 기능도 있다.
README의 데모 GIF는 가상의 온라인 상점과 미리 정한 질문으로 만든 것이며 실제 AI
생성 장면의 녹화가 아니라고 밝힌다.

## 동작 방식

### 질문의 순서가 명세의 계층을 따른다

작업 흐름은 README의 순서대로 이렇다.
문서를 추가하고 분석을 시작한 뒤, 제품 경계를 정하는 객관식 질문에 답한다.
그다음 Feature를 골라 Requirement를 찾고, Requirement를 골라 정상, 예외, 실패
Scenario를 정의한다.
마지막에 생성된 Markdown과 Gherkin 명세를 검토한다.
넓은 단위에서 좁은 단위로 내려가며 한 번에 하나의 Feature, 하나의 Requirement만
다루는 구조라서, 사용자는 한 번에 하나의 판단만 하면 된다.
이 설계가 README에 적힌 의도라고 단정할 근거는 없고, 이 문서의 해석이다.

### 실행 환경

Node.js 20 이상, Python 3.11 이상, ChatGPT 계정으로 로그인한 Codex Desktop 또는
Codex CLI가 필요하다.
OpenAI API 키는 필요 없고 모델도 Q2Spec이 고르지 않는다. 로그인한 Codex 환경에
설정된 기본 모델을 쓴다.
실행 전에 `codex --version`으로 Codex가 있는지 확인하라고 안내한다.

```bash
git clone https://github.com/tipop/Q2Spec.git
cd Q2Spec
npm install
python -m venv .venv
# macOS / Linux
.venv/bin/python -m pip install -r packages/source-onboarding/requirements.txt
npm start
```

브라우저에서 `http://127.0.0.1:8792/`를 연다.
시작할 때 저장소의 `.venv` Python을 자동으로 쓰며, 다른 환경을 쓰려면
`npm start` 전에 `Q2SPEC_PYTHON`에 그 Python 실행 파일을 지정한다.
검증은 `npm test`와 `npm run test:web`이다.
이 문서는 설치와 실행을 해 보지 않았고 README의 안내만 옮겼다.

## 함정

### 업로드한 문서는 로컬에 남고 Codex로 전달된다

업로드한 문서와 생성된 프로젝트는 `.local/product-runs/` 아래에 저장되고 Git에서
제외된다.
README는 기밀 자료를 쓰기 전에 조직의 AI와 데이터 취급 정책을 확인하라고 한다.
분석이 Codex 환경으로 이루어지므로 자료가 그쪽으로 전달되는 경로를 따져 봐야
한다는 뜻으로 읽히지만, README는 전달 범위를 설명하지 않고 이 문서도 코드를
확인하지 못했다.

### 코드 비교는 동작의 증거가 아니다

README는 생성된 명세에 사람의 검토가 필요하고, 코드 비교만으로는 실행 시 동작이
증명되지 않는다고 스스로 적는다.
확인된 Scenario와 코드를 읽기 전용으로 맞춰 보는 기능은 누락을 찾는 도구이지
테스트를 대체하지 않는다.

## 비평

### 사람의 확인이 병목이 되는 지점이 드러나지 않았다

이 도구의 신뢰는 모든 AI 제안을 사람이 확인한다는 약속에 기댄다.
그런데 Feature마다 Requirement를, Requirement마다 세 종류의 Scenario를 묻는
구조에서는 질문 수가 제품 크기에 비례해 늘어난다.
README에는 질문 수나 소요 시간, 대규모 제품에서의 사용 사례가 없다.
확인이 지칠 때 사람이 첫 번째 선택지를 누르는 일이 생기면 잠정적이던 제안이
확정으로 굳는다.
이 위험은 README가 다루지 않는 추정이고, 어느 정도로 일어나는지는 이 문서가
확인하지 못했다.

### 복원의 품질을 재는 기준이 없다

복원이라는 말은 원래 있던 명세와 얼마나 같은지를 전제하지만 README에는 정확도나
평가 방법이 없다.
데모도 미리 정한 질문으로 만든 것이라 AI가 문서를 읽고 던지는 질문의 질은 보여
주지 않는다.
따라서 이 도구가 문서의 빈틈을 잘 짚는지는 직접 써 보기 전에는 알 수 없다.

## 인사이트

### 명세 복원 도구가 맡는 일은 정답 생성이 아니라 질문 설계다

Q2Spec이 내세우는 것은 명세를 쓰는 AI가 아니라 명세에 필요한 질문을 던지는
순서다.
정상, 예외, 실패를 따로 묻는 방식은 사람이 흔히 정상 경로만 말하고 넘어가는
습관을 겨냥한 설계로 읽힌다.
이 해석은 이 문서의 것이다.

### 이 글을 읽는 방법

이 저장소는 별 0개의 초기 프로젝트이고, 판단에 필요한 정보는 README보다 실제
사용에 있다.
오늘 할 수 있는 일은 기밀이 없는 오래된 기획 문서 하나로 설치해서 첫 질문 열
개가 쓸 만한지 보는 것이다.
이 도구의 주장을 가를 관찰은 두 가지다.
같은 문서를 두 사람이 따로 돌렸을 때 확정된 Scenario가 얼마나 겹치는지, 그리고
생성된 Gherkin이 기존 코드의 실제 동작을 얼마나 놓치는지다.
둘 다 README에는 없다.
