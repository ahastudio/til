# Browser Use: 오픈소스 브라우저 에이전트와 그 위에 올린 세 갈래 제품

HN 토론: <https://news.ycombinator.com/item?id=43173378> (259점, 100개 댓글)

## 소개

브라우저를 쓰는 에이전트다.
저장소 설명도 홈페이지 제목도 같은 한 줄, `Agents that use the browser.`다.

README의 표제는 사람이 하듯 웹을 다루라는 것이고, 예시로 드는 작업이 이 프로젝트의 지향을 보여 준다.
빈 시간대를 찾고, 날짜와 시각을 고르고, CAPTCHA를 처리하고, 운전면허 시험을 예약하는 것이다.
CAPTCHA를 처리한다는 항목이 목록에 자연스럽게 들어 있다는 점이 이 도구의 성격을 드러낸다.

2024년 10월 31일에 만들어졌고 스타 115,127개, 포크 12,674개, 열린 이슈 444개다.
Python으로 작성되었고 MIT 라이선스다.
홈페이지는 GitHub에서 가장 많은 별을 받은 프로젝트 중 하나이며 월 다운로드가 2,080만이라고 밝힌다.

## 세 갈래 경로

README가 먼저 묻는 질문이 어느 Browser Use가 필요하냐는 것이다.
같은 이름 아래 성격이 다른 세 제품이 있기 때문이다.

| 경로                 | 무엇을 쓰는가                             | 무엇이 호스팅되는가            |
| -------------------- | ----------------------------------------- | ------------------------------ |
| 완전 호스팅 클라우드 | API로 작업을 보낸다                       | 에이전트와 브라우저 모두       |
| CLI                  | 이미 쓰는 에이전트에 브라우저 접근을 준다 | 브라우저만(로컬 또는 클라우드) |
| Python 라이브러리    | 자기 코드에서 오픈소스 에이전트를 돌린다  | 브라우저만(로컬 또는 클라우드) |

CLI와 Python 라이브러리는 각각 로컬 브라우저에도 클라우드 브라우저에도 붙을 수 있다.
클라우드 브라우저는 브라우저만 호스팅하고, 완전 호스팅 API는 에이전트까지 돌린다.

CLI 경로가 특이하다.
설치 명령을 주는 대신 Claude Code나 Codex, Hermes, OpenClaw 같은 에이전트에 붙여 넣을 프롬프트를 준다.

```text
Install or upgrade browser-use to the latest stable version with uv using Python 3.12,
run `browser-use skill install` to register the skill, and connect it to my browser.
If setup or connection fails, follow
https://github.com/browser-use/browser-harness/blob/main/install.md.
```

설치 문서를 사람이 아니라 에이전트가 읽게 만든 것이며, 실패했을 때 볼 문서의 주소까지 프롬프트 안에 넣어 두었다.
같은 발상이 README 상단에도 있다.
AI 에이전트와 크롤러를 향해 `browser-use.com/llms.txt`에서 제품 지도를, `docs.browser-use.com/llms.txt`에서 문서 색인을 읽으라고 안내한다.

## Python 라이브러리로 쓰기

Python 3.11 이상이 필요하다.

```bash
uv add browser-use
```

```bash
# .env
OPENAI_API_KEY=your-key
# BROWSER_USE_API_KEY=your-key  # 선택: BU2 모델 또는 클라우드 브라우저
```

```python
import asyncio

from browser_use import Agent, Browser, ChatBrowserUse, ChatOpenAI
from dotenv import load_dotenv

load_dotenv()

async def main():
    llm = ChatOpenAI(model='gpt-5.6-luna', reasoning_effort='xhigh')
    # llm = ChatBrowserUse(model='bu-2-0')  # BU2를 쓰려면 BROWSER_USE_API_KEY가 필요하다
    agent = Agent(
        task="Find the number of stars of the browser-use repo",
        llm=llm,
        # browser=Browser(use_cloud=True),  # 클라우드 브라우저를 쓰려면 같은 키가 필요하다
    )
    history = await agent.run()
    print(history.final_result())

if __name__ == "__main__":
    asyncio.run(main())
```

주석 처리된 두 줄이 이 프로젝트의 구조를 그대로 보여 준다.
모델을 바꾸는 줄과 브라우저를 클라우드로 옮기는 줄이며, 둘 다 같은 API 키를 요구한다.
오픈소스 코드 안에 유료 경로로 가는 문이 주석으로 들어 있고, 주석을 지우는 것이 전환 과정의 전부다.

`ChatBrowserUse`는 게이트웨이 역할도 한다.
제공자 접두어가 붙은 모델 ID를 받아 `BROWSER_USE_API_KEY` 하나로 여러 제공자를 쓸 수 있다.

```python
from browser_use import Agent, ChatBrowserUse

llm = ChatBrowserUse(model='anthropic/claude-sonnet-4-6')  # 또는 'google/gemini-3-pro'
agent = Agent(task='...', llm=llm)
```

물론 `ChatOpenAI`와 `ChatAnthropic`, `ChatGoogle` 래퍼로 각 제공자의 키를 직접 쓸 수도 있다.

## 내세우는 수치

홈페이지가 두 가지 벤치마크를 제시하며, 둘 다 자체 제작이다.

에이전트 정확도는 106개 작업의 내부 하드 벤치마크에서 잰 것이다.

| 대상           | 성공률 | 해결 작업당 비용 |
| -------------- | -----: | ---------------: |
| Browser Use    |    82% |              17¢ |
| Opus 5         |    62% |            $3.40 |
| Sonnet 5       |    59% |            $1.55 |
| Gemini 3.1 Pro |    59% |            $2.20 |

브라우저 인프라는 보호된 71개 사이트 중 도달한 비율로 비교한다.

| 제공자      | 도달 비율 |
| ----------- | --------: |
| Browser Use |       81% |
| Anchor      |       77% |
| Onkernel    |       67% |
| Steel       |       47% |

가격은 브라우저가 시간당 $0.02이고, 에이전트는 모델 비용에 20%를 더한 값이다.
둘 다 인터넷 트래픽이 별도이며, 신규 가입자에게 $15 크레딧을 준다.

Hermes가 Browser Use를 기본 브라우저 도구로 채택했고 작업 토큰이 48~66% 줄었다는 사례도 앞에 나온다.

README에는 별도의 Browser Use Benchmark v2가 있고, 가장 어려운 브라우저 작업을 겨냥한 매우 어려운 벤치마크라고 밝힌다.
쉬운 작업에서는 작은 모델도 매우 높은 성공률을 낼 수 있다는 단서를 붙이고, 표시된 결과가 60개 작업 부분집합에서 나왔다고 적는다.
벤치마크 저장소를 따로 공개한다.

## 트레이드오프

### 자체 벤치마크에서 1등이라는 수치의 성격

이 프로젝트가 제시하는 두 표 모두 자기가 만든 평가에서 자기가 1등인 구조다.
106개 작업 내부 하드 벤치마크도, 71개 보호 사이트 도달률도 Browser Use가 정의했다.

이것이 곧 조작이라는 뜻은 아니다.
브라우저 에이전트에는 널리 인정된 공개 벤치마크가 아직 없고, 만들려면 누군가는 작업 집합을 정해야 한다.
그리고 벤치마크 저장소를 공개한 것은 검증 가능성을 남긴 것이다.

문제는 작업 집합을 고르는 일 자체가 결과를 정한다는 점이다.
README가 그 사실을 알고 있다는 증거도 있다.
쉬운 작업에서는 작은 모델도 매우 높은 성공률을 낸다고 적어 두었기 때문이다.
어려운 작업만 골랐다는 것은 차이를 크게 만드는 선택이며, 그 선택은 정당할 수도 있고 유리할 수도 있다.

특히 비교 대상의 성격이 다르다는 점을 봐야 한다.
표에서 Browser Use 82%와 Opus 5 62%를 나란히 두는데, Browser Use는 브라우저 전용으로 만든 에이전트 제품이고 Opus 5는 범용 모델이다.
브라우저 작업에 특화된 시스템이 범용 모델보다 브라우저 작업을 잘하는 것은 놀랍지 않고,
그러니 이 표가 보여 주는 것은 특화가 효과가 있다는 사실이지 이 제품이 최선이라는 사실이 아니다.

그래서 채택을 검토한다면 자기 작업 10개로 직접 재는 편이 이 표들보다 훨씬 많은 것을 알려 준다.

### 오픈소스가 유입 경로인 구조

115,127개의 별과 MIT 라이선스는 진짜다.
동시에 README와 홈페이지 전체가 클라우드 제품으로 향한다.

구조를 보면 분명하다.
README 첫 화면에 클라우드 배지가 있고, 어느 제품이 필요하냐는 질문이 첫 번째 섹션이며, 그 답의 첫 경로가 완전 호스팅 클라우드다.
코드 예제에는 클라우드로 가는 두 줄이 주석으로 준비되어 있고, 추천 모델은 API 키가 필요한 BU2다.
신규 가입 $15 크레딧이 세 군데에 나온다.

이 배치가 부정직한 것은 아니다.
오픈소스를 유지하려면 수익이 필요하고, 이 방식은 널리 쓰이며, 코드를 실제로 열어 두었다.

대가는 기본값이 어디를 향하느냐에 있다.
가장 잘 동작하는 조합이 유료 경로에 있다면, 순수 오픈소스 경로는 문서에는 있지만 덜 다듬어진 길이 되기 쉽다.
추천 모델이 BU2라는 것과 `ChatBrowserUse`가 게이트웨이 역할을 겸한다는 것이 그 방향을 보여 준다.
자기 제공자 키를 직접 쓰는 것도 가능하지만, 그것은 두 번째로 안내되는 선택지다.

그래서 이 도구를 오래 쓸 계획이라면 어느 경로에 의존하고 있는지를 명시적으로 정해 두는 편이 낫다.
주석 두 줄을 지우는 것이 전환의 전부라는 사실은 편리함인 동시에, 전환이 얼마나 쉽게 일어나는지에 대한 경고이기도 하다.

이 구조의 지속 가능성에 대한 의문도 Launch HN에 있었다.
`rvz`는 MIT 라이선스이므로 Amazon 같은 회사가 관리형 버전을 배포해 더 싼 가격과 더 높은 무료 할당량으로 경쟁할 수 있다며,
이 프로젝트가 AGPL이나 새로운 비즈니스 라이선스로 바꿀 것이라고 예측했다.[^rvz]
`MagMueller`는 과거에 Amazon이 다른 프로젝트에 그렇게 한 것을 본 적 있느냐고 되물었다.[^MagMueller-license]

2025년의 이 예측은 지금까지는 빗나갔다. 저장소는 여전히 MIT다.
다만 예측의 근거였던 긴장은 남아 있고, 그 긴장을 해소하는 방식이 라이선스 변경만 있는 것은 아니다.
클라우드 경로에 더 좋은 모델과 더 편한 기본값을 두는 것도 같은 문제에 대한 답이며, 이 프로젝트가 택한 것은 그쪽에 가깝다.

### CAPTCHA 우회와 스텔스가 기능 목록에 있다

홈페이지의 솔루션 목록에 CAPTCHA 해결과 안티디텍트 브라우저가 있고,
브라우저 인프라 벤치마크의 지표 자체가 보호된 71개 사이트 중 몇 곳에 도달했느냐다.
README도 스텔스와 CAPTCHA 해결, 주거용 프록시를 제공한다고 적는다.

즉 이 제품의 인프라 경쟁력은 사이트가 자동화를 막으려는 조치를 얼마나 잘 뚫느냐로 측정된다.
지표를 그렇게 정의했다는 것은 그것이 고객이 사는 것이라는 뜻이다.

여기에 긴장이 있다.
자기 계정에서 자기 일을 자동화하는 것과, 막아 둔 사이트에 접근하는 것은 같은 기술이지만 다른 일이다.
도구는 둘을 구분하지 않으며, 구분은 쓰는 쪽의 몫으로 남는다.

그리고 이 긴장은 시간이 지날수록 커지는 쪽이다.
사이트들이 방어를 강화하면 도달률 지표가 떨어지고, 그것을 올리려면 더 공격적인 우회가 필요해진다.
도달률을 제품 지표로 삼은 이상 그 방향으로 계속 밀리게 되며, 이용약관과 법규가 그 경주를 따라가지 못하는 구간이 생긴다.

쓰는 쪽에서 정해야 할 것은 어느 사이트에 이 도구를 쓸지에 대한 자기 기준이다.
도구가 가능하게 한다는 것과 해도 된다는 것은 다르고, 이 경우 그 구분이 문서에 없다.

Launch HN에서 `jackienotchan`이 이 문제를 정면으로 물었다.
AI 에이전트가 웹의 스크래핑과 크롤링 활동을 크게 늘렸는데 많은 경우 적절한 user agent를 쓰지 않고
지난 20년간 업계가 만들어 온 관행, 즉 `robots.txt`와 속도 제한을 지키지 않으며,
그 결과 사이트 소유자가 비용과 다운타임을 떠안는다는 것이다.
이 문제를 다루는 내장 기능이 있느냐고 물었다.[^jackienotchan]

`MagMueller`의 답이 솔직하다.
일부 호스팅 서비스가 호스팅 비용이 100%에서 1000% 증가하는 것을 겪었다고 인정하면서,
대부분의 페이지에서 browser-use는 자기들이 추출하는 상호작용 요소만 필요하고 이미지나 비디오는 필요 없다고 설명했다.
그런데 바로 다음 문장이 핵심이다.
이 최적화를 아직 구현하지 않았지만 구현하면 양쪽 모두의 비용을 줄일 것이라고 적었다.
그리고 eTag가 바뀔 때만 갱신하는 캐시를 둘 수 있다는 구상을 덧붙였다.[^MagMueller-scraping]

즉 질문을 받은 시점에 이 문제에 대한 내장 대책은 없었다.
비용을 인지하고 있고 줄일 방법도 알고 있지만, 그것이 자기 사용자의 비용이 아니라 상대 사이트의 비용이라는 점이 이 순서를 설명한다.
외부효과는 그것을 부담하는 쪽이 요구하지 않으면 우선순위에서 밀리며, 여기서는 그 쪽에 발언권이 없다.

`35mm`의 보고가 반대편 현실을 보여 준다.
처음 시도한 사이트가 10초 만에 자기 집 IP를 봇으로 표시하고 차단했다는 것이다.[^35mm]
사이트는 막고, 도구는 뚫는 기능을 팔고, 그 사이에서 개별 사용자의 IP가 소모된다.

### 에이전트를 위한 문서가 사람을 위한 문서를 밀어낸다

설치 안내가 에이전트에 붙여 넣을 프롬프트인 것, `llms.txt`를 앞세우는 것은 새롭고 영리하다.
에이전트가 스스로 설치하고 연결까지 하게 만들면 진입 마찰이 크게 줄어든다.

그런데 이 방식은 무엇이 설치되는지를 사용자가 보지 않게 만든다.
프롬프트 하나가 패키지 설치와 스킬 등록, 브라우저 연결까지 수행하며, 실패하면 별도 저장소의 설치 문서로 넘어간다.
[Jev Ultrafast 노트](../jev/jev-ultrafast.md)에서 본 대로 browser-harness의 기본 텔레메트리에 대한 우려가 제기된 적이 있는데,
그런 것을 확인할 지점이 이 흐름에는 없다.

브라우저에 붙는 도구에서 이 구분이 특히 중요하다.
연결되는 것이 로그인 세션과 쿠키를 가진 실제 프로필일 수 있기 때문이다.
그래서 편의를 위해 만든 자동 설치 경로가 검토 없이 실행되는 경로이기도 하다.

### 디버깅 도구를 프로덕션 경로로 쓰는 것에 대한 지적

Launch HN에서 가장 무거운 질문이 이것이었고, 창업자의 답변까지 남아 있어 함께 읽을 가치가 있다.

`arjunchint`는 오픈소스 라이브러리의 보안을 검토했는지 물으면서 세 가지를 나열했다.
CDP 같은 디버거 도구를 쓰는 것, 샌드박스 없이 Playwright를 띄우는 것,
그리고 사용자에게 자기 주 브라우저를 디버거 모드로 띄워 연결하라고 안내하는 것이다.
이 디버깅 도구들에는 활성 익스플로잇이 있는데 Google이 고치지 않는다며,
디버깅용이지 프로덕션이나 일반 용도가 아니기 때문이라고 설명했다.
세 가지 설계가 겹치면 익스플로잇이 권한을 올려 주 기계를 감염시킬 수 있다는 것이다.[^arjunchint]

`101008`이 이것이 매우 중요하며 해결되지 않으면 완전히 쓸 수 없다고 덧붙였다.
에이전트가 기계를 장악하는 웹사이트에 접근할 수 있다는 것이다.[^101008]

창업자 `gregpr07`의 답변은 방어적이지 않지만 질문을 다시 던지는 쪽이다.
디버그 모드 없이 브라우저를 제어할 수 있느냐고 묻고,
프로덕션에서는 어차피 단일 인스턴스 도커 컨테이너에서 돌기 때문에 파일 시스템에 접근할 수 없다고 적었다.
그리고 가상 머신 안에서 해를 끼칠 수 있는 익스플로잇이 있느냐고 되물었다.[^gregpr07-security]

이 주고받음이 중요한 이유는 양쪽 다 부분적으로 맞기 때문이다.
클라우드에서 컨테이너 안에 격리해 돌리면 위험이 크게 줄어드는 것은 사실이다.
그런데 이 프로젝트가 가장 강조하는 편의, 즉 이미 로그인된 자기 브라우저에 붙이는 방식은 정확히 그 격리가 없는 경로다.
`mritchie712`가 LinkedIn 차단을 어떻게 피하느냐고 물었을 때 `MagMueller`가 권한 답이 그것이었다.
로컬에서 돌리면 이미 로그인된 실제 브라우저와 사용자 프로필에 연결할 수 있다는 것이다.[^MagMueller-linkedin]

즉 차단을 피하는 방법과 보안 위험이 같은 설정에서 나온다.
격리하면 안전하지만 로그인 세션이 없어 막히고, 로그인 세션을 쓰면 되지만 격리가 사라진다.
이 교환이 이 도구를 쓰는 사람이 실제로 마주하는 선택이며, 문서는 편한 쪽만 안내한다.

## 함정

벤치마크 두 개 모두 이 프로젝트가 만든 것이다. 자기 작업으로 다시 재지 않으면 옮겨 쓸 수 없는 수치다.

에이전트 가격이 모델 비용 + 20%다. 모델 비용이 변수이므로 월 비용을 예측하려면 작업당 토큰을 먼저 알아야 한다.

브라우저 시간당 $0.02에 인터넷 트래픽이 별도다. 오래 열어 두는 작업이라면 트래픽 쪽을 따로 봐야 한다.

추천 모델 BU2와 클라우드 브라우저가 모두 `BROWSER_USE_API_KEY`를 쓴다. 완전 오픈소스로만 돌릴 생각이라면 어느 경로를 쓰고 있는지 확인해야 한다.

CLI 설치가 에이전트에게 맡기는 프롬프트다. 무엇이 설치되고 어디에 연결되는지 직접 확인하지 않으면 모른 채로 지나간다.

브라우저 프로필 공유와 텔레메트리를 확인해야 한다. 로그인된 프로필에 붙는 도구라는 점을 전제로 격리 환경을 쓰는 편이 안전하다.

CAPTCHA 해결과 스텔스가 기능이다. 대상 사이트의 이용약관과 지역 법규를 확인할 책임은 쓰는 쪽에 있다.

열린 이슈가 444개다. 사용자 규모에 비해 대응 여력이 어떤지를 보고 의존 수준을 정해야 한다.

## 확인하기

가장 빠른 확인은 예제 하나를 로컬에서 끝까지 돌려 보는 것이다.

```bash
uv init --python 3.12
uv add browser-use
# .env에 OPENAI_API_KEY만 넣고 시작한다 — 유료 경로를 쓰지 않는 상태를 먼저 본다
uv run agent.py
```

여기서 봐야 할 것은 성공 여부가 아니라 두 가지다.
자기 제공자 키만으로 어디까지 되는지, 그리고 한 작업에 모델 토큰이 얼마나 드는지다.
두 번째 값이 있어야 모델 비용 + 20%라는 가격을 자기 숫자로 바꿀 수 있다.

벤치마크 주장을 검증하려면 공개된 벤치마크 저장소를 쓰되, 자기 도메인의 작업 10개를 직접 추가해서 재는 편이 낫다.
106개 중 82%가 자기 작업 10개 중 몇 개가 될지는 작업의 성격이 정한다.

## 체크리스트

- 세 경로(클라우드, CLI, 라이브러리) 중 어느 것에 의존할지 정했는가
- `BROWSER_USE_API_KEY`가 필요한 기능을 쓰고 있는지 확인했는가
- 자기 작업 10개로 성공률과 작업당 비용을 직접 쟀는가
- 로그인된 프로필이 아니라 격리된 브라우저 환경에서 돌리고 있는가
- 설치 과정에서 무엇이 설치되고 어디에 연결되는지 확인했는가
- 텔레메트리 설정을 확인했는가
- 대상 사이트의 이용약관과 자동화 정책을 확인했는가
- 브라우저 시간과 트래픽을 포함한 월 비용을 계산했는가

## 기억할 원칙

### 벤치마크를 만든 쪽이 1등인 표는 비교가 아니라 정의다

이 프로젝트의 두 표는 읽는 방법을 알면 여전히 유용하다.
82% 대 62%라는 숫자가 말해 주는 것은 이 제품이 더 낫다는 것이 아니라,
이 제품을 만든 사람들이 브라우저 에이전트의 어려움을 어떻게 정의하는지다.

106개 작업이 무엇인지, 71개 보호 사이트가 어디인지가 그 정의이고,
경쟁자들의 점수는 그 정의에 대한 상대적 위치일 뿐이다.
그러니 이런 표에서 먼저 읽어야 할 것은 순위가 아니라 평가 대상의 구성이다.

이 읽기 방법이 일반적으로 쓸모 있는 이유는 자체 벤치마크가 사라지지 않을 것이기 때문이다.
새로운 분야일수록 공인된 평가가 없고, 그래서 만든 쪽이 평가도 만든다.
그것을 문제라고만 보면 아무 정보도 얻지 못하고, 그대로 믿으면 잘못된 결론에 닿는다.

중간 지점은 평가의 구성을 자기 상황과 비교하는 것이다.
작업 목록이 자기 작업과 닮았다면 숫자가 참고가 되고, 닮지 않았다면 숫자는 무의미하며 그 사실 자체가 정보다.
그리고 이 프로젝트처럼 벤치마크를 공개한 경우, 그 안을 열어 보는 것이 표를 보는 것보다 언제나 많은 것을 알려 준다.

### 오픈소스 코드 안의 주석 처리된 두 줄이 사업 모델이다

이 저장소의 예제 코드에서 가장 많은 것을 말해 주는 부분은 실행되는 줄이 아니라 주석이다.
모델을 BU2로 바꾸는 줄과 브라우저를 클라우드로 옮기는 줄이 나란히 주석으로 놓여 있다.

이 배치는 잘 만든 설계다.
오픈소스 사용자는 주석을 무시하고 쓸 수 있고, 필요해진 사람은 주석을 지우면 된다.
마찰이 거의 없고, 강요도 없다.

그런데 같은 이유로 이 경계는 조용히 넘어간다.
`#` 하나를 지우는 것이 무료에서 유료로, 자기 제공자에서 게이트웨이로, 로컬에서 원격으로 넘어가는 일 전부다.
그리고 그 변화는 코드 리뷰에서 한 줄짜리 diff로 보인다.

여기서 나오는 실무 규칙이 있다.
오픈소스 도구를 도입할 때 유료 경로와의 경계가 어디인지를 문서에 한 번 적어 두는 것이다.
어떤 기능이 어느 쪽에 있는지, 지금 우리가 어느 쪽을 쓰는지, 넘어가면 무엇이 달라지는지다.
이 경계가 명시되어 있지 않으면 시간이 지나면서 조금씩 넘어가게 되고,
넘어간 것을 되돌리는 비용은 처음에 정하는 비용보다 훨씬 크다.
