# wigolo — local-first web intelligence for AI agents

<https://knockoutez.github.io/wigolo/>

<https://github.com/KnockOutEZ/wigolo>

HN 토론: <https://news.ycombinator.com/item?id=48971110> (3점, 0개 댓글)

GN 토론: <https://news.hada.io/topic?id=33246>

## 소개

AI 코딩 에이전트를 위한 로컬 퍼스트 웹 인텔리전스 MCP 서버다.
검색, 페이지 읽기, 크롤링, 추출, 캐시, 유사 문서 탐색, 리서치,
자율 수집(에이전트) 기능을 하나의 MCP 인터페이스로 제공한다.
API 키 없이, 클라우드 없이, 쿼리당 비용 없이 실행된다.

핵심 기능은 다음과 같다.

- **검색**: 18개의 검색 엔진 어댑터를 직접 조회한 뒤 순위
  융합(rank fusion)과 ML 기반 재정렬을 거친다.
  결과에는 정확한 바이트 오프셋 위치에 고정된 원문 발췌, 설명
  가능한 점수 분해, 실시간 엔진 텔레메트리가 붙는다.
  자체 채점기가 약한 결과를 쓰레기로 미리 표시한다.
- **페이지 읽기**: 계층적 라우팅으로 기본 HTTP 요청에서 시작해
  봇 차단 화면이나 SPA가 감지되면 헤드리스 브라우저로 자동
  전환한다.
  어떤 도메인에 어떤 방식이 통하는지 시스템이 스스로 학습하며,
  PDF와 인증된 세션, 클릭·입력·스크롤·스크린샷 같은 페이지
  상호작용도 처리한다.
- **크롤링과 추출**: 너비 우선, 깊이 우선, 사이트맵 기반 등
  다중 페이지 크롤링 방식을 지원한다.
  구조화된 데이터 추출은 표, 메타데이터, JSON-LD, 그리고
  커스텀 JSON Schema를 통한 이름 있는 스키마(Article, Recipe,
  Product 등)까지 다룬다.
- **캐시와 유사 문서 탐색**: 이전에 본 콘텐츠를 키워드와 하이브리드
  시맨틱 방식으로 조회할 수 있고, 키워드·시맨틱·실시간 웹을
  융합해 관련 페이지를 찾아낸다.
- **리서치 모드**: 질문을 하위 질의로 분해하고, 출처를 가져와
  인용이 달린 보고서로 종합한다.
- **에이전트 모드**: 계획·검색·읽기·추출·종합을 결합한 자율
  수집 루프를 수행한다.
- **변경 감지**: `diff`와 `watch` 도구가 변경 사항을 추적하고
  웹훅으로 전달한다.

## 사용법

```bash
npx wigolo init                                        # 로컬 엔진 설정
npx wigolo init --agents=claude-code,cursor            # 설정 + 에이전트 연결
```

`--agents` 플래그는 Claude Code, Cursor, Codex, Gemini CLI,
OpenCode, VS Code, Windsurf, Zed, Antigravity를 지원하며 설정
과정에서 자동으로 처리된다.
LangChain(`BaseTool`과 리트리버), CrewAI(도구 세트 직접 통합),
LlamaIndex(`BaseReader`), Vercel AI SDK(엣지 친화적 도구
팩토리) 프레임워크 통합도 제공한다.

TypeScript SDK(`npm install wigolo-sdk`, 의존성 없음, Node/
Bun/Deno/엣지에서 동작)와 Python SDK(`pip install wigolo`,
표준 라이브러리만 사용, 동기·비동기 지원)가 따로 있다.
Node.js 20 이상, macOS/Linux/Windows, 약 1.5GB의 디스크 공간이
필요하다.

## 아키텍처

단일 Node.js 프로세스가 stdio를 통해 JSON-RPC로 Model Context
Protocol(MCP)을 노출하는 구조다.
컴포넌트는 지연 로딩(lazy-load)되므로 쓰지 않는 기능은 자원을
소모하지 않는다.

검색·읽기·크롤링·추출·캐시·유사 문서 탐색 같은 핵심 도구는
API 키 없이 동작한다.
LLM 연동은 선택 사항이며, 키 없이도 종합 기능이 동작하지만
Gemini(무료 등급 제공), Anthropic, OpenAI, Groq, 또는 완전한
오프라인 운용을 위한 로컬 Ollama 인스턴스를 붙일 수 있다.

`wigolo serve`는 OpenAI 3.1과 호환되는 `/v1/{tool}` 엔드포인트를
가진 REST API를 노출하며, 루프백 밖에서 접근하려면 베어러
토큰이 필요하다.
`ghcr.io/knockoutez/wigolo`와 `towhid69420/wigolo` Docker
이미지로도 배포할 수 있고, stdio MCP나 HTTP 서버 모드를 고를 수
있다.

## 성능 검증

프로젝트가 공개한 실시간 비교 테스트 하나가 있다.
Claude Fable 5 세션 안에서 wigolo를 기본 내장 WebSearch,
Tavily, Exa와 나란히 비교했는데, 네 도구 모두 같은 답과 같은
최상위 출처로 수렴했다.
다만 wigolo만 바이트 단위로 고정된 발췌, 설명 가능한 점수,
실시간 엔진 텔레메트리를 함께 제공했고, 약한 결과를 신뢰할 수
없다고 표시했다는 차이가 있다.

## 라이선스 및 상태

GNU AGPL-3.0-only다.
기업 내부나 자체 호스팅 환경에서 사용·수정하는 것은 자유롭지만,
수정한 버전을 네트워크 서비스로 운영하면 그 수정 소스를 같은
라이선스로 공개해야 한다.
로컬 또는 내부 사용에는 상업 라이선스 의무가 없다.

퍼블릭 베타 상태이며, GitHub 스타 5,200개, 포크 413개, 커밋
2,005개를 기록하고 있다.
7,600개의 테스트로 문서화된 기능 전반의 안정성을 검증한다고
밝힌다.

## 분석

### 검색 엔진을 직접 붙이는 대신 융합하는 방식이 신뢰도를 사용자에게 넘긴다

wigolo는 하나의 우월한 검색 엔진을 고르는 대신 18개 엔진을
동시에 조회하고 순위를 융합한 뒤 재정렬하는 방식을 택했다.
이 설계의 핵심은 “어느 엔진이 가장 정확한가”라는 질문에 답하는
대신, 여러 엔진의 결과를 합쳐서 개별 엔진의 편향이나 실패를
서로 상쇄시키는 것이다.
동시에 바이트 오프셋 발췌와 설명 가능한 점수 분해를 노출해,
최종 판단(이 결과를 신뢰할지)을 시스템이 내리는 대신 에이전트나
사용자에게 넘긴다.
이는 “약한 결과를 숨기지 않고 명시한다”는 원칙과 일관되며,
검색 결과의 불확실성을 감추기보다 투명하게 드러내는 쪽을
택한 설계다.

### 계층적 라우팅이 헤드리스 브라우저의 비용 문제를 도메인 단위로 상쇄한다

모든 페이지 요청을 헤드리스 브라우저로 처리하면 정확하지만
느리고 자원을 많이 쓰며, 모든 요청을 기본 HTTP로 처리하면
빠르지만 SPA나 봇 차단 화면에서 실패한다.
wigolo는 기본 HTTP에서 시작해 실패가 감지될 때만 헤드리스
브라우저로 승격(escalate)하고, 그 판단을 도메인 단위로
학습해 재사용한다.
이는 매 요청마다 같은 비용-정확도 트레이드오프를 다시 계산하는
대신, 한 번 학습한 도메인별 전략을 캐싱해 반복 비용을 줄이는
접근이다.

### 리서치 모드와 에이전트 모드의 구분이 “종합”과 “자율 행동”을 서로 다른 위험 등급으로 분리한다

리서치 모드는 질문을 분해하고 출처를 모아 인용 달린 보고서로
종합하는 데 그치지만, 에이전트 모드는 계획·검색·읽기·추출·종합을
스스로 반복하는 자율 루프다.
이 둘을 별개의 도구로 분리한 것은, 사용자가 “정보를 종합해
달라”는 요청과 “알아서 판단하고 행동해 달라”는 요청을 명시적으로
구분해서 호출할 수 있게 만든다는 뜻이다.
자율성의 수준이 높아질수록 예측 불가능성과 위험도 커지므로,
이 구분은 에이전트 도구 설계에서 자율성 등급을 사용자가 선택할
수 있게 하는 일반적인 패턴을 보여준다.

## 비평

### AGPL-3.0과 “로컬은 무료”라는 마케팅 사이에 잠재적 긴장이 있다

wigolo는 “API 키 없이, 클라우드 없이, 쿼리당 비용 없이”를
전면에 내세우지만, 실제 라이선스는 AGPL-3.0이다.
개인 사용자나 로컬 실행에는 문제가 없지만, 이 도구를 기반으로
네트워크 서비스를 만들어 배포하려는 회사는 수정 소스 전체를
공개해야 하는 강한 카피레프트 의무를 진다.
“무료”라는 인상과 실제 상업적 이용 시의 의무 사이의 간극이
README나 마케팅 페이지에서 충분히 부각되지 않으면, 이를
서비스에 통합하려던 팀이 나중에야 그 의무를 알게 되는 상황이
생길 수 있다.

### 18개 검색 엔진 통합이 개별 엔진의 이용 약관 문제를 그대로 물려받는다

여러 검색 엔진을 직접 조회하는 방식은 각 엔진의 스크레이핑
정책이나 API 이용 약관을 따라야 한다.
프로젝트가 이 18개 엔진 각각과 공식 파트너십이나 API 계약을
맺고 있는지, 아니면 비공식적인 방식으로 조회하는지에 대한
설명이 없다.
비공식 스크레이핑에 의존한다면 개별 엔진의 정책 변경이나
차단 조치 하나로 전체 검색 기능의 신뢰성이 흔들릴 수 있는
구조적 취약점을 안고 있다.

### 성능 검증 사례가 하나뿐이고 제3자 검증이 없다

프로젝트가 제시하는 유일한 성능 비교는 자체적으로 수행한 단일
세션 테스트이며, 네 도구가 “같은 답으로 수렴했다”는 결과
자체는 오히려 wigolo의 차별화 요소(설명 가능성, 텔레메트리)가
최종 답의 정확도에는 큰 영향을 주지 않았다는 것을 보여준다.
독립적인 제3자가 재현한 벤치마크나, 더 다양한 질의 유형에
걸친 비교 없이 단일 사례만으로 도구의 우수성을 주장하는 것은
증거로서 얇다.

## 인사이트

### 로컬 우선 검색 도구는 에이전트 생태계에서 “신뢰 가능한 하부 구조”라는 새로운 역할을 만든다

클라우드 검색 API에 의존하는 에이전트는 그 API 제공자의 가용성,
요금 정책, 데이터 처리 방식에 종속된다.
wigolo처럼 검색·크롤링·추출 전체 파이프라인을 로컬에서
완결하는 도구가 등장하면, 에이전트 개발자는 외부 서비스의
장애나 정책 변경에 흔들리지 않는 하부 구조를 확보하게 된다.
이는 에이전트 생태계가 성숙하면서 “어떤 모델을 쓰는가”만큼
“그 모델이 의존하는 정보 검색 인프라를 누가 통제하는가”가
중요한 질문이 되고 있음을 보여준다.

### 설명 가능한 점수와 텔레메트리 노출은 에이전트 신뢰성 문제에 대한 인프라 계층의 대응이다

에이전트가 검색 결과를 바탕으로 잘못된 결론을 내리는 문제(할루시네이션의
한 원인)는 흔히 모델 자체의 결함으로 취급된다.
그러나 wigolo가 바이트 오프셋 발췌, 점수 분해, 실시간 텔레메트리를
노출하는 것은, 이 문제의 일부가 모델이 아니라 검색 결과의
불확실성이 충분히 드러나지 않는 데서 온다는 것을 시사한다.
검색 인프라 계층에서 불확실성을 명시적으로 드러내면, 그 위에
있는 에이전트나 모델이 그 정보를 활용해 더 나은 판단을 내릴
여지가 생긴다.
이는 AI 신뢰성 문제에 대한 해법이 모델 개선뿐 아니라 그 모델이
딛고 서 있는 데이터 파이프라인의 투명성 개선에서도 나올 수
있음을 보여준다.

### 다중 SDK와 프레임워크 통합 전략이 특정 에이전트 생태계에 대한 종속을 피하려는 시도다

TypeScript와 Python SDK를 모두 제공하고, LangChain·CrewAI·
LlamaIndex·Vercel AI SDK까지 통합하는 것은 특정 언어나 특정
에이전트 프레임워크에 종속되지 않으려는 명확한 전략이다.
이는 도구의 가치가 특정 생태계 안에서만 발휘되는 것이 아니라,
에이전트가 어떤 언어나 프레임워크로 구축되든 동일한 기반
인프라로 쓰일 수 있어야 한다는 판단을 반영한다.
이런 다중 통합 전략은 초기 채택 장벽을 낮추지만, 동시에 각
SDK와 프레임워크 어댑터를 계속 동기화하고 유지보수해야 하는
부담을 프로젝트에 지속적으로 지운다.
