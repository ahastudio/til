# AI Coding Usage Card

<https://github.com/Baek-Seunghyun/ai-coding-usage-card>

Show GN: [내가 AI에 태운 토큰이 얼마인지 보여주는 깃허브 프로필 카드 | GeekNews](https://news.hada.io/topic?id=31463)

## 소개

AI Coding Usage Card는 여러 AI 코딩 도구(Claude Code, Codex, Gemini CLI,
Copilot CLI, OpenCode 등)의 토큰 사용량을 집계해서 GitHub 프로필에 붙일 수
있는 SVG 카드로 만들어 주는 자가 호스팅(self-hosted) 도구다. 핵심 전제는
“모든 계산이 내 컴퓨터에서, 내 로컬 로그만 가지고 돌아간다”는 것이다.
외부 서비스, 별도 계정, API 키가 필요 없고 결과물은 프로필 저장소에
커밋되는 정적 SVG 하나뿐이다.

데이터 수집은 `ccusage`에 의존한다. `ccusage`가 감지할 수 있는 AI CLI라면
무엇이든 대상이 되며, 각 도구가 로컬에 남기는 로그를 읽어 토큰과 비용을
계산한다. 실행하면 `usage-card.mjs` 스크립트가 로그를 읽어 기기별 JSON
스냅샷을 갱신하고, 모든 기기의 스냅샷을 합쳐 SVG 네 종류를 한 번에
다시 생성한다.

카드는 누적 토큰 수와 캐시 적중률, USD 및 선택한 통화 기준의
API 환산 비용, 입력/출력/캐시 읽기/캐시 쓰기로 나눈 토큰 구성, 활동일 수와
일 평균·최고 사용량·주 사용 모델 같은 활동 지표, 도구별 비용 분해, 그리고
GitHub 잔디(contribution grass)를 닮은 일별 히트맵을 보여 준다.

## 명세

카드는 한 번의 실행으로 네 가지 변형이 모두 생성된다.

| 변형                 | 크기      | 내용                                          |
| -------------------- | --------- | --------------------------------------------- |
| `ai-usage-full.svg`  | 846×225   | 전체 누적, 비용, 토큰 구성, 활동, 도구별 분해 |
| `ai-usage-half.svg`  | 423×195   | 전체 누적 + 비용만                            |
| `ai-usage-grass.svg` | 423×195   | 26주 사용량 히트맵                            |
| `ai-usage-combo.svg` | 846×195   | half + grass 병합                             |

동작 요건은 Node.js 18+, 인증된 GitHub CLI, 그리고 공개 GitHub 프로필
저장소다. 설정 절차는 (1) 저장소를 fork 후 clone, (2) 절대 바뀌지 않을
고유 기기 ID(예: `macbook-work`) 부여, (3)
`USAGE_CARD_REPO=YOURNAME/YOURNAME USAGE_CARD_DEVICE=macbook-work node
usage-card.mjs`로 테스트 실행, (4) 프로필 README에 `cards/` 디렉터리의 SVG
삽입, (5) 시스템 스케줄러로 매일 실행 예약이다.

주목할 설계 선택은 **GitHub Actions를 쓰지 않는다**는 점이다. 스케줄링은
운영체제의 스케줄러에 맡긴다. Windows는 VBS 래퍼와 작업 스케줄러,
macOS/Linux는 cron(예: `37 9 * * * ... node /path/to/usage-card.mjs`)을
쓰고, 저장소 갱신은 GitHub Actions 실행 없이 파일 API 커밋으로 직접
이뤄진다. 여러 기기를 쓸 때는 실행 시각을 어긋나게 잡아 동시 브랜치
갱신 충돌을 피하도록 안내한다.

## 분석

### 로그가 사라진다는 전제 위에 설계가 서 있다

이 도구의 가장 특징적인 설계는 “일별 하이워터 원장(daily high-water
ledger)”이다. 매 실행마다 오늘의 `ccusage` 값을 저장된 스냅샷에 날짜별로
병합하되, 옛 값과 새 값 중 **최댓값**을 취한다. 언뜻 이상해 보이는 이
규칙은, AI CLI들이 오래된 로컬 로그를 주기적으로 정리(prune)한다는 현실을
전제로 한다. 로그가 사라지면 `ccusage`가 보고하는 누적치가 도리어 줄어들 수
있는데, 하이워터 방식은 한 번 관측된 고점을 놓지 않음으로써 전체 누적치가
역행하지 않게 막는다.

여기서 드러나는 핵심 통찰은, 이 프로젝트가 다루는 데이터 원천이
**신뢰할 수 없는, 사라지는 로그**라는 점이다. 대부분의 대시보드는 서버가
원본을 영구 보관한다고 가정하지만, 여기서는 원본 자체가 휘발성이다.
그래서 도구의 상당 부분이 “측정”이 아니라 “관측한 값을 잃지 않기”에
투자된다. v2 포맷의 날짜별 분해 저장, v1→v2 자동 스키마 업그레이드,
원장 이전 손실을 한 번 보정하는 baseline 시드 항목이 모두 같은 문제의
파생물이다.

### 중앙 서버 없는 다중 기기 집계라는 문제

한 사람이 여러 컴퓨터에서 AI 코딩 도구를 쓴다는 건 흔한 상황이다. 보통은
중앙 서버가 각 클라이언트의 보고를 받아 합산하지만, 이 도구는 서버를 두지
않겠다는 제약을 스스로 걸었다. 그 결과 각 기기는
`cards/devices/<device>.json`에 자기 원장을 따로 유지하고, 마스터 SVG를
만들 때 모든 기기 스냅샷을 합쳐 통합 총계를 낸다.

이 구조에서 저장소(Git 저장소)가 사실상 “동기화 지점”이자 “데이터베이스”
역할을 대신한다. 서버 대신 Git 히스토리가 상태를 들고 있고, 각 기기는
그저 자기 몫을 커밋할 뿐이다. 실행 시각 stagger 권고가 필요한 이유도
여기서 나온다. 진짜 트랜잭션이 없는 공유 저장소를 여러 클라이언트가
동시에 밀면 충돌하므로, 시간차로 경합을 회피하는 것이다.

흥미로운 것은 GN 공개 당시에는 이 다중 기기 집계가 **아직 없었다**는
점이다. 여러 PC나 서버에서 작업해도 합산이 되느냐는 질문에[^gn-kaydash]
제작자는 로컬 PC 한 대 기준이라고 답했다.[^gn-qor0328] 같은 스레드에서
여러 PC의 수집을 추가하면 좋겠다는 요청이 나왔고[^gn-hmmhmmhm-request],
그 요청자가 곧바로 여러 장비에서 토큰량을 수집하는 기능을 직접 구현해
PR을 올렸다.[^gn-hmmhmmhm-pr]

즉 위에서 설명한 기기별 원장과 통합 총계 구조는 원저자의 초기 설계가
아니라 공개 직후 며칠 사이에 사용자 기여로 들어온 것이다. 하루 만에
질문이 요청이 되고 요청이 PR이 되는 흐름인데, 하이워터 병합이나 stagger
권고 같은 방어 장치도 이 확장을 급하게 받아내는 과정에서 붙었을
가능성이 있다. 다중 기기 지원이 처음부터 요구사항이었다면 Git 저장소를
동기화 지점으로 삼는 선택 자체를 다시 검토했을 수도 있다.

### GitHub Actions를 의도적으로 배제한 선택

많은 프로필 카드 프로젝트가 GitHub Actions로 주기 실행을 돌린다. 이
도구는 그것을 명시적으로 피하고 OS 스케줄러 + 파일 API 커밋을 택했다.
표면적 이유는 자명하다. `ccusage`가 읽어야 할 로컬 로그는 **개발자의 실제
장비**에만 있기 때문이다. CI 러너에는 Claude Code나 Codex의 사용 로그가
존재하지 않는다.

즉 이 배제는 미학적 취향이 아니라 데이터 소재지(data locality)가 강제한
결과다. 데이터가 로컬에만 있으니 계산도 로컬에서 일어나야 하고, 클라우드
자동화가 낄 자리는 “커밋을 대신 밀어 주는” 파일 API 호출뿐이다. 이
관찰은 프라이버시 서사와도 맞물린다. 로그가 기기를 떠나지 않는다는 것은
선택이기 이전에 구조적 필연이다.

## 비평

### “완전 로컬·무서버”라는 서사는 Git 저장소라는 예외를 숨긴다

README는 “모든 것이 내 컴퓨터에서 돌아간다”는 프라이버시 서사를 전면에
내세운다. 그러나 결과물은 **공개** 프로필 저장소에 커밋되는 SVG다. 즉
누적 토큰, 비용(USD 환산), 활동일, 주 사용 모델, 일별 히트맵이 전 세계에
공개된다. 계산이 로컬에서 일어난다는 것과, 그 계산의 산출물이 공개된다는
것은 전혀 다른 층위의 문제인데 서사는 앞엣것만 강조한다.

여기에는 재식별 위험도 있다. 일별 히트맵과 활동일, 최고 사용량은 사실상
그 사람의 근무 리듬과 휴가, 야근 패턴을 드러내는 행동 지문이다. “내 로그는
기기를 떠나지 않는다”는 문장은 맞지만, 로그에서 파생된 **행동 요약**은
매일 공개 커밋된다. 프라이버시를 세일즈 포인트로 삼는 도구라면 이
비대칭을 더 정직하게 다뤘어야 한다.

### 하이워터 병합은 데이터를 단조증가하는 방향으로만 왜곡한다

하이워터 원장은 로그 정리로 인한 누적치 역행을 막지만, 그 대가로 **오직
위로만 틀리는** 시스템을 만든다. 만약 `ccusage`가 어느 날 버그나 중복
집계로 과대한 값을 한 번 보고하면, 최댓값 규칙 때문에 그 오류가 영구히
고점으로 남는다. 정상적인 후속 값들은 결코 그 고점을 끌어내리지 못한다.

이는 측정 도구로서 치명적인 성질이다. 카드에 적힌 “전체 누적 토큰”은
관측된 최댓값들의 합이지 실제 사용량이 아니며, 두 값의 차이는 시간이
갈수록 벌어지되 절대 좁혀지지 않는다. baseline 보정이 한 방향(과소 보정)만
다루고 과대 고점을 되돌릴 장치는 없다는 점에서, 설계는 “숫자가 줄지 않게”를
“숫자가 정확하게”보다 우선한 셈이다. 프로필 자랑용으로는 무해하지만
자기 사용량 분석 도구로 쓰기엔 신뢰하기 어렵다.

### 무서버 다중 기기 동기화를 stagger로 때우는 것은 임시방편이다

이 도구는 중앙 서버를 없앤 대가를 “실행 시각을 어긋나게 잡으라”는
사용자 수칙으로 떠넘긴다. 그러나 cron 시각을 벌려 놓는 것은 경합을
줄일 뿐 제거하지 못한다. 두 기기의 실행이 네트워크 지연이나 스케줄
드리프트로 겹치면, 진짜 잠금이 없는 파일 API 커밋은 서로의 갱신을
덮어쓰거나 병합 충돌을 낼 수 있다.

더 근본적으로, 정확성을 사용자의 설정 규율에 의존한다는 것은 확장성이
없다는 뜻이다. 기기가 두세 대일 땐 시각을 벌리는 게 통하지만, 대수가
늘거나 사용자가 무심코 같은 시각을 잡으면 조용히 데이터가 어긋난다.
그리고 이 실패는 요란한 에러가 아니라 “카드 숫자가 살짝 틀림” 형태로
나타나 사용자가 알아채기도 어렵다. 무서버라는 미학을 지키려다 정확성
보장을 사용자 규율로 외주한 셈이다.

## 인사이트

### AI 사용량이 개발자 정체성의 공개 지표로 편입되고 있다

이 도구의 진짜 의미는 기술이 아니라 **무엇을 자랑거리로 삼는가**의 변화에
있다. 예전 프로필 카드는 언어 통계, 스타 수, 커밋 잔디를 전시했다. 이제
누군가는 “내가 태운 토큰 총량”과 “AI 도구에 쓴 비용”을 프로필에 건다.
사용량이 곧 실력이나 생산성의 대리 지표라는 암묵적 가정이 여기 깔려 있다.

이 가정은 위험하다. 토큰 소비는 산출이 아니라 투입이다. 코드 줄 수로
생산성을 재던 시절의 오류가 그대로 되풀이될 수 있다. 많이 태운 사람이
일을 잘한 게 아니라 도구에 많이 의존했을 뿐일 수 있다. 그럼에도 공개
지표가 되는 순간, 사람들은 지표를 최적화하기 시작한다. 굿하트의 법칙이
말하듯, 측정이 목표가 되면 측정은 좋은 측정이길 그친다. AI 사용량 카드가
널리 퍼지면 “쓸데없이 토큰을 태워 숫자를 부풀리는” 행동이 나타날 것이라고
예상하는 편이 자연스럽다.

GN 반응 하나가 이 동기를 노골적으로 드러낸다. AI 때문에 개발자들에게
포모(FOMO)가 오는데 GitHub이 이런 걸 보여주지 않아 불편하다는 것이다.
사용량만 보여줘서는 체감이 안 되니 과시할 거리를 달라는 취지다.[^gn-happing94]

이 반응이 흥미로운 이유는 카드의 수요가 어디서 나오는지를 스스로
설명하기 때문이다. 이 도구가 채우는 것은 측정 욕구가 아니라 **불안**이다.
AI가 개발자의 기여를 눈에 보이지 않게 만들면서 커밋 잔디가 예전만큼
채워지지 않고, 그 자리를 메울 새로운 전시 지표가 필요해진 것이다.

그렇다면 앞서 말한 굿하트의 법칙은 더 빨리 작동한다. 지표가 정확해서
채택되는 것이 아니라 불안을 달래려고 채택되는 것이라면, 그 지표가 실제
산출과 무관하다는 사실은 오히려 장애물이 되지 않는다. 위에서 지적한
하이워터 병합의 “위로만 틀리는” 성질도 이 용도에서는 결함이 아니라
기능에 가깝다. 숫자가 줄지 않는 편이 전시물로는 낫기 때문이다.

### 휘발성 로그 위에 영속 지표를 세우려는 시도는 생태계의 공백을 드러낸다

이 프로젝트가 하이워터 원장, 스키마 마이그레이션, baseline 보정 같은
복잡한 방어 장치를 두는 이유는 하나다. AI CLI들이 자기 사용 이력을
영속적으로, 신뢰할 수 있게 제공하지 않기 때문이다. 사용자는 자기 데이터를
지키려고 로그를 뒤에서 긁고, 최댓값으로 방어하고, 사라진 과거를 손으로
보정한다.

이것은 개별 도구의 문제가 아니라 생태계의 공백이다. 클라우드 SaaS라면
사업자가 사용량 대시보드를 정확히 제공하는 게 당연하지만, 로컬 CLI 도구는
그 책임을 사용자에게 떠넘겨 왔다. 그 공백을 서드파티가 취약한 로그를
긁어 메우는 형태로 이 도구가 등장했다. 여기서 예측할 수 있는 2차 효과는,
AI 코딩 도구 사업자들이 결국 공식 사용량 API를 제공하게 되리라는 것이다.
비용이 실제 지출과 직결되는 순간(구독제에서 종량제·크레딧제로 이동하면서)
사용자는 정확한 수치를 요구하게 되고, 그때 이런 긁기 기반 도구는 공식
API의 얇은 래퍼로 흡수되거나 도태될 것이다.

### 저장소를 데이터베이스로 쓰는 패턴은 편리하지만 정합성 부채를 남긴다

Git 저장소를 상태 저장소이자 동기화 지점으로 쓰는 것은 이 도구만의
발상이 아니다. GitOps, 정적 사이트의 콘텐츠 관리, 각종 프로필 자동화가
모두 “서버 대신 Git”이라는 패턴을 공유한다. 매력은 분명하다. 인증, 이력,
접근 제어, 무료 호스팅이 공짜로 딸려 온다.

그러나 Git은 트랜잭션 데이터베이스가 아니다. 동시 쓰기 격리도, 원자적
읽기-수정-쓰기도 보장하지 않는다. 이 도구가 stagger로 회피하려는 문제,
즉 여러 기기가 같은 파일을 밀 때의 경합은 “Git을 DB처럼 쓰는” 모든
시스템이 결국 마주치는 정합성 부채다. 소규모 개인 프로젝트에서는 이
부채가 드러나지 않지만, 협업이나 다중 클라이언트로 규모가 커지는 순간
비용을 청구한다. 이 도구가 개인 프로필용에 머무는 한 우아하지만, 같은
아키텍처를 팀 단위 사용량 집계로 확장하려는 순간 서버 없는 미학은
깨질 수밖에 없다는 교훈을 준다.

GN 스레드의 전개가 이 예측을 작게 재현한다. 공개 하루 만에 다중 기기
질문이 나왔고, 곧바로 기능이 붙었다. 개인 한 대에서 여러 대로 넘어가는
가장 작은 확장에서조차 stagger 권고라는 사용자 수칙이 필요해졌다.
팀 단위는 그보다 훨씬 큰 도약이다.
