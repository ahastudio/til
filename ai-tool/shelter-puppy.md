# shelter-puppy

<https://github.com/chessire/shelter-puppy>

## 소개

shelter-puppy는 유기견 보호소에서 촬영한 폰 영상 여러 개와
자연어 요청 한 문단만으로 세로 9:16 숏폼 입양 홍보 영상을 만들어내는
로컬 AI 영상 파이프라인이다.
raw 영상과 "우리 토리 소개 영상 만들어줘.
뛰어노는 모습 나오다가 산책하고, 하이파이브로 끝나게" 같은 요청을 넣으면
약 4분 뒤 자막과 내레이션이 붙은 완성 영상이 나온다.
단순한 영상 편집 자동화를 넘어, 생성된 영상에서 강아지를 감지하고
추적한 관찰 기록을 입양 상담 챗봇의 지식 베이스로도 재사용한다.

## 아키텍처

핵심 설계는 역할을 층위별로 분리하는 것이다.
LLM은 행동 이름 붙이기, 요청 분해, 장면 관찰 같은 의미 해석에만 관여하고,
픽셀과 프레임 타이밍 처리는 Python, OpenCV, ffmpeg으로 구성된
결정론적 계층이 담당한다.
객체 탐지·추적·재식별·텍스트 생성은 각각 YOLO11, ByteTrack, DINOv2,
Gemma라는 전용 모델에 위임한다.
이렇게 계층을 나누어 두면 의도된 창작적 생성 부분을 제외하고는
"같은 입력이면 같은 출력"이 보장된다.

파이프라인은 P0부터 M6까지 이어지는 단계로 구성된다.

| 단계 | 기능                                                                    |
| ---- | ----------------------------------------------------------------------- |
| P0   | 정규화: 회전 보정, HDR→SDR, VFR→CFR 30fps, 768px로 다운스케일           |
| M1   | 탐지 및 추적: YOLO11m + ByteTrack, MPS 가속                             |
| M2   | 재식별: 트랙 병합, 다중 견종 확인 시 사진 앵커 활용                     |
| M3   | 모션 분석: 카메라 흔들림 보정, 동적/정적 구간용 모션 곡선 산출          |
| M4   | 행동 인식 및 관찰 프로파일링: Gemma logprob 투표 + 메타데이터           |
| M5   | TTS: 한국어 정규화 → 구절 합성 → Whisper CER 검증 → 무음 구간 조립      |
| M6   | 편집: 요청→플랜 변환, 텍스트 레이아웃, 결정론적 렌더링, AI 표시 배지    |

## 환각 통제 메커니즘

shelter-puppy가 스스로를 소개할 때 가장 강조하는 부분은
"로컬 AI가 생성한 문구를 어떻게 믿을 수 있는가"라는 질문에 대한 답이다.
다섯 가지 장치를 내세운다.

첫째, 텍스트 출처를 청크 단위가 아니라 테이블·레이어 단위로 고정해
사용자 입력, LLM 생성물, 관찰 기록을 구조적으로 분리한다.
둘째, 생성된 자막 문구는 주장을 잘게 쪼갠 뒤 소스 관찰 기록과
logprob 점수에 대조해 검증하는 팩트체크 계층을 거치며,
근거가 없는 주장은 관찰된 범위 안으로 다시 써진다.
셋째, 프롬프트에는 지시문만 담고 실제 콘텐츠는 사용자 요청과
영상 분석 결과에서만 가져오는 프롬프트 규율을 지킨다.
즉 프롬프트 안에 하드코딩된 문자열을 넣지 않는다.
넷째, 다중 견종이 섞여 모호하거나 모드 판정이 불확실한 경우
상태 기계가 멈추고 사용자 확인을 요구하는 인간 체크포인트를 둔다.
다섯째, 5~9개의 손으로 라벨링한 골든 셋을 두고
모델이나 파라미터를 바꿀 때마다 다시 채점해,
모델 크기·임베딩 전략·TTS 엔진 선택 같은 결정을 데이터 기반으로 내린다.

## 사용법

기본 파이프라인 실행은 다음과 같다.

```bash
python -m pipeline.job my_job \
  --inputs ~/videos/tori/ \
  --dog-photos ~/photos/tori/ \
  --request "우리 토리 소개 영상 만들어줘. 뛰어노는 모습 나오다가 산책하고, 하이파이브로 끝나게."
# → jobs/my_job/out/final.mp4
```

`--rerender`, `--prepare-only`, `--voice`, `--size`, `--weights`, `--conf`,
`--data-root` 같은 플래그로 렌더링 범위와 모델 선택을 조정할 수 있다.

파이프라인 산출물은 입양 상담 챗봇의 RAG 지식 베이스로도 흘러 들어간다.

```bash
python -m rag.cli init
python -m rag.cli ingest my_job --dog tori --dog-name 토리
python -m rag.cli search tori "다른 강아지랑 잘 지내나요?"
```

## 기술 스택 및 상태

핵심 처리는 Python 3, OpenCV, ffmpeg, PIL로 이루어지고,
탐지·추적에는 YOLO11m(MPS)과 ByteTrack, 재식별에는
1024차원 임베딩을 쓰는 DINOv2가 들어간다.
LLM은 로컬 Ollama로 구동하는 Gemma4 26B, TTS는 격리된
`venv-tts` 서브프로세스에서 MLX-Audio를 통해 구동하는 Qwen3-TTS를 쓴다.
RAG 임베딩은 BGE-M3, 벡터 DB는 PostgreSQL + pgvector를 사용한다.
플랫폼은 Apple Silicon(M1/M2 MPS)을 전제로 한다.

프로젝트는 커밋 35개, 스타 3개 수준의 MVP 단계다.
결정론적 파이프라인과 RAG 인제스트 기능은 동작하는 상태이며,
동일 ID로 작업을 동시 실행하는 것은 메타 레이스 컨디션 위험 때문에
금지되어 있다.
테스트/배치 실행은 사용자 작업 디렉터리와 분리되어 있다.
라이선스는 MIT다.

## 분석

### 환각 통제를 아키텍처 문제로 재정의한다

이 프로젝트가 흥미로운 지점은 "환각을 줄이자"는 목표를
프롬프트 튜닝이 아니라 시스템 설계 문제로 다룬다는 데 있다.
LLM의 역할을 의미 해석으로 한정하고 픽셀 처리와 렌더링을
결정론적 코드에 맡기는 구조 자체가, LLM이 틀릴 수 있는 범위를
원천적으로 좁힌다.
이는 최근 에이전트형 파이프라인에서 반복적으로 등장하는 패턴과 닿아 있다.
LLM을 "만능 실행기"로 쓰는 대신 좁은 역할만 맡기고,
나머지는 검증 가능한 결정론적 절차로 감싸는 방식이다.

### 팩트체크 계층은 검증 가능성을 텍스트에 되돌려준다

생성된 자막을 주장 단위로 쪼개 소스 관찰 기록과 대조하는 방식은,
생성 결과물이 "그럴듯한가"가 아니라 "관찰된 사실에 근거하는가"를
따지는 절차다.
이 접근은 자유 형식 생성물을 다루기 어렵게 만드는 검증 문제를,
구조화된 관찰 데이터라는 우회로로 해결한다.
관찰 기록이 먼저 존재하고 텍스트는 그 기록에 종속된다는 순서를
지키는 한, 생성된 문장이 사실과 어긋날 여지는 구조적으로 줄어든다.

### 골든 셋 기반 의사결정은 작은 팀의 현실적 타협이다

5~9개짜리 골든 셋으로 모델 교체를 검증한다는 대목은 소규모다.
그러나 이는 정확히 "측정 없이 모델을 바꾸지 않는다"는 원칙을
아주 작은 리소스로도 지킬 수 있음을 보여준다.
대규모 벤치마크나 A/B 테스트 인프라가 없어도, 손으로 라벨링한
소수의 샘플을 고정된 기준점으로 삼는 것만으로 회귀를 감지할 수 있다.
1인 또는 소규모 프로젝트에서 실용적으로 채택할 수 있는 검증 전략의
최소 단위를 보여주는 사례다.

## 비평

### 골든 셋 5~9개는 일반화를 보장하지 못한다

측정 우선 원칙 자체는 타당하지만, 5~9개의 손라벨 영상으로
검증되는 범위는 매우 제한적이다.
견종, 촬영 환경, 조명, 카메라 흔들림의 조합이 다양한 실제 보호소
영상 전체를 대표하기에는 표본이 지나치게 작다.
골든 셋에 포함되지 않은 견종이나 촬영 조건에서 재식별(M2)이나
행동 인식(M4)이 얼마나 안정적인지는 README만으로는 알 수 없다.
"측정 기반 의사결정"이라는 표현이 주는 신뢰감과, 실제로 그 측정이
커버하는 범위 사이에는 간극이 있다.

### 인간 체크포인트의 트리거 조건이 불투명하다

다중 견종이 모호하거나 모드 판정이 불확실할 때 상태 기계가 멈춘다는
설명은 있지만, 그 "모호함"과 "불확실함"을 판정하는 임계값이나
로직은 공개되어 있지 않다.
이 임계값이 지나치게 관대하면 실제로는 오탐이 발생한 상황에서도
확인 요청 없이 그대로 렌더링될 수 있고, 반대로 지나치게 엄격하면
사용자가 매번 불필요한 확인을 반복해야 한다.
환각 통제를 표방하는 시스템에서 이 지점이 블랙박스로 남아 있다는 점은
검증 가능성이라는 프로젝트의 핵심 가치와 부딪힌다.

### 단일 플랫폼 의존이 재현성과 배포 범위를 제한한다

YOLO의 MPS 가속과 MLX-Audio 기반 TTS 모두 Apple Silicon을 전제로
설계되어 있다.
결정론적 처리를 강조하는 프로젝트가 정작 하드웨어 종속적인
가속 경로 위에 서 있다는 점은 다소 모순적이다.
동일한 모델이라도 MPS와 CUDA, CPU 환경에서 부동소수점 연산 결과가
미세하게 달라질 수 있어, "같은 입력이면 같은 출력"이라는 결정론
주장은 사실 "같은 하드웨어에서는"이라는 단서가 붙어야 정확하다.
보호소처럼 예산이 한정된 조직이 Apple Silicon 기기를 갖추고 있다는
보장도 없어, 실사용 확산에는 현실적인 장벽이 남는다.

## 인사이트

### 로컬 AI 파이프라인은 신뢰 구축 비용을 코드에 새긴다

클라우드 API 기반 생성형 서비스는 모델 자체의 환각 통제를
벤더에게 위임할 수 있지만, 로컬에서 작은 오픈소스 모델을 조합해
쓰는 프로젝트는 그 신뢰 구축 작업을 스스로 코드로 구현해야 한다.
shelter-puppy가 계층 분리, 팩트체크, 프롬프트 규율, 인간 체크포인트,
골든 셋 검증까지 다섯 겹의 장치를 두는 이유는 여기에 있다.
이는 로컬 AI 채택이 늘어날수록, 개별 프로젝트마다 이런 신뢰 구축
인프라를 반복해서 재발명해야 한다는 비용을 시사한다.
장기적으로는 이 다섯 장치 각각이 재사용 가능한 라이브러리나
프레임워크로 분리되어 나올 가능성이 크다.

### 결정론적 계층과 생성 계층의 경계는 시간이 지나며 이동한다

지금은 픽셀 처리와 렌더링이 결정론적이고 텍스트 생성만 확률적이지만,
이 경계는 고정된 것이 아니다.
비디오 생성 모델이 더 저렴해지고 통제 가능해지면, 지금 ffmpeg으로
처리하는 편집 단계 자체가 생성 모델로 대체될 유인이 생긴다.
그렇게 되면 shelter-puppy가 지금 구축한 환각 통제 장치들은
그대로 이식되지 않고, 새로운 형태의 검증 계층을 다시 설계해야 한다.
결정론과 생성 사이의 경계선은 기술이 발전할수록 계속 안쪽으로
밀려 들어오는 이동선이지, 한 번 정해두면 끝나는 설계 결정이 아니다.

### 보호소 도메인 특화가 오히려 일반화 가능한 패턴을 만든다

유기견 소개 영상이라는 좁고 구체적인 도메인을 택했기 때문에,
관찰 대상(강아지 행동)과 검증 기준(골든 셋)을 명확하게 좁힐 수 있었다.
범용 영상 편집 AI를 목표로 했다면 환각 통제 대상 자체가
무한히 넓어져 팩트체크 계층을 설계하기 어려웠을 것이다.
이는 "범용 AI 도구를 만들려면 오히려 좁은 도메인에서 검증 가능한
파이프라인을 먼저 완성하라"는 역설적인 설계 교훈으로 일반화된다.
좁은 문제에서 검증 인프라를 먼저 단단하게 만든 뒤 도메인을
넓혀가는 순서가, 처음부터 범용성을 노리는 것보다 실질적으로
더 빠르게 신뢰할 수 있는 시스템에 도달하는 경로일 수 있다.
