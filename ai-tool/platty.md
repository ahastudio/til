# Platty: 코드에서 회사의 단일 진실 공급원을 만든다는 기업용 AI

<https://www.platty-ai.com/ko>

## 소개

Platty(플래티)는 주식회사 패러다임시프트가 개발하고 운영하는 기업용 서비스다.
스스로를 “The Enterprise SSOT”라고 부른다.
SSOT(Single Source of Truth, 단일 진실 공급원)는
조직의 정보가 한 곳에서 관리되어 모두가 같은 기준을 보는 상태를 말한다.

홈페이지의 첫 문장은 “AI는 모든 것을 압니다. 여전히, 당신의 회사만 빼고.”다.
범용 모델은 세상 지식은 많지만 특정 회사의 시스템은 모르므로,
회사 코드에서 그 회사의 지식을 뽑아 사람과 AI가 함께 쓰게 하겠다는 것이
제품의 주장이다.

### 풀겠다는 문제

홈페이지는 여덟 장면을 들고,
그 원인을 회사의 진실이 한 곳에 모여 있지 않다는 데서 찾는다.
사람은 다 볼 수 없어서 모르고, AI는 볼 곳이 없어서 모른다는 설명이다.

- 시스템 전체를 아는 사람이 없다.
- 기획자가 “이거 지금 어떻게 동작해요?”라는 답을 개발자에게서 기다린다.
- 동작 하나를 확인하려고 회의를 잡고 메일을 돌린다.
- 위키가 코드를 따라가지 못해 문서가 만들자마자 낡는다.
- AI 에이전트가 전체 연결을 보지 못한 채 코드를 고쳐 멀리 있는 기능을 깨뜨린다.
- 테이블의 뜻을 아는 사람이 없어 데이터 질문이 티켓으로 쌓인다.
- 새로 온 사람이 시스템을 익히는 데 한 분기가 걸린다.
- 답이 코드 안에만 있어 장애와 고객 문의마다 개발자를 부른다.

## 동작 방식

### 네 단계

| 단계 | 이름      | 하는 일                                                             |
| ---- | --------- | ------------------------------------------------------------------- |
| 1    | 코드 지도 | 모든 저장소를 정적분석해 하나의 논리지도로 잇는다                   |
| 2    | 역번역    | 코드 지도를 비즈니스 언어로 다시 써 “비즈니스 백과사전”을 만든다    |
| 3    | 채점 연결 | 기존 문서와 데이터를 코드에 대조해 채점하고, 맞는 것만 넣는다       |
| 4    | 갱신·축적 | 코드가 바뀌면 스스로 갱신하고, 사람이 확인한 지식은 메모리에 쌓는다 |

출발점이 문서가 아니라 코드라는 점이 핵심이다.
홈페이지는 문서가 하나도 없어도 SSOT가 만들어진다고 적는다.

### 근거의 등급

홈페이지는 모든 문장에 근거를 달고,
근거가 없으면 “확인되지 않음”이라고 답한다고 내세운다.
FAQ는 근거를 두 등급으로 나눈다.
정적분석으로 확정한 연결은 코드 구조에서 증명된 것으로 본다.
동적 호출처럼 정적분석으로 잇지 못해 LLM이 추론으로 이은 연결은 따로 표시하고,
사람이 확인하면 확정 등급으로 올린다.
답을 줄 때는 근거가 어느 쪽인지 함께 보여 준다고 한다.

### 도입 절차

1. GitHub이나 GitLab 저장소를 연결한다.
   원하면 고객 서버 안에서만 실행할 수 있다.
2. 분석부터 SSOT 완성까지 1~7일이 걸린다.
   세팅비는 없다고 한다.
3. 쓰던 AI 도구에 MCP로 붙인다.
   접근 권한은 팀 단위로 관리한다.

운영 DB와 BigQuery 같은 데이터 웨어하우스도 연결할 수 있다고 한다.

### 활용 예시

홈페이지는 같은 SSOT 하나로 열 가지 일을 한다며 질문과 답의 예를 보여 준다.

| 용도                 | 질문 예시                                            |
| -------------------- | ---------------------------------------------------- |
| 시스템 지식 검색     | 상품 판매상태를 관리하는 화면과 API가 뭐야?          |
| 업무규칙 조회        | 상품 승인이 가능한 조건이 뭐야?                      |
| 화면에서 백엔드 추적 | 이 화면에서 저장을 누르면 어디를 타?                 |
| 변경 영향도 분석     | 이 컬럼을 바꾸면 어디가 영향받아?                    |
| 장애 원인 탐색       | 이 오류코드는 어디서, 어떤 조건에서 발생해?          |
| 기획 지원            | 회원 등급 개편안을 쓰게, 지금 등급 로직부터 정리해줘 |
| 개발 설계 지원       | 쿠폰 중복 사용을 막으려면 어딜 고쳐야 해?            |
| AI 코딩 지원         | 환불 규칙 수정 작업, 컨텍스트 줘                     |
| 테스트 설계          | 포인트 적립 테스트 케이스 뽑아줘                     |
| 인수인계             | 정산 업무를 처음 맡았는데, 뭐부터 봐야 해?           |

변경 영향도 예시의 답은 화면 3개, API 5개, 배치 1개가 그 컬럼을 읽고,
그중 정산 배치가 금액 계산에 직접 쓰므로 위험 지점이라고 짚는 식이다.

### 숫자, 보안, 과금

- 홈페이지가 내세우는 숫자는 세 가지다.
  저장소 연결부터 SSOT 완성까지 1~7일,
  저장소 7개 프로젝트에서 자동 생성된 문서 항목 18,979개(실측),
  근거 없이 확정되는 연결 0건이다.
- 온프레미스로 설치할 수 있고,
  코드와 분석 결과물이 고객 서버 밖으로 나가지 않는다고 한다.
- LLM 호출에 쓴 프롬프트, 소스 조각, 요청과 응답 원문은 저장하지 않고,
  처리 시간과 토큰 사용량 같은 최소 정보만 로그에 남긴다고 한다.
  LLM은 AWS Bedrock이나 Azure OpenAI처럼 고객사 인프라에서 돌릴 수 있다.
- 과금은 분석한 코드량(LOC) 기준이고 사용자 수로는 받지 않는다.
  LLM 비용도 Platty가 낸다고 한다.

## 분석

### 문서가 아니라 코드를 기준으로 삼는다

사내 지식 관리 도구는 대개 위키와 문서를 모아 검색하게 한다.
Platty는 순서를 뒤집어 코드를 먼저 읽고,
문서는 코드와 맞는지 채점한 뒤에만 받아들인다.
홈페이지가 “낡은 문서는 없느니만 못하다”고 적은 것도 이 선택의 근거다.

이 선택은 운영 중인 시스템에서는 코드가 실제 동작을 가장 정확하게 담는다는
전제에 기대고 있다.
문서는 의도를 담지만 낡을 수 있고, 코드는 의도를 담지 않지만 낡지 않는다.
Platty의 역번역 단계는 코드에서 의도를 다시 끌어내려는 작업이다.

### 정적분석과 LLM 추론을 구분해 보여 준다

FAQ에서 가장 구체적인 부분은 근거의 등급이다.
정적분석으로 확정한 연결과 LLM이 추론으로 이은 연결을 나누고,
사람의 확인을 거쳐야 추론이 확정으로 올라간다.
LLM 기반 지식 도구의 가장 큰 약점이 그럴듯한 오답인 만큼,
어느 답이 어느 근거에서 나왔는지 드러내는 구조는 신뢰를 얻는 데 필요하다.

같은 FAQ는 모든 코드베이스를 다 처리한다고 말하지 않겠다고 적는다.
표준 언어와 프레임워크는 기본으로 지원하고,
회사 고유의 공통 모듈과 래퍼 패턴은 도입 과정에서 분석 규칙을 보강하며,
완전히 다른 전용 프레임워크는 따로 협의한다.
어느 부분이 어디에 속하는지 분석 전에 문서로 준다고 한다.
마케팅 페이지로서는 드물게 한계를 먼저 밝힌 대목이다.

### MCP로 붙는 맥락 계층을 노린다

Platty는 새 앱을 쓰게 하지 않고 쓰던 AI 도구에 MCP로 붙는다고 한다.
FAQ는 모델이 좋아져도 회사의 시스템을 알게 되지는 않는다며,
자신을 모델과 경쟁하지 않고 어떤 모델이든 회사를 이해하게 만드는 층이라고
설명한다.
코딩 에이전트에게 관련 업무 규칙, 대상 코드 위치, 최근 변경 이력,
건드리면 안 되는 경계를 묶어 넘기는 예시가 이 위치를 잘 보여 준다.

## 비평

### 숫자가 무엇을 증명하는지 알 수 없다

홈페이지의 숫자 세 가지 가운데 품질을 말해 주는 것은 없다.
18,979개라는 문서 항목 수는 많이 만들었다는 뜻일 뿐,
그 항목이 맞는지, 쓸모 있는지는 말하지 않는다.
저장소 7개 프로젝트가 어떤 규모와 언어였는지도 밝히지 않는다.

“근거 없이 확정되는 연결 0건”은 정의상 거의 당연한 숫자다.
근거가 없으면 확정하지 않는다는 규칙을 세웠다면,
그 규칙을 지킨 결과가 0건인 것은 정확도의 증거가 아니다.
정작 알고 싶은 것은 근거가 있다고 확정한 연결이 실제로 맞는 비율,
그리고 추론으로 이은 연결 중 사람이 확인했을 때 틀린 비율이다.

1~7일이라는 도입 기간도 무엇에 따라 1일이 되고 7일이 되는지 설명이 없다.
코드 규모, 언어 수, 레거시 패턴이 기간을 좌우할 텐데,
FAQ가 스스로 밝힌 대로 고유 패턴의 분석 규칙을 보강해야 한다면
그 작업도 이 기간에 들어가는지 알 수 없다.

### 할루시네이션이 없다는 주장은 범위를 좁혀야 성립한다

FAQ는 답이 틀리면 어떡하냐는 질문에 플래티는 답을 지어내지 않는다고 답한다.
그러나 같은 FAQ가 LLM이 추론으로 이은 연결이 있다고 인정하고,
2단계 역번역은 코드를 비즈니스 언어로 다시 쓰는 작업이라 LLM 생성에 기댄다.
코드 위치라는 근거가 붙어 있어도,
그 코드를 비즈니스 언어로 옮긴 문장이 맞는지는 따로 확인해야 하는 문제다.

“문장마다 근거가 있다”는 것과 “문장이 맞다”는 것은 다르다.
근거 링크는 검증을 쉽게 만들 뿐 검증을 대신하지 않는다.
사용자가 근거를 실제로 열어 보지 않는다면,
근거가 붙은 오답은 근거 없는 오답보다 더 쉽게 믿어질 수 있다.

### 코드가 담지 않는 지식은 여전히 빠진다

코드는 시스템이 무엇을 하는지는 담지만, 왜 그렇게 하는지는 잘 담지 않는다.
업무 규칙에 예외가 생긴 이유, 지금은 쓰지 않지만 남겨 둔 코드,
다른 회사와의 계약 때문에 고칠 수 없는 부분은 코드만 봐서는 알기 어렵다.
홈페이지의 예시가 “마지막 조건은 지난달 커밋에서 추가됐습니다”처럼
언제 바뀌었는지는 말하지만, 왜 바뀌었는지는 말하지 않는 것도 이 한계와 맞닿는다.
사람이 확인한 지식을 메모리에 쌓는다는 4단계가 이 공백을 메우려는 장치이지만,
그 축적이 얼마나 잘 되는지는 홈페이지만으로는 알 수 없다.

## 인사이트

### 코드에서 문서를 뽑는 도구가 늘수록 문서를 쓰는 동기는 줄어든다

Platty 같은 도구가 잘 작동할수록 개발자가 문서를 직접 쓸 이유는 줄어든다.
코드에서 언제든 설명을 뽑을 수 있다면,
문서에는 코드가 담지 못하는 이유와 맥락만 남기면 된다.
문서화의 역할이 동작 설명에서 결정 기록으로 옮겨 가는 셈이다.

이 변화는 앞의 비평과 맞물린다.
코드가 담지 않는 “왜”는 누군가 남겨야만 남는데,
도구가 “무엇”을 대신 써 주면 사람들은 “왜”마저 쓰지 않게 될 수 있다.
그래서 이런 도구를 들일 때는 아키텍처 결정 기록처럼
이유를 남기는 습관을 따로 유지해야 한다.

### 과금 단위가 사용 방식을 바꾼다

Platty는 사용자 수가 아니라 분석한 코드량으로 과금하고,
전 직원과 모든 AI 에이전트가 추가 비용 없이 쓴다고 한다.
사람마다 좌석을 사야 하는 도구는 꼭 필요한 사람에게만 배포되지만,
코드량 과금은 기획자, CS 담당자, 코딩 에이전트까지 모두에게 열어 두게 만든다.
홈페이지가 개발자 호출을 줄이는 것을 핵심 효과로 내세우는 것과
맞아떨어지는 과금 구조다.

반대로 코드량 과금은 쓰지 않는 레거시 코드까지 비용으로 잡는다.
오래된 저장소를 정리하지 않은 회사일수록 비용이 커지므로,
도입 전에 분석 대상 저장소를 고르는 일이 비용 결정이 된다.

### 제품의 가치는 갱신 속도에서 판가름 난다

모든 사내 지식 도구는 처음 만들 때보다 유지할 때 실패한다.
위키가 낡는 이유는 처음에 잘못 써서가 아니라 코드가 바뀐 뒤 아무도 고치지
않아서다.
Platty가 4단계에서 코드가 바뀌면 스스로 갱신한다고 내세우는 이유도 여기에 있다.
도입을 검토한다면 처음 만든 SSOT의 품질보다,
큰 변경이 들어간 뒤 그 변경이 SSOT에 얼마나 빨리, 얼마나 정확하게 반영되는지를
시험해 보는 편이 판단에 더 도움이 된다.
