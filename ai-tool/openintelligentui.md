# OpenIntelligentUI: 질문에 맞춰 차트와 계산기와 지도를 그려 주는 오픈소스 채팅 인터페이스

<https://github.com/CopilotKit/OpenIntelligentUI>

GN 토론: <https://news.hada.io/topic?id=35735>

## 소개

OpenIntelligentUI는 CopilotKit이 만든 오픈소스 채팅 인터페이스다.
질문을 받으면 에이전트가 글 답변, 기본 컴포넌트,
직접 생성한 인터랙티브 화면 가운데 알맞은 것을 골라 대화 안에 보여 준다.
README의 설명은 이해하기, 비교하기, 그 순간에 쓸 도구 만들기 세 가지다.
기계식 설명은 단계를 밟고 변수를 바꿔 보게 하고,
비교는 기준과 가정과 절충을 나란히 놓고,
도구는 계산기나 계획표처럼 실제로 동작하는 입력을 갖춘다.
MIT 라이선스이고 TypeScript 저장소이며, 이 글을 쓴 시점에 별은 3,600개 남짓이다.

저장소는 2026년 3월 12일에 만들어졌고 처음 이름은 Open Generative UI였다.
문서는 저장소 주소가 지금은 `CopilotKit/OpenIntelligentUI`이지만
패키지 이름, 런타임 옵션, 이벤트 이름,
배포 서비스 이름은 기존 식별자를 유지한다고 적는다.[^behavior]
이름 변경 시점은 문서만으로는 알 수 없다.
OpenAI가 10월 7일 ChatGPT에 GPT-6와 함께 Intelligent UI를 도입했고,
GeekNews의 요약에 따르면 이는 텍스트 대신 버튼, 폼, 차트,
조작 가능한 도표를 대화 안에 제공하는 기능이다.[^openai-gn]
README의 시연 장면(여행 경로 지도,
비용 나누기 계산기)이 그 소개와 겹치는 점은 있지만
README는 OpenAI나 ChatGPT를 언급하지 않는다.
OpenAI의 기능을 열어 둔 대안이라는 해석은 GeekNews 쪽 제목이 붙인 틀이다.

## 동작 방식

### 요청마다 표현 방식을 먼저 정한다

사용자의 새 메시지가 오면 Jev(`jev-latest`)가 이번 답을 글,
표, 차트, 도표, 계산기, 지도 중 무엇으로 보일지 한 번 정한다.
Jev는 TypeSafe의 System One API를 통해 부르는 외부 모델이고,
최근 사용자와 어시스턴트의 글 메시지를 네 개까지, 각각 6,000자 이내로만 받는다.
API 키, 시스템 지시문, 도구의 원시 출력,
생성된 도구 코드는 받지 않는다.[^routing]

선택에 따라 렌더러가 정해진다.
기본 표는 A2UI의 표 카탈로그가 맡고
최대 12열과 200행을 받으며 출처 라벨이 필수다.
차트, 도표, 계산기, 지도는 Open Generative UI가 맡는다.
렌더러는 Jev가 검증한 선택에서 파생되므로 서로 모순되는 조합이 나올 수 없다.
Jev의 인증 실패나 잘못된 선택이나 시간 초과는
그 턴을 재시도 가능한 오류로 끝내고,
다른 라우터로 조용히 대체하지 않는다.[^routing]

### 사용자 정의 화면은 정해진 순서로 스트리밍된다

Python Deep Agent가 `generateSandboxedUi` 도구로 HTML,
CSS, JavaScript를 흘려보낸다.
매개변수는 `initialHeight`, `placeholderMessages`, `css`,
`html`, `jsFunctions`, `jsExpressions` 순서로 와야 한다.
렌더러는 CSS가 끝날 때까지 자리 표시자를 두고,
미리보기 iframe을 점진적으로 갱신하다가 최종 Websandbox iframe을 띄운다.
테마 CSS와 CDN의 importmap이 주입되고,
JavaScript는 고전 스크립트로 실행되어 최상위 await을 쓸 수 없다.[^arch]

샌드박스는 저장소나 호스트 API에 같은 출처로 접근하지 못한다.
호스트는 검증된 `sendPrompt({ text })`와 HTTPS 전용
`openLink({ url })` 두 가지 콜백만 노출한다.[^arch]
화면 안의 슬라이더와 필터는 로컬에서 돌고,
사용자가 눌러 요청한 후속 질문만 선택값을 담아 새 에이전트 턴을 시작한다.
이전에 만든 출력은 새 출력과 별개의 대화 산출물로 남고,
서로를 고치는 패치 API는 없다.[^behavior]

### 증거의 출처를 계약으로 적어 둔다

문서는 사용자가 준 값, 가져온 증거,
계산한 결과, 예시용 가정을 구분하라고 요구한다.
`query_data` 도구는 내장 샘플 CSV의 모든 행을 돌려주고 질의를 적용하지 않으며,
반환값에 샘플임을 뜻하는 표시와 질의 미적용 표시가 들어 있다.
필요한 증거가 없으면 지어내지 말고 입력을 묻거나 한계를 설명해야 한다.
숫자 도구는 빈 값, 유한하지 않은 값, 범위 밖 값,
0으로 나누기를 거부해야 한다.[^behavior]

## 실행하기

사전 요구 사항은 Node.js 22 이상, pnpm 9 이상, Python 3.12 이상, uv다.
구성은 Next.js 프런트엔드(`apps/app`), Python 에이전트와 FastAPI(`apps/agent`),
선택 사항인 MCP 서버(`apps/mcp`),
공용 디자인 시스템(`packages/design-system`)이다.

```bash
git clone https://github.com/CopilotKit/OpenIntelligentUI.git
cd OpenIntelligentUI
make setup
# 선택: apps/agent/.env 에 OPENAI_API_KEY 와 TYPESAFE_API_KEY 를 넣는다.
# 넣지 않으면 앱을 띄운 뒤 채팅 헤더의 API keys 에서 입력한다.
make dev
```

앱은 `http://localhost:3000`,
에이전트 상태 확인은 `http://localhost:8123/health`다.
기본 답변 모델은 OpenAI가 최신 ChatGPT Instant에 붙인 별칭 `chat-latest`이고,
문서는 이것이 고정된 스냅샷이 아니라 움직이는 별칭이라고 밝힌다.[^routing]
`LLM_MODEL`을 `claude-*`나 `gpt-*`로 바꿀 수 있다.[^deploy]

### 키를 직접 넣는 방식과 서버에 두는 방식

채팅은 첫 메시지를 보내기 전에 OpenAI 키와 Jev 키를 모두 요구한다.
키는 브라우저 메모리에만 있고 새로고침이나 지우기에서
사라지며 저장소에는 쓰지 않는다.
요청은 애플리케이션 서버를 거쳐 각 제공자로 가고,
채팅 상태와 체크포인트에는 남지 않으며,
이 키를 쓴 요청에서는 호스팅 LangSmith 추적이 꺼진다.
README는 운영자를 신뢰할 수 있는 배포에서만 이 기능을 쓰라고 경고한다.
서버에 공유 키를 설정한 배포에서는
키 없이 직접 API를 부르는 클라이언트도 그 서버 자격 증명을 쓸 수 있다.

### 배포할 때의 한계

Render용 `render.yaml`은 에이전트와 앱 두 서비스를 정의하고
각각 1~3대로 확장할 수 있다.
에이전트 체크포인트는 프로세스 메모리의
`BoundedMemorySaver`(최대 스레드 200개)에 있고,
프런트엔드의 요청 제한도 프로세스 안에서만 동작한다.
재시작하거나 확장하면 대화 상태를 잃거나 나뉘고, 요청 제한 동작도 달라진다.
내구성 있는 공유 저장소와 조율된 제한에는 별도 인프라가 필요하다고
문서가 직접 적는다.[^deploy][^arch]

## 비평

### 오픈소스라는 이름과 두 개의 상용 API 의존이 같이 있다

코드는 MIT이지만 기본 경로는 OpenAI 키와 TypeSafe 키가 모두 필요하다.
표현 방식을 고르는 Jev는 외부 서비스이고,
문서에는 선택이 실패하면 턴이 실패한다고만 있다.
내가 읽은 README와 문서에서는 Jev 없이 돌리는 설정을 찾지 못했다.
모델은 `claude-*`나 `gpt-*`로 바꿀 수 있으니 답변 쪽은 열려 있지만,
어떤 화면으로 보일지의 결정은 닫힌 서비스 하나에 달려 있다.
이 문서가 확인한 것은 읽은 범위까지이며,
코드에 대체 경로가 있는지는 열어 보지 않았다.

비용과 가용성도 따라온다.
README는 사용량이 각자의 제공자 계정으로 청구된다고 적는다.
`chat-latest`는 별칭이어서 같은 설정이 시간이 지나면 다른 모델로 답할 수 있다.

### 시연 영상은 신뢰성의 증거가 아니다

README의 54초 영상은 발표용으로 렌더링한 장면이라고 스스로 밝힌다.
앱은 요청마다 에이전트를 돌리며
어떤 방식으로 보일지는 Jev가 고르므로 출력이 달라질 수 있다고 적는다.
각 장면은 4초에서 8초로 짧고,
견본 숫자는 예시일 뿐 실제 사업이나 날씨 자료가 아니며
지도의 연결선은 검증된 운전 경로가 아니라고 거듭 밝힌다.
정직한 단서이지만, 영상이 보여 주는 것은 성공한 한 번이지 성공률이 아니다.
문서에도 라우팅은 모델의 판단이며
객관적으로 가장 좋은 시각화를 보장하지 않는다는 문장이 있다.[^routing]

### 기본으로 켜진 사용 통계는 끌 수 있지만 알아야 한다

이 앱은 설치마다 최대 두 번 익명 이벤트를 CopilotKit으로 보낸다.
앱의 UI가 런타임에 처음 닿을 때와 에이전트의 첫 실행이 오류 없이 끝났을 때다.
설치 ID와 플랫폼과 버전 같은 메타데이터만 가고
프롬프트와 답변과 키는 가지 않는다고 문서는 적는다.
`DO_NOT_TRACK=1`이나 `COPILOTKIT_TELEMETRY_DISABLED=1`로 끌 수 있고,
끄면 저장된 설치 ID가 지워진다.
호스팅 데모는 브라우저에서 PostHog 분석을 불러오지만
세션 기록은 방문자가 키를 입력하므로 항상 꺼 둔다.[^telemetry]
템플릿을 가져다 쓰는 입장에서는
기본값이 옵트아웃이라는 점을 배포 전에 확인할 일이다.

### 생성된 코드를 실행하는 표면이 넓다

모델이 만든 HTML과 JavaScript가 사용자 브라우저에서 실행된다.
샌드박스 iframe과 검증된 두 콜백이 경계이고,
문서는 이 경계를 건드리지 말라고 당부한다.[^arch]
그래도 실행 환경은 CDN의 importmap을 불러오고,
`sendPrompt`는 화면이 에이전트의 다음 턴을 시작시키는 통로다.
문서는 로드나 타이머나 입력 변화에서 자동으로 메시지를 보내지 말라고 하지만
이는 생성되는 코드가 지켜야 할 규칙이지 렌더러가
강제하는 장치인지는 읽은 문서에서 확인하지 못했다.
이 문서의 판단으로는 생성 코드가 어디까지 호스트에 말을
걸 수 있는지를 직접 시험해 본 뒤에 공개 배포해야 한다.

## 인사이트

### 무엇을 보일지와 어떻게 그릴지를 분리하면 라우터의 실수가 제품의 실수가 된다

Jev가 표현 방식을 고르고 그 선택에서
렌더러가 파생되는 구조는 요청의 형태에 따라 뷰를 고르는 오래된 방식과 같다.
HTTP의 콘텐츠 협상이나 MVC 컨트롤러가 뷰를 고르는 것과 닮았다.
이 구조는 얻는 것이 분명하다. 답변 모델이 고르면서
쓰는 비용 없이 작은 모델이 빠르게 정하고,
모순된 조합이 구조적으로 생기지 않는다.

대가는 라우터의 오판이 곧 사용자가 보는 오류라는 점이다.
표가 알맞은 질문에 계산기가 나오면 답변 모델은 그 계약대로 따를 뿐이다.
라우터는 최근 네 개 메시지만 보므로
긴 대화의 앞부분이 결정에 영향을 주지 못한다.
저장소가 실패 시 다른 라우터로 조용히 대체하지 않기로 한 것은 같은 맥락에서
이해된다.
오판은 드러나게 하되 가짜 결정을 만들지 않겠다는 선택이고,
그 대가로 외부 서비스의 장애가 곧 대화의 장애가 된다.

### 매개변수의 순서가 곧 스트리밍 프로토콜이다

CSS가 먼저, HTML이 다음, JavaScript가 마지막이라는 순서는
취향이 아니라 화면을 점진적으로 그리기 위한 조건이다.
스타일 없이 마크업이 먼저 보이면 깜빡이고,
끝나지 않은 스크립트는 실행할 수 없다.
렌더러가 CSS가 끝날 때까지 자리 표시자를 두는 것은
HTML 파서가 스타일시트를 기다리는 방식과 같은 발상이다.

이 설계는 모델의 출력 순서를 프로토콜 계약으로 만든다.
스키마의 필드 순서를 바꾸는 것이 곧 호환성을 깨는 일이므로,
모델을 바꾸거나 프롬프트를 고칠 때 이
순서가 지켜지는지가 회귀 시험의 대상이 된다.
문서가 화면을 만들기 전의 순서를 따로 명시해 둔 것은 이를 알고 있다는 신호다.

### 화면 상태는 기본적으로 에이전트의 기억이 아니다

생성된 화면의 슬라이더와 입력은 로컬에서 돌고,
에이전트는 사용자가 눌러 보낸 값만 안다.
후속 질문은 새 턴이고 새 산출물이며, 이전 산출물을 고치는 패치 API는 없다.
이는 옛 웹의 폼과 같다. 입력 중의 상태는 브라우저에 있고,
제출할 때에야 서버로 간다.

이 선택은 단순하고 예측 가능하지만 비용이 있다.
작은 변경도 화면 전체를 다시 생성하므로 지연과 토큰이 든다.
사용자는 조작한 결과를 바탕으로 이어 가는 대화를 기대하는데,
에이전트가 그 상태를 모르면 대화와 화면이 어긋난다.
문서가 선택값을 명시적으로 `sendPrompt`에 담으라고
권하는 것은 이 간극을 설계자에게 넘긴 것이다.

### 생성형 화면은 지어낸 숫자를 권위 있게 보이게 하므로 출처 표시가 기능이다

글이 아니라 표와 차트로 나온 숫자는 같은 숫자라도 더 믿음직해 보인다.
이 저장소는 그 위험을 설계에 넣었다.
표에는 출처 라벨이 필수이고,
`query_data`는 샘플이라는 표시와 질의를 적용하지 않았다는 표시를 달고,
지도 연결선은 운전 경로가 아니라고 분명히 적는다.

이 선택은 보이는 화면의 완성도와 반대 방향으로 움직인다.
라벨과 단서가 많아질수록 시연은 덜 매끄러워진다.
그런데 사용자가 표와 차트를 의사결정에 쓰기 시작하면
이 라벨이 유일한 방어선이 된다.
같은 분야의 다른 도구를 평가할 때도 화면이 얼마나 근사한지보다
그 화면이 값의 출처와 가정을 얼마나 눈에 띄게 말하는지를 먼저 보는 편이 낫다.
