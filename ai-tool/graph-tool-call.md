# graph-tool-call: 도구 카탈로그를 그래프로 다뤄 필요한 것만 꺼내기

<https://github.com/SonAIengine/graph-tool-call>

GN 토론: <https://news.hada.io/topic?id=32066>

## 소개

LLM 에이전트에 붙일 도구가 많아질 때 생기는 문제를 다루는 파이썬 라이브러리다.
2026년 1월 16일에 만들어졌고 MIT 라이선스이며, 8월 초 기준 스타 9개다.
PyPI에 `graph-tool-call`로 올라와 있고 코어 패키지는 의존성이 없다.

저자가 GeekNews에 쓴 문제 제기가 구체적이다.
GitHub, Slack, 데이터베이스, 브라우저, 사내 API를 에이전트에 붙였더니 성능이
올라가는 대신 떨어졌다는 것이다.
원인은 세 가지였다. 쓰지 않는 도구가 컨텍스트를 잡아먹고, 비슷한 도구끼리 혼동을
일으키고, 필요한 파라미터가 없어서 목표 도구를 실행하지 못한다.

README는 이 중 마지막 문제를 특히 강조한다.
“내 주문을 환불해 줘”를 벡터 검색하면 `refundOrder`가 나오는데, 그 도구는
`order_id`를 요구한다.
실제로 쓸 수 있는 흐름은 그 ID를 만들어내는 도구에서 시작한다.
벡터 검색은 **비슷한** 도구를 찾지만 그 도구가 속한 **워크플로**를 놓친다는 것이
이 프로젝트의 출발점이다.

## 동작 방식

파이프라인은 단순하다.

```text
OpenAPI / MCP / Python 함수 → 수집 → 도구 그래프 구축 → 하이브리드 검색 → 에이전트
```

“주문을 취소하고 환불을 처리해 줘”라는 요청에서 벡터 검색은 `cancelOrder`를
찾지만, 실제 워크플로는 `listOrders`가 `getOrder`와 `cancelOrder`에 선행하고
(PRECEDES), `cancelOrder`가 `processRefund`와 짝을 이루는(COMPLEMENTARY) 구조다.
graph-tool-call은 도구 하나가 아니라 사슬 전체를 돌려준다.

검색은 네 가지 신호를 가중 상호 순위 융합(wRRF, weighted Reciprocal Rank Fusion)으로
합친다.

- **BM25** — 키워드 매칭
- **그래프 순회** — 관계 기반 확장(PRECEDES, REQUIRES, COMPLEMENTARY)
- **임베딩 유사도** — 의미 검색(선택, 임의 제공자)
- **MCP 어노테이션** — read-only / destructive / idempotent 힌트

MCP 어노테이션(`readOnlyHint`, `destructiveHint`, `idempotentHint`,
`openWorldHint`)은 질의 의도를 자동 분류해 검색 신호로 쓴다.
읽기 질의에는 읽기 전용 도구를, 삭제 질의에는 파괴적 도구를 우선한다.

## 설치와 사용

코어는 파이썬 표준 라이브러리만 쓴다. 필요한 것만 골라 설치한다.

```bash
pip install graph-tool-call                # 코어 (BM25 + 그래프), 의존성 없음
pip install graph-tool-call[embedding]     # + 임베딩, 크로스 인코더 리랭커
pip install graph-tool-call[openapi]       # + OpenAPI YAML 지원
pip install graph-tool-call[mcp]           # + MCP 서버 / 프록시 모드
pip install graph-tool-call[all]           # 전부
```

설치 없이 30초 만에 확인해 볼 수 있는 데모도 있다.

```bash
uvx graph-tool-call demo dependency-chain
```

```text
Query: "Refund the order for alice@example.com"

Selected target:
  refundOrder(order_id)

Required producer:
  findOrdersByEmail(email) -> order_id
  evidence: api_contract, openapi_link

Execution order:
  1. findOrdersByEmail
  2. refundOrder
```

파이썬 API는 OpenAPI 문서에서 바로 그래프를 만든다.

```python
from graph_tool_call import ToolGraph

tg = ToolGraph.from_url(
    "https://petstore3.swagger.io/api/v3/openapi.json",
    cache="petstore.json",
)
print(tg)
# → ToolGraph(tools=19, nodes=22, edges=100)

tools = tg.retrieve("create a new pet", top_k=5)
```

`plan_workflow()`는 선행 조건을 포함한 순서 있는 실행 사슬을 돌려준다.
에이전트의 왕복을 3~4회에서 1회로 줄인다는 설명이다.

## 통합 방식

여러 통합 패턴을 제공하고, 스택에 맞춰 고르게 되어 있다.

| 사용 환경 | 패턴 | 토큰 절감 |
| --- | --- | --- |
| Claude Code / Cursor / Windsurf | MCP 프록시(N개 서버 → 3개 메타 도구) | 턴당 약 1,200토큰 |
| LangChain v1 / LangGraph (50개 이상) | 모델 호출 미들웨어 또는 게이트웨이 도구 | 92% |
| OpenAI Responses / Chat / Anthropic SDK | 미들웨어(1줄 패치) | 76~91% |
| OpenAI Agents / PydanticAI / Google ADK | 원격 MCP 서버 | 경우에 따라 다름 |

가장 흔한 쓰임은 MCP 프록시다. 여러 MCP 서버의 도구 이름이 매 턴 쌓이는 문제를
하나의 서버 뒤로 묶어 172개 도구를 3개 메타 도구로 줄인다.

SDK 미들웨어는 한 줄로 끝난다.

```python
from graph_tool_call.middleware import patch_openai

patch_openai(client, graph=tg, top_k=5)   # ← 이 한 줄 추가
# 기존 코드 그대로. 248개 도구가 들어가고 관련된 5개만 전송된다
```

## 벤치마크

릴리스 대표 수치는 결정적(deterministic) 7건 커머스 회귀 테스트다.
목표 도구가 선택된 뒤 그래프 확장이 필요한 생산자(producer)를 모두 추가하는지를
묻는다. LLM이나 외부 API는 관여하지 않는다.

| 지표                        | 목표 도구만 | 그래프 + 생산자 |
| --------------------------- | ----------: | --------------: |
| 필수 생산자 재현율          |      0.1429 |      **1.0000** |
| 후보 계획 커버리지          |      0.4762 |      **1.0000** |
| 후보 바인딩 지원            |      0.1429 |      **1.0000** |
| 불필요한 확장 사례          |           0 |           **0** |

저장소에는 입력 해시, 기대 목표와 생산자, 후보 목록, 지표, 한계, 재실행 명령을
담은 사례 수준 아티팩트가 커밋돼 있다.
`make launch-evidence`로 재현할 수 있다.

이 밖에 BFCL v4 함수 호출 JSONL을 이용한 결정적 검색 벤치마크가 있고, README는
이것이 BFCL 리더보드의 모델 AST 점수가 아니며 정답 함수 이름이 상위 K개 안에
들어오는지만 묻는다고 명시한다.
`paper-*`, `xgen-*` 계열의 make 타깃이 여러 개 준비돼 있는데, 대부분 모델을 쓰지
않는 결정적 검사이고 일부만 고정된 E5 인코더나 CLI로 지정한 모델을 쓴다.

## 분석

### 이 라이브러리가 푸는 것은 검색 문제가 아니라 의존성 문제다

이름과 소개만 보면 도구 검색기(tool retriever)로 읽히지만, 실제 기여는 다른 데
있다.
RAG로 도구를 골라 컨텍스트를 줄이는 발상 자체는 새롭지 않다. 도구 설명을 임베딩해
질의와 유사한 것만 넣는 방식은 이미 여러 곳에서 쓰인다.

이 프로젝트가 겨누는 것은 그 방식이 구조적으로 놓치는 지점이다.
유사도 검색은 “질의와 닮은 도구”를 찾는데, 에이전트에게 필요한 것은 “지금 실행
가능한 도구”다.
`refundOrder`는 질의와 가장 닮았지만 `order_id`가 없으면 호출할 수 없다.
`findOrdersByEmail`은 질의와 별로 닮지 않았지만 반드시 필요하다.
유사도라는 척도로는 이 둘의 관계를 표현할 방법이 없다.

그래서 그래프를 쓴다.
PRECEDES, REQUIRES, COMPLEMENTARY라는 관계 타입은 유사도가 아니라 **실행 가능성**을
모델링한다.
벤치마크 지표 이름이 “필수 생산자 재현율(required-producer recall)”인 것도 이
관점을 반영한다. 관련 있는 도구를 얼마나 찾았는가가 아니라, 실행에 필요한 선행
도구를 빠뜨리지 않았는가를 묻는다.

이 전환은 문제 정의를 바꾼 것이지 알고리즘을 개선한 것이 아니다.
그리고 문제 정의가 바뀌었으므로 기존 방식과의 비교에서 큰 차이가 나는 것은
당연하다. 목표 도구만 뽑는 방식의 필수 생산자 재현율이 14.3%라는 것은, 그 방식이
생산자를 찾으려 하지 않았다는 뜻이지 성능이 나쁘다는 뜻이 아니다.

### 관계를 어디서 얻는가가 이 접근의 성패를 가른다

그래프 기반 검색의 핵심 질문은 “간선을 누가 그리는가”다.
도구 사이의 PRECEDES와 REQUIRES 관계를 사람이 손으로 정의해야 한다면 이 라이브러리의
실용성은 크게 떨어진다. 도구가 수백 개일 때 관계는 수천 개가 되기 때문이다.

README를 보면 이 문제를 OpenAPI 스펙에서 자동 추출하는 방식으로 푼다.
데모 출력의 `evidence: api_contract, openapi_link`가 그 근거다.
어떤 엔드포인트가 `order_id`를 응답으로 내보내고 어떤 엔드포인트가 그것을 요청으로
받는지를 스키마에서 읽어 생산자-소비자 관계를 만든다.

이 구조를 뒷받침하는 세부가 README에 꽤 길게 나온다.
요청 계약에서 `readOnly` 필드를 제외하고 응답 계약에서 `writeOnly` 필드를 제외해,
생성된 도구 입력과 그래프 간선이 각 필드가 실제로 이동할 수 있는 방향과 어긋나지
않게 한다는 것이다.
`oneOf`/`anyOf` 스키마를 분기 근거를 남긴 채 필드 합집합으로 읽어 첫 분기 이후를
조용히 버리지 않는다는 서술도 있다.
스키마가 빈약한 `object`뿐이고 예시만 있는 경우 예시에서 계약 행을 유도한다는
처리도 있다.

이 정도 수준의 스펙 해석은 실제 사내 Swagger 문서를 다뤄 본 흔적으로 읽힌다.
공개 API 스펙은 대체로 정갈하지만 사내 API 스펙은 그렇지 않고, 위에 나열된 예외
처리는 정갈하지 않은 스펙에서만 필요한 것들이다.

동시에 이 의존이 이 접근의 적용 범위를 정한다.
관계를 스키마에서 자동으로 뽑을 수 있는 도구 — OpenAPI로 기술된 REST API — 에서는
잘 동작하고, 그렇지 않은 도구에서는 근거가 약해진다.
MCP 도구와 파이썬 함수도 수집 대상이지만, 이들에게는 응답 스키마가 명세되지 않는
경우가 흔하다.

### 저자의 다른 저장소들이 이 프로젝트의 맥락을 설명한다

같은 계정의 저장소 목록을 보면 이 프로젝트가 고립된 아이디어가 아님이 드러난다.
`api-to-tools`는 OpenAPI, WSDL/SOAP, GraphQL, gRPC를 LLM이 호출 가능한 도구 정의로
바꾸는 라이브러리이고, `ai-api-lint`는 OpenAPI 스펙이 LLM 도구 호출에 적합한지
검사하는 린터다.
`mcp-pipeline`은 MCP 서버용 상태 저장 파이프라인 프레임워크다.

세 프로젝트가 같은 문제의 다른 층을 다룬다.
스펙을 도구로 변환하고(api-to-tools), 스펙 품질을 검사하고(ai-api-lint), 도구가
많아졌을 때 골라내고(graph-tool-call), 도구를 엮어 실행한다(mcp-pipeline).
`graph-tool-call[lint]` extra가 ai-api-lint를 설치해 나쁜 스펙을 자동 수정한다는
점에서 실제로 연결돼 있기도 하다.

이 배치는 저자가 “기존 사내 API를 LLM 에이전트에 붙이는 일”이라는 구체적 업무를
반복해서 다뤄 왔음을 시사한다.
그렇게 보면 앞서 짚은 OpenAPI 편향은 약점이라기보다 의도된 초점이다.
사내에 수백 개의 REST 엔드포인트가 있고 그것을 에이전트에 노출하려는 조직이
1차 대상 사용자다.

## 비평

### 대표 벤치마크가 자체 제작 7건이다

README 최상단에 크게 걸린 표 — 14.3% 대 100% — 가 나온 실험이 무엇인지 확인하면
평가가 달라진다.
“결정적 7건 커머스 회귀 테스트”이고, 이 픽스처는 저자가 만든 것이다.

7건이라는 표본 크기 자체가 통계적 주장을 하기에 부족하지만, 더 큰 문제는 픽스처와
알고리즘이 같은 사람에게서 나왔다는 점이다.
“목표 도구가 선택된 뒤 필요한 생산자를 모두 추가하는가”라는 질문은 이 라이브러리가
하도록 설계된 바로 그 일이다.
그 일을 하도록 만든 시스템이 그 일을 100% 해낸다는 결과는 정보량이 크지 않다.

비교 대상인 “목표 도구만(target only)”도 공정한 기준선이 아니다.
이건 경쟁 라이브러리가 아니라 생산자 확장을 끄고 돌린 자기 자신이다.
기능을 켜면 그 기능이 측정하는 지표가 올라간다는 것을 보인 셈이다.
14.3%라는 숫자는 벡터 검색의 성능이 아니라 “생산자를 찾지 않는 방식은 생산자를
찾지 않는다”는 동어반복에 가깝다.

README가 정직한 대목도 있다.
BFCL 관련 절에서 이것이 BFCL 리더보드 점수가 아니라고 명시하고, qwen3.6 수치가
로컬 증거이지 리더보드 주장이 아니라고 밝힌다.
과거의 모델 참여(model-in-the-loop) 결과가 전체 벤치마크 문서에 남아 있지만 현재
릴리스 헤드라인으로 쓰지 않는다는 서술도 있다.

그런데 이 정직함이 오히려 질문을 만든다.
왜 모델을 실제로 쓴 결과를 헤드라인에서 내리고 결정적 픽스처를 올렸는가.
모델 참여 결과는 재현이 어렵고 변동이 크다는 이유가 있을 수 있지만, 이 라이브러리의
가치 주장 — “에이전트 정확도가 올라간다” — 을 검증하려면 결국 모델이 관여해야 한다.
검색 단계에서 올바른 도구가 후보에 들어왔다는 것과 모델이 그것을 골라 제대로
호출했다는 것은 다른 명제다.

### 저장소 설명과 README 표의 숫자가 다르다

저장소 한 줄 설명은 “248 tools → 82% accuracy, 79% fewer tokens”다.
그런데 README 벤치마크 절에는 이 수치가 없다.
82%와 79%가 어느 실험에서 나온 것인지 README 본문만 봐서는 알 수 없고, `docs/`
아래 별도 문서를 봐야 한다.

통합 표의 토큰 절감 수치도 제각각이다.
LangChain은 92%, SDK 미들웨어는 76~91%, MCP 프록시는 턴당 약 1,200토큰, 나머지는
“경우에 따라 다름”이다.
92%가 62개 도구를 게이트웨이 2개로 바꿨을 때의 값이라는 설명은 붙어 있지만, 이건
당연한 산술이다. 도구 정의를 안 넣으면 그만큼 토큰이 준다.

여기서 놓치는 것이 비용의 반대편이다.
도구를 컨텍스트에서 빼면 에이전트는 `search_tools`를 먼저 호출하고 결과를 받은 뒤
다시 판단해야 한다. 왕복이 늘고, 검색 결과 자체도 토큰을 쓴다.
“92% 토큰 절감”은 첫 요청의 프롬프트 크기만 비교한 값으로 보이고, 대화 전체의
누적 토큰이나 지연 시간은 계산에 없다.
`plan_workflow()`가 “왕복을 3~4회에서 1회로 줄인다”고 주장하는 것을 보면 저자도
왕복 문제를 인식하고 있는데, 두 수치가 같은 표에서 정산되지는 않는다.

### make 타깃 30개가 신뢰를 주는 방향으로만 작동하지 않는다

README 후반부에는 `paper-corpus-check`, `paper-adapter-conformance`,
`paper-graph-ablation`, `paper-producer-coverage`, `paper-output-promotion`,
`xgen-benchmark`, `xgen-scale-acceptance`, `xgen-scale-sweep`,
`xgen-scale-contract-ablation`, `xgen-scale-028-gate-check`, `bfcl-028-gate-check`
등이 표로 나열된다.

이름에 “paper”가 붙은 것을 보면 논문 투고를 염두에 둔 검증 체계로 보인다.
독립적인 어노테이션 검토 커버리지를 포함하는 “더 엄격한 논문 게이트”라는 서술도
있다.
학술적 엄밀성을 지향하는 것 자체는 좋은 일이다.

문제는 이 목록이 README를 읽는 사람에게 무엇을 주는가다.
스타 9개짜리 라이브러리를 검토하는 개발자가 알고 싶은 것은 “내 도구 200개에 붙이면
잘 되는가”이고, 이 질문에 답하는 것은 30개의 make 타깃이 아니라 하나의 재현 가능한
실전 결과다.
검증 목록이 길어질수록 오히려 어느 것이 핵심 증거인지 흐려진다.

앞서 [온글 번역](ongeul-local-translator.md)에서 본 것과 같은 양상이다.
검증 자체의 생산 비용이 내려가면서 검증의 양이 프로젝트의 신뢰도와 비례하지 않게
됐다.
30개의 결정적 검사 대부분이 “모델 없음(none)”으로 표기돼 있다는 점이 이를 뒷받침한다.
모델 없이 돌리는 검사는 빠르고 재현 가능하지만, 이 라이브러리의 최종 사용자는
모델이다.

### 도구 선택 문제를 도구 하나 더 늘려서 푼다

가장 근본적인 긴장은 접근 방식 자체에 있다.
문제는 “에이전트에 붙은 도구가 많아서 잘못 고른다”였다.
해법은 도구 카탈로그를 관리하는 별도의 계층을 하나 더 넣는 것이다.

MCP 프록시 패턴에서 172개 도구가 3개 메타 도구로 줄어드는 것은 분명한 개선처럼
보인다.
그런데 에이전트 입장에서 달라진 것은 “172개 중 하나를 고르기”가 “3개 중 하나를
고른 뒤 자연어로 원하는 도구를 설명하기”로 바뀐 것이다.
선택 문제가 사라진 게 아니라 검색 질의 작성 문제로 형태를 바꿨다.

그리고 그 검색이 틀리면 에이전트는 존재하는 도구를 못 찾는다.
이 실패는 이전보다 진단하기 어렵다.
도구가 컨텍스트에 있는데 안 고른 경우는 로그에서 보이지만, 검색 단계에서 걸러져
컨텍스트에 없었던 경우는 왜 그 도구를 안 썼는지가 보이지 않는다.
README의 하이브리드 검색 구성 — BM25 + 그래프 순회 + 임베딩 + MCP 어노테이션을
wRRF로 융합 — 은 정교하지만, 정교할수록 왜 특정 도구가 상위 5개에 못 들었는지
설명하기 어려워진다.

GeekNews에서 jimmy2056이 남긴 반응이 이 지점을 우연히 건드린다.
MCP와 스킬을 넣을수록 좋아지기는커녕 잘못된 도구 선택으로 `agents.md`만 자꾸
커져서 고민이었는데 한번 써봐야겠다는 것이다.[^jimmy2056]
`agents.md`가 커진다는 것은 도구 선택을 프롬프트 지시로 교정하려다 실패한 흔적이다.
graph-tool-call은 그 교정을 검색 알고리즘으로 옮기는데, 검색이 틀렸을 때 무엇을
고쳐야 하는지는 프롬프트를 고치는 것보다 덜 분명하다.

## 인사이트

### 도구 카탈로그가 커지면 데이터베이스 문제가 된다

이 라이브러리를 보면 에이전트 도구 관리가 어느 방향으로 가고 있는지 보인다.
도구가 열 개일 때는 프롬프트에 나열하면 됐다. 백 개가 되자 검색이 필요해졌다.
천 개가 되면 스키마, 인덱스, 질의 계획, 조인이 필요해진다.

graph-tool-call이 실제로 구현한 것을 이 언어로 옮기면 명확하다.
OpenAPI 스펙에서 계약을 읽는 것은 스키마 추출이고, `readOnly`/`writeOnly`를 구분해
필드 이동 방향을 맞추는 것은 참조 무결성이고, PRECEDES/REQUIRES 간선은 외래 키
관계이며, `plan_workflow()`는 질의 계획 수립이다.
BM25와 임베딩과 그래프 순회를 wRRF로 합치는 것은 여러 인덱스를 결합하는 실행
계획에 해당한다.

이 관점이 시사하는 바는 앞으로 필요해질 것들이다.
데이터베이스가 겪은 문제를 도구 카탈로그도 겪게 된다.
스키마 변경(도구가 바뀌면 그래프를 다시 만들어야 하는가), 일관성(여러 MCP 서버에
같은 도구가 있을 때 무엇이 정본인가), 권한(어떤 사용자에게 어떤 도구가 보이는가),
관측 가능성(왜 이 도구가 선택됐는가)이 차례로 문제가 된다.

지금 이 영역은 각 프로젝트가 자기 방식으로 푸는 단계다.
그런데 도구 카탈로그가 조직 자산이 되면 — 사내 API 300개를 그래프로 만들어
여러 팀이 공유하는 상황 — 표준화 압력이 생긴다.
MCP가 도구 인터페이스를 표준화했듯, 도구 **카탈로그**를 기술하는 층이 다음
표준화 대상이 될 가능성이 있다.
graph-tool-call이 정의한 PRECEDES/REQUIRES/COMPLEMENTARY 같은 관계 타입이 그
논의의 초기 어휘가 될 수 있다.

### 컨텍스트 절감 주장은 총비용으로 다시 계산되어야 한다

“92% 토큰 절감” 같은 수치가 에이전트 도구 생태계에서 표준적인 마케팅 문구가 되고
있다.
이 수치들이 대부분 첫 프롬프트의 크기만 비교한다는 점은 짚어둘 필요가 있다.

실제 비용은 세 층에서 발생한다.
첫째, 프롬프트에 실린 도구 정의 토큰. 이건 줄어든다.
둘째, 검색 호출과 그 결과를 다시 컨텍스트에 넣는 토큰. 이건 늘어난다.
셋째, 검색이 틀렸을 때의 재시도. 이건 확률적으로 늘어난다.

세 번째가 특히 계산에서 빠진다.
도구를 전부 컨텍스트에 넣으면 모델이 잘못 고를 확률은 있지만 못 찾을 확률은 없다.
검색을 끼우면 못 찾을 확률이 새로 생기고, 그 경우 에이전트는 다른 질의로 다시
검색하거나 포기한다.
재시도 한 번의 비용이 도구 정의 50개를 컨텍스트에 넣는 비용보다 클 수 있다.

여기서 도구 개수에 따른 손익분기점이라는 개념이 나온다.
도구가 20개라면 전부 넣는 것이 거의 확실히 낫다. 200개라면 검색이 유리해진다.
그 사이 어딘가에 경계가 있고, 그 경계는 도구들의 유사도 분포와 질의의 성격에 따라
달라진다.
graph-tool-call의 통합 표가 “LangChain v1 / LangGraph (50개 이상)”이라고 조건을
단 것은 이 경계를 암묵적으로 인정한 것인데, 그 숫자의 근거는 제시되지 않는다.

이 계산이 중요해지는 이유는 컨텍스트 창이 계속 커지고 있기 때문이다.
100만 토큰 컨텍스트에서 도구 200개 정의는 큰 부담이 아니다.
그러면 남는 문제는 토큰이 아니라 주의력 — 모델이 많은 선택지 앞에서 더 자주
틀린다는 것 — 이 된다.
토큰 절감을 앞세운 도구들이 실제로 팔아야 하는 가치는 비용이 아니라 정확도이고,
정확도는 훨씬 측정하기 어렵다.

### 실행 가능성 그래프는 에이전트 안전장치로 재해석될 수 있다

이 라이브러리는 검색 정확도를 위해 도구 사이의 의존 관계를 모델링했다.
그런데 같은 그래프가 전혀 다른 목적에 쓰일 수 있다.

MCP 어노테이션을 검색 신호로 쓴다는 부분이 그 실마리다.
`destructiveHint`가 붙은 도구를 삭제 질의에서 우선한다는 것은 지금은 정확도를
위한 처리다.
같은 정보를 반대로 쓰면 안전장치가 된다. 파괴적 도구에 도달하는 경로에 승인 단계를
끼우거나, 특정 생산자 없이는 파괴적 도구를 실행할 수 없게 강제하는 식이다.

`plan_workflow()`가 실행 순서를 미리 내놓는다는 점은 이 방향에서 더 흥미롭다.
에이전트가 도구를 하나씩 호출하며 나아가면 사람이 개입할 지점을 잡기 어렵다.
계획 전체가 실행 전에 나오면 그 계획을 검토하고 승인하거나 거부할 수 있다.
[에이전트형 코딩의 실패 패턴](../agentic-coding/agentic-software-levels.md)에서
반복되는 질문 — 어디까지 자율을 주고 어디서 사람이 개입하는가 — 에 대해, 실행
계획을 명시적 객체로 만드는 것은 구체적인 답 하나가 된다.

`plan.save(“refund_workflow.json”)`으로 계획을 파일로 저장할 수 있다는 점도
같은 맥락에서 읽힌다.
저장된 계획은 검토 대상이 되고, 버전 관리가 되고, 승인된 계획만 실행하도록
제한할 수 있다.
앞서 [agent-device](agent-device.md)의 `.ad` 스크립트가 탐색을 자산으로 바꾼 것과
같은 구조다. 비결정적 탐색 단계와 결정적 실행 단계를 분리하는 것이다.

이 재해석이 시사하는 바는 도구 검색 계층의 최종 형태가 검색기가 아닐 수 있다는
것이다.
지금은 “많은 도구 중 맞는 것 고르기”가 문제로 설정돼 있지만, 도구가 실제로 사내
시스템을 건드리기 시작하면 “무엇을 실행하도록 허용할 것인가”가 더 큰 문제가 된다.
그때 필요한 것은 도구 사이의 관계를 아는 계층이고, 그 계층은 지금 검색 정확도를
위해 만들어지고 있다.
