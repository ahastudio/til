# CLIProxyAPI: AI 구독 계정을 표준 API로 바꿔 주는 프록시

<https://github.com/router-for-me/CLIProxyAPI>

## 소개

CLIProxyAPI는 OpenAI, Gemini, Claude, Codex, Grok 호환 API 인터페이스를
제공하는 프록시 서버다.
핵심 아이디어는 API 키가 아니라 OAuth 로그인으로 얻은 구독 계정을 로컬
프록시 뒤에 두고, 그것을 표준 API 형태로 노출하는 것이다.
그러면 기존 SDK나 클라이언트가 코드를 바꾸지 않고도 구독 모델을 호출할
수 있다.

저장소 규모는 작지 않다.
스타 50.3천 개, 포크 7.7천 개, main 브랜치 커밋 3,633개, 이슈 90개,
풀 리퀘스트 448개다.
라이선스는 MIT이고, 안내 문서는 `help.router-for.me`에 있으며 관리 API와
SDK 문서가 따로 제공된다.

## 지원 제공자와 기능

지원 목록은 주요 상용 모델을 폭넓게 덮는다.
Kimi(K3, K2.7 Code)는 OAuth 또는 호환 API로, OpenAI는 GPT 5.6과 5.5
계열, Anthropic Claude는 Fable·Opus·Sonnet 계열, Google Gemini는 3.5
Flash와 3.1 Pro, xAI Grok은 4.5와 Composer 2.5 Fast를 지원한다.

기능은 프록시가 갖춰야 할 것들을 대체로 갖췄다.
CLI 모델에 대한 OpenAI/Gemini/Claude/Grok 호환 엔드포인트, 지원되는
경우의 스트리밍·비스트리밍·WebSocket 응답, 함수 호출과 도구 지원,
텍스트와 이미지를 아우르는 멀티모달 입력이다.
운영 측면에서는 여러 계정을 등록해 라운드로빈으로 부하를 분산할 수 있고,
간단한 CLI 인증 흐름을 제공하며, 설정으로 OpenAI 호환 상위 제공자를
추가할 수 있다.
임베딩용으로 재사용 가능한 Go SDK도 있다.
데스크톱 클라이언트 EasyCLIProxyAPI는 그래픽 설정과 자동 업데이트를
지원한다.

## 분석

### 이 프로젝트는 구독제와 종량제 사이의 가격 차이를 차익 거래한다

이 도구가 존재하는 이유는 기술적 결핍이 아니라 가격 구조의 불일치다.
같은 모델에 접근하는 경로가 두 가지인데 값이 다르다 — 월정액 구독은
공식 클라이언트 안에서 사실상 정액이고, API 키는 토큰당 과금이다.
헤비 유저에게 이 차이는 자릿수 단위다.

CLIProxyAPI가 하는 일은 그 두 경로 사이에 어댑터를 놓는 것이다.
OAuth로 구독 세션을 얻어 두고, 들어오는 표준 API 요청을 그 세션으로
번역해 내보낸다.
사용자 입장에서는 코드를 바꾸지 않고 청구서만 바뀐다.
여러 계정을 라운드로빈으로 돌리는 기능이 특히 이 성격을 드러낸다 —
계정당 한도가 있다는 것을 전제하고, 그 한도를 계정 수로 곱해 늘리는
장치이기 때문이다.

이 관점에서 보면 기능 목록의 우선순위가 설명된다.
멀티모달이나 WebSocket보다 앞에 오는 것이 다중 계정과 로드 밸런싱이고,
이는 성능 최적화가 아니라 한도 회피의 도구다.
프로젝트가 스스로를 “프록시”라고 부르지만 실질은 요금제 재판매 계층에
가깝다.

### 스타 5만 개는 기능이 아니라 가격에 대한 투표다

커밋 3,633개짜리 프로젝트가 스타 5만 개를 받는 것은 이례적이다.
비교하자면 널리 쓰이는 인프라 라이브러리들도 이 규모에 도달하는 데
수년이 걸린다.
기술적 난이도로 설명되지 않는 숫자다.

설명은 수요 쪽에 있다.
2026년 현재 코딩 에이전트를 상시 돌리는 개발자에게 API 종량제 비용은
빠르게 누적되고, 구독제는 공식 클라이언트 밖에서 쓸 수 없다.
그 사이에 낀 사람들이 정확히 이 도구의 사용자층이며, 그 층이 매우
두껍다는 것을 스타 수가 증명한다.
포크 7.7천 개는 각자 자기 조합의 제공자와 계정을 붙이려는 수요를 보여
준다.

이 숫자가 시사하는 것은 프로젝트의 품질보다 시장의 상태다.
가격 구조에 이만한 틈이 있고 그 틈을 메우는 도구에 이만한 수요가 있다면,
그 틈은 제공자 쪽에서 언젠가 닫으려 할 것이다.
프로젝트의 생명주기가 코드가 아니라 상대의 정책에 달려 있다는 뜻이다.

### 관리 API와 SDK의 존재가 개인 도구를 넘어선 사용을 시사한다

README에서 조용히 중요한 항목은 관리 API와 Go SDK다.
개인이 자기 노트북에서 구독을 쓰려는 것이라면 둘 다 필요 없다.
계정을 프로그램으로 추가·제거하고 상태를 조회하는 관리 API는, 계정
풀을 자동으로 운영하는 시나리오를 전제한다.

Go SDK로 이 프록시를 다른 서비스에 임베드할 수 있다는 것도 같은 방향을
가리킨다.
즉 이 도구는 한 사람이 쓰는 로컬 프록시에서 그치지 않고, 여러 계정을
모아 다수에게 서빙하는 게이트웨이로 확장 가능하도록 설계돼 있다.
데스크톱 클라이언트 EasyCLIProxyAPI가 그래픽 설정과 자동 업데이트를
제공하는 것은 비개발자 사용자까지 포섭하려는 시도다.

이 확장성은 프로젝트를 법적으로 훨씬 위험한 영역으로 데려간다.
개인이 자기 구독을 다른 클라이언트에서 쓰는 것과, 계정 풀을 만들어
타인에게 접근을 파는 것은 완전히 다른 행위다.
README는 후자를 권하지 않지만 후자를 위한 부품을 모두 제공한다.

## 비평

### 약관 위반 가능성이 문서 어디에도 명시되지 않는다

이 프로젝트의 가장 큰 결함은 코드가 아니라 침묵이다.
README는 지원 제공자와 기능을 상세히 나열하면서, 그 제공자들의 이용
약관이 이런 사용을 허용하는지에 대해 아무 말도 하지 않는다.

주요 제공자의 약관은 대체로 구독 서비스의 자동화된·프로그램적 접근을
제한하고, 계정 공유를 금지하며, 인증 흐름의 우회를 문제 삼는다.
이 도구의 동작 방식 — OAuth 세션을 얻어 공식 클라이언트가 아닌 경로로
사용하고, 여러 계정을 돌려 한도를 늘리는 것 — 은 그 조항들과 정면으로
부딪힐 소지가 크다.
MIT 라이선스는 코드 사용에 대한 허가일 뿐 상대 서비스에 대한 접근
권한을 주지 않는데, 라이선스가 명시된 자리에 약관 경고는 없다.

이 침묵이 무책임한 이유는 위험이 사용자에게만 떨어지기 때문이다.
프로젝트 관리자는 코드를 배포할 뿐이고, 계정이 정지되는 것은 그것을
쓴 사람이다.
GeekNews 토론에서 이 우려가 곧바로 나왔다.
`click`은 Antigravity의 서드파티 OAuth 사용으로 구글 계정 전체가 잠기는
사례가 종종 발생하니 주의하라고 경고했고[^click], `xguru`는 구글의
서드파티 사용 금지 논란 관련 링크를 제시하면서 자신도 구글 계정은 좀
무섭다고 덧붙였다[^xguru].
경고가 커뮤니티 댓글에서 나오고 프로젝트 문서에서는 나오지 않는 구조가
문제다.

### 계정 정지의 손실이 비대칭적인데 그 비대칭이 다뤄지지 않는다

`click`이 지적한 위험의 핵심은 정지의 범위다.
API 키가 막히는 것과 구글 계정 전체가 잠기는 것은 손실의 크기가 다르다.
후자에는 메일, 문서, 사진, 결제 수단, 그리고 그 계정으로 로그인한
모든 서비스가 딸려 있다.

이 비대칭이 이 도구의 위험 계산을 완전히 바꾼다.
절감되는 것은 월 몇십 달러이고, 잃을 수 있는 것은 개인의 디지털 생활
전체다.
기대값으로 따지면 정지 확률이 아주 낮아도 손실 규모가 크기 때문에
합리적 선택이 아닐 수 있는데, 프로젝트는 이 계산에 필요한 어떤 정보도
제공하지 않는다 — 실제 정지 사례가 얼마나 보고됐는지, 어떤 제공자가
더 공격적인지, 탐지를 유발하는 사용 패턴이 무엇인지.

`xguru`가 자신은 `openai-oauth`를 썼는데 이쪽이 기능이 더 많고 깔끔하다고
평하면서도 약관 확인의 필요성을 강조한 것이 균형 잡힌 태도다[^xguru-2].
도구의 완성도와 사용의 안전성은 별개의 축이며, 완성도가 높을수록 오히려
더 많은 사람이 위험을 모른 채 쓰게 된다.

### 지원 제공자 목록의 최신성이 유지 부담을 감춘다

README는 Kimi K3부터 GPT 5.6, Claude Fable, Gemini 3.5 Flash, Grok 4.5까지
최신 모델을 촘촘히 나열한다.
목록이 화려할수록 좋아 보이지만, 이 목록이야말로 프로젝트의 구조적
취약점이다.

각 제공자의 OAuth 흐름과 내부 프로토콜은 공개 규격이 아니다.
공식 클라이언트가 쓰는 비공개 엔드포인트를 역공학해 따라가는 구조이며,
제공자가 인증 방식이나 요청 형식을 바꾸면 즉시 깨진다.
커밋 3,633개라는 숫자와 열려 있는 이슈 90개, 풀 리퀘스트 448개가 이
유지 부담의 흔적으로 읽힌다 — 기능을 추가하는 커밋보다 깨진 것을 고치는
커밋이 많을 가능성이 높다.

이 취약성은 사용자에게 직접 전가된다.
프로덕션 워크플로에 이 프록시를 끼워 넣었는데 제공자가 하룻밤 사이에
인증을 바꾸면, 복구 시점은 이 저장소의 메인테이너가 정한다.
공식 API 키를 쓰면 계약과 SLA가 있지만 여기에는 없다.
README가 “간단한 CLI 인증 흐름”이라고 소개하는 것은 설치 경험에 대한
서술이고, 그 흐름이 얼마나 자주 바뀌는지는 서술되지 않는다.

## 인사이트

### 이 도구의 인기는 AI 요금제 설계가 실패했다는 신호다

스타 5만 개짜리 우회 도구가 존재한다는 사실은 그 자체로 시장 정보다.
사람들이 규칙을 어기면서까지 쓰고 싶어 하는 것이 있다면, 대개는 공급자가
수요의 형태를 잘못 읽었다는 뜻이다.

지금 AI 제공자들의 요금 구조는 두 갈래다.
정액 구독은 공식 인터페이스 안에서만 쓸 수 있고, 프로그램 접근은
종량제 API로만 열린다.
이 분리의 논리는 명확하다 — 구독은 사람이 손으로 쓰는 양을 전제한 가격이고,
자동화된 접근은 그 전제를 깨기 때문이다.
그러나 에이전트 시대에는 사람이 손으로 쓰는 것과 프로그램이 쓰는 것의
경계가 사라진다.
코딩 에이전트를 쓰는 개발자는 자기 일을 하는 것이지 API를 재판매하는
것이 아닌데, 요금 체계는 그를 후자로 분류한다.

이 도구는 그 오분류에 대한 시장의 응답이다.
그리고 응답의 규모가 크다는 것은 오분류의 규모도 크다는 뜻이다.
실제로 제공자들이 이 압력을 인지하고 있다는 신호가 있다 — 구독 요금제
안에서 CLI 도구와 에이전트 사용을 공식 허용하는 방향으로 상품이 재편되고
있고, 그 흐름이 계속되면 이 프록시의 존재 이유는 줄어든다.

역사적으로 같은 패턴이 반복됐다.
음악 산업의 P2P, 케이블 방송의 코드 커팅, 지역 잠금 콘텐츠의 VPN —
모두 우회 도구의 폭발적 인기가 먼저 오고 가격·유통 구조의 재편이
뒤따랐다.
우회 도구는 그 자체로 지속되기보다 공급자가 요금제를 고치게 만드는
압력으로 기능했고, 고쳐지면 조용히 사라졌다.
CLIProxyAPI의 성공적인 결말도 아마 그 형태일 것이다.

### OAuth 토큰이 사실상의 API 키가 되면서 신뢰 경계가 무너진다

기술적으로 이 도구가 하는 일의 핵심은 사용자 인증용 토큰을 서비스
간 통신용 자격 증명처럼 쓰는 것이다.
그리고 이 둘은 원래 다른 물건이다.

API 키는 목적이 좁다 — 특정 서비스에 대한 프로그램 접근이고, 권한을
제한할 수 있으며, 유출되면 그것만 폐기하면 된다.
OAuth로 얻은 사용자 세션은 그 사람 자체를 나타내며, 같은 계정에 묶인
다른 서비스까지 잠재적 범위에 들어간다.
`click`이 경고한 “구글 계정 전체가 잠긴다”는 현상은 이 차이의 직접적
결과다.

이 혼동이 위험한 이유는 도구가 그것을 매끄럽게 만들기 때문이다.
`config`에 계정을 몇 개 등록하고 나면 그것이 API 키처럼 보이고 API
키처럼 다뤄진다 — 설정 파일에 저장되고, 컨테이너에 마운트되고,
팀원과 공유될 수도 있다.
그런데 유출됐을 때의 폭발 반경은 API 키와 비교가 되지 않는다.
추상화가 편의를 주면서 위험의 크기에 대한 감각을 함께 지운다.

이 문제는 이 프로젝트 하나를 넘어선다.
에이전트가 사용자를 대신해 여러 서비스에 접근하는 구조가 늘면서,
“사용자 인증”과 “위임된 프로그램 접근”의 경계는 계속 흐려질 것이다.
MCP 서버들이 OAuth 토큰을 들고 도는 상황도 같은 문제를 안고 있다.
필요한 것은 우회 도구를 금지하는 것이 아니라, 위임 전용의 범위 제한
자격 증명을 제공자가 정식으로 발급하는 것이다.
그 인터페이스가 없기 때문에 사람들이 사용자 세션을 대신 쓰고 있고,
이는 보안 설계의 공백이지 사용자의 부주의가 아니다.

### 여러 제공자를 하나의 인터페이스로 묶는 계층은 남고 우회 기능은 사라진다

이 프로젝트에는 서로 다른 두 가지가 섞여 있다.
하나는 구독을 API로 바꾸는 우회 기능이고, 다른 하나는 여러 제공자를
하나의 호환 인터페이스로 통합하는 라우팅 계층이다.
앞의 것은 정책 변화에 취약하지만 뒤의 것은 그렇지 않다.

라우팅 계층의 가치는 독립적이다.
OpenAI, Anthropic, Google, xAI, Moonshot이 각기 다른 API를 내놓고
서로 다른 속도로 모델을 바꾸는 상황에서, 애플리케이션이 그 차이를
직접 감당하는 것은 부채다.
한 곳에 어댑터를 모아 두면 모델 교체가 설정 변경이 되고, 장애가 났을
때 다른 제공자로 넘기는 것도 가능해진다.
라운드로빈 로드 밸런싱은 지금은 한도 회피에 쓰이지만, 정식 API 키
여러 개에 대해서도 똑같이 유용한 기능이다.

그래서 이 프로젝트의 미래를 예측하자면 분화일 가능성이 높다.
제공자들이 구독 내 프로그램 접근을 공식화하면 우회 기능은 의미를 잃고,
남는 것은 멀티 프로바이더 게이트웨이다.
이미 그 자리를 겨냥한 프로젝트들이 여럿 있고, `ai-tool` 디렉터리의
다른 기록들이 보여 주듯 이 계보는 서로를 포크하며 빠르게 번지고 있다.
CLIProxyAPI가 Go SDK와 관리 API를 갖춘 것은 그 경쟁에서 살아남을 준비이기도
하다.

여기서 도구를 고르는 사람에게 실용적 기준이 나온다.
이런 프록시를 도입할 때 물어야 할 것은 “지금 얼마나 아껴 주는가”가 아니라
“우회 기능을 전부 끄면 무엇이 남는가”다.
남는 것이 쓸 만한 라우팅 계층이라면 정책이 바뀌어도 투자가 보존되고,
남는 것이 없다면 그 도구는 제공자의 다음 공지와 함께 사라진다.
