## 소개

Ordewell은 목표 하나를 코딩 에이전트 작업의 그래프로 바꾸고, 그것을 실행하고 검증하는 오케스트레이터다.
작업끼리 독립적이면 병렬로, 의존하면 순서대로 돌리며, 작업마다 자기 러너(runner), 모델, 세션을 따로 가진다.
러너는 Claude Code, Codex, OpenCode가 기본으로 들어 있고, 한 계획 안에서 작업마다 섞어 쓸 수 있다.
TypeScript로 작성됐고 Apache 2.0 라이선스이며, 저장소는 2026년 7월 31일에 만들어져 9월 26일 기준 스타 149개다.

README가 내세우는 원칙은 여섯 가지다.

- 계획은 실행 전에 고쳐 쓸 수 있는 파일이다. 작업마다 러너, 모델, 사고 노력(thinking effort), 모드를 갖고, 무엇이든 바꾸거나 작업을 더하고 빼거나 의존 관계를 다시 이어도 완료된 작업은 남는다.
- 작업마다 러너와 모델이 하나씩이고, 모두 한 화면에 보인다. 보안 리팩터링과 README 수정에 같은 모델을 쓸 이유가 없다는 것이다.
- 작업은 러너의 출력에 완료 마커가 나타날 때만 끝난다. 종료 코드는 진단 증거로만 남기고, 어떤 모델도 자기 작업을 채점하지 않으며, 마커 없이 끝난 작업은 조용히 통과하지 않고 요란하게 실패한다.
- 플래너(planner)는 읽기 전용이고 사용자와 대화한다. 저장소를 조사하고, 목표가 모호하면 묻고, 마지막 메시지가 곧 계획이다.
- 별도 API 키가 필요 없다. Claude Code, Codex, OpenCode가 이미 가진 구독으로 읽기 전용 플래너가 될 수 있다.
- 여러 러너를 쓰도록 설계됐다. Aider나 직접 만든 CLI는 코드 변경이 아니라 플러그인 매니페스트로 붙인다.

## 사용법

Node.js 20 이상이 필요하고, 터미널 UI는 작업마다 tmux 창을 쓰므로 모든 플랫폼에서 tmux가 필요하다.

```bash
npm install -g ordewell
ordewell    # 왼쪽은 플래너와의 대화, 오른쪽은 계획 창인 터미널 UI
```

모든 슬래시 명령은 하위 명령으로도 있어서, 사람이 할 수 있는 모든 일을 헤드리스 자동화로도 할 수 있다.

```bash
export AI_PROVIDER="claude-code"   # 이미 쓰는 에이전트의 구독으로 계획한다
ordewell plan --goal "Add rate limiting to the public API"

ordewell task-runner 2 opencode    # 러너부터 바꾸면 모델, 노력, 모드가 다시 정해진다
ordewell task-deps 3 1,2
ordewell run                       # 독립 작업은 기본 3개까지 병렬로 돈다
```

API 키를 쓸 때는 OpenRouter, Anthropic, OpenAI, Gemini, DeepSeek 등 25개 제공자의 `*_API_KEY`를 인식하고, `OPENAI_COMPATIBLE_BASE_URL`로 로컬 모델 서버도 가리킬 수 있다.
플래너 모델의 기본값은 싼 모델인 `deepseek/deepseek-v4-flash`이고, 동시 실행 작업 수는 `ORDEWELL_MAX_PARALLEL`로 1에서 5 사이로 정한다.
`grilling`을 켜면 플래너가 계획 전에 최소 세 개의 캐묻는 질문을 하고, `prd`를 켜면 PRD를 쓰며, `tdd`를 켜면 작업에 red-green-refactor 지시가 붙는다.
이 세 흐름은 Matt Pocock의 스킬을 가져와 프롬프트 블록으로 다시 만든 것이다.

인터페이스는 VS Code 확장, 터미널 UI, CLI 세 가지이고, 모두 `127.0.0.1:3742`에서 도는 로컬 HTTP와 WebSocket 서버의 클라이언트다.

## 동작 방식

흐름은 다섯 단계다.

1. 사용자가 목표를 평문으로 적는다.
2. 플래너가 작업 공간을 읽기 전용으로 조사하며, 한 대화 안에서 조사와 질문을 섞는다.
3. 작업마다 러너, 모델, 노력, 모드가 붙은 계획이 나온다. 무엇이든 고치거나, 완료된 작업을 잃지 않고 계획 전체를 다시 짜게 할 수 있다.
4. 실행은 AI 작업마다 실제 코딩 에이전트 세션을 띄우고, 의존 그래프를 지키며, 앞선 작업의 결과를 넘긴다. 수동 작업은 체크리스트가 된다.
5. VerdictEngine은 마커가 나타날 때만 작업을 완료로 본다. 세션은 `.ordewell/sessions/`에 저장된다.

플래너의 탐색에는 경계가 있다.
읽기는 병렬로 돌고, 작업 공간 밖으로 나가는 것은 한 번 묻고, 쓰기가 되는 명령은 아예 거부한다.
계획은 JSON으로 직렬화되는 타입 있는 산출물이어서, 사람이 검토한 계획이 그대로 실행된다.

설계 노트 “왜 싸고 별도인 플래너를 쓰는가”는 이 구조의 이유를 적는다.
계획은 제한된 맥락에서 읽고 추론하는 일이라 가장 강한 코딩 모델이 필요 없고, 코드 생성은 범위가 좁고 토큰당 위험이 커 그 변경에 맞는 가장 강한 모델이 필요하다는 것이다.
비싼 모델 하나가 둘 다 하면 싼 절반에도 최고 가격을 내고, 사소한 작업마다 그 값을 다시 낸다.
노트는 이 이음매의 대가도 밝힌다.
계획을 타입 있는 산출물로 만들면 모델이 경계에서 올바른 JSON을 내는 데 모든 것이 걸리므로, 중괄호 균형을 따지는 추출, 원문을 담은 타입 있는 오류, 잘못된 출력에 한 번 다시 요청하는 재시도로 그 경계를 방어한다.

## 분석

### 계획과 실행을 가르는 선은 비용이 아니라 권한이다

Ordewell의 첫 인상은 비용 최적화 도구다.
싼 모델로 계획하고, 작업마다 필요한 만큼의 모델을 쓴다.
그러나 README를 따라가면 더 중요한 분리는 권한이다.
플래너는 쓰기 명령을 거부당하고, 변경은 언제나 러너가 한다.

이 분리는 사람이 개입할 자리를 만든다.
계획이 파일로 나와 실행 전에 멈춰 있으니, 사람은 어떤 작업이 어떤 모델로 무엇을 할지를 코드가 바뀌기 전에 본다.
한 에이전트가 계획부터 구현까지 한 맥락에서 하면, 사람이 볼 수 있는 것은 이미 바뀐 코드뿐이다.

Hacker News에서 ramon156은 DeepSeek 같은 저비용 모델을 위한 계획을 자신 있게 세워 주는 결정적 프로그램을 원한다며, LLM 부분은 결정적이지 않겠지만 이렇게 하면 품질을 재기가 훨씬 쉽다고 적었다.[^ramon156]
AGENTS.md가 그런 역할을 한다고 볼 수도 있지만, 경험상 그것만으로는 프런티어가 아닌 모델의 성공률을 높이기에 충분하지 않다는 것이다.
계획을 검토 가능한 데이터로 떼어 내는 것은, 이 “충분하지 않음”을 사람이 메우는 자리를 만드는 일이다.

### 검증을 모델의 의견에서 떼어 낸 것이 가장 강한 주장이다

README는 작업의 판정이 모델의 의견이 아니라 세션 출력의 마커로 얻어진다고 반복한다.
자기 작업을 스스로 채점하게 하면 모델은 쉽게 통과를 선언하고, 그것이 에이전트 파이프라인에서 가장 흔한 조용한 실패다.
마커 없이 끝나면 실패로 보고, 리뷰 응답이 깨지면 안전한 실패 판정으로 떨어지게 한 설계는, 잘못 통과시키는 것보다 잘못 실패시키는 쪽을 택한 것이다.

Hacker News에서 jedbrooke는 비슷한 원칙을 셸 스크립트로 구현한 경험을 적었다.[^jedbrooke]
간헐적으로 실패하는 경쟁 조건 버그를 찾으려고 셸 반복문이 빌드를 N번 돌리고, 테스트가 실패했을 때만 에이전트에게 로그 분석을 맡기고, 끝나면 셸이 Slack으로 알리게 했다는 것이다.
결정적인 뼈대가 흐름을 쥐고 에이전트는 필요한 곳에서만 부르는 구조는 Ordewell의 설계와 같은 방향이다.

## 비평

### 완료 마커는 “끝났다”를 증명할 뿐 “맞다”를 증명하지 않는다

마커 기반 판정은 모델이 자기 작업을 채점하지 않게 한다는 점에서 옳다.
그러나 마커를 출력하는 것도 결국 러너 세션 안의 모델이다.
작업 프롬프트가 “끝나면 이 마커를 출력하라”고 지시한다면, 마커는 모델이 스스로 끝났다고 판단했다는 신호이지, 변경이 요구 사항을 충족했다는 증거가 아니다.

README의 CLI 예시에서 판정 문구가 “완료 마커가 에이전트 출력에서 감지됐다”인 것도 이 점을 보여 준다.
테스트 통과나 타입 검사 같은 외부 기준과 묶이지 않는다면, 마커는 자기 채점을 없앤 것이 아니라 자기 채점의 형식을 문자열 하나로 바꾼 것일 수 있다.
`testingStrategy`와 `/verify` 같은 장치가 있지만, README는 기본 판정이 무엇을 보증하고 무엇을 보증하지 않는지를 분명히 가르지 않는다.

### 작업 사이의 맥락 전달이 가장 약한 고리인데 설명이 가장 적다

작업을 쪼개면 각 러너는 자기 세션에서 자기 작업만 본다.
README는 앞선 작업의 결과를 다음 작업에 넘긴다고만 적는다.
리미터를 만드는 작업과 그것을 라우트에 연결하는 작업이 다른 세션, 심지어 다른 러너와 모델에서 돈다면, 두 번째 작업이 첫 번째의 설계 의도를 얼마나 이어받는지가 결과를 좌우한다.

한 에이전트가 한 맥락에서 모두 하면 비싸지만, 앞서 내린 결정을 기억한다.
작업마다 새 세션을 쓰면 싸고 병렬로 돌지만, 작업 사이의 이음새에서 일관성이 깨질 위험이 생긴다.
기본 동시 실행이 3개이고 독립 작업을 병렬로 돌린다는 설계는, 플래너가 “독립적”이라고 판단한 작업이 정말 서로 영향을 주지 않을 때만 안전하다.

### 플랫폼이 흡수할 기능 위에 서 있다는 질문에 답이 약하다

Hacker News에서 popularonion은 이런 메타 프레임워크에 흥미를 느끼지 못한다며, 어떤 진전이든 몇 달 뒤 Claude와 Codex에 흡수되고 다시 몇 달 뒤 그 아래 경쟁자들에게 들어간다는 것을 다들 알지 않느냐고 적었다.[^popularonion]
작성자 ac-ciano는 그렇다고 인정하면서도, 어느 제공자든 골라 쓰고 Claude Code 하나에 묶이지 않는 자유를 중시한다며, Opus와 DeepSeek와 GPT 6을 동시에 쓰고 싶다고 답했다.[^ac-ciano-lockin]

이 답은 Ordewell의 진짜 차별점이 계획이나 검증이 아니라 벤더 중립성이라는 것을 드러낸다.
계획 모드, 하위 에이전트, 모델 선택은 이미 각 플랫폼이 제공하거나 곧 제공할 기능이다.
여러 벤더의 에이전트를 한 계획 안에서 섞는 일은 어느 한 벤더가 제공할 동기가 적은 기능이고, 그 점에서 오케스트레이터가 오래 설 자리가 있다.
그러나 README는 이 논점을 여러 원칙 중 하나로만 다루고, 비용 절감을 앞에 내세운다.

### AI가 쓴 문서는 차별점을 찾는 독자를 먼저 잃는다

Hacker News에서 Lalabadie는 차별점을 찾으려고 페이지를 열었는데 프로젝트의 모든 것, 댓글의 작성자 답변까지 AI가 쓴 것 같다고 적었다.[^Lalabadie]
작성자는 문서와 코드를 쓰는 데 AI를 많이 썼다고 인정하며, 설계는 자신이 했고 그것을 책임진다고 답했다.[^ac-ciano-design]
그리고 부끄러운 것은 AI를 쓴 것이 아니라 유지보수할 수 없는 것이며, 지금은 AI로 코드와 문서를 쓰는 것이 표준이라고 덧붙였다.[^ac-ciano-standard]

작성자의 말처럼 AI를 쓴 것 자체는 문제가 아니다.
문제는 README가 모든 것을 같은 강도로 강조한다는 점이다.
모든 원칙이 굵은 글씨의 선언이고, 모든 기능이 같은 무게로 나열되면, 독자는 무엇이 이 도구를 다른 도구와 다르게 만드는지를 스스로 골라내야 한다.

## 인사이트

### 오케스트레이터의 가치는 “어느 모델이 무엇을 했는지”를 기록하는 데서 나온다

작업마다 러너와 모델과 노력이 명시된 계획은, 실행이 끝난 뒤에도 남는 기록이 된다.
어떤 변경을 어떤 모델이 얼마나 생각해서 했는지가 파일에 남으면, 문제가 생겼을 때 원인을 모델 선택까지 거슬러 올라갈 수 있다.
한 에이전트가 모든 것을 한 세션에서 하면, 그 세션의 기록 속에서 결정의 경계를 찾기 어렵다.

이 기록은 모델 선택 자체를 실험 가능하게 만든다.
같은 계획을 다른 모델 배정으로 다시 돌려 결과를 비교하면, 어떤 종류의 작업에 어떤 모델이 충분한지를 증거로 배울 수 있다.
ramon156이 말한 “품질을 재기 쉬워진다”는 장점이 실제로 쌓이는 곳은 여기다.[^ramon156]

### 싼 모델이 강해질수록 계획과 실행의 분리는 더 가치 있어진다

Hacker News에서 jonaustin은 로컬 모델이 궤도를 벗어나지 않게 하려고, 최고 수준 모델이 처음 프롬프트와 이슈를 만들고 로컬 모델이 계획하고 구현하며 최고 수준 모델이 검토하는 순환을 만들었다고 적었다.[^jonaustin]
그는 Defender(1981) 클론을 꽤 성공적으로 만들었고 지금은 Prince of Persia 클론을 맡기고 있으며, Qwen3.8-Flash-Next와 27B가 놀랄 만큼 좋아서 이제야 가능해졌다고 덧붙였다.

이 경험은 Ordewell의 설계가 겨냥하는 미래를 보여 준다.
싼 모델이 충분히 좋아질수록, 비싼 모델은 모든 작업이 아니라 판단이 걸린 소수의 지점에만 쓰이게 된다.
그 소수의 지점을 고르는 일, 곧 어느 작업에 어느 모델을 쓸지 정하는 일이 오케스트레이터의 핵심 역할이 된다.
다만 jonaustin의 구조가 검토를 최고 수준 모델에게 맡긴 것과 달리, Ordewell의 기본 플래너는 가장 싼 모델이라는 점에서, 분리의 방향은 같아도 어느 쪽에 판단을 두는지는 다르다.

### 벤더 중립성은 기능이 아니라 입장이다

popularonion의 비판이 맞다면, 기능으로서의 오케스트레이션은 결국 플랫폼에 흡수된다.[^popularonion]
그러나 여러 벤더의 에이전트를 같은 계획 안에서 섞는 일은, 벤더가 스스로 흡수할 이유가 적은 기능이다.
각 플랫폼은 자기 모델과 자기 구독 안에서 사용자를 붙잡고 싶어 하기 때문이다.

그래서 Ordewell 같은 도구의 수명은 기술보다 시장 구조에 달려 있다.
코딩 에이전트 시장이 소수의 폐쇄 플랫폼으로 굳으면, 벤더 중립 오케스트레이터는 그 사이를 잇는 드문 자리가 된다.
반대로 플랫폼들이 서로의 모델을 부르는 개방형 구조로 가면, 이 자리는 줄어든다.
Ordewell이 “추가 API 키 없이 이미 가진 구독으로”를 강조하는 것도, 사용자를 한 벤더에서 빼내는 것이 아니라 여러 벤더의 구독을 동시에 쓰게 하는 쪽을 택한 것이다.
