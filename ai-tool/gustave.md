# Gustave: 데이터를 내 인프라 안에 두고 AI 어시스턴트를 몇 분 만에 올린다는 온프레미스 엔터프라이즈 AI 플랫폼

<https://www.higustave.ai/>

## 소개

Gustave는 기업이 자기 인프라 안에서 AI 어시스턴트를 만들고
운영하게 해 주는 플랫폼이다.
제작사는 이것을 완전한 온프레미스이고
에어갭(air-gap) 환경과도 호환되는 제품이라고 소개한다.
제작사가 내건 약속은 데이터가 환경 밖으로 나가지 않고,
핵심 기능에 클라우드 의존이나 외부 API 호출이 없으며,
프로덕션 수준의 어시스턴트를 몇 달이 아니라 몇 분 안에 올린다는 것이다.
개발은 영국의 ZeroDue Consulting LTD와 HexaQB IT Consulting — FZCO가 함께 하고,
사이트를 운영하고 개인정보를 관리하는 곳은 ZeroDue Consulting LTD다.[^privacy]

제작사는 숫자 네 개를 내세운다.
용도별로 나뉜 스튜디오가 4개, 지원하는 LLM 제공자가 5개, 온프레미스 비율 100%,
첫 어시스턴트까지 5분 미만이다.
문의 경로는 데모 요청 하나이며,
가격과 기술 문서와 고객 사례와 오픈소스 저장소는 사이트에 없다.
사이트 자체는 정적 HTML 한 장이고
쿠키와 분석 도구와 외부 스크립트를 쓰지 않는다고
개인정보 안내가 밝힌다.[^privacy]

## 구성

제작사는 플랫폼을 네 개의 스튜디오로 나눈다.
Admin과 Chat을 묶어 Core라 부르며 모든 배포가 여기서 시작하고,
Recall과 Tools는 필요할 때 더한다고 한다.
각 스튜디오는 독립된 서비스여서 Chat, Recall, Tools를 따로 확장하고
필요한 것만 배포할 수 있다고 제작사는 말한다.

| 스튜디오       | 역할                               | 제작사가 든 기능                                                                                                                             |
| -------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Gustave Admin  | 어시스턴트를 설계하는 작업대       | 다중 LLM 제공자 관리, 프롬프트와 스킬 작성, 어시스턴트 구성과 버전 관리, 역할 기반 접근 제어와 프로젝트 관리, 전체 감사 기록                 |
| Gustave Chat   | 어시스턴트가 사용자를 만나는 곳    | 실시간 스트리밍, MCP 기반 다중 턴 도구 호출, RAG 대화, 마크다운 표시, 외부에 끼워 넣을 어시스턴트 API                                        |
| Gustave Recall | 지식 베이스                        | 문서 컬렉션과 파일 관리, 설정 가능한 청킹 전략, 여러 임베딩 제공자, 벡터 저장소 생성과 색인, 의미 검색 API, 버전이 있는 지식 베이스          |
| Gustave Tools  | 어시스턴트에게 행동 능력을 주는 곳 | 핫 로딩 플러그인, 네이티브 MCP 지원, Bearer·API 키·Basic 인증, 상태 점검과 감사 로그, OpenAPI 명세를 불러와 MCP 도구로 노출하는 API 카탈로그 |

Recall은 문서를 지식 베이스로 바꾸고 자연어로 질의하게 하며,
결과는 관련도 순으로 프로젝트 범위 안에서 정렬되고
여러 저장소를 한 번에 검색할 수 있다고 한다.
Tools는 데이터베이스 조회, API 호출, 티켓 생성 같은 능력을 플러그인으로 주거나,
여러 단계의 업무 흐름을 하나의 결정적 도구로 감싸게 한다.
OpenAPI 명세를 붙여 넣으면 기존 REST API가 플러그인 없이 MCP 호환 도구가 된다고
한다.

## 동작 방식

제작사는 만드는 과정을 다섯 단계로 설명한다.

1. Admin에서 LLM 제공자를 등록한다.
OpenAI, Azure, AWS Bedrock, Anthropic, Ollama가 목록에 있고,
제공자를 바꿔도 어시스턴트 구성은 그대로이며
자격 증명은 환경 밖으로 나가지 않는다고 한다.
에어갭 환경에서는 로컬 모델을 돌린다.
2. Recall에서 지식 베이스를 만든다.
여러 파일 형식의 문서를 컬렉션으로 묶고 내용 종류에 맞는 청킹을 거쳐 색인하며,
버전에는 활성화 제어가 있다.
3. 다시 Admin에서 프롬프트를 쓴다.
시스템 프롬프트로 행동과 성격을 정하고, 맥락을 자동으로 보강하는 스킬을 만들고,
태그로 팀이 찾아 쓰게 한다.
4. Tools에서 MCP로 도구를 연결한다.
STDIO와 HTTP MCP 서버를 모두 지원하고, 서버마다 Basic·Bearer·API 키 인증을 두며,
재사용 가능한 도구 템플릿을 환경에 걸쳐 배포한다.
5. Chat에서 게시한다.
게시하면 바로 실시간 스트리밍과 도구 호출이 되는 어시스턴트가 열리고,
게시마다 되돌릴 수 있는 불변 버전이 만들어진다.

## 엔터프라이즈 기능

제작사는 다음을 처음부터 들어 있는 기능이라고 말한다.

- 온프레미스 배포: 인프라 안에서만 돌고 에어갭 네트워크와 엄격한 규정 환경에서
쓸 수 있다.
- 멀티 테넌시: 테넌트별 데이터 격리와 독립 설정으로
한 배포가 여러 팀이나 조직을 맡는다.
- SSO와 인증: 기업 단일 로그인과 연동되고 사용자는 첫 로그인에서
자동으로 만들어진다.
- 세분화된 접근 제어: 어시스턴트 생성, 파일 업로드, 도구 관리,
특정 기능 접근을 역할로 나눈다.
- 버전 관리: 어시스턴트와 지식 베이스의 불변 스냅샷으로 변경을 추적하고 비교하고
되돌린다.
- 독립 확장: 각 스튜디오를 부하에 따라 따로 늘린다.

## 분석

### 제품은 여섯 가지 실패 사례를 기능 목록으로 뒤집은 것이다

제작사는 “익숙하지 않은가”라는 문구 아래 기업 AI 사업이 부딪히는 여섯 가지 벽을
먼저 늘어놓는다.
문서를 그냥 올리는 방식, 제공자에 묶이는 함정, 시제품과 운영 사이의 틈,
배관이 예상보다 3배 걸리는 놀람, 뒤로 미룬 보안, 프롬프트를 바꿨더니
결과가 나빠졌는데 무엇이 바뀌었는지 모르는 문제다.
이 목록이 곧 제품의 사양서다.

| 제작사가 든 문제   | 대응하는 기능                                  |
| ------------------ | ---------------------------------------------- |
| 문서 덤프          | Recall의 청킹, 임베딩, 버전이 있는 지식 베이스 |
| 제공자 함정        | 다중 제공자와 설정 불변의 제공자 교체          |
| 시제품과 운영의 틈 | 인증, 멀티 테넌시, 버전 관리, 감사 기록        |
| 인프라 놀람        | 독립 서비스로 나뉜 스튜디오와 기성 배관        |
| 보안 뒷전          | 역할 기반 접근 제어, SSO, 테넌트 격리          |
| 무엇이 바뀌었나    | 어시스턴트와 지식 베이스의 불변 스냅샷         |

이 대응표는 이 문서가 사이트의 서술에서 정리한 것이다.
제작사의 판매 논리는 어시스턴트의 지능이 아니라 그 주변의 따분한 80%,
곧 운영 기반을 사 가라는 것이다.

### 구성 요소를 어시스턴트라는 하나의 단위로 묶는다

Gustave에서 어시스턴트는 프롬프트, 스킬, 지식 베이스, 도구, 제공자의 조합이다.
Admin이 그 조합을 구성하고 버전을 매기고 게시한다.
Recall과 Tools는 어시스턴트가 가져다 쓰는 자원이며,
Chat은 결과를 사용자와 API에 내보낸다.

이 구조는 에이전트를 만드는 데 필요한 부품을 각각 독립 서비스로 두고
구성 계층에서 조립하게 하는 설계다.
부품이 독립이면 도구나 지식 베이스를 여러 어시스턴트가 공유하고,
한 부품만 확장하거나 교체할 수 있다.
반면 조립 계층(Admin)이 모든 설정의 단일 지점이 되어 거기에서
버전과 권한이 정해진다.

### MCP를 도구 통합의 공용 규격으로 삼았다

Tools는 도구를 MCP 서버로 연결하는 것을 중심에 둔다.
제작사는 MCP를 AI 도구 통합의 부상하는 열린 표준이라 부르고
독점 잠금이 없다는 점을 강조한다.
MCP 사양은 표준 전송을 두 가지로 정의한다.
클라이언트가 띄운 하위 프로세스의 표준 입출력으로 주고받는 stdio와,
각 메시지를 단일 MCP 엔드포인트로 보내는 HTTP POST인 Streamable HTTP다.[^mcp]
제작사가 지원한다고 밝힌 STDIO와 HTTP 서버가 이 둘에 해당한다고 읽을 수 있으며,
이는 이 문서의 해석이다.

OpenAPI 명세를 MCP 도구로 자동 변환하는 API 카탈로그는 기존 REST 자산을 그대로
에이전트의 능력으로 바꾸는 지름길이다.
다만 API의 모든 엔드포인트가 도구로 노출되면
어시스턴트가 쓸 수 있는 능력의 범위가 넓어지므로,
제작사가 말한 구성별 접근 제어가 중요한 안전장치가 된다.

## 비평

### 데이터가 밖으로 나가지 않는다는 약속은 로컬 모델에서만 성립한다

제작사의 첫 약속은 데이터가 환경을 떠나지 않고 외부 API 호출이 없다는 것이다.
그러나 같은 사이트가 지원 제공자로 OpenAI, Azure, AWS Bedrock, Anthropic을 든다.
이 제공자를 쓰면 프롬프트와 검색된 문서 조각이 외부 서비스로 나간다.
제작사는 에어갭에서는 로컬 모델을 돌린다고 적고
“핵심 기능에는 외부 API 호출이 없다”는 단서를 달지만,
어시스턴트의 핵심 기능이 모델 호출이라는 점에서 이 단서의 범위가 모호하다.

따라서 100% 온프레미스라는 말은 제어 평면(관리, 저장,
인증)이 안에 있다는 뜻으로 읽는 편이 정확해 보인다.
이는 이 문서의 해석이며 제작사가 그렇게 풀어 쓰지는 않았다.
독자가 확인해야 할 것은 제공자별로 어떤 데이터가 나가는지,
특정 어시스턴트나 테넌트에 외부 제공자를 금지하는 설정이 있는지다.
사이트는 접근 제어가 어시스턴트 생성과 파일 업로드와 도구 관리를 나눈다고만 적고
제공자 제한은 말하지 않는다.

### 멀티 테넌시와 STDIO 도구를 함께 쓰는 보안 모델이 빠져 있다

제작사는 테넌트별 완전한 데이터 격리를 약속하고,
도구는 STDIO와 HTTP MCP 서버를 모두 지원한다고 한다.
stdio 전송에서 서버는 클라이언트가 띄운 하위 프로세스다.[^mcp]
여러 테넌트가 공유하는 호스트에서 테넌트가 구성한 도구가 프로세스로 실행된다면,
그 프로세스의 격리와 자원 제한과 파일 접근 범위가 핵심 문제가 된다.

사이트는 이 부분을 말하지 않는다.
Tools의 인증이 HTTP 서버의 Basic, Bearer,
API 키를 다루는 것과 달리 사이트의 화면
예시는 STDIO 서버의 인증을 “로컬”로 표시한다.
이 구성이 테넌트 격리 약속과 어떻게 양립하는지가 도입 전에 가장 먼저 물어볼
질문이다.

### 지원하는 MCP 개정판이 적혀 있지 않다

제작사는 MCP를 부상하는 표준으로 부르지만
어느 사양 개정판을 구현했는지 밝히지 않는다.
현재의 MCP 사양은 요청마다 프로토콜 버전과 클라이언트 능력이 본문의 메타데이터로
실리는 구조를 설명하고, 이전 개정판이 연결 범위의 세션과 초기화 핸드셰이크와
서버가 시작하는 요청을 허용했다고 적는다.[^mcp]
상대의 시대를 감지해 물러서는 호환 규칙도 사양에 있다.[^mcp]
개정판에 따라 구현해야 할 것이 달라지는 영역에서
지원 범위를 적지 않은 것은 도입 담당자가 가장 필요로 하는 정보가 빠진 것이다.

### 성능과 속도의 숫자는 근거 없이 제시된다

첫 어시스턴트까지 5분 미만이라는 수치와 몇 분이면
프로덕션 어시스턴트라는 문구는 측정 조건이 없다.
무엇을 갖춘 환경에서 어느 수준의 어시스턴트를 말하는지 알 수 없다.
화면 예시는 임의의 값(컬렉션의 파일 수, 날짜)이 들어 있는 모형이다.

또 제작사가 6가지 벽의 하나로 든 “배관이 3배 더 걸린다”는 말도 출처가 없다.
이 숫자가 제작사의 경험에서 나온 것인지 조사에서 나온 것인지 알 수 없다.
제작사는 수십 개의 AI 사업이 같은 벽에 부딪힌 것을 보았다고 하지만
어떤 사업인지는 밝히지 않는다.

### 검증할 수 있는 외부 증거가 없다

사이트에는 고객 이름도, 사례도, 보안 감사 결과도, 기술 문서도, 가격도 없다.
규정 준수(Compliance Ready)를 내세우지만
어떤 규정과 인증을 가리키는지 적지 않는다.
제작사는 두 곳의 컨설팅 회사이며,
사이트에 적힌 회사 정보는 영국 등록 회사의 소재와 연락처 정도다.[^privacy]

이는 이 제품이 나쁘다는 뜻이 아니라 사이트만으로는 평가할 수 없다는 뜻이다.
도입을 검토하는 팀은 데모를 요청해 위의 질문(제공자별 데이터 흐름, STDIO 격리,
MCP 개정판, 규정 인증)에 직접 답을 받아야 한다.

## 인사이트

### 운영 기반을 사는 플랫폼에서는 차별화가 지식과 도구 설계로 넘어간다

제작사는 RAG가 기능이 아니라 훈련이 필요한 영역이라고 말하고,
도구는 업무 흐름을 하나의 결정적 도구로 감싸게 한다고 한다.
이 말은 배관을 플랫폼이 맡아도 결과의 품질은 고객이 무엇을 올리고
어떻게 청킹하고 어떤 도구를 설계하는지에 달린다는 뜻이다.
플랫폼이 설정 가능한 청킹과 여러 임베딩 제공자를 열어 둔 것은 그 책임을 고객에게
돌려주는 설계이기도 하다.

그러므로 이런 플랫폼의 도입 효과는 설치 시간이 아니라 지식 베이스의 큐레이션과
도구의 설계에서 갈린다.
제작사가 말한 몇 분은 빈 어시스턴트를 여는 시간이고,
쓸 만한 어시스턴트가 되는 시간이 아니다.
이는 이 문서의 해석이다.

### 구성의 버전이 곧 동작의 버전은 아니다

제작사는 “무엇이 바뀌었나” 문제를 어시스턴트와 지식 베이스의 불변 스냅샷으로
푼다고 한다.
프롬프트 하나가 바뀌어 결과가 나빠졌을 때 어느 버전이 잘 돌았는지 되짚는 데
이 스냅샷이 유용하다.

그러나 어시스턴트의 동작은 프롬프트와 지식 베이스 버전뿐 아니라 모델 제공자의
모델 버전과 도구의 응답에도 달려 있다.
스냅샷이 모델 식별자를 고정하고 도구의 버전도 함께 기록하는지가 재현성을 정한다.
사이트는 이를 말하지 않으며, 제공자를 바꿔도 구성이 그대로라는 장점이 반대로
동작 변화의 원인을 늘린다.
이 점은 이 문서의 관점이며, 확인하려면 스냅샷이 담는 항목의 목록이 필요하다.

### 에어갭과 클라우드 모델 사이의 경계를 정책으로 만들어야 한다

데이터가 밖으로 나가는 경로가 모델 호출 하나라면,
경계를 지키는 가장 단순한 방법은 어시스턴트 단위로 쓸 수 있는 제공자를 제한하는
정책이다.
민감한 지식 베이스를 쓰는 어시스턴트는 로컬 모델만,
공개 자료를 쓰는 어시스턴트는 외부 제공자도 쓰게 하는 식이다.

이런 정책이 제품에 있는지가 온프레미스라는 이름의 실질을 정한다.
역할 기반 접근 제어가 사람의 권한을 다루는 것과 달리,
이 정책은 어시스턴트가 데이터를 보낼 수 있는 곳을 다룬다.
이 제안은 이 문서의 것이며 사이트에는 해당 기능이 적혀 있지 않다.

### 결론을 바꿀 관찰

- 데모나 문서에서
제공자별 데이터 흐름과 어시스턴트 단위 제공자 제한이 확인된다면,
100% 온프레미스라는 약속에 대한 비평은 약해진다.
- STDIO MCP 서버를 테넌트별로 격리해 실행하는 방식이 공개된다면,
멀티 테넌시와 STDIO를 함께 쓰는 보안 우려가 해소된다.
- 스냅샷에 모델 식별자와 도구 버전이 포함된다면,
구성의 버전과 동작의 버전의 간극에 대한 지적은 줄어든다.
