# Kimi Code CLI: 영상을 입력으로 받는 터미널 코딩 에이전트

<https://www.kimi.com/code/>

<https://www.kimi.com/code/docs/en/>

<https://github.com/MoonshotAI/kimi-code>

## 소개

저장소 설명이 스스로를 이렇게 규정한다 — “차세대 에이전트의 출발점”이다.
터미널에서 도는 AI 코딩 에이전트이며,
코드를 읽고 고치고 셸 명령을 실행하고 파일을 검색하고 웹 페이지를 가져오며
받은 피드백에 따라 다음 단계를 고른다고 적는다.
Moonshot AI의 Kimi 모델과 기본으로 붙고
호환되는 다른 제공자도 설정할 수 있다.

저장소는 `MoonshotAI/kimi-code`이고 MIT 라이선스다.
2026년 5월 22일에 만들어졌고 TypeScript로 작성되었으며,
별 6,969개, 포크 1,104개다.
최신 릴리스는 `@moonshot-ai/kimi-code@0.38.0`으로 2026년 8월 20일에 나왔다.

[같은 팀의 이전 프로젝트인 Kimi CLI](kimi-cli.md)와의 관계가 명시되어 있다.
그쪽 README 상단에 Kimi CLI가 Kimi Code CLI로 진화하고 있다는 알림이 있고,
Kimi Code CLI를 설치하면 설정과 세션이 자동으로 이전되며
이전 프로젝트는 단계적으로 종료된다고 적혀 있다.
Kimi CLI는 Python으로 작성되어 2025년 10월 15일에 시작됐고 별이 11,229개다.

## 설치

Node.js 없이 설치되는 것을 첫 기능으로 든다.

macOS와 Linux는 `curl -fsSL https://code.kimi.com/kimi-code/install.sh | bash`이고,
Windows는 PowerShell에서 `irm https://code.kimi.com/kimi-code/install.ps1 | iex`다.
Windows에서는 Git for Windows를 먼저 설치해야 하는데
번들된 Git Bash를 셸 환경으로 쓰기 때문이며,
다른 경로에 설치했으면 `KIMI_SHELL_PATH`에 `bash.exe`의 절대 경로를 넣는다.

첫 실행에서 `/login`으로 Kimi Code OAuth 또는
Moonshot AI 오픈 플랫폼 API 키를 고른다.
프로젝트 폴더에서 `kimi`를 실행하면 대화형 UI가 뜬다.

## 주요 기능

README가 아홉 개 항목을 든다.

단일 바이너리 배포라서 Node.js 설정이나 PATH 조정이나
전역 모듈 충돌이 없다고 적는다.
TUI가 밀리초 안에 준비되며,
긴 세션에 맞춰 처음부터 끝까지 조율된 전용 인터페이스라고 설명한다.

영상 입력이 가장 특이한 항목이다.
화면 녹화나 데모 클립을 대화에 넣으면
에이전트가 말로 설명하기 어려운 것을 직접 본다고 적고,
참조 클립을 LUT로 바꾸거나 긴 영상을 짧게 만들거나
화면 녹화를 동작하는 코드로 바꾸는 것을 예로 든다.

MCP 설정을 대화로 한다.
`/mcp-config`로 Model Context Protocol 서버를 추가하고 편집하고 인증하며
JSON을 손으로 고치지 않는다.
플러그인은 마켓플레이스나 아무 GitHub 저장소에서 설치할 수 있고,
스킬과 MCP 서버와 데이터 소스가 대상이며
설치마다 신뢰 수준이 먼저 표시된다.

서브에이전트로 `coder`와 `explore`와 `plan`이 내장되어 있고
격리된 컨텍스트에서 병렬로 돌면서 주 대화를 깨끗하게 유지한다.
수명 주기 훅으로 로컬 명령을 특정 시점에 실행해
위험한 도구 호출을 막거나 결정을 기록하거나
데스크톱 알림을 띄우거나 자체 자동화에 연결할 수 있다.

에디터 통합은 Agent Client Protocol로 한다.
`kimi acp`를 stdio로 붙이면 Zed와 JetBrains를 비롯한
ACP 호환 에디터가 세션을 구동하고,
한 번 로그인하면 에디터 쪽에서 추가 로그인이 필요 없다.
Zed는 `~/.config/zed/settings.json`의 `agent_servers`에 등록한다.

TUI는 `pi-tui` 위에 만들었고 README가 그 저자들에게 감사를 표한다.

## 모델과 요금제

README가 다루지 않는 조건들이 공식 문서의 모델 설정 페이지에 있다.
이 도구로 무엇을 할 수 있는지가 실제로는 여기서 결정된다.

모델은 두 종류이고 모델 ID는 네 개다.

| 모델 ID   | `k3`          | `k3-256k`     | `kimi-for-coding` | `kimi-for-coding-highspeed` |
| --------- | ------------- | ------------- | ----------------- | --------------------------- |
| 버전      | Kimi K3       | Kimi K3       | K2.7 Code         | K2.7 Code HighSpeed         |
| 컨텍스트  | 최대 1M       | 256k 고정     | 256k              | 256k                        |
| 속도      | 보통          | 보통          | 보통              | 6배(할당량 3배 소모)        |
| 추론      | low/high/max  | low/high/max  | Thinking ON       | Thinking ON                 |
| 멀티모달  | 이미지, 영상  | 이미지만      | 이미지, 영상      | 이미지, 영상                |
| 이용 조건 | Moderato 이상 | Moderato 이상 | 전체 회원         | Allegretto 이상             |

`k3`가 플래그십이며 파라미터 2.8조에 컨텍스트 1M이다.
1M 컨텍스트는 Allegretto 이상에서만 열리고,
Moderato 요금제에서 `k3`는 256K까지만 지원된다.

권장 모델은 `k3`가 아니라 `k3-256k`다.
256k 안에서는 같은 결과를 내면서
`k3`(1M)가 `k3-256k`의 약 두 배 할당량을 쓴다고 문서가 적으며,
일상적 질의응답과 코드 완성과 통상적 기능 개발과
단일·소규모 파일 편집에 적합하다고 안내한다.
그리고 같은 문장 끝에 영상 입력을 지원하지 않는다고 붙는다.

전환에 관한 주의사항이 길다.
`k3`에서 `k3-256k`로 옮길 때 현재 세션 컨텍스트가 이미 256k를 넘으면
Kimi Code CLI나 Claude Code 같은 도구 쪽에서 압축이 일어나므로
먼저 수동으로 압축하는 것을 권한다.
대화 이력에 영상 파일이 있으면 전환 자체가 실패하며,
`k3-256k`가 영상 입력을 지원하지 않기 때문이다.
반대 방향, 즉 256k에서 1M으로 가는 전환은 캐시에 영향이 없다.

권한 부족은 HTTP 401로 돌아온다.
Moderato 미만 요금제는 `k3`와 `k3-256k`를 호출할 수 없고,
`kimi-for-coding-highspeed`는 Allegretto 이상이 필요하다.
모델 ID 대신 `Kimi K3` 같은 버전 이름을 넣으면 호출이 실패한다.

조용히 다른 결과가 되는 경우가 두 가지 명시되어 있다.
Thinking을 끄면 요청이 K2.6으로 라우팅되며,
HighSpeed 모델 ID를 잘못 적으면 오류도 속도 향상도 없이
표준 `kimi-for-coding`으로 조용히 되돌아간다.
그리고 HighSpeed는 모델 출력만 빠르게 하므로
도구 호출과 스크립트 실행이 턴의 대부분을 차지하면 체감이 작다.

API는 OpenAI 규약과 Anthropic 규약을 모두 지원한다.
전자는 `https://api.kimi.com/coding/v1`,
후자는 `https://api.kimi.com/coding/`이다.
제3자 도구에서 K3를 쓸 때는 컨텍스트 창 필드를 `1048576`으로 직접 넣어야 하고,
추론 강도는 `ultra`/`max`/`xhigh`가 max로,
`high`/`medium`이 high로, `low`/`minimum`/`light`가 low로 매핑되며
알 수 없는 값은 HTTP 400이다.

## 개발

요구 사항은 Node.js 24.15.0 이상과 pnpm 10.33.0이다.
`pnpm dev:cli`로 개발 모드 실행,
`pnpm test`, `pnpm typecheck`, `pnpm lint`(oxlint), `pnpm build`가 스크립트다.

## 분석

### 파이썬에서 TypeScript로 다시 쓴 것이 이 프로젝트의 실제 사건이다

README는 Kimi Code CLI를 새 제품으로 소개하지만
저장소 두 개를 나란히 놓으면 다른 이야기가 보인다.
Kimi CLI는 2025년 10월에 Python으로 시작해 별 11,229개를 모았고,
Kimi Code CLI는 2026년 5월에 TypeScript로 시작해 별 6,969개다.
같은 팀이 반년 만에 언어를 바꿔 다시 쓴 것이며,
이전 프로젝트는 단계적으로 종료된다.

이 재작성의 이유가 기능 목록의 첫 두 항목에 있다.
Node.js 없는 단일 바이너리 설치와 밀리초 단위 TUI 시작이다.
Python 배포의 고질적 문제가 바로 그 둘이며 —
인터프리터 버전과 가상 환경과 전역 패키지 충돌,
그리고 임포트 시간에서 오는 시작 지연이다.
`pip install`을 안내하던 프로젝트가
`curl | bash`를 안내하는 프로젝트로 바뀐 것이 그 결론이다.

그런데 TypeScript를 골랐다는 점이 흥미롭다.
배포 문제를 해결하려면 Go나 Rust로 가는 것이 통상적 선택이고,
[이 저장소에 기록된 6MB 단일 바이너리 에이전트](../agentic-coding/fx.md)가 그 경로다.
TypeScript로 단일 바이너리를 만들려면 런타임을 함께 묶어야 하므로
바이너리가 커지고 배포 파이프라인이 복잡해진다.
그 비용을 감수한 이유는 생태계일 것이다 —
MCP와 ACP와 플러그인 마켓플레이스와 스킬이 전부
JavaScript 생태계에서 먼저 자리를 잡았고,
그 표준들에 붙는 비용이 언어 선택을 지배했다.

이 판단이 옳았는지는 별 개수가 아직 말해 주지 않는다.
이전 저장소가 여전히 별이 더 많고,
후속 저장소의 버전은 0.38.0이다.
반년 전에 사용자를 모은 프로젝트를 접고 새로 시작하면서
버전 번호를 1.0에 올리지 않은 상태로 승계를 선언한 것이며,
이 조합이 다음 절의 문제로 이어진다.

### 영상 입력은 코딩 에이전트의 입력 형식을 바꾸려는 시도다

기능 목록에서 다른 에이전트에 없는 항목은 하나다.
화면 녹화나 데모 클립을 대화에 넣는 것이며,
말로 설명하기 어려운 것을 에이전트가 직접 보게 한다는 설명이 붙는다.

이 기능의 의미는 명세 전달 방식에 있다.
지금까지 코딩 에이전트에게 UI 작업을 시키려면
스크린샷을 붙이고 원하는 동작을 산문으로 적었고,
그 산문이 실패의 주요 원인이었다 —
사람은 동작을 순서로 기억하는데 그것을 문장으로 옮기는 과정에서
타이밍과 전환과 예외가 빠진다.
화면 녹화는 그 세 가지를 그대로 담고 있다.

예로 든 세 가지가 그 범위를 보여 준다.
참조 클립을 LUT로 바꾸는 것은 색 보정 값의 추출이고,
긴 영상을 짧게 만드는 것은 편집 판단이며,
화면 녹화를 동작하는 코드로 바꾸는 것은 UI 재현이다.
셋 중 코딩 에이전트의 통상 범위에 있는 것은 마지막 하나뿐이고,
나머지 둘은 이 도구가 코딩 도구의 경계를 넘겠다는 신호다.

여기서 모델 쪽 조건이 드러난다.
영상을 프레임으로 쪼개 넣으면 컨텍스트가 폭발하므로
이 기능이 성립하려면 모델이 영상을 직접 다뤄야 하고,
그것은 CLI의 기능이 아니라 [Kimi 모델의 기능](../ai/kimi-k3.md)이다.
즉 이 항목은 도구의 차별점이 아니라
자사 모델을 쓰게 만드는 고리이며,
호환 제공자를 설정할 수 있다는 문장과 나란히 놓으면
어느 항목이 이식되지 않는지가 분명해진다.

### 신뢰 수준 표시와 수명 주기 훅이 같은 문제의 두 답이다

기능 목록에 안전 관련 항목이 두 개 있는데 성격이 다르다.
플러그인을 마켓플레이스나 아무 GitHub 저장소에서 설치할 수 있게 하면서
설치마다 신뢰 수준을 먼저 표시하고,
수명 주기 훅으로 위험한 도구 호출을 막을 수 있게 한다.

앞의 것은 공급 측 통제다.
누가 만든 것인지, 검증된 것인지를 설치 시점에 알려 주는 방식이며,
[제3자가 만든 것을 중개하는 플랫폼이 대체로 갖추지 않은 장치](../data/apify.md)를
이 프로젝트는 기능 목록에 적어 두었다.
아무 GitHub 저장소에서 설치할 수 있게 열어 놓았으므로
그 표시가 없으면 임의 코드 실행 경로가 되는데,
그 위험을 인지하고 표시를 붙인 순서가 옳다.

뒤의 것은 실행 측 통제다.
훅으로 로컬 명령을 특정 시점에 실행해 위험한 호출을 막고 결정을 기록한다.
설치 시점에 판단하는 것과 실행 시점에 판단하는 것은 다른 문제이고,
둘 다 필요한 이유는 신뢰할 만한 출처의 플러그인도
특정 상황에서 위험한 호출을 할 수 있기 때문이다.

두 장치가 함께 있다는 사실이 이 프로젝트의 설계 성숙도를 보여 준다.
다만 둘 다 사용자가 설정해야 작동하는 종류다.
신뢰 수준은 표시될 뿐 차단하지 않고,
훅은 사용자가 쓰지 않으면 없는 것과 같다.
기본값이 무엇인지가 README에 없고,
이 부분은 다음 절에서 다룰 문서 상태 문제와 이어진다.

## 비평

### 열린 이슈 713개와 닫힌 이슈 310개라는 비율은 정상 운영의 신호가 아니다

이 저장소의 이슈 상태를 보면 열린 것이 713개이고 닫힌 것이 310개다.
석 달 만에 1,023개의 이슈가 올라왔고 그중 30%가 닫혔다는 뜻이며,
별 6,969개에 대해 열린 이슈 713개는 별 열 개당 하나가 넘는다.
[같은 시기에 관찰한 다른 프로젝트](../issue-tracker/kaneo.md)는
별 8,411개에 열린 이슈 57개였다.

이 비율이 나쁜 코드의 증거는 아니다.
빠르게 성장하는 프로젝트에서 이슈가 쌓이는 것은 흔하고,
사용자가 많으면 신고도 많다.
그리고 이 저장소는 석 달 동안 0.38.0까지 왔으므로
릴리스 속도 자체는 느리지 않다.

문제는 이 상태에서 승계를 선언했다는 점이다.
이전 프로젝트를 단계적으로 종료하고
설치 시 설정과 세션을 자동 이전한다고 적었으므로,
별 11,229개짜리 프로젝트의 사용자가 이쪽으로 넘어온다.
넘어온 사용자가 마주하는 것은 713개의 열린 이슈이고,
자기가 겪는 문제가 이미 신고됐는지 찾기가 어렵다.
승계의 순서가 뒤바뀐 것이며,
안정화 후 이전이 아니라 이전 후 안정화를 하고 있다.

이 순서를 뒷받침할 문서가 없다는 것이 더 아쉽다.
README에 알려진 제한이나 마이그레이션 주의사항이나
이전 프로젝트와의 기능 차이 표가 없다.
Python 판에 있던 셸 명령 모드가 —
`Ctrl-X`로 셸과 에이전트를 전환하던 기능이 —
TypeScript 판에 있는지 없는지가 README만으로는 알 수 없다.
자동 이전을 약속했으므로 그 차이표가 가장 필요한 문서인데,
기능 목록은 새 기능만 나열한다.

### 단일 바이너리라고 적으면서 개발 요구 사항에 Node.js 24.15.0을 요구한다

첫 기능 항목의 문장은 이렇다 —
단일 바이너리 배포이며 Node.js 설정이나 PATH 조정이나
전역 모듈 충돌이 없다는 것이다.
같은 문서의 개발 절에는 Node.js 24.15.0 이상과 pnpm 10.33.0이 요구 사항으로 있다.
릴리스 태그는 `@moonshot-ai/kimi-code@0.38.0`이라는 npm 패키지 형식이고,
설치 안내에도 npm 설치 방법이 문서에 있다고 적혀 있다.

이것이 거짓은 아니다.
사용자용 배포는 런타임을 묶은 단일 실행 파일이고
개발용은 소스에서 빌드하므로 Node.js가 필요한 것이 당연하다.
그런데 두 사실이 같은 문서에서 설명 없이 붙어 있으면
읽는 사람이 어느 쪽 상태인지 판정하기 어렵다.

이 모호함이 실제 문제가 되는 지점이 있다.
npm으로 설치한 경우와 스크립트로 설치한 경우가
같은 버전을 쓰는지, 업데이트 경로가 같은지,
전역 모듈 충돌이 npm 경로에서도 없는지가 정해지지 않는다.
Windows에서 Git for Windows를 먼저 설치해야 하고
번들된 Git Bash를 셸로 쓴다는 조건이 있으므로,
의존성이 없다는 주장은 이미 한 번 예외를 갖고 있다.

정직한 서술은 두 줄이면 된다.
설치 스크립트는 런타임을 포함한 실행 파일을 놓고
npm 설치는 Node.js를 쓰며 양쪽 버전이 동기화된다고 적으면 된다.
지금은 마케팅 문구 하나가 배포 방식 두 개를 덮고 있다.

### 대표 기능이 권장 모델에서 작동하지 않는다

README의 기능 목록에서 가장 특이한 항목이 영상 입력이고,
이 문서도 그것을 제목으로 골랐다.
그런데 모델 문서를 보면 권장 모델인 `k3-256k`가 영상을 지원하지 않는다.

이 조합이 만드는 상태가 이상하다.
공식 문서가 일상 작업에는 `k3-256k`를 권하고
`k3`(1M)가 두 배 할당량을 쓴다고 알려 주므로,
안내를 따르는 사용자의 기본 설정에서 영상 입력이 빠진다.
대표 기능을 쓰려면 문서가 권하지 않는 모델로 옮겨야 하고,
그 이동의 비용이 할당량 두 배다.

전환 실패 조건이 그 어긋남을 더 분명히 한다.
대화 이력에 영상 파일이 있으면 `k3-256k`로의 전환이 실패하므로
먼저 압축해서 그 영상을 이력에서 지워야 한다.
즉 영상을 한 번 쓰면 권장 모델로 돌아가는 데 추가 조작이 필요하며,
그 사실이 기능 소개가 아니라 전환 주의사항 안에만 적혀 있다.

여기서 README와 문서의 역할 분담이 문제가 된다.
README는 무엇이 가능한지를 나열하고
문서는 어느 조건에서 가능한지를 적는데,
둘을 다 읽지 않으면 결론이 반대로 나온다.
기능 목록에 “일부 모델에서만”이라는 다섯 자를 넣는 것이
이 문서의 정확도를 가장 크게 올리는 수정이다.

### 조용한 강등이 세 곳에 있는데 신뢰 표시는 플러그인에만 붙어 있다

분석에서 이 프로젝트의 안전 설계를 칭찬할 근거로
플러그인 신뢰 수준 표시와 수명 주기 훅을 들었다.
그런데 모델 계층에는 그 원칙이 적용되지 않았다.

문서가 스스로 밝힌 조용한 동작이 세 가지다.
Thinking을 끄면 요청이 K2.6으로 라우팅되고,
HighSpeed 모델 ID를 잘못 적으면 오류도 속도 향상도 없이
표준 모델로 되돌아가며,
모델을 바꾸면 컨텍스트 캐시가 무효화되어 사용량이 갑자기 오른다.
셋 다 사용자가 요청한 것과 다른 것이 실행되는 경우이고,
셋 다 통지가 없다.

세 번째가 특히 비용으로 직결된다.
새 모델이 나온 뒤 사용량이 왜 올랐냐는 질문이
공식 FAQ 항목으로 들어가 있을 정도이며,
답이 이전 캐시가 새 모델에서 적중하지 않아 재프리필이 일어난다는 것이다.
그 설명은 정확한데, 설명이 필요한 상태 자체가 설계의 결과다.
모델을 바꿀 때 “캐시가 무효화되며 이번 턴 비용이 오릅니다”를
한 줄 띄우면 FAQ가 필요하지 않다.

그리고 이 대비가 이 프로젝트의 성격을 보여 준다.
제3자가 만든 플러그인에는 신뢰 수준을 표시하고
자사가 운영하는 라우팅에는 표시하지 않는다.
위험의 크기로 보면 순서가 뒤바뀌어 있다 —
플러그인 설치는 드물고 의식적인 행동인데
모델 전환과 추론 강도 변경은 세션마다 반복되는 조작이다.
빈도가 높은 쪽에 통지가 없는 것이 실제 손실을 만든다.

HN에서 요금 관련 정보의 부재가 반복적으로 지적됐다.
이 모델의 가격을 찾을 수 없다는 것이며,
컨텍스트가 풀 사이즈 K3의 4분의 1이니
가격도 그만큼 싼 것인지 묻는 질문이었다[^sergiotapia].
답은 Kimi Code 구독으로만 이용 가능하고 API 가격이 없으며
문서에 적힌 것은 1M 판의 절반 정도 할당량을 쓴다는 것뿐이라는 확인이었다[^daemonologist].
할당량이라는 단위는 요금제 내부의 상대 척도이므로
다른 제공자와의 비교가 불가능하고,
그 불투명함이 의도적 설계일 가능성을 배제할 근거가 없다.

### 실제 사용 보고는 아직 좋지 않고, 프로젝트는 그 지점을 다루지 않는다

Hacker News에 이 도구를 몇 시간 써 본 사람의 짧은 글이 있다.
Kimi 구독을 얻어 Claude Code의 스킬과 설정을 그대로 가져와 붙이고
JS와 Python 코드베이스에 리뷰와 리팩터링을 시키고 기능을 추가하게 했는데,
겉모습은 그럴듯하지만 어이없는 실수를 한다는 것이었다.
Claude Code에 비해 느리고 시간이 걸리고 토큰을 많이 먹으며,
끝났다고 여러 번 말했는데 앱이 아예 시작되지 않았다고 적었다.
조용한 실패를 절대 허용하지 않는다는 지시를 명시적으로 세워 두었는데도
그런 실패를 코드에 남겼다고 덧붙였다[^kimi-op].

이어진 댓글은 그 관찰을 다른 모델들로 확장했다.
Sonnet과 Opus를 제외한 모델들을 같은 스킬과 워크플로로 시험해 봤는데
전부 지시를 제대로 따르지 않았고
2024년에 나온 Sonnet 3.5 수준으로 느껴져서
무료 엔드포인트에서 간단한 작업에만 쓴다는 내용이었다[^CapyToolkit].

이 스레드는 2점에 댓글 하나이므로 대표성이 없고,
사용 시간도 몇 시간이며 비교 기준도 한 사람의 기존 설정이다.
그러므로 이것을 성능 평가로 읽을 수는 없다.
다만 두 보고가 같은 지점을 가리킨다는 점은 남는다 —
스킬과 설정을 이식했을 때 지시 준수가 무너진다는 것이다.

더 큰 스레드들을 보면 평가가 갈리는 축이 드러난다.
다중 에이전트 게임 코딩 평가를 돌린 쪽의 보고가 가장 구조적이다 —
중국 모델들이 통상 원샷 추론에서 고전하고
도구 사용과 반복을 통한 개선으로 그것을 메우는 패턴을 보이는데
Kimi K3도 그 패턴을 따라서 원샷 코딩 19위, 에이전틱 코딩 3위이며
평균 에이전틱 코딩 결과가 더 좋은 것은 Sol과 Fable뿐이라는 것이다[^gertlabs].
소프트웨어 엔지니어에게 중요한 것이 에이전틱 코딩이라는 점에서
이 순위 조합이 이 도구의 위치를 앞의 개인 보고보다 정확히 설명한다.

같은 스레드에서 만족한 사용자들의 근거도 구체적이다.
6개월 가까이 코딩 작업에 써 왔고 되돌아가지 않았으며
주기적으로 Claude로 확인해 보지만 놓치는 것이 없어 만족한다는 보고[^abalashov]와,
100달러 구독을 쓰면서 200달러로 올릴까 고민 중이고
모델이 Opus와 대략 동등한 수준인데 실사용에서 덜 짜증스럽고
슬롭 같은 표현이 조금 적다는 평가[^KronisLV-sub]가 있었다.

반대편의 불평은 성능이 아니라 용량과 비용에 몰려 있다.
Claude 사용량을 다 써서 20달러를 내고 시험해 봤는데
저장소를 훑어 보고서를 만들라는 지시에 12분을 생각하더니
일일 할당량을 다 썼다고 알려 왔고
다음 날 Fable이 같은 작업을 3분에 했다는 보고[^thevinter],
예제에서 복사한 실행 스크립트가 추론 강도를 max로 두고 있던 것을 몰라서
개인 프로젝트에 3~4시간 만에 50달러를 넘게 썼다는 보고[^noisy_boy],
20달러 요금제의 속도 제한이 너무 빨라서
주간 예산을 이틀에 소진하기 쉬우며
K3까지 그 요금제에서 쓰는 것은 상상하기 어렵다는 지적[^charcircuit]이다.
과부하 때문에 간단한 코드 리뷰조차 한참 걸린다는 관찰[^vblanco]도 함께 있었다.

이 보고들을 모으면 앞 절의 요금제 표가 다시 읽힌다.
추론 강도 기본값이 high이고 max가 존재하며
HighSpeed가 할당량을 세 배 쓰고 `k3`가 `k3-256k`의 두 배를 쓰는데,
이 승수들이 곱해지는 구조라는 것을 문서가 한 곳에서 계산해 주지 않는다.
50달러를 3~4시간에 쓴 사례가 나쁜 설정 하나에서 나왔다는 사실이
그 계산의 부재가 만드는 비용이다.

그리고 이 지점이 프로젝트 문서에서 비어 있다.
README는 Claude Code의 스킬 생태계와 붙는 것을 사실상 전제한다 —
플러그인 마켓플레이스에서 스킬을 설치하고
아무 GitHub 저장소에서도 가져올 수 있다고 적는다.
그런데 다른 에이전트를 위해 쓰인 스킬이 여기서 같은 결과를 내는지,
어떤 부분이 호환되지 않는지에 대한 문서가 없다.
호환성을 판매점으로 쓰면 호환의 범위를 적어야 하고,
그것이 없으면 이식한 사용자의 실망이 도구의 평가가 된다.

## 인사이트

### 코딩 에이전트의 재작성은 언어가 아니라 배포 형식을 고치기 위해 일어난다

이 프로젝트의 재작성 동기는 성능이나 표현력이 아니었다.
기능 목록의 첫 두 항목이 설치와 시작 시간이며,
그것은 언어의 문제가 아니라 배포의 문제다.
Python으로도 빠른 에이전트를 만들 수 있고,
문제는 사용자의 기계에 그것을 놓는 과정이었다.

이 패턴이 이 범주에서 반복되고 있다.
[6MB 단일 바이너리로 다시 만든 에이전트](../agentic-coding/fx.md)가 같은 동기이고,
자체 배포 CLI를 만들어 설치를 한 줄로 줄인
[데스크톱 앱](../agentic-coding/agentcodegui.md)도 같은 동기다.
셋의 언어와 형태가 다 다른데 해결하려는 것이 같다.

여기서 일반화할 수 있는 것은 이 도구 범주의 채택 병목이다.
코딩 에이전트의 가치는 몇 분 안에 드러나는데
설치가 몇 분을 넘기면 그 가치가 확인되기 전에 이탈이 생긴다.
게다가 대상 사용자가 개발자이므로
이미 자기 기계에 여러 런타임과 버전 관리자를 갖고 있고,
새 도구가 그것과 충돌하면 설치가 몇 분이 아니라 몇 시간이 된다.
그래서 이 범주에서 배포 형식은 부차적 항목이 아니라 제품 결정이다.

2차 효과는 언어 선택의 기준 이동이다.
전통적으로 CLI 도구의 언어는 성능과 개발 속도로 골랐는데,
지금은 그 위에 두 항목이 얹혔다 —
런타임을 함께 묶을 수 있는지, 그리고 MCP·ACP 같은
에이전트 표준의 참조 구현이 그 생태계에 있는지다.
이 프로젝트가 TypeScript를 고른 것은 뒤쪽 때문이고,
Go나 Rust를 고른 프로젝트들은 앞쪽을 우선한 것이다.
두 갈래가 당분간 공존할 것이며,
표준 구현이 여러 언어로 성숙하는 시점에 이 균형이 다시 움직인다.

### ACP를 지원하면 에디터 전쟁에서 빠져나올 수 있다

이 도구는 VS Code 확장을 만들지 않았다.
대신 Agent Client Protocol을 말하고 `kimi acp`를 제공하며,
Zed와 JetBrains가 stdio로 그 세션을 구동한다.
설정은 에디터 쪽 JSON에 명령 이름을 적는 것으로 끝난다.

이 선택의 값은 유지 비용에 있다.
에디터별 확장을 만들면 확장마다 UI와 상태 관리와 배포 심사가 생기고,
에디터가 API를 바꿀 때마다 따라가야 한다.
프로토콜을 말하면 그 비용이 에디터 쪽으로 넘어가며,
새 에디터가 프로토콜을 지원하면 이 도구는 아무 일도 하지 않고 지원된다.

이 구도가 웹 초기의 반복이다.
브라우저별 코드를 쓰던 시기에서 표준을 구현하는 시기로 넘어갈 때
같은 논리가 작동했고,
결국 표준을 먼저 구현한 쪽이 유지 비용에서 이겼다.
차이는 지금 표준이 더 어린 상태라는 점이며,
그래서 프로토콜에 없는 기능이 곧 없는 기능이 된다.

여기서 따라오는 긴장이 하나 있다.
이 도구의 차별점 중 하나가 영상 입력인데,
영상을 대화에 넣는 것은 파일 첨부와 미리보기와 진행 표시가 필요한 상호작용이다.
프로토콜이 그 형태를 정의하지 않으면
가장 특이한 기능이 에디터 안에서는 쓸 수 없다.
README가 ACP의 전체 기능 대응표를 별도 문서로 안내한다는 점이
그 문제를 인지한 흔적이며,
프로토콜 기반 통합을 고른 도구는 앞으로 반복해서
자기 차별점과 표준의 진도 사이에서 선택하게 된다.

### 별 개수보다 이슈의 개폐 비율이 에이전트 도구의 성숙도를 더 잘 알려 준다

이 저장소는 별 6,969개에 열린 이슈 713개, 닫힌 이슈 310개다.
이 비율이 알려 주는 것은 코드 품질이 아니라 대응 용량이다.
석 달에 1,023개가 올라오고 310개가 닫혔으므로
들어오는 속도가 처리하는 속도의 세 배가 넘는다.

이 지표가 에이전트 도구에서 특히 유용한 이유가 있다.
에이전트는 비결정적이므로 같은 명령이 다른 결과를 내고,
사용자가 겪는 문제를 재현하기 어렵다.
그래서 이슈 하나를 닫는 비용이 통상 소프트웨어보다 높고,
쌓이는 속도가 팀 규모를 넘어서면 회복되지 않는다.
별은 관심의 지표이고 개폐 비율은 부채의 지표인데,
이 범주에서는 후자가 사용 결정에 훨씬 가깝다.

같은 계산을 다른 프로젝트들에 적용하면 대비가 선명해진다.
[별 8,411개에 열린 이슈 57개인 프로젝트](../issue-tracker/kaneo.md)는
기능 범위를 좁게 유지한 결과이고,
[다운로드 3만 건에 열린 이슈 0개인 프로젝트](../agentic-coding/agentcodegui.md)는
보고 경로가 없는 결과다.
세 값이 다 다른 이야기이며,
숫자 하나만으로는 어느 쪽인지 알 수 없다.
읽어야 하는 것은 비율이고, 함께 봐야 하는 것은 창구의 존재다.

그래서 이 범주의 도구를 고를 때 쓸 만한 절차가 생긴다.
열린 이슈를 최근 생성순으로 열어 상위 스무 개의 제목을 훑는 것이다.
설치와 인증 문제가 몰려 있으면 배포가 아직 익지 않은 것이고,
지시 준수와 도구 호출 실패가 몰려 있으면 모델과 하네스의 접합이 문제이며,
기능 요청이 몰려 있으면 기본 동작이 안정된 것이다.
별 개수는 이 셋을 구분하지 못하고, 이슈 목록은 몇 분 만에 구분한다.

### 신규 가입을 막은 것이 신뢰 신호로 읽혔다는 사실이 이 시장의 기준을 알려 준다

이 도구를 쓰려면 구독이 필요한데,
K3 출시 직후 Moonshot AI가 신규 구독을 일시 중단했다.
48시간 동안 수요가 현재 용량의 한계에 근접했고
기존 구독자의 경험을 보호하기 위해 신규 구독을 잠시 멈추고
컴퓨트를 현재 회원에게 우선 배정하며
기존 사용자는 영향을 받지 않는다는 공지였다.

HN의 반응이 거의 일방적으로 호의적이었다는 점이 특이하다.
빠른 성장에만 집중하는 대신 현재 고객을 우선하고
만족을 유지하는 데 집중하는 회사라는 평가[^Alifatisk-sub]와,
용량이 없는데도 계속 사용자를 받으면서
뒤에서 조용히 모두의 한도를 낮추는 방식보다
이쪽이 훨씬 낫다는 비교[^0xc0c0c0]가 있었다.
같은 비교가 다른 회사로도 이어졌다 —
사용량 한도를 줄이고 K3를 요금제에서 빼고 주간 상한을 붙이고
그것을 “공정 사용”이라고 부르는 방법이 있었을 것이며
1조 달러 기업이 그 각본을 한동안 써 왔다는 지적[^kburman]이고,
활동이 크게 늘면 품질 유지를 위해 한도를 예고 없이 바꿀 수 있다는
Gemini의 약관을 인용한 대비[^cube00]도 있었다.

이 반응이 알려 주는 것은 이 시장의 기본값이 무엇으로 인식되고 있는지다.
사용자들은 조용한 성능 저하와 조용한 한도 축소를 이미 전제하고 있으며,
그래서 “지금은 팔지 않겠다”는 공지가 정직함의 증거로 읽힌다.
정상적인 시장이라면 재고 부족은 나쁜 소식인데
여기서는 좋은 소식으로 받아들여졌다.

그리고 이 정직함이 자발적이었는지는 확실하지 않다.
하드웨어 수출 통제에 영향을 받는 회사가 호스팅하는
극히 인기 있는 모델이며,
서비스 품질을 유지하려면 그럴 수밖에 없었을 것이라는 관찰[^InsideOutSanta]이 있었다.
그렇다면 이 사건의 교훈이 기업 윤리가 아니라 구조다 —
용량을 조용히 나눠 줄 여지가 없는 쪽이 공개적으로 멈추게 되고,
여지가 있는 쪽이 조용히 나눠 준다.
사용자가 관찰할 수 있는 것은 그 결과뿐이고,
같은 결과가 두 원인 중 어느 쪽에서 왔는지는 밖에서 구분되지 않는다.

그래서 이 도구를 도입 검토할 때 확인해야 할 항목이 하나 늘어난다.
모델의 품질이 아니라 자기 조직이 필요한 시점에
그 구독을 살 수 있는지, 그리고 산 뒤에 한도가 유지되는지다.
앞 절에서 본 할당량 승수들이 그 질문에 직결되며,
공개 벤치마크 순위는 이 질문에 아무 답도 주지 않는다.

### 오픈 가중치가 자체 호스팅 가능성을 뜻하지 않게 된 지점

이 CLI의 뒤에 있는 모델은 가중치가 공개되어 있다.
그 사실이 통상 대안 경로를 뜻하는데,
파라미터 2.8조라는 규모가 그 경로를 실질적으로 닫는다.

HN에서 그 계산이 나왔다.
오픈소스라는 것에 들떴다가
모델이 VRAM 1.5테라바이트를 요구한다는 것을 알게 됐고,
Unsloth가 1비트로 압축해 약 570GB에 75% 정확도로 만들었으며
그것이 거의 Mac Studio 영역이라는 것이다[^fumber].
정확도 75%짜리를 코딩 에이전트로 쓸 수 있느냐가 남는 질문이고,
그 답이 아니라면 가중치 공개가 선택지를 만들지 못한다.

그런데 같은 스레드에서 반대 논거도 성립했다.
오픈 가중치의 값이 자체 호스팅이 아니라
추론 제공자의 존재라는 것이며,
연구소 자체가 품질과 가용성에서 막히더라도
제공자와 자기 하드웨어가 필요한 토큰을 확보해 준다는 관찰[^tosh]이다.
실제로 OpenRouter를 통해 쓰는 사용자들이
구독 중단의 영향을 받지 않았다.

두 논거가 다 맞고, 그 조합이 새로운 상태를 만든다.
가중치 공개가 개인의 독립성이 아니라
공급자 다양성을 보장하는 장치로 기능하기 시작했다는 것이다.
그러면 확인할 것도 바뀐다 —
내가 돌릴 수 있는지가 아니라
몇 개의 제공자가 이 가중치를 서비스하고 있고
그들이 어떤 양자화를 쓰는지다.
후자가 실제로 문제가 됐고,
제공자들이 어떻게 양자화했는지 정보를 찾을 수 없었다는 보고[^ezekiel68]와
파트너 제공자의 정밀도가 노출된다는 확인[^HDBaseT]이 함께 있었다.

그리고 이 구조가 조용한 품질 저하의 새 경로를 만든다.
연구소가 아니라 제공자가 양자화 수준을 고르며,
사용자는 같은 모델 이름을 보면서 다른 것을 받는다.
최근 모델들이 갑자기 멍청해졌고 지원팀이 그것을 다루지 않으며
상당 비율의 요청이 양자화된 모델로 서비스되고 있다고 짐작한다는
의심[^dools]이 그 상태의 표현이다.
가중치가 공개되어도 자기가 지금 받는 것이 무엇인지는 여전히 불투명하며,
이 도구처럼 자사 구독으로 자사 모델에 붙는 경로에서는
그 불투명함이 한 겹 더 두꺼워진다.

### 자사 모델을 위한 CLI는 오픈소스이면서 이식 불가능한 부분을 갖는다

이 도구는 MIT 라이선스이고 호환 제공자를 설정할 수 있다고 적는다.
그러면 다른 모델로 갈아탈 수 있는 도구로 읽히는데,
기능 목록을 다시 보면 그 갈아타기가 균일하지 않다.

영상 입력은 모델이 영상을 다뤄야 성립한다.
서브에이전트의 격리된 병렬 실행은 모델의 도구 호출 안정성에 달려 있고,
스킬과 플러그인의 동작도 지시 준수 수준에 달려 있다.
셋 다 CLI의 코드로 구현된 부분이 있지만
결과의 품질을 결정하는 것은 뒤에 붙은 모델이다.
그러므로 이 도구를 다른 모델로 쓰면
같은 기능 목록에서 다른 제품이 된다.

이 구조가 오픈소스 코딩 에이전트 전반의 성질이 되어 가고 있다.
코드는 열려 있고 라이선스는 관대한데,
실제 값은 모델과의 접합에서 나오므로
포크해도 같은 것을 얻지 못한다.
[스크래핑 도구에서 코드는 열려 있지만
신뢰성을 만드는 계층은 닫혀 있던 구조](../data/firecrawl.md)와
형태가 같고, 여기서 닫혀 있는 것은 인프라가 아니라 모델이다.

그렇다면 이런 도구를 평가할 때 물어야 할 질문이 하나 정해진다.
이 도구를 다른 모델로 돌렸을 때 무엇이 남는지다.
남는 것이 TUI와 배포 방식과 훅과 ACP 통합이라면
그 자체로 값이 있으므로 도구로서 고를 이유가 되고,
남는 것이 없으면 그것은 도구가 아니라 자사 모델의 클라이언트다.
이 프로젝트는 전자에 가까운 항목들을 갖고 있는데 —
단일 바이너리, 밀리초 시작, 훅, ACP, 신뢰 수준 표시 —
README가 그것들을 자사 모델의 기능과 같은 목록에 섞어 두어서
어느 쪽이 이식되는지 읽는 사람이 직접 골라야 한다.
