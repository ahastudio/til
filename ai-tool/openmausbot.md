## 소개

OpenMausBot은 채팅 앱 형태의 에이전트 도구다.
사이드바에 봇 목록이 있고, 봇마다 성격, 모델, 클라우드 컴퓨터, 연결된 앱이
따로 있다.
README는 봇을 연락처처럼 대화하고, 작업을 지켜보고, 중요한 것만 승인하는
대상으로 설명한다.
개발자 Milind Soni는 이 프로젝트가 Grok Bot에서 영감을 받은 독립 프로젝트이며,
xAI와 제휴하지 않았다고 README에 밝혔다.
README는 Meta Muse, OpenAI dots, Cue by Manus의 오픈소스 대안이라고도 소개한다.
이름은 MausBot으로도 불리고, 예전 이름은 OpenGrokBot이었다고 적혀 있다.

GitHub API로 확인한 저장소의 상태는 다음과 같다.
2026년 10월 31일 기준으로 별은 8,172개, 포크는 1,171개다.
저장소는 2026년 8월 11일에 만들어졌고, 마지막 푸시는 2026년 10월 30일이다.
언어는 TypeScript이고, `package.json` 버전은 0.1.134다.
2026년 11월 9일에 다시 확인하니 별은 17,942개, 포크는 2,506개,
마지막 푸시는 11월 8일, 버전은 0.1.149였다.
열흘이 채 안 되는 사이 별이 두 배 넘게 늘었다.
`openmausbot.com`은 이제 `mausbot.com`으로 308 리디렉션되고,
저장소의 홈페이지 항목도 `mausbot.com`을 가리킨다.
README의 상태 항목은 이 프로젝트를 초기 단계이지만 메시지에서 에이전트 응답,
도구 사용, 승인, 컴퓨터 사용까지 흐름이 끝까지 돈다고 설명한다.

README가 정리한 설계의 핵심은 세 가지다.

| 항목                 | README의 설명                                                                                              |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| 에이전트 직접 지참   | `claude`, `codex`, `grok` CLI를 내 기기에서 로그인한 상태 그대로 쓰고 중계 서버가 없다                     |
| 로컬 우선            | `127.0.0.1`의 작은 하니스(harness) 서버가 모든 에이전트 프로세스를 소유하고 기록은 `~/.openmausbot`에 둔다 |
| 도구를 가진 에이전트 | 클라우드 리눅스 데스크톱, 격리된 로컬 VM, 승인한 경우 내 컴퓨터, Composio의 앱 500개 이상                  |

구조는 두 프로세스다.
앱은 전송 계층을 직접 갖지 않고 HTTP로 명령을 보내며 SSE(Server-Sent Events)
스트림 하나를 상태로 접어 넣는다.
하니스 서버가 각 제공자의 고유 프로토콜을 하나의 표준 런타임 이벤트 스트림으로
바꿔 스레드별 NDJSON으로 기록한다.

## 설치와 사용

릴리스 빌드는 하니스 서버를 내장하므로 서버를 따로 설정할 필요가 없다.
macOS(Apple silicon, Intel)는 서명하고 공증한 `.dmg`, Windows는 x64 설치
파일, Ubuntu 24.04 x64는 `.deb`나 AppImage 베타다.
README는 Windows 설치 파일이 아직 코드 서명되지 않아 SmartScreen이 알 수 없는
게시자 경고를 띄운다고 밝힌다.

터미널이나 서버에서는 Node 24 이상이 필요하다.

```bash
npm install -g openmausbot
openmausbot
```

처음 실행하면 방향키로 AI 접근 방식, 로그인 또는 API 키 입력, 모델 선택,
선택 사항인 휴대폰 연결을 안내한다.
API 키는 암호화하지 않은 평문으로 `config.json`에 저장되며 유닉스에서는 권한이
`0600`이라고 README가 적는다.
VPS에서는 `npx openmausbot serve`에 `--tunnel`, `--tailscale` 같은 원격 옵션을
명시해서 띄우고, 기기는 짧은 코드로 한 번 페어링한다.

소스에서는 `pnpm install` 뒤에 서버, 앱, 데스크톱을 따로 띄운다.

```bash
pnpm dev:server
pnpm dev
pnpm dev:desktop
```

`openmausbot` 명령은 화면 없이도 쓸 수 있다.
`openmausbot team apply team.yaml`로 팀을 만들고,
`openmausbot run "Room Lead" "..." --export ./out`으로 봇에게 일을 시켜 결과를
내보낸다.
MCP 서버도 stdio로 제공하며, README는 승인 권한 부여, 삭제, 임의 설정, 자격
증명, 컴퓨터 수명주기는 노출하지 않는다고 밝힌다.

승인 단계는 다섯 가지다.

| 단계                   | 동작                                                          |
| ---------------------- | ------------------------------------------------------------- |
| Ask for approval       | 명령과 파일 변경마다 승인을 요청한다                          |
| Auto-accept edits      | 파일 편집은 자동 승인하고 나머지는 요청할 수 있다             |
| Approve for me         | 제공자의 자동 검토로 일상 작업을 승인하고 나머지는 묻는다     |
| Full access            | 제공자의 가장 관대한 모드를 켜고 남은 승인 요청에 대신 답한다 |
| Custom (`config.toml`) | Codex 전용이며 Codex 설정의 승인 및 샌드박스 값을 따른다      |

## 요금과 사업 구조

홈페이지의 소개 문구는 24시간 일하는 팀을 얻으라는 것이고,
앱은 무료이며 Apache 2.0 오픈소스라고 한다.
모델 사용료는 따로이며, 사용자가 가진 AI 계정이나 API 키를 쓰고
제공자의 요금과 한도가 적용된다고 홈페이지가 적는다.

노트북을 닫아도 봇이 일하게 하려면 클라우드 플랜이 필요하다.
가격 페이지가 적은 내용은 다음과 같다.

| 플랜    | 월 요금 | 머신            | 클라우드 컴퓨터 사용 | 음성 답변 |
| ------- | ------- | --------------- | -------------------- | --------- |
| Free    | $0      | 사용자의 컴퓨터 | 연결한 제공자 것     | 자기 키로 |
| Starter | $15     | 2 CPU, 2GB      | 월 100시간           | 약 30분   |
| Pro     | $49     | 4 CPU, 4GB      | 월 300시간           | 약 1시간  |
| Max     | $99     | 8 CPU, 8GB      | 월 800시간           | 약 3시간  |

Pro에는 월 $10, Max에는 월 $20의 Claude 크레딧이 들어 있다고 한다.
크레딧을 넘는 모델 사용은 사용자 계정이나 API 키로 제공자가 청구한다.
동시에 일하는 봇 수는 한도가 아니라 봇 하나가 메모리 0.5~1GB를 쓴다는 추정에서
나온 대략의 값이라고 가격 페이지가 각주로 밝힌다.

기업 쪽 요금은 소프트웨어 회사가 고객에게 자기 이름으로 MausBot을 파는
화이트라벨이다.
월 $1,000(워크스페이스 25개, 사용자 100명)부터 $9,000(400개, 1,500명)까지의 플랜이
있고, 12개월 계약과 일회성 설치비 $5,000이 붙는다.
자체 서버에 설치할 때는 사용자당 월 $5, 최소 $1,000이다.
엔터프라이즈 페이지는 코어가 Apache 2.0이며,
라이선스 키가 사업 기능을 켜고 만료되면 오픈소스 에디션으로 돌아간다고 말한다.
이는 `LICENSING.md`가 설명하는 `enterprise/` 구조와 같은 이야기다.

MausBox는 개념 단계의 하드웨어다.
AMD Ryzen AI Max+ 395와 128GB 통합 메모리, 2TB SSD를 넣은 상자에서
오픈 모델과 봇을 집에서 돌린다는 구상이고, 가격은 미정이며 대기 목록을 받는다.
홈페이지는 사용자의 작업 방식을 보고 상자 위에서 작은 컴퓨터 사용 모델을
학습시킨다고 소개하지만, 이는 개념 설명이고 실제 동작은 확인되지 않았다.
이 문서는 앱과 클라우드 플랜을 실행해 보지 않았다.

## 분석

### 승인 단계는 제공자의 권한 모드를 그대로 전달하는 구조다

`server/auto-approve.ts`의 첫 주석은 이 파일의 어느 것도 행동이 안전한지
판정하지 않는다고 말한다.
각 단계는 제공자(Claude, Codex 등)의 고유 권한 모드를 그대로 넘긴 것이고,
이 프로세스에 도착한 요청은 제공자가 사람에게 맡겨 둔 요청이라는 뜻이다.
앱이 자체로 허용하는 것은 Full access, 사용자가 저장한 정확한 명령과 MCP 읽기
도구, Approve for me의 웹 검색, 봇이 자기 파일을 읽는 일뿐이다.

`shared/approval-mode.ts`는 모드 이름을 `ask`, `edits`, `auto`, `full`,
`custom` 다섯 개로 정의한다.
`edits`는 Claude, Grok, Antigravity, Qwen, Gemini 드라이버에서만 제공되고
`custom`은 Codex에서만 제공된다.
README가 말하는 엔진은 세 가지지만 코드의 드라이버 목록은 그보다 넓다.
홈페이지는 모델 제공자로 Claude, Codex, Grok에 더해 Cursor, Kimi, Droid,
Antigravity, OpenCode, Qwen, Hermes, Pi를 나열한다.
이 글은 각 드라이버를 실행해 보지 않았으므로 어느 엔진이 실제로 동작하는지는
확인하지 못했다.

### 밖으로 나가는 행동에는 별도 확인 계층이 있다

`shared/outbound.ts`는 사람이나 외부에 무언가를 보내거나 돈을 움직이는 도구를
아웃바운드(outbound) 행동으로 분류한다.
분류 기준은 도구 이름의 동사다.
`SEND`, `REPLY`, `FORWARD`, `POST`, `PUBLISH`, `TWEET`, `SHARE`, `REFUND`,
`CHARGE`, `PAY`, `TRANSFER` 등이 보내는 동작으로 취급된다.
`CREATE`, `ADD`, `NEW`는 만든 댓글이나 청구서를 누군가 받으므로 보내는 것과
같다고 코드 주석이 설명한다.
Full access보다 낮은 단계에서는 이런 호출이 따로 확인을 받거나, 봇별 일일
허용량(기본 25건)을 쓴다.
`auto-approve.ts`에서 `isOutboundTool`이 참이면 Full access가 아닌 모든 모드에서
자동 승인이 `outbound-guard`로 막힌다.

### 오픈 코어이며 `enterprise/`만 다른 라이선스다

README는 Apache 2.0이 `enterprise/` 폴더를 제외한 전체에 적용된다고 밝힌다.
`LICENSING.md`는 `enterprise/`를 소스 공개 라이선스로 두고, 읽고 빌드하고
개발과 테스트에서 돌리는 것은 자유지만 운영 환경에서 쓰려면 조직용 라이선스
키가 필요하다고 설명한다.
폴더를 지우면 서버가 `{"edition":"oss"}`를 응답하는 오픈소스 에디션이 된다.
기여 방식도 둘로 나뉜다.
`enterprise/` 밖은 Apache 2.0으로 기여하고 DCO나 CLA가 필요 없다.
안쪽은 CLA에 한 번 서명해야 한다.

## 비평

### 마케팅의 승인 카드와 기본값이 어긋난다

가장 강하게 읽으면 이 도구의 안전 주장은 이렇다.
위험한 행동은 모두 사용자가 결정하는 카드가 되므로 봇이 사용자 몰래 일하지
않는다.
README 기능 항목은 봇이 행동하기 전에 묻는다고 소개하고, 셸 명령, 파일 편집,
질문이 카드로 나타난다고 적는다.

그러나 `docs/approval-levels.md`는 모든 봇과 대화가 Full access에서 시작한다고
적는다.
이 문서는 Full access를 각 엔진이 가장 관대한 모드로 도는 것이라 설명하고,
진짜 질문과 빠진 자격 증명만 사용자에게 도달한다고 말한다.
새 봇, 새 스레드, 가져온 팀 파일의 봇 모두 이 기본값을 따른다.
호스팅 회사 워크스페이스만 기본이 Ask다.
따라서 카드 방식의 보호를 기대하는 사람은 첫 사용 때 봇별 승인 단계를 직접
낮춰야 한다.
이 글은 앱을 설치해 실제 기본값이 화면에 어떻게 보이는지는 확인하지 못했다.
설치 직후 새 봇의 승인 단계가 Ask로 표시된다면 이 비평은 성립하지 않는다.

### 평문 키 저장과 원격 접근의 조합은 사용자가 점검해야 한다

README는 API 키를 암호화하지 않고 `config.json`에 `0600` 권한으로 둔다고
적는다.
같은 README는 휴대폰 연결을 위해 관리형 공개 HTTPS 엔드포인트, Tailscale,
직접 구성한 리버스 프록시를 선택지로 준다.
Full access 봇과 평문 키, 원격 접근이 한 기기에 함께 있으면 페어링 코드나
기기가 탈취되는 경우의 피해 범위가 넓어진다.
README는 이 조합의 위험을 논하지 않으며, 이 글도 페어링 방식의 취약성은
검증하지 못했다.
원격 접근은 명시적으로 선택해야 하고 기본은 건너뛰기라는 점은 README가 밝혔다.

### 제품 이름과 비교 문구가 크게 차지한다

README 첫머리는 오픈소스 Grok Bot 대안이라는 문구와 네 개 제품의 대안이라는
문구로 채워져 있다.
저장소에는 크립토 토큰과의 무관함을 알리는 경고도 있다.
이름이 바뀐 이력과 맞물려, 프로젝트의 정체성이 비교 대상 제품에 상당히 기대어
있다.
이 비교 표의 상대 제품 설명은 개발자의 요약이며, 이 글은 상대 제품 쪽 자료를
열어 보지 않았다.

## 인사이트

### 제공자의 권한 모드를 그대로 전달하는 설계는 책임 소재를 분명히 한다

이 도구는 안전 판단을 제공자에게 맡기고, 자신은 그 판단을 중계하며 사용자가
명시적으로 준 권한만 대신 답한다.
여러 엔진을 한 앱에 묶는 도구에서 이 방식은 엔진마다 다른 보호 수준을 앱이
하나의 기준으로 덮어쓰지 않는다는 장점이 있다.
대가는 보호 수준이 엔진에 따라 달라진다는 점이다.
`modelSwitchNeedsAsk`는 엔진을 바꿀 때 지원하지 않는 단계를 Ask로 내리는
장치로, 이 문제를 알고 있다는 증거다.

### 쓰기 전에 확인할 것은 기본 승인 단계와 원격 접근이다

써 보려면 세 가지를 먼저 확인한다.
새로 만든 봇의 승인 단계가 무엇으로 표시되는지, 원격 접근을 켰는지,
그리고 API 키를 평문 파일에 둬도 되는 기기인지다.
민감한 저장소에서는 Full access 대신 Ask로 시작하고, 필요한 명령만 저장한
허용 목록에 올리는 순서가 안전하다.
아웃바운드 가드가 메일과 게시를 막아 주는 것은 Full access가 아닐 때뿐이다.

### 오픈 코어 경계는 운영 조건에서 갈린다

조직에서 쓸 계획이라면 필요한 기능이 `enterprise/FEATURES`의 권한 목록에 있는지
먼저 확인한다.
있다면 운영 환경 사용에 라이선스 키가 필요하다.
없다면 Apache 2.0 범위에서 끝난다.
기능이 코어에서 엔터프라이즈로 옮겨지는 시점이 생기는지는 지켜볼 일이다.
