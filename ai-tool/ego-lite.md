## 소개

CitroLabs가 만든 Chromium 기반 브라우저다.
저장소 README의 첫 문장은 AI 에이전트가 웹 자동화를 돌리기에 가장 빠른
브라우저라는 것이다.
사람은 평소처럼 자기 탭에서 브라우징하고,
Claude Code나 Codex 같은 에이전트는 같은 브라우저 안의 별도 작업 공간(Space)에서
로그인된 사이트를 열어 일한다.
에이전트가 사람의 탭이나 마우스,
키보드 포커스를 가져가지 않는다는 것이 핵심 약속이다.

2026년 11월 9일에 GitHub에서 읽은 저장소의 값은 다음과 같다.
별 22,187개, 포크 1,264개, 열린 이슈 257개이고 주 언어는 JavaScript다.
2026년 4월 16일에 만들어졌고 라이선스는 MIT다.
이 값이 모두 약 일곱 달 사이에 쌓였다.
README는 아홉 개 언어로 제공되며 한국어도 포함되고, 공식 문서도 한국어판이 있다.

이 문서는 홈페이지, README, 공식 문서, 저장소의 개발 문서와 릴리스 노트,
개인정보 처리방침, 일주일 써 본 사용기와 Hacker News 스레드를 읽고
정리한 것이다.
직접 설치하거나 돌려 보지 않았으므로 속도와 성공률, 안정성에 대한 서술은
모두 제품 측이나 사용자의 주장이다.

### 풀려는 문제

에이전트에게 웹 작업을 맡기면 브라우저를 어떻게 다룰지가 곧 문제가 된다.
요즘IT에 2026년 10월 1일 실린 사용기의 필자는 처음에 평소 쓰던 크롬과
에이전트 전용 크로미움을 따로 운영했다.
화면이 부딪히는 문제는 피했지만 두 브라우저의 로그인 상태가 달라서,
크롬에서 로그인한 사이트도 크로미움에서는 다시 로그인해야 했고
한동안 쓰지 않은 서비스는 세션이 풀려 있었다.[^yozm]
에이전트가 로그인 화면에서 멈추면 필자가 크로미움 창을 찾아 인증한 뒤
작업을 이어 달라고 다시 말해야 했다.[^yozm]
탭도 문제였다.
오늘 조사한 페이지와 어제 확인한 관리자 화면이 한 창에 계속 쌓였고,
에이전트가 일을 잘 끝내도 탭 정리는 사람의 몫이었다.[^yozm]
필자는 이를 조사를 한 번 맡길 때마다 브라우저 상태까지 관리해야 하는
새로운 업무가 되었다고 요약한다.[^yozm]

ego lite는 이 두 불편, 곧 로그인 상태가 갈라지는 것과 작업 흔적이 섞이는 것을
브라우저 안에서 풀겠다는 제품이다.
README는 기존 도구를 이렇게 나눈다.
browser-use나 agent-browser 같은 도구는 브라우저로 가는 다리이지 브라우저 자체가
아니어서,
조종할 브라우저가 따로 필요하고
사용자의 브라우저 데이터가 온전히 넘어오는 일이 드물며
연결이 불안정하고 사용자와 에이전트가 통제권을 두고 충돌한다는 것이다.
Atlas나 Comet 같은 AI 브라우저는 내장 에이전트만 브라우저를 조종할 수 있다고
본다.
ego lite는 처음부터 사용자와 사용자가 데려온 어떤 에이전트든 함께 쓰도록
설계했다는 주장이다.

### 구성 요소

제품은 세 층으로 나뉜다.

| 구성 요소        | 하는 일                                                                       | 어디에 있는가                         |
| ---------------- | ----------------------------------------------------------------------------- | ------------------------------------- |
| ego lite 앱      | 수정한 Chromium 위에서 Space와 Snapshot을 제공하는 브라우저                   | 별도로 내려받는 무료 앱               |
| ego-browser      | 에이전트가 브라우저를 부리는 실행기. 내장 Node.js로 스크립트를 한 번에 돌린다 | 앱에 포함, SDK 소스는 저장소          |
| ego-browser 스킬 | 에이전트에게 ego-browser 사용법을 알려 주는 스킬                              | 저장소, 앱이 에이전트 디렉터리에 설치 |

저장소의 라이선스 문단은 이 저장소의 내용이 MIT라고 하면서
ego lite 브라우저는 별도의 무료 다운로드라고 적는다.
저장소에는 스킬, ego-browser SDK, 에이전트 호스트용 플러그인 패키지,
문서가 들어 있고, 브라우저 앱이 구현해야 할 요구 사항은
`docs/` 아래의 문서로 적혀 있다.
그러므로 별 2만 개가 붙은 MIT 저장소는 브라우저의 소스가 아니라
브라우저를 쓰는 쪽의 코드다.

## 핵심 개념

### Space

Space는 에이전트가 작업을 돌리는 별도 작업 공간이다.
공식 문서는 Space가 새 브라우저 창도, 별도 Chrome 프로필도, 헤드리스(headless)
브라우저도 아니고 클라우드 세션도 아니라고 부정형으로 정의한다.[^d-space]
모든 Space가 같은 ego lite 브라우저 프로세스 안에서 돌고,
작업마다 자기 쿠키와 저장소를 가진 격리된 BrowserContext 하나를
받는다.[^d-space]
요즘IT 필자도 같은 설명을 옮기며 Space가 새 창이나 프로필이 아니라
같은 프로세스 안의 작업별 격리 공간이라고 적는다.[^yozm]

공식 문서가 이 방식을 택한 이유로 드는 것은 Chrome의 `user-data-dir`이다.
이 디렉터리는 보통 프로세스 하나에만 잠겨 있어서,
실제 로그인을 여러 에이전트 세션에서 쓰려면 잠금을 두고 다투거나
프로필을 임시 디렉터리에 복사해야 한다는 것이다.[^d-space]
Space는 메인 프로세스를 공유하고
BrowserContext만 따로 받는 방식으로 이를 피한다.
공식 문서의 여섯 개 동시 실행 시험이 이 차이를 수치로 보여 준다.

| 방식                                        | 추가 메모리 | 추가 프로세스 | 동시 시작 시간 |
| ------------------------------------------- | ----------- | ------------- | -------------- |
| 브라우저 인스턴스를 따로 띄우고 프로필 복사 | 약 15GB     | 약 84개       | 약 2.5초       |
| ego lite Space                              | 약 0.9GB    | 약 6개        | 약 0.6초       |

이 시험은 `about:blank`만 여는 것이고,
문서 스스로 정밀한 벤치마크가 아니라 자원 모델을 보여 주기 위한 수치이며
실제 비용은 페이지의 복잡도, 확장, 사이트 스크립트, 동시성에 따라 달라진다고
단서를 붙인다.[^d-space]
메모리는 약 17배, 프로세스는 약 14배 차이가 나는 것으로 읽히지만
빈 페이지에서 잰 값이다.

사용 흐름은 이렇다.
사용자가 에이전트에게 웹 작업을 말하면 에이전트가 ego-browser로 Space를 만들어
대상 사이트를 열고 Snapshot을 읽어 행동한다.
캡차, QR 코드 로그인, 결제 확인처럼 사람이 필요한 단계에서는 에이전트가 멈추고,
사람이 처리한 뒤에 에이전트가 이어 간다.
작업이 끝나도 Space의 탭은 닫히지 않고 남아서 감사(audit)할 수 있다.[^d-space]
화면 오른쪽 위의 Space 버튼으로 관리 패널을 열면 에이전트가 일하는 Space가
파란 빛으로 표시되고, 들어가서
지켜보거나 대신 로그인하거나 넘겨받을 수 있다.[^d-quick]

요즘IT 필자에게 이 마지막 부분이 가장 실용적이었다.
Space의 탭은 작업이 끝난 뒤에도 기본으로 남아 검토할 수 있고,
필요 없으면 작업 공간 전체를 닫고 결과를 확인해야 하면 해당 페이지만 남기면
된다.
탭이 저절로 사라지지는 않지만 작업별로 묶여 있어서
정리할 범위가 분명하다는 평이다.[^yozm]
필자는 에이전트가 일하는 동안 자기 화면과 포커스가 유지된다는 점을 가장 크게
체감했다.[^yozm]

### Snapshot

Snapshot은 에이전트가 페이지를 읽는 텍스트 표현이다.
브라우저의 접근성 트리(accessibility tree)에서 만들며,
버튼과 입력란과 링크 같은 조작 대상마다 `@3` 같은 임시 번호를
붙인다.[^d-snapshot]
로그인 페이지의 Snapshot은 이런 모양이다.

```text
Page: Example - Log in
URL: https://example.com/login
@1 [heading] "Log in"
@2 [form]
  @3 [input type="email"] placeholder="Email"
  @4 [input type="password"] placeholder="Password"
  @5 [button type="submit"] "Continue"
  @6 [link] "Forgot password?"
```

에이전트는 `fill('@3', '...')`나 `click('@5')`처럼 번호로 직접 조작한다.
공식 문서는 일반적인 페이지가 200에서 400 토큰이고,
관리자 화면 하나는 원본 HTML로 3만 토큰에 이를 수 있다고
대비한다.[^d-intro][^d-snapshot]
CSS 선택자를 추측하지 않아도 되므로 클래스 이름이 바뀌어도 작업이 깨지지
않는다는 주장이다.[^d-intro]

README가 가장 강하게 내세우는 것은 이 Snapshot을 페이지에 스크립트를 주입하는
방식이 아니라
브라우저 엔진 내부를 수정해서 만든다는 점이다.
그 결과 중첩된 교차 출처(cross-origin) iframe, shadow DOM,
Stripe 결제나 Salesforce, Intercom 패널 같은 제3자 구성 요소도 담는다고
한다.[^d-intro]
같은 문서의 Snapshot 항목은 한계도 적는다.
화면 밖의 내용, 이미지 안의 글자, 복잡한 canvas,
샌드박스된 교차 출처 iframe은 완전하게 나오지 않을 수 있고
그럴 때는 스크린샷이나 텍스트 추출, 사람의 확인을 섞는다고 한다.[^d-snapshot]
번호는 가장 최근 Snapshot에서만 유효해서, 탐색, 폼 제출, 탭 전환,
동적 재렌더링 뒤에는 새로 찍어야 한다.[^d-snapshot]

### ego-browser: 명령이 아니라 코드

ego-browser는 에이전트가 쓰는 실행기다.
Chrome DevTools Protocol로 ego lite 안의 실제 Chromium 세션과 통신하고,
에이전트가 Node.js 스크립트를 heredoc으로 한 번에 넘기면
전체를 한 호출로 실행한다.[^d-cli]
공식 문서가 보여 주는 예는 아래와 같다.

```bash
ego-browser nodejs <<'EOF'
await useOrCreateTaskSpace('follow-ego-agent')
await openOrReuseTab('https://x.com/ego_agent', { wait: true })
await snapshotText()
await click('@92')  // @92 is the Follow button from the snapshot
cliLog('Done.')
EOF
```

이 한 호출이 페이지를 열고, 읽고, 버튼을 누르고, 결과를 보고한다.
다른 도구에서는 이 동작이 각각 호출 하나이고,
모델이 앞 호출의 결과를 읽어야 다음 호출을 보낸다.
호출이 줄면 모델이 돌아가는 횟수가 줄어서 작업이 더 빨리 끝나고
토큰을 덜 쓴다는 것이 논리다.[^d-intro]
공식 문서는 이를 가능하게 하려고 Node.js를 ego lite에 내장했고
설치 크기가 10MB 늘어난다고 적는다.[^d-skills]

스크립트 안에서 쓰는 함수는 import 없이 이름만으로 부를 수 있다.

| 범주            | 함수                                                                            |
| --------------- | ------------------------------------------------------------------------------- |
| Task Space      | `listTaskSpaces`, `useOrCreateTaskSpace`, `completeTaskSpace`, `closeTaskSpace` |
| 탐색과 상태     | `listTabs`, `openOrReuseTab`, `gotoAndWait`, `newTab`, `switchTab`, `pageInfo`  |
| 관찰            | `snapshotText`, `captureScreenshot`, `drainEvents`                              |
| 마우스와 스크롤 | `click`, `doubleClick`, `hover`, `dragMouse`, `scrollBy`, `scrollToBottomUntil` |
| 입력            | `typeText`, `fillInput`, `pressKey`, `dispatchKey`                              |
| 파일과 네트워크 | `uploadFile`, `httpGet`                                                         |
| 대기            | `wait`, `waitForLoad`, `waitForElement`, `waitForNetworkIdle`                   |
| 브라우저 실행   | `js`, `elementEval`, `cdp`                                                      |
| 출력            | `cliLog`, `help`                                                                |

이 표는 공식 문서의 helper 목록을 옮긴 것이다.[^d-cli]
`js()`는 내부적으로 `Runtime.evaluate`이고 문자열을 받는다.
스크립트 본문은 Node.js 프로세스이고 `js(...)` 안은 페이지 안의 컨텍스트여서
둘을 섞으면 안 된다.[^d-cli]
`cdp`로 원시 Chrome DevTools Protocol 명령을 보낼 수도 있어서,
표준 helper로 안 되는 일을 위한 탈출구가 있다.[^d-cli]
Task Space의 이름은 3에서 6단어의 자연어 설명으로 지으라는 규칙이 있다.[^d-cli]

공식 문서는 이 도구가 사람이 손으로 쓰라고 만든 것이 아니고
Playwright나 Puppeteer를 대체하려는 것도 아니며, 독자는 LLM 에이전트라고
분명히 적는다.[^d-cli]
그래서 사용법은 스킬 문서에 있고 사람이 외울 필요가 없다.

HN의 Show HN 글 제목이 바로 이 선택을 다룬다.
Why our browser agent writes JavaScript not CLI commands라는 제목이다.
qddegtya는 왜 JavaScript냐고 물었고,[^qddegtya-js]
braxton4는 저장소를 읽어 보니 브라우저를 잇는 부분이 JS로 쓰여 있고
명령과 도구를 모두 JS 안에 두면 실행이 빨라지니 말이 되지만
벤치마크를 읽지 못해서 확신은 못 한다고 답했다.[^braxton4-js]
qddegtya는 Python이나 Rust 같은 AI 친화적 언어가 많고
Python 바인딩으로 만든 CDP 기반 프레임워크도 잘 돌아가니
JavaScript만이 답은 아니라고 되받았다.[^qddegtya-alt]
공식 문서에는 이 질문에 대한 직접적인 답이 없다.
읽은 문서에서 확인되는 것은 스크립트가 Node.js이고
페이지 안의 평가가 JavaScript라는 구조까지다.

### 스킬이 두 층인 이유

저장소의 개발 문서에 따르면 ego-browser 스킬은 두 층이다.
하나는 저장소의 `skills/ego-browser/`에 있는 진입 스킬로,
에이전트에게 `ego-browser skill`을 실행하라고만 알려 주고 설치 안내를 담는다.
다른 하나는 SDK와 같은 버전으로 관리되고
`ego-browser skill` 명령이 출력하는 사용 가이드다.[^gh-skill]
이렇게 나눈 이유는 에이전트가 항상 설치된 브라우저와 같은 버전의 가이드를 읽게
하려는 것이다.
빌드가 운영체제별로 가이드를 따로 만들어서 macOS 판에는 PowerShell 절이 없고
Windows 판에는 Bash와 PowerShell 절이 모두 있다.[^gh-skill]

앱은 실행할 때마다 `~/.agents/skills/ego-browser`를 살핀다.
없으면 진입 스킬을 복사하고, 이전 방식으로 앱이 만든 심볼릭 링크는 복사본으로
바꾸고,
사용자나 패키지 관리자가 설치한 것은 건드리지 않는다.[^gh-skill]
이 구조는 에이전트가 낡은 사용 가이드로 새 브라우저를 부리는 사고를 줄이려는
설계로 보인다.
v2.2.0 릴리스 노트에도 스킬을 진입 스킬과 버전이 있는 사용 가이드로 나눈 항목이
있다.[^rel-220]

### 경험 축적과 로드맵

경험 축적(Experience accumulation)은 성공한 동작을 사이트별로 재사용 가능한
도구나 워크플로로 저장해 다음 작업에서 시행착오를 줄이겠다는 기능이다.[^d-intro]
README는 비슷한 작업이 최대 5배 빨라진다고 하지만 아직 출시 전이라고 표시한다.
공식 문서의 Skills 페이지도 이 기능이 제한적 베타이고 이후 릴리스에서 제공된다고
적는다.[^d-skills]

로드맵 페이지는 진행 중인 항목으로 재사용 가능한 스킬,
어떤 하니스(harness) 에이전트든 호스팅하는 브라우저 ACP,
에이전트에게 주는 브라우저 제어 도구의 추가 강화를 든다.
계획된 항목은 Electron과 네이티브 애플리케이션 조작, Linux 지원이다.
완료된 항목은 세로 탭, Windows 지원, 다듬은 Space 상호작용이다.[^roadmap]

## 설치와 첫 작업

### 설치 경로

README는 설치 경로를 셋으로 소개한다.
macOS용 `.dmg`(Apple Silicon과 Intel)나 Windows용 `.exe`를 내려받는 방법,
스킬만 먼저 넣고 첫 작업 때 앱 설치를 안내받는 방법,
에이전트에게 설치를 시키는 방법이다.

```bash
npx skills add citrolabs/ego-lite
```

지원 환경은 README가 macOS와 Windows라고 하고 Linux는 로드맵에 있다고 한다.
요즘IT 사용기는 10월 1일에 macOS 전용이라 Windows에서는 쓸 수 없다고
적었다.[^yozm]
이후 10월 16일의 v2.1.0 릴리스 노트에 Windows에서 클립보드 붙여넣기를 지원하고
PowerShell과 cmd용 스크립트 호출 형식을 문서화한 항목이 보이고,[^rel-210]
Windows 빠른 시작 문서의 내려받기 버튼에는 베타(beta)가 붙어 있다.[^d-win]
같은 공식 문서의 What is ego(lite) 페이지는 여전히 macOS용이고
Windows와 Linux 버전은 계획 중이라고 적어서 문서끼리 어긋난다.[^d-intro]
Windows를 쓰려는 사람은 베타라는 표시를 기준으로 삼는 것이 안전하다.

### 첫 실행에서 일어나는 일

공식 빠른 시작 문서에 따르면 첫 실행에서
ego lite는 기계에 설치된 에이전트를 찾아서
`ego-browser` 스킬을 `~/.agents/skills`와 `~/.claude/skills/`에 써
넣는다.[^d-quick]
다른 브라우저의 데이터를 가져올지도 묻는다.
가져오기를 선택하면 세션, 북마크, 비밀번호, 확장이 함께 넘어온다.[^d-quick]
이 과정에서 macOS가 키체인 비밀번호를 묻고 같은 창이 여러 번 뜰 수 있으며
그때마다 입력해야 로그인 상태와 쿠키와 확장과 Chrome 프로필을 가져올 수 있다고
한다.[^d-quick]
브라우저 데이터는 컴퓨터에 남고
사용자의 통제 아래 있다는 것이 문서의 설명이다.[^d-quick]
계정이나 이메일 주소가 없어도 쓸 수 있다.[^d-intro]

### 에이전트별 권한 설정

도입을 따져 볼 때 가장 먼저 걸리는 부분이 이 대목이다.
공식 가이드는 에이전트의 권한을 크게 풀라고 안내한다.

- Codex는 Full access로 설정하라고 한다. ego-browser 명령이 앱을 실행해야 하고, ego lite는 로컬 기계에 설치된 앱이라 샌드박스 밖에서 앱을 실행할 권한이 필요하기 때문이다.[^d-quick]
- Claude Code는 Bypass permissions를 켜라고 한다. 터미널에서는 `claude --dangerously-skip-permissions`로 시작하고, 문서는 Bypass permissions가 꺼져 있으면 ego lite를 정상적으로 제어할 수 없다고 적는다.[^d-claude]
- 이 옵션이 목록에 없으면 설정에서 허용 항목을 켜야 하고, 팀이나 기업 정책이 옵션을 숨길 수 있다고 한다.[^d-claude]

Claude Code 가이드에는 함정도 하나 적혀 있다.
Claude 데스크톱 앱의 Cowork 모드에는 `/ego-browser`가 나타나지 않고
Code 모드로 바꿔야 스킬이 보인다는 것이다.[^d-claude]
스킬이 `~/.claude/skills/`에 설치되기 때문이며, 설치 실패로 오해하기 쉽다고
한다.[^d-claude]
공식 Skills 문서는 안전 관련 주의도 한 줄 단다.
ego lite는 에이전트에게 페이지 내용을 읽고
행동하는 실제 브라우저 제어권을 주므로
믿을 수 있는 출처의 에이전트를 쓰라는 것이다.[^d-skills]

### 작업을 맡기는 요령

공식 문서와 사용기가 같은 방향의 요령을 준다.
공식 Snapshot 문서는 좋은 작업 설명이 대상 페이지,
읽거나 채우거나 누르거나 내려받을 것,
하지 말아야 할 일(삭제, 게시, 결제, 메일 발송 등),
캡차나 결제나 권한 승인 화면에서 멈출지 여부, 원하는 결과의 모양을 알려 준다고
한다.[^d-snapshot]
요즘IT 필자가 일주일 동안 다듬은 방식이 이 항목들과 거의 겹친다.

- 작업의 끝을 먼저 정한다. 예전에는 이 주제를 조사해 달라고만 했지만 지금은 출처와 요약을 정리하고 확인할 페이지만 남기고 나머지 탭은 닫아 달라고 함께 요청한다.[^yozm]
- 결과물의 형태(표, 링크가 있는 요약, 화면 캡처)와 작업 뒤에 남길 탭을 요청에 적는다. 이렇게 하면 브라우저 탭이 결과물의 대체물이 되지 않고, 정보는 글이나 표로 받고 브라우저에는 사람이 확인할 화면만 남는다.[^yozm]
- 작업 공간 이름을 경쟁 서비스 가격 확인처럼 목적이 드러나게 짓고, 후속 확인은 기존 공간을 다시 쓰며 전혀 다른 일은 새 공간에서 시작한다. 공식 문서가 Task Space 이름을 3에서 6단어의 설명으로 지으라고 하는 것과 맞는다.[^yozm][^d-cli]
- 조회와 변경을 나눈다. 조회가 목적이면 내용만 확인하고 수정하거나 제출하지 말라고 적고, 설정 변경이나 게시처럼 결과가 남는 작업은 사람이 마지막 단계에서 확인한다.[^yozm]
- 읽기 전용인지, 입력은 하되 제출 전에 멈출지, 변경까지 허용할지를 미리 정한다. 공식 문서도 읽기 전용이나 제출 전 중지 같은 경계를 먼저 그을 수 있다고 안내한다.[^yozm][^d-space]

사람이 개입하는 순간도 정해져 있다.
공식 문서는 SMS나 이메일 코드, QR 코드 로그인, 하드웨어 보안 키,
결제와 주문, 송금과 환불, 게시와 삭제와 되돌리기 어려운 대량 수정,
제3자 앱에 계정 접근을 허가하는 단계에서 에이전트가 멈추고
제어권을 넘겨야 한다고 안내한다.[^d-space]
요즘IT 필자는 이를 에이전트가 실패했을 때의 예외 처리라기보다 역할을 나누는
방법으로 본다.
반복적인 탐색과 확인은 에이전트가,
보안 절차와 최종 판단은 사람이 맡는다는 것이다.[^yozm]
이 멈춤이 에이전트의 판단에 달린 약속일 뿐 브라우저가 강제하는 장치인지는
읽은 문서에서 확인되지 않는다.

## 무엇에 쓰는가

공식 빠른 시작 문서는 쓰임새를 여섯 갈래로 든다.[^d-quick]

- 소셜 미디어: 트윗에 답하거나 인용하고, 게시물을 쓰고 예약하고, 반응 수치를 긁고, 멘션을 모니터링한다. Twitter, LinkedIn, Threads, Reddit, Instagram, Facebook을 지원한다고 한다.
- 구직과 채용: LinkedIn, Wellfound 등에서 공고를 찾고 지원서를 채우되 최종 제출 직전에 멈춘다.
- 부동산, 금융, 쇼핑: Redfin이나 Zillow에서 조건에 맞는 매물을 거르고 대출 계산기를 돌려 결과를 로컬 Markdown 파일에 쓴다.
- 예약: 항공, 숙소, 식당 예약 양식을 실제 개인정보로 채우되 결제 페이지에서 멈춘다.
- SaaS 관리 화면: HubSpot, Salesforce, Notion, Airtable, Linear, Stripe, GA4 같은 곳에서 보고서를 뽑고 필드를 일괄 수정한다.
- 내부 도구: 로그인 뒤에 있어서 다른 자동화 프레임워크가 못 들어가는 관리자 패널, 스테이징 환경, QA 흐름을 다룬다.

홈페이지는 이를 직무별 여섯 개로 다시 나눈다.
코딩은 로그인된 브라우저로 테스트해서
셀렉터와 로그인 스크립트를 유지하지 않는 것이고,
영업은 Sales Navigator나 Salesforce처럼 내보내기를 막거나 유료로 파는 곳에서
화면에 보이는 리드를 에이전트가 읽는 것이다.
마케팅은 로그인 뒤 소셜 미디어 100개 탭을 훑는 경쟁사 조사,
재무는 월말에 Stripe, Shopify, 은행 등에서
인보이스를 모아 입금과 주문을 맞추는 일이고
승인과 결제는 사람이 한다고 적는다.
법무는 PACER 같은 판례 사이트에 로그인해 PDF를 하나씩 읽는 일을,
리서치는 Notion, Confluence, 대학 내부 사이트처럼 로그인 뒤에 있는 자료를
출처와 함께 읽는 일을 든다.

HN에서 imJack은 아주 틈새일 수 있다면서
웹 게임에 브라우저 에이전트를 쓰는 것을 좋아한다고 적었다.
에이전트가 조종하는 세션을 동시에 여러 개 돌릴 수 있으면 멀티박싱(multiboxing)이
힘든 일에서 한 번의 클릭으로 바뀐다는 것이다.
생산성은 오르지 않아도 게임 진행은 확실히 오를 것이라고 덧붙였다.[^imjack]
이 쓰임새는 제품 소개에는 없지만
Space가 동시에 여러 작업을 돌린다는 구조를 정확히 쓴 예다.

사용자 쪽에서 가장 현실적인 신호는 요즘IT 필자의 판단이다.
로그인 없이 공개 페이지 하나를 잠깐 찾는 일은 익숙한 브라우저나 검색으로
충분하고,
로그인된 여러 사이트를 오가거나 조사하는 동안 다른 일을 계속해야 하거나
작업마다 탭을 분리해 관리하고 싶을 때 더 유용했다고 한다.[^yozm]
공식 Space 문서도 공개 자료만 찾는 일에는 일반 웹 검색이 더 가볍다고
적는다.[^d-space]
도구를 바꾸는 데도 적응 비용이 있으니
반복되는 불편이 있는 작업부터 옮기라는 조언이 붙는다.[^yozm]

## 경쟁 제품과의 비교

README의 비교표는 개별 제품이 아니라 다섯 범주를 열로 세운다.
범주 안의 예시는 확장 프로그램에 Claude와 Codex in Chrome,
내장 브라우저에 Claude와 ChatGPT의 내장 브라우저,
클라우드 브라우저에 Browserbase와 Browser Use,
브라우저 CLI에 playwright-cli와 Browser Harness, AI 브라우저에 Comet과 Dia다.

| 능력                        | ego lite | 확장 프로그램 | 내장 브라우저 | 클라우드 브라우저 | 브라우저 CLI | AI 브라우저 |
| --------------------------- | -------- | ------------- | ------------- | ----------------- | ------------ | ----------- |
| 어떤 AI 에이전트와도 작동   | ✓        | —             | —             | ✓                 | ✓            | —           |
| 내 브라우저 로그인 사용     | ✓        | ✓             | —             | —                 | —            | ✓           |
| 캡차가 적음                 | ✓        | ✓             | —             | —                 | —            | ✓           |
| 컴퓨터 전체에서 작동        | ✓        | —             | ✓             | —                 | ✓            | —           |
| 내 브라우저를 가로채지 않음 | ✓        | —             | ✓             | ✓                 | —            | —           |
| 병렬 멀티태스킹             | ✓        | —             | —             | ✓                 | —            | —           |
| 대규모 수집 작업            | ✓        | —             | —             | ✓                 | ✓            | —           |
| 일상용 브라우저             | ✓        | ✓             | —             | —                 | —            | ✓           |
| 무료                        | ✓        | —             | —             | —                 | ✓            | —           |
| 데이터 로컬 저장            | ✓        | ✓             | ✓             | —                 | ✓            | —           |
| 재사용 스킬(곧 제공)        | ✓        | —             | —             | —                 | —            | —           |

공식 문서는 이 범주마다 ego lite가 더 낫다고 주장하는 이유를 쓴다.[^d-intro]
확장 프로그램은 짝짓기가 끊기거나 권한 창이 뜨거나 다른 확장과 충돌할 수 있는데
ego lite는 브라우저 자체라서 그런 단계가 없고, 확장은 사용자와 같은 창에서
일해서
에이전트가 사용자의 탭이나 포커스를 쓸 수 있다는 것이다.
클라우드 브라우저는 내 계정을 쓰려면 비밀번호나 쿠키,
로그인된 세션을 공급자에게 줘야 하고
세션이나 분 단위로 과금하며 공급자의 IP 주소 때문에 캡차가 늘 수 있다는 것이다.
내장 브라우저는 앱 하나 안에서만 쓸 수 있고 로그인 상태가 따로이며
기능이 적다는 것이다.
브라우저 CLI는 기본적으로 빈 프로필로 시작하고 한 단계씩 진행하며
헤드리스로 돌아 사람이 볼 수 없다는 것이다.
AI 브라우저는 회사의 AI 비서만 쓸 수 있고 로컬 파일이나 저장소에 접근하지 못하며
페이지를 그 회사의 AI 서비스에 보낸다는 것이다.

문서는 반대편의 장점도 인정한다.
클라우드 브라우저는 서버에서 100개 이상을 동시에 돌리는 제품이나 컴퓨터가 꺼진
동안 계속 돌아야 하는 작업에 맞고,
브라우저 CLI는 스크립트나 CI에서 매번 새 브라우저가 필요할 때 잘 맞는다고
적는다.[^d-intro]
그러므로 표의 ✓와 —는 서로 다른 용도 사이의 우열이 아니라
로그인된 개인 작업에서 ego lite가 맞는 정도를 보인 것에 가깝다.

공식 문서는 캡차를 건드리지 않는다고도 분명히 적는다.
캡차가 적은 것은 사용자 자신의 인터넷 연결과 VPN과 프록시 설정을 따르기 때문이고
사이트가 캡차나 보안 확인을 요구할 수는 있으며
ego lite는 이를 우회하지 않는다는 것이다.[^d-intro]

## 벤치마크

홈페이지와 README는 같은 시험을 내놓는다.
Real-World Bench라는 이름의 시험으로, 실제 웹사이트에서
도는 복잡한 브라우저 자동화 과제 31개를
ego-browser와 네 도구가 풀었다.
README는 모든 도구가 같은 에이전트(pi)와 같은 모델(gpt-5.6-sol,
thinking effort max)로 돌았고
같은 심사자가 과제별 채점 기준(rubric)으로 채점했으며,
모든 요구 사항을 채워야 완전 성공으로 센다고 적는다.
달러 금액은 1달러당 1,361.4원으로 환산해 함께 적었다.[^fx]

| 항목                            | ego-browser          | chrome-devtools-cli  | agent-browser        | browser-harness      | playwright-cli       |
| ------------------------------- | -------------------- | -------------------- | -------------------- | -------------------- | -------------------- |
| 작업당 평균 시간(낮을수록 좋다) | 398초                | 587초                | 605초                | 615초                | 648초                |
| 완전 성공률(높을수록 좋다)      | 93.50%               | 61.30%               | 62.90%               | 77.40%               | 71.00%               |
| 작업당 평균 비용(낮을수록 좋다) | 1.64달러(약 2,200원) | 4.95달러(약 6,700원) | 2.66달러(약 3,600원) | 2.43달러(약 3,300원) | 3.42달러(약 4,700원) |

속도는 다른 도구보다 47%에서 63% 빠르다고 표현한다.
587초에서 398초는 속도로 1.47배, 648초에서
398초는 1.63배이므로 이 표현은 속도 비율에서 1을 뺀 값이다.
같은 값을 시간 단축으로 읽으면 각각 약 32%와 39%다.
비용은 가장 가까운 browser-harness(2.43달러)와 비교하면 약 33% 낮고
chrome-devtools-cli(4.95달러)와 비교하면 약 67% 낮다.
성공률은 두 번째로 높은 browser-harness보다 16.1퍼센트포인트 높다.

공식 Skills 페이지는 같은 작업이 내부 벤치마크에서 20에서 50% 빨라진다고
적는다.[^d-skills]
이 수치는 홈페이지의 47에서 63%와 다르다.
저장소의 v2.2.0 릴리스 노트에 README의 벤치마크와 비교표를 홈페이지에 맞췄다는
항목이 있는 것으로 보아,
같은 시험의 최신 수치는 홈페이지와 README이고
Skills 페이지는 이전 수치로 보인다.[^rel-220]

## 데이터가 지나가는 길

공식 문서의 개인정보 항목은 이렇게 요약된다.
Chrome에서 가져온 비밀번호, 쿠키, 방문 기록, 북마크, 확장,
프로필은 컴퓨터에 저장된다.
에이전트가 페이지에서 일하면 에이전트가 페이지 내용을 읽어 자기가 쓰는 모델로
보낸다.
ego lite는 브라우저를 돌리고 브라우저와 에이전트 사이에서
명령과 결과를 전달할 뿐이다.[^d-intro]
모델은 사용자가 고르므로 컴퓨터에서 돌아가는 로컬 모델도 될 수 있다.[^d-intro]
공식 문서에는 Ollama와 OpenCode로 로컬 모델을 연결하는 가이드가 있다.[^d-quick]

개인정보 처리방침(2026년 10월 29일 개정)은 더 구체적이다.[^privacy]

- 외부 AI 도구에 연결하면 브라우저가 웹페이지 내용이나 작업 결과를 기기에서 그 도구로 직접 준다. 이 내용에 개인정보가 들어 있을 수 있다.
- 방침의 `Help improve ... features and performance` 항목이 꺼져 있으면 일반적인 인터페이스 동작에서 이 내용을 Citro도 서비스 제공자도 받지 않는다고 한다.
- 외부 AI 도구는 브라우저 인터페이스로 저장된 비밀번호, 인증 쿠키, 세션 토큰을 읽거나 내보낼 수 없다고 한다. 다만 로그인된 세션으로 웹페이지에 접근할 수 있어서 그 페이지에 든 개인정보와 민감 정보를 가져갈 수 있다고 분명히 적는다.
- `Make searches and browsing better`를 켜면 방문한 페이지의 URL과 관련 사용 정보를, `Improve search suggestions`를 켜면 주소창에 입력한 내용과 IP 주소를 기본 검색 엔진으로 보낸다. 설정에서 끌 수 있다.
- 방침의 적용 범위는 데스크톱과 모바일 AI 브라우저 앱, 브라우저 확장, 웹사이트, 클라우드 AI 에이전트 서비스까지 넓고, 계정을 등록할 때 사용자 이름, 이메일 주소, 전화번호를 모은다고 적는다.

이 문서가 읽은 범위에서 확인되지 않는 것이 두 가지 있다.
앞의 개선 항목이 기본으로 켜져 있는지 꺼져 있는지,
그리고 계정 없이 쓸 수 있다는 공식 문서와 계정 등록 시 수집을 적은 방침이 어떻게
이어지는지다.

## 개발 속도와 로드맵

저장소의 릴리스 날짜가 이 제품의 속도를 보여 준다.
v1.2.3이 2026년 8월 11일, v2.0.0이 9월 10일, v2.1.0이 10월 16일,
v2.2.0이 11월 5일이다.
석 달 사이에 메이저 버전을 한 번 올리고 마이너 버전을 두 번 냈다.

릴리스 노트에 쌓인 항목의 종류도 읽을 만하다.
v2.0.0에는 iframe Snapshot과 Page 참조(ref) 정체성을 보존하는 수정,
iframe 생명 주기 재시도, 다운로드 API 추가가 들어 있다.[^rel-200]
v2.1.0에는 아홉 개 에이전트 호스트용 플러그인 패키지,
Windows 키보드 붙여넣기 지원, JavaScript 대화상자가 열려 있을 때 모든 렌더러
명령이 빨리 실패하게 하는 수정이 있다.[^rel-210]
v2.2.0에는 클릭 가능 여부 확인을 한 번의 주입 호출로 합친 성능 개선,
고정된 안정화 대기 시간을 빼고 유휴 페이지에서 빨리 실패하게 한 변경,
응답 없는 Page를 이름과 함께 알리는 수정,
문서 커밋 도중에 걸친 Snapshot 재시도,
커밋되지 않은 탐색을 시간 초과로 멈추는 수정이 있다.[^rel-220]

이 목록은 두 가지로 읽힌다.
하나는 약속한 기능, 곧 iframe 처리와 속도가 실제로 계속 다듬어지고
있다는 점이다.
다른 하나는 브라우저 자동화가 부딪히는 현실적인 실패 유형,
곧 응답하지 않는 페이지, 문서 전환 중의 Snapshot, 열린 대화상자, 막힌 요청이
아직 한 건씩 고쳐지는 단계라는 점이다.
v2.2.0에는 에이전트에게 작업 공간 반납을 상기시키는 변경이 들어갔다가 되돌려진
항목도 있다.[^rel-220]
성숙한 기능을 쓴다는 기대보다는 빠르게 움직이는 제품을 쓴다는 기대가 맞다.
요즘IT 필자도 이름처럼 아직 lite 버전이라 완성 단계의 도구는 아니고
기능이나 사용 방식이 바뀔 가능성이 있다고 적었다.[^yozm]

## 분석

### 문제를 자동화가 아니라 소유권으로 정의했다

이 프로젝트의 출발점은 브라우저를 어떻게 조종하느냐가 아니다.
브라우저를 누가 쓰고 있느냐다.

README가 기존 도구를 비판하는 지점이 전부 그 축에 놓여 있다.
조종할 브라우저가 따로 필요하다는 것, 로그인이 넘어오지 않는다는 것,
그리고 사용자와 에이전트가 통제권을 두고 충돌한다는 것이다.
마지막 항목이 핵심이고, Space라는 개념이 그 하나를 겨냥해 만들어졌다.
요즘IT 필자의 경험이 이를 뒷받침한다.
브라우저를 둘로 나눠 소유권을 분리했는데도 로그인과 탭이라는 관리 비용이
남았다.[^yozm]

이 재정의가 경쟁 상대도 바꾼다.
자동화 능력으로 비교하면 browser-use와 Playwright 계열이 상대이지만,
소유권으로 비교하면 상대가 확장 프로그램과 AI 브라우저가 된다.
README의 비교표가 다섯 범주를 한 표에 놓은 이유도 그것이다.
그리고 그 표에서 ego lite만 모든 칸에 표시가 있는 이유는
표의 항목들이 이 제품의 설계 결정에서 역산되었기 때문이기도 하다.

### 코드 단위 인터페이스가 줄이는 것은 모델 왕복이다

이 제품의 성능 주장은 브라우저가 빨라졌다는 것이 아니라 왕복이 줄었다는 것이다.
도구를 CLI 명령으로 노출하면 에이전트는 한 번에 한두 개를 호출하고
결과를 본 뒤 다음을 호출한다.
JavaScript 함수로 노출하면 여러 단계를 한 조각에 담아 한 번에 실행할 수 있다.

HN에서 braxton4가 이 차이를 사용자 입장에서 확인해 준다.
agent-browser를 쓸 때 명령이 하나씩 실행되는 것을 지켜봐야 해서
정말 비효율적이었고,
JS 코드로 모든 명령을 한 번에 실행하는 것이 영리하다고 적었다.[^braxton4]

여기서 절약되는 것은 브라우저 시간이 아니라 모델 왕복이다.
각 왕복마다 페이지 상태를 다시 읽어 컨텍스트에 넣어야 하므로 토큰이 들고,
모델 호출 지연이 붙는다.
그래서 작업이 복잡할수록 격차가 커진다는 설명이 구조적으로 맞다.
단계가 많을수록 합쳐지는 왕복도 많아지기 때문이다.

Snapshot이 작아지는 것도 같은 방향의 효과다.
한 번 읽는 페이지가 수백 토큰이면 왕복이 남아 있어도 한 번의 비용이 작다.
왕복 횟수와 한 번의 크기를 둘 다 줄이는 설계라서
두 효과가 곱해진다고 보는 것이 제품 측의 논리다.
다만 이 두 요인이 벤치마크 격차에 각각 얼마나 기여하는지는 어느 문서에도
분해되어 있지 않다.

같은 방향의 설계가 최근 여러 곳에서 나타난다.
이 저장소에 정리된 Stagehand v4도 확장 프로그램을 브라우저 안에 넣어 왕복 지연을
줄였고,
그쪽 역시 속도와 토큰 효율을 함께 내세웠다.
브라우저 자동화의 경쟁 축이 기능에서 왕복 횟수로 옮겨 가고 있다는 신호다.

### 로그인 상속이 이 제품의 진짜 판매 포인트다

기술적으로 가장 어려운 부분은 Space 격리일 수 있지만,
사용자가 실제로 반응하는 지점은 로그인이 이어지는 것이다.

HN에서 haruharuha가 Space 개념이 바로 자기가 원하던 것이라면서
든 이유가 정확히 그것이다.
에이전트가 독립된 공간을 갖되 여전히 자기 자격 증명을 들고 있다는 점이며,
Arc에서 이어진 브라우저들이 워크스페이스 개념을 일찍부터 다뤘으면서도
이 방향으로 가지 않은 것이 놓친 기회라고 적었다.[^haruharuha]
요즘IT 필자도 일주일 동안 가장 편하다고 느낀 지점으로 이 부분을 꼽았다.
기존에는 로그인 페이지에서 작업이 멈출 때마다 직접 인증한 뒤 다시 맡겼는데,
옮긴 뒤에는 브라우저를 준비하는 과정이 눈에 띄게 줄었다는 것이다.[^yozm]

이 지적이 시사하는 바가 있다.
에이전트에게 웹을 시키는 일에서 가장 큰 마찰은 자동화 능력이 아니라 인증이다.
API가 없거나 부족한 서비스, 로그인 뒤에만 있는 데이터,
2단계 인증이 걸린 계정이 전부 그 벽이고,
사람이 이미 통과해 둔 세션을 그대로 쓰는 것이 유일하게 값싼 해법이다.

그런데 이 부분에는 문서가 설명하지 않는 구석이 있다.
Space 문서는 Space가 작업마다 자기 쿠키와 저장소를 가진 격리된
BrowserContext라고 하면서,
이미 로그인한 사이트라면 에이전트가 보통 로그인 뒤 페이지로 바로 간다고 하고
쿠키를 다시 옮길 필요가 없다고 한다.[^d-space]
요즘IT 필자도 같은 두 문장을 이어서 적는다.[^yozm]
자기 쿠키 저장소를 가진 컨텍스트가 어떻게 사용자의 로그인 상태를 받는지,
복사인지 공유인지, 한쪽에서 로그아웃하면 다른 쪽에 어떻게 되는지는
읽은 문서 어디에도 설명이 없다.
이 구조는 격리가 실제로 무엇을 막아 주는지를 정하는 것이어서 아래 비평에서
다시 다룬다.

### 사람이 필요한 순간을 설계에 넣었다

캡차, QR 코드, 결제 확인에서 에이전트가 멈추고
사람이 넘겨받는 흐름이 제품의 기본 사용 방식으로 적혀 있다.
대개의 자동화 도구는 이런 지점을 실패로 취급하는데,
여기서는 Space를 열어 사람이 직접 처리하고
에이전트가 이어 가는 것이 정상 경로다.
요즘IT 필자는 사람과 에이전트가 한 브라우저를 함께 쓴다는 설명이
이 과정에서 비로소 이해가 쉬웠다고 적는다.[^yozm]
이 설계가 사용자 입장의 안전장치이자 가장 현실적인 인증 해법이다.
2단계 인증이나 하드웨어 키를 에이전트가 풀 수는 없기 때문에,
제어권을 사람에게 돌리는 경로가 없으면 로그인 상속은 절반만 작동한다.

## 비평

### 비교표가 제품의 설계에서 역산되어 있다

열한 개 항목 중 ego lite가 모든 칸에 표시를 받고
나머지가 부분적으로만 받는 구조는
비교표가 공정한 축으로 만들어졌을 때 나오기 어려운 모양이다.

항목을 뜯어 보면 그 이유가 보인다.
병렬 멀티태스킹, 내 브라우저를 가로채지 않음, 재사용 가능한 스킬은
전부 이 제품이 선택한 구조를 그대로 항목으로 옮긴 것이다.
반대로 다른 제품들이 강한 축, 예컨대 헤드리스 운용이나 CI 통합,
서버에서의 대규모 병렬 실행, 언어 바인딩의 폭은 표에 없다.

브라우저 CLI가 라이브러리 형태인 이유는
사람이 보지 않는 곳에서 돌리기 위해서다.
일상용 브라우저라는 항목에 표시가 없는 것은 결함이 아니라 다른 용도라는 뜻인데,
표의 형식은 그것을 부족으로 읽게 만든다.
재사용 스킬 항목에는 곧 제공이라는 단서가 붙어 있지만
다른 범주에는 아직 출시 전인 기능이 이미 있는 것으로 비교할 수 없다는 점이 표에
드러나지 않는다.

### 벤치마크의 조건은 공개되었지만 반복 횟수가 빠져 있다

README는 과제 수(31개), 에이전트(pi), 모델(gpt-5.6-sol,
thinking effort max),
심사자와 채점 방식, 완전 성공의 정의까지 적었다.
제품 측이 직접 돌린 벤치마크로서는 갖출 조건을 대체로 밝힌 셈이다.
그래도 남는 질문이 있다.

첫째, 반복 횟수와 분산이 없다.
성공률 다섯 개를 보면 흥미로운 점이 있다.
93.5%, 61.3%, 77.4%, 71.0%는 31개 과제 중 29, 19, 24, 22개와 맞는다.
그런데 62.9%는 31로 나눈 값 중에 없다.
62회 실행, 곧 과제당 2회라면 다섯 값이 모두 맞는다(58, 38, 39, 48, 44회 성공).
이것은 이 문서의 추론이고 문서에는 반복 횟수가 적혀 있지 않다.
2회 반복이라면 한 번의 우연이 성공률에서 1.6퍼센트포인트를 움직이는 표본이고,
도구 사이의 일부 차이(예컨대 agent-browser 62.9%와 chrome-devtools-cli 61.3%)는
오차 안에 들 수 있다.

둘째, 모든 도구가 한 에이전트와 한 모델로만 시험되었다.
브라우저 CLI는 에이전트가 쓰는 방식에 민감하다.
ego-browser는 스킬 문서를 통해 코드로 부리도록 설계되었으므로
그 방식에 맞춘 에이전트 설정이 다른 도구에는 불리했을 수도 있고,
반대로 다른 도구의 최적 사용법이 시험에 반영되지 않았을 수도 있다.
이 문서가 읽은 범위에서는 이 질문에 답이 없었다.

셋째, 시험을 한 쪽이 제품을 만든 회사다.
README는 우리가 돌렸다고 적고,
공개된 과제 목록이나 재현 방법이 이 문서가 읽은 범위에 없었다.

넷째, 수치가 이 저장소 안에서도 일관되지 않다.
홈페이지와 README는 47에서 63%를, 공식 Skills 페이지는 20에서 50%를 말한다.
어느 쪽이 최신인지는 릴리스 노트로 짐작할 뿐이다.

비교 대상의 구성도 눈여겨볼 만하다.
시험에 들어간 도구는 chrome-devtools-cli, agent-browser, browser-harness,
playwright-cli로
모두 브라우저 CLI 범주다.
비교표에서 경쟁자로 세운 확장 프로그램, 내장 브라우저, 클라우드 브라우저,
AI 브라우저는
벤치마크에 없다.
제3자 소개 페이지를 올린 HN 스레드에서 sheo는 사이트가 팝업으로 가득하고,
벤치마크가 보이지 않아 가장 빠르다는 주장이 어색하며,
Lightpanda 같은 실제 브라우저 경쟁자가 비교에 없다고 적었다.[^sheo]
이 댓글은 벤치마크가 나오기 전의 소개 페이지를 향한 것일 수 있어
지금의 홈페이지에는 그대로 맞지 않는다.
다만 브라우저 경쟁자가 비교에서
빠졌다는 지적은 도구 목록에 Lightpanda가 보이지 않는다는 점에서 남는다.

이 저장소에 정리된 다른 재현 실험이 대조적이다.
그쪽은 고정한 모델 리비전과 프롬프트 해시와 행 단위 출력을 커밋해 두고,
빠른 경로가 결과를 미세하게 바꾼다는 사실까지 함께 적었다.
같은 종류의 속도 주장이라도 확인 가능성에서 차이가 크다.

속도가 사용자가 체감하는 이점인지도 따로 봐야 한다.
요즘IT 필자는 실제로 써 보니 작업 속도보다
에이전트가 일하는 동안 다른 일을 계속할 수 있다는 점이 더 크게 느껴졌다고
적었다.[^yozm]
이 글에는 속도나 비용의 수치가 없고 근거는 필자 한 사람의 일주일이다.[^yozm]
그래도 홈페이지가 첫 주장으로 내세우는 속도와 사용자가 체감하는 가장 큰 이점이
다를 수 있다는 한 사례다.

### 격리와 로그인 상속이 한꺼번에 성립하는 방식이 설명되지 않는다

Space는 작업마다 격리된 BrowserContext이고 자기 쿠키와 저장소를 가진다고 한다.
동시에 에이전트는 사용자가 이미 로그인한 사이트에 로그인 없이 들어간다고 한다.
두 문장이 모두 참이려면 사용자의 로그인 상태가 어떤 방식으로 Space에
들어가는지가 있어야 한다.
그 방식에 따라 보안 성질이 달라진다.

- 사용자의 쿠키가 Space로 복사된다면, 대상 사이트가 보는 것은 같은 세션이고 에이전트의 행동은 사용자의 행동이다.
- 쿠키 저장소를 공유한다면, Space 안에서 로그아웃하는 일이 사용자 탭의 세션도 끊을 수 있다.
- 사이트별로 승계하는 규칙이 있다면, 그 규칙이 무엇인지가 사용자가 알아야 할 부분이다.

공식 문서는 비밀번호나 인증 쿠키, 세션 토큰을 에이전트가 읽거나 내보낼 수 없다고
하면서도
에이전트가 로그인된 세션으로 페이지에 접근한다고 분명히 적는다.[^privacy]
토큰을 못 읽는다는 것과 그 토큰으로 인증된 요청을 보낼 수 있다는 것은 다르다.
`httpGet`이 페이지 컨텍스트에서 요청을 보내고
`cdp`로 원시 프로토콜을 쓸 수 있다는 점까지 보면,
에이전트가 인증된 요청을 보내는 능력은 사실상 열려 있다.[^d-cli]
이것은 이 제품의 결함이라기보다 로그인 상속이라는 기능의 본질이다.
다만 Space라는 이름이 주는 격리의 인상이 어디까지 맞는지를 사용자가 판단하려면
이 부분의 설명이 필요하다.

### 탐지 회피 문제를 사용자가 먼저 묻는데 답이 없다

HN 스레드에서 두 번째로 올라온 질문이 계정 안전이었다.
haruharuha는 API로는 안 되는 비공개 트위터 계정 추적에 쓰고 싶은데,
이 브라우저의 자동화가 얼마나 스스로를 가리는지가 걱정이라며
플랫폼의 봇 탐지를 건드려 계정이 정지될까 우려된다고 적었다.[^haruharuha-ban]
이어진 답은 한 줄이었다.
qddegtya가 자기 Twitter 시나리오로 써 봤는데 잘 돌아간다고 적었다.[^qddegtya]
제품을 만든 쪽의 설명은 이 스레드에서 읽히지 않았다.

이 공백이 중요한 이유는 제품의 설계가 그 위험을 키우는 방향이기 때문이다.
사용자의 실제 로그인과 쿠키를 물려받아 자동화를 돌린다는 것은,
탐지되었을 때 잃는 것이 임시 계정이 아니라 사용자의 본 계정이라는 뜻이다.
로그인 마찰이 없다는 항목이 표에서는 이점으로만 제시되지만
반대편에는 그만큼의 위험이 붙어 있다.

공식 문서는 이 영역에 대해 두 가지를 말한다.
하나는 캡차를 우회하지 않는다는 것이고,
다른 하나는 어떤 작업을 허용할지는 사용자가 고른 에이전트와 사용자가 둔 한도에
달렸고
ego lite가 정하지 않는다는 것이다.[^d-intro]
자동화가 대상 사이트에 어떻게 보이는지,
이용 약관 위반 위험을 어떻게 다루는지는 언급이 없다.
개인정보 보호와 계정 위험은 다른 문제이고, 이 제품에서는 후자가 더 크다.

요즘IT 필자는 이 위험을 요청 쪽에서 다룬다.
조회 작업에는 수정하거나 제출하지 말아 달라고 적고,
결과가 남는 작업은 사람이 마지막에 확인하며,
자료 조사와 읽기 작업부터 맡긴다고 한다.[^yozm]
이것은 사용자가 요청 문장으로 정하는 경계이고,
후기는 제품이 그 경계를 강제하는지 말하지 않는다.
공식 문서도 이 경계를 에이전트에게 말로 알려 주는 것으로 안내한다.[^d-space]
필자가 전하는 대로 공식 문서가 되돌리기 어려운 작업을 사람이 개입할 대상으로
분류한 것은
방향이 옳지만, 브라우저 수준에서
막는지 에이전트의 스킬 지침으로 따르게 하는지는 확인되지 않았다.[^yozm]

### 권한을 크게 풀어야 쓸 수 있다는 점이 안전 서사와 어긋난다

제품의 서사는 사람의 탭이 건드려지지 않고
사람이 언제든 넘겨받는다는 안전한 협업이다.
그런데 설치 가이드의 첫 요구 사항은 에이전트의 권한을 최대로 푸는 것이다.
Codex에는 Full access를, Claude Code에는 Bypass permissions나
`--dangerously-skip-permissions`를 요구한다.[^d-quick][^d-claude]
이 옵션이 켜진 에이전트는 ego-browser뿐 아니라 컴퓨터의 다른 명령도 확인 없이
실행한다.

문서가 이 요구의 이유로 드는 것은 앱을 샌드박스 밖에서 실행해야 한다는 점이다.
그렇다면 `ego-browser` 한 명령만 허용하는 좁은 규칙으로 충분한지가 사용자의
질문이 된다.
읽은 문서에는 이 질문에 대한 답이 없다.
권한 모드를 낮추고 쓸 수 있는지는 설치 전에 작은 시험으로 확인하는 편이
안전하다.
Space의 안전한 분리는 브라우저 안의 이야기이고,
에이전트의 권한은 그 바깥의 이야기라는 점을 도입 판단에서 나눠서 봐야 한다.

### 홈페이지의 사용 사례는 접근 권한과 약관의 문제를 건드린다

홈페이지의 사용 사례 가운데 영업과 법무는 이 위험이 선명한 곳이다.
영업 항목은 Sales Navigator나 Salesforce가 데이터를 보여 주면서 내보내기를
막거나 유료로 파는 곳이라고 설명하고,
에이전트가 사용자가 볼 수 있는 것을 읽어 쓴다고 한다.
법무 항목은 PACER 같은 사이트에 사용자의 로그인으로 접속해 문서를
읽어 오는 일이다.
이 문서는 이 서비스들의 약관을 읽지 않았으므로 위반인지 아닌지는 말하지 않는다.
다만 사이트가 내보내기를 막아 둔 이유가 있는 곳에서 사람의 로그인으로
자동 수집하는 것을 사용 사례로 앞세우는 것은,
앞의 계정 정지 우려와 같은 방향의 위험을 제품이 스스로 키우는 일이다.
데이터 항목은 브라우저 데이터가 기기에 남는다고 하면서
에이전트가 보는 페이지의 내용은 사용자가 고른 모델에게 간다고 밝힌다.
로컬 저장이라는 표시가 모델 쪽으로 나가는 내용까지 덮는 것은 아니다.

### 경험 축적 기능이 아직 없는데 비교표에는 들어가 있다

재사용 가능한 스킬 항목은 비교표에서 ego lite만 표시를 받은 항목 중 하나다.
그런데 특징 표에서 같은 기능을 설명하는 항목에는 출시 전이라는 단서가 붙어 있다.
성공한 동작을 재사용 가능한 도구로 정리해 비슷한 작업이 최대 5배 빨라진다는 것이
아직 출시되지 않은 기능이라는 뜻이다.

최대 5배라는 수치도 출시되지 않은 기능에 대한 것이므로 측정값일 수 없다.
홈페이지의 표와 README의 표는 같은 항목에 곧 제공이라는 표시를 붙여 이 비판이 덜
맞는다.
그러나 그 표에서도 ego lite의 모든 칸이 채워져 있고,
캡차가 적다는 항목처럼 근거가 보이지 않는 칸이 있다.
이 기능은 로드맵에서 진행 중이고 공식 문서는 제한적 베타라고 하므로
지금의 평가는 기능이 아니라 약속에 대한 것이다.[^roadmap][^d-skills]

### 열린 저장소와 닫힌 앱

별이 2만 개를 넘는 MIT 저장소라는 사실은 오픈소스 브라우저라는 인상을 준다.
저장소의 라이선스 문단은 이 저장소의 내용이 MIT이고
브라우저는 별도의 무료 다운로드라고 구분한다.
읽은 저장소의 디렉터리(`docs`, `package`, `plugins`, `skills`,
`spec`)에는 브라우저 엔진이나 앱의 소스가 없고,
앱이 구현해야 할 요구 사항을 적은 문서(`native-bindings-api.md` 등)가 있을
뿐이다.
브라우저 앱이 닫혀 있는지, 소스가 따로 공개되는지는 읽은 문서에서
확인되지 않았다.

이 구분이 도입 판단에 영향을 준다.
Space와 Snapshot과 로그인 처리는 모두 앱 안에서 일어나는 일이고,
사용자가 감사할 수 있는 코드는 에이전트 쪽(스킬과 SDK)에 한정된다.
개인정보 처리방침이 적는 데이터 흐름과 앱이 실제로 하는 일을 대조해 줄 코드는
공개되지 않은 부분이다.
무료이고 가입이 필요 없다는 점은 장점이지만,
HN의 howardlun7은 개인용은 0달러(0원)이고 기업용 가격은 별도 협의라고
적었다.[^howardlun7]
홈페이지 메뉴에도 Enterprise 페이지가 있으나 이 문서는 그 내용을 읽지 않았다.
지금의 무료와 로컬 저장과 어떤 에이전트든 연결 가능이라는 개방성 가운데
무엇이 먼저 바뀌는지가 장기적으로 이 선택의 성격을 정한다.

## 인사이트

### 에이전트 도구의 인터페이스 단위가 명령에서 코드로 옮겨 가고 있다

ego lite의 설계 결정 중 가장 이전 가능한 것은 도구를 CLI 명령이 아니라 함수로
노출한 것이다.
이 선택의 이유는 모델이 코드를 잘 쓴다는 것보다
한 번의 출력에 담을 수 있는 작업량이 달라진다는 데 있다.

명령 단위 인터페이스에서는 모델이 한 번에 한 단계씩만 진행할 수 있고,
단계마다 결과를 읽어 다음을 정해야 하므로 왕복이 단계 수만큼 생긴다.
코드 단위 인터페이스에서는 조건과 반복과 오류 처리를 조각 안에 넣을 수 있으므로
여러 단계가 하나의 왕복에 접힌다.

이 관점은 MCP 서버나 에이전트 도구를 설계할 때 바로 쓸 수 있다.
도구를 몇 개 만들지보다 그 도구들을 한 호출에서
조합할 수 있는지가 왕복 수를 정하고,
왕복 수가 지연과 토큰을 정한다.
도구 목록을 늘리는 대신 도구를 조합하는 실행 환경을 주는 쪽이
같은 기능에서 훨씬 적은 비용을 내는 구조다.
ego-browser의 `help('click')`처럼 도구가 자기 사용법을 에이전트에게 직접 알려
주고,
스킬이 버전에 맞는 가이드를 출력하게 한 것도 같은 철학의 연장이다.
에이전트가 문서를 찾아 읽는 왕복마저 도구 안으로 들여온 것이다.

### 에이전트에게 사람의 세션을 물려주는 순간 실패의 단위가 커진다

로그인 상속은 이 제품에서 가장 강력한 기능이면서 가장 위험한 기능이다.
같은 메커니즘이 두 가지를 동시에 한다.
에이전트가 인증 장벽을 넘게 해 주고,
에이전트의 실수를 사용자 계정의 실수로 만든다.

여기서 나오는 설계 원칙이 있다.
자격 증명을 공유하는 자동화에서는 격리 단위와 책임 단위가 어긋난다는 것이다.
Space는 브라우저 안에서 탭과 상태를 격리하지만
대상 사이트가 보는 것은 같은 계정이므로 사이트 쪽에서는 격리가 존재하지 않는다.
정지나 차단은 Space가 아니라 계정에 걸린다.

그러므로 이런 도구를 도입할 때 물어야 할 것은 얼마나 잘 동작하는가가 아니라
잘못되었을 때 무엇을 잃는가다.
버릴 수 있는 계정으로 먼저 돌려 보는 것,
읽기 작업과 쓰기 작업을 다른 계정으로 분리하는 것,
자동화가 건드릴 수 있는 사이트 목록을 좁혀 두는 것이
격리 단위를 책임 단위에 맞추는 실천이 된다.
요즘IT 필자가 되돌릴 일이 적은 자료 조사와 상태 확인부터 맡기고
최종 결과를 직접 검토하는 것은
이 원칙을 경험으로 찾아낸 방식에 가깝다.[^yozm]

### 브라우저가 에이전트의 운영체제 자리를 노리고 있다

ego lite가 스스로를 규정하는 방식, 즉 라이브러리도 아니고
내장 에이전트를 가진 앱도 아닌
공유되는 브라우저라는 자리는 새로운 종류의 층위다.
그 층위에서 벌어지는 일이 운영체제가 하는 일과 닮아 간다.
격리된 작업 공간을 나눠 주고, 자원 접근을 중개하고, 상태를 보존하고,
여러 클라이언트가 같은 자원을 두고 다투지 않게 조정한다.
로드맵에 오른 Electron과 네이티브 앱 조작,
어떤 하니스든 호스팅하는 브라우저 ACP는
브라우저 바깥의 자원까지 이 중재의 범위에 넣겠다는 방향이다.[^roadmap]

이 유비가 유용한 이유는 다음에 무엇이 필요해질지를 예측하게 해 주기 때문이다.
운영체제가 프로세스 격리 다음에 권한과 감사와 자원 할당을 필요로 했듯이,
이런 브라우저도 Space별 권한, 어느 에이전트가 어느 사이트에 무엇을 했는지의
기록,
그리고 폭주하는 에이전트를 멈추는 장치가 필요해진다.
Space를 열어 언제든 넘겨받거나 멈출 수 있다는 기능과
작업이 끝난 뒤 탭을 남겨 감사할 수 있게 하는 설계가 그 첫 조각이다.[^d-space]

동시에 같은 유비가 위험도 알려 준다.
운영체제 자리를 차지한 소프트웨어는 전환 비용이 크고,
데이터와 세션과 축적된 스킬이 모두 그 안에 쌓이면 이동이 어려워진다.
Chrome 데이터를 가져와 일상용 브라우저로 쓰라는 제안은 이 전환 비용을 스스로
키우는 방향이다.

### 도입을 진지하게 고민한다면

이 제품이 맞는 사람과 맞지 않는 사람을 가르는 기준은 아래와 같다.

| 상황                                                                               | 판단                                                                               |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| macOS나 Windows(베타)에서 에이전트에게 로그인된 사이트의 조사와 확인을 자주 맡긴다 | 가장 잘 맞는다. 요즘IT 필자의 일주일이 이 경우다.[^yozm]                           |
| 서버나 CI에서 사람 없이 브라우저를 돌린다                                          | 맞지 않는다. 앱 설치가 필요한 데스크톱 브라우저이고 Linux는 계획 단계다.[^roadmap] |
| 공개 페이지를 가끔 찾는 정도다                                                     | 차이를 크게 못 느낄 수 있다는 것이 사용자의 평이다.[^yozm]                         |
| 서버에서 수백 개를 동시에 돌려야 한다                                              | 클라우드 브라우저가 맞다고 공식 문서가 인정한다.[^d-intro]                         |
| 에이전트의 권한을 좁게 유지해야 한다                                               | 먼저 `ego-browser` 한 명령만 허용하는 구성이 되는지 확인해야 한다                  |

시험해 본다면 아래 순서를 권한다.

1. 먼저 읽기 전용 작업 하나로 시작한다. 로그인 상태가 이미 있는 사이트의 목록이나 수치 확인처럼 되돌릴 일이 없는 일이 좋다.
2. 요청에 대상, 하지 말 일, 멈출 지점, 결과의 모양, 작업이 끝난 뒤 남길 탭을 모두 적는다.
3. 같은 작업을 지금 쓰는 방법(agent-browser, Playwright MCP, 브라우저 확장)으로도 돌려서 걸린 시간과 사용한 토큰을 비교한다. 홈페이지의 수치는 자기 작업의 대리 지표일 뿐이다.
4. Chrome 데이터 가져오기는 쓰는 계정이 정지되어도 감당할 수 있는 범위에서 시작한다. 한 번에 모든 세션이 넘어간다는 점을 감안한다.
5. 에이전트의 권한 설정을 어떻게 둘지 먼저 정한다. Bypass permissions나 Full access를 켜야 한다면 그 권한이 ego-browser 밖의 명령에도 적용된다는 점을 계산에 넣는다.
6. 한 주 뒤에 무엇이 줄었는지를 묻는다. 요즘IT 필자의 기준대로 로그인을 맞추는 일과 탭을 정리하는 일이 실제로 줄었는지가 이 제품의 핵심 가치다.[^yozm]

이 문서가 확인하지 못한 것이 있다.
앱을 직접 설치해 보지 않았고, Space가 사용자의 로그인을 받는 방식과
앱이 닫혀 있는지, 권한을 낮춘 구성에서 작동하는지는 읽은 자료에 없었다.
HN 세 스레드는 합쳐서 댓글이 열 개 남짓이어서 사용자 경험의 표본으로는 얇다.
가장 풍부한 사용자 자료는 한 사람의 일주일 사용기이고,
그 글도 AI의 도움을 받아 작성했다는 표시가 글 끝에 있다.[^yozm]
