## 소개

Lemma는 사람과 AI 에이전트가 한 팀으로 일하는 오픈소스 작업 공간이다.
홈페이지의 첫 문구는 AI 팀원을 고용하라는 것이고,
그 팀원을 사람들과 공유하면 모두에게서 배우고
일하는 방식에 맞춰 스스로를 만들어 간다고 덧붙인다.
스스로를 소개하는 비유는 Dots + Spaces + Lovable을 팀용으로 합친 것이다.
만든 곳은 미국 델라웨어 법인 Folks and Machines, Inc.다.

이름이 같은 다른 대상과 헷갈리기 쉽다.
이 저장소의 `llm/lemmalog.md`가 다루는 Lemmalog는
취약점 연구용 Datalog 상태 엔진으로, 이 문서의 Lemma와는 관계가 없다.

### 하네스라는 자기 규정

README의 개발자용 설명은 제품을 하네스(harness)로 규정한다.
하네스는 모델을 둘러싼 모든 것,
즉 호출할 수 있는 도구, 읽는 기억, 쓰는 상태, 돌아가는 루프,
일하는 경계를 말한다.
README는 코딩 에이전트가 준 하네스가 한 사람, 한 기계, 한 세션짜리였다면
Lemma는 그 하네스를 팀 단위로 만든 것이라고 설명한다.
상태는 공유되고 권한이 걸려 있으며, 세션이 끝나도 일정, 웹훅,
테이블 이벤트로 계속 돈다.
교정은 상시 지침이 되고, 반복된 순서는 워크플로가 되며,
반복된 판단은 에이전트 역할이 된다.

사이트의 `llms.txt`는 같은 내용을 더 건조하게 적는다.
Lemma는 에이전트가 만든 소프트웨어의 런타임이며,
코딩 에이전트가 앱을 쓰면 Lemma가 팟(pod)을 주어
프롬프트를 친 한 사람이 아니라 팀이 그것을 운영할 수 있게 한다는 것이다.
같은 파일은 쓰지 말아야 할 경우도 밝힌다.
영속 상태도, 사용자 팀도, 대화 밖의 자동화도 없는 단일 세션 채팅 에이전트라면
모델 제공자 API를 바로 쓰는 편이 간단하다고 적는다.

## 팟의 구성 요소

Lemma의 모든 것은 팟 안에 있다.
팟은 한 사람, 한 팀, 한 업무 과정을 위한 독립된 환경으로,
공유 상태, 에이전트, 워크플로, 권한, 앱을 함께 담는다.

| 구성 요소   | README가 밝힌 역할                                                                    |
| ----------- | ------------------------------------------------------------------------------------- |
| Tables      | 행 수준 보안이 걸린 타입 있는 업무 데이터. 리드, 티켓, 작업, 승인 등                  |
| Files       | 선호, 플레이북, 문체 가이드를 담는 마크다운 기억. 정책이 사는 곳                      |
| Agents      | 역할과 도구 권한을 받고 특정 테이블, 파일, 커넥터로 접근이 제한된 LLM 작업자          |
| Workflows   | 에이전트, 함수, 분기, 반복, 대기, 사람 승인 단계를 섞은 그래프                        |
| Functions   | 같은 입력에 같은 출력을 내는 예측 가능한 쪽. 검증, 상태 전이, 외부 행동을 맡는 코드   |
| Permissions | 사람과 에이전트 모두의 역할. 팟 역할, 테이블 권한, 리소스 공개 범위, 위임 토큰        |
| Approvals   | 멈추고, 특정 사람에게 넘기고, 그 결정에 따라 재개하는 워크플로 단계                   |
| Connectors  | 연결된 계정, 그 접근 범위, 그것을 쓰는 주체를 보여 주는 외부 연결                     |
| Apps        | 사람들이 일을 보고 지시하고 결정하는 UI. URL로 배포되고 같은 팟 API를 쓴다            |
| Surfaces    | Slack, Microsoft Teams, Telegram, WhatsApp, 이메일. 신원 확인과 대화 연결을 갖춘 입구 |

홈페이지는 이것을 사용자 쪽 말로 다시 묶는다.
문서를 함께 쓰는 Pages, 모두가 보는 목록인 Tables,
손이 바뀌는 일을 적어 둔 Workflows, 한 가지 일을 위한 화면인 Apps,
한 번 고치면 기억하는 Memory, Slack이나 WhatsApp으로 묻는 Channels다.
홈페이지 데모의 Kit는 제품팀의 피드백 루프를 맡은 팀원으로,
한 대화 안의 네 가지 요청이 각각 보고서 페이지, 주제 테이블,
PR 병합 때 시작해 담당자의 확인을 기다리는 워크플로,
피드백 앱으로 남는 과정을 보여 준다.

함수와 에이전트를 나눈 이유가 이 설계의 요점이다.
README는 함수를 같은 입력에 같은 출력을 내는 예측 가능한 절반이라 부르고,
에이전트가 함수를 도구로 호출하므로 판단과 규칙이 분리된 채로 남는다고 설명한다.

## 동작 방식

### 구성 요소와 역할 분담

`ARCHITECTURE.md`는 저장소의 모든 것이
네 가지 일 중 하나를 위해 존재한다고 정리한다.

| 일                     | 구성 요소                                       |
| ---------------------- | ----------------------------------------------- |
| 플랫폼 실행            | `lemma-backend`, `lemma-frontend`               |
| 로컬 설치와 운영       | `desktop`, `lemma-stack`                        |
| 팟 만들기와 운영       | `lemma-cli`, `lemma-skills`, `lemma-pod-bundle` |
| 그 위에 다른 것 만들기 | `lemma-python`, `lemma-typescript`              |

백엔드는 FastAPI 애플리케이션이며 문서 기준으로 14개 모듈로 조립된다.
같은 코드베이스에서 HTTP와 WebSocket, 권한 확인, 영속 쓰기를 맡는 API 프로세스와
streaq 작업, 이벤트 소비, 긴 I/O, 시간 트리거를 맡는 Worker 프로세스가 나온다.
별도의 스케줄러 프로세스는 없고 시간 트리거도 Worker의 cron으로 돈다.
Desktop과 개발 모드는 둘을 한 프로세스에 담고,
Docker Compose 배포는 컨테이너로 나눈다.
문서는 이것이 패키징의 차이일 뿐 아키텍처의 차이가 아니라고 강조한다.

프런트엔드는 Next.js 앱이고,
팟 앱은 TypeScript SDK로 같은 팟 API를 부르는 별도 프런트엔드다.
Python과 TypeScript SDK는 커밋된 OpenAPI 명세에서 생성하며 손으로 고치지 않는다.
명세와 생성 코드가 어긋나면 CI가 실패한다.
저장소 언어 구성은 Python이 가장 크고 TypeScript, Rust가 뒤를 잇는다.
Rust는 Tauri 데스크톱 셸과 Agent Host 쪽이다.

### 상태가 사는 곳

| 저장소                  | 담는 것                                      | 특징                                       |
| ----------------------- | -------------------------------------------- | ------------------------------------------ |
| PostgreSQL 앱 DB        | 사용자, 팟, 에이전트, 워크플로, 커넥터, 실행 | Alembic 마이그레이션                       |
| PostgreSQL 데이터스토어 | 팟 테이블, 레코드, 파일 메타데이터           | 별도 DB, 팟별 스키마, 낮은 권한 역할로 RLS |
| Redis                   | 도메인 이벤트 스트림, 작업 큐, 캐시          | 프로세스 내부 캐시를 금지하고 모두 Redis로 |
| 객체 저장소             | 업로드 파일, 파생 문서, 앱 번들              | local, S3, GCS, Azure                      |
| SuperTokens             | 세션과 인증                                  | 자체 호스팅, 관리형 인증에 의존하지 않음   |

프로세스당 DB 커넥션 풀이 10개에 넘침 10개로 작다는 점에서 두 규칙이 나온다.
외부 I/O나 스트리밍 응답 동안 DB 세션을 쥐고 있지 말 것,
그리고 캐시는 프로세스가 아니라 Redis에 둘 것이다.

### 일이 움직이는 경로

상태 변경과 그것을 알리는 이벤트는 같은 트랜잭션에서 커밋된다.
API는 도메인 쓰기와 아웃박스 행을 한 트랜잭션에 넣고,
디스패처가 아웃박스 행을 Redis Stream에 내보내며,
Worker는 인박스 행으로 중복을 걸러 낸 뒤 일을 한다.
실패하면 제한된 횟수만 재시도하고 데드레터로 보낸다.

```text
호출자 → API: 요청
API → PostgreSQL: 도메인 쓰기 + 아웃박스 행 (한 트랜잭션)
API → 호출자: 응답
PostgreSQL → Redis Stream: 디스패처가 아웃박스 행을 발행
Redis Stream → Worker: 최소 한 번 전달
Worker → PostgreSQL: 인박스 행 (멱등)
Worker: 작업 수행, 실패 시 제한된 재시도 후 데드레터
```

전달이 최소 한 번(at-least-once)이므로 소비자는 멱등이어야 하고,
하위 작업 ID는 결정적으로 만들어 재생해도 일이 중복되지 않게 한다.
위협 모델 문서는 이 구조의 남은 위험도 적어 둔다.
외부 서비스에 부작용을 일으킨 뒤 인박스 완료를 쓰기 전에 프로세스가 죽으면
외부 I/O가 반복될 수 있고,
그래서 가능한 곳에서는 제공자의 멱등 키가 필요하다고 한다.

### 샌드박스

에이전트 작업 공간과 함수 실행은
백엔드 프로세스가 아니라 따로 준비한 샌드박스에서 돈다.
`WORKSPACE_PROVIDER` 설정 하나로 샌드박스 재료를 `docker`, `e2b`,
`lemma_local`(Desktop의 전용 VM) 중에서 고른다.
문서가 짚는 차이는 내구성이다.
Docker와 `lemma_local`에서는 계산 자원이 교체되어도 파일이 남지만,
E2B에서는 샌드박스 자체가 디스크라서 샌드박스와 함께 사라진다.
v0.9.0부터 샌드박스는 항상 인터넷에 닫힌 채로 만들어진다.

### Agent Host: 내 컴퓨터의 코딩 에이전트를 팟에 연결하기

Agent Host는 사용자 컴퓨터에 있는 Claude Code, Codex, OpenCode, Cursor를
팟의 실행 엔진으로 쓰게 하는 부분이다.
이 에이전트들은 사용자 본인의 자격 증명과 파일을 가지고 있어
클라우드로 옮길 수 없으므로,
컴퓨터가 바깥으로 WebSocket 하나를 열어 Lemma에 붙고,
들어오는 포트는 열지 않는다.
각 코딩 에이전트는 Agent Client Protocol(ACP)로 구동한다.
README가 새 AI 요금 없이 이미 내는 구독으로 돌린다고 하는 부분이 바로 이것이다.

설계 문서에서 눈여겨볼 부분은 동의의 경계를 어디에 두었는가다.
Desktop은 로그인한 사용자의 컴퓨터를 자동으로 페어링하고,
연결 해제 버튼도 없앴다.
문서의 논리는 페어링만으로는 아무것도 실행되지 않는다는 것이다.
페어링된 컴퓨터는 그것을 페어링한 한 사람에게 속하고 조직에 속하지 않는다.
작업 공간이 그 컴퓨터의 에이전트에 닿으려면 런타임 프로필을 만들어야 하는데,
프로필은 소유자만 묶을 수 있고 기본값이 개인 범위다.
그래서 문서는 동의의 경계가 페어링이 아니라 프로필이라고 말한다.
진짜 거절은 컴퓨터를 계정에서 제거하는 것이고,
제거된 컴퓨터는 다시 자동으로 페어링되지 않는다.

macOS 로컬 설치에서는 에이전트 명령을 VM이 아닌 사용자의 Mac에서
Claude Code를 본뜬 OS 샌드박스(Seatbelt)로 실행하는 호스트 실행도 있다.
`gh` 로그인, git 자격 증명, Homebrew 도구가 Mac에 있기 때문이다.
조건은 까다롭다.
실행을 일으킨 사람이 Lemma 앱 안의 그 사용자 본인이어야 하고,
워크플로, 일정, Slack이나 이메일 같은 외부 채널,
동료의 답장이 연 대화는 제외된다.
다른 사람의 말이 사용자의 Mac에서 명령을 움직이게 두지 않으려는 규칙이다.

### 기억은 팟 파일이다

별도의 기억 저장소는 없다.
에이전트가 배운 사실은 팟 데이터스토어의 평범한 파일로 남고, 두 루트로 나뉜다.

```text
/memory/AGENTS.md                    팟 전체 색인, 모든 에이전트
/memory/agents/<slug>/AGENTS.md      이 에이전트, 팟 전체 공유
/me/AGENTS.md                        이 사용자, 비공개
/me/agents/<slug>/AGENTS.md          이 사용자에 관한 이 에이전트의 기록, 비공개
```

파일에는 이미 사용자별 격리, 경로 기반 권한, 버전 관리,
전문 검색과 의미 검색이 있으므로
기억 전용 테이블을 만들면 그것을 모두 다시 만들어야 했다는 것이 문서의 설명이다.
네 개의 `AGENTS.md`는 매 실행마다 프롬프트에 들어가므로
문서는 이 파일을 저장소가 아니라 색인으로 쓰라고 한다.
여기 적은 것은 모든 대화의 매 턴마다 비용으로 돌아오기 때문이다.
플랫폼은 그 규칙이 지켜진다고 믿지 않고,
색인 길이와 섹션 전체 길이에 상한을 둔다.
잘라 낼 때는 어느 파일에서 몇 줄을 버렸는지 표시를 남기는데,
조용히 자르면 에이전트가 알아챌 수 없고 비대해진 색인을 고칠 수 있는 것도
에이전트뿐이기 때문이다.

## 설치하기

이 문서를 쓰면서 Lemma를 직접 설치하거나 실행하지는 않았다.
아래 명령은 README와 문서에서 옮겼고, 한국어 주석은 이 문서에서 붙였다.

### Lemma Cloud

```bash
uv tool install lemma-terminal
lemma servers select lemma-cloud
lemma auth login
lemma skills install                          # Claude Code, Codex, OpenCode, Cursor를 자동 감지
lemma pod create support-ops --with-starter   # 테이블과 에이전트가 든 시작 팟을 만들고 가져온다
lemma chat "what can you do in this pod?"
```

CLI는 반드시 `uv tool install`로 설치해야 한다.
`lemma-terminal`은 Python 3.14가 필요한데,
예전 인터프리터에서 `pip install lemma-terminal`을 하면 실패하지 않고
3.11을 허용한 마지막 릴리스인 0.6.2로 조용히 내려가
서버보다 몇 버전 뒤처진 CLI가 깔린다.
`lemma --version`과 `lemma doctor`로 실제 상태를 확인한다.

### 내 컴퓨터

Lemma Desktop은 Apple silicon의 macOS 14 이상용 서명된 온라인 패키지로 나온다.
앱에서 Local을 고르고 로컬 서비스 설치를 누르면
Lemma가 VZ 기반의 가벼운 Linux 런타임 안에 PostgreSQL, Redis, SuperTokens,
containerd를 직접 띄운다.
사용자가 Docker를 따로 설치할 필요는 없다.
포트는 설치마다 고르므로, CLI에 `local` 서버를 등록하려면 Desktop 설정이 끝난 뒤
`install.sh --cli-only`를 한 번 돌려야 한다.

```bash
curl -fsSL https://raw.githubusercontent.com/lemma-work/lemma-platform/main/install.sh |
  bash -s -- --cli-only          # Desktop이 실제로 고른 포트를 읽어 local 서버로 등록
lemma servers select local
lemma auth login
```

Windows 11 빌드도 릴리스마다 만들고 서명하지만 릴리스 자산으로 올리지는 않는다.
README는 Windows 경로를 끝까지 시험하기 전에 올리면 지원을 약속하는 셈이라
올리지 않는다고 설명한다.

### 팀용 서버

팀이 함께 쓰려면 직접 관리하는 VM에 Docker Compose 스택을 올린다.

```bash
git clone https://github.com/lemma-work/lemma-platform.git
cd lemma-platform/deploy/compose && ./bootstrap.sh && docker compose up -d
```

API, Worker, PostgreSQL, Redis, SuperTokens,
Caddy가 다이제스트로 고정한 이미지로 올라오고,
도메인을 연결하기 전까지는 `.sslip.io` 주소로 서비스된다.
DigitalOcean, Hetzner, Render, Railway용 원클릭 템플릿도 `deploy/`에 있다.

### 서버에서 도는 에이전트의 모델

서버에서 도는 에이전트는 Lemma가 관리하는 모델이나
Anthropic 또는 OpenAI 호환 키와 엔드포인트를 쓴다.
API 키가 없으면 Ollama나 LM Studio의 로컬 모델을 연결할 수 있다.
런타임 프로필은 팟별이라 에이전트마다 다른 모델을 줄 수 있다.

```bash
lemma-stack config set ai.protocol=openai_compat ai.base_url=http://127.0.0.1:11434/v1 ai.default_model=qwen3
```

비밀 값은 macOS 키체인이나 Windows 자격 증명 관리자에 저장되고,
모델 접근을 검증한 뒤에 활성화하며 실패한 변경은 되돌린다.

### 코딩 에이전트로 팟 만들기

Lemma의 주된 개발 방식은
쓰던 코딩 에이전트에 Lemma 스킬을 깔고 일을 설명하는 것이다.
`lemma-skills/`에는 `lemma-builder`, `lemma-app-design`, `lemma-app-qa`,
`lemma-evals`, `lemma-research` 등의 스킬이 들어 있다.
에이전트는 테이블, 에이전트, 워크플로, 권한, 앱을 파일로 쓰고,
가져온 뒤 워크플로를 실행해 승인 단계에서 제대로 멈추는지 확인한다.

```bash
lemma pod init support-ops                     # 편집할 시작 번들 생성
lemma pod import ./support-ops
lemma apps deploy support-ops ./index.html     # 빌드 없는 HTML 앱 또는 Vite 프로젝트 배포
lemma workflow run refund-review               # 사람 승인 단계에 닿으면 바로 반환
lemma pod export ./support-ops                 # 시스템 전체를 파일로 내보내기
```

팟이 파일이므로 내보내고, 바꾸고, 다시 가져올 수 있다.
README의 예시 팟 10개(Roundtable, Frontdesk, Panini,
Smart Inbox 등)도 이 형식으로 공개되어 있다.

## 라이선스

라이선스는 배포 경계를 따라 둘로 나뉜다.

| 라이선스   | 대상                                                                                               |
| ---------- | -------------------------------------------------------------------------------------------------- |
| AGPLv3     | `lemma-backend`, `lemma-frontend`, `desktop`                                                       |
| Apache-2.0 | `lemma-stack`, `lemma-cli`, `lemma-python`, `lemma-typescript`, `lemma-skills`, `lemma-pod-bundle` |

서버에서 제공되는 핵심은 AGPLv3이므로,
수정해서 네트워크로 서비스하면 수정한 소스도 같은 조건으로 공개해야 한다.
클라이언트 도구는 널리 넣어 쓰라는 뜻에서 Apache-2.0이다.
`lemma-pod-bundle`은 이음매에 놓인 패키지다.
Apache-2.0 CLI와 AGPLv3 백엔드가 같은 번들 형식에 합의해야 하므로
표준 라이브러리만 쓰는 Apache-2.0 패키지로 두었고,
AGPL 코드를 그 안으로 끌어오면 안 된다고 명시한다.

Folks and Machines는 상용 라이선스와 예외를 따로 판다.
README는 이 상용 예외가 AGPL 조달 문제를 풀어 주면서도
핵심은 그대로 오픈소스로 남긴다고 설명한다.
Lemma라는 이름과 로고는 상표이며,
코드는 포크해도 브랜드는 포크하지 말라고 적는다.
README의 라이선스 절은 AGPLv3 대상으로 백엔드와 프런트엔드만 나열하지만,
저장소 구성 표와 `ARCHITECTURE.md`는 `desktop/`도 AGPLv3로 적고 있고
`desktop/`에는 별도의 LICENSE 파일이 없다.

## 릴리스와 성숙도

### 하나의 버전, 베타의 호환 규칙

API, 두 SDK, CLI, 데스크톱 앱, 스택 도구는 모두 하나의 버전 문자열로 나간다.
`scripts/check_version_consistency.py`가
릴리스 태그와 모든 구성 요소의 버전을 대조한다.
베타 동안은 SemVer의 메이저와 마이너가 호환선이라,
호환되는 API 변경은 패치를, 깨지는 변경은 마이너를 올린다.
API가 `4.0.1`에서 `0.6.3`으로 내려간 적이 있는데,
문서는 1.0 전에 안정적인 4.x 계약을 약속하지 않으려고
SDK 번호에 맞춘 일회성 정리였다고 설명한다.
설치된 클라이언트와 서버의 어긋남은 버전 번호와 별개로 스키마 지문으로 잡아내고,
`lemma doctor`가 그것을 보고한다.

### v0.9.0에서 바뀐 것

v0.9.0 릴리스 노트와 변경 이력이 밝힌 주요 변화는 다음과 같다.

- 대화 옆에 리소스가 열리는 새 작업 공간이 나왔다.
- 에이전트의 브라우저 화면을 실시간으로 보고, 클릭하고, 직접 로그인할 수 있게 되었다.
- `wait_for`로 에이전트가 시간, 프로세스, 하위 에이전트를 비용 없이 기다리고, 아주 길거나 실패하는 실행은 멈춰서 묻는다.
- 승인된 행동은 승인한 사람의 권한으로 그 행동 하나에 한해 실행된다. 다른 사람이 공유 채널에서 approve라고 쳐도 `403 APPROVAL_NOT_OWNED`로 거절된다.
- 철회된 OAuth 연결은 `502`가 아니라 `409 CONNECTOR_REAUTH_REQUIRED`로 응답해, 장애로 오인해 재시도하지 않게 했다.
- 사용 한도 API는 달러 금액 대신 비율(`used_percent`)만 돌려준다. 변경 이력은 요금제 포함 범위를 조정할 수 있는데 달러 한도를 보여 주면 Lemma가 약속하지 않는 숫자에 맞춰 계획을 세우게 된다고 이유를 댄다.
- Agent Host 프로토콜이 HTTP 장치 API에서 WebSocket 링크 하나로 바뀌었다.

변경 이력은 요금제를 파는 배포에서는 팟이나 멤버 수 한도에 걸릴 수 있지만
오픈소스 빌드에는 요금제가 없다고 밝힌다.
`lemma.work/pricing`은 404를 돌려주어 호스팅 가격은 확인하지 못했다.

### 저장소가 스스로 적어 둔 결함

저장소 루트의 `issues.md`는
제품 명세와 구현이 어긋나는 지점을 코드 위치와 함께 적는 등록부다.
문서를 쓰는 시점에는 다섯 건이 있고, 그중 하나가 특히 눈에 띈다.
DEV-SURF-002는 통신사가 다른 사람에게 다시 배정한 전화번호로
WhatsApp 메시지를 보내면 이전 주인으로 로그인된다는 내용이다.
WhatsApp의 발신자 ID가 곧 전화번호이고,
Meta의 Cloud API는 번호 재배정을 알려 주지 않기 때문이다.
이 항목의 심각도는 accepted로, 번호를 계정에서 지우기 전까지는
그 번호가 한 사람의 것이라는 제품 결정으로 정리되어 있다.
문서 스스로 그 영향 범위를 해당 계정이 닿을 수 있는 모든 것이라고 적는다.

## 트레이드오프

### 하나의 권한 모델과 여러 입구

Lemma의 핵심 약속은 앱, Slack, WhatsApp 어디서 물어도 같은 레코드,
같은 권한이 적용된다는 것이다.
이 약속은 입구가 늘어도 데이터가 갈라지지 않게 해 주지만,
입구마다 사람을 확인하는 방식이 달라서
권한 모델은 가장 약한 신원 확인만큼만 강하다.
앱 로그인은 세션이지만, WhatsApp에서는 전화번호가,
이메일에서는 발신 주소가 신원이다.
DEV-SURF-002가 그 차이가 실제 결함으로 드러난 사례다.
팀이 입구를 하나 열 때마다 그 입구의 신원 확인 수준을 따로 따져 봐야 한다.

### 에이전트가 쓰는 시스템, 사람이 맡는 책임

Lemma의 개발 흐름은 코딩 에이전트가
테이블, 에이전트, 워크플로, 권한, 앱까지 파일로 쓰고
같은 에이전트가 가져와 검증하는 것이다.
속도는 빠르지만, 권한과 승인 단계까지 에이전트가 쓴다는 점이 문제다.
README의 권장 프롬프트는
바꾸기 전에 제안된 워크플로와 리소스 모델을 먼저 보여 달라고 요구하는데,
이는 해석하자면,
사람의 검토가 권한 설계 단계에 반드시 들어가야 한다는 신호로 읽힌다.
테이블별 권한과 승인 지점이 실제 업무의 책임 구조와 맞는지는
에이전트가 검증할 수 없는 부분이다.

### 이미 내는 구독을 쓰는 비용

Agent Host는 Claude Code나 Codex 구독을 그대로 실행 엔진으로 쓰게 해서
새 AI 요금을 피하게 한다.
대신 그 실행은
페어링한 사람의 컴퓨터가 켜져 있고 Lemma가 열려 있을 때만 가능하다.
문서도 Agent Host가 Lemma가 열려 있는 동안만 돈다고 밝힌다.
일정이나 웹훅으로 밤새 돌아야 하는 서버 실행 에이전트는 별도의 모델 키나 Lemma
관리형 모델이 필요하다.
또 개인 구독을 팀의 작업에 쓰는 것이 각 제공자의 이용 약관에 맞는지는 Lemma
문서가 다루지 않는다.

### 빠른 개발 속도와 안정성

6월 말 첫 공개 뒤 석 달 남짓 사이에 v0.5.0부터 v0.9.0까지 태그 13개가 나왔고,
v0.9.0만 해도 응답 형태 변경, 프로토콜 교체, 승인 권한 의미 변경을 담았다.
베타 규칙상 마이너 버전마다 깨지는 변경이 들어올 수 있다.
반면 아웃박스와 인박스, 결정적 작업 ID, 아키텍처 래칫,
비밀 값 누출을 잡는 카나리 테스트처럼
운영 시스템다운 규율이 문서와 CI에 들어 있다는 점은
초기 프로젝트로서 드문 편이다.
기능이 빨리 바뀌는 것과 내부 규율이 단단한 것이 동시에 성립하는 상태라,
도입하는 쪽은 API를 직접 쓰는 범위를 좁게 잡는 편이 안전하다.

## 함정

- `pip install lemma-terminal`은 오래된 Python에서 실패하지 않고 0.6.2를 설치한다. 반드시 `uv tool install`을 쓴다.
- `install.sh`를 `--cli-only` 없이 돌리면 Desktop용 등록이 아니라 Docker/Podman 호환 설치가 시작된다.
- 공개된 Windows 설치 파일은 없다. Windows 빌드는 GitHub Actions 아티팩트로만 받을 수 있다.
- E2B를 샌드박스로 쓰면 샌드박스가 곧 디스크라 샌드박스가 사라질 때 파일도 사라진다.
- 최소 한 번 전달 구조에서는 외부 부작용이 반복될 수 있다. 외부 API를 부르는 함수는 멱등 키를 갖춰야 한다.
- 기억 색인인 `AGENTS.md`에 많이 쓰면 매 턴 비용이 늘고 상한을 넘는 부분은 잘린다.
- WhatsApp 입구는 전화번호가 곧 신원이다. 번호가 재배정되면 새 주인이 이전 사람으로 로그인된다.
- v0.9.0에서 `SNOOZE` 도구 집합이 사라졌다. 이를 지정해 에이전트를 만들거나 수정하면 거절된다.

## 기억할 원칙

### 동의는 연결이 아니라 권한을 부여하는 지점에 둔다

Agent Host 문서는 컴퓨터 연결 버튼을 없애면서 그 이유를 길게 적었다.
연결 자체가 아무것도 허락하지 않으니 연결 앞에서 묻는 것은 의식(儀式)일 뿐이고,
실제 결정은 런타임 프로필을 만드는 다음 화면에서 내려진다는 것이다.
에이전트 시스템에서 확인 대화상자를 어디에 둘지 정할 때,
그 단계가 실제로 무엇을 허락하는지부터 따지는 것이 이 설계의 교훈이다.
허락하지 않는 단계에서 묻는 것은 사람을 지치게 하고,
정작 중요한 확인을 가볍게 만든다.

### 에이전트의 판단과 규칙은 분리해서 둔다

Lemma가 함수와 에이전트를 나누고 에이전트가 함수를 도구로 부르게 한 것은
같은 입력에 같은 결과가 필요한 부분을 LLM에게 맡기지 않겠다는 선택이다.
상태 전이, 검증, 외부 행동은 코드가 맡고, 에이전트는 무엇을 언제 할지 판단한다.
그 위에 승인 단계를 얹으면 사람의 결정이 들어갈 자리가 구조로 생긴다.
에이전트에게 어디까지 맡길지는 프롬프트가 아니라 이 분리 위치로 정해진다.
