# Octop: 가족과 작은 팀이 한 서버를 나눠 쓰는 다중 사용자 AI 비서

<https://octop.cloud/>

<https://github.com/TencentCloud/Octop>

HN 토론: <https://news.ycombinator.com/item?id=49976872> (1점, 3개 댓글)

GN 토론: <https://news.hada.io/topic?id=34916>

## 소개

Octop은 TencentCloud 조직이 공개한 셀프 호스팅 AI 비서 플랫폼이다.
README의 한 줄 설명은
“더 똑똑한 셀프 호스팅 AI 비서, 다중 사용자와 다중 에이전트”이고,
대상은 가정과 작은 팀이다.
관리자 한 명이 계정을 만들고 가족이나 팀원마다 다른 에이전트를 배정하는 구조다.
홈페이지 `octop.cloud`는 자바스크립트로 그리는 페이지라,
정적 HTML에서는 제목과 “Understands you, helps you, grows with you”라는
설명 문구만 읽을 수 있었다.
그래서 이 문서는 주로 저장소의 README, `docs/`, 소스, 변경 이력, 릴리스를
읽고 썼다.
설치하거나 실행해 보지는 않았다.

저장소는 2026년 7월 8일에 만들어졌다.
이 문서를 쓴 10월 8일 기준으로 별 7,775개, 포크 936개이며,
최신 릴리스는 10월 4일에 나온 `v1.0.2b6`이다.
릴리스는 9월 13일 `v0.9.35`, 9월 14일 `v1.0.0`, 9월 19일 `v1.0.1`에 이어
9월 23일부터 10월 4일까지 `1.0.2b1`부터 `b6`까지 여섯 번 나왔다.
열흘 남짓한 사이에 베타 여섯 개가 나온 셈이다.
라이선스는 MIT이고 저작권자는 “2026 Octop”으로 적혀 있다.
`CHANGELOG.md`는 중국어로 쓰였고, 설계 문서도 영어와 중국어가 섞여 있다.

### 주요 기능

사용자는 “전문가(expert)”라 부르는 에이전트를 여러 개 둔다.
전문가마다 작업 공간, 모델 제공자, 메신저 채널, 예약 작업이 따로 있다.
저장소에는 18개 전문가 템플릿과
영어판 기준 217개 하위 에이전트 정의가 들어 있고,
MBTI 16유형 성격 템플릿으로 에이전트의 말투를 정할 수 있다.
전문가는 같은 배포 안의 다른 사용자에게 공유하거나 게시할 수 있다.

| 영역          | README와 문서가 밝힌 내용                                                     |
| ------------- | ----------------------------------------------------------------------------- |
| 대화 창구     | 웹 대시보드, 데스크톱 앱, CLI, HTTP/SSE/WebSocket API                         |
| 메신저        | Feishu, DingTalk, QQ, WeChat, Telegram, Discord, WeCom                        |
| 다중 에이전트 | AgentTeams 베타: 주최 전문가가 구성원 전문가에게 작업을 병렬로 배정           |
| 자동화        | 자연어 예약 작업, Chromium 브라우저 자동화, 브라우저 안 터미널, 원격 데스크톱 |
| 확장          | RAG 지식베이스, OAuth와 MCP 커넥터, 플러그인                                  |
| 코딩 위임     | ACP로 OpenCode, CodeBuddy, Claude Code, Codex에 작업을 넘김                   |
| 모델          | OpenAI 호환 API, DashScope(Qwen), Ollama 등                                   |
| 저장소        | 제어용 DB는 SQLite(기본) 또는 PostgreSQL, 작업 공간은 로컬·Docker·S3·COS      |

ACP는 양방향이다.
`octop acp --agent main`을 띄우면
Zed나 OpenCode 같은 편집기가 Octop 에이전트를 쓴다.
반대로 Octop 에이전트가 Claude Code 같은 외부 코딩 에이전트를
실행기로 불러 일을 맡기기도 한다.
외부 에이전트가 권한을 물으면 그 질문이 채팅에 나타나고 사용자가 고른다.

10월 4일 `1.0.2b6`에는 Agent Mail 커넥터, LDAP 로그인,
飞牛(FnOS) NAS용 ARM 패키지가 더해졌다.
그 전 `1.0.2b5`에는 Octop 인스턴스끼리 잇는 브리지가 들어갔다.

### 구조

`docs/architecture.md`와 ADR 001이 설명하는 구조의 핵심은
프로세스가 하나라는 점이다.
웹 서버, CLI, 사용자별 에이전트 런타임, 메신저 연결, 예약 작업이 모두
uvicorn 위의 Python 프로세스 하나에서 돈다.
Redis나 RabbitMQ 같은 외부 큐도, 별도 워커도 없다.
웹 UI, 메신저, 예약 작업은 모두 프로세스 안의 같은 처리기를 거쳐
에이전트에 닿고, 재시작하면 제어용 DB에서 런타임 트리를 다시 만든다.

```text
OctopServer.start()
 ├─ open_database()       SQLite WAL 또는 PostgreSQL
 ├─ run_migrations()
 ├─ SharedServices        저장소와 팩토리
 ├─ ExpertCatalog / SubagentCatalog
 ├─ PluginManager
 ├─ AgentManager          프로세스 전역 하나, 에이전트 행마다 런타임 생성
 ├─ Gateway               메신저 채널, WebSocket 허브
 ├─ CronManager           APScheduler
 └─ UserManager
```

에이전트 런타임 자체는 같은 조직의 별도 저장소들이 맡는다.
`octop-harness`는 LangGraph 기반 런타임으로
모델 라우팅, 도구, 스킬, 체크포인트를 담당하고,
`octop-gateway`는 메신저 메시지를 하나의 파이프라인으로 모은다.
`octop-memory`는 전문 검색을 곁들인 계층형 기억을,
`octop-browser`는 CDP 기반 브라우저 자동화를 맡는다.
이 저장소는 이들을 묶는 FastAPI 백엔드와 React 18 대시보드다.
`src/` 아래 Python 파일은 656개, 약 14만 4천 줄이고,
`tests/` 아래 Python 파일은 501개다.

데이터는 `~/.octop/` 한곳에 모인다.
설정 파일, SQLite DB, JWT 비밀 키와 채널 토큰, 에이전트별 작업 공간,
셸 명령 가드 규칙, 로그, 설치기가 만든 Python 가상 환경이 모두 이 아래에 있다.

### 설치

README가 권하는 설치는 한 줄짜리 셸 스크립트다.

```bash
curl -fsSL https://finnie-1258344699.cos.ap-guangzhou.myqcloud.com/octop/install.sh | bash
octop init   # SQLite DB, JWT 비밀 키, 첫 관리자 계정 생성
octop run    # http://127.0.0.1:8088 에서 대시보드
```

스크립트는 Tencent Cloud 광저우 리전의 COS 버킷에서 내려받는다.
`scripts/install.sh`를 읽어 보면
`uv`를 Tencent와 Aliyun PyPI 미러에서 먼저 받으려 하고,
실패하면 `astral.sh` 설치 스크립트로 넘어간다.
그다음 `~/.octop/venv`에 Python 3.12 가상 환경을 만들고
PyPI의 `octop` 패키지를 설치한다.
그 밖에 `pip install octop`, Docker Compose, Windows·macOS·Linux 데스크톱 앱,
FnOS NAS 패키지, 휴대용 zip이 릴리스마다 함께 올라온다.
`octop update`는 패키지만 바꾸고 `~/.octop/` 데이터는 남겨 둔다.

## 분석

### 경쟁 지점은 모델이 아니라 집 안의 관리자 한 명이다

Octop이 다른 셀프 호스팅 비서와 갈라지는 지점은 다중 사용자다.
OpenClaw(`openclaw/README.md`)가 스스로를 개인 AI 비서라고 부르는 것과 달리,
Octop은 관리자 한 명이 서버를 띄우고
나머지 식구나 팀원은 계정만 받는 구성을 처음부터 전제한다.
JWT 인증, 관리자 역할, 사용자별 권한 템플릿, 초대 링크, LDAP 로그인까지
기능 목록의 상당 부분이 “여러 사람이 한 서버를 나눠 쓰는 일”을 위한 것이다.

이 선택은 셀프 호스팅의 비용 구조와 맞물린다.
에이전트 서버를 사람마다 하나씩 띄우는 것은
기술에 밝은 한 명에게나 가능한 일이다.
가족 전체가 쓰려면 누군가 한 번 설치하고
나머지는 브라우저나 메신저로 들어오는 편이 현실적이다.
NAS용 FnOS 패키지와 Windows 서비스 등록 기능이 함께 있는 것도
“집에 늘 켜져 있는 기계 한 대”를 겨냥한 것으로 읽힌다(해석).

전문가 공유와 공용 스킬 풀도 같은 축에 있다.
잘 만든 설정 하나를 다른 사람이 처음부터 다시 만들지 않게 하는 기능인데,
이는 사용자가 한 명이면 필요 없는 기능이다.
Octop의 기능 목록은 에이전트를 얼마나 똑똑하게 만드느냐보다
에이전트를 여러 사람 사이에서 어떻게 나누느냐에 더 많은 줄을 쓴다.

### 단일 프로세스는 운영 부담을 덜기 위한 의도적 선택이다

ADR 001은 단일 프로세스를 고른 이유를 분명히 적는다.
주 사용자층에게 Redis나 프로세스 감독기를 요구하면 운영 부담이 두 배가 되고,
에이전트 호출은 LLM 응답을 기다리는 I/O라서 asyncio로 충분하며,
재시작 때 맞춰야 할 외부 상태가 없다는 것이다.
대가도 표로 적어 두었다.
한 대의 기계 안에서만 키울 수 있고, CPU를 많이 쓰는 작업은 이벤트 루프를 막으며,
워커를 수평으로 늘릴 수 없다.

가정과 작은 팀이라는 대상을 생각하면 합리적인 거래다.
동시에 쓰는 사람이 몇 명이고, 병목이 원격 LLM 응답 시간이라면
프로세스를 쪼개 얻을 것이 별로 없다.
설치 문서가 `octop init` 다음에 곧바로 `octop run`을 부르는 짧은 흐름은
이 결정에서 나온다.

### 하위 라이브러리로 쪼갠 이유는 재사용 가능한 부품이다

Octop 저장소 자체는 조립 계층이고, 에이전트 런타임과 메신저 게이트웨이,
기억, 브라우저 자동화는 각각 독립 저장소로 나와 있다.
9월 26일 `1.0.2b3`에는
런타임 의존성을 이 네 패키지의 `1.0.0`으로 바꾼 기록이 있다.
보안 정책의 실제 구현도 이 저장소가 아니라 `octop-harness` 쪽에 있다.

이렇게 나누면 Tencent Cloud가 같은 부품을 다른 제품에 다시 쓸 수 있다.
README 로드맵에 있는 관리형 에이전트(Managed Agents)와
로컬과 클라우드를 오가는 실행 계획을 보면,
셀프 호스팅판은 이 부품들의 첫 번째 소비자일 가능성이 있다(해석).
같은 조직이 낸 TencentDB Agent Memory(`mcp/tencentdb-agent-memory.md`)도
에이전트 기억이라는 부품을 따로 떼어 낸 사례다.

### 생태계의 무게중심은 중국 사용자에 있다

메신저 목록의 앞자리는 Feishu, DingTalk, QQ, WeChat, WeCom이고,
설치기는 Tencent와 Aliyun PyPI 미러를 먼저 시도하며,
Playwright 브라우저도 npmmirror를 먼저 쓴다.
기본 전문가 템플릿에는 `tencentcloud-api`, `cvm-ai-doctor`,
`cvm-cluster-doctor`, `meituan-living-assistant`, `wechat-ops`가 있다.
변경 이력과 브리지·팀 설계 문서는 중국어다.

README는 영어로도 충실히 쓰였고 Telegram과 Discord도 지원하지만,
제품이 가장 매끄럽게 맞물리는 환경은 중국 메신저와 Tencent Cloud다.
GitHub에서 별을 모은 속도와 실제 사용자층이 같은 곳에 있지는 않을 수 있다.

## 비평

### README가 약속한 보안은 기본값에서 꺼져 있다

README의 보안 절은
위험한 도구나 셸 명령은 가드 규칙에 따라 명시적 승인을 받아야 하고,
민감한 데이터는 작업 공간을 떠나기 전에 가려진다고 적는다.
그러나 `src/octop/infra/agents/security/policy_store.py`의 기본 정책은
사람의 승인(HITL)을 `enabled = False`로 두고,
셸 명령 가드는 켜 두되 모드를 `warn`으로 둔다.
가드의 모드에는 `block`, `warn`, `require_approval`이 있는데,
기본값은 경고만 남기고 명령은 그대로 실행하는 쪽이다.

“민감정보 가림”도 범위가 좁다.
`octop-harness`의 `PiiPolicy` 주석은 이를 API 키와 비밀 값 가림이라고 설명한다.
이를 이름·주소·전화번호 같은 개인정보 전반을 걸러 낸다는 뜻으로 읽으면
과장이다.
GN 요약이 옮긴 “위험한 도구·셸 명령에 대한 승인 규칙”도 사실이지만,
그 규칙을 켜는 것은 관리자의 몫이다.

가족이 같이 쓰는 서버에서 에이전트는 셸과 브라우저, 원격 데스크톱을 다룬다.
이런 제품에서 승인을 기본으로 끄는 결정은 편의를 위해 이해할 수 있지만,
README는 그 기본값을 밝히지 않는다.
설치한 사람이 문서만 믿고 승인이 걸려 있다고 생각하기 쉽다.

### 기본 파일 시스템 차단 목록은 Linux 서버를 가정한다

`octop-harness`의 기본 차단 경로는 `/etc/**`, `/root/**`, `/home/*/.ssh/**`,
`/home/*/.aws/**`, 모든 위치의 `.env`, `id_rsa`, `id_rsa.pub`이다.
macOS의 홈 디렉터리는 `/Users/` 아래에 있으므로,
`/home/*` 패턴은 Mac에서 돌리는 Octop의 `~/.ssh`나 `~/.aws`를
직접 막지 못한다고 읽힌다.
`id_rsa` 패턴이 일부를 잡지만 `id_ed25519` 같은 다른 키 이름은 목록에 없다.
실행해서 확인하지는 않았고 코드의 기본값만 읽은 결과다.

Octop은 macOS와 Windows 데스크톱 앱을 릴리스마다 내놓는다.
“집에 있는 내 컴퓨터에서 돌린다”는 사용 장면을 내세우면서
기본 보호 규칙은 Linux 서버의 경로를 기준으로 쓴 셈이다.
데스크톱 사용자를 늘리려면 운영체제별 기본값이 필요하다.

### 단일 프로세스라는 원칙은 이미 흔들리고 있다

ADR 001은 프로세스 하나와 SQLite면 충분하다고 했지만,
9월 23일 `1.0.2b1` 변경 이력에는
`octop run --workers N`처럼 워커를 여럿 띄우거나
CLI와 서비스가 동시에 쓸 때 `database is locked`가 나던 문제를
`BEGIN IMMEDIATE`로 고쳤다는 항목이 있다.
여러 워커로 띄우는 옵션이 이미 있다는 뜻이다.
ADR이 말한 “프로세스가 모든 상태를 가지므로 안전한 전역 DI 컨테이너”라는 전제가
워커가 둘 이상일 때도 성립하는지는 문서에 없다.

문서끼리도 어긋난다.
README의 구조도는
`UserManager` 아래에 사용자마다 `HarnessAgentManager`를 두지만,
`docs/architecture.md`는 사용자별 `AgentManager`가 더는 없고
프로세스 전역 레지스트리 하나가 행 단위로 소유권을 검사한다고 적는다.
사용자 격리를 셀링 포인트로 내세우는 제품에서
격리가 어느 층에서 이루어지는지를 두 문서가 다르게 설명한다.
코드는 후자에 가까워 보이지만, 처음 읽는 사람은 README를 먼저 본다.

### “디지털 생명체”라는 수사는 제품 설명을 흐린다

README 첫 문단은 Octop을
“단순한 도구가 아니라 병렬로 움직이는 디지털 생명체”라고 부른다.
HN에서 prologic은 이 문장을 그대로 인용하며,
정말 그런지, 이 “생명체”가 자기에게 무엇을 해 줄 수 있는지 되물었다.[^prologic]
HN 스레드에서 제품에 대해 나온 질문은
이것과 기억 저장 위치를 묻는 질문 둘뿐이었다.

정작 README 뒷부분은 구체적이다.
단일 프로세스, SQLite, 사용자별 작업 공간, 채널별 자격 증명 표가 다 들어 있다.
그런데 첫 문단이 이 구체성 대신 과장된 비유로 시작하니,
처음 본 개발자에게 남는 인상이 수사 쪽으로 기운다.
가족과 작은 팀이 쓰는 비서라는 GN 제목이 오히려 제품을 더 정확히 설명한다.

## 인사이트

### 셀프 호스팅 비서의 다음 경쟁은 “누가 승인 버튼을 누르는가”다

에이전트가 한 사람의 도구일 때는 승인을 끄는 것이 그 사람의 선택이다.
여러 사람이 한 서버를 쓰는 순간 이 문제의 성격이 바뀐다.
관리자가 승인을 꺼 두면
아이의 계정에 붙은 에이전트도 경고만 남기고 셸 명령을 실행한다.
Octop은 사용자별 권한 템플릿과 `terminal` 같은 권한 항목을 두었지만,
도구 승인 정책은 사용자별이 아니라 관리자가 정하는 전역 설정에 가깝다(해석).

가정용 공유 서버라는 모델이 퍼지면 필요한 것은 사용자별 위험 한도다.
누구의 에이전트가 어떤 명령을 승인 없이 실행할 수 있는지,
승인 요청이 누구에게 가는지가 정해져야 한다.
운영체제가 사용자 계정과 `sudo` 권한을 나눈 것과 같은 과정을
에이전트 플랫폼이 다시 밟게 될 것이다.

### 단일 프로세스 설계는 성공하는 순간 부채가 된다

ADR 001은 이음새가 `infra/gateway/processor.py`에 “부분적으로 보인다”며
나중에 워커를 떼어 낼 여지를 남겨 두었다.
이런 설계는 작게 시작하는 제품에서 거의 항상 옳다.
문제는 별 7천 개를 넘긴 저장소가 로드맵에 관리형 에이전트,
클라우드와 엣지 연속 실행, 인스턴스 간 브리지를 함께 올려 두었다는 점이다.

인스턴스 간 브리지 설계 문서를 보면 상대 Octop의 비밀번호를
자동 재연결을 위해 암호화해 저장하고,
NAT 뒤의 집 서버에 클라우드가 WebSocket 터널로 들어온다.
가정용 단일 프로세스와 클라우드 연합이라는 두 방향이
같은 코드베이스 안에서 자라는 중이다.
SQLite 잠금 오류를 고친 기록은
그 긴장이 이미 코드에 나타나기 시작했다는 신호로 읽힌다(해석).

### 오픈소스 비서의 “로컬”은 데이터 위치이지 의존성 위치가 아니다

HN에서 fetchmark는 기억이 로컬에 저장되는지,
Tencent 클라우드가 필요한지를 물었고,[^fetchmark]
글을 올린 tomislavpet은 문서로 보면 전부 로컬이라고 답했다.[^tomislavpet]
문서와 코드로 보면 맞는 답이다.
제어용 DB와 에이전트 기억은 기본적으로 `~/.octop/` 아래 SQLite에 있다.

다만 “로컬”의 의미는 좁게 읽어야 한다.
외부 모델 API를 고르면 대화는 그 제공자에게 간다는 점은 GN 요약도 짚었다.
여기에 더해 권장 설치 경로는
Tencent COS 버킷의 셸 스크립트를 `bash`로 바로 실행하고,
패키지 미러도 Tencent와 Aliyun을 먼저 쓴다.
선택 기능인 Langfuse 관측도 켜면 외부로 추적 정보를 보낸다.
데이터는 내 기계에 있지만, 설치와 갱신의 신뢰 경로는 배포자에게 있다.
가족의 메신저와 셸을 맡길 서버라면 이 경로를 따로 검토해야 한다.

### 별 수보다 릴리스 속도가 이 프로젝트의 상태를 더 잘 말한다

저장소가 만들어진 지 두 달여 만에 `v1.0.0`이 나왔고,
그 뒤 3주 동안 정식 1개와 베타 6개가 이어졌다.
`1.0.2b1` 변경 이력 하나에만
승인 상태, 시간대, SQLite 잠금, 지식베이스 폴더 삭제처럼
데이터 정합성에 걸린 수정이 여럿 들어 있다.
지식베이스 폴더를 지울 때 `LIKE` 와일드카드 때문에
이름이 비슷한 다른 폴더까지 지워지던 버그도 그중 하나다.

이는 개발이 활발하다는 뜻이면서,
동시에 아직 데이터 계층이 다듬어지는 중이라는 뜻이다.
README가 `octop update` 전에 `octop backup`을 먼저 하라고 권하는 것도
그래서일 것이다.
가족 전체의 기억과 일정을 맡기려는 사람에게는
별 수보다 이 변경 이력이 더 중요한 자료다.
셀프 호스팅 작업 공간인 Odysseus(`ai-tool/odysseus-ai-workspace.md`)나
자기 학습형 에이전트 Hermes Agent(`ai-tool/hermes-agent.md`)와 견줄 때도
기능 목록보다 데이터 계층의 안정성과 기본 보안값을 먼저 비교하는 편이 낫다.
