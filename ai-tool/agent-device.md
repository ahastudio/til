# agent-device: 코딩 에이전트가 실제 기기에서 앱을 검증하게 하는 CLI

<https://agent-device.dev/>

<https://github.com/callstack/agent-device>

## 소개

Callstack이 만든 MIT 라이선스 CLI 도구다.
한 줄 소개는 “코딩 에이전트가 자기가 바꾼 것을
실행 중인 앱에서 직접 검증하게 하라”이다.
iOS, Android, HarmonyOS, tvOS, Android TV, Vega Virtual Device(VVD)를 통한
Amazon Vega OS TV, 웹, macOS, Linux에서
에이전트가 앱을 조사하고 조작하고 검증할 수 있게 한다.
지원되는 곳에서는 토큰 효율적인 접근성 스냅샷을 읽고,
ref나 셀렉터로 요소를 찾고, 기기 동작을 실행하고, 리뷰용 증거를 저장한다.

핵심 발상은 Vercel의 agent-browser에서 가져온 inspect-act-verify 절차를
모바일과 TV와 데스크톱 앱으로 옮긴 것이다.
에이전트가 결과를 읽고 다음 명령을 스스로 고르며,
CLI는 그 명령을 실행하고 요청받으면 증거를 남긴다.
`--platform web`을 쓰면 같은 세션과 리플레이 체계 안에서
agent-browser를 그대로 돌린다.

2026년 1월 30일에 만들어진 저장소로,
2026년 8월 10일 기준 4,036개의 스타와 247개의 포크를 갖고 있었고,
열흘 뒤에는 4,150개의 스타와 259개의 포크와 59개의 열린 이슈다.
최신 릴리스는 8월 17일의 `v0.20.9`이며 8월 초에만
`v0.20.3`부터 `v0.20.7`까지 나왔다.
Callstack 외에 JPMorgan Chase, Expensify, Shopify, Kindred, Total Wine & More,
LegendList, HerLyfe, App & Flow 등이 사용 중인 것으로 소개돼 있다.

문서는 사람용 문서 사이트와 별도로 에이전트가 읽는
`llms-full.txt`를 함께 제공한다.
README가 참조하는 외부 자료로는 EAS Workflows로 Expo 앱용
AI QA 에이전트를 만드는 Expo 블로그 글, Callstack이 쓴 소개와
Vercel Eve 기반 모바일 QA 에이전트 구축기,
그리고 모바일 앱 자동화를 위해 agent-device를 최적화한 과정을 다룬 글이 있고,
영상 세 편이 함께 걸려 있다.

## 사용법

Node.js 22.12 이상이 필요하고, 웹 자동화에는 24 이상이 필요하다.
설치 후 `doctor`로 환경을 점검하는 것을 권한다. README는 에이전트에게 CLI를
넘기기 전에 사람이 먼저 `agent-device doctor`를 돌려보라고 명시한다.

```bash
npm install -g agent-device@latest
agent-device doctor
agent-device help workflow
```

iOS 기본 연락처 앱에 항목을 추가하는 예시가 대표 워크플로다.

```bash
# 세션 시작
agent-device open Contacts --platform ios

# 화면 조사. ref는 실행마다 달라진다
agent-device snapshot -i
# @e2 [button] "Add"

# ref로 조작하고 UI가 안정될 때까지 대기
agent-device press @e2 --settle
# diff에 다음이 포함된다:
# + @e7 [text-field] "First name"

agent-device fill @e7 "Ada" --settle
# 다음 diff는 바뀐 값과 현재 ref를 보여준다:
# - @e7 [text-field] "First name"
# + @e14 [text-field] "Ada"
# = @e15 [text-field] "Last name"

# 증거를 남기고 세션 종료
agent-device screenshot ./contact-form.png
agent-device close
```

여기서 중요한 규약이 두 가지 있다.
첫째, ref는 항상 최신 출력의 것만 써야 한다.
이전의 `@eN`이 여전히 같은 요소를 가리킨다고 가정하면 안 된다.
`--settle`을 붙인 명령 뒤에는 그 diff에 나온 ref를 쓰고,
diff에 필요한 것이 없을 때만 스냅샷을 다시 찍는다.
둘째, 스냅샷은 앱의 접근성 트리를 쓴다.
레이블과 role과 test ID가 명확할수록 에이전트 실행이 안정적이다.

`--settle`은 `scroll`과 `back`에서도 똑같이 동작하므로,
스크롤한 뒤 관찰하는 것과 뒤로 간 뒤 관찰하는 것도 호출 한 번으로 끝난다.
왕복 횟수를 줄이는 이 설계가 뒤에서 다룰 토큰 효율성과 직결된다.

## 주요 기능

에이전트가 할 수 있는 일은 네 갈래로 정리돼 있다.

- **상태 조사** — 접근성 스냅샷, ref, 셀렉터, React Native 컴포넌트 트리
- **UI 조작** — 탭과 프레스, 필드 입력, 스크롤, 제스처, 대기, 상태 단언,
  알림 처리
- **실패 진단** — 스크린샷, 비디오, 로그, 트레이스, 네트워크 데이터,
  성능 샘플, 크래시 상세, React 프로파일
- **워크플로 반복** — 동작한 단계를 `.ad` 스크립트로 저장해 로컬이나 CI에서
  재생.
  필요하면 엄격한 Maestro YAML로 내보내기

지원 대상은 네이티브 iOS·Android 앱과 React Native, Expo, Flutter 앱이다.
대상별로 사용 가능한 명령과 증거 종류는 다르다.
Vega OS 지원은 초기 단계로 VVD 전용이며
탐색, 앱 생명주기, TV 리모컨 제어까지만 된다.
실제 Fire TV 기기와 캡처, 셀렉터 백엔드는 아직 지원하지 않는다.

## 아키텍처

세션 안에 기기 상태를 유지하면서 플랫폼별 백엔드에 명령을 보내는 구조다.

| 대상      | 백엔드               |
| --------- | -------------------- |
| iOS, tvOS | XCTest               |
| Android   | ADB + 스냅샷 헬퍼    |
| HarmonyOS | HDC + ArkUI `uitest` |
| Vega VVD  | Vega CLI / VDA       |
| macOS     | 로컬 헬퍼            |
| Linux     | AT-SPI               |
| Web       | agent-browser        |

HarmonyOS는 연결된 실기기와 DevEco 에뮬레이터에서 HDC와 ArkUI `uitest`를 쓴다.
어디까지 되는지는 `capabilities --platform harmonyos`로 확인하도록 안내하는데,
이 명령이 증거로 뒷받침되는 명령 부분집합을 돌려준다.

Node.js 앱에서는 타입이 붙은 클라이언트나 공개 서브패스를 쓸 수 있다.
`agent-device/android-adb`는 Android ADB 프로바이더 인터페이스와
logcat, 클립보드, 키보드, 앱 관련 헬퍼, 포트 리버스 관리를 제공한다.

실행 위치는 세 가지로 안내된다.
로컬(시뮬레이터·에뮬레이터·실기기), CI/CD(리플레이 스크립트로 PR 검증),
클라우드/원격(Agent Device Cloud 또는 원격 프로파일)이다.
Cursor, Codex, Claude Code, Windsurf 같은 에이전트 터미널에서 실행하도록
스킬과 규칙과 MCP 도구 설정을 별도 문서로 안내한다.

## 분석

### 이 도구의 진짜 주장은 자동화가 아니라 피드백 루프다

이름만 보면 모바일 자동화 도구로 읽히지만,
README가 가장 힘주어 말하는 것은 “에이전트가 자기 변경을 검증하게 하라”이다.
저장소가 싣고 있는 다이어그램의 제목도 “agentic development loop”다.
사람이 과제를 주고, 에이전트가 코드를 쓰고 리뷰하고,
agent-device가 모바일 앱을 검증하고, PR에 증거가 붙고,
버그와 성능 문제가 수정으로 이어지는 순환이다.

이 위치 설정이 중요한 이유는
코딩 에이전트의 가장 큰 약점을 정확히 겨누기 때문이다.
에이전트는 코드를 쓸 수 있지만 그 코드가 실제로 동작하는지 볼 수 없다.
웹에서는 이 문제가 이미 상당히 풀렸다.
Playwright와 agent-browser 계열 도구가 있고,
브라우저는 프로그래밍 가능한 인터페이스를 오래전부터 제공해 왔다.
모바일에서는 그 간극이 훨씬 컸다.
시뮬레이터를 띄우고 앱을 빌드하고 화면을 조작하는 일은
사람의 눈과 손을 전제로 설계된 절차였다.

그래서 이 도구의 가치는 “자동화 스크립트를 대신 써준다”가 아니다.
에이전트가 코드를 고친 뒤 실제 화면에서 결과를 확인하고,
틀렸으면 다시 고치는 닫힌 루프를 모바일에서도 가능하게 만드는 것이다.
FAQ가 Appium, Detox, Maestro와의 차이를 설명하며
“에이전트가 실행 시점에 앱 상태를 읽고 각 명령을 고른다”고 말하는 대목이
이 차이를 압축한다.
저쪽은 테스트 스위트를 작성하고 유지보수하는 도구이고,
이쪽은 실행 중에 판단하는 도구다.

### 접근성 트리를 선택한 것이 설계의 중심이다

스냅샷이 앱의 접근성 트리를 쓴다는 결정은 사소해 보이지만
이 도구의 성격을 대부분 결정한다.
대안은 스크린샷을 멀티모달 모델에 넣어 화면을 이해시키는 방식이다. 실제로 많은
컴퓨터 사용 에이전트가 그렇게 한다.

접근성 트리를 쓰면 얻는 것이 분명하다.
README가 “토큰 효율적인 접근성 스냅샷”이라고 표현하듯
텍스트 트리는 이미지보다 훨씬 적은 토큰을 쓴다.
요소를 `@e2` 같은 ref로 안정적으로 지목할 수 있고,
변경분을 diff로 보여줄 수 있다.
실제로 `--settle` 뒤에 나오는 출력이 `+`, `-`, `=` 기호가 붙은 diff인 것은
이 구조 덕분이다.
화면 전체를 다시 설명하는 대신 바뀐 부분만 전달하는 것은
긴 세션에서 컨텍스트를 아끼는 핵심 장치다.

대신 치르는 비용도 있다.
접근성 트리는 앱이 성실하게 채워 놓았을 때만 쓸모가 있다.
README가 “명확한 레이블과 role과 test ID가 에이전트 실행을
더 안정적으로 만든다”,
“접근성 데이터가 부실할 때는 스크린샷과 비디오를 쓰라”고
두 번에 걸쳐 당부하는 것은 이 의존성을 인정하는 것이다.
즉 이 도구의 성능은 도구 자체보다 대상 앱의 접근성 품질에 더 크게 좌우된다.

### 증거 생성이 기능 목록의 절반을 차지한다

기능 목록에서 눈에 띄는 것은 진단·증거 항목의 밀도다.
스크린샷, 비디오, 로그, 트레이스, 네트워크 데이터, 성능 샘플, 크래시 상세,
React 프로파일까지 나열된다.
조작 기능보다 관찰 기능이 더 촘촘하다.

이건 대상 사용자가 누구인지를 드러낸다.
개인 개발자가 앱을 잠깐 조작하려는 용도라면 이만큼의 증거 수집은 과하다.
PR에 증거를 첨부하고, CI에서 재생하고,
리뷰 대상으로 남기는 조직이 이 기능들을 쓴다.
“save evidence for review”라는 표현이 README에 반복해서 나오는 것도
같은 맥락이다.

여기서 이 도구가 푸는 문제의 두 번째 층이 보인다.
에이전트가 검증했다고 말하는 것을 사람이 어떻게 믿을 것인가.
에이전트의 자기 보고는 신뢰하기 어렵고,
실제로 코딩 에이전트가 “테스트를 통과했다”고 말하고
실제로는 아닌 경우는 흔하다.
스크린샷과 비디오와 로그는 그 보고를 검증 가능한 것으로 바꾼다.
[에이전트 하네스 엔지니어링](../agentic-coding/agent-harness-engineering.md)에서
다루는 문제 — 에이전트에게 무엇을 보게 하고 무엇을 증명하게 할 것인가 — 의
모바일 판이다.

### `.ad` 스크립트는 탐색을 자산으로 바꾸는 장치다

에이전트가 실행 시점에 판단한다는 것은
매번 결과가 달라질 수 있다는 뜻이기도 하다.
비결정적인 절차는 CI에 넣기 어렵다.
`.ad` 스크립트는 이 문제에 대한 답이다.
동작한 단계를 저장해 로컬이나 CI에서 재생하고,
필요하면 Maestro YAML로 내보낸다.

구조를 보면 두 단계 모델이다.
1단계에서 에이전트가 탐색적으로 경로를 찾고,
2단계에서 그 경로를 고정된 스크립트로 굳힌다.
탐색은 비싸고 느리고 비결정적이지만 한 번만 하면 되고,
재생은 싸고 빠르고 결정적이다.

이 분리는 기존 E2E 테스트 도구가 풀지 못한 부분을 건드린다.
Appium이나 Maestro의 비용은 실행이 아니라 작성과 유지보수에 있었다.
UI가 바뀔 때마다 셀렉터를 고치는 일이 반복됐다.
에이전트가 탐색 단계를 맡으면 그 작성 비용이 내려가고,
깨진 스크립트를 고치는 일도 다시 탐색시키는 것으로 대체할 수 있다.
FAQ가 Appium·Detox·Maestro와 “경쟁”이 아니라
“보완”이라고 말하는 근거가 여기 있다.

## 비평

### 접근성 트리 의존은 가장 필요한 곳에서 가장 약하다

README는 접근성 데이터가 부실하면 스크린샷을 쓰라고 안내한다.
합리적인 대비책처럼 보이지만,
이 조언은 도구의 핵심 가치가 사라지는 지점을 가리킨다.
ref 기반 조작, diff 출력, 토큰 효율성이 전부 접근성 트리에서 나오기 때문이다.
스크린샷으로 후퇴하면 남는 것은 좌표를 찍는 일반적인 컴퓨터 사용 에이전트이고,
그건 이 도구가 아니어도 된다.

문제는 접근성 품질이 나쁜 앱일수록 에이전트 검증이 더 필요하다는 점이다.
접근성을 잘 갖춘 팀은 대체로 테스트 문화도 좋고 test ID도 잘 붙어 있다.
접근성이 부실한 앱은 대체로 레거시이고, 테스트가 없고, 수동 QA에 의존한다.
자동화의 편익이 가장 큰 쪽이 이 도구를 가장 못 쓰는 구조다.

Flutter를 지원 목록에 넣은 것도 이 각도에서 보면 단서가 된다.
Flutter는 자체 렌더링 엔진으로 화면을 그리기 때문에
네이티브 접근성 트리에 노출되는 정보가 위젯 구조와 일대일로 대응하지 않는다.
README는 “대상별로 명령과 증거가 다르다”는 문장으로 이 차이를 뭉갠다.
어떤 대상에서 어느 수준까지 되는지는 별도 문서를 봐야 알 수 있고,
지원 목록만 읽으면 모두 동등하게 지원되는 것처럼 읽힌다.

### 지원 플랫폼의 폭은 성숙도를 가린다

지원 목록은 인상적이다.
iOS, Android, HarmonyOS, tvOS, Android TV, Vega OS, 웹, macOS, Linux.
그런데 이 목록의 항목들은 완성도가 전혀 같지 않다.

Vega OS는 README 스스로 밝히듯 VVD 전용이고
탐색과 앱 생명주기와 리모컨 제어까지만 된다.
실기기도 캡처도 셀렉터도 안 된다.
웹은 “basic `--platform web` support”라고 표현되며
실제로는 agent-browser를 같은 세션에서 돌리는 래퍼다.
macOS는 “로컬 헬퍼”, Linux는 AT-SPI인데 이 둘이 iOS의 XCTest 백엔드만큼
검증됐다고 볼 근거는 제시되지 않는다.

이건 흔한 패턴이지만 이 도구에서는 특히 문제가 된다.
에이전트에게 넘기는 도구이기 때문이다.
사람이 쓰는 CLI라면 안 되는 기능을 만났을 때 금방 알아채고 다른 방법을 찾는다.
에이전트는 명령이 실패하면 다른 명령을 시도하고,
그게 또 실패하면 또 다른 것을 시도하면서 토큰과 시간을 태운다.
어느 플랫폼에서 무엇이 되는지가 명확하지 않을수록 이 낭비가 커진다.
README가 “설치된 CLI의 help가 현재 동작을 정의한다”고 명시한 것은 정직하지만,
동시에 문서가 실제 동작을 보증하지 않는다는 뜻이기도 하다.

HarmonyOS 항목에 붙은 `capabilities --platform harmonyos`가
이 문제에 대한 부분적인 답이다.
플랫폼별로 증거가 뒷받침되는 명령 부분집합을
런타임에 물어볼 수 있게 한 것이고,
에이전트가 되는 것과 안 되는 것을 시행착오 대신 조회로 알 수 있다는 뜻이다.
지원 목록의 폭이 아니라 런타임 조회를 진실의 출처로 삼는 이 방향은 옳다.

다만 이 장치가 HarmonyOS 설명에만 등장한다는 점이 걸린다.
가장 최근에 추가된 플랫폼에서 문제를 겪고 대책을 만든 것으로 읽히는데,
같은 불확실성은 Vega OS와 macOS와 Linux에도 그대로 있다.
그리고 `capabilities`가 돌려주는 것이 명령 목록이라면 여전히 절반이다 —
에이전트에게 필요한 것은 이 명령이 있는가가 아니라
이 앱의 이 화면에서 이 명령이 쓸 만한 결과를 주는가이기 때문이다.
접근성 데이터가 부실한 앱에서 `snapshot`은 존재하지만 쓸모없고,
그 구분은 어떤 조회로도 나오지 않는다.

### 사용 기업 목록은 도입 깊이를 말하지 않는다

JPMorgan Chase, Expensify, Shopify가 사용자 목록에 있다.
이건 강력한 신호처럼 보이지만, 무엇을 얼마나 쓰는지는 나오지 않는다.

목록의 근거로 걸린 링크들을 보면 성격이 드러난다.
Expensify는 Callstack 자사 블로그의 사례 글이고,
Shopify와 LegendList는 개인 트윗이다.
트윗 한 건은 그 회사의 한 엔지니어가 써봤다는 증거이지
조직이 도입했다는 증거가 아니다.
6개월 된 저장소에서 대기업 이름이 목록에 오르는 통상적인 경로가 이것이다.

Callstack이 React Native 생태계의 주요 컨설팅 기업이라는 점도 함께 봐야 한다.
목록에 오른 회사들 상당수가 React Native를 쓰고,
그중 일부는 Callstack의 고객일 가능성이 높다.
그렇다면 이 목록은 독립적인 채택 증거라기보다 기존 관계망의 반영에 가깝다.
도구가 나쁘다는 뜻이 아니라, 이 목록으로 성숙도를 판단하면 안 된다는 뜻이다.

### 위임할 수 있는 계층과 팔 수 있는 계층이 같은 표에 있다

실행 위치를 안내하는 표의 세 번째 줄이 원격 경로를 다룬다.
Linux 러너와 관리형 기기와 원격 작업이 대상이고,
방법으로 원격 프록시 설정과 기기 클라우드 연결과
Callstack 문의가 나란히 제시된다.
연결 가능한 기기 클라우드로 BrowserStack과
AWS Device Farm과 Limrun을 이름으로 든다.

이 구성이 이 프로젝트의 위치를 정확히 보여 준다.
기기를 소유하는 계층은 남의 것을 쓰고,
그 위에서 세션과 선택자와 증거와 재생을 통일하는 계층을 자기가 갖는다.
FAQ의 한 항목이 그 계층을 명시적으로 개방한다 —
타입이 붙은 Node.js 클라이언트가 같은 런타임 위의 공개 표면이므로
그것으로 자기 에이전트나 QA 제품을 만들 수 있고,
Node.js API와 AI SDK와 Eve 가이드에서 시작하라고 안내한다.

즉 이 도구는 최종 제품이면서 동시에 플랫폼을 자칭한다.
CLI와 MCP 서버와 타입 클라이언트가
같은 런타임의 세 입구라는 설명이 그 구조이며,
셋 사이에서 세션과 기기 소유권과 증거와 CI 워크플로와 클라우드 경로가
일관되게 유지된다고 적는다.
이 설계는 실제로 값이 있다 — 입구를 바꿔도 학습한 조작이 그대로 재사용된다.

다만 플랫폼을 자칭하는 순간 확인해야 할 것이 하나 늘어난다.
이 런타임 위에 제품을 올린 쪽과 이 런타임을 만든 쪽이 같은 회사이고,
그 회사가 표의 세 번째 줄에서 팀 QA 문의를 받는다.
[스크래핑 마켓플레이스에서 관찰한 것과 같은 구도](../data/apify.md)이며,
차이는 여기서 중개되는 것이 스크래퍼가 아니라 QA 자동화라는 점이다.
그 구도에서 제3자 제품과 자사 제품이 경쟁하게 될 때
런타임의 우선순위가 어느 쪽을 향하는지가 문서에 없다.

### 상업 제품으로 이어지는 경로가 문서에 섞여 있다

MIT 라이선스 오픈소스이지만,
실행 위치를 안내하는 표의 세 번째 줄은 Agent Device Cloud라는
유료 서비스와 “팀 QA는 Callstack에 문의”로 이어진다.
이 구조 자체는 흔하고 문제될 것이 없다.
오픈소스로 배포하고 관리형 서비스로 수익을 내는 모델이다.

짚어둘 부분은 그 경로가 자연스럽게 배치돼 있다는 점이다.
로컬에서 시작해 CI로 넘어가면 GitHub Actions 템플릿은 “coming soon”이고,
EAS 워크플로 템플릿은 별도 저장소에 있다.
CI를 제대로 붙이려는 팀이 마주하는 마찰이 클라우드 쪽으로 흐르도록 되어 있다.

에이전트 도구에서 이 구조는 일반적인 오픈코어보다 결과가 무거울 수 있다.
검증 루프가 개발 프로세스에 들어가면 그 실행 환경을 바꾸기 어려워지기 때문이다.
`.ad` 스크립트와 Maestro YAML 내보내기가 있어 이론적으로는 이탈 경로가 있지만,
실제 종속은 스크립트 포맷이 아니라 증거 수집과 리포팅 파이프라인에서 생긴다.
그쪽 형식과 저장소에 대한 표준은 문서에 명시돼 있지 않다.

## 인사이트

### 에이전트 도구의 병목은 실행이 아니라 관찰이다

이 도구를 보면 코딩 에이전트 도구 설계의 무게중심이 어디로 옮겨갔는지가 보인다.
초기 도구들은 에이전트가 무엇을 할 수 있는가에 집중했다.
파일을 쓰고, 명령을 실행하고, API를 호출하는 능력이다.
agent-device의 기능 목록에서 조작은 한 줄이고 관찰과 증거가 세 줄이다.

이유는 단순하다. 실행은 이미 충분히 되고, 안 되는 것은 결과 확인이다.
에이전트가 코드를 고치는 능력은 2년 전에도 있었다.
고친 것이 맞는지 스스로 아는 능력이 없었을 뿐이다.
그래서 최근 도구들은 “무엇을 할 수 있게 할 것인가”보다
“무엇을 볼 수 있게 할 것인가”를 설계 문제로 다룬다.

이 전환은 도구의 좋고 나쁨을 가르는 기준도 바꾼다.
좋은 에이전트 도구는 기능이 많은 도구가 아니라
관찰 결과를 토큰 효율적이고 모호하지 않게 돌려주는 도구다.
agent-device의 diff 출력이 그 예다.
화면 전체를 다시 설명하는 대신 바뀐 부분만 `+`, `-`, `=`로 표시하는 것은
기능 추가가 아니라 출력 형식의 설계다.
그리고 그 설계가 이 도구의 실질적 경쟁력이다.

앞으로 이 층에서 표준화 압력이 커질 것으로 보인다.
지금은 브라우저용 agent-browser, 모바일용 agent-device처럼
도메인별 도구가 각자 관찰 포맷을 정의한다.
에이전트가 여러 도메인을 오가며 일하게 되면
이 포맷들이 서로 달라 생기는 비용이 드러나고,
접근성 트리 스냅샷 같은 표현이 사실상의 공통 규약으로 굳어질 가능성이 있다.

### 접근성 투자가 개발 생산성 투자로 바뀐다

접근성(a11y)은 오랫동안 도덕적 의무이자 규제 준수 항목으로 다뤄졌다.
장애가 있는 사용자를 위한 것이고, 하면 좋지만 우선순위에서 밀리고,
법이 요구할 때 비로소 예산이 붙는 종류의 일이었다.

이 도구는 그 계산을 바꾼다.
접근성 레이블이 잘 붙은 앱은 에이전트가 검증할 수 있고,
그렇지 않은 앱은 못 한다.
접근성 품질이 곧 자동화 가능성이고, 자동화 가능성이 곧 개발 속도다.
README가 “명확한 레이블과 role과 test ID가
에이전트 실행을 더 안정적으로 만든다”고 쓴 문장은 접근성 가이드가 아니라
성능 튜닝 안내로 읽힌다.

역사적으로 비슷한 전환이 있었다.
시맨틱 HTML은 처음에 접근성과 표준 준수를 위한 것이었지만,
검색 엔진이 그 구조를 읽기 시작하면서 SEO 문제가 됐다.
도덕적 명분으로는 움직이지 않던 조직이 트래픽 앞에서는 움직였다.
접근성 트리를 읽는 에이전트가 늘어나면 같은 일이 앱에서 반복될 수 있다.

이 전환에는 그림자도 있다.
동기가 사람에서 기계로 옮겨가면 최적화 대상도 옮겨간다.
에이전트가 잘 읽도록 최적화된 접근성 트리가
스크린 리더 사용자에게도 좋으리라는 보장은 없다.
test ID를 남발하거나 기계가 파싱하기 좋은 형태로 레이블을 다는 것은
실제 사용자 경험과 어긋날 수 있다.
SEO가 시맨틱 HTML을 확산시키는
동시에 키워드 스터핑을 만들어낸 것과 같은 구조다.

### 탐색과 재생의 분리는 테스트 경제학을 바꾼다

`.ad` 스크립트가 만드는 두 단계 구조 — 비싼 탐색 한 번, 싼 재생 여러 번 — 는
E2E 테스트의 비용 구조를 근본적으로 다시 짠다.

기존 E2E 테스트가 외면받은 이유는 실행 비용이 아니라 유지보수 비용이었다.
UI가 바뀌면 셀렉터가 깨지고, 깨진 테스트를 고치는 일은 지루하며,
고치지 않은 테스트는 무시되다가 결국 삭제된다.
테스트 피라미드가 E2E를 꼭대기의 얇은 층으로 그린 것은 이 비용 때문이었다.

에이전트가 탐색을 맡으면 이 계산이 달라진다.
깨진 스크립트를 고치는 대신 “이 화면에서 로그인해서 장바구니에 담아라”라는
의도만 남겨두고 경로는 매번 다시 찾게 할 수 있다.
테스트가 절차가 아니라 의도로 표현되면 UI 변경에 훨씬 강해진다.

그런데 여기에 조용한 함정이 있다.
의도 수준으로 표현된 테스트는 무엇이 회귀인지 판정하기 어려워진다.
버튼 위치가 바뀌었을 때 에이전트가 알아서 찾아내는 것은 편리하지만,
그 변경이 의도된 것인지 사고인지는 구분하지 않는다.
기존 E2E가 깨지는 것은 비용이었지만 동시에 신호였다.
유연한 테스트는 그 신호를 잃는다.

그래서 두 단계 구조를 실제로 쓸 때 판단해야 할 것은 어느 층을 고정할 것인가다.
자주 바뀌는 화면은 탐색에 맡기고 계약에 해당하는 흐름은
스크립트로 굳히는 식의 구분이 필요하다.
이 구분은 도구가 대신해 주지 않는다.
[AI 시대의 TDD](../agentic-coding/tdd-in-ai-era.md)에서
논의되는 문제와 같은 질문이 여기서도 나온다.
무엇을 기계에 맡기고 무엇을 사람이 고정해 둘 것인가.

### 모바일 QA 조직은 증거 심사 조직으로 바뀐다

이 도구가 성공적으로 확산되면 조직에서 먼저 바뀌는 것은
테스트 자동화 담당자가 아니라 QA 조직의 일 자체다.

지금 모바일 QA의 상당 부분은 수동 실행이다.
앱을 켜고, 시나리오를 따라가고, 이상한 것을 발견하고,
재현 경로를 정리해 이슈로 남긴다.
agent-device가 하는 일이 정확히 이것이다.
조작하고, 관찰하고, 스크린샷과 로그와 크래시 상세를 증거로 남긴다.

그러면 사람에게 남는 일은 실행이 아니라 판정이다.
에이전트가 100개의 흐름을 돌려 증거를 쌓았을 때,
그중 무엇이 진짜 문제인지 가려내는 일이다.
이건 앞서 다른 맥락에서 반복해서 나온 구조와 같다.
생성이 싸지면 판별이 병목이 된다.

QA 조직에는 특히 곤란한 전환이다.
판정 능력은 수동 테스트를 오래 해본 경험에서 나오는데,
그 경험을 쌓을 경로가 자동화로 사라진다.
게다가 증거의 양이 늘어나면 판정 자체가 형식화되기 쉽다.
스크린샷 100장을 성실히 보는 사람은 오래가지 않고,
