## 요약

mtsoukalos.eu 블로그가 2026년 11월에 올린 글이다.
글쓴이는 책 Systems Programming with Zig를 쓰는 사람이고, 이 글은 앞서 쓴 Why Zig Over Rust for Systems Programming의 후속이라고 밝힌다.
Rust 글이 안전과 의식(ceremony)의 비용에 관한 것이었다면, C 글은 Zig와 C가 같은 것을 원한다는 점에서 다르다.
둘 다 가비지 컬렉터가 없는 작은 언어이고 기계가 하는 일에 가깝다는 것이다.
그래서 이 글은 C를 완전히 다른 것으로 버리자는 글이 아니라, C에서 시간을 먹는 부분을 Zig가 어떻게 다루는지를 보여 주는 글이라고 한다.
코드는 Mac에서 Zig 0.17과 clang으로 컴파일했다고 적는다.

### C가 잘하는 것

글쓴이는 C를 가장 좋아하는 언어라고 말한다.
C는 유닉스의 언어이고, 커널과 C 라이브러리와 다른 언어가 결국 호출하는 시스템 라이브러리 대부분이 C로 쓰여 있으며 man 페이지도 C 원형으로 설명한다.
1990년대 C 프로그램이 지금도 컴파일되고, 거의 모든 CPU용 C 컴파일러가 있다고 한다.
Zig는 이를 대체하려 하지 않고 C 라이브러리를 직접 부르며 필요하면 C ABI를 쓴다.
그런데도 새 코드를 C로 쓰고 싶지 않다는 것이 글의 출발점이다.

### 여섯 가지 비교

첫째는 goto 없는 정리(cleanup)이다.
자원을 여러 개 얻고 중간에 실패하면 역순으로 풀어야 하는 함수를 C는 goto 라벨로 쓰고, 라벨 순서를 할당 순서와 손으로 맞춰야 한다.
Zig는 `errdefer`를 할당 바로 아래에 두면 오류로 반환될 때만 역순으로 실행된다.
`std.testing.FailingAllocator`가 첫 번째, 두 번째, 세 번째 할당을 차례로 실패시키고 테스트 할당자가 해제되지 않은 메모리를 알려 주므로 모든 실패 경로를 시험할 수 있다고 한다.
C에서 같은 세 경로를 시험하려면 `malloc()` 래퍼나 외부 도구가 필요하다는 것이 글쓴이의 말이다.

둘째는 길이를 아는 슬라이스이다.
C의 배열은 함수로 가면 포인터가 되고 길이는 따로 다닌다.
글의 C 함수는 `<` 대신 `<=`를 쓴 off-by-one 오류가 있고, `{1, 2, 3}`에 대해 Mac에서 `sum = 7`을 출력하며 종료 코드 0으로 끝난다고 한다.
clang의 `-Wall -Wextra`도 프로그램 자신도 불평하지 않는다.
Zig에서는 슬라이스가 길이를 가지므로 같은 실수가 디버그와 safe 모드에서 인덱스 범위 패닉으로 멈추고, 실제 코드에서는 `for (a) |x|`로 쓰면 아예 일어나지 않는다.
문자열도 길이를 가진 바이트 슬라이스라서 `strlen()`이나 종료 바이트 누락 문제가 없다.

셋째는 무시할 수 없는 오류이다.
C는 `-1`이나 `NULL`과 `errno`, 오류 코드 등 함수마다 다른 방식으로 오류를 알리고 확인을 강제하지 않아서, `close()`나 `fclose()`의 반환값을 안 보는 코드가 많다.
Zig는 오류가 반환 타입의 일부이고, 오류를 무시하는 호출은 컴파일되지 않으며 `try`, `catch`, `if`로 다뤄야 한다.

넷째는 전처리기 대신 `comptime`이다.
C 전처리기는 텍스트를 다루고 C를 모른다.
`MAX(a, b)` 매크로는 인자 하나를 두 번 평가하고, 큰 프로젝트에는 운영체제마다 `#ifdef`가 쌓인다.
Zig에서는 컴파일 시점에 도는 코드가 보통의 Zig 코드이고, `#ifdef __linux__` 대신 `if (builtin.os.tag == .linux)`를 쓰면 해당하지 않는 가지를 컴파일러가 버린다.
제네릭 자료구조는 타입을 받아 타입을 돌려주는 함수이다.

다섯째는 덜 놀라운 미정의 동작이다.
C에서 부호 있는 정수 오버플로는 미정의 동작(undefined behavior)이다.
`INT_MAX + 1`은 clang에서 `-2147483648`을 출력하고 0으로 끝나지만, 표준은 컴파일러가 도달할 수 없다고 판단한 코드를 지우는 것까지 허용한다.
Zig는 부호 있는 정수든 없는 정수든 디버그와 safe 모드에서 오버플로를 검사해 패닉으로 멈춘다.
감싸기가 필요하면 `+%`, 최댓값에서 멈추기가 필요하면 `+|`를 쓴다.

여섯째는 Zig가 C 컴파일러라는 점이다.
`zig cc`는 gcc나 clang 대신 쓸 수 있는 C 컴파일러이고 기본으로 교차 컴파일을 한다.
Mac에서 `zig cc -target x86_64-linux-musl`로 정적 리눅스 실행 파일을 설치 없이 만든다고 한다.
디버그 모드의 `zig cc`는 미정의 동작 새니타이저도 켜서 `add()` 예제가 패닉으로 멈춘다.
`build.zig`가 C 파일을 Zig 파일 옆에서 컴파일하므로 C 프로젝트를 한 파일씩 Zig로 옮길 수 있다고 한다.
헤더가 필요한 Zig 코드는 0.17에서 `@cImport()`가 사라져 `zig translate-c`를 쓴다고 쓴다.

### 솔직한 교환

글쓴이는 Zig가 모든 문제를 해결한 C가 아니라고 인정한다.
해제 뒤 사용이나 사라진 스택 변수를 가리키는 포인터는 막아 주지 않는다.
fast와 small 모드에서는 안전 검사 대부분이 꺼져 C처럼 미정의 동작으로 돌아간다.
C는 Zig가 아직 갖지 못한 안정성이 있다고 한다.
Zig 0.17이 나왔을 때 자신의 책 Zig 파일 152개 가운데 35개를 고쳐야 했고, 수십 년 전 C 코드는 지금도 컴파일된다.
C에는 더 많은 도구와 책과 사용자가 있고 Zig가 지원하지 않는 칩의 컴파일러도 있다.
공급업체의 C 컴파일러만 있는 마이크로컨트롤러라면 선택이 정해진다.
결론은 C를 계속 읽겠지만 새 코드는 Zig로 쓰겠다는 것이다.

## 분석

### 중심 주장은 같은 일을 하되 컴파일러가 말없이 통과시키는 실수를 줄이자는 것이다

글의 구조는 일관된다.
C가 말없이 통과시키는 사례 여섯 개를 고르고, 각각에 대해 Zig가 어떻게 컴파일 시점이나 디버그 모드에서 막는지를 보여 준다.
글은 Zig가 C보다 표현력이 크다고 주장하지 않는다.
같은 종류의 코드를 쓰되 실수의 비용을 바꾸자는 것이다.
이 점에서 이 글의 논거는 기능이 아니라 기본값이다.

### 기본값의 차이를 이 문서가 직접 확인했다

글의 C 쪽 주장을 Apple clang 21.0.0에서 그대로 돌려 보았다.
Zig는 설치되어 있지 않아 Zig 쪽은 실행하지 못했다.

| 실험                                      | 결과                                                      |
| ----------------------------------------- | --------------------------------------------------------- |
| off-by-one `sum`, `-Wall -Wextra`, `-O0`  | 경고 없음, `sum = 7`, 종료 코드 0                         |
| 같은 코드, `-O2`                          | `sum = -102924048`, 종료 코드 0                           |
| 같은 코드, `-fsanitize=address,undefined` | 스택 버퍼 오버플로(stack-buffer-overflow)를 보고하고 중단 |
| `INT_MAX + 1`, `-O0`과 `-O2`              | 둘 다 `-2147483648`                                       |
| 같은 코드, `-fsanitize=undefined`         | 부호 있는 정수 오버플로 런타임 오류를 위치와 함께 출력    |
| 같은 코드, `-ftrapv`                      | 실행이 중단됨(종료 코드 133)                              |
| `close()` 반환값 무시, `-Wall -Wextra`    | 경고 없음                                                 |
| 반환값 무시, `[[nodiscard]]`(`-std=c23`)  | 경고 출력                                                 |
| 반환값 무시, `warn_unused_result` 속성    | 경고 출력                                                 |
| 글의 goto 정리 함수, `-Wall -Wextra`      | 경고 없이 컴파일                                          |

여기서 읽을 수 있는 것은 두 가지이다.
첫째, 글쓴이의 주장은 맞다. 기본 옵션의 C는 off-by-one을 조용히 통과시키고, 결과는 최적화 수준에 따라 달라진다.
같은 코드가 `-O0`에서는 7을, `-O2`에서는 쓰레기 값을 돌려준 것이 미정의 동작의 모습이다.
글이 말한 `sum = 7`은 최적화 없는 빌드의 한 가지 결과일 뿐이다.
둘째, 같은 실수를 잡는 도구가 C에도 있다. 새니타이저는 스택 버퍼 오버플로와 정수 오버플로를 위치까지 알려 주고, `-ftrapv`는 중단시키며, `[[nodiscard]]`는 반환값 무시를 막는다.
글이 말하지 않은 것은 이 도구들이 기본값이 아니라는 점이 차이의 핵심이라는 것이다.

### Zig의 장점은 안전 모드가 기본이고 C의 장점은 선택하는 것이라는 구분이다

HN의 가장 위 댓글이 이 점을 겨냥한다.
이런 글은 늘 현대적인 도구를 쓰지 않는 구식 C와 비교하며, 나열된 장점 대부분은 새니타이저, `[[nodiscard]]`, 가변 수정 타입이나 span 타입으로 C에서도 얻을 수 있다는 것이다.
`defer`도 곧 C 컴파일러에 들어올 것이고 자신은 goto 기반 오류 처리가 더 명확하다고 본다고 덧붙인다.[^uecker]
답글은 Zig가 이런 관행을 성공의 구덩이(pit of success)로 만들려는 것이라고 받는다.
현대 C로도 할 수 있지만 일관되게 하려면 원하는 것보다 더 많은 규율이 필요하다는 것이다.[^bunderbunder]
다른 답글은 더 구체적이다.
Zig의 도구와 교차 컴파일 이야기가 좋은 것은 사실이지만 과소평가된 이점은 언어 문화라는 것이다.
Zig에서는 할당자를 함수에 넘기는 것이 관용구여서 모든 라이브러리가 그렇게 동작하지만, C에서도 할 수는 있어도 그렇게 하는 라이브러리는 거의 없어서 서드파티를 쓸 때마다 C의 전통적 방식과 싸워야 한다는 것이다.[^simjnd]
이 두 답글이 글의 결론을 정확히 요약한다.
Zig는 새 언어라서 관행을 처음부터 다시 정할 수 있었다.

## 비평

### 비교 대상이 가장 약한 C이다

글의 C 예제는 모두 도구 없는 기본값의 C이다.
HN의 한 댓글은 첫 예제부터 C를 더 잘 쓸 수 있다고 지적한다.
`calloc`으로 구조체를 0으로 채우고 정리 블록 하나만 두며 `free(NULL)`이 아무 일도 하지 않는다는 점을 이용하면 라벨 세 개가 필요 없다는 것이다.
그 댓글은 이 방식이 포인터 값 0의 비트 표현이 0이라는 가정에 기댄다는 단서도 붙인다.[^asveikau]
그렇다면 글이 보인 라벨 순서 맞추기의 고통은 C의 한 가지 스타일의 문제이지 C 전체의 문제가 아니다.
이 문서도 글의 goto 함수가 경고 없이 컴파일된다는 것만 확인했고, 이 함수가 정말 올바른지 따로 검증하지는 않았다.

글의 논지는 그래도 유효하다.
단일 정리 블록 방식은 널 해제의 관용에 기대는 규율이고, `errdefer`는 규율이 아니라 언어 기능이라는 차이가 남는다.
다만 비교가 균형을 잃었다는 불만은 정당하다.

### 안전의 비교에서 시간적 메모리 안전이 빠져 있다

글은 해제 뒤 사용을 막지 못한다는 것을 인정한다.
그러나 이것이 C와 Zig가 같은 약점을 공유한다는 뜻임을 분명히 하지 않는다.
HN의 한 댓글은 Rust에는 시간적 메모리 안전 면의 이점이 있지만 Zig에는 해당하지 않는다고 짚는다.[^uecker]
글이 고른 여섯 항목은 모두 Zig가 C보다 나은 부분이고, 같은 점수를 받는 부분(해제 뒤 사용, 스택 포인터)은 한 문단으로 줄었다.
따라서 이 글은 C보다 낫다는 것을 보이는 글이고, 안전하다는 것을 보이는 글은 아니다.

### 안정성의 비용은 한 줄로 넘겨졌다

글쓴이의 책 Zig 파일 152개 중 35개를 0.17에서 고쳐야 했다는 문장은 이 글에서 가장 큰 숫자이다.
약 23%이다.
이 문서는 Zig 0.17 릴리스 노트에서 `@cImport`가 0.16에서 폐기 예고되었다가 0.17에서 제거되었음을 확인했다.
노트는 `std.Build.Step.TranslateC`도 폐기하고 공식 translate-c 패키지를 명시적 의존성으로 추가하라고 안내한다.[^zig017]
글은 `zig translate-c`를 쓰면 된다고만 적는데, 릴리스 노트가 강조하는 것은 빌드 통합을 패키지 의존성으로 바꾸라는 것이다.
이 차이가 실제로 어떤 작업을 요구하는지는 Zig를 실행해 보지 않아 확인하지 못했다.

HN의 댓글들이 같은 경험을 전한다.
한 사용자는 예전 Zig 프로젝트를 다시 열 때마다 버전 문제를 고쳐야 해서 열의가 꺾인다고 했고,[^ginko]
다른 사용자는 Zig로 일할 때 자신이 베타 테스터라서 큰 Zig 프로젝트는 최신 버전을 목표로 하지 않는다고 했다.[^lukaslalinsky]
Zig의 공식 다운로드 목록에서 개발 버전이 이미 0.18-dev(2026년 11월 10일자)인 것도 같은 맥락이다.[^zigindex]
글의 결론인 새 코드는 Zig로가 가려지는 조건은 코드가 몇 달마다 고쳐져도 괜찮은 프로젝트이다.

### 글의 출처에 대한 의심이 스레드를 덮었다

HN의 한 댓글은 이 글이 AI가 쓴 쓰레기라고 비난하고, 사이트의 모든 글에 같은 소제목 The honest tradeoff가 있으며 책을 홍보하려는 글 같다고 했다.[^nvme]
답글은 Rust 글이 특히 AI가 쓴 티가 난다고 했고, 다른 답글은 AI 탐지 서비스가 99% AI로 판정했다고 링크를 걸었다.[^raincole][^eatonphil]
이 문서는 그 탐지 결과를 열어 보지 않았고, 탐지 서비스의 정확성도 판단할 수 없다.
다만 이 의심이 글의 주장 자체에는 영향을 주지 않는다는 점은 확인했다.
이 문서가 실행해 본 C 쪽 주장은 모두 맞았다.
글이 어떻게 쓰였는지와 글의 주장이 맞는지는 별개의 문제이고, 판단은 주장을 시험해서 해야 한다.
글 끝에 책 홍보가 붙어 있다는 점은 사실이며, 증거를 따질 때 걸러 읽을 이해관계이다.

### 에이전트 시대의 언어 선택이라는 질문은 근거 없이 오갔다

GeekNews의 한 사용자는 AI가 Rust 코드는 잘 짜지만 Zig 코드는 잘 못 짜며 이제 도구 체인 선택 기준이 바뀌었다고 썼다.[^iolo]
HN에도 Rust가 LLM 시대에 Zig를 무의미하게 만든다는 댓글이 있었고,[^qweqwe14]
Zig와 Rust의 목표가 전혀 다르다는 반박이 달렸다.[^chicagobuss]
이 논쟁은 근거가 모두 개인 경험이고, 이 글도 이를 다루지 않는다.
이 문서는 모델별 Zig 코드 품질을 시험하지 않았다.

## 인사이트

### 언어를 고르는 일은 기능 비교가 아니라 실수의 기본 경로를 고르는 일이다

이 글이 주는 가장 이식 가능한 생각은 실수의 기본 경로이다.
위 실험에서 같은 off-by-one이 `-O0`에서는 7, `-O2`에서는 쓰레기 값을 냈고 경고는 없었다.
새니타이저를 켜면 즉시 잡힌다.
Zig는 같은 실수를 디버그 모드에서 기본으로 잡는다고 한다.
차이는 도구의 존재가 아니라 아무것도 하지 않았을 때 무슨 일이 일어나느냐이다.
팀이 C를 쓴다면 이 차이를 빌드 설정에서 메울 수 있다.
디버그 빌드에 `-fsanitize=address,undefined`를 기본으로 넣고, 반환값을 무시하면 안 되는 함수에 `[[nodiscard]]`를 붙이고, 경고를 오류로 다루는 것이다.
그렇게 하면 글의 여섯 가지 중 둘이나 셋은 C에서도 기본으로 막힌다.
이는 이 문서의 실험에서 끌어낸 처방이며, 모든 프로젝트에서 같은 비용으로 되는지는 확인하지 않았다.

### 새니타이저가 있는 C와 안전 모드의 Zig는 같은 보호의 두 가지 전달 방식이다

글은 `zig cc`가 디버그 모드에서 미정의 동작 새니타이저를 켠다고 쓴다.
이 문서가 clang에서 켠 `-fsanitize=undefined`가 같은 종류의 진단을 낸다.
그러므로 이 점에서 Zig는 새 보호 장치를 발명한 것이 아니라 기존 보호를 기본값으로 올린 것이다.
이것은 단점이 아니라 설계의 요점이다.
도구가 이미 있는데도 쓰이지 않는 이유가 기본값과 관행이기 때문이다.
HN의 한 답글이 말한 성공의 구덩이가 이 현상의 이름이다.[^bunderbunder]

### 언어 문화는 라이브러리 생태계에서 가장 크게 나타난다

할당자를 인자로 받는 관용구는 한 프로젝트의 선택이 아니라 생태계의 계약이다.[^simjnd]
C에서는 같은 일을 하려면 모든 의존성과 싸워야 한다.
이 차이는 새 코드를 쓰는 사람이 서드파티 라이브러리를 얼마나 쓰느냐에 달려 있다.
의존성이 적은 시스템 코드라면 문화의 차이가 작고, 의존성이 많은 프로젝트라면 크다.
이는 HN 댓글에서 끌어낸 추론이다.

### 도입은 한 파일씩 되며 되돌림 비용을 가진다

글은 `build.zig`가 C 파일과 Zig 파일을 함께 컴파일하므로 한 파일씩 옮길 수 있다고 한다.
이 점은 위험을 나누는 좋은 방법이다.
다만 0.17에서 글쓴이 책의 23%가 고쳐졌다는 사실은 옮긴 파일이 몇 달마다 다시 고쳐질 수 있다는 뜻이다.
옮길 때는 안정 버전에 고정하고, 업그레이드를 일정으로 잡고, 새 파일부터 시작해 기존 안정된 C 코드는 건드리지 않는 방식이 이 위험을 줄인다.
이는 이 문서의 제안이다.

### 확인할 관찰

이 글의 주장이 맞는다면 같은 크기의 시스템 코드를 C와 Zig로 쓴 두 팀에서 Zig 팀의 메모리 오류 건수가 낮아야 하고, 그 차이는 새니타이저를 기본으로 켠 C 팀에서는 줄어들어야 한다.
반대로 안정화되지 않은 Zig의 버전 이동 비용이 오류 감소분을 넘으면 새 코드는 Zig로라는 결론은 약해진다.
이 문서는 Zig를 실행하지 못했고, 위의 비교는 C 쪽 실험과 글과 댓글에 기댄 것이다.
