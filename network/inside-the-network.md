# 네트워크 안쪽: 패킷 한 개가 소켓에서 주소 한 줄까지 가는 길

영상: [네트워크 안쪽 시리즈 합본](https://www.youtube.com/watch?v=lj8-fdRI_yU)

## 소개

Codedeck 채널이 2026년 10월 29일에 올린 42분 36초짜리 합본 영상이다.
패킷 한 개가 만들어져 상대 컴퓨터에 닿기까지,
그 아래에서 커널과 프로토콜이 하는 일을 처음부터 끝까지 따라간다.
0편부터 3편까지 네 편이고,
0편은 패킷 한 개의 여정, 1편은 소켓과 TCP 연결, 2편은 신뢰성과 혼잡 제어,
3편은 DNS에서 HTTP까지이다.

형식은 설명자와 신입의 2인 대화이다.
신입이 막히는 지점에서 질문하고 설명자가 단계별로 푼다.
설명란은 음성이 설명자 Fola와 신입 Finn의 AI Studio 다화자 생성이라고 밝힌다.
수치는 대부분 Linux 7.0.0-39-generic 환경에서 로컬 서버를 띄운
루프백(loopback)으로 직접 잰 값이고, 터미널 출력을 화면에 그대로 보였다고 한다.
잴 수 없는 것(루프백에서 생기지 않는 혼잡, 게이트웨이 리졸버가 만든 합성 주소)은
영상 안에서 전제를 밝혀 둔다.

이 문서에는 읽지 못한 구간이 있다.
YouTube 자동 자막에 두 군데가 비어 있다.
23분 20초에서 29분 50초까지는 2편의 손실 감지 설명 중간부터 실측과 정리까지이고,
36분 16초부터 영상 끝까지는 3편의 TLS, HTTP 요청, 시간 분해, 시리즈 회고이다.
영상에서 이 구간이 실제로 무음이었는지는 이 문서가 확인하지 못했다.
이 구간의 내용은 이 문서에 쓰지 않았고, 설명란이 적은 한두 문장만 그대로 옮겼다.
자동 자막은 숫자와 용어를 자주 틀리게 적어서(「SYN」을 「센트」,
「ACK」을 「AC」로 적는 식),
읽힌 숫자 가운데 자막이 흔들린 것은 문서에서 뺐다.
화면은 보지 못했고, 아래 확인하기의 명령은 이 문서가 실행해 보지 못한 것이다.

## 동작 방식

### 층마다 자기 헤더를 붙이고 올라올 때 떼는 대칭 구조다

앱이 보낼 데이터를 커널에 건네는 곳이 소켓(socket)이다.
데이터는 소켓에서 아래 층으로 내려가며 층마다 헤더(header)를 붙인다.
이렇게 헤더가 붙는 것을 캡슐화(encapsulation)라고 한다.

| 층             | 붙이는 것                                         | 책임                                     |
| -------------- | ------------------------------------------------- | ---------------------------------------- |
| TCP            | 보낸 순서 번호, 어느 앱으로 갈지 정하는 포트 번호 | 데이터가 빠짐없이 순서대로 도착하게 한다 |
| IP             | 출발지와 목적지의 IP 주소                         | 컴퓨터와 컴퓨터 사이의 주소를 맡는다     |
| 드라이버와 NIC | (헤더 없음) 전기 신호나 빛, 무선 전파로 바꾼다    | 와이어 구간에 싣는다                     |

덩어리 크기에는 길마다 상한이 있고 이것이 MTU(maximum transmission unit)이다.
영상이 잰 값은 자기 자신과 통신하는 루프백 길이 65,536바이트,
바깥으로 나가는 길이 1500바이트이다.
데이터가 상한보다 크면 잘라서 나눠 보낸다.

받는 쪽은 정확히 역순이다.
NIC가 신호를 덩어리로 복원해 올리면 IP가 자기 헤더를 확인하고 떼고(목적지가 자기
것인지 본다),
TCP가 자기 헤더를 떼며 순서 번호를 확인하고(빠진 덩어리는 다시 보내 달라고 하고,
어긋난 순서는 맞춰 조립한다), 소켓이 포트 번호로 어느 앱의 소켓인지 찾는다.
이 떼어내는 일이 역캡슐화(decapsulation)이다.
영상이 강조하는 핵심은 대칭성이다.
보내는 쪽 TCP와 받는 쪽 TCP가 한 쌍으로 약속을 지키고,
층은 위아래로 덩어리를 넘길 뿐 옆 층의 약속에는 끼어들지 않는다.

영상은 로컬 웹 서버에 파일을 한 번 요청하는 장면을 AF_PACKET 소켓(커널이 오가는
패킷을 기록해 주는 통로)으로 캡처했다.
캡처된 패킷은 24개이고, 루프백에서는 같은 패킷이 나가는 길과 들어오는 길에서 두
번씩 기록되므로
중복을 빼면 실제 패킷은 12개이다.
처음 세 개가 연결을 여는 인사이고, 네 번째 패킷에 87바이트짜리 HTTP
요청이 실렸다.
답은 두 패킷(헤더 186바이트, 본문 22바이트)으로 왔고,
마지막 세 개가 연결을 닫는 인사이며 시작부터 끝까지 약 16밀리초가 걸렸다.
같은 컴퓨터라서 빠른 것이고 실제 인터넷에서는 간격이 왕복 시간만큼 벌어진다고
영상은 덧붙인다.

### 연결은 두 커널이 적어 둔 상태 기록이다

1편의 관점은 연결이 두 컴퓨터 사이에 생기는 물리적인 선이 아니라는 것이다.
양쪽 커널이 각자 지금 상대와 연결돼 있다는 상태 기록을 소켓마다 적어 둔 것이다.
그래서 이 편의 주인공은 패킷이 아니라 상태이다.

서버는 네 함수로 연결을 받을 준비를 한다.

| 함수     | 하는 일                                                                          |
| -------- | -------------------------------------------------------------------------------- |
| socket() | 커널에 새 소켓을 만들어 달라고 부탁한다                                          |
| bind()   | 소켓에 포트 번호를 붙인다                                                        |
| listen() | 소켓 상태를 LISTEN으로 바꾸고 기다리는 연결을 세워 둘 줄(백로그)의 길이를 정한다 |
| accept() | 도착한 연결 전용의 새 소켓을 만들어 돌려준다. 원래의 LISTEN 소켓은 계속 기다린다 |

클라이언트는 socket()으로 소켓을 만들고 connect()를 한 번 부르면 되고,
그 호출 하나가 세 번의 인사를 전부 일으킨다.
TCP 상태는 전부 11개이고 영상은 정상적으로 열고 닫는 길만 따라간다.

세 번의 인사(three-way handshake)의 내용은 이렇다.

| 순서 | 보내는 쪽  | 내용                                                                    |
| ---- | ---------- | ----------------------------------------------------------------------- |
| 1    | 클라이언트 | SYN: 연결하고 싶다는 뜻과 자기 시퀀스 번호의 시작값                     |
| 2    | 서버       | SYN과 ACK을 한 패킷에: 자기 시작 번호와, 받은 번호에 1을 더한 확인 응답 |
| 3    | 클라이언트 | ACK: 서버의 시작 번호를 받았다는 확인                                   |

시퀀스 번호는 보내는 데이터의 바이트마다 매기는 번호이고 순서 확인과 누락
확인에 쓴다.
시작값은 0이 아니라 연결마다 달라지는 큰 수이다.
옛 연결에서 늦게 온 패킷과 헷갈리지 않게 하려는 것이다.
두 번으로 끝내지 않는 이유는 서버가 자기 시작 번호를 보냈지만
클라이언트가 받았는지는 확인할 수 없기 때문이다.
그래서 세 번이 최소이다.

확인 응답이 받은 마지막 번호에 1을 더한 값인 이유도 실측으로 보였다.
데이터가 한 바이트도 오가지 않았는데 1이 늘었다.
SYN 자체가 번호 하나를 차지하기 때문이다.
이후 클라이언트가 17바이트를 보내자 서버의 확인 응답이 정확히 17 늘었다.
시퀀스 번호는 바이트를 세는 번호 그대로이다.

상태는 클라이언트가 SYN-SENT, SYN을 받고 ACK을 보내면 ESTABLISHED로 바뀐다.
서버는 LISTEN에서 SYN을 받으면 SYN-RECEIVED,
마지막 ACK이 도착하면 ESTABLISHED이다.
영상은 ss(소켓 상태를 보는 도구)로 서버에 LISTEN 소켓과 ESTABLISHED 소켓이
나란히 있는 것을 확인했다.
기다리는 소켓과 통화 중인 소켓이 따로 있다는 확인이다.
중간 상태인 SYN-SENT는 ss를 25밀리초 간격으로 돌려도 잡히지 않았고,
대신 패킷 캡처 시각으로 SYN을 보낸 뒤 답이 오기까지의 시간을 계산해 그 상태에
머문 시간으로 삼았다.
영상은 이것이 도구의 눈이 아니라 패킷의 시각으로만 잴 수 있는 상태라고 말한다.

### 닫을 때는 방향마다 따로 닫고 먼저 닫은 쪽이 TIME-WAIT를 진다

연결을 닫는 인사는 기본 네 번이다.
FIN은 나는 이제 보낼 게 없다는 한 방향짜리 선언이라서 방향마다 따로 보낸다.
상대는 아직 보낼 게 남아 있을 수 있기 때문이다.
FIN도 시퀀스 번호 하나를 차지하므로 FIN에 대한 확인 응답도 1이 늘었다.

영상은 서버의 FIN이 약 0.76초 늦게 오도록 일부러 만든 측정을 보였다.
그 사이 서버 소켓은 CLOSE_WAIT에 머문다.
상대는 닫았고 이제 내 프로그램이 닫을 차례라는 뜻이다.
영상의 해석은 CLOSE_WAIT가 오래 쌓여 보이면 내 프로그램이 닫기를 미루고 있다는
신호라는 것이다.

먼저 닫은 쪽은 FIN을 보내 FIN-WAIT-1, 상대의 ACK을 받아 FIN-WAIT-2가 된다.
받은 쪽은 CLOSE_WAIT를 거쳐 자기 FIN을 보내고 LAST-ACK에서 마지막
확인을 기다린다.
마지막으로 먼저 닫은 쪽이 TIME-WAIT가 된다.
종료가 다 끝났는데도 소켓 기록을 바로 지우지 않고 남겨 두는 상태이다.

남겨 두는 이유는 두 가지이다.
첫째, 마지막 ACK이 길에서 사라질 수 있다.
그러면 상대는 FIN을 다시 보내는데, 먼저 닫은 쪽이 기록을 지웠다면 그런 연결이
없다고 답하게 돼
상대의 종료가 비정상으로 끝난다.
TIME-WAIT가 남아 있어야 다시 ACK으로 답할 수 있다.
둘째, 길에 늦게 떠도는 옛 패킷이 있다.
기다리는 시간은 패킷이 네트워크에 살아 있을 수 있는 최대 시간(MSL)의 두 배이고,
그 전에는 같은 주소와 포트의 조합으로 새 연결을 만들지 않으므로 옛 패킷이 새
연결에 들어갈 수 없다.
Linux에서 이 대기는 60초로 정해져 있고, 영상의 실측에서도 타이머가 59초, 58초,
57초로 줄었다.
먼저 닫는 쪽이 이 부담을 지므로 짧은 연결을 대량으로 먼저 닫는 쪽,
보통 클라이언트 쪽에 TIME-WAIT가 쌓이고 그 시간에는 그 포트를 다시 쓰지 못한다.

### 백로그는 핸드셰이크가 끝났는데 accept()가 안 데려간 줄이다

백로그(backlog)는 핸드셰이크까지 끝났지만 아직 accept()가 데려가지 않은
연결들이 선 줄이다.
그래서 클라이언트는 서버 프로그램이 받기도 전에 연결됐다고 느낀다.
핸드셰이크는 커널이 먼저 끝내 두기 때문이다.

영상은 백로그를 5로 정하고 accept()를 전혀 하지 않는 서버에 클라이언트를
하나씩 붙였다.
여섯 개까지는 붙이는 대로 약 0.15밀리초 안팎에 연결됐고,
ss의 LISTEN 줄에는 쌓인 연결 수가 1부터 6까지 그대로 찍혔다.
정한 값 5에 하나를 더한 6에서 멈추는 것이 이 스택의 동작이었다.
일곱 번째부터는 2초를 줘도 연결이 되지 않았다.
줄이 가득 차면 새 SYN을 조용히 버리는 설정이었기 때문이다.
답도 거절도 없으니 클라이언트는 SYN을 다시 보내며 기다린다.
백로그가 너무 작으면 서버가 멀쩡해도 연결이 안 되는 것처럼 보이는 이유이다.

연결이 수백 개 열리면 소켓도 수백 개 생긴다.
같은 연결인지 가르는 기준은 출발지와 목적지의 주소와 포트, 네 가지의 조합이다.
서버 포트가 같아도 클라이언트 포트가 매번 다르므로 구분된다.

### 신뢰성은 확인 응답과 재전송 타이머, 혼잡 제어는 두 개의 창으로 한다

2편의 두 약속은 보낸 데이터를 하나도 잃지 않는 것과
네트워크가 감당하지 못할 만큼 몰아넣지 않는 것이다.
영상은 얼마나 기다려 다시 보낼지, 한 번에 얼마나 보낼지가 전부 숫자
싸움이라고 말한다.
너무 조급하면 멀쩡한 것을 또 보내고, 너무 느긋하면 진짜로 잃은 것을 늦게 안다.

보내는 쪽은 ACK로 받았는지 안다.
ACK은 누적 방식이라 중간의 확인 응답 하나가 길에서 사라져도
다음 확인 응답이 여기까지 다 받았다고 한꺼번에 덮어 준다.
보내는 쪽은 기다리되 시간을 잰다.
RTT(round-trip time)는 세그먼트를 보낸 순간부터 확인 응답이 돌아올 때까지의
왕복 시간이고,
세그먼트는 TCP가 데이터를 잘라 보내는 단위이다.
RTO(재전송 타이머)는 이 시간까지 확인 응답이 없으면 그 세그먼트를 잃은 것으로
보고 다시 보내는 기다림의 상한이다.
RTO는 고정값이 아니라 실제 RTT를 계속 재서 그것보다 조금 넉넉하게 따라간다.
이 컴퓨터에서 확인한 최소값은 200밀리초로,
아무리 빠른 길이라도 타이머는 그 아래로 내려가지 않는다.
타이머 만료는 가장 비싼 신호로 취급되고 반응이 가장 강하다고 영상은 말한다.

보내는 양은 창 두 개가 정한다.

| 창                | 누가 정하나                           | 조절하는 것 | 막는 것                                |
| ----------------- | ------------------------------------- | ----------- | -------------------------------------- |
| 수신 윈도우       | 받는 쪽이 ACK에 적어 보낸다           | 흐름 제어   | 받는 쪽 그릇이 넘쳐 데이터를 버리는 일 |
| 혼잡 윈도우(cwnd) | 보내는 쪽이 길의 상태를 짐작해 정한다 | 혼잡 제어   | 중간 장비가 밀려 패킷이 버려지는 일    |

혼잡 제어는 길목 장비가 알려 주지 않으므로 추측의 기술이다.
잃은 패킷이 없으면 여유가 있다고 읽고 조금씩 늘리고,
손실이 보이면 붐빈다고 읽고 줄인다.

커지는 규칙은 두 단계이다.
슬로 스타트(slow start)는 RTT 한 번마다 cwnd가 대략 두 배가 된다.
이 컴퓨터에서 실측된 시작값은 세그먼트 열 개분이고 열 개, 스무 개,
마흔 개 식으로 늘어난다.
이름이 느린 이유는 시작값이 세그먼트 한 개이던 시절의 이름이 남은 것이다.
ssthresh(슬로 스타트 임계값)에 닿으면 혼잡 회피로 넘어가 RTT 한 번에 대략 한
개씩만 늘어난다.
손실이 한 번도 없던 연결에서는 ssthresh가 사실상 정해지지 않은 아주 큰 값이다.
손실이 보이면 그때 cwnd의 절반이 다음 ssthresh가 된다.
손실을 알아채는 방법 둘 가운데 첫째는 중복 확인 응답(duplicate ACK)이다.
받는 쪽은 빠진 세그먼트가 있으면 다음 것들이 도착해도 같은 번호를 계속
적어 보내고,
같은 번호가 세 번 중복되면 보내는 쪽은 타이머를 기다리지 않는다.
이 뒤의 둘째 방법(타임아웃)과 영상이 보인 실측은 자막에 없다.
설명란은 2편이 느린 수신자 앞에서도 cwnd가 10에 고정된 이유를
ss 샘플링과 TCP_INFO로 확인한다고 적을 뿐이다.

### 이름이 주소가 되는 일은 스텁 리졸버, 재귀 질의, 반복 질의로 나뉜다

3편은 주소 한 줄이 방문 한 번에서 어떻게 순서대로 조립되는지를 본다.
이름이 주소가 되고(DNS), 연결이 열리고(TCP), 암호화 통로가 뚫리고(TLS),
요청이 오간다(HTTP).
영상은 이 컴퓨터가 바깥으로 직접 나가는 길이 막혀 있어서
실제 사이트로 가는 것을 그대로 재지 못하고,
로컬 서버로 여정을 재현했다고 밝힌다.

DNS는 이름에 대응하는 숫자 주소를 적어 둔 전 세계가 나눠 쓰는 분산
전화번호부이다.
프로그램이 이름을 내밀면 운영 체제 안의 작은 담당인 스텁 리졸버(stub resolver)가
먼저 움직이고,
이름만 받아서 진짜로 찾아다니는 리졸버(resolver)에게 부탁을 넘긴다.
리졸버는 먼저 자기 기억인 캐시(cache)를 확인한다.
캐시에 없으면 두 종류의 질의가 이어진다.

| 질의                 | 누가 누구에게        | 내용                                                       |
| -------------------- | -------------------- | ---------------------------------------------------------- |
| 재귀 질의(recursive) | 프로그램에서 리졸버  | 중간 답은 됐고 최종 답을 구해다 달라고 통째로 맡긴다       |
| 반복 질의(iterative) | 리졸버에서 권위 서버 | 모르면 다음에 물어볼 곳이라도 알려 달라고 한 단계씩 묻는다 |

권위 서버(authoritative server)는 자기 구역의 이름에 대한 원본 답을
가진 서버이고,
리졸버는 맨 위 루트에서 시작해 뒤쪽 구역부터 차례로 좁혀 들어간다.
답에는 유효 기간 TTL이 붙어 온다.
답을 얼마 동안 믿고 캐시에 넣어도 되는지 정한 초 단위 시간이고,
기간이 지나면 버려지고 다음 질문 때 다시 구한다.
이름 뒤의 주소가 바뀔 수 있으므로 무한정 믿지 않는 것이다.

dig(DNS 질의를 직접 보내고 답을 출력하는 도구)로 잰 결과의 해석에는
전제가 붙는다.
돌아온 것은 A 레코드 하나였고 주소는 198.18로 시작했으며 TTL은 15초였다.
198.18로 시작하는 대역은 실제 인터넷 주소가 아니라 장비 시험용으로 예약된 대역이다.
이 컴퓨터의 리졸버는 바깥으로 나갈 수 없는 환경이라 이름마다 합성 주소를
만들어 돌려준다.
그러므로 이 주소와 TTL은 실제 인터넷의 답이 아니라 이 환경의 리졸버가
만든 답이고,
질의의 절차와 시간은 진짜이지만 답의 내용은 합성이라고 영상이 분명히 한다.
dig가 보인 질의 시간은 네 번 재는 동안 0에서 50밀리초 사이를 오갔다.
같은 질문과 같은 리졸버인데도 길목 장비가 답을 만드는 처리 시간이 그때그때
다르기 때문이고,
그래서 대표값 하나가 아니라 범위로 읽어야 한다.
같은 질의를 패킷으로 잡으면 나가는 질의가 IP 헤더까지 80바이트,
돌아온 응답이 73바이트였고
캡처 시각으로 잰 왕복은 0.1에서 0.2밀리초 사이였다.
dig의 시간과 패킷 왕복의 숫자가 다른 것은 재는 구간이 다르기 때문이다.
dig는 밀리초 단위로 깎아 표시하고 리졸버가 답을 만드는 시간까지 포함하며,
패킷 왕복은 선로 위를 오간 시간만 잰 것이다.
질의와 응답에는 같은 번호(트랜잭션 ID)가 적혀 있고 응답이 내 질문의 답인지 이
번호로 확인한다.

주소를 얻은 뒤의 TCP 연결은 1편이 그대로 재사용된다.
로컬 서버로 재면 세 번의 인사는 0.04밀리초 안팎이다.
이 뒤의 TLS와 HTTP, 그리고 시리즈 회고는 자막에 없어서 이 문서가 다루지 못한다.
설명란은 3편이 curl로 구간별 시간을 재고 dig, 패킷 캡처,
s_client의 결과를 숫자로 분해한다고 적는다.

어느 값도 환경과 설정에 따라 달라지므로 아래 표는 정답이 아니라 읽는 기준이다.

## 함정

### 읽은 숫자를 다른 환경에 그대로 옮기는 것

영상의 실측은 모두 루프백이다.
루프백에서는 혼잡도 손실도 생기지 않으므로 RTT는 0.04밀리초 수준이고 cwnd 증가를
가를 상황이 없다.
영상은 이 한계를 스스로 밝힌다.
백로그 5에서 6까지 붙는 것도 이 스택의 동작이라고 영상이 단서를 달았으므로,
다른 커널이나 설정에서는 숫자가 다를 수 있다.

### ss로 중간 상태를 못 잡는 것을 상태가 없는 것으로 읽는 것

영상은 ss를 25밀리초 간격으로 돌려도 SYN-SENT를 잡지 못했다.
상태는 있었지만 그 상태에 머문 시간이 샘플링 간격보다 짧았을 뿐이다.
관찰이 안 되는 것과 없는 것은 다르고, 영상은 이 차이를 패킷 캡처의
시각으로 메웠다.

### 리졸버가 합성한 답을 인터넷의 답으로 읽는 것

198.18로 시작하는 주소와 TTL 15초는 이 환경의 리졸버가 만든 값이다.
같은 절차를 실제 인터넷에서 돌리면 주소, TTL, 질의 시간이 모두 다르다.

## 비평

### 영상이 설명하는 구조와 관찰한 증거의 거리

1편의 관점은 연결이 상태 기록이라는 것이다.
이 관점은 ss로 LISTEN과 ESTABLISHED를 나란히 본 것으로 뒷받침되지만,
SYN-SENT와 LAST-ACK은 ss로 잡지 못했다.
영상은 이 상태들을 패킷 시각에서 계산했다고 밝히지만,
계산은 상태 이름이 가리키는 소켓 기록을 관찰한 것이 아니라 패킷 순서에서
추론한 것이다.
상태 기록이라는 관점을 이 컴퓨터에서 직접 보인 증거는 일부이다.

### TIME-WAIT가 쌓이는 문제에 대한 대처가 읽힌 구간에 없다

영상은 짧은 연결을 대량으로 먼저 닫으면 TIME-WAIT가 쌓이고 그동안 포트를 못
쓴다고 말한다.
이 문제가 실제로 어떻게 나타나는지(포트 고갈의 증상),
어떤 설정이나 설계로 완화하는지는
읽힌 구간에 없다.
이 설명을 들은 개발자가 바로 취할 행동이 정해지지 않는다.
CLOSE_WAIT가 쌓이면 내 프로그램이 닫기를 미루는 것이라는 해석이 있는
것과 대비된다.

### 두 번 읽는 숫자와 한 번 읽는 숫자를 같은 무게로 보인다

영상은 RTO의 최소값 200밀리초를 이 컴퓨터에서 확인한 값이라고 말한다.
이 값이 이 커널의 기본 설정인지, 연결마다 달라질 수 있는지는 말하지 않는다.
cwnd 시작값 10도 같은 단서가 붙는다.
영상은 이 값들이 정해진 규칙인 것처럼 문장을 쓰지는 않지만,
확인하기에서 다른 환경에서 같은 값이 나오는지 보라는 안내가 없으므로 독자가
일반화하기 쉽다.

### 자막이 비어 있는 구간 때문에 이 문서가 평가하지 못하는 것

2편의 실측과 정리, 3편의 TLS와 HTTP와 시리즈 회고는 이 문서가 읽지 못했다.
설명란은 이 구간이 시리즈의 결론(여정의 조립과 회고)을 담는다고 적는다.
이 문서의 평가는 읽은 약 70퍼센트에 대한 것이고,
시리즈 전체의 논증이 마지막에 어떻게 닫히는지는 판단하지 않았다.

## 확인하기

아래 명령은 Linux에서 영상의 장면을 직접 재현하는 것이다.
이 문서가 실행해 보지 못했으므로 출력은 환경에 따라 다르다.

### 연결 상태를 본다

```bash
# 터미널 1: 파일 하나를 내주는 로컬 웹 서버
mkdir -p /tmp/netlab && cd /tmp/netlab && echo "Hello network inside" > hello.txt
python3 -m http.server 8000 --bind 127.0.0.1

# 터미널 2: 상태를 0.025초 간격으로 계속 찍는다
while true; do ss -tan 'sport = :8000 or dport = :8000'; sleep 0.025; done

# 터미널 3: 요청을 한 번 보낸다
curl -s http://127.0.0.1:8000/hello.txt
```

LISTEN과 ESTABLISHED가 나란히 있는지, 요청이 끝난 뒤 TIME-WAIT가 남고 남은
시간이 줄어드는지 본다.

### 패킷을 직접 잡는다

```bash
# 루프백의 패킷을 잡는다. 같은 패킷이 두 번 보이는지 센다
sudo tcpdump -i lo -n -S 'tcp port 8000'
```

-S 옵션은 시퀀스 번호를 상대값이 아니라 원래 값으로 보여 준다.
SYN의 시퀀스 번호에 1을 더한 값이 SYN-ACK의 확인 응답에 있는지 확인한다.

### 백로그가 가득 차는 지점을 잰다

```python
import socket
import time

srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 9000))
srv.listen(5)  # accept()를 하지 않는다

clients = []
for i in range(1, 10):
    c = socket.socket()
    c.settimeout(2)
    start = time.monotonic()
    try:
        c.connect(("127.0.0.1", 9000))
        print(i, "연결됨", round((time.monotonic() - start) * 1000, 2), "ms")
    except OSError as e:
        print(i, "실패", type(e).__name__)
    clients.append(c)

# 다른 터미널에서 ss -ltn 'sport = :9000' 로 쌓인 연결 수를 본다
time.sleep(30)
```

몇 번째 연결부터 실패하는지, 그 값이 listen()에 준 5보다 하나 큰지 본다.

### DNS 질의와 패킷 왕복을 비교한다

```bash
dig example.com +noall +answer +stats
sudo tcpdump -i any -n -tt 'udp port 53'
```

dig가 적는 질의 시간과 패킷 캡처 시각의 차이가 영상이 말한 재는 구간의 차이로
설명되는지 본다.
반복해서 돌려 질의 시간이 범위로 흔들리는지 본다.

## 체크리스트

- 읽은 시간이나 숫자가 루프백에서 잰 것인지, 실제 네트워크에서 잰 것인지 구분하는가?
- 소켓 상태가 이상할 때 ss로 먼저 상태 이름(CLOSE_WAIT, TIME-WAIT 등)을 확인하는가?
- CLOSE_WAIT가 쌓였다면 내 프로그램이 close()를 미루는지 먼저 확인했는가?
- 짧은 연결을 대량으로 닫는 쪽(클라이언트)에서 TIME-WAIT가 쌓이는지 알고 있는가?
- listen()의 백로그를 정할 때 줄이 가득 차면 연결이 조용히 실패한다는 것을 알고 있는가?
- 연결이 안 되는 증상에서 서버가 멀쩡한지와 백로그가 찼는지를 따로 확인했는가?
- 재전송이 느린 원인을 볼 때 RTO의 바닥(최소값)과 RTT를 함께 보았는가?
- dig 같은 도구가 보인 시간이 어느 구간을 포함하는지 알고 값을 범위로 읽는가?
- DNS 답을 볼 때 그 리졸버가 합성한 답은 아닌지 확인했는가?

## 기억할 원칙

### 연결은 선이 아니라 양쪽이 적어 둔 상태이다

연결이 열려 있다는 것은 두 커널이 서로를 가리키는 상태 기록을 가지고
있다는 뜻이다.
그래서 문제는 상태 이름으로 읽을 수 있다.
CLOSE_WAIT는 내 프로그램의 닫기 미룸, TIME-WAIT는 먼저 닫은 쪽의 뒤처리,
LISTEN 줄이 가득 차는 것은 accept()가 느린 서버를 가리킨다.
