# 웹 서버 1,500만 개 실험

원문: [15 million web servers on one VM - smoltcp, DPDK, AF_XDP](https://kapteko.com/15-million-webservers/)

HN 토론: <https://news.ycombinator.com/item?id=50556533> (394점, 41개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/elmy67/15_million_web_servers_on_one_vm_smoltcp> (40점, 1개 댓글)

GN 토론: <https://news.hada.io/topic?id=37470>

## 요약

2026년 11월 18일 kapteko.com에 올라온 글이다.
목표는 램 10GB와 CPU 코어 1개인 가상 머신 한 대에서 웹 서버 1,500만 개를 돌리는
것이다.
글은 인터넷에 웹 서버를 올리면 모두가 해킹하려 드는 이유를 공급 부족으로
설명하는 농담으로 시작해, 80억 명 모두에게 웹 서버를 하나씩 주면 사이버 보안이
해결된다는 설정을 단다.

글은 단계별로 병목을 하나씩 만나고 푼다.

- 기본 서버: C로 listen, accept, recv, send, close만 하는 서버는 초당 약 6만 5천
요청을 처리한다. 이것을 1,500만 번 띄우려 하면 임시 포트
범위(32768~60999)가 먼저 바닥나 listen이 실패한다.
- 포트와 주소: 포트는 16비트이므로 65,535개가 상한이다. 서버는 (프로토콜, IP,
포트)로 식별되므로 AnyIP로 서브넷 전체를 수신하게 하면 IPv6에서는 약 18퀸틸리언
주소를 쓸 수 있다. IPv4로 1,500만 주소를 사려면 약 2억 5천만 달러가 든다고 쓴다.
- 프로세스: 서버 하나가 램 1.5MB를 쓰므로 1,500만 개는 약 20TB가 필요하다.
해법은 한 프로세스 안에서 모두 돌리는 맞춤 런타임이다. 글은 앞선 글에서 다룬 LFI
샌드박스와 사용자 공간 스케줄러를 쓴다.
- 상태 크기: 이 서버 루프의 상태는 명령 주소와 파일 기술자 두 개뿐이라 게스트당
16바이트, 1,500만 개에 약 220MB가 든다고 계산한다. 비트 패킹으로
8바이트까지 줄일 수 있다고 한다.
- 소켓: 저자는 유휴 연결이 메모리를 쓰지 않는다고 LLM에게 물어 믿었다가 틀렸음을
확인했다. 소켓 하나는 상태와 관계없이 약 3,300바이트를 쓰며, 글의 표는 tcp_sock
2,240B, socket_alloc 768B, file 184B, dentry 192B의 합계 3,384B를 보여 준다.
- 커널 우회: OSI 모델의 아래 계층으로 내려가 TCP/IP를 직접 구현하면 커널 소켓을
피할 수 있다. 글은 28바이트로 동작하는 Adam Dunkels의 Miniweb을 극단적 사례로,
gVisor, Seastar, lwIP, F-Stack을 성숙한 구현으로 든다.

저자가 고른 구현은 Rust의 smoltcp이다.
smoltcp는 힙 할당이 필요 없는 독립 TCP/IP 스택이며 입출력은 하지 못하므로 장치
연결 방식을 정해야 한다.
선택지는 TUN, TAP, DPDK, 그리고 AF_XDP이다.
DPDK는 커널을 완전히 우회해 네트워크 카드와 직접 통신하지만 CPU 코어 하나를 바쁜
대기 루프로 점유하고 장치가 운영체제에서 사라진다.
AF_XDP는 커널이 장치를 계속 소유하고 eBPF 필터로 패킷을 사용자 공간으로 보내므로
SSH가 유지된다.

결과로 글은 커널 네트워크 스택에서는 약 250만 서버에서 램이 바닥나고 서버가
늘수록 초당 요청이 떨어진다고 쓴다.
smoltcp에서는 유휴 서버당 620바이트, 활성 서버당 약 1KB로 1,600만 서버까지 갔다.
DPDK가 이 시험에서 가장 낫고 AF_XDP가 바로 뒤를 따른다고 한다.
글은 이 방식으로 램 사용과 성능을 통제할 수 있지만 Linux와 호환되는 런타임과
POSIX 100% 호환 구현은 별도의 글이 필요하다고 맺는다.
그래프의 수치와 벤치마크 그림은 이 문서가 확인하지 못했다.

## 분석

### 글의 구조는 병목을 한 겹씩 벗기는 것이다

글은 포트, 주소, 프로세스, 소켓이라는 순서로 병목을 만나고 매번 한 층 아래로
내려간다.
각 단계는 앞 단계의 해법이 새 병목을 드러내는 구조이며, 마지막에는 커널의 소켓
자체가 한계가 된다.
저자는 엔지니어링의 지혜를 빌려 작업이 풀리지 않으면 추상화 수준이 틀린 것이라고
쓰고, 그것이 OSI 모델을 내려가는 계기가 된다.
이는 글의 서술을 이 문서가 정리한 것이다.

HN의 mrheosuper는 모든 것이 사용자 공간으로 가는 추세라면 Linux가 마침내
마이크로커널이 되는 것이냐고 물었다.[^mrheosuper]
bewo001은 eBPF를 쓰면 마이크로커널보다 엑소커널에 가깝다고 답했다.[^bewo001]
두 댓글은 글의 해법이 커널의 역할을 재배치하는 일이라는 점을 짚는다.

### 숫자 계산이 설계를 이끈다

글은 매 단계에서 필요한 바이트를 먼저 계산하고 시험한다.
게스트당 16바이트와 활성 연결 5KB라는 가정으로 램 예산을 짠 뒤, 유휴 연결이
공짜라는 가정이 틀렸음을 시험으로 바로잡는다.
저자는 LLM이 학습에 큰 도움이지만 답을 비판 없이 받아들이면 나중에
부끄러워진다고 쓴다.
이 대목은 예산 계산이 측정으로 검증되어야 한다는 글의 방식을 보여 준다.

### 유머가 글의 전달 방식이다

HN의 여러 댓글이 글의 유머와 읽기 쉬운 기술 서술을 칭찬했다.
tempfile은 영국 열 개를 1,500만으로 나눈다는 농담에 웃었다고 적었고,[^tempfile]
101008은 2000년대 초 블로그가 정보를 나누면서도 웃기려 했던 분위기를
떠올렸다.[^101008]
LetMeLogin은 쉽고 간단하면서 기술적이고 AI가 쓰지 않은 글이라는 점을 높이
평가했다.[^LetMeLogin]
이 반응은 글의 기술 내용보다 문체에 대한 것이며, 글 자체가 AI 작성이 아니라고
단정할 근거는 이 문서에 없다.

## 비평

### 이 벤치마크는 실제 웹 서버의 일을 하지 않는다

글의 서버는 모든 요청에 OK를 돌려준다.
HTTP 파싱, 가상 호스트 선택, TLS, 응답 본문 생성은 빠져 있다.
HN의 ZiiS는 HOST 헤더를 언급했고 eptcyka는 소켓 주소는 6바이트나 18바이트인데
호스트 헤더는 보통 더 길다고 짚었다.[^ZiiS][^eptcyka]
ozozozd는 글이 이를 가상 호스팅으로 언급했다고 답했다.[^ozozozd]
1,500만 개라는 숫자는 요청마다 OK만 돌려주는 서버를 센 것이며, 실제 서비스에서
같은 수를 낼 수 있다는 뜻이 아니다.

### 활성 연결 비율 가정이 결과를 좌우한다

램 예산은 어느 순간에도 활성 연결이 100만 개이고 나머지가 유휴라는 가정에
기댄다.
이 가정이 바뀌면 5KB 곱하기 활성 수가 예산을 바꾸고, 글은 이 민감도를 보이지
않는다.
CPU 코어 하나로 100만 활성 연결의 요청을 처리할 수 있는지도 글에서 확인되지
않는다.
DPDK와 AF_XDP 결과에서 코어 하나가 바쁜 대기에 묶이는 비용이 어떻게
반영되었는지도 그래프를 읽지 못한 이 문서는 확인하지 못했다.

### 보안과 격리의 주장이 농담에 머문다

글의 서두는 서버를 모두에게 하나씩 주면 사이버 보안이 해결된다는 농담이다.
이후 LFI 샌드박스를 언급하지만 게스트 1,500만 개가 한 프로세스에서 돌 때 격리의
강도와 한 게스트의 오류가 다른 게스트에 미치는 영향은 다루지 않는다.
글의 목표가 램 예산이므로 범위 밖일 수 있으나, 한 프로세스에 모든 게스트를 넣는
방식의 대가는 쟁점으로 남는다.

### 호환 범위의 한계는 글이 직접 인정한다

글은 마지막에 호환되는 Linux 런타임과 POSIX 100% 호환 구현은 더 어렵다고 쓴다.
시제품은 서버 루프 한 가지에 맞춰진 것이다.
그래서 이 결과가 일반 프로그램을 같은 방식으로 돌릴 수 있다는 주장으로 읽히면
글의 범위를 넘는다.

### 외부 반응

반응은 대체로 호의적이었다.
Lobste.rs의 fratti는 마지막 그래프에서 글이 짚지 않은 점으로, 이 용도에서 TAP과 TUN의 성능이 나쁘지 않아 보이며 자신은 그 정도 손실은 받아들이겠다고 적었다.[^fratti]
athrowaway3z는 제목에서 web을 빼야 HTTP 처리 이야기로 오해하지 않는다고
제안했고,[^athrowaway3z] 3abiton은 제목이 이야기를 과소평가한다며 10GB는 평범한
맥 미니 수준이라고 적었다.[^3abiton]
magahugu는 축이 셋인 그래프가 2차원인 것을 이해하지 못하겠다고 적었고 ptejax가
한 축은 점선이라고 답했다.[^magahugu][^ptejax]

## 인사이트

### 커널 소켓은 접속 수에 비례해 쌓이는 고정비이다

글이 보여 준 소켓당 약 3,300바이트는 연결이 많은 서버의 메모리 하한이다.
연결이 유휴여도 이 비용이 사라지지 않으므로 수백만 연결을 다루는 설계는 소켓
수를 줄이는 쪽으로 가야 한다.
사용자 공간 스택은 이 고정비를 620바이트로 낮추는 길을 보여 주었고, 그 대가는
호환성과 운영의 복잡도이다.
이는 이 문서의 해석이다.

### 우회 방식마다 운영 비용이 다르다

글의 비교에서 DPDK는 성능이 가장 좋지만 장치가 운영체제에서 사라지고 코어 하나를
점유한다.
AF_XDP는 성능이 조금 낮은 대신 SSH가 유지되고 관리가 쉽다.
fratti의 관찰처럼 TAP과 TUN이 크게 나쁘지 않다면 가장 빠른 방식이 항상 가장
알맞은 방식은 아니다.
이는 이 문서의 해석이며 그래프 수치를 확인하지 못했다.

### 학습형 글의 가치는 틀린 가정을 보여 주는 데 있다

저자는 LLM이 알려 준 유휴 연결 비용을 믿고 시험했다가 틀렸다는 것을 보여 준다.
실패를 숨기지 않는 서술이 글을 따라 해 볼 수 있게 만든다.
HN의 101008이 오래된 블로그의 분위기를 떠올린 이유도 이 솔직함과 유머에 있을 수
있다.
이는 이 문서의 해석이다.

### 확인할 관찰

이 문서의 해석을 가를 관찰은 세 가지이다.
저장소의 시제품으로 같은 수치가 재현되는지,
요청 처리가 OK 이상일 때 서버 수와 처리량이 어떻게 변하는지,
게스트 격리의 강도이다.
세 가지 모두 이 문서가 확인하지 못했다.
