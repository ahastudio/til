# CNAME 플래트닝: 루트 도메인에 CNAME을 쓰기 위한 우회

원문: [CNAME flattening | Cloudflare Docs](https://developers.cloudflare.com/dns/cname-flattening/)

HN 토론: <https://news.ycombinator.com/item?id=7522065> (96점, 62개 댓글)

문서 자체에 대한 HN 토론은 없고,
이 기능을 처음 발표한 2014년 Cloudflare 블로그 글의 토론을 참고했다.

## 소개

CNAME 플래트닝은 CNAME 레코드가 가리키는 최종 IP 주소를 Cloudflare가 미리 찾아서,
CNAME 대신 그 IP 주소를 응답으로 돌려주는 기능이다.

이 기능이 존재하는 이유는 DNS 표준의 제약 때문이다.
CNAME 레코드는 같은 이름에 다른 레코드가 함께 존재할 수 없는데,
존 apex(`example.com` 자체)에는 SOA와 NS 레코드가 반드시 있어야 한다.
그래서 apex에는 CNAME을 둘 수 없고, `www.example.com`에는 되는 일이
`example.com`에는 안 되는 상황이 생긴다.

플래트닝은 이 제약을 지키면서 우회한다.
사용자는 apex에 CNAME을 설정하지만, 권한 있는 서버가 외부에 내보내는 응답에는
CNAME이 없고 A 또는 AAAA 레코드만 있다.
즉 표준을 어기는 것이 아니라, 표준을 어기지 않는 응답을 만들어 내는 것이다.

이 제약을 1987년 명세의 선견지명 부족으로 설명하는 서술이 흔하지만,
`mindslight`는 그것이 CNAME의 의미를 오해한 것이라고 반박했다.[^mindslight]
CNAME은 이 이름이 다른 이름과 하위 이름까지 포함해 완전히 같은 것을 가리킨다는 선언이다.
apex에 NS와 SOA가 있다는 것은 두 이름이 같지 않다는 뜻이므로,
명세가 별도 레코드를 금지한 것은 실수가 아니라 병합 규칙을 정의하지 않기 위한 선택이었다.
`example.com`과 대상 존이 각각 MX 레코드를 가지면 무엇을 돌려줄지 정해야 하는데,
명세는 그 질문 자체가 생기지 않게 막았다.

이 지적은 플래트닝이 무엇을 회피하는지도 드러낸다.
`AnthonyMouse`가 곧바로 물은 것이 그 지점이다.
A와 AAAA가 아닌 레코드 타입은 어떻게 되는가,
양쪽에 MX나 TXT가 있으면 어느 쪽을 주는가.[^AnthonyMouse]
답은 플래트닝이 A와 AAAA만 다룬다는 것이며,
따라서 병합 문제를 푼 것이 아니라 그 문제가 생기지 않는 레코드 타입에만 적용한 것이다.

문서는 두 가지 부수 효과도 밝힌다.
하나는 해석 속도로, 리졸버가 CNAME을 따라 다시 질의할 필요가 없어진다.
다른 하나는 Cloudflare Pages 사이트에 루트 커스텀 도메인을 쓸 수 있게 하는 것이
바로 이 기능이라는 점이다.

## 동작 방식

문서의 예시 시나리오를 그대로 따라가면 동작이 분명해진다.

- `domain.test`는 Cloudflare에 있는 존이고, apex에 `external-origin.test`를 가리키는 TTL 3600인 CNAME 레코드가 있다.
- `external-origin.test`는 다른 DNS 제공자에 있는 존이고, `192.0.2.1`을 가리키는 TTL 7200인 A 레코드가 있다.

리졸버가 `domain.test IN A`를 물으면 이런 순서로 처리된다.

1. Cloudflare가 레코드를 찾고, apex의 CNAME이므로 강제 플래트닝 대상이라고 판정한다.
2. `external-origin.test`를 해석한다. 외부 제공자가 `external-origin.test 7200 IN A 192.0.2.1`을 돌려준다.
3. 그 응답의 질의 이름을 원래 이름으로 덮어써서 `domain.test ... IN A 192.0.2.1` 형태로 만든다.
4. 프록시 상태에 따라 최종 응답이 갈린다.

마지막 단계가 실무에서 가장 중요하다.
프록시(주황색 구름)가 켜져 있으면 응답은 원본 IP가 아니라 Cloudflare 애니캐스트 IP 여러 개가 되고, TTL은 300으로 고정된다.
프록시가 꺼져 있으면(DNS only) 외부 제공자의 IP인 `192.0.2.1`이 그대로 나가고,
TTL은 외부 레코드의 값과 Cloudflare CNAME 레코드의 값 중 **작은 쪽**이 된다.

예시에서 외부가 7200, CNAME이 3600이므로 최종 TTL은 3600이다.
이 규칙이 중요한 이유는, DNS only 상태에서 사용자가 TTL을 온전히 통제하지 못한다는 뜻이기 때문이다.
CNAME 레코드의 TTL을 아무리 길게 잡아도 외부 레코드가 60초면 60초가 된다.

```bash
# 플래트닝 여부는 응답 타입으로 바로 확인된다
dig +noall +answer domain.test A
# 평탄화됨:   domain.test. 3600 IN A 192.0.2.1
# 평탄화 안 됨: domain.test. 3600 IN CNAME external-origin.test.
```

## 설정하기

적용 범위가 세 단계로 나뉘고, 각 단계의 조건이 다르다.

| 범위              | 조건                      | 동작                                     |
| ----------------- | ------------------------- | ---------------------------------------- |
| 존 apex           | 모든 요금제, 항상         | 이름이 `@`인 CNAME은 자동으로 평탄화된다 |
| 전체 CNAME 레코드 | 유료 요금제, 존 단위 설정 | 존의 모든 CNAME이 평탄화된다             |
| 개별 CNAME 레코드 | 유료 요금제, 레코드 단위  | 지정한 레코드만 평탄화된다               |

여기에 설정보다 우선하는 규칙이 하나 더 있다.
CNAME 대상이 같은 존 안에 있으면 Cloudflare는 설정값과 무관하게 평탄화를 진행한다.
설정 화면에서 껐다고 해서 안 되는 것이 아니므로, 같은 존 안을 가리키는 CNAME은 항상 평탄화된다고 봐야 한다.

프록시된 레코드도 마찬가지로 기본 평탄화 대상이다.
프록시 상태에서는 응답이 어차피 Cloudflare 애니캐스트 IP이므로 평탄화 외의 선택지가 없다.

존 전체를 켜려면 대시보드의 DNS Settings에서 `CNAME flattening for all CNAME records`를 켜거나,
Update DNS Settings 엔드포인트에 PATCH로 `flatten_all_cnames`를 `true`로 보낸다.

개별 레코드는 DNS Records 화면에서 해당 레코드를 편집해 `Flatten` 옵션을 켠다.
API로는 레코드 본문에 설정을 넣는다.

```json
{
  "settings": {
    "flatten_cname": true
  }
}
```

개별 설정을 쓰면 존 파일의 해당 레코드에 `cf-flatten-cname` 태그가 붙는다.
이 태그 덕분에 레코드를 내보내고 다시 가져와도 설정이 유지된다.
존 파일을 형상 관리하거나 다른 계정으로 옮기는 운영에서는 이 동작을 알고 있어야 한다.

`Flatten` 옵션이 아예 보이지 않는 경우가 세 가지 있고, 셋 다 이미 평탄화되고 있거나 재정의가 불가능한 상황이다.

- 레코드가 존 apex에 있다. 이미 강제로 평탄화된다.
- 레코드가 이미 프록시되어 있다. 기본으로 평탄화된다.
- 존 전체 설정이 켜져 있다. 레코드 단위로 끌 수 없다.

세 번째가 특히 중요하다.
전체 설정은 예외를 허용하지 않으므로, 한 레코드만 평탄화하지 않아야 한다면 전체 설정을 쓸 수 없고 개별 설정으로 가야 한다.

## 트레이드오프

### 표준을 지키려다 정보를 지운다

플래트닝이 하는 일은 결국 응답에서 CNAME이라는 사실을 지우는 것이다.
리졸버 입장에서 `domain.test`는 A 레코드를 가진 평범한 이름이고, 그 뒤에 다른 이름이 있다는 사실은 알 수 없다.

얻는 것은 표준 준수와 한 번의 왕복 절약이다.
잃는 것은 위임의 가시성이다.
`example.com`이 실제로는 SaaS 제공자의 호스트를 가리키고 있다는 사실이 DNS 응답에서 사라지므로,
장애가 났을 때 어느 계층이 문제인지를 응답만 보고 판단할 수 없다.

더 실질적인 대가는 갱신 전파다.
CNAME이 그대로 나가면 대상 IP가 바뀌었을 때 리졸버가 대상 존의 TTL을 따라 새 IP를 받는다.
평탄화되면 캐시에 남는 것은 IP이고, 그 IP의 수명은 앞서 본 TTL 규칙이 정한다.
대상이 IP를 자주 바꾸는 서비스라면, CNAME 레코드의 TTL을 길게 잡아 둔 것이 그대로 낡은 IP를 오래 들고 있는 시간이 된다.

여기서 빠져나갈 길이 좁다.
TTL을 짧게 잡으면 질의가 늘고, 길게 잡으면 전환이 느려지며,
DNS only에서는 외부 제공자가 자기 TTL을 짧게 유지해 주기를 기대하는 수밖에 없다.
문서가 최솟값 규칙을 명시한 것은 이 문제를 완화하려는 설계이지, 없애는 설계가 아니다.

### 서드파티 도메인 검증이 깨진다

문서가 두 번 반복해서 경고하는 항목이다.
서드파티 서비스가 도메인 소유를 확인하려고 특정 CNAME 레코드를 두라고 요구하는 경우,
전체 CNAME 평탄화를 켜면 그 검증이 실패한다.
검증기가 기대하는 것은 CNAME 레코드 자체인데, 응답에는 A 레코드만 나오기 때문이다.

이것이 까다로운 이유는 실패 시점이 설정 시점과 떨어져 있다는 데 있다.
평탄화를 켠 날에는 아무 일도 일어나지 않는다.
몇 달 뒤 인증서 갱신이나 재검증이 돌 때 비로소 실패하고, 그때 원인을 DNS 설정 변경까지 되짚어 올라가기가 어렵다.

해결은 개별 설정을 쓰는 것이지만, 앞서 본 제약이 여기서 걸린다.
전체 설정이 켜져 있으면 레코드 단위로 예외를 둘 수 없다.
그래서 검증용 CNAME이 하나라도 있는 존에서는 전체 설정이라는 선택지가 사실상 닫힌다.
편의를 위한 스위치가 예외를 허용하지 않아서 쓸 수 없게 되는 구조다.

### 끊어진 CNAME이 전파 문제처럼 보인다

최종 대상에 A/AAAA 레코드가 없으면(끊어진 CNAME) 평탄화할 IP가 없으므로 빈 응답, 즉 NODATA가 나간다.
문서는 이것이 마치 DNS 레코드가 전파되지 않는 것처럼 보일 수 있다고 적는다.

이 한 줄이 이 문서에서 가장 값진 부분이다.
평탄화가 없으면 같은 상황에서 CNAME 레코드는 정상적으로 응답되고, 그 다음 단계에서 대상이 없다는 사실이 드러난다.
평탄화가 있으면 그 단서가 사라지고 아무것도 없는 응답만 남는다.
증상이 원인에서 한 단계 멀어지는 것이다.

그래서 이 상황을 진단할 때는 응답이 아니라 대상을 직접 봐야 한다.

```bash
# apex 질의는 NODATA — 여기만 보면 원인을 알 수 없다
dig +noall +answer domain.test A

# 실제 원인은 대상 쪽에 있다. CNAME 대상을 직접 질의한다
dig +noall +answer external-origin.test A
dig +noall +answer external-origin.test AAAA
```

### 지리 기반 응답이 어긋난다

문서가 전혀 언급하지 않지만 HN 토론에서 곧바로 제기된 문제다.
대상이 질의자의 위치에 따라 다른 IP를 돌려주는 GeoDNS라면,
플래트닝은 그 판단을 망가뜨린다.
대상 입장에서 질의한 것은 최종 사용자가 아니라 Cloudflare의 서버이고,
따라서 돌아오는 IP는 Cloudflare 서버 근처의 것이다.

`zimbatm`이 이 점을 지적하면서 선행 사례도 함께 짚었다.[^zimbatm]
같은 동작이 DNSMadeEasy에서는 ANAME, 다른 제공자에서는 ALIAS라는 이름으로 이미 있었고,
발표 글이 그 선행 사례를 언급하지 않은 것이 아쉽다는 것이다.
`michaelbuckbee`가 정리한 바로는 DNSMadeEasy와 EasyDNS가 ANAME,
DNSimple과 PointDNS가 ALIAS를 쓴다.[^michaelbuckbee]
앞서 존 이전을 이야기할 때 이름이 제공자마다 다르다고 한 것이 이 목록이다.

완화 방법이 없지는 않다.
`samcrawford`는 상류 질의에 EDNS Client Subnet 옵션으로 원래 클라이언트의 IP를 실어 보내는 방법을 들었지만,
그것은 대상이 그 옵션을 지원한다는 전제가 필요하다고 덧붙였다.[^samcrawford]
`justincormack`은 실무적으로는 Cloudflare 서버 위치 기준으로 해석되므로 대개 괜찮다고 봤다.[^justincormack]
사용자가 가장 가까운 Cloudflare 거점에 닿는다면 그 거점의 위치가 사용자의 위치에 가깝기 때문이다.

이 논쟁의 결론은 애니캐스트 네트워크의 조밀함에 달려 있다는 것이다.
거점이 촘촘하면 오차가 작고, 대상 서비스의 지리적 판단이 세밀할수록 오차가 문제가 된다.
그래서 대상이 GeoDNS로 트래픽을 나누는 CDN이나 다중 리전 서비스라면,
플래트닝을 켜기 전에 실제로 어느 리전의 IP가 돌아오는지를 여러 지역에서 확인해야 한다.

### 도메인을 옮길 때 되돌아온다

플래트닝은 Cloudflare가 권한 있는 응답을 만드는 시점에 일어나는 일이므로, 존이 Cloudflare에 있는 동안에만 존재한다.
다른 DNS 제공자로 옮기면 apex의 CNAME은 그 제공자가 같은 기능을 제공하는지에 따라 운명이 갈린다.

ALIAS나 ANAME 같은 이름으로 같은 동작을 제공하는 제공자가 여럿 있으므로 대개는 옮길 수 있다.
다만 레코드 타입 이름이 다르고, TTL 처리 방식과 대상 해석 주기가 제공자마다 다르다.
표준 레코드가 아니라 각 제공자의 구현이기 때문이다.

그래서 apex CNAME은 존을 옮길 때 그대로 복사되지 않는 항목으로 목록에 올려 두어야 한다.
존 파일을 내보내서 가져오는 이전 절차에서 가장 조용히 깨지는 부분이 여기다.

## 함정

같은 존 안을 가리키는 CNAME은 설정과 무관하게 평탄화된다. 설정을 껐으니 CNAME이 그대로 나갈 것이라고 기대하면 어긋난다.

다른 Cloudflare 계정을 가리키는 CNAME은 금지되어 있고 Error 1014(CNAME Cross-User Banned)가 난다. 같은 Cloudflare를 쓰는 서비스를 가리킬 때 걸린다.

DNS only 상태의 TTL은 외부 레코드와 CNAME 레코드 중 작은 쪽이다. 대시보드에 적힌 TTL이 실제 응답의 TTL이라고 가정할 수 없다.

프록시 상태에서는 TTL이 300으로 고정되고 응답 IP가 Cloudflare의 것이다. 원본 IP를 기준으로 방화벽 허용 목록을 만드는 쪽에서는 이 사실이 전제를 바꾼다.

전체 평탄화를 켜면 개별 레코드로 예외를 둘 수 없다. 나중에 검증용 CNAME이 하나 필요해지면 전체 설정을 끄고 개별 설정으로 전부 다시 잡아야 한다.

끊어진 CNAME은 오류가 아니라 빈 응답으로 나타난다. 전파 지연으로 오진하기 쉬우므로 대상을 직접 질의해서 확인해야 한다.

개별 설정은 존 파일의 `cf-flatten-cname` 태그로 유지된다. 태그를 이해하지 못하는 도구로 존 파일을 가공하면 설정이 조용히 사라진다.

## 확인하기

평탄화 여부는 응답 타입 하나로 판정되므로 확인이 간단하다.

```bash
# 1. 권한 있는 서버에 직접 물어서 캐시를 배제한다
dig @ns1.cloudflare.com domain.test A +noall +answer

# 2. CNAME이 나오면 평탄화되지 않은 것, A가 나오면 평탄화된 것이다

# 3. TTL 규칙을 확인하려면 대상의 TTL과 비교한다
dig +noall +answer external-origin.test A   # 예: 7200
dig +noall +answer domain.test A            # 최솟값이 적용되었는지 본다
```

프록시 상태를 바꿔 가며 같은 질의를 해 보면 TTL 300과 애니캐스트 IP로 바뀌는 것을 직접 볼 수 있다.
설정 문서를 읽는 것보다 이 비교가 동작을 정확히 알려 준다.

## 체크리스트

- apex에 CNAME을 두었고, 그것이 강제 평탄화된다는 사실을 알고 있는가
- 존 안에 서드파티 검증용 CNAME이 있는가, 있다면 전체 평탄화를 켜지 않았는가
- CNAME 대상이 실제로 A 또는 AAAA 레코드로 해석되는가
- DNS only 레코드의 실제 TTL을 외부 레코드 TTL과 비교해서 확인했는가
- 대상이 다른 Cloudflare 계정의 존이 아닌가
- 존 파일을 내보내고 가져오는 절차가 `cf-flatten-cname` 태그를 보존하는가
- 다른 DNS 제공자로 옮길 계획이 있다면 apex CNAME의 대체 수단을 확인했는가

## 기억할 원칙

### 표준의 제약을 응답 생성 시점으로 옮겨서 푸는 방법

apex에 CNAME을 둘 수 없다는 것은 저장 형식의 제약이 아니라 프로토콜 응답의 제약이다.
CNAME과 다른 레코드가 같은 이름에 공존할 수 없다는 규칙은 리졸버가 받는 응답에 대한 규칙이지,
운영자가 설정 화면에 무엇을 입력하는지에 대한 규칙이 아니다.

플래트닝은 이 구분을 이용한다.
입력은 CNAME으로 받고, 출력은 A로 만든다.
표준을 바꾸지도 않고 어기지도 않으면서, 운영자가 원하던 것을 준다.

같은 형태가 다른 곳에도 있다.
데이터베이스의 뷰가 정규화된 테이블 위에 비정규화된 모양을 보여 주는 것,
컴파일러가 소스의 편의 문법을 표준 형태로 낮추는 것이 같은 구조다.
제약이 실제로 어느 계층에 걸려 있는지를 정확히 짚으면, 그 아래나 위에서 변환할 여지가 생긴다.

이 우회가 필요한 이유를 다른 계층에서 찾는 시각도 있다.
`rlpb`는 클라이언트가 SRV 레코드를 조회했다면 이 문제 자체가 없었을 것이라고 적었다.[^rlpb]
SRV는 사용자가 보는 이름과 실제 서버 이름을 나누는, 바로 이 상황을 위해 만들어진 추상이고,
CNAME을 여기에 쓰는 것은 둥근 구멍에 네모난 못을 넣는 일이라는 것이다.
그러니 문제는 DNS의 경직성이 아니라 새 기능을 쓰지 않는 클라이언트의 경직성이라고 봤다.

`teddyh`의 반박이 이 논의를 한 계층 더 옮긴다.
SRV 명세는 프로토콜 정의가 SRV 사용을 명시하지 않은 프로토콜에서 SRV를 쓰는 것을 금지한다.[^teddyh]
HTTP 명세가 SRV를 언급하지 않으므로 브라우저는 SRV를 조회할 수 없고,
따라서 책임은 브라우저가 아니라 HTTP 표준을 쓰는 쪽에 있다는 것이다.

이 주고받음이 보여 주는 것은 제약이 걸린 계층을 짚는 일이 생각보다 어렵다는 점이다.
같은 문제를 두고 DNS 명세, 클라이언트 구현, HTTP 표준이 차례로 지목되었고,
각 지목이 앞의 지목을 반박하면서 한 계층씩 위로 올라갔다.
플래트닝이 실제로 선택한 자리는 그중 어느 것도 아닌, 권한 있는 서버의 응답 생성 시점이다.
고칠 수 있는 계층이 자기가 통제하는 계층뿐일 때 답은 그곳에서 나온다.

다만 대가도 같은 형태로 온다.
변환이 일어난다는 사실이 결과물에는 남지 않으므로, 문제가 생겼을 때 증상과 원인 사이의 거리가 멀어진다.
끊어진 CNAME이 전파 문제로 보이는 것이 바로 그 대가이며,
이런 종류의 우회를 도입할 때는 변환 사실을 드러내는 진단 수단을 함께 준비해야 한다.
