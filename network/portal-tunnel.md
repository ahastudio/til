Show GN: [Portal-Tunnel: 로컬에서 퍼블릭으로 | GeekNews](https://news.hada.io/topic?id=28973)

## 소개

Portal은 로컬 서비스를 셀프호스팅 릴레이나 공개 릴레이를 통해 공개하는 터널 런타임이자 릴레이 네트워크다.

README가 내거는 조건이 넷이다. **포트 포워딩 없음, 인바운드 방화벽 규칙 없음, 수동 DNS 설정 없음, 계정 없음.**

라이선스는 MIT이고, 자기 정의를 “에이전트 웹에 서비스를 게시하기 위한” 런타임이라고 적는다.
로컬 앱·API·도구·에이전트를 릴레이를 통해 게시하고, 라우팅과 x402 결제 정책을 터널 프로세스 안에 유지하며, 호스팅 벤더 계정을 요구하지 않는 것이 목표다.

[Cloudflare Quick Tunnels 노트](../cloudflare/quick-tunnels.md)가 다룬 문제와 같은 영역인데, 답이 정반대 방향이다.
Quick Tunnels가 단일 사업자의 엣지에 모든 것을 맡기는 대신 마찰을 0으로 만든다면, Portal은 **릴레이를 신뢰하지 않는 것**을 설계의 출발점으로 삼는다.

## 핵심 주장

README가 일곱 가지를 내세운다.

**셀프호스팅 가능, 완전 오픈소스**: 명령 하나로 자기 릴레이를 돌릴 수 있고, 릴레이가 MIT 라이선스이며 엔터프라이즈 티어도 기능 게이팅도 콜홈도 없다는 것이다.

**익명 릴레이 네트워크**: 호스팅 계정이나 중앙 운영자 없이 공개 릴레이에 연결한다. 셀프호스팅 릴레이와 공개 릴레이를 풀로 묶어 **직접 고른 독립 운영자들에게 신뢰를 분산**할 수 있다고 적는다.

**선택적 정적 캐시**: `portal expose --serve ./dist --cache`가 정적 콘텐츠를 릴레이의 제한된 디스크 저장소로 넘기며, 오프라인 TTL을 선택할 수 있다.
그리고 이 모드가 무엇을 포기하는지 명시한다. **선택한 릴레이에 파일과 브라우저 TLS 종단을 명시적으로 신뢰하는 것**이다.

**종단 간 테넌트 TLS와 ECH**: 캐시하지 않는 일반 노출에서는 릴레이가 아니라 사용자 엔드포인트에서 테넌트 TLS를 종단한다. 평문 SNI로 실제 호스트명이 드러나지 않도록 ECH도 제공한다.

**내장 MITM 탐지**: 실제 트래픽이 시작된 뒤 자기 연결을 능동적으로 자가 탐침한다. 양쪽에서 내보낸 TLS 키 재료를 비교하고 불일치를 릴레이 측 TLS 종단 의심으로 취급한다.

**계정도 API 키도 없음**: 인증이 로컬에서 생성한 secp256k1 키 쌍을 쓰는 SIWE 호환 서명이다. 이메일도 등록도 벤더 종속도 없다.

**내장 x402 결제**: 라우팅된 HTTP 경로가 프록시 전에 Sui 가스리스 USDC나 Casper wCSPR x402 결제를 요구할 수 있다.
브라우저 앱은 `/x402/client.js`를 임포트하고, 네이티브 클라이언트는 `/x402/prepare`를 직접 호출해 `X-PAYMENT`를 보낸다.

## 동작 방식

종단 간 암호화가 이 프로젝트의 중심 주장이므로 경로를 그대로 옮긴다.

```text
브라우저
  -> 릴레이 SNI 라우터   (라우팅 토큰만 읽고 원시 바이트를 전달)
  -> 리버스 세션
  -> Portal 터널          (로컬에서 TLS 핸드셰이크 수행, 세션 키 도출)
  -> 로컬 서비스
```

절차가 다섯 단계로 설명된다.

1. 릴레이가 들어오는 연결을 받아 **SNI 기반 라우팅을 위해 TLS ClientHello만** 읽는다.
2. TLS를 종단하지 않고 원시 암호화 스트림을 리버스 세션으로 전달한다.
3. 사용자 쪽 Portal 터널이 로컬에서 핸드셰이크를 완료한다. **세션 키가 사용자 기기에서 도출된다.**
4. 릴레이가 호스팅하는 도메인의 경우, 터널이 `/v1/sign`을 통해 인증서 서명을 받는다. 릴레이를 **키리스 서명 오라클**로만 쓰는 것이며, 릴레이는 핸드셰이크 다이제스트에 서명하지만 세션 키를 받지 않는다.
5. 핸드셰이크 이후 릴레이는 평문에 접근하지 못한 채 암호문을 계속 전달한다.

ECH를 켜면 릴레이가 실제 테넌트 호스트명도 볼 수 없다.
터널 신원에서 파생된 불투명한 토큰으로 라우팅하고, 진짜 SNI는 ECH로 보호된 ClientHello 안에 남는다.

이 설계가 기존 터널 서비스와 갈리는 지점이 3번과 4번이다.
보통의 터널은 릴레이가 TLS를 종단하므로 운영자가 평문을 볼 수 있는데, 여기서는 릴레이가 라우팅에 필요한 최소 정보만 읽고 지나간다.

## 사용법

설치와 기본 노출이 두 줄이다.

```bash
# macOS / Linux
curl -fsSL https://github.com/gosuda/portal-tunnel/releases/latest/download/install.sh | bash
portal expose 3000
```

```powershell
# Windows (PowerShell)
$ProgressPreference = 'SilentlyContinue'
irm https://github.com/gosuda/portal-tunnel/releases/latest/download/install.ps1 | iex
portal expose 3000
```

더 구체적인 사용 예들이다.

```bash
# 커스텀 이름과 릴레이 지정, 자동 탐색 끄기
portal expose 3000 --name myapp --relays https://portal.example.com --discovery=false

# 리버스 스트림에 IVNP 오버레이 전송을 선호
portal expose 3000 --overlay

# 프런트엔드와 API를 한 URL 뒤에 마운트
portal expose --name myapp \
  --http-route /api=http://127.0.0.1:3001 \
  --http-route /=http://127.0.0.1:5173

# 특정 경로에 Sui USDC x402 결제를 요구
portal expose --name paid-app \
  --http-route "/paid=http://127.0.0.1:3001 GET:0.01" \
  --http-route /=http://127.0.0.1:5173 \
  --x402-pay-to 0x...

# 원시 TCP 포트 (Minecraft, 데이터베이스, SSH)
portal expose localhost:25565 --name minecraft --tcp
```

마지막 줄이 중요한 차이다. **HTTP(S) 외의 원시 TCP를 지원한다.**
Quick Tunnels가 HTTP(S)에 사실상 한정된 것과 대비된다.

### 지속 터널

터미널 밖에서 계속 돌아야 하는 터널을 위해 Portal Agent를 쓴다.
로컬 OS 서비스로 돌면서 하나의 TOML 설정에 있는 모든 터널을 살려 두고, 공개 릴레이 관리용 대시보드를 제공한다.

```bash
portal agent run --config config.toml
portal agent dashboard --config config.toml
portal agent restart --config config.toml
portal agent stop --config config.toml

# 포그라운드 모드는 OS 서비스 설치를 건너뛴다
portal agent run --config config.toml --foreground
```

### 자체 릴레이 운영

```bash
git clone https://github.com/gosuda/portal-tunnel
cd portal-tunnel && cp .env.example .env
docker compose up
```

공개 배포에는 DNS 자동화(ACME), TCP/UDP 포트 범위, 릴레이 정책 설정이 따로 문서화되어 있다.

### 에이전트 플러그인

저장소에 Codex, Claude Code, Cursor용 `portal-deploy` 플러그인이 포함되어 있다.

공유되는 `portal-expose` 스킬이 로컬 앱을 검사하고, Portal 터널을 열고, 명시적으로 요청된 x402 유료 경로를 설정하고, 공개 URL과 결제 챌린지를 검증한 뒤 생명주기를 넘긴다.

```bash
# GitHub CLI
gh skill install gosuda/portal-tunnel portal-deploy/portal-expose

# skills CLI
npx skills add gosuda/portal-tunnel --skill portal-expose
```

## 트레이드오프

### 캐시를 켜는 순간 종단 간 보장이 사라진다

이 프로젝트의 가장 정직한 부분이자 가장 중요한 함정이다.

README가 기능 목록에서 세 항목에 괄호를 달아 둔다. 종단 간 테넌트 TLS, SNI 은닉, MITM 자가 탐침이 모두 **“비캐시 노출”**에 한정된다.

그리고 캐시 항목에서 그 이유를 직접 적는다. 선택한 릴레이에 파일과 브라우저 TLS 종단을 명시적으로 신뢰하는 것이라는 문장이다.

구조적으로 당연한 결과다.
릴레이가 정적 파일을 대신 서빙하려면 그 파일을 갖고 있어야 하고, 브라우저에 직접 응답하려면 TLS를 종단해야 한다.

문제는 이 전환이 **플래그 하나**로 일어난다는 점이다.
`--cache`를 붙이면 신뢰 모델이 통째로 바뀌는데, 명령줄에서는 그냥 성능 옵션처럼 보인다.

그래서 실무에서 지켜야 할 규칙이 생긴다. 어느 노출이 캐시 모드인지를 추적해야 하고, 캐시 모드에서는 **릴레이 운영자를 콘텐츠 열람 주체로 간주**해야 한다.

### 신뢰 분산이 운영자를 아는 것을 전제한다

익명 릴레이 네트워크 항목이 매력적인 문구를 쓴다. 직접 고른 독립 운영자들에게 신뢰를 분산한다는 것이다.

그런데 공개 릴레이 레지스트리가 GitHub 저장소의 `registry.json`이고, 공개 릴레이를 운영하면 풀 리퀘스트를 열어 자기 URL을 추가하라고 안내한다.
그리고 터널 클라이언트가 **기본적으로 이 레지스트리를 포함한다**.

두 문장이 함께 놓이면 긴장이 생긴다.
“직접 고른”이라는 표현은 사용자가 운영자를 안다는 뜻인데, 기본값은 레지스트리에 있는 모든 릴레이를 신뢰 후보로 삼는 것이다.

병합 심사가 어떤 기준으로 이루어지는지는 README에 없다.

다만 이 위험이 종단 간 TLS로 상당 부분 완화된다는 점도 사실이다.
릴레이가 평문을 못 보므로 악의적 운영자가 얻는 것이 트래픽 메타데이터와 가용성 통제로 제한된다.

그래서 실제로 중요한 설정이 이것이다.

```bash
# 자동 탐색을 끄고 신뢰하는 릴레이만 명시한다
portal expose 3000 --relays https://portal.example.com --discovery=false
```

`--discovery=false`가 기본값이 아니라는 점을 알고 쓰는 것과 모르고 쓰는 것의 차이가 크다.

### MITM 탐지는 탐지이지 방지가 아니다

자가 탐침 기능이 이 프로젝트에서 가장 독창적인 부분이다.

방식이 영리하다. 실제 트래픽이 시작된 뒤 양쪽에서 내보낸 TLS 키 재료(exported keying material)를 비교해, 불일치하면 릴레이가 TLS를 종단하고 있다고 의심하는 것이다.
릴레이가 중간에서 TLS를 다시 맺으면 양쪽 세션의 키 재료가 달라지므로 원리상 탐지된다.

그런데 README는 탐지 이후를 말하지 않는다.
불일치가 발견되면 연결을 끊는지, 경고만 찍는지, 해당 릴레이를 풀에서 제외하는지가 적혀 있지 않다.

그리고 타이밍 문제가 남는다. 탐침이 **실제 트래픽이 시작된 뒤**에 일어나므로, 탐지 시점까지 흘러간 데이터는 이미 노출된 뒤다.

즉 이 기능의 값어치는 실시간 차단이 아니라 **사후 신뢰 평가**에 있다.
릴레이가 장기적으로 정직한지를 확인하는 용도로는 훌륭하고, 한 번의 민감한 요청을 지키는 용도로는 부족하다.

### 결제 기능이 터널 도구의 범위를 넘어선다

x402 결제가 README에서 큰 비중을 차지하고 비교표에서도 Portal만의 항목으로 제시된다.

이 결합의 논리는 이해된다.
“에이전트 웹에 게시한다”는 목표에서, 에이전트가 접근하는 엔드포인트에 기계가 지불할 수 있는 요금을 붙이는 것이 자연스러운 다음 단계이기 때문이다.

그런데 대가가 있다.

첫째, 터널 도구가 **특정 체인에 결합된다**. Sui의 가스리스 USDC와 Casper의 wCSPR이 명시되어 있다.
이 선택이 바뀌거나 해당 네트워크가 문제를 겪으면 터널 도구의 기능 하나가 영향을 받는다.

둘째, 인증 방식이 이미 secp256k1 키 쌍과 SIWE 호환 서명이다.
계정을 없애는 대신 지갑 키를 도입한 것이고, 그 키를 잃으면 신원을 잃는다.
“계정도 API 키도 없음”이라는 문구가 정확하지만, 관리할 비밀이 사라진 것이 아니라 종류가 바뀐 것이다.

셋째, 감사 범위가 넓어진다. 터널의 보안 검토가 이제 결제 경로까지 포함해야 한다.

### IVNP 오버레이 설명이 경계를 조심스럽게 긋는다

`--overlay` 플래그 설명이 README에서 가장 조심스럽게 쓰인 문단이다.

Portal이 여전히 두 엔드포인트(공개 인그레스와 오버레이 게이트웨이)를 선택하고 인가하며 위임된 리버스 능력을 발급하는 반면, 게이트웨이와 인그레스 사이의 네트워크 경로는 **IVNP가 소유**한다는 것이다.
그 한 논리적 홉을 Portal에게 보이지 않는 여러 내부 I2P 스타일 라우터 홉으로 나를 수 있다고 적는다.

그리고 세 문장으로 책임을 구획한다. **Portal은 엔드포인트를 선택하고 인가한다. IVNP는 목적지를 연결한다. Portal은 그 사이의 경로를 소유하지 않는다.**

직접 리버스 전송이 여전히 기본값이자 폴백이며, Portal 수준의 다중 홉 라우팅은 기능이 아니라고 못을 긋는다. 과거의 릴레이 체인 모델과 WireGuard 메시는 제거되었다는 이력도 함께 적는다.

이 문단이 조심스러운 이유가 분명하다.
익명 오버레이를 제공한다고 주장하면 그 익명성의 강도에 대한 책임이 따라오는데, Portal은 그 경로를 통제하지 않으므로 보증할 수 없다.

제거된 기능들을 명시한 것도 성숙한 선택이다.
릴레이 체인과 메시를 없애고 “엔드포인트 선택과 인가”로 범위를 좁힌 것이, 보안 주장을 실제로 지킬 수 있는 크기로 만든 것이다.

## 함정

### 설치 방법이 `curl | bash`다

README의 첫 설치 명령이 릴리스 스크립트를 내려받아 바로 실행하는 형태다.

보안을 중심 주제로 삼는 도구에서 이 방식은 어울리지 않는다.
종단 간 TLS와 MITM 탐지를 자랑하면서, 정작 바이너리를 얻는 경로는 스크립트를 검토 없이 실행하는 것이다.

Go 프로젝트이므로 `go install`이나 릴리스 바이너리 직접 검증 같은 대안이 가능한데 README에 제시되지 않는다.

실무에서는 최소한 스크립트를 먼저 받아 읽는 편이 낫다.

```bash
curl -fsSL -o install.sh https://github.com/gosuda/portal-tunnel/releases/latest/download/install.sh
less install.sh
bash install.sh
```

### 익명 노출의 남용 문제가 다뤄지지 않는다

계정 없음이 이 프로젝트의 핵심 매력인데, 그 결과에 대한 논의가 README에 없다.

[Quick Tunnels 노트](../cloudflare/quick-tunnels.md)에서 ngrok 창업자가 남긴 판단이 여기에 더 강하게 적용된다.
익명 사용이 플랫폼 전체에서 압도적으로 가장 큰 남용 원천이었고, 그래서 익명 계층을 제거했다는 것이다.

Cloudflare는 최소한 단일 운영자이므로 남용이 발생하면 도메인 단위로 차단하거나 정책을 바꿀 수 있다.
Portal의 공개 릴레이 네트워크에는 그 주체가 없다.

그리고 릴레이 운영자 입장에서 문제가 더 날카롭다.
종단 간 TLS 때문에 릴레이가 **자기 인프라를 통과하는 트래픽의 내용을 볼 수 없다**.
이것이 사용자에게는 프라이버시 보장이지만, 운영자에게는 자기 IP에서 나가는 것이 무엇인지 모른 채 책임을 지는 구조다.

즉 보안 설계의 강점이 운영 책임 면에서는 약점이 된다.
자체 릴레이를 공개 레지스트리에 올리기 전에 이 점을 계산해야 한다.

### 비교표가 자기 저작물이라는 점을 감안해야 한다

비교표의 몇 칸은 논쟁 여지가 있다.

Cloudflare Tunnel의 셀프호스팅이 “아니요”로 표시되어 있는데, `cloudflared` 클라이언트는 오픈소스다.
다만 같은 행의 오픈소스 칸에 “클라이언트만”이라고 적어 그 사실을 인정하고 있으므로, 여기서 “셀프호스팅”은 릴레이 측을 자기가 돌릴 수 있느냐를 뜻하는 것으로 읽어야 한다. 그 기준에서는 맞는 표시다.

`frp`의 다중 릴레이 장애 조치가 “아니요”인 것, ngrok의 것이 “관리형”인 것도 기준에 따라 달라진다.

표 전체가 Portal이 모든 행에서 유리하게 배열되어 있다는 점만 인지하면 된다.
이런 표는 후보를 좁히는 데 쓰고, 실제 선택은 각 항목을 직접 확인해 결정하는 것이 맞다.

### 성숙도 신호를 README에서 읽기 어렵다

CI 배지와 릴리스 배지가 있고 `awesome-tunneling` 등재 배지도 있다.

그런데 HN에서 `gosuda/portal`로 세 번 Show HN이 올라왔고 각각 2점·1점·1점에 댓글이 0개였다.
2025년 11월 30일, 2025년 12월 15일, 2026년 3월 6일이다.

즉 외부 검토가 거의 이루어지지 않은 상태다.
보안 주장이 강한 프로젝트일수록 이 점이 중요하다. 종단 간 TLS, 키리스 서명 오라클, ECH, MITM 탐지가 전부 구현 세부에서 틀리기 쉬운 것들이다.

README에 보안 모델 문서 링크가 있다는 점은 좋은 신호다. 다만 제3자 감사에 대한 언급은 없다.

## 확인하기

릴레이가 정말 TLS를 종단하지 않는지 직접 확인할 수 있다.

```bash
# 1. 요청을 그대로 되비추는 로컬 서버를 띄운다
python3 -m http.server 3000 &

# 2. 노출한다
portal expose 3000 --name check

# 3. 발급된 URL의 인증서 체인을 확인한다
echo | openssl s_client -connect <호스트>:443 -servername <호스트> 2>/dev/null \
  | openssl x509 -noout -issuer -subject -dates
```

캐시 모드와 비캐시 모드를 각각 돌려 인증서와 응답 헤더를 비교하면, 두 모드의 신뢰 경계 차이가 드러난다.

릴레이가 라우팅 토큰만 읽는다는 주장은 릴레이를 직접 돌려 확인하는 것이 가장 확실하다.

```bash
git clone https://github.com/gosuda/portal-tunnel
cd portal-tunnel && cp .env.example .env
docker compose up
# 자기 릴레이를 지정해 노출하고 릴레이 쪽 로그에서 평문이 보이는지 본다
portal expose 3000 --relays http://localhost:8080 --discovery=false
```

이것이 셀프호스팅 가능한 오픈소스라는 점의 실질적 가치다. **신뢰 주장을 직접 검증할 수 있다.**

## 체크리스트

- 이 노출이 캐시 모드인가? 그렇다면 릴레이 운영자를 콘텐츠 열람 주체로 간주했는가?
- `--discovery=false`로 릴레이를 명시했는가, 아니면 기본 레지스트리를 쓰고 있는가?
- 쓰는 공개 릴레이의 운영자를 실제로 아는가?
- secp256k1 키 쌍을 백업했는가? 이것이 신원이므로 잃으면 복구 수단이 없다.
- x402 경로를 설정했다면 결제 대상 주소가 맞는지 확인했는가?
- 자체 릴레이를 공개 레지스트리에 올린다면, 내용을 볼 수 없는 트래픽에 대한 책임을 감당할 수 있는가?
- 노출한 로컬 서비스 자체에 인증이 걸려 있는가? 터널은 인증을 추가하지 않는다.

## 기억할 원칙

### 릴레이를 신뢰하지 않는 설계가 릴레이 사업 모델을 바꾼다

기존 터널 서비스의 경제 구조는 릴레이가 트래픽의 중심에 있다는 데서 나온다.
TLS를 종단하므로 캐싱·압축·WAF·분석 같은 부가 가치를 얹을 수 있고, 그것이 유료 티어의 내용이 된다.

Portal의 설계는 그 자리를 비운다.
릴레이가 암호문을 전달하는 파이프이고, 부가 가치를 얹으려면 캐시 모드로 전환해 종단 간 보장을 포기해야 한다.

그래서 이 프로젝트가 MIT이고 엔터프라이즈 티어가 없다는 것이 이념적 선택이 아니라 **구조적 귀결**에 가깝다.
릴레이가 볼 수 있는 것이 없으면 릴레이로 팔 것도 별로 없다.

여기서 나오는 일반적 관찰이 있다.
중개자의 가시성을 없애는 설계는 **중개자의 수익 모델도 함께 없앤다**.
그래서 이런 설계는 대체로 오픈소스와 셀프호스팅 쪽에서 나오고, 상업 서비스는 반대 방향으로 간다.

그리고 이것이 공개 릴레이 네트워크의 지속 가능성 문제로 이어진다.
운영자가 트래픽을 못 보고 계정도 없고 과금 수단도 없다면, 왜 릴레이를 돌리는가.
x402 결제가 이 질문에 대한 답의 시도로 읽히지만, README는 그 연결을 명시하지 않는다.

### 플래그 하나가 신뢰 모델을 바꾸면 그 사실이 이름에 드러나야 한다

`--cache`가 성능 옵션처럼 보이지만 실제로는 위협 모델을 바꾸는 스위치다.

이런 종류의 설계는 흔하고 위험하다.
비슷한 예가 TLS 검증을 끄는 `-k`나 `--insecure` 플래그인데, 그것들은 최소한 이름이 경고를 담고 있다.

Portal의 문서는 이 점을 본문에서 정직하게 설명하지만, 명령줄에서는 그 경고가 사라진다.
기능 목록의 괄호(“비캐시 노출”)도 README를 끝까지 읽은 사람에게만 보인다.

이전 가능한 원칙은 이렇다. 보안 속성을 바꾸는 옵션은 **이름에서 그 사실이 읽혀야 하고**, 그 옵션이 켜진 상태가 런타임 출력에 계속 표시되어야 한다.

이것이 사용자 실수를 막는 가장 싼 방법이고, 특히 에이전트가 명령을 조립하는 환경에서 중요해진다.
`portal-deploy` 플러그인이 에이전트에게 노출 명령을 맡기는데, 에이전트가 성능을 이유로 `--cache`를 붙이면 사람이 모르는 사이 신뢰 경계가 옮겨진다.

### 에이전트 웹이라는 표현이 터널 도구의 요구사항을 바꾸고 있다

README가 자기를 “에이전트 웹에 게시하기 위한” 런타임이라고 부른다.

[Quick Tunnels](../cloudflare/quick-tunnels.md)도 같은 시기에 에이전트를 1급 사용자로 호명했다. JSON 출력을 더한 것이 그 개편의 실질이었다.

두 프로젝트가 서로 다른 것을 에이전트용 기능으로 골랐다는 점이 흥미롭다.
Cloudflare는 **기계가 읽을 수 있는 출력**을 골랐고, Portal은 **기계가 지불할 수 있는 요금**과 **에이전트 CLI용 스킬 패키지**를 골랐다.

이 차이가 두 제품의 위치를 드러낸다.
전자는 에이전트를 터널의 사용자로 보고, 후자는 에이전트를 터널 너머 서비스의 **고객**으로 본다.

그리고 후자의 그림이 성립하려면 조건이 있다.
에이전트가 자율적으로 지불할 수 있어야 하고, 그러려면 지갑과 예산과 승인 정책이 필요하다.
README는 그 정책 부분을 다루지 않는다. `--x402-pay-to`로 수취 주소를 정하는 것은 서비스 제공자 쪽이고, 지불하는 쪽의 통제는 범위 밖이다.

여기서 지금 단계에서 실용적인 결론이 나온다.
에이전트가 여는 터널을 다룰 때, **그 터널이 무엇을 노출하는지와 무엇을 청구하는지**를 사람이 승인 목록으로 관리해야 한다.
도구가 두 가지를 모두 플래그 하나로 설정할 수 있게 만들어 두었기 때문에 더 그렇다.
