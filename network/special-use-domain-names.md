# RFC 6761: 특수 용도 도메인 이름을 예약하는 규칙

원문: [RFC 6761: Special-Use Domain Names | RFC Editor](https://www.rfc-editor.org/info/rfc6761/)

## 소개

RFC 6761은 2013년 2월에 Apple의 Stuart Cheshire와 Marc Krochmal이
낸 Standards Track 문서이며, RFC 1918과 RFC 2606을 갱신한다.
도메인 이름을 특수 용도(special-use)로 예약한다는 말이 정확히 무엇을 뜻하는지,
어떤 경우에 예약이 적절한지, 어떤 절차로 예약하는지를 정한다.
그 결과를 담을 IANA 등록부(Special-Use Domain Names registry)를 만들고,
이미 쓰이던 이름 몇 개로 등록부를 채운다.

이 문서가 필요해진 이유는 RFC 2606의 빈칸이다.
RFC 2606은 `example.com`, `example.net`,
`example.org`와 최상위 이름 `invalid`를 예약했지만,
구현이 이 이름을 다르게 다뤄야 하는지,
다룬다면 어떻게 다뤄야 하는지는 말하지 않았다.
RFC 6761은 그 빈칸을 두 가지로 메운다.
하나는 이름마다 소프트웨어가 어떻게 행동해야 하는지를 일곱 갈래로 나눠 적게 하는
틀이고, 다른 하나는 그 틀로 `test`, `localhost`, `invalid`,
`example` 계열과 사설 주소 역방향 영역의 행동을 적어 둔 초기 등록 내용이다.

이 문서의 계약은 한 문장으로 줄일 수 있다.
예약된 이름은 어느 네트워크에서나 같은 의미를 가져야 하고,
그 의미는 ICANN의 이름 할당이 아니라 프로토콜 규칙으로 정해진다.
반대로 이 문서가 약속하지 않는 것도 분명하다.
이름별 행동 규정 대부분이 `SHOULD`이고 `MUST NOT`은 등록 기관 칸뿐이어서,
어떤 리졸버(resolver)나 DNS 서버가 이 규칙을 따를지는 구현에 달려 있다.

## 동작 방식

### 예약이 적절한 경우

RFC 6761은 이름을 예약해도 되는 기준을 구현에 미치는 영향으로 잡는다.
어떤 이름에 특별한 성질이 있어서,
그 성질이 접속한 네트워크와 무관하게 하드웨어와 소프트웨어의
이름 처리에 영향을 준다면 특수 용도 이름의 후보가 된다.
반대로 예약해도 구현이 하나도 바뀌지 않는다면
그 이름은 실질적으로 특별하지 않은 것이므로,
기존 DNS 위임이나 데이터 등록 절차로 풀어야 한다.
본문은 특수 용도 이름 예약이 일반 도메인 등록 절차를 우회하는 수단이 아니라고
분명히 적는다.

이 기준의 근거는 책임 소재다.
어떤 이름이 항상 `NXDOMAIN`을 돌려준다고
정해 놓고 개발자가 그것을 믿고 쓴다고 하자.
사용자의 DNS 서버가 그 이름에 긍정 응답을 돌려주면
개발자의 소프트웨어가 실패하는데, 이때 사용자는 ICANN에 따져야 하는지,
IETF에 따져야 하는지, DNS 서버 운영자에게 따져야 하는지 알 수 없다.
RFC는 그래서 보장을 프로토콜 수준에서 걸어야 한다고 말한다.
사설 네트워크의 DNS 설정은 ICANN의 관할 밖이지만,
프로토콜 규칙은 모든 네트워크에서
긍정 응답을 규칙 위반으로 만들 수 있다는 논리다.

### 일곱 가지 고려 범주

예약을 요청하는 문서는
IETF의 Standards Action 또는 IESG Approval을 거친 명세여야 하고,
어떤 이름에 특별 처리를 적용할지를 구현이 판별하는 방법을 밝혀야 한다.
보통은 특정 접미사로 끝나는 모든 정규화된 도메인 이름(FQDN)이 해당한다고
적어서 DNS 이름 공간의 한 가지(subtree)를 떼어 낸다.
이어서
IANA Considerations 절 안의 Domain Name Reservation Considerations
소절에 아래 일곱 질문에 대한 답을 적어야 한다.
일곱 답이 모두 아무것도 없음이면 특수 처리가 필요 없다는 뜻이고,
예약 요청 자체가 부적절할 수 있다.

| 번호 | 대상                       | 묻는 것                                                        |
| ---- | -------------------------- | -------------------------------------------------------------- |
| 1    | 사용자                     | 사람이 이 이름을 특별하게 알아보고 다르게 써야 하는가          |
| 2    | 응용 소프트웨어            | 이 이름을 인식하고 다르게 처리해야 하는가(예: 입력 거부)       |
| 3    | 이름 해석 API와 라이브러리 | 이 이름을 인식하고 다르게 처리해야 하는가                      |
| 4    | 캐싱 DNS 서버              | 이 이름을 인식하고 다르게 처리해야 하는가                      |
| 5    | 권한 DNS 서버              | 이 이름을 인식하고 다르게 처리해야 하는가                      |
| 6    | DNS 서버 운영자            | 이 이름 때문에 설정이나 운영에 생기는 영향이 있는가            |
| 7    | 등록 기관과 등록 대행      | 이 이름의 등록 요청을 거부하는가, 지정된 주체에게만 허용하는가 |

이 표는 이 문서의 가장 쓸모 있는 부분이다.
예약 이름 하나를 이해한다는 것은 이 일곱 칸을 채울 수 있다는 뜻이다.
또 같은 칸에서 이름끼리 비교하면
어떤 이름이 다른 이름보다 얼마나 강한 약속인지가 드러난다.

## 등록된 이름의 대우

RFC 6761의 6절은 초기 등록 내용을 이름별로 일곱 칸씩 채워 놓았다.
아래는 그 내용을 이름 해석 쪽(칸 3~5)을 중심으로 줄인 비교다.

| 이름           | 해석 API와 라이브러리                  | 캐싱·권한 DNS 서버         | 등록 기관            |
| -------------- | -------------------------------------- | -------------------------- | -------------------- |
| `test`         | 특별 취급 안 함, 캐싱 서버로 질의      | 기본값은 즉시 부정 응답    | 등록 거부(MUST NOT)  |
| `localhost`    | 루프백 주소를 반환, 질의를 보내지 않음 | 즉시 루프백 주소 응답      | 등록 거부(MUST NOT)  |
| `invalid`      | 즉시 부정 응답, 질의를 보내지 않음     | 즉시 `NXDOMAIN` 응답       | 등록 거부(MUST NOT)  |
| `example` 계열 | 특별 취급 안 함, 정상 질의             | 특별 취급 안 함, 정상 해석 | 등록 거부(IANA 소유) |
| 사설 역방향    | 특별 취급 안 함, 캐싱 서버로 질의      | 기본값은 즉시 응답         | 등록 거부(MUST NOT)  |

### test 이름

`test`와 `.test` 아래의 모든 이름은 사용자가 다른 도메인처럼 쓸 수 있다.
다만 중앙에서 책임지는 곳이 없으므로
네트워크마다 결과가 다를 수 있다는 점을 알아야 한다.
응용 소프트웨어와 해석 라이브러리는 이 이름을 특별 취급하지 않고
보통 도메인처럼 질의를 캐싱 서버로 보낸다.

특별한 처리는 서버 쪽에 있다.
캐싱 서버는 기본적으로 이 이름의 NS 레코드를 찾지 않고
즉시 부정 응답을 돌려줘야 한다(SHOULD).
이는 루트 이름 서버와 다른 서버의 불필요한 부하를 막기 위해서다.
캐싱 서버는 이를 끄고
상위로 질의하게 하는 설정 항목을 제공해야 하며 기본값은 꺼짐이다.
`.test`를 사설망의 권한 서버가 처리한다고
알려진 환경에서 그 항목을 켜 쓰라는 설계다.

### localhost 이름

`localhost`와 `.localhost` 아래의 모든 이름은 IPv4와 IPv6 주소
질의에 항상 해당 루프백 주소로 풀린다고 사용자가 가정해도 된다.
응용 소프트웨어는 이 이름을 특별 취급해도
되고(MAY) 일반 이름처럼 해석 API에 넘겨도 된다.
해석 API와 라이브러리는 이 이름을 인식해서 주소 질의에 루프백 주소를,
그 밖의 질의 유형에는 부정 응답을 돌려줘야 하며(SHOULD),
캐싱 DNS 서버로 질의를 보내서는 안 된다(SHOULD NOT).
`localhost`의 실제 응답 값이 설정이 아닌 프로토콜 명세로 정해져 있어서
DNS 서버 운영자는 이를 바꿀 수 없다는 점도 적혀 있다.

### invalid 이름

`invalid`와 `.invalid` 아래의 이름은 항상 `NXDOMAIN`을 돌려준다고
사용자가 가정해도 된다(MAY).
이름이 길이 제한 같은 다른 이유로 무효인 경우와 구별하려고
본문은 따옴표를 붙인 invalid라고 부른다.
해석 API와 라이브러리와 캐싱 서버와 권한 서버가 모두 이를 즉시 부정 응답으로
처리하라고 권고하며, 해석 API는 이 이름의 질의를 캐싱 서버로 보내서는 안 된다.

### example 이름

`example.`, `example.com.`, `example.net.`,
`example.org.`와 그 아래 이름은 문서 예시용이다.
다른 이름과 달리 응용과 해석 라이브러리와 서버 모두 특별 취급하지 않는다.
이 이름은 영구히 IANA 소유로 등록되어 있고,
IANA는 이 이름들의 용도를 설명하는 웹 페이지를 운영한다고 본문에 적혀 있다.
`example`이 나머지와 다른 점은 이 이름이 실제로 해석된다는 데 있다.
본문은 `www.example.org`가 문서 예시용으로 예약되어 등록할 수 없다고
적힌 웹 사이트가 실제로 그 이름에 존재하는 순환을 스스로 짚는다.

### 사설 주소 역방향 영역

RFC 1918 사설 주소의 역방향 영역 `10.in-addr.arpa.`,
`16.172.in-addr.arpa.`부터 `31.172.in-addr.arpa.`까지,
`168.192.in-addr.arpa.`가 같은 틀로 다뤄진다.
캐싱 서버는 기본적으로 이 영역에 대해 NS를 찾거나 권한 서버에 묻지 않고
즉시 긍정 또는 부정 응답을 내야 한다(SHOULD).
사설망 안에서 이 영역을 권한 서버가 처리하는 경우를 위해,
상위 해석을 켜는 설정 항목(기본값은 꺼짐)을 제공해야 한다.
사설 주소를 쓰는 운영자는 자기 권한 서버가 이
영역의 권한을 갖도록 설정해야 한다(SHOULD).

## 값 정하기

문서가 직접 숫자를 정하는 것은 없지만, 어떤 이름을 어디에 쓸지는 정해야 한다.
위 표를 기준으로 하면 아래처럼 갈린다.

| 하고 싶은 일                       | 쓸 이름                    | 근거                                             |
| ---------------------------------- | -------------------------- | ------------------------------------------------ |
| 문서와 예제에서 도메인을 보여 주기 | `example.com` 등           | 영구히 IANA 소유이고 정상 해석된다               |
| 반드시 해석 실패해야 하는 자리     | `.invalid`                 | `NXDOMAIN`이 프로토콜로 약속된 유일한 이름이다   |
| 내 컴퓨터를 가리키기               | `localhost`, `*.localhost` | 루프백으로 풀리고, 네트워크 질의가 나가지 않는다 |
| 사설망 안의 테스트 이름            | `.test`                    | 일반 등록이 금지되고 사설 DNS가 책임진다         |
| 사설망의 내부 이름, 유일성 불필요  | `home.arpa.`(RFC 8375)     | RFC 8375가 가정망용으로 지정했다[^rfc8375]       |

핵심 구분은 이름이 풀리는가와 풀리면 어디서 풀리는가다.
`.invalid`는 풀리면 안 되는 이름이고,
`localhost`는 DNS 없이 풀려야 하는 이름이며,
`.test`는 사설 DNS가 풀어야 하는 이름이다.
`example`은 공용 DNS가 풀지만 그 값은 문서 독자에게 의미가 없어야 하는 이름이다.

## 등록부는 그 뒤로 자랐다

RFC 6761이 만든 IANA 등록부는 2026-05-22 갱신본 기준으로 이 문서가
시드로 넣은 이름 외에도 여러 항목을 갖고 있다.[^iana-registry]
`local.`(RFC 6762)과 `onion.`(RFC 7686)이 대표적이고, `home.arpa.`(RFC 8375),
`ipv4only.arpa.`(RFC 8880), `resolver.arpa.`(RFC 9462),
`service.arpa.`(RFC 9665), `6tisch.arpa.`(RFC 9031),
`eap.arpa.`(RFC 9965)가 있다.[^iana-registry]
`alt.`는 RFC 9476으로 등록되어 있다.[^iana-registry]
등록부에는 `eap-noob.arpa.`가 폐기됨(DEPRECATED)
표시로 남아 있기도 하다.[^iana-registry]

RFC 8375는 `home.arpa.`를 가정 네트워크의 비유일(non-unique) 용도로 지정하고,
HNCP가 기존 `.home` 대신 이를 쓰도록 바꿨다.[^rfc8375]
RFC 9476은 `alt` 레이블을 DNS가 아닌 맥락에서 쓰라고 예약하고,
대체 이름 공간을 만드는 개발자에게 조언도 준다.[^rfc9476]

## 트레이드오프

### MUST가 아니라 SHOULD라서 생기는 틈

RFC 6761의 행동 규정은 거의 전부 `SHOULD`다.
사용자가 이름 처리에서 얻는 보장도 `localhost`는 가정해도 된다,
`invalid`는 가정할 수 있다(MAY) 수준이다.
이름별 행동 규정에서
`MUST NOT`은 등록 기관이 일반적인 방식으로
이름을 내주지 말아야 한다는 칸에만 붙는다.

이 설계가 얻는 것은 도입 가능성이다.
수많은 리졸버와 DNS 서버 구현에 모두 지켜야 하는 의무를 지우면,
지키지 않는 구현이 나오는 순간 표준 위반이 되어 모두가 손해를 본다.
`SHOULD`는 구현이 따르는 것이 합리적이라는 신호를 주면서도 예외를 허용한다.

잃는 것은 이름의 보장이다.
앞서 본 사용자의 DNS 서버가 `NXDOMAIN`을 안 돌려주면
누구에게 따지는가라는 질문에 RFC는 프로토콜 위반이라고 답하지만,
위반하는 구현을 막을 수단은 정해 두지 않았다.
그래서 `.invalid`가 항상 실패한다는 가정은 대부분의 환경에서
맞지만 보증된 것은 아니다.
`.test`처럼 설정으로 상위 해석을 켤 수 있게
둔 이름은 기본 동작만 정해져 있을 뿐이다.

### 절차가 느려서 생기는 우회

RFC 6761이 만든 절차는 실제로 쓰기 어려웠다는 평가가 뒤에 나왔다.
RFC 8244(Special-Use Domain Names Problem Statement)는 이 절차를 쓰다가
확인된 문제 열두 개를 나열한다.[^rfc8244]
첫 새 이름인 `.local`을 이 절차로 등록하는 데 10년 넘게 걸렸고,
그중 상당 부분은 절차 자체를 만드는 시간이었다고 적었다.[^rfc8244]
그 결과 일부 프로토콜 개발자는 IETF에서 이름을 얻지 못하리라고
보고 절차를 거치지 않고 이름을 쓰기도 한다.[^rfc8244]

같은 문서는 그 결과를 두 갈래로 정리한다.
하나는 IETF와 ICANN이 이름 이용을 조정하는 공식 절차가 없다는 점이다.[^rfc8244]
다른 하나는 특수 용도 이름을 모르는 소프트웨어가 그 이름을 일반 DNS로 보내서
루트 서버에 부담을 주고 질의 내용에서 사적 정보가 새는 문제다.[^rfc8244]
후자는 `.test`의 서버 쪽 기본 동작을 정한 이유와 직접 연결되지만,
기본 동작을 따르지 않는 소프트웨어까지 막아 주지는 못한다.

잃는 것과 얻는 것을 합치면,
예약 이름 제도는 합의가 가능한 소수의 이름을 단단하게 지키는
대신 새 이름을 얻는 비용이 커서 우회를 부르는 구조다.
RFC 8244는 이 문제의 해결책은 다루지 않고
문제만 나열한다고 스스로 밝힌다.[^rfc8244]

## 함정

사설망에서 등록부에 없는 이름을 TLD처럼 만들어 쓰는 습관은 위 문제의 현장판이다.
RFC 8244가 든 사유 중에는 로컬 전용으로 쓰던 이름이 밖으로 새어 나갈 수 있다는
점과,
비공식으로 쓰던 이름이 나중에 정식 할당되어
운영 문제를 만든다는 점이 있다.[^rfc8244]

`.test`가 어느 환경에서나 같다고 가정하는 것도 위험하다.
RFC 6761은 `.test`가 네트워크마다 다른 결과를 낼 수 있다고 처음부터 경고한다.
GeekNews에 올라온 한 보고는 macOS 26.3.1이 `/etc/resolver/`로 지정한 사설 DNS를
`.test`와 `.internal` 등에 대해 쓰지 않고
mDNS로만 처리한다고 전한다.[^gn-macos26]
이 보고는 `.test`가 RFC 6761 6.2절에 따라 정상 DNS로 풀려야 한다고
주장한다.[^gn-macos26]
RFC 본문에서 해석 라이브러리는 `.test`를 특별 취급하지 않고
질의를 캐싱 서버로 보내야 한다(SHOULD).
보고가 맞다면 mDNS로만 처리하는 동작은 이 권고와 어긋난다.
이 문서의 작성자는 그 동작을 재현하려 하지 않았으므로
보고 내용은 확인된 사실이 아니다.

`localhost` 하위 이름을 쓸 때도 라이브러리에 의존한다.
`foo.localhost`가 루프백으로 풀리는 것은 해석 라이브러리가 이
규칙을 구현했을 때만 보장되므로, 모든 환경에서 같다고 보면 안 된다.

## 확인하기

macOS 26.4에서 아래를 직접 실행해 RFC의 권고가 지켜지는지 확인했다.

```python
import socket

# 해석 라이브러리(getaddrinfo)가 예약 이름을 어떻게 다루는지 본다
for name in ["localhost", "foo.localhost", "a.b.localhost",
             "x.invalid", "foo.test", "foo.example", "www.example.com"]:
    try:
        addrs = sorted({a[4][0] for a in socket.getaddrinfo(name, None)})
        print(name, addrs)
    except socket.gaierror as e:
        print(name, "ERR", e)
```

```bash
# 시스템 리졸버를 거치지 않고 DNS 질의 결과(rcode)를 본다
dig +noall +comments foo.invalid | grep status
dig +noall +comments foo.test | grep status
```

실행 결과는 다음과 같았다.

| 이름              | 결과                                       |
| ----------------- | ------------------------------------------ |
| `localhost`       | `127.0.0.1`, `::1`                         |
| `foo.localhost`   | `127.0.0.1`, `::1`                         |
| `a.b.localhost`   | `127.0.0.1`, `::1`                         |
| `x.invalid`       | 해석 실패                                  |
| `foo.test`        | 해석 실패                                  |
| `foo.example`     | 해석 실패                                  |
| `www.example.com` | 공인 주소 4개(IPv4 2개, IPv6 2개)로 해석됨 |

`dig`로 `foo.invalid`와 `foo.test`를 조회하면 둘 다 `NXDOMAIN` 상태가 나왔다.
`localhost` 하위 이름이 DNS 질의 없이 루프백으로 풀린 것과,
`invalid`와 `test`가 기본 설정에서 부정 응답을 받은 것은 RFC의 권고와 일치한다.
`example.com`이 정상 해석되는 것도 RFC가 이 이름을 특별 취급하지 않는다고
적은 것과 맞는다.

이 실험은 한 대의 장비와 한 가지 네트워크 설정에서 한 번 실행한 것이다.
`.test`에 사설 DNS를 연결했을 때의 동작과,
앞서 말한 macOS 26의 보고는 재현하지 않았다.

## 체크리스트

- 문서 예제에 쓴 도메인이 `example.com`,
`example.net`, `example.org` 중 하나인가.
- 반드시 실패해야 하는 테스트 자리에 `.invalid`를 썼는가.
- 사설망 이름이 `.test`나 `home.arpa.`처럼 등록부에 있는 이름인가,
아니면 임의로 만든 TLD인가.
- 개발 환경에서
`foo.localhost` 같은 하위 이름이 루프백으로
풀리는지 사용하는 해석 라이브러리에서 확인했는가.
- 권한 DNS를 직접 운영한다면
사설 역방향 영역(`10.in-addr.arpa.` 등)의 권한을 서버에 설정했는가.
- 새 이름을 예약하려면 일곱 질문 모두에 답했고, 답이 전부 없음은 아닌가.
- 이름 하나가 해석 결과를 보장하는지 권고만
하는지(MUST와 SHOULD와 MAY)를 구분해서 읽었는가.

## 기억할 원칙

### 예약 이름은 해석 규칙이지 소유권 선언이 아니다

예약은 누가 그 이름을 갖는지가 아니라 소프트웨어가
그 이름을 어떻게 다뤄야 하는지를 정한다.
그래서 문서가 요구하는 것도 이름의 소유자가 아니라 일곱 질문에 대한 답이다.
어떤 이름을 쓰려는데 그 이름을 보고 달라지는 구현이 하나도 없다면,
예약이 아니라 일반 등록 절차를 쓰라는 것이 이 문서의 결론이다.

### 보장의 강도는 칸마다 다르다

`localhost`의 루프백, `invalid`의 `NXDOMAIN`,
`test`의 사설 위임은 모두 예약 이름이지만 같은 강도의 약속이 아니다.
이름을 코드에 고정하기 전에,
내가 의존하는 행동이 일곱 칸 중 어느 칸의 어느 키워드(MUST,
SHOULD, MAY)에 적혀 있는지부터 읽어야 한다.
