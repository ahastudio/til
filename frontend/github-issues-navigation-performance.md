# GitHub Issues를 즉시 열리게: 클라이언트 캐시와 예열과 서비스 워커로 체감 지연을 줄인 방법

원문: [From latency to instant: Modernizing GitHub Issues navigation performance - The GitHub Blog](https://github.blog/engineering/architecture-optimization/from-latency-to-instant-modernizing-github-issues-navigation-performance/)

HN 토론: <https://news.ycombinator.com/item?id=48137410> (2점, 0개 댓글)

HN 토론: <https://news.ycombinator.com/item?id=48148856> (1점, 0개 댓글)

## 요약

GitHub Issues 팀의 시니어 엔지니어 Alexander Lelidis가 2026년 5월 14일에 쓴
엔지니어링 글입니다.
이슈 페이지(`issues#show`)로 이동할 때 이미 본 데이터를 다시 받느라 생기는
지연을 줄이기 위해,
렌더링을 서버 응답이 아니라 브라우저에 있는 데이터에서 먼저 시작하고 뒤에서 최신
상태를 확인하는 구조로 바꾼 과정을 설명합니다.
글에 나오는 수치는 모두 GitHub 쪽의 보고입니다.

### 측정 기준

팀은 HPC(Highest Priority Content)라는 내부 지표를 씁니다.
Web Vitals의 LCP와 가까운 지표로, 브라우저가 고른 하나의 HTML 요소(이슈
페이지에서는 대개 제목이나 본문)가 처음 그려지는 시점입니다.
탐색을 HPC 200ms 미만은 즉시(Instant), 1,000ms 미만은 빠름(Fast),
그 이상은 느림(Slow)으로 나눕니다.
글은 예전에 p90과 p99 같은 꼬리 지연을 줄이는 데 힘을 썼지만,
이번에는 전체 탐색이 어느 구간에 놓이는지,
즉 분포의 질에 초점을 옮겼다고 말합니다.

### 출발점

탐색 유형은 세 가지입니다.
하드 탐색은 새로고침이나 첫 진입처럼 브라우저가 전부 새로 불러오는 경우이고,
Turbo 탐색은 Rails Turbo가 페이지 일부만 바꾸는 경우이며,
소프트 탐색은 이미 떠 있는 React 런타임 안에서 이동하는 경우입니다.
본문에 실린 그림의 설명 텍스트에 따르면 시작 시점의 비중은 하드 57.6%,
React 37.5%였고,
유형별 HPC 값은 하드 2.05, Turbo 1.76, React 1.04로 적혀 있습니다.
설명 텍스트에는 이 값의 단위가 없고, 그림 자체는 이 문서가 보지 못했습니다.
글은 가장 흔한 경로가 가장 느린 경로였다고 정리하고,
Rails 페이지에서 React 화면으로 넘어가는 경계가 하드 탐색을 늘린다고 설명합니다.
GitHub이 Rails 렌더링에서 React 프런트엔드로 옮겨 가는 중이라는 점이 배경입니다.

### 세 단계의 변경

첫째, 소프트 탐색에 IndexedDB 기반 클라이언트 캐시를 붙이고
stale-while-revalidate를 적용했습니다.
캐시에서 바로 그리고, 뒤에서 서버에 최신 여부를 물어 달라진 것만 반영합니다.
사전 분석은 같은 이슈를 자주 다시 여는 패턴을 근거로 캐시 적중률 약 30%를
가능성의 기준선으로 잡았고,
전체 사용자에게 배포한 뒤 적중률은 약 3분의 1(약 33%)이었습니다.
React 탐색 중 즉시 구간 비율은 4%에서 약 22%로 올랐고,
이는 전체 요청량의 약 15%에 해당한다고 합니다.
캐시와 서버 데이터가 어긋나는 비율은 약 4.7%로 측정했고,
이를 허용 범위로 두었다고 합니다.

둘째, 예열(preheating)입니다.
적중률을 더 올리려고 다음에 열 만한 이슈를 전부 미리 가져오면 목록이나 대시보드
같은 화면에서 요청이 폭증하고 N+1 형태의 접근이 생깁니다.
그래서 목표를 항상 최신인 데이터가 아니라 클릭 시점에 쓸 만한 데이터가 로컬에
이미 있는 상태로 바꿨습니다.
예열은 의도가 높은 화면(이슈 목록, 대시보드, 프로젝트,
의존성 보기)에서 이슈 참조를 훑으며, 캐시에 없을 때만 네트워크를 칩니다.
요청은 낮은 우선순위의 워커에서 속도 제한과 서킷 브레이커 아래 실행되고,
사용자 요청이 항상 앞섭니다.
IndexedDB 앞에는 메모리 캐시 계층을 하나 더 두어,
자주 쓰는 데이터를 비동기 읽기 없이 동기적으로 꺼냅니다.
결과로 `issues#show`의 즉시 탐색은 전체 약 30%, React 탐색은 최대 약 70%,
캐시 적중률은 약 96%가 되었다고 합니다.

셋째, 서비스 워커입니다.
하드 탐색에는 페이지 자바스크립트가 아직 없으므로,
브라우저가 이슈 페이지를 요청하는 순간 서비스 워커가 가로채 로컬 캐시에 데이터가
있는지 봅니다.
있으면 요청 헤더로 서버에 알리고, 서버는 레이아웃과 최소 마크업과 자바스크립트만
든 얇은 HTML 셸을 돌려주며, React가 로컬 페이로드로 화면을 그립니다.
없으면 평소처럼 서버가 데이터를 불러 렌더링합니다.
캐시가 비었거나 낡았거나 서비스 워커를 쓸 수 없으면 기존 서버 렌더링 경로로
돌아가는 엄격한 최적화라고 설명합니다.
Turbo 탐색은 서버 응답 시간에 묶여 있어 효과가 즉시 나타났고,
하드 탐색은 서버 렌더링 시간을 클라이언트 렌더링 시간과 맞바꾸는 셈이어서
자바스크립트 내려받기와 실행이 새 임계 경로가 됩니다.
이를 줄이려 React.lazy와 동적 라우트 미리 불러오기로 경로별 코드를 나누고,
이슈 편집기 번들은 편집 모드에 들어갈 때만 가져오며 마우스를 올리는 의도 기반
미리 불러오기로 지연을 가립니다.

### 결과와 다음 계획

롤아웃 전 기간의 `issues#show` 전체 트래픽 HPC 백분위는 다음과 같이
바뀌었다고 합니다.

| 백분위 | 이전       | 이후    |
| ------ | ---------- | ------- |
| P10    | 약 600ms   | 70ms    |
| P25    | 약 800ms   | 120ms   |
| P50    | 약 1,200ms | 700ms   |
| P75    | 1,800ms    | 1,400ms |
| P90    | 2,400ms    | 2,100ms |

글은 서버 렌더링에 기대는 콜드 스타트가 여전히 장애물이라고 인정하고,
다음 단계로 지연 시간에 맞춘 백엔드 일부 재작성과 엣지에 가까운 UI 전달 계층을
예고합니다.

## 분석

### 지표를 바꾼 것이 전략의 절반이다

글은 구조 변경을 설명하기 전에 무엇이 빠른가를 먼저 정의합니다.
꼬리(p90, p99)를 줄이는 일은 중앙값을 그대로 둔 채로도 성공할 수 있다는 지적은
맞습니다.
200ms와 1,000ms라는 구간 문턱을 두고 구간별 비율을 보면,
캐시가 만드는 효과가 어디에 나타나는지 드러납니다.
결과 표가 바로 그 모양입니다.
P10과 P25는 크게 줄었고 P90은 300ms 줄었습니다.
캐시와 예열이 적중한 탐색이 분포의 아래쪽을 채웠고,
위쪽은 콜드 스타트가 여전히 정한다는 글의 해석과 수치가 맞물립니다.

### 적중과 즉시는 같은 말이 아니다

소프트 탐색 단계에서 적중률은 약 33%인데 React 탐색 중 즉시 구간은 약 22%였고,
예열 뒤에는 적중률이 약 96%인데 React 탐색의 즉시 구간은 최대 약 70%였습니다.
적중한 탐색이 모두 200ms 안에 끝나지는 않는다는 뜻으로 읽힙니다.
글은 이 차이의 원인을 설명하지 않습니다.
이 문서가 추정하는 후보는 캐시에서 읽은 뒤의 렌더링 비용,
메모리 계층을 지나지 못하고 IndexedDB 비동기 읽기를 거친 경우,
적중이어도 화면이 다른 요소를 기다리는 경우이지만 어느 것이 맞는지는 글로 확인할
수 없습니다.

### 예열은 신선도 대신 용량을 지키는 선택이다

전부 미리 가져오는 방식이 막힌 이유를 글은 구현 난도가 아니라 용량이라고
밝힙니다.
그래서 예열은 이미 로컬에 쓸 만한 데이터가 있으면 멈추고,
낮은 우선순위와 속도 제한과 서킷 브레이커로 사용자 요청을 보호합니다.
데이터가 약간 낡아도 이동을 즉시 끝내고 열린 뒤에 최신 상태로 수렴시킨다는
명시적인 교환입니다.
같은 캐시라도 목적이 최신성 보장인지 존재 보장인지에 따라 설계가 달라진다는 점을
분명히 보여 줍니다.

### 서비스 워커는 서버의 일을 줄이는 신호로 쓰였다

서비스 워커는 응답을 대신 만들지 않고, 캐시에 데이터가 있다는 사실을 헤더로
서버에 알립니다.
서버는 그 신호를 받으면 데이터 조회와 렌더링을 건너뛰고 얇은 셸만 줍니다.
그래서 Turbo 경로에서는 서버 시간이 곧바로 줄고,
하드 탐색에서는 일을 클라이언트로 옮깁니다.
캐시가 없거나 서비스 워커가 없으면 기존 경로로 가므로,
실패해도 기존 동작보다 나빠지지 않도록 설계되어 있습니다.

## 비평

### 수치마다 분모가 달라 한 줄로 맞출 수 없다

글은 React 탐색의 22%, 전체 요청량의 15%,
이슈 전체의 30%처럼 서로 다른 분모를 같은 문단에서 씁니다.
그림 설명에 따르면 React 탐색은 시작 시점에 전체 탐색의 37.5%였으므로,
React 탐색의 22%가 즉시가 되었다면 전체 탐색 기준으로는 그보다 훨씬 작을
것입니다.
글이 말하는 전체 요청량의 15%가 어떻게 계산되었는지는 본문과 그림 설명만으로는
맞출 수 없습니다.
탐색 수와 요청 수가 다른 단위일 수 있다는 점은 글이 밝히지 않았습니다.

### 전후 비교에 대조군이 없다

최종 백분위는 초기 IndexedDB 캐시부터 서비스 워커까지 이어진 롤아웃 전체 기간을
비교한 것입니다.
같은 기간에 일어난 다른 변화는 분리되지 않습니다.
글이 스스로 밝힌 Rails에서 React로의 이전은 하드 탐색의 비중을 바꾸므로,
분포 전체를 움직일 수 있습니다.
일부 사용자에게 기능을 끈 채로 비교한 결과나 단계별 기여도 표는 없습니다.
따라서 이 수치는 이 구조가 만든 변화의 크기가 아니라,
이 기간에 관측된 변화로 읽어야 합니다.

### 신선도 비용은 예열 이전 단계의 숫자만 있다

어긋남 4.7%는 적중률이 약 33%이던 소프트 탐색 단계에서 측정한 값으로 소개됩니다.
예열은 정의상 낡았을 수 있는 데이터를 미리 채우고 적중률을 96%까지 올렸지만,
그 최종 상태의 어긋남 비율은 글에 없습니다.
어긋난 데이터를 화면에 먼저 그린 뒤 최신 값으로 바꿀 때 사용자에게 무엇이
보이는지(깜빡임, 닫힌 이슈가 잠시 열려 보이는 경우)도 다루지 않습니다.

### 지표가 낡은 데이터를 그린 순간을 완성으로 센다

HPC는 주요 요소가 처음 그려지는 시점이므로,
캐시에서 그린 낡은 제목이나 본문도 완료로 기록됩니다.
최신성은 이 지표에 들어 있지 않습니다.
글은 어긋남 비율을 따로 두어 이 한계를 일부 메우지만,
빠르게 보이는 것과 맞게 보이는 것의 간격을 묻는 지표는 소개하지 않았습니다.
이 문서의 해석으로는 이 간격이 이 구조에서 가장 먼저 확인해야 할 값입니다.

### 로컬에 남는 데이터의 수명은 다루지 않는다

IndexedDB는 탭을 닫아도 브라우저를 껐다 켜도 남는 저장소이고,
글도 그 점을 선택 이유로 듭니다.
그렇다면 로그아웃이나 권한 회수 뒤 비공개 저장소의 이슈 데이터가 로컬에 남는지,
공유 컴퓨터에서 어떻게 지우는지, 용량 한도를 넘으면 어떤 것을 버리는지가
물음으로 남습니다.
글에는 이 내용이 없고, 이 문서도 그것이 결함이라고 단정하지는 못합니다.
답이 없는 것이 확인된 것은 글이 다루지 않았다는 점뿐입니다.

### 예열이 서버에 주는 부담은 한 문장으로만 말한다

글은 조금의 통제된 백그라운드 용량을 썼다고 요약하지만 요청 증가율이나 서킷
브레이커가 실제로 작동한 빈도는 말하지 않습니다.
이 구조의 비용 쪽 수치가 빠져 있으므로 이득과 비용의 교환을 독자가 직접 평가할
수 없습니다.

## 인사이트

### 먼저 경로별로 쪼개서 재야 어디를 고칠지 보인다

글의 출발점은 탐색 유형별 비중과 지연을 분리해서 본 것입니다.
가장 흔한 경로(하드 탐색)가 가장 느리다는 사실을 알았기에,
소프트 탐색부터 개선하면서도 하드 탐색에 서비스 워커로 따로 대응하는 순서가
나왔습니다.
평균이나 전체 백분위 하나만 봤다면 소프트 탐색의 개선이 전체 지표를 거의 못
움직인다는 점이 가려졌을 것입니다.
다른 서비스에서도 진입 경로별 비중과 지연을 먼저 나누어 보는 일이 최적화의
우선순위를 정합니다.

### 예열 전략의 핵심 매개변수는 허용 가능한 낡음이다

예열은 최신성을 용량과 바꾸는 선택이므로,
어떤 화면에서 얼마나 낡은 데이터를 허용하는지가 설계값이 됩니다.
이 값이 없으면 적중률이 오를수록 낡은 화면을 보여 주는 빈도도 함께 오릅니다.
이 문서는 화면별로 허용하는 어긋남 비율과 갱신 주기를 먼저 정하고,
적중률과 같은 대시보드에서 함께 보는 것을 권합니다.
이슈 제목처럼 자주 안 바뀌는 데이터와 댓글 수처럼 자주 바뀌는 데이터의 값은 다를
것입니다.

### 서버가 두 갈래 응답을 가지면 시험할 경로도 두 배가 된다

서비스 워커가 헤더로 신호를 보내면 서버는 얇은 셸과 전체 서버 렌더링이라는 두
응답을 가집니다.
둘 사이에서 동작이 어긋나면 캐시 적중 여부에 따라 같은 주소가 다르게 보이는
문제가 생기고, 재현도 어렵습니다.
이 문서의 해석으로는 이 구조를 쓰는 팀이 두 경로를 같은 시험 항목으로 돌리고
적중 여부를 로그에 남기는 것이 필요합니다.
글이 밝힌 대로 실패 시 기존 경로로 돌아가는 설계는 이 위험을 줄이지만 없애지는
않습니다.

### 이 글의 판단을 바꿀 관찰

서비스 워커를 끈 사용자 집단과 비교한 HPC 분포가 공개되면 구조의 기여가 따로
드러납니다.
예열 이후의 어긋남 비율과 어긋남 시 화면에서 일어나는 일이 보고되면 빠름의
대가가 구체화됩니다.
P90이 자바스크립트 분할 이후 어디까지 내려가는지 보면 하드 탐색 쪽 한계도
확인됩니다.
