# 에이전트 시대에도 웹 프레임워크는 중요하고, 새 프레임워크도 필요하다

원문: [Do Frameworks Matter Anymore?](https://brookslybrand.com/posts/do-frameworks-matter-anymore/)

HN 토론: <https://news.ycombinator.com/item?id=49741128> (2점, 0개 댓글)

## 요약

Brooks Lybrand가 2026년 9월 16일 개인 블로그에 쓴 글이다.
그는 3년 동안 오픈소스 웹 프레임워크를 전업으로 만들어 왔고,
Shopify에서 Remix 팀과 일했으며, React Tips with Brooks Lybrand라는 YouTube
채널을 운영한다.
글의 질문은 바이브 코딩과 에이전트 프로그래밍의 시대에 어떤 웹 프레임워크를
쓰는지가 여전히 중요한가, 그리고 더 나아가 새 프레임워크를 만들어야 하는가다.

저자는 먼저 프레임워크의 가치를 한 문장으로 정의한다.
프레임워크는 웹사이트를 만들기 위한 추상화, 구조, 제약을 제공한다는 것이다.
이어서 요즘 업계에 퍼진 통념을 정리한다.
2025년에서 2026년으로 넘어가는 겨울쯤 모델이 에이전트 프로그래밍에 충분히
좋아졌으니 코드에는 점점 신경 쓰지 않아도 되고,
특히 프런트엔드는 보이는 게 좋으면 좋은 것이며,
React가 이미 지배적이고 학습 데이터도 압도적으로 많으니 다른 것을 시도할 이유가
없다는 주장이다.
저자는 Cursor 팀처럼 진지한 사람들도 에이전트 시대에는 React가 유리하다고 믿는
것 같다고 덧붙인다.

저자의 반박은 논리 구조에 있다.
LLM이 프런트엔드 코드를 그렇게 잘 쓰고 사람들이 HTML, JavaScript,
CSS의 세부를 신경 쓰지 않는다면, 왜 LLM과 웹사이트 사이에 React라는 추상화 층을
두는가.
그렇다면 오히려 Web Components를 받아들일 때라는 것이다.
그래서 저자는 둘 중 하나라고 정리한다.
프레임워크가 중요하지 않다면 React를 쓸 이유도 없고,
React를 쓰는 편이 여전히 유리하다면 프레임워크는 중요하다.

React가 왜 이겼는지에 대해서는 React 팀이 흔히 말하는 조합(composition)을
꼽으면서도, 자신의 경험으로는 기존 사이트에 끼워 넣기 쉬웠고,
로직과 마크업을 재사용 가능한 컴포넌트로 묶는 방식이 좋았고, 라우팅, 스타일링,
head와 meta 태그 관리 같은 빈자리를 채우는 생태계가 컸기 때문이라고 말한다.
Guillermo Rauch가 shadcn/ui를 React 승리의 이유처럼 말하는 데에는 동의하지
않는다.
shadcn/ui는 Radix, Reach UI, Material UI,
Bootstrap으로 이어진 계보의 최신판일 뿐이며,
그것이 존재한다는 사실이 React의 강점을 보여 주는 결과이지 원인이 아니라는
것이다.

글의 중심 논증은 React Conf 2024 핵심 팀 Q&A에서 Ricky Hanlon이 한 말에서
출발한다.
프레임워크를 쓰거나 만들거나 둘 중 하나이고,
프레임워크를 만드는 일은 정말 어렵다는 말이다.
저자는 텍사스의 한 식료품 체인 웹 플랫폼 팀에서 React 위에 직접 만든 메타
프레임워크를 운영했는데, 기능도 부족하고 이해하는 사람도 적어 부담이 되어 결국
Next.js로 옮겼던 경험을 든다.
그리고 지금은 이 말이 그 어느 때보다 맞으면서 동시에 조금 틀렸다고 말한다.
좋고 견고하고 안전한 풀스택 프레임워크를 만드는 일은 여전히 어렵지만,
그럭저럭 쓸 만한 프레임워크를 만드는 일은 어렵지 않다.
프레임워크 없이 LLM으로 웹사이트를 만들기 시작하면 LLM이 프레임워크를 만들어
주기 때문이다.
명시적인 프레임워크를 쓰거나, 암묵적인 프레임워크를 생성하거나 둘 중 하나라는
것이 저자의 결론이다.

에이전트와 일하며 프레임워크에 바라는 것도 바뀌었다고 한다.
핫 모듈 교체(HMR)는 복잡한 사용자 상호작용과 디자인을 다듬을 때 여전히 유용하다.
TypeScript는 예전에는 메서드를 찾아보는 문서 역할이 컸지만 지금은 그 쓰임이 거의
없고, 대신 복잡한 애플리케이션에서 LLM이 코드를 반복 수정하다 모든 것을 깨뜨리지
않게 하는 제약과, LSP를 통한 탐색 수단으로 가치가 있다.
`useEffect`는 직접 쓸 때는 다룰 자신이 있었지만 LLM이 쓰게 하는 것은 전혀 편하지
않으며, Grok Bot 개발에서는 아예 금지했다고 들었다고 적는다.
그가 원하는 것은 옳은 방법이 무엇인지 분명하고,
탈출구는 가능하지만 대개 필요 없고 쓸 때는 사람과 기계 모두에게 분명한
프레임워크다.
에이전트의 작업을 검사하는 테스트와 도구가 내장되어 있고,
좋은 문서가 `node_modules` 안에 바로 있어서 에이전트가 인터넷을 긁다가 나쁜
조언을 가져오지 않기를 바란다.

결론에서 그는 2013년부터 2019년까지의 프레임워크 전쟁과 2020년부터 2024년까지의
메타 프레임워크 전쟁은 끝났고, 사람들이 예전처럼 프레임워크를 갈망하지 않는다는
것을 받아들이고 있다고 말한다.
그러나 과대 선전의 중심이 아니어도 중요할 수 있다며,
에이전트가 시스템을 시험하자 git 성능과 GitHub 대안이 다시 주목받은 예를 든다.
그래서 질문을 새 프레임워크도 중요한가로 바꾸고,
진짜 풀스택이고 웹 표준과 API 위에 서서 특정 런타임이 아니라 웹의 언어를 말하며
AI가 다루기 쉽고 사람이 이해할 수 있는 코드를 내는 프레임워크를 원한다고 밝힌다.
에이전트에 가장 좋은 프레임워크를 객관적으로 가리는 방법이 아직 없다는 사실
자체가 개선의 여지가 있다는 증거라며, 직접 만들어 보자는 말로 글을 맺는다.

## 분석

### 딜레마의 형식으로 통념을 무너뜨린다

이 글의 가장 강한 부분은 React 지지 논리를 딜레마로 바꾼 대목이다.
코드가 중요하지 않다는 전제와 React가 유리하다는 결론은 함께 성립하기 어렵다.
코드가 정말 중요하지 않다면 학습 데이터의 양도,
컴포넌트 추상화도 의미가 없어야 하고, React가 유리하다면 그 이유는 결국 코드의
구조와 추상화가 결과에 영향을 준다는 데 있다.
저자는 React를 공격하지 않고 그 지지자의 논리를 끝까지 따라가 모순을 드러낸다.

### 암묵적 프레임워크라는 관찰이 핵심이다

프레임워크를 쓰지 않으면 에이전트가 프레임워크를 만든다는 관찰은 이 글에서 가장
오래 남을 주장이다.
에이전트는 사람이 손으로 코딩할 때와 같은 방식으로 함수, 클래스,
추상화를 만들고, 정리 없이 기능을 덧붙인다.
저자는 이것을 슬롭이라고 부르지도 않고, 자신의 첫 프로젝트들도 그렇게 만들었다고
말한다.
달라진 것은 속도뿐이라는 그의 진단은, 에이전트가 만든 코드의 문제를 AI 특유의
결함이 아니라 오래된 소프트웨어 문제의 가속으로 다시 본다.

이 관점에서 프레임워크 선택은 추상화를 쓸지 말지가 아니라,
검증된 공개 추상화를 쓸지 아무도 검토하지 않은 사적 추상화를 쓸지의 선택이 된다.
보안 문제를 생각하는 팀과 회사가 뒤에 있느냐,
나와 내 에이전트만 있느냐의 차이이기도 하다.

### 개발자 경험이 에이전트 경험으로 재분류된다

HMR, TypeScript, `useEffect`를 다룬 대목은 개발자 경험(DX)이라는 범주를 다시
나눈다.
어떤 기능은 여전히 사람에게 유용하고(HMR),
어떤 기능은 사람에게는 덜 유용해졌지만 에이전트에게 유용해졌으며(TypeScript),
어떤 기능은 사람에게는 괜찮았지만 에이전트에게는 위험해졌다(`useEffect`).
이 분류는 앞으로 프레임워크 기능을 평가하는 기준이 사람이 쓰기 편한가에서
에이전트가 틀리기 어려운가로 옮겨 가고 있음을 보여 준다.
저자가 원하는 프레임워크의 조건, 즉 옳은 길이 분명하고 탈출구가 눈에 띄며 검사
도구가 내장된 구조는 사실상 에이전트를 위한 가드레일의 명세다.

이 저장소의 `web/use-the-platform.md`가 다루는 Nolan Lawson의 글은 개발자들이 왜
웹 플랫폼 자체를 쓰지 않는지를 묻는다.
Lybrand가 웹 표준과 API 위에 선 프레임워크를 원한다고 말하는 대목은 그 질문과
같은 방향을 향한다.

## 비평

### 딜레마는 학습 데이터 논거를 너무 쉽게 넘긴다

저자는 React가 학습 데이터 때문에 유리하다는 주장을 따지는 것이 별 가치가 없다며
넘어간다.
그러나 그 주장은 딜레마를 빠져나갈 수 있는 길이다.
React 지지자는 코드 세부는 중요하지 않지만 모델이 가장 많이 본 패턴을 쓰면
오류가 줄어든다고 말할 수 있다.
이 경우 중요한 것은 프레임워크의 설계가 아니라 모델의 친숙도이고,
그렇다면 프레임워크는 중요하지만 새 프레임워크는 불리하다는 결론이 나온다.

이것은 저자가 피하고 싶은 바로 그 결론이다.
새 프레임워크는 학습 데이터가 적어서 에이전트가 덜 잘 다룰 것이라는 반론에 대해,
글은 문서를 `node_modules`에 넣으라는 바람 말고는 답을 내놓지 않는다.
딜레마의 형식은 우아하지만, 가장 현실적인 반론을 다루지 않은 채 결론으로
넘어간다.

### 프레임워크 제작자의 자리에서 쓴 결론이다

저자는 스스로 이 질문이 자신에게 매우 중요하다고 밝힌다.
프레임워크를 만드는 일을 사랑하고, 앞으로도 그 일을 하고 싶으며,
중요하지 않은 일을 하는 것이 싫다는 것이다.
그는 이 이해관계를 숨기지 않았고 그 솔직함은 미덕이지만,
결론이 새 프레임워크를 만들자는 쪽으로 향한다는 점은 그 이해관계와 정확히
겹친다.

그가 Remix 팀과 함께 일해 왔다는 점을 생각하면,
웹 표준 위에 서고 런타임에 묶이지 않으며 풀스택인 프레임워크라는 바람은 Remix가
내세워 온 방향과도 겹친다.
글이 새 프레임워크의 필요를 증명했다기보다,
자신이 만들고 싶은 프레임워크의 동기를 정리했다고 읽는 편이 정확하다.

### 측정할 수 없다는 것이 개선의 근거가 될 수는 없다

글의 마지막 논거는 에이전트에 가장 좋은 프레임워크를 객관적으로 측정하는 방법이
없다는 사실이 개선의 여지가 있다는 충분한 증거라는 것이다.
그러나 측정할 수 없다는 것은 지금 것이 충분히 좋은지도,
새것이 더 나은지도 알 수 없다는 뜻이다.
저자는 자신의 취향, 즉 모델과 일하며 얻은 주관적인 경험이 벤치마크보다
중요하다고 말하는데, 그렇다면 새 프레임워크의 성공 여부도 취향으로 판단할 수밖에
없다.
측정의 어려움은 실험을 정당화할 수는 있지만,
새 프레임워크가 중요하다는 결론을 뒷받침하지는 못한다.

## 인사이트

### 에이전트가 만든 암묵적 프레임워크는 레거시의 새 형태가 된다

저자의 관찰을 한 걸음 더 밀면, 프레임워크 없이 에이전트로 만든 프로젝트들은 몇
년 뒤 문서도 설계 의도도 없는 사내 프레임워크를 품게 된다.
그가 식료품 체인에서 겪은 사내 메타 프레임워크 문제,
즉 아는 사람이 적고 유지 비용이 큰 문제가 이번에는 아무도 직접 설계하지 않은
프레임워크에서 반복된다.
차이는 그 프레임워크를 이해하는 존재가 에이전트뿐이라는 점이다.
모델이 바뀌거나 컨텍스트가 사라지면 그 이해도 함께 사라진다.
이 점에서 공개 프레임워크의 가치는 기능보다 공유된 이해,
즉 사람과 여러 세대의 모델이 같은 추상화를 알고 있다는 데 있다.

### 프레임워크의 경쟁 기준이 사람의 생산성에서 에이전트의 오류율로 옮겨 간다

2010년대 프레임워크 전쟁의 기준은 사람이 얼마나 빨리,
얼마나 즐겁게 만들 수 있느냐였다.
저자의 `useEffect` 사례는 다음 경쟁의 기준이 다르다는 것을 보여 준다.
에이전트가 쓰기 쉬운 API보다 에이전트가 잘못 쓰기 어려운 API가 중요해진다.
이 변화는 과거 C에서 메모리 안전 언어로 넘어간 흐름과 닮았다.
숙련자에게는 강력한 도구가 대량의 자동 생성 코드 앞에서는 위험 요소가 되고,
언어와 프레임워크는 그 위험을 구조로 막는 쪽으로 진화한다.

### 문서를 패키지 안에 넣으라는 요구는 배포 방식을 바꾼다

저자는 좋은 문서가 `node_modules`에 바로 있어서 에이전트가 인터넷을 긁지 않기를
바란다고 적었다.
이것은 작은 바람처럼 보이지만, 패키지가 코드뿐 아니라 그 코드를 쓰는 방법까지
함께 배포해야 한다는 뜻이다.
