## 소개

UI SDK는 Vercel Labs가 만든 라이브러리로, 에이전트가 사용자 인터페이스를 만들 때 쓰는
동작(behavior)의 모음이다.
키보드 탐색, 포커스, 선택, 닫기, 팝업, 드래그 앤 드롭과 이에 필요한 ARIA를
`@ui-sdk/core`에 두고, React, Vue, Svelte, Solid, Web Components용 어댑터를 제공한다.
README는 이 라이브러리가 베타이고 Vercel 베타 약관을 따른다고 밝힌다.
프레임워크와 API, 문서, 동작이 정식 출시 전에 바뀔 수 있다.

프로젝트 사이트의 설명은 다음 생각에서 출발한다.
에이전트에게 Select 컴포넌트를 주면 Select를 만들 수 있다.
그 대신 Select를 이루는 조각, 곧 팝업(`createPopup`), 목록에서 고르기
(`createSelection`), 입력해서 옵션 찾기(`createTypeahead`)를 주면
Select뿐 아니라 자동 완성, 콤보박스, 아직 없는 새 컴포넌트도 만들 수 있다.
그래서 복잡한 상호작용을 재사용 가능한 동작으로 추상화하고,
에이전트에게 그 동작을 만들고 쓰는 법을 가르쳤다고 한다.

## 사용법

설치는 코어와 사용하는 프레임워크의 어댑터를 함께 받는다.

```bash
npm install @ui-sdk/react @ui-sdk/core
```

다른 프레임워크는 `@ui-sdk/react`를 `@ui-sdk/vue`, `@ui-sdk/svelte`,
`@ui-sdk/solid`, `@ui-sdk/web` 가운데 하나로 바꾼다.
그다음 에이전트에게 UI SDK 스킬을 준다.

```bash
npx skills@latest add vercel-labs/ui --skill ui-sdk
```

README의 예시는 `definePrimitive`로 `search-field`라는 원시 요소를 정의한다.
상태는 `value`이고, `input`과 `clear` 두 슬롯(slot)을 가진다.
clear 슬롯은 값이 비어 있지 않을 때만 보이며, `createFocusRecovery`가 포커스 복구를 맡는다.
이 정의를 프레임워크에서는 `createParts`로 렌더링하고,
README는 이 부분이 다섯 프레임워크에서 같다고 한다.
README는 이 코드를 직접 쓸 필요가 없으며 에이전트가 쓴다고 말한다.

## 주요 기능

사이트가 보여 주는 동작의 예는 다음과 같다.

- `createRovingFocus`: 방향키로 목록을 이동하고 Tab 정지점은 하나이다.
- `createTypeahead`: 몇 글자를 쳐서 항목으로 이동한다.
- `createPopup`: 버튼 옆에 열리고 화면 안에 머문다.
- `createSelection`: 하나나 여러 개를 고르며 Shift와 Ctrl이 파일 관리자처럼 동작한다.
- `createReorder`: 포인터나 키보드로 목록을 정렬한다.
- `createResize`, `createViewport`, `createVirtualizer`: 크기 조절, 캔버스 이동과 확대,
  보이는 행만 그리는 가상화.

사이트는 이런 동작을 50개 넘게 만들었다고 하며,
같은 동작으로 만든 컴포넌트 라이브러리(Color Picker, Command, Calendar, Tree 등)도
시작용으로 제공한다.
에이전트가 화면 이미지 없이 페이지를 읽고 컨트롤을 직접 조작하므로 두 배 넘게 빠르고
비용은 절반 미만이라는 주장도 사이트에 있다.

## 분석

### 컴포넌트 대신 동작을 건네는 설계

기존 UI 라이브러리는 완성된 컴포넌트를 건네고 개발자가 속성으로 조정한다.
UI SDK는 완성된 부품 대신 부품이 공통으로 쓰는 동작을 건네고
조합을 에이전트에게 맡긴다.
컴포넌트의 수가 아니라 동작의 수가 조합의 폭을 정한다는 것이 이 설계의 주장이다.
원시 요소가 상태, 슬롯, 동작을 선언적으로 묶고 프레임워크 어댑터가 같은 정의를 렌더링하므로
컴포넌트 정의는 한 번만 쓰면 된다.

### 에이전트용 인터페이스

설치 안내의 마지막 단계가 에이전트에게 스킬을 주는 것이라는 점이 눈에 띈다.
이 라이브러리의 사용자는 사람이 아니라 에이전트이고,
문서도 코드를 읽는 법보다 에이전트에게 맡기는 법을 먼저 안내한다.

## 비평

### 검증 가능한 주장의 범위

핵심 주장은 에이전트가 동작을 조합해 올바른 컴포넌트를 만들고 더 빠르고 싸게 쓴다는 것이다.

### 접근성의 책임

동작에 ARIA가 포함되므로 접근성은 라이브러리가 맡는 영역으로 보인다.
그러나 에이전트가 동작을 잘못 조합했을 때 접근성이 어떻게 보장되는지는
README와 사이트 첫 화면에 나와 있지 않다.

### 베타라는 상태

저장소는 한 달 안에 별 6천 개를 넘겼지만 API는 정식 출시 전에 바뀔 수 있다.
에이전트가 이 API를 학습한 스킬이 있으므로 API가 바뀌면 스킬도 함께 바뀌어야 한다.

## 인사이트

### 시험해 볼 것

이 라이브러리를 판단하려면 에이전트가 자기 프로젝트의 컴포넌트를 동작으로 조립하는지
작은 범위로 시험하는 것이 가장 빠르다.
관찰할 것은 다음과 같다.

1. 에이전트가 만든 컴포넌트가 키보드와 스크린 리더에서 기대대로 동작하는지.
2. 같은 요구를 기존 컴포넌트 라이브러리로 만들 때와 코드량과 비용이 어떻게 다른지.
3. API가 바뀐 뒤 스킬 갱신이 얼마나 빨리 이루어지는지.
