## 소개

MOSS-Image는 OpenMOSS 팀(MOSI.AI)이 2026년 10월 16일 공개한
텍스트-이미지 생성 모델과 그 추론 코드다.
저장소는 사전학습 기반 모델인 MOSS-Image-Base와
선별한 데이터로 추가 학습한 MOSS-Image-SFT 두 가지 가중치를 안내한다.
README가 내세우는 특징은 글자와 요소의 배치를 지정하는 레이아웃 제어,
선명하고 정확한 글자 렌더링, 4K 토큰까지의 긴 프롬프트,
애니메이션부터 사실적인 그림까지의 다양한 스타일,
LoRA 같은 미세조정의 용이함, 50억 파라미터 골격의 효율이다.
다른 GPU 플랫폼에서 학습했다는 점도 특징으로 꼽는다.

홈페이지는 이 제품군을 Base와 선별한 데이터로
미세조정한 SFT 두 체크포인트로 소개한다.
자연어 프롬프트에 더해 객체와 그릴 글자와
그 공간 위치를 JSON 프롬프트로 지정하는
텍스트 기반 레이아웃 생성을 기본 기능으로 내세우고,
Python과 Gradio 인터페이스가 같은 Diffusers 파이프라인을 쓴다고 설명한다.
홈페이지의 소식란은 10월 16일 공개를 알리는 한 줄뿐이다.
라이브 데모(Hugging Face Space)와 QQ 그룹, Feishu 커뮤니티 링크가 있다.
쇼케이스는 글자, 일러스트, 사진,
시각 디자인을 보여 주는 이미지로 이루어져 있어서
이 문서가 읽을 수 있는 것은 설명 문구뿐이다.

README의 소식란에 따르면 기술 보고서는 10월 19일 arXiv(2610.23374)에 올라왔다.
공개 당일인 10월 16일에 SGLang, vLLM-Omni, ComfyUI가 처음부터 지원했고,
10월 18일에는 외부 개발자가 만든 학습 도구 KohakuMossTrainer가 나왔다.
공개 후 사흘 만에 추론 엔진과 학습 도구가 붙었다는 뜻이다.

기술 보고서의 문제 설정은 이렇다.
공개 가중치 모델은 포스터나 인포그래픽처럼 글자가 많고 배치가 복잡한 그림에서
여전히 약하다고 한다.[^report]
보고서는 렌더링과 사양 지정이라는 두 가지 문제가 엮인 데서 원인을 찾는다.
렌더링은 긴 글자를 정확히 그리고 공간 제약을 따르는 일이고,
사양 지정은 짧은 요청을 내용과 배치 지시로 풀어 쓰는 일이다.[^report]
그래서 생성 모델과, 요청을 구체적인 사양으로 바꿔 주는
에이전트형 프롬프트 향상기를 짝지었다.[^report]

홈페이지는 가중치가 Apache-2.0이고
파이프라인 코드와 외부 구성요소는 각자의 라이선스를 유지한다고 적는다.
README는 독립 실행형 파이프라인 코드가 Apache-2.0이라고 적는다.
Hugging Face의 Base와 SFT 모델 항목에는 `apache-2.0`
라이선스 태그가 달려 있다.[^hf-base][^hf-sft]
두 페이지가 라이선스의 대상을 다르게 서술하므로
쓰기 전에 저장소의 LICENSE와 모델 카드를 직접 확인해야 한다.
저장소는 2026년 10월 16일에 만들어졌고,
Hugging Face의 모델 저장소는 10월 11일에
만들어진 것으로 표시된다.[^hf-base][^hf-sft]
이 글을 쓴 시점에 내려받기는 Base가 약 3,600회, SFT가 약 4,500회이고
좋아요는 각각 438개와 498개다.[^hf-base][^hf-sft]

## 구성

### 골격과 입력 경로

생성기는 처음부터 학습한 단일 스트림(single-stream) DiT다.
텍스트 토큰과 이미지 잠재 벡터를 하나의 열로
합쳐 공동 자기 어텐션으로 처리한다.[^report]
텍스트 인코더는 고정된 Qwen3.5-9B이고 VAE는 고정된 FLUX.2 VAE이며,
50억이라는 수는 이 둘을 뺀 생성기만을 센 것이다.[^report] 42개 블록,
은닉 크기 3072, 24개 헤드로 구성되고 어텐션에는 참조 인덱스,
순서 위치, 너비, 높이를 담은 4차원 RoPE를 쓴다.[^report]

자연어 설명과 구조화된 레이아웃은 같은 텍스트 조건 경로로 들어간다.
그래서 모델은 어느 쪽 형식으로든 지시를 따른다.[^report]
참조 이미지 축은 앞으로의 확장을 위해 남겨 두었고,
지금은 모든 토큰이 이 축을 0으로 둔다.[^report]

### 사전학습 데이터와 학습 방식

그림 3에 따르면 말뭉치는 공개 출처 16곳에서 모은 55억 장이며,
중복 제거와 AI 생성 이미지 제거를 거쳐 32억 장이 남았다.[^report]
그 뒤에는 추가 필터링을 하지 않는다.[^report]
워터마크나 흐릿함, 압축 열화 같은 속성은 제외 기준으로 쓰지 않고
캡션에 적어 넣는 방식을 택했다.
보고서는 이를 거르지 말고 주석을 달라는 원칙으로 요약한다.[^report]

캡션은 Gemma 4로 한 문장, 한 문단, 상세 설명의 세 가지 길이로 만들었다.[^report]
원래 캡션과 재작성 캡션은 20 대 80으로 섞어 쓰고,
일부 이미지에는 바운딩 박스와 글자 내용을 담은 구조화 주석을 붙인다.[^report]
글자의 줄바꿈도 주석에 그대로 보존하며,
보고서는 줄바꿈이 곧 배치의 한 형태라고 말한다.[^report]
최적화는 Muon과 AdamW를 섞어 쓴다. 10억 파라미터 규모의 소규모 실험에서는
이 조합이 AdamW보다 손실 0.41까지 33.2%, 0.403까지 28.6%
적은 스텝으로 도달했다고 한다.[^report]

### 에이전트형 프롬프트 향상기

짧은 요청을 상세한 사양으로 바꾸는 단계는 GPT-6을 기획자로 쓴다.[^report]
요청한 매체(포스터, 인포그래픽, 사용자 인터페이스)에 따라 작업 경로를 고르고,
웹과 이미지 검색으로 참고 자료를 찾아 보며,
글자 원문, 요소, 바운딩 박스, 타이포그래피를 JSON으로 적는다.[^report]
JSON 문법, 좌표 유효성, 글자가 상자에 들어가는지를 반환 전에 검사한다.[^report]
저장소에는 이 역할을 하는 프롬프트 향상기 스킬이 들어 있고,
GPT-6 계열 에이전트와 로컬 파일·Python 도구를 가정한다.

## 사용하기

설치하려면 저장소를 받아 `pip install -r requirements.txt`를 실행한다.
Python에서는 Diffusers의 `DiffusionPipeline`을
`custom_pipeline="pipeline_moss_image"`와
`trust_remote_code=True`로 불러 쓴다.
Gradio 앱은 `pip install -e '.[ui]'` 뒤에 `python gradio_app.py`로 실행하고,
ComfyUI는 안내가 둘로 나뉜다.
홈페이지는 ComfyUI Manager에서
MOSS-Image를 검색해 기본 플러그인을 설치하라고 하고
공식 ComfyUI 저장소로의 통합은 진행 중이라고 적는다.
README는 그 뒤의 상태를 적는다.
ComfyUI의 최신 master나 nightly가 MOSS-Image를 기본으로 지원하므로
ComfyUI 형식 가중치와 내장 로더만 있으면 되고 별도 플러그인이 필요 없으며,
저장소의 플러그인은 로컬 Hugging Face와 Diffusers 디렉터리를 읽거나
기존 플러그인 워크플로를 이어 쓸 때를 위해 남아 있다는 것이다.
홈페이지가 더 이른 상태를 담고 있는 것으로 보이며 이는 이 문서의 해석이다.

홈페이지의 빠른 시작은 Python 3.10 이상과 NVIDIA GPU를 요구하고,
쓰는 CUDA 환경에 맞는 PyTorch를 먼저 설치한
뒤 `requirements.txt`를 설치하라고 한다.
레이아웃 예제는 JSON을 `layout.json`으로 저장해 Python에서 읽은 뒤
`json.dumps(layout, ensure_ascii=False)`로 프롬프트에 넘기며,
1024×1024 크기에 50스텝, CFG 3.0, 비조건 분기의 22번 층 건너뛰기를 쓴다.
Gradio에서는 JSON을 프롬프트 칸에 붙여 넣고 너비와 높이를 1024로 맞춘다.
Gradio의 Compile DiT는 기본으로 꺼져 있고 순차 메모리 모드에서는 쓸 수 없으며,
메모리가 모자라면 순차 모드를 고르거나 이미지 크기를 줄이라고 한다.
홈페이지에는 GPU 메모리 요구량이나 평가 수치가 없다.

사용자 가이드가 권장하는 추론 설정은 다음과 같다.
Base 모델은 CFG 같은 추론 매개변수를 증류하지 않은 상태라서
알맞은 설정을 직접 골라야 좋은 결과가 나온다고 가이드는 말한다.[^guide]
README의 Python 예제는 1456×1456, 50스텝, CFG 3.0,
비조건 분기의 22번 층 건너뛰기로 호출하고,
Python API의 부정 프롬프트 기본값은 비어 있다.
아래 표의 부정 프롬프트는 가이드가 권하는 값이다.[^guide]

| 항목          | 권장값                                                            |
| ------------- | ----------------------------------------------------------------- |
| 해상도        | 100만, 150만, 200만 화소 권장, 25만에서 400만 화소까지 외삽 가능  |
| 크기 제약     | 가로와 세로는 16의 배수                                           |
| 스텝 수       | 50 이상                                                           |
| CFG           | 기본 3.0, 권장 범위 3.0~6.0, 짧은 프롬프트에서는 높임             |
| 시프트        | 5.0                                                               |
| 샘플러        | 플로 매칭 Euler                                                   |
| SLG           | 두 번 추론하는 방식에서 비조건 분기의 22번 층(0부터 셈)을 건너뜀  |
| 부정 프롬프트 | `nsfw, worst quality, bad anatomy, watermark, jpeg artifact` 권장 |

SLG(Skip Layer Guidance)를 끄면 결과가 매우 사실적으로 보이지만
일부 디테일이 무너질 수 있다고 가이드는 경고한다.[^guide]
메모리 모드는 GPU 상주, 구성 요소 단위 이동,
순차(느리지만 메모리 절약)의 세 가지다.

레이아웃 입력은 `summary`와 `items`로 이루어진 JSON이다.
`bbox_format`이 `yxyx`이면 `[y_min, x_min, y_max, x_max]`이고,
`bbox_coord_space`가 `abs_centralized`이면
캔버스 중심을 원점으로 한 픽셀 좌표다. 1024×1024 캔버스에서는
각 축이 −512에서 +512까지이고 x는 오른쪽으로, y는 아래쪽으로 커진다.
출력 크기와 좌표가 일치해야 하므로 Gradio에서는 같은 너비와 높이를 지정한다.

미세조정을 할 때는 텍스트 인코더를 고정한 채 두라고 가이드는 권한다.[^guide]
간단한 SFT로 GIF 생성이나 참조 기반 생성 같은 기능을 얻을 수 있었다고 적지만
그 결과는 이 가이드에 없다.[^guide]
공식 쪽의 소수 단계 증류(DMD)와 레이아웃 향상기 모델은 작업 중이라고
한다.[^guide]
다만 공개 첫 주에 외부 개발자가 8스텝 증류를 먼저 내놓았다(아래 생태계 절).

## 실행 방법별 안내

같은 모델을 네 가지 경로로 돌릴 수 있다.
경로마다 매개변수 이름과 기본값이 조금씩 다르므로 아래에 나란히 정리한다.
이 절의 코드는 소스에서 읽은 매개변수로 쓴 것이며
이 문서를 쓰면서 실행해 보지는 않았다.
그래서 처음 돌릴 때는 작은 해상도로 한 장을 먼저 뽑아 보는 편이 안전하다.

### Diffusers

저장소 README의 예제를 기준으로, 레이아웃 JSON을 넣는 형태로 바꾼 것이다.
`trust_remote_code=True`는 저장소가 제공하는 파이프라인 코드를 내려받아
실행하므로 그 코드를 먼저 읽어 보는 것이 좋다.
Hugging Face 파이프라인 시그니처에서 읽은 기본값은
`num_inference_steps=50`, `guidance_scale=3.0`,
`uncond_skip_layers=(22,)`, `max_sequence_length=4096`이다.

```python
import json
import torch
from diffusers import DiffusionPipeline

pipe = DiffusionPipeline.from_pretrained(
    "OpenMOSS-Team/MOSS-Image-SFT",
    custom_pipeline="pipeline_moss_image",
    trust_remote_code=True,
    torch_dtype={"default": torch.bfloat16, "vae": torch.float32},
)
pipe.scheduler = type(pipe.scheduler).from_config(pipe.scheduler.config)
pipe.to("cuda")

layout = json.load(open("layout.json", encoding="utf-8"))
image = pipe(
    json.dumps(layout, ensure_ascii=False),
    height=1088,
    width=1920,
    num_inference_steps=50,
    guidance_scale=3.0,
    negative_prompt="nsfw, worst quality, bad anatomy, watermark, jpeg artifact",
    uncond_skip_layers=[22],
    generator=torch.Generator("cpu").manual_seed(42),
).images[0]
image.save("menu.png")
```

가로 1920에 세로 1080은 16의 배수가 아니므로 1088로 올렸다.
좌표는 반드시 이 출력 크기를 기준으로 계산해야 한다.
가중치는 bf16 기준으로 트랜스포머 약 10.2GB,
텍스트 인코더 약 16.8GB, VAE 0.25GB로 합이 약 27GB이므로
한 장의 GPU에 모두 올리려면 큰 메모리가 필요하다.[^hf-sft]
메모리가 모자라면 홈페이지가 안내하는 순차 모드나
ComfyUI의 양자화 가중치를 쓴다.

DiffSynth-Studio는 다른 Python 경로를 제공한다.
`MOSSImagePipeline`을 쓰고 VRAM 관리를 켜 두면
프레임워크가 매개변수를 CPU와 GPU 사이에서 옮겨 준다.
호출 인자는 `cfg_scale`(기본 3.0), `sigma_shift`(기본 5.0),
`uncond_skip_layers`(기본 `(22,)`)처럼 Diffusers와 이름이 다르다.[^diffsynth]

### ComfyUI

ComfyUI 저장소에는 MOSS-image 지원 풀 리퀘스트가
2026년 10월 16일에 병합되었다.[^comfy-pr]
Comfy-Org가 올린 변환 가중치 저장소는
모델별로 정밀도 변형을 제공한다.[^comfy-repack]

| 구성 요소        | 파일                                         | 크기                   |
| ---------------- | -------------------------------------------- | ---------------------- |
| diffusion_models | `moss_image_{base,sft}_bf16`                 | 각 10.16 GB            |
| diffusion_models | `moss_image_{base,sft}_int8_convrot`         | 각 5.41 GB             |
| text_encoders    | `qwen3.5_9b` bf16 / int8_convrot / w4a8_gptq | 19.31 / 9.75 / 7.34 GB |
| vae              | `flux2-vae` / `flux2-vae_small`              | 0.34 / 0.25 GB         |
| loras            | `moss_image_color_depth_control`             | 0.31 GB                |

워크플로는 다음 순서로 이어 붙이면 된다.
이 순서는 파일 구성에서 이 문서가 정리한 개요이며
노드의 정확한 이름은 ComfyUI의 내장 템플릿을 열어 확인해야 한다.

```text
UNet 로더 (moss_image_sft_bf16 또는 int8_convrot)
CLIP 로더 (qwen3.5_9b 계열 텍스트 인코더)
VAE 로더 (flux2-vae)
→ 프롬프트 노드 (자연어 또는 레이아웃 JSON 문자열)
→ 부정 프롬프트 노드
→ 샘플러 (스텝 50, CFG 3, shift 5, Euler)
→ VAE 디코드 → 이미지 저장
```

정밀도 변형 중 어느 것이 품질을 얼마나 잃는지는
어느 소스에도 측정이 없다.
메모리가 허락하면 bf16으로 기준 이미지를 만들고
양자화본과 같은 시드로 비교해 보는 것이 방법이다.
Comfy-Org 저장소에는 색 영역 지도와 깊이 지도를 쓰는 제어 LoRA가
들어 있고, 비공식 어댑터 `darask0/MOSS-Image-color-depth-control`은
영역마다 프롬프트를 따로 쓰는 방식으로 쓰라고 안내한다.
장면 프롬프트 하나만 주면
마네킹 모양의 지도를 마네킹으로 그린다고 한다.[^darask]

### fal.ai API

fal.ai는 SFT 체크포인트를 호스팅하며 1메가픽셀에 0.05달러를 받는다.[^fal]
계산해 보면 1024×1024는 약 0.052달러,
1456×1456은 약 0.106달러, 1920×1072는 약 0.103달러다.
입력 매개변수는 페이지의 스키마에서 읽은 것이다.[^fal]

| 매개변수                  | 값                                                               |
| ------------------------- | ---------------------------------------------------------------- |
| `prompt`                  | 1~16384자, 자연어와 태그 열과 JSON 레이아웃                      |
| `negative_prompt`         | 비어 있으면 부정 분기에서 트랜스포머 층 건너뛰기를 쓴다          |
| `enable_prompt_expansion` | 기본 true, 레이아웃을 먼저 구조화하고 보여 줄 글자는 보존한다    |
| `image_size`              | 이름 열거형 또는 `{width, height}`, 16의 배수로 반올림, 512~2048 |
| `num_inference_steps`     | 1~100, 기본 50                                                   |
| `guidance_scale`          | 0~10, 기본 3                                                     |
| `num_images`              | 1~4                                                              |
| `enable_safety_checker`   | 기본 true                                                        |
| `output_format`           | jpeg(기본), png, webp                                            |

응답에는 `images`, `seed`, `has_nsfw_concepts`와
확장된 JSON을 담은 `actual_prompt`가 들어 있다.[^fal]
레이아웃을 직접 쓸 때는 확장 기능을 꺼야 내가 쓴 좌표가 그대로 쓰인다는 것이
이 문서의 추론이다.
페이지는 확장을 켜면 레이아웃을 새로 기획한다고만 설명한다.[^fal]

```python
import fal_client

result = fal_client.subscribe(
    "fal-ai/moss-image",
    arguments={
        "prompt": open("layout.json", encoding="utf-8").read(),
        "image_size": {"width": 1920, "height": 1088},
        "num_inference_steps": 50,
        "guidance_scale": 3,
        "enable_prompt_expansion": False,
        "output_format": "png",
        "seed": 42,
    },
)
print(result["images"][0]["url"], result["has_nsfw_concepts"])
```

`image_size`의 상한이 2048이므로 4K 해상도는 이 경로로 얻을 수 없다.
모델 자체는 25만에서 400만 화소까지 외삽한다고 가이드가 적는다.[^guide]

### Gradio와 Hugging Face Space

저장소의 `gradio_app.py`를 로컬에서 실행하거나 공식 Space를 쓴다.
Space는 ZeroGPU에서 돌아가며
호출마다 GPU를 80초씩 쓰도록 설정되어 있다.[^hf-space]
Base와 SFT를 모두 불러오고, 너비와 높이, 스텝, CFG, shift, 시드,
이미지 수, 최대 글자 길이(1~4096), 건너뛸 층,
SLG 층과 세기를 조절한다.[^hf-space]
기본 부정 프롬프트는
`nsfw, worst quality, bad anatomy, watermark, jpeg artifact`다.[^hf-space]
로그인한 사용자는 자기 ZeroGPU 할당량을 쓰고
로그인하지 않은 사용자는 작은 공용 할당량을 나눠 쓴다.[^hf-space]
Space의 쇼케이스 20장은 모두 Base로 만든 것이고
그중 10장의 프롬프트가 JSON 레이아웃이다.
스텝은 19장이 50이고 1장이 30이며,
CFG는 5가 10장, 3이 9장, 4가 1장이다.[^hf-space]

### 목표별 샘플링 설정

가이드와 Space 쇼케이스, fal.ai 기본값에서 읽은 숫자로 정리했다.
소스가 직접 권한 값과 이 문서의 추론을 구분해 적는다.

| 목표                 | 설정                                                  | 근거                                 |
| -------------------- | ----------------------------------------------------- | ------------------------------------ |
| 기본값               | 스텝 50, CFG 3, shift 5, 22번 층 건너뛰기             | 가이드와 fal.ai 기본값[^guide][^fal] |
| 짧은 프롬프트        | CFG를 3보다 높임(3~6 범위)                            | 가이드[^guide]                       |
| 글자와 레이아웃 위주 | 스텝 50 이상, JSON 입력, 출력 크기와 좌표 기준을 일치 | 가이드[^guide]                       |
| 사진 질감            | 건너뛰기 층을 22, 24, 26 중에서 시험                  | 가이드[^guide]                       |
| 해상도               | 100만, 150만, 200만 화소 중에서 고름                  | 가이드[^guide]                       |
| 빠른 시안            | 8스텝 DMD LoRA, 진행 중인 실험 단계                   | 모델 카드[^dmd]                      |
| 한 번에 여러 후보    | `num_images` 최대 4(fal.ai), 시드를 바꿔 반복         | fal.ai[^fal]                         |

빠른 시안용 DMD와 FP16 변형이 정식 가중치와 같은 품질인지는
어디에도 비교가 없으므로 최종 산출물은 정식 가중치로 다시 뽑는 것을
이 문서는 권한다.

## 맥북과 맥미니에서 돌리기

결론부터 쓰면, 돌릴 수 있다.
다만 공식 경로로는 돌릴 수 없고 커뮤니티 경로로만 돌릴 수 있다.
공식 Gradio 앱은 CUDA가 없으면 생성을 거부하고,
`inference_runtime.py`의 장치 선택은 CUDA가 없을 때
MPS(Apple의 GPU 가속 백엔드)가 아니라 CPU로 떨어진다.
Diffusers 파이프라인도 시간 임베딩을 float64로 계산하는데
MPS는 float64를 지원하지 않아서,
첫 디노이징 스텝에서 `TypeError: Cannot convert a MPS Tensor to float64 dtype`이
난다.[^gh-issue5][^gh-pr7]
이 절은 2026-10-21 시점에 열어 본 자료만 근거로 한다.
측정값은 모두 남이 올린 것이고 이 문서가 직접 돌려 본 것은 없다.
이 문서를 쓴 맥은 36GB 통합 메모리의 Apple silicon이지만
PyTorch가 없어서 실행해 보지 않았다.

### 지금 되는 경로

| 경로                                    | 상태                                   | 막히는 곳                                    |
| --------------------------------------- | -------------------------------------- | -------------------------------------------- |
| 공식 Gradio, 공식 `configure_pipeline`  | CUDA 전제, 맥에서는 안 됨              | CUDA 없으면 생성 거부 또는 CPU로 낙하        |
| Diffusers + MPS (PR #7)                 | 열려 있고 병합되지 않은 PR             | PR을 직접 받아 써야 함                       |
| ComfyUI + MPS (PR #7의 `model.py` 수정) | 한 사용자가 M5 Max에서 확인            | 같은 수정이 필요, 단일 파일 로더는 별도 결함 |
| MLX 포팅 (moss-image-mlx)               | 가장 적은 메모리, 사전 양자화본 있음   | 제3자 구현, 속도는 양자화로 줄지 않음        |
| mflux 포팅                              | 병합되지 않은 PR, 작성자 자체 벤치마크 | 제3자 구현, 검증 근거가 PR 본문뿐            |
| GGUF + stable-diffusion.cpp             | DiT만 변환, 인코더와 VAE 별도          | 맥 실행 보고를 이번에 찾지 못함              |
| 호스팅 (fal.ai, 공식 Space)             | 장치와 무관                            | 비용, 정책, 앞의 안내 절 참고                |

Diffusers + MPS 경로의 PR #7은
`mps_runtime.py`, 맥용 설치와 실행 스크립트, 버전 고정 파일,
ComfyUI `model.py` 수정을 한꺼번에 추가한다.
핵심은 세 가지다.
Qwen 텍스트 인코더(약 17GB)와 DiT(약 10GB)를 동시에 올리지 않고
두 프롬프트 가지를 먼저 인코딩해 캐시한 뒤 DiT를 올린다.
float64 사인파 계산만 CPU로 보낸다.
Compile DiT와 CUDA 오프로드 모드는 MPS에서 끈다.
런처는 DiT를 FP16으로 기본 설정하고
`MOSS_MPS_DIT_DTYPE=bfloat16`으로 비교할 수 있게 한다.
PR은 torch 2.14.1, diffusers 0.41.0, transformers 5.20.1,
Python 3.12 네이티브 arm64를 고정하고
디스크 여유 약 40GB를 요구하며
512×512, 10스텝부터 시작하라고 안내한다.[^gh-pr7]
이 PR은 작성 시점에 병합되지 않았고,
저장소 README에는 맥이나 MPS 언급이 없다.[^gh-pr7]

별도 결함이 하나 더 있다.
ComfyUI의 네이티브 단일 파일 로더 `MOSSImageUNETLoader`는
Comfy-Org가 올린 체크포인트 4종에서 모두 실패한다는 보고가 있다.
융합된 `proj.qkv`와 분리된 q/k/v가 맞지 않기 때문이다.
보고자는 CUDA 환경이었고 수정 PR #11이 열려 있다.[^gh-issue10]
따라서 맥의 ComfyUI에서는 PR #7이 쓰는 `MOSSImageHFLoader`
경로(Diffusers 형식 디렉터리)가 확인된 쪽이다.[^gh-pr7]

### 구성 요소별 메모리

DiT 약 50억 파라미터, 텍스트 인코더 Qwen3.5-9B, VAE의 크기다.
“실측”은 저장소 파일 크기이고 “추정”은 이 문서의 계산이다.

| 구성 요소  | bf16/fp16                                            | fp8             | int8                         | 4비트                                          |
| ---------- | ---------------------------------------------------- | --------------- | ---------------------------- | ---------------------------------------------- |
| DiT        | 10.16GB (실측)[^hf-sft]                              | 약 5.1GB (추정) | 5.41GB (실측)[^comfy-repack] | 2.66GB (mflux 변환본, 제3자 표기)[^mflux-card] |
| Qwen3.5-9B | 16.79GB (실측)[^hf-sft], 리팩 19.31GB[^comfy-repack] | 약 9GB (추정)   | 9.75GB (실측)[^comfy-repack] | 7.34GB (w4a8_gptq, 실측)[^comfy-repack]        |
| VAE        | 0.25GB (fp32 보관)                                   | 해당 없음       | 해당 없음                    | 해당 없음                                      |

fp16은 bf16과 크기가 같다.
fp8 열은 파라미터 수를 반으로 나눈 계산이고 파일로 확인하지 않았다.
이 표는 가중치만 센 것이다.
활성값, 어텐션 작업 공간, VAE 디코드, 긴 프롬프트가 더해진다.

실행 중 최대 메모리로는 다음 값이 보고되어 있다.

| 구현            | 설정                 | 최대 메모리 | 출처                   |
| --------------- | -------------------- | ----------- | ---------------------- |
| MLX 8bit        | 1024², 짧은 프롬프트 | 9.3GB       | 포팅 README[^mlx-port] |
| MLX compact     | 같음                 | 7.4GB       | 포팅 README[^mlx-port] |
| MLX bf16        | 같음                 | 16.6GB      | 포팅 README[^mlx-port] |
| MPS 전부 상주   | 1024², 50스텝        | 37.4GB      | PR #8[^gh-pr8]         |
| MPS 인코더 해제 | 같음                 | 27.4GB      | PR #8[^gh-pr8]         |

MLX 쪽 수치는 프롬프트가 650토큰이면 약 1GB 더 든다고 밝혀 두었다.
MLX 포팅은 단계를 차례로 올리고 내려서
최대치가 단계 합이 아니라 가장 큰 단계가 되도록 했다.[^mlx-port]
같은 모델을 MPS에서 단계 구분 없이 올리면 37GB까지 올라가므로
같은 하드웨어에서도 구현에 따라 메모리가 4배 가까이 다르다.

### 메모리별 판정

macOS와 다른 앱이 쓰는 몫을 6~8GB로 잡은 것은
이 문서의 추정이다.
“확인”은 같은 구성의 맥에서 누군가 측정했다는 뜻이다.

| 통합 메모리 | 판정                      | 근거 구분                                                                |
| ----------- | ------------------------- | ------------------------------------------------------------------------ |
| 8GB         | 사실상 어렵다             | compact 최대 7.4GB가 가용분을 넘는다 (추정). 실행 보고 없음              |
| 16GB        | MLX compact로 가능성 있음 | 최대 7.4GB (실측, 다른 기기). 16GB 기기 실행 보고는 못 찾음              |
| 24GB        | MLX 8bit가 권장 구간      | 포팅 카드가 24GB 이상에 8bit를 권장[^mlx-card]. 24GB 실행 보고는 못 찾음 |
| 32GB        | 가능                      | M1 Max 32GB에서 SFT가 PR #7 경로로 돌았다[^gh-issue5]                    |
| 36GB        | 32GB와 같다고 본다        | 추정. 36GB 실행 보고는 못 찾음                                           |
| 48GB        | 가능                      | M4 Pro 48GB에서 MLX 측정[^mlx-port]                                      |
| 64GB        | 가능, 단계 구분 없이도    | M4 Pro 64GB에서 MPS 측정, 최대 37.4GB[^gh-pr8]                           |
| 96GB        | 64GB와 같다고 본다        | 추정. 96GB 실행 보고는 못 찾음                                           |
| 128GB       | 가능                      | M5 Max 128GB에서 ComfyUI 측정[^gh-pr7]                                   |

“못 찾음”은 없다는 뜻이 아니라 이번 검색에서 열어 보지 못했다는 뜻이다.

### 속도

속도는 메모리와 달리 양자화로 줄지 않는다.
MLX 포팅 쪽은 모델이 연산량에 묶여 있어서
양자화는 메모리만 줄이고 시간은 줄이지 않는다고 밝혔다.[^mlx-port]
PR #8의 층별 측정도 같은 결론이다.
1024²에서 DiT 한 층이 약 200ms였고
이론 7.6 TFLOPS 가운데 5.7을 쓰고 있었다.[^gh-pr8]

| 기기         | 구현         | 설정                 | 시간                                     |
| ------------ | ------------ | -------------------- | ---------------------------------------- |
| M1 Max 32GB  | PR #7, BF16  | 1024², 20스텝        | 320초[^gh-issue5]                        |
| M4 Pro 64GB  | PR #8 MPS    | 1024², 50스텝, CFG 3 | 922초[^gh-pr8]                           |
| M4 Pro 48GB  | MLX          | 1024², 50스텝, CFG 3 | 약 11.5~12.5분[^mlx-port]                |
| M5 Max 128GB | ComfyUI MPS  | 1024², 50스텝, CFG 3 | 242초 (4.51초/스텝)[^gh-pr7]             |
| M3 Max       | mflux 변환본 | 1024², BF16          | 스텝당 약 13.9초, 작성자 표기[^mflux-pr] |

M1 Max 값은 로딩과 저장을 포함한 전체 시간이고
통제된 벤치마크가 아니다.[^gh-issue5]
PR #8은 스텝을 줄여도 글자가 맞게 나온다고 보고했다.
10스텝 186초, 20스텝 385초, 30스텝 575초였다.
다만 시드 하나로 본 결과다.[^gh-pr8]
CFG 1은 글자가 깨졌고 CFG 2~4.5는 글자가 맞게 나왔다.[^gh-pr8]
스텝과 CFG를 낮추면 맥에서 한 장에 몇 분대로 줄일 수 있지만
그 품질은 이 문서가 확인하지 못했다.

### 목적별 권장 구성

- **16GB:** MLX compact 한 가지가 후보다.
  메모리는 맞지만 실행 보고가 없으니 먼저 512² 한 장으로 확인한다.
- **24GB:** MLX 8bit. 포팅 쪽 평가에서
  14개 프롬프트의 글자 인식이 bf16과 같았다는 점이 근거지만
  평가 규모는 14장이다.[^mlx-card]
- **32GB와 36GB:** MLX 8bit 또는 PR #7 경로. 둘을 같은 프롬프트로 비교한다.
- **64GB 이상:** MLX bf16이나 PR #7/ComfyUI 경로.
  양자화 없는 기준 화질이 필요할 때 고른다.
- **팀 내부 비교용:** 어느 경로든 프롬프트 30개를 같은 시드로 돌려
  인용한 글자와 레이아웃이 유지되는지 본다.

### 걸림돌

- **bf16과 MPS:** PR #7은 DiT를 FP16 기본으로 하고
  bf16은 비교용으로 둔다.[^gh-pr7]
  FP16-fixed 가중치가 따로 나온 것은 원본을 FP16으로 돌리면
  넘침이 날 수 있다는 뜻이므로, FP16 기본값은 화질을 확인하고 쓴다.[^fp16]
- **fp32 VAE:** VAE는 fp32로 두는 것이 원래 설정이다.
  메모리는 작아서(0.25GB) 줄일 이유가 없다.
- **컴파일과 오프로드:** MPS에서는 Compile DiT와
  CUDA 오프로드 모드가 꺼진다.[^gh-pr7]
- **Metal 교착:** PR #7은 모델을 올리고 동기화하는 중 Metal 교착을 피하려고
  `torch.mps.empty_cache`와 `torch.mps.synchronize`를 프로세스 전역으로
  감쌌다.[^gh-pr7] 다른 MPS 코드와 한 프로세스에서 쓰면 영향이 있을 수 있다.
- **열 제한:** 팬이 없는 맥북 에어는 몇 분짜리 연속 연산에서
  클럭이 내려갈 수 있다. 이 부분은 이 문서의 일반론이고
  MOSS-Image에서 측정한 자료는 찾지 못했다.
- **디스크:** 공식 가중치는 약 27GB(bf16)이고
  PR #7은 여유 40GB를 요구한다.[^hf-sft][^gh-pr7]
- **Hugging Face 토론:** SFT 저장소에는 파이프라인의 float64가
  MPS와 NPU, XPU에서 깨진다는 제목의 토론이 열려 있다.[^hf-disc5]

### 맥에서 먼저 확인할 것

아래 스크립트는 모델을 받지 않고 PyTorch의 MPS가 켜져 있는지,
float64가 막혀 있는지, bf16 연산이 되는지만 확인한다.
float64 실패가 보이면 위에서 설명한 첫 스텝 오류가 그대로 날 환경이다.

```python
import torch

print("torch", torch.__version__)
print("MPS built:", torch.backends.mps.is_built())
print("MPS available:", torch.backends.mps.is_available())

if torch.backends.mps.is_available():
    dev = torch.device("mps")
    for dtype in (torch.float32, torch.float16, torch.bfloat16, torch.float64):
        try:
            x = torch.ones(4, 4, device=dev, dtype=dtype)
            y = (x @ x).sum().item()
            print(f"{str(dtype):15} ok ({y})")
        except Exception as e:
            print(f"{str(dtype):15} FAIL: {type(e).__name__}: {e}")
```

float64가 FAIL로 나오는 것이 정상이다.
그 다음 단계는 PR #7의 `setup-mac.sh`가 쓰는 점검,
즉 `torch.backends.mps.is_available()` 단언과 같은 확인이다.[^gh-pr7]

### 이 절이 확인하지 못한 것

- 16GB, 24GB, 36GB, 96GB 기기에서 실제로 돌았다는 보고.
- GGUF와 stable-diffusion.cpp 경로가 맥에서 도는지.
  GGUF 카드는 DiT만 변환했고 인코더와 VAE를 따로 받아야 한다고 쓰며
  stable-diffusion.cpp의 MOSS-Image 지원 문서를 가리킨다.
  카드의 예시는 PowerShell이다.[^gguf-card]
- 위 속도 표의 값은 기기, 구현, 스텝 수가 제각각이라 서로 비교할 수 없다.
- PR #7과 mflux PR은 둘 다 병합되지 않았으므로
  내용이 바뀌거나 닫힐 수 있다.[^gh-pr7][^mflux-pr]

## 게임 개발에 쓰기

소스가 직접 다루는 것은 포스터, 인포그래픽, 사용자 인터페이스 화면이다.
보고서의 RealLayoutArena는 포스터 20개, 인포그래픽 20개,
사용자 인터페이스 21개로 이루어져 있다.[^report]
게임 개발에서는 이 가운데 사용자 인터페이스와 포스터 쪽이 가장 가깝다.
아래 용도는 소스가 직접 검증한 것과 이 문서가 추론한 것을 나누어 적는다.

### 메뉴와 HUD 시안, 포스터

레이아웃 JSON은 요소마다 종류, 설명, 글자, 상자를 받는다.
상자는 `[y_min, x_min, y_max, x_max]` 순서이고
캔버스 중심이 원점인 픽셀 좌표다.[^guide]
디자인 도구는 보통 왼쪽 위가 원점이므로 변환이 필요하고,
가이드는 가로 W와 세로 H에서 x에 W/2, y에 H/2를 빼라고 안내한다.[^guide]
다음 함수는 그 규칙을 적용한 것이며 메인 메뉴 시안을 만들어 출력을 확인했다.

```python
import json

W, H = 1920, 1088


def to_centered(box):
    x0, y0, x1, y1 = box
    return [round(y0 - H / 2), round(x0 - W / 2),
            round(y1 - H / 2), round(x1 - W / 2)]


buttons = [("게임 시작", (760, 520, 1160, 600)),
           ("설정", (760, 640, 1160, 720)),
           ("종료", (760, 760, 1160, 840))]
layout = {
    "summary": {"caption": "Main menu of a sci-fi game, dark space "
                           "background, glowing blue panels"},
    "items": [{"label": "text", "caption": "menu button", "text": t,
               "bbox": to_centered(b)} for t, b in buttons],
    "bbox_coord_space": "abs_centralized",
    "bbox_format": "yxyx",
}
print(json.dumps(layout, ensure_ascii=False))
```

높이를 1080이 아니라 1088로 둔 것은 출력 크기가 16의 배수여야 해서다.
좌표 변환 코드는 실행해서 확인했지만
이 입력으로 모델이 상자 안에 글자를 맞게 그리는지는 실행하지 않았다.
사용자 가이드는 레이아웃 입력을 실험적 기능으로 분류한다.[^guide]
MOSS_Global 트윗도 JSON 레이아웃 제어를 실험적이라고 적는다.[^tweet-moss]
보고서의 7Bench에서는 검출된 객체 기준 평균 IoU가 0.8786이지만
576개 대상 중 445개(77.3%)만 검출되었고 전체 평균 IoU는 0.6788이다.[^report]
따라서 열 개 중 두 개 정도는 요소가 아예 없거나 위치가 어긋난다고 보고
후보를 여러 장 뽑아 고르는 흐름을 짜는 것이 안전하다.
이 해석은 이 문서의 추론이다.

### 화면 안의 글자

보고서의 글자 평가(LLTB)는 영어와 중국어만 다룬다.[^report]
한국어 글자의 정확도는 보고서에 측정이 없다.
README의 예제도 중국어 메모지이며 한국어 예제는 확인하지 못했다.
그래서 한글 UI를 만들 때는 한글 문구를 직접 넣은 시험 세트를
먼저 돌려 오탈자 비율을 재 봐야 한다.
LLTB의 측정 방식에도 주의할 점이 있다.
OCR로 읽은 글자 단위의 재현율이어서 글자의 순서를 확인하지 않고
불필요하게 더 그린 글자에도 벌점이 없다.[^report]
게임 화면의 짧은 버튼 문구에서는 이 점수보다
눈으로 본 글자 오류가 더 믿을 만한 지표다.
영어 짧은 프롬프트에서 MOSS-Image는 98.0이고
중국어 긴 프롬프트에서는 92.4로 내려간다.[^report]

### 아이콘 묶음, 콘셉트 아트, 배경 텍스처

소스에는 아이콘 세트나 스프라이트 시트를 만든 사례가 없다.
태그 열 입력과 다양한 스타일(애니메이션부터 사실적인 그림까지)은
README가 내세우는 특징이다.
이를 바탕으로 콘셉트 아트와 배경 이미지를 뽑는 용도는 자연스럽지만,
이는 이 문서의 추론이다.
가이드의 태그 입력은 품질, 점수, 메타, 연도, 캐릭터, 시리즈,
작가, 일반 태그의 순서를 권장한다.[^guide]
캐릭터와 작가 태그는 훈련 데이터에 그 이름이 있었다는 전제를 두는데,
보고서가 밝힌 16개 출처 가운데 그런 태그 기반 출처는 확인되지 않는다.[^report]
이 출처 문제는 아래 안전 절에서 다시 다룬다.

### 일관된 화풍과 대량 생성

프로젝트 고유의 화풍은 LoRA로 맞추는 것이 현실적이다.
KohakuMoss는 어댑터 학습이 6GB와 8GB 카드에서 돌아간다고 적고
`vram_24g`부터 `vram_6g`까지 메모리 프로필을 제공한다.[^kohaku]
DiffSynth-Studio에는 LoRA와 전체 학습을 위한 `train.py`가 있고
학습 데이터는 이미지 경로와 설명이 담긴 메타데이터 파일로 준비한다.[^diffsynth]
가이드는 미세조정 때 텍스트 인코더를 고정하라고 권한다.[^guide]
캡션 작성을 위해서는 장문, 중문, 단문 세 길이와 워터마크 상자를 담는
JSON 프롬프트 예시를 제공한다.[^guide]
대량 생성에서는 fal.ai가 한 번에 최대 4장을 내고 메가픽셀당 요금이 붙으며,
ZeroGPU Space는 호출당 80초 제한이 있어
서비스용으로는 맞지 않는다.[^fal][^hf-space]
Space를 게임 서비스의 백엔드로 쓰는 것은 이 문서가 권하지 않는다.

fal.ai는 서비스 약관에서
API를 최종 사용자에게 직접 노출하지 말라고 요구한다.[^fal-tos]
따라서 게임 안에서 이미지를 생성하는 기능은
자체 서버를 거치도록 설계해야 한다.

### 한계

이 모델이 못 하거나 소스가 다루지 않는 것은 다음과 같다.

- 편집과 참조 이미지 입력.
  보고서는 이 골격이 텍스트-이미지 전용이며
  참조 이미지 조건이나 편집 기능이 없다고 한계에 적는다.[^report]
  레이아웃을 바꿔 다시 그리는 사례도 원본
이미지를 조건으로 쓰지 않는 재생성이다.[^report]
- 알파 채널.
  fal.ai 출력은 jpeg, png, webp이고 투명 배경을 낸다는 소스가 없다.[^fal]
  스프라이트용 투명 배경은 별도 배경 제거 단계가 필요하다고 추정하며
  이는 이 문서의 추론이다.
- 픽셀 아트 격자와 프레임 간 일관성.
  두 주제 모두 소스에 평가나 사례가 없고,
  GIF 생성은 가이드가 “간단한 SFT로 얻을 수 있었다”고만 적는다.[^guide]
- 프롬프트 향상기 의존.
  보고서 시스템의 높은 점수는 외부 대형 언어 모델이 쓴 사양에 기대며
  그 향상기는 비공개 모델을 가정한다.[^report]

## 검열과 안전

한국어 Threads 소개 글이 모델을 검열이 적은 모델로 부르면서
이 모델의 안전 장치가 무엇인지 묻는 사람이 생겼다.
이 절은 확인할 수 있는 사실만 모아 가중치를 직접 돌릴 때와
호스팅 서비스를 쓸 때를 나누어 정리한다.
유해한 이미지를 만드는 방법은 다루지 않고,
게임을 만드는 팀이 위험을 관리하는 관점으로만 쓴다.

### 모델과 파이프라인에는 필터가 들어 있지 않다

Hugging Face의 `model_index.json`은 구성 요소를 스케줄러, 텍스트 인코더,
토크나이저, 트랜스포머, VAE 다섯 가지로만 적고 안전 검사기 항목이 없다.
파이프라인 코드와 저장소의 파이썬 파일에도
안전, 검열, 거부, 필터와 관련된 코드나 문자열이 없다는 것을
이 문서가 직접 내려받아 검색해서 확인했다.
사용자 가이드에서 `nsfw`라는 단어는 권장 부정 프롬프트 태그로만 나온다.[^guide]
Base와 SFT 모델 카드에는 라이선스 항목만 있고
안전이나 한계를 다루는 항목은 없으며
접근을 제한하는 승인 절차도 없다.[^hf-base][^hf-sft]
따라서 가중치를 내려받아 직접 돌리는 경우
모델 쪽에는 요청을 막는 장치가 없고, 막을지는 돌리는 사람의 몫이다.
이것은 모델이 어떤 내용을 학습 단계에서 얼마나 덜 배웠는지와는 다른 이야기이며
그 부분은 아래에서 다룬다.

### 학습 데이터에 대한 보고서의 입장

보고서는 중복 제거와 AI 생성 이미지 제거 뒤에 추가 필터링을 하지 않았다고
적는다.[^report]
워터마크나 흐릿함 같은 속성은 거르지 않고 캡션에 표시하는 원칙이다.[^report]
다만 이는 출처 수준의 필터와 별개다.
보고서의 부록에 따르면 말뭉치의 큰 부분인 ReLAION과 OmniCorpus에서
약 93%(32억 3천만 장 중 약 30억 1천만 장)가 나오는데,
ReLAION에는 성인물과 워터마크 검사가 이미 적용되어 있었다.[^report]
따라서 추가로 거르지 않았다는 말은 출처에 적용된 필터를 제외하고
이 연구진이 더하지 않았다는 뜻으로 읽어야 한다.
이 단락의 마지막 문장은 이 문서의 해석이다.

연구진은 필터를 더한 소규모 실험도 보고한다.
초기 24층 모델에서 필터를 쓰면
OneIG의 글자 점수가 0.5243에서 0.1180으로 떨어졌고
남은 이미지는 11억 8천만 장 중 5억 1천만 장(43.35%)이었다.[^report]
즉 연구진이 필터를 쓰지 않은 이유는 성능이었고
안전 정책의 선택은 아니었다고 보고서의 서술은 말한다.
이 비교는 소규모 설정에서만 이루어졌으므로
최종 모델에 대한 증거로 확대하면 안 된다.

### 공식 발표와 소개 글이 말한 것

MOSS_Global 트윗은 Base와 SFT 가중치가 공개되었고
“Apache-2.0 licensed inference code”를 쓴다고 적는다.[^tweet-moss]
이 트윗은 검열이나 안전에 대한 말을 담고 있지 않다.
Open_MOSS 트윗은 앞의 게시물을 인용하며
새 모델을 써 보라는 짧은 말만 한다.[^tweet-open]
Threads 사용자 choi.openai는 모델이 검열이 적고
Apache 2.0 라이선스로 누구나 수정할 수 있다고 적었다.[^threads]
그 글은 검열이 적다는 근거를 제시하지 않으며
공식 자료에서도 그 표현을 찾을 수 없다.
같은 글의 답글에서 Threads 사용자 samlee0329는
원래 이미지 모델에는 검열이 없었고
이 모델은 검열을 추가한 것이 아니겠느냐고 했고,
filming.jun은 모델에도 검열이 적용된 경우가 많다고 했다.[^threads]
이 의견들은 모두 근거가 없는 추측이며
앞서 확인한 사실, 즉 파이프라인에 필터가 없다는 점과 어긋나지도 않고
뒷받침하지도 않는다.
글에서 말한 8스텝 버전은 공식 배포가 아니라
진행 중인 커뮤니티 DMD LoRA다.[^dmd]

### 호스팅 서비스는 다르다

fal.ai는 안전 검사기를 기본으로 켜 둔다.
꺼서 쓰려면 계정이 승인되어야 하고 승인되지 않은 요청은 항상 검사받으며,
걸러진 이미지는 검은 이미지로 돌아온다고 모델 페이지가 적는다.[^fal]
응답의 `has_nsfw_concepts`로 결과를 확인할 수 있다.[^fal]
fal.ai의 이용 정책은 미성년자 성적 착취, 동의 없는 성적 이미지,
노골적인 성적 콘텐츠, 사칭과 딥페이크, 저작권 침해,
안전 장치나 콘텐츠 필터를 우회하는 행위를 금지한다.[^fal-aup]
이용 약관에 따르면 이용자는 18세 이상이어야 하고
fal.ai에는 입력을 감시할 의무가 없으며
최종 사용자의 연령 확인 책임은 이용자에게 있다.[^fal-tos]
따라서 같은 가중치라도 fal.ai로 쓰면 필터와 약관이 있고
직접 돌리면 그것을 스스로 만들어야 한다.
Hugging Face의 콘텐츠 정책은 동의 없이 만든 성적 콘텐츠와
미성년자가 관련된 성적 콘텐츠, 지식재산권 침해를 금지하고
머신러닝 산출물을 올리는 사람이 아동 착취나 테러 목적의
사용 위험을 줄이는 조치를 취하라고 요구한다.[^hf-content]
공식 Space의 기본 부정 프롬프트에도 `nsfw`가 들어 있으나
이는 이미지 품질 조절용 문구이지 검사기가 아니다.[^hf-space]

### 라이선스가 말하는 것과 말하지 않는 것

모델 카드는 Apache-2.0이다.[^hf-base][^hf-sft]
Space의 NOTICE는 파이프라인 코드에
Meta Platforms의 BSD-3-Clause 코드가 섞여 있고
Qwen3.5-9B 인코더와 FLUX.2 VAE는 각자의 Apache-2.0 라이선스를 따르며
모델 가중치의 라이선스는 파이프라인 코드의 라이선스와 별개라고
적는다.[^hf-space-notice]
Apache-2.0은 상업적 이용을 허용하지만 이미지의 내용이 합법임을 보증하지 않는다.
학습 데이터의 출처에 대한 권리 문제도 이 라이선스가 해결해 주지 않는다.
이는 이 문서의 해석이다.

### 게임 스튜디오를 위한 위험 관리

게임에 이 모델을 쓰는 방식은 크게 둘이다.
개발 중에 에셋을 미리 만들어 두는 방식과
게임 안에서 플레이어의 입력으로 실시간 생성하는 방식이다.
세 플랫폼의 규정이 두 방식을 다르게 다룬다.

- Steam.
  콘텐츠 설문의 AI 항목은 미리 생성한 콘텐츠와 실시간 생성 콘텐츠를 나눈다.
  미리 생성한 것은 다른 콘텐츠처럼 검토하고,
  실시간 생성을 쓰면
불법 콘텐츠를 만들지 못하게 하는 방어책을 설문에 적어야 한다.[^steam]
- Apple App Store.
  사용자 생성 콘텐츠를 만들고 공유하는 앱(AI 콘텐츠 생성 앱 포함)은
  부적절한 자료를 거르는 방법, 신고 기능과 신속한 대응,
  악성 사용자 차단 기능, 공개된 연락처를 갖춰야 한다.[^apple]
- Google Play.
  생성형 AI 앱이 불쾌한 콘텐츠를 만들지 않게 할 책임이 개발자에게 있다고 하며
  텍스트-이미지 앱도 대상이다.
  동의 없는 딥페이크 성적 자료가 위반 사례로 들어 있다.[^gplay]

권리 문제는 미국 저작권청의 보고서가 짚는다.
2025년 1월 보고서는 순수하게 AI가 만든 결과물이나
사람의 표현 통제가 충분하지 않은 결과물에는 저작권이 없고
프롬프트만으로는 충분한 통제가 되지 않는다고 판단한다.[^usco]
사람이 만든 표현이 결과물에서 인식되거나
사람이 창의적으로 선택하고 배열하고 수정한 부분은 보호받을 수 있다.[^usco]
게임의 핵심 캐릭터나 로고를 생성 결과 그대로 쓰면
독점권을 주장하기 어려울 수 있다는 뜻이며,
레이아웃 JSON처럼 사람이 구조를 정하는 방식이 이 판단에 어떻게 반영될지는
소스에 없고 사안별로 따져야 한다.
이 문장의 해석은 이 문서의 추론이며 법률 자문이 아니다.

가장 무거운 위험은 미성년자가 관련된 이미지다.
미국 법무부의 안내는 실제 미성년자와 구별할 수 없는
컴퓨터 생성 이미지도 연방법상 아동 포르노의 정의에 들어가며
불법 소지물이라고 적는다.[^doj]
실시간 생성 기능을 넣는 팀은 이를 설계 단계의 필수 요건으로 보아야 한다.
EU AI Act 50조는 합성 이미지를 만드는 AI 시스템의 제공자에게
기계가 읽을 수 있는 인공 생성 표시를 요구하고,
딥페이크를 쓰는 쪽에 공개 의무를 지운다.[^eu-ai-act]
유럽에 서비스하는 게임이 생성 이미지를 노출한다면
표시 방식을 미리 정해 두어야 한다.

이 사실들에서 이 문서가 끌어낸 권고는 다음 순서다.

1. 미리 생성하는 에셋은 사람이 모든 결과를 보고 고르는 단계를 두고,
   프롬프트와 시드와 모델 버전, 생성일을 기록한다.
2. 실시간 생성은 입력에 대한 사전 검사와 출력에 대한 사후 검사를 모두 두는데,
   모델에 필터가 없으므로 둘 다 자체나 외부 서비스로 구현해야 한다.
3. 실시간 생성은 연령 확인과 신고 기능을 두고 생성 기록을 보관하며
   사람이 검토하는 경로를 마련한다.
4. 호스팅 API를 쓸 때는 서비스의 이용 정책이 요구하는 연령과 신고 의무를
   게임의 약관에 이어 준다.
5. 캐릭터와 작가 이름을 넣는 태그 입력은 쓰지 않거나,
   특정 작가의 화풍을 노리는 태그를 사내 금지어로 둔다.

이 권고를 뒤집을 관측은 두 가지다.
모델 개발자가 공식 안전 장치나 학습 데이터의 성적 콘텐츠 처리를
문서로 공개하는 경우, 그리고 사용하려는 플랫폼이 실시간 생성에 대한 규정을
바꾸는 경우다.

## 분석

### 렌더링과 사양 지정을 분리해 각각을 맡긴다

보고서의 구조는 문제를 둘로 나눈 데서 나온다.[^report]
글자를 정확히 그리는 능력은 생성기가 맡고,
무엇을 어디에 쓸지는 향상기가 정한다.
두 부분은 같은 텍스트 조건 경로로 이어진다.
그래서
향상기의 출력이 자연어든 JSON이든 생성기는 같은 입력 채널로 받는다.[^report]

이 분리에는 책임을 나누는 이점이 있다.
생성기를 평가할 때는 향상기를 빼고,
시스템을 평가할 때는 향상기를 넣는다.
그래서 보고서도 두 평가를 따로 세웠다.[^report]

### 레이아웃을 텍스트로 쓴다

레이아웃 제어는 별도의 어댑터나 제어 네트워크 없이
JSON 텍스트를 프롬프트로 받는 방식이다.
학습 때 바운딩 박스를 정규화, 절대 픽셀,
중심 기준 픽셀 좌표로 바꿔 가며 섞어 넣고,
사용자 가이드는 해상도와 종횡비가 달라져도 통하도록
중심 기준 절대 좌표를 쓴다고 설명한다.[^guide]
보고서는
0을 중심으로 한 절대 좌표가 0에서 1000으로 정규화한 상대
좌표보다 학습에 없던 해상도에 잘 일반화된다고 관찰했다고 적는다.[^report]

글자의 줄바꿈도 레이아웃의 한 형태로 다룬다.
줄바꿈을 주석에 보존하면 디노이징 초반에
각 줄의 글자 내용이 더 일찍 자리잡는다고 한다.[^report]

### 필터링을 하지 않고 주석을 단다

데이터 쪽 판단은 거르지 않고 표시하자는 것이다.
부록의 사전 실험은 이 선택을 뒷받침한다.[^report]
작은 24층 모델로 ReLAION 기반 말뭉치를 휴리스틱으로 걸러
11.8억 건 중 43.35%만 남기자 GenEval과 OneIG가 떨어졌고,
특히 OneIG의 글자 점수가 0.5243에서 0.1180으로 내려갔다.[^report]

보고서는 FDr⁶ 같은 분포 지표가 학습 데이터가 다를 때 공정하지 않을 수 있어
이 결과를 추세로만 읽으라고 덧붙인다.[^report]
이 글은 이 차이를 이렇게 해석한다.
엔트로피, 채도, 종횡비, 워터마크 면적에 건 조건이
글자가 빽빽한 이미지를 선택적으로 버렸을 가능성이 있다.

## 비평

### 가장 눈에 띄는 비교는 저자가 만든 벤치마크 위에서 이루어진다

LLTB와 RealLayoutArena는 이 보고서가 직접 만든 벤치마크이고
7Bench는 기존 벤치마크이지만 비교 모델의 점수는 저자가 직접 돌려 얻었다.
부록은 LongTextBench의 점수만 공개 보고서에서 가져왔고
7Bench, LLTB, RLA의 결과는 모두 자체 평가라고 밝힌다.[^report]
기존 벤치마크인 LongTextBench에서
MOSS-Image는 97.63점으로 표에 실린 열 개 모델 중 다섯 번째다.
SenseNova-U1.5(98.85), Seedream 4.5(98.80), HiDream-O1-Image-Pro(98.10),
HiDream-O1-Image(97.85)가 앞선다.[^report]

보고서는 이를 LongTextBench가 포화에 가깝다는 이유로 설명하고
더 긴 글자를 요구하는 LLTB를 주 평가로 삼는다.[^report]
그 판단은 일리가 있지만 새 벤치마크를 만든 쪽이
자기 모델이 강한 조건을 골랐을 가능성은 배제할 수 없다.
독립적인 재현이 없으면 이 가능성은 남는다.

독립적인 사용 후기는 있다.
FLUX 3 Image Klein 스레드에서 dragonwriter는 막 나온 MOSS-Image 5B가
글자와 구조화된 레이아웃이 강점이라는 소개와 달리
내용 폭, 프롬프트 유연성, 출력 품질, 검열과 학습 부족이 없다는 점에서
자신이 본 가장 좋은 범용 기반 모델이라고 평했다.
일반 용도의 가장 좋은 해상도는 1~2메가픽셀로 보인다고도 했다.[^dragonwriter]
jjcm은 MOSS의 디자인 능력이 기본 상태에서도 매우 인상적이고
글자 재현은 본 것 중 가장 좋은 편이지만 취향은 부족하다고
평했다.[^jjcm] jjcm은 이 글자 재현을 새 VAE 덕으로 돌렸는데,
보고서는 FLUX.2의 고정된 VAE를 쓴다고
적으므로 그 귀속은 확인되지 않는다.[^report]
두 평은 각각 한 사람의 정성 평가이고 다른 스레드의 댓글이지만,
저자가 만든 벤치마크의 순위와 별개로 사용자
평가도 같은 방향이라는 점은 참고할 만하다.

### 레이아웃 비교는 인터페이스가 다른 모델끼리 이루어진다

7Bench에서 MOSS-Image의 0.88과 0.70은
비교 모델의 0.30과 0.16 안팎에 비해 매우 높다.
그런데 이 모델은 JSON 레이아웃 형식으로 학습되었고,
다른 모델들은 같은 JSON을 프롬프트 텍스트로 받는다.
부록에 따르면 GPT Image 2는 224개 요청 중 22개가 안전 차단되어
흰 플레이스홀더가 영점으로 들어간다.[^report]

보고서는 Ideogram 4.0의 공개 보고 값이 약 0.69인데
자체 측정은 0.2433이라는 점도 그대로 적고,
모델 변종과 프롬프트 형식과 평가 구현의 차이가 원인일 수 있다고 한다.[^report]
이 차이에서 비교의 한계가 드러난다.
같은 평가가 비교 대상 하나에서 이만큼 달라진다면
다른 모델의 낮은 점수도 설정에 따라 크게 달라질 수 있다.
점수 차이의 얼마가 모델의 능력이고
얼마가 인터페이스의 일치인지는 분리되지 않는다.

### 사람 평가는 규모가 작고 신뢰구간이 겹친다

RLA는 61개 과제이고 종단 간 비교에는 참가자 11명, 1,420표가 쓰였다.
평가한 과제와 시스템 쌍 중 표가 하나라도 있는 비율은 31.1%이고,
공유 프롬프트 비교는 576표에 커버리지가 19.6%다.
신뢰구간은 같은 과제나 같은 평가자 사이의 상관을
보정하지 않는다고 부록이 명시한다.[^report]

그래서 2위라는 순위는 조심해서 읽어야 한다.
MOSS-Image의 1698.70(95% 구간 1655.96~1741.43) 안에
3위 Seedream 5.0 Pro의 1661.16이 들어간다.
GPT Image 2와의 차이는 크지만 이것도 표본이 작다.
보고서는 보조로 GPT-6 루브릭 평가를 실었는데,
이 평가에서는 MOSS-Image가 94.93, GPT Image 2가 97.72였고,
GPT-6이 기획자이자 자동 심사자라는 점을 부록이 스스로 지적한다.[^report]

### 열린 가중치 모델이라는 말과 비공개 기획자에 대한 의존이 같이 있다

가장 높은 결과는 JSON 레이아웃을 쓸 때 나오고,
그 JSON을 만드는 것은 GPT-6이다.
저장소가 내놓는 것은 이 역할의 스킬과 스크립트이고
오픈 소스 LLM을 레이아웃 향상기로 미세조정하는 작업은 아직 예고 단계다.
사용자 가이드도 레이아웃 입력이 모델을 쓰기 더 어렵게 만든다고 인정한다.[^guide]

따라서 가중치가 열려 있다는 것과
보고서의 최고 성능을 재현할 수 있다는 것은 다른 말이다.
프롬프트 향상기가 외부 언어 모델에 의존하고
그 한계가 사양 품질을 떨어뜨릴 수 있다고 보고서도 한계 절에 적는다.[^report]

### 홈페이지와 저장소가 같은 것을 다르게 말한다

두 곳을 겹쳐 읽으면 서로 맞지 않는 곳이 몇 군데 나온다.
첫째는 ComfyUI다. 홈페이지는 플러그인을 설치하라고
하고 공식 통합을 진행 중이라고 하지만,
README는 이미 기본 지원이라고 적는다.
둘째는 인용이다.
홈페이지는 프로젝트 저장소를 인용하라며 `@misc` 항목(제목 MOSS-Image,
저자 OpenMOSS Team)을 주고,
README는 기술 보고서를 인용하라며 저자를 MOSI. AI로 적은 arXiv 항목을 준다.
논문을 쓰는 사람은 어느 쪽을 인용할지 정해야 하고,
같은 모델이 두 이름으로 인용되면 인용 집계가 갈라진다.
셋째는 소식이다. 홈페이지는 10월 16일 한 줄이 전부인데
README는 보고서 공개와 세 개 추론 엔진 지원,
학습 도구, 커뮤니티 프로젝트까지 나열한다.
arXiv 목록의 제출일은 10월 16일로 표시되어
README가 말한 10월 19일과 달라 보이는데,
이는 제출일과 공개 시점을 구분한 표현일 수 있다.[^report]
넷째는 라이선스의 대상이다. 홈페이지는 가중치가 Apache-2.0이고
코드는 각자의 라이선스라고 하고,
README는 파이프라인 코드가 Apache-2.0이라고 한다.

이 불일치는 홈페이지가 더 이른 시점에 쓰였고
덜 자주 갱신되는 데서 나온 것으로 보인다.
이는 이 문서의 추정이다.
홈페이지의 몇몇 서술은 정직하다.
레이아웃 도식에 대해 이 그림은 입력 사양을 시각화한
것이지 모델이 생성한 결과가 아니라고 명시한다.
그러나 홈페이지만 읽는 사람은 성능의 근거도, 필요한 GPU 메모리도 알 수 없다.
둘 다 저장소나 보고서에 있다.

### SFT의 알려진 결함은 공식 자료에 나오지 않는다

README는 Base와 SFT 비교를 한 장의 사례 이미지로만 보여 준다.
같은 주에 외부 개발자는 SFT가 하늘, 안개, 벽처럼 매끄러운 영역에
옅은 세로 줄무늬를 자주 그린다고 보고하고
이를 줄이는 LoRA를 여러 개 내놓았다.[^deband]
이 문제가 Base에도 있는지, 어느 설정에서
심해지는지는 공식 자료만으로 알 수 없다.
SFT를 기본으로 쓰려는 사람은 배경이 넓은 이미지로 직접 확인해야 한다.

공식 가이드가 SFT의 약점을 다루지 않았다는 점은 흠이지만,
공개 첫 주에 외부 사용자가 원인을 추적하고
해결책을 내놓았다는 점도 같이 읽어야 한다.
열린 가중치의 장점이 이런 곳에서 드러난다.

### 본문과 표가 맞지 않는 곳이 있다

작은 점이지만 3.3절은 세 단계라고 쓰면서 표 1은 네 단계를 나열한다.
부록 A.2도 세 단계이고 마지막 3단계 체크포인트를 31만 스텝으로 잡는데
표 1의 3단계는 37만 스텝이다.
단계를 세는 방식이 달라서 생긴 차이일 수 있다.
그러나 어느 쪽이 최종 모델의 학습 이력인지 독자가 가려낼 수 없다.[^report]

SFT 모델의 개선은 README의 한 사례 이미지로만 제시되고
내가 읽은 보고서 본문에는 SFT를 따로 평가한 수치가 없다.
Base와 SFT 중 무엇을 쓸지는 직접 비교해야 안다.[^report]

## 인사이트

### 거르지 않고 표시한 데이터는 추론 때 조절 항목이 된다

워터마크와 압축 열화를 캡션에 적어 넣으면
모델은 그 속성과 글자 사이의 연결을 배운다.
추론 때 사용자가 부정 프롬프트에 watermark나 jpeg artifact를 적는
이유가 여기에 있다.
사용자 가이드가 권장하는 부정 프롬프트가 바로 이 속성들이다.[^guide]

이는 조건부 생성의 오래된 아이디어와 같다.
언어 모델에서 제어 코드로 생성 특성을 조절하는 CTRL이 그랬고,
애니메이션 이미지 모델에서 품질 태그를 앞에 붙이는 관행도 같은 원리다.
다만 이차 효과가 있다.
저품질 데이터를 그대로 학습하면
같은 조절 항목이 나쁜 스타일을 끌어내는 데도 쓰이고, 출처 수준에서
적용한 안전 필터 외에는 노출 위험을 모델이 알아서 구분해야 한다.
이 위험이 얼마나 큰지는 보고서가 다루지 않는다.

### 레이아웃 JSON은 이미지 쪽의 페이지 기술 언어다

내용과 배치를 JSON으로 쓰고 생성기가 이를 그림으로 바꾸는 구조는
문서 인쇄에서 페이지 기술 언어와 래스터라이저를 나눈 일과 닮았다.
무엇을 보일지를 서술하는 층과 어떻게 그릴지를 맡은 층을 나누면
각 층을 따로 개선할 수 있다.
보고서가 향상기를 교체할 수 있는 모듈로 설명하는 이유다.

이 구조는 품질의 상한을 기획자에게 옮긴다.
렌더러가 아무리 좋아도 상자의 위치와 글자 내용이 틀리면 그림도 틀리고,
그 틀림이 렌더링 실패가 아니라 사양 실패라는 점에서 진단하기 어렵다.
실무에서는 JSON을 먼저 눈으로 검토하는 단계를 두면 이 둘을 갈라 볼 수 있다.

같은 주에 나온 다른 모델도 비슷한 구조를 택했다. dragonwriter의 설명에 따르면
FLUX 3 Image Klein은 상세한 프롬프트 양식으로 학습되었고
원본 프롬프트를 그 양식으로 바꾸는 LLM 재작성기와 함께 쓰라고 안내한다.
재작성기 없이 쓰면 결과가 나빠진다는 것이다.[^dragonwriter]
생성기는 상세한 입력에 맞춰 학습하고 짧은 요청의 해석은 LLM에 맡기는 분업이
이 시기 이미지 모델의 공통 흐름이라는 해석이 가능하다.
이는 이 글의 해석이다.

### 도입 전에는 자기 프롬프트 30개로 같은 파이프라인을 돌려 봐야 한다

보고서의 수치는 저자의 프롬프트와 설정에서 나온 것이다.
도입을 결정하려면 자기 용도의 프롬프트로 직접 재는 편이 확실하다.
먼저 실제로 쓸 요청 30개쯤을 모으고,
Base와 SFT를 같은 시드와 같은 해상도로 돌린다.
글자 정확도는 LLTB가 쓰는 방식, 곧 OCR로 읽어 낸 단위와
정답 단위가 겹치는 비율로 같은 기준을 적용한다.

레이아웃을 쓸 계획이라면
JSON을 직접 쓰는 경우와 향상기가 쓰는 경우를 나눠서 재야 한다.
그래야 모델의 능력과 기획자의 품질이 섞이지 않는다.
이 세 가지가 보고서가 빠뜨린 독립 검증의 최소한이다.

### 소개 페이지는 스냅샷이고 저장소는 흐르므로 도입 전에 둘을 대조해야 한다

프로젝트 홈페이지는 공개 시점의 모습을 굳혀 두는 경향이 있고
README는 매일 바뀐다.
이 모델의 경우 공개 후 사흘 만에 엔진
지원과 학습 도구와 ComfyUI 통합이 일어났고,
그 사이 홈페이지의 ComfyUI 안내는 낡은 채로 남았다.
따라서 설치 절차를 따를 때는 README의 소식란과 최근 커밋 날짜를 먼저 보고,
충돌하면 저장소 쪽을 따르는 편이 안전하다.

이차 효과는 인용과 평판이다.
같은 모델이 홈페이지의 저장소 인용과 README의 보고서 인용으로 나뉘면
후속 연구에서 이 모델의 사용을 세기 어려워지고,
보고서의 한계가 담긴 평가 수치가 홈페이지를 통해 들어온 독자에게는 가려진다.
홈페이지가 성능을 숫자로 말하지 않는 것은 과장을 피한다는 점에서 장점이지만,
숫자가 있는 곳을 가리키지 않는다는 점에서 단점이기도 하다.
이는 이 문서의 해석이다.
