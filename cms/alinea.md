# Alinea: 콘텐츠를 저장소에 커밋하는 타입 안전 헤드리스 CMS

<https://alineacms.com/>

<https://github.com/alineacms/alinea>

## 소개

Alinea는 스스로를 현대적인 콘텐츠 관리 시스템으로 규정하며 세 줄로 자기를 요약한다.
콘텐츠가 평문 파일에 저장되어 저장소에 커밋되고, 인메모리 데이터베이스를 통해 쉽게 질의할 수 있으며, 완전히 타입이 붙는다는 것이다.
홈페이지의 표제는 “Git 기반 CMS, Next.js를 위해 만들어진”이고 부제는 최소한의 설정을 갖춘 오픈소스 헤드리스 CMS이며 저장소 안에서 완전히 타입이 붙은 콘텐츠를 다룬다는 것이다.

저장소는 2021년 9월 9일에 만들어졌고, 이 문서 작성 시점 기준 스타 850개, 포크 39개, 열린 이슈 38개이며 라이선스는 MIT다.
npm의 `alinea`는 258개 버전이 올라와 있고 최신은 2026년 6월 26일의 1.7.0이며 지난 한 달 다운로드는 53,171회다.
기여자는 12명으로 집계되지만 `benmerckx`가 2,410건이고 그다음 사람이 69건이라 사실상 1인 프로젝트이며, `alinea-cloud[bot]`이 137건으로 두 번째다.
마지막 커밋은 2026년 7월 28일이고 GitHub 릴리스는 세 개만 등록되어 있다.
README에는 Vercel OSS 프로그램 배지가 붙어 있다.

시작 절차는 세 명령이다.
`npm install alinea`로 설치하고 `npx alinea init`으로 설정 파일을 만들고 `npx alinea dev`로 대시보드를 열어 둘러본다.
설정은 `cms.ts`에서 하며 `Config.document`로 문서 타입을 선언하고 그 안에 `Field.text`와 `Field.richText` 같은 필드를 둔다.
문서 타입끼리는 `contains`로 담을 수 있는 관계를 표현한다.

질의는 `Query`로 한다.
`cms.get`에 타입과 `select`를 넘겨 필요한 필드만 골라 오고, `Query.children`으로 하위 문서를 중첩해 가져오며 필터와 정렬과 제한을 적용할 수 있다.
README는 콘텐츠가 정적 사이트 생성 시점과 서버 사이드 질의 시점 모두에 사용 가능하며, 코드와 함께 번들되어 네트워크 오버헤드 없이 질의된다고 밝힌다.
홈페이지도 같은 문장을 다르게 표현하는데, 모든 것이 빌드 시점에 번들되므로 런타임 페칭이나 외부 요청이 필요 없다는 것이다.

홈페이지가 내세우는 세 가지 기둥은 최소 설정과 Git 기반과 완전한 타입이다.
데이터베이스와 마이그레이션을 다루지 않고 콘텐츠를 모델링할 수 있다는 것, 저장소 안에서 버전 관리되는 콘텐츠를 브랜치로 나누어 기능 단위로 시험할 수 있다는 것, TypeScript 사용자를 위해 과도한 복잡성 없이 최적화된 타입 안전 경험을 제공한다는 것이다.
스키마를 코드로 기술하면 생성 단계 없이 즉시 완전히 타입이 붙은 콘텐츠를 얻는다는 문구가 별도 절로 강조되어 있고, 끝없는 폼 클릭을 건너뛰고 코드와 같은 워크플로로 브랜치를 만들고 시험하고 반복한다고 적는다.

그 밖에 소개되는 기능은 계층적 콘텐츠 구성, 초안과 아카이브를 다루는 발행 통제, React Server Components를 완전히 지원하는 실시간 미리보기, 단순한 생성자 함수로 만드는 커스텀 필드다.
Next.js와 Tailwind CSS로 만들어진 Vetra라는 블로그 템플릿도 제공된다.
문서 사이트의 목차에는 워크스페이스와 루트와 미디어와 스키마, Path부터 Image까지 열여섯 종의 필드, 역할과 권한, 국제화, CLI가 나열되어 있다.

배포는 두 갈래다.
README는 Alinea가 단순한 Node.js 프로세스나 서버리스 런타임에서 호스팅할 수 있는 커스텀 백엔드를 지원한다고 밝히고, 문서는 자체 호스팅과 Alinea Cloud를 나누어 안내한다.
Alinea Cloud 문서는 몇 번의 클릭으로 백엔드를 구성하는 클라우드 서비스이며 인증과 다른 사용자 초대와 git 저장소로의 변경 푸시를 처리한다고 여섯 줄로 설명한다.
`alinea.cloud` 사이트는 매끄러운 설정과 인증과 초안과 발행과 팀을 기능으로 든다.
그중 초안 항목의 설명은 alinea.cloud에서 발행되지 않은 초안이 저장되어 저장소를 오염시키는 것을 막는다는 것이다.

README에는 코딩 에이전트를 위한 절이 따로 있다.
`alinea`에 의존하는 프로젝트에서 작업 중이라면 npm 배포본의 `./llms-full.txt`에 핸드북이 들어 있다는 안내다.
문서 사이트에도 “Agents playbook”이라는 참조 문서가 있는데, Alinea 콘텐츠 JSON을 직접 만들거나 갱신해야 하는 코딩 에이전트를 위한 운영 지침서이며 Alinea 코어 동작과 저장소의 콘텐츠 형태에 맞는 결정론적 규칙에 집중한다고 밝힌다.
진실의 원천 우선순위도 명시되어 있다.
모든 문서를 담은 `full-llms.txt`가 일차 원천이고, 모호하거나 문서가 없으면 alinea 코어 소스 코드를 참조하되 alinea를 쓰는 프로젝트는 대개 `node_modules`에 번들된 의존성으로 갖고 있으므로 컴파일된 소스에 직접 접근할 수 있으며, 그것도 불분명하면 GitHub의 소스를 본다.
그리고 대상 프로젝트의 스키마 구현과 구체적인 JSON 픽스처를 참고해 같은 구조를 따르라고 지시하며, 문서 사이트 자체가 Alinea와 Next.js로 만들어져 공개되어 있으므로 유용한 예제가 된다고 안내한다.

## 분석

### 콘텐츠를 저장소에 넣는 결정 하나가 나머지 전부를 파생시킨다

이 프로젝트의 특징으로 나열된 것들이 사실 하나의 결정에서 갈라져 나온다.
콘텐츠가 평문 파일로 저장소에 커밋된다는 것이 그것이다.

거기서 마이그레이션이 사라진다.
데이터베이스가 없으므로 스키마 변경이 테이블 변경이 아니라 파일 형태 변경이 되고, 홈페이지가 데이터베이스와 마이그레이션을 다루지 않고 콘텐츠를 모델링한다고 적은 것이 그 귀결이다.
거기서 브랜치와 기능 시험도 나온다.
콘텐츠가 코드와 같은 저장소에 있으면 콘텐츠 변경도 브랜치로 격리되고 풀 리퀘스트로 검토되며 롤백된다.
거기서 네트워크 오버헤드 없는 질의도 나온다.
빌드 시점에 콘텐츠가 번들에 들어가므로 런타임에 CMS API를 호출할 일이 없다.

이 구조는 [Instatic 노트](instatic.md)에서 본 것과 대비하면 성격이 분명해진다.
그쪽은 SQLite나 Postgres에 콘텐츠를 두고 발행 시점에 정적 HTML로 구워 원자적으로 교체하며, 백업이 데이터베이스 파일과 업로드 폴더를 복사하는 것이다.
Alinea는 그 단계를 하나 더 앞당겨 데이터베이스 자체를 없애고 저장소를 저장소로 쓴다.
곧 두 프로젝트가 같은 목표를 다른 지점에서 달성하며, 어느 쪽이 나은지는 콘텐츠를 편집하는 사람이 개발 워크플로 안에 있는지 밖에 있는지로 갈린다.

### 스키마를 코드로 쓰고 생성 단계를 없앤 것이 실제 차별점이다

타입 안전을 내세우는 CMS는 많지만 대부분은 스키마를 대시보드나 YAML로 정의하고 거기서 TypeScript 타입을 생성한다.
Alinea는 순서를 뒤집어 `cms.ts`의 TypeScript 코드가 스키마 자체이며, `Config.document`와 `Field.text`가 반환하는 값의 타입에서 질의 결과의 타입이 직접 유도된다.
홈페이지가 “생성 단계 없이 즉시 완전히 타입이 붙은 콘텐츠”라고 적은 것이 그것이다.

이 차이가 왜 중요한지는 [React가 풀스택이 되어 간다는 글](../react/full-stack.md)에서 정리한 진단과 겹친다.
그 글이 REST와 SPA의 조합을 불편하게 만든 원인으로 지목한 것이 생성된 타입 인터페이스의 세 가지 결함, 곧 생성 단계가 끼어든다는 것과 출력이 지저분하다는 것과 늘 정확하지는 않다는 것이었다.
Alinea의 설계는 그 셋을 동시에 없앤다.
생성 단계가 없으므로 첫째가 사라지고, 사람이 읽으라고 만든 코드가 곧 스키마이므로 둘째가 사라지며, 타입이 유도된 것이지 복제된 것이 아니므로 셋째가 사라진다.

대가는 스키마가 TypeScript에 묶인다는 점이다.
콘텐츠 구조를 아는 유일한 방법이 TypeScript 소스를 읽는 것이므로, 다른 언어의 소비자나 코드 바깥의 도구는 그 구조를 알 수 없다.
질의 API가 그 언어 안에서만 존재한다는 사실도 같은 제약이며, 헤드리스 CMS를 쓰는 흔한 이유 중 하나인 여러 소비자 지원이 여기서는 어려워진다.
README가 “헤드리스”라는 단어를 쓰지 않고 홈페이지 부제에서만 쓴다는 점이 이 긴장을 시사한다.

### 에이전트 플레이북이 이 아키텍처의 부수 효과를 먼저 알아챘다

문서 사이트의 “Agents playbook”은 지금 흔한 종류의 문서가 아니다.
LLM용 문서 덤프를 두는 프로젝트는 늘었지만, 이 문서는 그것을 넘어 에이전트가 콘텐츠 JSON을 직접 만들거나 갱신할 때 따라야 할 결정론적 규칙을 규정하고 진실의 원천에 우선순위를 매긴다.
`full-llms.txt`가 먼저이고, 모호하면 `node_modules`의 컴파일된 코어 소스를 보고, 그것도 불분명하면 GitHub 소스를 보고, 대상 프로젝트의 스키마 구현과 JSON 픽스처를 참고하라는 순서다.

이 문서가 존재할 수 있는 이유가 아키텍처에 있다.
콘텐츠가 데이터베이스가 아니라 저장소의 JSON 파일이라면, 에이전트가 콘텐츠를 편집하는 일이 코드를 편집하는 일과 같은 종류의 작업이 된다.
파일을 읽고 고치고 커밋하면 되며, API 키도 세션도 대시보드 조작도 필요 없다.
반대로 데이터베이스형 CMS에서는 에이전트가 콘텐츠를 바꾸려면 관리 API를 호출해야 하고, 그러려면 인증과 권한과 스키마 발견이 전부 문제가 된다.

곧 Git 기반이라는 선택이 2021년에는 버전 관리와 브랜치 때문에 매력적이었는데, 2026년에는 다른 이유로 매력적이 되었다.
프로젝트가 그 변화를 먼저 알아차리고 문서로 만들었다는 점이 이 저장소에서 가장 앞서 있는 부분이며, README의 코딩 에이전트 절이 설치 안내 바로 다음에 놓인 배치가 그 우선순위를 보여 준다.

### 다운로드와 스타의 비율이 이 프로젝트의 성격을 말해 준다

숫자를 나란히 놓으면 특이한 조합이 나온다.
GitHub 스타 850개에 npm 월 다운로드 53,171회다.
스타 하나당 월 62회 다운로드인 셈이며, 이 비율은 오늘 살펴본 다른 프로젝트들과 정반대다.

[Instatic](instatic.md)은 스타 7,822개에 crates.io 누적 다운로드 30회였고, [FullSoak](../typescript/fullsoak.md)은 스타 237개에 JSR 의존 패키지 0개였으며, [rari](../react/rari.md)는 스타 1,167개에 npm 월 4,162회였다.
셋 다 문서와 표어가 잘 만들어져 관심을 모았지만 실제 사용은 적었다.
Alinea는 반대로 눈에 띄지 않으면서 쓰이고 있다.

다운로드 수에 CI 실행이 포함된다는 점을 감안해도 이 격차는 크다.
2022년 Show HN이 8점에 댓글 세 개였고 Lobste.rs와 GeekNews에는 스레드가 없으며 HN에 다시 올라온 적도 없는데, 258개 버전이 나왔고 다섯 해째 유지되고 있다.
이런 형태는 대개 소수의 실사용 프로젝트가 계속 쓰면서 만들어진다.
`alinea-cloud[bot]`이 두 번째로 많은 커밋을 남겼다는 사실도 같은 방향을 가리키는데, 상용 서비스가 이 저장소를 실제로 굴리고 있다는 뜻이기 때문이다.

## 비평

### Git 기반의 대가가 어느 문서에도 서술되지 않는다

홈페이지는 Git 기반을 세 기둥 중 하나로 내세우며 저장소 안에서 버전 관리되고 브랜치로 기능 시험을 할 수 있다고 적는다.
이득만 적혀 있고 그 구조가 무엇을 요구하는지는 적혀 있지 않다.

콘텐츠가 저장소에 커밋되고 빌드 시점에 번들된다면, 편집자가 오타 하나를 고치는 일이 커밋 하나와 빌드 하나와 배포 하나를 만든다.
CI가 3분이면 오타 수정이 반영되는 데 3분이 걸리고, 편집자 다섯 명이 오후에 각각 열 번씩 고치면 하루에 오십 번 배포된다.
데이터베이스형 CMS에서는 발행 버튼이 행 하나를 바꾸고 끝나는 일이 여기서는 파이프라인 전체를 돈다.
이 사실이 문서 어디에도 없다.

`alinea.cloud`의 기능 설명 한 줄이 이 문제를 우회적으로 인정한다.
발행되지 않은 초안이 클라우드에 저장되어 저장소를 오염시키는 것을 막는다는 문장이다.
곧 순수한 Git 기반 모델은 초안 단계에서 이미 무리가 있으며, 저장하지 않으면 작업이 날아가고 저장하면 저장소가 커밋으로 뒤덮인다.
해결책은 콘텐츠를 저장소 밖의 유료 서비스에 두는 것이다.

이 우회가 나쁜 설계라는 뜻은 아니다.
초안을 저장소 밖에 두고 발행만 커밋하는 것은 합리적인 절충이다.
문제는 그 절충이 홈페이지의 세 기둥 서술에는 없고 클라우드 제품 페이지의 기능 목록에만 있다는 점이다.
자체 호스팅을 선택한 사용자는 초안을 어디에 둘지 스스로 정해야 하는데, 그 결정이 필요하다는 사실조차 문서가 알려 주지 않는다.

### 홈페이지는 Next.js 전용이라 하고 README는 어디든 배포된다고 한다

홈페이지 표제의 두 번째 줄이 “Built for Next.js”이고, 문서 사이트의 통합 목록에는 Next.js 하나만 있으며 그 아래에 “More coming soon”이 붙어 있다.
제공되는 템플릿 Vetra도 Next.js와 Tailwind로 만들어졌다.

반면 README는 프레임워크를 한 번도 언급하지 않는다.
대신 “Deploy anywhere”라는 절을 두고 단순한 Node.js 프로세스나 서버리스 런타임에 호스팅할 수 있는 커스텀 백엔드를 지원한다고 적으며, 질의 예시도 프레임워크와 무관한 형태다.
저장소의 topics에는 `nextjs`와 함께 `bun`과 `nodejs`가 들어 있다.

두 서술이 모순은 아니지만 사용자에게 다른 기대를 만든다.
README를 읽고 온 사람은 프레임워크 중립 라이브러리를 기대하고, 홈페이지를 읽고 온 사람은 Next.js 통합 제품을 기대한다.
실제로는 후자에 가까울 가능성이 높은데, 실시간 미리보기가 React Server Components를 완전히 지원한다고 명시된 것이나 통합 목록이 하나뿐이라는 것이 그 신호다.
“More coming soon”이 언제부터 그 자리에 있었는지는 알 수 없다.

이 어긋남이 실질적인 이유는 이 CMS의 가장 큰 장점이 프레임워크 통합 지점에 있기 때문이다.
빌드 시점 번들링과 실시간 미리보기와 정적 생성 연계는 전부 프레임워크가 무엇인지 알아야 성립한다.
프레임워크 중립을 표방하면 그 장점을 스스로 포기하는 셈이고, Next.js 전용을 표방하면 대상이 좁아지는 대신 약속이 명확해진다.
현재 문서는 두 표방을 서로 다른 자리에서 하고 있다.

### 수익 모델이 문서 여섯 줄과 별도 도메인에 나뉘어 있다

이 프로젝트에는 상용 서비스가 있다.
`alinea.cloud`가 인증과 GitHub 통합과 초안 저장과 발행과 팀 기능을 제공하며, 저장소에서 두 번째로 많은 커밋을 남긴 것이 `alinea-cloud[bot]`이다.
곧 이 오픈소스 프로젝트는 상용 서비스와 함께 개발되고 있고, 그 사실이 이 프로젝트가 다섯 해째 유지되는 이유일 가능성이 높다.

그런데 그 관계가 문서에서 거의 보이지 않는다.
README는 클라우드를 한 번도 언급하지 않고, 문서 사이트의 Alinea Cloud 페이지는 여섯 줄이며 무엇이 무료이고 무엇이 유료인지 적지 않는다.
`alineacms.com/pricing`과 `alinea.cloud/pricing`은 모두 404를 반환한다.

이 구조가 문제가 되는 이유는 자체 호스팅과 클라우드가 기능적으로 대등하지 않기 때문이다.
앞 절에서 본 초안 저장이 그 예이며, 인증과 팀 관리도 마찬가지로 클라우드 기능으로 나열되어 있다.
자체 호스팅을 고른 사용자가 무엇을 직접 만들어야 하는지가 두 페이지를 오가며 유추해야 하는 정보로 남아 있고, 클라우드를 고른 사용자는 가격을 알기 위해 가입해야 한다.

같은 형태를 오늘 여러 번 봤다.
[Instatic](instatic.md)은 “등급 없음, 오픈코어 꼬리표 없음”을 선언하면서 유일한 수익 인접 장치인 Railway 추천 코드를 링크 안에만 두었고, [Dioxus](../rust/dioxus.md)는 유료 엔터프라이즈 도구로 자립하겠다는 문장에 대응하는 페이지가 “Coming soon”과 대기자 명단이었다.
Alinea는 그중 상용 제품이 실제로 존재하고 돌아가는 유일한 경우인데, 그 사실이 가장 덜 문서화되어 있다.

### 1인 프로젝트인데 릴리스 노트가 258개 중 세 개뿐이다

npm에 258개 버전이 올라와 있고 GitHub 릴리스는 세 개다.
v1.6.3(2026년 2월 19일), v1.6.4(2026년 3월 2일), v1.7.0(2026년 6월 26일)이며 그 이전 255개 버전에는 릴리스 항목이 없다.
저장소 루트에 `changelog.md`와 `changelog.v0.md`가 있으므로 기록이 아예 없는 것은 아니지만, 버전을 올릴지 판단하려는 사용자가 보는 자리는 릴리스 페이지다.

이것이 특히 문제가 되는 조건이 이 프로젝트에 갖춰져 있다.
스키마가 코드이고 콘텐츠가 저장소의 JSON이므로, 라이브러리 버전이 올라가면서 콘텐츠 파일 형태나 설정 API가 바뀌면 사용자가 직접 마이그레이션해야 한다.
데이터베이스가 없다는 것이 마이그레이션이 없다는 뜻은 아니며, 오히려 마이그레이션 도구가 없다는 뜻에 가깝다.
1.x 대의 마이너 버전 사이에서 무엇이 바뀌었는지가 릴리스 노트에 없으면 그 판단을 커밋 로그에서 해야 한다.

같은 맥락에서 버스 팩터도 세어 볼 만하다.
`benmerckx` 2,410건에 다음 사람이 69건이고 열린 이슈가 38개다.
월 53,171회 다운로드가 있는 프로젝트로서는 얇은 구성이며, 앞서 짚은 상용 서비스가 그 얇음을 지탱하는 구조이기도 하다.
그 구조가 안정적인지 아닌지를 판단할 근거가 문서에 없다는 것이 앞 절의 비판과 여기서 만난다.

## 인사이트

### Git 기반 CMS의 진짜 경쟁자는 다른 CMS가 아니라 마크다운 파일이다

이 부류의 제품을 평가할 때 흔히 Contentful이나 Sanity 같은 호스팅형 헤드리스 CMS와 비교하지만, 실제로 대체되는 것은 대개 그것이 아니다.
저장소 안에 마크다운 파일을 두고 프런트매터로 메타데이터를 붙이는 방식이 그 자리에 있었고, 지금도 대부분의 정적 사이트가 그렇게 돌아간다.

그 비교에서 Alinea가 주는 것은 세 가지다.
편집자를 위한 대시보드, 스키마로 강제되는 구조, 그리고 타입이 붙은 질의 API다.
마크다운 파일 방식에서는 편집자가 저장소를 다뤄야 하고, 프런트매터의 필드가 빠지거나 오타가 나도 빌드가 통과하며, 콘텐츠를 읽는 코드가 자기가 무엇을 받을지 모른다.
Alinea는 파일이라는 저장 형태를 유지한 채 그 셋을 더한다.

이 관점에서 보면 이 제품의 성패를 가르는 질문도 달라진다.
“Contentful보다 나은가”가 아니라 “마크다운 파일에 대시보드와 스키마를 더하는 값이 라이브러리 의존과 JSON이라는 덜 읽기 좋은 저장 형태를 감수할 만한가”이다.
마크다운의 가장 큰 자산은 도구 없이 읽고 쓸 수 있다는 것이고, Alinea의 JSON 콘텐츠는 그 자산을 일부 포기한다.
편집자가 개발자이면 마크다운이 이기고, 편집자가 개발자가 아니면 Alinea가 이긴다.

그리고 그 경계가 이 프로젝트의 시장 크기를 정한다.
개발자만 있는 팀에는 필요 없고, 편집자가 많은 조직에는 앞서 본 커밋과 배포 문제가 걸린다.
남는 것은 개발자가 만들고 소수의 비개발자가 관리하는 사이트이며, 그것이 마케팅 사이트와 문서 사이트와 소규모 블로그다.
문서 사이트 자체가 Alinea와 Next.js로 만들어졌다는 사실이 그 자리를 정확히 보여 준다.

### 콘텐츠를 코드 옆에 두면 에이전트가 편집자가 된다

Agents playbook이 존재한다는 사실보다 그 문서가 무엇을 전제하는지가 중요하다.
에이전트가 Alinea 콘텐츠 JSON을 직접 만들거나 갱신한다는 전제이며, 그러려면 콘텐츠가 파일이어야 하고 스키마가 코드여야 하고 예제가 저장소 안에 있어야 한다.
Alinea는 세 조건을 모두 갖췄고, 그래서 이 문서를 쓸 수 있었다.

이 조합이 만드는 것이 새로운 작업 형태다.
“블로그에 이 주제로 글을 추가하고 카테고리를 붙여 줘”라는 지시가 에이전트에게는 파일 생성 작업이 되며, 스키마 파일을 읽어 필드 구조를 알아내고 기존 JSON 픽스처를 보고 형태를 맞추고 커밋한다.
결과는 풀 리퀘스트로 검토되고 CI가 타입 검사를 돌리며, 스키마와 맞지 않으면 빌드가 깨진다.
곧 콘텐츠 편집에 코드 리뷰와 타입 검사와 롤백이 그대로 적용되는데, 이것은 데이터베이스형 CMS에서 에이전트가 관리 API를 호출할 때는 얻을 수 없는 안전망이다.

여기서 나오는 이차 효과가 흥미롭다.
CMS의 대시보드가 사람을 위한 것이라면 저장 형태는 사람의 편의에 맞추면 되지만, 편집 주체에 에이전트가 섞이면 저장 형태가 검증 가능해야 한다.
스키마가 코드로 존재하고 콘텐츠가 그 스키마를 따르는 JSON이라는 구조는 사람을 위해 설계된 것인데, 결과적으로 에이전트 검증에 훨씬 적합한 형태가 되었다.
[Instatic](instatic.md)이 MCP 서버를 열어 외부 에이전트가 자기 엔진을 호출하게 한 것과 비교하면 접근이 반대다.
그쪽은 에이전트를 위한 통로를 새로 만들었고, 이쪽은 이미 있던 통로가 그대로 쓰인다.

다만 이 이점에는 조건이 있다.
에이전트가 콘텐츠를 커밋할 수 있다는 것은 콘텐츠 변경이 코드 변경과 같은 권한 경계에 놓인다는 뜻이기도 하다.
마케터가 오타를 고치는 일과 프로덕션 코드를 고치는 일이 같은 저장소의 쓰기 권한을 요구하며, 역할과 권한 문서가 있다고는 하지만 그것은 대시보드 안의 권한이지 저장소 권한이 아니다.
조직이 커질수록 이 경계가 문제가 되고, 앞서 본 클라우드 서비스가 그 사이에 서는 이유도 여기 있다.

### 스타 수와 다운로드 수는 서로 다른 것을 측정하며, 후자가 더 늦게 움직인다

오늘 살펴본 프로젝트들을 한 줄로 놓으면 지표의 성격이 드러난다.

| 프로젝트   | 스타   | 실사용 지표                  |
| ---------- | ------ | ---------------------------- |
| Instatic   | 7,822  | crates.io 누적 30회          |
| Dioxus     | 38,596 | crates.io 최근 76만 2천 회   |
| Alinea     | 850    | npm 월 53,171회              |
| rari       | 1,167  | npm 월 4,162회               |
| FullSoak   | 237    | JSR 의존 패키지 0            |

스타는 README와 홈페이지와 데모 영상의 품질을 반영하고 공개 첫 주에 대부분 결정된다.
다운로드는 누군가 실제로 프로젝트에 넣고 CI를 돌린 결과이며 몇 달에서 몇 년에 걸쳐 쌓인다.
Instatic이 세 달 만에 7,822개의 스타를 모으고 다운로드가 30회인 것과 Alinea가 다섯 해 동안 850개를 모으고 월 5만 회를 넘긴 것은 같은 축에서 잴 수 없는 두 상태다.

이 대비가 실천적인 이유는 채택 판단의 순서를 바꾸기 때문이다.
새 프로젝트를 만났을 때 스타 수는 그 프로젝트가 잘 소개되었는지를 알려 주고, 다운로드 수는 누군가 그것으로 실제 문제를 풀었는지를 알려 준다.
전자는 하루 만에 만들 수 있고 후자는 만들 수 없다.
같은 이유로 다운로드가 낮은 신생 프로젝트를 배제할 필요는 없지만, 스타가 높다는 이유로 검증을 건너뛰어서는 안 된다.

Alinea는 이 축에서 특이한 위치에 있다.
기술 커뮤니티의 토론이 사실상 없고(2022년 Show HN 8점이 전부이며 Lobste.rs와 GeekNews에는 스레드가 없다) 그래서 외부 검증 기록도 없는데, 사용량은 오늘 본 다른 어떤 CMS보다 많다.
곧 이 프로젝트에 대해 판단할 재료가 화제성이 아니라 지속성밖에 없으며, 그것이 오히려 더 믿을 만한 재료다.

### 빌드 시점 번들링은 콘텐츠 규모에 상한을 만들고 그 상한이 문서화되어 있지 않다

README와 홈페이지가 함께 강조하는 문장이 있다.
콘텐츠가 코드와 함께 번들되어 네트워크 오버헤드 없이 질의되며, 모든 것이 빌드 시점에 번들되므로 런타임 페칭이 필요 없다는 것이다.
이 성질이 이 CMS의 성능 이야기 전부를 만든다.

그런데 같은 성질이 규모 상한도 만든다.
콘텐츠가 번들에 들어간다면 콘텐츠가 커질수록 번들이 커지고 빌드가 느려진다.
인메모리 데이터베이스로 질의한다는 것은 전체 콘텐츠가 메모리에 올라간다는 뜻이며, 서버리스 런타임에서는 그것이 콜드 스타트 시간과 메모리 상한에 직접 닿는다.
글 100편짜리 블로그에서는 아무 문제가 없고 글 10만 편짜리 아카이브에서는 성립하지 않으며, 그 사이 어디에 경계가 있는지가 이 CMS를 고를지 정하는 가장 중요한 숫자다.

문서에 그 숫자가 없다.
성능 절도 벤치마크도 없고, 콘텐츠 항목 수에 따른 빌드 시간이나 메모리 사용량에 대한 안내도 없다.
[Tuono](../rust/tuono.md)와 [rari](../react/rari.md)가 벤치마크 숫자를 표제로 삼아 문제를 만든 것과 정반대의 문제이며, 이쪽은 재야 할 것을 재지 않았다.

여기서 나오는 조언은 이 CMS를 검토하는 팀이 스스로 그 곡선을 재 보라는 것이다.
콘텐츠 항목을 1,000개와 10,000개와 100,000개로 늘려 가며 빌드 시간과 번들 크기와 프로세스 메모리를 재면 자기 프로젝트가 상한 안에 있는지 알 수 있고, 그 측정은 하루면 끝난다.
그리고 그 곡선이 꺾이는 지점이 이 아키텍처가 감당하는 범위이며, 그 범위 밖의 프로젝트에는 데이터베이스형 CMS가 여전히 옳은 선택이다.
Git 기반이 데이터베이스를 없앤 것이 아니라 콘텐츠 규모가 작다는 전제로 데이터베이스를 대신한 것이라는 점을, 문서가 명시하지 않으므로 사용자가 기억해야 한다.
