# Plasmic: 코드베이스에 꽂아 쓰는 React 비주얼 빌더

<https://www.plasmic.app/>

<https://github.com/plasmicapp/plasmic>

## 소개

Plasmic은 스스로를 “당신의 코드베이스를 위한 오픈소스 비주얼 빌더”로 규정하는 React용 시각 편집 도구다.
저장소 설명은 “React를 위한 비주얼 빌더. 앱, 웹사이트, 콘텐츠를 만들고 당신의 코드베이스와 통합하라”이고, README의 부제는 아름다운 앱과 웹사이트를 대단히 빠르게 만들라는 것, 자기 컴포넌트를 끌어다 놓고 코드베이스와 통합하라는 것, 그리고 “로우코드의 천장을 뚫어라”는 것 세 줄로 이어진다.
저장소는 2021년 2월 2일에 만들어졌고, 이 문서 작성 시점 기준 GitHub 스타 6,949개, 포크 705개, 열린 이슈 42개이며 주 언어는 TypeScript다.
최근 커밋은 2026년 8월 8일이고 기여자 목록에는 43명이 올라 있다.

주요 사용 사례로 세 가지를 든다.
콘텐츠 관리는 마케팅 팀이 Next.js 웹사이트 안에서 개발팀의 React 컴포넌트를 끌어다 놓아 디자인 가드레일 안에서 랜딩 페이지를 만들게 하는 것이다.
애플리케이션은 개발자와 기술적 사용자가 내부 도구와 고객 포털과 업무용 소프트웨어를 빠르게 만드는 것이다.
세 번째는 특정 이커머스 플랫폼이나 CMS나 호스팅에 묶이지 않는 웹사이트 빌더 겸 디자인 도구다.

README가 스스로 특별하다고 내세우는 근거는 장르 통합이다.
Webflow와 워드프레스 같은 사이트 빌더, Retool 같은 도구 빌더, Glide 같은 노코드 앱 빌더, Contentful 같은 CMS가 오늘날에는 각각 따로 익혀야 하는 도구지만, 사용자 로그인이 있는 이커머스 상점을 생각해 보면 웹사이트와 애플리케이션의 경계는 흐릿하다는 것이다.
올바른 기반이 있으면 이것들을 통합할 수 있고 Plasmic의 UI는 서로 다른 페르소나와 작업에 맞춰 통제 수준을 조절할 수 있다고 주장한다.
그러나 더 중요한 것은 기존 도구와 달리 코드베이스와 통합된다는 점이며, 이것이 Plasmic을 포함한 모든 로우코드 도구가 갖는 복잡도 천장을 넘기는 데 결정적이라고 밝힌다.
기존의 복잡한 React 컴포넌트를 끌어다 놓을 수 있고, 전통적으로 코드로 작성된 애플리케이션 안에서 새 UI와 컴포넌트를 시각적으로 만들어 코드와 노코드를 매끄럽게 엮을 수 있다는 것이다.

기능 목록은 완전한 디자인 자유와 빠른 현대적 디자인 도구 UX, 기존 React 컴포넌트를 끌어다 놓고 화면을 기존 애플리케이션에 발행하고 Studio 자체를 확장하는 코드베이스 통합, 풍부한 상태 기반 상호작용, 임의의 데이터 소스와 백엔드 통합, 컴포넌트와 변형(variant)과 슬롯과 조합 가능한 상태 관리 같은 강력한 추상, react-aria로 구동되는 맞춤 가능한 헤드리스 디자인 시스템 컴포넌트를 든다.
협업자에게 디자인 가드레일이 걸린 단순화된 편집 경험을 주는 콘텐츠 크리에이터 모드, CMS와 이커머스 플랫폼과 호스팅 제공자를 직접 고르는 열린 통합, 멀티플레이어와 브랜칭과 프로젝트 간 임포트와 다중 워크스페이스 조직, Figma의 독자 벡터 문서 형식을 DOM/CSS로 옮기는 디자인 임포트도 나열한다.
정적 사이트 생성과 자동 이미지 최적화와 레이아웃 이동 감소를 포함한 페이지 성능과 고품질 코드 생성, Vercel과 Netlify를 포함한 어디로든 배포와 호스팅과 내보내기, RBAC와 사용자 범위 권한을 포함한 최종 사용자 인증도 있다.
마지막 항목은 언제든 포크하고 통제할 수 있는 오픈소스 플랫폼이다.

CMS로 통합하는 절차는 다섯 단계로 제시된다.
프레임워크에 맞는 패키지를 설치하고(`npm install @plasmicapp/loader-nextjs`), 선택적으로 앱이나 디자인 시스템의 컴포넌트를 `PLASMIC.registerComponent`로 등록해 노출할 프롭과 함께 시각 편집기에서 끌어 쓸 수 있게 만들고, 앱 어디든 `PlasmicRootProvider`와 `PlasmicComponent`로 자리표시자를 두어 편집기에서 만든 페이지와 컴포넌트를 렌더링한다.
그러면 비개발자도 새 페이지와 섹션과 컴포넌트를 만들어 앱과 웹사이트로 바로 내보낼 수 있고, 발행을 누르면 웹훅이 재빌드를 트리거하거나 증분 정적 재검증이나 Plasmic CDN에서의 동적 페치 같은 더 구체적인 기법으로 변경이 반영된다.

동작 방식은 세 갈래로 설명된다.
코드베이스 통합은 CMS로 쓸 때 핵심이지만 필수는 아니어서 Plasmic 안에서만 완결된 앱과 사이트를 만들 수도 있다.
자기 React 컴포넌트를 코드 컴포넌트로 등록해 Studio의 빌딩 블록으로 쓸 수 있다.
헤드리스 API 외에 코드 생성도 있어 React 코드를 코드베이스로 뽑아낼 수 있으며, README는 Plasmic Studio 자신이 그 방식으로 만들어진 예라고 밝힌다.

버전 관리에 대한 주의가 별도 절로 길게 붙어 있다.
자주 보는 문제가 패키지 버전 불일치와 중복이며, `@plasmicapp` 패키지들은 서로를 정확한 버전으로 의존해 항상 동기화된 상태를 보장한다.
`@plasmicapp/host` 같은 패키지는 `registerComponent`가 전역과 부수 효과를 쓰기 때문에 반드시 중복 제거되어야 하고, 그러지 않으면 잘못된 인스턴스를 쓰게 된다.
npm과 yarn이 버전 불일치와 중복을 쉽게 만들고 문제가 끈적하게 남으므로 `npm list`로 확인하고 때로는 `npm dedupe`나 패키지 재설치와 잠금 파일 초기화가 필요하다고 안내한다.
반면 내장 코드 컴포넌트 패키지인 `@plasmicpkgs`는 `@plasmicapp`을 피어 의존성으로 두되 정확한 버전이 아니라 범위로 지정해 유연성을 준다.

라이선스는 두 갈래다.
`platform/` 바깥의 모든 내용은 MIT이고, `platform/` 자체는 AGPL이다.
기여에는 개인 또는 법인 기여자 라이선스 동의(CLA)가 요구되며, `platform/`에 첫 PR을 낼 때 자동으로 동의를 요청받는다.
지원 창구는 문서와 포럼과 3,000명 이상의 Slack 커뮤니티이고, Plasmic 팀의 지원은 검색 가능한 포럼을 쓰라고 안내한다.

## 분석

### 코드베이스 통합이라는 하나의 주장이 나머지 전부를 지탱한다

이 README에서 반복되는 단어는 천장이다.
“로우코드의 천장을 뚫어라”가 표제 아래 세 번째 줄에 놓이고, 본문에서는 코드베이스 통합이 Plasmic을 포함한 모든 로우코드 도구가 갖는 복잡도 천장을 넘기는 데 결정적이라고 다시 말한다.
자기 제품도 그 천장을 갖는다고 명시한 것이 이 서술의 특징이다.

이 자기 인정이 논증에 필요하다.
천장이 없다고 주장하면 검증 대상이 되고 반례 하나로 무너지지만, 천장이 있되 탈출구가 있다고 주장하면 논점이 탈출구의 품질로 옮겨 간다.
그래서 `registerComponent`가 이 제품의 중심에 놓인다.
임의의 React 컴포넌트를 편집기의 빌딩 블록으로 등록할 수 있다면, 시각 편집기가 표현하지 못하는 것은 코드로 만들어 등록하면 되고 편집기의 표현력 한계가 제품의 한계가 되지 않는다.

HN에서 창업자 `chungwu`가 같은 논리를 더 짧게 표현했다.
자기 React 컴포넌트를 Plasmic 디자인에 쓸 수 있다는 것이 주요 탈출구이며, 그 덕분에 임의의 양의 데이터 페칭이나 비즈니스 로직을 Plasmic 디자인이 소비할 수 있게 된다는 것이다.[^chungwu-escape]
`jason_plasmic`은 기술적 근거를 덧붙였다.
과거의 대부분의 WYSIWYG 편집기에서는 개발자가 어떤 한계에 부딪혀 시스템 밖의 미지의 영역으로 밀려났지만 Plasmic에서는 개발자가 일급 시민이며, 특히 Plasmic 컴포넌트가 사용자의 React 트리 안에서 실행되므로 Plasmic 컴포넌트를 React 컴포넌트 안에 자연스럽게 넣을 수 있고 그 반대도 가능하다는 것이다.[^jason-firstclass]

이 구조를 받아들이면 기능 목록의 성격이 달라 보인다.
Figma 임포트도 react-aria 기반 디자인 시스템도 멀티플레이어도 전부 편집기의 표현력을 넓히는 항목인데, 위 논증이 옳다면 그것들은 편의이지 필수가 아니다.
필수인 것은 등록 규약 하나이며, 그것이 이 제품에서 유일하게 대체 불가능한 부분이다.

### 네 장르를 합치겠다는 선언은 제품 설명이 아니라 시장 정의 시도다

README가 Webflow와 Retool과 Glide와 Contentful을 나란히 놓고 이 넷이 오늘날에는 따로 익혀야 하는 도구라고 적은 것은 경쟁자 목록이 아니다.
그것은 이 넷이 사실 하나의 시장이어야 한다는 주장이며, 그 주장이 참일 때만 Plasmic의 포지션이 성립한다.

이 주장의 논거로 든 것은 경계의 흐릿함이다.
사용자 로그인이 있는 이커머스 상점을 생각해 보라는 예시가 그것인데, 웹사이트와 애플리케이션이 실제로 한 제품 안에서 섞이는 흔한 경우다.
`xyzzyrz`는 HN에서 같은 논리를 반복하면서 고객 포털을 하나 더 예로 들었다.[^xyzzyrz-genres]

문제는 이 논거가 사용자 쪽이 아니라 산출물 쪽에서만 성립한다는 점이다.
결과물이 섞인다는 사실과 그것을 만드는 사람이 같은 도구를 원한다는 사실은 다른 이야기다.
마케터가 랜딩 페이지를 만드는 작업과 개발자가 내부 도구를 만드는 작업은 필요한 통제 수준이 다르고, README도 그것을 알고 있어서 “Plasmic의 UI는 서로 다른 페르소나와 작업에 맞춰 통제 수준을 조절할 수 있다”는 단서를 단다.
곧 통합의 근거는 시장이 하나라는 것이 아니라 한 제품이 여러 얼굴을 가질 수 있다는 것이며, 이것은 훨씬 약한 주장이자 훨씬 어려운 실행이다.

HN 반응이 이 어려움을 그대로 보여준다.
`theogravity`는 페이지를 끝까지 읽으면 Retool 경쟁자로 보인다고 했고[^theogravity], `chaos_emergent`는 Framer와 Retool을 합친 것 같다며 Framer는 UI 빌더는 훌륭하지만 백엔드 연결이 약해 마케팅 사이트에 쓰이고 Retool은 데이터 소스는 많이 붙지만 못생겨서 고객 대면 앱에는 자랑스럽게 쓰기 어렵다고 정리했다.[^chaos]
`wiltonn`은 Builder.io와 무엇이 다르냐고 물었고[^wiltonn], `promiseofbeans`는 MUI Toolpad와 비교했다.[^promiseofbeans]
네 장르를 합치겠다는 선언의 실제 효과는 네 장르 각각의 사용자가 자기 장르의 대표 제품과 비교하는 것이다.

### 라이선스 분할이 이 프로젝트의 실제 경계를 그린다

README의 기능 목록 마지막 항목은 “언제든 포크하고 통제할 수 있는 오픈소스 플랫폼”이다.
그러나 라이선스 절은 두 갈래를 명시한다.
`platform/` 바깥은 MIT이고 `platform/` 자체는 AGPL이다.

이 분할은 우연이 아니라 사업 구조의 직접적 표현이다.
`platform/`은 시각 편집기와 그 백엔드, 곧 Plasmic이 SaaS로 파는 바로 그것이다.
그 바깥은 `@plasmicapp/*` 클라이언트 라이브러리와 `@plasmicpkgs/*` 컴포넌트 패키지와 예제인데, 이것들은 사용자의 코드베이스 안으로 들어가는 코드이므로 MIT여야 한다.
AGPL 라이브러리를 자기 앱에 넣으라고 하면 아무도 넣지 않는다.

여기에 CLA가 겹쳐 그림이 완성된다.
`platform/`에 기여하려면 개인 또는 법인 기여자 라이선스 동의에 서명해야 한다.
CLA는 프로젝트가 기여물의 라이선스를 나중에 바꿀 수 있게 해 주는 장치이고, AGPL 코드에 CLA를 얹는 조합은 상용 라이선스를 따로 파는 오픈코어 구조에서 표준적이다.
즉 “언제든 포크하고 통제할 수 있다”는 문구는 사실이지만, 포크한 것을 SaaS로 팔면 AGPL이 걸리고 상류에 기여하면 저작권이 회사로 흘러간다는 조건이 함께 있다.

### 이 저장소는 개발의 원본이 아니라 동기화본이다

저장소를 들여다보면 공개 저장소가 내부 저장소의 필터링된 사본이라는 흔적이 여러 개 보인다.
`platform/wab/README.md`는 디렉터리 구조를 설명하며 `internal/`이 “공개적으로 동기화되지 않는 Plasmic 내부 전용 코드”라고 명시한다.
최근 커밋 목록에는 GitHub 계정이 연결되지 않은 `upgrade-internal`과 `Publish` 커밋이 섞여 있고, 저장소 루트에는 Gerrit 코드 리뷰 설정인 `.gitreview`가 있다.

이 구조 자체가 잘못된 것은 아니며 규모 있는 상용 오픈소스에서 흔하다.
다만 이것이 “포크하고 통제할 수 있다”는 문구가 실제로 무엇을 뜻하는지를 좁힌다.
포크하면 얻는 것은 공개적으로 동기화된 부분이고, 얻지 못하는 것은 무엇이 빠졌는지에 대한 목록이다.
`internal/`이 어떤 기능을 담고 있는지, 그것 없이 `platform/`이 완전히 동작하는지가 문서화되어 있지 않다.

이 관찰이 다음 절의 첫 비판으로 이어진다.
2023년 오픈소스 전환 당시 가장 많이 나온 질문이 셀프호스팅 가능 여부였고, 그 질문의 실질은 공개된 코드로 이 제품을 혼자 굴릴 수 있느냐였다.

## 비평

### 2023년의 셀프호스팅 약속이 3년째 문서로 남지 않았다

2021년 12월 스레드에서 `alangibson`은 흥미롭다고 하다가 편집기에 완전한 셀프호스팅 선택지가 없어 보인다며 스스로 결론을 취소했다.[^alangibson]
`tmikaeld`는 더 날카로웠다.
사용 가능하고 신뢰할 만한 사이트 편집기를 만들기가 어려운 한 이런 서비스는 계속 구독 전용일 것이고, 오픈소스처럼 보이게 만들지만 실은 겉만 그럴듯한 API 클라이언트일 뿐이며 Builder.io도 마찬가지라는 것이다.[^tmikaeld]
공동 창업자 `yaaang`이 직접 답했다.
오해를 부르거나 짜증나게 할 의도가 정말 아니며 Plasmic의 클라이언트 라이브러리는 오픈소스로 GitHub에 있지만 시각 편집기는 현재 아니라고, 저장소에 설명을 추가하겠다고 했다.[^yaaang]

2년 뒤인 2023년 12월, 플랫폼이 실제로 공개되었고 그 발표가 214점을 받았다.
`octopoc`이 어느 컴포넌트가 오픈소스가 되었고 셀프호스팅이 가능해질 가능성이 있는지, 당장 직접 호스팅할 생각은 없지만 그 선택지가 있는 회사에 돈을 내고 싶다고 물었다.
`xyzzyrz`의 답은 셀프호스팅을 훨씬 쉽게 만들기 위해 할 일이 남았지만 그것이 계획이라는 것이었다.[^xyzzyrz-selfhost]

2026년 8월 현재 저장소를 확인하면 그 계획의 진척을 문서에서 찾을 수 없다.
저장소의 `docs/` 디렉터리에는 `contributing/` 하나만 있고 배포나 셀프호스팅 문서가 없다.
루트의 `docker-compose.yml`은 존재하지만 Postgres 컨테이너와 함께 `Dockerfile.dev.aio`를 빌드해 `yarn dev`를 실행하는 개발 환경 구성이며, 소스 디렉터리를 컨테이너에 마운트하는 방식이다.
CONTRIBUTING.md도 이것을 “스튜디오를 로컬에서 돌리려면 시작하기 가이드를 따르라”는 기여자용 안내로 위치시킨다.

이 차이가 중요한 이유는 오픈소스 전환의 근거 자체가 여기에 걸려 있기 때문이다.
2021년의 비판은 라이선스가 아니라 실행 가능성에 대한 것이었고, 코드가 공개되어도 그것을 굴릴 수 없다면 비판의 핵심은 그대로 남는다.
`platform/` 전체가 AGPL로 공개되었다는 사실은 큰 진전이지만, 프로덕션 배포 경로가 3년째 문서화되지 않았다는 사실과 `internal/`이 공개 동기화에서 제외된다는 사실을 함께 놓으면 “포크하고 통제할 수 있다”는 문구는 여전히 검증되지 않은 상태다.
이것은 약속 위반이라기보다 우선순위의 표현이며, 그 우선순위가 3년간 유지되었다는 것이 정보다.

### 무엇을 하는 물건인지 설명하지 못한다는 지적이 세대를 넘어 반복된다

2023년 스레드의 최상위 댓글은 기능 비판이 아니라 이해 실패였다.
`solardev`는 이것이 뭘 하는지 잘 모르겠고 첫 페이지가 빈 마케팅으로 가득한 느낌인데 어떻게 동작하는지는 여전히 모르겠다고 적었다.[^solardev]
`nkozyra`는 교과서적인 과잉 홍보 사례라며, 마케팅 문구를 다 모으면 노코드/로우코드 앱 빌더인데 그런 건 이미 있으니 무엇이 다른지가 첫 페이지가 팔아야 할 것이라고 했다.[^nkozyra]
`jbverschoor`는 한 줄로 “이게 뭘 하는지 모르겠다”고만 적었다.[^jbverschoor]

주목할 것은 창업자들이 이 지적을 반박하지 않았다는 점이다.
`xyzzyrz`는 홈페이지를 아직 다듬는 중이었고 여기 올라올 줄 몰랐다며 저장소가 더 구체적일 것이라고 답했고[^xyzzyrz-feedback], 다른 답글에서도 GitHub 페이지가 지금 웹사이트보다 아마 더 명확할 것이라고 했다.[^xyzzyrz-clearer]
`octopoc`은 존재하지 않는 새 시장을 만들려는 것 같으며 그럴 때는 아주 명확하게 소통해야 한다며, 자기에게는 README의 통합 방법 절이 도움이 되었다고 짚었다.[^octopoc-market]
`solardev`도 그 링크를 받고 나서야 가치 제안의 요지를 이해했다며 README가 제품이 무엇인지에 대해서는 더 명확하다고 인정했다.[^solardev-thanks]

이 문제가 단순한 카피라이팅 실패가 아닌 이유는 앞 절에서 짚은 장르 통합 주장과 직결되기 때문이다.
네 장르를 합치겠다는 제품은 정의상 기존 범주 이름으로 자기를 설명할 수 없다.
“React용 Webflow”라고 하면 앱 빌더 기능이 지워지고 “오픈소스 Retool”이라고 하면 디자인 자유도가 지워진다.
그 결과 남는 것이 여러 문장으로 이어지는 추상적 서술이고, `nkozyra`가 지적한 과잉 홍보의 인상이 거기서 나온다.

`catapart`가 요구한 것이 이 문제의 가장 간명한 해법이었다.
출력물이 정확히 무엇인지 설명해 주는 것이 없어 아쉽다며, 항상 React 앱인지 바닐라 JS 웹 앱일 수도 있는지 Svelte 컴포넌트를 만들 수 있는지 물었고, 출력 예시 하나만 있어도 자기가 쓸 수 있는 것을 만드는지 판단하는 데 큰 도움이 되겠다고 했다.[^catapart]
`jason_plasmic`이 다른 갈래에서 실제로 생성 코드 파일 세 개의 링크를 제시한 것[^jason-files]이 그 스레드에서 가장 구체적인 답변이었는데, 그것은 README가 아니라 댓글에 있었고 지금도 그렇다.

### 생성된 코드를 직접 고칠 수 없다는 문제가 답해지지 않은 채 넘어갔다

`superfrank`는 이런 WYSIWYG 편집기에 대한 자기 질문이 언제나 출력 코드의 유지보수성이라고 했다.
비교적 정적인 작은 프로젝트에는 문제없지만 더 복잡한 것에서는 도구가 지원하지 않는 일을 하려 할 때 스파게티 코드를 헤쳐야 해서 아낀 시간을 도로 잃는 느낌이었다는 것이다.[^superfrank]

`chungwu`의 답은 Plasmic이 일회성 코드 생성 도구가 아니라는 것이었다.
코드를 생성하고 비즈니스 로직을 더하고 디자인을 반복하고 다시 생성해도 아무것도 날아가지 않게 설계했으며, 사용자는 Plasmic이 생성한 코드를 직접 편집하지 않는다는 설명이다.[^chungwu-codegen]
`nkozyra`가 곧바로 문제를 짚었다.
그 답이 오히려 우려를 키우며, 요컨대 “출력을 건드리지 말라”는 것인데 건드리고 싶거나 건드려야 하면 어떻게 하느냐는 것이다.[^nkozyra-dont-touch]

`superfrank`도 자기 질문이 그것이 아니었다고 다시 설명했다.
과거에 써 본 대부분의 WYSIWYG는 반복해서 쓸 수 있다는 발상 위에 있었고 자기 질문은 어느 시점엔가 편집기로 할 수 없는 일이 반드시 생긴다는 쪽에 초점이 있으며, 그때 VS Code를 열고 코드를 직접 고칠 수 있는지, 고친다면 도구가 그 변경을 반복 사이에 어떻게 유지하는지, 그리고 생성 코드가 얼마나 유지보수 가능한지를 묻는 것이라고 했다.[^superfrank-again]

이 재질문에는 답이 달리지 않았다.
`jason_plasmic`은 로더 API를 쓰면 출력 코드를 볼 일이 아예 없다고 안내했는데[^jason-files], 이것은 질문을 회피하는 답이다.
로더 API는 코드를 보지 않는 선택지이지 코드를 고치는 선택지가 아니기 때문이다.
앞서 분석한 탈출구 논증과 겹쳐 보면 구조가 분명해진다.
Plasmic의 탈출구는 컴포넌트를 등록해 편집기 안으로 가져오는 방향이며, 편집기가 만든 것을 밖으로 꺼내 고치는 방향은 설계상 열려 있지 않다.
천장을 뚫는 방향이 한쪽뿐이라는 사실은 제품 설명 어디에도 명시되어 있지 않다.

### React 종속이 저장소 설명에는 있지만 제품 소개에는 없었다

`bossyTeacher`는 실사용자 후기에서 React/Next 생태계를 잘 아는 사람이 필요하다는 말을 읽고 그렇다면 이것이 React 전용이냐고 물으며, 홈페이지에는 그런 말이 없고 “데이터 소스, React 컴포넌트, 배포 환경, 디자인 시스템 등을 가져오라”는 문구로 모호하게 암시할 뿐이라고 지적했다.[^bossyteacher]
`throwup238`도 그 누락이 눈에 띄었다며 곧바로 “django plasmic”을 검색했고 GitHub 저장소 제목에서야 “React를 위한 비주얼 빌더”라는 사실을 알게 되었다고 적었다.[^throwup238]

Plasmic 쪽 답변은 두 갈래로 갈렸는데 그 자체가 문제를 보여준다.
`chungwu`는 다른 맥락에서 쓰는 것도 가능하지만 Plasmic의 힘을 제대로 끌어내려면 React를 써야 한다고 했고[^chungwu-react], `___victor`는 Angular나 Vue나 순수 HTML로 내보내는 유연성도 제공하지만 주로 React를 겨냥하며 사용자 코드베이스의 커스텀 컴포넌트 등록 같은 기능은 React 전용이라고 했다.[^victor-react]
두 답을 합치면 결론은 하나다.
이 제품의 유일한 대체 불가능한 기능인 컴포넌트 등록이 React에서만 작동하므로, 다른 프레임워크 지원은 실질적으로 정적 내보내기다.

`claytongulick`이 이 지점에서 더 나아간 질문을 던졌다.
왜 이런 도구들이 특정 프레임워크를 승자로 고르는 대신 프레임워크 래퍼가 붙은 웹 컴포넌트로 렌더링하거나 Stencil처럼 어느 프레임워크로든 렌더링할 수 있는 것을 쓰지 않는지 모르겠다는 것이다.[^claytongulick]
이 질문에는 답이 없었고, 답이 없는 이유는 아마 기술 선택이 아니라 시점 선택이기 때문이다.
2021년에 시작한 제품이 React에 건 것은 합리적이었고, 그 결정이 이제 제품의 정체성이 되었다.
다만 홈페이지가 그 사실을 말하지 않고 저장소 제목에만 두는 배치는 잠재 사용자에게 검색 비용을 떠넘긴다.

## 인사이트

### 오픈소스 전환은 소유권 이전이 아니라 신뢰 비용의 지불이었다

2021년과 2023년 스레드를 나란히 놓으면 이 프로젝트가 무엇을 사려고 무엇을 지불했는지가 보인다.
2021년에 `tmikaeld`가 “겉만 그럴듯한 API 클라이언트”라고 부른 것은 정확한 사실 진술이었고 공동 창업자도 인정했다.
2년 뒤 `platform/` 전체가 AGPL로 열렸고, 그 발표 스레드에는 `ryscheng`의 “오픈소스가 되어 정말 기쁘다”[^ryscheng]와 `octopoc`의 축하[^octopoc-market] 같은 반응이 붙었다.

그런데 실질적으로 이전된 통제권은 크지 않다.
CLA가 기여물의 저작권을 회사로 모으고, AGPL이 SaaS 재판매를 막고, `internal/`이 공개 동기화에서 빠지고, 셀프호스팅 문서는 3년째 없다.
포크는 법적으로 가능하지만 실행 경로가 문서화되어 있지 않다.

그렇다면 무엇을 얻었는가.
`octopoc`의 질문이 그 답을 담고 있다.
당장 직접 호스팅할 생각은 없지만 그 선택지가 있는 회사에 돈을 내고 싶다는 것이다.
이것이 상용 오픈소스가 실제로 파는 것이며, 상품은 코드가 아니라 이탈 가능성이라는 보험이다.
`Lincolnmitchell`이 오픈소스 전환이 커뮤니티 규모와 지원 부족 문제를 해결해 주기를 바란다고 적은 것[^lincoln]도 같은 계열의 기대다.

여기서 나오는 일반적 함의는 상용 오픈소스를 평가할 때 라이선스보다 배포 경로를 먼저 보라는 것이다.
라이선스는 선언이고 배포 문서는 실행이며, 둘 사이의 간격이 그 프로젝트가 실제로 무엇을 열었는지를 말해 준다.
Plasmic의 경우 그 간격이 3년이고 아직 줄지 않았다.

### 비주얼 빌더의 진짜 해자는 편집기가 아니라 컴포넌트 등록 규약이다

이 제품에서 대체하기 가장 어려운 것이 무엇인지 물으면 답이 뜻밖이다.
편집기는 아니다.
`promiseofbeans`가 MUI Toolpad와 비교하고 `wiltonn`이 Builder.io와 비교하고 `bogwog`가 GrapesJS와 비교한 것[^bogwog]에서 보듯 시각 편집기는 경쟁자가 많고 차별점을 설명하기도 어렵다.
`xyzzyrz`가 Toolpad와의 차이로 열거한 항목들[^xyzzyrz-diff]은 전부 기능 목록이며 기능은 따라잡힌다.

대체하기 어려운 것은 `registerComponent`가 만들어 내는 상태다.
어떤 팀이 자기 디자인 시스템 컴포넌트 50개에 프롭 메타데이터를 붙여 등록해 두었다면, 그 등록 코드는 Plasmic의 API 형태를 그대로 따른 자산이고 다른 도구로 옮기려면 다시 써야 한다.
게다가 그 위에서 마케팅 팀이 만든 페이지들은 Plasmic의 문서 모델로 저장되어 있다.
편집기를 바꾸는 비용이 아니라 등록층과 콘텐츠를 함께 옮기는 비용이 이탈 비용이다.

이 관점이 앞의 논쟁들을 다시 정렬한다.
`superfrank`가 물은 생성 코드의 유지보수성은 사실 부차적이다.
로더 API를 쓰면 생성 코드를 볼 일이 없다는 답이 성립하는 이유가, 진짜 결합은 코드가 아니라 등록 규약과 콘텐츠 저장소에 있기 때문이다.
같은 이유로 React 종속 논란도 프레임워크 취향의 문제가 아니라 이 해자가 React에서만 파진다는 문제다.

여기서 나오는 예측은 이런 부류의 도구가 서로를 이기는 방식이 편집기 품질이 아니라 등록 규약의 이식성 경쟁이 되리라는 것이다.
누군가 프레임워크 중립적이고 도구 중립적인 컴포넌트 메타데이터 표준을 만들어 낸다면, 그것이 이 시장 전체의 해자를 얕게 만든다.
`claytongulick`이 웹 컴포넌트와 Stencil을 언급한 것[^claytongulick]은 취향 제안처럼 보였지만 사실 그 표준화 가능성을 건드린 것이었고, 아무도 답하지 않은 이유도 그것이 답하기 곤란한 질문이었기 때문일 수 있다.

### 이 저장소는 지금 비주얼 빌더 프로젝트인 동시에 에이전트 코딩 실험장이다

2023년 스레드에서 `octopoc`이 예측을 하나 남겼다.
언젠가 누군가 AI 어시스턴트가 붙은 충분히 좋은 비주얼 앱 빌더를 만들 것이고, 그러면 아무도 모르는 사이에 자원과 기민함이 무한해 보이는 신비한 스타트업이 모든 SaaS 시장을 접수할 것이라는 것이다.[^octopoc-ai]
`ukFxqnLa2sBSBf6`는 SaaS 제품의 진입 장벽이 “얼마나 빨리 조잡한 프런트엔드를 만드느냐”는 아니라고 반박했다.[^ukfx]

3년 뒤 저장소를 보면 그 예측은 절반만 맞았고 방향이 달랐다.
Plasmic이 AI로 시장을 접수한 것이 아니라, Plasmic 자신의 개발 방식이 에이전트 중심으로 재편되고 있다.
저장소 루트에는 `CLAUDE.md`가 있고 `ai/skills/plasmic-designer/` 디렉터리가 있으며, 최근 커밋 목록에는 `charliecreates[bot]`이 루트 테스트 설정 지침 문서를 갱신한 커밋이 사람 커밋들 사이에 섞여 있다.
같은 주의 커밋들이 `updateDataQuery` 코파일럿 도구 구현, 데이터 질의 코파일럿 삭제, 코파일럿의 `VarRef`와 `PageHref` 읽기 지원처럼 전부 에디터 안의 AI 기능을 다룬다.

이 배치가 흥미로운 이유는 두 방향이 같은 저장소에서 만나기 때문이다.
한쪽에서는 에이전트가 이 코드베이스를 고치고 있고, 다른 쪽에서는 이 코드베이스가 사용자를 위한 에이전트를 만들고 있다.
`ai/skills/plasmic-designer`라는 이름은 이 도구의 편집 능력을 에이전트에게 기술로 노출하려는 시도로 읽히며, 그것이 실현되면 비주얼 빌더의 사용자 인터페이스는 캔버스가 아니라 대화가 된다.

그렇게 되면 앞 절에서 짚은 해자 논의가 뒤집힌다.
등록 규약이 해자인 이유는 사람이 캔버스에서 컴포넌트를 골라 쓰기 때문인데, 에이전트가 코드를 직접 쓸 수 있다면 컴포넌트를 미리 등록해 둘 이유가 줄어든다.
`ukFxqnLa2sBSBf6`의 반박이 여기서 다시 유효해진다.
프런트엔드를 빠르게 만드는 것이 장벽이 아니었다면, 그것을 더 빠르게 만드는 도구도 장벽을 넘지 못한다.
이 저장소가 두 방향을 동시에 추구하는 것은 그 위험을 알고 있다는 신호로 읽힌다.

### 두 사용자층을 한 도구로 묶는 구조가 조직 문화 쪽에서 먼저 마찰을 만든다

이 제품의 핵심 시나리오는 개발자가 통합하고 비개발자가 발행하는 것이다.
README의 다섯 단계가 정확히 그 순서이고, `xyzzyrz`도 개발팀이 통합하면 마케팅과 콘텐츠와 디자인 팀이 랜딩 페이지를 만든다고 요약했다.[^xyzzyrz-cms]
기술적으로 이 분업은 잘 정의되어 있다.

그런데 실제 사용자들이 보고한 어려움은 기술이 아니었다.
`Lincolnmitchell`은 현재 워크플로가 코드 컴포넌트로 웹앱 디자인을 완성해 Vercel로 프로토타입을 배포하는 것이고 나중에는 Plasmic에서 직접 프로덕션으로 발행하는 것을 목표로 한다며, 이 작은 단계들이 주로 문화적 문제를 다루고 있다고 적었다.
디자인 팀이 프런트엔드를 발행한다는 발상이 보고 체계와 프로세스와 실직 우려 같은 문화적 문제를 많이 건드리며 변화는 무섭다는 것이다.[^lincoln-culture]
`ireadmevs`는 프런트엔드 엔지니어로서 자기 선호는 웹사이트 자체보다 웹사이트를 만드는 도구 쪽에서 일하는 것이라고 답했다.[^ireadmevs]

이 대화가 드러내는 것은 이 도구가 파는 것이 시간 절약이 아니라 권한 재배치라는 사실이다.
마케터가 개발자에게 티켓을 넣지 않고 페이지를 내보낼 수 있게 된다는 것은, 그때까지 개발자가 쥐고 있던 게이트가 사라진다는 뜻이다.
디자인 가드레일과 콘텐츠 크리에이터 모드와 RBAC 같은 기능이 존재하는 이유가 여기 있으며, 그것들은 편의 기능이 아니라 그 게이트를 사람에서 설정으로 옮기는 장치다.

같은 긴장이 가격 논쟁에서도 나왔다.
`ilrwbwrkhv`는 오픈소스가 되는 것으로 한몫 챙기려는 스타트업이며 오픈소스 프로젝트가 상단 바에 눈에 띄는 가격 페이지를 두는 것은 오픈소스 정신에 어긋나니 그렇게 마케팅하는 것을 부끄러워해야 한다고 적었다.[^ilrwbwrkhv]
Plasmic의 `_fmota_`는 오픈소스도 상업적 측면을 가질 수 있고 핵심은 투명성과 협업과 자유로운 배포이며, 지속적인 개발과 전문 지원과 운영 비용을 감당하기 위한 상업 전략이라고 답했다.[^fmota]
두 입장 모두 익숙하지만, 이 제품에서는 그 논쟁이 더 무겁다.
게이트를 대신하는 도구가 유료 SaaS라면 조직은 사람이 쥐고 있던 통제를 회사 밖 공급자에게 옮기는 셈이고, 그 이전을 되돌리는 비용이 앞서 본 이탈 비용이다.
셀프호스팅 문서의 부재가 조직 정치의 문제가 되는 지점이 정확히 여기다.
