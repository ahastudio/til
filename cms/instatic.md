## 소개

Instatic은 Bun 위에서 동작하는 셀프호스팅형 비주얼 CMS다.
“당신의 사이트를 소유하라. 만드는 과정을 사랑하라(Own your site. Love building it)”는 슬로건을 내세우며, 비주얼 에디터와 콘텐츠 엔진과 퍼블리셔를 하나의 서버에 통합해 깔끔한 시맨틱 HTML을 생성한다.
개발팀은 자신들을 “수천 명이 생계를 위해 웹사이트를 만드는 데 쓰는 도구인 Motion.page와 Core Framework를 만든 팀이며, 대부분 WordPress 생태계 안에서 활동해 왔다”고 소개하며, 기존 디자인 토큰 기술을 별도 플러그인이 아니라 핵심 시스템으로 통합했다고 밝힌다.
저장소는 2026년 4월 30일에 만들어졌고, 이 문서 갱신 시점 기준 GitHub 스타 7,822개, 포크 700개, 열린 이슈 87개이며 최신 릴리스는 2026년 7월 28일의 v0.0.14다.

README가 세우는 대비는 스택 조립이다.
현대적인 웹사이트를 만들려면 보통 헤드리스 CMS, 프레임워크, 호스트, 폼 서비스, 애널리틱스 벤더, 이미지 CDN을 조립해야 하고 각각이 자기 청구서와 대시보드와 새벽 두 시의 장애를 갖는데, Instatic은 그 반대에 건다는 것이다.
Bun 서버 하나가 캔버스 에디터와 콘텐츠 엔진과 미디어와 인증과 폼과 플러그인과 퍼블리셔를 전부 담고, SQLite나 Postgres를 뒤에 두고 원하는 곳에서 돌린다.
홈페이지는 이것을 환경 변수 하나가 SQLite냐 Postgres냐를 정한다고 표현하고, 백업은 데이터베이스와 업로드 폴더를 복사하는 것이라고 요약한다.

기술 스택은 서버와 툴링 모두 Bun 위에서 돌아가고 TypeScript가 전체 코드베이스의 95.5%를 차지한다.
서버는 `Bun.serve`에 손으로 쓴 라우터를 얹었고, 관리자 인터페이스는 React Compiler를 켠 React 19에 Vite, Zustand와 Mutative, CodeMirror, dnd-kit으로 만들어졌다.
데이터베이스는 `DATABASE_URL`로 선택되는 하나의 `DbClient` 인터페이스 뒤에 SQLite와 Postgres가 있고, 타입이 없는 모든 경계에서 TypeBox로 검증하며 스키마를 진실의 원천으로 삼는다.
AI는 벤더 SDK 없이 원시 HTTP/SSE 위에 올린 공급자 중립 드라이버를 쓴다.

기능은 다섯 갈래로 소개된다.
디자인 쪽에서는 캔버스가 미리보기 창을 붙인 폼이 아니라 진짜 캔버스이며, 여러 브레이크포인트 프레임을 나란히 놓고 함께 편집해 데스크톱을 바꾸면 모바일 프레임이 같은 화면에서 반응한다.
실물을 만지고 싶으면 라이브 모드로 전환해 전체 크기 페이지를 제자리에서 편집한다.
Core Framework가 내장되어 브랜드 색 하나에서 조율된 명암 계열 전체를 자동 생성하고, 뷰포트에 따라 스케일되는 수학적 타입 램프와 간격 체계를 제공하며, 유틸리티 클래스 생성기가 잠긴 생성 클래스를 하나의 작은 `framework.css`로 내보낸다.
디자인 시스템 전체가 데이터로 존재하므로 토큰 하나를 바꾸면 그것을 쓰는 모든 페이지가 갱신된다.

빌드 쪽에서는 컨테이너, 텍스트, 이미지, 버튼, 비디오, 목록, 링크, SVG, 폼이 모듈로 제공된다.
Visual Component는 타입이 지정된 매개변수와 이름 붙은 슬롯을 갖는 재사용 조각이며, 매개변수는 문자열, 숫자, 불리언, 색, 이미지, URL, 리치 텍스트, 열거형, 또는 콘텐츠 슬롯 전체가 될 수 있고, 자기 자신을 참조하게 되는 컴포넌트는 만들어지기 전에 차단된다.
템플릿은 사이트 전체 레이아웃과 포스트 타입별 레이아웃과 직접 디자인하는 404 페이지를 담당하고 콘텐츠는 아웃렛으로 흘러든다.
루프는 포스트, 페이지, 미디어, 또는 플러그인이 소스로 노출한 무엇이든 컬렉션 위에서 레이아웃을 반복하며, 변형을 두어 번갈아 쓸 수 있다.
폼은 시맨틱 필드로 만들면 제출이 자기 데이터 테이블로 들어오고, Instatic이 배치된 필드를 읽어 대응하는 테이블을 만들어 준다.

AI 에이전트는 원하는 것을 설명하면 스크린샷이나 코드 덩어리가 아니라 실제 편집 가능한 노드로 캔버스에 만들어 낸다고 설명한다.
구조는 시맨틱 HTML로 쓰고 스타일은 CSS로 쓰되 사용자가 마크업을 붙여 넣을 때와 같은 임포트 파이프라인을 지난다.
도구는 두 범위로 나뉘어 페이지를 만드는 Site 범위가 35개, 항목을 편집하는 Content 범위가 15개이며, 홈페이지는 에이전트가 렌더링된 페이지를 되읽어 자기 작업을 확인한다고 덧붙인다.
모델은 직접 가져오는 방식이라 Claude, OpenAI, OpenRouter, 로컬 Ollama 중에서 고르며 “당신의 키, 당신의 모델, 당신의 청구서”라고 표현한다.
Super Import는 HTML을 붙여 넣으면 편집 가능한 노드로 바꾸고, HTML과 CSS와 이미지와 폰트를 담은 정적 사이트 전체를 떨어뜨리면 페이지와 스타일 규칙과 디자인 토큰과 미디어로 바꾸는데, 모든 충돌을 쓰기 전에 보여 주고 임포트 전체가 하나의 실행 취소로 되돌아간다.

관리 쪽의 핵심은 단일 콘텐츠 모델이다.
페이지, 포스트, 컴포넌트, 커스텀 컬렉션, 직접 만든 구조화 테이블이 전부 `data_tables`와 `data_rows`라는 같은 저장소에 있고, 구석에 숨은 특별 취급 “pages” 테이블이 없다.
`/admin/data`의 데이터 워크스페이스에서 커스텀 포스트 타입과 커스텀 데이터 테이블을 자기 필드와 함께 만들고 스프레드시트 형태의 격자에서 검색, 정렬, 필터, 일괄 발행, 일괄 내보내기를 한다.
커스텀 포스트 타입은 초안과 예약과 발행이라는 편집 워크플로와 발행본에 대한 버전 이력을 갖고, 일반 데이터 테이블은 폼 제출이나 상품 목록이나 가벼운 CRM이나 후기 목록을 담을 수 있는 단순한 격자이며, 만든 모든 테이블이 루프가 렌더링할 수 있는 콘텐츠 소스가 된다.
미디어 워크스페이스는 폴더와 스마트 폴더, 일괄 작업, 어떤 파일이 실제로 어디에 쓰이는지 알려 주는 사용 추적, 교체 워크플로, 로컬 디스크를 넘어설 때를 위한 착탈식 저장소 어댑터를 제공한다.
접근 제어는 38개의 권한(capability)으로 역할을 구성하고, 토큰 기반 세션과 비밀키를 저장 시 암호화하는 TOTP 2단계 인증, 반복 실패 후 백오프가 걸리는 계정 잠금, 사용자 삭제나 전체 기기 로그아웃 같은 위험한 작업 전의 단계 상승 확인을 갖췄다.
관리자 전체를 훑는 퍼지 커맨드 팔레트(⌘K)가 있고, 발행하지 않은 편집은 방문자에게 절대 새지 않는다.

분석 쪽은 12열 격자에 타일 위젯을 드래그하고 크기를 조절해 배치하는 대시보드이고 배치는 사용자별로 저장되며 플러그인도 같은 격자에 자기 위젯을 실을 수 있다.
로그인과 콘텐츠 변경과 역할 편집과 플러그인 수명 주기 같은 모든 의미 있는 관리자 행동이 한 행씩 기록되는 추가 전용 감사 로그가 있고, 폼 제출은 자기 테이블에 있어 질의하고 내보내고 그 위에 무언가를 만들 수 있다.
README는 오늘의 분석 영역이 의도적으로 운영 중심이라며 서드파티 방문자 추적 대신 대시보드 상태와 감사 이력과 소유한 폼 데이터를 제공한다고 밝히고, 홈페이지는 이를 “솔직한 공백”이라 부르며 방문자 분석이 아직 없고 자체적이고 프라이버시를 존중하는 방식이 다음이라고 적는다.

확장 쪽은 백엔드 플러그인 코드가 어디서 도는가로 차별점을 세운다.
Instatic 플러그인은 매니페스트가 담긴 zip 패키지이고, 서버 진입점은 QuickJS를 WebAssembly로 컴파일한 인터프리터를 호스팅하는 플러그인별 워커에서 실행된다.
이 샌드박스에는 Node도 Bun도 파일시스템도 환경 변수도 없고, 매니페스트가 호스트를 나열하고 설치 시 소유자가 승인해야만 네트워크에 닿을 수 있으며 그것도 한 번에 한 호스트다.
플러그인이 죽으면 호스트가 그 워커 하나만 재시작하고 페이지는 계속 서빙된다.
에디터 확장과 app 종류의 관리자 페이지는 다르게 취급되어 관리자 창에서 실행되므로 설치 전에 명시적인 `editor.code` 권한을 요구한다.
SDK로 플러그인은 HTTP 라우트와 자체 관리자 페이지, 저장소와 예약 백그라운드 작업, 루프 데이터 소스, 캔버스 모듈, 미디어 저장소 어댑터와 프런트엔드 자산, 설치와 활성화 전반의 수명 주기 훅을 더할 수 있다.

발행된 페이지는 대부분 디스크에 놓인 파일이며, 속도가 조정하는 설정이 아니라 발행 방식에서 떨어져 나온다고 설명한다.
정적 페이지는 발행 시 디스크로 바로 구워지고 원자적으로 교체되어 방문자는 렌더링이 아니라 파일을 받고, 실제로 바뀌는 라우트는 버전이 붙은 인메모리 캐시를 거쳐 발행이 버전을 올리면 옛 항목이 지연 미스가 되며, 진짜로 방문자마다 다른 소수의 부분만 자동으로 탐지되어 약 1.1kB의 런타임이 지연 로딩한다.
공개 페이지에는 React도 에디터 런타임도 프레임워크도 남지 않는다.

홈페이지는 호스팅형 빌더가 줄 수 없는 것으로 네 가지를 따로 조명하는데, 그중 두 가지가 README에 없는 내용이다.
하나는 MCP 서버로, Instatic 자신이 MCP 서버이므로 Claude Code나 Cursor나 Codex나 원격 에이전트를 `/_instatic/mcp`라는 하나의 Streamable HTTP 라우트에 붙이면 내장 패널이 돌리는 것과 같은 도구를 얻는다.
두 번째 구현이 아니라 내장 에이전트가 이미 쓰는 엔진에 붙는 또 하나의 호출자이며, 커넥터마다 베어러 토큰 하나가 발급되고 해시로만 저장되며 권한으로 범위가 걸리고 취소하는 순간 죽는다.
다른 하나는 이미지 처리로, 모든 업로드가 백그라운드 워커에서 WebP 변형 사다리로 크기 조정되고 BlurHash 자리표시자를 받으며, 발행 시 퍼블리셔가 컨테이너 상한과 열 비율과 격자 트랙 같은 실제 레이아웃을 읽어 그에 맞는 `srcset`과 `sizes`를 페이지에 써 넣는다.
CSS 배경으로 쓰이는 이미지도 `image-set()`으로 같은 사다리를 받는다.

배포는 Railway 원클릭이 가장 빠른 경로로 제시된다.
템플릿을 고르고 버튼을 누르고 2분쯤 기다리면 비밀 키 생성과 스토리지 볼륨 연결과 헬스 체크 설정이 알아서 되고 터미널을 열 일이 없다.
제공자 표는 단일 사이트에는 Railway와 SQLite를, 여러 저자와 관리형 백업에는 Railway와 Postgres를, Render 서비스를 선호하는 팀에는 Render를, 자체 서버와 Caddy TLS와 맞춤 백업 정책에는 Docker/VPS를 권한다.
갱신은 최신 이미지로 재배포하는 것이고 데이터베이스와 업로드는 연결된 스토리지에 남는다.
빠른 시작은 Bun만 있으면 되며 `git clone` 후 `bun install`, `bun run dev`로 5173 포트를, `bun run start`로 3001 포트의 `/admin`을 띄운다.
아키텍처 규칙은 `src/__tests__/architecture/`에 실제 테스트로 존재해, 출력을 깨끗하게 유지하는 구조가 조용히 썩지 못하게 한다고 밝힌다.

라이선스는 MIT이며 “등급 없음, 오픈코어 꼬리표 없음, 영업팀 문의 없음”이라고 명시한다.
로드맵은 여섯 항목으로 공개되어 있고 각각 진행 상태가 붙어 있다.
편집기에서 다루고 퍼블리셔가 내보내는 SEO/AEO 메타데이터와 구조화 데이터가 “Building”, 이미 패치 기반인 실행 취소 이력을 바탕에 둔 실시간 협업이 “Building”, 관리자를 떠나지 않고 플러그인을 쓰고 돌리고 배포하는 플러그인 IDE가 “Next up”, 방문자 브라우저에 아무것도 싣지 않고 자기 서버 요청에서 계산하는 자체 애널리틱스가 “Next up”, 더 많은 모듈과 SDK 표면이 “Ongoing”, 더 날카로운 에이전트가 “Ongoing”이다.
날짜는 약속하지 않으며 변경 이력이 정직한 기록이라고 적는다.

## 분석

### 플러그인 보안 서술이 고발에서 명세로 바뀌었다

이 프로젝트의 샌드박스 아키텍처는 처음부터 WordPress 경험의 직접적 번역으로 읽혔다.
개발팀이 스스로 밝혔듯 이들은 수년간 WordPress 생태계 안에서 Motion.page와 Core Framework를 만들어 온 사람들이고, WordPress는 취약한 서드파티 플러그인을 통한 보안 사고가 반복적으로 보고돼 온 플랫폼이다.
즉 Instatic은 추상적인 “더 나은 CMS를 만들자”에서 출발한 것이 아니라 자신들이 그 생태계 안에서 목격한 구체적인 실패에 대한 반작용으로 설계됐다.

주목할 만한 것은 그 서술 방식이 바뀌었다는 점이다.
이전 판 README는 이 아키텍처를 설명하며 플러그인이 사이트를 다운시키고 데이터베이스를 낯선 사람에게 이메일로 보냈다는 흔한 이야기가 여기서는 일어나지 않는다는 문구를 썼다.
현재 README에 그 문장은 없다.
대신 무엇이 없는지를 열거하는 명세로 대체되었다.
Node도 Bun도 파일시스템도 환경 변수도 없고, 네트워크는 매니페스트가 호스트를 나열하고 소유자가 설치 시 승인해야만 열리며 한 번에 한 호스트라는 서술이다.

이 교체가 의미하는 바가 작지 않다.
“이런 일은 일어나지 않는다”는 결과에 대한 약속이고 검증할 수 없으며 반례 하나로 무너진다.
“파일시스템 접근이 없고 네트워크는 허용 목록으로만 열린다”는 능력에 대한 진술이고 코드로 확인할 수 있으며 틀렸다면 어디가 틀렸는지 지목할 수 있다.
0.0.x 단계의 프로젝트가 홍보 문구를 검증 가능한 방향으로 좁히는 것은 흔한 일이 아니다.
같은 변화가 플러그인 충돌 시 호스트가 그 워커 하나만 재시작한다는 서술에서도 보이는데, 이것은 보안 주장이 아니라 가용성 주장이고 훨씬 구체적이다.

### 모델을 직접 가져오게 하는 설계가 이제 프로토콜 층위까지 확장되었다

AI 에이전트가 Claude, OpenAI, OpenRouter, 로컬 Ollama 중에서 사용자가 고르게 한 것은 많은 AI 통합 제품이 특정 공급자와 배타적으로 제휴하는 것과 대비된다.
사용자는 비용과 성능과 프라이버시 요구에 맞춰 모델을 고를 수 있고, Instatic 자신은 특정 LLM 공급자의 가격 정책이나 API 변경에 종속되지 않는다.
“당신의 키, 당신의 모델, 당신의 청구서”라는 문구와 벤더 SDK 없이 원시 HTTP/SSE로 드라이버를 쓴다는 기술 선택이 같은 방향을 가리킨다.

이 방향이 이제 한 층 더 올라갔다.
Instatic 자신이 MCP 서버가 되어, 내장 패널이 돌리는 것과 같은 도구를 외부 에이전트에게 그대로 연다.
Claude Code든 Cursor든 Codex든 원격 에이전트든 `/_instatic/mcp` 하나에 붙으면 되고, 두 번째 구현이 아니라 같은 엔진의 또 다른 호출자라는 점이 명시되어 있다.

이 결정이 왜 일관된지는 이 제품의 슬로건에서 나온다.
사이트를 소유한다는 것이 데이터를 소유한다는 뜻에 그치면 셀프호스팅으로 충분하다.
편집 도구까지 소유한다는 뜻이 되려면 CMS가 자기 UI를 유일한 입구로 삼지 않아야 하고, MCP 서버화가 정확히 그 조건을 만든다.
내장 에디터가 마음에 들지 않으면 다른 도구로 같은 일을 하라는 제안이며, 이것은 비주얼 빌더 제품이 보통 하지 않는 종류의 양보다.
동시에 이 양보에는 계산이 있다.
에이전트 코딩 도구를 이미 쓰는 개발자층이 CMS의 새 진입 경로가 되고, 그 경로에서 Instatic은 UI 경쟁이 아니라 엔진 경쟁을 하게 된다.

### 단일 콘텐츠 모델이 루프 소스라는 하나의 개념으로 결실을 맺는다

전통적인 CMS는 대개 고정된 페이지와 시간순으로 쌓이는 포스트를 서로 다른 데이터 모델로 취급해 왔고, 재사용 가능한 컴포넌트는 위젯이나 숏코드나 블록 패턴 같은 또 다른 시스템으로 관리되는 경우가 많았다.
Instatic이 이 셋을 `data_tables`와 `data_rows`라는 같은 저장소에 통합하고 구석에 숨은 특별 취급 pages 테이블이 없다고 분명히 한 것은, 콘텐츠의 형태와 재사용 가능성을 서로 독립적인 축으로 다루겠다는 설계 결정이다.

이 통합이 실제로 무엇을 낳는지는 루프 설명에서 드러난다.
만든 모든 테이블이 루프가 렌더링할 수 있는 소스가 된다는 문장, 그리고 Team 테이블을 한 번 정의해 소개 페이지에 루프로 얹으면 끝이라는 예시가 그것이다.
데이터 모델이 하나이므로 “어떤 종류의 콘텐츠를 반복할 수 있는가”라는 질문이 아예 사라진다.
플러그인이 노출한 데이터 소스도 같은 자리에 들어오고, 폼 제출도 같은 격자에서 다뤄진다.

이 설계의 값어치는 기능 개수가 아니라 없어진 개념의 개수로 재야 한다.
커스텀 필드 플러그인, 커스텀 포스트 타입 등록 API, 폼 제출 저장소, 반복 위젯이 각각 별개의 하위 시스템으로 존재하는 CMS와 비교하면 배워야 할 것이 훨씬 적다.
다만 이 통합은 구현 복잡도가 높고, 0.0.x라는 이른 단계에서 이런 근본 결정을 먼저 굳혔다는 사실은 처음부터 프로덕션급 복잡도를 감당할 자신이 있었거나 나중에 갈아엎기 어려운 결정을 서둘러 확정하려 했다는 두 해석을 모두 허용한다.

### 반응형 이미지 처리가 이 제품의 논지를 가장 잘 보여 주는 기능이다

이미지 파이프라인은 목록의 아홉 번째 항목으로 놓여 있지만, 사실 이 제품의 주장 전체를 압축한다.
업로드 한 번에 WebP 사다리와 BlurHash 자리표시자가 만들어지는 것까지는 흔한 기능이다.
특이한 것은 발행 시점에 퍼블리셔가 실제 레이아웃, 곧 컨테이너 상한과 열 비율과 격자 트랙과 브레이크포인트를 읽어 `sizes` 속성을 계산한다는 부분이다.

`sizes`는 사람이 손으로 쓸 때 거의 언제나 틀리는 속성이다.
브라우저에게 이 이미지가 화면에서 얼마나 넓게 표시될지 미리 알려 주는 값인데, 그것을 정확히 쓰려면 CSS 레이아웃 계산을 머릿속으로 해야 하기 때문이다.
홈페이지가 이것을 “손으로 하면 모두가 틀리는 부분”이라고 표현한 것은 과장이 아니다.

이 기능이 논지를 압축하는 이유는 에디터와 퍼블리셔가 한 프로그램 안에 있어야만 가능하기 때문이다.
헤드리스 CMS는 레이아웃을 모르므로 `sizes`를 계산할 수 없고, 프레임워크는 콘텐츠를 모르므로 어떤 이미지가 올지 모른다.
디자인 정보와 콘텐츠와 발행이 같은 프로세스 안에 있을 때만 나오는 출력이며, 그래서 이것은 스택을 조립하지 않는다는 이 제품의 선택이 실제로 무엇을 주는지에 대한 가장 구체적인 답이다.

## 비평

### “등급 없음”이라는 선언과 유일한 수익 경로가 URL 안에 숨어 있다

README는 라이선스를 소개하며 “등급 없음, 오픈코어 꼬리표 없음, 영업팀 문의 없음”이라고 선언하고, 홈페이지도 “MIT 라이선스, 하나의 등급, 앉아 있어야 할 영업 통화 없음”이라고 되풀이한다.
유료 엔터프라이즈 기능을 잠가 두는 오픈코어 모델을 채택하지 않겠다는 강한 약속처럼 들린다.
그러나 이 프로젝트가 어떻게 지속적으로 개발될 것인지, 곧 자금 조달 방식이나 개발팀의 생계 수단에 대한 산문 설명은 여전히 한 줄도 없다.

그런데 문서를 소스 수준에서 보면 하나의 경로가 보인다.
README의 Railway 배포 링크 두 개에는 모두 `referralCode=Zm9bVJ`가 붙어 있다.
추천 코드는 흔하고 규모도 대개 작으므로 그 자체가 문제는 아니다.
문제는 이 프로젝트가 수익 모델의 부재를 여러 번 명시적으로 자랑하면서, 실제로 존재하는 유일한 수익 인접 장치는 산문에 밝히지 않고 링크 안에만 둔다는 비대칭이다.

이 비대칭이 실질적인 이유는 배포 표에서 Railway가 “권장”으로 표시되어 있기 때문이다.
권장의 근거로 제시된 것은 속도와 편의이고 그것은 사실일 것이다.
다만 권장하는 쪽이 그 권장으로부터 수익을 얻는다면 독자는 그 사실을 알고 판단할 수 있어야 하며, 한 문장이면 충분하다.
Motion.page와 Core Framework라는 상용 도구를 만들어 온 팀이라는 점을 함께 놓고 보면, Instatic 자체가 그 두 제품의 유통 경로로 기능하는 구조인지 아니면 별개의 계획이 있는지도 여전히 답이 없다.
Core Framework가 플러그인이 아니라 핵심 시스템으로 들어가 있다는 사실은 좋은 통합인 동시에 기존 상용 제품의 사용자 기반을 새 제품으로 옮기는 경로이기도 하다.

### 에이전트가 권한 체계 안에서 어디에 서는지가 여전히 불분명하다

AI 에이전트에 대한 정보는 이전보다 훨씬 구체적이다.
도구가 두 범위로 나뉘어 Site가 35개, Content가 15개라는 것, 결과가 실제 편집 가능한 노드로 들어온다는 것, 사용자가 마크업을 붙여 넣을 때와 같은 임포트 파이프라인을 지난다는 것, 렌더링된 페이지를 되읽어 자기 작업을 확인한다는 것까지 밝혀져 있다.
MCP 쪽은 한 걸음 더 나아가 커넥터마다 베어러 토큰 하나이고 해시로만 저장되며 권한으로 범위가 걸리고 취소 즉시 죽는다고 명시한다.

그런데 바로 그 대비가 빈칸을 드러낸다.
외부 MCP 커넥터에는 권한 범위가 걸린다고 명시되어 있는데, 관리자 화면 안의 내장 에이전트가 38개 권한 체계 안에서 어떤 위치인지는 어디에도 없다.
에이전트를 실행한 사용자의 권한을 그대로 물려받는지, 에이전트 자체에 별도 권한이 있는지, 편집자 권한만 가진 사람이 에이전트를 통해 디자인 토큰을 바꿀 수 있는지가 답해지지 않는다.
토큰 하나를 바꾸면 그것을 쓰는 모든 페이지가 갱신되는 시스템에서 이것은 사소한 질문이 아니다.

되돌리기에 대한 서술도 절반만 있다.
Super Import는 모든 충돌을 쓰기 전에 보여 주고 임포트 전체가 하나의 실행 취소로 되돌아간다고 명시되어 있으며, 이것은 좋은 설계이고 이전 판 문서가 지적한 되돌리기 문제에 대한 부분적인 답이다.
그러나 같은 보장이 에이전트 편집에도 적용되는지는 나오지 않는다.
에이전트가 14개 노드를 추가했다는 홈페이지의 예시 화면에는 그 14개를 한 번에 취소하는 장치가 보이지 않고, 사람이 승인하거나 거부하는 검토 단계도 서술되어 있지 않다.
에이전트가 만든 결과가 초안 상태에 머무는지 아니면 곧바로 편집 중인 문서에 반영되는지도 마찬가지다.

### 자체 아키텍처 테스트는 여전히 외부 검증을 대체하지 않는다

README는 `src/__tests__/architecture/`의 테스트로 아키텍처 규칙을 강제해 구조가 조용히 썩지 못하게 한다고 밝힌다.
이것은 좋은 관행이고 실제로 드문 관행이다.
다만 이는 프로젝트가 스스로 정의한 규칙을 스스로 지키고 있는지 확인하는 내부 일관성 검사이지, 그 규칙 자체가 올바른 설계인지를 외부에서 검증한 것은 아니다.

보안 주장은 특히 그렇다.
QuickJS-WASM 샌드박스가 실제로 파일시스템과 환경 변수 접근을 차단하는지, 네트워크 허용 목록이 우회 불가능한지, 알려진 샌드박스 탈출 취약점 부류에 대응했는지는 자체 테스트로 확인되지 않는다.
앞서 짚었듯 현재 README의 표현은 결과 약속에서 능력 명세로 좁혀졌고 그만큼 신중해졌지만, 명세가 코드와 일치한다는 것을 확인해 줄 독립적인 감사나 침투 테스트 결과는 여전히 공개되어 있지 않다.

관리자 창에서 도는 코드에 대해서는 더 조심스럽게 읽을 필요가 있다.
에디터 확장과 app 종류의 관리자 페이지는 샌드박스 밖, 곧 관리자 창 안에서 돌고 명시적인 `editor.code` 권한을 요구한다.
설치 전에 사용자가 그 권한을 본다는 점은 정직하지만, 그것을 승인한 순간 그 플러그인은 샌드박스가 제공하는 보호를 전부 우회한다.
플러그인 생태계가 커질수록 실제로 유용한 확장 다수가 이 권한을 요구하게 될 가능성이 크고, 그때 이 CMS의 실효 보안은 샌드박스의 강도가 아니라 사용자가 권한 요청을 얼마나 신중히 읽는가로 결정된다.
이것은 WordPress 플러그인이 겪은 문제의 구조와 그리 멀지 않으며, 문서는 이 경로를 예외로 언급할 뿐 그 함의를 다루지 않는다.

### 커뮤니티 검증이 거의 없는 상태에서 성장 지표만 앞선다

이 프로젝트의 외형 지표는 빠르게 자랐다.
2026년 4월 30일에 만들어진 저장소가 세 달 남짓 만에 스타 7,822개와 포크 700개를 모았고, README에는 Trendshift 배지가 붙어 있으며 홈페이지는 “오늘의 저장소 1위”를 내세운다.
반면 기술 커뮤니티의 실사용 검증은 사실상 없다.
Hacker News에는 2026년 6월 30일에 한 번 제출되어 2점에 댓글 0개를 받았고, Lobste.rs에는 스레드가 없으며 GeekNews에도 없다.

이 대비는 이 부류 프로젝트를 읽을 때 주의가 필요한 지점이다.
스타 수는 README와 홈페이지와 데모 영상의 품질을 반영하고, 이 프로젝트의 그것들은 실제로 잘 만들어져 있다.
그러나 스타 수는 누가 이것을 실제 사이트에 올려 몇 달을 굴려 봤는지를 말해 주지 않는다.
열린 이슈 87개가 유일한 실사용 신호인데, 그 수만으로는 성숙의 증거인지 초기 결함의 증거인지 구분되지 않는다.

이 상태에서 판단 근거가 될 만한 것은 프로젝트 자신이 밝힌 미확정 지점들이다.
0.0.x이고 1.0 전에 API와 워크플로가 바뀔 수 있다는 것, 방문자 분석이 아예 없다는 것, 실시간 협업이 아직 구현 중이라는 것을 스스로 적어 두었다.
이런 자기 개시가 있는 프로젝트는 없는 프로젝트보다 낫지만, 자기 개시는 자기 평가이지 제3자 검증이 아니다.
현재로서 이 CMS에 대해 확실히 말할 수 있는 것은 설계 문서가 훌륭하다는 것까지이며, 그 설계가 운영에서 어떻게 버티는지에 대한 공개된 증거는 아직 없다.

## 인사이트

### WordPress 생태계 출신 팀의 이탈은 플러그인 보안 부채가 새 CMS 세대를 만들어 내는 동력임을 보여준다

Instatic 팀의 배경, 곧 WordPress 생태계 안에서 수년간 상용 도구를 만들어 오다가 독립적인 셀프호스팅 CMS를 새로 만들기로 한 결정은 개별 사례로 보이지만 더 큰 패턴의 일부일 수 있다.
WordPress는 방대한 플러그인 생태계 덕분에 성공했지만, 바로 그 개방성이 오랫동안 보안 사고의 주된 원인으로 지목되어 왔다.
검증되지 않은 서드파티 코드가 전체 사이트에 대한 무제한 접근 권한을 갖는 구조가 문제의 핵심이다.

Instatic의 설계는 그 구조를 정면으로 뒤집는다.
플러그인은 기본적으로 아무것도 할 수 없고, 필요한 것을 매니페스트에 적어 소유자에게 승인받아야 하며, 네트워크는 호스트 단위 허용 목록으로만 열린다.
이것은 브라우저 확장과 모바일 앱이 20년에 걸쳐 도달한 권한 모델을 CMS 플러그인에 적용한 것이고, 웹 서버 애플리케이션 생태계에서는 아직 표준이 아니다.

여기서 나오는 예측은 두 갈래다.
하나는 이런 흐름이 이어지면 WordPress 자신도 플러그인 샌드박싱 압박을 받으리라는 것인데, PHP의 실행 모델과 20년 치 하위 호환을 생각하면 실현 가능성이 낮다.
다른 하나가 더 현실적이다.
샌드박스 모델은 플러그인이 할 수 있는 일을 좁히므로, 기존 생태계에서 인기 있는 종류의 확장 상당수가 그 안에서 구현되지 않는다.
WordPress 플러그인 중 다수가 코어 함수를 후킹하고 전역 상태를 만지고 다른 플러그인과 상호작용하는데, 그런 일은 정의상 샌드박스에서 불가능하다.
그러므로 이 설계의 진짜 시험은 보안이 아니라 생태계 규모이며, 안전한 플러그인 100개가 위험한 플러그인 60,000개를 이길 수 있는지가 관건이다.

### AI 편집 에이전트의 경쟁축은 의도 해석에서 이미 프로토콜 개방으로 옮겨 갔다

기존 비주얼 빌더의 경쟁력은 얼마나 다양한 블록과 템플릿을 제공하고 그것들을 얼마나 매끄럽게 조합하게 하는가였다.
자연어로 의도를 설명하고 해석을 에이전트에게 맡기는 방향으로 상호작용의 축이 옮겨 간 것은 이제 새로운 관찰이 아니며, 이 제품에서도 이미 전제다.
더 흥미로운 것은 그 다음 축이다.

Instatic이 자기 자신을 MCP 서버로 열고 내장 패널이 쓰는 것과 같은 도구를 외부에 노출한 결정은, 에이전트 UI의 품질로 경쟁하기를 포기했다는 뜻이기도 하다.
사용자가 이미 Claude Code나 Cursor를 열어 두고 일한다면 CMS 안의 채팅창은 하나 더 열어야 할 창이며, 그 싸움에서 CMS는 이기기 어렵다.
그렇다면 남는 전략은 자기 창을 강화하는 것이 아니라 남의 창에서 호출되는 대상이 되는 것이다.

이 전환이 제품 카테고리 전체에 미칠 영향이 있다.
CMS가 MCP 서버가 되면 그 제품의 실질은 UI가 아니라 도구 표면, 곧 어떤 연산을 얼마나 안전하고 되돌릴 수 있게 노출하는가가 된다.
Instatic이 35개와 15개라는 도구 수를 공개하고 커넥터별 토큰과 권한 범위와 취소를 명시한 것은 그 표면을 제품 사양으로 취급하기 시작했다는 신호다.
동시에 새로운 위험도 생긴다.
외부 에이전트가 사이트 구조를 편집할 수 있다는 것은 프롬프트 인젝션의 표적 표면이 CMS 콘텐츠 자체로 확장된다는 뜻이고, 에이전트가 렌더링된 페이지를 되읽어 자기 작업을 확인한다는 설계는 바로 그 되읽기 경로가 주입 통로가 될 수 있다는 뜻이다.
이 문제는 문서 어디에도 언급되어 있지 않다.

### 발행 결과물을 인질로 잡지 않겠다는 약속이 이 제품의 유일한 장기 보증이다

홈페이지의 첫 문장은 “아무도 당신의 웹사이트를 인질로 잡지 못한다”이고, 발행 방식 설명은 “그 파일들이 곧 사이트다. 읽을 수 있고 어느 호스트로든 복사할 수 있으며 Instatic을 그만 쓰는 날 가져갈 수 있다”로 끝난다.
이 진술이 이 제품에 대한 판단에서 다른 어떤 기능보다 무겁다.

이유는 앞 절에서 짚은 검증 부재와 맞물린다.
0.0.x 프로젝트를 실제 사이트에 쓸 때의 진짜 위험은 버그가 아니라 프로젝트가 사라지거나 방향을 바꾸는 것이다.
MIT 라이선스는 코드가 계속 존재하게 해 주지만 아무도 그 코드를 유지보수하지 않을 때는 큰 위안이 못 된다.
반면 출력물이 프레임워크 런타임도 에디터 잔재도 빌더 속성도 없는 시맨틱 HTML과 CSS라면, 프로젝트가 멈춰도 사이트는 멈추지 않는다.

이 구조가 만드는 위험 프로파일이 흥미롭다.
Instatic을 채택할 때 잃을 수 있는 최대치는 편집 도구이지 사이트가 아니다.
데이터는 SQLite 파일이나 Postgres 덤프에 있고, 출력은 정적 파일이며, 둘 다 다른 도구로 옮길 수 있다.
비교하자면 호스팅형 빌더에서 이탈할 때 잃는 것은 사이트 전체이고, 헤드리스 CMS에서 이탈할 때 잃는 것은 콘텐츠 API에 맞춰 쓴 프런트엔드 코드다.

그러므로 이 프로젝트에 대한 합리적인 판단 기준은 “이 CMS가 오래 갈 것인가”가 아니라 “오래 가지 않았을 때 얼마를 잃는가”다.
그 관점에서 보면 검증 부재라는 위험이 상당 부분 상쇄된다.
동시에 이 논리는 하나의 조건에 전적으로 달려 있다.
발행 출력이 실제로 깨끗하고 이식 가능해야 하며, 커스텀 데이터 테이블과 컴포넌트와 폼 제출 같은 구조화 데이터가 표준적인 형식으로 나올 수 있어야 한다.
정적 페이지의 이식성은 문서에서 강조되지만 데이터의 이식성, 곧 내보내기 형식과 스키마 문서화는 일괄 내보내기 기능이 있다는 언급을 넘어서지 않는다.
이 제품의 가장 강한 약속이 가장 덜 문서화된 지점 위에 서 있다.

### 통합 데이터 모델과 세분화된 권한의 조합은 팀 규모 운영을 처음부터 상정한 설계다

페이지와 포스트와 컴포넌트를 하나의 저장소로 통합하면서 동시에 38개의 세분화된 권한을 제공하는 조합은, 이 CMS가 개인 블로거나 소규모 사이트만 겨냥한 것이 아님을 시사한다.
통합된 데이터 모델만 있고 세분화된 권한이 없다면 여러 사람이 같은 저장소를 건드릴 때 통제가 어려워지고, 반대로 권한만 있고 데이터가 파편화되어 있다면 그 권한 체계를 데이터 타입마다 따로 관리해야 하는 부담이 생긴다.

이 판단을 뒷받침하는 신호가 이번 판에서 여럿 늘었다.
발행본에 대한 버전 이력, 반복 실패 후 백오프가 걸리는 계정 잠금, 위험한 작업 전의 단계 상승 확인, 추가 전용 감사 로그, 사용자별로 저장되는 대시보드 배치, 그리고 로드맵에서 “Building” 상태인 실시간 협업이 전부 여러 명이 같은 사이트를 만지는 상황을 전제한다.
감사 로그를 추가 전용으로 만든 것은 특히 그런데, 혼자 쓰는 CMS에서 자기 행동 기록을 스스로 고칠 수 없게 만들 이유가 없기 때문이다.

그런데 배포 안내는 반대 방향을 가리킨다.
권장 구성은 단일 사이트용 Railway와 SQLite이고, 문서는 대부분의 사이트에 SQLite가 옳은 기본값이며 저자가 여럿이거나 관리형 백업을 원할 때 Postgres를 고르라고 안내한다.
빠른 시작 경로 전체가 혼자 2분 만에 띄우는 시나리오로 최적화되어 있다.

이 어긋남은 결함이라기보다 이 부류 제품의 전형적인 성장 전략으로 보인다.
개인이 쉽게 시작할 수 있게 하되 팀으로 커졌을 때 갈아타지 않아도 되게 만드는 것이며, 그래서 아키텍처는 조직 규모를 상정하고 온보딩은 개인을 상정한다.
Ghost나 Strapi 같은 이전 세대가 가벼운 도구로 시작해 점진적으로 조직용 기능을 붙인 것과 달리, 이 프로젝트는 조직용 구조를 먼저 세우고 개인용 진입로를 낸 순서다.
그 순서의 대가가 0.0.x 단계에서 이미 감당해야 하는 복잡도이며, 열린 이슈 87개와 1.0 전 API 변경 예고가 그 비용의 현재 표시값이다.
