# tsrs는 AI가 하룻밤에 옮긴 TypeScript 컴파일러지만 가치는 테스트와 측정의 규율에 있다

원문: [Introducing tsrs: a Port of TypeScript to Rust | Cloudflare Blog](https://blog.cloudflare.com/typescript-rust-port/)

HN 토론: <https://news.ycombinator.com/item?id=50165953> (345점, 172개 댓글)

GN 토론: <https://news.hada.io/topic?id=35724>

## 요약

Cloudflare는 2026년 10월 20일 VoidZero와 함께 Owner.com의
Max Schwenk가 만든 tsrs를 이어받아 키운다고 발표했다.
tsrs는 TypeScript 컴파일러의 Rust 포트이고
Oxc JavaScript 컴파일러 도구 체계의 일부로 키워지며,
TypeScript 팀과 긴밀히 협력한다고 한다.
글은 TypeScript를 포크하는 것이 아니라고 분명히 한다.
언어 설계의 통제권은 TypeScript 팀에 남아야 하고,
포트는 그 결정을 따라가지 않으면 호환성이 깨진다는 이유다.

초기 벤치마크는 같은 수의 타입 검사 워커에서
tsrs가 TypeScript 7.0보다 최대 8배 빠르고 메모리를 약 70% 적게 쓴다고 한다.
다음 버전 TypeScript 7.1 베타는 7.0보다 최대 2.5배 빠르고,
그 최적화 일부는 tsrs에서 역으로 가져온 것이라고 밝힌다.
기본 설정의 tsrs는 기계 사양에 맞춰 메모리를 더 쓰고
더 빠르게 도는 적응형 구성이다.
npm의 `tsrs` 패키지로 실험판을 써 볼 수 있다.

Rust를 고른 이유로 글은 속도보다 WebAssembly를 든다.
Go를 Wasm으로 컴파일하면 가비지 컬렉터를 같이 실어야 하지만,
Rust의 메모리 모델은 Wasm 게스트와 호스트의 메모리 상호작용이 단순하다는 것이다.
Cloudflare Workers에서 개발 도구 전체를 샌드박스 안에서
돌리고 브라우저나 임베디드 기기에서도 돌리는 것이 목표다.
유지 방식은 Next.js를 따라가는 vinext와 같다고 한다.
에이전트가 매일 업스트림 변경을 검토하고 밤마다 호환성 표를 다시 만든다.
Theo Browne의 tsc-rs와 합치는 작업도 진행 중이다.

## 분석

### 발표의 이야기는 Wasm이고 속도는 부수 효과로 배치된다

글은 왜 지금인가를 두 가지로 설명한다.
TypeScript를 다른 언어로 옮기려던 시도는 많았지만
성공한 것은 TypeScript 팀의 Go 포트 하나뿐이었는데,
이제 최전선 AI 모델이 대규모 포트를 며칠 만에 거의 독자적으로 해낸다는 것이다.
이어서 Rust를 고른 이유를 속도가 아니라 Wasm에서의 메모리 효율로 정리한다.
HN의 sheepscreek은 이 글의 숨은 맥락이 빠른 Rust 컴파일러를 만들려던 것이 아니라
Wasm 전용 샌드박스에서
돌릴 TypeScript 컴파일러가 필요했던 것이라고 읽었다.[^sheepscreek]
nsm은 Cloudflare처럼 수백만 개를 돌리며
비용을 아끼는 쪽의 필요가 일반 웹 개발자의 수정 주기와 전혀 다르니
당장 바꿀 계획을 세울 필요는 없다고 일깨웠다.[^nsm]

### 하루 만에 만든 것의 설계가 오히려 규율에 있다

글의 근거는 Owner의 Max Schwenk가 10월 19일에 쓴 글이다.
Owner의 백엔드 모놀리스 Olympus는 TypeScript 파일
약 3만 7천 개를 하나의 프로그램으로 검사한다.
TypeScript 7.0으로 단일 스레드 검사에 메모리 19GiB와 80초가 들었고,
옆에서 tsgolint를 돌리면 검사기가 하나 더 떠서 메모리가 두 배가 되었다.[^owner]
그는 9월 30일 Claude Opus 5.5에게 TypeScript의
Go 구현을 Rust로 충실히 옮겨 달라고 요청했고
자신은 코드를 한 줄도 쓰지 않았다고 쓴다.[^owner]

포트의 규칙은 세 가지였다.
알고리즘, 함수 구조, 평가 순서,
진단을 특정 업스트림 커밋에 고정해 그대로 옮기고,
Go 패키지 하나당 Rust 크레이트 하나를 두어 서명을 먼저 정하고
구현은 비워 병렬로 일하게 하고,
TypeScript 팀이 Go 포트 때 남긴 15,197개 적합성 사례를 명세로 삼았다.[^owner]
에이전트가 하위 에이전트 20여 개로 밤새 일했고
아침에 첫 종단 실행에서 오류 기준선의 78%가 바이트 단위로 일치했다.
유형 출력기를 더하자 13,462개 중 네 개를 뺀 99.97%가 일치했다.[^owner]
이 순서는 구현을 먼저 믿지 않고 기준선과 어긋남을 숫자로 재는 데서 출발했다.

### 최적화는 착륙 기준을 둔 경쟁이었다

저장소에는 에이전트가 끝없이 최적화하지 않도록 기준이 있다.
변경은 단일 스레드 명령 수를 1% 이상, 실행 시간을 2% 이상,
최대 메모리를 5% 이상 줄이고 출력이 바이트 단위로 같을 때만 반영된다.[^owner]
그가 든 효과는 포인터 압축이 최대 메모리를 14~15% 줄이고 명령은 6.5% 늘리는 것,
지연 멤버 해석, 검사가 끝난 말단 파일의 해제,
작업 훔치기로 4개 검사기에서 13.8%, 8개에서 17%의 시간 단축 등이다.[^owner]
일곱 번의 별도 A/B 실험이라 퍼센트를 곱할 수 없다고 직접 밝힌다.[^owner]

## 비평

### 가장 큰 숫자는 가장 좋은 경우다

발표 글은 최대 8배 빠르고 메모리를 약 70% 적게 쓴다고 하는데,
이는 이어지는 문장과 Owner의 글을 합치면 조건을 알 수 있다.
저장소의 공개 프로젝트 17개 벤치마크에서는
최신 야간 빌드 대비 메모리 약 3분의 1, 속도 2.5~5배이다.[^owner]
Olympus에서는 검사기 4개에서 tsrs 0.14.0이 8.75초, 6.1GiB이고
TypeScript 7.0.2는 61.4초, 36.0GiB로 7.0배 빠르고 5.9배 적다.
검사기 8개에서는 9.8배 빠르고 6.6배 적다.[^owner]
이 숫자를 직접 나눠 보면 맞다.
다만 이 비교는 7.0이고, 7.1 야간 빌드 대비는 4개 검사기에서
5.0배 빠르고 4.7배 적게 줄어든다.[^owner]
기준 버전이 새로워질수록 간격이 줄어들고,
글은 7.1 베타가 7.0보다 최대 2.5배 빠르다고 스스로 인정한다.

그리고 글이 밝히듯 기본 설정의 tsrs는 같은 워커 수 비교와 다르다.
이 문서는 Olympus 외의 큰 저장소에서 재현해 보지 않았고,
다른 수치는 저장소의 벤치마크 보고서에 의존한다.
HN의 jscheel은 tsgo, ts-rust, tsrs,
bun으로 자기 모노레포를 시험해 보니
tsrs는 스레드를 늘릴 때 메모리 효율이 매우 좋고
bun보다는 덜하지만 증분 검사가 있다는 점이 다르다고 했다.[^jscheel]
같은 방향이지만 조건이 달라 서로 비교할 수 없다.

### 충실한 포트라는 말과 의도적 차이가 같이 있다

글은 이를 충실한 포트라 하고 99.97% 일치를 말하지만
Owner 자신이 이 적합성 집합이 컴파일러가 옳다는 증명이 아니라고 쓴다.[^owner]
저장소 README는 실제 프로젝트에서 정확성 버그를 아직 못 찾았다고
하면서도 알려진 순서 문제가 있다고 적는다.
Go 컴파일러는 병렬 파싱과 해석과 검사의
순서에 따라 진단과 추적이 달라질 수 있는데,
tsrs는 기본적으로 검사기 이력을 정규화한다는 것이다.
`--init`과 `--showConfig`는 지원하지 않는다.[^readme]
Owner는 순서에 따라 진단이 달라지는 컴파일러는 의견을 가진 난수 발생기라며
이를 일부러 결정적으로 만들었다.[^owner]
이는 개선일 수 있지만 충실한 복제가 아니라 의도적인 차이이고,
일치율 수치가 이 차이를 어떻게 다루는지는 글이 설명하지 않는다.

### 개방성의 약속과 닫힌 기여 경로가 부딪힌다

글은 tsrs를 건강한 오픈소스 프로젝트로 운영하겠다고 한다.
그런데 README는 이슈는 받지만
풀 리퀘스트는 검토할 여력이 없어 닫혀 있다고 한다.[^readme]
유지 방식도 에이전트가 업스트림을 검토하고 호환성 표를 다시 만드는 것이라,
기여자가 들어올 자리가 지금은 좁다.
HN의 egonschiele는 손으로 조심스럽게 쓴 포트에서
전부 AI가 만든 포트로 옮겨 간다는 점이 달갑지 않다고 했고,
자신은 에이전트의 결과를 검토하는데
며칠 만에 거의 노력 없이 같은 일을 하는 사람이 있다면
지금의 일하는 방식이 사라지는 신호일지 모른다고 했다.[^egonschiele]
이 반응은 코드 소유와 유지에 대한 질문으로 이어진다.
samuelstros는 그렇다면 왜 tsgo에 더 투자하느냐고 물었고,[^samuelstros]
magicalist는 TypeScript 팀이 무엇을 쓰고 읽고 추론하고
싶은지가 마이그레이션 용이성과는 별개라고 답했다.[^magicalist]

## 인사이트

### 테스트 집합이 구현보다 옮기기 쉬운 자산이다

tsrs가 하룻밤에 거의 맞는 컴파일러를 낸 것은 TypeScript
팀이 Go 포트 때 남긴 15,197개 적합성 사례와 기준선 덕이다.
Owner는 이를 팀이 남긴 선물이라고 불렀다.[^owner]
구현은 AI가 며칠 만에 다시 쓸 수 있게 되었지만,
입력과 정답의 쌍인 테스트 집합은 그렇게 만들 수 없다.
이 때문에 언어와 도구 프로젝트의 해자가 구현에서
명세와 테스트와 거버넌스로 옮겨 갈 가능성이 있다.
이는 이 문서의 해석이다.

그 반대편에서 이 사건은 테스트 집합을 공개하는 일의 이차 효과를 보여 준다.
공개된 집합이 클수록 다른 구현이 빨리 나오고, 원본 구현은 속도 경쟁에 놓인다.
TypeScript 팀의 Dan Rosenwasser는 HN에서 자기들도 Rust 바이브 포트를 해 봤고
속도의 상당 부분이 언어 선택만으로 설명되지 않는다고 보며,
TS 7.1이 빨라지는 일부는 tsrs에서
발견된 최적화에서 온다고 했다.[^DanRosenwasser]
포트가 원본의 성능 감사 역할을 하고, 원본이 그 결과를 흡수하는 관계다.

### 가치는 속도보다 에이전트가 병렬로 돌 수 있는 메모리에 있다

Owner의 글에서 가장 구체적인 이득은 속도가 아니라 메모리다.
검사 하나가 19GiB를 쓰면 로컬에서 에이전트 여럿을 동시에 돌릴 수 없어서,
그들은 클라우드 샌드박스와 에이전트에게 순번을 요청하는 방법과 설정
분할과 모놀리스 분해를 시도했고 모두 임시방편이었다고 한다.[^owner]
tsrs를 쓴 뒤 CI에서 7초, 맥북에서 약 12초가 걸리고
여러 에이전트가 로컬에서 병렬로 돌 수 있게 되었다고 한다.[^owner]

이는 에이전트 시대의 개발 도구를 평가하는 단위가 달라진다는 뜻이다.
사람 한 명이 쓸 때는 한 번의 검사 시간이 중요했지만,
에이전트 여럿이 동시에 검증을 돌리면
검사 한 번의 최대 메모리에 동시 실행 수를 곱한 값이 병목이 된다.
도구의 속도를 말할 때 이제 에이전트당 메모리를 같이 봐야 한다.
이는 이 문서의 해석이다.

### 4바이트 포인터는 Wasm이라는 목표와 어떻게 만나는지 열려 있다

포인터 압축은 모든 객체가 예약한 하나의 큰 메모리 블록(32GiB) 안에 있으므로
8바이트 주소 대신 블록 안의 거리를 4바이트로 쓰는 방법이다.
14~15%의 메모리를 줄이고 CPU 일은 6.5% 늘었다.[^owner]
HN의 afdbcreid는 이 포트가 GC 언어를 Rust로 옮길 때 구조를 바꿔야 하는 문제를
오래 쓰는 객체에 해제되지 않는 아레나를 두는 식으로 우회한다고
읽었다.[^afdbcreid]

그런데 발표의 가장 큰 이유가 Wasm이다.
tsrs의 Wasm 패키지는 wasm32-wasip1을 겨냥한다.[^readme]
32비트 Wasm의 주소 공간은 4GiB이므로 32GiB
블록을 예약하는 방식이 그대로는 들어맞지 않는다.
Wasm 빌드가 다른 메모리 설계를 쓰는지,
쓴다면 위의 절감이 그대로 따라오는지는 이 글에도 Owner의 글에도 나오지 않는다.
이는 이 문서가 읽고 던지는 질문이며 확인한 사실이 아니다.
이 질문의 답이 발표의 중심 논거와 수치 사이의 연결을 정한다.
