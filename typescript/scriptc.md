# scriptc | TypeScript-to-Native Compiler

<https://scriptc.dev/>

<https://github.com/vercel-labs/scriptc>

## 소개

scriptc는 일반적인 TypeScript 코드를 Node.js, V8, 혹은 바이너리에
내장된 어떤 JavaScript 엔진도 없이 동작하는 작고 빠른 네이티브
실행 파일로 변환하는 컴파일러다.
프로젝트는 이를 “zero-runtime TypeScript”라고 부른다.
전통적인 TypeScript 컴파일은 결과물을 실행하기 위해 런타임 환경을
필요로 하지만, scriptc는 네이티브 코드로 직접 컴파일함으로써 이
의존성을 제거한다.
그 결과로 시작 시간은 Node의 약 47ms 대비 약 2.4ms, 바이너리
크기는 170~200KB, 메모리 사용량은 일반적으로 1~4MB(Node는
67~116MB)로 각각 크게 줄어든다고 소개한다.

컴파일 방식은 세 단계 전략을 취한다.
기본값인 정적 컴파일(static compilation)은 TypeScript를 네이티브
코드로 직접 변환하고, 정적으로 컴파일할 수 없는 코드는 내장된
JavaScript 엔진(quickjs-ng, 약 620KB)이 동적으로 실행하며, 지원되지
않는 구문은 구체적인 진단 메시지와 함께 거부(rejection)된다.
컴파일러 파이프라인은 TypeScript를 타입 체크한 뒤 중간 표현(IR)으로
낮추고, 이를 C 또는 LLVM 코드로 생성한 다음 clang이 실행 파일로
컴파일하는 구조다.

설치는 `npm install -g scriptc`로 하며 clang이 필요하다(macOS에서는
Xcode Command Line Tools에 포함).
주 지원 대상은 macOS arm64이고, Linux와 Windows는 크로스 컴파일로
빌드된다.
언어 커버리지는 상속을 포함한 클래스, 클로저, 제네릭(모노모픽화),
구별된 유니온(discriminated union), 스택풀 파이버(stackful fiber)
기반의 async/await, finally 블록을 포함한 예외 처리, 구조 분해,
템플릿 리터럴, 정규식까지 포괄한다.
표준 라이브러리로는 UTF-16을 정확히 다루는 문자열, 배열, Map, Set,
검증된 캐스트를 지원하는 JSON, Math, 타입 배열, Buffer, 에러 계층이
있으며, Node API로는 fs(동기/프로미스), path, process,
child_process, os, crypto, url, zlib, timers, 시그널 핸들러, net,
http, https, tls, dgram, dns, fs.watch, readline이 지원된다.
fetch, WHATWG 스트림, Headers, AbortSignal 같은 웹 표준도 네이티브
네트워킹 위에서 제공된다.
npm 의존성은 Node의 해석 알고리즘을 그대로 따르며, JavaScript
코드는 빌드 시점에 바이너리에 내장(embed)된다.

주목할 만한 탈출구(escape hatch)로는 빌드 시점에 TypeScript를
실행해 결과를 리터럴로 굳히는 `comptime(() => ...)`, TypeScript
선언을 C ABI 호출에 직접 연결하는 네이티브 FFI(`--ffi`), npm
의존성이나 `any` 타입 코드를 위해 엔진을 내장하는 `--dynamic`이
있다.
`JSON.parse(...) as Config` 같은 검증된 캐스트는 런타임에 유효성을
검사해 구체적인 에러를 던진다.
정확성 보장을 위해 800개 이상의 테스트 케이스에 걸쳐 Node.js와
바이트 단위로 동일한 출력을 내는지 확인하는 차등 테스트(differential
testing)를 수행하고, AddressSanitizer 아래에서 코퍼스를 실행해
메모리 누수와 use-after-free를 빌드 실패로 처리하는 메모리 안전성
검증 레인도 운영한다.
`scriptc coverage`는 코드의 어느 부분이 정적으로 컴파일되고 어느
부분이 동적으로 실행되는지 보여준다.
Node와의 의도적인 차이(타이밍 내부 동작, 에러 객체 속성 등)는
문서화되고 번호가 매겨져 있다.
아키텍처는 프론트엔드(tsc API → IR)와 IR 검증, LLVM/C 백엔드를
담당하는 compiler, 참조 카운팅과 순환 참조 수집, 스택풀 파이버,
이벤트 루프, 서버 스택을 갖춘 C 런타임인 runtime, 그리고 build,
run, coverage 같은 명령줄 도구를 제공하는 cli 세 패키지로
구성된다.

## 분석

### “zero-runtime”이라는 표현이 가리키는 진짜 경쟁 상대

scriptc가 스스로를 “zero-runtime TypeScript”라 칭하는 것은 단순한
마케팅 문구가 아니라, 이 프로젝트가 겨루려는 대상이 다른
TypeScript 컴파일러가 아니라 Go, Rust, Zig 같은 네이티브
컴파일 언어라는 점을 드러낸다.
스타트업 시간 2.4ms, 바이너리 크기 200KB 미만이라는 수치는
Node.js 애플리케이션이 아니라 CLI 도구나 서버리스 함수, 임베디드
환경에서 흔히 요구되는 성능 기준과 비교되는 값이다.
Vercel이 이 프로젝트를 내놓았다는 사실도 이 문맥에서 이해할 수
있는데, 서버리스 함수의 콜드 스타트 비용을 줄이려는 그들의
인프라 이해관계가 TypeScript 생태계 전체를 네이티브 컴파일
방향으로 확장하려는 시도와 맞닿아 있다.

### 3단계 컴파일 전략이 정적 타입과 동적 언어 기능 사이의 근본적 긴장을 관리하는 방식

TypeScript는 결국 JavaScript의 동적 특성을 그대로 물려받은
언어이기 때문에, 모든 코드를 정적으로 네이티브 코드로 변환하는
것은 원리적으로 불가능하다.
scriptc가 “정적 컴파일 → 동적 실행(quickjs-ng) → 거부”라는 3단계
구조를 택한 것은, 이 근본적 한계를 인정하면서도 실용적인 절충안을
찾으려는 설계다.
이는 정적 타입 언어가 동적 기능을 포용할 때 흔히 택하는
전략(예: Julia의 타입 특수화, GraalVM의 다중 언어 실행)과 유사한
계보에 있으며, “모든 것을 정적으로 컴파일한다”는 이상보다
“컴파일 가능한 부분을 최대화하고 나머지는 명시적으로 표시한다”는
현실적 타협을 우선시한다.

### `coverage` 명령이 컴파일러의 신뢰를 구축하는 방식

`scriptc coverage`가 코드의 어떤 부분이 정적으로, 어떤 부분이
동적으로 컴파일되는지 보여준다는 것은, 이 프로젝트가 사용자에게
“믿고 써라”가 아니라 “직접 확인하라”는 태도를 취하고 있음을
보여준다.
성능이 핵심 가치 제안인 컴파일러에서, 실제로 어느 정도의 코드가
느린 동적 경로로 떨어지는지를 개발자가 사전에 알 수 있게 하는
것은 신뢰 구축 장치인 동시에, 코드를 정적 컴파일 가능한 형태로
리팩터링하도록 유도하는 은근한 압력이기도 하다.
이는 컴파일러가 성능을 오직 내부적으로만 최적화하는 대신,
개발자의 코드 작성 습관 자체를 변화시키려는 의도를 담고 있다.

## 비평

### macOS arm64 우선 지원이 “네이티브 컴파일”이라는 약속의 보편성을 제한한다

README는 Linux와 Windows를 크로스 컴파일로 지원한다고 언급하지만,
주 지원 대상은 명시적으로 macOS arm64뿐이다.
네이티브 컴파일러의 핵심 가치는 플랫폼에 특화된 최적화와 검증인데,
크로스 컴파일 경로가 macOS arm64와 동일한 수준의 테스트와 메모리
안전성 검증(AddressSanitizer 레인 등)을 거치는지에 대한 설명이
없다.
서버 환경의 대다수가 Linux인 상황에서, 실제 프로덕션 배포
환경에서의 신뢰성이 개발 환경(macOS)과 동등한지 검증되지 않은 채
“Linux 지원”이라는 문구만으로 뭉뚱그려져 있다는 점은 이 프로젝트를
서버 환경에 도입하려는 팀에게는 중요한 정보 공백이다.

### “Node.js와 바이트 단위로 동일한 출력”이라는 주장이 검증 범위를 스스로 좁힌다

800개 이상의 테스트 케이스로 차등 테스트를 수행한다는 것은
인상적인 수치지만, 동시에 README는 “타이밍 내부 동작과 에러 객체
속성에서 의도적인 차이가 존재한다”고 명시한다.
이는 “바이트 단위로 동일하다”는 주장이 사실은 제한된 조건 하에서만
성립하는 조건부 진술임을 뜻하는데, 어떤 종류의 코드가 이 800개의
테스트 케이스에 포함되어 있고 어떤 종류의 코드가 제외되어 있는지는
공개되어 있지 않다.
결과적으로 이 수치는 검증의 엄밀함을 보여주는 증거이면서 동시에,
검증되지 않은 나머지 영역이 얼마나 넓은지를 가늠할 방법이 없다는
한계를 함께 드러낸다.

### 세 가지 탈출구가 결국 “네이티브 컴파일”의 순수성을 스스로 무너뜨린다

`comptime`, `--ffi`, `--dynamic`이라는 세 가지 탈출구는 실용성
측면에서는 합리적인 선택이지만, 이 도구들이 존재한다는 사실
자체가 “TypeScript를 순수 네이티브 코드로 컴파일한다”는 프로젝트의
핵심 주장에 이미 여러 개의 예외 조항이 붙어 있음을 뜻한다.
특히 `--dynamic`이 npm 의존성이나 `any` 타입 코드를 위해 엔진
전체를 내장한다는 것은, 실제 프로덕션 코드베이스가 흔히 의존하는
서드파티 패키지나 점진적으로 타입이 붙은 레거시 코드에서는 이
“제로 런타임”이라는 약속이 상당 부분 무효화될 수 있다는 뜻이다.
README는 이 escape hatch들을 유연성의 장점으로만 서술할 뿐, 실제
평균적인 npm 프로젝트에서 이 탈출구들이 얼마나 자주 발동되는지에
대한 데이터는 제시하지 않는다.

## 인사이트

### 컴파일 타깃의 이동이 언어 생태계의 권력 구조를 바꾼다

TypeScript가 지금까지 성공할 수 있었던 이유 중 하나는 JavaScript
런타임(브라우저, Node.js)이라는 이미 존재하는 거대한 실행 환경
위에 타입 체크만 얹었기 때문이다.
scriptc처럼 TypeScript를 네이티브 코드로 직접 컴파일하는 시도가
늘어나면, TypeScript는 더 이상 “JavaScript의 상위 집합”이 아니라
독자적인 컴파일 타깃을 가진 별개의 언어로 서서히 갈라지게 된다.
이는 과거 CoffeeScript나 Dart가 JavaScript로의 컴파일에서 시작해
독자적인 런타임과 생태계로 분화를 시도했던 역사와 유사한 패턴이며,
이런 분화가 실제로 성공하려면 언어 자체의 우수성보다 그 배후에
있는 자본과 생태계(Vercel의 인프라적 이해관계 같은)가 결정적인
역할을 한다는 점을 시사한다.

### “빠른 시작 시간”이라는 가치가 서버리스 과금 구조를 재편할 잠재력

시작 시간 2.4ms라는 수치는 단순히 개발자 경험의 문제가 아니라,
서버리스 컴퓨팅의 과금 모델 자체에 영향을 미칠 수 있는 변수다.
현재 서버리스 플랫폼 대부분은 콜드 스타트 지연을 흡수하기 위해
warm pool을 유지하거나 최소 실행 시간을 과금 단위로 설정하는데,
scriptc 수준의 시작 시간이 보편화되면 이런 warm pool 유지 전략
자체가 불필요해질 수 있다.
이는 클라우드 벤더 입장에서는 인프라 비용 구조를 근본적으로
재검토해야 하는 상황을 만들 수 있으며, Vercel이 이런 컴파일러를
직접 개발하는 것은 자사 플랫폼의 비용 구조를 스스로 개선하려는
수직적 통합 전략으로도 읽을 수 있다.

### 메모리 안전성 검증 레인이 컴파일러 자체의 새로운 공격 표면을 암묵적으로 인정한다

AddressSanitizer 아래에서 코퍼스를 실행해 메모리 누수와
use-after-free를 빌드 실패로 처리한다는 설명은, C/LLVM으로
컴파일하는 이 프로젝트가 원래 TypeScript/JavaScript가 갖고 있던
메모리 안전성 보장(가비지 컬렉션에 의한 자동 관리)을 스스로
포기하고 그 대가로 수동 메모리 관리에 준하는 위험을 다시 떠안았다는
뜻이다.
JavaScript 개발자들은 지금까지 use-after-free 같은 버그를
언어 차원에서 신경 쓸 필요가 없었지만, scriptc로 컴파일된
바이너리는 참조 카운팅과 순환 참조 수집을 구현한 C 런타임에
의존하므로, 컴파일러 자체의 버그가 곧 메모리 안전성 취약점으로
이어지는 새로운 위험 계층이 생긴다.
이는 성능을 위해 안전성 모델을 교체한 데 따르는 트레이드오프이며,
이 프로젝트가 장기적으로 신뢰를 얻으려면 애플리케이션 코드의
정확성뿐 아니라 컴파일러와 런타임 자체의 메모리 안전성 검증
이력을 투명하게 공개하는 것이 중요해질 것이다.
