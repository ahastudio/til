## 소개

이창근이 쓴 위키독스 책이다.
부제가 내용을 그대로 말한다. 12GB·24GB GPU로 Qwen 기반 나만의 엔지니어링 에이전트 만들기.
소비자용 GPU 한 장으로 27B 규모 모델을 실행하고, 그 모델이 내 업무에 쓸 만한지 직접 검증하는 실전 가이드다.

구조는 아홉 장과 부록으로 되어 있고, 01~09장과 부록은 웹에서 무료로 읽을 수 있다.
10장 「업무 데이터로 최적화한 나만의 양자화 모델 만들기」만 유료 전자책 전용이며 가격은 9,000원이다.
예제 코드는 전자책 전용 장의 것까지 전부 공개되어 있고, 저자는 코드는 공개하되 만드는 과정과 해설과 실측 데이터가 책의 가치라고 밝힌다.

집필 방식도 명시되어 있다.
Claude Code를 활용해 작성했으며, 정확성을 위해 실제 설치와 실행 검증을 거치고 각 페이지 상단에 검증 상태와 대상 소프트웨어 버전을 표시한다.
실제로 본문 페이지마다 `[참고] 공식 문서 기준(미실측) · Ollama v0.34 · 자료 확인 2026-09-11` 같은 배지가 붙어 있어, 그 문단이 실측인지 문서 인용인지 구별된다.

실습 환경은 다음과 같다.

| 항목      | 내용                                                            |
| --------- | --------------------------------------------------------------- |
| OS        | Ubuntu 22.04/24.04 LTS, Windows는 WSL2                          |
| 실행기    | Ollama, llama.cpp                                               |
| 에이전트  | OpenCode                                                        |
| 실습 모델 | Qwen 3.8 27B 양자화 배포본 비교, 그리고 직접 양자화용 소형 모델 |
| 실측 GPU  | RTX 3090 24GB, RTX 3060 12GB                                    |
| 보조      | Apple 실리콘 Mac을 MLX 비교와 BF16 기준선에 사용                |

## 이 책이 다루는 범위

아홉 장의 흐름이 하나의 판단으로 수렴한다. 내 장비에서 무엇을 쓸 것인가.

1~2장은 환경을 맞추고 Ollama로 첫 모델을 띄운 뒤 `nvidia-smi`와 `/api/ps`로 VRAM을 읽는다.
3장이 원리 장이다. 정밀도와 비트, GGUF 파일 구조, K-quants와 I-quants와 importance matrix, `Q4_K_M`·`IQ4_XS`·`AD-IQ2_XS` 같은 이름 읽는 법, 양자화의 절벽이 어디인지, 그리고 필요 VRAM 공식을 다룬다.
4장은 직접 양자화한다. llama.cpp로 소형 원본 모델을 GGUF로 변환하고 Q8·Q4·IQ4·IQ2를 만들어 크기와 출력과 퍼플렉시티를 비교한 뒤 Modelfile로 Ollama에 등록한다.
5장은 반대로 남이 만든 배포본을 고르는 법이다. Hugging Face에서 출처·해시·구성을 읽고 템플릿과 내장 파라미터를 확인한다.
6장에서 두 GPU의 실용 설정을 찾고, 예측 VRAM과 실측 VRAM을 나란히 놓는다.
7장에서 OpenCode를 붙여 실제로 파일을 읽고 수정하고 테스트하는 에이전트를 만든다.
8~9장이 이 책의 본론이다. 채팅 답변이 아니라 업무로 모델을 평가하고, 실패를 유형별로 분석해 최종 설정을 고른다.

부록은 3090 두 장 동시 사용, OOM과 도구 호출 실패와 템플릿 오류 해결, 용어 정리, 참고 자료와 버전 기록이다.

## 필요 VRAM을 네 항으로 나누기

이 책에서 가장 실무적으로 쓸모 있는 대목이 3-7절이다.
출발 질문이 정확하다. 파일이 12GB보다 작은데 왜 12GB GPU에서 안 돌아가는가.

답은 가중치 말고도 GPU가 써야 할 메모리가 있다는 것이고, 책은 그것을 네 항으로 나눈다.

```text
필요 VRAM ≈ GPU에 적재된 가중치
          + KV 캐시·모델 상태
          + 연산 버퍼
          + 기타 사용량 (드라이버, 다른 프로세스, 스케줄러 여유분)
```

| 항        | 크기를 정하는 것                         | 줄이는 방법                        |
| --------- | ---------------------------------------- | ---------------------------------- |
| 가중치    | 양자화 타입, 오프로딩 비율               | 더 낮은 비트, 일부 층을 CPU로      |
| KV 캐시   | 문맥 길이, 층 수, KV 헤드 수, 정밀도     | 문맥 축소, KV 캐시 양자화          |
| 연산 버퍼 | 배치 크기, 문맥 길이, 어휘 크기          | 배치 축소, flash attention         |
| 기타      | CUDA 컨텍스트, 디스플레이, 다른 프로세스 | 모니터를 다른 GPU로, 프로세스 정리 |

핵심은 가중치가 가장 크지만 고정값이고, 설정에 따라 달라지는 것은 KV 캐시라는 점이다.
그리고 KV 캐시는 설정한 문맥 길이만큼 적재 시점에 미리 잡힌다. 작업 중 쌓이는 토큰은 그 예약 공간을 채울 뿐 메모리를 늘리지 않는다.

이 사실이 12GB 경로의 딜레마를 만든다.
문맥을 크게 잡으면 적재 단계에서 층이 CPU로 내려가고, 작게 잡으면 작업 도중 누적된 대화가 문맥을 넘어 앞부분이 잘린다.
양쪽으로 막히는 구조이며, 그래서 12GB에서는 KV 캐시 양자화가 선택이 아니라 사실상 전제가 된다.

### 네 개의 숫자를 구분해 읽기

책이 반복해서 강조하는 것이 숫자의 출처다.

| 수치             | 어디서 읽는가                | 뜻                         |
| ---------------- | ---------------------------- | -------------------------- |
| 모델 파일 크기   | `ls`, Hugging Face 페이지    | 디스크 크기                |
| 가중치 VRAM      | 실행기 로그의 모델 버퍼 크기 | GPU에 실제 올라간 가중치   |
| KV 캐시 크기     | 실행기 로그의 KV 버퍼 크기   | 문맥 설정에 따라 예약된 양 |
| 보드 전체 사용량 | `nvidia-smi`                 | 위 모두 + 연산 버퍼 + 기타 |

파일에는 토큰 임베딩이 들어 있는데 실행기에 따라 이 텐서를 CPU 메모리에 두기도 하고, 반대로 GPU에 올릴 때 정렬 때문에 조금 커지기도 한다.
그래서 파일 크기와 적재된 가중치 크기는 비슷하지만 같지 않다.

여기서 나오는 경고가 실무에서 가장 자주 어기는 것이다.
`nvidia-smi`가 보여 주는 숫자만 보고 “이 모델은 VRAM을 15GB 쓴다”고 말하면, 문맥 설정이 다른 환경에서는 틀린 말이 된다.

### KV 캐시 계산

```text
KV 캐시 = 2 (K와 V) × 층 수 × KV 헤드 수 × 헤드 차원 × 토큰 수 × 바이트 수
```

모델마다 층 수와 KV 헤드 수가 달라 토큰 하나당 필요한 양이 다르다.
Qwen 3.8 27B의 경우 공개 배포 페이지의 어림은 FP16 KV 캐시 32K 토큰에 약 2.3GB, 토큰당 약 70KB인데, 이 책의 6장 실측은 1K 토큰당 64MiB(32K에서 2,048MiB)로 그보다 약 10% 작다.
배포 페이지의 숫자와 실측이 어긋난다는 것을 그냥 넘기지 않고 차이를 적어 둔 대목이다.

| 문맥 길이 | FP16 (어림) | Q8       | Q4        |
| --------- | ----------- | -------- | --------- |
| 8K        | 약 0.6GB    | 약 0.3GB | 약 0.15GB |
| 16K       | 약 1.2GB    | 약 0.6GB | 약 0.3GB  |
| 32K       | 약 2.3GB    | 약 1.2GB | 약 0.6GB  |
| 64K       | 약 4.6GB    | 약 2.3GB | 약 1.2GB  |
| 128K      | 약 9.2GB    | 약 4.6GB | 약 2.3GB  |

12GB 계산 예시가 이 표의 의미를 보여 준다.
27B IQ2_S 배포본의 가중치 약 9.3GB를 올리면 남는 것이 2.7GB이고, 연산 버퍼와 기타로 1GB 정도를 빼면 KV 캐시에 쓸 수 있는 것은 약 1.7GB, FP16 기준 약 24K 토큰이다.
OpenCode의 도구 정의와 파일 내용과 대화 이력이 쌓이는 것을 생각하면 넉넉하지 않다.

### 두 양자화는 별개다

3장에서 다루는 것은 전부 가중치 양자화이며, 파일을 만들 때 한 번 결정되고 실행 중에는 바뀌지 않는다.
KV 캐시 양자화는 실행기가 실행 중에 키와 값을 저장할 때 정밀도를 낮추는 것으로, 모델 파일과 무관하게 실행 옵션으로 켜고 끈다.

| 구분          | 가중치 양자화           | KV 캐시 양자화                          |
| ------------- | ----------------------- | --------------------------------------- |
| 언제 결정     | 파일 제작 시            | 실행 시 옵션                            |
| 무엇을 줄이나 | 가중치 VRAM             | KV 캐시 VRAM                            |
| 영향          | 모델의 지식과 판단 전체 | 긴 문맥에서 이전 내용을 기억하는 정확도 |
| 대표 설정     | `Q4_K_M`, `IQ4_XS`      | `f16`(기본), `q8_0`, `q4_0`             |

Ollama는 KV 캐시 타입을 환경 변수로 지정할 수 있고, 공식 FAQ는 `q8_0`이 대부분의 경우 품질 손실이 거의 없이 메모리를 절반으로 줄인다고 안내한다.
다만 flash attention이 켜져 있어야 하고, 모델과 백엔드 조합에 따라 적용되지 않는 경우가 있다.
책은 이 안내를 그대로 옮기지 않고 6장에서 실제 모델과 GPU로 적용 여부와 품질 영향을 확인한 결과만 기록한다고 밝힌다.

두 양자화는 겹쳐 쓸 수 있지만 오차도 겹친다.
가중치를 2비트로 강하게 줄인 모델에 KV 캐시까지 `q4_0`으로 줄이면 두 오차가 누적되고, 반대로 가중치는 4비트로 여유 있게 두고 KV 캐시만 `q8_0`으로 줄여 문맥을 두 배 늘리는 조합이 24GB 경로의 유력한 후보다.

## 값 정하기

책이 3-7절에서 제시한 예측표가 실제 설정의 출발점이다.
가중치는 배포본 파일 크기를 그대로 썼고, 연산 버퍼와 기타는 1~1.5GB로 잡았다.

| 경로                     | 가중치 | KV  | 버퍼·기타 | 합계 | 판단                                   |
| ------------------------ | ------ | --- | --------- | ---- | -------------------------------------- |
| 24GB, IQ4_XS, 32K FP16   | 14.3   | 2.3 | 1.5       | 18.1 | 여유 약 6GB. 문맥 64K 또는 Q4_K_M 가능 |
| 24GB, Q4_K_M, 64K `q8_0` | 16.5   | 2.3 | 1.5       | 20.3 | 가능. 긴 작업용 설정 후보              |
| 12GB, IQ2_S, 16K FP16    | 9.3    | 1.2 | 1.0       | 11.5 | 경계선. 기타 사용량에 따라 실패 가능   |
| 12GB, IQ2_S, 16K `q8_0`  | 9.3    | 0.6 | 1.0       | 10.9 | 가능성 높음. 12GB 경로의 시작점 후보   |
| 12GB, IQ3_XXS, 8K `q8_0` | 10.9   | 0.3 | 1.0       | 12.2 | 초과. 부분 오프로딩 필요               |

단위는 GB다.
책은 이 표가 예측이며 실측이 아니라고 명시한다. 실행기가 스케줄러 여유분을 따로 잡거나, 모니터가 연결된 GPU에서 이미 수백 MB가 쓰이고 있어 결과가 달라진다.

무엇을 측정해 이 값을 고칠지도 분명하다.
실행기 로그의 모델 버퍼와 KV 버퍼를 읽어 예측과 대조하고, `nvidia-smi`의 보드 전체 사용량에서 나머지 항을 역산하는 것이다.
6-5절이 이 대조를 전담한다.

## 평가 설계가 이 책의 차별점

8장이 이 책을 다른 양자화 가이드와 갈라 놓는 부분이다.
평가 대상이 채팅 답변이 아니라 다섯 개의 업무 영역이고, 서버·GPU·코드·보고·권한 업무로 모델을 본다.

채점 기준이 다섯 축으로 나뉜다. 답안, 원인, 근거, 도구, 위험한 확정이다.
마지막 축이 특히 눈에 띈다. 확신할 수 없는 것을 확신한 것처럼 말하는 실패를 별도 항목으로 센다는 뜻이며, 로컬 에이전트에서 이것이 오답보다 비싼 실패다.

그리고 최초 답안과 보정 단계를 분리해 기록한다.
한 번에 맞히는 것과 지적받고 고치는 것을 같은 성공으로 세면 작은 양자화본의 약점이 지워지기 때문이다.

측정 항목은 업무 성공률, 작업 완료율, 완료 시간, 최대 VRAM, 재시도 수이며, 두 GPU에서 같은 모델과 같은 과제로 재고 표로 제시한다.
저자는 결과를 과장하지 않는다고 명시하고, 합성 데이터와 표본 수와 평가 한계를 밝힌다.

9장의 비교 구도가 실제 구매 판단과 맞닿는다.
같은 GPU에서 IQ3와 IQ2를 비교하고, 12GB에서 소형 모델 Q4와 27B IQ2를 비교한다.
후자가 로컬 LLM에서 가장 자주 나오는 질문이다. 작은 모델을 넉넉한 비트로 돌릴 것인가, 큰 모델을 빠듯한 비트로 돌릴 것인가.

## 함정

파일 크기로 VRAM을 가늠하면 12GB에서 반드시 틀린다.
네 항 중 하나만 본 것이고, 특히 문맥 길이를 정하지 않은 상태의 파일 크기는 예측값이 되지 못한다.

`nvidia-smi` 하나로 결론을 내리면 다른 문맥 설정에서 재현되지 않는다.
실행기 로그의 모델 버퍼와 KV 버퍼를 따로 읽어야 어느 항이 문제인지 알 수 있다.

KV 캐시 양자화는 조건부 기능이다.
flash attention이 켜져 있어야 하고 모델과 백엔드 조합에 따라 적용되지 않으므로, 설정했다고 적용된 것이 아니다. 로그에서 실제 KV 버퍼 크기가 줄었는지 확인해야 한다.

두 양자화를 동시에 강하게 걸면 오차가 겹친다.
가중치 2비트에 KV `q4_0`을 더하는 조합은 각각의 벤치마크로는 설명되지 않는 실패를 만든다.

에이전트 작업은 문맥을 빠르게 먹는다.
OpenCode의 도구 정의만으로도 상당한 토큰이 들어가고 거기에 파일 내용이 붙는다. 채팅 기준으로 잡은 문맥 길이는 에이전트 작업에서 금방 모자란다.

책의 페이지마다 붙은 검증 배지를 무시하면 안 된다.
`[참고] 공식 문서 기준(미실측)`이 붙은 문단은 저자가 직접 재지 않은 내용이며, 실제로 Qwen 배포 페이지의 KV 캐시 어림과 저자 실측이 10% 어긋났다.

## 비평

### 모델 하나에 묶인 실측의 수명

이 책의 가치는 실측 데이터에 있고, 그것이 동시에 가장 빨리 낡는 부분이다.
Qwen 3.8 27B의 특정 배포본, Ollama v0.34, 특정 시점의 llama.cpp에서 잰 숫자이며, 층 수와 KV 헤드 수가 다른 모델에는 KV 캐시 표가 그대로 적용되지 않는다.

저자도 이것을 알고 있다.
페이지마다 대상 소프트웨어 버전을 적고 부록 D에 버전 기록을 둔 것이 그 대응이며, 전자책 구입이 책을 최신 버전으로 유지하는 데 도움이 된다고 밝힌 것도 같은 맥락이다.

다만 독자 입장에서 남는 문제는 어느 숫자가 옮겨 쓸 수 있고 어느 숫자가 이 모델 전용인지다.
네 항 분해와 KV 캐시 공식은 모델과 무관하게 성립하고, 문맥 길이별 GB 표와 배포본별 파일 크기는 전용이다.
책이 이 구분을 절 단위로 더 분명히 갈라 두었다면 1년 뒤에도 쓸 수 있는 부분이 더 뚜렷했을 것이다.

### AI로 쓴 기술서라는 조건

저자는 Claude Code를 활용해 썼다고 첫 화면에 밝히고, 실제 설치와 실행 검증을 거치며 페이지마다 검증 상태를 표시한다고 덧붙인다.
이 공개는 평가할 만하다. 밝히지 않는 쪽이 훨씬 흔하기 때문이다.

그리고 검증 배지는 단순한 면피 장치가 아니라 실제로 기능한다.
`[참고] 공식 문서 기준(미실측)`이라고 적힌 문단은 독자가 그것을 저자의 측정으로 오해하지 않게 하고, 같은 절 안에서 배포 페이지 어림과 6장 실측이 10% 다르다는 사실을 나란히 적은 대목이 이 표시 체계가 작동하고 있음을 보여 준다.

그럼에도 남는 질문은 검증의 범위다.
설치와 실행이 되는 것과 설명이 맞는 것은 다른 층위이고, 원리 설명 부분은 실행 검증으로 확인되지 않는다.
K-quants와 I-quants의 차이나 importance matrix의 역할 같은 서술은 돌려 봐서 확인할 수 있는 종류가 아니며, 이 책에서 가장 많이 인용될 부분이 정확히 그쪽이다.

### 무료와 유료의 경계가 그어진 자리

01~09장이 무료이고 10장만 유료인 구조는 명확하고 정직하다.
게다가 예제 코드는 전자책 전용 장의 것까지 전부 공개한다.

경계가 그어진 자리도 합리적이다.
10장은 내 업무 데이터로 importance matrix를 만들고 텐서별 정밀도를 지정해 목표 크기의 양자화 파일을 만든 뒤 공개 배포본과 같은 표에서 비교하는 내용이며, 앞의 아홉 장이 전부 이 장의 준비 과정으로 읽힌다.

다만 그래서 무료 부분만 읽은 독자에게 남는 결론이 “남이 만든 배포본 중에 고르라”가 된다.
그것도 실용적인 답이지만, 책의 제목이 약속한 “직접 양자화”의 가장 흥미로운 부분은 4장의 소형 모델 실습과 10장으로 갈라져 있다.
4장이 소형 모델로 원리를 익히는 데 그치고 27B를 직접 다루는 것은 유료 장으로 간 구조이며, 이 분할이 콘텐츠 설계인지 수익 설계인지는 독자가 판단할 문제다.

## 체크리스트

- 내 GPU의 가용 VRAM에서 모니터와 다른 프로세스가 쓰는 양을 빼고 계산했는가
- 모델 파일 크기가 아니라 실행기 로그의 모델 버퍼 크기를 읽었는가
- 문맥 길이를 정한 뒤 KV 캐시 예약량을 계산했는가
- 에이전트 도구 정의가 차지하는 토큰을 문맥 예산에 포함했는가
- KV 캐시 양자화를 켰다면 로그에서 실제로 적용됐는지 확인했는가
- 가중치와 KV 캐시 양쪽을 동시에 강하게 줄이고 있지는 않은가
- 평가할 때 최초 답안과 보정 후 결과를 분리해 기록했는가
- 읽고 있는 문단이 실측인지 문서 인용인지 배지를 확인했는가

## 기억할 원칙

### 돌아가는 것과 쓸 만한 것은 다른 측정이다

이 책이 반복해서 말하는 구분이 대상 독자 항목에도 그대로 적혀 있다.
내 장비에서 모델이 돌아가는 것과 쓸 만한 것의 차이를 직접 측정해 보고 싶은 사람이 독자라는 것이다.

로컬 LLM 논의가 대체로 앞의 것에서 멈춘다.
몇 GB에 몇 토큰이 나오는지는 쉽게 재고 공유되지만, 그 설정으로 실제 업무를 끝낼 수 있는지는 각자 다르게 재거나 아예 재지 않는다.
이 책이 8장 전체를 평가 설계에 쓴 이유가 여기 있고, 채점 축에 “위험한 확정”을 넣은 것이 그 태도를 가장 잘 보여 준다.

옮겨 쓸 수 있는 형태로 정리하면 이렇다.
로컬 모델 설정을 고를 때 재야 할 것은 토큰 생성 속도가 아니라, 내 업무 과제 몇 개를 정의해 두고 그 과제의 완료율과 재시도 수를 재는 것이다.
그리고 최초 답안과 보정 후를 분리해 적어야 한다. 그 둘을 합치면 작은 양자화본이 실제보다 좋아 보이기 때문이다.
