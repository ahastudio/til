# Go의 url.Error는 요청이 응답 전에 실패하면 쿼리 문자열까지 에러에 담아 로그로 샌다

원문: [Go url.Error가 쿼리 문자열을 로그에 남기는 경로와 마스킹 방법](https://velog.io/@commitlog/go-url-error-query-masking)

GN 토론: <https://news.hada.io/topic?id=37086>

## 소개

글쓴이 commitlog가 velog에 올린 사례 글이다.
실제 계좌로 전환하기 전에 계좌번호가 평문으로 보이는 곳을 점검했더니 로그 파일 한 곳에서 4899줄이 나왔다.
테스트용 계좌 두 개의 번호였고, 원인은 Go의 `*url.Error`가 쿼리 문자열을 그대로 에러에 담는 것이었다.
글은 쿼리를 통째로 잘라 같은 `*url.Error`로 다시 만드는 해결책과, 그것을 검증하는 테스트를 설명한다.
글쓴이는 Go 1.25와 `http.Client`의 `Timeout` 기준이라고 밝힌다.

## 어떻게 새는가

### 글쓴이가 본 경로

계좌 조회는 GET 요청이라 계좌번호가 쿼리 문자열에 실린다.
Go의 `http.Client`는 응답 전에 실패하면(타임아웃, 연결 거부) `*url.Error`를 돌려주고,
이 에러의 URL 필드에는 주소가 쿼리까지 들어 있다.
글쓴이는 이 에러를 감싸 경고 로그로 남기고 있었다.
출력은 이런 모양이다.

```text
Get "https://api.example.com/v1/summary?account=<acct>": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
```

비밀 값을 가리는 함수는 있었지만 메신저 알림 경로에만 붙어 있었고 가리는 대상도 봇 토큰 하나였다.
로그 파일로 가는 조회 실패 에러는 그 함수를 거치지 않았다.

### Go 소스에서 확인한 것

이 문서는 Go 저장소의 소스에서 글의 주장을 확인했다.
`net/url`의 `Error`는 Op, URL, Err 세 필드를 가지고, `Error()` 문자열은 `Op`와 `URL`과 `Err`를 이어 붙인 것이다.[^url]
`http.Client`가 실패를 `url.Error`로 감쌀 때 쓰는 URL 문자열은 `stripPassword` 함수를 거치는데,
이 함수는 사용자 정보에 비밀번호가 있을 때 그것만 별표로 바꾸고 나머지는 그대로 돌려준다.[^client]
그러므로 쿼리 문자열은 가려지지 않는다.
글쓴이가 말한 표준 라이브러리가 지우는 것은 주소 속 비밀번호뿐이라는 문장과 일치한다.
이 문서는 저장소의 현재 기본 브랜치 소스를 읽었고, Go 1.25의 해당 릴리스 소스는 열어 보지 않았다.
Go를 실행해 실제 출력을 만들어 보지도 않았다.

## 해결

### 쿼리를 통째로 버린다

글쓴이는 가릴 파라미터 목록을 두는 대신 쿼리 문자열을 통째로 버렸다.
목록은 새 값이 붙을 때마다 고쳐야 하고 한 번 잊으면 다시 새기 때문이다.
대가는 다른 조회의 쿼리 조건도 로그에서 빠지는 것이다.

### 같은 `*url.Error`로 다시 만든다

에러를 문자열로 바꾸지 않고 같은 타입으로 다시 만들면 `Op`와 `Err`가 그대로 남아,
`errors.As`나 `Timeout()`으로 원인을 묻는 코드가 전과 같은 값을 받는다.
글의 재구성 코드는 다음과 같다.

```go
func redactURLError(err error) error {
	var ue *url.Error
	if !errors.As(err, &ue) {
		return err
	}
	u := ue.URL
	if i := strings.IndexByte(u, '?'); i >= 0 {
		u = u[:i]
	}
	return &url.Error{Op: ue.Op, URL: u, Err: ue.Err}
}
```

### 응답 본문도 같은 메시지에 실렸다

같은 메시지에는 200이 아닌 응답의 body도 통째로 실리고 있었다.
계좌번호가 돌아온 적은 없지만 응답이 보낸 값을 되돌려 줄지는 글쓴이가 정할 수 없다.
그래서 오류 코드 같은 진단 필드만 남기고, 형식을 모르는 body는 길이만 적는다.

## 테스트

고치기 전에 실패하는 테스트 세 개를 먼저 썼다.
연결 거부, 재시도 중 타임아웃, 서버가 계좌번호를 되돌려 주는 경우이다.
셋 다 메시지에 계좌번호와 필드 이름과 `?`가 없는지 본다.
그런데 없어야 할 것만 보면 전부 지우는 코드도 통과한다.
그래서 연결 거부는 경로와 원인이, 되돌려 주는 경우는 오류 코드가 남는지도 함께 확인한다.
이 이중 확인이 글에서 가장 이식하기 쉬운 부분이다.

수정은 새로 쌓이는 줄만 막는다.
이미 찍힌 줄은 따로 정하기로 했고 배포 뒤 다시 세어 늘었는지 볼 계획이라고 글쓴이는 적는다.

## 값 정하기

### 통째로 버릴지, 허용할 키만 남길지

이 선택이 글의 핵심 판단이자 토론이 모인 곳이다.
GeekNews에서 한 사용자는 쿼리를 전부 지우면 장애 분석 때 아쉬울 수 있으니 허용할 키만 남기는 방식은 어떠냐고 물었다.[^eggkmc3]
글쓴이는 이 대가를 스스로 밝히고 다르게 처리한 경험을 듣고 싶다고 댓글을 달았다.[^commitlog]

두 방식의 차이는 실패의 방향이다.

- 통째로 버리면 새 쿼리 파라미터가 생겨도 새지 않는다. 실패는 로그가 덜 유용해지는 쪽으로 난다.
- 허용 목록은 장애 분석에 필요한 키를 남긴다. 그러나 목록에 잘못 넣은 키는 곧바로 샌다. 실패는 비밀이 새는 쪽으로 난다.

비밀이 들어 있을 수 있는 값에서는 새는 쪽의 실패가 더 비싸므로 글쓴이의 선택이 보수적이다.
허용 목록을 쓴다면 키 이름만이 아니라 값의 형식까지 검사하거나,
목록에 오른 키를 코드 리뷰의 대상으로 삼아야 한다.
이 판단은 글에서 이 문서가 끌어낸 것이다.

## 함정

- 글쓴이는 에러를 한 곳(메신저 알림)에서만 가렸다. 가리는 함수는 로그가 나가는 경로 전부에 붙여야 한다.
- 가리는 위치를 에러를 만드는 곳이 아니라 기록하는 곳 한 군데로 모으면 새 경로가 생겨도 놓치지 않는다. 이는 이 문서의 제안이며 글에 있는 내용은 아니다.
- 에러 메시지에 응답 본문이 들어가면 쿼리를 지워도 값이 샐 수 있다. 글쓴이가 본문까지 줄인 이유이다.
- 문자열로 바꾼 에러는 `errors.As`와 `Timeout()`을 잃는다. 같은 타입으로 다시 만드는 이유이다.
- 이미 남은 로그는 수정으로 지워지지 않는다. 배포 뒤 다시 세어 보는 계획이 필요하다.

## 체크리스트

- [ ] 외부 호출 에러를 로그에 남기는 코드를 찾는다.
- [ ] 그 에러가 URL을 통째로 들고 있는지 확인한다(`*url.Error`).
- [ ] 비밀 값이 쿼리 문자열에 실리는 요청이 있는지 확인한다. GET 요청의 식별자와 토큰이 대표적이다.
- [ ] 쿼리를 버릴지 허용 목록으로 남길지 정한다.
- [ ] 에러를 같은 타입으로 다시 만들어 `errors.As`를 유지한다.
- [ ] 응답 본문이 에러 메시지에 실리는지 확인한다.
- [ ] 없어야 할 것과 남아야 할 것을 함께 검사하는 테스트를 쓴다.
- [ ] 배포 뒤 기존 로그에서 같은 값이 다시 늘지 않는지 센다.

## 비평

### 글의 일반화는 한 사례의 범위를 넘지 않는다

글은 자신의 사례를 정확히 한정한다. Go 1.25, `http.Client`의 타임아웃, GET 요청, 계좌 조회이다.
그러나 제목은 `url.Error`가 쿼리 문자열을 남기는 경로라고 일반적으로 말한다.
Go 소스에서 확인한 것은 URL이 에러에 담긴다는 점이고, 이는 모든 `url.Error`에 해당한다.
글쓴이가 시험한 실패 유형(타임아웃, 연결 거부)이 전부는 아닐 수 있다.
다른 실패 경로에서의 동작은 글에도 이 문서에도 없다.

### 비밀을 쿼리 문자열에 싣는 설계 자체가 원인이다

글은 에러를 마스킹하는 방법을 다루지만, 계좌번호가 GET 요청의 쿼리 문자열에 실리는 것 자체가 로그뿐 아니라 프록시와 접근 로그에도 남는 설계의 문제이다.
글쓴이는 외부 API의 형식을 바꿀 수 없을 수 있다.
그럴 때는 이 마스킹이 필요한 방어이다.
바꿀 수 있다면 값을 요청 본문이나 헤더로 옮기는 것이 더 근본적이다.
이는 이 문서의 의견이며 글은 이 선택지를 다루지 않는다.

## 기억할 원칙

### 에러 값은 기록하기 전에 무엇을 들고 있는지 먼저 본다

에러는 보통 원인을 담는 값으로 여겨지지만 요청의 일부를 담을 수 있다.
외부 호출의 에러를 로그에 남기기 전에 그 에러가 URL이나 본문을 통째로 들고 있는지를 먼저 확인한다.

### 막는 테스트는 남겨야 할 것도 함께 확인한다

없어야 할 것만 검사하면 모두 지우는 코드도 통과한다.
없어야 할 것과 남아야 할 것을 한 쌍으로 검사해야 마스킹이 로그의 쓸모를 지우지 않는다.
