# encoding/json의 결함은 API에서 나왔고, 그래서 v2에 6년이 걸렸다

원문: [A new Go API for JSON - The Go Programming Language](https://go.dev/blog/jsonv2)

HN 토론: <https://news.ycombinator.com/item?id=50369106> (344점, 175개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/gfm0xn/new_go_api_for_json> (30점, 5개 댓글)

GN 토론: <https://news.hada.io/topic?id=36615>

## 요약

Go 블로그가 2026년 11월 4일에 올린 글로,
Michael Pratt, Joe Tsai, Daniel Martí 등 일곱 명이 공동 저자로 올라 있다.
새 `encoding/json/v2`와 `encoding/json/jsontext` 패키지가
Go 1.27에서 안정화되어 정식으로 제공된다고 알린다.
1년 전에 실험으로 소개한 글을 갱신한 것이다.
Go 1.27 릴리스 노트가 이 패키지를 어떻게 다루는지는
[Go 1.27](go-1-27.md) 문서에 정리돼 있다.
이 문서는 릴리스 노트에 없는 설계 근거와 호환 전략을 다룬다.

저자들은 `encoding/json`(이하 v1)의 문제를 세 갈래로 나눈다.
첫째는 동작 결함이다.
v1은 잘못된 UTF-8과 중복된 객체 멤버 이름을 받아들이고,
nil 슬라이스와 맵을 JSON `null`로 내보내며,
언마샬링(unmarshaling) 때 멤버 이름과 구조체 필드 이름을
대소문자 구분 없이 맞춘다.
포인터 리시버의 `MarshalJSON` 호출이 일관되지 않다는 점도 든다.
둘째는 API 결함이다.
`json.NewDecoder(r).Decode(v)`는 입력 끝에 붙은 잘못된 데이터를 거부하지 못하고,
옵션은 `Encoder`와 `Decoder`에만 있어 `Marshal`과 `Unmarshal`에서 못 쓰며,
`MarshalJSON` 안으로 옵션을 전달할 길이 없다.
셋째는 성능 한계다.
`MarshalJSON`은 결과 `[]byte`를 할당하고 검증과 재포맷을 거치게 만든다.
`UnmarshalJSON`은 값의 끝을 찾으려고 한 번,
메서드 안에서 또 한 번 파싱하게 만든다.
`Encoder`와 `Decoder`는 이름과 달리 값 전체를 메모리에 버퍼링하고,
`MarshalJSON` 안에서 `Marshal`을 재귀 호출하면 성능이 이차(quadratic)가 된다.

저자들은 이 문제들이 모두 기존 API의 필연적 결과여서
Go 1 호환성 약속(compatibility promise) 안에서는 고칠 수 없다고 본다.
`MarshalV2` 같은 이름을 같은 패키지에 더하는 것은
같은 패키지 안에 병렬 이름 공간을 만드는 일과 같다고 설명하며,
그래서 별도의 `v2` 패키지를 택했다고 말한다.

새 설계는 두 층이다.
`jsontext`는 JSON 문법만 다루는 층으로,
Go 리플렉션(reflection)에 의존하지 않는다.
`Encoder`와 `Decoder`, 값(`Value`, 이름 있는 `[]byte`),
토큰(`Token`)을 제공하고,
v1의 `RawMessage`는 `jsontext.Value`의 타입 별칭(alias)이 됐다.
그 위의 `json/v2`는 JSON 값과 Go 값을 대응시키는 의미 층이다.
`Marshal`, `MarshalWrite`, `MarshalEncode`,
`Unmarshal`, `UnmarshalRead`, `UnmarshalDecode`가 모두 가변 옵션을 받는다.
타입은 기존 `Marshaler`와 `Unmarshaler`에 더해
`Encoder`나 `Decoder`를 직접 받는
`MarshalerTo`와 `UnmarshalerFrom`을 구현할 수 있고,
호출하는 쪽도 `WithMarshalers`로 임의 타입의 표현을 덮어쓸 수 있다.

v2의 동작 변경으로는 잘못된 UTF-8과 중복 이름에 대한 오류,
nil 슬라이스와 맵의 빈 배열과 빈 객체 출력,
대소문자를 구분하는 필드 매칭,
`omitempty`의 재정의(`null`, `""`, `[]`, `{}`로 인코딩될 값을 생략),
기본 표현이 없는 `time.Duration`의 오류를 든다.
대부분은 구조체 태그나 호출 옵션으로 v1 동작을 되살릴 수 있다.
성능은 `Marshal`이 대체로 같은 수준이고
`Unmarshal`은 벤치마크에서 최대 10배까지 빨라졌다고 한다.
Kubernetes의 한 서비스에서는
`UnmarshalJSON` 안의 재귀 파싱을 `UnmarshalJSONFrom`으로 바꿔
성능이 자릿수 단위로 개선됐다고 소개한다.
저자들은 v2가 v1보다 느린 경우를 계속 최적화하며
Go 1.28에서 추가 개선을 기대할 수 있다고 쓴다.

호환성에서는 v1과 v2가 서로 섞여 쓰일 수 있게 했다.
v1이 v2 위에 구현돼 있어서,
v2가 쓰는 패키지가 v1의 `MarshalJSON`을 정의한 타입을 만나도,
v1이 쓰는 패키지가 v2의 `MarshalJSONTo`를 정의한 타입을 만나도 동작한다.
v1은 계속 지원되며 마이그레이션이 필요 없다고 분명히 말한다.
저자들은 v2가 6년 가까이 걸렸고,
Daniel Martí의 2020년 말 초안과
protojson 작업을 하던 Joe Tsai의 문제의식에서 시작해
2023년 GopherCon 발표, 2025년 정식 제안, Go 1.25 실험을 거쳤다고 정리한다.
개발과 홍보를 주로 Google 소속이 아닌 사람들이 맡았다는 점도 적었다.

## 분석

### 문제의 원인이 구현이 아니라 시그니처에 있어서 새 메이저 버전이 필요했다

글의 중심 주장은 두 단계다.
v1의 결함은 고칠 수 있는 버그가 아니라 API가 낳은 결과라는 것,
그리고 그렇다면 Go 1 호환성 약속 때문에 같은 패키지 안에서는
고칠 수 없다는 것이다.
이 논증이 성립하는 이유는 결함의 목록을 보면 드러난다.
`MarshalJSON`이 `[]byte`를 반환한다는 시그니처 자체가
할당과 재검증을 강제한다.
`UnmarshalJSON`이 완결된 JSON 값을 받는다는 시그니처 자체가
이중 파싱을 강제한다.
구현을 아무리 다듬어도 인터페이스가 요구하는 일은 줄지 않는다.

저자들이 `MarshalV2` 같은 이름 추가를 거부한 이유도 같은 구조에서 나온다.
기능을 더하기는 쉽지만 기존 기능의 의미를 바꾸기는 어렵다는 말은,
호환성 약속이 막는 것이 추가가 아니라 변경이라는 뜻이다.
동작 결함(중복 이름 허용, 대소문자 무시)은 변경 없이는 고칠 수 없고,
이름만 바꿔 병렬로 두면 패키지 하나가 두 벌의 API를 갖게 된다.
그 대안으로 새 import 경로를 고른 것이 v2다.

### jsontext가 구문과 의미를 나누어 성능 문제를 구조적으로 푼다

저자들은 JSON 처리를 구문(syntax)과 의미(semantics)로 나누고,
용어도 구분한다.
구문 쪽은 인코딩(encode)과 디코딩(decode),
의미 쪽은 마샬링(marshal)과 언마샬링(unmarshal)이다.
v1의 `Encoder`와 `Decoder`는 이 구분을 흐렸고,
그래서 스트리밍(streaming)이라는 이름과 달리 값 전체를 버퍼링했다.

`jsontext`는 리플렉션 없이 토큰과 값의 열을 읽고 쓰는 층이다.
이 층이 있어야 `MarshalJSONTo`와 `UnmarshalJSONFrom`이 의미를 가진다.
메서드가 `Encoder`나 `Decoder`를 직접 받으면
검증과 재포맷, 값 경계 탐색의 책임이 `json` 패키지에서
`jsontext`로 넘어간다.
옵션도 `Encoder`와 `Decoder`가 들고 있으므로
호출 스택 아래로 전달된다.
v1의 세 가지 성능 한계와 옵션 전달 문제가
하나의 구조 변경으로 함께 풀리는 것이다.

### v1을 v2 위에 구현해 호환성을 옵션 집합으로 바꿨다

호환성 전략의 핵심은 v1을 v2의 옵션 조합으로 구현한 것이다.
모든 동작 차이가 옵션 하나에 대응하므로,
v1은 v1 호환 옵션 전체를 넘긴 v2이고
마이그레이션은 옵션을 하나씩 빼는 일이 된다.
글이 드는 예처럼 중복 이름 허용만 남기고 나머지는 v2 동작으로 두거나,
반대로 v1 동작을 두고 중복 이름만 금지할 수 있다.

이 방식의 부수 효과도 글이 직접 말한다.
v2에 추가되는 `MarshalJSONTo`와 `embed` 태그 같은 기능이
v1 사용자에게도 자동으로 적용된다.
두 패키지가 하나의 구현을 공유하므로
한쪽에서 고친 것이 다른 쪽에도 반영된다.

### 코드 변경 없이 얻는 이득과 코드를 바꿔야 얻는 이득이 나뉜다

글의 성능 서술을 읽을 때는 조건을 구분해야 한다.
`Unmarshal`의 최대 10배 개선은 단순히 import 경로를 바꿔서 얻는 수치로
제시되지만,
`Marshal`은 대체로 같은 수준이라고 한다.
더 큰 이득은 `Marshaler`와 `Unmarshaler` 구현을
`MarshalerTo`와 `UnmarshalerFrom`으로 옮겨야 얻는다는 것이 저자들의 권고다.
Kubernetes 사례의 자릿수 단위 개선도 이 경우다.
이 글이 약속하는 속도 개선의 상당 부분은
사용자가 자기 타입의 메서드를 다시 써야 실현된다.

HN에서 `Philip-J-Fry`는 이 수치가 실무에서 갖는 의미를 따져 보았다.
그는 매우 높은 처리량의 사이트 백엔드를
`encoding/json`과 `net/http`만으로 만들었고,
요청이 I/O를 한 번이라도 하면 JSON 처리의 나노초 절감은 보이지 않으며,
CPU 시간은 자기 팀의 한계였던 적이 없다고 적었다.
그래서 v2의 가장 큰 이점은 속도가 아니라 개선된 API라고 보았다.[^Philip-J-Fry]
이 관찰은 저자들이 `UnmarshalJSON`의 이중 파싱과
API 결함을 같은 비중으로 다룬 구성과 맞는다.

### 작년 실험판과 달라진 점은 글이 아니라 코어 팀의 답글에 있다

Lobste.rs에서 fanf는 이 일이 1년 넘게 진행되어 왔고 이전 글도 있었으니,
글만 빠르게 훑어서는
작년과 무엇이 달라졌는지 요약이 보이지 않는다고 지적했다.[^fanf]
Go 코어 팀의 prattmic이 이에 답했다.
이 글은 작년 실험 글(go.dev/blog/jsonv2-exp)의 갱신판이고 GOEXPERIMENT 시절과 큰
변화는 없으며,
그 글에서 고친 것은 `inline` 구조체 태그가 `embed`로 바뀐 점이라고 한다.
그 밖의 작은 변화로 `string` 태그가 더는 재귀적으로 적용되지 않고(다른 태그와
일관되게),
`format` 태그가 제거되었으며(더 나은 문법으로 되살리려는 이슈가 있다),
`jsontext` 보조 함수가 오류를 돌려줄 수 있게 바뀌었다(예:
`jsontext.Token.Int`)는 것이다.[^prattmic]
이 변화 목록은 원문에 없고, 실험판을 이미 써 본 사람이 확인할 항목이다.

같은 스레드에서 xilef는 JSON을 많이 쓰는 서비스 묶음을 v2로 옮겼고 매끄러웠으며,
걸린 것은 생성된 JSON에 줄바꿈이 없다는 점 하나였는데 테스트를 다시 점검하게
해서 나쁘지
않았다고 보고했다.[^xilef]
이는 한 사람의 이전 보고이고 통제된 비교가 아니다.

GeekNews의 click은 encoding/xml도 같은 문제가 있어 `encoding/xml/v2`를 만들고 싶지만,
Go 이슈에서는 아무도 관심이 없는 것 같아 잘 진행될지 모르겠다고 적었다.[^click]

## 비평

### nil을 빈 배열로 내보내는 기본값은 왕복 변환(round trip)을 보장하지 않는다

글은 nil 슬라이스와 맵을 `null`이 아니라 빈 배열과 빈 객체로 내보내는
변경의 근거로 설문을 든다.
설문은 대부분의 Go 사용자가 그 기본값을 선호한다고 나왔다는 것이다.
그런데 글은 이 변경이 무엇을 잃는지는 말하지 않는다.

HN에서 `SkiFire13`은 이 기본값이 여러 사람에게 문제를 일으켜
결국 v3에서 고쳐야 할 것이라고 예측했다.[^SkiFire13]
`Someone`이 그 이유를 구체적으로 짚었다.
nil과 빈 슬라이스가 같은 JSON 문자열로 나가면
모든 객체가 마샬링과 언마샬링을 거쳐 원래대로 돌아오지는 못한다는
것이다.[^Someone]
이는 선호 조사로 풀리지 않는 성질의 문제다.
설문은 어느 출력을 보고 싶은지를 묻지만,
왕복 변환의 보존은 데이터를 다시 읽는 쪽에서만 문제가 되기 때문이다.

반대 의견도 설득력이 있다.
`throwaway894345`는 Go에서 nil 슬라이스를 빈 슬라이스와
똑같이 다루고 싶은 경우가 거의 전부이고,
JSON v1이 거의 유일하게 그렇게 동작하지 않아 잦은 버그를 냈다고
적었다.[^throwaway894345]
두 주장은 양립한다.
Go 코드의 관례에서는 v2의 기본값이 맞고,
데이터를 정확히 보존해야 하는 경로에서는 틀릴 수 있다.
글이 이 구분을 하지 않은 것은 빠진 부분이며,
설문이 어느 집단을 대표하는지도 글에는 없다.
글은 대부분의 동작 변경을 구조체 태그나 호출 옵션으로 되돌릴 수 있다고 말한다.
그러나 nil 처리가 그 안에 드는지와 어떤 옵션인지는
이 글에 적혀 있지 않아 확인하지 못했다.

### 엄격한 기본값이 곧 상호운용성이라는 전제는 논쟁적이다

글은 디코더가 점차 엄격해지는 추세를 상호운용성(interoperability)의
근거로 삼아 잘못된 UTF-8과 중복 이름을 오류로 바꾼다.
같은 JSON을 두 구현이 다르게 해석하는 일을 줄이려는 것이고,
중복 이름은 보안 응용에서 악용된 적이 있다고 적는다.

HN에서 `layer8`은 이 전제의 허점을 짚었다.
중복 키가 있는 JSON도 유효하고 표준이 처리 방법을 둘로 열어 두었으므로,
모든 쓰임을 지원하려면 둘 다 제공하고 기본값을 골라야 하는데,
파싱에서 더 엄격한 기본값은 동시에 덜 호환적이라는 것이다.
숫자 정밀도에도 같은 양면이 있어,
생성 쪽에서 높은 정밀도를 허용하면 받는 쪽과의 상호운용성이 떨어지고
파싱 쪽에서 받아들이면 올라간다고 설명했다.[^layer8]
이 비평은 글의 결론을 뒤집지는 않는다.
v2가 옵션으로 두 쪽을 모두 제공하기 때문이다.
그러나 엄격함이 안전하다는 주장은
무엇을 기준으로 안전한지를 밝혀야 한다는 점을 보여 준다.
글에서 안전은 보안 악용 가능성을 뜻하고,
상호운용성과는 다른 척도다.

### 편의 함수가 사라지는 비용은 마이그레이션 문서가 다룰 몫이다

글은 v1 사용이 v2로 바로 옮겨져도 대체로 같게 동작하는 것을 목표로 삼는다.
HN에서 `CamouflagedKiwi`는 v2를 좋아하지만
`MarshalIndent`가 빠진 점이 아쉽다고 했다.
동등한 코드가 복잡하고 직관적이지 않아 이식이 번거롭고,
빠르게 읽기 좋은 JSON을 뽑아 보고 싶을 때도 불편하다는 것이다.[^CamouflagedKiwi]
답글에서 `arccy`는 `json.Marshal(v, jsontext.WithIndent(" "))`를
제시했다.[^arccy]
`arccy`의 답이 맞다면 대체 방법은 한 줄이다.
그렇다면 문제는 기능의 부재보다 발견하기 어려움과
함수 하나가 옵션 조합으로 바뀐 데서 오는 이식 비용이다.

글은 이 종류의 이식 비용을 짧게만 다룬다.
마이그레이션 가이드로 안내하고,
v1 동작의 차이를 옵션과 대응시킨 문서를 가리킬 뿐이다.
저자들이 목표로 삼은 대체로 같은 동작이 실제로 얼마나 같은지는
이 글만으로는 가늠할 수 없다.

## 인사이트

### v1 호환 옵션의 집합이 v1 동작의 명세로 남는다

v1을 v2의 옵션 조합으로 구현하면 이득이 크지만,
이것은 글이 말하지 않는 귀결을 낳는다.
v1에서 고칠 수 없던 동작이 이제 이름 붙은 옵션이 되어 v2에 영구히 남는다.
v2의 API는 v1 호환 옵션들을 계속 지원해야 하고,
그 옵션 집합이 v1 동작을 정의하는 가장 정확한 명세가 된다.
이 해석은 글이 직접 말한 것이 아니라 글의 구조에서 내가 끌어낸 추론이다.

이 구조에서는 결함이 사라지지 않고 선택 사항이 된다.
v2를 쓰는 코드는 그 동작을 피할 수 있지만,
v1을 쓰는 코드는 여전히 그 동작을 가진다.
저자들이 v1은 무기한 지원되고 이식이 필요 없다고 말한 만큼
이는 의도된 결과다.
다만 그 때문에 JSON을 다루는 Go 코드의 안전 기본값이
두 갈래로 나뉜다.
중복 이름을 거부하는 코드와 허용하는 코드가 같은 언어 안에 공존하고,
어느 쪽인지는 import 경로와 옵션을 읽어야 안다.

### 구현을 공유하는 호환 방식은 v1과 v2를 섞어 쓰는 시기를 만든다

HN에서 `thiht`는 `math/rand/v2`가 2024년 Go 1.22에서 추가됐다고
짚었다.[^thiht]
표준 라이브러리에서 패키지의 v2를 새 import 경로로 두는 방식은
그 전에도 있었다는 뜻이다.
이 글은 거기에 더해 두 버전이 구현을 공유하게 만들어,
의존 패키지들이 서로 다른 버전을 쓰는 시기에도
함께 동작하게 한다.
저자들이 말한 생태계 전체의 매끄러운 이식은 이 상호 호환을 가리킨다.
`math/rand/v2`가 구현을 공유하는지는 열어 보지 않아 알지 못한다.

이 방식은 한 가지 조건이 있다.
v2의 모든 동작 차이를 옵션으로 표현할 수 있어야 한다.
JSON 패키지는 동작 차이가 열거 가능해서 이 조건을 만족하지만,
모든 표준 라이브러리 패키지가 그렇지는 않다.
다른 패키지가 같은 방식을 따르려면
먼저 동작 차이를 옵션으로 쪼갤 수 있는지부터 확인해야 한다.
이는 이 글에서 다른 패키지로 옮겨 가는 방법에 대한 내 판단이다.

### 구문 층 jsontext는 독립된 도구로도 쓰인다

글은 `jsontext`를 `json/v2`의 토대로 소개하지만,
이 층은 리플렉션 없이 토큰만 읽고 쓰는 파서로도 쓸 수 있다.
HN에서 `txomon`은 까다로운 고객의 입력을 받는 파서를 만들며
각 실수 종류별로 구체적인 오류를 내야 했는데,
`jsontext`로 성능을 지키면서 만들었다고 했다.
그는 리플렉션이 없어 속도가 아주 좋고,
단순하지 않은 파싱에는 이 패키지를 추천한다고 적었다.[^txomon]

이 사례는 글이 놓친 쓰임을 보여 준다.
글은 `jsontext`를 의미 층의 하부로만 설명하지만,
오류 위치와 종류를 세밀하게 다루는 입력 검증기처럼
Go 값으로 바꾸지 않는 JSON 처리에서 독립적인 가치가 있다.
이는 한 사용자의 보고이므로 일반화하려면 더 많은 사례가 필요하다.

### v2에서 빠진 API는 원문의 목록에 없고 사용자 보고로 드러난다

글은 v2의 동작 변경을 나열하지만 제거된 API는 다루지 않는다.
HN에서 `ncruces`는 v1의 `json.Number`가 거의 쓰이지 않아
v2에서 빠졌다고 했다.
그러면서도 아직 쓸 수 있고, 자신은 이를 바탕으로
작은 십진수 라이브러리를 만들었다고 덧붙였다.[^ncruces]
원문의 동작 변경 목록에는 이 제거가 나오지 않는다.
v2로 이식하려는 사람은 그 목록을 읽는 데서 그치지 않고
쓰는 API가 남아 있는지 직접 확인해야 한다.
이 문서는 원문과 댓글에서 읽은 범위에서만 말하며,
`json.Number`의 v2 상태를 별도로 확인하지 않았다.
