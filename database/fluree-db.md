# Fluree DB: 시간 여행과 브랜치와 삼중항 단위 접근 제어를 갖춘 그래프 데이터베이스

<https://fluree.github.io/db/>

<https://github.com/fluree/db>

## 소개

Rust로 쓰인 그래프 데이터베이스다.
저장소 설명은 한 줄로 시작한다.
중요한 데이터를 위한 그래프 데이터베이스라는 것이다.

내세우는 성질을 한 문장에 몰아 담는다.
시간적이고, 검증 가능하고, 표준을 따르고, git 같은 브랜치와 병합이 되며, AI 에이전트에 최적화되어 있다는 것이다.
벡터와 텍스트와 지리 검색이 통합되어 있고,
외부 의존성 없이 세밀한 접근 제어를 한다고 적는다.

질의 언어를 넷 지원한다.
RDF 1.1과 1.2 위에서 SPARQL과 JSON-LD와 openCypher를 받으며,
이력 질의를 비롯한 자체 확장도 포함한다.
README가 세 언어로 같은 질의를 보여 준 뒤 한 문장으로 정리한다.
셋 다 같은 엔진으로 컴파일되므로 같은 기능과 같은 성능을 낸다는 것이다.

규모에 대한 주장도 구체적이다.
평범한 하드웨어에서 수십억 개의 그래프 사실을 다루고 초당 200만 사실 이상을 일괄 적재한다는 것이다.
215억 삼중항 규모의 공개 데이터 덤프에서
850개 그래프 패턴 질의를 전부 완료하며 기하평균 43밀리초를 기록했고,
81.9억 삼중항 판본에서는 다음으로 빠른 엔진이 10.4배 느리다고 적는다.
그리고 재현 가능한 비교 벤치마크 저장소를 따로 링크한다.

라이선스는 Business Source License 1.1이며
지정된 시점에 Apache License 2.0으로 바뀐다고 명시한다.
별 460개에 열린 이슈 177개이고, 2020년 10월에 만들어졌다.

CLI에 딸린 두 기능도 눈에 띄는 자리에 배치되어 있다.
하나는 AI 코딩 도구를 위한 영속 기억이다.
사실과 결정과 선호가 세션을 넘어 자기가 통제하는 원장에 남으며,
저장소 단위나 사용자 단위로 범위를 정하고 git으로 공유할 수 있다고 적는다.
다른 하나는 비정형 문서 수집이다.
PDF와 사무 문서와 마크다운과 스캔본을 넣으면
구조와 조각과 임베딩을 담은 검색 가능하고 인용 가능한 그래프가 나온다는 것이며,
기본적으로 결정적이고 오프라인으로 동작한다고 밝힌다.

## 60초 예제

README의 시작 예제가 이 도구의 사용 모양을 그대로 보여 준다.

```bash
fluree init
fluree create movies

fluree insert '
@prefix schema: <http://schema.org/> .
@prefix ex:     <http://example.org/> .

ex:blade-runner  a schema:Movie ;
  schema:name        "Blade Runner" ;
  schema:dateCreated "1982-06-25"^^<http://www.w3.org/2001/XMLSchema#date> ;
  schema:director    ex:ridley-scott .

ex:ridley-scott  a schema:Person ;
  schema:name "Ridley Scott" .
'

fluree query --format table 'SELECT ?title ?date WHERE {
  ?movie a <http://schema.org/Movie> ;
         <http://schema.org/name> ?title ;
         <http://schema.org/dateCreated> ?date .
} ORDER BY ?date'
```

같은 질의를 JSON-LD로도 쓸 수 있고, Cypher로도 쓸 수 있다.
Cypher의 경우 맨 레이블과 속성이 원장의 기본 문맥을 통해 해석되므로
먼저 어휘를 가리켜 두어야 한다고 적는다.

```bash
fluree context set movies -e '{"@vocab": "http://schema.org/"}'

fluree query --cypher -e 'MATCH (m:Movie)
  RETURN m.name AS title, m.dateCreated AS date
  ORDER BY date'
```

## 시간 여행

모든 트랜잭션이 불변이며, 어느 시점의 데이터든 질의할 수 있다고 적는다.
지정 방식은 세 가지다.
트랜잭션 번호, ISO-8601 시각, 내용 주소 방식의 커밋 식별자다.

```bash
# 특정 시각 기준으로 본다
fluree query --at 2024-06-15T00:00:00Z 'SELECT * WHERE { ?s ?p ?o }'

# 트랜잭션 번호로 그 시점의 상태를 본다
fluree query --at 1 'SELECT ?title ?genre WHERE {
  ?movie a <http://schema.org/Movie> ;
         <http://schema.org/name> ?title .
  OPTIONAL { ?movie <http://schema.org/genre> ?genre }
}'
```

특별한 테이블도 없고 느리게 변하는 차원 설계도 없으며 저장 모형에 내장되어 있다는 것이 주장이다.

## 브랜치와 병합

코드에 쓰는 흐름을 데이터에 그대로 적용한다고 적는다.
브랜치와 리베이스와 병합과 푸시와 풀이 있고, 브랜치마다 독립된 커밋 이력을 갖는다.

```bash
fluree branch create experiment
fluree use mydb:experiment
# 프로덕션에 영향을 주지 않고 실험한다

fluree branch rebase experiment    # 상류 변경을 따라잡는다
fluree branch merge experiment     # main으로 빨리 감기 병합
fluree branch drop experiment      # 정리
```

## 엣지 주석

관계 자체에 속성을 붙일 수 있다는 것이 별도 기능으로 제시된다.
노드가 아니라 `worksFor` 같은 엣지에 역할과 시작 연도를 붙이거나,
주장에 출처와 확신도를 붙이는 식이다.
RDF 1.2와 SPARQL 1.2의 주석 문법을 구현했으므로
레이블 달린 속성 그래프의 엣지와
같은 두 노드 사이의 병렬 관계와 문장 단위 출처 표기를 한 표면에서 얻는다고 적는다.

```sparql
# Alice나 Acme가 아니라 엣지 자체에 메타데이터를 붙인다
INSERT DATA {
  ex:alice ex:worksFor ex:acme {| ex:role "Engineer" ; ex:since 2024 |} .
}

# 엣지와 그 메타데이터를 함께 맞춘다
SELECT ?role ?since WHERE {
  ex:alice ex:worksFor ex:acme {| ex:role ?role ; ex:since ?since |} .
}
```

중요한 단서가 붙는다.
평범한 삼중항 질의는 그대로 두며, 주석은 요청할 때만 카디널리티를 바꾼다는 것이다.

## 그 밖의 기능

| 항목          | 내용                                                                            |
| ------------- | ------------------------------------------------------------------------------- |
| 통합 검색     | BM25 전문 검색과 HNSW 벡터 유사도가 질의 엔진에 내장되어 조인과 필터에 참여한다 |
| 접근 제어     | 정책이 원장 안의 데이터이며 질의와 트랜잭션 시점에 삼중항 단위로 적용된다       |
| 추론          | RDFS 하위 클래스와 하위 속성, OWL 2 RL 전방 연쇄, 사용자 정의 Datalog 규칙      |
| 검증          | SHACL 형상 제약을 트랜잭션 시점에 대상별과 속성별로 보고한다                    |
| 외부 데이터원 | Apache Iceberg와 R2RML 관계형 매핑을 일급 그래프 원본으로 다룬다                |
| 저장 백엔드   | 메모리, 파일, 클라우드 객체 저장소와 키값 저장소, IPFS                          |
| 검증 가능성   | JWS로 서명한 트랜잭션과 검증 가능한 자격 증명                                   |
| 관측 가능성   | OpenTelemetry 추적과 구조화 로깅                                                |

표준 준수도 강조한다.
W3C 시험 묶음에 대해 SPARQL 1.1 적합성 실패가 0건이며,
두 질의 언어가 같은 엔진에 접근해 시간 여행과 정책과 그래프 원본을 똑같이 쓸 수 있다는 것이다.

## 쓰는 방법

네 가지 형태가 제시된다.

```bash
# 1) CLI — 탐색과 파이프라인 스크립트
fluree query -f report.rq --format csv > output.csv

# 2) HTTP 서버 — OIDC 인증과 콘텐츠 협상을 갖춘 운영 API
fluree server run
curl -X POST http://localhost:8090/v1/fluree/query?ledger=mydb:main \
  -H "Content-Type: application/sparql-query" \
  -d 'SELECT ?s ?p ?o WHERE { ?s ?p ?o } LIMIT 10'

# 3) MCP 서버 — AI 도구에 노출
fluree mcp serve
```

Rust 라이브러리로 직접 넣을 수도 있으며 별도 서버 프로세스가 필요 없다.

```rust
let fluree = FlureeBuilder::memory().build_memory();
fluree.create_ledger("mydb").await?;

let result = fluree.graph("mydb:main")
    .query()
    .sparql("SELECT ?s WHERE { ?s a <http://schema.org/Person> }")
    .execute()
    .await?;
```

설치는 Docker 이미지와 Homebrew, 셸 설치 스크립트, Windows PowerShell 스크립트를 제공한다.

문서를 `llms.txt` 관례에 따라 기계가 읽을 수 있는 형태로도 내놓는다고 밝힌다.
선별 색인과 전체 말뭉치 두 가지다.

## 분석

### 이 프로젝트는 기능 목록이 아니라 통합을 판다

README를 읽으면 기능이 아주 많다.
네 개의 질의 언어, 시간 여행, 브랜치, 전문 검색, 벡터 검색, 지리 질의,
추론, 정책, 형상 검증, 외부 데이터원 연결이다.
보통 이 정도 목록은 초점 없음의 신호로 읽힌다.

그런데 이 문서가 반복해서 강조하는 것은 목록이 아니라 그것들이 한 엔진 안에 있다는 점이다.
세 질의 언어가 같은 엔진으로 컴파일된다는 문장,
검색 결과가 다른 그래프 패턴과 똑같이 조인과 필터와 집계에 참여한다는 문장,
정책이 별도 계층이 아니라 원장 안의 데이터라는 문장이 전부 같은 주장이다.

이 주장이 겨냥하는 것은 일반적인 구성의 비용이다.
그래프 데이터베이스에 검색 엔진을 붙이고 벡터 저장소를 붙이고
접근 제어를 애플리케이션 계층에 두는 구성에서는
각 경계마다 동기화와 일관성 문제가 생긴다.
검색 결과를 그래프 질의와 합치려면 애플리케이션이 두 번 질의해 조인해야 하고,
그 조인은 데이터베이스의 최적화기를 거치지 않는다.

그래서 이 프로젝트의 실제 제안은 기능이 많다는 것이 아니라 경계를 없앴다는 것이다.
그리고 그 제안이 값을 갖는지는 사용자가 실제로 그 경계를 넘나드는 질의를 하느냐에 달려 있다.

### 성능 주장을 재현 가능한 형태로 내놓은 것이 이 문서의 강점이다

이런 문서에서 성능 수치는 대개 검증할 수 없는 형태로 제시된다.
그런데 이 README는 세 가지를 함께 제공한다.
경쟁 엔진의 이름을 구체적으로 나열하고,
질의 수와 데이터 규모와 인스턴스 종류를 밝히고,
고정된 데이터셋과 엔진별 설정과 전체 결과를 담은 벤치마크 저장소를 링크한다.

그리고 통과한 질의 수를 함께 싣는다.
어떤 엔진이 105개 중 3개만 통과했다는 표는
기하평균 수치보다 많은 것을 말해 준다.
느린 것과 못 하는 것을 구분해 주기 때문이다.

성능 문서에 현재 한계에 대한 솔직한 서술이 있다고 명시한 것도 같은 성격이다.
실제 내용은 이 문서 밖에 있으므로 확인할 수 없지만,
그런 절을 두었다고 밝히는 것 자체가 검증을 권하는 태도다.

### AI 에이전트를 향한 배치가 구조에서 나온다

첫 문장에 AI 에이전트에 최적화되었다는 말이 들어 있고,
CLI 기능 두 개가 그쪽을 겨냥하며, MCP 서버와 `llms.txt`가 제공된다.
이것만 보면 유행을 좇은 배치로 읽힐 수 있다.

그런데 이 데이터베이스의 기본 성질이 그 용도와 실제로 맞물리는 지점이 있다.
시간 여행은 에이전트가 무엇을 언제 바꿨는지 되짚게 해 주고,
브랜치는 에이전트에게 격리된 작업 공간을 주며,
삼중항 단위 정책은 에이전트가 볼 수 있는 사실의 범위를 데이터 계층에서 제한한다.
서명된 트랜잭션은 어떤 주체가 그 사실을 넣었는지를 남긴다.

즉 이 조합은 사람이 쓰는 데이터베이스에서는 과한 기능일 수 있는데,
자동화된 주체가 자율적으로 쓰는 데이터베이스에서는 감사와 격리의 기본 요건이 된다.
이 문서가 그 논증을 명시적으로 하지는 않지만, 기능 배치가 그 방향을 가리킨다.

## 비평

### 벤치마크가 유리한 축만 보여 준다

제시된 비교는 두 묶음이다.
SPARQL 계열 엔진들과의 질의 지연 비교, 그리고 속성 그래프 엔진들과의 쓰기와 읽기 지연 비교다.

두 표 모두 지연의 기하평균과 평균을 쓴다.
그런데 데이터베이스 선택에서 실제로 문제가 되는 것은 꼬리 분포인 경우가 많다.
상위 99백분위 지연이나 동시 부하에서의 성능은 제시되지 않는다.

그리고 쓰기 비교에서 내구성 있는 쓰기라는 점을 강조하는데,
비교 대상들이 같은 조건에서 측정되었는지는 표만으로 알 수 없다.
내구성 설정은 엔진마다 기본값이 다르고 그 차이가 지연에 직결되므로,
이 항목이야말로 각주가 필요한 자리다.
README는 재현 저장소를 링크하는 것으로 그 설명을 대신한다.

또한 적재 성능과 질의 성능은 있는데 갱신 성능이 없다.
모든 트랜잭션이 불변이고 이력이 보존되는 구조에서는
잦은 갱신이 저장 공간과 인덱스에 어떤 부담을 주는지가 핵심 질문이 되는데,
그 축의 수치가 이 문서에 없다.

### 불변 저장의 비용이 서술되지 않는다

시간 여행 절은 이득만 서술한다.
특별한 테이블이 필요 없고 저장 모형에 내장되어 있다는 것이다.

그런데 모든 변경이 보존된다는 것은 저장 공간이 단조 증가한다는 뜻이다.
자주 바뀌는 값이 많은 작업 부하에서 이것이 어떻게 되는지,
오래된 이력을 잘라 내는 방법이 있는지,
잘라 내면 그 시점 이전의 질의가 어떻게 되는지가 README에 없다.

같은 질문이 규정 준수 쪽에서도 생긴다.
개인 정보를 다루는 체계에서는 삭제 요구를 이행해야 하는데,
모든 트랜잭션이 불변이면 그 요구를 어떻게 충족하는지가 설계상의 난점이 된다.
이 데이터베이스가 검증 가능성과 서명을 내세우므로 더욱 그렇다.
이력을 지우면 검증 사슬이 어떻게 되는지가 답해져야 할 질문이다.

브랜치 기능도 같은 성질을 공유한다.
브랜치마다 독립된 커밋 이력을 갖는다면 브랜치가 늘어날수록 저장이 늘고,
병합 시 충돌이 생기면 어떻게 되는지가 서술되어 있지 않다.
git의 비유를 쓰면 독자는 git의 충돌 해결을 떠올리는데,
데이터에서의 충돌은 같은 사실에 대한 서로 다른 주장이므로 해결 방식이 다를 수밖에 없다.
`merge` 명령의 예제에 빨리 감기 병합이라고 적혀 있는 것이
충돌이 있는 경우가 다뤄지지 않았음을 시사한다.

### 라이선스가 오픈소스로 읽히기 쉬운 자리에 있다

이 저장소는 Business Source License 1.1을 쓴다.
지정된 시점에 Apache 2.0으로 바뀐다는 조항이 붙어 있다.

이 라이선스는 소스가 공개되지만 오픈소스 정의를 만족하지 않는다.
사용 범위에 제한이 있고, 그 제한이 해제되는 시점이 판본마다 따로 정해진다.

README는 이 사실을 문서 맨 끝의 한 줄로 적는다.
그런데 문서 전체는 설치와 임베딩과 자체 운영을 전제로 쓰여 있고,
Rust 라이브러리로 직접 넣을 수 있다는 항목까지 있다.
그렇게 읽고 내려온 독자가 마지막 줄에서야 제약을 만난다.

이 배치가 의도적인지는 알 수 없지만 결과는 분명하다.
경쟁 제품으로 쓰는 것이 허용되는지, 사내 서비스에 넣는 것은 되는지,
변경 시점이 각 판본마다 언제인지를 라이선스 원문에서 직접 확인해야 하며,
그 확인 없이 도입 결정을 내리면 나중에 되돌리기 어렵다.

### 대안 대비 위치가 제시되지 않는다

이 README는 성능에서 경쟁 엔진을 명시적으로 지목하는데,
기능 선택에서는 그렇게 하지 않는다.

독자가 실제로 묻게 되는 질문은 이런 것이다.
이력이 필요하면 관계형 데이터베이스에 감사 테이블을 두는 것과 무엇이 다른가,
그래프 질의가 필요하면 기존 그래프 데이터베이스에 검색을 붙이는 것과 무엇이 다른가,
RDF 생태계를 쓸 것이면 성숙한 삼중항 저장소와 무엇이 다른가다.

성능 표가 마지막 질문에는 부분적으로 답한다.
그런데 앞의 두 질문에는 답이 없고,
기능이 많다는 사실이 곧 다른 구성보다 낫다는 결론으로 이어지지는 않는다.
특히 RDF와 SPARQL을 중심에 두는 선택은 그 자체로 학습 비용이 크고,
관계형이나 속성 그래프에 익숙한 팀에게는 그것이 도입의 가장 큰 장벽이다.
README가 관계형 개발자를 위한 문서를 따로 링크하는 것이
그 장벽을 인지하고 있다는 신호이기는 하다.

## 인사이트

### 감사 가능성은 뒤에 붙이면 비싸고 바닥에 두면 싸다

이 데이터베이스의 설계 선택 가운데 가장 이식성 높은 것은
이력과 출처와 접근 제어를 애플리케이션이 아니라 저장 계층에 둔 것이다.

이 위치 선택의 값은 평소에 보이지 않다가 두 상황에서 드러난다.
사고 조사와 규정 대응이다.
누가 언제 무엇을 바꿨는지를 애플리케이션 로그로 재구성하려면
로그가 빠짐없이 남아 있어야 하고, 로그와 데이터의 시점이 맞아야 하며,
그 둘을 잇는 식별자가 일관되어야 한다.
이 셋 중 하나만 어긋나도 재구성이 불가능해진다.

반면 저장 계층이 이력을 갖고 있으면 그 재구성이 질의 하나가 된다.
이 README의 `--at` 예제가 보여 주는 것이 정확히 그것이다.

여기서 나오는 판단 기준이 있다.
어떤 체계를 설계할 때 감사 요구가 있을 가능성을 먼저 세고,
있다면 그 기능이 어느 계층에 있어야 하는지를 정하는 것이다.
나중에 붙이는 것은 언제나 가능하지만,
나중에 붙인 감사는 붙인 시점 이후만 답할 수 있다.
그리고 감사가 필요해지는 시점은 대개 그 이전에 무슨 일이 있었는지를 묻는 순간이다.

### 자율 에이전트가 쓰는 데이터 저장소에는 다른 요구 사항이 생긴다

이 프로젝트가 AI 에이전트를 앞세우는 것이 마케팅으로만 읽히지 않는 이유가 있다.
에이전트가 데이터를 직접 쓰기 시작하면 요구 사항의 구성이 바뀐다.

사람이 쓰는 체계에서는 실수가 드물고, 드물기 때문에 사후 복구로 충분하다.
에이전트가 쓰는 체계에서는 시도 횟수가 몇 자릿수 많아지므로
잘못된 쓰기가 드문 사건이 아니라 상시 조건이 된다.
그러면 세 가지가 필요해진다.
되돌릴 수 있을 것, 격리된 공간에서 시도할 수 있을 것,
그리고 각 사실이 누구에게서 왔는지 남을 것이다.

이 README가 내세우는 시간 여행과 브랜치와 서명된 트랜잭션이 정확히 그 셋이다.
그리고 이 셋은 전부 사람이 쓰는 체계에서는 과한 기능으로 분류되던 것들이다.

여기서 일반화할 수 있는 관찰이 있다.
자동화의 비율이 올라가면 안전 장치의 비용 대비 효용이 뒤집힌다는 것이다.
전에는 비싸서 쓰지 않던 기능이 시도 횟수가 늘면 값이 매겨진다.
같은 논리가 격리된 실행 환경, 자동 롤백, 변경 이력 보존에 모두 적용되며,
에이전트 도입을 검토하는 조직이 도구보다 먼저 봐야 할 항목이 이쪽이다.

### 여러 질의 언어를 한 엔진에 올리는 선택에는 숨은 비용이 있다

세 언어가 같은 엔진으로 컴파일되어 같은 기능과 성능을 낸다는 주장은 강력하고,
사실이라면 도입 장벽을 크게 낮춘다.
기존 팀이 아는 언어로 시작해 점진적으로 옮길 수 있기 때문이다.

그런데 이 설계에는 잘 드러나지 않는 비용이 있다.
언어마다 의미론이 조금씩 다르다는 것이다.
속성 그래프의 질의 언어는 노드와 엣지를 일급으로 두고,
RDF 계열은 모든 것을 삼중항으로 둔다.
두 모형 사이의 사상은 완전하지 않으며, 그 틈이 경계 사례에서 드러난다.

이 README가 그 틈을 한 군데 보여 준다.
Cypher에서 맨 레이블과 속성이 원장의 기본 문맥을 통해 해석되므로
먼저 어휘를 가리켜 두어야 한다는 설명이다.
사용자 입장에서 이것은 같은 언어가 아니라 그 언어의 방언을 쓰는 것이다.

그래서 이런 다중 언어 지원을 평가할 때 물어야 할 것이 정해진다.
내가 쓰던 언어의 코드를 그대로 옮길 수 있는지가 아니라,
내가 쓰던 언어의 관용 표현 중 무엇이 동작하지 않는지다.
그리고 그 목록은 대개 문서의 호환성 절에 있고, 홍보 문구에는 없다.

### 벤치마크에 통과한 질의 수를 함께 싣는 관행은 더 퍼져야 한다

이 README의 성능 표에서 가장 유용한 줄은 지연이 아니라 통과 질의 수다.
105개 중 몇 개를 처리했는지를 각 엔진에 대해 적어 두었다.

이 숫자가 없으면 평균 지연이 오해를 만든다.
어려운 질의를 실패로 처리하고 쉬운 것만 센 엔진이 빨라 보이기 때문이다.
그리고 그 실패가 시간 초과인지 기능 부재인지에 따라 의미가 또 달라진다.

이 관행은 데이터베이스 벤치마크 바깥에도 적용된다.
모델 평가에서 점수만 보고 응답 실패율을 보지 않는 것,
부하 시험에서 처리량만 보고 오류율을 보지 않는 것이 같은 구조의 누락이다.

그래서 남이 만든 벤치마크를 읽을 때 첫 질문이 정해진다.
분모가 무엇이며 실패한 항목이 분모에 포함되어 있느냐다.
포함되지 않았다면 그 수치는 성능이 아니라 성공한 경우의 성능이고,
두 값은 완전히 다른 결정을 이끈다.
