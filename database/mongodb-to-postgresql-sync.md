# MongoDB를 PostgreSQL로 동기화할 때 진짜 어려운 것은 스키마 매핑이다

원문: [How to Copy and Sync a MongoDB Collection to PostgreSQL](https://visualeaf.com/blog/copy-and-sync-a-mongodb-collection-to-postgresql/)

HN 토론: <https://news.ycombinator.com/item?id=49081275> (3점, 0개 댓글)

GN 토론: <https://news.hada.io/topic?id=33219>

## 요약

VisuaLeaf에서 일하는 Roxana-Maria Haidiner가 2026년 7월
27일에 쓴 글이다.
MongoDB 컬렉션을 PostgreSQL로 복사한 뒤, 이후 발생하는
추가·수정·삭제까지 계속 동기화해 본 과정을 정리했다.

지속적인 동기화는 MongoDB의 체인지 스트림(change stream)을
사용하는데, 체인지 스트림은 레플리카 셋과 샤드 클러스터에서만
동작하고 단일 인스턴스(standalone) MongoDB에서는 동작하지
않는다는 전제 조건이 있다.

실제로 해 보니 동기화 자체보다 MongoDB 문서 구조를 PostgreSQL
테이블에 맞게 매핑하는 과정이 더 까다로웠다.
MongoDB 문서는 문자열, 날짜, 중첩된 객체, 배열, `_id`로
구성되는 반면, PostgreSQL은 고정된 컬럼, 명확한 데이터
타입, 기본 키를 요구한다.
저자는 `database_compare_demo.visits`라는 테스트 컬렉션(중첩
필드 9개, 단순 필드 5개)을 대상으로 다음과 같은 테이블을
만들었다.

```sql
CREATE TABLE public.mongo_visits_sync (
    mongo_id TEXT PRIMARY KEY,
    visit_id TEXT,
    status TEXT,
    visit_date TIMESTAMPTZ,
    visit_reason TEXT,
    patient JSONB,
    doctor JSONB,
    symptoms JSONB,
    prescriptions JSONB,
    invoice JSONB,
    lab_results JSONB,
    visit_details JSONB,
    vitals JSONB,
    clinic JSONB
);
```

단순한 필드는 일반 컬럼으로 저장하고, 중첩된 객체와 배열은
JSONB로 유지했다.
MongoDB의 `_id`는 PostgreSQL의 `mongo_id` 컬럼에 기본 키로
매핑했다.

과정에서 두 가지 오류를 만났다.
첫째, 기본 키 컬럼이 없어 “멱등적으로 upsert할 수 없다”는
오류가 발생해 동기화가 중단됐다.
둘째, MongoDB 필드명(camelCase)과 PostgreSQL 컬럼명
(snake_case)이 달라 발생한 불일치 오류다.
매핑을 수정한 뒤에는 추가, 수정, 삭제가 PostgreSQL에 정상적으로
반영되는지 각각 확인했다.
이 모든 과정에는 필드 매핑을 시각적으로 구성하고 동기화 상태를
모니터링할 수 있는 VisuaLeaf Mongo Sync 도구를 사용했다.

## 분석

### 동기화 메커니즘이 아니라 스키마 철학의 충돌이 진짜 난제다

이 글의 제목은 “복사하고 동기화하기”라는 절차를 내세우지만,
실제 내용의 무게중심은 동기화 메커니즘(체인지 스트림 구독,
upsert 로직)이 아니라 두 데이터베이스가 세계를 구조화하는
방식의 근본적 차이에 있다.
MongoDB는 스키마리스(schemaless) 문서 모델을 전제하고,
PostgreSQL은 고정된 컬럼과 타입을 전제한다.
저자가 겪은 실질적 어려움(중첩 객체를 어떻게 저장할지, 기본
키를 어떻게 확보할지)은 모두 이 철학적 차이가 구체적인 기술적
문제로 발현된 사례들이다.
즉 이 글이 보여주는 것은 “동기화 도구를 쓰는 법”이 아니라
“스키마리스와 스키마풀(schemaful) 사이의 임피던스 불일치를
어떻게 다루는가”라는 더 근본적인 문제다.

### JSONB로의 도피가 매핑 문제를 해결하는 것이 아니라 연기한다

중첩된 객체와 배열을 JSONB 컬럼에 그대로 밀어넣는 선택은
실용적이지만, 이는 매핑 문제를 실제로 “해결”하는 것이 아니라
PostgreSQL 쪽으로 미뤄두는 것에 가깝다.
JSONB에 저장된 데이터는 PostgreSQL의 타입 시스템이나 관계형
제약(외래 키, NOT NULL, 체크 제약)의 보호를 받지 못한다.
결과적으로 이 테이블은 겉보기에는 PostgreSQL 테이블이지만,
`patient`, `doctor`, `symptoms` 같은 핵심 데이터의 무결성
검증은 여전히 애플리케이션 계층이나 MongoDB 쪽 로직에 의존하는
반쪽짜리 관계형 테이블이 된다.

### 체인지 스트림이라는 전제 조건이 이 가이드의 적용 범위를 조용히 좁힌다

체인지 스트림이 레플리카 셋과 샤드 클러스터에서만 동작하고
단일 인스턴스 MongoDB에서는 동작하지 않는다는 사실은, 이
가이드가 처음부터 일정 규모 이상의 프로덕션 환경을 전제하고
있다는 것을 보여준다.
개발 환경이나 소규모 프로젝트에서 흔히 쓰이는 단일 인스턴스
MongoDB 사용자는 이 방법을 그대로 적용할 수 없으며, 먼저
레플리카 셋으로 전환하는 별도의 작업이 필요하다.
이 전제 조건이 본문 초반에 짧게 언급되고 넘어가는 것은, 이
가이드가 실제로 적용 가능한 독자층을 상당히 좁히고 있다는
점을 충분히 강조하지 않는 것이다.

## 비평

### 저자가 자사 제품을 사용한 사례 연구라는 이해관계가 명시되지 않는다

저자는 VisuaLeaf에서 일하며 이번 테스트에 VisuaLeaf Mongo
Sync를 사용했다고 밝히지만, 이 글이 VisuaLeaf 자사 블로그에
게시된 콘텐츠 마케팅이라는 성격은 본문 어디에서도 명시적으로
드러나지 않는다.
독자는 이 글을 “중립적인 기술 가이드”로 받아들이기 쉽지만,
실제로는 “우리 제품을 쓰면 이렇게 쉽게 할 수 있다”는 것을
보여주는 사례 연구에 가깝다.
다른 동기화 방법(예: Debezium 같은 오픈소스 CDC 도구, 직접
작성한 스크립트)과의 비교가 없다는 것도 이 해석을 뒷받침한다.

### 두 개의 오류만으로 “매핑이 더 어렵다”는 결론을 일반화하기는 이르다

저자는 기본 키 부재로 인한 upsert 실패와 필드명 케이스
불일치라는 두 가지 구체적 오류를 근거로 “매핑이 동기화 자체보다
어렵다”는 결론을 내리지만, 이 두 오류는 사실 상당히 흔하고
예측 가능한 초보적 실수에 가깝다.
진짜 어려운 매핑 문제(예: MongoDB의 다형적 스키마 — 같은
컬렉션 안에서 문서마다 필드 구성이 다른 경우, 배열 안에
배열이 중첩된 경우, 타입이 문서마다 바뀌는 경우)에 대한
사례는 다루지 않는다.
이는 이 글이 다루는 “어려움”이 실제로 프로덕션급 마이그레이션에서
마주치는 어려움의 전체 스펙트럼을 대표하지 못한다는 것을
시사한다.

### 지속적 동기화의 장애 복구 시나리오가 전혀 다뤄지지 않는다

체인지 스트림 기반의 지속적 동기화를 다루는 글이라면, 동기화
프로세스가 중단됐다가 재개될 때(네트워크 장애, 도구 재시작)
유실된 변경 사항을 어떻게 따라잡는지, resume token을 어떻게
관리하는지가 핵심적인 신뢰성 문제다.
이 글은 정상적인 추가·수정·삭제가 반영되는지 확인했다고만
밝힐 뿐, 동기화가 중단된 이후의 복구 시나리오나 데이터 일관성
보장에 대해서는 전혀 언급하지 않는다.
지속적 동기화를 프로덕션에 적용하려는 독자에게는 이 부분이야말로
가장 중요한 정보인데, 이 글은 “정상 경로(happy path)”만
보여준다.

## 인사이트

### 스키마리스-스키마풀 변환 문제는 데이터베이스 역사에서 반복되는 근본 문제의 최신 사례다

MongoDB와 PostgreSQL 사이의 이 매핑 문제는 사실 새로운
문제가 아니다.
객체-관계 매핑(ORM)이 객체지향 프로그래밍과 관계형
데이터베이스 사이의 임피던스 불일치를 다뤄온 것처럼, 문서
데이터베이스와 관계형 데이터베이스 사이에도 구조적으로 동일한
문제가 존재한다.
JSONB로의 도피는 사실 이 오래된 문제에 대한 오래된 해법(구조화되지
않은 데이터를 위한 “탈출구” 컬럼을 두는 것)의 재현이며, 이는
데이터베이스 기술이 아무리 발전해도 서로 다른 데이터 모델
사이의 근본적 임피던스 불일치는 완전히 해소되지 않고 계속
새로운 형태로 재등장한다는 것을 보여준다.

### 이런 종류의 “사용기” 콘텐츠는 벤더 블로그의 신뢰 구축 전략으로 자리 잡았다

VisuaLeaf 같은 개발자 도구 회사가 “우리 제품 홍보”가 아니라
“내가 직접 해보니 이런 문제가 있었다”는 1인칭 경험담 형식으로
콘텐츠를 만드는 것은, 전통적인 제품 소개 페이지보다 훨씬
효과적인 신뢰 구축 전략이다.
독자는 이 글을 검색 엔진이나 커뮤니티(GeekNews 같은)를 통해
“기술 문제 해결기”로 접하게 되고, 그 안에서 자연스럽게 특정
제품을 발견한다.
이는 개발자 도구 마케팅이 명시적인 광고보다 “문제를 푸는
과정에서 자연스럽게 우리 도구가 등장하는” 콘텐츠 형식으로
점점 옮겨가고 있다는 더 넓은 트렌드를 보여주며, 독자는 이런
콘텐츠를 읽을 때 그것이 사례 연구인지 순수한 문제 해결기인지
스스로 판별하는 부담을 져야 한다.

### 체인지 스트림 요구사항은 클라우드 매니지드 MongoDB로의 이전을 암묵적으로 유도한다

체인지 스트림이 레플리카 셋이나 샤드 클러스터를 요구한다는
사실은, 지속적 동기화를 원하는 조직이 결국 MongoDB Atlas
같은 매니지드 서비스로 이전하도록 유도하는 효과를 낳는다.
스스로 레플리카 셋을 구성하고 운영하는 것보다 매니지드
서비스를 쓰는 것이 훨씬 간단하기 때문이다.
이는 특정 기능(이 경우 체인지 스트림)의 기술적 요구사항이
의도했든 아니든 특정 배포 방식(셀프 호스팅에서 매니지드
서비스로)을 향한 유인을 만들어낸다는 것을 보여주며, 오픈소스
데이터베이스의 고급 기능이 결국 그 데이터베이스를 만든 회사의
클라우드 서비스로 사용자를 이끄는 통로가 되는 패턴은 여러
오픈소스 프로젝트에서 반복적으로 관찰된다.
