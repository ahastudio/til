# 래칫 쿼리로 데이터베이스 부하를 4분의 1 줄이기

원문: [Ratcheting SQL Queries: reducing a database's Load by 1/4th with a simple change](https://will-keleher.com/posts/ratcheting-sql-queries/)

## 소개

Will Keleher가 쿼리 플래너가 할 수 없는 최적화를 애플리케이션 쪽에서 하는 방법을 다룬 글이다.
글머리에 던지는 수수께끼가 이 기법의 성격을 암시한다.
마구간에 말 25마리가 있고 가장 빠른 세 마리를 찾으려 하는데 한 번에 다섯 마리만 달릴 수 있다면 몇 번을 달려야 하는가.

저자는 먼저 쿼리 플래너를 충분히 칭찬한다.
JOIN과 ORDER BY와 GROUP BY와 서브쿼리의 거의 모든 조합을
효율적으로 데이터를 찾는 계획으로 바꿔 낸다는 것이다.
그 계획은 테이블 크기, 인덱스 카디널리티, 예상 일치 행 수 같은 단순한 휴리스틱에 근거한다.

대부분의 경우 이 계획은 잘 동작한다.
가끔 조인 순서나 사용할 인덱스에 대해 플래너가 나쁜 가정을 하는데,
그럴 때는 인덱스 힌트로 방향을 잡아 줄 수 있다.
다른 경우에는 쿼리를 다시 써서 더 나은 계획을 세울 단서를 주기도 한다.

그리고 이 글의 전제가 되는 문장이 나온다.
애플리케이션의 데이터와 감수할 트레이드오프에 대해서는
우리가 쿼리 플래너보다 훨씬 많이 알고 있으므로,
플래너가 내놓는 계획과 같거나 더 나은 계획을 언제나 만들어 낼 수 있다는 것이다.

## 사례 하나: 존재 여부 확인

저자가 최적화 작업 중 발견한 가장 흔한 쿼리는
UI의 일부를 보여 줄지 정하기 위해 사용자에게 `class_post`가 하나라도 있는지 확인하는 것이었다.

```javascript
// 위험한 코드. 설명을 위한 예시일 뿐이다
const results = await Promise.all(classIds.map((classId) => {
  return runQuery(`SELECT 1 FROM class_post WHERE classId = ? LIMIT 1`, [classId]);
}));
const hasAnyEntries = results.some((rows) => rows.length > 0);
return hasAnyEntries;
```

실제 코드는 커넥션 풀을 포화시키지 않도록 동시성을 제한하는 유틸리티를 썼다고 저자는 덧붙인다.
그러면서 동시성 제어가 있어도 N + 1 쿼리 패턴은 쉽게 성능 문제가 된다고 경고한다.

여기서 당연한 질문이 나온다.
왜 `WHERE classId IN (1, 2, 3, 4, 5)` 한 방이 아닌가.
답은 실측이다.
데이터베이스가 내놓은 계획이 훨씬 느렸고 `classId`마다 질의하는 것보다 부하도 컸다.

각주에 실린 `EXPLAIN ANALYZE` 결과가 이유를 보여 준다.
`IN` 목록에 값이 하나면 커버링 인덱스 조회가 되고,
둘이면 두 조건의 OR로 인덱스 범위 스캔이 되며,
셋부터는 커버링 인덱스 전체 스캔으로 계획이 바뀐다.
저자의 로컬 시험에서는 행 하나만 필요한데 20,001행을 스캔했다.
그는 실제 경계값은 상황마다 다를 것이라면서
자기 로컬 시험이 매우 비현실적이니 반드시 실제 데이터로 시험하라고 강조한다.

### 플래너가 알 수 없는 네 가지 사실

저자가 활용한 것은 플래너가 접근할 수 없는 도메인 지식이다.

| 사실                                                           | 활용 방법                       |
| -------------------------------------------------------------- | ------------------------------- |
| 한 학급의 게시물만 있으면 확인이 끝난다                        | 첫 일치에서 즉시 반환한다       |
| 대부분의 학급이 조건을 만족한다                                | 대개 조기 종료된다              |
| 사용자 행동이 변해서 최신 학급일수록 조건을 만족할 확률이 높다 | 최신순으로 정렬해 먼저 확인한다 |
| 부하가 크게 줄면 지연이 약간 느는 것은 괜찮다                  | 병렬 대신 직렬로 돈다           |

```javascript
// 생성일 역순으로 정렬한다. 최신 학급이 조건을 만족할 확률이 높다
const sortedClassIds = _.orderBy(classIds, _.identity, ["desc"]);
for (const classId of sortedClassIds) {
  const result = await runQuery(
    `SELECT 1 FROM class_post WHERE classId = ? LIMIT 1`,
    [classId],
  );
  if (result.length) {
    return true;   // 하나만 찾으면 나머지는 볼 필요가 없다
  }
}
return false;
```

결과는 극적이었다.
16개 vCPU에서 피크 부하가 활성 세션 17.2에서 12.4로 떨어졌고, 같은 양의 요청을 처리했다.
목표가 아니었는데도 사용자 체감 성능까지 좋아졌다.

저자는 이 사례에 정직한 단서를 단다.
이것은 이 기법의 최선의 시나리오이며,
원래 코드가 전혀 최적화되지 않은 채 끊임없이 호출되고 있었다는 것이다.
정렬 없이 동시성만 제어한 조기 종료 유틸리티만 써도 큰 효과가 있었을 것이고,
어떤 `classId`에 게시물이 있는지를 저장하는 단순한 캐시로도 충분했을 것이다.
그는 여러분의 코드에 이 정도로 최적화되지 않은 부분이 없기를 바란다고 덧붙인다.

## 사례 둘: 친구 피드

같은 발상을 더 복잡한 상황에 적용한다.
배경은 2006년이고, 기계 학습도 광고도 없는 단순한 피드다.
친구들의 게시물을 시간 순으로 보여 주는 것뿐인데,
사람들이 친구를 30명 넘게 가질 줄 몰랐기에 이 질의가 정기적으로 데이터베이스를 내려앉힌다.
팀의 누구도 친구가 세 명을 넘지 않아서 성능 특성이 충격이었다는 농담이 붙는다.

```sql
SELECT *
FROM friend
JOIN post ON post.posterId = friend.toFriend
WHERE fromFriend = ?
ORDER BY post.createdAt DESC
LIMIT 30
```

이 질의는 각 친구의 최근 게시물 몇 개가 아니라 모든 친구의 모든 게시물을 스캔하기 쉽다.
이를 피하는 표준 기법은 여러 개의 질의를 UNION으로 묶고 정렬하는 것이다.

래칫 발상은 여기서 한 걸음 더 간다.
각 친구가 마지막으로 게시한 시각을 알고 있다면,
2년간 글을 쓰지 않은 친구는 이미 지난주에서 20개를 찾은 이상 확인할 필요가 없다.

```javascript
const sortedFriends = _.orderBy(friends, (friend) => friend.lastPosted, ["desc"]);
const LIMIT = 20;
let results = [];
for (const friend of sortedFriends) {
  // 이 친구의 마지막 게시 시각보다 뒤인 게시물은 최종 결과에 반드시 포함된다
  const winningPosts = results.filter((post) => post.postedAt > friend.lastPosted);

  // 확정된 게시물만으로 정원이 찼으면 남은 친구는 볼 필요가 없다
  if (winningPosts.length === LIMIT) {
    return results;
  }

  let after = new Date(0);

  // 이미 20개가 있으면 새 게시물은 마지막 게시물보다 최신이어야 의미가 있다
  if (results.length === LIMIT) {
    after = new Date(results.at(-1).postedAt);
  }

  // 확정된 것이 11개라면 이 친구에게서는 최근 9개만 보면 된다
  const ratchetedLimit = LIMIT - winningPosts.length;

  const posts = await Posts.findByPoster(friend.friendId, {
    limit: ratchetedLimit,
    after,
  });
  results = merge(results, posts, (post) => post.postedAt); // 양쪽 다 정렬되어 있으므로 병합만 한다
}
return results;
```

핵심은 두 개의 래칫이 동시에 조여진다는 점이다.
하나는 각 친구에게서 가져올 개수를 줄이는 `ratchetedLimit`이고,
다른 하나는 조회 범위를 자르는 `after` 시각이다.
확정된 결과가 쌓일수록 두 값이 모두 좁아지고, 결국 남은 친구들은 아예 조회되지 않는다.

저자가 드는 수치가 효과를 보여 준다.
래칫이 없으면 데이터베이스는 친구 50명 곱하기 게시물 20개를 찾아야 한다.
래칫이 있으면 첫 친구에게서 20개, 둘째에게서 18개, 셋째에게서 14개를 보고
마지막 25명은 조회하지 않을 수도 있다.
여전히 N + 1 문제이지만 덜 아픈 N + 1이라고 그는 정리한다.

## 트레이드오프

이 기법의 교환 대상은 명확하다.
데이터베이스가 읽는 행 수를 줄이는 대신 네트워크 왕복 횟수를 늘린다.

저자는 이 패턴을 몇 번 써 봤는데 값어치가 있었던 것은 그중 일부뿐이었다고 밝힌다.
질의 효율이 좋아진 만큼을 추가 왕복이 상쇄할 수 있으며,
데이터의 실제 특성과 감수하려는 트레이드오프에 따라
데이터베이스 이득은 거의 없이 성능만 나빠질 수도 있다는 것이다.

그러므로 이 기법이 유리한 조건을 정리하면 이렇다.

| 조건                                               | 이유                                               |
| -------------------------------------------------- | -------------------------------------------------- |
| 조기 종료 확률이 높다                              | 대부분의 호출이 첫 몇 번의 왕복에서 끝난다         |
| 후보를 유용하게 정렬할 수 있다                     | 정렬 기준이 없으면 래칫이 조여지지 않는다          |
| 데이터베이스가 병목이고 애플리케이션은 여유가 있다 | 부하를 애플리케이션 쪽으로 옮기는 것이 이득이 된다 |
| 지연 증가를 감수할 수 있다                         | 직렬 왕복이 늘어난다                               |
| 호출 빈도가 높다                                   | 절약이 누적된다                                    |

반대로 후보 수가 적거나 조기 종료가 드물거나 왕복 지연이 큰 환경이라면 이 기법은 손해다.

## 함정

- 정렬 기준이 틀리면 래칫이 전혀 조여지지 않고 왕복만 늘어난다. 최신 학급일수록 게시물이 있을 확률이 높다는 가정은 사용자 행동이 바뀌면 함께 무너진다.
- 최악의 경우가 원래보다 나빠진다. 일치하는 항목이 하나도 없으면 모든 후보를 직렬로 조회하므로 지연이 후보 수에 비례한다.
- `IN` 절의 계획 전환 지점은 데이터와 통계에 따라 달라지므로, 저자의 세 개라는 관찰을 그대로 옮겨 적용하면 안 된다.
- 친구 피드 예시는 `lastPosted`가 항상 최신이라는 전제 위에 있다. 이 값이 지연되어 갱신되면 이미 확정된 결과가 뒤집힌다.
- 한 번에 하나씩 조회하는 구조는 커넥션 점유 시간이 길어진다. 커넥션 풀이 좁으면 부하를 줄이고도 처리량이 떨어질 수 있다.

## 비평

### 플래너보다 항상 같거나 낫다는 주장은 과하다

저자는 우리가 데이터와 트레이드오프를 더 잘 알기 때문에
플래너의 계획과 같거나 더 나은 계획을 언제나 만들 수 있다고 적는다.
이 문장은 글의 전제인데, 성립 조건이 생략되어 있다.

플래너가 가진 것 중 애플리케이션이 갖지 못한 정보도 있다.
현재의 인덱스 통계, 버퍼 풀에 무엇이 올라와 있는지,
동시에 실행 중인 다른 질의가 어떤 자원을 쓰고 있는지가 그렇다.
게다가 손으로 만든 계획은 데이터 분포가 바뀌어도 자동으로 갱신되지 않는다.
저자 자신이 이 문제를 알고 있다는 증거가 글 안에 있다.
최신 학급이 조건을 만족할 확률이 높다는 근거가 사용자 행동의 변화라는 것인데,
그 행동은 또 바뀔 수 있다.

더 정확한 진술은 우리가 더 나은 계획을 만들 수 있다는 것이 아니라,
우리가 정확성과 지연을 교환할 권한을 갖고 있다는 것이다.
플래너는 정확한 결과를 내야 하지만 우리는 조기 종료를 선택할 수 있다.
이것은 지식의 우위가 아니라 목표의 차이이며, 글은 이 둘을 섞는다.

### 사례의 성과가 기법의 성과인지 구별되지 않는다

부하가 17.2에서 12.4로 떨어진 것은 인상적인 숫자이고 제목에도 들어가 있다.
그런데 저자 스스로 이것이 최선의 시나리오이며
원래 코드가 전혀 최적화되지 않은 상태였다고 인정한다.
정렬 없는 조기 종료만으로도, 혹은 단순한 캐시만으로도 큰 효과가 있었을 것이라고도 적는다.

그렇다면 4분의 1이라는 수치가 측정하는 것은 래칫 기법의 효과가 아니라
아무 최적화도 없던 코드에 최적화를 한 효과다.
정렬이 기여한 몫, 조기 종료가 기여한 몫, 직렬화가 기여한 몫이 분리되지 않는다.

이 구별이 중요한 이유는 독자의 기대를 정하기 때문이다.
이미 조기 종료를 하고 있는 코드에 정렬을 추가했을 때 얼마가 줄어드는지가
이 기법을 도입할지 판단하는 실제 근거인데, 글에는 그 숫자가 없다.
저자가 마지막에 이 패턴이 값어치 있었던 것은 일부뿐이었다고 밝히는 것과
제목의 4분의 1 사이에 상당한 거리가 있다.

### 캐시를 대안으로 언급하고 검토하지 않는다

첫 사례에서 저자는 단순한 캐시로도 잘 동작했을 것이라고 한 줄 적고 넘어간다.
그러나 존재 여부 확인처럼 결과가 거의 변하지 않는 질의는 캐시의 교과서적 대상이다.
게시물이 한 번 생기면 그 학급의 답은 영원히 참이므로 무효화조차 단순하다.

두 방식의 비교가 빠진 것이 아쉬운 이유는 선택 기준이 다르기 때문이다.
래칫은 코드 안에서 끝나고 새 인프라가 필요 없지만 왕복이 남는다.
캐시는 왕복을 거의 0으로 만들지만 저장소와 무효화 정책이 늘어난다.
읽기 대 쓰기 비율이 극단적으로 읽기에 치우친 이 사례에서는 캐시가 더 나은 답일 가능성이 높다.

래칫 기법이 진짜 빛나는 자리는 오히려 두 번째 사례다.
피드는 결과가 계속 바뀌어 캐시하기 어렵고, 후보마다 가져올 개수를 줄이는 것이 유일한 절약 수단이다.
글의 구성이 반대로 되어 있어서, 캐시로 풀 수 있는 사례가 제목의 성과를 가져간다.

- 후보를 성공 확률 순으로 정렬할 근거가 데이터에 있는가? 그 근거가 언제 무너지는가?
- 최악의 경우, 즉 일치가 하나도 없을 때의 지연을 측정했는가?
- 데이터베이스가 병목인가, 아니면 애플리케이션이나 네트워크가 병목인가?
- 같은 문제를 캐시로 풀 수 있는가? 무효화가 단순한가?
- `IN` 절을 쓰고 있다면 실제 데이터에서 `EXPLAIN ANALYZE`로 계획을 확인했는가?
- 직렬 조회로 커넥션 점유 시간이 길어져 처리량이 떨어지지는 않는가?

## 기억할 원칙

### 플래너는 정확해야 하고 우리는 그럴 필요가 없다

이 글의 기법이 통하는 진짜 이유는 지식의 우위가 아니라 요구 수준의 차이다.
쿼리 플래너는 요청받은 결과를 정확히 내놓아야 하므로 모든 후보를 고려해야 하지만,
애플리케이션은 하나만 찾으면 된다거나 20개만 있으면 된다는 조건을 알고 있어서 나머지를 버릴 수 있다.

이 구분은 데이터베이스 밖에서도 유효하다.
전체를 정렬하는 대신 상위 몇 개만 필요하다는 사실을 아는 쪽이 이기고,
전수 검사 대신 첫 반례에서 멈출 수 있다는 사실을 아는 쪽이 이긴다.
최적화를 찾을 때 물어야 할 질문은 어떻게 더 빨리 계산하느냐가 아니라
무엇을 계산하지 않아도 되느냐다.

### 결과가 쌓일수록 남은 작업의 상한이 내려가게 설계한다

래칫이라는 이름이 가리키는 것은 한 방향으로만 조여지는 구조다.
이미 확정된 결과가 다음 조회의 범위와 개수를 동시에 줄이고, 그 축소는 되돌아가지 않는다.

이 형태는 여러 곳에서 반복된다.
최선 우선 탐색이 지금까지의 최선값으로 가지를 쳐 내는 것,
일정 시간 안에 끝내야 하는 작업이 남은 예산으로 다음 단계의 범위를 정하는 것이 같은 구조다.
반대로 각 단계가 독립적으로 전체 작업을 하는 구조는
앞선 단계의 성과를 활용하지 못하며, 병렬화하기는 쉬워도 총 작업량은 줄지 않는다.
병렬화가 늘 답이 아닌 이유가 여기에 있다.
