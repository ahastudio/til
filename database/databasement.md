# Databasement — 웹 UI로 관리하는 셀프호스팅 DB 백업 매니저

<https://david-crty.github.io/databasement/>

<https://github.com/David-Crty/databasement>

## 소개

Databasement는 여러 종류의 데이터베이스를 하나의 웹 UI에서 백업하고 복원하고 일정을 잡는 셀프호스팅 도구다.
Laravel로 만들어졌고 MIT 라이선스이며, 별 1.8천 개에 포크 189개, 커밋 697개 규모다.
Docker Hub에 이미지가 올라가 있고 태그가 78개다.

지원 엔진은 여덟 가지다.
MySQL(5.6, 5.7, 8.x, 9.x), MariaDB(10.x~12.x), PostgreSQL(12~18),
Microsoft SQL Server(2017, 2019, 2022, Azure SQL), MongoDB(4.2~8.0),
SQLite(3.x), Firebird(3.x~5.x), Redis/Valkey(2.8+, Valkey는 7.2+)다.

각 엔진마다 실제로 호출하는 CLI 도구가 문서에 명시돼 있다.
MySQL과 MariaDB는 `mariadb-dump`, PostgreSQL은 `pg_dump` v18,
SQL Server는 `sqlpackage`로 `.dacpac`을 만들고, MongoDB는 `mongodump`/`mongorestore`,
SQLite는 `sqlite3 .backup`, Firebird는 `gbak` v5, Redis는 `redis-cli --rdb`를 쓴다.

복원 지원 여부가 엔진마다 다르다.
Redis와 Valkey만 복원이 지원되지 않고 나머지 일곱은 지원된다.

## 주요 기능

**연결 경로.**
SSH 터널을 지원해서 배스천이나 점프 서버를 거쳐 사설망의 데이터베이스에 붙을 수 있고,
비밀번호와 키 기반 인증을 모두 쓴다.
방화벽 안이나 격리된 망에는 원격 에이전트를 두는 방식을 제공한다.
인바운드 포트를 열지 않고, 가벼운 에이전트가 HTTPS로 바깥을 향해 연결한 뒤
로컬에서 덤프를 뜨고 스토리지로 업로드한다.

**백업과 보존.**
일간 또는 주간 주기로 반복 백업을 예약한다.
보존 정책은 단순 기간 기반(일 단위)과 GFS(grandfather-father-son) 두 가지다.
압축은 gzip, zstd, 암호화 세 가지 중에 고른다.
zstd는 20~40% 더 나은 압축률을 낸다고 적혀 있고, 암호화는 AES-256이다.

**복원.**
운영에서 스테이징으로 스냅숏을 옮기는 것처럼 호환되는 서버 사이의 교차 복원이 된다.
복원 자체를 예약할 수도 있어서, 매일 밤 운영에서 스테이징으로 최신 스냅숏을 재생하는 식으로 쓴다.

**스토리지.**
로컬, S3 호환(AWS S3, MinIO 등), Azure Blob, Samba/SMB 공유, SFTP/FTP를 지원한다.

**운영 편의.**
작업 로그와 함께 백업·복원 진행 상황을 실시간으로 추적한다.
작업이 실패하면 Email, Slack, Discord, Telegram, Pushover, Gotify, 웹훅으로 알린다.
앱 안에서 Adminer를 열어 MySQL, PostgreSQL, SQLite를 들여다볼 수 있고, 관리자 설정과 역할로 통제된다.

**팀 기능.**
워크스페이스가 분리된 멀티테넌트 조직, 역할 기반 접근 제어,
OAuth/SSO 로그인(Google, GitHub, GitLab, OpenID Connect), 선택적 2단계 인증을 갖췄다.

**자동화.**
REST API와 MCP 서버를 제공한다.
MCP 쪽은 Claude Code, Cursor, VS Code Copilot 같은 AI 어시스턴트를 붙여
자연어로 백업을 관리하는 용도로 소개된다.
문서를 llmstxt.org 형식(`llms.txt`, `llms-full.txt`)으로도 발행한다.

## 배포

배포 방식은 네 가지다.
단일 컨테이너 Docker, 외부 DB를 쓰는 Docker Compose, Kubernetes + Helm, Docker 없는 네이티브 Ubuntu다.

```bash
docker run -d \
  --name databasement \
  -p 2226:2226 \
  -e DB_CONNECTION=sqlite \
  -e DB_DATABASE=/data/database.sqlite \
  -e ENABLE_QUEUE_WORKER=true \
  -v ./databasement-data:/data \
  davidcrty/databasement:1
```

컨테이너 하나에 웹 서버, 큐 워커, 스케줄러가 함께 들어 있다.
볼륨 권한은 컨테이너가 알아서 처리하고, `PUID`와 `PGID`로 호스트의 사용자·그룹 ID에 맞출 수 있다.

## 분석

### 이 프로젝트가 만든 것은 백업 엔진이 아니라 관리 계층이다

지원 표를 보면 이 도구가 실제로 무엇을 하는지가 분명해진다.
MySQL은 `mariadb-dump`, PostgreSQL은 `pg_dump`, MongoDB는 `mongodump`를 호출한다.
전부 각 데이터베이스가 이미 제공하는 표준 도구다.
Databasement가 새로 만든 덤프 방식은 없다.

그러면 남는 가치는 그 도구들을 둘러싼 것들이다.
자격 증명을 어디에 보관할지, 언제 실행할지, 결과물을 어디로 올릴지,
얼마나 오래 보관할지, 실패하면 누구에게 알릴지.
이 다섯 가지가 실제 제품의 내용이고, 덤프 자체는 그 안에서 한 단계에 불과하다.

이 구조는 의도적인 선택으로 보이고 합리적이기도 하다.
덤프 형식을 직접 구현하면 엔진 버전이 올라갈 때마다 따라가야 하고,
데이터 정합성 문제를 스스로 책임져야 한다.
표준 도구를 호출하면 그 책임이 벤더 쪽에 남는다.
여덟 개 엔진을 지원하면서도 관리 가능한 규모를 유지하는 방법이기도 하다.

동시에 이것은 이 도구의 한계도 규정한다.
`pg_dump`로 할 수 없는 것은 Databasement로도 할 수 없다.
PostgreSQL을 `pg_dump` v18로 고정했다는 서술이 그래서 중요하다.
덤프 도구의 버전 정책이 곧 이 제품의 호환성 정책이 된다.

### 원격 에이전트 설계가 이 도구의 실제 대상을 드러낸다

기능 목록에서 가장 공들인 설계는 원격 에이전트다.
인바운드 포트를 열지 않고 에이전트가 바깥으로 HTTPS 연결을 맺은 뒤,
로컬에서 덤프를 뜨고 스토리지로 직접 올린다.

이 구조가 푸는 문제는 기술적인 것이 아니라 조직적인 것이다.
방화벽에 인바운드 규칙을 하나 추가하려면 보안팀 승인이 필요하고,
그 승인이 백업 도구 도입보다 오래 걸리는 경우가 흔하다.
아웃바운드 HTTPS는 대체로 이미 열려 있다.
에이전트 방식은 승인 절차를 우회하는 설계다.

덤프를 중앙 서버로 보내지 않고 에이전트가 스토리지로 직접 올린다는 점도 중요하다.
중앙 서버가 데이터 경로에서 빠지므로 대역폭 병목이 생기지 않고,
관리 서버가 실제 데이터베이스 내용을 보지 않게 된다.
백업 데이터가 관리 도구를 통과하지 않는다는 것은 감사 관점에서 설명하기 좋은 성질이다.

SSH 터널 지원이 함께 있는 것도 같은 맥락이다.
배스천을 거치는 접근은 이미 조직에 존재하는 경로를 재사용한다.
두 기능 모두 “새 경로를 뚫지 않는다”는 하나의 원칙을 공유한다.
이 도구가 개인의 홈랩보다 이미 망 분리가 이루어진 조직을 겨냥하고 있다는 신호다.

### GFS 보존 정책의 존재가 대상 사용자를 좁힌다

보존 정책으로 GFS를 제공한다는 점은 기능 목록에서 눈에 덜 띄지만 의미가 크다.
단순 기간 기반 보존은 “30일 지난 것은 지운다”이고, 구현도 이해도 쉽다.
GFS는 일간·주간·월간 백업을 서로 다른 주기로 남기는 방식이다.

GFS를 요구하는 곳은 대체로 규제나 감사 요건이 있는 조직이다.
“3개월 전 특정 시점의 데이터를 제출하라”는 요구에 답해야 하는 상황에서
단순 기간 보존은 쓸 수 없다.
개인 프로젝트나 소규모 서비스에서 GFS를 쓰는 경우는 드물다.

이 기능이 들어 있다는 것은 개발자가 어떤 사용자를 상정했는지를 말해 준다.
멀티테넌트 조직, 역할 기반 접근 제어, OAuth/SSO, 2단계 인증이 함께 있는 것도 같은 방향이다.
셀프호스팅 도구지만 개인용이 아니라 팀용으로 설계됐다.

### MCP 서버 제공이 이 범주에서 이례적이다

백업 도구가 MCP 서버를 내장한 사례는 아직 흔하지 않다.
REST API는 자동화의 표준 수단이므로 놀랍지 않지만,
AI 어시스턴트를 붙여 자연어로 백업을 관리한다는 소개는 성격이 다르다.
문서를 `llms.txt` 형식으로 따로 발행하는 것까지 포함하면
이 프로젝트가 LLM 도구 생태계를 명시적인 사용자로 잡고 있다는 것이 분명하다.

저장소 루트에 `CLAUDE.md`와 `.mcp.json`이 있다는 점도 함께 볼 만하다.
개발 과정 자체에서 AI 에이전트를 쓰고 있다는 뜻이고,
제품이 제공하는 MCP 서버와 개발에 쓰는 MCP 설정이 같은 저장소에 공존한다.

다만 백업이라는 영역에서 자연어 인터페이스가 무엇을 의미하는지는 따져볼 필요가 있다.
조회는 자연스럽다.
“어제 실패한 백업 보여줘”는 안전하고 유용하다.
복원은 다르다.
잘못 지정된 대상 하나가 운영 데이터베이스를 덮어쓴다.
MCP 서버가 어떤 동작까지 노출하는지, 파괴적 동작에 별도 확인이 있는지가
이 기능의 성격을 가르는데, README 수준에서는 드러나지 않는다.

## 비평

### Redis 복원 미지원이 표 한 칸으로 처리된다

지원 표에서 Redis와 Valkey만 복원 열이 “No”다.
이 사실은 표의 한 칸으로만 표시되고, 기능 목록이나 소개 문구에서는 언급되지 않는다.
README 상단은 여덟 개 엔진을 나란히 나열하며 “관리한다”고만 적는다.

백업 도구에서 복원 불가는 부차적 제약이 아니다.
백업의 목적이 복원이기 때문이다.
복원할 수 없는 백업은 데이터 보관이지 백업이 아니다.
`redis-cli --rdb`로 RDB 파일을 받아 두는 것은 유용하지만,
그것을 되돌리는 절차는 사용자가 따로 마련해야 한다.

문제는 이 비대칭이 사용자에게 어떻게 전달되느냐다.
여덟 개 엔진을 지원한다는 문구를 보고 도입한 팀이
Redis 복원이 필요한 순간에 비로소 표의 그 칸을 발견하게 되는 구조다.
그 순간은 대체로 장애 상황이다.

기술적으로 어려운 일이라서 빠졌을 가능성이 높다.
RDB 파일을 되돌리려면 인스턴스를 멈추고 파일을 교체한 뒤 재시작해야 하는데,
이는 원격에서 안전하게 자동화하기 까다롭다.
그렇다면 그 이유를 표 밖에서 설명하는 편이 낫다.
제약을 숨기지 않는 것과 표에 적어 두는 것은 다른 일이다.

### 단일 컨테이너 권장이 백업 도구의 요건과 어긋난다

빠른 시작 예시는 SQLite를 메타데이터 저장소로 쓰는 단일 컨테이너다.
웹 서버, 큐 워커, 스케줄러가 한 컨테이너에 들어 있고 데이터는 볼륨 하나에 담긴다.
도입 장벽을 낮추는 좋은 설계다.

그런데 이 구성은 이 도구가 다루는 문제와 묘하게 충돌한다.
Databasement는 데이터베이스가 유실될 상황에 대비하는 도구인데,
정작 자기 자신의 상태는 볼륨 하나에 의존한다.
그 볼륨이 사라지면 백업 일정, 자격 증명, 보존 정책, 작업 이력이 함께 사라진다.
스토리지에 올라간 덤프 파일은 남지만, 그것을 어떤 서버에서 어떤 설정으로 떴는지는 잃는다.

Docker Compose와 Kubernetes 옵션이 있으므로 해결 경로는 존재한다.
문제는 기본값이 어디에 놓였느냐다.
README의 빠른 시작이 SQLite 단일 컨테이너이고,
“운영 배포는 설정 가이드를 보라”는 한 줄로 넘어간다.
백업 도구라는 성격을 감안하면 자기 자신의 백업 전략이
설정 가이드 안쪽이 아니라 README에 있어야 할 항목으로 보인다.

특히 이 도구는 데이터베이스 자격 증명을 집중적으로 보관한다.
운영 DB 여덟 종의 접속 정보가 한곳에 모인다는 것은
편의인 동시에 단일 침해 지점이다.
그 저장소가 기본 구성에서 SQLite 파일 하나라는 점은
보안 관점에서도 더 많은 설명이 필요한 선택이다.

### 자격 증명 취급에 대한 설명이 기능 목록에 없다

기능 목록에는 OAuth/SSO, 역할 기반 접근 제어, 2단계 인증이 있다.
전부 사람이 이 도구에 로그인하는 경로에 관한 것이다.
정작 이 도구가 데이터베이스에 로그인하는 경로에 대한 서술은 없다.

백업 매니저는 구조상 운영 데이터베이스의 읽기 권한을 상시 보유한다.
SSH 키, DB 비밀번호, S3 액세스 키, SMB 자격 증명이 한 시스템에 모인다.
이것들이 어떻게 저장되는지가 이 제품의 가장 중요한 보안 속성인데,
README는 암호화 항목을 백업 파일 압축 옵션(AES-256) 자리에서만 언급한다.
저장된 자격 증명 자체의 암호화는 별개 문제다.

`SECURITY.md`와 별도 문서가 있으니 어딘가에는 설명이 있을 수 있다.
그러나 기능을 나열하는 자리에서 이 항목이 빠져 있다는 사실 자체가
제품이 스스로를 어떻게 소개하는지를 보여준다.
“여덟 개 엔진 지원”과 “일곱 가지 알림 채널”은 앞에 나오고,
비밀 관리는 나오지 않는다.

셀프호스팅이라는 성격이 이 문제를 완화한다는 반론이 가능하다.
데이터가 내 서버에 있으니 벤더를 믿을 필요가 없다는 것이다.
그러나 셀프호스팅은 신뢰 대상을 벤더에서 나 자신으로 옮길 뿐,
자격 증명이 한곳에 모인다는 사실은 바꾸지 않는다.
오히려 전담 보안팀이 없는 조직일수록 이 집중의 위험이 크다.

### 검증되지 않은 백업이라는 문제를 다루지 않는다

기능 목록에는 백업, 복원, 예약, 알림, 보존이 있다.
없는 것은 검증이다.
뜬 덤프가 실제로 복원 가능한지 확인하는 절차가 기능으로 제시되지 않는다.

백업 운영에서 가장 흔한 실패는 백업이 돌지 않는 것이 아니다.
몇 달 동안 성공 로그를 남기며 잘 돌던 백업이
정작 복원하려니 쓸 수 없는 상태였다는 것이 전형적인 사고다.
덤프가 중간에 잘렸거나, 스키마가 바뀌었거나, 암호화 키가 사라졌거나,
압축 파일이 손상됐어도 백업 작업 자체는 성공으로 기록된다.

이 도구에는 이 문제를 풀 재료가 이미 있다.
예약 복원 기능이 그것이다.
매일 밤 운영에서 스테이징으로 최신 스냅숏을 재생하는 구성은
사실상 자동 복원 검증으로 기능한다.
그러나 README는 이 기능을 “스테이징 데이터 갱신” 용도로만 소개한다.

검증 용도로 위치를 바꿔 제시하는 것과 데이터 갱신으로 소개하는 것은 다르다.
전자라면 검증 실패를 알림 대상으로 삼고, 마지막 검증 성공 시점을 지표로 노출해야 한다.
후자에 머무르면 사용자는 자기 백업이 복원 가능한지 여전히 모른 채 운영한다.
알림 채널을 일곱 개나 붙인 도구가 “복원 검증에 실패했다”는 알림은 보내지 않는 셈이다.

## 인사이트

### 백업 도구의 진짜 경쟁 상대는 다른 도구가 아니라 크론 스크립트다

이 범주의 제품이 부딪히는 현실은 대안이 이미 존재한다는 것이다.
`pg_dump`를 크론에 걸고 결과를 S3로 올리는 셸 스크립트는 20줄이면 된다.
많은 팀이 실제로 그렇게 운영하고 있고, 그 스크립트는 몇 년째 잘 돌고 있다.

따라서 이런 도구가 제공해야 하는 것은 백업 능력이 아니라
스크립트가 감당하지 못하는 지점이다.
엔진이 여덟 종으로 늘어날 때, 서버가 수십 대가 될 때,
누가 어떤 백업에 접근할 수 있는지 통제해야 할 때,
감사 로그를 제출해야 할 때 스크립트는 무너진다.

Databasement의 기능 배치가 이 판단을 반영한다.
멀티테넌트, RBAC, SSO, GFS, 작업 로그는 전부 스크립트로 만들기 번거로운 것들이다.
반대로 덤프 자체는 스크립트가 하던 일을 그대로 위임한다.
경쟁 지점을 정확히 파악한 구성이다.

여기서 파생되는 함의가 있다.
이런 도구의 도입 시점은 기술적 필요가 아니라 조직 규모가 결정한다.
서버가 세 대일 때는 스크립트가 이긴다.
관리 계층의 가치는 관리할 것이 많아진 뒤에야 발생하기 때문이다.
그래서 이 범주의 채택 곡선은 서비스 성장 곡선을 뒤따르며,
도입을 검토하는 시점은 대체로 스크립트가 이미 한 번 실패한 뒤다.

### 자격 증명을 모으는 도구는 스스로 침해 대상이 된다

Databasement가 정상 동작하려면 운영 데이터베이스 전부에 대한 읽기 권한과
스토리지 쓰기 권한을 상시 보유해야 한다.
이것은 결함이 아니라 기능의 전제 조건이다.
백업 도구는 정의상 모든 데이터를 읽을 수 있어야 한다.

그 결과 이 도구 자체가 조직에서 가장 가치 높은 침해 대상이 된다.
공격자가 여덟 개 데이터베이스를 각각 뚫는 대신 백업 매니저 하나만 장악하면
모든 데이터에 접근할 수 있고, 덧붙여 스토리지에 쌓인 과거 스냅숏까지 얻는다.
현재 상태만이 아니라 시간 축 전체가 노출된다.

이 패턴은 백업 도구 고유의 것이 아니다.
비밀 관리 시스템, CI/CD 러너, 모니터링 에이전트가 같은 구조를 갖는다.
편의를 위해 권한을 집중시키는 모든 시스템이 동일한 성질을 띤다.
CI 러너가 배포 자격 증명을 갖기 때문에 공급망 공격의 표적이 되는 것과 같은 자리다.

그래서 이런 도구를 도입할 때 물어야 할 질문은
“이 도구가 안전한가”가 아니라
“이 도구가 침해됐을 때 피해 범위가 어디까지인가”다.
읽기 전용 계정을 쓰는지, 스토리지 키에 삭제 권한이 없는지,
백업본에 객체 잠금이 걸려 있는지가 실제 방어선이 된다.
셀프호스팅이라는 성질은 이 질문을 없애 주지 않고 답할 책임을 사용자에게 옮길 뿐이다.

### 백업의 신뢰도는 복원 횟수에 비례하며 시간이 지날수록 떨어진다

백업 시스템에는 다른 인프라와 구별되는 성질이 있다.
평소에 쓰이지 않는다는 것이다.
웹 서버는 매 요청마다 자기가 동작한다는 것을 증명하지만,
백업은 재난이 오기 전까지 한 번도 실제로 쓰이지 않는다.

쓰이지 않는 경로는 조용히 썩는다.
덤프 도구 버전이 올라가고, 스키마가 바뀌고, 스토리지 자격 증명이 만료되고,
암호화 키를 아는 사람이 퇴사한다.
이 변화들은 백업 작업의 성공 로그를 건드리지 않는다.
매일 초록불이 켜지는 동안 복원 가능성만 조용히 사라진다.

이 성질 때문에 백업 시스템의 품질 지표는 “백업 성공률”이 아니라
“마지막으로 실제 복원에 성공한 시점”이어야 한다.
전자는 항상 높게 나오고 후자는 대체로 비어 있다.
그리고 후자를 채우는 유일한 방법은 정기적으로 복원을 실행하는 것이다.

Databasement의 예약 복원 기능이 흥미로운 이유가 여기 있다.
운영에서 스테이징으로 매일 밤 데이터를 재생하는 구성은
개발 편의를 위한 기능으로 소개되지만,
실제로는 백업 경로 전체를 매일 한 번씩 통과시키는 장치다.
덤프, 압축, 업로드, 다운로드, 해제, 복원이 전부 실행된다.

이 관점에서 보면 “스테이징 데이터 갱신”은 부수 효과이고
본질은 상시 복원 훈련이다.
백업 도구를 고를 때 복원 예약 기능의 유무를 편의 항목이 아니라
신뢰성 항목으로 평가해야 하는 이유다.

### 관리 계층은 얇게 시작해서 필연적으로 두꺼워진다

이 프로젝트의 구조는 얇은 관리 계층으로 출발했다.
덤프는 표준 도구에 위임하고, 예약과 저장과 알림만 담당한다.
그런데 기능 목록을 보면 이미 그 경계가 확장되고 있다.
Adminer를 앱 안에 넣어 데이터를 열람하고, MCP 서버로 자연어 조작을 받고,
멀티테넌트 조직과 SSO를 갖췄다.

이 확장에는 논리가 있다.
백업을 관리하다 보면 백업된 내용을 확인하고 싶어지고,
확인하려면 조회 도구가 필요하고,
조회 도구가 생기면 접근 통제가 필요하고,
통제가 생기면 조직 개념이 필요해진다.
각 단계가 이전 단계에서 자연스럽게 따라 나온다.

같은 패턴이 다른 곳에서도 반복됐다.
CI 도구는 빌드만 돌리다가 아티팩트 저장, 배포, 시크릿 관리, 권한 체계를 흡수했다.
모니터링 도구는 지표 수집에서 알림, 온콜, 인시던트 관리로 번졌다.
관리 계층은 인접 문제를 계속 끌어당긴다.
사용자가 이미 그 화면을 보고 있기 때문이다.

이 확장이 사용자에게 갖는 의미는 양면적이다.
한 도구에서 더 많은 일을 처리하는 편의가 생기는 대신,
그 도구를 벗어나기가 점점 어려워진다.
Adminer 접근 권한과 조직 구조와 알림 라우팅이 백업 도구 안에 자리 잡으면
백업 도구를 교체하는 일이 백업 이상의 마이그레이션이 된다.
MIT 라이선스와 셀프호스팅이라는 성질이 이 잠김을 완화하지만,
데이터 이동성과 별개로 운영 절차가 도구 모양에 맞춰지는 종류의 잠김은 남는다.
