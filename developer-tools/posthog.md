## 소개

PostHog는 제품 분석, 세션 리플레이, 에러 추적, 기능 플래그, 실험 등을
한 저장소와 한 데이터 계층에 모은 오픈소스 플랫폼이다.
저장소는 2020년 1월에 만들어졌고, 2026년 10월 기준 GitHub 별 약 4만 개,
포크 약 3,500개, 열린 이슈 약 5,500개를 가진 거대한 모노레포다.

README의 첫 제목은 “PostHog is your product's context layer”다.
분석, 에러, 리플레이, 비즈니스 데이터를 받아 저장해
사람과 에이전트가 함께 조회하고 행동할 수 있게 한다는 설명이다.
저장소 설명은 한발 더 나가 PostHog를
“self-driving products”를 만드는 플랫폼이라고 부르고,
에이전트가 문제를 진단하고 기회를 찾고
수정을 배포하는 데 필요한 맥락을 모은다고 적는다.

### 제품 구성

| 묶음            | 제품                                                               |
| --------------- | ------------------------------------------------------------------ |
| 분석            | 제품 분석, 웹 분석, 그룹 분석                                      |
| 세션 리플레이   | 세션 리플레이, Replay Vision(AI가 녹화를 보고 관찰을 기록), 히트맵 |
| 관측 가능성     | 에러 추적, 로그, 분산 트레이싱                                     |
| 출시와 반복     | 기능 플래그, 실험, 얼리 액세스 기능                                |
| 사용자와의 대화 | 설문, 고객 지원 채팅과 통합 받은편지함, 워크플로                   |
| 데이터          | 관리형 웨어하우스와 120개 이상 소스, 데이터 파이프라인, Endpoints  |
| AI와 에이전트   | AI 관측 가능성, MCP 분석, PostHog AI, Self-driving                 |

Self-driving은 에러, 분노 클릭(rage click), 실패한 쿼리 같은 신호를
조사 보고서와 풀 리퀘스트로 바꿔 받은편지함에 넣어 주고,
사람은 검토하고 병합만 하게 하는 기능이다.
이 모든 것을 Slack, 웹, 데스크톱 앱, MCP로 연결한 편집기에서 다룰 수 있다.

### 에이전트를 위한 README

README에는 “What is this, a readme for agents?”라는 접힌 절이 따로 있다.
원격 MCP 서버 주소 `https://mcp.posthog.com/mcp`를 알려 주고,
사람이 로그인하면 미국과 EU 데이터 리전으로 알아서 연결된다고 설명한다.
설치는 한 줄이다.

```bash
# Claude Code, Cursor, Codex, VS Code, Zed, PostHog Desktop에 MCP 서버를 추가한다.
npx @posthog/wizard mcp add
```

문서 전체는 `posthog.com/llms.txt`로, 변경 이력은 `changelog.md`로 제공된다.
앱에 PostHog를 심는 일도 설정 마법사가 대신한다.

```bash
# 앱 코드에 SDK를 설치하고 설정까지 해 준다.
npx -y @posthog/wizard@latest
```

### 가격과 셀프 호스팅

클라우드는 제품마다 월 무료 한도가 있고 카드 등록이 필요 없다.
README는 사용자의 97%가 0달러를 낸다고 말한다.
매달 이벤트 100만 건, 녹화 5천 건, 기능 플래그 요청 100만 건, 예외 10만 건,
로그 10GB, 설문 응답 1,500건까지 무료이고 그 이상은 사용량 과금이다.
50만 개 이상의 팀이 쓴다고 한다.

셀프 호스팅은 Docker로 한 줄 배포하는 hobby 인스턴스이며 메모리 4GB를 권장한다.
README는 월 약 10만 이벤트까지 감당하고 그 뒤에는 클라우드로 옮기라고 권하며,
오픈소스 배포에는 고객 지원도 보증도 없다고 명시한다.

### 라이선스와 저장소 구조

저장소는 MIT(expat) 라이선스지만
`ee` 디렉터리는 별도의 엔터프라이즈 라이선스를 따른다.
이 라이선스는 유효한 구독 없이 해당 코드를 운영 환경에서 쓰는 것을 금지하고,
개발과 테스트 목적의 복제와 수정만 허용한다.
완전한 자유 소프트웨어가 필요하면
독점 코드를 걷어 낸 `posthog-foss` 저장소를 쓰라고 안내한다.
회사 핸드북도 공개되어 있다.

모노레포 안내 문서에 따르면 `posthog/`는 레거시 Django 모놀리스이고,
새 기능은 `products/<제품>/` 아래에 Django 앱과 React 프론트엔드를 묶은
수직 조각(vertical slice)으로 들어간다.
제품끼리는 서로의 내부를 가져다 쓰지 않고
facade와 고정된 데이터 클래스로만 소통한다.
2026년 10월 기준 `products/` 아래 디렉터리는 98개다.
많은 제품이 자기 MCP 도구 정의(`mcp/tools.yaml`)와
에이전트 스킬(`skills/`)을 함께 가진다.

## 분석

### 고객의 정의가 사람에서 에이전트로 넓어졌다

PostHog의 README는 지금 두 독자를 상대로 쓰여 있다.
제품 목록과 무료 한도는 사람을 위한 것이고,
MCP 주소, `llms.txt`, Markdown 변경 이력, 설정 마법사는 에이전트를 위한 것이다.
“context layer”라는 새 정체성은 이 두 번째 독자를 위해 만든 말이다.

이 전환에는 논리가 있다.
분석 도구의 가치는 원래 사람이 대시보드를 보고 판단하는 데 있었다.
그런데 코딩 에이전트가 코드를 고치게 되자 병목은
“무엇을 고쳐야 하는가”를 알려 주는 맥락으로 옮겨 갔다.
에러 스택, 그 에러를 겪은 사용자의 리플레이,
같은 시각의 로그와 트레이스, 그 기능의 플래그 상태가
한 곳에 있으면 에이전트는 사람보다 빨리 원인을 좁힐 수 있다.
PostHog는 이미 그 데이터를 다 갖고 있었고,
이제 그것을 에이전트용 인터페이스로 다시 포장하고 있다.

Self-driving은 이 논리의 끝이다.
신호가 보고서가 되고 보고서가 풀 리퀘스트가 되면,
분석 도구는 관찰하는 도구에서 코드를 바꾸는 도구가 된다.
사람의 역할은 대시보드를 보는 사람에서 병합 버튼을 누르는 검토자로 줄어든다.

### 제품을 계속 붙이는 것이 성장 전략이다

`products/` 아래 98개 디렉터리는 PostHog의 성장 방식이 무엇인지 보여 준다.
한 제품을 깊게 파는 대신, 이미 수집 중인 이벤트 위에 새 제품을 계속 얹는다.
각 제품은 따로 무료 한도를 갖고, 무료 한도를 넘은 고객에게서만 돈을 받는다.
고객 한 명이 쓰는 제품 수가 늘수록 매출이 늘고,
동시에 다른 도구로 옮기기 어려워진다.

이 전략을 가능하게 하는 것이 코드 구조다.
제품을 수직 조각으로 나누고 서로의 내부를 가져다 쓰지 못하게 막으며,
새 제품은 `hogli product:bootstrap` 한 번으로 뼈대가 생긴다.
제품마다 MCP 도구와 스킬을 함께 넣게 한 규칙은
새 제품이 나오는 순간 에이전트 인터페이스도 함께 생긴다는 뜻이다.
조직 구조, 코드 구조, 가격 구조,
에이전트 인터페이스가 모두 “제품을 하나 더”라는 같은 방향을 향한다.

### 오픈소스는 배포 수단이 아니라 신뢰 수단이다

PostHog의 오픈소스는 직접 운영하라는 초대가 아니다.
README와 셀프 호스팅 고지 모두 클라우드를 권하고,
셀프 호스팅은 취미용이며 지원도 데이터 손실 복구도 없다고 말한다.
그런데도 코드, 핸드북, 가격표를 모두 공개하는 이유는
분석 도구라는 범주의 특수성에 있다.

분석 도구는 고객의 사용자 데이터를 가장 많이 가져가는 도구다.
코드가 공개되어 있으면 고객은 무엇이 수집되고
어떻게 처리되는지 직접 확인할 수 있고,
최악의 경우 직접 돌릴 수 있다는 선택지가 남는다.
실제로 그 선택지를 쓰는 고객은 드물어도,
선택지가 있다는 사실이 구매 결정을 쉽게 만든다.
PostHog의 오픈소스는 무료 한도와 함께 영업 비용을 대신하는 장치다.

출발점을 보면 이 변화가 더 선명하다.
2020년 Launch HN 글에서 창업자들은 PostHog를
셀프 호스팅하는 오픈소스 Mixpanel이자 Amplitude라고 소개했고,
사용자 데이터를 제3자에게 보내야 하는 것이 불편해서 만들었다고 적었다.
당시 호스팅 버전은 직접 설치하지 못하는 사람을 위한 것일 뿐
핵심이 아니라는 답글도 남겼다.[^james_impliu-launch]
GeekNews에서 xguru는 PostHog가 처음부터 오픈소스로 YC에 들어간 것이 아니라
중간에 방향을 바꾼 것으로 보인다고 짚으면서,
GitLab과 Mattermost처럼 오픈소스가 중심인 회사에
투자가 이어지는 흐름을 반겼다.[^xguru]

2024년 스레드에서 공동 창업자 james_impliu는 방향이 바뀐 이유를 설명했다.
셀프 호스팅만으로 사업을 해 보려 했지만
고객의 운영 환경보다 PostHog가 다루는 데이터가 더 많은 경우가 흔했고,
남의 Kubernetes를 스크린샷으로 디버깅하는 데
시간을 너무 많이 썼다는 것이다.[^james_impliu]
셀프 호스팅으로 쓰다가 서비스가 커져 클라우드로 옮긴 danr4는
그래도 셀프 호스팅의 쉬움, 기능, 공개된 회사 운영 방식을 합치면
PostHog가 가장 균형 잡힌 오픈소스 제품 중 하나라고 평가했다.[^danr4]

반대로 resiros는 PostHog를 상업 오픈소스 모델이 잘 맞지 않는 사업으로 본다.
데이터베이스처럼 많은 사용자가 반드시 직접 띄워야 하는 소프트웨어는
오픈소스가 유통 이점을 계속 주지만,
PostHog는 초기에 셀프 호스팅 커뮤니티를 교두보로 삼은 뒤로는
오픈소스가 더하는 가치가 크지 않다는 것이다.[^resiros]

## 비평

### 셀프 호스팅은 이름만 같은 다른 제품이다

README는 hobby 인스턴스를 메모리 4GB 권장으로 한 줄에 배포할 수 있다고 소개한다.
그런데 hobby 배포에 쓰이는 `docker-compose.hobby.yml`에는
PostgreSQL, Valkey, ClickHouse, ZooKeeper,
Kafka 호환 브로커, Temporal과 Elasticsearch,
여러 수집 서비스와 에러 심볼 처리 서비스까지 30개가 넘는 서비스가 정의되어 있다.
ClickHouse와 Kafka를 한 대의 4GB 머신에서
안정적으로 돌린다는 기대는 현실과 거리가 있다.

규모에 대한 안내도 서로 어긋난다.
README는 월 약 10만 이벤트까지 감당한다고 하고,
셀프 호스팅 고지는 상당한 노력 없이는 수십만 이벤트를 넘기 어렵다고 말한다.
클라우드 무료 한도가 월 100만 이벤트라는 점을 생각하면,
셀프 호스팅은 공짜 클라우드보다 열 배 작은 규모에서 멈추는 선택지다.

빠지는 기능도 많다.
고지 문서는 그룹 분석, 데이터 파이프라인, 1년 이벤트 보존, 녹화 다운로드,
다중 환경 기능 플래그, 여러 질문 설문, SSO와 SAML, RBAC, 감사 로그 등이
셀프 호스팅에서 빠진다고 나열한다.
그러니 “오픈소스이니 직접 운영할 수 있다”는 말은
개인 프로젝트 수준에서만 참이고,
규제나 데이터 주권 때문에 셀프 호스팅이 꼭 필요한 조직에게는 답이 되지 못한다.

HN의 경험담도 같은 방향이다.
nurple은 운영팀에 “PostHog 설치” 티켓이 왔을 때
Helm 차트를 열어 보고 웃었다고 적었다.
ClickHouse 오퍼레이터에 Kafka와 ZooKeeper까지 설치하는 구성이어서,
전담 인력 몇 명을 둘 생각이 아니면 직접 운영할 물건이 아니라는 것이다.[^nurple]
2026년 스레드에서 madjam002는
hobby 배포 스크립트가 master의 최신 빌드를 받아 오기 때문에
“어느 정도 동작”과 “완전히 고장” 사이를 오간다고 했고,[^madjam002]
geekuillaume는 클라우드를 위한 최근 변경 때문에 설치 과정이 깨져
하루를 쓰고도 띄우지 못했다고 덧붙였다.[^geekuillaume]
btown은 PostHog가 2023년에
사용자의 3.5%가 쓰던 Kubernetes 지원을 접었다는 점을 짚었다.[^btown]

### 라이선스 경계가 디렉터리 경계와 함께 흔들린다

README는 저장소가 MIT이고 `ee` 디렉터리만 예외라고 설명한다.
그러나 GitHub API는 이 저장소의 라이선스를 “Other(NOASSERTION)”로 표시하고,
README의 문장 자체도 `ee`의 라이선스가 “해당하는 경우(if applicable)” 적용된다고
흐리게 적는다.

더 큰 문제는 모노레포 안내 문서가
`ee`를 “products/와 posthog/로 옮기는 중”이라고 적고 있다는 점이다.
독점 코드가 디렉터리 이름으로 구분되는 구조에서 그 디렉터리가 해체되는 중이라면,
옮겨진 코드가 어떤 라이선스를 따르는지는 파일마다 확인해야 하는 문제가 된다.
MIT 코드만 쓰려는 사용자에게 현실적인 답은 `posthog-foss`뿐이고,
그것은 결국 기본 저장소가 법적으로 단순하지 않다는 사실을 인정하는 셈이다.

PostHog 쪽의 설명은 이 우려를 일부 덜어 준다.
mariusandra는 PostHog가 첫날부터 `ee/`만 빼고 MIT였고
`posthog-foss`는 그 폴더를 제거한 미러로 오래전부터 있었다고
말했고,[^mariusandra]

그러나 `ee/`가 작고 해체되는 중이라는 설명은
오히려 경계가 파일 단위로 흩어진다는 이 비평의 근거이기도 하다.

### 맥락을 한곳에 모을수록 위험도 한곳에 모인다

“context layer”는 편리함의 언어로 쓰여 있지만, 뒤집으면 집중의 언어다.
분석 이벤트, 세션 녹화, 로그, 트레이스, 에러, 고객 지원 대화, 결제 데이터가
한 공급자의 한 데이터 계층에 모이고,
그 위에서 에이전트가 쿼리를 날리고 풀 리퀘스트까지 만든다.
README는 이 집중이 주는 이점만 말하고,
권한을 어떻게 나누는지,
에이전트가 볼 수 있는 데이터의 범위를 어떻게 제한하는지는 말하지 않는다.

세션 리플레이는 화면에 보이는 개인정보를 담을 수 있고,
로그와 트레이스에는 토큰이나 내부 식별자가 섞이기 쉽다.
이 데이터 전체에 MCP로 접근하는 에이전트는
프롬프트 인젝션 한 번으로 그 맥락을 엉뚱한 곳에 쓸 수 있다.
이 저장소의 다른 노트에서도 PostHog 텔레메트리가 기본으로 켜진 서드파티 도구가
자격 증명을 흘릴 수 있다는 지적이 나왔다.
수집이 쉬울수록 무엇이 수집되는지 아는 사람은 줄어든다.

HN에서도 같은 지적이 나왔다.
kelsey98765431은 open-interpreter에 하드코딩된 키로

놀랐다고 적었다.[^kelsey98765431]

맥락을 모으는 속도에 비해 맥락을 지우는 도구는 늦게 따라오고 있다.

## 인사이트

### README가 에이전트를 위한 영업 문서가 되면 설치 경로가 곧 유통 경로가 된다

PostHog README의 에이전트용 절은 작은 변화처럼 보이지만,
소프트웨어 유통 방식의 변화를 미리 보여 준다.
예전에 개발 도구는 개발자가 문서를 읽고 SDK를 골라 직접 설치했다.
지금은 코딩 에이전트가 “분석 붙여 줘”라는 요청을 받고 어떤 도구를 쓸지 고른다.
그 순간 에이전트가 읽을 수 있는 `llms.txt`, 한 줄짜리 MCP 설치 명령,
앱 코드를 대신 고쳐 주는 설정 마법사를 가진 도구가 선택될 확률이 높아진다.

이것은 검색 엔진 시대의 SEO와 같은 구조다.
사람에게 보이기 위한 랜딩 페이지 경쟁이,
에이전트에게 선택되기 위한 기계 판독 문서 경쟁으로 옮겨 가고 있다.
조코딩의 바이브 코딩 강의는 React를 고른 이유로
많이 쓰여서 AI가 잘 안다는 점을 들었다.
이 내용은
[1인 창업 강의의 3주차 노트](../vibe-coding-solo-founder-bootcamp/03-ai-api-and-payments.md)에
정리했다.
에이전트가 잘 아는 도구가 기본값이 되는 흐름은 이미 시작되었다.

이 흐름의 두 번째 효과는 공급자의 에이전트가 고객의 코드를 직접 고친다는 점이다.
설정 마법사가 SDK를 심고, Self-driving이 풀 리퀘스트를 연다.
고객 저장소에 대한 쓰기 권한이 영업 파이프라인의 일부가 되는 셈이고,
그 권한을 어떻게 검토할지는 고객 쪽 엔지니어링 문화의 숙제로 남는다.

### PostHog는 오피스 번들 전략을 데이터 계층에서 다시 하고 있다

1990년대 Microsoft Office는 워드, 엑셀, 파워포인트 각각에서 최고가 아니어도
한 묶음으로 팔리면서 전문 제품들을 밀어냈다.
번들이 이긴 이유는 가격보다 파일 형식과 클립보드,
즉 데이터가 제품 사이를 오가는 경로였다.
Atlassian이 Jira 위에 Confluence와 Bitbucket을 얹은 방식도 같은 계보다.

PostHog의 번들은 이 전략을 이벤트 데이터 위에서 반복한다.
같은 사용자 ID와 같은 이벤트 스트림을 모든 제품이 공유하므로,
에러 추적만 쓰던 고객이 리플레이를 켜는 순간 두 제품이 저절로 연결된다.
그리고 에이전트 시대에는 이 연결이 더 강한 해자가 된다.
에이전트에게 필요한 것은 각 영역 최고의 도구가 아니라
한 번의 질의로 이어지는 맥락이기 때문이다.

역사가 알려 주는 반대편 교훈도 있다.
번들은 지배적인 위치에 오르면 개별 제품의 품질 압력이 약해지고,
결국 특정 영역에서 훨씬 나은 전문 도구가 번들의 틈을 파고든다.
PostHog가 98개 제품의 품질을 계속 유지할 수 있는지가
이 전략의 수명을 정할 것이다.

번들이 넘어야 할 기술적 벽도 이미 2020년에 예고되었다.
Heap의 확장을 맡았던 malisper는 Launch HN에서
멀티테넌시 없이는 질의 성능을 감당하기 어렵다고 경고했다.
Heap에서는 한 고객의 질의가 클러스터 전체의 디스크 처리량을 쓰기 때문에
50배 이상의 성능 차이가 났다는 것이다.[^malisper]
timgl은 단일 테넌트라면 가장 큰 고객 하나만 감당하면
된다고 답했고,[^timgl-scale]
james_impliu는 그래서 이미 ClickHouse를 붙였지만
유료 버전에 넣었다고 밝혔다.[^james_impliu-clickhouse]
그 뒤 PostHog는 결국 ClickHouse와 Kafka 위의 멀티테넌트 클라우드로 옮겨 갔고,
셀프 호스팅이 무거워진 이유도 여기에 있다.
번들의 데이터 연결성은 거대한 공용 데이터 계층이라는 비용을 치르고 얻은 것이다.

### 97%가 무료인 구조는 에이전트가 사용량을 만들기 시작하면 바뀐다

사용자의 97%가 0달러를 내는 구조는
나머지 3%가 무료 한도를 넘는 사용량으로 전체를 떠받치는 구조다.
지금까지 무료 한도를 넘게 만드는 것은 사람이 만든 트래픽이었다.
에이전트가 데이터를 조회하고, Replay Vision이 녹화를 보고,
Self-driving이 신호를 분석하면
사용량은 사람의 행동과 무관하게 늘어난다.

[플랫폼과 토큰 가격에 관한 노트](../thinking/platform-plus-tokens.md)는
PostHog가 AI 크레딧 비용을 20% 마크업으로 고객에게 넘긴다고 정리한다.
이 구조에서는 에이전트가 많이 일할수록 PostHog의 매출이 늘어난다.
고객에게는 편리함이지만, 동시에 과금의 통제권이
사람의 클릭에서 에이전트의 판단으로 넘어간다는 뜻이기도 하다.

규모가 커지면 이 긴장은 예산 문제로 드러난다.
에이전트가 어떤 신호를 얼마나 자주 조사할지 정하는 설정이 곧 비용 설정이 되고,
무료 한도와 사용량 경보를 이해하지 못한 팀은 에이전트가 만든 청구서를 받게 된다.
“카드 없이 시작”이라는 문턱이 낮을수록
그 이후의 비용 설계는 고객 몫으로 넘어온다.

### 분석에서 수정까지 이어지는 고리는 책임의 위치를 바꾼다

전통적인 분석 도구는 질문에 답했고, 행동은 사람이 했다.
Self-driving은 질문을 스스로 고르고, 답을 조사하고, 수정까지 제안한다.
사람이 하는 일은 병합 여부를 정하는 것뿐이다.

이 구조는 생산성을 크게 높이지만, 실패의 원인을 추적하기 어렵게 만든다.
잘못된 수정이 배포되었을 때 원인은 신호 선택일 수도 있고,
조사 단계의 오판일 수도 있고, 검토자가 대충 넘긴 병합일 수도 있다.
PostHog가 신호에서 풀 리퀘스트까지 같은 데이터 계층 안에서 처리하므로,
고객은 그 판단 과정을 PostHog의 기록에 의존해 재구성해야 한다.

그래서 이 도구를 도입하는 팀이 먼저 정해야 할 것은 기능 목록이 아니라 경계다.
에이전트가 볼 수 있는 데이터의 범위, 열 수 있는 풀 리퀘스트의 범위,
자동 병합을 허용하지 않을 영역을 정하지 않으면
“self-driving product”는 운전자가 누구인지 모르는 제품이 된다.
