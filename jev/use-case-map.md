# TypeSafe 사용 사례 지도: 어디에 Jev를 넣을지 고르는 법

원문: [Example use cases - TypeSafe AI](https://docs.typesafe.ai/concepts/use-case-map)

GN 토론: <https://news.hada.io/topic?id=33978>

## 소개

TypeSafe 공식 문서의 `TypeSafe foundations` 아래에 있는 페이지다.
성격은 튜토리얼도 API 레퍼런스도 아니고, 브레인스토밍용 지도다.
자기 산업에서 TypeSafe가 들어갈 자리를 찾아보라고 안내하며,
가장 가까운 산업을 열어 예시 결정들을 훑고 자기 워크플로의 문서와 동작에 맞게 바꾸라고 적는다.

이 페이지가 주는 것과 주지 않는 것이 분명하다.
주는 것은 세 가지다.
다섯 개의 사용 사례 범주, 열여덟 개의 업무별 예시 묶음, 그리고 열 가지 결정 형태를 정리한 표다.
주지 않는 것은 코드, 가격, 지연 시간 측정치, 정확도 수치, 그리고 각 사례에서 무엇이 어려운지에 대한 서술이다.

그래서 이 페이지만으로는 실행에 옮길 수 없다.
결정 형태 표가 가리키는 것은 같은 문서의 질문 타입이며,
그 타입을 알아야 지도의 항목이 실제 코드가 된다.
이 노트는 지도를 읽는 법과 그 지도를 질문 타입으로 옮기는 법을 함께 다룬다.
질문 타입에 관한 내용은 같은 문서의 [Primitives (Questions)](https://docs.typesafe.ai/primitives) 페이지에서 확인한 것이다.

## 다섯 가지 범주

지도의 맨 위는 산업이 아니라 시스템 형태로 나뉜다.
각 범주가 내세우는 근거가 다르다는 점이 중요하다.

| 범주                        | 성립 근거                                                   | 노리는 자리                                                              |
| --------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------ |
| AI Automation Software      | 코드가 제어 흐름을 소유하고 마크다운 파일이 소유하지 않는다 | 사람이 부조종사로 붙지 않은 채 백그라운드에서 백만 번 돌려도 되는 작업   |
| Real-time applications      | 150ms라는 응답 속도                                         | 사람의 지각보다 빠른 결정, 게임 조작이나 UI 내장                         |
| AI Map Reduce over Big Data | 100배 저렴하다는 비용 구조                                  | 거대 코퍼스 검색, 에이전트 트레이스 분류, 예측용 특징 추출               |
| Universal Verification      | LLM 호출 대비 낮은 단가                                     | 프롬프트·추출·추론 트레이스·도구 호출 검증, 탈옥과 인용 오류와 환각 탐지 |
| Harness Engineering         | 위 셋의 조합                                                | 모델 라우팅, 의미 기반 컨텍스트 검색, LLM 오류 탐지와 가드레일           |

읽는 순서를 뒤집으면 유용하다.
범주 이름이 아니라 성립 근거에서 출발하는 것이다.
내 문제가 빨라야 하는지, 싸야 하는지, 아니면 그냥 코드가 흐름을 쥐어야 하는지를 먼저 정하면
다섯 중 어느 칸을 볼지가 정해진다.

세 근거 중 어느 것도 이 페이지에서 측정되지 않았다는 점은 기억해 둘 만하다.
150ms와 100배는 제품 쪽 주장이며, 자기 작업 부하에서 재보기 전에는 설계 전제로 쓰기 어렵다.

## 결정 형태를 질문 타입으로 옮기기

페이지 아래쪽의 표가 이 지도에서 가장 실용적인 부분이다.
열 가지 결정 형태와 각각을 꺼내 쓸 조건, 그리고 예시가 정리되어 있다.

그런데 그 표는 결정의 모양만 말하고 어떤 질문 타입으로 물을지는 말하지 않는다.
질문 타입은 셋뿐이다.

| 타입   | 무엇에 답하는가            | 돌려주는 값                                      |
| ------ | -------------------------- | ------------------------------------------------ |
| Choice | 이 선택지들 중 어느 것인가 | `choice`, `probabilities`, `confidence`          |
| Score  | 어느 수준인가              | `score`, `legend`, `probabilities`, `confidence` |
| Noul   | 이것이 참인가              | `noul` (0에서 1 사이)                            |

둘을 겹치면 지도가 실행 가능한 형태가 된다.

| 결정 형태                  | 꺼낼 조건                                     | 질문 타입                   | 코드가 받는 것          |
| -------------------------- | --------------------------------------------- | --------------------------- | ----------------------- |
| Classification             | 알려진 범주 하나가 이겨야 함                  | Choice                      | 범주 이름과 범주별 확률 |
| Detection                  | 어떤 속성이 있을 확률이 필요함                | Noul                        | 0에서 1 사이 값 하나    |
| Scoring                    | 답이 순서 있는 척도 위에 있음                 | Score                       | 수준 번호와 수준별 확률 |
| Routing                    | 범주가 다음 코드 경로를 고름                  | Choice                      | 분기 키로 쓸 범주 이름  |
| Search                     | 자연어 질의에 맞는 항목을 찾아야 함           | Noul 또는 Score를 후보마다  | 후보별 점수 또는 확률   |
| Retrieval                  | 가장 관련 있는 맥락이나 레코드가 필요함       | Score를 후보마다            | 정렬에 쓸 점수          |
| Ranking                    | 항목을 의미적 관련성이나 품질로 정렬해야 함   | Score 또는 쌍 비교용 Choice | 정렬 키                 |
| Verification               | 산출물에서 특정 실패 유형을 확인해야 함       | Noul을 실패 유형마다        | 유형별 확률             |
| ML Feature Extraction      | 하위의 고전적 ML 모델이 의미 신호를 필요로 함 | Noul과 Score를 특징마다     | 모델에 넣을 수치 특징   |
| Structured Data Extraction | 비정형 입력에서 알려진 필드를 복원해야 함     | 필드마다 Choice 또는 Score  | 필드별 값               |

이 표를 만들면서 드러나는 사실이 하나 있다.
열 가지 형태 중 검색과 검수와 랭킹과 특징 추출은 질문 하나로 끝나지 않고
후보나 항목이나 특징의 수만큼 질문을 반복한다는 점이다.
지도에서는 한 줄로 보이지만 호출 구조가 다르며, 이것이 비용과 지연을 정하는 실제 변수다.

## 구현하기

질문은 ID와 `type`과 `instructions`로 이루어지고, Choice와 Score는 `criteria`를 더 받는다.
ID는 응답에서 답을 찾는 키이며 모델에 전달되지 않으므로,
ID가 자명해 보여도 질문 전체를 `instructions`에 적어야 한다.

한 번의 호출에 여러 질문을 함께 보낼 수 있고,
같은 요청 안의 모든 질문은 같은 state를 보며 서로 독립적으로 평가된다.

지도의 고객 지원 항목은 티켓을 이슈와 제품 영역과 고객 의도로 분류하고,
긴급도와 불만과 이탈 위험과 환불 요청을 탐지하고,
적절한 팀이나 큐나 자동 워크플로로 보내라고 적는다.
그 세 줄을 질문 묶음으로 옮기면 이렇게 된다.

```python
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

# 분류와 라우팅은 Choice. 분기 키로 쓸 이름이 필요하기 때문이다.
# 선택지가 입력을 다 덮지 못할 수 있으면 other를 반드시 넣는다.
TICKET_QUESTIONS = {
    "department": Choice(
        instructions="Which team should handle this ticket?",
        criteria={
            "returns": "Exchanges, wrong or damaged items",
            "shipping": "Delivery status, delays, lost packages",
            "billing": "Charges, invoices, payment problems",
            "other": "A request that fits none of the above",
        },
    ),
    # 탐지는 Noul. 있고 없고가 아니라 확률이 필요하기 때문이다.
    "refund_requested": Noul(
        instructions="Does the customer request a refund?",
    ),
    "churn_risk": Noul(
        instructions="Does the customer signal they may stop using the service?",
    ),
    # 정도는 Score. 각 수준이 무엇인지 말로 적을 수 있을 때만 쓴다.
    "frustration": Score(
        instructions="How frustrated is the customer?",
        criteria=[
            "Calm, just stating facts",
            "Frustrated but civil",
            "Very angry, strong language or threatening to leave",
        ],
    ),
}


def triage(ticket: str) -> None:
    with TypeSafeClient() as client:
        response = client.system_one(state=ticket, questions=TICKET_QUESTIONS)
    answers = response.answers

    department = answers["department"]
    # 어느 팀인지가 흐릿하면 자동 분기를 하지 않는다. 임계값은 아래 절에서 정한다.
    if department.confidence < 0.3:
        send_to_manual_triage(ticket)
        return

    # 확률이 유의미하게 남은 두 번째 팀에도 사본을 보낸다.
    for team, probability in department.probabilities.items():
        if team != department.choice and probability > 0.25:
            notify(ticket, team=team)

    # 환불은 금전이 움직이므로 확률이 높아도 사람 승인을 거친다.
    if answers["refund_requested"].noul > 0.7:
        flag_for_refund_approval(ticket)

    # 점수는 최상위 수준 번호로 나눠 0에서 1로 정규화한 뒤 가중합한다.
    top_level = len(TICKET_QUESTIONS["frustration"].criteria) - 1
    frustration = answers["frustration"].score / top_level
    priority = 0.7 * frustration + 0.3 * answers["churn_risk"].noul

    assign(ticket, team=department.choice, priority=priority)
```

질문을 쪼개 두고 가중치를 코드에서 정하는 것이 이 설계의 핵심이다.
문서도 같은 점을 강조한다.
여러 독립 요인에 의존하는 판단이라면 요인별로 따로 묻고 자기 논리로 합치라는 것이며,
우선순위가 바뀌면 프롬프트를 다시 쓰는 대신 가중치 값을 바꾸면 된다.

## 값 정하기

지도는 임계값을 하나도 제시하지 않는다.
그런데 위 코드에서 보듯 실제 동작을 정하는 것은 임계값이므로, 시작값과 그 근거를 스스로 정해야 한다.

| 값                       | 무엇을 정하는가                         | 시작값의 근거                                     | 무엇을 재서 고칠 것인가                        |
| ------------------------ | --------------------------------------- | ------------------------------------------------- | ---------------------------------------------- |
| Choice의 confidence 하한 | 자동 분기할지 사람에게 넘길지           | 사람에게 넘기는 비율이 감당 가능한 수준이 되는 값 | 수동 처리 건수와 그중 자동 처리가 옳았을 비율  |
| 두 번째 후보 확률 하한   | 사본을 보낼지                           | 잘못 보낸 사본의 비용이 놓친 비용보다 작아지는 값 | 사본을 받은 팀이 실제로 처리한 비율            |
| Noul 임계값              | 탐지를 행동으로 옮길지                  | 거짓 양성과 거짓 음성의 비용 비율                 | 탐지 후 되돌린 건수와 놓쳐서 사고가 난 건수    |
| Score 가중치             | 여러 요인 중 무엇이 우선순위를 지배할지 | 현재 운영 규칙을 숫자로 옮긴 값                   | 우선순위 상위 구간의 실제 처리 순서와의 불일치 |

confidence와 probability를 혼동하지 않는 것이 여기서 중요하다.
확률은 각 선택지에 얼마씩 배분되었는지이고, confidence는 그 분포가 얼마나 한쪽으로 몰렸는지다.
문서의 confidence 페이지에 실린 대화형 설명기는 Choice에서
선택지 수와 최고 확률로부터 `(선택지수 × 최고확률 − 1) / (선택지수 − 1)` 를 계산해
0과 1 사이로 자른 값을 보여 준다.
선택지가 셋일 때 최고 확률이 33.3%면 confidence는 0이고, 100%면 1이 된다.

그래서 임계값을 두 축으로 나눠 걸 수 있다.
무엇을 골랐는지로 분기하고, 얼마나 확실한지로 자동화 여부를 가르는 것이다.
확률 하나만 보면 선택지가 많을 때 최고 확률이 낮게 나오는 상황을 불확실과 구분할 수 없다.

## 트레이드오프

### 질문을 쪼갤수록 제어권은 늘고 설계 부담도 늘어난다

이 설계가 권하는 것은 큰 판단 하나를 작은 질문 여럿으로 나누고 코드에서 합치는 것이다.
얻는 것이 분명하다.
각 요인의 가중치를 코드에서 조정할 수 있고, 어떤 요인이 결과를 뒤집었는지 로그에 남고,
요인 하나를 고쳐도 나머지가 영향을 받지 않는다.

대가는 쪼개는 판단 자체가 설계 작업이 된다는 점이다.
어떤 요인들로 나눌지, 각 요인이 서로 독립인지, 가중치를 어떻게 줄지는 도메인 지식이 필요한 결정이고
그 결정이 틀리면 개별 질문의 정확도와 무관하게 결과가 어긋난다.
프롬프트 하나에 맡길 때는 모델이 암묵적으로 하던 일을 사람이 명시적으로 하게 되는 것이며,
명시적인 쪽이 고치기 쉬운 대신 처음에 더 비싸다.

그리고 남는 어려움이 있다.
요인들이 실제로는 독립이 아닐 때다.
불만과 이탈 위험은 상관이 높으므로 둘을 따로 묻고 더하면 같은 신호를 두 번 세게 된다.
문서는 요인이 독립일 때를 전제로 조언하고, 독립이 아닐 때 무엇을 해야 하는지는 말하지 않는다.

### 검증과 가드레일로 쓰면 비용은 줄지만 실패가 겹친다

Universal Verification 범주의 논리는 단순하다.
LLM 호출보다 훨씬 싸므로 모든 입력과 출력과 도구 호출에 의미 검사를 걸 수 있다는 것이다.
비용 구조만 보면 맞는 이야기다.

문제는 검사기도 모델이라는 점이다.
LLM이 놓치는 것을 잡으라고 둔 검사기가 놓치는 경우를 무엇이 잡는지가 정해지지 않는다.
두 모델의 실패가 독립이면 겹쳐 쓰는 것이 이득이지만,
같은 종류의 텍스트에서 같은 방향으로 어긋나는 실패는 상관이 높을 가능성이 있다.
특히 탈옥과 프롬프트 주입처럼 적대적으로 설계된 입력은
두 모델을 동시에 속이도록 만들어질 수 있다는 점에서 독립 가정이 가장 약한 자리다.

그래서 가드레일을 얹을 때 확인해야 할 것이 정해진다.
검사기가 잡은 건수가 아니라, 검사기를 통과한 뒤에 사고가 난 건수다.
전자는 늘 인상적이고 후자만이 검사기의 가치를 재며,
후자를 세려면 검사기를 통과한 표본을 따로 감사하는 절차가 필요하다.

### 산업별 목록은 탐색을 돕고 적용 범위를 과대평가하게 만든다

열여덟 개 묶음은 채용과 영업과 고객 지원과 보험과 금융 범죄와 법무와 커머스와 모더레이션과 광고와 게임에 걸쳐 있다.
자기 분야가 목록에 있으면 적용 가능성을 빠르게 가늠할 수 있다는 점이 이 지도의 효용이다.

동시에 목록의 항목들은 난이도가 전혀 다른데 같은 무게로 나열된다.
티켓을 부서로 분류하는 일과 보험 청구에서 사기 지표를 탐지하는 일은
둘 다 한 줄로 적혀 있지만 필요한 정확도와 실패 비용이 자릿수로 다르다.
채용에서 이력서를 직무 기준으로 평가하고 후보를 매칭하는 항목은
차별 규제와 설명 의무가 걸린 영역인데 그 사실이 언급되지 않는다.

이 지도를 쓸 때 항목마다 덧붙여야 할 질문이 있다.
틀렸을 때 누가 무엇을 잃는가다.
답이 티켓이 잘못된 큐로 간다는 것이면 바로 시작해도 되고,
답이 지원자가 이유를 모른 채 걸러진다는 것이면 지도의 한 줄로 시작할 일이 아니다.

## 함정

### 지도의 한 줄이 호출 한 번을 뜻하지 않는다

검색과 랭킹과 검수 항목은 후보 수만큼 질문이 반복된다.
후보 천 개를 재정렬한다면 질문도 천 개이고,
쌍 비교로 재정렬한다면 비교 횟수가 후보 수에 비례해 더 크게 늘어난다.
100배 싸다는 서술이 단가에 대한 것이고 총액에 대한 것이 아니라는 점을 놓치면
예산 추정이 자릿수로 어긋난다.

### 선택지에 other를 넣지 않으면 분포가 조용히 망가진다

Choice는 주어진 선택지 중에서 고른다.
입력이 어느 선택지에도 맞지 않으면 모델은 그래도 하나를 고르며,
그때 확률이 여러 선택지에 퍼져 confidence가 낮아지는 것이 정상적인 신호다.
그러나 우연히 한쪽으로 몰리면 잘못된 범주가 높은 확신과 함께 나온다.
문서가 선택지 목록이 모든 입력을 덮지 못할 수 있으면
`other`나 `none of the above`를 넣으라고 적은 이유가 이것이다.

### 확신이 낮다는 것은 모른다는 뜻이 아니다

confidence가 낮게 나오는 상황은 둘이고 대응이 다르다.
정말로 애매한 입력일 수도 있고, 선택지 설계가 나빠서 두 선택지가 겹칠 수도 있다.
후자는 사람에게 넘겨도 사람 역시 헷갈리며,
반복해서 같은 두 선택지에 확률이 갈린다면 그것은 입력의 문제가 아니라 범주 정의의 문제다.
수동 처리로 넘어간 건들의 확률 분포를 모아 보면 어느 쪽인지 구분된다.

### 지도는 사례를 주고 평가 방법을 주지 않는다

이 페이지에는 어떻게 정확도를 잴지, 어떤 표본으로 검증할지, 어느 수준이면 배포해도 되는지가 없다.
사례가 구체적이어서 바로 만들 수 있을 것처럼 보이지만,
정답이 있는 표본 수백 개를 만들어 각 질문의 정확도를 재는 단계가 빠지면
배포 후에 무엇이 틀렸는지 알 방법이 없다.
특히 Score는 사람끼리도 수준 판정이 갈리므로, 사람 두 명의 일치율을 먼저 재는 것이 상한선을 알려 준다.

## 체크리스트

- 내 문제가 다섯 범주 중 어느 근거에 걸리는지 정했는가 — 속도인가, 비용인가, 제어 흐름인가
- 그 근거가 되는 수치를 내 작업 부하에서 직접 재 보았는가
- 하려는 결정을 열 가지 형태 중 하나로 이름 붙였는가
- 그 형태에 맞는 질문 타입을 골랐는가 — 범주면 Choice, 있고 없음이면 Noul, 정도면 Score
- 질문 하나로 끝나는지, 후보 수만큼 반복되는지 확인했는가
- Choice 선택지가 모든 입력을 덮는가, 아니면 `other`를 넣었는가
- Score의 각 수준을 말로 적어 구분되게 썼는가
- 여러 요인으로 쪼갰다면 그 요인들이 서로 독립인지 검토했는가
- confidence 임계값과 확률 임계값을 따로 정했는가
- 임계값마다 그 값을 고칠 때 볼 지표를 정했는가
- 정답이 있는 표본으로 각 질문의 정확도를 재 보았는가
- 틀렸을 때 누가 무엇을 잃는지 항목별로 적었는가

## 기억할 원칙

### 결정의 모양을 먼저 이름 붙이면 도구 선택이 따라온다

이 지도에서 가장 오래 쓸 부분은 산업별 목록이 아니라 열 가지 결정 형태다.
분류와 탐지와 점수와 라우팅과 검색과 검수는 TypeSafe에만 있는 개념이 아니라
판단을 자동화하는 모든 시스템에 있는 모양이고, 각각이 요구하는 출력의 형태가 다르다.

이 이름들이 유용한 이유는 도구보다 먼저 오기 때문이다.
하려는 일이 분류인지 점수 매기기인지 정하면
필요한 출력이 범주 이름인지 순서 있는 값인지가 정해지고,
그러면 정확도를 어떻게 잴지와 임계값을 어디에 걸지도 함께 정해진다.
반대로 도구를 먼저 고르면 그 도구가 잘하는 모양에 문제를 맞추게 된다.

실천으로 옮기면 한 문장이다.
무엇을 쓸지 정하기 전에 무엇을 결정해야 하는지를 위 열 개 중 하나로 적어 본다.
적히지 않으면 아직 자동화할 준비가 안 된 것이고,
그 상태에서 도구를 붙이면 잘 도는 시스템을 만든 뒤에 무엇을 만들었는지 모르게 된다.

### 프롬프트에 담긴 판단 기준은 코드로 꺼낼수록 오래간다

이 문서 전체가 권하는 방향은 판단을 잘게 나누고 결합 규칙을 코드에 두는 것이다.
그 이유를 문서는 수정 편의로 설명한다.
우선순위가 바뀌면 프롬프트를 다시 쓰는 대신 가중치 값을 바꾸면 된다는 것이다.

편의보다 큰 이유가 하나 더 있다.
코드에 있는 가중치는 읽을 수 있고, 버전 관리되고, 리뷰되고, 테스트된다.
프롬프트 문장 안에 녹아 있는 우선순위는 그중 어느 것도 되지 않으며,
여섯 달 뒤에 왜 이 항목이 먼저 처리되는지 물으면 아무도 답하지 못한다.

그래서 어떤 모델을 쓰든 적용되는 원칙이 나온다.
모델에게는 사실 판단을 맡기고 가치 판단은 코드에 남기는 것이다.
이 고객이 화가 났는지는 모델이 잘 보지만,
화난 고객을 이탈 위험보다 먼저 처리할지는 조직이 정할 일이며 그 결정은 숫자로 적혀 있어야 한다.
