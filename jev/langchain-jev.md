# LangChain에서 Jev로 에이전트 루프의 결정을 분리하기

원문: [Building a Harness with Jev](https://www.langchain.com/blog/building-a-harness-with-jev)

## 소개

에이전트는 루프로 돈다.
LLM이 무엇을 할지 정하고, 도구가 실행하고, 모델이 결과를 평가하고, 작업이 끝날 때까지 그 루프를 계속한다.

글은 에이전트를 소프트웨어에 붙이기 어려웠던 이유와 그것을 푼 두 가지 원시를 먼저 짚는다.
도구 호출(tool calling)이 모델로 하여금 구조화된 요청을 하고 구조화된 결과를 받게 했고,
구조화된 출력(structured outputs)이 결과를 정해진 형태로 돌려주게 했다.

그런데 그 둘이 갖춰져도 에이전트 루프는 여전히 느리고 비싸다.
결정 하나마다 또 한 번의 모델 호출이 필요하기 때문이다.

이 지점에 [Jev](jev.md)를 넣자는 것이 이 글의 제안이다.
TypeSafe AI가 낸 모델이며, 분류 작업에서 비슷한 LLM 대비 추론이 최대 200배 빠르고 비용이 400배 낮다고 회사가 보고한다고 글은 적는다.
이 문장의 주어가 회사라는 점을 글이 밝혀 둔 것은 기억해 둘 만하다.

글이 다루는 범위는 세 가지다.
Jev가 어떻게 동작하는지, 에이전트 루프의 어디에 들어가는지, LangChain과 어떻게 쓰는지다.

## 동작 방식

Jev는 전통적인 LLM이 아니며 텍스트를 생성하지 않는다.
TypeSafe 팀이 System One 모델이라 부르는 것이다.
글의 정의를 그대로 옮기면, 소프트웨어가 직접 쓸 수 있는 빠르고 구조화된 결정을 내리도록 만들어진 AI 모델의 한 부류다.
상태(state)를 평가하고 타입이 정해진 답과 확률을 돌려준다.
보정된 결정을 위한 강화학습(RLCD, reinforcement learning for calibrated decisions)으로 학습된다.

호출할 때는 상태와 그 상태에 대한 질문들을 보낸다.
글이 TypeSafe 문서의 지원 티켓 예제를 질문 하나로 줄여 보여 준다.

```json
{
  "model": "jev-latest",
  "state": "Hi, I've been trying to connect my Stripe account for 3 days and it keeps failing. I'm losing sales. Please help ASAP.",
  "questions": {
    "is_urgent": {
      "type": "noul",
      "instructions": "The message conveys urgency or time-sensitivity"
    }
  }
}
```

응답은 이렇게 온다.

```json
{
  "is_urgent": {
    "type": "noul",
    "noul": 0.999
  }
}
```

긴급할 확률이 99.9%라는 뜻이고, 애플리케이션은 이 값으로 티켓 우선순위를 정할 수 있다.

질문은 세 종류를 지원한다.

| 종류     | 하는 일                                      | 돌려주는 것                      |
| -------- | -------------------------------------------- | -------------------------------- |
| `choice` | 주어진 선택지 집합에서 고른다                | 선택지별 확률과 전체 확신도      |
| `score`  | 낮음·중간·높음처럼 순서가 있는 수준에 매긴다 | 연속 점수와 그 바탕 분포, 확신도 |
| `noul`   | 예 또는 아니오로 답한다                      | 진술이 참일 확률                 |

여기서 이 모델의 비용 구조를 정하는 성질이 하나 있다.
한 요청에서 같은 상태에 대해 여러 질문을 할 수 있고, System One 모델은 한 요청의 모든 질문을 병렬로 평가한다.
글의 표현으로는 질문을 추가해도 응답 시간이 거의 변하지 않고, 추가 질문의 토큰 비용만 드는데 그것이 싸다.

이 성질이 설계에 미치는 영향이 크다.
LLM으로 분류할 때는 질문을 늘리면 출력이 길어지고 지연이 늘어나므로 질문 수를 아끼게 된다.
Jev에서는 그 압력이 사라지므로, 한 번의 평가에서 물을 수 있는 것을 전부 묻는 편이 낫다.
글이 요약한 대로 Jev는 텍스트 생성에도, 순차적 결정에도 묶여 있지 않다.

### 구조가 강제하는 설계 제약

글은 Jev를 블랙박스로 다루지만, [외부 구조 분석](architecture-unmasked.md)이 밝힌 정보 경계가 이 미들웨어를 설계하는 방식을 직접 규정한다.

규칙이 둘이다. 모든 질문은 `state`를 볼 수 있고, 어떤 질문도 다른 질문의 텍스트나 답을 보지 못한다.

분석에 실린 실험이 이 경계를 수치로 보여 준다.
비밀 코드를 형제 질문 안에 넣고 다른 질문에서 그 코드를 물으면 확률이 0.00이고, 같은 코드를 `state`에 넣으면 0.90~0.92다.

이 경계가 미들웨어 설계에 주는 규칙이 셋 나온다.

여러 질문이 공유해야 하는 맥락은 전부 `state`에 넣어야 한다.
공통 지침을 각 질문의 `instructions`에 복사해 넣으면 토큰을 낭비할 뿐 아니라 공유 상태 캐시의 이점을 잃는다.

질문 사이에 의존이 있으면 한 호출로 표현할 수 없다.
“이 도구가 위험한가”를 먼저 정하고 그 답에 따라 “얼마나 위험한가”를 묻는 구조라면 호출을 두 번 나누거나 결합 질문 하나로 만들어야 한다.
맥락을 공유한다고 워크플로의 논리 구조가 사라지지는 않는다.

그리고 선택지 목록이 확률을 바꾼다.
같은 분석이 선택지 순서를 뒤집자 확률이 0.84~0.89에서 0.93~0.96으로 옮겨 갔다고 보고했다.
아래에서 임계값을 정하는 모든 논의가 이 변동 폭 위에서 이루어진다는 뜻이다.

## 구현하기

LangChain 통합은 `TypeSafeClassifier`로 Jev를 노출한다.
상태와 질문을 `.invoke()`에 넘기면 대화 응답이 아니라 분류 결과를 받는다.

`langchain-typesafe`를 설치하고 `TYPESAFE_API_KEY`를 설정한 뒤 호출한다.

```python
from langchain_typesafe import Noul, TypeSafeClassifier

classifier = TypeSafeClassifier()

response = classifier.invoke(
    state=(
        "The deploy failed twice and customers are seeing 500s. "
        "Can someone look now?"
    ),
    questions={
        "urgent": Noul(
            instructions="Does this need attention right now?"
        ),
    },
)

urgency = response.nouls["urgent"].noul
```

상태에는 텍스트와 구조화된 데이터, LangChain 메시지를 넣을 수 있다.
그래서 에이전트가 이미 들고 있는 맥락을 그대로 노드나 미들웨어 훅에서 Jev에 넘기기 쉽다고 글은 설명한다.

마지막 줄이 중요하다.
돌아오는 것이 참이냐 거짓이냐가 아니라 확률이다.
이 값을 어떻게 임계값으로 바꿀지는 호출하는 쪽이 정해야 하며, 글은 그 결정을 다루지 않는다.

### 모델 라우팅

단순 조회와 어려운 디버깅 작업에 같은 모델을 쓸 이유가 없다는 것이 첫 번째 용례다.
모델 라우팅 미들웨어가 Jev로 요청을 평가하고 정해 둔 기준에 따라 모델을 고른다.

```python
from langchain.agents import create_agent
from langchain_typesafe.experimental.middleware import (
    ModelChoice,
    ModelRouterMiddleware,
)

router = ModelRouterMiddleware(
    choices={
        "fast": ModelChoice(
            model="openai:luna",
            criteria="Direct lookups, extraction, and localized changes.",
        ),
        "powerful": ModelChoice(
            model="openai:sol",
            criteria="Architecture and high-stakes decisions.",
        ),
    },
    instructions="Choose the least costly model that can complete the task.",
)

agent = create_agent("openai:gpt-5.6-luna", middleware=[router])
```

라우터는 가장 최근 사용자 메시지에서 모델을 고르고, 실행 전체에 걸쳐 그 모델을 쓴다.
확률과 확신도는 에이전트 상태에 남아 있어서 나중에 꺼내 볼 수 있다.

이 두 문장에 설계 결정이 둘 들어 있다.
판단 근거가 마지막 사용자 메시지 하나이고, 한 번 고른 모델이 실행 내내 유지된다는 것이다.
두 결정 모두 비용을 아끼지만, 뒤에서 볼 대가가 따른다.

주목할 점은 `experimental` 네임스페이스다.
두 미들웨어 모두 `langchain_typesafe.experimental.middleware`에 있다.

### Auto Mode

두 번째 용례는 안전장치다.
글은 이 문제를 솔직하게 연다.
에이전트는 본질적으로 신뢰할 수 없으며, 자연스럽게든 충분히 동기가 있는 공격자에 의해서든 나쁜 지시를 받아 원하지 않은 행동을 하도록 설득될 수 있다.

그리고 현재 상태를 짚는다.
claude와 codex, cursor 같은 코딩 하네스들은 위험한 행동을 실행 전에 분류하는 방법을 어떤 형태로든 내놓았고 그것이 에이전트에 대한 신뢰를 조금씩 쌓아 왔는데,
지금까지 이 분류 단계는 하네스의 비공개 부분에 갇혀 있었다는 것이다.
싸고 성능 좋은 분류기 모델이 생겼으니 같은 패턴을 모든 에이전트에 적용할 수 있다는 것이 글의 주장이다.

```python
from langchain.agents import create_agent
from langchain_typesafe.experimental.middleware import (
    AutoModeMiddleware,
)

guardrail = AutoModeMiddleware(tools=["bash"])

agent = create_agent("openai:gpt-5.6-luna", middleware=[guardrail])
```

`AutoModeMiddleware`가 Jev로 도구 호출이 취할 수 있는 위험한 결정을 검사하고, 도구가 실행되기 전에 호출을 막는다.

여기서 설정으로 드러난 것은 `tools=["bash"]` 하나다.
무엇을 위험으로 볼지, 어느 확률에서 막을지, 막힌 뒤에 무엇이 일어나는지는 글에 없다.

## 값 정하기

글이 값을 하나도 제시하지 않으므로, 쓰려면 직접 정해야 하는 것들이 남는다.
아래는 글에서 도출되는 결정 지점과 그 근거다.

| 정해야 할 것            | 근거                                                 | 무엇을 재야 하는가                             |
| ----------------------- | ---------------------------------------------------- | ---------------------------------------------- |
| `noul` 임계값           | 0.999 같은 값이 예시로 나오지만 경계는 용도가 정한다 | 임계값을 바꿔 가며 본 거짓 양성과 거짓 음성 수 |
| 차단과 확인 요청의 경계 | 막을 확률과 사람에게 물을 확률은 같을 이유가 없다    | 사람에게 넘어간 비율과 그중 실제 위험 비율     |
| 라우팅 확신도 하한      | 확신도가 낮으면 강한 모델로 보내는 편이 안전하다     | 약한 모델로 갔다가 실패해 재시도한 비율        |
| 한 요청에 담을 질문 수  | 병렬 평가라 늘려도 지연이 거의 안 늘어난다           | 질문 수에 따른 실제 지연과 토큰 비용           |
| Jev를 쓸 결정의 범위    | 분류로 환원되는 결정만 대상이다                      | LLM 호출 중 분류로 대체 가능한 비율            |

`choice`와 `score`가 확신도를 따로 돌려준다는 점을 활용할 수 있다.
확률이 높아도 확신도가 낮은 경우와 둘 다 높은 경우를 다르게 처리하는 것이 이 모델을 쓰는 이유에 가깝다.
글은 확신도가 상태에 남는다고만 하고 그것으로 무엇을 하라고는 말하지 않는다.

## 트레이드오프

### 확률을 돌려주는 것이 판단을 없애 주지는 않는다

이 모델이 파는 것은 타입이 정해진 답과 확률이다.
LLM에게 위험한지 물어보고 텍스트를 파싱하던 것에 비하면 분명한 개선이다.
파싱이 사라지고, 값이 비교 가능해지고, 임계값을 코드로 쓸 수 있다.

그런데 그 임계값을 정하는 일이 새로 생긴다.
0.999는 막고 0.95는 통과시킬 것인가, 아니면 0.7부터 사람에게 물을 것인가.
이 값이 거짓 양성과 거짓 음성의 교환 비율을 정하며, 그 비율은 도구가 무엇을 하느냐에 따라 전혀 다르다.
파일을 읽는 명령과 프로덕션 데이터베이스를 지우는 명령에 같은 임계값을 쓸 이유가 없다.

글은 이 문제를 언급하지 않는다.
`AutoModeMiddleware(tools=["bash"])` 한 줄로 끝나므로, 읽는 사람은 기본값이 합리적으로 정해져 있다고 짐작하게 된다.
그런데 안전장치의 기본 임계값은 그것을 만든 쪽이 정한 위험 선호이지 쓰는 쪽의 것이 아니다.

여기서 빠져나갈 길이 좁다.
임계값을 높이면 통과하는 위험이 늘고, 낮추면 사람에게 물어보는 횟수가 늘어 결국 확인을 대충 하게 된다.
확인 피로가 쌓이면 안전장치는 통과 버튼을 누르는 의식이 되고, 그러면 없는 것과 비슷해진다.
그래서 이 층을 도입하는 일의 실제 작업은 미들웨어를 꽂는 것이 아니라, 도구마다 다른 임계값을 정하고 그것을 측정으로 고쳐 나가는 것이다.

### 분류기를 뚫는 것이 목표가 되면 분류기도 공격면이다

글은 에이전트가 동기가 있는 공격자에게 설득될 수 있다는 점을 인정하면서 그 해법으로 분류기를 제시한다.
그런데 그 분류기 역시 공격자가 제어하는 텍스트를 입력으로 받는다.

여기가 이 설계의 핵심 긴장이다.
`AutoModeMiddleware`가 검사하는 도구 호출은 에이전트가 만든 것이고, 에이전트는 웹 페이지나 이메일 같은 외부 내용을 읽고 그것을 만든다.
공격자가 에이전트를 설득할 수 있다면, 같은 경로로 분류기가 볼 상태에도 영향을 줄 수 있다.

Jev가 텍스트를 생성하지 않는다는 점은 도움이 된다.
지시를 따라 다른 일을 하게 만들 여지가 작기 때문이다.
그러나 판단을 특정 방향으로 밀어 넣는 것과 다른 일을 시키는 것은 다르다.
위험한 명령을 무해해 보이게 감싸는 것은 여전히 남는 문제이며, 분류기가 작고 빠를수록 그런 위장에 약할 수 있다.

그래서 이 층을 유일한 방어로 두는 것이 위험하다.
샌드박스와 권한 제한, 되돌릴 수 없는 작업에 대한 별도 취급이 함께 있어야 하고, 분류기는 그 위에 얹는 한 겹이다.
글이 코딩 하네스들의 비공개 분류기를 열어 모두에게 준다는 틀로 이야기하는데,
그 하네스들에서 분류기는 여러 겹 중 하나였다는 사실은 함께 전해지지 않는다.

### 마지막 메시지로 고르고 실행 내내 유지하는 라우팅

라우터가 가장 최근 사용자 메시지에서 모델을 고르고 실행 전체에 그것을 쓴다는 것은 명시된 동작이다.
싸고 단순하며, 라우팅 자체가 병목이 되지 않게 한다.

대가는 작업의 난이도가 도중에 드러나는 경우다.
단순한 조회로 시작했는데 중간에 어려운 디버깅으로 번지는 일은 흔하고, 그때 에이전트는 이미 약한 모델에 묶여 있다.
반대 방향의 낭비도 있다. 어려워 보이는 첫 메시지 때문에 강한 모델을 고르고, 실제 작업은 단순했던 경우다.

그리고 판단 근거가 마지막 사용자 메시지 하나라는 점이 이 문제를 키운다.
앞선 대화에서 드러난 맥락이나 지금까지 실행한 도구의 결과는 보지 않는다.
사용자가 한 줄로 물어도 그 앞에 긴 작업이 있었다면 난이도는 그 맥락에 있는데, 라우터는 그것을 보지 않는다.

여기서 흔히 떠올리는 해법, 즉 매 단계 다시 라우팅하는 방식은 비용이 아니라 일관성에서 걸린다.
모델이 실행 중간에 바뀌면 앞서 쌓은 맥락의 해석이 달라지고, 도구 호출 형식이나 응답 습관도 달라진다.
그래서 한 번 고르고 유지하는 것이 게으른 선택이 아니라 방어적인 선택이며,
바꾸려면 어느 지점에서 다시 고를지를 명시적으로 정해야 한다.

### 200배와 400배가 옮겨 쓸 수 있는 숫자인지

글은 회사가 보고한 수치라고 밝히고 인용한다.
출처를 밝힌 것은 정직하지만, 그 수치가 이 글의 제안 전체를 떠받친다는 점은 짚어 둘 만하다.
Jev를 루프에 끼우는 것이 이득이려면, 추가되는 호출의 비용과 지연이 그것이 아끼는 LLM 호출보다 작아야 하기 때문이다.

라우팅에서는 이 계산이 쉽다.
한 번의 분류로 여러 번의 강한 모델 호출을 약한 모델로 돌리는 것이므로, 분류 비용이 차액보다 작으면 이득이다.

안전장치에서는 계산이 다르다.
모든 도구 호출마다 분류가 붙으므로 비용과 지연이 호출 수에 비례해 늘고, 아끼는 것은 없다.
여기서 사는 것은 속도가 아니라 안전이며, 그렇다면 200배와 400배는 이 용례를 정당화하는 숫자가 아니라 감당 가능하게 만드는 숫자다.
글은 두 용례를 같은 도입부 아래 두면서 이 구분을 하지 않는다.

그리고 비교 대상이 비슷한 LLM이라는 것 외에 조건이 없다.
어떤 모델과 어떤 분류 작업에서 잰 것인지가 없으므로, 자기 작업에 옮겨 쓰려면 다시 재는 수밖에 없다.

그런데 다시 재는 것에도 제약이 있을 수 있다.
[SemIf 스레드](semif.md)에서 jakozaur가 TypeSafe 이용약관 1(v)와 MCA 2.3(f)이 사용자의 “벤치마크나 성능 정보” 게시를 금지한다고 지적했다.

이 조항이 사실이라면 이 글의 수치는 검증하기 특히 어려운 종류가 된다.
회사가 조건 없이 배수를 발표하고, 제3자가 그것을 공개적으로 반박할 수 없기 때문이다.
그래서 이 글이 “회사가 보고한다”고 주어를 밝힌 것이 형식적 단서가 아니라 실질적인 경고로 읽혀야 한다.

조직 안에서 재는 것은 여전히 가능하다. 그 결과를 바깥과 공유할 수 없을 뿐이다.
그 말은 같은 측정을 모든 도입 조직이 각자 반복하게 된다는 뜻이고, 도입 비용에 그 시간을 포함시켜야 한다.

### LangChain에 묶이지 않는 선택지도 나오고 있다

이 글은 LangChain 미들웨어라는 형태로 통합을 제시하는데, 같은 아이디어를 프레임워크 없이 구현하려는 시도도 나왔다.

`jodan-alberts/sokit`이 그 예다. Jev나 다른 System 1 모델을 위한 LangChain 같은 하네스라고 스스로 소개한다.

이것이 시사하는 바가 있다.
결정 모델을 에이전트 루프에 끼우는 데 필요한 것은 대부분 프레임워크 기능이 아니라 규약이다.
어디서 분류하고, 임계값을 어디 두고, 실패했을 때 무엇을 기본값으로 할지를 정하는 일이다.

그렇다면 LangChain 미들웨어를 쓰는 값은 그 규약을 대신 정해 준다는 데 있지 통합 자체에 있지 않다.
그리고 그 규약이 자기 상황과 다르면 — 예를 들어 라우팅을 마지막 메시지가 아니라 누적 맥락으로 하고 싶다면 — 미들웨어를 쓰는 것이 오히려 방해가 된다.

두 미들웨어가 `experimental` 네임스페이스에 있다는 사실도 같은 방향을 가리킨다.
지금 이 통합에 깊이 묶이는 것보다, 분류 호출을 자기 코드의 얇은 함수로 감싸 두고 그 안에서 미들웨어를 쓰든 직접 호출하든 바꿀 수 있게 두는 편이 안전하다.

## 함정

돌아오는 값이 불리언이 아니라 확률이다. `response.nouls["urgent"].noul`은 0과 1 사이의 수이므로, 그대로 조건문에 넣으면 0이 아닌 모든 값이 참이 된다.

임계값이 도구마다 달라야 한다. 파일 읽기와 되돌릴 수 없는 삭제에 같은 기준을 쓰면 한쪽은 과하고 한쪽은 모자란다.

두 미들웨어 모두 `experimental` 네임스페이스에 있다. API가 바뀔 수 있다는 뜻이므로 버전을 고정하는 편이 안전하다.

라우팅은 마지막 사용자 메시지만 본다. 앞선 맥락에서 난이도가 드러나는 작업이라면 판단 근거가 부족하다.

한 번 고른 모델이 실행 내내 유지된다. 도중에 난이도가 올라가도 자동으로 바뀌지 않는다.

분류기도 공격자가 제어할 수 있는 텍스트를 본다. 이 층을 유일한 방어로 두면 안 된다.

질문을 늘리는 비용이 싸다는 것은 질문을 아끼지 말라는 뜻이지, 질문의 품질이 덜 중요하다는 뜻이 아니다. `instructions` 문구가 결과를 정한다.

`state`에 LangChain 메시지를 통째로 넣을 수 있다는 것은 편리하지만, 그만큼 공격자가 심은 내용도 함께 들어간다.

질문끼리는 서로를 보지 못한다. 한 질문의 `instructions`에 적은 공통 맥락은 다른 질문에 전달되지 않으므로 `state`에 넣어야 한다.

선택지 순서가 확률을 바꾼다. 임계값 근처에서 동작하는 분류라면 선택지 목록을 정렬하거나 항목을 추가하는 변경이 결정을 뒤집을 수 있다.

컨텍스트가 32K다. 대화 기록을 통째로 `state`에 넣는 방식은 긴 세션에서 한계에 닿는다.

`jev-latest`를 쓰면 모델이 예고 없이 바뀐다. 임계값을 쓰는 자리에서는 [날짜가 붙은 고정 슬러그](jev-1-13-openrouter.md)를 쓴다.

측정 결과를 외부에 공개하는 것이 약관에 걸릴 수 있다. 도입 근거를 블로그에 쓸 계획이라면 먼저 확인한다.

## 확인하기

도입 전에 확인할 것은 두 가지이고 둘 다 자기 데이터로 재야 한다.

```python
# 1. 분류가 실제로 맞는지 — 라벨이 있는 과거 사례로 임계값별 오류를 센다
from langchain_typesafe import Noul, TypeSafeClassifier

classifier = TypeSafeClassifier()

def probe(samples, threshold):
    """samples: [(state, expected_bool)] — 임계값 하나에 대한 오분류 수를 센다."""
    fp = fn = 0
    for state, expected in samples:
        p = classifier.invoke(
            state=state,
            questions={"risky": Noul(instructions="This action is destructive or irreversible")},
        ).nouls["risky"].noul
        got = p >= threshold          # 여기가 정해야 할 값이다
        if got and not expected:
            fp += 1
        elif not got and expected:
            fn += 1
    return fp, fn

for t in (0.5, 0.7, 0.9, 0.99):
    print(t, probe(my_labeled_cases, t))
```

임계값을 하나 고르는 것이 아니라 곡선을 보고 정하는 것이 요점이다.
거짓 음성이 하나라도 있으면 안 되는 도구라면 임계값을 낮추고 사람에게 묻는 비율을 감수해야 한다.

두 번째는 비용과 지연이다.
질문 수를 1개에서 10개로 늘려 가며 같은 상태로 호출해 보면, 병렬 평가 주장이 자기 환경에서 성립하는지 바로 보인다.
그리고 그 지연을 아끼려는 LLM 호출의 지연과 비교해야 라우팅이 이득인지 알 수 있다.

## 체크리스트

- 확률을 임계값과 비교하고 있는가, 값을 그대로 조건으로 쓰고 있지는 않은가
- 도구마다 다른 임계값을 정했는가
- 차단할 확률과 사람에게 물을 확률을 구분했는가
- 확신도가 낮을 때의 동작을 정했는가
- 분류기 외의 방어(샌드박스, 권한 제한, 되돌릴 수 없는 작업의 별도 취급)가 있는가
- 라우팅 판단이 마지막 메시지만으로 충분한 작업인가
- `experimental` 네임스페이스의 API 변경에 대비해 버전을 고정했는가
- 200배와 400배를 자기 작업과 자기 기준 모델로 다시 쟀는가
- 공통 맥락을 `instructions`가 아니라 `state`에 넣었는가
- 질문 사이에 의존 관계가 없는지 확인했는가(있다면 호출을 나눴는가)
- 선택지 순서를 바꿔 확률 변동 폭을 쟀고, 임계값 여유가 그보다 큰가
- 고정 버전 슬러그를 쓰고 있는가
- 분류 호출을 얇은 함수로 감싸 미들웨어 교체가 가능하게 두었는가
- 안전장치 용례에서 호출 수를 곱한 월 비용과 누적 지연을 계산했는가

## 기억할 원칙

### 결정과 생성을 분리하면 각각을 다른 기준으로 최적화할 수 있다

이 글의 실제 제안은 새 모델을 쓰라는 것이 아니라, 에이전트 루프 안의 일을 두 종류로 나누라는 것이다.
열린 추론과 생성은 LLM이 하고, 빠르고 구조화된 결정은 그것을 위해 만든 것이 한다.

이 분리가 값을 만드는 이유는 두 일의 요구사항이 정반대이기 때문이다.
생성은 길고 유연해야 하므로 느리고 비싼 것을 감수한다.
결정은 짧고 자주 일어나므로 지연과 비용이 곧 설계 제약이 된다.
한 모델에 둘 다 맡기면 결정이 생성의 비용 구조를 물려받는다.

같은 형태가 다른 곳에도 있다.
데이터베이스에서 쿼리 플래너와 실행 엔진을 나눈 것,
컴파일러에서 타입 검사와 코드 생성을 나눈 것,
웹 서비스에서 라우팅과 처리를 나눈 것이 모두 같은 구조다.
앞단은 싸고 빨라야 하고 뒷단은 무거워도 되며, 그 경계가 있어야 앞단을 따로 최적화할 수 있다.

다만 분리에는 값이 따른다.
경계가 생기면 그 경계에서 정보가 줄어들고, 그래서 앞단이 뒷단만큼 잘 판단하지 못하는 경우가 생긴다.
라우터가 마지막 메시지만 보고 모델을 고르는 것이 정확히 그 손실이다.
그러니 이런 분리를 도입할 때 물어야 할 것은 앞단이 무엇을 못 보게 되는가이고,
그 손실이 감당 가능한 범위인지를 정하는 것이 설계자의 몫이다.

### 확률을 돌려주는 인터페이스는 결정을 호출자에게 넘긴다

이 모델이 불리언 대신 확률을 돌려주는 것은 구현 세부가 아니라 인터페이스 선택이다.
그리고 그 선택은 어디서 결정할지를 옮긴다.

불리언을 돌려주면 모델이 결정한 것이고, 확률을 돌려주면 호출자가 결정한다.
후자가 더 정직한 이유는 임계값이 도메인 지식이기 때문이다.
같은 0.8이 지원 티켓 우선순위에서는 충분하고 프로덕션 삭제 차단에서는 턱없이 낮은데, 모델은 그 차이를 알 수 없다.

그런데 정직한 인터페이스는 더 많은 일을 요구한다.
임계값을 정하고, 그것이 만드는 오류를 재고, 도구마다 다르게 두고, 데이터가 바뀌면 다시 정해야 한다.
그래서 확률을 돌려주는 API를 쓰면서 임계값을 한 번 정하고 잊는 것은 불리언 API를 쓰는 것보다 나쁘다.
모델이 정한 기본값이 적어도 만든 쪽의 측정에 기반했을 가능성이 있는 반면, 잊힌 임계값은 아무 근거도 없기 때문이다.

여기서 나오는 규칙은 이렇다.
확률이나 점수를 돌려주는 인터페이스를 쓸 때는 임계값을 코드 어딘가에 흩뿌리지 말고 한곳에 모으고,
각 값 옆에 그것을 정한 근거와 마지막으로 잰 날짜를 적어 두는 것이다.
근거 없는 임계값은 나중에 아무도 바꾸지 못하며, 바꾸지 못하는 값은 시간이 지나면 반드시 틀린 값이 된다.
