# Jevgrep: 코드가 하는 일을 물어 파일을 찾는 코딩 에이전트용 Jev 검색기

<https://github.com/dzhng/jevgrep>

HN 토론: <https://news.ycombinator.com/item?id=49880146> (5점, 0개 댓글)

GN 토론: <https://news.hada.io/topic?id=35208>

## 소개

Jevgrep은 코딩 에이전트가 낯선 저장소에서 관련 파일을 찾는 단계를 대신하는
CLI다.
“요청이 핸들러에 닿기 전에 인증은 어디서 검사하는가”처럼 동작을 질문하면,
관련 파일 목록과 읽을 단서, 원문 그대로의 소스 발췌를 표준 출력 한 번으로
돌려준다.
폴더, 파일, 선언 단위의 관련성 판단은 TypeSafe의 결정 모델 Jev가 맡고,
구현과 테스트는 그 출력을 받은 코딩 에이전트가 한다.
README의 한 줄 요약은 “같은 지능, 약 30% 낮은 비용”이다.

저장소는 2026년 9월 26일에 만들어졌고 MIT 라이선스의 TypeScript 프로젝트다.
2026년 10월 13일 기준 별 2,629개, 포크 192개다.
npm 패키지 이름은 `@dzhng/jevgrep`이고 명령은 `jg`이며,
Node.js 22 이상과 macOS, Linux, Windows를 지원한다.
Jev 호출은 Vercel AI Gateway, TypeSafe, OpenRouter, OpenCode Zen,
또는 TypeSafe 호환 엔드포인트 가운데 하나의 키로 한다.
Python이나 ripgrep을 따로 설치할 필요는 없다.

이 저장소의 다른 Jev 문서가 다루는 System One 모델과 RLCD 학습은
[System One 모델과 Jev](./jev.md)에 정리되어 있다.
Jevgrep은 그 모델을 “채팅이 아니라 결정”이라는 원래 용도대로,
코드 검색의 관련성 분류기로 쓴 사례다.

## 동작 방식

### 색인 없이 계층을 따라 내려간다

Jevgrep은 저장소 전체를 먼저 올리거나 임베딩 색인을 만들지 않는다.
디렉터리 메타데이터와 내용 미리보기로 어디를 더 탐색할지 정하고,
관련성 기준을 넘는 가지만 따라 내려간다.
`docs/architecture.md`는 고정된 상위 N개 제한 없이 기준을 통과한 파일을
모두 남긴다고 설명한다.
대신 소스 선택이 쓸모 있는 코드를 확인하기 전까지는 탐색 바이트 예산을 두고,
예산에 닿으면 검색이 불완전했다고 보고해 호출자가 검색 범위를 좁히게 한다.

판단은 여러 층으로 나뉜다.
관련성(relevance)과 범위(scope)를 따로 판단하고,
같은 클래스 계약을 다른 플랫폼에서 구현한 코드를 찾는 관계 패스가 있으며,
구체적으로 참조된 코드를 뒤따라 찾거나 앞선 선택을 철회하는 후속 패스가 있다.
버그가 있는 현재 구현도 “관련 있음”으로 센다는 점이 눈에 띈다.
보고된 동작을 만든 코드가 바로 고쳐야 할 코드이기 때문이다.

### 파서는 좌표만 주고 원문을 바꾸지 않는다

Python, Go, Rust는 패키지에 포함된 Tree-sitter WASM 문법으로,
TypeScript와 JavaScript는 TypeScript 컴파일러 파서로 선언 단위를 나눈다.
그 밖의 텍스트는 크기를 제한한 덩어리로 검색한다.
아키텍처 문서는 트리에서 코드를 다시 조립하지 말고 원래 바이트를 그대로
보존하라고 적고,
저장소의 코드는 절대 실행하지 않는다고 밝힌다.
문법 오류가 있는 트리나 CR만 쓰는 Python 파일은 줄 좌표가 어긋나므로
텍스트 방식으로 처리한다.

### 출력은 원문 발췌가 먼저 온다

표준 출력은 상태와 짧은 파일 요약으로 시작하고,
줄 번호가 붙은 원문 발췌가 이어지며,
선언과 호출 위치의 상세 목록이 마지막에 온다.
발췌가 없는 경로는 반드시 읽을 목록이 아니라 선택적인 단서로 표시된다.
출력 전체에 상한이 있고, 상한에 닿으면 생략 표시와 함께 `End context.`로
끝난다.
README는 이 출력이 생성된 답이 아니라 근거이며,
관련 파일을 모두 찾았다는 보장도 아니라고 분명히 적는다.

## 사용법

```sh
npm install -g @dzhng/jevgrep
jg auth      # 공급자를 고르고 키를 소유자 전용 설정 파일에 저장
jg skill     # 코딩 에이전트용 스킬 설치 (Claude Code, Codex, OpenCode 등)
jg files .   # 검색이 읽을 수 있는 파일 수를 최상위 디렉터리별로 센다
jg "How are database connections created, pooled, and closed?" ./src
jg "Which tests cover retry behavior when a request times out?" . \
  --exclude 'src/generated/'
```

CLI만 설치해서는 에이전트가 쓰지 않으므로 스킬 설치가 필수라고 README가
강조한다.
`jg skill`은 Vercel의 skills CLI를 불러 감지한 에이전트에 스킬을 넣고,
`npx skills add dzhng/jevgrep --skill jevgrep`으로 직접 설치할 수도 있다.
npm 패키지를 올려도 프로젝트에 설치된 스킬은 갱신되지 않으므로
`jg skill`을 다시 돌려야 한다.
인증은 대화형으로만 하고 환경 변수는 쓰지 않으며,
`jg doctor`가 합성 입력으로 설정을 확인한다.

검색은 무시 파일을 존중하고 숨김 파일, 의존성과 빌드 산출물, 바이너리,
명백한 자격 증명 파일을 뺀 뒤 해당 내용을 선택한 공급자를 거쳐 Jev로 보낸다.
README는 이 필터가 민감 정보 제거를 보장하지 않으니,
보내도 되는 루트를 고르라고 경고한다.
`jg files`는 키나 네트워크 요청 없이 읽을 수 있는 파일 수만 세며,
스킬 문서는 이것이 업로드 추정치나 개인정보 감사가 아니라고 덧붙인다.

## 측정 결과

평가는 조정한(tuned) Python SWE-bench 과제 10개로 했다.
코딩 에이전트는 `openai/gpt-5.6-sol`(중간 추론 강도, 이하 Sol)이고,
처음에 반드시 Jevgrep을 호출한 뒤 일반 도구를 쓸 수 있다.
비교 대상은 저장해 둔 Jev 없는 기준 실행이며 다시 돌리지 않았다.

| 실행                  | 해결 | Sol 비용 | Jev 비용          | 합계    | 기준 대비    |
| --------------------- | ---- | -------- | ----------------- | ------- | ------------ |
| Jev 없는 기준         | 8/10 | $7.6221  | -                 | $7.6221 | -            |
| 9월 27일 최종 후보    | 8/10 | $5.4397  | 최소 $1.57 (제외) | -       | Sol만 -28.6% |
| 9월 28일 속도 연구    | 8/10 | $5.3380  | 알 수 없음 (제외) | -       | Sol만 -30.0% |
| 9월 28일 0.4.3 총비용 | 8/10 | $4.1780  | $1.4784           | $5.6564 | -25.8%       |

README 표지의 “약 30%”는 Jev 비용을 뺀 Sol 비용만 비교한 수치이고,
Jev를 포함한 첫 측정은 0.4.3 재실행의 25.8%다.
Jev 비용은 `jev-1.13.0`의 공개 가격인 입력 100만 토큰당 $0.042로 계산한
추정치이며 출력 토큰은 무료다.
속도 연구는 기준보다 12.70% 빠르고 Sol 토큰을 41.51% 덜 썼다고 보고한다.

0.5.0에서는 선언 묶음을 키우고 질문 기준을 공유해 Jev 비용을 0.4.3보다
약 59% 줄였지만,
Sol과 Jev를 합친 비용은 0.4.3 실행보다 2~3% 높았다.
결과 문서는 이를 통계적 동등성이 아니라 사용자가 받아들인 제품 결정이라고
적고,
원래 15% 목표를 사용자가 완화했다는 사실도 숨기지 않는다.
연구 전체로는 Sol에 최소 $57.05, Jev에 최소 $18.78이 들었고,
32건의 요청은 비용을 확인하지 못했다.

## 분석

### 검색과 추론을 서로 다른 모델에 나누는 설계다

Jevgrep의 핵심 판단은 “어디를 볼 것인가”를 비싼 추론 모델에게서 떼어 내는
것이다.
코딩 에이전트는 낯선 저장소에서 `grep`과 파일 읽기를 반복하며 토큰을 쓰는데,
그 탐색의 상당 부분은 깊은 추론이 아니라 “이 파일이 질문과 관련 있나”라는
반복적인 분류다.
입력 100만 토큰당 $0.042이고 출력이 무료인 결정 모델에 그 분류를 맡기면,
Sol은 이미 골라진 원문을 읽는 데서 출발한다.

이 구조는 TypeSafe가 Jev를 내놓으며 내세운 System One과 System Two의 분업을
코드 검색에 그대로 옮긴 것이다.
에이전트 루프 전체를 대신하겠다는 주장이 아니라,
루프 안의 한 단계를 싼 모델로 바꾸겠다는 주장이다.
그래서 평가도 “더 많이 푼다”가 아니라 “같은 과제를 덜 들여 푼다”는
틀로 짜여 있다.

### 색인을 버린 대가로 신선도를 얻는다

언어 모델을 붙인 코드 검색은 흔히 임베딩 색인을 먼저 만드는 방식을 썼다.
Jevgrep은 색인을 만들지 않고 질의마다 계층을 내려가며 미리보기를 분류한다.
이렇게 하면 색인이 코드보다 뒤처지는 문제가 없고,
에이전트가 방금 고친 파일도 다음 질의에 바로 반영된다.
아키텍처 문서가 원문 스냅숏의 신선도 검사와 무시 규칙의 파일 시스템
식별자 검사를 여러 번 강조하는 것도 같은 맥락이다.

대가는 질의마다 비용이 든다는 점이다.
색인은 한 번 만들면 질의가 싸지만,
Jevgrep은 질문할 때마다 미리보기와 선언을 Jev로 보낸다.
캐시가 반복 질의를 줄여 주기는 하지만,
큰 저장소에서 넓은 질문을 하면 분류할 대상 자체가 많아진다.
GeekNews에서 i8hn3은 직접 써 보니 토큰을 무척 많이 먹는다며
프로젝트가 커서 그런 것 같다고 적었다.[^i8hn3]

### 평가 기록이 마케팅 문구보다 정직하다

이 저장소에서 가장 흥미로운 부분은 코드가 아니라 `evals/results`의 기록이다.
결과 문서들은 과제가 조정된 개발용 집합이지 홀드아웃이 아니고,
과제당 한 번의 표본으로는 인과 효과나 분산을 말할 수 없다고 반복한다.
Jev 응답에 가격 정보가 없으면 비용을 0이 아니라 “알 수 없음”으로 적고,
빈 응답 19건에는 요청 한도 전체를 비용 상한으로 매긴다.
줄인 검색 비용이 총비용을 줄이지 못한 0.5.0 실험도 실패로 기록했다.

같은 저장소의 README 첫 화면은 다른 이야기를 한다.
표지 이미지와 첫 굵은 문장은 여전히 “같은 지능, 약 30% 낮은 비용”이고,
본문 아래쪽에서야 그 그림이 Jev를 뺀 오래된 수치라고 밝힌다.
연구 기록은 엄격한데 제품의 첫 문장은 가장 유리한 숫자를 고른 셈이다.

## 비평

### 절감액의 대부분은 과제 하나에서 나온다

0.4.3 총비용 실행에서 기준 대비 절감액은 $1.9657이다.
그 가운데 `pytest-dev__pytest-6197` 한 과제가 $1.8156,
즉 약 92%를 차지한다.
기준 실행이 이 과제에 $2.3445를 썼고 Jevgrep 실행은 $0.5289를 썼기 때문이다.
이 과제를 빼면 나머지 아홉 과제의 절감액은 $0.15,
기준 비용의 약 3%에 불과하다.
9월 27일 Sol 단독 비교에서도 pytest가 절감액의 약 70%다.

열 과제 가운데 다섯 과제(requests, astropy, xarray, matplotlib, pylint)는
0.4.3 실행에서 오히려 기준보다 비쌌다.
결과 문서도 집계 절감이 과제별 보장이 아니라고 적지만,
“25.8% 절감”이라는 숫자가 주는 인상은 열 과제에 고르게 퍼진 효과다.
실제로 보이는 것은 기준 실행이 pytest에서 크게 헤맨 한 번의 표본과,
나머지 과제에서의 작은 변동이다.

저자들이 홀드아웃이 아니라고 밝힌 점은 정직하지만,
그 경고는 결과의 일반화만 겨냥한다.
더 직접적인 문제는 같은 열 과제 안에서도 효과가 한 과제의 분산에 기대고
있다는 점이며,
이는 과제를 반복 실행하지 않는 한 구별할 수 없다.

### “같은 지능”은 8/10이 같다는 뜻일 뿐이다

README는 기준과 Jevgrep이 둘 다 열 과제 중 여덟을 풀었다는 사실을
“같은 지능”으로 요약한다.
하지만 두 과제(matplotlib, pylint)는 양쪽 모두 실패했고,
pylint는 공식 테스트 패치가 픽스처에 없는 상수를 가져와
행동 테스트가 돌기도 전에 수집 단계에서 실패한다.
의미 있는 비교 대상은 사실상 여덟 과제이고,
그 여덟은 기준이 이미 푼 과제다.

이런 설계는 Jevgrep이 기준의 해결을 망치지 않는지를 확인할 수는 있어도,
기준이 못 푸는 과제를 Jevgrep이 풀게 하는지는 볼 수 없다.
결과 문서에는 Django, Astropy, Sphinx, Matplotlib 과제에서 모델에 전달된
출력이 잘렸다는 기록도 있다.
검색 결과가 잘린 채로도 같은 과제를 풀었다면 Sol이 일반 도구로 빈틈을
메운 것이고,
그 경우 해결의 공이 검색에 있는지 Sol에 있는지 나눌 수 없다고 문서
스스로 인정한다.

### 스킬은 소스 업로드를 기본 동작으로 만든다

스킬 설명은 함수나 설정 이름이 나오는 질문까지 포함해,
동작을 묻는 질문이면 넓은 텍스트 검색이나 git 이력보다 먼저 `jg`로 시작하라고
에이전트에게 지시한다.
하위 에이전트에 탐색을 맡길 때도 `jg`로 시작하라고 명시하게 한다.
README는 정확한 심볼을 알면 `rg`로 충분하다고 말하지만,
에이전트가 실제로 읽는 스킬 설명은 거의 모든 탐색 질문을 `jg`로 보낸다.

`jg`를 한 번 부를 때마다 저장소 일부가 외부 공급자로 나간다.
필터가 자격 증명으로 보이는 파일을 거르지만,
README 스스로 그것이 보장이 아니라고 쓴다.
사람이 직접 `jg`를 칠 때는 루트를 고르는 판단이 끼어들지만,
전역 스킬로 설치된 에이전트는 그 판단 없이 여러 번 호출한다.
코드를 외부로 보내도 되는 저장소인지를 정하는 일은 이제 스킬을 설치하는
순간에 한 번만 일어난다.

### 측정의 비용이 측정된 절감보다 크다

연구 원장에는 Sol 시도에 최소 $57.05, Jev에 최소 $18.78이 기록되어 있다.
열 과제 한 번 실행에서 얻은 절감은 $2 안팎이다.
제품을 만드는 연구비가 벤치마크 한 회의 절감보다 큰 것은 이상한 일이
아니지만,
이 숫자는 다른 질문을 던진다.
그만큼의 실험을 거치고도 결론이 “이 산출물을 채택할 근거는 있지만
최적이라는 근거는 없다”는 데 머문다면,
열 과제 단일 표본이라는 측정 틀 자체가 의사결정을 감당하지 못한다는 뜻이다.

## 인사이트

### 에이전트의 첫 도구 호출이 새로운 유통 경로가 된다

Jevgrep이 가장 공을 들인 산출물 가운데 하나는 코드가 아니라 스킬 설명이다.
CLI만 설치하면 에이전트가 쓰지 않는다는 README의 경고는,
에이전트 시대의 개발 도구가 사람보다 에이전트의 도구 선택 단계에서
경쟁한다는 사실을 보여 준다.
에이전트가 어떤 질문에 어떤 도구를 먼저 부를지는 스킬 설명 몇 문장이
정한다.

이 구조는 검색 엔진 최적화의 초기와 닮았다.
도구는 에이전트가 읽을 설명을 다듬어 더 많은 질문을 자기 쪽으로 끌어오고,
`grep`이나 파일 읽기처럼 공짜인 기본 도구는 설명을 다듬어 줄 주인이 없다.
같은 에이전트에 비슷한 검색 스킬이 여럿 설치되면,
에이전트는 각 스킬이 “먼저 나를 쓰라”고 주장하는 설명 사이에서 골라야 한다.
그 경쟁의 비용은 토큰과 업로드된 소스라는 형태로 사용자가 낸다.

### 총비용이 유일한 정직한 지표다

Jevgrep 연구가 남긴 가장 쓸모 있는 교훈은 0.5.0 실험의 실패에 있다.
검색 요청 수와 Jev 입력 비용을 59% 줄였는데도,
코딩 에이전트가 더 탐색하고 패치를 더 고치면서 총비용은 늘었다.
결과 문서는 쓸모 있는 발췌가 자동으로 싼 문맥이 아니고,
짧은 패킷이 자동으로 나은 것도 아니라고 정리한다.

이는 에이전트 파이프라인을 부분 최적화할 때 반복될 함정이다.
검색, 요약, 문맥 압축처럼 루프의 한 단계를 싸게 만드는 도구는 그 단계의
비용만 보고하기 쉽고,
그 절감이 다른 단계의 비용으로 옮겨 가는지는 따로 재야 보인다.
Jevgrep이 처음에는 Sol 비용만 보고하다가 Jev를 포함한 총비용으로 회계 정책을
바꾼 과정 자체가,
이런 도구를 평가할 때 무엇을 재야 하는지에 대한 좋은 사례다.

### 관련성 분류기는 코드 검색의 경계를 다시 긋는다

정확한 이름을 알 때는 `grep`이, 동작만 알 때는 의미 검색이 맞다는 구분은
오래됐다.
Jevgrep은 그 의미 검색을 임베딩 유사도가 아니라 구조화된 “관련 있음,
없음” 판단의 연쇄로 구현한다.
판단에 임계값이 붙으니 문턱을 0.25에서 0.5로 올리자 Django 과제의
결과 파일이 51개에서 10개로 줄었다는 식의 조정이 가능해진다.

이 방식이 퍼지면 코드 검색은 색인의 문제가 아니라 판단 비용의 문제가 된다.
질의마다 판단을 사는 구조에서는 저장소가 클수록,
질문이 넓을수록 비용이 늘고,
GeekNews 사용자가 겪은 토큰 소모가 그 첫 신호다.[^i8hn3]
결국 판단 비용이 충분히 싸지면 색인을 버리는 쪽이 이기고,
그렇지 않으면 이전 세대 도구처럼 판단 결과를 색인으로 굳히는 쪽으로
되돌아갈 것이다.
