## 소개

공개 모델을 추가 학습 없이 결정 도구로 쓰는 브라우저 실험이다.
원래 이름이 OpenJev였고 지금은 SemIf로 바뀌었다.

첫 화면에 면책이 먼저 나온다.
독립 연구 프로젝트이며 예전 이름이 OpenJev였고, TypeSafe와 제휴 관계가 없고 승인받지도 않았으며 침해 의도가 없다는 것이다.

표어는 “브라우저 안에서, 공개 모델로 만든 시맨틱 if”다.

핵심 제안이 한 문단으로 정리된다.
로컬 모델은 허용된 선택지들에 대한 확률을 디코딩하지 않고 읽어 낼 수도 있고, 같은 종류의 분포를 토큰 단위로 써 낼 수도 있다.
크기를 고르고 자기 GPU에서 둘 다 돌려서 차이를 재 보라는 것이다.

이 설계가 [Jev 발표문](jev.md)과 결정적으로 다른 지점이 여기다.
Jev는 자기 수치를 제시하고 믿어 달라고 하는데, 이 프로젝트는 같은 모델에서 두 경로를 나란히 돌려 사용자 기기의 시계로 재게 한다.

화면 위쪽에 배지 넷이 붙어 있다. 브라우저 전용, 백엔드 없음, 당신의 측정치, 1.56GB 모델이다.
그리고 대기자 명단이 없으니 그냥 써 보라고 적는다.

## 무엇을 재는가

같은 결정을 두 경로에 똑같이 넣는다.

| 경로          | 방식                                                      | 출력      |
| ------------- | --------------------------------------------------------- | --------- |
| 02A 직접 판독 | 모델의 선택 로짓을 읽어 제공한 선택지들에 대해서만 정규화 | 판독 1회  |
| 02B 생성      | 같은 분포를 추정해 JSON 텍스트로 쓰게 한다                | 토큰 단위 |

두 경로가 같은 GPU를 두고 경합하지 않도록 순차로 돌린다. 직접 판독이 먼저이고 생성이 다음이다.

계측 항목도 명시된다.
설정, 워밍업, 프롬프트 준비, 직접 실행, 생성 첫 토큰, 생성 완료가 `performance.now()`로 측정되며, 미리 만들어 둔 결과는 나타나지 않는다고 적는다.

모델은 셋 중에 고른다.

| 모델        | 다운로드 | Authored | Perturbed | TypeSafe |
| ----------- | -------- | -------- | --------- | -------- |
| Qwen3 0.6B  | 639MB    | 44.0%    | 52.8%     | 40.7%    |
| MiniCPM5 2B | 1.56GB   | 68.6%    | 69.3%     | 63.7%    |
| Qwen3.5 4B  | 3.01GB   | 81.3%    | 76.6%     | 84.5%    |
| 공개된 Jev  | 호스팅   | —        | —         | 88.3%    |

Qwen3 0.6B는 휴대폰과 작은 기기용, MiniCPM5 2B는 데스크톱 기본값, Qwen3.5 4B는 메모리가 넉넉한 데스크톱용이라고 안내한다.

표의 의미도 각주로 정확히 규정한다.
소유 열은 균형 정확도(balanced accuracy)이고, TypeSafe 열은 같은 102행 공개 부분집합에 대한 동등 사례 일치도이며 Jev는 공개된 값이라는 것이다.
브라우저 양자화가 모델 정확도를 바꿀 수 있다는 단서도 붙는다.

가중치는 Hugging Face에서 오고 브라우저 캐시에 남으며, 입력은 이 페이지를 떠나지 않는다.
첫 로딩은 선택한 모델과 네트워크와 GPU에 따라 몇 분이 걸릴 수 있다.

## 스스로 붙인 단서

이 사이트에서 가장 눈에 띄는 부분이 “이 숫자들이 무엇이고 무엇이 아닌가”라는 절이다.

| 항목           | 밝힌 내용                                                                                                                                |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 조건부 확률    | 직접 점수는 표시된 선택지 토큰에 대해서만 소프트맥스를 건 것이며, 보정된 신뢰도가 아니고 모델이 선호할 수 있는 모든 답을 포함하지 않는다 |
| 로컬 모델 등급 | 휴대폰 모델은 정확도를 크기와 맞바꾼 것이고, 4B는 메모리가 훨씬 더 필요하며, 어느 것도 Jev에 맞먹는다고 주장하지 않는다                  |
| 실제 로컬 시간 | 설정부터 생성 완료까지가 `performance.now()`로 측정되며 미리 만든 결과는 없다                                                            |
| 양자화 가중치  | 고정된 GGUF 빌드를 `wllama`로 쓰며, 양자화가 품질과 속도를 모두 바꿀 수 있다                                                             |

첫 줄이 특히 중요하다.
직접 판독이 주는 숫자가 보정된 신뢰도가 아니라는 것은, [Jev가 내세우는 핵심 주장](jev.md)을 이 재현이 재현하지 않는다는 선언이다.

GitHub 쪽 설명도 같은 선을 긋는다.
Jev가 런타임에 정의되는 시맨틱 결정을 위한 TypeSafe의 폐쇄 서비스이며, 이 프로젝트는 그 인터페이스 패턴을 공개 모델로 재현할 뿐 Jev의 비공개 모델이나 학습은 재현하지 않는다는 것이다.

## 직접 확인하기

이 사이트 자체가 확인 도구이므로, 의미 있는 실험을 설계하는 것이 사용자의 몫이다.

```text
1. 모델을 MiniCPM5 2B 로 고르고 로드한다(첫 로딩 몇 분)
2. 제공된 예시(Account support / Email triage)로 먼저 두 경로를 돌려 기준선을 잡는다
3. 자기 업무의 실제 분기 하나를 state + question + options 로 옮긴다
4. 선택지 순서를 뒤집어 다시 돌린다
5. 같은 입력을 5회 반복해 분산을 본다
```

4번과 5번이 이 사이트가 안내하지 않지만 반드시 해야 할 단계다.
[아키텍처 분석](architecture-unmasked.md)이 보고한 선택지 순서 효과가 여기서도 나타나는지를 자기 모델로 확인할 수 있기 때문이다.

댓글에 실제 실험 결과가 여럿 올라왔고, 그것들이 이 사이트의 교육적 가치를 잘 보여 준다.

ludicrousskill은 닫힌 고속도로 옆에 선 마지막 인간이 길을 건너겠느냐는 질문을 던졌다.[^ludicrousskill]

| 모델        | 직접 판독            | 생성               |
| ----------- | -------------------- | ------------------ |
| Qwen3 0.6B  | Yes 0.985 / No 0.015 | Yes 0.5 / No 0.5   |
| MiniCPM5 2B | Yes 0.122 / No 0.878 | Yes 0.5 / No 0.5   |
| Qwen3.5 4B  | Yes 0.529 / No 0.471 | Yes 0.95 / No 0.05 |

그리고 결론을 이렇게 적었다. 동전 던지기 답을 더 빨리 얻고 있는 것 같다는 것이다.

paulluuk은 1d6을 굴리면 어느 면이 나오겠느냐고 물었고, 확률 경로가 1.968초에 1이 나올 확률 76%를, 생성 경로가 3.083초에 균등 분할을 냈다고 보고했다.[^paulluuk]

두 실험이 같은 것을 보여 준다.
직접 판독이 훨씬 빠르지만, 작은 공개 모델에서 그 숫자가 의미 있는 확률이라는 보장은 없다는 것이다.
그리고 사이트가 그것을 미리 밝혀 두었다. 보정된 신뢰도가 아니라는 문장이 정확히 이 현상을 가리킨다.

## 저장소가 공개한 측정값

사이트는 브라우저에서 두 경로를 비교하게 해 주지만, 저장소에는 사이트에 없는 측정이 들어 있다.
Python으로 쓰였고 MIT 라이선스이며 별 2,094개, 포크 129개, 미해결 이슈 7개다.
저장소 설명이 범위를 한 줄로 밝힌다.
집에 있는 3090에서 공개 모델로 만드는 시맨틱 if이며,
독립 프로젝트이고 Jev나 TypeSafe와 제휴 관계가 없다는 것이다.

첫 번째 측정은 같은 결정을 두 경로로 낼 때의 비용이다.
동결한 Qwen3.5-4B, 같은 상태, 같은 이진 기준 21개, RTX 3090 한 장이다.

| 출력 경로                      | 시간    | 출력 토큰 | 결과                  |
| ------------------------------ | ------- | --------- | --------------------- |
| 직접 타입 로짓, 3회 중앙값     | 1.023초 | 0         | 확률 쌍 21개          |
| 자기회귀 JSON 배열, 3회 중앙값 | 5.332초 | 111       | 유효한 21값 순서 배열 |

여기서 비교 대상을 어떻게 잡았는지가 중요하다.
생성 쪽 기준선은 키나 신뢰도 객체나 설명 없이 순서대로 `"yes"`와 `"no"`만 내보내는 가장 압축된 형태다.
첫 토큰까지의 중앙값은 0.489초였지만 배열을 완성하는 데는 직접 판독의 5.21배가 걸렸다.

그리고 저자가 스스로 단서를 붙인다.
세 번의 배열이 모두 유효했고 서로 같았으며,
그 선택이 직접 판독의 argmax와 21개 중 18개에서 일치했다는 것이다.
그러므로 이것은 시스템 비교이지 두 판독이 의미적으로 동등하다는 주장이 아니라고 적는다.

두 번째 측정은 상태를 여러 결정에 재사용할 때의 이득이다.
상태 37개와 기준 21개, 즉 결정 777건을 돌린 결과다.

| 실행 경로          | 초당 결정 | 777건 소요 |
| ------------------ | --------- | ---------- |
| 매번 새로 채점     | 2.33      | 333.1초    |
| 접두사 직렬 재사용 | 10.75     | 72.3초     |
| 접미사 병렬        | 20.03     | 38.8초     |
| 네이티브 리랭커    | 1.86      | 417.3초    |

빠른 재사용 경로가 실험적이라는 경고가 붙는다.
BF16 실행이 새로 채점한 경우와 비교해 777건 중 5~6건의 argmax를 바꿨다는 것이다.
8.6배 빨라지는 대신 결과가 미세하게 달라진다는 뜻이며,
이 수치를 함께 적어 둔 것이 이 저장소의 태도를 보여 준다.

감사 가능성도 명시적으로 설계되어 있다.
소유한 픽스처, 정확한 실행기, 행 단위 출력, 모델 리비전, 프롬프트,
그리고 알려진 실패가 전부 커밋되어 있다고 밝힌다.
결과 파일마다 타입이 붙은 선택지 점수와 타이밍, 정확한 모델 리비전, 프롬프트 해시가 들어간다.

macOS는 별도 경로를 둔다.
Apple Silicon에서는 MLX 백엔드로 직접 채점과 접두사 직렬 재사용과 공유 상태 병렬 결정을 쓸 수 있다.

## 트레이드오프

### 인터페이스를 재현하는 것과 모델을 재현하는 것이 전혀 다르다

이 프로젝트에 대한 가장 흔한 혼란이 이름에서 온다.

mukundesh가 그 혼란을 직접 말했다. 이것이 어떻게 JEV인지 모르겠고 표준 LLM을 쓰면서 JEV의 API를 따르는 것일 뿐이며, JEV의 주된 기여는 API가 아니라 모델 자체 아니냐는 것이다.[^mukundesh]
wuhhh도 같은 질문을 했다. OpenAI의 구조화 출력과 어떻게 다른지 이해가 안 되며, 다들 그것에서 넘어갔던 패러다임 아니냐는 것이다.[^wuhhh]
그러면서 GitHub의 면책 문구를 스스로 인용하고, 다른 사람이 지적했듯 이것이 실제로 Jev가 아닌데 누가 설명해 줄 수 있느냐고 물었다.

이 혼란이 프로젝트의 잘못만은 아니다. 사이트와 저장소 모두 면책을 맨 앞에 두었기 때문이다.
그리고 이름을 OpenJev에서 SemIf로 바꾼 것이 그 혼란에 대한 대응으로 보인다. algoth1이 Jev가 상표 아니냐고 물은 것도 같은 맥락이다.[^algoth1]

그런데 이름 문제를 걷어 내면 진짜 질문이 남는다.
Jev의 가치가 인터페이스에 있는가 모델에 있는가다.

이 프로젝트의 답은 “둘 다이되 분리해서 확인할 수 있다”에 가깝다.
인터페이스는 공개 모델로 재현되고 실제로 5배 남짓 빠르며, 모델의 기여는 정확도 표의 격차로 드러난다. 4B가 84.5%이고 공개된 Jev가 88.3%다.
즉 이 사이트는 Jev를 복제하는 데 실패한 것이 아니라, Jev의 어느 부분이 어느 만큼 기여하는지를 분해해 보여 준다.

### 작은 로컬 모델에서 직접 판독은 빨라지지만 의미가 얇아진다

속도 이득은 분명하다. GN 요약 기준 JSON 생성 대비 5.21배다.

문제는 그 숫자가 무엇에 대한 확률이냐다.
사이트가 밝힌 대로 직접 점수는 표시된 선택지 토큰에만 소프트맥스를 건 것이다.
모델이 “잘 모르겠다”고 생각하더라도 그 상태를 표현할 자리가 없고, 주어진 선택지 안에서 상대적 선호만 정규화된다.

ludicrousskill의 실험이 이 성질을 잘 드러낸다.
같은 질문에 Qwen3 0.6B는 0.985로 Yes를, MiniCPM5 2B는 0.878로 No를 확신했다.
둘 다 높은 확률인데 방향이 반대다. 확률의 크기가 정확성과 무관하다는 뜻이다.

생성 경로가 0.5/0.5를 낸 것도 시사적이다.
모델이 텍스트로 쓸 때는 모른다는 것을 표현할 수 있는데, 로짓을 읽으면 그 표현이 사라진다.

그래서 이 방식이 통하려면 모델이 그 질문 형태에 대해 이미 잘 보정되어 있어야 하고, 그것이 바로 TypeSafe가 RLCD로 학습했다고 주장하는 부분이다.
학습 없이 인터페이스만 가져오면 속도는 얻지만 보정은 얻지 못한다는 것이 이 실험의 가장 정직한 결론이다.

### 브라우저에서 돌린다는 선택이 접근성과 측정 신뢰도를 맞바꾼다

대기자 명단 없이 지금 써 볼 수 있다는 것이 이 프로젝트의 가장 큰 미덕이다.
[Jev 출시 당시 Lobste.rs에서 나온 불만](jev.md)이 정확히 그것이었다. 대기자 명단에 등록해야 하고 문서도 못 본다는 것이다.

대가는 측정 조건의 통제 불가능이다.
브라우저 양자화가 정확도를 바꿀 수 있다고 사이트가 밝히고, 고정된 GGUF 빌드를 `wllama`로 쓴다고도 밝힌다.
그러면 여기서 얻은 5배라는 숫자는 이 양자화와 이 런타임과 이 GPU에 묶인 값이다.

mmastrac가 더 진지한 대안을 제시했다.
자기 평가에서 Jev와 맞먹는 제대로 된 구현을 써 보고 싶다면 DiffusionGemma를 Jev로 바꾸는 vLLM 패치가 있다는 것이다.[^mmastrac]
자기 DGX Spark에서 매우 비슷한 지연 시간이 나왔고 각 시험에서 몇 점 차이로 평가가 일치했으며, 어느 쪽이 이기기도 하고 둘 다 틀릴 때는 낮은 신뢰도를 보였다고 했다.
같은 평가를 Qwen36에 돌렸더니 둘 모두에게 확실히 졌으며, 더 작은 모델을 쓰면 지식과 직관적 추론을 둘 다 포기하는 셈이라고 덧붙였다.

이 대비가 두 프로젝트의 역할을 가른다.
브라우저 실험은 개념을 체감하게 하고, vLLM 패치는 실제 성능을 검증한다.
전자의 숫자를 후자의 근거로 쓰면 안 된다.

## 함정

직접 판독의 확률은 보정된 신뢰도가 아니다. 사이트가 명시하지만 화면의 숫자만 보면 그렇게 보인다.

표시된 선택지에만 정규화되므로 “해당 없음”에 가까운 상태가 표현되지 않는다. 선택지에 명시적으로 넣어야 한다.

작은 모델일수록 직접 판독과 생성의 답이 엇갈린다. 두 경로의 일치 여부 자체가 유용한 신호다.

정확도 표의 TypeSafe 열은 102행 공개 부분집합에 대한 동등 사례 일치도이지 정확도가 아니다.

첫 로딩이 몇 분 걸리며 실패할 수 있다. tomaytotomato는 회사 방화벽과 VPN이 `huggingface.co`를 막아 모델 다운로드에서 깨진다고 보고했다.[^tomaytotomato]

이름이 바뀌었다. OpenJev로 알고 있던 저장소와 문서가 SemIf를 가리킬 수 있다.

## 체크리스트

- 이 사이트의 숫자를 Jev의 성능으로 읽고 있지 않은가
- 직접 판독 확률이 보정된 신뢰도가 아니라는 것을 인지했는가
- 선택지에 “해당 없음”에 해당하는 항목을 넣었는가
- 선택지 순서를 뒤집어 확률이 얼마나 움직이는지 확인했는가
- 같은 입력을 여러 번 돌려 분산을 봤는가
- 두 경로(직접 판독 / 생성)의 답이 엇갈리는 사례를 모아 봤는가
- 양자화와 런타임이 고정된 조건에서 얻은 수치임을 기록했는가
- 실제 배포를 검토한다면 vLLM 패치 같은 통제된 환경에서 다시 쟀는가

## 비평

### 이 프로젝트가 드러낸 가장 중요한 사실은 기술이 아니라 약관이다

HN 스레드에서 가장 무거운 정보가 jakozaur의 댓글에 있다.

진짜 Jev가 꽤 이상해졌는데 벤치마크 금지 조항이 있다는 것이다.[^jakozaur]
이용약관 1(v)와 MCA 2.3(f)이 사용자가 서비스에 대한 “벤치마크나 성능 정보”를 게시하는 것을 금지한다고 적었다.
주요 AI 중에 이런 조항을 가진 곳이 없으며 Oracle식 법무로 돌아간 것이라는 평가다.
그러면서 Jev가 독창적이긴 하지만 복제하기 매우 쉬워 보인다고 덧붙였다.

이 조항이 사실이라면 여러 문서의 맥락이 한꺼번에 바뀐다.

[Jev 발표문](jev.md)이 공개 벤치마크를 내지 않겠다고 선언한 것이 방법론적 선택으로 제시되었는데, 약관이 제3자 측정도 막는다면 그것은 일방적 정보 통제가 된다.
[아키텍처 분석](architecture-unmasked.md)이 1만 번의 API 호출로 지연 시간과 토큰 회계를 측정해 공개한 것도 이 조항과 충돌할 수 있다.
그 분석은 이 모델에 대한 유일한 독립 검증인데, 그것이 약관 위반일 수 있다는 뜻이다.

그리고 이 프로젝트 자체의 위치도 설명된다.
Jev를 직접 재지 못한다면 남는 방법은 같은 인터페이스를 다른 모델로 구현해 그 차이를 재는 것이고, 그것이 정확히 이 사이트가 하는 일이다.
정확도 표에서 TypeSafe 열이 “동등 사례 일치도”라는 우회적 지표인 것도 같은 제약의 흔적으로 읽힌다.

다만 이 정보가 댓글의 주장이라는 점은 짚어야 한다. 조항 번호까지 특정했지만 원문이 인용되지는 않았다.

### 바이브 코딩된 사이트라는 인상이 내용의 신뢰도를 깎는다

이 사이트에 대한 첫 반응 다수가 디자인이었다.

prodigycorp는 이런 원샷 바이브 코딩 사이트가 늘 시각적 두통이라며, 끝없는 잡동사니와 의미 없는 채움 텍스트가 사방에 있고 실제 사용성에 대한 고려가 전혀 없다고 적었다.[^prodigycorp]
kul_은 자기만 그런지 다른 사람들도 LLM이 만든 웹사이트를 불쾌하게 느끼는지 물었다.[^kul_]
dankobgd는 더 짧게 비꼬았다. 슬롭 만드는 사람들이 스키마를 발견했는데 마치 JSON 스키마 명세가 없었던 것처럼 군다는 것이다.[^dankobgd]

이 반응들이 부당한 면이 있다.
이 사이트는 실제로 동작하는 측정 도구이고, 자기 수치가 무엇이 아닌지를 네 항목으로 밝혀 두었으며, 미리 만든 결과가 없다고 명시한다.
그 정직함의 밀도는 많은 상용 발표문보다 높다.

그러나 형식이 내용에 대한 신뢰를 좌우한다는 사실은 남는다.
daxaxelrod가 지적한 것이 그 예다. `run both methods`가 비활성일 때 “먼저 모델을 받으세요”라는 툴팁이 있어야 한다는 것이다.[^daxaxelrod]
사소한 지적이지만, 측정 도구에서 사용자가 무엇을 눌러야 하는지 모르면 측정이 시작되지 않는다.

그리고 이 문제가 이 프로젝트에만 있는 것도 아니다.
[Jev 출시 당시](jev.md)에도 페이지가 읽기 힘들다는 불만과 접근성이 말로 다 할 수 없는 수준이라는 지적이 있었다.
결정 모델이라는 새 부류를 설명하는 두 사이트가 모두 전달에서 먼저 걸린다는 것이 이 분야의 현재 상태를 말해 준다.

이 지적에 대한 후속 대응이 저장소에 기록되어 있다.
2026년 9월 18일 변경 사항에 Unsloppify site가 추가되었는데,
통상적인 인터페이스로 바꾸는 전환 스위치다.
같은 날 브라우저 데모에 MiniCPM5 2B와 Qwen3.5 4B도 추가되었다.
표현 때문에 내용이 평가절하된다는 반응을 프로젝트가 읽고 선택지를 하나 더 만든 셈이며,
이 대응 자체가 이 비평이 취향 문제가 아니었다는 증거이기도 하다.

### 선행 연구를 뒤늦게 발견하는 패턴이 반복된다

이 스레드에서 여러 사람이 비슷한 기존 작업을 링크했다.

corysama는 작년에 모델과 논문과 데이터셋까지 갖춰 Jev 아키텍처를 오픈소스로 공개한 작업이 있다며 Reddit 글과 arXiv 논문 둘과 Hugging Face 모델·데이터셋을 링크했다.[^corysama]
kouteiheika는 `convaiinnovations/laya`를 관련 작업으로 들었다.[^kouteiheika]
aatd86은 GLiNER 2.5와 비교해 봤느냐고 물었다.[^aatd86]
hmokiguess는 [jevlike](jevlike.md) 쪽이 더 흥미로워 보인다고 적었다.[^hmokiguess]

[Jev 발표문 스레드](jev.md)에서도 같은 일이 있었다. 기존 인코더 모델과 GLiNER가 언급되었다.

이 반복이 말해 주는 것은 이 아이디어가 새롭지 않다는 것이 아니라, **흩어져 있었다**는 것이다.
제로샷 분류기, 인코더 기반 점수 매기기, 제약된 디코딩, 리스트와이즈 랭킹이 각각 다른 커뮤니티에서 다른 이름으로 발전해 왔다.

TypeSafe가 한 일은 그것들을 하나의 제품 인터페이스와 하나의 이름으로 묶은 것이고, 이 프로젝트가 한 일은 그 인터페이스가 특별한 모델 없이도 성립하는지를 보인 것이다.
그리고 두 작업 모두 선행 연구 목록을 앞에 두지 않았기 때문에, 댓글에서 매번 그 목록이 다시 작성된다.

## 기억할 원칙

### 남의 수치를 반박하는 가장 좋은 방법은 읽는 사람이 직접 재게 만드는 것이다

Jev 발표문은 193.6배와 444.6배를 제시하고 그것이 상단값임을 단서로 달았다.
읽는 사람은 그 숫자를 믿거나 믿지 않는 것 외에 할 수 있는 일이 없었다. 대기자 명단이 있었기 때문이다.

이 프로젝트는 다른 길을 택했다. 숫자를 제시하는 대신 측정 장치를 준다.
같은 모델에 두 경로를 태우고, 시계를 브라우저에 두고, 미리 만든 결과가 없다고 명시한다.

이 전략이 강한 이유는 반박 불가능성에 있다.
사이트가 어떤 수치를 주장하지 않으므로 그 수치가 틀렸다고 말할 수 없고, 사용자가 자기 기기에서 얻은 값은 그 사용자에게 참이다.

그리고 이 구조가 회의론자를 설득하는 방식도 바꾼다.
ludicrousskill과 paulluuk이 올린 결과는 이 프로젝트에 불리한 내용인데도 이 프로젝트의 가치를 높인다.
직접 판독이 동전 던지기를 빨리 준다는 발견이 가능했던 것은 그 사이트가 그 실험을 허용했기 때문이다.

일반화하면, 성능을 주장하는 쪽이 할 수 있는 가장 강한 행동은 재현 도구를 함께 내놓는 것이다.
그것이 불가능한 이유가 기술적인 것이라면 이해할 수 있고, 약관이라면 그 자체가 신호다.

### 인터페이스와 모델을 분리해 보면 어느 쪽에 돈을 낼지가 보인다

이 사이트의 정확도 표가 의도치 않게 훌륭한 분해 분석이다.

| 얻는 것             | 필요한 것    |
| ------------------- | ------------ |
| 5배 남짓의 속도     | 인터페이스만 |
| 타입 안전성         | 인터페이스만 |
| 84.5% 수준의 일치도 | 4B 공개 모델 |
| 88.3%               | Jev          |
| 보정된 확률         | Jev의 학습   |

속도와 타입 안전성은 공개 모델로 공짜다. 확률을 로짓에서 읽는 순간 따라오기 때문이다.
그래서 “생성하지 않아서 빠르다”와 “환각하지 않는다”는 주장은 이 부류 전체의 성질이지 특정 제품의 성취가 아니다.

값이 매겨지는 부분은 두 곳이다. 마지막 몇 퍼센트의 정확도와, 그 확률이 실제 빈도와 맞는다는 보장이다.
그리고 후자가 훨씬 어렵다. 정확도는 벤치마크로 좁힐 수 있지만 보정은 학습 목표를 바꿔야 얻어지기 때문이다.

이 분해가 도입을 검토하는 쪽에 주는 지침이 명확하다.
분기의 결과가 임계값에 민감하지 않다면 — 예를 들어 가장 높은 확률의 선택지만 쓰고 그 값을 보지 않는다면 — 공개 모델로 충분하다.
확률 값 자체로 정책을 만든다면 보정이 필요하고, 그때가 돈을 낼 자리다.

### 재현 프로젝트의 가치는 성공률이 아니라 무엇을 재현하지 않았는지를 말하는 데 있다

이 프로젝트가 스스로 재현하지 않은 것을 세 군데에서 밝힌다.
GitHub 설명, 사이트의 단서 절, 그리고 정확도 표의 각주다.

비공개 모델과 학습을 재현하지 않았고, 직접 점수가 보정된 신뢰도가 아니며, 어느 로컬 모델도 Jev에 맞먹는다고 주장하지 않는다는 것이다.

이 선언들이 없었다면 이 프로젝트는 위험했을 것이다.
mukundesh와 wuhhh의 혼란이 이미 이름만으로 생겼는데, 면책이 없었다면 “공개 모델로 Jev를 재현했다”는 잘못된 서사가 퍼졌을 것이다.

그리고 같은 기준이 [jevlike](jevlike.md)에도 적용된다.
그 프로젝트도 Jev의 입출력 모양만 가져왔다고 밝히며, 같은 모양이라는 것과 같은 것이라는 것이 다르다는 점을 스스로 적는다.

일반화하면, 재현 프로젝트를 평가할 때 봐야 할 것은 벤치마크 수치가 아니라 경계 선언이다.
무엇을 재현했는지만 적힌 문서는 독자가 나머지를 상상하게 만들고, 무엇을 재현하지 않았는지가 적힌 문서는 독자가 그 결과를 어디까지 쓸 수 있는지 안다.
