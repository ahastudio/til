# Jev Ultrafast: 행동 공간을 매번 새로 만들어 한 번의 요청으로 고르는 브라우저 에이전트

<https://github.com/browser-use/jev-ultrafast>

HN 토론: <https://news.ycombinator.com/item?id=49735979> (88점, 14개 댓글)

## 소개

동적이고 인덱스가 붙은 행동 공간을 가진 브라우저 에이전트다.
목표 하나를 주면 [TypeSafe의 Jev](jev.md)가 연산과 요소를 고르고,
연산이 `TYPE_TEXT`일 때만 작은 LLM이 텍스트를 쓴다.

내세우는 결과는 구체적이다.
Google Flights에서 취리히에서 런던으로 가는 항공편 검색을 7.1초에 끝냈으며,
자연어 목표 하나에서 시작해 실제 텍스트 생성과 로딩 대기를 포함한 시간이라고 밝힌다.

2026년 9월 16일에 만들어졌고 스타 4,964개, 포크 310개, 열린 이슈 29개다.
Python으로 작성되었고 MIT 라이선스다.
저장소 설명은 `i. am. speed.` 한 줄이다.

Browser Use와 TypeSafe의 협업 결과물이며, README 상단에 Browser Use Cloud 대기자 명단 링크가 있다.
이 점은 나중에 다시 짚는다.

## 행동 공간

관측할 때마다 새 요소 표가 만들어진다.

```text
[1] button    Change ticket type · Round trip
[2] combobox  Where from?        · San Francisco
[3] combobox  Where to?          · empty
[4] textbox   Departure          · empty
...
```

연산은 `CLICK`, `TYPE_TEXT`, `SELECT`, `SCROLL_UP`, `SCROLL_DOWN`, `WAIT`, `DONE`, `BLOCKED` 여덟 가지다.
지원되는 연산과 대상만 제시된다.

핵심 설계는 한 번의 요청으로 두 가지를 정하는 것이다.

```text
                      TypeSafe 요청 하나
                     ┌───────────────────────────┐
페이지 → 요소 표  →   │ operation                 │
                     │ click_target              │
                     │ type_text_target          │
                     │ select_target (있을 때)   │
                     └─────────────┬─────────────┘
                        연산에 맞는 대상만 사용
                                   │
                    CLICK [7] ─────┤──→ 브라우저
                TYPE_TEXT [3] ─────┘
                          ↓
                   작은 LLM → 텍스트 → 브라우저
```

대상 질문들은 투기적(speculative)이다.
연산이 `CLICK`이면 `click_target`만 실행될 수 있다.
결정은 둘인데 네트워크 왕복은 한 번이며, TypeSafe 문서에서는 이것을 투기적 팬아웃(fan-out) 패턴이라 부른다.

각 대상 헤드에는 그 연산과 호환되는 요소만 들어간다.
네이티브 드롭다운 선택지는 관측된 요소와 옵션 인덱스를 함께 지닌다.

정책에 사이트별 행동 스크립트나 미리 준비한 필드 문자열이 없다고 README가 명시한다.
Flights 예제는 목표를 제공하고 결과를 독립적으로 검증할 뿐이다.
스크린샷 렌더러는 나중에 라벨을 붙이는 것이며 브라우저를 조종하지 않는다.

이 구조가 앞서 본 [Jev의 비용 구조](jev-1-13-openrouter.md)와 맞물린다.
질문을 추가해도 지연과 비용이 거의 늘지 않으므로, 쓰지 않을 대상까지 한꺼번에 묻고 버리는 편이 왕복을 한 번 더 하는 것보다 싸다.

그리고 [구조 분석](architecture-unmasked.md)이 왜 그런지를 설명한다.
질문들이 공유 상태를 함께 읽되 서로를 보지 못하는 분기로 처리되므로, 요소 표를 한 번만 인코딩하고 질문마다 자기 접미사만 더한다.
페이지가 클수록 이 공유의 이득이 커지고, 그래서 요소가 수십 개인 화면에서도 질문 넷을 붙이는 비용이 거의 상수가 된다.

그런데 같은 구조가 이 설계에 두 가지 제약을 건다.

첫째, 대상 질문들이 서로를 볼 수 없다.
`click_target`이 무엇을 골랐는지를 `type_text_target`이 알 수 없으므로, 두 대상이 논리적으로 연결된 상황은 한 호출로 표현되지 않는다.
이 정책에서는 연산 하나만 실행되므로 문제가 없지만, 연산 두 개를 한 번에 내리려는 확장은 이 벽에 부딪힌다.

둘째, 선택지 목록이 확률을 바꾼다.
같은 분석이 선택지 순서를 뒤집자 확률이 0.84~0.89에서 0.93~0.96으로 옮겨 갔다고 보고했다.
요소 표는 관측할 때마다 새로 만들어지고 순서는 DOM 순서를 따르므로, 페이지가 조금만 달라져도 같은 요소의 인덱스와 위치가 바뀐다.
즉 이 정책에서 행동 선택의 안정성은 페이지 구조의 안정성에 묶여 있다.

선택지 상한도 구조에서 온다.
Jev가 받는 선택지는 최대 255개이고, 그 이상은 독립 채점 후 명시적 선택이라는 2단계로 나뉜다.
요소가 255개를 넘는 페이지에서는 이 정책의 한 번의 요청이라는 전제가 깨진다.

## 실행하기

```bash
git clone https://github.com/browser-use/jev-ultrafast.git
cd jev-ultrafast
uv sync
cp .env.example .env
# TYPESAFE_API_KEY와 TEXT_MODEL_API_KEY를 넣는다
uv run jev
```

`http://127.0.0.1:8766`을 열고 Start demo를 누른 뒤 Run automatically를 고른다.
인스펙터가 번호가 붙은 요소, 연산 확률, 대상 확률, 실행된 행동을 보여 준다.
`Choose next`는 실행 전에 멈춘다.

Chrome은 Browser Harness를 통해 연결되며 `uv sync`가 함께 설치한다.
연결이 필요하면 `uv run browser-harness --doctor`를 돌리고, Chrome이 물어보면 원격 디버깅을 허용한다.

`TEXT_MODEL_API_KEY`는 예제 설정에서 OpenRouter 키다.
현재 데모는 `inception/mercury-2.5`를 추론 비활성 상태로 쓴다.
Gemini와 GLM, DeepSeek도 OpenAI 호환 텍스트 헬퍼로 쓸 수 있으며 모델과 엔드포인트, 추론 설정을 맞추면 된다.

라이브러리로 쓸 때는 이렇게 한다.

```python
from jev_ultrafast import Agent

with Agent(
    "https://www.google.com/travel/flights?hl=en",
    "Find one-way flights from Zurich to London on September 20, 2026, "
    "for one adult in economy. Stop when matching flight options are visible.",
) as agent:
    for state in agent.run():
        print(state["elapsed_ms"], state["status"])
```

같은 정책으로 다른 작업도 돌릴 수 있다.

```bash
uv run --env-file .env python examples/run.py \
  --url https://en.wikipedia.org/wiki/Main_Page \
  --goal 'Find and open the Wikipedia article about Gödel’s incompleteness theorems.'
```

## 속도를 만든 것들

README가 빠른 이유를 여덟 가지로 열거하는데, 대부분이 모델이 아니라 브라우저를 다루는 방식에 대한 것이다.

결정 주기마다 요청이 하나다. 연산 헤드와 대상 헤드가 같은 관측 상태를 공유한다.

기본 에이전트 루프에 스크린샷이 없다. Jev는 구조화된 상태를 소비하며, 인스펙터가 스크린샷을 선택적으로 켜고 영상은 별도의 연속 스크린캐스트를 쓴다.

스냅숏마다 브라우저 호출이 하나다. 보이는 컨트롤과 그 이름, 값, 텍스트를 원자적으로 읽고 실제 DOM 노드의 참조를 유지한다.

선택된 대상을 검증한다. 클릭은 문서와 폼 값, 대상, 주변 맥락을 확인한다. 애니메이션만으로는 다시 예측하지 않는다.

쓸모 있는 상태를 기다린다. 콤보박스에 입력한 뒤에는 보이는 제안을 최대 200 ms까지 기다리고, 다른 상호작용은 애니메이션 프레임 두 개 또는 50 ms까지만 기다린다.

숨은 탭도 계속 렌더링한다. 포커스 에뮬레이션으로 배경 애니메이션 스로틀링을 막되 Chrome의 보이는 탭을 바꾸지 않는다.

보이는 텍스트만 보낸다. 화면 밖 본문과 푸터가 모델 컨텍스트를 채우지 않는다.

중단된 텍스트 요청을 재사용한다. 생성된 값은 텍스트 헬퍼 입력 전체가 바뀌지 않았을 때만 오래된 페이지 재시도에서 살아남는다.

안전 쪽 진술도 명확하다.
실행되는 모든 대상은 관측된 노드에서 해석되고, 실행기가 페이지 신선도와 클릭 가림을 다시 확인한다.
모델 출력은 결코 선택자나 좌표, 셸 명령, 실행 가능한 JavaScript가 되지 않으며,
텍스트 헬퍼 출력은 입력 전에 작은 JSON 객체로 파싱되어야 한다.

## 측정 결과

`docs/performance.md`가 이 저장소에서 가장 읽을 만한 문서다.

여섯 번의 교대 실행, 한 작업, 기존 Chrome 프로필 하나로 비교했다.
양쪽 모두 같은 자연어 목표와 독립 결과 검사기, 1120×780 뷰포트, TypeSafe `jev-1.13.0`, `inception/mercury-2.5`, 텍스트 추론 비활성, 같은 행동·요청 예산을 썼다.
초기 내비게이션은 양쪽 모두에서 제외했다.

| 쌍     | 원본 실행 시간 | 최적화 실행 시간 | 검증   |
| ------ | -------------- | ---------------- | ------ |
| 1      | 11.214 s       | 6.964 s          | 둘 다  |
| 2      | 8.984 s        | 7.913 s          | 둘 다  |
| 3      | 9.450 s        | 7.092 s          | 둘 다  |
| 중앙값 | 9.450 s        | 7.092 s          | 각 3/3 |

중앙값 작업 시간이 25.0% 줄었고, TypeSafe 요청 중앙값은 22에서 17로,
브라우저 프로토콜 호출 중앙값은 1,092에서 101로 줄었다.

여기서 이 문서가 보기 드문 일을 한다.
세 쌍은 강한 통계적 주장을 하기에 너무 적다고 스스로 적고, 양측 부호 검정 p = 0.25라는 값까지 밝힌다.
그리고 이것은 작은 통제 입력 비교이지 광범위한 에이전트 벤치마크가 아니며,
Google과 네트워크 응답, 라우팅, 브라우저 캐시는 여전히 살아 있다고 덧붙인다.

세부 수치도 공개된다.
녹화에는 Jev 요청 17회, 상호작용 10회와 명시적 `WAIT` 1회, 헬퍼 호출 2회가 담겼다.
Jev 지연 중앙값은 178 ms였고, 검색은 5.217초에 실행되었으며 검증된 완료는 7.073초였다.
텍스트 생성은 취리히가 581 ms, 런던이 346 ms 걸렸다.
TypeSafe 입력 토큰 90,558개와 출력 토큰 6,325개를 기록했고,
OpenRouter가 텍스트 호출 두 건에 대해 $0.00006272를 보고했다.
그리고 그것이 텍스트 헬퍼 요금일 뿐 작업 전체 비용이 아니라고 명시한다.

다른 작업의 측정도 있다.

| 작업                                       | 시간    | 독립 검증 결과             |
| ------------------------------------------ | ------- | -------------------------- |
| Wikipedia에서 괴델 불완전성 정리 문서 열기 | 2.798 s | 정확한 문서 URL            |
| 로컬 호텔 픽스처 검색과 필터 적용          | 1.896 s | 숙소와 적용된 세 필터 모두 |

실패한 개발 시도까지 남겨 두었다.
접근성 트리 기반 후보 두 개가 9.395초와 10.157초였고,
첫 직접 DOM 후보는 8.697초로 빨랐지만 이름과 값 추출이 불완전해 독립 검증에 실패했다.
이후 검증을 통과한 진단들이 8.051, 8.631, 8.395, 8.385, 7.741초였다.

## 트레이드오프

### 시계를 언제 시작하느냐가 7.1초라는 숫자를 정한다

HN에서 나온 가장 날카로운 질문이 이것이다.
`ofisboy`는 초기 페이지 관측 이후에 타이밍이 시작된다는 문장을 인용하며, 그 부분이 가장 오래 걸리는 것 아니냐고 물었다.[^ofisboy]

이 질문이 정확한 이유는 문서가 경계를 분명히 적어 두었기 때문이다.
타이밍은 초기 홈페이지 관측 이후 첫 예측에서 시작해 수락된 `DONE` 선택에서 끝나며,
브라우저 설정과 초기 내비게이션, 실행 후의 독립 검증은 시계 밖이다.

그러니 7.1초는 사용자가 체감하는 전체 시간이 아니라 정책이 결정을 내리는 구간의 시간이다.
브라우저를 띄우고 Google Flights를 여는 시간은 여기 없다.

다만 이 경계 선택 자체가 부당한 것은 아니다.
비교의 목적이 자기 코드의 개선을 재는 것이라면, 양쪽 팔에서 똑같이 제외한 항목은 차이를 만들지 않는다.
문서도 초기 내비게이션이 양쪽 모두에서 제외되었다고 적는다.

문제는 그 경계가 25% 개선이라는 내부 비교에는 적절하지만, 7.1초라는 절대 숫자를 홍보 문구로 쓸 때는 다른 인상을 준다는 것이다.
README 첫머리의 굵은 글씨는 7.1초이고, 시계의 시작점은 성능 문서까지 가야 나온다.
그래서 이 저장소의 정직함은 문서에 있고, 인상은 제목에 있다.

### 투기적 팬아웃은 계산을 버려서 왕복을 아낀다

연산과 모든 대상 헤드를 한꺼번에 묻고 연산에 맞는 대상만 쓰는 방식은, 나머지 헤드의 계산을 버리는 것이다.

이 교환이 성립하는 조건이 명확하다.
버려지는 계산의 비용이 왕복 한 번의 지연보다 작아야 한다.
Jev에서는 질문 추가가 거의 공짜이므로 이 조건이 성립하고, 그래서 이 패턴이 가능하다.

같은 패턴을 일반 LLM으로 흉내 낼 수 없는 이유도 여기 있다.
LLM에게 연산과 세 종류의 대상을 한 번에 물으면 출력이 길어지고 지연이 늘어나므로, 버리는 계산이 아끼는 왕복보다 비싸진다.
그러니 이 저장소가 보여 주는 것은 Jev의 속도가 아니라, 질문이 싸질 때 에이전트 루프의 설계가 어떻게 달라지는가다.

대가는 헤드가 늘어날수록 표가 커진다는 것이다.
각 대상 헤드에 호환되는 요소만 넣는다고 해도, 요소가 많은 페이지에서는 여러 헤드에 같은 요소들이 반복해서 들어간다.
입력 토큰 90,558개가 17번의 요청에서 나왔다는 것은 요청당 평균 5,300 토큰이라는 뜻이고, 이것이 이 방식의 실제 비용 구조다.
[Jev의 가격이 입력 기준](jev-1-13-openrouter.md)이므로 여기가 비용이 쌓이는 자리다.

### 실행 가능한 것을 모델이 만들지 않는 설계

이 저장소에서 가장 값진 설계 결정은 속도와 무관한 쪽에 있다.
모델 출력이 선택자나 좌표, 셸 명령, 실행 가능한 JavaScript가 되지 않는다는 규칙이다.

모델이 고르는 것은 인덱스뿐이고, 그 인덱스는 이미 관측된 노드 표를 가리킨다.
그러니 모델이 아무리 이상한 값을 내놓아도 표에 없는 것을 건드릴 수 없다.
프롬프트 주입으로 임의 코드를 실행시키는 경로가 구조적으로 막힌다.

텍스트 헬퍼 쪽은 다르다.
`TYPE_TEXT`일 때 작은 LLM이 실제 문자열을 만들고 그것이 페이지에 입력된다.
여기에 대한 방어는 출력이 작은 JSON 객체로 파싱되어야 한다는 것 하나다.
형식은 검사하지만 내용은 검사하지 않으므로, 페이지 내용이 생성될 문자열에 영향을 줄 여지는 남는다.

그리고 남는 위험을 README가 숨기지 않는다.
`DONE` 선택은 여전히 독립적인 결과 검증을 요구하며, `DONE`은 결코 성공의 독립적 증거가 아니라고 적는다.
유효한 연산도 여전히 틀릴 수 있다는 문장도 있다.
에이전트가 끝났다고 말하는 것과 실제로 끝난 것을 분리한 것이 이 프로젝트의 태도를 보여 준다.

### 클라우드 모델에 묶인 로컬 도구

`nojvek`은 Jev가 클라우드 모델이 아니었다면 훨씬 흥분했을 것이라며,
소비자 하드웨어에서 아주 빠르게 돌 수 있는 것을 원한다고 적었다.
인상적인 작업이고 깎아내리려는 것이 아니지만, 쓸 때마다 문지기에게 AI 세금을 내는 것이 싫다는 것이다.[^nojvek]
`dsabanin`이 답으로 [jevlike](jevlike.md)를 링크했다.[^dsabanin]

이 지적이 이 저장소의 구조를 드러낸다.
브라우저와 정책 코드는 로컬에서 돌지만 결정은 전부 네트워크 너머에 있다.
Jev 지연 중앙값 178 ms가 그 왕복이며, 17번이면 약 3초다.
7.1초 중 3초가 네트워크 왕복이라는 뜻이고, 이것은 모델을 로컬로 옮기지 않는 한 줄지 않는다.

`ramon156`은 더 나아가 Jev에 대해 알수록 관심이 줄어든다며,
Home Assistant 같은 곳의 로컬 모델이었다면 좋았을 것이고 이런 프로젝트들은 잘해야 오해를 부른다고 적었다.[^ramon156]
반론도 있었다. `adam_arthur`는 이것이 분류와 프로그래밍적 분기, 실시간 결정을 한 자릿수 빠르고 싸게 할 수 있다는 점을 사람들이 못 보는 것 같다고 했다.[^adam_arthur]

그리고 README 상단의 Browser Use Cloud 대기자 명단 링크가 이 논의와 무관하지 않다.
이 저장소는 MIT 라이선스의 열린 코드이면서, 동시에 유료 클라우드 제품으로 가는 입구이기도 하다.

### 원격 디버깅으로 기존 프로필에 붙는다

README는 소유한 탭이 기존 Chrome 프로필을 공유한다고 적는다.
편의로 보이는 이 문장이 보안 경계를 정한다.
로그인된 세션과 쿠키, 저장된 비밀번호가 있는 프로필에서 에이전트가 돌아간다는 뜻이다.

HN에서 `maho`가 관련된 문제를 보고했다.
browser-use 내부를 살펴봤는데 기본 활성화된 PostHog 텔레메트리가 지나치며,
특히 browser-harness 구성 요소가 자격 증명을 PostHog로 흘릴 수 있어 전혀 괜찮지 않다는 것이다.[^maho]

이 보고는 이 저장소가 아니라 그것이 의존하는 browser-harness에 대한 것이지만, 실제 사용자에게는 같은 문제다.
`uv sync`가 browser-harness를 함께 설치하고, 그것이 로그인된 Chrome 프로필에 붙는다.

그래서 이 도구를 시험할 때 첫 단계는 별도 프로필이나 격리된 환경을 쓰는 것이어야 한다.
README는 이 점을 다루지 않고, 대신 원격 디버깅을 허용하라고만 안내한다.

## 함정

7.1초는 초기 관측 이후부터 잰 시간이다. 브라우저 설정과 초기 내비게이션, 실행 후 검증은 포함되지 않는다.

비교는 세 쌍뿐이고 문서 스스로 p = 0.25라고 밝힌다. 25% 개선을 일반적인 결과로 옮기면 안 된다.

기존 Chrome 프로필을 공유한다. 로그인된 세션에서 에이전트를 돌리는 것이므로 별도 프로필을 쓰는 편이 안전하다.

의존하는 browser-harness의 텔레메트리가 기본 활성화되어 있다는 보고가 있다. 설치 후 확인해야 한다.

`DONE`은 성공의 증거가 아니다. 독립적인 결과 검증을 따로 두어야 한다.

DOM 리더가 완전한 접근 가능 이름 알고리즘을 구현하지 않는다. 그림자 루트와 프레임, 캔버스, 업로드, 팝업 탭, 중첩 스크롤, 임의 키보드 위젯은 MVP 범위 밖이다.

텍스트 헬퍼 출력은 형식만 검사된다. 작은 JSON으로 파싱되면 통과하므로 내용에 대한 방어는 없다.

비용은 입력 토큰이 정한다. 요소가 많은 페이지일수록 대상 헤드들이 커지므로 요청당 토큰이 늘어난다.

요소가 255개를 넘는 페이지에서는 한 번의 요청이라는 전제가 깨진다. Jev의 선택지 상한이 255다.

요소 표의 순서가 확률을 바꾼다. DOM 순서가 조금만 달라져도 같은 요소에 대한 선택 확률이 움직인다.

대상 질문들은 서로를 보지 못한다. 연산 두 개를 한 호출로 내리려는 확장은 이 경계에 막힌다.

컨텍스트가 32K다. 요소가 많은 페이지에서 표 자체가 상태 예산을 먹는다.

## 확인하기

이 저장소는 확인 장치를 스스로 갖추고 있다.

```bash
# 모델 호출 없이 로컬 브라우저에서 실제 컨트롤을 검사한다
uv run python scripts/check_guards.py

# 오프라인 테스트: 모델 계약, 오래된 재시도, 중단된 변경, 헬퍼 검증
uv run pytest
```

주장을 재현하려면 성능 문서의 경계를 그대로 맞춰야 한다.
같은 뷰포트와 같은 모델, 같은 예산으로 교대 실행해야 하고, 무엇보다 시계의 시작과 끝을 같게 두어야 한다.

그리고 자기 작업에 옮길 때 가장 먼저 봐야 할 것은 Jev 요청 횟수다.
Flights가 17회였으므로 왕복 지연에 17을 곱한 것이 하한이고, 그 값이 감당 가능한지가 도입 여부를 정한다.

## 체크리스트

- 별도 Chrome 프로필이나 격리된 환경에서 돌리고 있는가
- browser-harness의 텔레메트리 설정을 확인했는가
- `DONE` 이후의 독립적인 결과 검증을 붙였는가
- 대상 페이지가 그림자 루트나 프레임, 캔버스를 쓰지 않는가
- 작업당 예상 Jev 요청 횟수와 왕복 지연을 곱해 봤는가
- 요소가 많은 페이지에서 요청당 입력 토큰이 얼마나 되는지 쟀는가
- 텍스트 헬퍼가 만든 문자열이 입력되기 전에 통과하는 검사가 형식뿐임을 알고 있는가

## 기억할 원칙

### 한 계층의 비용이 내려가면 그 위 설계의 정답이 바뀐다

이 저장소의 핵심은 새 모델을 썼다는 것이 아니라, 모델 호출이 싸지자 루프 설계를 다시 그렸다는 것이다.

투기적 팬아웃이 그 예다.
쓰지 않을 답까지 미리 묻고 버리는 것은 호출이 비쌀 때는 명백히 낭비이지만, 싸지면 왕복을 아끼는 최적화가 된다.
같은 코드가 한쪽 조건에서는 낭비이고 다른 쪽에서는 최적화인 것이다.

이 형태는 컴퓨팅 역사에서 반복된다.
메모리가 싸지자 캐시와 비정규화가 정답이 되었고,
CPU가 싸지자 분기 예측과 투기적 실행이 표준이 되었으며,
대역폭이 싸지자 필요한 것만 요청하던 프로토콜이 통째로 보내는 쪽으로 옮겨 갔다.
공통점은 자원 하나의 값이 내려갈 때 그것을 아끼려고 만든 모든 구조가 갑자기 부채가 된다는 것이다.

그래서 새 기술의 영향을 가늠할 때 물어야 할 것은 그것이 얼마나 빠른가가 아니라, 무엇이 싸졌는가다.
그리고 그 자원을 아끼려고 만들어 둔 구조들을 찾아보는 것이다.
에이전트 루프에서 그 구조는 결정을 아끼는 것이었다.
한 번에 많이 계획하고, 재확인을 줄이고, 불확실해도 진행하던 관행들이 전부 호출이 비싸서 생긴 것이며,
호출이 싸지면 자주 묻고 자주 확인하는 쪽이 정답이 된다.

### 자기 주장을 약화시키는 수치를 문서에 남기는 것이 그 문서를 쓸 수 있게 만든다

이 저장소의 성능 문서는 자기에게 불리한 정보를 여러 번 적는다.
세 쌍은 너무 적다고 적고, p = 0.25를 밝히고, 광범위한 벤치마크가 아니라고 분명히 하고,
검증에 실패한 개발 시도와 그 시간까지 남기고, 보고된 비용이 텍스트 헬퍼 요금일 뿐이라고 분리한다.

이 단서들이 없었다면 25%와 7.1초는 그냥 마케팅 숫자였을 것이다.
있기 때문에 읽는 사람이 자기 상황과 비교할 수 있다.
p = 0.25를 알면 이 결과를 근거로 채택 결정을 내리지 않고 직접 재 보게 되며, 그것이 이 문서가 실제로 유용해지는 방식이다.

여기서 나오는 규칙은 성능 주장을 적을 때 측정의 경계를 함께 적으라는 것이다.
시계가 언제 시작하고 언제 끝나는지, 무엇이 제외되었는지, 표본이 몇이고 그것이 무엇을 말할 수 없는지다.

다만 이 저장소는 그 규칙의 한계도 함께 보여 준다.
단서는 성능 문서에 있고 숫자는 README 제목에 있으며, 대부분의 사람은 제목만 읽는다.
`ofisboy`의 질문이 나온 것이 그 증거다.
그러니 정직함을 문서 깊은 곳에 두는 것으로는 부족하고, 숫자를 제시하는 바로 그 자리에 경계를 한 줄이라도 붙이는 것이 필요하다.
