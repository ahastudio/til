# Laya 실측기: 정확도 78%보다 틀린 답에 붙은 확신 0.9가 문제였다

원문: [틀렸는데, 확신은 0.9였다](https://decipher99.com/posts/tool-review/%ED%8B%80%EB%A0%B8%EB%8A%94%EB%8D%B0-%ED%99%95%EC%8B%A0%EC%9D%80-09%EC%98%80%EB%8B%A4/)

GN 토론: <https://news.hada.io/topic?id=34599>

## 요약

글쓴이는 개인용 Obsidian 플러그인을 만들고 있다.
원문 자료를 넣으면 LLM이 개념별 노트로 정리해 주는 도구인데,
자료를 여러 번 넣다 보면 같은 제목의 노트가 두 번 생긴다.
그러면 플러그인이 두 노트를 OpenAI API에 보내 같은 개념이면 합치고 제목만 같고
내용이 다르면 구분되는 이름으로 바꾼다.
“합칠까 말까” 같은 판단 하나하나에 LLM 호출 전체를 쓰는 것이 아깝다고 생각하던
차에, 이런 저차원 판단만 전담하는 모델을 들었다는 것이 출발점이다.
TypeSafe의 Jev와 그 오픈소스 대항마 Laya를 지금 하는 판단에 붙일 수 있는지
확인했고, 결론은 더 쓰지 않기로 한 것이다.

글은 Jev와 Laya를 이렇게 설명한다.
텍스트를 생성하지 않고 상황(state)과 타입이 정해진 질문을 주면 확률과 함께
답만 돌려주는 모델이다.
답의 형태는 choice(선택지 중 하나), score(순서형 점수),
noul(참일 확률) 세 가지뿐이다.
Jev는 프로프라이어터리로 2026년 9월 15일에 얼리 액세스로 나왔고,
Laya는 ModernBERT-large 기반 421M 파라미터에 Apache 2.0이다.

시도 과정에서 글쓴이는 먼저 두 번 헛다리를 짚었다.
허깅페이스의 “GGUF” 파일은 llama.cpp의 표준 GGUF가 아니라 ggmlc라는 별도
컴파일러가 만든 형식이어서 Ollama에서 열리지 않았다.
처음 찾은 GitHub 저장소(`he-jev/laya`)는 README가 실제 모델 정보와 일치해
원본처럼 보였지만, README 맨 아래 링크 섹션이 다른 주소를 원본으로 가리켰다.
원본은 별 27,891개의 `NandhaKishorM/laya`였고 처음 본
저장소는 별 7개짜리 미러였다.

속도는 광고와 차이가 컸다.
GPU 없는 12코어 집 PC(가용 RAM 23GB)에서
`pip install laya`로 설치해 영어 체크포인트(`convaiinnovations/laya`)를 돌렸고,
콜드 로딩은 모델 다운로드 포함 23초, 로드 후 메모리는 2.7GB,
호출당 평균 지연은 1.3초였다.
README의 33ms와 39.5ms는 Tesla T4 GPU 기준이었다.

정확도는 보관소에 남아 있던 실제
중복 노트 17쌍(같은 원문 기사가 서로 다른 자료 파일 두 개에 겹쳐 들어가 생긴 것,
전부 “같음”이 정답)과 제목만 같고 무관한 노트 6쌍을 직접 만든 합성 사례로 쟀다.
23건 중 18건(78%)을 맞혔고, 진짜 중복 17건 중 14건과 합성 6건 중 4건이다.
그러나 맞힌 답에도 confidence가 0.01, 0.011,
0.016처럼 동전 던지기 수준인 경우가 많았고, 전혀 다른 노트를 “같다”고 틀리면서
0.802와 0.896의 높은 확신을 보인 경우가 있었다.
모델을 로드할 때 이미 이 체크포인트가 손상된 temperature 값을 갖고 있어
confidence를 믿을 수 없다는 경고가 떠 있었다.

개선 경로는 둘 다 막혀 있었다.
Laya의 공식 문서는 Kaggle 무료 2×T4 GPU에서 RLCD로 학습하고
학습 데이터에서 최대 400개를 떼어 confidence temperature를 다시 맞추라고
하지만, 필요한 것은 정답 라벨이 아니라 state, 질문들,
교사 모델이 각 선택지에 준 확률 분포이며 문서의 데모도 1,200건(질문 6,000개),
실제 벤치마크는 3만 건 규모였다.
손에 있는 실측은 23건뿐이다.
Jev는 고객 데이터로 파인튜닝이나 LoRA를 아예 지원하지 않으며 모든 계정이 같은
가중치를 공유하고 맞춤화는 프롬프트 수준에 한정된다고 TypeSafe 쪽이 답했다.
글쓴이는 Jev에는 계정 접근이 아직 열리지 않아 공식 문서만으로 비교했다.

## 분석

### 글의 중심 주장은 숫자에는 조건이 붙는다는 것이다

글은 세 가지 숫자를 차례로 해체한다.
33ms는 GPU 수치였고, 78%라는 정확도는 개별 답을 열어 보니 확신이 엉망이었으며,
확신 자체는 로드 시점에 이미 경고가 떠 있던 손상된 값이었다.
마지막 문단의 교훈(“숫자는 어떤 조건에서 나온 건지까지 같이 봐야
한다”)이 글 전체를 요약한다.

이 구성의 효과는 결론이 도구 평가에서 평가 방법으로 옮겨 가는 데 있다.
Laya를 쓸지 말지의 답은 “지금은 쓰지 않는다”이지만,
독자가 가져가는 것은 실측 방법이다.
광고 수치의 하드웨어 조건 확인, 정확도의 분해(맞힌 답의 확신까지 열어 보기),
모델이 보내는 경고 읽기가 그것이다.

### System One 모델의 가치는 확률을 믿을 수 있을 때만 성립한다

글쓴이는 이런 모델의 핵심 가치를 확률을 믿고 임계값으로 자동 게이팅할 수
있다는 것으로 정의한다.
LLM 호출을 줄이는 이득은 확신이 높은 건은 모델이 처리하고 낮은 건만 사람이나
LLM에게 넘기는 구조에서 나온다.
이 구조에서는 정확도 평균보다 보정(calibration)이 더 중요하다.

78%라는 정확도만 보면 “아직 부족하지만 써볼 만하다”가 되지만,
보정이 깨져 있으면 임계값으로 거를 수 없고 78%는 쓸 수 없는 숫자가 된다.
틀린 답이 높은 확신으로 나오면 자동 처리 경로로 흘러 들어가기 때문이다.

### 개선 경로가 데이터 비용으로 막혔다

Laya의 파인튜닝은 GPU가 아니라 데이터가 병목이라는 진단이 글의
가장 구체적인 대목이다.
필요한 입력이 정답 라벨이 아니라 교사 모델의 확률 분포이므로,
사용자는 지금의 OpenAI API 판단을 확률과 함께 쌓아 두어야 한다.
이는 “작은 모델로 갈아타기”가 하루짜리 작업이 아니라 판단 로그를 쌓는
장기 투자라는 뜻이다.

Jev와의 대비도 선명하다.
Laya는 직접 개선할 수 있는 대신 그 개선의 부담을 지고, Jev는 그 부담이 없는
대신 정확도 상한이 벤더가 만든 모델 성능에 묶인다.
어느 쪽을 택하든 사용자의 도메인 데이터를 반영하는 일은 사용자가
해야 한다는 점은 같다.

## 비평

### 23건의 표본은 78%를 해석하기에 모양이 나쁘다

표본 23건은 작을 뿐 아니라 구성이 한쪽으로 치우쳐 있다.
진짜 사례 17건은 전부 정답이 “같음”이고,
정답이 “다름”인 사례 6건은 글쓴이가 직접 만든 합성이다.
모든 질문에 “같음”이라고만 답하는 모델도 이 표본에서 17/23, 약 74%를
맞힌다(필자의 계산이다).
Laya의 78%는 이 기준선을 크게 넘지 못한다.

더 읽어 보면 클래스별 정확도(진짜 중복 14/17, 합성 4/6)가 더 의미 있는 수치다.
다만 합성 6건은 서로 무관한 노트 쌍이라 실제 운영에서 마주칠 “제목만 같고 내용이
조금 다른” 어려운 사례를 대표하지 않을 수 있다.
글은 78%를 결론의 근거로 쓰지 않고 확신 문제로 넘어가므로 치명적인 약점은
아니지만, 숫자를 인용하는 사람은 이 구성을 알아야 한다.

### 대안으로 남긴 OpenAI API의 정확도는 재지 않았다

결론은 정확도도 확신에 대한 신뢰도도 이미 검증된 방식을 굳이 바꿀
이유가 없다는 것이다.
그런데 같은 23건에 OpenAI API가 몇 건을 맞히는지는 글에 없다.
검증된 방식이라는 판단은 글쓴이의 운영 경험에 기댄 것으로 읽히며,
측정된 비교가 아니다.

공정한 비교는 같은 23건을 같은 방식으로 API에 물어 78%와 나란히 놓는 것이다.
이 비교가 있어야 “Laya가 모자라다”와 “이 과제가 어렵다”를 구분할 수 있다.

### 제목의 일반화는 손상된 체크포인트에 대한 것이다

제목과 마지막 교훈은 확신이라는 값을 마케팅 문구만 보고 믿으면 안
된다는 일반론으로 읽힌다.
그러나 글 중간에 밝힌 대로 이 체크포인트는 temperature 값이 손상돼 있고 모델
스스로 confidence를 믿을 수 없다고 경고했다.
틀린 답의 0.9는 Laya라는 설계가 아니라 이 체크포인트의 보정 실패를 보여 준다.

공정하게 말하면 글쓴이도 이 경고를 본문에서 밝히고 파인튜닝으로 temperature를
다시 맞추는 방법을 검토했다.
그래도 제목이 앞세우는 메시지와 본문의 단서 사이에는 간격이 있다.
보정이 깨진 체크포인트를 재보정해도 같은 문제가 남는지는 이 글로는 알 수 없다.

### 속도와 환경 조건에 보이지 않는 변수가 있다

호출당 평균 1.3초가 GPU 없는 12코어 PC의 값이라는 점은 분명히 적혀 있다.
그러나 이 평균이 첫 호출을 포함하는지,
입력 길이는 얼마였는지, 두 노트를 한 번에 넣은 경우인지는 글에 없다.
또 영어 체크포인트를 썼다고만 밝히고 노트의 언어는 말하지 않는다.
노트가 한국어라면 영어 체크포인트의 성능 저하가 78%에 섞여 있을 수 있다(노트의
언어는 글에서 확인되지 않았다).
421M 트랜스포머를 CPU로 돌리면 이 정도 격차는 흔하다는 설명도 글쓴이의
추정이며 측정이 아니다.

## 인사이트

### 확률을 내놓는 모델의 진짜 자산은 가중치가 아니라 보정 데이터다

글의 가장 중요한 사실은 Laya 문서가 학습 데이터에서 최대 400개를 떼어 confidence
temperature를 다시 맞추라고 한다는 점이다.
보정은 모델이 낸 확률이 실제 정답률과 맞는지를 확인하는 작업이고,
그러려면 운영 환경에서 쌓은 정답 데이터가 필요하다.
Jev는 모든 계정이 같은 가중치를 공유하므로 보정도 벤더가 정한 상태에
머물러 사용자의 도메인 분포와 어긋날 가능성이 있다(문서에서 확인된 것은 가중치
공유뿐이며 보정 방식은 확인하지 못했다).

2차 효과는 로깅의 가치다.
지금 LLM 호출로 판단을 처리하는 팀은 그 판단과 확률(또는 신뢰도 신호)을 버리지
않고 쌓는 것만으로 나중에 작은 모델로 옮길 때 쓸 보정 자원을 갖게 된다.
글쓴이가 개선 경로로 짚은 “플러그인이 중복 판단을 할 때마다 결과를 확률과 함께
꾸준히 모아야 한다”는 대목이 이것이다.

### 광고 수치는 조건이 붙은 문장으로 읽어야 한다

33ms가 T4에서의 값이라는 지적은 이번 글만의 일이 아니다.
이 저장소의 엣지 VLA 노트([[vla-on-npu]])도 기준은 Jetson Thor에서,
적용은 IQ-9075에서 하는 식으로 측정 환경이 섞여 있었다(필자의 관찰이다).
하드웨어, 입력 크기, 배치, 콜드와 웜,
포함하는 구간이 다르면 같은 이름의 지연이 다른 수치가 된다.

이 패턴의 비용은 비대칭이다.
조건을 확인하는 쪽은 한 번의 실측이면 되지만,
확인하지 않고 도입하면 지연 예산이 30배 틀어질 수 있다.
글쓴이가 아낀 것은 사실상 이 검증의 비용이었고, 그 검증이 결론을 정했다.

### 모델 저장소의 신뢰 사슬은 이름과 별이 아니라 링크 구조에서 확인된다

글쓴이는 README가 실제 모델 정보와 일치해서 원본이라고 믿었다가 README 안의
링크가 다른 주소를 원본으로 가리키는 것을 보고 미러임을 알았다.
별 7개와 27,891개의 차이는 그 뒤에 확인했다.
“GGUF”라는 이름이 붙은 파일이 표준 GGUF가 아닌 것도 같은 부류의 문제다.
이름이 같은 형식이 서로 다른 도구 체인을 가리킨다.

AI 모델 생태계에서는 내용을 복제한 저장소와 이름을 빌린 형식이 쉽게
생긴다(필자의 관찰이다).
그러면 내려받기 전에 확인할 최소 항목은 소유자, 별 수, 링크가 가리키는 원본,
파일 형식의 실제 의미가 된다.
글의 첫 번째 교훈은 이렇게 도구 평가 이전의 출처 확인에 있다.

### 호출 횟수를 보면 이 교체의 경제성은 애초에 낮았다

글쓴이의 동기는 판단마다 LLM 호출 전체를 쓰는 것이 아깝다는 것이었다.
그런데 실측에 쓴 진짜 중복은 보관소 전체에 17쌍이다.
이 정도 호출량이라면 API 비용은 미미하고, 교체로 얻을 수 있는 절감도 작다.
작은 모델로 얻을 이득은 호출량이 아주 많거나 지연 예산이 빠듯할 때 생긴다(필자의
계산이며 글에는 호출량이나 비용 수치가 없다).

그렇다면 이 실험이 보여 준 것은 Laya의 한계만이 아니라 교체의 전제다.
교체 전에 호출량, 호출당 비용,
허용 지연을 적어 보면 모델의 정확도를 재기 전에 결론이 나는 경우도 있다.
글쓴이가 끝내 OpenAI API를 유지한 것은 정확도 때문이기도
하지만, 이 경제성 계산에서도 같은 결론이 나온다.
