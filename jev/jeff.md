# Jeff: 집에서 학습한 0.8B 모델로 Jev와 같은 요청을 30ms 안에 결정하기

<https://github.com/firelex/jeff>

HN 토론: <https://news.ycombinator.com/item?id=49883844> (571점, 223개 댓글)

GN 토론: <https://news.hada.io/topic?id=34459>

## 소개

Jeff는 Qwen3.5와 Gemma 4를 제로샷 분류용으로 파인튜닝한 작은 의사결정 모델 모음이다.
상황을 글로 쓰고 선택지를 평범한 말로 나열하면, 한 번의 순전파로 선택지마다 보정된 확률을 돌려준다.
텍스트를 생성하지 않으니 파싱할 것도 없다.
요청 형식은 [Jev](jev.md)와 같지만, README는 TypeSafe와 제휴하거나 승인받은 프로젝트가 아니라고 밝힌다.

저장소는 2026년 9월 28일에 v1.0으로 공개되었고, 다음 날 v1.1이 나왔다.
2026년 10월 1일 기준 GitHub 별 1,188개, 포크 49개다.
코드는 MIT, 모델 가중치는 Apache 2.0이다.
학습 코드는 Denis Yarats의 AutoJev에서 출발했다.
AutoJev는 Qwen3.8-27B를 Jev 스타일 결정을 내도록 파인튜닝하는 공개 레시피이고, Jeff는 그 핵심 설계인 결정당 한 번의 순전파, 학습된 답 판독부, 보정용 온도 하나를 유지한 채 학생 모델의 크기를 0.8B와 2B로 줄였다.

이 프로젝트의 특징은 전부 집에서 만들었다는 점이다.
학습은 RTX PRO 6000 워크스테이션 GPU 한 장에서 했고, 0.8B는 약 2시간, 2B는 약 3.5시간이 걸렸다.
합성 학습 데이터는 DGX Spark 두 대에서 돌린 공개 모델 Qwen3.8-Flash-Next가 썼고, 테스트는 MacBook에서 했다.
클라우드 GPU도, 학습 데이터 안의 폐쇄 모델 출력도 없다.
폐쇄 모델은 합성 데이터 표본의 품질을 확인하는 데만 썼다고 한다.
작성자 firelex는 HN 첫 댓글에서 이 모든 과정을 휴대폰으로 Tailscale을 통해 지켜봤다고 덧붙였다[^firelex].

README가 스스로 그은 경계는 분명하다.
아주 작은 모델이므로 선택지 사이의 빠르고 잘 보정된 판단은 하지만, 추론은 훨씬 큰 모델 위에서 도는 Jev를 따라가지 못한다.
제로샷 정확도가 부족하면 자기 예시로 짧게 파인튜닝하라는 것이 README의 답이다.

## 요청 형식

서빙만 하려면 학습과 평가 패키지를 뺀 설치로 충분하다.

```bash
uv sync --no-default-groups                 # CPU
uv sync --no-default-groups --extra cuda    # NVIDIA GPU, 빠른 커널 포함
uv sync --no-default-groups --extra mac     # Apple silicon, MLX 포함
uv run --no-default-groups hf download mstrasser/Jeff-Qwen3.5-0.8B --local-dir checkpoints/jeff-0.8b

# NVIDIA GPU 또는 CPU(PyTorch)
JEFF_CHECKPOINT=checkpoints/jeff-0.8b PORT=8765 uv run --no-default-groups jeff-serve
# Apple silicon(MLX, Qwen 모델만)
JEFF_BACKEND=mlx JEFF_CHECKPOINT=checkpoints/jeff-0.8b PORT=8765 uv run --no-default-groups --extra mac jeff-serve
```

요청은 Jev의 `/v1/systemone` 모양을 그대로 쓴다.

```bash
curl -s localhost:8765/v1/systemone -H 'content-type: application/json' -d '{
  "model": "jeff-latest",
  "state": "Refund request: the customer says the parcel arrived crushed and wants their money back.",
  "questions": {
    "route": {"type": "choice", "instructions": "Which team should handle this?",
              "criteria": {"1": "Refunds and payments", "2": "Damaged or lost parcels", "3": "Account and login problems"}},
    "angry": {"type": "noul", "instructions": "Is the customer angry?"}
  }
}'
```

질문 유형은 셋이다.
`choice`는 여러 선택지 중 하나를 고르고, `noul`은 예/아니오를 확률로 돌려주고, `score`는 설명한 척도 위의 한 점을 고른다.
한 요청 안의 독립 질문 여러 개는 함께 답한다.
답마다 선택지별 확률, 고른 선택지, 신뢰도가 붙는다.

## 모델 고르기

README가 같은 200개 벤치마크 질문(각 약 200 입력 토큰)으로 잰 결정당 중앙값 시간이다.

| 모델              | 파라미터           | 가중치(16비트) | RTX PRO 6000 | M4 Max(MLX) | CPU(32스레드) |
| ----------------- | ------------------ | -------------- | ------------ | ----------- | ------------- |
| Jeff-Qwen3.5-0.8B | 0.8B               | 1.7 GB         | 22 ms        | 28 ms       | 463 ms        |
| Jeff-Qwen3.5-2B   | 2B                 | 4.2 GB         | 24 ms        | 60 ms       | 708 ms        |
| Jeff-Gemma4-E2B   | 유효 2B(저장 4.6B) | 9.3 GB         | 29 ms        | 지원 안 함  | 1.0 s         |

비교 대상인 Jev는 파라미터가 공개되지 않은 API 전용 모델이고, 공개된 Doom 실행에서 네트워크를 포함해 호출당 114~212ms가 걸렸다.

선택지 수의 상한도 모델마다 다르다.
v1.1의 Qwen 모델은 20~254개 선택지 목록으로 학습해 254개까지 받는다.
Jeff-Gemma4-E2B는 v1.0 그대로라 26개까지만 믿을 만하고, 서버가 그보다 긴 목록을 거부하므로 먼저 후보를 줄여야 한다.

README의 권장은 0.8B다.
2B는 벤치마크 점수가 더 높지만 더 조심스럽고 게임을 더 못한다.
빠르게 선택지를 고르는 용도라면 0.8B가 적정점이라는 것이다.

## 게임으로 본 제로샷

벤치마크와 전혀 다른 과제에서 제로샷 성능을 보려고 Doom, Frogger, Pac-Man을 시켰다.
매 턴 코드가 상황과 합법적인 수를 글로 설명하고 모델이 하나를 고른다.
선택지는 각 수가 무엇으로 이어지는지 말해 주지만, 어느 수가 옳은지는 말하지 않는다.
결과는 v1.0 모델로 잰 것이고 게임당 20 에피소드다.

| 모델                 | Doom 처치 수 | Frogger 건넌 횟수 | Pac-Man 알갱이(98개 중) |
| -------------------- | ------------ | ----------------- | ----------------------- |
| 무작위               | −0.05        | 0                 | 11.2                    |
| 손으로 짠 규칙 봇    | 6.55         | 10.25             | 94.1                    |
| Qwen3.5-0.8B 학습 전 | 5.0          | 1.0               | 25.8                    |
| Jeff-Qwen3.5-0.8B    | 6.55         | 10.3              | 57.0                    |
| Jeff-Qwen3.5-2B      | −0.9         | 6.0               | 41.2                    |
| Jeff-Gemma4-E2B      | 0.55         | 0.15              | 53.2                    |

Jev의 공개 Doom 실행은 조준 규칙을 알려 주면 6.55, 알려 주지 않으면 −0.60이었다.
Jeff 0.8B는 규칙 대신 가장 가까운 몬스터가 조금 왼쪽에 있다는 문장을 받아 같은 6.55를 냈고, M4 Max에서 수당 29~49ms에 결정했다.
두 시간은 같은 하드웨어에서 잰 것이 아니다.

## 파인튜닝

제로샷이 부족할 때의 예시가 둘 있다.

음성 내비게이션은 앱 전용 예시 약 1만 1,000개로 GPU 한 장에서 30분쯤 파인튜닝해, 보류 명령 정확도를 31.7%에서 95.8%로 올렸다.
M4 Max에서 결정당 약 40ms다.

체스는 Stockfish가 라벨을 붙인 Lichess 포지션 60만 개로 0.8B를 약 3시간 반 학습했다.
보류 퍼즐 1,000개에서 학습 전 6.2%, 체스 학습 없는 제로샷 15.5%, 체스 파인튜닝 55.8%를 풀었다.
탐색 없이 약 1,000 Elo라 Stockfish의 가장 약한 설정에도 지지만, README는 요점이 속도라고 말한다.
수마다 순전파 한 번이라, GPU 한 장이 사람 블리츠 게임 약 600판을 동시에 따라간다.

```bash
# 기존 Jeff 체크포인트에서 이어 학습한다
jeff-train --initial-checkpoint <jeff> --epochs 1 ...
```

학습 레시피는 전체 가중치 파인튜닝 1에폭, 배치 256, 선택지 글자에 대한 교차 엔트로피, 그리고 보정용 온도 하나 맞추기다.
v1.1부터는 에폭 끝의 체크포인트를 쓰고, 벤치마크 패널은 선택이나 튜닝에 쓰지 않는다.

## 트레이드오프

### 제로샷의 편리함은 자기 과제에서 다시 재야 한다

README의 83%는 공개 벤치마크의 평균이고, 자기 과제의 정확도를 말해 주지 않는다.
HN의 AgentMasterRace는 자기 분류 과제에서 Jev 94%에 Jeff 70%였다며 분류에는 받아들일 수 없는 수치라고 했다[^AgentMasterRace].
Oras는 채용 공고의 업종, 근무 형태, 고용 형태 분류에서 Gemini 2.5 Flash Lite, Jev, Jeff를 나란히 비교했는데, 0.8B는 쓸모가 없었고 2B는 나았지만 고용 형태를 놓쳤다고 보고했다[^Oras].
tbeseda는 그건 당신의 분류에서 받아들일 수 없는 것이고, 작성자가 바로 그 경우를 위해 파인튜닝을 제시했다고 반박했다[^tbeseda].

여기서 트레이드오프가 드러난다.
제로샷은 라벨 데이터 없이 바로 쓸 수 있다는 점이 가치인데, 정확도가 부족해 파인튜닝을 해야 한다면 그 가치의 상당 부분이 사라진다.
sharih는 이런 클론 대부분이 결국 자기 과제로 파인튜닝해야 하니 차라리 ModernBERT를 파인튜닝하는 편이 낫고, Jev는 빠르고 싸면서 일반화가 잘된다는 점이 다르다고 지적했다[^sharih].
dingody는 임베딩 모델 뒤에 단순한 MLP를 붙이는 것만으로 많은 텍스트 분류 문제를 푼다고 했다[^dingody].
Jeff의 파인튜닝 경로가 이 고전적 방법보다 나은지는 README가 비교하지 않는다.

### 생성형 LLM에 구조화 출력을 거는 것과 무엇이 다른가

jubilanti는 스키마를 제한하는 Structured Outputs가 이미 오래 있었고, logprobs를 주는 공개 가중치 모델이면 키마다 분포도 얻을 수 있는데 무엇을 놓치고 있느냐고 물었다[^jubilanti].
wgd는 공개 모델이라면 Y/N 한 토큰으로 답하게 하고 로짓 차이를 보면 되며, 여러 질문은 공유 맥락을 앞에 두고 따로 물어 캐시를 쓰면 된다고 했다[^wgd].
thomasikzelf는 Qwen에게 한 토큰으로 답하게 하는 방식과 속도가 어떻게 다르냐고 물었다[^thomasikzelf].

차이는 구조보다 보정과 판독에 있다.
Jeff는 선택지 글자에 대한 학습된 판독부와 개발 세트에 맞춘 온도로 확률을 보정한다.
한 토큰 로짓 방식은 학습 없이 쓸 수 있지만, 그 확률이 실제 정답률과 맞는다는 보장이 없다.
README가 v1.1에서 보정 오차를 0.049에서 0.021로 낮췄다고 강조하는 것도 이 차이가 핵심이기 때문이다.
다만 같은 기반 모델에 한 토큰 로짓을 쓴 기준선과의 직접 비교는 README에 없다.

### 30ms는 짧은 입력에서의 숫자다

anvuong은 2020년에 TensorRT로 RTX 2080 Ti에서 200M 파라미터 비전 모델을 10ms 아래로 돌렸다며, 0.8B 분류기의 30ms가 특별하지 않다고 했다[^anvuong].
prodigycorp는 3만 2,000 토큰 프리필은 몇 ms냐고 물었다[^prodigycorp].
README의 속도표는 입력 약 200 토큰에서 잰 값이다.
긴 문서나 대화 전체를 상태로 넣는 순간, 시간은 프리필에 지배되고 30ms라는 숫자는 더 이상 적용되지 않는다.

## 함정

### 예측을 시키면 무작위와 같다

README는 이 모델이 계획자가 아니라 분류기라고 경고한다.
각 선택지가 무엇으로 이어지는지 말해 주면 잘 고르지만, 차가 두 턴 뒤에 온다처럼 예측을 요구하면 무작위보다 나을 게 없다.
추론은 코드에서 하고 결정만 Jeff에 맡기라는 것이 README의 원칙이다.

### 선택지의 말 한 마디가 결과를 바꾼다

Frogger에서 목표 칸 선택지에 다른 전진 선택지와 같은 말을 주자, 한 에피소드가 15번에서 23번 건너기로 늘었다.
작성자는 그 전에는 개구리가 마지막 통나무 위에 그냥 머물렀다고 적었다[^firelex].
Jev의 Doom 프롬프트, 즉 방위 숫자와 조준 규칙은 Jeff의 어느 모델에서도 통하지 않았고, 결과를 말로 적은 선택지만 통했다.
Jev에서 옮겨 올 때 프롬프트를 그대로 가져오면 안 된다는 뜻이다.

### v1.1부터 일부 과제는 더 이상 제로샷이 아니다

v1.1은 긴 선택지 목록을 학습시키려고 MASSIVE와 CLINC150의 학습 분할을 학습 데이터에 넣었고, 변경 기록에 두 과제가 더 이상 제로샷이 아니라고 밝혔다.
HN에서 ironqcold는 v1.0 공개 직후, 제로샷 분류라면 추론 중심의 BBH나 JudgeBench보다 Banking77이나 CLINC150처럼 실제 System 1 사용처에 가까운 벤치마크가 더 적절하지 않느냐고 물었다[^ironqcold].
그 제안에 등장한 CLINC150이 하루 만에 학습 데이터가 되었으니, 이제 이 과제로 Jeff의 제로샷 능력을 재는 것은 불가능하다.
의도 분류처럼 이 두 데이터셋과 겹치는 과제에서 좋은 결과가 나오면, 그것이 일반화인지 학습 분포 덕인지 구분해야 한다.

### 작성자 글과 README의 숫자가 다르다

HN 첫 댓글은 2B가 다섯 벤치마크 패널에서 83.1%로 Jev의 공개치 83.0%를 넘는다고 썼다[^firelex].
v1.1 README에서는 2B가 82.0%이고, 변경 기록은 2B가 더 이상 Jev의 83.0%를 넘지 않는다고 적는다.
토론을 읽고 저장소를 보는 독자는 서로 다른 버전의 숫자를 보게 된다.
Hugging Face에는 v1.0이 `v1.0` 리비전으로 남아 있으므로, 어느 숫자를 인용하는지 버전을 함께 적어야 한다.

### 영어와 텍스트만 된다

README의 마지막 경고다.
한국어 상태나 선택지를 넣은 결과는 README가 약속하지 않는다.

## 비평

### 83.0 대 83.1이라는 비교는 애초에 성립하지 않았다

README와 작성자의 글은 Jev 공개치와의 비교를 앞세우지만, 바로 옆에 공개치가 같은 벤치마크의 다른 표본에서 나왔다고 적는다.
표본이 다르면 0.1점 차이는 잡음 안에 있다.
folayii는 패널에서 83.1 대 83.0인데 누군가의 실제 사용에서는 70 대 94라는 것이 제로샷 분류의 전부를 말해 준다고 요약했다[^folayii].

이 프로젝트의 진짜 성과는 Jev와 동률이라는 숫자가 아니라, 워크스테이션 한 장과 공개 모델만으로 Jev와 같은 인터페이스를 이틀 만에 재현하고 그 한계를 표로 정직하게 공개했다는 데 있다.
그런데 제목과 첫 문단이 동률 비교를 앞세우는 바람에, 토론의 상당 부분이 자기 과제에서 Jev보다 못하다는 반박으로 흘렀다.
비교할 수 없는 숫자를 비교처럼 보여 주는 대가다.

### 크기를 키우면 게임을 더 못한다는 발견이 설명 없이 남아 있다

2B는 벤치마크에서 0.8B보다 높지만, Doom에서 −0.9로 무작위보다도 나쁘다.
README는 학습 전 2B가 이미 더 위험 회피적이고 학습이 그것을 악화시킨 것 같다며 더 조사해야 한다고 적는다.
학습 전 Gemma 4 E2B는 벤치마크에서 가장 높은데 게임을 가장 못한다.

이 관찰은 부록이 아니라 이 모델 계열의 핵심 위험을 가리킨다.
벤치마크 점수로 모델 크기를 고르면 실제 결정 루프에서 더 나쁜 모델을 고를 수 있다는 뜻이기 때문이다.
실시간 루프에서는 대부분 맞지만 가끔 틀리는 모델의 실수가 누적된다는 작성자의 설명[^firelex]도, 결정 모델을 평가할 때 정확도 평균보다 실패의 분포를 봐야 한다는 점을 말해 준다.

## 기억할 원칙

### 결정 모델은 추론을 코드로 밀어낼수록 강해진다

Jeff가 게임에서 규칙 봇과 같은 점수를 낸 것은 모델이 게임을 이해해서가 아니라, 코드가 각 수의 결과를 말로 번역해 주었기 때문이다.
결과를 말하지 않고 예측을 요구하면 무작위와 같아진다.
작은 결정 모델을 쓸 때의 설계 원칙은 모델이 똑똑해지기를 바라는 것이 아니라, 모델이 판단만 하면 되도록 상태와 선택지를 코드가 미리 정리해 주는 것이다.

### 벤치마크가 다르면 동률은 없다

다른 표본에서 잰 두 숫자는 비교가 아니라 나란히 놓인 두 숫자일 뿐이다.
결정 모델의 가치는 결국 자기 과제의 정확도, 보정, 지연으로 정해지고, 그 셋은 자기 데이터로만 잴 수 있다.
