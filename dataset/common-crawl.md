# Common Crawl: 15년간 3천억 페이지를 모아 무료로 공개하는 웹 크롤 저장소

<https://commoncrawl.org/>

HN 토론: <https://news.ycombinator.com/item?id=26594172> (397점, 61개 댓글)

## 소개

Common Crawl은 누구나 쓸 수 있는 무료 공개 웹 크롤 데이터 저장소를 유지하는 501(c)(3) 비영리 재단이다.
2007년에 설립되었고, 스스로 밝히는 목적은 공개 웹 데이터의 대규모 추출·변환·분석을 연구자가 할 수 있게 만드는 것이다.

랜딩 페이지가 내세우는 숫자는 네 개다.

- 15년에 걸친 3,000억 페이지 이상
- 2007년부터 무료 공개 코퍼스
- 10,000편 이상의 연구 논문에 인용
- 매달 30~50억 페이지 신규 추가

데이터는 AWS의 Open Data Sets Sponsorships 프로그램이 호스팅하며 `s3://commoncrawl/` 버킷에 있고, 리전은 us-east-1(북버지니아)이다.
AWS 클라우드 안에서 처리하거나, 회선이 괜찮다면 HTTP(S)로 무료로 내려받을 수 있다.
클라우드 밖에서 접근할 때는 `https://data.commoncrawl.org/` 접두사를 써야 하고, AWS 계정을 만들 필요가 없다.
S3 API로 접근하는 경로는 인증된 사용자에게만 열려 있다.

크롤은 `CC-MAIN-2026-30` 같은 식별자로 나뉘고, 선택 가능한 목록은 2016년부터 현재까지 이어진다.
파일 형식은 세 가지다.

| 형식 | 이름                        | 내용                              |
| ---- | --------------------------- | --------------------------------- |
| WARC | Web ARChive                 | 크롤에서 나온 원본 데이터         |
| WAT  | Web Archive Transformation  | WARC 레코드에 대한 계산된 메타데이터 |
| WET  | WARC Encapsulated Text      | WARC에서 추출한 평문만            |

사이트가 제공하는 나머지 자원은 CDXJ 인덱스, URL 인덱스, 웹 그래프, 최신 크롤, 크롤 통계, 그래프 통계, 정오표(Errata), 시작 가이드, AI 에이전트, 블로그, 예제, CCBot 문서, 인프라 상태 페이지, 옵트아웃 대장(Opt-Out Ledger), FAQ다.
커뮤니티 쪽에는 연구 논문 목록, 메일링 리스트 아카이브, Hugging Face, Discord, 협력 기관이 있다.

## CCBot

크롤러의 이름은 CCBot이고, User-Agent 문자열로 자기를 밝힌다.

```text
CCBot/2.0 (https://commoncrawl.org/faq/)
```

크롤을 원하지 않으면 `robots.txt`에 두 줄을 넣으면 된다.

```text
User-agent: CCBot
Disallow: /
```

문서는 CCBot을 사칭하는 크롤러가 존재한다는 사실을 인지하고 있다고 명시하고, User-Agent 문자열을 검증할 것을 권한다.
그리고 그 검증을 가능하게 하는 장치를 함께 제공한다 — CCBot은 이제 전용 IP 대역에서 역방향 DNS와 함께 운영된다(IPv6는 아직 역방향 DNS 미지원).

```bash
$ host 18.97.14.84
84.14.97.18.in-addr.arpa domain name pointer 18-97-14-84.crawl.commoncrawl.org.
$ host 18-97-14-84.crawl.commoncrawl.org
18-97-14-84.crawl.commoncrawl.org has address 18.97.14.84
```

정방향과 역방향 조회가 일치하는지 확인하는 표준적인 방식이고, IPv4와 IPv6 대역은 `https://index.commoncrawl.org/ccbot.json`에 JSON으로도 제공된다.

## 분석

### 자기 정체를 검증 가능하게 만드는 데 들인 노력이 이 조직의 위치를 설명한다

CCBot 문서에서 분량의 대부분을 차지하는 것은 크롤러의 능력이 아니라 크롤러의 신원 증명 방법이다.
User-Agent 문자열, `robots.txt` 옵트아웃 두 줄, 사칭 경고, 전용 IP 대역, 역방향 DNS, 그 대역의 JSON 공개, 그리고 별도의 옵트아웃 대장.

이 목록이 길어진 이유는 Common Crawl이 놓인 자리 때문이다.
이 조직은 자기가 만든 데이터를 팔지 않고, 그래서 사이트 운영자에게 돌려줄 수 있는 것이 없다.
[내 사이트 트래픽의 99%는 봇이다](../web/99-percent-bots.md)가 제시한 지표 — 유입 방문자 1명당 크롤링 페이지 수 — 를 CCBot에 적용하면 값은 무한대다.
Google은 검색 트래픽으로 대가를 지불하고, Bing도 그렇다.
Common Crawl은 아무것도 보내지 않는다.

그래서 이 조직이 협상 테이블에 올릴 수 있는 것은 대가가 아니라 예측 가능성뿐이다.
“우리가 언제 오는지 확인할 수 있고, 오지 말라고 하면 오지 않으며, 우리를 사칭하는 것과 우리를 구분할 수 있다.”
전용 IP 대역과 역방향 DNS는 그 문장을 기술적으로 뒷받침하는 장치다.
그리고 이것이 사칭 크롤러 문제를 문서 안에서 직접 언급하는 이유이기도 하다 — CCBot을 사칭한 트래픽이 CCBot의 평판을 깎으면, 이 조직이 가진 유일한 자산이 손상된다.

이 구조를 [Anubis](../security/anubis.md)와 겹쳐 보면 흥미로운 대칭이 나온다.
Anubis는 사칭에 비용을 매겨 정체 공개를 유도하는 장치이고, Common Crawl은 그 정체 공개를 이미 최대한 성실하게 수행하는 쪽이다.
그런데 Anubis 문서가 명시하듯, 작업 증명 벽은 Internet Archive 같은 “좋은 봇”을 함께 차단한다.
정직하게 밝힌 크롤러가 정직함 때문에 더 쉽게 차단되고, 사칭하는 크롤러는 자바스크립트를 실행해서 통과한다.
현재 방어 도구들의 유인 구조가 뒤집혀 있다는 뜻이다.

### “구글만 웹을 크롤할 수 있다”에 대한 답으로 제시되지만 그 역할은 하지 못한다

HN 스레드가 열린 맥락 자체가 이 긴장을 보여준다.
rektide가 지적했듯 이 글은 당시 화제였던 “Only Google is allowed to crawl the web” 게시물과 밀접하게 연결되어 있었다[^rektide].
공개 코퍼스가 검색 독점의 대안이라는 기대가 자연스럽게 따라붙는다.

그 기대에 대한 반박이 스레드의 가장 밀도 높은 부분이다.
Grimm1은 여러 용도로 대단히 귀중하게 써 왔지만 구글 킬러의 자양분은 아니라고 정리했다 — 그들 스스로 밝히듯 구글이 크롤하는 규모에 접근하지 못하고, 같은 주기로 하지도 않으며, 폭·깊이·타임라인·속도·우선순위·수집 정보 모든 축에서 한참 못 미친다는 것이다[^Grimm1].
ricardo81은 크롤 우선순위의 문제를 짚었다 — 검색 엔진이 다음으로 크롤해야 한다고 판단하는 페이지에 대한 결정권이 완전히 자기 손 밖에 있고, 결국 Common Crawl 데이터 위에 자기 크롤을 얹어야 한다는 것이다.
그러면서 영국 CMA의 온라인 광고 독점 보고서가 추정한 색인 규모를 인용했다 — 구글 약 5,000~6,000억 페이지, Bing 약 1,000~2,000억 페이지[^ricardo81].
그렇다면 3,000억 페이지 15년치라는 숫자는 구글의 현재 색인 하나에도 못 미친다.

cblconfederate는 문제 자체를 다시 정의했다 — 이것은 검색 엔진을 만들기에 적합한 거대한 아카이브일 뿐, 링크 미리보기 도구나 학술 논문용 크롤러를 만들려는 사람에게는 답이 아니라는 것이다.
대부분의 웹사이트가 Cloudflare 뒤에 있고 그것이 구글과 주요 소셜 사이트만 화이트리스트에 넣은 채 나머지를 차단하거나 CAPTCHA를 띄우기 때문이며, 필요한 것은 이 SEO 과잉의 봇 감염 생태계가 아니라 웹을 기본으로 되돌리는 조치라는 것이다[^cblconfederate].

이 반박들이 공통으로 지적하는 것은 코퍼스와 크롤 권한이 다른 자산이라는 점이다.
Common Crawl이 제공하는 것은 과거의 스냅샷이고, 검색 엔진이 필요로 하는 것은 지금 임의의 URL에 접근할 권한이다.
후자는 데이터를 나눠준다고 해결되지 않는다.

### 이 코퍼스의 실제 최대 수요자는 검색이 아니라 언어 모델이었다

2021년 스레드에서 이미 그 전환이 언급된다.
gillesjacobs는 이것이 주로 언어 모델링 연구에 쓰인다며, 필터링된 CC가 GPT-3에 쓰였고 자신도 NLP 프로젝트에 CC 데이터를 썼다고 했다[^gillesjacobs].

이 사실은 사이트의 구성에도 나타난다.
WET 형식 — WARC에서 평문만 추출한 파일 — 이 세 형식 중 하나로 제공된다는 것이 그 증거다.
검색 엔진을 만들려면 원본 HTML과 링크 구조가 필요하고, 언어 모델을 학습시키려면 평문만 있으면 된다.
웹 그래프를 별도 자원으로 제공하면서 동시에 평문 전용 형식을 제공하는 구성은 두 종류의 사용자를 모두 상정한 것이다.
그리고 현재 페이지의 Featured Papers 목록을 보면 어느 쪽이 우세한지 짐작할 수 있다 — 웹 데이터에서의 언어 식별 성능 재평가(CommonLID), 5천만 건 독일어 뉴스 기사의 지오코딩과 임베딩, 스페인어 대규모 크롤링 코퍼스(esCorpius) 같은 항목들이다.

동시에 목록에는 크롤 자체를 연구 대상으로 삼은 논문도 있다.
“크롤러가 지키는 것과 잃는 것”이라는 부제가 붙은 종단 크롤 연구는 발견 곡선, 핵심의 지속성, 껍질의 동역학을 다루고, 다른 하나는 일관성 없고 신호가 부실한 차단에 직면한 웹 크롤러를 다룬다 — “Web Crawl Refusals: Insights From Common Crawl”.
즉 이 조직은 웹을 수집하는 주체이면서 수집 가능성 자체의 변화를 기록하는 관측소가 되었다.
차단이 늘어나는 과정을 데이터로 남기는 유일한 장기 기록이라는 점에서, 이 코퍼스의 가치는 내용물보다 시계열에 있을 수 있다.

### 비영리 구조가 이 데이터의 존재 조건이자 한계다

psKama가 데이터를 Amazon 대신 IPFS나 Sia 같은 탈중앙 시스템에 저장하는 것이 얼마나 실현 가능한지 물었을 때, duskwuff의 답이 이 프로젝트의 물리적 규모를 드러냈다 — 데이터셋 크기를 제대로 가늠하지 못한 것 같다며, 최근 몇 년간 매달 200~300TB씩 꾸준히 커졌고 전체 코퍼스는 거의 확실히 수십에서 수백 페타바이트 사이일 것이라고 했다.
이것은 예를 들어 Sia 네트워크 전체 용량보다 훨씬 크며, 이 규모의 데이터셋을 저장하고 온라인으로 제공하는 것은 저렴하지 않고, Amazon이 두 작업을 모두 관대하게 기부해 왔으니 그것을 거절하는 것은 어리석다는 것이다[^duskwuff].

이 답변이 조직의 구조를 요약한다.
Common Crawl은 데이터를 소유하지만 그것을 저장할 능력은 기부에 의존한다.
그리고 그 의존은 데이터 접근 정책에도 나타난다 — us-east-1에서 접근하는 것이 필수이고, Elastic IP나 로드 밸런서를 쓰면 라우팅된 트래픽에 요금이 붙을 수 있다고 경고하며, S3 API 접근은 인증된 사용자로 제한되었다.
공개 데이터이지만 접근 경로는 특정 클라우드의 구조에 묶여 있다.

staunch는 다른 방향에서 규모의 문제를 제기했다 — 구글의 지배력을 정면으로 공격하지 않는 이유가 돈이 없어서일 텐데, 구글만큼 공격적이고 포괄적으로 웹을 크롤하는 데 연간 얼마가 드는지 추산해 본 적이 있는지 물었다.
만약 연 20억 달러나 100억 달러 같은 숫자가 나온다면 구글을 끌어내릴 만큼의 기부를 모으는 것이 실제로 가능할지도 모르며, 수많은 구글 경쟁자가 그것을 보고 싶어 할 것이고 사실상 다른 모두에게도 큰 승리가 될 것이라는 논리다[^staunch].
이 제안이 5년 넘게 실현되지 않았다는 사실이 답에 가깝다.

## 비평

### 3,000억 페이지라는 숫자는 규모를 말하지만 유용성은 말하지 않는다

랜딩 페이지의 네 숫자는 모두 누적량이다 — 15년, 3,000억 페이지, 논문 10,000편, 월 30~50억 페이지.
그런데 이 코퍼스를 실제로 쓰려는 사람이 알아야 하는 것은 누적량이 아니다.

빠진 것들이 있다.
한 번의 크롤이 얼마나 많은 도메인을 덮는지, 같은 도메인에서 몇 페이지까지 들어가는지, 크롤 간 중복 비율이 얼마인지, 그리고 무엇보다 어떤 종류의 사이트가 빠져 있는지.
Grimm1이 지적한 폭·깊이·우선순위의 문제가 정확히 이 지점이다.
3,000억이라는 수는 그 안에 같은 페이지가 몇 번 들어 있는지, 스팸 도메인이 몇 퍼센트인지에 따라 완전히 다른 의미를 갖는다.

빠진 것 중 가장 중요한 항목은 차단률이다.
자기 사이트를 CCBot에게 열지 않는 도메인의 비율은 이 코퍼스의 대표성을 결정하는 핵심 수치이고, 2026년에는 그 수치가 빠르게 변하고 있을 것이다.
ricardo81이 2021년에 이미 이 질문을 던졌다 — 사이트 소유자 중 이것을 차단하는 비율이 유의미한지 알면 흥미로울 텐데, 과거 데이터를 보면 그렇지 않은 것 같다고[^ricardo81].
5년이 지난 지금 그 답은 달라졌을 가능성이 높고, 재단이 그 데이터를 가장 잘 알면서도 랜딩 페이지에 올리지 않는다.
Featured Papers에 “Web Crawl Refusals”가 들어 있다는 것은 조직이 이 문제를 인지하고 있다는 뜻이지만, 인지와 공표는 다르다.

### 옵트아웃이 유일한 통제 수단이고, 그 옵트아웃은 되돌릴 수 없는 것을 되돌리지 못한다

`robots.txt`에 두 줄을 넣으면 CCBot이 오지 않는다.
이것은 명확하고 존중되는 약속이지만, 다루지 못하는 것이 하나 있다 — 이미 수집된 데이터다.

Common Crawl의 코퍼스는 누적이고 영구 공개다.
2015년에 수집된 페이지는 그 사이트가 2026년에 옵트아웃하더라도 `CC-MAIN-2015-*` 안에 남아 있고, 이미 내려받은 수천 개의 사본에도 남아 있다.
“옵트아웃 대장”이라는 자원이 별도로 존재하는 것은 이 문제를 다루려는 시도로 보이지만, 근본적으로 배포된 데이터를 회수할 방법은 없다.

이 문제의 법적 측면은 2021년 스레드에서 이미 제기되었다.
riedel은 독일인으로서 저작물과 데이터베이스의 사본을 만들어 공개하는 것과 포함된 개인정보를 처리하는 것의 법적 근거가 늘 궁금했다고 썼다 — Internet Archive는 예외 규정이 적용되는 도서관에 가까워 보이지만 Common Crawl은 아카이빙을 넘어서는 여러 목적을 함께 광고하는 것 같고, 유럽에서도 이것이 가능할지, 미국 법제가 다른 것인지 물었다[^riedel].
nodamage는 두 갈래로 나눠 물었다 — 애초에 이 데이터를 수집하는 것이 합법인가(크롤한 모든 사이트의 명시적 허락은 없을 텐데), 그리고 이 데이터를 상업적 ML 학습에 쓰는 것이 합법인가(사이트가 그런 사례를 여럿 소개하지만 이용약관은 모호하다)[^nodamage].
sennight는 미국 판례로 답을 시도했다 — 메타데이터는 전화번호부 판결(Feist)에, 원시 WARC 데이터는 변형적 이용으로 볼 여지가 있고 시장 대체를 위협하지도 않으므로 공정이용에 해당할 것이라는 논리다[^sennight].

이 교환이 2021년의 것이라는 점이 중요하다.
당시 “시장 대체를 위협하지 않는다”는 논거는 설득력이 있었다 — 코퍼스를 쓰는 쪽은 주로 연구자였다.
그 논거는 GPT-3 이후 급격히 약해졌다.
학습 데이터로 만들어진 모델이 원본 사이트의 트래픽을 대체하는 구조가 성립한 뒤에는, 같은 판례를 같은 방식으로 적용하기 어렵다.
사이트는 이 변화에 대해 아무 입장도 표명하지 않는다.

### 이 데이터의 존재가 크롤 중복을 줄이지 못했다는 사실이 이 프로젝트의 전제를 반증한다

Common Crawl의 암묵적 약속은 “한 번 긁어서 모두에게 나눠주면 각자 긁을 필요가 없다”는 것이다.
15년이 지난 지금, 그 약속이 지켜졌는지는 다른 문서의 숫자가 답한다.

[내 사이트 트래픽의 99%는 봇이다](../web/99-percent-bots.md)의 HN 스레드에서 andai가 정확히 이 아이디어를 제안했다 — P2P 네트워크가 빠진 것 같다, 같은 데이터를 반복해 내려받는 대신 한 번 내려받아 공유하면 모두에게 낫지 않겠나.
NicuCalcea가 세 단어로 답했다 — Common Crawl?[^NicuCalcea]
그 답은 제안이 아니라 반증이다.
공유 코퍼스는 이미 존재하고 무료이고 널리 알려져 있는데, 그 사이트는 여전히 Amazon 크롤러에게 하루 117,000번 긁힌다.

왜 채택되지 않는지는 이 사이트의 자기 소개에서 읽을 수 있다.
크롤은 `CC-MAIN-2026-30` 같은 배치 단위로 나뉘고, 배치는 대략 한 달에 하나씩 나온다.
AI 검색 제품이 원하는 것은 지금 이 페이지이고, 한 달 전 스냅샷이 아니다.
게다가 자기 크롤러를 돌리면 무엇을 언제 어떤 깊이로 가져올지 자기가 정하지만, 남의 코퍼스를 쓰면 그 결정을 위탁해야 한다 — ricardo81이 크롤 우선순위 문제로 지적한 바로 그것이다.

그러나 가장 결정적인 이유는 다른 데 있다.
크롤링의 한계비용은 크롤러에게 거의 0이고, 그 부담은 크롤당하는 쪽이 진다.
공유 코퍼스는 크롤러의 비용을 줄여주는 해법인데, 크롤러는 애초에 비용 압박을 느끼지 않는다.
그렇다면 Common Crawl이 채택되지 않는 것은 이 프로젝트의 실패가 아니라 유인 설계의 문제다.
그리고 이 진단이 맞다면, 공유 코퍼스를 더 좋게 만드는 노력보다 직접 크롤링에 가격을 붙이는 쪽이 채택률을 훨씬 크게 움직인다.

## 인사이트

### 이 코퍼스의 장기적 가치는 웹의 내용이 아니라 웹의 접근 가능성 변화를 기록한 시계열이다

3,000억 페이지 중 대부분은 지금 다시 긁으면 얻을 수 있거나, 이미 사라져서 쓸모없거나, 스팸이다.
반면 15년 동안 같은 크롤러가 같은 방식으로 웹을 돌면서 남긴 기록에는 다른 곳에 없는 정보가 있다 — 어느 시점에 어떤 종류의 사이트가 크롤러에게 문을 닫았는가.

이 정보가 희소한 이유는 관측자가 되려면 관측을 15년간 일관되게 해야 하기 때문이다.
구글은 같은 기간의 데이터를 갖고 있지만 공개하지 않는다.
Internet Archive는 수집 목적이 달라 커버리지 패턴이 다르다.
개별 사이트 운영자는 자기 서버 로그만 본다.
Common Crawl은 유일하게 “바깥에서 웹 전체를 향해 문을 두드린 기록”을 공개된 형태로 갖고 있다.

그리고 지금 그 기록이 특히 중요해진 이유는 웹의 개방성이 빠르게 변하는 중이기 때문이다.
Cloudflare 챌린지, 작업 증명 벽, 국가 단위 차단, 로그인 담장, `robots.txt`의 AI 조항이 지난 몇 년 사이에 급격히 늘었다.
이 변화의 속도와 분포를 측정하려면 변화 이전의 기준선이 필요하고, 그 기준선을 가진 데이터셋은 사실상 이것뿐이다.
Featured Papers에 크롤 자체를 연구하는 논문 둘이 올라와 있는 것은 그 전환의 신호로 읽힌다 — 코퍼스가 웹을 연구하는 재료에서 웹의 폐쇄를 연구하는 재료로 옮겨가고 있다.

### 무료 공개 자원은 대체재가 될 때가 아니라 가격이 붙을 때 채택된다

Common Crawl의 15년은 하나의 자연 실험이다.
질문은 이것이었다 — 좋은 무료 대안을 만들어 두면 사람들이 낭비적인 중복 작업을 그만둘 것인가.
답은 아니오였다.

이 결과가 시사하는 바는 인프라 공유 프로젝트 전반에 적용된다.
공유 자원의 채택은 그 자원의 품질이 아니라 대안의 비용에 달려 있다.
자기 크롤러를 돌리는 비용이 거의 0인 동안, 코퍼스가 아무리 커도 채택률은 오르지 않는다.
같은 논리가 공용 CDN, 공용 패키지 미러, 공유 캐시 계층에 모두 적용된다 — 이들이 널리 쓰이는 경우를 보면 대개 직접 하는 쪽에 명시적 비용이나 마찰이 있었다.

그래서 Cloudflare가 준비 중인 요청당 과금이 실제로 도입된다면, 그 가장 큰 효과는 크롤러가 사이트에 지불하는 돈이 아닐 수 있다.
15년째 아무도 진지하게 쓰지 않던 무료 공유 코퍼스가 갑자기 합리적인 선택이 되는 것이다.
가격은 새 대안을 만들지 않는다 — 이미 있던 대안을 보이게 만든다.

여기에는 뒤따르는 위험도 있다.
채택이 급증하면 Common Crawl의 인프라 비용도 함께 오르고, 그 비용은 기부에 의존한다.
duskwuff가 지적한 수십에서 수백 페타바이트를, AWS의 기부에 기대어 무료로 서빙하는 구조는 수요가 지금 수준일 때 성립한다.
공유 코퍼스가 정말로 대안이 되는 순간, 이 조직은 자기가 해결하려던 문제 — 무료로 데이터를 제공하는 쪽이 비용을 다 낸다 — 를 자기 스스로 겪게 된다.

### 크롤러의 정직함이 처벌받는 균형은 오래가지 못한다

현재 웹의 봇 방어 구조에는 뒤집힌 유인이 있다.
CCBot은 자기를 밝히고, IP 대역을 공개하고, `robots.txt`를 지키고, 역방향 DNS로 검증 가능하게 만든다.
그 결과 CCBot은 차단하기 가장 쉬운 크롤러가 된다.
반면 자바스크립트를 실행하고 주거용 IP에서 최신 브라우저를 사칭하는 크롤러는 어떤 방어도 통과한다.

이 구조가 유지되면 결론은 하나다 — 정직한 크롤링이 소멸한다.
Common Crawl, Internet Archive, 학술 크롤러, 소규모 검색 엔진 신규 진입자가 모두 같은 위치에 있고, 모두 같은 이유로 먼저 차단된다.
방어자가 잘못한 것이 아니다.
그들에게는 정직한 크롤러를 구분해 통과시킬 저렴한 수단이 없고, 있다 해도 그 수단이 사칭당한다.
Anubis 문서가 “알려진 좋은 봇의 큐레이션 목록을 준비 중”이라고 적어둔 것이 그 어려움의 표현이다.

그런데 이 균형에는 자기 파괴적 성질이 있다.
정직한 크롤러가 사라지면 남는 것은 사칭하는 크롤러뿐이고, 그러면 방어자는 더 이상 “정직한 쪽을 통과시킨다”는 정책을 쓸 수 없게 된다.
동시에 웹의 공개 기록 — 아카이브, 공개 코퍼스, 학술 데이터셋 — 이 함께 끊긴다.
그 손실은 개별 사이트 운영자의 손익 계산에는 나타나지 않고, 10년 뒤에 “2020년대 중반 이후의 웹이 잘 보존되지 않았다”는 형태로만 드러난다.

여기서 실질적으로 필요한 것은 도구가 아니라 표준이다.
CCBot의 역방향 DNS 검증 방식은 Googlebot이 오래전에 확립한 관행을 그대로 따른 것이고, 이 방식은 실제로 작동한다 — 다만 각 크롤러가 개별적으로 문서화하고 각 운영자가 개별적으로 구현해야 한다.
검증 가능한 크롤러 신원을 표현하는 공통 형식과, 그것을 방어 도구가 기본으로 소비하는 관행이 없다.
Common Crawl이 `ccbot.json`을 공개하는 것은 그 방향의 최소 단위이고, 그것이 하나의 조직에 그치는 한 문제는 해결되지 않는다.
재단의 최신 블로그 글이 HTTP Workshop과 IETF 회의 참석기이며 “기계 판독 가능(machine readable)”이 실제로 무엇을 뜻하는지 정의하려는 시도를 다룬다는 사실은, 이 조직이 그 표준화 지점을 자기 역할로 인식하기 시작했다는 신호로 읽힌다.

### 39번째 게시가 397점을 받는 현상은 지식의 재발견 비용을 보여준다

작은 관찰이지만 일반화할 만한 것이 있다.
kristopolous가 이것이 사람들에게 새롭다는 사실에 놀랐다며, 10년 된 프로젝트인데 HN에서 처음 이야기되는 것이냐고 물었다[^kristopolous].
TechBro8615가 답했다 — 제출 옆의 도메인을 클릭해 보면 알 수 있듯 39번째다[^TechBro8615].
lovelearning은 그것이 문제가 아니라고 봤다 — 매번 누군가에게는 새로운데, 업계에 새로 들어오는 사람, HN에 가입하는 사람, 새로운 관심사가 생기는 사람이 매일 있기 때문이며 그래서 재게시나 오래된 콘텐츠를 개인적으로 개의치 않는다는 것이다[^lovelearning].

이 교환이 흥미로운 이유는 Common Crawl이 겪는 채택 문제와 같은 구조이기 때문이다.
15년째 존재하고, 39번 소개되었고, 논문 10,000편에 인용되었는데도, 크롤을 직접 돌리려는 사람이 “이미 있는 코퍼스”를 먼저 떠올리지 않는다.
정보가 부족해서가 아니라, 문제에 부딪힌 순간에 그 정보가 떠오르지 않기 때문이다.

여기서 나오는 실무적 함의는 공개 인프라의 홍보 전략에 관한 것이다.
존재를 알리는 것과 필요한 순간에 떠오르게 만드는 것은 다른 작업이고, 후자는 반복 노출로만 달성된다.
39번의 게시가 39번 새로운 사람에게 닿았다는 lovelearning의 관찰이 정확하다면, 공개 자원의 홍보에서 중복은 낭비가 아니라 필수 비용이다.
그리고 이것이 무료 공개 프로젝트가 구조적으로 불리한 또 하나의 지점이다 — 반복 노출에 예산을 쓸 주체가 없다.
