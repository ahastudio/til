# Luna Chat Coder: 채팅 샌드박스를 개발 환경으로 되돌려 쓴다

> Agent Skill and repository template for reliable software development
> from constrained chat AI environments.

<https://github.com/Osteoporosis/luna-chat-coder>

GN 토론: <https://news.hada.io/topic?id=32606>

## 소개

Luna Chat Coder는 저장소 템플릿이다.
평범한 채팅에서 신뢰할 만한 소프트웨어 개발을 하기 위한 폴백 스킬을 저장소 안에 심어 두었다.

일회성 설정을 마치면 사용자 경험은 단순하다 — ChatGPT에게 저장소와 개발 과업을 주면 된다.
Luna는 저장소에서 발견되고, 평상시 작업에는 채팅 샌드박스를 쓰며, 그 경로로 부족할 때만 GitHub
Actions에 손을 뻗는다.

만든 사람이 GeekNews에 밝힌 배경이 이 프로젝트의 성격을 잘 설명한다.
ChatGPT 웹 채팅은 Codex 한도와 별개로 쓸 수 있고, 최근 변경 이후 무료 사용자에게도 넉넉한 채팅
사용량이 주어진다.
웹 채팅에는 간단한 코드를 실행할 수 있는 작업 컨테이너가 들어 있는데, 인터넷과 단절되어 있어서
지금까지는 실용적으로 쓰기 어려웠다는 것이다.

## 설정 절차

검증된 ChatGPT 웹 경로는 네 단계다.

1. 템플릿 저장소에서 **Use this template → Create a new repository**로 새 저장소를 만든다.
2. ChatGPT의 Plugins Directory에서 **GitHub Plugin**을 설치하고 GitHub 계정을 연결한다.
3. GitHub에서 **ChatGPT Codex Connector**를 설치하고 새 저장소에 접근 권한을 준다.
   이미 Selected repositories only로 설치되어 있다면 새 저장소를 access 목록에 추가한다.
4. 일반 ChatGPT 대화에서 저장소 URL과 원하는 개발 작업을 알려 준다.

Luna Chat Coder를 언급할 필요는 없다 — 저장소의 `AGENTS.md`가 모델을 내장 스킬로 안내한다.
GeekNews 글은 3번이 무료 사용자에게 특히 누락되기 쉬우니 꼭 확인하라고 강조한다.

## Luna가 자동으로 하는 일

README는 모델이 저장소 작업에서 조용히 수행해야 할 아홉 단계를 열거한다.

`AGENTS.md`와 내장 `SKILL.md`를 읽고, 정확한 저장소/PR/커밋 상태를 확인하며 살아남은 샌드박스
작업을 점검한다.
목표 커밋이나 PR head 소스를 완전한 샌드박스 작업 트리로 구성하고 편집 전에 기준 신원을 검증한다.
무언가를 설치하거나 획득하기 전에 샌드박스에 이미 무엇이 있는지 먼저 조사한다.
일반적인 편집·빌드·테스트·디버그는 샌드박스 작업 컨테이너에서 수행한다.
Actions 미션은 실제 능력·전송·실행의 공백이 있을 때만 쓴다.
저장소와 과업이 요구하는 검사로 실행 가능한 동작을 검증한다.
검증된 변경을 가장 단순하고 신뢰할 만한 GitHub 경로로 발행한다.
그리고 실제로 실행된 것만 보고하며, 원격 실행이 불가피했을 때는 그 사실을 밝힌다.

README는 이 목록에 조건 하나를 붙인다 — 정상적인 과업이라면 사용자가 Luna를 조작하거나 그 내부
체크리스트를 지켜보게 만들어서는 안 된다.

## Actions 미션을 쓰는 세 가지 경우

GitHub Actions는 기본 개발 환경이 아니라 폴백 실행 경계라고 규정한다.
미션이 유용한 이유는 셋으로 나뉜다.

| 이유          | 상황                                                                 |
| ------------- | -------------------------------------------------------------------- |
| Supply        | 샌드박스가 작업은 할 수 있으나 의존성·런타임·SDK·컴파일러 등을 못 구함 |
| Exact transport | 결정적 패치나 번들이 반복적인 GitHub 쓰기보다 안전하거나 효율적일 때 |
| Degraded remote execution | 샌드박스 자체가 없거나 사용량·시간·자원 한계로 과업을 못 버틸 때 |

README는 패치 전송이 최후의 벌칙이 아니라 선택지라고 분명히 한다.
파일 조작, 네이티브 Git 오브젝트 조작, 정확한 패치·번들 미션은 서로 대안적인 발행 메커니즘이며,
Luna는 관측된 변경에 대해 정확하고 신뢰할 만하면서 가장 부담이 적은 것을 고른다.

실패 처리 규칙도 명시되어 있다.
API나 Actions 실패는 재시도 전에 진단해야 하며, 반환된 오류와 실패 단계와 로그와 부분 결과를 살핀
뒤에 소스를 고치거나 재실행해야 한다.
변경 없는 재시도는 일시적 실패라는 증거가 있을 때만 적절하고, 반복적인 맹목적 재시도는 명시적으로
권장하지 않는다고 적었다.

## 왜 이 프로젝트가 존재하는가

README의 “Why Luna exists” 절이 설계 전제를 열거한다.

샌드박스는 초기화되거나 사라질 수 있다.
네트워크, 스토리지, 자원, 시간, 사용량 한계가 필요한 작업을 막을 수 있다.
저장소가 처음에는 없는 도구나 외부 입력을 요구할 수 있다.
대화 텍스트는 의도를 잘 보존하지만 정확한 바이트의 출처로는 형편없다.
그리고 GitHub Actions는 원격의 계량된 실행이며 워크플로와 기동과 아티팩트와 정리에 부담이 따른다.

그래서 정책은 **샌드박스 우선, 실제 공백이 있을 때만 원격**이다.
더 획득하기 전에 이미 있는 것을 조사하라는 것이다.

## 분석

### 제약을 우회하지 않고 제약 안에서 뒤집었다

GeekNews 댓글에서 만든 사람이 직접 설명한 사고 과정이 이 프로젝트의 핵심이다.

ouroboros가 Ngrok을 활용해도 꽤 괜찮다며 나중에는 자기 도메인을 경유해 쓰고 있다고
했다[^ouroboros].
osteoporosis의 답이 방향의 차이를 분명히 한다 — Ngrok도 터널이고 사용자가 제공하는 서버나 로컬
컴퓨터에 연결하기 위해 필요한 것인데, luna-chat-coder가 문제를 푼 방식은 정반대라는
것이다[^osteoporosis].

그가 밝힌 사고의 순서는 이렇다.
“웹 채팅 모델에게 개발용 컴퓨터를 제공해야겠다 → 터널까지 제공해야 된다”가 아니라, “터널조차
설치하기 귀찮다/어렵다 → 채팅 모델에게 외부 환경을 제공할 게 아니라 처음부터 모델에 내장된 코드 실행
환경을 개발용으로 써 보자 → 그런데 인터넷도 끊어 놨다, pip/npm으로 패키지조차 못 받아온다 → GitHub
플러그인으로 우회하자”였다.
결과적으로 사용자가 개발용 컴퓨터를 제공할 필요조차 없어졌고, 약점과 한계를 장점으로 뒤집은 셈이
되어 뿌듯하다고 했다.

이 설명이 기존 접근과의 차이를 정확히 짚는다.
MCP 기반 방식은 모델을 사용자 환경으로 데려오려 하고, 그래서 노출과 터널이라는 인프라 문제를 낳는다.
Luna는 모델이 이미 있는 환경 안에서 필요한 것을 조달하려 하고, 그래서 인프라가 필요 없다.

### 인터넷이 끊긴 컨테이너에서 GitHub 플러그인이 유일한 통로가 된다

샌드박스가 네트워크에서 격리되어 있다는 것은 `pip install`도 `npm install`도 되지 않는다는 뜻이다.
보통은 여기서 끝난다.

Luna의 우회는 GitHub 플러그인이 모델의 다른 능력으로 존재한다는 사실을 이용한다.
샌드박스는 인터넷에 못 나가지만 모델은 플러그인을 통해 GitHub과 통신할 수 있고, 그러면 저장소가
사실상 파일 전송 채널이 된다.
의존성이 필요하면 Actions에서 만들어 저장소로 보내고, 샌드박스는 모델을 거쳐 그것을 받는다.

이 구조에서 GitHub Actions가 맡는 역할이 흥미롭다.
CI가 아니라 **네트워크 프록시이자 빌드 팜**이다.
README가 Supply를 미션의 첫 번째 이유로 든 것이 정확히 이 용도를 가리킨다 — 샌드박스가 엔지니어링
작업은 할 수 있는데 필요한 외부 입력을 못 구할 때.

### 대화 텍스트를 바이트 전송에 쓰지 말라는 원칙이 설계를 지배한다

README의 전제 목록에서 가장 실무적인 문장은 이것이다 — 대화 텍스트는 의도를 잘 보존하지만 정확한
바이트의 출처로는 형편없다.

이 한 줄에서 여러 규칙이 파생된다.
편집 전에 목표 커밋이나 PR head를 완전한 작업 트리로 구성하고 기준 신원을 검증하라는 것, 결정적
패치나 번들을 반복적인 GitHub 쓰기보다 선호할 수 있다는 것, 바이너리나 모드 민감 변경에서는
특히 그렇다는 것.

채팅 기반 코딩의 실패는 대개 여기서 난다.
모델이 파일 내용을 대화에 옮겨 적고 다시 옮겨 쓰는 과정에서 공백과 인코딩과 잘림이 발생하며, 그
손실은 조용히 일어난다.
Luna는 그 경로를 명시적으로 차단하고 Git 오브젝트 조작이나 패치 전송으로 밀어낸다.

## 비평

### 이 우회가 얼마나 오래 유효할지에 대한 언급이 없다

이 프로젝트의 전제는 두 가지 정책적 사실이다.
ChatGPT 웹 채팅의 사용량이 Codex 한도와 별개라는 것, 그리고 웹 채팅에 코드 실행 컨테이너가 딸려
있다는 것이다.

둘 다 OpenAI가 언제든 바꿀 수 있다.
그리고 이 도구의 존재 이유가 “Codex 한도 차감 없이”라는 점을 감안하면, 사용량 회계의 구멍을
활용하는 성격이 있다.
구멍은 대개 메워진다.

README도 GeekNews 글도 이 위험을 다루지 않는다.
사용자 입장에서는 저장소 템플릿을 만들고 플러그인 두 개를 설치하고 커넥터 권한을 설정하는 초기
비용을 치르는데, 그 투자가 정책 변경 한 번에 무효가 될 수 있다는 정보가 필요하다.

그리고 이 위험은 스킬 자체의 설계로 완화할 수 있는 종류다.
Actions 폴백 경로가 이미 있으므로, 샌드박스가 사라진 환경에서 Actions만으로 동작하는 모드가 문서화
되어 있다면 정책 변경에 대한 대비가 된다.
README는 “degraded remote execution”을 미션 사유로 열거하지만 그것이 전면화된 경우의 사용 경험을
설명하지는 않는다.

### 아홉 단계 체크리스트를 모델이 지킬 것이라는 보장이 없다

“모델이 조용히 수행해야 하는” 아홉 단계와 미션 판단 규칙과 실패 진단 규칙은 잘 짜여 있다.
그런데 이것들은 전부 프롬프트다.

에이전트 스킬의 근본 문제가 여기 있다.
지시를 아무리 정교하게 써도 그것은 강제가 아니라 권유이고, 모델은 맥락이 길어지거나 과업이 어려워지면
지시를 흘린다.
특히 “먼저 조사하고 나서 획득하라”, “재시도 전에 진단하라” 같은 절제 규칙은 모델이 가장 잘 어기는
종류다 — 무언가를 시도하는 것이 아무것도 안 하는 것보다 늘 그럴듯해 보이기 때문이다.

README는 “정상적인 과업이라면 사용자가 내부 체크리스트를 지켜보게 만들어서는 안 된다”고 적는데,
이것은 목표 진술이지 보장이 아니다.
지켜보지 않으면 지켜졌는지 알 수 없고, 지켜졌는지 알 수 없으면 결과를 신뢰할 근거가 없다.

검증 가능한 형태로 바꿀 여지가 있다.
“실제로 실행된 것만 보고하라”는 아홉 번째 규칙은 특히 그렇다 — Actions 실행 기록과 커밋 이력이라는
객관적 흔적이 남으므로, 보고와 대조할 수 있다.
스킬이 그 대조를 스스로 하도록 만들면 자기 보고의 신뢰도를 사용자가 확인할 수 있게 된다.

### 무엇이 검증됐는지의 경계가 흐리다

README는 “the validated ChatGPT Web workflow”라는 표현을 쓴다.
그런데 무엇이 어떻게 검증됐는지는 나오지 않는다.

버전은 0.1.1이고, 저장소 템플릿과 스킬 문서와 참조 문서로 이루어져 있다.
이 구성에서 자연스럽게 나오는 질문들이 있다 — 어떤 규모의 저장소까지 샌드박스에서 다뤄 봤는가,
어떤 언어와 빌드 시스템에서 성공했는가, 샌드박스 초기화가 작업 중간에 일어났을 때 실제로 복구되는가.

이 질문들에 답이 없으면 사용자가 자기 저장소에 적용해 보기 전까지 적합성을 판단할 수 없다.
그리고 초기 설정 비용이 네 단계에 걸쳐 있으므로 시험 삼아 해 보는 비용도 낮지 않다.

## 인사이트

### 모델 안에 있는 실행 환경이 새로운 컴퓨팅 자원이 되고 있다

지금까지 코딩 에이전트의 실행 환경은 두 곳이었다 — 사용자의 로컬 머신이거나, 서비스 제공자가
운영하는 전용 클라우드 샌드박스거나.
전자는 CLI 도구의 방식이고 후자는 Codex나 클라우드 에이전트의 방식이다.

Luna는 세 번째 자리를 발견했다.
채팅 인터페이스에 딸린 코드 인터프리터 컨테이너다.
그것은 데이터 분석을 위해 제공된 것이고 개발 환경으로 의도되지 않았지만, 파일 시스템과 프로세스
실행이 있다는 점에서는 다르지 않다.

이 발견의 일반적 함의가 있다.
LLM 제품에 딸려 나오는 부수 기능들 — 코드 인터프리터, 파일 업로드, 커넥터, 플러그인 — 이 각각
컴퓨팅 자원이고, 그것들을 조합하면 제품이 의도하지 않은 능력이 만들어진다.
그리고 그 조합의 가치는 제품 가격 정책과 어긋난다.
전용 에이전트 제품에는 사용량 한도가 붙지만 채팅에는 그보다 관대한 한도가 붙는데, 두 곳의 근본
능력 차이는 점점 좁아지고 있다.

그러므로 이런 조합은 계속 나타날 것이고 계속 막힐 것이다.
막는 쪽의 수단은 기술이 아니라 약관과 회계일 가능성이 높다.

### 인터넷 격리는 보안 장치이면서 능력 제한이고, 둘을 분리할 방법이 없다

채팅 샌드박스가 인터넷과 끊겨 있는 이유는 명확하다 — 임의 코드 실행 환경이 외부와 통신할 수 있으면
데이터 유출과 남용의 경로가 된다.

그런데 그 격리가 정확히 개발 용도를 막는다.
패키지를 받을 수 없는 실행 환경에서는 거의 모든 실제 소프트웨어를 빌드할 수 없다.
그래서 이 격리는 보안 조치이면서 동시에 제품 구획의 도구가 된다 — 진지한 개발을 하려면 별도로
과금되는 제품을 쓰라는 것이다.

Luna의 우회는 이 이중 목적을 드러낸다.
GitHub 플러그인을 통한 조달이 가능하다는 것은, 격리가 데이터 유출을 완전히 막지는 못한다는 뜻이기도
하다 — 저장소를 경유하는 통로가 열려 있다면 그 통로로 나갈 수 있는 것도 있다.
보안 경계로서는 이미 새고 있고, 제품 경계로서만 온전히 기능하는 셈이다.

이 관찰은 샌드박스 설계 일반에 적용된다.
격리를 네트워크 계층에서만 걸고 모델의 도구 호출 계층은 그대로 두면, 모델 자체가 프록시가 된다.
진짜 격리를 원한다면 모델이 쓸 수 있는 모든 채널을 함께 봐야 하고, 그것은 유용성을 크게 해친다.

### 제약이 명시된 환경이 오히려 좋은 에이전트 설계를 강제한다

Luna의 규칙들 — 획득 전에 조사하라, 재시도 전에 진단하라, 대화로 바이트를 옮기지 말라, 원격 실행은
실제 공백이 있을 때만 — 은 사실 채팅 샌드박스에만 해당하는 규칙이 아니다.
로컬 CLI 에이전트에도 그대로 좋은 규칙이다.

그런데 로컬 환경에서는 이런 규칙이 잘 지켜지지 않는다.
디스크가 넉넉하고 네트워크가 열려 있으니 조사보다 설치가 빠르고, 재시도가 싸니 진단보다 재실행이
쉽다.
자원이 풍족하면 낭비의 대가가 보이지 않는다.

샌드박스의 빈약함이 그 대가를 즉시 드러낸다.
사용량 한도, 세션 소멸, 네트워크 부재가 각각 규율로 작용하고, 그 규율 아래에서 짜인 절차가 결과적으로
더 나은 절차가 된다.
[에이전트에게 자율을 어디까지 줄 것인가](../agentic-coding/mini-dev-agent.md)라는 문제에서 보통
논의되는 것은 안전장치와 승인 게이트인데, 이 사례는 다른 답을 시사한다 — 환경 자체를 좁히면
에이전트가 스스로 절제하게 만들 필요가 줄어든다.

역으로 이것은 풍족한 환경에서 에이전트를 돌릴 때 무엇을 인위적으로 만들어야 하는지도 알려 준다.
설치 전 인벤토리 확인, 실패 진단 강제, 전송 방식의 명시적 선택 — 샌드박스가 물리적으로 강제하는
것들을 정책으로 세워야 같은 품질이 나온다.
