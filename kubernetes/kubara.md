# kubara - 모범 사례 기반으로 Kubernetes 플랫폼을 부트스트랩하는 CLI

> kubara — Your Framework for Efficient Platform Engineering

<https://kubara.io/>

<https://github.com/kubara-io/kubara>

## 소개

kubara는 GitOps 우선 워크플로우를 통해 Kubernetes 플랫폼을 부트스트랩하고
운영하기 위한 Go 기반 단일 바이너리 CLI 도구입니다. 플랫폼 스캐폴딩, 환경
설정, 프로덕션 수준의 기본값을 하나의 도구 안에 통합해서 제공하는 것을
목표로 합니다.

프로젝트가 내세우는 핵심 가치는 다음 네 가지입니다.

- 플랫폼 설정과 생명주기 관리를 위한 통합 CLI
- 반복 가능한 배포를 위한 GitOps 기반 구조
- 다중 클러스터 및 다중 테넌트 환경 지원
- Terraform과 Helm 컴포넌트를 통한 확장 가능성

## 아키텍처

kubara는 OCI 카탈로그에서 부트스트래핑 기초(bootstrap foundations)와 플랫폼
스택을 불러오는 구조를 취합니다. 카탈로그 소스와 버전 관리는 별도
저장소인 kubara-io/catalogs에서 이루어지며, 사용자는 클러스터별 카탈로그
설정과 커스텀 카탈로그를 구성할 수 있습니다. 즉 kubara 자체는 실행기
역할을 하고, 실제 배포 대상이 되는 매니페스트와 정책은 카탈로그
저장소에서 버전 관리되는 분리된 구조입니다.

## CLI

주요 명령어는 다음과 같습니다.

| 명령어 | 기능 |
|-----------|------------------------------------------|
| `init` | 새 kubara 디렉토리 초기화 |
| `generate` | 구성된 카탈로그 템플릿으로 Helm/Terraform 아티팩트 생성 |
| `bootstrap` | 필수 CRD와 Argo CD를 대상 클러스터에 배포 |
| `schema` | 설정 구조의 JSON 스키마 파일 생성 |
| `agents` | AI 코딩 어시스턴트용 온보딩 파일 스캐폴딩 |
| `catalog` | 플랫폼 카탈로그 관리 |
| `cluster` | kubara 클러스터 설정 관리 |

전역 옵션으로는 설정 파일 경로(`--config-file`), kubeconfig 위치
(`--kubeconfig`), 작업 디렉토리(`--work-dir`)를 지정할 수 있고, Base64
인코딩/디코딩(`--base64`, `--encode`, `--decode`)과 클러스터 연결 테스트
(`--test-connection`) 기능도 포함되어 있습니다. 도구는 실행할 때마다 새
GitHub 릴리스를 확인하며, `KUBARA_UPDATE_CHECK=0` 환경 변수로 비활성화하거나
`--check-update`로 수동 확인할 수 있습니다.

## 사용법

설치는 Linux, macOS, Windows용 안내가 INSTALLATION.md에 별도로 정리되어
있습니다. 일반적인 흐름은 `init`으로 kubara 디렉토리를 초기화한 뒤,
`catalog`와 `cluster` 명령으로 사용할 카탈로그와 클러스터 설정을 구성하고,
`generate`로 Helm/Terraform 아티팩트를 뽑아낸 다음, `bootstrap`으로 대상
클러스터에 Argo CD와 전제조건 CRD를 배포하는 방식입니다. 이후 GitOps
루프(Argo CD가 Git 저장소 상태를 클러스터에 지속적으로 동기화)로 운영이
넘어갑니다.

소스 코드는 Apache 2.0, 문서는 CC BY 4.0으로 이중 라이선싱되어 있으며,
Kubernetes Slack의 #kubara 채널과 GitHub Issues/Discussions를 통해 커뮤니티
지원을 받을 수 있습니다.

## 분석

### “부트스트랩 도구”라는 카테고리가 노리는 빈틈

Kubernetes 생태계에는 이미 Helm, Kustomize, Argo CD, Flux, Terraform,
Crossplane 등 각 계층을 담당하는 도구가 존재합니다. kubara는 이 도구들을
대체하는 것이 아니라, “새 클러스터를 처음 부트스트랩할 때 이 도구들을 어떤
순서와 구조로 조합할 것인가”라는, 개별 도구가 답하지 않는 질문을 겨냥합니다.
`bootstrap` 명령이 Argo CD와 전제조건 CRD를 미리 정해진 방식으로 깔아주는
것 자체가 이 도구의 정체성입니다. 즉 kubara는 실행 엔진이 아니라 “의견이
담긴 초기 배선(opinionated initial wiring)”을 파는 도구에 가깝습니다.

### 카탈로그를 코드와 분리한 설계의 함의

부트스트랩 로직을 바이너리에 내장하지 않고 OCI 카탈로그(kubara-io/catalogs)
로 외부화한 것은 의도적인 선택으로 보입니다. 이렇게 하면 CLI 자체의
릴리스 주기와 “모범 사례”의 갱신 주기를 분리할 수 있고, 조직이 자체
카탈로그를 만들어 공식 모범 사례를 커스터마이즈할 여지도 생깁니다. 반대로
말하면 kubara CLI만 봐서는 실제로 무엇이 배포되는지 알 수 없고, 카탈로그
저장소의 내용과 버전이 실질적인 신뢰의 단위가 됩니다. CLI는 얇은
오케스트레이터이고, 무게중심은 카탈로그 쪽에 있습니다.

### AI 에이전트 온보딩을 1급 명령으로 넣은 시점

`agents` 명령이 “AI 코딩 어시스턴트용 온보딩 파일 스캐폴딩”을 전용 명령으로
제공한다는 점은, 이 프로젝트가 2025~2026년 시점에 만들어졌다는 사실을
드러냅니다. 몇 년 전이었다면 이런 기능은 존재하지 않았을 자리입니다.
인프라 부트스트랩 도구가 “이 저장소 구조를 AI 에이전트에게 어떻게
설명할 것인가”까지 초기 설계 범위에 넣었다는 것은, 플랫폼 엔지니어링
도구의 대상 사용자가 더 이상 사람만이 아니라는 인식이 이미 도구
설계 단계에 반영되고 있음을 보여줍니다.

## 비평

### “모범 사례”라는 단어가 검증 없이 소비된다

README와 소개 문구는 “모범 사례 기반”이라는 표현을 반복하지만, 그 모범
사례가 무엇을 근거로 정해졌는지, 누가 유지보수하는지, 얼마나 자주
갱신되는지에 대한 설명은 CLI 저장소 자체에는 없습니다. 실제 판단 근거는
별도 저장소인 catalogs에 있고, kubara 저장소만 읽는 사용자는 “모범
사례”라는 말을 검증 없이 받아들이게 됩니다. 이는 도구의 신뢰성 문제라기보다
문서 구조의 문제지만, 결과적으로 사용자가 실제로 무엇을 신뢰하고 있는지
불투명하게 만듭니다.

### 다중 테넌트 지원의 구체성이 부족하다

“다중 클러스터/다중 테넌트 환경 지원”은 핵심 가치 제안 중 하나로
제시되지만, 무엇이 테넌트 격리의 단위인지(네임스페이스인지, 별도
클러스터인지, RBAC 정책인지), 어떤 실패 모드를 방지하도록 설계됐는지는
드러나지 않습니다. 멀티테넌시는 Kubernetes 플랫폼 설계에서 가장 어려운
축 중 하나이며, 이를 한 줄짜리 특징으로 나열하는 것은 실제 구현의
난이도를 가리는 결과를 낳습니다.

### Argo CD로의 종속을 선택이 아닌 전제로 삼는다

`bootstrap` 명령은 Argo CD 배포를 전제로 하고 있어, 이미 Flux나 다른
GitOps 컨트롤러를 채택한 조직에는 처음부터 선택지가 좁습니다. GitOps
“우선”이라는 표현이 실제로는 “Argo CD 우선”을 의미한다는 점은 도구
이름이나 소개 문구만으로는 드러나지 않고, CLI 명령의 동작을 살펴봐야
비로소 알 수 있는 사실입니다. 이런 종류의 암묵적 결합은 초기 채택
단계에서는 눈에 띄지 않다가, 나중에 GitOps 컨트롤러를 바꾸려 할 때
비로소 비용으로 드러납니다.

## 인사이트

### 부트스트랩 도구는 결국 조직의 정치적 합의를 코드로 굳힌다

kubara 같은 도구가 실제로 하는 일은 기술적 자동화보다는, “우리 조직에서
클러스터는 이렇게 시작한다”는 합의를 코드로 고정하는 작업에 가깝습니다.
카탈로그를 버전 관리 가능한 별도 저장소로 분리한 설계는 이 정치적 합의가
시간에 따라 바뀔 수 있다는 것을 전제하고 있으며, 이는 조직이 성장하면서
“표준”이 계속 재협상된다는 현실을 반영한 구조입니다. 이 도구를 도입한다는
것은 기술 스택을 고르는 결정이 아니라, 누가 카탈로그를 편집할 권한을
갖는가라는 거버넌스 결정을 함께 내리는 일입니다.

### CLI가 얇아질수록 신뢰의 무게중심이 저장소 밖으로 이동한다

kubara CLI 자체는 카탈로그를 가져와 실행하는 얇은 오케스트레이터이기
때문에, 이 도구의 보안성과 신뢰성을 평가하려면 kubara 저장소가 아니라
kubara-io/catalogs와 사용자가 지정하는 커스텀 카탈로그의 공급망을 감사해야
합니다. 이는 최근 여러 “선언적 구성 기반” 도구들(Terraform 모듈 레지스트리,
Helm 차트 저장소, OCI 아티팩트 생태계)에서 반복되는 패턴으로, 실행기의
코드 감사만으로는 실제 공격 표면을 다 덮지 못한다는 구조적 함정을
공유합니다. 도입 검토 시 “카탈로그 서명 검증이 있는가”, “카탈로그 변경
이력을 누가 감사하는가”가 CLI 자체의 코드 품질보다 더 중요한 질문이 될 수
있습니다.

### AI 에이전트 온보딩 명령은 향후 플랫폼 도구의 표준 인터페이스를 예고한다

`agents` 명령이 존재한다는 사실은 사소해 보이지만, 앞으로 플랫폼
엔지니어링 도구들이 “사람이 읽는 문서”와 “AI 에이전트가 읽는 온보딩
컨텍스트”를 별도의 1급 산출물로 관리하게 될 가능성을 시사합니다.
Kubernetes 클러스터 구조, 카탈로그 스키마, RBAC 경계 같은 정보를 AI
에이전트가 정확히 이해하지 못하면 자동화된 인프라 변경 제안 자체가
위험해지므로, 이런 온보딩 파일은 문서화 편의 기능이 아니라 향후 AI 기반
운영(AIOps, 자동 PR 생성 등)의 안전장치로 진화할 가능성이 높습니다.
