# find은 이제 대체로 필요 없다

원문: [You probably don't need find](https://will-keleher.com/posts/you-probably-dont-need-find/)

## 소개

Will Keleher가 `find` 대신 셸 글로빙과 `fd`를 쓰라고 권하는 짧은 글이다.
출발점은 가장 단순한 사용례다.
특정 확장자의 파일을 전부 찾는 `find . -name '*.md'`인데,
이 단순한 검색조차 걸리는 곳이 너무 많다는 것이다.

## find의 거친 모서리들

| 시도                   | 결과                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `find . --name '*.md'` | `find`는 다른 셸 도구와 달리 짧은 옵션에 `-`를 쓰지 않아서 오류가 난다                                                    |
| `find . -name *.md`    | 따옴표가 없으면 셸이 `*.md`를 먼저 확장해 버린다                                                                          |
| `find -name '*.md' .`  | 디렉터리가 필터보다 앞에 와야 한다고 알려 주는 대신 알아보기 힘든 오류를 낸다                                             |
| `find . -name '*.md'`  | 검색할 디렉터리를 반드시 지정해야 하며, 셸에 익숙하지 않은 사람에게 `.`이 현재 디렉터리라는 사실이 곧바로 분명하지는 않다 |
| 위 전부                | 숨김 파일과 `.gitignore`에 걸린 파일까지 전부 뒤진다                                                                      |

이 목록의 성격을 정확히 하려면 하나를 덧붙여야 한다.
저자가 인용한 오류 메시지는 구현에 따라 달라진다.
이 글을 정리하며 맥에서 확인해 보니 `find`가 `bfs`로 연결되어 있었고,
그 구현은 필터를 경로보다 앞에 두어도 정상적으로 동작했다.

```text
$ find -name '*.md' .
./a.md
./sub/b.md
```

즉 필터 순서 문제는 BSD 계열 `find`의 동작이며 모든 구현에서 같지 않다.
그러나 이 사실은 저자의 논지를 약화시키지 않고 오히려 강화한다.
같은 명령이 기계마다 다르게 동작한다는 것이 `find`를 쓰기 어렵게 만드는 이유 중 하나이기 때문이다.

## 글로빙

zsh에서는 `**/*.md`로 패턴에 맞는 파일을 재귀적으로 찾을 수 있다.
`README.md`, `posts/my_post.md`, `a/b/c.md`가 모두 걸린다.
저자는 `echo **/*.md`가 그 `find` 명령보다 읽고 쓰기 훨씬 쉽다고 적는다.

Bash도 재귀 글로빙을 지원한다.
`shopt -s globstar`로 `**` 패턴 매칭을 켜야 하며,
`~/.bashrc`에 넣어 두어도 안전하다.
켜고 나면 zsh의 글로빙과 똑같이 동작한다.

다만 맥에서는 주의가 필요하다.
많은 맥의 기본 Bash가 2006년에 나온 3.2이고 `globstar`를 지원하지 않는다.
실제로 확인해 보면 이렇다.

```text
$ /bin/bash --version | head -1
GNU bash, version 3.2.57(1)-release (arm64-apple-darwin25)

$ /bin/bash -c 'shopt -s globstar'
/bin/bash: line 0: shopt: globstar: invalid shell option name
```

2025년에 출시된 macOS에서도 `/bin/bash`는 여전히 3.2이다.
라이선스 문제로 애플이 Bash를 GPLv2 시절 버전에 묶어 두었기 때문이며,
기본 셸이 zsh로 바뀐 뒤에도 이 상태는 그대로다.
스크립트의 셔뱅에 `#!/bin/bash`를 쓰면서 `globstar`를 기대하면 맥에서 조용히 실패한다.

## fd

글로빙은 잘 동작하지만 모든 파일을 뒤지고, 추가 필터를 지정할 수 없다.
`node_modules`나 `lib`은 뒤지고 싶지 않을 수 있다.

`fd`는 ripgrep과 비슷한 계열의 도구이고,
합리적인 기본값을 가지며 `.gitignore`를 존중한다.
`fd -e md`가 `find . -name '*.md'`보다 훨씬 간단하다.
수정 날짜로 파일을 찾는 것처럼 `find`의 복잡한 옵션들도 상당수 지원한다.

| 하고 싶은 일   | find                  | fd                       |
| -------------- | --------------------- | ------------------------ |
| 확장자로 찾기  | `find . -name '*.md'` | `fd -e md`               |
| 기본 제외      | 없음                  | `.gitignore`와 숨김 파일 |
| 숨김 파일 포함 | 기본 동작             | `--hidden` 필요          |

`fd`와 `rg`의 유일한 함정이 바로 그 기본값이다.
`.`으로 시작하는 숨김 파일과 디렉터리를 `--hidden` 없이는 무시한다.
저자가 겪은 사례가 구체적이다.
GitHub Action은 `.github/actions` 디렉터리에 저장되는데,
존재를 아는 액션을 왜 찾지 못하는지 몇 분 동안 어리둥절했다는 것이다.

## 언제 무엇을 쓸 것인가

| 상황                                               | 선택          |
| -------------------------------------------------- | ------------- |
| 패턴 하나로 충분하고 대상이 추적 중인 파일이다     | 글로빙        |
| `.gitignore`를 존중하면서 추가 조건이 필요하다     | `fd`          |
| 숨김 디렉터리를 뒤져야 한다                        | `fd --hidden` |
| 도구를 설치할 수 없는 기계이고 글로빙으로 부족하다 | `find`        |

저자의 결론이 이 표의 마지막 줄이다.
글로빙은 수십 년 되었고 `fd`도 거의 10년이 되었으며,
새 도구와 기법이 반드시 옛것보다 나은 것은 아니지만,
도구를 쉽게 설치할 수 없는 기계가 아니고 글로빙으로 원하는 검색이 안 되는 경우가 아니라면
오늘날 `find`를 피하는 편이 합당하다는 것이다.

## 함정

- 글로빙은 결과를 명령줄 인자로 펼치므로 파일이 아주 많으면 인자 길이 한계에 걸린다. `find`와 `fd`는 이 문제가 없거나 `-exec`와 `-x`로 우회한다.
- 일치하는 파일이 없을 때 zsh는 오류를 내고 Bash는 패턴 문자열을 그대로 넘긴다. 후자는 `rm *.md` 같은 명령에서 위험하다.
- `.gitignore`를 존중한다는 기본값은 git 저장소 밖에서는 다르게 동작한다. 빌드 산출물을 찾으려 할 때 무시되는 원인이 되기도 한다.
- 스크립트에 쓸 때는 대화형 편의가 함정이 된다. `fd`의 기본 제외 규칙은 저장소 상태에 따라 결과가 달라지므로, 재현이 중요한 스크립트에서는 조건을 명시하는 편이 안전하다.
- 맥에서 `#!/bin/bash`와 `globstar`의 조합은 조용히 실패한다. `#!/usr/bin/env bash`로 Homebrew의 최신 Bash를 쓰거나 zsh를 쓰는 편이 낫다.

## 비평

### find을 비판하는 근거가 대부분 인터페이스에 대한 것이다

나열된 다섯 가지 문제 중 넷은 문법에 관한 것이다.
옵션 접두사가 다르다, 따옴표가 필요하다, 인자 순서가 정해져 있다, 경로를 반드시 써야 한다.
이것들은 실제 불편이지만, 한 번 익히면 다시 겪지 않는 종류이기도 하다.

진짜 논거는 다섯 번째, 즉 기본값이다.
`.gitignore`와 숨김 파일을 뒤진다는 것은 익힌다고 해결되지 않고 매번 필터를 붙여야 한다.
그리고 이 항목은 `fd`를 지지하지 글로빙을 지지하지 않는다.
글로빙도 `.gitignore`를 모르기 때문이다.

글이 글로빙과 `fd`를 함께 대안으로 묶으면서 이 차이가 흐려진다.
두 도구는 서로 다른 문제를 푼다.
글로빙은 문법의 불편을 없애고, `fd`는 기본값의 문제를 없앤다.
문법만 문제라면 글로빙으로 충분하고, 기본값이 문제라면 글로빙은 답이 아니다.

### 도구 설치 가능성을 예외로 밀어 두지만 그것이 find의 존재 이유다

저자는 도구를 쉽게 설치할 수 없는 기계라는 조건을 마지막 문장의 단서로 처리한다.
그러나 그 조건이 걸리는 상황은 드물지 않다.
컨테이너 안, 남의 서버, 최소 이미지, CI 러너, 고객사 장비가 그렇다.

이런 환경에서는 `fd`가 없을 뿐 아니라 zsh도 없고 Bash도 낡았을 수 있다.
그리고 이런 환경이야말로 파일을 찾아야 할 일이 잦은 곳이다.
그러므로 `find`를 쓸 줄 아는 것은 구식 취향이 아니라
통제할 수 없는 환경에서 일할 수 있는 능력에 가깝다.

더 정확한 권고는 `find`를 피하라는 것이 아니라
자기 기계에서는 편한 도구를 쓰고 남의 기계에서는 `find`를 쓸 수 있게 해 두라는 것이었을 것이다.
저자가 다른 글에서 SSH 접속 시 `EDITOR`를 `vim`으로 되돌리는 설정을 제시한 것과 같은 발상이다.

### 함정을 하나만 들고 나머지 기본값 문제는 다루지 않는다

숨김 파일 문제는 잘 짚었지만 같은 성격의 함정이 더 있다.
`.gitignore` 존중은 편리한 기본값인 동시에
검색 결과가 저장소의 상태에 의존하게 만든다.

같은 명령이 저장소 안에서는 빌드 산출물을 빼고 밖에서는 포함하며,
동료의 `.gitignore`가 다르면 결과도 달라진다.
대화형으로 쓸 때는 대개 원하는 동작이지만 스크립트에서는 재현성을 깨뜨린다.

글이 `fd`를 권하면서 이 성질을 장점으로만 제시하는 것은 균형이 맞지 않는다.
합리적인 기본값이라는 표현 자체가 판단을 담고 있으며,
그 판단은 사용 맥락에 따라 뒤집힌다.

## 체크리스트

- 이 검색이 대화형인가, 스크립트에 들어갈 것인가?
- 찾으려는 파일이 `.gitignore`에 걸려 있거나 숨김 디렉터리에 있지는 않은가?
- 결과가 많을 때 인자 길이 한계에 걸리지 않는가?
- Bash 스크립트에서 `**`를 쓴다면 `globstar`를 켰고, 실행될 기계의 Bash 버전을 확인했는가?
- 일치하는 파일이 없을 때의 동작을 고려했는가?
- 남의 기계에서도 같은 작업을 해야 한다면 `find` 형태도 알아 두었는가?

## 기억할 원칙

### 기본값이 문법보다 오래 남는 비용이다

이 글이 드는 `find`의 문제 중 익히면 사라지는 것과 영원히 남는 것을 나누면,
문법은 앞쪽이고 기본값은 뒤쪽이다.
매번 같은 필터를 손으로 붙여야 하는 도구는 숙련도로 해결되지 않는다.

그래서 도구를 고를 때 물어야 할 것은 배우기 쉬운가보다
자주 쓰는 방식이 기본값인가다.
`fd`가 `find`보다 나은 진짜 이유도 문법이 짧아서가 아니라
사람들이 대개 원하는 동작이 옵션 없이 나오기 때문이다.

### 편의를 기본값으로 삼은 도구는 스크립트에서 재현성을 잃는다

`.gitignore`를 존중하고 숨김 파일을 건너뛰는 것은
사람이 터미널 앞에 앉아 있을 때 옳은 선택이다.
그러나 같은 성질이 스크립트에서는 환경 의존을 만든다.
결과가 저장소 상태, 설정 파일, 도구 버전에 따라 달라지기 때문이다.

그러므로 대화형에서 쓰는 도구와 자동화에서 쓰는 도구를 같은 기준으로 고르지 않는 편이 낫다.
자동화에서는 옵션이 길어지더라도 동작이 명시적인 쪽,
그리고 어디에나 설치되어 있는 쪽이 대개 옳다.
