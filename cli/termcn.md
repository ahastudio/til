# termcn: shadcn 방식으로 가져다 쓰는 터미널 UI 컴포넌트

<https://termcn.dev/>

<https://github.com/shadcn-labs/termcn>

GN 토론: <https://news.hada.io/topic?id=32005>

## 소개

termcn은 React로 터미널 UI를 만들 때 쓰는, 복사해 가져다 쓰는 컴포넌트 모음이다.
무료 오픈소스이며 MIT 라이선스이고, 설정 없이 바로 쓸 수 있다는 것을 내세운다.
현재 저장소는 스타 1.1k, 포크 48개, 커밋 310개 규모다.

이름이 말하듯 shadcn/ui의 방식을 터미널로 옮긴 것이다.
shadcn/ui가 그랬듯 이것도 설치해서 임포트하는 패키지가 아니라, CLI로 컴포넌트 소스를 내 프로젝트에 복사해 넣는 배포 모델을 쓴다.
실제로 설치 명령이 `npx shadcn@latest add`이며, termcn은 그 CLI가 읽는 레지스트리로 존재한다.

렌더링은 직접 하지 않는다.
Ink 또는 OpenTUI 위에서 동작하므로, 둘 중 하나가 설정된 프로젝트가 전제 조건이다.
즉 이 프로젝트가 채우는 자리는 렌더러가 아니라 그 위의 컴포넌트 계층이다.

제공하는 것은 크게 네 묶음이다.

- 터미널 테마에 자동으로 맞춰지는 테마 통합
- 차트 계열: 막대, 선, 게이지, 히트맵
- AI 인터페이스 계열: 채팅 화면, 승인 흐름, 스트리밍 텍스트
- 내비게이션 계열: 커맨드 팔레트, 탭, 메뉴, 사이드바

## 동작 방식

### 레지스트리에서 소스를 복사해 온다

설치 단위가 패키지가 아니라 컴포넌트다.

```bash
# Ink 기반 프로젝트
npx shadcn@latest add @termcn/ink/spinner

# OpenTUI 기반 프로젝트
npx shadcn@latest add @termcn/opentui/spinner
```

네임스페이스가 렌더러별로 갈린다는 점이 중요하다.
같은 `spinner`라도 Ink용과 OpenTUI용이 별개의 소스로 존재하며, 프로젝트가 쓰는 렌더러에 맞는 쪽을 가져와야 한다.

가져온 결과물은 내 저장소의 파일이 된다.
사용할 때 `@/components/ui/spinner`에서 임포트하는 것이 그 증거다. 노드 모듈 경로가 아니라 프로젝트 내부 경로다.

```tsx
import { Spinner } from "@/components/ui/spinner";
import { Text } from "ink";

export function App() {
  return (
    <>
      <Text>Loading...</Text>
      <Spinner />
    </>
  );
}
```

`Text`는 Ink에서 직접 가져오고 `Spinner`만 termcn에서 온다.
즉 termcn은 Ink를 감싸지 않고 그 옆에 놓인다. 두 출처의 컴포넌트를 한 트리 안에서 섞어 쓰는 것이 정상적인 사용 형태다.

### 프로바이더가 횡단 관심사를 맡는다

테마, 모션, 유니코드 처리는 개별 컴포넌트가 아니라 프로바이더로 주입한다.
이것들도 컴포넌트와 마찬가지로 레지스트리에서 가져온다.

```bash
# 테마 프로바이더 (렌더러에 맞는 쪽 하나)
npx shadcn@latest add @termcn/ink/theme-provider
npx shadcn@latest add @termcn/opentui/theme-provider

# 선택 사항
npx shadcn@latest add @termcn/ink/motion-provider @termcn/ink/unicode-provider
```

테마는 객체로 전달한다.

```tsx
import { ThemeProvider } from "@/providers/theme-provider";
import { draculaTheme } from "@/lib/terminal-themes/dracula";

export function App() {
  return <ThemeProvider theme={draculaTheme}></ThemeProvider>;
}
```

여기서 눈여겨볼 것은 테마 파일의 위치다.
`@/lib/terminal-themes/dracula`는 노드 모듈이 아니라 프로젝트 안의 파일이고, 이 배포 모델에서는 테마도 복사해 온 소스다.
그래서 색 하나를 바꾸고 싶을 때 오버라이드 API를 찾을 필요 없이 그 파일을 열어 고치면 된다.

`motion-provider`와 `unicode-provider`가 선택 사항으로 분리되어 있다는 점도 설계 의도를 드러낸다.
애니메이션과 유니코드 폭 처리는 터미널 환경에 따라 비용과 위험이 다르므로, 기본으로 켜지 않고 필요한 프로젝트만 켜도록 두었다.

## 도입하기

순서는 세 단계다.

첫째, Ink 또는 OpenTUI로 돌아가는 프로젝트를 먼저 만든다.
termcn은 이 단계를 대신해 주지 않으며, 어느 쪽을 고르느냐가 이후 모든 컴포넌트의 네임스페이스를 결정한다.

둘째, 테마 프로바이더를 먼저 가져와 앱 최상단에 감싼다.
컴포넌트를 먼저 가져다 쓰고 나중에 테마를 붙이는 순서도 동작하지만, 그렇게 하면 이미 하드코딩해 둔 색과 테마 값이 섞인 상태에서 정리해야 한다.

셋째, 필요한 컴포넌트를 하나씩 가져온다.
전부 가져올 이유가 없다. 복사 모델에서는 가져온 파일이 전부 유지보수 대상이 되므로, 쓰지 않는 컴포넌트를 미리 가져오는 것은 순손해다.

## 값 정하기

| 결정 항목           | 출발점                       | 근거                                                                           |
| ------------------- | ---------------------------- | ------------------------------------------------------------------------------ |
| 렌더러              | Ink                          | 생태계와 예제가 더 많고, termcn 문서의 기본 예시도 Ink 쪽이다                  |
| 테마                | 터미널 테마 자동 감지에 위임 | 사용자의 터미널 설정과 어긋나지 않는 것이 고정 테마보다 안전하다               |
| 모션 프로바이더     | 처음에는 도입하지 않음       | 터미널에서 애니메이션은 갱신 비용이 크고, 없어도 기능은 완전하다               |
| 유니코드 프로바이더 | 한글·이모지를 쓰면 도입      | 폭 계산이 어긋나면 테두리와 정렬이 무너지므로, 해당 문자를 쓸 때는 사실상 필수 |
| 가져올 컴포넌트     | 실제 화면에 쓰는 것만        | 복사된 소스는 곧 내 코드이며, 쓰지 않는 파일도 리뷰와 갱신 부담이 된다         |

무엇을 보고 이 값들을 고칠지도 정해 두는 편이 낫다.
렌더러 선택은 되돌리기 가장 비싼 결정이므로, 프로토타입 단계에서 필요한 컴포넌트 두세 개를 양쪽으로 다 가져와 비교해 보는 것이 싸다.
테마는 밝은 배경과 어두운 배경 터미널에서 각각 확인해야 하며, 자동 감지가 의도대로 동작하지 않는 조합이 나오면 그때 명시적 테마로 고정한다.

## 트레이드오프

### 복사 모델은 소유권을 주고 갱신을 가져간다

shadcn 계열의 핵심 거래가 여기 있다.
컴포넌트가 내 저장소의 파일이므로 원하는 대로 고칠 수 있고, 라이브러리의 추상화와 싸울 일이 없다.
터미널 UI처럼 환경 편차가 크고 세부 조정이 잦은 영역에서 이 자유는 실질적인 가치가 있다.

대가는 업스트림 수정이 자동으로 오지 않는다는 것이다.
버그가 고쳐져도, 유니코드 폭 처리가 개선되어도, 내 파일은 가져온 시점에 멈춰 있다.
다시 `add`하면 최신 소스를 받을 수 있지만 그 순간 내가 고친 부분이 사라지므로, 실제로는 수동 병합이 된다.

여기서 흔히 제안되는 해법이 통하지 않는다.
“고친 부분을 래퍼로 분리하면 되지 않나”는 생각이 자연스럽지만, 복사 모델에서 고치게 되는 것은 대개 컴포넌트 내부의 렌더링 세부이지 바깥에서 감쌀 수 있는 동작이 아니다.
감쌀 수 있는 수준의 수정이었다면 애초에 패키지로 써도 됐을 것이다.

실무적인 절충은 가져온 파일을 별도 커밋으로 분리해 두는 것이다.
가져온 원본 하나, 내 수정 하나로 커밋을 나눠 두면 나중에 재수입할 때 내 수정만 다시 얹을 수 있다.
번거롭지만, 이 모델에서 갱신 경로를 확보하는 유일한 실용적 방법이다.

### 렌더러를 고르지 않고 둘 다 지원하는 비용

Ink와 OpenTUI 양쪽을 지원한다는 것은 도입자에게는 선택지이지만, 프로젝트에게는 표면적이 두 배라는 뜻이다.
컴포넌트 하나가 두 벌의 구현을 갖고, 어느 한쪽이 먼저 갱신되면 그 차이가 그대로 사용자에게 간다.

도입자 입장에서 실제로 신경 써야 할 지점은 두 네임스페이스의 동등성이 보장되지 않는다는 것이다.
문서에서 `@termcn/ink/...`로 소개된 컴포넌트가 OpenTUI 쪽에도 같은 이름과 같은 속성으로 존재하는지는 개별 확인 대상이고, 이 확인을 건너뛰면 렌더러를 바꾸려 할 때 비용이 드러난다.

그리고 렌더러 전환은 사실상 재작성이다.
`Text` 같은 기본 요소를 Ink에서 직접 가져다 쓰는 구조이므로, termcn 컴포넌트를 전부 다시 받더라도 그 사이를 잇는 코드가 남는다.
양쪽 지원은 시작할 때의 선택지일 뿐 나중의 이동 경로가 아니다.

### 터미널 테마 자동 감지가 주는 것과 못 주는 것

사용자의 터미널 테마에 맞춰 색이 조정된다는 것은 터미널 도구로서 올바른 기본값이다.
사용자가 자기 색 설정을 해 뒀는데 앱이 자기 색을 강요하면 그 자체로 결함이고, 특히 대비가 무너져 읽히지 않는 조합이 나온다.

다만 자동 감지는 디자인 일관성과 맞바꾼 것이다.
차트와 히트맵처럼 여러 색의 상대 관계가 의미를 지니는 컴포넌트에서는, 환경에 따라 색이 바뀌면 그 관계가 흐려질 수 있다.
히트맵의 단계 구분이 어떤 터미널 테마에서는 뚜렷하고 어떤 테마에서는 뭉개지는 상황이 이 계열의 전형적인 문제다.

여기서 양쪽을 다 가질 수는 없다.
사용자 테마를 존중하면 시각적 인코딩의 정확성을 보장할 수 없고, 고정 팔레트를 쓰면 사용자 설정을 무시하게 된다.
현실적인 절충은 의미를 색에만 싣지 않는 것이다. 차트에서 색 외에 문자나 밀도로도 단계를 구분해 두면 어느 테마에서도 읽힌다.

### AI 컴포넌트가 별도 묶음인 이유와 그 함의

채팅 화면, 승인 흐름, 스트리밍 텍스트가 차트·내비게이션과 나란히 1급 범주로 들어가 있다는 점은 이 프로젝트의 시기를 보여 준다.
터미널 UI 컴포넌트 모음이 몇 년 전에 나왔다면 이 묶음은 없었을 것이다.

이 선택의 이점은 분명하다.
스트리밍 텍스트는 직접 만들면 까다롭다. 부분 출력이 계속 들어오는 동안 줄바꿈과 재렌더링을 어떻게 다루느냐에 따라 화면이 심하게 떨린다.
승인 흐름 역시 에이전트 CLI에서 반복해 나타나는 형태이고, 매번 새로 만들 이유가 없다.

대가는 컴포넌트가 특정 상호작용 모델을 전제한다는 것이다.
승인 흐름 컴포넌트는 “에이전트가 제안하고 사람이 승인한다”는 구조를 UI에 담고 있으며, 그 구조가 내 도구와 다르면 컴포넌트를 쓰는 대신 고쳐 쓰게 된다.
복사 모델이라 고치는 것 자체는 쉽지만, 그렇게 고친 컴포넌트는 앞서 말한 갱신 부담을 그대로 떠안는다.

## 함정

렌더러를 먼저 정하지 않고 시작하면 되돌리기 비싸다.
`npx shadcn@latest add`의 네임스페이스가 렌더러를 고정하며, 몇 개를 가져온 뒤에 바꾸려 하면 가져온 것을 전부 다시 받고 그 사이 코드를 고쳐야 한다.

한글과 이모지의 폭 문제는 컴포넌트를 쓴다고 사라지지 않는다.
터미널에서 한중일 문자와 이모지는 셀 두 개를 차지하며, 이것을 처리하라고 `unicode-provider`가 따로 존재한다.
선택 사항으로 분리되어 있다는 것은 기본 상태에서는 처리되지 않는다는 뜻이므로, 한글 UI를 만든다면 이 프로바이더를 켜고 테두리 정렬을 직접 확인해야 한다.

모션은 켜기 전에 갱신 비용을 확인해야 한다.
터미널은 전체 화면을 다시 그리는 방식이라 애니메이션의 비용 구조가 웹과 다르고, 느린 SSH 연결에서는 애니메이션이 지연을 체감시키는 주범이 된다.

가져온 파일이 리뷰 대상이라는 사실을 잊기 쉽다.
`add` 한 번으로 수백 줄이 저장소에 들어오는데, 이 코드는 의존성이 아니라 내 코드다.
보안 검토, 린트 규칙, 코드 소유자 설정이 전부 이 파일들에 적용되며, 팀 규모가 커질수록 이 사실이 비용으로 돌아온다.

스타 1.1k, 커밋 310개는 활발하지만 성숙하지는 않은 규모다.
컴포넌트 API가 바뀔 수 있고, 복사 모델에서는 그 변화가 이미 가져온 파일에 자동으로 오지 않는 대신 새로 가져오는 파일과 기존 파일 사이의 불일치로 나타난다.

## 확인하기

가장 빠른 검증은 스피너 하나를 가져와 띄워 보는 것이다.

```bash
npx shadcn@latest add @termcn/ink/spinner
```

파일이 `components/ui/` 아래에 실제로 생겼는지 확인하는 것이 첫 단계다.
생기지 않았다면 `components.json` 경로 설정이 shadcn CLI가 기대하는 형태가 아닌 것이고, 컴포넌트를 더 가져오기 전에 그것부터 맞춰야 한다.

그다음은 자기 환경에 특화된 두 가지다.

```tsx
import { ThemeProvider } from "@/providers/theme-provider";
import { Text } from "ink";

// 테마 프로바이더 없이 한 번, 감싸고 한 번 렌더링해 색이 실제로 바뀌는지 본다.
export function App() {
  return (
    <ThemeProvider>
      <Text>한글 테두리 정렬 확인 ██ 끝</Text>
    </ThemeProvider>
  );
}
```

한글이 포함된 줄에서 오른쪽 끝의 블록 문자가 예상 위치에 오는지 보면 폭 계산이 맞는지 알 수 있다.
어긋난다면 `unicode-provider`를 켜고 다시 확인하고, 그래도 어긋나면 그 조합에서는 직접 폭을 다루어야 한다.

테마는 터미널 배경을 밝게 한 번, 어둡게 한 번 바꿔 가며 같은 화면을 띄워 보는 것으로 충분하다.
차트나 히트맵을 쓸 계획이라면 그 컴포넌트로 같은 검증을 반복해야 한다. 텍스트는 괜찮은데 다단계 색 인코딩이 무너지는 경우가 흔하기 때문이다.

## 체크리스트

- Ink와 OpenTUI 중 어느 쪽을 쓸지 정했고, 그 결정의 근거를 적어 두었는가
- 테마 프로바이더를 컴포넌트보다 먼저 도입했는가
- 한글 또는 이모지를 쓴다면 `unicode-provider`를 켜고 정렬을 눈으로 확인했는가
- 밝은 터미널과 어두운 터미널에서 각각 확인했는가
- 차트류에서 색 외의 수단으로도 단계를 구분할 수 있는가
- 가져온 컴포넌트 중 실제로 화면에 쓰이지 않는 것이 있는가
- 가져온 원본과 내 수정을 별도 커밋으로 나눠 두었는가
- 느린 원격 연결에서 화면 갱신 지연을 확인했는가

### GN 반응: 터미널에 React를 얹는 것에 대한 감각차

GeekNews 스레드에서 오간 이야기는 기능 비교가 아니라 이 접근 자체에 대한 감각이었다.
click은 생산성이 높은 것은 맞지만, 예전 세대 개발자에게 React로 TUI를 만든다고 하면 터미널에 쓸데없는 오버헤드를 얹는다고 할 것 같다며, 폰 노이만이 어셈블리어를 쓰는 제자들을 보고 왜 기계어로 짜지 않느냐고 했다는 일화를 떠올렸다.[^click]
snisper는 폰 선생님께 물어보니 그런 적 없다고 한다고 받아쳤고[^snisper], 이 농담 자체가 그 비유가 과장이라는 지적이기도 하다.

poleewer의 반응이 실질적인 논점을 짚는다.
요즘 TUI 도구는 사용성이 좋아서, IDE와 비교할 때 기계어와 어셈블리어의 관계라기보다 마우스와 트랙패드 같은 취향 차이에 가깝다는 것이다.[^poleewer]
이 구분이 중요한 이유는 추상화 계층을 정당화하는 논거가 달라지기 때문이다.
성능 계층이라면 오버헤드가 곧 손실이지만, 취향과 작업 방식의 문제라면 오버헤드는 다른 이득과 교환되는 비용일 뿐이다.

실무적으로 여기서 남는 질문은 하나다.
React를 얹어 얻는 것이 개발 생산성이라면, 그 생산성이 실제로 사용자가 체감하는 지연을 넘어서는가.
termcn을 평가할 때 이 질문에 답하는 방법은 벤치마크가 아니라, 가장 큰 화면을 느린 원격 연결에서 띄워 보는 것이다.

## 기억할 원칙

### 배포 모델이 곧 유지보수 계약이다

termcn에서 실제로 선택하는 것은 컴포넌트의 모양이 아니라 배포 방식이다.
패키지로 받으면 갱신이 자동으로 오고 수정이 어렵다. 복사로 받으면 수정이 자유롭고 갱신이 수동이다.
어느 쪽이 옳은지는 라이브러리의 품질이 아니라 내가 그 코드를 얼마나 고칠 것인지에 달려 있다.

이 판단을 미리 하는 방법이 하나 있다.
도입 전에 “이 컴포넌트의 내부를 열어 볼 일이 있을까”를 물어보는 것이다.
답이 아니오라면 복사 모델은 순손해이고, 답이 그렇다면 패키지의 추상화는 결국 싸울 대상이 된다.
터미널 UI는 환경 편차가 커서 후자가 되기 쉬운 영역이고, termcn이 이 모델을 고른 것도 그래서일 것이다.
