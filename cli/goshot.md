# goshot: Go로 만든 코드 스크린샷 생성기

<https://github.com/watzon/goshot>

## 소개

goshot은 코드와 터미널 출력을 스크린샷 이미지로 만드는 Go 라이브러리이자 CLI다.
문법 하이라이팅, 윈도우 크롬(창 장식), 풍부한 배경을 제공하며 README는 스스로를 Carbon과 Silicon에 견준다.
MIT 라이선스이고 GitHub 스타는 300개대, main 브랜치 커밋은 160여 개 수준이다.

비교 대상이 이 프로젝트의 위치를 잘 설명한다.
Carbon은 웹 서비스라 브라우저를 열고 코드를 붙여넣어야 하고, Silicon은 Rust로 쓰인 CLI다.
goshot은 Silicon과 같은 자리를 노리면서 Go 단일 바이너리 배포와 라이브러리 API를 함께 제공한다.

## 주요 기능

chroma 기반의 수백 개 테마로 문법 하이라이팅을 하고, ANSI 컬러를 완전히 지원해 터미널 출력도 그대로 렌더링한다.
윈도우 크롬은 macOS, Windows 11, GNOME, KDE Breeze 네 가지를 지원한다.
배경은 단색, 일곱 종류의 그라디언트, 이미지 중에서 고를 수 있다.

나머지 기능은 실제 공유 상황에서 걸리는 것들을 겨냥한다.
코드와 터미널 출력 안의 컬러 이모지를 시스템 이모지 폰트로 그리고, API 키·토큰·비밀번호 같은 비밀값을 자동으로 가린다.
드롭 섀도, 둥근 모서리, 블러 효과가 있고, 폰트는 내장 폰트와 시스템 폰트 탐색을 함께 쓴다.
출력은 PNG·JPEG·BMP 파일과 클립보드·표준출력을 지원하며, 명령을 실행해 그 출력을 한 번에 스크린샷으로 만드는 경로도 있다.

## CLI

설치는 `go install github.com/watzon/goshot/cmd/goshot@latest` 한 줄이고, Arch(AUR)와 Ubuntu(PPA) 패키지도 있다.

```bash
# 파일 스크린샷
goshot main.go -o main.png

# 표준입력을 읽어 클립보드로
cat main.go | goshot -c

# 테마·크롬·배경 지정
goshot main.go -t catppuccin-mocha -C gnome -b '#1e1e2e'

# 그라디언트 배경과 강조 줄
goshot main.go --gradient-type linear \
    --gradient-stops '#4158D0;0' --gradient-stops '#C850C0;100' \
    --highlight-lines 10..14

# 공유 전에 비밀값 가리기
goshot config.go --redact --redact-style blur

# 명령을 실행하고 그 출력을 스크린샷으로
goshot exec -A -p -- go test ./...
```

`goshot themes`, `goshot fonts`, `goshot languages`로 사용 가능한 목록을 확인한다.
모든 플래그의 기본값은 `~/.config/goshot/config.yaml`에 플래그 이름과 값의 평평한 맵으로 넣을 수 있고, 명령줄에서 준 플래그가 항상 이긴다.

```yaml
theme: catppuccin-mocha
chrome: mac
background: "#1e1e2e"
corner-radius: 12
```

## 라이브러리

라이브러리는 작은 파이프라인이다.
콘텐츠(코드 또는 터미널 출력)를 이미지로 렌더링하고, 크롬으로 감싸고, 배경 위에 올린다.

```go
err := goshot.New().
    WithContent(code.New(`fmt.Println("Hello, goshot!")`).
        WithLanguage("go").
        WithTheme("dracula")).
    WithChrome(chrome.Mac().WithTitle("hello.go").Dark()).
    WithBackground(background.Gradient(background.LinearGradient,
        background.Stop{Color: color.RGBA{26, 27, 38, 255}, Position: 0},
        background.Stop{Color: color.RGBA{40, 42, 54, 255}, Position: 1},
    ).
        WithAngle(45).
        WithPadding(60).
        WithCornerRadius(10).
        WithShadow(background.NewShadow().WithBlur(20).WithOffset(0, 8))).
    Save("hello.png")
```

터미널 출력은 `term` 패키지로 같은 방식으로 다룬다.
`WithTitleBarMatchingContent`는 타이틀 바를 콘텐츠 배경에 녹이고, `WithTitleBarColor`와 `WithTitleTextColor`는 색을 직접 지정한다.
패키지 구성은 파이프라인의 각 단계와 일대일로 대응한다.

| 패키지       | 역할                                        |
| ------------ | ------------------------------------------- |
| `goshot`     | 캔버스 파이프라인과 이미지 내보내기         |
| `code`       | 문법 하이라이팅 코드 렌더링                 |
| `term`       | 터미널 출력 렌더링(ANSI 이스케이프, 256색)  |
| `chrome`     | 창 장식(mac, windows, gnome, breeze)        |
| `background` | 단색·그라디언트·이미지 배경                 |
| `fonts`      | 내장 폰트와 시스템 폰트 로딩                |

## 분석

### 이 도구의 진짜 차별점은 예쁜 배경이 아니라 exec 서브커맨드다

기능 목록만 보면 goshot은 Carbon 계열의 반복처럼 읽힌다.
테마, 크롬, 그라디언트는 이 장르의 표준 구성이고 어느 도구에나 있다.

차이는 `goshot exec -- go test ./...`에 있다.
기존 도구는 이미 존재하는 텍스트를 입력으로 받는다 — 코드 파일이든, 붙여넣은 문자열이든, 파이프로 넘긴 출력이든.
goshot은 명령을 직접 실행하고 그 출력을 잡는다.
이 한 단계 차이가 작업 흐름을 바꾼다 — 명령을 돌리고, 출력을 복사하고, 다른 도구에 붙여넣고, 색이 깨진 것을 확인하고, 다시 손보는 네 단계가 한 줄로 줄어든다.

ANSI 완전 지원이 여기에 붙어야 의미가 있다.
`go test`나 `cargo build`의 출력은 색이 정보다 — 빨간 FAIL과 초록 ok를 구분하지 못하면 스크린샷의 절반이 사라진다.
대부분의 코드 스크린샷 도구가 코드에만 집중하고 터미널을 부차적으로 다루는 것과 달리, goshot은 `term` 패키지를 `code`와 동등한 층위에 놓았다.

### 자동 비밀값 가리기는 기능이 아니라 사고 예방 장치다

`--redact` 플래그는 API 키, 토큰, 비밀번호를 자동으로 탐지해 가린다.
기능 목록에서는 한 줄이지만 이 도구가 어떤 사고를 겨냥하는지 말해준다.

코드 스크린샷이 유출되는 경로는 대개 같다 — 설정 파일이나 로그 출력을 공유하려다 그 안에 섞인 자격 증명을 못 보고 지나치는 것이다.
텍스트라면 검색과 스캐너가 잡지만 이미지가 되는 순간 자동 검출을 벗어난다.
GitHub의 시크릿 스캐닝도, 사내 DLP도 스크린샷 속 문자열은 잘 못 잡는다.

그래서 이 기능의 위치가 중요하다.
공유 시점이 아니라 렌더링 시점에 개입하기 때문에, 사람이 기억해야 할 절차가 아니라 도구의 기본 동작으로 만들 수 있다.
설정 파일에 `redact: true`를 넣어두면 그 이후로는 잊어도 된다.
다만 README는 어떤 패턴을 어떻게 탐지하는지 밝히지 않으며, 이 침묵이 뒤에서 다룰 문제로 이어진다.

### 라이브러리와 CLI를 같은 저장소에 두는 선택

goshot은 CLI 도구이면서 동시에 `WithContent().WithChrome().WithBackground()` 체이닝 API를 가진 라이브러리다.
Go 생태계에서 흔한 구조이지만 항상 성립하는 것은 아니다 — CLI의 플래그 표면과 라이브러리의 타입 표면은 다른 속도로 변하고, 하나를 위해 다른 하나를 타협하기 쉽다.

여기서는 파이프라인 추상이 그 긴장을 흡수한다.
콘텐츠 → 크롬 → 배경이라는 3단 구조가 CLI 플래그 묶음과 라이브러리 빌더 메서드에 동일하게 대응하기 때문에, 한쪽에 기능이 추가되면 다른 쪽의 대응물이 자명하게 정해진다.
`-t`는 `WithTheme`, `-C`는 `WithChrome`, `-b`는 `WithBackground`다.

이 대응이 문서화 비용도 낮춘다.
README 하나로 두 인터페이스를 설명할 수 있고, 사용자가 CLI에서 라이브러리로 넘어갈 때 새로 배울 개념이 없다.
설계 문서 없이도 구조가 드러나는 이런 종류의 일관성은, 커밋 160여 개 규모의 프로젝트에서 유지보수 가능성을 좌우한다.

## 비평

### 비밀값 자동 탐지는 검증 없이 신뢰를 요구한다

`--redact`는 이 도구에서 유일하게 안전과 직결된 기능인데, README는 그 동작을 전혀 설명하지 않는다.
어떤 패턴을 탐지하는지, 정규식 기반인지 엔트로피 기반인지, 사용자 정의 패턴을 추가할 수 있는지, 놓친 경우 어떻게 되는지가 모두 비어 있다.

보안 기능에서 이 침묵은 중립이 아니다.
자동 가리기가 있다는 사실 자체가 사용자의 경계를 낮추기 때문이다.
직접 눈으로 확인하던 사람이 플래그 하나를 믿고 확인을 생략하게 되면, 탐지율이 90%인 도구는 확인을 하던 이전보다 나쁜 결과를 낼 수 있다.
API 키의 형태는 서비스마다 다르고, 사내 시스템의 토큰이나 데이터베이스 접속 문자열은 어떤 공개 패턴 목록에도 없다.

최소한 필요한 것은 두 가지다.
탐지 대상 목록을 문서에 공개하는 것과, 가려진 항목이 몇 개인지 표준오류로 알려주는 것이다.
후자가 특히 중요하다 — 0개가 가려졌다는 출력은 파일에 비밀이 없다는 뜻일 수도, 탐지가 실패했다는 뜻일 수도 있는데, 사용자는 그 차이를 알아야 확인 여부를 결정할 수 있다.

### 코드 스크린샷이라는 형식 자체가 접근성을 파괴한다

이 비평은 goshot만의 문제가 아니라 이 도구 범주 전체를 향한다.
코드를 이미지로 만드는 순간 검색이 안 되고, 복사가 안 되고, 스크린 리더가 읽지 못하고, 확대해도 흐려지고, 화면 폭에 맞춰 줄바꿈이 되지 않는다.
텍스트가 가진 모든 장점을 버리고 얻는 것은 시각적 완성도 하나다.

문제는 이 형식이 기본값이 되어가고 있다는 점이다.
소셜 미디어의 코드 공유는 대부분 이미지이고, 그 이유는 플랫폼이 코드 블록을 제대로 렌더링하지 않기 때문이다.
즉 이 도구들은 플랫폼의 결함을 우회하는 장치인데, 우회가 편리해질수록 플랫폼이 결함을 고칠 이유가 사라진다.

goshot에게 이를 해결하라고 요구하는 것은 부당하다.
다만 이 도구가 할 수 있는 일은 있다 — 이미지를 만들 때 원본 텍스트를 클립보드에 함께 넣거나, PNG 메타데이터에 원문을 심어 나중에 추출할 수 있게 하는 것이다.
`goshot exec`처럼 명령의 출력을 잡는 경우라면 실행한 명령 자체를 메타데이터에 남기는 것만으로도 재현 가능성이 크게 올라간다.
이미지가 텍스트를 대체하는 것이 아니라 텍스트를 감싸는 형태가 되면 손실의 상당 부분이 회복된다.

### 이 범주의 도구가 계속 새로 만들어진다는 사실이 무언가를 말한다

Carbon, Silicon, ray.so, snappify, CodeSnap, 그리고 goshot.
같은 일을 하는 도구가 언어를 바꿔가며 반복해서 등장한다.
새 도구마다 이유는 있다 — Carbon은 웹이라 느리고, Silicon은 Rust 툴체인이 필요하고, 웹 서비스는 코드를 서버로 보내야 한다.

그런데 이 반복은 근본 문제가 해결되지 않았다는 신호이기도 하다.
어느 도구도 편집기와 통합되어 있지 않고, 어느 도구도 공유 대상 플랫폼과 협상하지 않으며, 모두가 렌더링만 한다.
결과적으로 사용자는 매번 도구를 고르고 설정하고 테마를 맞추는 일을 반복한다.

goshot이 이 흐름에서 한 걸음 나아간 지점은 `exec` 서브커맨드와 설정 파일이다.
전자는 입력 획득을 자동화했고 후자는 반복 설정을 제거했다.
남은 것은 출력 쪽인데, 여기서 클립보드 지원 이상으로 나아가지 못한 것이 아쉽다.
이슈 트래커나 PR 코멘트에 바로 올리는 경로가 있었다면 이 범주가 정체된 지점을 실제로 넘었을 것이다.

## 인사이트

### 스크린샷 도구의 가치는 렌더링 품질이 아니라 마찰 제거의 총량에서 나온다

이 범주의 도구를 비교할 때 사람들은 대체로 결과물의 모양을 본다 — 그림자가 자연스러운지, 테마가 예쁜지, 크롬이 실제 OS와 닮았는지.
그러나 실제 채택을 결정하는 것은 결과물이 아니라 그 결과물에 이르는 단계 수다.

goshot의 설계는 이 점을 이해하고 있다.
`cat main.go | goshot -c`는 파일에서 클립보드까지 한 단계이고, `goshot exec -- go test ./...`는 실행에서 이미지까지 한 단계이며, `config.yaml`은 그 한 단계에서 플래그마저 없앤다.
같은 결과물을 만드는 다른 도구가 세 단계를 요구한다면, 렌더링 품질이 조금 나아도 실제로는 덜 쓰이게 된다.

이 관찰은 도구를 만드는 쪽에 일반화된다.
개발자 도구의 경쟁은 대개 기능 목록에서 벌어지지만 승부는 워크플로 단계 수에서 난다.
기능을 하나 더 붙이는 것보다 단계를 하나 없애는 것이 사용자에게 더 큰 변화이며, 후자는 기능 목록에 잘 드러나지 않기 때문에 마케팅에서는 불리하고 실사용에서는 유리하다.

### 자동 편집 기능은 도구를 워크플로에서 정책의 집행 지점으로 옮긴다

`--redact`는 기능 하나지만 도구의 성격을 바꾼다.
렌더링 도구는 무엇을 그릴지에 대해 판단하지 않는데, 비밀값을 가리는 순간 도구가 콘텐츠에 대해 판단을 시작한다.

이 전환에는 조직적 함의가 있다.
설정 파일에 `redact: true`를 기본값으로 넣고 그 설정 파일을 팀 전체에 배포하면, 개인의 주의력에 의존하던 정책이 도구의 기본 동작이 된다.
보안 정책이 실패하는 가장 흔한 이유가 사람이 매번 기억해야 하는 절차라는 점을 생각하면, 이 배치는 교육이나 체크리스트보다 효과적이다.

같은 원리가 다른 곳에도 적용된다.
사내 도메인 이름 가리기, 고객사 식별자 마스킹, 내부 IP 주소 치환은 모두 같은 지점에 넣을 수 있는 규칙이다.
goshot이 사용자 정의 패턴을 지원하지 않는다면 그것이 이 도구의 가장 큰 미실현 잠재력이다 — 범용 비밀 탐지보다 조직별 규칙이 실제 유출을 더 많이 막는다.

그리고 이 자리는 한 번 점유되면 강력하다.
스크린샷을 만드는 모든 경로가 한 도구를 지나가면 그 도구가 조직의 공유 정책을 집행하는 마지막 관문이 되고, 그 관문은 다른 도구로 갈아타기 어려워진다.

### AI 에이전트 시대에 스크린샷 도구의 수요는 반대 방향으로 움직인다

코드 스크린샷은 사람이 사람에게 코드를 보여주기 위한 형식이다.
그런데 코드를 읽는 주체가 점점 에이전트가 되어가는 흐름에서 이미지는 최악의 전달 형식이다 — 토큰 비용이 높고, OCR 오류가 생기고, 편집이 불가능하다.

그렇다면 이 범주는 축소될까.
반대일 가능성이 크다.
에이전트가 코드를 쓰고 읽는 비중이 커질수록 사람 사이의 소통에 남는 것은 오히려 요약과 증거이고, 스크린샷은 전형적인 증거 형식이다.
테스트가 통과했다는 주장보다 통과한 터미널 출력의 이미지가 설득력을 갖는 이유는, 이미지가 편집하기 어렵기 때문이 아니라 특정 시점의 실제 실행을 담고 있다고 읽히기 때문이다.

여기서 `goshot exec`의 위치가 다시 드러난다.
명령을 실행해 출력을 잡는 경로는 사람이 텍스트를 손댈 틈을 없앤다.
에이전트가 만든 결과를 사람에게 보고하는 파이프라인에서, 실행과 캡처가 한 단계로 묶인 도구는 단순한 편의가 아니라 신뢰의 근거가 된다.
다만 그 신뢰는 도구가 실제로 명령을 실행했다는 것 외에는 아무것도 보증하지 않으며, 이미지가 증거처럼 읽히는 이 관습 자체가 검증되지 않은 습관이라는 점은 기억해 둘 만하다.
