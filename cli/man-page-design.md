# 좋은 man 페이지는 무엇이 다른가

원문: [Notes on clarifying man pages](https://jvns.ca/blog/2026/02/18/man-pages/)

HN 토론: <https://news.ycombinator.com/item?id=47065972> (76점, 49개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/zpifkh/notes_on_clarifying_man_pages> (55점, 14개 댓글)

## 요약

Julia Evans가 2026년 2월 18일에 쓴 메모다.

[작년에 Git man 페이지 작업을 한 뒤](../git/git-data-model-docs.md) **무엇이 좋은 man 페이지를 만드는지 조금 더 생각해 보게 되었다**는 것이다.

동기가 솔직하다.
tcpdump, git, dig 같은 도구의 치트 시트를 쓰는 데 많은 시간을 썼는데 **그 도구들이 man 페이지를 주 문서로 삼고 있으며, 원하는 정보를 얻으려고 man 페이지를 훑는 것이 어려운 경우가 많기 때문**이라는 것이다.

그래서 최근 생각하는 것이 이것이다. **man 페이지 자체에 훌륭한 치트 시트가 들어 있을 수는 없을까? 무엇이 man 페이지를 쓰기 쉽게 만들까?**

아직 생각이 아주 초기 단계라며, Mastodon에서 좋아하는 man 페이지를 물어 모은 사례를 정리한다.

### OPTIONS SUMMARY

man 페이지를 많이 읽었다면 `SYNOPSIS`에서 이런 것을 봤을 것이다.

```text
ls [-@ABCFGHILOPRSTUWabcdefghiklmnopqrstuvwxy1%,]
grep [-abcdDEFGHhIiJLlMmnOopqRSsUVvwXxZz]
```

알파벳 거의 전체를 나열하는 지경이 되면 **읽기 어렵다**.

`rsync` man 페이지에 저자가 **한 번도 본 적 없는 해법**이 있다. `SYNOPSIS`를 아주 간결하게 유지하고,

```text
Local:
  rsync [OPTION...] SRC... [DEST]
```

그다음 **`OPTIONS SUMMARY` 절에 각 옵션의 한 줄 요약**을 둔다.

```text
--verbose, -v            increase verbosity
--info=FLAGS             fine-grained informational verbosity
--debug=FLAGS            fine-grained debug verbosity
--stderr=e|a|c           change stderr output mode (default: errors)
--quiet, -q              suppress non-error messages
--no-motd                suppress daemon-mode MOTD
```

그리고 뒤에 각 옵션의 전체 설명이 담긴 평소의 `OPTIONS` 절이 온다.

### 범주별로 묶은 OPTIONS

`strace` man 페이지는 옵션을 알파벳순이 아니라 **범주별**(General, Startup, Tracing, Filtering, Output Format)로 조직한다.

저자가 실험으로 `grep` man 페이지에 범주별 `OPTIONS SUMMARY`를 만들어 봤다고 한다.
**결과가 어떤지는 잘 모르겠지만 재미있는 연습이었다**는 평가다.

그리고 왜 이것을 시도했는지 밝힌다.
**`grep`의 `-l` 옵션 이름을 도무지 기억하지 못하며, man 페이지에서 그것을 찾는 데 영원처럼 느껴지는 시간이 걸린다**는 것이다. 찾기 쉽게 만들 구조가 무엇일까 생각하다가 범주를 떠올렸다는 것이다.

### 치트 시트

몇 사람이 Perl man 페이지 모음(`perlfunc`, `perlre` 등)을 알려 줬는데, 그중 **`man perlcheat`**이 눈에 띄었다고 한다.

```text
SYNTAX
foreach (LIST) { }     for (a;b;c) { }
while   (e) { }        until (e)   { }
if      (e) { } elsif (e) { } else { }
unless  (e) { } elsif (e) { } else { }
given   (e) { when (e) {} default {} }
```

**정말 멋지다**며, man 페이지에 쓸 압축된 80자 폭 ASCII 치트 시트를 쓰는 다른 방법이 있을지 궁금해진다고 적는다.

### 예제가 아주 인기 있다

흔한 의견이 **“예제가 있는 man 페이지라면 뭐든 좋다”**는 취지였다고 한다.

누군가 OpenBSD man 페이지를 언급했는데, OpenBSD의 `tail` man 페이지 끝에 **저자가 `tail`을 쓰는 정확히 그 두 방식의 예제**가 있었다는 것이다.

`EXAMPLES` 절을 man 페이지 끝에서 가장 자주 봤는데, `rsync` 같은 일부는 **예제로 시작**한다고 짚는다.
그리고 자기가 `git-add`와 `git rebase` man 페이지를 작업할 때 **맨 앞에 짧은 예제를 넣었다**고 밝힌다.

### 목차와 절 사이 링크

man 페이지 자체의 속성은 아니지만, 터미널에서 man 페이지를 볼 때 문제 하나가 **어떤 절들이 있는지 알기 어렵다**는 것이다.

Git man 페이지 작업 때 Marie와 함께 **Git 사이트에 올라간 HTML 판본 사이드바에 목차를 추가**했다고 한다.
그리고 “INCOMPATIBLE OPTIONS”를 클릭하면 그 절로 가도록 **내부 하이퍼링크를 더 넣고 싶다**고 적는다. Git man 페이지가 AsciiDoc으로 생성되므로 링크 추가가 아주 쉽다는 것이다.

이것을 **좋은 절충**이라고 평가한다. **완전히 다른 형태의 문서를 따로 유지하지 않으면서 man 페이지 형식을 개선하는 것**이기 때문이다. 다만 Git의 AsciiDoc 같은 툴체인을 갖춰야 한다는 단서를 단다.

그리고 미해결 과제를 하나 남긴다.
**man 페이지에서 특정 옵션을 찾기 쉽게 해 주는 보편적인 시스템이 있으면 놀라울 것**이라는 것이다(“`-a`가 뭐 하는 거지?”).

```text
# 저자가 아는 최선의 요령
/^ *-a
```

그런데 **이것을 쓸 생각을 한 번도 못 하고 결국 `-a`가 나오는 모든 자리를 훑게 된다**고 적는다.

### 옵션마다 예제

`curl` man 페이지는 **모든 옵션에 예제**가 있고 HTML 판본에는 목차도 있다.

`--cert`의 예제를 보면 **`--key`도 함께 넘겨야 한다는 것을 쉽게 알 수 있다**는 것이다.

```bash
curl --cert certfile --key keyfile https://example.com
```

구현 방식은 **옵션마다 파일 하나**를 두고 그 파일에 “Example” 필드를 두는 것이다.

### 표로 데이터 보여 주기

꽤 많은 사람이 **`man ascii`**를 가장 좋아하는 man 페이지로 꼽았다고 한다.

```text
Oct   Dec   Hex   Char
───────────────────────────────────────
000   0     00    NUL '\0' (null character)
001   1     01    SOH (start of heading)
007   7     07    BEL '\a' (bell)
011   9     09    HT  '\t' (horizontal tab)
012   10    0A    LF  '\n' (new line)
```

특이한 man 페이지이지만 멋진 점이 **표 형식 덕분에 필요한 정보를 찾아 훑기가 아주 쉽다**는 것이며, man 페이지에서 정보를 표로 보여 줄 기회가 더 있을지 궁금해진다고 적는다.

### GNU 방식

GNU coreutils man 페이지(`man tail` 같은)에 예제가 없다는 이야기가 자주 나온다며, **꽤 정치적인 주제로 보여서 깊이 들어가지 않겠다**고 선을 긋는다.

다만 참이라고 믿는 것들을 나열한다.

**GNU 프로젝트는 man 페이지 대신 “info” 매뉴얼로 문서를 유지하기를 선호하며**, 어떤 페이지에는 “man 페이지는 더 이상 유지되지 않는다”고 적혀 있다.
info 매뉴얼을 읽는 방법이 셋(HTML, Emacs, 독립 `info` 도구)인데, **Emacs info 브라우저를 좋아한다는 사람은 들어 봤지만 독립 `info` 도구를 쓰는 사람과는 이야기해 본 적이 없는 것 같다**는 것이다.
`tail`의 info 매뉴얼 항목이 man 페이지 하단에 링크되어 있고 **거기에는 예제가 있다**.

그리고 균형 잡힌 관찰을 하나 남긴다.
**일정 복잡도를 넘으면 man 페이지가 정말 탐색하기 어려워진다**며, coreutils info 매뉴얼은 써 본 적 없고 앞으로도 안 쓸 것 같지만 **GNU Bash 레퍼런스 매뉴얼이나 GNU C 라이브러리 레퍼런스 매뉴얼은 man 페이지보다 HTML 문서로 보는 편을 거의 확실히 선호할 것**이라는 것이다.

### 인접한 도구들

fish 셸에 **man 페이지에서 탭 완성을 자동 생성하는 파이썬 스크립트**가 딸려 온다.
`tldr.sh`는 커뮤니티가 관리하는 예제 데이터베이스다.
Mac의 `Dash` 문서 브라우저에 목차가 있는 man 페이지 뷰어가 있다.

### 제약된 형식을 생각하는 것이 흥미롭다

마무리가 솔직하다.

man 페이지가 대단히 제약된 형식이라 **그런 제한된 서식 선택지로 무엇을 할 수 있을지 생각하는 것이 재미있다**는 것이다.

그리고 자기 한계를 밝힌다.
**글쓰기를 아주 좋아하는데도 문서를 절대 안 읽는 나쁜 습관이 있어서 man 페이지에서 자기가 실제로 무엇을 유용하게 여기는지 생각하기가 조금 어렵다**는 것이다.
**이 글에 적은 것 대부분이 자기 경험을 개선할지 아닐지 잘 모르겠다**고 적는다.

단 하나 예외를 둔다. **예제는 정말 사랑한다.**

## 분석

### 옵션 목록과 옵션 분류는 다른 종류의 문서다

이 글의 중심 질문이 **옵션을 알파벳순으로 둘 것인가 범주별로 묶을 것인가**인데, Lobste.rs 최고점 댓글이 그 질문 자체를 재구성했다.

fanf가 37점을 받았다.[^fanf]

먼저 관찰 하나를 던진다. **이 글의 모든 예제가 크고 복잡하게 뻗어 나간 프로그램의 man 페이지**라는 것이 눈에 띈다는 것이다.
놀랄 일은 아니라며, **그것들이 명확화가 가장 필요한 프로그램이고 jvns가 우리 모두에게 설명을 잘해 주는 바로 그 프로그램들**이기 때문이라고 짚는다.
그런데 자기는 **작은 프로그램의 man 페이지에 실망하는 경우가 많다**고 덧붙인다.

그리고 짧은 man 페이지를 훨씬 좋게 만드는 규칙들을 제시하는데, 그중 하나가 정렬 문제에 대한 답이다.

**주 레퍼런스에서는 옵션을 알파벳순으로 기술하는 것이 가장 좋다**는 것이다.
**기능이나 목적으로 순서를 잡는 것은 아주 어렵고 그 분류가 독자에게 유용한 경우가 드물다**는 것이다.

kwas가 반대했다.[^kwas-order]
다른 데는 다 동의하는데 그것만은 아니라며, **`yt-dlp`의 man 페이지가 꽤 복잡한 프로젝트에서 그것을 제대로 해낸 예**이고 일상 사용에 훨씬 쉽다는 것이다. `rg`도 좋은 예로 들었다.

fanf의 재반박이 이 논쟁의 값어치를 만든다.[^fanf-diataxis]

`yt-dlp`가 자기가 싫어하는 예라며 두 가지를 묻는다.
**각 절 안에서 옵션의 순서를 무엇이 정하는가.** 그리고 어떤 옵션이 여러 절에 들어갈 수 있을 때 **어느 절에 넣을지 어떻게 고르는가**.

그리고 자기가 알파벳순을 선호하는 이유를 문서 이론으로 설명한다.
**그 문서 부분의 목적과 관련이 있으며, Diátaxis 용어로 옵션의 주 목록은 레퍼런스 문서이고 옵션을 어떻게 분류하는가는 설명 문서**라는 것이다.
그러므로 **이것이 같은 요점을 서로 다른 목적을 가진 서로 다른 절에서 다른 스타일로 반복하는 것이 더 나은 좋은 예**라고 정리한다.

이 프레임이 저자의 질문을 해소한다.

저자가 `grep`의 `-l`을 못 찾겠다는 문제를 **분류로 풀려고** 했는데, fanf의 구분에 따르면 그 문제는 **두 문서가 다 필요하다**는 뜻이다.

| 목적                         | 형태      | 정렬     |
| ---------------------------- | --------- | -------- |
| `-l`이 무엇인지 안다, 찾는다 | 레퍼런스  | 알파벳순 |
| 파일명만 출력하고 싶다       | 설명·안내 | 범주별   |

그리고 `rsync`의 `OPTIONS SUMMARY`가 정확히 그 둘을 다 두는 형태다. 요약과 전체 설명을 별도 절로 나눈 것이다.

즉 **저자가 좋다고 꼽은 rsync 방식이 이미 fanf의 결론을 구현하고 있다**.

### 검색으로 옵션을 찾는 것이 왜 안 되는가

저자가 남긴 미해결 과제 — 특정 옵션을 찾는 보편적 방법 — 에 대해 Lobste.rs에서 짧지만 알찬 교환이 있었다.

IcePic이 알파벳순을 지지하며 이유를 댔다.[^IcePic]
옵션이 많은 프로그램에서 어떤 옵션이 무엇에 좋은지 찾으려 할 때 **절로 나뉘어 있으면 아주 어렵고**, **`-a`가 무엇을 하는지 알려고 “a”를 검색해서 맞기를 바랄 수는 없기 때문**이라는 것이다.

kwas가 반문했다. **앞에 공백을 붙여 `' -a'`로 검색하면 되지 않느냐**는 것이다.[^kwas-search]

iamnearlythere의 답이 이 교환의 핵심이다.[^iamnearlythere]

**자기가 man 페이지를 쓸 때마다 엄청나게 운이 없는 게 아니라면 이것은 그냥 안 통한다**는 것이다. 그리고 이유를 다섯 가지로 나열했다.

`DESCRIPTION`이나 `EXAMPLES`의 산문도 **“이 맥락에서 `-a`를 쓸 수 있다”** 같은 식으로 일치한다.
`SYNOPSIS`와 `EXAMPLES`가 **`tool -a -b -c`처럼 옵션을 포함**할 수 있다(운 좋게 `tool -bca`처럼 쓰였으면 피할 수 있다).
일부 프로그램은 **긴 형식 옵션에도 대시를 하나만 쓴다**(`find`가 예다).
PAGER에 따라 **`' -a'` 검색이 `' -A'`에 일치**할 수 있다(스마트 케이스 검색 등).
CLI가 **하위 명령에만 그 플래그가 적용되도록** 구성되어 있을 수 있다(`man git` 대 `man git log`).

이 목록이 저자의 문제를 정확히 진단한다.
`-a`라는 문자열이 man 페이지에서 **“옵션 정의”만을 가리키는 것이 아니라는 것**이 근본 원인이다.

그래서 저자가 아는 최선의 요령(`^ *-a`)이 **행 시작 위치를 정의의 표지로 쓰는 우회**인 것이고, 그것이 man 페이지마다 다른 서식 때문에 늘 통하지는 않는다.

### 이미 나온 해법이 있는데 널리 알려지지 않았다

저자가 “보편적인 시스템이 있으면 놀라울 것”이라고 적은 문제에 HN에서 구체적인 답이 나왔다.

SoftTalker가 짚었다.[^SoftTalker]
**OpenBSD가 man 페이지에 태그 파일을 두어서 `more(1)`이나 `less(1)`의 태그 탐색을 쓸 수 있게 한다**는 것이다.
**옵션에 특히 좋다**며 사용법을 보였다. 어떤 명령의 man 페이지를 보다가 `-k` 옵션이 무엇을 하는지 알고 싶으면 **`:t k`를 누르면 바로 그리로 간다**는 것이다.

이것이 저자가 찾던 바로 그것이다. 문자열 검색이 아니라 **구조화된 색인**이기 때문이다.

그리고 앞서 iamnearlythere가 나열한 다섯 가지 실패 이유가 전부 해소된다. 산문의 언급이나 예제의 사용례가 태그가 아니기 때문이다.

zahlman은 문제를 다른 층위로 옮겼다.[^zahlman]
저자의 그 문단을 인용하고 **어쩌면 우리에게 필요한 것은 더 나은 man 페이지 리더가 아닐까**라고 물었다.

이 제안이 OpenBSD 태그 파일과 짝을 이룬다.
**태그 파일은 man 페이지 쪽의 준비이고 `:t`는 리더 쪽의 기능**이므로, 양쪽이 다 있어야 동작한다.

즉 저자가 “man 페이지 형식이 제약되어 있다”고 본 문제의 일부가 **형식이 아니라 리더의 문제**다.
같은 맥락에서 저자가 좋게 평가한 Dash의 목차도 man 페이지를 바꾸지 않고 리더만 바꾼 것이다.

실용적으로 쓸 수 있는 것도 나왔다. wpollock이 옵션만 뽑아 보는 셸 함수를 올렸다.[^wpollock]

```bash
showoptions() {
  man -s 1 "$*" | col -bx | awk '/^[ ]*-/,/^$/' | less
}
```

모든 man 페이지에서 되지는 않지만 **옵션이 대시로 시작하는 대부분에서 통한다**는 단서를 달았다.

## 비평

### 정치적이라며 비껴간 GNU 문제에 실제로는 문서화된 근거가 있다

저자가 GNU coreutils man 페이지에 예제가 없는 문제를 **꽤 정치적인 주제로 보여서 깊이 들어가지 않겠다**고 했다.

그런데 HN에서 teddyh가 그것이 취향이나 정치가 아니라 **명시된 설계 원칙**임을 보여 줬다.[^teddyh]

man 페이지와 문서 조직에 대한 논의가 나올 때마다 인용하기 좋아하는 대목이 있다며 GNU 코딩 표준을 인용했다.

**프로그래머는 프로그램의 구조를 그 문서의 구조로 옮겨 오는 경향이 있다.** 그런데 **그 구조가 프로그램을 어떻게 쓰는지 설명하는 데 반드시 좋은 것은 아니며, 사용자에게 무관하고 혼란스러울 수 있다**는 것이다.
**대신 문서를 구조화하는 올바른 방법은 사용자가 그것을 읽을 때 마음에 품고 있을 개념과 질문에 따르는 것**이라고 적혀 있다.

이 인용이 논의의 성격을 바꾼다.

GNU가 man 페이지를 유지하지 않는 것이 게으름이나 파벌 싸움이 아니라, **명령 하나당 문서 하나라는 man 페이지의 구조 자체가 사용자의 질문 구조와 맞지 않는다는 판단**에서 나온 것이다.

그리고 이 판단에 일리가 있다는 것을 저자 자신이 인정하고 있다.
**Bash 레퍼런스 매뉴얼이나 glibc 레퍼런스 매뉴얼은 man 페이지보다 HTML로 보는 편을 선호할 것**이라고 적었기 때문이다.

그러면 진짜 쟁점이 드러난다.
**GNU의 진단이 큰 프로그램에 대해 옳고, 그 결론(man 페이지를 포기하고 info로 간다)을 작은 프로그램에까지 적용한 것이 문제**다.

`man tail`에 예제가 없는 것은 `tail`의 문서 구조가 사용자 질문과 안 맞아서가 아니다. **`tail`은 질문이 두세 개뿐인 프로그램**이고, OpenBSD가 보여 준 대로 예제 두 개면 끝난다.

fanf가 “작은 프로그램의 man 페이지에 실망하는 경우가 많다”고 한 것, 그리고 alper가 fanf의 “크고 복잡하게 뻗은 프로그램” 표현에 **“`tail` 같은?”**이라고 반문한 것이[^alper] 같은 지점을 가리킨다.

### 저자가 자기 판단을 신뢰하지 않는다고 밝힌 것이 이 글의 한계이자 정직함이다

이 글의 마지막 문단이 이례적이다.

**문서를 절대 안 읽는 나쁜 습관이 있어서 man 페이지에서 자기가 실제로 무엇을 유용하게 여기는지 생각하기가 어렵고, 이 글에 적은 것 대부분이 자기 경험을 개선할지 잘 모르겠다**는 것이다.

이 고백이 글의 신뢰도를 높이는 동시에 그 유용성을 제한한다.

높이는 쪽은 명확하다. **수집한 사례를 자기 선호로 포장하지 않았다.**
`grep` 실험에 대해서도 “결과가 어떤지 잘 모르겠다”고 적었고, 확신하는 것은 예제 하나뿐이라고 범위를 좁혔다.

제한하는 쪽도 명확하다. **어느 사례가 실제로 효과가 있는지에 대한 판단이 없다.**

그리고 이 한계가 [Git 문서 작업 글](../git/git-data-model-docs.md)의 방법론과 대비된다.

거기서 저자는 정확히 이 문제를 풀었다. **전문 사용자는 어떤 설명이 명확할지 판단하는 데 서투르므로 시험 독자 80명을 모았다.**

그런데 이 글에서는 그 방법을 쓰지 않았다. Mastodon에서 **“좋아하는 man 페이지”를 물었을 뿐**이다.

두 질문의 차이가 크다.

| 질문                             | 얻는 것                |
| -------------------------------- | ---------------------- |
| 좋아하는 man 페이지는?           | 선호. 기억에 남은 인상 |
| 이 man 페이지에서 어디서 막혔나? | 관찰. 구체적 실패 지점 |

저자 자신이 앞선 글에서 전자의 한계를 지적했는데, 여기서는 전자를 썼다.

물론 이 글이 “빠른 메모”이고 “생각의 아주 초기 단계”라고 밝혔으니 결함이라기보다 단계의 문제다.
다만 다음 단계가 무엇이어야 하는지는 저자가 이미 알고 있다는 점은 짚어 둘 만하다.

### 예제에 대한 합의가 압도적인데 원문이 그것을 충분히 밀지 않았다

이 글에서 유일하게 저자가 확신한 것이 예제이고, 댓글에서도 그것이 가장 일치된 의견이었다.

erock이 짧게 적었다. **man 페이지에 예제가 없으면 자기에게는 존재 목적이 거의 사라진다**는 것이다.[^erock]

NoSalt는 더 강하게 말했다.[^NoSalt]
저자가 인용한 “예제가 있는 man 페이지라면 뭐든 좋다”는 의견에 전적으로 공감하며, **man 페이지를 읽고 나서 도대체 누가 이 도구를 어떻게 쓰는지 알아냈을까 궁금해질 때가 있다**는 것이다.
그리고 **man 페이지에 아주 단순한 예제 한두 개를 넣는 것을 요구 사항으로 만들어야 한다**고 적었다.

여러 사람이 `tldr`을 대안으로 들었다.
victorstanciu는 `tldr ffmpeg`의 출력을 통째로 붙여 그 유용성을 보였고,[^victorstanciu] aphaelion도 큰 도구에 상대적으로 도움이 된다고 적었다.[^aphaelion]
ramses0는 `bropages`를 소개하며, man 페이지가 **“적당히 포괄적인 옵션 설명”**을 맡는다면 bro는 **“야, 네가 실제로 하려는 건 이거야”**에 집중하며 때로는 명령의 경계를 넘나든다고 정리했다.[^ramses0]

그런데 이 합의를 앞에 놓고 보면 원문의 구성이 아쉽다.

예제가 **여러 사례 중 하나**로 나열되어 있다. `OPTIONS SUMMARY`, 범주 분류, 치트 시트, 목차, 표와 나란히 놓인다.

합의의 강도로 보면 예제가 나머지와 같은 층위가 아니다.
**나머지는 “찾기 쉽게 만드는” 개선이고 예제는 “쓸 수 있게 만드는” 개선**이다.

그리고 oger의 댓글이 그 차이를 설명한다.[^oger]

자기는 **레퍼런스 문서를 원할 때만 man 페이지를 쓴다**는 것이다. 어떤 옵션이나 주제를 찾는지 이미 알고 있고 권위 있는 출처에서 전체 세부를 원할 때다.
그런데 **훨씬 많은 경우 도구를 배우려는 것이 아니라 구체적 문제를 풀려는 것이고, 어떤 도구를 쓰든 상관없다**는 것이다. 그래서 man 페이지를 읽기보다 대개 검색한다고 적었다.

이 구분이 이 글의 여러 제안을 갈라놓는다.
목차·태그·범주 분류는 레퍼런스 용도를 개선하고, **예제는 문제 해결 용도를 man 페이지 안으로 끌어온다**.

그리고 사용자 대부분이 후자의 상황에 있다면, 예제가 다른 모든 개선보다 우선한다.

### 형식을 바꾸자는 주장과 유지하자는 주장이 갈린다

저자가 **제약된 형식으로 무엇을 할 수 있을지 생각하는 것이 재미있다**고 맺었는데, 그 전제에 반대하는 의견도 나왔다.

eviks가 한 줄로 적었다. **더 나은 형식으로 교체하라**는 것이다.[^eviks]

kazinator는 다른 각도에서 물었다.[^kazinator]
`rsync`의 간결한 `SYNOPSIS`에 대해 **그런 표현은 명령 자체의 `--help`에 속하는데 왜 man 페이지에 그 형태로 반복하느냐**는 것이다.

ramon156은 반대 방향의 불만을 냈다.[^ramon156]
**`kubectl`의 man 페이지가 대체로 온라인 문서를 링크할 뿐이라 이상했다**며, **`man` 도구를 여는 데는 이유가 있고 그것은 온라인 문서를 읽지 않기 위해서**라고 적었다.

세 의견이 서로 다른 방향인데 공통 전제가 하나 있다.
man 페이지가 **무엇을 위한 것인지에 대한 합의가 없다**.

kazinator에게 man 페이지는 `--help`와 구별되는 무언가여야 하고, ramon156에게는 오프라인에서 완결되어야 하고, eviks에게는 대체되어야 하고, 저자에게는 제약 안에서 창의적일 수 있는 형식이다.

그리고 fanf가 제시한 Diátaxis 프레임이 이 혼란에 답을 준다. **man 페이지가 레퍼런스라면 무엇이 들어가야 하는지가 정해진다.**

그 기준에서 보면 kazinator의 지적이 반쯤 맞다. `--help`와 man 페이지가 둘 다 레퍼런스이면 중복이다.
다만 `--help`는 화면 한 장이고 man 페이지는 페이저이므로 **상세도가 다른 레퍼런스**라고 보면 중복이 아니다.

scruss가 반대편 극단을 하나 보여 줬다.[^scruss]
GNU coreutils의 info 스타일이 싫다면 **uutils coreutils(러스트 재작성)의 매뉴얼은 엉망으로 서식된 옵션 목록에 군데군데 빠진 부분이 섞여 있다**며, **완전한 쓰레기라고 부르기에도 부족하다**고 적었다.

즉 형식을 바꾸는 것만으로 좋아지지 않는다. 내용을 쓰는 일이 남기 때문이다.

## 인사이트

### 문서의 종류를 구분하지 않으면 정렬 논쟁이 끝나지 않는다

이 글의 중심 질문(알파벳순 대 범주별)이 답이 없어 보이는 이유가 fanf의 Diátaxis 지적으로 설명된다.

두 정렬이 서로 다른 질문에 답하고 있고, **그 질문들이 다른 종류의 문서에 속한다**.

| 사용자의 상태                      | 필요한 것 | 좋은 정렬 |
| ---------------------------------- | --------- | --------- |
| 이름을 안다, 의미를 모른다         | 레퍼런스  | 알파벳순  |
| 하고 싶은 일을 안다, 이름을 모른다 | 설명·안내 | 범주별    |

그리고 이 둘이 **양자택일이 아니라는 것**이 요점이다. fanf가 “같은 요점을 서로 다른 절에서 다른 스타일로 반복하는 것이 나은 예”라고 한 것이 그 말이다.

문서에서 반복을 피하려는 본능이 여기서 해롭게 작동한다.
같은 정보를 두 번 쓰는 것이 낭비처럼 보이지만, 두 독자가 다른 경로로 접근한다면 **두 입구가 필요하다**.

그리고 `rsync`가 저자에게 인상적이었던 이유도 이것으로 설명된다. **한 줄 요약 목록과 전체 설명을 별도 절로 나눈 것**이 두 입구를 만든 것이다.

일반화하면, 어떤 정보를 어떻게 배열할지가 논쟁이 될 때 대개 그 정보를 찾는 경로가 둘 이상이라는 뜻이고, **배열을 고르는 대신 경로를 둘 다 만드는 것**이 답이다.

그 비용은 유지보수다. 두 곳을 갱신해야 하므로 **생성 도구가 없으면 곧 어긋난다**.
`curl`이 옵션마다 파일 하나를 두고 거기서 목록과 상세를 함께 생성하는 것이 그 문제의 해법이다.

### 형식의 제약이라고 생각한 것 중 일부는 도구의 제약이다

저자가 man 페이지를 **제약된 형식**으로 규정하고 그 안에서 무엇을 할 수 있을지 묻는다.

그런데 이 글이 다룬 문제들을 나눠 보면 층이 섞여 있다.

| 문제                    | 어디의 제약인가 | 해법 사례           |
| ----------------------- | --------------- | ------------------- |
| 옵션 하나를 찾기 어렵다 | **리더**        | OpenBSD 태그 + `:t` |
| 어떤 절이 있는지 모른다 | **리더**        | Dash 목차, HTML TOC |
| 예제가 없다             | **내용**        | OpenBSD, curl       |
| 서식 선택지가 적다      | 형식            | 표, ASCII 치트 시트 |

**앞의 둘이 형식 문제가 아니다.** man 페이지 소스에는 절 구조와 옵션 정의가 이미 구조로 들어 있고, 그것을 쓰지 않는 것은 `man`과 페이저다.

그리고 이 구분이 실행 가능성을 바꾼다.
형식을 바꾸려면 수십 년 치 문서를 고쳐야 하지만, **리더를 고치면 기존 문서가 그대로 좋아진다**.

zahlman이 “더 나은 man 페이지 리더가 필요한 것 아니냐”고 한 것과 저자가 Dash 목차를 좋게 평가한 것이 같은 곳을 가리킨다.

일반화하면, “이 형식으로는 X를 할 수 없다”는 판단을 만났을 때, **형식에 X를 위한 정보가 이미 들어 있는데 도구가 쓰지 않는 것은 아닌지** 먼저 봐야 한다.

man 페이지가 좋은 예다. roff 매크로에 **의미론적 표시**가 들어 있다. fanf가 “mdoc 매크로를 쓰라”고 권한 이유가 그것이다. 무엇이 옵션이고 무엇이 파일명인지가 마크업에 있는데, 터미널 렌더링이 그것을 굵게와 밑줄로 뭉개 버린다.

즉 **정보는 있고 표현 단계에서 버려진다**.

### 자기 사용 패턴을 모르면 남의 선호를 수집해도 설계가 되지 않는다

저자가 마지막에 밝힌 것이 이 글의 가장 정직한 부분이면서 방법론적 교훈이다.

**문서를 잘 안 읽어서 man 페이지에서 자기가 무엇을 유용하게 여기는지 생각하기 어렵다**는 것이다.

그리고 그 결과가 글에 드러난다. 사례는 풍부한데 **우선순위가 없다**.

무엇이 부족했는가.

Mastodon에서 물은 것이 **“좋아하는 man 페이지”**였다. 이것은 **기억에 남은 인상**을 수집한다.
필요했던 것은 **“최근에 man 페이지에서 무엇을 찾다가 실패했는가”**다. 이것은 **실제 사용 패턴**을 수집한다.

둘의 차이가 결과를 갈랐다.
`man ascii`가 여러 번 꼽혔는데, 저자도 인정하듯 **아주 특이한 man 페이지**다. 좋아하기는 쉬운데 그 교훈을 `grep`에 옮기기는 어렵다.

반면 oger의 댓글 — 자기는 레퍼런스를 원할 때만 man 페이지를 쓰고 문제 해결에는 검색한다 — 이 설계에 직접 쓸 수 있는 정보다. **사용 상황을 말하기 때문**이다.

일반화하면, 무엇을 만들지 정하려고 사람들에게 물을 때 “무엇을 좋아하는가”는 취향을 주고 **“최근에 무엇을 하려다 실패했는가”는 요구사항을 준다**.

그리고 저자가 이것을 모를 리 없다. [Git 문서 작업](../git/git-data-model-docs.md)에서 정확히 후자를 물어 80명에게서 구체적 실패 지점을 받았기 때문이다.

차이는 그때는 **고칠 대상이 정해져 있었다**는 것이다. Git man 페이지 네 개였다.
이 글에서는 대상이 “man 페이지 일반”이라 물을 구체적 대상이 없었다.

여기서 나오는 규칙이 하나 있다.
설계를 위한 조사는 대상이 좁을수록 잘 작동하고, **대상이 넓으면 취향 수집으로 퇴화한다**.

그래서 이 글이 “빠른 메모”에 머문 것이 자연스럽고, 다음 단계는 사례를 더 모으는 것이 아니라 **man 페이지 하나를 골라 그것에 대해 묻는 것**이다.
