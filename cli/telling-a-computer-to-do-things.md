# 컴퓨터에게 일을 시킨다는 것

원문: [Telling a Computer to Do Things](https://will-keleher.com/posts/telling-your-computer-to-do-things/)

## 요약

Will Keleher가 셸을 익히기 전과 후의 차이를 회고하는 글이다.
경력 초기 몇 해 동안 자신은 컴퓨터에게 일을 시킬 줄 몰랐다고 말하며 시작한다.

터미널에서 명령 몇 개는 띄울 수 있었다.
테스트를 돌리고, 의존성을 설치하고, 컨테이너를 띄우고, 다른 기계에 접속하는 정도다.
그러나 한 번에 단순한 명령 하나씩만 실행할 수 있었다.
저자의 표현이 그 상태를 정확히 담는다.
자기 터미널은 세상에서 가장 나쁜 GUI였고,
셸이란 응용 프로그램 껍데기가 없는 프로그램을 시작하는 방법이라고 여겼다는 것이다.

근본적으로 그는 논리나 여러 프로그램의 결합이 필요한 일을 시킬 수 없었다.

- 하나를 하고 그다음에 다른 것을 하기
- 명령이 실패하면 오류 메시지 남기기
- 컴퓨터가 켜질 때 프로그램 띄우기
- 두 명령을 동시에 돌리기
- 디렉터리의 모든 파일을 훑으며 각각에 작업하기
- 한 명령의 출력을 다른 명령의 입력으로 쓰기

이론적으로는 NodeJS로 이런 프로그램을 쓸 수 있었지만 실제로는 한 번도 그러지 않았다.
저자는 이유를 둘로 나눈다.
절반은 사고방식이었다.
명령줄에서 쓰는 프로그램들을 자기가 통제할 수 있는 대상으로 생각하는 데 익숙하지 않았다는 것이다.
나머지 절반은 기술 부족이었다.
자기가 쓰는 프로그램들을 자기 스크립트에 엮어 넣을 만큼 잘 알지 못했다.

## 첫 스크립트와 그 결함

그래도 계속 셸을 배우려 했고, 기본적인 논리가 들어간 스크립트를 더듬거리며 쓸 수 있게 되었다.

```bash
set +e
npm install
status_code=$?
if [[ "$status_code" != "0" ]]; then
    echo "Something went wrong with your npm install. Check your ~/.npmrc to make sure it's authed to our registry."
    exit 1
fi
set -e
```

저자는 셸에 익숙한 독자라면 지금쯤 헛소리를 웅얼거리고 있을지 모르겠다고 농담한 뒤,
각주에서 이 코드가 왜 나쁜지를 스스로 설명한다.

핵심은 `if`의 본래 동작을 몰랐다는 것이다.
`if`는 명령을 받는 것이 주된 방식이고 `[[`나 `test`는 그저 특수한 명령일 뿐이다.
그 사실을 알면 검사는 그냥 `! npm install`이면 된다.

```bash
if ! npm install; then
    echo "Something went wrong with your npm install. Check your ~/.npmrc to make sure it's authed to our registry."
    exit 1
fi
```

이렇게 쓰면 명령 실패를 허용하려고 `set +e`를 켤 필요가 없어지고,
`$?`로 종료 코드를 따로 잡을 필요도 없어진다.
`set +e`와 `set -e`를 오가는 것은
명령 하나가 실패했다고 스크립트 전체가 죽는 것을 피하려는 장치인데, 애초에 필요가 없어지는 셈이다.

그럼에도 저자는 그 어설픈 스크립트가 자신에게 변혁이었다고 말한다.
기존 프로그램들을 엮어 자기 목적을 이루라고 컴퓨터에게 시킬 수 있게 된 것이,
처음 프로그래밍을 배웠을 때의 변화와 조금 비슷하게 느껴졌다는 것이다.

## GUI에 갇히는 문제

저자는 셸에 시간을 덜 쓴 대단히 뛰어난 엔지니어들과 많이 일해 봤다고 말한다.
그들은 테스트 실행, git 관리, 데이터베이스 접속, 일상 작업을 GUI로 처리한다.

GUI에 의존하는 것은 GUI가 상정하지 않은 일을 하려 할 때까지는 잘 동작한다.
문제는 그다음이다.
자신이 할 수 있는 일이 GUI가 할 수 있는 일로 제한되는 사고방식에 빠지기 쉽다는 것이다.
저자는 능숙한 엔지니어들이 `while`로 명령을 반복하는 법이나
디렉터리의 모든 파일에 같은 작업을 하는 for 루프를 몰라서
엄청난 노력을 쏟는 것을 봤다고 적는다.

같은 GUI 중심 태도가 셸 스크립트를 고치고 유지하는 데에서도 문제가 된다.
대부분의 회사에는 빌드, 배포, 코드 검증, 테스트를 위한 필수 로직이
Bash나 Zsh로 상당량 쓰여 있을 것이다.
도구가 쓰인 언어에 익숙하지 않으면 그것을 읽거나 개선할 수 없다.
저자의 정리가 뼈아프다.
코드가 돌아가는 원격 서버에게는 어떻게 행동하라고 지시할 수 있으면서
정작 자기가 쓰는 컴퓨터에게는 린트와 테스트를 병렬로 돌리라고 시키지 못하는 상태라는 것이다.

## 왜 하필 셸인가

저자는 여기서 잠시 옆길로 빠져 묻는다.
왜 그렇게 많은 스크립트가 팀이 주로 쓰는 언어가 아닌 언어로 쓰이는가.

답은 명령을 엮기 쉽도록 설계된 언어에서 명령을 엮는 스크립트를 쓰는 편이
대체로 더 편하기 때문이라는 것이다.
테스트가 실패할 때까지 반복 실행하는 아주 단순한 예로 비교한다.

```bash
while pnpm exec mocha ./pathToFile.test.ts; do true; done
```

```javascript
const { execSync } = require("child_process");
while (true) {
    try {
        // stdio: inherit가 없으면 테스트 출력이 보이지 않는다
        execSync(`pnpm exec mocha ./pathToFile.test.ts`, { stdio: "inherit" });
    } catch (err) {
        console.error("failed", err);
        break;
    }
}
```

저자는 셸 쪽이 더 쉽다고 본다.
파일을 만들 필요도, `child_process`를 불러올 필요도,
출력을 보려고 `{ stdio: "inherit" }`를 설정할 필요도 없기 때문이다.
게다가 이 예시는 파이프로 여러 프로그램을 엮지도, 출력을 잡지도, 임시 파일을 쓰지도 않는 단순한 경우다.

다만 Bash나 Zsh에 스스로를 가둘 필요는 없다고 덧붙인다.
JavaScript를 잘 아는 팀에는 zx가 쓸 만하고,
Ruby와 Python은 NodeJS보다 쉬우며,
이런 작은 스크립트를 쓰는 데 더 많은 격식을 요구하는 언어도 많다는 것이다.

그리고 균형을 잡는다.
빌드 스크립트에 셸이 언제나 쉽다고 주장하는 것은 아니며,
프로그램 둘을 엮는 정도로 단순한 문제에서 셸이 편할 뿐이다.
더 정교한 논리와 자료형이 필요해지는 순간,
그것을 표현하고 시험하기 쉬운 언어를 골라야 한다.

이어지는 관찰이 날카롭다.
빌드 스크립트가 셸로 쓰였다고 불평하는 엔지니어 상당수가
실제로 그것을 다른 언어로 옮겨 본 적이 없으리라는 것이다.
문법이 더 복잡해질 수 있다는 점을 빼더라도,
셸 스크립트를 배운다는 일의 큰 부분은 사실 문법이 아니다.
명령을 엮는 스크립트를 옮겨 적으면서 그 명령들이 어떻게 동작하는지 모른다면,
결과물도 똑같이 알아보기 어려운 스크립트가 된다.

## 셸은 문법 20퍼센트, 도구 80퍼센트

저자의 핵심 주장이 여기 있다.
컴퓨터에게 일을 시킬 수 있다는 것은
하고 싶은 일을 해 주는 프로그램들에 대한 지식에 크게 달려 있으며,
셸을 안다는 것은 문법 20퍼센트와 좋은 도구 상자 80퍼센트라는 것이다.

| 도구                 | 열리는 능력                                                       |
| -------------------- | ----------------------------------------------------------------- |
| `fzf`                | 대화형 퍼지 검색을 붙인 작은 유틸리티를 만든다                    |
| `tldr`, `eg`         | 다른 명령의 사용 예시를 바로 꺼낸다                               |
| `rsync`              | 바뀐 파일만 빠른 원격 서버로 옮겨 무거운 작업을 돌린다            |
| `xargs`              | 명령을 점진적으로 쌓고 작업을 병렬화한다                          |
| `sed -i`, `ast-grep` | 복잡한 패턴을 여러 파일에 걸쳐 고쳐 쓴다                          |
| `direnv`             | 코드베이스에서 명령을 돌리는 모두에게 올바른 환경 변수를 보장한다 |
| `duckdb`             | 로컬 CSV와 JSON에 SQL을 던지는 단계를 스크립트에 넣는다           |
| `gh`                 | PR 상태를 확인하고 새 PR을 여는 스크립트를 만든다                 |
| `ngrok`              | 로컬 포트를 다른 기계에서 시험할 수 있게 연다                     |

`fzf` 예시가 이 표의 취지를 잘 보여 준다.

```bash
# 최근 커밋 순으로 브랜치를 나열하고 퍼지 검색으로 고른다
git checkout $(git branch --sort=-committerdate | fzf)
```

저자가 강조하는 것은 곱셈 효과다.
새로 배우는 프로그램 하나하나가 이미 아는 모든 도구와 함께 쓰일 수 있기 때문에,
도구를 하나 더 알 때마다 능력이 더 크게 늘어난다.

글은 겸손으로 끝난다.
자신은 셸 스크립팅 전문가와는 세상에서 가장 먼 사람이고
깊이 아는 사람들에 비하면 형편없지만,
프로그램을 엮을 만큼의 문법과 엮고 싶은 프로그램들을 아는 것만으로 많은 값어치를 얻었다는 것이다.

각주에서 저자는 이전 글에 달렸던 Hacker News 댓글 하나를 자조적으로 인용한다.
이 글과 댓글난을 보니 자기가 마주치는 셸 스크립트의 99퍼센트가
왜 서투르게 보이는지 더는 궁금하지 않다는 Arch-TK의 말이다.[^Arch-TK]
그 댓글은 이어서 구체적인 지적을 한다.
빌드를 깨뜨린 커밋을 찾으려고 선형 for 루프를 쓸 필요를 느꼈다면 그것은 `git bisect`가 필요했던 것이고,
PID를 그런 식으로 기다리지 말고 Bash가 제공하는 배열을 쓰라는 것이고,
변수에 넣어 단어 분리에 의존하는 쪽이 오히려 덜 명확하다는 것이고,
무엇보다 인용을 하라는 것이다.

## 비평

### 자조가 반복되면서 주장의 힘을 깎는다

이 글은 자신이 셸을 못한다는 고백으로 시작해
전문가와는 세상에서 가장 멀다는 고백으로 끝나고,
중간에 자기 코드가 왜 나쁜지를 각주로 설명하고,
마지막에는 자기를 비판한 댓글까지 인용한다.

이 태도는 호감을 사고 진입 장벽을 낮추지만 대가가 있다.
글의 실질적 주장, 즉 셸 지식의 80퍼센트가 도구 상자라는 명제는
초보자의 소감이 아니라 검증할 수 있는 주장인데
자조의 틀 안에 놓이면서 개인 경험담으로 축소된다.

실제로 그 명제는 논쟁의 여지가 있다.
Arch-TK가 지적한 문제들, 즉 인용 누락과 단어 분리 의존과 종료 코드 처리는
전부 문법 쪽 지식이고 도구를 더 안다고 해결되지 않는다.
그 댓글을 인용하면서도 그것이 자기 20 대 80 비율에 대한 반례라는 점을 저자는 짚지 않는다.
인용이 반박을 수용하는 제스처로만 쓰이고 논의로 이어지지 않는다.

### GUI 사용자를 능력이 아니라 사고방식의 문제로 진단한다

GUI에 의존하면 할 수 있는 일이 GUI의 능력으로 제한되는 사고방식에 빠지기 쉽다는 진단은
절반만 맞다.

GUI가 제공하는 것 중 셸이 잘 주지 못하는 것이 있다.
발견 가능성이다.
메뉴를 열면 무엇이 가능한지 보이지만, 셸에서는 존재를 모르는 도구를 검색할 수 없다.
저자 자신이 제시한 도구 목록이 바로 이 문제의 증거다.
`ast-grep`이나 `duckdb`나 `direnv`가 있다는 사실을 모르면
그것으로 풀 수 있는 문제를 계속 손으로 푼다.

그렇다면 처방은 사고방식을 바꾸라는 것이 아니라
도구의 존재를 알게 되는 경로를 만드는 것이다.
저자가 목록에 `tldr`을 넣은 것은 그 방향의 실마리인데,
그 도구가 해결하는 것은 이미 이름을 아는 명령의 사용법이지 이름을 모르는 도구의 발견이 아니다.
글이 이 구별을 하지 않는다.

### 셸과 다른 언어의 비교가 가장 유리한 예시 하나에 기대어 있다

테스트를 반복 실행하는 예시에서 셸은 한 줄이고 NodeJS는 열 줄이다.
이 대비는 인상적이지만 저자가 고른 것은 셸이 가장 잘하는 종류의 작업이다.
외부 명령을 돌리고, 종료 코드만 보고, 출력은 그대로 흘려보내는 작업이다.

같은 비교를 조금만 바꾸면 결과가 뒤집힌다.
여러 명령의 출력을 구조화된 자료로 모으고,
실패를 분류해 요약을 만들고, 그 결과를 JSON으로 내보내는 작업이라면
셸에서는 임시 파일과 문자열 조작이 쌓이고 NodeJS나 파이썬 쪽이 훨씬 짧아진다.

저자도 정교한 논리와 자료형이 필요해지면 다른 언어를 고르라고 적으므로 결론 자체는 균형 잡혀 있다.
다만 그 경계가 어디인지는 말하지 않는다.
실무적으로 쓸 만한 기준은 하나 제시할 수 있다.
중간 결과를 변수에 담아 나중에 다시 다뤄야 하는 순간이 오면 셸을 떠날 때다.
문자열 하나로 흘려보낼 수 있는 동안에는 셸이 이긴다.

## 체크리스트

- 자주 하는 수작업 중 반복문이나 조건문 하나면 끝나는 것이 있는가?
- 팀의 빌드와 배포 스크립트를 읽고 고칠 수 있는가?
- `if`에 명령을 직접 넣을 수 있다는 것을 알고 있는가?
- 변수 확장에 인용을 빠뜨리지 않았는가?
- 새 도구를 알게 되는 경로가 있는가? 아니면 아는 도구만 반복해 쓰고 있는가?
- 중간 결과를 변수에 담아 다시 다루기 시작했다면, 다른 언어로 옮길 때가 아닌가?

## 기억할 원칙

### 능력은 문법이 아니라 도구 목록에서 곱해진다

도구를 하나 더 알 때 능력이 하나만큼 늘지 않고 더 크게 느는 이유는
새 도구가 이미 아는 모든 도구와 조합될 수 있기 때문이다.
파이프와 명령 치환이 그 조합을 만드는 접착제이고,
그래서 셸 문법의 핵심은 사실 몇 가지뿐이다.

이 관점은 학습 순서를 정해 준다.
셸 문법서를 끝까지 읽는 것보다 자주 마주치는 문제 하나를 골라
그것을 푸는 도구를 익히는 편이 빠르고,
그렇게 익힌 도구는 다음 문제에서 다시 쓰인다.
반대로 문법만 쌓으면 엮을 것이 없어서 쓸 일이 생기지 않는다.

### 자기가 쓰는 기계에게 일을 시킬 수 없는 상태를 방치하지 않는다

원격 서버의 동작은 코드로 지시할 수 있으면서
자기 노트북에게는 같은 일을 시키지 못하는 상태가 실제로 흔하다.
그 격차는 대개 눈에 띄지 않는다.
손으로 하는 일은 일정에 잡히지 않고, 그래서 비용도 집계되지 않기 때문이다.

이 격차를 줄이는 첫걸음은 거창한 자동화가 아니라
이번 주에 세 번 이상 손으로 한 일이 무엇이었는지 적어 보는 것이다.
대부분은 반복문 하나나 파이프 하나로 끝나는 일이고,
그것을 한 번 해 보면 다음 문제에서 같은 발상이 먼저 떠오르게 된다.
