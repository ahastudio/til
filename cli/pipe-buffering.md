## 요약

Julia Evans가 2024년 11월 29일에 쓴 글이다.

증상이 아주 구체적이다.

```bash
tail -f /some/log/file | grep thing1 | grep thing2
```

로그 줄이 비교적 느리게 추가되고 있으면 결과가 **아무것도 없다**. 파일에 매치가 있든 없든 출력이 나오지 않는다.

저자는 이것을 **“음, 파이프가 가끔 멈춰서 출력을 안 보여 주는구나, 이상하네”**라고 내면화하고, 대신 `grep thing1 /some/log/file | grep thing2`를 돌려 해결해 왔다고 밝힌다.
그러다 몇 달간 터미널을 깊이 파면서 드디어 정확한 이유를 알게 되어 신났다는 것이다.

### 파이프가 멈춘 것이 아니다

원인은 버퍼링이다.

프로그램이 파이프나 파일에 쓰기 전에 출력을 버퍼에 모으는 것이 **매우 흔하다**.
그러니 **파이프는 멀쩡히 동작하고 있고, 문제는 프로그램이 애초에 데이터를 파이프에 쓰지도 않았다는 것**이다.

성능 때문이다. 할 수 있는 즉시 모든 출력을 쓰면 시스템 콜을 더 많이 쓰게 되므로, 8KB 정도가 모일 때까지(또는 프로그램이 종료할 때까지) 저장해 두었다가 쓰는 편이 효율적이다.

위 예에서는 **`grep thing1`이 8KB가 될 때까지 매치를 모으고 있고, 그런 일이 말 그대로 영원히 일어나지 않을 수도 있다**.

### 터미널에 쓸 때는 버퍼링하지 않는다

저자가 이것을 특히 혼란스러워한 이유가 있다. `tail -f file | grep thing`은 완전히 잘 되는데 **두 번째 `grep`을 붙이면 멈춘다**는 것이다.

`grep`이 버퍼링을 결정하는 방식이 이렇다.

```text
1. isatty 함수로 stdout이 터미널인지 확인한다
2. 터미널이면 줄 버퍼링 (한 줄이 생기는 즉시 출력)
3. 아니면 블록 버퍼링 (8KB 정도 모여야 출력)
```

버퍼 크기가 늘 8KB인 것은 아니고 구현에 달렸다. `grep`의 버퍼링은 libc가 처리하고 libc의 버퍼 크기는 `BUFSIZ`에 정의되어 있다.

저자가 여기에 단서를 하나 단다.
**“프로그램이 터미널에 쓸 때 8KB 출력 버퍼를 쓰지 않는다”는 것이 터미널 물리 법칙 같은 것은 아니며**, 원한다면 그렇게 할 수도 있지만 그러면 지극히 이상할 것이고 그렇게 동작하는 프로그램을 떠올릴 수 없다는 것이다.

## 어떤 명령이 버퍼링하는가

이 버퍼링 동작에서 성가신 점 하나가 **어떤 명령이 파이프에 쓸 때 버퍼링하는지 기억해야 한다**는 것이다.

버퍼링하지 **않는** 명령은 `tail`, `cat`, `tee`다.

나머지는 거의 전부 버퍼링하며, 특히 일괄 처리에 쓸 법한 명령이라면 그렇다.

| 명령      | 블록 버퍼링을 끄는 플래그 |
| --------- | ------------------------- |
| `grep`    | `--line-buffered`         |
| `sed`     | `-u`                      |
| `awk`     | `fflush()` 함수           |
| `tcpdump` | `-l`                      |
| `jq`      | `-u`                      |
| `tr`      | `-u`                      |
| `cut`     | **끌 수 없다**            |

`sort` 같은 명령은 버퍼링할 수도 있고 아닐 수도 있지만 **어차피 입력을 다 받기 전에는 아무것도 할 수 없으므로 상관없다**고 덧붙인다.

프로그래밍 언어의 기본 출력 함수도 마찬가지다.

| 언어   | 버퍼링을 끄는 법                                          |
| ------ | --------------------------------------------------------- |
| C      | `setvbuf`                                                 |
| Python | `python -u`, `PYTHONUNBUFFERED=1`, `print(x, flush=True)` |
| Ruby   | `STDOUT.sync = true`                                      |
| Perl   | `$OUTPUT_AUTOFLUSH = 1`                                   |

Perl의 경우 원문이 적은 것은 `$OUTPUT_AUTOFLUSH`의 축약형인 특수 변수 쪽이다. `use English;` 없이 쓰는 그 형태가 파이프를 뜻하는 기호를 이름으로 쓴다.

저자는 이 언어들이 **일괄 처리를 할 때 기본 출력 함수가 빠르도록** 설계된 것이라고 추정한다.

그리고 출력 방식에 따라서도 달라진다. C++에서 `cout << "hello\n"`은 파이프에 쓸 때 버퍼링하지만 `cout << "hello" << endl`은 출력을 플러시한다.

## `Ctrl-C`를 누르면 버퍼 내용이 사라진다

DNS 요청을 지켜보려고 `-l`을 빠뜨린 채 이렇게 돌렸다고 하자.

```bash
sudo tcpdump -ni any port 53 | grep example.com
```

`Ctrl-C`를 누르면 마법 같은 완벽한 세상에서는 `tcpdump`가 버퍼를 플러시하고 `grep`이 검색해 놓친 출력을 다 보여 줄 것이다.

현실에서는 **모든 프로그램이 죽고 `tcpdump` 버퍼의 출력은 사라진다**.

저자가 `strace`로 확인한 바로는 **`grep`이 `tcpdump`보다 먼저 `SIGINT`를 받으므로**, `tcpdump`가 버퍼를 플러시하려 해도 `grep`은 이미 죽어 있다.

우회로는 있다. `tcpdump`의 PID를 찾아 `kill -TERM $PID`를 하면 버퍼를 플러시해 출력을 볼 수 있다는 것이다. 번거롭지만 시험해 보니 동작한다고 밝힌다.

파일로 리디렉션해도 버퍼링되지만, 이쪽은 `Ctrl-C`가 버퍼를 완전히 파괴하는 문제가 없다. 저자 경험상 대체로 종료 전에 버퍼 내용이 파일에 쓰이는데, 늘 그럴 것이라고 믿어도 되는지는 100% 확신하지 못한다고 적는다.

## 다섯 가지 해법

저자가 Mastodon에서 물어본 결과 다섯 가지 접근이 나왔다.

```bash
# 해법 1: 빨리 끝나는 프로그램을 쓴다 (문제를 회피)
cat /some/log/file | grep thing1 | grep thing2 | tail

# 해법 2: grep의 줄 버퍼 플래그를 기억한다
tail -f /some/log/file | grep --line-buffered thing1 | grep thing2

# 해법 3: awk 하나로 합친다 (awk가 마지막이어야 한다)
tail -f /some/log/file | awk '/thing1/ && /thing2/'
tail -f /some/log/file | grep -E 'thing1.*thing2'

# 해법 4: stdbuf (LD_PRELOAD로 libc 버퍼링을 끈다)
tail -f /some/log/file | stdbuf -o0 grep thing1 | grep thing2

# 해법 5: unbuffer (출력을 TTY로 만든다)
tail -f /some/log/file | unbuffer grep thing1 | grep thing2
```

각각의 대가가 다르다.

`stdbuf`는 `LD_PRELOAD` 방식이라 다소 불안정하다. **정적 바이너리에서 안 되고, 프로그램이 libc 버퍼링을 쓰지 않으면 안 되며, macOS에서 늘 되지는 않는다**.

`unbuffer`는 `stdbuf`와 달리 **언제나 동작**하지만 원치 않는 부작용이 있을 수 있다. 예를 들어 `grep thing1`이 매치에 색도 입힌다. `expect` 패키지에 들어 있다.

저자는 **언제나 동작한다는 것을 알기 때문에 `unbuffer`를 가장 많이 쓸 것 같다**고 정리한다.

### 표준 환경 변수가 있으면 좋겠다

저자가 제안을 하나 던진다.
Python의 `PYTHONUNBUFFERED`처럼 **버퍼링을 끄는 표준 환경 변수가 있으면 멋질 것 같다**는 것이다. `NO_COLOR`처럼 `NO_BUFFER`는 어떻겠냐고 묻는다.

다만 설계를 제대로 하기가 까다로워 보인다고 덧붙인다. NetBSD에 `STDBUF`, `STDBUF1` 같은 환경 변수가 있어 버퍼링을 세밀하게 제어할 수 있지만, 대부분의 개발자가 **비교적 사소한 엣지 케이스를 위해 여러 환경 변수를 구현하고 싶어 하지는 않을 것** 같다는 것이다.

그리고 궁금한 것을 하나 남긴다. **일정 시간(1초 같은)이 지나면 자동으로 버퍼를 플러시하는 프로그램이 있는지**다. 이론적으로 좋을 것 같은데 그렇게 하는 프로그램을 떠올릴 수 없으니 단점이 있을 것 같다는 것이다.

이 질문이 댓글에서 가장 활발한 논의를 낳았다.

## 비평

### 저자가 틀린 예를 실었고 그 자리에서 고쳤다

이 글의 초기 버전에 사실 오류가 있었다.

masklinn이 Lobste.rs에서 짚었다.[^masklinn]

원문이 “Rust에서 `print!`는 파이프에 쓸 때 버퍼링하지만 `println!`은 출력을 플러시한다”고 적었는데, **자기가 아는 한 이것이 맞지 않다**는 것이다.
**Rust의 stdout은 (현재로서는) 언제나 줄 버퍼링**이며, `println!`이 언제나 개행을 붙이므로 암묵적으로 플러시하는 것처럼 보일 뿐이고 `print!`로 개행을 출력해도 같은 결과가 나온다는 것이다.
엄밀히 말해 그것은 함수의 명시적 동작이 아니라 **출력되는 데이터와 스트림 설정의 상호작용**이라는 정리다.

저자가 바로 답했다.[^jvns]
**소셜 미디어에서 누가 말해 준 것을 직접 시험해 보지 않고 믿은 대가**라며, 이 글의 대부분을 확인하려 했지만 이건 놓쳤다고 인정했다.
시험해 보니 말한 대로 둘 다 줄 버퍼링이었고, **자기가 실제로 시험해서 참인 것으로 글을 고쳤다**고 밝혔다.

지금 글에 C++ 예제가 들어 있는 것이 그 결과다.

이 교환이 값진 이유가 두 가지다.

정정 자체가 유용하다. **Rust에서 버퍼링 문제가 덜 생기는 이유**를 알려 주기 때문이다. 줄 버퍼링이 기본이면 이 글이 다루는 증상이 애초에 잘 안 나타난다.

그리고 실수의 출처가 명확히 밝혀졌다. 저자가 이 글의 여러 부분을 사람들에게 물어 만들었고 — 다섯 가지 해법도 Mastodon에서 모은 것이다 — **그중 하나가 검증을 통과하지 못했다**.

크라우드소싱한 기술 정보의 전형적인 실패 모드이고, 그것을 공개적으로 수정한 것이 모범적인 대응이다.

### “cat은 버퍼링하지 않는다”도 확실하지 않다

BoingBoomTschak이 더 근본적인 지적을 했다.[^BoingBoomTschak]

버퍼링하지 않는 명령 목록에 대해 이것이 **구현 의존적이거나 `cat`의 경우 아예 틀렸다**는 것이다. POSIX 규격에 `cat`의 `-u` 플래그가 있다는 점을 근거로 든다.
그리고 **POSIX가 이것을 관리하는 공식적인 방법을 한 번도 포함하지 않은 것이 엄청난 고통**이라고 적었다.

`-u`가 존재한다는 사실 자체가 `cat`이 기본적으로 버퍼링할 수 있다는 뜻이다. 실제로 GNU coreutils의 `cat`은 `-u`를 받아들이지만 무시한다(항상 버퍼링하지 않으므로). 그러나 다른 구현은 다를 수 있다.

같은 댓글에서 **입력 버퍼링**도 짚었는데, 이것이 글에서 완전히 빠진 부분이다.

```bash
$ seq 5 | { v1=$(head -1); v2=$(head -1); printf '%s=%s\n' v1 "$v1" v2 "$v2"; }
v1=1
v2=
```

첫 `head`가 필요한 한 줄보다 훨씬 많이 읽어 버려서 두 번째 `head`에게 남는 것이 없다.

```bash
# 고치는 법
seq 5 | { v1=$(stdbuf -i0 head -1); v2=$(stdbuf -i0 head -1); ... }
```

이 사례가 중요한 이유는 **출력 버퍼링은 출력이 늦게 나오는 문제인 반면 입력 버퍼링은 데이터가 사라지는 문제**이기 때문이다. 후자가 훨씬 위험하다.

글이 “빠뜨린 것” 목록에 입력 버퍼링을 넣지 않았다.

### 버퍼링을 끄는 것과 줄 버퍼링이 혼동되어 있다

o11c가 이 글의 개념 구분을 문제 삼았다.[^o11c]

이 글이 **“버퍼링 없음”과 “줄 버퍼링” 두 가지를 혼동하고 있다**는 것이다.

버퍼링을 완전히 끄면 공연히 성능이 나빠지고, **여러 소스가 같은 파이프에 쓰고 있으면 잘못된 출력이 나올 수 있다**는 지적이다.
줄 버퍼링이 터미널의 기본값이고 보통 파이프에서도 원하는 것이며, 각 명령을 `stdbuf -oL -eL`로 돌리면 얻을 수 있다고 정리했다.

이 구분이 실무적으로 중요하다.

저자가 제시한 해법 4가 `stdbuf -o0`인데, 이것이 **버퍼링을 완전히 끄는 것**이다.
o11c의 제안은 `stdbuf -oL`, 즉 **줄 버퍼링으로 바꾸는 것**이다.

```bash
# 저자의 해법: 버퍼링 완전 제거
stdbuf -o0 grep thing1

# 더 나은 기본값: 줄 버퍼링
stdbuf -oL grep thing1
```

차이가 무엇인가.
`-o0`은 `write()` 시스템 콜이 훨씬 많이 발생하고, 여러 프로세스가 같은 파이프에 쓰면 **한 줄 중간에 다른 프로세스의 출력이 끼어들 수 있다**.
`-oL`은 줄 단위로 원자적으로 쓰므로(줄이 `PIPE_BUF`보다 짧으면) 그 문제가 없다.

그리고 `-oL`이 **터미널에 직접 쓸 때의 동작과 같다**. 즉 “파이프를 터미널처럼 행동하게 만든다”는 이 글의 목적에 정확히 맞는 것은 `-oL`이다.

저자가 `--line-buffered`를 해법 2로 제시하면서 `stdbuf`는 `-o0`으로 쓴 것이 일관되지 않은 지점이다.

### 타임아웃 기반 플러시 제안은 이미 답이 있다

저자가 “일정 시간이 지나면 자동으로 플러시하는 프로그램이 있는지 궁금하다”고 던진 질문에 댓글이 몰렸다.

Veserv가 가장 체계적으로 답했다.[^Veserv]
버퍼링된 접근이 거의 언제나 **“임계값 또는 타임아웃”** 방식이어야 한다는 것이다. 임계값 바이트 수에 도달하거나, 최소 1바이트라도 있으면 일정 시간이 지난 뒤 플러시하는 것이다.
그리고 **비슷한 문제를 풀기 위해 하드웨어 인터페이스에서는 흔한 방식**이라고 덧붙였다.
타임아웃 값으로는 인자로 전달받거나, 인간 규모보다 약간 짧거나(1~100ms), 대역폭 대비 임계값에 비례하는 것을 제안했다.

calibas도 같은 구도를 정리했다.[^calibas]
UART를 다룰 때 자주 만나는 오래된 문제이며 세 가지 접근이 있다는 것이다.
개행 같은 특수 문자로 출력의 끝을 알리거나(줄 기반), 8KB를 기다리는 길이 기반이거나, X밀리초마다 출력하는 시간 기반이다. 각각 장단점이 있고 응용에 달렸다는 것이다.

londons_explore는 더 과감한 제안을 했다.[^londons_explore]
**시스템 전체 CPU가 유휴 상태가 될 때마다 모든 버퍼가 플러시되면 좋겠다**는 것이다.
버퍼링이 일반적으로 CPU를 아끼는 기법이며, CPU가 무한하다면 모든 버퍼가 1바이트일 것이라는 논리다. 그러니 CPU가 유휴가 되면 “할 일이 기다리고 있으면” 안 되고, 커널 스케줄러가 유휴가 되는 즉시 모든 프로세스에 “버퍼를 플러시하라” 신호가 가야 한다는 것이다.

josephcsible은 더 구현 가능한 제안을 했다.[^josephcsible]
**비어 있던 출력 버퍼에 데이터가 들어가면 입력을 논블로킹으로 바꾸고, 읽기가 `EWOULDBLOCK`으로 돌아오면 출력 버퍼를 플러시하고 입력을 다시 블로킹으로 바꾸는 것**이다.
다시 말해 **잠들기 전에는 언제나 출력 버퍼가 플러시되어 있도록 보장**하자는 것이며, 이러면 문제가 해결되지 않겠냐고 물었다.

이 마지막 제안이 가장 정확하다. 문제의 본질이 **“쓸 것이 있는데 아무도 기다리고 있지 않다”**는 상황이기 때문이다.

그런데 Lobste.rs에서 이 방향에 대한 반론도 나왔다.

walleye가 Nagle 알고리즘 같은 것을 쓰지 않는 이유를 물었고,[^walleye]
cyberia가 답했다. **Nagle 알고리즘은 보낸 데이터의 확인 응답을 볼 수 있어야 하는데** 파이프에는 그것이 없다는 것이다.[^cyberia]

fanf가 문제를 정확히 재정의했다.[^fanf]
**문제는 `write()`가 느린 것이 아니라 버퍼가 차지 않아서 `write()`가 아예 호출되지 않는 것**이라는 지적이다.
그러니 `print()`에서 10ms 같은 타이머를 설정하고 그것이 울리면 버퍼를 플러시하는 식이어야 한다는 것이다.

이 교환이 왜 아무도 이것을 구현하지 않았는지를 설명한다.
**타이머 기반 플러시는 라이브러리가 시간을 다뤄야 한다는 뜻이고**, 그것은 stdio 같은 계층이 지금까지 하지 않아 온 종류의 일이다. 시그널이나 스레드나 이벤트 루프가 필요해진다.

### `Ctrl-C`에서 버퍼가 사라지는 문제의 구조

저자가 이 문제를 “아마 피할 수 없을 것”이라고 정리했는데, 댓글이 그 구조를 더 명확히 했다.

toast0는 **대부분의 프로그램이 `SIGINT`에 버퍼를 플러시할 것**이라고 보면서, 셸에서 그것이 통하려면 **파이프라인의 첫 프로그램에만 `SIGINT`를 전달해야 하는데 그렇게 동작하지 않는다**고 짚었다.[^toast0]

Joker_vD가 더 정확히 설명했다.[^Joker_vD]
꽤 많은 유틸리티가 실제로 `SIGINT`를 받으면 stdout을 플러시하려 하지만, 파이프 반대편도 `SIGINT`를 받았을 수 있고 **아무도 `SIGINT`에 stdin을 짧게 기다리지 않는다**는 것이다.
그럴 만한 이유가 있다. **애초에 `SIGINT`를 받은 이유가 사용자가 지금 멈추기를 원하기 때문**이라는 것이다.

이 설명이 저자의 “피할 수 없다”를 원리로 바꾼다.

문제가 기술적 한계가 아니라 **의미의 충돌**이다.
`SIGINT`는 “지금 멈춰라”인데 버퍼 플러시는 “조금 더 일해라”이며, 프로세스 그룹 전체가 동시에 신호를 받는 구조에서 둘을 동시에 만족시킬 방법이 없다.

wyuenho는 반대 방향의 문제를 겪은 이야기를 남겼다.[^wyuenho]
**파이프 앞쪽 명령이 뒤쪽의 버퍼링을 기대하는 탓에 파이프가 깨지는 경우**다.
`curl ... | grep -q`가 `Failed write body error`를 내는 이유를 찾느라 머리를 싸맸다는 것이다. `grep -q`가 매치를 찾는 즉시 stdin을 닫고 종료하므로 grep 앞에 버퍼가 필요했는데, macOS에는 `sponge`도 `stdbuf`도 `unbuffer`도 없어서 적당히 버퍼링하는 크로스 플랫폼 명령을 찾아야 했다는 것이다.

이 사례가 이 글의 짝이다. **버퍼링이 없어서 생기는 문제도 있다.**
carlana가 그 해법을 짧게 적었다. 버퍼링을 원한다면 끝에 `| cat`을 붙여 TTY가 아니라고 생각하게 만들면 된다는 것이다.[^carlana]

### 파이프 앞의 `cat`은 아무것도 바꾸지 않는다

작은 오해가 하나 정정되었다.

jmtd가 **파이프라인 시작에서 grep의 블록 버퍼링을 피하는 데 `cat`이 유용할 수도 있겠다**고 적었다.[^jmtd]

LeahNeukirchen이 짧게 답했다. **그 예에서 `cat`은 아무것도 바꾸지 않는다**는 것이다.[^LeahNeukirchen]

맞는 지적이다. 저자의 해법 1이 통하는 이유는 `cat`을 앞에 붙였기 때문이 아니라 **`tail -f`를 `cat`으로 바꿔 입력이 빨리 끝나기 때문**이다.
입력이 끝나면 `grep`이 종료하면서 버퍼를 플러시한다.

저자 본인도 “불필요한 `cat`을 쓰는 것을 종종 선호한다”고 농담처럼 적었는데, 그 `cat`이 버퍼링에 기여하는 바는 없다.

## 체크리스트

- 파이프라인에서 출력이 안 나오는가? 마지막이 아닌 단계에 `grep`/`sed`/`jq`/`tr`이 있는지 먼저 확인했는가
- 데이터를 천천히 흘려보내는 소스(`tail -f`, `tcpdump`, `kubectl logs`)를 쓰고 있는가? 그렇다면 버퍼링을 의심하라
- 해당 명령의 버퍼링 해제 플래그를 아는가? 모르면 `unbuffer`를 쓰라
- `stdbuf`를 쓴다면 `-o0`이 아니라 `-oL`이 맞는 경우가 아닌가
- 정적 바이너리나 macOS에서 `stdbuf`를 쓰려 하고 있지 않은가
- `Ctrl-C`로 파이프라인을 끊기 전에, 잃어도 되는 버퍼인지 생각했는가
- 출력이 아니라 **입력**이 사라지고 있는가? `head` 같은 명령이 필요한 것보다 많이 읽었을 수 있다
- 반대로 파이프가 깨진다면(`Failed write body`), 뒤쪽이 일찍 종료하는 명령인지 확인했는가

## 기억할 원칙

### 관찰되는 동작이 구성 요소가 아니라 관계에서 나온다

이 글이 푸는 수수께끼의 구조가 특이하다.

`tail -f file | grep thing`은 되고 `tail -f file | grep thing1 | grep thing2`는 안 된다.
같은 `grep`인데 **위치에 따라 동작이 다르다**.

원인이 `grep`에도 파이프에도 없다. `grep`이 **자기 stdout이 무엇인지 보고 행동을 바꾸기 때문**이다.

이 패턴이 유닉스 도구 전반에 퍼져 있다.
`ls`가 열을 나누는지, `rg`가 색을 쓰는지, `git log`가 페이저를 띄우는지가 전부 `isatty()` 결과에 달렸다.

그래서 디버깅할 때 잘못된 질문을 하기 쉽다.
“`grep`이 왜 이러지”라고 물으면 답이 없다. **“이 `grep`의 출력이 어디로 가고 있지”라고 물어야 답이 나온다.**

일반화하면, 어떤 도구가 맥락에 따라 행동을 바꾼다면 그 도구를 아무리 들여다봐도 원인을 찾을 수 없고, **맥락을 바꿔 가며 관찰해야 한다**.

이 글의 진단법이 정확히 그것이다. 파이프를 하나 빼 보고, 터미널에 직접 출력해 보고, 차이를 본다.

### 편의를 위한 자동 판단은 판단이 틀렸을 때 설명하지 않는다

`isatty()` 기반 자동 전환은 좋은 기본값이다. 대부분의 경우 사용자가 원하는 것을 준다.

그런데 그것이 틀렸을 때 **아무 신호도 주지 않는다**.

`grep`이 버퍼링을 켰다고 말해 주지 않고, 출력이 안 나오는 것과 매치가 없는 것이 **구분되지 않는다**.
저자가 몇 년 동안 “파이프가 가끔 멈춘다”고 생각한 이유가 그것이다. 증상이 정확히 “매치 없음”과 같아 보인다.

이것이 자동 판단의 일반적 비용이다.

명시적 설정은 틀렸을 때 어디를 고칠지 알려 주지만, **자동 판단은 틀렸을 때 증상만 남긴다**.

그리고 이 비용은 자동 판단이 잘 맞을수록 커진다. 잘 맞으면 사람들이 그 메커니즘의 존재 자체를 모르게 되고, 그러면 틀렸을 때 의심할 대상 목록에 올라가지 않는다.

`NO_COLOR` 같은 환경 변수가 존재하는 이유가 그것이고, 저자가 `NO_BUFFER`를 제안한 것도 같은 맥락이다.
자동 판단을 끌 수 있는 표준 스위치가 있으면, **그 스위치의 존재가 메커니즘을 가르쳐 준다**.

### 남에게 물어 모은 지식은 검증 단계를 따로 가져야 한다

이 글은 크라우드소싱으로 만들어졌다. 다섯 가지 해법이 Mastodon 답변에서 왔고, Rust 예제도 누군가 알려 준 것이었다.

그리고 **검증되지 않은 것 하나가 틀렸다**.

저자가 정정하며 쓴 문장이 정확하다. **직접 시험해 보지 않고 소셜 미디어에서 누가 말해 준 것을 믿은 대가**라는 것이다.

이 실패가 이 방식을 부정하지는 않는다. 다섯 가지 해법은 혼자서는 모았을 수 없는 것이고, `unbuffer`와 `stdbuf`의 차이 같은 실무 지식도 그렇게 왔다.

문제는 **수집과 검증이 같은 단계로 처리되었다**는 것이다.

수집된 정보에는 두 종류가 섞인다. 제보자가 실제로 해 본 것과, 제보자도 어디서 들은 것이다.
전자는 신뢰할 만하고 후자는 그렇지 않은데, **제보의 형태만 보면 구분되지 않는다**.

그래서 규칙이 하나 나온다.
남에게 받은 정보를 글에 넣을 때, 그것을 확인하는 명령 한 줄을 함께 적을 수 없다면 **아직 넣을 준비가 안 된 것**이다.

이 글이 잘한 부분들이 그 기준을 만족한다. `stdbuf`에는 실행 예가 있고, `kill -TERM`에는 “시험해 보니 동작한다”는 문장이 붙어 있고, `BUFSIZ`에는 glibc 소스 링크가 있다.
틀린 한 줄만 그 기준을 만족하지 않았다.
