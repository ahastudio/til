# PATH에 디렉터리를 더하는 전체 절차와 함정

원문: [How to add a directory to your PATH](https://jvns.ca/blog/2025/02/13/how-to-add-a-directory-to-your-path/)

HN 토론: <https://news.ycombinator.com/item?id=43156662> (38점, 63개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/ndcuhz/how_add_directory_your_path> (17점, 6개 댓글)

## 요약

Julia Evans가 2025년 2월 13일에 쓴 안내다.

동기가 구체적이다. 친구와 PATH에 디렉터리를 더하는 법을 이야기하다가, 자기에게는 “당연”하게 느껴지는 일인데 **막상 검색해 보니 모든 단계를 설명하는 글을 찾을 수 없었다**는 것이다.

무엇이 빠졌는지도 짚는다.
대부분이 **“`~/.bashrc`에 이걸 추가하세요”**라고만 하는데, bash를 안 쓰면 어떻게 하는가, bash 설정이 다른 파일에 있으면 어떻게 하는가, **애초에 어느 디렉터리를 더해야 하는지는 어떻게 알아내는가**.

그래서 더 완전한 지침을 적고 몇 년간 부딪힌 함정들을 함께 언급하려 했다는 것이다.

## 절차

### 1단계: 어떤 셸을 쓰는가

```bash
ps -p $$ -o pid,comm=
```

bash면 `97295 bash`, zsh면 `97295 zsh`가 나온다.
fish면 **“In fish, please use $fish_pid”** 같은 오류가 나오는데(`$$`가 fish 문법이 아니다), 어쨌든 그 오류 메시지가 fish를 쓰고 있다고 알려 준다.

리눅스 기본은 bash이고 2024년 기준 macOS 기본은 zsh다. 이 글은 셋만 다룬다.

### 2단계: 셸 설정 파일 찾기

| 셸   | 설정 파일                                                     |
| ---- | ------------------------------------------------------------- |
| zsh  | 아마 `~/.zshrc`                                               |
| bash | `~/.bashrc`일 수도 있지만 복잡하다                            |
| fish | 아마 `~/.config/fish/config.fish` (`echo $__fish_config_dir`) |

bash에는 `~/.bashrc`, `~/.bash_profile`, `~/.profile` 세 후보가 있다.

저자의 권고가 실용적이다. **어느 것이 쓰이는지 모르겠으면 시험해 보라**는 것이다.

```text
1. ~/.bashrc 에 echo hi there 를 추가한다
2. 터미널을 재시작한다
3. "hi there"가 보이면 ~/.bashrc 가 쓰이는 것이다
4. 아니면 지우고 ~/.bash_profile 로 같은 것을 해 본다
5. 그래도 안 되면 ~/.profile
```

bash가 어느 설정 파일을 고르는지 설명하는 **정교한 순서도가 많지만 그것을 내면화할 가치가 없다고 보며 그냥 시험하는 것이 가장 빠르다**는 것이 저자의 입장이다.

이 권고가 댓글에서 문제가 된다.

### 3단계: 어느 디렉터리를 더할지 알아내기

```text
$ npm install -g http-server
$ http-server
bash: http-server: command not found
```

`http-server`가 어느 디렉터리에 있는지 어떻게 찾는가.
저자가 솔직하다. **일반적으로 이것이 그렇게 쉽지 않으며, 답이 “npm이 어떻게 설정되었느냐에 달렸다” 같은 것인 경우가 많다**는 것이다.

몇 가지 방법을 제시한다.

새 설치 도구(cargo, npm, homebrew 등)를 처음 설정할 때 **PATH를 갱신하는 방법을 출력해 주는 경우가 많으니 그때 주의 깊게 보면 된다**.
설치 도구가 셸 설정 파일을 자동으로 갱신해 주기도 한다.
“npm은 어디에 설치하나?”를 검색하면 답이 나오기도 한다.

그리고 도구별 하위 명령이 있다.

```bash
npm config get prefix      # 뒤에 /bin/ 을 붙인다
go env GOPATH              # 뒤에 /bin/ 을 붙인다
asdf info | grep ASDF_DIR  # 뒤에 /bin/ 과 /shims/ 를 붙인다
```

#### 3.1단계: 맞는 디렉터리인지 확인하기

찾았다고 생각되면 **실제로 맞는지 확인하라**는 것이다. 그 디렉터리에서 프로그램을 직접 실행해 보면 된다.

```bash
$ ~/.npm-global/bin/http-server
Starting up http-server, serving ./public
```

### 4단계: 설정 편집

```bash
# bash
export PATH=$PATH:~/.npm-global/bin/
```

```bash
# zsh — 위와 같이 해도 되고, 조금 더 멋진 문법도 있다
path=(
  $path
  ~/.npm-global/bin
)
```

```fish
# fish
set PATH $PATH ~/.npm-global/bin
```

### 5단계: 셸 재시작

**대단히 중요한 단계**라고 강조한다. 설정을 갱신해도 셸을 재시작하지 않으면 적용되지 않는다.

새 터미널(또는 탭)을 열거나, `bash`를 실행해 새 셸을 시작하면 된다.

## 네 가지 문제

### 문제 1: 잘못된 프로그램이 실행된다

잘못된 **버전**이 돌고 있다면 디렉터리를 PATH의 **앞쪽**에 더해야 할 수 있다.

```bash
$ which -a python3
/usr/bin/python3
/opt/homebrew/bin/python3
```

**셸이 쓰는 것은 첫 번째로 나열된 것**이다.

```bash
# 앞에 붙인다
export PATH=/opt/homebrew/bin/:$PATH
```

### 문제 2: 셸에서 실행하는 것이 아니다

이 모든 지침이 **셸에서 프로그램을 실행할 때만** 통한다.
IDE나 GUI나 cron 작업에서 실행한다면 다른 방식이 필요하고 세부는 상황에 달렸다.

cron이라면 전체 경로를 쓰거나, crontab 첫 줄에 원하는 전체 PATH를 넣으면 된다(`echo "PATH=$PATH"`로 얻을 수 있다).

IDE나 GUI에 대해서는 **솔직히 어떻게 하는지 모르겠으며 오랫동안 겪지 않아서 누가 알려 주면 지침을 추가하겠다**고 적는다.

### 문제 3: 중복된 PATH 항목

설정을 고치고 `bash`를 실행해 새 셸을 시작하면, **셸이 시작할 때마다 PATH에 계속 더하므로 중복 항목이 생기는 경우가 많다**.

저자는 이 중복이 무언가를 망가뜨린 상황을 겪은 적이 없다고 생각하지만, **PATH 내용을 이해하려 할 때 디버깅을 어렵게 만든다**고 적는다.

대처법 셋을 제시한다.
PATH를 디버깅할 때는 새 터미널을 열어 “깨끗한” 상태에서 하고, 셸 설정 끝에서 중복을 제거하거나(zsh는 `typeset -U path`), 더할 때 이미 있는지 확인하는 것이다(fish는 `fish_add_path --path`).

### 문제 4: PATH를 고친 뒤 히스토리를 잃는다

```text
1. 명령을 실행한다 (실패)
2. PATH를 갱신한다
3. bash 를 실행해 설정을 다시 읽는다
4. 위 화살표를 몇 번 눌러 실패한 명령을 다시 실행하려 한다
→ 실패한 명령이 히스토리에 없다
```

**bash에서 기본적으로 히스토리가 셸을 종료할 때까지 저장되지 않기 때문**이다.

해법은 `bash`를 실행하는 대신 `source ~/.bashrc`를 쓰거나, 히스토리를 계속 저장하도록 설정하는 것이다.

### `source`에 대한 메모

cargo를 처음 설치하면 **특정 디렉터리를 전혀 언급하지 않는** 지침을 준다.

```bash
. "$HOME/.cargo/env"            # sh/bash/zsh/ash/dash/pdksh
source "$HOME/.cargo/env.fish"  # fish
```

저자는 두 가지 접근이 있다고 정리한다. 도구가 시키는 대로 하거나, **그 스크립트가 어떤 디렉터리를 더하는지 알아내 직접 더하는 것**이다.

```bash
. "$HOME/.cargo/env"
echo "$PATH" | tr ':' '\n' | grep cargo   # 무엇이 더해졌는지 본다
# /Users/bork/.cargo/bin → ~/.cargo/bin 으로 줄여서 직접 추가
```

도구가 시키는 대로 하는 것이 잘못은 아니고 오히려 “최선”일 수도 있다면서, 다만 자기는 **정확히 어떤 설정을 바꾸고 있는지 알고 싶어서** 두 번째를 쓴다고 밝힌다.

### `fish_add_path`에 대한 메모

fish에는 `fish_add_path /some/directory`라는 편리한 함수가 있는데, 저자는 두 가지 이유로 **쓰기를 그만두었다**.

**어떨 때는 미래의 모든 세션에 대해 PATH를 갱신하고(범용 변수로) 어떨 때는 현재 세션만 갱신하는데 어느 쪽인지 알기 어렵다**는 것이 첫째다. 이론상 문서가 설명하지만 이해할 수 없었다고 한다.
몇 주나 몇 달 뒤에 실수를 깨닫고 **그 디렉터리를 제거하려면 꽤 어렵다**는 것이 둘째다.

## 함정

### `echo hi there` 시험법이 다른 것을 망가뜨릴 수 있다

2단계의 권고가 실용적이지만 위험이 하나 있다.

jjnoakes가 HN에서 짚었다.[^jjnoakes]
이런 글이 **bash의 여러 시작 파일과 그것들이 언제 로드되는지를 얼버무리지 않았다면 더 나았을 것**이라는 지적이다.
남의 셸을 디버깅해 줄 때 근본 원인이 **그 파일들이 각각 무엇을 위한 것인지 이해하지 못하는 것**인 경우가 많다는 것이다.

그리고 결정적인 경고를 붙인다.
**엉뚱한 파일에 `echo`를 추가하고 대화형 셸인지 확인하지 않으면 `scp` 같은 온갖 것이 깨질 수 있으며, 그것도 이상하고 뻔하지 않은 방식으로** 깨진다는 것이다.

이 경고가 정확하다.

`scp`와 `sftp`와 `rsync`가 원격 셸을 비대화형으로 띄우는데, **그 셸이 표준 출력에 무언가를 내면 프로토콜이 깨진다**.
그래서 `~/.bashrc`에 `echo`를 넣어 둔 채 잊으면 다음에 `scp`가 “protocol error” 같은 것으로 실패하고, 원인을 찾기가 대단히 어렵다.

```bash
# 시험용 출력을 넣어야 한다면 대화형일 때만 내게 한다
case $- in
  *i*) echo "hi there" ;;
esac
```

이 글이 시험법으로 `echo`를 권하면서 이 조건을 말하지 않는다.

### rc 파일에 PATH를 넣으면 덮어쓰기 어려워진다

t43562가 다른 각도의 문제를 짚었다.[^t43562]

**`.bashrc`는 셸이 시작할 때마다 실행되므로 거기에 PATH 설정을 넣지 않겠다**는 것이다.
그러면 **그 PATH 설정을 다른 곳에서 덮어쓰기가 아주 어려워지기 때문**이다.

그것을 원할 수도 있지만, **PATH를 설정한 뒤 셸 명령을 실행하려는 다른 프로그램의 시도를 망칠 수도 있다**는 지적이다.
자기는 이런 용도로 `.bash_profile`이나 `.profile`을 더 쓰고, 터미널 프로그램에 bash를 로그인 셸로 실행하라고 알려 준다고 밝혔다.

이것이 실무에서 자주 겪는 문제다.

```bash
# 이렇게 하면 .bashrc 의 설정이 이걸 덮어쓴다
PATH=/custom/path:$PATH ssh host 'some-command'
```

`.bashrc`가 매번 `export PATH=$PATH:~/whatever`를 실행하므로 **바깥에서 정한 PATH 위에 계속 덧붙는다**. 순서를 통제할 수 없다.

ljm은 같은 문제의 다른 면을 적었다.[^ljm]
셸이 어떻게 시작되느냐에 따라 설정을 읽을 위치가 여러 개이고, 데스크톱 앱이 설정을 끌어오려고 하는 것(emacs의 `exec-path-from-shell` 같은)까지 겹친다는 것이다.
그리고 **`.zprofile`과 `.zshrc` 양쪽에, 또는 `.bash_profile`과 `.profile`과 `.bashrc` 전부에 넣을 수도 없다**고 짚는다. 그러면 한 번 넘게 실행되고 그것을 막으려면 어떤 상태를 유지해야 하기 때문이다.

### 중복이 “해가 없다”는 판단이 성급하다

저자가 문제 3에서 중복이 **무언가를 망가뜨린 상황을 겪은 적이 없다**고 적는다.

이 판단이 대체로 맞지만 예외가 있다.

PATH가 길어지면 **명령 하나를 찾는 데 필요한 파일시스템 접근이 늘어난다**. 셸이 항목을 순서대로 뒤지기 때문이다.
로컬 디스크에서는 무시할 만하지만 **NFS나 느린 마운트가 PATH에 있으면 체감된다**.

그리고 앞에서 본 순서 문제와 겹치면 더 나빠진다. 중복 때문에 **같은 디렉터리가 앞뒤 양쪽에 있으면 어느 쪽이 이기는지 읽기가 어려워진다**.

raggi가 HN에서 이 연쇄를 단계별로 정리했다.[^raggi]

1단계는 `echo $SHELL`이면 되고, **2단계는 프로파일을 언급했어야 한다**.
3단계는 **로그인 셸을 시작하지 않는 터미널 에뮬레이터** 때문에 혼란스러워질 수 있다. 프로파일이 다시 읽히지 않기 때문이며, **그것이 평소에 중복 PATH 항목이 수십 개씩 생기지 않는 이유이기도 하다**. 로그인 항목이 왜 다시 읽히거나 읽히지 않는지 모르면 시행착오가 오해를 부른다는 것이다.
4단계는 rc에 이런 구문을 넣으면 중첩 셸에서 대체로 중복 항목을 낳고, **5단계가 중첩 셸을 시작하므로 4단계의 문제를 그대로 시연한다**.

마지막 지적이 날카롭다. **이 글의 5단계가 3번 문제를 만든다.**

`source`를 쓰라는 조언이 4번 문제(히스토리)에 대한 해법으로만 제시되는데, **3번 문제의 해법이기도 하다**.

### GUI와 IDE에 대한 답이 비어 있다

저자가 문제 2에서 **IDE나 GUI는 어떻게 하는지 모르겠다**고 솔직히 적고 넘어간다.

peniblec이 Lobste.rs에서 답을 시도했다.[^peniblec]
**“그 방법”을 가리킬 수는 없지만 방향은 줄 수 있다**며, 경험적으로 `~/.profile`이 여러 배포판에서 통했다고 적었다(Debian/Wayland/Plasma, Ubuntu/Wayland/Plasma, Ubuntu/X11/GNOME, openSUSE/Wayland/Plasma).
다만 사각지대가 있다며 XFCE는 시도한 지 오래되었다고 덧붙이고, **“GUI 세션을 위해 PATH를 수정하는 것”이 10년 된 자료들을 거쳐 가는 토끼굴 중 하나**라고 적었다.

bandrami는 또 다른 층을 더했다.[^bandrami]
**셸이 emacs 버퍼 안에서 하위 프로세스로 돌고 있으면 또 다른 것을 해야 한다**는 것이다.

이 공백이 이 글의 구조적 한계를 드러낸다.
제목이 “PATH에 디렉터리를 더하는 법”인데, 내용은 **“대화형 셸의 PATH에 더하는 법”**이다.

## 비평

### 애초에 셸 설정 파일이 맞는 장소인가

Lobste.rs의 최고점 댓글이 이 글의 전제를 통째로 반박했다.

intelfx가 적었다.[^intelfx]

**“이 글이 제목의 질문에 실제로 답했으면 좋았을 텐데”**라는 것이다.

그리고 논거를 댄다.
**`$PATH`는 세션 전역 자원이며, 대화형 셸의 또 다른 눈요기 설정인 것처럼 셸 rc 파일로 설정하게 되어 있지 않다**는 것이다.
다른 말로 하면 **이 자원을 잘못된 범위와 잘못된 수명에 묶고 있다**는 지적이다.

systemd 이전에는 프로파일 파일(`~/.profile`, `~/.bash_profile`, `/etc/profile`)로 설정했고, X11 세션이라면 또 다른 경로가 있었다는 것이다.

| 증상                           | intelfx의 진단에서 나오는 설명 |
| ------------------------------ | ------------------------------ |
| GUI/IDE에서 PATH가 안 잡힌다   | 셸 rc는 셸에서만 읽히므로      |
| 중복 항목이 쌓인다             | rc가 셸마다 실행되므로         |
| 바깥에서 PATH를 덮어쓸 수 없다 | rc가 매번 덧붙이므로           |
| cron에서 안 된다               | 같은 이유                      |

즉 저자가 “문제”로 나열한 넷 중 셋이 **rc 파일을 쓴 결과**다.

세션 수준에 설정하면 셸이든 GUI든 cron이든 상속받고, 한 번만 설정되므로 중복이 없고, 바깥에서 덮어쓸 수 있다.

```bash
# systemd 환경: 세션 전역
mkdir -p ~/.config/environment.d
echo 'PATH=$HOME/.npm-global/bin:$PATH' > ~/.config/environment.d/10-path.conf
# 로그아웃 후 다시 로그인해야 적용된다
```

다만 이 접근에도 대가가 있다.
**로그아웃해야 적용되고**, 배포판과 데스크톱 환경에 따라 동작이 다르며, macOS에는 아예 없다.
그리고 `environment.d`는 변수 확장이 제한적이라 복잡한 조합이 어렵다.

그러니 이 글이 rc 파일을 택한 것이 틀렸다기보다 **선택지를 제시하지 않은 것**이 문제다.
“대화형 셸에서만 필요하면 rc, 세션 전체에 필요하면 다른 곳”이라는 한 줄이 있었다면 문제 2가 공백으로 남지 않았을 것이다.

soneil은 더 단순한 대안을 언급했다.[^soneil]
**맥이 쓰는 `/etc/paths.d/` 방식이 정말 마음에 들며 이렇게 단순한 것이 다른 데서 채택되지 않은 것이 놀랍다**는 것이다.

이 방식은 디렉터리에 파일 하나를 넣으면 그 내용이 PATH에 들어간다. 패키지마다 파일 하나씩을 두면 되므로 **설치와 제거가 대칭적**이다.

duped는 그것을 일반화한 상상을 적었다.[^duped]
`/var/share/env`에 디렉터리가 있어서 일반 파일은 환경 변수가 되고 나머지 파일 종류는 무시되며, `env` 프로그램이 그것을 전부 읽어 기본 환경을 만든 뒤 셸별 dotfile의 커스터마이징을 적용하는 것이다.
그러면 PATH에 더하는 것이 `echo ':' >> /var/share/env/PATH`가 된다.

### “시험해 보는 것이 가장 빠르다”는 조언의 대가

저자가 bash 설정 파일 순서도를 **내면화할 가치가 없다**고 적는다.

이 판단이 실용적이고, 한 번 쓰고 잊을 문제라면 맞다.

그런데 jjnoakes의 지적이 그 대가를 보여 준다. **남의 셸을 디버깅할 때 근본 원인이 대개 그 구분을 모르는 것**이다.

그리고 raggi의 3단계 지적이 더 구체적이다. **로그인 셸을 시작하지 않는 터미널 에뮬레이터에서는 시행착오가 오해를 부른다.**

무슨 뜻인가 하면 이렇다.

`~/.bash_profile`에 `echo hi there`를 넣고 새 탭을 열었는데 안 보인다고 하자.
결론은 “`.bash_profile`은 안 쓰이는구나”가 된다.
그런데 실제 이유는 **그 터미널 에뮬레이터가 로그인 셸을 띄우지 않아서**일 수 있고, SSH로 접속하면 정반대가 된다.

즉 **시험이 알려 주는 것은 “이 터미널의 이 설정에서 어떤 파일이 읽히는가”이지 “이 시스템에서 어떤 파일이 읽히는가”가 아니다**.

최소한의 구분은 이 정도다.

| 파일              | 언제 읽히는가                         |
| ----------------- | ------------------------------------- |
| `~/.bash_profile` | 로그인 셸 (SSH 접속, 콘솔 로그인)     |
| `~/.bashrc`       | 대화형 비로그인 셸 (보통 터미널 탭)   |
| `~/.profile`      | 로그인 셸. `sh` 호환. GUI 세션도 읽음 |

그리고 많은 배포판이 `~/.bash_profile`에서 `~/.bashrc`를 소싱하도록 해 둔 것이 혼란의 출처다. 그래서 겉보기에 둘이 같아 보인다.

philsnow가 실용적 우회로를 적었다.[^philsnow]
bash와 zsh를 오갈 때 **둘 모두와 호환되는 문법 부분집합만 쓰는 `~/.commonrc`를 두고 `.bashrc`와 `.zshrc` 양쪽에서 소싱**했다는 것이다.
PATH 추가나 별칭이나 셸 함수를 거기 넣고 잊으면 되니 좋다고 정리했다.

### 도구가 늘어날수록 이 문제가 커진다

이 글이 개인 기계를 전제하는데, 여러 사람의 환경을 세팅하는 입장에서는 성질이 달라진다.

evntdrvn이 그 경험을 적었다.[^evntdrvn]
소규모 회사들의 사내 개발 도구를 유지해 왔는데, **임의의 셸을 쓰는 리눅스나 macOS 노트북을 동작하는 환경으로 부트스트랩하는 견고한 설치 스크립트를 쓰는 것이 정말 골칫거리**라는 것이다.
느낌보다 훨씬 많은 일이라며, 결국 **컨테이너화된 개발 환경이 더 나은 해법일 것이라고 받아들였는데 원칙적으로는 이렇게 되어야 한다는 것이 만족스럽지 않다**고 적었다.

이 반응이 이 글의 절차를 자동화하려 할 때 무엇이 어려운지 보여 준다.

절차의 각 단계가 **조건 분기**다. 어떤 셸인가, 어떤 파일인가, 이미 있는가, 앞인가 뒤인가.
사람은 시험해 보면 되지만 스크립트는 전부 판단해야 한다.

그래서 컨테이너가 답이 되는 논리가 성립한다. **환경을 설정하는 대신 환경을 고정하는 것**이다.

throwaway314155가 이 글에 대한 감상을 한 줄로 적었다.[^throwaway314155]
**엄청나게 도움이 되는 글이면서 동시에 PATH에 디렉터리를 더하는 것처럼 단순한 일이 얼마나 과도하게 복잡한지를 보여 주는 글**이라는 것이다.

이 두 평가가 모순이 아니다. 좋은 안내서일수록 그 영역의 복잡도를 정확히 드러낸다.

## 확인하기

```bash
# 지금 셸이 무엇인가 (두 가지 방법)
ps -p $$ -o pid,comm=
echo $0

# PATH를 읽기 좋게 본다
echo "$PATH" | tr ':' '\n'

# 중복 항목이 있는가
echo "$PATH" | tr ':' '\n' | sort | uniq -d

# 어떤 프로그램이 어디서 오는가. 전부 본다
which -a python3

# 로그인 셸에서 무엇이 읽히는지 본다
bash -lc 'echo $PATH' | tr ':' '\n'

# 비로그인 대화형 셸에서는
bash -ic 'echo $PATH' | tr ':' '\n'
```

`zk`가 `echo $0`을 쓴다고 적었는데,[^zk] 자기는 유닉스 sh 계열만 써 봐서 fish 같은 데서도 되는지는 모르겠다고 덧붙였다.

두 방법의 차이가 있다. `ps -p $$`는 **실제로 돌고 있는 프로세스**를 보고, `echo $0`은 **셸이 자기를 어떻게 부르는지**를 본다. 로그인 셸이면 `-bash`처럼 앞에 대시가 붙으므로 그것으로 로그인 셸 여부도 알 수 있다.

## 체크리스트

- 어느 셸인지 확인했는가? `$SHELL`이 아니라 실제 돌고 있는 셸인가
- 그 디렉터리에서 프로그램을 직접 실행해 확인했는가
- 이 PATH가 셸에서만 필요한가, GUI·cron·IDE에서도 필요한가? 후자면 rc 파일이 맞는 장소가 아니다
- 버전 충돌이 있다면 앞에 붙였는가 뒤에 붙였는가? `which -a`로 확인했는가
- 설정 파일을 시험하려고 `echo`를 넣었다면, 대화형일 때만 출력하게 했는가? `scp`가 깨질 수 있다
- 시험이 끝난 뒤 그 `echo`를 지웠는가
- 재시작에 `bash`를 쓰는 대신 `source`를 썼는가? 중복과 히스토리 손실을 함께 피한다
- 팀에 배포할 스크립트라면, 조건 분기 대신 환경을 고정하는 편이 낫지 않은가

## 기억할 원칙

### 설정의 위치는 그 값의 수명과 범위가 정한다

intelfx의 비판이 이 글을 넘어 일반화된다.

**`$PATH`는 세션 전역 자원인데 셸 rc 파일은 셸 하나의 수명을 가진다.** 범위와 수명이 어긋나 있다.

그리고 어긋남의 결과가 전부 저자가 “문제”라고 부른 것들이다.
셸 밖에서 안 된다, 셸마다 중복된다, 바깥에서 덮어쓸 수 없다.

이 진단법이 다른 설정에도 적용된다.

무언가를 어디에 둘지 정할 때 물어야 할 것이 **“어디에 두는 것이 관례인가”가 아니라 “이 값이 언제부터 언제까지 유효해야 하고 누가 읽어야 하는가”**다.

| 범위                         | 적절한 위치                          |
| ---------------------------- | ------------------------------------ |
| 이 명령 하나                 | `VAR=x command`                      |
| 이 셸 세션                   | 셸에서 직접 `export`                 |
| 이 사용자의 모든 셸          | 셸 rc 파일                           |
| 이 사용자의 로그인 세션 전체 | 프로파일, `environment.d`, `launchd` |
| 이 기계의 모든 사용자        | `/etc/profile.d/`, `/etc/paths.d/`   |

관례를 따르면 대체로 맞지만, 문제가 생겼을 때 **관례는 왜 그런지 설명해 주지 못한다**.
범위로 생각하면 설명이 나온다.

### 좋은 절차서일수록 대상의 복잡도를 숨기지 못한다

이 글이 받은 두 종류의 반응이 흥미롭다.

한쪽은 “고맙다, 이런 것을 찾고 있었다”이고, 다른 쪽은 “이렇게 복잡한 게 말이 되냐”다.
throwaway314155가 **둘 다**라고 적은 것이 정확하다.

그리고 이것이 우연이 아니다.

절차서를 쓰려면 **모든 분기를 다뤄야 한다**. 어떤 셸인가, 어떤 파일인가, 앞인가 뒤인가, 어디서 실행하는가.
그 분기들이 원래 있던 것인데, 사람들은 자기 경로 하나만 걸어서 나머지를 보지 않는다.

그래서 완전한 절차서는 필연적으로 **그 영역이 얼마나 복잡한지를 드러내는 문서**가 된다.

이것이 “그냥 `~/.bashrc`에 추가하세요”라고 쓰는 글들이 더 많은 이유이기도 하다. **그쪽이 쓰기 쉽고 대부분의 독자에게 통한다.**
통하지 않는 소수는 검색 결과 어디에도 답이 없는 상태로 남는다.

일반화하면, 어떤 작업에 대한 안내가 한결같이 짧다면 그 작업이 단순해서일 수도 있고 **안내들이 다수 경로만 다루기 때문**일 수도 있다.
구분하는 방법은 소수 경로에 있는 사람이 무엇을 겪는지 보는 것이다.

이 글의 가치가 거기 있다. **저자가 `fish_add_path`를 이해할 수 없어 그만뒀다고 적고, GUI는 모르겠다고 적은 것**이 절차서로서는 결함이지만 지형도로서는 정확하다.

### 시험은 현재 상태를 알려 주고 원리는 다른 상태를 예측하게 한다

저자가 bash 설정 파일 순서도 대신 **시험을 권한 것**이 이 글의 핵심 방법론이다.

그리고 그것이 옳은 경우가 많다. 순서도를 외우는 비용이 크고, 한 번 알아내면 다시 알아낼 일이 드물다.

그런데 raggi의 지적이 그 한계를 정확히 짚는다.
로그인 셸을 띄우지 않는 터미널에서 한 시험의 결과가 **SSH 접속에는 적용되지 않는다**.

즉 시험은 **자기가 시험한 상황에 대해서만** 답한다.

그래서 이런 규칙이 나온다.
상황이 하나뿐이면 시험이 낫고, **상황이 여럿이면 원리가 필요하다**.

혼자 쓰는 노트북의 터미널 하나라면 시험으로 충분하다.
SSH로 들어가고 cron을 돌리고 GUI 앱도 쓴다면, 시험을 상황 수만큼 반복해야 하고 그 결과들을 연결할 틀이 없다.

evntdrvn이 사내 부트스트랩 스크립트에서 겪은 어려움이 그 극단이다. **상황이 사람 수만큼 있으면 시험이 아예 불가능하다.**

그리고 이 구분이 학습 전략으로 이어진다.
**자주 바뀌지 않는 원리는 배워 두고 자주 바뀌는 값은 시험한다.** bash 시작 파일 규칙은 전자이고 `npm config get prefix`의 출력은 후자다.

이 글은 후자를 아주 잘 다루고 전자를 생략했으며, 댓글들이 채운 것이 대부분 전자다.
