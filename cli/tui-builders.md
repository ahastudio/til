# tui.builders: 드래그 앤 드롭으로 만드는 TUI

<https://tui.builders/>

<https://github.com/subinium/SuperLightTUI>

GN 토론: <https://news.hada.io/topic?id=27581>

## 소개

tui.builders는 터미널 UI를 시각적으로 설계하고 코드로 내보내는 웹 편집기다.
웹사이트를 만들듯 터미널 UI를 만든다는 것이 내건 문구이고, 코드를 먼저 쓰지 않고 화면부터 조립한다.
무료이며 가입이 필요 없고 오픈소스다.

기반은 SuperLightTUI라는 Rust 라이브러리다.
이 라이브러리는 unsafe 코드가 전혀 없고, 의존성이 두 개이며, 60fps 렌더링과 2MB 미만의 출력 크기를 내세운다.
편집기가 내보내는 코드는 이 라이브러리의 실제 API를 쓰므로, 생성된 결과를 기존 프로젝트에 그대로 가져다 붙일 수 있다.

프레임워크 지원 상태는 단계가 나뉘어 있다.

| 프레임워크                     | 상태      | 비고                     |
| ------------------------------ | --------- | ------------------------ |
| SuperLightTUI (Rust)           | 정식 지원 | v0.17.1                  |
| Ink (TypeScript/React)         | 베타      | 위젯 44종 사용 가능      |
| Ratatui (Rust)                 | 예정      | —                        |
| Textual (Python)               | 예정      | —                        |
| Bubbletea (Go)                 | 예정      | —                        |

제공하는 것은 드래그 앤 드롭 위젯 팔레트, 실시간 미리보기, 속성 검사기, 코드 내보내기다.
위젯은 50종이 넘으며 텍스트, 버튼, 입력, 표, 차트, 게이지 등이 포함된다.
테마는 Dark, Catppuccin, Tokyo, Dracula, Nord, Gruvbox, Solarized 일곱 가지가 내장되어 있다.

## 동작 방식

작업 흐름은 네 단계다.
시각적으로 설계하고, 속성을 설정하고, 프로덕션용 Rust 또는 TypeScript 코드를 내보내고, 애플리케이션을 실행한다.

여기서 중요한 성질은 이 도구가 런타임이 아니라 생성기라는 점이다.
편집기가 만들어 내는 것은 설정 파일이나 중간 표현이 아니라 해당 라이브러리 API를 직접 호출하는 소스 코드이고, 실행 시점에 이 도구는 개입하지 않는다.
즉 의존성이 늘어나지 않는다. 늘어나는 것은 내보낸 코드가 쓰는 라이브러리 하나뿐이다.

이 구조가 앞의 프레임워크 표를 설명한다.
프레임워크를 지원한다는 것은 그 프레임워크의 API로 코드를 쓸 줄 안다는 뜻이며, 지원 목록이 하나씩 늘어나는 방식으로 진행될 수밖에 없다.
Ink가 베타이면서 위젯이 44종으로 줄어드는 이유도 같다. 편집기의 위젯 개념이 각 프레임워크에서 어디까지 대응되는지가 지원 범위를 결정한다.

시작점을 위해 미리 만들어진 레이아웃도 있다.
게이지와 차트와 표가 들어간 다중 패널 대시보드, 카운터 애플리케이션, 폼 레이아웃이다.

### 인스펙터와 코드가 1:1로 대응한다

만든 사람인 subinium이 GeekNews에 올린 설명이 이 도구의 설계 의도를 가장 정확히 밝힌다.
편집기의 인스펙터에서 `width=30, padding=2, border=rounded`를 설정하면 생성되는 코드가 `.w(30).p(2).border(Border::Rounded)`다.
속성 하나가 메서드 하나로 그대로 옮겨지는 대응이며, SuperLightTUI는 애초에 이 1:1 매핑을 위해 설계됐다고 밝힌다.

이 대응이 중요한 이유는 생성 코드의 읽기 쉬움이 우연이 아니라 목표였다는 뜻이기 때문이다.
편집기가 먼저 있고 라이브러리를 거기 맞춘 순서이며, 그래서 Ratatui 같은 기존 라이브러리가 아니라 새 라이브러리가 기본 대상이 됐다.

라이브러리 자체는 CSS 플렉스박스와 Tailwind 유틸리티 클래스 방식을 빌려 왔다.
웹 개발 경험이 있으면 별도 학습 없이 레이아웃을 잡을 수 있게 하려는 것이고, 앱 전체가 클로저 하나로 표현된다.

```rust
slt::run(|ui| {
    ui.bordered(Border::Rounded).p(2).gap(1).col(|ui| {
        ui.text("hello").bold().fg(Color::Cyan);
        if ui.button("click").clicked { count += 1; }
    });
});
```

App 구조체도, 이벤트 루프도, 트레이트 구현도 없다.
즉시 모드(immediate mode) 렌더링이며 프레임당 1밀리초 수준이고, 의존성은 `crossterm`과 `unicode-width` 두 개다.
`cargo add superlighttui`로 설치해 편집기 없이 라이브러리만 쓸 수도 있다.

## 써 보기

가장 짧은 검증 경로는 템플릿에서 시작하는 것이다.
대시보드 템플릿을 열고 위젯 하나를 옮기거나 속성 하나를 바꾼 뒤 코드를 내보내면, 그 한 번의 왕복으로 이 도구가 실제로 무엇을 주는지 대부분 알 수 있다.

확인할 것은 세 가지다.

첫째, 내보낸 코드를 사람이 읽고 고칠 수 있는가.
생성 코드가 기계가 쓴 티가 심하게 나거나 한 함수에 전부 몰려 있으면, 처음 한 번은 빠르지만 그다음부터는 손으로 쓴 코드보다 느려진다.

둘째, 내가 필요한 위젯이 팔레트에 있는가.
50종이 넘는다는 숫자보다 중요한 것은 내 화면에 필요한 그 하나가 있는지다. 없으면 편집기 밖에서 직접 만들어야 하고, 그러면 편집기로 돌아갈 수 없게 된다.

셋째, 한글이 포함된 텍스트에서 폭 계산이 맞는가.
터미널에서 한중일 문자는 셀 두 개를 차지하며, 미리보기는 브라우저에서 렌더링되므로 실제 터미널과 어긋날 수 있다.
템플릿의 라벨 몇 개를 한글로 바꿔 보고, 내보낸 코드를 실제 터미널에서 실행해 테두리가 밀리지 않는지 보는 것이 이 도구를 채택할지 정하는 가장 실질적인 시험이다.

## 트레이드오프

### 한 방향 생성기는 첫 왕복만 빠르다

이 도구가 주는 것은 빈 화면에서 시작하는 비용의 제거다.
어떤 위젯이 있는지 목록으로 보이고, 배치가 즉시 눈에 보이고, 속성 이름을 문서에서 찾지 않아도 된다.
TUI 레이아웃은 눈으로 보기 전에는 감이 잘 오지 않는 영역이라 이 이점은 실질적이다.

대가는 왕복이 한 방향이라는 것이다.
내보낸 코드를 손으로 고치고 나면 편집기로 돌아갈 수 없고, 다시 내보내면 고친 것이 사라진다.
그래서 실제 프로젝트에서 이 도구의 수명은 대개 첫 화면까지이며, 그 이후로는 쓰지 않게 된다.

이 한계를 설계로 없애기는 어렵다.
양방향 편집을 지원하려면 생성 코드에 편집기가 읽을 수 있는 구조적 표시를 남겨야 하고, 그러면 “실제 라이브러리 API를 쓰는 평범한 코드”라는 이 도구의 핵심 장점이 훼손된다.
사람이 읽기 좋은 출력과 기계가 다시 읽을 수 있는 출력은 여기서 서로를 밀어낸다.

실무적인 절충은 경계를 미리 긋는 것이다.
레이아웃과 위젯 배치는 생성된 파일에 두고 로직은 별도 파일에 두면, 레이아웃을 다시 내보내도 로직은 살아남는다.
이 분리를 처음부터 하지 않으면 두 번째 내보내기 시점에 이미 늦는다.

### 기반 라이브러리가 편집기와 한 몸이다

SuperLightTUI만 정식 지원이고 나머지는 베타이거나 예정이라는 사실은, 이 도구를 쓰기로 하면 사실상 그 라이브러리를 쓰기로 하는 것임을 뜻한다.
Rust TUI 생태계에서 지배적인 것은 Ratatui이고, 그것은 아직 예정 상태다.

이 선택에는 얻는 것이 있다.
의존성 두 개, unsafe 없음, 2MB 미만이라는 특성은 실제로 가치가 있고, 특히 배포 크기와 감사 가능성이 중요한 환경에서 그렇다.

잃는 것은 생태계다.
Ratatui에는 예제와 서드파티 위젯과 스택오버플로 답변이 쌓여 있고, 문제에 부딪혔을 때 검색으로 해결될 확률이 훨씬 높다.
이 교환은 만든 사람도 명시적으로 인정한 것이다. GeekNews 글에서 그는 Ratatui가 좋은 생태계를 갖추고 있다고 전제한 뒤, 문제는 레이아웃을 잡는 데 드는 시간이라고 범위를 좁혔다.
GN 댓글 하나가 그 진단이 맞았음을 보여 준다. 한 사용자는 Ratatui를 쓰다가 귀찮아서 결국 안 쓰게 됐는데 딱 그 단점을 잡았다고 적었다.[^gn-ratatui]
생태계의 크기가 아니라 시작하는 데 드는 마찰이 실제 채택을 막고 있었다는 것이고, 이 도구가 겨냥한 자리가 거기다.
편집기가 주는 초기 속도와 생태계가 주는 중장기 속도 중 어느 쪽이 큰지는 프로젝트의 수명에 달려 있으며, 짧을수록 편집기가, 길수록 생태계가 이긴다.

여기서 흔한 기대가 통하지 않는다.
“나중에 Ratatui로 옮기면 된다”는 계획은 두 라이브러리의 API가 다르므로 사실상 재작성이고, 편집기가 Ratatui를 지원하게 되더라도 이미 손으로 고친 코드는 다시 내보낼 수 없다.
지원 예정 목록은 새로 시작하는 프로젝트에 대한 약속이지 이미 시작한 프로젝트의 이동 경로가 아니다.

### 시각적 편집이 터미널의 제약과 어긋나는 지점

웹사이트를 만들듯 터미널 UI를 만든다는 문구는 정확히 이 도구의 이점이자 위험이다.
브라우저 안의 미리보기는 픽셀 단위로 렌더링되지만 실제 출력은 문자 셀 격자다.
폰트, 셀 비율, 유니코드 폭, 터미널 팔레트가 전부 실행 환경에 달려 있고 미리보기는 그중 어느 것도 보장하지 않는다.

가장 자주 어긋나는 것이 폭이다.
미리보기에서 정렬이 맞아 보이는 표가 한글이나 이모지가 들어가는 순간 실제 터미널에서 틀어지고, 그것은 편집기에서 확인할 수 없다.
테마 일곱 가지도 마찬가지다. 편집기는 그 색을 그대로 보여 주지만 터미널은 자기 팔레트로 근사한다.

그래서 이 도구를 쓸 때 실제로 필요한 절차가 하나 늘어난다.
설계 → 내보내기 → 실행이 아니라, 설계 → 내보내기 → 실제 터미널에서 확인 → 설계로 돌아가기다.
그런데 앞서 본 대로 설계로 돌아가는 것은 손으로 고친 것을 버리는 일이므로, 이 확인은 손으로 고치기 전에 해야 한다.

## 함정

미리보기를 신뢰해 설계를 확정하면 나중에 되돌리기 비싸다.
실제 터미널에서 한 번 실행하기 전에는 레이아웃이 맞는지 알 수 없고, 실행은 코드를 내보낸 뒤에만 가능하다.

베타 표시를 가볍게 보면 안 된다.
Ink 지원은 위젯이 44종으로 줄어들며, 어떤 위젯이 빠졌는지는 설계를 다 하고 내보내는 시점에 드러난다.
TypeScript로 갈 계획이라면 필요한 위젯이 Ink 쪽 목록에 있는지 먼저 확인하는 것이 순서다.

내보낸 코드를 저장소에 커밋할 때 출처를 남기지 않으면 다음 사람이 헤맨다.
이 코드가 손으로 쓴 것인지 생성된 것인지, 다시 생성해도 되는지 아닌지가 파일만 봐서는 보이지 않는다.
생성된 파일의 맨 위에 출처와 다시 생성 가능 여부를 주석으로 적어 두는 것이 최소한의 조치다.

라이브러리 버전이 편집기에 고정되어 있다.
현재 SuperLightTUI v0.17.1을 대상으로 코드를 내보내므로, 프로젝트가 다른 버전을 쓰고 있으면 생성 코드가 컴파일되지 않을 수 있다.
1.0 이전 버전에서는 마이너 버전 사이에도 API가 바뀔 수 있다는 점을 전제해야 한다.

## 체크리스트

- 내보낸 코드를 실제 터미널에서 실행해 보았는가
- 한글 또는 이모지를 포함한 라벨로 폭 정렬을 확인했는가
- 필요한 위젯이 대상 프레임워크의 지원 목록에 있는가
- 레이아웃 파일과 로직 파일을 분리해 두었는가
- 생성된 파일에 출처와 재생성 가능 여부를 주석으로 남겼는가
- 프로젝트의 라이브러리 버전이 편집기가 대상으로 삼는 버전과 맞는가
- 이 프로젝트의 수명을 고려했을 때 생태계보다 초기 속도가 중요한가

## 기억할 원칙

### 코드 생성기의 가치는 생성 품질이 아니라 재생성 가능성에서 나온다

시각적 편집기가 내놓는 코드가 얼마나 깔끔한지는 첫인상을 좌우하지만 실제 수명은 결정하지 않는다.
결정하는 것은 손으로 고친 뒤에도 다시 생성할 수 있는가이며, 이 도구를 포함한 대부분의 한 방향 생성기는 그 답이 아니오다.

그래서 이런 도구를 평가할 때 던져야 할 질문은 “코드가 좋은가”가 아니라 “이 코드를 다시 생성할 일이 있을까”다.
한 번 만들고 끝나는 화면이면 생성기는 순이득이고, 계속 바뀌는 화면이면 첫 왕복의 이득을 두 번째 왕복에서 반납한다.
이 구분을 도입 전에 해 두면, 나중에 편집기를 버리게 되더라도 그것이 실패가 아니라 예정된 수순이 된다.
