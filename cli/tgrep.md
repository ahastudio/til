# tgrep: 트라이그램 색인으로 ripgrep보다 빠른 코드 검색

<https://github.com/microsoft/tgrep>

HN 토론: <https://news.ycombinator.com/item?id=49562928> (3점, 2개 댓글)

## 소개

Microsoft가 공개한 Rust 기반 정규식 검색 도구다.
겨냥하는 것은 대형 코드베이스이며, MIT 라이선스다.

기존 grep 계열과 갈라지는 지점은 하나다.
질의마다 모든 파일을 훑는 대신 트라이그램 색인을 미리 만들어 두고, 매치 가능성이 있는 파일만 골라낸 뒤 그 후보들만 병렬로 검색한다.
아주 큰 저장소에서는 ripgrep 대비 최대 52배 빠르다고 밝힌다.

운영 모델은 클라이언트/서버다.
서버를 한 번 띄워 두면 이후 검색이 즉시 이뤄진다는 것이 내건 문구이고, 실제로 GitHub Copilot CLI에 통합되어 대형 저장소 검색을 담당한다.

## 동작 방식

### 트라이그램 색인이 하는 일

트라이그램은 연속한 세 글자다.
`function`이라는 패턴은 `fun`, `unc`, `nct`, `cti`, `tio`, `ion`으로 쪼개지며, 색인은 각 트라이그램이 어느 파일에 있는지를 정렬된 포스팅 리스트로 갖고 있다.

질의가 들어오면 패턴에서 뽑은 트라이그램들의 포스팅 리스트를 교집합으로 좁혀 후보 파일 목록을 만든다.
README가 정렬된 포스팅 리스트의 교집합과 합집합을 재정렬 없이 처리한다고 밝히는 부분이 이 단계다.

여기서 중요한 성질은 색인이 답을 주지 않는다는 것이다.
색인은 “이 파일에는 확실히 없다”만 말해 주고, 후보로 남은 파일들은 전체 정규식 엔진으로 병렬 검증한다.
그래서 결과의 정확성은 ripgrep과 같고, 달라지는 것은 읽지 않아도 되는 파일의 수뿐이다.

이 구조가 성능 특성도 설명한다.
매치가 수만 건 나오는 질의는 색인이 아껴 준 시간보다 결과를 전달하는 데 드는 시간이 커져 이득이 줄어든다.
README가 이것을 직접 명시한다. 이득의 폭은 저장소 크기와 매치 개수에 달려 있다.

발상 자체는 새로운 것이 아니다.
HN에서 RicoElectrico는 같은 접근을 쓰는 선행 사례로 `grip`을 들며 README가 그것을 언급하지 않은 것이 이상하다고 지적했다.[^RicoElectrico]
코드 검색에 트라이그램 색인을 쓰는 것은 Google Code Search 시절부터 알려진 기법이므로, tgrep이 내세울 수 있는 것은 착상이 아니라 구현의 완성도와 서버 모델과 배포 채널이다.

### 색인 계층

색인이 세 층으로 되어 있다.

| 구성 요소   | 역할                                    |
| ----------- | --------------------------------------- |
| IndexReader | mmap된 디스크 색인. 이진 탐색으로 조회  |
| LiveIndex   | 최근 수정된 파일을 담는 메모리 오버레이 |
| HybridIndex | 둘을 합치되 오버레이를 우선             |

이 분리가 파일이 바뀌는 동안에도 검색이 정확한 이유다.
디스크 색인은 마지막 빌드 시점의 것이고, 그 이후 수정된 파일은 LiveIndex가 덮어쓴다.
파일시스템 감시가 기본이고 그것이 안 되는 환경에서는 폴링으로 대체된다.

빌드 쪽에도 경계가 잡혀 있다.
백그라운드 인덱서가 rayon으로 1,024개 파일씩 병렬 처리하고, 5만 개 파일마다 또는 5분마다 주기적으로 디스크에 플러시해 메모리를 묶어 둔다.
빌드 중 외부 병합 정렬을 써서 힙이 폭주하지 않게 한다는 설명도 같은 목적이다.

그리고 색인이 끝나기를 기다릴 필요가 없다.
백그라운드 인덱싱이 진행되는 동안에도 질의가 바로 동작한다.

### 서버

통신은 줄 단위로 구분되는 TCP 위의 JSON-RPC 2.0이다.
파일 캐시는 5만 항목 LRU이며 `RwLock`으로 읽기 경합 없이 동시 질의를 받는다.

## 설치하고 쓰기

```bash
# Homebrew
brew install tgrep

# 소스에서
git clone https://github.com/microsoft/tgrep.git
cd tgrep
cargo install --path tgrep-cli --locked
```

Linux, macOS(Intel과 Apple Silicon), Windows용 사전 빌드 바이너리도 릴리스 페이지에 있다.

색인을 만들고 서버를 띄운 뒤 검색하는 순서다.

```bash
# 색인 만들기
tgrep index .                          # 현재 디렉터리
tgrep index . --exclude vendor         # 특정 디렉터리 제외
tgrep index . --index-path /tmp/idx    # 색인 위치 지정

# 서버 띄우기 (색인이 없으면 자동으로 만든다)
tgrep serve .
tgrep serve . --watch-mode poll        # 네이티브 감시가 안 되는 환경

# 검색
tgrep "pattern" .
tgrep "TODO|FIXME" .                   # 교대(alternation)
tgrep "error" . -i                     # 대소문자 무시
tgrep -F "Vec<T>" .                    # 리터럴 문자열
tgrep "MyStruct" . -l                  # 파일 이름만
tgrep "pattern" . --stats              # 소요 시간과 질의 계획 확인

# 상태 확인
tgrep status .
```

`--stats`가 도입 판단에 가장 유용한 플래그다.
질의 계획을 보여 주므로 색인이 후보를 얼마나 좁혔는지, 시간이 색인 조회에서 갔는지 후보 검증에서 갔는지를 알 수 있다.

### 플래그는 ripgrep 어휘를 따른다

옮겨 가는 비용을 낮추려는 설계가 플래그에 드러난다.

| 범주 | 플래그                                                                            |
| ---- | --------------------------------------------------------------------------------- |
| 매칭 | `-i`, `-S`(스마트 케이스), `-F`, `-w`, `-v`, `-U`(멀티라인), `-P`(PCRE2)          |
| 출력 | `-n`, `-c`, `-l`, `-o`, `-A`/`-B`/`-C`, `--json`, `--vimgrep`, `--color`          |
| 필터 | `-g`, `-t`/`-T`, `--max-filesize`(기본 64M), `-L`, `-.`(숨김 파일), `--no-ignore` |
| 기타 | `-E`(인코딩), `-r`(치환), `-m`, `-j`, `-x`                                        |

`--json`이 ripgrep 호환 형식이라는 점이 특히 실무적이다.
ripgrep의 JSON을 파싱하는 편집기 플러그인이나 스크립트가 이미 있다면 그 파이프라인을 그대로 둘 수 있다.

`-P`로 PCRE2 백트래킹 엔진을 쓸 수 있는 것도 짚어 둘 만하다.
전방 탐색(lookahead)이나 역참조(backreference)가 필요한 패턴은 트라이그램으로 후보를 좁히기 어려운 종류이므로, 이 조합에서는 색인의 이득이 줄어든다고 보는 편이 맞다.

## 색인 관련 설정 정하기

| 옵션              | 기본값 | 무엇을 정하는가                  |
| ----------------- | ------ | -------------------------------- |
| `--max-cpu`       | 50     | 색인이 쓸 CPU 비율 상한          |
| `--max-memory`    | —      | 이 값에 도달하면 디스크로 플러시 |
| `--poll-interval` | 120초  | 폴링 감시 주기                   |
| `--watch-budget`  | 8192   | 네이티브 감시 대상 수 상한       |
| `--max-filesize`  | 64M    | 이 크기를 넘는 파일은 건너뜀     |
| `--index-path`    | —      | 색인 디렉터리 위치               |

기본값이 왜 그런지가 곧 조정 기준이다.

`--max-cpu` 기본값 50은 색인이 개발 작업을 방해하지 않게 하려는 값이다.
최초 색인을 빨리 끝내고 싶으면 일시적으로 올리고, 평소에는 되돌리는 편이 낫다.

`--watch-budget` 8192는 OS의 파일 감시 핸들이 유한하다는 사실에서 나온 값이다.
이 수를 넘는 디렉터리를 감시하려 하면 감시 자체가 실패할 수 있으므로, 대형 저장소에서는 이 한도에 걸려 폴링으로 내려가는지 확인해야 한다.

`--poll-interval` 120초는 폴링 모드에서 수정이 검색에 반영되기까지의 최대 지연이다.
방금 고친 코드를 바로 찾아야 하는 작업 흐름이라면 이 값이 체감을 좌우한다.

`--index-path`는 색인을 저장소 밖에 두고 싶을 때 쓴다.
색인은 파생 데이터이므로 백업 대상이나 동기화 폴더 안에 두면 용량과 동기화 비용만 늘어난다.

## 성능

README가 제시하는 벤치마크다.

| 저장소    | 파일 수 | 플랫폼      | ripgrep  | tgrep   | 배수  |
| --------- | ------- | ----------- | -------- | ------- | ----- |
| gecko-dev | 388K    | macOS arm64 | 33,402ms | 643ms   | 51.9x |
| gecko-dev | 388K    | Windows     | 17,841ms | 463ms   | 38.6x |
| chromium  | 504K    | macOS arm64 | 41,806ms | 2,643ms | 15.8x |
| linux     | 96K     | macOS arm64 | 5,390ms  | 256ms   | 21.0x |
| linux     | 96K     | Windows     | 3,280ms  | 94ms    | 34.8x |
| go        | 16K     | Windows     | 592ms    | 79ms    | 7.53x |

읽는 방법이 중요하다.
이 숫자들은 서버가 이미 떠 있고 색인이 완성된 상태의 질의 시간이며, 색인 구축 시간은 포함되지 않는다.
그리고 파일 수가 16K인 go에서는 7.5배로 떨어진다. 저장소가 작을수록 이득이 줄어든다는 뜻이고, 대부분의 사내 저장소는 이 구간에 있다.

Windows에서 배수가 더 크게 나오는 것도 같은 원리다.
ripgrep의 절대 시간이 macOS보다 짧은데도 배수가 커지는 gecko-dev 사례처럼, 플랫폼별 파일 시스템 호출 비용이 결과를 좌우한다.
즉 이 표가 재는 것은 tgrep의 빠름만이 아니라 전수 탐색이 얼마나 비싼 환경인가이기도 하다.

## 트레이드오프

### 상주 프로세스를 하나 더 갖는 값

가장 큰 거래가 이것이다.
grep과 ripgrep은 실행하면 끝나는 프로그램이고, tgrep은 서버가 떠 있어야 제 성능이 나온다.

얻는 것은 분명하다. 첫 질의부터 마지막 질의까지 색인이 메모리에 있고, 파일 변경이 감시되어 색인이 계속 최신으로 유지된다.

대가는 두 가지다.
하나는 자원이다. 파일 캐시 5만 항목과 메모리 오버레이와 감시 핸들이 저장소마다 붙으며, 여러 저장소를 오가면 서버도 여러 개가 된다.
다른 하나는 상태다. 서버가 죽어 있거나 다른 커밋 시점의 색인을 들고 있으면 결과가 조용히 달라진다.

여기서 흔한 기대가 통하지 않는다.
“필요할 때만 띄우면 되지 않나”는 생각이 자연스럽지만, 그러면 매번 색인 적재 비용을 치르게 되어 서버 모델의 이점이 사라진다.
`tgrep status`로 서버 상태를 확인하는 습관이 사실상 필수이고, 이것이 무상태 도구와의 진짜 차이다.

### 색인이 낡을 수 있다는 것

LiveIndex와 파일시스템 감시가 이 문제에 대한 대응이지만 완전히 없애지는 못한다.

네이티브 감시는 `--watch-budget` 한도가 있고, 그 한도를 넘거나 지원되지 않는 환경에서는 폴링으로 내려간다.
폴링 기본 주기는 120초다. 그 사이의 수정은 검색에 잡히지 않는다.

이 지연이 문제가 되는 상황은 구체적이다.
`git checkout`으로 브랜치를 갈아타면 수천 개 파일이 한꺼번에 바뀌고, 그 직후의 검색 결과는 어느 시점의 것인지 알기 어렵다.
감시가 정상 동작해도 인덱싱이 따라잡는 데 시간이 걸린다.

양쪽을 다 가질 수는 없다.
색인을 항상 정확하게 유지하려면 매 질의마다 파일 상태를 확인해야 하고 그러면 전수 탐색과 다를 바 없어진다.
현실적인 대응은 결과가 이상할 때 색인을 의심하는 습관을 갖는 것이고, 그래서 `--no-index` 플래그가 존재한다.
이 플래그로 색인 없이 전 파일을 훑어 같은 결과가 나오는지 비교하면 색인 문제인지 패턴 문제인지 갈린다.

### 트라이그램이 못 좁히는 패턴

색인의 이득은 패턴에서 뽑을 수 있는 트라이그램에 비례한다.
세 글자 미만의 짧은 패턴, 정규식 메타 문자가 대부분인 패턴, 전방 탐색이나 역참조를 쓰는 패턴은 후보를 좁히지 못한다.

이 경우 tgrep은 사실상 후보 전체를 검증하게 되어 ripgrep과 비슷하거나 색인 조회 비용만큼 느려진다.
README가 매치가 많은 질의에서 이득이 줄어든다고 밝힌 것과는 다른 종류의 손실이며, 이쪽은 README에 명시되지 않는다.

실무적으로는 `--stats`가 이 상황을 드러낸다.
후보 파일 수가 전체 파일 수와 비슷하게 나오면 색인이 일을 못 한 것이고, 그 패턴 계열은 tgrep으로 굳이 돌릴 이유가 없다.

### 도구를 하나 더 배우지 않아도 되는 설계

플래그 어휘를 ripgrep에 맞추고 `--json`을 호환 형식으로 낸 것은 도입 마찰을 줄이는 명백한 이점이다.
편집기 통합이나 스크립트에서 `rg`를 `tgrep`으로 바꾸는 것만으로 대체가 되도록 한 설계다.

다만 호환은 완전한 동일성이 아니다.
같은 플래그 이름이라도 색인을 전제로 한 도구에서는 `--no-ignore`나 `-.`(숨김 파일 포함) 같은 옵션이 색인에 포함되지 않은 파일에 대해 어떻게 동작하는지가 따로 결정된다.
색인 시점에 제외한 것을 검색 시점 플래그로 되살릴 수는 없으며, `--exclude vendor`로 색인을 만들어 두고 나중에 `vendor` 안을 찾으려 하면 결과가 비어 나온다.

## 함정

색인 시점의 제외 설정이 검색 결과를 조용히 제한한다.
`tgrep index . --exclude vendor`로 만든 색인에서는 그 디렉터리가 영영 검색되지 않으며, 검색 명령에는 아무 경고가 나오지 않는다.

`--max-filesize` 기본값 64M이 큰 파일을 말없이 건너뛴다.
생성된 코드나 대형 데이터 파일을 찾을 때 결과가 없다면 파일 크기를 먼저 의심해야 한다.

서버가 감시 대상 한도에 걸리면 조용히 폴링으로 내려간다.
그때부터 최대 120초의 지연이 생기지만 검색 명령은 평소와 똑같이 동작한다.

브랜치를 갈아탄 직후의 검색 결과는 신뢰하기 어렵다.
수천 개 파일이 한꺼번에 바뀐 상태에서 인덱서가 따라잡는 중이기 때문이다.

색인 디렉터리를 저장소 안에 두면 백업과 동기화 대상이 된다.
파생 데이터이므로 `--index-path`로 저장소 밖에 두거나 최소한 무시 목록에 넣어야 한다.

벤치마크 배수를 그대로 기대하면 실망한다.
표의 가장 큰 숫자는 파일 38만 개짜리 저장소의 것이고, 파일 1만 6천 개에서는 7.5배로 떨어진다.

## 확인하기

도입 판단은 자기 저장소에서 두 가지를 재는 것으로 충분하다.

```bash
# 1) 색인 구축에 얼마나 걸리는지, 색인이 얼마나 큰지
time tgrep index . --index-path /tmp/tgrep-idx
du -sh /tmp/tgrep-idx

# 2) 실제로 쓰는 패턴으로 비교
tgrep serve . --index-path /tmp/tgrep-idx &
time rg "자주-쓰는-패턴" .
time tgrep "자주-쓰는-패턴" . --stats
```

`--stats` 출력에서 볼 것은 총 시간이 아니라 후보 파일 수다.
전체 파일 수 대비 후보가 얼마나 줄었는지가 이 저장소에서 색인이 얼마나 일하는지를 직접 보여 준다.

그다음은 낡은 색인 시나리오다.
파일 하나를 고치고 바로 그 내용을 검색해 잡히는지, 잡히지 않는다면 몇 초 뒤에 잡히는지를 재면 감시가 네이티브인지 폴링인지 알 수 있다.
브랜치를 갈아탄 직후에 같은 검사를 반복하면 대량 변경 상황에서의 지연도 나온다.

## 체크리스트

- 자기 저장소의 파일 수가 벤치마크의 어느 구간에 해당하는지 확인했는가
- 색인 구축 시간과 색인 크기를 재 보았는가
- `--stats`로 후보 파일이 실제로 좁혀지는지 확인했는가
- 실제로 자주 쓰는 패턴으로 ripgrep과 비교했는가
- 파일을 고친 직후 검색에 반영되는 지연을 측정했는가
- 네이티브 감시가 동작하는지, 폴링으로 내려갔는지 확인했는가
- 색인 디렉터리를 저장소 밖이나 무시 목록에 두었는가
- `--exclude`로 제외한 경로를 나중에 찾을 일이 없는지 확인했는가

## 기억할 원칙

### 색인은 답을 주는 것이 아니라 읽지 않아도 될 것을 알려 준다

tgrep의 정확성이 ripgrep과 같은 이유가 여기 있다.
트라이그램 색인은 “이 파일에 매치가 있다”를 말하지 않고 “이 파일에는 확실히 없다”만 말하며, 남은 후보는 전부 진짜 정규식 엔진으로 검증된다.

이 구조가 주는 이점은 성능보다 신뢰다.
색인이 틀리거나 낡으면 결과가 덜 나올 수는 있어도 없는 매치가 생기지는 않으며, 실패 방향이 한쪽으로 고정된다.
그래서 이상하면 `--no-index`로 확인하는 절차가 성립한다.

같은 형태가 검색 시스템 전반에 있다.
블룸 필터, 파티션 프루닝, 쿼리 플래너의 인덱스 스캔이 전부 후보를 좁히고 정확한 판정은 뒤로 미루는 구조다.
새로운 검색 도구를 평가할 때 던질 질문 하나가 여기서 나온다. 이 색인은 후보를 좁히는가, 아니면 답을 대신 내놓는가.
후자라면 색인이 낡았을 때의 실패가 조용하고 위험하다.
