# ANSI 이스케이프 코드에 표준이 있기는 한가

원문: [Standards for ANSI escape codes](https://jvns.ca/blog/2025/03/07/escape-code-standards/)

HN 토론: <https://news.ycombinator.com/item?id=43298930> (24점, 3개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/mpvjj8/standards_for_ansi_escape_codes> (29점, 8개 댓글)

## 요약

Julia Evans가 2025년 3월 7일에 쓴 글이다.

출발점이 솔직하다. 오랫동안 ANSI 이스케이프 코드를 **“터미널에서 글자를 빨갛게 만드는 그거”** 정도로만 막연히 알았고, 어디에 정의되어 있어야 하는지나 표준이 있는지는 **전혀 이해하지 못한 채 “여기 용이 산다”는 막연한 느낌**만 있었다는 것이다.

한 해 동안 터미널을 공부하며 두 가지를 배웠다고 밝힌다.

이스케이프 코드가 **터미널의 많은 사용성 개선을 책임진다**는 것이 하나다.
그리고 예로 든 것이 인상적이다. **원격 기계에 SSH로 들어가 있을 때 시스템 클립보드로 복사하는 방법이 있다는 것을 아는가? `OSC 52`라는 이스케이프 코드다.**

다른 하나는 **완전히 표준화되어 있지 않아서 늘 안정적으로 동작하지는 않는다**는 것이다.
그리고 **보이지 않기까지 해서 이스케이프 코드 문제를 해결하는 것이 대단히 답답하다**고 적는다.

그래서 이 글을 쓴 이유를 밝힌다.
**이것들이 꼭 불안정하고 답답해야만 하는지, 아니면 우리 모두가 더 확신을 갖고 의지할 수 있는 미래가 있는지** 알고 싶었다는 것이다.

### 이스케이프 코드가 무엇인가

터미널에서 왼쪽 화살표를 누르고 `^[[D`를 본 적이 있다면 그것이 이스케이프 코드다.
첫 문자가 “이스케이프” 문자라서 그렇게 부르며, 보통 `ESC`, `\x1b`, `\E`, `\033`, `^[`로 쓴다.

두 종류가 있다.

**입력 코드**는 유니코드에 들어맞지 않는 키 입력이나 마우스 움직임에 대해 터미널 에뮬레이터가 보내는 것이다. 왼쪽 화살표가 `ESC[D`, `Ctrl+왼쪽`이 `ESC[1;5D`, 마우스 클릭이 `ESC[M :3` 같은 것이다.
**출력 코드**는 프로그램이 색을 입히고 커서를 옮기고 화면을 지우고 커서를 숨기고 클립보드로 복사하고 마우스 보고를 켜고 창 제목을 정하려고 출력하는 것이다.

### 표준들

**ECMA-48**이 처음 찾은 표준이고 1976년에 처음 나왔다.

두 가지를 한다.
이스케이프 코드의 **일반적 형식**을 정의하고(`ESC[`로 시작하는 CSI 코드, `ESC]`로 시작하는 OSC 코드),
구체적인 코드를 정의한다(커서 왼쪽 이동이 `ESC[D`, 글자를 빨갛게가 `ESC[31m`).

형식이 확장 가능해서 나중에 다른 이들이 더 정의할 여지가 있다.
그래서 **오늘날 흔한 이스케이프 코드 상당수가 ECMA-48에 정의되어 있지 않다**. 예를 들어 vim이나 htop이나 tmux가 마우스를 지원하는 것이 흔한데 ECMA-48에는 마우스 코드가 없다.

**xterm 제어 시퀀스**가 그 공백을 메운다.
마우스 보고 활성화, 괄호 붙여넣기, OSC 52 같은 것들이 xterm에서 왔고 `XTerm Control Sequences` 문서에 정리되어 다른 에뮬레이터들이 널리 구현했다고 저자는 이해한다(틀리면 알려 달라고 덧붙인다).
**정확히 표준은 아니지만 xterm이 대단히 영향력 있어서 중요한 문서로 보인다**는 것이다.

**terminfo**가 세 번째다.
80년대에는 터미널마다 실제로 지원하는 이스케이프 코드의 차이가 엄청났고, 그것을 다루려고 만든 데이터베이스다.
표준은 `X/Open Curses`인 것 같은데 **어째선지 계정을 만들어야 볼 수 있다**고 적는다. 데이터베이스 형식과 그것에 접근하는 C 라이브러리 인터페이스(“curses”)를 정의한다.

```bash
# 시스템이 아는 모든 터미널의 "화면 지우기" 코드를 본다
for term in $(toe -a | awk '{print $1}')
do
  echo $term
  infocmp -1 -T "$term" 2>/dev/null | grep 'clear=' | sed 's/clear=//g;s/,//g'
done
```

### 프로그램이 terminfo를 써야 하는가

저자가 흥미롭다고 본 지점이 애플리케이션의 두 접근이다.

**`TERM` 환경 변수에 따라 terminfo로 어떤 코드를 쓸지 알아내는 것**(fish가 이렇게 한다)과,
**“충분히 많은” 에뮬레이터에서 동작하는 “하나의 공통 집합”을 정해 하드코딩하는 것**이다.

두 번째를 택한 예로 kakoune, python-prompt-toolkit, linenoise, libvaxis, chalk를 든다.

왜 terminfo에서 멀어지는지 궁금해져서 찾아보니 fish 메인테이너의 **아주 흥미롭고 대단히 상세한 terminfo 비판**이 있었다고 소개한다.
인용된 문장이 이렇다. **“[terminfo 저자들은] 당시에는 대단히 중요하고 도움이 되는 일을 많이 했다. 내 요점은 이제는 그렇지 않다는 것이다.”**

### “하나의 공통 집합”이 있기는 한가

저자가 **이 답을 정말로 모른다**고 밝히면서, 읽어 본 바로는 이 조합인 것 같다고 정리한다.

VT100이 지원한 코드들(일부는 현대 터미널과 무관), ECMA-48에 있는 것(역시 일부는 무관), xterm이 지원하는 것(전부가 충분히 널리 지원되지는 않을 것), 그리고 어쩌면 궁극적으로는 **“사용자가 가장 자주 쓸 것 같은 에뮬레이터를 정해서 거기서 시험하는 것”**이다. 웹 개발자가 어떤 CSS 기능을 써도 되는지 정할 때처럼.

그런데 **터미널에는 Can I use나 Baseline 같은 자료가 없다**고 짚는다.
이론상 terminfo가 터미널의 caniuse여야 하지만, **새 기능이 발명되고 나서 추가되기까지 10년 넘게 걸리는 경우가 많아 아주 제한적**이라는 것이다.

### terminfo를 쓸 이유

Mastodon에 2025년에 terminfo가 왜 가치 있는지 물어 납득할 만한 답을 몇 개 얻었다고 한다.

`TERM=dumb` 같은 식으로 **`TERM`으로 프로그램 동작을 제어할 수 있기를 기대하는 사람들이 있는데 terminfo 이후 세계에서 그것이 어떻게 되어야 하는지에 대한 표준이 없다**는 것이 하나다.

80년대보다 차이가 **적어졌지만 0과는 거리가 멀다**는 것이 둘이다.
그래픽 터미널, 리눅스 프레임버퍼 콘솔, 서버의 시리얼 콘솔로 접속한 상황, Emacs 셸 모드, 그 밖에 자기가 놓친 것들이 있다는 것이다.

**“하나의 공통 집합”이 무엇인지에 대한 표준이 없고, 프로그램이 실제로는 충분히 널리 지원되지 않는 코드를 쓰기도 한다**는 것이 셋이다.

### terminfo와 사용자 에이전트 탐지

이 글에서 가장 좋은 비유가 여기 나온다.

ncurses가 `TERM`으로 어떤 코드를 쓸지 정하는 방식이, **웹 서버가 브라우저 사용자 에이전트로 어떤 버전의 사이트를 낼지 정하던 것을 떠올리게 한다**는 것이다.

그리고 결과도 비슷해 보인다고 짚는다.
**iTerm2가 자기를 `xterm-256color`라고 보고하는 것**이 Safari의 사용자 에이전트가 `Mozilla/5.0 ... AppleWebKit/605.1.15 (KHTML, like Gecko) ... Safari/605.1.15`인 것과 비슷하다는 것이다.
둘 다 **잘 동작하지 않는 사용자 에이전트 탐지를 우회하려고 자기 정체를 바꾼 것**이다.

그런데 결론은 유보적이다.
웹에서는 사용자 에이전트 탐지가 좋은 관행이 아니라고 결론짓고 표준화에 집중해 같은 HTML/CSS를 모든 브라우저에 내기로 했는데, **터미널에서도 같은 접근이 미래일지는 모르겠다**는 것이다.
**오늘날 터미널 지형이 웹이 그랬던 것보다 훨씬 파편화되어 있고 자금도 훨씬 적기 때문**이다.

## 분석

### 제목이 묻는 질문에 답이 이미 있다

이 글의 가장 큰 문제를 tssva가 HN에서 짚었다.[^tssva]

**저자가 ANSI 이스케이프 코드와 터미널 이스케이프 코드 일반을 혼동하고 있으며**, 그 때문에 ANSI 이스케이프 코드가 표준화되어 있지 않다고 선언하는데 **그것이 좀 우스운 말**이라는 것이다.

이유가 명확하다. **ANSI X3.64 표준으로 표준화되었고 그래서 ANSI 이스케이프 코드라고 부른다**는 것이다.
그런데 **글에 ANSI X3.64가 아예 언급되지 않는다**.
X3.64는 ISO 6429로 대체되어 철회되었는데 **그것도 언급되지 않는다**. ISO 6429가 ECMA-48에 기반하고, 글에 나오는 것은 ECMA-48뿐이다.

그다음 지적이 핵심이다.
글이 그 뒤에 여러 다른 터미널 이스케이프 코드 집합의 문서를 참조하는데, **그것들은 ANSI 이스케이프 코드의 일부가 아니다**.

이 정정이 이 글의 구조를 다시 보게 만든다.

실제 상황은 이렇다.

| 구분                  | 표준화 상태                                      |
| --------------------- | ------------------------------------------------ |
| ANSI 이스케이프 코드  | **표준화되어 있다** (X3.64 → ISO 6429 ≒ ECMA-48) |
| xterm 확장            | 표준 아님. 문서만 있음                           |
| OSC 52, 괄호 붙여넣기 | 표준 아님                                        |
| kitty 키보드 프로토콜 | 표준 아님                                        |
| 마우스 보고           | 표준 아님                                        |

그러므로 저자가 느낀 불안정함의 원인은 **표준이 없어서가 아니라, 실제로 쓰는 것 대부분이 표준 밖이기 때문**이다.

그리고 그 편이 더 나쁜 진단이다.
표준이 없으면 만들면 되지만, **표준이 있는데 아무도 그 범위 안에서만 살 수 없다면** 표준을 하나 더 만드는 것으로 해결되지 않는다.

저자가 이 구분을 했다면 마지막 절의 희망 — HTML/CSS도 나빴는데 지금은 훨씬 낫다 — 이 다르게 읽혔을 것이다.
웹의 문제는 표준의 부재가 아니라 **구현의 불일치**였고, 터미널의 문제는 **사람들이 쓰는 기능의 대부분이 애초에 표준 대상이 아니라는 것**이다.

### 사용자 에이전트 비유가 정확한데 결론이 반대로 나온다

저자의 `TERM` ↔ User-Agent 비유가 이 글에서 가장 좋은 부분이다.

그리고 이 비유가 실제로 얼마나 정확한지 cblake가 Lobste.rs에서 확인했다.[^cblake]

**“xterm이라고 거짓말하는” 경향이 최소 25~30년, 어쩌면 더 오래되었다**는 것이다.
그리고 오늘의 상황을 이렇게 표현할 수 있겠다고 정리한다. **우리에게는 다양한 정도의 에뮬레이션 충실도와 다양한 확장을 가진 “xterm의 에뮬레이터들”이 있다.**

이 문장이 웹의 역사와 정확히 겹친다. 모든 브라우저의 User-Agent가 `Mozilla/5.0`으로 시작하는 것과 같은 구조다.

그런데 저자가 이 비유에서 끌어낸 결론이 웹과 반대 방향이다.
웹은 **탐지를 버리고 표준화로 갔는데**, 터미널은 파편화와 자금 부족 때문에 같은 길이 가능할지 모르겠다는 것이다.

여기서 한 걸음 더 갈 수 있었다.

웹이 사용자 에이전트 탐지를 버릴 수 있었던 것은 **기능 탐지(feature detection)로 대체했기 때문**이다. `if (window.IntersectionObserver)` 같은 것이다.
터미널에 그에 해당하는 것이 무엇인가.

`XTGETTCAP`이 그것이고, 앞서 [터미널 프로그램 규칙 문서](terminal-program-rules.md)에서 johannes가 언급한 대로 **`$TERM`과 무관하며 SSH 너머로도 동작한다**.
DA1/DA2(Device Attributes) 질의와 kitty의 기능 질의도 같은 계열이다.

즉 저자가 던진 “이것이 꼭 불안정해야 하는가”라는 질문에 대한 기술적 답이 이미 존재한다.
없는 것은 메커니즘이 아니라 **채택**이다.

### terminfo에 대한 판단이 정반대로 갈린다

이 글이 terminfo를 쓸지 말지를 양쪽 다 소개하고 판단을 유보한다.

댓글에서는 양쪽이 선명하게 갈렸다.

kazinator가 쓰지 말자는 쪽이다.[^kazinator]
**terminfo를 쓰지 않으며 ANSI 터미널 제어보다 덜 표준화되어 있다**는 것이다. POSIX가 존재 말고는 거의 아무것도 정의하지 않는다고 짚는다.
완전히 다른 터미널에서 프로그램이 동작하게 도울 수는 있지만 **모든 것이 ANSI를 말하는 세상에서는 그것이 거의 가치가 없다**는 것이다.
ANSI에 대한 터미널별 확장이 있고 일부는 인기가 있어 사실상 표준이니 써도 되는데, **terminfo는 어디서나 동작하지 않는 것들에 대해 도움이 되지 않는다**고 정리한다.
**기능이 존재하지 않는 곳에 그 기능을 마법처럼 생기게 할 수는 없기 때문**이다.

smarks는 역사를 아는 쪽에서 비슷한 결론에 도달했다.[^smarks]
1980년대 BSD termcap과 System V terminfo까지 거슬러 아는데, **원리상 terminfo가 더 나을 수 있었다**는 것이다. 데이터를 이진 형식으로 컴파일해 대체로 바로 쓸 수 있게 했으므로, 매번 전체 termcap 파일을 파싱하는 것보다 나았다는 것이다.
그런데 **대부분의 이진 형식처럼 까다롭고 취약하고 다루기 어려웠다**고 적는다.
그 사이 몇 년간 이것을 놓치고 있었는데 **반쯤 방치되고 대체로 유지보수되지 않는 것을 보니 슬프다**며, 새로 알게 된 것은 **어쩌면 이제 이것이 필요 없을지도 모른다는 것**이라고 맺었다.

그런데 이 문서와 같은 시기의 다른 글에서는 정반대 진단이 나왔다.

[터미널 불만 설문 문서](terminal-frustrations.md)에서 quotemstr가 색 문제의 원인 일부가 **terminfo와 `TERM`을 무시하고 이스케이프 시퀀스를 하드코딩하는 경향**이라고 지목했고, 문제 패키지로 든 것이 prompt_toolkit·chalk·linenoise다.

이 글이 “terminfo를 안 쓰는 예”로 든 목록과 **정확히 같다**.

그러니 상황이 이렇다. 같은 관행을 두고 한쪽은 **낡은 것을 버린 진보**로 보고 다른 쪽은 **색이 깨지는 원인**으로 본다.

그리고 둘 다 맞을 수 있다.
kazinator의 말대로 terminfo가 없는 기능을 만들어 주지는 않지만, 하드코딩하면 **있는 기능도 못 쓰게 된다**. `TERM=dumb`이나 리눅스 콘솔이나 시리얼 콘솔에서 그렇다.

저자가 Mastodon에서 얻은 세 가지 이유가 정확히 그 경계를 그린다. **변이가 0은 아니다.**

## 비평

### 표준화가 안 되는 이유가 기술이 아니라 사회라는 것이 드러났다

저자가 마지막에 **“표준화가 쉽지 않고 무슨 어려움이 있는지도 다 모른다”**고 적는다.

Lobste.rs 댓글이 그 어려움의 정체를 알려 준다.

mattrose가 정리했다.[^mattrose]
**모든 터미널 에뮬레이터 저자와 그 지지자들에게서 합의를 얻는 것이 정치적 악몽**이라는 것이다.
그리고 관찰을 하나 덧붙인다. **어째선지 터미널 에뮬레이터를 쓰는 사람들이 평균보다 무뚝뚝하고 퉁명스럽다**는 것이다.
Egmont Koblinger가 이 분야의 관심 당사자들을 위한 WHATWG 비슷한 것을 만들려 했고(freedesktop의 `terminal-wg`), **기본적으로 시도하다 소진되었다**고 전한다. 가을에 시간이 나면 되살려 볼까 한다고 덧붙였다.

Screwtape가 왜 안 되는지를 설명했다.[^Screwtape-wg]
**WHATWG는 대략 같은 대상 독자를 가지고 협력에서 이득을 볼 구성원이 몇 안 되었다**는 것이다.
반면 **터미널은 보통 취미로 개발하는 사람들이 만들고, 각자 “이래야 한다”는 특유의 생각이 있으며, 마음을 바꿀 진짜 이유가 없다**는 것이다.
다른 터미널과 버그까지 호환되게 만드는 것이 **주가나 광고 수익을 올려 주지 않으면서 슬프게 만들고, 또 다른 이미지 임베딩 시스템이나 MIDI 이벤트 인코딩 방법을 구현할 시간을 뺏는다**고 적었다.
누군가 터미널이 무엇이 될 수 있고 되어야 하는지에 대한 명확한 비전을 갖고 그 방향으로 합의를 쌓는 힘든 일을 하기 전까지는 **어떤 터미널 워킹 그룹도 성공하지 못할 것**이라는 결론이다.

그리고 **당사자의 증언**이 나왔다.

junon이 자기를 **Chalk(JavaScript) 메인테이너**라고 밝히며 적었다.[^junon]
몇 년 전에 자기도 이것을 시도했다가 포기했다는 것이다.
작업 부담을 덜어 주려고 **표준 스위치 등을 통합하는 PR을 자기가 먼저 열어도 되겠느냐고 물었는데, 몇몇 에뮬레이터 메인테이너에게서 단호하게 “안 된다”는 답을 받았다**는 것이다.

이 증언이 중요한 이유가 있다.

Chalk는 이 글이 **“terminfo를 안 쓰는 라이브러리”**로 지목한 바로 그 목록에 있다.
그런데 그 메인테이너가 표준화를 시도했고 거절당했다.

즉 하드코딩이 게으름이나 무지의 결과가 아니라 **협력이 거부된 뒤의 선택**이었다는 뜻이다.

이것이 저자가 던진 질문 — 꼭 이래야 하는가 — 에 대한 실질적인 답이다.
기술적으로는 아니고, **사회적으로는 그렇다**.

### terminfo를 버리자는 주장이 데이터베이스의 다른 값어치를 놓친다

terminfo 논쟁이 “이스케이프 코드를 조회하는 용도”에만 집중되는데, Lobste.rs에서 다른 값어치가 드러났다.

Screwtape가 권했다.[^Screwtape-db]
터미널 역사에 조금이라도 관심이 있다면 **terminfo 데이터베이스 소스 코드를 뒤져 보기를 추천한다**는 것이다.
**tzdata 데이터베이스처럼, 실제 정의와 나란히 어떻게 이렇게 되었고 왜 이런지를 설명하는 주석이 많다**는 것이다.

brandon이 그 값어치를 겪은 이야기를 적었다.[^brandon]
몇 년 전 H19 Heathkit 터미널과 통신을 확립하는 데 도움이 된 것이 바로 그 terminfo 데이터베이스 주석이었다는 것이다.
이스케이프 코드에 대한 건조한 기계 판독용 서술을 **DIP 스위치가 무엇을 설정하는지에 대한 유쾌하고 완전한 요약으로 보충해 주었기 때문**이다.

```text
# Here is a description of the H19 DIP switches: ...
# S402
# 0 = block cursor (0 = underscore cursor)
# 1 = no key click (0 = keyclick)
# 2 = wrap at end of line (0 = no wrap)
# 3 = auto LF on CR (0 = no LF on CR)
...
```

이 관점이 논쟁을 다시 틀 잡는다.

terminfo를 **런타임 조회 메커니즘**으로 보면 kazinator와 smarks의 주장이 설득력 있다. 대부분의 항목이 없는 하드웨어를 위한 것이고, 새 기능 반영이 10년씩 걸린다.

그런데 **역사 기록**으로 보면 대체 불가능하다.
하드코딩하는 라이브러리들은 아무것도 기록하지 않는다. `\x1b[31m`이 왜 빨강인지, 어떤 터미널이 그것을 다르게 했는지가 어디에도 남지 않는다.

그리고 이 구분이 실무와도 무관하지 않다.
**저자가 말한 “새 기능이 추가되기까지 10년”이 문제인 것은 terminfo를 caniuse로 쓸 때이고**, 역사 기록으로는 지연이 문제가 아니다.

### “caniuse가 없다”는 지적이 가장 실행 가능한 제안이다

이 글에서 가장 구체적인 부재 지적이 **터미널에 Can I use나 Baseline 같은 것이 없다**는 것이다.

stuaxo가 HN에서 이것을 집어 올렸다.[^stuaxo]
**ANSI용 caniuse가 훌륭한 아이디어**라며, 지난 15년쯤 안에도 새로운 것들이 일어나고 있으니 이것이 지식을 퍼뜨리는 데 도움이 될 것이라고 적었다.

이 제안이 앞서 본 사회적 장벽을 **우회한다**는 점이 중요하다.

표준을 만들려면 합의가 필요하고, Screwtape와 mattrose와 junon의 증언대로 그 합의가 안 된다.
그런데 **caniuse는 합의가 필요 없다**. 관찰의 기록이기 때문이다.

웹에서도 순서가 그랬다. caniuse가 표준을 만든 것이 아니라 **무엇이 어디서 되는지를 보여 줌으로써 개발자가 판단할 수 있게** 했고, 그 가시성이 나중에 압력이 되었다.

터미널에서 이것을 만드는 데 필요한 것은 기능 목록과 에뮬레이터 목록과 **각 조합을 시험하는 자동화**뿐이다.
그리고 시험 자동화가 실제로 가능한데, 앞에서 본 `XTGETTCAP`과 DA 질의가 그 재료다.

저자가 “이론상 terminfo가 터미널의 caniuse여야 한다”고 적은 것이 정확한데, **terminfo는 선언이고 caniuse는 측정이라는 차이**가 있다.
terminfo는 에뮬레이터가 자기 `TERM` 이름으로 무엇을 지원한다고 **주장하는지**를 담고, caniuse는 **실제로 되는지**를 담는다.

그리고 iTerm2가 자기를 `xterm-256color`라고 보고한다는 저자 자신의 관찰이 왜 전자로는 부족한지를 보여 준다.

### 근본적으로 새 것이 없다는 점을 짚어 둘 만하다

cblake의 한 줄이 이 글 전체에 대한 논평이기도 하다.[^cblake]

저자가 링크한 fish 메인테이너의 비판이 읽을 가치가 정말 있다면서, **터미널이 워낙 오래되어서 구체적 사례와 세부만 빼면 이 비판이 20년 전에도 같은 취지로 나올 수 있었을 것**이라고 적었다.

이것이 비관으로만 읽히지는 않는다.

20년 동안 같은 진단이 반복된다는 것은 **진단이 틀리지 않았다는 뜻이면서 동시에 진단만으로는 안 움직인다는 뜻**이다.

그리고 그 사이에 실제로 바뀐 것이 없지는 않다.
OSC 52가 널리 퍼졌고, 괄호 붙여넣기가 사실상 기본이 되었고, 24비트 색이 일반화되었고, kitty 그래픽 프로토콜과 키보드 프로토콜이 여러 에뮬레이터에 들어갔다.

공통점이 있다. **전부 표준화 절차 없이, 한 구현이 먼저 만들고 남들이 따라간 것**이다.

Screwtape가 말한 대로 “터미널이 무엇이 되어야 하는지에 대한 명확한 비전을 가진 누군가”가 필요하다면, 실제 역사에서 그 역할을 한 것이 위원회가 아니라 xterm이었고 지금은 kitty와 ghostty 쪽이다.

## 인사이트

### 표준이 있다는 것과 표준 안에서 살 수 있다는 것은 다르다

tssva의 정정이 이 글의 전제를 바로잡는데, 그 정정이 상황을 더 어렵게 만든다는 점이 흥미롭다.

ANSI 이스케이프 코드는 1979년에 X3.64로 표준화되었고 지금은 ISO 6429이며 ECMA-48과 사실상 같다.
표준은 **50년 가까이 존재해 왔다**.

그런데 오늘 터미널에서 실제로 유용한 것들 — 마우스, 괄호 붙여넣기, 클립보드 복사, 이미지, 하이퍼링크, 키보드 구분 — 이 **하나도 그 안에 없다**.

그러면 문제가 “표준을 만들자”가 아니게 된다.

표준이 그 영역의 변화 속도보다 느리게 갱신되면, **표준은 존재하되 무관해진다**.

그리고 이것이 터미널만의 이야기가 아니다.
POSIX가 있는데 실무에서 GNU 확장 없이 셸 스크립트를 쓰기 어렵고, C 표준이 있는데 실제 코드는 컴파일러 확장에 의존한다.

이런 상황에서 생기는 특유의 비용이 있다.
**무엇이 표준인지는 알 수 있는데 무엇이 안전한지는 알 수 없다.** 표준 준수가 안전을 보장하지 않고(표준 안에 필요한 것이 없으므로), 표준 위반이 위험을 뜻하지도 않기 때문이다(모두가 쓰는 확장이 있으므로).

그래서 이 영역에서 실제로 필요한 문서는 표준 문서가 아니라 **채택 현황표**다.
저자가 caniuse의 부재를 지적한 것이 정확했던 이유가 그것이다.

### 탐지에서 질의로 가는 것이 표준화보다 먼저다

저자의 User-Agent 비유가 정확한데, 그 비유의 결론을 끝까지 밀면 다른 답이 나온다.

웹이 사용자 에이전트 탐지를 버린 과정이 **표준화 → 탐지 폐기**가 아니었다.
**기능 탐지 도입 → 탐지 폐기 → 표준화 가속**에 가까웠다.

`if (window.IntersectionObserver)`가 가능해지자 브라우저 이름을 물을 이유가 사라졌고, 그러자 브라우저들이 이름으로 차별받지 않게 되어 새 기능을 내놓기 쉬워졌다.

터미널에서 이에 해당하는 것이 이미 있다.

| 방식              | 무엇을 묻는가            | 유추              |
| ----------------- | ------------------------ | ----------------- |
| `TERM` + terminfo | 너는 누구냐              | User-Agent 문자열 |
| DA1/DA2           | 너는 어떤 장치냐         | 여전히 정체 질의  |
| `XTGETTCAP`       | 이 능력이 있느냐         | **기능 탐지**     |
| kitty 질의        | 이 프로토콜을 지원하느냐 | **기능 탐지**     |

그리고 **기능 탐지에는 합의가 필요 없다**는 점이 결정적이다.
질의 메커니즘 하나만 합의되면, 그 뒤로는 각 에뮬레이터가 무엇을 지원하든 애플리케이션이 알아서 대응한다.

일반화하면, 파편화된 생태계에서 먼저 표준화해야 하는 것은 기능이 아니라 **“무엇을 지원하는지 묻는 방법”**이다.

기능을 표준화하려면 모두가 같은 것을 구현해야 하지만, 질의를 표준화하면 **서로 다른 것을 구현해도 된다**.
그리고 후자가 앞서 본 사회적 장벽 — 각자 자기 생각이 있고 바꿀 이유가 없다 — 을 정면으로 피해 간다.

icefox가 [터미널 불만 문서](terminal-frustrations.md)에서 **“표준 기능 탐지 메커니즘만 있어도 정말 좋을 것”**이라고 한 것이 같은 결론이다.

### 보이지 않는 것이 고치기 어려운 이유가 문제의 절반이다

저자가 이스케이프 코드의 답답함을 설명하며 붙인 단서가 이 글에서 가장 적게 다뤄지고 가장 중요하다.

“보이지 않기까지 해서 **이스케이프 코드 문제를 해결하는 것이 대단히 답답하다**.”

이것이 부차적 불편이 아니라 이 영역이 개선되지 않는 구조적 이유다.

무언가가 깨졌을 때 고칠 수 있으려면 **무엇이 깨졌는지 관찰할 수 있어야 한다**.
그런데 이스케이프 코드는 정의상 화면에 나타나지 않는다. 나타나면 그것이 곧 버그다.

그 결과가 진단의 비대칭이다.
**동작할 때는 보이지 않고, 동작하지 않을 때도 대체로 보이지 않는다.** 색이 안 나오는 것과 코드를 안 보낸 것과 에뮬레이터가 무시한 것이 화면에서 같아 보인다.

그래서 이 영역의 버그 리포트가 부정확해진다. “터미널에서 색이 이상해요”가 어느 층의 문제인지 보고자가 알 수 없고, 그러면 **고칠 사람에게 도달하지 않는다**.

그리고 고쳐지지 않으면 각자 우회한다. [터미널 불만 설문](terminal-frustrations.md)에서 본 그 순환이다.

**일반화하면, 관찰 가능성이 낮은 계층은 개선 압력을 받지 못한다.** 사용자가 불만을 정확한 주소로 보낼 수 없기 때문이다.

그래서 이 영역에서 가장 저평가된 도구가 **바이트를 그대로 보여 주는 것들**이다.

```bash
# 프로그램이 실제로 무엇을 내보내는지 본다
some-program | cat -v
some-program | hexdump -C | head

# 키를 누르면 무엇이 오는지 본다
cat -v     # 또는 셸에서 Ctrl-V 뒤에 키
```

저자가 [ASCII 제어 문자 글](ascii-control-characters.md)에서 `echo-key.py`를 직접 만들었다고 한 것도 같은 필요에서다.
이 계층에는 개발자 도구가 없고, **그것이 브라우저와의 가장 큰 차이**다.
