# 터미널의 ASCII 제어 문자 33개는 누가 처리하는가

원문: [ASCII control characters in my terminal](https://jvns.ca/blog/2024/10/31/ascii-control-characters/)

HN 토론: <https://news.ycombinator.com/item?id=42014639> (29점, 5개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/wm9sff/ascii_control_characters_my_terminal> (30점, 6개 댓글)

## 요약

Julia Evans가 2024년 10월 31일에 쓴 글이다.

터미널에 대해 많이 생각하다가 `Ctrl-A`, `Ctrl-C`, `Ctrl-W` 같은 제어 코드들이 **대체 어떻게 된 것인지** 궁금해져서 정리했다고 밝힌다.

글은 33개 제어 문자 전부를 담은 표를 만든 뒤, **그 표에 대해 자기가 아는 모든 단서를 하나씩 붙이는** 방식으로 진행된다.
저자 스스로 “백만 가지 단서가 있다”고 적는데, 실제로 글의 절반 이상이 단서다.

그리고 마지막에 이 글의 성격을 스스로 규정한다.
내용이 흥미롭기는 한데 **꼭 유용하지는 않다고 생각한다**는 것이다.
지난 20년 동안 이 중 아무것도 모른 채 터미널을 매일 성공적으로 써 왔으며, `Ctrl-C`·`Ctrl-D`·`Ctrl-Z`·`Ctrl-R`·`Ctrl-L`이 실제로 무엇을 하는지만 알았고(어쩌면 `Ctrl-A`·`Ctrl-E`·`Ctrl-W`까지), 세부는 대체로 신경 쓰지 않았는데 **xterm.js를 쓰려 할 때를 빼면 언제나 완전히 괜찮았다**는 것이다.

## 누가 처리하는가

이 글에서 가장 쓸모 있는 부분이 33개 코드의 **분류**다.

| 처리 주체          | 예                                      | 성격                                 |
| ------------------ | --------------------------------------- | ------------------------------------ |
| OS 터미널 드라이버 | `Ctrl-C`(3) → `SIGINT`                  | 애플리케이션에 닿기 전에 가로챈다    |
| 키보드 키 자체     | `Enter`(13), `Tab`(9), `Backspace`(127) | 물리 키 누름에 대응한다              |
| `readline`         | `Ctrl-A`, `Ctrl-E`, `Ctrl-R` 등         | 애플리케이션이 그렇게 하기로 한 관습 |
| 그 밖              | `Ctrl-X`                                | 표준 의미 없음. emacs가 많이 쓴다    |

`readline` 항목의 설명이 정확하다.
“애플리케이션이 원하는 대로 할 수 있다”는 말이 실제로는 **그 애플리케이션이 실제로 readline을 쓰든 안 쓰든 readline 라이브러리가 하는 것과 대체로 같은 일을 한다**는 뜻이라는 것이다.

그리고 이 분류에 구조가 있느냐는 질문에 저자가 없다고 답한다.
어떤 코드가 어떤 범주에 있는지에 **실제 구조는 없고 그냥 무작위로 흩어져 있으며, 유기적으로 진화했기 때문**이라는 것이다.

이 주장은 나중에 HN에서 정정된다.

## 33개뿐이다

저자가 놀랐다고 적은 두 번째 사실이다.

제어 코드가 **33개뿐**이다. A부터 Z까지에 일곱 개(`@`, `[`, `\`, `]`, `^`, `_`, `?`)를 더한 것이다.

그래서 터미널 애플리케이션에서 `Ctrl-1`을 단축키로 쓰겠다는 것이 **의미가 없다**. 저자 기기에서 `Ctrl-1`은 그냥 `1`을 누르는 것과 정확히 같고 `Ctrl-3`은 `Ctrl-[`와 같다.

경계를 두 개 더 긋는다.

`Ctrl+Shift+C`는 제어 코드가 아니다. 터미널 에뮬레이터에 따라 달라지며, 리눅스에서 `Ctrl-Shift-X`는 종종 에뮬레이터가 복사나 새 탭이나 붙여넣기에 쓰므로 **TTY에 전달되지 않는다**.

`Ctrl+왼쪽 화살표`도 제어 코드가 아니다. ANSI 이스케이프 시퀀스(`ctrl-[[1;5D`)를 보내는 전혀 다른 것이다.

그리고 이 33개 제약이 GUI와 근본적으로 다르다는 점을 짚는다.
GUI에서는 원하는 아무 키에나 `Ctrl+KEY`를 붙일 수 있다.

### 겹치는 것이 있다

33개뿐이라는 사실의 직접적 귀결이 충돌이다.

기본적으로 `Ctrl-S`는 화면을 얼어붙게 만드는데, 그것을 끄면 `readline`이 `Ctrl-S`를 정방향 검색에 쓴다.

`Ctrl-T`는 더 심하다. 저자 기기에서 어떨 때는 `SIGINFO`를 보내고 어떨 때는 두 문자를 뒤바꾸고 어떨 때는 완전히 다른 일을 하는데, **프로그램에 `ISIG`가 설정되어 있는지**와 **프로그램이 readline을 쓰거나 흉내 내는지**에 달렸다.

### `Ctrl-M`과 `Ctrl-I`는 단축키로 쓸 수 없다

`Ctrl-M`이 문자 그대로 `Enter`와 같고 `Ctrl-I`가 `Tab`과 같다.

일부는 여전히 이 둘을 단축키로 쓰지만, 그러려면 터미널 에뮬레이터를 기본값과 다르게 설정해야 한다.

저자의 결론이 실용적이다. **터미널 애플리케이션을 만든다면 `Ctrl-I`와 `Ctrl-M`을 단축키로 피해야 한다**는 것이다.

## 단서들

이 글의 진짜 내용이 여기 있다. 표 하나를 그려 놓고 그것이 왜 정확하지 않은지를 계속 설명한다.

### 정규 모드와 비정규 모드

표에서 “OS가 처리”라고 표시한 `Ctrl-W`와 `Ctrl-U`가 **항상 그런 것은 아니다**.

| 모드   | 언제 입력을 받는가  | `Ctrl-W`/`Ctrl-U`      |
| ------ | ------------------- | ---------------------- |
| 정규   | `Enter`를 눌렀을 때 | OS가 처리한다          |
| 비정규 | 키를 누르는 즉시    | 프로그램에 그대로 전달 |

정규 모드를 쓰는 예로 `grep`이나 `cat` 같은 비대화형 프로그램 대부분과 git을 든다.
비정규 모드를 쓰는 예로 `python3`과 `irb` 같은 REPL, 셸, 그리고 `less`나 `vim` 같은 전체 화면 TUI를 든다.

### `stty`로 전부 바꿀 수 있다

`Ctrl-C`가 `SIGINT`를 보낸다고 했지만 **기술적으로 반드시 그런 것은 아니다**.
“OS 터미널 드라이버”로 표시된 코드 전부와 Backspace를 `stty`로 재배치할 수 있다.

```bash
stty -a
```

```text
cchars: discard = ^O; dsusp = ^Y; eof = ^D; eol = <undef>;
eol2 = <undef>; erase = ^?; intr = ^C; kill = ^U; lnext = ^V;
min = 1; quit = ^\; reprint = ^R; start = ^Q; status = ^T;
stop = ^S; susp = ^Z; time = 0; werase = ^W;
```

저자는 이것들을 한 번도 재배치한 적이 없고 **그럴 이유를 상상할 수도 없다**고 적는다. 자기에게는 혼란과 재앙의 지름길일 것이라는 이유다.

그런데 Mastodon에 물어보니 사람들이 `stty`를 쓰는 가장 흔한 이유가 나왔다.

```bash
stty sane          # 망가진 터미널을 고친다
stty erase ^H      # Backspace 동작을 바꾼다
stty ixoff
```

일부는 `SIGINT`를 `DELETE` 키 같은 다른 키에 매핑하기도 한다는 것이다.

### 시그널에 대한 단서

`ISIG` 터미널 모드가 꺼져 있으면 OS가 시그널을 보내지 않는다. 예를 들어 **`vim`이 `ISIG`를 끈다**.

BSD에는 `SIGINFO`를 보내는 추가 제어 코드 `Ctrl-T`가 있다.

어떤 터미널 모드를 설정하는지 직접 볼 수 있다. 터미널 모드는 `ioctl` 시스템 콜로 설정된다.

```bash
strace -tt -o out vim
grep ioctl out | grep SET
```

`vim`이 시작할 때 설정하는 모드에서 **`ISIG`와 `ICANON`이 빠져 있고**, 종료할 때 되돌린다.
저자는 이 특정 조합을 “raw 모드”라고 부르는 것 같다며 `man cfmakeraw`를 가리킨다.

### Backspace가 두 개다

표에서 127을 “backspace”로, 8을 “다른 backspace”로 표시했는데, 저자는 이것이 **Mastodon 답글에서 단연 가장 큰 화제**였으며 엄청난 역사가 있는데 전혀 들어 본 적이 없었다고 적는다.

자기 기기에서의 동작은 이렇다.
`Backspace` 키를 누르면 TTY에 바이트 **127**(ASCII의 `DEL`)이 가고, OS 터미널 드라이버와 readline 양쪽이 127을 backspace로 매핑해 두어서 정규 모드와 비정규 모드 모두에서 동작한다.

`Ctrl+H`를 누르면 readline을 쓸 때는 Backspace와 같은 효과이지만, readline 지원이 없는 프로그램(예를 들어 `cat`)에서는 그냥 `^H`가 출력된다.

그런데 어떤 사람들은 `Backspace` 키가 **바이트 8을 보내고**, 그래서 Backspace가 동작하게 하려면 `stty`로 `erase = ^H`를 설정해야 한다는 것이다.

저자는 Debian 정책 매뉴얼의 키보드 설정 절을 “믿기 힘든 절”이라고 소개하며, 이 정책이 **90년대에 Backspace가 무엇을 해야 하는지 혼란이 많아서 표준이 필요해 쓰였다**고 정리한다.

Lobste.rs에서 Screwtape가 이 역사의 짧은 답을 줬다.[^Screwtape]
**“왜 backspace 키가 `$08` Backspace가 아니라 `$7F` Delete를 보내는가”에 대한 짧은 답은 “당신의 터미널 에뮬레이터가 VT220을 에뮬레이트하고 있고 그것이 VT220의 동작이었다”**는 것이다.

### 저자도 모르는 것들

`stty -a`에 따르면 `Ctrl-O`가 “discard”, `Ctrl-R`이 “reprint”, `Ctrl-Y`가 “dsusp”인데, **이것들이 실제로 무언가 하게 만드는 방법을 전혀 모른다**고 적는다.
눌러도 뚜렷한 일이 일어나지 않고, 역사적으로 무엇을 했는지 알려 준 사람들이 있었지만 2024년에 쓸모가 있는지는 분명하지 않다는 것이다.
그리고 실제로는 대체로 애플리케이션에 그대로 전달되므로 `Ctrl-R`과 `Ctrl-Y`를 그냥 readline으로 표시했다고 밝힌다.

## 확인하기

저자가 이 글을 쓰면서 여러 키 조합이 무엇을 하는지 알아내려고 실험을 많이 해야 했고, 그래서 출력해 주는 파이썬 스크립트 `echo-key.py`를 만들었다고 적는다.
더 공식적인 방법이 있을 것 같지만 **직접 고칠 수 있는 스크립트가 있어서 좋았다**는 것이다.

스크립트 없이 확인하는 방법도 있다.

```bash
# 키 입력의 바이트를 그대로 보여 준다. 끝내려면 Ctrl-C
cat -v

# Backspace를 누르면 ^? 가 나오면 127, ^H 가 나오면 8이다
```

`Ctrl-V`가 다음 키 입력을 문자 그대로 만드는 것도 같은 일에 쓸 수 있다.

```bash
# 셸에서 Ctrl-V 를 누른 뒤 확인하려는 키를 누른다
```

그리고 `stty -a`와 `strace`로 모드를 보는 방법은 앞에서 본 그대로다.

## 비평

### “무작위로 흩어져 있다”는 서술이 틀렸다

이 글에서 가장 눈에 띄는 주장이 제어 코드 배치에 실제 구조가 없고 유기적으로 진화해 무작위로 흩어졌다는 것이다.

kps가 이것을 정면으로 정정했다.[^kps]

1967년 개정이 약간 흐려 놓기는 했지만 **이들은 종류별로 묶여 있다**는 것이다. 그리고 규격을 인용한다.

```text
A8.2 The controls that were selected logically fall into four groups:
  (1) Transmission controls
  (2) Format effectors
  (3) Device controls
  (4) Information separators
Within each group the controls are ordered so that the binary
and hierarchical order are directly related.
```

각 그룹 안에서 **이진 순서와 계층 순서가 직접 관련되도록** 정렬되어 있다는 것이다.
“형식 효과자(format effectors)”가 캐리지나 인쇄 헤드나 커서를 움직이는 제어이고, “장치 제어(device controls)”는 기본적으로 사설 용도의 형식 효과자라고 설명한다.

이 정정이 중요한 이유가 있다.

저자의 서술은 **유닉스 터미널에서의 현재 쓰임**을 보고 내린 판단이다. 그 층위에서는 실제로 무질서하다.
하지만 원래 배치에는 설계가 있었고, 무질서해진 것은 **유닉스가 그 위에 다른 의미를 덮어썼기 때문**이다.

그러니 정확한 서술은 “구조가 없다”가 아니라 **“원래 구조가 있었는데 지금 쓰임과 대응하지 않는다”**다.
그리고 그 차이가 앞서 저자가 ASCII 이름을 무시하자고 한 이유를 오히려 더 잘 설명한다.

kps는 오늘날 엉망의 뿌리에 대해서도 한마디 덧붙였다.
유닉스가 ASCII 터미널 상호작용으로 시작했는데 **리눅스 데스크톱이 Microsoft Windows를 너무 많이 흉내 냈고, 거기서 Control 키에는 무관하고 충돌하는 다른 의미가 덧씌워져 있었다**는 것이다.[^kps-windows]

### 전신기 기원 설명이 정확하지 않다

저자가 제어 코드들이 원래 정의될 때 컴퓨터나 터미널이 아니라 **전신기(telegraph machine)에 쓰였다**고 적는다.

wpollock이 이 설명에 이의를 제기했다.[^wpollock]

원래 텔레타이프는 키를 누를 때 ASCII를 보냈고, **Control 키 수식자는 단지 눌린 다른 키에 비트 하나를 더했을 뿐**(Break 키만 예외)이라는 것이다.
그리고 **이것은 전신 시스템과 아무 관계가 없다**고 분명히 한다.

그러면서 현대 키보드가 스캔코드라는 숫자를 보내며 이것이 대략적으로만 표준화되어 있고, 특이한 키보드라면 리눅스의 `setkeycodes(8)`로 일부 스캔코드를 재매핑할 수 있다고 배경을 덧붙였다.

keybored는 다른 각도에서 같은 감상을 적었다.
**군살 없고 날렵한 ASCII의 약 25%가 전신 잡동사니라는 것이 웃기다**는 것이다.[^keybored]
공백 문자 중 둘이 유용하고 나머지 중 몇 개를 메타 문자로 쓸 수 있다고 정리했다.

두 지적을 합치면 이렇게 된다.
**제어 문자 중 상당수가 지금 쓸모없는 것은 맞지만, 그 이유가 전신기 때문은 아니다.** 텔레타이프와 초기 전송 프로토콜 때문이고, 그 둘은 다른 것이다.

### 33개의 제약을 문제로만 보면 놓치는 것이 있다

이 글은 33개뿐이라는 사실을 **제약**으로 제시한다. GUI와 달리 원하는 키에 `Ctrl`을 붙일 수 없다는 것이다.

그런데 그 33개 중 네 개는 거의 아무도 쓰지 않는 자리에 있고, 그것이 기회이기도 하다.

euroderf가 표의 28·29·30·31이 각각 FS·GS·RS·US 아니냐고 물었고,[^euroderf]
TristanBall이 여기에 실무적인 답을 붙였다.[^TristanBall]

**자신과 자기 도구들에게 이것들을 구분자로 쓰도록 가르치는 것이 반쯤 초능력에 가깝다**는 것이다. CSV/TSV 같은 반구조화 표 형식에서 그렇다.
필드 정의와 이스케이프와 내장된 개행 문제가 **거의 전부 사라진다**는 것이다.
개행이 더 어려운 쪽인데, 일부 도구가 줄 기반이기를 고집하며 CR/LF 변형을 개행으로 하드코딩하기 때문이다.

그리고 과소평가된 장점을 하나 짚는다. 이것들이 **UTF-8에서도 의미와 고유성을 유지한다**는 것이며, 모든 ASCII 제어 코드가 그렇다는 점이다.

```bash
# US(0x1F)를 필드 구분자로, RS(0x1E)를 레코드 구분자로 쓴다
printf 'a\x1fb\x1fc\x1ed\x1fe\x1ff\x1e' | tr '\x1e' '\n' | tr '\x1f' '\t'
```

이것이 이 글의 프레이밍을 뒤집는다.
33개라는 숫자가 단축키 관점에서는 부족하지만, **데이터 구분자 관점에서는 아무도 쓰지 않는 네 개가 남아 있다**는 뜻이다.

billpg가 “제어 문자가 16개쯤만 있으면 될 것 같고 그 자리를 출력 가능한 문자에 쓰면 되지 않겠느냐, 아 그러면 ASCII를 쓰는 모든 프로그램이 깨지겠구나”라고 농담했는데,[^billpg]
keybored의 답이 정확하다. **“아무도 안 쓰겠지”라고 생각하며 시작하는 순간 굉장한(끔찍한) 판도라의 상자가 열린다**는 것이다.[^keybored-can]

TristanBall의 용례가 바로 그 “아무도 안 쓴다”의 반례다.

### 결정판 문헌이 없다는 것이 이 분야의 상태다

Lobste.rs의 반응이 짧지만 이 주제 전체를 요약한다.

deepchasm이 적었다. **터미널을 제어하는 일은 전승 지식과 거의 무한한 예외로 가득 차 있으며, 유일하게 놀라운 것은 결정판 문헌이 목록에 없다는 것**이다.[^deepchasm]

spc476이 답했다. **결정판 문헌에 가장 가까운 것은 아마 termcap/terminfo 데이터베이스**일 것이라는 것이다.[^spc476]

이 교환이 이 글의 형식을 정당화한다.

저자가 표 하나를 그리고 단서를 열 개 넘게 붙인 것이 게으름이 아니다. **이 주제에 단서 없는 서술이 불가능하기 때문**이다.
“내 기기에서는 이렇다”로 시작해 “다른 기기에서는 다를 수 있다”로 끝나는 것이 이 주제에서 가능한 가장 정직한 형식이다.

그리고 “결정판 문헌이 termcap/terminfo 데이터베이스”라는 답이 상황을 압축한다.
**사람이 읽는 설명이 아니라 기계가 읽는 데이터베이스가 유일한 권위**라는 뜻이기 때문이다.

### 계층이 많아지면 누가 가로챘는지 알 수 없다

jiehong이 이 글의 분류에 대해 실질적인 질문을 던졌다.[^jiehong]

터미널 에뮬레이터를 돌리고 그 안에서 bash를 돌리고 거기서 `ssh`를 실행해 원격 호스트의 긴 프로그램을 돌리는 중에 `Ctrl-C`를 누르면, **원격 호스트의 긴 프로그램만 죽는다**는 것이다.
그렇다면 셸과 ssh가 `SIGINT`를 무시하고 전달만 하는 것이냐고 묻는다.

답이 달리지 않았지만 이 질문이 이 글의 모델에서 빠진 층을 정확히 가리킨다.

이 글의 표는 **하나의 TTY와 그 위의 하나의 프로그램**을 전제한다.
실제로는 TTY가 겹겹이 쌓인다. 로컬 TTY가 있고, ssh가 원격에 의사 TTY를 만들고, `tmux`를 쓰면 또 하나가 생긴다.

그러면 같은 `Ctrl-C`가 **어느 층의 터미널 드라이버에 도달하느냐**에 따라 결과가 달라진다.
ssh 클라이언트는 자기 TTY를 raw 모드로 두어 `ISIG`를 끄므로 로컬에서 시그널이 발생하지 않고, 바이트 3이 그대로 원격으로 흘러가 그쪽 TTY가 `SIGINT`를 만든다.

이 글이 그 층위를 다루지 않는 것이 잘못은 아니다. 다만 **“누가 처리하는가”라는 분류가 층이 하나일 때만 성립한다**는 점은 짚어 둘 만하다.

## 체크리스트

- 터미널 애플리케이션에 단축키를 정할 때 `Ctrl-I`(Tab)와 `Ctrl-M`(Enter)을 피했는가
- `Ctrl-1` 같은 숫자 조합을 단축키로 쓰려 하고 있지 않은가? 제어 코드가 아니다
- `Ctrl-S`가 화면을 얼리는 것을 껐는가? 그러면 readline 정방향 검색을 쓸 수 있다
- 터미널이 이상해졌을 때 `stty sane`을 먼저 시도했는가
- Backspace가 이상하다면 `cat -v`로 127(`^?`)인지 8(`^H`)인지 확인했는가
- 프로그램이 시그널을 받지 못한다면 `ISIG`가 꺼져 있는지 `stty -a`로 확인했는가
- ssh나 tmux를 거치고 있다면, 제어 코드가 어느 층의 TTY에서 처리되는지 구분했는가
- 구분자가 필요한 데이터 형식을 설계 중이라면 `0x1E`/`0x1F`를 검토했는가

## 기억할 원칙

### 단서가 본문보다 긴 글은 그 주제의 상태를 보여 준다

이 글의 구조가 특이하다. 표 하나를 제시하고 나머지 전부가 그 표가 왜 정확하지 않은지에 대한 설명이다.

절 제목만 훑어도 드러난다. “정규 모드 대 비정규 모드에 대한 단서”, “OS 터미널 드라이버 코드는 전부 설정 가능하다는 단서”, “시그널에 대한 단서”, “backspace와 다른 backspace에 대한 단서”, “아마 이것이 동작하는 방식에 훨씬 더 많은 다양성이 있을 것이다”.

보통은 이런 글을 덜 다듬어진 글로 본다. 정리해서 하나의 깔끔한 규칙으로 만들어야 한다고 느낀다.

그런데 이 주제에서는 그것이 **거짓말이 된다**.

deepchasm이 말한 대로 결정판 문헌이 없고, spc476이 답한 대로 가장 가까운 것이 데이터베이스다.
즉 이 영역에는 **일반화가 존재하지 않는다**. 사례와 예외가 있을 뿐이다.

그러므로 단서의 양은 저자의 게으름이 아니라 **그 주제가 얼마나 표준화되지 않았는지의 측정값**이다.

그리고 읽는 쪽에서 쓸 수 있는 규칙이 여기서 나온다.
어떤 주제에 대해 깔끔하게 정리된 설명을 만났을 때, **그것이 단순해서인지 아니면 단서를 생략해서인지**를 물어야 한다.
이 글은 후자를 택하지 않았고, 그래서 덜 우아하지만 더 쓸 만하다.

### 쓸모없어 보이는 자리가 가장 쓸 만한 자리일 수 있다

저자는 `Ctrl-O`와 `Ctrl-R`과 `Ctrl-Y`에 대해 **실제로 무언가 하게 만드는 방법을 모르겠다**고 적고 넘어간다.
그리고 33개 제어 코드를 단축키가 부족하다는 관점에서만 본다.

TristanBall의 댓글이 같은 사실을 반대로 읽는다.
`0x1C`부터 `0x1F`까지의 정보 구분자들이 아무도 안 쓰기 때문에 **구분자로서 완벽하다**는 것이다.
데이터 안에 절대 나타나지 않으므로 이스케이프가 필요 없고, 그래서 CSV의 고질적 문제가 통째로 사라진다.

같은 사실이 관점에 따라 결함이 되기도 하고 자원이 되기도 한다.

“이 자리가 비어 있다”는 관찰은 그 자체로는 아무 값도 없고, **무엇을 하려는지 정한 다음에야 부호가 정해진다**.
단축키를 찾는 사람에게 33개는 부족하고, 구분자를 찾는 사람에게 네 개는 충분하다.

그리고 이 역전에는 조건이 하나 붙는다. TristanBall이 짚은 대로 **UTF-8에서도 의미와 고유성이 유지된다**는 점이다.
비어 있으면서 동시에 안정적이어야 자원이 된다. 그냥 비어 있기만 하면 언젠가 다른 누가 채운다.

billpg의 농담과 keybored의 답이 그 짝이다.
쓰이지 않는 것처럼 보이는 자리를 재활용하려는 순간, **정확히 그것을 쓰고 있던 사람이 나타난다.**
