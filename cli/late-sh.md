# late.sh: SSH로 접속하는 터미널 클럽하우스

<https://late.sh/>

<https://github.com/mpiorowski/late-sh>

## 소개

late.sh는 스스로를 “컴퓨터 하는 사람들을 위한 아늑한 커맨드라인 클럽하우스”라고
소개한다.
채팅, 음악, 게임, 아트, 코딩, 기술 뉴스를 담고 있으며 어떤 SSH 클라이언트로든 접속할
수 있다.

```bash
ssh late.sh
```

터미널 우선 소셜 앱이라는 규정이 이 프로젝트의 성격을 요약한다 — 실시간 채팅, 음악,
게임, 뉴스, 프로필, 그리고 어떤 SSH 클라이언트에서든 들어갈 수 있는 항상 켜져 있는
공유 공간이다.
저장소의 소개 문구는 “Lofi beats, casual games, chat, and tech news, all via SSH”이고
토픽은 `cli`, `irc`, `ssh`, `terminal`, `tui`다.
별 1.3k, 포크 89개 상태다.

상태 표기가 명확하다.
이 저장소가 late.sh의 주 코드베이스이며, 소스 읽기·로컬 개발·감사·기여에 열려 있고,
공개 호스팅되는 late.sh 서비스가 정식 배포판으로 남는다.
그리고 라이선스에 대해 분명히 선을 긋는다 — FSL 보호 기간 동안 이 코드는
source-available이며 OSI 오픈소스가 아니라는 것이다.
세부는 `LICENSE`에, 평이한 영어로 쓴 정책은 `LICENSING.md`에, 기여 규칙은
`CONTRIBUTING.md`에 있다고 안내한다.

## 구성

포함된 것은 다음과 같다.

- 대시보드·채팅·프로필·뉴스·아케이드 화면을 갖춘 SSH TUI
- 실시간 전역 채팅과 공유 활동 피드
- Icecast/Liquidsoap을 통한 오디오 스트리밍 — 짝지어진 CLI나 공개 `/listen` 페이지에서 재생
- 2048, 스도쿠, 노노그램, 지뢰찾기, 솔리테어를 포함한 터미널 게임
- 랜딩·프로필·토큰 없는 `/listen` 페이지를 위한 웹 프런트엔드
- 로컬 오디오 재생과 동기화된 비주얼라이저 데이터를 위한 컴패니언 CLI

Rust 워크스페이스이며 다섯 개의 크레이트로 나뉜다.

| 크레이트       | 역할                                                                |
| -------------- | ------------------------------------------------------------------- |
| `late-cli`     | 로컬 오디오 재생, 짝지어진 제어, 비주얼라이저 동기화용 컴패니언 CLI |
| `late-core`    | 공유 도메인 코드, 데이터베이스 계층, 마이그레이션, 인프라 헬퍼      |
| `late-ssh`     | SSH 서버와 터미널 UI 애플리케이션                                   |
| `late-web`     | 웹 서버, 랜딩 페이지, 프로필/갤러리, 스트림 프록시, `/listen` 페이지 |
| `late-webview` | CLI를 위해 공식 YouTube IFrame Player를 호스팅하는 헬퍼 프로세스    |

백엔드 스택은 PostgreSQL, Icecast, Liquidsoap이다.

## 사용법

라이브 서비스에 접속하는 것이 가장 빠른 경로다.

```bash
ssh late.sh
```

SSH 로그인 이름은 공개 핸들로 쓰이지 않고 버려진다.
첫 접속 시 새 계정에 무작위 수식어+명사 조합의 사용자명이 부여되며, 이후 설정에서
바꿀 수 있다.

직접 돌리려면 Docker가 필요하다.

```bash
git clone https://github.com/mpiorowski/late-sh
cd late-sh
make start
ssh localhost -p 2222
```

Postgres와 Icecast와 Liquidsoap이 모두 자동으로 올라온다.

컴패니언 CLI는 로컬 오디오 재생과 동기화된 비주얼라이저를 위한 것이다.

```bash
# macOS / Linux / Termux
curl -fsSL https://cli.late.sh/install.sh | bash

# Windows PowerShell (x64)
irm https://cli.late.sh/install.ps1 | iex

# Nix / NixOS
nix run github:mpiorowski/late-sh#late
```

Termux에서는 설치 스크립트가 GNU/Linux 빌드 대신 안드로이드 CLI 빌드를 가져온다.
소스에서 빌드하려면 `mise install`로 예상 Rust 툴체인을 맞춘 뒤
`cargo build --release --bin late`을 쓴다.

Docker가 Rust 빌드를 감싸지 않는 로컬 개발에서는 인프라만 Docker로 띄우고 앱은
네이티브로 돌린다.

```bash
docker compose up -d postgres icecast liquidsoap
cargo run -p late-ssh
cargo run -p late-web
```

PR을 열기 전 로컬 게이트로 `make check`를 돌린다.
이것은 `cargo fmt --check`를 먼저 실행한 뒤 워크스페이스 전체에 대해 `--features otel`로
`cargo clippy`와 `cargo nextest`를 돌리는 전체 사전 병합 스윕이며, CI는 속도를 위해
otel을 건너뛰므로 otel 관련 문제가 잡히는 유일한 지점이 여기이거나 릴리스 빌드라는
설명이 붙는다 — 프로덕션에서는 결코 잡히지 않는다는 것이다.
로컬 체크는 포트 55433에 전용 Compose Postgres 프로젝트(`late-check`)를 띄우고
`TEST_DATABASE_URL`로 DB 기반 테스트를 그쪽으로 보낸다.

기여에는 DCO 사인오프(`git commit -s`)가 요구되고, 포크를 배포할 때 공식 late.sh
서비스인 것처럼 제시하거나 프로젝트 브랜딩을 자기 것으로 쓰지 말라는 조건이 붙는다.
문서 목록에서 눈에 띄는 것은 `CONTEXT.md`인데, 아키텍처와 불변 조건과 작업 맥락을
담고 있으며 “LLM을 위해 쓰였다 — 최상의 결과를 위해 AI 편집기에 이것을 먹이라”고
명시되어 있다.
`CONTRIBUTING.md`에도 AI 보조 개발 팁이 포함된다고 안내한다.

## 분석

### SSH를 애플리케이션 전송 계층으로 쓰는 계보에 속하지만, 목적이 다르다

`ssh <domain>` 한 줄로 접속하는 서비스는 최근 몇 년간 하나의 장르가 되었다.
`ssh terminal.shop`으로 커피를 사는 것, `ssh git.charm.sh`로 저장소를 다루는 것,
`sshtron.zachlatta.com`으로 게임을 하는 것이 같은 계보다.
기술적 기반도 공유한다 — Go의 Wish나 Rust의 `russh` 같은 라이브러리가 SSH 서버 위에
TUI를 얹는 것을 쉽게 만들었다.

이 장르가 매력적인 이유는 설치 비용이 0이라는 데 있다.
클라이언트가 이미 모든 유닉스 계열 기기와 최신 윈도우에 있고, 인증 인프라(공개키)가
내장되어 있고, 암호화가 기본이다.
웹 앱이라면 회원 가입과 브라우저 호환성과 번들 크기를 신경 써야 하는 자리를 SSH가
전부 대신한다.

그런데 late.sh는 이 계보의 다른 항목들과 목적이 다르다.
앞선 사례 대부분은 데모이거나 단일 기능 도구였고, 화제성이 목적이었다.
late.sh는 지속적 사회적 공간을 지향한다 — 계정과 프로필이 있고, 상태가 유지되고,
전역 채팅과 활동 피드가 있고, 항상 켜져 있다.
즉 SSH를 재미있는 진입점으로 쓰는 것이 아니라 클라이언트 플랫폼으로 쓴다.
그래서 다섯 개 크레이트와 PostgreSQL과 스트리밍 인프라가 필요하다.

### 실시간 오디오를 SSH 세션 밖으로 빼낸 설계가 이 프로젝트의 기술적 핵심이다

기능 목록에서 가장 어려운 항목은 음악이다.
SSH 세션은 텍스트 스트림이고, 그 위로 오디오를 흘릴 수는 있어도 실용적이지 않다.
그래서 late.sh는 오디오를 별도 경로로 뺐다 — Icecast와 Liquidsoap이 스트리밍을 맡고,
컴패니언 CLI가 로컬에서 재생하며, 웹의 `/listen` 페이지가 토큰 없이도 들을 수 있는
대안 경로다.

이 분리가 만드는 구조가 흥미롭다.
SSH 세션은 제어와 상태를 담당하고, 별도 채널이 미디어를 담당하며, 둘이 “짝지어진
제어(paired controls)”와 “비주얼라이저 동기화”로 연결된다.
이것은 사실상 SSH를 시그널링 채널로 쓰는 설계이고, 화상 회의 프로토콜이 제어와 미디어를
분리하는 것과 같은 형태다.

`late-webview` 크레이트의 존재가 이 설계의 대가를 보여준다.
CLI를 위해 공식 YouTube IFrame Player를 호스팅하는 헬퍼 프로세스이며, 즉 어떤 음원은
브라우저 엔진 없이는 재생할 수 없어 별도 프로세스로 브라우저를 띄운다는 뜻이다.
터미널 앱을 표방하는 프로젝트가 웹뷰 프로세스를 크레이트로 갖는다는 사실이 이 영역의
현실 — 음악 라이선스가 재생 경로를 규정한다는 것 — 을 드러낸다.

### FSL 채택이 이 프로젝트의 사업적 위치를 규정한다

README의 Status 섹션은 라이선스를 세 문장으로 못 눌러 둔다 — 소스 읽기와 로컬 개발과
감사와 기여에 열려 있고, 공개 호스팅 서비스가 정식 배포판이며, FSL 보호 기간 동안
source-available이지 OSI 오픈소스가 아니라는 것이다.
그리고 기여 조건에 “포크를 배포할 때 공식 late.sh 서비스인 것처럼 제시하지 말라”는
항목이 붙는다.

FSL(Functional Source License)은 Sentry가 2023년에 만든 라이선스로, 경쟁 사용을 2년간
금지한 뒤 Apache 2.0이나 MIT로 자동 전환되는 구조다.
BSL과 달리 전환 기간이 짧고 금지 범위가 “경쟁 제품”으로 좁게 정의되어 있어, 소스
공개의 이득은 취하면서 즉각적 호스팅 경쟁만 막으려는 프로젝트가 택한다.

이 선택이 late.sh의 성격을 말해준다.
순수 취미 프로젝트라면 라이선스에 이만큼 공을 들일 이유가 없다 — MIT로 던지면 된다.
FSL을 고르고 별도 `LICENSING.md`를 두고 브랜딩 조항까지 넣었다는 것은, 이것이 호스팅
서비스로 지속될 것을 전제하며 누군가 코드를 가져다 같은 서비스를 여는 것을 실질적
위험으로 본다는 뜻이다.
별 1.3k와 포크 89개라는 숫자가 그 위험이 가설이 아님을 보여준다.

### `CONTEXT.md`를 LLM용으로 명시한 것이 이 저장소의 가장 현대적인 부분이다

문서 목록에서 `CONTEXT.md`에 붙은 설명은 이례적이다 — 아키텍처와 불변 조건과 작업
맥락을 담고 있으며 “LLM을 위해 쓰였다, 최상의 결과를 위해 AI 편집기에 이것을
먹이라”는 것이다.
`CONTRIBUTING.md`에도 AI 보조 개발 팁이 들어 있다고 안내한다.

이것은 `AGENTS.md`나 `CLAUDE.md` 같은 파일이 관행이 되어 가는 흐름의 한 사례이지만,
문서의 성격 규정이 조금 다르다.
에이전트 지침 파일은 보통 “이 저장소에서 어떻게 행동하라”는 규칙을 담는다.
`CONTEXT.md`는 “이 시스템이 어떻게 생겼는지”를 담는다고 서술되며, 즉 규칙이 아니라
설계 문서이고 독자만 기계로 상정된 것이다.

이 구별이 시사하는 바가 있다.
아키텍처 문서는 언제나 만들어졌지만 잘 유지되지 않았다 — 읽는 사람이 적고, 낡아도
아무도 즉시 곤란해지지 않기 때문이다.
에이전트가 그것을 읽고 코드를 쓰기 시작하면 문서의 낡음이 즉시 잘못된 코드로 나타난다.
즉 이 관행은 문서화의 인센티브 구조를 바꾸며, 그것이 이 저장소가 다섯 개의 별도
설명 문서(`CONTEXT.md`, `LICENSING.md`, `MUSIC.md`, `SCALE.md`, `THEME.md`,
`DOOR.md`, `DRAGON.md`)를 유지하는 이유일 수 있다.

## 비평

### “오픈소스가 아니다”를 명시했지만 기여를 요청하는 구조의 비대칭

README는 라이선스에 대해 정직하다 — source-available이며 OSI 오픈소스가 아니라고
분명히 밝힌다.
이 정직함은 최근 여러 프로젝트가 “오픈소스”를 느슨하게 쓰는 것과 대조되며 칭찬할
만하다.
그런데 같은 문단이 곧바로 기여를 환영한다고 말하고, DCO 사인오프를 요구한다.

이 조합에는 구조적 비대칭이 있다.
기여자는 자기 노동을 FSL 코드베이스에 넣고, 그 코드는 보호 기간 동안 프로젝트 소유자만
상업적으로 활용할 수 있다.
DCO는 기여자가 그 기여를 할 권리가 있음을 증명하는 장치이지 기여자에게 무엇을 보장하는
장치가 아니다.
2년 뒤 오픈 라이선스로 전환된다는 것이 완화 요소이지만, 전환은 각 릴리스 시점 기준으로
굴러가므로 최신 코드는 항상 보호 상태다.

이 문제는 late.sh만의 것이 아니라 FSL과 BSL 전반의 것이다.
다만 이 저장소가 특이한 것은 상업적 이해가 뚜렷하지 않다는 점이다 — 유료 플랜이나
수익 모델에 대한 언급이 README에 없다.
보호할 상업적 자산이 무엇인지 밝히지 않은 채 경쟁 사용을 금지하면, 기여자는 자기
기여가 무엇을 위해 보호되는지 알 수 없다.
`LICENSING.md`가 그 답을 담고 있을 수 있지만, 그렇다면 README에 한 줄 요약이 있어야
했다.

### 아늑함을 표방하는 프로젝트가 요구하는 진입 비용

프로젝트의 언어는 일관되게 편안함을 향한다 — “cozy”, “clubhouse”, “lofi beats”,
“casual games”.
그런데 실제 진입 경로를 보면 그 톤과 어긋나는 지점이 여럿이다.

라이브 서비스 접속은 정말 `ssh late.sh` 한 줄이므로 이 약속을 지킨다.
문제는 그다음이다 — 음악을 들으려면 컴패니언 CLI를 설치해야 하고, 설치 경로는
`curl | bash`나 `irm | iex`다.
로컬에서 돌리려면 Docker와 Postgres와 Icecast와 Liquidsoap이 올라와야 하고, 개발
환경을 맞추려면 mise와 mold와 cargo-nextest가 필요하다.

이 격차가 문제인 이유는 대상 사용자층이 갈리기 때문이다.
`ssh late.sh`의 매력에 끌리는 사람은 “아무것도 설치하지 않아도 된다”에 반응한 것인데,
핵심 기능인 음악이 설치를 요구한다.
`/listen` 웹 페이지가 대안으로 제공되지만, 그러면 터미널 앱을 쓰면서 브라우저 탭을
따로 열어야 한다.
아늑한 클럽하우스라는 컨셉의 가장 큰 구멍이 여기 있고, README는 그것을 기능 목록의
평평한 항목으로만 제시한다.

### 로컬 검증 절차의 무게가 “기여를 환영한다”와 충돌한다

Verification 섹션은 이 저장소에서 가장 상세한 부분 중 하나다.
`make check`가 `cargo fmt --check`와 워크스페이스 전체에 대한 `cargo clippy`와
`cargo nextest`를 `--features otel`로 돌리고, 전용 Compose Postgres 프로젝트를 포트
55433에 띄우고, `TEST_DATABASE_URL`로 DB 테스트를 그쪽으로 보낸다.

이 절차의 품질은 높다.
특히 CI가 속도를 위해 otel을 건너뛰므로 그 조합이 검증되는 유일한 지점이 로컬 게이트와
릴리스 빌드라는 설명은 정직하고 유용하다 — 어디서 무엇이 잡히는지를 명시한 저장소는
드물다.

그러나 기여자 관점에서 이것은 상당한 진입 비용이다.
작은 오타 수정 하나를 위해 Docker Compose 프로젝트를 띄우고 전체 워크스페이스에
clippy와 nextest를 돌려야 한다면, 캐주얼한 기여는 사실상 차단된다.
그리고 프로젝트가 “테마 하나를 PR로 기여하는 법”(`THEME.md`)을 별도 문서로 안내한다는
사실은 정확히 그런 작은 기여를 기대한다는 뜻이다.
빠른 경로 — 문서나 테마만 바꿀 때 건너뛸 수 있는 축약된 체크 — 가 안내되지 않은
것이 이 문서의 공백이다.

### 지속 가능성에 대한 정보가 README 어디에도 없다

이 프로젝트가 제공하는 것은 항상 켜져 있는 호스팅 서비스다.
사용자가 계정을 만들고 프로필을 쌓고 채팅 이력을 남긴다.
그런데 그 서비스가 얼마나 오래 유지될 것인지, 누가 비용을 대는지, 데이터가 어떻게
되는지에 대한 언급이 README에 없다.

이 공백이 실질적인 이유는 이 장르의 역사 때문이다.
`ssh` 기반 서비스와 소규모 소셜 공간은 운영자의 개인 시간과 서버 비용 위에서 돌아가며,
대부분 몇 년 안에 조용히 사라진다.
사용자가 축적하는 것 — 프로필, 대화, 관계 — 은 그때 함께 사라진다.
Sponsor 섹션이 저장소에 있다는 것이 재정 구조에 대한 유일한 힌트이며, 그것만으로는
판단할 수 없다.

FSL을 택한 것이 이 문제와 맞물린다.
공식 서비스가 멈춰도 소스가 있으니 누구나 띄울 수 있다는 것이 source-available의
이론적 이점인데, 보호 기간 동안 그 경로가 제약되고 브랜딩도 쓸 수 없다.
즉 이 프로젝트는 이탈 경로를 코드로는 열어 두고 라이선스로는 좁혀 놓았으며, 그
조합이 사용자에게 어떤 보장을 주는지가 문서화되어 있지 않다.

## 인사이트

### SSH가 새로운 애플리케이션 배포 채널이 되는 이유는 향수가 아니라 마찰 계산이다

`ssh late.sh`류 프로젝트는 흔히 레트로 취향으로 설명된다 — BBS와 IRC와 talk의 향수라는
것이다.
실제로 이 프로젝트도 `irc`를 토픽에 넣었다.
그러나 이 장르가 지금 늘어나는 이유는 미학이 아니라 웹 배포의 마찰이 올라갔기 때문이다.

웹 앱 하나를 내놓으려면 도메인, TLS, 프런트엔드 빌드, 번들 최적화, 브라우저 호환성,
회원 가입과 비밀번호 재설정, 이메일 발송, 봇 방어, 쿠키 동의, 접근성, 모바일 반응형이
필요하다.
SSH 앱은 이 목록의 대부분을 건너뛴다 — 전송 보안과 인증이 프로토콜에 있고, 렌더링
대상이 하나이며, 클라이언트가 이미 설치되어 있다.
1인 개발자가 사회적 공간을 만들려 할 때 이 차이는 결정적이다.

이 계산은 시간이 지날수록 SSH 쪽에 유리해진다.
웹 플랫폼은 계속 복잡해지고 SSH는 거의 변하지 않기 때문이다.
그리고 봇 방어라는 항목이 특히 그렇다 — 웹에서 계정 생성 봇을 막는 비용이 매년
올라가는데, SSH는 공개키 기반이고 접속 자체에 약간의 마찰이 있어 자연스러운 필터가
된다.
late.sh가 로그인 이름을 버리고 무작위 사용자명을 부여하는 설계도 같은 논리로 읽힌다 —
신원 선택을 없애면 스쿼팅과 사칭이 사라진다.

그러므로 이 장르의 확산은 일시적 유행이 아니라 배포 비용 곡선의 결과일 가능성이 높다.
그리고 이 흐름이 계속되면 SSH 위에서 부족한 것들 — 이미지, 오디오, 링크 클릭,
결제 — 을 우회하는 패턴이 표준화될 것이다.
late.sh가 오디오를 별도 채널로 빼고 웹 `/listen` 페이지를 붙인 구조가 그 초기
형태이며, 앞으로 이 조합 — SSH를 제어 평면으로, HTTP를 미디어 평면으로 — 이 하나의
아키텍처 관용구가 될 수 있다.

### 소규모 소셜 공간의 부활은 대형 플랫폼의 실패가 아니라 규모의 재정의다

late.sh 같은 공간이 겨냥하는 것은 소셜 미디어의 대안이 아니다.
사용자 수천 명 규모에서 멈추도록 설계되어 있고, 발견 기능도 추천 알고리즘도 없다.
전역 채팅 하나와 활동 피드 하나가 전부다.

이 규모는 우연이 아니라 조정 비용의 함수다.
공유 채팅방 하나가 작동하는 인원 상한은 대략 수백 명 동시 접속이며, 그 이상에서는
대화가 읽을 수 없게 된다.
IRC 채널이 그 상한에서 분화했고, 디스코드 서버가 채널로 쪼개지고, 슬랙이 같은 문제를
같은 방식으로 푼다.
late.sh가 전역 채팅 하나를 유지한다는 것은 이 상한 안에 머물겠다는 선언이다.

여기서 흥미로운 것은 성공이 실패 조건이 되는 구조다.
별 1.3k에서 사용자가 백 배 늘면 전역 채팅이 무너지고, 무너지지 않으려면 채널을 나눠야
하고, 채널을 나누면 “하나의 공유 공간”이라는 정체성이 사라진다.
그리고 모더레이션이 필요해지는데, 1인 프로젝트에 그것은 감당 불가능한 비용이다.
`DOOR.md`와 `DRAGON.md` 같은 파일명이 저장소에 있는 것을 보면 접근 제어와 관련한
장치가 이미 설계되어 있을 가능성이 있고, 그것이 이 문제에 대한 대비일 수 있다.

역사적으로 이 규모의 공간은 성장하지 않는 방식으로 오래 살아남았다.
개별 BBS, 소규모 MUD, 특정 IRC 네트워크, 그리고 지금의 tildeverse 같은 것들이 그렇다.
공통점은 성장을 목표로 삼지 않았다는 것이고, 그래서 광고도 투자도 없었다는 것이다.
late.sh가 FSL을 택하고 공식 배포를 정식으로 규정한 것은 이 계보와 다른 신호이며 —
지킬 상업적 무언가가 있다는 뜻이기 때문에 — 이 프로젝트가 어느 쪽 궤도를 탈지가
앞으로의 관전 포인트다.

### LLM용 문서를 명시하는 관행이 아키텍처 문서의 경제학을 바꾼다

`CONTEXT.md`에 붙은 “LLM을 위해 쓰였다, AI 편집기에 이것을 먹이라”는 안내는 사소해
보이지만 문서화의 오래된 문제를 건드린다.

아키텍처 문서가 낡는 이유는 피드백 루프가 없기 때문이다.
코드는 컴파일러와 테스트가 즉시 틀렸다고 알려주지만, 문서는 몇 달 뒤 누군가 읽고
혼란스러워할 때까지 아무 신호도 내지 않는다.
그래서 문서 갱신은 항상 우선순위 밖으로 밀린다.

에이전트가 문서를 읽고 코드를 쓰면 이 루프가 생긴다.
문서에 적힌 불변 조건이 실제와 다르면 에이전트가 그 문서를 믿고 잘못된 코드를 만들고,
그것이 테스트에서 즉시 실패한다.
즉 문서가 실행 가능한 명세에 가까워지고, 갱신 압력이 코드와 같은 층위로 올라온다.

이 변화가 확산되면 문서 작성의 기준도 바뀐다.
사람을 위한 아키텍처 문서는 서사와 배경과 “왜 이렇게 했는지”를 담는 것이 좋고,
기계를 위한 것은 불변 조건과 경계와 금지 사항을 명시적으로 열거하는 것이 좋다.
late.sh가 `CONTEXT.md`(아키텍처와 불변 조건)와 `CONTRIBUTING.md`(워크플로와 테스트
규칙, AI 보조 개발 팁)를 나눈 것이 이 분화의 초기 형태로 보인다.
그리고 이 분화가 진행되면 “문서”라는 하나의 범주가 사람용 설명과 기계용 명세로
갈라지고, 후자는 점점 코드에 가까운 형식 — 스키마, 어서션, 린트 규칙 — 으로 수렴할
가능성이 크다.

### 브랜딩 보호 조항이 오픈소스 포크 문화의 실질적 경계를 보여준다

기여 규칙 마지막에 붙은 한 줄이 눈에 띈다 — 포크를 배포할 때 공식 late.sh 서비스인
것처럼 제시하거나 프로젝트 브랜딩을 자기 것으로 쓰지 말라는 것이다.
라이선스가 아니라 사회적 규범으로 진술된 조항이다.

이 종류의 조항은 최근 늘어나고 있고, 그 배경에는 포크의 성질 변화가 있다.
전통적 포크는 개발 방향 불일치에서 나왔고 새 이름과 새 정체성을 가졌다 — LibreOffice,
MariaDB, Jenkins가 그랬다.
지금 문제가 되는 것은 정체성 없는 복제다 — 코드를 그대로 띄우고 이름만 살짝 바꿔
검색 결과에서 원본과 경쟁하거나, 최악의 경우 자격증명을 수집하는 것이다.
SSH 서비스에서 이것은 특히 위험하다 — 사용자가 공개키를 넘기는 대상이 누구인지
확인할 방법이 도메인 이름뿐이기 때문이다.

여기서 오픈소스 라이선스의 오래된 공백이 드러난다.
GPL도 MIT도 코드의 사용을 규율하지 상표와 신뢰를 규율하지 않는다.
그래서 실제 보호는 상표법과 커뮤니티 규범에 맡겨져 왔고, 개인 개발자에게 상표
등록과 집행은 비현실적이다.
late.sh가 라이선스(FSL)와 규범(브랜딩 조항)을 함께 쓴 것은 이 공백을 메우려는
실용적 조합이며, 두 장치가 겨누는 위험이 서로 다르다 — FSL은 상업적 경쟁을, 브랜딩
조항은 사칭을 막는다.

이 구분을 명확히 하는 것이 앞으로 소규모 프로젝트에 점점 중요해질 것이다.
에이전트가 코드베이스를 통째로 복제하고 변형해 배포하는 비용이 거의 0이 되었기
때문이다.
“누구나 포크할 수 있다”는 오픈소스의 약속과 “누구도 나인 척할 수 없다”는 신뢰의
요구가 충돌하는 지점이 여기이며, 이 저장소의 한 줄짜리 조항은 그 충돌에 대한 가장
작고 가장 흔한 형태의 답이다.
