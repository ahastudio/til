# 매주 쓰게 되는 셸 패턴들

원문: [More Shell Patterns I Use Weekly](https://will-keleher.com/posts/more-shell-patterns-i-use-weekly/)

## 소개

Will Keleher가 자기가 자주 쓰는 셸 패턴을 정리한 글이며,
같은 제목의 이전 글에 이어지는 두 번째다.
이전 글은 `sed`와 `xargs`로 찾아 바꾸기, 성공하거나 실패할 때까지 도는 while 루프,
`wait`로 명령을 병렬화하기, `$SECONDS`를 다뤘다.

글의 전제가 솔직하다.
저자는 자신이 특별히 셸을 잘하는 사람이 아니라고 밝힌다.
공백이 들어간 입력을 제대로 다루는 Bash for 루프를 쓸 줄 모르고,
`trap`도 쓸 줄 모르고, 셸 배열은 문서를 보지 않으면 엄두도 못 낸다.
조금이라도 복잡한 일이 필요하면 보통 파이썬이나 zx로 넘어간다.

그럼에도 일상적으로 하고 싶은 일을 해내고
자기 필요에 맞는 작은 도구를 빠르게 만들 만큼은 명령줄에 능하다고 말한다.
이 글이 다루는 것은 바로 그 수준의 패턴들이다.

## 문자열 파라미터 확장

```bash
for file in **/*.md; do
    pandoc $file -o "${file/.md/.html}"
done
```

저자는 셸 문자열 조작에 약하지만 `${variable/pattern/replacement}`만은 기억한다고 적는다.
셸에서 변수를 참조하는 방법은 `$x`와 `${x}` 둘인데, 중괄호 형태가 몇 가지를 더 해 준다.

| 문법                       | 동작                                                                                            |
| -------------------------- | ----------------------------------------------------------------------------------------------- |
| `${x}y`                    | `x`의 값 뒤에 문자 `y`를 붙인다. `$xy`는 `xy`라는 변수를 찾으므로 보통 아무것도 출력하지 않는다 |
| `${x:-fallback}`           | 변수가 없을 때 쓸 기본값을 준다                                                                 |
| `${x%%.html}`              | 문자열 끝에서 `.html`을 제거한다                                                                |
| `${x/pattern/replacement}` | 첫 일치를 치환한다                                                                              |

저자는 `%`와 `#`의 방향을 외우지 못해서 끝을 자를 때도 그냥 `${x/.html/}`를 쓴다고 고백한다.
정확히는 `%`가 뒤에서 자르고 `#`이 앞에서 자르며,
한 개면 가장 짧은 일치를, 두 개면 가장 긴 일치를 제거한다.
`.html`처럼 일치가 하나뿐인 경우에는 `%`와 `%%`의 결과가 같다.

`**/*.md`는 zsh에서 바로 동작하고 Bash에서는 `shopt -s globstar`가 필요하다.
저자는 `pandoc` 외에 `magick`이나 `ffmpeg` 같은 도구와 함께 이름을 바꾸는 for 루프를 자주 쓴다고 덧붙인다.

## 출력에 색 넣기

동료에게 배웠다는 패턴으로, 복사해 붙일 수 있는 색 정의 블록을 스크립트에 넣는 방식이다.

```bash
# ----- Colours easy def: Usage: printf "%s\n" "${red}foobar${end}"
red=$'\e[1;31m'
green=$'\e[1;32m'
yellow=$'\e[1;33m'
blue=$'\e[1;34m'
mag=$'\e[1;35m'
cyn=$'\e[1;36m'
end=$'\e[0m'

printf "\n\t%s\n" "${red}Helpful error message that we want to highlight.${end}"
```

`$'...'` 형태를 쓰는 이유가 이 블록의 핵심이다.
일반 따옴표 안에서는 `\e`가 문자 그대로 남지만,
`$'...'`는 이스케이프 시퀀스를 해석해 실제 제어 문자를 만든다.

저자는 출력 가독성에 아주 약간의 노력을 들이면
급조한 셸 스크립트도 훨씬 다루기 좋아진다고 말한다.
다만 스크립트에 오류 메시지를 넣기 시작하는 시점이
JS나 파이썬 같은 언어로 옮길 때라고 본다.

## /tmp와 mktemp를 적극적으로 쓰기

명령 하나가 엄청난 출력을 뿜는데 그 내용이 실패했을 때만 필요하다면 성가시다.
저자는 그런 데이터를 자동으로 정리되는 자리에 보관하기 위해 `/tmp`를 많이 쓰기 시작했다고 말한다.

```bash
output_log_file=$(mktemp)
# &>로 표준 출력과 표준 오류를 함께 파일로 보낸다
if ! some_build_command_with_tons_of_output &> "$output_log_file"; then
    printf "\n%s\n" "${red}some_build_command_with_tons_of_output FAILED${end}"
    printf "\t%s\n" "${red}Full log output available at ${output_log_file}${end}"
    printf "\t%s\n\n" "${red}Last ten lines of output:${end}"
    tail -n10 "$output_log_file"
    exit 1
fi
```

저자는 이 패턴이 LLM과 함께 쓸 때 특히 유용하다고 적는다.
성공 메시지로 컨텍스트 창을 오염시키지 않기 때문이다.
사람에게도 컨텍스트 창이 있으며, 제대로 동작하고 있다면 그 로그를 보고 싶지 않다는 것이다.

주목할 점은 저자가 자기 예시의 결함을 스스로 밝힌다는 것이다.
표준 출력과 표준 오류를 한데 섞어 버리고,
실패한 명령의 정확한 종료 코드를 잃어버린다.
그럼에도 일반적인 패턴을 보여 주기에는 충분하다는 것이다.

관련된 습관 둘도 소개한다.
실행하는 명령에 `| tee /tmp/just-in-case`를 붙여 두면
실패한 명령의 출력을 `less`로 돌아다닐 수 있어,
무거운 명령을 다시 돌려 출력을 얻는 것보다 편하다.
그리고 `mktemp`는 파일뿐 아니라 디렉터리도 만들 수 있다.

각주에서는 다른 접근도 언급한다.
더 저렴한 모델을 쓰는 서브에이전트가 출력을 요약하게 하는 스킬을 만드는 방식이다.

## 중간 변수 대신 $() 쓰기

셸에 익숙해지면서 저자는 빠른 스크립트를 쓸 때 중간 변수를 쓰지 않게 되었다고 말한다.
명시적으로 이름 붙인 변수보다 가독성이 떨어지는 방식이라고 스스로 인정하면서도,
명령이 한 줄로 유지되어 고쳐서 다시 실행하기 좋기 때문에 더 편하다고 본다.

```bash
x=$(command | grep foo)
do_something_with_x "$x"

# 대신

do_something_with_x "$(command | grep foo)"
```

실제로 쓰는 예가 둘 나온다.

```bash
# 검색에 걸린 테스트 파일만 실행한다
mocha $(rg -l pattern)

# command의 실제 스크립트를 열거나, 패턴으로 찾은 파일을 골라 연다
hx $(which command)
hx $(rg -l pattern | fzf)
```

첫 번째에 붙은 설명이 유용하다.
큰 코드베이스에서 이 방식이 `mocha -g`보다 훨씬 빠른 이유는,
`-g`가 어떤 파일을 돌릴지 정하기 위해 모든 테스트 파일을 먼저 로드해야 하기 때문이다.
바깥에서 파일 목록을 좁히면 그 로딩 자체가 사라진다.

저자는 `$()`와 `<()`가 아직 편하지 않다면 중간 변수를 계속 쓰는 편이 낫다고 덧붙인다.

## grep 대신 awk로 거르기

| 명령                    | 동작                                                   |
| ----------------------- | ------------------------------------------------------ |
| `awk '!seen[$0]++'`     | 중복을 제거한다. `sort`와 `uniq` 조합의 대안이다       |
| `awk '$5 == "keyword"'` | 다섯 번째 필드만 보므로 `grep keyword`의 오탐을 피한다 |
| `awk '$2 ~ "pattern"'`  | 두 번째 필드에 대해서만 정규식을 맞춘다                |

첫 번째 관용구의 동작 원리를 저자가 풀어 준다.
`awk`는 1부터 세며 `$0`은 줄 전체를 가리킨다.
`seen`은 참조되는 순간 만들어지고,
`awk`는 참으로 평가되는 값이 주어지면 줄 전체를 출력한다.
`seen[$0]++`는 후위 증가라 첫 등장에서는 0을 돌려주고,
앞의 부정 연산자가 그것을 참으로 뒤집어 그 줄을 출력한다.
두 번째부터는 1 이상이 되어 출력되지 않는다.
`sort`와 달리 원래 순서가 유지되고 전체를 메모리에 정렬하지 않는다는 차이도 있다.

저자는 필터로 `grep`을 쓰기 시작해 복잡한 검색을 만들고 나서야
처음부터 `awk`로 시작했어야 했다는 것을 깨닫는 일이 종종 있다고 적는다.

## 함정

- `for file in **/*.md`에서 파일 이름에 공백이 있으면 깨진다. 저자가 첫 문단에서 공백 처리를 못 한다고 밝힌 바로 그 문제이며, 변수를 `"$file"`처럼 인용하면 대부분 해결된다.
- `${file/.md/.html}`는 첫 일치만 바꾸므로 경로 중간에 `.md`가 들어 있으면 엉뚱한 곳이 치환된다. 끝만 바꾸려면 `${file%.md}.html`이 안전하다.
- `mocha $(rg -l pattern)`은 일치하는 파일이 없으면 인자 없이 `mocha`가 실행되어 전체 테스트가 돌 수 있다.
- `$(...)`의 결과를 인용하지 않으면 공백에서 쪼개진다. 파일 목록처럼 여러 개를 넘길 때는 쪼개짐이 의도이지만, 단일 값일 때는 반드시 인용해야 한다.
- 색 변수는 출력이 터미널이 아닐 때도 그대로 나간다. 로그 파일이나 파이프에 제어 문자가 섞이므로, 실제 스크립트라면 `[ -t 1 ]`로 확인해 비대화형에서는 빈 문자열을 쓰는 편이 낫다.

## 비평

### 자신을 초보라 부르는 것이 설명의 빈자리를 정당화한다

글은 저자가 셸에 약하다는 선언으로 시작하고, 그 선언이 글 전체의 어조를 정한다.
`%`와 `#`을 못 외운다거나 배열은 문서를 봐야 한다는 고백은 읽기 편하고 솔직하다.
그러나 그 자리에 들어갔어야 할 설명이 비게 만들기도 한다.

`${x%%.html}`이 대표적이다.
글은 이것이 끝에서 `.html`을 제거한다고만 적고,
`%`와 `%%`의 차이도 `#`의 존재도 설명하지 않은 채 자신은 안 쓴다고 넘어간다.
그런데 이 문법이 필요한 진짜 상황은 `${x/.html/}`가 틀리는 상황,
즉 문자열 중간에도 같은 패턴이 있을 때다.
읽는 사람은 두 문법이 교환 가능하다는 인상을 받는데 그렇지 않다.

같은 문제가 첫 코드 블록에도 있다.
`$file`이 인용되지 않아 공백이 든 파일에서 깨지는데,
저자는 바로 앞 문단에서 자신이 그 문제를 못 다룬다고 밝혔다.
알고 있다고 말한 결함을 예제에 그대로 남겨 두는 것은 솔직함이 아니라 전달의 실패에 가깝다.

### LLM을 근거로 든 부분이 이 글에서 가장 약하다

`/tmp` 패턴의 장점으로 저자가 드는 것 중 하나는
LLM의 컨텍스트 창을 성공 메시지로 오염시키지 않는다는 점이다.
그리고 사람에게도 컨텍스트 창이 있다는 비유로 마무리한다.

비유는 재치 있지만 논증의 방향이 거꾸로다.
실패했을 때만 로그를 보는 것이 좋은 이유는 LLM이 등장하기 훨씬 전부터 성립했고,
저자 자신이 든 두 번째 이유, 즉 잘 돌아가는 것의 로그는 보고 싶지 않다는 것이 원래 이유다.
LLM이 추가하는 것은 새로운 근거가 아니라 같은 문제의 더 비싼 버전이다.

그리고 LLM 맥락에서는 이 패턴이 오히려 역효과를 낼 수 있다.
에이전트가 실패 원인을 진단하려면 로그가 필요한데,
`tail -n10`만 남기고 나머지를 파일에 감추면
에이전트는 그 파일을 다시 읽는 도구 호출을 한 번 더 해야 한다.
사람에게는 링크 하나가 편하지만 에이전트에게는 왕복이 한 번 늘어난다.
각주에 언급된 서브에이전트 요약 방식이 이 문제를 겨냥한 것인데,
본문의 주장과 각주의 보완이 연결되지 않은 채 흩어져 있다.

### 가독성을 포기한다고 말하면서 그 대가를 재지 않는다

중간 변수를 쓰지 않는 스타일에 대해 저자는
자기 방식이 덜 읽히는 스타일임을 인정하고 더 편하다는 이유로 선택한다.
이 정직한 서술에는 기준이 빠져 있다.
언제까지 편의를 택하고 언제부터 가독성을 택할지에 대한 선이 없다.

실제로 이 선택이 갈리는 지점은 명확하다.
한 번 실행하고 버릴 명령이라면 한 줄 유지가 옳고,
파일로 저장되어 다른 사람이 읽을 스크립트라면 이름 붙인 변수가 옳다.
중간 변수의 진짜 값어치는 가독성보다 디버깅에 있기도 하다.
`$(...)`가 예상과 다른 값을 내놓을 때, 변수에 담아 두면 그 값만 출력해 확인할 수 있다.

글이 마지막에 `$()`와 `<()`가 편하지 않다면 중간 변수를 쓰라고 적은 것은
숙련도를 기준으로 삼은 것인데, 더 나은 기준은 그 명령의 수명이다.

## 체크리스트

- 파일 이름에 공백이 있을 수 있다면 변수를 인용했는가?
- 확장자를 바꾸는 치환이 경로 중간의 같은 문자열을 건드리지 않는가?
- 명령 치환의 결과가 비었을 때 명령이 위험하게 동작하지는 않는가?
- 색 이스케이프가 파이프나 파일로 나갈 가능성을 처리했는가?
- 로그를 `/tmp`로 돌렸다면 실패 시 파일 경로를 출력하는가?
- 임시 파일에 표준 출력과 표준 오류를 섞어도 되는 상황인가?
- 한 줄로 쓴 명령이 재사용될 스크립트에 들어가지는 않는가?

## 기억할 원칙

### 성공은 조용하고 실패만 말하게 한다

이 글의 `/tmp` 패턴이 담고 있는 발상은 셸에만 해당하지 않는다.
정상 동작의 출력을 기본으로 감추고 실패했을 때만 드러내면,
읽는 쪽의 주의를 아껴 실제 문제가 눈에 띄게 만든다.

이 원칙은 CI 로그, 배포 스크립트, 크론 작업, 알림 설계에 그대로 적용된다.
모든 것이 다 출력되는 환경에서는 아무것도 읽히지 않고,
그 상태에서 진짜 오류가 섞여 들어오면 발견이 늦어진다.
감춘 것을 언제든 꺼내 볼 수 있게 경로를 남겨 두는 것이
이 패턴을 단순한 출력 억제와 구별해 준다.

### 필터링은 열이 있는 데이터에서 줄 단위 도구로 하지 않는다

`grep`에서 시작해 복잡해진 뒤에야 `awk`로 갔어야 했음을 깨닫는다는 저자의 고백이
이 절의 핵심이다.
`grep`은 줄 전체를 하나의 문자열로 보고, `awk`는 줄을 필드로 나눠 본다.
데이터에 구조가 있다면 구조를 아는 도구로 시작하는 편이 거의 항상 낫다.

같은 판단이 다른 곳에서도 반복된다.
JSON에는 `jq`, CSV에는 전용 도구, HTML에는 파서가 그 자리다.
정규식으로 구조화된 데이터를 다루기 시작하면
처음에는 짧아 보이다가 예외가 하나씩 붙으며 길어지고,
그 시점에는 이미 갈아타기가 번거로워져 있다.
