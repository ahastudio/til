# FTL: 운영체제를 컨테이너마다 라이브러리로 돌리는 클라우드용 OS

<https://ftl-os.org/>

<https://github.com/nuta/ftl>

HN 토론: <https://news.ycombinator.com/item?id=49944912> (160점, 63개 댓글)

GN 토론: <https://news.hada.io/topic?id=34729>

## 소개

FTL은 Seiya Nuta가 만드는 새 운영체제로, 클라우드 환경에서 Linux, BSD, Illumos를
대신할 OS를 목표로 한다.
홈페이지는 이를 “클라우드를 위한 새 운영체제”라고 소개하고,
핵심 문장은 OS를 라이브러리로 직접 만들 수 있다는 것이다.
저자는 2026년 9월 14일 블로그 글 “Introducing FTL”에서 취미 OS가 아니라 실용적인
클라우드 OS를 지향한다고 밝히면서도, 아직 매우 초기의 알파 품질이라고 적었다.
코드는 전부 Rust로 작성되었고 MIT와 Apache 2.0의 이중 라이선스다.
홈페이지 자체가 Google Compute Engine 위의 FTL에서 도는 Rust
HTTP 서버로 서비스된다.

홈페이지가 내세우는 약속은 세 가지다.
- OS 기능을 사용자 공간 라이브러리로 구현해서, 애플리케이션을 작성하듯 기능을 더하고 디버깅하고 안전하게 업그레이드할 수 있다.
- 사용자 모드라는 가벼운 하드웨어 격리 위에 하이퍼바이저 같은 인터페이스를 두어, 기존 모놀리식 커널보다 컨테이너를 더 잘 격리한다. 베어메탈 머신이 필요 없다.
- Linux 바이너리와 호환되며, POSIX 추상화 없이 유니커널 같은 특화 애플리케이션도 실행할 수 있다.

목표는 경량 컨테이너를 VM만큼 안전하게 만들고 성능을 희생하지 않으면서
애플리케이션이 OS 수준의 기능을 쓰게 하는 것이라고 홈페이지는 말한다.
이 문서는 홈페이지, GitHub README,
저자의 블로그 글 두 편(소개 글과 v0.1.0 릴리스 노트)을 바탕으로 했다.
나는 FTL을 직접 빌드하거나 실행하지 않았다.

## 동작 방식

### 컨테이너마다 하나씩 도는 사용자 공간 OS

FTL에서 프로세스, VFS, TCP/IP 같은 OS 개념은 커널이 아니라 사용자 공간 OS라는
공유 라이브러리에 들어 있다.
각 컨테이너는 자기만의 사용자 공간 OS 인스턴스를 가지며,
이 라이브러리는 그 컨테이너의 모든 프로세스 주소 공간에 매핑된다.
Linux 프로세스가 시스템 호출을 하면
커널은 이를 해석하지 않고 사용자 공간 OS의 핸들러로 넘긴다.
README는 이 구조가 전통적인 모놀리식 커널 기능을 라이브러리 OS로
옮긴 Exokernel과 비슷하고, 컨테이너마다 격리된 Linux 비슷한 애플리케이션 커널을
둔다는 점에서 gVisor와 비슷하다고 설명한다.
블로그 글은 사용자 공간 OS를 gVisor의 애플리케이션 커널(Sentry)에 빗댄다.

사용자 공간 OS가 라이브러리이므로 업그레이드는 새 라이브러리로 컨테이너를
다시 시작하는 일이 된다.
README는 커널 프로그래밍이나 머신 재부팅 없이 기능을 더하고,
디버깅용 `printf`를 넣고, 최적화할 수 있다고 강조한다.
컨테이너마다 서로 다른 OS 버전을 쓸 수도 있고,
사용자 공간 OS가 자체 TCP 스택을 구현할 수도 있다.

### 하이퍼바이저 모양의 커널

FTL 커널은 하드웨어 자원을 나누어 주는 일에 집중한다.
블로그 글 시점에 커널이 제공하는 기본 요소는 vCPU(스레드),
핸들 공간(파일 디스크립터 테이블), 가상 주소 공간, 가상 메모리 객체,
가상 네트워크 인터페이스다.
커널은 프로세스를 모른다.
README는 이를 virtio처럼 최소한의 인터페이스로 하드웨어를 다중화하는
하이퍼바이저에 가깝다고 설명한다.
저자는 소개 글에서 “하이브리드 커널”이라고 불렀지만 기술적으로는
Exokernel이라고 스스로 정리한다.

하이퍼바이저와 다른 점은 격리 수단이다.
Intel VT-x 같은 하드웨어 가상화가 아니라 사용자 모드(ring 3)에서
예외를 잡아 격리한다.
저자는 전통적인 OS에서 사용자 모드가 덜 안전한 경계로 여겨지지만,
하이퍼바이저처럼 커널 인터페이스를 최소화해서 강한 격리 경계로
만들겠다고 설명한다.
하드웨어 가상화를 쓰지 않으므로 성능을 위해 메탈 인스턴스를 빌릴 필요가
없다는 것이 저자의 논리다.
블로그 글에 따르면 커널은 x86-64 QEMU에서 2MB RAM으로 동작하고
바이너리 크기는 100KB였다.

### Linux 호환 계층과 여러 개성

FTL은 여러 개성(personality)을 지원하도록 설계되었고,
1순위 개성은 수정 없이 Linux 실행 파일을 돌리는 Linux다.
README는 WSL 1, FreeBSD의 Linuxulator, OSv 같은 ABI 에뮬레이션 선례를 들고,
FTL의 차이는 이 계층이 커널 기능이나 별도 감독 프로세스가 아니라 사용자 공간
라이브러리라는 점이라고 말한다.
Linux 호환 라이브러리는 선택 사항이고,
그 대신 FTL 네이티브 유니커널이나 직접 만든 OS를 컨테이너에 올릴 수도 있다.

### 커널 안의 장치 드라이버

현재 장치 드라이버(virtio-net)는 커널 안에 있다.
저자는 이것이 원래의 마이크로커널 설계에 비해 큰 단점이라고 인정한다.
대신 드라이버를 “Hard Mode Rust”로 작성한다.
드라이버는 암묵적인 동적 할당이 없는 `#![no_std]` 라이브러리이고,
커널이 `env`라는 명시적 I/O 인터페이스를 넘겨준다.
저자는 이를 Zig의 명시적 `Io` 인터페이스에 비유하며, 이렇게 하면 드라이버가
sans-io가 되어 자원 사용을 추적하고 단위 테스트할 수 있다고 설명한다.
다만 Rust 컴파일러가 의존성 속에 숨은 암묵적 panic을 거부할 방법을 주지 않으므로
panic 안전성은 보장되지 않는다고 덧붙인다.
드라이버 격리는 엄격한 안전이 아니라 충분히 좋은 수준을 목표로 한다.

## 실행하기

README의 절차는 Rust 툴체인, LLVM 도구,
QEMU를 설치한 뒤 스크립트를 돌리는 것이다.

```bash
# macOS
brew install rustup qemu
# Ubuntu
apt install rustup qemu-system

git clone https://github.com/nuta/ftl.git
cd ftl
./run.sh

# 특정 Linux 명령으로 시작하기
./run.sh "/bin/echo Hello World"

# 클라우드에서 돌릴 ISO 이미지 만들기
ISO=1 ./build.sh
```

README는 TypeScript로 쓴 종단 간 테스트와 빠른 편집, 컴파일,
실행 주기를 장점으로 든다.
나는 이 명령을 실행해 보지 않았다.

## 현재 상태와 로드맵

소개 글 시점(v0.0.1)의 Linux 호환 계층은 `read`, `write`, `fork`, `execve`,
`wait4`, `listen`, `accept`, `exit_group`, `poll` 같은 시스템 호출을 구현해서
musl 기반의 단순한 Linux 바이너리를 돌리는 수준이었다.
디스크 지원, 효율적인 copy-on-write `fork`,
`/proc` 파일 시스템, TTY 지원은 없다고 저자가 적었다.

2026년 10월 3일 릴리스된 v0.1.0은 멀티스레드 Tokio 런타임을
지원하며 다음을 더했다.
- Linux 스레드, futex, epoll, 시그널, tty, `brk`, `mmap`, `dup3`, `pipe`, `eventfd` 등
- 셸 접근을 위한 콘솔(시리얼 포트) 시스템 호출
- 벽시계 시간 API
- virtio-mmio와 QEMU microVM 지원
- 익명 메모리 페이지의 지연 할당
- x86-64 SMEP/SMAP 같은 보안 강화

릴리스 노트에는 블로킹 Linux 시스템 호출이 시그널로 중단되지
않는다는 항목도 있다.
홈페이지는 이 버전부터 Tokio 기반 HTTP 서버로 서비스된다.

| 시기        | 홈페이지 로드맵                       | 상태            |
| ----------- | ------------------------------------- | --------------- |
| 2026년 9월  | 간단한 Linux HTTP 서버 실행           | v0.0.1에서 완료 |
| 2026년 10월 | 비동기 Rust 앱 지원(스레드, epoll 등) | v0.1.0에서 완료 |
| 2026년 11월 | 파일 시스템                           | 예정            |
| 2026년 12월 | Node.js, Go 지원                      | 예정            |
| 2027년 1월  | SMP, 컨테이너 이미지, 64비트 Arm 지원 | 예정            |

v0.1.0 노트는 11월 릴리스에
Kubernetes의 임시 볼륨 같은 무상태 작업에 맞춘 파일 시스템,
동적 Linux 컨테이너 생성,
신뢰할 수 없는 코드를 돌리기 위한 더 나은 샌드박스 개념이 들어간다고 예고한다.
README는 런타임에 OS 구성 요소의 동작을 웹 프레임워크의 미들웨어처럼 제어하는
인터셉터(속도 제한, 보안 감사, 패킷 라우팅, 라이브 패치)도 계획으로 적는다.
FTL은 Linux보다 BSD에 가까운,
사용자 공간 소프트웨어를 함께 묶은 OS로 배포할 계획이라고 한다.

## 트레이드오프

### 같은 컨테이너 안에서는 OS가 프로세스로부터 보호되지 않는다

저자가 직접 밝힌 가장 큰 약점이다.
사용자 공간 OS는 공유 라이브러리이므로 같은 컨테이너 안의 프로세스가
OS 자체를 간섭할 수 있다.
그래서 Chromium처럼 프로세스 격리에 의존하는 애플리케이션은 FTL 위에서
구성 요소를 안전하게 나누려면 추가 작업이 필요하다고 한다.
저자는 Intel MPK 같은 프로세스 내부 격리 장치로 OS를 보호하는
방안을 미래 과제로 든다.

이 설계에서 격리의 단위는 프로세스가 아니라 컨테이너다.
컨테이너 사이 경계는 강해지지만,
컨테이너 안에서 Linux가 원래 주던 프로세스 간 경계는 약해진다.
컨테이너 하나에 프로세스 하나를 두는 클라우드 작업에서는 이 비용이 작다.
그러나 한 컨테이너에 슈퍼바이저와 작업자,
혹은 신뢰 수준이 다른 플러그인을 함께 두는 구성이라면 Linux 위의 컨테이너보다
오히려 약해질 수 있다는 것이 내 해석이다.

### 시스템 호출 경로가 짧아진다는 보장은 없다

HN의 tekacs는 Unikraft보다 gVisor에 가깝고 가로채는 경로가 더 빠를 수도
있겠다고 물었다.[^tekacs]
convolvatron은 반대로 짐작했다.
FTL이 자기 게스트로 돌면서 Linux를 라이브러리로 두고
더 줄인 호출 집합으로 내려간다면,
gVisor의 시스템 호출에서 vmexit로 가는 경로 대신
프로세스에서 게스트로, 다시 하이퍼바이저로 가는 경로가 되어
더 싸지 않을 것이라는 의견이다.[^convolvatron]
홈페이지는 성능을 희생하지 않는다고 말하지만 이를 뒷받침하는
측정치는 공개된 자료에 없다.

다만 FTL을 VM 안에서 돌리는지 베어메탈에서 돌리는지에 따라 이 계산은 달라진다.
현재 공개 데모는 Google Compute Engine의 VM 위에서 돈다.
그렇다면 FTL의 격리 위에 클라우드 하이퍼바이저의 격리가 한 겹 더 있는 셈이고,
저자가 말하는 “베어메탈이 필요 없다”는 장점이 실제로 무엇과
비교되는지가 중요해진다.

### 모놀리식 커널의 성숙도와 맞바꾼다

저자는 Linux가 성숙하고 검증된 커널이라는 점을 인정하면서도 모놀리식 설계가
만들 수 있는 소프트웨어 구조를 불필요하게 제한한다고 본다.
eBPF로 확장이 쉬워졌지만 여전히 제한적이고 깊은 커널 지식이 필요하다는 이유다.
대가는 분명하다.
FTL은 아직 디스크, 효율적인 `fork`, `/proc`이 없거나 막 생기는 중이고,
Node.js와 Go는 12월, SMP는 2027년 1월 로드맵에 있다.
지금 FTL에서 돌릴 수 있는 것은 단순한 musl 바이너리와 Tokio 기반 Rust 서버다.

## 함정

### 비슷한 설계와 헷갈리기 쉽다

HN에서는 이것이 마이크로커널인지 유니커널인지 묻는 댓글이 여럿이었다.
monocasa는 고전적인 Exokernel이라고 답하며,
핵심은 커널에 절대 최소한만 두는 것이 아니라 하드웨어를 다중화하는 데 필요한
최소한을 가장 적은 추상화로 두는 것이라고 설명했다.[^monocasa]
네트워크 드라이버는 커널에 두되 TCP 스택은 둘 필요가 없고,
디스크 드라이버는 두되 VFS는 둘 필요가 없다는 식이다.
그는 MirageOS와 비교하는 질문에도 FTL은 여전히 커널과 사용자 공간을 나누므로
MirageOS와 다르다고 답했다.[^monocasa-mirage]
raggi는 핸들 중심 객체나 VMO 같은 부분이 Fuchsia의 Zircon을 떠올리게
하지만, 커널이 스레드는 알고 프로세스는 모른다는 점처럼 선을 긋는 위치가
다르다고 짚었다.[^raggi]

### 비교 대상이 Linux뿐이다

trunnell은 하이퍼바이저가 없는 Linux 시스템이 아니라 Firecracker와
간단히 비교해 주면 좋겠다고 했다.[^trunnell]
홈페이지와 블로그 글의 그림은 FTL과 일반 Linux만 나란히 놓는다.
그러나 FTL이 겨냥하는 “VM만큼 안전한 경량 컨테이너”라는 자리에는 이미 gVisor,
Firecracker 같은 microVM, Kata Containers 같은 선택지가 있다.
도입을 검토한다면 이들과의 비교표를 직접 만들어야 한다.

### 클라우드용이라는 말의 범위

sigbottle은 클라우드용 OS라는 말이
KVM 같은 반가상화에 장치 모델을 맡긴다는 뜻인지,
직접 하드웨어 위에서 도는 OS를 처음부터 만든다는 뜻인지 물었다.[^sigbottle]
배포할 기계를 미리 알기 때문에 하드웨어 지원 범위를 좁혀 다룰 수
있다는 뜻이냐는 질문이다.
공개 자료로 확인되는 답은 현재 드라이버가 virtio-net이고 v0.1.0에서
virtio-mmio와 QEMU microVM을 지원했다는 정도다.
즉 지금의 FTL은 가상화된 장치 위에서 도는 게스트 OS로 보는 편이
정확하다는 것이 내 해석이다.

## 확인하기

1. README 절차로 `./run.sh`를 돌려 QEMU에서 HTTP 서버가 뜨는지 본다.
2. `./run.sh "<명령>"` 형식으로 이미지 안의 여러 Linux 명령을 실행해 어디서 멈추는지 확인한다.
3. 자기 서비스가 쓰는 시스템 호출 목록을 `strace -c`로 뽑아 v0.1.0이 구현한 목록과 대조한다.
4. 같은 Tokio 서버를 Linux 컨테이너, gVisor, Firecracker, FTL에서 각각 돌려 지연 시간과 처리량을 잰다. 공개 자료에는 이 비교가 없다.

## 기억할 원칙

### 격리 경계를 옮기면 경계 안쪽의 보호가 사라진다

FTL은 커널과 사용자 공간의 경계를 컨테이너 단위로 옮기고, 그 안의 OS 기능을
라이브러리로 내린다.
그 결과 컨테이너 사이의 경계는 하이퍼바이저처럼 좁고 강해지지만,
컨테이너 안의 프로세스와 OS 사이에는 경계가 사라진다.
저자가 Chromium을 예로 들며 이를 스스로 인정한 점은 설계 문서로서 정직하다.

경계를 어디에 두느냐는 성능이나 유연성만의 문제가 아니라
무엇을 하나의 신뢰 단위로 보느냐의 결정이다.
“컨테이너 하나는 하나의 신뢰 단위”라는 가정이 맞는 작업이라면
FTL의 거래는 좋아 보인다.
그 가정이 깨지는 작업이라면 같은 설계가 Linux보다 약한 격리를 준다.
새 격리 기술을 평가할 때는 어디가 더 강해졌는지보다 어디가 약해졌는지를
먼저 찾는 편이 빠르다.
