원문: [How Unix Works: Become a Better Software Engineer | Neil Kakkar](https://neilkakkar.com/unix.html)

## 소개

Neil Kakkar가 2019년 12월 14일에 쓴 Unix 입문 글이다.
그는 명령어 목록을 설명하지 않겠다고 먼저 밝힌다.
원하는 것은 검색 한 번이면 찾을 수 있지만, 그 해법이 왜 원하는 대로 동작하는지 이해하는 것은 다르고, 그 이해가 두려워하지 않을 힘을 준다는 것이다.
그래서 글의 목표는 시스템에 대해 추론하는 능력이다.

출발점은 Unix 철학 세 문장이다.
한 가지 일을 잘하는 프로그램을 쓰고, 함께 일하는 프로그램을 쓰고(불필요한 출력 없이, 대화형 입력을 고집하지 않고), 텍스트 스트림을 다루는 프로그램을 써라.
그 결과 Unix의 설계는 두 구성 요소로 모인다.
모든 것은 프로세스이거나 파일이고, 다른 것은 없다.

글은 파일과 파일 시스템(아이노드, 권한, 링크, 트리 구조), 프로세스(속성, 수명 주기, 리디렉션), 커널과 유틸리티라는 층, 셸의 동작(파이프, `PATH`, 셸 스크립트), 패키지 관리자, Unix와 Linux의 역사 순서로 이어진다.
이 노트는 그 가운데 셸 명령을 실제로 추론하는 데 필요한 부분을 따라가며 직접 돌려 볼 수 있게 정리한다.

## 동작 방식

### 파일: 데이터와 메타데이터의 분리

Unix에서 프로세스가 아닌 모든 것은 파일이다.
사진과 문서뿐 아니라 디렉터리, 터미널 화면, 프린터도 파일로 다뤄진다.
운영체제는 모든 프로세스에 열린 파일 세 개를 준다.
표준 입력(`stdin`), 표준 출력(`stdout`), 표준 오류(`stderr`)이고, 셸에서는 키보드가 입력, 화면이 출력과 오류다.

파일의 데이터와 별개로, 그 파일이 어디에 저장되고 누가 소유하고 누가 볼 수 있는지 같은 메타데이터는 아이노드(inode)에 있다.
모든 파일은 파일 시스템 안에서 고유한 아이노드 번호를 갖고, `ls -i`로 볼 수 있다.
사용자와 그룹은 Unix에게 파일의 속성일 뿐이다.

이 분리에서 두 가지 성질이 나온다.
첫째, 같은 파일 시스템 안에서 1GB 파일을 `mv`하는 것은 순식간이지만 `cp`는 오래 걸린다.
옮길 때는 데이터가 아니라 디렉터리 구조의 항목만 바꾸기 때문이다.
둘째, 자기 파일의 모든 권한을 없애도 되돌릴 수 있다.
권한이 파일 안이 아니라 아이노드에 있고, 아이노드는 소유자와 root가 언제든 고칠 수 있기 때문이다.

### 권한: 세 주체, 세 비트

`-rwxrwxrwx` 같은 문자열의 첫 글자는 파일 종류(디렉터리, 심볼릭 링크, 문자 장치 등)이고, 나머지 아홉 글자는 소유자, 그룹, 그 밖의 사람에 대한 읽기(`r`), 쓰기(`w`), 실행(`x`) 권한이다.
디렉터리에서 `x`는 그 안을 탐색할 수 있다는 뜻이다.
주체마다 세 비트이므로 숫자 하나로 표현할 수 있고, `chmod 721`은 `rwx-w---x`가 된다.
저자는 `chmod u+rwx`, `chmod g+w`, `chmod o+x`처럼 읽기 쉬운 형식을 더 좋아한다고 쓴다.

실행 비트 자리에 `s`가 있으면 setuid다.
`/usr/bin/passwd`는 root만 쓸 수 있는 `/etc/passwd`를 고쳐야 하므로, 누가 실행하든 파일 소유자인 root의 권한으로 돈다.

### 링크: 같은 아이노드를 가리키는 두 이름

하드 링크는 같은 아이노드를 가리키는 또 하나의 이름이다.
`.`와 `..`도 하드 링크다.
심볼릭 링크는 원래 파일의 경로를 담은 새 작은 파일이고, 원래 파일을 지우면 가리킬 곳이 없는 끊긴 링크(dangling symlink)가 된다.
`ls -l`의 권한 다음 숫자가 하드 링크 수다.

### 프로세스: fork, exec, exit, wait

프로세스는 실행 중인 코드의 인스턴스다.
각 프로세스는 고유한 `pid`와 자기를 만든 부모의 `ppid`를 갖고, 부모로부터 사용자 ID와 그룹 ID를 물려받는다.
파일 시스템의 루트 `/`처럼 프로세스에도 뿌리가 있어, `init`(현대 Linux에서는 대개 `systemd`)이 보통 `pid` 1이다.

새 프로세스는 이렇게 생긴다.

1. 부모가 `fork()`로 자기를 복제해 자식을 만든다.
2. 자식이 `exec()`로 자기 안의 프로그램을 실행하려는 프로그램으로 바꾼다.
3. 자식이 끝나면 `exit()`로 종료 코드 하나만 남긴다. 0은 성공, 나머지는 오류다.
4. 부모가 `wait()`로 그 종료 코드를 받는다.

부모가 `wait()`를 부르지 않으면 종료 코드가 소비되지 않아 운영체제가 정리하지 못하는 좀비 프로세스가 남는다.
부모가 먼저 죽으면 자식은 고아 프로세스가 되어 `init`에 입양된다.
자식이 부모에게 돌려줄 수 있는 것은 종료 코드뿐이므로, 그 이상은 프로세스 간 통신이 필요하다.

### 셸이 명령 하나를 실행하는 순서

셸도 프로세스이고, 터미널에서 띄우면 세 표준 파일이 `tty` 장치 파일에 연결된다.
명령 하나를 입력하면 셸은 이렇게 한다.

1. `fork()`로 자기를 복제한다. 자식은 부모의 파일 디스크립터를 그대로 물려받는다.
2. 리디렉션이 있으면 자식의 파일 디스크립터를 바꾼다. 이 일은 명령이 실행되기 전에 일어난다.
3. 자식이 `execve()`로 명령을 실행한다. close-on-exec 표시가 없는 디스크립터는 그대로 열려 있다.
4. 셸은 자식이 끝날 때까지 기다린다.

모든 명령이 이 과정을 거치지는 않는다.
`cd`나 `export`처럼 셸 자체의 상태를 바꿔야 하는 명령은 자식이 부모에게 값을 돌려줄 수 없으므로 셸 안에서 실행되는 내장 명령(builtin)이어야 한다.

파이프 `|`는 이 구조 위에서 단순해진다.
`pipe()` 시스템 호출로 앞 프로세스의 `stdout`을 뒤 프로세스의 `stdin`에 이어 줄 뿐이다.
`stderr`은 파이프를 타지 않고 원래 자리로 간다.

### `PATH`: 명령 이름에서 실행 파일까지

`ls`라고 입력하면 셸은 절대 경로가 없는 명령을 환경 변수 `PATH`의 디렉터리 목록에서 순서대로 찾아 처음 찾은 파일을 실행한다.
환경 변수는 자식에게 전달되지만, 셸의 지역 변수는 전달되지 않는다.
그리고 자식이 환경 변수를 바꿔도 부모에게는 돌아가지 않는다.

## 확인하기

글의 실험을 순서대로 돌려 보면 위의 설명이 직접 보인다.
임시 디렉터리에서 한다.

### 아이노드와 링크

```bash
cd "$(mktemp -d)"
touch a
ln a x          # 하드 링크: 같은 아이노드
ln -s a y       # 심볼릭 링크: 새 아이노드
ls -li          # a와 x의 아이노드 번호가 같고 링크 수가 2다
echo lsd >> y   # y를 거쳐 a에 쓴다
cat x           # 같은 아이노드이므로 lsd가 보인다
rm a
cat y           # 끊긴 링크: No such file or directory
ls -li          # x의 링크 수가 1로 줄었다
```

### `.`와 `..`가 하드 링크라는 것

```bash
mkdir sample_dir
ls -ail                  # sample_dir의 아이노드 번호를 본다
cd sample_dir && ls -ail # 여기서 .의 번호가 위와 같고, ..의 번호는 부모 .와 같다
cd ..
```

### 리디렉션은 실행 전에 일어난다

```bash
printf 'd\nc\nb\na\n' > res.txt
sort res.txt > res.txt   # sort가 읽기 전에 셸이 res.txt를 비운다
cat res.txt              # 비어 있다

printf 'd\nc\nb\na\n' > res.txt
set -o noclobber
sort res.txt > res.txt   # cannot overwrite existing file
set +o noclobber
```

### `stderr`만 파이프로 보내기

```bash
# 2>&1이 먼저 stderr를 지금의 stdout(파이프)로 복제하고,
# 그다음 >/dev/null이 stdout만 버린다. 순서를 바꾸면 결과가 달라진다.
ls /nonexistent . 2>&1 >/dev/null | tr a-z A-Z
```

### 환경 변수와 한 번짜리 `PATH`

```bash
FOO=local; bash -c 'echo "child sees: [$FOO]"'        # 지역 변수는 전달되지 않는다
export FOO; bash -c 'echo "child sees: [$FOO]"'       # 환경 변수는 전달된다
PATH='' ls                                            # 이 명령에만 PATH가 비어 실패한다
echo "$PATH"                                          # 셸의 PATH는 그대로다
```

### 입력은 기다리는 동안에도 쌓인다

```bash
sleep 5
# sleep이 도는 동안 ls를 치고 Enter를 누르면, sleep이 끝난 뒤 ls가 실행된다.
# 막힌 것은 프로세스이지 tty 입력 스트림이 아니기 때문이다.
```

## 트레이드오프

### 모든 것은 파일이라는 추상화는 강력하지만 새는 곳이 있다

모든 것을 파일로 다루면 같은 도구로 문서와 장치와 프로세스 정보를 다룰 수 있다.
`cat`, `grep`, 리디렉션, 파이프가 모두 같은 인터페이스 위에서 돈다.
글이 이 원칙을 함수형 프로그래밍의 합성과 연결하는 것도 그 강력함 때문이다.

그러나 추상화는 완벽하지 않다.
Lobste.rs에서 zge는 글의 디렉터리를 열어 내용을 볼 수 있다는 예를 반박했다.[^zge]
지금은 디렉터리를 `cat`할 수 없고, Vim이 디렉터리를 보여 주는 것은 파일 관리자(netrw)가 내장되어 있어서일 뿐 GUI 파일 관리자나 `ls`와 다르지 않다는 것이다.
디렉터리는 개념적으로 파일이지만, 일반 파일처럼 `read()`할 수 있는 바이트 스트림은 아니다.
소켓, 장치, `/proc` 항목도 저마다 다른 규칙을 가진다.

### 텍스트 스트림은 보편적이지만 구조를 잃는다

글의 긴 파이프라인 예시는 `ls -ail`의 출력을 크기로 정렬해 가장 큰 파일의 크기를 뽑는다.
저자 스스로 더 우아한 방법이 검색 한 번이면 나온다고 인정하듯, 이것은 사람이 읽으라고 만든 출력을 칸 위치로 잘라 내는 방식이다.
`cut -d ' '`는 연속된 공백을 칸 하나로 보지 않으므로, 파일 크기의 자릿수가 달라지면 칸 번호가 어긋난다.

텍스트 스트림이 보편적인 인터페이스라는 철학은 도구를 쉽게 잇게 해 주지만, 도구 사이에 오가는 데이터의 구조는 약속하지 않는다.
그래서 스크립트에서는 `stat`이나 `find -printf`처럼 기계가 읽으라고 만든 출력을 쓰는 편이 안전하다.

### 터미널의 생산성 상한은 도구가 아니라 조합에서 나온다

zge는 명령줄을 미화하는 사람들이 싫다며, 그들이 생산적인 것은 그만큼 시간을 들였기 때문이라고 지적했다.
levlaz는 소프트웨어마다 도달할 수 있는 생산성의 이론적 최대가 있고, 터미널 편집기의 상한이 GUI 편집기보다 높지만 둘 다 많은 시간을 들여야 한다고 답했다.[^levlaz]
arxitt은 터미널 프로그램은 키보드로만 움직이고 모든 기능이 의미 있어야 한다는 제약 때문에 그 상한이 높다고 봤고,[^arxitt] zge는 vi의 가치는 키 조합에 있으니 GUI에서도 그대로 구현할 수 있다고 반박했다.[^zge-2]
akavel은 gvim도 GUI 편집기이니 터미널 대 GUI라는 축 자체가 좋은 비교가 아니라고 정리했다.[^akavel]

이 논쟁의 결론은 Unix 철학과 같은 곳에 닿는다.
생산성은 도구의 화면 모양이 아니라 작은 동작을 얼마나 자유롭게 조합할 수 있느냐에서 나온다.

## 함정

### `>`는 명령보다 먼저 파일을 비운다

`sort res.txt > res.txt`가 빈 파일을 남기는 것은 셸이 명령을 실행하기 전에 출력 파일을 열면서 내용을 지우기 때문이다.
같은 파일을 읽고 쓰는 모든 명령에서 같은 일이 생긴다.
`noclobber`를 켜 두거나, 임시 파일에 쓴 뒤 옮기거나, `sponge` 같은 도구를 쓴다.

### `2>1`과 `2>&1`은 다르다

`2>1`은 `stderr`를 `1`이라는 이름의 파일로 보낸다.
파일 디스크립터를 가리키려면 `&`가 필요하다.
그리고 `2>&1 >/dev/null`과 `>/dev/null 2>&1`은 결과가 다르다.
리디렉션은 왼쪽부터 차례로 적용되고, `2>&1`은 그 순간의 `stdout`을 복제하기 때문이다.

### 자식은 부모의 상태를 바꿀 수 없다

스크립트 안에서 `cd`나 `export`를 해도, 그 스크립트를 실행한 셸은 바뀌지 않는다.
스크립트는 자식 프로세스이고, 자식은 종료 코드 말고는 부모에게 아무것도 돌려주지 못한다.
현재 셸을 바꾸려면 `source`로 읽어 들여야 한다.

### 원문의 몇몇 설명은 시간이 지나며 낡았다

글은 맨 Docker 컨테이너를 프로덕션에서 돌리면 root로 돌아야 해서 위험하다고 쓰지만, 컨테이너 안에서 비root 사용자로 실행하거나 rootless 모드로 데몬을 돌리는 방법이 있다.
`systemd`가 `init`보다 전반적으로 더 안정적이라는 문장에 대해서도 HN에서 coribuci가 그것이 한 가지 일을 잘하라는 앞의 Unix 철학과 어떻게 맞느냐고 되물었다.[^coribuci]
이런 문장은 2019년의 한 관점으로 읽는 편이 맞다.

## 체크리스트

- 같은 파일을 읽고 쓰는 명령에 `>`를 쓰고 있지 않은가?
- `stderr` 리디렉션의 순서가 의도한 대로인가?
- 스크립트가 부모 셸의 디렉터리나 환경을 바꿀 것이라고 기대하고 있지 않은가?
- 파이프라인이 사람이 읽는 출력을 칸 위치로 자르고 있지 않은가?
- setuid 파일이 필요한 곳에만 있는가(`find / -perm -4000 -type f 2>/dev/null`)?
- 끊긴 심볼릭 링크를 찾아 정리했는가(`find . -xtype l`)?

## 기억할 원칙

### 명령을 외우지 말고 파일 디스크립터가 어디에 연결되어 있는지 그려 본다

저자는 파이프나 터미널에서 무엇을 하든 입력과 출력 파일이 어떻게 연결되어 있는지 상상하면 문제가 생기지 않는다고 쓴다.
리디렉션, 파이프, 백그라운드 실행, 서브셸은 모두 fork 순간에 복제된 디스크립터가 어디를 가리키느냐의 문제다.
그 그림만 그릴 수 있으면 처음 보는 명령 조합도 동작을 예측할 수 있다.

HN에서 roryrjb는 업계의 많은 사람이 이런 것을 모른 채 위쪽 인터페이스만 쓰다가, 문제가 생기면 막혀서 왜 되는지 모르는 해법을 복사해 붙인다고 적었다.[^roryrjb]
그것이 나쁜 것은 아니지만, 아래층의 그림을 가진 사람은 복사하기 전에 그 해법이 왜 통하는지 판단할 수 있다.
저자가 글 첫머리에 말한 두려워하지 않을 힘이 바로 그 판단력이다.
