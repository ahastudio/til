# 4장 리소스 지향 아키텍처(ROA)

《RESTful Web Services》(Leonard Richardson, Sam Ruby, O'Reilly 2007) 4장 정리.

## 개요

이 장은 REST의 힘을 어떻게 체계적으로 구조화하고 드러낼 수 있는지를 다룬다.
저자는 구체적인 RESTful 아키텍처로서 리소스 지향 아키텍처(Resource-Oriented Architecture, ROA)를 제시한다.
ROA는 하나의 문제를 RESTful 웹 서비스로 바꾸는 방법이며, URI와 HTTP와 XML을 나머지 웹과 같은 방식으로 작동하도록 배치해 프로그래머가 즐겁게 사용할 수 있게 한다.

1장에서 저자는 두 가지 질문에 대한 답으로 RESTful 웹 서비스를 분류했고, 그 답은 REST의 네 가지 정의적 특징 중 둘에 대응한다.

- 범위 지정 정보(“서버는 왜 이 데이터를 저 데이터 대신 보내야 하는가?”)는 URI에 담긴다. 이것이 주소 지정 가능성(addressability)의 원칙이다.
- 메서드 정보(“서버는 왜 이 데이터를 삭제하지 않고 보내야 하는가?”)는 HTTP 메서드에 담긴다. HTTP 메서드는 몇 개뿐이고 그것들이 무엇을 하는지 모두가 미리 알고 있다. 이것이 통일 인터페이스(uniform interface)의 원칙이다.

이 장에서는 ROA의 구성 요소인 리소스, 그 이름, 그 표현(representation), 그리고 그것들 사이의 링크를 소개한다.
그리고 ROA의 네 가지 속성인 주소 지정 가능성, 무상태성(statelessness), 연결성(connectedness), 통일 인터페이스를 설명한다.
웹 기술(HTTP, URI, XML)이 이 구성 요소들을 어떻게 구현해 그 속성들을 가능하게 하는지도 보여 준다.

## 리소스 지향이라니, 그게 뭔가

저자는 왜 그냥 REST라 하지 않고 새로운 용어인 리소스 지향 아키텍처를 만들었는지 설명한다.
ROA에 속하는 모든 것은 RESTful하지만, REST 자체는 아키텍처가 아니라 설계 기준(design criteria)의 집합이다.
어떤 아키텍처가 다른 아키텍처보다 그 기준을 더 잘 충족한다고 말할 수는 있어도, 유일한 “REST 아키텍처”란 존재하지 않는다.

지금까지 사람들은 각자의 REST 이해에 따라 서비스를 설계하면서 일회성 아키텍처를 만들어 왔고, 그 결과가 스스로 RESTful하다고 주장하는 다양한 REST-RPC 하이브리드 웹 서비스다.
저자는 실제로 RESTful한 웹 서비스를 만들기 위한 구체적 규칙을 제시해 이런 흐름을 멈추려 한다.

설계 기준으로서의 REST는 매우 일반적이어서 웹에 묶여 있지 않다.
REST의 어떤 부분도 HTTP의 작동 방식이나 URI의 구조에 의존하지 않는다.
그러나 이 책은 웹 서비스를 다루므로, 저자는 ROA를 명시적으로 웹의 기술에 묶어 HTTP와 URI로 REST를 하는 방법을 이야기한다.

저자는 새로운 용어를 만든 또 다른 이유로, “REST”가 종종 진영 다툼에 쓰이는 용어라는 점을 든다.
자신의 철학에 별도의 이름을 붙임으로써, 동의하지 않는 사람들이 ROA의 측면을 다른 RESTful 아키텍처나 REST 일반과 분리해 논할 수 있게 하려는 것이다.

## 리소스란 무엇인가

리소스(resource)는 그 자체로 하나의 사물로서 참조될 만큼 충분히 중요한 모든 것이다.
사용자가 그것에 하이퍼텍스트 링크를 걸거나, 그것에 대한 주장을 하거나 반박하거나, 그것의 표현을 가져오거나 캐시하거나, 그 일부나 전부를 참조로 다른 표현에 포함하거나, 주석을 달거나, 그 밖의 조작을 하고 싶어 할 만하다면, 그것을 리소스로 만들어야 한다.

보통 리소스는 컴퓨터에 저장되어 비트 스트림으로 표현될 수 있는 것이다.
문서 한 편, 데이터베이스의 한 행, 알고리즘 실행 결과 같은 것이다.
리소스는 사과 같은 물리적 대상일 수도 있고 용기(courage) 같은 추상적 개념일 수도 있지만, 그런 리소스의 표현은 만족스럽지 못할 수밖에 없다.

책이 드는 리소스 예시는 다음과 같다.

- 소프트웨어 릴리스 1.0.3 버전
- 소프트웨어 릴리스의 최신 버전
- 2006년 10월 24일의 첫 번째 블로그 항목
- 아칸소주 리틀록의 도로 지도
- 해파리에 관한 어떤 정보
- 해파리 관련 리소스들의 디렉터리
- 1024 다음의 소수
- 1024 다음의 소수 다섯 개
- 2004년 4분기 매출 수치
- 지인인 앨리스와 밥 사이의 관계
- 버그 데이터베이스에 등록된 미해결 버그 목록

## URI

리소스를 리소스로 만드는 것은 무엇인가.
리소스는 적어도 하나의 URI를 가져야 한다.
URI는 리소스의 이름이자 주소다.
어떤 정보 조각이 URI를 갖지 않는다면, 그것은 리소스가 아니고 웹에 실제로 존재하지도 않는다. 단지 다른 어떤 리소스를 설명하는 데이터 조각에 불과할 뿐이다.

HTTP 클라이언트는 리소스를 호스팅하는 서버에 접속해 메서드(“GET”)와 리소스로 가는 경로(“/hello.txt”)를 보내 리소스를 조작한다.
서버와 경로는 모두 리소스의 URI에서 나온다.

예를 들어 `http://www.example.com/hello.txt`에 대한 HTTP 1.1 요청과 응답은 다음과 같다.

```http
GET /hello.txt HTTP/1.1
Host: www.example.com
```

```http
200 OK
Content-Type: text/plain

Hello, world!
```

URI는 웹의 근본 기술이다.
HTML 이전에도 하이퍼텍스트 시스템이 있었고 HTTP 이전에도 인터넷 프로토콜이 있었지만, 그것들은 서로 대화하지 못했다.
URI는 이 인터넷 프로토콜들을 하나의 웹으로 연결했고, 이는 TCP/IP가 Usenet, Bitnet, CompuServe 같은 네트워크를 하나의 인터넷으로 연결한 것과 같다.
웹은 다른 프로토콜을 자기 안으로 흡수한 뒤 소멸시켰다.
오늘날 우리는 Gopher가 아니라 웹에서 서핑하고, FTP 사이트가 아니라 웹에서 파일을 내려받으며, WAIS가 아니라 웹에서 출판물을 검색하고, Usenet 뉴스그룹이 아니라 웹에서 대화한다.
웹이 다른 프로토콜을 밀어낸 까닭은 대부분의 프로토콜에 없는 것, 즉 이용 가능한 모든 항목에 이름표를 붙이는 단순한 방법을 갖고 있기 때문이다.

### URI는 서술적이어야 한다

여기서부터 ROA는 REST 논문과 W3C 권고의 성긴 권고 위에 무언가를 더한다.
저자는 리소스와 그 URI 사이에 직관적인 대응 관계가 있어야 한다고 제안한다.
앞서 나열한 리소스에 대한 좋은 URI 예시는 다음과 같다.

```text
http://www.example.com/software/releases/1.0.3.tar.gz
http://www.example.com/software/releases/latest.tar.gz
http://www.example.com/weblog/2006/10/24/0
http://www.example.com/map/roads/USA/AR/Little_Rock
http://www.example.com/wiki/Jellyfish
http://www.example.com/search/Jellyfish
http://www.example.com/nextprime/1024
http://www.example.com/next-5-primes/1024
http://www.example.com/sales/2004/Q4
http://www.example.com/relationships/Alice;Bob
http://www.example.com/bugs/by-state/open
```

URI는 구조를 가져야 하고 예측 가능한 방식으로 변해야 한다.
해파리는 `/search/Jellyfish`로 찾으면서 쥐는 `/i-want-to-know-about/Mice`로 찾게 해서는 안 된다.
클라이언트가 서비스의 URI 구조를 알면 스스로 진입점을 만들어 낼 수 있고, 이는 설계자가 생각하지 못한 방식으로도 클라이언트가 서비스를 쉽게 사용하게 한다.

이것은 REST의 절대 규칙은 아니다.
URI는 기술적으로 어떤 구조나 예측 가능성을 반드시 가질 필요가 없지만, 저자는 가져야 한다고 본다.
이는 좋은 웹 설계의 규칙 가운데 하나이며, RESTful 서비스와 REST-RPC 하이브리드 서비스 모두에 나타난다.

### URI와 리소스의 관계

몇 가지 경계 사례를 생각해 본다.
두 리소스가 같을 수 있는가, 두 URI가 같은 리소스를 가리킬 수 있는가, 하나의 URI가 두 리소스를 가리킬 수 있는가.

정의상 두 리소스는 같을 수 없다.
같다면 리소스는 하나뿐일 것이다.
다만 어느 시점에 서로 다른 두 리소스가 같은 데이터를 가리킬 수는 있다.
현재 릴리스가 1.0.3이라면 `.../releases/1.0.3.tar.gz`와 `.../releases/latest.tar.gz`는 한동안 같은 파일을 가리키지만, 두 URI 뒤의 개념은 다르다.
하나는 언제나 특정 버전을 가리키고, 다른 하나는 클라이언트가 접근하는 시점의 최신 버전을 가리킨다.
그것은 두 개념이자 두 리소스다.
1.0.3 버전의 버그를 보고할 때 latest에 링크를 걸지는 않을 것이다.

하나의 리소스는 하나의 URI를 가질 수도, 여러 개를 가질 수도 있다.
`.../sales/2004/Q4`에서 얻는 매출 수치는 `.../sales/Q42004`에서도 얻을 수 있다.
리소스가 여러 URI를 가지면 클라이언트가 그 리소스를 참조하기 쉬워진다.
단점은 URI 하나가 늘 때마다 다른 URI들의 가치가 희석된다는 점이다.
어떤 클라이언트는 이 URI를, 어떤 클라이언트는 저 URI를 쓰게 되고, 모든 URI가 같은 리소스를 가리킨다고 자동으로 검증할 방법이 없다.

이를 완화하는 한 가지 방법은 같은 리소스에 여러 URI를 두되 그중 하나를 정규(canonical) URI로 삼는 것이다.
클라이언트가 정규 URI를 요청하면 서버는 해당 데이터와 함께 응답 코드 200(“OK”)을 보낸다.
클라이언트가 다른 URI를 요청하면 서버는 응답 코드 303(“See Other”)과 함께 정규 URI를 보낸다.
클라이언트는 두 URI가 같은 리소스를 가리키는지 직접 볼 수는 없지만, 두 번의 HEAD 요청을 보내 한 URI가 다른 URI로 리다이렉트되는지, 아니면 둘 다 제3의 URI로 리다이렉트되는지 확인할 수 있다.

또 다른 방법은 모든 URI를 같은 것처럼 제공하되, 비정규 URI를 요청받을 때마다 응답의 Content-Location 헤더에 정규 URI를 담아 주는 것이다.

모든 URI는 정확히 하나의 리소스를 가리킨다.
둘 이상을 가리킨다면 그것은 Universal Resource Identifier가 아닐 것이다.
그러나 URI를 가져올 때 서버는 요청한 리소스와 그와 관련된 다른 리소스들에 관한 정보를 함께 보낼 수 있다.
웹 페이지를 가져오면 그 페이지 자신의 정보와 함께 다른 페이지로 가는 링크도 담겨 있고, S3 버킷을 가져오면 버킷 정보와 그 안의 객체들에 관한 정보가 함께 담겨 있다.

## 주소 지정 가능성(Addressability)

애플리케이션이 자기 데이터셋의 흥미로운 측면들을 리소스로 드러낸다면 그 애플리케이션은 주소 지정 가능하다.
리소스는 URI로 드러나므로, 주소 지정 가능한 애플리케이션은 제공할 만한 모든 정보 조각에 URI를 부여한다.
이는 보통 무한히 많은 URI가 된다.

최종 사용자 관점에서 주소 지정 가능성은 어떤 웹 사이트나 애플리케이션에서든 가장 중요한 측면이다.
사용자는 데이터가 충분히 흥미로우면 거의 모든 결함을 눈감아 주거나 우회하지만, 주소 지정 가능성의 부재만은 우회하기가 매우 어렵다.

“해파리에 관한 리소스 디렉터리”라는 장르의 실제 URI인 `http://www.google.com/search?q=jellyfish`를 생각해 본다.
그 해파리 검색은 `http://www.google.com`만큼이나 실제 URI다.
HTTP가 주소 지정 가능하지 않았거나 구글 검색 엔진이 주소 지정 가능한 웹 애플리케이션이 아니었다면, 저자는 그 URI를 책에 실을 수 없었을 것이다.
대신 “google.com에 접속해 검색 상자에 'jellyfish'를 입력하고 'Google Search' 버튼을 클릭하시오”라고 설명해야 했을 것이다.

이는 학술적 걱정거리가 아니다.
1990년대 중반 파일을 가리키는 `ftp://` URI가 보급되기 전까지 사람들은 “ftp.example.com에서 익명 FTP 세션을 시작한 뒤 pub/files/ 디렉터리로 이동해 file.txt를 내려받으시오”라고 써야 했다.
URI는 FTP를 HTTP만큼 주소 지정 가능하게 만들었고, 이제는 그 단계를 기계가 수행할 수 있다.

주소 지정 가능성 덕분에 URI를 북마크하고 나중에 다시 찾아올 수 있고, 자기 웹 페이지에 링크를 걸 수 있고, 다른 사람에게 이메일로 보낼 수 있다.
로컬 네트워크에 HTTP 프록시 캐시를 두어 대역폭을 아낄 수도 있는데, 이는 모든 페이지가 고유한 식별 문자열, 곧 주소를 갖기에 가능하다.
심지어 한 URI를 다른 URI의 입력으로 사용하는 URI 연쇄도 가능하다.
외부 웹 서비스로 페이지의 HTML을 검증하거나 텍스트를 다른 언어로 번역하려면, 그 서비스는 URI를 입력으로 기대한다.

아마존 S3 서비스는 모든 버킷과 객체가, 그리고 버킷 목록도 각자의 URI를 갖기 때문에 주소 지정 가능하다.
아직 존재하지 않는 버킷과 객체는 아직 리소스가 아니지만, 그것들도 자기 URI를 가지며, 그 URI로 PUT 요청을 보내 리소스를 생성할 수 있다.

가정용 컴퓨터의 파일 시스템도 주소 지정 가능한 시스템이며, 스프레드시트의 셀도 마찬가지다.
URI는 웹의 파일 경로이자 셀 주소다.

불행히도 많은 웹 애플리케이션은 이렇게 작동하지 않으며, 특히 Ajax 애플리케이션이 그렇다.
구글의 Gmail을 예로 들면, 최종 사용자 관점에서 Gmail의 URI는 오직 하나, `https://mail.google.com/`뿐이다.
무엇을 하든 다른 URI를 보게 되지 않으므로 “해파리에 관한 이메일 메시지” 리소스는 주소 지정 가능하지 않다.
그러나 그 뒤에는 주소 지정 가능한 웹 사이트가 있어, 해파리 관련 메시지 목록에도 URI가 있다.
문제는 그 웹 사이트의 소비자가 사용자가 아니라 브라우저 안에서 도는 자바스크립트 프로그램이라는 점이다.
Gmail 웹 서비스는 주소 지정 가능하지만, 그것을 사용하는 Gmail 웹 애플리케이션은 그렇지 않다.

## 무상태성(Statelessness)

무상태성은 ROA의 네 가지 주요 특징 중 둘째다.
저자는 두 가지 정의를 제시한다. 하나는 다소 일반적인 정의이고, 다른 하나는 ROA에 맞춘 더 실용적인 정의다.

무상태성은 모든 HTTP 요청이 완전한 고립 상태에서 일어남을 뜻한다.
클라이언트가 HTTP 요청을 할 때 서버가 그 요청을 처리하는 데 필요한 모든 정보를 담아 보낸다.
서버는 이전 요청의 정보에 의존하지 않는다.
그 정보가 중요했다면 클라이언트가 이번 요청에서 다시 보냈을 것이다.

더 실용적으로는 주소 지정 가능성과 연결해 이해할 수 있다.
주소 지정 가능성이 서버가 제공할 수 있는 모든 흥미로운 정보를 리소스로 드러내 URI를 부여해야 한다고 말한다면, 무상태성은 서버가 가질 수 있는 상태들 역시 리소스이며 각자의 URI를 부여받아야 한다고 말한다.
클라이언트는 어떤 요청을 받아들이도록 서버를 특정 상태로 몰아넣을 필요가 없어야 한다.

검색 엔진은 검색할 문자열마다 적어도 하나씩, 무한히 많은 상태를 가질 수 있는 웹 서비스다.
각 상태는 자기 URI를 갖는다.
쥐에 관한 디렉터리는 `.../search?q=mice`로, 해파리에 관한 디렉터리는 `.../search?q=jellyfish`로 요청할 수 있고, URI를 직접 만들기가 불편하면 `http://www.google.com/`에서 양식을 받아 채울 수 있다.

디렉터리를 요청하면 전체가 아니라 한 페이지, 곧 검색 엔진이 최선의 일치로 꼽은 10개 남짓의 항목 목록을 얻는다.
더 보려면 HTTP 요청을 더 해야 한다.
둘째 이후의 페이지들은 애플리케이션의 별개 상태이며 각자의 URI를 가져야 한다. 예컨대 `.../search?q=jellyfish&start=10` 같은 것이다.
다른 주소 지정 가능한 리소스와 마찬가지로, 그 상태를 남에게 전달하거나 캐시하거나 북마크해 두었다가 다시 올 수 있다.

이것이 무상태 애플리케이션이다.
클라이언트가 요청할 때마다 출발한 곳으로 돌아오며, 각 요청은 다른 요청들과 완전히 분리되어 있다.
클라이언트는 이 리소스들을 몇 번이든 어떤 순서로든 요청할 수 있고, “mice”의 1페이지를 요청하지 않고 2페이지를 먼저 요청해도 서버는 개의치 않는다.

이와 대비되는 상태 유지(stateful) 방식에서는 상태들이 서로 자연스럽게 이어진다.
대부분의 데스크톱 애플리케이션이 이렇게 설계된다.
상태를 두면 개별 HTTP 요청은 단순해질 수 있다.
FTP가 이렇게 작동한다. FTP에는 세션 동안 유지되는 “작업 디렉터리” 개념이 있어, 한 번 cd 한 뒤에는 다시 cd 하지 않고 같은 디렉터리에서 여러 파일을 가져올 수 있다.

그러나 상태를 두면 개별 요청은 단순해져도 프로토콜 전체는 훨씬 복잡해진다.
FTP 클라이언트가 HTTP 클라이언트보다 훨씬 복잡한 것은 세션 상태를 클라이언트와 서버 사이에서 동기화해야 하기 때문이며, 이는 신뢰할 수 없는 네트워크인 인터넷에서 특히 어렵다.

프로토콜에서 상태를 없애는 것은 곧 많은 실패 조건을 없애는 것이다.
서버는 클라이언트의 타임아웃을 걱정할 필요가 없다. 어떤 상호작용도 단일 요청보다 오래 지속되지 않기 때문이다.
서버는 각 클라이언트가 애플리케이션의 “어디”에 있는지 잃어버리지 않는다. 클라이언트가 매 요청마다 필요한 모든 정보를 보내기 때문이다.
클라이언트는 서버가 몰래 상태를 쥐고 있다가 잘못된 “작업 디렉터리”에서 동작을 수행하는 일도 겪지 않는다.

무상태성은 새로운 이점도 가져온다.
무상태 애플리케이션은 부하 분산 서버들에 분산하기 쉽다.
어떤 두 요청도 서로 의존하지 않으므로, 서로 조율하지 않는 두 서버가 각각 처리할 수 있고, 확장은 부하 분산기에 서버를 더 꽂는 것만큼 단순하다.
무상태 애플리케이션은 캐시하기도 쉽다.
소프트웨어는 단일 요청 하나만 보고 그 결과를 캐시할지 결정할 수 있으며, 이전 요청의 상태가 이번 요청의 캐시 가능성에 영향을 줄까 하는 불안이 없다.

클라이언트도 이득을 본다.
“mice” 디렉터리를 50페이지까지 처리하고 `.../search?q=mice&start=50`을 북마크한 뒤 일주일 뒤에 돌아와도, 앞선 상태들을 다시 거칠 필요가 없다.

HTTP는 본질적으로 무상태 프로토콜이므로 웹 서비스를 작성하면 기본적으로 무상태성을 얻는다.
무상태성을 깨려면 무언가를 해야 한다.
가장 흔히 무상태성을 깨는 방법은 프레임워크의 HTTP 세션 기능을 쓰는 것이다.
사용자가 사이트를 처음 방문하면 세션을 식별하는 고유 문자열을 받는데, 이 문자열은 쿠키에 담기거나 사이트가 제공하는 모든 URI에 전파된다.
Rails 애플리케이션이 세션 쿠키를 설정하는 예는 다음과 같다.

```http
Set-Cookie: _session_id=c1c934bbe6168dcb904d21a7f5644a2d; path=/
```

PHP 애플리케이션이 세션 ID를 URI로 전파하는 예는 `http://www.example.com/forums?PHPSESSID=27314962133`이다.

중요한 것은, 이 무의미한 16진수나 10진수 숫자 자체는 상태가 아니라는 점이다.
그것은 서버 쪽 데이터 구조로 들어가는 키일 뿐이며, 상태는 그 데이터 구조 안에 있다.
상태를 담은 URI 자체에는 RESTful하지 않은 점이 없다. 그것은 서버가 클라이언트에게 가능한 다음 상태를 알리는 방식이다.
그러나 쿠키에는 RESTful하지 않은 점이 있다.
브라우저 비유로 말하면, 쿠키는 웹 서비스 클라이언트의 뒤로 가기 버튼을 망가뜨린다.

구글 검색 엔진이 제공한 HTML 페이지에 있는 `start=10` 같은 쿼리 변수는 서버가 클라이언트에게 가능한 다음 상태를 보내는 것이다.
그러나 URI는 서버에 저장된 상태로 가는 키가 아니라 상태 자체를 담아야 한다.
`start=10`은 그 자체로 의미가 있지만 `PHPSESSID=27314962133`은 그렇지 않다.
RESTful함은 상태가 클라이언트 쪽에 머물고, 그 상태가 필요한 매 요청마다 서버로 전송될 것을 요구한다.
서버는 따라갈 상태 있는 링크를 보내 클라이언트를 새 상태로 넌지시 이끌 수는 있지만, 자기 상태를 쥐고 있을 수는 없다.

### 애플리케이션 상태 대 리소스 상태

“무상태성”을 말할 때 무엇이 “상태”로 치는가.
서버 쪽에 두려는 유용한 영속 데이터와, 서버에서 치우려는 이 상태의 차이는 무엇인가.
Flickr는 사진을 계정에 올리게 하고 그 사진을 서버에 저장한다.
서버가 어떤 상태도 갖지 않게 하려고 매 요청마다 모든 사진을 함께 보내게 한다면 미친 짓이고 서비스의 존재 이유를 무너뜨릴 것이다.

문제는 용어에 있다.
무상태성이라는 말은 마치 상태가 한 종류뿐이고 서버가 그것 없이 지내야 하는 것처럼 들린다.
실제로는 두 종류의 상태가 있다.
저자는 이 지점부터 클라이언트에 있어야 할 애플리케이션 상태(application state)와 서버에 있어야 할 리소스 상태(resource state)를 구별한다.

검색 엔진을 쓸 때 현재 질의와 현재 페이지는 클라이언트 상태 조각이다.
이 상태는 클라이언트마다 다르다.
당신은 “jellyfish” 검색 결과의 3페이지에, 나는 “mice” 검색 결과의 1페이지에 있을 수 있다.
우리가 애플리케이션을 서로 다른 경로로 지나왔기 때문에 각자의 클라이언트가 서로 다른 애플리케이션 상태를 저장한다.

웹 서비스는 클라이언트가 실제로 요청할 때만 그 애플리케이션 상태에 신경 쓰면 된다.
그 외의 시간에는 클라이언트의 존재조차 모른다.
그래서 클라이언트가 요청할 때마다 서버가 처리에 필요로 할 모든 애플리케이션 상태를 담아야 한다.
서버는 링크가 담긴 페이지를 돌려주어 앞으로 할 만한 다른 요청을 클라이언트에게 알릴 수 있지만, 그러고 나면 다음 요청 때까지 클라이언트를 잊어도 된다.
클라이언트가 애플리케이션을 지나는 자기 경로를 스스로 관리해야 한다.

리소스 상태는 모든 클라이언트에게 동일하며, 그 자리는 서버다.
Flickr에 사진을 올리면 새 리소스가 만들어진다. 그 사진은 자기 URI를 가지며 이후 요청의 대상이 될 수 있다.
그 “사진” 리소스는 HTTP로 가져오고 수정하고 삭제할 수 있으며, 모두에게 열려 있어 나도 가져올 수 있다.
사진은 리소스 상태의 한 조각이고, 클라이언트가 삭제할 때까지 서버에 남는다.

클라이언트 상태는 예상치 못한 곳에서 나타나기도 한다.
많은 웹 서비스가 API 키 또는 애플리케이션 키라 부르는 고유 문자열에 가입하게 한다.
매 요청에 이 키를 보내면 서버가 그것으로 하루 요청 수를 제한한다.
예컨대 구글의 (지금은 폐기된) SOAP 검색 API용 API 키는 하루 1,000회 요청까지 유효하다.
이는 클라이언트 상태로, 클라이언트마다 다르다. 1,000번째 요청에서는 데이터를 얻지만 1,001번째 요청에서는 오류를 얻는 반면, 다른 클라이언트는 402번째 요청에서 여전히 잘 작동한다.

물론 클라이언트가 이 애플리케이션 상태를 스스로 정직하게 보고하리라 믿을 수는 없으므로, 서버는 이런 종류의 애플리케이션 상태를 서버에 두어 무상태성을 위반한다.
API 키는 Rails의 _session_id 쿠키처럼 하루 지속되는 서버 쪽 클라이언트 세션으로 가는 키다.
이는 그런대로 괜찮지만 확장성의 대가가 따른다.
서비스를 여러 대의 기계에 분산하려면 클러스터의 모든 기계가 당신이 1,001번째, 내가 402번째 요청 중임을 알아야 하거나(기술 용어로 세션 복제, session replication), 아니면 부하 분산기가 당신의 모든 요청을 클러스터의 같은 기계로 보내도록 보장해야 한다(기술 용어로 세션 어피니티, session affinity).
무상태성은 이 요구를 없앤다.
서비스 설계자는 리소스 상태를 여러 기계에 나눠야 할 때에만 데이터 복제를 고민하면 된다.

## 표현(Representations)

애플리케이션을 리소스로 나누면 표면적이 넓어진다.
사용자는 적절한 URI를 만들어 필요한 바로 그 지점으로 애플리케이션에 진입할 수 있다.
그러나 리소스는 데이터 자체가 아니라, 데이터를 “미해결 버그 목록”이나 “해파리에 관한 정보”로 나누는 설계자의 착상일 뿐이다.
웹 서버는 착상을 보낼 수 없고, 특정 파일 형식과 특정 언어로 된 바이트 열을 보내야 한다.
이것이 리소스의 표현(representation)이다.

리소스는 표현의 원천이며, 표현은 리소스의 현재 상태에 관한 어떤 데이터일 뿐이다.
대부분의 리소스 자체가 (버그 목록처럼) 데이터 항목이므로, 그 데이터 자체가 리소스의 명백한 표현이 된다.
서버는 미해결 버그 목록을 XML 문서로, 웹 페이지로, 또는 쉼표로 구분된 텍스트로 제시할 수 있다.
2004년 4분기 매출 수치는 숫자로도 그래프 차트로도 표현될 수 있다.
많은 뉴스 사이트가 기사를 광고가 실린 형식과 간소화된 “인쇄용” 형식으로 제공하는데, 이것들은 모두 같은 리소스의 서로 다른 표현이다.

그러나 어떤 리소스는 물리적 대상 등 정보로 환원할 수 없는 것을 나타낸다.
그런 것의 좋은 표현은 무엇인가.
완벽한 충실성을 걱정할 필요는 없다. 표현은 리소스 상태에 관한 유용한 정보라면 무엇이든 된다.

웹 서비스에 연결된 물리적 대상인 음료 자판기를 생각해 본다.
목표는 손님이 자판기까지 헛걸음하지 않게 하는 것이며, 이 서비스로 손님은 음료가 차가운지, 좋아하는 상표가 다 팔렸는지 알 수 있다.
물리적 음료 캔이 서비스로 제공되기를 기대하는 사람은 없다. 물리적 대상은 데이터가 아니기 때문이다.
그러나 그것들에 관한 데이터, 곧 메타데이터는 있다.
자판기의 각 슬롯에 다음 캔의 맛, 가격, 온도를 아는 장치를 달 수 있고, 각 슬롯은 물론 자판기 전체도 리소스로 드러낼 수 있으며, 계기의 메타데이터를 리소스 표현에 쓸 수 있다.

대상의 어떤 표현이 실제 데이터를 담더라도, 메타데이터를 담는 표현을 함께 가질 수 있다.
온라인 서점은 책 한 권에 두 가지 표현을 제공할 수 있다.

1. 표지 이미지와 리뷰 같은 메타데이터만 담아 책을 광고하는 표현.
2. 값을 치르면 HTTP로 전송되는, 책 내용의 전자 사본.

표현은 반대 방향으로도 흐를 수 있다.
새 리소스의 표현을 서버에 보내 서버가 리소스를 만들게 할 수 있는데, Flickr에 사진을 올릴 때 이런 일이 일어난다.
또는 기존 리소스의 새 표현을 서버에 주어, 서버가 그 새 표현에 맞게 리소스를 수정하게 할 수도 있다.

### 표현 사이에서 결정하기

서버가 한 리소스의 여러 표현을 제공한다면, 클라이언트가 어느 것을 요청하는지 어떻게 알아내는가.
예컨대 보도자료가 영어와 스페인어로 나온다면 특정 클라이언트는 어느 것을 원하는가.

REST의 제약 안에서 이를 알아내는 방법은 여럿이다.
가장 단순하고 저자가 ROA에 권장하는 방법은 리소스의 각 표현에 별개의 URI를 부여하는 것이다.
`http://www.example.com/releases/104.en`은 영어 표현을, `http://www.example.com/releases/104.es`는 스페인어 표현을 가리킬 수 있다.

저자가 ROA 애플리케이션에 이 기법을 권장하는 까닭은, URI가 서버의 요청 처리에 필요한 모든 정보를 담기 때문이다.
같은 리소스에 여러 URI를 드러낼 때 늘 그렇듯 단점은 희석이다. 서로 다른 언어로 보도자료를 이야기하는 사람들이 서로 다른 것을 이야기하는 것처럼 보인다.
`http://www.example.com/releases/104`를 어떤 언어와도 무관한 플라톤적 형상(Platonic form)으로서 드러내면 이 문제를 다소 완화할 수 있다.

다른 방법은 콘텐츠 협상(content negotiation)이다.
이 경우 드러나는 URI는 플라톤적 형상 URI인 `http://www.example.com/releases/104` 하나뿐이다.
클라이언트가 그 URI를 요청할 때, 자신이 받아들일 수 있는 표현 종류를 알리는 특별한 HTTP 요청 헤더를 함께 제공한다.

웹 브라우저에는 어떤 언어로 페이지를 받고 싶은지 설정하는 언어 기본 설정이 있고, 브라우저는 이 정보를 매 HTTP 요청의 Accept-Language 헤더에 담아 보낸다.
서버는 대개 이 정보를 무시하는데 대부분의 페이지가 한 언어로만 있기 때문이다.
그러나 같은 리소스의 서로 다른 언어 표현을 드러내려는 여기서는 잘 들어맞는다.
클라이언트가 `http://www.example.com/releases/104`를 요청하면 서버는 Accept-Language 헤더를 근거로 영어 표현과 스페인어 표현 중 무엇을 보낼지 결정할 수 있다.

클라이언트는 Accept 헤더를 설정해 표현의 파일 형식 선호도 지정할 수 있다.
XHTML을 HTML보다, SVG를 다른 그래픽 형식보다 선호한다고 말할 수 있다.

서버는 어느 표현을 보낼지 결정할 때 이런 요청 메타데이터를 무엇이든 쓸 수 있다.
다른 종류의 요청 메타데이터로는 결제 정보, 인증 자격 증명, 요청 시각, 캐싱 지시, 심지어 클라이언트 IP 주소까지 있다.
이 모든 것이 표현에 어떤 데이터를 담을지, 어떤 언어와 형식을 쓸지, 나아가 표현을 아예 보낼지 접근을 거부할지에 영향을 줄 수 있다.

이 정보를 HTTP 헤더에 두는 것도 RESTful하고 URI에 두는 것도 RESTful하다.
저자는 가능한 한 많은 정보를 URI에, 가능한 한 적은 정보를 요청 메타데이터에 둘 것을 권한다.
URI가 메타데이터보다 유용하다고 보기 때문이다.
URI는 사람에서 사람으로, 프로그램에서 프로그램으로 전달되지만 요청 메타데이터는 그 과정에서 거의 언제나 유실된다.

이 딜레마의 간단한 예는 `http://validator.w3.org/`에 있는 W3C HTML 검증기다.
영어판 보도자료에 대한 검증 보고서는 하나의 리소스이고, 스페인어판에 대한 검증 보고서는 또 다른 리소스다.
당신의 웹 공간에 있는 모든 URI는, 그것이 당신 사이트에서 별개의 리소스를 가리키든 아니든, W3C 웹 애플리케이션에서 하나의 리소스가 된다.
보도자료가 표현마다 별개의 URI를 가지면 W3C에서 두 개의 리소스, 곧 영어판과 스페인어판의 검증 보고서를 얻을 수 있다.
그러나 플라톤적 형상 URI만 드러내고 두 표현을 그 URI에서 제공하면 W3C에서 하나의 리소스만 얻을 수 있고, 그것은 기본 판(아마 영어)에 대한 검증 보고서다.
그러면 스페인어 표현에 HTML 형식 오류가 있는지 알 길이 없다.

사람과 달리 컴퓨터 프로그램은 예상치 못한 표현을 다루는 데 매우 서툴다.
저자는 자동화된 웹 클라이언트가 자신이 원하는 표현을 가능한 한 명시적으로 밝혀야 한다고 본다.
이는 거의 언제나 URL에 표현을 지정하는 것을 뜻한다.

## 링크와 연결성(Links and Connectedness)

때때로 표현은 직렬화된 데이터 구조에 지나지 않아, 데이터만 빨아들이고 버려지도록 되어 있다.
그러나 가장 RESTful한 서비스에서 표현은 하이퍼미디어(hypermedia)다. 곧 데이터뿐 아니라 다른 리소스로 가는 링크까지 담은 문서다.

구글의 해파리 문서 디렉터리(`http://www.google.com/search?q=jellyfish`)에 가면 검색 결과 몇 개와 디렉터리의 다른 페이지로 가는 내부 링크 묶음을 본다.
여기에는 데이터와 링크가 있다.
데이터는 웹 어딘가에서 누군가가 해파리에 대해 이러저러하게 말했다고 알려 주고, 링크는 다른 리소스로의 접근을 준다.
링크에는 구글 검색 “웹 서비스” 내부의 것도, 웹의 다른 곳의 것도 있다.

- 해파리를 이야기하는 외부 웹 페이지로 가는 링크. 이런 종류의 링크를 제시하는 것이 이 웹 서비스의 핵심 목적이다.
- 그 외부 페이지의 구글 캐시로 가는 링크(“Cached” 링크). 이 링크는 언제나 구글 소유 IP 주소를 가리키는 긴 URI를 갖는다.
- 그 외부 페이지와 관련되었다고 구글이 판단한 페이지들의 디렉터리로 가는 링크(“Similar pages”). 이는 웹 서비스가 URI를 입력으로 받는 또 다른 사례다.
- “jellyfish” 디렉터리의 다른 페이지로 데려가는 탐색 링크 묶음. `.../search?q=jellyfish&start=10`, `.../search?q=jellyfish&start=20` 등.

REST에 관한 글을 읽어 봤다면 Fielding 논문의 격언인 “애플리케이션 상태의 엔진으로서의 하이퍼미디어(Hypermedia as the engine of application state)”를 접했을 것이다.
그 격언의 뜻은 이렇다.
HTTP “세션”의 현재 상태는 리소스 상태로서 서버에 저장되지 않고, 애플리케이션 상태로서 클라이언트가 추적하며, 클라이언트가 웹을 지나는 경로에 의해 만들어진다.
서버는 하이퍼텍스트 표현 안의 링크와 양식, 곧 “하이퍼미디어”를 제공해 클라이언트의 경로를 이끈다.

서버는 현재 상태에서 가까운 상태들에 관한 안내를 클라이언트에게 보낸다.
`.../search?q=jellyfish`의 “next” 링크는 상태의 지렛대(lever of state)로서, 현재 상태에서 관련된 상태로 가는 방법을 보여 준다.
URI를 담은 문서는 애플리케이션의 또 다른 가능한 상태(“2페이지”, “이 URI와 관련됨”, “이 URI의 캐시본”)를 가리키거나, 전혀 다른 애플리케이션의 가능한 상태를 가리킬 수도 있다.

저자는 링크를 갖는 이 성질을 연결성(connectedness)이라 부른다.
링크를 따라가고 양식을 채우는 것만으로 서비스를 서로 다른 상태로 만들 수 있는 정도만큼 웹 서비스는 연결되어 있다.
“하이퍼미디어가 애플리케이션 상태의 엔진”이라는 말이 개념을 실제보다 어렵게 들리게 하므로 저자는 이를 “연결성”이라 부른다.
요지는 리소스가 자신들의 표현 안에서 서로 링크를 걸어야 한다는 것뿐이다.

사람의 웹이 쓰기 쉬운 것은 잘 연결되어 있기 때문이다.
많은 사용자가 ISP가 설정해 준 브라우저 홈페이지라는 단일 출발점에서 모든 서핑을 하는데, 이는 페이지들이 사이트를 넘나들며 서로 링크되어 웹이 잘 연결되어 있기에 가능하다.

그러나 대부분의 웹 서비스는 서로 연결되기는커녕 내부적으로도 연결되어 있지 않다.
아마존 S3는 주소 지정 가능하고 무상태이지만 연결되어 있지 않은 RESTful 웹 서비스다.
S3 표현은 결코 URI를 담지 않는다.
S3 버킷을 GET 하려면 버킷 URI를 구성하는 규칙을 알아야 하며, 버킷 목록을 GET 한 뒤 원하는 버킷으로 가는 링크를 따라갈 수는 없다.

저자는 세 가지 서비스로 이를 대비시킨다.

- 서비스 A는 전형적인 RPC 스타일 서비스로, 모든 것을 단일 URI로 드러낸다. 주소 지정 가능하지도 연결되어 있지도 않다.
- 서비스 B는 주소 지정 가능하지만 연결되어 있지 않다. 리소스 사이의 관계를 알리는 표시가 없다. REST-RPC 하이브리드 서비스이거나 아마존 S3 같은 RESTful 서비스일 수 있다.
- 서비스 C는 주소 지정 가능하고 잘 연결되어 있다. 리소스들이 (아마도) 말이 되는 방식으로 서로 링크되어 있다. 완전한 RESTful 서비스일 수 있다.

저자는 S3 버킷 목록 XML에 URI 태그를 더해 연결되도록 바꾼 예를 보인다.
이는 XML 표현에 URI를 넣는 한 가지 방법이며, 리소스들이 잘 연결될수록 그 사이의 관계가 더 뚜렷해진다.

```xml
<?xml version='1.0' encoding='UTF-8'?>
<ListAllMyBucketsResult xmlns='http://s3.amazonaws.com/doc/2006-03-01/'>
  <Owner>
    <ID>c0363f7260f2f5fcf38d48039f4fb5cab21b060577817310be5170e7774aad70</ID>
    <DisplayName>leonardr28</DisplayName>
  </Owner>
  <Buckets>
    <Bucket>
      <Name>crummy.com</Name>
      <URI>https://s3.amazonaws.com/crummy.com</URI>
      <CreationDate>2006-10-26T18:46:45.000Z</CreationDate>
    </Bucket>
  </Buckets>
</ListAllMyBucketsResult>
```

## 통일 인터페이스(The Uniform Interface)

웹 전체에서 리소스에 할 수 있는 기본 동작은 몇 가지뿐이다.
HTTP는 가장 흔한 네 가지 작업을 위해 네 개의 기본 메서드를 제공한다.

- 리소스의 표현을 가져오기: HTTP GET
- 새 리소스를 생성하기: 새 URI에 HTTP PUT, 또는 기존 URI에 HTTP POST(아래 POST 절 참조)
- 기존 리소스를 수정하기: 기존 URI에 HTTP PUT
- 기존 리소스를 삭제하기: HTTP DELETE

저자는 이 네 가지로 생각해 낼 수 있는 거의 모든 작업을 표현하는 법을 설명하고, 덜 흔한 두 작업을 위한 HTTP 메서드인 HEAD와 OPTIONS도 다룬다.

### GET, PUT, DELETE

리소스를 가져오거나 삭제하려면 클라이언트는 그 URI로 GET 또는 DELETE 요청을 보낸다.
GET 요청의 경우 서버는 응답 엔티티 본문(entity-body)에 표현을 돌려보낸다.
DELETE 요청의 경우 응답 엔티티 본문에는 상태 메시지가 담기거나 아무것도 담기지 않을 수 있다.

리소스를 생성하거나 수정하려면 클라이언트는 보통 엔티티 본문을 포함한 PUT 요청을 보낸다.
엔티티 본문에는 클라이언트가 제안하는 리소스의 새 표현이 담긴다.
이 데이터가 무엇이고 어떤 형식인지는 서비스에 달려 있다.
어떤 모습이든, 이 지점이 애플리케이션 상태가 서버로 옮겨져 리소스 상태가 되는 지점이다.

S3 서비스를 다시 생각해 보면 생성할 수 있는 리소스는 버킷과 객체 두 종류다.
객체를 생성하려면 그 URI로 PUT 요청을 보내며 요청의 엔티티 본문에 객체 내용을 넣는다.
객체를 수정할 때도 같은 일을 하며, 새 내용이 옛 내용을 덮어쓴다.

버킷 생성은 조금 다른데, PUT 요청에 엔티티 본문을 지정할 필요가 없기 때문이다.
버킷은 이름 외에는 리소스 상태가 없고, 그 이름은 URI의 일부다.
버킷의 URI를 지정하면 그 표현을 지정한 셈이다.
대부분의 리소스에 대한 PUT 요청은 표현을 담은 엔티티 본문을 포함하지만, 이처럼 그것이 필수는 아니다.

### HEAD와 OPTIONS

저자가 통일 인터페이스의 일부로 여기는 다른 세 HTTP 메서드가 있다.
그중 둘은 단순한 유틸리티 메서드다.

- 메타데이터만 담은 표현을 가져오기: HTTP HEAD
- 특정 리소스가 어떤 HTTP 메서드를 지원하는지 확인하기: HTTP OPTIONS

S3 클라이언트는 HEAD를 사용해, 어쩌면 거대할 엔티티 본문을 내려받지 않고도 리소스에 관한 메타데이터를 가져온다.
클라이언트는 HEAD로 리소스가 존재하는지 확인하거나 리소스에 관한 다른 정보를 알아낼 수 있으며, 그 전체 표현을 가져오지 않아도 된다.
HEAD는 GET 요청이 줄 것과 정확히 같은 것을 주되, 엔티티 본문만 뺀 것을 준다.

OPTIONS 메서드는 클라이언트가 리소스에 무엇을 하도록 허용되는지 알아내게 한다.
OPTIONS 요청에 대한 응답에는 HTTP Allow 헤더가 담기며, 이 헤더는 그 리소스가 지원하는 통일 인터페이스의 부분집합을 펼쳐 보인다.
예시 헤더는 다음과 같다.

```http
Allow: GET, HEAD
```

이 헤더는 클라이언트가 그 리소스에 GET 또는 HEAD 요청을 하면 서버가 합당하게 응답하리라 기대할 수 있지만, 그 리소스가 다른 HTTP 메서드는 지원하지 않음을 뜻한다.
사실상 그 리소스는 읽기 전용이다.

클라이언트가 요청에 담는 헤더가 서버가 응답으로 보내는 Allow 헤더에 영향을 줄 수 있다.
예컨대 OPTIONS 요청에 적절한 Authorization 헤더를 함께 보내면 특정 URI에 GET, HEAD, PUT, DELETE 요청을 할 수 있음을 알게 될 수 있지만, 같은 OPTIONS 요청에서 Authorization 헤더를 빼면 GET과 HEAD만 할 수 있음을 알게 될 수 있다.
OPTIONS 메서드는 클라이언트가 간단한 접근 제어 검사를 하게 해 준다.

이론상 서버는 OPTIONS 요청에 대해 추가 정보를 보낼 수 있고 클라이언트는 서버 능력에 관해 매우 구체적으로 묻는 OPTIONS 요청을 보낼 수 있다.
그러나 클라이언트가 OPTIONS 요청에서 무엇을 물을 수 있는지에 대한 표준이 없고, Allow 헤더를 빼면 서버가 응답으로 무엇을 보낼 수 있는지에 대한 표준도 없다.
대부분의 웹 서버와 프레임워크가 OPTIONS를 매우 빈약하게 지원한다.
지금까지 OPTIONS는 유망하지만 아무도 쓰지 않는 착상이다.

또한 저자는 이 책에서 다루지 않는 표준 HTTP 메서드로 TRACE와 CONNECT를 언급한다.
TRACE는 프록시를 디버깅하는 데, CONNECT는 다른 프로토콜을 HTTP 프록시로 전달하는 데 쓰인다.

### POST

POST는 HTTP 메서드 가운데 가장 오해받는 메서드다.
이 메서드에는 본질적으로 두 가지 목적이 있다. 하나는 REST의 제약에 들어맞고, 다른 하나는 REST를 벗어나 RPC 스타일의 요소를 끌어들인다.
HTTP 표준인 RFC 2616 9.5절은 POST가 다음 기능들을 아우르는 통일된 방법이 되도록 설계되었다고 말한다.

- 기존 리소스에 대한 주석 달기
- 게시판, 뉴스그룹, 메일링 리스트, 또는 그와 유사한 글 모음에 메시지 올리기
- 양식 제출 결과 같은 데이터 블록을 데이터 처리 프로세스에 제공하기
- 추가(append) 연산으로 데이터베이스를 확장하기

POST 메서드가 실제로 수행하는 기능은 서버가 결정하며 보통 Request-URI에 의존한다.
올려진 엔티티는 그 URI에 종속되는데, 이는 파일이 그것을 담은 디렉터리에, 뉴스 기사가 올려진 뉴스그룹에, 레코드가 데이터베이스에 종속되는 것과 같다.

#### 종속 리소스 생성하기

RESTful 설계에서 POST는 흔히 종속 리소스(subordinate resource), 곧 다른 “부모” 리소스와의 관계 속에 존재하는 리소스를 생성하는 데 쓰인다.
블로그 프로그램은 각 블로그를 리소스(`/weblogs/myweblog`)로, 개별 블로그 항목을 종속 리소스(`/weblogs/myweblog/entries/1`)로 드러낼 수 있다.
웹 연동 데이터베이스는 테이블을 리소스로, 개별 행을 그 종속 리소스로 드러낼 수 있다.
블로그 항목이나 데이터베이스 레코드를 생성하려면 부모, 곧 블로그나 데이터베이스 테이블에 POST 한다.
어떤 데이터를 어떤 형식으로 올리는지는 서비스에 달렸지만, PUT과 마찬가지로 이 지점이 애플리케이션 상태가 리소스 상태가 되는 지점이다.
저자는 이 용법의 POST를 “추가(append)”를 뜻하는 POST(a)라 부르며, 이 책에서 “POST”라 할 때는 거의 언제나 POST(a)를 뜻한다.

종속 리소스 생성에 PUT을 쓸 수는 없는가.
때로는 쓸 수 있다.
S3 객체는 종속 리소스로, 모든 S3 객체는 어떤 S3 버킷에 담긴다.
그러나 우리는 버킷에 POST 요청을 보내 S3 객체를 만들지 않고, 객체의 URI로 직접 PUT 요청을 보낸다.
PUT과 POST의 차이는 이렇다.
새 리소스가 어떤 URI를 가질지 클라이언트가 결정할 때는 PUT을 쓰고, 서버가 결정할 때는 POST를 쓴다.

S3 서비스는 클라이언트가 PUT으로 S3 객체를 만들기를 기대하는데, S3 객체의 URI가 그 이름과 버킷 이름으로 완전히 결정되기 때문이다.
객체를 만들 만큼 알고 있다면 그 URI가 무엇일지도 안다.

그러나 서버가 URI를 더 통제하는 애플리케이션, 예컨대 블로그 프로그램을 생각해 본다.
클라이언트는 블로그 항목을 만드는 데 필요한 정보를 다 모으고도 생성 후 그 항목이 어떤 URI를 가질지 모를 수 있다.
어쩌면 서버가 순서나 내부 데이터베이스 ID를 근거로 URI를 정할 수도 있는데, 최종 URI가 `/weblogs/myweblog/entries/1`이 될지 `/weblogs/myweblog/entries/1000`이 될지 클라이언트는 알 수 없다.
어쩌면 최종 URI가 게시 시각을 근거로 정해질 수도 있는데, 서버가 몇 시라고 여기는지 클라이언트는 알 수 없다.
클라이언트가 이런 것을 알 필요가 없어야 한다.

POST 메서드는 클라이언트가 정확한 URI를 몰라도 새 리소스를 만드는 방법이다.
대개 클라이언트는 “부모” 또는 “팩토리(factory)” 리소스의 URI만 알면 된다.
서버는 엔티티 본문에서 표현을 받아 그것으로 “부모” 리소스 “아래에” 새 리소스를 만든다(“아래”의 의미는 맥락에 달렸다).

이런 종류의 POST 요청에 대한 응답은 보통 HTTP 상태 코드 201(“Created”)을 가지며, 그 Location 헤더에 새로 만들어진 종속 리소스의 URI가 담긴다.
이제 리소스가 실제로 존재하고 클라이언트가 그 URI를 알므로, 이후 요청은 PUT으로 그 리소스를 수정하고, GET으로 표현을 가져오고, DELETE로 삭제할 수 있다.

저자는 같은 URI에 대한 PUT과 POST의 작용을 표로 보인다.
`/weblogs`에 PUT 하면(이미 존재하므로) 효과가 없고, POST 하면 새 블로그를 만든다.
`/weblogs/myweblog`에 새 리소스로 PUT 하면 이 블로그를 만들고, 기존 리소스로 PUT 하면 이 블로그의 설정을 수정하며, POST 하면 새 블로그 항목을 만든다.
`/weblogs/myweblog/entries/1`은 새 리소스로 PUT 하는 것은 해당 없고(그 URI를 어떻게 얻겠는가), 기존 리소스로 PUT 하면 이 항목을 편집하고, POST 하면 이 항목에 댓글을 단다.

#### 리소스 상태에 추가하기

리소스에 POST로 전달한 정보가 반드시 온전한 새 종속 리소스로 귀결되어야 하는 것은 아니다.
때때로 리소스에 데이터를 POST 하면, 그것을 새 리소스에 넣는 대신 그 리소스 자신의 상태 끝에 덧붙인다.

단일 리소스인 로그를 드러내는 이벤트 로깅 서비스를 생각해 본다.
그 URI가 `/log`라 하자. 로그를 얻으려면 `/log`에 GET 요청을 보낸다.
그렇다면 클라이언트는 어떻게 로그에 덧붙이는가.
`/log`에 PUT 요청을 보낼 수도 있지만, PUT에는 새 리소스를 만들거나 옛 설정을 새 설정으로 덮어쓴다는 함의가 있다.
클라이언트는 그 어느 것도 하지 않고, 그저 로그 끝에 정보를 덧붙일 뿐이다.

여기서는 POST가 들어맞으며, 그 의미는 각 로그 항목이 별개 리소스로 드러날 때와 같다.
두 경우 모두 POST의 의미는 클라이언트가 기존 리소스에 종속 정보를 더한다는 것이다.
다만 블로그와 블로그 항목의 경우에는 그 종속 정보가 새 리소스로 나타났고, 여기서는 부모의 표현에 새 데이터로 나타난다는 점만 다르다.

#### 오버로드된 POST: 그다지 통일적이지 않은 인터페이스

앞의 관점은 POST에 관한 HTTP 표준의 설명 대부분을 다룬다.
POST로 부모 리소스 아래에 리소스를 만들 수도 있고, 리소스의 현재 상태에 데이터를 덧붙일 수도 있다.
아직 설명하지 않은 한 가지 용법은 아마 가장 익숙한 것, 곧 거의 모든 웹 애플리케이션을 움직이는 것이다. 양식 제출 결과 같은 데이터 블록을 데이터 처리 프로세스에 제공하는 용법이다.

“데이터 처리 프로세스”란 무엇인가. 꽤 모호하게 들리고, 실제로 거의 무엇이든 데이터 처리 프로세스가 될 수 있다.
이 방식으로 POST를 쓰면 리소스가 XML-RPC 서버처럼 행동하는 작은 메시지 처리기로 변한다.
리소스는 POST 요청을 받아 요청을 살피고 무언가를 하기로 결정한 다음 클라이언트에게 어떤 데이터를 제공하기로 결정한다.

저자는 이 용법을 프로그래밍 언어의 연산자 오버로딩에 빗대어 오버로드된 POST(overloaded POST)라 부른다.
하나의 HTTP 메서드가 여러 개의 비HTTP 메서드를 뜻하는 데 쓰이므로 오버로드된 것이며, 연산자 오버로딩이 그렇듯 혼란스럽다.
POST가 무엇을 하는지 안다고 여겼는데 이제 알 수 없는 목적을 이루는 데 쓰이기 때문이다.
저자는 이를 “처리(process)”를 뜻하는 POST(p)라 부르기도 한다.

서비스가 오버로드된 POST를 드러내면 “서버는 왜 이것 대신 저것을 해야 하는가?”라는 물음이 다시 열린다.
모든 HTTP 요청은 메서드 정보를 담아야 하는데, 오버로드된 POST를 쓰면 그 정보가 HTTP 메서드에 들어갈 수 없다.
이때 POST 메서드는 서버에게 “진짜 메서드 정보는 HTTP 요청 안을 들여다보라”고 지시하는 것일 뿐이다.
진짜 정보는 URI, HTTP 헤더, 또는 엔티티 본문 어디에나 있을 수 있다.
어떻게 되든 RPC 스타일의 요소가 서비스에 스며든 것이다.

메서드 정보가 HTTP 메서드에서 발견되지 않으면 인터페이스는 더 이상 통일적이지 않다.
저자는 REST 지지자로서 이를 그리 좋아하지 않지만 때로는 피할 수 없다고 말한다.
거의 모든 시나리오를 HTTP의 통일 인터페이스로 드러낼 수 있지만, 여러 리소스에 걸친 복잡한 연산을 표현하는 가장 쉬운 방법이 RPC 스타일일 때도 있다.

POST를 종속 리소스 생성이나 리소스 표현에 추가하는 데만 쓰더라도 오버로드된 POST가 필요할 수 있다.
단일 리소스가 두 종류의 POST를 모두 지원한다면, 서버는 클라이언트가 종속 리소스를 만들려고 POST 하는지 기존 리소스 표현에 덧붙이려고 POST 하는지 어떻게 아는가.
HTTP 요청의 다른 어딘가에 추가 메서드 정보를 담아야 할 수 있다.

오버로드된 POST를 빈약한 리소스 설계를 덮는 데 써서는 안 된다.
리소스는 무엇이든 될 수 있음을 기억해야 한다.
서비스에 RPC 스타일을 끌어들이기보다, 통일 인터페이스가 적용되도록 리소스 설계를 재배치하는 것이 대개 가능하다.

### 안전성과 멱등성(Safety and Idempotence)

HTTP의 통일 인터페이스를 설계된 대로 드러내면 두 가지 유용한 속성을 거저 얻는다.
올바르게 사용하면 GET과 HEAD 요청은 안전(safe)하고, GET, HEAD, PUT, DELETE 요청은 멱등(idempotent)하다.

#### 안전성

GET 또는 HEAD 요청은 어떤 데이터를 읽는 요청이지, 서버 상태를 바꾸는 요청이 아니다.
클라이언트가 GET 또는 HEAD 요청을 열 번 해도 한 번 한 것과 같고, 한 번도 하지 않은 것과도 같다.
`http://www.google.com/search?q=jellyfish`를 GET 해도 해파리 리소스 디렉터리에 관해 아무것도 바꾸지 않고 그저 표현을 가져올 뿐이다.
클라이언트는 알 수 없는 URI에 GET 또는 HEAD 요청을 보내면서, 재앙 같은 일은 일어나지 않으리라 안심할 수 있어야 한다.

그렇다고 GET과 HEAD 요청에 부수 효과가 있을 수 없다는 뜻은 아니다.
어떤 리소스는 클라이언트가 GET 할 때마다 증가하는 조회수 카운터이고, 대부분의 웹 서버는 들어오는 모든 요청을 로그 파일에 기록한다.
이것들은 부수 효과이며, GET 요청에 대해 서버 상태와 심지어 리소스 상태까지 바뀐다.
그러나 클라이언트는 그 부수 효과를 요청하지 않았고 그에 책임이 없다.
클라이언트는 부수 효과만을 노리고 GET이나 HEAD 요청을 해서는 결코 안 되며, 그 부수 효과는 클라이언트가 요청을 하지 말걸 하고 후회할 만큼 커서도 안 된다.

#### 멱등성

멱등성은 조금 더 까다로운 개념이다.
이 개념은 수학에서 왔다.
수학에서 멱등 연산은 한 번 적용하든 여러 번 적용하든 같은 효과를 내는 연산이다.
어떤 수에 0을 곱하는 것은 멱등하다. 4×0×0×0은 4×0과 같다.
이에 빗대어, 리소스에 대한 연산이 멱등하다는 것은 한 번 요청하는 것이 동일한 요청을 연달아 하는 것과 같다는 뜻이다.
둘째 이후의 요청은 리소스 상태를 첫 요청이 남긴 것과 정확히 같은 상태로 둔다.

PUT과 DELETE 연산은 멱등하다.
리소스를 DELETE 하면 그것은 사라지고, 다시 DELETE 해도 여전히 사라진 채다.
PUT으로 새 리소스를 만든 뒤 같은 PUT 요청을 다시 보내도 리소스는 그대로 있고 만들 때 준 속성을 그대로 갖는다.
PUT으로 리소스 상태를 바꾼 뒤 PUT 요청을 다시 보내도 리소스 상태는 다시 바뀌지 않는다.

이로부터 실천적으로 얻는 결론은, 클라이언트가 리소스 상태를 상대적(relative)으로 바꾸는 표현을 PUT 하도록 허용해서는 안 된다는 것이다.
리소스가 리소스 상태의 일부로 어떤 수치를 유지한다면, 클라이언트가 PUT으로 그 값을 4나 0이나 -50으로 설정할 수는 있어도 값을 1 증가시키게 해서는 안 된다.
초깃값이 0일 때 “값을 4로 설정하라”는 PUT 요청을 두 번 보내면 값은 4에 머문다.
그러나 초깃값이 0일 때 “값을 1 증가시켜라”는 PUT 요청을 두 번 보내면 값은 1이 아니라 2가 된다.
그것은 멱등하지 않다.

또한 저자는 각주에서 곱셈을 예로 든다.
어떤 수에 1을 곱하는 것은 안전하면서 멱등하다. 4×1×1×1은 4×1과 같고 4와도 같다.
0을 곱하는 것은 안전하지 않은데 4×0은 4와 다르기 때문이며, 다만 (앞서 보았듯) 멱등하기는 하다.
그 밖의 어떤 수를 곱하는 것은 안전하지도 멱등하지도 않다.

#### 안전성과 멱등성이 중요한 이유

안전성과 멱등성은 클라이언트가 신뢰할 수 없는 네트워크에서 신뢰할 수 있는 HTTP 요청을 하게 해 준다.
GET 요청을 했는데 응답을 못 받으면 그냥 다시 하면 된다. 안전하기 때문이다. 앞선 요청이 전달되었더라도 서버에 실질적 효과가 없었다.
PUT 요청을 했는데 응답을 못 받으면 그냥 다시 하면 된다. 앞선 요청이 전달되었더라도 둘째 요청은 추가 효과가 없다.

POST는 안전하지도 멱등하지도 않다.
“팩토리” 리소스에 동일한 POST 요청을 두 번 하면 아마 같은 정보를 담은 종속 리소스가 두 개 만들어질 것이다.
오버로드된 POST에서는 무슨 일이 일어날지 아무것도 장담할 수 없다.

통일 인터페이스를 가장 흔히 오용하는 사례는 안전하지 않은 연산을 GET으로 드러내는 것이다.
del.icio.us와 Flickr API가 모두 이렇게 한다.
`https://api.del.icio.us/posts/delete`를 GET 하면 표현을 가져오는 것이 아니라 del.icio.us 데이터셋을 수정하는 것이다.

왜 이것이 나쁜가.
2005년 구글은 Web Accelerator라는 클라이언트 쪽 캐싱 도구를 내놓았다.
이 도구는 브라우저와 함께 돌며, 지금 보는 페이지에서 링크된 페이지들을 “미리 가져온다(pre-fetch)”.
그 링크 중 하나를 클릭하면 컴퓨터가 이미 가져왔기에 페이지가 더 빨리 뜬다.

Web Accelerator는 재앙이었다.
소프트웨어 자체의 문제가 아니라, 웹에 GET을 오용하는 애플리케이션이 가득했기 때문이다.
Web Accelerator는 GET 연산이 안전하다고 가정해, 사람이 표현을 보고 싶어 할 경우에 대비해 클라이언트가 미리 GET 해도 된다고 여겼다.
그러나 실제 URI에 GET 요청을 보내자 데이터셋이 바뀌었고, 사람들이 데이터를 잃었다.

책임은 양쪽에 있다.
프로그래머는 안전하지 않은 동작을 GET으로 드러내서는 안 되고, 구글은 실제 웹과 맞지 않는 도구를 내놓아서는 안 되었다.
현재 버전의 Web Accelerator는 쿼리 변수를 담은 URI를 모두 무시한다.
이는 문제의 일부를 풀지만, GET으로 써도 안전한 많은 리소스(구글 웹 검색 등)까지 미리 가져오지 못하게 막는다.

많은 웹 서비스와 웹 애플리케이션이 URI를 입력으로 받아, 먼저 GET 요청을 보내 리소스의 표현을 가져온다.
이 서비스들은 재앙적 부수 효과를 일으킬 뜻이 없지만, 그것은 그들에게 달린 일이 아니다.
GET 요청을 HTTP 표준에 맞게 처리하는 것은 서비스에 달린 일이다.

### 통일 인터페이스가 중요한 이유

REST에서 중요한 것은 HTTP가 정의하는 특정 통일 인터페이스를 쓴다는 점이 아니다.
REST는 통일 인터페이스를 명시하지만 어느 통일 인터페이스인지는 말하지 않는다.
GET, PUT 등은 영원히 완벽한 인터페이스가 아니다.
중요한 것은 통일성, 곧 모든 서비스가 HTTP의 인터페이스를 같은 방식으로 쓴다는 점이다.

요점은 GET이 읽기 연산의 최선의 이름이라는 것이 아니라, 어느 리소스에 쓰든 GET이 웹 전체에서 “읽기”를 뜻한다는 것이다.
리소스의 URI가 주어지면 표현을 어떻게 얻을지 물을 필요가 없다. 그 URI로 HTTP GET 요청을 보내면 된다.
통일 인터페이스는 임의의 두 서비스를 임의의 두 웹 사이트만큼 비슷하게 만든다.
통일 인터페이스가 없으면 각 서비스가 어떻게 정보를 주고받기를 기대하는지 일일이 배워야 하고, 그 규칙이 한 서비스 안의 리소스마다 다를 수도 있다.

GET이 무엇을 뜻하는지 컴퓨터에 이해시킬 수 있고, 그 이해는 모든 RESTful 웹 서비스에 적용된다.
서비스마다 다른 코드는 표현을 다루는 부분에 담기면 된다.
통일 인터페이스가 없으면 GET의 자리를 대신하는 doSearch, getPage, nextPrime 같은 메서드가 넘쳐 나고, 모든 서비스가 다른 언어를 말하게 된다.
저자가 오버로드된 POST를 그리 좋아하지 않는 것도 이 때문이다. 그것은 통일 인터페이스라는 단순한 에스페란토를 일회성 하위 언어들의 바벨탑으로 바꾼다.

어떤 애플리케이션은 HTTP의 통일 인터페이스를 확장한다.
가장 뚜렷한 사례는 WebDAV로, MOVE, COPY, SEARCH를 비롯해 여덟 개의 새 HTTP 메서드를 더한다.
웹 서비스에서 이 메서드를 쓰는 것은 REST의 어떤 원칙도 위반하지 않는다. REST는 통일 인터페이스가 어떤 모습이어야 하는지 말하지 않기 때문이다.
다만 그것은 저자의 ROA는 위반한다(저자는 ROA를 표준 HTTP 메서드에 명시적으로 묶었다). 그래도 그 서비스는 일반적 의미에서 리소스 지향적일 수 있다.

WebDAV 메서드를 쓰지 말아야 할 진짜 이유는, 그렇게 하면 서비스가 다른 RESTful 서비스와 호환되지 않기 때문이다.
그 서비스는 대다수 다른 서비스와 다른 통일 인터페이스를 쓰게 된다.
Subversion처럼 WebDAV 메서드를 쓰는 웹 서비스가 있어 완전히 혼자는 아니겠지만, 훨씬 작은 웹의 일부가 될 것이다.
그래서 자기만의 HTTP 메서드를 만드는 것은 매우 나쁜 착상이다. 맞춤 어휘는 당신을 한 명뿐인 공동체에 두며, 그럴 바에는 XML-RPC를 쓰는 편이 낫다.

또 다른 통일 인터페이스는 HTTP GET과 오버로드된 POST만으로 이루어진다.
리소스의 표현을 가져오려면 그 URI로 GET을 보내고, 리소스를 생성하거나 수정하거나 삭제하려면 POST를 보낸다.
이 인터페이스는 완벽히 RESTful하지만 역시 저자의 ROA에는 부합하지 않는다.
이 인터페이스는 안전한 연산과 안전하지 않은 연산을 구별할 만큼만 풍부하다.
리소스 지향 웹 애플리케이션은 오늘날 HTML 양식이 GET과 POST만 지원하기 때문에 이 인터페이스를 쓸 것이다.

## 그게 전부다(That's It!)

이것이 리소스 지향 아키텍처다.
네 가지 개념뿐이다.

1. 리소스(Resources)
2. 그 이름(URI)
3. 그 표현(Representations)
4. 그것들 사이의 링크(Links)

그리고 네 가지 속성뿐이다.

1. 주소 지정 가능성(Addressability)
2. 무상태성(Statelessness)
3. 연결성(Connectedness)
4. 통일 인터페이스(A uniform interface)

물론 아직 열린 물음이 많다.
실제 데이터셋을 어떻게 리소스로 나누고 리소스를 어떻게 배치해야 하는가.
실제 HTTP 요청과 응답에는 무엇이 들어가야 하는가.
저자는 책의 나머지 대부분을 이런 문제를 탐구하는 데 쓴다.

## 핵심 정리

- ROA는 REST를 웹 기술(HTTP, URI, XML)에 명시적으로 묶어 구체화한 아키텍처이며, REST 자체는 아키텍처가 아니라 설계 기준의 집합이다.
- ROA는 네 개념(리소스, URI, 표현, 링크)과 네 속성(주소 지정 가능성, 무상태성, 연결성, 통일 인터페이스)으로 이루어진다.
- 리소스는 그 자체로 참조될 만큼 중요한 모든 것이며, 리소스가 되려면 적어도 하나의 URI를 가져야 한다. URI는 서술적이고 예측 가능한 구조를 갖는 것이 좋다.
- 주소 지정 가능성은 흥미로운 정보 조각마다 URI를 부여해, 북마크, 링크, 캐싱, URI 연쇄를 가능하게 한다.
- 무상태성은 모든 요청이 완결적이어야 함을 뜻하며, 상태는 클라이언트가 가지는 애플리케이션 상태와 서버가 가지는 리소스 상태로 나뉜다. 애플리케이션 상태를 서버에 두면 세션 복제나 세션 어피니티 같은 확장성 대가가 따른다.
- 표현은 리소스 상태에 관한 데이터이며, 한 리소스가 여러 표현을 가질 때는 표현마다 URI를 부여하거나 콘텐츠 협상으로 고를 수 있다. 저자는 정보를 되도록 URI에 담기를 권한다.
- 연결성은 표현이 다른 리소스로의 링크를 담는 성질이며, 이것이 “애플리케이션 상태의 엔진으로서의 하이퍼미디어”의 실천이다.
- 통일 인터페이스에서 GET은 표현 조회, PUT은 (기존 URI에서) 수정 또는 (새 URI에서) 생성, POST는 (부모 URI에서) 종속 리소스 생성 또는 상태 추가, DELETE는 삭제, HEAD는 메타데이터만 조회, OPTIONS는 지원 메서드 확인에 쓰인다.
- GET과 HEAD는 안전하며(서버 상태를 바꾸지 않음), GET·HEAD·PUT·DELETE는 멱등하다(여러 번 요청해도 한 번과 결과가 같음). POST는 안전하지도 멱등하지도 않다. 그래서 상대적 변경(값 증가 등)을 PUT으로 노출해서는 안 되고, 안전하지 않은 연산을 GET으로 노출해서는 안 된다.
- 오버로드된 POST(POST(p))는 메서드 정보를 HTTP 메서드 밖에 두어 인터페이스의 통일성을 깨는 RPC 스타일이며, 빈약한 리소스 설계를 덮는 데 쓰지 말아야 한다.
