# 1장 프로그래머블 웹과 그 거주자들

《RESTful Web Services》(Leonard Richardson, Sam Ruby, O'Reilly 2007) 1장 정리.

## 개요

이 장은 “프로그래머블 웹(programmable web)”이 무엇인지 조망하고, 그 위에서 살아가는 다양한 웹 서비스들을 어떻게 분류할 것인가를 다룬다.
저자의 핵심 주장은 웹 서비스를 겉모습(사용하는 기술)이 아니라 밑바탕의 아키텍처와 설계 철학으로 분류해야 한다는 것이다.
사람이 쓰는 웹(human web)에서 브라우저가 HTTP 요청을 보내고 HTML 응답을 화면에 그리듯이, 프로그래머블 웹에서는 소프트웨어가 HTTP 요청을 보내고 대개 XML 문서로 된 응답을 받아 그 의미를 스스로 해석하고 판단한다.

저자는 모든 웹 서비스가 공유하는 공통 기반인 HTTP를 “봉투 속 문서”라는 은유로 설명한 뒤, 웹 서비스들이 서로 달라지는 두 가지 큰 질문을 제시한다.
하나는 클라이언트가 무엇을 하려는지를 어떻게 전달하는가(메서드 정보), 다른 하나는 데이터 집합의 어느 부분을 대상으로 하는가(스코핑 정보)이다.
이 두 질문에 대한 답의 조합으로 저자는 웹 서비스를 세 가지 아키텍처로 나눈다.
RESTful 리소스 지향(resource-oriented), RPC 스타일, 그리고 그 사이에 놓인 REST-RPC 하이브리드이다.
마지막으로 이 아키텍처들을 구현하는 데 쓰이는 기술들(HTTP, URI, XML-RPC, SOAP, WS-*, WSDL, WADL)과, 논의에 자주 등장하지만 저자가 부정확하다고 보는 잔여 용어들을 정리한다.

## 프로그래머블 웹 위에 있는 것들

프로그래머블 웹은 사람이 쓰는 웹과 본질적으로 같은 방식으로 작동한다.
사람이 책을 찾으려고 브라우저로 온라인 서점의 URI(예: `http://www.amazon.com/`)에 접속하면, 서버는 HTML 문서를 돌려주고 브라우저가 이를 그래픽으로 렌더링한다.
검색어를 입력하고 폼을 제출하면 브라우저는 검색어를 포함한 두 번째 URI로 다시 HTTP 요청을 보내고, 서버는 검색 결과가 담긴 또 다른 HTML 문서로 응답한다.

프로그래머블 웹도 마찬가지지만, 데이터를 사람 눈에 예쁜 HTML 페이지 대신 대체로 건조하고 투박한 XML 문서로 제공한다는 점이 다르다.
이 데이터는 사람이 읽으라고 있는 것이 아니라, 무언가 유용한 일을 하는 소프트웨어 프로그램의 입력으로 쓰이도록 의도된 것이다.

책의 예제(Example 1-2)는 Ruby/Amazon 라이브러리를 이용해 키워드에 맞는 책 제목을 찾는 Ruby 스크립트를 보여준다.
이 스크립트가 `keyword_search` 메서드를 호출하면 프로그램은 웹 브라우저처럼 행동한다.
`http://xml.amazon.com/onca/xml3?KeywordSearch=restful+web+services&mode=books&f=xml&type=lite&page=1` 같은 URI로 HTTP 요청을 보내고, 서버는 검색 결과를 기술한 XML 문서로 응답한다.

여기서 사람이 쓰는 웹과의 결정적 차이가 드러난다.
브라우저는 응답을 사람이 이해할 수 있게 렌더링하기만 하면 되고, 응답의 의미를 알아내는 일은 사람의 몫이다.
반면 웹 서비스 클라이언트에게는 그런 여유가 없다.
클라이언트는 미리 프로그래밍되어 있으므로 데이터를 가져오는 브라우저 역할과, 그 데이터가 무엇을 뜻하는지 판단하는 “사람” 역할을 동시에 해야 한다.
즉 웹 서비스 클라이언트는 HTTP 응답에서 자동으로 의미를 추출하고 그 의미에 근거해 결정을 내려야 한다.

데이터가 늘 클라이언트 쪽으로만 흐르는 것도 아니다.
사람이 블로그에 글을 올리거나 책을 사면서 웹에 영향을 주듯, 프로그래머블 웹을 수정하는 클라이언트도 작성할 수 있다.
책은 그 예로 Amazon S3(Simple Storage Service)를 다루는 대화형 셸 s3sh(Example 1-4)를 든다.
S3는 라벨이 붙은 데이터 조각(“객체”, object)을 라벨이 붙은 컨테이너(“버킷”, bucket)에 저장하게 해 주는 서비스이며, s3sh는 그 위에 대화형 프로그래밍 인터페이스를 얹는다.

## HTTP: 봉투 속 문서

프로그래머블 웹은 HTTP와 XML에 기반한다.
일부는 HTML, JSON(JavaScript Object Notation), 평문, 이진 문서를 제공하지만 대부분은 XML을 쓴다.
그리고 전부 HTTP 위에서 돌아간다.
저자는 “HTTP를 쓰지 않으면 웹 위에 있는 것이 아니다”라고 단언한다.

바다 생물을 겉모습으로 분류하던 옛 방식(고래를 물고기로 묶는)과, 진화적 계통으로 분류하는 현대 방식(고래를 포유류로 묶는)의 비유가 이 장의 뼈대다.
겉모습에 따른 분류는 대개 통하지만, 왜 고래가 물속에서 숨 쉴 수 없는지를 이해하려면 겉모습이 아니라 밑바탕 구조로 분류해야 한다.
오늘날 웹 서비스 용어 대부분은 서비스가 쓰는 기술이라는 겉모습으로 분류하는데, 이는 “고래를 물고기로 착각하는” 오류를 낳는다.
그래서 저자는 기술 선택이 밑바탕 설계 원리에서 비롯됨을 보여주는, 아키텍처 기반 분류를 제시한다.

### 봉투 은유

HTTP는 문서 기반 프로토콜이다.
클라이언트가 문서를 봉투에 넣어 서버에 보내면, 서버도 응답 문서를 봉투에 넣어 클라이언트에게 돌려준다.
HTTP는 봉투가 어떻게 생겨야 하는지에 대해서는 엄격한 표준을 두지만, 봉투 안에 무엇이 들어가는지는 별로 상관하지 않는다.

### HTTP 요청의 구성 요소

책은 `http://www.oreilly.com/index.html`에 대한 GET 요청(Example 1-5)을 예로 들어 요청의 주요 부분을 설명한다.

HTTP 메서드(HTTP method).
이 요청에서 메서드는 “GET”이다.
다른 REST 논의에서는 이를 “HTTP 동사(verb)”나 “HTTP 액션(action)”이라 부르기도 한다.
메서드 이름은 프로그래밍 언어의 메서드 이름과 비슷해서, 클라이언트가 서버에게 이 봉투를 어떻게 처리하기를 기대하는지 나타낸다.

경로(path).
호스트명 오른쪽에 오는 URI의 일부로, 위 예에서는 `/index.html`이다.
봉투 은유에서 경로는 봉투에 적힌 주소에 해당한다.
저자는 때때로 경로만을 가리키는 축약어로 “URI”를 쓴다.

요청 헤더(request headers).
봉투에 붙인 정보용 스티커처럼 작동하는 키-값 쌍 형태의 메타데이터다.
이 예제 요청에는 Host, User-Agent, Accept 등 여덟 개의 헤더가 있다.
표준 HTTP 헤더 목록이 있고, 애플리케이션이 자체 헤더를 정의할 수도 있다.

엔티티 바디(entity-body, 문서 또는 표현(representation)이라고도 함).
봉투 안에 든 문서다.
이 GET 요청에는 엔티티 바디가 없어서 봉투가 비어 있는데, 이는 GET 요청에서 흔한 일이다.
요청을 완수하는 데 필요한 정보가 모두 경로와 헤더에 담기기 때문이다.

### HTTP 응답의 구성 요소

HTTP 응답도 봉투 속 문서이며 형태가 요청과 거의 같다(Example 1-6).
응답은 세 부분으로 나뉜다.

**HTTP 응답 코드(response code)**.
요청이 잘되었는지 아닌지, 클라이언트가 이 봉투와 내용물을 어떻게 봐야 하는지를 알려주는 숫자 코드다.
예제에서는 GET이 성공했으므로 응답 코드가 200(“OK”)이다.

**응답 헤더(response headers)**.
요청 헤더와 마찬가지로 봉투에 붙은 정보용 스티커다.
예제 응답에는 Date, Server 등 11개의 헤더가 있다.

**엔티티 바디(entity-body) 또는 표현(representation)**.
봉투 안의 문서이며, 이번에는 실제로 들어 있다.
엔티티 바디는 GET 요청의 결실이고, 응답의 나머지는 브라우저에게 이 문서를 어떻게 다룰지 알려주는 스티커 붙은 봉투일 뿐이다.

이 스티커 중 가장 중요한 것이 Content-Type 헤더로, 엔티티 바디의 미디어 타입(media type)을 알려준다.
예제에서 미디어 타입은 `text/html`이며, 이 덕분에 브라우저는 엔티티 바디를 HTML 문서, 즉 웹 페이지로 렌더링할 수 있음을 안다.
표준 미디어 타입 목록이 있으며, 가장 흔한 것은 텍스트 문서(`text/html`), 구조화된 데이터 문서(`application/xml`), 이미지(`image/jpeg`)를 가리킨다.
다른 논의에서는 이를 “MIME 타입”, “content type”, “data type”이라 부르기도 한다.

## 메서드 정보

HTTP는 프로그래머블 웹의 모든 “동물”이 공유하는 공통점이다.
웹 서비스들이 서로 달라지는 첫 번째 큰 질문은 클라이언트가 자신의 의도를 서버에 어떻게 전달하는가이다.
어떤 요청이 데이터를 가져오려는 것인지, 아니면 같은 데이터를 삭제하거나 다른 데이터로 덮어쓰려는 것인지를 서버는 어떻게 아는가.

저자는 이 “데이터로 무엇을 할지”에 관한 정보를 메서드 정보(method information)라고 부른다.
이를 전달하는 한 방법은 HTTP 메서드 자체에 넣는 것이다.
RESTful 웹 서비스가 바로 이 방식을 쓴다.
가장 흔한 다섯 가지 HTTP 메서드는 GET, HEAD, PUT, DELETE, POST이며, 이것만으로도 “데이터를 가져오라”(GET), “그 데이터를 삭제하라”(DELETE), “다른 데이터로 덮어써라”(PUT)를 구분할 수 있다.

HTTP 메서드 이름의 큰 장점은 표준화되어 있다는 점이다.
다만 HTTP 메서드 이름의 공간은 프로그래밍 언어의 메서드 이름 공간보다 훨씬 제한적이다.
그래서 어떤 웹 서비스들은 애플리케이션 고유의 메서드 이름을 HTTP 요청의 다른 곳(대개 URI 경로나 요청 문서)에서 찾는다.

### 경로에 메서드 정보를 넣는 방식: Flickr

Flickr(야후!의 사진 공유 서비스) API 클라이언트(Example 1-7)는 메서드 정보를 경로에 두는 예다.
이 클라이언트는 `http://www.flickr.com/services/rest?method=flickr.photos.search&api_key=xxx&tags=penguins` 같은 URI로 요청한다.
메서드 이름이 `flickr.photos.search`임은 꽤 분명하다.

처음에는 HTTP 메서드가 GET이고 실제로 정보를 가져오고 있으니, 진짜 메서드 정보는 HTTP 액션에 있는 것 아닐까 하는 가설이 생긴다.
그러나 이 가설은 오래가지 못한다.
Flickr API는 `flickr.photos.search`나 `flickr.people.findByEmail` 같은 “get” 계열뿐 아니라 `flickr.photos.addTags`, `flickr.photos.comments.deleteComment` 같은 메서드도 지원하는데, 데이터를 “가져오는지” 여부와 무관하게 이 모두가 HTTP GET 요청으로 호출된다.
결국 Flickr는 메서드 정보를 `method` 쿼리 변수에 넣고, 클라이언트가 HTTP 메서드는 무시하도록 기대하고 있음이 분명하다.

### 엔티티 바디와 헤더에 넣는 방식: SOAP

전형적인 SOAP 서비스는 메서드 정보를 엔티티 바디와 HTTP 헤더에 둔다.
책은 Google의 SOAP 기반 검색 API를 쓰는 Ruby 스크립트(Example 1-8)를 예로 든다.
(집필 당시 Google은 이 SOAP 검색 서비스를 RESTful 리소스 지향 서비스로 대체하며 단계적으로 폐지한다고 발표했으나, 저자는 SOAP를 설명하는 가장 좋은 예이므로 그대로 두었다고 각주로 밝힌다.)

WSDL 라이브러리가 세부를 감추지만 내부에서 일어나는 일은 이렇다.
`doGoogleSearch` 메서드를 호출하면 WSDL 라이브러리는 Google SOAP 서비스의 “엔드포인트(endpoint)”인 `http://api.google.com/search/beta2`로 POST 요청을 보낸다.
이 단 하나의 URI가 모든 API 호출의 목적지이며, 오직 POST 요청만 보내진다.
`doGoogleSearch`의 정의 같은 세부는 `http://api.google.com/GoogleSearch.wsdl`의 WSDL 파일에 담겨 있다.

URI와 HTTP 메서드가 결코 바뀌지 않으므로, 메서드 정보인 “doGoogleSearch”는 그 어느 쪽에도 들어갈 수 없다.
대신 그것은 POST 요청의 엔티티 바디로 들어간다(Example 1-10).
메서드 정보 “doGoogleSearch”는 SOAP Envelope 안 XML 태그의 이름이자, WSDL 파일 내 operation의 이름이며, Ruby 메서드의 이름이기도 하다.
또한 SOAPAction HTTP 요청 헤더의 값에서도 발견되는데, 일부 SOAP 구현은 엔티티 바디 대신 여기서 메서드 정보를 찾는다.

이야기를 한 바퀴 돌려, Google SOAP 검색 API가 아니라 Google 검색 엔진 자체를 보자.
브라우저로 REST를 검색하려면 `http://www.google.com/search?q=REST`로 GET 요청을 보내 HTML 응답을 받는다.
여기서 메서드 정보는 HTTP 메서드에 담긴다.
검색 결과 목록을 GET 하고 있는 것이다.

## 스코핑 정보

웹 서비스들이 달라지는 두 번째 큰 질문은, 클라이언트가 데이터 집합의 어느 부분을 대상으로 삼는지를 서버에 어떻게 알리는가이다.
서버가 클라이언트가 무언가를 삭제하려 한다는 것을 이해했다 해도, 어느 데이터를 삭제하려는지 어떻게 아는가.

저자는 이 정보를 스코핑 정보(scoping information)라고 부른다.
가장 뻔한 위치는 URI 경로이며, 대부분의 웹 사이트가 그렇게 한다.
`http://www.google.com/search?q=REST`에서 메서드 정보는 “GET”이고 스코핑 정보는 `/search?q=REST`이다.
클라이언트는 다른 것(예: jellyfish 검색 결과라면 `/search?q=jellyfish`, Google 홈페이지라면 `/`)이 아니라 REST에 관한 검색 결과 목록을 GET 하려는 것이다.

많은 웹 서비스가 스코핑 정보를 경로에 넣는다.
Flickr도 그중 하나로, API URI의 쿼리 변수 대부분이 스코핑 정보다.
`tags=penguin`은 `flickr.photos.search` 메서드의 범위를 “penguin” 태그가 붙은 사진만 검색하도록 좁힌다.
메서드 정보가 프로그래밍 언어적 의미의 메서드를 정의하는 서비스에서는, 스코핑 정보를 그 메서드의 인자 집합으로 볼 수 있다.
어떤 언어에서 `flickr.photos.search(tags=penguin)` 같은 코드 한 줄을 볼 법도 하다.

대안은 스코핑 정보를 엔티티 바디에 넣는 것이다.
전형적인 SOAP 웹 서비스가 이렇게 한다.
Example 1-10에는 내용이 문자열 “REST”인 `q` 태그가 있는데, 이것이 스코핑 정보이며 메서드 정보를 제공하는 `doGoogleSearch` 태그 안에 편안히 자리 잡고 있다.

무엇이 메서드 정보이고 무엇이 스코핑 정보인지는 서비스 설계가 결정한다.
이는 웹 사이트와 웹 서비스가 같은 일을 하지만 설계가 다른 Flickr, Google 같은 사례에서 가장 잘 드러난다.
다음 두 URI는 같은 정보를 담고 있다.

- `http://flickr.com/photos/tags/penguin`
- `http://api.flickr.com/services/rest/?method=flickr.photos.search&tags=penguin`

첫 번째 URI에서 메서드 정보는 “GET”, 스코핑 정보는 “'penguin' 태그가 붙은 사진들”이다.
두 번째 URI에서 메서드 정보는 “사진 검색을 하라”, 스코핑 정보는 “penguin”이다.
기술적으로는 둘 다 HTTP GET을 쓰므로 차이가 없다.
차이는 아키텍처 수준에서, 한 걸음 물러나 `flickr.photos.delete`처럼 HTTP GET을 본래 의도되지 않은 곳으로 끌고 가는 methodname 값을 볼 때 비로소 드러난다.

## 경쟁하는 아키텍처

웹 서비스가 서로 다르게 답하는 두 질문을 확인했으니, 이제 그 답에 따라 서비스를 묶을 수 있다.
저자는 세 가지 흔한 웹 서비스 아키텍처를 식별한다.
RESTful 리소스 지향(resource-oriented), RPC 스타일, REST-RPC 하이브리드이다.

### RESTful 리소스 지향 아키텍처

이 책의 주제는 RESTful하다고 볼 수 있는 웹 서비스 아키텍처, 즉 Roy Fielding의 학위 논문이 제시한 기준으로 판단했을 때 좋은 점수를 받는 것들이다.
기술적으로 RESTful한 아키텍처는 많지만, 저자는 그중 웹 서비스에 가장 적합한 것에 집중한다.
그래서 저자가 말하는 RESTful 웹 서비스는 “웹처럼 생긴” 서비스이며, 이를 리소스 지향(resource-oriented)이라 부른다.

RESTful 아키텍처에서는 메서드 정보가 HTTP 메서드로 들어간다.
리소스 지향 아키텍처에서는 스코핑 정보가 URI로 들어간다.
이 조합은 강력하다.
리소스 지향 RESTful 웹 서비스에 대한 HTTP 요청의 첫 줄(`GET /reports/open-bugs HTTP/1.1`)만 봐도 클라이언트가 무엇을 하려는지 기본적으로 알 수 있다.
나머지는 세부일 뿐이며, 실제로 HTTP 한 줄만으로 많은 요청을 보낼 수 있다.

저자는 두 가지 경험 법칙을 제시한다.
HTTP 메서드가 메서드 정보와 일치하지 않으면 그 서비스는 RESTful하지 않다.
스코핑 정보가 URI에 없으면 그 서비스는 리소스 지향이 아니다.
이것이 유일한 요건은 아니지만 좋은 기준이 된다.

RESTful 리소스 지향 웹 서비스의 잘 알려진 예로는 다음이 있다.

- Atom Publishing Protocol과 그 변종(GData 등)을 노출하는 서비스
- Amazon의 Simple Storage Service(S3)
- 야후!의 웹 서비스 대부분
- SOAP를 쓰지 않는 대부분의 읽기 전용 웹 서비스
- 정적 웹 사이트
- 많은 웹 애플리케이션, 특히 검색 엔진처럼 읽기 전용인 것들

저자는 각주에서, 놀랍게도 Google SOAP 웹 검색 API를 비롯한 많은 읽기 전용 SOAP·XML-RPC 서비스가 기술적으로는 RESTful 아키텍처를 갖는다고 지적한다.
그러나 이들은 웹과 전혀 닮지 않았으므로 웹 서비스로서는 나쁜 아키텍처라고 본다.

### RPC 스타일 아키텍처

RPC 스타일 웹 서비스는 클라이언트로부터 데이터가 가득 든 봉투를 받아, 비슷한 봉투를 되돌려 보낸다.
메서드 정보와 스코핑 정보는 봉투 안에 담기거나 봉투에 붙인 스티커에 담긴다.
어떤 종류의 봉투인지는 분류에 중요하지 않다.
HTTP가 인기 있는 봉투 형식인 것은 웹 서비스라면 어차피 HTTP를 써야 하기 때문이고, SOAP도 또 하나의 인기 봉투 형식이다(SOAP 문서를 HTTP로 전송하면 SOAP 봉투가 HTTP 봉투 안에 들어간다).

모든 RPC 스타일 서비스는 완전히 새로운 어휘(vocabulary)를 정의한다.
프로그램을 작성할 때마다 서로 다른 이름의 함수를 정의하는 것과 같다.
반면 모든 RESTful 웹 서비스는 표준화된 HTTP 메서드 어휘를 공유하며, RESTful 서비스의 모든 객체는 동일한 기본 인터페이스에 응답한다.

XML-RPC 프로토콜이 RPC 아키텍처의 가장 뚜렷한 예다.
책은 UPC(Universal Product Code)로 제품을 조회하는 XML-RPC 서비스의 Ruby 클라이언트(Example 1-11)를 든다.
XML-RPC 서비스는 C 같은 프로그래밍 언어를 본뜬다.
함수(`lookupUPC`)를 인자(“001441000055”)와 함께 호출하고 반환값을 돌려받는다.
메서드 데이터(함수 이름)와 스코핑 데이터(인자)는 XML 문서 안에 들어간다(Example 1-12).

이 XML 문서는 서버로 전송하기 위해 봉투에 담긴다.
봉투는 메서드, URI, 헤더를 갖춘 HTTP 요청이며, XML 문서는 그 봉투 안의 엔티티 바디가 된다(Example 1-13).
어떤 메서드를 호출하느냐에 따라 XML 문서는 달라지지만 HTTP 봉투는 항상 같다.
UPC 데이터베이스 서비스로 무엇을 하든 URI는 늘 `http://www.upcdatabase.com/rpc`이고 HTTP 메서드는 늘 POST다.
요컨대 XML-RPC 서비스는 HTTP의 기능 대부분을 무시한다.
단 하나의 URI(“엔드포인트”)만 노출하고, 그 URI에서 단 하나의 메서드(POST)만 지원한다.

RESTful 서비스가 스코핑 정보 값마다 다른 URI를 노출하는 반면, RPC 스타일 서비스는 대개 “문서 처리기(document processor)”마다 하나의 URI를 노출한다.
문서 처리기란 봉투를 열어 소프트웨어 명령으로 변환할 수 있는 무언가다.
만약 UPC 데이터베이스가 RESTful 웹 서비스였다면 코드가 어떻게 보일지를 보여주는 가상 예제(Example 1-14)에서는, 메서드 정보가 HTTP 메서드에 담긴다.
기본 HTTP 메서드는 GET이며 이 시나리오에서 `lookupUPC`와 동등하다.
스코핑 정보는 URI에 담기고, 이 가상 서비스는 가능한 모든 UPC마다 하나씩 엄청난 수의 URI를 노출하며, HTTP 봉투는 비어 있다.

HTTP POST를 많이 또는 전적으로 쓰는 서비스는 아마 RPC 스타일 서비스다.
확실한 신호는 아니지만, 메서드 정보를 HTTP 메서드에 넣는 데 별 관심이 없다는 단서다.
그 밖에는 RESTful하지만 POST를 많이 쓰는 서비스는 REST-RPC 하이브리드 쪽으로 기우는 경향이 있다.

RPC 스타일 웹 서비스의 잘 알려진 예는 다음과 같다.

- XML-RPC를 쓰는 모든 서비스
- 사실상 거의 모든 SOAP 서비스
- 몇몇 웹 애플리케이션(대체로 설계가 나쁜 것들)

### REST-RPC 하이브리드 아키텍처

이 용어는 RESTful 웹 서비스와 순수 RPC 스타일 서비스 사이 어딘가에 놓이는 서비스를 가리키려고 저자가 만든 말이다.
이런 서비스는 실제 웹 애플리케이션에 대해서는 많이 알지만 REST 이론은 잘 모르는 프로그래머들이 흔히 만든다.

Flickr가 쓰는 URI `http://www.flickr.com/services/rest?api_key=xxx&method=flickr.photos.search&tags=penguin`을 다시 보자.
URI에 “rest”가 들어 있음에도, 이는 HTTP를 봉투 형식으로 쓰는 RPC 스타일 서비스로 설계된 것이 분명하다.
스코핑 정보(“'penguin' 태그가 붙은 사진”)를 URI에 두는 것은 RESTful 리소스 지향 서비스와 같지만, 메서드 정보(“사진을 검색하라”)도 URI에 넣는다.
RESTful 서비스라면 메서드 정보는 HTTP 메서드(GET)로 가고 남은 것이 스코핑 정보가 되었을 것이다.

그런데 이 서비스가 만드는 실제 HTTP 요청(Example 1-15)을 보면, 이제 메서드 정보가 HTTP 메서드에 있는 것처럼 보인다.
GET 요청을 보내 무언가를 get 하고 있고, 그 무언가는 “penguin” 태그가 붙은 사진 검색 결과 목록이다.
메서드 정보였던 것(`photoSearch()`)이 이제는 스코핑 정보(`photos/tag/penguin`)처럼 보인다.
이 착시(optical illusion)는 RPC 스타일 서비스가 평범한 HTTP를 봉투 형식으로 쓰고, 메서드 정보와 스코핑 정보가 마침 둘 다 URI 부분에 살게 될 때 일어난다.
HTTP 메서드가 GET이고 요청의 목적도 정보를 “get” 하는 것이면, 메서드 정보가 HTTP 메서드에 있는지 URI에 있는지 구분하기 어렵다.

이 때문에 많은 읽기 전용 웹 서비스가 RPC 스타일로 설계되었음에도 온전히 RESTful하고 리소스 지향적인 것으로 통한다.
그러나 서비스가 클라이언트에게 데이터 집합에 쓰기를 허용하는 순간, 클라이언트가 실제 메서드 정보와 맞지 않는 HTTP 메서드를 쓰는 때가 생긴다.
바로 이 지점이 서비스가 될 수 있는 만큼 RESTful해지는 것을 막으며, 이런 서비스를 저자는 REST-RPC 하이브리드로 본다.

Flickr가 그 예다.
Flickr 웹 API는 데이터 집합을 수정할 때조차 클라이언트에게 HTTP GET을 쓰라고 요구한다.
사진을 삭제하려면 `method=flickr.photos.delete`가 포함된 URI로 GET 요청을 보내는데, 이는 GET의 용도가 아니다.
따라서 Flickr 웹 API는 GET으로 데이터를 조회할 때는 RESTful하고, 데이터를 수정할 때는 RPC 스타일인 REST-RPC 하이브리드다.

REST-RPC 하이브리드 서비스의 잘 알려진 예는 다음과 같다.

- del.icio.us API
- “REST” Flickr 웹 API
- RESTful하다고 주장되는 많은 다른 웹 서비스
- 대부분의 웹 애플리케이션

설계 관점에서 아무도 처음부터 REST-RPC 하이브리드를 의도해 만들지는 않는다고 저자는 본다.
HTTP의 작동 방식 때문에, 평범한 HTTP를 쓰면서 여러 URI를 노출하는 RPC 스타일 서비스는 결국 RESTful하거나 하이브리드가 되는 경향이 있다.
많은 프로그래머가 웹 서비스를 웹 애플리케이션처럼 설계하다가 하이브리드 서비스에 이른다.

하이브리드 아키텍처의 존재는 많은 혼란을 낳았다.
이 스타일은 웹 애플리케이션을 설계해 본 사람에게 자연스럽고, 사람이 쓰는 웹과 “같은 방식으로” 작동하니 RESTful하다는 주장도 흔하다.
저자의 REST-RPC 하이브리드라는 분류는 이런 서비스를 설명하려는 오랜 신조어 계보의 최신판이며, 집필 당시 가장 인기 있던 다른 표현은 “HTTP+POX”였다.

### 사람의 웹은 프로그래머블 웹 위에 있다

저자는 앞에서 모든 정적 웹 사이트는 RESTful하고, 웹 애플리케이션은 세 범주 중 하나에 속하며 다수가 REST-RPC 하이브리드라고 주장했다.
사람이 쓰는 웹은 전부 정적 웹 사이트와 웹 애플리케이션으로 이루어져 있으므로, 사람의 웹 전체도 프로그래머블 웹 위에 있는 셈이다.
웹 브라우저는 HTTP 요청을 보내고 응답을 어떤 식으로든(사람에게 보여주며) 처리하는 소프트웨어이며, 이는 정확히 웹 서비스 클라이언트가 하는 일이다.
웹 위에 있다면 그것은 웹 서비스다.

저자는 이 책의 목표가 프로그래머블 웹을 더 크게 만드는 것이 아니라고 밝힌다.
프로그래머블 웹은 이미 HTTP 인터페이스를 가진 거의 모든 것을 포괄하므로 더 키우는 것은 사실상 불가능하다.
목표는 더 낫게, 즉 더 균일하고 더 잘 구조화되며 HTTP의 기능을 최대로 활용하도록 만드는 것이다.

## 프로그래머블 웹의 기술들

아키텍처로 서비스를 분류해 물고기와 고래를 구분했으니, 이제 기술과 아키텍처를 혼동하지 않고 서비스들이 쓰는 기술을 살펴볼 수 있다.

### HTTP

모든 웹 서비스가 HTTP를 쓰지만 쓰는 방식이 다르다.
RESTful 웹 서비스는 메서드 정보를 HTTP 메서드에, 스코핑 정보를 URI에 넣는다.
RPC 스타일 웹 서비스는 HTTP 메서드를 무시하는 경향이 있고, 메서드·스코핑 정보를 URI, HTTP 헤더, 엔티티 바디에서 찾는다.
어떤 RPC 스타일 서비스는 HTTP를 문서를 담는 봉투로 쓰고, 다른 서비스는 또 다른 봉투를 담는 라벨 없는 봉투로만 쓴다.

### URI

역시 모든 웹 서비스가 URI를 쓰지만 방식이 다르다.
RESTful 리소스 지향 서비스는 클라이언트가 다룰 만한 데이터 조각마다 하나의 URI를 노출한다.
REST-RPC 하이브리드는 클라이언트가 수행할 만한 연산마다 하나의 URI를 노출한다.
데이터를 가져오는 URI와 그 데이터를 삭제하는 URI가 서로 다르다.
RPC 스타일 서비스는 원격 프로시저 호출(RPC)을 처리할 수 있는 프로세스마다 하나의 URI를 노출하는데, 대개 그런 URI는 하나뿐이며 그것이 서비스 “엔드포인트”다.

### XML-RPC

주로 레거시인 소수의 웹 서비스가 HTTP 위에서 XML-RPC를 쓴다.
XML-RPC는 함수 호출과 그 반환값을 표현하는 데이터 구조 형식이다.
이름이 말해주듯 명시적으로 RPC 스타일을 쓰도록 설계되었다.

### SOAP

많은 웹 서비스가 HTTP 위에서 SOAP를 쓴다.
SOAP는 HTTP처럼 봉투 형식이지만 XML 기반 봉투 형식이다.

저자는 여기서 논쟁적인 주장을 편다.
근사적으로 말해, SOAP를 쓰는 현재의 모든 웹 서비스는 RPC 아키텍처를 갖는다는 것이다.
이는 많은 SOAP 프로그래머가 RPC 아키텍처를 촌스럽게 여기며 자기 서비스를 “메시지 지향(message-oriented)”이나 “문서 지향(document-oriented)”이라 부르기를 선호하기에 논쟁적이다.

그러나 HTTP 자체가 메시지 지향이므로 모든 웹 서비스가 메시지 지향이다.
HTTP 요청은 문서가 든 봉투, 즉 메시지일 뿐이다.
관건은 그 문서가 무엇을 말하느냐다.
SOAP 기반 서비스는 클라이언트에게 HTTP 봉투 안에 두 번째 봉투(SOAP 문서)를 넣으라고 요구한다.
SOAP 봉투는 어떤 XML 데이터든 담을 수 있지만, 현존하는 모든 SOAP 서비스에서 SOAP 봉투는 XML-RPC와 유사한 형식으로 RPC 호출을 기술하는 내용을 담는다.

이 RPC 기술을 이리저리 옮기고 “document/literal”이나 “wrapped/literal” 같은 다른 라벨을 붙이는 방법이 여럿 있지만, 어떻게 나누든 결과는 방대한 메서드 정보 어휘를 갖고 스코핑 정보를 봉투가 아니라 문서 안에서 찾는 서비스다.
이는 RPC 아키텍처를 규정하는 특징이다.
저자는 이것이 SOAP에 관한 사실이 아니라 SOAP가 현재 쓰이는 방식에 관한 사실임을 강조한다.
SOAP도 HTTP처럼 데이터를 봉투에 넣는 방법일 뿐이지만, 지금은 그 봉투에 원격 함수 호출 방법이나 그 반환값에 관한 XML-RPC 유사 데이터만 담긴다.

### WS-*

이 표준들은 SOAP 봉투를 위한 특수한 XML “스티커”를 정의한다.
이 스티커들은 HTTP 헤더와 유사하다.

### WSDL

WSDL(Web Service Description Language)은 SOAP 기반 웹 서비스를 기술하는 데 쓰이는 XML 어휘다.
클라이언트는 WSDL 파일을 읽어 어떤 RPC 스타일 메서드를 호출할 수 있는지, 그 메서드가 어떤 인자를 기대하며 어떤 데이터 타입을 반환하는지 정확히 알 수 있다.
현존하는 거의 모든 SOAP 서비스가 WSDL 파일을 노출하며, 대부분은 WSDL 파일이 안내서 역할을 하지 않으면 쓰기가 매우 어렵다.
저자는 WSDL이 SOAP를 RPC 스타일과 묶어두는 데 그 어떤 기술보다 큰 책임이 있다고 본다.

### WADL

WADL(Web Application Description Language)은 RESTful 웹 서비스를 기술하는 데 쓰이는 XML 어휘다.
WSDL처럼 범용 클라이언트가 WADL 파일을 읽으면 해당 웹 서비스의 전체 기능에 즉시 접근할 수 있게 된다.
다만 RESTful 서비스는 인터페이스가 더 단순하므로, WADL은 RPC 스타일 SOAP 서비스에 WSDL이 필요한 만큼 절실하지는 않다.
이는 좋은 일인데, 집필 당시 공식 WADL 파일을 제공하는 실제 웹 서비스가 거의 없었기 때문이다.
야후!의 웹 검색 서비스가 그런 소수의 예다.

## 잔여 용어

REST 논의에 자주 등장하지만 저자가 부정확하거나 이 책의 범위 밖이라고 보아 앞에서 다루지 않은 용어들이 있다.

### 서비스 지향 아키텍처(SOA)

큰 업계 유행어다.
저자가 깊이 다루지 않는 이유는 두 가지다.
첫째, 용어가 잘 정의되어 있지 않다.
둘째, 정의된 범위에서 보자면 “웹 서비스의 생산과 소비에 기반한 소프트웨어 아키텍처” 정도를 뜻한다.
이 책은 개별 서비스의 설계를 다루는 반면, 서비스 지향 아키텍처를 다루는 책은 한 단계 위에서 서비스를 소프트웨어 구성 요소로 쓰고 하나의 일관된 전체로 통합하는 법을 다뤄야 한다.
저자는 그런 내용을 다루지 않는다.

### REST의 경쟁자로서의 SOAP

웹 서비스 논쟁에 끼면 자주 듣는 말이지만 잘못된 인상을 주므로 저자는 쓰지 않는다.
RESTful 아키텍처의 주된 경쟁자는 SOAP 같은 특정 기술이 아니라 RPC 아키텍처다.
현존하는 거의 모든 SOAP 서비스가 RPC 아키텍처를 갖는 것은 사실이지만, SOAP는 HTTP처럼 스티커 붙은 봉투에 문서를 넣는 방법일 뿐이다.
SOAP가 RPC 아키텍처에 묶인 것은 주로 역사적 우연과 현세대 자동화 도구 때문이다.
여기에는 실제 긴장이 있지만 이 책에서 많이 다루지는 않는데, 대략 문서를 SOAP 봉투에 넣은 뒤 HTTP 봉투에 넣는 서비스와, HTTP 봉투만 쓰는 서비스 사이의 긴장이다.

### HTTP+POX

HTTP plus Plain Old XML의 약자다.
대략 저자가 REST-RPC 하이브리드라 부르는 서비스들을 가리킨다.
특히 데이터를 조회할 때 RESTful 설계와 겹치지만, 기본 아키텍처는 RPC 지향이다.
저자가 이 용어를 싫어하는 이유는 “Plain Old XML”이 부정확하기 때문이다.
이 서비스들의 흥미로운 점은 (SOAP 봉투에 싼 XML이 아니라) 평범한 XML 문서를 만든다는 것이 아니다.
일부는 아예 XML을 제공하지 않고 JSON, 평문, 이진 파일을 제공한다.
흥미로운 점은 이들의 RPC 아키텍처이며, 그것이 이들을 REST와 대립시킨다.

### STREST

Service-Trampled REST의 약자로, 이 역시 REST-RPC 하이브리드 아키텍처를 가리키는 또 다른 용어다.
RESTful 아키텍처가 다른 무언가(여기서는 RPC 스타일)에 점령당했다는 관념을 전달하므로 HTTP+POX보다는 정확하다.
그러나 저자는 이 용어도 싫어하는데, 진짜 웹 서비스는 오직 RPC 스타일 서비스뿐이라는 통념을 받아들이기 때문이다.
REST를 짓밟은 그 서비스가 RPC 서비스였으니, REST 서비스도 진짜 서비스라고 본다면 “RPC에 짓밟힌 REST”가 더 정확하겠지만 약어로는 좋지 못하다.

### 하이 REST와 로우 REST

진정 RESTful한 서비스와 저자가 REST-RPC 하이브리드라 부르는 것을 구분하는 또 하나의 방식이다.
하이 REST 서비스는 Fielding 논문을 충실히 따르는 것들로, 무엇보다 메서드 정보를 HTTP 메서드에, 스코핑 정보를 URI에 넣는다.
로우 REST 서비스는 거기서 벗어난 것으로 간주된다.
로우 REST 서비스는 대체로 특정 방향(RPC 스타일 쪽)으로 이탈하는 경향이 있으므로, 저자는 더 구체적인 용어를 선호한다.

## 핵심 정리

- 프로그래머블 웹은 사람의 웹과 같은 방식으로 작동하지만, HTML 대신 대개 XML을 제공하며 사람이 아니라 소프트웨어의 입력을 위한 것이다.
- 웹 서비스 클라이언트는 브라우저처럼 데이터를 가져오는 동시에, 사람처럼 그 데이터의 의미를 스스로 해석하고 결정을 내려야 한다.
- 모든 웹 서비스는 HTTP를 공유한다. HTTP는 봉투 속 문서 프로토콜로, 봉투의 형식은 엄격히 정하지만 내용물은 상관하지 않는다.
- 요청은 HTTP 메서드, 경로, 요청 헤더, 엔티티 바디(표현)로, 응답은 응답 코드, 응답 헤더, 엔티티 바디로 이루어진다.
- 웹 서비스를 가르는 두 질문은 “무엇을 할지”를 전달하는 메서드 정보와 “어느 데이터를 대상으로 할지”를 전달하는 스코핑 정보를 어디에 두느냐다.
- 세 아키텍처는 이렇게 구분된다. RESTful 리소스 지향은 메서드 정보를 HTTP 메서드에, 스코핑 정보를 URI에 둔다. RPC 스타일은 둘 다 봉투 안(또는 스티커)에 두고 대개 단일 엔드포인트에 POST만 쓴다. REST-RPC 하이브리드는 조회할 때는 RESTful하지만 데이터를 수정할 때 잘못된 HTTP 메서드를 써서 RPC 스타일로 기운다.
- 기술과 아키텍처는 별개다. 특히 SOAP는 봉투 형식일 뿐이지만, 현존하는 SOAP 서비스는 사실상 모두 RPC 아키텍처를 가지며 WSDL이 그 결합을 강화한다.
- RESTful 아키텍처의 진짜 경쟁자는 SOAP 같은 기술이 아니라 RPC 아키텍처다. HTTP+POX, STREST, 로우 REST 등은 모두 REST-RPC 하이브리드를 가리키는 부정확한 별칭들이다.
