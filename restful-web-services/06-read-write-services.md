# 6장 읽기/쓰기 리소스 지향 서비스 설계

《RESTful Web Services》(Leonard Richardson, Sam Ruby, O'Reilly 2007) 6장 정리.

## 개요

5장에서 설계한 지도 서비스는 여러 행성의 지도 이미지, 지도 위를 이동하기 위한 내비게이션 정보, 그리고 행성 위의 장소(식당, 운석 분화구 등) 정보를 제공했다.
방대한 데이터를 다루지만 전부 미리 만들어 둔 데이터셋 안에 담겨 있었고, 사용자가 서버에 자기 데이터를 올릴 방법은 없었다.

6장은 이 읽기 전용 지도 서비스에 쓰기 기능을 더한다.
검색 엔진의 웹 서비스에 가까웠던 서비스가, 데이터를 제공할 뿐 아니라 클라이언트를 대신해 데이터를 저장해 주는 Amazon S3, Flickr, del.icio.us API에 가까운 서비스로 바뀐다.

새 서비스를 얼마나 개방할 것인가는 설계상의 핵심 질문이다.
완전히 개방한다면 사용자가 표준 데이터셋의 모든 것을 자기 버전으로 제공할 수 있고, 자기 행성을 만들거나 커스텀 지도와 장소 데이터베이스를 올릴 수도 있다.
del.icio.us와 Flickr는 실제로 빈 데이터베이스에서 출발해 커뮤니티가 데이터셋 전체를 채우게 했다.

어떤 상태의 손잡이(lever of state)를 노출하고 어떤 것을 서버가 쥐고 있을지는, 사용자가 무엇을 하고 싶어 하는지와 그들의 애플리케이션을 얼마나 대신 작성해 줄 의향이 있는지에 달려 있다.
웹 서비스는 운영체제 API나 프로그래밍 언어 라이브러리처럼 하나의 추상화 계층이다.
사용자 모두가 같은 기능을 서비스 위에 직접 구현하고 있다면, 그 기능을 서비스 안으로 옮겨 새로운 종류의 리소스로 지원해 주는 편이 낫다.

이 장의 목표는 리소스 지향 서비스 설계 개념을 보여 주는 것이므로 야심을 절제한다.
빈 데이터셋에서 출발해 전부를 사용자 기여로 채우는 서비스는 설명할 개념보다 움직이는 부품이 훨씬 많아진다.
그래서 이전 장의 서비스를 딱 필요한 만큼만 확장해, 클라이언트가 커스텀 장소로 지도에 주석을 달 수 있게 한다.
모든 커스텀 장소는 하나의 사용자 계정에 연결되며, 그 계정에 대해 공개이거나 비공개일 수 있다.

## 사용자 계정을 리소스로 만들기

누구든 웹 서비스 클라이언트로 지도에 주석을 달 수 있게 하려면, 커스텀 장소를 표준 장소와 구별하고 한 사용자의 장소를 다른 사용자의 장소와 구별할 방법이 필요하다.
근본적으로 사용자 계정이 필요하다는 뜻이다.

클라이언트가 지구나 화성에 커스텀 장소를 만들면 그 장소는 그의 사용자 계정에 연결되어, 나중에 다시 찾을 수 있다.
그 장소를 공개로 지정하면 다른 클라이언트가 받아 가는 표현(representation) 안에서 그 장소로 향하는 링크를 보게 된다.

대부분의 기존 웹 서비스는 사람이 사용자 계정이나 “API 키”를 발급받는 절차를 둔다.
읽기 전용 접근만 주는 서비스조차 사용량을 추적하고 제한하려고 계정 가입을 요구하곤 한다.
Yahoo! Web Services는 조금 다르게, 키를 개인이 아니라 애플리케이션에 묶어 원하는 만큼 애플리케이션 키를 발급받고 배포할 수 있게 한다(저자는 이 책을 위한 “restbook” 키를 등록했다).

일반적인 웹 계정 가입 절차는 브라우저로 사이트에 가서 HTML 폼을 채우고, 약관에 동의하고, 때로 확인 이메일에 응답하는 식이다.
이 장에서 설계하는 계정 시스템은 다르다.
이 지도 서비스에서 사용자 계정은 지도 자체와 마찬가지로 리소스이며, 사실상 이 책의 첫 읽기/쓰기 리소스다.
클라이언트는 브라우저로 가입할 필요 없이 범용 웹 서비스 클라이언트로 계정을 만들 수 있다.

### 왜 사용자 계정을 리소스로 만드는가

첫째 이유는 설명의 초점 때문이다.
대부분의 서비스는 웹 애플리케이션을 통해 계정을 만들게 하는데, 웹 애플리케이션 설계는 이미 잘 정립된 별도 주제다.
특히 HTML 폼은 현재 GET과 POST만 지원하므로, 웹 애플리케이션은 안전하지 않은 연산을 전달하려면 오버로디드 POST(overloaded POST)를 써야 한다.
사용자 계정을 읽기/쓰기 리소스로 다루면, 익숙한 데이터 구조 위에서 새로운 리소스 지향 설계 절차를 온전히 보여 줄 수 있다.

둘째 이유는, 일상적인 데이터 구조를 균일 인터페이스(uniform interface)에 따르는 리소스로 다룰 때 새로운 가능성이 열린다는 것을 보이기 위해서다.
매시간 자기 현재 위치로 지구에 주석을 달아 이동 기록을 남기는 인터넷 연결 GPS 장치를 생각해 보자.
이런 장치가 수천 대라면 각 장치는 자기 주석만 볼 수 있어야 하고, 프로그래머가 개인용 계정 하나로 묶여서도, 구매자마다 웹 폼을 채워야 해서도 안 된다.

사용자 계정이 리소스라면 각 장치는 (일련번호 기반 사용자명 등으로) 저마다 계정을 가질 수 있고, 그 계정들은 자동으로 생성될 수 있다.
제조 시 일괄 생성될 수도 있고, 소유자가 처음 켤 때 장치가 스스로 계정을 만들 수도 있다.
최종 사용자는 자신이 웹 서비스를 쓰고 있다는 사실조차 모를 수 있다.
장치 프로그래머는 사용자 계정을 생성하는 소프트웨어를 작성해야 하는데, 계정이 리소스라면 그 방법은 자명하다.
HTTP의 균일 인터페이스가 답의 대부분을 미리 제공하기 때문이다.

### 인증, 인가, 프라이버시, 신뢰

사용자 계정을 노출하기 시작하면, 주어진 HTTP 요청에 어떤 사용자가 책임이 있는지를 판별할 방법이 필요하다.
인증(authentication)은 요청을 사용자에 묶는 문제이고, 인가(authorization)는 그 사용자에게 어떤 요청을 통과시킬지 결정하는 문제다.
이 서비스에서는 사용자 A로 인증하면 A의 계정만 조작할 수 있고 다른 사용자의 것은 조작할 수 없다.

클라이언트는 HTTP 요청을 보낼 때 `Authorization` 헤더에 자격 증명(credentials)을 담을 수 있다.
서버는 이를 검사해 인증과 인가를 판정하고, 두 조건이 모두 충족되면 요청을 수행한다.
자격 증명이 없거나 잘못되었거나 인가에 부족하면 서버는 응답 코드 401(“Unauthorized”)을 보내고, 앞으로 올바른 자격 증명을 보내는 방법을 담은 `WWW-Authenticate` 응답 헤더를 설정한다.

표준적인 인증 방식으로는 HTTP Basic, HTTP Digest, WSSE가 흔하고, Amazon S3처럼 정교한 요청 서명 방식을 쓰는 커스텀 인증도 있다.
이 서비스는 실제 구현하지 않으므로 가장 단순한 HTTP Basic 인증을 택한다.

프라이버시 문제도 있다.
사용자 A의 비공개 주석 목록은 다른 사용자가 접근할 수 없지만, 그 표현은 여전히 인터넷을 거쳐 여러 컴퓨터를 지나 전송된다.
중간 컴퓨터가 이 목록을 들여다보지 못하게 하려고, 모든 HTTP 트랜잭션을 SSL로 암호화한다.
그래서 이전 장의 `http://maps.example.com/` 대신 이 장의 URI는 모두 `https://maps.example.com/`로 시작한다.
HTTP 대신 HTTPS를 쓰면 도청을 막을 수 있는데, 이는 자격 증명을 평문으로 보내는 HTTP Basic 인증을 쓸 때 특히 중요하다.

마지막으로 남는 것은 클라이언트 소프트웨어와 사람인 최종 사용자 사이의 신뢰 관계다.
사람들은 웹사이트에 로그인할 때 브라우저가 사용자명과 비밀번호를 해당 사이트에만 보낸다고 믿는다.
대개는 그저 믿음으로 브라우저를 신뢰한다.
그러나 새로 받은 del.icio.us 관리용 웹 서비스 클라이언트에게 같은 자격 증명을 맡길 만큼 신뢰하기는 어렵다.
어떤 웹 서비스 클라이언트도 브라우저만큼 널리 쓰이거나 많은 사람이 소스 코드를 들여다보지 않기 때문이다.

이는 HTTP가 다룰 수 없는 문제다.
HTTP는 클라이언트와 서버 사이에 있지만, 이 문제는 최종 사용자와 클라이언트 사이에 있기 때문이다.
Basic, Digest, WSSE는 모두 클라이언트가 자격 증명을 알아야 하므로 이 문제를 근본적으로 풀지 못한다.
Google, Amazon, eBay, Flickr 같은 곳은 클라이언트가 실제 자격 증명을 모르고도 요청을 보내는 방법을 고안했다(3장에서 본 S3 요청 서명 후 특별 URI를 남에게 넘기는 방식이 그 힌트다).
아직 표준화된 해법이 없으므로 지금은 이 문제를 미뤄 두고 HTTP Basic 인증을 쓴다.
사용자는 자기 클라이언트를 브라우저만큼 신뢰해야 한다.

### 요구사항을 읽기/쓰기 리소스로 바꾸기

새 데이터셋(사용자 계정)을 식별했으니, 이전 장에서 밟은 것과 같은 설계 절차를 따른다.
다만 이전 장 절차는 읽기 전용 리소스에만 충분했다.
이 장은 클라이언트가 리소스를 생성·수정·삭제할 수 있게 하므로 3단계와 4단계가 추가되어 아홉 단계가 된다.

1. 데이터셋을 파악한다.
2. 데이터셋을 리소스로 나눈다.
3. 리소스에 URI로 이름을 붙인다.
4. 균일 인터페이스의 부분집합을 노출한다.
5. 클라이언트로부터 받을 표현을 설계한다.
6. 클라이언트에게 제공할 표현을 설계한다.
7. 하이퍼미디어 링크와 폼으로 이 리소스를 기존 리소스에 통합한다.
8. 정상적인 경우 무슨 일이 일어나야 하는지 고려한다.
9. 오류 조건, 즉 무엇이 잘못될 수 있는지 고려한다.

3단계부터 6단계까지는 “각 종류의 리소스마다” 반복한다.

### 데이터셋을 파악한다

대부분의 사이트는 이름이나 이메일 같은 개인 정보를 계정에 연결하지만, 이 서비스는 그런 것에 관심이 없다.
사용자 계정에 연결된 정보는 두 가지뿐이다.

- 계정의 이름(사용자명)
- 계정에 접근하기 위한 비밀번호

각 계정에는 하위 리소스(행성 위의 커스텀 장소)도 딸려 있지만 그 부분은 뒤에서 다룬다.
개인 정보를 추적하지 않으므로 사실 “사용자 계정”이라 부를 이유는 관례뿐이며, “비밀번호로 보호된 주석 모음”이라 불러도 무방하다.

### 데이터셋을 리소스로 나눈다

데이터셋이 “사용자 계정”으로 제한적이라 이 단계는 간단하다.
각 사용자 계정을 하나의 리소스로 노출한다.
5장의 용어로 이들은 두 번째 유형의 리소스, 즉 서비스가 그 아래의 사용자 객체를 노출하는 관문(portal)이다.
다른 사이트라면 사용자 계정 목록 자체를 별도 리소스로 노출하거나 사용자 목록을 검색하는 알고리즘적 리소스를 둘 수도 있지만, 여기서는 그러지 않는다.

### 리소스에 URI로 이름을 붙인다

리소스 종류가 하나뿐이라 이 부분도 쉽다.
사용자 계정을 다음 형태의 URI로 노출한다.

```text
https://maps.example.com/user/{user-name}
```

### 균일 인터페이스의 부분집합을 노출한다

이것이 첫 번째 새 단계다.
읽기 전용 리소스에서는 결정할 것이 없어 건너뛰었다.
정의상 읽기 전용 리소스는 GET, HEAD, OPTIONS만 노출하기 때문이다.
런타임에 생성·수정되는 리소스를 설계하는 지금은 PUT, POST, DELETE도 고려한다.

균일 인터페이스는 늘 동일하므로 이 단계 자체는 단순하다.
HTTP 메서드가 더 있었으면 하는 생각이 들면, 가장 먼저 2단계로 돌아가 데이터셋을 더 잘게 나눠 리소스 종류를 늘려야 한다.
그래도 안 될 때에만 특정 리소스가 오버로디드 POST를 지원하도록 RPC 스타일 요소를 들이는 것을 고려한다.

5장 예시처럼, “구독자”와 “발행된 칼럼” 리소스가 있는데 “HTTP에 SUBSCRIBE 메서드가 있으면 좋겠다”는 생각이 든다면, 가장 좋은 방법은 “구독”이라는 새 리소스를 만드는 것이다.
구독을 리소스로 만들면 HTTP 균일 인터페이스의 적용을 받는다.
반대로 “구독자” 리소스에 오버로디드 POST로 구독을 처리하기로 하면, 그 리소스의 인터페이스를 정의하기가 훨씬 어려워진다.

의도된 사용법에 대한 질문으로 어떤 부분을 노출할지 정한다.

- 클라이언트가 이 유형의 리소스를 새로 생성하는가? 물론이다. 사용자가 시스템에 등록되는 다른 방법이 없다.
- 새 리소스를 만들 때 새 URI를 정하는 주체가 클라이언트인가 서버인가? URI가 상수 문자열(`https://maps.example.com/user/`)과 클라이언트가 통제하는 변수(`{user-name}`)로만 이루어지므로 클라이언트가 주체다.

이 두 답에서 첫 결론이 나온다.
계정을 만들려면 클라이언트는 그 계정의 URI로 PUT 요청을 보낸다.
만약 최종 URI를 서버가 정하는 경우였다면, 클라이언트가 어떤 “팩토리”나 “부모” URI로 POST 요청을 보내 사용자를 만들 것이라 기대했을 것이다(그 경우는 뒤의 “커스텀 장소” 절에서 다룬다).

- 클라이언트가 이 유형의 리소스를 수정하는가? 그렇다. 사용자명 변경은 논쟁의 여지가 있어 단순함을 위해 허용하지 않지만, 비밀번호 변경은 언제나 허용한다.
- 클라이언트가 이 유형의 리소스를 삭제하는가? 그렇다. 다 쓴 계정은 삭제할 수 있다.
- 클라이언트가 이 유형의 리소스 표현을 가져가는가? 논쟁의 여지가 있다. 지금 계정에 딸린 정보는 URI에 든 사용자명과, 내주지 않을 비밀번호뿐이다. 그래도 GET과 HEAD를 노출하기로 한다. 원하는 사용자명이 이미 존재하는지 확인하거나, 나중에 특정 사용자가 정의한 공개 장소를 살펴보려는 클라이언트가 있기 때문이다.

### 클라이언트로부터 받을 표현을 설계한다

이 데이터셋에는 기본 제공 사용자 계정이 없고 모든 계정은 클라이언트가 만든다.
따라서 클라이언트가 계정을 어떻게 만드는지를 정해야 한다.

3장의 Amazon S3를 다시 보면, 클라이언트는 버킷 URI로 빈 PUT 요청을 보내 버킷을 만든다.
버킷은 이름 외에 다른 상태가 없어 엔티티 바디가 필요 없다.
반면 S3 객체는 이름과 값 두 가지 상태를 가지므로, 이름은 URI에, 값은 PUT 요청의 엔티티 바디에 담는다.
S3는 객체 값이 무엇이든 될 수 있기에 엔티티 바디에 어떤 데이터든 받지만, 빈 객체는 허용하지 않는다.

대부분의 웹 서비스는 엔티티 바디에 담기는 내용에 더 까다로워서, 특정 형식이어야 하고 특정 리소스 상태를 전달해야 한다.
이 서비스의 사용자 계정은 사용자명과 비밀번호 두 상태를 가진다.
사용자명은 스코핑 정보로서 URI에 들어가므로, 계정을 만드는 PUT 요청은 그 URI에 사용자명을 담는다.
비밀번호는 표현의 일부로서 엔티티 바디에 담아 보낸다.

표현은 반대 방향으로도 흐른다.
5장에서 표현은 서버가 리소스 상태를 전달하려고 클라이언트에게 보내는 문서라고 소개했지만, 표현은 클라이언트가 리소스 상태 변경을 제안하는 수단이기도 하다.
PUT 요청에 실어 보내는 표현은 리소스의 새 상태에 대한 주장(assertion)이다.

상태가 복잡할 때는 서버가 자신이 보내는 것과 같은 표현 형식을 받아들이는 편이 유용하다.
그러면 클라이언트는 GET으로 표현을 받아 수정한 뒤 그대로 PUT으로 되돌려 변경을 반영할 수 있다(9장의 Atom Publishing Protocol이 이 기법을 효과적으로 쓴다).
그러나 여기서는 상태가 비밀번호 하나뿐이고 그것을 서버가 클라이언트에 되돌려 보낼 일도 없다.
이런 단순한 경우에 알맞은 표현 형식을 도입한다.

#### 폼 인코딩

이 표현 형식은 미디어 타입(`application/x-www-form-urlencoded`) 외에 공식 이름은 없지만 익숙한 형식으로, “CGI 이스케이핑”이라고도 불린다.
브라우저에서 HTML 폼을 제출할 때 폼 데이터를 HTTP 요청에 담을 수 있게 정리하는 형식이다.
예 6-1은 텍스트 필드 `color1`, `color2`를 가진 간단한 HTML 폼이다.

```http
<form action="http://www.example.com/color-pairs" method="POST">
  <input name="color1" type="text"/>
  <input name="color2" type="text"/>
</form>
```

사용자가 두 필드에 “blue”와 “green”을 넣으면 폼 인코딩된 표현은 `color1=blue&color2=green`이 된다.
폼이 제출되면 브라우저는 `http://www.example.com/color-pairs`로 POST 요청을 보내면서 이 문자열을 엔티티 바디에 담는다.
만약 폼의 `method`가 GET이었다면 브라우저는 `http://www.example.com/color-pairs?color1=blue&color2=green`으로 GET 요청을 보낸다.
같은 데이터, 같은 형식이지만 이때는 그 데이터가 표현이 아니라 리소스를 식별하는 스코핑 정보다.

객체 상태를 키-값 쌍으로 나타낼 수 있을 때 폼 인코딩이 가장 단순한 표현 형식이다.
거의 모든 프로그래밍 언어가 HTTP나 CGI 라이브러리에 폼 인코딩/디코딩 기능을 내장하고 있다.

이 지도 서비스는 클라이언트가 사용자를 생성하거나 편집할 때 폼 인코딩 표현을 받는다.
이름은 URI에 들어가고 바꿀 수 없으므로, 사용자 표현은 `password={the-password}` 형태다.
예 6-2는 이 서비스로 계정을 만드는 가상의 Ruby 코드다.

```text
require 'rubygems'
require 'rest-open-uri'
require 'cgi'
require 'uri'

def make_user(username, password)
  open("https://maps.example.com/user/#{URI.escape(username)}",
       :data => CGI.escape("password=#{password}"), :method => :put)
end
```

두 가지를 눈여겨볼 점이 있다.
첫째, 비밀번호라는 민감한 데이터를 전송하므로 HTTPS를 쓴다.
둘째, 서로 다른 두 인코딩을 함께 쓴다.
URI에 들어가는 사용자명은 `URI.escape`로 URI 인코딩하고, 표현에 들어가는 비밀번호는 `CGI.escape`로 폼 인코딩한다.
URI 인코딩과 폼 인코딩은 비슷하지만 같지 않으며, 둘을 혼동하는 것은 미묘한 버그의 흔한 원인이다.

계정 비밀번호 변경은 계정을 처음 만드는 것과 같다.
클라이언트는 계정 URI로 새 표현(새 비밀번호)을 담은 PUT 요청을 보낸다.
다만 인가 없이는 아무도 비밀번호를 바꿀 수 없으므로, 수정 요청에는 그 계정을 수정할 권한이 있음을 서비스에 납득시키는 `Authorization` 헤더를 담아야 한다.
즉, 비밀번호를 바꾸려면 현재 비밀번호를 알아야 한다.
이 서비스는 들어오는 `Authorization` 헤더가 HTTP Basic 인증 표준을 따를 것으로 기대한다.

DELETE 요청에는 표현이 필요 없지만, 사용자를 삭제하려면 올바른 `Authorization` 헤더가 필요하다.
즉, 계정을 삭제하려면 그 사용자의 비밀번호를 알아야 한다.

### 클라이언트에게 제공할 표현을 설계한다

클라이언트는 지도나 장소의 표현을 GET으로 가져오듯, 계정 URI로 GET을 보내 계정 표현을 가져온다.
지금은 전달할 상태가 사용자명과 비밀번호 둘뿐이고 비밀번호는 내보내고 싶지 않으므로 표현이 빈약하다.
잘 설계된 시스템이라면 서버에 평문 비밀번호 자체가 없고 인증용 암호화 버전만 있을 것이다.
커스텀 장소를 통합하면 이 표현은 더 풍부해진다.
예 6-3은 지금으로선 다소 성긴 XHTML 문서다.

```xml
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.1//EN"
  "http://www.w3.org/TR/xhtml11/DTD/xhtml11.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en">
<head>
  <title>User homepage for leonardr</title>
</head>
<body>
  <p class="authenticated">
    You are currently logged in as
    <a class="user" href="/user/leonardr">leonardr</a>.
  </p>
  <p>User homepage for
    <a class="user" href="/user/leonardr">leonardr</a></p>
  <form id="modifyUser" method="put" action="">
    <p>Change your password:
      <input class="password" name="password" /><br />
      <input class="submit" /></p>
  </form>
</body>
</html>
```

여기서도 표현은 현재 리소스 상태를 전달하면서, 클라이언트가 다른 상태로 이동하도록 돕는다.
비밀번호를 바꾸려고 앞으로 보낼 PUT 요청을 HTML 폼으로 서술했다.
표현을 가져오는 법이나 사용자를 삭제하는 법을 안내하는 폼은 없다.
그런 일에는 HTTP GET과 DELETE를 쓴다는 것이 당연하기 때문이다.
하이퍼미디어는 복잡한 것, 즉 다른 리소스로 향하는 링크(어느 URI를 GET/DELETE할지 알려 주는 것)와 표현에 대한 서술에만 필요하다.

예 6-3에는 문제가 하나 있다.
폼이 메서드로 PUT을 지정하는데 HTML 폼은 GET과 POST만 허용한다는 점이다.
5장 예 5-11의 `repeat` 문법과 마찬가지로, 여기서는 현재 HTML의 한계를 우회하려고 아직 정식 발표되지 않은 XHTML 5를 쓴다.
다른 방법으로는 HTML 폼 대신 WADL 스니펫을 보내거나, 8장에서 다룰 오버로디드 POST로 PUT을 실어 보내는 방법이 있다.

남의 계정을 GET하면 예 6-4처럼 다른 표현을 받는다.

```xml
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.1//EN"
  "http://www.w3.org/TR/xhtml11/DTD/xhtml11.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en">
<head>
  <title>User homepage for samruby</title>
</head>
<body>
  <p class="authenticated">
    You are currently logged in as
    <a class="user" href="/user/leonardr">leonardr</a>.
  </p>
  <p>User homepage for <a class="user" href="/user/samruby">samruby</a></p>
</body>
</html>
```

이 표현에는 리소스 상태를 바꾸는 컨트롤이 없다.
클라이언트가 leonardr로 인증했는데 이 페이지는 samruby의 것이라 그럴 권한이 없기 때문이다.
지금 이 표현은 samruby라는 사용자가 존재함을 leonardr에게 확인해 줄 뿐이다.
그런 사용자가 없었다면 `/user/samruby`로 보낸 GET은 상태 코드 404(“Not Found”)를 반환하고, 클라이언트는 PUT으로 samruby를 자유롭게 만들 수 있다.

### 이 리소스를 기존 리소스에 연결한다

이전 장에서 정의한 리소스(지도 목록, 개별 지도, 장소, 장소 목록)는 사용자 계정과 직접 관련이 없지만, 여기서 더할 만한 좋은 기능이 있다.

하나는 위 두 예시에 보이는 “authenticated” 메시지를 모든 리소스의 표현에 넣는 것이다.
유효한 자격 증명으로 요청할 때마다 표시되며, 인증된 클라이언트에게 자기 계정 데이터를 가져오는 법을 보여 주는 하이퍼미디어다.
이제 모든 리소스가 그것을 요청한 사용자의 계정에 연결된다.

또 하나는 인증되지 않은 클라이언트에게 계정 만드는 법을 보여 주는 하이퍼미디어다.
가장 좋은 자리는 서비스의 “홈페이지”인 행성 목록의 표현이다.
이미 서비스의 다른 주요 부분으로 향하는 링크를 담고 있으니 이 새 부분으로 향하는 링크도 담아야 한다.
예 6-5는 사용자 생성 방법을 알려 주는 XHTML 5 스니펫이다.

```xml
<form id="createUser" method="PUT" template="/user/{username}">
  <p>Username: <input type="text" name="username" /><br />
  <p>Password: <input type="password" name="password" /><br />
  <input class="submit" />
</form>
```

익숙한 HTML과 다른 점은 두 가지다.
`method` 속성이 (예 6-3처럼) HTML 4가 허용하지 않는 PUT을 지정하는 점, 그리고 URI 템플릿(URI Templating) 표준으로 폼 변수 `username`을 URI에 끼워 넣는 새 `template` 속성이다.
집필 시점에 URI 템플릿은 HTML 5에 제안되었으나 승인되지 않았고, 거부된다면 이 예제는 비공식으로 쓰거나(사용자가 커스텀 클라이언트를 작성해야 함) WADL로 전환하면 된다.

이 하이퍼미디어 폼은 PUT 요청의 구문(syntax)은 말해 주지만 의미(semantics)는 거의 말해 주지 못한다.
클라이언트는 폼이 “createUser”라는 라벨을 가졌다는 것은 알지만 그 뜻은 모르고, 특정 표현을 특정 URI에 PUT하면 서버가 받아 줄 것이라는 것과 PUT의 의미는 안다(PUT은 언제나 같은 뜻이므로).
표현에 “username”이 들어가야 한다는 것은 알아도 username이 무엇인지는 모른다.
“createUser”가 “사용자를 만든다”는 뜻임을 이해하고 규칙을 정하는 것은 사람인 프로그래머의 몫이다.
이 하이퍼미디어는 그저 “createUser” 시점에 PUT 요청을 어떻게 구성할지 알려 주는, 서비스가 클라이언트에게 하는 약속이다.

많은 웹 서비스는 이런 데이터를 클라이언트 프로그래머의 편의를 위해 하나의 WSDL이나 WADL 파일에 미리 몰아 둔다.
이는 연결성(connectedness) 원칙을 훼손하므로 REST 설계 철학에 다소 어긋나지만, 클라이언트를 미리 프로그래밍해야 하는 웹 서비스에서는 이해할 만한 충동이고 흔히 문제를 일으키지 않는다.

### 정상적인 경우 무슨 일이 일어나야 하는가

클라이언트가 `/user/leonardr`로 PUT 요청을 보낼 때를 생각해 보자.
서버는 요청을 읽고, 이면에서 어떤 조치를 취한 뒤 응답한다.
응답의 숫자 코드, HTTP 헤더와 엔티티 바디, 그리고 리소스 상태에 미치는 실제 효과를 정해야 한다.

정상 흐름은 어렵지 않다.
“leonardr”라는 사용자가 없으면 서비스는 지정된 비밀번호로 사용자를 만든다.
응답 코드는 201(“Created”)이고 `Location` 헤더에는 새로 만든 사용자의 URI가 담긴다.

계정이 이미 있으면, 클라이언트가 제안한 새 표현에 맞춰 리소스 상태가 수정된다. 즉, 비밀번호가 바뀐다.
이때 응답 코드는 200(“OK”)이고 엔티티 바디에 계정 표현이 담길 수 있다.
또는 비밀번호 변경이 표현에 영향을 주지 않으므로 응답 코드를 205(“Reset Content”)로 하고 엔티티 바디를 아예 생략할 수도 있다.

PUT만이 표현을 포함하므로 유일하게 복잡한 요청이다.
GET과 DELETE는 균일 인터페이스대로 정확히 작동한다.
성공한 GET은 응답 코드 200(“OK”)과 엔티티 바디의 표현을 갖는다.
성공한 DELETE도 응답 코드 200(“OK”)을 갖는다.
서버는 성공한 DELETE에 엔티티 바디를 실을 수 있지만, 표현할 리소스가 더 이상 없으므로 대개 상태 메시지 정도만 담긴다.

### 무엇이 잘못될 수 있는가

리소스를 생성·수정·삭제하는 요청은 단순히 표현을 가져오는 요청보다 실패 조건이 더 많다.

가장 뻔한 문제는 클라이언트의 표현을 서버가 이해하지 못하는 경우다.
서버는 폼 인코딩 형식을 기대하는데 클라이언트가 XML 문서를 보내면 상태 코드는 415(“Unsupported Media Type”)다.

클라이언트가 표현을 아예 안 보냈거나, 형식이 잘못되었거나 말이 안 되는 데이터로 채운 폼 인코딩 표현을 보냈다면 상태 코드는 400(“Bad Request”)이다.

표현은 말이 되지만 리소스를 모순되거나 불가능한 상태로 만들라고 하는 경우도 있다.
예컨대 표현이 `password=`인데 빈 비밀번호 계정을 허용하지 않는다면, 정확한 코드는 상황에 따라 다르지만 빈 비밀번호의 경우 대개 400(“Bad Request”)이고, 다른 상황에서는 409(“Conflict”)일 수 있다.

클라이언트가 잘못된 자격 증명을 보내거나, 전혀 다른 계정의 인가 자격 증명을 보내거나, `Authorization` 헤더를 아예 안 보냈다면 응답 코드는 401(“Unauthorized”)이다.
그리고 HTTP Basic 인증 규칙에 맞게 헤더를 구성하는 단서를 담아 `WWW-Authenticate` 헤더를 설정한다.

이미 존재하는 사용자를 만들려 하면 가능한 응답 코드 하나는 409(“Conflict”)다.
PUT을 수행하면 같은 사용자명의 사용자 리소스가 둘 생겨 서비스 리소스가 모순 상태에 빠지기 때문이다.
다른 가능성은 이를 인증 없이 기존 사용자의 비밀번호를 바꾸려는 시도로 보고 401(“Unauthorized”)을 보내는 것이다.

이전 장처럼 서버 쪽의 불특정 문제로 500(“Internal Server Error”)이나 503(“Service Unavailable”)이 날 수도 있다.

## 커스텀 장소

이제 리소스 설계 절차를 처음부터 다시 밟는다.
이번에는 클라이언트가 만들 수 있는 커스텀 장소, 즉 기본 제공 장소와 나란히 지도에 표시되는 장소를 설계한다.
절차에 익숙해졌을 테니 이번 통과는 다소 축약하고, 커스텀 장소가 사용자 계정과 무엇이 다른지에 초점을 맞춘다.

### 데이터셋을 파악한다

클라이언트는 지도가 있는 어느 행성에나 원하는 만큼 장소를 만들 수 있다.
커스텀 장소는 기본 제공 장소처럼 검색 결과 목록에 나타나며, 기본 제공 장소와 같은 데이터를 가질 수 있다.
즉 유형(“city”), 이름(“Springfield”), 위도·경도 좌표(“39.8N 89.64W”), 그리고 텍스트 설명(“일리노이의 주도”)이다.
여러 커스텀 장소가 같은 좌표를 공유할 수 있고(“우리 집”과 “내 현재 위치”), 커스텀 장소가 기본 제공 장소와 위치를 공유할 수도 있다.

모든 커스텀 장소는 어떤 사용자 계정에 연결된다.
커스텀 장소는 공개이거나 비공개일 수 있다.
비공개 장소는 그 장소를 “소유한” 계정의 자격 증명을 제시한 사람에게만 보이고 수정 가능하다.

### 데이터셋을 리소스로 나눈다

각 커스텀 장소는 기본 제공 장소처럼 하나의 리소스가 된다.
클라이언트가 자기 커스텀 장소 목록을 가져올 수 있게도 하고 싶다.
이 설계에서 사용자 계정은 곧 비밀번호로 보호된 장소 목록이므로, 장소 목록을 별도 리소스로 노출하지 않고 “사용자 계정” 리소스를 확장해 사용자의 장소 목록을 포함시킨다.
이는 Amazon S3에서 버킷이 객체 목록으로만 표현되는 것과 유사하다.

### 리소스에 URI로 이름을 붙인다

커스텀 장소는 분명 하위 리소스이지만 무엇에 종속되는가?
사용자 계정, 행성 위의 지리적 점, 또는 도시·국가·행성 같은 상위 장소에 연결할 수 있다.

여기서는 커스텀 장소를 기본 제공 장소와 거의 같은 방식으로 이름 붙인다.
각 장소는 지리적 점에 연결되며 다음 형태의 URI로 접근한다.

```text
/user/{username}/{planet}/{latitude},{longitude}/{place-name}
```

새 요소는 `{username}`으로, 같은 장소에 대한 사람마다의 견해를 구별한다.
예컨대 Joe's Diner에 대한 Sam의 후기는 `/user/samruby/Earth/45.2;-114.2/Joe's%20Diner`에, Leonard의 덜 호의적인 후기는 `/user/leonardr/Earth/45.2;-114.2/Joe's%20Diner`에 있다.

`/Earth/USA?show=Joe's+Diner` 같은 URI는 이전처럼 작동해, 미국 내 “Joe's Diner”라는 장소의 검색 결과를 반환한다.
달라진 점은 검색 대상이 늘었다는 것이다.
기본 제공 장소 데이터베이스뿐 아니라 각 사용자의 공개 장소 목록과 자신의 비공개 목록까지 검색된다.

기본 제공 장소는 여전히 특권을 가진다.
일본의 어느 테마파크에 러시모어산 3분의 1 축소 모형이 있다고 하자.
클라이언트가 도쿄 북쪽에 “Mount Rushmore”라는 커스텀 장소를 만들어도 `/Earth/Mount%20Rushmore`는 여전히 사우스다코타의 원본을 가리킨다.
어느 “Mount Rushmore”인지 모호해지지 않는다.
다만 `/Earth?show=Mount+Rushmore`는 두 장소를 모두 보여 준다.

### 균일 인터페이스의 부분집합을 노출한다

클라이언트는 GET과 HEAD로 기본 제공 장소, 자기 장소(공개든 비공개든), 남이 만든 공개 장소의 표현을 가져올 수 있다.
DELETE로 자기 장소를 삭제하고, PUT으로 자기 장소의 상태를 바꿀 수 있다.

클라이언트가 지도 주석을 만드는 방법은 두 가지다.
지도 위 기존 장소에 코멘트를 다는 것(“Mount Rushmore”), 또는 특정 위도·경도의 점에 새 이름을 붙이는 것(“베티에게 키스한 옥수수밭”)이다.

첫째 경우, 만들어지는 리소스는 “leonardr의 관점에서 본 Mount Rushmore”다.
이 리소스를 만들 때 클라이언트는 러시모어산이 지도에서 정확히 어디인지 몰라도 된다.
“Mount Rushmore”는 합의된 이름이고 그 이름의 기본 제공 장소가 있으므로, 좌표 조회는 서버에 맡길 수 있다.
둘째 경우, 만들어지는 리소스는 서버가 처음 접하는 완전히 새로운 장소이고, 좌표를 아는 책임은 클라이언트에 있다.

“leonardr의 관점에서 본 Mount Rushmore”는 다른 리소스, 즉 기본 제공 장소 “Mount Rushmore”의 하위 리소스다.
이 상위 리소스는 이미 존재하며 `/Earth/Mount%20Rushmore` 같은 URI를 가진다.
합의된 이름을 재사용하려는 클라이언트는 위치를 조회할 필요 없이, 주석의 최종 URI를 직접 계산해 PUT을 보내는 대신 “Mount Rushmore” URI로 POST 요청을 보내 최종 URI 결정을 서버에 맡긴다.
마찬가지로 앨라배마 주 의사당에 코멘트하려면 정확한 좌표나 주소를 계산하지 않고 `/Earth/USA/AL/State%20capitol`로 POST하면 된다.
기본 제공 장소를 식별하는 어떤 URI든 그 장소에 코멘트하는 POST 요청의 대상이 될 수 있다.

커스텀 이름은 어떨까?
사우스다코타의 원본이 아니라 이마이치의 축소 모형에 “Mount Rushmore”라는 이름을 주고 싶거나, “베티에게 키스한 옥수수밭” 주석을 만들고 싶다면?
이때 클라이언트는 그 장소의 위도·경도를 알아야 하며, 그러면 새 리소스의 URI(행성, 지리적 점, 장소 이름, 자신의 사용자명)를 구성할 모든 정보를 갖게 된다.
따라서 `/user/bob/Earth/42;-93.7/the%20cornfield%20where...` 같은 URI로 PUT을 보낼 수 있는데, 이는 `/user/bob`로 PUT을 보내 계정을 만드는 것과 똑같이 작동한다.

그럼에도 여기서조차 POST를 쓰는 편이 더 깔끔하다.
지도 위 새 장소는 하위 리소스로, 기본 제공 장소에 대한 코멘트가 행성 위 어떤 점에 종속되듯 행성 위 어떤 점에 종속되기 때문이다.
그래서 클라이언트는 `/Earth/42;-93.7`로 POST 요청을 보내 새 장소를 지도에 올릴 수도 있다.
기존 장소에 대한 코멘트(`/Earth/Mount%20Rushmore`로의 POST)와 같은 방식이되, 여기서는 장소가 합의된 이름이 아니라 위도·경도로 식별될 뿐이다.

이 서비스는 더 단순하다는 이유로 완전히 새로운 장소에 대해 POST를 지원한다.
행성에 완전히 새로운 장소를 더하든 합의된 장소에 코멘트하든 인터페이스가 같아진다.
다른 서비스라면 두 방법을 다 지원할 수도 있다.
클라이언트가 최종 URI를 계산할 의향이 있으면 그 URI로 PUT을, 아니면 부모 URI로 POST를 보내게 하는 식이다.

여기서 POST를 쓰지만 오버로디드 POST가 아니라는 점에 유의한다.
이 서비스의 클라이언트는 오직 기존 리소스 “아래에” 리소스를 만들고 싶을 때만 POST를 쓴다.
새 리소스의 URI(`/user/leonardr/Earth/43.9;-103.46/Mount%20Rushmore`)가 기존 URI(`/Earth/Mount%20Rushmore`)를 직접 확장하지는 않을 수 있지만, 두 리소스는 개념적 관계를 가진다.

### 클라이언트로부터 받을 표현을 설계한다

클라이언트가 행성에 핀을 꽂아 커스텀 장소를 만들 때 어떤 정보가 필요한가?
행성과 그 위의 장소를 식별해야 한다.
장소는 위도·경도로, 또는 “Mount Rushmore” 같은 표준 이름을 참조해 식별할 수 있다.
이 변수들을 `planet`, `latitude`, `longitude`, `name`이라 하자.
서버는 장소의 유형(type)을 알아야 하고, 장소는 공개일 수도 아닐 수도 있으며, 클라이언트는 커스텀 설명(description)을 줄 수 있다.
최종 URI에는 사용자명도 들어가지만, 클라이언트가 이미 `Authorization` 헤더로 제공하므로 두 번 보낼 필요는 없다.

이들은 모두 키-값 쌍이다.
따라서 사용자 계정과 마찬가지로 장소도 폼 인코딩 문자열로 표현하게 한다.
JSON이나 XML이 필요할 만한 복잡한 데이터 구조가 없다.

클라이언트 요청은 일부 키-값 쌍만 보내고 나머지를 생략할 수 있다.
URI에 스코핑 정보로 들어간 정보는 표현에서 되풀이할 필요가 없다.
`/Earth/43.9;-103.46`으로 POST할 때는 위도·경도가 URI에 있으므로 지정할 필요 없이 `name`과 `type`만 지정하면 된다.
`/Earth/Mount%20Rushmore`로 POST할 때는 `latitude`, `longitude`, `name`을 지정하면 안 된다.
잘 알려진 기존 장소를 바탕으로 새 장소를 만드는 것이라 새 장소가 기존 장소의 이름과 위치를 물려받기 때문이다.
클라이언트는 커스텀 유형(“national-park”, “political” 등)을 지정하거나 기본값(“monument”)을 물려받을 수 있다.

클라이언트는 언제나 `description`과 `public`을 생략할 수 있다.
서비스가 기본값을 설정하기 때문이다.
설명은 기본적으로 비어 있고, 장소는 기본적으로 공개다.

클라이언트가 자기 커스텀 장소를 수정할 때는 이름, 위치, 유형, 설명, 공개 여부 등 무엇이든 바뀔 수 있다.
장소를 수정하는 PUT 요청은 장소 생성에 쓰인 것과 같은 키-값 쌍을 임의 조합으로 지정할 수 있고, 서버는 변경이 말이 되는 한 적절히 반영한다.

예 6-6은 새 커스텀 장소를 만드는 HTTP POST 요청의 예다.
폼 인코딩 표현과 URI의 스코핑 정보가 합쳐져 새 리소스의 모든 필수 상태를 전달한다.
이름과 위치는 스코핑 정보에서, 유형과 설명은 표현에서 온다.
표현이 `public` 값을 지정하지 않으므로 기본값이 적용되어 이 새 리소스는 공개가 된다.

```http
POST /Earth/USA/Mount%20Rushmore HTTP/1.1
Host: maps.example.com
Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=

type=national-park&description=We%20visited%20on%203/5/2005
```

### 클라이언트에게 제공할 표현을 설계한다

작업의 대부분은 이미 끝났다.
5장에서 장소를 위한 XHTML 기반 표현 형식을 정의했고, 커스텀 장소는 기본 제공 장소와 똑같이 보인다.

새로운 부분은 하나뿐이다.
인증된 클라이언트가 자기 커스텀 장소 중 하나의 표현을 요청하면, 서비스는 그 장소를 편집하는 법을 보여 주는 하이퍼미디어를 표현에 덧붙인다(예 6-7).
삭제 방법은 균일 인터페이스가 처리하므로 알려 줄 필요가 없다.
다만 장소가 행성, 위도, 경도 등으로 정의된다는, 위에서 산문으로 쓴 정보는 전달해야 한다.

```xml
<form id="modifyPlace" method="PUT" action="">
  <p>Modify this place:</p>
  <p>
    Name: <input name="name" value="Mount Rushmore" type="text" /><br />
    Type: <input name="type" value="national-park" type="text" /><br />
    Position:
    <input name="latitude" value="43.9" type="text" />,
    <input name="longitude" value="-103.46" type="text" /><br />
    Description:
    <textarea name="description">We visited on 3/5/2005</textarea><br />
    Public?
    <input name="public" type="checkbox" value="on"/>
    <input type="submit" />
  </p>
</form>
```

앞서의 유의점이 여기에도 적용된다.
PUT을 메서드로 지정하므로 XHTML 4로는 유효하지 않고 XHTML 5로만 유효하다.
또한 클라이언트는 미리 프로그래밍되지 않으면 이 폼으로 무엇을 할지 모른다.
컴퓨터는 “modifyPlace”가 무슨 뜻인지, “latitude”에 어떤 값이 적절한지 모른다.

클라이언트가 이런 폼을 이해하려면 미리 프로그래밍되어야 하므로, 오늘날 대부분의 서비스는 리소스 수정 폼을 그 리소스 표현에 넣지 않는다.
모든 폼을 앞단(WSDL이나 WADL 파일)에서 제공하거나, (위에서처럼) 산문으로 명세하고 구현은 서비스 프로그래머에게 맡긴다.
표현과 함께 폼을 제공하는 것이 정말 도움이 되는지는 논쟁거리이지만, API를 산문으로만 명세하고 프로그래머에게 구현을 떠넘기는 것보다는 폼을 제공하는 편이 낫다.

### 이 리소스를 기존 리소스에 연결한다

세 종류의 통합이 필요하다.
첫째는 데이터 통합이다.
사용자 계정을 DELETE하면 `/user/{username}` 아래의 커스텀 장소도 모두 삭제되어야 한다.
그 리소스로 향하던 URI들은 이제 410(“Gone”)이나 404(“Not Found”)를 반환한다.

나머지 통합은 기존 리소스의 표현을 새 리소스에 대해 언급하도록 바꾸는 일이다.
검색 결과가 커스텀 장소로 링크되게 하고, 지구 위의 점이 사용자에게 그 점에 커스텀 장소를 만드는 법을 보여 주게 해서 연결성을 높인다.

특히 예 6-3의 성긴 계정 표현은 링크 기반 통합이 절실하다.
여기가 사용자의 커스텀 장소를 나열하기에 이상적인 자리다.
검색 결과를 나타낼 때와 같은 XHTML 링크 목록으로 장소 목록을 표현한다.

5장 서비스에서 “Mount Rushmore”를 검색하면(`/Earth?show=Mount+Rushmore`) 기본 제공 데이터베이스의 장소, 아마 사우스다코타의 합의된 위치만 나왔다.
새 버전에서는 결과가 여럿일 가능성이 크다.
다른 사용자들이 러시모어산에 단 주석과, 이마이치의 축소 모형처럼 사용자들이 “Mount Rushmore”라 이름 붙인 다른 장소들도 함께 반환된다.
이는 5장에서 데이터베이스에 “Joe's diner”가 여럿이던 경우와 같다.
검색 결과를 각기 특정 리소스로 링크되는 목록으로 제시하며, 달라진 것은 검색 범위가 넓어진 것뿐이다.
검색 결과는 기본 제공 장소, 남이 공개한 커스텀 장소, 또는 인증된 사용자가 만든 커스텀 장소(공개 또는 비공개)일 수 있다.

클라이언트에게 지도에 자기 장소를 만드는 법도 보여 줘야 한다.
커스텀 장소는 기존 장소의 하위 리소스로 생성되므로, 그 정보를 `/Earth/Mount%20Rushmore`, `/Earth/42;-93.7` 같은 장소 표현에 담는 것이 논리적이다.

예 6-8은 지난 두 장에서 다룬 대부분을 한데 모은, `/Earth/43.9;-103.46`의 표현 예다.
여러 지도 위의 한 점, 기본 제공 장소, 다른 사용자들의 커스텀 장소, 인증된 사용자의 커스텀 장소로 링크하고, 이 좌표에 새 커스텀 장소를 만드는 하이퍼미디어 폼까지 담아 하이퍼미디어가 풍부하다.

### 정상적인 경우 무슨 일이 일어나야 하는가

새 리소스인 커스텀 장소는 대체로 이미 정의한 다른 리소스처럼 작동한다.
GET에는 기본 제공 장소처럼 응답하고, PUT(키-값 쌍 표현)과 DELETE(표현 없음)에는 “사용자 계정” 리소스처럼 응답한다.
새로 고려할 예외적 경우는 몇 가지뿐이다.

커스텀 장소를 만들면 사용자 때와 똑같이 응답 코드는 201(“Created”)이다.
그러나 사용자명은 바꿀 수 없게 막아 사용자 URI가 바뀔 일이 없었던 반면, 장소는 이름을 바꾸거나 (배처럼) 한 점에서 다른 점으로 옮길 수 있어 URI가 바뀔 수 있다.

위치를 바꾸지 않고 커스텀 장소를 수정하면 응답 코드는 200(“OK”)이다.
위치가 바뀌면 응답 코드는 301(“Moved Permanently”)이고 `Location` 헤더에 장소의 새 URI가 담긴다.
클라이언트는 새 URI를 추적하도록 자기 자료 구조를 갱신할 책임이 있다.
이는 8장에서 다시 다룰 논쟁, 즉 유용한 정보를 담은 URI와 결코 바뀌지 않는 URI 중 무엇이 더 중요한가와 이어진다.
이 서비스의 URI는 좌표와 이름이라는 두 리소스 상태로 장소를 서술하므로(`/user/leonardr/Earth/43.9;-103.46/Mt.%20Rushmore`), 둘 중 하나가 바뀌면 옛 URI는 깨진다.

깨진 URI는 사람의 웹에서도 곤란하지만 프로그래머블 웹에서는 더 곤란하다.
커스텀 “장소”가 배처럼 끊임없이 움직인다면 사실상 영구 URI가 없는 셈이다.
이것이 이 시스템의 가장 큰 설계 결함이다.
실제 서비스로 노출한다면 바뀌는 리소스 상태를 담지 않는 대체 URI, 즉 “퍼머링크(permalink)”를 모든 장소에 부여할 것이다.
장소에서 바뀌지 않는 것은 소속 행성과 소유자뿐이므로 이런 URI는 `/user/leonardr/Earth/36028efa8`처럼 친근해 보이지 않겠지만, 적어도 언제나 같은 장소를 가리킨다.

### 무엇이 잘못될 수 있는가

새 리소스는 새 오류 조건을 들여오지만 대부분 이미 다룬 것의 변형이라 빠르게 짚는다.
클라이언트가 잘못된 위도·경도로 기존 장소를 지도 밖으로 옮기려 하면 응답 코드는 400(“Bad Request”)으로, 5장의 비슷한 경우와 같다.
클라이언트가 서버에 필요한 정보를 모두 주지 않고 장소를 만들려 할 때도 400이 적절하며, 이는 비밀번호 변경을 지시하면서 새 비밀번호를 실제로 주지 않은 경우와 비슷하다.

이 서비스는 한 사용자가 같은 좌표에 같은 이름의 장소를 둘 이상 정의하는 것을 허용하지 않는다.
`/user/leonardr/Earth/43.9;-103.46/Mt.%20Rushmore`는 한 번에 한 장소만 식별할 수 있다.
“My car”라는 장소를 둘 가진 클라이언트가 PUT으로 하나를 다른 하나의 위치로 옮기려 하면, 서비스는 409(“Conflict”)로 거부한다.
그 좌표로 장소를 옮기는 것 자체는 문제가 없지만, 지금 마침 같은 이름의 다른 장소가 거기 있는 것이 문제다.
같은 좌표의 커스텀 장소 둘 중 하나를 다른 하나의 이름으로 바꾸려 할 때도 같은 409가 난다.
어느 쪽이든 구문상 유효한 요청이 시스템 리소스를 모순 상태로 만들려는 것으로, 이미 존재하는 사용자를 만들려는 것과 같다.

완전히 새로운 오류 조건이 하나 있다.
클라이언트가 남이 만든 비공개 장소에 접근하려는 경우다.
가능성은 둘이다.
첫째는 403(“Forbidden”)으로 거부하는 것이다.
403은 인증이 없거나 불충분할 때 쓰이며, 이 경우 후자에 해당한다.

그러나 403 응답은 리소스가 존재한다는 사실을 은연중에 인정하는 것이라, 서버가 내주면 안 되는 정보다.
A가 만들어 비공개로 표시한 장소를 B가 추측으로라도 이름조차 알아내지 못하게 해야 한다.
리소스의 존재를 드러내는 것이 보안을 해칠 때, HTTP 표준은 서버가 “거짓말”을 하고 404(“Not Found”)를 보내는 것을 허용한다.

## 지도 서비스를 되돌아보며

여전히 단순한 설계지만 꽤 많은 기능을 갖췄다.
5장에서 클라이언트는 지도 이미지를 얻고, 지도를 돌아다니고, 지구 위 점을 북마크하고, 기본 제공 장소 데이터베이스에 지리 검색을 할 수 있었다.
이제는 커스텀 장소를 관리하고, 합의된 장소에 코멘트를 등록하고, 다른 사용자와 장소를 공유할 수 있다.

이 모든 기능은 균일 인터페이스를 노출하는 리소스를 통해 제공된다.
때때로 PUT이나 POST 요청에 어떤 표현을 실을 수 있는지 알려 주는 하이퍼미디어 폼(여기서는 XHTML 5 폼)으로 균일 인터페이스를 보완해야 한다.
그러나 대다수 요청은 GET일 것이고, GET은 언제나 같은 뜻이므로 하이퍼미디어 보완이 필요 없다.

클라이언트는 URI를 직접 구성해 원하는 리소스로 바로 가거나, 제공된 하이퍼미디어의 링크를 따라갈 수 있다.
서비스 루트(행성 목록)에서 링크를 따라가고 폼을 채우면 어디든 도달할 수 있다.
각 리소스는 꽤 단순하지만 서비스 전체는 매우 강력하다.
그 힘은 리소스의 다양성, 그들을 잇는 링크, 그리고 각 리소스가 개별적으로 주소 지정 가능하다는 사실에서 나온다.

리소스 지향 아키텍처(ROA)는 스스로에게 던져야 할 설계 질문 목록을 제시한다.
이전 장의 7단계 절차와 이 장의 확장된 9단계 절차가 그 질문들을 담고 있다.
다른 아키텍처처럼 ROA도 설계 제약을 두지만, 모든 설계 결정을 대신 내려 주지는 않는다.
데이터셋을 어떻게 리소스로 나누고, 어떤 표현을 정의하며, 하이퍼미디어로 어떻게 묶느냐에 따라 RESTful하고 리소스 지향적인 지도 서비스는 여러 방식으로 정의될 수 있다.

이 설계는 구현하지 않고 개념 설명을 위해 만든 것이므로 실제로 통하는지는 확신할 수 없다.
실제 서비스를 설계할 때는 구현 문제도 고려해야 한다.
어떤 리소스를 노출하고, 그것이 균일 인터페이스의 어느 부분에 응답하며, 어떤 URI를 고르고, 어떤 표현을 제공·수용하는지 등 모든 결정을 코드로 뒷받침해야 한다.
다음 장에서는 다른 데이터셋을 놓고 이 결정들을 다시 내리되, 이번에는 실제 구현으로 뒷받침한다.

## 핵심 정리

- 읽기 전용 서비스에 쓰기 기능을 더하려면, 5장의 7단계 절차에 “균일 인터페이스의 부분집합 노출”과 “클라이언트로부터 받을 표현 설계” 두 단계를 더한 9단계 절차를 따른다.
- 사용자 계정을 웹 애플리케이션 폼이 아니라 리소스로 다루면, 범용 클라이언트가 자동으로 계정을 생성할 수 있어 GPS 장치 같은 무인 클라이언트에도 자연스럽게 들어맞는다.
- 리소스 생성 시 URI를 클라이언트가 정하면 그 URI로 PUT을 보내고, 서버가 정하면 부모/팩토리 URI로 POST를 보낸다. 사용자 계정은 전자, 커스텀 장소는 후자의 예다.
- 표현은 서버가 상태를 전달하는 수단일 뿐 아니라 클라이언트가 상태 변경을 제안하는 수단이기도 하다. PUT에 실린 표현은 리소스의 새 상태에 대한 주장이다.
- 상태가 단순한 키-값 쌍이면 폼 인코딩(`application/x-www-form-urlencoded`)이 가장 단순한 표현 형식이며, URI 인코딩과 혼동하지 않도록 주의한다.
- 여기서 쓰는 POST는 오버로디드 POST가 아니라, 기존 리소스 “아래에” 하위 리소스를 만드는 정규 용법이다. HTTP 메서드가 부족하게 느껴지면 먼저 데이터셋을 더 잘게 나눠 리소스 종류를 늘려야 한다.
- 인증은 요청을 사용자에 묶는 문제, 인가는 그 사용자에게 요청을 허용할지 정하는 문제다. 이 서비스는 HTTP Basic 인증과 HTTPS를 쓰며, 실패 시 401과 `WWW-Authenticate` 헤더로 응답한다.
- 응답 코드로 결과를 정확히 전한다. 생성은 201과 `Location`, 수정은 200 또는 205, 위치 변경으로 URI가 바뀌면 301, 형식 오류는 415/400, 상태 충돌은 409, 비공개 리소스 은닉은 (403 대신) 404다.
- 좌표와 이름을 URI에 담으면 정보성은 높지만 그것들이 바뀔 때 URI가 깨진다. 끊임없이 움직이는 장소에는 바뀌지 않는 상태만으로 만든 퍼머링크를 함께 두는 편이 낫다.
- 하이퍼미디어(링크와 폼)는 구문은 전달하지만 의미는 전달하지 못한다. 클라이언트는 미리 프로그래밍되어야 하며, ROA는 설계 질문을 제시할 뿐 답을 대신 정해 주지 않는다.
