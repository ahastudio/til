# 5장 읽기 전용 리소스 지향 서비스 설계

《RESTful Web Services》(Leonard Richardson, Sam Ruby, O'Reilly 2007) 5장 정리.

## 개요

이 장은 앞에서 소개한 리소스 지향 아키텍처(ROA)를 실제 설계에 적용하는 첫 사례를 다룹니다.
목표는 네트워크 너머의 사람들에게 데이터를 노출하되, 클라이언트가 데이터를 수정하거나 추가하지는 못하는 읽기 전용(read-only) 서비스를 설계하는 것입니다.
GET(그리고 필요하면 HEAD)만 사용하는 서비스이며, 데이터를 검색하고 조회하는 데 집중합니다.

저자는 “그냥 감으로” 만드는 접근이 대개 RESTful하지 않은 REST-RPC 혼합형 서비스를 낳는다고 지적합니다.
반면 잘 설계된 웹 사이트는 의미가 분명한 이름의 리소스를 GET으로 접근할 수 있는 깔끔한 표현으로 제공하기 때문에, 의도치 않게라도 RESTful한 성질을 갖습니다.
정적 지도 타일을 URI만 바꿔 서로 다른 지역을 가리키게 하는 Google Maps의 타일 이미지가 그런 예입니다.

예제로 저자는 지도 정보를 제공하는 가상의 웹 서비스를 설계합니다.
Google Maps 같은 애플리케이션에서 영감을 받았지만, 사람의 임시적 사용이 아니라 프로그래머 친화적으로 지도 데이터를 조회하도록 만든 서비스입니다.
실제 구현은 하지 않고, 문제를 리소스 지향 관점에서 바라보는 법을 가르치는 것이 목적입니다.

## 리소스 설계

객체 지향 설계는 시스템을 명사(객체)로 나누고, RPC 스타일 설계는 동사(프로시저)로 나눕니다.
리소스는 “무언가(something)”이므로 저자는 리소스 설계에 객체 지향적 접근을 취하며, 이를 “극단적 객체 지향”이라 부릅니다.

핵심 제약은 균일 인터페이스(uniform interface)입니다.
프로그래밍 언어의 클래스는 임의의 이름을 가진 메서드를 얼마든지 노출할 수 있지만, HTTP 리소스는 최대 여섯 개의 HTTP 메서드로 이루어진 균일 인터페이스만 노출합니다.
이 메서드들이 허용하는 것은 생성(PUT 또는 POST), 수정(PUT), 읽기(GET), 삭제(DELETE)라는 기본 동작뿐입니다.
필요하면 POST를 오버로딩해 인터페이스를 확장할 수 있지만, 그럴 일은 자주 없어야 합니다.

이 제약 때문에 객체 지향 설계에서 동사로 취급하던 것을 리소스 지향 설계에서는 객체로 다뤄야 합니다.
예컨대 “publish(발행)”는 여섯 개 동작에 없으므로, 초안 Story를 라이브 사이트에 발행하는 별도의 RPC식 URI를 만드는 대신, 발행된 상태를 나타내는 새 표현을 Story에 PUT합니다.
그 결과 리소스는 새 URI에서 접근 가능해지고 더 이상 읽기에 인증이 필요 없어질 수 있습니다.

마찬가지로 Reader가 Column을 “구독(subscribe)”하는 관계는 균일 인터페이스에 없으므로, Reader와 Column의 관계를 나타내는 제3의 객체 Subscription을 두어야 합니다.
이 관계 객체는 균일 인터페이스의 적용을 받아 생성되고, (예를 들어 신디케이션 피드로) 조회되고, 삭제됩니다.
리소스 “클래스”에 새 메서드를 추가하고 싶어질 때마다, 대신 새로운 종류의 리소스를 정의해 문제를 해결합니다.

## 요구사항을 읽기 전용 리소스로 바꾸기

저자는 프로그램이 무엇을 해야 하는지 대략 정한 뒤 따를 수 있는 절차를 제시합니다.
이 절차는 HTTP 균일 인터페이스의 읽기 전용 부분집합(GET, 필요하면 HEAD)에 응답하는 리소스 집합을 만들어 냅니다.

1. 데이터 집합(data set)을 파악한다.
2. 데이터 집합을 리소스로 분할한다.
   이후 3~9단계는 리소스의 각 종류에 대해 반복한다.
3. URI로 리소스에 이름을 붙인다.
4. 균일 인터페이스의 부분집합을 노출한다.
5. 클라이언트로부터 받을 표현(들)을 설계한다.
6. 클라이언트에 제공할 표현(들)을 설계한다.
7. 하이퍼미디어 링크와 폼을 사용해 이 리소스를 기존 리소스에 통합한다.
8. 전형적인 흐름을 고려한다. 무엇이 일어나야 하는가?
9. 오류 조건을 고려한다. 무엇이 잘못될 수 있는가?

이 절차는 Joe Gregorio의 “How to create a REST Protocol”과 많은 공통점이 있습니다.
저자는 각 리소스마다 절차를 반복하는 대신, 모든 리소스를 한꺼번에 설계해 나가는 방식으로 서술합니다.

## 데이터 집합 파악하기

웹 서비스는 데이터 집합, 또는 최소한 그에 대한 구상에서 시작합니다.
저자의 가상 서비스는 온갖 투영법과 축척의 지도, 과거/현재/미래의 지도, 다른 행성과 개별 도시의 지도, 정치 지도/도로 지도/지형 지도/지질 지도 등을 제공합니다.

단, 표준 2차원 좌표계를 쓰는 지도만 다룹니다.
지도는 정확할 필요는 없지만 위도와 경도로 임의의 점을 지정할 수 있어야(addressable) 합니다.
따라서 가상의 장소를 그린 지도, 지하철 노선도처럼 지리를 임의로 왜곡한 지도, 경도를 정확히 측정하기 전에 만든 지도는 대부분 제외됩니다.

지도는 무수히 많은 점(위도와 경도)으로 이루어집니다.
하지만 모든 점을 데이터로 저장할 필요는 없습니다.
이미지 데이터와 몇 가지 기본 정보(지도 모서리의 위도·경도, 또는 행성 전체 지도라면 본초 자오선의 위치)만 있으면, 표준 지리 알고리즘으로 지도 위 임의의 점을 찾고 이동할 수 있습니다.

지도는 어떤 행성(planet)의 지도입니다.
저자는 편의상 “행성”이라 부르지만 위도·경도를 갖는 위성, 소행성 등 어떤 천체든 포함합니다.
지도뿐 아니라 그 지도가 나타내는 실제 행성 자체도 데이터 집합의 흥미로운 일부입니다.
특정 지점을 어떤 지도와도 무관하게 행성 위의 점으로 지칭할 수 있으면, “지구의 이 지점을 담은 지도가 무엇이 있는가” 같은 질의가 가능해집니다.
행성 전체를 하나의 리소스로 다루는 것이 과해 보일 수 있지만, 리소스의 전체 상태를 다 설명할 의무는 없습니다.
“지구”의 표현이 그저 지구 지도들의 목록이어도 괜찮습니다.
중요한 것은 클라이언트가 “정치 지도 말고 지구 자체에 대해 알려 달라”라고 말할 수 있고 서비스가 답할 수 있다는 점입니다.

행성 위의 어떤 점들은 다른 점보다 흥미롭습니다.
어떤 점은 도시나 분화구에 해당하고, 이런 점들이 곧 장소(place)입니다.
대부분의 장소에는 “San Francisco”, “Mount Whitney” 같은 합의된 이름이 있으므로, 데이터 집합은 장소 이름을 행성 위 점으로 매핑하는 정보를 포함합니다.
한 행성에 같은 이름의 장소가 여럿 있을 수 있으므로(지구의 수많은 “Joe's Diner”), 이름만으로 모호하면 위치를 더 정밀하게 지정해야 합니다.

도시, 국가, 강처럼 점이 아닌 장소는 단순화를 위해 잘 고른 대표 점 하나로 나타냅니다.
예를 들어 “미국”이라는 장소는 미국 지리적 중심 근처의 점으로 대표합니다.
(실제 GIS 프로그램은 이런 영역을 점들의 목록, 즉 선이나 다각형으로 표현합니다.)

모든 장소는 특정 유형(type)을 가집니다.
도시, 산, 온천, 선박의 현재 위치, 고오염 지역 등입니다.
유형이 다른 두 장소가 행성 위 같은 점에 해당할 수도 있습니다(오염 매립지 위에 지어진 집 등).

이 서비스는 이름, 유형, 설명으로 장소를 찾고, 적절한 지도에 표시하고, 근처 장소를 찾을 수 있습니다.
이름이 모호하면(“Springfield”) 주어진 범위 안의 해당 점들을 모두 나열하고, 특정 유형의 장소를 검색할 수도 있습니다(“네바다주 리노 근처의 오염 지역” 등).

### 일반 교훈

이는 어떤 분석에서든 표준적인 첫 단계입니다.
데이터 집합을 직접 고를 때도 있고, 이미 가진 데이터를 노출해야 할 때도 있습니다.
리소스로 노출하는 방법을 궁리하다 보면 이 단계로 되돌아오기도 합니다.
저자도 “행성 위의 점”과 “특정 지도 위의 점”을 구별해야 한다는 것을 깨닫기까지 설계 과정을 두세 번 거쳤습니다.

검색 결과(“지구의 Springfield들”)를 데이터 집합의 일부로 제시한 점에 주목해야 합니다.
RPC 지향 분석은 이를 클라이언트가 호출하는 동작(예: Google SOAP 서비스의 `doGoogleSearch`)으로 다룹니다.
반면 리소스 지향 분석에서는 데이터를 바라보는 방식 자체가 하나의 데이터입니다.
알고리즘의 출력을 리소스로 간주하면, 알고리즘 실행은 그 리소스에 GET을 보내는 것만큼 단순해집니다.

## 데이터 집합을 리소스로 분할하기

리소스는 하이퍼텍스트 링크의 대상이 될 만큼 흥미로운 모든 것이며, 이름으로 지칭될 수 있는 것에는 이름이 있어야 합니다.
웹 서비스가 흔히 노출하는 리소스는 세 종류입니다.

첫째, 애플리케이션의 특히 중요한 측면을 위한 미리 정의된 일회성(one-off) 리소스입니다.
다른 리소스들의 최상위 디렉터리가 여기 포함됩니다.
예를 들어 웹 사이트의 홈페이지, 또는 Amazon S3의 루트 URI(`https://s3.amazonaws.com/`)가 있습니다.
S3 루트는 버킷 목록을 제공하며, GET은 되지만 DELETE나 직접 수정은 안 됩니다.

둘째, 서비스가 노출하는 각 객체에 대응하는 리소스입니다.
한 서비스가 여러 종류의 객체를 노출할 수 있고, 대개 그 수는 많거나 무한합니다.
S3의 각 버킷과 각 객체가 그 예입니다.

셋째, 데이터 집합에 알고리즘을 적용한 결과를 나타내는 리소스입니다.
주로 질의 결과인 컬렉션 리소스가 여기 속합니다.
검색 엔진은 무한히 많은 알고리즘 리소스를 노출합니다.
예를 들어 Google은 `http://google.com/search?q=jellyfish` 형태의 URI를 “{query}에 관한 리소스 디렉터리”라는 알고리즘 리소스로 변환합니다.
S3도 접두어 검색(`https://s3.amazonaws.com/MyBucket?Prefix=movies/`)으로 알고리즘 리소스를 노출합니다.

이 분류를 지도 서비스에 적용하면 다음과 같습니다.
행성 목록을 나열하는 특별 리소스가 하나 필요합니다(S3의 버킷 목록과 유사).
각 행성도 리소스이고(“Venus”), 각 행성의 지도도 리소스입니다(“금성의 레이더 지도”).
행성 목록은 첫째 유형(하나뿐인 리소스)이며, 행성과 지도는 소수만 제공하므로 일회성 리소스입니다.

지금까지의 리소스 예:

```text
행성 목록
Mars
Earth
화성의 위성 지도
금성의 레이더 지도
지구의 지형 지도
지구의 정치 지도
```

하지만 지도 전체만 제공하면 거대한 정적 파일 호스팅에 불과합니다.
따라서 특정 점과 장소를 중심으로 한 지도의 일부도 제공해야 합니다.

행성 위의 모든 점은 잠재적으로 흥미로우므로 리소스가 되어야 합니다(둘째 유형, 무한히 많음).
행성 위 각 점은 하나 이상의 지도 위 점에 대응합니다.
지도를 위도·경도로 지정할 수 있게 한정한 덕분에, 행성 위 점을 지도 위 점으로 쉽게 옮길 수 있습니다.

좌표로 식별되는 리소스 예:

```text
지구의 24.9195N 17.821E
지구 정치 지도의 24.9195N 17.821E
화성의 24.9195N 17.821E
지구 지질 지도의 44N 0W
```

좌표 대신 이름으로 식별되는 장소도 제공합니다.
데이터베이스에는 크지만 유한한 수의 장소가 있고, 각 장소는 유형, 위도·경도, 그리고 부가 데이터를 가질 수 있습니다.

### 장소는 정말 리소스인가

장소가 “행성 위의 점” 리소스의 또 다른 이름에 불과한 것 아니냐는 의문이 생깁니다.
그러나 선박의 현재 위치를 나타내는 장소는 지금은 특정 점과 일치하지만 한 시간 뒤에는 다른 점과 일치합니다.
이 서비스에서 장소는 위치(location)가 아니라 위치를 가지는 것이며, 그것이 차지한 점과는 독립적인 생을 가집니다.

이는 4장에서 “버전 1.0.3”과 “최신 버전”이 같은 리소스를 가리키는가를 논의한 것과 유사합니다.
지금은 같은 데이터를 가리키더라도 서로 다른 두 가지이며, 각각 링크의 대상이 될 수 있습니다.
지구 위의 한 점에 “여기 보물이 묻혀 있다”라고 링크할 수도 있고, 같은 좌표의 “USS Mutiny”라는 장소에 “우리 배가 지금 여기 있다”라고 링크할 수도 있습니다.
따라서 장소는 그 자체로 둘째 유형의 리소스입니다.

이름은 모호할 수 있으므로(미국에 약 6,000개의 Springfield) 필요하면 대륙, 국가, 도시 등 범위 지정 정보를 덧붙입니다.

이름으로 식별되는 장소 예:

```text
금성의 Cleopatra 분화구
지구의 Ubehebe 분화구
1005 Gravenstein Highway North, Sebastopol, CA
O'Reilly Media, Inc. 본사
지구, 미국, 매사추세츠에 있는 Springfield라는 장소
```

여기까지는 미리 정의된 데이터의 상호작용만 다뤘습니다.
가장 흔한 알고리즘 리소스는 검색 결과 목록입니다.
클라이언트가 특정 이름이나 장소별 기준에 맞는 장소를 검색하게 하며, 검색 범위를 행성뿐 아니라 특정 영역으로 제한할 수 있습니다.

알고리즘 리소스 예:

```text
지구의 Springfield라는 장소들
화성의 지름 1km 이상 분화구들
콜로라도의 온천지들
인도네시아 근처의 유조선 또는 컨테이너선
Mount Rushmore 근처의 식당들
프랑스에서 인구 1,000명 미만인 마을들
```

저자는 온갖 리소스를 떠올릴 수 있지만, 모두 다섯 가지 기본 유형에 들어맞는다고 정리합니다(예제 5-1).

```text
1. 행성 목록
2. 이름으로 식별되는, 행성 위의 장소(행성 전체일 수도 있음)
3. 위도와 경도로 식별되는, 행성 위의 지리적 점
4. 어떤 검색 기준에 맞는, 행성 위 장소들의 목록
5. 특정 점을 중심으로 한, 행성의 지도
```

실제 서비스는 리소스를 더 정의할 수 있습니다.
예를 들어 길찾기(driving directions)는 두 장소 사이의 관계를 다루는 알고리즘 리소스로 노출할 수 있고, 그 표현은 도로 지도 위 점들을 참조하는 텍스트 지시 목록이 될 것입니다.

### 일반 교훈

RESTful 웹 서비스는 데이터와 알고리즘을 모두 리소스로 노출합니다.
대개 작게 시작해 무수한 잎 노드로 뻗어 나가는 계층 구조가 생깁니다.
행성 목록은 행성을 담고, 행성은 점과 장소를 담고, 그것들은 지도를 담습니다.

알고리즘을 리소스 집합으로 노출하는 데는 익숙해지는 시간이 필요합니다.
“지도에서 장소를 검색한다”라는 동작이 아니라, “검색 기준에 맞는 지도 위 장소들의 목록”이라는 그 동작의 결과로 사고해야 합니다.
설계가 HTTP 균일 인터페이스에 맞지 않으면 이 단계로 되돌아오게 됩니다.

## URI로 이름 짓기

리소스는 URI로 이름 붙입니다.
리소스 지향 서비스에서 URI는 모든 범위 지정(scoping) 정보를 담습니다.
저자는 서비스 루트를 `http://maps.example.com/`으로 두고, 편의상 상대 URI(`/Earth/political`)를 사용합니다.

가장 기본 리소스인 행성 목록은 루트 URI에 둡니다.
서비스 전체를 아우르므로 범위 지정 정보가 없습니다.

경험에서 나온 URI 설계의 세 가지 기본 규칙이 있습니다.

```text
1. 경로 변수로 계층을 인코딩한다: /parent/child
2. 계층이 없는 곳에 계층을 암시하지 않도록 경로 변수에 구두점을 넣는다: /parent/child1;child2
3. 알고리즘의 입력을 암시할 때는 쿼리 변수를 쓴다: /search?q=jellyfish&start=20
```

### 계층은 경로 변수로 인코딩

행성과 장소에는 “어떤 행성인가”라는 범위 지정 정보가 있고, 이는 자연스럽게 계층을 이룹니다.
슬래시로 계층을 표현합니다.

```text
http://maps.example.com/Venus
http://maps.example.com/Earth
http://maps.example.com/Mars
```

장소를 이름으로 식별할 때는 계층을 오른쪽으로 확장합니다.
경로 변수를 덧붙여 계층을 쉽게 확장할 수 있으면 좋은 URI 설계입니다.

```text
http://maps.example.com/Venus/Cleopatra
http://maps.example.com/Earth/France/Paris
http://maps.example.com/Earth/USA/Mount%20Rushmore
http://maps.example.com/Earth/1005%20Gravenstein%20Highway%20North,%20Sebastopol,%20CA%2095472
```

이 URI로 GET을 보내면 가변 개수의 인자를 받아 행성 위 장소를 원하는 정밀도로 찾는 원격 연산이 실행됩니다.
그러면서도 URI 자체는 북마크하고 캐시하고 다른 서비스에 입력으로 넘길 수 있는 평범한 웹 사이트 URI처럼 보입니다.

### 계층이 없다면 쉼표나 세미콜론

위도와 경도는 서로 묶여 있어 계층이 아닙니다.
`/Earth/24.9195/17.821`처럼 슬래시를 쓰면 경도가 위도의 하위 개념인 것처럼 보입니다.
대신 같은 계층 수준에서 구두점(쉼표 또는 세미콜론)으로 결합합니다.

```text
http://maps.example.com/Earth/24.9195,17.821
http://maps.example.com/Venus/3,-80
```

여기서는 한 경로 변수 안에 두 가지 범위 지정 정보(위도와 경도)를 넣습니다.
순서가 중요하면 쉼표를, 순서가 중요하지 않으면 세미콜론을 권합니다.
위도·경도는 순서가 바뀌면 다른 점이 되므로 쉼표를 씁니다(사람도 위도·경도를 쉼표로 구분하는 관례가 있습니다).
반대로 페인트 색을 섞는 서비스에서 `/color-blends/red;blue`와 `/color-blends/blue;red`는 같은 리소스이므로 세미콜론이 낫습니다.
세미콜론은 쿼리 변수 없이 URI에 키-값 쌍을 정의하는 매트릭스 URI(matrix URI) 개념으로 이어지며, WADL 같은 표준이 이를 지원합니다.

URI는 매우 길어질 수 있습니다.
HTTP 표준은 URI 길이를 제한하지 않지만 실제 서버·클라이언트는 제한합니다(Internet Explorer는 2,083자, Apache는 8KB).
범위 지정 정보가 아주 많이 필요한 리소스라면 일부를 HTTP 헤더로 받거나, 오버로딩된 POST를 써서 개체 본문(entity-body)에 담아야 할 수 있습니다.

### 지도 URI

지도의 URI에는 좌표(또는 장소 이름)에 더해 행성 이름과 지도 유형(위성 지도, 도로 지도 등)이 필요합니다.

```text
http://maps.example.com/radar/Venus
http://maps.example.com/radar/Venus/65.9,7.00
http://maps.example.com/geologic/Earth/43.9,-103.46
```

### 축척

`/satellite/Earth/41,-112`는 얼마나 상세한 지도인지 말하지 않습니다.
그래서 첫 경로 변수에 축척(scale)까지 담습니다.
`/satellite.10/Earth`은 매우 상세한 대축척 지도, `/satellite.1/Earth`은 매우 개략적인 소축척 지도이며, 기본값은 큰 축척(예: 2)으로 둡니다.

```text
/satellite.10/Earth/41,-112 : 1:24,000, 하이킹·탐사용 지도
/satellite.5/Earth/41,-112  : 1:250,000, 고속도로 지도 수준
/satellite.1/Earth/41,-112  : 1:51,969,000, 세계 지도 수준
```

축척은 지도의 픽셀 크기뿐 아니라 어떤 지형지물이 표시되는지도 좌우합니다.

숫자가 클수록 상세한 지도로 정한 이유는 URI 설계의 흔한 기법 때문입니다.
저자는 결정을 극단으로 과장해 보고, 일반화된 상황이 어떻게 작동해야 하는지 따진 뒤 다시 축소했습니다.
지도는 얼마든지 상세해질 수 있지만 개략화에는 한계가 있습니다.
가장 개략적인 지도를 1로 두면, 더 상세한 지도가 생길 때 11, 12로 자연스럽게 늘릴 수 있습니다.
반대로 했다면 0, -1 같은 이상한 URI를 붙여야 했을 것입니다.

### 알고리즘 리소스라면 쿼리 변수

대부분의 웹 애플리케이션은 상태를 쿼리 변수에 담지만, 다음 URI들은 쿼리 변수 없이 더 깔끔하게 쓸 수 있습니다.

```text
http://www.example.com/colorpair?color1=red&color2=blue  ->  /colorpair/red;blue
http://www.example.com/articles?start=20061201&end=20071201  ->  /articles/20061201-20071201
http://www.example.com/weblog?post=My-Opinion-About-Taxes  ->  /weblog/My-Opinion-About-Taxes
```

그러나 때로는 쿼리 변수가 적절합니다.
`http://www.google.com/search?q=jellyfish`를 경로 변수로 바꾸면 알고리즘 실행 결과가 아니라 디렉터리처럼 보입니다.
경로 변수는 계층을 순회하는 느낌, 쿼리 변수는 알고리즘에 인자를 넘기는 느낌을 줍니다.
“검색”은 알고리즘처럼 들립니다.
HTML 폼을 작성하면 입력이 쿼리 변수로 변환되는 경험이 이 인식을 강화합니다.
브라우저는 기본 URL에 쿼리 변수를 붙일 줄은 알지만, `.../search/{q}`처럼 일반 URI에 변수를 대입할 줄은 모릅니다.

이 선례 때문에 많은 REST-RPC 혼합형 서비스가 경로 변수가 더 자연스러운 곳에도 쿼리 변수를 씁니다.
그 결과 URI가 함수 호출처럼 보입니다(예: `http://api.flickr.com/services/rest/?method=flickr.photos.search&tags=penguin` 대 사람용 `http://flickr.com/photos/tags/penguin`).
쿼리 변수가 든 URI는 프록시, 캐시, 크롤러 같은 도구에서 무시되기 쉽습니다.
예를 들어 Google Web Accelerator는 쿼리 변수가 든 URI를 미리 가져오지 않습니다.
GET을 남용하는 잘못 설계된 애플리케이션이 그런 URI를 노출하기 때문이며, 외부 도구는 이 서비스가 GET을 남용하지 않는다는 것을 알 방법이 없습니다.

하지만 검색 결과 목록은 실제로 알고리즘을 실행한 결과이므로 쿼리 변수가 적절합니다.
저자는 검색 인터페이스를 단순화해 자연어로 찾고자 하는 것을 지정하는 `show` 쿼리 변수 하나만 둡니다.
서버가 `show` 값을 해석해 결과에 넣을 장소를 결정합니다.

```text
http://maps.example.com/Earth?show=Springfield
http://maps.example.com/Mars?show=craters+bigger+than+1km
http://maps.example.com/Earth/Indonesia?show=oil+tankers&show=container+ships
http://maps.example.com/Earth/USA/Mount%20Rushmore?show=diners
http://maps.example.com/Earth/24.9195;17.821?show=arsenic
```

이 URI들은 특정 지도가 아니라 행성을 검색한다는 점에 주의합니다.

### URI 요약

서비스가 지원하는 URI는 결국 세 가지 기본 형태입니다.

```text
행성 목록: /
행성 또는 행성 위의 장소: /{planet}/[{scoping-information}/][{place-name}]
  ({scoping-information}은 장소 이름 계층 또는 위도/경도 쌍이고, show 쿼리를 붙여 근처 장소를 검색할 수 있음)
행성의 지도 또는 지도 위의 점: /{map-type}{scale}/{planet}/[{scoping-information}]
  ({scoping-information}은 항상 위도/경도 쌍, {scale}은 점과 숫자)
```

## 표현 설계

이제 클라이언트가 리소스를 요청할 때 어떤 데이터를 어떤 형식으로 보낼지 정합니다.
RESTful 표현의 목표는 두 가지입니다.
리소스의 현재 상태를 전달하는 것, 그리고 가능한 새로운 애플리케이션·리소스 상태로 링크하는 것입니다.

표현의 주된 목적은 리소스 상태를 전달하는 것입니다.
“리소스 상태”란 그 리소스에 관한 정보로, 이 서비스에서는 지형이 어떻게 보이는지, 분화구의 좌표가 어디인지, 근처 식당은 무엇인지 등입니다.

표현의 다른 임무는 상태 전이 수단(levers of state)을 제공하는 것입니다.
표현은 “가까운” 리소스, 즉 가능한 새 애플리케이션 상태로 링크해야 하며, 이 목표가 바로 연결성(connectedness)입니다.
웹을 서핑할 때 URI를 계속 입력하지 않고 링크와 폼을 따라가는 것과 같습니다.
다만 프로그램은 문서를 보고 스스로 따라갈 링크를 고를 수 없으므로, 표현에는 각 링크가 어디로 가는지 알려 주는 기계가 읽을 수 있는 신호가 있어야 합니다.
이 장의 리소스는 모두 읽기 전용이므로 애플리케이션 상태 전이 수단만 노출합니다.

### 행성 목록 표현하기

행성 목록은 표현 형식을 고르는 문제를 소개하기 좋은 예입니다.
평문(plain text)은 단순하지만 전용 파서가 필요합니다(예제 5-2).
JSON은 평문의 단순함에 약간의 구조를 더합니다(예제 5-3).
그러나 평문도 JSON도 일반적으로 하이퍼미디어 형식으로 여겨지지 않습니다.

또 다른 선택지는 커스텀 XML 어휘입니다(예제 5-4).
XML은 문서 표현에 훌륭하지만, 커스텀 어휘를 새로 만들어야 할 일은 드뭅니다.
링크 목록에는 이미 Atom이라는 XML 어휘가 있습니다.
다만 Atom은 발행된 텍스트 목록을 위한 것이라 이 맥락에 잘 맞지 않습니다(행성의 “저자”나 “최종 수정일”은 의미가 없습니다).

저자가 실제로 선택한 형식은 XHTML입니다(예제 5-5).

```xml
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.1//EN"
    "http://www.w3.org/TR/xhtml11/DTD/xhtml11.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en">
  <head>
    <title>Planet List</title>
  </head>
  <body>
    <ul class="planets">
      <li><a href="/Earth">Earth</a></li>
      <li><a href="/Venus">Venus</a></li>
    </ul>
  </body>
</html>
```

사람의 웹과 연관된 XHTML을 웹 서비스 형식으로 쓰는 것이 이상해 보일 수 있지만, XHTML은 일반적인 마크업 문제를 많이 해결해 주고 이미 익숙합니다.
사람이 읽을 수 있으면서도 XML처럼 자동 처리할 수 있고 확장도 가능합니다.
`class` 속성으로 일반 XHTML 목록을 “planets” 목록으로 만든 것은 마크업에 의미를 더하는 XHTML 마이크로포맷(microformat)의 간단한 예입니다.

### 지도와 지도 위 점 표현하기

지도를 요청하면 PNG나 SVG 같은 이미지를 보내는 것이 자연스럽지만, 최대 축척을 제외하면 이미지가 거대해집니다.
초고대역폭 클라이언트라면 큰 파일을 원하겠지만, 대개는 사람이 브라우징할 작은 지도를 원하는 클라이언트일 것입니다.

따라서 43N 71W 중심의 하이킹 지도를 요청받으면 전 세계 지도를 보내지 않고, 그 점을 중심으로 한 지도의 일부와 초점을 옮길 수 있는 내비게이션 링크를 함께 보냅니다.
이는 온라인 지도 사이트의 작동 방식과 비슷합니다.
Google Maps는 지도를 한 변 256픽셀의 정사각형 “타일” 이미지로 나누고, 브라우저가 필요한 타일을 가져와 이어 붙여 탐색 가능한 지도를 만듭니다.
Google은 위도·경도를 대체로 무시하고 지구를 256픽셀 타일 격자로 나눠 줌 레벨마다(총 10회) 정적 이미지를 생성합니다.

저자는 교육 목적상 더 단순한 방식을 택합니다.
어떤 축척, 어떤 지점이든 256×256 이미지를 동적으로 생성해 제공한다고 가정합니다.
클라이언트가 지도 위 점을 요청하면, 그 점을 중심으로 한 작은 지도 이미지(타일 하나)로의 링크를 담은 하이퍼미디어 파일을 보냅니다.
이 파일에는 인접한 점들로의 링크가 들어 있어, 클라이언트가 링크를 따라 여러 타일을 이어 붙여 원하는 크기의 지도를 만들 수 있습니다.

`http://maps.example.com/road/Earth`의 표현 예(예제 5-6)는 XHTML로 리소스 상태(지도 위 특정 점의 정보)를 전달하고 인접한 점들로 링크합니다.

```xml
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.1//EN"
    "http://www.w3.org/TR/xhtml11/DTD/xhtml11.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en">
  <head>
    <title>Road Map of Earth</title>
  </head>
  <body>
    <img class="map" src="/road.2/Earth/images/37.0,-95.png" alt="Map tile"/>
    <a class="map_nav" href="46.0518,-95.8">North</a>
    <a class="map_nav" href="41.3776,-89.7698">Northeast</a>
    <a class="map_nav" href="36.4642,-84.5187">East</a>
    <a class="map_nav" href="32.3513,-90.4459">Southeast</a>
    <a class="zoom_in" href="/road.1/Earth/37.0;-95.8">Zoom out</a>
    <a class="zoom_out" href="/road.3/Earth/37.0;-95.8">Zoom in</a>
  </body>
</html>
```

“지구의 도로 지도”를 요청하면 감당할 수 없는 거대 이미지 대신, 다른 여러 리소스로 링크하는 작은 XHTML 문서를 받습니다.
사람은 문서를 보면 뜻을 알지만 프로그램은 알 수 없으므로, 표현에는 `zoom_in`, `Northeast` 같은 의미 단서(semantic cue)를 채워 넣습니다.
웹 서비스는 특정 구조의 표현을 제공하겠다는 약속으로 작동하며, 프로그래머는 그 단서를 읽는 클라이언트를 작성합니다.

### 지도 타일 표현하기

도로 지도 표현에서 가장 중요한 링크는 IMG 태그의 `src`가 가리키는 URI(`.../road/Earth.8/images/37.0;-95.png`)입니다.
이는 “지구 도로 지도에서 37°N 95.8°W를 중심으로 한 이미지”라는 새 리소스이며, 그 표현은 256×256 이미지입니다(그림 5-1, 5-2).
이 이미지는 예제 5-6 같은 XHTML 파일과는 구별됩니다.
XHTML 파일이 이 이미지를 참조하고 인접 점들로 링크합니다.

핵심은 타일 시스템의 정확한 설정이나 URI 형식이 아니라, 표현에 무엇을 담느냐입니다.
`/road/Earth`는 “지구의 도로 지도”라는 리소스이지만, 서비스는 미국 네 개 주도 채 못 담는 256×256 타일을 참조하는 XHTML 문서를 보냅니다.

표현은 리소스 상태를 전달하되 전체 상태를 전달할 필요는 없고 일부만 전달하면 됩니다.
다만 이 표현은 임의로 고른 점을 북쪽, 동쪽 등 인접 점들로 연결하므로, 클라이언트가 링크를 따라 더 큰 그림을 이어 붙일 수 있습니다.
그런 의미에서 이 표현은 도로 지도의 모든 상태를 담고 있으며, 링크를 따라가면 원하는 만큼 상태를 얻을 수 있습니다.
이 서비스를 위해 Google Maps 애플리케이션처럼 동작하는 Ajax 클라이언트를 작성할 수 있습니다.

### 행성과 그 밖의 장소 표현하기

행성 목록에서 지구의 도로 지도까지 가려면, 목록에서 “Earth”를 눌러 `/Earth`에 GET을 보내 지구의 표현을 받고, 거기서 지도 링크를 따라갑니다.
행성 표현은 행성에 관한 유용한 정보와 지도 링크들을 담습니다(예제 5-7).

```xml
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.1//EN"
    "http://www.w3.org/TR/xhtml11/DTD/xhtml11.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en">
  <head><title>Earth</title></head>
  <body>
    <dl class="place">
      <dt>name</dt> <dd>Earth</dd>
      <dt>maps</dt>
      <dd>
        <ul class="maps">
          <li><a class="map" href="/road/Earth">Road</a></li>
          <li><a class="map" href="/satellite/Earth">Satellite</a></li>
        </ul>
      </dd>
      <dt>type</dt> <dd>planet</dd>
      <dt>description</dt>
      <dd>Third planet from Sol. ...</dd>
    </dl>
  </body>
</html>
```

장소는 키-값 쌍의 목록으로 표현하며, HTML의 `dl` 태그를 씁니다.
여기서 행성 지구는 San Francisco나 Egypt처럼 이름을 가진 하나의 장소입니다.
행성을 장소로 표현한 이유는, 클라이언트가 장소를 파싱하는 코드로 행성도 파싱할 수 있게 하기 위해서입니다.

Mount Rushmore의 표현(예제 5-8)은 지도 이미지를 직접 담는 대신 이미 정의한 리소스, 즉 그 좌표의 지도들로 링크합니다.
행성 표현과 장소 표현의 유일한 차이는 장소에는 정의 목록에 위치(location)가 있고 행성에는 없다는 점뿐이며, 같은 코드로 둘 다 파싱할 수 있습니다.

이 서비스에는 전용 클라이언트가 필요 없고 평범한 브라우저로도 쓸 수 있습니다.
홈페이지에서 링크를 눌러 행성을 고르고, “Road”를 눌러 도로 지도를 보고, “North”나 “Zoom out”을 눌러 지도를 탐색합니다.
저자는 이 책에서 하나만 얻는다면 “웹 서비스는 로봇을 위한 웹 사이트”라는 생각이 자연스러워지는 것이길 바란다고 말합니다.
모든 RESTful 리소스 지향 웹 서비스는 표준 브라우저로 쓸 수 없더라도 웹의 본성을 공유합니다.

지도 위 점의 표현(예제 5-9)은 전적으로 링크로만 이루어집니다.
그 점을 중심으로 한 지도들로의 링크, 그 점에 있는 장소들로의 링크로 구성되며, 자체 상태는 없이 더 흥미로운 리소스로 가는 관문 역할만 합니다.
또한 근처 장소를 검색하는 폼(`show`)도 포함합니다.

### 검색 결과 목록 표현하기

검색 결과는 검색된 장소와 연관되므로, “Mount Rushmore 근처 식당”의 표현은 “Mount Rushmore”로 링크해야 합니다.
장소를 검색하면 결과도 장소이므로(Springfield라는 도시들, 식당들, 고비소 지역들), 검색 결과 목록은 결국 이미 정의한 리소스(이름 있는 장소)로의 링크 목록입니다.

`/Earth/USA?show=Springfield`의 표현 예(예제 5-10)는 검색된 장소(“미국”)로의 링크와 각 결과 장소로의 링크로 거의 전부 이루어지며, 각 링크에는 어느 Springfield인지 유일하게 식별할 만큼의 범위 지정 정보가 담깁니다.

```xml
<ul>
  <li><a class="place" href="/Earth/USA/IL/Springfield">Springfield, IL</a></li>
  <li><a class="place" href="/Earth/USA/MA/Springfield">Springfield, MA</a></li>
  <li><a class="place" href="/Earth/USA/MO/Springfield">Springfield, MO</a></li>
</ul>
```

Google Maps처럼 검색 결과를 대축척 지도에 마커로 표시하는 클라이언트도 작성할 수 있습니다.
먼저 `/Earth/USA`로부터 타일 주소를 얻어 내비게이션 링크로 지도를 이어 붙이고, 그다음 각 검색 결과 링크를 따라가 해당 Springfield의 위도·경도를 얻어 마커를 찍습니다.
링크를 많이 따라가야 하지만 표현이 단순하고 전이 규칙도 단순합니다.
데이터를 수많은 리소스에 펼쳐 두고 링크를 따라 원하는 리소스를 찾게 하는 이 전략은 사람의 웹에서도, 프로그래밍 가능한 웹에서도 통합니다.

## 리소스를 서로 연결하기

모든 리소스를 병렬로 설계했으므로 이미 서로 링크로 가득 차 있습니다.
클라이언트는 홈페이지(행성 목록)에서 행성으로, 지도로, 다시 내비게이션·줌 링크로 이동할 수 있습니다.

하지만 검색 결과 목록에는 어떻게 도달할까요?
검색 결과 URI 규칙을 정했지만, 클라이언트가 규칙을 따라 직접 URI를 만들어야 한다면 서비스는 잘 연결된 것이 아닙니다.
`/Earth/USA/Mount%20Rushmore`에서 `...?show=diners`로 가고 싶지만, “diners”만 링크하는 것은 무의미합니다.
클라이언트가 검색할 수 있는 무한히 많은 것 중 하나일 뿐이기 때문입니다.

HTML은 이 문제를 폼(form)으로 해결합니다.
표현에 적절한 폼을 넣으면 쿼리 문자열에 변수를 어떻게 대입할지 클라이언트에 알려 줄 수 있고, 폼 하나가 특정 패턴을 따르는 무한히 많은 URI를 나타냅니다.
저자는 장소 표현에 검색 폼(예제 5-11)을 추가합니다.

```xml
<form id="searchPlace" method="get" action="">
  <p>
    Show places, features, or businesses:
    <input id="term" repeat="template" name="show" />
    <input class="submit" />
  </p>
</form>
```

사람은 이 폼을 텍스트 상자와 버튼으로 보고 “diners”를 입력해 `/Earth/USA/Mount%20Rushmore?show=diners`로 이동합니다.
자동 클라이언트도 같은 방식으로, `searchPlace` 폼 정의를 URI 구성 지침으로 삼아 동일한 URI를 만듭니다.

`repeat=“template”`은 XHTML 5의 기능입니다(집필 당시 설계 중).
이 서비스는 `show`에 임의 개수의 값을 받는데(`?show=diners&show=arsenic&...`), XHTML 4 폼은 고정된 수의 텍스트 상자만 보여 줄 수 있습니다.
XHTML 5의 반복 모델(repetition model)은 무한히 긴 페이지를 쓰지 않고도 임의 개수의 텍스트 상자를 표현하게 해 줍니다.

이제 서비스는 더 잘 연결되었습니다(그림 5-4).
루트(`/`)에서 지구(`/Earth`)를 고르고, 폼으로 “Mount Rushmore”를 검색해 결과 링크(`/Earth/USA/Mount%20Rushmore`)를 따라가고, 그 표현의 폼에 “diners”를 입력해 근처 식당에 도달합니다.
검색 기능은 클라이언트가 직접 URI를 만들 필요를 없앨 뿐 아니라, 늘 모호한 사람의 장소 이름을 정규 리소스 URI로 해석해 줍니다(“Mount Rushmore National Monument”로 검색해도 `/Earth/USA/Mount%20Rushmore`가 나오도록).

## HTTP 응답

이제 응답 자체를 고려합니다.
표현은 개체 본문에 들어가지만, 아직 응답 코드와 HTTP 헤더, 그리고 오류 조건을 정하지 않았습니다.

### 무엇이 일어나야 하는가

읽기 전용 리소스의 전형적 흐름은 단순합니다.
클라이언트가 URI에 GET을 보내면 서버가 200(“OK”) 같은 응답 코드, HTTP 헤더, 표현을 돌려줍니다.
HEAD 요청도 같지만 표현은 생략됩니다.

이 서비스의 주된 응답 헤더는 표현의 미디어 타입을 알려 주는 `Content-Type`입니다.
지도 표현과 검색 결과는 `application/xhtml+xml`, 지도 이미지는 `image/png`입니다.
저자는 요청 헤더를 자주 쓰지 않고, 요청 헤더 대신 URI를 조정해 표현을 바꾸는 편을 선호합니다.
다만 조건부 GET을 가능케 하는 헤더들은 모든 HTTP 클라이언트와 서비스에 기본으로 있어야 한다고 봅니다.

### 조건부 HTTP GET

조건부 GET은 클라이언트와 서버의 시간·대역폭을 절약합니다.
두 응답 헤더(`Last-Modified`, `ETag`)와 두 요청 헤더(`If-Modified-Since`, `If-None-Match`)로 구현됩니다.

인기 있는 리소스(“미국 도로 지도” 등)는 한 클라이언트가 수명 동안 여러 번 요청하지만, 지도 데이터는 자주 바뀌지 않습니다.
그래서 두 번째 이후 요청은 대개 낭비이며, 클라이언트는 첫 요청의 표현을 재사용하면 됩니다.

이를 위해 서버는 표현을 제공할 때마다 데이터가 마지막으로 바뀐 시각을 `Last-Modified`에 담습니다.

```http
Last-Modified: Thu, 30 Nov 2006 20:00:51 GMT
```

클라이언트는 이 값을 저장했다가 다음 요청 때 `If-Modified-Since`에 실어 보냅니다.

```http
GET /road/Earth HTTP/1.1
Host: maps.example.com
If-Modified-Since: Thu, 30 Nov 2006 20:00:51 GMT
```

데이터가 그사이 바뀌었으면 서버는 200(“OK”)과 새 표현을 보내고, 바뀌지 않았으면 304(“Not Modified”)를 보내며 개체 본문을 생략합니다.
그러면 클라이언트는 캐시된 표현을 재사용해도 된다는 것을 알게 되어, 모두가 시간과 대역폭을 아낍니다.

### 무엇이 잘못될 수 있는가

이행할 수 없는 요청도 대비해야 합니다.
오류 조건에서는 3xx, 4xx, 5xx 범위의 응답 코드를 보내고, 개체 본문이 있다면 그것은 요청 리소스의 표현이 아니라 오류를 설명하는 문서입니다.

이 지도 애플리케이션의 대표적 오류 조건은 다음과 같습니다.

존재하지 않는 지도(`/road/Saturn`)를 요청하면 무엇을 원하는지는 알지만 데이터가 없는 경우이므로 404(“Not Found”)가 적절합니다.

데이터베이스에 없는 장소 이름을 쓰면 404를 반환하거나, 검색 엔진에 돌려 좋은 후보가 나오면 그 장소로 리다이렉트하며 돕는 편이 낫습니다.
이때 응답 코드는 303(“See Other”)이고 `Location` 헤더에 클라이언트가 “정말로” 원했을 리소스의 URI를 담습니다.
그 URI를 따를지는 클라이언트의 책임입니다.
검색해도 못 찾으면 404를 반환합니다.

논리적으로 불가능한 위도·경도(예: `500,-181`)를 쓰면 404도 가능하지만 400(“Bad Request”)이 더 정확합니다.
존재하지 않는 이름 “Tanhoidfog”는 지금 없을 뿐 나중에 생길 수 있어 요청 자체가 잘못은 아닙니다(어떤 장소가 실제로 존재하는지 확인하는 것도 이 서비스의 쓸모입니다).
반면 좌표 `500,-181`은 기하학 법칙상 존재할 수 없고 최소한의 지식만 있어도 요청 전에 알 수 있으므로, 요청을 한 클라이언트의 잘못입니다.

검색 결과가 없는 것은 오류가 아닙니다.
다른 검색과 똑같이 200(“OK”)과 표현을 보내되, 표현에는 검색된 장소로의 링크와 빈 결과 목록을 담습니다.

서버가 요청 폭주로 처리할 수 없으면 503(“Service Unavailable”)을 보내거나 아예 요청을 거부합니다.
서버가 정상 작동하지 않으면(데이터 손상, 버그, 하드웨어 장애 등) 500(“Internal Server Error”)을 보냅니다.
5xx 계열은 클라이언트가 할 수 있는 것이 없어 답답한 응답이며, 많은 웹 프레임워크가 서버 측 예외 발생 시 자동으로 500을 보냅니다.

## 결론

이 장에서 저자는 클라이언트가 큰 사전 투자 없이 쓸 수 있을 만큼 단순하면서도, 수많은 유용한 프로그램의 기반이 될 만큼 쓸모 있는 지도 웹 서비스 설계를 완성했습니다.
이 서비스는 웹의 철학에 매우 충실해 브라우저로도 쓸 수 있으며, RESTful하고 리소스 지향적이며, 주소 지정 가능하고(addressable), 무상태(stateless)이고, 잘 연결되어(well connected) 있습니다.

다만 이 서비스는 읽기 전용입니다.
클라이언트가 데이터에 대한 왕성한 수요만 있을 뿐 서버에 내놓을 것은 없다고 가정합니다.
많은 기존 웹 서비스가 이렇게 작동하지만 읽기 전용 서비스는 절반의 이야기일 뿐이며, 다음 장에서는 클라이언트가 HTTP 균일 인터페이스로 자신만의 새 리소스를 생성하는 법을 다룹니다.

## 핵심 정리

리소스 지향 설계는 “극단적 객체 지향”이며, 시스템을 동사가 아니라 리소스(명사)로 나눕니다.
객체 지향 설계에서 동사로 보이던 것(구독, 발행, 검색)도 리소스로 바꿔야 하며, 메서드를 추가하고 싶을 때는 새 리소스를 정의해 해결합니다.

읽기 전용 서비스 설계 절차는 다음 순서를 따릅니다.
데이터 집합 파악 → 리소스로 분할 → URI로 이름 짓기 → 표현 설계 → 리소스 연결 → HTTP 응답 고려(정상 흐름과 오류 조건).

웹 서비스가 흔히 노출하는 리소스는 세 종류입니다.
미리 정의된 일회성 리소스(홈페이지, 최상위 디렉터리), 각 객체에 대응하는 리소스, 알고리즘 적용 결과(주로 검색 결과)를 나타내는 리소스입니다.
검색 같은 알고리즘은 “동작”이 아니라 “그 동작의 결과”로 사고해 리소스로 노출합니다.

URI 설계의 세 규칙은 다음과 같습니다.
계층은 경로 변수(`/parent/child`)로 인코딩하고, 계층이 아닌 것은 구두점(순서가 중요하면 쉼표, 아니면 세미콜론)으로 결합하며, 알고리즘 입력은 쿼리 변수로 표현합니다.
URI는 모든 범위 지정 정보를 담아야 하며, 북마크·캐시·재사용이 가능한 평범한 웹 URI처럼 보여야 합니다.

표현은 리소스의 (전체가 아닌 일부) 상태를 전달하고, 동시에 인접 리소스로의 링크(상태 전이 수단)를 제공해 연결성을 확보해야 합니다.
저자는 XHTML을 표현 형식으로 택했는데, 사람도 브라우저로 읽을 수 있고 기계도 자동 처리할 수 있으며 마이크로포맷으로 의미를 덧붙일 수 있기 때문입니다.

무한히 많은 검색 URI는 표현에 일일이 링크할 수 없으므로 HTML 폼으로 연결합니다.
폼 하나가 특정 패턴의 무한한 URI를 나타내며, 사람과 자동 클라이언트 모두 이를 URI 구성 지침으로 사용합니다.

HTTP 응답에서 정상 흐름은 200(GET)이며, `Content-Type`으로 미디어 타입을 알립니다.
조건부 GET(`Last-Modified`/`If-Modified-Since`, `ETag`/`If-None-Match`)으로 변하지 않은 데이터에는 304를 반환해 시간과 대역폭을 아낍니다.
오류는 상황에 맞게 구분합니다(없는 리소스는 404, 도울 수 있으면 303 리다이렉트, 논리적으로 불가능한 요청은 400, 결과 없는 검색은 오류가 아닌 200, 서버 과부하는 503, 서버 오류는 500).
