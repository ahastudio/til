# 8장 REST와 ROA 베스트 프랙티스

《RESTful Web Services》(Leonard Richardson, Sam Ruby, O'Reilly 2007) 8장 정리.

## 개요

이 장은 앞선 이론 장과 실습 장에서 흩어져 있던 핵심 아이디어를 한자리에 모으고, 설명 없이 지나쳤던 빈틈을 채운다.
저자는 조건부 GET, HTTP 기본 인증, Amazon 커스텀 인증 클라이언트 등을 구현만 하고 원리를 충분히 설명하지 않았음을 인정한다.
앞부분은 REST와 리소스 지향 아키텍처(ROA)의 주요 개념을 요약하고, 뒷부분은 HTTP의 구체적 기능과 리소스 설계의 까다로운 사례를 다룬다.
9장의 서비스 구성 요소와 함께, 이 두 장은 기술과 설계를 결정할 때 참고할 실무 레퍼런스 역할을 한다.

웹 서비스와 웹 사이트의 유일한 차이는 청중(사람 대신 미리 프로그래밍된 클라이언트)과 몇 가지 클라이언트 능력뿐이다.
둘 다 HTTP, URI, 그리고 보통 XML에 기반한 리소스 지향 설계에서 이득을 얻는다.

## 리소스 지향의 기본기

애플리케이션이 관리하는 흥미로운 모든 것은 리소스로 노출되어야 한다.
리소스는 클라이언트가 링크하고 싶어 할 만한 무엇이든 될 수 있다. 예술 작품, 정보 조각, 물리적 객체, 개념, 또는 다른 리소스에 대한 참조 묶음까지 포함한다.

URI는 리소스의 이름이다.
모든 리소스는 최소 하나의 이름을 가져야 하며, 이름은 가능한 한 적게, 그리고 모두 의미 있게 지어야 한다.

클라이언트는 리소스에 직접 접근할 수 없다.
웹 서비스는 리소스의 표현(representation)을 제공한다. 표현이란 리소스에 대한 정보를 담은 특정 데이터 형식의 문서다.
정적 사이트에서는 리소스가 곧 디스크의 파일이라 리소스와 표현의 구분이 다소 학술적이지만, 리소스가 데이터베이스의 행, 물리 객체, 추상 개념, 진행 중인 실세계 이벤트일 때 그 구분의 중요성이 커진다.

리소스에 대한 모든 접근은 HTTP의 균일한 인터페이스를 통해 이뤄진다.
네 개의 기본 동사(GET, POST, PUT, DELETE)와 두 개의 보조 동사(HEAD, OPTIONS)가 그것이다.
복잡성은 표현, 노출하는 리소스의 다양성, 리소스 간 링크에 두고, 접근 방법 자체에는 두지 말라.

## 일반적인 ROA 절차

6장에서 재수록한, 문제 공간을 RESTful 리소스로 나누는 범용 절차다.
이 절차는 REST와 ROA의 제약만 고려하며, 사용하는 프레임워크가 추가 제약을 걸 수 있다(12장에서 Ruby on Rails용 변형을 제시한다).

1. 데이터 집합을 파악한다.
2. 데이터 집합을 리소스로 나눈다.
   이후 3~9단계는 각 종류의 리소스에 대해 반복한다.
3. URI로 리소스에 이름을 붙인다.
4. 균일한 인터페이스의 부분집합을 노출한다.
5. 클라이언트로부터 받을 표현을 설계한다.
6. 클라이언트에 제공할 표현을 설계한다.
7. 하이퍼미디어 링크와 폼을 사용해 이 리소스를 기존 리소스에 통합한다.
8. 전형적인 진행 흐름을 고려한다. 무엇이 일어나야 하는가. Atom 발행 프로토콜 같은 표준 제어 흐름이 도움이 된다(9장).
9. 오류 상황을 고려한다. 무엇이 잘못될 수 있는가. 여기서도 표준 제어 흐름이 도움이 된다.

## 주소 지정 가능성(Addressability)

서비스가 데이터 집합의 흥미로운 측면을 리소스로 노출하면 그 서비스는 주소 지정이 가능하다.
모든 리소스는 자신만의 고유한 URI를 갖는다. URI는 “Universal Resource Identifier”의 약자다.
대부분의 RESTful 서비스는 무한한 수의 URI를 노출하고, 대부분의 RPC 스타일 서비스는 극소수의 URI만, 흔히 단 하나만 노출한다.

하나의 URI는 결코 둘 이상의 리소스를 가리켜서는 안 된다.
나아가 저자는 리소스의 각 표현마다 자체 URI를 주기를 권한다. URI는 다른 서비스로 전달되거나 입력으로 쓰이는 일이 잦기 때문이다.

예를 들어 보도자료를 `/releases/104`에 노출하고 영어와 스페인어 버전, 각각의 HTML과 평문 버전이 있다고 하자.
클라이언트는 `Accept-Language`로 언어를, `Accept`로 형식을 고를 수 있어야 한다.
동시에 각 표현에 별도 URI도 주는 것이 좋다. 예를 들어 `/releases/104.en`, `/releases/104.es.html`, `/releases/104.txt` 같은 식이다.

클라이언트가 표현별 URI 중 하나를 요청하면, 서버는 `Content-Location` 응답 헤더를 정규 위치인 `/releases/104`로 설정해야 한다.
이로써 클라이언트는 언어나 형식과 무관하게 “보도자료” 리소스를 가리키는 정규 URI를 알 수 있다.

7장 북마킹 서비스에서는 일반 XML 표현을 `/v1/users/leonardr/bookmarks.xml`에, Atom 표현을 `/v1/users/leonardr/bookmarks.atom`에, 정규 URI를 `/v1/users/leonardr/bookmarks`에 노출했다.
Accept 헤더로 구분하는 방법과 URI를 조정하는 방법 모두 RESTful하지만, 리소스와 표현을 함께 지정하는 URI가 클라이언트 사이에서 더 잘 전달된다.

클라이언트가 HTTP 요청 헤더로 정보를 보내는 것은 괜찮다. 다만 서버가 그것을 리소스나 표현을 선택하는 유일한 수단으로 삼지 않아야 한다.
헤더에는 인증 자격 증명처럼 민감한 정보나 클라이언트마다 다른 정보를 담을 수도 있지만, 헤더가 표현·리소스 선택의 유일한 도구가 되어서는 안 된다.

## 상태와 무상태성(Statelessness)

RESTful 서비스에는 두 종류의 상태가 있다.
리소스 상태는 리소스에 관한 정보이고, 애플리케이션 상태는 클라이언트가 애플리케이션을 거쳐 온 경로에 관한 정보다.
리소스 상태는 서버에 남아 있고 표현의 형태로만 클라이언트에 전달된다.
애플리케이션 상태는 클라이언트에 머무르다가, 리소스를 생성·수정·삭제하는 데 쓰일 때 POST·PUT·DELETE 요청의 일부로 서버에 전송되어 리소스 상태가 된다.

서버가 애플리케이션 상태를 전혀 저장하지 않으면 그 서비스는 “무상태”다.
무상태 애플리케이션에서 서버는 각 요청을 고립된 것으로, 현재 리소스 상태에 비추어 처리한다.
애플리케이션 상태를 고려하길 원한다면 클라이언트가 요청의 일부로 제출해야 하며, 여기에는 매 요청마다 함께 보내는 인증 자격 증명도 포함된다.

클라이언트는 PUT이나 POST 요청으로 표현을 보내 리소스 상태를 조작한다(DELETE도 같은 방식이나 표현이 없다).
서버는 클라이언트의 GET 요청에 표현으로 응답해 클라이언트 상태를 조작한다. 여기서 “Representational State Transfer”라는 이름이 나온다.

## 연결성(Connectedness)

서버는 표현 안에 링크와 폼을 넣어 클라이언트를 한 애플리케이션 상태에서 다른 상태로 안내할 수 있다.
저자는 링크와 폼이 리소스를 서로 잇는다는 뜻에서 이를 연결성이라 부른다. Fielding의 논문은 이를 “애플리케이션 상태의 엔진으로서의 하이퍼미디어”라 부른다.

잘 연결된 서비스에서 클라이언트는 링크를 따라가고 폼을 채우며 애플리케이션을 통과하는 경로를 만든다.
연결되지 않은 서비스에서는 클라이언트가 방문하려는 모든 URI를 미리 정해진 규칙으로 직접 구성해야 한다.
현재 사람 웹은 매우 잘 연결되어 있지만, 프로그래밍 가능한 웹은 그렇지 못하다.

서버는 표현에 폼을 넣어 클라이언트를 한 리소스 상태에서 다른 상태로 안내할 수도 있다.
폼은 어떤 표현이 받아들여지는지 힌트를 주어, PUT·POST로 리소스 상태를 수정하는 과정을 안내한다.

링크와 폼은 상태의 레버, 즉 클라이언트가 미래에 애플리케이션·리소스 상태를 바꾸기 위해 할 수 있는 요청을 드러낸다.
물론 상태의 레버는 표현 형식이 링크나 폼을 지원할 때만 노출할 수 있다. XHTML 같은 하이퍼미디어 형식이 좋고, XHTML이나 WADL을 품을 수 있는 XML 형식도 좋다.

## 균일한 인터페이스(Uniform Interface)

클라이언트와 리소스 사이의 모든 상호작용은 몇 가지 기본 HTTP 메서드를 통해 중개된다.
어떤 리소스든 이 메서드의 일부 또는 전부를 노출하며, 한 메서드는 그것을 지원하는 모든 리소스에서 같은 일을 한다.

GET은 리소스에 관한 정보를 요청하며, 정보는 헤더 묶음과 표현으로 전달된다. 클라이언트는 GET에 표현을 함께 보내지 않는다.
HEAD는 GET과 같지만 헤더만 응답하고 표현은 생략한다.
PUT은 리소스 상태에 대한 단언이다. 보통 표현을 함께 보내며, 서버는 표현이 말하는 상태에 맞게 리소스를 생성하거나 변경하려 한다. 표현 없는 PUT은 특정 URI에 리소스가 존재해야 한다는 단언일 뿐이다.
DELETE는 리소스가 더 이상 존재하면 안 된다는 단언이다. 표현을 함께 보내지 않는다.
POST는 기존 리소스로부터 새 리소스를 생성하려는 시도다. 기존 리소스는 자료구조상 부모일 수도, 다른 리소스를 만들기 위한 “팩토리” 리소스일 수도 있다. 함께 보내는 표현이 새 리소스의 초기 상태를 기술한다. PUT처럼 표현이 없어도 된다.
POST는 새 리소스를 만들지 않고 기존 리소스 상태에 덧붙이는 데도 쓸 수 있다.
OPTIONS는 상태의 레버를 발견하려는 시도, 즉 리소스가 균일한 인터페이스의 어느 부분집합을 지원하는지 알아내려는 시도지만 거의 쓰이지 않는다.

HTTP에 메서드나 기능을 더하고 싶어지면 POST를 오버로딩할 수 있지만, 대개는 새로운 종류의 리소스가 필요한 것이다.
트랜잭션 지원을 더하고 싶다면 트랜잭션을 생성·갱신·삭제할 수 있는 리소스로 노출하는 편이 낫다.

### 안전성과 멱등성

GET과 HEAD는 안전(safe)해야 한다. 즉 이 요청을 하는 클라이언트는 서버 상태 변경을 요청하는 것이 아니다.
서버가 로깅이나 조회 수 증가처럼 스스로 상태를 바꿀 수는 있어도, 그 변경의 책임을 클라이언트에 지워서는 안 된다.
특정 URI에 GET을 몇 번 하든, 아무 요청도 하지 않은 것과 실질적으로 같은 효과여야 한다.

PUT과 DELETE는 멱등(idempotent)해야 한다. 같은 URI에 여러 번 요청해도 한 번 요청한 것과 같은 효과여야 한다.
흔한 문제는 “값을 5만큼 증가”처럼 상대적으로 상태를 설정하는 PUT이다. 이런 PUT을 10번 하는 것은 한 번 하는 것과 크게 다르다. PUT은 리소스 상태를 특정 값으로 설정해야 한다.

안전한 GET과 HEAD는 자동으로 멱등하기도 하다.
리소스 생성을 위한 POST는 안전하지도 멱등하지도 않다. 오버로딩된 POST는 무엇이든 할 수 있어 그 여부를 클라이언트가 알 수 없다.
9장의 POST Once Exactly로 POST를 멱등하게 만들 수 있다.

### 새 리소스: PUT 대 POST

새 리소스 생성은 PUT, POST, 또는 둘 다로 노출할 수 있다.
다만 클라이언트가 PUT으로 리소스를 만들려면 새 리소스의 최종 URI를 스스로 계산할 수 있어야 한다.
Amazon S3에서 버킷 경로는 `/{bucket-name}`이고 이름은 클라이언트가 정하므로, 해당 URI를 구성해 PUT하면 버킷을 만들 수 있다.
반면 전형적인 Rails 서비스의 URI는 `/{database-table-name}/{database-ID}` 꼴이며, ID는 레코드가 저장되기 전에는 알 수 없다.
그래서 클라이언트는 `/{database-table-name}` 팩토리 리소스에 POST하고, 서버가 새 리소스의 URI를 정한다.

### POST 오버로딩

POST는 새 리소스 생성과 덧붙이기 외에, 리소스를 작은 RPC 스타일 메시지 처리기로 바꾸는 데도 쓸 수 있다.
오버로딩된 POST를 받은 리소스는 들어온 표현에서 추가 메서드 정보를 훑어 어떤 작업이든 수행한다.
대부분의 웹 애플리케이션이 이렇게 동작하며, XML-RPC와 SOAP/WSDL 서비스도 오버로딩된 POST 위에서 돈다.
저자는 오버로딩된 POST가 균일한 인터페이스를 망치므로 강하게 권하지 않는다. 복잡한 객체나 프로세스는 각자 URI를 주어 리소스로 노출하라.

논란의 여지가 없는 두 가지 용도가 있다.
첫째, PUT·DELETE를 지원하지 않는 웹 브라우저 같은 클라이언트를 위해 균일한 인터페이스를 흉내 내는 것.
둘째, URI 최대 길이 제한을 우회하는 것이다. HTTP 표준은 URI 길이에 제한을 두지 않지만 클라이언트와 서버가 자체 제한을 둔다(Apache는 8KB를 넘는 URI에 응답하지 않는다).
`http://www.example.com/numbers/1111111`에 GET할 수 없다면, `http://www.example.com/numbers?_method=GET`에 POST하고 엔티티 본문에 `1111111`을 담으면 된다.

PUT과 DELETE를 아예 쓰지 않기로 하고, 안전한 연산은 GET으로, 나머지는 모두 오버로딩된 POST로 노출하는 것도 완전히 RESTful하다.
이는 저자의 ROA는 위반하지만 더 느슨한 REST 규칙에는 부합한다. REST는 균일한 인터페이스를 쓰라고 할 뿐, 어떤 것인지는 말하지 않는다.

균일한 인터페이스가 정말 맞지 않는다면 POST를 오버로딩하되, 리소스 지향 설계는 잃지 말라.
`/weblog/myweblog/rebuild-index`처럼 URI에 메서드 정보를 넣는 대신, 기존 리소스(`/weblog/myweblog`)에 오버로딩된 POST를 노출하고 들어온 표현에서 메서드 정보(`method=rebuild-index`)를 받으라.
경험칙으로, 오버로딩된 POST를 쓰면서 같은 URI에 GET과 POST를 함께 노출하지 않는다면, 아마 리소스가 아니라 RPC 스타일 서비스를 만들고 있는 것이다.

## 이 원칙들이 중요한 이유

REST와 ROA의 원칙은 임의의 제약이 아니라, 리소스 지향 서비스에 경쟁 우위를 주는 단순화 가정이다.
RESTful 리소스 지향 서비스는 RPC 스타일보다 더 단순하고, 쓰기 쉽고, 상호운용성이 높으며, 조합하기 쉽다.

주소 지정 가능성이 중요한 이유는, 서비스의 흥미로운 모든 측면이 외부에서 즉시 접근 가능해지기 때문이다.
모든 측면이 컴퓨터를 쓸 줄 아는 사람에게 익숙한 형식의 고유 식별자, 즉 URI를 갖는다.
이 식별자는 북마크되고, 애플리케이션 사이에서 전달되며, 실제 리소스의 대역으로 쓰인다. 이는 남들이 상상하지 못한 방식으로 서비스를 매시업할 수 있게 한다.
4장에서 저자는 URI를 스프레드시트의 셀 주소, 명령줄 셸의 파일 경로에 비유했다.

무상태성이 중요한 이유는, 이것이 모든 단순화 가정을 압도하는 가정이기 때문이다.
각 요청이 그 요청을 이해하는 데 필요한 애플리케이션 상태를 모두 담으므로, 서버에는 아무것도 남지 않고 이전 요청에 의존하지도 않는다.
그래서 확장이 쉽다. 한 서버로 부족하면 로드 밸런서를 두고 서버를 늘리면 되고, 요청을 무작위나 라운드로빈으로 아무 서버에나 배정해도 된다.
“세션”을 위한 서버 어피니티나 서버 간 메모리 공유가 필요 없다. 병목이 리소스 상태 접근으로 옮겨갈 때까지 웹 서버를 계속 추가할 수 있다.
무상태 애플리케이션은 더 신뢰할 수 있다. 요청이 타임아웃되어도 세션이 이상한 상태에 빠질 걱정 없이 다시 보낼 수 있다.
“서버에 클라이언트 상태를 두고 시스템을 확장하려니 아프다”는 환자에게 의사는 “그러면 그러지 마세요”라고 답한다. 그것이 무상태성의 핵심이다.

균일한 인터페이스가 중요한 이유는, 리소스가 무엇인지는 몰라도 어떻게 다룰지는 알 수 있기 때문이다.
`http://www.example.com/myresource`가 무엇인지는 몰라도, GET으로 가져오고 DELETE로 지우고 PUT으로 상태를 대략 바꾸고 POST로 하위 리소스를 만드는 법은 안다.
모든 리소스가 기본적으로 같은 방식으로 동작하고 범용 클라이언트로 접근할 수 있다는 점이 웹 성공의 큰 부분이다.
이론상 어떤 연산이 지원되는지는 OPTIONS로 알아낼 수 있지만, 현재는 아무도 OPTIONS를 지원하지 않는다.
균일한 인터페이스가 부과하는 제약(GET·HEAD의 안전성, PUT·DELETE의 멱등성)은 HTTP를 더 신뢰할 수 있게 한다. 요청이 전달되지 않았으면 부작용 없이 다시 보내면 된다(POST만 예외).
균일한 인터페이스의 힘은 특정 메서드가 아니라 균일함 자체에 있다. 사람 웹은 안전한 연산에 GET, 나머지에 POST를 쓰는 다른 균일한 인터페이스로도 잘 돌아간다.
ROA의 균일한 인터페이스에서 벗어나면(사람 웹이나 WebDAV의 인터페이스를 택하면) 커뮤니티를 바꾸는 것이다. 어떤 서비스와의 호환성을 다른 서비스와의 호환성을 대가로 얻는다.

연결성이 중요한 이유는, 링크가 없으면 웹 페이지가 다음 페이지의 URI를 만드는 영어 설명만 주는 것과 같기 때문이다.
오늘날 대부분의 RESTful 서비스가 그렇게 동작해, 사람 대상 사이트보다 더 취약하고, PageRank 같은 웹의 창발적 속성이 프로그래밍 가능한 웹에서는 일어나지 않는다.
Amazon S3는 주소 지정 가능하고 무상태이며 균일한 인터페이스를 지키지만 전혀 연결되어 있지 않다. 버킷 목록 표현은 버킷 이름만 줄 뿐 버킷으로 링크하지 않고, 버킷 표현도 객체로 링크하지 않는다.
S3 클라이언트는 링크를 따라가지 못하고 URI 구성 규칙을 내면화해야 한다. 그 규칙은 서비스 자체가 아니라 기술 문서에 있다.

우리는 대체로 사람 웹보다 웹 서비스에 덜 기대한다. 프로그래밍 가능한 웹은 범용 클라이언트가 아니라 맞춤 클라이언트로 경험하며, 이들은 URI 구성 규칙을 심어둘 수 있기 때문이다.
S3가 연결성 부족을 감당할 수 있는 것은 URI 구성 규칙이 셋뿐이고, 리소스 간 관계가 단순하고 안정적이기 때문이다. “포함한다”는 가장 단순한 관계다.
클라이언트가 리소스 간 관계를 미리 알고 있다면, 그 관계만 전달하는 링크는 중복이다.
그러나 관계가 복잡하거나 불안정할 때, 연결성 부족이 낳는 문제는 잘 드러나지 않는다. 이 문제는 URI 구성 규칙이 바뀌지 않아도 클라이언트를 깨뜨릴 수 있다.

5장 지도 서비스의 표현은 대부분 기술적으로 불필요한 링크와 폼으로 가득했다.
줌 레벨을 바꾸는 링크나 지구의 지도 목록 링크는 규칙으로 대체할 수 있어, S3처럼 대역폭을 아끼려 링크를 생략할 여지가 있었다.
그러나 지도 타일 사이를 오가는 내비게이션 링크는 다르다. 위도·경도, 줌 레벨별 축척, 행성의 크기와 모양을 알아야 URI를 만들 수 있어, 관계가 단순한 규칙으로 표현하기엔 너무 복잡해진다. 여기서 연결성이 매우 중요해진다.

연결성이 값진 또 다른 이유는, 시간에 따라 변하는 관계를 클라이언트가 다룰 수 있게 하기 때문이다.
링크는 URI 구성 규칙을 감출 뿐 아니라, 리소스들이 서로 어떻게 관계 맺는지의 규칙을 담는다.

무서운 예: 더 정확하지만 축척이 살짝 다른 새 지도 데이터를 받았다고 하자.
위도·경도는 그대로라 모든 지점의 URI는 여전히 유효하다. 만약 클라이언트가 위도·경도를 이미지 URI로 바꾸는 법을 “이미 안다”면, 축척이 바뀌면서 인접했던 타일 사이에 틈이 생겨 지도가 어긋나 보인다.
반면 서버가 제공한 내비게이션 링크를 따라 인접 타일을 찾는 클라이언트는 새 축척에 자동으로 적응한다.
URI를 하나도 바꾸지 않은 합리적인 변경이 URI를 스스로 구성하는 클라이언트를 깨뜨린 것이다. 바뀐 것은 리소스가 아니라 리소스 간 관계, 즉 애플리케이션을 한 상태에서 다른 상태로 이끄는 규칙이었다.
그래서 리소스를 서로 연결하는 것이 중요하다. 초기 URI 구성을 클라이언트에 맡기는 것은 괜찮지만, 한 URI에서 다른 URI로 이동해야 한다면 적절한 링크를 제공해야 한다.

## 리소스 설계

서비스가 노출하는 “무언가” 하나마다 리소스 하나가 필요하다.
리소스에는 세 종류가 있다.

첫째, 서비스 홈페이지나 정적 링크 목록 같은 미리 정의된 일회성 리소스. 객체 지향 시스템의 클래스나 데이터베이스 테이블처럼 몇 개 없는 것에 대응한다.
둘째, 개별 데이터 항목에 대응하는 크고(어쩌면 무한한) 리소스 집합. 객체 지향 시스템의 객체나 데이터베이스 행에 대응한다.
셋째, 알고리즘의 가능한 출력에 대응하는 크고(대개 무한한) 리소스 집합. 검색 결과 목록이나 필터링된 목록이 여기 속한다.

리소스 설계에는 균일한 인터페이스에 맞지 않아 보이는 까다로운 경우가 있다.
그 답은 거의 언제나, 문제를 일으키는 그것을 새로운 리소스 집합으로 노출하는 것이다. 이 리소스들은 더 추상적이어도 괜찮다. 리소스는 무엇이든 될 수 있기 때문이다.

### 리소스 간 관계

Alice와 Bob이 리소스이고 둘이 결혼한다고 하자.
Alice의 URI에 PUT하고 Bob의 URI에 PUT하는 방식은 두 단계여서 만족스럽지 않다. 한쪽만 PUT하고 잊으면 Alice는 Bob과 결혼했지만 그 반대는 아닌 상태가 된다.
대신 결혼이라는 관계 자체를 세 번째 리소스로 다뤄야 한다.
클라이언트는 “marriage” URI에 PUT하거나 “registrar” URI에 POST해 두 사람을 결혼시킨다. 표현에는 Alice와 Bob의 URI 링크가 담긴다.
서버는 결혼 가능 규칙을 적용해 오류를 보내거나 결혼을 나타내는 새 리소스를 만든다. 이 리소스는 다른 리소스가 링크할 수 있고 균일한 인터페이스에 응답한다.

### 비동기 연산

HTTP는 동기 요청-응답 모델이다. 클라이언트는 소켓을 열어 요청하고 서버가 응답할 때까지 소켓을 열어둔다.
모든 연산을 그 시간 안에 끝낼 수는 없다. 몇 시간, 며칠 걸리는 연산은 타임아웃되며, 그렇게 오래 소켓을 열어두고 싶은 사람도 없다.
해법은 연산을 둘 이상의 동기 요청으로 쪼개는 것이다. 첫 요청이 연산을 시작하고, 이후 요청으로 상태를 확인한다. 비결은 상태 코드 202(“Accepted”)다.

작업 큐 서비스를 예로 들면, 클라이언트가 요청을 보내면 서버는 새 작업을 만들어 큐 끝에 넣고 곧바로 응답한다.

```http
202 Accepted
Location: http://jobs.example.com/queue/job11a4f9
```

서버는 새 “job” 리소스에 충돌 없는 URI를 부여한다. 클라이언트는 이 URI에 GET해 진행 상태를 확인하고, 완료되면 결과가 이 리소스의 표현으로 제공된다.
다 읽고 나면 클라이언트는 job 리소스를 DELETE할 수 있고, 미리 DELETE해 연산을 취소할 수도 있다.

한 가지 주의점이 있다. 비동기 연산을 시작하는 요청은 매번 서버가 새 리소스를 만들게 하므로 안전하지도 멱등하지도 않다.
따라서 GET, DELETE, 보통 PUT으로는 비동기 연산을 시작할 수 없고, 균일한 인터페이스를 지키면서 쓸 수 있는 메서드는 POST뿐이다.
그래서 대개 작업 큐 같은 단일 리소스를 노출하고, 클라이언트가 거기에 POST해 하위 리소스인 작업을 만든다.

### 배치 연산

때로 클라이언트는 한 번에 여러 리소스를 다뤄야 한다. 검색 결과 목록이 일종의 배치 GET이다.
대량 생성이 필요하면, 들어온 표현이 리소스 하나가 아니라 여러 개를 기술하고 한 요청으로 여럿을 만드는 팩토리 리소스를 노출할 수 있다.
한 번에 여러 리소스를 수정·삭제하려면, URI가 다른 URI 경로나 이스케이프된 URI 전체를 품을 수 있다는 점을 활용한다.
예를 들어 `http://www.example.com/sets/resource1;subdir/resource2`는 두 리소스의 집합을 가리킬 수 있다. 이 “집합” 리소스에 DELETE하면 둘 다 삭제되고, 각 리소스의 표현을 담아 PUT하면 한 요청으로 둘 다 수정된다.

배치 연산의 응답 상태 코드가 문제다. 한 PUT은 성공하고 다른 하나는 실패할 수 있다.
한 방법은 배치 연산을 여러 비동기 작업으로 쪼개 202를 보내고 개별 작업 상태를 확인하게 하는 것이다.
또는 WebDAV 확장이 만든 207(“Multi-Status”) 상태 코드를 쓸 수 있다. 207은 클라이언트에게 엔티티 본문에서 200, 500 같은 개별 상태 코드 목록을 확인하라고 알린다.
이는 오버로딩된 POST가 메서드 정보를 본문으로 옮기듯 정보를 상태 코드에서 본문으로 옮기므로 이상적이진 않지만, 연산마다 상태 코드가 다를 수 있어 선택지가 제한된다.

### 트랜잭션

일부 서비스는 여러 리소스에 걸친 연산을 노출한다. 고전적 예가 당좌예금에서 저축예금으로의 송금이다.
간단한 트랜잭션은 배치 연산이나 오버로딩된 POST로 노출할 수 있지만, 트랜잭션 자체를 리소스로 노출하는 방법도 있다.
당좌예금 `/accounts/checking/11`과 저축예금 `/accounts/savings/55`가 각각 잔액 $200이고 $50을 옮긴다고 하자.

먼저 트랜잭션 팩토리 리소스에 POST해 트랜잭션을 만든다.

```http
POST /transactions/account-transfer HTTP/1.1
Host: example.com
```

응답으로 새 트랜잭션 리소스의 URI를 받는다.

```http
201 Created
Location: /transactions/account-transfer/11a5
```

당좌예금의 줄어든 잔액을 트랜잭션 관점의 리소스에 PUT한다.

```http
PUT /transactions/account-transfer/11a5/accounts/checking/11 HTTP/1.1
Host: example.com

balance=150
```

저축예금의 늘어난 잔액을 PUT한다.

```http
PUT /transactions/account-transfer/11a5/accounts/savings/55 HTTP/1.1
Host: example.com

balance=250
```

이 시점까지는 트랜잭션 리소스를 DELETE해 롤백할 수 있다. 대신 커밋한다.

```http
PUT /transactions/account-transfer/11a5 HTTP/1.1
Host: example.com

committed=true
```

이 최종 PUT에서 서버는 트랜잭션이 리소스 상태에 불일치를 만들지 않는지(돈이 생기거나 사라지지 않는지, 무단 이체가 아닌지) 확인하고 결과를 응답한다.
커밋 후에도 트랜잭션은 주소 지정 가능한 리소스로서, 감사 추적을 위해 영구 보관되고 다른 리소스가 링크할 수 있다.

RESTful 트랜잭션의 어려움은, 모든 HTTP 요청이 하나의 리소스에 대한 자기 완결적 연산이어야 하는데 트랜잭션 중에는 리소스 상태가 유동적이라는 점이다.
트랜잭션 안에서 본 당좌예금 잔액은 $150이지만 밖에서 본 잔액은 여전히 $200이다. 마치 두 개의 다른 리소스 같다.
이 해법은 실제로 그것을 두 리소스로 제시한다. 실제 당좌예금 `/accounts/checking/11`과, 한 트랜잭션이 본 당좌예금 `/transactions/account-transfer/11a5/accounts/checking/11`이다.
구현은 대개 들어오는 요청을 트랜잭션에 딸린 작업 큐로 쌓아두었다가, 커밋 시 데이터베이스 트랜잭션을 시작해 적용하고 커밋을 시도하는 식이다.
RESTful 트랜잭션은 구현이 더 복잡하지만, 트랜잭션이 리소스의 이점을 얻는다. 주소 지정이 가능하고, 연산이 투명하며, 보관하거나 나중에 링크할 수 있다.

### 의심스러우면 리소스로 만들라

여기서 보인 기법들은 트랜잭션이나 비동기 연산을 다루는 공식적인 RESTful 방법이 아니라 저자가 생각해낸 최선일 뿐이다.
더 큰 요점은 “무엇이든 리소스가 될 수 있다”는 말 그대로다.
설계를 어렵게 하는 개념이 있으면 대개 그것을 새로운 종류의 리소스로 노출해 ROA에 맞출 수 있다. 성능 때문에 균일한 인터페이스를 위반해야 한다면 언제나 오버로딩된 POST가 있다.

## URI 설계

URI는 의미 있고 잘 구조화되어야 한다. 가능한 한 클라이언트가 접근하려는 리소스의 URI를 직접 구성할 수 있어야 한다.
이는 애플리케이션의 “표면적”을 넓혀, 중간 리소스를 거치지 않고 어떤 상태로든 바로 갈 수 있게 한다. (다만 관계 전달에는 링크가 가장 신뢰할 만하다.)

계층이나 방향 그래프의 경로를 나눌 때는 경로 변수를 쓴다.
`/weblogs/myweblog/entries/100`은 일반에서 구체로 간다. 각 경로 변수는 어떤 의미로 이전 변수 “안에” 있다.

같은 계층 수준의 여러 데이터를 나눌 때는 구두점을 쓴다.
순서가 중요하면 쉼표를 쓴다(위도·경도의 `/Earth/37.0,-95.2`). 순서가 상관없으면 세미콜론을 쓴다(`/color-blends/red;blue`).

쿼리 변수는 알고리즘에 넣는 인자를 나타내거나 다른 두 기법이 실패할 때만 쓴다.
두 URI가 쿼리 변수만 다르다면, 같은 기저 알고리즘에 대한 서로 다른 입력 집합임을 암시한다.

URI는 리소스를 가리키는 것이지 리소스에 대한 연산을 가리키는 것이 아니다.
따라서 URI에 연산 이름을 넣는 것은 거의 부적절하다. `/object/do-operation` 같은 URI는 RPC 스타일로 빠질 위험이 있다.
아무도 do-operation에 링크하고 싶어 하지 않는다. 연산은 균일한 인터페이스로 노출하거나 필요하면 오버로딩된 POST로 노출하되, URI는 객체를 가리키게 하라.

## 나가는 표현(Outgoing Representations)

제공하는 문서 대부분은 리소스의 표현이지만 일부는 오류 상황이다.
HTTP 상태 코드로 클라이언트가 문서를 어떻게 봐야 하는지 전달하라. 오류가 있으면 400(“Bad Request”) 등 적절한 오류 코드를 설정해야 한다. 그러지 않으면 클라이언트가 오류 메시지를 요청한 리소스의 표현으로 오해할 수 있다.

상태 코드가 문서의 용도를 말한다면, `Content-Type` 응답 헤더는 문서의 형식을 말한다. 이 헤더가 없으면 클라이언트는 문서를 파싱하거나 처리할 방법을 모른다.

표현은 사람이 읽을 수 있되 컴퓨터 지향적이어야 한다.
프로그래밍 가능한 웹의 주된 일은 컴퓨터 프로그램이 조작할 정보를 제공하는 것이다. 계기 판독값을 노출한다면 초점은 사람이 읽을 그래프가 아니라 원시 데이터 접근에 두어야 한다. 그래프는 편의로 제공할 수 있어도 주된 표현이 되어서는 안 된다.

표현은 유용해야 한다. 즉 아무도 쓰지 않을 데이터가 아니라 흥미로운 데이터를 노출해야 한다.
하나의 표현은 하나의 필요를 충족하는 데 필요한 관련 정보를 모두 담아야 하며, 클라이언트가 한 작업을 위해 같은 리소스의 표현을 여러 번 가져오게 해서는 안 된다.
다만 클라이언트가 데이터의 어느 부분을 쓸지 예측하기 어려우므로, 의심스러우면 리소스의 모든 상태를 노출하라. Rails 서비스가 기본으로 데이터베이스 행을 완전히 기술하는 표현을 제공하는 것이 그 예다.
리소스의 표현은 그 상태와 함께 바뀌어야 한다.

## 들어오는 표현(Incoming Representations)

들어오는 표현에는 크게 두 종류가 있다.
단순한 표현은 대개 키-값 쌍이다(`username=leonardr` 같은 “이 상태를 저 값으로 설정”). 폼 인코딩이 가장 널리 쓰인다.
리소스 상태가 키-값 쌍으로 표현하기엔 너무 복잡하면, 서비스는 나가는 표현과 같은 형식으로 들어오는 표현을 받아야 한다.
클라이언트가 표현을 가져와 수정한 뒤 원래 자리에 PUT할 수 있어야 하기 때문이다. 나가는 표현과 들어오는 표현에 서로 다른 복잡한 형식을 쓰게 하는 것은 말이 되지 않는다.

## 서비스 버저닝

웹 사이트는 대대적으로 개편해도 큰 문제가 없다. 청중이 사람이라 페이지를 보고 뜻을 이해해 변화에 잘 적응하기 때문이다.
웹의 URI는 바뀌지 않아야 하지만 실제로는 늘 바뀌고, 그 결과 외부 링크와 북마크가 깨지는 심각한 문제가 생긴다. 그래서 대개 대개편 후 한동안 옛 버전을 남겨둔다.

컴퓨터 프로그램은 변화에 적응하는 데 형편없어, 사람(프로그래머)이 대신 적응해줘야 한다.
그래서 연결성이 중요하고, Atom과 XHTML 같은 확장 가능한 표현 형식이 유용하다.
클라이언트의 선택지가 하이퍼미디어로 기술되면 프로그래머는 구현 세부가 아니라 서비스의 고수준 의미에 집중할 수 있다.
리소스 구현, URI, 표현 자체가 바뀌어도 의미 단서가 그대로면 옛 클라이언트는 계속 동작한다.

5장 지도 서비스는 완전히 연결되었고 확장 가능한 형식으로 표현을 제공했다. 표현이 링크로 가득했고 링크에 `zoom_in`, `coordinates` 같은 의미 내용이 붙어 있었다.
6장에서 리소스와 기능을 더했지만 의미 단서가 그대로여서 5장 기준으로 작성한 클라이언트도 여전히 동작했다(HTTP에서 HTTPS로 바뀐 프로토콜 변경만 예외).
반면 7장 북마킹 서비스는 잘 연결되어 있지 않아, 영어 산문으로 설명한 URI 구성 규칙에 의존했다. 그 규칙을 바꾸면 클라이언트가 깨진다.
이런 경우 옛 리소스와 새 리소스가 나란히 동작하는 전환기를 두어야 한다. 가장 단순한 방법은 URI에 버전 정보를 넣는 것으로, 7장에서 `/users/leonardr` 대신 `/v1/users/leonardr`로 한 것이 그 예다.

잘 연결된 서비스도 버저닝이 필요할 수 있다. 재작성이 표현의 의미를 바꾸면 옛 의미 단서를 이해하던 클라이언트조차 깨진다. 의심스러우면 버저닝하라.
버전은 소프트웨어 릴리스 번호를 매기는 어떤 방식이든 쓸 수 있다(`v1`, `1.4.0`, `2007-05-22`).
가장 단순한 방법은 버전을 첫 경로 변수로 두는 것이다(`/v1/resource` 대 `/v2/resource`). 조금 더 멋을 부리면 호스트명에 버전을 넣을 수 있다(`v1.service.example.com` 대 `v2.service.example.com`).
이상적으로는 아무도 옛 버전을 쓰지 않을 때까지 남겨두겠지만, 이는 모든 클라이언트를 통제하는 사설 환경에서만 가능하다.
현실적으로는 아키텍처 변경으로 옛 리소스 노출이 불가능해지거나, 옛 버전 유지 비용이 사용자 이전을 적극 돕는 비용을 넘어설 때까지 남겨두어야 한다.

## 영구 URI 대 읽기 좋은 URI

저자는 URI와 그것이 식별하는 리소스 사이에 직관적 대응이 있어야 한다고 본다.
REST는 이를 금하지도 요구하지도 않는다. REST는 리소스에 이름이 있어야 한다고 할 뿐, 이름이 무언가를 뜻해야 한다고는 하지 않는다.
그래도 URI와 리소스를 대응시키는 것은 클라이언트를 위해 할 수 있는 가장 유용한 일 중 하나다. 사용성 전문가 Jakob Nielsen은 “URL as UI” 에세이에서 이를 권한다.
URI가 충분히 직관적이면 그것이 서비스 사용자 인터페이스의 일부가 되어, 적절한 URI를 구성하거나 URI를 변형하며 리소스를 서핑할 수 있다.

문제가 있다. 의미 있는 URI는 리소스를 말하므로 리소스 상태의 일부를 담는데, 그 상태가 바뀌면 어떻게 되는가.
행성 화성의 이름은 바뀌지 않겠지만 마을 이름은 가끔, 사업체 이름은 자주 바뀐다. 사용자명도 바뀌고 사람은 결혼하며 이름을 바꾼다. URI에 의미를 더하는 거의 모든 리소스 상태는 바뀔 수 있고, 그러면 URI가 깨진다.

그래서 Rails 애플리케이션은 데이터베이스 테이블 ID를 담은 `/weblogs/4` 같은 URI를 노출한다.
7장에서 저자가 깎아내렸던 URI지만, 그 장점은 절대 바뀌지 않는 리소스 상태에 기반한다는 것이다. 클라이언트에게는 쓸모없는 상태지만 바뀌지 않는다는 점에 가치가 있다.

Jakob Nielsen이 의미 있는 URI를 주장한다면, Tim Berners-Lee는 절대 바뀌지 않는 “의미 없는” URI, 즉 URI 불투명성을 주장한다.
그의 “Axioms of Web Architecture”는 불투명성을 이렇게 기술한다. 역참조하지 않을 때는 다른 정보를 얻으려 URI 문자열의 내용을 들여다보지 말라.
즉 URI를 리소스 이름으로 쓸 수는 있어도, 무엇을 말하는지 뜯어보거나 URI를 바꿔 리소스를 바꿀 수 있다고 가정하지 말라는 것이다.
이는 웹 전체에는 URI에 대한 어떤 보장도 없으므로 범용 클라이언트에게 좋은 규칙이다(`.html`로 끝나도 HTML 문서가 있으리란 보장은 없다).
그러나 오늘날 평균적인 RESTful 서비스는 URI 구성 규칙을 중심으로 지어진다. URI 템플릿으로 서비스는 특정 패턴에 맞는 URI 부류 전체에 대해 약속할 수 있다.
프로그래밍 가능한 웹에서 URI 불투명성을 지지하는 가장 좋은 논거는, 불투명하지 않은 URI가 바뀔 수 있는 리소스 상태를 담는다는 사실이다. 불투명한 URI는 “쿨한(cool)” URI다.

그래서 어느 쪽인가. URI as UI인가, URI 불투명성인가.
답은 “경우에 따라 다르다”이다. 리소스와 눈에 보이는 관계가 없는 URI와, 리소스 상태가 바뀌면 깨지는 URI 중 무엇이 클라이언트에게 더 나쁜지에 달렸다.
Leonard는 거의 항상 URI as UI 쪽이되 가장 덜 바뀔 리소스 상태를 골라 URI에 넣는다(블로그 글 URI에 날짜는 넣되 제목은 넣지 않는다).
Sam은 검색 엔진 최적화와 가독성을 위해 제목을 URI에 넣고, 글 제목이 바뀌면 옛 URI에 영구 리다이렉트를 설정한다.

## HTTP의 표준 기능

HTTP에는 특정 엔지니어링 문제를 풀도록 설계된 기능이 여럿 있다.
이 기능들은 사람 웹에서는 잘 나타나지 않는 문제를 풀거나 브라우저가 투명하게 구현하기 때문에 널리 알려져 있지 않다.
프로그래밍 가능한 웹에서 일할 때 이 기능을 알아야, 다시 발명하거나 HTTP를 애플리케이션 프로토콜로 쓰길 성급히 포기하지 않는다.

### 인증과 인가

HTTP 인증과 인가는 HTTP 헤더, 즉 HTTP “봉투”에 붙는 “스티커”로 처리된다.
이 헤더들은 확장 가능하게 설계되었다. HTTP는 두 인증 방식을 정의하지만, `Authorization`과 `WWW-Authenticate` 헤더 값을 커스터마이즈해 다른 방식을 통합하는 표준 방법이 있다.

기본 인증(Basic)은 단순한 챌린지/응답이다.
보호된 리소스에 자격 증명 없이 접근하면 챌린지를 받고 다시 요청해야 한다.

```http
GET /resource.html HTTP/1.1
Host: www.example.com
```

자격 증명이 없으면 서버가 챌린지로 응답한다.

```http
401 Unauthorized
WWW-Authenticate: Basic realm="My Private Data"
```

`WWW-Authenticate` 헤더는 인증 종류(여기서는 Basic)와 realm을 알려준다.
realm은 사이트에서 보호되는 리소스 모음을 식별하는 이름이다. 한 사이트가 서로 다르게 보호되는 여러 리소스 집합을 가질 수 있어, realm이 클라이언트에게 어떤 자격 증명을 줘야 하는지 알려준다. realm은 “무엇”, 인증 종류는 “어떻게”에 해당한다.

Basic 챌린지에 응하려면 사용자명과 비밀번호를 하나의 문자열로 합쳐 base64로 인코딩한다.

```text
"Alibaba:open sesame"  ->  QWxpYmFiYTpvcGVuIHNlc2FtZQ==
```

이 문자열을 `Authorization` 헤더 값으로 다시 요청한다.

```http
GET /resource.html HTTP/1.1
Host: www.example.com
Authorization: Basic QWxpYmFiYTpvcGVuIHNlc2FtZQ==
```

서버가 이 문자열을 디코딩할 수 있듯 트래픽을 엿보는 누구든 디코딩할 수 있다. Basic 인증은 사실상 사용자명과 비밀번호를 평문으로 전송한다.
해법 하나는 HTTPS(TLS/SSL)를 쓰는 것으로, 클라이언트-서버 간 통신을 `Authorization` 헤더까지 포함해 모두 암호화한다. 6장에서 지도 서비스에 인증을 더하며 평문 HTTP에서 HTTPS로 전환한 이유가 이것이다.

다이제스트 인증(Digest)은 자격 증명을 엿보기로부터 숨기는 또 다른 방법으로, Basic보다 복잡하지만 암호화되지 않은 HTTP에서도 안전하다.
흐름은 Basic과 같은 요청·챌린지·응답이지만 챌린지가 더 많은 정보를 담는다.

```http
401 Unauthorized
WWW-Authenticate: Digest realm="My Private Data",
    qop="auth",
    nonce="0cc175b9c0f1b6a831c399e269772661",
    opaque="92eb5ffee6ae2fec3ad71c777531578f"
```

nonce는 매 요청마다 바뀌는 무작위 문자열이다.
클라이언트는 클라이언트 측 nonce와 시퀀스 번호를 만든 뒤, 요청의 HTTP 메서드와 경로, 챌린지의 네 정보, 사용자명과 비밀번호, 클라이언트 nonce, 시퀀스 번호를 재료로 하나의 “다이제스트” 문자열을 만든다.
계산은 MD5 해시를 세 단계로 조합하는 방식으로, Basic보다 훨씬 복잡하다.

```text
ha1 = MD5(user:realm:password)
ha2 = MD5(method:path)
ha3 = MD5(ha1:nonce:nc:cnonce:qop:ha2)
```

계산이 끝나면 클라이언트는 비밀번호를 제외한 상수들과 최종 결과를 담아 다시 요청한다.

```http
GET /resource.html HTTP/1.1
Host: www.example.com
Authorization: Digest username="Alibaba",
    realm="My Private Data",
    nonce="0cc175b9c0f1b6a831c399e269772661",
    uri="/resource.html",
    qop=auth,
    nc=00000001,
    cnonce="4a8a08f09d37b73795649038408b5f33",
    response="2370039ff8a9fb83b4293210b5fb53e3",
    opaque="92eb5ffee6ae2fec3ad71c777531578f"
```

Digest의 핵심 차이는 두 가지다.
첫째, 서버조차 다이제스트로부터 비밀번호를 알아낼 수 없다. 서버는 `user:realm:password`의 해시(ha1)만 저장해두면 실제 비밀번호 없이 최종값을 검증할 수 있다.
둘째, 클라이언트의 모든 요청이 사실은 두 요청이다. 첫 요청은 챌린지를 받기 위한 것이라 항상 401로 실패하고, 거기 담긴 고유 nonce로 `Authorization`을 만들어 두 번째 요청을 보낸다. Basic과 달리 첫 요청에 자격 증명을 실어 챌린지를 건너뛸 수 없다.
`qop=auth-int`를 쓰면 ha2 계산에 요청 엔티티 본문까지 포함해, 중간자가 PUT·POST에 딸린 표현을 조작하지 못하게 한다.
핵심은 `WWW-Authenticate`가 “인증에 필요한 모든 것이 여기 있다(비밀만 안다면)”고 말하고, `Authorization`이 “나는 비밀을 안다, 증거가 여기 있다”고 말한다는 것이다.

Basic도 Digest도 맞지 않으면 `WWW-Authenticate`와 `Authorization`에 넣을 자체 표준을 정의할 수 있다.
실제 사례로, 저비용 호스팅 계정 사용자는 여러 기술적 이유로 Basic도 Digest도 쓸 수 없었고 이것이 Atom 커뮤니티의 일부에 중요했다.
Atom 워킹 그룹은 WS-Security 명세에서 UsernameToken 아이디어 하나를 가져와 SOAP 헤더에서 HTTP 헤더로 옮겼다. 이 확장을 WSSE UsernameToken, 줄여서 WSSE라 부른다.

WSSE는 Digest처럼 클라이언트가 비밀번호를 해시해 보낸다. 챌린지는 다음과 같다.

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: WSSE realm="My Private Data", profile="UsernameToken"
```

profile은 UsernameToken 규칙으로 응답을 만들라고 알린다.
클라이언트는 nonce를 만들고 비밀번호를 nonce, 현재 시각과 함께 SHA1로 해시한다.

```text
PasswordDigest = Base64(SHA1(nonce + created + password))
```

그리고 응답을 보낸다.

```http
GET /resource.html HTTP/1.1
Host: www.example.com
Authorization: WSSE profile="UsernameToken"
X-WSSE: UsernameToken Username="Alibaba",
    PasswordDigest="Z2Y59TewHV6r9BWjtHLkKfUjm2k=",
    Nonce="EFD89F06CCB28C89",
    Created="2007-04-13T09:00:00Z"
```

같은 헤더, 같은 메시지 흐름에 인증 방식과 해시 알고리즘만 바꾸면 HTTP 인증을 확장할 수 있다.
WSSE의 큰 장점은 두 가지다. Basic처럼 비밀번호를 평문으로 보내지 않고, Digest처럼 서버 측 특별 설정이 필요 없다.
큰 단점 하나는, Basic·Digest는 서버가 비밀번호의 단방향 해시만 저장할 수 있는 반면 WSSE는 서버가 챌린지 응답을 검증하려면 비밀번호를 평문으로 저장해야 한다는 점이다. 서버가 뚫리면 모든 비밀번호가 노출된다. 보안에는 늘 이런 트레이드오프가 따른다.

### 압축

XML 문서 같은 텍스트 표현은 원래 크기의 일부로 압축할 수 있다.
클라이언트는 요청에 `Accept-Encoding` 헤더로 이해하는 압축 알고리즘을 알린다. 표준 값은 `compress`와 `gzip`이다.

```http
GET /resource.html HTTP/1.1
Host: www.example.com
Accept-Encoding: gzip,compress
```

서버가 그 알고리즘 중 하나를 이해하면 표현을 압축해 제공하고, 압축 여부를 알리는 `Content-Encoding` 헤더를 함께 보낸다. `Content-Type`은 압축하지 않았을 때와 같다.

```http
200 OK
Content-Type: text/html
Content-Encoding: gzip

[압축된 이진 표현]
```

클라이언트는 `Content-Encoding`의 알고리즘으로 데이터를 풀고 `Content-Type`의 미디어 타입으로 다룬다.
저자는 압축 여부를 URI가 아니라 헤더로 구분하도록 권하는데, 압축은 암호화처럼 전송 중 표현에 일어나는 일이고 클라이언트가 쓰기 전에 되돌려야 하는 것이라 서로 다른 표현이 아니라고 보기 때문이다.
현재는 대부분의 브라우저가 압축 표현을 자동으로 요청하지만 프로그래밍 가능한 클라이언트는 거의 그렇지 않다.

### 조건부 GET

조건부 HTTP GET은 서버와 클라이언트가 협력해 대역폭을 아끼는 기법이다.
이미 표현을 가진 클라이언트에게 같은 표현을 다시 보내지 않도록 한다.
클라이언트나 서버 어느 한쪽만으로는 풀 수 없다. 서버는 무상태라 클라이언트가 언제 마지막으로 표현을 받았는지 모르므로, 클라이언트가 그 정보를 애플리케이션 상태의 일부로 제공해야 한다.

서버가 표현을 보낼 때 `Last-Modified`, `ETag` 응답 헤더를 설정한다.
클라이언트는 같은 표현을 다시 요청할 때 그 값을 각각 `If-Modified-Since`, `If-None-Match`로 보낸다. 그러면 서버가 표현을 다시 보낼지 결정할 수 있다.

첫 요청의 응답은 다음과 비슷하다.

```text
Status code: 200 OK
Representation size: 41123
Last-Modified: Sun, 21 Jan 2007 09:35:19 GMT
Etag: "7359b7-a37c-45b333d7"
```

두 번째 요청에서 `Last-Modified` 값을 `If-Modified-Since`로, `ETag` 값을 `If-None-Match`로 보내면, 표현이 바뀌지 않았을 때 다음처럼 응답한다.

```text
Status code: 304 Not Modified
Representation size: 0
```

40KB 대신 0바이트 표현을, 200 대신 304를 받아 양쪽 모두 대역폭을 아낀다. 브라우저 캐시를 떠받치는 트릭 중 하나이며 커스텀 클라이언트에서도 쓰지 않을 이유가 없다.

`Last-Modified`는 표현이 마지막으로 바뀐 시각이다.
Apache 같은 서버는 정적 파일을 다루므로 파일시스템의 수정 시각을 그대로 쓰면 되지만, 복잡한 경우에는 표현을 구성 요소로 나눠 각 상태가 언제 바뀌었는지 봐야 한다. 7장에서 북마크 목록의 `Last-Modified`는 목록 중 가장 최근 타임스탬프였다.
`Last-Modified`는 완전히 신뢰할 수는 없다. 초 단위 해상도로는 같은 초 안에 일어난 변경을 놓쳐 서버가 잘못 304를 보낼 수 있다. 사실 어떤 해상도도 변경 시점을 완벽히 추적하기엔 부족하다.

그래서 `ETag`(엔티티 태그) 응답 헤더가 등장한다.
`ETag`는 해당 표현이 바뀔 때마다 반드시 바뀌는 무의미한 문자열이다. `If-None-Match`는 `ETag`에 대해 `If-Modified-Since`가 `Last-Modified`에 대하는 것과 같은 관계로, “엔티티 태그로 구현된 표현이 바뀌었는가”를 조건으로 하는 완전히 신뢰할 만한 변경 식별 수단이다.
좋은 `ETag`는 MD5 해시 같은 변환으로 쉽게 만들 수 있지만, 그러려면 표현을 이미 바이트 문자열로 만들어야 하는 문제가 있다. 전송 대역폭은 아껴도 표현을 만드는 일은 이미 끝난 셈이다.
Apache는 정적 파일의 크기와 수정 시각 같은 파일시스템 정보로 내용을 읽지 않고 `ETag`를 만든다. 이처럼 잘 바뀌는 데이터나 요약 데이터만으로 태그를 만들면 된다. `ETag`는 모든 데이터를 담을 필요 없이 표현이 바뀔 때마다 바뀌기만 하면 된다.
서버가 둘 다 제공하면 클라이언트는 이후 요청에 둘 다 보내고, 서버는 표현이 바뀌었고 `ETag`도 다를 때만 새 표현을 보내야 한다.

### 캐싱

조건부 GET이 대역폭이 거의 들지 않는 두 번째 GET으로 표현을 갱신하게 한다면, 캐싱은 그 두 번째 GET 자체를 불필요하게 만드는 대략적 지침을 준다.
HTTP 캐싱은 복잡한 주제이며 여기서는 프록시 캐시를 빼고 클라이언트 측 캐시로 논의를 한정한다.
기본은 이렇다. 클라이언트가 GET이나 HEAD를 하면 응답 문서를 헤더까지 통째로 캐시할 수 있고, 다음에 같은 요청을 하면 실제 요청 대신 캐시된 문서를 돌려줄 수 있다. 사용자 관점에서 캐싱은 투명하다.
서비스 제공자 관점에서 세 가지가 중요하다. 캐시하라고 알리는 법, 캐시하지 말라고 알리는 법, 모르는 사이 클라이언트가 캐시하고 있을 때다.

캐시를 허용할 때 서버는 응답 헤더 `Expires`에 날짜를 보낼 수 있다.

```http
Expires: Tue, 30 Jan 2007 17:02:06 GMT
```

이 헤더는 응답을 얼마나 오래 캐시해도 되는지 알린다. 과거 날짜(도착 시 이미 만료)부터 1년 뒤(사실상 만료되지 않음)까지 가능하다.
`Expires` 시각이 지나면 응답은 상해도(stale) 캐시에서 즉시 제거될 필요는 없다. 클라이언트가 조건부 GET으로 아직 신선한지 확인하고 만료 날짜를 갱신할 수 있다.
`Expires`는 정확한 날짜가 아니라 대략적 안내다. 대부분의 서비스는 응답이 언제 바뀔지 초 단위로 예측할 수 없다. 의심스러우면 클라이언트가 다시(가능하면 조건부로) 요청하면 된다.
서버는 1년보다 먼 미래의 `Expires`를 보내면 안 된다. 소프트웨어 업그레이드 등 실세계 사건이 예상보다 빨리 캐시를 무효화하기 때문이다.

만료 날짜를 계산하고 싶지 않으면 `Cache-Control`로 몇 초 동안 캐시할지 말할 수 있다.

```http
Cache-Control: max-age=3600
```

반대로 캐시하지 말아야 할 때가 있다. 매번 다르게 동적 생성되는 응답이나 민감한 정보를 담은 응답이 그렇다.

```http
Cache-Control: no-cache
```

`Expires`가 단순한 반면 `Cache-Control`은 매우 복잡하며, 클라이언트 측 캐시와 프록시 캐시를 제어하는 주된 인터페이스다.
`max-age`는 신선 유지 시간을, `no-cache`는 캐시 금지를 뜻한다. 유용한 세 번째 값 `private`은 클라이언트 캐시는 되지만 클라이언트와 서버 사이의 프록시 캐시는 안 된다는 뜻이다.

`Expires`나 `Cache-Control`이 없으면 HTTP 표준 13절이 복잡한 기본 규칙을 정한다. 상식적인 기본 규칙은 다음과 같다.
일반적으로 클라이언트는 성공한 GET·HEAD 응답을 캐시할 수 있다. 성공은 상태 코드로 정의되며 흔한 성공 코드는 200, 301(“Moved Permanently”), 410(“Gone”)이다.
설계가 나쁜 많은 웹 애플리케이션은 GET에 부작용이 있는 URI를 노출하는데, 대개 쿼리 문자열을 담는다. HTTP 표준은 URI에 쿼리 문자열이 있으면 서버가 명시적으로 허용하지 않는 한 응답을 자동 캐시하지 말라고 권한다. 그래야 같은 URI를 두 번 GET할 때 부작용이 두 번 일어난다.
클라이언트가 어떤 URI에 PUT·POST·DELETE하면 그 URI의 캐시된 응답은 즉시 상한다. PUT·POST·DELETE 응답의 `Location`이나 `Content-Location`에 언급된 URI도 마찬가지다.
다만 한 사이트가 다른 사이트의 캐시에 영향을 줄 수는 없다. `www.example.com/resource`에 POST해 응답 `Location`이 `www.example.com/resource2`면 그것의 캐시는 상하지만, `Location`이 `www.oreilly.com/resource2`면 그 캐시는 상하지 않는다.
어떤 규칙도 해당하지 않고 서버가 캐시 기간을 명시하지 않으면 결정은 클라이언트 몫이다. 현실적으로 클라이언트 캐시는 한 시간에서 하루 사이에 응답을 상한 것으로 간주해야 하며, 상한 응답도 조건부 GET으로 여전히 쓸 수 있는지 확인할 수 있다.

### 뛰기 전에 살피는 요청(Look-Before-You-Leap)

조건부 GET이 서버가 이미 가진 표현을 다시 보내지 않게 한다면, 덜 쓰이는 이 기능은 클라이언트가 거대한(또는 민감한) 표현을 헛되이 보내지 않게 한다.
클라이언트는 PUT·POST를 보내되 엔티티 본문을 생략하고 `Expect` 헤더를 `100-continue`로 설정한다.

```http
PUT /filestore/myfile.txt HTTP/1.1
Host: example.com
Content-length: 524288000
Expect: 100-continue
```

이는 실제 PUT이 아니라 미래의 PUT에 대한 질문이다. “이 리소스에 새 표현을 PUT해도 되겠는가”를 묻는 것이다.
서버는 리소스의 현재 상태와 헤더(여기서는 `Content-length`로 500MB 파일을 받을지)를 보고 결정한다.
허용하면 100(“Continue”)을 보내고, 클라이언트는 `Expect`를 빼고 500MB 표현을 본문에 담아 PUT을 다시 보낸다.
거부하면 417(“Expectation Failed”)을 보낸다. 쓰기 금지, 인증 미비, 크기 초과 등 어떤 이유든, 이 사전 질문이 클라이언트가 거부될 데이터 500MB를 헛되이 보내는 것을 막는다.
물론 클라이언트가 헤더로 거짓말해 100을 받아낼 수는 있지만, 서버는 두 번째 요청에서도 나쁜 표현을 받아들이지 않으므로 소용없다.

### 부분 GET

부분 HTTP GET은 클라이언트가 표현의 일부만 가져오게 하며, 보통 중단된 다운로드를 재개하는 데 쓴다.
대부분의 웹 서버가 정적 콘텐츠에 대해, Amazon S3도 이를 지원한다. 클라이언트는 `Range` 헤더로 바이트 범위를 지정한다.

```http
Range: bytes=10-20
Range: bytes=40000-
```

응답은 206(“Partial Content”)이며 `Content-Range` 헤더로 반환한 범위와 전체 크기를 알린다.

```text
Status code: 206 Partial Content
Content Range: bytes 10-20/41123
Etag: "7359b7-a0a3-45b5d90e"
```

`ETag`는 항상 문서 전체에 대해 계산한 값이라, 조건부 GET과 부분 GET을 함께 쓸 수 있다.
부분 GET은 리소스의 하위 리소스에 접근하는 수단처럼 보이지만 그렇지 않다. 바이트 범위로만 지정할 수 있어 이진 데이터가 아니면 별로 쓸모없고, 더 중요하게는 따로 이야기하고 싶은 하위 리소스가 있다면 그것은 이미 별개의 리소스다. 그런 하위 리소스에는 자체 URI를 주라.

## PUT과 DELETE 우회하기

모든 클라이언트가 PUT과 DELETE를 지원하지는 않는다.
XHTML 4 폼의 action은 GET이나 POST만 가능해, 많은 사람이 PUT·DELETE가 진짜 HTTP 메서드가 아니라고 여기게 되었다. 일부 방화벽은 POST는 두고 PUT·DELETE는 막는다.
서버가 지원하면 클라이언트는 오버로딩된 POST로 PUT·DELETE를 터널링해 이런 제약을 우회할 수 있다.

저자가 권하는 방법은 오늘날 가장 RESTful한 프레임워크들이 개척한 방식, 즉 “진짜” HTTP 메서드를 쿼리 문자열에 넣는 것이다.
Ruby on Rails는 `_method`라는 숨은 폼 필드로 진짜 메서드를 참조한다. DELETE를 못 하면 `/my/resource?_method=delete`에 POST하거나 본문에 `_method=delete`를 넣는다. Restlet도 `method` 변수를 같은 용도로 쓴다.
두 번째 방법은 `X-HTTP-Method-Override` 요청 헤더에 진짜 메서드를 넣는 것으로, Google의 GData API가 이 헤더를 인식한다.
저자는 쿼리 문자열에 붙이는 쪽을 권한다. PUT·DELETE를 지원하지 않는 클라이언트는 커스텀 요청 헤더도 지원하지 않을 가능성이 높기 때문이다.

## 쿠키의 문제

HTTP 쿠키를 보내는 웹 서비스는 무상태성 원칙을 위반한다. 보통 두 번 위반한다.
클라이언트에 있어야 할 애플리케이션 상태를 서버로 옮기고, 클라이언트가 자기 애플리케이션 상태를 통제하지 못하게 한다.

많은 프레임워크가 쿠키로 세션을 구현한다. 4장에서 본 Rails 쿠키처럼 말이다.

```http
Set-Cookie: _session_id=c1c934bbe6168dcb904d21a7f5644a2d; path=/
```

그 긴 16진수는 클라이언트 상태로 저장되지만 애플리케이션 상태는 아니다. 서버에 저장된 세션 해시로 들어가는 무의미한 키일 뿐이다.
클라이언트는 이 상태에 접근할 수도, 무엇이 저장되는지 알 수도 없다. 그저 매 요청에 쿠키를 보내고 서버가 알아서 상태를 찾게 할 뿐이다. 클라이언트에게도 서버에게도 부담이다. 서버는 요청 중일 때만이 아니라 늘 이 상태를 보관해야 한다.

그렇다면 세션 ID 대신 실제 애플리케이션 상태를 담은 쿠키는 어떤가.
이는 RESTful할 수 있지만 대개 그렇지 않다. 쿠키 표준은 클라이언트가 쿠키를 만료되거나 종료될 때 버릴 수 있다고 하는데, 이는 클라이언트의 애플리케이션 상태 통제에 큰 제약이다.
요청을 10번 한 뒤 서버가 쿠키를 주면 이후 요청에 그 쿠키를 계속 보내야 하고, 종료하고 다시 시작하지 않는 한 쿠키 이전의 10개 요청을 다시 할 수 없다. 브라우저에 비유하면 “뒤로” 버튼이 고장 난 것이다.
현실의 클라이언트가 표준을 그렇게 곧이곧대로 따르지는 않는다. 하지만 클라이언트는 대개 서버의 쿠키를 수정하거나 그 의미를 이해하도록 허용되지 않는다.
의미를 모른 채 애플리케이션 상태를 보내면 클라이언트는 자신이 무슨 요청을 하는지 정말로는 모르는 셈이다. 쿠키는 거의 언제나 서버가 이유를 설명하지 않은 채 클라이언트를 자기 뜻대로 움직이게 하는 수단이다. 서버가 하이퍼미디어 링크와 폼으로 클라이언트를 새 상태로 안내하는 편이 더 RESTful하다.

쿠키의 유일한 RESTful한 용도는 클라이언트가 쿠키 값을 통제하는 경우다.
서버는 `Set-Cookie`로 값을 제안할 수 있지만, 따를 링크를 클라이언트가 고르듯 어떤 쿠키를 보낼지도 클라이언트가 고른다.
일부 브라우저 기반 애플리케이션에서는 쿠키가 클라이언트에 의해 만들어지고 서버로는 전혀 보내지지 않는다. 쿠키가 그저 애플리케이션 상태를 담는 편리한 그릇이고, 그 상태는 표현과 URI를 통해 서버에 이르는 것이다. 이는 매우 RESTful한 쿠키 사용이다.

## 사용자는 왜 HTTP 클라이언트를 신뢰해야 하는가

HTTP 인증은 클라이언트가 서버에 자격 증명을 증명하는 클라이언트-서버 인증을 다룬다.
HTTP가 다루지 않는 것은, 사용자가 왜 웹 서비스 클라이언트에게 자신의 자격 증명을 맡겨야 하는가다.
사람 웹에서는 보통 문제가 아니다. 우리는 브라우저를 암묵적으로 신뢰하기 때문이다. example.com의 웹 애플리케이션을 쓸 때 example.com 자격 증명을 넣는 것은 편하다.

그런데 example.com이 뒤에서 eBay 웹 서비스의 클라이언트라면, 그리고 숨은 요청을 위해 내 eBay 자격 증명을 요구한다면, 기술적으로 이 애플리케이션과 ebay.com을 사칭하는 피싱 사이트 사이에 차이가 없다.
이 책의 독립형 클라이언트들은 사용자명과 비밀번호를 `Authorization` 헤더에 인코딩해 인증한다. 브라우저처럼 신뢰하는 클라이언트라면 괜찮지만, 신뢰할 수 없는, 어쩌면 남의 컴퓨터에서 도는 프로그램에 자격 증명을 넘기는 것은 순진한 일이다.
그래서 어떤 웹 서비스는 클라이언트가 사용자명·비밀번호를 아예 다루지 못하게 해 피싱에 대응한다.

이 방식에서 사용자는 신뢰하는 브라우저로 인가 토큰을 얻는다.
사용자명·비밀번호 대신 이 토큰을 클라이언트에 주고, 클라이언트는 이 토큰을 `Authorization` 헤더에 실어 보낸다.
사용자는 자신으로서 웹 서비스를 호출할 능력을 위임하는 것이다. 클라이언트가 그 능력을 남용하면, 사용자가 비밀번호를 바꾸지 않고도 토큰을 취소할 수 있다.
Google, eBay, Yahoo!, Flickr 모두 이런 사용자-클라이언트 인가 시스템을 갖고 있고, 3장의 Amazon 요청 서명도 같은 기능을 한다. 공식 표준은 없지만 개념은 비슷하다.

웹 인터페이스를 가진 애플리케이션이 가장 단순한 경우다.
Google Calendar 같은 서비스를 호출해야 할 때, 웹 애플리케이션은 사용자를 google.com의 URI로 리다이렉트한다.

```text
https://www.google.com/accounts/AuthSubRequest
    ?scope=http%3A%2F%2Fwww.google.com%2Fcalendar%2Ffeeds%2F
    &next=http%3A%2F%2Fcalendar.example.com%2Fmy
```

`scope`는 토큰을 얻으려는 웹 서비스의 기본 URI이고, `next`는 Google이 제어를 웹 애플리케이션에 돌려줄 때 쓸 URI다.
사용자가 이 URI에 이르면 Google은 example.com이 사용자를 대신해 캘린더에 접근하려 한다는 페이지를 보여준다. 사용자가 example.com을 신뢰하기로 하면 Google에 인증하며, Google 사용자명·비밀번호를 example.com에 결코 주지 않는다.
인증 후 Google은 `next` 값에 기반한 URI로 리다이렉트해 제어를 돌려준다. 예를 들어 `http://calendar.example.com/my?token=...`처럼 일회용 인가 토큰을 쿼리 변수 `token`에 담는다.
웹 애플리케이션은 이 토큰을 `Authorization` 헤더에 실어 호출한다.

```http
Authorization: AuthSub token="IFM29SdTSpKL77lNCn"
```

이제 웹 애플리케이션은 사용자에 대해 아무것도 모른 채 사용자로서 호출할 수 있다. 인증 정보는 google.com을 떠나지 않고, 이 일회용 토큰은 한 요청에만 유효하다(일회용 토큰으로 여러 요청에 쓸 세션 토큰을 얻을 수도 있다).
핵심 흐름은, 제어가 웹 애플리케이션 도메인에서 웹 서비스 도메인으로 넘어가 사용자가 서비스에 인증하고 외부 애플리케이션을 인가한 뒤, 다시 웹 애플리케이션 도메인으로 돌아오는 것이다.

웹 인터페이스가 없는 애플리케이션은 다르다.
웹 서비스 클라이언트가 사용자 컴퓨터에서 도는 GUI나 명령줄 프로그램이라면 두 가지 견해가 있다.
첫째 견해는 사용자가 클라이언트 측 애플리케이션을 브라우저만큼 신뢰해야 한다는 것이다. 웹 애플리케이션은 신뢰할 수 없는 컴퓨터에서 돌지만 내 컴퓨터의 클라이언트는 내가 통제하고 감시하며 멈출 수 있기 때문이다.
Google이 이 태도를 취한다. 데스크톱 애플리케이션용 인증은 브라우저를 로그인 페이지로 리다이렉트하지 않고, 사용자명·비밀번호를 모아 “로그인”해 토큰을 얻는다. 이 토큰은 보안상 별 의미가 없다. 토큰을 얻으려면 이미 더 값진 사용자명·비밀번호를 알아야 하기 때문이다.
둘째 견해는 브라우저만이 사용자가 자격 증명을 맡길 유일한 클라이언트라는 것이다. 그러면 데스크톱 클라이언트 프로그래머는 신뢰하는 클라이언트인 브라우저를 띄워 사용자를 특정 URI로 보내 인증 토큰을 얻어야 한다. Flickr의 URI는 다음과 비슷하다.

```text
http://flickr.com/services/auth/?perms=write&api_sig=925e1&api_key=1234&frob=abcd
```

여기서 가장 중요한 쿼리 변수는 `frob`, 이전 웹 서비스 호출로 얻은 미리 정해진 ID다.
사용자 브라우저가 갑자기 떠 Flickr 로그인 화면을 보여주고, 사용자는 인증해 `api_key=1234` 클라이언트가 자신을 대신하도록 인가한다.
`frob`이 없으면 데스크톱 클라이언트는 사용자에게 토큰을 복사·붙여넣기 하도록 졸라야 하지만, 미리 합의한 `frob`으로 클라이언트가 토큰을 얻을 수 있다. 사용자는 브라우저를 닫아도 되고, 클라이언트는 다음과 같은 URI에 GET한다.

```text
http://flickr.com/services/rest/?method=flickr.auth.getToken
    &api_sig=1f348&api_key=1234&frob=abcd
```

eBay와 Flickr는 이런 메커니즘을 쓴다. Flickr의 `frob`을 eBay는 `runame`이라 부른다. 사용자는 사용자명·비밀번호를 알려주지 않고 독립형 클라이언트에 자신을 대신할 권한을 인가할 수 있다.
네트워크는 되지만 브라우저가 없는 일부 모바일 기기의 경우, 브라우저만 신뢰하는 서비스는 특별한 예외를 두거나 그 기기를 배제하는 것을 감수해야 한다.

이것이 실제로 무슨 문제를 푸는가.
사용자는 여전히 웹 폼에 사용자명·비밀번호를 입력해야 하고, 악의적 작성자가 브라우저를 가짜 인가 페이지로 보내는 것을 막지 못한다. 피셔들은 늘 그렇게 한다.
그러나 은행 같은 피싱 표적 사이트는 “브라우저로 <https://www.mybank.com/>으로 시작하는 URI를 방문할 때만 사용자명·비밀번호를 입력하라”는 경고를 둘 수 있다.
반면 대부분의 웹 서비스는 이 미약한 방어조차 제공하지 못한다. 이 책의 독립형 애플리케이션들은 서비스 사용자명·비밀번호를 입력으로 받는데, 그것들을 신뢰할 수 있는가.
사람 웹에는 범용 클라이언트인 브라우저 하나가 있어, 내 컴퓨터에서 도는 그 하나를 신뢰하는 것은 큰 도약이 아니다. 프로그래밍 가능한 웹에는 용도별로 다른 클라이언트가 있는데, 사용자가 그것들을 모두 신뢰해야 하는가.
여기서 설명한 메커니즘은 사용자가 이미 신뢰하는 브라우저를, 다른 클라이언트에 더 낮은 수준의 신뢰를 부여하는 수단으로 쓰게 한다.
클라이언트가 신뢰를 남용하면 이후 요청을 막을 수 있다. 이 전략들이 피싱을 없애지는 못하지만, 눈 밝은 사용자가 피싱을 피할 수 있게 하고 서비스 제공자가 경고를 낼 수 있게 한다. 이런 메커니즘이 없으면 사용자는 정당한 클라이언트와 피싱 사이트를 구별할 수 없다. 둘 다 비밀번호를 받아가고, 차이는 그것으로 무엇을 하느냐뿐이다.

## 핵심 정리

리소스 지향의 네 기둥은 주소 지정 가능성, 무상태성, 연결성, 균일한 인터페이스다. 흥미로운 모든 것에 URI를 주고, 상태를 서버에 두지 말고, 링크와 폼으로 리소스를 잇고, 몇 가지 표준 HTTP 메서드만 쓰라.
GET·HEAD는 안전하게, PUT·DELETE는 멱등하게 유지하라. POST는 새 리소스 생성과 오버로딩에 쓰되, 오버로딩된 POST는 균일한 인터페이스를 망치므로 최후의 수단으로만 쓰라.
설계가 균일한 인터페이스에 맞지 않으면, 문제를 일으키는 그것(비동기 작업, 배치, 트랜잭션, 관계)을 새로운 리소스로 노출하라. 의심스러우면 리소스로 만들라.
URI는 계층에 경로 변수, 같은 수준에 구두점(순서 중요하면 쉼표, 아니면 세미콜론), 알고리즘 인자에 쿼리 변수를 쓰고, 연산이 아니라 객체를 가리키게 하라.
나가는 표현에는 상태 코드로 용도를, `Content-Type`으로 형식을 밝히고 모든 관련 상태를 담으라. 들어오는 표현은 단순하면 키-값, 복잡하면 나가는 것과 같은 형식으로 받으라.
프로그램은 변화에 약하므로 확장 가능한 형식과 연결성으로 대비하고, 의미가 바뀌면 URI에 버전을 넣어 버저닝하라(가장 단순하게는 첫 경로 변수).
읽기 좋은 URI(URI as UI)와 절대 바뀌지 않는 불투명한 URI 사이의 선택은 경우에 따라 다르며, 저자들은 잘 바뀌지 않는 상태를 골라 의미 있는 URI를 쓰는 쪽을 택한다.
HTTP의 표준 기능을 활용하라. Basic·Digest·WSSE 인증(트레이드오프를 이해하고), 압축(`Accept-Encoding`/`Content-Encoding`), 조건부 GET(`Last-Modified`/`ETag`와 `If-Modified-Since`/`If-None-Match`, 304로 대역폭 절약), 캐싱(`Expires`, `Cache-Control`), 100-continue, 부분 GET(`Range`, 206).
PUT·DELETE를 못 쓰는 클라이언트는 `_method` 쿼리 변수로 오버로딩된 POST에 터널링한다.
세션 ID 쿠키는 애플리케이션 상태를 서버로 옮겨 무상태성을 위반하므로 피하라. 클라이언트가 값을 통제하는 쿠키만 RESTful하다.
HTTP 인증은 클라이언트가 서버에 자신을 증명할 뿐, 사용자가 클라이언트를 신뢰할 이유를 주지 않는다. 사용자가 신뢰하는 브라우저로 인가 토큰을 얻어 클라이언트에 위임하면, 비밀번호를 넘기지 않고 남용 시 토큰만 취소할 수 있다.
