# 10장 ROA 대 빅 웹 서비스(SOAP/WS-*)

《RESTful Web Services》(Leonard Richardson, Sam Ruby, O'Reilly 2007) 10장 정리.

## 개요

이 책은 줄곧 웹의 결을 거스르지 않는 기술과 아키텍처에 집중해 왔다.
저자는 리소스를 서비스로 배치해 강력하면서도 개념적으로는 단순하고 다양한 표준 클라이언트에서 접근 가능한 방식을 설명해 왔다.
그러나 정작 많은 사람이 “웹 서비스” 하면 떠올리는 기술, 즉 SOAP과 WSDL, 그리고 WS-* 스택에 대해서는 거의 언급하지 않았다.
이 기술들은 웹 서비스의 또 다른 패러다임을 이루는데, 이 패러다임은 실제로는 웹처럼 동작하지 않는다.
저자는 이 진영이 웹 서비스라는 분야 전체를 독차지하도록 두지 않기 위해, 그다지 친절하지는 않지만 비교적 온건한 별명을 붙였다.
바로 “빅 웹 서비스(Big Web Services)”다.

빅 웹 서비스가 웹과 어긋나는 지점은 근본적이다.
웹은 리소스에 기반하지만 빅 웹 서비스는 리소스를 노출하지 않는다.
웹은 URI와 링크에 기반하지만, 전형적인 빅 웹 서비스는 하나의 URI를 노출하고 링크는 하나도 노출하지 않는다.
웹은 HTTP에 기반하지만 빅 웹 서비스는 HTTP의 기능을 거의 쓰지 않는다.
이것은 말장난 같은 트집이 아니다.
그 결과 빅 웹 서비스는 리소스 지향 웹 서비스가 주는 이점을 얻지 못하기 때문이다.
주소지정성이 없고, 캐시할 수 없으며, 잘 연결되어 있지도 않고, 어떤 통일 인터페이스도 따르지 않는다(다만 상당수는 무상태이긴 하다).
빅 웹 서비스는 불투명해서 하나를 이해해도 다음 것을 이해하는 데 도움이 되지 않는다.
실무에서는 다양한 클라이언트를 상대할 때 상호운용성 문제를 겪는 경향도 있다.

저자는 REST 아키텍처 스타일과 리소스 지향 아키텍처(ROA)를 설명할 때 쓰던 분석 도구를 빅 웹 서비스에도 그대로 적용한다.
목표는 이 기술들의 완전한 입문서를 제공하는 것이 아니라, 두 철학이 어떻게 대비되는지를 보이는 것이다.
저자는 SOAP 같은 기술을 과장이나 악마화가 아니라 기술적 수준에서, 그리고 신버전의 미실현 잠재력보다는 널리 배포된 실제 모습에 초점을 맞춰 살핀다.
분석은 연대순으로 진행된다.
최초의 “발행하고, 찾고, 바인딩한다(publish, find, and bind)” 비전에서 시작해, “안전하고 신뢰할 수 있는 트랜잭션”으로 넘어가고, 마지막으로 ESB, BPEL, SOA 같은 최근 발전을 다룬다.

## 빅 웹 서비스가 풀려는 문제

웹은 리소스 지향적이므로, 그 위에 RPC 스타일을 구현하는 것은 웹의 결을 거스르는 일이다.
그러나 웹은 애초에 범용 분산 프로그래밍을 지원하도록 설계되지 않았다.
때로는 애플리케이션 자체에 고유한 결이 있고, 그것을 거스르는 것이 오히려 문제가 된다.

저자가 이 장 내내 되짚는 구체적 예시는 여행 예약 서비스다.
여행을 예약하려면 항공편, 호텔, 렌터카를 함께 잡아야 할 수 있다.
이 작업들은 서로 얽혀 있어서, 호텔을 못 구하면 렌터카와 항공 좌석만 잡아 봐야 클라이언트에게 별 소용이 없다.
각 작업은 항공사, 렌터카 회사, 호텔 같은 외부 주체와 조율해 최선의 조건을 찾아야 한다.
이들 각각은 별개의 서비스일 수 있고, 이들과 거래한다는 것은 곧 여러 확약(commitment)을 만든다는 뜻이다.
나머지 거래를 맞추는 동안 항공사가 5분간 좌석 하나를 잡아 둘 수도 있고, 손님이 나타나든 아니든 첫날 숙박비를 청구하는 호텔 예약이 필요할 수도 있다.
이런 시간제한 확약은 공유 상태(shared state)를 나타낸다.

저자가 옹호하는 리소스 지향 접근은 튜링 완전하므로 여행 브로커처럼 복잡한 것까지 어떤 애플리케이션이든 모델링할 수 있다.
이를 리소스 지향 서비스로 구현한다면 “좌석 24C에 대한 5분간의 홀드” 같은 리소스를 노출하게 될 것이다.
동작은 하겠지만 그런 리소스에는 별 가치가 없을 것이다.
그런 리소스의 URI를 북마크하고 여기저기 넘겨주고 싶어 할 사람이 있을 것 같지는 않다.

여행사 서비스는 웹의 나머지와는 결이 다르다.
그렇다고 성공적인 웹 애플리케이션으로 만들 수 없다는 뜻도 아니고, SOAP과 관련 명세가 더 적합하다는 뜻도 아니다.
다만 이것이야말로 빅 웹 서비스가 풀려는 주된 문제다.
바로 프로세스 지향적이고 브로커를 거치는 분산 서비스의 설계다.
어떤 이유에서인지 이런 종류의 애플리케이션은 기업과 정부 영역에서 더 흔하고, 기술·학술 영역에서는 덜 흔한 편이다.

## SOAP

SOAP은 수많은 WS-* 명세가 그 위에 세워지는 토대다.
과장과 반작용의 저평가를 함께 받아 왔지만, 정작 이 명세 자체에는 놀라울 만큼 내용이 적다.
DOCTYPE이나 처리 지시(processing instruction)만 없다면 어떤 XML 문서든 작은 XML 엘리먼트 두 개로 감싸기만 하면 유효한 SOAP 문서가 된다.
다만 최선의 결과를 위해서는 문서의 루트 엘리먼트가 네임스페이스에 속하는 것이 좋다.

다음은 평범한 XML 문서다.

```xml
<hello-world xmlns="http://example.com" />
```

같은 문서를 SOAP 봉투(envelope)로 감싸면 다음과 같다.

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <hello-world xmlns="http://example.com" />
  </soap:Body>
</soap:Envelope>
```

유일한 제약은 SOAP 봉투가 자신이 감싸는 문서와 같은 문자 인코딩을 가져야 한다는 점이다.
사실상 이게 전부다.
XML 문서를 엘리먼트 두 개로 감싸는 것은 부당하거나 과중한 작업은 아니지만, 그렇다고 세상의 모든 문제를 풀어 주지도 않는다.

너무 단순해 보인다면, 실제 예시를 보자.
아래는 구글의 웹 검색 서비스에 보낼 법한 SOAP 문서의 전체 형태다.

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <gs:doGoogleSearch xmlns:gs="urn:GoogleSearch">
      <key>00000000000000000000000000000000</key>
      <q>REST book</q>
      <start>0</start>
      <maxResults>10</maxResults>
      <filter>true</filter>
      <restrict/>
      <safeSearch>false</safeSearch>
      <lr/>
      <ie>latin1</ie>
      <oe>latin1</oe>
    </gs:doGoogleSearch>
  </soap:Body>
</soap:Envelope>
```

이 문서는 원격 프로시저 `gs:doGoogleSearch`에 대한 호출을 기술한다.
모든 질의 매개변수가 이름 붙은 엘리먼트 안에 깔끔하게 담겨 있다.
이 예시는 완전히 동작하지만, 구글에 POST하면 키가 유효하지 않다는 오류(fault) 문서가 돌아온다.

원격 함수의 매개변수를 이렇게 인코딩하는 방식을 RPC/literal 또는 5절(Section 5) 인코딩이라 부른다.
SOAP 1.1 명세에서 SOAP을 RPC 용도로 쓰는 법을 보인 절이 5절이기 때문이다.
그러나 시간이 흐르며 유행이 바뀌었다.
이후 명세 버전에서 이 인코딩 지원이 선택 사항이 되면서 사실상 폐기(deprecated)되었다.
그 자리는 document/literal 인코딩이 대체했고, 다시 wrapped document/literal이 대체했다.
wrapped document/literal은 매개변수가 네임스페이스로 스코프된다는 점만 빼면 5절 인코딩과 대체로 비슷해 보인다.

바디 엘리먼트에 관한 마지막 참고 사항이 하나 있다.
매개변수에는 XML 스키마 데이터 타입에 기반한 데이터 타입 정보를 애트리뷰트로 달 수 있는데, 이는 대체로 문서의 가독성을 떨어뜨린다.
`<ie>latin1</ie>` 대신 `<ie xsi:type=“xsd:string”>latin1</ie>` 같은 것을 보게 되며, 이를 인자 개수만큼 곱해 보면 왜 많은 사람이 “SOAP”이라는 말에 진저리를 치는지 짐작이 간다.

HTTP와 SOAP은 둘 다 메시지를 봉투에 담는 서로 다른 방식일 뿐이다.
HTTP의 주요 부품은 엔티티 바디와 헤더다.
SOAP에도 Body 엘리먼트가 있으니 Header 엘리먼트도 있으리라 짐작할 수 있고, 실제로 그렇다.
Body에 들어갈 수 있는 것(DOCTYPE이나 처리 지시가 없는 네임스페이스 문서)은 무엇이든 Header에도 들어갈 수 있다.
다만 Body 안에는 보통 엘리먼트가 하나만 있는 반면, Header에는 임의 개수의 엘리먼트가 들어갈 수 있고 헤더 엘리먼트는 작은 편이다.
HTTP 봉투 비유로 보면 헤더는 봉투에 붙이는 “스티커”에 해당하며, SOAP 헤더는 보통 보안·라우팅 정보처럼 바디 데이터에 관한 정보를 담는다.

SOAP은 헤더 엔티티에 대해 두 개의 애트리뷰트, actor와 mustUnderstand를 정의한다.
메시지가 목적지에 도달하기 전 중개자(intermediary)를 거친다는 것을 미리 안다면, 특정 헤더의 대상이 되는 actor를 URI로 지정할 수 있다.
mustUnderstand 애트리뷰트는 그 중개자(또는 최종 목적지)에 제약을 건다.
어떤 actor가 자신에게 지정된 헤더를 이해하지 못하는데 mustUnderstand가 true이면, 그 actor는 다른 부분은 처리할 수 있다고 여겨도 메시지를 거부해야 한다.
2단계 커밋(two-phase commit) 관련 헤더가 그 예다.
목적지가 2단계 커밋을 이해하지 못한다면 그 작업이 진행되기를 원치 않을 것이다.

그 밖에 SOAP에 특별한 것은 별로 없다.
요청과 응답은 HTTP처럼 같은 형식을 쓰고, 오류 상황을 알리는 SOAP Fault라는 별도 형식이 있다.
현재 SOAP 문서에 들어갈 수 있는 것은 XML 문서뿐이다.
바이너리 데이터를 메시지에 첨부하려는 시도가 몇 번 있었지만 뚜렷한 승자는 나오지 않았다.

이렇게 단순한 프로토콜인데 과장과 논란의 근거는 무엇인가.
SOAP은 주로 그 위에 세워진 기술들 때문에 악명이 높은데, 그것은 뒤에서 다룬다.
SOAP 자체가 내세우는 이점이 하나 있긴 하다.
바로 전송 독립성(transport independence)이다.
헤더가 메시지 안에 들어 있으므로 메시지를 나르는 프로토콜과 무관하다는 것이다.
SOAP 봉투를 반드시 HTTP 봉투 안에 넣어 보낼 필요는 없으며, 이메일·인스턴트 메시징·생 TCP 등 어떤 프로토콜로도 보낼 수 있다.
그러나 실무에서 이 기능은 거의 쓰이지 않는다.
SMTP 전송의 공개 사용이 다소 있었고 방화벽 안에서 JMS 전송이 쓰이기도 했지만, 압도적 다수의 SOAP 트래픽은 HTTP 위로 흐른다.

### 리소스 지향 대안

SOAP은 거의 항상 HTTP 위로 전송되지만, SOAP 툴킷은 HTTP 상태 코드를 거의 활용하지 않고 모든 작업을 POST 메서드로 밀어 넣는 경향이 있다.
이것이 REST 아키텍처 스타일에서 기술적으로 금지된 것은 아니지만, REST가 주기로 한 이점을 하나도 얻지 못하는 퇴화한 형태의 RESTful 아키텍처다.
대부분의 SOAP 서비스는 다양한 데이터에 대한 여러 작업을 단일 URI의 POST 하나로 매개한다.
이는 리소스 지향이 아니라 RPC 스타일이다.

가장 중요한 변화 하나는 서비스를 리소스로 쪼개는 것이다.
서비스 안의 모든 “것(thing)”을 각각 별도의 URI로 식별하라.
사실상 모든 SOAP 툴킷이 이 정보에 접근할 수단을 제공하니 이를 활용하라.
객체 참조를 앞으로 끌어내라.
처음에는 관용적이지 않게 느껴질 수 있지만, 잠시 생각해 보면 SOAP이 정말 “Simple Object Access Protocol”이라면 바로 이렇게 해야 마땅하다.
이는 C 같은 함수 지향 언어의 `my_function(object, argument)`와 C++ 같은 객체 지향 언어의 `object->my_method(argument)`의 차이와 같다.
스코프 정보를 괄호(여기서는 Envelope) 바깥으로 옮기면, 공통 기능을 가진 많은 리소스를 식별하게 되고, 그 공통점을 활용하도록 로직을 리팩터링하고 싶어진다.

그다음으로 중요한 변화는 객체 지향의 다형성(polymorphism) 개념과 관련된다.
서로 다른 타입의 객체가 같은 이름의 메서드 호출에 응답하도록 만들어야 한다.
웹의 세계에서 이는 최소한 HTTP의 GET 메서드를 지원한다는 것을 뜻한다.
왜 중요한가.
거의 모든 객체 지향 언어가 표준 클래스 계층을 정의하고, 그 뿌리에는 정규 표현(canonical representation)을 제공하는 toString 같은 메서드를 갖춘 Object 클래스가 있다.
GET 메서드는 HTTP 리소스에 대해 그와 유사한 기능을 한다.

이렇게 하고 나면 GET이 제공한 다른 모든 메서드를 합친 것보다도, 그것도 큰 격차로 더 많이 쓰인다는 것을 알게 된다.
바로 여기서 조건부 GET과 캐싱이 등장한다.
HTTP의 이 표준 기능들을 구현하고 표현을 캐시 가능하게 만들면 애플리케이션이 더 확장 가능해지고, 이는 직접적이고 실질적인 경제적 이득으로 이어진다.

이 세 가지 단순한 일을 하고 나면 더 많은 것을 원하게 될 수 있는데, 그에 대한 조언은 8장에 가득하다.

## WSDL

SOAP은 메시지에 봉투를 제공할 뿐 그 이상은 거의 하지 않는다.
(사양이 떨어지는) 5절을 빼면 SOAP은 메시지 구조를 조금도 제약하지 않는다.
특히 정적 타이핑에 의존하는 환경에서는 사전에 조금 더 많은 정의가 필요하고, 여기서 WSDL이 등장한다.

저자는 배포된 SOAP 인터페이스 중 가장 단순한 축인 weblogs.com의 SOAP 1.1 인터페이스로 WSDL의 개념을 설명한다.
이 인터페이스는 ping이라는 RPC 스타일 함수 하나를 노출한다.
이 함수는 문자열 두 개를 인자로 받아 pingResult 구조체를 반환한다.
이 커스텀 구조체는 불리언인 flerror와 문자열인 message라는 두 엘리먼트를 담는다.
문자열과 불리언은 표준 원시 타입이지만, pingResult를 쓰려면 이를 XML 스키마의 complexType으로 정의해야 하며, 이는 WSDL 파일의 types 엘리먼트 안에서 이뤄진다.

```xml
<types>
  <s:schema targetNamespace="uri:weblogscom">
    <s:complexType name="pingResult">
      <s:sequence>
        <s:element minOccurs="1" maxOccurs="1" name="flerror" type="s:boolean"/>
        <s:element minOccurs="1" maxOccurs="1" name="message" type="s:string"/>
      </s:sequence>
    </s:complexType>
  </s:schema>
</types>
```

커스텀 타입을 정의했으니 다음은 클라이언트와 서버 사이에 오갈 메시지를 정의한다.
여기에는 ping 요청과 ping 응답 두 메시지가 있으며, 요청은 두 부분, 응답은 한 부분으로 이뤄진다.

```xml
<message name="pingRequest">
  <part name="weblogname" type="s:string"/>
  <part name="weblogurl" type="s:string"/>
</message>

<message name="pingResponse">
  <part name="result" type="tns:pingResult"/>
</message>
```

이제 이 메시지들을 WSDL operation 정의에 쓸 수 있고, operation은 port type의 일부로 정의된다.
port는 단순히 operation들의 모음이다.
프로그래밍 언어라면 이를 라이브러리, 모듈, 클래스라고 부를 것이다.
다만 여기는 메시징의 세계라서 연결점을 port라 부르고, port의 추상적 정의를 port type이라 부른다.
아래는 ping이라는 단일 operation을 지원하는 port type이다.

```xml
<portType name="pingPort">
  <operation name="ping">
    <input message="tns:pingRequest"/>
    <output message="tns:pingResponse"/>
  </operation>
</portType>
```

이 시점까지는 정의가 여전히 추상적이다.
문자열 둘을 받아 구조체를 반환하는 이 ping operation을 구현하는 방법은 무수히 많다.
메시지를 SOAP으로 전송한다거나 심지어 XML로 한다는 것조차 아직 지정하지 않았다.
아래는 이 port type을 5절을 준수하는 SOAP 메시지에 바인딩하고 HTTP 위로 보내는, 즉 SOAP/HTTP 바인딩이다.

```xml
<binding name="pingSoap" type="tns:pingPort">
  <soap:binding style="rpc" transport="http://schemas.xmlsoap.org/soap/http"/>
  <operation name="ping">
    <soap:operation soapAction="/weblogUpdates" style="rpc"/>
    <input>
      <soap:body use="encoded" namespace="uri:weblogscom"
        encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"/>
    </input>
    <output>
      <soap:body use="encoded" namespace="uri:weblogscom"
        encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"/>
    </output>
  </operation>
</binding>
```

그래도 아직 끝이 아니다.
마지막 조각은 service를 정의하는 것으로, 이는 port type을 binding과 이어 주고 (SOAP over HTTP이므로) 엔드포인트 URI와 연결한다.

```xml
<service name="weblogscom">
  <document>
    For a complete description of this service, go to the following URL:
    http://www.soapware.org/weblogsCom
  </document>
  <port name="pingPort" binding="tns:pingSoap">
    <soap:address location="http://rpc.weblogs.com:80/"/>
  </port>
</service>
```

문자열 매개변수 두 개를 받아 불리언과 문자열을 반환하는 단일 operation치고는 솔직히 손이 너무 많이 간다.
WSDL이 어떤 단순화 가정도 하지 않기 때문에 이 모든 일을 해야 했다.
요청과 응답을 추상적으로 명세하는 데서 시작해, 이를 operation으로 묶고, port type으로 노출하고, HTTP로 SOAP 메시지를 받는 port를 정의하고, 그 port를 특정 URI에 노출해야 했다.
이 단순한 경우조차 WSDL을 손으로 작성하는 것은 가능하지만 어렵다.
그래서 대부분의 WSDL은 자동화 도구가 생성한다.

여기서 진짜 이야기는 도구가 된다.
도구는 service, binding, port type, message, 스키마, 심지어 네트워크 자체까지 추상화해 버린다.
C#이나 자바 같은 정적 타입 언어로 코딩한다면 버튼 한 번으로 이 모든 WSDL을 생성할 수 있고, 보통은 어떤 클래스의 어떤 메서드를 웹 서비스로 노출할지 고르기만 하면 된다.
오늘날 거의 모든 WSDL은 도구가 생성하고 도구만이 이해할 수 있다.
설정을 마치면 클라이언트 도구가 웹 서비스를 통해 당신의 메서드를 호출하는데, 마치 네이티브 언어 메서드를 부르는 것처럼 보인다.

무엇이 문제인가.
이것이 고수준 개념을 기계어로 바꾸는 컴파일러와 무엇이 다른가.
우려해야 할 점은, 이런 방식이 당신을 웹에서 점점 더 멀어지게 한다는 것이다.
기계어는 고수준 언어를 대신할 수 없지만, 웹은 이미 분산 프로그래밍을 위한 완벽하게 훌륭한 플랫폼이며 그것이 이 책의 요지다.
프로그래밍 언어 메서드를 웹 서비스로 노출하는 이 방식은 HTTP의 오버헤드는 지면서도 앞서 말한 이점은 하나도 얻지 못하는 RPC 스타일을 조장한다.

document/literal 인코딩 같은 새 WSDL 기능조차 RPC 스타일 웹 서비스를 조장한다.
모든 메서드가 POST이고, 여러 작업을 지원하려고 URI를 과부하(overload)시키는 스타일 말이다.
WSDL로 완전히 RESTful하고 리소스 지향적인 웹 서비스를 정의하는 것이 이론적으로 불가능하지는 않다(WSDL 2.0에서는 더 가능해진다).
평평한 바닥에 달걀을 세우는 것도 이론적으로는 가능하다.
할 수는 있지만 내내 환경과 싸워야 한다.

생성된 SOAP/WSDL 인터페이스는 잘 깨지는(brittle) 경향도 있다.
서로 다른 빅 웹 서비스 스택은 표준을 다르게 해석하고 조금씩 다른 WSDL을 생성하며 서로의 메시지를 이해하지 못한다.
그 결과 클라이언트는 같은 스택을 쓰는 서버에 강하게 결합된다.
웹 서비스는 느슨하게 결합되고 회복력이 있어야 한다.
전혀 다른 소프트웨어 도구를 쓸지도 모르는 클라이언트에게 네트워크 너머로 노출되기 때문이다.
웹은 이미 이 목표를 달성할 능력을 입증했다.

무엇보다 나쁜 점은, WSDL의 이 모든 복잡함이 여행 브로커 시나리오를 푸는 데 전혀 도움이 되지 않는다는 것이다.
여행 브로커 문제를 풀려면 “좌석 24C에 대한 5분간의 홀드” 같은 여러 비즈니스 문제를 풀어야 한다.
강한 타이핑과 프로토콜 독립성은 이런 문제들의 해법이 아니다.
때로는 이런 요구사항이 그 자체로 정당화될 수 있지만, 많은 경우 아무도 눈치채지 못하고 이의도 제기되지 않은 채 단순성과 확장성 같은 다른 요구사항을 조용히 갉아먹는다.

### 리소스 지향 대안

실제 웹 서비스에서 WSDL은 두 가지 주된 목적에 쓰인다.
서비스가 노출하는 인터페이스(어떤 RPC 스타일 함수들인지)를 기술하고, 서비스가 받고 보내는 XML 문서의 스키마, 즉 표현 형식을 기술한다.
리소스 지향 서비스에서는 이 기능들이 대개 불필요하거나 훨씬 단순한 표준으로 처리할 수 있다.

RESTful 관점에서 WSDL의 가장 큰 문제는, 그것이 어떤 종류의 인터페이스를 잘 기술하느냐에 있다.
WSDL은 서비스 설계자가 어떤 통일 인터페이스에도 응답하지 않는 하나의 “엔드포인트”에 여러 커스텀 작업을 몰아넣도록 부추긴다.
이 모든 기능이 단일 엔드포인트 URI의 과부하된 POST로만 접근되므로, 결과 서비스는 주소지정성이 없다.
WADL은 웹의 결에 더 맞는 대안적 서비스 기술 언어로, RPC 스타일 함수 호출이 아니라 HTTP의 통일 인터페이스에 응답하는 리소스를 기술한다.

WSDL에는 XML 스키마에 내장된 anyURI 데이터 타입을 넘어서는 하이퍼텍스트 링크 정의 수단이 없다.
SOAP 서비스는 잘 연결되어 있지 않은데, 서비스 전체가 하나의 주소 뒤에 숨어 있으니 어떻게 그럴 수 있겠는가.
WADL은 한 리소스가 다른 리소스로 어떻게 링크되는지를 기술함으로써 이 문제도 해결한다.

표현 형식을 아예 기술할 필요가 없는 경우도 많다.
많은 Ajax 애플리케이션에서는 클라이언트와 서버를 같은 집단이 작성한다.
weblogs.com ping 서비스처럼 그저 데이터 구조를 직렬화해 전송하는 것이 전부라면 표현 형식으로 JSON을 고려하라.
스키마를 정의하지 않고도 꽤 복잡한 데이터 구조를 JSON으로 표현할 수 있고, XML을 쓸 필요조차 없다.

XML이 정말 필요한 경우에도, 형식적으로 정의된 스키마까지는 필요 없는 때가 많다.
이 책 곳곳의 여러 예시에서 클라이언트는 `“/posts/post”` 같은 XPath 표현으로 더 큰 XML 문서에서 원하는 조각을 추출한다.
이런 짧은 문자열이 클라이언트에게 필요한 XML 문서 기술의 전부인 경우가 많다.

XML 스키마 정의가 언RESTful하거나 리소스 지향에 어긋나는 것은 아니다.
스키마 정의는 대개 과잉이지만, 그것이 작업에 맞는 도구라면 쓰면 된다.
다만 그것이 필수여서는 안 된다는 것이 저자의 생각이다.

## UDDI

UDDI에 대한 완전한 설명은 이 책의 범위를 크게 벗어난다.
UDDI는 WSDL을 위한 전화번호부, 즉 클라이언트가 자기 필요에 맞는 서비스를 찾는 방법이라고 생각하면 된다.
UDDI는 WSDL보다 훨씬 더 복잡하다.
UDDI 명세는 웹 서비스 기술에 대한 메타데이터를 제공하는 4계층 계층적 XML 스키마를 정의한다.
UDDI 레지스트리에서 볼 수 있는 데이터 구조 타입은 businessEntity, businessService, bindingTemplate, tModel이다.

UDDI의 비전은 여러 레지스트리로 이뤄진 것이었다.
기업들을 위한 완전 복제된 인터넷 규모 레지스트리 하나와, 이를 두고 싶어 하는 모든 회사의 방화벽 뒤에 놓인 사설 레지스트리들이었다.
2006년 IBM과 마이크로소프트는 자신들의 공용 UDDI 레지스트리를 공개적으로 성공이라 선언한 뒤 폐쇄했다.
이 IBM/마이크로소프트 레지스트리는 5만 개 기업을 기술한다고 보고되었지만, 내부적으로는 그 데이터가 모두 제대로 검증된 것은 아니라는 점이 인정되었고, 이는 채택을 저해했다.

그러니 순전한 복잡성만이 UDDI의 공용 채택이 자리 잡지 못한 유일한 이유는 아니다.
추측이지만, 공용 SOAP 서비스의 수가 상대적으로 적었던 점, 성공한 기업들이 스스로를 범용재화(commoditize)하지 않으려는 일반적 성향, 그리고 웹 서비스마다 고유 인터페이스를 만들도록 조장하는 WSDL의 경향도 추가 요인이었을 것이다.
이는 안타까운 일인데, UDDI는 여행 브로커가 독립적으로 운영되는 호텔을 찾는 데 분명 도움이 될 수 있었기 때문이다.
UDDI는 품질 관리와 통일 인터페이스를 강제하기가 현실적인 기업 내부에서는 더 큰 성공을 거뒀다.

### 리소스 지향 대안

여기에는 만병통치약이 없다.
사람들이 호텔을 찾도록 돕는 자동화 시스템에는 호텔 체인이 그 시스템을 악용할 경제적 유인이 내재한다.
컴퓨터가 그 과정을 도울 수 없다는 뜻은 아니지만, 최종 결정은 사람이 내려야 한다는 뜻이다.

UDDI에 가장 가까운 RESTful 등가물은 구글, 야후!, MSN 같은 검색 엔진이다.
이들은 (사람) 클라이언트가 찾는 리소스를 찾도록 돕고, REST가 촉진하는 통일 인터페이스와 공통 데이터 형식을 활용한다.
이조차 완벽하지는 않다. 스패머가 검색 엔진을 악용하려 하고 때로 성공한다.
그러나 검색 엔진의 가치를 떠올려 보면, UDDI가 복잡성으로 거부감을 주더라도 그것이 약속했던 가능성을 볼 수 있다.

RESTful 웹 서비스가 인기를 얻고 (내부적으로도, 웹 전반과도) 더 잘 연결됨에 따라, 오늘날의 검색 엔진 같은 것이 공용 UDDI 레지스트리의 약속을 실현할지도 모른다.
특정 API를 노출하는 서비스를 찾는 대신, 특정 시맨틱을 가진 표현을 받거나 제공하는 리소스를 찾게 될 것이다.
이 역시 추측이다.
지금으로서는 공용 웹 서비스 디렉터리(부록 A에 몇 개가 실려 있다)는 사람의 사용을 지향한다.

## 보안

“보안”은 서명, 암호화, 키, 신뢰, 페더레이션, 신원 등 많은 관련 개념을 떠올리게 한다.
HTTP의 보안 기법은 거의 전적으로 인증과 메시지 전송에 집중한다.
보안 관련 WS-* 명세들(그 수가 많다)은 더 완전한 그림을 담으려 한다.

WS-Security의 가장 단순한 적용은 UserName 토큰 프로파일이다.
이는 요청에 맥락을 부여하기 위해 봉투에 붙이는 SOAP “스티커”로, 여기서는 누가 요청하는지를 설명한다.

```xml
<Security xmlns:wsse="http://schemas.xmlsoap.org/ws/2002/xx/secext">
  <UsernameToken>
    <Username>Zoe</Username>
    <Password>ILoveDogs</Password>
  </UsernameToken>
</Security>
```

SOAP 메시지의 Header 섹션 안에 놓이면 이것은 일련의 인증 자격 증명을 전달한다.
이는 Authorization HTTP 헤더에 들어가는 HTTP 스티커인 HTTP 기본 인증과 같은 성질을 가진다.

비밀번호를 평문으로 넘기는 것은, 특히 채널이 안전하지 않다면 좋은 관행이 아니다.
WS-Security는 여러 대안을 정의한다.
크게 단순화하면, WS-Security 명세는 다른 표준에서 정의된 개념들(비밀번호, SAML 토큰, X.509 토큰, Kerberos 토큰 등)을 전달하기 위한 일관된 XML 엘리먼트 이름 집합을 정의한다.
비슷한 개념을 HTTP 헤더로 매핑하는 유사한 시도를 못 할 이유는 없다.
HTTP 인증은 확장 가능하며, Atom 개발 초기에는 일부 WS-Security 개념이 WSSE라는 이름으로 HTTP에 이식되기도 했다.

그러나 빅 웹 서비스 보안은 WS-Security 표준 이상을 포괄한다.
두 가지 예를 들면 다음과 같다.
첫째, 서명은 부인방지(nonrepudiation)를 가능하게 한다.
어떤 메시지의 발신자가 누구였는지, 그리고 그 메시지가 수신 후 수정되지 않았음을 나중에 증명할 수 있다.
이런 개념은 계약과 수표에서 중요하다.
둘째, 페더레이션은 제3자가 신원에 대한 신뢰를 중개할 수 있게 한다.
이를 통해 여행 브로커는 특정 인물이 자기 고객사 중 한 곳의 직원임을 검증할 수 있고, 이는 청구와 할인에 영향을 줄 수 있다.

요컨대, 보안 개념은 네이티브 HTTP 프로토콜보다 SOAP 기반 프로토콜에서 훨씬 잘 명세되고 배포되어 있다.
그렇다고 이 격차를 좁힐 수 없다거나, SOAP 스티커를 HTTP 스티커로 이식할 수 없다거나, SOAP 없이 일회성 해법이 불가능하다는 뜻은 아니다.
다만 지금으로서는 SOAP에 HTTP에 없는 보안 관련 스티커가 많고, 이 스티커들은 여행 브로커 같은 애플리케이션을 구현할 때 유용하다.
한 가지 주의할 점은, 이 영역 상당수는 아마추어가 함부로 손댈 곳이 아니라는 것이다.
누구도 혼자서 HTTP에 새 보안 개념을 추가하려 해서는 안 된다.

### 리소스 지향 대안

애플리케이션은 가장 약한 고리만큼만 안전하다.
신용카드 번호를 암호화해 전송한 뒤 그냥 데이터베이스에 저장해 둔다면, 공격자가 데이터베이스를 노리도록 만든 것뿐이다.
보안에 대한 관점은 네트워크로 전송되는 비트뿐 아니라 시스템 전체를 아울러야 한다.

그렇긴 해도 그 비트를 보호하는 도구가 WS-Security 계열 명세만 있는 것은 아니다.
HTTPS(즉 TLS, 즉 SSL)는 신용카드 정보를 네트워크로 전송할 때 실무적으로 충분함이 입증되었다.
사람들은 늘 SSL에 신용카드를 맡기고, 대다수 공격은 SSL을 깨는 것과 무관하다.
XML 서명과 암호화의 사용도 WS-*에 국한되지 않는다.
Atom 신디케이션 형식 표준의 5절은 이 기능들을 Atom 문서에서 쓰는 법을 보이며, S3가 요청 서명과 접근 제어를 구현하는 방식은 3장에서 이미 보았다.
이런 보안 측면은 RESTful 리소스 지향 서비스에서도 가능하며 실제로 배포되어 왔다.
다만 이 기능들을 범용으로 쓸 수 있게 만드는 작업을 아무도 아직 하지 않았을 뿐이다.

결국 최선의 보호는 리소스 지향 아키텍처가 단순성과 통일성을 촉진한다는 사실 자체일 수 있다.
안전한 애플리케이션을 지으려 할 때, 복잡성도 수많은 인터페이스도 이점이 되지 못한다.

## 신뢰할 수 있는 메시징

WS-ReliableMessaging 표준은 일련의 메시지가 AtMostOnce, AtLeastOnce, ExactlyOnce, InOrder 중 하나로 전달됨을 애플리케이션에 보장하려 한다.
이를 위해 시퀀스 식별자와 메시지 번호를 추적하는 새 헤더(봉투에 붙이는 스티커)와 재시도 로직을 정의한다.

### 리소스 지향 대안

이 역시 SOAP 기반 프로토콜의 명세와 구현이 네이티브 HTTP보다 앞선 영역이다.
그러나 이 경우에는 중요한 차이가 있다.
특정 방식으로 쓰면 HTTP는 이런 스티커가 아예 필요 없다.

앞서 말했듯 거의 모든 HTTP 메서드는 멱등(idempotent)하다.
GET, HEAD, PUT, DELETE 작업이 실패했거나 성공 여부를 모른다면, 적절한 대처는 그냥 요청을 재시도하는 것이다.
멱등 작업에서는 AtMostOnce, AtLeastOnce, ExactlyOnce 사이에 차이가 없다.
InOrder를 얻으려면 그저 메시지를 순서대로, 각각이 확실히 전달되도록 하며 보내면 된다.

유일한 비멱등 메서드는 POST이고, 이것이 바로 SOAP이 쓰는 메서드다.
SOAP은 추가 스티커를 정의해 신뢰할 수 있는 전달 문제를 처음부터 새로 푼다.
RESTful 애플리케이션에서 모든 작업에 대해 신뢰할 수 있는 메시징을 원한다면, 저자는 (9장에서 다룬) POST Once Exactly를 구현하거나 POST를 아예 없앨 것을 권한다.
WS-ReliableMessaging 표준은 주로 RESTful 웹 서비스가 아예 다루지 않는 복잡한 시나리오에서 동기가 부여된다.
메시지가 목적지에 이르는 동안 여러 프로토콜을 거쳐 라우팅되는 상황이나, 출발지와 목적지가 모두 네트워크 접속이 간헐적인 휴대전화인 상황 같은 것이다.

## 트랜잭션

트랜잭션은 설명하기는 간단하지만 구현하기는, 특히 분산 환경에서는 지독하게 어렵다.
개념은 이렇다.
“은행 A에서 은행 B로 50달러 이체”처럼 일련의 작업이 있고, 전체가 모두 성공하거나 모두 실패해야 한다.
은행 A와 은행 B는 서로 경쟁하며 별개의 웹 서비스를 노출한다.
은행 A는 출금되고 은행 B는 입금되거나, 아니면 아무 일도 일어나지 않기를 원한다.
입금 없는 출금도, 출금 없는 입금도 바람직하지 않다.

기본 접근은 두 가지다.
WS-AtomicTransaction 표준은 2단계 커밋(two-phase commit)이라는 흔한 알고리즘을 명세한다.
일반적으로 이는 서로 신뢰하는 당사자 사이에서만 현명하지만, 구현이 가장 쉽고 기존 제품의 범위에 들어가므로 가장 널리 배포되어 있다.

두 번째 접근은 WS-BusinessActivity가 정의하며, 실제 비즈니스가 돌아가는 방식을 더 가깝게 따른다.
외국 은행의 수표를 예치하면 당신의 은행은 그것을 보류(hold)해 두고 외국 은행에 확인을 구할 수 있다.
보류 기간이 만료되기 전에 문제를 들으면 트랜잭션을 롤백하고, 그렇지 않으면 수표를 받아들인다.
커밋한 뒤에 문제를 듣게 되면, 예치를 되돌리는 보상 트랜잭션(compensating transaction)을 만든다.
초점은 실수를 애초에 막는 것이 아니라, 감사 가능한 방식으로 실수를 되돌리는 데 있다.

### 리소스 지향 대안

이 역시 네이티브 HTTP 애플리케이션에는 이 수준의 명세와 배포에 대응하는 것이 별로 없고, 대개 아예 필요하지도 않다.
8장에서 저자는 트랜잭션을 리소스로 노출해 트랜잭션 시스템을 구현했지만, 트랜잭션의 당사자가 하나뿐이었으므로 2단계 커밋이 필요하지 않았다.
한 은행 안의 계좌들 사이에서 돈을 옮겼기 때문이다.
그러나 여러 웹 서비스가 이런 종류의 트랜잭션을 지원한다면, 그 위에 약간의 인프라를 얹어 RESTful 2단계 커밋으로 오케스트레이션할 수 있다.

2단계 커밋은 조율하는 서비스에 대한 일정한 통제권과 신뢰를 요구한다.
모든 서비스가 당신 것일 때는 잘 되지만, 경쟁 은행과 협력해야 할 때는 그렇지 않다.
SOA 아키텍트들은 2단계 커밋이 웹 서비스 기반 상호작용 일반에 부적절하다고 보고, 저자는 그것이 RESTful 웹 서비스에도 대개 부적절하다고 본다.
조율하는 서비스를 당신이 통제하지 못할 때, 저자는 WS-BusinessActivity의 발상을 (역시 8장의) 비동기 작업으로 구현할 것을 권한다.

외국 은행 수표 예로 돌아가면, 당신의 은행은 외국 은행의 웹 서비스에 “작업(job)” 리소스를 만들어 수표가 유효한지 물을 수 있다.
그 리소스에 일주일간 갱신이 없으면 은행은 잠정적으로 수표를 받아들일 수 있다.
이틀 뒤 외국 은행이 수표가 부도라며 그 “작업” 리소스를 갱신하면, 당신의 은행은 보상 트랜잭션을 만들어 초과인출 등의 경보를 촉발할 수 있다.
이런 복잡한 시나리오를 만들 일은 아마 없겠지만, 이미 보여 준 패턴들이 이런 새 발상을 구현하는 데 어떻게 쓰일 수 있는지는 알 수 있다.

## BPEL, ESB, SOA

지금까지 설명한 토대 위에 세워진, 빅 웹 서비스 진영 안에서조차 논쟁적인 개념 몇 가지를 간단히 다룬다.

BPEL(Business Process Execution Language)은 여러 당사자에 걸친 비즈니스 프로세스를 기술할 수 있게 하는 XML 문법이다.
이 프로세스들은 소프트웨어와 웹 서비스를 통해 자동으로 오케스트레이션될 수 있다.

ESB(Enterprise Service Bus)의 정의는 제각각이지만, 대체로 웹 서비스 요청의 발견, 로드 밸런싱, 라우팅, 브리징, 변환, 관리를 포함한다.
이는 흔히 운영과 개발의 분리로 이어져, 각각을 더 단순하고 운영하기 쉽게 만든다.

BPEL과 ESB의 단점은 공통 제3자 미들웨어와의 결합과 의존을 키우는 경향이 있다는 것이다.
한 가지 장점은 미들웨어 선택지가 여럿이라는 점으로, 잘 지원되는 오픈소스부터 자리 잡힌 유명 상용 벤더의 것까지 다양하다.

SOA(Service-Oriented Architecture)는 아마 이 모든 용어 중 가장 정의가 불분명하며, 그래서 저자는 1장에서 쓰지 않겠다고 밝힌 용어다.
어떤 구현이 SOA인지 아닌지를 가리는 리트머스 시험 같은 것을 저자는 알지 못한다.
때때로 SOA 논의는 SOA가 모든 REST/HTTP 애플리케이션을 포괄한다는 말로 시작하지만, 결국 초점은 이 장에서 설명한 빅 웹 서비스 표준으로 옮겨간다.

그렇긴 해도 SOA의 한 측면은 주목할 만하다.
지금껏 분산 프로그래밍에 대한 많은 접근은 원격 프로시저 호출을 가능한 한 로컬 프로시저 호출과 구별되지 않게 만드는 데 힘썼다.
기존 애플리케이션에서 생성한 WSDL 파일이 그 예다.
반면 SOA 발상은 적어도 초점을 인터페이스로, 특히 기계 경계(machine boundary)를 넘나드는 인터페이스로 되돌린다.
기계 경계는 우연히 생기는 법이 별로 없다.
그것은 흔히 신뢰 경계와 상관되고, 메시지 신뢰성이 문제가 되는 지점이기도 하다.
기계 경계는 추상화해 없앨 것이 아니라 연구되어야 한다.

SOA의 다른 측면들은 서비스의 기술적 아키텍처와 독립적이다.
그것들은 리소스 지향 환경, 원격 프로시저 호출 서비스로 가득한 환경, 또는 이질적인 환경 어디서든 구현될 수 있다.
예컨대 “거버넌스(governance)”는 감사와 정책 준수에 관한 것이다.
이 “정책”은 정부 규제부터 아키텍처 원칙까지 무엇이든 될 수 있다.
가능한 정책 하나는 “RPC 스타일 웹 서비스 호출을 하지 말라”일 것이다.

## 결론

REST와 웹 서비스는 둘 다 유행어(buzzword)가 되었다.
멋지고 세련된 말이 되어, 주제를 제대로 이해하지 못하는 사람들이 파워포인트 발표에 교묘히 엮어 넣는다.
이 장, 나아가 이 책은 그 혼란을 걷어 내려는 시도다.

이 장에서 당신은 SOAP이 가져다주는 가치(그리 크지 않다)와 WSDL이 가져오는 복잡성(지나치게 크다)을 직접 보았다.
또한 매 단계마다 리소스 지향 대안이 함께 제시되었다.
이 장에서 설명한, SOAP 봉투의 스티커로만 제공되는 기능이 정말 필요하리라는 것을 미리 안다면, 처음부터 SOAP 경로로 시작하는 것이 쌓아 올릴 기반을 마련해 줄 것이다.

그 대안은 가볍게 시작하고 YAGNI(You Aren't Gonna Need It) 원칙을 적용해, 실제로 필요하다고 아는 기능만 더해 가는 것이다.
빅 웹 서비스만이 제공하는 스티커가 정말 필요해지면, 언제든 XML 표현을 SOAP 봉투로 감싸거나, 필요한 스티커만 골라 HTTP 헤더로 이식할 수 있다.
입증된 웹의 확장성을 생각하면, 단순하게 시작하는 것은 대개 안전한 선택이며, 저자가 보기에 이는 기본값으로 삼을 만큼 충분히 안전하다.

## 핵심 정리

빅 웹 서비스(SOAP/WSDL/UDDI/WS-*)는 항공·호텔·렌터카를 묶는 여행 브로커처럼 프로세스 지향적이고 브로커를 거치며 공유 상태와 확약을 다루는 분산 서비스를 겨냥한다.
이는 리소스 지향적인 웹과 결이 다르며, 그래서 주로 기업·정부 영역에서 나타난다.

SOAP 자체는 XML 문서를 Envelope와 Body로 감싸는 얇은 봉투 규약에 불과하다.
문제는 그 위에 얹힌 것들이다.
SOAP 툴킷은 HTTP 상태 코드를 거의 안 쓰고 모든 작업을 단일 URI의 POST로 몰아 RPC 스타일을 조장하므로, 주소지정성·캐시성·연결성·통일 인터페이스라는 REST의 이점을 잃는다.

WSDL은 단순화 가정을 하지 않아 사소한 서비스에도 types, message, portType, binding, service를 층층이 요구한다.
그 결과 도구 없이는 다루기 어렵고, 스택마다 해석이 달라 잘 깨지며 클라이언트를 서버에 강하게 결합시킨다.
리소스 지향 대안으로는 통일 인터페이스와 링크를 기술하는 WADL, 스키마 없는 JSON, XPath 같은 가벼운 수단이 있다.

UDDI는 WSDL을 위한 전화번호부였으나 복잡성 등으로 공용 채택에 실패했고(2006년 IBM/MS 공용 레지스트리 폐쇄), 그 약속은 검색 엔진이 사람 중심으로 대신 실현하고 있다.

보안·신뢰 메시징·트랜잭션 영역은 SOAP 기반 명세가 HTTP보다 앞서 있는 것이 사실이다.
그러나 HTTP 메서드의 멱등성 덕분에 신뢰 메시징은 대부분 재시도로 해결되고(비멱등 POST는 POST Once Exactly로 대처), 보안은 HTTPS와 XML 서명·WSSE로, 다자 트랜잭션은 리소스와 비동기 보상 트랜잭션(WS-BusinessActivity의 발상)으로 다룰 수 있다.

BPEL/ESB는 제3자 미들웨어 결합을 키우고, SOA는 정의가 모호하나 “기계 경계를 추상화하지 말고 연구하라”는 통찰만은 새길 만하다.
저자의 결론은 YAGNI다.
단순하게 시작하고, 정말 필요할 때만 SOAP 스티커를 골라 붙이거나 HTTP 헤더로 이식하라.
입증된 웹의 확장성을 생각하면 단순한 시작이 안전한 기본값이다.
