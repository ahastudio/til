### 사용할 수 있는 서비스

저자는 읽기 전용 리소스 지향 서비스와 읽기/쓰기 REST-RPC 하이브리드는 흔하고 잘 이해된 반면, 클라이언트가 리소스를 생성·수정할 수 있는 진짜 읽기/쓰기 RESTful 서비스는 상대적으로 드물다고 지적하며, 그런 서비스를 소개하는 데 초점을 둡니다.

서비스 디렉터리입니다.

- ProgrammableWeb — 가장 인기 있는 웹 서비스 디렉터리. 다만 REST-RPC 하이브리드를 “REST”로 분류하는 등 용어가 정확하지 않은 편.
- servicereg.com — 등록된 서비스는 거의 없지만, 서비스 목록 자체를 Atom Publishing Protocol을 말하는 “컬렉션” 리소스로 노출한다는 점이 흥미로움.
- MicroApps — Amazon S3처럼 다른 애플리케이션의 구성 요소로 쓰이도록 설계된 RESTful 애플리케이션에 초점.

읽기 전용 서비스 예시입니다.

- irrepressible.info — 여러 정부가 검열한 자료의 확산을 돕는 신디케이션 피드 모음.
- Audioscrobbler — 음악과 청취자에 관한 대규모 데이터셋을 노출.
- Coral Content Distribution Network — 웹 리소스의 분산 캐시에 대한 단순한 인터페이스 제공.

읽기/쓰기 서비스 예시입니다.
Atom Publishing Protocol(APP, 9장)이 읽기/쓰기 RESTful 서비스의 가장 인기 있는 모델입니다.

- Google의 여러 사이트가 APP 확장인 GData를 노출 (Blogger, Google Calendar, Google Notebook 등).
- Ning에 호스팅된 애플리케이션들이 APP를 노출.
- 43 Things — 인생 목표 목록을 APP 컬렉션으로 노출 (REST-RPC 하이브리드도 함께 노출).
- Blogmarks — del.icio.us 유사 소셜 북마킹 서비스로 북마크 목록을 APP 컬렉션으로 노출.
- Lotus Connections, Lotus Quick — APP에 응답하는 리소스 노출.

APP를 쓰지 않고 균일 인터페이스로 커스텀 RESTful 리소스를 노출하는 서비스들도 있습니다.

- Amazon S3 (3장) — Amazon 서버에 데이터를 저장하고 HTTP나 BitTorrent로 제공. 저장 공간과 대역폭에 과금하며, 저자는 가장 견고한 비즈니스 모델을 가진 웹 서비스로 평가.
- Amazon Simple Queue Service — 한쪽이 큐에 메시지를 넣고 다른 쪽이 읽어 시스템의 두 부분을 분리(decouple).
- BlinkSale API — 청구서 관리를 위한 RESTful 리소스 노출.
- Stikkit API — 짧은 메모를 위한 읽기/쓰기 리소스 노출.
- CouchDb — RESTful 웹 서비스로 접근하는 “문서 데이터베이스”.
- Object HTTP Mapper — Python 객체를 RESTful 리소스로 노출하는 클라이언트/서버.
- Beast 포럼 패키지 — ActiveResource 호환 웹 서비스를 노출하는 Rails 애플리케이션. 협업용 강화판은 Dev'il.
- linkaGoGo — 북마크를 담은 중첩 폴더를 리소스로 갖는 또 다른 소셜 북마킹 사이트.
- OpenStreetMap — 자유롭게 이용 가능한 지도 데이터 프로젝트로, 지구 도로 지도에 대한 RESTful 인터페이스 제공. 리소스는 이미지나 장소가 아니라 지도를 이루는 점과 벡터.
- Numbler — 스프레드시트, 셀, 셀 범위를 리소스로 노출.
- NEEScentral Web Services API — 지진공학자를 위한 서비스로 Experiments, Trials, SensorPools 등의 리소스를 노출.
- Fozzy — 전문(full-text) 검색에 대한 RESTful 인터페이스를 노출하는 설치형 애플리케이션.
- Tasty — 태깅에 대해 Fozzy와 유사한 일을 수행.
- MusicBrainz — 앨범 메타데이터(아티스트, 트랙명 등)를 관리. HTTP의 전체 균일 인터페이스를 쓰지 않고 PUT 대신 오버로드된 POST를 사용하지만, GET할 때와 같은 URI에 POST하므로 여전히 리소스 지향적.
- Subversion, Arch 같은 현대 버전 관리 시스템 — 리소스 지향 HTTP 인터페이스로 동작. WebDAV, DeltaV가 정의한 확장 메서드(COPY, CHECKOUT 등)를 채택해 리소스당 최대 26개 메서드의 풍부한 인터페이스를 갖지만, 표준 메서드를 쓰지 않아 나머지 웹과 분리되는 단점이 있음 (Arch는 표준 메서드만으로도 동작 가능).

## 부록 B: HTTP 상태 코드

저자는 인간 웹에서는 상태 코드가 거의 무시되어 오류에도 200(“OK”)을 보내는 경우가 많지만, 프로그래머블 웹에서는 사람이 없으므로 상태 코드가 매우 중요하다고 강조합니다.
클라이언트나 중개자(방화벽 등)는 응답의 첫 3바이트만 보고도 요청이 어떻게 처리되었는지 판단할 수 있습니다.
이 부록은 HTTP 표준의 41개 코드 전부와 WebDAV 확장 코드 207(“Multi-Status”)까지 다룹니다.

### 최소한의 3~7개 코드

상태 코드의 난립이 부담스럽다면, 다음 세 개만으로도 클라이언트가 응답을 처리하는 데 필요한 기본 정보를 전달할 수 있습니다.

- 200 (“OK”) — 모든 것이 정상. 엔티티 바디는 어떤 리소스의 표현.
- 400 (“Bad Request”) — 클라이언트 쪽 문제. 엔티티 바디는 오류 메시지.
- 500 (“Internal Server Error”) — 서버 쪽 문제. 엔티티 바디는 오류 메시지이지만 클라이언트가 서버 문제를 고칠 수는 없음.

여기에 웹 서비스에서 특히 흔한 네 개를 더할 수 있습니다.

- 301 (“Moved Permanently”) — 리소스의 URI가 바뀌었을 때, 또는 클라이언트가 예전 URI로 요청했을 때.
- 404 (“Not Found”) — 클라이언트가 어떤 리소스에도 대응하지 않는 URI를 요청. 서버가 무엇을 찾는지 전혀 모를 때.
- 410 (“Gone”) — 예전에 리소스가 있었지만 이제 없음을 서버가 알 때.
- 409 (“Conflict”) — 하나 이상의 리소스를 불일치 상태로 만드는 작업을 시도했을 때.

SOAP 웹 서비스는 200(“OK”)과 500(“Internal Server Error”)만 사용하며, 무슨 일이 일어났는지 알려면 SOAP 문서 본문의 “fault”를 파싱해야 한다고 저자는 지적합니다.

### 1xx: 메타

1xx 계열은 HTTP 서버와의 협상(negotiation)에서만 사용됩니다.

| 코드                        | 중요도                  | 의미와 용도                                                                                                 |
| --------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------- |
| 100 (“Continue”)            | 중간 (집필 시점 드물게) | LBYL(look-before-you-leap) 요청에 대한 응답. 클라이언트가 생략했던 표현을 포함해 원 요청을 재전송하라는 뜻. |
| 101 (“Switching Protocols”) | 매우 낮음               | 클라이언트가 `Upgrade` 헤더로 다른 프로토콜을 원할 때. “이제 다른 프로토콜로 말하겠다”는 의미.              |

100(“Continue”)을 받으려면 클라이언트는 `Expect` 헤더를 리터럴 값 `100-continue`로 설정하고, 서버가 100/417 판단에 필요한 다른 헤더들도 함께 보내야 합니다.
LBYL 요청의 다른 가능한 응답은 417(“Expectation Failed”)입니다.
101에서 서버가 업그레이드를 수용하면 어떤 프로토콜로 전환하는지 담은 `Upgrade` 헤더와 빈 줄을 보낸 뒤, TCP 연결을 닫지 않고 새 프로토콜로 말하기 시작합니다.

### 2xx: 성공

2xx 계열은 작업이 성공했음을 나타냅니다.

| 코드                                  | 중요도                                | 의미와 용도                                                                                 |
| ------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------- |
| 200 (“OK”)                            | 매우 높음                             | 서버가 요청한 작업을 성공적으로 수행했고 더 구체적인 2xx 코드가 부적절할 때.                |
| 201 (“Created”)                       | 높음                                  | 클라이언트 요청으로 새 리소스를 생성했을 때.                                                |
| 202 (“Accepted”)                      | 중간                                  | 요청을 실시간으로 처리하지 않고 나중에 처리. 비동기 작업 등에 적합.                         |
| 203 (“Non-Authoritative Information”) | 매우 낮음                             | 200과 같으나 일부 응답 헤더가 서버가 아닌 제3자나 이전 요청에서 온 것임을 알림.             |
| 204 (“No Content”)                    | 높음                                  | PUT/POST/DELETE 응답으로 상태 메시지나 표현을 보내지 않을 때. Ajax에서 자주 사용.           |
| 205 (“Reset Content”)                 | 낮음                                  | 204와 같으나 클라이언트가 데이터 입력 폼/뷰를 원래 값으로 리셋해야 함을 함의.               |
| 206 (“Partial Content”)               | 부분 GET 지원 시 매우 높음/그 외 낮음 | `Range` 요청 헤더를 쓴 부분 GET에 대한 응답. 큰 이진 표현의 중단된 다운로드 재개 등에 사용. |
| 207 (“Multi-Status”)                  | 낮음~중간                             | WebDAV 확장. 배치 요청 응답에서 각 작업별 상태 코드 목록을 엔티티 바디로 전달.              |

201(“Created”)은 `Location` 헤더에 새 리소스의 정식(canonical) URI를 담고, 엔티티 바디로 새 리소스를 설명·링크해야 합니다.
202(“Accepted”)는 대기 중인 요청을 리소스로 노출해 `Location`으로 가리키고, 확인 수단이 없다면 처리 예상 시각이라도 제공하는 것이 좋습니다.
204와 205의 엔티티 바디는 허용되지 않습니다. 204는 한 레코드를 여러 번 편집할 때, 205는 여러 레코드를 연달아 입력할 때 유용합니다.
206은 `Date` 헤더가 필수이고, `ETag`와 `Content-Location`은 표현 전체를 보낼 때와 같은 값이어야 하며, 각 바이트 범위마다 `Content-Range` 헤더가 필요합니다.
207의 엔티티 바디는 WebDAV 어휘(RFC 2518)를 쓰는 XML 문서여야 합니다.

### 3xx: 리다이렉션

3xx 계열은 클라이언트가 원하는 것을 얻으려면 추가 작업이 필요함을 나타냅니다.
주로 GET에 쓰이며, 대개 다른 URI로 두 번째 GET을 보내라는 뜻이고 그 URI는 `Location` 응답 헤더에 담깁니다.
저자는 301, 302, 303, 307이 매우 비슷해 혼동의 원천이라고 지적하며 이를 정리하는 데 이 절의 목표를 둡니다.

| 코드                       | 중요도                                  | 의미와 용도                                                                                    |
| -------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 300 (“Multiple Choices”)   | 낮음                                    | 요청한 리소스의 표현이 여럿이고 어느 것을 원하는지 모를 때. 표현 URI 목록을 제공 가능.         |
| 301 (“Moved Permanently”)  | 중간                                    | 리소스는 알지만 사용된 URI가 마음에 안 들 때. 새 URI를 기억하고 앞으로 사용하라는 뜻.          |
| 302 (“Found”)              | 알아둘 것(특히 클라이언트), 사용 비권장 | 리다이렉션 혼동의 근원. 원래 307처럼 다뤄져야 하나 실제로는 303처럼 처리됨. 303/307 사용 권장. |
| 303 (“See Other”)          | 높음                                    | 요청은 처리했고, 응답 문서 대신 그 문서의 URI를 알려줌. 클라이언트는 그 URI로 GET.             |
| 304 (“Not Modified”)       | 높음                                    | 조건부 GET에서 표현이 바뀌지 않았을 때. 바디를 다시 보내 대역폭을 낭비할 필요 없음.            |
| 305 (“Use Proxy”)          | 낮음                                    | 지정된 HTTP 프록시를 거쳐 요청을 반복하라는 뜻. 드물게 사용.                                   |
| 306: Unused                | 없음                                    | HTTP 표준에 들어가지 못한 코드(“Switch Proxy”). 신경 쓸 필요 없음.                             |
| 307 (“Temporary Redirect”) | 높음                                    | 요청한 리소스가 다른 URI에 있어 처리하지 않음. 클라이언트는 전체 요청을 재전송해야 함.         |

300은 서버가 선호 표현이 있으면 `Location`에 담을 수 있고, 엔티티 바디로는 사용자가 고를 수 있도록 주석이 달린 URI 목록(XHTML 링크 목록이 적합)을 제공합니다.
301/302/303/307은 모두 `Location`에 대상 URI를 담고, 새 URI로 연결되는 하이퍼텍스트 문서를 엔티티 바디로 보내는 것이 좋습니다.
303은 리소스를 정규화(canonicalize)하는 좋은 방법으로, 여러 URI가 하나의 “진짜” URI를 303으로 가리키게 할 수 있습니다.
304는 `Date` 헤더가 필수이고 `ETag`, `Content-Location`은 200일 때와 같은 값이어야 하며, 캐싱 헤더 `Expires`, `Cache-Control`, `Vary`는 이전과 달라졌다면 필수입니다. 엔티티 바디는 허용되지 않습니다.

303과 307의 차이를 저자는 약국 비유로 설명합니다.
GET에서는 둘이 동일하지만, POST/PUT/DELETE에서 303은 “처방을 조제했으니 옆 창구에서 약을 받으세요”(작업 성공, 응답 바디는 다른 URI에서 GET), 307은 “그 처방은 못 지어드립니다. 옆 약국으로 가세요”(작업을 시도조차 안 함, 전체 요청을 재전송)를 뜻합니다.

### 4xx: 클라이언트 측 오류

4xx 계열은 클라이언트 쪽에 문제가 있음을 나타냅니다.

| 코드                                    | 중요도       | 의미와 용도                                                                              |
| --------------------------------------- | ------------ | ---------------------------------------------------------------------------------------- |
| 400 (“Bad Request”)                     | 높음         | 다른 4xx가 적절치 않을 때 쓰는 일반 클라이언트 오류. 형식은 맞지만 말이 안 되는 표현 등. |
| 401 (“Unauthorized”)                    | 높음         | 보호된 리소스에 올바른 인증 자격 증명 없이 접근. 자격 증명이 틀렸거나 없음.              |
| 402 (“Payment Required”)                | 없음         | 이름만 있고 정의되지 않음(“향후 사용 예약”). HTTP용 소액결제 시스템이 없기 때문.         |
| 403 (“Forbidden”)                       | 중간         | 요청 형식은 맞지만 서버가 수행을 원치 않음. 자격 증명 부족(401)과는 다름.                |
| 404 (“Not Found”)                       | 높음         | URI를 리소스에 매핑할 수 없음. 401/403을 감추기 위한 거짓일 수도 있음.                   |
| 405 (“Method Not Allowed”)              | 중간         | 이 리소스가 지원하지 않는 HTTP 메서드를 사용.                                            |
| 406 (“Not Acceptable”)                  | 중간         | `Accept-*` 제약이 너무 많아 서버가 어떤 표현도 보낼 수 없을 때.                          |
| 407 (“Proxy Authentication Required”)   | 낮음         | 401과 같으나 문제는 웹 서비스가 아니라 프록시 인증.                                      |
| 408 (“Request Timeout”)                 | 낮음         | 연결만 열고 요청(또는 요청 끝 빈 줄)을 보내지 않을 때 서버가 연결을 닫으며 응답.         |
| 409 (“Conflict”)                        | 높음         | 리소스를 불가능하거나 불일치한 상태로 만들려 할 때.                                      |
| 410 (“Gone”)                            | 중간         | 예전엔 있었지만 이제 없고, 새 URI도 모를 때. 404보다 조금 더 많은 정보 제공.             |
| 411 (“Length Required”)                 | 낮음~중간    | 서버가 `Content-Length`를 요구하는데 클라이언트가 보내지 않았을 때.                      |
| 412 (“Precondition Failed”)             | 중간         | 요청 헤더의 전제 조건(precondition)이 충족되지 않았을 때.                                |
| 413 (“Request Entity Too Large”)        | 낮음~중간    | 서버가 처리하기에 표현이 너무 클 때. 연결을 끊을 수 있음.                                |
| 414 (“Request-URI Too Long”)            | 낮음         | URI가 서버의 상한을 넘을 때. 대개 바디에 들어갈 데이터를 URI에 넣은 것이 원인.           |
| 415 (“Unsupported Media Type”)          | 중간         | 서버가 이해 못 하는 미디어 타입의 표현을 보냈을 때(예: XML 기대에 JSON).                 |
| 416 (“Requested Range Not Satisfiable”) | 낮음         | 표현이 너무 작아 요청한 바이트 범위가 적용되지 않을 때.                                  |
| 417 (“Expectation Failed”)              | 중간(드물게) | 100(“Continue”)의 반대 면. LBYL 요청을 서버가 거부할 때.                                 |

401은 `WWW-Authenticate` 헤더로 어떤 인증을 받는지 알리고, 엔티티 바디로 실패 사유와 필요한 자격 증명을 설명합니다.
서버는 리소스 존재를 숨기려고 401/403 대신 404(“Not Found”)로 거짓말할 수 있습니다.
403이 클라이언트 오류(4xx)인 이유는, 서버가 요청의 형식이 아니라 요청 시각 같은 다른 측면을 근거로 판단하기 때문입니다.
405는 `Allow` 헤더에 지원 메서드를 나열합니다 (예: `Allow: GET, POST`).
407은 자격 증명을 `Authorization` 대신 `Proxy-Authorization`으로 보내고, 서버는 `Proxy-Authenticate`로 요구합니다. 프록시와 웹 서비스가 모두 인증을 요구하면 407을 해결한 뒤 401을 다시 만날 수 있습니다.
409는 충돌 원인이 다른 리소스라면 `Location`으로 그 리소스를 가리키고, 엔티티 바디로 충돌 내용을 설명합니다.
410은 성공한 DELETE 응답으로 쓰기엔 부적절하며(클라이언트가 자신이 지운 건지 원래 없던 건지 알 수 없음), DELETE 성공의 올바른 응답은 200(“OK”)입니다.

412와 조건부 요청의 관계는 다소 미묘합니다.
`If-Match`, `If-None-Match`, `If-Unmodified-Since` 헤더로 이 코드를 받을 수 있습니다.
단, GET/HEAD 요청에서 `If-None-Match`의 전제 조건이 실패하면 412가 아니라 304(“Not Modified”)가 반환되며(이것이 조건부 HTTP GET의 기초), PUT/POST/DELETE에서 `If-None-Match`가 실패하거나 `If-Match`/`If-Unmodified-Since`가 실패하면 412가 반환됩니다.
413은 문제가 서버 측 일시적 자원 부족일 수 있어 `Retry-After` 헤더를 함께 보낼 수 있습니다.
415에서 미디어 타입은 맞지만 형식(어휘)이 틀린 경우엔 더 일반적인 400이 낫고, 특별히 다루려면 WebDAV 확장 422(“Unprocessable Entity”)를 쓸 수 있습니다.
416은 요청에 `Range` 필드가 있을 때만 반환되며(`If-Range`가 있으면 반환 안 함), 응답에 실제 표현 크기를 담은 `Content-Range` 필드를 보내야 합니다.

### 5xx: 서버 측 오류

5xx 계열은 서버 쪽 문제를 나타냅니다.
대개 서버가 요청을 실행하거나 정확성을 확인할 상태가 아니라는 뜻이며, 클라이언트는 나중에 재시도해야 합니다.
서버는 재시도 시점을 `Retry-After` 응답 헤더에 담을 수 있습니다.

| 코드                               | 중요도    | 의미와 용도                                                                     |
| ---------------------------------- | --------- | ------------------------------------------------------------------------------- |
| 500 (“Internal Server Error”)      | 높음      | 일반 서버 오류. 대부분의 웹 프레임워크가 핸들러 코드에서 예외 발생 시 반환.     |
| 501 (“Not Implemented”)            | 낮음      | 서버가 인식조차 못 하는 HTTP 기능(예: WebDAV의 COPY)을 사용하려 할 때.          |
| 502 (“Bad Gateway”)                | 낮음      | HTTP 프록시에서만 발생. 프록시나 프록시-상위 서버 사이의 문제.                  |
| 503 (“Service Unavailable”)        | 중간~높음 | HTTP 서버는 살아있지만 하부 웹 서비스가 정상 동작 안 함. 대개 자원 고갈이 원인. |
| 504 (“Gateway Timeout”)            | 낮음      | 프록시에서만 발생. 프록시가 상위 서버에 연결하지 못함.                          |
| 505 (“HTTP Version Not Supported”) | 매우 낮음 | 서버가 클라이언트가 쓰려는 HTTP 버전을 지원하지 않음.                           |

501은 405(“Method Not Allowed”)와 비슷하지만, 405는 인식된 메서드를 지원하지 않는 리소스에 썼다는 뜻이고 501은 메서드 자체를 서버가 인식하지 못한다는 뜻입니다.
프록시가 상위 서버에 아예 닿지 못하면 502가 아니라 504가 반환됩니다.
503은 반복 요청이 원인일 가능성이 높으므로, 서버가 요청을 받아 503을 보내는 대신 아예 거부할 수도 있고, `Retry-After`로 재시도 시점을 알릴 수 있습니다.
505의 엔티티 바디는 서버가 지원하는 프로토콜을 설명하는 문서를 담아야 합니다.

## 부록 C: HTTP 헤더

저자는 각 헤더가 요청/응답 중 어디에 나타나는지, 리소스 지향 웹 서비스를 만들 때 얼마나 유용한지에 대한 견해와 짧은 설명을 제공합니다.
헤더는 봉투 위의 정보 스티커에 비유되며, 자신만의 메서드나 응답 코드를 만드는 것은 나쁜 형식이지만 자신만의 헤더(스티커)를 만드는 것은 괜찮다고 봅니다.
커스텀 헤더 지침은 다음과 같습니다.
기존 헤더를 재발명하지 말고, 엔티티 바디에 속할 것을 헤더에 넣지 말며, 확장을 뜻하는 `X-` 접두어 명명 규칙을 따르라는 것입니다.
Amazon S3는 `X-amz-acl`, `X-amz-date`를 정의하고 `X-amz-meta-`로 시작하는 임의 헤더로 메타데이터를 저장하게 하는 좋은 예입니다.

### 표준 헤더 — 요청 헤더

| 헤더                  | 중요도       | 의미와 용도                                                                                     |
| --------------------- | ------------ | ----------------------------------------------------------------------------------------------- |
| `Accept`              | 중간         | 서버가 표현에 써주길 바라는 데이터 형식을 알림(예: JSON, RDF).                                  |
| `Accept-Charset`      | 낮음         | 표현에 써주길 바라는 문자 집합을 알림.                                                          |
| `Accept-Encoding`     | 중간~높음    | `compress`, `gzip` 같은 압축 알고리즘으로 응답 바디를 압축해도 됨을 알림.                       |
| `Accept-Language`     | 낮음         | 표현에 써주길 바라는 자연어를 알림.                                                             |
| `Authorization`       | 매우 높음    | 사용자명/비밀번호 등 인증 자격 증명을 합의된 방식으로 인코딩해 담음. HTTP Basic/Digest 등.      |
| `Expect`              | 중간(드물게) | LBYL 요청 신호. 서버는 진행하라면 100, 아니면 417로 응답.                                       |
| `From`                | 매우 낮음    | 요청자의 이메일 주소. 프라이버시 문제로 거의 사용 안 됨.                                        |
| `Host`                | 필수         | URL의 도메인 이름 부분. 이름 기반 가상 호스팅 때문에 HTTP 1.1에서 필수.                         |
| `If-Match`            | 중간         | `If-Unmodified-Since`와 같은 역할이되 값으로 `ETag`를 받음.                                     |
| `If-Modified-Since`   | 매우 높음    | 조건부 HTTP GET의 근간. 이전 `Last-Modified` 값을 담아, 바뀌었을 때만 새 바디를 받음.           |
| `If-None-Match`       | 매우 높음    | 조건부 GET에 사용. 이전 `ETag` 값을 담아, `ETag`가 바뀌었을 때만 새 바디를 받음.                |
| `If-Range`            | 낮음         | 조건부 부분 GET. 해당 부분이 바뀌었을 때만 새 범위를 받음.                                      |
| `If-Unmodified-Since` | 중간         | `Last-Modified` 값을 담아 GET 이외 동작을 조건부로 만듦.                                        |
| `Max-Forwards`        | 매우 낮음    | 주로 TRACE 메서드에서 요청이 거칠 수 있는 프록시 수를 제한.                                     |
| `Pragma`              | 매우 낮음    | 특수 지시자용. 유일한 공식 값 `no-cache`는 HTTP 1.1에서 폐기됨.                                 |
| `Proxy-Authorization` | 낮음~중간    | 인증을 요구하는 프록시를 통과하려는 시도. `Authorization`과 유사.                               |
| `Range`               | 중간         | 리소스 표현의 일부만 요청(부분 GET). 흔히 `If-Unmodified-Since`와 함께 사용.                    |
| `Referer`             | 낮음         | 방금 있던 페이지의 URI. 프로그래머블 웹에서는 드묾. (철자가 틀린 채로 표준화됨.)                |
| `TE`                  | 낮음         | 클라이언트가 받아들일 전송 인코딩을 지정. 실질적으로 chunked 인코딩 이해 여부를 전달.           |
| `Upgrade`             | 매우 낮음    | HTTP 대신 쓰고 싶은 프로토콜 목록. 서버가 지원하면 101로 응답.                                  |
| `User-Agent`          | 높음         | 요청하는 소프트웨어의 종류를 알림. 통계·불량 클라이언트 차단에만 쓰고 표현 재단에는 쓰지 말 것. |

`Accept` 계열(`Accept`, `Accept-Charset`, `Accept-Language`)에 대해 저자는 표현을 구분하는 유일한 수단으로 삼지 말고, 서로 다른 표현은 서로 다른 URI로 노출하되 이 헤더 지원은 보너스로 얹으라고 권합니다.
`Authorization`은 확장 가능하므로 이론상 유일하게 필요한 인증 헤더이지만, 실제로는 그 위에서 동작하는 `X-WSSE` 같은 비공식 헤더로 HTTP가 확장되어 왔습니다.
`If-Modified-Since`는 1초 단위 정확도라 가끔 틀린 결과를 낼 수 있어, `ETag`/`If-None-Match`를 두 번째 방어선으로 함께 씁니다.
`User-Agent`에 대해서는 인간 웹에서 벌어진 브라우저 스니핑과 그로 인한 “Mozilla를 사칭하는” 군비 경쟁을 경계하며, 프로그래머블 웹에서 같은 일이 반복되지 않도록 표현 재단에 쓰지 말라고 강조합니다.

### 표준 헤더 — 응답 헤더

| 헤더                 | 중요도                 | 의미와 용도                                                                               |
| -------------------- | ---------------------- | ----------------------------------------------------------------------------------------- |
| `Accept-Ranges`      | 낮음~중간              | 해당 URI에 대해 부분 GET을 지원함을 알림.                                                 |
| `Age`                | 낮음                   | 응답 바디가 서버를 떠난 지 얼마나 됐는지. 주로 캐시가 설정.                               |
| `Allow`              | 잠재적 높음, 현재 낮음 | OPTIONS 응답으로, 해당 URI가 노출하는 균일 인터페이스의 부분집합을 알림.                  |
| `Content-Encoding`   | 중간~높음              | `Accept-Encoding`의 짝. 서버가 실제로 어떤 압축 알고리즘을 썼는지 알림.                   |
| `Content-Language`   | 중간                   | `Accept-Language`의 짝. 바디에서 의미를 얻으려면 이해해야 할 자연어를 명시.               |
| `Content-Length`     | 높음                   | 엔티티 바디의 크기(바이트). HEAD로 크기만 미리 알아볼 수도 있음.                          |
| `Content-Location`   | 낮음                   | 요청한 리소스의 정식 URI를 순전히 정보 제공용으로 알림(`Location`과 달리 이동 요구 아님). |
| `Content-MD5`        | 낮음~중간              | 바디의 암호학적 체크섬. 전송 중 손상 검출용(보안용 아님).                                 |
| `Content-Range`      | 낮음~중간              | `Range` 부분 GET에서 클라이언트가 표현의 어느 부분을 받는지 알림.                         |
| `Content-Type`       | 매우 높음              | 가장 유명한 응답 헤더. 바디가 어떤 종류인지 알려 파서/표시 방법을 결정.                   |
| `ETag`               | 매우 높음              | 표현의 특정 버전을 가리키는 불투명 문자열. 조건부 GET에서 `If-None-Match`로 사용.         |
| `Expires`            | 중간                   | 특정 시각까지 응답을 캐시해도 됨을 알림. 이를 지키면 요청 자체를 아예 피할 수 있음.       |
| `Last-Modified`      | 매우 높음              | 표현이 마지막으로 바뀐 시각. 조건부 HTTP GET을 가능하게 함.                               |
| `Location`           | 매우 높음              | 리소스에 접근할 URI를 알림. 3xx와 201 등 여러 응답 코드와 밀접.                           |
| `Proxy-Authenticate` | 낮음~중간              | 프록시의 인증 요구. 407과 함께 전송되며 `WWW-Authenticate`와 유사.                        |
| `Retry-After`        | 낮음~중간              | 413이나 5xx와 함께, 나중에 재시도할 시점/대기 초를 알림.                                  |
| `Trailer`            | 낮음                   | chunked 인코딩에서 바디 뒤에 붙일 헤더(트레일러)의 이름을 미리 알림.                      |
| `Transfer-Encoding`  | 낮음                   | 크기를 모른 채 바디를 chunk로 보내고 `Content-Length` 등을 트레일러로 뒤에 붙일 때.       |
| `Vary`               | 낮음~중간              | 다른 표현을 얻으려 바꿀 수 있는 요청 헤더를 알림. 캐시 분리에도 영향(`*`이면 캐시 금지).  |
| `WWW-Authenticate`   | 매우 높음              | 401과 함께 전송되는 서버의 인증 요구. 어떤 인증(Basic/Digest/WSSE 등)을 기대하는지 알림.  |

`Connection`은 응답 헤더로, TCP 연결에만 해당하는 특수 헤더들의 이름을 담으며 프록시는 이를 다음 홉에 넘기기 전에 제거합니다. 프록시를 안 쓰는 클라이언트가 볼 값은 대개 `close`뿐입니다.
`Date`는 요청/응답 양쪽에 쓰이며(요청 시 클라이언트 시각, 응답 시 서버 시각), 응답에서는 캐시가 사용하고 필수입니다.
`Location`은 어떤 응답 코드와 함께 왔는지에 따라서만 해석할 수 있으므로, 자세한 내용은 부록 B의 해당 코드 절을 참조하라고 저자는 안내합니다.
`Via`는 요청/응답 양쪽에 쓰이며 중개자(프록시)마다 자신을 덧붙여, 메시지가 거쳐 온 경로를 드러냅니다.
`Warning`은 주로 캐싱 프록시가 삽입하는 응답 보충 정보로, 세 자리 warn-code를 가집니다 (예: `Warning: 110 localhost:9090 Response is stale`, 여기서 110은 “Response is stale”).

### 비표준 헤더

수년간 대부분 `X-` 확장을 통해 많은 헤더가 생겼습니다.
공식 HTTP 표준에 들어가진 않았지만 웹 서비스에 중요한 것들을 저자가 추립니다.

| 헤더                     | 유형 | 중요도                             | 의미와 용도                                                                              |
| ------------------------ | ---- | ---------------------------------- | ---------------------------------------------------------------------------------------- |
| `Cookie`                 | 요청 | 인간 웹 높음, 프로그래머블 웹 낮음 | 서버가 클라이언트 측에 저장한 준영구 상태를 매 요청마다 되돌려 보냄. Netscape 확장.      |
| `Set-Cookie`             | 응답 | 인간 웹 높음, 프로그래머블 웹 낮음 | 서버가 클라이언트 측에 쿠키로 상태를 설정하려는 시도.                                    |
| `POE`                    | 요청 | 중간                               | Post Once Exactly에 쓸 URI를 원하는 클라이언트가 보냄(9장).                              |
| `POE-Links`              | 응답 | 중간                               | `POE` 요청에 대한 응답으로, POST를 정확히 한 번만 받는 URI들을 제공.                     |
| `Slug`                   | 요청 | APP 애플리케이션에서만 상당히 높음 | APP에서 이진 문서를 컬렉션에 POST할 때 제목을 지정하는 수단.                             |
| `X-HTTP-Method-Override` | 요청 | 낮음~중간                          | 오버로드된 POST로 PUT/DELETE 등을 흉내낼 때 “진짜” 메서드를 담음.                        |
| `X-WSSE`                 | 요청 | 중간                               | WSSE Username Token 표준이 정의. `Authorization`과 함께 보내 실제 WSSE 자격 증명을 담음. |

`Cookie`/`Set-Cookie`는 REST 진영에서 평판이 나쁩니다.
담기는 “상태”가 흔히 서버 측 대형 자료구조를 가리키는 세션 ID여서 무상태성(statelessness) 원칙을 깨고, 쿠키를 받은 클라이언트가 이후 요청을 쿠키 없이 하던 대로 할 수 없게 되기 때문입니다.
꼭 써야 한다면 모든 상태를 클라이언트 측에 저장하라고 저자는 권합니다.
`X-WSSE`가 `Authorization`과 별도로 존재하는 이유는, WSSE가 웹 서버가 아니라 CGI 프로그램에서 처리되도록 설계되었기 때문입니다.
웹 서버는 `Authorization`을 자기 몫으로 여겨 `WSSE profile=“UsernameToken”`을 이해하지 못하고 무시하지만, CGI 표준은 `X-` 헤더 값을 전달하도록 요구하므로 `X-WSSE`가 자격 증명을 밀반입하는 통로가 됩니다.
