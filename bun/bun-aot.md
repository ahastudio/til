# 타입이 실제가 되면 TypeScript는 다른 언어가 된다

트윗: [Some of the language changes when TypeScript types become real (with ahead-of-time compilation)](https://twitter.com/bunjavascript/status/2108441841498804715)

GN 토론: <https://news.hada.io/topic?id=35124>

## 요약

Bun 공식 계정이 2026년 10월 9일에 올린 트윗이다.
본문은 “TypeScript 타입이 (선행 컴파일과 함께) 실제가 되면
언어의 일부가 달라진다”는 한 문장이고,
나머지는 “When TypeScript's types are real”이라는 제목의 이미지 4장에 담겼다.
각 이미지는 같은 코드 조각을 두 방식으로 실행한 결과를 나란히 보여 준다.
today는 타입을 지우고 실행하는 지금의 Bun과 Node이고,
AoT는 `bun build --compile --aot`로 만든 바이너리다.
이미지마다 아래에는 모든 결과가 실제 출력이며,
각 조각을 Bun 1.4와 AoT 컴파일러에서 따로 실행했다는 주석과
“Work in progress”라는 문구가 붙어 있다.

첫 장은 타입 표기가 검사가 된다는 내용이다.
`JSON.parse`로 받은 값을 `User`로 선언하면, `age`에 문자열 `"36"`이 들어 있을 때
지금은 `u.age + 1`이 `"361"`을 내지만 AoT에서는
`expected User, got plain object`라는 `TypeError`가 난다.
`const port: number = "8080"` 같은 정적 타입 오류는
`TS2322` 빌드 오류가 되고 바이너리가 만들어지지 않는다.
`o.n!` 같은 non-null 단언은 실제로 검사해서 `undefined`이면 예외를 던진다.
그리고 `as`는 변환이 된다.

```typescript
const raw: any = "5"
(raw as number) + 1
// today: "51"
// AoT:   6
```

둘째 장은 `any`가 타입 붙은 코드로 거짓을 실어 나르지 못한다는 내용이다.
`any`로 만든 `{ x: "2", y: 3 }`를 `Point`를 받는 함수에 넘기면 예외가 난다.
`(p as any).x = "one"`처럼 타입이 정해진 필드에 다른 타입을 쓰는 것도,
필수 필드를 `delete`하는 것도 막힌다.
`delete`의 오류 메시지는 “선택적 속성만 지울 수 있다”고 적는다.
`number[]`로 선언한 `JSON.parse('[1,"2",3]')` 결과를 순회하면,
지금은 합이 `"123"`이 되지만 AoT에서는 `"2"`에서 멈춘다.

셋째 장은 객체 모델을 다룬다.
`Object.prototype`에 속성을 추가하는 프로토타입 오염,
`Array.prototype.map` 같은 내장 메서드 교체,
사용자 클래스 `Account.prototype.deposit`의 교체가 모두
`Attempted to assign to readonly property`로 실패한다.
이미지는 `JSON.parse`, `Math.max`, `Symbol.iterator`도
같은 보호를 받는다고 덧붙인다.
또 같은 필드와 메서드를 가진 평범한 객체를 `Account` 자리에 넘기면 거부된다.
이미지의 표현으로는 “클래스는 모양이 아니라 클래스”다.

넷째 장은 두 가지를 보여 준다.
AoT로 컴파일한 함수에 `String(secret)`을 호출하면 소스 대신
`function secret() { [native code] }`가 나온다.
그리고 “여전히 JavaScript”라는 항목에서,
객체에 새 속성 `z`를 붙이고 `Object.keys`를 부르는 일,
`Math`에 `tau`를 추가하는 일, 타입이 맞는 JSON을 읽는 일은
지금과 결과가 같다고 보여 준다.

## 분석

### 세 종류의 변화가 한 묶음으로 제시된다

트윗의 예시들은 겉으로는 모두 “타입이 실제가 된다”는 한 문장 아래 있지만,
성격이 다른 세 가지 변화가 섞여 있다.
첫째는 정적 검사를 빌드 관문으로 만드는 것이다.
`port: number = "8080"`이 빌드 오류가 되는 사례가 여기에 속하는데,
이것은 이미 `tsc --noEmit`을 CI에 거는 팀이 하던 일이고 의미론의 변화가 아니다.
Bun은 트윗 다음 날인 10월 10일에 나온
[Bun v1.4.3](https://bun.com/blog/bun-v1.4.3)에서
typescript-go를 포팅한 타입 검사기 `bun check`와
`bun run --check`, `bun build --check`를 정식으로 내놓았다.
첫 장의 `TS2322` 사례는 이 기능만으로도 얻을 수 있다.

둘째는 경계에서의 런타임 검사다.
`JSON.parse` 결과나 `any`에서 들어온 값이
선언된 타입과 맞는지 실행 중에 확인하는 것이다.
일반적으로 지금 TypeScript 생태계에서는
이 역할을 zod 같은 검증 라이브러리가 따로 맡는데,
AoT는 타입 선언 자체를 검증 스키마로 쓰겠다는 것이다.
non-null 단언 `x!`가 실제로 검사하는 것도 같은 범주다.

셋째가 진짜 의미론의 변화다.
`as`가 단언이 아니라 변환이 되고,
클래스 타입이 구조가 아니라 정체성으로 판정되며,
프로토타입이 읽기 전용이 되고, 필수 필드는 지울 수 없다.
이 변화들은 타입 오류를 잡는 것이 아니라
같은 소스가 오류 없이 다른 값을 내게 만든다.
`(raw as number) + 1`이 `"51"` 대신 `6`을 내는 것이 대표적이다.

### TypeScript가 스스로 금지해 온 것을 정면으로 뒤집는다

일반적으로 알려진 TypeScript의 설계 목표(Design Goals) 문서는
비목표(non-goal)로 “런타임 타입 정보를 추가하거나 의존하는 것,
또는 타입 시스템의 결과에 따라 다른 코드를 내보내는 것”을 명시한다.
타입은 지워지고, 타입을 지운 결과가 그대로 JavaScript라는 것이
이 언어의 계약이었다.
Bun이 TypeScript를 빠르게 실행할 수 있었던 것도 이 계약 덕분이다.
타입을 검사하지 않고 지우기만 하면 됐기 때문이다.

이번 실험은 그 계약의 정반대 편에 선다.
`as`는 TypeScript에서 컴파일러에게 “내가 더 잘 안다”고 말하는 장치였는데,
AoT에서는 컴파일러가 값을 바꾸는 명령이 된다.
구조적 타이핑은 TypeScript 타입 시스템의 기본 원리인데,
AoT는 클래스에 대해서는 명목적(nominal) 판정을 택했다.
트윗 제목이 “언어의 일부가 달라진다”고 쓴 것은 과장이 아니라 정확한 묘사다.

### 객체 모델을 굳히는 이유는 트윗에 나와 있지 않다

셋째 장의 제약들, 즉 프로토타입을 읽기 전용으로 만들고
메서드 교체를 막는 것은 “프로토타입 오염이 불가능하다”는 보안의 언어로 소개된다.
하지만 선행 컴파일러 입장에서 이 제약은 다른 의미도 가진다고 해석할 수 있다.
메서드가 바뀌지 않는다는 보장이 있으면 호출 대상을 컴파일 시점에 정할 수 있고,
필드 타입이 바뀌지 않는다는 보장이 있으면 객체 배치를 고정할 수 있다.
GN 요약도 이 제약이 AOT 최적화에 활용될 수 있다고 정리했다.
다만 트윗 자체는 성능 수치나 최적화 근거를 하나도 제시하지 않는다.
보안과 정확성의 언어로만 말하고 있다는 점은 기억해 둘 만하다.

### 같은 시도의 앞선 사례들

TypeScript와 비슷한 문법에 다른 의미론을 붙여
네이티브로 컴파일하는 시도는 처음이 아니다.
아래는 일반적으로 알려진 사례다.
AssemblyScript는 TypeScript와 닮은 문법으로 WebAssembly를 생성하지만,
자체 타입(`i32`, `f64` 등)을 갖는 별도 언어로 자리를 잡았다.
Microsoft의 Static TypeScript는 MakeCode에서 마이크로컨트롤러용으로 쓰는
TypeScript의 부분집합이다.
Meta의 Static Hermes는 타입 표기를 신뢰할 수 있는 정보로 삼아
선행 컴파일하는 방향을 실험했다.
Python 쪽에서는 mypyc가 타입 힌트가 붙은 Python 코드를 C 확장으로 컴파일하면서
힌트를 런타임에 강제한다.

이 사례들은 대체로 두 가지를 공유한다.
하나는 별도의 이름이나 별도의 도구로 경계를 분명히 그었다는 것,
다른 하나는 기존 언어와 의미가 어긋나는 지점을
주로 컴파일 오류나 런타임 예외로 드러냈다는 것이다.
Bun의 실험은 `--aot`라는 빌드 플래그 하나로 경계를 긋고,
`as`처럼 오류가 아니라 다른 결과를 내는 지점을 일부러 만든다는 점에서
이들과 갈린다.
같은 저장소의 `bun/bun-1-4.md`가 다룬 Rust 재작성이 구현 언어를 바꾼 일이라면,
이번 실험은 Bun이 실행하는 언어 자체의 의미를 정하려는 시도다.

## 비평

### `as`의 변환은 오류가 아니라 조용한 분기를 만든다

트윗의 사례 중 대부분은 “지금은 이상한 값이 나오고,
AoT에서는 예외가 난다”는 형태다.
`"361"`이 `TypeError`가 되는 것은 대체로 반길 만한 변화다.
틀린 프로그램이 일찍 실패하기 때문이다.
그런데 `as`의 사례만은 성격이 다르다.
지금은 `"51"`을 내고 AoT에서는 `6`을 낸다.
둘 다 오류 없이 끝난다.

같은 소스가 실행 환경에 따라 다른 값을 내고 아무도 경고하지 않는다면,
그 코드는 두 환경 중 어느 쪽에서든 조용히 틀릴 수 있다.
테스트를 `bun test`로, 배포를 `--aot` 바이너리로 하는 팀을 생각해 보면
위험이 분명해진다.
테스트는 타입을 지운 의미로 통과하고, 운영은 변환된 의미로 동작한다.
게다가 트윗은 `"abc" as number`나 객체에 대한 `as`가
어떻게 되는지 보여 주지 않는다.
변환이 실패할 때 무엇이 일어나는지 모르는 상태에서
`as`의 의미를 바꾼다는 결정은 근거가 가장 얇은 부분이다.
GN에서 click은 `as`의 동작을 아예 바꾸는 시도가 가장 급진적이라고 지적하며,
새 문법을 내세웠다가 사라진 CoffeeScript를 떠올렸다.[^click]

### 생태계 코드가 이 의미론을 견디는지는 보여 주지 않는다

네 장의 예시는 모두 한 파일 안에서 완결되는 짧은 조각이다.
실제 프로그램은 `node_modules`의 수많은 패키지와
그 타입 선언(`.d.ts`) 위에서 돈다.
일반적으로 알려진 사정으로,
DefinitelyTyped의 타입 선언은 실제 런타임 동작과 어긋나는 경우가 적지 않다.
타입 지우기 의미론에서는 이 어긋남이 대개 무해하지만,
타입이 런타임 검사가 되는 순간
선언의 작은 거짓이 모두 `TypeError`로 바뀔 수 있다.
트윗은 `.d.ts`로만 타입이 주어진 라이브러리의 값이 어떻게 검사되는지,
제네릭과 유니언 타입이 어디까지 런타임에 검사되는지 말하지 않는다.

셋째 장의 제약은 더 직접적으로 기존 관행과 부딪힌다.
프로토타입 메서드를 바꿔치기하는 것은 공격 기법이기도 하지만,
테스트 목(mock)과 스파이, 폴리필이 일상적으로 쓰는 방법이기도 하다.
`Account.prototype.deposit`을 교체할 수 없다면
그 메서드를 감시하는 테스트도 쓸 수 없다.
“Methods cannot be swapped out”이라는 문장은 보안 쪽에서 읽으면 장점이지만,
테스트 도구 쪽에서 읽으면 호환성 단절이다.
트윗은 앞쪽만 보여 준다.

### 성능 실험이라면서 성능을 말하지 않는다

선행 컴파일의 일반적인 동기는 성능, 시작 시간, 배포 크기다.
그런데 네 장 어디에도 수치가 없다.
오히려 트윗이 보여 주는 변화의 상당수는 비용을 더한다.
모든 타입 경계에서 값의 구조를 검사하는 일은 공짜가 아니다.
일반적으로 알려진 점진적 타입(gradual typing) 연구,
예컨대 Takikawa 등의 “Is Sound Gradual Typing Dead?”(POPL 2016)는
타입 있는 코드와 없는 코드의 경계 검사가 큰 성능 저하를 낳을 수 있음을 보였다.
`JSON.parse`로 받은 큰 배열을 `number[]`로 선언했을 때
원소마다 검사하는지, 언제 검사하는지는
이 실험의 실용성을 결정하는 질문인데 답이 없다.

“Work in progress”라는 주석이 있으니 수치가 없는 것 자체를 탓할 수는 없다.
문제는 발표의 틀이다.
의미론 변경을 먼저 보여 주고 그 대가를 감춘 채로는
독자가 이 거래가 타당한지 판단할 수 없다.

### “여전히 JavaScript”라는 마지막 장은 경계를 흐린다

넷째 장의 마지막 항목은 새 속성 추가, `Math` 확장,
타입이 맞는 JSON 파싱이 그대로 동작한다고 보여 준다.
안심시키려는 장면이지만 논리적으로는 약하다.
같은 결과가 나오는 사례 세 개는
다른 결과가 나오는 사례 열세 개를 상쇄하지 못한다.
게다가 `Math`에는 새 속성을 붙일 수 있지만 `Math.max`는 바꿀 수 없다는 규칙은,
어떤 객체의 어떤 속성이 보호되는지를 사용자가 외워야 한다는 뜻이다.
“여전히 JavaScript”라기보다는 “JavaScript처럼 보이는 다른 규칙”에 가깝다.

## 인사이트

### 타입 검사기를 소유하는 순간 런타임은 언어의 주인이 된다

이 실험이 가능해진 전제는 트윗 다음 날 공개된 `bun check`다.
v1.4.3 발표문은 이것이 typescript-go의 포팅이며
TypeScript 7.0.2의 적합성(conformance) 테스트를 100% 통과한다고 적는다.
타입을 지우기만 하던 런타임이 타입 검사기를 직접 갖게 되면,
타입 정보를 코드 생성에 쓰는 것은 자연스러운 다음 단계가 된다.

그 결과로 생기는 2차 효과는 TypeScript의 의미가 둘로 갈라진다는 것이다.
정적 의미는 Microsoft의 TypeScript가 정하고,
`--aot` 아래의 동적 의미는 Bun이 정한다.
지금까지 TypeScript에는 동적 의미라는 것이 없었다.
타입이 지워졌으니 JavaScript의 의미가 곧 TypeScript의 의미였다.
Bun이 이 빈자리를 처음 채우는 쪽이 되면,
“TypeScript 프로그램의 실행 결과”를 정의하는 권한이
사실상 한 런타임으로 넘어간다.
이 해석이 맞다면 다른 런타임과 TypeScript 팀이
이 의미론에 어떻게 반응하는지가 실험의 성패보다 더 큰 변수다.

### 이름을 따로 붙이지 않은 방언은 오래 버티기 어렵다

click이 꺼낸 CoffeeScript는 문법이 달라서 실패했다기보다,
JavaScript가 그 기능을 흡수하자 존재 이유가 사라진 경우에 가깝다는 것이
일반적인 평가다.
이 실험에 더 잘 맞는 비교는 앞서 든 AssemblyScript, Static TypeScript,
mypyc 같은 “같은 문법, 다른 의미” 계열이다.
이들은 대부분 별도 이름이나 별도 도구로 자신을 구분했고,
기존 언어 사용자가 실수로 넘어오지 않게 했다.

Bun의 실험은 `.ts` 파일과 TypeScript라는 이름을 그대로 쓰면서
플래그로만 갈라진다.
이렇게 하면 진입은 쉽지만 같은 파일이 두 의미를 갖는 상태가 오래 지속된다.
장기적으로는 어느 쪽 의미를 기준으로 코드를 쓰는지 표시하는 장치,
예컨대 파일 단위 선언이나 별도 확장자가 필요해질 가능성이 크다.
이것은 트윗이 다루지 않은 부분이고 해석이다.

### 런타임 타입 검사는 실패를 없애지 않고 실패의 모양을 바꾼다

`"361"`과 `TypeError` 중 무엇이 나은가는 맥락에 따라 다르다.
배치 작업이라면 잘못된 값으로 끝까지 도는 것보다 즉시 멈추는 쪽이 낫다.
하지만 사용자 요청을 처리하는 서버라면,
외부 API가 숫자 필드를 문자열로 보내기 시작한 날
모든 요청이 예외로 떨어질 수 있다.
지금은 검증 라이브러리를 쓰는 팀이 경계마다 실패 처리 방식을 정한다.
AoT 의미론에서는 타입 선언이 곧 검증이 되므로,
실패 처리를 정하지 않은 모든 타입 표기가 잠재적인 예외 지점이 된다.

그래서 이 의미론을 채택하는 팀은 타입 표기를 쓰는 방식부터 바꿔야 한다.
외부에서 들어오는 값은 `unknown`으로 받고 명시적으로 좁히는 관행이
권장 사항이 아니라 운영 안정성의 조건이 된다.
타입이 문서였던 시절에는 느슨한 표기가 비용이 없었지만,
타입이 계약이 되면 느슨한 표기는 장애가 된다.

### 보안 기능과 테스트 가능성은 같은 손잡이를 쥐고 있다

프로토타입을 읽기 전용으로 만드는 것은
프로토타입 오염이라는 실재하는 공격 범주를 없앤다.
동시에 런타임에 동작을 바꿔 끼우는 모든 기법,
즉 목, 스파이, 폴리필, 계측(instrumentation)을 없앤다.
두 가지는 같은 능력의 양면이라서 한쪽만 남길 수 없다.

JavaScript 생태계의 테스트 도구는 오랫동안 이 동적 교체 능력에 기대 왔다.
AoT 의미론이 퍼진다면 테스트 방식은 의존성 주입처럼
교체 지점을 설계에 미리 드러내는 쪽으로 옮겨 가야 한다.
이는 정적 언어들이 이미 겪은 이행이고,
JavaScript 코드베이스에서는 상당한 재작성 비용을 뜻한다.
트윗이 보안으로 소개한 기능의 진짜 가격표는 아마 테스트 코드에 붙어 있을 것이다.
