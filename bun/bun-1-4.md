# Bun 1.4: Zig에서 Rust로 다시 쓴 판본이 처음 정식 출시됐다

원문: [Bun 1.4](https://bun.com/blog/bun-v1.4)

HN 토론: <https://news.ycombinator.com/item?id=49374797> (233점, 138개 댓글)

## 요약

발표문의 첫 단락이 이 릴리스의 목록을 한 문장으로 정리한다.
Node.js 테스트 스위트에서 1,517개 테스트를 추가로 통과했고 —
Bun 1.0 이후 Node 호환성에서 가장 큰 도약이라고 적는다 —
2,900개 이상의 이슈를 고쳤고,
유휴 CPU 사용을 5배 줄이고 메모리를 최대 35% 줄이고
리눅스 시작 시간을 50% 단축했다.
`Bun.Image`, `Bun.WebView`, `Bun.markdown`, `Bun.cron()`, `Bun.Terminal`,
`bun run --parallel`, `bun test --parallel`, `bun audit fix`,
`bun dedupe`, `bun prune`를 추가했다.
그리고 마지막 문장이 이것이다 — Bun을 Zig에서 Rust로 다시 썼다.

Rust 재작성에 대한 절은 두 문장뿐이다.
Bun은 이제 Rust로 작성되었고 이것이 그 첫 릴리스이며,
다만 Claude Code는 몇 달째 Bun의 Rust 포트를 쓰고 있었고
Prisma는 그 위에서 Prisma Compute를 출시했다고 적는다.
자세한 내용은 별도의 블로그 글로 넘긴다.

Node 호환성은 모듈별 통과율로 제시된다.
`node:http`와 `node:fs`와 `node:cluster`와 `node:timers`와 `node:zlib`과
`node:vm`과 `node:stream`이 Node 자체 테스트의 97%를 통과하고,
`node:quic`이 99%, `node:events`와 `node:trace_events`와 `node:sqlite`가 100%다.
Bun이 아직 Node.js와 100% 호환은 아니라고 명시한다.
생태계 쪽에서는 Playwright가 Bun에서 돌고,
`bun --bun next build`가 Turbopack과 React Compiler를 쓴 Next.js 16.3에서 동작하고,
vitest가 `--coverage`와 threads·forks 풀까지 포함해 돌며,
OpenTelemetry와 dd-trace가 스팬을 내보내고 프로파일을 뜬다.

성능 개선의 근거를 표로 제시한다.
Bun 1.4까지 Bun은 JavaScriptCore의 libpas와 mimalloc 두 개의 할당기를 썼는데
이제 JavaScriptCore도 mimalloc을 쓰며,
부분 페이지 해제와 JavaScript가 유휴일 때 메모리를 반납하는 청소 스레드와
개선된 지연 0 초기화를 mimalloc에 더했다.

CPU 사용의 대표 사례로 Claude Code를 든다.
Bun 위에 만들어진 크고 오래 도는 애플리케이션인데
프로덕션 CPU 사용이 절반으로 줄어 p99가 24%에서 10%로,
p50이 5.8%에서 2.5%로 내려갔다는 것이다.
작은 hello world 앱의 유휴 CPU는 5배 줄었다.

메모리는 HTTP 서버에서 13~48% 감소한다.

| 서버           | Bun 1.4 | Bun 1.3 | Node.js 26 | 1.3 대비 |
| -------------- | ------- | ------- | ---------- | -------- |
| fastify        | 120 MB  | 233 MB  | 156 MB     | −48%     |
| Express        | 92 MB   | 169 MB  | 145 MB     | −46%     |
| `node:http`    | 81 MB   | 135 MB  | 107 MB     | −40%     |
| Elysia         | 55 MB   | 91 MB   | 해당 없음  | −40%     |
| Next.js        | 285 MB  | 397 MB  | 342 MB     | −28%     |
| `Bun.serve`    | 36 MB   | 45 MB   | 해당 없음  | −20%     |
| Vite 개발 서버 | 233 MB  | 268 MB  | 214 MB     | −13%     |

Next.js App Router의 서버 렌더링에서는 감소폭이 더 크다.
1.3에서 무한히 늘어나던 패턴 — 동적 경로에서 `React.cache`와
`no-store` fetch를 함께 쓰는 구성 — 이 4,000 페이지에서 238 MB로 안정되며
Node의 410 MB보다 낮다고 적는다.

시작 시간과 바이너리 크기도 제시한다.
Windows에서 `hello.js` 시작이 39.0 ms에서 15.5 ms로 2.5배 빨라졌고
Node 26은 40.1 ms다.
리눅스에서는 10.9 ms에서 5.1 ms로 2배 빨라졌고 Node 26은 27.2 ms다.
바이너리는 리눅스 x64가 88.5 MB에서 77.0 MB로 최대 17% 작아졌는데,
macOS arm64는 60.2 MB에서 61.2 MB로 오히려 커졌다.

속도 개선의 출처를 밝힌 문단이 있다.
1.3과 1.4 사이에 WebKit 핀을 39번 올려 약 8개월치의
JavaScriptCore 작업을 가져왔고,
정규식 엔진과 Promise와 대부분의 String·Array 내장 함수가
자체 호스팅 JavaScript에서 C++로 옮겨졌으며,
zlib-ng와 SIMD 커널을 뜨거운 경로에 넣었다.
그 결과 `new URL()`이 최대 4.6배 빨라졌고,
`marked.parse()`가 80 KB 마크다운에서 912 ms에서 약 6 ms로 138배 빨라졌고,
`isbot`이 218 µs에서 1.07 µs로 200배 빨라졌으며 Node 26은 1.47 µs다.
`Buffer.from(str, "hex")`가 8배, `base64url`이 46배 빨라졌다.
`bun build --react-compiler`는 React Compiler를 Rust로 실행해
큰 React 코드베이스에서 Babel 플러그인보다 19배 빠르다.

새 API 다섯 개가 각각 기존 라이브러리의 자리를 대신한다.
`Bun.Image`는 내장 이미지 라이브러리이고,
`Bun.WebView`는 Puppeteer나 Playwright 없이 Bun에 내장된 헤드리스 브라우저 자동화이며
macOS에서는 WebKit을, 아니면 설치된 Chrome·Edge를 CDP로 구동하고
클릭이 신뢰된 입력으로 도달한다(`event.isTrusted === true`).
`Bun.markdown`은 내장 마크다운 파서로 HTML 문자열과 React 요소와
요소별 콜백을 낼 수 있다.
`Bun.cron()`은 운영체제의 스케줄러에 작업을 등록한다 —
리눅스는 crontab, macOS는 launchd, Windows는 작업 스케줄러다.
`Bun.Terminal`은 내장 의사 터미널로 `node-pty` 없이
JavaScript에서 bash와 vim과 htop을 구동한다.

## 저장소 상태

저장소 `oven-sh/bun`의 주 언어가 이제 Rust로 표시된다.
별은 95,517개이고 열린 이슈가 3,252개, 열린 풀 리퀘스트가 4,993개다.
라이선스는 표준 식별자로 분류되지 않은 형태다.

## 분석

### 재작성을 마지막 한 문장에 둔 배치가 이 발표문의 핵심 결정이다

첫 단락은 열두 개 항목을 나열하고 재작성을 맨 끝에 놓는다.
그리고 재작성 절은 두 문장이며 자세한 설명을 다른 글로 넘긴다.
이 배치는 우연이 아니다.

같은 재작성이 발표되던 시기에 이 저장소가 기록한 논쟁이 몇 개 있다.
[Rust 재작성을 알린 원래 발표](../rust/rewriting-bun-in-rust.md)와
[Zig 창시자가 그 코드베이스에 대해 남긴 평가](../agentic-coding/zig-creator-calls-spade-a-spade.md)와
[Claude Code가 Rust 판 Bun으로 실행되기 시작한 사실](../claude/claude-code-bun-in-rust.md)이며,
세 문서의 HN 토론 점수 합이 2,000점을 넘는다.
그 논쟁의 중심은 언어 선택과 AI 생성 코드의 품질이었다.

그러므로 이 발표문의 전략은 주제를 옮기는 것이다.
언어와 방법론에 대한 논쟁을 다시 열지 않고,
숫자로 결과를 제시한 뒤 재작성을 목록의 마지막 항목으로 처리한다.
설득의 방식으로 보면 합리적이다 —
메모리 48% 감소와 시작 2.5배는 측정 가능하고,
Rust가 옳았는지는 측정 가능하지 않다.

다만 이 배치가 한 가지를 빠뜨린다.
재작성의 명분은 메모리 안전이었는데,
발표문 어디에도 안전성에 관한 항목이 없다.
2,900개 이슈를 고쳤다는 문장이 있지만 그중 얼마가 메모리 문제였는지,
Zig 시절 있었던 어떤 종류의 버그가 구조적으로 불가능해졌는지가 없다.
성능은 재작성의 부수 효과이고 안전은 목적이었는데,
발표문은 부수 효과만 계량한다.

### 자기 표를 세로로 읽으면 개선의 절반이 회귀 복구다

메모리 표의 마지막 열은 Bun 1.3 대비 감소율이다.
fastify가 −48%, Express가 −46%, `node:http`가 −40%다.
가로로 읽으면 큰 개선이다.

같은 표를 Node.js 26 열과 함께 읽으면 다른 그림이 나온다.
Bun 1.3의 fastify는 233 MB였고 Node 26은 156 MB였다.
Express는 169 MB 대 145 MB, `node:http`는 135 MB 대 107 MB,
Next.js는 397 MB 대 342 MB, Vite 개발 서버는 268 MB 대 214 MB다.
다섯 행 전부에서 Bun 1.3이 Node보다 메모리를 더 썼다.

그러면 1.4의 감소분 중 상당 부분은 개선이 아니라 복구다.
Node보다 40~50% 더 쓰던 상태에서 Node보다 덜 쓰는 상태로 온 것이며,
그것은 훌륭한 성과이지만 “Bun은 빠르고 가볍다”는 오랜 주장과
1.3의 실제 상태 사이에 간극이 있었다는 뜻도 된다.
발표문은 그 간극을 언급하지 않고 감소율만 제시한다.

Next.js SSR 사례는 그 성격을 더 분명히 한다.
1.3에서 무한히 늘어나던 패턴이라고 적혀 있는데,
`React.cache`와 `no-store` fetch의 조합은
App Router에서 흔한 구성이며 특이한 사용이 아니다.
그것이 1.3에서 무한히 증가했다는 사실은 버그였고,
1.4의 238 MB는 그 버그가 고쳐진 결과다.
Vite 개발 서버가 1.4에서도 여전히 Node보다 많이 쓴다는 점(233 MB 대 214 MB)이
이 표를 균형 있게 읽을 마지막 단서다.

### 새 API 다섯 개가 전부 인기 npm 패키지의 자리다

`Bun.Image`, `Bun.WebView`, `Bun.markdown`, `Bun.cron()`, `Bun.Terminal`은
서로 무관해 보이지만 하나의 기준으로 골라졌다.
각각 널리 쓰이는 npm 패키지가 하던 일이다 —
이미지 처리, 헤드리스 브라우저, 마크다운 파싱, 크론 스케줄링, 의사 터미널이며,
발표문 자신이 `Bun.WebView` 설명에서 Puppeteer와 Playwright를,
`Bun.Terminal` 설명에서 `node-pty`를 이름으로 든다.

이 전략의 이점은 명확하고 실제로 사용자가 원하는 것이다.
설치 없이 쓸 수 있고 런타임과 함께 버전이 관리되며
공급망 위험이 줄어든다.
HN에서 한 사용자가 1.3에서는 의존성 없이 REPL도 쓸 수 없었는데
1.4에서 내장되어 드디어 진짜 이식 가능한 TypeScript REPL이 생겼다고
반가워한 것이 그 수요의 표현이다[^tredre3].

그런데 같은 스레드에서 반대 방향의 지적도 나왔다.
LLM으로 기능을 손쉽게 만들어 런타임에 직접 넣는 방식이
그 라이브러리들이 오랜 시간에 걸쳐 검증한 설계를 가져다 쓰는 것이며,
단순화된 API를 번들로 제공하면
그 라이브러리에 기여하는 일의 값이 줄어든다는 것이다[^jiangplus].
범용 런타임이 그 모든 영역을 깊이 있게 계속 개선할 수는 없으므로
가장 흔한 경우만 제공하게 된다는 지적도 함께 있었다.

표준 라이브러리의 적정 크기에 대한 논쟁도 이어졌다.
한 사용자는 더 큰 표준 라이브러리를 원하지만 부엌 싱크는 아니라고 정리했다 —
유틸리티 함수 모음과 SQLite 바인딩은 좋고,
YAML과 이미지 처리는 복잡성과 보안 우려 때문에 반대라는 것이다[^joshkel].
다른 사용자는 제3의 답을 냈다 —
런타임이 번들하는 것과 아무 GitHub 계정의 개인이 만든 것 사이에
공백이 있으며, Node 프로젝트가 공식으로 개발·지원하되
npm으로 배포하는 형태가 있으면 좋겠다는 것이다[^mort96].
이미지 처리를 런타임에 넣는 결정에 대해서는
보안 표면의 관점에서 이 세 번째 답이 가장 설득력 있다.

## 비평

### 11일이라던 포트가 석 달이 되었는데 발표문에 그 문장이 없다

이 릴리스의 배경에는 하나의 숫자가 있다.
Rust 포트가 11일에 끝났다는 발표였고,
그것이 이 재작성을 화제로 만든 근거였다.
그리고 1.4는 그로부터 석 달 뒤에 나왔다.
2022년 이후 Bun의 안정 릴리스 사이 최장 공백이다.

발표문은 이 공백을 다루지 않는다.
1.3.0 이후 출시한 모든 것을 담았다고 적을 뿐
왜 오래 걸렸는지에 대한 문단이 없다.
HN 스레드가 그 공백을 두 방향으로 채웠다.
옹호 쪽은 11일이 기능적으로 동등한 상태까지의 포트를 뜻했고
그 뒤의 시간은 재작성이 가능하게 만든 새 기능과 안정화에 들어갔다는 것이며[^rwz],
11일은 충실한 기계적 포트였고 그 뒤에 리팩터링을 지시한 것이 명백한데
왜 그렇게 적대적으로 읽으려 하는지 모르겠다는 반응도 있었다[^nsonha].

비판 쪽의 논지는 인과가 반대라는 것이다.
급하게 밀어 넣은 자동 생성 코드와 기능이 버그를 너무 많이 만들어서
간단한 재작업이 석 달의 두더지 잡기가 되었으며,
그것이 엔지니어링 규율이 없을 때의 예측 가능한 결과라는 것이다[^solid_fuel].
같은 사용자는 11일이 아니라고 했던 쪽이
석 달이 11일보다 훨씬 길다는 점에서 옳았던 것 아니냐고 되물었다.

어느 해석이 맞는지는 이 문서가 판정할 수 없다.
확인 가능한 것은 발표문의 선택이다 —
석 달 전의 11일 발표로 얻은 주목을 유지한 채
그 간극에 대한 설명을 생략했다.
날짜를 반복해서 미룬 것에 대한 지적이 스레드에 여러 개 있고[^blks],
그 지적의 근거가 개발자 본인의 공개 발언이었으므로,
한 문단으로 정리하는 편이 이 릴리스의 신뢰에 더 도움이 됐을 것이다.

### 열린 풀 리퀘스트 4,993개는 이 개발 방식의 청구서다

저장소를 지금 열면 열린 풀 리퀘스트가 4,993개다.
열린 이슈 3,252개보다 많다.
정상적인 프로젝트에서는 이 비율이 반대다 —
이슈는 누구나 열고 PR은 코드를 쓴 사람만 열기 때문이다.

이 역전을 설명하는 것은 커밋의 출처다.
최근 한 달 커밋의 대부분이 봇 계정에서 나왔고,
개발자 본인의 표현으로는 6개월 전에는 대부분의 PR이
사람이 Claude에게 프롬프트를 주어 만들어졌는데
지금은 대부분이 Claude가 Claude에게 프롬프트를 주어 만들어진다.
PR을 만드는 비용이 거의 0이 되면 PR 수는 검토 용량과 무관하게 늘어난다.

이 상태가 실질적 문제를 만드는 지점이 있다.
GitHub 자체가 단일 브랜치에 대한 열린 PR을 1,000개 미만으로 유지하라고 권고하는데
그 이상에서는 병합 가능성 검사가 시간 초과되기 시작하기 때문이며,
지금 수치는 그 다섯 배다.
비교하자면 React의 열린 PR이 수백 개 규모다.

그리고 이 문제는 생성 쪽을 더 빠르게 만들어서는 해결되지 않는다.
검토가 병목이고 검토는 사람의 시간에 묶여 있으므로,
생성이 빨라질수록 큐가 길어진다.
[검증 부채라는 이름으로 이 저장소가 여러 번 다룬 구조](../agentic-coding/verification-debt.md)가
한 저장소의 PR 큐로 계량된 사례이며,
4,993이라는 숫자는 그 부채의 잔액이다.

### 프로덕션 성능의 대표 사례가 인수한 회사의 자기 제품이다

CPU 개선을 설명하는 절의 사례는 Claude Code다.
Bun 위에 만들어진 크고 오래 도는 애플리케이션이라고 소개하고,
프로덕션 CPU가 p99 24%에서 10%로, p50 5.8%에서 2.5%로 내려갔다고 적는다.
구체적이고 유용한 숫자다.

그런데 이 사례의 지위가 통상적이지 않다.
같은 발표문의 재작성 절이 Claude Code가 몇 달째 Rust 포트를 쓰고 있었다고 적으므로,
Claude Code는 벤치마크 대상이면서 동시에 사전 검증 환경이었다.
그리고 이 재작성이 Anthropic과 결부되어 논쟁이 되었던 사실을 함께 놓으면,
그 회사의 제품이 이 릴리스의 대표 프로덕션 지표라는 배치가 남는다.

이것이 숫자를 틀리게 만드는 것은 아니다.
오래 도는 큰 애플리케이션의 실제 CPU 프로파일은
합성 벤치마크보다 훨씬 값나가는 정보이며,
그런 데이터를 공개하는 것 자체가 드물다.

문제는 최적화의 방향이 그 하나의 워크로드에 맞춰졌을 가능성을 배제할 수 없다는 점이다.
가비지 컬렉터 타이머가 GC를 요청하는 시점을 조정하고
JavaScriptCore가 Strong 루트를 방문하는 방식을 바꾸고
futex 호출 수를 줄였다고 적는데,
셋 다 오래 도는 유휴 프로세스에 특화된 개선이다.
짧게 실행되고 끝나는 스크립트나
CPU를 계속 쓰는 작업에서 같은 이득이 있는지는 제시되지 않는다.
HN에서 이 재작성 전체를 Claude의 마케팅으로 읽는 시각이 반복해서 나왔고[^nicce],
대표 사례의 선택이 그 시각에 근거를 준다.

## 인사이트

### 런타임이 라이브러리를 흡수하면 흡수되지 않은 영역의 유지 보수 유인이 먼저 사라진다

이 릴리스가 내장한 다섯 개 API는 각각 성숙한 라이브러리의 영역이다.
그 라이브러리들이 당장 사라지지는 않는다 —
`Bun.markdown`이 marked를 대체하려면
확장과 옵션과 예외 처리까지 따라와야 하고 그것은 시간이 걸린다.

먼저 일어나는 일은 다른 쪽이다.
그 라이브러리에 기여할 유인이 줄어든다.
런타임이 같은 기능을 무료로 제공하기 시작하면
그 라이브러리의 미래 사용자 수에 대한 기대가 내려가고,
기여는 대체로 그 기대에 비례한다.
[LLM이 기여의 비용을 낮추면 검토가 병목이 된다는 구조](../agentic-coding/verification-debt.md)와
반대 방향의 압력이며, 여기서는 기여가 줄어드는 쪽이다.

이 압력이 만드는 2차 효과는 흡수된 기능의 품질 상한이다.
런타임은 가장 흔한 경우를 구현하고 그것으로 대부분의 사용자를 만족시키는데,
흔하지 않은 경우를 처리해 온 것은 그 라이브러리들이었다.
기여가 줄어들면 그 처리가 갱신되지 않고,
런타임은 그 영역까지 들어갈 이유가 없다 —
소수 사용자를 위해 표면적을 늘리는 것은 런타임의 유인에 맞지 않는다.
결국 중간 난도의 사용 사례가 가장 먼저 비게 된다.

역사적으로 같은 형태가 반복됐다.
브라우저가 jQuery의 기능을 표준 API로 흡수했을 때
jQuery는 남았지만 그 생태계의 플러그인 문화가 먼저 사라졌고,
남은 것은 표준이 다루는 범위였다.
Node가 fetch를 내장했을 때 request 계열 라이브러리들이 겪은 것도 같은 순서다.
차이는 속도다 — 그때는 표준화에 몇 년이 걸렸고,
지금은 한 릴리스에 다섯 개가 들어온다.

### 재작성의 성공 지표가 명분에서 결과로 조용히 교체됐다

이 재작성의 명분은 메모리 안전이었다.
Zig의 메모리 문제가 이유로 제시되었고,
그것이 언어를 바꾸는 결정을 정당화하는 논거였다.

이 발표문의 지표는 전부 다른 것이다.
Node 테스트 통과 수, 이슈 수정 수, CPU, 메모리, 시작 시간, 바이너리 크기다.
메모리 사용량은 메모리 안전이 아니며,
전자는 얼마나 쓰는지이고 후자는 잘못 쓰지 않는지다.
두 단어가 비슷해서 이 교체가 눈에 잘 띄지 않는다.

이 교체가 왜 문제인지는 반증 가능성에 있다.
안전을 명분으로 삼으면 검증 방법이 정해진다 —
Zig 시절 발생했던 메모리 관련 버그 유형을 열거하고
그것이 구조적으로 불가능해졌는지 보이는 것이며,
Rust에서 `unsafe` 블록이 얼마나 쓰였는지가 그 판정의 핵심이 된다.
성능을 지표로 삼으면 그 검증이 필요 없어지고,
성능은 언어를 바꾸지 않고도 개선할 수 있으므로
재작성의 필요성 자체가 증명되지 않는다.

그리고 이 발표문에는 그 검증을 할 재료가 없다.
`unsafe` 블록 수도, 메모리 관련 CVE나 크래시의 추이도,
Zig 판과 Rust 판의 동일 워크로드 크래시 비교도 없다.
WebKit 핀을 39번 올려 8개월치 JavaScriptCore 작업을 가져왔다는 문장이
성능 개선의 상당 부분을 설명하는데,
그것은 Zig로도 할 수 있는 일이었다.
그러므로 이 릴리스는 재작성이 성공했음을 보여 주지만
재작성이 필요했음은 보여 주지 않는다.

### 벤치마크 표의 세로 읽기가 벤더 성능 주장의 기본 검증법이다

이 발표문의 메모리 표는 잘 만들어졌다.
자기 이전 버전과 경쟁 런타임을 같은 표에 넣었고,
감소율을 마지막 열에 명시했다.
숨긴 것이 없다.

그런데 강조된 방향이 하나뿐이다.
마지막 열이 자기 이전 버전 대비이므로 눈이 가로로 움직이고,
그 방향에서는 −48%가 보인다.
Node 열을 세로로 훑으면 다섯 행에서 이전 버전이 경쟁자보다 나빴다는 사실이 보인다.
같은 데이터에서 두 개의 다른 이야기가 나온다.

이 읽기 방법이 일반화 가능하다.
벤더의 성능 표에서 강조 열은 벤더가 이기는 축이고,
검증은 강조되지 않은 축을 따라 읽는 것으로 시작한다 —
경쟁자와의 절대값 비교, 개선되지 않은 행,
그리고 표에서 빠진 조합이다.
이 표에서 빠진 것은 Bun 1.4와 Node 26의 CPU 비교와
macOS의 바이너리 크기 개선인데,
후자는 본문에 적혀 있고 값이 반대 방향이다(60.2 MB에서 61.2 MB).
불리한 수를 적어 둔 것은 이 발표문의 신뢰를 높이는 부분이다.

같은 방법을 이 저장소가 최근 기록한 다른 비교 문서들에 적용하면
대비가 선명해진다.
[벤더가 직접 쓴 경쟁 제품 비교 페이지들](../data/firecrawl.md)에는
경쟁자 열의 값이 그 경쟁자의 사이트와 어긋나는 사례가 있었고,
[반대 방향의 비교 페이지도 같은 문제를 갖고 있었다](../security/scrape-do.md).
차이는 여기서는 데이터가 자기 제품의 이전 버전이라는 점이다 —
자기 과거는 반박하지 않으므로 정확하게 적을 유인이 있고,
그래서 벤더의 표에서 가장 믿을 만한 열은 대개 자기 이전 버전 열이다.

### 런타임이 특정 회사의 제품 워크로드를 대표 사례로 삼으면 최적화의 축이 그쪽으로 굽는다

이 릴리스에서 프로덕션 성능의 대표 사례는 Claude Code이고,
CPU 최적화의 세 항목 — GC 타이머 요청 시점, Strong 루트 방문 방식,
futex 호출 감소 — 은 오래 도는 유휴 프로세스를 위한 것이다.
그리고 개선 폭이 가장 큰 지표가 유휴 CPU 5배 감소다.

이 조합에서 읽을 수 있는 것은 최적화의 우선순위다.
JavaScript 런타임의 워크로드는 크게 세 갈래다 —
짧게 실행되고 끝나는 CLI와 빌드 도구,
요청을 처리하는 서버,
그리고 오래 켜져 있는 대화형 애플리케이션이다.
이번 릴리스의 대표 지표는 셋 중 마지막에 속하며,
그것이 이 런타임을 인수한 회사의 주력 제품 형태다.

이 방향이 나쁘다는 것은 아니다.
오래 도는 대화형 애플리케이션은 지금 가장 빠르게 늘어나는 범주이고,
코딩 에이전트와 데스크톱 앱과 로컬 개발 서버가 모두 여기 속한다.
[이 저장소가 최근 기록한 도구들](../agentic-coding/agentcodegui.md)의
상당수가 그 형태이며, 유휴 CPU와 메모리 반납은 그들에게 직접적인 값이다.

문제는 우선순위가 공개되지 않는다는 점이다.
런타임을 고르는 사람은 자기 워크로드가 그 우선순위 안에 있는지 알아야 하는데,
발표문은 대표 사례를 하나만 제시하고
다른 워크로드에서의 변화는 hello world 앱과 HTTP 서버 벤치마크로만 보여 준다.
빌드 도구나 배치 작업처럼 CPU를 계속 쓰는 워크로드의 수치가 없고,
그 침묵이 정보다 —
개선이 없었거나 측정하지 않았거나 둘 중 하나이며,
어느 쪽이든 그 워크로드를 가진 사람은 직접 재 봐야 한다.
