# Vite 8.1 출시

원문: [Vite 8.1 is out!](https://vite.dev/blog/announcing-vite8-1)

HN 토론: <https://news.ycombinator.com/item?id=48657370> (5점, 0개 댓글)

## 요약

2026년 6월 23일 Vite 공식 블로그에 실린 Vite 8.1 출시 글이다. 저자 표기는 없다.
Vite 8이 3월에 Rolldown 기반의 단일 번들러로 나왔고 지금 주간 내려받기가 4,160만 회로 Vite 7 전체에 가깝다고 하며, 업그레이드 회귀 수정과 함께 8.1을 내놓는다고 한다.
시작은 `vite.new`나 `pnpm create vite`이다.

기능은 여섯 가지이다.

- 실험적 번들 개발 모드(Bundled Dev Mode): 이전 이름은 전체 번들 모드이며 모듈이 매우 많은 큰 앱을 빠르게 한다. React 컴포넌트 1만 개를 불러오는 앱에서 번들하지 않은 개발 서버보다 시작이 약 15배, 전체 새로 고침이 10배 빠르고 HMR은 즉각적이라고 한다. Linear 팀의 결과는 콜드 스타트 렌더링 최대 3배, 전체 새로 고침 약 40%, 네트워크 요청 10배 감소이다. 브라우저 쪽과 기본 플러그인과 핵심 기능에 집중하며 서드파티 플러그인과 사소한 기능은 동작하지 않을 수 있다. `--experimental-bundle` 플래그나 `experimental.bundledDev: true`로 켠다.
- 실험적 청크 임포트 맵: 청크 임포트에 해시가 들어가 한 파일이 바뀌면 그것을 가져오는 모든 청크의 해시가 연쇄해서 바뀌는 문제를 임포트 맵으로 줄여 캐시 효율을 높인다. Rolldown의 기능 위에 Vite 지원을 얹은 것이고 `experimental.renderBuiltUrl`은 아직 함께 동작하지 않는다.
- Wasm ESM 통합: WebAssembly ESM 통합 제안을 지원해 `import { add } from './add.wasm'`처럼 가져오고 내보낸 함수를 바로 부른다.
- Lightning CSS 기본 사용에 한 걸음: PostCSS에 있고 Lightning CSS에 없던 두 기능(CSS 파일이 외부 CSS 파일을 가져오는 것, 플러그인이 파일 의존성을 등록하는 것)을 Lightning CSS 팀과 함께 추가했다. 다음 메이저에서 기본 변환기로 삼는 것을 검토하며 `css.transformer: 'lightningcss'`로 시험한다.
- `import.meta.glob`의 대소문자 무시: 새 옵션 `caseSensitive`가 있다.
- 사용자 정의 HTML 요소와 속성의 자산 발견: 새 옵션 `html.additionalAssetSources`로 커스텀 요소와 속성(예 `data-src-dark`)의 자산을 찾는다.

글에는 호환성을 깨는 변경이나 이전 안내가 없고 기타 변경은 변경 기록으로 안내한다. 감사 절은 Vite가 VoidZero의 제공이며 Bolt와 Nuxt Labs와 협력한다고 적는다.

## 분석

### 중심 주장은 큰 앱의 개발 서버 병목을 푼다는 것이다

앞선 8.0 글이 예고한 전체 번들 모드가 이름을 바꿔 실험 기능으로 들어왔다. 번들하지 않는 개발 서버가 프로젝트가 커질수록 느려지는 문제(특히 네트워크 프록시 뒤)를 번들로 푸는 것이다.
이는 글의 서술을 이 문서가 정리한 것이다.

### 빌드 도구 교체의 여파를 정리하는 릴리스이다

Lightning CSS의 기본값 전환 준비, 청크 임포트 맵, Wasm 통합은 Vite 8의 Rolldown과 Oxc 위에서 가능해진 기능이다. 이는 이 문서의 해석이다.
`vite/vite-8-0.md`가 다룬 통합 체인의 후속이다.

## 비평

### 수치는 특수한 조건의 값이다

15배와 10배는 컴포넌트 1만 개를 불러오는 앱의 실험이고 Linear 수치는 한 회사의 보고이다.
일반 앱에서의 이득과 번들하지 않은 모드와의 정확한 차이는 글에 없다.

### 실험 기능의 제약이 크다

번들 개발 모드는 서드파티 플러그인이 동작하지 않을 수 있고 플러그인 쪽 문서도 진행 중이라고 글이 적는다.
청크 임포트 맵은 `renderBuiltUrl`과 함께 동작하지 않는다. 둘 다 프로덕션 도입의 전제 조건이 아니라 의견을 구하는 단계이다.

### 외부 반응

Lobste.rs의 `vite.dev` 도메인에는 Vite 8.0 글 하나뿐이고 이 글은 없었다.
GeekNews에서는 `Vite 8.1`로 검색해 이 글의 토픽이 없었다(대조 쿼리는 정상이었다).

## 인사이트

### 가져갈 것은 번들하지 않는 개발 서버의 한계를 측정하는 기준이다

모듈 수와 네트워크 요청 수에 따라 시작과 새로 고침이 느려지는 정도를 재 보면 이 모드가 필요한 규모를 알 수 있다. 이는 이 문서의 적용이다.

### 실험 옵션은 격리해서 시험한다

`--experimental-bundle`은 별도 브랜치에서 자기 플러그인 구성으로 시험하고 피드백 토론에 결과를 남기는 방식이 맞다.

### 확인할 관찰

이 글의 주장을 가를 관찰은 세 가지이다.
번들 개발 모드의 일반 앱 효과와 플러그인 호환 범위,
Lightning CSS가 다음 메이저의 기본값이 되는지,
청크 임포트 맵과 `renderBuiltUrl`의 공존이다.
