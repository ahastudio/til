# Vinext

<https://github.com/cloudflare/vinext>

<https://blog.cloudflare.com/vinext/>

HN 토론: <https://news.ycombinator.com/item?id=47142156> (540점, 236개 댓글)

## 요약

Vinext는 Next.js API 표면을 Vite 위에서 재구현한
Vite 플러그인이다.

Next.js를 fork하거나 `next build` 출력을 감싸는 방식이 아니라,
Next.js의 라우팅·SSR·`next/*` 모듈 임포트·CLI를
처음부터 독립적으로 다시 구현했다.

핵심 수치:

- **4x** 빠른 빌드 속도
- **57%** 더 작은 번들 크기
- **94%** Next.js API 표면 커버리지
- **$1,100** 상당의 AI 토큰 소비
- **1주일** 개발 기간

## 배경: 왜 만들었나

Cloudflare가 느낀 문제는 두 가지였다.

1. Next.js 빌드 도구체인에 종속되면
   배포 대상과 성능 최적화 여지가 좁아진다.
2. OpenNext처럼 `next build` 결과를 어댑팅하는 방식은
   Next.js 내부 변경마다 깨질 위험이 있다.

해법으로 택한 것은 “API 계약만 존중하고
빌드 전체를 갈아치우는” 접근이다.

## OpenNext와의 차이

| 항목          | OpenNext                          | Vinext                       |
|---------------|-----------------------------------|------------------------------|
| 방식          | next build 결과를 플랫폼에 맞게 변환 | 빌드 자체를 Vite로 대체       |
| Next.js 의존  | 있음                              | 없음                          |
| API 재구현    | 부분적                            | 전체                          |
| 깨짐 위험     | Next.js 내부 변경 시 높음         | API 표면 변경 시에만           |

## 핵심 기능

### 라우팅

Pages Router와 App Router 모두 지원한다.

- 동적 라우트, catch-all 세그먼트
- 병렬 라우트, 인터셉팅 라우트
- 미들웨어
- 파일 기반 메타데이터 라우트
  (sitemap, robots.txt, OG 이미지)

### 서버 사이드 렌더링

- 두 라우터 모두 스트리밍 SSR 지원
- Vite RSC 플러그인을 통한 React Server Components
- ISR(증분 정적 재생성) 포함 정적 생성
- Server Actions

### 개발 경험

- 설정 없이 앱 구조 자동 감지
- HMR 지원
- `.env` 파일 자동 로드

### 배포

- Cloudflare Workers 기본 타깃
  (콜드 스타트 없음, 글로벌 분산)
- 라우팅·모듈 심·SSR 파이프라인은
  Cloudflare 비특화 구조이므로
  다른 플랫폼 이식도 가능
- Vercel 프루프오브컨셉을 30분 만에 완성했다고 밝힘

## Traffic-aware Pre-Rendering (TPR)

가장 주목할 만한 신기능이다.

기존 정적 생성은 “모두 사전 렌더”이거나
“아무것도 사전 렌더하지 않음” 중 하나였다.

TPR는 배포 시점에 Cloudflare 존(zone) 분석을 쿼리해
**실제 트래픽이 높은 페이지만 골라 사전 렌더**한다.

- 나머지는 온디맨드 SSR + ISR 캐시 활용
- 새 배포마다 최신 트래픽 패턴 기반으로 갱신

트래픽 데이터로 사전 렌더 범위를 동적으로 결정하는
아이디어는 인프라와 렌더링 전략을 연결하는 흥미로운 접근이다.

## 마이그레이션 방법

Vinext에는 AI 에이전트용 스킬이 내장되어 있다.
Claude Code, OpenCode, Cursor, Codex 등
주요 AI 코딩 도구와 연동된다.

마이그레이션은 비파괴적이다.

- `next.config`, `tsconfig.json`, 소스 파일 수정 없음
- Next.js 의존성 제거 없음
- 기존 Next.js 설정이 그대로 공존

## AI가 코드를 만든다는 것

Vinext의 코드 대부분은 Claude Code가 작성했다.
인간 엔지니어 1명이 아키텍처 방향을 결정하고,
AI가 구현과 테스트를 담당하는 방식이었다.

결과물:

- Vitest 테스트 1,700개 이상
- Playwright E2E 테스트 380개
- tsgo 기반 전체 TypeScript 타입 검사
- oxlint 기반 린팅
- CI에서 PR마다 전체 실행

Cloudflare는 이 경험을 일반화해서
“API 계약 + 빌드 도구 + AI 모델”이 있으면
그 사이를 AI가 채울 수 있다는 패턴이
다양한 소프트웨어 영역에서 반복될 것이라 전망했다.

## 비평

### “처음부터 다시 만들었다”는 서사가 물려받은 토대를 감춘다

Vinext의 발표 제목은 “AI로 일주일 만에 Next.js를 다시 만들었다”이지만,
그 “처음부터”라는 말이 감추는 것이 많다.
HN에서 wesselbindt는 가장 기본적인 hello world 예제조차 동작하지 않는데
무언가를 “다시 만들었다”고 할 수 있느냐고 물었고,
다시 만드는 대상에서 검증된 방대한 테스트 스위트를 물려받았다면
그것을 “처음부터”라 부르는 것이 말이 되느냐고 되물었다[^wesselbindt].
발표 자신도 이를 인정한다.
adithyassekhar가 인용했듯, Next.js 팀의 잘 문서화된 API 표면과
포괄적인 테스트 스위트가 이 프로젝트를 가능하게 한 큰 부분이라고
발표가 스스로 밝힌 것이다[^adithyassekhar].

이 서사가 문제인 이유는 그것이 AI의 성취를 과장하기 때문이다.
troupo가 본문에 묻혀 있다고 짚은 문장이 핵심이다.
vinext의 약 95%가 순수 Vite이고,
라우팅·모듈 심·SSR 파이프라인·RSC 통합 어느 것도 Cloudflare 특화가 아니라는 것,
곧 진짜 성취는 사람이 만든 Vite라는 것이다[^troupo].
AI가 일주일에 채운 것은 Next.js라는 명세와 Vite라는 엔진,
그리고 물려받은 테스트 사이의 틈이었다.
그 틈을 채운 것은 인상적이지만,
그것을 “처음부터 다시 만들었다”고 부르는 것은
그 아래 수년간 쌓인 사람의 일을 지운다.
AI가 값싸게 복제한 것은 이미 잘 명세되고 잘 테스트된 것뿐이다.

### “Next.js는 잘 명세되어 있다”는 전제가 흔들린다

Vinext의 접근 전체는 Next.js의 API 표면이 명확한 계약이라는 전제에 선다.
그런데 HN에서 cline6은 그 전제를 정면으로 반박했다.
발표는 “Next.js가 잘 명세되어 있다”고 하지만,
문서가 많은 것과 잘 명세된 것은 다르며,
반복해서 문제가 된 수많은 미문서화·부실 문서화 동작이 있다는 것이다[^cline6].
wewewedxfgdf도 “재구현했더니 쉬웠다”는 이야기에 깊이 회의하며,
악마는 디테일에 있고, 수년간의 버그 수정과 무수한 엣지 케이스가
그 안에 있을 리 없다고 했다[^wewewedxfgdf].

이 반박이 결정적인 이유는 그것이 94% 커버리지의 의미를 뒤집기 때문이다.
발표는 Next.js API 표면의 94%를 커버한다고 자랑하지만,
진짜 어려움은 남은 6%에 있다.
그 6%가 바로 미문서화된 동작, 오랜 버그 수정, 프로덕션의 엣지 케이스다.
잘 명세된 부분을 재구현하는 것은 AI에게 쉽지만,
명세되지 않은 채 코드에만 존재하는 동작은 재구현되지 않는다.
실제 앱이 깨지는 곳은 정확히 그 명세 바깥의 6%인데,
“94% 커버”라는 숫자는 그 6%가 가장 중요하다는 사실을 가린다.
잘 명세된 것을 복제하기 쉬운 만큼,
명세의 바깥에 있는 것이 진짜 벽으로 남는다.

### AI가 만든 프레임워크의 보안은 테스트로 증명되지 않았다

이 문서의 기존 인사이트는 1,700개의 테스트와 380개의 E2E 테스트를
AI 코드에 대한 신뢰의 근거로 제시했다.
그러나 그 신뢰는 발표 직후 시험대에 올랐다.
공개 직후 Vercel이 vinext의 취약점들을 공개 폭로했고,
보안 연구자들은 “바이브 코딩된 Next.js 대체물을 바이브 해킹한다”는 제목으로
그 취약점들을 파고들었다.
HN에서 thawab이 Next.js가 RSC 구현 때문에 원격 코드 실행 취약점을 겪었다며
AI 버전은 한동안 손대지 않겠다고 한 우려[^thawab]가
곧바로 현실이 된 것이다.

이 사실이 기존 인사이트를 반박하는 이유는
테스트가 증명하는 것과 증명하지 못하는 것이 다르기 때문이다.
1,700개의 테스트는 명세된 동작이 의도대로 작동함을 증명하지만,
명세되지 않은 위험, 곧 보안 취약점의 부재는 증명하지 못한다.
테스트는 “해야 할 일을 하는가”를 검사하지
“하지 말아야 할 일을 하지 않는가”를 검사하지 않는다.
AI가 테스트를 통과하도록 코드를 짜면 기능은 맞지만,
그 코드가 열어 둔 공격 표면은 테스트의 눈 밖에 있다.
이 저장소의 다른 노트들이 반복해 온 주제,
곧 형식적 검증의 통과가 의미적·보안적 정확성을 보장하지 않는다는 문제가
AI가 짠 프레임워크에서 가장 날카롭게 드러난다.
테스트 커버리지는 신뢰의 필요조건이지 충분조건이 아니며,
AI 생성 코드에서 그 간극은 더 넓다.

### 이미 Astro를 산 Cloudflare가 또 만드는 전략의 모순

Vinext의 존재 이유에도 의문이 있다.
HN에서 ratorx는 Cloudflare가 한 달 전 Astro를 인수했는데,
Astro가 Next와 비슷한 문제를 다루는 것으로 보인다며,
그렇게 값싸게 만들어 권장까지 하는 것이라면 무엇을 위한 것이냐고 물었다[^ratorx].
samtheprogram은 README의 아이러니를 짚었다.
Node.js 프로덕션 서버(`vinext start`)는 테스트용이고
Workers 배포보다 덜 완전하며, Cloudflare Workers가 주 타깃이라는 것이다[^samtheprogram].

이 모순이 드러내는 것은 vinext의 진짜 목적이다.
발표는 라우팅·SSR 파이프라인이 Cloudflare 비특화라 이식 가능하다고 하지만,
실제로 완전히 지원되는 배포 대상은 Cloudflare Workers다.
곧 vinext는 중립적 프레임워크가 아니라
Next.js 앱을 Cloudflare Workers로 끌어오는 통로다.
이것은 이 저장소의 다른 노트가 EmDash에서 관찰한 패턴,
곧 오픈소스를 인프라 채택의 미끼로 삼는 전략의 반복이다.
Astro 인수와 vinext 개발이 겹치는 것도 모순이 아니라,
어떤 경로로든 개발자를 Cloudflare 런타임으로 데려오려는 여러 베팅으로 읽힌다.
공개된 소스와 이식 가능하다는 문구가,
실제로는 한 플랫폼으로 수렴하는 기울기를 가린다.
발표가 밝힌 “빌드 타임 정적 사전 렌더링은 아직 지원하지 않는다”는 제약도,
이 프로젝트가 완성된 대안이 아니라
특정 플랫폼을 겨냥한 실험임을 함께 말해 준다.

## 인사이트

### 1. API 표면이 진짜 계약이다

Next.js를 쓰는 앱 코드는 `next/*` import,
파일 기반 라우팅 규칙,
Server Action 시그니처에만 의존한다.

내부 컴파일러가 무엇인지는 관심 밖이다.
이 사실이 vinext의 가능성을 열었다.

“구현을 교체해도 사용자 코드는 그대로”라는 전략은
플러그인 아키텍처, 인터페이스 우선 설계의
전형적인 활용 사례다.

HN에서 switz는 이 계약이 AI 시대에 낳는 뒤틀린 유인을 짚었다.
일을 더 잘 문서화하고 계약을 더 강하게 정의할수록,
그것을 다른 사람이 복제하기 더 쉬워진다는 것이다[^switz].
잘 명세된 API는 좋은 설계의 증거이지만,
동시에 그 명세가 AI에게 복제의 청사진이 된다.
Next.js가 자기 API를 잘 문서화한 바로 그 미덕이,
vinext가 그것을 일주일에 재구현할 수 있게 한 조건이 되었다.
명세를 공개하고 계약을 명확히 하는 오픈소스의 미덕이,
AI가 그 구현을 값싸게 복제하는 시대에는
경쟁 우위를 스스로 넘겨주는 일이 될 수 있다.

### 2. 빌드 도구 교체가 성능 레버가 된다

Next.js 컴파일러를 Vite로 바꾼 것만으로
빌드 4x 향상, 번들 57% 감소가 나왔다.

프레임워크 기능 설계와
빌드 도구 효율이 분리 가능한 문제임을
실증했다.

### 3. 플랫폼 데이터가 렌더링 전략을 바꾼다

TPR는 단순한 최적화가 아니라
“인프라가 어플리케이션 레이어 결정에
직접 개입”하는 새로운 패턴이다.

Cloudflare가 트래픽 데이터를 갖고 있기 때문에
할 수 있는 접근이다.
플랫폼 수직 통합의 이점이 렌더링 전략으로
연결된 사례로 볼 수 있다.

### 4. AI 코드 생성의 신뢰 조건

AI가 쓴 코드 1,700개 테스트와
380개 E2E 테스트는 단순한 품질 보증이 아니다.

“AI가 작성했다”는 사실을 신뢰할 수 있으려면
테스트 커버리지와 CI 파이프라인이
그 신뢰의 실질적 근거가 된다.

사람이 리뷰하는 범위가 줄어들수록
검증 자동화의 범위와 엄밀성이
더 중요해진다.

### 5. 실험적이다 = 진지하게 살펴볼 때다

“실험적(experimental)”이라는 레이블은
사용을 미루라는 신호가 아니라,
설계 아이디어를 살펴볼 최적의 시점이라는 신호다.

코드베이스가 작고, 의존이 단순하고,
아키텍처 의도가 명확할 때
구조를 읽기 가장 쉽다.
