# LLM 시대의 웹 소프트웨어는 사용자가 확장하게 하되 코드가 아니라 좁은 권한만 쥐어 줘야 한다

원문: [Extensible Software in the age of LLMs | Jeremy Morrell](https://jeremymorrell.dev/blog/extensible-software-in-the-age-of-llms/)

HN 토론: <https://news.ycombinator.com/item?id=49363668> (177점, 88개 댓글)

GN 토론: <https://news.hada.io/topic?id=36837>

## 요약

관측성(observability)을 오래 다뤄 온 Jeremy Morrell이 2026년 8월 18일에 쓴
긴 글이다.
글쓴이는 Cloudflare에서 일하며 Kenton Varda의 글에 영향을 받았다고 처음에
밝힌다.
중심 주장은 웹 소프트웨어가 정적이어서 개발자가 시간과 관심을 가장 큰
사용자층에 쏟는 동안 사용자마다 다른 긴 꼬리의 요구가 채워지지 않는데,
LLM이 확장의 작성 비용을 크게 낮췄으니 웹에서도 사용자가 확장할 수 있는
소프트웨어를 만들 때가 되었다는 것이다.
앱은 책임질 수 있는 단단한 핵심으로 두고, 사용자가 LLM으로 빈 곳을 채우되
샌드박스 기술이 배포 비용을 낮추고 좋은 보안 경계를 준다는 구상이다.

글은 이미 일어난 변화를 출발점으로 삼는다.
LLM이 개인 한 사람의 작업 방식에 맞춘 소프트웨어를 만드는 데 능하다는 것이고,
Y Combinator가 작은 소프트웨어(small software)를 위한 클라우드를 말한 것도
인용한다.
Pi는 LLM 기반 소프트웨어의 예로 든다.
검증된 핵심이 있고 요청만으로 끝없이 확장되며 사용자가 맞춤 설정을 공유할 수
있다는 것이다.
다만 지금의 확장 가능한 소프트웨어는 AI 에이전트, IDE, 게임 모드, Blender와
CAD 확장 같은 로컬 소프트웨어이고 진입 장벽이 높은 전문가용 도구라고 한다.

글이 상상하는 웹 쪽 모습은 이렇다.
지금은 웹훅으로 앱의 변화에 반응하게 하는데, 별도 서비스를 만들고 운영해야
해서 확장의 문턱이 높다.
읽을 거리 저장 앱에 4,000단어가 넘는 즐겨찾기를 전자책 리더로 보내게 하거나,
arXiv에서 내 전공의 새 논문을 매주 찾아 요약을 붙이게 하거나, 내가 자주 읽는
사이트를 기본 알고리즘이 망치면 예시를 몇 개 가져와 맞춤 파서를 만들게 하는
식이다.
글은 같은 접근이 맞는 영역으로 AI 에이전트, 사내 플랫폼, 지원 플랫폼, 관측성
플랫폼을 든다.
사내 플랫폼에서는 직원이 만든 도구가 수백, 수천 개가 되면 어떻게 유지하고,
필요한 데이터만 어떻게 받게 하고, 무엇을 하는지 어떻게 감사하고, 토큰은 누가
회전하는지 같은 문제가 생긴다고 짚는다.
데이터 접근을 내부 플랫폼 팀이 맡고 새어 나갈 인증 토큰이 없는 곳에 배포하게
하자는 것이 글의 제안이다.
관측성에서는 데이터 수집 때의 임의 변환, 알람이 부르는 사용자 코드, 위험이 큰
순간(배포, 기능 플래그 출시)에 돌리는 코드를 말한다.

웹에서의 확장은 어렵다고 글이 인정한다.
Obsidian이 보여 주듯 확장 모델이 모든 플러그인을 신뢰하게 하면 능력은
크지만 다른 사람의 데이터를 담은 소프트웨어에서는 무너진다.
사용자 코드의 오류나 무한 루프가 서비스를 내려서는 안 되고, 키를 가진 확장이
제3자에게 전달하면 안 되며, 서비스 거부 공격, Spectre, 무료 연산으로 하는
채굴까지 막아야 하는 위험의 목록을 든다.
그런데도 2007년부터 이를 대규모로 해 온 선례가 Salesforce라고 한다.
Salesforce는 컴파일러, 타입 시스템, 런타임, 표준 라이브러리, 디버거, 언어에
통합된 SQL을 직접 만들고 교육 생태계까지 세웠고, 같은 일을 오늘은 서버리스로
쓰는 코드와 견주어 보인다.

새로운 기본 요소(primitive)에 필요한 속성은 다섯 가지다.
경제적이어야 하고(쓰지 않을 때 비용이 거의 0), 콜드 스타트가 빨라야 하고,
한도를 통제해야 하고, 고립 경계가 단단해야 하고, 코드가 안전하게 행동할 수
있어야 한다.
마지막 속성에서 글이 가장 길게 다루는 것이 능력(capability) 모델이다.
사용자 코드에 API 키를 주거나 프록시를 세우는 대신, 사전에 승인된 이메일 하나를
가져오는 함수 같은 좁은 참조만 건네는 방식이다.
주변 환경의 입출력을 없애면 코드는 받은 참조로만 행동할 수 있어서 키가 코드에
노출되지 않고, 다른 외부 통신 수단이 없으면 데이터를 빼돌릴 길도 없다고 한다.
이 방식은 OpenAPI 정의 더미보다 TypeScript로 쓴 능력 정의가 LLM에게 토큰
효율적이라는 부수 효과도 있다고 한다.

기술 선택지는 인터프리터, V8 격리(isolate), microVM, WASM과 WASI다.
microVM은 오버헤드가 크지만 POSIX와 전체 OS를 주고, 작성과 번들과 시험에
쓰기 좋다고 한다.
글은 그중 Cloudflare의 Dynamic Workers를 가장 완성된 틀로 꼽으면서, 직접
만들어야 하는 것으로 관측성, 사용자별 데이터 저장, 내구성 있는 실행, 소스 관리,
호스팅 LLM, JavaScript 도구의 자체 호스팅을 든다.
끝에는 정적 블로그를 가장 작은 바이브 코딩 플랫폼으로 바꾼 시연이 있고,
플랫폼은 설계하기도 운영하기도 디버그하기도 어렵지만 그럴 가치가 있다는
말로 맺는다.

## 분석

### 핵심 전제는 확장의 작성 비용이 내려갔다는 것이다

글의 논리는 두 개의 비용 변화에 기댄다.
LLM이 확장 작성 비용을 낮추었고, 현대의 샌드박스 기술이 배포 비용과 보안을
해결한다는 것이다.
이 둘이 함께 있어야 웹 소프트웨어가 로컬 도구처럼 확장될 수 있다.
앞의 것만 있으면 사용자 코드를 서버에서 돌릴 수 없고, 뒤의 것만 있으면 아무도
확장을 쓰지 않는다.
글이 이를 한꺼번에 말하는 것은 두 변화가 최근에 동시에 일어났다는 인식 때문이다.

### 안전한 확장의 설계 원리는 프록시가 아니라 능력이다

글이 가장 오래 남는 부분은 프록시 방식의 한계다.
프록시는 불투명 토큰을 진짜 자격 증명으로 바꾸고 허용 목록과 속도 제한을
적용하지만, 허용할 동작을 좁히는 필터가 곧 복잡해지고 API가 바뀌면 따라가야
한다.
좁게 시작해서 넓히는 것이 아니라 넓은 권한에서 시작해 정밀하게 줄이려는 시도는
어렵다는 판단이다.
능력 모델은 반대로 필요한 만큼만 건네고, 코드가 그 밖의 어떤 것도 호출할 수
없게 만든다.
글은 이를 IFTTT가 트위터 API 키 대신 새 트윗을 올리는 함수를 주는 것에
빗댄다.

### Salesforce는 새 아이디어의 증거가 아니라 오래된 선례다

글은 이 접근이 새롭다고 말하지 않고, 20년 전에 이미 같은 문제를 푼 회사가
있다고 한다.
그때는 값싸게 샌드박스 코드를 돌릴 방법이 없어서 언어와 런타임과 생태계를
통째로 만들어야 했고, 오늘은 선택지가 많아졌다는 것이다.
이 구도는 확장 가능한 웹 소프트웨어가 가능한지에 대한 의심을 이미 가능했던
일의 비용이 내려간 문제로 바꾼다.
이 해석은 글의 구성을 읽은 것이다.

### 격리 방식은 목록이고 능력 모델은 격리와 독립적이다

글은 인터프리터, V8 격리, microVM, WASM을 서로 배타적이지 않다고 말한다.
WASM을 V8 격리나 microVM 안에서 돌릴 수 있고, 격리 기술이 능력 모델을 주지
않으면 어떻게 기능을 노출할지 생각하는 틀로 쓰라고 한다.
이 구분 덕분에 글의 핵심 주장은 특정 제품과 분리해서 읽을 수 있다.
다만 그 뒤의 Dynamic Workers 소개는 제품 선택으로 이어진다.

## 비평

### 기술 조사가 한 제품으로 모이는 구조다

글쓴이는 Cloudflare에서 일한다고 밝히지만, 선택지를 훑은 뒤 Dynamic Workers를
특별히 강조하며 가장 프로덕션에 가까운 틀이라고 말한다.
HN의 bensyverson은 이 글이 Cloudflare OS의 광고로 읽힌다고 했고, 모든 기술
회사가 기업이 작은 일회성 앱을 안전하게 만들 안정적 기반이 되려 하는 중이어서
Cloudflare가 기본이 되기는 상상하기 어렵다고 썼다.[^bensyverson]
저자는 이것이 샌드박스와 능력 모델이라는 발상의 광고에 가깝다고 답하고,
조사한 한 이 패턴을 구현한 제품은 Dynamic Workers가 사실상 하나라고 했다.[^masterj]
글의 앞쪽에서 이해 충돌을 밝힌 점은 공정하지만, 다른 제품과 실제로 비교한
내용이 없어서 가장 완성된 틀이라는 판단은 독자가 직접 확인해야 한다.

### 웹이어야 한다는 전제가 사례로 증명되지 않는다

HN의 zahlman은 한 사람을 위한 소프트웨어라면 왜 인터넷에 있어야 하고 왜
클라이언트와 서버 모델과 배포가 필요하냐고 물었다.
여러 운영체제를 위한 네이티브 개발이 번거로워서 웹으로 가는 것인데 혼자 쓰면
하나만 지원하면 되고, 확장 가능한 로컬 소프트웨어를 설계하면 되지 않느냐는
것이다.[^zahlman]
wild_egg는 개인 소프트웨어도 웹 기반을 선호한다고 답했다.
폰과 노트북과 데스크톱에서 동기화와 설치와 갱신을 걱정하지 않고 가족에게
접근을 여는 것도 쉽다는 이유다.[^wild_egg]
글은 웹의 배포 이점을 말하지만 소프트웨어를 혼자 쓰는 사용자가 왜 웹을
선택하는지는 다루지 않는다.
두 답이 다른 것은 이 질문이 취향과 사용 환경에 달려 있음을 보여 준다.

### 사용자가 확장을 원한다는 수요를 가정한다

HN의 13415는 전통적으로 확장에 관심 있는 사람은 고급 사용자뿐이며 일반
사용자는 믿을 만한 소프트웨어를 원한다고 썼다.
AI는 사람을 대신하고 전통적 소프트웨어는 사람과 AI가 쓰는 도구라서 두 세계가
잘 섞이지 않는다는 견해다.[^13415]
bevr1337은 87세 할아버지가 어학 연습용 앱을 직접 만들고 있다며 맞춤 소프트웨어가
일반 대중에게 열릴 수 있다고 답했다.[^bevr1337]
zahrevsky는 확장 가능한 소프트웨어가 오히려 사용자가 원하는 것을 더 잘 하게
한다고 보지만, 확장이 문서 하나를 만드는 만큼 쉬워질 수 있는지는 의심스럽다고
했다.[^zahrevsky]
글은 각주에서 확장 생태계의 대부분을 소수가 만들 것이라고 스스로 인정한다.
그러면 이 소수가 만든 확장을 다수가 설치하는 구조가 되고, 그때의 신뢰 문제는
확장 도입 전에 이미 있는 문제와 같다.
이 마지막 연결은 이 문서의 추론이다.

### 샌드박스가 푸는 문제와 남는 문제가 구분되지 않는다

HN의 socketcluster는 샌드박스 실행이 바이브 코더에게는 충분히 안전하지 않다고
썼다.
그들이 소집단이 공유하는 데이터 기반 앱을 만들 때 외부 엔드포인트를 열거나
접근 제어 논리가 틀리면 샌드박스의 보안은 의미가 없고, 사용자마다 다른 접근
규칙을 설정하려 할 것이기 때문이다.[^socketcluster]
글의 능력 모델은 코드가 가진 권한을 좁히지만 어떤 능력을 누구에게 주는가라는
정책은 여전히 사람이 정해야 한다.
0xbadcafebee는 확장을 더할수록 복잡해져서 앱이 쓸 수 없게 되며, 확장 대신
독립된 작은 프로그램들을 조합하는 유닉스식 접근이 더 낫다고 했다.
이미 그런 일을 하는 플랫폼이 운영체제라는 것이다.[^0xbadcafebee]
글의 구상이 이 지적에 어떻게 답하는지는 글에 없다.

## 인사이트

### 능력 정의가 곧 LLM을 위한 제품 API가 된다

글이 말한 TypeScript 능력 정의의 토큰 효율은 부수 효과가 아니라 구조다.
사용자의 요청을 코드로 바꾸는 LLM이 읽는 인터페이스는 사람이 읽는 API 문서와
다르다.
어떤 능력을 노출할지가 곧 확장이 할 수 있는 일의 전부를 정한다.
그러므로 호스트 개발자의 가장 중요한 설계 결정은 확장 지점이 아니라 능력의
어휘와 그 경계가 된다.
이 능력의 목록은 앞으로 제품이 지원할 기능의 지도이기도 해서, 나중에 넓히기는
쉽고 좁히기는 어렵다.
이는 이 문서의 해석이며 글이 말한 것은 아니다.

### 사용자 확장의 책임은 사라지지 않고 이동한다

글의 사내 플랫폼 사례는 사용자가 만든 도구의 유지, 감사, 접근 범위, 토큰
회전이라는 문제를 플랫폼 팀으로 옮긴다.
이 이동은 문제를 푸는 것이 아니라 한곳에 모으는 것이다.
수천 개의 확장이 생기면 플랫폼 팀이 그것들의 수명 주기와 소유자를 알아야 하고,
확장이 깨질 때 누가 고치는지가 새 문제가 된다.
HN의 hosh는 Smalltalk도 한 사람을 위한 확장성을 가졌지만 오픈소스처럼 코드가
공유되고 협업이 폭발한 흐름은 놓쳤고, 핵심은 클라이언트와 서버가 아니라
아이디어를 어떻게 공유하느냐라고 했다.[^hosh]
글이 공유를 말하지만 공유된 확장의 신뢰와 유지보수는 다루지 않는다.
이 부분은 이 문서의 추론이다.

### 이 구상의 성패는 수요가 아니라 운영 경제에서 갈린다

글이 제시한 다섯 속성 가운데 경제성은 가장 구체적인 제약이다.
쓰지 않을 때 비용이 거의 0이고 실행 한 번이 아주 싸야 한다.
이는 사용자당 컨테이너를 띄우는 방식이 안 되는 이유이기도 하다.
수요가 있더라도 이 경제성이 안 맞으면 확장은 소수 고객에게만 제공된다.
이 글은 관측성에서 시작해 플랫폼 운영을 오래 해 온 사람이 쓴 글이어서, 수요보다
운영의 어려움을 더 구체적으로 안다는 점이 장점이자 한계다.
어려운 부분이 운영이라는 판단은 이 문서의 해석이다.
