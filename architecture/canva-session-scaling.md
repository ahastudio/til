# Canva는 어떻게 수억 건의 사용자 세션을 빠르고 안전하게 유지할까?

원문: [Session revocations at scale - Canva Engineering Blog](https://www.canva.dev/blog/engineering/session-revocations-at-scale/)

GN 토론: <https://news.hada.io/topic?id=32156>

## 요약

Canva는 수억 명의 사용자 세션을 관리하며, 매초 수십만 건의 백엔드 요청마다
로그인 사용자가 여전히 유효한지 확인해야 한다. 기존 방식은 최근 12시간
동안의 세션 취소(revocation) 기록, 즉 로그아웃되었거나 무효화된 세션
목록을 각 게이트웨이 인스턴스가 메모리에 캐시로 들고 있는 것이었다. 문제는
배포(deploy) 시점마다 발생했다. 새 버전을 롤아웃하면 수백 개의 게이트웨이
포드가 동시에 부팅되면서, 각각 MySQL에서 100만 건이 넘는 취소 기록을
한꺼번에 내려받았고, 이 급격한 트래픽 스파이크가 데이터베이스에 과부하를
일으켰다. 임시방편으로 읽기 레플리카를 늘려 버텼지만 근본적인 해결책은
아니었다.

Canva 팀은 Redis 같은 인메모리 캐시 도입도 검토했지만, 내구성 부족과
운영 복잡성 증가라는 이유로 채택하지 않았다. 대신 채택한 해법은 S3를
분산 캐시처럼 사용하는 것이었다. 취소 기록을 30분 단위 시간 윈도우로
쪼개어 각각 하나의 S3 객체로 저장하고, 게이트웨이는 과거 12시간에
해당하는 최신 청크(chunk)들만 내려받는다. 이렇게 하면 부팅 시 폭증하는
트래픽이 데이터베이스가 아니라 S3로 향하게 되고, S3는 이런 종류의 팬아웃
읽기 부하에 훨씬 강하다.

성능을 더 끌어올리기 위해 각 취소 기록을 사용자 ID와 로그인 타임스탬프를
포함하는 16바이트의 이진(binary) 형식으로 압축했다. 이는 기존 대비 메모리
사용량을 87.5% 줄이는 효과를 냈다. 각 청크 내부의 기록은 주체(principal)
기준으로 정렬되어 있어, 게이트웨이는 다운로드한 바이트 배열에 대해
역직렬화(deserialize) 없이 곧바로 이진 탐색(binary search)을 수행할 수
있다. 30분 윈도우에 100만 건의 취소 기록이 몰려도 크기는 16MB에 불과하다.

데이터 갱신은 비동기 워커 프로세스가 담당한다. 워커는 데이터베이스를
스캔해 S3 청크를 업데이트하며, 여러 워커가 동시에 실행되어 고가용성을
확보한다. 동시 쓰기 충돌은 S3의 조건부 PUT을 이용한 낙관적 동시성
제어(optimistic concurrency control)와 ZooKeeper 기반 리더 선출로
최소화한다. 게이트웨이 측에서는 S3의 조건부 GET을 활용해 변경되지 않은
청크는 재다운로드하지 않는다. 그 결과 데이터베이스 읽기 레플리카는
중복성(redundancy) 목적의 2대로 줄었고, 워커는 초당 2,000건 이상의 취소
기록을 처리할 수 있게 되었으며, 데이터베이스 부하는 이제 쓰기 처리량에만
비례한다.

## 분석

### 문제의 본질은 "읽기 폭증"이지 "쓰기 부하"가 아니다

이 글의 핵심은 세션 취소 자체가 아니라, 취소 기록을 조회하는 패턴에 있다.
세션 취소는 상대적으로 드문 쓰기 이벤트지만, 그것을 확인하는 읽기는
초당 수십만 건에 달한다. 더 나쁜 것은 이 읽기가 균등하게 분산되지 않고
배포라는 특정 이벤트에 맞춰 순간적으로 집중된다는 점이다. 즉 이 문제는
평균 부하가 아니라 순간 최대 부하(peak load)의 문제이며, MySQL 읽기
레플리카를 늘리는 대응은 평균값 기준 사고방식으로 순간 폭증 문제를 풀려는
시도였기에 구조적으로 비효율적이었다. Canva가 S3로 옮긴 것은 단순한
캐시 계층 교체가 아니라, "동시 다발적 콜드 스타트(cold start) 읽기"라는
문제의 성격 자체를 재정의한 것에 가깝다.

### S3를 캐시로 쓰는 선택은 CDN적 사고의 확장이다

S3는 원래 객체 저장소이지 캐시가 아니다. 그런데도 이 설계가 성립하는
이유는, S3가 사실상 무제한에 가까운 동시 읽기 처리량과 조건부 GET(ETag
기반)이라는 HTTP 캐싱 프리미티브를 이미 갖추고 있기 때문이다. 이는
정적 자산을 CDN에 올려 배포 폭증을 흡수하는 전통적 웹 아키텍처 패턴을,
게이트웨이 간 내부 상태 공유라는 완전히 다른 문제에 그대로 적용한
것이다. Redis 같은 "정석적인" 분산 캐시를 버리고 객체 스토리지를
선택했다는 점은, 문제에 맞는 도구를 고를 때 카테고리 이름(캐시=Redis)이
아니라 실제 접근 패턴(쓰기는 드물고 읽기는 폭발적이며 최종 일관성으로
충분함)을 기준으로 삼아야 한다는 것을 보여준다.

### 16바이트 이진 포맷과 정렬은 "역직렬화 비용 제거"라는 같은 목적을 향한다

이 설계에서 이진 인코딩과 사전 정렬은 별개의 최적화가 아니라 하나의
전략이다. 데이터를 미리 정렬해두면 다운로드한 바이트 배열 자체를 인덱스로
쓸 수 있고, 이는 JSON 파싱이나 객체 역직렬화 같은 CPU 비용을 완전히
없앤다. 여기서 드러나는 원칙은, 극한의 처리량이 필요한 시스템에서는
"데이터를 어떻게 저장할까"보다 "데이터를 어떻게 조회할까"를 먼저 정하고
저장 형식을 그 조회 패턴에 맞춰 역설계해야 한다는 것이다. 이진 탐색이
가능하려면 정렬이 전제되어야 하고, 정렬된 상태를 유지하려면 쓰기 시점에
비용을 지불해야 한다 — 즉 이 설계는 읽기 비용을 쓰기 비용으로 의도적으로
전가한 것이며, 이는 읽기:쓰기 비율이 이 시스템처럼 극단적으로 기울어져
있을 때만 정당화된다.

### 리더 선출과 조건부 쓰기는 "느슨한 일관성을 허용하되 완전한 무질서는 막는다"는 절충이다

여러 워커가 동시에 S3 청크를 갱신할 수 있게 하면서도 ZooKeeper 리더
선출과 조건부 PUT을 함께 쓴 것은, 강한 일관성(strong consistency)을
포기하지 않으면서도 다중 워커로 가용성을 확보하려는 절충이다. 완전한
단일 쓰기자(single writer) 모델은 가용성이 떨어지고, 완전한 무제약
동시 쓰기는 데이터 충돌 위험이 있다. Canva는 "보통은 한 명의 리더가
쓰되, 장애 시 다른 워커가 조건부 쓰기로 안전하게 이어받는다"는 중간
지점을 택했다. 이는 분산 시스템에서 흔히 반복되는 패턴 — 가용성과
일관성 사이에서 완전한 양극단이 아니라 실패 시나리오별로 다른 보장
수준을 적용하는 설계 — 의 한 사례다.

## 비평

### "이론과 실제의 차이"라는 결론은 구체적 실패 사례 없이 신뢰를 요구한다

글은 마지막에 "이론과 실제 구현 간의 차이"가 중요했다고 말하지만, 정작
그 차이가 무엇이었는지 구체적으로 서술하지 않는다. 어떤 가정이 실제
운영 환경에서 깨졌는지, 어떤 예상치 못한 병목이 발견되었는지에 대한
사례가 없다면 이 문장은 실질적 정보가 아니라 수사적 마무리에 가깝다.
엔지니어링 블로그가 "우리는 검증했다"고 말할 때 정말 신뢰를 얻으려면,
검증 과정에서 무엇이 틀렸었는지를 보여줘야 한다. 이 글은 최종적으로
성공한 설계만 보여줄 뿐, 그 과정에서 폐기된 대안이나 겪은 실패를
구체적으로 다루지 않아 "선택 편향된 성공담"이라는 인상을 준다.

### Redis를 배제한 근거가 지나치게 압축되어 있다

글은 Redis 검토 후 "내구성 부족과 복잡성 증가"를 이유로 배제했다고만
언급한다. 그러나 Redis 클러스터도 AOF/RDB 영속성, 복제, Sentinel/Cluster
기반 장애조치를 통해 상당한 내구성을 확보할 수 있다. 왜 이런 표준적인
Redis 운영 방식이 Canva의 요구사항을 충족하지 못했는지, 혹은 단순히
새로운 운영 부담(별도 클러스터 관리, 스케일링 정책 등)을 피하고 싶었던
것인지가 불분명하다. 이 부분이 명확하지 않으면 "우리는 익숙한 대안보다
더 복잡한 커스텀 시스템(30분 청크, 이진 포맷, 리더 선출, 조건부 쓰기)을
직접 구축하는 것을 선택했다"는 결정이 실제로 더 단순했는지 판단하기
어렵다.

### 12시간 윈도우라는 설계 상수가 왜 정답인지 설명하지 않는다

세션 취소 확인 범위를 12시간으로 잡은 이유가 이 글에는 없다. 이는 "12시간
이상 지난 세션 취소 요청은 무시해도 된다"는 보안 가정을 내포하는데, 이
가정이 어떤 위협 모델을 기반으로 하는지가 설명되지 않는다. 예를 들어
장기 미접속 세션이나 오프라인 상태에서 탈취된 토큰이 12시간을 넘겨
재사용될 가능성은 없는지, 혹은 다른 보안 계층(토큰 만료 정책 등)이
이 위험을 별도로 상쇄하는지에 대한 언급이 전혀 없다. 성능 최적화의
근거는 상세히 설명하면서, 그 최적화가 딛고 선 보안 가정은 검증 없이
당연시하는 비대칭적 서술이다.

### 이 아키텍처가 성립하는 전제 조건이 일반화되어 제시된다

이 설계는 "취소는 드물고 조회는 폭발적이며, 몇 초에서 몇십 초의 지연은
허용 가능하다"는 특수한 접근 패턴 위에서만 성립한다. 만약 세션 취소가
즉시 반영되어야 하는 요구사항(예: 결제 시스템의 권한 회수)이었다면,
S3의 최종 일관성 기반 캐시 갱신 주기는 치명적인 보안 구멍이 될 수 있다.
글은 이 아키텍처를 마치 세션 관리 일반에 적용 가능한 모범 사례처럼
제시하지만, 실제로는 "몇십 초의 취소 반영 지연을 감수할 수 있는
서비스"라는 좁은 조건에서만 유효한 해법이다.

## 인사이트

### 이 설계는 "쓰기 증폭"을 "읽기 증폭 회피"로 맞바꾼 트레이드오프다

겉보기에 이 시스템은 순수하게 효율을 개선한 것처럼 보이지만, 실제로는
비용을 다른 곳으로 옮긴 것에 가깝다. 워커가 데이터베이스를 스캔하고
30분마다 S3 객체를 재생성하는 과정 자체가 새로운 쓰기 파이프라인이며,
이는 예전에는 없던 오퍼레이션이다. 배포 시 발생하던 순간적 읽기 폭증은
사라졌지만, 대신 상시적으로 돌아가는 워커 인프라, 조건부 쓰기 재시도
로직, 리더 선출 장애 처리 코드라는 새로운 운영 표면이 생겼다. 규모가
커질수록 조직은 "폭발적이지만 드문 부하"를 "낮지만 상시적인 복잡성"으로
바꾸는 결정을 반복하게 되는데, 이 트레이드오프가 항상 옳은 것은 아니다.
만약 배포 빈도가 낮은 조직이었다면 이 정도의 상시 인프라 투자는
과잉이었을 것이다. 이 글이 다루지 않는 진짜 질문은 "우리 조직의 배포
빈도와 트래픽 패턴에서 이 트레이드오프가 언제부터 정당화되는가"다.

### 이 패턴은 CRL(인증서 폐기 목록)과 구조적으로 동일한 문제다

세션 취소 확인은 사실 X.509 인증서 폐기 목록(CRL) 배포 문제와 근본적으로
같은 형태를 띤다. CRL도 "폐기는 드물지만 확인은 모든 TLS 핸드셰이크마다
필요하다"는 동일한 비대칭 구조를 가지며, 업계는 이를 해결하기 위해
OCSP(실시간 조회)에서 OCSP Stapling(캐시된 응답을 서버가 미리 첨부)으로,
나아가 짧은 수명의 인증서로 진화해왔다. Canva의 30분 청크 방식은 사실상
"OCSP Stapling의 세션 관리 버전"이다. 이 구조적 유사성이 흥미로운 이유는,
Canva 팀이 처음부터 PKI 업계의 CRL/OCSP 진화사를 참고했다면 Redis 검토
같은 중간 단계 없이 곧바로 이 해법에 도달했을 수도 있다는 점이다. 서로
다른 도메인(세션 관리 vs. 인증서 검증)이 동일한 "폐기 확인" 문제 구조를
공유한다는 사실은, 엔지니어링 문제를 도메인 명칭이 아니라 데이터 접근
패턴으로 분류하는 습관이 왜 유용한지를 보여준다.

### 이진 탐색으로의 회귀는 "제약이 오래된 도구를 최적해로 되돌린다"는 사례다

현대 백엔드 개발은 대체로 관계형 데이터베이스, 인덱스, ORM, 캐시
레이어라는 고수준 추상화 위에서 이루어진다. 그런데 Canva의 최종 해법은
정렬된 바이트 배열에 대한 이진 탐색이라는, 자료구조 교과서 1장에 나오는
가장 기초적인 알고리즘이다. 이는 퇴보가 아니라, 극한의 처리량 요구사항이
추상화 계층을 하나씩 벗겨내며 결국 하드웨어에 가장 가까운 원시적 해법을
다시 최적해로 만든 결과다. 이런 패턴은 이 사례에 국한되지 않는다 —
고빈도 거래 시스템, 게임 서버, 임베디드 시스템 등 극한의 지연시간
요구사항이 있는 곳에서는 반복적으로 "오래된 단순한 자료구조가 최신
고수준 도구를 이긴다"는 현상이 나타난다. 이는 소프트웨어 엔지니어링의
발전이 항상 "더 높은 추상화로의 일방향 진행"이 아니라, 요구사항의
극단성에 따라 추상화 사다리를 오르내리는 양방향 과정임을 시사한다.

### S3를 범용 조정(coordination) 계층으로 쓰는 흐름이 이 사례에서도 반복된다

최근 몇 년간 S3를 단순 저장소가 아니라 분산 시스템의 조정 도구로 쓰는
사례가 늘고 있다(예: S3 조건부 쓰기를 이용한 분산 락, Delta Lake/Iceberg
같은 테이블 포맷의 트랜잭션 로그). Canva의 조건부 PUT 기반 낙관적
동시성 제어도 이 흐름의 연장선에 있다. 이 현상이 시사하는 바는, 클라우드
오브젝트 스토리지가 제공하는 원시 프리미티브(조건부 쓰기, 강한 읽기 후
쓰기 일관성)가 충분히 강력해지면서, 과거에는 별도의 조정 서비스
(ZooKeeper, etcd, Redis)가 전담하던 역할의 일부를 저장 계층 자체가
흡수하고 있다는 것이다. 다만 이 사례에서도 ZooKeeper는 완전히
대체되지 않고 리더 선출에는 여전히 남아있다는 점이 흥미롭다 — 이는
S3의 조정 능력이 아직 "저비용 충돌 회피"까지는 확장되었지만 "합의
기반 리더십"까지는 대체하지 못했다는 현재의 경계선을 보여준다.
