# SDUI는 자기 책임으로 쓰라

원문: [Server Driven UI - DEV Community](https://dev.to/nishant_keshav/server-driven-ui-3l0p)

## 요약

Nishant Keshav가 2025년 7월 7일 dev.to에 발행한 6분 분량의 글이다.
태그는 programming, ui, backend, webdev이며 반응은 6개, 댓글은 0개다.

도입부는 농담으로 시작한다 — 서버 주도 UI는 백엔드에 저장된 CSS 파일이 아니라는 것이다.
전통적인 개발에서는 프런트엔드의 디자인이나 비즈니스 로직을 바꾸려면 전체를 다시 써야
하고, 결제 앱의 UI/UX를 바꾸려면 디자인과 비즈니스 로직의 구조 전체를 바꿔야 하며, 그것은
새 앱 업데이트를 내보내고 사용자가 업데이트하기를 바라는 일 — 보통 일어나지 않는 일 —
을 뜻한다.
SDUI는 UI 요소를 앱에 하드코딩하는 대신 UI 정의를 JSON이나 다른 형식으로 백엔드에서
내려보내고, 클라이언트 앱은 서버가 보낸 UI 구조를 읽어 표시하는 렌더러가 된다.

본문 중간은 상품 목록 화면을 예로 릴리스 주기를 설명한다.
목록 화면이 사용자에게 표시될 때 앱은 서버에서 상품 목록을 가져오고, 그 데이터가 개발자가
만든 UI와 결합되어 리스트 뷰로 변환된다.
여기에 별점을 각 행에 추가하고 세일 상품에 특별한 처리를 하려면 표현 로직이 앱에 들어
있으므로 전체 릴리스 주기를 다시 돌아야 한다 — 개발자가 코드를 쓰고, 테스터가 검토하고,
새 버전을 스토어에 제출하고, Apple/Google이 심사해 승인하고, 사용자가 새 버전으로
업데이트하는 다섯 단계다.
iOS와 안드로이드를 모두 지원하는 앱이라면 이 주기를 두 번 돌아야 하고 보통 플랫폼별로 다른
개발자가 필요하며, 변경이 사용자 기기에 도달할 때쯤에는 이미 추가 변경 — 예컨대 추천
상품을 가로 스크롤 컨테이너로 상단에 배치하는 일 — 을 하고 싶어진다.
개발과 테스트와 두 플랫폼의 승인 대기를 합치면 이런 단순한 변경 하나가 스토어에 도달하는
데 몇 주에서 몇 달이 걸리며, 스토어에 올라간 뒤에도 사용자가 업데이트하기를 기다려야
한다 — 어떤 사용자는 바로 업데이트하고 어떤 사용자는 미루며 어떤 사용자는 아예 하지
않는다.

해법으로 제시되는 것은 서버의 JSON 응답에 따라 렌더링되도록 웹·앱 디자인을 작성하고 그
디자인을 JSON 형식으로 서버에 저장하는 것이다.
이 JSON 응답이 버튼, 입력 필드, 라벨, 레이아웃 컨테이너 같은 UI의 구조와 스타일과 로직을
정의하며, 프런트엔드 앱은 그것을 파싱해 레이아웃을 렌더링한다.
그러면 상품 목록을 가져오는 대신 앱은 리스트 뷰를 가져오고, 그 안에 행 뷰들이 있고, 각 행에
간격·정렬·색·텍스트 정보를 담은 텍스트 뷰와 이미지 뷰가 들어 있다.
앱이 서버 응답을 렌더링한 결과는 전통적 방식으로 만든 것과 동일하며, 몇 주에서 몇 달이
걸리던 업데이트를 며칠이나 몇 시간 만에 할 수 있고 iOS와 안드로이드에 일관되게 적용되며
모든 사용자가 같은 시점에 같은 버전을 본다.

이득은 네 가지로 정리된다 — 사용자에게 앱 업데이트를 강요하지 않고 UI를 갱신하는 것,
사용자별로 UI를 개인화하는 것, 새 흐름이나 기능을 빠르게 실험하는 것(A/B 테스트), 공유
스키마로 안드로이드·iOS·웹의 UI 로직을 통일하는 것이다.
전통적 네이티브 릴리스의 문제도 네 가지로 대응된다 — 느린 갱신 주기, 느린 사용자 채택,
플랫폼별 코드로 인한 이중 작업과 별도 코드베이스, 느린 피드백 루프다.

글의 무게는 그다음 단점 목록에 있다.
백엔드 복잡도 증가 — 백엔드가 UI 로직과 레이아웃 생성과 동적 렌더링 규칙까지 다뤄야 하며,
데이터 제공자가 아니라 UI 컨트롤러가 되고, 그 결과 프런트엔드와 백엔드 로직이 강하게
결합되어 빠르게 지저분해질 수 있다.
리치 UI 개발 지연 — 설정 화면처럼 정적이거나 폼 기반인 UI에는 훌륭하지만 상호작용이 많고
애니메이션이 있고 맞춤형인 컴포넌트를 만드는 것은 어려워지거나 아예 불가능해지며,
React나 Vue 같은 프런트엔드 프레임워크의 강력한 컴포넌트 시스템의 이점을 잃는다.
디버깅 난이도 — UI 버그가 잘못된 JSON이나 잘못된 서버 설정에서 올 때 원인 파악이 어렵고,
로그가 근본 원인을 분명히 보여주지 않으며, 전통적 UI에서처럼 컴포넌트 트리에 직접 접근할
수 없다.
성능 오버헤드 — 왕복이 늘어나 앱이 먼저 UI 정의를 요청하고 그다음 데이터를 가져오며,
UI JSON과 데이터가 합쳐져 페이로드가 커지고 최적화하지 않으면 초기 로드가 무거워지므로
공격적인 캐싱과 폴백 전략이 필요할 수 있다.
IDE·도구 이점 상실 — 전통적 UI 개발에서는 타입 안전성과 코드 완성과 미리보기와 강력한
디버거를 얻지만, JSON 기반 렌더링은 커스텀 도구를 만들지 않는 한 이 이점들을 잃는다.
팀의 학습 곡선 — 백엔드 팀이 UI 구조와 렌더링 로직을 이해해야 한다.
디자인 제약 — 픽셀 완벽한 디자인이나 드래그 앤 드롭, 고급 차트 같은 복잡한 UI 동작은
SDUI로 달성하기 어려워 하드코딩된 네이티브 UI로 되돌아가야 하는 경우가 많다.

결론은 두 문장이다.
SDUI는 런타임의 유연성을 코드베이스와 성능과 개발 경험의 복잡도와 맞바꾸며, CMS 기반
페이지와 폼과 온보딩 흐름에는 훌륭하지만 애니메이션과 풍부한 상호작용과 빠른 프런트엔드
반복에는 나쁘다.
저자의 견해는 대문자로 적혀 있다 — “USE AT YOUR OWN RISK”.
끝에는 PhonePe가 LiquidUI로 SDUI를 도입한 두 편의 글(“그들의 구현은 미쳤다”는 평과 함께)과
Airbnb, Swiggy의 기술 블로그 링크가 참고로 붙는다.

## 분석

### 이득 넷 대 비용 일곱이라는 배분이 결론을 미리 정한다

이 글의 구조에서 눈에 띄는 것은 분량의 배분이다.
이득은 네 항목의 한 줄 목록으로 처리되고, 단점은 일곱 항목이 각각 소제목과 두세 개의 하위
불릿으로 전개된다.
같은 주제의 대부분의 소개 글이 반대 비율 — 이득을 길게, 비용을 마무리 단락에 — 로 쓰인다는
점에서 이 배분 자체가 이 글의 성격이다.

그래서 마지막의 “USE AT YOUR OWN RISK”는 갑작스러운 선언이 아니라 구조의 자연스러운
귀결이다.
독자는 일곱 개의 비용을 차례로 읽은 뒤 그 문장을 만나므로, 결론이 근거보다 앞서 나온다는
느낌을 받지 않는다.
이 점에서 이 글은 SDUI를 소개하는 글이 아니라 SDUI 도입에 반대 의견을 정리한 글로 읽는
편이 정확하다.

값어치도 거기에 있다.
이 글은 새로운 사례나 측정치를 제공하지 않지만, 비용 목록의 완성도는 같은 주제의 옹호
글들이 대체로 갖추지 못한 것이다.
특히 “커스텀 도구를 만들지 않는 한 타입 안전성과 코드 완성과 미리보기와 디버거를 잃는다”는
항목은 다른 곳에서 자주 생략된다.

### 일곱 개의 비용 중 사용자에게 닿는 것은 하나뿐이다

목록을 다시 읽으면 항목들의 성격이 한쪽으로 몰려 있다.
백엔드 복잡도, 리치 UI 개발 지연, 디버깅 난이도, IDE 이점 상실, 학습 곡선, 디자인 제약 —
여섯 개가 만드는 사람의 경험에 관한 것이고, 사용자에게 직접 도달하는 것은 성능 오버헤드
하나다.

이 편향은 우연이 아니라 이 논쟁의 실제 성격을 보여준다.
SDUI를 둘러싼 대립은 “사용자에게 더 좋은가”가 아니라 “누가 어떤 불편을 감당하는가”에 관한
것이며, 그래서 옹호 측은 조직의 속도를 근거로 들고 반대 측은 개발 경험을 근거로 든다.
두 목록은 서로를 반박하지 않고 서로 다른 것을 센다.

같은 주제를 옹호하는 글이 이해관계자별로 이득을 나열해 여섯 부서의 편익을 만들어 내는
구성을 쓴다면[^ref-evil], 이 글은 그 반대편에서 개발자가 잃는 것을 일곱 개로 나눈다.
두 글을 나란히 놓으면 SDUI 논쟁의 지형이 드러난다 — 이득은 조직 프로세스에, 비용은 개발
경험에 계상되며, 사용자 쪽 계정은 양쪽 모두 거의 비어 있다.

### 타입 안전성 상실이 이 목록에서 가장 깊은 항목이다

일곱 항목 중 여섯은 정도의 문제다 — 백엔드가 더 복잡해지고, 디버깅이 더 어려워지고, 학습이
더 필요하다.
반면 IDE·도구 이점 상실은 종류의 문제다.
JSON으로 UI를 기술하는 순간 컴파일 타임에 잡히던 오류 범주가 런타임으로 이동하며, 이는
불편이 아니라 검증 시점의 이동이다.

이 항목이 깊은 이유는 되돌리기 어렵다는 점에 있다.
백엔드 복잡도는 코드를 정리해 줄일 수 있고 학습 곡선은 시간이 해결하지만, 타입 검증은
스키마 언어와 코드 생성이라는 별도의 장치를 만들지 않으면 회복되지 않는다.
저자가 “커스텀 도구를 만들지 않는 한”이라는 조건절을 붙인 것이 정확히 이 지점이며, 그
조건절이 사실 SDUI 도입의 진짜 비용 항목이다.

맥락을 넓히면 방향의 문제도 보인다.
모바일 생태계는 Objective-C에서 Swift로, Java에서 Kotlin으로, JavaScript에서 TypeScript로
정적 검증을 강화하는 쪽으로 20년을 움직였다.
SDUI는 UI 구성이라는 영역에서 그 흐름을 반대로 돌리며, 그래서 저자가 관측한 “모바일
개발자의 저항”은 취향이 아니라 그 20년의 투자를 지키려는 반응으로 읽을 수 있다.

### 적합 영역의 경계가 이 글에서 유일하게 실행 가능한 결론이다

결론 문단의 조건부 권고 — CMS 기반 페이지, 폼, 온보딩 흐름에는 좋고 애니메이션과 풍부한
상호작용에는 나쁘다 — 는 이 글에서 바로 쓸 수 있는 유일한 판단 재료다.
그리고 그 경계는 임의로 그어진 것이 아니다.

설정 화면이 잘 맞는 이유를 풀어 보면 규칙이 나온다.
상태가 적고, 가능한 조합이 유한하고, 픽셀 정밀도 요구가 낮고, 상호작용이 탭과 토글로
끝난다.
반대로 드래그 앤 드롭이 맞지 않는 이유는 상태가 프레임 단위로 바뀌고 그 상태가 손가락의
위치처럼 클라이언트만 아는 것이기 때문이다.

이 경계는 뒤의 인사이트에서 더 일반적인 규칙으로 다시 정리할 만한 재료이며, 저자가 그것을
규칙으로 승격시키지 않고 예시 목록으로 둔 것이 이 글의 아쉬운 지점이다.

## 비평

### 중간 절의 문장들이 앞선 제3자 설명과 동일한데 출처 표시가 없다

이 글에서 가장 먼저 확인해야 할 문제는 저작의 경계다.
도입부와 결론은 굵은 글씨와 이탤릭을 남용하는 특유의 문체로 쓰여 있는데, 중간의 릴리스
주기 설명 절은 문체가 급격히 달라져 정제된 설명문이 된다.

그 절의 문장들은 다른 곳에도 똑같이 존재한다.
“Server-driven UI (SDUI) is an emerging technique used by companies like Airbnb and Lyft that
leverage the server to build the user interfaces of their mobile apps”와 “Some will update
right away, some will take their time, and some won't update at all”은 SDUI 도구를 만들던
Judo의 설명 글을 비롯한 여러 문서에서 같은 문장으로 확인된다.
Judo의 제품과 관련 콘텐츠가 2021~2022년에 알려진 것을 감안하면 이 글(2025년 7월)보다
앞선 것으로 보이지만, 어느 쪽이 먼저인지와 무관하게 동일한 문장이 출처 표시 없이 실려
있다는 사실은 남는다.
상품 목록 예시와 다섯 단계 릴리스 주기, “상품 목록을 가져오는 대신 리스트 뷰를 가져온다”는
서술도 같은 계열의 설명을 따른다.
이 글은 말미에 PhonePe와 Airbnb, Swiggy 링크를 붙이지만 그것은 “그들이 어떻게 도입했는지”의
참고이고, 본문 문장의 출처로 제시되지는 않는다.

이것을 예절 문제로만 볼 수 없는 이유는 독자의 검증 경로가 끊긴다는 점이다.
설명문에서 출처가 중요한 이유는 공적을 나누기 위해서가 아니라, 읽는 사람이 원 문맥으로
돌아가 전제와 한계를 확인할 수 있어야 하기 때문이다.
특히 이 글의 중간 절에는 “몇 주에서 몇 달”이나 “며칠이나 몇 시간” 같은 시간 추정이 들어
있는데, 그것이 어떤 조직의 어떤 앱에서 나온 수치인지 확인할 길이 없다.

문체의 단절이 만드는 두 번째 문제는 어느 진술이 저자의 경험인지 알 수 없다는 것이다.
마지막 “USE AT YOUR OWN RISK”는 강한 1인칭 판단인데, 그 판단을 지탱하는 본문의 어느 부분이
저자가 직접 겪은 것인지 구별되지 않는다.
경험에 기댄 결론과 인용에 기댄 서술이 같은 목소리로 섞이면, 결론의 신뢰도는 그중 약한 쪽을
따른다.

### 이득과 비용이 서로 다른 단위로 계산되어 비교가 성립하지 않는다

결론은 “런타임의 유연성을 코드베이스와 성능과 개발 경험의 복잡도와 맞바꾼다”고 단정한다.
그런데 앞의 두 목록은 서로 비교할 수 없는 단위로 되어 있다.

이득 쪽은 조직 프로세스의 시간이다 — 릴리스 주기, 사용자 채택 속도, 실험 반복 횟수,
플랫폼 간 일관성.
비용 쪽은 코드와 도구의 상태다 — 결합도, 디버깅 난이도, 타입 안전성, 학습 필요량.
두 목록 중 어느 쪽에도 숫자가 없고, 유일하게 등장하는 수치(“몇 주에서 몇 달”, “며칠이나
몇 시간”)는 앞서 본 대로 출처가 불분명한 인용이다.

그래서 이 글은 무엇을 얼마나 맞바꾸는지 말하지 못한 상태로 맞바꿈이라고 결론짓는다.
교환을 주장하려면 최소한 한쪽 축에 규모가 필요하다 — 화면 몇 개부터 백엔드 복잡도가
회수되는지, 실험을 한 달에 몇 번 돌리는 조직에서 이득이 비용을 넘는지.
그 임계가 없으면 목록은 의사결정 도구가 아니라 우려의 목록으로 남는다.

### “자기 책임으로”라는 결론은 이미 갖춘 판단 재료를 포기한다

저자는 일곱 개의 비용을 열거하고, 나아가 적합·부적합 영역까지 구분해 제시했다.
그 두 가지를 갖췄다면 결론은 조건으로 쓸 수 있었다 — 이런 조건에서는 도입하고 저런 조건에서는
하지 말라는 형태로.
그런데 마지막 한 줄은 판단을 독자에게 되돌려 준다.

이 회피가 아쉬운 이유는 이 글의 강점이 정확히 그 판단을 할 재료를 모았다는 데 있기 때문이다.
비용 목록의 완성도가 이 글을 같은 주제의 다른 개요들과 구별해 주는데, 마지막 문장은 그
완성도를 결론으로 전환하지 않는다.
결과적으로 독자는 걱정거리 일곱 개를 얻고 결정 기준은 얻지 못한다.

더 실용적인 결론의 형태는 어렵지 않게 상상할 수 있다.
화면 수와 실험 빈도와 팀 구성을 축으로 하는 도입 임계, 또는 “먼저 온보딩 흐름 하나만
SDUI로 전환해 스키마 버저닝 비용을 측정하라”는 식의 점진 경로가 그것이다.
후자는 이 글이 인정한 위험을 실제로 관리하는 방법이며, “자기 책임으로”보다 훨씬 적은 위험을
독자에게 남긴다.

### 성능 진단이 특정 구현을 SDUI 전체의 속성으로 일반화한다

성능 항목의 첫 불릿은 “왕복이 늘어난다 — 먼저 앱이 UI 정의를 요청하고, 그다음 데이터를
가져온다”고 적는다.
이 서술은 UI 정의와 데이터를 분리해 두 번 요청하는 구현에만 해당한다.

Airbnb가 공개한 방식은 그렇지 않다.
Ghost Platform에서 섹션은 “이미 번역되고 지역화되고 서식이 적용된, 표시할 정확한 데이터”를
담는 가장 기본적인 구성 단위이고 화면은 그 섹션들이 어디에 놓일지를 기술하므로, 구성과
데이터가 한 응답에 함께 온다.
왕복은 한 번이며 오히려 클라이언트가 여러 엔드포인트를 조합하던 기존 방식보다 줄어드는
경우도 있다.
Lyft도 BFF가 상위 서비스에서 데이터를 가져와 병합한 뒤 그 데이터의 뷰 표현을 클라이언트에
돌려주는 구조로 설명한다.
즉 왕복 증가는 SDUI의 본질적 비용이 아니라 설계 선택의 결과이며, 그것을 구조적 단점으로
제시하면 독자는 회피 가능한 비용을 필연적인 것으로 오해한다.

반대로 이 글은 본질에 더 가까운 성능 비용을 놓친다.
UI 정의가 응답에 실리면 그 응답은 사용자별·실험군별로 달라지므로 캐시 키가 폭발하고 CDN
캐싱이 어려워진다.
그리고 구버전 클라이언트가 새 컴포넌트 타입을 이해하지 못하는 상황을 처리하려면 서버가
클라이언트 버전별로 다른 응답을 만들어야 하는데, 이것이 “버저닝”이라는 이름으로 다른 글들이
악몽이라 부르는 비용이다.
페이로드 크기와 왕복 횟수는 최적화로 줄일 수 있지만, 이 두 항목은 구조에서 나오므로 줄어들지
않는다.

## 인사이트

### 성숙한 SDUI는 JSON을 자유롭게 쓰는 방향이 아니라 다시 타입으로 묶는 방향으로 간다

저자가 조건절로 처리한 “커스텀 도구를 만들지 않는 한”은 사실 이 패턴의 성숙 경로를 가리킨다.
UI를 JSON으로 옮기면 컴파일 타임 검증을 잃고, 잃은 검증은 어디선가 복원해야 하며, 실제
사례들이 복원하는 방식은 모두 같다 — 스키마를 먼저 정의하고 그 스키마에서 클라이언트 타입을
생성하는 것이다.

Lyft가 Protocol Buffers를 쓰고 Airbnb가 GraphQL 스키마를 축으로 삼는 것이 그 예이며, 두
선택 모두 “서버가 임의의 JSON을 보낼 수 있다”는 자유를 스스로 포기하는 결정이다.
자유를 포기한 대가로 얻는 것은 클라이언트 렌더러가 모르는 타입을 받는 사고를 컴파일
단계에서 줄이는 것이고, 이는 SDUI가 해결하려던 문제(배포 게이트)와는 아무 관련이 없는
별도의 문제다.

그래서 이 패턴을 도입하는 조직이 실제로 만들게 되는 것은 렌더러가 아니라 타입 파이프라인이다.
스키마 정의, 코드 생성, 버전 호환 규칙, 미리보기 도구, 그리고 스키마 변경의 리뷰 절차.
저자가 일곱 번째로 든 “디자인 제약”이나 여섯 번째의 “학습 곡선”보다 이 파이프라인의 유지비가
장기 비용의 대부분을 차지하며, 그것이 이 글에서도 다른 소개 글에서도 항목으로 잡히지 않는
이유는 도입 초기에는 존재하지 않기 때문이다.

### 서버가 정할 수 있는 것과 클라이언트만 아는 것 사이에 경계가 있다

적합·부적합 목록을 규칙으로 바꾸면 이렇게 정리된다 — 서버가 정할 수 있는 것은 “무엇을
보여줄지”이고, 클라이언트만 아는 것은 “지금 사용자의 손가락이 어디 있는지”다.

이 경계로 목록을 다시 읽으면 예시들이 모두 설명된다.
설정 화면과 폼과 온보딩은 무엇을 보여줄지가 전부이므로 서버가 정할 수 있다.
드래그 앤 드롭과 애니메이션과 고급 차트의 상호작용은 프레임 단위의 입력 상태에 의존하므로
서버가 알 수 없다.
픽셀 완벽한 디자인이 어려운 이유도 같은 축에 있다 — 실제 화면 밀도와 폰트 확대 설정과
안전 영역은 기기가 아는 정보다.

이 경계가 실무에서 유용한 이유는 프레임워크 평가 기준이 되기 때문이다.
경계를 지키는 프레임워크는 서버 스키마에 조건 분기와 계산식과 이벤트 핸들러를 넣지 않고,
경계를 넘으려는 프레임워크는 JSON 안에 작은 프로그래밍 언어를 만들기 시작한다.
후자에 도달한 순간 그 JSON은 데이터가 아니라 인터프리터의 입력이 되고, 디버깅 난이도와
버저닝 비용은 저자가 우려한 수준을 훨씬 넘어선다.
평가할 때 물어야 할 질문은 “무엇을 표현할 수 있는가”가 아니라 “무엇을 표현할 수 없도록
막아 두었는가”다.

### 도구 이점의 상실은 학습 곡선이 아니라 온콜 경계의 재정의로 나타난다

저자는 “백엔드 팀이 UI 구조와 렌더링 로직을 이해해야 한다”를 학습 곡선 항목에 넣었다.
그런데 이 항목의 실제 무게는 학습이 아니라 책임의 이동에 있다.

화면이 깨졌을 때 호출되는 사람이 바뀐다.
전통 구조에서 레이아웃 버그는 클라이언트 팀의 것이고, SDUI 구조에서 같은 증상은 서버가 보낸
조합의 문제일 수 있다.
그 판별을 하려면 서버 팀이 렌더링 결과를 볼 수 있어야 하는데, 대부분의 조직은 그 도구를
갖추지 않은 상태로 도입을 시작한다.

그래서 SDUI 도입은 기술 변경이 아니라 조직 개편으로 계획되어야 한다.
UI 조합의 소유자가 누구인지, 그 소유자가 배포 전에 결과를 확인할 방법이 무엇인지, 사용자
신고가 들어왔을 때 1차 대응이 어느 팀인지가 스키마 설계보다 먼저 정해져야 한다.
그것을 정하지 않고 기술만 들이면 두 팀이 서로를 가리키는 상태가 되고, 그 상태는 저자가
네 번째로 든 디버깅 난이도를 조직 차원에서 몇 배로 키운다.

### 이 장르에 축적되는 것은 사례가 아니라 요약의 재요약이다

이 글의 반응 6개, 댓글 0개라는 수치는 글의 품질에 대한 평가라기보다 이 장르의 상태를
보여주는 신호다.
SDUI 소개 글은 대량으로 생산되지만 그 아래에서 논쟁이 벌어지지 않으며, 앞서 확인한 대로
서로의 문장을 재사용하며 순환한다.

이 순환의 결과는 정보 지형의 왜곡이다.
같은 개요가 수십 번 다시 쓰이는 동안 실무자가 실제로 필요한 종류의 글은 드물게 남는다 —
도입했다가 되돌린 조직의 이유, 스키마 버저닝이 무너진 구체적 지점, 접근성 회귀가 발견된
경위, 캐시 전략을 다시 설계해야 했던 사연.
Airbnb와 PhonePe와 Swiggy의 글이 반복 인용되는 것도 같은 이유다 — 그것 말고는 인용할
1차 자료가 별로 없다.

이 공백은 SDUI에 국한되지 않고 최근 아키텍처 담론 전반의 특징이다.
성공 사례는 회사 블로그로 공개되고 실패 사례는 공개되지 않으므로, 어떤 패턴이든 문헌상으로는
성공률이 100%로 보인다.
그래서 이런 목록형 개요를 읽을 때 실제로 얻어야 하는 것은 항목 자체가 아니라 “이 항목들이
어떤 규모에서 문제가 되었는지”이고, 그 정보가 없는 개요는 도입 결정에 쓸 수 없다.
이 글의 “USE AT YOUR OWN RISK”는 그 공백을 정직하게 인정한 표현으로도 읽히지만, 인정과
안내는 다른 일이다.
