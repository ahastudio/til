# KRP 4년: 구조는 미리 변하지 않고 이유가 생길 때만 변했다

원문: [PyCon Korea 2026 CFP - 파이썬 소프트웨어의 나이테 - 김승호 - Google Slides](https://docs.google.com/presentation/d/1BJDF2zzAHmAS2N1kB8gP5M8-gxkFbLTnXn7nZYsLtfI/view)

## 요약

PyCon Korea 2026 CFP 자료이며 64쪽이다.
발표자는 김승호(Alan Kim, `raccoony`)로 당근마켓 SRE 클라우드파트에 있고
클라우드·인프라·프로그래밍을 다루는 44bits를 팟캐스트와 블로그와 유튜브로 운영한다.
제목은 “파이썬 소프트웨어의 나이테 / The tree rings of Python software”이고
부제가 범위를 정한다 — 한 파이썬 시스템의 4년을 읽어 보자는 것이다.

발표 목적을 네 개의 질문으로 세운다.
코드 구조는 왜 변할까, 변할 거라면 왜 미리 변하지 않았을까,
변화에서 오는 장단점은 무엇일까, 그리고
AI가 없던 시절에 프로젝트는 어떻게 자라날까다.
각 장은 같은 틀을 따른다 — 시퀀스 다이어그램, 불편했던 점, 폴더 구조,
코드 비교, 이 시기의 장단점 순서다.

대상은 KRP(Karrot Resource Provider)다.
사내 개발자 플랫폼의 클라우드 리소스를 담당하는 백엔드이며,
개발자가 직접 클라우드 리소스를 만들고 고치고 지울 수 있게 하면서
회사 정책(태그, 이름 규칙, 서브넷, 보안그룹 등)이 적용되게 한다.
프로젝트 규모는 2022년 7월 시작에 커밋 3,542개, PR 1,591개, 기여자 21명이고
상위 세 명이 전체 커밋의 78%를 차지한다.

코드 규모를 오픈소스 프로젝트들과 나란히 놓는다.

| 프로젝트 | 라인 수 | 테스트 비율 | 커버리지 |
| -------- | ------- | ----------- | -------- |
| KRP      | 71,465  | 35%         | 71%      |
| Celery   | 101,413 | 53%         | 88%      |
| FastAPI  | 112,887 | 70%         | 100%     |
| Django   | 524,942 | 69%         | ?        |

본문은 구조가 바뀐 일곱 순간을 시간순으로 따라간다.

| 시점          | 변화                     | 자료가 적은 방아쇠                          |
| ------------- | ------------------------ | ------------------------------------------- |
| 2022. 07. 15. | 첫 API `detail_redis`    | 없음 — `api/api_v1/redis.py` 한 파일        |
| 2022. 07. 22. | `providers/` 추가        | API가 AWS 호출을 직접 들고 있음             |
| 2023. 01.     | Client 미리 생성         | 4리전(KR·JP·CA·GB) × 2환경 순회가 느림      |
| 2023. 02.     | `services/` 추가         | API 시그니처에 클라이언트가 여러 개 붙음    |
| 2023. 08.     | DB 도입                  | 플랫폼의 목록 읽기 속도, 자원 묶음 관리     |
| 2023. 07.     | BackgroundTasks → Celery | 배포 주기와 재실행 고민, 대기열 가시성 부재 |
| 2025. 04.     | 서비스 공통 로직 추출    | 스무 개 넘는 서비스에서 로직이 파편화       |

각 단계의 장단점이 함께 적혀 있다.
첫 API의 장점은 파일 하나에서 전체 흐름이 보이고 고칠 곳이 한 군데라는 것이었다.
Provider를 나누면 API가 비즈니스 로직을 몰라도 되고
`RedisClient`만 모킹하면 AWS 연결 없이 테스트할 수 있지만,
API 레이어에서 어느 계정을 쓰는지 알 수 없고
작동 방식을 파악하려면 파일을 두 개 열어야 하며 배포 후 첫 요청이 느려진다.
Client를 미리 만들어 두면 유닛테스트가 빨라지고 전체 순회가 빨라지는 대신
`redis_client`라는 이름만으로는 클라이언트인지 생성 함수인지 헷갈리고
서버 시작이 느려진다.
Service 레이어는 HTTP 없이 로직을 테스트할 수 있고 규칙을 한 파일에서 관리하게 하지만,
요청 하나에 볼 파일이 셋이 되고
슬랙 알림이 redis 서비스의 일인지 모호해지며
service의 예외와 api의 예외가 쌍으로 늘어난다.
DB 도입은 목록 읽기를 빠르게 하고 여러 자원을 묶어 다루게 하고
ARN 대신 KRP ID로 조회할 길을 열지만,
DB와 AWS 중 어디가 진짜인지 묻게 만들고 —
KRP는 AWS를 원천으로 정했다 —
AWS가 정상이어도 DB가 문제면 시스템이 죽는다.
Celery 전환은 배포 주기와 재실행 고민을 없애고 대기열을 보이게 하고
실패 알림 경로를 만드는 대신 응답 코드의 뜻을 바꾸고(201이 생성 완료에서 생성 요청 접수로)
worker 관련 코드를 복잡하게 만든다.
공통 로직 추출은 KRP의 규칙 자체를 코드로 관리하게 하고
서비스를 추가할 때 빠뜨리는 항목을 없애고 새 규칙을 한 곳에만 넣게 하는 대신
신규 입사자의 온보딩 시간을 늘리고 아직 다 옮기지 못한 코드를 남긴다.

구현의 형태도 코드로 제시된다.
`core/loaders.py`가 `{region: {stage: {service: ClientInstance}}}` 맵을 미리 만들고
`dependencies/`가 그것을 뷰에 꽂아 준다.
`services/redis.py`의 `_populate_create_request`가 이름 규칙과 태그 규칙을 적용하며
`f'{env}-{project_name}-{purpose}-redis'` 형태의 ID와
`Engine`·`krp_group`·`Name`·`Environment` 태그를 붙인다.
DB 쪽은 `models/`와 `controllers/`로 나뉘고
`functools.partial`로 `get_or_create`를 리소스별로 특화한다.
Celery 전환 뒤에는 `BaseKrpService.task()` 데코레이터가
서비스 메서드를 태스크 레지스트리에 등록하고
`worker/app.py`의 `make_krp_service_to_celery_task`가 그것을 Celery 태스크로 감싼다.
마지막 단계에서는 `BaseKrpServiceEnhanced`가 DB 세션과 레코드 생성,
이벤트 기록, Celery 태스크 등록, 진행 중 자원 접근 차단을 맡고
`RedisService`·`S3Service`·`GcsService`는 `on_create`·`on_retrieve`·`on_delete`만 구현한다.

최종 비교는 첫 구조 — `backend/api/api_v1/redis.py` 하나 — 와
최종 구조 — `api/`, `core/`, `services/`, `controllers/`,
`models/`, `providers/`, `worker/` — 를 나란히 놓는다.
4년 회고는 네 줄이다.
너무 미리 변하지 않아서 속도를 유지할 수 있었다는 것,
명확한 이유가 있을 때만 변경해서 재미와 성과를 모두 챙겼다는 것,
코드 흐름을 파악하기가 점점 어려워졌다는 것,
그리고 리팩터링이 덜 끝난 코드가 늘어났다는 것 —
마지막 항목에 “이제 AI에게 시키면 되니까 미루지 말기”가 붙는다.

자료 자체에 대해 두 가지를 적어 둔다.
각 장의 시퀀스 다이어그램은 이미지여서 텍스트로 추출되지 않는다.
그리고 시점 라벨 중 두 개가 서로 맞지 않는다 —
DB 도입이 2023년 8월인데 다음 장인 Celery 전환이 2023년 7월로 앞서고,
공통 로직 추출은 2025년 4월인데 라벨이 “8개월 후”다.

## 분석

### 단계마다 장단점을 병기한 구성이 이 자료의 형식적 기여다

아키텍처 회고의 흔한 형태는 최종 구조를 설명하고 그것이 왜 옳은지 정당화하는 것이다.
이 자료는 일곱 단계마다 ➕와 ➖를 함께 적고, ➖를 지운 흔적이 없다.
그 결과 각 결정이 승리가 아니라 거래로 남는다.

➖의 내용이 반복된다는 점이 더 중요하다.
Provider 단계에서 “파일을 두 개 열어야 함”이 나오고
괄호로 “레이어 나눌 때마다 늘어남”이 붙는다.
Service 단계에서 “요청 하나에 대해 살펴볼 파일이 세 개”가 되고,
마지막 회고에서 “코드 흐름을 파악하기가 점점 어려워짐”으로 총계가 적힌다.
첫 단계의 ➕이 “파일 하나 안에서 전체 흐름이 보임”이었으므로,
일곱 고리의 서사는 같은 자산을 계속 팔아 온 이야기로 읽힌다.

이 구성이 독자에게 주는 것은 결론이 아니라 가격표다.
레이어를 나누면 테스트가 쉬워진다는 주장은 어디에나 있는데,
그 대가가 무엇이고 언제 청구되는지를 같은 지면에 적어 둔 자료는 드물다.
[계층 아키텍처를 정적으로 설명하는 자료](layered-architecture.md)가
관심사의 분리라는 이득을 말하는 자리에
이 자료는 열람 지점의 증가라는 비용을 나란히 놓는다.

### 변화의 방아쇠가 전부 측정 가능한 불편이고 원칙이 아니다

일곱 단계의 이유를 모아 보면 공통 형식이 있다.
Provider는 API가 AWS 호출을 직접 들고 있어서,
Client 사전 생성은 4리전 2환경을 순회할 때 느려서,
Service는 API 시그니처에 클라이언트가 두 개 붙어서,
DB는 플랫폼의 목록 읽기가 느려서,
Celery는 배포 주기와 재실행을 신경 써야 해서,
공통 로직 추출은 서비스가 스무 개를 넘어서다.

전부 증상이고, 대부분 숫자로 확인되는 증상이다.
“레이어가 없으니 결합도가 높다” 같은 문장은 하나도 없다.
이 목록이 발표 목적의 두 번째 질문 — 변할 거라면 왜 미리 변하지 않았을까 — 에 대한
답의 형식을 정한다.
미리 변할 이유가 없었기 때문이며, 이유는 원칙이 아니라 증상으로만 인정됐다.

날짜가 그 원칙의 결과를 보여 준다.
첫 API에서 Provider까지 열흘, 그다음 6개월, 1개월, 6개월,
그리고 마지막 단계까지 상당한 공백이다.
간격이 불규칙한 것 자체가 논지의 증거다 —
일정에 따라 리팩터링한 것이 아니라 증상이 나타날 때 움직였다는 뜻이다.
[지루한 기술을 선택하라는 논의](choose-boring-technology.md)가
혁신 토큰이라는 비유로 같은 절제를 말하는데,
이 자료는 그 절제를 4년간의 날짜로 기록해 두었다.

### 레이어 이름은 표준 어휘인데 도입 순서가 교과서와 반대다

최종 폴더 구조를 이름만 보면 익숙하다 —
`api`, `services`, `controllers`, `models`, `providers`, `worker`다.
그런데 생긴 순서가 통상적인 설계 순서와 다르다.
`providers`가 두 번째로 생기고 `services`가 그로부터 7개월 뒤에 온다.

교과서적 계층 설계는 도메인을 중심에 두고 인프라를 바깥에 배치한다.
설계를 먼저 하면 서비스 레이어가 먼저 존재하고,
어댑터는 그 서비스가 필요로 하는 인터페이스를 만족시키기 위해 나중에 붙는다.
KRP는 반대로 인프라 어댑터가 먼저 생겼고 도메인이 나중에 발견됐다.

이 순서가 자연스러운 이유가 시스템의 성격에 있다.
KRP는 AWS 호출 래퍼로 시작했고, 처음에는 도메인이라 할 것이 없었다 —
요청을 받아 AWS에 넘기는 것이 전부였다.
회사 정책, 즉 이름 규칙과 태그 규칙이 쌓이면서 비로소
AWS 호출도 아니고 HTTP 처리도 아닌 로직이 생겼고,
그때 `services`가 필요해졌다.
`_populate_create_request`가 하는 일이 정확히 그 정책의 구현이며,
이 시스템의 도메인은 설계된 것이 아니라 축적된 것이다.

### 코드 규모 비교표가 감각을 주면서 동시에 약점을 드러낸다

KRP 71,465줄을 Celery 101,413줄과 FastAPI 112,887줄과 Django 524,942줄과 나란히 놓은 표는
청중에게 규모 감각을 주는 장치다.
4년 된 사내 백엔드가 널리 쓰이는 프레임워크의 절반 이상 크기라는 사실이
이 회고의 무게를 정한다 — 장난감 프로젝트의 이야기가 아니라는 것이다.

그런데 같은 표의 나머지 두 열이 다른 이야기를 한다.
테스트 비율 35%와 커버리지 71%는 넷 중 가장 낮다.
비교 대상이 오픈소스 프레임워크이므로 이 차이는 예상 가능하고 —
공개 라이브러리는 더 높은 테스트 비율을 요구받는다 —
자료가 그 사실을 숨기지 않고 표에 넣은 것은 정직하다.

다만 이 숫자가 자료의 다른 주장과 맞물릴 자리가 있는데 그 연결이 없다.
일곱 단계 중 세 단계의 ➕가 테스트에 관한 것이다 —
Provider는 `RedisClient`만 모킹하면 되고,
Client 사전 생성은 유닛테스트 속도를 올렸고,
Service는 HTTP 없이 로직을 테스트할 수 있게 했다.
구조 변경의 주된 이득으로 테스트 용이성을 반복해서 든 시스템이
4년 뒤 셋 중 가장 낮은 테스트 비율을 갖고 있다면
그 사이에 무슨 일이 있었는지가 이 회고의 자연스러운 주제인데 다뤄지지 않는다.

## 비평

### “미리 변하지 않아서 좋았다”는 결론은 반증 사례 없이 제시된다

회고의 첫 줄이 결론이다 — 너무 미리 변하지 않아서 속도를 유지할 수 있었다는 것이다.
이 문장은 매력적이고 실무 감각과 맞는데, 제시된 근거가 결론을 지지하지 못한다.
근거는 일곱 번의 변경이 모두 증상이 나타난 뒤에 이뤄졌다는 사실이며,
그것은 “미리 변하지 않았다”를 확인하지만 “그래서 좋았다”를 확인하지는 않는다.

판단 기준도 사후적으로만 작동한다.
“명확한 이유가 있을 때만 변경했다”는 규칙은 변경 시점에서 보면 항상 참이다 —
변경했다는 것이 곧 이유가 있었다는 뜻이므로 반례가 생길 수 없는 형태다.
이 규칙이 검증 가능해지려면 반대 방향의 사례가 필요하다.
이유가 있었는데 변경하지 않았고, 그래서 무엇을 얼마나 잃었는지에 대한 기록이다.

그리고 그 사례가 실은 자료 안에 있다.
회고의 마지막 ➖가 “리팩터링이 덜 끝난 코드가 늘어남”이고,
공통 로직 추출 단계의 ➖ 중 하나가 “아직 다 옮기지 못함”이다.
이것은 늦은 변경의 증거이며 결론의 반례로 다뤄져야 하는 항목인데,
장단점 목록의 한 줄로 처리되고 결론에서는 “AI에게 시키면 되니까 미루지 말기”라는
농담에 가까운 문장으로 넘어간다.

가장 아쉬운 것은 이 자료가 그 질문에 답할 재료를 갖고 있다는 점이다.
커밋 3,542개와 PR 1,591개가 있으므로
각 리팩터링 직전 구간의 변경 빈도나 리버트 비율을 볼 수 있고,
“증상이 나타난 시점”과 “변경한 시점” 사이의 간격을 측정할 수 있다.
그 간격이 짧았다면 결론이 데이터로 뒷받침되고,
길었다면 결론이 “늦었지만 버텼다”로 바뀐다.

### 시점 라벨이 서로 맞지 않아 논지의 재료가 흔들린다

이 발표의 논지는 변화의 간격에 걸려 있다.
언제 변했는지, 얼마나 참았는지가 “미리 변하지 않았다”의 유일한 증거다.
그래서 시점 표기의 정확성이 장식이 아니라 논증의 재료다.

두 곳이 맞지 않는다.
DB 도입 장이 2023년 8월이고 그 다음 장인 Celery 전환이 2023년 7월이므로
시간순 서술이 한 번 역행한다.
그리고 공통 로직 추출이 2025년 4월인데 라벨은 “8개월 후”다 —
직전 장의 2023년 8월을 기준으로 하면 20개월이다.

주제별로 묶어 순서를 바꾼 것이라면 그 사실을 한 줄 표시하면 되고,
그편이 오히려 독자에게 유용하다 — BackgroundTasks와 Celery는
DB와 독립적으로 다뤄야 할 축이기 때문이다.
문제는 표시가 없어서 독자가 각 장의 “N개월 후”를 누적할 수 없다는 점이다.

“8개월 후”가 오기라면 방향이 더 흥미롭다.
실제 간격이 20개월이면 “너무 미리 변하지 않았다”는 주장이 훨씬 강해진다.
서비스가 스무 개를 넘는 동안 공통 로직 추출을 미뤘다는 것이며,
그 인내가 이 회고의 가장 강한 증거다.
오기가 자기 주장을 약하게 만들고 있는 셈이다.

### “AI가 없던 시절”이라는 프레임을 목적에 걸고 회수하지 않는다

발표 목적의 네 번째 질문이 “AI가 없던 시절에 프로젝트는 어떻게 자라날까”다.
목적으로 세운 질문이므로 본문이 그것에 답할 것으로 기대되는데,
64쪽 어디에도 AI 시대와의 대조가 없다.

AI는 두 번 등장하고 둘 다 같은 형태다.
공통 로직 추출 단계의 “아직 다 옮기지 못함. 이제 AI에게 시키면 되지만”과
최종 회고의 “리팩터링이 덜 끝난 코드가 늘어남. 이제 AI에게 시키면 되니까 미루지 말기”다.
질문으로 세운 프레임이 결론에서 “미룬 일을 AI가 처리해 줄 것”이라는 낙관으로 대체된다.

그 낙관이 자료의 다른 관찰과 부딪힌다.
일곱 단계의 ➖가 반복적으로 열람 지점의 증가였고,
마지막 단계의 ➖는 온보딩 시간의 증가였다.
그 비용은 코드를 처음 읽는 주체에게 붙는 비용이며,
에이전트가 코드를 읽을 때도 같은 자리에서 발생한다 —
요청 하나를 이해하려고 파일 세 개를 열어야 하는 구조는
사람에게든 도구에게든 같은 수의 열람을 요구한다.

이 프레임을 회수했다면 자료의 값이 커질 수 있었다.
네 번째 질문의 정직한 답은 “AI가 없던 시절에는 구조 변경의 속도가
사람의 이해 속도에 묶여 있었고, 그 제약이 과도한 선제 설계를 막아 줬다”쯤이며,
그 답에서 자연스럽게 따라오는 질문이 이 자료가 열어 둔 진짜 논점이다 —
그 제약이 사라지면 무엇이 남아서 선제 설계를 막을 것인가다.

## 인사이트

### 레이어의 비용 단위는 파일 수가 아니라 이름이 바뀌는 경계의 수다

자료는 ➖에 파일 수를 세어 두었다 — 둘, 셋으로 늘어나고 “레이어 나눌 때마다 늘어남”이라고 적는다.
그런데 파일 수는 비용의 대리 지표이고, 실제 비용은 다른 데서 나온다.
경계를 지날 때마다 같은 것의 이름이 바뀌기 때문이다.

자료 안에 그 증거가 있다.
Client 사전 생성 단계의 ➖가
`redis_client`라는 이름만으로는 클라이언트인지 클라이언트 생성 함수인지 헷갈린다는 것이다.
파일이 하나 늘어난 것이 아니라 같은 개념이 두 층에서 다른 것을 뜻하게 된 문제이며,
Service 단계의 “예외가 쌍으로 늘어남”도 같은 종류다 —
`ClusterExistsError`와 `HTTPException`은 같은 사건의 두 이름이다.

그래서 레이어 추가의 비용을 줄이는 방법이 파일 병합이 아니다.
경계에서 이름을 유지하는 것이며, 이름이 바뀌어야 한다면
그 대응을 한 곳에 모아 두는 것이다.
KRP가 마지막 단계에서 `on_create`·`on_retrieve`·`on_delete`라는
세 개의 훅으로 수렴한 것이 사실상 그 작업이다 —
스무 개 서비스가 각자 다른 이름으로 하던 일에 공통 이름을 붙였다.

여기서 따라오는 2차 효과가 비용의 이전이다.
자료는 그 수렴의 ➖로 “신규 입사자의 온보딩에 시간이 더 걸림”을 적었다.
즉 레이어 추가의 이득은 지금 있는 팀원이 받고 비용은 나중에 오는 사람이 낸다.
조직이 커지면 그 비대칭도 커지며, 지금은 나중에 오는 사람 중 하나가 에이전트다.
에이전트의 컨텍스트 예산이 열람 지점 수에 비례하므로
이 비용 항목은 사람 온보딩 시간에서 토큰 비용으로 이름만 바꿔 계속 청구된다.

### “이유가 생길 때까지 미룬다”는 원칙은 가역적 변경에만 안전하다

일곱 단계를 성격으로 다시 분류하면 여섯 개와 하나로 갈린다.
Provider·Client·Service·Celery·공통 로직은 전부 코드의 위치를 옮기는 일이고,
되돌리려면 다시 옮기면 된다.
DB 도입은 다르다.

자료가 그 차이를 감지하고 있다.
DB 단계의 ➖가 “DB와 AWS 중 어디가 진짜일까”와
“AWS가 잘 작동해도 DB가 문제라면 시스템이 죽음”이다.
이것은 코드 구조에 관한 불편이 아니라 진실의 원천에 관한 질문이며,
한 번 데이터가 쌓이면 결정을 되돌릴 수 없다.
같은 부류의 결정이 스키마 설계와 ID 체계와 공개 URL 구조다 —
전부 나중에 바꾸는 비용이 처음에 정하는 비용의 수십 배가 된다.

그러므로 “증상이 나타날 때까지 미룬다”는 규칙은 가역성으로 분할되어야 한다.
가역적인 변경은 미루는 것이 이득이고 —
미룬 동안 얻은 정보로 더 나은 선택을 하게 되므로 —
비가역적인 결정은 증상이 나타나기 전에 설계해야 한다.
증상이 나타난 시점에는 이미 되돌릴 수 없는 상태이기 때문이다.

KRP는 그 결정을 잘 내렸다.
“KRP에서는 AWS를 원천으로 정함”이라는 괄호 한 줄이
이 시스템의 4년을 지탱한 판단이며,
DB를 캐시로 규정했기 때문에 DB 장애가 데이터 손실이 아니라 가용성 문제로 남는다.
그 한 줄이 일곱 단계의 다른 장단점 항목들과 같은 무게로 나열되어 있는 것이
이 자료 구성의 아쉬운 지점이며,
회고에서 뽑아 낼 수 있는 가장 이전 가능한 교훈이 거기 있다 —
미룰 수 있는 것과 미룰 수 없는 것을 먼저 나누라는 것이다.

### 상위 세 명이 커밋의 78%라는 사실이 이 회고의 성립 조건이다

기여자 21명 중 세 명이 커밋의 78%를 만들었다.
이 숫자가 규모 슬라이드에 무심하게 적혀 있는데,
회고의 결론이 성립하는 조건이 여기 있다.

“명확한 이유가 있을 때만 변경한다”는 규칙은 판단을 요구하고,
무엇이 명확한 이유인지는 사람마다 다르게 본다.
결정권이 소수에 모여 있으면 그 판단이 4년간 일관되게 유지되고,
그래서 변경의 리듬에 일관성이 생긴다.
21명이 균등하게 기여하는 구조에서 같은 규칙을 적용하면
결과는 두 가지 중 하나다 — 각자의 기준으로 변경해서 구조가 흔들리거나,
합의 비용이 커져서 필요한 변경도 멈춘다.

콘웨이 법칙의 익숙한 형태는 구조가 조직의 소통 경로를 반영한다는 것인데,
이 사례가 보여 주는 것은 한 층 더 들어간 관계다.
구조 변경의 리듬이 결정권의 집중도를 반영한다.
불규칙한 간격과 일관된 판단 기준은 소수 결정 구조의 특징이고,
정기적 리팩터링과 문서화된 규칙은 분산 결정 구조가 도달하는 형태다.
어느 쪽이 낫다기보다, 회고에서 원칙만 옮기고 조직 조건을 옮기지 않으면
그 원칙이 다른 팀에서 작동하지 않는다.

여기서 실질적인 위험이 하나 보인다.
그 세 명이 떠나면 구조는 남고 판단 기준은 사라진다.
`BaseKrpServiceEnhanced`가 무엇을 담아야 하는지는 코드에 있지만
“왜 2025년 4월까지 기다렸는지”는 코드에 없다.
그래서 이런 발표 자료가 대외 홍보가 아니라 기준의 이전 장치이며,
사내 위키의 어느 문서보다 오래 남을 가능성이 높다는 점이 아이러니다.

### 나이테 비유를 끝까지 밀면 기록해야 할 것이 결정이 아니라 제약이다

나이테는 나무의 성장 기록이면서 동시에 그 해의 기후 기록이다.
비가 많은 해는 넓고 가문 해는 좁으며,
그래서 고고학과 기후학이 나이테를 자료로 쓴다.
비유를 그렇게 읽으면 이 자료의 일곱 고리도 코드의 이력이 아니라 제약의 이력이다.

각 고리가 무엇을 기록했는지 보면 분명하다.
Client 사전 생성 고리에는 4리전 2환경이라는 회사의 지리적 확장이 새겨져 있고,
KR과 GB가 Prod와 Alpha 계정을 공유한다는 예외까지 남아 있다.
DB 고리에는 플랫폼 사용량이 목록 조회를 병목으로 만들 만큼 늘었다는 사실이 있고,
공통 로직 고리에는 서비스가 스무 개를 넘었다는 성공이 있다.
Celery 고리에는 배포 주기라는 운영 현실이 있다.
구조를 읽으면 회사의 4년이 읽힌다.

여기서 아키텍처 기록에 대한 실무적 함의가 나온다.
[아키텍처 결정 기록](adr.md)의 통상적인 형식은
무엇을 골랐고 어떤 대안을 검토했는지를 남기는 것인데,
나이테의 관점에서 더 값나가는 것은 그때 무엇이 제약이었는지다.
제약은 사라지고 결정은 남기 때문이다.

이 비대칭이 실제 사고를 만든다.
4리전 2환경 때문에 만든 클라이언트 사전 생성 맵은
리전이 하나로 줄어도 그대로 남고,
그 코드를 읽는 후임자는 왜 이렇게 되어 있는지 모른 채 그것을 원칙으로 받아들인다.
`redis_client`가 생성 함수인지 클라이언트인지 헷갈린다는 그 자료의 불만도
사실 이 종류의 화석이다.
그래서 회고에 남겨야 할 문장은 “서비스 레이어를 추가했다”가 아니라
“API 시그니처에 클라이언트가 두 개 붙었을 때 추가했다”이며,
이 자료가 실제로 그렇게 쓰여 있다는 점이 형식적으로 가장 잘한 선택이다 —
[코드베이스가 팀을 느리게 만드는 방식](codebase-drag.md)을
사후에 감사하는 것보다 당시의 제약을 그때 적어 두는 편이 싸다.
