# Server-Driven User-Interface (SDUI): 서버는 표현을 지시하되 디자인은 통제하지 않는다

<https://github.com/csmets/Server-Driven-UI>

HN 토론: <https://news.ycombinator.com/item?id=33730227> (5점, 4개 댓글)

## 소개

SDUI를 처음부터 끝까지 구현한 예제 프로젝트와 그 구현이 따라야 할 표준 문서를 함께 담은
저장소다.
저장소 설명은 “규모 확장의 모범 사례를 가르치는 SDUI 프레임워크 예제”이고, README는 이
프로젝트를 SDUI를 배우기 위한 자원이자 놀이터로 규정한다.
동시에 첫 줄에 경고가 있다 — “초기 초안. 동작하지 않고 바뀔 것을 예상하라.”

2021년 9월 18일에 만들어졌고 마지막 커밋은 2024년 8월 25일이다.
TypeScript로 작성되었고 라이선스는 GPL-3.0이며, 스타 211개, 포크 19개, 워처 8명, 열린
이슈 0개다.

핵심 주장은 굵게 강조되어 있다 — SDUI의 주된 장점은 모든 비즈니스 로직이 서버 쪽에
유지되고 클라이언트(프런트엔드)는 UI만 제공하는 “멍청한” 상태로 남아야 한다는 것이다.
앱에 미리 만들어 둔 컴포넌트를 서버가 조합해 사용자가 앱을 업데이트하지 않아도 새 경험을
전달할 수 있으므로 이점이 모바일 쪽에 더 크다고 적으며, 참조로 Airbnb, Expedia, Lyft를
든다.

## 아키텍처와 모듈

다이어그램의 구조는 단순하다.
안드로이드, iOS, 웹(React) 클라이언트가 모두 템플릿 서비스를 바라보고, 템플릿 서비스는
컴포넌트를 구성할 스키마를 가진 컴포지터를 호출한다.
모든 클라이언트는 그 스키마에 기반해 컴포넌트를 만들어야 하며, 그래야 응답과 결합된다.

저장소는 다섯 모듈로 나뉜다.

| 모듈              | 역할                                                                                                                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `graphql-server`  | 컴포지터. UI 모듈과 컴포넌트, 페이지의 스키마를 정의하는 곳이며 응답도 여기서 제공하므로 표현 데이터 변경과 레이아웃 변경이 모두 여기서 일어난다                          |
| `template-server` | 컴포지터와 클라이언트 사이의 중간 계층. GraphQL 서버의 여러 쿼리를 호출해 화면을 이어 붙이며, 클라이언트가 크고 복잡한 GraphQL 쿼리를 만들 필요를 없애고 REST 응답을 준다 |
| `tokens`          | 클라이언트 전반에서 쓸 스타일 토큰을 생성한다                                                                                                                             |
| `web-app`         | SDUI 설계를 보여주는 React 웹 앱                                                                                                                                          |
| `android-app`     | SDUI를 보여주는 Android Jetpack Compose 앱                                                                                                                                |

모든 클라이언트는 템플릿 서버를 호출해야 페이지를 구성할 수 있다고 README가 분명히 적는다.

## 문서

문서는 11개 장과 2개 부록으로 되어 있다.
아키텍처 기본, 타입명과 인터페이스와 유니온, 스키마 작성, 조합 가능한 디자인 시스템,
액션, 쿼리와 뮤테이션 작성, 폼, 시그널, 캐시가 본문이고, 여기에 “모든 비즈니스 로직은
서버 쪽에만 있어야 한다”와 “SDUI에서 클라이언트가 GraphQL을 호출하지 않는 것의 이점”이라는
두 편의 지식 문서가 붙는다.
부록으로는 Expedia의 “Sending Signals in Server-Driven UI”와 “Why Server-Driven UI Is Key
to the Longevity of Web Software Architecture Platforms”가 링크된다.

서문은 정의의 폭을 인정한다.
SDUI는 서버에서 문구나 지역화된 텍스트를 제공하는 정도로 단순할 수도 있고, 스타일과
템플릿까지 서버가 제공해 완전히 서버 주도가 될 수도 있다는 것이다.
어느 쪽이든 클라이언트는 “멍청해야” 하고 서버 응답에서 비즈니스 로직을 끌어내서는 안
된다고 적는다.
이 프로젝트는 SDUI를 특정 방식으로 해야 한다는 의견을 가진 프로젝트이며, 그 의견의 바탕이
GraphQL을 SDUI에 쓴 경험에서 왔다고 밝힌다.

장단점도 문서에 직접 정리되어 있다.
장점으로는 네이티브 클라이언트가 조합 가능한 콘텐츠를 제공할 수 있다는 것, 앱 업데이트
횟수를 줄인다는 것, A/B 테스트 추가가 새 클라이언트 릴리스 없이 빨라진다는 것, 여러
플랫폼에 일관된 데이터를 제공한다는 것, 비즈니스 로직을 각 클라이언트에서 바꿀 필요가
없어진다는 것, 클라이언트가 멍청해져 가벼워지고 클라이언트 고유 버그가 줄어든다는 것을
든다.
단점 목록이 더 흥미롭다 — 플랫폼 고유 기능을 활용하기 어려워지고, 엔터프라이즈 규모에서는
조직 전반의 조율이 어렵고, 클라이언트 중심 연산을 서버로 옮기기 어렵고, 표준화되지 않은
미성숙한 설계 아이디어여서 개발자와 디자이너와 제품 담당자가 이 패러다임을 배우고
가르쳐야 하고, 복잡한 비즈니스 로직이 많으면 응답이 서버에 부담이 되어 서버 비용이
올라간다는 것이다.
GraphQL에 국한된 문제도 명시한다 — 여러 타입을 표시할 수 있는 조합 가능 컴포넌트를 만들면
클라이언트의 요청이 매우 빠르게 커지고 그것이 성능에 영향을 준다는 것이다.

문서 전체를 관통하는 규칙은 인용문으로 강조되어 있다.

> 서버는 항상 표현(presentation)을 지시해야 하지만, 디자인을 통제해서는 절대 안 된다.

이어지는 설명이 이 규칙의 구체적 내용이다.
서버 응답에는 어떤 스타일 값도 절대 넣지 말고, 디자인은 컴포넌트를 렌더링하는 데 필요한
데이터 계약을 갖게 하라는 것이다.
이것은 관심사 분리를 위한 것이며, 서버 응답을 만들 때 클라이언트에 어떤 스타일 옵션을
제공해야 할지 고민하지 않게 된다.
시각적으로 어떻게 보일지는 클라이언트가 결정한다.

## 사용법

전제 조건은 docker와 docker-compose, 그리고 nvm이다.

```bash
bash ./quickly-get-started.sh   # 동작하는 웹 데모까지 한 번에
docker-compose up               # 서버 쪽 앱만 실행
```

## 분석

### 이 저장소의 지도 원리가 SDUI라는 이름의 정의를 정면으로 좁힌다

SDUI를 소개하는 글들은 대체로 서버가 보내는 JSON이 UI의 “구조와 스타일과 로직”을
정의한다고 쓴다[^ref-risk].
간격과 정렬과 색과 텍스트 정보를 담은 뷰가 응답에 들어온다는 서술도 같은 계열이다.
이 저장소는 정확히 그것을 금지한다 — 스타일 값을 응답에 절대 넣지 말라는 것이다.

같은 이름 아래 두 개의 다른 아키텍처가 유통되고 있는 셈이다.
스타일을 응답에 포함하는 쪽에서는 디자인 시스템의 소유권이 서버로 넘어가고 클라이언트는
범용 렌더링 엔진이 된다.
데이터 계약만 보내는 쪽에서는 클라이언트가 디자인 시스템을 소유하고 서버는 어떤 컴포넌트를
어떤 순서로 놓을지만 정한다.
`tokens` 모듈이 존재하는 이유가 후자의 귀결이다 — 스타일이 응답에 없으므로 플랫폼 간
일관성은 응답이 아니라 공유 토큰으로 확보해야 한다.

반대 진영의 대표 사례가 이 저장소가 참조로 든 Airbnb라는 점이 이 대립을 선명하게 만든다.
Ghost Platform의 섹션 상세에는 스타일 정보가 담기고, 섹션 컴포넌트 타입이 같은 제목을
다른 시각 처리로 렌더링하도록 지시한다.
즉 이 저장소가 “절대 하지 말라”고 규정한 것을 이 분야에서 가장 많이 인용되는 구현이
하고 있으며, 그러면서도 둘 다 SDUI라는 같은 이름으로 불린다.

이 구분이 실무에서 결정적인 이유는 뒤따르는 모든 판단이 여기서 갈리기 때문이다.
누가 디자인을 바꿀 권한을 갖는지, 스타일 변경에 앱 배포가 필요한지, 응답이 사용자별로
달라져 캐시가 무력화되는지, 접근성 검증의 범위가 컴포넌트인지 조합인지가 모두 이 한 줄의
규칙에 달려 있다.
그런데 SDUI를 다루는 대부분의 글은 이 갈림길을 언급조차 하지 않는다.

### `template-server`라는 중간 계층은 GraphQL의 대가를 인정한 설계다

이 저장소는 스스로 GraphQL에서 출발했다고 밝히면서도, 클라이언트에게는 GraphQL을 숨긴다.
`template-server`가 여러 GraphQL 쿼리를 호출해 화면을 이어 붙이고 클라이언트에는 REST
응답을 주며, 모든 클라이언트가 이 계층을 거쳐야 한다.

이 설계의 이유가 문서의 단점 목록에 적혀 있다.
여러 타입을 표시할 수 있는 조합 가능 컴포넌트를 만들면 클라이언트가 보내야 하는 쿼리가
급격히 커지고 그것이 성능을 해친다는 것이다.
SDUI에서 화면은 “어떤 컴포넌트가 올지 미리 알 수 없는 목록”이므로, 클라이언트가 GraphQL로
그것을 표현하려면 가능한 모든 유니온 분기를 쿼리에 나열해야 한다.
화면 하나의 쿼리가 수백 줄이 되는 상황이 이 패턴의 알려진 함정이며, 이 저장소는 그것을
중간 계층으로 우회한다.

여기서 얻을 수 있는 일반적 판단이 있다.
SDUI에서 스키마 언어의 값은 서버 내부에서 조합을 정의하고 검증하는 데 있고, 클라이언트
인터페이스로서는 오히려 부담이 된다.
Lyft가 protobuf로 표현한 뷰를 BFF에서 병합해 내려보내고 Airbnb가 GraphQL 스키마를
쓰면서도 클라이언트에는 화면 단위 응답을 주는 것과 같은 방향이며, 이 저장소는 그 구조를
두 개의 서비스로 명시적으로 분리해 보여준다.

### SSR과의 차이를 저자가 직접 정리한 대목이 통상의 비유를 교정한다

SDUI를 설명할 때 가장 흔히 쓰이는 비유가 “웹은 이미 서버 사이드 렌더링으로 이것을 해
왔다”는 것이다.
2022년 Show HN에서 `jallasprit`이 정확히 그 지점을 물었다 — SDUI와 SSR의 차이가 무엇이며,
결국 Angular와 Vue와 React 이전에 웹이 작동했던 방식이 아니냐는 것이다[^jallasprit].

저자의 답이 이 비유의 한계를 짚는다.
SSR과 SDUI가 클라이언트가 그릴 표현 결과를 제공한다는 점에서 유사하지만 SSR은 웹에
국한되며, 모바일 앱은 웹뷰가 아니면 웹이 하는 일을 할 수 없고 웹뷰는 오프라인 지원이
제한적이거나 없어 바람직하지 않다는 것이다.
또한 프런트엔드 프레임워크가 등장하기 전의 백엔드에서는 표현과 데이터가 결합되어 있었고
관심사 분리가 분명하지 않아 비즈니스 로직과 UI가 얽혀 있었는데, 그때의 UI는 SDUI처럼
추상적인 것이 아니라 실제 DOM 요소였다고 구별한다[^csmets-ssr].

이 답이 중요한 이유는 SDUI의 정체를 추상 수준으로 규정하기 때문이다.
SSR은 최종 표현(HTML)을 보내고 SDUI는 표현의 추상 기술(컴포넌트 이름과 데이터 계약)을
보낸다.
전자는 렌더링 대상이 고정되어 있고 후자는 렌더링 주체가 플랫폼별로 다르다.
그래서 SDUI는 SSR의 모바일 이식이 아니라, 여러 렌더러를 전제한 표현 기술 계층이라고
불러야 정확하다.

### 문서의 분량 분포가 이 패턴의 진짜 난이도를 알려준다

문서 11장의 크기를 재 보면 순서가 뚜렷하다.
시그널이 가장 길고(약 11,400자), 액션과 스키마가 그다음(각 5,600자, 5,500자)이며, 아키텍처
기본은 3,100자, 캐시는 2,100자다.

컴포넌트를 어떻게 정의하고 렌더링하는지는 문서가 짧다.
반면 시그널 — 무엇이 바뀌었음을 클라이언트에 알리고 그에 따라 화면 일부를 갱신하는 문제 —
가 가장 많은 분량을 요구한다.
캐시 문서가 클라이언트 내비게이션과 오프라인 경험에서 데이터를 유지하는 문제를 다루는 것도
같은 축이다.

이 분포는 SDUI를 평가하는 기준을 바꾼다.
프레임워크를 고를 때 눈에 먼저 들어오는 것은 컴포넌트 카탈로그의 크기이지만, 실제로
프로젝트의 성패를 가르는 것은 상태 전파와 캐시 무효화 모델이다.
“무엇을 그릴지”는 스키마로 표현되지만 “지금 바뀐 것이 무엇인지”는 프로토콜로 표현되어야
하며, 후자를 설계하지 않은 SDUI 구현은 화면 전체를 매번 다시 받는 것으로 귀결된다.

## 비평

### “초기 초안”인 상태로 2년간 멈춰 있다

마지막 커밋이 2024년 8월 25일이므로 이 글을 쓰는 시점에서 약 2년이 지났다.
열린 이슈는 0개이고 워처는 8명이며, 스타는 211개다.
이 조합은 잘 관리된 프로젝트의 신호가 아니라 활동이 없다는 신호로 읽어야 한다 — 이슈가
없는 것은 문제가 없어서일 수도 있지만 아무도 보고하지 않아서일 수도 있다.

학습 자원으로 제시된 프로젝트에서 이 정지는 특히 문제다.
`quickly-get-started.sh` 한 줄로 데모를 띄우겠다는 약속은 의존성이 그대로일 때만 성립하는데,
그 사이 React와 Jetpack Compose와 Apollo 계열 라이브러리가 여러 차례 메이저 버전을 지났다.
Docker 이미지와 Node 버전 고정(`.nvmrc`)이 있어 완화되지만, 5MB가 넘는 저장소를 받아 실행이
되는지 확인하는 비용은 결국 독자가 지불한다.

README가 “동작하지 않을 것을 예상하라”고 미리 밝힌 것은 정직하다.
그러나 그 문장은 초안 시점의 면책이고 2년 정지 상태에 대한 안내가 아니다.
참조 구현의 값은 지금 돌아가는지에 크게 의존하므로, 마지막 검증 시점과 검증된 의존성 버전을
README 앞에 적는 것이 이 프로젝트에서 가장 값싼 개선이다.

### GPL-3.0이 이 프로젝트가 자칭한 목적과 충돌한다

저장소는 자신을 배움을 위한 자원이자 놀이터로 규정하고, 설명에는 “규모 확장의 모범 사례를
가르친다”고 적혀 있다.
그런데 라이선스는 GPL-3.0이다.

참조 구현의 목적은 읽고 배우고 자기 코드로 옮기는 것인데, 강한 카피레프트는 마지막 단계에
법적 검토를 요구한다.
구조를 참고하는 것과 코드를 옮기는 것의 경계는 실무에서 흐릿하고, 사내 프레임워크를 만들며
스키마 정의나 렌더러 구현을 참고할 때 그 흐릿함이 그대로 위험이 된다.
같은 성격의 예제 프로젝트들이 대체로 MIT나 Apache-2.0을 택하는 이유가 이것이다.

라이선스 선택은 저자의 권리이므로 잘못이라고 말할 수는 없다.
문제는 목적과 수단의 불일치가 문서에서 설명되지 않는다는 점이다.
가르치려는 프로젝트가 카피레프트를 택했다면 “구조는 자유롭게 참고하되 코드를 옮길 때는
라이선스를 확인하라”는 안내가 있어야 하고, 그것이 없으면 독자는 이 저장소를 어떻게 써야
하는지에 대한 가장 실질적인 정보를 얻지 못한다.

### 지도 원리를 지키는 대가가 문서에 계산되어 있지 않다

“서버 응답에 스타일 값을 절대 넣지 말라”는 규칙은 설계 원칙으로 훌륭하지만, 그 규칙에는
숨은 청구서가 있다.
스타일이 클라이언트에 있다면 스타일을 바꾸려면 클라이언트를 다시 배포해야 한다.

그런데 SDUI를 도입하는 가장 큰 동기가 정확히 그 배포를 우회하는 것이다.
마케팅이 캠페인 색을 바꾸고 싶을 때, 새 배지 모양이 필요할 때, 폰트 크기 위계를 조정하고
싶을 때 — 이 규칙 아래에서는 `tokens`를 갱신하고 앱을 다시 내보내야 한다.
즉 이 저장소의 SDUI는 “레이아웃과 조합은 서버가, 스타일은 릴리스가”라는 절충이며, 그
절충의 경계에서 무엇을 포기하는지가 문서에 적혀 있지 않다.

같은 문제가 더 깊은 곳에서도 나타난다.
새 컴포넌트가 필요할 때도 클라이언트 릴리스가 필요하다 — 서버는 미리 만들어 둔 컴포넌트만
조합할 수 있다.
README가 “앱에 미리 만들어 둔 컴포넌트를 활용해” 새 경험을 만든다고 정확히 적고 있으므로
이 제약을 숨기는 것은 아니지만, 장점 목록의 “앱 업데이트 횟수를 줄인다”와 나란히 놓고
읽어야 할 정보가 서로 다른 절에 떨어져 있다.
독자가 알아야 하는 것은 “업데이트가 없어진다”가 아니라 “업데이트가 컴포넌트 추가와 스타일
변경에만 필요해진다”이며, 이 문장 하나가 이 패턴에 대한 기대를 현실적으로 만든다.

### 접근성이 12개 문서 어디에도 없다

문서 11장과 문서 인덱스를 전부 확인했지만 접근성에 해당하는 항목이 하나도 없다.
`accessibility`, `a11y`, 스크린 리더, VoiceOver, TalkBack, 동적 폰트 크기 어느 것도 등장하지
않는다.
버저닝은 “모든 비즈니스 로직은 서버에” 문서에서 클라이언트 업데이트 이야기로 한 번 언급되는
정도다.

이 공백이 범위 누락이 아니라 표준의 결함인 이유는 이 문서 세트가 다루는 범위 때문이다.
폼과 액션과 시그널과 캐시까지 표준을 제시하는 문서라면 접근성은 같은 층위의 항목이다.
게다가 서버가 조합을 결정하는 아키텍처에서 접근성은 컴포넌트 단위로 해결되지 않는다 —
읽기 순서, 초점 이동, 그룹 라벨, 폰트 확대 시 레이아웃 붕괴는 조합에서 결정되고, 조합의
가능한 수는 서버 스키마가 허용하는 만큼 커진다.

필요한 것은 별도의 장 하나다.
컴포넌트가 노출해야 하는 접근성 계약(라벨, 역할, 그룹 관계)을 데이터 계약의 일부로 정의하고,
서버가 조합을 만들 때 그 계약이 깨지지 않는지 검증하는 규칙을 두는 것이다.
지도 원리가 “디자인은 클라이언트가 결정한다”고 선언했으므로 접근성도 클라이언트의 몫이라고
넘길 수 있지만, 조합에서 발생하는 접근성 문제는 클라이언트가 통제할 수 없는 위치에 있다.
원리가 만들어 낸 공백이므로 원리를 만든 문서가 답해야 한다.

## 인사이트

### 같은 이름으로 두 개의 아키텍처가 유통되는 상태가 이 분야의 실제 문제다

SDUI 도입 논의에서 가장 먼저 합의해야 하는 것은 이점이나 위험이 아니라 정의다.
스타일 값을 응답에 담는 구조와 데이터 계약만 담는 구조는 이름만 같고 거의 모든 결정이
다르다.

두 구조의 차이를 항목으로 펼치면 이렇다.
디자인 시스템의 소유자가 서버인가 클라이언트인가, 스타일 변경에 앱 배포가 필요한가, 응답이
사용자별로 달라져 CDN 캐싱이 무력화되는가, 접근성 검증의 단위가 컴포넌트인가 조합인가,
디자이너가 서버 설정을 직접 만질 수 있는가.
어느 항목도 사소하지 않고, 전부 첫 번째 질문의 답에서 따라 나온다.

그래서 실무 처방은 단순하다 — SDUI 도입 회의의 첫 안건은 “응답에 색과 여백을 넣을
것인가”여야 한다.
이 질문을 건너뛰면 백엔드 팀은 조합 API를 상상하고 디자이너는 원격 테마 편집을 상상하며
같은 단어로 합의한 뒤, 구현 중반에 서로 다른 것을 만들고 있었음을 발견한다.
이 저장소의 지도 원리가 값진 이유는 그 답을 문장 하나로 고정해 두었기 때문이다.

### 표현과 스타일을 섞은 시스템은 역사적으로 늘 되돌려졌다

“서버는 표현을 지시하되 디자인은 통제하지 않는다”는 규칙은 새로운 발명이 아니라 오래된
교훈의 재적용이다.

웹은 같은 길을 이미 걸었다.
초기 HTML은 `<font>`와 `<center>` 같은 표현 태그로 구조와 스타일을 섞었고, 그 결과 문서가
특정 표시 환경에 묶여 재사용이 불가능해졌다.
CSS로 분리하고 시맨틱 마크업을 강조한 흐름은 그 결합을 되돌린 것이며, 그 뒤에 반응형 디자인과
다크 모드와 동적 폰트가 가능해진 것은 분리의 배당이었다.
스타일이 문서에 섞여 들어가 있었다면 그중 어느 것도 사후에 얹을 수 없었다.

SDUI에서 스타일 값을 응답에 넣는 것은 같은 결합을 서버-클라이언트 경계에서 반복하는 일이다.
그리고 대가도 같은 형태로 온다 — 새 화면 밀도나 새 다크 모드 팔레트나 새 접근성 설정이
등장할 때, 이미 저장된 응답과 로그와 캐시에 남은 스타일 값을 전부 다시 만들어야 한다.
csmets의 규칙을 지킨 구조에서는 클라이언트 릴리스 한 번으로 끝나는 일이다.

부수 효과 하나가 특히 실용적이다.
스타일이 응답에 없으면 응답의 다양성이 줄어 캐시 가능성이 높아진다.
스타일 실험이 응답을 사용자별로 갈라놓지 않으므로 화면 응답을 실험군 단위로만 캐싱할 수
있고, 이는 SDUI의 알려진 성능 비용 하나를 구조적으로 줄이는 방법이다.

### 문서 분량은 프레임워크의 난이도 지도이므로 평가 기준으로 쓸 수 있다

이 저장소에서 가장 긴 문서가 시그널이라는 사실은 우연이 아니라 이 패턴의 성질이다.
서버가 화면을 그리는 구조에서 어려운 문제는 처음 화면을 그리는 것이 아니라, 사용자가 폼에
값을 넣고 버튼을 누른 뒤 무엇이 어떻게 바뀌어야 하는지를 정하는 것이다.

이 관찰을 도구 선택에 쓰면 질문이 달라진다.
컴포넌트를 몇 종류 지원하는지, JSON이 얼마나 표현력이 있는지가 아니라 — 상태 변경을 어떻게
알리는지, 부분 갱신의 단위가 무엇인지, 낙관적 업데이트를 지원하는지, 캐시 무효화가 서버
주도인지 클라이언트 주도인지를 먼저 물어야 한다.
이 저장소가 액션과 시그널과 폼과 캐시에 각각 장을 배정한 것은 그 질문들을 정면으로 다룬
것이며, 그 점에서 이 문서 세트는 코드보다 값이 크다.

일반화하면 문서의 분량 분포는 어떤 기술의 난이도 지도로 읽을 수 있다.
잘 쓰인 문서에서 긴 장은 저자가 실제로 고생한 곳이며, 짧은 장은 쉬웠거나 아직 부딪히지
않은 곳이다.
새 프레임워크를 평가할 때 목차를 훑고 각 장의 길이를 보는 것은 30초짜리 작업인데, 그것만으로
그 팀이 어디까지 가 봤는지를 상당히 정확하게 추정할 수 있다.

### 5점짜리 Show HN과 211개의 스타 사이의 간극이 이 분야의 정보 공급 상태를 요약한다

이 저장소는 2022년 11월 Show HN에 올라와 5점과 4개의 댓글을 받았다.
그중 하나는 SSR과의 차이를 묻는 질문이었고 다른 하나는 React Native와 Node.js 조합을
쓰고 있으니 살펴보겠다는 짧은 관심 표명이었다[^ano88888].
발표로는 거의 확산되지 않은 것이다.

그런데 지금 스타는 211개다.
즉 이 프로젝트는 소개 글로 퍼진 것이 아니라 검색으로 발견되었다.
SDUI를 도입하려는 팀이 참조 구현을 찾아 검색하고 있고, 그 수요를 채우는 공개 자료가 거의
없기 때문에 초안 상태의 개인 프로젝트가 그 자리를 차지한 것이다.

이 구도가 이 분야의 정보 공급 상태를 그대로 보여준다.
개요를 설명하는 글은 대량으로 생산되지만 스키마 설계와 시그널 프로토콜과 캐시 전략을
구체적으로 보여주는 자료는 드물고, 대기업의 사례 글은 자체 프레임워크를 소개하되 코드를
공개하지 않는다.
수요는 명확하고 유지되는 공급은 없다.

그래서 이 저장소를 평가하는 올바른 방식은 “쓸 수 있는 프레임워크인가”가 아니라 “읽을 값이
있는 문서인가”다.
코드는 2년 전에 멈췄고 의존성은 낡았지만, 시그널과 액션과 폼을 어떻게 나눌지에 대한 판단은
지금도 유효하다.
그리고 이 공백은 기회이기도 하다 — SDUI를 실제로 도입한 팀이 스키마 버저닝이 무너진 지점과
접근성 회귀를 발견한 경위를 공개하면, 그것이 지금 이 분야에서 가장 값진 1차 자료가 될
것이다.
