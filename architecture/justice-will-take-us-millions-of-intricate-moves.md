# Justice Will Take Us Millions Of Intricate Moves

원문: <https://www.crummy.com/writing/speaking/2008-QCon/>

## 요약

이 글은 “RESTful Web Services”의 공저자 Leonard Richardson이 2008년
11월 20일 QCon에서 발표한 강연의 원고다.
그는 당시 Canonical에서 Launchpad(오픈소스 개발 플랫폼)의 웹
서비스를 만들고 있었고, 이 강연의 진짜 목적은 기술 자체의 설명이
아니라 “REST적인 사고방식이 뉴에이지 종교 같은 것이 아니”라는
것을 동료들에게 설득하는 과정을 공유하는 데 있었다고 말한다.
그가 택한 설득 전략은 이론적 원칙을 나열하는 대신 웹 서비스와
월드와이드웹(WWW) 사이의 유비(analogy)를 사용하는 것이었고, 강연
전체는 “This American Life” 라디오 프로그램처럼 역사(1막), 실무
사례(2막), 이론(3막) 세 개의 장으로 구성된다.

### 1막 — Intergalactic Computer Network 대 Information Superhighway

1막은 인터넷의 두 가지 서로 다른 기원 서사를 대비시킨다.
베트남 전쟁 중 ARPA의 수장이었던 J.C.R. Licklider는 국방부 예산의
일부를 컴퓨터 과학 연구로 돌렸고, 그 배후에는 모든 사람이 서로
접근할 수 있고 모든 프로그래머가 원격으로 충분한 컴퓨팅 자원에
접근할 수 있어야 한다는 “Intergalactic Computer Network(ICN)”라는
비전이 있었다.
이 비전은 몇 년 뒤 ARPANET으로, 다시 인터넷으로 구체화되었다.
반면 1991년 상원의원 Al Gore가 발의한 High Performance Computing
and Communication Act는 “Information Superhighway(ISH)”라는 또
다른 비전에서 출발했는데, 이는 사람과 사람을 연결하려던 ICN과
달리 기업들이 화물을 옮기듯 정보를 옮기도록 돕는, 공공사업으로서의
성격이 강한 프로젝트였다.
일반 대중 입장에서 ISH는 사실상 “쌍방향 TV”에 가까웠다.

80~90년대에는 FTP, Usenet, IRC 같은 프로토콜들이 우후죽순 등장했고
HTTP도 그 목록 어딘가에 있었지만, 당시 사람들은 HTTP, URI, HTML
세 기술을 묶어 “WWW”라 불렀다.
Richardson은 자신이 고등학교 시절 BBS를 통해 처음 인터넷에
접속했고 ICN 계열 도구들을 열심히 익혔지만, 대학에 들어가기 직전
웹이 그 모든 프로토콜을 지워버렸다고 회고한다.
웹은 다른 프로토콜들을 잡아먹은 것에서 그치지 않고, “인터넷은
정보를 공유하는 곳”이라는 ICN의 세계관과 “인터넷은 물건을 사는
곳”이라는 ISH의 세계관이 충돌했을 때 후자까지 흡수해 버렸다.
1972년 ARPANET 관계자들이 “Computer Networks: The Heralds of
Resource Sharing”이라는 다큐멘터리에 등장했을 때, 그들은 스스로를
자원 공유의 전령이라 여겼지만, 실제로는 은하계를 먹어치우는
Galactus의 전령이었던 Silver Surfer와 비슷한 역할을 했다는
농담으로 이 상황을 정리한다.

세기 전환기에 웹의 성공에 대한 두 가지 중요한 반응이 있었다.
이론적 반응은 HTTP 스펙의 공동 저자인 Roy Fielding이 박사 논문을
통해 웹이 다른 프로토콜을 흡수하고 모든 분야로 뻗어나갈 수 있었던
이유를 규명한 것이었고, 실무적 반응은 Dave Winer와 Microsoft가
HTTP 위에서 동작하는 XML-RPC와 SOAP를 내놓은 것이었다.
Richardson은 XML-RPC와 SOAP의 근본적인 실수가 “HTTP라는 잘못된
밴드왜건에 올라탔다”는 데 있다고 주장한다.
그들은 HTTP를 기업 방화벽을 뚫고 데이터를 이곳에서 저곳으로
옮기는 “트럭”으로만 이해했는데, 이는 HTTP를 Information
Superhighway 관점(트럭)으로만 바라본 것이다.
그가 강조하는 핵심은 “인터넷은 트럭이 아니”라는 것, 그리고 웹의
진짜 힘은 HTTP 하나가 아니라 URI(주소 지정 기술)와 HTML(하이퍼텍스트
마크업 언어)까지 포함한 세 기술의 조합에서 나온다는 것이다.
그는 이 세 기술의 역사가 곧 3막에서 다룰 REST 아키텍처 제약의
근거가 된다고 예고하며 1막을 마친다.

### 2막 — Launchpad 웹 서비스 설계 실전

2막은 Launchpad 웹 서비스를 만들면서 겪은 실제 설계 결정과 고통을
다룬다.
Launchpad는 Python과 Zope 프레임워크로 작성되었고, 버그, 블루프린트,
코드 브랜치와 리뷰, 번역, 스프린트, 질문과 FAQ 등 오픈소스 개발의
거의 모든 측면을 아우르는 방대한 객체와 워크플로를 다룬다.
요구사항 중 하나는 최종 사용자가 네트워크 경계가 어디인지만 알면
되고, 그 외에는 웹 서비스에 대해 아무것도 몰라도 되도록 파이썬
클라이언트가 평범한 ORM 스타일 라이브러리처럼 보여야 한다는
것이었다.
Richardson은 이 요구사항이 하이퍼미디어를 애플리케이션 상태의
엔진으로 삼는 REST 제약을 지키면 오히려 더 빨리 달성될 수 있다고
동료들을 설득했다.

Launchpad는 내부 데이터 모델을 AtomPub에서 볼 수 있는 것과 유사한
컬렉션(collection), 엔트리(entry), 바이너리 파일이라는 세 종류의
외부 노출 리소스로 매핑했다.
Zope의 인터페이스 시스템 위에 파이썬 데코레이터를 만들어 내부
모델과 외부 노출 모델 사이의 차이를 어노테이션으로 기술하는
방식을 택했고, 컬렉션과 엔트리는 하이퍼링크가 내장된 JSON으로,
리소스의 조작 가능한 기능은 HTML 폼과 유사한 WADL 형식의 하이퍼미디어
폼으로 제공했다.

하지만 이 어노테이션 기반 접근에는 근본적인 약점이 있었다.
Zope 인터페이스의 내부 데이터 모델과 외부에 노출하고자 하는 모델이
완전히 같지 않았기 때문에, 일부 필드명 불일치 같은 사소한 문제는
어노테이션으로 해결할 수 있었지만, 버그 트래커의 상태(status)
필드처럼 `transitionToStatus`라는 메서드로만 변경 가능한 값은
시간 부족으로 PUT을 통한 균일한 수정 대신 커스텀 이름의 연산으로
POST를 통해 노출하는 “추한 편법”을 택할 수밖에 없었다.
이는 균일한 인터페이스(uniform interface) 위반이었고, 버그를
생성할 때도 컬렉션에 POST하는 대신 별도의 커스텀 연산을 거치는
등 비슷한 위반이 여러 곳에서 반복되었다.

Richardson은 이 타협들의 실질적 대가를 클라이언트 라이브러리
`launchpadlib`을 통해 실측할 수 있었다고 말한다.
그는 웹 브라우저가 HTML을 미리 컴파일하지 않고 런타임에 읽어
동작을 결정하듯, `launchpadlib`도 JSON과 WADL 표현을 런타임에
읽어들여 파이썬 관용구로 변환하는 하이퍼미디어 기반 클라이언트로
설계했다.
그 결과 “웹 서비스의 흠은 하이퍼미디어의 흠으로, 하이퍼미디어의
흠은 클라이언트 코드의 흠으로 그대로 이어진다”는 원칙이
관찰되었고, `transitionToStatus` 문제는 실제로 사용자가 예상하는
자연스러운 코드가 그대로 동작하지 않고 특수한 코드를 따로 배워야
하는 결과로 나타났다.
반대로 REST 원칙을 지킨 부분에서는, 서버가 새로운 어노테이션을
추가하거나 `transitionToStatus` 노출을 없애도 클라이언트 코드를
따로 수정할 필요가 없었는데, 이는 클라이언트가 서버가 그 순간
제공하는 하이퍼미디어 문서로부터 행동 지침을 얻기 때문이다.
같은 WADL 설명에 XSLT 변환을 적용해 파이썬 docstring에서 나온
참조 문서를 자동 생성할 수 있었다는 부수 효과도 언급된다.
Richardson은 2막을 “REST의 제약은 구속복(bondage gear)이 아니라
안전 하네스(safety harness)”라는 문장으로 마무리한다.

### 3막 — 성숙도 휴리스틱(Maturity Heuristic)

3막은 REST 제약과 주관적으로 판단되는 웹 서비스 품질 사이의
관계를 좀 더 완전한 형태로 정리한 이론적 틀을 제시한다.
Richardson은 웹 서비스를 설계할 때 사람들이 웹 기술 스택의
바닥에서부터 몇 가지 기술을 골라 쓰는 경향이 있으며, 이를 0개,
1개, 2개, 3개를 선택했는지로 대략 등급을 매길 수 있다고
설명한다.

**레벨 0(기술 미채택)**: XML-RPC나 Google의 (당시) SOAP 검색
서비스는 단일 URI에 POST를 보내 함수를 호출하는, C 라이브러리와
비슷한 형태다.
이는 웹처럼 보이지 않으며, 마치 식당이나 예술가의 Flash 기반
웹사이트처럼 “웹 안의 작은 피어홀을 통해 다른 우주와 통신하는”
방식에 가깝다.

**레벨 1(URI)**: Flickr, del.icio.us, Amazon ECS 같은 서비스들은
REST를 자처하지만 엄밀하지 않은데, 그럼에도 크게 인기 있는 이유는
자신들의 우주 안의 개별 사물마다 URI를 부여했기 때문이다.
사람들은 URI를 좋아하고, 원하는 정보 조각을 골라 그 URI에
무언가를 할 수 있게 해 주기 때문에 매시업과 재미있는 해킹을 쉽게
만든다.

**레벨 2(HTTP)**: 프로그래밍 언어의 클래스가 저마다 다른 이름의
메서드를 갖는 것처럼, 예전 인터넷은 WAIS의 Z39.50처럼 온갖 종류의
프로토콜을 발명해 왔다.
웹의 힘은 읽기 연산(GET)을 별도로 취급해 “그것을 가져와라”는
동작을 모든 자원에 대해 동일한 의미로 통일시킨 데 있다.
URI가 “That”을 가리키고 HTTP 메서드가 “Gimme”를 말한다는
비유로, GET을 모든 객체가 지원하는 `toString()`에 빗댄다.
RFC 2616이 GET에 안전성(safe)과 멱등성(idempotent) 같은 제약을
부여하기 때문에 조건부 GET, 부분 GET, 캐시 가능성 같은 최적화가
가능해지는데, XML-RPC처럼 모든 요청에 POST만 쓰면 이런 최적화를
전혀 적용할 수 없다.
PUT과 DELETE를 POST에서 분리할지에 대한 논쟁은 순수성이 아니라
바로 이 레벨 2 차원의 논쟁이라고 짚는다.

**레벨 3(하이퍼미디어)**: 많은 사람이 하이퍼미디어의 가치를
이해하기 어렵다는 이유로 레벨 2에 안주하지만, Richardson은
Launchpad 사례가 하이퍼미디어의 가치를 보여준다고 주장한다.
그는 Amazon S3의 문서가 버킷과 파일 간의 실제 링크 없이 규칙만
문서로 설명해 클라이언트-서버 결합을 만드는 사례와, Netflix의
문서가 실제 하이퍼링크를 담고 있어 URL이 바뀌어도 클라이언트가
깨지지 않는 사례를 대비시킨다.
그는 하이퍼미디어를 링크(자원이 어디 있는지)와 폼(그 자원에 무엇을
할 수 있는지) 두 가지로 나누고, 미디어 타입이 표현물 안에서 무엇이
링크이고 무엇이 폼인지 알려주는 역할을 한다고 설명한다.
주식 매수 페이지와 위키 편집 페이지가 둘 다 HTML의 POST
요청이지만 그 안의 FORM 태그가 각기 다른 의미를 부여한다는
예시로 이를 구체화한다.
하이퍼미디어의 대안은 사람이 읽고 이해해서 클라이언트에 하드코딩해야
하는 일반 문서(regular media)뿐이며, 하이퍼미디어를 쓰면 개발자는
사람이 웹 브라우저 앞에 앉아 링크를 클릭하고 폼을 채우는 행동을
시뮬레이션하기만 하면 되므로 그 일까지 겸해 사람과 브라우저 전체를
시뮬레이션하는 것보다 쉽다고 설명한다.

### 결론 — George Jetson을 만나다

결론은 만화 “The Jetsons”의 조지 젯슨이 공장에서 버튼 하나만
누르면 로봇이 모든 일을 하는 상황을 유머러스하게 인용하며
시작한다.
Richardson은 이런 시나리오가 현실적으로 불가능하다고 말하는데,
복잡성을 자동으로 없애 주는 로봇 자체가 매우 복잡한 기계이기
때문이다.
그는 웹 서비스 업계가 서버 사이드를 그대로 두고 버튼 하나로
클라이언트 사이드를 만들어낼 수 있다는 믿음에 기반해 왔다고
지적하며, 이것이 불가능한 이유를 두 가지로 정리한다.
첫째, 복잡성을 숨기는 장치는 네트워크 경계가 없는 것처럼 가장해
깨지기 쉬워지거나(brittle) HTTP를 TCP/IP 같은 전송 프로토콜처럼
취급해 비효율적이 된다.
둘째, 그 버튼은 당신보다 똑똑하지 않으므로, 당신 쪽에 불필요한
복잡성이 있다면 버튼은 그것을 없애 주지 못하고 그대로 클라이언트에
전가한다.
Launchpad를 최소한의 어노테이션으로 발행했을 때 겪은 문제가
바로 이것이었다.

해법은 복잡성을 자동으로 없애는 것이 아니라, (1) 복잡한 것을 작은
조각으로 쪼개어 복잡성을 분산시키고, (2) 근본적으로 같은 것을
같은 방식으로 다뤄 복잡성을 줄이고, (3) 두 복잡한 것의 차이를
표준적인 방식으로 기술하는 것이라고 정리한다.
이 세 가지는 각각 URI, HTTP, HTML의 교훈에 대응하며, 이 세
기술을 결합하면 무상태성(statelessness), 하이퍼미디어를
애플리케이션 상태의 엔진으로 삼는 것 등 사람들을 혼란스럽게
만드는 REST 제약들을 풀어서 설명할 수 있다고 마무리한다.
그는 웹 기술의 관점에서 사고하는 것이 역사, 이론, 실무를 하나로
묶어 준다는 점이 이 접근법의 가치라고 강조하며 강연을 끝맺는다.

## 분석

### 유비(analogy)를 설득 도구로 선택한 근본적인 이유

Richardson이 굳이 “REST 아키텍처 스타일의 여섯 가지 제약”을
나열하는 대신 웹의 역사를 다시 짚는 방식을 택한 것은, 그가
동료들을 설득해야 하는 청중으로 상정했기 때문이다.
Fielding의 논문은 REST를 추상적 제약 조건의 집합으로 공리화하지만,
이런 공리적 설명은 “왜 이 제약을 지켜야 하는가”라는 실무자의
질문에 직접 답하지 못한다.
반면 “여러분이 10년 넘게 매일 쓰고 있는 웹이 사실 이런 원리로
다른 모든 프로토콜을 잡아먹었다”는 서사는 청중이 이미 체득하고
있는 경험적 직관을 REST의 정당성으로 곧바로 연결한다.
이 선택은 단순한 수사적 기교가 아니라, 이론이 실무자 집단에
받아들여지려면 그 이론이 실무자의 기존 경험을 재해석하는 언어로
번역되어야 한다는 더 일반적인 원칙을 보여준다.

### 성숙도 모델이 이분법적 정합성 판단을 연속적 스펙트럼으로 바꾼다

Richardson 이전까지 REST 논쟁은 대개 “이 서비스는 RESTful한가
아닌가”라는 이분법으로 흘렀고, 이는 그가 지적하듯 “피가 흐르지
않는(bloodless)” 논쟁, 즉 왜 신경 써야 하는지 설득력이 없는
논쟁이 되기 쉬웠다.
레벨 0부터 3까지의 성숙도 모델(이후 이 강연을 바탕으로 그가
정리한 개념이 “Richardson Maturity Model”이라는 이름으로 업계에
자리 잡았다)은 “RESTful이냐 아니냐”를 “어느 수준까지 웹 기술의
이점을 취했느냐”는 정도의 문제로 바꾸어 놓는다.
이 재구성이 중요한 이유는, 완벽하지 않은 설계도 그 나름의 이점을
취할 수 있다는 실용적 여지를 만들어 주기 때문이다.
Flickr나 Amazon ECS가 엄밀하게는 RESTful하지 않지만 URI 하나만
제대로 도입해도 매시업이 쉬워진다는 그의 관찰은, 순수성 논쟁에서
벗어나 “지금 이 설계는 어느 지점에 있고, 다음 단계로 가면 무엇을
얻는가”라는 점진적 개선의 언어를 제공한다.

### 클라이언트 라이브러리를 설계 결정의 실측 도구로 사용하는 방법론

이 강연에서 가장 독창적인 방법론적 기여는, 서버 측 설계의 타협이
초래하는 대가를 추상적으로 논하지 않고 실제로 작성한 클라이언트
라이브러리 `launchpadlib`을 통해 구체적으로 관찰했다는 점이다.
“웹 서비스의 흠은 하이퍼미디어의 흠으로, 하이퍼미디어의 흠은
클라이언트 코드의 흠으로 이어진다”는 그의 표현은, 설계의 결함이
숨을 곳이 없다는 뜻이며 이는 일종의 강제된 정직성 장치로
기능한다.
서버 API 설계자가 자신의 타협을 정당화하기는 쉽지만, 그 타협을
그대로 반영한 클라이언트 코드가 부자연스럽게 보이는 것은 부정하기
어렵다.
이는 API 설계 검증 방법론으로서, 문서나 스펙 검토만으로는
드러나지 않는 설계 결함을 실제 사용자 코드의 관점에서 역으로
검증하는 실천적 기법을 보여준다.

## 비평

### “웹은 트럭이 아니다”라는 핵심 은유가 정작 왜 HTML이 필수적인지는 설명하지 못한다

Richardson은 XML-RPC와 SOAP의 근본적 실수가 HTTP를 트럭으로,
즉 Information Superhighway의 관점으로만 이해한 데 있다고
비판하고, 웹의 진짜 힘은 URI와 HTML까지 포함한 조합에 있다고
주장한다.
그러나 강연 전체에서 HTML(하이퍼미디어)이 정말로 “필수적인” 이유는
2막의 Launchpad 사례와 3막의 S3-대-Netflix 비교를 통해 경험적으로
예시될 뿐, 왜 하이퍼미디어 없이는 원리적으로 시스템이 깨지는지에
대한 논증은 제시되지 않는다.
실제로 그 자신도 3막에서 “레벨 2에 머무는 서비스도 매우 인기
있고 유용하다”고 인정하는데, 이는 레벨 3(하이퍼미디어)이 레벨
2보다 우월하다는 주장이 필수성의 문제가 아니라 정도의 문제,
즉 트레이드오프의 문제라는 것을 스스로 드러낸다.
“웹은 트럭이 아니다”라는 강력한 은유가 실제로 뒷받침하는 것은
“HTML 없이는 안 된다”가 아니라 “HTML을 쓰면 특정 상황에서
이득이 크다”는, 더 약한 주장이다.

### Launchpad 사례가 하이퍼미디어의 보편적 가치를 증명하기에는 특수한 조건에 의존한다

2막에서 하이퍼미디어의 가치를 입증하는 핵심 증거는 서버 측
어노테이션이 바뀌어도 `launchpadlib` 클라이언트 코드를 고칠
필요가 없었다는 관찰이다.
그런데 이 증거가 성립하려면 클라이언트가 애초에 하이퍼미디어를
런타임에 해석하도록 설계되어 있어야 하고, 이는 Richardson
자신이 Launchpad 클라이언트를 처음부터 그렇게 설계했기 때문에
가능했던 결과다.
현실의 많은 웹 서비스 클라이언트는 타입 안전성이나 자동완성,
컴파일 타임 검증을 위해 SDK를 코드 생성(codegen) 방식으로
만드는데, 이런 클라이언트는 애초에 하이퍼미디어의 유연성을
활용하도록 설계되어 있지 않으므로 서버가 링크를 바꾼다고 해서
자동으로 이득을 보지 못한다.
즉 이 강연이 보여주는 하이퍼미디어의 이점은 “클라이언트가
하이퍼미디어 기반으로 설계되었을 때”라는 조건이 이미 충족된
상태에서만 성립하는데, 강연은 이 전제 조건 자체를 만드는 데
드는 비용(하이퍼미디어 인식 클라이언트 프레임워크를 처음부터
설계하는 비용)에 대해서는 다루지 않는다.

### “구속복이 아니라 안전 하네스”라는 결론이 실제로 겪은 타협의 반복성과 부딪힌다

Richardson은 2막을 REST 제약이 “구속복이 아니라 안전
하네스”라는 낙관적인 문장으로 마무리하지만, 그 직전까지
서술한 내용은 시간 부족으로 인해 `transitionToStatus`나 버그
생성 같은 균일한 인터페이스 위반이 “여러 곳에서” 반복되었다는
것이다.
이는 실제 프로젝트에서 REST 제약을 지키는 것과 마감 기한을
맞추는 것 사이의 긴장이 일회성이 아니라 구조적으로 반복되는
문제라는 것을 보여주는데, 강연은 이 긴장을 “나중에 고치면
된다”는 낙관으로 봉합한다.
그가 언급한 “annotation을 추가할 시간이 없었다”는 이유가 이후
실제로 해소되었는지, 아니면 다른 프로젝트에서도 마감 압박이
반복적으로 같은 방식의 타협을 유도했는지에 대한 후속 검증은
이 강연 안에서는 확인할 수 없다.
결과적으로 “안전 하네스”라는 표현은 설계 철학에 대한 신뢰
선언이지, 실제로 그 철학이 마감 압박을 이겨냈다는 증거는
아니다.

## 인사이트

### 성숙도 모델은 REST를 이념에서 도구로 전환시켜 산업 전체의 언어를 바꾸었다

이 강연에서 제시된 성숙도 모델은 이후 “Richardson Maturity
Model”이라는 이름으로 REST API 설계 논의에서 사실상의 표준
어휘가 되었다.
이는 강연 하나가 업계의 담론 구조 자체를 바꾼 드문 사례인데,
그 전환의 핵심은 “RESTful이냐 아니냐”는 존재/부재의 질문을
“레벨 몇이냐”는 정도의 질문으로 바꾼 데 있다.
이 언어적 전환 덕분에 이후 API 설계자들은 완벽한 REST 준수를
목표로 삼지 않고도 “우리는 레벨 2까지 왔고, 레벨 3으로 갈
가치가 있는가”라는 실용적 질문을 던질 수 있게 되었다.
동시에 이는 REST라는 개념이 애초에 가졌던 아키텍처적 엄밀함,
즉 Fielding이 박사 논문에서 제시한 통합된 제약 집합으로서의
REST와는 다른, 좀 더 느슨하고 실무 친화적인 하위 개념으로
재정의되는 계기가 되기도 했다.
오늘날 많은 개발자가 “REST API”라고 부르는 것이 실제로는
Fielding의 원래 정의보다 이 강연이 제시한 레벨 2 수준의 관행을
가리킨다는 점은, 이 강연이 REST라는 용어의 실제 의미를 바꾸어
놓았다는 방증이다.

### 웹이 다른 프로토콜을 흡수한 역사는 이후 API 생태계의 반복되는 패턴을 예고했다

1막에서 다뤄진 “웹이 FTP, Gopher, WAIS, 심지어 SOAP와 XML-RPC의
경쟁자였던 다른 프로토콜들까지 잡아먹었다”는 역사는, 사실 이후
20년간 여러 차례 반복된 패턴의 첫 사례에 불과하다.
GraphQL이 REST의 여러 엔드포인트를 단일 쿼리 언어로 흡수하려
했던 시도, gRPC가 사내 마이크로서비스 통신에서 HTTP/JSON을
대체하려 했던 시도, 그리고 최근 AI 에이전트를 위한 도구 호출
프로토콜들이 REST API를 감싸는 또 다른 추상화 계층으로 등장하는
현상은 모두 “기존 프로토콜의 복잡성을 새로운 통일된 계층으로
흡수하겠다”는 동일한 충동에서 나온다.
Richardson이 그린 “ICN 대 ISH”라는 이중 서사, 즉 기술적으로
우아한 비전과 상업적으로 실용적인 비전이 충돌하다가 결국 하나가
다른 하나를 흡수하는 패턴은, 새로운 통신 계층이 등장할 때마다
반복해서 관찰할 가치가 있는 구조적 렌즈를 제공한다.

### 클라이언트 실측 방법론은 오늘날 API 계약 테스트와 스키마 검증 문화의 선구적 형태다

`launchpadlib`을 통해 서버 설계의 타협을 실측했다는 방법론은,
오늘날 OpenAPI 스펙 기반의 계약 테스트(contract testing)나
소비자 주도 계약(consumer-driven contract) 테스트 같은 관행의
초기 형태로 볼 수 있다.
차이가 있다면, 2008년의 Richardson은 이 실측을 자동화된 테스트
스위트가 아니라 사람이 직접 클라이언트 코드를 작성하며 느끼는
불편함으로 수행했다는 점이다.
오늘날의 계약 테스트 도구들은 이 “불편함을 느끼는 과정”을
자동화해 CI 파이프라인에 넣었지만, 정작 “이 API 설계가 클라이언트
입장에서 자연스러운가”라는 질적 판단은 여전히 자동화하기 어려운
영역으로 남아 있다.
이는 Richardson이 2막에서 보여준 방법론, 즉 실제 사용자 코드의
관점에서 설계를 거꾸로 검증하는 접근이 도구가 아무리 발전해도
사람의 판단을 완전히 대체할 수 없는 이유를 보여주는 사례이기도
하다.
