# 일회용 샌드박스에 버전 관리되는 파일 시스템을 붙이는 법: Tines 3B의 스냅샷과 포인터

원문: [A versioned filesystem for disposable sandboxes](https://www.shayon.dev/post/2026/283/versioned-filesystem-for-disposable-sandboxes/)

GN 토론: <https://news.hada.io/topic?id=35606>

## 소개

2026년 10월 10일 올라온 이 글은 Tines의 3B가 일회용 샌드박스에 붙인 파일
시스템을 설계한 과정을 설명한다. 3B는 워크플로의
모든 단계가 하나의 컴퓨터라는 생각에서 출발한다.
단계의 코드는 사람이 썼든 에이전트가 썼든 새 Linux 샌드박스 안에서
돌고 자격 증명은 프록시로 받는다.
일을 마치면 샌드박스는 버려진다.
이렇게 버려서 남은 상태가 나중에 보안 문제를 일으키지 못하게 한다.

그런데 단계에서 하는 일이 늘면 상태를 둘 곳이 필요하다.
고객들은 저장소를 복제해 분석을 돌리고,
Salesforce 리드의 SQLite 데이터베이스를 두고,
들어온 웹훅을 DuckDB에 저장해 다른 워크플로가 나중에 검색하게 한다.
그래서 단계마다 샌드박스보다 오래 사는 파일 시스템을 주었고
이 파일 시스템이 버전 관리되도록 만들었다.
글쓴이는 이것이 예상보다 훨씬 중요한 것으로 드러났다고 쓴다.
샌드박스 한 번의 실행과 그 실행이 파일에 낸 변화가 데이터베이스
트랜잭션처럼 전부 반영되거나 하나도 반영되지 않는다는 뜻이다.
그 덕분에 라이브 워크플로가 의존하는 데이터를 건드리지 않고
초안 브랜치에서 에이전트와 함께 워크플로를 만들 수 있다.

글에 등장하는 구성 요소는 세 가지다.
샌드박스에서 단계의 코드가 돌고
파일에 대한 모든 조작은 샌드박스 바깥에 있는
작은 gVisor 고퍼(gofer)인 Nest로 간다.
Nest 아래의 Spongeblob은 모든 볼륨을 저장하는 저장 엔진이고
S3가 있으면 복구와 퇴출을 위해 거기에도 복사한다.

## 설계 목표

글쓴이는 코드를 쓰기 전에 시스템이 맞혀야 할 목록을 적었고,
이후의 모든 결정을 그 목록에서 거슬러 올라갈 수 있다고 한다.

| 요구                                 | 이유                                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------- |
| 진짜 POSIX 파일 시스템처럼 동작      | Git, SQLite, 컴파일러, pip는 mmap, fsync, 이름 바꾸기에 기대고 SDK를 쓰지 않는다 |
| 실행하는 기계에 아무것도 남기지 않음 | 다음 단계가 며칠 뒤 다른 곳에서 돌 수 있다                                       |
| 빠른 로컬 경로                       | 128KB 쓰기를 보통 2~4ms 안에 내구성 있게 만들려 했다                             |
| 병렬 쓰기가 서로 망치지 않음         | 같은 볼륨에 쓰는 두 단계가 조용히 덮어쓰면 안 된다                               |
| S3 없이도 동작                       | 3B는 자체 호스팅으로도 돌고 거기에 S3가 항상 있지는 않다                         |
| 단순함 유지                          | 부품마다 충돌 뒤 일관성을 유지할 대상이 늘어난다                                 |

단순함의 구체적인 뜻은 내구성 있는 로그 하나, 디스크마다 소유자 하나,
별도의 데이터베이스나 합의 시스템이 없는 것이다.
위 요구가 강제할 때만 복잡성을 더했다는 것이 글의 태도다.

## 동작 방식

### 단계가 보는 것은 디렉터리 하나다

단계는 Dockerfile에 `VOLUME` 한 줄로 볼륨을 선언하고,
볼륨은 샌드박스 안의 `/storage/<이름>` 디렉터리로 마운트된다.
읽기 전용이나 읽고 쓰기, 브랜치나 한 번의 실행으로 한정하기,
동시 쓰기를 허용하거나 번갈아 쓰기가 선택지다.
단계가 시작하면 그 실행 동안 볼륨의 한 버전에 고정된다.

샌드박스는 gVisor이고 `/storage`에 닿는 모든 시스템 호출은 Nest로 넘어간다.
FUSE 파일 시스템을 쓸 수도 있었지만 gVisor가 이미 파일 조작을 고퍼로 보내므로
자체 고퍼를 확장하면 중간 계층이 없다.
또 Nest가 진짜 파일 디스크립터를 샌드박스에 건네 읽기와 쓰기가
FUSE 데몬을 거치지 않고 로컬 파일에 바로 닿게 할 수 있다.

### 파일은 열 때 통째로 로컬에 복사된다

볼륨을 열어도 내려받지 않는다.
프로그램이 디렉터리 트리를 순회할 때 Nest가 필요한 만큼만 그때그때 찾는다.
프로그램이 파일을 열면
Nest가 호스트 메모리의 임시 파일로 복사해 파일 디스크립터를 건네고,
그 뒤의 읽기와 쓰기와 mmap은 모두 메모리 속도의 로컬 파일에 닿는다.
열기와 이름 바꾸기와 목록 조회 같은 제어 조작만 샌드박스 경계를 넘는다.

글쓴이는 파일을 열 때 통째로 복사하는 것이 단점임을 인정한다.
모든 파일을 요청이 올 때마다 가져오게도 해 봤지만
실제 프로그램은 같은 페이지를 계속 다시 읽어서
커널 페이지 캐시가 프록시를 계속 이겼다고 한다.
그래서 작은 파일은 미리 복사해 빠른 로컬 경로를 유지하고
큰 파일은 복사를 건너뛰어 프로그램이 건드리는
블록만 가져오는 분할을 실험 중이다.

Nest는 생성과 이름 바꾸기와 삭제, 파일에서 쓰인 부분을 추적하고
열 때 파일 청크의 지문을 떠서 공유 mmap을 통한 변경도 잡는다.
단계 안의 `fsync`는 로컬 복사본만 비우고 내구성은 단계가 끝날 때 생긴다.
샌드박스가 죽거나 메모리가 부족하거나 종료 코드 1로 끝나면
변경은 버려지고 볼륨은 움직이지 않는다.

### 단계 하나가 커밋 하나다

볼륨은 스냅샷의 열과 현재 스냅샷을 가리키는 작은 포인터 하나이고
스냅샷은 한 번 쓰이면 바뀌지 않는다.
단계가 성공하면 Nest가 바뀐 것을 올리고
Spongeblob이 현재 스냅샷 위에 새 스냅샷을 만들어 포인터를 앞으로 옮긴다.
Git처럼 커밋이 트리 전체의 상태를 기록하되
성공한 단계마다 자동으로 하나씩 생기는 셈이다.
다중 버전 동시성 제어(MVCC)도 빌려 왔다.
누군가 43번 스냅샷을 게시하는 동안 42번을 읽던 쪽은 계속 42번을 읽고
읽는 쪽과 쓰는 쪽은 서로 기다리지 않는다.

모든 버전을 전체 복사로 두면 비싸므로 쓰기 시 복사(COW)를 쓴다.
새 스냅샷은 트리에서 바뀐 부분만 다시 쓰므로 거대한 볼륨에서
파일 하나를 고쳐도 작은 노드 몇 개만 쓰고 나머지는 공유한다.
`events.db`를 바꾸면 새 잎, 새 `/data` 노드,
새 뿌리가 쓰이고 나머지는 42번 스냅샷과 공유된다.

### 동시에 쓰면 포인터의 비교-교환이 가른다

게시는 포인터에 대한 비교-교환(compare-and-swap)이다.
42에서 43으로 옮기되 아직 42일 때만 옮기라는 뜻이다.
다른 단계가 먼저 도착했으면 두 단계가 바꾼 것을 비교한다.
서로 다른 파일의 변경은 새 스냅샷 위에 다시 얹고
같은 파일의 변경은 경로를 알려 주는 충돌로 실패한다.
글쓴이는 이 의미를 아직 다듬는 중이며 곧 더 나올 것이라고 적는다.

### 포크는 포인터 하나다

스냅샷이 바뀌지 않으므로 포크는 같은 스냅샷을 가리키는 두 번째 포인터일 뿐이고
기가바이트 데이터가 든 볼륨도 빈 볼륨만큼 빨리 포크된다.
지금은 새 초안 브랜치가 비어 있거나 라이브에서 시작할 수 있다.
곧 자신이 갈라져 나온 브랜치에서도 포크할 수 있게 되며,
포크한 뒤에는 두 포인터가 따로 움직인다.
브랜치 사이의 파일은 병합하지 않는다.
각 브랜치가 자기 복사본으로 일하고
파일 시스템을 위한 3-way 병합을 새로 만들고 싶지 않았기 때문이라고 한다.

### Spongeblob은 팩 파일 하나가 곧 로그다

Nest 아래의 Spongeblob은 Rust로 쓴 저장 엔진이고 두 부분으로 나뉜다.
하나는 불변 객체와 버전 있는 트리와 포인터만 아는 임베디드 데이터베이스다.
다른 하나는 그것을 이 트리는 파일 시스템이고
이 두 쓰기는 충돌한다는 제품 개념으로 바꾸는 서비스다.
한 프로세스만 자기 디스크를 소유하므로 쓰기 사이의 조율이 없고
그 대가로 배포 때 이전 프로세스가 물러나고
새 프로세스가 같은 디스크를 다시 여는 짧은 인수인계를 치른다.
스택마다 자기 Spongeblob과 자기 디스크를 두어 바쁜
워크로드가 다른 쪽의 읽기와 쓰기를 끌어내리지 못하게 한다.
글쓴이가 밝힌 운영 수치는 보통의 읽기가 약 1ms, 쓰기가 2ms 미만이다.

쓰기가 내구성을 얻는 길은 이렇다.
Nest가 단계의 변경을 게시하면
Spongeblob이 새 데이터를 디스크의 큰 파일인 팩의 끝에 붙이고
`fsync`를 부르며 쓰기는 끝난다.
비슷한 때 도착한 다른 단계의 쓰기는 같은 `fsync`를 공유하는 그룹 커밋이어서
내구성의 비용이 쓰기 수가 아니라 시간을 따른다.
별도의 저널 파일은 없다.
각 쓰기가 데이터와 작은 저널 기록으로 같은 `fsync` 아래 팩에 쓰이므로
팩이 곧 로그다.

팩에 든 것이 어디에 있는지 답하는 것은 LSM 트리인 색인이다.
RocksDB의 블롭 파일처럼 큰 바이트는 트리 밖에 두고
색인에는 팩을 가리키는 작은 항목만 둬서 병합이 파일 데이터를 옮기지 않는다.
글쓴이는 RocksDB와 WiscKey 논문에서 많이 배웠다고 밝힌다.
그래도 직접 쓴 것은 자기 데이터에 맞춘 형식과 한 프로세스가 저널과
색인과 백그라운드 작업을 함께 예산으로 관리하는 구조를 원했기 때문이다.
스냅샷 트리와 포크의 기반이 되는 요소와 임대, 충돌 검사,
이미지 청크 저장은 어느 키-값 저장소도 주지 않아 어차피 직접 만들어야 했다.

### 뜨거운 데이터는 디스크에, 차가운 데이터는 S3에 둔다

팩은 가득 차거나 30초가 지날 때까지 추가를 받다가 봉인되어 다시는 바뀌지 않는다.
S3가 설정되어 있으면 봉인된 팩이 백그라운드로 올라가고
복구 체크포인트에 기록된다.
S3에 안전하게 올라간 팩은 퇴출 후보가 된다.
디스크가 차서 상한선을 넘으면 한동안 읽히지 않은 팩의 로컬 복사본을 버린다.
퇴출된 팩을 나중에 읽으면 S3에서 필요할 때 가져온다.
거의 죽은 팩은 살아 있는 부분을 새 팩으로 옮기고,
완전히 죽은 팩은 체크포인트가 더 필요하지 않을 때 지운다.
옮기는 기준이 절반 이상이 죽은 팩이므로
파일 데이터는 평생 많아야 약 두 번 쓰인다.

S3에 곧바로 쓰지 않는 이유도 글에 있다.
첫째는 자체 호스팅 요구이고 둘째는 지연이다.
Nest가 페이지 수준의 읽기와 쓰기를 흡수하므로
Spongeblob은 열 때의 읽기 한 번과 끝날 때의 게시 한 번만 본다.
둘 다 로컬 디스크에서 1~2ms 안에 나오는데
AWS의 안내는 작은 S3 요청을 수십 ms로 잡는다.
셋째는 비용이다.
모든 쓰기를 S3로 보내면
지금 S3 요청에 쓰는 비용의 몇 배가 들고 트래픽을 따라 늘어난다.

## 보장하는 것

### 내구성

쓰기는 그룹의 `fsync`가 디스크에서 돌아오면 내구성이 생긴다.
클라우드에서는 이 디스크가 EBS 볼륨이어서 AWS가 가용 영역 안에서
복제하므로 충돌과 재시작과 배포가 확인된 쓰기를 잃게 하지 않는다.
볼륨 자체를 잃는 경우는 EBS가 막지 못하고 S3가 보루다.
봉인된 팩과 복구 체크포인트를 백그라운드로 S3에 복사하므로
볼륨을 잃으면 마지막 체크포인트에서 다시 만든다.
그 체크포인트는 마지막 쓰기에서 약 1분 이내로 유지한다.
S3 없이 자체 호스팅한 설치에서는 디스크가 주는 만큼만 내구성이 있다.

### 일관성

모든 단계는 시작부터 끝까지 한 스냅샷을 읽는다.
한 프로세스가 디스크 하나를 소유하고
모든 게시가 포인터의 비교-교환이므로 게시가 순서대로 일어난다.
따라서
브랜치를 읽는 다른 단계나 UI나 에이전트는 단계의 변경 전체를
보거나 하나도 보지 못하고 반쯤 쓰인 파일을 보지 않는다.

### 가용성

한 프로세스가 디스크를 소유하므로 쓰는 쪽의 조율이 없고
모든 것이 로컬 디스크에서 나온다.
이것은 배포 때 이전 프로세스가 비우고
디스크를 새 프로세스에 넘길 때 보이며 보통 1~2초 걸린다.
Spongeblob 앞의 작은 라우터가 어느 프로세스가 디스크를 소유하는지 확인해 새
프로세스가 준비되자마자 트래픽을 옮기고
그 틈에 도착한 요청은 1초 뒤에 다시 시도하라는 빠른 응답을 받는다.

## 트레이드오프

### 로그의 끝을 어디에 두는가가 마지막 남은 큰 선택이다

볼륨 손실 구간은 로그의 끝을 한 디스크에 두는 데서
나오고 설계에서 가장 바꾸기 쉬운 부분이기도 하다.
저널만이 쓰기가 일어났는지를 결정하고
그 위의 색인과 스냅샷과 포크는 모두 저널에서 파생되므로,
로그의 끝이 있는 곳을 옮겨도 나머지를 다시 설계하지 않는다고 글쓴이는 말한다.

선택지는 두 가지다.
꼬리만 S3 Express One Zone에 동기적으로 쓰는 방법은 커밋당 약
7~10ms가 들어 쓰기 예산 밖이지만 S3 Standard보다는 훨씬 가깝다.
대신 볼륨 손실 구간이 닫히고 새 소유자가 이전 디스크에 의존하지 않게 되며
데이터는 로컬 디스크에 그대로 남는다.
다만 S3 Express는 단일 가용 영역이어서
EBS처럼 영역 전체를 잃는 경우는 막지 못한다.
다른 선택지는 몇 대의 기계에 걸친 쿼럼 기반 로그를 직접 만드는 것으로,
커밋은 빠르게 유지되지만 합의 시스템을 직접 운영해야 한다.
글쓴이는 이것을 누가 관리하고 싶겠느냐는 말로 꺼린다.

### 디스크 소유자를 하나로 두면 인수인계의 틈이 생긴다

한 프로세스가 디스크를 소유하면 조율이 필요 없고 일관성의 이야기가 단순해진다.
그 대가는 배포 때의 1~2초 틈이다.
이 틈은 쓰기를 잃는 것이 아니라 잠시 거부하는 것이어서
클라이언트가 재시도하면 된다.
하지만 재시도하지 않는 호출자가 있으면 실패가 보인다.

### 파일 전체를 복사하는 열기와 블록 단위 가져오기

작은 파일은 통째로 복사해 로컬 속도를 얻고
큰 파일은 블록만 가져와 열기를 싸게 만드는 분할은 아직 실험이다.
커널 페이지 캐시가 프록시를 이긴 경험에서 나온 결정이어서,
프로그램이 같은 페이지를 반복해서 읽는 방식을 가정한다.
이 문서의 추측으로는 큰 파일의 접근 패턴이 순차적이면
블록 단위 가져오기가 이기고 같은 곳을 반복해서 읽으면 지는 식으로 갈릴 수 있다.
글은 이 분할선을 정하지 않았다.

### 병합하지 않는 대신 포크가 싸다

브랜치 사이의 파일을 병합하지 않는 것은 병합 논리가 틀릴 여지를
없애는 대신 초안의 결과를 라이브에 합치는 길이 없다는 뜻이다.
이 문서가 확인한 글에는 초안의 결과를 라이브로 반영하는 방법이 나와 있지 않다.

## 함정

`fsync`는 단계 안에서 로컬 복사본만 비운다.
SQLite처럼 `fsync`에 기대는 프로그램도 단계가 끝나기 전에는 내구성이 없고
단계가 실패하면 모든 쓰기가 버려진다.

종료 코드 1로 끝난 단계는 아무것도 게시하지 않는다.
부분 성공으로 얻은 파일이 필요한 워크플로는 이 모델에 맞지 않는다.

같은 파일을 두 단계가 바꾸면 충돌로 실패한다.
다른 파일이면 다시 얹히므로,
한 DuckDB나 SQLite 파일을 여러 단계가 동시에 쓰는 설계는 충돌을 낳는다.

팩이 퇴출되면 처음 읽는 요청이 S3까지 가므로
오래된 스냅샷을 여는 요청은 느릴 수 있다.

S3 없이 자체 호스팅하면 퇴출할 곳이 없어서 모든 팩이 디스크에 남는다.
죽은 팩을 회수해도 부족하면 디스크를 키워야 한다.

## 확인하기

글의 핵심은 스냅샷이 불변이고 포인터만 비교-교환으로 움직이며
포크는 포인터 하나라는 세 가지다.
아래 예제는 이 세 가지를 쓰기 시 복사 트리 없이 흉내 낸다.
스냅샷마다 전체 사상을 복사하므로 공유 구조의 비용은 재현하지 않고
충돌 판정과 포크의 의미만 확인한다.

```python
"""스냅샷 트리, 포인터 compare-and-swap, 충돌 판정을 흉내 내는 최소 예제."""
from dataclasses import dataclass, field


@dataclass(frozen=True)
class Snapshot:
    """불변 스냅샷. 경로에서 파일 내용으로 가는 사상을 통째로 들고 있다."""
    files: tuple  # ((경로, 내용), ...) 정렬된 튜플
    parent: int | None = None

    def get(self, path):
        return dict(self.files).get(path)


@dataclass
class Volume:
    snapshots: list = field(default_factory=lambda: [Snapshot(())])
    branches: dict = field(default_factory=lambda: {"live": 0})

    def head(self, branch):
        return self.branches[branch]

    def fork(self, new, source):
        """포크는 같은 스냅샷을 가리키는 포인터 하나를 더 만드는 일이다."""
        self.branches[new] = self.branches[source]

    def publish(self, branch, base, changes):
        """base에서 시작한 한 번의 실행이 바꾼 파일(changes)을 한 번에 반영한다."""
        cur = self.branches[branch]
        if cur != base:
            # 포인터가 앞서 나갔다: 두 실행이 바꾼 파일이 겹치면 충돌, 아니면 위에 다시 얹는다
            theirs = self._diff(base, cur)
            clash = sorted(set(theirs) & set(changes))
            if clash:
                raise RuntimeError(f"충돌: {clash}")
        merged = dict(self.snapshots[cur].files)
        merged.update(changes)
        self.snapshots.append(Snapshot(tuple(sorted(merged.items())), parent=cur))
        self.branches[branch] = len(self.snapshots) - 1  # 포인터 한 번 옮기기
        return self.branches[branch]

    def _diff(self, a, b):
        fa, fb = dict(self.snapshots[a].files), dict(self.snapshots[b].files)
        return {p for p in set(fa) | set(fb) if fa.get(p) != fb.get(p)}


if __name__ == "__main__":
    v = Volume()
    base = v.head("live")
    print("A가 events.db를 쓴다:", v.publish("live", base, {"events.db": "v1"}))
    try:
        v.publish("live", base, {"events.db": "other"})
    except RuntimeError as e:
        print("B가 같은 파일을 쓴다:", e)
    print("B가 다른 파일을 쓴다:", v.publish("live", base, {"notes.txt": "hi"}))
    v.fork("draft", "live")
    v.publish("draft", v.head("draft"), {"events.db": "draft-only"})
    print("live의 events.db:", v.snapshots[v.head("live")].get("events.db"))
    print("draft의 events.db:", v.snapshots[v.head("draft")].get("events.db"))
```

이 문서가 실행한 결과는 이렇다.
A의 게시는 스냅샷 1을 만들고,
같은 파일을 쓴 B는 `충돌: ['events.db']`로 실패한다.
다른 파일을 쓴 B는 성공해 스냅샷 2가 되고
포크한 초안이 `events.db`를 바꿔도 라이브의 값은 `v1`로 남는다.

실제 시스템을 확인하려면 자신의 워크로드로 두 가지를 재 본다.
작은 쓰기를 `fsync`와 함께 반복해 단계 안의 지연이 예산 안인지,
큰 파일을 열 때 통째로 복사하는 비용이
단계 시작 시간에 얼마나 더해지는지를 잰다.

## 체크리스트

- 단계가 실패했을 때 파일 변경이 모두 버려져도 되는 워크플로인가.
- 한 파일을 여러 단계가 동시에 쓰는 설계가 없는가.
- 큰 파일이 많다면 열 때 전체 복사가 시작 시간 예산에 들어가는가.
- 자체 호스팅이라면 S3 없이 디스크 크기를 키우는 절차가 있는가.
- 배포 때 1~2초의 거부를 호출자가 재시도하는가.
- 로그의 끝을 한 디스크에 둔 설계에서 볼륨 손실 구간이 허용되는가.

## 기억할 원칙

### 상태를 불변 값과 움직이는 포인터로 나누면 기능이 파생된다

글쓴이는 마지막에 몇 가지 원시 요소를 든다.
스냅샷은 바뀌지 않고 포인터는 비교-교환으로만 움직이며
포크는 포인터 하나이고 데이터는 내용으로 이름이 붙는다.
그리고 이 요소들 위에서 많은 제품 기능이 따로 만들지 않고도 나왔다고 정리한다.
초안이 라이브를 건드릴 수 없는 것은 다른 포인터이기 때문이고,
단계가 커밋하거나 아무것도 남기지 않는 것은
게시가 마지막의 교환 한 번이기 때문이다.
이 문서의 읽기로는 이 설계에서 배울 점이 파일 시스템의 세부보다 구조에 있다.
바뀌지 않는 값과 한 곳에서만 일어나는 갱신을 나누면
일관성의 규칙이 하나로 줄어든다.
