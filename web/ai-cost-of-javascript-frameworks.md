# 에이전트로 같은 앱을 12가지 프레임워크로 만들어 보니, 비용 차이는 2배 안팎이었다

원문: [The AI cost of JavaScript frameworks | Read the Tea Leaves](https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/)

HN 토론: <https://news.ycombinator.com/item?id=50323088> (468점, 387개 댓글)

GN 토론: <https://news.hada.io/topic?id=36393>

## 요약

Nolan Lawson이 2026년 10월 28일에 쓴 글이다.
그는 웹 개발 커뮤니티의 선택이 분위기(vibes)에 좌우된다고 보고,
코딩 에이전트 시대에도 프레임워크가 에이전트에게 더 낫다는 주장이 근거 없이
나온다고 지적한다.
그래서 직접 벤치마크를 만들었다.

설계는 단순하다.
PokéAPI를 쓰는 작고 사소하지 않은 Pokémon 앱을 설계하고,
에이전트에게 특정 JavaScript 프레임워크나 메타 프레임워크로 만들게 한다.
결과물은 에이전트가 속이지 못하도록 명세 적합성 테스트 모음으로 검사하고,
개발 시간, 토큰, 코드 줄 수, Lighthouse의 성능과 접근성 점수로 평가한다.
에이전트는 Opus 5.5(높은 노력 설정)를 쓰고 프레임워크마다 5번씩 돌려
중앙값을 보고했다.
각 프레임워크의 공식 MCP나 스킬이 있으면 설치해 주었고,
SSR과 CSR 같은 구조는 지정하지 않았으며, 성능을 최적화하라는 지시도 주지 않았다.

비용은 중앙값 기준으로 Hono+htmx가 2.67달러, Astro가 2.76달러, Nuxt가 2.82달러,
Vanilla가 2.98달러, Next.js가 3.14달러로 낮은 쪽이었고, SvelteKit 4.28달러,
Gracile+Lit 4.65달러, Angular 4.97달러가 높은 쪽이었다.
이 달러 수치는 Claude Code가 보고한 API 가격이며,
Lawson은 월 100달러 Max 요금제를 쓰므로 실제 지출이 아니라고 밝힌다.
시간은 Astro 8.2분이 가장 짧고 Angular 17.2분이 가장 길었다.
토큰은 Nuxt 385만 개가 가장 적고 Angular 976만 개가 가장 많았다.

공식 MCP나 스킬을 설치해 주었지만 에이전트가 쓴 정도는 제각각이었다.
Hono+htmx와 React Router의 에이전트는 5번 모두 스킬을 썼고,
Nuxt의 MCP는 한 번도 쓰이지 않았으며,
Next.js의 스킬 파일은 5번 중 1번만 읽혔다.

품질 지표에서 Lighthouse의 성능, 접근성,
누적 레이아웃 이동(CLS)은 거의 포화되었다.
성능은 Vanilla 97점에서 여러 프레임워크의 100점까지이고,
접근성은 전부 100점이다.
차이가 드러나는 지표는 전송된 JavaScript 용량이다.
Astro는 0KiB, Vanilla 7KiB, Hono+htmx 18KiB, Nuxt 84KiB, React Router 115KiB,
Next.js 142KiB였다.
코드 줄 수는 Hono+htmx 1,370줄에서 Angular 2,009줄까지였다.
Lawson은 Hono+htmx가 Angular와 거의 같은 일을 약 70%의 코드로 하고 더 빠르기까지
하다고 쓴다.

총 차단 시간(TBT, Total Blocking Time)은 Astro, Gracile+Lit, Hono+htmx,
SvelteKit, Vanilla가 0ms이고 Nuxt 40ms, Next.js 71ms, Angular 103ms였다.
최대 콘텐츠 페인트(LCP, Largest Contentful Paint)의 중앙값은 Astro 810ms에서
Next.js 2,090ms까지 벌어졌다.
Lawson은 LCP가 지표 자체의 변동이 크지만 대체로 JavaScript 번들 크기와 함께
움직인다고 쓰고, SPA이면서 MPA 계열처럼 나온 Qwik을 예외로 든다.
측정은 2025년형 Framework 13 노트북의 Ubuntu 24.04에서
CPU 4배 제한과 “Slow 4G” 네트워크 제한을 걸고 모바일 설정으로만 했으며,
보고한 값은 홈페이지 결과뿐이다.

글은 결론에서 이 벤치마크가 어떤 프레임워크를 고를지 정해 주는 결정판이
아니라고 말한다.
목적은 AI 코딩 시대에도 분위기가 아니라 증거로 결정할 수 있음을 보이는
것이라고 한다.
그는 현재의 MCP와 스킬이 도움보다 해를 끼치고 있을지도 모른다는 강한
의심을 적는다.
벤치마크 코드 자체도 대체로 바이브 코딩으로 만들었고 직접 검토했으므로
오류가 있다면 자신의 것이라고 덧붙인다.

## 분석

### 글의 핵심 주장은 결론이 아니라 방법이다

Lawson은 어느 프레임워크가 이긴다고 주장하지 않는다.
글이 내세우는 것은 에이전트에게 같은 명세를 주고 결과를 측정하는 방법이
가능하다는 점이다.
그래서 이 글은 순위표보다 설계 선택으로 읽는 것이 맞다.
프레임워크 도구를 모두 켜 준 점, 구조를 지정하지 않은 점,
정적 HTML 미리 생성을 금지하고 명세 적합성 검사에 접근성 트리를 쓴 점이
그 선택이다.

### 명세는 구조를 열어 두고 검증은 엄격하게 닫았다

글이 링크한 벤치마크 명세서는 프레임워크 이름만 정해 주고 렌더링 방식, 라우팅,
데이터 가져오기, 상태 관리, 프로젝트 구조는 에이전트에게 맡긴다.
에이전트에게는 `npm test`가 통과할 때까지 질문 없이 혼자 일하라고
지시한다.[^spec]
반면 검증은 촘촘하다.
앱은 API 데이터를 빌드 시점에 가져오거나 미리 생성하거나 포함해서는 안 되고
요청 시점에 HTTP로 받아야 한다.
테스트는 정상 API로 빌드한 앱을 Pokémon 하나가 더 있는 다른 데이터의 API에 붙여
한 번 더 돌려서 이를 강제한다.[^spec]
테스트는 HTML 구조가 아니라 역할, 접근 가능한 이름, 텍스트,
URL을 검사한다.[^spec]
Lawson이 글에서 말한 정적 HTML 미리 생성 금지와 접근성 트리 기준 검사가
명세서의 이 조항들에 해당한다.[^spec]

앱의 범위도 글의 “작은” 앱이라는 표현보다 넓다.
명세서는 1,025종 전부를 48개씩 나눠 보여 주는 목록, 입력하는 즉시 갱신되는
검색, 유형과 세대 필터, 열마다 정렬되는 기술 표, 게임 선택 상자를 요구한다.
다만 필터 상태는 URL 쿼리에 두라고 정해 둔다.[^spec]
이 설계는 페이지마다 서버가 응답하는 구조와 잘 맞는다.
이것은 명세서를 읽고 내린 추정이며, 명세서 자체가 어느 구조를 선호한다고
적은 것은 아니다.

### 도구를 설치해도 에이전트가 쓰는 정도는 제각각이었다

아래 표는 글의 도구 사용 표에 비용 중앙값을 붙인 것이다.

| 프레임워크     | 설치한 도구                        | 에이전트의 사용                       | 비용 중앙값 |
| -------------- | ---------------------------------- | ------------------------------------- | ----------- |
| Hono+htmx      | Hono skills                        | 스킬 도구 5/5                         | 2.67달러    |
| Astro          | Astro MCP 서버                     | MCP 2/5                               | 2.76달러    |
| Nuxt           | Nuxt MCP                           | 한 번도 쓰지 않음                     | 2.82달러    |
| Vanilla        | 없음                               | 해당 없음                             | 2.98달러    |
| Next.js        | next-devtools-mcp, next-dev-loop   | 스킬 파일 1/5, AGENTS.md 2/5          | 3.14달러    |
| Qwik           | 없음                               | 해당 없음                             | 3.27달러    |
| TanStack Start | 없음                               | `node_modules`의 스킬 파일을 2/5 발견 | 3.54달러    |
| SolidStart     | 없음                               | 해당 없음                             | 3.79달러    |
| React Router   | React Router 스킬                  | 스킬 도구 5/5, 스킬 파일 5/5          | 3.81달러    |
| SvelteKit      | Svelte Claude Code 플러그인        | MCP 5/5                               | 4.28달러    |
| Gracile+Lit    | 없음                               | 해당 없음                             | 4.65달러    |
| Angular        | Angular MCP, Angular 에이전트 스킬 | MCP 3/5, 스킬 도구 4/5, 스킬 파일 2/5 | 4.97달러    |

도구를 5번 모두 쓴 세 프레임워크는 가장 싼 쪽(Hono+htmx),
아홉 번째(React Router),
열 번째(SvelteKit)에 흩어져 있다.
한 번도 쓰이지 않은 Nuxt의 MCP는 세 번째로 싼 비용과 가장 적은 토큰에 공존한다.
설치한 도구도 사용 기록도 없는 네 조합은 2.98달러에서 4.65달러까지 퍼져 있다.
이 표에서 도구의 사용 정도와 비용 사이에 관계는 보이지 않는다.
다만 같은 프레임워크를 도구를 쓸 때와 쓰지 않을 때로 나눠 돌린 비교가 없으므로,
관계가 없다는 결론도 있다는 결론도 이 데이터로는 낼 수 없다.
Lawson도 개선 방법의 하나로 MCP와 스킬을 쓰는 경우와 쓰지 않는 경우를
비교하는 것을 든다.

### 아키텍처를 지정하지 않았으므로 프레임워크 이름이 구조를 보장하지 않는다

에이전트에게 SSR과 CSR 중 무엇을 쓸지 정해 주지 않은 결과가 표에 섞여 있다.
Gracile+Lit의 에이전트는 두 번의 실행에서 Lit를 쓰지 않았다.
Vanilla는 Vite만 쓰라는 지시를 받았는데 5번 모두 SPA를 골랐다.
Qwik은 클라이언트 라우팅을 쓰는 SPA인데도 MPA 계열처럼 낮은 LCP를 냈다.
Angular의 두 번 실패는 에이전트가 SSR 앱을 만들고 localhost 외의 접속을
거부하게 한 탓이다.
명세서는 역방향 프록시가 HTTPS, HTTP/2, 압축을 맡는다고 가정하라고
적는다.[^spec]
그러므로 표의 한 줄은 “그 프레임워크”의 결과라기보다
“그 프레임워크로 에이전트가 고른 구조”의 결과다.
Next.js의 LCP 범위가 1,028ms에서 2,187ms로 넓은 것은
한 앱이 이미지 지연 로딩을 하지 않았기 때문이라고 Lawson이 설명한다.
Astro와 Vanilla의 큰 변동은 우선순위나 LCP 계산의 특성 탓으로 보인다고 한다.

### 비용 차이는 크지 않고 변동은 크다

중앙값의 최고와 최저는 4.97달러와 2.67달러로 약 1.9배다.
시간은 17.2분과 8.2분으로 약 2.1배, 토큰은 976만 개와 385만 개로 약 2.5배다.
반면 같은 프레임워크의 5번 실행 사이 범위가 넓다.
Hono+htmx의 비용은 2.23달러에서 3.19달러이고, Nuxt는 2.39달러에서 4.25달러다.
Lawson 자신이 React Router의 중앙값이 Hono+htmx보다 약 1달러 나쁘지만 React
Router의 가장 싼 실행(2.82달러)이 Hono+htmx의 가장 비싼 실행(3.19달러)보다
싸다고 적는다.
따라서 중앙값 순위의 한 칸 차이는 신뢰하기 어렵고,
믿을 만한 것은 그가 짚은 몇 가지 뚜렷한 패턴이다.

시간도 마찬가지다.
Nuxt의 시간은 중앙값 9.0분인데 가장 오래 걸린 실행은 17.6분으로,
Angular의 중앙값(17.2분)과 같은 수준이다.
Vanilla도 6.9분에서 18.6분까지 벌어진다.
Lawson은 에이전트가 이상한 곳으로 빠져 토큰을 낭비하는 일이
프레임워크의 잘못이 아니어도 일어난다고 쓴다.

### 비싼 쪽의 이유는 프레임워크의 성질이 아니라 모델이 아는 것의 양이다

Lawson이 든 비싼 프레임워크의 원인은 서로 다르다.
SvelteKit은 에이전트가 매번 SvelteKit v3 마이그레이션 안내서(migration guide)를
읽었는데, 너무 새로워서 Opus 5.5의 학습 데이터에 없었을 가능성이 있다고 한다.
Gracile은 에이전트가 프레임워크를 잘 몰라 저장소를 복제하거나 node_modules의
컴파일된 소스를 읽었다고 한다.
Angular는 총 코드 크기에 따라 달라진 것으로 보인다고 한다.
앞의 둘은 모델의 지식 문제이고 셋째는 코드 양의 문제다.
그러므로 비용 순위에는 프레임워크의 설계 품질과 학습 데이터의
최신성이 섞여 있다.

Vanilla도 이 관점에서 읽어야 한다.
Vanilla의 비용(2.98달러)은 12개 중 네 번째로 싸고,
Hono+htmx, Astro, Nuxt 세 개만 더 쌌다.
Lawson은 이 결과가 프레임워크가 아예 없는 것보다는 어떤 프레임워크든 있는 편이
나을 수 있음을 보여 준다고 해석한다.
그러나 Vanilla 조건은 “Vite로 UI 프레임워크 없이”라는 한 줄의 지시이고,
이 지시 아래에서 에이전트가 무엇을 직접 만들었는지는 글에 없다.

### 성능 지표는 작은 콘텐츠 앱에서 거의 의미가 없고, 용량이 남는다

Lighthouse 성능과 접근성이 포화되었으므로 이 두 지표로는 프레임워크를
가를 수 없다.
Lawson이 믿을 만하다고 본 지표는 JavaScript 전송 용량이고,
이것이 클라이언트 쪽 프레임워크의 크기를 거의 그대로 반영한다.
LCP는 지표 자체의 변동이 크지만 대체로 JavaScript 번들 크기와 함께 움직인다고
그는 설명한다.
Lighthouse와 Core Web Vitals가 SPA에 불리하게 기울어 있으므로 MPA 계열이
앞서리라 짐작했다고 글에서 인정한다.

### 비용과 사용자에게 가는 값은 따로 움직인다

글에 실린 12개 조합의 중앙값을 순위로 바꿔 Spearman 순위 상관계수를 계산하면
두 묶음이 갈린다.
이 계산은 이 문서의 것이며 글에 없다.
비용은 토큰(0.97), 시간(0.90), 코드 줄 수(0.83)와 강하게 함께 움직인다.
반면 JavaScript 전송 용량(0.28), TBT(0.25), LCP(0.22)와는 약하게만 움직인다.
용량은 LCP(0.88), TBT(0.81)와 강하게 움직인다.
조합이 12개뿐이므로 이 숫자는 방향을 보여 줄 뿐 정밀한 값이 아니다.

이 결과가 뜻하는 것은 하나다.
에이전트가 싸게 만든 프레임워크와 사용자에게 가볍게 전달되는 프레임워크는
같은 목록이 아니다.
Next.js(142KiB)는 JavaScript 용량이 가장 큰데 비용은 중간(3.14달러)이고,
SvelteKit은 용량이 작은 쪽(36KiB)인데 비용은 셋째로 비싸다(4.28달러).
Angular는 93KiB로 용량이 중간인데 TBT가 가장 크고(103ms) 비용도 가장 높다.
비용 하나로 프레임워크를 고르면 사용자에게 가는 값을 놓치고,
그 반대도 마찬가지다.
비용 중앙값을 토큰 중앙값으로 나눈 값도 토큰 100만 개당 0.50달러에서
0.73달러까지 벌어지는데, 글은 이유를 설명하지 않는다.

### TBT와 LCP가 재는 것은 사용자의 체감 전체가 아니다

TBT는 첫 콘텐츠 렌더링(FCP) 이후 메인 스레드에서 50ms를 넘긴 작업(Long Task)마다
50ms를 넘은 부분을 모두 더한 값이다.[^tbt]
이 값은 입력에 대한 응답성(INP, Interaction to Next Paint)을 점검하는
실험실 지표로 쓰이지만, 사용자가 상호작용하지 않으면 실제로는 문제가 없는
곳에서도
문제를 가리킬 수 있다.[^tbt]
그러므로 이 벤치마크의 TBT는 첫 로딩 동안의 차단만 재고,
앱을 쓰는 동안의 반응은 재지 않는다.
Lawson은 앱 안의 성능 지표를 넣을까 생각했지만, 복잡도와 변동이 늘고
업계 표준이 아니라 직접 만든 지표가 된다는 이유로 접었다고 쓴다.

성능 점수가 포화된 이유는 점수 계산 방식에서 짐작할 수 있다.
Lighthouse 문서는 Lighthouse 10의 성능 점수를 FCP 10%, Speed Index 10%,
LCP 25%, TBT 30%, CLS 25%의 가중 평균으로 적는다.[^lh-scoring]
각 지표 값은 HTTP Archive의 실제 사이트 분포로 만든 곡선에서 0~100점으로
바뀌고, 상위 사이트의 LCP인 약 1,220ms가 99점으로 대응한다.[^lh-scoring]
글은 쓴 Lighthouse 버전을 밝히지 않으므로 이 가중치가 그대로 적용되었는지는
확인할 수 없다.
다만 Vanilla만 CLS가 0.111이고 성능 점수도 97점으로 가장 낮다는 사실은
CLS의 가중치가 크다는 점과 어긋나지 않는다.
이것은 추정이며, 글은 Vanilla의 CLS 원인을 설명하지 않는다.

### 증거와 분위기는 이분법이 아니다

### 12개 조합은 같은 층위가 아니다

### 실행 5번은 작은 표본이고 일부는 3번이다

정정 자체는 정직하지만, 표본이 작아 순위 한 칸의 차이를 말할 근거가 약하다는
점을 다시 보여 준다.
Angular의 두 번 실패는 SSR로 만든 앱이 localhost 외의 접속을 거부했기 때문이며,

다섯 번의 실행 모두가 말하는 것은 아니다.

표본이 늘면 더 넓어질 가능성이 크다.

“망가져 있다”도 “큰 앱에서는 다르다”도 이 글의 데이터 밖에 있다.

### 모델 하나와 시점 하나의 결과다

실험은 Opus 5.5의 높은 노력 설정 하나로 했고,

적는다.

주장했다.[^oatmealsnap]
글은 Vanilla에서 에이전트가 직접 만든 추상화의 양과 모양을 보고하지 않으므로,
두 의견 어느 쪽도 이 데이터로는 검증되지 않는다.

### 코드 줄 수가 가장 좁게 벌어지는 지표이고, 무엇을 센 것인지 글에 없다

12개 조합에서 최고와 최저의 비율은 비용 약 1.9배, 시간 약 2.1배,

Lawson이 이 지표를 유지 보수성 항목 아래 둔 것은 이 해석을 전제로 한 배치다.

### 글의 전제는 코드를 직접 치지 않는 개발자다

Lawson은 에이전트 시대에 개발자가 더는 코드를 손으로 치지 않는다고 전제한다.

불가피론 글쓰기라고 비꼬았다.[^keybored]
이 전제가 틀렸다고 단정할 근거는 이 글에 없지만,
비용이 아니라 사람의 가독성과 유지 보수가 중요한 팀에서는 이 벤치마크의
최적화 목표가 다를 수 있다.

### 이 벤치마크가 측정하는 것은 처음 만들 때의 비용이다

글의 가장 큰 공백은 유지 보수다.
에이전트 시대에 코드가 많을수록 이후 수정에도 토큰이 든다고 Lawson이 직접
말하지만, 그가 잰 것은 처음 한 번 만드는 비용과 줄 수다.
기능을 계속 추가하는 과정은 측정하지 않았다.
Hacker News에서 injidup은 한 번에 간단한 프론트엔드를 만드는 것은 잘 되지만
기능을 추가하고 옮기다 보면 JS와 CSS와 HTML이 한 페이지에 모인 3,000줄짜리
괴물이 되어, 작은 수정에도 모델이 앱의 더 많은 부분을 머릿속에 들고 있어야
한다고 적었다.[^injidup]
selfmodruntime은 프레임워크가 에이전트가 라이브러리 전체 코드를 컨텍스트에 담지
않아도 되게 해 준다고 반론했다.
그의 예는 에이전트가 React 내부 코드를 몰라도 컴포넌트 두세 개만으로 티켓 하나를
처리할 수 있다는 것이다.[^selfmodruntime]
두 주장은 모두 처음 한 번의 측정으로는 확인할 수 없는 영역이다.

## 인사이트

### 프레임워크 선택의 변수가 모델의 학습 시점으로 바뀌고 있다

SvelteKit과 Gracile의 비용이 높은 이유는 모델이 그 프레임워크를 덜 알았기
때문으로 설명된다.
이 경우 프레임워크가 얼마나 좋은지와 에이전트가 쓰기 얼마나 쉬운지가
다른 축이 된다.
모델이 학습하지 못한 새 프레임워크는 MCP와 스킬 같은 보조 자료로 채워야 하는데,
Lawson은 현재의 보조 자료가 해를 끼칠 수도 있다고 의심한다.
그러나 이 글의 표가 그 의심을 뒷받침하지는 않는다.
쓰이지 않은 도구(Nuxt의 MCP)는 해를 끼칠 수 없고,
꾸준히 쓰인 도구는 가장 싼 쪽에도(Hono 스킬) 비싼 쪽에도(SvelteKit 플러그인)
있다.
의심을 확인하려면 같은 프레임워크를 도구를 쓸 때와 쓰지 않을 때로 나눠 돌려야
한다.
그러므로 프레임워크 제작자에게 AI 대응이란 문서를 늘리는 것이 아니라
도구가 실제로 쓰이게 만들고, 쓰인 경우와 안 쓰인 경우를 비교해 보는 쪽의
문제다.

dofm은 Nuxt가 에이전트에게 쉬운 이유를 문서에서 찾았다.
그는 Nuxt와 Laravel의 문서가 사람 중심으로 쓰인 이해하기 쉬운 예제와 참조로
되어 있고 중간 계층도 알아보기 어렵지 않아서 LLM이 코드를 잘 쓰는 것
같다고 추측했다.[^dofm]
이것은 Nuxt의 MCP를 한 번도 쓰지 않고도 세 번째로 싸고 토큰이 가장 적었다는
결과와 어긋나지 않는 가설이다.
검증되지는 않았지만, 에이전트에게 쉬운 프레임워크의 조건이
에이전트용 도구가 아니라 사람용 문서일 수 있다는 방향을 가리킨다.

### API가 새로울 때의 비용은 조회 비용과 오류 비용으로 나뉜다

incrudible는 순수 JavaScript로 에이전트를 돌리면 결함률이 빠르게 오르고
에이전트가 스스로 만든 혼란 속에서 시간을 쓴다고 적었다.
그는 React를 다시 택했는데, 이유 중 하나는 API가 안정적이라는 점이다.
호환이 깨지는 API 변경은 에이전트에게 독이라는 것이 그의 말이다.
에이전트는 아는 줄 알고 틀리게 쓴 뒤에야 문서를 찾기 때문에,
아예 모르는 사내 라이브러리는 곧바로 문서를 찾아보게 만든다는 점에서 오히려
낫다고 했다.[^incrudible]
이 말을 Lawson의 SvelteKit 사례와 겹쳐 읽으면 API가 새로울 때의 비용이
두 갈래로 보인다.
하나는 SvelteKit 에이전트가 매 실행 v3 마이그레이션 안내서를 읽은 것처럼
문서를 조회하는 데 드는 토큰이다.
다른 하나는 incrudible가 말한 것처럼 모델이 옛 API를 안다고 믿고 틀리게 쓴 뒤
고치는 비용이다.
이 벤치마크는 앞의 비용을 보여 주지만 뒤의 비용은 따로 재지 못했다.
따라서 비용 비교에서 의미 있는 질문은 어느 프레임워크가 싼가만이 아니라,
그 프레임워크의 주요 버전이 모델의 학습 시점보다 앞인지 뒤인지,
그리고 API가 얼마나 바뀌었는지이기도 하다.

### 처음 비용의 차이보다 이후 비용의 구조가 결정적일 수 있다

중앙값 비용의 차이는 약 2달러이고 같은 프레임워크 안의 변동 폭과 겹친다.
사람이 코드를 읽고 고치는 일이 줄수록 코드 줄 수가 이후 수정 비용을 결정한다는
Lawson의 지적이 맞다면, 줄 수가 적은 Hono+htmx나 Nuxt,
Astro 같은 구성이 계속 유리할 수 있다.
다만 줄 수가 적다는 것이 수정하기 쉽다는 뜻은 아니다.
unsloppable은 htmx로 만든 앱이 복잡한 폼과 상태 관리를 만났을 때 에이전트가
어려움을 겪었다고 보고했다.
그는 폼이 동작하는데도 페이지가 30초 걸리거나 상태가 갑자기 사라지는 일이
있었고, React로 다시 쓰면 한 번에 해결했을 것이라고 믿는다고
적었다.[^unsloppable]
이는 한 사용자의 경험이지만, 복잡한 상호작용에서는 줄 수가 적은 구성이 오히려
불리해질 수 있다는 가설을 세울 근거가 된다.

비슷한 경험이 더 있었다.
afavour는 htmx에는 다른 것으로 넘어가야 하는 지점이 있고,
그 경우 Svelte가 React보다 빠르다는 이점을
에이전트를 달래는 수고 없이 줄 것이라고 추측했다.[^afavour]
smrtinsert는 상호작용이 있는 앱을 Claude 4 계열로 htmx로 만들었을 때
사용자 경험이 자주 틀렸고,
SvelteKit 2로 바꾸자 원하는 것이 거의 바로 나왔다고 적었다.[^smrtinsert]
Hono+htmx의 낮은 비용과 적은 코드는 콘텐츠 중심 앱이라는 조건에서 얻은 값이며,
조건이 바뀌면 같은 방향의 이점이 유지된다는 보장이 없다.

### 프레임워크가 에이전트에게 주는 것은 강제되는 제약일 수 있다

robgibbons는 AGENTS.md는 에이전트가 무시할 수 있고 스킬도 항상 호출되지는
않지만, 프레임워크는 소리 나는 실패와 알려진 해법을 가진 기계적 제약을 준다고
주장했다.[^robgibbons]
miki123211은 장바구니 같은 상태를 20곳에서 동기화해야 하는 화면에서
React 계열은 그런 버그를 심으려면 일부러 애써야 하게 만든다고
적었다.[^miki123211]
deepsun은 프레임워크의 가장 큰 가치가 허용하는 것이 아니라 금지하는 것에 있지만
에이전트에게는 이것이 중요하지 않을 것이라고 보았다.[^deepsun]
Lawson의 표는 이 논쟁에 한 가지를 보탠다.
Next.js의 에이전트가 AGENTS.md를 5번 중 2번만 읽었다는 사실은 문서 형태의 규칙이
읽힐 때만 작동한다는 점을 보여 준다.
읽지 않아도 작동하는 제약이 따로 있다는 가설은 이 사실과 어긋나지 않지만,
이 글의 데이터가 가설을 확인해 주지는 않는다.
이 가설을 검증하는 실험은 같은 명세에서 상태 동기화가 많은 화면을 넣고
프레임워크별 결함률을 비교하는 것이다.

### 에이전트에게 묻는 것과 에이전트를 재는 것은 다르다

Lawson은 프레임워크가 에이전트에게 더 낫다며 프런트엔드를 재작성하는 사람들에게
에이전트에게 물어는 봤느냐고 괄호 안에서 되묻는다.
buildfocus는 에이전트가 추천하는 도구와 가장 효율적으로 쓰는 도구가 같으리라는
것은 놀라운 일이며, 에이전트는 이 도구로 더 빨리 반복할 수 있다고 분석한 것이
아니라 보통의 모범 관행을 말하는 것이라고 지적했다.[^buildfocus]
h0rv는 기술 스택을 모르는 바이브 코더 친구들에게서 에이전트가 고르는 기본
스택이 늘 Next.js, Vercel, Supabase라고 전했다.[^h0rv]
이 벤치마크에서 Next.js는 JavaScript 용량이 가장 크고(142KiB) 중앙값 비용은
다섯 번째로 낮았다.
에이전트가 가장 자주 고르는 선택과 이 벤치마크에서 싸고 가벼운 선택은 일치하지
않을 수 있다.
다만 이 벤치마크는 에이전트가 직접 고르게 하지 않았으므로 이 차이를 재지는
못했다.
에이전트의 선택 성향도 하나의 변수이며, 같은 명세를 주고 프레임워크를 고르게
하는 별도 실험이 가능하다.

### 시간은 에이전트의 생각보다 도구 호출을 기다리는 시간일 수 있다

jillesvangurp는 AI로 무엇을 쓸 때의 비용을 재는 좋은 잣대가 도구 출력의 장황함,
복잡한 실패 방식, 느린 도구라고 적었다.
이런 것들이 에이전트가 더 많은 출력을 뒤지고 준비 상태를 확인하느라 토큰을
쓰게 만들며, AI 도구를 기다리는 시간의 대부분은 사실 도구 호출을 기다리는
시간이라는 것이다.[^jillesvangurp]
Lawson의 시간 지표는 에이전트 관점의 실제 경과 시간이므로
이 해석이 맞는다면 시간 지표는 프레임워크의 빌드와 테스트가 얼마나 빨리
끝나는지를
상당 부분 반영한다.
그것은 코드 양과는 다른 비용이다.
이 점에서 시간과 토큰이 비용을 따라 움직인다는 글의 관찰(순위 상관 0.90, 0.97)은
원인이 하나라는 뜻으로 읽으면 안 된다.
smrtinsert는 기업 요금제라면 이 정도 비용 차이는 무시할 만하고,
부정확한 요구사항 때문에 낭비하는 토큰이 개발 자체에 쓰는 토큰보다 많다고
적었다.[^smrtinsert]
한 번에 2달러 안팎인 차이는 그 요구사항의 품질 앞에서 작은 변수일 수 있다.

### 자기 앱에서 같은 실험을 하는 것이 이 글을 쓸모 있게 만드는 방법이다

Lawson은 벤치마크를 GitHub에 공개했고 다른 사람이 돌리거나 포크하기를 권한다.
이 글에서 실제로 쓸 수 있는 결정 규칙은 결과 표가 아니라 방법이다.
팀이 프레임워크를 바꾸려 한다면 자기 앱의 가장 흔한 화면 하나를 명세와 적합성
테스트로 만들고, 후보마다 5번씩 에이전트로 만들어 비용, 시간, 줄 수,
용량의 중앙값과 범위를 비교하면 된다.
범위가 겹치는 차이는 무시하고, 범위가 겹치지 않는 차이만 근거로 삼는다.
그 앱이 이 글의 앱처럼 콘텐츠 중심이 아니라면 결과가 다르게 나올 것이라는 점도
처음부터 가정하고 시작해야 한다.

여기에 이 글의 공백에서 얻은 조건을 더하면 실험이 훨씬 쓸모 있어진다.
첫째, 앱 하나에 상호작용이 많은 화면(상태를 여러 곳에서 동기화하는 화면, 복잡한
양식)을 반드시 넣는다.
이 글의 결과가 가장 약한 곳이기 때문이다.
둘째, 같은 프레임워크를 도구를 쓸 때와 쓰지 않을 때로 나눠 돌려서 도구의 효과를
따로 잰다.
셋째, 모델과 프레임워크의 버전을 기록해 두고, 모델이 바뀌면 다시 돌린다.
넷째, 첫 구현 뒤에 기능을 하나 더 추가시켜 두 번째 비용을 잰다.
이 글이 재지 않은 유지 보수가 여기서 처음으로 숫자가 된다.
다섯째, 비용과 사용자에게 가는 값(용량, TBT, LCP)을 한 순위로 합치지 않고
따로 본다.
이 글의 데이터에서 두 묶음의 상관은 0.3 안팎에 그쳤기 때문이다.

실패 조건도 미리 정해 둔다.
후보끼리의 비용 범위가 겹치면 결정하지 않고 표본을 늘린다.
후보의 최신 주요 버전이 모델의 학습 시점보다 새롭다면 처음 비용이 높게 나오는
것은 프레임워크의 성질이 아니라 시점의 문제로 보고 따로 기록한다.
에이전트가 명세를 놓쳐 실패한 실행은 Lawson이 Angular에서 한 것처럼
이유를 적어 두되, 실패를 어느 쪽 탓으로 볼지는 실험을 시작하기 전에 정한다.
