# PDF.js: PDF 구문 분석과 렌더링을 웹 표준 위에서 하는 Mozilla의 뷰어

<https://github.com/mozilla/pdf.js>

HN 토론: <https://news.ycombinator.com/item?id=4520456> (371점, 90개 댓글)

## 소개

PDF.js는 HTML5로 만든 PDF(Portable Document Format) 뷰어다.
README는 커뮤니티가 이끌고 Mozilla가 지원하며,
PDF를 구문 분석하고 렌더링하는 범용 웹 표준 기반 플랫폼을 만드는 것이 목표라고
소개한다.
저장소 설명은 한 줄로 JavaScript로 만든 PDF 리더다.

저장소는 2011년 4월 26일에 만들어졌고 Apache-2.0 라이선스다.
2026년 11월 10일에 GitHub API로 확인한 별은 54,118개, 포크는 10,735개,
열린 이슈는 474개이고, 마지막 푸시는 11월 9일이었다.
최신 릴리스는 11월 1일의 v6.5.438이며, 그 앞은 10월 3일의 v6.4.299,
8월 29일의 v6.3.289, 7월 28일의 v6.2.108로 달마다 릴리스가 나온다.
릴리스 노트는 접근성, 주석 편집과 렌더링, 글꼴 변환, 이미지 변환, 성능,
스크립팅, 타일링 패턴 렌더링, 뷰어의 개선을 요약한다.

README는 Firefox 19 이상에 PDF.js가 내장되어 있다고 쓴다.
Chrome 확장 프로그램은 Chrome 웹 스토어에 있고 별도 관리자(Rob--W)가 유지하며,
직접 빌드할 수도 있다.
온라인 데모는 최신 JavaScript 기능을 가정하는 현대 브라우저판과
이전 브라우저용 레거시판이 따로 있고,
PDF의 내부 구조를 보는 디버거 페이지도 있다.

## 구성

### 세 층과 뷰어

저장소의 `AGENTS.md`는 구조를 다섯 부분으로 설명한다.

| 부분     | 위치                 | 맡은 일                                                                                                                                                        |
| -------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 코어     | `src/core/`          | PDF 구문 분석: 상호 참조 표, 스트림, 글꼴(CFF, TrueType, Type1), 이미지 디코더(JPEG, JBIG2, JPX), 연산자 처리, XFA 양식, 색 공간. 웹 워커(Web Worker)에서 돈다 |
| 표시     | `src/display/`       | 캔버스 렌더링, 텍스트 레이어, 주석 레이어, 편집기 레이어, 메타데이터와 스트림. 공개 API(`getDocument()`, `PDFDocumentProxy`)가 여기 있다                       |
| 스크립팅 | `src/scripting_api/` | 양식 계산과 검증을 위한 샌드박스 JavaScript 실행. Acrobat JavaScript API 객체(App, Doc, Field)를 구현한다                                                      |
| 웹 뷰어  | `web/`               | 툴바, 사이드바(썸네일, 윤곽, 첨부), 찾기, 주석 편집기 UI, 발표 모드를 갖춘 완전한 뷰어 앱                                                                      |
| 공유     | `src/shared/`        | 워커 메시지 처리와 공통 유틸리티                                                                                                                               |

메인 스레드의 표시 층이 워커 스레드의 코어 층과 `MessageHandler`로 대화하므로
PDF 구문 분석이 메인 스레드 밖에서 일어난다.
외부 의존성(`external/`)으로 CJK 글꼴을 위한 바이너리 CMap, 비내장 표준 글꼴을
만드는 WASM 글꼴 생성기, JPEG2000용 openjpeg(WASM), 샌드박스 실행용 QuickJS가
있다.

### 빌드와 테스트

빌드는 Gulp가 조율하고 Webpack이 묶고 Babel이 변환하며,
`PDFJSDev.test("GENERIC")` 같은 전처리 조건으로 빌드 대상(GENERIC, MOZCENTRAL,
CHROME, MINIFIED, TESTING, LIB)을 가른다.
단위 테스트는 Jasmine, 통합 테스트는 Puppeteer이고,
기준 이미지(reference images)를 쓰는 시각 회귀 시험이 있다.
README는 코드 커버리지를 Codecov로 추적하며,
`coverage_search`로 특정 줄이나 함수를 실행하는 기준 시험만 찾아
돌리거나 기준 이미지를 다시 만들 수 있다고 설명한다.
번역은 Firefox Nightly에서 가져오므로 직접 고치지 않는다.

## 사용하기

### 웹 앱에서 쓰기

미리 빌드한 버전을 NPM의 `pdfjs-dist` 이름으로 받거나 소스에서 빌드한다.
`npx gulp generic`이 `pdf.js`와 `pdf.worker.js`를 만들고,
둘이 모두 필요하지만 페이지에는 `pdf.js`만 넣으면 워커는 그것이 불러온다.
README는 이 파일이 크므로 운영에서는 최소화해야 한다고 적는다.
jsDelivr, cdnjs, unpkg 같은 CDN에서도 받을 수 있다.

### 로컬에서 돌려 보기

```sh
git clone https://github.com/mozilla/pdf.js.git
cd pdf.js
npm install
npx gulp server
```

그다음 `http://localhost:8888/web/viewer.html`을 연다.
일부 브라우저가 `file://` URL로 PDF를 여는 것을 막으므로 로컬 서버가 필요하다.
시험용 PDF는 `http://localhost:8888/test/pdfs/?frame`에서 볼 수 있다.

## 분석

### 브라우저가 PDF를 이해하는 계층을 웹 기술로 다시 쓴 프로젝트다

PDF.js의 구조는 코어(구문 분석)와 표시(렌더링 API)를 워커 경계로 가르는 것이
핵심이다.
PDF는 글꼴 형식만 해도 여러 가지(CFF, TrueType, Type1)이고,
이미지 코덱(JBIG2, JPX), XFA 양식, Acrobat 스크립팅까지 다룬다.
그 모두를 브라우저 안에서 플러그인 없이 처리하려면 느린 메인 스레드를 비워 두는
설계가 필요하고, 워커와 메시지 전달이 그 답이다.
README가 목표로 말하는 웹 표준 기반 플랫폼이라는 말은 이 구조를 가리킨다.

### 부품이 뷰어와 라이브러리로 나뉜다

저장소는 `web/`의 완성된 뷰어와 `pdfjs-dist`로 배포되는 라이브러리를 함께
낸다.
같은 코어가 Firefox 내장 뷰어, Chrome 확장,
다른 웹 앱에 쓰이는 이유가 이 분리다.
빌드 대상(GENERIC, MOZCENTRAL, CHROME, LIB)이 이 분리를 전처리 조건으로
드러낸다.

### 시험 기반이 재현성을 지탱한다

PDF는 비정상적으로 깨진 문서가 많아서 구문 분석의 예외 처리가 끝이 없다.
릴리스 노트가 형식이 틀린 /Kids 항목 처리,
선택적 콘텐츠(Optional Content) 오류가 렌더링 전체를
막지 않게 하기 같은 수정을 이슈 번호와 함께 싣는 것은 이 프로젝트의 일상이
깨진 파일에 대한 대응임을 보여 준다.
기준 이미지와 커버리지로 줄 단위 시험 대응을 찾는 도구는 이 일상을 지탱하는
인프라다.

## 비평

### 이 문서가 읽은 범위는 README와 구조 문서에 한정된다

HN 토론 줄의 2012년 스레드는 저장소가 아니라 당시 데모 주소가 올라간 것이다.
이번에 읽은 것은 README, 에이전트용 `AGENTS.md`, 최신 릴리스 노트, 저장소 메타
데이터와 2012년의 HN 스레드다.
소스 코드, 성능, 렌더링 정확도 비교는 직접 확인하지 않았다.
`AGENTS.md`의 구조 설명은 사람이 아니라 코딩 에이전트에게 주는 요약이므로
정확성을 코드와 맞춰 보지 못했다는 점을 밝혀 둔다.

### 쓸모의 한계는 오래전부터 지적되었다

2012년 HN 공개 스레드에서 한 사용자는 이 프로젝트가 기술적으로는 매우
인상적이지만, 웹사이트들이 이를 써서 PDF를 쉽게 보여 주는 것이 반갑지 않다고
썼다.[^jowiar]
다른 사용자는 지도처럼 벡터가 너무 많은 문서는 JavaScript와 캔버스가 따라가지
못한다고 했고,[^ianb]
한 사용자는 인상적이지만 느리다고 했다.[^chj]
이 지적들은 14년 전 상태에 대한 것이어서 지금의 성능을 말하지 않는다.
다만 큰 벡터 문서와 성능이라는 쟁점이 이 프로젝트의 오랜 과제이며,
릴리스 노트가 캔버스 그리기 작업을 워커로 넘기는 변경(PR 21860)을 싣는 것은
그 과제가 지금도 진행 중임을 보여 준다.
이 변경이 효과를 내는지는 이 문서가 확인하지 못했다.

### 열린 이슈의 수가 유지 부담을 가리킨다

열린 이슈 474개가 많은지 적은지는 비교 대상이 없어 판단하지 못한다.
다만 달마다 릴리스가 나가는 프로젝트의 이슈가 이만큼 열려 있다는 것은
PDF 규격의 폭이 개발자 수보다 크다는 점과 맞닿아 있다.
어떤 유형의 이슈가 많은지는 이 문서가 확인하지 못했다.

## 인사이트

### 코딩 에이전트용 안내가 프로젝트 문서의 새 장르가 되었다

저장소 최상위에는 `AGENTS.md`와 `.mcp.json`이 있다.
`.mcp.json`은 Firefox 개발자 도구용 MCP 서버(`@padenot/firefox-devtools-mcp`)를
에이전트에 연결하도록 설정한다.
`AGENTS.md`는 개요, 명령, 구조, 빌드 시스템, 코드 스타일, PR 절차를 에이전트가
읽도록 정리하고, 번역 파일은 직접 고치지 말라는 금지 사항도 적는다.
사람이 읽는 `CONTRIBUTING`과 별개로 에이전트용 안내가 따로 필요하다는 것을
14년 된 프로젝트가 받아들인 셈이다.
이 문서의 해석은 이것이 기여자의 진입 비용을 에이전트가 낮출 수 있다는 기대를
반영한다는 것이다.

### 웹이 충분하다는 주장의 가장 오래된 증거가 이 프로젝트다

2012년 HN 스레드에서 한 사용자는 웹 애플리케이션이 네이티브보다 빠르게
좋아지고 있어 언젠가 웹이 네이티브를 넘어설 것이라고 썼다.[^uams]
PDF.js는 브라우저가 PDF라는 거대한 규격을 플러그인 없이 처리할 수 있음을
보여 준 사례이고, Firefox가 내장하게 된 것이 그 결과다.
2026년 10월 Paul Ford의 글도 PDF.js를 웹 브라우저가 이미 가진 강력한 부품의
한 예로 든다.[^ford]
다만 이 문장은 이 문서의 해석이며, 웹이 네이티브를 넘어섰는지는 영역마다 다르다.

### 구문 분석이 렌더링보다 오래 남는 일이다

PDF.js의 코드는 렌더링 계층보다 구문 분석 계층(코어)이 훨씬 넓다.
글꼴과 이미지 코덱과 양식과 스크립팅 모두가 규격의 오래된 부분이고,
렌더링 방식(캔버스, 워커로의 이전)은 바뀌어도 구문 분석 규칙은 그대로 남는다.
릴리스 노트가 글꼴 변환과 이미지 변환을 거의 매번 개선 항목으로 올리는 것은
이 부분이 끝나지 않는 일이라는 뜻이다.
