# Modern Web Guidance 1.0 발표

원문: [Modern Web Guidance 1.0: The web platform expertise your coding agent is missing](https://developer.chrome.com/blog/modern-web-guidance-v1)

HN 토론: <https://news.ycombinator.com/item?id=50460398> (34점, 9개 댓글)

GN 토론: <https://news.hada.io/topic?id=37324>

## 요약

Chrome 개발자 블로그에 Philip Walton이 2026년 11월 10일 올린 발표문이다.
이 문서는 글 전문을 읽었다. 평가 대시보드와 문서, 글이 가리키는 〈Top 10 things AI gets wrong in web development〉는 열지 않았다. 수치와 성공 사례는 모두 Chrome 팀과 도입 기업이 말한 것이다. 이 도구를 GitHub 저장소 기준으로 다룬 문서는 `web/modern-web-guidance.md`에 따로 있다.

글의 주장은 이렇다.
최신 모델은 동작하는 코드를 만들 수 있지만 웹 전문가가 검토하면 더 빠르고 접근성 있고 안전하게 고칠 곳이 거의 항상 보인다는 것이다. Modern Web Guidance는 웹 플랫폼의 전문 지식과 모범 사례와 브라우저 호환성 데이터를 코딩 에이전트에 직접 넣는 스킬 모음이고, 5월 Google I/O의 초기 미리보기를 거쳐 1.0이 안정 버전이 되었다.

1.0이 담은 것은 다음이다.

- 기존 코드베이스를 훑어 안전하게 현대화할 기회를 찾는 현대화 워크플로. 이번 첫 릴리스는 정적 분석으로 제한된 패턴만 점검하고, 나중에 에이전트가 코드를 직접 추론하는 감사까지 넓힐 계획이라고 한다.
- AI가 모르는 것으로 검증된 수백 개의 지식 공백을 겨냥하고 전문가가 검토한 크로스 브라우저 해법의 가이드 데이터베이스.
- 모든 가이드에 대한 더 깊은 전문가 검토. 내용 영역 책임자의 승인과, 사용자 대면 가이드에 대해 실제 보조 기술을 쓰는 접근성 전문가의 전담 검토가 포함된다.
- 모든 가이드에 대한 평가와, 가이드 없는 에이전트와의 개선폭을 보여 주는 공개 평가 대시보드.
- Firefox와 Edge가 Chrome과 함께 호환성 개선과 기여에 참여하는 크로스 브라우저 협업.

글이 개발자와 기업이 써야 할 이유로 드는 것은 이렇다.

- 모델이 놓치는 모범 사례를 보강한다. 평가에서 접근성(키보드 포커스와 inert 관리, 모션 축소, 접근 가능한 폼 검증), 사용자 경험(스와이프와 터치 제스처, 대화상자와 팝오버 전환, 라이트와 다크 테마), 성능(메인 스레드 작업 스케줄링, 화면 밖 렌더링 격리, 레이아웃 이동 방지), 보안(안전한 HTML 정화, 엄격한 콘텐츠 보안 정책, 패스키 관리)에서 부족했다고 한다.
- 일에 맞는 웹 기능을 쓰게 한다. AI는 JavaScript로 되게 만드는 데 능하지만 HTML이나 CSS 기능이 훨씬 적은 코드로 같은 일을 하고 브라우저가 처리해 성능과 접근성이 낫다. 가이드에는 Baseline과 호환성 데이터가 들어 있어 프로젝트의 브라우저 지원 요건에 맞춘다.
- 기존 코드베이스의 현대화: `/modern-web-guidance Modernize the code in this directory` 같은 지시로 HTML과 CSS와 JavaScript와 package.json을 분석한다.
- 플랫폼과 함께 갱신된다: Baseline 호환성 데이터 위에 만들어지고 권고는 브라우저 엔지니어와 표준 전문가와 접근성 전문가가 유지한다.
- 학습 자료로도 쓸 수 있다고 한다.
- Chrome DevTools for agents와 함께 쓰라고 권한다. 가이드가 사전 전문 지식을, DevTools가 실행 시점 가시성을 준다. 저성능 CPU로 성능 추적을 하며 메인 스레드가 50밀리초를 넘지 않을 때까지 반복하기, 애니메이션을 녹화해 검증하고 prefers-reduced-motion을 확인하기, 메모리 누수 점검의 예를 든다.

성공 사례는 다음이다.

- Pensionbazaar(인도 Paisabazaar의 퇴직 설계 플랫폼): 새 페이지 구축과 검증의 소요를 90% 넘게(약 나흘에서 몇 시간으로), 새 화면의 UI 버그를 90% 넘게 줄였다. 자매 플랫폼 Policybazaar는 약 30개 랜딩 페이지의 성능 감사를 자동화해 수동 감사 노력을 92% 줄였다고 한다.
- WeTV(Tencent): CI/CD에 AI 코딩 에이전트를 넣어 성능 검사 실패의 90%를 자동 진단하고 해결하며, 디버깅과 해결 시간이 87%(네 시간에서 30분, 수동 평가 포함) 줄었다.
- note inc.: 프로덕션 코드베이스의 180회 평가에서 현대 웹 검사 통과율이 61%에서 94%로 올랐고, 431개 병합 PR에서 LCP 이미지 우선순위 지정이 28% 늘었다.
- MetaMask: 모든 PR에 세 줄짜리 프롬프트의 자동 리뷰 봇으로 쓰고, 첫 5주에 약 480개 PR을 검토해 64개에 댓글을 달았으며 43개 지적을 고쳤다(주로 린터가 못 잡는 접근성과 HTML 의미론과 폼). 댓글에서 수정까지 중앙값 15분이다.

설치는 `npx modern-web-guidance@latest install`이고 Claude Code와 Codex와 Cursor와 Copilot 등의 플러그인 마켓플레이스로도 설치할 수 있다고 한다.

## 분석

### 중심 주장은 속도가 아니라 품질이 이제 차별 요소라는 것이다

글은 모두가 코딩 에이전트를 쓰는 세상에서 속도는 경쟁 우위가 아니고 사용성과 경험의 질이 차별점이라고 말한다.
그 질을 에이전트가 안정적으로 내게 하려면 모델이 모르는 영역의 전문가 검토를 에이전트가 읽을 수 있는 지침으로 넣어야 한다는 구조이다. 이는 글의 서술을 이 문서가 압축한 것이다.

### 이 도구의 효과는 지침과 런타임 검증의 짝으로 설명된다

가이드는 쓰기 전의 전문 지식을, DevTools는 쓴 뒤의 확인을 맡는다는 분업이 글의 틀이다.
성능이나 애니메이션의 예에서 가이드가 방법을 알려도 실제로 되는지는 실행해서 봐야 한다는 점이 반복된다.

## 비평

### 사례의 수치는 도입 기업 자신의 보고이다

90%와 92%와 87% 같은 감소는 각 기업이 내부 측정으로 낸 값이고, 기준(무엇과 비교했는지)과 측정 방법이 글에 거의 없다.
Chrome 팀이 자기 도구의 발표문에서 고른 사례이며 부정적인 사례나 효과가 없었던 경우는 나오지 않는다.
note의 61%에서 94%는 평가 횟수(180회)와 비교 조건이 있는 편이나 이 문서는 이를 확인하지 못했다.

### 평가가 같은 팀의 것이다

가이드를 만든 팀이 평가를 만들고 대시보드로 개선폭을 공개한다.
평가가 가이드의 내용과 맞춰 설계되었을 가능성을 외부에서 가늠하기 어렵다. 공개 대시보드는 이 문서가 열지 않았다.

### 특정 개발 방식을 전제한다는 지적

HN의 한 댓글은 이 스킬이 일반 HTML로 충분한 곳에서도 JavaScript를 선호하는 경향이 있으며, 서버 렌더링을 선호하는 팀은 다른 것을 보라고 했다.[^braiamp]
답글은 서버 렌더링 HTML은 일반 HTML이 아니라고 하며 SPA가 차선책이라는 입장을 폈고, 이에 다시 SPA가 차선이라는 말이냐는 반문이 달렸다.[^sublinear][^timw4mail]
글은 반대로 HTML과 CSS 기능을 JavaScript보다 우선하라고 말한다. 따라서 댓글의 지적이 글의 가이드 전체에 맞는지는 이 문서가 확인하지 못했다.
다른 댓글은 에이전트에게 프레임워크의 기억을 믿지 말고 설치된 버전을 읽게 하며, 문서와 다르게 동작하는 부분은 실패하는 테스트로 고정한다고 하면서, 가이드를 프레임워크 버전에 어떻게 묶느냐고 물었다.[^DeepOntology]
글은 Baseline 호환성 데이터에 기대어 갱신된다고 하나 프레임워크 버전과의 연동은 다루지 않는다.
이 스레드는 같은 도구에 대한 이전 Show HN 스레드와 중복으로 표시되었다.[^ChrisArchitect]
Lobste.rs에서는 `developer.chrome.com` 도메인 최근 23개 글에 이 글이 없었고, GeekNews 토픽에는 댓글이 없었다.

## 인사이트

### 가져갈 것은 에이전트에게 도메인 지침과 런타임 검증을 함께 주는 구성이다

지침만 주면 쓴 코드가 실제로 되는지 모르고, 검증만 있으면 처음부터 올바른 방법을 모른다.
웹이 아닌 영역에서도 사전 지침(전문가 검토를 거친 짧은 가이드)과 사후 검증(실행해 보는 도구)을 짝지어 에이전트에 주는 구조는 적용할 만하다. 이는 이 문서의 정리이다.

### 도입 전에 볼 것은 현대화 워크플로의 범위이다

첫 릴리스의 현대화는 정적 분석이 제한된 패턴만 점검한다고 글이 밝힌다.
기존 코드베이스에 쓰려면 어떤 패턴을 어디까지 점검하는지부터 확인해야 한다.

### 확인할 관찰

이 발표의 주장을 가를 관찰은 세 가지이다.
공개 평가 대시보드의 개선폭이 외부 코드베이스에서도 재현되는지,
Firefox와 Edge의 참여가 가이드의 내용과 호환성 데이터에 어떻게 반영되는지,
서버 렌더링 중심의 프로젝트에서도 권고가 맞는지이다.
셋 모두 이 문서가 확인하지 못했다.
