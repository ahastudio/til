# Twitter 웹 앱을 서버 하나로 다시 만들기

## 요약

Twitter(도메인 `x.com`)의 엔지니어링 블로그에 Principal Engineer인 Yagiz Nizipli가 2026년 11월 4일 올린 글이다.

글의 주장은 이렇다.
느린 연결에서 프로필을 열면 옛 웹 앱은 첫 게시물이 나오기까지 22초 넘게 로고만 보여 주었는데 새 앱은 2.7초라는 것이다.
새 앱은 사람과 검색 크롤러와 링크 미리보기 봇에 각각 서버를 따로 두던 구조를 서버 하나로 합쳤다. 이미 로그아웃 상태의 사이트와 검색 엔진이 긁는 페이지를 서비스하고, 로그인 상태는 나라 하나씩 옮기는 중이다.
필자는 Similarweb 기준 세계 6위 사이트라고 쓰고, 엔지니어 5명이 AI 코딩 에이전트와 함께 6개월 안에 첫 버전을 만들었으며 9월 말 이후 20명 넘는 사람이 커밋했다고 한다.

글의 전개는 다음과 같다.

- 배경: 2017년의 Twitter Lite는 클라이언트 쪽 React 앱과 작은 Node.js 서버가 HTML 껍데기만 내려 주는 구조였고, 2019년 같은 코드베이스가 데스크톱 웹이 되었다. 이 앱을 필자는 rweb이라 부른다. 시간이 지나며 서버가 둘 더 붙었다. 검색 크롤러용으로 서버에서 앱을 그리는 rweb SSR과, 검색에 노출되는 로그아웃 페이지(이벤트, Spaces, Communities, 트렌드, 검색, 뉴스)용 별도 서버 Jetfuel SSR이다.
- 문제: 한 URL에 독자가 셋이다. 사람은 빨리 보이는 프로필을, 검색 크롤러는 구조화 데이터와 언어별 링크와 올바른 상태 코드가 담긴 완성된 HTML을, 링크 미리보기 봇은 제목과 설명과 이미지만 원한다. rweb에서는 로그아웃 방문자의 브라우저가 껍데기와 자바스크립트를 내려받고 실행한 뒤 GraphQL API를 호출하고서야 프로필을 그렸다. 서버 셋은 서로 어긋났고(검색 최적화 수정이 하나에만 들어가기 쉬움), 로그아웃 방문자는 가장 느린 경로를 받았으며, 기술 스택(Redux, Relay, React Native for Web 기반 스타일, Flow, 현대·구형 번들 이원화)은 변경을 늦추었다고 한다.
- 결정: 세 선택지를 비교한다. rweb을 그대로 개선하면 서버 셋이 남고 로그아웃용 렌더링 경로가 넷째로 늘어난다. 도구만 바꾸면(Webpack과 Babel을 Vite로, Flow를 TypeScript로, Express를 Fastify로) 거의 모든 파일을 건드리면서 문제의 구조는 남는다. 세 번째는 모든 독자를 서버 하나로 받는 새 앱을 만들어 트래픽을 조금씩 옮기는 것이고 이것을 골랐다. 두 가지 반론에 답한다. 다시 쓰기는 하지 말라는 Joel Spolsky의 조언에는 rweb을 계속 배포하고, 옛 서버를 명세로 삼아 새 앱을 시험하고, 에이전트 덕에 몇 달에 끝나 옛 제품이 앞서 나갈 시간이 없었다고 답한다. Webpack만 올리면 되지 않느냐는 물음에는 빠른 빌드는 개발자에게 좋지만 느린 연결의 방문자에게 서버 렌더링 HTML을 주지도, 서버 셋을 하나로 만들지도 못한다고 답한다.
- 남긴 것: 반응형 단일 코드베이스, GraphQL과 Relay, rweb SSR이 모은 URL 정리 규칙(끝에 구두점이 붙은 검색어, 언어 매개변수가 붙은 질의, 채팅 앱이 감싼 링크), Jetfuel SSR의 구조화 데이터와 언어별 링크와 진짜 404, 같은 URL과 리다이렉트, 링크 미리보기 카드 이미지(새 Rust 서비스가 픽셀 단위로 똑같이 다시 그림).
- 새 스택: 클라이언트와 서버 번들은 Vite(Rolldown 사용), 렌더링은 스트리밍 서버 렌더링과 Suspense를 쓰는 React, 서버는 Fastify, 서버 실행은 Node.js v26에서 작업 스레드 여럿을 한 프로세스로 돌리는 Platformatic Watt, 데이터는 Relay와 GraphQL, 자체 컴포넌트 라이브러리 XDS(Base UI와 Tailwind CSS 기반, 컴포넌트 40개 넘음), 타입 검사는 TypeScript 컴파일러의 Rust 포트인 tsrs이다.
- 데이터와 이동: 라우트가 필요한 데이터를 미리 선언하고, 링크는 사용자가 가리키거나 포커스를 줄 때 코드와 데이터를 미리 가져온다. 타임라인의 게시물은 마우스가 100밀리초 머물거나 눌렀을 때 미리 가져온다. 필자는 rweb이 클라이언트 캐시를 크게 두어 화면 전환이 즉각적이었던 점이 아직 앞선다고 인정한다.
- 작은 팀이 만든 방법: 엔지니어가 설계를 정하고 모든 변경을 검토했고 에이전트가 이식과 변환과 테스트 작성과 CI 지적 수정을 맡았다고 한다. 저장소 루트의 지침 파일 하나, 저장소 안의 25개 넘는 작업 절차(커밋 작성, 풀 리퀘스트 쌓기, 코드 리뷰, CI 통과, 의존성 변경, 번역 추가, Relay와 라우터 작업), 커밋마다 도는 검사가 신뢰를 만든다고 한다. 검사에는 자체 oxlint 플러그인이 있고 그중 하나는 에이전트가 자주 만드는 패턴(연쇄 타입 단언, unknown으로 둔 매개변수, 빈 객체의 조건부 펼치기)을 거부한다. 옛 서버가 그대로 명세였기에 에이전트가 동작을 이식하고 테스트로 고정하고 사람이 원본과 대조할 수 있었다. 엔지니어의 일은 코드를 쓰는 데서 시스템이 무엇을 해야 할지 정하고 실제 브라우저에서 확인하는 쪽으로 옮겨 갔다고 한다.
- 트래픽 이동: 크롤러가 먼저였다. 두 SSR 서버를 명세로 삼아 페이지 유형마다 응답을 비교해 간극을 메웠고, 검증된 Googlebot으로 두 서버에 같은 경로를 요청해 상태 코드와 제목과 canonical URL과 구조화 데이터 유형 등을 비교하는 스크립트를 썼다. 2026년 8월 1일 Jetfuel SSR을 없앴고, 9월 초 새 앱이 rweb SSR이 받던 크롤러 트래픽을 모두 받아 rweb SSR을 껐다. 그 배포와 빌드를 지우자 rweb에서 거의 36,000줄이 사라졌다고 한다. 로그인 상태는 엣지가 경로와 요청자에 따라 서버를 고르는 방식으로 나라 하나씩 옮기며, 기능 스위치로 누구를 옮길지 배포 없이 바꾸고 문제가 생기면 바로 되돌린다. 첫 나라에서는 일부만 새 앱으로 보내는 실험을 하며, 로그인 페이지는 먼저 `lite.x.com`에서 직원과 시험 참가자가 쓴다. Chat과 Calls와 Money 같은 기능은 모듈 연합(Module Federation)으로 한 번만 만들어 두 앱이 같은 것을 불러온다.
- 결과: 2026년 11월 3일 같은 계정으로 Lighthouse 기본의 Slow 4G(왕복 150밀리초, 내려받기 1.6Mbps, 올리기 750Kbps, CPU 감속 없음, 빈 캐시, 서비스 워커 끔)에서 각 앱을 세 번씩 녹화해 중앙값을 쓴 결과가 새 앱 2.7초(페이지는 2.4초)와 rweb 23.9초(로고는 1.0초에서 계속 떠 있음)이다. 구조적 결과로는 로그아웃 웹이 서버 셋에서 하나가 되었고 검색 최적화 수정이 한 번에 들어가며, 트래픽이 옮겨 가면서 rweb의 로그아웃 서버 규모가 데이터센터당 1,400대에서 700대로, rweb SSR이 2,400대에서 1,200대로 줄었다고 한다.
- 속도 작업: 9월 1일 이후 perf 라벨이 붙은 커밋이 80개를 넘는다. 서버 쪽에서는 렌더링 작업자를 늘렸고(이벤트 루프가 중앙값 67%, p95 84% 바빴고 최장 정지가 중앙값 1.9초, p95 3.7초였다고 한다), 게스트 토큰 요청과 기능 플래그 요청을 동시에 시작했고, 직렬화하던 Relay 저장소 레코드(응답의 4~5배 크기) 대신 GraphQL 응답을 JSON 텍스트로 한 번만 실었다. 크롤러 문서는 긴 스레드에서 2.2~3.5MB까지 커져 Googlebot이 처음 2MB만 읽는 한계를 넘었는데, 아이콘을 스프라이트로 모으는 등의 변경으로 165KB(14.2%), 340KB(13.6%), 450KB(13.0%), 54KB를 줄였다고 한다. 브라우저 쪽에서는 진입 스크립트를 async 모듈로 바꿔 hydration이 문서 파싱 끝을 기다리지 않게 했고, 시작 때 받는 파일을 로그인 진입에서 754개에서 182개로, 로그아웃 진입에서 582개에서 10개로 줄였으며(지연을 275밀리초 준 실험에서 로그인 홈 타임라인이 6.63초에서 4.95초), 스타일시트가 로드된 뒤에 스크립트를 시작하게 해 느린 프로필의 첫 콘텐츠 표시를 로그아웃 프로필에서 3,064밀리초에서 1,984밀리초로, 로그아웃 게시물에서 7,216밀리초에서 1,804밀리초로 줄였다. 대가로 다섯 페이지 중 둘은 hydration이 0.3%와 0.6% 늦게 끝났다고 한다.
- 오늘의 비교(11월 3일, 헤드리스 Chromium, 빈 캐시, 서비스 워커 끔, 앱·설정마다 7회 교대 측정): 로그인 상태에서 프로필과 게시물은 느린 프로필에서 8~13배 빠르다. @SpaceX 게시물은 1.7초로 12.8배, 프로필은 3.0초로 8.2배이고, 감속 없이는 각각 3.2배와 2.3배이다. Home 타임라인은 새 앱이 브라우저에서만 그려서 가장 적게 이득을 본다(느린 프로필 14.1초 대 24.6초로 1.7배, 감속 없음 1.8초 대 2.2초로 1.2배). 첫 바이트는 새 앱이 430~560밀리초로 rweb의 300밀리초 미만보다 느린데, 서버가 데이터를 가져와 그린 뒤 응답하기 때문이라고 한다. 첫 게시물 전에 내려받는 압축 자바스크립트는 rweb이 3.0~3.6MB이고 새 앱은 프로필과 게시물에서 0, Home에서 1.9MB이며, 페이지 전체로는 새 앱이 1.3~2.3MB, rweb이 4.1~4.8MB이다. 로그아웃은 느린 프로필에서 게시물 1.7초, 프로필 2.2초이고 감속 없이는 442밀리초와 792밀리초이다.
- 교훈 셋: 옛 서버가 가장 좋은 명세였고, 점진적 이동이 다시 쓰기를 안전하게 했으며, 실험실 숫자 옆에 현장 숫자가 있어야 한다. 로그인 상태 롤아웃이 끝나면 rweb을 은퇴시킬 예정이고, 7월에 Android 앱도 처음부터 다시 만들었다고 덧붙인다.

## 분석

### 중심 주장은 독자가 셋인 URL을 서버 하나로 받는 것이 느린 연결의 문제를 구조로 푼다는 것이다

글에서 가장 설득력 있는 부분은 속도 숫자가 아니라 원인의 설명이다.
옛 앱은 껍데기를 받고 자바스크립트를 내려받아 실행한 다음 데이터를 요청하는 직렬 사슬이었고, 느린 연결에서는 단계마다 왕복이 붙는다.
새 앱은 첫 응답에 내용을 실어 보내므로 사슬이 사라진다. 필자도 이 점을 숫자의 모양이 구조에서 나온다고 말한다.

### 이 글의 수치는 한 가지 조건이 아니라 여러 조건이 섞여 있다

글에는 실험 조건이 서로 다른 숫자가 함께 나온다.
도입부의 22초와 2.7초, 11월 3일 녹화의 23.9초와 2.7초(CPU 감속 없음), 같은 날 벤치마크의 22~25초(CPU 4배 감속), 6월 녹화의 약 18초와 3초가 모두 다른 설정이다.
필자는 실험실 숫자이며 장치와 네트워크에 따라 다르다고 여러 번 밝히지만, 독자가 비교할 때는 어느 숫자가 어느 조건인지를 직접 가려야 한다.

### AI 에이전트의 몫은 서술일 뿐 측정이 없다

엔지니어 5명이 6개월에 만들었다는 문장과 AI 에이전트가 구현의 많은 부분을 맡았다는 문장은 글에서 나란히 놓이지만, 에이전트가 쓴 양이나 되돌린 비율 같은 수치는 없다.
글이 구체적으로 보이는 것은 방법(지침 파일, 25개 넘는 작업 절차, 자체 린트 규칙, 커밋 전 검사)이다.
옛 서버가 동작을 정한 명세였다는 설명이 일의 상당 부분을 이식과 대조로 바꾼 이유로 읽히지만, 에이전트 없이 걸렸을 시간과의 비교는 없다.

## 비평

### 비교 대상이 같지 않다

로그인 상태 비교에서 새 앱은 `lite.x.com`에서, rweb은 `x.com`에서 측정했다.
글이 이를 밝히지만, 서로 다른 호스트와 서버 구성에서 나온 숫자이고 새 앱 쪽은 직원과 시험 참가자 위주의 환경이다.
또 rweb의 수치는 지난 10년 쌓인 스택의 값이라서, 다시 쓰기의 이득과 서버 렌더링 전환의 이득을 가를 수 없다. 다시 쓰지 않고 서버 렌더링 경로만 넷째로 더하는 대안(글의 선택지 하나)과 실제로 비교한 값은 없다.

### 약점도 글이 직접 적는 점은 평가할 만하다

Home 타임라인의 이득이 가장 작고, 로그인 상태의 첫 바이트가 느리며(430~560밀리초 대 300밀리초 미만), 스타일시트를 먼저 로드하는 변경이 일부 페이지에서 hydration을 늦춘다는 것을 글이 적는다.
rweb의 클라이언트 캐시가 화면 전환을 즉각적으로 느끼게 했다는 점도 인정한다.
이는 글이 선전에만 머물지 않았다는 근거이다.

### 서버 규모의 절반 감소는 순비용이 아니다

rweb의 로그아웃 서버가 1,400대에서 700대로, rweb SSR이 2,400대에서 1,200대로 줄었다는 서술은 옛 쪽의 감소만 보여 준다.
새 앱이 데이터센터당 몇 대로 돌아가는지, 서버에서 더 많이 렌더링하는 비용이 얼마인지는 없다.

### 외부 반응은 아주 적다

HN에는 이 글의 스레드가 둘 있다. 13점에 댓글 2개인 스레드와 1점에 댓글이 없는 스레드이다.
13점 스레드의 댓글 하나는 23.9초에서 2.7초가 극적인 개선이지만 그래도 느려 보인다고 했다.[^nailer]
글에 따르면 2.7초는 Slow 4G 프로파일로 제한한 실험실 값이고, 같은 글의 로그아웃 측정은 제한 없이 442~792밀리초이다. 댓글은 이 조건을 말하지 않는다.
다른 댓글은 내용이 한 단어 조각이라 반응으로 쓸 수 없었다.
Lobste.rs에서는 점수가 -1이고 댓글이 하나이며, 그 댓글은 joke 태그를 붙이면 더 낫겠다는 농담이었다.[^buherator]
그래서 이 글의 기술적 서술은 독자의 검토를 거의 거치지 않았다.

## 인사이트

### 가져갈 것은 옛 시스템을 명세로 쓰는 이전 방법이다

글에서 일반화할 수 있는 부분은 이전 절차이다.
옛 서버 둘이 하던 일(URL 정리, 구조화 데이터, 언어별 링크, 404, 리다이렉트)을 페이지 유형별로 새 앱과 비교하는 스크립트로 확인하고, 그 결과를 테스트로 남기고, 엣지에서 경로와 요청자별로 트래픽을 옮기고 즉시 되돌릴 수 있게 둔다.
이는 에이전트를 쓰든 쓰지 않든 큰 다시 쓰기의 위험을 줄이는 방법이다. 글이 직접 말하는 교훈 두 개와 같은 이야기이다.

### 크롤러를 User-Agent가 아니라 검증된 IP로 가르는 이유는 따로 기억할 만하다

헤더만 바꿔도 비싼 경로를 요청할 수 있고, 성능 측정 도구를 크롤러로 취급하면 사람이 받는 페이지를 재지 못한다는 두 이유는 크롤러와 사람을 서로 다르게 렌더링하는 모든 서비스에 적용된다.
적용 여부는 서비스의 엣지가 크롤러 IP를 검증할 수 있는지에 달렸고, 글은 이를 엣지에서 한다고만 쓴다.

### 확인할 관찰

이 글의 서술을 가를 관찰은 네 가지이다.
현장 측정(Core Web Vitals)에서 실험실의 개선 폭이 유지되는지,
로그인 상태 롤아웃이 끝난 뒤 Home의 이득이 얼마나 커지는지,
새 앱의 서버 규모와 렌더링 비용을 합친 순인프라 비용이 줄었는지,
에이전트 몫을 측정한 수치가 나오는지이다.
