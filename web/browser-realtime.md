# 브라우저의 실시간은 전송 수단이 아니라 마감과 복구와 확인의 계약이다

원문: [웹 실시간 통신: 폴링·SSE·WebSocket | Wonkook Lee](https://blog.wonkooklee.com/docs/api-and-interfaces/browser-realtime/)

GN 토론: <https://news.hada.io/topic?id=34572>

## 소개

요구사항에 “이 화면은 실시간으로 바뀌어야 한다”고 적혀 있으면
WebSocket부터 떠올리기 쉽다.
이 글(2026년 9월 8일, 읽는 데 약 31분)은 그 반사 작용을 늦추는 데 쓰인다.
채팅 메시지, 파일 처리 완료 알림,
함께 편집하는 사람의 커서는 기다릴 수 있는 시간이 서로 다르고,
연결이 끊겼을 때 빠짐없이 되찾아야 하는 데이터도 있고 지금의 값만 다시 받으면
되는 데이터도 있기 때문이다.

그래서 이 글의 순서는 전송 수단이 아니라 질문에서 시작한다.
실시간이라는 말이 무엇을 약속하는지를 정하고, 폴링과 롱폴링,
SSE, WebSocket이 데이터를 전달하는 경로를 따라가며 어디서 지연이 생기는지 짚고,
연결이 끊긴 뒤 무엇을 따로 처리해야 하는지를 다룬다.
WebRTC DataChannel, WebTransport, 탭 밖의 푸시까지 범위를 넓히며, 특정
라이브러리나 서비스의 구현을 재현하지 않고 파일 작업 목록과 협업 화면이라는 두
가상 사례로 브라우저 API와 서버 계약과 사용자에게 보이는 상태를 연결한다.
이 노트는 그 내용을 작업에 쓸 수 있도록 다시 정리한 것이다.

## 실시간이 약속하는 것

### 평균과 상한은 다른 주장이다

공학에서 실시간(real-time)은 결과의 정확성을 판단할 때 결과가 언제
나왔는지도 포함하는 성질이다.
“평균 10ms 걸린다”는 관측한 속도에 대한 말이고,
“항상 100ms 안에 끝난다”는 마감(deadline)을 넘지 않는다는 상한의 약속이다.
평균이 짧아도 드물게 3초씩 멈추면 두 번째 약속은 지킬 수 없다.

마감을 넘겼을 때의 의미로 세 가지가 구분된다.
하드 실시간은 마감을 넘기면 시스템의 시간적 정확성을
위반하고, 펌 실시간은 늦은 결과의 가치가 사라지지만 일부 위반은 허용하며,
소프트 실시간은 늦어질수록 가치나 품질이 낮아진다.
제품에서 “실시간”이라고 부르는 기능은 대부분 엄격한 마감 보장이 아니라 짧은
지연과 최신 상태에 대한 기대다.

### 요구를 세 가지 질문으로 적는다

글은 요구사항을 쓸 때 답해야 할 질문 세 개를 제시한다.

| 질문                       | 요구사항에 적을 내용                           | 선택에 미치는 영향                            |
| -------------------------- | ---------------------------------------------- | --------------------------------------------- |
| 얼마나 늦어도 되는가?      | 시작·종료 시점, 허용 지연, 목표 달성 비율      | 폴링 간격, 전송·처리 예산, 오래된 상태의 표시 |
| 누가 언제 보내야 하는가?   | 서버의 변경 통지, 클라이언트의 명령, 발생 빈도 | 반복 조회, 서버 스트림, 양방향 메시지 연결    |
| 놓친 것은 어떻게 되찾는가? | 최신 상태만 복구, 모든 이벤트 재생, 중복 허용  | 스냅샷, 이벤트 로그와 커서, 멱등 처리         |

파일 처리 완료 알림을 예로 들면 “실시간으로 알려 준다”보다 다음
문장이 구현에 도움이 된다.
사용자가 작업 목록을 보고 있고 통신 가능한 동안,
서버가 완료 상태를 확정한 시점부터 목록에 반영될 때까지의 지연을 측정하며,
목표는 99%를 2초 이내에 반영하는 것이다.
연결을 복구하면 현재 목록을 다시 조회하고,
확인하지 못한 상태는 갱신 중으로 표시한다.
여기서 달성하려는 기준이 SLO이고 실제로 측정한 지연이나 성공 비율이 SLI다.
측정 기간과 분모도 정해야 하고,
화면이 닫혀 있던 시간을 제외했다면 그 조건을 숨기지 말아야 한다.

### 지연과 최신성은 다르다

지연(latency)은 어떤 일이 시작되고 관측될 때까지 걸린 시간이다.
최신성(freshness)은 지금 보고 있는 상태가 원본의 현재 상태를
얼마나 반영하는지다.
연결이 끊긴 동안 변경이 일어났는데 화면이 그대로라면 마지막 이벤트의 전송 지연이
아무리 짧았어도 화면은 오래된 상태일 수 있다.
반대로 문서가 하루 동안 바뀌지 않았다면 `updatedAt`이 어제라는 이유만으로
오래됐다고 판단할 수 없다.
마지막 데이터 변경 시각, 마지막 서버 확인 시각, 마지막으로 적용한 버전은 서로
다른 정보이므로 UI에 “방금 갱신됨”을 쓸 때도 무엇을 확인한 시각인지 정해야 한다.

## 동작 방식

### 전송 수단은 경로의 한 구간만 정한다

이벤트가 서버에서 발생해 화면에 보이기까지는 여러 단계가 있고,
WebSocket이나 SSE는 그중 전달 방법만 정한다.
서버 큐가 밀리는 문제나 브라우저의 긴 JavaScript 작업은 해결하지 않는다.
서버가 20ms 만에 보냈더라도 메인 스레드가 큰 파일을 분석하느라 막혀 있으면
화면 반영은 늦어진다.
브라우저 타이머도 정확한 예약 장치가 아니어서 `setTimeout(fn, 100)`을 100ms 상한
보장으로 읽을 수 없다.
그래서 보장 범위를 나눠 적는다.
전송은 연결과 스트림 안의 순서와 전달 특성,
애플리케이션은 이벤트 식별과 재생 범위와 중복 처리와 상태 재조회,
서비스 운영은 특정 조건에서 지연 목표를 얼마나 자주 충족하는지,
사용자 경험은 단절·복구 중·오래된 데이터 상태를 어떻게 알리는지를 약속한다.

### 폴링과 롱폴링

폴링은 클라이언트가 일정 간격으로 서버에 변경을 묻는 방식이다.
간격을 Δ라고 하고 변경이 구간에 고르게 일어난다고 가정하면 평균 대기 시간은 대략
Δ/2이고, 클라이언트가 N개면 요청률은 대략 N/Δ다.
1만 개 클라이언트가 5초마다 조회하면 초당 약 2천 건이다.
간격을 줄여 지연을 낮추면 변경이 없는 동안의 조회 비용도 같이 늘어난다.
최신 상태만 조회하면 두 조회 사이의 중간 변화는 알 수 없고,
모든 이벤트가 필요하면 조회 API가 마지막 커서 이후의 이벤트를 돌려줘야 한다.

롱폴링은 변경이 없을 때 응답을 바로 끝내지 않고 기다렸다가, 변경이 생기거나 대기
시간이 지나면 응답하고 클라이언트가 곧바로 다음 요청을 보낸다.
응답을 받고 다음 요청을 여는 짧은 틈에도 이벤트는 일어날 수 있으므로 “연결이
열려 있을 때 발생한 이벤트만 보내기”로 구현하면 누락이 생긴다.
서버가 커서 이후의 이벤트를 보관해 다음 요청에 돌려줘야 하며 롱폴링 자체가 그
저장소를 만들어 주지는 않는다.
프록시가 먼저 응답을 끊지 않도록 애플리케이션의 대기 시간과 중간 장비의
타임아웃도 맞춰야 한다.

### SSE

SSE는 서버가 HTTP 응답을 열어 둔 채 텍스트 이벤트를 이어 보내는 방식이며
브라우저에서는 `EventSource`로 구독한다.
빈 줄이 이벤트 블록을 구분하고, `id`는 재연결 때 이어받을 위치, `retry`는 재연결
대기 시간, 콜론으로 시작하는 줄은 메시지 이벤트를 일으키지 않는 주석이다.
SSE가 JSON 프로토콜인 것은 아니어서 데이터에 JSON 문자열을 실으면
클라이언트가 `JSON.parse()`한다.

`EventSource`는 연결이 끊기면 재연결을 시도하고,
직전에 받은 `id`를 `Last-Event-ID` 헤더로 보낸다.
그러나 서버가 이벤트를 보관하고 재생하지 않으면 빠진 내용은 돌아오지 않는다.
브라우저가 이벤트를 수신했다는 사실은 애플리케이션이 그 이벤트를 성공적으로
적용했다는 뜻도 아니다.
새로고침 후 새로 만든 `EventSource`는 이전 객체의 커서를 이어받지 못하므로,
재시작 뒤에도 이어받으려면 저장한 애플리케이션 커서나 서버 스냅샷으로
시작하는 계약이 필요하다.

기본 `EventSource` 생성자는 URL과 `withCredentials`만 받고 임의의
`Authorization` 헤더를 넣을 수 없다.
같은 오리진의 쿠키 인증이나 자격 증명을 허용한 CORS를 검토하고,
헤더나 POST 본문이 필요하면 `fetch`로 응답 스트림을 읽되 이벤트 구분과 재연결과
커서 처리를 직접 구현해야 한다.
토큰을 URL에 넣으면 로그나 관측 도구에 남을 수 있다.

### WebSocket

WebSocket은 연결을 열어 둔 채 양쪽이 독립적으로 메시지를 보내는 프로토콜이다.
HTTP/1.1에서는 업그레이드 요청에
서버가 101 Switching Protocols로 응답한 뒤 프레임을 주고받고,
HTTP/2와 HTTP/3에서는 확장 CONNECT로 연결하는 방법이 정의돼 있다.
프레임(프로토콜의 전송 단위)과 메시지(앱이 받는 논리적 단위)는 다르고,
패킷 수와 프레임 수와 `message` 이벤트 수는 서로 다른 숫자다.
클라이언트 프레임의 마스킹은 암호화가 아니며 전송 구간 보호에는 `wss://`를 쓴다.

기본 WebSocket API에는 자동 재연결이 없다.
재시도 간격을 늘리는 백오프와 무작위 지터를 적용하고, 인증
만료나 권한 거부나 사용자의 명시적 종료처럼 재시도하면 안 되는 경우를 구분하며,
이전 연결의 타이머와 핸들러를 정리하고, 연결이 잠깐 열렸다 곧 닫히는 상황을
고려해 백오프 초기화 시점을 `open` 발생만으로 정하지 않는다.
`open` 이벤트는 서버가 구독을 받아들이고 누락분을 전달했다는 뜻이 아니므로 구독
승인과 동기화 완료를 별도 메시지로 알리는 편이 좋다.

하트비트는 상대가 응답하는지 확인하는 신호다.
프로토콜에는 Ping/Pong 프레임이 있지만 브라우저 JavaScript에는 이를 직접
보내는 API가 없어서 응답 시간이 필요하면 `{"type":"ping"}` 같은 별도 메시지와
응답을 설계해야 한다.
pong은 그 왕복 경로가 동작했다는 증거일 뿐 구독한 데이터가
최신이라는 증거는 아니다.

기본 API에는 수신 속도에 맞춰 송신을 조절하는 백프레셔도 없다.
커서 위치나 진행률 같은 현재 값은 중간 값을 합치고 최신만 반영하고,
채팅 기록이나 변경 이력은 유실 없이 이어받을 로그와 배치를 구성하고,
사용자가 실행한 명령은 요청 식별자로 결과를 확인하고 중복 실행을 막는다.
다만 서로 다른 변경을 뜻하는 이벤트까지 “마지막 것만 남기기”로
합치면 정보가 사라진다.
연결 후에도 Origin을 허용 목록과 대조하고 사용자 인증과 구독 대상별 권한을
검사해야 하며, 로그아웃이나 계정 전환이나 권한 회수 뒤에 이전 구독이 남지 않게
연결 수명을 세션에 묶는다.

## 구현하기

### 스냅샷과 커서와 재생을 함께 쓰는 SSE

글이 강조하는 복구 계약을 실제로 돌려볼 수 있게 줄인 예제다.
서버는 이벤트 로그를 유한하게 보관하고,
스냅샷과 커서를 같은 상태 경계에서 한 번에 만들며, 보관 범위를 벗어난 커서에는
조용히 넘기지 않고 `reset` 이벤트로 재시작을 지시한다.
Node.js에서 `node server.mjs`로 실행하며 필자가 로컬에서 스냅샷,
`Last-Event-ID` 재생, `cursor=0` 재생이 의도대로 나오는 것까지 확인했다(`reset`
경로는 따로 실행해 보지 않았다).

```js
import http from "node:http";

const log = []; // 이벤트 로그: { id, type, data }
const MAX_LOG = 1000; // 보관 상한. 이보다 오래된 커서는 복구할 수 없다
const jobs = new Map(); // 현재 상태(스냅샷의 원본)
const clients = new Set();
let nextId = 1;

function write(res, ev) {
  res.write(`id: ${ev.id}\nevent: ${ev.type}\ndata: ${JSON.stringify(ev.data)}\n\n`);
}

function publish(type, data) {
  const ev = { id: nextId++, type, data };
  log.push(ev);
  if (log.length > MAX_LOG) log.shift();
  for (const res of clients) write(res, ev);
}

http
  .createServer((req, res) => {
    const url = new URL(req.url, "http://localhost");

    if (url.pathname === "/snapshot") {
      // 스냅샷과 커서를 같은 상태 경계에서 한 번에 만든다
      res.setHeader("content-type", "application/json");
      res.end(JSON.stringify({ cursor: nextId - 1, jobs: Object.fromEntries(jobs) }));
      return;
    }

    if (url.pathname === "/events") {
      const last = Number(req.headers["last-event-id"] ?? url.searchParams.get("cursor") ?? 0);
      res.writeHead(200, {
        "content-type": "text/event-stream",
        "cache-control": "no-cache",
        "x-accel-buffering": "no", // nginx 버퍼링 끄기
      });
      const oldest = log.length ? log[0].id : nextId;
      if (last > 0 && last < oldest - 1) {
        // 보관 범위를 벗어난 커서: 조용히 넘기지 않고 재시작을 지시한다
        res.write("event: reset\ndata: {}\n\n");
      } else {
        for (const ev of log) if (ev.id > last) write(res, ev); // 누락분 재생
      }
      clients.add(res);
      const ping = setInterval(() => res.write(": keep-alive\n\n"), 15000);
      req.on("close", () => {
        clients.delete(res);
        clearInterval(ping);
      });
      return;
    }

    if (req.method === "POST" && url.pathname.startsWith("/jobs/")) {
      const id = url.pathname.split("/")[2];
      const job = { id, status: "done", version: (jobs.get(id)?.version ?? 0) + 1 };
      jobs.set(id, job);
      publish("job-updated", job);
      res.end("ok");
      return;
    }

    res.statusCode = 404;
    res.end();
  })
  .listen(3000, () => console.log("http://localhost:3000"));
```

클라이언트는 스냅샷으로 시작해 그 커서 이후를 구독하고,
엔티티 버전으로 늦게 온 상태가 최신을 덮지 못하게 하며,
`reset`을 받으면 스냅샷부터 다시 시작한다.
이 예제는 브라우저 콘솔에서 서버와 같은 오리진에 로드했을 때를 가정하며 필자가
브라우저에서 실행해 보지는 않았다.

```js
const state = new Map();
let cursor = 0;
let source;

async function resync() {
  const snap = await (await fetch("/snapshot")).json();
  state.clear();
  for (const [id, job] of Object.entries(snap.jobs)) state.set(id, job);
  cursor = snap.cursor;
  connect();
}

function connect() {
  source?.close();
  source = new EventSource(`/events?cursor=${cursor}`);
  source.addEventListener("job-updated", (e) => {
    const job = JSON.parse(e.data);
    const cur = state.get(job.id);
    if (!cur || job.version > cur.version) state.set(job.id, job); // 늦게 온 이전 버전은 무시
    cursor = Number(e.lastEventId);
  });
  source.addEventListener("reset", () => {
    source.close();
    resync(); // 복구 불가를 인식하고 스냅샷으로 재시작
  });
}

resync();
```

### 겹치지 않는 폴링

폴링은 한 번의 조회와 반영이 끝난 뒤에 다음 조회를 예약해야
요청이 쌓이지 않는다.
`setInterval`에서 요청을 보내면 느린 서버에서 요청이 겹치고 응답 순서가 뒤집혀
오래된 상태가 화면을 덮을 수 있다.
실패가 반복되면 대기 시간을 늘리고 무작위 지터를 섞으며,
이때 시작 시점 간격은 조회·반영 시간에 `intervalMs`를 더한 값이므로 앞의 Δ/2
계산을 그대로 대입하면 안 된다.
필자는 `read`가 두 번 실패한 뒤 성공하는 상황을 Node.js에서 흉내 내 백오프 후
정상 폴링으로 돌아오는 것을 확인했다.

```js
function startPolling({ read, apply, onError }, intervalMs = 5000) {
  let stopped = false;
  let timer;
  let failures = 0;
  const ctl = new AbortController();

  async function tick() {
    if (stopped) return;
    try {
      apply(await read(ctl.signal)); // read는 signal을 fetch에 연결하고 HTTP 오류도 던진다
      failures = 0;
    } catch (err) {
      if (stopped) return;
      failures += 1;
      onError(err);
    }
    if (stopped) return;
    // 성공은 고정 간격, 실패는 백오프(최대 60초)와 지터
    const ceiling = Math.min(60000, intervalMs * 2 ** Math.min(failures, 4));
    const delay = failures ? ceiling * (0.5 + Math.random() * 0.5) : intervalMs;
    timer = setTimeout(tick, delay);
  }

  tick();
  return () => {
    stopped = true;
    clearTimeout(timer);
    ctl.abort();
  };
}
```

## 값 정하기

글은 값을 정해 주지 않고 요구에서 후보를 좁히는 순서를 제안한다.
아래 표는 그 기준을 정리한 것이며 숫자는 모두 예시이자 출발점이다.

| 상황                                                              | 출발점                              | 근거                                                |
| ----------------------------------------------------------------- | ----------------------------------- | --------------------------------------------------- |
| 파일 작업 완료를 몇 초 간격으로 확인해도 되고 사용자 수가 작다    | 폴링                                | 기존 조회 API로 시작하기 쉽다                       |
| 목표를 맞추려 조회 간격을 계속 줄이고 응답 대부분이 “변경 없음”   | SSE                                 | 서버가 변경을 통지하므로 빈 조회 비용이 사라진다    |
| 양쪽이 위치와 입력 상태를 자주 보낸다                             | WebSocket                           | 양방향 메시지 연결이 자연스럽다                     |
| 이미 WebRTC 피어 연결이 있고 오래된 위치는 재전송하지 않아도 된다 | DataChannel                         | 순서와 재전송 정책을 조정할 수 있다                 |
| 취소 같은 클라이언트 명령이 드물다                                | SSE와 별도 POST                     | 입력이 있다는 이유만으로 SSE가 부적합한 것은 아니다 |
| 협업 커서는 100ms, 일반 알림은 30초                               | 요구의 예시일 뿐 보편 기준이 아니다 | 허용 지연은 사용자 행동과 실패 비용으로 정한다      |

측정할 경계도 정해야 한다.
서버 내부 지연(상태 확정부터 전송까지), 클라이언트
처리 지연(핸들러 진입부터 화면 반영까지), 복구 지연(재시도부터 누락분 적용까지),
최신 여부 미확인 시간(단절이나 동기화 미확인이 지속된 시간)을 따로 잰다.
브라우저 안의 구간은 `performance.now()` 같은 단조 시계로 재고,
서버 시각과 브라우저 시각의 차이로 종단 지연을 낼 때는 시계 오차를 고려한다.
RTT의 절반을 편도 지연으로 쓰지 않고, 평균과 함께 p95와 p99를 보되 서버와
브라우저에서 각각 구한 p99를 더해 전체 p99로 쓰지 않는다.
도착하지 않은 이벤트를 표본에서 빼면 성공한 것만 재게 되므로 목표 시간 안에
적용한 비율과 미수신·복구 실패를 함께 집계한다.

## 트레이드오프

### 조회 간격을 줄이면 지연이 줄지만 빈 조회가 늘어난다

폴링은 간격과 요청량을 맞바꾼다.
평균 대기 Δ/2를 줄이려고 Δ를 줄이면 요청률 N/Δ가 그만큼 늘고,
변경이 드문 서비스에서는 늘어난 요청 대부분이 “변경 없음”이다.
`ETag`와 조건부 요청이 응답 본문의 반복 전송은 줄여 주지만 요청이 서버에 도착해
변경 여부를 확인하는 비용까지 없애지는 않는다.
그렇다고 SSE로 가면 끝나는 것도 아니어서, 서버가 연결과 상태를 들고 있어야 하고
앞에서 본 복구 계약과 프록시 버퍼링 문제가 새로 생긴다.

### 순서를 지키면 오래된 값 때문에 새 값이 기다린다

순서대로 빠짐없이 도착하는 성질은 유용하지만 앞의 데이터가 유실돼 복구를
기다리는 동안 뒤의 데이터도 전달되지 못할 수 있다.
이것이 Head-of-Line Blocking이다.
과거 커서 위치를 되찾느라 더 새로운 위치까지 기다리는 것은 요구에 맞지 않을 수
있고, 중간 위치를 버리고 최신 위치를 빨리 쓰는 편이 낫다.
그러면 순서와 재전송을 다르게 고를 수 있는 WebRTC DataChannel이 후보가 된다.
`ordered: false`와 `maxRetransmits: 0`을 주면 재전송 없이 순서에 얽매이지 않는
채널을 만들 수 있다.
다만 `maxRetransmits`와 `maxPacketLifeTime`은 동시에 지정하지 않으며, 이 옵션은
화면 반영까지의 마감 보장이 아니다.
늦거나 뒤바뀐 위치를 무시하려면 메시지에 순서 번호를 넣는 등
애플리케이션의 판단이 필요하다.

얻는 것과 치르는 것을 함께 보면 이렇다.
피어 연결을 쓰면 시그널링을 직접 준비해야 하고 ICE와
STUN과 TURN을 고려해야 하므로 “피어 간 통신이니 서버 비용이 없다”거나 “항상 직접
연결된다”고 가정할 수 없다.
공동 문서 상태처럼 서버가 확정해야 하는 것은 낮은 지연으로 메시지를 교환해도
동시 편집 충돌과 최종 상태의 권위가 해결되지 않는다.
WebTransport는 독립된 스트림으로 한
스트림의 유실 복구가 다른 스트림의 대기를 직접 만들지 않게 해 주지만,
같은 스트림 안의 대기는 남고 연결의 대역폭과 혼잡 제어는 공유한다.
지원 브라우저와 서버, 프록시, 네트워크의 HTTP/3와 UDP 경로도 함께 확인해야 한다.

### 연결을 하나로 줄이면 복구 상태 머신이 복잡해진다

같은 서비스의 탭을 여러 개 열면 SSE나 WebSocket 연결도 탭마다 늘어난다.
`BroadcastChannel`은 같은 오리진 안의 실행 환경끼리 메시지를 나눌 뿐 서버와의
전송 수단이 아니고 닫힌 탭을 위해 메시지를 보관하지 않는다.
한 탭이 연결을 맡거나 `SharedWorker`가 연결을 소유하는 설계는 소유 탭 종료,
소유권 교체, 늦게 열린 탭의 초기 스냅샷,
계정 전환 때의 구독 정리를 모두 처리해야 성립한다.
연결 하나를 줄이려고 복구 상태 머신을 훨씬 복잡하게 만들지 않는지 비교해야 한다.

### 전송 수단을 고르는 일과 업무 효과를 한 번으로 만드는 일은 다른 문제다

| 계약              | 얻는 성질                                   | 남는 책임                                |
| ----------------- | ------------------------------------------- | ---------------------------------------- |
| 최대 한 번        | 중복을 피하지만 전달되지 않을 수 있다       | 누락을 허용하거나 상태를 재조회한다      |
| 최소 한 번        | 재시도나 재생으로 전달을 추구하며 중복 가능 | 중복 제거와 멱등 처리                    |
| 한 번의 업무 효과 | 같은 명령을 여러 번 받아도 효과는 한 번     | 서버의 영속 기록, 트랜잭션, 키 범위 설계 |

“WebSocket이라 정확히 한 번 처리된다”는 약속은 성립하지 않는다.
서버가 명령을 처리한 직후 연결이 끊기면 클라이언트는 결과를 못 받을 수 있고,
이때 타임아웃의 의미는 실패가 아니라 성공했는지 아직 모른다는 것이다.
멱등 키로 이를 막으려면 키의 기록과 실제 상태 변경을 원자적으로 다뤄야 하고, 키
보관 기간과 같은 키에 다른 입력이 왔을 때의 정책도 정해야 한다.

## 함정

- 연결됨을 최신 상태로 읽는다. 연결이 열렸어도 구독을 복원하지 않았거나 단절 중의 이벤트를 따라잡는 중일 수 있으므로 연결 상태와 데이터 동기화 상태를 별도로 둔다.
- 스냅샷을 읽은 뒤 따로 “지금의 최신 커서”를 가져와 붙인다. 중간 변경이 빠졌는데도 이미 반영한 위치처럼 보일 수 있으므로 스냅샷의 내용과 커서는 같은 상태 경계를 가리켜야 한다.
- 오래된 커서를 조용히 무시하고 최신 이벤트부터 보낸다. 로그 보관 기간을 넘기면 복구가 불가능하다는 사실을 서버가 명시하고 클라이언트는 새 스냅샷으로 초기화해야 한다.
- 순서가 있는 연결이라 버전 검사가 필요 없다고 생각한다. 한 연결 안의 순서와 서비스 전체의 변경 순서는 범위가 다르고, HTTP 재조회와 스트림 수신이 경합하거나 재연결 뒤 이벤트가 다시 오면 버전 검사가 필요하다.
- 차분 이벤트(“진행률에 10을 더한다”)에 최신 번호만 적용한다. 중간 이벤트 누락을 무시하면 상태가 맞지 않는다.
- 주석 줄을 보냈으니 유휴 타임아웃이 해결됐다고 믿는다. 실제로 flush되는지와 각 장비의 제한을 확인해야 하고, 이 동작이 브라우저가 최신 상태를 적용했다는 뜻도 아니다.
- `Cache-Control: no-cache`가 전송 버퍼링까지 끈다고 생각한다. 고르게 보낸 이벤트가 묶여서 도착하면 중간 버퍼를 먼저 보며, Nginx의 `proxy_buffering`과 `X-Accel-Buffering: no`는 Nginx의 동작이고 모든 CDN과 프록시에서 통하지 않는다.
- 푸시를 숨은 페이지를 계속 깨우는 수단으로 설계한다. 푸시는 정확한 시각의 실행 예약이 아니고, 알림을 받았다고 페이지 상태가 갱신된 것도 아니며, 알림을 눌러 돌아왔을 때 서버에서 현재 상태를 확인하는 흐름이 필요하다.
- 로컬 개발 서버에서 이벤트가 바로 도착하는 것을 목표 달성으로 읽는다. 실제 배포 경로의 CDN과 로드밸런서와 사용자 네트워크에서 다시 검증해야 한다.

- 로그 보관 기간을 넘긴 커서에 서버가 복구 불가를 명시하는가?
- 이벤트 ID, 커서, 엔티티 버전, 요청 ID, 멱등 키의 역할을 구분해 문서화했는가?
- UI가 연결됨과 동기화 완료를 구분해 표시하는가?
- 재시도에 백오프와 지터가 있고 재시도하면 안 되는 실패를 구분하는가?
- 느린 클라이언트의 송신 큐에 상한과 합치기 또는 재동기화 정책이 있는가?
- 로그아웃과 권한 회수 뒤에 구독이 종료되는가?
- 실제 배포 경로에서 p99와 복구 지연을 측정했는가?

## 기억할 원칙

### 실시간은 전송이 아니라 계약이다

전송 수단은 서버에서 화면까지의 경로 중 한 구간만 정한다.
유효한 시간과 실패 조건, 누락을 되찾는 방법, 처리 완료를 확인하는 방법이
정해지지 않으면 어떤 수단을 골라도 “실시간”이라는 말은 비어 있다.
모든 상황의 마감을 약속할 수 없더라도 언제 데이터가 유효하고 언제 다시 확인해야
하는지는 분명히 표현할 수 있다.

### 연결과 데이터는 서로 다른 상태다

연결이 열렸다는 사실, 송신 버퍼가 비었다는 사실, pong이 돌아왔다는 사실은 모두
경로가 동작했다는 증거일 뿐 데이터가 최신이거나 명령이 처리됐다는 증거가 아니다.
UI와 서버 계약은 연결 단계와 동기화 단계를 따로 표현해야 하고,
확인하지 못한 상태를 최신으로 표시하지 않아야 한다.
