# htmx에서 Datastar로 옮긴 이유

원문: [Why I switched from HTMX to Datastar](https://everydaysuperpowers.dev/articles/why-i-switched-from-htmx-to-datastar/)

HN 토론: <https://news.ycombinator.com/item?id=45536000> (315점, 380개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/nx57oo/why_i_switched_from_htmx_datastar>

GN 토론: <https://news.hada.io/topic?id=23582>

## 요약

Everyday Superpowers의 Chris가 htmx에서 Datastar로 옮긴 경위를 정리한 글이다.
서두는 2022년 DjangoCon Europe에서 David Guillot이 발표한 사례로 시작한다.
React 앱처럼 동적으로 보이고 느껴지는 웹 앱을 React에서 htmx로 전환해
코드베이스를 거의 70% 줄이면서 기능은 오히려 개선했다는 이야기이며,
그 뒤로 여러 팀이 단일 페이지 앱을 다중 페이지 하이퍼미디어 앱으로 바꾸면
코드가 60% 이상 줄고 개발자 경험과 사용자 경험이 모두 나아진다는 사실을 확인해
왔다는 것이다.
저자는 htmx에서 Datastar로 옮겼을 때 비슷한 결과를 얻었다고 말한다.

전환의 계기는 FlaskCon 2025 발표를 준비하다 부딪힌 벽이었다.
UI 조각들의 동기를 맞추려고 htmx와 AlpineJS를 함께 다루고 있었는데
둘이 어긋났고,
컴포넌트가 왜 갱신되지 않는지 디버깅하는 데 몇 시간을 잃었다.
두 라이브러리는 서로 소통하지 않으며
서로 다른 개발자가 만든 별개의 라이브러리이므로
둘을 협력시키는 책임은 사용자에게 있다는 것이다.
컴포넌트를 여러 시점에 초기화하고 이벤트를 조율하는 춤을 관리하느라
원하는 것보다 많은 코드를 쓰고 감당할 수 있는 것보다 많은 시간을 쓰고 있었다.
Datastar가 두 라이브러리의 기능을 더 작은 내려받기 용량으로 제공한다는 것을 알고
시험해 봤더니 땀 한 방울 흘리지 않고 처리했고 결과 코드도 훨씬 이해하기 쉬웠다고
적는다.
11KB 미만이라는 용량은 특히 모바일 사용자의 페이지 적재 성능에 좋다는 점도
덧붙인다.

API 비교가 글의 다음 축이다.
htmx에서는 대체로 요청할 URL, 응답으로 대상을 지정할 요소, 그리고 동작 방식을
조정하는 속성을 붙여야 한다.
그가 든 예시는 `hx-target`, `hx-select`, `hx-swap`, `hx-trigger`,
`hx-get`이 모두
달린 앵커다.
전부 필요한 것은 아니지만 매번 두세 개는 붙게 되며,
조상 요소를 거슬러 올라가 기대한 동작을 바꾸는 속성이 있는지 확인해야 할 때도
있고
그런 버그는 혼란스럽다는 것이다.
Datastar에서는 보통 `data-on-click="@get('/rebuild/status-button')"` 하나면
된다.

핵심 차이는 어디서 갱신을 결정하느냐다.
htmx는 HTML 명세를 밀고 나가려는 프런트엔드 라이브러리이고,
Datastar는 고성능의 웹 네이티브 실시간 갱신 앱을 목표로 하는 서버 주도
라이브러리라고
정리한다.
htmx에서는 페이지 저 멀리를 갱신하더라도 요청을 촉발하는 요소에 속성을 붙여
동작을
서술하므로 논리가 여러 층에 흩어지는 반면,
Datastar는 서버가 무엇을 바꿀지 결정하므로 갱신 논리가 한곳에 모인다는 것이다.
그는 htmx 문서의 `hx-select-oob` 예시를 들어, 버튼 하나가 알아야 하는 것이
너무 많고 서버가 무엇을 돌려줄지 HTML 밖에서 알아야 하므로
이 지점에서 htmx가 자신이 좋아하는 행동의 지역성을 잃는다고 지적한다.
Datastar에서는 같은 동작을 클릭 속성 하나로 두고,
서버가 갱신 대상과 같은 id를 가진 최상위 요소 두 개를 담은 HTML 문자열을
돌려주면
된다.

그다음 절은 컴포넌트 단위 사고를 권한다.
정보를 보여 주거나 오류를 보여 주는 두 상태를 각각 템플릿으로 두고
서버가 상태에 맞는 컴포넌트를 통째로 렌더링해 보내면,
잘못된 상태에 들어가거나 사용자 상태를 놓치는 일을 막을 수 있다는 것이다.
여러 컴포넌트를 한 번에 갱신하는 예로는 장바구니를 든다.
David Guillot의 발표에서 인상적이었던 것이 멀리 떨어진 즐겨찾기 개수가 함께
갱신되는 장면이었는데, 그 팀은 htmx가 JavaScript 이벤트를 촉발하고
그 이벤트가 원격 컴포넌트로 하여금 GET 요청을 보내 스스로를 갱신하게 하는
방식으로
구현했다.
Datastar에서는 동기 함수 안에서도 여러 컴포넌트를 한 번에 갱신할 수 있으며,
Django 예시로 `DatastarResponse`에 `SSE.patch_elements`를 두 번 담아
구매 폼과 장바구니 개수를 함께 보내는 코드를 제시한다.

웹 네이티브라는 절에서는 철학의 차이를 말한다.
htmx가 HTML 명세를 앞으로 밀려 한다면,
Datastar는 CSS 뷰 트랜지션과 서버 전송 이벤트와 웹 컴포넌트 같은 웹 네이티브
기능의
채택을 촉진하는 데 더 관심이 있다는 것이다.
그는 복잡한 AlpineJS 컴포넌트를 리팩터링해 여러 곳에서 재사용할 단순한 웹
컴포넌트로
뽑아낸 것을 가장 큰 성과로 꼽는다.
실시간 갱신에 대해서는, 대부분의 htmx 개발자가 몇 초마다 폴링하거나
직접 웹소켓 코드를 써서 복잡도를 키우는 반면
Datastar는 SSE로 서버가 갱신을 밀어 준다고 설명한다.
연결이 끊겨도 브라우저가 알아서 재연결을 시도하고 마지막으로 받은 이벤트를
서버에 알릴 수도 있다는 점을 좋게 본다.

커뮤니티에서 배운 요령도 정리한다.
컴포넌트 전체를 다시 렌더링해 내려보내는 것을 두려워하지 말라는 것,
성능에 큰 영향이 없고 압축률도 좋으며
브라우저가 HTML 문자열을 파싱하는 것은 매우
빠르다는 것이다.
서버가 진실의 상태이고 브라우저보다 강력하므로 상태 대부분을 서버가 다루게 두고
반응형 시그널은 생각만큼 자주 필요하지 않다는 조언,
그리고 웹 컴포넌트가 논리를 캡슐화하기 좋다는 조언이 이어진다.
마지막으로 Datastar가 열어 주는 가능성을 든다.
데이터베이스 모니터링 데모,
Anders Murphy가 저렴한 서버에서 만든 10억 개 체크박스,
그리고 미국 전역 레이더 관측소 데이터를 100밀리초 안에 반영하며
초당 80만 개 이상의 점을 갱신하고 한 시간까지 시간을 되감을 수 있는 웹 앱이다.
htmx를 처음 쓸 때의 기쁨을 느껴 본 사람이라면 Datastar에서 같은 도약을 느낄
것이라는
문장으로 끝난다.

## 분석

### 전환의 실제 원인은 htmx가 아니라 htmx와 Alpine의 조합이었다

글이 서술하는 계기는 명확하다.
htmx와 AlpineJS를 함께 쓰다가 둘이 어긋났고,
둘을 협력시키는 책임이 자신에게 있었다.
즉 문제의 위치는 htmx 안이 아니라 두 라이브러리 사이의 빈틈이다.

이 진단이 정확하다면 선택지는 셋이다.
빈틈을 메우는 접착 코드를 계속 쓰거나, 둘 중 하나를 버리거나,
둘의 일을 함께 하는 도구로 갈아타거나.
저자는 세 번째를 택했고, 그 선택 자체는 합리적이다.
Datastar가 요청 처리와 클라이언트 상태를 한 모델 안에 두고 있기 때문이다.

Lobste.rs에서는 두 번째 선택지를 권하는 반론이 나왔다.
carlana는 저자가 Alpine과 htmx를 조합하는 데 어려움을 겪은 것이라면
새 도구로 갈아타기보다 htmx를 빼고 Alpine이 전부 처리하게 하는 편이 쉬웠을
것이라고
적었다.[^carlana]
gonz는 반대 방향을 제시한다.
서버가 진실의 원천이기를 원한다면 데이터가 저장되고 수정되는 애매한 중간 층은
무의미하므로 Alpine 쪽을 빼는 것이 합리적이며,
글에서 언급된 것 중 htmx로 간단히 못 할 일이 보이지 않는다는 것이다.[^gonz]
hashemi는 또 다른 답을 보고했다.
htmx에서 Alpine AJAX로 옮겼고 Alpine 플러그인이라 htmx보다 직관적이고
점진적 향상으로 통합하기 쉬웠으며, Django 뷰는 그대로 두고 템플릿에서 처리한다는
것이다.[^hashemi]
같은 문제에 최소 네 가지 답이 있고, 글은 자기가 고른 하나만 검토한다.

### 클라이언트 속성이 줄어든 만큼 서버 책임이 늘어난다

글의 API 비교는 속성 다섯 개짜리 htmx 코드와 속성 하나짜리 Datastar 코드를
나란히 놓는다.
시각적으로 강력하지만, 사라진 정보가 어디로 갔는지는 다루지 않는다.

htmx 사용자이자 서두에 인용된 그 발표의 주인공인 David Guillot이 HN에 직접 답을
달았다.
자신의 편향을 먼저 밝히면서, 이 글의 예시가 보여 주는 것이 htmx와 Datastar의
주된 아키텍처 차이라고 정리한다.
htmx는 HTML 주도이고 Datastar는 서버 주도이므로 클라이언트 쪽 API가 단순한 것은
맞지만 그것은 반대쪽이 더 복잡해지기 때문이라는 것이다.
첫 예시에서 HTML 요소가 서버 응답 조각을 어디에 넣을지에 대한 정보를 갖고 있지
않다면 서버가 그것을 알아야 하므로,
그 정보를 서버 어딘가에 써야 한다는 지적이다.
결국 취향의 문제 같다고 덧붙인다.[^David-Guillot]

이 반박은 글의 논지를 무너뜨리지는 않지만 프레임을 바꾼다.
문제는 코드 양이 아니라 결합의 방향이다.
htmx는 HTML이 서버 라우트를 알게 하고, Datastar는 서버가 DOM 구조를 알게 한다.
어느 쪽이 나은지는 팀이 HTML을 더 자주 바꾸느냐 서버를 더 자주 바꾸느냐에
달렸고,
글은 자기 답을 일반적 우위로 제시한다.

### 실시간 갱신이 이 비교의 진짜 승부처다

기능 목록을 정리하면 두 도구의 겹치는 영역은 넓고 갈라지는 지점은 좁다.
HN의 leg100이 글보다 나은 요약을 내놓았다.
Datastar는 모든 응답을 SSE로 보내며,
보통 SSE는 서버가 클라이언트로 이벤트를 미는 데
쓰이지만 Datastar는 버튼 클릭 같은 클라이언트 발신 동작의 응답에도 SSE 인코딩을
쓴다는 것이다.
클릭이 GET을 보내면 서버가 자기가 정한 시간 동안 0개 이상의 SSE 이벤트로
응답한다.
반면 htmx는 SSE를 여러 확장 중 하나로 지원하며 서버 발신 이벤트에 대해서만 쓰고
양방향 상호작용에는 웹소켓을 지원한다.
Datastar에는 프런트엔드 상태를 관리하는 시그널 개념이 있지만 htmx에는 없어
AlpineJS 같은 것이 추가로 필요하다는 정리다.[^leg100]

이 요약이 글이 말하지 않은 것을 드러낸다.
저자가 겪은 문제(htmx + Alpine의 조합)는 정확히 leg100이 짚은 마지막 항목,
즉 htmx에 시그널이 없다는 사실에서 나온다.
그리고 htmx 4.0이 스트리밍과 SSE를 코어에 넣겠다고 예고한 것은
이 차이의 절반을 메우려는 움직임이다.
남는 차이는 클라이언트 상태 관리이며,
htmx는 그것을 코어에 넣지 않겠다고 명시했다.
두 도구의 경계는 여기서 갈린다.

## 비평

### htmx가 못 한다고 서술한 것의 상당수를 htmx는 이미 한다

글의 API 비교와 갱신 모델 설명은 htmx가 HTML 쪽에만 동작을 서술할 수 있다는 전제
위에 서 있다.
이 전제가 부정확하다는 지적이 세 커뮤니티 모두에서 나왔다.

Lobste.rs의 mccd는 Datastar가 htmx보다 의견이 강한 도구로 보이고 그 점이 좋지만,
페이지 갱신을 다루는 앞부분은 부분적으로 틀렸다고 적었다.
htmx도 응답 헤더로 서버가 대상과 스왑 방식을 정하게 할 수 있다는 것이다.[^mccd]
tsion은 응답 HTML의 대역 외 스왑도 있다고 덧붙였다.[^tsion]
HN의 Hnus는 더 짧게,
htmx도 OOB 갱신으로 그 전부를 할 수 있지 않느냐고 물었다.[^Hnus]
CraigJPerry는 자신이 Datastar로 시작했다가 지금은 htmx를 쓴다며,
Datastar API가 조금 더 낫지만 htmx 2.0도 같은 접근을 지원하고
핵심은 htmx가 OOB 갱신이라 부르는 것이며 그것이 있으면 나머지는 전부 htmx 쪽에
유리하다고 적었다.[^CraigJPerry]

이 지적들이 중요한 이유는 글의 구조 때문이다.
저자는 htmx 문서의 `hx-select-oob` 예시를 인용하면서
바로 그 기능이 자기 주장의 반례라는 점을 다루지 않는다.
버튼이 너무 많이 안다는 비판은 타당하지만,
그것이 htmx의 유일한 방식이라는 서술은 사실과 다르다.
GN에 재수록된 Guillot의 반응에서도 속성을 줄인다는 논리가 htmx에서 선택적으로
붙일
수 있는 속성까지 예시로 든 것이라 온전히 공정하지 않다는 지적이 나온다.

### 상용 라이선스 변경이라는 가장 큰 도입 변수를 글이 언급하지 않는다

글은 Datastar 커뮤니티 경험을 여러 번 긍정적으로 언급하지만
Datastar Pro에 대해서는 한 줄도 쓰지 않는다.
그런데 두 커뮤니티에서 가장 많은 반응을 모은 주제가 바로 그것이었다.

HN에서 rubenvanwyk는 Datastar의 기본적이면서
훌륭한 기능 일부가 Datastar Pro 제품으로
옮겨 갔다는 글을 읽었다며, 오픈소스를 재정적으로 지원하고 싶고 저자도 훌륭하다고
생각하지만 이 선례가 좋지는 않다고 적었다.[^rubenvanwyk]
Lobste.rs의 nemith는 이벤트 기반 설계에 깊은 인상을 받았다가
좋은 기능들이 결제 뒤에 잠겨 있는 것을 발견했고,
유료화 자체에 반대하지는 않지만 좌석 단위 라이선스가 일을 복잡하게 만든다고
적었다.[^nemith]
colman의 증언이 가장 구체적이다.
v1 이전 Datastar로 몇 가지를 만들고 있었는데 새 라이선스 때문에 반대에 부딪히고
있으며, 새롭고 다른 소프트웨어를 쓰는 것 자체가 이미 혁신 토큰을 쓰는 베팅인데
그 위에 라이선스 불확실성까지 얹힌다는 것이다.
v1 이전 버전에 머무르면 보안 수정을 포함한 어떤 갱신도 받지 못하고,
최신으로 옮기면 Pro 기능을 쓰지 않아야 하며 Pro 기능 집합이 빨리 안정되기를
바랄 수밖에 없다고 설명했다.[^colman]
hoistbypetard도 1.0 이전에 무료로 쓸 수 있던 기능이 유료화 뒤로 옮겨 간 점과
그 상업적 조건이 마음에 들지 않아 자신은 참여하지 않겠다고
적었다.[^hoistbypetard]

반론도 있다.
TeddyDD는 Pro 플러그인이 대부분 편의 기능이고
작은 JavaScript로 같은 효과를 낼 수
있으며 `data-persist`는 이미 오픈소스 구현이 있다면서,
오픈소스 프로젝트에서 Pro 플러그인을 쓸 수 없다는 점만 아니면 돈을 낼 의향도
있다고 적었다.[^TeddyDD]
그러나 도입을 검토하는 독자에게 이것은 기능 비교만큼 중요한 정보이며,
전환을 권하는 글이 이를 다루지 않은 것은 공백이다.

### 서버가 DOM을 패치하는 모델에 대한 반감을 과소평가한다

글은 서버가 무엇을 바꿀지 결정하는 것을 일관되게 장점으로 제시한다.
그러나 같은 사실이 여러 사람에게는 도입을 막는 이유로 읽힌다.

HN의 highwaylights는 서버가 HTML을 주입하는 패치 구문이 관심사 분리 관점에서
끔찍해 보이며,
규모가 조금만 커져도 감당하기 힘든 악몽이 될 것 같다고 적었다.[^highwaylights]
adlpz는 더 구체적으로 불편함을 서술한다.
프런트엔드에 하드코딩된 id가 있는 `div`들이 있고,
버튼의 트리거가 어떤 엔드포인트를 블랙박스처럼 호출하고,
백엔드에서 SDK로 `patchElements()` 같은 메서드를 호출하면
그것이 HTTP 스트림의 사용자 정의 이벤트 헤더와 메타데이터로 번역되고,
프런트엔드의 엔진이 그것으로 DOM을 패치한다는 것이다.
추론하기 매우 어렵고 흩어져 있다고 느낀다고 적었다.[^adlpz]
brokegrammer는 더 단순하게, 글의 예시들을 이해할 수 없고
저자가 왜 옮겼는지 결국 모르겠다고 적었다.[^brokegrammer]

이 반응들은 취향의 문제로 치부하기 어렵다.
서버가 클라이언트 DOM의 id 구조를 알아야 한다는 것은 실제 결합이고,
그 결합은 프런트엔드 마크업을 리팩터링할 때 서버 코드를 깨뜨린다.
글은 갱신 논리가 한곳에 모인다는 이점만 세고,
그 한곳이 이제 두 계층의 지식을 모두 갖게 된다는 비용은 세지 않는다.

### 인용된 성공 사례들이 실제로 무엇을 증명하는지 검증되지 않았다

글은 70% 코드 감소로 시작해 10억 개 체크박스와 초당 80만 점 갱신으로 끝난다.
수치는 인상적이지만 비교 기준이 없다.

HN의 gloosx가 첫 수치를 직접 겨냥했다.
70%를 줄였다는 주장은 늘 웃음이 나오는데 원래 코드베이스에서 무슨 일이 있었는지
알 수 없기 때문이며, 해당 발표에는 달까지 늘어질 듯한 저주받은 줄들이 그대로
나온다는 것이다.
그러면서 앱을 최적화한 것인지, 잡음을 대량 삭제한 것인지,
아니면 전부를 300자짜리 거대 줄로 합친 것인지 알기 어렵다고 적었다.[^gloosx]

성능 데모에 대해서도 같은 주의가 필요하다.
체크박스와 레이더 점 갱신은 전부 상태가 단순하고 구조가 균일한 사례다.
이런 작업부하는 하이퍼미디어 모델에 가장 유리하며,
업무용 애플리케이션에서 실제로 어려운 것은 초당 갱신 수가 아니라
권한과 검증과 상태 전이의 복잡성이다.
andersmurphy가 5달러 VPS에서 Pro 기능 없이 돌아가는 데모 세 개를 제시한
것은[^andersmurphy]
기술적 역량의 증거로는 충분하지만, 저자가 만들려는 종류의 앱이 그 데모와 같은
성격인지는 별개의 질문이다.

## 인사이트

### 두 라이브러리를 조합하다 생긴 문제는 세 번째 라이브러리로 가는 근거가 되기 쉽지만 대체로 잘못된 근거다

이 글의 전환 서사는 흔한 구조를 갖는다.
A와 B를 붙여 쓰다가 접합부에서 고생했고,
A와 B를 합친 C로 옮겨 해결했다는 것이다.
이 서사는 설득력이 크지만 검증되지 않은 전제를 품는다.
접합부의 문제가 A나 B의 결함이지 내 설계의 결과가 아니라는 전제다.

Lobste.rs의 두 답변이 그 전제를 흔들었다.
하나는 Alpine만 남기라는 것이고 다른 하나는 htmx만 남기라는 것이다.
둘 다 라이브러리를 늘리지 않고 줄이는 방향이며,
둘 다 새 도구를 배우는 비용이 없다.
저자가 이 선택지들을 검토했는지는 글에 나오지 않는다.

여기서 나오는 실무 규칙은 단순하다.
두 도구의 접합부에서 고생하고 있다면, 갈아타기 전에 하나를 빼 보는 실험을 먼저
해야 한다.
접합부 문제는 대개 두 도구가 같은 책임을 두고 다투기 때문에 생기고,
그 경우 하나를 빼면 사라진다.
합친 도구로 옮기면 지금 다툼은 사라지지만,
그 도구가 감당하지 않는 영역에서 언젠가 같은 다툼이 다시 생긴다.
저자가 웹 컴포넌트를 도입한 대목이 이미 그 조짐이다.

### 오픈소스 유료화에서 가장 비싼 것은 가격이 아니라 소급성이다

Datastar Pro에 대한 반응을 읽어 보면 반대의 근거가 유료화 자체가 아니다.
nemith도 hoistbypetard도 TeddyDD도 개발자가 돈을 받아야 한다는 데는 동의한다.
문제가 된 것은 1.0 이전에 무료였던 기능이 유료로 옮겨 갔다는 사실이다.

colman의 서술이 이 비용의 구조를 정확히 보여 준다.
기존 버전에 머무르면 보안 수정을 못 받고, 최신으로 가면 쓰던 기능을 잃는다.
어느 쪽도 처음 도입할 때 계산에 넣은 시나리오가 아니다.
사용자가 잃은 것은 기능이 아니라 예측 가능성이며,
예측 가능성은 되돌려 줄 수 없는 종류의 자산이다.

이 사건은 앞선 문서들에서 다룬 htmx의 안정성 약속과 흥미로운 대조를 이룬다.
htmx는 코드를 바꾸지 않겠다는 약속을 파기하면서도
기존 버전을 영구 지원하겠다는 약속으로 갈아탔고, 그 교체가 대체로 수용되었다.
Datastar는 코드를 계속 개선하면서 기존 사용자의 조건을 소급해 바꿨고,
그 변경이 기술적 장점을 상쇄할 만큼의 반발을 불렀다.
두 사건이 말하는 것은 같다.
사용자가 실제로 사는 것은 현재 기능이 아니라 미래 조건이며,
그 조건을 바꿀 때는 기존 사용자에게 손해가 가지 않는 경로를 함께 제시해야 한다.

도입을 검토하는 쪽에서 이 교훈을 쓰는 방법도 분명하다.
라이선스 파일을 읽는 것만으로는 부족하고, 그 프로젝트가 수익 모델을 어떻게
바꿔 왔는지의 이력을 봐야 한다.
상용 티어가 있는 오픈소스에서는 무엇이 무료인지보다
무엇이 무료였다가 유료가 되었는지가 더 중요한 정보다.

### 서버 주도와 HTML 주도의 선택은 어느 쪽을 더 자주 고치느냐로 결정된다

David Guillot의 반박은 이 논쟁을 가장 유용한 형태로 정리한다.
정보는 사라지지 않고 어느 한쪽에 적혀야 하며, 선택은 취향의 문제라는 것이다.
다만 취향이라는 말로 끝내면 실무에서 쓸 수 없으므로 한 걸음 더 갈 수 있다.

결합의 방향을 정하는 실질적 기준은 변경 빈도다.
마크업이 자주 바뀌고 서버 라우트가 안정적인 프로젝트에서는
서버가 DOM 구조를 아는 구조가 비싸다.
디자인을 고칠 때마다 서버 코드가 따라 깨지기 때문이다.
반대로 화면 구조가 안정적이고 서버 논리가 자주 바뀌는 프로젝트에서는
갱신 결정을 서버에 모으는 쪽이 싸다.
한 번의 배포로 여러 컴포넌트의 동작을 함께 바꿀 수 있기 때문이다.

이 기준은 조직 구조와도 맞물린다.
디자이너나 퍼블리셔가 마크업을 직접 만지는 팀에서는
서버가 id 구조에 의존하는 설계가 사고를 부른다.
반대로 백엔드 개발자가 화면까지 함께 만드는 팀에서는
그 의존이 오히려 한 사람의 머릿속에서 관리되므로 비용이 낮다.
어느 도구가 나은가라는 질문보다
우리 팀에서 마크업과 서버 코드 중 어느 쪽이 더 자주, 누구 손에 의해 바뀌는가라는
질문이 결정에 더 가깝다.

### 하이퍼미디어 도구 선택은 이제 성능이 아니라 거버넌스 비교가 되었다

이 글과 그 반응 전체를 놓고 보면 기술적 비교는 놀랍도록 빨리 수렴한다.
OOB 갱신으로 htmx도 서버 주도를 할 수 있고,
htmx 4.0이 SSE와 스트리밍과 모핑을 코어에 넣으면 기능 격차의 상당 부분이
사라진다.
남는 차이는 클라이언트 상태 시그널을 코어에 두느냐 정도다.

그래서 논의의 무게 중심이 다른 곳으로 옮겨 갔다.
라이선스가 어떻게 바뀌었는지, 유지 주체가 사용자를 어떻게 대하는지,
커뮤니티에서 질문했을 때 어떤 대접을 받는지가 실제 선택 기준이 되고 있다.
HN에서 wolfgangbabad가 저자와의 불쾌한 교류를 이유로 이 제품을 쓰지 않겠다고
적은
것[^wolfgangbabad]은 개인적 증언이고 반대편 이야기는 확인되지 않았지만,
그런 증언이 기능 논쟁 한가운데에서 상당한 주목을 받는다는 사실 자체가
이 전환을 보여 준다.

기술이 수렴하면 신뢰가 차별점이 된다는 것은 새로운 관찰이 아니다.
데이터베이스, 언어 런타임, 클라우드 서비스가 모두 같은 경로를 밟았다.
성능 벤치마크가 의미를 잃는 지점에서 사람들은 지원 정책, 후방 호환 이력,
메인테이너의 응답 태도를 비교하기 시작한다.
하이퍼미디어 라이브러리가 그 단계에 들어섰다는 것은 이 범주가 성숙했다는
신호이며,
동시에 지금 도구를 고르는 팀이 무엇을 조사해야 하는지 알려 준다.
벤치마크와 기능표를 비교하는 데 쓰는 시간보다,
지난 2년간 그 프로젝트가 사용자에게 무엇을 요구했는지 읽는 데 쓰는 시간이
더 값지다.
