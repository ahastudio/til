# Sätteri - 고성능 Markdown 및 MDX 처리기

<https://satteri.bruits.org/>

<https://github.com/bruits/satteri>

GN 토론: <https://news.hada.io/topic?id=31967>

## 소개

Sätteri는 "Rust로 파싱·컴파일하고 JavaScript로 플러그인을 실행하는" 고성능
Markdown/MDX 처리기다. JavaScript의 풍부한 플러그인 생태계와 Rust의 빠른
파싱 성능 사이의 간극을 메우는 것을 목표로 한다.

## 아키텍처

파서와 AST는 Rust로 구현되어 있고, 플러그인은 JavaScript/TypeScript로 남겨
언어 경계를 넘나드는 비용을 최소화하는 하이브리드 구조를 취한다. CommonMark와
GFM, frontmatter, 수식 표기 등을 지원하는 MDX 확장까지 처리한다.

## 패키지 구성

`satteri`, `satteri-arena`, `satteri-ast`, `satteri-plugin-api` 등 여러 Rust
크레이트와, `pulldown-cmark`·`mdxjs-rs`를 포크한 전용 버전, 그리고 TypeScript
연동·Vite 플러그인·Expressive Code 렌더링을 위한 npm 패키지들로 구성된다.
macOS/Linux/Windows용 네이티브 바이너리를 제공하며, 브라우저·엣지 환경을 위한
WASI 폴백도 지원한다.

## 사용법

공식 문서 사이트(satteri.bruits.org)에서 설치 방법, API 레퍼런스, 퀵스타트
예제, 온라인 플레이그라운드를 제공한다. Discord 커뮤니티를 통해서도 지원을
받을 수 있다.

## 라이선스 및 상태

MIT 라이선스로 배포되며, unified.js, pulldown-cmark, mdxjs-rs, OXC, Lightning
CSS 등으로부터 영향을 받았다고 밝히고 있다.

## 분석

### 성능 병목만 Rust로 떼어내는 절개 방식

MDX 생태계는 그동안 순수 JavaScript(remark/rehype 기반 unified.js)로 구축돼
왔고, 이는 유연성은 뛰어나지만 대규모 콘텐츠를 파싱할 때 성능 병목이 되기
쉬웠다. Sätteri는 파싱이라는 계산 집약적 작업만 Rust로 옮기고 플러그인
인터페이스는 JavaScript로 유지함으로써, 기존 unified.js 플러그인 생태계와의
호환성을 크게 해치지 않으면서 성능을 끌어올리려는 시도로 보인다. 전체를
Rust로 새로 짜는 대신 "가장 비용이 큰 부분만" 도려내 대체하는 이 접근은,
언어 전환의 위험을 국소화하면서도 체감 성능 개선은 크게 가져가는 실용적
절충안이다.

### 최근 프론트엔드 툴체인의 공통 궤도 위에 있다

OXC(Rust 기반 JS 툴체인)나 Lightning CSS 같은 최근 프론트엔드 툴체인의
"코어는 Rust, 확장점은 JS"라는 흐름과 Sätteri는 같은 궤도에 있다. 이 패턴이
반복적으로 나타나는 이유는, 프런트엔드 생태계의 진짜 자산이 코드가 아니라
플러그인·설정·관례로 이뤄진 생태계 그 자체이기 때문이다. 파서나 컴파일러
같은 핵심 엔진을 Rust로 바꿔도 플러그인 API의 JS 표면을 유지하면 기존
생태계를 그대로 흡수할 수 있지만, 반대로 API 자체를 Rust 전용으로 바꾸면
그 생태계와 단절된다. Sätteri가 pulldown-cmark와 mdxjs-rs를 포크해서까지
JS와의 상호운용 계층을 정교하게 다듬은 이유도 여기에 있을 가능성이 크다.

## 비평

### 포크 유지보수 비용이 장기적으로 누적된다

pulldown-cmark와 mdxjs-rs를 그대로 쓰지 않고 포크했다는 사실은 성능이나
상호운용성 면에서 필요한 선택이었을 수 있지만, 동시에 상류(upstream)
프로젝트의 개선 사항을 자동으로 받지 못하고 직접 병합해야 하는 부담을
의미한다. CommonMark 스펙이나 MDX 문법이 바뀔 때마다 포크된 두 크레이트를
독립적으로 추적하고 반영해야 하며, 이 비용은 프로젝트가 커질수록 선형이
아니라 누적적으로 증가한다. 소규모 팀이 유지하는 오픈소스 프로젝트에서
포크 두 개를 동시에 감당하는 것은 결코 가벼운 약속이 아니다.

### 벤치마크 없이 "고성능"을 주장한다

README와 공식 문서는 "고성능"을 핵심 가치로 내세우지만, 정작 unified.js
대비 몇 배 빠른지, 어떤 크기의 문서에서 이점이 두드러지는지에 대한
구체적인 벤치마크 수치는 제시되지 않는다. Rust 코어를 쓴다는 사실만으로
성능 우위를 주장하는 것은 설계 의도로는 타당하지만, 실제 채택을 고민하는
개발자에게는 "얼마나" 빠른지가 훨씬 중요한 정보다. 특히 JS-Rust 경계를
넘는 데이터 직렬화 비용이 오히려 병목이 될 수 있는 상황(작은 문서를 대량으로
처리하는 경우 등)에서는 Rust 코어의 이점이 상쇄될 수도 있는데, 이런 경계
사례에 대한 논의가 없다.

## 인사이트

### 포크는 대개 인터페이스 경계를 다시 설계해야 했다는 신호다

pulldown-cmark와 mdxjs-rs를 그대로 쓰지 않고 포크한 이유는 아마도 언어
경계를 넘는 AST 표현이나 arena 할당 방식(satteri-arena)처럼, JS 플러그인과의
상호운용을 위해 원본 크레이트의 내부 구조에 손을 대야 했기 때문일 가능성이
크다. 오픈소스 생태계에서 잘 관리되는 라이브러리를 굳이 포크하는 경우는
대개 기능 부족보다 "이 라이브러리가 애초에 상정하지 않은 사용 맥락"에
맞춰 내부 구조 자체를 바꿔야 할 때 발생한다. 이는 라이브러리를 평가할 때
"이 라이브러리가 얼마나 잘 만들어졌는가"뿐 아니라 "내가 필요로 하는
확장 지점이 이 라이브러리의 설계 경계 안에 있는가"를 먼저 물어야 한다는
교훈으로 일반화할 수 있다.

### Rust 코어 + JS 확장점 패턴은 재사용 가능한 설계 템플릿이다

Rust 코어 + JS 플러그인 조합은 최근 프론트엔드 툴체인(OXC, Lightning CSS,
SWC 등)에서 반복되는 패턴이므로, 유사한 트레이드오프를 가진 도구를 설계할
때 참고 사례로 삼을 만하다. 이 템플릿이 성립하려면 세 가지 조건이 맞아야
한다. 첫째, 핵심 연산이 명확히 계산 집약적이어야 언어 전환의 이득이 크고,
둘째, 확장 지점의 API가 안정적으로 설계될 수 있어야 언어 경계를 넘는
직렬화 비용이 감당할 만한 수준으로 유지되며, 셋째, 기존 생태계가 이미
그 언어(JS)로 두텁게 쌓여 있어야 API 표면을 유지할 유인이 생긴다. 이
세 조건이 모두 맞는 문제 영역—파서, 컴파일러, 린터—에서 이 패턴이
반복적으로 재발명되고 있다는 점은 우연이 아니라 하나의 검증된 설계
해법으로 굳어지고 있다는 신호다.

### 실사용 채택이 벤치마크 부재의 공백을 메운다

GeekNews에서 click은 "Astro가 이 라이브러리 기반으로 파싱하는데 플러그인
확장할 때 꽤 편리했다"고 실사용 경험을 남겼는데,[^click] 이는 Sätteri가
단순 실험 프로젝트가 아니라 이미 실제 프레임워크의 파싱 계층에 채택되어
검증되고 있음을 보여준다. 벤치마크 수치가 없다는 비평은 여전히 유효하지만,
Astro처럼 대규모 사용자를 가진 정적 사이트 생성기가 파싱 계층으로 채택했다는
사실 자체가 일종의 간접 검증 신호로 기능한다. 실제 프로덕션 환경에서
플러그인 확장이 편리했다는 경험담은, 이 프로젝트가 적어도 "코어는 Rust,
확장점은 JS"라는 설계 목표를 실제로 달성했다는 근거가 된다.
