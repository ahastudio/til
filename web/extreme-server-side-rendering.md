# JavaScript 없이 서버가 HTML을 끝없이 흘려보내는 렌더링

원문: [EXTREME SERVER SIDE RENDERING | The Cat House](https://www.scd31.com/posts/extreme-server-side-rendering)

HN 토론: <https://news.ycombinator.com/item?id=43100870> (28점, 5개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/tprfej/extreme_server_side_rendering> (40점, 21개 댓글)

GN 토론: <https://news.hada.io/topic?id=33384>

## 요약

2025년 2월 16일 The Cat House에 올라온 글이다.
저자는 자신이 XSSR(extreme server side rendering)이라 부르는 방식을 소개하기에 앞서
통상적인 서버 사이드 렌더링을 두 갈래로 나눈다.

구식 SSR은 서버가 로직으로 HTML을 즉석에서 만드는 것이다.
`/users/39`에 접속하면 39번 사용자의 정보를 받는데,
디스크에 `39.html`이 있는 것이 아니라 백엔드가 동적으로 만든다.
프런트엔드에는 렌더링에 필요한 JavaScript나 로직이 없고,
그 결과 페이지가 로드된 뒤에는 동적으로 움직일 수 없다.

신식 SSR은 여기에 약간의 프런트엔드 JavaScript가 붙는다.
사용자가 상호작용하면 JS가 백엔드에 요청을 보내고,
백엔드가 HTML을 돌려주면 JS가 그것을 페이지 어딘가에 끼워 넣는다.
동적인 페이지를 얻는 대신 프런트엔드 로직을 유지보수해야 한다는 대가가 붙는다.

여기서 저자는 HTTP 서버 자체로 화제를 돌린다.
HTTP 요청을 하면 서버는 헤더와 실제 HTML 콘텐츠에 해당하는
ASCII 텍스트 뭉치를 돌려주고, 그것은 한 글자씩 전송된다 —
버퍼링이 있지만 목적상 무시할 수 있다는 단서를 단다.
그렇다면 HTML을 사람의 속도로 천천히 보내면 어떻게 되는가.
저자는 netcat으로 직접 사람 HTTP 서버가 되어 브라우저를 붙이는 영상을 보여준다.
netcat은 줄 단위 버퍼링이므로 엔터를 칠 때마다 한 줄씩 브라우저로 간다.

결과는 새 HTML이 들어오는 대로 페이지가 즉석에서 렌더링된다는 것이다.
Firefox와 Chromium 양쪽에서 작동했고,
CSS까지 작동하므로 요소를 계속 움직이거나
기존 요소를 숨기고 새 것을 추가하는 일도 가능하다.
즉 HTTP 연결을 무기한 열어두면
JavaScript 없이 서버에서 페이지를 동적으로 갱신할 수 있다.

남은 문제는 사용자 입력이다.
JS 없이 입력을 받는 통상적인 방법은 `<form>`인데
페이지 로드를 요구하므로 XSSR의 취지를 무너뜨린다.
저자는 친구 DJ Chase가 알려준 요령을 소개한다 —
숨긴 `<iframe>`을 만들고 폼의 `target`을 그 iframe으로 지정하면,
폼을 제출해도 메인 페이지 대신 iframe만 다시 로드된다.
iframe을 숨겨두면 사용자 입력이 완전히 매끄러워진다.
폼에는 서버가 최초 페이지 로드 때 생성한 `uuid` 값을 숨은 필드로 넣는데,
이벤트를 원래 페이지에 묶어 사용자를 섞이지 않게 하기 위한 것이다.

이 재료로 저자가 만든 것은 Flappy Bird 클론이다.
점수를 위한 동적 텍스트가 있고, 파이프가 예상대로 움직이고,
클릭하면 새가 점프한다 —
마지막 것은 앞의 iframe 요령에 화면 전체를 덮는 숨은 버튼을 결합해 구현했다.
그래서 아무 데나 클릭할 수 있고,
한 번 클릭해 보이지 않는 버튼을 선택하고 나면
스페이스바와 엔터로도 계속 클릭할 수 있다.
페이지는 결코 로딩을 멈추지 않는다 — 물리 엔진이 전적으로 백엔드에서 돌고,
파이프와 새의 위치, 점수 텍스트의 내용을 갱신하는 새 CSS가
초당 60프레임으로 계속 전송되기 때문이다.
프런트엔드 JS는 전혀 필요 없어서 꺼도 똑같이 작동하며,
`curl`로 페이지를 받아 무한히 이어지는 CSS를 직접 볼 수도 있다.

성능은 생각만큼 나쁘지 않다고 밝힌다.
클라이언트 쪽은 Firefox와 Chromium 모두에서 몇 분 지나면 느려지는 것을 인정하지만,
초당 60프레임으로 스트리밍하고 있다는 점과
사용자 상호작용이 있을 때만 갱신되는 페이지라면
실질적 문제가 아닐 수 있다는 점을 든다.
서버 쪽은 더 낫다 — 간단한 Rust 서버 구현으로,
홈랩의 비교적 오래된 서버에서 코어당 약 500개의 게임을
동시에 돌릴 수 있다는 것이다.
이것이 어지간히 복잡한 Ruby on Rails 앱보다 상당히 낫다고 적으면서,
애정을 담아 하는 말이라고 덧붙인다.

대역폭은 “전적으로 합리적”이라고 표현한다.
게임 하나가 초당 약 20KiB를 쓰는데,
이는 1MB짜리 JavaScript 애플리케이션을 내려받는 것과 같은 양을 쓰는 데
약 49초의 게임 시간이 걸린다는 뜻이다.
그리고 1MB는 요즘 기준으로 작은 축이라는 말을 괄호로 붙인다.

지연 시간에 대해서는 “oh no.”라는 한 줄로 절을 연다.
클릭할 때마다 서버 왕복이 필요하기 때문인데,
서버의 물리 엔진에 동작을 반영하고
새의 새 위치를 브라우저로 돌려보내야 하기 때문이다.
이것은 거의 전적으로 전송 시간에 지배된다.
그래서 서버가 있는 캐나다 대서양 연안 근처에서는 대단히 잘 플레이되고,
동부 해안 아래쪽에서는 지연이 느껴지지만
사람이 조금 일찍 클릭해 보정할 수 있으며,
서부 해안에서는 거슬리고, 지구 반대편에서는 플레이가 불가능하다.
멀리 사는 사람이라면 소스를 받아 로컬에서 돌려보라고 권한다.
그리고 요즘은 다들 엣지에 올리는 것을 좋아하니
그렇게 하면 문제없을 것이라고 농담을 덧붙인다.

마지막에서 두 번째 절은 사고 보고다.
데모가 자랑스러워서 자신의 Pleroma 페디버스 서버에 올렸더니
얼마 뒤 서버가 내려가 글이 로드되지 않았다.
20분쯤 뒤 돌아왔고, 사람들이 자기 글을 재게시했다는 알림이 몰려왔으며,
그러자 다시 내려갔다.
이 주기가 서너 번 반복된 뒤에야 안정되었고,
그 글을 본 다른 Pleroma 서버들도
비슷한 순환적 정전을 겪었을 것으로 짐작한다.
연결을 무기한 열어둔 채 데이터를 천천히 흘려보내는 사이트를
어떤 애플리케이션들은 정말 싫어한다는 것이다.
친구 Olivia가 Pleroma 소스를 뒤져
서버 사이드에서 링크 미리보기를 생성할 때 문제가 생긴다는 것을 찾아냈고,
저자는 이것이 DoS 공격 벡터이므로 보안 버그로 신고했으며 곧 패치되었다.

향후 작업으로 두 가지를 든다.
하나는 전적으로 서버에서 돌아가는 React 포크를 만드는 것이다 —
가상 DOM을 diff하고 그 차이를 XSSR로 프런트엔드에 전송하며,
여전히 프런트엔드 JS는 필요 없다.
실용적이지는 않겠지만 멋질 것이라고 적는다.
다른 하나는 조금 더 쓸모 있는 아이디어로,
XSSR이 구형 기기에서 어떻게 작동할지 궁금하다는 것이다.
느린 인터넷은 즉석 동적 렌더링이 의도된 기능이었다는 뜻일 수 있으므로
꽤 잘 작동하리라 짐작하면서,
헤드리스 브라우저 인스턴스로 웹 페이지를 DOM으로 렌더링하고
그 DOM을 XSSR로 전송하는 프록시 서비스를 생각해본다.
JavaScript를 전혀 지원하지 않는 구형 기기에서
현대적 웹 페이지를 쓸 수 있게 될 것이라는 구상이다.

## 분석

### 이 글의 발견은 새 기술이 아니라 오래된 동작의 재발견이다

XSSR을 가능하게 하는 성질은 전부 원래부터 있던 것이다.
HTTP 응답이 스트림이라는 것,
브라우저가 도착하는 대로 점진적으로 파싱하고 렌더링한다는 것,
나중에 도착한 CSS가 이미 그려진 요소에 적용된다는 것.

이 성질들은 1990년대 저속 회선을 위한 것이었다.
페이지 전체를 받을 때까지 흰 화면을 보여주는 대신 위에서부터 그려나가는 것이
당시에는 필수적인 최적화였고, 그 동작이 표준의 일부로 굳었다.

저자가 한 일은 그 동작을 끝까지 밀어붙인 것이다.
점진적 렌더링이 “느린 회선에 대한 대응”이 아니라
“서버가 화면을 계속 조종하는 채널”로 쓰일 수 있다는 것을 보인 것이고,
그 전환에는 새 기술이 하나도 필요하지 않았다.

netcat으로 사람이 직접 HTTP 서버가 되는 영상이 논증의 전부라는 점이
이 글의 설득력이다.
어떤 라이브러리도, 어떤 확장도, 어떤 브라우저 플래그도 없다.
프로토콜이 원래 그렇게 되어 있었다는 사실만 남는다.

### iframe 요령이 없었다면 이 글은 성립하지 않는다

스트리밍만으로는 출력 채널이 생길 뿐이다.
서버가 화면을 계속 갱신할 수 있지만 사용자는 아무것도 할 수 없고,
그러면 XSSR은 애니메이션 재생기에 머문다.

DJ Chase가 알려준 요령 — 폼의 `target`을 숨긴 iframe으로 돌리는 것 — 이
입력 채널을 만든다.
그리고 이 요령 역시 새 기술이 아니다.
`target` 속성으로 폼 제출 결과를 다른 프레임에 보내는 것은
프레임셋 시대의 기본 동작이고,
AJAX 이전에 부분 갱신을 흉내 내던 표준 기법이었다.

그러니 XSSR의 실체는 이렇게 정리된다.
출력은 무한 스트리밍 응답, 입력은 숨은 iframe 폼,
상태 연결은 서버가 발급한 UUID.
세 조각 모두 2000년대 초반에 존재했고, 조합된 적이 없었을 뿐이다.

정확히 말하면 조합된 적이 있었다.
Lobste.rs에서 DustyFuzzy는 이것이 새로운 기법이 아니며
초기 IE 시절까지 거슬러 올라가 실시간 갱신에 쓰였던 것으로
기억한다고 적는다.[^DustyFuzzy]
viraptor는 그 기억에 이름을 붙인다 —
처음에는 `document.write()`를 잘못 기억한 것이라고 생각했는데,
“포에버 프레임(forever frame)”을 잊고 있었다는 것이다.[^viraptor]
그 기법에는 전용 nginx 모듈까지 있었다고 덧붙인다.

포에버 프레임은 Comet 시대의 표준 기법 중 하나였다.
숨긴 iframe으로 끝나지 않는 응답을 받고,
서버가 그 스트림에 스크립트 조각을 계속 흘려보내 부모 페이지를 갱신하는 방식이다.
XSSR과의 차이는 갱신 수단이 스크립트냐 HTML과 CSS냐이고, 구조는 같다.

그러니 이 글의 기여를 다시 규정해야 한다.
발명이 아니라, 사라진 기법을 JavaScript 없이 재구성한 것이다.
포에버 프레임은 WebSocket이 표준화되면서 쓸모를 잃었는데,
WebSocket이 해결하지 못한 조건 하나 —
클라이언트 코드를 전혀 두지 않는 것 — 아래에서는
여전히 유일한 선택지로 남아 있었다는 이야기다.

여기서 흥미로운 질문이 나온다.
왜 그때는 조합되지 않았는가.
답은 아마 그 시절 서버가 연결당 하나의 프로세스나 스레드를 쓰는
모델이었기 때문일 것이다.
수천 개의 연결을 무기한 열어두는 것은 당시에는 상상하기 어려운 비용이었고,
저자의 Rust 서버가 코어당 500개를 돌릴 수 있는 것은
비동기 런타임 이후의 이야기다.

### 성능 수치의 배치가 논증의 방향을 정한다

성능 절의 구성이 세심하다.
클라이언트 쪽은 문제를 먼저 인정하고, 서버 쪽은 유리한 비교를 내놓고,
대역폭은 익숙한 기준으로 환산하고, 지연 시간은 항복한다.

특히 대역폭 환산이 논쟁적으로 설계되어 있다.
초당 20KiB를 1MB짜리 JavaScript 번들과 비교해 49초라는 숫자를 뽑고,
1MB가 요즘 기준으로 작은 편이라는 말을 붙인다.
비교 대상을 무엇으로 잡느냐에 따라 이 숫자의 인상이 완전히 달라지는데,
저자는 현대 프런트엔드가 가장 비판받는 지점을 골랐다.

Rails와의 비교도 같은 성격이다.
코어당 500개 동시 게임이 “어지간히 복잡한 Rails 앱보다 상당히 낫다”는 것인데,
게임 세션과 웹 요청은 같은 단위가 아니다.
Rails 앱의 동시 처리 수는 요청 처리량이고, XSSR의 500개는 유지되는 연결 수다.
비교가 성립하지 않는 것은 아니지만 성립하는 축이 무엇인지가 명시되지 않는다.

이 배치들이 글을 농담에서 주장으로 옮긴다.
“재미있는 해킹이지만 실용성은 없다”로 끝났다면 아무 반론도 부르지 않았을 텐데,
저자는 “생각만큼 나쁘지 않다”는 절 제목으로
실용성을 주장하는 쪽에 발을 걸친다.

### Pleroma 사고가 이 글에서 가장 실질적인 부분이다

데모를 페디버스에 올렸더니 서버가 반복해서 내려갔다는 서술은 일화처럼 읽히지만,
실제로는 XSSR이 웹 생태계와 어떻게 충돌하는지에 대한 유일한 실증이다.

문제의 지점이 링크 미리보기라는 것이 중요하다.
링크를 게시하면 서버가 그 URL을 가져와 제목과 이미지를 뽑는데,
그 가져오기가 응답의 끝을 기다린다.
끝나지 않는 응답을 만나면 그 작업이 영원히 붙들리고,
여러 인스턴스가 같은 링크를 미리보기하면 자원이 고갈된다.

이것이 시사하는 바는 XSSR의 진짜 제약이 브라우저가 아니라 중간자들이라는 점이다.
브라우저는 잘 처리했다 — Firefox도 Chromium도 문제없이 렌더링했다.
문제를 일으킨 것은 응답이 유한하다고 가정한 모든 소프트웨어다.

저자가 이것을 보안 버그로 신고하고 패치되었다고 적은 것은 성실한 처리다.
동시에 이 사건은 XSSR이 실용 기술이 되려면 무엇이 필요한지도 알려준다 —
프로토콜은 이미 지원하지만 생태계는 지원하지 않으며,
생태계를 고치는 일은 명세를 읽는 것보다 훨씬 오래 걸린다.

## 비평

### 지연 시간 문제를 엣지 배포로 넘기는 것은 이 접근의 핵심을 포기하는 것이다

지연 시간 절은 솔직하다.
서부 해안에서 거슬리고 지구 반대편에서는 플레이 불가능하다고 적는다.
그리고 “다들 엣지에 올리는 걸 좋아하니 그렇게 하면 된다”는 농담으로 넘어간다.

농담이지만 이 문장이 논증의 가장 약한 고리다.
XSSR의 매력은 상태와 로직이 전부 서버 한 곳에 있다는 단순함이다 —
프런트엔드가 없으니 동기화할 것도 없고,
클라이언트 상태와 서버 상태가 어긋날 일도 없다.

엣지에 올리는 순간 그 단순함이 사라진다.
게임 상태를 여러 엣지 노드가 가지려면 노드 간 일관성 문제가 생기고,
사용자를 특정 노드에 고정해야 하고,
노드가 죽으면 진행 중인 연결이 전부 끊긴다.
JavaScript를 없애서 얻은 단순함이 분산 상태 관리로 옮겨간 셈이고,
후자가 대체로 더 어렵다.

더 근본적으로, 엣지가 해결할 수 없는 경우가 있다.
게임처럼 세션이 독립적이라면 엣지에 흩어놓을 수 있지만,
여러 사용자가 같은 상태를 보는 협업 화면이라면 상태가 한 곳에 있어야 하고
그러면 왕복 지연이 그대로 남는다.
그리고 실시간 협업 화면이야말로 XSSR이 가장 그럴듯해 보이는 용도다.

### 접근성을 다루지 않은 것이 이 접근의 가장 큰 공백이다

글은 JavaScript 없이 작동한다는 점을 반복해 강조하고,
JS를 꺼도 똑같이 동작한다는 것을 자랑한다.
JS 없이 작동한다는 성질은 통상 접근성과 함께 이야기되는데,
이 글에는 접근성이라는 단어가 없다.

그리고 XSSR은 접근성 관점에서 상당히 나쁠 가능성이 높다.
스크린 리더는 DOM이 안정된 상태를 전제로 읽어나가는데,
초당 60번 DOM이 갱신되는 페이지에서 무엇을 읽어야 할지는 정의되지 않는다.
결코 완료되지 않는 로드 상태 자체도 보조 기술에 신호를 주는 요소다.

입력 쪽은 더 나쁘다.
화면 전체를 덮은 보이지 않는 제출 버튼은 시각적 사용자에게는 영리한 요령이지만,
키보드와 스크린 리더 사용자에게는 이름도 역할도 없는 컨트롤이다.
저자가 “한 번 클릭해 선택하고 나면 스페이스바와 엔터로도 된다”고 적은 것은
우연히 키보드 접근을 얻은 것이지 설계한 것이 아니다.

이 공백이 문제인 이유는 저자가 향후 작업으로 제안한 것 때문이다.
구형 기기를 위한 프록시 — 헤드리스 브라우저로 렌더링해 XSSR로 전송하는 것 — 는
명백히 접근성 도구의 성격을 갖는다.
그 방향을 진지하게 생각한다면
무한히 갱신되는 DOM이 보조 기술에 무엇을 하는지가 첫 번째 질문이어야 한다.

### 신식 SSR에 대한 서술이 실제 대안들을 빠뜨린다

글은 SSR을 구식과 신식 둘로 나누고,
신식을 “JS가 요청을 보내고 받은 HTML을 끼워 넣는 것”으로 정의한다.
그리고 “더 나은 방법이 있으면 좋지 않겠느냐”며 XSSR로 넘어간다.

이 이분법이 비교 대상을 유리하게 좁힌다.
서버가 주도해 화면을 갱신하되 클라이언트 상태를 유지하는 방식은 이미 여럿 있다 —
서버 전송 이벤트(SSE), WebSocket,
그리고 그 위에 지어진 서버 주도 UI 프레임워크들이다.
그중 일부는 XSSR과 목표가 거의 같다 —
로직을 서버에 두고 클라이언트를 얇게 유지하는 것이다.

차이는 클라이언트에 작은 런타임이 있느냐다.
XSSR은 그것을 0으로 만들고,
대신 브라우저가 무한한 응답을 파싱하며 DOM을 계속 키우게 한다.
저자가 인정한 “몇 분 뒤 느려짐”이 정확히 그 대가다 —
갱신이 기존 노드를 교체하는 것이 아니라 스트림에 계속 덧붙는 방식이기 때문이다.

이 비교를 하지 않으면 XSSR이 “JS 있는 방식 대 JS 없는 방식”의 선택처럼 보인다.
실제 선택은 “몇 킬로바이트의 클라이언트 런타임 대 무한히 자라는 문서”이고,
그렇게 놓으면 결론이 달라질 수 있다.

두 커뮤니티 모두 같은 지적을 했다.
HN에서 AdieuToLogic은 저자가 “더 나은 방법이 있으면 좋지 않겠느냐”고 물은 데 대해
한 단어로 답한다 — htmx라는 것이다.[^AdieuToLogic]
저자가 신식 SSR로 묘사한 것 — JS가 요청을 보내고 받은 HTML을 끼워 넣는 것 — 을
프레임워크로 정리한 것이 정확히 htmx이고,
저자는 그것을 개선 대상으로만 언급하고 이름은 대지 않는다.

향후 작업으로 제안한 서버 사이드 React에 대해서도 smw가 답한다.
그것은 기본적으로 Elixir의 LiveView이며 훌륭하다는 것이다.[^smw]

이 두 댓글이 함께 보여주는 것은 이 글의 서지가 얇다는 점이다.
서버가 UI를 주도하고 클라이언트를 얇게 유지한다는 목표를 향해
이미 여러 성숙한 구현이 있고,
그중 LiveView는 저자가 “실용적이지 않겠지만 멋질 것”이라 상상한 바로 그 설계를
수년째 프로덕션에서 돌리고 있다.
비교하지 않은 것이 논증을 유리하게 만든 대신,
이 기법이 스펙트럼 어디에 놓이는지를 독자가 판단할 수 없게 만들었다.

### 전제가 되는 정의가 결론을 미리 담고 있다

글의 출발점은 구식 SSR에 대한 서술이다.
프런트엔드에 렌더링에 필요한 로직이 없으므로
페이지가 로드된 뒤에는 동적일 수 없다는 것이다.

Lobste.rs의 colonelpanic이 이 문장을 문제 삼는다.
프런트엔드 개발자들이 15년쯤 전의 과거에 대해
집단적 기억상실을 겪고 있는 것 아니냐고 묻는다.[^colonelpanic]
그리고 그런 명백히 틀린 전제에서 출발하는 글은
진지하게 받아들이기 어렵다고 덧붙인다.

정확히 말하면 저자의 문장은 자기 정의 안에서는 참이다 —
구식 SSR을 “프런트엔드 로직이 없는 것”으로 정의했으니
동적일 수 없는 것은 동어반복이다.
문제는 그 정의가 실제 역사를 대표하지 않는다는 데 있다.
서버가 HTML을 만들고 그 위에 약간의 스크립트로 화면을 조작하는 구성은
15년 전에도 흔했고, 그것을 부르는 이름이 없었을 뿐이다.

이 정의가 결론에 미치는 영향이 크다.
“서버 렌더링은 정적, 동적이려면 프런트엔드 프레임워크”라는 이분법을 세워두면
그 사이의 넓은 영역이 사라지고, XSSR이 그 빈자리를 채우는 것처럼 보인다.
실제로 그 영역은 비어 있지 않고, 앞의 htmx와 LiveView가 그 안에 있다.

### DoS 취약점을 남의 버그로만 다룬다

Pleroma 사고에 대한 저자의 처리는 이렇다.
어떤 애플리케이션은 연결을 오래 여는 사이트를 싫어하고, 친구가 원인을 찾았고,
DoS 벡터이므로 보안 버그로 신고했고, 패치되었다.

이 서술에서 문제는 전적으로 Pleroma 쪽에 있다.
그리고 그것이 틀린 것은 아니다 —
외부 URL을 가져오는 코드에 타임아웃과 크기 제한이 없는 것은 실제로 결함이다.

그러나 뒤집어 보면 XSSR로 만든 사이트는
URL 하나로 여러 서버를 무너뜨릴 수 있는 물건이다.
저자가 의도 없이 올린 링크 하나가 페디버스 인스턴스 여러 개를 반복해서 내렸다.
같은 성질을 의도적으로 쓰면 손쉬운 공격 도구가 된다.

그렇다면 이 기술을 소개하는 글은
“이것을 배포하면 무엇을 깨뜨릴 수 있는가”를 함께 다뤄야 한다.
링크 미리보기뿐 아니라 크롤러, 아카이버, 리더 모드, 기업 프록시,
그리고 지금은 웹을 가장 많이 읽는 주체인 AI 크롤러가 전부 같은 가정 위에 있다.
저자가 신고와 패치로 자기 몫을 다한 것과 별개로,
이 기법을 따라 하려는 독자에게 필요한 경고는 글에 없다.

## 인사이트

### 완료되지 않는 응답은 웹의 암묵적 계약을 깨뜨린다

Pleroma 사고에서 드러난 것은
특정 소프트웨어의 버그가 아니라 웹 전반에 깔린 가정이다.
HTTP 응답은 언젠가 끝난다는 가정이고, 거의 모든 클라이언트 코드가 그 위에 서 있다.

이 가정이 명시된 곳은 없다.
명세는 응답이 끝나야 한다고 말하지 않고,
청크 전송 인코딩은 오히려 끝을 모른 채 시작하는 것을 허용한다.
그럼에도 구현들은 끝을 기다린다 —
응답 본문을 문자열로 만들고, 파싱하고,
그다음에 처리하는 형태로 코드가 쓰이기 때문이다.

이런 종류의 가정은 위반이 드물기 때문에 발견되지 않는다.
그리고 발견될 때는 대개 사고의 형태로 발견된다 —
저자의 게시물 하나가 여러 인스턴스를 내린 것처럼.

같은 구조의 취약점이 웹에 얼마나 더 있을지는 알 수 없다.
슬로로리스 공격이 20년 전에 같은 성질을 서버 쪽에서 보여줬고,
그때 웹 서버들은 타임아웃을 배웠다.
클라이언트 쪽 — 크롤러, 프리뷰 생성기, 스크래퍼 — 은 같은 교훈을 아직 배우지 못했고,
지금 그 쪽 코드를 가장 많이 새로 쓰고 있는 것은 AI 회사들이다.

### 서버가 화면을 직접 조종하는 구조는 주기적으로 돌아온다

XSSR은 새로워 보이지만 계보가 있다.
메인프레임 시대의 3270 단말은 화면 전체를 서버가 그렸고, 단말에는 로직이 없었다.
X11은 애플리케이션이 원격에서 창을 그리게 했다.
씬 클라이언트, 시트릭스, 그리고 지금의 클라우드 게이밍과 원격 개발 환경이
같은 축 위에 있다.

이 축은 진자처럼 움직여왔다.
클라이언트가 강해지면 로직이 클라이언트로 가고,
배포와 일관성 문제가 쌓이면 다시 서버로 간다.
프런트엔드 프레임워크의 무게에 대한 지금의 피로가 진자를 서버 쪽으로 미는 힘이고,
XSSR은 그 극단에 있는 표본이다.

돌아올 때마다 같은 문제를 다시 만난다는 것이 이 계보의 교훈이다.
지연 시간, 연결 상태, 그리고 서버 자원.
저자가 정직하게 항복한 지연 시간 문제는
씬 클라이언트가 30년간 풀지 못한 것과 같은 문제이고,
물리 법칙이 바뀌지 않는 한 앞으로도 그렇다.

다른 점이 하나 있다면 이번에는 클라이언트가 브라우저라는 것이다.
브라우저는 이미 강력한 실행 환경이므로,
서버로 로직을 옮기는 것은 있는 능력을 쓰지 않기로 하는 선택이다.
그 선택의 근거가 “프런트엔드 유지보수가 싫다”라면,
그것은 기술적 판단이 아니라 조직적 판단이다.

### JavaScript를 없앤 자리에 남는 것은 무상태가 아니라 연결 상태다

이 글의 매력은 “프런트엔드 없음”이라는 단순함이지만,
그 단순함은 다른 곳으로 옮겨간 복잡성을 감춘다.

JavaScript 기반 앱에서 사용자의 상태는 브라우저 메모리에 있다.
서버가 재시작되어도, 네트워크가 잠깐 끊겨도,
사용자가 탭을 백그라운드에 두어도 그 상태는 유지된다.
XSSR에서는 상태가 서버에 있고 연결이 그것을 붙들고 있다.

그러면 연결이 끊기는 모든 순간이 상태 손실의 순간이 된다.
지하철에 들어가거나, 와이파이가 셀룰러로 바뀌거나, 노트북이 잠들거나,
서버가 배포로 재시작되면 진행 중이던 것이 사라진다.
저자의 Flappy Bird에서는 게임 한 판이지만,
긴 폼이나 편집 중인 문서라면 이야기가 다르다.

이 문제를 풀려면 재연결과 상태 복구가 필요하고,
그것은 클라이언트에 로직을 요구한다.
즉 XSSR을 실제 애플리케이션에 쓰려는 순간 JavaScript가 돌아온다 —
없앴던 그 자리에 다시 필요해지는 것이다.

역사적 유비는 초기 웹의 세션 관리다.
HTTP가 무상태라는 성질을 우아하다고 여겼지만,
실제 애플리케이션은 상태를 필요로 했고 쿠키와 세션 저장소가 그 위에 얹혔다.
지금 XSSR이 서 있는 자리가 그 지점이다 —
우아한 원리가 실무의 요구와 만나기 직전이고, 만나는 순간 우아함이 깎인다.

### 이 기법의 실제 쓸모는 게임이 아니라 진행 상황 표시에 있다

저자가 Flappy Bird를 고른 것은 시연으로서 탁월하지만,
그 선택이 이 기법의 적용 범위를 잘못 인식시킨다.
게임은 XSSR의 모든 약점 — 지연 시간, 높은 프레임률, 긴 연결 — 을
동시에 최대로 요구하는 용도다.

같은 재료가 훨씬 잘 맞는 용도가 있다.
서버에서 오래 걸리는 작업의 진행 상황을 보여주는 화면이다.
빌드 로그, 배포 진행률, 대용량 업로드 처리, 데이터 마이그레이션 같은 것들이다.

이런 용도에서는 XSSR의 약점이 전부 사라진다.
사용자 입력이 거의 없으므로 왕복 지연이 문제되지 않고,
갱신 빈도가 초당 몇 번이면 충분하므로 DOM이 부풀지 않으며,
작업이 끝나면 연결도 자연스럽게 끝난다.
그리고 이 용도는 지금 대부분 WebSocket이나 폴링으로 구현되어 있는데,
둘 다 클라이언트 코드를 요구한다.

실제로 이 패턴은 이미 조용히 쓰이고 있다.
스트리밍 응답으로 로그를 흘려보내는 CI 도구들,
그리고 LLM 응답을 한 글자씩 보내는 지금의 챗 인터페이스가 같은 원리 위에 있다.
후자가 이 기법이 대중화된 실제 경로다 —
사람들이 스트리밍 응답에 익숙해진 것은 XSSR 같은 실험 때문이 아니라
토큰이 하나씩 나타나는 화면을 매일 보게 되었기 때문이다.

그러니 이 글의 가치를 “JS 없는 게임”으로 요약하면 아깝다.
남는 것은 스트리밍 응답이 UI 갱신 채널이 될 수 있다는 관찰이고,
그 관찰의 가장 좋은 용도는
서버가 이미 진실을 알고 있고 클라이언트는 그것을 볼 뿐인 화면이다.
