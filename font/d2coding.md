# D2Coding 1.4.0: 점 있는 0을 고를 수 있게 되고 코드가 보이는 그대로 표시된다

원문: [D2Coding 폰트 1.4.0 릴리즈 소식을 전합니다.](https://d2.naver.com/news/7193556)

GN 토론: <https://news.hada.io/topic?id=34987>

## 요약

NAVER D2가 2026년 10월 7일 D2 News에 올린 글로,
코딩 전용 글꼴 D2Coding의 1.4.0 공개를 알린다.
글은 D2Coding을 한글과 영문, 숫자, 기호가 섞인 코드에서도
일정한 간격과 높은 가독성을 유지하도록 만든 글꼴이라고 소개한다.
1.4.0은 GitHub에 2026년 10월 3일 릴리스되었고,
글은 그 직전에 나온 1.3.4(10월 2일)와 1.3.5(10월 3일)의 개선 사항도
모두 포함한다고 밝힌다.
기존 버전은 먼저 제거하고 새 버전을 설치한 뒤
에디터나 터미널을 다시 실행해야 새 버전이 적용될 수 있다고 안내한다.
나는 이 글꼴을 설치하거나 화면에 띄워 확인하지 않았고,
아래 내용은 원문과 GitHub 저장소의 README, 릴리스 노트,
`CHANGELOG.md`를 읽고 옮긴 것이다.

### 1.4.0의 세 가지 변경

첫째, 점이 들어간 숫자 0을 고를 수 있게 되었다.
기본 0은 영문 대문자 O와 구분하려고 가운데에 빗금이 들어가 있는데,
1.4.0부터 가운데에 점이 들어간 0을 대신 쓸 수 있다.
기본값은 꺼짐이고 OpenType `cv01` 기능을 켜면 적용되며,
`cv01`을 지원하지 않고 스타일 세트만 보여 주는 애플리케이션을 위해
같은 치환을 `ss01`에도 등록했다.
점 있는 0은 기존 0의 외곽선, 너비, 세로 방향 힌팅을 그대로 유지하므로
다른 숫자와 같은 자리에 정렬된다.
CHANGELOG에 따르면 리거처 빌드에서는 리거처 처리 뒤에 0을 바꾸기 때문에
모든 리거처가 그대로 만들어지고,
표준 빌드에는 이 두 기능만 담은 `GSUB` 테이블이 새로 생겼다.

원문과 README가 제시하는 설정은 다음과 같다.

| 애플리케이션       | 설정                                                        |
| ------------------ | ----------------------------------------------------------- |
| VS Code            | `"editor.fontLigatures": "'cv01'"`                          |
| VS Code(리거처 끔) | `"editor.fontLigatures": "'calt' off, 'liga' off, 'cv01'"`  |
| Windows Terminal   | `"font": { "face": "D2Coding", "features": { "cv01": 1 } }` |
| WezTerm            | `config.harfbuzz_features = { "cv01" }`                     |
| kitty              | `font_features D2Coding +cv01` (`D2CodingBold`에도 같은 줄) |
| Ghostty            | `font-feature = cv01`                                       |

원문에는 VS Code와 Windows Terminal만 나오고,
WezTerm, kitty, Ghostty 설정은 README 표에서 가져왔다.
미리 보기 사이트(<https://naver.github.io/d2-coding-font/>)의
Dotted zero 옵션으로 두 모양을 비교할 수 있다.

둘째, 일부 글자가 기준선보다 한 픽셀 위에 그려지던 문제를 고쳤다.
FreeType 힌팅을 쓰는 환경에서 Regular는 `i`와 일부 키릴 문자를 포함한 27자,
Bold는 악센트 문자와 그리스·키릴 문자를 포함한 87자가
9~29ppem 사이의 일부 크기에서 한 픽셀 떠 있었다.
1.4.0은 해당 크기에만 힌팅 보정을 넣어 이 글자들을 주변 문자와 같은
기준선에 놓았고, 외곽선은 바꾸지 않았으며 다른 크기의 표시도 그대로다.
CHANGELOG는 이 보정이 -1px이고,
`tools/check_hinting.py`가 이제 U+0020부터 U+052F까지의 기준선 글자를
9~29ppem 전 범위에서 검사한다고 덧붙인다.

셋째, 마침표의 의미를 바꿔 보이게 하던 리거처 네 개를 없앴다.
`.=`, `.-`, `{.`, `.}` 조합의 리거처는 마침표를 가운데점 높이로 올려 그렸는데,
마침표 자체가 의미를 갖는 코드에서는 원래 문자를 오해하게 만들 수 있었다.
원문이 드는 예는 숫자와 연산자가 붙은 `1.-x`, Go 템플릿의 `{{.}}`,
Nim pragma `{.inline.}`, CSS 선택자 `.-mt-2`다.
1.4.0부터 이 네 조합은 입력한 문자 그대로 표시되고,
`..`, `...`, `..<`를 비롯한 다른 리거처는 그대로 남는다.

### 1.3.4와 1.3.5에서 들어온 변경

1.3.5는 한글이 포함된 줄에서도 코딩 리거처가 적용되게 했다.
원문은 일부 텍스트 처리 엔진이 한글 영역에서 OpenType `calt` 기능을 끄기 때문에
`<!-- 주석 -->` 같은 줄의 `<!--`와 `-->`에
리거처가 적용되지 않을 수 있었다고 설명한다.
CHANGELOG는 그 엔진을 HarfBuzz의 한글 셰이퍼와 Uniscribe라고 적는다.
해결책은 같은 리거처 규칙을 `calt`뿐 아니라 `liga`에도 등록하는 것이었고,
그 결과 이제 리거처를 끄려면 `calt`와 `liga`를 모두 꺼야 한다.
VS Code에서는 `"editor.fontLigatures": false`가 둘을 함께 끈다.

1.3.5는 Keynote에서 문단 끝에 상자 안의 원 같은 기호가 나타나던 문제도 고쳤다.
D2Coding에 들어 있던 DOS 방식 제어 문자 그림이
줄 바꿈 같은 제어 코드에 연결되어 있었고,
Keynote가 줄 바꿈 문자를 글리프로 그리면서 생긴 현상이다.
U+0001~U+001F 가운데 캐리지 리턴 U+000D를 뺀 문자의 매핑을 지웠고,
탭도 더 이상 매핑하지 않으며, 일반 공백은 기존 글리프를 유지한다.
그림 자체는 글꼴에 남아 있지만 어떤 문자 코드와도 연결되지 않는다.

1.3.4는 터미널에서 폭이 맞지 않던 기호 20자를 고쳤다.
`◽ ◾ ☔ ☕ ♈ ♉ ♊ ♋ ♌ ♍ ♎ ♏ ♐ ♑ ♒ ♓ ♿ ⚓ ⚡ 〜`는
유니코드에서 동아시아 전각(East Asian Wide)으로 분류되어
터미널이 두 칸을 주는데,
D2Coding은 영문 한 글자 폭으로 그려
기호가 왼쪽에 치우치거나 출력 정렬이 어긋났다.
이제 한글 한 글자와 같은 폭을 쓰고, 기호 크기는 그대로 둔 채 넓어진 칸의
가운데에 놓인다.
릴리스 노트는 `★ ◆ →`, 곡선 따옴표, `…`처럼
Ambiguous나 Neutral로 분류되는 기호는 반각을 유지한다고 선을 긋는다.
같은 릴리스에서 위첨자, 아래첨자, 분수 문자도 다시 만들었다.
이 문자들은 주변 숫자보다 작고 가늘었고 Regular와 Bold가 같은 윤곽선을 써서
Bold에서도 Regular 굵기로 보였는데,
이제 `¹ ² ³`과 `¼ ½ ¾`을 기준으로 비율과 위치를 맞추고 Bold에서는 굵게 그린다.

### 저장소가 함께 전하는 배경

원문에는 없지만 저장소는 이번 릴리스의 맥락을 더 많이 담고 있다.
CHANGELOG를 보면 1.3.2(2018년 5월 24일) 다음 릴리스는
2026년 7월 25일의 1.3.3이고, 그 사이 8년 넘게 새 버전이 없었다.
1.3.3은 `name`과 `head` 테이블만 고친 메타데이터 릴리스로,
NHN Corporation으로 남아 있던 저작권 표기를 NAVER Corporation으로 바꾸고
죽은 `dev.naver.com` 위키를 가리키던 라이선스 URL을 고쳤으며
`OFL.txt`를 배포 파일에 넣었다.
저장소 주소도 2017년 글에 나오는 `naver/d2codingfont`에서
지금의 `naver/d2-coding-font`로 바뀌었다.

README는 원본 디자인 소스가 이 저장소에 한 번도 들어온 적이 없다고 밝힌다.
글꼴은 2015년 FONTRIX가 NAVER를 위해 그렸고,
`.glyphs`나 `.ufo` 원본을 누가 갖고 있는지 찾는 데 시간이 걸리기 때문에,
`sources/`의 UFO 파일은
배포된 바이너리를 fontTools와 extractor로 역추출한 것이다.
README는 이를 원본 디자인 데이터가 아니라 이후 작업의 출발점이라고 부른다.
또 1.4.0이 19,936개 코드포인트를 26,190개 글리프에 매핑하며
한글 음절 11,172자 전부와 CJK 통합 한자 4,620자를 담고 있다고 적고,
한자가 없어서 다른 글꼴로 대체된다던 예전 README 설명은
배포 빌드에 한 번도 맞은 적이 없는 내용이었다고 정정한다.
라이선스는 SIL Open Font License 1.1이다.

## 분석

### 이번 릴리스의 공통 주제는 글꼴이 문자를 속이지 않게 하는 것이다

원문은 변경점을 일곱 개의 번호로 나열하지만,
묶어 놓고 보면 대부분이 같은 방향을 향한다.
마침표를 가운데점으로 올리던 리거처는
화면의 문자가 파일의 문자와 달라 보이게 했다.
제어 문자에 연결된 그림은 원래 보이지 않아야 할 줄 바꿈을 기호로 드러냈다.
전각 기호를 반각으로 그린 것은
터미널이 계산한 칸 수와 글꼴이 그린 폭이 어긋난 것이다.
Bold에서 Regular 굵기로 나오던 분수 문자와 한 픽셀 떠 있던 글자도
글꼴이 스스로 약속한 일관성을 지키지 못한 경우다.

이 관점에서 1.4.0을 다시 읽으면 “개선”이라기보다 “어긋남 바로잡기”에 가깝다.
새 기능이라 할 만한 것은 점 있는 0 하나뿐이고,
그것마저 기본값을 꺼 두어
아무것도 켜지 않은 사용자에게는 표시가 바뀌지 않게 했다.
CHANGELOG가 표준 빌드에 `GSUB` 테이블이 새로 생겼지만
두 기능을 켜지 않으면 아무것도 달라지지 않는다고 굳이 적은 것도 같은 태도다.

코딩 글꼴에서 이 기준이 중요한 까닭은
코드에서는 문자 하나의 차이가 의미의 차이이기 때문이다.
본문용 글꼴이라면 마침표 위치가 조금 달라도 읽는 데 지장이 없지만,
`{{.}}`의 마침표가 가운데점처럼 보이면
Go 템플릿을 읽는 사람은 다른 문자를 떠올린다.
리거처 네 개를 지운 결정은 이 기준을 리거처에도 적용한 것이다.

### 글꼴과 렌더링 엔진 사이의 계약이 문제의 대부분이다

이번 변경에서 눈에 띄는 점은 원인이 글꼴 안에만 있지 않다는 것이다.
한글 줄에서 리거처가 사라진 이유는 글꼴 설계가 아니라
HarfBuzz의 한글 셰이퍼와 Uniscribe가 한글 구간에서 `calt`를 끄는 동작이었다.
Keynote의 기호 문제는 Keynote가 줄 바꿈 문자를 글리프로 찾아 그리는 동작과
글꼴의 매핑이 만나서 생겼다.
기호 폭 문제는 터미널이 유니코드 East Asian Width 표를 보고 칸을 나누는 규칙과
글꼴의 실제 폭이 달라서 생겼다.

세 경우 모두 글꼴 쪽에서 맞춰 주는 방식으로 해결했다.
`liga`에 같은 규칙을 한 번 더 등록하고, 제어 문자 매핑을 지우고,
유니코드 분류에 맞춰 폭을 넓혔다.
렌더링 엔진은 수없이 많고 고칠 수 없지만 글꼴은 한 곳에서 고칠 수 있으니
현실적인 선택이다.
다만 그 대가로 글꼴은 어느 엔진이 어떤 기능을 끄는지,
어느 터미널이 어떤 표를 쓰는지를 알고 있어야 하는 처지가 된다.

이 계약의 비용은 사용자에게도 넘어온다.
1.3.5 이후 리거처를 끄려면 `calt`와 `liga`를 모두 꺼야 한다.
VS Code의 `false`처럼 둘을 함께 끄는 설정을 쓰던 사용자는 영향이 없지만,
`calt`만 끄는 방식으로 리거처를 없애 왔던 환경이라면
업데이트 뒤에 리거처가 다시 나타날 수 있다는 것이 내 해석이다.
원문은 두 기능을 모두 꺼야 한다는 사실은 적었지만,
그것이 기존 설정을 깨뜨릴 수 있다는 점까지는 짚지 않는다.

### 같은 문제가 8년을 사이에 두고 다시 나타났다

CHANGELOG를 처음부터 읽으면 같은 종류의 문제가 되풀이된다.
1.3.2(2018년)는 IntelliJ에서 18pt `i`가 짧게 보이는 문제(#70)를 고쳤고,
1.4.0은 Regular의 `i`, `і`, `ѝ`가
18ppem에서 한 픽셀 떠 있는 문제(#107)를 고쳤다.
CHANGELOG는 19와 20ppem에 이미 있던 보정을 18ppem에도 넣었다고 적는데,
크기별로 따로 손을 대는 힌팅 보정은 한 크기를 고치면
다른 크기에서 같은 글자가 또 문제를 일으키기 쉬운 구조라는 뜻이다.

제어 문자 그림은 더 직접적인 예다.
1.2(2016년)는 화살표와 상자 등 아스키 제어 문자 그림 31자를
표현 다양성 강화를 위해 추가했다고 적었는데,
10년 뒤 1.3.5는 바로 그 그림들의 매핑을 지웠다.
1.3.2가 고친 Source Insight의 탭 표시 겹침(#68)도
탭에 그림이 연결된 데서 생긴 문제였을 수 있다는 것이 내 추측이다.
한때 기능으로 넣은 것이 시간이 지나며 버그의 원천이 된 셈이다.

1.4.0에서 `tools/check_hinting.py`가 기준선 글자 전체를 9~29ppem 범위에서
검사하게 된 것은 이런 반복을 끊으려는 장치로 읽힌다.
개별 이슈를 하나씩 고치는 대신 범위 전체를 기계로 검사하면,
다음에 같은 종류의 어긋남이 생겼을 때
사람이 화면에서 발견하기 전에 잡을 수 있다.

## 비평

### 원문은 이번 릴리스에서 가장 무거운 사실을 빠뜨린다

D2 News 글은 변경점과 설정법을 꼼꼼히 설명하지만,
이 프로젝트가 8년 동안 멈춰 있다가
2026년 7월에야 다시 움직였다는 사실은 말하지 않는다.
원본 디자인 소스가 저장소에 없고
지금의 UFO가 배포 바이너리에서 역추출한 것이라는 사실도 원문에는 없다.
이 두 가지는 README와 CHANGELOG를 열어야 알 수 있다.

이 생략이 중요한 이유는 원문이 끝에서 오픈 소스로 공개되어 있으니
문제를 발견하면 이슈를 남겨 달라고 요청하기 때문이다.
기여를 부탁한다면 기여자가 무엇을 고칠 수 있는지도 알려야 한다.
README가 스스로 인정하듯 역추출한 UFO에는 2차 곡선 외곽선만 남아 있고
원래의 설계 의도는 담겨 있지 않다.
외곽선을 크게 다시 그리는 수정은 지금의 소스로는 어렵고,
힌팅 보정이나 매핑, OpenType 기능처럼 바이너리 수준에서 다룰 수 있는 범위가
현실적인 기여의 영역이라는 것이 내 해석이다.
이번 릴리스의 변경이 모두 외곽선을 건드리지 않는 쪽에 모여 있는 것도
이 제약과 무관해 보이지 않는다.

### 리거처 네 개를 지운 근거가 정책으로 남지 않았다

마침표 리거처 제거는 옳은 방향이지만 근거의 범위가 좁다.
CHANGELOG가 드는 근거는 이슈 #97과 그 안의 예시 네 가지이고,
마침표의 의미를 바꾸는 조합이라는 기준은 이 네 개에만 적용되었다.
`..`, `...`, `..<`는 그대로 남았는데,
이 리거처들이 원래 문자를 오해하게 만들지 않는다는 판단의 근거는 원문에도
저장소에도 없다.

리거처의 본질은 여러 문자를 한 모양으로 바꾸어 그리는 것이므로,
문자를 다르게 보이게 하는 것은 리거처 전체의 성질이다.
어느 선을 넘으면 오해이고 어느 선까지는 가독성 개선인지에 대한 기준이 없으면,
다음 이슈가 들어올 때마다 같은 논의를 처음부터 다시 해야 한다.
예컨대 원문이 기준으로 삼은 언어는 Go 템플릿, Nim, CSS인데,
다른 언어에서 `..<`나 다른 조합이 의미를 가질 때 어떻게 판단할지는 열려 있다.
이번 결정이 사례별 수정으로 끝나지 않으려면
README의 리거처 절에 판단 기준을 한 줄이라도 남기는 편이 낫다.

### 점 있는 0의 지원 범위는 터미널 쪽에 치우쳐 있다

README 표는 VS Code, Windows Terminal, WezTerm, kitty,
Ghostty 다섯 곳의 설정만 싣는다.
2017년 1.3 공개 글이 지원 대상으로 꼽았던 JetBrains IDE, Visual Studio, Xcode,
Eclipse, Sublime Text는 이 표에 없다.
이 도구들이 `cv01`이나 `ss01`을 켤 수 있는지는
원문과 저장소 어디에도 나오지 않는다.

`ss01`을 함께 등록한 것은
스타일 세트만 보여 주는 애플리케이션을 배려한 조치지만,
OpenType 기능을 아예 고를 수 없는 도구에서는 점 있는 0을 쓸 방법이 없다.
D2Coding은 별도 빌드를 만들지 않고 기능 플래그 하나로 해결하는 길을 골랐다.
그 선택이 빌드 수를 늘리지 않는 장점이 있는 것은 분명하지만,
설정 경로가 없는 사용자에게는 이 기능이 사실상 존재하지 않는다는 점을
원문은 말하지 않는다.

## 인사이트

### 멈춘 회사 오픈 소스를 되살리는 일은 기능이 아니라 출처와 검증에서 시작한다

1.3.3부터 1.4.0까지의 순서는
방치된 프로젝트를 되살리는 하나의 모범 순서처럼 보인다.
먼저 저작권 표기와 라이선스 URL, 라이선스 전문처럼
누가 이 글꼴을 쓸 수 있는지에 관한 메타데이터를 고쳤다.
다음으로 원본이 없다는 사실을 README에 밝히고 바이너리에서 소스를 역추출해
빌드할 거리를 만들었다.
그다음에야 오래 쌓인 이슈를 고치고 `check_hinting.py` 같은 검사 도구를 붙였다.

이 순서가 의미 있는 이유는 기능 추가가 맨 뒤에 있다는 점이다.
내 해석으로는, 라이선스 URL이 죽어 있는 글꼴은 회사 법무 검토를 통과하기 어렵고,
소스가 없는 글꼴은 아무리 이슈가 많아도 고칠 방법이 없다.
README가 한자 미포함이라는 잘못된 설명을 오랫동안 달고 있었다는 고백도
같은 맥락이다.
문서와 실제가 어긋난 상태로는 사용자 보고를 신뢰할 수 없다.
8년 공백 동안 글꼴은 여전히 쓰였지만,
쓰이는 것과 유지보수할 수 있는 것은 다른 상태였다.

### 터미널 시대의 코딩 글꼴은 유니코드 폭 표를 따르는 부속품이 된다

1.3.4의 전각 기호 수정은 작은 변경처럼 보이지만 방향을 바꾸는 결정이다.
예전에는 글꼴이 기호를 어떤 폭으로 그릴지 정했다면,
이제 D2Coding은 유니코드 East Asian Width 분류를 따르고
Ambiguous와 Neutral은 반각으로 남긴다는 규칙을 명시했다.
결정의 주도권이 디자이너에서 터미널과 유니코드 표로 넘어간 것이다.

이 흐름은 한글 글꼴에 특히 무겁다.
한글은 전각, 영문은 반각이라는 2:1 규칙을 지키는 것이
원래 한글 코딩 글꼴의 존재 이유였고,
README도 한글 음절이 라틴 문자 폭의 정확히 두 배라서
표와 상자 그리기 출력이 정렬된다고 강조한다.
그 규칙이 이제 한글 밖의 기호로 넓어졌다.
`font/jetendard.md`가 다루는 Jetendard처럼 라틴 글꼴과 한글 글꼴을 합쳐
2칸 정렬을 맞추는 프로젝트가 계속 나오는 것도 같은 요구에서 나온다고 본다.
앞으로 터미널 출력에 이모지와 기호가 더 많이 쓰일수록,
Ambiguous로 분류된 기호를 몇 칸으로 그릴지가
한글 코딩 글꼴의 다음 쟁점이 될 가능성이 크다.

### 기본값을 끈 기능은 호환성과 발견 가능성을 맞바꾼다

점 있는 0을 기본값 꺼짐으로 둔 것은
빗금 0에 익숙한 기존 사용자를 보호하는 결정이다.
`ss01`까지 등록하고 표준 빌드의 `GSUB`가 다른 것을 바꾸지 않게 한 것도
업데이트가 아무것도 깨지 않게 하려는 배려다.
보수적인 유지보수자라면 같은 선택을 했을 것이다.

하지만 기본값이 꺼진 기능은 설정을 찾아보는 사람에게만 존재한다.
원문을 읽은 사람은 설정 줄을 복사하겠지만,
설정을 건드리지 않고 글꼴 파일만 바꾸는 사용자는 변화가 있는지도 모를 것이다.
대신 미리 보기 사이트에 토글을 두어 두 모양을 비교하게 한 것은
이 비용을 줄이려는 장치로 볼 수 있다.

같은 긴장은 1.3.5의 `liga` 등록에서는 반대 방향으로 나타났다.
그쪽은 한글 줄에서 리거처를 살리려고 기본 동작을 바꾸었고,
그 대가로 기존 설정 일부가 의도와 다르게 동작할 여지를 남겼다.
한 릴리스 묶음 안에서 한 기능은 호환성을, 다른 기능은 올바름을 우선했다.
어느 쪽이 맞다기보다,
유지보수자가 변경마다 이 저울질을 어떻게 했는지를 릴리스 노트에 적어 두는 것이
사용자가 업데이트 영향을 예측하는 데 가장 쓸모 있는 정보라고 본다.

UI 글꼴을 고르는 기준을 다룬 `font/ui-font-criteria.md`가 수직 메트릭을 따지듯,
코딩 글꼴을 고를 때도 모양보다 이런 유지보수 방식과
렌더러와의 계약을 먼저 보는 편이 오래 쓰기에 안전하다.
