# BFF 서버에 SSE를 도입한 이유: 전시 서버의 통신 구조 재설계

원문: [BFF 서버에 SSE를 도입한 이유: 전시 서버의 통신 구조 재설계 | 우아한형제들 기술블로그](https://techblog.woowahan.com/26507/)

## 요약

우아한형제들 배달의민족 앱의 가게 리스트 페이지는 시간이 지나며 광고 배너,
큐레이션, 테마 배너, 가게 목록 등 여러 콘텐츠 영역이 결합된 복잡한 화면으로
진화했다. 이 하나의 화면을 그리기 위해 클라이언트는 먼저 화면 구성 정보를
받아온 뒤, 그 정보를 바탕으로 여러 서버의 엔드포인트를 병렬로 호출하는
2단계 구조를 거쳐야 했다.

이 구조에서 두 가지 성능 문제가 드러났다. 첫째, 무거운 콘텐츠 섹션
6개(섹션당 약 280KB)를 통합하면 응답이 약 1.7MB까지 부풀었다. 둘째,
전체 응답 시간이 가장 느린 컴포넌트의 응답 시간(약 300ms)에 종속되는
“가장 느린 작업자(slowest-worker)” 문제로, 사용자는 그동안 빈 화면을
보게 되었다.

팀은 이를 해결하기 위해 “하나의 지면은 하나의 API로 응답한다”는 원칙
아래 BFF(Backend For Frontend) 아키텍처를 도입해 여러 서버 호출을
단일 API 호출로 통합했다. BFF가 콘텐츠 취합과 폴백 전략을 전담하고,
클라이언트는 더 이상 개별 서버의 타임아웃과 에러 처리를 신경 쓰지
않아도 된다.

프로토콜 선택 과정에서 일반 REST, ResponseBodyEmitter, WebSocket,
SSE(Server-Sent Events) 네 가지를 비교했다. REST는 느린 작업자 문제를
해결하지 못했고, ResponseBodyEmitter는 브라우저의 EventSource API를
지원하지 않아 커스텀 파싱이 필요했으며, WebSocket은 단방향 데이터
조회에는 과한 선택이었다. 결국 팀은 “표준화된 메시지 포맷, 점진적
푸시, 클라이언트 생산성”을 근거로 SSE를 선택했다.

서버는 `DISPLAY_GROUP`(레이아웃 스켈레톤, 약 15ms 내 도착),
`SUBCATEGORY`, `SHOP_LIST`, `CURATION` 등 개별 섹션 이벤트, 마지막
`DONE` 이벤트 순으로 구조화된 스트림을 전송한다. 프런트엔드는 인증
헤더 첨부와 AbortSignal 취소 등 기존 REST 요청 패턴을 그대로 유지하기
위해 브라우저 네이티브 EventSource 대신 fetch와 ReadableStream을
조합해 구현했다. 각 이벤트는 도착하는 대로 React Query 캐시에 채워지고,
컴포넌트는 각자 구독한 캐시 키에 따라 독립적으로 렌더링된다.

nginx의 `proxy_buffering` 설정에 대해서도 통념과 다른 실험 결과를
얻었다. 일반적으로 SSE에는 버퍼링을 꺼야 한다고 알려져 있지만, 300ms
수준의 짧은 스트림에서는 200바이트 이벤트가 버퍼링 설정과 무관하게
5ms 만에 도착했다. 버퍼링은 서버와 클라이언트의 속도 차이를 완충하는
역할이며, 알림처럼 끝나지 않는 스트림에서 버퍼가 넘칠 때만 임시 파일이
생성된다. 결과적으로 유한한 응답에는 기본 설정이 최적이었다. 과거
gzip과 버퍼링을 함께 켰을 때 이벤트가 뭉쳐 도착했던 현상은 압축
필터를 통과하며 flush 신호가 전달되는 방식 때문이었지, 버퍼링 자체가
근본 원인은 아니었다.

이 변경으로 전체 데이터 도착 시간(약 300ms)은 그대로였지만, 첫
렌더링까지 걸리는 시간은 스켈레톤 기준 약 15ms로 줄었다. 네트워크
연결은 섹션별 다중 연결에서 단일 연결로 통합되었고, 사용자 경험은
빈 화면 대기에서 점진적으로 채워지는 화면으로 바뀌었다. 단순한 단일
섹션 엔드포인트에는 REST를 그대로 유지했고, QA 프로세스나 컴포넌트의
캐시 구독 모델도 기존과 동일하게 유지했다.

## 분석

### “1페이지 = 1API”는 성능 문제를 조직 구조 문제로 재정의한 것이다

이 글이 실제로 다루는 문제는 네트워크 지연이 아니라 여러 팀이 소유한
서버들의 응답 속도 차이다. 광고, 큐레이션, 가게 목록이 각각 다른
팀의 서버에서 나온다는 사실 자체가 “가장 느린 작업자” 문제의
근본 원인이며, 이는 기술이 아니라 조직 경계에서 비롯된 문제다. BFF를
도입해 “1페이지 = 1API”로 만든 것은 표면적으로는 통신 구조 개선이지만,
본질은 여러 백엔드 팀의 SLA 편차를 클라이언트가 아니라 중간
계층(BFF)이 흡수하도록 책임을 재배치한 것이다. 이 프레임은 Conway's
Law가 API 설계에 어떻게 반영되는지를 보여주는 사례이기도 하다. 조직이
분산되어 있으면 API도 분산되고, 그 분산을 다시 봉합하는 계층이
필요해진다.

### SSE 선택은 “완벽한 기술”이 아니라 “이미 알고 있는 기술”의 승리다

WebSocket이 이론적으로 더 유연한 양방향 프로토콜임에도 팀이 SSE를
선택한 이유는 기능이 아니라 생산성이었다. “표준 메시지 포맷”과
“클라이언트 생산성”이라는 선택 기준은, 이 팀에게 중요한 것이
프로토콜의 이론적 완성도가 아니라 기존 개발 관행과의 정합성이었음을
보여준다. 특히 브라우저 네이티브 EventSource를 버리고 fetch +
ReadableStream을 택한 결정은 “표준을 따르되 표준의 제약(커스텀 헤더
불가)은 우회한다”는 실용주의를 드러낸다. 이는 신기술 도입 시 흔히
벌어지는 “이상적인 스펙 준수 대 기존 인프라와의 호환성” 사이의
타협이며, 이 글에서는 후자가 이겼다.

### nginx 버퍼링 실험은 “통념을 의심하고 측정하라”는 원칙의 실천이다

SSE 도입 시 `proxy_buffering off`가 사실상 정설처럼 통용되는 상황에서,
팀은 그 통념을 그대로 따르지 않고 실제로 측정해 반증했다. 이 지점이
이 글에서 가장 값진 부분이다. 버퍼링은 무한 스트림에서 서버-클라이언트
속도 차를 흡수하기 위한 장치이므로, 300ms 안에 끝나는 유한한 응답에는
애초에 버퍼가 문제될 상황 자체가 발생하지 않는다는 논리는 프로토콜
가이드보다 워크로드의 실제 특성(스트림 길이, 이벤트 크기, 전체
지속 시간)에서 출발한 판단이다. 이는 “SSE=스트리밍=버퍼링
끄기”라는 단순 연상이 아니라, 자신들의 트래픽 패턴에 맞춰 세팅을
재검증하는 태도를 보여준다.

### 이 아키텍처는 “즉시성”이 아니라 “지각된 즉시성”을 최적화한다

전체 데이터 도착 시간은 개선 전후로 동일하게 300ms다. 실제로
줄어든 것은 사용자가 무언가를 보기 시작하는 시점(약 15ms)뿐이다.
이는 성능 최적화가 항상 “더 빠르게”를 의미하지 않고, 종종 “체감
대기 시간을 줄이는 방식으로 같은 시간을 재분배”하는 것임을 보여주는
전형적인 사례다. 스켈레톤을 먼저 보여주고 나머지를 점진적으로
채우는 패턴은 이미 프런트엔드 UX에서 널리 쓰이던 기법이지만, 이
글은 그것을 서버-클라이언트 통신 프로토콜 수준까지 끌어올려 구현한
사례라는 점에서 의미가 있다.

## 비평

### “1.7MB, 300ms”라는 숫자만으로는 SSE가 필요했다는 근거가 부족하다

글은 응답이 1.7MB, 최대 응답 시간 300ms라는 구체적 수치를 제시하지만,
이 수치가 실제로 사용자에게 문제였다는 증거(이탈률, 체감 성능 지표,
Core Web Vitals 변화)는 제시하지 않는다. 300ms는 웹 성능 기준에서
그리 긴 시간이 아니며, 스켈레톤 UI만으로도(SSE 없이) 비슷한 체감
개선을 얻을 수 있는 경우가 많다. 실제로 REST 응답을 유지한 채
클라이언트에서 섹션별로 로딩 스피너나 스켈레톤을 먼저 그리고
개별 fetch가 끝나는 대로 채우는 방식으로도 “빈 화면 대신 점진적
렌더링”은 구현 가능하다. 이 글은 SSE가 왜 “그 방식보다” 나은지를
직접 비교하지 않는다. 인프라 계층(단일 연결, 프로토콜 통합)의
이점은 언급되지만, 그것이 클라이언트 다중 요청 방식 대비 실제로
얼마나 나은지에 대한 정량적 비교가 빠져 있다.

### fetch + ReadableStream 선택의 트레이드오프가 축소되어 서술된다

네이티브 EventSource 대신 fetch + ReadableStream을 택한 이유로
커스텀 헤더와 AbortSignal 지원을 들었지만, 이 선택에는 상당한 비용이
따른다. EventSource는 브라우저가 자동 재연결, `Last-Event-ID`를 통한
스트림 재개, 파싱 등을 표준으로 제공하지만, fetch + ReadableStream을
쓰면 이 모든 것을 직접 구현해야 한다. 특히 자동 재연결 로직의 부재는
네트워크가 불안정한 모바일 환경에서 사용자 경험에 직접적인 영향을
줄 수 있는 부분인데, 글에서는 이 재연결 처리를 어떻게 했는지, 혹은
안 했는지에 대한 언급이 없다. “표준 요청 패턴을 그대로 가져갈 수
있었다”는 서술은 얻은 것만 강조하고 잃은 것(브라우저 표준 재연결
메커니즘)은 침묵한다.

### 버퍼링 실험의 일반화 범위가 암묵적으로 확장된다

nginx 버퍼링을 끄지 않아도 된다는 결론은 “300ms 안에 끝나는 이
특정 워크로드”에서만 검증되었다. 하지만 글의 어조는 이 결론을 마치
SSE 일반에 적용 가능한 통찰처럼 서술한다. 실제로는 이벤트 크기가
커지거나, 네트워크 상태가 나빠지거나, 스트림 지속 시간이 늘어나면
버퍼 오버플로가 발생할 조건이 달라진다. “우리 트래픽에서는 버퍼가
차지 않았다”와 “SSE에 버퍼링을 끌 필요는 없다”는 서로 다른 수준의
주장인데, 글은 전자의 실험 결과를 후자의 일반 원칙처럼 제시하는
경향이 있다. 다른 팀이 이 글만 보고 자신들의 워크로드 특성을 검증하지
않은 채 버퍼링 설정을 그대로 따라 한다면, 이 글이 정확히 경계하려던
“통념을 검증 없이 따르는” 실수를 반복하게 된다.

### BFF가 새로운 단일 장애점이 된다는 사실이 다뤄지지 않는다

여러 서버 호출을 BFF 하나로 통합하면 클라이언트의 장애 처리는
단순해지지만, 동시에 BFF 자체가 전체 페이지 렌더링의 단일 장애점이
된다. 기존 구조에서는 광고 서버가 죽어도 가게 목록은 보일 수 있었지만,
BFF가 죽으면 전체 스트림이 시작조차 되지 않는다. 글은 “BFF가 폴백
전략을 담당한다”고만 언급할 뿐, BFF 자체의 장애 시나리오, 부분 실패
시 어떤 이벤트까지 보내고 어떤 이벤트를 생략하는지, 그리고 이
아키텍처가 만들어내는 새로운 실패 모드에 대한 논의가 빠져 있다.
통합은 항상 복잡성을 어딘가로 이동시킬 뿐 없애지 않는데, 그 이동한
복잡성이 어디로 갔는지에 대한 설명이 부족하다.

## 인사이트

### SSE 기반 BFF는 관측 가능성(observability) 도구 체계를 재설계해야 한다는 숨은 비용을 만든다

글은 QA에서 Postman이 SSE를 표시할 수 있어 프로세스가 바뀌지 않았다고
언급하지만, 이는 빙산의 일각이다. 기존 REST 기반 모니터링은 요청 하나에
응답 코드 하나, 응답 시간 하나가 대응되는 단순한 모델을 전제로
APM(Application Performance Monitoring) 대시보드, 알람, SLA 지표가
설계되어 있다. SSE 스트림으로 전환하면 하나의 HTTP 연결 안에 여러
이벤트가 서로 다른 시점에 도착하고, 각 이벤트가 서로 다른 백엔드
서비스에서 왔을 수 있다. “이 요청이 실패했다”는 개념 자체가 모호해진다.
`DISPLAY_GROUP`은 왔지만 `SHOP_LIST`가 타임아웃되면 이것은 부분
성공인가 실패인가? 이 질문에 답하려면 이벤트 단위의 세밀한 트레이싱,
연결 단위가 아닌 이벤트 단위의 에러율 집계, 그리고 “스트림이 정상
종료(`DONE` 수신)됐는지”를 별도로 추적하는 지표 체계가 필요하다. 이
글은 이 전환 비용을 언급하지 않지만, 실제로 SSE를 도입한 팀이라면
반드시 마주치는 다음 단계의 과제다.

### 이 패턴은 GraphQL의 “느린 필드” 문제와 같은 문제를, 다른 시대의 다른 도구로 재발명한 것이다

“1페이지 = 1API인데 그 안의 컴포넌트 중 하나가 느리다”는 문제는
GraphQL 진영에서 `@defer`, `@stream` 디렉티브로 이미 다뤄온 문제와
본질적으로 동일하다. GraphQL은 쿼리 하나로 여러 리졸버(resolver)를
호출하고, 느린 필드는 나중에 스트리밍으로 채워 넣는 방식을 표준화하려
시도했다. 이 글의 팀은 GraphQL을 도입하는 대신 REST + SSE 조합으로
같은 문제를 자체적으로 해결했다. 이는 두 가지를 시사한다. 하나는
“여러 백엔드를 하나의 응답으로 점진적으로 합성한다”는 요구가 특정
회사나 기술 스택에 국한된 문제가 아니라 마이크로서비스/BFF
아키텍처가 일정 규모 이상으로 커지면 필연적으로 마주치는 구조적
문제라는 것이다. 다른 하나는, 표준화된 해법(GraphQL 스트리밍)이
존재함에도 실무에서는 조직의 기존 스택과 팀 역량에 맞춰 더 단순하고
직접적인 해법(SSE)을 재발명하는 경우가 많다는 것이다. 표준의 이론적
우아함보다 팀이 이미 능숙하게 다루는 도구가 실제 선택을 좌우한다.

### “1페이지 = 1API” 원칙은 페이지가 늘어날수록 BFF의 조합 폭발(combinatorial explosion)을 부른다

이 원칙을 하나의 페이지에 적용하는 것은 합리적이지만, 서비스 전체로
확장하면 새로운 문제를 낳는다. 배달의민족 앱에는 가게 리스트 페이지
외에도 검색 결과, 주문 내역, 프로모션 페이지 등 여러 화면이 있을
것이고, “1페이지 = 1API” 원칙을 일관되게 적용한다면 페이지마다 전용
BFF 엔드포인트가 필요해진다. 각 엔드포인트는 여러 백엔드 서비스의
조합을 알고 있어야 하므로, 백엔드 서비스 하나가 API를 변경하면 그
서비스를 참조하는 모든 BFF 엔드포인트를 함께 수정해야 하는 결합이
생긴다. 이는 마이크로서비스가 해결하려 했던 “독립 배포 가능성”을
BFF 계층에서 다시 깨뜨리는 역설적 결과로 이어질 수 있다. 페이지 수가
늘어날수록 BFF 코드베이스는 각 페이지의 조합 로직을 담은 접착제
코드(glue code)로 채워지고, 이 접착제 코드 자체가 유지보수 부담이
되는 시점이 반드시 온다. 이 글은 단일 페이지 사례만 다루고 있어
그 확장 시나리오에서의 트레이드오프를 검증할 기회를 놓치고 있다.
