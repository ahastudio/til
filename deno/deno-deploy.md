# Deno Deploy: 정식 출시 여덟 달 만에 종료가 정해진 JavaScript 호스팅

<https://deno.com/deploy>

HN 토론: <https://news.ycombinator.com/item?id=26621028> (22점, 1개 댓글)

## 소개

Deno Deploy는 Deno를 만드는 Deno Land가 운영하는
JavaScript, TypeScript 앱 호스팅 서비스다.
홈페이지는 “Now Generally Available”이라는 문구 아래 모든 JavaScript와
TypeScript 앱을 위한 단순한 플랫폼 하나라고 소개한다.
Fresh, Next, Nuxt, SvelteKit, Astro, Remix, Hono, Express 같은 프레임워크 로고를
늘어놓고, ISR, SSG, SSR, PPR, FFI, 서브프로세스, Node 애드온까지 돌릴 수 있다고
적는다.
매달 100억 건 이상의 요청을 처리한다는 수치와 Netlify Edge Functions가 Deno를
고른 이유를 말하는 Netlify CEO Mathias Biilmann의 인용도 함께 실었다.

지금의 Deno Deploy는 2021년부터 운영하던 서비스를 처음부터 다시 만든 것이다.
문서는 예전 서비스를 Deploy Classic이라 부르며,
새 서비스는 대시보드와 실행 환경이 모두 바뀌었다고 설명한다.
대시보드 주소는 Classic의 `dash.deno.com`에서 `console.deno.com`으로 옮겼다.
2026년 2월 3일 Luca Casonato, Ryan Dahl, Andy Jiang이 블로그에 정식 출시를
알렸다.
Classic과 서브호스팅 v1 API는 문서에 2026년 7월 20일 종료로 예고되어 있었다.

그런데 정식 출시 여덟 달 뒤인 2026년 10월 9일,
Ryan Dahl은 Deno 팀 전체가 Cloudflare에 합류한다고 발표했다.
그 글은 Deno Deploy가 앞으로 6개월 동안 운영한 뒤 종료된다고 밝힌다.
홈페이지 상단에는 Deno가 Cloudflare에 합류한다는 띠 배너만 붙었고,
본문과 가격표, 문서에는 종료 일정이 아직 반영되지 않았다.
합류 발표 자체는 `deno/deno-cloudflare.md`에서 따로 다룬다.

## 동작 방식

### 실행 환경

런타임 문서에 따르면 모든 앱은 격리된 Linux 환경에서 표준 Deno 런타임으로 돈다.
JSR과 npm 의존성, 파일 시스템 읽기와 쓰기, 서브프로세스, FFI,
Node 네이티브 애드온까지 Deno CLI의 기능을 그대로 쓴다.
권한은 `--allow-all`로 고정되어 있고,
`--unstable-*`를 비롯한 런타임 플래그는 넘길 수 없다.
아키텍처는 x64나 ARM64이며, 문서가 밝힌 런타임 버전은 Deno 2.5.0이다.
Node 앱도 Deno 위에서 돌린다는 점이 Classic과 가장 크게 다르다.
Classic은 FFI, 네이티브 애드온, 서브프로세스,
쓰기 권한을 막았고 npm 호환성도 떨어졌다.

홈페이지는 코드가 가벼운 V8 아이솔레이트에서 돌아
람다 함수나 가상 머신보다 콜드 스타트가 빠르다고 적는다.
반면 런타임 문서는 미리 준비해 둔 Linux microVM과 Deno 런타임에서 앱을
띄운다고 설명한다.
두 설명은 층위가 다르다.
문서의 microVM 설명이 실제 격리 단위에 가깝다고 보는 것은 이 노트의 해석이다.

### 생명주기

앱은 서버리스 방식으로 요청이 올 때 시작하고, 요청이 끊기면 멈춘다.
멈추기까지의 유휴 시간은 5초에서 10분 사이로 정해져 있지 않다.
데이터가 오가는 WebSocket 연결은 ping/pong 프레임까지 포함해 앱을 살려 둔다.
종료할 때는 `SIGINT`를 보내고 5초 안에 끝나지 않으면 `SIGKILL`로 강제 종료한다.
트래픽이 있어도 부하가 줄거나 서버 자원이 모자라거나 인프라를 갱신할 때는
인스턴스를 내리는 퇴출(eviction)이 일어난다.
HTTP 서버가 뜨기 전에 앱이 죽으면 그 시작을 일으킨 요청은 502로 실패한다.

콜드 스타트는 hello world 앱 기준 100밀리초 안, 큰 앱은 수백 밀리초라고 한다.
클라이언트가 TLS 연결을 위해 첫 TCP 패킷을 보내는 순간 앱을 띄우기 시작하고,
빌드의 워밍업 단계에서 시작할 때 읽는 파일을 분석해 파일 시스템을 최적화한다.
문서는 의존성을 줄이고, 드물게 쓰는 코드는 동적 `import()`로 미루고,
시작 시점의 최상위 `await`와 네트워크 요청을 줄이라고 권한다.

### 타임라인과 리비전

빌드 하나가 리비전 하나이고, GitHub에서 배포하면 커밋과 대체로 일대일로 맞는다.
리비전은 타임라인에 쌓이며, 타임라인마다 트래픽을 받는 활성 리비전이 하나 있다.

| 타임라인   | 주소                                          | 컨텍스트    |
| ---------- | --------------------------------------------- | ----------- |
| Production | `https://<app>.<org>.deno.net`, 커스텀 도메인 | Production  |
| Git 브랜치 | `https://<app>--<branch>.<org>.deno.net`      | Development |
| 프리뷰     | `https://<app>-<revision>.<org>.deno.net`     | Development |

특정 리비전을 활성 리비전으로 고정하면 롤백이 되고,
고정을 풀지 않는 한 새 빌드가 자동으로 활성화되지 않는다.
문서는 큰 행사 기간처럼 배포를 얼려야 할 때 이 잠금을 쓰라고 한다.
30일 넘게 트래픽을 받지 않은 리비전은 비활성화되고, 다시 7일이 지나면 삭제된다.

### 환경 변수와 데이터베이스

환경 변수는 평문과 시크릿으로 나뉘고 앱이나 조직 단위로 둔다.
컨텍스트는 Production, Development, 빌드 중에만 보이는 Build로 나뉜다.
조직 변수는 앱 변수가 덮어쓴다.

데이터베이스는 PostgreSQL과 Deno KV를 지원한다.
PostgreSQL은 외부 인스턴스를 연결하거나 Prisma가 호스팅하는 Prisma Postgres를
대시보드에서 바로 만들 수 있다.
연결한 인스턴스 안에 타임라인마다 논리 데이터베이스를 따로 만들고 접속 정보를
환경 변수로 주입하므로, 풀 리퀘스트마다 격리된 데이터베이스가 생긴다.
정식 출시 글의 예제는 설정 없이 `new Pool()`만으로 연결한다.
타임라인마다 데이터베이스를 새로 만들기 때문에,
외부 인스턴스에 연결하는 사용자에게는 데이터베이스 생성 권한이 있어야 한다.

### 주변 기능

`deno run --tunnel`과 `deno task --tunnel`은 로컬 앱을 공개 주소로 노출하면서
대시보드의 환경 변수를 내려받고 텔레메트리를 대시보드로 보낸다.
`Deno.cron()`으로 코드에 정의한 크론 작업은 배포할 때 자동으로 등록되고,
실행 이력은 대시보드의 Cron 탭에서 본다.
로그, 트레이스, 메트릭은 OpenTelemetry 기반으로 자동 수집되며,
2026년 3월부터 조직 단위로 외부 OTLP 수집기에 내보낼 수 있다.
OIDC 토큰 발급과 AWS, GCP용 Cloud Connections를 쓰면
장기 자격 증명 없이 클라우드에 인증할 수 있다.
브라우저에서 바로 프로젝트를 만드는 플레이그라운드와,
에이전트가 만든 코드를 microVM에서 돌리는 Deno Sandbox도 같은 콘솔에 있다.

홈페이지 하단은 `deployd`로 자기 AWS나 GCP에서 Deno Deploy를 직접 운영할 수
있다고 소개하며, 관심이 있으면 연락하라는 링크를 붙였다.

## 배포하기

### 대시보드와 GitHub

`console.deno.com`에서 조직을 만들고 `+ New App`으로 GitHub 저장소를 고르면
프레임워크를 감지해 빌드 설정을 채운다.
조직 이름과 슬러그는 처음에는 바꿀 수 없었지만 2026년 1월부터 바꿀 수 있다.
빌드는 대기, 준비, 설치, 빌드, 배포 순서로 진행되고 로그가 실시간으로 흐른다.
배포 단계에서는 타임라인마다 데이터베이스 생성, 사전 배포 명령, 워밍업,
라우팅이 차례로 일어난다.
사전 배포 명령은 마이그레이션용이며 `DENO_TIMELINE` 환경 변수로 어느 타임라인을
준비하는지 알려 준다.
커밋 메시지에 `[skip ci]`나 `[skip deploy]`를 넣으면 그 커밋은 배포하지 않는다.

빌드 시작과 끝에는 GitHub `repository_dispatch` 이벤트가 나가므로 GitHub
Actions에서 프리뷰 주소를 받아 후속 작업을 돌릴 수 있다.

```yaml
on:
  repository_dispatch:
    types: [deno_deploy.build.routed] # 트래픽이 새 리비전으로 넘어간 뒤

jobs:
  smoke:
    runs-on: ubuntu-latest
    steps:
      - name: 프리뷰 주소 확인
        run: curl -fsSI "${{ github.event.client_payload.revision.preview_url }}"
```

### 설정을 코드로 두기

2026년 1월부터 `deno.json`의 `deploy` 키로 앱 설정을 저장소에 둘 수 있다.
`deploy.buildTimeout`을 뺀 옵션이 하나라도 있으면
대시보드 설정은 통째로 무시된다.

```json
{
  "deploy": {
    "install": "deno install",
    "build": "deno task build",
    "predeploy": "deno task migrate",
    "buildTimeout": "10m",
    "runtime": {
      "type": "dynamic",
      "entrypoint": "main.ts",
      "memoryLimit": 1024
    }
  }
}
```

`buildTimeout`은 정수 초나 `s`, `m`, `h` 접미사만 받는다.
`"1.5m"`처럼 형식이 틀리면 `deploy` 섹션 전체가 무시되고,
요금제 상한을 넘으면 상한으로, 1분보다 짧으면 1분으로 맞춘다.
앱 디렉터리만은 소스가 어디 있는지를 정하므로 대시보드에서만 바꾼다.

### CLI

Classic의 `deployctl`은 사라졌고 Deno CLI의 `deno deploy` 하위 명령이 대신한다.
이 노트를 쓰면서 아래 명령을 직접 실행하지는 않았다.

```bash
# 대화형 마법사로 앱 만들기
deno deploy create

# CI용: 플래그를 주면 마법사 없이 만든다
deno deploy create --org my-company --app my-api \
  --source local --framework-preset fresh \
  --build-timeout 5 --build-memory-limit 1024 --region us

# 현재 디렉터리를 프로덕션에 배포
deno deploy --org my-company --app my-api --prod

# 시크릿 환경 변수 추가와 .env 파일 불러오기
deno deploy env add DATABASE_URL "postgresql://..." --secret
deno deploy env load .env.production
```

CI에서는 사용자 토큰이나 조직 토큰을 `DENO_DEPLOY_TOKEN` 환경 변수로 넘긴다.

## 요금과 제한

### 요금제

가격 페이지의 요금은 Deno Sandbox와 서브호스팅을 포함한 Deno Deploy 전체
사용량에 적용된다.
Enterprise는 모든 항목이 협의이며,
99.95% 가용성 SLA와 SOC2 Type 1, DPA가 붙는다.

| 항목                | Free       | Pro                            | Builder                          |
| ------------------- | ---------- | ------------------------------ | -------------------------------- |
| 월 요금             | $0         | $20                            | $200                             |
| 월 요청             | 1M         | 5M, 이후 $2/M                  | 25M, 이후 $2/M                   |
| 송신 트래픽         | 20GiB      | 200GiB, 이후 $0.20/GiB         | 2,000GiB, 이후 $0.20/GiB         |
| 활성 CPU            | 10시간     | 50시간, 이후 $0.10/시간        | 500시간, 이후 $0.10/시간         |
| 메모리 시간         | 150 GiB-hr | 750 GiB-hr, 이후 $0.025/GiB-hr | 7,500 GiB-hr, 이후 $0.025/GiB-hr |
| 리비전 저장 공간    | 10 GiB     | 50 GiB, 이후 $0.08/GiB-월      | 500 GiB, 이후 $0.08/GiB-월       |
| 활성 앱             | 10         | 50                             | 10,000                           |
| 커스텀 도메인       | 5          | 100                            | 1,000                            |
| 와일드카드 도메인   | 없음       | 있음                           | 있음                             |
| 동시 빌드           | 1          | 3                              | 20                               |
| 시간당 빌드         | 15         | 60                             | 250                              |
| KV 저장 공간        | 1 GiB      | 5 GiB, 이후 $0.75/GiB          | 10 GiB, 이후 $0.75/GiB           |
| 로그, 트레이스 보존 | 1일        | 1주                            | 1주                              |
| 팀원                | 3          | 10                             | 25                               |

CPU는 코드가 실제로 실행되는 시간만 센다.
요청을 기다리거나 네트워크 I/O에 막혀 있는 동안은 세지 않는다.
메모리는 앱이 메모리에 올라 있는 초마다 기본 할당량 768MB로 계산하고,
더 높은 한도를 설정하면 그 값으로 계산한다.
유휴 앱은 20~30초쯤 뒤 내려가므로 0으로 줄어든 동안에는 메모리 요금이 없다.

Free 조직이 요청, 대역폭, CPU, 메모리 한도를 넘으면
다음 결제 주기까지 앱이 멈춘다.
Pro 이상은 초과분을 월말에 청구하고, 지출 상한을 걸 수 있다.
신용카드를 등록해 조직을 인증하기 전까지는 Free 한도보다 더 좁은 제한이 걸린다.

### 무료 한도는 출시 뒤에 줄었다

2026년 2월 정식 출시 글은 무료 요금제를 월 100만 요청, 송신 100GB,
CPU 15시간으로 소개했다.
지금 가격 페이지의 무료 한도는 송신 20GiB, CPU 10시간이다.
2026년 3월 변경 기록의 Builder 요금제는 요청 2천만 건과 CPU 400시간이었다.
지금 가격 페이지에는 2,500만 건과 500시간으로 올라 있다.
요금표가 출시 뒤에도 여러 번 바뀌었으므로
숫자는 가격 페이지에서 직접 확인해야 한다.

### 기술적 제한

| 항목            | 값                                                   |
| --------------- | ---------------------------------------------------- |
| 리전            | `us`, `eu` 두 곳과 둘 다 쓰는 `global` (Classic은 6) |
| 배포 크기       | 소스와 정적 파일 합계 1GB 이하                       |
| 런타임 메모리   | 기본 768MB, Pro에서 4GB까지                          |
| 빌드 시간 제한  | 기본 5분, Pro에서 30분까지                           |
| 빌드 메모리     | 기본 3GB, Pro에서 4GB까지                            |
| 종료 유예       | `SIGINT` 뒤 5초                                      |
| 큐              | 지원하지 않음 (`Deno.Kv.enqueue()` 불가)             |
| 앱 조직 간 이전 | 지원하지 않음                                        |

443 포트로 나가는 연결은 TLS를 종료해야 하므로 `Deno.connect` 대신
`Deno.connectTls`를 써야 한다.
TLS-over-TLS 프록시를 막기 위한 제한이며 `fetch`는 상관없다.
외부 데이터베이스를 연결할 때 Deno Deploy의 IP 목록을 줄 수 없으니 모든 IP에서
접속을 허용하라고 문서는 적는다.

문서끼리 어긋나는 곳도 있다.
제한 문서는 앱 최대 메모리를 512MB라고 하지만,
빌드 문서와 가격 페이지는 기본값을 768MB로 적는다.
Classic 비교표는 OpenTelemetry 내보내기를 작업 중이라 표시하지만,
변경 기록은 2026년 3월에 이미 출시했다고 적는다.
제한 문서는 초기 공개 베타 동안 가용성을 보장하지 않는다는 문장도 정식 출시
뒤까지 그대로 두었다.

## 종료 일정과 이전

Ryan Dahl은 2026년 10월 9일 Deno 블로그 글에서 Deno 팀이 Cloudflare Workers와
Durable Objects 팀과 함께 일하게 되었다고 밝혔다.
별도의 런타임과 호스팅 서비스를 계속 개발하는 대신 공동 플랫폼에 개발 역량을
모으기로 했다는 것이다.
그가 밝힌 구체적인 내용은 다음과 같다.

| 대상        | 발표 내용                                                         |
| ----------- | ----------------------------------------------------------------- |
| Deno Deploy | 6개월 더 운영한 뒤 종료, 유료 고객의 Cloudflare Workers 이전 지원 |
| Deno 런타임 | 1년 동안 월간 버그·보안 릴리스, 그 뒤 개발 종료, 오픈소스로 유지  |
| JSR         | 계속 운영, 인프라는 Cloudflare로 이전                             |
| `rusty_v8`  | 계속 지원, `workerd`에 통합하는 작업 진행                         |

발표 날짜에서 6개월을 세면 2027년 4월 무렵이지만, 정확한 종료일은 글에 없다.
이전 지원은 유료 고객만 대상으로 적혀 있다.
Deno Sandbox, 서브호스팅, Deno KV, `deployd`를 어떻게 할지는
이 글에 나오지 않는다.
Cloudflare 블로그의 공동 글에서 Ryan Dahl은 Deno Deploy를 만들고 운영하면서
여러 퍼블릭 클라우드와 데이터베이스, 서로 얽힌 서비스 때문에
클라우드 인프라가 얼마나 복잡해지는지 배웠다고 적었다.
그 반성에서 나온 것이 Rust로 쓴 단일 바이너리에 객체 저장소 하나만 외부 의존으로
두는 `celld`이고, 이제 `celld`의 코드와 아이디어를 `workerd`에 합친다.

### 이전할 때 걸리는 것

Cloudflare Workers로 옮길 때 무엇이 그대로 가고
무엇을 다시 짜야 하는지는 발표에 없다.
아래는 문서에 적힌 Deno Deploy의 특성을 기준으로 이 노트가 짚는 지점이다.

- 실행 모델이 다르다.
  Deno Deploy는 `--allow-all` Deno 프로세스가 microVM 안에서 파일 쓰기,
  서브프로세스, FFI, Node 네이티브 애드온까지 쓰는 구조였다.
  이런 기능에 기댄 앱은 단순한 이식으로 끝나지 않을 가능성이 크다.
- `Deno.*` API 의존을 찾아야 한다.
  `Deno.serve()`, `Deno.cron()`, `Deno.openKv()`처럼 Deno 전용 API를 쓰는 부분이
  이전 비용의 대부분이 된다.
- 데이터는 플랫폼 밖으로 꺼내야 한다.
  Prisma Postgres는 문서상 자기 Prisma 계정으로 내보낼 수 있다.
  Deno KV는 S3 호환 버킷으로 연속 백업하는 문서가 있지만,
  새 Deploy의 KV 통합을 알린 2025년 8월 변경 기록은 수동 백업을 아직 지원하지
  않는다고 적었다.
  Classic에서 새 Deploy로 옮길 때도 KV는 자동 이전이 없어 지원팀에 문의해야 했다.
- 커스텀 도메인은 DNS를 옮기는 데 시간이 걸린다.
  Classic 이전 안내는 DNS 전파에 최대 48시간을 두라고 했다.

## 트레이드오프

### 프레임워크를 고치지 않고 올리는 편의와 그 대가

Deno Deploy의 핵심 약속은 어댑터도, 플랫폼 전용 설정 파일도 없이
지금 쓰는 프레임워크를 그대로 올린다는 것이었다.
표준 Deno 런타임을 microVM에서 통째로 돌리니 Node 앱의 파일 쓰기나
네이티브 애드온도 돈다.
그 대가로 앱 하나가 프로세스 하나 크기의 자원을 쓰고,
요금도 768MB 기본 메모리 시간과 CPU 시간으로 매겨진다.
아이솔레이트 단위로 쪼개는 Workers보다 앱당 무게가 크다는 것은 이 노트의
해석이며, Deno 팀이 직접 비교한 수치는 없다.

### 타임라인별 데이터베이스 격리

풀 리퀘스트마다 격리된 데이터베이스를 만드는 기능은 프리뷰에서 실데이터를
망가뜨릴 위험을 없앤다.
대신 연결한 데이터베이스 사용자에게 데이터베이스 생성 권한을 줘야 하고,
브랜치가 늘수록 인스턴스 안의 논리 데이터베이스도 늘어난다.
접속 정보가 환경 변수로 자동 주입되므로 코드는 간결해지지만,
그만큼 앱이 Deno Deploy의 주입 방식에 기대게 된다.

### 리전 두 곳

Classic의 6개 리전이 2개로 줄었다.
한국이나 일본 사용자에게 가까운 리전은 없으므로 지연 시간이 중요한 앱은
처음부터 불리하다.
문서는 모자란 리전을 자체 인프라에서 운영할 수 있다고 하지만,
홈페이지가 안내하는 `deployd` 자체 호스팅은 연락을 거쳐야 하는 길이었다.

## 함정

- 홈페이지만 보면 안 된다.
  2026년 10월 10일 현재 홈페이지와 가격 페이지는 여전히 정식 출시와 확장을 말하지만
  서비스는 6개월 뒤 종료가 예고된 상태다.
- Classic 시절 코드가 워밍업에서 죽는다.
  `deno.land/std`의 옛 `serve()`를 쓰면 새 Deploy의 워밍업 단계에서 타임아웃으로
  실패하므로 `Deno.serve()`로 바꿔야 한다.
- `deno.json`에 `deploy` 키를 하나라도 넣으면 대시보드에서 고친 설정이 조용히
  무시된다.
- 앱 슬러그를 바꾸면 이전 `deno.net` 주소가 바로 끊긴다.
  커스텀 도메인은 영향이 없다.
- Free 요금제는 한도를 넘으면 청구 대신 앱이 다음 주기까지 멈춘다.
  트래픽이 갑자기 몰리는 개인 프로젝트에는 장애가 된다.
- 유휴 타임아웃이 5초에서 10분 사이로 흔들리고 퇴출도 일어나므로,
  긴 요청과 WebSocket 클라이언트는 재연결을 전제로 짜야 한다.

## 체크리스트

- 종료 공지 이후 새 프로젝트를 Deno Deploy에 올리지 않기로 했는가?
- 운영 중인 앱에서 `Deno.*` 전용 API와 FFI, 서브프로세스, 파일 쓰기 사용처를
  목록으로 뽑았는가?
- Deno KV 데이터를 내보낼 방법을 지원팀에 확인했는가?
- Prisma Postgres를 자기 Prisma 계정으로 내보냈는가?
- 커스텀 도메인 이전에 DNS 전파 시간을 감안한 일정을 잡았는가?
- 유료 고객이라면 Cloudflare Workers 이전 지원을 요청했는가?

## 기억할 원칙

### 정식 출시는 지속을 약속하지 않는다

Deno Deploy는 Classic을 대체할 새 서비스로 2026년 2월에 정식 출시했고,
사용자에게 7월 20일까지 Classic에서 옮기라고 했다.
옮긴 사용자는 석 달도 안 되어 다시 이전 공지를 받았다.
작은 회사가 운영하는 플랫폼에서는 “Generally Available”이라는 문구보다 운영사가
그 사업에 얼마나 오래 돈을 댈 수 있는지가 더 중요한 신호다.
홈페이지가 종료 사실을 아직 말하지 않는다는 점도,
서비스 상태를 홈페이지가 아니라 운영사의 공지에서 확인해야 하는 이유다.

### 표준 API에 가까울수록 이전 비용이 작다

Deno Deploy가 내세운 장점 가운데 웹 표준 `fetch`, Web Cache API, OpenTelemetry,
OIDC처럼 표준에 기댄 것은 다른 플랫폼으로 그대로 가져갈 수 있다.
타임라인별 데이터베이스 주입, `Deno.cron()`, Deno KV처럼 플랫폼에 묶인 편의는
종료와 함께 다시 만들어야 한다.
어느 플랫폼을 고르든 편의 기능을 쓸 때마다 그것을 떼어낼 비용을 같이 적어 두면,
이번 같은 종료 공지가 와도 대응 범위를 금방 가늠할 수 있다.
