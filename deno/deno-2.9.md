# Deno 2.9: 데스크톱 앱, 절반으로 준 기동 시간, 그리고 탈-npm 이주

원문: [Deno 2.9](https://deno.com/blog/v2.9)

HN 토론: <https://news.ycombinator.com/item?id=48675717> (145점, 61개 댓글)

GN 토론: <https://news.hada.io/topic?id=30726>

## 요약

Deno가 2026년 6월 25일에 발표한 2.9 릴리스다.
헤드라인 기능은 `deno desktop`으로,
Electron이나 Tauri의 보일러플레이트 없이
웹 기술로 네이티브·자체 완결 데스크톱 애플리케이션을 만들어
단일 배포 바이너리로 컴파일한다.
UI는 웹뷰에서, 로직은 Deno에서 돈다.
Next.js, Astro, Fresh, Remix, Nuxt, SvelteKit, SolidStart,
TanStack Start, Vite SSR을 자동 감지하고,
`Deno.BrowserWindow`, `Deno.Tray`, macOS의 `Deno.Dock` 같은
네이티브 API를 제공한다.
백엔드로 OS 내장 엔진을 쓰는 webview(기본)와
Chromium을 번들하는 cef가 있고,
Linux·Windows·macOS로 교차 컴파일한다.

성능이 크게 개선됐다.
콜드 기동 시간이 34.2ms에서 17.3ms로 절반이 되었고(1.98배),
`Deno.serve` 실제 처리량이 1.27배(초당 5.68만→7.24만 요청),
실제 워크로드의 RSS 메모리가 2.2배(142MB→64MB),
1MiB 응답에서 3.1배(197MB→63MB) 줄었다.
CSS 모듈을 import 속성으로 가져와(`with { type: "css" }`)
구성 가능한 스타일시트로 만드는 것도 지원한다.

npm·pnpm·yarn·Bun에서의 이주가 간소해졌다.
`deno install`이 각 도구의 락파일을 직접 읽어 정확한 버전으로 `deno.lock`을
시드하고,
도구가 `node`를 호출하면 Deno로 전달하는 Node 심을 둔다.
공급망 보안으로 기본 24시간의 최소 의존성 나이와,
탈취된 메인테이너 토큰 공격을 막는 no-downgrade 신뢰 정책을 도입했다.
테스트는 내장 스냅숏, 변경 인식 선택(`--changed`), 재시도/반복,
커버리지 임계값, 샤딩, 매개변수 테스트를 더했다.
Node 호환성이 26 버전으로 올랐고,
웹 암호화에 ML-KEM·ML-DSA·SLH-DSA 같은 후양자(post-quantum) 알고리즘이 추가됐다.
`Deno.serve`의 자동 압축은 기본 비활성으로 바뀌었다.

## 분석

### 이 릴리스의 무게 중심은 Deno의 영역 확장이다

Deno 2.9의 여러 변화를 관통하는 방향은 Deno가 다루는 영역의 확장이다.
`deno desktop`은 서버·CLI 런타임이던 Deno를 데스크톱 앱으로,
npm 락파일 직접 읽기는 Deno를 npm 생태계 이주의 종착지로,
후양자 암호화는 Deno를 미래 보안 표준의 선두로 넓힌다.
Deno는 자기가 커버하는 표면을 계속 늘린다.

이 확장이 중요한 이유는 런타임 경쟁의 성격을 드러내기 때문이다.
modern-nodejs-2025에서 본, Node.js가 fetch·테스트·감시를 내장하며
경쟁 런타임을 따라잡았듯,
Deno는 데스크톱·이주·보안으로 영역을 넓혀 앞서 나가려 한다.
런타임들은 더 많은 것을 내장하는 경쟁에 있고,
Deno의 2.9는 그 경쟁에서 새 영역(데스크톱)을 선점하려는 수다.
HN에서 phaser가 도시 건설 게임 Microlandia를 Deno 사이드카로 돌린다고 한
것은,[^phaser]
Deno가 이미 게임 로직 같은 예상 밖 영역에 쓰이고 있음을 보여 준다.

성능 개선이 이 확장을 뒷받침한다.
기동 시간이 절반으로 줄고 메모리가 2배 이상 준 것은,
Deno를 더 가벼운 곳,
곧 서버리스나 데스크톱 바이너리에 쓸 수 있게 한다.
rendering-one-million-pdfs와 floci에서 본,
네이티브 바이너리의 가벼움이 배포 가능성을 넓히듯,
Deno의 성능 개선은 그것을 더 많은 환경에 넣을 수 있게 한다.

### npm 락파일 직접 읽기는 이주 마찰을 없애는 전략이다

Deno 2.9가 npm·pnpm·yarn·Bun의 락파일을 직접 읽는 것은
경쟁 생태계에서의 이주를 겨냥한 전략이다.
기존 프로젝트를 Deno로 옮길 때 가장 큰 마찰은
의존성 재설정이었다.
락파일을 그대로 읽어 정확한 버전으로 시드하면,
그 마찰이 사라진다.
Node 심으로 `node` 호출을 Deno로 전달하는 것도 같은 의도다.

이 저마찰 전략이 중요한 이유는 런타임 전환의 진짜 장벽이 이주이기 때문이다.
Deno가 아무리 우아해도,
기존 npm 프로젝트를 옮기는 비용이 크면 아무도 옮기지 않는다.
switchyard가 OpenAI API 호환으로 채택 마찰을 없앴듯,
Deno는 npm 락파일 호환으로 이주 마찰을 없앤다.
경쟁 런타임의 자산(락파일, node 호출)을 그대로 받아들여,
사용자가 점진적으로 넘어오게 한다.

그러나 이 전략에는 긴장이 있다.
Deno의 원래 매력은 npm과 Node의 유산에서 벗어난 깨끗한 설계였다.
그런데 npm 락파일을 읽고 Node 26 호환을 강화할수록,
Deno는 자기가 거부했던 npm 생태계를 더 깊이 껴안는다.
sanori가 modern-nodejs-2025에서 Deno가 연 길을 Node가 따라온다고 했는데,
이제 Deno가 Node·npm 쪽으로 다가가는 역방향도 함께 일어난다.
두 런타임이 서로를 향해 수렴하고 있다.

## 비평

### deno desktop의 바이너리 크기가 약속과 어긋난다

`deno desktop`은 Electron·Tauri 없이 가벼운 데스크톱 앱을 약속하지만,
실제 결과는 그 약속과 어긋날 수 있다.
GN에 재수록된 한 사용자의 시험에서,
5줄짜리 Hello World를 `deno desktop`으로 빌드하니
Windows 10에서 442MB가 나왔다.
Electron 빌드보다 작을 줄 알았는데 훨씬 커서 놀랐다는 것이다.

이 간극이 중요한 이유는 핵심 가치 제안을 위협하기 때문이다.
`deno desktop`의 매력은 Electron의 무거움에 대한 대안이라는 것이다.
그런데 가장 단순한 앱조차 442MB라면,
그 무거움에서 벗어났다는 약속이 무색해진다.
webview 백엔드가 OS 내장 엔진을 쓴다지만,
Deno 런타임 자체와 프레임워크 산출물이 더해지면
바이너리가 커진다.
가벼움을 내세운 기능이 실제로는 가볍지 않을 수 있다.

이것은 ios-wallet-library-card와 modern-nodejs-2025에서 본,
테스트 없이 공유된 방법이나 낙관적 서술의 문제와 이어진다.
릴리스 글은 단일 배포 바이너리라는 편의를 강조하지만,
그 바이너리의 실제 크기라는 대가는 언급하지 않는다.
데스크톱 앱 배포에서 크기는 사용자 다운로드 경험에 직결되므로,
442MB라는 실측치는 이 기능의 실용성을 다시 보게 한다.

### Node 호환성의 안정성이 여전히 발목을 잡는다

Deno가 Node 26 호환을 내세우지만,
그 호환성의 안정성에 대한 실무자의 불신은 여전하다.
HN에서 Tiberium은 과거 Deno가 멋졌고 자신도 홍보했지만,
요즘은 안정성과 테스트,
특히 Node 호환성에 대한 미흡한 접근에 실망했다며
최근 여러 문제에 부딪혔다고 했다.[^Tiberium]
새 버전마다 호환 범위를 넓히지만, 그 깊이가 따라오지 못한다는 것이다.

이 불신이 중요한 이유는 이주 전략의 전제를 위협하기 때문이다.
Deno의 npm 락파일 읽기와 Node 심은
Node 생태계에서 넘어오게 하려는 것인데,
막상 넘어온 뒤 Node 호환성이 불안정하면
그 이주는 실망으로 끝난다.
kumo·floci·ministack에서 본, 폭이 깊이를 보장하지 않는 문제가
Deno의 Node 호환성에도 적용된다.
Node 26 호환이라는 선언과
실제 npm 패키지가 문제없이 도는 것은 다른 문제다.

lackoftactics가 지금으로선 Bun을 이기기 어렵고
Bun의 라이브 리로드가 대단하다고 한 것도[^lackoftactics]
이 경쟁의 현실을 드러낸다.
Deno가 데스크톱·보안·이주로 영역을 넓히는 동안,
Bun은 Node 호환성과 개발자 경험에서 앞서 나간다.
Deno의 넓은 야심이 오히려 각 영역의 완성도를 분산시킬 수 있다는 우려가,
안정성에 대한 실무자의 불신으로 나타난다.

### VC 투자가 오픈소스 런타임의 방향을 왜곡한다는 비판

Deno에 대한 더 근본적인 비판은 그 사업 구조를 겨냥한다.
HN에서 shimman은 Deno가
VC 투자를 받는 것이 오픈소스 프로젝트의 존립을 어떻게 해치는지 보여 주는
사례라고 했다.
극도로 작고 분열된 커뮤니티를 위해
돈이 되는 프로젝트에 계속 집중한다는 것이다.[^shimman]

이 비판이 중요한 이유는 기능 선택의 동기를 묻기 때문이다.
`deno desktop` 같은 화려한 기능이
커뮤니티의 진짜 필요에서 나온 것인지,
아니면 VC에 성장을 보여 주기 위한 것인지가 불분명하다.
palantir-fde에서 본, 야심이 규율을 강제한다는 관점과 반대로,
shimman은 VC 자본이 야심을 왜곡한다고 본다.
투자자를 만족시키려는 성장 압력이,
작은 커뮤니티의 안정성 요구보다
눈에 띄는 새 기능을 우선하게 만든다는 것이다.

mmastrac의 관찰이 이 긴장을 다른 각도에서 조명한다.
AI 시대에 풍부한 AI 접근이 회사의 특성을 증폭하는데,
Deno는 늘 표준에 방법론적이고 집중적,
어쩌면 지나치게 집중적이었다는 것이다.[^mmastrac]
표준에 대한 집착이 Deno의 강점이자,
때로는 실무적 안정성보다 이상을 앞세우는 약점이 된다.
2.9의 후양자 암호화 같은 선도적 기능은 이 표준 집착의 산물이며,
그것이 커뮤니티의 당면 필요와 얼마나 맞는지는 별개의 문제다.

## 인사이트

### 런타임 경쟁이 서로를 향한 수렴으로 귀결된다

Deno 2.9가 드러내는 가장 이전 가능한 통찰은
경쟁하는 JavaScript 런타임들이
서로를 향해 수렴하고 있다는 점이다.
Deno는 npm 락파일을 읽고 Node 26 호환을 강화하며 Node에 다가가고,
Node는 modern-nodejs-2025에서 본 대로
fetch·테스트·감시를 내장하며 Deno에 다가간다.
경쟁이 차별화가 아니라 수렴을 낳는다.

이 수렴이 중요한 이유는 경쟁의 역설을 드러내기 때문이다.
Deno는 Node의 유산을 거부하며 시작했지만,
사용자를 얻으려면 그 유산과 호환되어야 한다.
Node는 Deno의 현대성을 따라잡아야 경쟁력을 유지한다.
그 결과 둘은 각자의 출발점에서 멀어져 중간으로 모인다.
sanori의 관찰, 곧 Deno가 연 길을 Node가 따라온다는 것은
이제 양방향이 되었다.
차별화하려는 경쟁이 오히려 둘을 닮게 만든다.

두 번째 차수의 효과는 이것이 사용자의 선택 기준을 바꾼다는 점이다.
런타임들이 기능에서 수렴하면,
남는 차이는 안정성, 성능, 생태계, 사업 구조다.
Tiberium이 안정성을, lackoftactics가 Bun의 경험을,
shimman이 사업 구조를 들어 Deno를 평가한 것은
이 이동을 보여 준다.
기능이 비슷해지면 경쟁은 신뢰와 성숙도로 옮겨 가며,
그것은 새 기능보다 쌓기 어렵다.

### 표준 선도가 커뮤니티 필요와 어긋날 수 있다

Deno가 후양자 암호화와 웹 표준을 앞서 채택하는 것은
표준 선도라는 정체성의 표현이지만,
그것이 커뮤니티의 당면 필요와 어긋날 수 있다는 통찰을 준다.
ML-KEM·ML-DSA 같은 후양자 알고리즘은 미래를 대비하지만,
지금 Node 호환성 버그에 시달리는 사용자에게는
더 시급한 것이 안정성이다.
mmastrac가 지나치게 집중적이라고 한 것이 이 지점이다.

이 통찰이 새로운 프레임을 주는 이유는
오픈소스의 우선순위 배분 문제를 드러내기 때문이다.
표준을 선도하는 것은 프로젝트의 명성과 방향성을 주지만,
사용자의 일상적 불편을 해결하지 않으면 채택을 잃는다.
behavior-specs와 opentelemetry에서 본,
명세와 실무의 간극이 여기서도 나타난다.
표준의 우아함과 실무의 안정성 사이에서,
Deno는 전자에 기운다는 비판을 받는다.

세 번째 차수의 함의는 이것이 VC 자본의 영향과 얽힌다는 점이다.
shimman의 지적대로 VC 투자가 성장을 요구하면,
프로젝트는 눈에 띄는 선도적 기능에 집중하게 된다.
후양자 암호화나 `deno desktop`은 투자자에게 보여 줄 성장 서사이지만,
Node 호환성 버그 수정은 그렇지 않다.
자본의 성장 압력이 화려한 선도와 지루한 안정성 사이에서
전자를 택하게 만든다면,
표준 선도라는 정체성이 사업 구조에 의해 강화되는 것이다.

### 데스크톱 런타임 통합의 반복되는 실패 패턴

`deno desktop`이 442MB의 Hello World를 낳은 것은
웹 기술로 데스크톱 앱을 만드는 시도의 반복되는 실패 패턴을 드러낸다.
Electron이 무겁다는 비판에서 Tauri가 나왔고,
Tauri의 복잡함에서 `deno desktop`이 나왔지만,
각 대안이 약속한 가벼움은 실제로는 부분적으로만 달성된다.
웹 기술과 네이티브의 통합에는 지울 수 없는 무게가 있다.

이 통찰이 중요한 이유는 추상화의 대가를 드러내기 때문이다.
웹 기술로 데스크톱 앱을 만드는 것은
웹 개발자가 네이티브 툴킷을 배우지 않아도 되게 한다.
그 편의의 대가가 런타임과 웹뷰 엔진의 무게다.
GN에 재수록된 지적대로, 그냥 네이티브 툴킷을 쓰고
각 플랫폼의 차이를 받아들이면 가볍지만,
그러려면 훨씬 많은 리소스가 들고 지원 플랫폼이 줄어든다.
편의와 무게, 이식성과 네이티브성은 맞바꿀 수밖에 없다.

이 통찰의 함의는 데스크톱 앱 개발에 은탄환이 없다는 것이다.
Electron, Tauri, `deno desktop`이 차례로 등장하며
각자 이전의 문제를 푼다고 주장하지만,
웹-네이티브 통합의 근본 트레이드오프는 남는다.
systemd-boot-kexec-kernel에서 본,
폴리글롯이 우아하되 취약하듯,
웹 기술로 네이티브를 겸하려는 시도는 편리하되 무겁다.
`deno desktop`은 이 오래된 문제의 새 시도이지,
그 문제를 해소한 해법이 아니다.
