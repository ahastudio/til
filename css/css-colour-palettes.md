# CSS 컬러 팔레트 링크 모음

원문: [Links to CSS colour palettes](https://jvns.ca/blog/2026/05/04/css-colour-palettes/)

HN 토론: <https://news.ycombinator.com/item?id=48014920> (3점, 1개 댓글)

## 요약

Julia Evans는 새 프로젝트에서 Tailwind를 쓰지 않고 바닐라 CSS로 돌아갔는데,
그 과정에서 유일하게 아쉬웠던 것이 Tailwind의 컬러 팔레트였다고 적는다.
연한 파랑이 필요하면 `blue-100`을 쓰고 마음에 안 들면 `blue-200`이나 `blue-50`으로 옮기면 되는 방식이며,
색에 자신이 없는 사람에게는 색을 잘 아는 누군가가 미리 생각해 둔 단계표가 있다는 것 자체가 큰 차이를 만든다고 말한다.

동시에 Tailwind 색에 조금 질리기도 해서 Mastodon에 다른 팔레트를 물었고,
친구가 그 링크들을 달라고 해서 글로 정리했다는 것이 이 글의 전부다.
주장하는 글이 아니라 링크 모음이며, 분류는 네 덩어리다.

본인이 가장 좋았다고 꼽은 것은 uchū, flexoki, 그리고 접근성에 초점을 둔 reasonable colours 셋이다.
그 외 팔레트로 web awesome, radix, US web design systems, material design을 나열하고,
생성기로 harmonizer, tints.dev, coolors, colorpalette.pro를 든다.
다만 생성기류는 본인이 늘 쓰기 어려웠다고 솔직하게 적으면서,
언젠가 색을 더 잘 알게 되면 쓸 수 있을지도 모르니 링크는 남겨 둔다고 덧붙인다.

마지막으로 색맹 관련 정보를 제공하는 colorhexa와,
`oklch()` 함수로 색을 동적으로 만들어 내는 방법을 보여 주는 글을 덧붙인다.

## 링크별로 실제 무엇인가

글 자체는 이름과 링크만 나열하므로, 각 팔레트가 어떤 문제를 풀려고 만들어졌는지를 확인해 두면 고르기가 쉬워진다.

| 팔레트             | 성격                                                                       |
| ------------------ | -------------------------------------------------------------------------- |
| uchū               | oklch 값으로 정의된 색 9단계 구성, 기본 팔레트와 파스텔 팔레트를 함께 제공 |
| flexoki            | 종이와 잉크를 본뜬 고대비 색 구성, 글과 코드를 읽고 쓰는 화면에 맞춤       |
| reasonable colours | 단계 번호 차이로 대비율이 보장되는 접근성 중심 체계                        |
| radix              | 12단계를 용도별로 배정한 UI 전용 체계                                      |
| USWDS              | 미국 정부 디자인 시스템의 색 토큰                                          |
| material design    | 구글 머티리얼의 색 체계                                                    |

uchū는 모든 색을 `oklch()` 값으로 적어 두었다는 점이 특징이다.
예컨대 파랑 5단계는 `oklch(0.5487 0.222 260.33)`이고 초록 5단계는 `oklch(0.7523 0.209 144.64)`인데,
첫 값인 밝기가 색상별로 다르다는 사실이 그대로 드러난다.
색을 hex로만 보면 모르는 정보를 팔레트 파일 자체가 노출한다.

flexoki는 Steph Ango가 자기 사이트를 위해 만든 것으로, MIT 라이선스로 공개되어 있다.
플렉소그래피라는 인쇄 방식에서 이름을 따왔고,
발광하는 화면 위에서 종이 위 잉크의 감각을 내려는 목표를 분명히 밝힌다.
배경과 UI와 글자를 `bg`, `ui`, `tx` 같은 접두어로 나눠 두었기 때문에 역할이 이름에 드러난다는 점이 실무적으로 유용하다.

radix는 12단계 각각에 역할을 하나씩 지정하는 대신 구간별 용도를 명시한다.
배경, 상호작용하는 컴포넌트, 테두리와 구분선, 솔리드 색, 읽을 수 있는 텍스트 순으로 번호가 올라간다.
즉 숫자가 밝기만 뜻하는 Tailwind 방식과 달리, 숫자가 곧 용도다.

## reasonable colours가 실제로 보장하는 것

이 팔레트가 다른 것들과 다른 지점은 규칙이 검증 가능한 형태로 서술되어 있다는 점이다.
각 색은 6단계이고, 두 단계 사이의 대비는 단계 번호의 차이만으로 추론된다.

| 단계 차이 | 보장 대비율 | 충족하는 기준                      |
| --------- | ----------- | ---------------------------------- |
| 2         | 3:1 이상    | WCAG 2 AA 큰 글자, 아이콘과 그래픽 |
| 3         | 4.5:1 이상  | WCAG 2 AA 본문, WCAG 2 AAA 큰 글자 |
| 4         | 7:1 이상    | WCAG 2 AAA 본문                    |

여기서 결정적인 부분은 이 규칙이 같은 색 안에서만이 아니라 24개 색 전체에 걸쳐 성립한다는 점이다.
LCH 색 공간 위에서 각 단계의 상대 휘도를 일정 범위에 고정했기 때문에,
파랑 2단계 위에 회색 5단계를 얹어도 4.5:1이 보장된다.
순백은 모든 1단계보다 밝고 순흑은 모든 6단계보다 어두우므로,
`#FFFFFF`를 1단계로, `#000000`을 6단계로 취급해도 규칙이 그대로 적용된다.

24개 색상은 LCH 색상환에서 15도 간격으로 균등 배치되어 있어 보색이나 인접색을 각도로 계산할 수 있다.

## 고르는 기준

색을 잘 모르는 상태에서 팔레트를 고를 때 실제로 물어야 할 질문은 “어느 것이 예쁜가”가 아니다.
그 팔레트가 나 대신 무엇을 결정해 주는가다.

| 내 상황                                | 맞는 선택                     |
| -------------------------------------- | ----------------------------- |
| 대비를 매번 검사기에 넣기 싫다         | reasonable colours            |
| 어떤 단계를 어디에 쓸지 모르겠다       | radix                         |
| 글 읽는 화면이고 다크 모드를 같이 낸다 | flexoki                       |
| 색을 코드에서 계산해 만들고 싶다       | uchū 또는 `oklch()` 직접 사용 |
| 조직 전체가 따를 근거가 필요하다       | USWDS 또는 material design    |

Tailwind 팔레트에서 옮겨 올 때 가장 크게 걸리는 것은 단계 번호의 의미가 다르다는 점이다.
Tailwind의 `50`부터 `950`까지는 밝기 축이고,
radix의 1부터 12까지는 용도 축이며, reasonable colours의 1부터 6까지는 대비 축이다.
`blue-100`을 기계적으로 다른 팔레트의 비슷한 번호로 바꾸면 의미가 어긋난다.

## 트레이드오프

### 팔레트를 쓴다는 것은 결정을 포기하는 대가로 일관성을 사는 일이다

미리 정의된 단계표는 색을 고르는 시간을 없애 준다.
그러나 동시에 그 팔레트가 상정하지 않은 색은 만들 수 없게 된다.
Julia Evans가 Tailwind 색에 질렸다고 말한 것이 바로 이 지점이며,
Tailwind로 만든 사이트들이 서로 닮아 보이는 이유이기도 하다.

여기서 흔히 나오는 해법인 “팔레트를 조금만 커스터마이즈한다”는 생각보다 잘 듣지 않는다.
한 색만 바꿔도 그 색이 다른 단계와 맺고 있던 휘도 관계가 깨지기 때문에,
대비 보장이 걸려 있는 팔레트라면 보장 자체가 무효가 된다.
결국 팔레트를 그대로 쓰거나, 규칙까지 이해하고 팔레트를 다시 만들거나 둘 중 하나다.

### 접근성 보장과 색의 자유도는 같이 얻기 어렵다

reasonable colours가 대비를 보장할 수 있는 이유는 각 단계의 휘도를 고정했기 때문이고,
휘도를 고정한다는 것은 원하는 색을 원하는 밝기로 쓸 수 없다는 뜻이다.
아주 진한 노랑이나 아주 밝은 남색처럼 휘도 범위를 벗어나는 색은 애초에 팔레트에 없다.

반대로 flexoki처럼 심미적 목표가 먼저인 팔레트는 색이 훨씬 매력적이지만,
어떤 조합이 본문 대비를 충족하는지는 직접 확인해야 한다.
이 둘을 한 팔레트가 동시에 주지 못한다는 사실이,
팔레트가 여럿 존재하는 이유이자 하나를 고를 때 무엇을 포기할지 먼저 정해야 하는 이유다.

### 생성기는 팔레트가 아니라 팔레트 만들기를 판다

harmonizer, tints.dev, coolors 같은 도구는 색 하나를 넣으면 단계를 뽑아 준다.
Julia Evans가 이런 도구를 쓰기 어려웠다고 말한 이유는 도구가 나쁘기 때문이 아니라,
입력해야 할 기준색을 고르는 것이 정확히 그가 못한다고 말한 그 일이기 때문이다.
생성기는 색을 아는 사람의 작업 속도를 올려 주는 물건이지, 색을 모르는 사람의 대체재가 아니다.

## 비평

### 링크 모음이 좋은 글이 될 수 있는 조건

이 글은 각 팔레트를 비교하지도, 언제 무엇을 쓰라고 말하지도 않는다.
친구가 링크를 달라고 해서 썼다는 동기를 그대로 밝히는 짧은 글이고, 그 이상을 표방하지 않는다.
그 솔직함은 미덕이지만, 읽는 쪽에서는 목록을 받은 뒤에 할 일이 그대로 남는다.

흥미로운 것은 이 글의 가치가 선별에 있다는 점이다.
저자는 여러 링크 중 셋을 좋아하는 것으로 따로 묶었고,
생성기 묶음에는 자기가 잘 못 쓴다는 단서를 달았다.
이 두 가지 표시가 없었다면 이 글은 검색으로 대체 가능한 목록이 된다.
링크 모음이 읽을 가치를 갖는 지점은 링크의 개수가 아니라 저자가 어디에 표시를 남겼는가에 있다.

### 색을 잘 모른다는 전제가 결론을 좁힌다

저자는 자신이 색을 잘 다루지 못한다는 전제를 여러 번 밝히고, 그 전제 위에서 팔레트를 고른다.
이 정직한 자기 규정은 글을 읽기 편하게 만들지만 동시에 판단 기준을 한 방향으로 고정한다.
좋은 팔레트란 내가 결정하지 않아도 되게 해 주는 팔레트라는 기준이다.

그러나 실제 작업에서는 반대 방향의 필요도 자주 생긴다.
브랜드 색이 이미 정해져 있어서 그 색을 중심으로 단계를 만들어야 하는 경우가 그렇고,
이때는 완성된 팔레트보다 생성기 쪽이 정답에 가깝다.
글이 생성기를 사실상 각주로 밀어낸 것은 저자 개인에게는 타당하지만,
독자 전체에게 적용하면 절반의 상황을 놓치는 분류가 된다.

### 다크 모드가 분류에서 빠져 있다

나열된 팔레트들이 다크 모드를 다루는 방식은 제각각이다.
flexoki는 밝고 어두운 모드 사이를 오갈 때의 지각적 균형을 명시적인 설계 목표로 삼고,
radix는 각 색에 대응하는 어두운 단계 집합을 따로 제공한다.
반면 밝은 화면만 가정하고 만든 팔레트를 다크 모드에 쓰려면 단계를 뒤집어야 하는데,
단순히 뒤집으면 채도가 과해져서 어두운 배경 위에서 눈을 찌른다.

다크 모드를 같이 낼 계획이 있다면 이것이 첫 번째 선별 기준이 되어야 하지만,
글의 네 묶음 어디에도 이 축은 없다.
링크를 받아 든 독자가 가장 먼저 마주칠 실무 문제가 분류에서 빠져 있는 셈이다.

## 함정

세 가지가 실제로 자주 문제가 된다.

첫째, 단계 번호를 팔레트 사이에서 그대로 옮기는 것이다.
앞서 적었듯 Tailwind의 번호는 밝기, radix의 번호는 용도, reasonable colours의 번호는 대비 기준이다.
번호가 같아도 같은 것을 뜻하지 않는다.

둘째, 대비가 보장된 팔레트를 쓰면 접근성이 끝났다고 여기는 것이다.
보장되는 것은 색 대비뿐이고,
색만으로 상태를 구분하는 UI나 포커스 표시의 부재는 팔레트가 해결해 주지 않는다.

셋째, hex로 색을 직접 섞는 것이다.
`oklch()`는 밝기와 채도와 색상이 분리되어 있어서 밝기만 바꾸는 조작이 가능하지만,
hex 값을 눈대중으로 조정하면 밝기를 바꾸려다 채도까지 함께 움직인다.
동적으로 색을 만들 계획이라면 팔레트가 어떤 색 공간으로 정의되어 있는지를 먼저 확인해야 한다.

## 확인하기

팔레트를 실제로 정하기 전에 다음을 한 번 돌려 보면 선택이 빨라진다.

```css
/* oklch에서 밝기만 바꿔 보기: 뒤의 두 값(채도, 색상)은 그대로 둔다 */
:root {
  --brand-light: oklch(0.85 0.09 260);
  --brand-base:  oklch(0.55 0.22 260); /* 채도만 올린 기준색 */
  --brand-dark:  oklch(0.40 0.15 260);
}

.sample {
  background: var(--brand-light);
  color: var(--brand-dark);
}
```

세 값을 각각 화면에 띄워 놓고 밝기 값만 0.05씩 움직여 보면,
단계표가 왜 필요한지와 어느 구간에서 색이 무너지는지가 직접 보인다.
그다음 같은 조합을 브라우저 개발자 도구의 대비 검사로 확인하면
직접 만든 단계와 기성 팔레트의 차이가 수치로 드러난다.

## 체크리스트

- 이 프로젝트에서 팔레트가 대신 결정해 주기를 바라는 것이 대비인가, 용도 배정인가, 심미인가?
- 다크 모드를 낼 계획이 있고, 고른 팔레트가 그에 대응하는 단계를 제공하는가?
- 브랜드 색이 이미 고정되어 있는가? 그렇다면 완성 팔레트가 아니라 생성기가 맞다.
- 팔레트의 색이 hex인가 `oklch()` 같은 지각 기반 공간인가? 색을 코드에서 계산할 계획이라면 후자여야 한다.
- 단계 번호의 의미를 팀이 같은 방식으로 이해하고 있는가?
- 색 대비 외의 접근성 항목을 팔레트와 별개로 확인했는가?

## 기억할 원칙

### 팔레트는 색 모음이 아니라 규칙 모음이다

좋은 팔레트가 주는 것은 예쁜 색 스무 개가 아니라,
어떤 색을 언제 쓸지에 대한 판정 기준이다.
reasonable colours의 가치는 색 자체가 아니라 번호 차이로 대비를 추론할 수 있다는 규칙에 있고,
radix의 가치는 번호가 곧 용도라는 약속에 있다.
팔레트를 평가할 때 스와치를 보지 말고 규칙이 무엇인지를 먼저 찾아야 하는 이유다.

규칙이 없는 팔레트는 색을 고르는 일을 없애 주지 않는다.
단지 고를 후보의 수를 줄여 줄 뿐이며, 그것도 나쁘지 않지만 같은 것은 아니다.

### 자신이 못하는 일을 아는 것이 도구 선택의 출발점이다

이 글이 링크 모음 이상으로 읽히는 이유는 저자가 자기가 색을 잘 모른다는 사실을 먼저 적었기 때문이다.
그 전제가 있으니 왜 완성된 단계표를 선호하고 왜 생성기를 미뤄 뒀는지가 설명된다.
도구를 고를 때 “무엇이 가장 좋은가”보다 “나는 무엇을 못하는가”를 먼저 정하면
후보 목록이 훨씬 빨리 줄어든다.

같은 저자의 후속 글인 Tailwind에서 벗어나 CSS를 직접 구조화하는 이야기는
이 저장소의 `css/moving-away-from-tailwind.md`에 정리되어 있고,
팔레트 선택은 그 전환에서 남은 마지막 조각에 해당한다.
