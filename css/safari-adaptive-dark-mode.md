# Safari의 Adaptive Dark Mode: 다크 모드가 없는 사이트를 브라우저가 어둡게 바꾼다

원문: [Introducing Adaptive Dark Mode | WebKit](https://webkit.org/blog/18541/introducing-adaptive-dark-mode/)

HN 토론: <https://news.ycombinator.com/item?id=50358562> (411점, 219개 댓글)

GN 토론: <https://news.hada.io/topic?id=36549>

## 소개

2026년 11월 3일에 WebKit 블로그가 Safari 27.3 베타의 새 기능
Adaptive Dark Mode를 소개했다.
사용자가 켜면 Safari가 밝은 웹사이트를 분석해 어두운 모습으로 바꿔 보여 준다.
글쓴이는 Simon Fraser, Luming Yin, Lily Spiniolas, Joanne Pan, Veda Periwal,
Jen Simmons이다.

WebKit 팀이 밝힌 동기는 이렇다.
Safari 12.1이 2019년 봄에 웹에서 다크 모드를 처음 지원한 뒤로 이를 좋아하는
사용자가 많은데, 다크 모드 버전이 없는 사이트가 여전히 많다는 것이다.
글은 chromestatus 지표를 들어 페이지 로드의 거의 40%가 다크 모드 사용자에게서
나오지만 다크 모드를 지원하는 페이지 로드는 10%뿐이라고 쓴다.
Adaptive Dark Mode는 이 간격을 줄여 웹 전체에서 일관된 다크 경험을 주려는 기능이다.

켜는 방법은 시스템 모양(appearance)을 다크로 두고 밝은 배경의 사이트에 들어가는
것이다.
그러면 Safari가 미리 보기를 제안하고, 사용자가 Try를 누른다.

이 기능이 약속하는 것과 약속하지 않는 것의 경계는 다음과 같다.

- 사이트가 `color-scheme: light dark`로 다크 모드 지원을 선언했다면 아무것도
  바꾸지 않는다.
- 선언이 없으면 색을 분석해 페이지가 대체로 밝은지 어두운지 추정하고,
  밝은 페이지만 어둡게 바꾼다.
- 이미 어두운 배경에 밝은 글자인 페이지는 그대로 둔다.
- 모든 사이트에서 완벽한 결과를 낸다고 약속하지는 않는다.
  글은 사이트가 현대적인 웹 개발 관행을 따르면 잘 동작한다고만 적고,
  오래된 기법을 쓰는 사이트에는 작은 수정이 도움이 된다고 한다.

## 동작 방식

핵심은 색 변환이다.
색이 장식일 때도 있고 의미를 가질 때도 있으므로,
Adaptive Dark Mode는 요소가 계속 보이도록 색을 뒤집을 때와 그대로 둘 때를 가른다.
WebKit 팀은 색의 휘도(luminosity)를 뒤집되 색조(hue)는 보존하는 색 행렬을
만들었다고 한다.
이 행렬로 밝은 배경은 어둡게, 어두운 글자는 밝게 바뀐다.
글자색을 바꿀 때는 WCAG가 정한 4.5:1 대비를 목표로 하고,
밝은 CSS 그라디언트도 어둡게 바꾼다.

요소 종류별 처리는 다음과 같다.

| 대상                            | 처리                                                               |
| ------------------------------- | ------------------------------------------------------------------ |
| 배경과 글자색                   | 휘도를 뒤집고 색조는 유지, 글자는 4.5:1 대비를 목표로 함           |
| CSS 그라디언트                  | 밝은 것은 어둡게 변환                                              |
| SVG 이미지                      | 내용을 검사해 필요할 때 색을 변환                                  |
| 비트맵 이미지                   | 대부분 그대로 둠, 픽셀 히스토그램을 분석해 단순한 흑백 로고만 반전 |
| `mask`, `mix-blend-mode`        | 색이 바뀐 요소에서 이상한 결과가 나올 수 있어 일부 경우 효과를 끔  |
| `<canvas>`                      | 내용을 예측하기 어려워 그대로 둠                                   |
| 버튼, 호버 메뉴, 이미지 위 글자 | 배경 대비 가독성을 유지하도록 판단                                 |

이 변환이 WebKit 엔진 안쪽에서 일어나기 때문에 속도와 전력 효율을 얻고
사용자 개인정보도 지킬 수 있다고 글은 설명한다.

개인정보 면에서는 사이트가 변환 여부를 알 수 없게 막았다.
사이트가 Adaptive Dark Mode가 켜졌는지 알아낼 수 있다면 핑거프린팅(fingerprinting)에
쓸 정보가 늘기 때문이다.
그래서 CSS 색을 조회하는 JavaScript는 변환된 색이 아니라 작성된 원래 색을 받고,
canvas에 그려 넣은 이미지도 원래 모습으로 그려진다.

## 사이트 운영자가 할 일

글이 권하는 일은 세 단계로 나눌 수 있다.
첫째, 현대적인 방식으로 만든 페이지는 그대로 둔다.
둘째, 오래된 기법이 있다면 작게 고친다.
셋째, 더 통제하고 싶다면 직접 다크 모드를 만든다.

### 오래된 기법을 고친다

글이 나열한 수정 항목은 다음과 같다.

- 로고와 아이콘은 비트맵 대신 SVG를 쓴다.
- 타일처럼 반복하는 배경 이미지 대신 CSS의 단색이나 그라디언트를 쓴다.
- 이미지 스프라이트 대신 모서리, 그림자, 버튼 상태를 CSS로 만든다.
- 콘텐츠 이미지는 페이지 배경색을 이미지에 굽지 말고 투명 배경으로 만든다.
- 컨테이너에 패딩을 넣어 내용이 빽빽해지지 않게 한다.

### 일부 영역만 다크로 만든다

페이지의 특정 부분에서만 직접 만든 다크 경험을 원하면
해당 요소에 `color-scheme: light dark`를 적용하고 다크 스타일을 추가한다.

### 직접 다크 모드를 만든다

글은 지금이 완전한 지원을 추가하기 좋은 때이고 그 어느 때보다 쉽다고 쓴다.
필요한 웹 기술로 다음을 든다.

- `<meta name="color-scheme" content="light dark">`
- `:root { color-scheme: light dark }`
- `@media (prefers-color-scheme: dark) { }`
- `<picture><source media="(prefers-color-scheme: dark)">`
- `light-dark()`
- 더 새로운 `color-mix()`와 `contrast-color()`

선언은 HTML의 `<head>`에 있는 `color-scheme` 메타 태그나
CSS의 `:root`나 `body`의 `color-scheme` 속성으로 해야 하고,
나중에 JavaScript로 넣지 말라고 한다.
그래야 사이트가 가능한 한 빨리 올바르게 그려진다는 이유다.

아래 예시는 원문의 코드가 아니라 위 목록을 이 문서가 조합해 본 것이다.

```html
<meta name="color-scheme" content="light dark">
```

```css
:root {
  color-scheme: light dark;
}

body {
  /* 라이트일 때 앞 값, 다크일 때 뒤 값이 쓰인다 */
  background: light-dark(#ffffff, #121212);
  color: light-dark(#1a1a1a, #eaeaea);
}
```

### 변환을 원하지 않으면

변환을 피하고 싶다면 `color-scheme`으로 알린다.
HTML의 `<meta name="color-scheme" content="light only">`는
이 페이지가 라이트 모드를 지원하고 라이트 모드로만 보여야 한다고 알린다.
CSS의 `color-scheme: light only`도 같은 일을 하며,
`:root { }`로 전체 페이지를 가리킬 수도 있고 특정 요소만 가리킬 수도 있다.
다만 `only` 키워드는 Safari 27.3 베타 1에서 지원되지 않는다.
글은 베타 과정에서 기능이 바뀔 수 있으니 다시 확인하라고 한다.

```css
/* 베타 1에서는 only가 아직 지원되지 않는다 */
:root {
  color-scheme: light only;
}
```

## 비평

### 40%와 10%라는 두 숫자는 격차의 크기를 직접 보여 주지 않는다

글은 페이지 로드의 거의 40%가 다크 모드 사용자에게서 나오고
다크 모드를 지원하는 페이지 로드는 10%뿐이라고 두 지표를 나란히 놓는다.
이 문서는 글이 링크한 chromestatus 페이지를 열어 보지 않았으므로 두 지표의 정의는
확인하지 못했다.
글 안에서만 보면 두 숫자는 서로 다른 집합의 비율이다.
다크 모드 사용자의 페이지 로드 중 얼마가 지원하지 않는 사이트로 가는지는
두 숫자를 빼서 알 수 있는 값이 아니다.
그래서 이 숫자는 문제가 있다는 방향을 말할 뿐 이 기능이 해결하는 몫을
말해 주지 않는다.

### 품질에 대한 서술은 측정 없이 판단이라는 말에 기댄다

글은 버튼에 대비를 주고, 이미지 위 글자를 보이게 하고,
호버 메뉴를 분명하게 한다고 적는다.
그러나 변환 결과가 어느 정도 사이트에서 쓸 만한지, 실패하는 유형이 무엇인지를
숫자나 사례로 보이지 않는다.
이 글은 베타 1을 소개하는 글이므로 그 자체가 결함은 아니다.
다만 이 서술만으로 자기 사이트가 괜찮을지 판단할 수는 없고,
직접 켜 보는 것 외에는 확인 방법이 없다.
Hacker News의 internet2000은 베타에서 Hacker News에 이 기능을 써 보니 잘 동작했다고 적었다.[^internet2000]
한 사이트에 대한 한 번의 경험이어서 위 판단을 바꾸지는 않는다.

### 거부 수단이 지금은 완성되어 있지 않다

변환을 원하지 않는 사이트가 쓸 수단은 `light only`인데,
`only`가 베타 1에서 지원되지 않는다고 글이 스스로 적는다.
변환 결과가 브랜드 색이나 데이터 시각화를 망가뜨리는 사이트가 지금 할 수 있는 일은
`color-scheme: light dark`를 선언하고 직접 다크 스타일을 만드는 것뿐이다.
이 경우 거부가 아니라 다크 모드 지원을 직접 구현하는 일이 되므로,
거부의 비용이 사이트 쪽에 있다.

### 변환 여부를 감추는 설계는 사이트가 문제를 알 길을 줄인다

개인정보 논거는 설득력이 있다.
변환 여부가 노출되면 핑거프린팅에 쓸 정보가 늘기 때문이다.
그러나 이 설계의 다른 면도 있다.
사이트 운영자는 사용자가 어떤 모습으로 자기 사이트를 보는지 코드로 알 수 없고,
JavaScript가 읽는 색은 화면에 보이는 색과 다르다.
글이 제시한 연락 수단은 이메일 주소 하나와 사용자의 Feedback Assistant 신고다.
문제를 발견하는 일이 사용자의 신고와 운영자의 자발적인 문의에 맡겨져 있다.

Hacker News의 `_boffin_`은 이를 브라우저가 이제 의도적으로 거짓말을 한다고 적었다.[^_boffin_]
kccqzy는 방문한 링크의 색을 사이트가 읽지 못하게 막는 것처럼
브라우저는 개인정보를 위해 오래전부터 사이트에 거짓 값을 준다고 답했다.[^kccqzy]
mortenjorck은 스타일링으로 로직을 처리하는 허술한 프런트엔드가 깨지는 것을 막으려면
어쩔 수 없는 일이라고 봤다.[^mortenjorck]
이를 거짓말로 부를지 방어로 부를지는 관점의 문제다.
다만 사이트가 변환 여부를 코드로 알 수 없다는 비용은 두 관점에서 모두 남는다.

### 변환은 어두운 쪽으로만 일어난다

글이 설명하는 방향은 밝은 사이트를 어둡게 바꾸는 것 하나다.
Hacker News의 nsoam은 난시 때문에 검은 바탕의 흰 글자가 읽기 어렵다며,
Safari가 다크 모드 사이트를 라이트 모드로 바꿔 주면 좋겠다고 적었다.[^nsoam]
hahnchen도 어두워 보이는 사이트를 라이트 모드로 보고 싶을 때는 어떻게 하느냐고 물었다.[^hahnchen]
글은 이 반대 방향을 언급하지 않으므로, 이 기능이 그 요구를 다루는지는 확인되지 않는다.

## 트레이드오프

### 자동 변환과 직접 구현

자동 변환은 사이트를 고치지 않아도 되는 대신 결과를 통제할 수 없다.
직접 구현은 결과를 통제하는 대신 색 체계를 둘로 관리해야 한다.
글은 두 방법의 중간도 제시한다.
요소 단위로 `color-scheme: light dark`를 적용해 그 부분만 직접 다크 스타일을 주는 것이다.

가장 안 풀리는 부분은 페이지 하나에 두 방식이 섞일 때다.
일부는 변환되고 일부는 직접 만든 다크 스타일이 되면
같은 페이지 안에서 색 체계가 둘이 된다.
글은 이 경우에 생길 일관성 문제를 다루지 않는다.

Hacker News에서는 이 선택을 두고 개발자들의 반응이 갈렸다.
guessmyname은 사용자에게는 좋지만 웹 개발자에게는 사이트가 사람마다 다르게 보이게 되는 악몽이라고 적었고,[^guessmyname]
vulcan01은 글이 `light only`라는 거부 수단을 이미 안내했다고 짚었다.[^vulcan01]
drusepth는 사용자가 오래 요구해서 다크 모드를 넣었더니 지원 부담만 커졌고,
다른 브라우저도 비슷한 기능을 내놓으면 직접 만든 다크 모드 지원을 걷어내고 싶다고 적었다.[^drusepth]
같은 사람은 5~10년 동안 다크 모드 문제를 시험하고 고치는 데 100시간 넘게 썼고,
그 결과 UI 품질 확인 시간이 두 배 이상 늘었다고 덧붙였다.[^drusepth-cost]
saagarjha는 조금이라도 공을 들일 생각이 있다면 다크 모드의 모습을 직접 정하고 싶을 것이라고 답했다.[^saagarjha]
vinnymac은 iOS와 Android의 Gmail 다크 모드 구현이 개발자와 사용자를 모두 화나게 한 전례를 들어,
잘 동작하지 않는 경우에 사용자의 불만이 사이트 개발자에게 돌아올 것을 걱정했다.[^vinnymac]
drusepth의 경험은 직접 구현의 비용이 얼마나 클 수 있는지를 보여 주고,
vinnymac의 걱정은 변환 결과가 나빴을 때 책임이 사이트에 돌아올 수 있다는 점을 보여 준다.

### 개인정보와 디버깅

사이트가 변환 여부를 감지하지 못하게 하면 핑거프린팅 위험을 막는 대신,
사이트가 변환 결과에 맞춰 스스로 조정하거나 문제를 보고하게 할 수단이 없어진다.
감지 수단을 주고 이를 개인정보 위험과 맞바꿀 수는 없다는 것이 WebKit의 선택이다.
이 선택을 하면 사이트가 가질 수 없는 것은 “내 사이트가 지금 변환되고 있는가”를
코드로 아는 능력이다.

### 거부의 범위

`light only`가 완성되면 거부는 쉬워지지만,
거부한 사이트는 다크 모드 사용자에게 밝은 페이지를 그대로 보여 주게 된다.
기능이 해결하려던 문제로 되돌아가는 것이다.
거부는 사이트의 권리이지만 사용자 경험의 비용을 사용자가 치른다.

## 함정

글에 명시된 것과 글이 짚지 않은 것을 나눠 적는다.

글이 명시한 것은 다음과 같다.

- 비트맵 로고는 단순한 흑백 로고만 반전되므로,
  색이 들어간 비트맵 로고는 어두운 배경에서 대비를 잃을 수 있다.
- 이미지에 페이지 배경색이 구워져 있으면 그 배경이 어두운 페이지 위에 밝게 남는다.
- `<canvas>`는 변환되지 않으므로 canvas로 그린 차트가 밝은 바탕이면 어두운 페이지에서
  밝은 상자로 남는다.
- `mask`와 `mix-blend-mode`는 일부 경우 꺼지므로 그 효과에 의존하는 디자인이 달라질 수 있다.
- JavaScript로 읽은 색은 변환 전의 값이다.

글이 짚지 않은 것, 곧 추론은 다음과 같다.

- `color-scheme` 선언을 JavaScript로 나중에 넣으면 변환 판단 시점보다 늦을 수 있다.
  글은 늦게 넣지 말라고만 하고 그 결과는 설명하지 않는다.
- 반은 밝고 반은 어두운 페이지가 어느 쪽으로 추정되는지 기준이 글에 없다.
- 글자색을 JavaScript로 계산해 대비를 판단하는 코드는 화면에 보이는 색과 다른 값을
  보고 판단하게 된다.

직접 만들 때의 흔한 지름길도 함정이다.
AndrewStephens는 `@media(prefers-color-scheme: dark)`에서 `body { filter: invert(); }`로
다크 모드를 흉내 낼 수 있지만 사진까지 반전되어 어울리지 않는다고 적었다.[^AndrewStephens]
iza는 `invert`가 서브픽셀 렌더링을 망가뜨려 글자가 흉하고 읽기 어려워지니 쓰지 말라고 했다.[^iza]

## 확인하기

이 문서는 Safari 27.3 베타를 직접 실행해 확인하지 않았다.
글이 설명한 절차를 아래처럼 정리한다.

1. Safari 27.3 베타를 설치하고 시스템 모양을 다크로 설정한다.
2. 자기 사이트를 열고 Safari가 제안하는 미리 보기에서 Try를 누른다.
3. 세 상태를 비교한다.
   선언이 없는 상태, `color-scheme: light dark`를 선언한 상태,
   `color-scheme: light only`를 선언한 상태이다.
4. 두 번째 상태에서 변환이 일어나지 않는지, 세 번째 상태에서 베타 1이 `only`를
   무시하는지 기록한다.
5. 개발자 도구나 스크립트로 `getComputedStyle(document.body).backgroundColor`를
   읽어 화면과 다른 원래 색이 나오는지 본다.

문제가 있는 사이트를 찾으면 사용자는 Feedback Assistant로,
운영자는 web-evangelist@apple.com으로 알린다.

## 체크리스트

- [ ] 사이트가 `<head>`의 메타 태그나 `:root`의 CSS로 `color-scheme`을 선언하는가.
- [ ] 선언을 JavaScript로 나중에 넣고 있지 않은가.
- [ ] 로고와 아이콘이 SVG인가, 아니면 색이 들어간 비트맵인가.
- [ ] 이미지에 페이지 배경색이 구워져 있지 않은가.
- [ ] 타일 배경이나 스프라이트에 의존하는 부분이 있는가.
- [ ] canvas로 그린 밝은 바탕의 차트가 있는가.
- [ ] `mask`나 `mix-blend-mode`에 의존하는 디자인이 있는가.
- [ ] 글자색이나 배경색을 JavaScript로 읽어 판단하는 코드가 있는가.
- [ ] 선언이 없는 상태, 선언한 상태, `light only` 상태를 모두 직접 열어 보았는가.

## 기억할 원칙

### 선언하면 변환하지 않고, 선언하지 않으면 추정한다

Adaptive Dark Mode의 판단은 사이트의 선언에 달려 있다.
`color-scheme: light dark`가 있으면 아무것도 하지 않고,
없으면 Safari가 색을 보고 추정한다.
그래서 변환 결과를 바꾸는 가장 직접적인 방법은 변환 알고리즘에 맞추는 것이 아니라
자기 사이트의 의도를 선언하는 것이다.

### 브라우저가 보여 주는 색과 코드가 읽는 색은 달라질 수 있다

개인정보를 위해 JavaScript는 변환 전의 색만 본다.
색에 따라 동작을 정하는 코드는 이제 화면의 색을 안다고 가정하면 안 된다.
