## 요약

Julia Evans가 2026년 5월 15일에 쓴 글이다.
8년 전 Tailwind를 발견하고 신나게 글을 썼던 사람이, 이번에는 몇 개 사이트를 Tailwind에서 시맨틱 HTML과 바닐라 CSS로 옮긴 기록을 남겼다.

출발점에 대한 회고가 솔직하다.
그때는 CSS 코드를 어떻게 구조화할지 전혀 몰랐고, 완전한 혼돈 더미와 Tailwind 중에 고르라면 Tailwind가 정말 반가웠다는 것이다.
그 덕에 작은 사이트를 많이 만들었다고 적는다.

이번 이주에서 얻은 첫 깨달음이 글의 골격을 정한다.
CSS 구조화를 생각하기 시작했을 때 처음에는 겁이 났지만, 구조화에 대한 글들을 읽으면서 세 가지를 알게 되었다는 것이다.
모든 CSS 코드베이스에는 레이아웃, 폰트, 색상, 공통 컴포넌트 같은 여러 가지가 돌아가고 있고, 각각을 관리할 체계나 지침이 없으면 혼돈에 빠지며, Tailwind에는 그중 일부에 대한 체계가 있고 자기는 이미 그 체계를 안다는 것이다.
그러니 마음에 드는 체계를 흉내 내면 된다는 결론이다.

그렇게 아홉 가지 영역에 대한 규칙을 정한다.

| 영역        | 정한 규칙                                                                  |
| ----------- | -------------------------------------------------------------------------- |
| 리셋        | Tailwind의 preflight 스타일 앞부분 200줄 정도를 그대로 복사                |
| 컴포넌트    | 컴포넌트마다 고유 클래스, 서로의 CSS를 덮어쓰지 않음, 파일 하나씩          |
| 색상        | `colours.css`에 변수로 모아 두고, 사이트에서 쓰는 색은 전부 여기 있어야 함 |
| 폰트 크기   | Tailwind에서 가져온 `--size-*`와 `--line-height-*` 변수                    |
| 유틸리티    | 여러 컴포넌트에 나타나는 버튼 같은 것들. `.sr-only` 등을 Tailwind에서 복사 |
| 베이스      | 전역에 적용할 스타일. 자신 없으므로 아주 작게 유지                         |
| 간격        | 아직 미정. 바깥 레이아웃 컴포넌트가 간격을 맡게 하는 방향                  |
| 반응형      | 미디어 쿼리 대신 유연한 그리드                                             |
| 빌드 시스템 | 개발 중에는 없음. 프로덕션에는 esbuild                                     |

리셋에 대한 관찰이 재미있다.
Tailwind의 CSS 리셋과 관계를 맺어 왔다는 것을 알아차렸으며, 예를 들어 Tailwind가 모든 요소에 `box-sizing: border-box`를 설정한다는 점이다.

```css
* { box-sizing: border-box; }
```

이것들 없이 CSS를 쓰는 것으로 옮겨 가면 상당한 적응이 필요할 것 같고, `html { line-height: 1.5; }`처럼 무의식적으로 익숙해져 있어 거기 있는지도 모르는 것들이 리셋에 많을 것이라고 적는다.

컴포넌트 절이 CSS의 대부분이다.
Vue나 React 컴포넌트와 정신적으로 관련된 방식으로 CSS를 조직한다는 것이며, 사이트에 JavaScript가 전혀 없을 수도 있다는 단서가 붙는다.

```html
<figure class="zine horizontal">
    <img src="whatever.jpg">
</figure>
```

```css
.zine {
  &.horizontal { }
  &.vertical { }
  &:hover { }
}
```

컴포넌트끼리 간섭하지 않도록 보장하는 프로그램적 장치(웹 컴포넌트나 `@scope`)는 쓰지 않았고, 규약을 두고 최선을 다하는 것만으로도 이미 큰 개선으로 느껴진다고 적는다.
그리고 이 구조의 이점을 수치로 설명한다. 실제로 바꾸고 싶은 CSS의 80% 정도가 컴포넌트 파일에 있으므로, 100줄짜리 컴포넌트를 고칠 때는 그 100줄만 생각하면 된다는 것이다.

폰트 크기에서 Tailwind를 흉내 낸 이유가 명확하다.
“글자를 크게 하고 싶다”고 생각하고 `text-lg`를 쓰면 끝이었고, 충분히 크지 않으면 `xl`이나 `2xl`로 가면 됐으며, `em`인지 `px`인지 `rem`인지 기억하려 애쓸 필요가 없었다는 것이다.

```css
--size-xs: 0.75rem;
--line-height-xs: 1rem;

--size-sm: 0.875rem;
--line-height-sm: 1.25rem;
```

```css
h3 {
  font-size: var(--size-lg);
  line-height: var(--line-height-lg);
}
```

Tailwind보다 조금 장황하지만 지금은 만족한다고 적는다.

베이스 스타일은 딱 두 개만 두었다.

```css
/* 각 <section> 가운데에 950px 칼럼을 둔다 */
section {
  --inner-width: 950px;
  padding: 3rem max(1rem, (100% - var(--inner-width))/2);
}

a {
  color: var(--orange);
}
```

전역에 많은 스타일을 강제할 만큼 자신이 없으므로 이 영역을 정말 작게 유지해야 한다고 적는다.
접근 방식도 밝힌다. 베이스에 거의 아무것도 없는 상태로 시작한 뒤, 공통으로 원하는 것이 보이면 컴포넌트에서 베이스로 옮기는 상향식이 자기에게 가장 쉬울 것 같다는 것이다.

간격은 아직 정리되지 않았다고 인정한다.
다만 Tailwind에서 하던 방식, 즉 원하는 모습이 될 때까지 아무렇게나 패딩과 마진을 뿌리는 것보다는 원칙적으로 하려 한다고 적는다.

```css
section > *+* {
  margin-top: 1rem;
}
```

반응형 절이 이 글에서 기술적으로 가장 새로운 부분이다.
Tailwind에서는 미디어 쿼리를 많이 썼고 `md:text-xl` 같은 문법이 그것이었는데, 이제는 브레이크포인트가 덜 필요한 유연한 그리드 레이아웃을 만드는 쪽으로 가고 있다는 것이다.
어렵지만 그리드로 무엇이 가능한지 배우는 것이 정말 흥미로우며, Tailwind로는 불가능하다고 보는 것의 좋은 예라고 적는다.

```css
display: grid;
grid-template-columns: repeat(auto-fit, minmax(min(100%, 400px), max-content));
justify-content: center;
```

`grid-template-areas`도 많이 썼는데 Tailwind로는 쓸 수 없다고 보는 놀라운 기능이라고 덧붙인다.

빌드 시스템은 개발 중에는 필요 없다고 한다. CSS에 `@import`와 중첩 선택자가 이제 내장되어 있기 때문이다.
프로덕션 번들이 필요하면 esbuild를 쓴다.

```bash
esbuild style.css --bundle --loader:.svg=dataurl --loader:.woff2=file --outfile=/tmp/out.css
```

CSS와 JS 빌드 시스템을 보통 피하지만 esbuild는 웹 표준에 기반하고 정적 Go 바이너리라서 쓰는 것이 싫지 않다고 적는다.

왜 옮기느냐는 질문에 대한 답이 여섯 가지로 정리된다.

- Tailwind가 2018년 이후 빌드 시스템에 훨씬 더 의존하게 되었고, 최신 버전을 빌드 시스템 없이 쓰는 것은 불가능해 보인다. 그래서 몇 년째 Tailwind v2를 쓰고 있었다
- 원래도 빌드 시스템과 함께 쓰는 것이 전제였지만 실제로 그러지 않았고, 그래서 여러 프로젝트에 2.8MB짜리 `tailwind.min.css`(gzip 270K)가 들어 있는데 좀 우스꽝스럽게 느껴진다
- Tailwind를 쓰기 시작했을 때보다 CSS를 훨씬 잘하게 되었다
- 결국 Tailwind는 제한적이다. CSS로 이상한 것을 하고 싶을 때 Tailwind로는 항상 가능하지는 않다. 그 제한은 매우 유용할 수 있고 이 글의 상당 부분이 그 제한을 다시 구현하는 이야기이지만, 이제는 골라 쓰고 싶다
- 바닐라 CSS와 Tailwind가 한 프로젝트에 섞인 사이트가 되었고 유지보수가 즐겁지 않았다
- 더 시맨틱한 HTML을 쓰는 것이 어떤 느낌인지 궁금해졌다

마지막 이유가 따로 한 절을 차지한다.
3년 전에 읽은 “Tailwind and the Femininity of CSS”라는 글이 계속 마음에 남았다는 것이다.
그 글이 묘사하는 태도, 즉 “단순하다고 들었으니 쉬울 거라고 가정하고, 그런데 막상 써 보면 안 된다”는 태도를 자기도 처음에는 조금 갖고 있었을 것이라고 적는다.

그래서 몇 년 전에 “CSS는 어렵다”에 대응하는 방식을 정했다고 한다.
CSS를 평가절하하는 대신 더 잘하게 되고 기술로서 진지하게 대하는 것이었고, 그렇게 하니 모든 것이 달라졌다는 것이다.
“가운데 정렬은 불가능하다” 같은 자기 좌절의 상당수가 오래전에 CSS에서 해결되었다는 것을 배웠고, 가운데 정렬이 무엇을 뜻하는지가 늘 단순하지 않으며 방법이 여럿인 것이 말이 된다는 것도 알게 되었다고 적는다.
CSS가 어려운 것은 어려운 문제를 풀고 있기 때문이라는 문장이 그 절의 결론이다.

그리고 그 글이 Tailwind가 CSS 전문성의 평가절하에 기여한다고 느끼게 만들었으며, Tailwind가 개인적으로 유용한 도구였더라도 그 일부가 되고 싶지 않다고 적는다.
인간의 전문성을 가치 있게 여기는 것이 그 어느 때보다 중요하게 느껴지는 LLM의 시대에는 특히 그렇다는 말로 맺는다.

## 분석

### 이 글의 논지는 Tailwind 비판이 아니라 제약의 소유권 이전이다

제목만 보면 탈-Tailwind 선언이지만, 본문 아홉 절 중 다섯 절이 Tailwind에서 무언가를 복사해 오는 이야기다.
리셋 200줄을 그대로 가져왔고, 폰트 스케일 변수를 가져왔고, `.sr-only` 같은 유틸리티를 가져왔다.

저자 자신이 이 구조를 명시한다. Tailwind의 제약이 매우 유용할 수 있고 이 글의 상당 부분이 그 제약을 다시 구현하는 이야기이지만, 이제는 골라 쓰고 싶다는 문장이다.
즉 버리는 것은 제약이 아니라 제약을 누가 정하느냐다.

이 구분이 왜 중요한가.
Tailwind 논쟁은 대개 “제약이 좋은가 나쁜가”로 진행되고, 그 틀에서는 팀 규모나 성숙도에 따라 답이 갈릴 뿐 결론이 나지 않는다.
저자의 틀은 다르다. 제약이 필요하다는 데 동의하되, 그 제약의 목록을 자기가 관리할 수 있느냐를 묻는다.

그리고 그 질문에 답할 수 있는 시점이 따로 있다는 것이 글의 숨은 전제다.
8년 전에는 답할 수 없었고 지금은 답할 수 있으며, 그 사이에 바뀐 것은 Tailwind가 아니라 저자의 CSS 숙련도다.
그래서 이 글은 도구 평가가 아니라 숙련도가 도구 선택을 어떻게 바꾸는지에 대한 기록이다.

### 그리드로 브레이크포인트를 없애는 시도가 진짜 전환점이다

복사해 온 다섯 절과 달리, 반응형 절만은 Tailwind가 제공하지 않는 것을 향한다.

```css
grid-template-columns: repeat(auto-fit, minmax(min(100%, 400px), max-content));
```

이 한 줄이 하는 일은 브레이크포인트를 선언하지 않고 컨테이너 폭에 따라 열 수를 스스로 정하는 것이다.
미디어 쿼리는 뷰포트를 보지만 이 선언은 사용 가능한 공간을 본다. 논리의 층위가 다르다.

Tailwind의 `md:text-xl` 문법이 왜 이것을 대체하지 못하는지도 분명하다.
그 문법은 미디어 쿼리를 클래스 이름으로 압축한 것이므로 미디어 쿼리가 할 수 있는 일만 할 수 있다.
반대로 `auto-fit`이나 `grid-template-areas`는 값 자체가 조건 논리를 품고 있어서, 유틸리티 클래스로 잘게 나누는 순간 의미가 사라진다.

그래서 이 절이 글 전체의 주장을 실증한다.
“Tailwind는 제한적이다”라는 말이 추상적 불만이 아니라, 유틸리티 클래스라는 표현 형식이 애초에 담을 수 없는 CSS 기능이 있다는 구체적 진단인 것이다.
그리고 그 기능들이 최근 10년의 CSS 발전에서 나온 것들이라는 점이 저자의 마지막 절, 즉 CSS를 기술로 존중하자는 주장과 연결된다.

### 컴포넌트 규약이 도구 없이 규약만으로 성립한다는 주장

컴포넌트 절에서 저자는 세 규칙을 세운다. 고유 클래스, 서로 덮어쓰지 않기, 파일 하나씩이다.
그리고 이를 강제하는 프로그램적 장치는 쓰지 않았다고 명시한다.

이 선택에 대한 반응이 갈렸다.
HN에서 locallost는 20년 전에 처음 CSS를 썼는데 이런 식으로 CSS를 구조화하는 것이 정말 불가능하다고 확언할 수 있다고 적었다.[^locallost]
구조는 시간이 지나면 무너지고 어차피 버그가 생기며 꼬리를 쫓게 되는데, 하는 모든 것이 전역인 한 그렇다는 것이다.
혼자 개발하면 통할 수 있지만 현실의 프로젝트 대부분은 여러 사람이 관여하고, 스타일이 전역인 한 그것을 바꾸면 다른 것이 깨진다고 했다.
동료 A가 B의 것을 깨고, B가 고치면서 내 것을 깨고, 내가 고치면서 다시 A의 것을 깨는 순환이 한 바퀴 더 돈 뒤에야 셋을 동시에 고칠 수 있었다는 일화를 덧붙였다.
요즘은 스코프 스타일만 쓴다는 것이 결론이다.

이 비판이 정확히 겨냥하는 것은 저자가 인정한 바로 그 지점이다.
규약은 사람이 지키는 것이고, 사람이 여럿이면 규약은 깨진다.
다만 저자의 프로젝트가 1인 프로젝트라는 조건이 글에 드러나 있으므로, 이 비판은 글의 오류라기보다 적용 범위의 경계를 그린다.

efortis는 중간 지점을 제시했다. CSS Modules가 캐스케이드 문제에 대한 더 단순한 해법이며, 고유한 클래스 이름을 만들어 주므로 충돌하지 않고, Tailwind의 두 가지 주요 단점인 가독성과 도구 지원 문제가 없다는 것이다.[^efortis]
브라우저 개발자 도구로 디버깅하고 상호작용하며 실험할 수 있다는 점을 특히 들었다.

### 반응이 글의 내용보다 태도를 두고 갈렸다

이 글에 달린 반응에서 눈에 띄는 것은, 기술적 논점보다 “CSS를 제대로 배웠는가”라는 주제가 반복된다는 점이다.

HN에서 JimDabell은 Tailwind 지지자들의 논거가 사실상 전부 “나는 CSS를 주니어 수준 이상으로 배운 적이 없다”로 귀결된다고 적었다.[^JimDabell]
Tailwind가 없으면 통제 불능으로 커지고 쓸모없는 것이 잔뜩 쌓이고 `!important`가 도처에 깔린 큰 CSS 파일 하나가 될 것이라는 식의 주장을 흔히 듣는다는 것이다.
CSS도 다른 기술과 마찬가지로 하나의 기술이며, 보기에 맞을 때까지 대충 때우는 최소한만 배우면 야망이 능력을 금방 앞지른다고 했다.

Lobste.rs에서는 같은 논조가 저자와의 직접 대화로 이어졌다.
wrs는 이것이 CSS가 원래 동작하는 방식이며, 이를 모른 채 Tailwind를 맹목적으로 쓰는 사람들을 보면 밖에 나가 구름에 대고 소리치고 싶어진다고 적었다.[^wrs]
자기에게 Tailwind의 90%는 문법만 다른 인라인 스타일이며 태그보다 한 단계 위일 뿐이라는 것이다.

저자가 직접 답했고, 그 스레드에서 가장 높은 점수를 받았다.
이 댓글의 목적이 무엇인지 모르겠지만, Tailwind를 쓴 거의 8년 동안 Tailwind 사용자를 무시하는 이런 댓글을 수없이 읽었고 그중 어느 것도 Tailwind에서 벗어나거나 CSS 실력을 높이는 데 도움이 되지 않았다는 것이다.[^jvns]
이 블로그 글이 자기가 실제로 알아야 했던 것을 설명한 것이라고 맺었다.

wrs는 도구를 최대한 활용하지 않는 것에 대한 좌절이 무시는 아니며 오히려 반대라고 답했고, CSS 튜토리얼이 수백만 개 있는데 자기가 또 쓸 이유는 모르겠다고 했다.[^wrs2]
CSS를 쓰고 싶으면 CSS를 배워야 하고, 그러고도 Tailwind를 쓰고 싶으면 그건 정보에 근거한 선택이니 좋다는 것이다.

이 교환이 드러내는 것은 두 사람이 다른 질문에 답하고 있다는 사실이다.
wrs는 “무엇을 알아야 하는가”에 답하고 저자는 “어떻게 알게 되는가”에 답한다.
bitshift가 그 간극을 짚었다. Tailwind가 jvns가 CSS를 배운 방법이었던 것 같다며, 자기도 CSS를 오래 썼지만 논리적 수준에서 아는 것과 정말 아는 것이 다르고 Tailwind가 유용한 진입로일지 궁금하다고 적었다.[^bitshift]
CSS 튜토리얼이 통하지 않았던 사람들에게 확실히 통했다는 것이다.

## 비평

### Tailwind가 그리드를 못 쓴다는 주장은 정확하지 않다

글에서 기술적으로 가장 약한 부분이다.
저자는 `grid-template-areas`를 Tailwind로는 쓸 수 없다고 보는 놀라운 기능이라고 적고, `auto-fit` 그리드도 Tailwind로 불가능하다고 본다고 적는다.

두 진술 모두 “내가 알기로는”이라는 유보를 달고 있지만, 실제로는 틀렸다.
Tailwind에는 임의 값 문법이 있어서 `grid-cols-[repeat(auto-fit,minmax(min(100%,400px),max-content))]`처럼 쓸 수 있고, `grid-template-areas`도 테마 확장이나 임의 값으로 지정할 수 있다.
저자가 몇 년째 v2를 쓰고 있었다고 밝혔으므로 이 오해의 출처는 짐작할 수 있다. 임의 값 문법은 v3에서 도입되었다.

이것이 사소한 사실 오류에 그치지 않는 이유는, 이 주장이 글의 핵심 논거이기 때문이다.
“Tailwind는 제한적이다”라는 여섯 번째 이유를 뒷받침하는 유일한 구체적 사례가 반응형 절이고, 그 절이 든 두 예가 모두 반례를 갖는다.

더 정확한 진술은 가능성이 아니라 인체공학에 관한 것이다.
`grid-cols-[repeat(auto-fit,minmax(min(100%,400px),max-content))]`는 문법적으로 가능하지만, 이 시점에서 유틸리티 클래스가 주는 이점, 즉 짧고 기억하기 쉬운 이름은 전부 사라진다.
클래스 이름 안에 CSS 값을 통째로 넣는 순간 그것은 문자열로 감싼 CSS일 뿐이며, 그럴 바에는 CSS 파일에 쓰는 것이 낫다는 것이 옳은 주장이다.
저자가 하려던 말도 아마 그것이지만, 글은 그 말 대신 더 강하고 틀린 주장을 한다.

### 2.8MB CSS 파일은 Tailwind의 문제가 아니라 쓰는 방식의 문제다

이주 이유 여섯 가지 중 둘이 빌드 시스템에 관한 것이고, 그중 하나가 2.8MB `tailwind.min.css`다.

저자가 스스로 원인을 밝힌다. 원래도 빌드 시스템과 함께 쓰는 것이 전제였지만 실제로 그러지 않았다는 것이다.
그러니 이것은 Tailwind가 만든 문제가 아니라 문서화된 전제를 따르지 않은 결과이고, 글도 그렇게 인정한다.

문제는 그 인정이 이유 목록에서 제거되지 않는다는 점이다.
“내가 권장 사용법을 따르지 않아서 생긴 문제”와 “도구의 한계”가 같은 목록에 나란히 놓이면, 읽는 사람은 둘을 구분하지 않는다.

그리고 이 항목에는 반론도 붙는다.
HN에서 simonreiff는 외부 라이브러리 의존을 없애고 직접 짜는 쪽을 좋아하지만 Tailwind만큼은 그러지 않기로 했다며, 프로덕션 최적화가 필요한 최소한의 CSS만 내보내도록 보장해 주기 때문이라고 적었다.[^simonreiff]
그래서 색상과 간격 등의 선택지를 `globals.css`에 전부 나열해 두고도 프로덕션에서 그 변형들을 다 쓰는지 걱정할 필요가 없으며, Next.js 같은 프레임워크 안에서는 빌드 시 자동으로 일어나 신경 쓸 일조차 없다는 것이다.

즉 저자가 우스꽝스럽다고 느낀 2.8MB는 빌드 시스템을 쓰는 사람에게는 애초에 존재하지 않는 문제이고, 빌드 시스템 없이 쓰겠다는 저자의 다른 선호가 만든 결과다.
그 선호 자체는 정당하지만, 그렇다면 이유 목록은 “Tailwind가 빌드 시스템을 요구한다”는 한 줄로 합쳐졌어야 한다.

### 페미니티 논거가 글의 나머지와 결이 맞지 않는다

마지막 절에서 저자는 Tailwind가 CSS 전문성의 평가절하에 기여한다고 느꼈고 그 일부가 되고 싶지 않다고 적는다.

이 주장이 앞선 여덟 절과 긴장 관계에 있다.
글의 대부분은 Tailwind가 자신에게 CSS 구조화를 가르쳤다는 이야기이며, 리셋과 폰트 스케일과 유틸리티를 그대로 가져올 만큼 잘 설계되어 있다는 증언이다.
“Tailwind가 나에게 많은 것을 가르쳐 주었다”가 첫 소제목이다.

그렇다면 Tailwind는 CSS 전문성을 평가절하하는 도구인가, 아니면 전문성으로 가는 진입로인가.
글은 둘 다라고 말하지만 그 둘이 어떻게 양립하는지는 설명하지 않는다.
bitshift가 제기한 질문, 즉 Tailwind가 CSS의 멘탈 모델을 세우는 진입로가 될 수 있는지가 바로 이 지점이며, 저자 자신의 경험이 그 질문에 긍정으로 답하는 증거인데도 그렇다.

그리고 이 절이 글의 설득력 구조를 바꾼다.
앞의 여덟 절은 검증 가능한 기술적 근거이고 독자가 자기 상황에 맞춰 판단할 수 있다.
마지막 절은 가치 판단이며, 동의하지 않는 독자에게는 앞의 논거까지 의심하게 만든다.

이 절을 빼는 것이 낫다는 말은 아니다. 저자가 이 이유를 가장 중요하게 여긴다는 점이 분명하고, 밝히지 않는 편이 덜 정직하다.
다만 “내가 그렇게 느꼈다”와 “Tailwind가 그런 역할을 한다”는 다른 주장이고, 글은 전자의 언어로 후자를 말한다.

### LLM 시대라는 언급이 반대 결론으로도 읽힌다

마지막 문장에서 저자는 인간의 전문성을 가치 있게 여기는 것이 그 어느 때보다 중요하게 느껴지는 LLM의 시대라고 적는다.

그런데 LLM은 이 논쟁에서 반대편 근거로도 쓰인다.
luodaint는 에이전트가 컴포넌트를 쓸 때 스타일이 JSX와 함께 오며, `flex items-center gap-4 bg-purple-600 rounded-lg`는 별도 스타일시트 파일로 정신적 문맥 전환을 요구하지 않는다고 적었다.[^luodaint]
커스텀 클래스는 컴포넌트마다 별도 파일로 가게 만들지만 유틸리티 클래스는 스타일 정보를 손 닿는 곳에 둔다는 것이다.
그리고 Tailwind가 막아 주는 다른 것으로 클래스 이름 비대를 들었다. Tailwind가 없으면 에이전트가 `card-header-inner`, `feature-block-content`, `sidebar-item-wrapper` 같은 클래스를 발명하고, 몇 달 뒤에는 아무도 소유하지 않는 클래스가 수백 개 쌓인다는 것이다.
Tailwind가 두는 한계가 어휘에 있으며 발명할 이름이 없다는 문장이 핵심이다.

brokegrammer는 더 직접적으로 정리했다. Tailwind 클래스에 대한 데이터가 이미 학습 데이터에 있고 스타일이 충돌하지 않으므로, AI가 새 스타일을 만들 때 기존 스타일시트를 참조할 필요가 없어 문맥 관리에 좋다는 것이다.[^brokegrammer]
커스텀 CSS에서는 AI가 기존 스타일시트를 읽어야 하며, 그러지 않으면 충돌하는 스타일을 쓰거나 이미 있는 것을 다시 쓰게 된다는 점을 들었다.

이 논거들이 저자의 결론과 정반대 방향을 가리키면서도 같은 전제를 쓴다.
LLM이 코드를 쓰는 시대라는 사실이, 저자에게는 인간 전문성을 지켜야 할 이유이고 이들에게는 기계가 다루기 좋은 어휘를 써야 할 이유다.
글은 이 방향의 논거가 존재한다는 것을 언급하지 않으며, 그래서 마지막 절의 주장이 반대 논거를 다루지 않은 채 끝난다.

## 인사이트

### 도구가 가르친 것과 도구 자체를 분리할 수 있는 시점이 숙련의 정의다

이 글에서 가장 이전 가능한 통찰은 CSS와 무관하다.
Tailwind가 제공한 것이 무엇이었는지를 목록으로 적을 수 있게 된 것, 그것이 이주가 가능해진 조건이다.

도구를 처음 쓸 때는 도구가 주는 것과 도구가 강제하는 것과 도구가 숨기는 것이 구분되지 않는다.
전부 “그냥 그렇게 동작하는 것”으로 묶여 있고, 그래서 도구를 빼면 무엇이 없어지는지 알 수 없다.
저자가 리셋에 대해 적은 문장이 정확히 이 상태를 묘사한다. 무의식적으로 익숙해져 있어 거기 있는지도 모르는 것들이 많을 것이라는 문장이다.

그렇다면 숙련의 실무적 정의가 나온다.
도구를 잘 쓰는 것이 아니라, 도구가 대신해 주던 결정들의 목록을 만들 수 있는 것이다.
그 목록이 있으면 도구를 바꾸는 비용을 추정할 수 있고, 목록이 없으면 이주는 언제나 미지의 크기를 갖는다.

이 관점은 프레임워크 선택 논쟁 전체를 다시 배치한다.
“이 프레임워크를 쓰면 종속된다”는 흔한 걱정의 실질은 코드가 얽힌다는 것이 아니라, 그 프레임워크가 내린 결정들을 내가 모른 채로 의존하게 된다는 것이다.
그리고 그 위험을 낮추는 방법은 프레임워크를 피하는 것이 아니라, 쓰면서 그 결정 목록을 조금씩 적어 두는 것이다.

### 유틸리티 클래스의 진짜 비용은 이름을 짓지 않아도 된다는 데 있다

Tailwind 논쟁에서 양쪽이 같은 사실을 놓고 정반대로 평가하는 지점이 하나 있다.
유틸리티 클래스를 쓰면 이름을 짓지 않아도 된다는 사실이다.

pauxel은 Tailwind에서 가장 아쉬울 부분으로 모든 래퍼와 행과 카드와 내부 카드와 카드 콘텐츠에 시맨틱한 이름을 발명하지 않아도 되는 것을 꼽았다.[^pauxel]
luodaint는 같은 성질을 에이전트 맥락에서 이점으로 들었다. 발명할 이름이 없으니 이름이 비대해지지 않는다는 것이다.

반대편에서 TonyAlicea10은 이것을 순서의 역전으로 설명했다.
HTML은 문서의 의미를 표시하는 것이므로 거기서 시작해야 하고 그다음 CSS로 스타일을 입혀야 하며, 스타일링을 위해 요소가 더 필요하면 div나 span을 쓰되 더 나은 것이 없는지 먼저 자문해야 한다는 것이다.[^TonyAlicea10]
Tailwind는 개발자를 CSS 우선 접근으로 밀어서, 원하는 Tailwind 클래스를 먼저 생각하고 그 클래스를 걸 요소가 필요해서 div를 또 하나 DOM에 던져 넣게 만든다고 했다.

두 진영이 다투는 것은 결국 이름을 짓는 행위가 비용인가 사고 과정인가다.
이름을 지어야 하면 “이것이 무엇인가”를 결정해야 하고, 그 결정이 문서 구조를 만든다.
이름을 짓지 않아도 되면 그 결정이 생략되고, 생략된 결정은 나중에 접근성이나 구조 파악의 문제로 되돌아온다.

일반화하면 명명을 요구하지 않는 추상화는 속도를 주고 모델을 가져간다.
이것은 CSS만의 이야기가 아니다. 익명 함수, 인라인 타입, 자동 생성된 식별자가 전부 같은 거래를 한다.
그 거래가 옳은지는 그 코드를 다시 읽을 사람이 누구인지에 달려 있고, 그 답이 “몇 달 뒤의 나”라면 이름의 값이 대체로 더 크다.

### 빌드 시스템 없이 쓸 수 있느냐가 도구의 수명을 정한다

이 글에서 반복적으로 등장하지만 주제로 다뤄지지 않는 축이 하나 있다.
저자가 몇 년째 Tailwind v2에 머물러 있었던 이유, esbuild만은 예외로 받아들인 이유, 개발 중에는 빌드가 없다고 강조한 이유가 전부 같은 것이다.

이 선호가 개인 취향으로 보이지만 실제로는 수명 문제다.
빌드 시스템에 의존하는 자산은 그 빌드 시스템이 돌아가는 동안만 수정 가능하고, Node 생태계에서 그 기간은 생각보다 짧다.
5년 전 프로젝트의 `node_modules`를 다시 설치해 보면 안다.

저자가 esbuild를 예외로 둔 근거도 정확히 이 축 위에 있다. 웹 표준에 기반하고 정적 Go 바이너리라는 두 가지다.
전자는 산출물이 빌드 없이도 의미를 갖는다는 뜻이고, 후자는 도구 자체가 의존성 없이 보존된다는 뜻이다.

Lobste.rs 스레드가 이 축을 보안 문제로 확장했다.
dkasper는 개인 프로젝트에서는 더 이상 CSS나 JS 프레임워크를 쓰지 않는다며, 의존성이 없으면 공급망 취약점도 있을 수 없다고 적었고 가장 높은 점수를 받았다.[^dkasper]
sebastien은 프레임워크 피로와 `npm audit` 과부하, 그리고 LLM 덕분에 다른 사람이 구현을 어떻게 생각하는지 더 이상 신경 쓰지 않아도 되는 것의 조합이라고 했다.[^sebastien]
dzwdz는 프레임워크의 `.css` 파일을 그냥 받아서 문서 루트에 두던 방식이 어디로 갔느냐고 물으면서, 그 방식이 Tailwind에는 매우 비효율적이며 그것이 자기가 Tailwind를 쓰지 않는 주된 이유일 것이라고 적었다.[^dzwdz]

GN에서 shakespeares가 던진 질문이 이 축의 현재 상태를 묻는다. 제로 설정으로 바뀌면서 좀 더 낫지 않느냐는 것이다.[^shakespeares]
Tailwind v4가 설정 파일을 없애고 CSS 안에서 테마를 정의하는 방향으로 간 것은 실제로 이 방향의 개선이며, 저자가 v2에 머물러 있었다는 사실이 이 글의 판단에 얼마나 반영되었는지를 되묻게 만든다.

일반화하면 도구를 고를 때 물어야 할 질문 하나가 추가된다.
이 도구가 사라지거나 내가 업데이트를 멈춘 뒤에도 이 코드를 고칠 수 있는가다.
답이 아니라면 그 도구는 코드의 수명에 상한을 씌우는 것이며, 그 상한이 프로젝트의 예상 수명보다 짧은지를 따져 봐야 한다.
