## 소개

네이티브 앱 안에 웹뷰를 띄워 화면 일부를 웹으로 만들면 웹과 앱이 JavaScript 브릿지로 메시지를 주고받는다.
이 메시지가 문제일 때, 확인하려면 핸들러마다 로그를 넣고 Logcat이나 Xcode 콘솔을 스크롤하며 요청과 응답을 손으로 맞춰야 한다.
Dari는 한국어 다리(bridge)에서 따온 이름이며, 이 메시지를 한 목록에서 `requestId`로 짝지어 보여 주는 도구이다.
GeekNews에 Show GN으로 올린 글쓴이는 mraz3068이고 저장소 소유자는 easyhooon이다.

저장소는 2026년 2월 11일에 만들어졌고 Apache-2.0이며, 주 언어는 Kotlin이다.
2026년 11월 13일에 읽은 값으로 별 44개, 포크 5개, 열린 이슈 9개이다.
이 문서는 README와 GeekNews 글을 읽은 것이며 Dari를 설치하거나 실행해 보지는 않았다.

## 무엇을 보여 주나

한 줄에 웹에서 앱으로, 앱에서 웹으로 가는 호출 하나가 요청과 응답이 짝지어 나온다.
각 줄에는 상태(진행 중, 성공, 오류)와 소요 시간, 접힘이 되는 정리된 JSON, 핸들러별 호출 수와 오류 수와 평균, 최소, 최대 응답 시간이 있다.
평균 500ms 이상인 핸들러는 강조되고 느린 순으로 정렬된다고 README가 적는다.

두 가지 방식으로 본다.
데스크톱 앱(macOS, Windows, Linux)은 더 큰 화면에서 연결된 디버그 빌드의 메시지를 보여 준다.
프록시나 인증서나 포트 설정이 없고, Android는 `adb`로, iOS는 Mac에서 시뮬레이터나 USB 기기로 연결한다.
앱 안의 인스펙터는 Android에서 알림이나 흔들기로 열고, iOS에서는 `DariUI` 라이브러리의 화면을 앱의 디버그 메뉴에서 연다.

| 항목                | Android                               | iOS                                                             |
| ------------------- | ------------------------------------- | --------------------------------------------------------------- |
| 패키지              | `dari`, `dari-noop`(Maven Central)    | `Dari` Swift 패키지(3.0.0 이상)                                 |
| 최소 OS             | Android 8.0(API 26)                   | iOS 16                                                          |
| 수동 호출 없이 기록 | Gradle 플러그인(2.6.0 이상)           | `autoCapture`(3.1.0 이상) 또는 `@DariBridge` 매크로(3.2.0 이상) |
| 데스크톱 앱         | macOS, Windows, Linux에서 `adb`로     | macOS에서 시뮬레이터나 USB 기기만                               |
| 앱 안 인스펙터      | 전체                                  | 목록, 상세, 검색, 내보내기                                      |
| 릴리스 빌드         | `dari-noop`(같은 API, 기록 코드 없음) | `#if DEBUG` 안에서만 `start()` 호출                             |

### 그 밖의 기능

토큰과 비밀번호와 쿠키 같은 값은 데이터가 기기를 떠나기 전에 가릴 수 있고,
iOS에서는 데스크톱용으로 직접 정한 규칙(`setPayloadRedactor`)도 추가한다.
Protocol Buffers 페이로드를 해석하고, 텍스트와 JSON으로 내보내며, 앱을 다시 켜도 기록을 유지할 수 있다.
iOS에서는 기록 유지가 `persistsMessages`로 켜야 하는 옵션이다.

## 한계로 밝힌 것

글쓴이와 README가 직접 적은 한계는 다음과 같다.

- 디버그용이다. 릴리스 빌드에는 Android는 `dari-noop`, iOS는 `#if DEBUG`로 들어가지 않게 한다.
- iOS를 데스크톱 앱으로 보려면 Mac이 필요하다. Wi-Fi 연결은 아직 Android만 된다.
- `requestId`로 요청과 응답을 맞추는 구조이므로 콜백 방식이 많이 다른 브릿지에서는 짝이 안 맞을 수 있다.
- Windows 설치 파일은 코드 서명이 되어 있지 않아 처음 실행할 때 SmartScreen이 경고할 수 있고, Linux는 미리보기 단계이다.
- Android 앱이 1.x 버전이면 업그레이드하기 전에는 데스크톱 앱에 연결할 수 없다. 데스크톱 앱에는 `dari` 2.0.0 이상이 필요하다.

README의 보안과 개인정보 항목도 짚을 만하다.
브릿지 페이로드에는 토큰이나 개인정보가 들어 있을 수 있으므로 내보낸 메시지는 검토하고 공유해야 한다.
iOS에서는 `start()`가 실행되는 동안 기기의 루프백에 닿을 수 있는 프로세스는 기록된 메시지를 읽을 수 있다고 한다.
데스크톱 앱은 기본으로 Sentry에 충돌 보고를 보내는데, 예외 형식과 스택 트레이스와 OS, 아키텍처, Java 버전만 보내고 예외 메시지와 브릿지 메시지와 호스트 이름과 IP 주소는 보내지 않는다고 밝힌다.
끄려면 설정의 개인정보 항목에서 충돌 보고 전송을 끈다.

## 분석

### 중심 주장은 짝짓기가 디버깅의 병목이라는 것이다

글쓴이의 관찰은 구체적이다.
브릿지 문제는 메시지 자체보다 어떤 요청에 어떤 응답이 돌아왔는지, 응답이 왔는지, 얼마나 걸렸는지를 맞추는 일에 시간이 든다는 것이다.
로그를 흩뿌리고 콘솔을 스크롤하는 방식은 이 짝짓기를 사람 눈에 맡긴다.
Dari는 `requestId`라는 이미 있는 값을 키로 삼아 이것을 도구로 옮긴다.
추가 입력이 필요 없는 점이 설계의 중심이고, 같은 이유로 한계도 같은 곳에 있다.
`requestId`가 없거나 규칙이 다른 브릿지는 짝이 맞지 않는다고 글쓴이가 스스로 밝힌다.

### 어디를 가로채는지가 도입 비용을 정한다

기록하려면 요청이 브릿지에 들어오는 곳과 응답이 나가는 곳에서 인터셉터를 호출해야 한다.
README는 핸들러마다가 아니라 진입점과 출구에서 한 번씩 호출하라고 안내한다.
수동 호출을 줄이는 방법은 플랫폼마다 다르다.
Android는 Gradle 플러그인, iOS는 `autoCapture`나 컴파일 시점의 `@DariBridge` 매크로이다.
기존 브릿지에 붙이는 비용은 브릿지의 구조가 얼마나 한곳에 모여 있는지에 달려 있다.

## 비평

### 비교와 근거가 README에 없다

README는 Dari가 무엇인지는 자세히 설명하지만 다른 방법과 비교하지 않는다.
Android의 Chrome DevTools 원격 디버깅이나 Safari의 웹 인스펙터가 웹뷰 안의 JavaScript를 보여 주는 것과 달리,
Dari는 네이티브 쪽의 브릿지 호출을 짝으로 보여 준다는 차이가 있을 것이다.
그러나 이 둘이 서로 대체하는지 보완하는지는 README가 말하지 않는다.
GeekNews 글의 추천 글 목록에는 안드로이드 WebView에 DevTools를 붙이는 글과 React Native 웹뷰 브릿지 라이브러리 등이 있지만,
이 문서는 그 글들을 열어 보지 않았다.

### 채택의 근거가 약하다

별 44개와 열린 이슈 9개는 초기 프로젝트의 규모이다.
README는 Android Weekly 748호에 소개되었다는 배지를 달았지만 이는 홍보 사실이지 사용 사례가 아니다.
다운로드 수를 Maven Central 요청으로 재는 그래프를 싣지만 이 문서가 읽은 시점의 값은 확인하지 못했다.
그래서 이 도구가 팀 단위로 쓰이는지, 어떤 브릿지 구조에서 잘 맞는지에 대한 외부 증거는 없다.

### 보안 설명은 있으나 기본값이 열려 있다

iOS에서 기록이 도는 동안 루프백에 닿을 수 있는 다른 프로세스가 메시지를 읽을 수 있다는 점은 디버그 도구로서 가벼운 문제가 아니다.
브릿지 메시지에는 인증 토큰이 흔히 지나가기 때문이다.
README가 이를 명시하고 디버그 빌드에서만 호출하라고 요구하는 것은 좋다.
그러나 마스킹은 선택 기능이며 기본으로 켜져 있다고 적혀 있지 않다.
이 문서는 기본값이 어떤지 확인하지 못했다.

### GeekNews 글에는 아직 반응이 없다

이 문서가 읽은 시점에 GeekNews 글의 댓글은 없었고 점수는 4점이었다.
글쓴이가 묻는 두 질문, 곧 다른 브릿지 구조에서 요청과 응답이 제대로 짝지어지는지와 iOS 앱 안 인스펙터에서 QA에 빠진 기능이 무엇인지는 아직 답이 없다.
도구의 평가는 이 질문들에 대한 실사용 답이 쌓여야 가능하다.

## 인사이트

### 이 도구가 맞는 조건은 브릿지에 요청 식별자가 있는 구조이다

Dari가 힘을 내려면 브릿지 메시지가 `requestId` 같은 식별자로 요청과 응답을 잇는 형식이어야 한다.
자기 브릿지가 콜백 이름만으로 응답을 돌려주거나 식별자가 없는 구조라면 짝짓기가 맞지 않는다.
도입 전에 해 볼 일은 브릿지의 요청 하나와 응답 하나를 골라 식별자가 공유되는지 확인하는 것이다.
이 확인은 도구를 설치하지 않고도 할 수 있다.

### 디버그 도구는 릴리스에 들어가지 않는다는 보증을 구조로 만들어야 한다

Dari의 `dari-noop` 방식은 같은 API를 유지하면서 기록 코드를 빼는 구조이다.
호출 코드를 릴리스 빌드에서 조건 컴파일로 지우는 대신 의존성 해석을 바꾸므로 호출부가 분기 없이 남는다.
이런 설계는 실수로 릴리스에 기록 코드가 들어가는 위험을 줄인다.
iOS는 `#if DEBUG`에 기대므로 호출부에서 조건을 빠뜨릴 위험이 남는다.
이 비교는 README의 설명에서 끌어낸 것이며 실제 빌드 산출물을 검사한 것은 아니다.

### 확인할 관찰

이 도구가 문제를 줄인다는 주장은 두 가지로 확인한다.
실제 브릿지 이슈를 디버깅할 때 로그를 넣는 시간이 줄어드는지,
짝이 맞지 않는 브릿지 구조의 비율이 어느 정도인지이다.
후자는 글쓴이가 요청한 피드백이기도 하다.
