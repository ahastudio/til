# Running Tested Features: 기능 수가 일정하게 늘어나게 만들면 팀이 애자일해진다는 2004년의 지표

원문: [A Metric Leading to Agility](https://ronjeffries.com/xprog/articles/jatrtsmetric/)

## 요약

Ron Jeffries가 2004년 6월 14일에 쓴 이 글은 소프트웨어
프로젝트의 진행을 하나의 지표로 재 보자고 제안한다.
지표의 이름은 Running Tested Features(RTF)이고, 정의는 세 문장이다.
원하는 소프트웨어를 이름 붙은 기능(요구 사항, 스토리)으로 쪼개고,
기능마다 동작하면
그 기능이 구현되었음을 보여 주는 자동화된 인수 테스트를 하나 이상 두고,
어느 시점에든 인수 테스트를 모두 통과하는 기능이 몇 개인지를 센다.
Running은 기능이 하나로 통합된 제품 안에서 돌아간다는 뜻이고,
Tested는 요구 사항을 주는 고객이 제공한 테스트를 계속 통과한다는 뜻이며,
Features는 데이터베이스 설치 같은 기술 작업이
아니라 최종 사용자가 보는 기능이라는 뜻이다.

글이 요구하는 곡선 모양은 분명하다.
RTF는 프로젝트 첫날부터 끝까지 거의 직선으로 늘어나야 하고,
첫 주나 둘째 주부터 기능이 나오기 시작해야 한다.
처음 몇 달 동안 평평하면 틀린 곡선이고,
빠르게 시작했다가 느려져도 틀린 곡선이다.
저자는 이 곡선을 지키려는 팀이 큰 설계를 미리 할 수도,
인수 테스트를 건너뛸 수도,
리팩터링을 건너뛸 수도 없어서 결국 애자일해질 수밖에 없다고 주장한다.
그래서 이 지표는 측정 도구이면서 행동을 이끄는 장치로 제시된다.

글에는 손으로 그린 곡선 세 장이 들어 있다.
애자일 프로젝트는 매끄럽게 올라가는 직선이다.
폭포수 방식 프로젝트는 요구 사항과 설계와
시험이라는 눈에 보이지 않는 일이 먼저 쌓이고,
겉보기 RTF가 먼저 오른 뒤 결함과 재작업이 드러나면서
실제 RTF가 더 낮게 확정된다.
세 번째 그림은 어느 프로젝트의 곡선으로 소개되는데,
초반에 갑자기 떨어졌다가 중반에 평평해진다.
저자는 이 하락과 정체가 문제의 신호일 뿐 원인을 알려 주지는 않는다며
팀에게 물어보라고 한다.
자동화된 인수 테스트, 잦은 통합, 고객과의 접촉, 깨끗한 설계가
모두 이 곡선을 유지하기 위한 조건으로 따라 나온다는 것이 글의 결론이다.
글 끝의 각주에 따르면 글은 한 번 고쳐 쓰였고, 이름은 Patrick Welsh가 제안했다.
저자는 첫 곡선을 흔히 번업 차트라 부른다고 덧붙인다.
번업 차트는 이 저장소의 `agile/burn-up-chart.md`에,
눈에 잘 띄는 큰 차트라는 발상은
`agile/big-visible-charts.md`에 따로 정리되어 있다.

## RTF를 오늘의 CI에서 계산하는 법

이 지표는 점수 공식이 없어서 계산이 쉽다.
어려운 부분은 세는 일이 아니라 기능과 테스트를 잇는 대응표를 유지하는 일이다.
아래 코드는 그 대응표(`FEATURES`)와 날짜별 CI 결과(`RUNS`)에서 RTF를 계산한다.
테스트가 하나도 없는 기능은 절대 세지 않고,
`window`를 늘리면 최근 여러 번의 실행에서 모두 통과해야 센다.

```python
"""Running Tested Features(RTF)를 CI 결과에서 계산하는 최소 예제."""
from collections import defaultdict

# 고객이 정의한 기능과, 그 기능을 입증하는 독립 인수 테스트의 대응.
# 테스트가 하나도 없는 기능은 Tested가 아니므로 절대 센다고 하지 않는다.
FEATURES = {
    "F1 로그인": ["acc_login_ok", "acc_login_bad_password"],
    "F2 장바구니 담기": ["acc_cart_add"],
    "F3 결제": ["acc_pay_card", "acc_pay_declined"],
    "F4 주문 내역": ["acc_history_list"],
    "F5 쿠폰": [],  # 아직 인수 테스트가 없다
}

# 날짜별 CI 실행 결과: 테스트 이름 -> True(통과) / False(실패).
RUNS = {
    1: [{"acc_login_ok": True, "acc_login_bad_password": True}],
    2: [{"acc_login_ok": True, "acc_login_bad_password": True,
         "acc_cart_add": True}],
    3: [{"acc_login_ok": True, "acc_login_bad_password": True,
         "acc_cart_add": True, "acc_pay_card": True,
         "acc_pay_declined": False}],
    4: [{"acc_login_ok": True, "acc_login_bad_password": True,
         "acc_cart_add": True, "acc_pay_card": True,
         "acc_pay_declined": True}],
    5: [{"acc_login_ok": True, "acc_login_bad_password": False,  # 회귀
         "acc_cart_add": True, "acc_pay_card": True,
         "acc_pay_declined": True, "acc_history_list": True}],
    6: [{"acc_login_ok": True, "acc_login_bad_password": True,
         "acc_cart_add": True, "acc_pay_card": True,
         "acc_pay_declined": True, "acc_history_list": True}],
}


def feature_is_running_tested(tests, runs):
    """테스트가 있고, 최근 runs 모두에서 그 테스트가 전부 통과했을 때만 True.

    runs를 여러 번(예: 최근 3회) 넘기면 불안정(flaky) 테스트 한 번의 우연한
    통과로 기능을 세는 일을 막는다.
    """
    if not tests:
        return False
    return all(run.get(t) is True for run in runs for t in tests)


def rtf_by_day(features, runs_by_day, window=1):
    """날짜별 (day, RTF, 세지 못한 이유, 어제는 셌는데 오늘 못 센 기능)."""
    history = []
    seen = []
    previous = set()
    for day in sorted(runs_by_day):
        seen.extend(runs_by_day[day])
        recent = seen[-window:]
        counted, missing = [], defaultdict(list)
        for name, tests in features.items():
            if feature_is_running_tested(tests, recent):
                counted.append(name)
            elif not tests:
                missing[name].append("인수 테스트 없음")
            else:
                for t in tests:
                    if not all(run.get(t) is True for run in recent):
                        missing[name].append(t)
        regressed = sorted(previous - set(counted))
        previous = set(counted)
        history.append((day, len(counted), dict(missing), regressed))
    return history


def bar(n, total):
    return "#" * n + "." * (total - n)


if __name__ == "__main__":
    total = len(FEATURES)
    print(f"기능 {total}개 중 RTF (window=1)")
    for day, n, missing, regressed in rtf_by_day(FEATURES, RUNS):
        print(f"day {day}: {n} {bar(n, total)}")
        if regressed:
            print("   회귀:", regressed, "<-", {k: missing[k] for k in regressed})
```

이 코드를 실제로 돌린 출력은 다음과 같다.

```text
기능 5개 중 RTF (window=1)
day 1: 1 #....
day 2: 2 ##...
day 3: 2 ##...
day 4: 3 ###..
day 5: 3 ###..
   회귀: ['F1 로그인'] <- {'F1 로그인': ['acc_login_bad_password']}
day 6: 4 ####.
```

실무에서는 `RUNS`를 JUnit XML이나 테스트 러너의 JSON에서 만들고,
테스트 이름이나 마커에 기능 ID를 붙여 대응표를 자동으로 얻는 방식이 흔하다.
이는 이 문서의 구현 제안이며 원문이 이 방법을 말하지는 않는다.

## 분석

### 지표가 아니라 압박 장치로 설계되었다

글의 핵심 논리는 측정이 행동을 바꾼다는 것이다.
저자는 RTF를 진행을 정확히 재는 계기로 팔기보다,
이 곡선을 지키라고 요구하면
팀이 필요한 관행을 스스로 발명한다는 압박 장치로 소개한다.
기능이 첫날부터 늘어야 하니 인프라를 먼저 짓지 못하고,
계속 늘어야 하니 자주 통합해야 하고,
독립된 테스트를 통과해야 하니 고객과 접촉해야 하고,
테스트가 계속 통과해야 하니 자동화해야 하고,
곡선이 매끄러워야 하니 설계를 깨끗하게 유지해야 한다는 연쇄다.
이 연쇄는 글 가운데의 목록 여섯 줄이 그대로 말한다.

이 구조의 장점은 한 가지를 요구해서 여러 관행을 얻는다는 점이다.
저자는 Scrum과 Crystal Clear가 매 반복마다 바로
쓸 수 있는 소프트웨어를 내놓으라고만 요구하며
나머지는 따라온다고 쓰고, XP는 도움이 될 관행 목록까지 덤으로 준다고 덧붙인다.
이는 RTF가 새로운 방법론이 아니라 이 요구를
눈에 보이는 곡선으로 옮긴 것임을 보여 준다.

### 이 생각은 20년 동안 모양을 바꿔 반복됐다

저자는 이후에도 같은 주장을 다른 말로 되풀이했다.
2006년 InfoQ 인터뷰에서 그는 화이트보드에 그림을 그리며
RTF 추적이 애자일의 핵심이고
다른 모든 관행이 그로부터 필연적으로 나온다는 입장을 설명했고,
TDD가 RTF에 필수이지만 눈에 덜 띄면서
똑같이 필수인 관행은 XP가 말하는 단순한 설계라고 짚었다.
단순한 설계가 없으면 설계 부채가 쌓여 속도가 떨어진다는 것이다.[^infoq-news]
같은 기사는 2007년 2월 14일 정정 문구를 달았다.
처음에는 Alistair Cockburn의 글에서 이 생각이 나왔다고 썼다가,
Cockburn이 오히려 2004년의 이 글을 인용했다고 바로잡았다.[^infoq-news]
이 정정이 이 글의 선행성을 확인해 주는 자료다.

2008년 6월 30일 블로그 글에서 저자는 Scrum이 두 가지를 요구해서 통한다고 썼다.
정기적으로 완료된(done-done) 소프트웨어를 내놓을 것,
그것을 막는 모든 장애물을 치울 것.
그는 이를 오래된 RTF 관념의 재진술이라고 불렀고
견해가 한동안 흔들리지 않았다고 적었다.[^yet-again]
2017년 8월 4일 글에서는 이름이 Increment로 바뀐다.
개발자들이 매주나 격주로 모든 기능과 능력을 담은 통합되고
돌아가고 검증된 소프트웨어를 내놓고,
이해관계자가 그것을 검토한다는 정의다.[^increment]
지표가 사라지고 매번 내놓는 물건이 남았다는 점이 이 변화의 요점이다.

### 글이 잰 것은 진행의 크기가 아니라 진행의 모양이다

RTF는 기능 하나를 1로 세므로 값 자체는 크기를 담지 않는다.
글이 요구하는 것은 값이 아니라 곡선의 모양, 곧 기울기가 일정한 직선이다.
이 모양은 몇 가지를 한꺼번에 알려 준다.
시작이 늦으면 앞에 일이 숨어 있고, 중간에 떨어지면 회귀나 요구 변경이 있고,
기울기가 완만해지면 설계가 막히거나 인력이 빠졌거나 고객이 테스트를 안 쓴다.
저자가 각 경우에 팀에게 물어보라고
하는 것은 이 지표가 진단이 아니라 질문을 만들어 내는 장치임을 인정하는 것이다.

## 비평

### 게임하기 어렵다는 주장은 의도에 기대고 구조에 기대지 않는다

저자는 RTF를 조작할 수 있을지도 모르지만
애자일해지는 편이 더 쉬울 것이라고 쓴다.
거짓으로 대응하려면 정말 사악한 팀이어야 하는데 그런 팀은 많지 않다는 것이다.
이는 조작이 어렵다는 구조의 논증이 아니라 팀이 정직할 것이라는 믿음이다.

세는 방식을 보면 조작 지점이 분명하다.
무엇을 한 기능으로 세는지,
어떤 인수 테스트가 기능을 입증하는지가 모두 사람의 판단이다.
로그인이라는 기능을 열 개로 쪼개면 같은 일로 RTF가 열 배가 되고,
인수 테스트를 약하게 쓰면 기능이 쉽게 통과한다.
저자는 고객이 독립적으로 정의한 테스트가 이를 막는다고 하지만,
고객이 테스트를 쓰지 않거나 쓸 수 없는
프로젝트가 흔하다는 사실은 글이 다루지 않는다.
DORA의 가이드도 지표를 목표로 삼으면 팀이 지표를 조작하려 할 가능성이 높아진다며
굿하트의 법칙을 무시하지 말라고 경고한다.[^dora]
RTF를 곡선이 직선이 되어야 한다는 목표로 쓰는 순간 이 경고가 그대로 적용된다.

### 기능 하나를 1로 세면 크기와 가치가 사라진다

저자가 프로젝트의 목적으로 든 것은 투자한 돈 대비 가능한 한 많은 기능이다.
그러나 RTF는 사흘짜리 기능과 석 달짜리 기능을 똑같이 센다.
기능을 가치 순서가 아니라 쉬운 것부터 만들면
곡선은 더 곧게 보이고 가치는 더 늦게 쌓인다.
곡선이 직선이어야 한다는 요구는 기능 크기가 비슷하다고 가정하는데,
실제 요구 사항은 크기가 크게 갈린다.
또 기능을 지우는 것이 진척인 단계에서는 곡선이 정당하게 떨어진다.
이 글의 해석으로는 RTF는 기능 크기를 정규화한 뒤에야 쓸모 있는 선이 된다.

### 순증가라서 회귀가 가려진다

RTF는 어느 시점에 통과하는 기능의 개수이므로 순증가만 보인다.
글은 곡선이 갑자기 떨어지면 문제의 신호라고 하지만,
새 기능 하나가 늘면서 기존 기능 하나가 깨지면 숫자는 그대로다.
위의 예제를 돌린 결과가 이를 보여 준다.
5일째에 로그인의 잘못된 비밀번호 테스트가 깨졌는데 주문 내역이 통과하기 시작해서
RTF는 3으로 그대로이고, 회귀는 어제는 셌는데
오늘은 못 센 기능을 따로 비교해야 드러났다.
RTF 곡선만 보는 팀은 이 날의 회귀를 놓친다.
글의 곡선은 순증가이고 총 회귀가 아니므로, 기능별 상태 전이를 함께 봐야 한다.
이는 이 문서가 코드를 실행해서 확인한 점이다.

### 곡선 세 장은 실제 자료가 아니라 스케치다

글의 그림은 모두 손으로 그린 것이다.
세 번째 그림은 다른 프로젝트의 RTF 곡선을 보자며
소개되지만 어느 프로젝트인지, 기능이 몇 개였는지,
기간이 얼마였는지가 없다.
이 글은 실제 프로젝트의 측정값을 하나도 제시하지 않으며
곡선은 주장을 설명하는 삽화다.
앞의 두 그림의 세로축은 RTS, 폭포수 그림은 RTF라고 적혀 있다.
글 끝의 각주가 이름 제안을 받아 글을 고쳤다고 하므로
앞의 두 그림은 이전 이름이 남은 것으로 보이며, 이는 이 문서의 추정이다.

저자도 부당하다는 반론을 스스로 꺼낸 뒤 폭포수를 뒤에서
쏘는 것이 자기 일이라고 답한다.
이 글은 논증이라기보다 옹호이고, 폭포수 곡선의 모양은 저자가 그린 것이다.
실제 폭포수 프로젝트가 항상 이 그림처럼
늦게 올라가는지는 자료로 확인되지 않는다.

### 사용자에게 닿았는지, 언제 끝나는지는 재지 않는다

Running은 기능이 통합된 하나의 제품 안에서 돌아간다는 뜻이다.
운영 환경에 배포되어 사용자 손에 닿았다는 뜻이 아니다.
기능이 인수 테스트를 통과해도 배포가 한 달 뒤라면
RTF는 올랐고 사용자는 얻은 것이 없다.
DORA의 소프트웨어 전달 성과 지표는 이 지점을 직접 잰다.
변경 리드타임, 배포 빈도, 실패한 배포의 복구 시간이 처리량이고,
변경 실패율과 배포 재작업 비율이 불안정성이다.[^dora]
RTF가 기능이 맞는지를 잰다면 DORA는 배포가 얼마나 빠르고
안전한지를 재서 서로 다른 질문에 답한다.

또 글의 곡선에는 전체 범위를 나타내는 선이 없다.
지금까지 몇 개가 되었는지는 알려 주지만 몇 개가 남았는지,
언제 끝날지는 알려 주지 않는다.
번업 차트가 보통 완료한 양과 함께 전체 범위의 선을
그려 끝나는 시점을 읽게 하는 것과 다른 점이다.
이는 이 문서가 글의 그림을 보고 한 판단이다.

## 인사이트

### RTF는 목표로 쓰면 무너지고 계기로 쓰면 쓸모가 있다

글 스스로 이 지표의 가장 좋은 쓰임을 보여 준다.
하락하면 팀에게 물어보라는 것이다.
연기 감지기처럼 울리는 지표이며 목표값을 정해 놓고 따라가는 지표가 아니다.
DORA 가이드가 지표 하나로 모든 것을 재려는 시도를 피하고
서로 긴장하는 지표를 함께 쓰라고 권하는 것과 같은 결론이다.[^dora]
실무에서는 RTF 곡선, 기능별 회귀 목록, 변경 실패율을 한 화면에 놓고
세 개가 서로 다른 방향을 가리킬 때를 질문의 시작으로 삼는 것이 안전하다.
이는 이 문서의 제안이다.

### 현대 CI에서 어려운 것은 세는 일이 아니라 기능과 테스트를 잇는 일이다

예제의 핵심 줄은 테스트가 없는 기능은 센다고 하지 않는다는 한 줄이다.
이 한 줄이 Tested를 지킨다.
그런데 현실의 대응표는 쉽게 낡는다.
기능이 바뀌면 테스트가 바뀌고 대응표가 틀어지며,
대응표가 틀어지면 RTF는 정확하게 틀린 숫자를 낸다.
불안정한 테스트는 또 다른 문제다.
예제에서 최근 세 번의 실행에서 모두 통과해야 센다고 `window=3`으로 바꿨더니
6일째 RTF가 4가 아니라 2로 나왔다.
회귀한 로그인이 5일째에 깨졌으므로 연속 통과 조건이 로그인을 세지 않았고,
5일째에 처음 통과한 주문 내역도 연속 통과 횟수가 모자라서 세지 않은 것이다.
불안정한 테스트로 인한 과대 계상을 막는 대가가 새 기능의 인정이 늦어지는 것이다.
이 절충은 이 문서가 코드를 돌려서 본 결과이고
최근 몇 번이 알맞은지는 팀의 테스트 신뢰도에 달려 있다.

### AI가 기능과 테스트를 모두 쓰면 독립이라는 전제가 무너진다

RTF의 Tested는 요구 사항을 주는 고객이 독립적으로 정한 테스트를 뜻한다.
지금은 코딩 에이전트가 기능을 쓰면서 그 기능의 인수 테스트도 쓸 수 있다.
기능과 테스트를 같은 주체가 쓰면 곡선은 매끄럽게 오르는데
그 곡선이 보증하는 것은 줄어든다.
코드와 테스트의 빈틈이 같은 곳에 생기기 때문이다.
이 저장소의 `agentic-coding/black-box-ai-code.md`가
다룬 논쟁의 한 갈래와 같은 문제다.
2004년의 글이 독립이라는 단어를 넣은 이유가 오늘 더 중요해졌다는 점이,
이 글을 지금 읽을 가치가 있게 만드는 가장 분명한 이유다.
이는 이 문서의 해석이다.

### 지표는 사라지고 정기적으로 내놓는 물건만 남았다

저자가 2004년의 곡선에서 2008년의 두 가지 요구로,
2017년의 Increment로 옮겨 온 길은 하나의 방향이다.[^yet-again][^increment]
측정하려던 것은 처음부터 정기적으로 통합되고 돌아가고
검증된 소프트웨어를 내놓고 그것을 보는 일이었다.
곡선은 그 일을 눈에 보이게 하는 수단이었고,
수단이 목표가 되려는 순간을 저자 스스로 피한 셈이다.
따라서 RTF를 도입하려는 팀이 먼저 물어야 할 것은 곡선을 어떻게 그릴지가 아니라
매주 통합된 제품을 누가 어떤 기준으로 확인하느냐다.
그 확인이 있으면 곡선은 덤이고, 없으면 곡선은 장식이다.
