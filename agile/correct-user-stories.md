# 올바른 유저 스토리 쓰기: 고쳐 쓰는 순서와 테스트로 잇는 방법

원문: [Engineering guide to writing correct User Stories](https://sobolevn.me/2019/02/engineering-guide-to-user-stories)

HN 토론: <https://news.ycombinator.com/item?id=19543181> (3점, 0개 댓글)

## 소개

2019년 2월 sobolevn이 쓴 글이다.
저자는 자신의 감사 경험에서 유저 스토리를 잘못 쓰는 팀이 많다고 보고,
흔한 예시 하나를 단계적으로 고쳐 가며 방법을 보여 준다.
글은 세 부분으로 나뉜다.
기본 형식(As a, I want, So that)을 고치는 부분,
행동 주도 개발(BDD)로 검증할 수 있게 다시 쓰는 부분,
유저 스토리를 테스트와 소스 코드와 문서에 연결하는 부분이다.

출발점은 다음 스토리다. 저자는 여기에 적어도 여덟 가지 문제가 있다고 한다.

```text
As a user
I want to receive issue webhooks from Gitlab
So that I can list all current tasks
```

저자는 요구사항이 올바르고 모호하지 않고 완전하고 일관되고 순위가 있고
검증할 수 있고 수정할 수 있고 추적할 수 있어야 한다는 IEEE 830 기준을 든다.
유저 스토리는 이 가운데 몇 가지가 빠지기 쉬워서 고쳐야 한다는 것이 글의 전제다.
이 문서는 그 순서를 따라 무엇을 어떻게 고치는지 정리하고,
글이 말하지 않은 부분을 따로 적는다.

## 동작 방식: 한 스토리를 여섯 번 고치기

글이 보여 주는 수정은 모두 같은 질문의 반복이다. 스토리의
각 줄이 사용자의 말인지, 만드는 쪽의 말인지 묻는다.

| 단계 | 문제                                        | 수정                                                         | 확인 방법                                  |
| ---- | ------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| 1    | 같은 대상을 task와 issue로 섞어 부른다      | 용어집을 두고 도메인 전문가에게 물어 한 단어로 통일한다      | 두 단어가 같은 것인지 전문가에게 묻는다    |
| 2    | “이슈 목록을 본다”는 사용자의 목적이 아니다 | 진짜 이유(진행 상황을 파악하고 추적한다)를 사용자에게 묻는다 | 사용자나 대리인과의 대화                   |
| 3    | “웹훅을 받는다”는 구현 세부다               | 목표(Gitlab 이슈의 최신 정보를 갖는다)로 바꾼다              | 구현이 웹소켓으로 바뀌어도 문장이 유효한가 |
| 4    | 역할이 “user”로 뭉뚱그려져 있다             | 역할을 정하고(예: 건축가) 역할마다 스토리를 나눈다           | 역할별로 같은 목표인지 묻는다              |
| 5    | 검증할 수 없다                              | Gherkin 형식의 시나리오를 붙여 테스트로 쓴다                 | 시나리오를 테스트로 실행한다               |
| 6    | 빠진 경우가 있다                            | 외부 문서로 실패 경우를 찾아 시나리오를 더한다               | 시나리오가 성공과 실패를 모두 덮는가       |

### 용어를 통일한다

“이슈 웹훅을 받는다”와 “현재 작업을
나열한다”가 같은 대상을 말하는지 글은 묻는다.
프로젝트 초기에 용어집을 만들어 도메인 전문가에게 확인하고,
같은 단어가 맥락에 따라 다르게 이해될 수 있다는 점도 챙기라는 것이다.
이 예에서는 전문가가 task가 issue와 같다고 확인해 task를 지운다.

### 사용자의 목적과 만드는 쪽의 목적을 가른다

“이슈를 나열한다”를 사용자가 원할 리 없다는 것이 저자의 관찰이다.
우리는 사용자를 만족시키는 것이 목표이면서도 요구사항에 우리 목적을 섞는다.
사용자가 무엇을 원하는지는 알 수 없으므로 실제 사용자나 대리인에게 묻고,
물을 사람이 없으면 가설을 세우라고 한다.
이 예에서는 의견을 모은 결과 사용자가 원하는 것이 프로젝트의 진행 상황이고,
그래서 외부 서비스에서 이슈 정보를 받아 저장해야 한다는 결론이 나온다.

### 기술 세부를 뗀다

“웹훅을 받는다”를 문자 그대로 원하는 사람은 없다.
내일 웹소켓이나 푸시 알림으로 바뀌어도 사용자의 목표는 그대로이므로,
목표와 기술적 방법을 나눠 목표만 남긴다.
결과는 “Gitlab 이슈에 대한 최신 정보를 갖고 싶다”가 된다.

### 역할을 정한다

글은 프로젝트마다 사용자 유형이 있고,
명시된 유형이 없어 보여도 제품을 쓰는 방식이나 목적에 따라 역할이 생긴다고
말한다.
주니어와 프로젝트 관리자와 건축가가 진행 상황을 같은 방식으로 추적하지는
않으므로, 역할도 용어처럼 정의해 두고 역할마다 스토리를 나눈다.
이렇게 하면 어떤 기능을 누구에게 내놓을지 세밀하게 통제할 수 있다고 한다.
이 예에서 저자는 맥락으로 건축가라고 추측해 `As an architect`로 바꾼다.

## 검증할 수 있게 만들기

여기까지 고친 스토리도 아직 검증되지 않는다.
스토리와 테스트 사이에 대응이 없기 때문이다.
저자의 해법은 BDD와 Gherkin 언어다. 스토리를 Gherkin으로 쓰면
그대로 테스트가 되어 상태를 추적할 수 있다.
업무 요구사항을 구현 세부로 대체하는 것이 아니라 보완한다는 점도 강조한다.

```gherkin
Feature: Tracking issues' progress
  As an architect
  I want to have up-to-date information about Gitlab issues
  So that I can overview and track the issues' progress

  Scenario: new valid issue webhook is received
    Given issue webhook is valid
    When it is received
    Then a new issue is created
```

### 빠진 경우를 찾는다

시나리오를 쓰기 시작하면 한 스토리에 시나리오가 여럿이라는 것이 드러난다.
저자는 “유효한 웹훅이 오면”만 있고 유효하지 않은 웹훅이 오면
어떻게 하는지가 없다는 점을 짚고,
Gitlab 문서를 열어 무엇이 잘못될 수 있는지 찾는다.
결과는 두 가지 실패 경우다. 쓰레기 값이 오는 경우와
인증 토큰이 맞지 않는 경우이고, 두 경우의 처리가 다르다.

```gherkin
Feature: Tracking issues progress
  As an architect
  I want to have up-to-date information about Gitlab issues
  So that I can overview and track the issues' progress

  Scenario: new valid issue webhook is received
    Given issue webhook is valid
    And issue webhook is authenticated
    When it is received
    Then a new issue is created

  Scenario: new invalid issue webhook is received
    Given issue webhook is not valid
    When it is received
    Then no issue is created

  Scenario: new valid unauthenticated issue webhook is received
    Given issue webhook is valid
    And issue webhook is not authenticated
    When it is received
    Then no issue is created
    And webhook data is saved for future investigation
```

저자는 단순해 보이던 스토리가 이제 복잡하게 느껴지는 것을 좋게 본다.
내부 복잡도가 드러나고, 그에 맞춰 개발 과정을 조정할 수 있기 때문이다.

## 우선순위 정하기

건축가가 진행 상황을 파악하는 일이 다른
스토리보다 중요한지는 지금까지 알 수 없다.
저자는 MoSCoW 방법을 권한다. 모든 스토리를 필수(must), 권장(should),
가능(could), 제외(won't) 네 범주로 나눈 표를 문서 어딘가에 따로 둔다.
중요도 역시 사용자에게 물어야 한다고 한다.

| 기능                                         | 우선순위 |
| -------------------------------------------- | -------- |
| 인증된 사용자는 비공개 메시지를 보낼 수 있다 | Must     |
| 건축가는 이슈 진행 상황을 추적한다           | Must     |
| 비공개 메시지가 오면 알림이 있어야 한다      | Should   |
| 여러 메시지 제공자를 지원할 수 있다          | Could    |
| 암호화된 비공개 메시지는 지원하지 않는다     | Won't    |

이 표를 쓰면
Feature 이름을 우선순위 표의 기능 이름에 맞출 수
있다(`Feature: Architects must track issues' progress`).
우선순위 표에서 스토리 파일로 하이퍼링크를 걸어 두면
우선순위가 높은 기능이 먼저 개발된다는 것을 확인할 수 있다고 한다.

## 요구사항과 테스트와 코드와 문서를 잇기

관리하지 않으면
스토리와 테스트와 코드와 문서가 뒤엉켜 어느 부분이
어떤 업무 사용 사례를 맡는지 알 수 없게 된다.
저자는 파이썬으로 연결 방법을 보인다.
유스케이스를 앱이 수행하는 고유한 상위 동작의 집합으로 정의하고,
`usecases` 패키지 하나에 파일마다 클래스(또는 함수) 하나를 둔다.

```python
class CreateNewIssueFromWebhook(object):
    """
    Creates new :term:`issue` from the incoming webhook payloads.

    .. literalinclude:: path/to/your/bdd/user-story/file
      :language: gherkin

    .. versionadded:: 0.2.0
    """

    def __call__(self, webhook_payload: 'WebhookPayload') -> 'Issue':
        # Do something ...
        ...
```

docstring의 `literalinclude`는 Sphinx의 지시어이고,
테스트에 쓰는 같은 Gherkin 파일을 도메인 로직 문서에 그대로 끼워 넣는다.
`:term:`은 `issue`가 그냥 단어가 아니라 이
프로젝트의 용어집에 있는 용어라는 표시다.
저자는 이렇게 하면 테스트와 코드와 문서가 최대한 서로 묶인다고 말하고,
`usecases/` 안의 모든 클래스가 이 지시어를 갖는지 자동으로 검사할 수도 있다고
덧붙인다.
클래스는 스토리를 테스트하는 데도 쓸 수 있다.

## 트레이드오프

### 사용자에게 묻는다는 전제가 모든 수정을 받친다

6단계 중 2단계와 4단계는 사용자나 대리인에게 물어야만 올바른 답이 나오고,
글은 묻지 못하면 가설을 세우라고만 한다.
예시에서도 저자는 건축가라는 역할을 “지적인 추측”으로 정했고,
우선순위는 “여러 건축가와 대화해” 알아냈다고 쓴다.
가설로 쓴 스토리는 틀릴 수 있으므로, 이 문서는 가설에서
나온 스토리를 확인된 스토리와 구별해 표시해 두는 것이 안전하다고
본다. 글이 이를 말하지는 않는다.

### 시나리오를 더하면 스토리가 커진다

빠진 경우를 찾는 과정은 스토리 하나를 시나리오 세 개로 늘린다.
한 스토리의 크기가 커지면 한 번의 개발 주기에 들어가지 않을 수 있다.
글은 이를 “복잡도를 드러내서 좋다”고만 말하고
스토리를 쪼개는 기준은 다루지 않는다.
쪼갤지 말지는 이 문서의 판단이 아니라 팀이 정할 일이며,
시나리오 수가 늘어 우선순위가 다른 경우가 섞이면
스토리를 나누는 쪽이 낫다는 것이 이 문서가 보는 기준이다.

### 문서와 코드의 결합은 도구에 묶인다

마지막 연결 방식은 파이썬과 Sphinx를 전제로 한 한 가지 구현이다.
다른 언어에서는 같은 원리, 곧 한 파일을 테스트의 입력이면서
문서의 일부로 쓰는 것을 각자의 도구로 옮겨야 한다.
이 문서는 그 이식을 시험하지 않았다.

## 함정

- 용어집 없이 task와 issue를 섞어 쓰면
스토리마다 같은 대상이 다른 이름으로 나타나 검증과 추적이 모두 흔들린다.
- “웹훅을 받는다”처럼 기술 이름이 들어간 문장을 목표로 착각한다. 기술이 바뀌면
문장을 다시 써야 한다면 구현 세부다.
- 역할을 “user” 하나로 둔다. 역할이 다르면
같은 기능도 우선순위와 방식이 달라진다.
- 성공 시나리오만 쓴다. 외부 서비스가 있으면
그 서비스의 문서에서 실패 경우를 찾는다.
- 우선순위 표와 스토리 파일이 따로 논다. 링크가 없으면
우선순위가 개발 순서에 반영되는지 확인할 수 없다.

## 체크리스트

- 스토리의 모든 명사가 용어집에 있는가.
- “I want” 줄에서 기술 이름을 지워도 문장이 유효한가.
- “So that” 줄이 사용자에게 직접 확인했거나 가설로 표시된 목적인가.
- 역할이 구체적인가(user가 아닌가).
- 시나리오가 성공과 알려진 실패 경우를 모두 포함하는가.
- 스토리가 우선순위 표의 항목과 이름과 링크로 연결되어 있는가.
- 스토리 파일이 테스트가 실행하는 파일과 같은가.

## 기억할 원칙

### 스토리의 각 줄에 “누구의 말인가”를 묻는다

고치는 여섯 단계는 모두 같은 질문의 변주다.
“이 줄을 사용자가 말할 것인가”에 답이 아니오이면 그 줄은 만드는 쪽의 말이고,
사용자의 목적으로 바꾸거나 구현 세부로 내려야 한다.
이 판별은 도구 없이 지금 쓰는 스토리에 바로 적용할 수 있다.

### 스토리를 쓰기보다 실행하게 만든다

저자의 해법은 형식을 더 정교하게 만드는
것이 아니라 스토리를 테스트로 실행하는 것이다.
검증할 수 없는 요구사항은 시간이 지나면 어긋났는지 알 수 없다.
실패 조건은 이렇다. 시나리오가 테스트로 실행되지 않고
문서로만 남으면 이 방법의 이점이 사라진다.
