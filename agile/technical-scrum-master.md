# 기술형 Scrum Master가 되려면: 코딩 실력이 아니라 시스템의 흐름을 이해하라

영상: [How to become a Technical scrum master](https://www.youtube.com/watch?v=dKfY8HZbthY)

## 소개

AgileProjectAcademy가 2026-10-29에 올린 3분 20초짜리 영상이다.
Scrum Master가 기술적으로 더 알아야 한다고 느낄 때 어디까지 알아야
하는지를 답한다.
영상의 답은 전업 개발자가 될 필요는 없고, 소프트웨어가 어떻게 만들어지는지, 구성 요소가 어떻게 통신하는지, 테스트가 어떻게 이루어지는지, 릴리스가 사용자에게 어떻게 닿는지를 이해하면 된다는 것이다.
목표는 코딩 숙련이 아니라 시스템을 이해하는 것이고,
그 이해가 엔지니어링 팀을 돕는 더 나은 질문을 만든다고 한다.
영상 끝에는 강의를 보고 작은 예제를 연습하라는 권유가 붙는다.

이 글은 영상의 내용을 실무에서 쓸 수 있는 순서로 다시 정리하고,
영상이 말하지 않는 한계를 덧붙인다.
덧붙인 부분은 영상이 아니라 필자의 판단임을 구분해 적는다.

## 한 번의 저장 요청이 지나가는 길

영상은 의료 감사 대시보드(healthcare audit dashboard)를 예로 든다.
사용자가 저장(Save)을 누르면 React 프런트엔드가 API로 요청을 보내고,
Java Spring Boot 백엔드가 요청을 검증하고 업무 규칙을 적용한 뒤
데이터베이스와 통신한다.
응답이 돌아오면 화면이 갱신된다.
문제가 생기면 이 단계 어디에서나 생길 수 있다는 것이 요점이다.

각 기술이 맡는 일은 다음과 같다.

| 기술        | 맡는 일                                    |
| ----------- | ------------------------------------------ |
| React       | 사용자 인터페이스를 만든다                 |
| Java        | 프로그래밍 언어이다                        |
| Spring Boot | 개발자가 백엔드 서비스를 만들게 돕는다     |
| SQL         | 관계형 데이터베이스를 질의한다             |
| REST API    | 서로 다른 구성 요소가 정보를 주고받게 한다 |

영상은 한꺼번에 익힐 필요는 없고 각 구성 요소의 목적부터 이해하라고 한다.

## 테스트의 종류

영상은 테스트를 다섯 가지로 나눈다.
단위 테스트(unit test)는 작은 로직을 검사하고,
통합 테스트(integration test)는 구성 요소가 함께 동작하는지 본다.
API 테스트는 엔드포인트와 응답을 검사하고,
종단 간 테스트(end-to-end test)는 사용자 여정 전체를 다룬다.
회귀 테스트(regression test)는 변경 뒤에도 기존 기능이 그대로
동작하는지 확인한다.

## 전달 파이프라인

코드를 쓰는 것은 한 단계일 뿐이라고 영상은 말한다.
코드 리뷰, 자동 빌드, 테스트, 보안 검사, 배포 승인,
운영 모니터링이 모두 관여할 수 있다.
릴리스가 막히면 던질 질문은 하나이다.
어느 단계에서 실패했고, 그 근거가 무엇인가.

이 질문을 실제로 쓰려면 단계마다 어떤 근거를 볼 수 있는지 알아야 한다.
다음 표는 영상에 없는, 필자가 덧붙인 예이다.

| 단계          | 실패했다는 근거가 되는 것                   |
| ------------- | ------------------------------------------- |
| 코드 리뷰     | 풀 리퀘스트의 대기 시간과 미해결 코멘트     |
| 자동 빌드     | CI 빌드 로그의 실패 항목                    |
| 테스트        | 실패한 테스트 이름과 어느 종류의 테스트인지 |
| 보안 검사     | 검사 도구의 보고서와 예외 승인 기록         |
| 배포 승인     | 승인 요청이 머문 시간과 담당자              |
| 운영 모니터링 | 배포 직후의 오류율과 알림 기록              |

## Scrum 이벤트에서 쓰는 방법

영상은 앞의 지식을 Scrum 이벤트별로 적용한다.

| 이벤트                         | 하는 일                                               |
| ------------------------------ | ----------------------------------------------------- |
| 백로그 정제(refinement)        | API 의존성, 데이터 요구 사항, 통합 위험을 분명히 한다 |
| 스프린트 계획(sprint planning) | 의존성과 테스트 데이터를 쓸 수 있는지 확인한다        |
| 데일리 스크럼(daily Scrum)     | 막힌 곳이 눈에 보이게 한다                            |
| 스프린트 리뷰(sprint review)   | 동작하는 기능에 집중한다                              |
| 회고(retrospective)            | 지연과 재작업이 반복되는 원인을 찾는다                |

## 학습 순서

영상이 권하는 순서는 다음과 같다.
먼저 Java의 기초와 객체지향 프로그래밍을 배운다.
그다음 Spring Boot, REST API, SQL을 배운다.
이어서 테스트, Git, 지속적 통합과 전달(continuous integration and delivery,
CI/CD)을 살핀다.
마지막으로 로그, 배포, 클라우드 컴퓨팅, 마이크로서비스의 기초를 배운다.
큰 그림을 먼저 이해하고, 준비가 되면 작은 예제로 연습하라고 한다.

## 비평

### 로드맵은 한 가지 기술 스택에 묶여 있다

영상의 예제도 로드맵도 React, Java, Spring Boot, SQL이다.
그래서 학습 순서의 첫 줄이 Java 기초이다.
그러나 담당 팀이 다른 스택을 쓴다면 이 순서는 맞지 않는다.
영상이 실제로 주는 보편적인 내용은 앞쪽의 원칙, 곧 구성 요소의 목적과 연결 방식을 이해하라는 것이고, Java부터 시작하라는 부분은 팀에 따라 바뀌는 선택이다.
필자의 판단으로는 로드맵의 첫 단계는 언어가 아니라 자기 팀이 쓰는 스택을
확인하는 일이다.

### 영상은 기술 지식이 역할을 어떻게 바꾸는지 다루지 않는다

기술을 더 알면 Scrum Master가 팀에 더 나은 질문을 할 수 있다는 것이
영상의 전제이다.
그러나 기술 지식이 늘면 질문이 답으로 바뀌기 쉽다.
Scrum Master가 해법을 제안하기 시작하면 팀이 스스로 해결하는 것을 막을 수 있다.
영상은 이 위험을 언급하지 않고, 질문으로 머무르는 방법도 알려 주지 않는다.
이는 필자의 추정이며, 반대로 기술적 이해가 있어야 팀이 하는 말이 들린다는 이점도
분명히 있다.

### 효과를 확인할 기준이 없다

영상은 어떻게 알 수 있는지, 곧 기술형이 되었다는 것이 무엇으로 드러나는지 말하지 않는다.
짧은 영상이라 이해할 수 있지만, 이 글을 따라 공부하는 사람은 자신의 수준을
가늠할 근거가 필요하다.
아래 체크리스트가 그 한 가지 시도이다.

## 체크리스트

다음 질문에 예 또는 아니오로 답할 수 있으면 영상이 말한 이해에 가까운 것이다.
이 항목들은 영상의 내용을 질문으로 바꾼 것이다.

- 팀의 제품에서 사용자가 버튼을 눌렀을 때 요청이 어떤 구성 요소를 거치는지 그릴 수 있는가.
- 팀이 쓰는 테스트가 다섯 종류 가운데 어디에 속하는지 구별할 수 있는가.
- 릴리스가 막혔을 때 어느 단계에서 실패했는지 근거와 함께 말할 수 있는가.
- 백로그 정제에서 API 의존성과 통합 위험을 물어본 적이 있는가.
- 스프린트 계획에서 테스트 데이터를 쓸 수 있는지 확인했는가.
- 회고에서 반복되는 지연의 원인을 단계 이름으로 말하고 있는가.

## 기억할 원칙

### 질문의 품질은 흐름을 이해하는 데서 나온다

영상의 중심 문장은 모든 줄의 코드를 쓸 필요는 없고, 흐름을 이해하고 용어를 배우고 더 나은 질문을 하라는 것이다.
막힌 곳을 찾는 질문은 어느 단계에서 실패했고 근거가 무엇이냐는 형태로 짧게
줄일 수 있다.
이 질문은 팀의 일을 대신하지 않으면서 막힌 곳을 눈에 보이게 한다.
단, 질문이 답으로 바뀌지 않도록 하는 것은 듣는 쪽의 몫이 아니라 질문하는
사람의 습관이다.
