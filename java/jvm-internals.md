# JVM 안쪽 여행: 클래스 로딩, 메모리와 GC, JIT로 따라가는 자바 코드의 실행

영상: [JVM 안쪽 여행 전편 합본 | 자바 코드는 어떻게 실행될까 (1~3편)](https://www.youtube.com/watch?v=KksqbjC-rTQ)

## 소개

Codedeck 채널이 2026년 10월 25일에 올린 8분 35초짜리 합본 영상이다.
자바 코드 한 줄이 JVM 안에서 거치는 여정을 세 편으로 나눠 보여 준다.
1편은 바이트코드와 클래스 로딩, 2편은 메모리와 GC, 3편은 실행 엔진과 JIT다.
설명란은 모든 수치와 출력을 Temurin OpenJDK 21에서 직접 실행해 확인한 실측이라고
밝힌다.

영상의 첫 질문은 자바가 컴파일 언어인지 인터프리터 언어인지다.
답은 둘 다이고, 자바 코드는 실행되기까지 두 번 번역된다.
처음에는 `javac`가 소스를 바이트코드로, 실행 중에는 JIT 컴파일러가 뜨거운 코드를
기계어로 번역한다.
JVM은 클래스 로더, 메모리(런타임 데이터 영역), 실행 엔진의 세 부품으로 나뉜다고
영상은 전체 지도를 그린다.

## 동작 방식

### 1편: 코드가 기계에 실리기까지

예제는 음료 가격과 수량을 곱해 합계를 내는 카페 주문 프로그램이다.
컴파일하면 클래스 파일 두 개가 나오고, 영상에서는 각각 408바이트와
1,024바이트다.
파일 안에 든 것은 기계어가 아니라 JVM만 읽는 중간 언어인 바이트코드이며,
`javap`로 열면 `getfield`로 값을 꺼내고 `imul`로 곱하고 `ireturn`으로 돌려주는
명령이 보인다.

실행하면 이 작은 프로그램 하나로 클래스 554개가 로딩된다.
자바의 기본 클래스가 먼저 오고 우리 클래스는 나중에 온다.
로딩 절차는 로딩, 연결, 초기화 순서이고 연결은 다시 검증, 준비, 해결로 나뉜다.
로더는 부트스트랩, 플랫폼, 애플리케이션 셋이며 요청을 받으면 먼저 부모 로더에게
묻는 것이 규칙이다.
클래스 파일이 특정 컴퓨터가 아니라 JVM에 맞춰 만들어지므로 같은 파일을 운영
체제가 다른 JVM에 그대로 넣을 수 있고, 한 번 쓰면 어디서나 실행된다는 약속이
여기서 나온다.

### 2편: 객체는 어디에 살고 누가 치우는가

런타임 데이터 영역은 다섯 구역이다.
메서드 영역(클래스 정보), 힙(객체), 스택(메서드 호출), PC 레지스터(현재 실행
위치), 네이티브 메서드 스택이다.
메서드를 호출할 때마다 전용 작업 공간인 프레임이 스택에 쌓이고 끝나면 빠진다.
그래서 재귀가 끝없이 이어지면 프레임이 쌓여 `StackOverflowError`가 나며,
설명란에 따르면 영상의 기본 설정 실측은 재귀 깊이 20,552다.

`new`로 만든 객체와 배열은 모두 힙에 산다.
`main`의 프레임에는 객체 자체가 아니라 객체를 가리키는 참조만 있어서, 스택의
화살표가 힙 객체를 가리키는 그림이 기본 풍경이다.
힙을 32MB로 제한하고 1MB 배열을 쌓으면 `OutOfMemoryError`로 죽는다.

GC의 기준은 도달 가능성이다.
스택이나 메서드 영역에서 출발해 참조를 타고 갈 수 있으면 살리고 갈 수 없으면
쓰레기다.
객체 대부분이 만들어진 직후에 죽는다는 세대 가설에 따라 힙을 젊은 세대와 늙은
세대로 나누고, 젊은 쪽을 자주 치우는 것이 마이너 GC, 전체를 치우는 것이 메이저
GC다.
실측은 최근 주문 10만 건만 들고 나머지는 버리는 프로그램으로 주문 2천만 건을
처리해 Young GC가 30번 돈 것으로, 대부분이 젊어서 죽는다는 가설과 맞는다.
청소 중에는 프로그램이 잠깐 멈춘다.

### 3편: 돌수록 빨라지는 실행 엔진

실행 엔진의 기본 모드는 인터프리터로, 바이트코드를 한 줄씩 읽어 바로 실행한다.
JVM은 스택 머신이어서 계산도 스택으로 한다.
`iadd`는 두 값을 스택에서 꺼내 더한 뒤 결과를 다시 올리며, 모든 연산이 뽑고
계산하고 넣는 리듬으로 돈다.
인터프리터는 시작이 빠르지만 매번 해석하느라 느리다.

그래서 JVM은 실행하면서 메서드 호출 횟수와 루프 반복 횟수를 센다.
자주 도는 뜨거운 코드가 핫스팟이며 JIT 컴파일러가 이를 기계어로 번역해 저장해
둔다.
번역에는 빠르고 가볍게 하는 단계와 시간은 걸려도 깊게 최적화하는 단계가 있고,
자주 불리는 작은 메서드는 부르는 자리에 코드를 끼워 넣는 인라이닝으로 호출
비용을 없앤다.
합계 메서드를 라운드마다 3,000번 부르고 세 번 측정해 가장 빠른 값을 그린 실측은
1라운드 약 12ms, 2라운드 약 4ms, 이후 약 3ms로 안정된다.
중간에 JIT가 기계어로 바꿔치기해 같은 코드가 4배 가까이 빨라진 것이다.

## 직접 확인하기

영상의 숙제는 자신의 코드로 `javap`를 한 번 돌려 보는 것이다.
아래는 같은 흐름을 재현하는 최소 실험이며 JDK 21에서 확인하는 것을 전제로 한다.

```java
// Order.java: 곱셈 한 줄이 바이트코드로 어떻게 번역되는지 본다
public class Order {
    int price = 2750;
    int qty = 2;

    int total() {
        return price * qty;
    }

    public static void main(String[] args) {
        System.out.println(new Order().total());
    }
}
```

```bash
javac Order.java
javap -c -p Order                 # total()의 getfield, imul, ireturn 확인
java -Xlog:class+load Order | wc -l   # 로딩되는 클래스 수 확인
```

스택과 힙의 한계는 다음 코드로 본다.

```java
// Limits.java: 인자로 재귀 깊이 측정(stack) 또는 힙 한계 측정(heap)을 고른다
import java.util.ArrayList;
import java.util.List;

public class Limits {
    static int depth = 0;

    static void recurse() {
        depth++;
        recurse();
    }

    public static void main(String[] args) {
        if (args[0].equals("stack")) {
            try {
                recurse();
            } catch (StackOverflowError e) {
                System.out.println("깊이 " + depth);
            }
        } else {
            List<byte[]> keep = new ArrayList<>();
            try {
                while (true) {
                    keep.add(new byte[1024 * 1024]);
                }
            } catch (OutOfMemoryError e) {
                System.out.println("1MB 배열 " + keep.size() + "개에서 실패");
            }
        }
    }
}
```

```bash
javac Limits.java
java Limits stack                    # 기본 스택 크기에서의 깊이
java -Xss256k Limits stack           # 스택을 줄이면 깊이도 줄어든다
java -Xmx32m Limits heap             # 힙을 32MB로 제한
```

JIT의 워밍업은 다음 프로그램으로 본다.

```java
// Warmup.java: 같은 메서드를 라운드마다 반복 호출해 시간이 줄어드는지 본다
public class Warmup {
    static int sum(int n) {
        int s = 0;
        for (int i = 0; i < n; i++) {
            s += i * 3;
        }
        return s;
    }

    public static void main(String[] args) {
        int sink = 0;
        for (int round = 1; round <= 10; round++) {
            long best = Long.MAX_VALUE;
            for (int rep = 0; rep < 3; rep++) {   // 세 번 재서 가장 빠른 값을 쓴다
                long t = System.nanoTime();
                for (int i = 0; i < 3000; i++) {
                    sink += sum(10_000);
                }
                best = Math.min(best, System.nanoTime() - t);
            }
            System.out.printf("라운드 %d: %.2f ms%n", round, best / 1e6);
        }
        System.out.println(sink);   // 결과를 쓰지 않으면 JIT가 계산을 지울 수 있다
    }
}
```

```bash
javac Warmup.java
java Warmup                          # 라운드가 갈수록 빨라지는지 확인
java -Xint Warmup                    # JIT를 끄면 빨라지지 않는다
java -XX:+PrintCompilation Warmup | head -50   # 번역되는 시점 관찰
java -Xlog:gc Order                  # GC 로그 형식 확인
```

GC 로그는 `-Xlog:gc`로 본다.
영상의 숫자는 설명란에 따른 Temurin OpenJDK 21의 값이므로 자신의 환경에서는
다르게 나온다.

## 함정

### 워밍업 실측은 측정 방식에 쉽게 속는다

영상은 세 번 재서 가장 빠른 값을 쓰지만, 이런 손으로 만든 측정은 JIT가 결과를
쓰지 않는 계산을 지우거나 측정 구간 안에서 컴파일이 일어나는 문제에 약하다.
위 예제가 결과를 `sink`에 모으고 마지막에 출력하는 이유다.
진지한 성능 측정이라면 JMH 같은 도구가 필요하다.
이는 이 문서의 해석이다.

### 영상의 숫자는 한 환경의 값이다

재귀 깊이 20,552나 12ms에서 3ms는 한 JDK와 한 머신의 값이다.
스택 크기, 프레임의 크기, JIT 단계는 JDK 버전과 옵션에 따라 달라지므로 비율과
경향을 읽는 것이 맞다.

### 마이너 GC가 있다고 정지가 없는 것은 아니다

영상은 청소 중 프로그램이 잠깐 멈춘다고 말한다.
이 정지는 젊은 세대만 치우는 마이너 GC에서도 생기며, 정지 시간이 서비스 지연
목표를 넘는지는 GC 종류와 힙 크기에 따라 다르다.
영상은 GC 알고리즘의 종류별 차이까지는 다루지 않는다.

## 체크리스트

- 자신의 클래스 하나를 `javap -c`로 열어 한 줄이 어떤 명령이 되는지 확인했는가.
- 같은 클래스 파일이 다른 운영 체제의 JVM에서도 도는지 알고 있는가.
- 스택에 있는 것과 힙에 있는 것을 구분해 설명할 수 있는가.
- 재귀 깊이 문제와 힙 고갈 문제를 서로 다른 오류로 구분해 진단할 수 있는가.
- `-Xlog:gc` 출력에서 마이너 GC와 메이저 GC를 구분해 읽을 수 있는가.
- 성능 측정 코드의 결과가 JIT에 의해 지워지지 않도록 쓰고 있는가.
- 측정은 워밍업 이후의 값을 쓰고 있는가.

## 기억할 원칙

### 자바의 성능은 시작 시점이 아니라 도달한 상태를 봐야 한다

같은 코드가 돌수록 빨라지므로 짧게 한 번 재고 느리다고 결론짓는 것은 인터프리터
구간만 본 것이다.
반대로 서버가 한 번 데워진 뒤의 값이 곧 모든 요청의 지연은 아니므로, 시작 직후
구간과 안정 구간을 나눠 보는 습관이 필요하다.
이는 이 문서의 해석이다.

### 메모리 오류는 어느 구역이 찼는지부터 구분한다

스택 오버플로와 힙 고갈은 원인도 해법도 다르다.
스택은 호출 깊이의 문제이고 힙은 도달 가능한 객체가 쌓이는 문제라서, 오류 이름을
보고 구역을 먼저 가르는 것이 진단의 출발점이다.
이는 이 문서의 해석이다.
