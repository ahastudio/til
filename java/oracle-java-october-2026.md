# Oracle Java 2026년 10월 보안 업데이트: IPA의 조기 적용 권고와 실제로 올릴 버전

원문: [Oracle Java の脆弱性対策について(2026年10月) | 情報セキュリティ | IPA 独立行政法人 情報処理推進機構](https://www.ipa.go.jp/security/security-alert/2026/1021-jre.html)

## 지금 해야 할 일

### 무엇이 위험한가

Oracle Java SE를 쓰는 모든 환경이 대상이다.
IPA는 취약점이 악용되면 애플리케이션이 비정상 종료되거나 공격자가 컴퓨터를 제어하는 피해가 생길 수 있다고 알리고, 영향이 크므로 서둘러 업데이트를 적용하라고 권한다.

Oracle의 10월 보안 패치 묶음(Critical Patch Update) 권고문에 따르면 Java SE에 새로 들어간 보안 패치는 55건이다.
그중 49건은 사용자 인증 없이 네트워크로 악용될 수 있다.[^oracle-cpu]
이 권고문의 위험 표를 직접 세어 보면 CVSS 3.1 기준 최고 점수는 7.5이고, 9.0 이상인 치명적(Critical) 등급은 없다.[^oracle-cpu]
그러나 높은 점수가 없다는 것이 안전하다는 뜻은 아니다.

서버라서 괜찮다고 판단하면 안 된다.
Oracle은 항목마다 영향 조건을 세 가지 주석으로 나눈다.
첫 번째 주석 12건은 인터넷에서 받은 신뢰할 수 없는 코드를 샌드박스에서 실행하는 클라이언트(Java Web Start, 애플릿)에만 해당하고, 신뢰하는 코드만 실행하는 서버에는 해당하지 않는다.
두 번째 주석 31건은 해당 컴포넌트의 API에 웹 서비스처럼 데이터를 공급하는 경로로도 악용할 수 있고 샌드박스 클라이언트에도 해당한다.
세 번째 주석 12건은 애플릿 없이 웹 서비스 같은 경로로 API에 데이터를 공급하는 것만으로 악용된다.[^oracle-cpu]
즉 55건 중 43건은 서버 애플리케이션이 외부 입력을 API로 넘기는 구조라면 해당될 수 있다.

### 오늘 할 일

우선순위는 이 글의 판단이며 IPA나 Oracle이 정한 순서가 아니다.

1. 사용 중인 Java가 어느 벤더의 어느 버전인지 확인한다. 이 글의 `확인하기` 절 스크립트를 쓰면 된다.
2. Oracle Java라면 아래 표의 수정 버전으로 올린다.
3. 올린 뒤 Java 프로세스를 모두 재시작한다. 실행 중인 프로세스는 이전 런타임을 계속 쓴다.
4. 외부 입력을 받는 서버, 그중에서도 인터넷에 노출된 서비스부터 올린다.
5. 컨테이너 이미지, 빌드 서버, IDE, 번들로 포함된 런타임까지 설치된 Java를 모두 찾는다.
6. Oracle Java가 아니라면(OpenJDK 계열 배포판 등) 해당 벤더가 낸 공지의 수정 버전으로 올린다.
7. 상용으로 쓴다면 라이선스를 먼저 확인한다. IPA는 2019년 4월 16일 이후 릴리스부터 라이선스가 바뀌었다고 안내한다.

| 사용 중인 라인 | 올릴 버전 (Oracle Java) |
| -------------- | ----------------------- |
| 8              | 8u511                   |
| 11             | 11.0.33                 |
| 17             | 17.0.21                 |
| 21             | 21.0.13                 |
| 25             | 25.0.5                  |
| 27             | 27.0.1                  |

이 표는 Oracle이 JDK 27 릴리스 노트에 실은 보안 기준선(security baseline)이다.[^jdk27]
JDK 26은 표에 없다.
JDK 26의 릴리스 노트 페이지에서 확인되는 가장 최근 버전은 8월 18일의 26.0.2.1이다.[^jdk26]
이번 갱신에서 26.0.2는 한 건에만 해당한다.
JDK 26을 쓴다면 27.0.1로 옮기는 것이 이 글의 판단이며, 26용 수정이 따로 나왔는지는 확인하지 못했다.

### IPA 공지의 버전 목록을 올릴 버전으로 읽으면 안 된다

IPA는 대상으로 Oracle Java SE 8 Update 503, 11.0.32.1, 17.0.20.1, 21.0.12.1, 25.0.4.1, 26.0.2, 27 등을 나열한다.
이 번호들은 이번 업데이트로 고쳐지는 대상, 즉 업데이트 전 버전이다.
Oracle 권고문의 같은 목록 열 제목이 영향받는 지원 버전(Supported Versions Affected)이고,[^oracle-cpu] 보안 기준선은 8u511, 11.0.33, 17.0.21, 21.0.13, 25.0.5, 27.0.1이기 때문이다.[^jdk27]
IPA 목록과 같은 버전이면 아직 대상이다.

## 요약

IPA는 2026년 10월 21일에 Oracle Java의 보안 업데이트가 일본 시간 같은 날 공개되었다고 알렸다.
이 취약점이 악용되면 애플리케이션이 비정상 종료되거나 공격자가 컴퓨터를 제어하는 등 여러 피해가 생길 수 있고, 영향이 크므로 서둘러 적용하라는 것이 핵심이다.
공지는 필요한 정보가 생기면 그때마다 페이지를 갱신하겠다고 밝힌다.

대상은 지원되는 Oracle 제품으로, Oracle Java SE 27, 26.0.2, 25.0.4.1, 21.0.12.1, 17.0.20.1, 11.0.32.1, 8 Update 503, 8 Update 503-perf다.
대응은 Oracle이 제공하는 최신 버전으로 업데이트하는 것이고, Oracle의 Java Downloads 페이지에서 설치한다.
IPA는 Oracle이 2019년 4월 16일 이후 Java 릴리스의 라이선스를 바꾸었다고 안내하며, 특히 상용으로 쓰는 조직은 라이선스를 확인하고 벤더의 유료 지원을 받는 등 적절히 대응하라고 한다.
라이선스와 지원 내용은 IPA가 알지 못하므로 Oracle의 공개 정보를 보거나 Oracle에 직접 문의하라고 덧붙인다.

참고 정보로는 Oracle의 Critical Patch Update 권고문, 소프트웨어가 최신인지 확인하는 MyJVN 버전 체커, IPA의 주의 환기 서비스 icat for JSON을 안내한다.
공지는 개별 시스템과 환경에 대한 질문에는 답하지 못할 수 있으니 제품 벤더에 문의하라고 적는다.

## 동작 방식

IPA 공지는 취약점의 종류를 설명하지 않는다.
세부 내용은 Oracle 권고문의 Java SE 위험 표에 있다.
표에는 55건이 CVE 번호, 컴포넌트, 프로토콜, 인증 없는 원격 악용 여부, CVSS 점수, 영향받는 버전과 함께 실려 있다.[^oracle-cpu]

### 점수와 컴포넌트

55건을 점수대로 세면 7.0 이상이 3건, 4.0에서 6.9까지가 38건, 4.0 미만이 14건이다.
7.0 이상인 3건은 JavaFX의 WebKitGTK 컴포넌트 `CVE-2026-43660`(7.5), Java 플러그인 `CVE-2026-91484`(7.5), 2D 컴포넌트 `CVE-2026-91415`(7.0)다.[^oracle-cpu]
`CVE-2026-91484`는 로컬에서만 악용되고 Java 8에만 해당한다.
`CVE-2026-91415`는 26.0.2를 뺀 이번 갱신 대상 버전 전체에 해당하는 네트워크 취약점이다.[^oracle-cpu]

컴포넌트별로는 Networking이 9건으로 가장 많고, JGSS, Security, Compiler가 각각 4건이다.[^oracle-cpu]
서버 쪽에서 외부 입력을 다루는 라이브러리와 암호·인증 관련 컴포넌트가 많다는 뜻이다.
Oracle은 CVSS 점수가 애플릿이나 Java Web Start를 쓰는 사용자가 관리자 권한을 가졌다는 가정(Windows에서 일반적)으로 계산되었고, 관리자가 아니면 영향 점수가 낮아진다고 적는다.[^oracle-cpu]

### 영향 조건 세 갈래

| 주석   | 건수 | 인증 없이 원격 | 영향 조건                                                                               |
| ------ | ---- | -------------- | --------------------------------------------------------------------------------------- |
| 주석 1 | 12   | 9              | 신뢰할 수 없는 코드를 샌드박스로 실행하는 클라이언트. 신뢰 코드만 쓰는 서버는 해당 없음 |
| 주석 2 | 31   | 28             | API에 데이터를 공급하는 웹 서비스 등과 샌드박스 클라이언트 양쪽                         |
| 주석 3 | 12   | 12             | 애플릿 없이 웹 서비스 등으로 API에 데이터를 공급하는 경로                               |

표는 Oracle 권고문의 Java SE 위험 표 55행을 주석별로 직접 센 결과다.[^oracle-cpu]
서버만 운영한다면 주석 1을 뺀 43건이 관련될 수 있다.

버전별 건수는 위험 표의 영향 버전 열을 직접 세어 얻은 값이다.[^oracle-cpu]
26.0.2에 해당하는 것은 Compiler 컴포넌트의 `CVE-2026-101737` 한 건이다.[^oracle-cpu]

## 업데이트하기

설치 방법은 Oracle Java Downloads 페이지에서 해당 라인의 최신 버전을 내려받는 것이다.
패키지 관리자나 SDKMAN 같은 도구로 설치했다면 그 도구로 올린다.
올린 뒤에는 Java를 쓰는 프로세스를 모두 재시작해야 한다.

IPA의 참고 정보에 있는 MyJVN 버전 체커는 소프트웨어가 최신인지 간단한 조작으로 확인하는 도구다.
이름에 .NET이 붙어 있어 Windows 클라이언트용으로 보이지만, 서버와 컨테이너에서 쓸 수 있는지는 확인하지 못했다.

## 확인할 값

| 라인 | 수정 버전 (`java.version`) | 근거                       |
| ---- | -------------------------- | -------------------------- |
| 8    | `1.8.0_511`                | 8u511 (Oracle 보안 기준선) |
| 11   | `11.0.33`                  | Oracle 보안 기준선         |
| 17   | `17.0.21`                  | Oracle 보안 기준선         |
| 21   | `21.0.13`                  | Oracle 보안 기준선         |
| 25   | `25.0.5`                   | Oracle 보안 기준선         |
| 27   | `27.0.1`                   | Oracle 보안 기준선         |

Oracle의 기준선 표는 JRE 보안 기준선을 8의 경우 `1.8.0_511-b09`, 11은 `11.0.33+9`처럼 빌드 번호까지 적는다.[^jdk27]
`java.version` 속성에는 보통 빌드 번호가 빠지므로 위 표는 그 앞부분만 적었다.

## 확인하기

다음 스크립트는 `java` 명령이 보고하는 벤더와 버전을 위 표와 비교한다.
Oracle 빌드가 아니면 버전 번호를 비교하지 않는다.
다른 벤더는 자체 번호 체계를 쓰기 때문이다.

```bash
#!/usr/bin/env bash
# 사용법: check-java.sh [java 실행 파일] [--oracle]
# --oracle: 벤더 표시와 무관하게 Oracle 기준선과 비교한다.
set -euo pipefail

JAVA="${1:-java}"
FORCE_ORACLE=0
[ "${2:-}" = "--oracle" ] && FORCE_ORACLE=1

props="$("$JAVA" -XshowSettings:properties -version 2>&1)"
vendor="$(printf '%s\n' "$props" | sed -n 's/^ *java\.vendor = //p' | head -1)"
version="$(printf '%s\n' "$props" | sed -n 's/^ *java\.version = //p' | head -1)"

echo "java.vendor  = $vendor"
echo "java.version = $version"

# 라인별 수정 버전. Java 8은 java.version이 1.8.0_NNN 형태다.
case "$version" in
  1.8.0_*)  major=8;  fixed="1.8.0_511" ;;
  11.*)     major=11; fixed="11.0.33" ;;
  17.*)     major=17; fixed="17.0.21" ;;
  21.*)     major=21; fixed="21.0.13" ;;
  25.*)     major=25; fixed="25.0.5" ;;
  27.*)     major=27; fixed="27.0.1" ;;
  26.*)     echo "JDK 26: 27.0.1로 옮기는 것을 검토한다."; exit 2 ;;
  *)        echo "이 표에 없는 라인이다. 지원되는 라인으로 올려야 한다."; exit 2 ;;
esac

case "$vendor" in
  *Oracle*) ;;
  *)
    if [ "$FORCE_ORACLE" -eq 0 ]; then
      echo "Oracle 빌드가 아니다. 이 벤더의 보안 공지로 수정 버전을 확인한다."
      exit 3
    fi ;;
esac

# sort -V로 버전 순서를 비교한다. 수정 버전이 더 작거나 같으면 통과다.
lowest="$(printf '%s\n%s\n' "$fixed" "$version" | sort -V | head -1)"
if [ "$lowest" = "$fixed" ]; then
  echo "OK   $major 라인: $version >= $fixed"
else
  echo "FAIL $major 라인: $version < $fixed (수정 버전으로 올려야 한다)"
  exit 1
fi
```

이 글을 쓴 컴퓨터의 Java는 `Corretto-25.0.3.9.1` 빌드다.
스크립트를 그대로 돌리면 Oracle 빌드가 아니라는 안내가 나오고, `--oracle`을 붙여 기준선과 비교하면 25.0.3이 25.0.5보다 낮다는 `FAIL`이 나온다.
다만 Corretto의 수정 버전은 Oracle의 번호와 같다고 볼 수 없으므로 이 `FAIL`은 스크립트 동작을 확인하는 용도일 뿐 판정이 아니다.

## 트레이드오프

### 서버라서 괜찮다는 판단은 가장 위험하다

주석 1만 읽으면 서버는 영향이 없다는 결론이 나온다.
그러나 55건 중 43건은 서버에서 웹 서비스가 API에 데이터를 넘기는 경로를 다루는 주석 2와 3이다.
서버에서 Java가 외부 입력을 파싱하거나 네트워크 통신을 하는 이상, 애플릿을 쓰지 않는다는 이유로 건너뛰는 것은 근거가 약하다.
반대로 모든 서버를 즉시 올리는 데는 재시작과 호환성 확인이라는 비용이 든다.
그래서 인터넷에 노출된 서비스부터 올리고 내부 전용 시스템은 일정을 잡는다.

### 최신 라인으로 옮기는 비용

JDK 26은 이번 갱신에서 수정 버전이 확인되지 않아 27.0.1로 옮기는 것이 이 글의 판단이다.
27.0.1로 옮기면 취약점은 해소되지만, 라인이 바뀌므로 호환성과 프레임워크 지원을 따로 확인해야 한다.
같은 LTS 안의 마이너 업데이트(예: 21.0.12.1에서 21.0.13)는 위험이 작지만 라인 이전은 그렇지 않다.
위험이 큰 쪽은 업데이트를 미루는 것이 아니라 확인 없이 라인을 바꾸는 것이다.

### 라이선스 확인이 업데이트보다 늦어질 수 있다

IPA가 별도로 안내할 만큼 Oracle Java는 라이선스 조건이 있다.
상용으로 쓰는 조직이 라이선스를 확인하느라 업데이트가 늦어지면 그 기간은 노출 기간이 된다.
라이선스 확인과 업데이트는 서로 다른 팀의 일이므로 병렬로 진행해야 한다.
라이선스 조건의 세부는 IPA가 알지 못한다고 밝혔으므로 이 글에서도 판단하지 않는다.

## 함정

### 설치된 Java는 하나가 아니다

`java -version`이 보여 주는 것은 PATH에서 첫 번째로 잡히는 Java 하나다.
빌드 서버, IDE에 포함된 런타임, 애플리케이션이 번들로 넣은 JRE, 컨테이너 이미지 안의 Java는 따로 있다.
이들이 모두 대상일 수 있으므로 하나만 올리고 끝났다고 보면 안 된다.

### 수정 버전의 번호 체계가 벤더마다 다르다

이 글의 표는 Oracle Java 기준이다.
다른 배포판은 같은 취약점을 고쳐도 번호가 다를 수 있다.
IPA 공지는 Oracle 제품만 대상으로 적었으므로, 다른 벤더의 대응은 해당 벤더의 공지로 확인해야 한다.

### 재시작하지 않은 프로세스는 그대로다

파일을 교체해도 실행 중인 JVM은 이전 런타임을 메모리에 들고 있다.
업데이트 뒤에 프로세스를 재시작하지 않으면 보호되지 않는다.
장기 실행 서비스와 데몬은 특히 이 점을 놓치기 쉽다.

### 공지가 갱신될 수 있다

IPA는 추가할 정보가 있으면 이 페이지를 갱신하겠다고 적었다.
이 글은 2026년 10월 21일 게시본을 기준으로 하므로, 적용 전에 원문과 Oracle 권고문의 갱신 여부를 다시 확인해야 한다.

## 체크리스트

- 사용 중인 Java의 벤더와 `java.version`을 확인했는가?
- Oracle Java라면 라인별 수정 버전 이상인가?
- Oracle Java가 아니라면 해당 벤더의 공지를 확인했는가?
- IPA 목록의 버전과 같다면 아직 취약한 버전으로 판단했는가?
- 업데이트 뒤 Java 프로세스를 모두 재시작했는가?
- 컨테이너 이미지, 빌드 서버, IDE, 번들 런타임의 Java도 찾았는가?
- 인터넷에 노출된 서버를 먼저 올렸는가?
- JDK 26을 쓴다면 27.0.1로 옮길 계획이 있는가?
- 상용으로 쓴다면 라이선스를 확인했는가?

## 기억할 원칙

### 대상 버전 목록은 올릴 버전이 아니다

보안 공지의 버전 표는 영향받는 버전일 수도, 수정된 버전일 수도 있다.
이 사례에서 IPA와 Oracle 권고문의 목록은 업데이트 전 버전이었고, 올릴 버전은 다른 페이지의 기준선 표에 있었다.
목록에 있는 버전을 그대로 설치하면 고쳐지지 않은 버전을 설치하는 것이다.

### 점수가 높지 않아도 노출 경로가 넓으면 우선순위가 높다

가장 높은 점수가 7.5라는 사실보다, 55건 중 49건이 인증 없이 네트워크로 악용될 수 있다는 사실이 대응 순서를 정한다.
점수는 한 건의 심각도를 말하고, 노출 경로는 공격자가 닿을 수 있는지를 말한다.
둘은 서로 다른 질문이므로 우선순위를 정할 때는 둘 다 봐야 한다.
