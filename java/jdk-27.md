# JDK 27 정식 출시 — 기본값이 된 것들과 프리뷰의 진척

원문: [Java 27 / JDK 27: General Availability](https://mail.openjdk.org/archives/list/announce@openjdk.org/thread/ORGGLMN75HFEWP7YL3ZLGHLYHVIBJDYT/)

HN 토론: <https://news.ycombinator.com/item?id=49712041> (316점, 284개 댓글)

## 소개

Mark Reinhold가 2026년 9월 15일 JDK 27의 정식 출시(General Availability)를 알렸다.
8월 20일 두 번째 릴리스 후보(RC)로 나온 빌드 35 이후 P1 버그가 보고되지 않아,
빌드 35가 그대로 GA 빌드가 되어 프로덕션에 쓸 수 있다.
Oracle의 GPL 라이선스 OpenJDK 빌드는 <https://jdk.java.net/27>에서 받을 수 있다.

이번 릴리스는 아홉 개의 JEP를 담는다.
JDK 27은 LTS(장기 지원) 릴리스로, 프로덕션 채택 판단이 실제로 걸리는 버전이다.
따라서 이 노트는 아홉 JEP를 세 부류로 나눠 본다.
기본값이 되어 코드를 바꾸지 않아도 동작이 달라지는 것,
보안 표면을 넓히는 것, 그리고 아직 프리뷰·인큐베이터로 남아 켜야 쓰는 것이다.

## 기본값이 되어 자동으로 동작이 바뀌는 것

기본값 변경은 코드를 고치지 않아도 런타임 동작을 바꾸므로 가장 먼저 확인해야 한다.

JEP 523은 G1을 모든 환경에서 기본 가비지 컬렉터로 만든다.
그동안 작은 힙이나 컨테이너 환경에서는 Serial GC가 기본이 되는 경우가 있었는데,
이제 환경과 무관하게 G1이 기본이 된다.
GC 동작이 환경마다 갈리던 불일치가 사라지는 대신,
아주 작은 힙에서 Serial GC의 낮은 오버헤드에 기대던 워크로드는
기본값만 믿지 말고 명시적으로 GC를 지정해 재검증해야 한다.

JEP 534는 Compact Object Headers를 기본으로 켠다.
객체 헤더를 기존 96~128비트에서 64비트로 줄여 힙 메모리와 캐시 압력을 낮추는 기능으로,
이전 릴리스에서 실험적으로 제공되던 것이 이제 기본값이 되었다.
객체 수가 많은 애플리케이션일수록 메모리 절감 효과가 크지만,
객체 헤더 레이아웃을 가정하는 일부 저수준 도구나 에이전트,
`Unsafe`에 의존하는 코드는 이 변경에 영향을 받을 수 있으므로
업그레이드 후 그런 도구의 호환성을 먼저 확인해야 한다.

## 보안 표면을 넓히는 것

JEP 527은 TLS 1.3에 후양자(post-quantum) 하이브리드 키 교환을 추가한다.
고전 알고리즘과 후양자 알고리즘을 결합한 하이브리드 방식으로,
지금 수집해 두었다가 미래의 양자 컴퓨터로 복호화하는
지금 수집·나중 복호(harvest-now-decrypt-later) 위협에 대비한다.
장수명 세션이나 민감 데이터를 다루는 서비스라면 우선 검토할 항목이다.

JEP 538은 암호 객체의 PEM 인코딩(3차 프리뷰)을 다룬다.
키와 인증서 같은 암호 객체를 PEM 텍스트 형식으로 인코딩·디코딩하는 표준 API로,
그동안 외부 라이브러리나 수작업 파싱에 의존하던 영역을 표준화한다.

JEP 536은 JFR(Java Flight Recorder)의 인프로세스 데이터 편집을 추가한다.
비행 기록에 담기는 민감 데이터를 기록 시점에 편집(redaction)할 수 있게 해,
운영 진단 데이터를 외부로 넘길 때의 유출 위험을 줄인다.

## 아직 프리뷰·인큐베이터인 것

다음 다섯은 켜야 쓸 수 있고 이후 릴리스에서 API가 바뀔 수 있으므로,
프로덕션에서는 실험 용도로만 다뤄야 한다.

JEP 533은 구조적 동시성(Structured Concurrency)의 7차 프리뷰다.
여러 병렬 작업을 하나의 단위로 묶어, 한 작업이 실패하면 나머지를 정리하고
부모-자식 관계를 명확히 하는 모델이다.
프리뷰가 7차까지 이어졌다는 것은 API가 아직 다듬어지는 중이라는 신호다.

```java
// 프리뷰 기능이므로 --enable-preview 로 컴파일·실행해야 한다.
try (var scope = StructuredTaskScope.open()) {
    // 두 작업을 자식으로 띄운다. 하나가 실패하면 스코프가 나머지를 취소한다.
    var user = scope.fork(() -> findUser(id));
    var order = scope.fork(() -> fetchOrder(id));
    scope.join();                       // 두 작업이 끝날 때까지 대기
    return new Response(user.get(), order.get());
}
```

JEP 532는 패턴, `instanceof`, `switch`에서의 원시 타입(5차 프리뷰)이다.
그동안 참조 타입에만 적용되던 패턴 매칭을 `int`, `long` 같은 원시 타입까지 확장한다.
JEP 531은 지연 상수(Lazy Constants, 3차 프리뷰)로,
불변 값의 초기화를 최초 사용 시점까지 미루면서도 JIT가 상수 폴딩할 수 있게 한다.
JEP 537은 Vector API(12차 인큐베이터)로 SIMD 연산을 표현하며,
JEP 538과 함께 여러 릴리스에 걸쳐 표준화를 기다리는 장기 인큐베이션의 사례다.

HN에서 이 장기 인큐베이션에 대한 반응이 갈렸다.
svcrunch는 Vector API를 수년째 쓰고 있으면서도 여전히 GA를 기다린다며,
RAG나 메모리 같은 신경망 정보 검색에서 콘텐츠 벡터화와
내적 기반 유사도 계산에 유용하다고 적었다.[^svcrunch]
실사용 가치가 있는데도 정식화가 늦다는 것이다.
rf15는 12차 인큐베이터라는 표현을 두고,
이 알이 정말 부화할 수 있는 것이냐고 꼬집었다.[^rf15]
오래된 인큐베이터가 유용함과 별개로 표준화 신뢰를 얻기 어렵다는 현실을 보여준다.

## 주의할 점

프리뷰 번호가 알려주는 정보를 흘리지 말아야 한다.
구조적 동시성 7차, 원시 타입 패턴 5차, Vector API 12차 인큐베이터처럼
번호가 클수록 표준화까지의 남은 시간과 API 변경 위험을 가늠하는 단서가 된다.
LTS라는 이유로 프리뷰 기능까지 안정적이라고 오해하면,
다음 릴리스에서 시그니처가 바뀔 API에 프로덕션 코드를 묶게 된다.

현장의 채택 속도는 릴리스 속도와 크게 다르다는 점도 함께 봐야 한다.
HN의 pineappletooth_는 은행이 아직 Java 8을 쓰고,
자신의 직장은 Java 17을 쓰며, 정부 기관에서는 Java 7을 요구하는 공고까지 있다고 전했다.[^pineappletooth]
새 LTS가 나와도 다수 조직은 여러 버전 뒤에 머물러 있으므로,
JDK 27의 새 기능을 학습하는 것과 그것을 실제로 배포할 수 있는 시점은 별개다.

기본값 변경은 조용히 성능 프로파일을 바꾼다.
G1 기본화와 Compact Object Headers 기본화는 벤치마크 없이도 적용되므로,
업그레이드 전후로 메모리 사용량과 GC 지연을 실제로 측정해 비교해야 한다.
발표문이 밝히듯 이번 릴리스는 아홉 JEP 외에도
수백 개의 개선과 수천 개의 버그 수정을 포함하므로,
눈에 띄는 JEP만 보고 회귀 검증을 건너뛰면 안 된다.

## 기억할 원칙

### 기본값 변경은 코드 변경보다 먼저 검증한다

새 릴리스에서 가장 먼저 확인할 것은 새 문법이 아니라 바뀐 기본값이다.
G1 기본화나 Compact Object Headers처럼 코드를 한 줄도 고치지 않아도
런타임 동작이 달라지는 변경은, 명시적 API 변경보다 발견하기 어렵고
프로덕션에서 성능 회귀로 나타난다.
릴리스 노트를 읽을 때 프리뷰 기능의 화려함보다
기본값이 된 항목을 먼저 목록으로 뽑아 각각을 측정으로 검증하는 순서가 안전하다.

### 프리뷰 번호는 채택 시점을 가늠하는 지표다

같은 릴리스에 담긴 기능이라도 성숙도는 프리뷰·인큐베이터 번호로 크게 갈린다.
1~2차 프리뷰는 실험, 여러 차수를 지난 기능은 표준화 임박,
오래된 인큐베이터는 여전히 유동적이라는 신호다.
이 번호를 읽으면 어떤 기능에 지금 프로덕션 코드를 투자해도 되는지,
어떤 기능은 학습만 하고 대기해야 하는지를 릴리스마다 판단할 수 있다.
