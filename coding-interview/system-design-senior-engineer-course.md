# 시니어 엔지니어처럼 시스템 설계하기: 5단계 틀과 세 가지 사례

영상: [Design Software Systems Like a Senior Engineer – Complete Course](https://www.youtube.com/watch?v=soTfFFIQQ8U)

GN 토론: <https://news.hada.io/topic?id=35613>

## 소개

freeCodeCamp.org가 2026년 10월 13일에 올린 3시간 17분짜리 강의다.
설명란은 강의를 @hayk.simonyan의 것이라고 적는다.
면접용 시스템 설계를 다섯 단계 틀로 정리하고,
그 틀을 음악 스트리밍과 호텔 예약과 메시징 앱 설계에 차례로 적용한다.
이 문서는 영상의 순서를 따라 틀과 세 사례를 요약하고,
사례마다 어떤 선택에 어떤 이유를 댔는지 가려 적는다.
영상에 나온 숫자는 이 문서가 다시 계산해 확인했고, 어긋난 곳은 본문에 적었다.

## 면접이 평가하는 다섯 가지

강사는 시스템 설계 면접이 라이브 코딩과 반대 성격이라고 말한다.
코딩 문제는 입력과 출력이 분명하고 실행해 보면 맞는지 알 수 있지만,
설계 문제는 요구사항이 모호하고 정답이 하나가 아니다.
그래서 면접관은 어떤 구조를 외웠는지가 아니라 어떻게 생각하는지를 본다고 한다.
평가 항목은 다음 다섯 가지다.

- 소통과 협업: 명확하지 않은 부분을 묻고 가정을 확인하며 진행하는지 본다.
- 구조화된 사고: 모호한 문제를 단계별 작업으로 나누고
지금 어느 단계인지 분명히 하는지 본다.
- 기술적 판단: 데이터베이스와 캐시와 메시지 큐를
익숙해서가 아니라 요구사항 때문에 골랐는지 본다.
- 실무 깊이: 정상 경로만이 아니라 실패 방식과 규모에서
생기는 문제를 짚는지 본다.
- 시간 관리: 한 영역에서
막혀 상위 설계만 하다 끝나지 않도록 면접관과 초점을 맞추는지 본다.

강사는 이 다섯 가지가 실제 업무 태도와 같다고 덧붙인다.
시간 관리를 못하는 사람이 일에서도 못하고,
실무 깊이가 없으면 이론만 아는 사람이라는 것이다.
면접 형식도 화이트보드 설계 하나가 아니라 기존 인프라의 병목 논의,
과거 프로젝트의 구조 설명, 개념 질문까지 네 가지라고 한다.

## 60분을 쓰는 5단계 틀

면접이 60분이라고 가정한 시간 배분이다.

| 단계                    | 시간    | 할 일                                                             |
| ----------------------- | ------- | ----------------------------------------------------------------- |
| 1. 요구사항 확인        | 5~10분  | 기능 요구사항과 비기능 요구사항을 확정하고 범위 밖을 정한다       |
| 2. 데이터와 API         | 15~20분 | 엔터티와 관계, 키와 인덱스, 엔드포인트와 응답 형식을 정한다       |
| 3. 상위 아키텍처        | 15~20분 | 구성요소와 읽기와 쓰기 경로를 그린다 (2단계와 순서를 바꿔도 된다) |
| 4. 병목과 확장과 신뢰성 | 5~10분  | 단일 장애점, 대체 경로, 중복 구성, 모니터링과 경보를 다룬다       |
| 5. 절충점과 확장        | 마지막  | 결정과 포기한 것을 요약하고 부하가 10배가 되면 무엇을 할지 말한다 |

1단계에서 기능 요구사항은 핵심 사용 사례와 범위 밖에 둘 것,
사용자와 플랫폼을 가리킨다.
비기능 요구사항은 일간 활성 사용자 수,
읽기와 쓰기 비율, 지연 시간, 허용 중단 시간이다.
Spotify 전체를 60분에 설계할 수는 없으므로
범위를 줄이는 일이 첫 단계의 핵심이라고 한다.

2단계의 데이터 모델에서는 주요 엔터티, 기본 키와 외래 키, 레코드 크기,
강한 일관성이 필요한 데이터와 최종 일관성으로 충분한 데이터를 구분한다.
API에서는 페이지네이션과 오류 처리와 요청 제한과 버전 관리를 말하고,
데이터베이스를 고른 이유와 고르지 않은 후보를 함께 설명한다.

3단계에서 떠오르는 것이 없을 때의 출발점은 API 서버,
로드 밸런서, 데이터베이스, 선택적인 캐시 네 가지다.
클라이언트에서
로드 밸런서와 API 서버를 거쳐 캐시와 데이터베이스까지 요청이 오가는
길을 따라가며 설명하고, 캐시를 쓰면 TTL(유효 시간)과 무효화 방식을 말한다.

4단계는 정상 경로 밖을 보는 단계이고,
강사는 이 단계가 중급과 시니어를 가르는 가장 분명한 신호라고 한다.
5단계에서는 완벽한 설계를 낼 수 없다는 것을 전제로 하며,
부하가 10배가 되면 무엇을 바꿀지 말하는 것이 목적이다.

### 면접 중에 하면 좋은 행동과 피할 행동

- 설계 전에 반드시 질문한다. 범위를 모른
채 해법으로 뛰어드는 것은 이미 나쁜 신호다.
- 말없이 그림만 그리거나 침묵이 두려워 혼자 계속 말하는 두 극단을 피한다.
면접관을 같은 회사 동료로 대하고 각 단계가 끝날 때 빠진 것이 없는지 확인한다.
- 선택이 뻔해 보여도 대안을 말한다. 결제 시스템에서 SQL을 고르더라도
NoSQL을 왜 쓰지 않았는지 설명하지 않으면 모르고 고른 것으로 읽힌다.
- 기술을 고를 때마다 절충을 말한다.

## 사례 1: 음악 스트리밍

가정은 사용자 50만 명, 곡 3천만 곡이다.
기능은 아티스트가 곡을 올리고, 사용자가 검색하고 재생하고
재생 목록을 관리하는 것이고, 건강 점검과 오류 추적 같은 관측도 포함한다.
음질은 64, 128, 320 kbps를 두고, 128 kbps 곡의 평균 크기를 3MB로 잡는다.

### 용량 계산

| 항목                | 계산                 | 결과  |
| ------------------- | -------------------- | ----- |
| 곡 저장             | 3MB × 3천만 곡       | 90TB  |
| 곡 메타데이터       | 100바이트 × 3천만 곡 | 3GB   |
| 사용자 프로필       | 1KB × 50만 명        | 0.5GB |
| 규모를 키운 곡 저장 | 3MB × 2억 곡         | 600TB |

곡 저장은 복제본과 재업로드 때문에 실제로는 두세 배라고 한다.
결론은 저장과 전송 비용을 지배하는 것이 오디오이고
메타데이터는 작은 부분이라는 것이다.
하루 재생은 사용자당 10~15곡이고 곡당 3~4MB이므로
전송 비용(인터넷으로 데이터가 나갈 때 클라우드가 받는 요금)이 크다고 한다.

### 구조

- 클라이언트는 로드 밸런서를 거쳐 상태가 없는 REST API 서버에 닿는다. 분산
방식은 라운드 로빈이나 최소 연결이고, 로드 밸런서가 서버 건강 점검을 한다.
- 인증은 JWT 토큰으로 하고, 곡 메타데이터는 SQL 데이터베이스에 둔다.
- 오디오 파일은 S3 같은 객체 저장소에 두고
서명된 URL(만료되는 일회성 주소)로 내려준다.
- 재생은 `GET /songs/{id}`가 메타데이터와 서명된 URL을 돌려주면
클라이언트가 그 주소로 오디오 조각을 범위 요청으로 받는
순서다. 분석용으로 `POST /songs/{id}/play`도 따로 호출한다.
- 업로드는 파일 형식과 크기를 검증하고
객체 저장소에 저장한 뒤 오디오 메타데이터를 뽑아 SQL에 넣고,
필요하면 CDN 캐시를 무효화한다.

객체 저장소에는 폴더가 없고
`artist/{id}/album/{id}/...` 같은 경로는 겉모양일 뿐이지만
파일을 찾기 쉽게 하려고 쓴다고 한다.
오디오 파일은 바꿀 수 없는 파일로 다루고, 고치려면 다시 올리고 옛 파일을 지운다.

### 데이터 모델과 SQL을 고른 이유

테이블은 `users`, `playlists`, `playlist_items`(재생 목록과 곡의 연결,
위치 포함), `songs`(파일 URL 포함), `artists`, `artist_songs`다.
SQL을 고른 이유는 재생 목록과 곡, 곡과 아티스트 사이에 조인이 많고
“내가 팔로우하는 아티스트의 곡 전부” 같은 복잡한 질의가 가능해서라고 한다.
인덱스는 곡 제목, 아티스트 이름, 연결 테이블의 곡 id에 건다.

### 규모 확장

사용자가 5천만 명, 곡이 2억 곡으로 늘었을 때의 순서다.

1. 대륙별 CDN 엣지와 지역별 로드 밸런서를 둔다. CDN 캐시는 LRU로 내보내고
실패하면 원본에서 가져온다.
2. API 서버는 상태가 없으므로 복제만 하면 된다.
그래서 처음부터 상태 없는 서버로 설계한다.
3. 데이터베이스는 쓰기를 리더가 받고 읽기를 팔로워가 받도록 가른다.
4. 그래도 모자라면 샤딩한다. 지역으로 나누고 곡은 아티스트 id 범위로 나눈다.
5. 객체 저장소는 지역별로 복제하고 여전히 서명된 URL로 접근한다.

강사는 작은 규모에서는 단순하게 시작하고 필요가 생길 때 키우라고 말한다.
설계 피라미드로는 요구사항과 용량 추정과 구조 선택이 맨 아래의 가장 큰 층이고,
기술 선택이 그 위, 코딩이 가장 작은 꼭대기 층이라고 설명한다.
코딩만 할 수 있는 개발자가 모델에게 밀린다는 것이 그의 논지이고,
이 부분은 영상의 주장으로만 적는다.

## 사례 2: 호텔 예약

강사는 이 문제를 흔한 CRUD 앱에 캐시와 복제를 얹은 것으로 보면 틀린다고 말한다.
마지막 방 하나를 두 사람이 동시에 예약하는 이중 예약이 핵심이고,
단순한 조회 뒤 삽입 방식은 카드를 두 번 결제하고 환불로 이어진다는 것이다.

### 요구사항

- 질문으로 범위를 정한다: 플랫폼에서 결제할지(예),
웹과 모바일을 함께 지원할지(예), 취소와 초과 예약을 지원할지(예),
가격이 수요에 따라 바뀌는지(예), 관리자 화면이 있는지(예).
- 핵심 기능을 가르는 질문은 “이 기능을 빼면
Booking.com이 아니게 되는가”다. 위치와 날짜와
인원과 가격대로 검색하는 일이 여기에 든다.
- 비기능은 예약에는 강한 일관성, 검색에는 최종 일관성이면 충분하다는 것,
검색 응답 500ms 이하, 예약 확인은 2~3초 허용, 가용성 99.9%다.

### 부하 계산

예약 쪽은 연간 11억 방-박에서 시작한다.
평균 2박이면 5억 5천만 건이고, 이를 365로 나누면 하루 약 150만 건,
86,400초로 나누면 초당 약 17건(TPS)이다.
읽기 쪽은 월 5억 방문에서 시작한다. 하루 약 1,700만 방문,
초당 약 200 방문이고, 방문당 백엔드 읽기 5번이면 초당 약 1,000(QPS)이다.
영상은 월 일수로 40을 말하지만
1,700만이라는 결과는 30일로 나눠야 나오므로 말실수로 보인다.
결과는 읽기 1,000 QPS 대 쓰기 17 TPS인 읽기 위주 시스템이고,
과제는 읽기를 최적화하면서 쓰기의 일관성을 지키는 일이다.

### 구조

서비스는 CDN, API 게이트웨이(인증과 요청 제한과 라우팅),
호텔 서비스(정적이라 캐시하기 좋다), 예약 서비스(재고 확인과 동시성),
요금 서비스(날짜별 동적 요금), 결제 서비스, 알림 서비스, 검색 서비스로 나눈다.
데이터는 ACID가 필요한 PostgreSQL이 기준이고, 검색은 Elasticsearch가 맡는다.
이유는 PostgreSQL이 초당 1,000번의 필터 검색을 감당하지 못하고,
Elasticsearch가 전문 검색과 반경 내 필터와
가격대와 평점 필터를 빠르게 처리하기 때문이다.

`LIKE` 검색은 전체 테이블 훑기가 되어 인덱스가 소용없고
관련도 순위도 오타 처리도 거리 계산도 못 한다고 강사는 지적한다.
Elasticsearch는 문서 하나에 객실 유형까지 중첩해 조인 없이 담는 중복 저장소이고,
진실의 원천은 여전히 PostgreSQL이다.
둘을 맞추는 방법으로 변경 데이터 캡처(CDC)를 든다. PostgreSQL의 쓰기 선행 로그를
Debezium이 읽어 Kafka 주제로 내보내고, 소비자가 Elasticsearch 색인을 갱신한다.
그래서 결제 직후 검색에는 아직 방이 보일 수 있지만,
실제 예약은 데이터베이스로 다시 확인하므로 안전하다는 설명이다.

서비스 경계는 세 가지를 비교한다.
모놀리스는 트랜잭션이 단순하지만 수백 명이 함께 배포하기 어렵고,
완전한 마이크로서비스는 서비스마다
데이터베이스를 가져 분산 트랜잭션 문제가 생긴다.
강사가 고른 절충은 서비스는 애플리케이션 계층에서
나누되 예약과 호텔처럼 강하게 묶인 데이터는 한 데이터베이스에 두고
로컬 ACID 트랜잭션을 쓰는 것이다.

### API와 중복 요청

호텔과 객실은 `/hotels`, `/hotels/{id}/rooms`처럼 하위 자원으로 나누고,
예약은 `/reservations`로 만든다.
같은 사용자의 이중 클릭은 클라이언트가 한 번 만든 예약 id(UUID)를 키로 쓰면
막힌다. 같은 id가 다시 오면 중복 키 오류 대신 기존 예약을 돌려준다.
호텔 id와 객실 id와 사용자 id와 날짜를 섞은 해시를 서버에서
만드는 방법도 있지만,
같은 사용자의 이후 예약까지 막을 수 있어
클라이언트가 만드는 id가 더 간단하다고 한다.
취소는 정책을 확인한 뒤 허용하고(일주일 전은 되고
직전은 안 된다는 식), 날짜 변경은 `PUT`으로 한다.

### 데이터 모델

예약하는 것은 특정 방이 아니라 객실 유형이고, 방 번호는 체크인 때 정해진다.
테이블은 `hotels`, `room_types`, `room_type_rates`(유형별 요금),
`rooms`, `room_type_inventory`, `reservations`, `transactions`다.
재고 테이블은 호텔과 객실 유형과 날짜 한 칸마다 한 행이고
`total_inventory`와 `total_reserved`를 갖는다. 앞으로 2년 치를 미리 채워 두고
매일 크론 작업으로 날짜를 더한다.
거래를 예약과 분리한 이유는 한 예약에 결제와 날짜 변경
차액과 환불(음수 금액)이 여러 번 생길 수 있기 때문이다.
가용성 확인은 `total_reserved + 예약할 방 수 <= total_inventory`이고,
초과 예약 10%를 허용하면 이 상한에 1.1을 곱한다.

### 동시성: 서로 다른 두 사용자

읽기 확정(read committed) 격리 수준에서는
두 트랜잭션이 모두 남은 방 하나를 읽고 둘 다 검사를 통과한 뒤 덮어쓴다.
해법은 두 가지다.

| 방법                                | 장점                        | 단점                                                          |
| ----------------------------------- | --------------------------- | ------------------------------------------------------------- |
| 직렬화 가능(serializable) 격리      | 구현이 쉽다                 | 트랜잭션이 서로 막아 TPS가 높으면 확장되지 않고 교착이 생긴다 |
| 읽기 확정 + `SELECT ... FOR UPDATE` | 같은 행만 순서대로 기다린다 | 잠글 행을 정확히 정해야 한다                                  |

강사의 선택은 후자다. 같은 재고 행을 잠근 트랜잭션만 차례를 기다리고
다른 행을 다루는 트랜잭션은 병렬로 진행하며,
TPS가 낮으면 직렬화 가능도 괜찮다고 덧붙인다.

### 확장

- 샤드 키는 호텔 id다. 한 호텔의 데이터가 한 샤드에 모이므로
조인이 샤드를 가로지르지 않고 트랜잭션이 로컬에서
끝난다. 1,000 QPS를 16개 샤드로 나누면 샤드당 읽기 약 62과 쓰기 약 1이다.
- 샤드 수가 자주 안 바뀌면 나머지 연산(모듈로) 샤딩이면 되고,
샤드를 자주 늘린다면
일관된 해싱이 낫다. 17번째 샤드를 더할 때 모듈로 방식은
거의 모든 데이터를 옮기지만 일관된 해싱은 약 17분의 1만 옮긴다.
- 캐시는 호텔과 객실 유형과 날짜를 키로 재고를 5분 TTL로 둔다. 예약이 성공하면
해당 키를 무효화한다.
- 읽기 복제본을 가용 영역마다 두되 방금 쓴 데이터는 기본 데이터베이스에서
읽는다. 쓰기용 기본 데이터베이스는 하나로 두어 지역 사이 쓰기 충돌을 피한다.
- 로드 밸런싱은 지역 지연 기준이고,
캐시와 Elasticsearch와 읽기 복제본을 지역마다 둔다.

## 사례 3: WhatsApp식 메시징

강사는 이 사례를 상태가 있는 연결과 실시간 전달과
다기기 동기화와 장애를 한꺼번에 묻는 문제라고 소개한다.

### 요구사항과 규모

- 기능은 1:1 대화, 최대 100명의 그룹 대화, 오프라인 사용자에게 전달,
이미지와 영상과 음성 메모, 보냄과 전달됨과 읽음 상태,
접속 상태와 마지막 접속 시각이다.
- 비기능은 접속 중일 때 500ms 이하 전달, 메시지 유실 없는 전달, 수십억 명 규모,
서버 보관 최소화(미전달 메시지 30일 보관), 구성요소 장애에 견디는 것이다.
- 규모 가정은 가입자 10억, 일간 활성 5억,
피크 동시 연결 5천만, 사용자당 하루 최대 20건이다.

| 항목        | 계산                | 결과            |
| ----------- | ------------------- | --------------- |
| 하루 메시지 | 5억 × 20            | 100억 건        |
| 평균 쓰기   | 100억 ÷ 86,400      | 초당 약 11.5만  |
| 피크 쓰기   | 평균의 3~5배        | 초당 약 35~50만 |
| 하루 저장   | 100억 × 1KB         | 10TB            |
| 연간 저장   | 10TB × 365          | 약 3.6PB        |
| 피크 대역폭 | 5천만 연결 × 10KB/s | 약 500GB/s      |

대부분의 메시지는 몇 초 안에 전달되고 서버에서 지워지므로
모두를 영원히 저장하지 않는다는 점이 이
시스템이 작은 인프라로 돌아가는 이유라고 한다.

### 구성요소와 연결 방식

앱, 로드 밸런서, 채팅 서버(WebSocket 유지), 메시지 큐(Kafka나 RabbitMQ),
메시지 저장 서비스, 사용자 연결 캐시(Redis), 객체 저장소와 CDN,
알림 서비스(APNs와 FCM), 접속 상태 서비스로 이루어진다.
저장소는 쓰기가 많고 질의가 단순한 메시지에는 Cassandra나 DynamoDB를,
사용자와 그룹에는 PostgreSQL을 쓴다.
연결 방식은 다음 세 가지를 비교한다.

| 방식      | 동작                                           | 약점                                                               |
| --------- | ---------------------------------------------- | ------------------------------------------------------------------ |
| 폴링      | 주기적으로 새 메시지가 있는지 묻는다           | 빈 응답으로 대역폭을 쓰고 확인 주기만큼 지연된다                   |
| 롱 폴링   | 서버가 새 메시지나 시간 초과까지 응답을 미룬다 | 연결을 계속 열고 닫고 대기 중인 HTTP 연결이 메모리와 스레드를 쓴다 |
| WebSocket | 한 번 맺은 양방향 연결로 양쪽이 언제든 보낸다  | 메모리를 더 쓰고 이를 지원하는 로드 밸런서가 필요하다              |

강사는 메시징에서는 WebSocket의 비용을 감수할 만하고
다른 상황에서는 폴링이 나을 수도 있다고 말한다.
WebSocket에는 계층 7이 아니라 계층 4 로드 밸런싱을 써야 한다고 하는데,
이 문서는 그 주장을 확인하지 못했다.
채팅 서버의 생사는 서비스 디스커버리(Consul이나 AWS Cloud Map)가
10초마다 건강 점검을 해 로드 밸런서의 라우팅 표를 갱신하는 방식으로 관리한다.

### 메시지 흐름

둘 다 접속 중이면
채팅 서버 A가 메시지 id를 만들어 “보냄”으로 응답하고 큐에 넣는다.
Redis의 연결 캐시에서
수신자가 있는 서버를 찾아 Redis 발행-구독으로 서버 B에 넘기고,
서버 B가 WebSocket으로 전달한 뒤 확인 응답이 돌아오면
“전달됨”으로 바꾼다. 읽으면 같은 과정으로 “읽음”이 된다.
수신자가 오프라인이면 Redis와 데이터베이스의 수신함에 넣고
알림 서비스가 푸시 알림을 보낸다. 수신자가 다시 접속하면
채팅 서버가 수신함에서 밀린 메시지를 꺼내 전달한다.

그룹은 그룹 서비스에서
구성원 목록을 받아 온라인인 사람에게는 발행-구독으로 각자 접속한 서버에 병렬
전달하고,
오프라인인 사람에게는 수신함과 푸시를 쓴다.
메시지 자체는 큐와 데이터베이스에 한 번만 쓴다.

다기기 동기화는 사용자의 모든 기기에 같은 메시지를 보내 상태를 맞추는 방식이고,
충돌은 버전 번호를 붙인 “마지막 쓰기가 이김”으로 푼다.
전달 작업량이 대략 두 배가 되는 대가가 있고, 새 기기에는 최근 30일만 동기화하고
나머지는 위로 스크롤할 때 불러오며 오래된 것은 차가운 저장소에서 늦게 가져온다.

### 미디어와 처리량

미디어를 채팅 서버로 올리면 서버가 대역폭에 묶이므로,
사전 서명된 URL로 객체 저장소에 직접 올리고
내려받는다. 수신자는 CDN을 거치는 쪽이 복잡하지만 이 규모에서는 이득이 크다.
미디어에는 메시지 보관 정책과 맞춘 TTL(약 30일)을 두어 자동으로 지운다.

메시지 저장 서비스는 큐의 파티션을 인스턴스마다 나눠 읽고,
한 번에 약 500개씩 가져와 20개 스레드로 검증과 가공(중복 제거용 해시,
멘션 추출, 링크 미리보기, 색인 준비)을 한다.
이를 1,000개나 5초 단위로 모아 대화별로 묶어 일괄 삽입한다. 한 번 삽입에
5ms라면 1,000번은 5초이고 일괄은 50ms여서 처리량이 100배라고 한다.
실패한 것은 재시도하고, 그래도 안 되면
데드 레터 큐로 보내며 큐에서 지우지 않는다.

### 암호화와 요청 제한

종단간 암호화는 Signal 프로토콜로 한다. 각자 가입 때 신원 키 쌍을 만들어
공개 키만 키 서버에 올리고, 수신자는 미리 만든 사전 키(약 100개)도 올린다.
송신자가 수신자의 공개 신원 키와 사전 키 하나를 받아 세션 키를 만들면
이후 메시지는 서버가 읽을 수 없고,
메시지마다 카운터를 더해 세션 키가 새어도 한 번에 풀리지 않게 한다.
영상은 암호화 설명에서 송신자의 공개 키로 암호화한다고도 말하는데,
앞서 설명한 세션 키 방식과 말이 어긋난다.
이 문서는 Signal 프로토콜의 실제 동작을 확인하지 않았다.

요청 제한은 토큰 버킷을 쓴다. 행동마다(메시지 100개/분,
그룹 생성 시간당 5개 등) 용량과 보충 속도를 두고,
넘으면 막고 알리거나 캡차를 요구하며, 경고에서 1시간 제한,
24시간 제한, 계정 정지와 사람의 검토로 단계적으로 벌칙을 올린다.
서버를 옮겨 다니며 우회하지 못하도록 한도 정보는 Redis 같은 중앙 저장소에 둔다.

### 샤딩과 복제, 정리 작업

샤드 키로 사용자 id를 쓰면 한 사용자의 메시지가 한 샤드에 모여 읽기가 빠르지만
많이 쓰는 사용자 때문에 쏠린다.
메시지 id로 나누면 고르게 퍼지지만
한 사용자의 메시지를 읽으려면 모든 샤드를 질의해야 한다.
강사가 권하는 절충은 사용자 id로 샤딩하고
쓰기를 상대 샤드에도 복사해 쓰기를 두 배로 늘리는
대신 읽기를 빠르게 하는 것이다. 읽기는 복제본만 쓴다.
면접에서는 하나를 고르는 것이 아니라 대안과 절충을 말하고,
읽기와 쓰기 중 무엇이 중요한지 요구사항 단계에서 묻는 것이 좋다고 한다.
만료된 미디어와 미전달 메시지와 오래된 연결은 Airflow나
크론 같은 스케줄러가 작업 큐와 작업자 풀로 정기 정리한다.

### 장애 대응

- Redis가 죽으면: 미전달 메시지는 Redis 수신함과 함께 데이터베이스에도 써
두었으므로 데이터베이스로 대체해 읽고,
Redis가 돌아오면 배경 작업이 데이터베이스에서 다시 채운다.
- Kafka 클러스터가 통째로 죽으면: 채팅 서버가 메모리 버퍼(약 10만 건,
넘치면 오래된 것부터 버림)에 쌓고
새 클러스터가 뜰 시간만큼 기다렸다 다시 발행한다. 서버도 함께 죽을
때를 위해 디스크에 추가 전용 로그를 남기고 복구 때 되돌려 발행한다.
- 지역 분산: 지역마다 채팅 서버와 Redis와 데이터베이스 샤드의 전체 구성을 두고,
DNS가 가까운 지역으로 연결하며 지역별 사용자 수에 따라 서버 수를 다르게 둔다.
- 기능 플래그: LaunchDarkly나 클라우드 제공 서비스로 환경별,
사용자 20%별 점진 공개를 하고
채팅 서버가 클라이언트 버전에 따라 새 필드를 보내거나 뗀다.

## 이 강의에서 가져갈 판단 기준

### 틀이 알려 주는 순서

이 강의의 가장 쓸 만한 부분은 사례가 아니라 순서다.
요구사항과 추정을 먼저 하고, 단순한 구조에서 출발하고,
병목을 찾고, 그다음에 장애를 다룬다.
강사는 장애를 구조가 정해지기 전에 꺼내지 말라고 말한다.
세 사례에서 이 순서는 같다. 용량 계산이 저장소를 정하고(오디오가 지배하니
객체 저장소),
읽기와 쓰기 비율이 구조를 정하고(읽기 1,000 대 쓰기 17이라 검색을 분리),
장애는 마지막에 온다.

### 각 사례에서 기억할 결정

| 사례          | 핵심 결정                                           | 이유                                                        |
| ------------- | --------------------------------------------------- | ----------------------------------------------------------- |
| 음악 스트리밍 | 오디오는 객체 저장소와 서명된 URL, 메타데이터는 SQL | 오디오가 저장과 전송을 지배하고 조인이 많다                 |
| 호텔 예약     | 재고 행 잠금(`FOR UPDATE`)과 예약 id 중복 방지      | 서로 다른 두 사용자와 같은 사용자의 중복 요청이 다른 문제다 |
| 메시징        | WebSocket과 큐와 Redis 수신함, 쓰기 이중화 샤딩     | 상태 있는 연결과 오프라인 전달과 읽기 속도를 함께 만족한다  |

### 이 강의의 한계

영상은 정답이 하나가 아닌 문제를 다루면서도 사례마다 하나의 구조를 제시한다.
강사의 선택은 하나의 합리적인 답일 뿐이고,
면접에서 같은 답을 외워 말하라는 뜻이 아니라는 것은 영상이 스스로 말한다.
이 문서가 보기에 더 중요한 한계는 검증의 부재다.
영상의 구조는 대부분 말로 설명한 것이어서 실제 부하에서
어느 수치가 병목이 되는지 직접 확인하지 않았다.
암호화 설명처럼 앞뒤가 맞지 않는 서술이 있으므로,
개별 기술 서술을 그대로 받아 쓰기보다
각 기술의 세부는 해당 기술의 공식 문서로 확인해야 한다.

### 적용할 때의 규칙

- 설계를 시작하기 전에 읽기와 쓰기 비율과 일관성 요구를
숫자로 확정한다. 확정하지 못하면 1단계에서 더 나아가지 않는다.
- 선택마다 고르지 않은 대안과 그 이유를 한 문장으로 말한다. 이유를 못 대면
그 선택은 습관이다.
- 일관성이 필요한 쓰기와 지연에 민감한 읽기를 같은 저장소에 맡기지 않는다. 호텔
예약처럼 쓰기의 원천(PostgreSQL)과 읽기용
사본(Elasticsearch)을 분리하되 마지막 확인은 원천으로 한다.
- 실패 조건은 이렇다. 검색 사본이 원천보다 늦어 사용자가 이미 찬 방을 보는 일이
잦거나, 재고 행 잠금이 인기 호텔 하나에 몰려 대기 시간이 늘면
샤딩이나 재고 분할을 다시 검토한다.
