# Windows 11 기본 날씨 앱이 램 1GB를 넘게 쓴다

원문: [Windows 11's built-in Weather app wastes more than 1 GB of RAM](https://www.notebookcheck.net/Windows-11-s-built-in-Weather-app-wastes-more-than-1-GB-of-RAM.1364205.0.html)

HN 토론: <https://news.ycombinator.com/item?id=49232138> (382점, 318개 댓글)

## 요약

Notebookcheck의 Andrew Sozinov가 2026년 8월 9일에 쓴 기사다.
Microsoft가 램이 적은 PC에서 Windows 11을 더 효율적으로 만들려고 애써 왔는데 정작 자사 기본 앱 하나가 그 목표를 거스르고 있다는 내용이며, Windows Latest가 발표한 테스트를 근거로 삼는다.

Windows Latest는 사용자의 집중적인 조작 없이 날씨 예보를 표시하는 것만으로 이 앱이 램 1.2GB를 넘겼다고 보고했다.
Wccftech도 비슷한 동작을 관찰했다 — 메모리 사용량이 대략 1GB에서 시작해 유휴 상태에서 500~600MB로 떨어지고, 확대나 인터페이스 탐색 같은 기본 동작 중에는 1.5~1.6GB까지 올라갈 수 있다는 것이다.
램 8GB PC에서는 이 앱 하나가 시스템 메모리의 20% 가까이를 차지할 수 있다는 뜻이다.
비교 대상으로 제시된 macOS의 기본 날씨 앱은 비슷한 조건에서 250MB 미만을 쓴다고 하며, Microsoft 구현의 메모리 사용량이 약 다섯 배라는 계산이 나온다.

원인은 날씨 앱이 완전한 네이티브 Windows 애플리케이션이 아니라는 데 있다.
본질적으로 Microsoft의 WebView2 프레임워크 위에 올린 MSN Weather 웹 앱이며, 작업 관리자에는 Chromium 기반 하위 프로세스 여러 개가 동시에 돌고 있는 것이 보이고 그것이 비정상적으로 높은 램 사용에 기여한다.

램 32GB 이상 고사양 PC에서는 문제가 되지 않겠지만 보급형 시스템에는 눈에 띄는 영향을 줄 수 있다.
8GB나 심지어 16GB 메모리 컴퓨터에서는 날씨 앱을 실행하는 것만으로 메모리 압박이 커져 Windows가 페이지 파일에 더 의존하게 되고 시스템 반응이 굼떠질 수 있다는 것이다.

앱 인터페이스 안에는 광고도 들어 있다.
Windows Latest에 따르면 후원 콘텐츠가 예보 피드에 직접 들어가 날씨 카드와 비슷한 시각 양식으로 나란히 나타난다.
Microsoft가 Foreca, 유럽중기예보센터(ECMWF), 기타 지역 기상 기관 등 여러 제공자로부터 날씨 데이터를 라이선스하고 있음에도, Windows 기본 앱에 광고가 있다는 사실은 비판을 받아왔다.

기사는 이 발견이 Windows 11의 효율을 개선하려는 Microsoft의 최근 노력과 어긋나 보인다고 정리한다.
회사는 여러 기본 앱을 갱신해 왔고 저사양 하드웨어에서 운영체제가 더 잘 동작하기를 원한다고 거듭 말해왔다.
Microsoft 임원 Rudy Huyn은 앞으로 완전한 네이티브 Windows 애플리케이션을 더 만들 계획이라고 밝혔지만, Weather 같은 MSN 브랜드 앱이 결국 WinUI로 다시 만들어질지는 불분명하다.

## 분석

### 이 기사는 취재가 아니라 두 매체의 측정을 모은 집계다

기사에 자체 측정은 없다.
Windows Latest의 테스트가 1차 출처이고, Wccftech의 관찰이 교차 확인이며, macOS 비교 수치도 전해 들은 것(reportedly)으로 표기된다.
Notebookcheck가 더한 것은 8GB 시스템에서 20%라는 환산과, Microsoft의 효율 개선 발표와 대비시키는 서사다.

이 구조가 기사의 강점이자 약점이다.
강점은 서로 다른 두 매체가 비슷한 범위의 숫자를 내놓았다는 점이다 — 1GB 시작, 유휴 500~600MB, 조작 중 1.5~1.6GB라는 Wccftech의 관찰은 Windows Latest의 1.2GB와 모순되지 않고 오히려 변동 폭을 보여준다.
약점은 어느 쪽도 측정 방법을 밝히지 않는다는 점이며, 뒤에서 다룰 문제의 출발점이다.

HN에서 이 약점은 첫 댓글부터 지적되었다.
hyperhello는 저자가 실제 메모리와 페이징 공간 확보의 차이를 아는지 확인받고 싶다고 적었다.[^hyperhello]
그리고 stock 상태의 최신 Windows 11 x64 25H2 데스크톱에서 직접 재본 smileybarry는 날씨 앱이 실행 직후 약 670MB를 쓰고 댓글을 쓰는 사이 450MB로 떨어졌다고, 1GB보다 훨씬 낮다고 보고했다.[^smileybarry]
디블로트 스크립트나 커스터마이저를 돌리지 않은 기본 상태라는 단서까지 붙였다.
같은 앱을 두고 1.2GB와 670MB가 나온다는 사실은 이 기사의 숫자가 조건에 크게 좌우된다는 뜻이고, 그 조건이 무엇인지는 어느 기사에도 없다.

이런 집계 기사가 성립하는 이유는 검증 비용이 낮기 때문이다.
독자가 작업 관리자를 열어 직접 확인할 수 있는 주장이고, 그래서 틀리면 즉시 반박당한다.
반대로 이 검증 용이성이 기사를 얕게 만든다 — 누구나 확인할 수 있는 숫자만 남고, 왜 그런 숫자가 나오는지에 대한 설명은 원인은 WebView2다 한 줄로 끝난다.

### 문제의 본질은 앱 하나가 아니라 배포 방식의 선택이다

날씨 앱이 WebView2 위의 MSN Weather 웹 앱이라는 사실이 이 기사의 유일한 기술적 설명이다.
그런데 이 한 줄이 실제로는 조직 구조에 대한 진술이다.

MSN은 Microsoft의 콘텐츠·광고 사업이고 웹 자산이다.
그 웹 자산을 Windows 기본 앱으로 배포하는 가장 싼 방법은 웹뷰로 감싸는 것이며, 그러면 웹팀 하나가 브라우저의 MSN 날씨, 위젯 패널, 기본 앱을 동시에 유지할 수 있다.
네이티브로 다시 만들면 Windows 전용 코드베이스가 하나 더 생기고, 그것을 유지할 인력이 필요하며, 웹 쪽 변경과 동기화해야 한다.

즉 1GB는 버그가 아니라 조직 경계가 만든 비용이다.
운영체제 팀의 목표(저사양에서 잘 도는 Windows)와 콘텐츠 팀의 목표(하나의 웹 자산을 모든 표면에 배포)가 충돌하고, 기본 앱이라는 자리에서 후자가 이겼다.
Rudy Huyn의 네이티브 앱을 더 만들겠다는 발언과 MSN 브랜드 앱이 WinUI로 다시 만들어질지 불분명하다는 기사의 유보가 정확히 이 경계를 가리킨다.

### 광고가 함께 언급된 것은 곁가지가 아니다

메모리 기사에 광고 이야기가 들어간 것은 산만해 보이지만 인과적으로 연결된다.
예보 피드에 후원 콘텐츠가 날씨 카드와 같은 시각 양식으로 섞여 들어간다는 것은, 이 앱이 날씨 표시 도구가 아니라 콘텐츠 피드라는 뜻이다.

피드는 날씨 표시보다 훨씬 무겁다 — 이미지, 추적 스크립트, 광고 입찰, 무한 스크롤, 개인화가 따라온다.
그러면 왜 웹뷰인지도 자동으로 설명된다.
광고 스택은 웹 기술 위에 만들어져 있고 네이티브로 옮기는 비용이 크며, 무엇보다 광고 사업이 요구하는 변경 속도는 OS 릴리스 주기와 맞지 않는다.

그래서 이 기사가 두 사실을 나란히 놓은 것은 옳다.
메모리 사용량과 광고는 같은 원인의 두 증상이고, 광고를 뺄 생각이 없다면 메모리도 크게 줄지 않는다.
다만 기사는 이 연결을 명시하지 않고 두 사실을 병렬로 나열하는 데 그친다.
calini는 이를 한 줄로 정리한다 — Windows의 날씨 앱은 날씨보다 광고가 더 많으니 앞뒤가 맞는다는 것이다.[^calini]

이 진단이 맞다는 실증도 스레드에 있다.
SBArbeit는 우회 방법을 제시했다 — Edge에 uBlock Origin을 설치하고 MSN Weather에 접속한 뒤 주소창의 애플리케이션 추가 버튼으로 시작 메뉴 아이콘을 만들고 기본 날씨 앱 아이콘을 지우면, 같은 앱을 약 130MB로 광고 없이 쓸 수 있다는 것이다.[^SBArbeit]
같은 콘텐츠를 같은 엔진으로 띄우는데 광고와 MSN 피드를 차단하는 것만으로 메모리가 한 자릿수 배 줄어든다면, 문제의 상당 부분이 렌더링 엔진이 아니라 그 위에 실리는 것에 있다는 뜻이다.
같은 댓글은 위젯 설정에서 Discover / Microsoft Start 피드도 끄라고 덧붙이는데, 같은 것이 표면만 바꿔 여러 곳에 들어와 있다는 지적이다.

## 비평

### 측정 방법이 없어서 숫자가 무엇을 뜻하는지 알 수 없다

Windows에서 프로세스 메모리를 말할 때 어떤 값을 보느냐에 따라 숫자가 크게 달라진다.
작업 관리자의 기본 열은 프라이빗 작업 집합에 가깝지만 사용자가 보는 값과 실제 물리 메모리 점유는 다르고, Chromium 기반 앱은 여러 하위 프로세스가 페이지를 공유하므로 단순 합산이 실제보다 크게 나온다.
기사는 1.2GB, 1.5~1.6GB 같은 숫자를 제시하면서 그것이 어떤 지표인지 말하지 않는다.

이 문제는 macOS 비교에서 더 커진다.
macOS의 250MB 미만이라는 값이 어떤 지표인지도 밝혀지지 않았고, 두 운영체제의 메모리 회계 방식은 애초에 직접 비교 가능하지 않다.
macOS는 압축 메모리를 적극적으로 쓰고 활동 모니터의 메모리 열은 Windows 작업 관리자와 다른 것을 센다.
다섯 배라는 결론은 인상적이지만 서로 다른 자로 잰 값의 비율이다.

더 중요한 것은 이 앱이 캐시로 쓰는 메모리와 반드시 필요한 메모리의 구분이 없다는 점이다.
Chromium 계열 엔진은 여유가 있으면 캐시를 늘리고 압박이 오면 반납하도록 설계되어 있다 — Wccftech가 관찰한 1GB에서 500~600MB로 떨어지는 동작이 바로 그 증거다.
그렇다면 8GB 시스템에서 실제로 이 앱이 붙잡는 양은 1.2GB가 아닐 가능성이 크고, 20%라는 환산은 최악의 순간값을 상시 점유처럼 제시한 것이다.

GuB-42가 이 문제를 가장 정확하게 정리했다.[^GuB-42]
끔찍하게 비대하다는 사실은 접어두더라도 램 사용량을 정확히 재는 것은 까다로우며 여러 측정치가 있고 옳은 하나는 없다는 것이다.
기사에서 분명한 것은 램을 먹는 것이 날씨 앱 자체가 아니라 그것이 올라탄 프레임워크라는 점이고, Renderer와 GPU Process 같은 것들이 대부분을 차지한다.
작업 관리자가 말해주지 않는 것은 이것들이 공유 구성 요소인지 여부다 — Renderer가 쓰는 662MB가 여러 Windows 구성 요소와 공유되고 있다면 날씨 앱을 죽여도 기대만큼 회수되지 않으며, 회수하려면 그 구성 요소를 쓰는 모든 것을 죽여야 하는데 그중에는 핵심 시스템 앱도 있을 수 있다.
사설 메모리와 공유 메모리의 구분 위에 실제 램 사용량과 가상 메모리의 구분도 겹친다.

alkonaut는 같은 지점을 계산으로 옮긴다 — 여러 WebView 앱이 같은 라이브러리를 메모리에서 공유해야 한다는 점을 넣으면 이 계산이 공정한지 의문이라는 것이다.[^alkonaut]
Edge/Chromium 라이브러리를 올리는 데 0.5~1GB를 내더라도 그 메모리가 사용자가 실행할 N개 앱에 걸쳐 상각된다면, 날씨 앱에 1GB라는 표현은 일어나기 어려운 최악의 경우가 된다.
이 반론이 성립하려면 사용자가 실제로 여러 WebView 앱을 동시에 쓰고 있어야 하는데, 기사도 반론도 그 조건을 확인하지 않는다.

### 8GB 시스템에서 페이지 파일에 의존하게 된다는 서술이 검증되지 않았다

기사의 실질적 피해 주장은 이것 하나다 — 8GB나 16GB 시스템에서 이 앱을 실행하면 메모리 압박이 커져 페이지 파일 사용이 늘고 시스템이 굼떠질 수 있다는 것이다.

그런데 이 주장에는 어떤 측정도 붙어 있지 않다.
날씨 앱을 실행했을 때 페이지 파일 활동이 실제로 늘었는지, 다른 앱의 응답 시간이 나빠졌는지, 체감 가능한 정도였는지에 대한 데이터가 없다.
가능성의 서술(may, potentially)만 반복되고, 그 가능성이 실현되는 조건 — 이미 다른 앱들이 얼마나 쓰고 있어야 하는지 — 도 제시되지 않는다.

이 공백이 중요한 이유는 현대 운영체제의 메모리 관리가 이 시나리오를 다루도록 설계되어 있기 때문이다.
16GB 시스템에서 1.2GB짜리 앱 하나가 페이지 파일 압박을 만든다는 주장은 상당한 근거를 요구하는데, 기사는 8GB와 16GB를 한 문장에 묶어 같은 위험으로 서술한다.
두 경우는 전혀 다르고, 그 차이를 뭉갠 것이 이 기사에서 가장 느슨한 부분이다.

### 비교 대상 선택이 결론을 미리 정해 놓았다

macOS 날씨 앱과의 비교는 극적이지만 공정하지 않다.
Apple의 날씨 앱에는 광고 피드가 없고, 콘텐츠 카드가 없으며, 웹 자산의 재사용도 아니다.
같은 이름을 가졌을 뿐 다른 제품이다.

더 적절한 비교 대상은 두 가지였을 것이다.
하나는 브라우저 탭에서 MSN 날씨를 여는 경우다 — 같은 콘텐츠를 같은 엔진으로 렌더링하므로, 기본 앱이라는 껍데기가 추가로 얼마를 쓰는지 분리해 낼 수 있다.
다른 하나는 Windows 11의 다른 WebView2 기반 기본 앱들이다 — 이 앱만의 문제인지 프레임워크 전체의 특성인지가 그때 드러난다.

기사는 이 둘 중 어느 것도 하지 않고 가장 큰 격차가 나오는 비교를 택했다.
그 결과 독자가 얻는 결론은 Microsoft가 Apple보다 비효율적이다이지, 웹뷰 기반 기본 앱의 비용이 얼마다가 아니다.
후자가 실제로 유용한 정보이고 전자는 이미 널리 퍼진 인상의 재확인일 뿐이다.

비교 대상이 무너지는 증언도 나왔다.
hokkos는 Apple 날씨 앱도 지도에서 돌풍 방향 파티클 효과를 조금 눌러보면 Mac에서 1GB까지 뛴다고 전한다.[^hokkos]
그렇다면 250MB 대 1.2GB라는 대비는 두 앱의 효율 차이가 아니라 두 측정 시점의 상호작용 강도 차이일 수 있다.
기사는 Windows 쪽은 조작 중 값(1.5~1.6GB)까지 인용하면서 macOS 쪽은 유휴에 가까운 값만 인용했고, 이 비대칭이 다섯 배라는 숫자를 만들어냈다.

반대 방향의 지적도 있다.
eviks는 250MB도 이미 비대하며 이 정도 낭비를 보여주려면 더 나은 비교 대상을 찾았어야 한다고 말한다.[^eviks]
cherryteastain가 제시한 GNOME Weather의 80MB가 그 기준에 가깝고,[^cherryteastain] iamcoder18은 잘 설계된 네이티브 날씨 앱이라면 100MB를 넘지 않을 것이라고 본다.[^iamcoder18]
i-e-b는 셰익스피어 전집이 약 6MiB인데 나중에 비가 올지 알려주는 데 100MiB가 효율적이라고 여겨지는 것이 싫다고 적었다.[^i-e-b]
이 기준들을 적용하면 기사의 비판은 방향은 맞되 강도가 부족했던 셈이 된다.

가장 아픈 반례는 이 앱 자신의 과거다.
hadrien01은 같은 날씨 앱의 이전 버전이 Windows 10에서는 완전한 네이티브였다고 지적하며, 멀쩡히 동작하던 앱을 왜 이렇게 퇴보시켰느냐고 묻는다.[^hadrien01]
이 사실이 맞다면 문제는 웹 기술의 한계도 프레임워크의 특성도 아니라 순수한 선택이며, 기사가 든 Microsoft의 효율 개선 노력과의 모순은 훨씬 무거워진다.

## 인사이트

### 기본 앱은 사용자가 고르지 않으므로 비용이 사용자에게 전가된다

서드파티 앱이 램을 1GB 쓰면 사용자가 다른 앱을 고르면 된다.
그것이 시장이 작동하는 방식이고, 그래서 무거운 앱은 시장 압력을 받는다.
기본 앱에는 그 압력이 없다.

정확히 말하면 압력의 방향이 다르다.
사용자는 기본 앱을 삭제하거나 무시할 수 있지만, 그 선택을 하려면 먼저 문제를 알아야 하고 대안을 찾아야 하며 위젯이나 잠금화면 통합 같은 부가 이득을 포기해야 한다.
그래서 실제로는 대부분 그대로 쓰고, 비용은 조용히 흡수된다.

이 구조가 만드는 유인은 명확하다 — 기본 앱을 만드는 팀은 효율을 개선할 이유가 시장에서 오지 않는다.
개선 압력은 오직 내부 정책이나 언론 보도에서 온다.
이 기사가 하는 실질적 역할이 바로 그 두 번째 압력이며, 기술적으로 얕음에도 존재 가치가 있는 이유가 여기에 있다.

두 번째 함의는 플랫폼 사업자의 이중 지위다.
Microsoft는 저사양 PC에서 Windows가 잘 돌아야 한다고 말하는 주체이면서 동시에 그 PC에 무거운 앱을 기본 설치하는 주체다.
플랫폼과 앱을 같은 회사가 만들 때 앱 쪽 결정이 플랫폼 목표를 갉아먹어도 시정 기제가 없고, 이는 규제 논의에서 다뤄지는 자사 우대와는 다른 종류의 문제다 — 남을 밀어내는 것이 아니라 스스로를 망가뜨리는 형태다.

### 웹뷰로 감싼 데스크톱 앱의 비용은 메모리가 아니라 통제권 이전이다

램 1GB는 눈에 보이는 비용이라 기사가 된다.
보이지 않는 비용은 그 앱의 동작이 언제든 서버 쪽에서 바뀔 수 있다는 점이다.

네이티브 앱은 사용자가 설치한 버전이 그대로 돈다.
웹뷰 앱은 껍데기만 설치되어 있고 내용은 매번 서버에서 온다 — 광고 배치가 바뀌고, 레이아웃이 바뀌고, 추적 스크립트가 추가되어도 업데이트 없이 반영된다.
사용자 입장에서는 설치한 적 없는 소프트웨어가 계속 바뀌는 것이며, 오프라인에서는 아예 동작하지 않을 수도 있다.

이 관점에서 보면 램 사용량은 증상이지 병이 아니다.
Chromium 하위 프로세스 여러 개가 도는 이유는 그것이 웹 콘텐츠를 안전하게 격리하는 방법이기 때문이고, 격리가 필요한 이유는 그 콘텐츠가 신뢰 경계 밖에서 오기 때문이다.
즉 메모리 비용은 원격 콘텐츠를 실행한다는 선택의 직접적 귀결이며, 그 선택을 유지하는 한 최적화로 줄일 수 있는 폭은 제한적이다.

실무자에게 이 구분은 판단 기준을 준다.
데스크톱 앱을 웹뷰로 만들지 결정할 때 물어야 할 것은 램을 얼마나 쓰는가가 아니라 이 앱의 내용이 서버에서 와야 하는가다.
와야 한다면 웹뷰가 옳고 메모리 비용은 그 대가다.
오지 않아도 된다면 웹뷰는 개발 편의를 위해 사용자의 자원과 통제권을 함께 지불하는 선택이 된다.

feverzsj는 여기서 한 가지 실무적 질문을 던진다 — 앱마다 브라우저 하나씩이 아니라 모든 앱에 브라우저 하나를 쓸 수는 없느냐는 것이다.[^feverzsj]
Dwedit도 같은 진단을 내린다 — 이것이 도처에서 Chromium 인스턴스를 따로 띄울 때 벌어지는 일이라는 것이다.[^Dwedit]
기술적으로는 가능하지만 그러려면 앱들이 하나의 렌더러 프로세스 풀을 공유해야 하고, 그 순간 앱 간 격리가 약해진다.
지금의 낭비는 격리를 사기 위해 지불하는 값이며, 광고와 원격 콘텐츠를 실행하는 이상 그 격리를 포기하기도 어렵다.

cogman10은 이 문제를 언어 런타임 쪽으로 확장한다 — 운영체제 수준의 공유 GC 풀이 있어서 모든 GC 언어가 그 안에서 놀아야 한다고 점점 더 확신하게 된다는 것이다.[^cogman10]
단순한 애플리케이션이 기가바이트를 쓰는 큰 이유는 GC가 멈춤과 버벅임을 피하려고 최대한 자라기 때문이며, 그 1GB 중 실제로 살아 있는 것은 10%일 수 있다.
JVM 세 개를 돌리면서 각각 실제로는 200MB면 되는데 1GB씩 주는 상황을, 하나로 합칠 수 있다면 할당 오버헤드와 전체 메모리를 크게 아낄 수 있다는 논리다.
이 관점은 낭비의 책임을 앱에서 런타임 설계로 옮기며, 웹뷰든 JVM이든 여유 메모리를 성능으로 바꾸는 모든 런타임에 같은 진단이 적용된다는 점에서 이 사건을 더 넓은 문제의 사례로 만든다.

### 이 사건은 데스크톱 앱 크기 인플레이션의 최신 사례이고, 그 곡선은 하드웨어 곡선을 따른다

날씨를 보여주는 프로그램이 1GB를 쓴다는 사실이 충격적으로 들리는 이유는 그 작업의 본질적 복잡도가 낮기 때문이다.
그런데 소프트웨어 크기는 언제나 본질적 복잡도가 아니라 가용 자원을 따라 커져 왔다.

이 현상에는 이름이 여럿 붙어 있다 — Wirth의 법칙, Andy와 Bill의 법칙, 소프트웨어 비만화.
그리고 매 세대마다 같은 형태의 기사가 나왔다.
텍스트 편집기가 메가바이트를 넘겼을 때, 채팅 앱이 수백 메가바이트를 쓰기 시작했을 때, 그리고 지금 날씨 앱이 기가바이트를 넘겼을 때다.
공통점은 증가가 기능 때문이 아니라 배포와 개발 편의를 위한 추상 계층 때문이라는 점이다.

여기서 나오는 예측은 비관적이다.
8GB 시스템이 문제라는 서술은 8GB가 여전히 흔하다는 뜻인데, 표준 메모리 용량이 16GB로 올라가면 이 기사의 논거 자체가 약해진다.
그리고 그 시점에 앱들은 다시 자라 있을 것이다.
즉 이 문제는 특정 앱을 고쳐서 해결되지 않고, 하드웨어가 앞서가는 동안 반복된다.

다만 이번 세대에는 이전과 다른 변수가 하나 있다.
로컬 AI 기능이 램을 대량으로 요구하기 시작했고, Microsoft 자신이 그 방향으로 가고 있다.
온디바이스 모델이 상시 메모리를 점유하는 환경에서는 남는 여유가 줄어들고, 그러면 지금까지 무해했던 앱들의 낭비가 갑자기 문제가 된다.
Microsoft가 저사양 효율을 강조하기 시작한 배경에 이 계산이 있을 가능성이 크고, 그렇다면 기본 앱의 메모리 예산은 취향 문제가 아니라 제품 전략의 제약 조건이 된다.

Wowfunhappy가 이 전환을 정확히 짚는다.[^Wowfunhappy]
메모리 가격 이야기를 계속 듣게 되는데 15년 전보다는 여전히 기가바이트당 훨씬 싸며, 중요한 것은 소비자가 컴퓨터로 하는 일이 지난 15년간 별로 바뀌지 않았다는 점이다 — 웹을 보고 사진을 편집하고 친구와 메시지를 주고받는 일이고, AI는 대개 원격 서버에서 돈다.
수년간 모두가 Electron이 기가바이트를 써도 괜찮다고 말했던 이유는 현대 PC에 메모리가 넉넉했기 때문인데, 이제 넉넉하지 않다는 것이다.
ndriscoll는 다른 방향에서 같은 대비를 만든다 — 2006년에 조립한 게이밍 PC로 1680x1050 화면에서 Battlefield 2, Trillian, Xfire, Thunderbird, Winamp를 동시에 돌렸는데 시스템 전체 램이 1GB였다는 것이다.[^ndriscoll]

이 스레드에서 반복된 또 하나의 기대는 LLM이 이 곡선을 되돌릴 수 있다는 것이다.
polyterative는 자기 Mac에서 돌던 독점 드라이버와 동반 소프트웨어를 AI로 다시 쓰고 있으며, 원본의 5~10% 램으로 더 많은 기능을 얻었고 여러 개를 자기 버전으로 바꾼 뒤 백그라운드 램 사용량이 절반이 되었다고 보고한다.[^polyterative]

어느 쪽이 맞든 이 관찰은 낭비의 원인이 기술이 아니라 경제였음을 다시 확인시킨다 — 최적화 비용이 내려가면 최적화가 일어나고, 그 비용을 결정하는 것이 지금은 도구다.

### 광고가 들어간 기본 앱은 운영체제의 신뢰 모델을 조금씩 깎는다

기사는 광고를 비판이 있었다는 사실로만 언급하고 넘어가지만, 이 부분이 장기적으로는 메모리보다 중요할 수 있다.

운영체제의 기본 앱은 사용자가 검증하지 않고 신뢰하는 소프트웨어다.
그 신뢰는 이 프로그램은 내 이익을 위해 동작한다는 전제 위에 있고, 광고가 들어가는 순간 그 전제가 깨진다 — 예보 피드에 후원 콘텐츠가 날씨 카드와 같은 양식으로 섞인다는 것은 어떤 항목이 정보이고 어떤 항목이 광고인지 사용자가 구분하기 어렵게 설계되었다는 뜻이다.

이 침식은 개별 앱에서 끝나지 않는다.
기본 앱이 광고를 보여준다는 경험이 쌓이면 사용자는 시작 메뉴의 추천, 검색 결과, 알림도 같은 눈으로 보게 된다.
그리고 한 번 그렇게 읽히기 시작하면 실제로 유용한 기능까지 광고로 의심받는다.

여기에 메모리 이야기가 다시 연결된다.
사용자가 날씨 앱에 대해 램을 많이 쓰고 광고를 보여준다는 두 가지를 동시에 알게 되면, 결론은 이 앱은 나를 위한 것이 아니다가 된다.
그리고 그 결론은 하나의 앱이 아니라 그 앱을 기본으로 넣은 주체에 대한 판단으로 옮겨간다.
기술 부채는 갚을 수 있지만 이런 종류의 신뢰 손실은 개별 앱을 고쳐도 회복되지 않으며, 그것이 이 작은 기사가 반복해서 화제가 되는 진짜 이유다.

그리고 이 판단은 제품을 떠나 플랫폼으로 옮겨간다.
