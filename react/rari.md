## 소개

rari는 Rust 런타임 위에서 도는 React Server Components 프레임워크다.
이름은 “Runtime Accelerated Rendering Infrastructure”의 축약이고, README는 이 프로젝트가 세 계층으로 이루어진다고 설명한다.
V8을 내장한 HTTP 서버와 RSC 렌더러와 라우터로 이루어진 Rust 런타임, 앱 라우터와 서버 액션과 스트리밍/서스펜스를 갖춘 React 프레임워크, 그리고 Rolldown 기반 Vite 번들링과 TypeScript 7 타입 검사로 이루어진 빌드 도구 사슬이다.
표준 React를 쓰되 그 아래 런타임이 Node가 아니라 Rust라는 것이 한 줄 요약이다.

저장소는 2025년 7월 26일에 만들어졌고, 이 문서 갱신 시점 기준 스타 1,167개, 포크 31개, 열린 이슈 3개이며 라이선스는 MIT다.
npm의 `rari`는 163개 버전이 올라와 있고 최신은 0.15.9이며 지난 한 달 다운로드는 4,162회, `create-rari-app`은 1,070회다.
기여자는 7명으로 집계되지만 `skiniks`가 2,915건이고 두 번째가 17건이라 사실상 1인 프로젝트이며, 커밋은 2026년 8월 10일까지 이어진다.
후원사로 Namespace와 Neon이 README에 표시되어 있다.

기능 목록은 열한 가지다.
레이아웃과 로딩 상태와 에러 경계를 갖춘 파일 기반 앱 라우터, 사전 렌더링된 HTML과 즉시 하이드레이션을 제공하는 서버 사이드 렌더링, 기본이 서버 컴포넌트이고 필요할 때 클라이언트 컴포넌트를 쓰는 RSC, V8을 내장한 Rust로 작성된 HTTP 서버와 RSC 렌더러와 라우팅, 사전 빌드 바이너리로 즉시 동작하는 무설정 초기화, 핫 모듈 리로딩, `npm:` 지정자 없이 표준 npm 패키지를 해석하는 `node_modules` 지원, 서버와 클라이언트 경계를 가로지르는 타입 안전성, macOS와 리눅스와 윈도우 지원, 서스펜스 경계를 통한 스트리밍 SSR, 내비게이션 중 자동 로딩 스켈레톤이다.
시작은 `npm create rari-app@latest my-app` 한 줄이고 개발 서버는 5173 포트에서 돈다.

성능 주장이 README의 가장 큰 부분을 차지한다.
2026년 8월 10일 v0.15.9 기준으로 갱신되었다고 표시된 표에서, 단일 요청 응답 시간이 평균 0.12ms 대 Next.js 1.74ms로 14.5배 빠르고 P95는 0.12ms 대 2.44ms로 20.3배 빠르며 번들은 287KB 대 573KB로 50% 작다고 적는다.
50개 동시 접속 30초 부하에서는 초당 89,371 요청 대 1,683 요청으로 53.1배 높고 평균 지연이 0.56ms 대 29.73ms이며 오류는 양쪽 다 0이다.
빌드는 1.12초 대 3.88초로 3.5배 빠르다고 한다.
스트리밍 항목은 다른 양상인데, TTFB는 1ms 대 12ms로 11.1배 빠르지만 첫 콘텐츠는 107ms 대 108ms이고 마지막 바이트는 1007ms 대 1009ms로 비슷하며 처리량은 초당 24.99건으로 동일하다.
README는 마지막 바이트 시간이 프레임워크 오버헤드가 아니라 의도적인 1000ms 카드 지연에 지배된다는 단서를 붙이고, 모든 벤치마크가 재현 가능하며 방법론과 도구는 별도 저장소에 있다고 안내한다.

벤치마크 저장소는 측정 대상을 명시한다.
홈페이지는 Counter와 TestComponent와 ShoppingList를 비롯한 8개의 서버 컴포넌트를 정적으로 렌더링하고, `/stream`은 점진적 RSC 전달을 위해 지연이 몰려 있는 10개의 서스펜스 경계를 쓴다.
측정 항목은 서버 렌더링 속도, TTFB의 P50·P95·P99, 스트리밍 전달, 번들 크기, 빌드 시간, 부하 시 처리량, 부하 시 메모리 사용량이다.

숫자는 시간에 따라 크게 달라졌다.
2025년 11월 GeekNews에 소개될 당시에는 P99 지연 12배와 처리량 10.5배(초당 20,226 요청), 응답 속도 3.8배(0.69ms 대 2.58ms), 번들 68% 감소(27.6KB 대 85.9KB), 빌드 5.6배(1.64초 대 9.11초)였고 스트리밍 RSC와 서스펜스는 개발 중이라고 표시되어 있었다.
2026년 2월 HN 스레드에서 저자는 46.5배라고 적었고, 2026년 6월 자체 블로그 글의 제목은 67배였으며, 현재 README는 53.1배다.

저자의 블로그 글 「Building rari with rari」가 그 숫자의 성격을 직접 설명한다.
따뜻한 캐시 상태의 성능이 가장 큰 이득을 내는 지점이며 67배라는 처리량 우위는 재렌더링 없이 사전 압축된 응답을 제공하는 데서 온다고 밝힌다.
`loading.tsx`가 없는 페이지는 이 캐시 경로를 쓰고 `loading.tsx`가 있는 페이지는 스트리밍 SSR을 써서 요청마다 실제 렌더링을 수행하며, 콜드 렌더와 스트리밍 페이지는 서버 처리 시간이 2~3ms에 가깝다고 적는다.
그리고 67배는 최선의 경우인 캐시된 응답을 나타내며 모든 경우가 아니라고 명시한다.

같은 글이 구조도 설명한다.
HTTP 서버는 axum이고 여러 OS 스레드에서 요청을 처리하며, JavaScript 런타임은 V8을 감싼 `deno_core::JsRuntime`이 자기 전용 스레드에서 별도의 단일 스레드 tokio 런타임과 함께 돈다.
둘은 메시지 채널로 통신하는데 그 채널은 캐시 미스에서만 쓰이므로, 라우트가 한 번 렌더링되어 캐시되면 HTTP 스레드가 메시지 없이 응답을 제공하고 JS 스레드가 멈춰 있어도 캐시된 라우트는 전속력으로 서빙된다.
요청이 오면 axum이 응답 캐시를 먼저 확인하고 적중이면 HTTP 스레드의 메모리에서 제공하며 V8은 깨어나지 않는다고 적는다.
V8은 렌더링할 것이 있을 때만 돌고 실질적으로는 라우트의 첫 요청이며, 그 결과가 RSC Flight 프로토콜로 돌아와 HTML로 변환되고 zstd로 압축되어 캐시된 뒤로는 그 라우트에 대해 JS 스레드가 유휴 상태가 된다는 설명이다.
같은 글은 첫 버전이 Next.js보다 4배 빨랐고 현재는 67배인데 Rust도 도움이 되었지만 이득의 대부분은 제대로 된 SSR과 응답 캐싱과 올바른 RSC 의미론이라는 아키텍처 변경에서 왔다고 밝힌다.
운영 지표로는 서버가 500MB 미만으로 돌며 관측 도구를 갖춘 대형 SSR React 애플리케이션이 흔히 1~2GB에서 유휴 상태인 것과 대비된다고 적는다.

## 분석

### 세 계층 중 실제 차별점은 두 번째가 아니라 첫 번째다

README가 세운 세 계층 가운데 React 프레임워크 계층과 빌드 도구 사슬 계층은 대체 가능한 것들이다.
앱 라우터와 서버 액션과 스트리밍은 Next.js와 TanStack Start와 React Router가 모두 제공하고, Rolldown 기반 Vite 번들링과 TypeScript 타입 검사도 마찬가지다.
남는 것은 첫 번째 계층, 곧 V8을 내장한 Rust HTTP 서버다.

저자가 HN에서 이 계층을 설명한 방식이 정확하다.
`splix`가 Deno VM을 돌리는 것이냐고 묻자, 전체 Deno VM이 아니라 `deno_core` 바인딩을 통해 V8을 Rust 런타임에 직접 내장한 것이며 WebAssembly로 컴파일하지 않고 JavaScript를 V8에서 바로 실행한다고 답했다.
`deno_core`가 V8의 C++ API에 깔끔한 Rust 바인딩을 제공하므로 최소 오버헤드로 JS/TypeScript를 돌릴 수 있고, 모듈 해석과 임포트와 React 렌더링 파이프라인을 전부 Rust에서 처리한 뒤 실제 컴포넌트 코드를 V8에서 실행하며, 대가는 V8에 묶인다는 것이라고 밝혔다.[^splix-reply]

이 구조가 [ssr_rs 노트](../rust/ssr-rs.md)에서 정리한 것과 같은 계열이라는 점이 흥미롭다.
그쪽도 `rusty_v8`로 V8을 Rust에 심어 React를 렌더링하고, 그 위에 [Tuono](../rust/tuono.md)라는 프레임워크가 얹혔다.
rari는 같은 조합을 하나의 프로젝트 안에서 수직으로 통합했으며, 그래서 `mpeg`가 이것이 사실 두 가지 일을 하고 있다고 정리한 것이 정확하다.
하나는 Next.js나 TanStack이나 React Router 같은 RSC 프레임워크이고, 다른 하나는 Node나 Deno나 Bun 같은 JavaScript용 Rust 런타임이되 아마 그만큼 범용은 아닌 것이다.[^mpeg-two]

### 벤치마크의 정체를 저자 자신의 블로그가 밝힌다

README의 표는 초당 89,371 요청과 0.12ms 응답 시간을 내세우는데, 이 숫자가 무엇을 잰 것인지는 저장소가 아니라 블로그에 있다.
요청이 오면 axum이 응답 캐시를 확인하고 적중이면 메모리에서 제공하며 V8은 깨어나지 않는다는 서술, 그리고 67배가 재렌더링 없이 사전 압축된 응답을 제공하는 데서 온다는 서술이 그것이다.

이 사실을 알고 나면 숫자가 갑자기 자연스러워진다.
0.12ms 응답 시간은 React 컴포넌트 트리를 렌더링한 시간이 아니라 zstd로 미리 압축해 둔 바이트 버퍼를 메모리에서 꺼내 소켓에 쓴 시간이다.
초당 89,371 요청도 마찬가지로 렌더링 처리량이 아니라 axum의 정적 응답 처리량이다.
반대편 Next.js 1,683 요청은 요청마다 실제로 렌더링한 결과다.

같은 블로그가 이 대비를 스스로 인정한다.
콜드 렌더와 스트리밍 페이지는 서버 처리 시간이 2~3ms에 가깝다는 문장이 그것이며, 그 값은 Next.js의 1.74ms와 같은 자릿수다.
README의 스트리밍 표가 이를 뒷받침한다.
TTFB만 11.1배 빠르고 첫 콘텐츠는 107ms 대 108ms, 마지막 바이트는 1007ms 대 1009ms, 처리량은 24.99 대 24.99로 완전히 같다.
곧 실제 렌더링이 일어나는 경로에서는 두 프레임워크가 구별되지 않는다.

저자가 4배에서 67배로 간 경위를 설명하며 Rust도 도움이 되었지만 이득의 대부분이 아키텍처 변경, 곧 제대로 된 SSR과 응답 캐싱과 올바른 RSC 의미론에서 왔다고 적은 것이 결정적이다.
이 프로젝트의 성능 이야기는 언어 이야기가 아니라 캐시 이야기이며, 저자 본인이 그렇게 말한다.

### “Rust-powered”라는 표현이 반복해서 오해를 만든다

HN 스레드에서 가장 자주 반복된 것은 성능 논쟁이 아니라 “이게 뭐냐”는 질문이었다.
`dev_l1x_be`는 궁금해하는 사람을 위해서라며 “Rust 런타임으로 구동되는 React Server Components 프레임워크”라는 한 줄을 그대로 옮겨 적었고[^devl1xbe], `desireco42`는 그것이 무엇인지 알아내려고 댓글로 왔으며 이제 사이트로 돌아가 볼 수 있겠다고 답했다.[^desireco]
`samrith`는 웹사이트를 다 봤지만 왜 Actix나 그냥 오래된 Express 서버 대신 rari를 써야 하는지, “Rust로 구동되는 성능”이 무엇인지 즉시 분명하지 않다고 적었다.[^samrith]
`satvikpendem`은 ReasonML과 React-Reason 같은 것이냐며 어느 부분이 Rust로 구동되는지, JS 엔진을 Rust로 다시 구현한 것이냐고 물었고[^satvik], `CrociDB`는 프런트엔드를 전혀 모르는데 이것이 React를 실제 JavaScript와 DOM 호출로 바꾸는 Rust 컴파일러냐고 물었다.[^crocidb]

`mpeg`의 반응이 가장 구체적이었다.
자신은 “rust-powered”가 JavaScript를 번들링하는 데 Rolldown을 쓴다는 뜻인 줄 알았고 그것은 괜찮지만 강조할 만한 이상한 것이며, Vite에 아주 익숙하지 않은 사람에게는 혼란스럽고 이것이 Rust 프레임워크라고 생각하게 만들 수 있다는 것이다.
문서에서 “rari의 초능력 중 하나는 매끄러운 NPM 패키지 통합”이라는 문장을 보고 문서가 LLM이 쓴 것 같다는 인상을 받았다고도 적었다.
그러면서도 좋은 점으로 React용 단순한 프레임워크가 아주 적은데 빈 프로젝트에서 RSC까지 가는 단순함이 대단히 좋으며 그것이 표어여야 한다고 했다.[^mpeg]

저자의 답이 정직했다.
메시지가 혼란스럽다는 것이 맞으며 자신이 전부 혼자 써 왔으므로 문구를 돕는 PR을 환영한다고 밝히고, “Rust-powered”가 번들러가 아니라 서버 런타임 자체를 가리키며 HTTP 서버와 RSC 렌더러와 라우팅이 전부 Rust로 작성되었다고 정정했다.
npm 통합에 대해서는 rari의 Rust 런타임이 전통적인 `node_modules` 해석을 처리하며 이것이 Rust 기반 JS 런타임에서는 꽤 드문 일이고 예컨대 Deno는 npm 지정자를 대신 쓴다고 말했어야 했다고 덧붙였다.[^skiniks-clarify]

`lionkor`가 이 명명 문제를 한 줄로 압축했다.
V8은 C++인데 왜 “C++로 구동된다”고는 하지 않느냐는 것이다.[^lionkor]

### 1인 프로젝트가 Next.js를 비교 대상으로 고른 대가

저장소 설명 자체가 Next.js와의 배수 비교로 되어 있다.
“Next.js보다 14.5배 빠른 응답 시간(0.12ms 대 1.74ms)과 53.1배 높은 처리량(89,371 대 1,683 req/sec)을 제공하는 무설정 초기화”라는 문장이 GitHub 검색 결과와 링크 미리보기에 그대로 노출된다.

이 선택에는 분명한 이득이 있다.
Next.js는 이 영역에서 모두가 아는 기준점이고, 배수 하나로 관심을 얻을 수 있으며, 실제로 HN에서 135점을 받았다.
1인이 마케팅 자원 없이 눈에 띄어야 하는 상황에서 합리적인 선택이다.

대가는 평가 기준도 함께 따라온다는 점이다.
Next.js를 기준점으로 삼는 순간 사용자는 미들웨어와 증분 정적 재생성과 이미지 최적화와 국제화와 배포 생태계 전부를 기대하게 되고, 성능 배수 하나로는 그 기대를 채울 수 없다.
더 직접적으로는 그 배수 자체가 검증 대상이 되며, 다음 절에서 보듯 검증에서 약해진다.

공개 당일의 사고가 이 대가를 상징적으로 보여 준다.
`mattrighetti`는 웹사이트가 트래픽에 눌렸다고 적었고[^mattrighetti] `tuhgdetzhh`는 그것이 rari의 성능 주장에 좋은 광고가 아니라고 했다.[^tuhgdetzhh]
저자는 rari 자체는 트래픽을 잘 처리했고 문제는 자신이 설정한 과도하게 방어적인 속도 제한기였으며 프록시 트래픽을 잘못 묶고 있었다고 해명했다.[^skiniks-rate]
해명은 사실일 것이고 뒤에 블로그에서 HN 트래픽 중에도 메모리가 기준선을 유지했다고 다시 밝혔지만, 성능을 표제로 삼은 프로젝트의 사이트가 첫날 응답하지 않았다는 인상은 남는다.

## 비평

### 표제 숫자에서 단서가 사라진다

블로그는 67배가 최선의 경우인 캐시된 응답을 나타내며 모든 경우가 아니라고 명시한다.
이것은 좋은 문장이고 이 프로젝트의 정직함을 보여 준다.
문제는 그 문장이 README에도, 저장소 설명에도, GitHub 링크 미리보기에도 없다는 점이다.

README의 표는 “단일 요청 응답 시간”과 “부하 시 처리량”이라는 중립적 제목 아래 숫자를 놓는다.
어느 쪽에도 캐시라는 단어가 없다.
스트리밍 표에서 처리량이 24.99 대 24.99로 같다는 사실이 사실상 단서 역할을 하지만, 그것을 읽어 내려면 캐시 경로와 렌더링 경로가 다르다는 것을 이미 알아야 한다.
그 지식은 별도 블로그 글에 있다.

이 배치가 만드는 결과는 예측 가능하다.
HN에서 `satvikpendem`은 저자가 Next보다 처리량이 약 50배 높다고 말했다고 요약했고, `re-thc`가 “Node 기준으로 말이겠죠?”라고 되물었다.[^satvik-50x][^rethc-node]
두 사람 다 그 숫자가 렌더링 처리량이라고 전제하고 대화했으며, 아무도 캐시를 언급하지 않았다.
저자도 그 갈래에는 답하지 않았다.

비교 가능한 서술로 바꾸는 데 필요한 것은 한 문장이다.
캐시 적중 경로에서는 초당 89,371 요청이고 렌더링 경로에서는 서버 처리 시간이 2~3ms라는 두 값을 나란히 놓으면 된다.
후자를 함께 적으면 표가 훨씬 유용해지는데, 실제 애플리케이션의 성능은 두 값 사이 어딘가에 캐시 적중률로 결정되기 때문이다.

### 숫자가 계속 바뀌는데 무엇이 바뀌었는지는 알 수 없다

같은 비교의 결과가 아홉 달 사이에 네 번 달라졌다.

| 시점        | 출처              | 처리량 주장            | 번들 비교         |
| ----------- | ----------------- | ---------------------- | ----------------- |
| 2025년 11월 | GeekNews 소개     | 10.5배 (20,226 req/s)  | 27.6KB 대 85.9KB  |
| 2026년 2월  | HN 저자 댓글      | 46.5배                 | —                 |
| 2026년 6월  | 자체 블로그 제목  | 67배                   | —                 |
| 2026년 8월  | README v0.15.9    | 53.1배 (89,371 req/s)  | 287KB 대 573KB    |

숫자가 오르는 것은 개선의 표시일 수 있으므로 그 자체가 문제는 아니다.
문제는 번들 비교다.
27.6KB 대 85.9KB에서 287KB 대 573KB로 양쪽이 모두 10배 커졌다는 것은 벤치마크 애플리케이션이 통째로 달라졌다는 뜻이며, 그렇다면 앞뒤 숫자를 같은 축에 놓고 개선으로 읽을 수 없다.
같은 기간 Next.js의 응답 시간은 2.58ms에서 1.74ms로 빨라졌는데 처리량은 초당 약 1,926건에서 1,683건으로 느려졌다.
한 시스템이 응답은 빨라지고 처리량은 줄어드는 것이 불가능하지는 않지만 설명이 필요한 조합이다.

블로그가 4배에서 67배로 간 경위를 설명하며 앱 라우터 지원과 올바른 RSC 의미론과 사전 압축 응답 캐시를 이유로 든 것이 유일한 설명이고, 그것도 서술이지 데이터가 아니다.
벤치마크 저장소는 방법론과 도구를 담고 있고 재현 가능하다고 안내하지만, 버전별 결과의 이력은 담고 있지 않다.
README가 “벤치마크 최종 갱신: 2026년 8월 10일(rari v0.15.9)”이라고 날짜를 적는 것은 좋은 관행인데, 그 앞의 숫자들이 어디 갔는지는 알 수 없다.

이 상태가 실무자에게 만드는 비용은 신뢰의 문제다.
성능이 유일한 표제 주장인 프로젝트에서 그 숫자가 분기마다 크게 바뀌고 변경 근거가 산문으로만 있으면, 다음 숫자도 같은 정도로만 신뢰할 수 있다.

### 비교 대상이 잘못 골라져 있다

`re-thc`가 이 문제를 정확히 짚었다.
Bun이나 Deno에 Next.js나 TanStack Start나 React Router를 얹은 구성과 성능을 비교하는 편이 더 흥미로울 것이라는 지적이다.[^rethc-compare]
`laurencerowe`도 같은 방향에서 물었다.
HTTP 서버가 역시 Rust로 작성된 Deno에서 같은 React 코드를 돌리는 것과 무엇이 다르냐는 것이다.[^laurencerowe]

두 질문 모두 답이 달리지 않았고, 벤치마크 저장소도 Next.js 하나만 상대한다.
이것이 문제인 이유는 rari의 주장이 두 겹이기 때문이다.
“Rust 런타임이 Node보다 빠르다”는 주장과 “응답 캐싱이 매번 렌더링하는 것보다 빠르다”는 주장이 섞여 있는데, Next.js 하나와만 비교하면 두 요인이 분리되지 않는다.
Deno나 Bun 위의 Next.js와 비교하면 런타임 요인이 분리되고, 캐시를 끈 rari와 비교하면 캐싱 요인이 분리된다.
둘 다 없다.

기준선의 구성도 명시되지 않았다.
`re-thc`가 “Node 기준으로 말이겠죠?”라고 물은 것[^rethc-node]이 그 공백을 가리킨다.
Next.js를 어떤 모드로 빌드했는지, 몇 개의 워커로 띄웠는지, 프로덕션 구성인지가 벤치마크 저장소의 README에는 나오지 않는다.
초당 1,683 요청이라는 값은 단일 프로세스 Next.js에 가까운 수치이고, 코어 수만큼 인스턴스를 띄운 구성에서는 달라진다.
[Tuono의 벤치마크 저장소](../rust/tuono.md)가 Next.js를 `pm2`로 띄우면서도 인스턴스 수를 밝히지 않아 같은 문제를 남긴 것과 정확히 같은 종류의 공백이다.

### 캐시가 기본 동작이면 무효화가 프레임워크의 책임이 된다

블로그의 서술에 따르면 `loading.tsx`가 없는 페이지는 캐시 경로를 타고 있는 페이지는 스트리밍 경로를 탄다.
곧 응답 캐싱 여부가 파일 하나의 존재로 결정되며, 개발자가 캐시를 켠 기억이 없어도 캐시가 동작한다.

이 설계가 성능 숫자를 만들지만 정확성 문제도 함께 만든다.
서버 컴포넌트가 데이터베이스를 읽는다면 그 결과가 zstd로 압축되어 메모리에 남고, 데이터가 바뀌어도 캐시가 무효화되지 않는 한 옛 HTML이 서빙된다.
README와 블로그 어디에도 무효화 정책에 대한 서술이 없다.
얼마나 오래 유지되는지, 쓰기 후에 어떻게 비우는지, 사용자별로 다른 콘텐츠를 어떻게 구분하는지가 문서화되어 있지 않다.

특히 마지막 항목이 위험하다.
로그인한 사용자마다 다른 내용을 렌더링하는 서버 컴포넌트가 URL만으로 캐시된다면 한 사용자의 응답이 다른 사용자에게 갈 수 있다.
Next.js가 라우트 세그먼트 설정과 `dynamic` 옵션과 `cookies()` 호출에 따른 자동 동적 전환 같은 장치를 여러 겹으로 둔 이유가 정확히 이 문제이며, 그 복잡성이 Next.js를 느리게 만드는 요인이기도 하다.
rari가 그 복잡성을 걷어내고 얻은 속도라면 걷어낸 것이 무엇인지가 함께 문서화되어야 한다.

이것이 앞 절의 벤치마크 문제와 이어지는 지점이다.
캐시를 끈 상태의 rari와 Next.js를 비교하면 두 프레임워크가 같은 일을 하는 상태에서의 차이가 나오고, 그 차이가 이 프로젝트의 진짜 공학적 성취다.
캐시를 켠 상태의 rari와 캐시가 없는 Next.js를 비교한 53.1배는 두 가지 다른 것을 비교한 값이다.

## 인사이트

### 이 프로젝트의 진짜 발명은 압축된 응답 캐시이고 그것은 Rust와 무관하다

블로그가 밝힌 아키텍처를 다시 보면 성능의 출처가 분명하다.
axum이 요청을 받아 캐시를 확인하고, 적중이면 zstd로 미리 압축된 바이트를 그대로 소켓에 쓰고, V8은 깨어나지 않는다.
미스일 때만 메시지 채널로 JS 스레드에 넘어가 렌더링하고 그 결과를 압축해 캐시한다.

이 구조에서 Rust가 기여하는 것은 두 가지다.
캐시 적중 경로가 GC 없는 언어에서 도는 것과, HTTP 계층이 여러 OS 스레드에서 도는 것이다.
그런데 이 두 가지는 Node에서도 근사할 수 있다.
Node의 `cluster`로 코어만큼 프로세스를 띄우고 렌더링 결과를 미리 압축해 `Buffer`로 들고 있다가 그대로 쓰면 같은 경로가 만들어지며, 그 경로의 처리량은 Node에서도 수만 건 단위가 나온다.
곧 53.1배의 대부분은 언어가 아니라 “렌더링하지 않는다”에서 온다.

이 관찰이 프로젝트를 깎아내리는 것은 아니다.
사전 압축 응답 캐시를 프레임워크 기본값으로 만들고 라우트 단위로 자동 적용한 것은 실제로 유용한 설계 결정이며, 대부분의 팀이 Next.js에서 같은 효과를 얻으려면 CDN이나 리버스 프록시를 앞에 두고 캐시 헤더를 조율해야 한다.
그 일을 프레임워크가 대신한다는 것이 팔 만한 가치다.

다만 그렇게 팔면 비교 대상이 바뀐다.
Rust가 Node보다 빠르다는 이야기가 아니라 프레임워크가 캐싱을 내장했다는 이야기가 되고, 그러면 경쟁 상대는 Next.js의 런타임이 아니라 Next.js의 캐싱 모델이다.
그 축에서의 비교는 아직 아무도 하지 않았다.

### 벤치마크 숫자가 마케팅이 되면 그 숫자가 로드맵을 정한다

저장소 설명 문장 안에 배수가 들어 있다는 사실이 이 프로젝트의 구조를 말해 준다.
GitHub 설명은 프로젝트가 무엇인지를 적는 자리인데 거기에 “14.5배”와 “53.1배”가 들어가 있고, README의 절반 가까이가 성능 표이며, 블로그 글의 제목도 배수다.

이 배치가 만드는 되먹임이 있다.
숫자가 제품의 정체성이 되면 다음 릴리스에서 그 숫자를 올리는 것이 목표가 되고, 숫자를 올리는 가장 확실한 방법은 캐시 적중률을 높이는 것이다.
실제로 4배에서 67배로 간 경로가 정확히 그것이었고, 저자 본인이 이득의 대부분이 응답 캐싱에서 왔다고 적었다.

문제는 캐시가 프레임워크의 정확성 예산을 쓴다는 점이다.
앞서 짚은 무효화와 사용자별 콘텐츠 문제는 캐시를 공격적으로 쓸수록 커지며, 성능 숫자를 지키려는 압력과 정확성을 지키려는 압력이 반대 방향으로 작용한다.
`loading.tsx`의 존재 여부로 캐시 경로가 갈리는 현재 설계는 그 긴장이 이미 API 표면에 드러난 상태다.
로딩 스켈레톤이 필요한지를 정하는 파일이 캐싱 정책도 정한다면, 개발자는 UI 결정을 내리면서 성능과 정확성 결정을 함께 내리고 있는 것이다.

여기서 나오는 일반적 교훈은 성능을 정체성으로 삼은 프로젝트를 볼 때 그 숫자가 어느 예산에서 나왔는지를 물으라는 것이다.
계산을 더 빨리 해서 나온 숫자는 지속되고, 계산을 하지 않아서 나온 숫자는 조건부다.
후자를 표제로 삼으면 그 조건이 무너지는 순간 제품의 정체성도 함께 무너진다.

### 언어를 브랜드로 쓰는 관행에 비용이 있다

`lionkor`의 한 줄, 곧 V8은 C++인데 왜 “C++로 구동된다”고 하지 않느냐는 질문[^lionkor]은 농담처럼 보이지만 정확한 지적이다.
rari에서 React 컴포넌트를 실제로 실행하는 것은 C++로 쓰인 V8이고, Rust는 그 주위의 HTTP와 라우팅과 캐시를 담당한다.
“Rust로 구동되는 React”라는 문구는 참이면서 동시에 어디가 Rust인지를 알려 주지 않는다.

그 결과가 HN 스레드의 절반이다.
Rolldown 얘기냐고 묻고, ReasonML 같은 것이냐고 묻고, JS 엔진을 Rust로 다시 구현했냐고 묻고, React를 JavaScript로 바꾸는 컴파일러냐고 묻는다.
질문 다섯 개에 저자가 각각 답해야 했고, 그중 하나는 “궁금해하실 분들을 위해”라며 다른 사용자가 한 줄 요약을 대신 붙여 주는 형태로 나왔다.

이 관행이 지금 흔하다는 점이 문제를 키운다.
같은 시기에 나온 [Topcoat](../rust/topcoat.md)과 [Tuono](../rust/tuono.md)와 [Dioxus](../rust/dioxus.md)가 모두 Rust를 이름표로 달고 있고, 각각이 Rust로 하는 일이 다르다.
Topcoat은 Rust 표현식을 JavaScript로 교차 컴파일하고, Tuono는 Rust 서버가 V8을 통해 React를 렌더링하며, Dioxus는 UI 자체를 Rust로 쓴다.
세 가지가 전혀 다른 제품인데 표어가 구분되지 않으므로, 독자는 매번 아키텍처 설명을 찾아 읽어야 하고 그 설명은 대개 README가 아니라 댓글에 있다.

`mpeg`가 제안한 대안이 이 문제의 해법을 보여 준다.
빈 프로젝트에서 RSC까지 가는 단순함이 대단히 좋으며 그것이 표어여야 한다는 것이다.[^mpeg]
언어가 아니라 사용자가 겪는 것을 표어로 삼으라는 조언이며, 그렇게 하면 검증 대상이 배수에서 경험으로 옮겨 간다.

### 이 계층의 진짜 경쟁자는 Next.js가 아니라 CDN이다

응답을 미리 렌더링해 압축해 두고 메모리에서 서빙하는 것은 새로운 발상이 아니다.
그것은 정적 사이트 생성이고, 그 앞에 CDN을 두는 것이 지난 10년의 표준 배포 형태다.
rari가 초당 89,371 요청을 낸다는 것은 하나의 오리진 인스턴스가 낼 수 있는 값이고, CDN은 같은 콘텐츠를 전 세계 엣지에서 그보다 훨씬 큰 규모로 서빙한다.

그렇다면 이 프레임워크가 이기는 자리는 CDN이 이기지 못하는 자리여야 한다.
그 자리는 캐시 키가 URL만으로 정해지지 않는 경우, 곧 사용자별로 다르거나 데이터가 자주 바뀌어 무효화 지연이 문제가 되는 경우다.
공교롭게도 그것이 앞서 비평에서 짚은 미문서화 영역과 정확히 겹친다.
프레임워크 안에 캐시를 두는 것의 유일한 우위는 애플리케이션 상태를 알고 있다는 점인데, 그 앎을 어떻게 쓰는지가 설명되어 있지 않다.

이 관점이 벤치마크의 설계도 다시 보게 만든다.
벤치마크 저장소가 재는 홈페이지는 8개의 서버 컴포넌트를 정적으로 렌더링하는 페이지다.
정적으로 렌더링되는 페이지라면 그것은 빌드 시점에 구울 수 있는 페이지이며, 그런 페이지의 런타임 처리량을 재는 것은 프레임워크가 아니라 파일 서버를 재는 것에 가깝다.
`/stream` 페이지가 실제로 요청마다 렌더링하는 유일한 시나리오인데, 거기서는 두 프레임워크의 처리량이 24.99 대 24.99로 같다.

여기서 나오는 실천적 결론은 이 프로젝트를 평가하려면 벤치마크가 아니라 캐시 정책 문서를 읽어야 한다는 것이다.
그 문서가 아직 없으므로 현재로서 확실히 말할 수 있는 것은 Rust HTTP 계층과 `deno_core` 통합이 잘 만들어졌다는 것까지이며, 그것은 [ssr_rs](../rust/ssr-rs.md)가 이미 보인 것과 같은 종류의 성취다.
차이는 rari가 그 위에 앱 라우터와 캐시 계층까지 수직으로 쌓았다는 점이고, 그 두 층이 이 프로젝트의 실제 값어치인데 표제는 그것을 말하지 않는다.
