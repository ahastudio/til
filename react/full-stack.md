# React는 풀스택 프레임워크가 되어 가고 있다

원문: [React is (becoming) a Full-Stack Framework - Robin Wieruch](https://www.robinwieruch.de/react-full-stack-framework/)

## 요약

Robin Wieruch가 2024년 8월 20일에 쓴 글로, 서버 컴포넌트와 서버 액션의 추가로 React가 풀스택 프레임워크로 진화하고 있다고 주장한다.
가장 인기 있는 프런트엔드 프레임워크였던 것이 이제 프런트엔드와 백엔드 사이의 간극을 성공적으로 이어 그 골짜기 양쪽을 다스리게 되었다는 것이다.
저자는 어떤 삽화 하나가 머릿속을 떠나지 않아 이 글을 쓴다고 밝히며 시작한다.

역사 서술이 논증의 앞자리를 차지한다.
2010년 Backbone과 Knockout과 Ember로 프레임워크 전쟁이 시작되고 곧 Angular와 React가 뒤따랐을 때 아무도 결과를 예측할 수 없었으며, 오랫동안 클라이언트 사이드 렌더링 JavaScript 애플리케이션이 판을 지배했다고 적는다.
단일 페이지 애플리케이션으로도 불린 이 애플리케이션들은 코드 분할이 등장하기 전까지 대개 작은 HTML 파일 하나에 큰 JavaScript 파일 하나가 연결된 형태였다.
이 시기 프런트엔드는 여러 JavaScript 프레임워크와 라이브러리가 지배했지만 백엔드는 REST가 API 통신의 표준이 되면서 특정 언어에 묶이지 않았다는 것이다.
저자는 프리랜서 웹 개발자로 일하며 주로 .NET과 Java와 Python과 PHP 백엔드를 다뤘고, 백엔드에서 TypeScript/JavaScript를 본 것은 신규 프로젝트이거나 자신이 백엔드를 통제할 수 있는 작은 프로젝트일 때뿐이었지만 풀스택 React의 부상과 함께 이것이 달라질 수 있다고 적는다.

세대에 따른 인식 차이를 하나의 축으로 세운다.
2010년 이전에 시작한 개발자는 서버 사이드 렌더링 환경에 있었으므로 최근의 서버 사이드 기법으로의 회귀를 대체로 더 편안하게 받아들이는 반면, 다른 많은 이들은 거의 10년을 클라이언트 사이드 렌더링 애플리케이션에서 REST API만 다루며 보냈기에 새로운 풀스택 React 세계를 어떻게 받아들여야 할지 모른다는 것이다.
글 중간에는 “SPA를 잊은 사람 있나요?”라는 문구가 붙은 아스키 아트가 삽입되어 있다.

TypeScript가 전환의 실질적 동력으로 제시된다.
TypeScript가 업계 표준으로 떠오르며 프런트엔드 개발자에게 타입이 있고 더 견고한 언어를 주었고 일단 받아들인 뒤에는 되돌아갈 수 없었다는 서술이다.
그러나 TypeScript가 REST에 미친 영향에는 임시방편이 많이 끼어들었으며, OpenAPI(이전의 Swagger)가 그 전부터 REST API를 문서화하게 해 주었지만 이제 그 주된 목적이 타입이 붙은 API 인터페이스를 생성하는 것이 되었다고 적는다.
클라이언트-서버 구조에서 완벽하게 타입이 붙은 인터페이스를 만드는 것이 가능함에도 저자의 오랜 프리랜서 경험에서 많은 프로젝트가 처음부터 그것을 제대로 구현하지 못했다는 것이다.
타입이 없는 SPA와 REST가 괜찮아 보이던 시절과 달리 TypeScript가 표준이 되자 프런트엔드 코드베이스에서 높은 기준에 익숙해진 탓에 생성된 타입 인터페이스가 다루기 불쾌해졌다고 설명하고, 그 단점으로 언제나 생성 단계가 끼어든다는 것, 생성된 출력이 지저분하다는 것, 초기 설정에 따라 생성된 코드가 늘 정확하지는 않다는 것 세 가지를 든다.
OpenAPI 기반 아키텍처에서 긍정적인 경험을 한 개발자도 있을 수 있지만 자신은 불행히도 그렇지 않다는 개인적 단서도 붙인다.

그 다음 자리를 tRPC가 차지한다.
원격 프로시저 호출은 새로운 것이 아니었지만 tRPC 덕분에 React 생태계에서 인기를 얻었으며, 2023년에 반년 동안 8만 줄짜리 애플리케이션을 혼자 만들며 백엔드의 함수를 호출해 데이터를 읽고 쓰는 것이 계시와 같았고 스택 양쪽이 TypeScript인 환경에서 그만큼 생산적이라고 느낀 적이 없었다고 적는다.
몇 해 전 생성된 타입이 붙은 GraphQL 아키텍처에서만 비슷한 생산성을 느꼈다고 덧붙인다.
그러나 2023년 한 해 동안 tRPC보다 나은 것을 상상할 수 없었지만 그것이 필요한 전부였느냐는 물음에 아니라고 답하며, 진짜 돌파구는 2024년의 서버 컴포넌트와 서버 액션이었고 그것들은 서버를 호출하는 데 그치지 않고 반대편에서 코드를 구현하고 실행할 수 있게 함으로써 간극을 이었다고 말한다.

기술적 설명은 짧다.
서버 컴포넌트는 React 컴포넌트를 서버에서 실행해 데이터베이스 같은 데이터 소스에 직접 접근한 뒤 JSX로 UI를 반환하게 하며, 예시로 `getMessages()`를 `await`한 뒤 `<ul>`을 반환하는 `MessageList`가 제시된다.
서버 액션은 내부적으로 HTTP API 엔드포인트를 만들어 함수를 실행하는 것만으로 원격 프로시저 호출처럼 불러 쓸 수 있게 한다.
React 자체는 서버 컴포넌트와 서버 액션의 원시 요소와 명세만 제공하며, 그 위에 세워진 메타 프레임워크가 `'use client'`와 `'use server'` 지시어를 해석하는 번들러로 클라이언트와 서버 사이의 간극을 잇는다고 밝힌다.
Next.js가 선도적인 메타 프레임워크로 그 구현을 이끌었고 이전에도 SSR을 지원했지만 이제 개발자가 데이터베이스와 메시지 큐 같은 서버 자원에 접근할 수 있게 되었다는 것이다.

마무리는 예고와 권유다.
이것이 React 풀스택 개발의 시작일 뿐이며 개발자들이 서버 컴포넌트와 서버 액션으로 데이터베이스에 직접 접근하기 시작하면 단순한 CRUD를 넘어선 복잡성을 다스리기 위한 학습 곡선이 기다린다고 적는다.
충분한 교육이 있으면 프런트엔드 개발자들이 계층과 디자인 패턴과 모범 사례를 갖춘 백엔드 아키텍처를 곧 능숙하게 구현하게 될 것이라며, 솔직히 말해 아무도 React 컴포넌트 안에서 ORM 함수 호출을 보고 싶어 하지 않기 때문이라고 덧붙인다.
그리고 바로 그 지점에서 자신의 강의 The Road to Next가 도울 수 있기를 바란다고 밝히며, 이 패러다임 전환에 들떠 있고 React 개발자가 UI에서 데이터베이스까지 수직으로 기능을 구현하는 새 시대를 맞을 준비가 되었다고 끝맺는다.

## 분석

### 이 글의 논증은 기술사가 아니라 개인사다

글의 형식은 업계 역사 서술이지만 근거의 대부분은 저자 본인의 경험이다.
프리랜서로 .NET과 Java와 Python과 PHP 백엔드를 다뤘다는 것, 많은 프로젝트가 타입 인터페이스 생성을 제대로 구현하지 못하는 것을 봤다는 것, 2023년에 8만 줄짜리 애플리케이션을 혼자 만들며 tRPC로 가장 생산적이었다는 것, 몇 해 전 GraphQL에서 비슷했다는 것이 논증의 기둥들이다.
OpenAPI에 대해서는 아예 “긍정적 경험을 한 개발자도 있겠지만 나는 아니다”라는 단서를 명시적으로 단다.

이 정직함이 글을 읽기 좋게 만들면서 동시에 논증의 사정거리를 좁힌다.
8만 줄을 혼자 반년간 만드는 상황은 스택 양쪽이 한 사람의 머릿속에 있는 상황이고, 그런 조건에서 클라이언트-서버 경계는 순수한 비용이다.
경계를 없애면 생산성이 오른다는 관찰은 그 조건에서 반박할 수 없지만, 프런트엔드 팀과 백엔드 팀이 따로 있고 백엔드가 여러 클라이언트를 상대하며 API가 계약으로 기능하는 조건에서는 같은 경계가 비용이 아니라 인터페이스다.
글은 후자의 조건을 언급하지 않는다.

세대 프레임도 같은 성격이다.
2010년 이전에 시작한 개발자가 서버 회귀를 편안해하고 그 뒤 10년을 CSR에서 보낸 개발자가 혼란스러워한다는 구도는, 새로운 방식에 대한 반대를 익숙함의 문제로 재배치한다.
그러면 기술적 반론이 세대 경험의 차이로 번역되고, 반론의 내용을 다룰 필요가 줄어든다.
이 배치가 의도적인지는 알 수 없지만 효과는 분명하다.

### TypeScript가 REST를 불편하게 만들었다는 관찰이 실제 동력이다

이 글에서 가장 값진 대목은 서버 컴포넌트 설명이 아니라 그 앞의 진단이다.
타입이 없던 시절에는 SPA와 REST의 조합이 괜찮아 보였는데, TypeScript가 표준이 되어 프런트엔드 코드베이스의 기준이 높아지자 생성된 타입 인터페이스가 견디기 어려워졌다는 서술이다.
같은 기술이 그대로인데 주변 기대치가 바뀌면서 불편해졌다는 관찰이며, 이것은 기술 변화가 아니라 기준 변화에 대한 이야기다.

이 진단이 정확하다면 뒤따르는 해법의 성격도 달라진다.
문제가 REST의 결함이 아니라 경계에서 타입이 두 번 정의된다는 것이라면, 해결책은 서버 렌더링일 필요가 없고 타입을 한 번만 정의하는 어떤 방법이든 된다.
실제로 저자가 든 세 가지 해법인 GraphQL 코드 생성, tRPC, 서버 컴포넌트는 서로 아주 다른 기술인데 같은 만족을 주었다고 서술된다.
공통점은 렌더링 위치가 아니라 타입이 경계를 건너서도 유지된다는 점이다.

그런데 글은 이 셋을 발전 단계로 배열한다.
GraphQL에서 tRPC로, 다시 서버 컴포넌트로 이어지는 서사이며 각 단계가 앞 단계를 대체한다는 인상을 준다.
같은 문제를 서로 다른 지점에서 푸는 세 가지 선택지라는 서술이 더 정확했을 것이고, 그 차이가 다음 절의 비판으로 이어진다.

### 호출과 구현의 구분이 이 글의 핵심 주장이다

tRPC에서 서버 컴포넌트로 넘어가는 문단에 이 글의 논지가 한 문장으로 들어 있다.
서버 컴포넌트와 서버 액션이 서버를 호출하는 데 그치지 않고 반대편에서 코드를 구현하고 실행할 수 있게 했다는 것이다.

이 구분이 실제로 무엇을 뜻하는지 보면 주장의 크기를 가늠할 수 있다.
tRPC에서는 서버에 프로시저를 정의해 두고 클라이언트가 그것을 함수처럼 부른다.
경계는 여전히 있고 다만 타입이 그 경계를 넘어 흐른다.
서버 컴포넌트에서는 컴포넌트 자체가 서버에서 실행되므로 데이터 조회와 UI 생성이 같은 함수 안에서 일어나고, 개발자는 그 함수가 어디서 도는지를 파일 위치와 지시어로 정한다.

이 차이가 크다는 저자의 주장은 옳다.
동시에 이 차이가 만드는 새 부담도 같은 크기다.
경계가 사라진 것이 아니라 코드의 어휘 안으로 들어왔기 때문에, 어떤 코드가 어디서 도는지가 이제 파일과 지시어와 임포트 그래프의 함수가 된다.
글이 마지막 문단에서 “단순한 CRUD를 넘어선 복잡성을 다스리기 위한 학습 곡선”을 예고하는 것이 그 부담을 가리키는데, 그것을 학습의 문제로만 규정한다.

### 마지막 문단이 이 글의 장르를 바꾼다

글은 예고와 낙관으로 끝나지만 그 사이에 한 문장이 끼어 있다.
충분한 교육이 있으면 프런트엔드 개발자들이 계층과 디자인 패턴을 갖춘 백엔드 아키텍처를 곧 능숙하게 구현할 것이며 “바로 그 지점에서 The Road to Next가 도울 수 있기를 바란다”는 문장이다.
페이지 상단에도 같은 강의의 배너가 있고 하단에도 강의 소개 카드가 있다.

이 배치를 숨기지 않았다는 점은 인정할 만하다.
저자는 오랫동안 The Road to learn React와 The Road to GraphQL 같은 학습 자료로 알려져 왔고, 새 패러다임을 설명하고 그것을 가르치는 것이 그의 일이다.
글의 마지막 문장이 강의를 가리킨다는 사실이 앞의 분석을 무효화하지도 않는다.

다만 그 사실이 글을 읽는 방식을 정한다.
이것은 기술 평가가 아니라 전환에 대한 안내이며, 안내자는 전환이 실제로 일어나고 있고 그것이 배울 만큼 어렵다는 두 가지를 동시에 전제한다.
전환이 일어나지 않는다면 안내가 필요 없고, 전환이 쉽다면 강의가 필요 없다.
이 구조가 글의 결론을 결정하지는 않지만 논조의 방향을 설명한다.

## 비평

### 두 해가 지난 지금 tRPC는 대체되지 않았다

글의 서사는 tRPC를 서버 컴포넌트 이전 단계로 배치한다.
2023년 한 해 동안 tRPC보다 나은 것을 상상할 수 없었지만 그것이 전부는 아니었고 진짜 돌파구는 2024년의 서버 컴포넌트였다는 문장이 그 배열을 만든다.
읽는 사람은 tRPC가 징검다리였고 이제 건너왔다는 인상을 받는다.

측정 가능한 사실은 다르다.
이 문서를 쓰는 2026년 8월 기준 `@trpc/server`의 지난 한 달 npm 다운로드는 1,875만 회다.
같은 기간 `next`는 2억 1,240만 회이므로 tRPC가 Next.js보다 작은 것은 맞지만, 대체되었다고 부를 수 있는 규모는 아니다.
서버 컴포넌트가 안정판으로 들어간 React 19.0.0이 2024년 12월 5일에 나왔고 그 뒤 19.2.8까지 스무 달 넘게 이어졌는데도 그렇다.

이 어긋남에는 이유가 있다.
tRPC와 서버 컴포넌트는 같은 문제를 푸는 두 방법이 아니라 서로 다른 문제를 푼다.
서버 컴포넌트는 서버에서 렌더링해 HTML을 내려보내는 경로를 다루고, tRPC는 이미 렌더링된 클라이언트가 서버와 계속 대화하는 경로를 다룬다.
모바일 앱과 웹이 같은 백엔드를 쓰거나, 클라이언트에서 낙관적 갱신과 캐시 무효화를 정교하게 다루거나, React가 아닌 소비자가 있는 경우에 서버 컴포넌트는 답이 아니다.
글이 두 기술을 시간축에 놓은 것이 이 차이를 지웠고, 그 결과 독자에게 잘못된 선택 문제를 제시한다.

### 글이 스스로 던진 문장이 자기 낙관을 무너뜨린다

마지막 문단의 한 구절이 이 글에서 가장 날카롭다.
아무도 React 컴포넌트 안에서 ORM 함수 호출을 보고 싶어 하지 않기 때문에 프런트엔드 개발자들이 계층과 디자인 패턴과 모범 사례를 배우게 될 것이라는 문장이다.

이 문장은 두 가지를 동시에 인정한다.
첫째, 서버 컴포넌트가 자연스럽게 유도하는 코드 형태가 컴포넌트 안의 직접적인 데이터 접근이라는 것이다.
글이 든 예시 코드 자체가 그렇다.
`MessageList`가 `getMessages()`를 `await`하고 곧바로 `<ul>`을 반환하며, 그것이 이 기능의 매력으로 제시된다.
둘째, 그 형태가 규모가 커지면 문제가 된다는 것이다.

문제는 해결책이 “충분한 교육”이라는 점이다.
기술이 나쁜 구조를 쉽게 만들고 좋은 구조를 어렵게 만든다면, 그 격차를 메우는 것은 교육이 아니라 도구여야 한다.
REST와 SPA 시절에는 이 규율이 물리적으로 강제되었다.
브라우저에서 데이터베이스에 연결할 방법이 없었으므로 계층이 자동으로 생겼고, 백엔드 개발자가 그 계층 안에서 설계했다.
서버 컴포넌트는 그 물리적 강제를 없애고 규율을 개인의 학습에 맡긴다.

같은 전환이 과거에 어떻게 끝났는지에 대한 기록도 있다.
PHP와 초기 Rails에서 뷰 안에 질의를 쓰는 것이 가능했고 실제로 널리 그렇게 되었으며, 그것을 정리하는 데 프레임워크 규약과 린터와 수년의 관행이 필요했다.
글이 세운 세대 서사대로라면 2010년 이전 개발자들이 서버 회귀를 편안해하는 이유가 그 시절을 겪었기 때문인데, 그들이 겪은 것에는 그 실패도 포함된다.
글은 편안함만 세고 실패는 세지 않는다.

### 프런트엔드 개발자의 관점만 있고 운영의 관점이 없다

HN 스레드는 작았지만 그중 한 반론이 이 글의 가장 큰 공백을 짚었다.
`re-thc`는 저자가 “프런트엔드 개발자가 풀스택 역할로 옮겨 가는 것에 들뜬 개발자와 유보적인 개발자 사이에 분열이 있다”고 정리한 것에 대해, 그것이 개발자 대 개발자의 문제로만 서술된다는 점을 문제 삼았다.
다른 역할과 다른 관심사는 어디 있느냐는 것이다.
CDN은 성능과 비용에 잘 최적화되어 있는데 이제 엣지 함수를 돌려야 하니 CDN 회사들이 돈을 더 벌게 되었고, 람다와 클라우드 함수 같은 해법 대부분이 복잡성과 콜드 스타트와 소동을 더해 상황을 오히려 나쁘게 만들었으며 결국 한 가지를 다른 것과 맞바꾼 것뿐이라고 적었다.[^rethc]

`acdha`가 반박한 지점도 함께 볼 만하다.
React가 개발자만을 위한 것이 아니기를 바란다는 표현에 대해 그것은 전적으로 개발자를 위한 것이며, 원래의 판매 논리가 시스템 자원 요구가 커지고 견고성이 낮아지는 대신 새 기능을 더 빨리 내놓는 것으로 상쇄된다는 것이었다고 답했다.[^acdha]

두 발언을 합치면 이 글이 재고 있는 것과 재지 않는 것이 분명해진다.
글이 재는 것은 개발자 한 명의 생산성이고, 그 지표에서 서버 컴포넌트는 확실히 이긴다.
재지 않는 것은 운영 비용과 배포 형태와 장애 양상이다.
정적 자산을 CDN에 올리고 API 서버 하나를 운영하던 구성이 서버 렌더링과 서버 액션을 쓰는 구성으로 바뀌면 요청마다 계산이 일어나는 자리가 생기고, 그것을 어디서 돌릴지가 새 결정 항목이 된다.
저자가 2023년 8만 줄 애플리케이션의 경험을 근거로 들 때 그것이 혼자 만들고 혼자 배포한 애플리케이션이었다는 사실이 이 공백과 이어진다.

### 세대 서사가 반대 방향의 증거를 미리 배제한다

2010년 이전 개발자가 서버 회귀를 편안해하고 CSR만 겪은 개발자는 어리둥절해한다는 구도는 설명력이 있어 보이지만, 검증 가능한 형태가 아니다.
어떤 개발자가 서버 컴포넌트에 반대하면 그것이 기술적 판단인지 익숙함의 문제인지 이 틀 안에서는 구분되지 않는다.
그리고 그 틀은 한 방향으로만 작동한다.
찬성은 경험의 산물로, 반대는 적응의 부족으로 읽힌다.

더 중요한 것은 회귀라는 단어가 정확하지 않다는 점이다.
서버 컴포넌트는 2008년의 서버 렌더링으로 돌아가는 것이 아니다.
서버에서 컴포넌트를 실행해 직렬화된 결과를 클라이언트로 보내고, 클라이언트 컴포넌트와 서버 컴포넌트가 하나의 트리 안에서 섞이며, 번들러가 지시어를 읽어 두 그래프를 나눈다.
이것은 이전의 어느 쪽과도 다른 세 번째 것이고, 그래서 두 세대 모두에게 새롭다.

이 점이 실무적으로 중요한 이유는 새 실패 양상이 두 세대의 경험 어느 쪽에도 없기 때문이다.
서버 컴포넌트에서 클라이언트 컴포넌트로 넘어가는 경계에서 직렬화할 수 없는 값을 넘기는 실수, 서버 전용 모듈이 클라이언트 번들로 새는 사고, 지시어의 전파 규칙에 대한 오해는 SSR 시절에도 SPA 시절에도 없던 것들이다.
글은 학습 곡선을 예고하면서 그 곡선이 무엇으로 이루어져 있는지는 말하지 않고, 세대 서사가 그 공백을 “익숙해지면 된다”로 덮는다.

## 인사이트

### 같은 시기에 여러 언어가 같은 지점으로 왔고, 그것이 이 현상의 실체다

이 글은 React의 이야기로 쓰였지만 2024년부터 2026년 사이에 일어난 일을 놓고 보면 React는 그중 하나였다.
같은 기간에 Rust 진영에서 최소 네 개의 프로젝트가 정확히 같은 문제를 겨냥해 나왔다.
Tokio 조직의 [Topcoat](../rust/topcoat.md)은 타입 검사된 Rust 표현식을 JavaScript로 교차 컴파일해 서버와 브라우저에서 같은 코드를 돌리려 하고, [Tuono](../rust/tuono.md)는 Next.js API를 그대로 본떠 Rust 서버가 React를 렌더링하게 하며, [Dioxus](../rust/dioxus.md)는 하나의 Rust 코드베이스로 서버 함수와 UI를 함께 쓰게 하고, [FullSoak](../typescript/fullsoak.md)은 Deno 위에서 같은 시도를 한다.

이 프로젝트들이 서로를 참조하지 않으면서 같은 형태에 도달했다는 사실이 중요하다.
공통점은 프레임워크의 구조가 아니라 없애려는 대상이다.
넷 다 클라이언트와 서버 사이의 직렬화된 경계를 없애거나 언어 통일로 그 경계의 비용을 낮추려 하며, 넷 다 그 이득을 성능이 아니라 인지 부담과 배포 단순성으로 설명한다.
Wieruch가 tRPC와 서버 컴포넌트에서 느꼈다는 것과 같은 만족이다.

그렇다면 이 글이 관찰한 것은 React의 진화가 아니라 경계 자체가 문제로 인식되기 시작했다는 사실이다.
그 인식이 각 생태계에서 자기 언어로 표현되었고, JavaScript 진영에서는 이미 양쪽에 같은 언어가 있었으므로 렌더링 위치를 옮기는 형태로, Rust 진영에서는 언어를 통일하는 형태로 나타났다.
글이 “React가 골짜기 양쪽을 다스리게 되었다”고 쓴 자리에 더 정확한 서술은 “여러 진영이 동시에 골짜기를 메우려 하고 있다”이다.

이 재구성이 실천적인 이유는 선택의 폭을 바꾸기 때문이다.
경계를 없애고 싶다는 요구가 React 고유의 것이 아니라면, 그 요구를 만족시키는 방법도 React 고유의 것이 아니다.
이미 Rust 백엔드를 운영하는 조직에게는 프런트엔드를 Rust로 가져오는 쪽이 더 자연스러울 수 있고, 그 선택지가 2024년에는 없었지만 지금은 있다.

### 경계를 없애는 것과 경계를 어휘 안으로 옮기는 것은 다르다

이 글의 표현은 간극을 이었다는 것이고, 그 표현이 서버 컴포넌트가 실제로 하는 일을 오도한다.
네트워크 경계는 그대로 있다.
서버 컴포넌트의 결과는 여전히 직렬화되어 전선을 건너고, 서버 액션은 글 자신이 밝히듯 내부적으로 HTTP API 엔드포인트를 만든다.

달라진 것은 그 경계가 어디에 표시되느냐다.
REST에서는 경계가 URL과 스키마에 있었고, tRPC에서는 프로시저 정의에 있었고, 서버 컴포넌트에서는 `'use client'`와 `'use server'`라는 지시어와 파일 배치에 있다.
곧 경계가 인프라의 사실에서 코드의 어휘로 이동했다.

이 이동에는 명확한 이득이 있다.
경계가 코드 안에 있으면 컴파일러와 번들러가 그것을 검사할 수 있고, 타입이 자동으로 따라간다.
동시에 명확한 손실도 있다.
경계가 인프라에 있을 때는 그것이 눈에 보이고 측정 가능했다.
어떤 요청이 몇 번 나가는지가 네트워크 탭에 있었고, 캐시를 어디에 둘지가 명시적 결정이었다.
경계가 어휘로 들어오면 컴포넌트 트리의 모양이 곧 네트워크 동작이 되고, UI 구조를 바꾸는 일이 의도치 않게 데이터 접근 패턴을 바꾼다.

이 절충을 알아보는 방법이 하나 있다.
경계가 어디 있는지를 시스템의 어느 계층에서 답할 수 있는지 물어보는 것이다.
REST에서는 인프라 담당자가 답할 수 있고, tRPC에서는 타입 정의를 읽으면 되고, 서버 컴포넌트에서는 임포트 그래프를 따라가야 한다.
`re-thc`가 CDN과 엣지 함수를 두고 한 지적[^rethc]이 이 이동의 운영 측면이며, 어휘 안으로 들어간 경계는 개발자에게 편해지는 만큼 운영자에게 불투명해진다.

### 이 글에서 풀스택의 의미가 조용히 바뀐다

글의 제목과 결론은 React 개발자가 UI에서 데이터베이스까지 수직으로 기능을 구현하는 시대를 말한다.
그런데 그 직전 문장이 요구하는 능력은 다르다.
계층과 디자인 패턴과 모범 사례를 갖춘 백엔드 아키텍처를 구현하는 능력이다.

이 둘은 같은 말이 아니다.
UI에서 데이터베이스까지 코드를 쓰는 것은 접근 권한의 문제이고, 계층과 패턴을 갖추는 것은 설계 규율의 문제다.
서버 컴포넌트가 준 것은 전자이며, 후자는 주어지지 않았고 오히려 이전보다 지키기 어려워졌다.
데이터베이스에 접근할 수 없던 시절에는 계층이 저절로 생겼기 때문이다.

그래서 이 글이 예고하는 학습 곡선의 실체는 “백엔드 배우기”가 아니다.
프런트엔드 파일 안에서 백엔드 아키텍처의 규율을 스스로 세우는 일이며, 그것은 백엔드 개발자가 하는 일보다 어렵다.
백엔드 개발자는 프레임워크와 디렉터리 구조와 팀 관행이 규율을 대신 강제해 주는 환경에서 일한다.
서버 컴포넌트를 쓰는 프런트엔드 개발자에게는 그 강제가 없고, `MessageList` 안에서 `getMessages()`를 부르는 것이 문서의 첫 예시로 제시된다.

여기서 나오는 실천적 결론은 이 전환을 채택할 때 필요한 것이 강의가 아니라 규약이라는 것이다.
데이터 접근 코드가 놓일 디렉터리를 정하고, 컴포넌트에서 ORM을 직접 임포트하는 것을 린터로 막고, 서버 전용 모듈에 표시를 두는 것 같은 조치가 개인의 학습보다 먼저 와야 한다.
글이 예상한 대로 “아무도 컴포넌트 안의 ORM 호출을 보고 싶어 하지 않는다”면, 보고 싶지 않은 것을 보지 않게 만드는 가장 싼 방법은 도구다.

### 전환을 설명하는 사람과 전환을 가르치는 사람이 같을 때 생기는 것

이 글은 강의 광고로 끝나고 저자는 그것을 숨기지 않는다.

그럼에도 이 구조가 만드는 편향은 기록해 둘 만하다.
새 패러다임을 가르치는 사람에게는 그 패러다임이 실재해야 하고 동시에 충분히 어려워야 한다.
너무 쉬우면 배울 것이 없고 실재하지 않으면 배울 이유가 없다.
그래서 이런 글은 구조적으로 “큰 변화가 오고 있으며 준비가 필요하다”는 형태를 띠게 되고, 그 형태 자체가 결론의 일부를 미리 정한다.

같은 편향이 반대편에도 있다는 점을 함께 말해야 공정하다.
기존 방식으로 일하는 사람에게는 변화가 과장이어야 하고, 경쟁 기술을 만드는 사람에게는 이 기술이 실패해야 한다.
어느 글에도 이해관계가 없는 자리는 없으며, 독자가 할 수 있는 일은 그 이해관계를 지운 뒤 남는 검증 가능한 진술을 세는 것이다.

이 글에서 그렇게 남는 것은 짧다.
서버 컴포넌트가 서버에서 실행되어 데이터 소스에 접근할 수 있다는 것, 서버 액션이 내부적으로 HTTP 엔드포인트를 만든다는 것, React가 원시 요소만 제공하고 메타 프레임워크가 지시어를 해석한다는 것이다.
나머지, 곧 이것이 패러다임 전환인지와 프런트엔드 개발자들이 곧 백엔드 아키텍처를 능숙하게 다루게 될지는 예측이다.
두 해가 지난 지금 첫 예측은 절반쯤 맞았고 — React 19가 나왔고 서버 컴포넌트가 널리 쓰인다 — 두 번째 예측은 여전히 검증되지 않았으며, tRPC의 월 1,875만 다운로드가 그 사이에 놓여 있다.
