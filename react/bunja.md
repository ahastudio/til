# Bunja: 프론트엔드 상태 관리의 네 가지 난제를 계층 분리로 풀다

원문: [프론트엔드 상태 관리의 네 가지 난제, Bunja로 풀어보기](https://hackers.pub/@flow/2026/bunja-solves-four-problems-with-fe-state)

GN 토론: <https://news.hada.io/topic?id=33627>

## 소개

@flow와 @xiniha가 hackers.pub에 쓴 글이다.
Bunja는 프론트엔드 상태 관리의 반복되는 네 난제를,
모든 것을 React 컴포넌트 트리로 관리하는 대신
관심사를 여러 계층으로 분리해 푼다.

Bunja는 Jotai나 Zustand 같은 전통적 상태 관리 라이브러리가 아니다.
대신 상태 인스턴스와 그 수명(lifespan)을 관리한다.
Jotai와 결합하면 `useBunja`를 제공해,
처음 쓰일 때 생성되고 마지막 소비자가 사라질 때 정리되는 인스턴스를 얻는다.

Bunja가 다루는 네 난제는 다음과 같다.
첫째, 스코프 변경이 구현 변경을 요구하는 문제다.
상태를 더 넓게 공유해야 할 때
전통적으로 `useState`에서 props나 Context로 리팩터링해야 하지만,
Bunja에서는 로컬이든 공유든 같은 코드로,
여러 컴포넌트가 같은 Bunja 인스턴스를 참조하기만 하면 된다.

둘째, 상태 수명 불일치다.
전역 스토어는 무한히 유지되지만 기능 상태는 실제 사용에 맞아야 하는데,
Bunja 인스턴스는 필요할 때 자동 초기화되고
모든 사용자가 언마운트되면 정리되어 수동 초기화·정리 코드를 없앤다.
`bunja.effect`가 WebSocket 연결 같은 자원 관리를 다룬다.
셋째, 파생 상태 중복이다.
커스텀 훅의 계산 값이 컴포넌트마다 재계산되는 문제를,
Bunja 안에서 파생 값이 인스턴스 내 단일 공유 상태 노드가 되어 막는다.
넷째, 흩어진 기능 로직이다.
구매 옵션이 가격 계산과 주문 요청 양쪽에 영향을 주는 것처럼
관련 상태 제약이 컴포넌트에 파편화되는데,
Bunja 인스턴스가 기능 전체를 캡슐화하고
내부 의존성을 `bunja.use`로 외부에 감춘다.

## 명세

Bunja의 핵심 아키텍처는 세 계층의 분리다.
React 렌더 트리는 현재 UI를 표현하고,
Bunja 인스턴스 그래프는 활성 기능 인스턴스와 그 의존성을 표현하며,
상태 관리 도구 그래프는 값의 변경과 파생을 표현한다.
스코프는 Context 주입으로 조건부 인스턴스 유일성을 가능하게 하고,
`bunja.use`를 통한 의존성 선언은
내부 요구를 노출하지 않으면서 기능을 조합한다.

## 분석

### 이 라이브러리의 핵심은 상태의 수명을 UI 트리에서 분리한 것이다

Bunja의 근본 통찰은 상태의 수명이
React 컴포넌트 트리의 구조와 일치할 필요가 없다는 것이다.
전통적으로 React에서 상태의 범위와 수명은 컴포넌트 트리에 묶인다.
로컬 상태는 컴포넌트와 함께 살고 죽으며,
공유 상태는 Context나 전역 스토어로 올려야 한다.
Bunja는 이 결합을 끊어, 상태 인스턴스에 독립적 수명을 준다.

이 분리가 중요한 이유는 상태 관리의 흔한 두 극단을 모두 피하기 때문이다.
로컬 `useState`는 공유가 어렵고,
전역 스토어는 무한히 살아 메모리와 정합성 문제를 낳는다.
Bunja 인스턴스는 처음 쓰일 때 나고 마지막 소비자가 떠날 때 죽어,
정확히 필요한 만큼만 산다.
이것은 kafka-streams-core-concepts와 living-computers에서 본,
살아 있는 상태를 필요한 동안만 유지한다는 원리의 프론트엔드 판본이다.
상태의 수명이 사용에 맞춰지면 수동 정리 코드가 사라진다.

세 계층 분리가 이 통찰을 구조화한다.
UI(렌더 트리), 기능(인스턴스 그래프), 값(상태 그래프)을 나누면,
각 계층이 자기 관심사만 다룬다.
UI가 바뀌어도 기능 인스턴스는 유지될 수 있고,
기능이 조합되어도 UI는 그것을 몰라도 된다.
이 분리가 스코프 변경이 구현 변경을 요구하지 않게 하는 근거다.

### 네 난제가 사실 하나의 근원에서 나온다

Bunja가 드는 네 난제는 별개처럼 보이지만
하나의 근원, 곧 상태를 컴포넌트 트리에 묶는 것에서 나온다.
스코프 변경, 수명 불일치, 파생 중복, 로직 파편화는 모두
상태의 논리적 구조와 UI의 물리적 구조가 강제로 일치될 때 생긴다.
Bunja는 이 일치를 끊어 네 문제를 한꺼번에 겨냥한다.

이 통합적 진단이 중요한 이유는 해법의 일관성을 설명하기 때문이다.
각 문제를 따로 풀면 서로 다른 도구가 필요하다.
공유는 Context로, 수명은 정리 훅으로,
파생 중복은 메모이제이션으로, 파편화는 커스텀 훅으로.
Bunja는 이 모두를 인스턴스라는 단일 추상으로 푼다.
인스턴스가 공유의 단위이자 수명의 단위이자
파생의 단위이자 기능 캡슐화의 단위다.
하나의 추상이 네 문제를 덮는 것이 이 설계의 우아함이다.

`bunja.use`를 통한 의존성 선언이 이 캡슐화를 완성한다.
기능이 다른 기능에 의존할 때 그 내부 요구를 노출하지 않고 조합하는 것은,
palantir-fde에서 본, 현장 조직과 제품 조직의 구분을 없앤 것처럼,
기능의 경계를 명확히 하되 내부는 감춘다.
구매 옵션이라는 기능이 가격과 주문 양쪽에 걸쳐도,
그 제약이 하나의 인스턴스에 캡슐화되면
컴포넌트는 그 내부를 몰라도 된다.

## 비평

### 새로운 추상이 학습 비용과 생태계 종속을 더한다

Bunja의 인스턴스 그래프라는 추상은 강력하지만,
개발자가 익혀야 할 새 정신 모델을 요구한다.
React의 컴포넌트 트리에 익숙한 개발자에게
UI 트리, 인스턴스 그래프, 상태 그래프의 삼중 구조는
추가 학습 부담이다.
문제를 푸는 대신 새로운 개념 계층을 얹는 것이다.

이 부담이 중요한 이유는 채택의 실질 장벽이기 때문이다.
Bunja가 해결하는 네 난제는 실재하지만,
많은 프로젝트가 그 난제를 기존 도구의 관용구로 견딘다.
새 추상을 도입하는 비용이 그 난제의 고통보다 크면,
개발자는 익숙한 불편을 택한다.
switchyard나 behavior-specs에서 본, 표준·도구의 채택이
임계점을 넘어야 가치를 낸다는 문제가 여기도 적용된다.
Jotai와 결합해야 온전히 동작한다는 점은 생태계 종속도 더한다.

또한 세 계층 분리가 디버깅을 복잡하게 할 수 있다.
상태가 컴포넌트 트리에 묶여 있으면
React DevTools로 그 흐름을 따라가기 쉽지만,
인스턴스 그래프라는 별도 계층이 생기면
상태가 어디서 나고 죽는지가 UI에서 보이지 않는다.
long-running-agents에서 본, 상태를 외부화하면
그것을 추적할 별도 관측 수단이 필요하다는 교훈이
프론트엔드 상태에도 적용된다.

### 자동 수명 관리의 마법이 예측 불가능성을 부를 수 있다

Bunja의 매력인 자동 초기화·정리는 편의를 주지만,
그 자동성이 예측 불가능성을 낳을 수 있다.
인스턴스가 처음 쓰일 때 나고 마지막 소비자가 떠날 때 죽는다면,
그 생성과 소멸의 시점이 컴포넌트의 마운트·언마운트에 암묵적으로 묶인다.
개발자가 명시적으로 통제하지 않는 이 수명이
의도치 않은 재생성이나 조기 정리를 부를 수 있다.

이 위험이 중요한 이유는 자원 관리의 미묘함 때문이다.
`bunja.effect`가 WebSocket 연결 같은 자원을 다룬다면,
그 연결이 언제 열리고 닫히는지가 인스턴스 수명에 종속된다.
컴포넌트가 잠깐 언마운트되었다 다시 마운트되면
연결이 끊겼다 다시 열릴 수 있고,
그 재연결 비용이 사용자에게 지연으로 나타날 수 있다.
자동 수명 관리는 수동 정리 코드를 없애는 대신,
수명 경계에서의 미묘한 동작을 개발자의 통제 밖으로 옮긴다.

kafka exactly-once에서 본, 강한 보장이 그 경계를 이해하는 사용자에게만
안전하다는 교훈이 여기서도 성립한다.
자동 수명 관리를 마법처럼 켜면 편하지만,
그 인스턴스가 정확히 언제 나고 죽는지를 모르면
자원 누수나 조기 정리 같은 버그를 만난다.
편의의 대가는 그 자동성의 경계를 이해할 책임이며,
글은 이 경계의 함정을 충분히 경고하지 않는다.

## 인사이트

### 상태의 논리적 구조와 UI의 물리적 구조를 분리하는 것이 성숙의 방향이다

Bunja가 드러내는 가장 이전 가능한 통찰은
프론트엔드 상태 관리의 성숙이
상태의 논리적 구조를 UI의 물리적 구조에서 분리하는 방향으로 간다는 점이다.
초기 React는 상태를 컴포넌트에 묶어 단순함을 얻었지만,
앱이 커지면 그 묶임이 네 난제를 낳는다.
Bunja는 그 묶임을 끊어 상태에 독립적 생명을 준다.

이 통찰이 중요한 이유는 상태 관리 도구 진화의 궤적을 설명하기 때문이다.
Redux는 전역화로, Context는 트리 주입으로,
Jotai와 Recoil은 원자화로 이 문제에 접근했다.
Bunja는 인스턴스와 수명이라는 새 축을 더한다.
각 도구는 상태를 UI에서 얼마나, 어떻게 떼어 낼지의 서로 다른 답이다.
이 진화의 공통 방향은 상태가 UI의 종속물이 아니라
독립적 관리 대상이 되는 것이다.

두 번째 차수의 효과는 이것이 백엔드의 교훈을 프론트엔드로 가져온다는 점이다.
kafka의 상태 저장소, long-running-agents의 세션 로그가
상태를 프로세스에서 분리했듯,
Bunja는 상태를 컴포넌트에서 분리한다.
서버 상태 관리가 오래전 배운 것,
곧 상태의 수명이 그것을 담는 그릇의 수명과 달라야 한다는 것을
프론트엔드가 뒤늦게 재발견하는 것이다.
계층의 분리는 규모가 커진 시스템의 공통 성숙 패턴이다.

### 추상의 우아함과 채택의 현실 사이에는 늘 간극이 있다

Bunja가 네 난제를 하나의 인스턴스 추상으로 우아하게 푸는 것은
기술적으로 인상적이지만,
그 우아함이 곧 채택을 보장하지는 않는다.
GN 토픽에 댓글이 하나도 달리지 않은 것은,
적어도 아직 이 라이브러리가 논의의 열기를 얻지 못했음을 보여 준다.
behavior-specs가 별을 받았지만 채택은 별개였던 것과 같다.

이 간극이 새로운 프레임을 주는 이유는
좋은 해법과 확산되는 해법이 다름을 상기시키기 때문이다.
프론트엔드 상태 관리는 도구가 넘치는 레드오션이다.
Redux, Zustand, Jotai, Recoil, XState가 이미 경쟁한다.
새 도구가 더 우아해도,
기존 도구에 쌓인 생태계, 문서, 개발자 경험을 넘어서기 어렵다.
influential-blog-posts에서 본, 기억하기 좋은 것이 이기듯,
상태 관리 도구도 우아함만이 아니라
채택의 관성과 생태계의 두께로 승부가 갈린다.

세 번째 차수의 함의는 니치 혁신의 운명이 확산 전략에 달렸다는 것이다.
Bunja의 인스턴스·수명 관리는 진짜 문제를 풀지만,
그것이 널리 쓰이려면 기술적 우수성을 넘어
채택 마찰을 낮추는 노력이 필요하다.
Jotai 위에서 점진적으로 도입할 수 있다는 점,
기존 코드를 크게 바꾸지 않아도 된다는 점은 그 마찰을 낮추는 설계다.
gitbybit이나 dreeve처럼,
개인이나 소수가 만든 좋은 도구가 살아남으려면
그 우아함을 채택 가능한 형태로 포장하는 일이
기술만큼이나 중요하다.
