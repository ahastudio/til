# Helix: 선택이 먼저인 포스트모던 모달 에디터

<https://helix-editor.com/>

<https://github.com/helix-editor/helix>

25.07 릴리스 HN 토론: <https://news.ycombinator.com/item?id=44574815> (331점, 153개 댓글)

## 소개

Helix는 Rust로 작성된 “포스트모던 모달 텍스트 에디터”다.
Kakoune과 Neovim에서 영감을 받았고,
README는 편집 모델이 “Kakoune에 매우 강하게 기반한다”고 명시한다.
GitHub 스타 45.7k에 MPL-2.0 라이선스다.

주로 터미널에서 동작하며,
개발진은 “wgpu를 이용한 커스텀 렌더러(Emacs와 유사한) 탐색”에 관심을 표한 바 있다.

## 주요 기능

- Vim과 유사한 모달 편집
- 다중 선택(multiple selections)
- 내장 언어 서버 지원
- “tree-sitter를 통한 똑똑하고 점진적인 문법 강조와 코드 편집”

들여쓰기 정의는 일부 언어에만 있으며,
`runtime/queries/<lang>/`의 `indents.scm` 파일에서 확인할 수 있다.

설치 문서는 docs.helix-editor.com/install.html에 있고,
문제 해결 위키 페이지와 Matrix Space 커뮤니티를 운영한다.
로고 디자인은 @jakenvac이 맡았다.

## 25.07 릴리스 주요 변경

2025년 7월 15일에 나온 25.07 릴리스에는 195명이 기여했다.

### 파일 탐색기

`<space>e`로 여는 계층형 파일 브라우저가 추가되었다.
퍼지 검색이 가능한 “피커” 인터페이스로 디렉터리 구조를 살펴볼 수 있으며,
기존의 재귀적 파일 열기 기능을 보완한다.

### LSP 문서 색상

Document Color Request 명세를 지원하는 언어 서버로부터
색상 견본을 받아 인라인으로 표시한다.
인레이 힌트와 유사하게 동작하되 대상이 RGB 값이다.

### 커맨드 모드 개선

커맨드 파싱 시스템을 전면 재작성해 여러 문제를 함께 해결했다.

- **플래그**: `:sort --reverse`(또는 `-r`),
  `:write --no-format`처럼 셸과 유사한 플래그 문법을 지원한다.
- **확장(expansion)**: `%{buffer_name}`, `%{cursor_line}` 같은
  `%{variable_name}` 형태의 변수 보간과
  `%sh{...}` 형태의 셸 명령 실행으로 동적 커맨드를 구성할 수 있다.
- **확장 가능한 파싱**: 커맨드의 부분마다 다른 파싱 전략을 적용해
  파일명 자동 완성을 개선하고 이스케이프 문자의 복잡도를 낮췄다.

### tree-house 아키텍처

코어의 Tree-sitter 연동을 “tree-house”라는 새 크레이트로 교체했다.
기존 하이라이터 구현의 오래된 한계를 겨냥한 변경이다.

- **점진적 처리**: 문서 전체가 아니라 영향받은 인젝션 레이어만 다시 파싱하고 분석한다.
- **견고한 인젝션 처리**: Rust 문서 주석 안의 마크다운, 그 안의 코드 펜스처럼
  깊게 중첩된 언어 인젝션 상황을 지원한다.
- **로컬 추적**: 파라미터와 변수 정의를 파싱 시점에 추적해
  뷰포트 위치와 무관하게 강조가 유지된다.
- **레이어 간 일관성**: 새 `TreeCursor`와 `QueryIter` API로
  언어 경계를 넘어 Tree-sitter 기능이 일관되게 동작한다.

## 분석

### 선택이 먼저라는 것은 인터페이스가 아니라 인식론의 차이다

Helix와 Vim의 차이를 “키 순서가 반대”로 요약하면 핵심을 놓친다.
Vim은 `d3w`처럼 동사를 먼저 말하고 명사를 나중에 말한다.
Helix는 `3wd`처럼 대상을 먼저 고르고 동작을 나중에 지시한다.

이 차이가 근본적인 이유는 피드백의 유무에 있다.
Vim에서 `d3w`를 입력하는 동안 사용자는 무엇이 지워질지 볼 수 없다.
머릿속에서 모델을 돌려 예측하고, 결과를 보고 나서 맞았는지 확인한다.
틀렸으면 `u`로 되돌린다.
즉 Vim의 편집은 예측과 검증의 순환이다.

Helix에서는 `3w`를 누른 순간 선택 영역이 화면에 표시된다.
무엇이 지워질지 보고 나서 `d`를 누른다.
예측이 필요 없고, 따라서 되돌릴 일도 줄어든다.

이것은 명령줄과 GUI의 오래된 대립과 같은 구조다.
Vim의 모델은 언어에 가깝다.
문법을 익히면 표현력이 무한하지만 익히기 전에는 아무것도 못 한다.
Helix의 모델은 직접 조작에 가깝다.
보면서 하므로 진입 장벽이 낮고, 대신 명령을 미리 조합하는 능력은 줄어든다.

Kakoune이 이 발상의 원조이고 Helix는 그것을 Rust로 다시 구현했다.
그런데 Kakoune은 소수 사용자에 머물렀고 Helix는 스타 45.7k에 이르렀다.
발상만으로 채택이 결정되지 않는다는 점을 보여주는 대목이다.

### 기본 내장이라는 전략이 Vim 생태계의 약점을 정확히 겨냥한다

Helix의 기능 목록에서 “내장 언어 서버 지원”과
“tree-sitter를 통한 문법 강조”는 기술 항목이 아니라 전략 선언이다.

Vim과 Neovim에서 이 두 기능은 설정의 영역이다.
LSP를 붙이려면 플러그인 매니저를 고르고,
LSP 클라이언트 플러그인을 설치하고,
자동 완성 엔진을 고르고, 스니펫 엔진을 붙이고,
언어별 서버 설정을 쓰고, 키맵을 정의해야 한다.
이 조합에서 각 부분은 독립적으로 진화하고 서로 깨진다.

Helix는 이 전부를 기본값으로 옮겼다.
설치하면 동작한다.
플러그인 시스템이 아예 없다는 사실이 이 전략의 뒷면이다.
확장할 수 없으므로 조합 문제도 없다.

이 결정은 명백한 트레이드오프다.
Vim 사용자가 수십 년에 걸쳐 쌓은 플러그인 생태계를 통째로 포기한다.
그 대가로 얻는 것은 “설정 없이 동작하는 상태”이고,
[Julia Evans의 전환 노트](helix-switching-from-vim.md)에서
설정이 4개의 키 바인딩으로 줄었다는 것이 그 결과다.

여기서 겨냥하는 사용자층이 드러난다.
에디터를 다듬는 것 자체를 즐기는 사람이 아니라
에디터가 그냥 동작하기를 바라는 사람이다.
Vim 커뮤니티에서 오래 논쟁되어온 “설정에 쓰는 시간”에 대한
가장 급진적인 답이 “설정 기능을 없앤다”인 셈이다.

### tree-house 재작성이 드러내는 문법 강조의 실제 난이도

25.07의 tree-house 크레이트 도입은 릴리스 노트에서 가장 기술적인 항목이지만
가장 많은 것을 말해주는 항목이기도 하다.

문법 강조는 겉보기에 단순한 기능이다.
키워드를 파랗게, 문자열을 초록색으로.
정규식으로도 대충 되고, 실제로 오랫동안 그렇게 해왔다.

Tree-sitter가 등장하면서 기준이 올라갔다.
실제 파서로 구문 트리를 만들면
같은 이름이라도 함수 호출인지 변수 참조인지 구분할 수 있다.
문제는 여기서부터 생기는 조합 폭발이다.

인젝션이 그 핵심이다.
Rust 코드 안의 문서 주석, 그 안의 마크다운, 그 안의 코드 펜스, 그 안의 SQL.
릴리스 노트가 든 예시가 정확히 이 중첩이다.
각 레이어는 다른 파서를 쓰고, 한 레이어의 편집이
다른 레이어의 경계를 바꿀 수 있다.

“영향받은 인젝션 레이어만 다시 파싱한다”는 개선이 필요했다는 것은
그전에는 문서 전체를 다시 파싱했다는 뜻이다.
큰 파일에서 타이핑할 때마다 전체 재파싱은 명백한 병목이다.
“뷰포트 위치와 무관하게 로컬 정의가 유지된다”는 항목도
그전에는 스크롤하면 강조가 틀어졌다는 고백이다.

즉 Helix가 초기부터 내세운 “tree-sitter 기반 똑똑한 강조”는
릴리스 25.07에 이르러서야 제대로 동작하기 시작했다.
기능을 목록에 넣는 것과 그 기능이 실제로 작동하는 것 사이의 거리를
이 재작성이 보여준다.

### 커맨드 모드 재작성은 플러그인 부재를 메우려는 시도다

25.07의 커맨드 모드 개선을 개별 기능으로 보면 사소해 보인다.
플래그 지원, 변수 보간, 셸 명령 실행.

그러나 플러그인 시스템이 없다는 사실과 함께 놓으면 성격이 달라진다.
`%sh{...}`로 셸 명령을 실행하고 그 결과를 커맨드에 넣을 수 있다는 것은
외부 프로그램과 조합하는 통로가 열렸다는 뜻이다.
`%{buffer_name}`, `%{cursor_line}` 같은 변수는
에디터 상태를 외부로 전달하는 수단이다.

이것은 Unix 철학의 방식으로 확장성을 얻는 접근이다.
에디터 안에 플러그인 런타임을 두는 대신
셸을 통해 바깥의 도구와 이어붙인다.
[Artem Golubin의 활용기](helix-editor-usage.md)에서
tmux 키 바인딩으로 Yazi, Lazygit, `clickhouse-client`를 붙이는 방식이
정확히 이 철학의 실천이다.

이 접근이 어디까지 갈 수 있는지는 미지수다.
셸 조합으로 되는 것과 에디터 내부 상태에 접근해야 되는 것은 다르다.
자동 완성 소스 추가, 커스텀 인레이 힌트, 디버거 통합 같은 것은
프로세스 경계를 넘어서는 것만으로 되지 않는다.
그럼에도 커맨드 모드 재작성은
“플러그인 없이 어디까지 가능한가”를 밀어보는 실험으로 읽힌다.

## 비평

### 플러그인 부재를 설계 철학으로 제시하지만 실제로는 미완의 상태다

Helix가 플러그인 시스템을 갖지 않은 것은
흔히 의도적 단순함으로 설명된다.
그러나 프로젝트의 이슈 트래커와 논의를 보면
플러그인 시스템은 오래전부터 계획되어 있고 계속 미뤄지고 있다.
철학이 아니라 아직 못 만든 것에 가깝다.

이 구분이 중요한 이유는 사용자의 판단이 달라지기 때문이다.
영구적으로 플러그인이 없을 것이라면
셸 조합 중심의 워크플로에 투자하는 것이 합리적이다.
언젠가 플러그인이 온다면
지금의 우회 방법들은 나중에 버려질 임시 조치다.

더 곤란한 것은 이 불확실성이 생태계 형성을 막는다는 점이다.
플러그인 API가 없으므로 아무도 플러그인을 만들지 않고,
확장 기능에 대한 수요는 각자의 설정 파일과 셸 스크립트로 흩어진다.
공유되지 않으므로 축적되지 않고,
같은 문제를 각자 다시 푼다.
Golubin의 글이 개인 설정 모음의 형태를 띠는 것이
이 상황의 자연스러운 결과다.

Vim의 힘이 에디터 자체가 아니라 30년치 플러그인에 있었다는 점을 생각하면,
Helix는 가장 큰 자산 없이 경쟁하고 있는 셈이다.
기본 기능이 좋다는 것으로 초기 사용자는 얻을 수 있지만,
장기적으로 특수한 요구를 가진 사용자를 유지할 수 있을지는 다른 문제다.

HN 릴리스 토론에서 이 미완의 상태가 구체적인 이탈 사유로 나타났다.
danslo는 몇 주간 Neovim에서 Helix로 옮겨보려다
자기에게 필수적인데 구현되지 않은 것들을 정리해 돌아갔다.
Go import 추가 같은 저장 시 코드 액션,
디스크의 파일이 변경될 때 버퍼를 자동 갱신하는 기능,
그리고 브라우저 형태의 파일 트리다.
특히 마지막 항목이 시사적이다.
그 PR은 “플러그인 시스템을 위해” 거부되었는데,
그 플러그인 시스템이 아직 실체화되지 않았다.[^danslo]
있지도 않은 확장 시스템을 이유로 기능이 거부되는 상태가
프로젝트의 현재 위치를 정확히 보여준다.
bitcrshr는 몇 년째 Helix를 주력으로 쓰면서
여전히 플러그인 시스템을 애타게 기다리고 있다고 적었다.[^bitcrshr]

torben-friis는 이 조합 자체를 문제로 지목했다.
Helix가 단순함에 대해서는 확고한 입장을 가지면서(터미널 통합 없음)
플러그인으로 확장하기도 어렵다면(LSP에서 오지 않는 한 린팅 없음),
제한적인 조합이 되어 결국 에디터 바깥에
전체 설정을 tmux 등으로 세워야 하지 않느냐는 것이다.
그는 프로젝트를 폄하하려는 것이 아니라,
이 단점들을 상쇄할 만한 큰 장점이 무엇인지 궁금하다고 물었다.[^torben-friis]

### 안정성 문제가 소개 문서에 반영되지 않는다

Helix의 저장소 소개는 기능과 설치 안내로 구성되어 있고
성숙도에 대한 언급이 없다.
버전 번호도 25.07처럼 날짜 기반이라
1.0 이전인지 이후인지 같은 신호를 주지 않는다.

그런데 실사용 보고는 다른 그림을 보여준다.
Julia Evans는 3개월 사용 중 대략 주 1회 크래시를 경험했다고 적었다.
지속 실행 취소 파일이 없고, 파일 자동 다시 읽기가 없어
`:reload-all`을 손으로 쳐야 한다는 점도 언급된다.

주 1회 크래시는 에디터로서 가벼운 결함이 아니다.
저장하지 않은 작업이 사라질 수 있고,
지속 실행 취소가 없다는 것과 겹치면 손실이 복구되지 않는다.
두 결함이 각각이 아니라 함께 작동해서 위험이 커진다.

스타 45.7k와 195명의 릴리스 기여자라는 지표는
성숙한 프로젝트의 인상을 준다.
그 인상과 실제 안정성 사이의 간극을
프로젝트가 스스로 밝히지 않는 것은 문제다.
“터미널 에디터”라는 범주에서 사용자가 기대하는 신뢰도는
텍스트 편집기 중에서도 특히 높다.
Vim과 Emacs는 수십 년간 데이터를 잃지 않는다는 평판을 쌓았고,
같은 자리를 노리는 프로젝트라면 그 기준으로 평가받게 된다.

HN에서 Xiol32는 크래시가 아닌 다른 경로로 작업을 잃은 사례를 보고했다.
Helix를 대체로 마음에 들어 했지만
실행 취소가 동작하는 방식에 무언가 대단히 잘못된 느낌이 든다는 것이다.
무엇을 되돌리려 하는지가 늘 논리적으로 보이지 않고,
언제나 너무 많이 되돌린다.
그는 과거에 이것 때문에 작업을 잃었다고 적었다.[^Xiol32]
크래시가 자주 나는 것과 실행 취소가 예측되지 않는 것이
같은 에디터에 함께 있으면 위험이 곱해진다.

eviks는 Evans의 태도 자체를 문제 삼았다.
“주 1회 정도 세그폴트로 크래시가 나는데 그렇게 신경 쓰이지는 않는다,
그냥 다시 열면 된다”는 서술을 인용하며,
지속 실행 취소가 없는 상태에서
다시 열어도 같은 편집 상태로 돌아갈 수 없는데
데이터 손실을 대하는 태도가 이상하다고 지적했다.[^eviks]

### Kakoune의 발상을 가져왔으면서 그 한계도 함께 가져왔다

Helix가 Kakoune의 편집 모델을 계승했다는 점은 명시되어 있다.
그런데 계승된 것은 장점만이 아니다.

선택 우선 모델의 구조적 약점은
“보이지 않는 것을 편집할 수 없다”는 것이다.
Vim에서 `d}`는 커서 아래 문단 전체를 지우고,
문단이 화면을 넘어가도 상관없다.
선택 우선 모델에서는 선택 영역이 시각적으로 표현되므로
화면 밖의 큰 범위를 다룰 때 확인이 어렵다.

매크로와의 관계도 마찬가지다.
Vim의 매크로는 명령 열이므로 어디서 실행해도 같은 문법이 적용된다.
선택 우선 모델에서는 다중 커서가 매크로를 상당 부분 대체하는데,
Evans도 매크로 대신 다중 커서를 선호하게 되었다고 적었다.
그러나 다중 커서는 모든 대상이 동시에 화면에 있어야 다루기 쉽고,
조건부 동작이나 반복 횟수가 가변적인 작업에는 약하다.

Golubin이 Vim의 모션을 다시 이식했다는 점도 시사적이다.
`0`, `$`, `^`, `G`, 비주얼 라인 선택, `D` 같은 것들이다.
그는 비주얼 모드에서 Helix가 줄을 “부분적으로 선택한다”고 지적했다.
이는 선택 우선 모델이 줄 단위 작업에서
Vim보다 불편한 지점이 있다는 구체적 증거다.

HN에서 soraminazuki가 이 구조적 약점을 가장 정밀하게 분석했다.
그는 처음에 Helix의 명사-동사 모델이 매력적이라고 느꼈지만
써본 뒤에는 동사-명사 쪽을 훨씬 선호하게 되었다고 밝혔다.

첫 번째 이유는 반복이다.
명사-동사 접근은 Vim에서 가장 좋아하는 기능인 `.` 명령을 통한 반복을 지원하지 못한다.
`dd..`, `dap..`, `..`, `/foocgnbar...un...` 같은 형태를
자주 쓰게 된다는 것이다.

더 중요한 이유는 키가 부족해진다는 것이다.
너무 많은 흔한 조작이 Alt 키를 요구하게 되며,
이것이 명사-동사 모델에 내재된 성질로 보인다는 것이다.
그의 설명은 이렇다.
Vim은 노멀, 비주얼, 인서트 모드를 갖는다.
명사-동사 에디터는 비주얼과 인서트만 가지므로
키를 배정할 자리가 그만큼 적다.
게다가 명사-동사 에디터는 모션과 텍스트 오브젝트를 구분하지 않으므로
텍스트 오브젝트를 비주얼 모드에 매핑해야 하는데,
Vim은 특정 동사 뒤에만 매핑하면 된다.
결국 더 적은 모드에서 더 많은 키를 소모하게 된다.[^soraminazuki]

즉 두 모델은 우열 관계가 아니라 각자 잘하는 영역이 다르다.
Helix의 소개는 자기 모델의 장점만 제시하고
어떤 작업에서 불리한지는 말하지 않는다.
Kakoune이 소수에 머문 이유 중 일부가 이 지점에 있었을 텐데,
같은 모델을 채택하면서 그 교훈을 다루지 않았다.

흥미로운 것은 Kakoune 사용자 쪽에서도 불만이 나온다는 점이다.
GrantMoyer는 Helix에 “Kakoune 모드”가 생기기를 바란다고 적었다.
직장에서 Windows로 개발하는데 Kakoune은 그 환경에 이상적이지 않아
Helix가 딱 맞을 것 같지만 키 바인딩을 넘어설 수 없다는 것이다.
Helix의 키 바인딩 철학이 Kakoune의 간결함 대신 장황함을 조장하며,
키맵 설정이 Kakoune을 제대로 흉내 낼 만큼 강력하지도 않다고 그는 봤다.
애초에 그를 Kakoune으로 밀어낸 것이
Vim의 일관성 없는 키 바인딩과 동작이었는데,
Helix는 그 축에서 한 걸음 후퇴한 느낌이라는 것이다.[^GrantMoyer]
원조와 계승자 사이의 이 간극은
Helix가 채택한 것이 Kakoune의 모델이지 그 설계 미학은 아니었음을 보여준다.

### 근육 기억 충돌이 채택의 실질적 장벽이다

HN 토론에서 가장 자주 반복된 이탈 사유는 기능이 아니라 손가락이었다.
spapas82는 Helix가 설정이나 플러그인 설치 없이
파일 피커, 문법 강조, 린팅 같은 것을 기본 제공한다는 점을 인정하면서도,
Vim과 다르게 동작하는 키 바인딩이 주된 단점이라고 했다.
키 바인딩이 Vim보다 나을 수는 있지만,
수년간 Vim을 쓴 뒤로는 노멀 모드의 `x`가 커서 아래 문자를 지우고
`d`가 모션을 기다리기를 기대하게 된다는 것이다.
그렇게 되지 않으면 혼란스럽고 화가 난다고 그는 적었다.
Vim은 어디에나 있어서 결코 벗어날 수 없기 때문에
습관을 바꾸기가 특히 어렵다는 것이다.
그는 해법으로 Vim 키 바인딩을 도입한 소프트 포크
evil-helix를 추천했다.[^spapas82]

Macha는 이 충돌이 왜 유독 심한지에 대해 흥미로운 가설을 냈다.
그는 브라우저 텍스트 필드나 채팅 앱과 Vim 사이를 오갈 때는
아무 어려움을 느끼지 않으므로
“전통적” 키 바인딩에 대해서는 머릿속에 별도 모드를 둘 수 있다는 것이다.
그렇다면 문제는 Helix 근육 기억이 아직 충분히 새겨지지 않은 것인지,
아니면 Vim 경험에 대한 언캐니 밸리에 있는 것인지 궁금하다고 했다.[^Macha]
eminence32는 더 실용적인 제약을 짚었다.
Helix를 모든 곳에 설치할 수는 없어서
기계에 따라 Helix와 Vim을 오가게 되고,
그때마다 근육 기억에 큰 압력이 걸린다는 것이다.[^eminence32]

lukaslalinsky는 흐름을 익힌 뒤에 내린 판단을 공유했다.
스스로에게 강제해 배웠고 이제는 효율적으로 쓸 수 있게 되었지만,
뒤집힌 흐름이 구현하기 쉽고 배우기 쉬운 대신
쓰기에는 그냥 더 느리다는 결론에 도달했다는 것이다.
그는 Vim으로 돌아갔고 결국 Zed(Vim 모드)로 갔다.[^lukaslalinsky]
학습 난이도와 사용 효율이 다른 축이라는 이 관찰은,
“배우기 쉽다”를 장점으로 내세우는 프로젝트가
반드시 답해야 할 질문을 제기한다.

### 터미널 우선이라는 선택이 장기적으로 제약이 된다

README는 Helix가 주로 터미널 기반이며
wgpu 커스텀 렌더러에 관심이 있다고 언급한다.
이 언급은 짧지만 프로젝트가 인식하고 있는 제약을 드러낸다.

터미널은 텍스트 편집기에 여러 제약을 건다.
문자 격자를 벗어나는 표현이 어렵다.
LSP 문서 색상 기능에서 색상 견본을 보여주려면
결국 색깔 있는 문자로 근사할 수밖에 없다.
인라인 이미지, 부드러운 스크롤, 가변 폭 글꼴,
비례 간격의 인레이 힌트 같은 것들이 전부 어렵거나 불가능하다.

더 큰 문제는 입력 쪽이다.
터미널의 키 입력 프로토콜은 오래된 제약을 그대로 안고 있어
Ctrl과 특정 키의 조합이 구분되지 않는 경우가 있다.
Kitty 키보드 프로토콜 같은 확장이 있지만 지원이 균일하지 않다.

wgpu 렌더러를 고려한다는 것은 이 천장을 인식했다는 뜻이지만,
동시에 프로젝트 범위가 크게 늘어난다는 뜻이기도 하다.
자체 렌더러는 글꼴 렌더링, 입력기 처리, 접근성, 플랫폼별 창 관리를
전부 직접 감당한다는 것이고,
이는 에디터 코어보다 큰 작업이 될 수 있다.
Neovim이 여러 GUI 프런트엔드를 외부에 맡긴 것과
Helix가 직접 만들려는 것 사이의 차이가
이 프로젝트의 자원 배분에 어떤 영향을 줄지가 관건이다.

## 인사이트

### 설정 가능성을 없애는 것은 기능 축소가 아니라 비용 이전이다

Helix가 플러그인 없이 좋은 기본값을 제공한다는 점은
대체로 사용자 편의의 관점에서 이야기된다.
설정할 필요가 없어서 편하다는 것이다.
그러나 이 변화의 더 중요한 측면은 비용이 어디로 옮겨갔는지에 있다.

Vim 모델에서 “어떤 LSP 클라이언트를 쓸 것인가”의 결정 비용은
사용자 각자가 지불한다.
100만 명의 사용자가 있으면 100만 번 지불된다.
플러그인 조합이 깨졌을 때의 디버깅 비용도 마찬가지다.

Helix 모델에서 이 결정은 한 번만 내려진다.
비용은 프로젝트 관리자에게 집중되고,
사용자 쪽에서는 사라진다.
총량으로 보면 압도적으로 효율적이다.

그런데 이 효율에는 조건이 있다.
결정이 대다수 사용자에게 맞아야 한다는 것이다.
맞지 않는 소수는 이전에는 스스로 고칠 수 있었지만
이제 고칠 수단이 없다.
중앙 결정의 이득은 다수에게 가고 손실은 소수에게 집중된다.

이 구조는 에디터를 넘어 소프트웨어 전반에서 반복된다.
Rails의 관례 우선 설정, Go의 포맷터 강제,
Prettier의 옵션 최소화, Deno의 표준 라이브러리 내장.
전부 같은 거래를 제안한다.
결정권을 넘기면 결정 비용을 없애주겠다는 것이다.

이 거래가 좋은 거래인지는 시간이 지나야 안다.
중앙에서 내린 결정이 시대에 뒤처지고
사용자가 우회할 수단이 없을 때 무슨 일이 벌어지는지가 진짜 시험이다.
Helix는 아직 그 시험대에 오르지 않았다.
tree-house 재작성처럼 코어를 갈아엎을 수 있는 동안은 괜찮지만,
사용자 기반이 커져 하위 호환성이 발목을 잡기 시작하면
플러그인 부재는 유연성이 아니라 경직성으로 나타날 것이다.

### 좋은 기본값 전략은 에디터에서 개발 환경 전반으로 번지고 있다

Helix가 LSP와 tree-sitter를 내장한 것을
개별 에디터의 설계 선택으로만 보면 흐름을 놓친다.
같은 패턴이 개발 도구 전반에서 동시에 진행 중이다.

Go는 포맷터와 테스트 러너와 의존성 관리를 언어에 넣었다.
Rust는 Cargo, rustfmt, clippy를 표준 도구로 제공한다.
Deno는 런타임에 린터, 포맷터, 테스트 러너, 번들러를 넣었다.
Bun도 같은 방향이다.
Zig는 빌드 시스템을 언어의 일부로 만들었다.

공통점은 조합의 부담을 없애는 것이다.
2010년대 JavaScript 생태계가 도구 조합의 지옥을 겪은 것이
이 흐름의 직접적 배경이다.
Babel, Webpack, ESLint, Prettier, Jest를 각각 고르고 설정하고
버전 충돌을 해결하는 데 드는 시간이
실제 코드를 쓰는 시간을 잠식하는 상황이 널리 인식되었다.

Helix는 이 흐름이 에디터에 도달한 사례다.
그리고 에디터는 이 흐름의 마지막 보루에 가까웠다.
Vim과 Emacs가 대표하는 “무한히 설정 가능한 도구”라는 이상은
개발자 문화의 핵심 가치 중 하나였다.
그 자리에서 반대 방향의 제안이 45.7k의 스타를 받는다는 것은
가치관 자체가 이동하고 있다는 신호다.

이 이동의 다음 단계는 짐작 가능하다.
LSP와 tree-sitter를 내장한 다음에 내장될 것은
AI 코딩 보조다.
그리고 그것이 내장되면 설정 가능성 논쟁은
지금과 다른 형태로 다시 시작될 것이다.
어떤 모델을 쓸 것인가, 어디로 코드가 전송되는가,
어떤 컨텍스트가 수집되는가.
플러그인 시스템이 없는 에디터가 이 결정을 중앙에서 내리면
그 결정은 사용자가 우회할 수 없는 것이 된다.

### 에디터 전환의 진짜 비용은 근육 기억이 아니라 축적된 우회 지식이다

Helix로 옮기는 사람들의 기록을 보면 흥미로운 공통점이 있다.
키 바인딩 적응은 예상보다 쉬웠다고 말한다.
Evans는 “Helix 방식”을 그대로 배우는 편이 나았다고 했다.

그런데 불편함의 목록은 다른 곳에서 나온다.
마크다운 텍스트 재정렬이 `gq`와 다르게 동작한다.
마크다운 목록이 Enter에서 자동으로 이어지지 않는다.
지속 실행 취소가 없다.
파일을 손으로 다시 읽어야 한다.

이 항목들의 성격을 보면 전부 “특정 상황에서의 미세한 동작”이다.
편집 모델과 무관하고, 배워서 극복할 수 있는 것도 아니다.
수년간 특정 도구를 쓰면서 몸에 익은
“이럴 때는 이렇게 하면 된다”는 우회 지식의 목록이
새 도구에서 하나씩 무효화되는 것이다.

이 관찰은 도구 전환 일반에 적용된다.
전환 비용을 추정할 때 사람들은 대체로 학습 곡선을 생각한다.
새 문법, 새 개념, 새 워크플로.
그러나 이것들은 집중해서 며칠이면 넘는다.
정말 오래 걸리는 것은 예외 상황 목록을 다시 쌓는 일이다.
그리고 이 지식은 문서에 없다.
문서는 정상 경로를 설명하지 예외를 설명하지 않는다.

여기서 나오는 실무적 함의는 두 가지다.
하나는 전환을 검토할 때 “며칠 써보고 판단”이 부정확하다는 것이다.
며칠로는 예외 상황을 만나지 못한다.
Evans가 3개월을 쓰고도 “영구 채택을 보장하지 않는다”고 유보한 것은
이 성질을 정확히 반영한 태도다.

다른 하나는 도구를 만드는 쪽에 대한 것이다.
채택을 막는 것은 대체로 핵심 기능의 부재가 아니라
주변부의 작은 마찰들이다.
목록 자동 이어쓰기 같은 기능은 로드맵에서 우선순위가 낮지만
실제 전환 결정에는 크게 작용한다.
전환 사례 기록을 모아 마찰 목록을 만드는 것이
새 기능을 추가하는 것보다 채택에 효과적일 수 있다.

### 의존성 최소화가 보안 논거로 제시되는 것은 새로운 국면이다

Golubin이 Neovim에서 Helix로 옮긴 이유로 제시한 것은
편집 모델의 우월성이 아니라 공급망 공격에 대한 우려였다.
수많은 플러그인이 각각 공급망 위험을 만든다는 것이다.

이 논거가 등장했다는 사실 자체가 시대의 변화를 보여준다.
과거 에디터 선택의 기준은 기능, 성능, 익숙함이었다.
플러그인이 많다는 것은 명백한 장점으로만 여겨졌다.

npm 생태계에서 반복된 공급망 사건들이 이 인식을 바꿨다.
`event-stream`, `ua-parser-js`, `node-ipc` 같은 사례에서
널리 쓰이는 패키지가 악성 코드를 담아 배포되었다.
Vim과 Neovim 플러그인 생태계는 npm보다 검증 장치가 약하다.
대부분 GitHub 저장소를 직접 클론하는 방식이고,
서명도, 감사도, 중앙 심사도 없다.

에디터가 특히 위험한 표적인 이유도 명확하다.
개발자의 소스 코드 전체에 접근하고,
자격 증명 파일이 있는 홈 디렉터리에서 실행되며,
셸 명령을 실행할 수 있고,
언제나 켜져 있다.
에디터 플러그인은 사실상 최고 권한으로 도는 코드다.

여기서 나오는 예측은 플러그인 생태계의 신뢰 모델이
앞으로 몇 년 안에 재편되리라는 것이다.
서명된 배포, 권한 선언, 샌드박스 실행 같은
브라우저 확장 프로그램이 이미 거쳐온 경로를
에디터 플러그인도 밟게 될 가능성이 높다.

그리고 이것은 Helix에게 양날의 검이다.
지금은 플러그인이 없어서 안전하다는 논거가 성립하지만,
플러그인 시스템을 도입하는 시점에 이 논거를 잃는다.
반대로 처음부터 권한 모델을 갖춘 플러그인 시스템을 설계한다면
후발 주자의 이점을 살릴 수 있다.
Helix가 플러그인 시스템을 오래 미뤄온 것이
결과적으로 이 설계 기회를 만들어줬다는 해석도 가능하다.

다만 이 논거가 얼마나 견고한지는 따져볼 문제다.
HN에서 bitbasher는 정면으로 반박했다.
그렇다면 그냥 Vim을 쓰지 그러느냐는 것이다.
설정의 절반이 Helix 안에서 Vim을 재현하는 일이고,
Helix에도 의존성이 많은데 Neovim에서처럼 눈에 보이지 않을 뿐이라는 것이다.
그는 자기 Vim 설정이 Helix보다 공급망 측면에서 더 안전하다고 주장할 수 있다고 했다.
8년 넘게 유지해온 vim8 설정에서
자동 로드되는 플러그인은 하나뿐이고,
코드를 검토했으며 업데이트하지 않는다.
선택적으로 두 개를 더 쓰는데 각각 코드를 읽고 만족한 뒤
이유 없이는 갱신하지 않는다는 것이다.
필요할 때가 아니면 코드를 자동으로 실행할 이유가 없다고 그는 정리했다.[^bitbasher]

이 반론의 핵심은 공급망 위험이 플러그인 개수가 아니라
갱신 정책과 코드 검토 여부에서 온다는 것이다.
플러그인을 쓰지 않는 에디터도 자체 의존성을 갖고 정기적으로 갱신되며,
그 코드를 사용자가 읽지는 않는다.
반면 소수의 플러그인을 고정해두고 코드를 검토한 설정은
공격 표면이 오히려 작을 수 있다.

그럼에도 이 우려가 실제 채택 동기로 작동한다는 증거는 늘어나고 있다.
rmrf100은 Golubin이 인용한 문장
“새로 생겨나는 공급망 공격이 많은데,
에디터를 쓸 만하게 만들려고 플러그인 수십 개를 설치한다는 발상이 그냥 싫다”를
그대로 옮기며 자기 걱정이 정확히 이것이라고 밝혔다.[^rmrf100]
commandersaki는 Neovim에서 공급망 공격을 고려해본 적이 없었는데
플러그인을 15개쯤 쓰고 있으니 다소 걱정스럽다며,
저자가 공격 표면이 작은 쪽으로 옮긴 이유를 이해할 수 있다고 적었다.[^commandersaki]
논거의 엄밀함과 무관하게,
이 문제의식이 도구 선택 기준으로 자리 잡고 있다는 것 자체가
앞의 예측을 뒷받침한다.
