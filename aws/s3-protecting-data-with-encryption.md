# S3 Protecting Data with Encryption

원문: [Protecting data with encryption - Amazon S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryption.html)

## 요약

Amazon S3의 데이터 암호화 옵션을 총괄하는 사용자 가이드 문서다.
데이터 보호를 전송 중(in transit)과 저장 시(at rest)로 나누고,
전송 중 보호는 SSL/TLS(하이브리드 포스트 퀀텀 키 교환 포함)와 클라이언트 측 암호화로,
저장 시 보호는 서버 측 암호화(SSE)와 클라이언트 측 암호화로 정리한다.
문서 첫머리의 공지가 현재 상태를 규정한다.
2023년 1월 5일부터 모든 신규 객체 업로드는
S3 관리 키 기반 서버 측 암호화(SSE-S3)로 추가 비용과 성능 영향 없이 자동 암호화되며,
SSE-S3가 모든 버킷의 기본 암호화 구성이다.

서버 측 암호화는 상호 배타적인 네 가지 옵션으로 나뉜다.
기본값인 SSE-S3는 객체마다 고유 키로 AES-256 암호화하고
그 키를 정기 순환되는 루트 키로 다시 암호화한다.
SSE-KMS는 AWS KMS 통합으로 키에 대한 통제를 높인 옵션으로,
키를 개별적으로 보고, 정책을 편집하고, CloudTrail로 사용을 추적할 수 있다.
DSSE-KMS는 SSE-KMS와 비슷하지만 KMS 데이터 키와
S3 관리 키로 독립적인 AES-256 암호화를 두 겹 적용해
다층 암호화 규정 준수 요구를 서버 측에서 충족한다.
SSE-C는 고객이 키를 제공·관리하고 S3가 암복호화만 수행하는 방식이다.
같은 객체에 서로 다른 서버 측 암호화를 동시에 적용할 수는 없다.

운영상의 세부도 담겨 있다.
버킷의 기본 암호화 구성을 SSE-KMS로 바꿔도 기존 객체의 암호화 방식은 바뀌지 않으므로,
기존 객체를 재암호화하려면 S3 Batch Operations의 Copy 작업으로
객체를 같은 버킷에 다시 써야 하며, 단일 작업으로 수십억 객체를 처리할 수 있다.
암호화된 객체와 그렇지 않은 객체의 접근 방식에는 차이가 없어서
프리사인드 URL이나 목록 API는 동일하게 동작하고,
스토리지에서 암호화된 바이트의 비율은 S3 Storage Lens 지표로 확인할 수 있다.

하위 문서의 최신 공지 하나가 눈에 띈다.
2026년 4월부터 S3는 모든 신규 범용 버킷에서 SSE-C를 기본 비활성화했고,
SSE-C 객체가 없는 계정의 기존 버킷에도 신규 쓰기 요청의 SSE-C를 차단했다.
SSE-C가 필요한 애플리케이션은 버킷 생성 후
`PutBucketEncryption` API로 명시적으로 활성화해야 한다.

## 분석

### 기본값의 역사 — 옵트인 암호화에서 강제 암호화까지

이 문서의 현재 모습은 15년에 걸친 기본값 이동의 결과물이다.
S3의 서버 측 암호화는 처음에 순수한 옵트인 기능이었고,
암호화되지 않은 버킷의 대량 유출 사고
(Capital One 사건을 비롯한 수많은 “S3 버킷 노출” 뉴스)가
업계의 반복 레퍼토리가 된 뒤에야
2023년의 전면 기본 암호화로 귀결됐다.
“추가 비용 없음, 성능 영향 없음”이라는 문구는
기술적 성과인 동시에, 그렇다면 왜 처음부터 기본이 아니었는가라는
질문을 남기는 고백이기도 하다.

주목할 점은 기본 암호화 이후 이 문서의 역할 변화다.
모든 객체가 어차피 암호화되는 세계에서
이 문서가 실제로 안내하는 것은 “암호화할 것인가”가 아니라
“누가 키를 통제하고 감사할 것인가”다.
SSE-S3, SSE-KMS, DSSE-KMS, SSE-C의 구분은 암호 강도의 구분이 아니라
(전부 AES-256이다) 키 관리 책임과 통제권의 구분이며,
문서 스스로 “키를 어떻게 관리할지에 따라” 옵션이 갈린다고 명시한다.

### 네 가지 옵션은 사실상 신뢰 모델의 스펙트럼이다

네 옵션을 나란히 놓으면 AWS를 얼마나 신뢰하는가의 스펙트럼이 드러난다.
SSE-S3는 키 생성·보관·순환·사용을 전부 AWS에 위임하는 완전 신뢰,
SSE-KMS는 키는 AWS에 있지만 정책과 감사를 고객이 쥐는 조건부 신뢰,
DSSE-KMS는 단일 암호화 계층의 실패까지 가정하는 규제 수준의 불신,
SSE-C는 키를 AWS에 맡기지 않는 최소 신뢰다.
클라이언트 측 암호화는 스펙트럼의 끝, 즉 암호화 과정 자체를 AWS 밖에 두는 선택이다.

이 스펙트럼에서 실질적 기본 선택지는 SSE-KMS다.
SSE-S3는 규정 준수 문서에 “누가 키에 접근했는가”를 답할 수 없고,
DSSE-KMS와 SSE-C는 특수한 요구가 있을 때만 정당화되기 때문이다.
문서가 SSE-KMS 단락에서 CloudTrail 추적을 강조하는 것은
암호화의 실무적 가치가 기밀성 그 자체보다
감사 가능성(auditability)에 있다는 점을 반영한다.
저장 시 암호화는 디스크 탈취라는 낮은 확률의 위협보다,
“키 사용 기록”이라는 형태로 접근 통제를 증명하는 수단으로 쓰인다.

### SSE-C 기본 비활성화 — 랜섬웨어가 바꾼 기능의 지위

2026년 4월의 SSE-C 기본 비활성화는 이 문서에서 가장 정치적인 변화다.
SSE-C는 “고객에게 최대의 키 통제권을 주는” 기능으로 설계됐지만,
공격자가 탈취한 자격 증명으로 피해자의 객체를
공격자만 아는 키의 SSE-C로 재암호화하는 랜섬웨어 기법
(2025년 초 Codefinger 캠페인으로 널리 알려졌다)에 그대로 악용됐다.
AWS는 키를 보관하지 않으므로 복호화를 도울 수 없고,
피해자는 백업이 없으면 데이터를 영구히 잃는다.
키 비보관이라는 프라이버시 강점이 복구 불가능이라는 공격 표면으로 뒤집힌 것이다.

이 대응 방식 자체가 흥미롭다.
AWS는 SSE-C를 제거하지 않고 기본값을 뒤집었다.
새 버킷은 SSE-C 쓰기가 차단되고, 필요한 쪽이 명시적으로 켜야 한다.
위험한 기능을 옵트아웃에서 옵트인으로 강등시키는 이 패턴은
기능의 존재와 기능의 접근성을 분리하는 클라우드 사업자의
전형적인 위험 관리 수법이고,
“기존에 SSE-C 객체가 있는 계정은 건드리지 않는” 예외 처리에서
하위 호환성과 보안 사이의 타협선이 어디에 그어지는지 보인다.

## 비평

### “기본 암호화”의 안심 효과는 위협 모델을 흐린다

문서는 2023년 이후 모든 객체가 자동 암호화된다는 사실을
가장 눈에 띄는 위치에서 반복하지만,
이 기본 암호화(SSE-S3)가 어떤 위협을 막고 어떤 위협을 못 막는지는 말하지 않는다.
SSE-S3는 AWS 데이터 센터의 디스크가 물리적으로 탈취되는 시나리오를 막는다.
그러나 S3 유출 사고의 압도적 다수는 디스크 탈취가 아니라
퍼블릭 버킷 설정 오류, 과도한 IAM 권한, 자격 증명 탈취로 일어나고,
이 경우 요청이 정상 인증되므로 SSE-S3는 아무것도 막지 못한다.
문서 스스로 “인증되고 권한이 있으면 암호화 여부와 무관하게 동일하게 접근된다”고
명시하면서도, 이 문장이 곧 기본 암호화의 보호 범위 한계라는 점은 짚지 않는다.

결과적으로 “모든 것이 암호화되어 있다”는 메시지는
체크리스트 규정 준수에는 유용하지만 실질 보안 판단에는 오해를 낳는다.
“encryption at rest: yes”를 체크한 조직이
버킷 정책과 퍼블릭 액세스 차단 점검을 뒤로 미루는 것이
이 안심 효과의 전형적 부작용이다.
위협 모델별로 어떤 옵션이 무엇을 막는지 표 하나면 해결될 공백인데,
15년 된 문서가 여전히 그 표를 제공하지 않는 것은
옵션 나열이 위협 설명보다 벤더에게 안전하기 때문이라고 볼 수밖에 없다.

### 옵션 선택의 실질 비용이 문서 바깥에 숨어 있다

이 문서는 네 옵션을 중립적으로 나열하지만,
실무에서 선택을 좌우하는 변수들은 전부 하위 문서와 요금표에 흩어져 있다.
SSE-KMS는 KMS API 호출 비용과 요청 쿼터가 발생하고,
고트래픽 버킷에서는 S3 Bucket Keys를 켜지 않으면
KMS 비용이 폭증하거나 스로틀링이 일어난다.
DSSE-KMS는 GB당 추가 요금이 붙는다.
크로스 계정 접근, 리플리케이션, Athena 같은 다른 서비스와의 상호작용에서
SSE-KMS는 키 정책이라는 별도의 실패 지점을 추가한다.
이 총람 문서만 읽고 옵션을 고르면 비용과 운영 복잡성의 함정을 그대로 밟는다.

기존 객체 재암호화 안내도 같은 문제가 있다.
Batch Operations의 Copy로 “수십억 객체를 처리할 수 있다”고 쓰지만,
그 복사가 객체당 요청 비용과 (버전 관리 버킷에서) 이전 버전의 보관 비용을 발생시키고,
Glacier 계열 스토리지 클래스에서는 복원부터 필요하다는 점은 언급이 없다.
가능하다(can)와 저렴하다(cheap)의 간극을 문서가 채워 주지 않으므로,
독자는 마케팅적 수치(“billions of objects”)만 얻고
의사결정에 필요한 비용 구조는 얻지 못한다.

### SSE-C 정책 반전은 문서 구조에 조용히 묻혀 있다

SSE-C 기본 비활성화는 보안 태세에 대한 중대한 정책 반전인데,
그 배경 — 왜 갑자기 2026년에 기본값을 뒤집었는가 — 을
문서는 “Default SSE-C setting FAQ” 링크 뒤에 숨긴다.
랜섬웨어 악용이라는 실제 이유를 본문에서 언급하지 않으므로,
독자는 이 변경을 임의적인 정책 변덕으로 읽거나 아예 지나치게 된다.
보안 문서에서 변경의 위협 맥락을 생략하는 것은
사용자가 자신의 환경에서 같은 위협을 점검할 기회를 뺏는 일이다.
SSE-C를 여전히 쓰는 조직이라면 “우리 자격 증명이 탈취되면
공격자가 우리 데이터를 그들의 키로 잠글 수 있는가”를 자문해야 하는데,
문서는 그 질문으로 안내하지 않는다.

더 넓게 보면 이는 벤더 문서의 구조적 한계다.
AWS 문서는 현재 상태의 기술(記述)에 최적화되어 있고,
“왜 이렇게 바뀌었는가”라는 역사와 사고의 기록은
블로그, FAQ, 외부 보안 리서치로 외주화된다.
현재 상태만 읽는 독자는 기본값 하나하나가
과거 사고의 흉터라는 사실을 알 수 없고,
그래서 같은 종류의 판단 착오 — 위험한 유연성을 켜 두는 것 — 를 반복한다.

## 인사이트

### 저장 시 암호화의 실효 위협 모델은 이제 외부 침입자가 아니라 계정 내부의 폭발 반경이다

기본 암호화가 보편화된 뒤에도 SSE-KMS를 선택하는 이유를 따라가 보면,
저장 시 암호화의 실질 역할이 바뀌었음이 드러난다.
디스크 탈취 방어는 SSE-S3로 이미 충족되므로,
SSE-KMS가 추가로 제공하는 것은 암호학이 아니라
IAM과 독립적인 두 번째 인가 계층이다.
객체에 접근하려면 S3 권한과 KMS 키 권한이 모두 필요하므로,
S3 권한이 과도하게 풀리는 사고(잘못된 버킷 정책, 훔친 자격 증명)가 나도
키 정책이 폭발 반경(blast radius)을 한 번 더 자른다.
암호화 옵션 선택은 사실상 “권한 사고 시 피해 범위를
몇 겹의 독립 정책으로 제한할 것인가”의 선택이다.

이 관점은 옵션 선택 기준을 단순화한다.
컴플라이언스 체크박스가 목적이면 SSE-S3로 이미 충분하고,
내부자·자격 증명 탈취까지 위협 모델에 넣는 순간 SSE-KMS가 하한이 되며,
DSSE-KMS와 SSE-C는 규제나 계약이 명시적으로 요구할 때만 존재 이유가 있다.
문서가 중립적으로 나열하는 네 옵션은
실제로는 이렇게 위협 모델별 계단으로 읽어야 하고,
“어떤 암호화를 쓰는가”보다 “키 정책을 누가 어떻게 관리하는가”가
운영 보안의 실질 변수가 된다.

### 고객 통제권의 극대화는 공격자 통제권의 극대화이기도 하다 — SSE-C의 교훈

SSE-C의 흥망은 보안 기능 설계의 일반 원리를 보여 준다.
“서비스 제공자가 키를 절대 보관하지 않는다”는 속성은
설계 문서에서는 프라이버시의 극치지만,
자격 증명 탈취라는 흔한 사고와 결합하면
공격자가 서비스 제공자조차 풀 수 없는 잠금을 만드는 도구가 된다.
복구 불가능성은 대칭적이다.
벤더가 고객 데이터를 볼 수 없게 만드는 메커니즘은
벤더가 고객을 구할 수 없게 만드는 메커니즘이기도 하다.

같은 구조는 다른 곳에서도 반복된다.
종단 간 암호화 메신저의 계정 복구 불가,
자체 관리 키(BYOK)를 잃은 조직의 데이터 영구 손실,
하드웨어 지갑 시드 분실로 사라지는 암호화폐가 모두 같은 대칭성의 사례다.
교훈은 “통제권 극대화 기능을 만들지 말라”가 아니라,
그런 기능의 기본값은 꺼져 있어야 하고
켜는 쪽이 복구 전략(백업, 키 에스크로, 버전 관리)을 증명해야 한다는 것이다.
AWS가 2026년에 한 일이 정확히 이것이고,
3년이 걸렸다는 사실은 기본값 변경이 기술 문제가 아니라
하위 호환성과 고객 반발을 계산하는 정치 문제임을 보여 준다.

### 클라우드 보안의 진화는 기능 추가가 아니라 기본값 교정의 역사다

이 문서에 쌓인 지층 — 2023년 전면 기본 암호화, 2026년 SSE-C 기본 차단 —
을 나란히 놓으면 클라우드 보안의 실제 진행 방향이 보인다.
새 보안 기능의 발명보다,
이미 있던 기능의 기본값을 안전한 쪽으로 옮기는 것이
집합적 보안 수준을 실제로 끌어올린다.
S3의 퍼블릭 액세스 차단 기본화, EBS 기본 암호화, IMDSv2 강제화가 모두 같은 계열이다.
개별 고객의 보안 역량에 기대는 옵트인 모델은
역량 분포의 하위 절반에서 반드시 실패하고,
그 실패가 뉴스가 될 만큼 쌓이면 벤더가 기본값을 옮긴다.

이 패턴에는 예측력이 있다.
지금 옵트인으로 존재하는 보안 기능 중 사고가 누적되는 것
— 예컨대 버킷 소유권 강제, 조직 수준의 리전 제한 —
은 몇 년 안에 기본값이 될 가능성이 높고,
아키텍처를 설계할 때 “미래의 기본값”을 미리 채택하는 조직은
전환 비용 없이 그 흐름에 올라탄다.
반대로 위험한 유연성(SSE-C 같은)에 의존한 설계는
벤더의 기본값 교정 한 번에 마이그레이션 부채로 바뀐다.
벤더 문서의 “Important” 공지들은 기능 안내가 아니라
이 기본값 이동의 방향을 알리는 신호로 읽는 것이 옳다.

### 문서의 중립적 옵션 나열은 그 자체가 설계 부채를 만든다

이 문서가 보여 주는 벤더 문서의 관행 —
모든 옵션을 동등하게 나열하고 선택 기준을 독자에게 맡기는 것 —
은 개별 기능 문서로는 합리적이지만,
생태계 수준에서는 잘못된 선택의 양산 장치가 된다.
네 옵션의 실제 적합 분포는 극도로 비대칭이어서
대부분의 워크로드에는 SSE-S3 또는 SSE-KMS + Bucket Keys가 정답이고
나머지는 좁은 예외인데,
중립 서술은 이 비대칭을 전달하지 못한다.
그 결과 “더 많은 통제 = 더 안전”이라는 직관에 이끌려
필요 없는 DSSE-KMS나 SSE-C를 선택하고
비용과 운영 복잡성, 심지어 새로운 공격 표면을 떠안는 조직이 생긴다.

이 공백을 메우는 것이 사내 표준과 가드레일의 역할이다.
성숙한 조직이 벤더 문서를 그대로 개발자에게 주지 않고
“우리는 SSE-KMS + Bucket Keys를 쓴다, 예외는 보안팀 승인”이라는
한 줄의 정책으로 번역하는 이유가 여기에 있다.
벤더 문서는 가능한 것의 지도이고, 조직 정책은 해야 할 것의 경로다.
전자를 후자로 오독하는 것 — 문서에 있으니 써도 된다는 판단 —
이 클라우드 설정 오류의 꾸준한 공급원이며,
SSE-C 랜섬웨어 사태는 그 오독의 비용이 어디까지 갈 수 있는지 보여 준 사례다.
