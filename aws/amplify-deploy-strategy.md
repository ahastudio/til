# Amplify 배포 전략

AWS Amplify Hosting은 배포 모델이 Git 브랜치에 묶여 있다.
이 제약을 그대로 따라가면 팀의 저장소가 환경별 장수 브랜치로 쪼개지고,
트렁크 기반 개발(Trunk-Based Development, TBD)은 소리 없이 무너진다.
이 글은 그 위험이 왜 생기는지, 왜 나쁜지, 그리고 브랜치를 나누거나
브랜치 간 머지를 하는 일 없이 `main`의 특정 시점 커밋을
배포 대상에 그대로 부어주는 방식으로 어떻게 관리해야 하는지를 정리한다.

## Amplify에는 promote가 없다

### promote가 있는 세계

Vercel이나 Netlify는 "빌드 산출물"과 "환경"을 분리한다.
어떤 커밋에서 만들어진 빌드(deployment)가 먼저 존재하고,
그 빌드를 프로덕션 도메인에 연결하는 행위(promote)가 별도로 있다.
이 분리가 주는 이점은 구체적이다.

- 스테이징에서 검증한 바로 그 산출물을 손대지 않고 프로덕션으로 승격할 수 있다.
- 문제가 생기면 이전 빌드로 즉시 되돌릴 수 있다. 재빌드도, Git 조작도 필요 없다.
- 배포 이력이 배포 시스템 안에 남는다. 어떤 빌드가 언제 어디에 연결됐는지가
  Git 히스토리와 무관하게 조회된다.

핵심은 "검증"과 "공개"가 서로 다른 시점에 일어날 수 있다는 것이다.
빌드는 커밋 시점에 한 번 일어나고,
그 빌드를 어느 환경에 보여줄지는 나중에 몇 번이든 바꿀 수 있다.

### Amplify: 브랜치가 곧 환경

Amplify Hosting은 이 분리가 없다.
환경은 오직 Git 브랜치에 연결되며,
배포는 "그 브랜치에 커밋이 들어오는 것"으로만 일어난다.
프로덕션 환경을 원하면 `production` 같은 브랜치를 만들어 연결해야 하고,
배포하고 싶으면 저장소에 푸시해서 그 브랜치에 새 커밋이 도달하게 해야 한다.
정확히 말하면 배포를 일으키는 것은 푸시라는 행위 자체가 아니라,
Amplify가 관찰하는 연결된 브랜치에 커밋이 나타나는 사건이다.
환경 변수조차 브랜치 단위로 설정한다.
플랫폼의 모든 개념이 브랜치를 중심으로 조직되어 있다.

언뜻 `git push heroku main`으로 배포하던 Heroku의 전통을
이어받은 것처럼 보이지만, 뒤에서 살펴보듯 이 인상은 절반만 맞다.
분명한 것은, CodePipeline과 CodeDeploy라는 배포 오케스트레이션 제품을
보유한 AWS가 자사 호스팅 제품에는 그 개념을 넣지 않았다는 점에서,
이것이 설계 철학이라기보다 제품의 미성숙에 가깝다는 사실이다.

### 플랫폼별 배포 모델 비교

| 플랫폼  | 배포 단위   | promote | 재빌드 없는 롤백 |
| ------- | ----------- | ------- | ---------------- |
| Vercel  | 빌드 산출물 | 있음    | 가능             |
| Netlify | 빌드 산출물 | 있음    | 가능             |
| Heroku  | 슬러그      | 있음    | 가능             |
| Amplify | Git 브랜치  | 없음    | 불가능           |

이 표가 보여주는 것은 promote가 특별한 고급 기능이 아니라는 사실이다.
주요 호스팅 플랫폼이 모두 제공하는 기본기를 Amplify만 제공하지 않는다.

## 왜 Amplify는 이렇게 만들었나

비판에 앞서, Amplify가 왜 이런 모델을 택했는지 배경을 검토할 필요가 있다.
이유를 알아야 비판이 공정해지고, 우회 전략의 한계도 정확해지기 때문이다.

### 계보: Heroku에서 GitHub Pages를 거쳐 Netlify로

먼저 "Git으로 배포한다"는 경험의 족보를 정확히 그려야 한다.
Amplify가 무엇을 따라 했고 그중 무엇을 빼먹었는지는
이 족보 위에 놓고 봐야 선명해지기 때문이다.

- **Heroku(2009년경)**: `git push heroku`로 "푸시가 곧 배포"라는
  경험 자체를 개척했다.
  다만 뒤에서 자세히 보듯 푸시 대상은 팀의 공유 저장소가 아니라
  배포 전용 전송 리모트였고,
  내부적으로는 슬러그와 릴리스라는 산출물 계층을 갖고 있었다.
- **GitHub Pages(2008)**: "공유 저장소의 특정 브랜치(`gh-pages`)가
  곧 배포 대상"이라는 발상의 직계 조상은 오히려 이쪽이다.
  브랜치를 환경에 결부시키는 모델은 Heroku가 아니라 여기서 왔다.
- **Netlify(2014~15)**: 두 흐름을 합류시켰다.
  공유 저장소를 웹훅으로 관찰해 브랜치마다 사이트를 만들어 주는 경험
  (GitHub Pages 계열)에,
  빌드마다 불변 산출물을 만들고 그 위에 promote와 롤백을 얹는 구조
  (Heroku의 슬러그/릴리스 계열)를 결합했다.
  "저장소를 연결하면 브랜치마다 사이트가 생긴다"를 대중화한 것은
  Netlify가 맞지만, 개척이 아니라 완성에 가깝다.

Amplify Console(현 Amplify Hosting)은 2018년 re:Invent에서
"Git 기반 워크플로(Git-based workflow)"를 전면에 내세우며 출시됐다.
Netlify의 경험이 프런트엔드 생태계를 사로잡던 시기에
그 AWS판 대항마로 설계된 제품이다.
문제는 무엇을 따라 했느냐다.
Amplify는 Netlify가 합류시킨 두 층 가운데
브랜치 관찰 층만 따라 하고 산출물 층은 만들지 않았다.
Heroku도 슬러그가 있었고 Netlify도 불변 배포가 있었으니,
상용 배포 제품을 자처하면서 산출물 계층 없이 출발한 것은
이 계보에서 Amplify뿐이다.
(GitHub Pages도 산출물 계층이 없지만,
저장소의 무료 부가 기능이지 배포 제품이 아니므로 같은 선상에서 비교할 수 없다.)
즉 Amplify가 브랜치 중심 모델로 출발한 것은 깊은 배포 철학의 결과가 아니라,
경쟁 제품의 온보딩 경험을 반쪽만 따라잡은 결과다.

### 풀스택 지향이 브랜치 결합을 굳혔다

Amplify의 정체성은 단순 정적 호스팅이 아니라
"풀스택 서버리스 앱"의 배포다.
Amplify의 CI/CD는 브랜치마다 프런트엔드와 백엔드(클라우드 리소스)를
한 세트로 묶어 배포하는 구조이고[^amplify-fullstack],
공식 문서는 `main`을 프로덕션, `develop`을 통합 테스트용으로 두는
GitFlow식 팀 워크플로를 권장 패턴으로 안내한다[^amplify-workflows].
백엔드 리소스가 브랜치에 결부되는 순간
"환경 = 브랜치"는 UI 편의가 아니라 아키텍처가 된다.
프런트엔드 빌드 산출물이야 만들어서 승격하면 그만이지만,
브랜치마다 별도로 프로비저닝된 백엔드 스택은
승격이라는 개념 자체가 성립하지 않기 때문이다.
따라잡기로 출발한 브랜치 결합이 왜 되돌리기 어려운 구조로 굳었는지는
이것으로 설명된다.
그러나 설명이 정당화는 아니다.
백엔드가 없는 순수 호스팅 사용자까지 이 결합을 강요받아야 할 이유는 없고,
공식 문서가 GitFlow를 권장 워크플로로 안내하는 것은
TBD 관점에서 보면 안티패턴을 플랫폼이 공인하는 것이다.

이 모델의 결과는 이슈 트래커에 남아 있다.
이전 배포로 즉시 되돌리는 기능 요청은
2020년에 열린 이래 수년째 미해결 상태다[^amplify-542].
브랜치 모델을 유지하는 한 롤백은 "Git을 되감고 재빌드"일 수밖에 없으니,
이것은 구현 지연이 아니라 모델이 만든 구조적 공백이다.

### Heroku의 전통을 이어받았나: 절반의 진실

"결국 Heroku식 아닌가"라는 인상은 정밀하게 따질 가치가 있다.
결론부터 말하면, 겉모습은 닮았지만 구조는 오히려 반대다.

Heroku의 `git push heroku main`에서 `heroku` 리모트는
팀이 협업하는 공유 저장소가 아니라 **배포 전용 전송 계층**이다.
Heroku 공식 문서는 코드 관리는 GitHub 등에서 하고,
Heroku Git은 배포 수단으로만 쓰라고 명시한다[^heroku-git].
리모트의 `main`만 배포를 트리거하며 다른 브랜치 푸시는 무시된다.
심지어 다른 브랜치를 배포하는 공식 방법이
`git push heroku testbranch:main`, 즉 refspec으로
임의 커밋을 배포 포인터에 밀어 넣는 것이다.
이 모양을 기억해 두자.
이 글이 뒤에서 제안할 `git push origin "${SHA}:refs/heads/production"` 전략과
정확히 같은 형태다.
Heroku의 모델은 "배포 브랜치는 포인터일 뿐"이라는 감각을
처음부터 내장하고 있었던 셈이다.

Amplify는 여기서 한 걸음 더 나아갔고, 그것이 나쁜 방향이었다.
배포 트리거를 별도의 전송용 리모트가 아니라
**팀이 실제로 협업하는 저장소의 브랜치**에 연결한 것이다.
그 결과 배포 상태가 팀의 브랜치 구조를 침범하기 시작했다.
Heroku에서는 배포 이력이 팀 저장소 밖(전송용 리모트와 릴리스 목록)에 있었지만,
Amplify에서는 배포용 장수 브랜치가 팀 저장소 안에 상주한다.
"Heroku의 전통을 이어받았다"기보다,
Heroku 모델에서 안전장치 역할을 하던 격리를 제거하고
계승한 것이라고 평가하는 편이 정확하다.
게다가 Heroku 자신은 이후 pipeline promote를 도입해
슬러그를 재빌드 없이 스테이지 간에 승격하는 길을 열며
푸시 전용 모델을 졸업했다.
앞의 비교표에서 Heroku의 promote가 "있음"인 것은 그 결과다.
원조가 졸업한 모델의 열화 계승판만 남아 있는 셈이다.

## 브랜치 쪼개짐이라는 기본 경로

Amplify에서 dev/staging/production 환경을 나누려는 팀이
가장 자연스럽게 도달하는 구성은 브랜치 세 개다.
플랫폼의 문서와 콘솔 UI가 그 방향을 안내하고,
별다른 고민 없이 따라가면 저장소에는 코드의 역사와 무관한,
오직 배포를 위해서만 존재하는 장수(long-lived) 브랜치가 생긴다.
그리고 배포라는 행위가 "머지"라는 Git 조작으로 표현되기 시작한다.

- 스테이징 배포 = `main`을 `staging`에 머지
- 프로덕션 배포 = `staging`을 `production`에 머지
- 롤백 = revert 커밋을 만들거나 브랜치를 강제로 되감기

중요한 것은 이 구성이 누군가의 잘못된 선택이 아니라
플랫폼 제약이 만들어내는 기본 경로(default path)라는 점이다.
promote가 없으니 환경을 나누려면 브랜치를 나누게 되고,
브랜치를 나누면 머지로 배포하게 된다.
아무도 "TBD를 버리자"고 결정한 적이 없는데,
어느 날 돌아보면 저장소는 git-flow 비슷한 무언가가 되어 있다.
방법론은 이렇게 명시적 결정이 아니라 도구의 기본값에 의해 무너진다.

## 이 쪼개짐이 나쁜 이유

TBD의 핵심 주장은 단순하다.
공유 브랜치는 트렁크(`main`) 하나여야 하고,
장수 브랜치는 통합을 지연시켜 머지 지옥과 검증되지 않은 조합을 만들어내므로 없애야 한다.
환경별 브랜치 구성은 이 원칙을 여러 지점에서 무너뜨린다.
하나씩 짚어 보자.

### 검증한 것과 배포된 것이 달라질 수 있다

머지는 새로운 커밋을 만들어내는 연산이다.
이것이 문제의 뿌리다.
promote는 이미 존재하는 불변의 산출물에 포인터를 옮기는 행위라 실패 모드가 거의 없지만,
머지는 두 히스토리를 조합해 새로운 상태를 만들어낸다.

`staging`과 `production`이 조금이라도 어긋나 있으면
(hotfix, 실수로 들어간 직접 푸시, 되감기 흔적)
충돌이 나거나, 더 나쁘게는 충돌 없이 의도하지 않은 조합이 만들어진다.
충돌은 차라리 낫다. 사람이 알아차리기라도 하기 때문이다.
정말 위험한 것은 조용히 성공하는 머지다.
"스테이징에서 검증한 것"과 "프로덕션에 배포된 것"이
같은 커밋이라는 보장이 모델 차원에서 사라진다.
검증한 그대로를 내보내는 것이 배포의 제1원칙인데,
이 모델은 그 원칙을 지키는 일을 사용자 규율에 떠넘긴다.
규율에 의존하는 안전장치는 팀이 바쁠 때, 즉 가장 필요할 때 가장 먼저 무너진다.

### hotfix가 트렁크를 우회하는 경로를 연다

장애 상황에서 `production` 브랜치에 직접 수정을 넣고 싶은 유혹은 강하다.
"지금은 급하니까 일단 프로덕션에 먼저 넣고 나중에 main에 반영하자"는 판단은
그 순간에는 합리적으로 보인다.
그러나 한 번이라도 그 경로가 열리면 `main`에 없는 코드가 프로덕션에 존재하게 되고,
역머지(back-merge)를 잊는 순간 두 브랜치는 영구히 어긋난다.
다음 정기 배포가 그 hotfix를 덮어써서 같은 장애가 재발하는 것은
이 구성에서 놀랄 일이 아니라 예정된 수순이다.
TBD가 장수 브랜치를 금지하는 이유가 정확히 이 발산(divergence)이다.

### Git 히스토리가 배포 로그로 오염된다

`production` 브랜치의 머지 커밋들은 코드의 진화와 아무 관련이 없다.
"2월 3일에 배포했다"는 운영 이벤트는 배포 시스템의 로그에 있어야 할 정보다.
Git은 소스 코드의 역사를 담는 도구이지 배포 이력 대장이 아니다.
배포 브랜치는 도구의 책임 경계를 흐리는 설계이며,
시간이 지나면 "이 머지 커밋이 뭐였지"를 아무도 설명하지 못하는 그래프만 남는다.
`git log`가 코드의 역사 대신 배포 의식(ritual)의 기록으로 채워지는 것이다.

### 롤백이 Git 수술이 된다

장애 상황에서 가장 빨라야 할 작업이
revert 커밋 작성이나 강제 되감기 같은 가장 조심스러운 Git 조작이 된다.
선택지는 둘 다 나쁘다.

- **강제 되감기**: 브랜치 보호 규칙과 충돌하고,
  다른 팀원의 로컬 저장소와 어긋나며, 실수하면 복구가 어렵다.
- **revert 커밋**: 히스토리에 노이즈가 쌓이고,
  나중에 같은 변경을 다시 넣을 때 revert의 revert라는 혼란이 생긴다.

Vercel에서 클릭 한 번인 일이 Amplify에서는 수술이 된다.
그리고 어느 쪽을 택하든 Amplify는 처음부터 다시 빌드한다.
장애 시간은 그만큼 늘어난다.

### 단순함의 비용은 누가 치르는가

Amplify를 변호할 여지가 없지는 않다.
Git 브랜치는 모든 개발자가 아는 인터페이스이고,
"연결된 브랜치에 커밋이 도달하면 배포된다"는 모델은 학습 비용이 거의 없다.
브랜치 하나로 프리뷰 환경을 얻는 경험 자체는 단순하고 매끄럽다.

그러나 그 단순함의 대가가 잘못된 곳에서 지불된다.
호스팅 서비스가 배포 오케스트레이션(산출물 관리, 승격, 롤백)을
구현하지 않은 비용을 팀의 브랜치 전략이 대신 치르는 구조이기 때문이다.
플랫폼의 편의가 사용자의 방법론을 침식하는 것,
이것이 이 모델에 대한 가장 근본적인 비판이다.

다만 이 글의 결론은 "Amplify를 쓰지 말라"가 아니다.
플랫폼 제약은 주어진 조건이고,
그 제약 아래에서도 TBD를 지키는 운용 방법이 존재한다.

## 전략: main의 한 시점을 그대로 부어준다

### 핵심 아이디어: 브랜치의 격하

원칙은 하나다.
**사람이 관리하는 배포 브랜치를 두지 않고,
`main`의 검증된 커밋 SHA를 배포 대상 브랜치에 기계적으로 복사한다.**

Amplify가 브랜치를 요구하는 것을 막을 수는 없다.
그렇다면 그 브랜치의 지위를 바꾸면 된다.
`production`을 사람이 머지하고 관리하는 "브랜치"가 아니라,
기계만 움직이는 "포인터"로 격하시키는 것이다.
포인터가 된 배포 브랜치는 항상 `main` 히스토리 위의 어느 한 커밋을 가리킬 뿐,
독자적인 커밋을 단 하나도 갖지 않는다.
이렇게 하면 Git 그래프 관점에서 저장소는 여전히 트렁크 하나짜리다.
브랜치가 존재하되 쪼개짐은 존재하지 않는 상태를 만드는 것이 이 전략의 요체다.

### 네 가지 운용 원칙

1. **개발자가 보는 브랜치는 `main` 하나다.**
   `production` 브랜치는 존재하더라도
   사람이 절대 직접 조작하지 않는 배포 전용 포인터로 취급한다.
   체크아웃할 일도, 머지할 일도, 열어 볼 일도 없다.
2. **배포 브랜치에는 머지 커밋이 생기지 않는다.**
   오직 `main`의 특정 커밋으로 fast-forward(또는 리셋)만 일어난다.
   따라서 배포 브랜치의 모든 커밋은 `main`에 존재하는 커밋과 동일하다.
3. **배포는 Git 이벤트가 아니라 파이프라인의 결정이다.**
   "어느 SHA를 내보낼 것인가"는 CI가 검증 결과를 근거로 정하고,
   Git 조작은 그 결정을 Amplify에 전달하는 전송 수단일 뿐이다.
4. **hotfix도 `main`에 먼저 넣고 그 SHA를 부어준다.**
   트렁크를 우회하는 경로는 어떤 예외 상황에서도 열지 않는다.
   예외를 하나 허용하는 순간 이 전략 전체가 무너진다.

## 구현

### 강제 동기화 스크립트

배포 스크립트는 머지 대신 강제 동기화를 쓴다.

```bash
# main의 검증된 커밋을 production 포인터에 그대로 복사한다.
# 머지 커밋도, 충돌도, 새로운 커밋도 생기지 않는다.
git push origin "${VERIFIED_SHA}:refs/heads/production" --force
```

`--force`가 불편하게 느껴질 수 있다.
그러나 여기서의 강제 푸시는 사람의 작업을 덮어쓰는 위험한 조작이 아니다.
배포 브랜치에는 사람의 커밋이 존재하지 않으므로 덮어써서 잃을 것이 없다.
그리고 `--force`는 선택이 아니라 필수다.
롤백은 포인터를 과거 커밋으로 되돌리는, 즉 fast-forward가 아닌 이동이므로
강제 푸시 없이는 아예 성립하지 않는다.
전진과 후진을 같은 명령으로 다루려면 처음부터 강제 푸시로 통일하는 것이 맞다.

### GitHub Actions 워크플로

GitHub Actions로 감싸면 다음과 같다.

```yaml
name: promote
on:
  workflow_dispatch:
    inputs:
      sha:
        description: "배포할 main 커밋 SHA"
        required: true

jobs:
  promote:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Verify SHA is on main
        run: git merge-base --is-ancestor "${{ inputs.sha }}" origin/main
      - name: Move production pointer
        run: git push origin "${{ inputs.sha }}:refs/heads/production" --force
```

`merge-base --is-ancestor` 검증이 핵심이다.
`main`에 존재하지 않는 커밋은 절대 프로덕션 포인터가 될 수 없도록 강제한다.
이로써 "프로덕션에 있는 코드 = `main`의 어느 한 시점"이라는 불변식이 지켜진다.
누군가 실수로 기능 브랜치의 SHA를 넣어도 워크플로가 그 자리에서 실패한다.
사람의 규율이 아니라 파이프라인의 검증이 불변식을 지키는 것이 중요하다.
규율은 무너지지만 검증은 무너지지 않는다.

여기서는 사람이 SHA를 입력하는 `workflow_dispatch`를 예로 들었지만,
"CI 통과 시 자동으로 스테이징에 부어주기"처럼
트리거를 자동화하는 것도 같은 구조 위에서 자연스럽게 확장된다.

### 대안: Amplify API 직접 호출

Git 조작조차 없애고 싶다면 Amplify의 `start-job` API를
특정 커밋에 대해 호출하는 방법도 있다.

```bash
aws amplify start-job \
  --app-id "${APP_ID}" \
  --branch-name production \
  --job-type RELEASE \
  --commit-id "${VERIFIED_SHA}"
```

이 방식은 원격 저장소의 브랜치 포인터를 움직이지 않고
Amplify에게 직접 "이 커밋을 빌드해서 이 환경에 올려라"고 지시한다.
Git 히스토리를 완전히 깨끗하게 유지할 수 있다는 장점이 있지만,
Amplify 콘솔에 연결된 브랜치 설정과 실제 배포 상태가 어긋나 보일 수 있어
팀이 배포 상태를 어디서 확인하는지에 대한 합의가 필요하다.

### 스테이징 환경도 같은 방식으로

이 전략은 프로덕션에만 해당하는 것이 아니다.
스테이징 환경이 필요하다면 `staging` 브랜치도 같은 방식의 포인터로 운용한다.

```text
main:        A --- B --- C --- D --- E
staging:                            ^ (E를 가리킴)
production:              ^ (C를 가리킴)
```

두 포인터는 모두 `main` 히스토리 위의 서로 다른 시점을 가리킬 뿐이다.
스테이징이 프로덕션보다 앞선 커밋을 가리키는 것이 일상적인 상태이고,
프로덕션 배포는 `production` 포인터를 `staging`이 가리키던 커밋으로
옮기는 것으로 표현된다.
브랜치 간 머지는 어디에도 등장하지 않는다.

### 배포 브랜치 보호 설정

"사람이 직접 조작하지 않는다"는 원칙도 규율이 아니라 설정으로 강제한다.

- `production`, `staging` 브랜치에 대한 푸시 권한을
  배포 파이프라인의 봇 계정(또는 GitHub App)에만 부여한다.
- GitHub의 브랜치 보호 규칙 또는 ruleset으로
  일반 개발자의 직접 푸시를 차단한다.
- PR의 대상(base) 브랜치가 배포 브랜치로 지정되는 것도 차단한다.
  배포 브랜치로 향하는 PR 자체가 이 전략의 위반 신호다.

## 운영 시나리오

전략이 실제 상황에서 어떻게 작동하는지 대표적인 장면별로 확인한다.

### 일상 배포

1. 기능 브랜치(단명 브랜치)에서 작업하고 PR로 `main`에 머지한다.
2. CI가 `main`의 새 커밋을 검증한다.
3. 검증된 SHA를 스테이징 포인터에 부어준다(자동화 권장).
4. 스테이징에서 확인이 끝나면 같은 SHA를 프로덕션 포인터에 부어준다.

개발자의 Git 사용은 1번에서 끝난다.
2번부터는 전부 파이프라인의 일이다.

### 롤백

직전에 배포한 SHA가 문제라면, 이전에 배포했던 SHA로 같은 명령을 다시 실행한다.

```bash
git push origin "${PREVIOUS_GOOD_SHA}:refs/heads/production" --force
```

revert 커밋도, 강제 되감기 협의도, 히스토리 정리도 필요 없다.
배포 이력은 파이프라인 로그에 있으므로
"이전에 배포했던 SHA"를 찾는 것도 Git이 아니라 파이프라인에서 한다.
다만 Amplify가 재빌드를 하므로 롤백이 순간적이지는 않다는 한계는 남는다.
이것은 전략의 한계가 아니라 플랫폼의 한계다.

### 장애 상황의 hotfix

1. 수정을 기능 브랜치에서 만들어 PR로 `main`에 머지한다.
   급하면 리뷰를 사후로 미루더라도 경로는 반드시 `main`을 거친다.
2. CI 통과를 확인하고 그 SHA를 프로덕션 포인터에 바로 부어준다.
   스테이징을 건너뛸지는 팀의 판단이지만, 건너뛰더라도
   "main에 있는 커밋"이라는 불변식은 유지된다.

프로덕션에만 존재하는 코드는 어떤 상황에서도 만들어지지 않는다.
따라서 역머지라는 작업 자체가 존재하지 않고, 잊을 일도 없다.

### PR 프리뷰는 예외가 아니다

Amplify의 PR 프리뷰 기능(기능 브랜치마다 임시 환경 생성)은
이 전략과 충돌하지 않는다.
프리뷰가 연결되는 기능 브랜치는 PR 머지와 함께 사라지는 단명 브랜치이고,
단명 브랜치는 TBD가 트렁크 외에 허용하는 유일한 브랜치 형태다.
문제가 되는 것은 장수하는 환경 브랜치이지 브랜치라는 개념 자체가 아니다.

## 이 전략이 지키는 것과 못 지키는 것

### 지키는 것

- 팀의 브랜치 전략은 TBD 그대로 유지된다.
  사람이 다루는 공유 브랜치는 `main` 하나다.
- `main` 밖의 코드가 프로덕션에 나가는 경로가 없다.
  파이프라인의 `merge-base` 검증이 이를 기계적으로 보장한다.
- 롤백은 이전 SHA로 같은 명령을 다시 실행하는 것이다. Git 수술이 필요 없다.
- 배포 이력은 파이프라인 로그에 남고, Git 히스토리는 코드의 역사만 담는다.
- 별도 hotfix 브랜치 운영과 역머지 관리가 사라진다.
- 환경이 늘어나도(예: QA 환경 추가) 포인터 하나가 늘어날 뿐,
  머지 경로의 조합이 늘어나지 않는다.

### 못 지키는 것

한계는 정직하게 적어야 한다.
이 방식은 promote의 "의미"는 복원하지만 "산출물"은 복원하지 못한다.
Amplify는 여전히 포인터가 움직일 때마다 다시 빌드하므로,
"한 번 빌드하고 여러 번 배포한다(build once, deploy many)"는
지속적 전달(Continuous Delivery)의 권고는 끝내 달성되지 않는다.

이것이 실제로 의미하는 바를 구체적으로 적으면 다음과 같다.

- 스테이징에서 검증한 바이너리와 프로덕션 바이너리는 다른 빌드다.
  같은 SHA라는 보장이 최선이고, 같은 바이너리라는 보장은 불가능하다.
  의존성 잠금이 느슨하거나 빌드가 비결정적이면 그 틈으로 차이가 스며든다.
- 롤백에도 빌드 시간이 소요된다. 장애 복구 시간의 하한이 빌드 시간이 된다.
- 브랜치별 환경 변수 설정이 콘솔에 흩어져 있어,
  포인터 이동만으로는 환경 구성의 차이까지 옮겨지지 않는다.

이 한계들이 팀에 수용 불가능한 수준이라면
답은 운용 전략이 아니라 플랫폼 교체다.
운용으로 메울 수 있는 것은 모델의 틈이지 모델의 부재가 아니다.

## 맺으며

배포 모델이 브랜치 전략을 좌우하게 두면 도구와 방법론의 주종이 뒤집힌다.
브랜치 전략은 팀이 코드를 통합하는 방식에 대한 결정이지,
호스팅 서비스의 API 제약에 맞추는 타협이어서는 안 된다.

Amplify처럼 브랜치를 요구하는 플랫폼에서 TBD를 지키는 열쇠는,
플랫폼이 요구하는 브랜치를 사람이 "관리"하는 대상에서 제외하는 것이다.
배포 브랜치를 기계만 움직이는 포인터로 격하시키고
`main`의 한 시점을 그대로 부어주는 순간,
플랫폼 제약은 남지만 방법론의 훼손은 사라진다.
그리고 그 격하는 팀의 다짐이 아니라
파이프라인의 검증과 브랜치 보호 설정으로 강제되어야 한다.
규율은 무너지지만 설정은 무너지지 않기 때문이다.
브랜치를 관리하기 시작하면 지는 게임이다.
