# AWS Emulator는 AWS가 직접 만든 로컬 AWS API 에뮬레이터로, 서비스별 충실도 점수를 공개하고 AI 에이전트가 계속 고친다

<https://github.com/aws/aws-emulator>

HN 토론: <https://news.ycombinator.com/item?id=50456631> (899점, 250개 댓글)

GN 토론: <https://news.hada.io/topic?id=37001>

## 소개

AWS Emulator는 AWS API를 내 컴퓨터에서 흉내 내는 로컬 에뮬레이터이다.
AWS 계정 없이, 실제 AWS를 호출하지 않고 개발 머신이나 개발 서버나 CI에서 소프트웨어를
시험하는 용도이다.
요청은 AWS가 아니라 에뮬레이터로 가고, 만들어지는 것도 실제 리소스가 아니라 에뮬레이트된
리소스이다.
추가 서비스 요금은 없고, AWS에 배포할 때의 리소스 요금만 낸다.[^what-is]
저장소는 AWS가 직접 운영하는 `aws/aws-emulator`이고 Rust로 쓰였다.
2026년 9월 11일에 만들어졌고, 이 문서가 읽은 2026년 11월 12일에는 별 3,944개와
포크 100개였으며 마지막 푸시는 11월 11일이었다.
라이선스는 CC0 1.0이고, `vendor/` 아래의 프레임워크 코드만 Apache License 2.0이다.

에뮬레이터는 AWS API 엔드포인트를 제공하는 로컬 프로그램이고 그래픽 인터페이스는 없다.
실행한 뒤 환경 변수로 AWS CLI나 SDK의 엔드포인트를 에뮬레이터로 돌리면 코드를 바꾸지
않고 쓸 수 있다.
세 가지 방식이 있다.
첫째는 서버 모드이다.
Linux에서는 RPM이나 Debian 패키지로 설치해 `aws-emulator`를 실행하고,
Windows와 macOS에서는 짧은 Dockerfile로 만든 컨테이너에서 실행한다.
기본은 `127.0.0.1:9297`의 자체 서명 인증서 HTTPS이다.
둘째는 임베디드 모드이다.
Rust 테스트에서 에뮬레이터를 개발 의존성으로 추가하면 테스트마다 격리된 인스턴스가
프로세스 안에서 돌고, 엔드포인트 URL이나 인증서나 환경 변수가 필요 없다.
셋째는 AI 코딩 에이전트용 스킬이다.
`aws agent-toolkit add-skill --skill-name aws-emulator --region us-east-1`으로
`aws-emulator` 스킬을 설치하면 에이전트가 에뮬레이터를 설치하고 띄우고 연결한다.
이 명령은 AWS CLI 2.35.0 이상이 필요하다.

용도는 로컬 테스트, 계정 없는 CI/CD 통합 테스트, AI 코딩 에이전트와의 로컬 프로토타이핑이
다.[^what-is]
빌드와 테스트용이고 운영 워크로드나 보안 시험에는 쓰지 말라고 README가 먼저 밝힌다.

### 저장소의 구성

서비스마다 crate가 하나씩 있다.
`services/service-<이름>/` 안에 서비스의 Smithy 모델(`smithy-model/`)이 있고,
그 모델이 와이어 프로토콜을 이끈다.
`build.rs`가 모델에서 서비스 선언을 생성하고, `src/ops/` 아래에는 연산 하나당 파일
하나가 있다.
`core/router/`는 모든 서비스를 한 엔드포인트에 붙이는 바이너리이고,
`core/embedded/`는 프로세스 안 실행의 facade이다.
`vendor/`의 프레임워크 crate는 수정하지 않으며 업데이트 때 교체된다.
`issues/`에는 충실도 문제가 추적되는데, 아직 안 되는 API와 동작은
`issues/things-that-do-not-work/`에, 고쳐진 것은 `issues/things-that-now-work/`로
옮겨진다.
이 문서가 읽은 시점에 `services/` 폴더에는 438개 항목이 있었고, 대부분이 서비스별
crate이다.

### 한계

문서는 한계를 직접 적는다.[^what-is]
IAM 정책과 리소스 기반 정책을 AWS처럼 평가하지 않는다.
리전과 계정을 하나만 쓰는 것을 전제로 하고, 임의의 리전과 계정 ID를 받아 주지만
리소스를 리전과 계정별로 나누어 보관하지 않는다.
충실도는 서비스와 기능마다 다르다.
동작은 미국 서부(오레곤, us-west-2)에서만 AWS와 대조하고, 글로벌 서비스만
미국 동부(버지니아 북부, us-east-1)에서 대조한다.
리소스는 모두 메모리에 있고 에뮬레이터를 멈추면 사라진다.
장시간 사용이나 부하 시험은 시험해 보지 않았고, 테스트 때만 띄우고 끝나면 멈추거나
`--idle-timeout`으로 스스로 멈추게 하라고 한다.[^what-is]

소스에서 빌드하려면 Rust 툴체인과 C 컴파일러와 `target/`용 100GB 이상의 여유 디스크가
필요하다.
서비스마다 crate가 있어서 전체 디버그 빌드가 크기 때문이다.
임베디드 모드는 에뮬레이터를 테스트 바이너리에 컴파일해 넣으므로 첫 `cargo test`가 같은
비용을 낸다.
README는 `CARGO_TARGET_DIR`을 프로젝트 사이에 공유하고, CI에서 `target/`을 캐시하거나
sccache를 쓰고, 에뮬레이터를 릴리스 커밋에 고정하라고 권한다.
PR은 받지 않고 버그와 충실도 차이는 Issues로만 받는다.

## 만든 방식

이 에뮬레이터는 AWS의 Sr. Principal Engineer인 Matthew Goldberg가 2026년 11월 11일
공식 블로그에 쓴 글에서 100% 자율 AI 에이전트가 썼다고 소개된다.
글은 팀이 코드를 쓰지도 검토하지도 않았다고 밝힌다.[^about-amazon]
출발은 주말 실험이었다.
Anthropic 연구진이 에이전트로 C 컴파일러를 만든 사례를 보고, 잘 정의된 명세와
참조 구현이 있으면 에이전트가 명세를 충실히 구현할 수 있다고 가설을 세웠다고 한다.
AWS에는 둘 다 있다.
AWS API 모델이 명세이고 실제 AWS 클라우드가 참조 구현이다.
가설을 시험한 프롬프트는 세 줄이었다.
AWS CLI 기반 테스트를 쓰고, 그 테스트가 실제 AWS에서 통과할 때까지 고치고,
같은 테스트가 통과하는 메모리 구현을 만들라는 것이었다.
Kiro가 15분 만에 SQS의 쓸 만한 첫 버전을 내놓았고,
주말 동안 나머지 AWS를 만들었으며 팀은 월요일부터 자기 소프트웨어를 시험하는 데
썼다고 한다.[^about-amazon]

이것을 제품으로 만드는 데는 주말 이상이 걸렸고 가드레일 구축이 그 일이었다고 글은
말한다.
구조는 세 에이전트 팀이다.
첫째 팀은 충실도 테스트를 관리한다.
공개된 AWS API 모델에서 실제 AWS 시나리오(SQS라면 큐를 만들고 메시지를 보내고 받고
확인하고 큐를 지우는 흐름)를 만들고, 제출 전에 실제 AWS에서 검증한다.
테스트는 전체 AWS에 걸쳐 수만 개이고 AWS를 다시 부르지 않고도 되풀이해 돌릴 수 있다.
둘째 팀은 테스트를 재생해 에뮬레이터가 어긋나는 곳을 찾고 이슈를 올리며,
같은 뿌리의 실패를 묶도록 지시받는다.
저장소가 처음 만들어질 때는 438개의 AWS API 모델을 받지만 아무것도 하지 않는 빈 웹
서버였다.
셋째 팀은 이슈 하나씩을 맡아 원인을 찾고 고친 뒤 병합 게이트를 통과시킨다.
게이트는 컴파일뿐 아니라 코딩 표준을 검토하는 에이전트, 보안을 확인하는 에이전트,
충실도가 후퇴하지 않았는지 확인하는 단계를 포함한다.
하루에 수천 개의 이슈가 고쳐지고 수백 개의 에이전트가 동시에 일한다고 한다.[^about-amazon]

배포 경로도 밝힌다.
병합된 변경은 AWS Developer Tools로 만든 릴리스 파이프라인을 흐르고,
에이전트의 주 저장소는 AWS CodeCommit이며, 릴리스 과정의 끝에서야 GitHub에
코드를 공개한다.
GitHub의 `issues/` 폴더가 에이전트가 올린 이슈와 백로그이다.
이전 버전에서 에이전트가 AWS Lambda 함수를 지원하려고 자체 Python 인터프리터를
만들었고, 지금은 기존 라이브러리를 쓰라는 지침을 준다는 일화도 있다.
이 이력에서 얻은 통찰이 CC0로 공개한 주된 동기라고 한다.[^about-amazon]
이 문서는 이 블로그 글을 AWS 쪽 설명으로 읽었고, 글에 적힌 수치(수만 개의 테스트,
하루 수천 개의 이슈)는 직접 확인하지 못했다.

## 신뢰의 범위를 정하는 방식

### 충실도 점수와 충실도 테스트

README는 서비스가 AWS와 얼마나 같은지를 릴리스마다 공개하는 충실도 점수로 보라고
안내한다.
점수는 서비스의 충실도 테스트 중 통과한 수를 나타내고, 테스트는 별도 저장소
`aws-emulator-evaluation-suite`의 `manifest.jsonl`에 있다.[^check-project]
내 프로젝트에 쓸 수 있는지 확인하는 순서도 문서에 있다.
워크플로가 부르는 AWS 연산을 나열하고, 그 연산의 충실도 테스트를 manifest에서 찾고,
쓰는 릴리스의 서비스별 점수를 확인하고, 어떤 테스트도 덮지 않는 연산은 에뮬레이터와
AWS 양쪽에 직접 테스트를 돌려 비교한다.[^check-project]
`aws-emulator` 스킬을 쓰면 에이전트가 이 과정을 대신하고, AWS와 다른 동작을 찾으면
이슈 초안을 만들어 보여 준 뒤에 올린다.[^check-project]
문서는 충실도 테스트가 아직 모든 동작을 덮지 않고, 테스트가 덮지 않는 동작은 이미
맞을 수도 있지만 확인된 것은 아니라고 적는다.[^check-project]

이 문서는 릴리스마다 붙는 `scores.json.gz` 첨부 파일은 내려받지 않았다.
그래서 서비스별 실제 점수는 확인하지 못했다.

### 릴리스 속도

에뮬레이터는 AI 에이전트가 AWS 변화에 맞춰 계속 갱신하고, 하루에 여러 번 업데이트가
나간다고 문서가 밝힌다.[^what-is]
릴리스 기록도 이 속도를 보여 준다.
v1.0.292가 2026년 11월 10일 12:38(UTC), v1.0.293이 같은 날 14:02, v1.0.322가 11월 11일
00:32에 나왔고, 가장 오래된 목록 항목인 v1.0.250은 11월 7일이다.[^releases]
릴리스 본문은 `fix:`로 시작하는 줄의 나열이고, 한 릴리스에 수십 개가 들어가기도 한다.
항목 이름에는 `-stub`으로 끝나는 것(`bedrock-agent-deleteflow-stub` 등)과
`glue-startjobrun-is-an-unimplemented-501-scaffold` 같은 것이 섞여 있다.[^releases]
뼈대만 있고 구현되지 않아 501을 돌려주던 연산이 여전히 많이 남아 있다는 뜻으로 읽힌다.

### 에이전트가 따르는 저장소 규칙

`AGENTS.md`는 에뮬레이터를 고치는 사람과 에이전트가 따를 규칙을 적는다.
서비스 crate마다 고칠 파일이 정해져 있다.
연산 구현은 `ops/<연산>.rs`, 라우팅과 거절 문구는 `service.rs`, 서비스의 상태는
`state.rs`이다.
모델의 `@auth`와 `@optionalAuth` 특성은 있는 그대로 두어야 하고, `auth_schemes()`가
빈 목록을 돌려주게 하면 안 된다.
연산이 서명 없이 열리는 것은 모델이 그렇게 정의한 경우뿐이다.[^agents]
에뮬레이터 자신의 루트 자격 증명은 다른 서비스 호출에 서명하는 데만 쓰고 응답이나 로그에
넣지 않는다.
호출자에게 돌려주는 자격 증명은 자격 증명 저장소에서 만들고 파일이나 로그에 남기지
않는다.
미리 서명된 URL은 컨텍스트의 서명기로만 만들고, AWS SDK로 서명하면 실제 서비스로
가거나 검증에 실패하므로 하지 않는다.
요청 서명은 에뮬레이터가 한 곳에서 검증하고 서비스는 서명을 직접 확인하지 않는다.[^agents]
`vendor/`는 에이전트가 바꿀 수 없는 프레임워크로 표시되어 있다.[^agents]

## 보안과 텔레메트리

### 기본값은 내 컴퓨터 안에서만 열린다

에뮬레이터는 `127.0.0.1:9297`에서만 듣는다.
시작할 때마다 새 액세스 키와 비밀 키를 만들어 `~/.aws/emulator/<포트>/emulator_credentials`
에 쓰고, 이 파일은 사용자만 읽을 수 있다.
로컬 프로세스로 돌 때는 기본적으로 그 실행의 키로 서명한 요청만 받고,
정상 종료하면 자기가 쓴 파일을 지운다.[^security]
`--auth off`로 시작하면 서명 여부와 상관없이 모든 요청을 받는다.
사용자가 지켜야 할 일도 적혀 있다.
에뮬레이터를 비공개로 두고, 진짜 AWS 자격 증명과 진짜 데이터를 넣지 않고,
믿을 수 있는 코드만 실행한다.
함수 코드를 실행할 때 머신으로부터 격리하지 않고 사용자 권한으로 돌린다.[^security]
테스트가 에뮬레이터에 닿는지도 확인해야 하는데, `AWS_ENDPOINT_URL`이 없으면 코드가
실제 AWS를 호출한다고 문서가 경고한다.[^security]

### 텔레메트리는 기본적으로 켜져 있다

텔레메트리는 기본으로 켜져 있고 AWS가 소유한 엔드포인트로 TLS로 보내며 최대 90일
보관한다.[^telemetry]
설치와 실행마다 무작위 ID, 운영체제와 CPU, 요청을 보낸 SDK와 버전, 리전, 설치 방법,
단독인지 임베디드인지, 컨테이너나 CI에서 도는지, 에뮬레이터를 모는 AI 코딩 도구가
무엇인지가 포함된다.
연산별 호출 횟수와 결과(성공, 클라이언트 오류, 서버 오류, 아직 구현되지 않음 501),
응답 시간의 최소와 최대와 합, 최대 메모리 사용 범위, 시작 시간, 충돌의 종류도 보낸다.[^telemetry]
요청과 응답의 내용, 리소스 이름과 ARN, 환경 변수 값, 자격 증명, 코드는 수집하지
않는다고 한다.[^telemetry]
끄는 방법은 네 가지이다.
`--telemetry off`(약칭 `-t`), 환경 변수 `EMULATOR_TELEMETRY=off`, 설정 파일 `config.toml`의
`[telemetry] enabled = false`, 임베디드 API의 `Telemetry::Off`이다.
환경 변수는 on, true, 1이 아닌 값을 모두 끄기로 해석하고 시작 안내에 경고를 보인다.
이 에뮬레이터를 포함한 도구를 만들어 배포한다면 사용자에게 텔레메트리를 알리고 끌 방법을
주거나 끈 채로 배포하라고 README가 요구한다.

## 분석

### 이 프로젝트의 핵심은 AWS와 같다고 말하는 대신 얼마나 같은지를 재서 공개하는 것이다

가장 강하게 말하면 AWS Emulator는 모든 AWS를 완벽히 흉내 낸다고 주장하지 않는 대신
서비스별로 몇 개의 충실도 테스트를 통과했는지를 릴리스마다 공개해 신뢰의 범위를 사용자가
직접 정하게 하는 도구이다.
문서의 구조가 이를 뒷받침한다.
한계 절이 IAM, 리전, 계정, 부하, 영속성을 먼저 나열하고,
프로젝트가 쓸 수 있는지 확인하는 절차는 연산을 나열해 테스트와 점수에 대응시키는 것으로
되어 있다.
점수의 분모가 충실도 테스트이므로 점수의 의미는 테스트가 얼마나 넓은지에 달려 있다.
문서가 테스트가 모든 동작을 덮지 않았다고 직접 인정하는 것은 이 점을 보여 준다.

### 서비스 수백 개를 에이전트로 유지하는 구조를 저장소 규칙이 지탱한다

서비스가 수백 개이고 하루에도 여러 번 릴리스되는 규모는 사람이 손으로 고치는 방식으로
유지하기 어렵다.
저장소는 이를 Smithy 모델에서 선언을 생성하고, 연산 하나를 파일 하나로 쪼개고,
프레임워크를 에이전트가 바꿀 수 없는 `vendor/`에 두고, 서명과 자격 증명 처리를 한 곳에서
하게 하는 규칙으로 지탱한다.
에이전트가 서비스마다 같은 실수를 되풀이하지 않도록 고치는 위치와 금지 사항을 `AGENTS.md`가
정한다.
이 문서는 이것이 규칙 덕분에 품질이 유지되는지는 확인하지 못했다.

### 사람이 코드를 읽지 않는 대신 외부 기준과 게이트가 검토를 맡는다

블로그의 구조는 사람의 코드 검토를 세 가지로 대체한다.
실제 AWS라는 외부 기준(오라클), 되풀이해 돌릴 수 있는 충실도 테스트,
컴파일과 코딩 표준과 보안과 충실도 후퇴를 막는 병합 게이트이다.[^about-amazon]
글이 이 게이트를 가장 공들여 다듬는 부분이라고 하는 것도 같은 뜻이다.
이 구조에서 신뢰의 근거는 코드가 읽혔다는 사실이 아니라 기준이 바깥에 있고 어긋남이
수치로 드러난다는 사실이다.
같은 저장소의 다른 문서가 다룬 에이전트 시대의 검토 문제(요약보다 증거,
초록색이 증명하는 것)를 이 도구가 제품 구조로 옮긴 사례로 읽힌다.
이 연결은 이 문서의 해석이다.

### 릴리스 목록은 구현 현황의 지도이기도 하다

릴리스의 `fix:` 항목에는 stub이나 미구현 scaffold를 구현으로 바꾸는 것이 많이 보인다.
동작이 아니라 이름이 있는 연산이 먼저 만들어지고 나중에 채워지는 순서로 보인다.
이것은 이 문서의 읽기이고, 한 릴리스의 항목 이름만으로 전체 비율을 말할 수는 없다.

## 비평

### 에뮬레이터에서 통과한 테스트가 안전하다는 뜻이 아니라고 문서가 반복한다

문서는 IAM 정책, 리소스 기반 정책, KMS 키 정책, 계정 간 접근을 시험하는 데 쓰지 말라고
한다.
일부 서비스가 에뮬레이터 안에서 만든 IAM 사용자와 역할의 정책을 평가하지만 AWS와 같지
않고,
자기 키로 서명한 요청은 절대 거부하지 않으며,
AWS가 거부할 요청이 에뮬레이터에서는 성공하고 AWS가 허용할 요청이 실패할 수도 있다고
한다.[^security]
문제는 이것이 권한 때문에 실패해야 할 테스트가 에뮬레이터에서는 통과하는 방향으로
틀린다는 점이다.
권한 설정이 틀린 채로 CI가 초록이 되는 일을 막을 장치는 도구 안에 없고,
실제 AWS에서의 별도 검증이라는 사용자의 절차에 맡겨져 있다.

### 텔레메트리가 기본적으로 켜져 있어서 CI와 에이전트 환경에서도 보낸다

수집 항목은 범위가 좁고 값을 고정 목록과 대조한다고 문서가 밝히지만,
컨테이너나 CI에서 도는지, 어떤 AI 코딩 도구가 모는지, 연산별 호출 횟수가 포함된다.[^telemetry]
꺼야만 보내지 않는 기본값이어서 CI 이미지를 만드는 사람은 `EMULATOR_TELEMETRY=off`를
이미지에 넣어 두어야 한다.
이 문서는 실제로 어떤 패킷이 나가는지는 확인하지 않았고 문서의 설명을 옮긴 것이다.

### 변경 속도와 소스 빌드 비용이 안정성 기대와 어긋난다

하루에 여러 번 릴리스되는 속도는 충실도 개선이 빠르다는 뜻이지만,
같은 연산의 동작이 릴리스마다 바뀐다는 뜻이기도 하다.
README가 에뮬레이터를 릴리스 커밋에 고정하라고 권하는 것도 이 때문으로 읽힌다.
임베디드 모드는 테스트 바이너리에 서비스 crate 수백 개를 컴파일해 넣으므로 첫 빌드와
`target/`이 소스 빌드와 같은 규모라고 README가 직접 적는다.
Rust 외의 언어는 서버 모드를 써야 하고, Linux 외에서는 Docker를 거친다.
PR을 받지 않으므로 사용자가 고칠 수 있는 길은 이슈를 올리는 것뿐이다.

### 검증 기준이 한 리전과 한 조직의 테스트에 한정된다

동작은 us-west-2에서만 AWS와 대조한다고 문서가 밝히고,
충실도 테스트도 같은 조직이 관리하는 저장소에 있다.
외부가 다시 재현한 결과는 이 문서가 읽은 자료에 없다.
리전별로 서비스와 기능의 제공 범위가 다른 점도 반영되지 않는다.[^what-is]

## 인사이트

### 에이전트가 만든 도구는 외부 기준이 있는지로 믿는다

이 도구에서 얻을 가장 일반적인 교훈은 코드가 읽혔는지보다 기준이 어디에 있는지를 묻는
것이다.
이 도구의 기준은 실제 AWS이고, 테스트는 실제 AWS에서 검증된 뒤에만 제출되며,
되풀이 재생할 수 있고, 어긋나면 이슈가 되고, 병합 게이트가 후퇴를 막는다.[^about-amazon]
이 문서의 제안은 에이전트가 만든 도구를 도입할 때 이 네 가지가 있는지를 묻는 것이다.
외부 기준이 있는가, 그 기준의 결과가 공개되는가, 같은 결과가 재현되는가, 후퇴를
막는 장치가 있는가이다.
이 질문은 이 문서의 제안이다.

### 용도를 기능 시험과 개발 속도로 한정한다

이 도구가 약속하는 것과 약속하지 않는 것이 문서에서 갈라진다.
계정 없이 빠르게 돌고 에이전트 프로토타이핑에 맞는다는 것은 약속이다.
권한과 보안의 정합성은 약속하지 않는다.
이 문서의 제안은 CI에서 에뮬레이터 단계를 기능 시험으로만 두고,
권한과 정책을 다루는 시험은 실제 AWS 계정의 별도 단계로 분리하는 것이다.
이 구분은 이 문서의 제안이다.

### 도입 전에 내 프로젝트의 연산 목록을 점수와 맞춰 본다

문서가 안내한 절차를 그대로 쓸 수 있다.
프로젝트가 호출하는 AWS 연산 목록을 만들고, manifest에서 그 연산의 테스트가 있는지
찾고, 쓰는 릴리스의 서비스별 점수를 본다.
테스트가 없는 연산은 에뮬레이터와 실제 AWS에 같은 시험을 돌려 비교하고,
다르면 이슈로 올린다.[^check-project]
이 문서의 제안은 이 목록을 저장소에 남기고 릴리스를 올릴 때 다시 맞춰 보는 것이다.

### 실수로 실제 AWS를 호출하지 않게 한다

문서가 경고하듯 엔드포인트 환경 변수가 빠지면 코드가 실제 AWS로 간다.[^security]
이 문서의 제안은 테스트 시작 전에 실제 자격 증명 변수를 모두 지우고,
엔드포인트 변수가 설정되었는지를 테스트 시작 시점에 검사해 실패하게 하는 것이다.
에뮬레이터는 시작 때마다 새 키를 만들고 그 실행의 키만 받으므로,
다른 키가 들어가면 에뮬레이터는 요청을 거부한다.[^security]

### 서비스 수백 개를 에이전트가 유지하는 방식에서 배울 수 있다

규모가 큰 호환 계층을 에이전트로 유지하려는 팀은 이 저장소의 규칙을 참고할 수 있다.
모델에서 선언을 생성하고, 연산 하나를 파일 하나로 쪼개고, 프레임워크를 바꿀 수 없게 두고,
인증과 자격 증명 처리 규칙을 문서에 적고, 충실도를 테스트와 점수로 공개하는 것이다.
이 선택은 이 문서의 정리이다.

### 판단을 바꿀 관찰

서비스별 점수가 릴리스를 거치며 어떻게 움직이는지, stub과 501 scaffold가 줄어드는지,
IAM과 리전과 계정 분리 같은 지금의 한계가 문서의 한계 목록에서 빠지는지를 본다.
점수가 오르지 않고 같은 연산의 동작이 릴리스마다 흔들리면 이 도구는 아직 빠른 시제품이고,
점수가 꾸준히 오르며 동작이 안정되면 CI용으로 믿을 만하다는 뜻이다.
이 판단 기준은 이 문서의 제안이다.
