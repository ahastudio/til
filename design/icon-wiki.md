# Icon Wiki: 무료 아이콘·이모지 12만 개를 한곳에서 찾는 검색기

> Icon Wiki: Browse Icons

<https://iconwiki.aoo.kr/>

Show GN: [Icon Wiki - 무료 아이콘·이모지 12만 개를 한곳에서 검색하기](https://news.hada.io/topic?id=34408)

## 소개

2026년 9월 28일 GeekNews에 Show GN으로 올라온 개인 프로젝트다.
작성자는 혼자 서비스를 만들다 보니 아이콘을 찾을 일이 많았고, 그때마다 구글에서 검색해 쓰다가 무료로 공개된 아이콘 라이브러리가 생각보다 많다는 것을 알게 됐다고 한다.
여기저기 돌아다니지 않고 한곳에서, 그리고 한글로도 검색할 수 있으면 좋겠다는 생각에 만든 것이 Icon Wiki다.

서비스는 `iconwiki.aoo.kr`에서 무료로 쓸 수 있고, 코드는 GitHub의 `resoliwan/iconwiki` 저장소에 MIT 라이선스로 공개되어 있다.
개별 아이콘과 이모지에는 각 라이브러리의 원래 라이선스가 적용된다.
GitHub 저장소는 2026년 9월 20일 만들어졌다.
작성자는 LLM으로 작업할 때 사이트 주소를 알려 주고 원하는 아이콘을 찾아 달라고 하면 꽤 잘 찾아 준다는 사용 팁도 덧붙였다.

## 주요 기능

게시글과 README가 소개하는 기능은 다음과 같다.

- 이름, 키워드, 카테고리로 통합 검색
- 검색 결과 안에서 별도 입력란으로 범위 좁히기(예: `face`를 검색한 뒤 결과 필터에 `smile` 입력, `Tab`으로 두 입력란 이동)
- 라이브러리, 라이선스, 일치 유형, 피부색으로 필터링
- 여러 라이브러리의 스타일을 나란히 비교
- 각 아이콘의 원본 출처와 라이선스 확인
- 한글 등 여러 언어로 검색하기(예: `캥거루`)와 AI 연관 검색어 확장

한글 검색과 AI 확장은 내장 AI를 쓸 수 있는 데스크톱 Chrome에서만 지원되고, 다른 브라우저에서는 기본 검색만 된다.
저장소의 `smart-search.js`를 보면 이 기능은 브라우저에 `LanguageModel`(Chrome Prompt API)과 `Translator`(Chrome Translator API)가 있는지 확인해 쓰며, 모델이 “다운로드 가능” 상태면 진행률을 보여 주며 받는다.
곧 서버에 LLM을 두지 않고 사용자의 브라우저 안에서 번역과 검색어 확장을 처리한다.

로컬에서는 Python 내장 HTTP 서버로 정적 파일을 띄운다.

```bash
npm start       # python3 -m http.server 4174 --bind 127.0.0.1
npm run data    # 라이브러리별 빌드 스크립트로 아이콘 카탈로그 재생성
```

## 수록 라이브러리와 라이선스

README 기준으로 42개 라이브러리의 아이콘과 이모지 120,972개를 담는다.
이모지로는 Unicode Emoji, Noto Color Emoji, Noto Emoji, Microsoft Fluent Emoji 세 가지 스타일, Twemoji, 토스페이스(Tossface), Blobmoji, OpenMoji, Mozilla FxEmojis가 있다.
아이콘으로는 Google Material Symbols, Pictogrammers Material Design Icons, Tabler, Lucide, Phosphor, Heroicons, Font Awesome Free, Bootstrap Icons, Microsoft Fluent UI System Icons, IBM Carbon, Ant Design, Octicons, Radix, Codicons, IconPark, Solar, Game Icons 등이 들어 있다.
가장 많은 항목은 IconPark(9,207개)와 Phosphor(9,072개), Solar(8,280개)이고, 가장 적은 것은 Maki(215개)와 Weather Icons(219개)다.

라이선스는 제각각이다.
MIT가 가장 많고, Apache-2.0(Material Symbols, Noto Color Emoji, IconPark 등), CC-BY-4.0(Twemoji, Font Awesome Free, Codicons, Solar 등), CC-BY-SA-4.0(OpenMoji), CC-BY-3.0(Game Icons), OFL-1.1(Noto Emoji, Weather Icons), CC0-1.0(Simple Icons, Maki), Unicode-3.0, 그리고 토스페이스의 자체 라이선스가 섞여 있다.
IconPark, MingCute, Carbon 등 열 개 라이브러리는 `@iconify-json` 패키지 버전을 고정해 로컬 SVG를 생성했다고 README에 적혀 있다.

## 분석

### 아이콘 검색의 진짜 문제는 이름이 아니라 라이선스다

아이콘 검색 서비스는 이미 많다.
GeekNews의 관련 글 목록만 봐도 Iconduck, Iconify, SVG Repo, Iconhunt, Icônes가 보인다.
Icon Wiki가 이들과 다른 점은 검색 결과마다 출처와 라이선스를 붙이고, 라이선스로 필터링하게 했다는 것이다.
이 선택이 서비스의 실제 가치를 정한다.

아이콘을 찾는 사람에게 가장 어려운 질문은 “이 모양이 있는가”가 아니라 “이것을 내 제품에 써도 되는가”다.
MIT나 CC0 아이콘은 거의 제약 없이 쓸 수 있지만, CC-BY는 출처 표기를 요구하고, CC-BY-SA는 파생물도 같은 라이선스로 공개하라고 요구하며, 토스페이스처럼 자체 라이선스를 가진 것은 조건을 따로 읽어야 한다.
여러 라이브러리를 한 화면에 섞어 보여 주면서 라이선스를 숨긴다면, 검색은 편해지지만 사용자는 모르고 조건을 어기게 된다.
라이선스를 첫 번째 필터로 둔 것은 이 서비스가 그 위험을 알고 있다는 뜻이다.

### 번역과 검색어 확장을 사용자 브라우저에 맡긴 구조

한글 검색은 이 서비스가 내세우는 차별점이지만, 구현 방식이 더 흥미롭다.
아이콘 이름과 태그는 대부분 영어인데, 한글 검색어를 서버에서 번역하려면 번역 API 비용이나 서버 쪽 모델이 필요하다.
Icon Wiki는 이것을 Chrome에 내장된 번역 API와 Prompt API로 해결해, 번역과 연관어 확장이 사용자의 브라우저 안에서 일어나게 했다.
정적 파일만 올려 두면 되는 서비스에 AI 기능을 비용 없이 붙인 셈이다.

이 구조는 개인이 만든 무료 서비스에 잘 맞는다.
서버 비용이 거의 들지 않으니 사용자가 늘어도 운영 부담이 늘지 않고, 검색어가 외부 서버로 가지 않으니 개인정보 부담도 적다.
대신 기능이 특정 브라우저와 기기에 묶인다.
Chrome 데스크톱에서만, 그리고 내장 모델을 내려받을 수 있는 기기에서만 한글 검색이 된다.

## 비평

### 핵심 차별점이 가장 좁은 환경에서만 동작한다

Icon Wiki가 기존 아이콘 검색기와 다르다고 내세우는 가장 큰 이유는 한글 검색이다.
그러나 그 기능은 내장 AI를 쓸 수 있는 데스크톱 Chrome에서만 된다.
모바일 브라우저, Safari, Firefox, 그리고 사양이 낮아 내장 모델을 받을 수 없는 기기에서는 영어 검색만 남는다.
한국어 사용자가 이 서비스를 고를 이유가 한글 검색이라면, 그 이유가 적용되는 사용자는 생각보다 적을 수 있다.

해결책은 어렵지 않다.
아이콘 이름에 대한 한글 동의어 사전을 미리 만들어 정적 데이터로 넣어 두면, 브라우저와 무관하게 기본적인 한글 검색이 된다.
브라우저 AI는 그 위에서 사전에 없는 검색어를 확장하는 보조 수단으로 두는 편이 기능의 신뢰성을 높인다.
지금 구조에서는 가장 중요한 기능이 가장 선택적인 기반 위에 있다.

### 숫자가 서로 맞지 않고, 첫 댓글은 장애 보고였다

GitHub 저장소 설명에는 “21개 라이브러리”라고 적혀 있고, README와 게시글에는 42개라고 적혀 있다.
아이콘 수 120,972개는 두 곳이 같지만, 라이브러리 수가 두 배 차이 난다.
라이브러리를 늘리는 동안 저장소 설명은 고치지 않은 것으로 보인다.
사소한 불일치지만, 라이선스 정확성을 핵심 가치로 내세우는 서비스라면 메타데이터의 정확성도 신뢰의 일부다.

게시글에 달린 유일한 댓글도 기능 소개가 아니라 장애 보고였다.
GN의 toida는 DB 조회가 안 되는 것 같다고 적었다.[^toida]
정적 파일로 동작하는 서비스라서 원인은 대용량 카탈로그 파일을 불러오는 과정이었을 가능성이 크지만, 공개 직후 사용자가 처음 만난 경험이 “안 된다”였다는 점은 기록해 둘 만하다.
Show GN에 올리는 순간이 가장 많은 사람이 처음 들어오는 순간이고, 그때의 첫인상이 대부분의 사용자에게는 마지막 인상이 된다.

## 인사이트

### 브라우저 내장 AI는 무료 개인 서비스의 경제학을 바꾼다

Icon Wiki의 구조가 보여주는 것은 한 서비스의 구현 선택을 넘어선다.
지금까지 개인이 만든 무료 서비스에 AI 기능을 붙이려면, API 비용을 감당하거나 사용량을 제한하거나 유료화를 고민해야 했다.
사용자가 늘수록 비용이 늘어서, 인기가 곧 운영 위기가 되는 구조였다.
브라우저에 내장된 모델은 이 비용을 사용자의 기기로 옮긴다.

이것은 웹이 이미 여러 번 겪은 변화다.
서버에서 렌더링하던 페이지가 JavaScript로 브라우저에서 렌더링되면서 서버 비용이 클라이언트로 옮겨 갔고, 그 덕분에 정적 호스팅만으로 복잡한 애플리케이션을 운영할 수 있게 됐다.
브라우저 AI는 같은 이동을 추론 비용에 적용한다.
정적 파일 몇 개와 무료 호스팅만으로 번역과 검색어 확장을 제공하는 Icon Wiki는 그 변화의 작은 사례다.

다만 이 경제학은 브라우저 벤더의 결정에 달려 있다.
어떤 모델이 어떤 기기에 들어가는지, API가 표준이 되는지는 Chrome이 정한다.
개인 개발자는 추론 비용을 공짜로 얻는 대신, 기능의 범위를 한 브라우저 벤더에 맡긴다.

### 아이콘 검색기의 다음 사용자는 사람이 아니라 코딩 에이전트다

작성자가 지나가듯 적은 팁, 곧 LLM에 사이트 주소를 알려 주고 아이콘을 찾아 달라고 하면 꽤 잘 찾는다는 말은 이 서비스의 미래 사용자를 가리킨다.
UI를 코딩 에이전트가 만드는 비중이 늘수록, 아이콘을 고르는 것도 에이전트의 일이 된다.
에이전트는 검색 화면을 보지 않고, 이름과 태그와 라이선스를 구조화된 데이터로 읽는다.

그렇다면 아이콘 검색기가 제공해야 할 것은 예쁜 격자 화면보다 기계가 읽기 좋은 카탈로그다.
아이콘마다 이름, 동의어, 카테고리, 라이선스, 출처 URL, SVG를 담은 정적 JSON이나 MCP 서버가 있으면, 에이전트는 “출처 표기가 필요 없는 라이선스 중에서 캥거루 아이콘”을 한 번에 찾을 수 있다.
Icon Wiki는 이미 라이선스와 출처를 구조화해 두었으므로, 그 데이터를 에이전트용 인터페이스로 여는 것은 작은 한 걸음이다.

그리고 에이전트에게 라이선스 정보는 사람에게보다 더 중요하다.
사람은 아이콘을 고를 때 라이선스를 한 번쯤 확인하지만, 에이전트는 시키지 않으면 확인하지 않는다.
라이선스를 기본 필터로 삼은 검색기가 에이전트의 표준 도구가 된다면, 에이전트가 만든 UI에 라이선스를 어긴 아이콘이 섞이는 일을 구조적으로 줄일 수 있다.
