## 소개

PhotoCraft는 ArtCraft 팀이 내놓은 Crafting Apps 가운데
Photoshop을 겨냥한 이미지 편집기다.
저장소 설명은 순수 Rust로 쓴
Adobe Photoshop의 오픈소스 클린룸(clean-room) 재구현이다.
제품군 전체와 첫 반응, 그리고 README가 내세운 기능 목록은
`design/artcraft-apps.md`가 이미 다뤘고,
ArtCraft 본체는 `design/artcraft.md`에 있다.
이 문서는 저장소를 직접 받아서 코드, 문서, 커밋 이력, 이슈를 읽고
PhotoCraft 하나를 더 깊게 본다.
앱을 빌드하거나 실행하지는 않았고, 테스트 코퍼스도 내려받아 돌려 보지 않았다.

저장소는 2026년 9월 30일에 만들어졌다.
2026년 10월 10일 GitHub API 기준으로 별 35,317개, 포크 5,048개이고,
`design/artcraft-apps.md`를 쓴 10월 7일의 별 6,644개에서
사흘 만에 다섯 배가 넘게 늘었다.
같은 날 이슈는 모두 998개가 열렸고 그중 395개가 열려 있으며,
풀 리퀘스트는 1,207개 중 932개가 병합되었다.
README의 상태 배지는 여전히 초기 알파(early alpha)다.

라이선스도 그사이에 바뀌었다.
`design/artcraft-apps.md`가 확인한 시점의 일곱 앱은 Apache-2.0이었지만,
0.2.0 릴리스에 들어간 PR #32가 MIT 또는 Apache-2.0 이중 라이선스와 `NOTICE`,
ArtCraft 상표 조건, 자산 출처 목록을 추가했다.
GitHub의 저장소 정보는 지금도 Apache-2.0 하나만 표시한다.
`docs/brand/`의 ArtCraft 로고는 오픈소스가 아니며, 포크는 로고를 지워야 한다.

## 크레이트 구조

작업 공간은 `crates/` 아래 25개 크레이트와
`apps/` 아래 세 개의 실행 파일로 나뉜다.
README는 24개라고 적지만,
그 뒤에 Affinity 파일을 여는 `affinity` 크레이트 등이 더해졌다.
`AGENTS.md`의 지도에 따르면 크레이트는 L0부터 L6까지 층으로 묶인다.

| 층  | 크레이트                             | 역할                                                   |
| --- | ------------------------------------ | ------------------------------------------------------ |
| L0  | `geom` `cms` `color` `raster`        | 기하, ICC 색 관리, 픽셀 형식과 블렌드 수식, COW 타일   |
| L0  | `psd` `codecs` `tablet`              | 독립 포맷 크레이트, 펜 태블릿 입력                     |
| L1  | `doc`                                | 레이어, 마스크, 조정, 효과, 스마트 오브젝트 데이터     |
| L2  | `ops` `paint` `algo` `text` `vector` | 히스토리, 브러시 엔진, 이미지 알고리즘, 문자, 경로     |
| L3  | `compose` `gpu` `format`             | CPU 합성기(기준), wgpu 합성기, `.pcraft` 네이티브 포맷 |
| L4  | `io` `plugins`                       | 문서와 PSD 변환, WebAssembly 플러그인 샌드박스         |
| L5  | `engine`                             | 세션과 명령 레지스트리                                 |
| L6  | `ui-egui` `automation`               | egui 셸, MCP 서버                                      |

한 크레이트는 자기보다 낮은 층에만 의존할 수 있고,
`cargo xtask layers`가 빌드에서 이를 검사한다.
`psd`, `codecs`, `cms`는 작업 공간의 다른 크레이트에 전혀 의존하지 않는다.
`ui-egui` 아래의 어떤 크레이트도 egui, eframe, winit을 쓸 수 없다.
L0부터 L6까지는 모두 `wasm32-unknown-unknown`으로 컴파일되어야 하므로,
파일 시스템 코드는 조건부 컴파일로 분리된다.

`crates/`, `apps/`, `xtask/` 아래 Rust 코드는 줄 수로 37만 3천 줄 정도다.
`unsafe`는 작업 공간 전체에서 금지되어 있고,
macOS에서 펜 태블릿 이벤트를 읽는 `photocraft-tablet`의 한 파일만 예외다.
테스트가 아닌 코드에서는
`unwrap()`, `expect()`, `panic!`을 clippy 설정으로 막는다.
`panic_hunt`라는 통합 테스트는 등록된 모든 명령에 적대적인 파라미터를 넣어
패닉이 나는지 확인한다.

## PSD 읽기와 쓰기

### 독립 크레이트의 바이트 단위 왕복

`photocraft-psd`는 다른 PhotoCraft 크레이트에 의존하지 않는
PSD와 PSB 읽기·쓰기 크레이트로, 약 1만 2천 줄이다.
README는 Adobe의 공개 명세로 구현했고,
명세가 말하지 않는 부분은 MIT 라이선스인 psd-tools와 ag-psd의 문서를 따랐으며
코드 주석에 그렇게 밝혔다고 적는다.

이 크레이트가 보장하는 첫 번째 성질은
수정하지 않은 파일을 읽고 다시 쓰면 입력과 같은 바이트가 나온다는 것이다.
그런데 이 성질을 만드는 방법이 중요하다.
채널 데이터는 원래 인코딩 그대로 보관하고,
모르는 블록과 리소스는 해석하지 않은 채 원본 바이트로 저장한다.
태그 블록이나 섹션 끝의 패딩까지 원래 길이를 기록해 둔다.
디코딩은 요청이 있을 때만 일어난다.
즉 바이트 단위 왕복은 해석하지 않은 것을 건드리지 않는다는 보존 성질이며,
레이어를 올바르게 해석하고 그렸다는 증거가 아니다.

`crates/psd/tests/corpus.rs`는 `corpus/psd`와 psd-tools 전체 테스트 세트의
모든 파일을 파싱하고 다시 써서 원본과 비교하며, 하나라도 다르면 실패한다.
예외는 psd-tools 쪽에서 1,906바이트로 잘려 병합 이미지가 없는 파일 하나뿐이다.
로드맵의 M2 항목은 이를 실제 파일 135개 중 134개의 바이트 단위 왕복이라고 적고,
홈페이지는 같은 숫자를
실제 테스트 파일 135개 중 134개가 바이트 단위로 왕복한다고 소개한다.

### 앱을 거친 왕복과 Photoshop 기준 비교

앱이 PSD를 열어 문서 모델로 바꾸고 다시 저장하는 경로는
`crates/io/tests/corpus.rs`가 시험한다.
이 테스트는 두 가지를 잰다.
하나는 파일을 문서로 읽어 합성한 결과를
그 파일에 Photoshop이 저장해 둔 병합 이미지와 비교하는 기준(oracle) 비교다.
다른 하나는 문서를 PSD로 내보냈다가 다시 읽어 합성한 결과가
첫 합성과 같은지 보는 왕복 비교다.
병합 이미지가 없는 파일은
Photoshop이 넣어 둔 최대 160픽셀의 JPEG 썸네일과 비교한다.

| 코퍼스                     | 기준 비교 하한 | 왕복 비교 하한 |
| -------------------------- | -------------- | -------------- |
| 직접 고른 ag-psd·psd-tools | 146 / 170      | 169 / 170      |
| psd-tools 전체             | 236 / 309      | 307 / 309      |
| 자체 Photoshop 기준 파일   | 133 / 256      | 258 / 256      |

README가 내세우는 309개 중 307개는 오른쪽 열,
즉 PhotoCraft가 자기 결과를 다시 읽었을 때 같게 그린다는 숫자다.
Photoshop이 그린 결과와 맞는 파일은 왼쪽 열의 236개다.
README도 다시 저장한 파일은 원본과 바이트 단위로 같지 않다고 분명히 적는다.
자체 Photoshop 기준 파일은 `storytold/photocraft-corpus`라는 별도 저장소에 있고,
코퍼스는 고정된 커밋에서 내려받아 sha256으로 검증한 뒤에만 쓴다.
마지막 행의 258 / 256은 `docs/scorecard.md`에 실제로 그렇게 생성된 숫자로,
하한이 전체 파일 수보다 크다.

## 레이어, 블렌드 모드, 필터의 범위

블렌드 모드는 `color` 크레이트에 27개가 있고,
PSD 크레이트도 27개 모드와 통과(pass-through)를 키로 읽고 쓴다.
비트 깊이(8, 16, 32비트 부동소수)와
색 모델(RGB, Grayscale, CMYK, Lab 등)은 실행 중의 데이터로 다루며,
공개 API에 8비트 전용 픽셀 경로를 두지 말라는 것이 규칙이다.
색 변환은 반드시 `photocraft-cms`를 거친다.

로드맵의 마일스톤 표는 조정 레이어 16종, Blur Gallery를 포함한 필터 70여 개,
레이어 스타일 효과 10종을 CPU와 GPU 모두에서 그리며
차이가 1/255 이내라고 적는다.
README의 도구는 52개로 늘었다.
Photoshop 메뉴 트리를 옮긴 `menu_catalog.rs`의 627개 항목이
모두 명령에 연결되어 `docs/parity.md`는 100%를 표시한다.
하지만 같은 로드맵의 솔직한 동등성 평가(Honest parity assessment)는
이 숫자가 배선만 잴 뿐 동작은 말하지 않는다고 분명히 적어 둔다.

그 평가는 2026년 10월 5일 기준으로,
일반 Photoshop 사용자가 만지는 기능의 60~70%가 어떤 형태로든 있고,
전문가가 매일 작업을 옮길 수 있는 수준은 25~35%라고 추정한다.
진짜 1:1 동등성은 몇 달이 걸리며, 생성형 AI 기능은 0%다.
메뉴 동등성은 9월 30일 224개(35.8%)에서
10월 1일 532개(85.1%)로 하루 만에 뛰었다.

카메라 RAW는 `photocraft-raw`가
DNG, CR2, Sony ARW, Nikon NEF 일부, RW2, 비압축 ORF와 RAF를 읽는다.
CR3와 압축 RAF는 아직 열지 못한다.
Affinity 문서(`.af`, `.afdesign`, `.afphoto`, `.afpub`)는
10월 8일부터 읽기 전용으로 열린다.
쓰기는 확인할 Affinity 설치본이 없다는 이유로 구현하지 않았다.

## 렌더링

캔버스는 wgpu 위의 GPU 합성기(`photocraft-gpu`)가 그리고,
CPU 합성기(`photocraft-compose`)는 내보내기와 테스트의 기준으로 남는다.
GPU 플래너가 표현하지 못하는 문서,
예를 들어 Multichannel 문서나 GPU 텍스처 한도를 넘는 영역은 CPU로 넘어간다.
픽셀은 256×256 크기의 희소 타일에 쓰기 시 복사(copy-on-write)로 저장된다.

이 구조가 실제로 시험받은 곳은 사용자 하드웨어였다.
첫 이슈 중 하나인 #4에서는
Windows의 Intel Vulkan 드라이버가 시작하자마자 죽었다.
`Rgba32Float` 렌더 타깃을 지원하지 않는 드라이버 때문이었고,
PR #22가 어댑터마다 이를 확인해 `Rgba16Float`로 내려가게 했다.
드라이버 안에서 프로세스가 죽는 경우는 코드로 잡을 수 없으므로,
PR #252는 GPU 장치를 만들기 전에 표시 파일을 남기고,
직전 실행이 드라이버에서 죽었으면 다음 실행에서 Vulkan, DX12,
CPU 순으로 안전한 백엔드로 내려가게 했다.
Intel 어댑터는 Windows에서 기본값이 DX12가 되었다.
같은 계열의 EffectCraft 0.4.0에서 이 방식이 동작했다는
사용자 확인이 이슈에 남아 있다.

wesbos가 올린 #332는 11796×9799 크기에 레이어가 수백 개인 PSD를 열면
앱이 죽는다는 보고였다.
한 번의 새로 고침이 거대한 GPU 명령 버퍼 하나로 나가 macOS가 GPU를 리셋했고,
egui 렌더러가 잃어버린 장치에 접근하다 중단된 것이었다.
PR #187이 큰 새로 고침을 잘게 나누고 GPU 메모리 예산을 더해 고쳤다.
`docs/scorecard.md`의 성능 시나리오 56개 가운데 예산을 지키는 것은 3개이고,
150개 레이어 문서에서 화살표 키로 이동하는 시나리오는
GPU 합성기의 wgpu 검증 오류로 측정조차 되지 않는다.

## CLI, 제어 채널, MCP 서버

모든 메뉴, 도구, 대화상자는 `engine`의 명령 레지스트리를 거친다.
명령은 ID, 라벨, 메뉴 경로, Photoshop 기본 단축키, 파라미터 설명 문자열,
활성 조건, 실행 함수를 가지며,
한 번 실행하면 히스토리에 정확히 한 단계를 남겨야 한다.
에이전트는 이 파라미터 설명을 `command_list`로 읽는다.

MCP 서버는 `photocraft-cli mcp`로 헤드리스 세션을 띄우거나,
`--bridge`로 실행 중인 데스크톱 앱에 붙는다.
도구는 `command_list`, `command_run`, `command_batch`, `doc_inspect`,
`render_preview`, 브리지 모드의 `ui_inspect`와 `ui_screenshot` 등이다.
0.2.0부터는 자동화 클라이언트의 파일 접근이 `--automation-read-root`와
`--automation-write-root`로 허락한 폴더 안으로 제한되고,
허락이 없으면 파일 작업은 실패한다.
데스크톱 앱의 제어 채널은 루프백 주소에서만 듣고,
실행마다 만드는 256비트 토큰으로 인증한 뒤에만 요청을 받는다.

pcglue는 HN에서 사람 셋이 있는 사진과 한 명이 있는 사진을 합치는 일을
ChatGPT의 이미지 생성은 얼굴을 바꿔 버려 해내지 못했지만,
Claude와 PhotoCraft MCP 서버로는 5분 동안 세 번 시도해 해냈다고
적었다[^pcglue].
에이전트가 생성 모델 대신 편집기를 조작하게 하면
원본 픽셀이 보존된다는 점을 보여 주는 사례다.

## 클린룸 규칙

`docs/contributing.md`와 `AGENTS.md`가 말하는 클린룸은 다음과 같다.
Photoshop과 다른 독점 편집기는 동작과 겉모습만 연구했다.
그들의 코드, 셰이더, ICC 프로파일, 자산은 복사하지 않는다.
구현의 근거는 Adobe PSD 명세, ICC, ISO 32000의 블렌드 모드, 논문, 관찰이다.
제3자 자산은 허용적인 라이선스여야 하고 파일 옆에 라이선스를 두며
`ATTRIBUTION.md`에 행을 추가한다.
글꼴은 저장소에 넣지 않고 `storytold/craft-fonts`에서 빌드 입력으로 받는다.

가장 엄격하게 적용된 곳은 카메라 RAW다.
Nikon 압축 NEF 디코더의 주석은 dcraw, LibRaw, rawspeed, darktable,
RawTherapee 같은 RAW 디코더 소스를 읽지 않았다고 명시하고,
근거가 된 산문 형식 설명서를 하나씩 든다.
허프만 표는 파일에 들어 있지 않아서,
같은 장면을 압축과 비압축으로 찍은 CC0 표본을 비교하는
블랙박스 분석으로 복원했다고 한다.
공개 설명이 GPL 디코더 소스밖에 없는 형식은 지원하지 않고
내장 JPEG 미리보기를 연다.

## 분석

### 저장소 자체가 에이전트를 위한 작업 환경이다

PhotoCraft 저장소에서 가장 공들인 부분은
이미지 처리 알고리즘이 아니라 에이전트가 망가뜨리지 못하게 하는 장치다.
층 규칙은 빌드에서 검사되고, 패닉 경로는 clippy가 막으며,
`panic_hunt`가 모든 명령에 무작위 입력을 넣는다.
`photocraft-format`은 문서 구조체에 필드가 생기면 일부러 컴파일에 실패해서,
새 필드가 `.pcraft` 저장에서 조용히 빠지는 일을 막는다.
코퍼스 하한은 올릴 수만 있고 내릴 수 없다고 문서마다 반복한다.

이 장치들은 사람 팀에게도 좋은 습관이지만, 여기서는 역할이 다르다.
에이전트는 세션이 끝나면 맥락을 잃으므로,
규칙은 프롬프트가 아니라 빌드가 강제해야 다음 세션에도 남는다.
`AGENTS.md`가 세션이 갑자기 끝날 수 있다는 이유로
개발 기록을 남기라고 지시하는 대목은
이 저장소가 누구를 위해 설계되었는지 잘 보여 준다.
에이전트가 수백 개의 명령을 병렬로 추가해도 앱이 무너지지 않는 것은
모델의 능력보다 이 울타리 덕분이라고 보는 편이 맞다.

### 명령 레지스트리는 시험 장치이자 제품 기능이다

모든 동작을 명령으로 만든 설계는
`design/artcraft-apps.md`가 에이전트 인터페이스로 짚은 부분이다.
저장소를 읽어 보면 이 설계의 첫 번째 사용자는
바깥의 에이전트가 아니라 앱을 만드는 에이전트다.
README의 스크린숏은 제어 채널로 오프스크린 렌더링해 찍었고,
UI를 바꾼 에이전트는
오프스크린 스냅숏을 렌더링해 PNG를 직접 보라는 지시를 받는다.
메뉴 항목의 ID만 맞추면 메뉴가 저절로 살아나므로,
메뉴 동등성이 하루 만에 35.8%에서 85.1%로 오를 수 있었다.

같은 인터페이스가 MCP로 밖에 나가면
pcglue의 사례처럼 생성 모델이 못 하는 정밀 편집을
다른 에이전트에게 맡길 수 있는 기능이 된다.
개발 도구와 제품 기능이 같은 코드라는 점은 이 방식의 효율이다.
다만 이 효율은 명령으로 표현할 수 있는 것에만 미치고,
붓질의 느낌이나 패널을 끌 때의 반응처럼
명령 하나로 담기지 않는 것은 그만큼 늦게 따라온다.

### 측정을 문서로 남기는 습관이 정직함을 만든다

이 프로젝트의 문서는 마케팅 문구와 자기 평가가 놀랄 만큼 따로 논다.
홈페이지는 이미 알고 있는 편집기라고 말하지만,
로드맵은 전문가가 옮겨 올 수준을 25~35%로 적고
실제 동등성은 50%에 한참 못 미친다고 말한다.
메뉴 동등성 100%라는 숫자 바로 옆에서 그것이 배선일 뿐이라고 경고한다.
점수표는 예산을 못 지킨 성능 시나리오와
아무것도 하지 않는 설정의 수를 그대로 싣는다.

이런 자기 평가가 가능한 것은
숫자가 사람의 판단이 아니라
`cargo xtask scorecard` 같은 생성 도구에서 나오기 때문이다.
에이전트에게 정직하라고 요구하기보다,
정직한 숫자를 만드는 도구를 주고 그 숫자를 갱신하라고 시키는 방식이다.
그래서 이 저장소에서 가장 믿을 만한 문서는
README가 아니라 로드맵의 평가 절과 점수표다.

모르는 블록을 손대지 않는 파서는 그 블록을 이해하지 못해도 이 시험을 통과한다.
수정 없는 왕복은 파서가 파일을 망가뜨리지 않는다는 최소 조건이지,
레이어를 제대로 해석했다는 증거가 아니다.

Photoshop에서 만든 파일이 같은 모습으로 열리는 것이므로,
대표 숫자로는 왼쪽 열이 맞다.

`docs/scorecard.md`에 적힌 258 / 256처럼

측정을 자동화했다고 해서 측정값을 검토했다는 뜻은 아니다.

### 클린룸은 절차가 아니라 출처 목록으로만 주장된다

전통적인 클린룸에서 핵심은 출처 목록이 아니라 분리다.
원본을 분석한 팀과 구현하는 팀이 나뉘고,
구현자가 원본을 보지 않았다는 사실을 서약과 기록으로 입증한다.
PhotoCraft의 규칙은 무엇을 근거로 삼았는지는 꼼꼼히 적지만,
구현자가 무엇을 보지 않았는지는 입증할 방법이 없다.
구현자가 모델이고, 그 모델의 학습 자료는 아무도 확인할 수 없기 때문이다.

Lobste.rs에서 가장 많은 표를 받은 댓글은
커밋 메시지의 Claude Opus 5.5 공동 작성자 꼬리말 한 줄을 인용하며
그다지 클린룸은 아니지 않냐고 꼬집은 Halkcyon의 것이었다[^Halkcyon].
david_chisnall은 Adobe 소스 유출본이 학습 자료에 들어가지 않았다는 데
걸 수 있겠냐며,
Adobe가 감사해서 실제 Photoshop 코드를 C에서 Rust로 그대로 옮긴 부분이
얼마나 되는지 보고 싶다고 했다[^david_chisnall].
dvshkn은 LLM에 반대하지 않지만
LLM이 상당한 역할을 한 프로젝트는 클린룸으로 보지 않는다고 했다[^dvshkn].
stop50도 HN에서
모델이 유출된 Photoshop 코드로 학습하지 않았다는 보장이 어디 있냐고
물었다[^stop50].

흥미로운 것은 저장소가 RAW 디코더에서는 이 문제를 정확히 이해하고 있다는 점이다.
GPL 디코더 소스를 읽지 않았다고 밝히고,
공개 설명이 GPL 소스뿐인 형식은 아예 지원하지 않는다.
사람이 읽는 출처에는 이렇게 엄격하면서,
그 GPL 소스를 학습했을 가능성이 높은 모델에게 구현을 맡기는 일은

이슈 #341에 관리자가 아직 답하지 않은 것은
이 비대칭에 대한 답이 없기 때문으로 읽힌다.

### 공개 저장소의 규칙이 비공개 저장소에 기댄다

`AGENTS.md`와 `docs/contributing.md`는
충돌 금지, 글꼴, 릴리스 절차 같은 공통 표준의 원본이
`craftrules`에 있다고 여러 번 가리킨다.
그런데 이 저장소는 공개되어 있지 않아서, 외부 기여자는 관리자에게 물어봐야 한다.
에이전트의 개발 기록과 계획 문서도 `.gitignore`에 들어 있다.
코드는 MIT와 Apache-2.0으로 열려 있지만,
이 코드를 만든 과정을 재현하는 데 필요한 문서는 열려 있지 않은 셈이다.

이 구조에서 포크는 코드만 가져갈 수 있다.
같은 품질로 개발을 이어 가려면 같은 규칙, 같은 개발 기록,
같은 계획이 필요한데 그것은 한 회사 안에 남는다.
에이전트로 만드는 프로젝트에서는
코드보다 규칙 문서가 더 핵심 자산일 수 있다는 점에서,
이는 오픈소스라는 주장의 범위를 좁힌다.

### 하루 단위 릴리스는 검증을 사용자에게 넘긴다

일주일에 릴리스 일곱 개, 10월 9일 하루에 커밋 358개라는 속도는 인상적이지만,
로드맵 스스로 0.2.0 이후의 수정 대부분이 테스트는 통과했지만
사용자 검증을 거치지 않았다고 인정한다.
그리고 첫 공개 사용에서 사용자가 찾은 기본 결함이
모두 parity 문서에서 살아 있는 항목으로 세어지고 있었다고 적었다.
테스트가 사용자가 부딪히는 것을 놓친다는 사실을
프로젝트가 이미 알고 있는 것이다.

그런데도 릴리스는 더 빨라졌다.
qustrolabe는 v0.3.0 소프트웨어에서 기대할 만한 수준이며,
매일 그 기능을 쓰는 사람의 피드백을 받으려면
지금 공개하는 것이 맞다고 옹호했다[^qustrolabe].
그 말은 맞지만,
그러면 22만 회 넘게 내려받은 사용자는 QA 팀 역할을 한다는 뜻이 된다.
작업물을 맡기는 도구에서 이 역할 분담은 사용자에게 분명히 알려야 하는데,
홈페이지의 이미 알고 있는 편집기라는 문구는 그 반대의 인상을 준다.

## 인사이트

### 에이전트 개발은 측정되는 것부터 수렴한다

메뉴 배선은 하루 만에 100%에 가까워졌고, PSD 왕복은 하한이 거의 꽉 찼으며,
패닉 금지는 28개 크레이트 모두에 적용되었다.
반면 성능 예산은 56개 중 3개만 지켜지고, 문자 영역은 완료 항목이 0개이며,
jenniferhooley가 말한 느림과 어색함은 숫자로 잡히지 않는다.
이것은 우연이 아니라 에이전트 개발의 구조적 성질로 보인다.
에이전트는 실패하는 시험이 있으면 그것을 통과시키고,
시험이 없는 것은 개선할 신호를 받지 못한다.

굿하트의 법칙이 사람 조직에 대해 말하는 것과 같은 현상이
훨씬 빠른 속도로 일어난다.
사람 팀은 측정되지 않는 것도 감각으로 챙기지만,
에이전트에게 감각에 해당하는 것은 결국 누군가 써 둔 시험이다.
그래서 이런 프로젝트의 진척을 보려면
통과한 숫자보다 아직 측정되지 않는 영역의 목록을 보는 편이 정확하다.
PhotoCraft가 점수표에 측정 불가 항목과
아무것도 하지 않는 설정 수를 따로 세는 것은 이 함정을 알고 있다는 신호다.

장기적으로는 느낌을 시험으로 바꾸는 사람이 가장 귀한 기여자가 된다.
ljkx나 EthanSuquet처럼 사용자의 충돌 보고를 재현 가능한 시험으로 만드는 일,
bubbl000처럼 불편을 확인할 수 있는 항목으로 나누는 일이 이 프로젝트에서
코드를 쓰는 일보다 희소하다.

### 기여자가 에이전트를 데려오는 오픈소스는 리뷰의 병목을 옮긴다

외부 기여자의 PR에도 Claude 공동 작성자 꼬리말이 흔하고,
`AGENTS.md`는 기여자를 위해 일하는 에이전트에게
사람의 이름을 크레딧 파일에 넣을지 물어보라고 지시한다.
이는 오픈소스 기여의 단위가
사람에서 사람과 그의 에이전트의 묶음으로 바뀌었다는 뜻이다.
열흘 만에 161명의 이름이 커밋에 남은 것도 이 덕분이다.

기여 비용이 거의 없어지면 병목은 리뷰로 옮겨 간다.
Linux 커널이나 대형 프로젝트가 오래 겪은 문제,
즉 패치를 쓰는 사람은 많고 판단할 사람은 적다는 문제가
이제 열흘 된 프로젝트에서 바로 나타난다.
PhotoCraft는 리뷰의 상당 부분을 빌드 규칙, clippy, 코퍼스 하한,
CI 같은 기계 판정으로 대신해 이 병목을 넘고 있다.
PR #1682처럼 같은 수정이 다른 기여자에게서 중복으로 들어온 기록도
커밋 메시지에 남아 있는데,
기여 비용이 낮을수록 같은 일을 여러 에이전트가 동시에 하는 낭비도 늘어난다.

이 방식의 한계는 기계가 판정할 수 없는 결정에서 드러난다.
생성형 AI 공급자를 고르는 #41처럼 제품 방향이 걸린 문제는
PR이 몇 개 와도 관리자가 결정하기 전까지 멈춰 있다.
에이전트로 코드를 늘리는 속도가 빨라질수록
프로젝트의 진짜 속도는 사람의 결정 속도로 수렴한다.

### 클린룸은 원래 법정을 위한 기록이었고, 에이전트 시대의 기록은 커밋 로그다

1980년대 Phoenix와 Compaq의 IBM BIOS 클린룸은
기술적 방법이기 이전에 법정에서 쓸 증거를 만드는 절차였다.
분석 팀과 구현 팀을 나누고,
구현자가 원본을 보지 않았다는 서류를 남기는 것이 핵심이었다.
ljkx가 말한 대로 원본을 아는 것 자체는 문제가 아니었고,
그 앎이 구현자에게 어떻게 전달되었는지를 증명할 수 있느냐가 문제였다.

qarl은 HN에서 한 에이전트가 원본을 보고 명세를 쓰고
다른 에이전트가 그 명세로 구현하면 클린룸 역공학의 요건이 된다고
했다[^qarl].
형식만 보면 그럴듯하지만,
두 에이전트가 같은 학습 자료를 공유하는 같은 모델이면 분리는 이름뿐이다.
옛 클린룸의 분리는 사람의 기억이 서로 다르다는 데 기댔고,
모델의 기억은 복제된다.

역설적으로 PhotoCraft는 클린룸 시대보다 훨씬 많은 기록을 남겼다.
커밋마다 어떤 모델이 썼는지 적혀 있고,
코드 주석은 어떤 문서를 근거로 했는지 밝힌다.
다만 그 기록이 증명하는 것은 무엇을 보았는지가 아니라 누가 썼는지다.
앞으로 이런 분쟁이 생기면 쟁점은 구현자가 무엇을 보았는가에서
결과물이 원본과 얼마나 닮았는가로 옮겨 갈 가능성이 높고,
그때는 커밋 로그보다 코드 비교가 증거가 될 것이다.
이는 해석이지만,
ljkx가 Photoshop 1.0.1 소스와 직접 비교해 보라고 한 말은
이미 그 방향을 가리킨다.
