# Craft Anything: 웹사이트와 앱과 게임을 살펴본 뒤 AI로 비슷한 것을 다시 만들어 원본과 비교해 고치는 Rust 엔진

<https://github.com/storytold/craft-anything>

HN 토론: <https://news.ycombinator.com/item?id=50377361> (5점, 3개 댓글)

GN 토론: <https://news.hada.io/topic?id=36730>

## 소개

Craft Anything은 대상을 조사하고 코딩 에이전트에게 새 프로젝트를 만들게 한 뒤
결과를 원본과 비교해 다듬는 오픈소스 엔진이다.
저장소 설명은 어떤 소프트웨어가 어떻게 동작하는지 이해하고 자기 것을 만든다는
한 줄이고,
README는 웹사이트, 앱, 게임이 어떻게 동작하는지 보고 AI가 자기 버전을
만들게 하는
클린룸(clean-room) 방식의 순수 Rust 엔진이라고 소개한다.
README의 상태 표시는 초기 알파(early alpha)다.

2026년 11월 7일에 읽은 GitHub 정보는 다음과 같다.
스타 18,327개, 포크 3,389개, 열린 이슈 215개이고 2026년 10월 31일에 만들어졌다.
같은 날 읽은 최신 릴리스는 11월 6일의 `v0.5.0`이고, 그 앞은 같은 날의 `v0.4.0`과
11월 2일의 `v0.3.0`이다.
저장소를 만든 지 일주일이 되지 않았다.
README의 라이선스 표기는 MIT 또는 Apache-2.0 이중 라이선스이고
`LICENSE-MIT`와 `LICENSE-APACHE`가 둘 다 있으며, GitHub의 판정은 Apache-2.0이다.

이 저장소는 ArtCraft 팀이 만드는 Craft 앱 모음의 하나다.
README의 표에는 PhotoCraft, VectorCraft, FilmCraft, LightCraft, PdfCraft,
EffectCraft,
DesignCraft, FigCraft, WordCraft, SoundCraft, DeckCraft, CADCraft, GridCraft,
TextureCraft, MaterialCraft와 Craft Anything이 열여섯 개로 올라 있고,
Tangency Labs의 커뮤니티 앱 SolidCraft가 따로 붙는다.
모음 전체는 [ArtCraft Crafting Apps](./artcraft-apps.md)에서,
이미지 편집 앱은 [PhotoCraft](./photocraft.md)에서,
AI 이미지와 영상 스튜디오는 [ArtCraft](./artcraft.md)에서 다룬다.

## 동작 방식

대상을 가리키고 원하는 것을 말한 뒤 시작을 누르면 네 단계로 일한다.
결정이 사용자의 몫일 때는 쉬운 말로 묻는다.

| 단계        | 하는 일                                                                       |
| ----------- | ----------------------------------------------------------------------------- |
| 조사(Study) | 원본의 페이지를 모든 너비에서, 코드와 파일과 실행 방식을 살펴본다             |
| 제작(Build) | 코딩 에이전트가 요청에 적힌 언어나 프레임워크나 엔진으로 새 프로젝트를 만든다 |
| 점검(Check) | 결과를 원본과 비교해 아직 맞지 않는 것을 나열한다                             |
| 준비(Ready) | 결과를 열고 실행하거나 미리 보고, 고칠 것을 말하면 다시 다듬는다              |

사용 방식은 둘이다.
단순(Simple) 방식은 기본이고, 무엇을 만들지 고르고 설명한 뒤 시작을 누르면
프로젝트 페이지가 네 단계의 진행과 에이전트가 하는 일, 질문과 승인 카드,
결과가 원본과 얼마나 닮았는지를 보여 준다.
고급(Advanced) 방식은 모든 도구(Ctrl 또는 Cmd+K), 함수, 문자열, 의사 C 코드,
디스어셈블리, 헥스, 호출 그래프, 증거, 미해결 항목, 작업, 로그,
에이전트 콘솔을 가진
작업대다.
두 방식은 같은 엔진을 쓴다.
만들지 않고 대상만 열어 질문하는 방식(Just look inside)은 딥(Deep)
모드에서 쓴다.

### 클린룸과 딥 모드

클린룸은 기본값이고 원본 안쪽을 읽지 않는다.
코드도, 파일도, 페이지 소스도 읽지 않고 눈에 보이는 것에서만 출발한다.
사용자가 넣은 그림, 방문자가 보는 대로의 웹사이트(스크린샷, 보이는 글,
측정한 배치,
색과 글꼴과 간격, 열어 본 메뉴), 허락하면 앱 창의 그림이다.
안쪽을 들여다보는 도구는 거절되고 딥 모드를 켜는 방법이 안내된다.

딥 모드는 모든 도구를 쓰며 개인용을 전제로 한다.
프로그램의 코드와 파일을 내장 엔진(Ghidra가 설치되어 있으면 함께)으로 읽고,
웹사이트의 자바스크립트를 읽고 시작 페이지를 관찰하며,
제작자는 이 모두를 쓸 수 있다.
모드는 제목 표시줄이나 설정, `settings_set deep_mode true`, 명령줄의
`--deep`과 `--clean-room`으로 바꾼다.

README는 클린룸이 Craft Anything이 제공하고 거절하는 것에 대한 규칙이지
운영체제 샌드박스가 아니라고 분명히 적는다.
컴퓨터를 격리하지 않으며, 사용자가 돌리는 코딩 에이전트는 여전히 사용자 권한으로
움직이고 읽고 쓰고 실행할 수 있는 범위는 그 에이전트의 권한에 달려 있다.

### 조사 엔진과 도구

내부는 순수 Rust로 만든 리버스 엔지니어링 엔진이고 도구는 320개다(엔진 300개,
나머지는 AI와 설정 계층).
다루는 대상은 네이티브 프로그램, .NET, 자바, 안드로이드, 애플,
Electron과 자바스크립트,
웹사이트, 펌웨어, 패킷 캡처, 데이터베이스, 게임 파일이다.
자체 디코더, 디스어셈블러, 디컴파일러가 외부 프로그램 없이 동작하고,
Ghidra가 있으면 딥 모드가 함께 쓴다.
데스크톱 앱(egui), 명령줄, MCP 서버가 같은 엔진을 쓰고 일부는 웹어셈블리로
브라우저에서 돈다.

모든 도구는 명령줄 하위 명령이면서 MCP 도구라서 앱 없이 에이전트가 대상을
조사하거나
재구축 전체를 돌릴 수 있다.
결과는 신뢰도와 범위와 한계가 붙은 증거 기록이고, 큰 결과는 요약이 먼저 오고
`core_evidence_browse`로 나눠 읽는다.

## 설치와 사용

Rust 1.97 이상이 필요하다.
데비안과 우분투에서는 데스크톱 앱을 위해 추가 패키지가 필요하다.

```sh
git clone https://github.com/storytold/craft-anything && cd craft-anything
cargo run --release -p craft-anything                # 데스크톱 앱
cargo install --path apps/craft-anything-cli         # 명령줄, craft-anything-cli
craft-anything-cli doctor                            # 설치, 코딩 에이전트, 엔진을 점검한다
```

제작에는 컴퓨터에 로그인된 코딩 에이전트가 필요하고 `doctor`가 빠진 것을
알려 준다.
명령줄 재구축은 다음과 같다.

```sh
craft-anything-cli rebuild https://example.com "Recreate this website"
craft-anything-cli rebuild - "A snake game in Rust" --rounds 1
craft-anything-cli rebuild https://example.com "Make the header blue" --continue-in "<project folder>"
craft-anything-cli rebuild - "Add a contact form" --project-folder "<your folder>" --existing edit
```

새 프로젝트는 `Documents/Craft Anything`에 생기고 설정에서 바꿀 수 있다.
프로젝트 폴더에는 요청과 대상과 상태와 이력을 담은 `craft.json`, 대상에서 기록한
`capture/`, 생성된 프로젝트 `app/`, 원본과의 비교 결과 `checks/`, 증거
`investigation.cany/`, 열린 질문 `inbox/`가 있다.
이미 파일이 있는 폴더에서 시작하면 그것이 앱 자체인지(제작자가
제자리에서 고친다)
시작 재료인지(`app/`에 새로 만든다) 사용자가 말해야 한다.

설치 파일은 윈도우(x64, arm64, x86의 `.msi`와 휴대용 `.zip`),
맥(유니버설 `.dmg`,
서명과 공증 완료, 명령줄 도구 `.zip`), 리눅스(AppImage, Flatpak, `.deb`, `.rpm`,
tar.gz, x86_64와 aarch64, riscv64는 tar.gz만), FreeBSD(x86_64 tar.gz),
브라우저용
웹어셈블리 뷰어가 있다.
리눅스 Flatpak은 샌드박스라 브라우저를 띄울 수 없어서 웹사이트 조사에는 다른
패키지를
쓰라고 안내한다.
macOS에서 명령줄 zip을 브라우저로 받으면 “Apple could not verify”가 뜰 수 있어
터미널의 `curl`로 받으라는 우회 방법이 README에 있다.

## 코딩 에이전트와 약관

제작에는 컴퓨터의 코딩 에이전트가 필요하고 Claude Code를 가장 먼저 지원한다.
README는 Craft Anything이 사용자의 수정하지 않은 `claude` 프로그램을 돌리고
사용자 본인의 로그인을 쓰며 계정을 보거나 다루지 않는다고 한다.
사용은 사용자 본인과 Anthropic 사이의 계약을 따른다고 적는다.
Codex 어댑터는 있지만 실제 설치에서 확인되지 않았고,
GitHub Copilot과 Grok Build는 ACP를 거쳐 설치된 프로그램을 쓴다.
ACP를 말하는 다른 에이전트(Gemini CLI, Qwen Code, opencode, goose,
Hermes, Maki)는
백엔드별로 바꿀 수 있지만 실제로 돌려 본 것은 Maki뿐이라고 한다.
Anthropic, OpenAI, OpenRouter, xAI, 로컬 서버의 API 키는 질문과 분석에 쓸
수 있다.

`docs/claude-code.md`는 연동 방식을 자세히 적는다.
헤드리스 모드로 `claude -p`를 자식 프로세스로 돌리고,
작업 폴더는 프로젝트 폴더이며,
Craft Anything의 도구는 `--mcp-config`로 자기 MCP 서버를 통해 제공하고,
권한 요청은 `--permission-prompt-tool`로 자기 승인 도구가 받는다.
승인 도구는 프로젝트의 `app/` 안 편집과 정해진 빌드 명령(`npm install`,
`npm run build`,
`cargo build` 등)을 허용하고 끝나지 않는 개발 서버를 거절하며,
나머지는 종류별(웹,
명령, 프로젝트 밖의 파일, 푸시와 배포, 삭제, 시스템 변경)로 프로젝트마다 허용,
질문, 거절을 고른다.
문서는 이 장치들이 문턱을 높일 뿐 벽은 아니라고 스스로 적는다.
명령 실행을 허용한 제작자는 사용자의 권한으로 움직이므로 기본값인 자동 모드의
명령 허용은 제작자를 신뢰하는 것이라는 설명이다.

같은 문서는 이것이 Anthropic의 약관에 맞는다고 보는 이유를 적는다.
2026년 10월에 공개된 약관을 기준으로, 서드파티가 Claude.ai 로그인을 제공하거나
구독 자격으로 요청을 중개하는 것은 안 되지만 최종 사용자가 수정하지 않은
Claude Code
바이너리에 자기 구독으로 로그인하는 것은 막지 않는다는 것이다.
Craft Anything은 수정하지 않은 바이너리를 쓰고,
자격을 읽거나 저장하거나 전달하지
않으며, Claude 사용량을 대신 내거나 팔거나 계량하지 않고,
문서화된 플래그만 쓴다고 적는다.
Anthropic의 로고와 Claude Code라는 이름도 제품이나 기능의 이름으로 쓰지
않는다고 한다.

문서는 유료 제품에 대해서는 확인이 필요한 질문을 세 가지 남긴다.
Agent SDK 개요가 서드파티가 로그인이나 사용 한도를 제공하는 것을 승인
없이 못 하게
한다는 점, 구독의 광고된 한도가 일반적인 개인 사용을 전제한다는 점
(그래서 재구축 회차를 첫 제작 한 번과 앱에서 최대 6번,
명령줄에서 최대 2번의 다듬기로
제한했다), 사용자가 아니라 회사가 모델 비용을 내는 관리형(managed) 단계는 구독이
아니라 자체 API 키와 상업 약관을 써야 한다는 점이다.
README의 다음 계획에 관리형 단계가 올라 있다.
구독 경로가 맞지 않으면 같은 흐름을 API 키 백엔드로 돌릴 수 있지만,
그 백엔드로 제작하려면 자체 에이전트의 파일 쓰기 도구 반복이 더 필요하다고 이
문서는 적는다.
상태 문서는 이미 자체 루프와 제작 도구로 제작하는 코드가 있고 실제 API 제작은
아직 돌려 보지 않았다고 적어, 두 문서의 서술이 같지 않다.

## 현재 상태와 검증 수준

README는 초기 알파라고 밝히고 지금 되는 것과 부분적인 것을 나눈다.
지금 되는 것은 데스크톱 앱(단순과 고급), 명령줄, MCP 서버,
Claude Code를 제작자로 쓰는 웹사이트와 앱과 게임의 조사, 제작, 점검, 다듬기,
세 가지 화면 너비에서의 웹사이트 점검, Unity와 Unreal과 Godot에서의 게임 재구축,
Ghidra를 쓰는 딥 모드, 선택해서 켜는 이미지와 3D 모델 생성(사용자의 fal.ai 키),
플러그인(MCP 서버, `wasm-plugins` 옵션이 있는 빌드에서 WASM 컴포넌트)이다.
부분적인 것은 API 키와 다른 코딩 에이전트로 제작하는 것, 앱과 게임의 행동 점검,
가짜 대역에서만 시험한 몇몇 엔진 도구다.

`docs/STATUS.md`는 무엇을 어떻게 확인했는지를 적는다.
2026년 10월 23일의 기준 감사에서는 `main`에서 테스트 923개가 통과했고,
문서의 마지막 갱신은 11월 5일이다.
실제 끝까지의 실행(2026년 10월 18일, 윈도우 10, 헤드리스 명령줄)으로는
웹사이트 복제가 1.5분 만에 닮은 정도 96%로 준비 상태에 도달했고,
작은 데스크톱 앱을 Rust와 egui로 다시 만든 것이 9분 만에 준비 상태가 되었으며
(빌드만으로 확인), 게임 재구축은 제작 단계까지 갔다가 점검 전에 멈췄다고
적혀 있다.

한계 목록에서 눈에 띄는 것은 다음과 같다.
웹사이트 점검은 시작 페이지와 링크된 페이지 최대 12개를 설정한 너비에서
비교한다.
게임은 자체 `--self-test`를 통과해야 하지만,
이 시험은 빌드가 스스로 내는 보고이고
Craft Anything이 게임이 하는 것을 보거나 값을 재지는 않는다고 한다.
딥 모드에서 쓴 게임에는 `app/CREDITS.md`와 개인용이라는 문구가 필요하다.
Frida 세션 도구는 일부가 모의다.
에이전트마다 승인 방식이 달라서, Claude Code는 이 도구의 승인 도구를 거치고
OpenCode의 제작자는 `--auto`로 돌고 Hermes는 승인을 끄므로
클린룸의 승인 규칙이 모든 에이전트에 닿지는 않는다.

## 책임 있는 사용과 보안

README는 소유하거나 조사할 권한이 있는 소프트웨어에만 쓰라고 한다.
DRM, 로그인, 치트 방지를 우회하지 않고, 재구축은 증거에서 배치와 스타일과 행동을
다시 만들며, 에이전트에게는 소유권이나 허락을 확인해 주지 않으면 로고와
사진과 글을
복사하지 말라고 지시한다고 적는다.

README가 따로 경고하는 것은 의존성 설치가 코드를 실행한다는 점이다.
제작자가 프로젝트의 의존성을 설치하면 명령이 사용자의 컴퓨터에서 돌고,
npm은 기본으로 각 패키지의 설치 스크립트를 실행하며 Rust 빌드 스크립트와
파이썬 소스
패키지도 자기 설정 코드를 실행한다.
Craft Anything은 이 프로젝트에서 본 적 없는 종류의 명령(`npm`,
`cargo`)은 먼저 묻지만,
`npm`을 항상 허용으로 고르면 이후의 모든 npm 명령이 묻지 않고 돈다.
신뢰하는 프로젝트에서만 그렇게 하고, 스크립트 없이 설치하려면
`npm install --ignore-scripts`를 쓰라고 한다.

`SECURITY.md`는 이 도구가 적대적인 파일을 읽고 다른 프로그램을 실행한다고
전제한다.
취약점으로 치는 것은 어떤 입력 파일이나 웹사이트에서의 충돌, 멈춤, 메모리 폭주(
“절대 죽지 않는다”가 `AGENTS.md`의 강한 규칙이다),
사용자의 동의 없이 대상의 코드가
실행되는 것, 도구가 선언한 효과보다 더 많이 하는 것,
에이전트가 승인 없이 프로젝트
밖에서 행동하는 경로, 비밀이 로그와 출력과 증거와 저장소로 새는 것,
플러그인이 샌드박스를
벗어나는 것이다.
WASM 플러그인은 아무것도 가져오지 않고 MCP 플러그인은 호출마다 묻는다.

`CONTRIBUTING.md`는 로드맵의 할 일을 고르고 그 줄에 담당을 적은 뒤 초안 풀
리퀘스트를
열라고 하며, 사람과 AI 에이전트 모두에게 같은 규칙을 적용한다.
안전한 Rust만 쓰고 모든 외부 프로그램을
`craft_anything_platform::process`로 부르며
비밀과 개인 정보를 어디에도 두지 말고, 다른 프로젝트의 코드와 이름과
문장을 베끼지
말라는 규칙이 있다.
ArtCraft 이름과 로고는 라이선스 밖의 상표이고,
앱 아이콘인 까마귀도 오픈소스가 아니다.

## 비평

### 클린룸이라는 이름은 법적 의미가 아니라 도구의 권한 모드다

클린룸은 보통 원본을 본 사람과 새로 구현하는 사람을 나누어 원본의 표현이
새 구현에
들어가지 않았음을 보이려는 절차를 가리킨다.
이 도구의 클린룸은 다르다.
README의 정의로는 이 도구가 제공하고 거절하는 도구의 범위,
곧 코드와 파일과 페이지
소스를 읽지 않는다는 규칙이다.
그 규칙 안에서도 원본의 보이는 모습(스크린샷, 측정한 배치,
색과 글꼴과 간격)을 모아
에이전트가 같은 모양과 행동을 다시 만들게 한다.
보이는 것을 베끼는 일이 저작권이나 트레이드 드레스의 문제를 만들지는 이 문서가
판단할 수 없다.
다만 이름이 법적 안전을 말해 주지 않는다는 점은 분명하다.
README의 책임 있는 사용 항목이 소유하거나 조사할 권한이 있는
소프트웨어에만 쓰라고
한 것이 실질적인 경계이고, 그것을 지키는지는 사용자에게 맡겨져 있다.

### 모드의 보장은 에이전트마다 다르다

클린룸의 읽기 금지는 Claude Code에서는 `--disallowedTools`와 승인 도구로
강제된다고
문서가 설명한다.
그러나 같은 문서와 상태 문서는 다른 에이전트가 채팅에서는 이 제한을 받지 않고
자기 샌드박스를 유지하며, Hermes의 `-z`는 승인을 끄고 Maki의 `-p`는 아예 묻지
않는다고
적는다.
따라서 클린룸이라는 같은 이름의 모드가 어떤 에이전트로 돌리느냐에 따라 다른
뜻이 된다.
문서가 이를 숨기지는 않지만, 모드를 켜는 사용자가 에이전트별 차이를 로드맵
문서까지
찾아가 읽어야 알 수 있다.
Claude Code의 클린룸 채팅 제한도 문서가 아직 실제로 확인하지 않았다고 적은
항목이다.

### 점검 단계의 근거가 약한 곳이 있다

점검이 이 도구의 중심 주장이다.
그런데 웹사이트는 닮은 정도를 재지만 그 정의를 이 문서가 읽은 범위에서는 알
수 없었고,
기록된 실제 실행 가운데 96%는 하나의 웹사이트 복제다.
앱은 빌드만으로 확인했고, 게임은 점검 전에 멈춘 실행이 기록되어 있다.
게임의 자체 시험은 빌드가 스스로 내는 보고이며 관찰하거나 값을 재는
장치가 없다고
문서가 인정한다.
README는 Unity와 Unreal과 Godot의 게임 재구축을 지금 되는 것에 넣었는데,
상태 문서의 실제 실행 기록에서 이를 직접 뒷받침하는 것은 이 문서가 읽은 범위에서
보이지 않았다.
이는 이 문서가 문서를 읽은 한계일 수 있으므로 기능이 안 된다는 말이 아니다.

GN의 bluekai17은 독립적인 전환(cutover)을 앞두고 있어 이 도구가 도움이 될 것
같다고 하면서, 비개발자가 시각적 유사성을 기능적 동일성으로 착각하기 쉽겠다고
지적했다.[^bluekai17]
닮은 정도를 재는 점검이 화면에 보이는 것에 대한 것이라면 이 지적이 정확히 그
한계를 가리킨다.
이 문서는 닮은 정도의 정의를 읽지 못했으므로,
점검이 기능의 동일성까지 재는지는 알지 못한다.

### 속도와 범위가 검증 깊이를 앞선다

만든 지 일주일이 안 된 저장소에 도구 320개, 열여섯 개의 앱 모음, 아홉 개 언어의
README, 네 개 운영체제의 설치 파일이 있다.
상태 문서의 테스트는 2026년 10월 23일 기준 923개이고, 실제 실행 기록은 10월 18일
윈도우 한 대의 세 번이다.
이 속도가 어떻게 나왔는지를 문서는 설명하지 않는다.
다만 `CLAUDE.md`와 `AGENTS.md`와 기여 문서가 AI 에이전트를 같은 규칙으로 일하는
기여자로
다루는 것을 보면, AI가 작업의 많은 부분을 한 것으로 읽힌다.
이것은 이 문서의 추측이다.
이 문서는 코드를 읽거나 빌드하지 않았으므로 품질을 평가하지 못한다.

### 약관의 근거는 저장소 스스로 열어 둔 질문 위에 서 있다

README는 사용이 사용자와 Anthropic 사이의 계약을 따른다고 말한다.
그러나 같은 저장소의 문서는 규모가 커진 뒤에도 이 방식이 허용되는지, 특히 관리형
단계에서 어떻게 되는지를 Anthropic에 확인해야 한다고 적었다.
이 문서는 Anthropic의 약관을 열지 않았으므로 문서의 해석이 맞는지 알 수 없다.
저장소가 인용한 것은 약관의 몇 문장이며,
일반적인 개인 사용을 전제한다는 한도에는
회차 제한이라는 장치로 맞췄다고 한다.
무료 릴리스가 사용자의 구독에 올라타 있다는 점이 이 도구의 비용 구조를 정한다.

### 모방당하는 쪽의 반응은 이 도구의 가장 직접적인 쟁점이다

HN 스레드에서 가장 긴 댓글은 이 도구가 한 걸음 지나쳤다는 항의였다.
mcoliver는 웹사이트나 소프트웨어를 가리키면 한 번에 복사해 자기 상표로 바꿀 수
있다는 점이 비열하고 불쾌하다고 썼다.[^mcoliver]
자신이 직접 만든 서비스 둘이 이미 복사되어 이름만 바뀌고 코드를 도용당했고
책임을 물을 길이 없다고도 했다.[^mcoliver]
그는 누구나 다시 만들 수 있는 것이라 해도 주소를 모으고 데이터 출처를 찾고
셀렉터가 안 될 때의 호출 방법을 알아내는 데 많은 노력이 든다며,
기술의 가치는 설계와 협력사와 의존성의 선택에 있다고 주장했다.[^mcoliver]
이어서 이 도구 저장소의 이슈 1044번을 링크로 남겼다.[^mcoliver-issue]
이 문서는 그 이슈를 열지 않았고, 두 서비스가 정말 복사되었는지도
확인하지 못했다.
이는 한 사람의 주장이지만 README가 다룬 책임 있는 사용 항목이 막으려는 사용자가
대상이 아니라 복사당하는 쪽의 시점에서 어떻게 보이는지를 보여 준다.

같은 스레드의 jaggs는 이 도구가 프로세서를 매우 많이 쓴다고 짧게 적었다.[^jaggs]
근거는 적혀 있지 않고, 이 문서는 코드를 실행하지 않았으므로 부하를
확인하지 못했다.

### 대상 코드를 실행하는 연구가 켜질 때의 동의 방식이 분명하지 않다

런타임 조사가 켜지면 원본을 한 번 실행해 창의 그림과 화면 구조(UI 트리)를
얻는다고
한다(윈도우와 맥).
`SECURITY.md`는 사용자의 동의 없이 대상의 코드가 실행되는 것을 취약점으로 친다.
런타임 조사를 켜는 동의가 어떤 화면에서 어떻게 받아지는지는 이 문서가
읽은 범위에
없었다.
미지의 프로그램을 내려받아 돌리는 일이 이 도구의 정상 사용에 포함되므로,
동의의 형식은 안전의 핵심이다.

## 인사이트

### 제품은 생성이 아니라 점검의 반복이다

사용자가 보는 약속은 원본을 다시 만든다는 것이지만,
제품의 구조는 만드는 단계보다 조사와 점검에 더 많이 놓여 있다.
README가 소개하는 도구 320개는 리버스 엔지니어링 엔진에서 나오고,
결과를 원본과 비교해 맞지 않는 것을 나열하는 점검이
다듬기의 입력이 된다.
이렇게 하면 에이전트가 만드는 일이 막연한 요청에서 측정 가능한 목표(세 개의 화면
너비에서의
차이)를 줄이는 일로 바뀐다.
이 문서의 해석으로는 이 구조가 코딩 에이전트의 가장 큰 약점인 끝났는지를 스스로
판단하지 못한다는 문제를 원본과의 비교로 대신한다.
그 대신 점검의 질이 결과의 질을 정하므로, 닮은 정도의 정의와 점검이 놓치는 것
(눈에 안 보이는 행동, 서버 쪽 논리)이 제품의 실질적인 한계가 된다.

### 보이는 것이 곧 명세가 된다

원본이 비교 대상이면 명세를 따로 쓸 필요가 없고,
공개된 웹사이트나 설치할 수 있는
앱은 누구에게나 명세다.
이 점이 이 도구가 흥미로운 이유이면서 논쟁이 되는 이유다.
화면과 상호작용만으로 복제할 수 있는 제품은 차별성이 데이터, 네트워크 효과, 법적
권리에 있고 인터페이스에 있지 않다는 것을 보여 준다.
이것은 이 문서의 해석이며, 이 도구가 얼마나 정확히 복제하는지는 이 문서가
확인하지
못했다.
복제하기 쉬운 쪽과 어려운 쪽의 경계가 어디에 있는지를 알려면 실제 복제
사례를 점검
기록과 함께 봐야 한다.

### 모드의 이름이 아니라 에이전트별 보장 표를 읽어야 한다

오케스트레이터가 여러 에이전트를 어댑터로 붙이는 구조에서는 보장이 모드가 아니라
어댑터마다 정해진다.
이 저장소는 그 차이를 로드맵의 항목(R2.2)과 상태 문서의 한계 목록에 적어 두었다.
이런 도구를 쓰려면 모드의 이름(클린룸, 자동)보다 내가 쓸 에이전트에서
무엇이 실제로
강제되는지를 먼저 확인해야 한다.
지금 문서로는 Claude Code만이 읽기 금지와 승인이 모두 이 도구의 도구를 거치는
경로이고,
나머지는 부분적이거나 확인되지 않았다.

### 자기 구독 위에 선 무료 배포는 다음 단계에서 비용 구조를 바꾼다

이 도구는 사용자의 수정하지 않은 Claude Code를 돌려 모델 비용을 사용자에게 두고
무료로 배포된다.
README가 다음으로 꼽는 관리형 단계는 회사가 모델 비용을 낸다는 뜻이고,
저장소의 문서는 그 경우 구독이 아니라 API 키와 상업 약관을 써야 한다고 적는다.
그러므로 무료 릴리스와 관리형 단계는 비용을 누가 내느냐가 다른 두 제품이다.
관리형 단계에서 닮은 정도 점검과 여러 회차의 다듬기가 호출 수를 늘리는 구조라면
가격이 어떻게 정해질지가 이 도구의 지속성을 가르는 질문이 된다.

### 결론을 바꿀 관찰

점검에서 닮은 정도를 무엇으로 재는지와 다양한 대상에서의 점검 결과가 공개되면
점검 단계에 대한 의문이 풀린다.
Unity, Unreal, Godot 게임의 재구축이 점검 단계까지 마친 기록이 나오면
README의 지금 되는 것 목록이 뒷받침된다.
Anthropic이 이런 오케스트레이션을 허용하는지에 대한 확인이 나오면 약관 쪽의
열린 질문이
정리된다.
에이전트별 보장 표가 모든 어댑터에서 같은 수준으로 채워지면 모드의 이름이 곧
보장이 된다.
