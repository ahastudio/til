# Agent Compute Engine: 에이전트마다 자격 증명 없는 microVM 한 대를 주는 Google의 설계

원문: [Agent Compute Engine deep dive | Google Cloud Blog](https://cloud.google.com/blog/topics/ai-infrastructure/agent-compute-engine-deep-dive?hl=en)

GN 토론: <https://news.hada.io/topic?id=35917>

## 요약

Google Cloud의 Distinguished Engineer인 Ramanathan Venkatapathy와 Rohit Jnagal이
2026년 10월 23일에 쓴 글이다.
Google 내부의 에이전트 워크로드를 위해 만든 Agent Compute Engine을 설명하고,
이를 Google Cloud 서비스로 낸다고 밝힌다.
이 서비스는 모든 AI 에이전트에 하드웨어로 격리된 microVM 하나를 주며, 컨테이너
수준의 속도를 내고 샌드박스 안에는 자격 증명이 하나도 없다고 한다.
프리뷰는 몇 달 안에 나올 예정이다.

글은 에이전트를 두 부분으로 나눈다.
모델을 부르고 다음 행동을 정하는 하네스(harness, “두뇌”)와, 모델이 요구한 코드와
셸 명령과 브라우저를 실행하는 샌드박스(“손”)다.
Gemini 팀의 목표는 모든 사용자에게 클라우드에서 돌며 작업을 기억하고 자리를 비운
동안에도 일하는 개인 에이전트를 주는 것이었다.
Gemini for business 팀은 기업이 직원용 에이전트를 만들게 하려 했고, 그
에이전트는 Workspace 문서를 읽고 내부 데이터베이스를 조회하고 회사 사설망 안의
서비스를 불러야 했다.
둘 다 각 에이전트에 파일시스템, 언어 런타임, 브라우저, 네트워크가 있는 진짜
컴퓨터가 필요했다.

기존 방식은 각각 한계가 있었다.
전통적인 VM은 하이퍼바이저가 강제하는 격리를 주지만 전체 머신을 부팅하고
설정하므로 시작, 중지, 재개에 몇 초에서 몇 분이 걸린다.
에이전트는 시작, 중지, 재개를 끊임없이 한다.
컨테이너는 호스트 커널을 공유해 빠르고 가볍지만 코딩 에이전트처럼 완전한 격리와
커널 및 루트 수준 제어가 필요한 경우가 있다.
에이전트가 모델의 다음 단계를 기다리며 유휴 상태일 때도 작업 상태를 쥐고
있으므로, 매 턴마다 환경을 없애면 상태가 사라지고 항상 켜 둔 전용 VM은 자원을
낭비한다.
그래서 VM의 격리, 컨테이너의 속도와 밀도, 그리고 에이전트가 일하는지
기다리는지를 아는 시스템이 필요했다고 한다.

이 플랫폼은 Google 안에서 네 가지 워크로드를 받는다.
대화형 소비자와 기업용 에이전트(코드를 즉석에서 쓰고 돌리는 채팅, 대화형 셸,
헤드리스 브라우저 샌드박스), 며칠이나 몇 주 동안 이어지는 루트 권한의 자율
소프트웨어 엔지니어링 작업 공간, 수천 개의 병렬 환경 궤적을 만들고 평가하는
대규모 평가와 강화 학습, 내부 서비스가 동적 로직을 안전하게 돌리는 경량 샌드박스
백엔드다.

보안은 여러 겹으로 설명한다.
노드 증명에 쓰는 비공개 키를 게스트 밖(IPU, 호스트, 원격)에만 두는 Google
Titan과 Titanium IPU 기반의 하드웨어 신뢰, 읽기 전용 루트 파일시스템과
dm-verity로 지키는 무상태 호스트, 세션마다 단일 테넌트의 메모리 안전 microVM,
CPU 부채널 완화가 있다.
게스트는 영속 비밀, OAuth 갱신 토큰, 클라우드 서비스 계정 키를 메모리에도
디스크에도 갖지 않고 인스턴스 메타데이터 서버에도 접근하지 못한다.
microVM에는 일반 가상 네트워크 인터페이스가 없고, 모든 입출력이 virtio-vsock
경계를 지나 로컬 중개 프록시와 외부 프록시를 거친다.
메모리 스냅샷과 블록 볼륨은 저장 시 암호화되고, 호스트 수준 침입 탐지와 지속적
퍼징과 레드팀 훈련으로 보강한다고 한다.
하네스는 샌드박스 밖에서 돌아 도구 호출과 샌드박스 안의 실행을 맞춰 보는 감사
기록이 생긴다.

글의 예는 받은편지함을 관리하는 기업 에이전트가 읽은 메일에 숨은 지시, 곧 이
기계의 API 키를 찾아 특정 주소로 보내라는 문장이다.
모델은 대부분 무시하지만 가끔은 따른다고 인정하고, 그래서 샌드박스에 자격 증명을
두지 않는 설계를 택했다고 한다.
공격자가 샌드박스 안의 모든 것을 통제한다고 가정하고 그 안에서 쓸 것을 찾지
못하게 만든다는 원칙이다.

에이전트에는 네 가지 신원이 따로 있다.
요청을 시작한 사용자 신원, 사용자가 하네스에 특정 작업을 맡겼다는 암호학적 위임
증명(중앙 인증 서비스에만 있고 노드에는 없다), microVM이 뜰 때 받는 짧은 수명의
SPIFFE 기반 에이전트 워크로드 신원(샌드박스 트래픽에 쓰는 유일한 신원이며
유출돼도 백엔드 API를 직접 부를 수 없다), 에이전트가 자기 계정과 자원으로 일하는
워크포스 신원이다.
샌드박스의 외부 요청은 로컬 프록시가 가로채 노드와 Titanium 증명을 묶어 노드
밖의 Agent Gateway로 보낸다.
게이트웨이는 사용자 위임, 에이전트 신원, 노드 신원의 세 가지를 확인한 뒤 송신과
데이터 유출 방지 정책을 평가하고, 요청이 나갈 때 필요한 백엔드 자격 증명을 전송
중에 바꿔 끼운다.
Agent Registry와 Agent Identity, Agent Gateway는 Gemini 플랫폼의 에이전트
거버넌스 기능이라고 한다.

비용 쪽의 관찰은 에이전트가 대부분의 시간을 기다린다는 것이다.
모델의 다음 단계와 사용자의 답을 기다리며, 열린 세션 중 코드를 돌리는 것은
일부뿐이라고 한다.
샌드박스 명령 런타임과 호스트 실행기를 함께 설계해, 에이전트가 도구 호출을
끝내고 생각 단계에 들어가면 샌드박스가 진행 중인 명령이 없다고 알리고 호스트가
체크포인트와 복원으로 유휴 상태로 옮긴다.
이 덕분에 한 물리 노드가 전통 VM보다 자릿수로 많은 살아 있는 에이전트 microVM을
둔다고 한다.
복제, 스냅샷과 포크, 되감기와 롤백도 지원한다.
같은 기본 이미지와 Python 런타임과 브라우저를 도는 수백 개의 에이전트가 메모리
복사본을 따로 갖지 않도록 미리 데워 둔 스냅샷을 DAX와 Copy-on-Write 메모리
복제로 물리 메모리에 직접 매핑하고, 각 에이전트가 바꾼 작은 개인 페이지만 따로
할당한다.

저장소는 에이전트가 쓰는 데이터를 셋으로 나눈다.
임시 스크래치는 버려지는 오버레이에, 기본 이미지와 도구 체인과 공유 패키지
캐시는 읽기 전용으로 공유하며(팀은 Google Cloud Storage의 FUSE 볼륨도
마운트한다), 사용자의 작업 상태와 저장된 산출물만 지속 상태로 남긴다.
기본 제공은 Hyperdisk이며 저장과 전송 모두 암호화된다고 한다.
기업 고객에게는 Agent Gateway와 Private Service Connect, VPC Service Controls
기반의 온디맨드 사설 네트워크 연결로, 관리자가 에이전트가 닿을 수 있는 VPC
엔드포인트와 승인된 Workspace API와 외부 도메인 허용 목록을 선언한다.
수요는 시간대별로 서로 겹치지 않으므로 전 세계 정책 인식 스케줄링, 지연 가능한
작업의 한가한 시간대 배치, 모든 제품이 공유하는 대체 가능한 하드웨어 풀로 같은
용량에서 더 많은 에이전트를 받는다고 한다.

글이 꼽은 세 가지 문제는 이렇다.
모델은 실수하므로 샌드박스가 공격자가 쓸 것을 쥐고 있으면 안 된다.
에이전트는 대부분 기다리므로 유휴 에이전트는 거의 공짜여야 하고 사람이 알아채기
전에 깨어나야 한다.
에이전트는 기억할수록 쓸모 있으므로 작업 공간이 턴 사이, 며칠 사이, 운영체제
버전 사이에 살아남아야 한다.
Google Cloud 서비스로서는 개발자가 환경의 이미지, 신원, 네트워크 접근, 수명을
제어하고 Google이 하부 플릿을 관리하며, 코딩과 평가와 강화 학습 파이프라인은
환경을 한 번 스냅샷해 메모리가 중복 제거된 수천 개의 복사본으로 병렬 포크할 수
있다고 한다.

## 분석

### 세 가지 요구가 한꺼번에 있다는 정의가 설계를 끌고 간다

글의 출발점은 에이전트 실행 환경이 VM의 격리, 컨테이너의 속도와 밀도, 일하는
중인지 기다리는 중인지를 아는 인식을 모두 요구한다는 정의다.
VM은 첫째만, 컨테이너는 둘째만 주고, 셋째는 어느 쪽도 주지 못한다는 것이다.
이 정의 덕에 이후의 모든 기능이 한 줄로 이어진다.
인식이 있으니 유휴 상태를 체크포인트로 내릴 수 있고, 같은 이미지를 공유하니
메모리를 중복 제거할 수 있고, 상태를 쪼개 저장하니 디스크 슬롯과 용량 문제를
피한다.
따라서 이 글은 새 기술의 나열이 아니라 한 정의에서 나온 설계 결과들을 보여 주는
구성이다.

### 샌드박스에서 비밀을 빼는 설계가 보안의 중심이다

글은 모델이 가끔 악성 지시를 따른다는 점을 숨기지 않고, 지시를 거부하게 만드는
방어보다 따르더라도 쓸 것이 없게 만드는 방어를 택한다.
이를 위해 신원을 넷으로 나누고, 샌드박스에는 유출돼도 백엔드를 직접 부를 수 없는
워크로드 신원만 둔다.
진짜 자격 증명은 게이트웨이가 요청이 나가는 순간에만 끼워 넣는다.
이 구조에서 비밀이 있는 곳은 샌드박스가 아니라 게이트웨이와 중앙 인증 서비스다.
위험이 사라지는 것이 아니라 그 두 곳으로 모인다.

### 경제성의 근거는 대기 시간과 수요의 어긋남이다

글이 내세우는 비용 논리는 에이전트 세션이 대부분 대기 상태라는 측정과, 수요
곡선이 제품마다 다른 시간에 정점을 찍는다는 관찰이다.
첫째는 유휴 비용을 거의 없애는 체크포인트의 이유이고, 둘째는 평가와 강화 학습을
한가한 시간에 채우는 이유다.
두 근거 모두 Google 내부 플릿의 관찰이다.
외부 고객이 같은 분포를 가질지는 글에서 알 수 없다.
GN에서 ghboo0927는 ChatGPT에 에이전트 작업 하나를 시켜 시간을 재 봤더니 4분 29초
가운데 도구가 실제로 일한 시간은 20~40%였고 나머지는 모델 응답과 승인 클릭을
기다리는 시간이었다고 했다.[^ghboo0927]
그래서 글이 꼽은 세 문제 가운데 대기 문제가 비용에서 가장 클 것이라고 짚었다.
한 번의 측정이므로 일반화할 수는 없지만, 글의 관찰과 같은 방향의 사례다.

## 비평

### 핵심 주장이 수치 없이 서술돼 있다

글에는 재개 지연, 노드당 에이전트 수, 메모리 중복 제거율, 비용의 숫자가 하나도
없다.
컨테이너 속도라는 말은 몇 밀리초를 뜻하는지, 한 노드가 전통 VM보다 자릿수로 많은
microVM을 둔다는 말은 몇 배를 뜻하는지 알 수 없다.
기존 VM은 몇 초에서 몇 분이라고 적으면서 이 서비스의 시간은 적지 않는다.
따라서 이 글의 성능 주장은 방향은 설득력이 있어도 확인할 수 없다.
프리뷰가 몇 달 뒤라서 외부 고객이 직접 재볼 수 있는 시점도 아직 오지 않았다.

### 자격 증명을 빼도 데이터는 빠져나갈 수 있다

글의 예는 숨은 지시가 API 키를 찾아 보내라고 하는 경우이고, 방어는 키가
샌드박스에 없다는 점이다.
그러나 같은 에이전트가 읽은 메일 내용이나 문서 자체를 허용된 경로로 내보낼 수
있다면 키 없이도 정보는 유출된다.
글은 게이트웨이가 송신과 데이터 유출 방지 정책을 평가한다고 말하지만, 이 정책이
어떤 기준으로 정해지고 얼마나 막아 주는지는 설명하지 않는다.
허용된 도메인이나 승인된 API로 나가는 정보의 정당성은 자격 증명이 아니라 정책의
문제다.
이 문서는 정책의 실제 동작을 확인하지 못했다.

### 신뢰의 중심이 게이트웨이와 Google의 하드웨어로 옮겨 간다

설계가 의존하는 것은 Titan, Titanium IPU, Agent Gateway, Agent Identity, Agent
Registry 같은 Google 플랫폼의 구성요소다.
게이트웨이는 사용자 위임과 에이전트 신원과 노드 신원을 확인하고 자격 증명을
끼우는 유일한 지점이므로, 이곳의 오류는 모든 에이전트에 영향을 준다.
글은 이 구성요소 가운데 무엇이 Google Cloud 고객에게 어떤 형태로 제공되는지
말하지 않는다.
개발자가 이미지와 신원과 네트워크와 수명을 제어한다고만 적는다.
가격이나 다른 클라우드와의 호환성, 이전 방법도 없다.

### 내부 규모의 경험을 외부에 그대로 옮긴다

글은 Gemini, Gemini for business, Antigravity, 내부 평가와 강화 학습이라는 서로
다른 네 워크로드를 한 플릿에 얹어 효율을 얻었다고 한다.
이 효율은 수요가 서로 다른 시간에 정점을 찍는 큰 내부 고객들이 한 풀을 나눠 쓰기
때문에 나온다.
고객 한 곳이 같은 효과를 얻으려면 자기 워크로드가 고르게 분포해야 하고, 그렇지
않으면 Google이 풀 전체에서 얻는 이득의 일부만 받는다.
글은 외부 고객의 가격에 이 이득이 얼마나 반영되는지 말하지 않는다.

## 인사이트

### 샌드박스를 믿지 않고 비밀을 두지 않는 방식은 최소 권한의 새 형태다

전통적인 최소 권한은 프로세스에 필요한 권한만 주는 것이었다.
이 글은 한 걸음 더 나가 샌드박스에는 권한 자체가 아니라 신원의 증거만 두고,
권한은 밖의 중개자가 요청 시점에 붙인다.
이는 에이전트가 모델의 출력에 따라 예측할 수 없는 일을 한다는 사실에서 나온
설계다.
같은 구조는 비밀을 쥔 중개자에게 요청을 보내고 중개자가 대신 서명하는 오래된
방식과 닮았지만, 이것은 이 문서의 비유다.
그 구조의 대가는 중개자가 병목이자 단일 장애점이 된다는 것이다.
에이전트 수가 늘수록 게이트웨이의 정책 평가와 감사 로그가 지연과 비용의 중심이
된다.

### 대기 비용을 없애면 가격 모델이 사용 시간에서 활동 시간으로 옮겨 간다

에이전트가 대부분 기다린다면, 열려 있는 시간으로 요금을 매기는 모델은 낭비를
사용자에게 청구하는 셈이다.
글이 유휴 세션이 거의 영점의 활성 컴퓨트로 내려가고 유휴 VM에는 돈을 내지
않는다고 말하는 이유다.
이것이 실제 가격표가 되면 샌드박스를 파는 다른 서비스도 같은 방식으로 따라올
압력을 받는다.
그 압력이 어느 쪽으로 가는지, 곧 체크포인트 비용을 누가 부담하는지는 글에 없다.
이 해석은 이 문서의 것이다.

### 하네스와 샌드박스의 분리가 감사 기록을 만든다

글은 하네스가 샌드박스 밖에서 돌므로, 모든 도구 호출과 샌드박스 안의 실제 실행을
대응시킨 결정적인 감사 기록이 생긴다고 쓴다.
에이전트의 행동을 사후에 설명해야 하는 조직에게는 이 대응이 보안만큼 중요할 수
있다.
다만 이 기록이 맞는지는 하네스가 보낸 명령과 실제 실행이 일치하는지 검증하는
층에 달려 있고, 글은 그 층을 설명하지 않는다.

### 이 글을 읽는 방법

이 글은 Google이 자사 플랫폼을 설명한 설계 소개이며, 수치와 가격과 고객 제공
범위가 없다.
오늘 할 일은 자기 에이전트가 샌드박스 안에서 어떤 자격 증명과 네트워크 접근을
갖고 있는지 목록으로 만들고, 그것이 유출돼도 피해가 적도록 밖의 중개자로 옮길 수
있는지 따져 보는 것이다.
이 글의 주장을 가를 관찰은 두 가지다.
프리뷰에서 재개 지연과 노드당 에이전트 수와 요금이 공개됐을 때 글의 컨테이너
속도와 자릿수 차이라는 표현이 어떤 수치가 되는지, 그리고 자격 증명이 없는
샌드박스에서도 에이전트가 읽은 데이터를 허용된 경로로 내보내는 일을 게이트웨이
정책이 어디까지 막는지다.
둘 다 이 글에는 없다.
