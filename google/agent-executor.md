## 소개

AX는 저장소 설명대로 “Google의 개방형 에이전트 오케스트레이션 런타임”이다.
Apache 2.0 라이선스이며 Go로 작성됐고, 2026년 3월 30일에 저장소가 만들어져 9월 25일 기준 스타 10,709개, 포크 524개다.

이 프로젝트의 자기소개는 반년 사이에 크게 바뀌었다.
6월에 공개됐을 때 README는 AX를 이벤트 로그로 실행 상태를 유지하고 중단된 지점부터 재개하는 분산 에이전트 실행기로 소개했고, 이 문서의 “초기 설계” 절이 그 내용을 담고 있다.
9월에 다시 쓴 README는 AX를 클러스터에서 수십억 개의 자율 에이전트 작업을 돌리는 고처리량 선언형 오케스트레이터로 소개한다.
작업 공간과 모델 명세로 에이전트 작업을 선언하면 AX가 그것을 샌드박스에 넣고 작업 공간을 연결해 대규모로 돌리는 것을 돕는다는 것이며, Kubernetes를 써 봤다면 `ax`가 비슷하게 느껴질 것이라고 적는다.
샌드박스 실행은 Agent Substrate가 맡는다.

README 첫머리에는 경고가 붙어 있다.
핵심 개념, 프로토콜, 명세를 아직 다듬는 중이며 안정 릴리스 전에 큰 호환성 파괴 변경을 들여올 가능성이 높다는 것이다.

홈페이지 agentexecutor.io는 동기를 이렇게 설명한다.
에이전트는 1분 동안 격렬하게 일한 뒤 모델 응답이나 도구 응답이나 사람의 승인을 기다린다.
무상태 마이크로서비스나 예측 가능한 배치 작업을 위해 만든 기존 오케스트레이터는 쉬는 샌드박스를 계속 켜 두면 비용이 감당되지 않고, 1초 안의 중단과 재개도 기본으로 지원하지 않는다.
AX는 Google DeepMind의 에이전트 런타임 연구와 대규모 격리, 재개, 스케줄링 경험을 바탕으로 만들어지는 에이전트 실행 전용 선언형 컨트롤 플레인이며, Agent Substrate에 크게 기대면서 그 위에 에이전트용 추상화와 생성형 런타임 구성 요소를 더한다고 적는다.

## 현재 구조

### 선언하는 자원

모든 자원은 `ax.io/v1alpha1` 매니페스트로 표현되고 명령 하나로 적용되며, atespace라는 범위 안에 산다.
기본 atespace는 `default`다.

| 자원        | 하는 일                                                                                         |
| ----------- | ----------------------------------------------------------------------------------------------- |
| `Task`      | 격리된 실행의 가장 작은 단위, 이미지와 명령, CPU·메모리 요청과 한도, 환경 변수, 작업 공간 참조  |
| `Workspace` | Git 저장소 클론, MCP 서버와 레지스트리, 스킬 레지스트리를 선언해 모든 샌드박스에 미리 준비      |
| `Model`     | 플랫폼 자신이 쓸 모델 설정, 제공자·모델 식별자·생성 파라미터·API 키가 든 Kubernetes 시크릿 참조 |
| `Gateway`   | 허용 목록 기반 네트워크 정책과 요청에 자격 증명 주입, 홈페이지에만 소개됨                       |

`Task`는 일부러 작게 만든 단위다.
개념 문서는 에이전트가 끝까지 도는 하나의 프로세스가 아니라 평생 계획하고 위임하고 재시도하고 일을 펼치는 존재이며, AX는 그 모양을 모델링하려 하지 않는다고 설명한다.
만들고 격리하고 중단하고 버리기 싼 원시 요소 하나를 주고, 에이전트가 필요한 만큼 조합하게 한다는 것이다.
태스크 하나가 작업 전체일 수도 있고, 에이전트가 문제를 쪼개며 만든 큰 태스크 트리의 뿌리일 수도 있다.

`Workspace`의 바인딩에는 `goal`을 붙일 수 있다.
태스크가 필요로 하는 환경을 평범한 말로 적으면, 첫 부팅 때 러너가 그 목표를 에이전트에게 넘겨 툴체인이나 의존성 설치 같은 준비를 끝낸다.
README 예시의 목표는 “Go 툴체인을 쓸 수 있고 소스에서 빌드되어 있게 하라”다.

`Model`에 대해 개념 문서는 “Model은 모델이 아니다”라고 적는다.
이름 붙은 모델 설정이며, 자원으로 선언해 두면 키 교체나 모델 버전 고정이 모든 태스크 정의를 뒤지는 대신 `ax apply` 한 번이 된다.
`ax get models`의 예시 출력에서 기본 모델은 제공자 `google`의 `gemini-3.8-flash`다.

README의 “Why?” 절은 AX가 주는 것을 “세 가지 작은 원시 요소”, 곧 `Task`, `Workspace`, `Model`로 설명하고, 홈페이지는 `Gateway`를 더해 “네 가지”라고 쓴다.

### 태스크 수명 주기

`status.phase`는 `Running`, `Suspended`, `Failed`, `Terminating` 같은 한 단어 요약이고, 세부는 조건(condition)에 담긴다.
`WorkspaceReady`는 모든 작업 공간 준비가 끝나면 True가 되어 그대로 유지되고, `Ready`는 태스크가 돌고 있으면서 `WorkspaceReady`가 True일 때 True이며 기다려야 할 것은 이것이다.
태스크를 중단하면 `Ready`가 이유 `TaskSuspended`와 함께 False가 되고, 재개하면 돌아온다.
삭제하면 컨트롤러가 샌드박스를 걷어 내는 동안 `Terminating`에 머물다가 기록이 사라지며, `ax delete`는 그때까지 기다린다.

### 컨트롤 플레인

설계 문서는 수백만 개의 짧게 사는 태스크를 Kubernetes CRD로 저장하면 etcd가 한계를 넘는다고 설명한다.
저장 용량이 한 자릿수 GB로 제한되고, 쓰기 속도가 병목이 되며, 컨트롤 플레인이 느려진다는 것이다.
그래서 AX는 상태를 Redis에 두고, API 서버와 수평 확장되는 컨트롤러 풀 사이의 작업 큐로 Redis Streams를 쓴다.

```text
ax apply -f task.yaml
        │
        ▼
    ax-server (gRPC API, /healthz)
        │ 저장 후 이벤트 발행
        ▼
      Redis (Task 해시, 이벤트 스트림, PubSub)
        │ XREADGROUP
        ▼
    ax-controller (수평 확장 워커)
        │ gRPC Control API
        ▼
    Agent Substrate (atespace 준비, 액터 생성·활성화, 워커 배정)
```

| 바이너리         | 역할                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------ |
| `ax`             | 개발자 CLI, 매니페스트 적용, 자원 조회와 감시, 클러스터로의 터널                     |
| `ax-server`      | 8080 포트의 무상태 gRPC API, 매니페스트 검증, Redis 저장, 이벤트 발행                |
| `ax-controller`  | 조정 워커, Redis 스트림을 소비해 Substrate에 atespace와 액터를 준비, 복제본으로 확장 |
| `ax-task-runner` | 모든 태스크 컨테이너의 진입점, 작업 공간 준비, 메타데이터 제공, 에이전트 명령 실행   |

API는 `ax.v1alpha1.AX` gRPC 서비스이며 태스크, 작업 공간, 모델마다 Get, List, Update, Delete를 두고, 태스크에는 `SuspendTask`, `ResumeTask`, 서버 스트리밍 `WatchTask`가 더 있다.

홈페이지는 Substrate 덕분에 모든 태스크가 가벼운 액터로 돌아 클러스터당 수십억 개의 동시 에이전트 세션까지 오케스트레이터 한계 없이 확장되고, 모델 응답이나 도구 호출이나 사람의 응답을 기다리는 쉬는 에이전트는 체크포인트되어 중단된 뒤 1초 안에 콜드 스타트 없이 돌아오며, 수십 개의 태스크가 워커 자원을 나눠 써서 에이전트가 실제로 생각하고 코드를 돌릴 때만 비용을 낸다고 적는다.

## 사용법

AX는 모든 태스크를 Agent Substrate 위의 샌드박스 액터로 스케줄하므로, AX를 배포하기 전에 클러스터에 Substrate가 돌고 있어야 한다.
Kubernetes 클러스터, Go와 `kubectl`, `ko`, 클러스터가 받아 올 수 있는 컨테이너 레지스트리가 필요하다.
Substrate는 `ate-system` 네임스페이스에 설치되고 `api.ate-system.svc.cluster.local:443`에 Control API를 노출하며, AX는 그 주소를 찾는다.

```bash
kubectl get svc api -n ate-system              # Substrate Control API 확인
go install github.com/google/ax/cmd/ax@latest  # CLI 설치
make deploy AX_IMAGE_REPO=<your-registry>      # Redis와 컨트롤 플레인을 ax-system에 배포
```

CLI는 gRPC로 컨트롤 플레인과 이야기하며, 일부러 `kubectl` 모양으로 만들어졌다.

```bash
ax apply -f examples/task.yaml       # Task, Workspace, Model을 한 파일로
ax get tasks
ax watch task task123                # 단계와 조건 변화를 실시간으로
ax ssh task123 -- ls -la /workspace  # 샌드박스 안에서 명령 실행 (spec.debug: true 필요)
ax suspend task task123              # 액터 상태를 체크포인트하고 멈춤
ax resume task task123               # 멈춘 곳에서 다시 시작
ax delete task task123
ax --context=dev-cluster get tasks   # kubectx를 따르며, 전환 없이 다른 컨텍스트도 지정
```

`-a`는 atespace, `-n`은 AX가 설치된 네임스페이스(기본 `ax-system`), `--server`는 자동 탐지를 건너뛰고 컨트롤 플레인 주소를 직접 준다.
홈페이지의 데모는 태스크 안에서 `notes.txt`를 만든 뒤 중단하고 재개해도 파일이 그대로 있는 것을 보여 준다.

## 로드맵

로드맵은 다섯 갈래다.

1. 핵심 명세 안정화: `Task`의 수명 주기, 토큰과 시간 예산, 승인 정책, `Workspace`, `Model`, 그리고 격리 백엔드와 시스템 호출 제약과 보안 프로필을 다룰 `Sandbox`와 `SandboxConfig`의 스키마를 굳힌다.
2. 액터 구조: 새 Substrate Actor API로 옮기고, 작업 공간 준비를 별도 설정 액터로 떼어 내 자격 증명과 이그레스를 준비 단계에만 주는 최소 권한 정책을 적용하며, 쉬는 태스크를 감지해 자동으로 중단하고, 실행 중이거나 중단된 태스크를 메모리와 파일시스템 상태째 여러 병렬 태스크로 분기한다.
3. 에이전트 환경: 목표 기반 작업 공간 준비가 저장소를 살펴 툴체인과 MCP 서버와 스킬을 스스로 찾게 하고, 내장 부트스트랩과 코딩 에이전트 하네스를 분리해 사용자 정의를 허용한다.
4. 네트워킹, 신원, 거버넌스, 관측성: 모든 태스크에 SPIFFE 신원을 발급해 mTLS를 쓰고, MCP와 스킬 레지스트리 연동과 접근 통제와 예산 가드레일과 감사 준수에 대한 Google 플랫폼 요건을 맞추며, 러너 계층에서 OpenTelemetry 지표와 추적과 에이전트 궤적을 자동으로 수집한다.
5. 문서: Substrate와의 역할 분담, 사용자 정의 이미지와 러너 가이드를 쓴다.

## 초기 설계

이 절은 2026년 6월 공개 당시 README를 바탕으로 쓴 내용이다.
지금 README와 설계 문서에는 여기의 `exec`, `serve`, `fork`, `trace` 명령이나 이벤트 로그와 단일 라이터 구조에 대한 설명이 남아 있지 않다.

### 기능

당시 README는 AX(Agent eXecutor)를 신뢰성, 안전성, 커스터마이징 가능성, 효율성을 설계 목표로 내세운 분산 에이전트 런타임으로 소개했다.
에이전트 루프의 조율과 실행 관리를 담당하며 로컬 또는 원격 액터와 통신하고, MCP와 A2A(Agent to Agent) 프로토콜을 기본 지원한다고 적었다.

자동 복구(automatic recovery)와 재개(resumption)가 핵심 기능이다.
장애나 중단이 발생해도 실행 상태를 이벤트 로그 기반으로 유지하므로 중단된 지점부터 재개할 수 있다.

단일 라이터 아키텍처(single-writer architecture)로 일관된 상태 관리를 보장한다.
모든 사용자·에이전트 호출을 공통 컨트롤러가 조율하므로 완전한 감사 추적(audit trail)과 관찰 가능성(observability) 훅이 제공된다.

모델 독립성이 설계 원칙 중 하나다.
사용자가 LLM과 계획 로직을 직접 가져오면 AX는 실행, 지속성, 조율을 담당한다.
특정 LLM 제공자에 종속되지 않는다.

Kubernetes를 1급 지원한다.
Agent Substrate를 통해 프로덕션 환경의 대규모 배포에 적합하도록 설계되었다.

### 아키텍처

```text
클라이언트 → 라우터 → AX 컨트롤러
                          ├── executor
                          ├── event log
                          └── registry
                      ↕
                원격 에이전트 및 도구
                      ↕
            스킬과 내장 도구가 있는 환경
```

컨트롤러, 스킬, 도구, 에이전트가 독립적으로 실행되는 분산 구조다.
이벤트 로그가 내구성 있는 실행 상태의 원천이 된다.

### CLI

```bash
go install github.com/google/ax/cmd/ax@latest
ax --help
```

주요 명령어:

- `exec` — 새로운 실행 시작 또는 기존 대화 재개
- `serve` — gRPC 서버로 컨트롤러 시작
- `fork` — 특정 체크포인트에서 새 이벤트 로그로 분기
- `trace` — 웹 UI에서 실행 추적 시각화

## 라이선스 및 상태

Apache 2.0 라이선스.
6월에는 “active early development” 단계라고 적었고, 지금은 안정 릴리스 전에 큰 호환성 파괴 변경이 있을 것이라고 경고한다.

## 분석

### 에이전트 신뢰성 문제를 런타임 레이어에서 해결

대부분의 에이전트 프레임워크는 LLM 호출과 도구 실행을 어떻게 연결할지에 집중한다.
AX는 다른 문제를 다룬다. 에이전트가 실패했을 때 어떻게 복구할 것인가.
장시간 실행되는 에이전트 태스크에서 중간 실패는 불가피하다.
서버 재시작, 네트워크 오류, API 타임아웃이 발생하면 기존 프레임워크는 처음부터 다시 시작해야 한다.

이벤트 로그 기반 상태 관리는 데이터베이스 WAL(Write-Ahead Log)과 같은 원리다.
모든 상태 변경이 로그에 기록되고, 장애 발생 시 로그를 재생해 상태를 복원한다.
이것은 에이전트를 단순한 스크립트가 아닌 내구성 있는 프로세스로 만드는 설계다.

### Kubernetes 네이티브 설계의 의미

에이전트를 Kubernetes에서 운영하는 것은 아직 초기 단계다.
AX가 Kubernetes를 1급 지원으로 설계한 것은 에이전트가 클라우드 네이티브 인프라의 일급 구성요소가 될 것을 전제한 설계다.
스케일 아웃, 장애 격리, 롤링 업데이트가 에이전트에도 적용된다는 의미다.

MCP와 A2A 프로토콜 지원은 에이전트 생태계의 상호운용성을 겨냥한다.
특정 프레임워크에 종속되지 않고 다양한 에이전트와 도구를 조합할 수 있는 기반이다.

### 실행기에서 오케스트레이터로 정체성을 바꿨다

6월의 AX가 풀려던 문제는 에이전트 하나가 실패했을 때 어떻게 복구하느냐였다.
이벤트 로그와 체크포인트와 분기가 그 답이었다.
9월의 AX가 풀려는 문제는 에이전트 수십억 개를 어떻게 싸게 돌리느냐다.
작게 만든 태스크, 쉬는 동안의 중단, 워커 자원의 다중화가 그 답이다.

이 전환은 단순한 기능 추가가 아니라 관점의 이동이다.
하나의 에이전트 실행을 내구성 있는 프로세스로 만드는 일은 에이전트 프레임워크의 관심사에 가깝고, 수많은 에이전트 작업을 격리하고 배치하는 일은 클러스터 스케줄러의 관심사다.
AX는 앞의 역할을 내려놓고 뒤의 역할을 택했으며, 그래서 CLI의 모양도 `exec`와 `trace`에서 `apply`와 `get`과 `watch`로 바뀌었다.
개념 문서가 AX는 에이전트의 모양을 모델링하려 하지 않는다고 명시한 것은, 에이전트 내부의 논리를 다시 에이전트에게 돌려준다는 선언이다.

### etcd를 버리고 Redis를 택한 것이 규모 주장의 근거다

AX의 CLI는 `kubectl`처럼 생겼지만 자원은 Kubernetes CRD가 아니다.
설계 문서가 밝히는 이유는 처리량이다.
수백만 개의 짧게 사는 태스크를 CRD로 저장하면 etcd의 저장 한도와 쓰기 속도가 병목이 된다.
HN에서 ahmedtd도 이 객체들의 처리량이 kube-apiserver와 etcd의 조합에는 너무 높으며, Substrate는 액터 스케줄링과 재개의 뜨거운 경로에서 CRD를 전혀 쓰지 않는다고 설명했다.[^ahmedtd]

이 선택이 “클러스터당 수십억 개”라는 주장을 가능하게 한다.
Kubernetes는 파드 수천 개에서 수만 개를 다루도록 설계됐고, 에이전트 세션 수십억 개는 그 규모를 몇 자릿수 넘는다.
상태를 Redis에 두고 Substrate의 가벼운 액터로 실행을 맡기면, Kubernetes는 AX의 컨트롤 플레인과 Substrate를 올려 두는 기반으로만 쓰이고 태스크 하나하나는 Kubernetes 객체가 되지 않는다.
HN에서 motoboi가 이것을 Kubernetes를 위한 가상 스레드라고 부른 것[^motoboi]이 이 구조를 잘 요약한다.
운영체제 스레드 위에 가벼운 스레드를 수백만 개 올리듯, Kubernetes 파드 위에 가벼운 액터를 수십억 개 올리는 것이다.

이것을 런타임 레이어에서 기본으로 제공하는 것은 의미 있는 설계 선택이다.

GeekNews에서 eajrezz는 구글 것은 내부에서 십수 년 쓴 것을 오픈 소스로 푼 게 아니면 언제 없어질지 몰라 못 쓸 것 같고, 특히 AI 관련된 것은 1년 뒤에도 유지될지 모르겠다고 적었다.[^eajrezz]

프로덕션 환경에서 에이전트 인프라의 핵심 런타임으로 채택하기에는
프로젝트의 장기 유지보수 가능성에 대한 판단이 필요하다.

### Kubernetes를 전제로 한 복잡도는 작은 사용 사례를 밀어낸다

Kubernetes 네이티브 설계와 분산 아키텍처는 소규모 사용 사례에는 과도한 복잡도일 수 있다.
단순한 에이전트 태스크를 위해 Kubernetes 클러스터를 운영하는 것은 비용 대비 효율이 낮다.
어떤 규모와 복잡도의 에이전트 태스크에서 AX가 적합한지에 대한 명확한 가이드가 필요하다.

### `kubectl` 모양이지만 Kubernetes 생태계에는 들어가지 않는다

HN에서 zactato는 CLI의 사용 경험이 `kubectl`과 거의 같은데 실제로는 Kubernetes CRD 위에 만들어지지 않았다는 점에 혼란스러워했다.
Kubernetes 위에서 도는 백엔드가 있지만 기본적으로 통합되어 있지 않고, `kubectl apply` 대신 `ax apply`를 써야 하므로 Argo CD 같은 도구로 자원을 관리할 수 없다는 것이다.[^zactato]
앞서 분석한 대로 이 선택에는 처리량이라는 분명한 이유가 있다.
그러나 사용자가 치르는 대가도 분명하다.

`kubectl` 모양의 CLI는 Kubernetes 사용자에게 익숙함을 약속하지만, 그 익숙함은 명령어의 모양에서 끝난다.
GitOps 도구, 정책 엔진, RBAC, 감사 로그처럼 Kubernetes 생태계가 CRD 위에 쌓아 온 것들은 AX 자원에 닿지 않는다.
mmq는 몇 달 전 이 프로젝트를 보면서 Kubernetes가 이미 서비스와 배치 작업, 갱 스케줄링, GPU 워크플로의 추상화를 주는데 왜 Kubernetes를 쓰지 않고 추상화를 다시 만드는지 이해하지 못했다고 적었다.[^mmq]
“Kubernetes를 써 봤다면 비슷하게 느껴질 것”이라는 README의 문장은, 비슷하게 느껴지는 만큼 같은 도구가 통하지 않는다는 사실을 가린다.

### “Google의” 프로젝트라는 이름과 실제 뒷받침 사이에 간극이 있다

HN에서 Mond_는 이런 공개물은 대부분의 Google 고위층이 들어 보지도 못했을 것이며, Google 직원이 만들었다고 해서 Google이나 DeepMind나 GCP의 전폭적 지원을 뜻하지는 않는다고 봤다.[^Mond_]
sheepscreek는 홈페이지의 문장을 인용하며 이것이 Google 안에서 쓰이는 것이 아니라 몇몇 Google 직원의 경험에서 나온 오픈 소스 이니셔티브로 보인다고 했고[^sheepscreek], mukundesh는 페이지와 도메인 어디에도 Google이 언급되지 않는 것이 놀랍다고 적었다.[^mukundesh]
반론도 있었다.
저장소가 Google의 GitHub 조직에 있고 제목도 거기서 왔다는 지적[^Stagnant], 4개월 전 Google Cloud 블로그에 공식 발표가 있었다는 지적[^dudus], 팀이 꽤 있는 GCP 쪽 작업으로 보인다는 관찰[^mynegation]이다.

이 논쟁은 앞의 지속성 우려와 같은 뿌리를 갖는다.
홈페이지가 “연구에서 태어나 프로덕션을 위해 만들어졌다”고 쓰면서 Google 안에서 무엇을 돌리고 있는지는 말하지 않는다면, 사용자는 이 프로젝트가 몇 명의 열정에 기대는지 조직의 약속에 기대는지 판단할 근거가 없다.
GeekNews에서 kaydash가 하둡의 역사를 떠올리며, 구글이 10년쯤 쓰고 더는 쓰지 않을 무렵 논문으로 발표하고 끝냈지만 그때부터가 빅데이터 분산 처리 오픈 소스의 전성기였다고 적은 것[^kaydash]은, 내부에서 오래 검증된 뒤 공개된 기술과 공개부터 하고 검증을 기다리는 기술의 차이를 짚는다.

### 인체공학을 강조하면서 진입 조건은 가장 무겁다

홈페이지는 AX가 인체공학, 빠른 반복, 즐거운 작업 흐름에 타협 없이 집중했다고 말한다.
HN에서 alembic_fumes는 같은 페이지의 그 문장과 README 빠른 시작의 “Kubernetes 클러스터가 필요하다”를 나란히 놓았다.[^alembic_fumes]
dabeeeenster는 컨트롤 플레인을 배포하려면 Kubernetes 클러스터가 필요하다는 대목에서 웃으며 떠났다.[^dabeeeenster]

실제 진입 조건은 이보다 더 무겁다.
Kubernetes 클러스터 위에 Agent Substrate를 먼저 설치하고, `ko`와 컨테이너 레지스트리를 갖추고, Redis와 컨트롤 플레인을 직접 빌드해 배포해야 한다.
연구자가 재현 가능한 샌드박스를 대량으로 띄우는 용도라면 이 비용은 감당할 만하지만, 에이전트 몇 개를 격리해 돌려 보고 싶은 개발자에게는 과하다.
HN에서 Lethalman이 Kubernetes Job과 무엇이 다르냐고 묻자 srcreigh가 Job은 안전한 런타임에서 돌지 않고 동적 제로 트러스트 권한을 주지 않으며 하네스를 500ms에 복원하는 것은 새 Job을 만드는 것보다 훨씬 빠르다고 답한 것[^srcreigh]처럼, 이 도구의 이점은 규모와 보안이 필요한 곳에서만 드러난다.

### 원시 요소의 수조차 문서마다 다르다

README는 세 가지 원시 요소를, 홈페이지는 `Gateway`를 더한 네 가지를 말한다.
README와 설계 문서의 API 목록에는 `Gateway`가 없고, 로드맵의 핵심 명세 목록에도 없다.
홈페이지가 앞서 가는 것인지, 문서가 뒤처진 것인지는 알 수 없다.

사소해 보이지만 선언형 시스템에서는 사소하지 않다.
선언형 도구의 약속은 무엇을 선언할 수 있는지가 명확하다는 것이고, 네트워크 정책처럼 보안의 핵심인 자원이 문서마다 있다가 없다가 하면 사용자는 그것을 믿고 설계할 수 없다.
README 첫머리의 호환성 파괴 경고와 함께 읽으면, 지금의 AX는 명세가 아니라 방향을 보여 주는 단계다.

## 인사이트

### 에이전트 인프라의 계층 분리

소프트웨어 시스템은 성숙할수록 관심사가 계층으로 분리된다.
초기 웹 개발에서는 비즈니스 로직과 데이터베이스 접근이 한 파일에 섞여 있었다.
성숙하면서 ORM, 미들웨어, API 게이트웨이가 각 관심사를 담당하는 계층으로 분리됐다.

에이전트 개발도 같은 방향으로 진화하고 있다.
초기에는 LLM 호출, 도구 실행, 오류 처리, 상태 관리가 한 스크립트에 섞여 있었다.
AX는 실행 신뢰성, 상태 지속성, 감사 추적을 별도 런타임 레이어로 분리하는 시도다.
에이전트 개발자는 무엇을 할지에 집중하고, 어떻게 신뢰성 있게 실행할지는 런타임이 담당한다는 분리다.

이 계층 분리가 완성되면 에이전트 개발의 추상화 수준이 높아진다.
“이 에이전트가 실패하면 어떻게 하는가”라는 질문을 개발자가 매번 답하지 않아도 된다.

### “fork” 명령이 드러내는 에이전트 디버깅의 미래

`fork` 명령 — 특정 체크포인트에서 새 이벤트 로그로 분기 — 은 표면적으로 단순하지만 깊은 함의가 있다.
이것은 에이전트 실행의 타임 트래블 디버깅을 가능하게 한다.

인간 개발자가 코드를 디버깅할 때 중단점(breakpoint)을 설정하고 상태를 검사한다.
에이전트 디버깅에서 동등한 것은 “특정 결정이 내려진 시점으로 돌아가 다른 입력을 주면 어떻게 됐을까”를 실험하는 것이다.
`fork`는 이 실험을 가능하게 한다.
에이전트 행동의 원인 분석과 대안 시나리오 탐색이 이 기능 위에서 이루어진다.

장기적으로 이것은 에이전트 테스트 방법론의 기반이 된다.
다만 9월에 다시 쓴 README에서는 `fork` 명령이 사라졌고, 실행 중이거나 중단된 태스크를 메모리와 파일시스템 상태째 여러 병렬 태스크로 분기하는 기능은 로드맵의 “상태 있는 태스크 분기” 항목으로 옮겨 갔다.
지금은 약속된 방향이지 쓸 수 있는 기능이 아니다.
“이 에이전트가 이 상황에서 올바르게 작동했는가”를 재현 가능한 방식으로 검증하는 것이다.

### 태스크를 작게 만든 결정은 파드가 컨테이너를 감싼 결정과 같은 계보다

개념 문서의 가장 흥미로운 문장은 AX가 에이전트의 모양을 모델링하지 않는다는 것이다.
에이전트는 계획하고 위임하고 재시도하는 복잡한 존재이지만, AX는 그 복잡성을 표현하는 자원을 두지 않고, 싸게 만들고 버릴 수 있는 태스크 하나만 준다.
에이전트는 필요한 만큼 태스크를 만들어 트리를 이룬다.

Kubernetes도 같은 결정을 했다.
서비스나 워크플로를 기본 단위로 두지 않고, 컨테이너 몇 개를 묶은 파드라는 작은 단위를 두었으며, 그 위의 구조는 Deployment나 Job 같은 상위 자원과 사용자에게 맡겼다.
그 결정 덕분에 Kubernetes는 어떤 워크로드든 담을 수 있었고, 대신 상위 구조를 설계하는 부담이 사용자에게 돌아갔다.

AX도 같은 대가를 치를 것이다.
태스크 트리를 누가 어떻게 관리하는지, 부모 태스크가 죽으면 자식은 어떻게 되는지, 트리 전체의 예산은 어디서 통제하는지는 지금 문서에 없다.
로드맵의 토큰과 시간 예산, 승인 정책이 그 빈자리를 향하지만, 그것은 태스크 하나의 속성이지 트리의 속성이 아니다.
HN에서 zhoujinliang이 에이전트를 조율할 때 진짜 어려운 것은 돌리는 것이 아니라 상태 변화, 곧 에이전트가 기다리는지 막혔는지 끝났는지를 판단하는 것이라고 지적한 것[^zhoujinliang]이 바로 이 트리 수준의 판단이다.

### 메모리째 체크포인트하는 밀도 전략은 상태 통제와 맞바꾼다

홈페이지가 약속하는 1초 안의 재개와 조밀한 다중화는, 쉬는 에이전트를 메모리 상태째 체크포인트하고 필요할 때 되살린다는 데 기댄다.
에이전트가 대부분의 시간을 모델 응답을 기다리며 보낸다면, 그 시간 동안 자원을 돌려주는 것은 비용을 크게 줄인다.

HN에서 dbmikus는 반대편의 비용을 짚었다.
에이전트 VM을 재개할 때 앱을 정확히 중단된 상태로 되돌리고 싶다면 메모리 복원이 유용하지만, 대부분의 경우 번거로움이 더 크다는 것이다.
늘 메모리에서 재개하면 VM의 상태를 통제하는 능력을 잃으며, 어떤 서비스가 돌아야 하는지 정의하는 것이 어떤 RAM 상태를 지워야 하는지 정의하는 것보다 훨씬 쉽다고 봤다.[^dbmikus]
ahmedtd는 디스크 상태만으로 재개하는 선택지도 제공할 계획으로 알고 있다고 답했다.[^ahmedtd-resume]

이 긴장은 규모가 커질수록 커진다.
메모리 체크포인트는 수십억 개의 세션을 싸게 유지하는 수단이지만, 동시에 수십억 개의 “왜 이 상태인지 아무도 모르는” 스냅숏을 쌓는 일이기도 하다.
재현성과 디버깅을 원하는 연구자에게는 선언된 상태에서 새로 시작하는 쪽이 낫고, 비용을 원하는 운영자에게는 메모리째 되살리는 쪽이 낫다.
AX가 연구자와 운영자를 모두 겨냥한다면, 두 재개 방식을 태스크마다 고를 수 있게 하는 것이 필수가 될 것이다.
