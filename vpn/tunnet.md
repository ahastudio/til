# Tunnet: 조정 서버까지 공개한 메시 네트워크, Tailscale과 ngrok을 한 스택으로

<https://docs.tunnet.io/>

<https://github.com/tunnetio/Tunnet>

GN 토론: <https://news.hada.io/topic?id=34204>

## 소개

Tunnet은 오픈 소스 사설 메시 네트워킹 플랫폼이다.
여러 곳에 흩어진 머신을 하나의 암호화된 네트워크로 묶은 뒤, 그 위에서 SSH를 하고, 내부 앱을 제공하고, 공개 터널을 열고, 파일을 보내고, Kubernetes를 같은 네트워크에 연결한다.
README는 이것을 “하나의 신원, 하나의 정책 엔진, 완전히 자체 호스팅할 수 있는 하나의 스택”으로 요약한다.
Rust로 작성됐고, 2026년 7월 3일에 저장소가 만들어졌으며 9월 24일 기준 스타 127개, 포크 8개다.
README 첫머리에 “개발 중(In development)” 배지가 붙어 있다.

출발점이 되는 문제 인식은 두 가지다.
하나는 상용 메시 제품이 훌륭하지만 대부분 조정 서버를 닫아 둔다는 것이다.
Tunnet은 에이전트, 컨트롤 플레인, 관리 API, 대시보드, 릴레이를 모두 이 저장소에 넣어, 모든 줄을 읽고 전부 자체 호스팅할 수 있게 하며 독점 조정 서비스나 뒤처지는 제3자 재구현에 기대지 않게 하겠다고 말한다.
다른 하나는 Tailscale, ngrok, scp, 배스천 서버를 이어 붙이는 대신, 메시와 공개 터널과 내부 서비스와 파일 전송과 신원 기반 SSH와 기기 상태 점검과 Kubernetes를 하나의 신원과 하나의 ACL 체계 아래 두겠다는 것이다.

## 주요 기능

README가 나열한 기능과 각 기능이 대신하려는 제품은 다음과 같다.

| 기능                  | 대신하려는 것                       |
| --------------------- | ----------------------------------- |
| Mesh                  | Tailscale, NetBird, Cloudflare WARP |
| Serve                 | Cloudflare Access, Tailscale Serve  |
| Tunnel                | ngrok, Cloudflare Tunnel            |
| Send                  | Taildrop, 임시 파일 전달            |
| SSH                   | 키 배포와 배스천                    |
| Device posture        | MDM, EDR 정책 관문                  |
| 자체 호스팅 릴레이    | 벤더의 엣지 네트워크                |
| Kubernetes 오퍼레이터 | 직접 만든 VPN과 Ingress 연결        |
| Policy as Code        | HuJSON ACL과 임시 GitOps            |
| 감사 로그             | SIEM 전용이거나 닫힌 관리 기록      |
| Node, Rust, Go SDK    | 터널과 관리 API 내장                |

### LAN처럼 느껴지는 메시

등록된 머신마다 오버레이 IP와 호스트 이름이 생기고, `ping`, `curl`, `ssh`, 브라우저 같은 평범한 도구가 그대로 동작한다.
PeerDNS, 서브넷 라우트, 종료 노드, 고가용성 게이트웨이가 들어 있다.
문서에 따르면 연결은 iroh의 QUIC 위에서 이루어지는 암호화된 P2P다.
비교 문서는 WireGuard 대신 QUIC을 쓰는 이유로 기본 제공되는 다중화 스트림, 내장 NAT 통과, 사용자 공간 WireGuard 우회 없이 되는 릴레이 폴백을 든다.

### Kubernetes와 앱 내장

Tunnet 오퍼레이터는 CRD로 클러스터를 네트워크에 연결한다.
클러스터 CIDR을 알리고, `TunnetIngress`로 서비스를 피어에게 공개하고, `TunnetTunnel`로 공개 HTTPS를 열고, `TunnetEgress`로 클러스터 안에서 메시 호스트에 닿고, 선택적으로 사이드카를 주입한다.
Node.js와 Bun, Rust SDK로는 메시 노드를 프로세스 안에 넣어, 별도 에이전트 없이 앱끼리 스트림을 열고 파일을 주고받을 수 있다.
정책, 그룹, ACL 같은 관리 자동화는 Go 관리 SDK가 맡는다.

### 두 가지 운영 방식

Managed 모드는 컨트롤 플레인, 대시보드, SSO와 OIDC, 중앙 정책, Policy as Code(HCL, JSON, YAML, Terraform, GitOps), 감사 로그, 터널, SSH 세션 녹화를 갖춘 팀용 방식이다.
Direct 모드는 서버 없이 도는 P2P 메시로, 개인과 작은 그룹을 위한 것이다.
Policy as Code는 ACL, 그룹, 태그, SSH, 기기 상태 규칙을 Git에서 작성하고, 오프라인으로 검증과 시뮬레이션을 하고, PR에 의미 단위 diff를 올리고, 드리프트를 감지하며 적용하고, Terraform으로 내보내고, 개정판을 되돌릴 수 있게 한다.

## 설치

Linux와 macOS에서는 설치 스크립트를, Windows에서는 관리자 PowerShell을 쓴다.

```bash
curl -fsSL https://get.tunnet.io | sh
```

```powershell
irm https://get.tunnet.io | iex
```

에이전트 설치, Managed와 Direct 빠른 시작, 전체 스택 자체 호스팅, CLI 참조는 docs.tunnet.io에 따로 있다.

## 라이선스

구성 요소마다 라이선스가 다르다.
내장 런타임, 에이전트, SDK, 클라이언트 쪽 런타임은 MPL-2.0이다.
컨트롤 플레인, 관리, 대시보드, 관리형 릴레이, 감사, 영속성, 내부 API, 배포 조율 구성 요소는 AGPL-3.0-only이다.
프로토콜과 공통 코드, 클라이언트, 계약, 정책 형식, SDK 도구, 예제, 설치 스크립트, CI 도구는 Apache-2.0이다.
AGPL 구성 요소에는 대안으로 상업 라이선스가 있으며, MPL과 Apache 구성 요소에는 필요하지 않다.

## 분석

### 경쟁의 축을 “조정 서버가 열려 있느냐”로 옮겼다

Tailscale 계열 제품의 기술적 핵심은 데이터 평면이 아니라 조정 서버다.
누가 네트워크에 들어올 수 있는지, 어떤 노드가 어떤 노드와 통신할 수 있는지, 키를 어떻게 나눠 주는지를 조정 서버가 정한다.
Tailscale은 클라이언트를 공개했지만 조정 서버를 닫아 두었고, 그 빈자리를 [[headscale]]이 커뮤니티 재구현으로 채워 왔다.

Tunnet의 비교 문서는 Headscale을 “뒤처지는 재구현”이라고 부르며, 처음부터 조정 서버를 공개한 쪽이 그 격차를 없앤다고 주장한다.
이 주장이 성립하는 이유는 재구현이 본래 제품의 기능을 따라가는 구조이기 때문이다.
본래 제품이 새 기능을 내면 재구현은 그것을 역으로 파악해 다시 만들어야 하고, 그 사이의 지연이 늘 생긴다.
조정 서버가 처음부터 같은 저장소에 있으면 그런 지연이 없다.

### 비교표에 “솔직한 단서”를 붙인 것이 신뢰의 전략이다

README의 비교표는 Tunnet이 거의 모든 칸에서 “Yes”를 받는 모양이지만, 바로 아래에 Tailscale과 Cloudflare가 기업용 완성도와 실전에서 검증된 규모에서 더 성숙하다는 단서를 붙인다.
비교 문서도 Tailscale이 성숙도, 플랫폼 지원 범위, 기업 기능, 검증된 안정성에서 앞서며 Tunnet은 그 격차를 솔직히 인정한다고 적는다.

네트워크 인프라에서 이 단서는 특히 중요하다.
VPN과 메시 네트워크는 한 번 깔면 조직의 모든 접근 경로가 그 위를 지나므로, 기능 수보다 장애가 없는 기간이 선택을 좌우한다.
기능표만 앞세웠다면 경험 있는 운영자는 곧바로 의심했을 것이다.
약점을 먼저 밝혀 두면, 적어도 이 프로젝트가 자기 위치를 알고 있다는 인상을 준다.

### WireGuard 대신 QUIC을 고른 것은 기능 목록과 맞물린 선택이다

대부분의 메시 VPN은 WireGuard를 데이터 평면으로 쓴다.
Tunnet은 iroh의 QUIC을 택했고, 그 이유로 다중화 스트림, NAT 통과, 릴레이 폴백을 든다.

이 선택은 Tunnet의 기능 목록과 맞물린다.
WireGuard는 IP 패킷을 나르는 계층 3 터널이라, 그 위에서 파일 전송이나 앱 사이 스트림을 하려면 다른 프로토콜을 또 얹어야 한다.
QUIC은 처음부터 여러 스트림을 한 연결에 담는 전송 계층이라, Send와 SDK의 스트림 열기와 Tunnel의 HTTPS 전달을 같은 연결 위에서 표현하기 쉽다.
“하나의 스택”이라는 약속을 지키려면 데이터 평면부터 여러 용도를 담을 수 있어야 했고, QUIC은 그 요구에 맞는 선택이다.

## 비평

### 모든 것을 대신하겠다는 목록이 개발 중인 프로젝트의 규모를 넘어선다

README는 메시, 서비스 공개, 공개 터널, 파일 전송, SSH와 세션 녹화, 기기 상태 점검, 릴레이, Kubernetes 오퍼레이터, Policy as Code, 감사 로그, 세 언어의 SDK를 한꺼번에 내놓는다.
대신하겠다는 제품은 Tailscale, NetBird, Cloudflare WARP와 Access와 Tunnel, ngrok, MDM과 EDR까지 이른다.
각각이 한 회사의 주력 제품이다.

이 목록을 스타 127개, 포크 8개, “개발 중” 배지가 붙은 석 달 된 저장소가 모두 떠받친다.
기능이 많다는 것 자체가 문제는 아니지만, 네트워크 인프라에서는 기능 하나하나가 공격 표면이고 운영 부담이다.
비교표의 “Yes”가 “구현되어 있다”인지 “프로덕션에서 쓸 수 있다”인지는 표에서 구별되지 않는다.
솔직한 단서가 전체 성숙도에 대해서는 있지만, 기능마다의 성숙도에 대해서는 없다.

### 보안 모델을 설명하는 문서가 비교 문서보다 앞서야 한다

메시 VPN을 평가할 때 가장 먼저 알아야 하는 것은 기능이 아니라 신뢰 경계다.
조정 서버가 탈취되면 무엇을 할 수 있는지, 키는 어디서 만들어지고 어디에 저장되는지, 릴레이는 트래픽을 볼 수 있는지, Direct 모드에서 피어의 신원은 어떻게 확인하는지 같은 질문이다.

README와 비교 문서는 QUIC과 iroh를 쓴다는 것 외에 이 질문들에 답하지 않는다.
보안 개념 문서를 찾아보려 했지만, 문서 사이트에서 그런 경로는 찾지 못했다.
WireGuard는 작은 코드 크기와 공개된 형식 검증으로 신뢰를 쌓았고, Tailscale은 조정 서버가 개인 키를 보지 않는다는 설계를 공개적으로 설명해 왔다.
WireGuard가 아닌 다른 전송을 고른 프로젝트일수록, 그 선택이 보안 속성에 무엇을 바꾸는지를 먼저 설명해야 한다.

### 설치 경로가 제품의 약속과 어긋난다

Tunnet의 핵심 약속은 모든 것을 읽고 자체 호스팅할 수 있다는 것이다.
그런데 기본 설치는 `curl | sh`와 `irm | iex`, 곧 원격 스크립트를 검증 없이 관리자 권한 셸에 넘기는 방식이다.
VPN 에이전트는 네트워크 인터페이스를 만들고 라우팅을 바꾸는 높은 권한으로 돈다.
모든 줄을 읽을 수 있다는 약속은 소스 저장소에 대한 것이고, 설치 스크립트가 받아 오는 바이너리가 그 소스에서 빌드된 것인지 확인하는 방법은 README에 나오지 않는다.

## 인사이트

### 연결 계층의 통합은 인증 계층의 통합을 따라온다

Tunnet이 한 스택으로 묶으려는 제품들, 곧 메시 VPN, 공개 터널, 제로 트러스트 접근, SSH 배스천은 원래 서로 다른 문제를 풀었다.
그런데 지난 몇 년 동안 이 제품들은 모두 같은 방향으로 수렴했다.
Tailscale은 Serve와 Funnel로 터널을 더했고, Cloudflare는 Tunnel과 Access에 Mesh를 더했다.
이 수렴의 이유는 기술이 아니라 신원이다.

모든 연결이 “누가 이 연결을 하는가”라는 같은 질문에서 출발한다면, 신원을 하나로 묶은 쪽이 연결의 종류를 늘리는 것은 쉬운 일이다.
Tunnet이 “하나의 신원, 하나의 정책 엔진”을 앞세운 것은 이 구조를 정확히 읽은 것이다.
경쟁은 누가 더 빠른 터널을 만드느냐가 아니라, 누구의 신원 체계 위에 조직의 모든 연결이 올라가느냐로 옮겨 가고 있다.

### 오픈 코어 네트워크 제품은 라이선스로 사업 모델을 말한다

Tunnet의 라이선스 배치는 그 자체로 사업 계획서다.
사용자 기기에 깔리는 에이전트와 SDK는 MPL-2.0으로 가볍게 열고, 서버 쪽의 컨트롤 플레인과 대시보드와 감사는 AGPL-3.0-only로 두며, 그 대안으로 상업 라이선스를 판다.
누구나 에이전트를 자기 제품에 넣을 수 있지만, 컨트롤 플레인을 고쳐서 서비스로 팔려면 소스를 공개하거나 라이선스를 사야 한다.

이 구조는 “조정 서버를 연다”는 약속과 “조정 서버로 돈을 번다”는 필요를 동시에 만족시키려는 설계다.
Tailscale이 조정 서버를 닫아 사업을 지켰다면, Tunnet은 조정 서버를 열되 AGPL로 클라우드 사업자의 무임승차를 막는다.
같은 목적을 다른 수단으로 이루려는 것이며, 어느 쪽이 사용자에게 더 나은지는 결국 자체 호스팅을 실제로 하는 사용자가 얼마나 되느냐에 달려 있다.

### 메시 VPN 시장의 진입 장벽은 코드가 아니라 장애 기록이다

Tunnet의 솔직한 단서, 곧 Tailscale과 Cloudflare가 실전에서 검증된 규모에서 앞선다는 인정은 이 시장의 진짜 진입 장벽을 가리킨다.
코드는 몇 달이면 쓸 수 있고, 기능 목록은 금방 따라잡을 수 있다.
그러나 수만 개 조직의 네트워크에서 몇 년 동안 큰 장애 없이 돌았다는 기록은 시간만이 만든다.

그래서 새 메시 네트워크 프로젝트가 처음 얻을 수 있는 사용자는 기록보다 통제를 중시하는 쪽이다.
벤더에 기대지 않고 모든 것을 직접 운영하려는 조직, 규제 때문에 외부 조정 서비스를 쓸 수 없는 조직, 그리고 실험을 즐기는 개인이다.
Tunnet이 Direct 모드를 개인과 작은 그룹용으로 두고 Managed 모드를 팀용으로 둔 것은, 이 첫 사용자층에서 기록을 쌓아 다음 사용자층으로 넘어가려는 경로로 읽힌다.
[[tailscale]]이 개인 사용자의 무료 요금제로 신뢰를 쌓은 뒤 기업으로 넘어간 길과 같은 경로다.
