# Tailnet Lock: 조정 서버를 믿지 않고 Tailscale을 쓰는 방법

원문: [Tailnet Lock · Tailscale Docs](https://tailscale.com/docs/features/tailnet-lock)

## 소개

Tailnet Lock은 신뢰하는 노드가 서명하지 않은 노드는 tailnet에 들어올 수 없게
하는 기능이다.
켜 두면 Tailscale이 악의적이거나 Tailscale 인프라가 해킹당해도 공격자는
tailnet에서 트래픽을 보내거나 받을 수 없다고 문서는 설명한다.
Personal과 Enterprise 요금제에서 쓸 수 있다.

이 기능이 없을 때는 새 노드가 들어오면 조정 서버(coordination server)가 그
노드의 공개 키를 다른 피어에게 나눠 준다.
조정 서버가 새 노드를 몰래 끼워 넣으면 그 노드가 기존 노드와 평문으로 통신할 수
있다는 것이 문서의 위협 모델이다.
Tailnet Lock은 공개 키 배포를 조정 서버에만 맡기지 않고, 신뢰하는 노드의 서명을
거치게 한다.

보장의 경계도 문서에 적혀 있다.
이 기능은 신뢰할 대상을 없애는 것이 아니라 옮기는 것이다.
처음에는 조정 서버를 믿고 시작하고(Trust On First Use, TOFU), 켠 뒤에는 신뢰의
중심이 고객의 노드로 옮겨 간다.
문서는 Headscale로 조정 서버를 직접 운영하는 길도 있지만 SaaS의 가용성과 낮은
운영 부담을 잃는다고 하면서, Tailnet Lock을 그 중간 지점으로 소개한다.

## 동작 방식

### 두 종류의 키

노드마다 키가 두 개 있다.
노드 키(node key)는 Tailscale 클라이언트가 만드는 공개/비공개 키 쌍이고, 조정
서버가 이 키를 특정 신원에 묶는다.
Tailnet Lock 키(TLK)도 공개/비공개 키 쌍인데, 모든 노드가 Tailnet Lock을
켰는지와 상관없이 하나씩 만든다.
TLK의 비공개 키는 만든 노드에 남고, 신뢰하는 TLK의 공개 키는 tailnet key
authority(TKA)에 저장된다.

### 서명 노드와 TKA

Tailnet Lock은 두 부분으로 이루어진다.
서명 노드(signing node)는 새 노드를 tailnet에 들이는 서명을 할 수 있는 노드다.
TKA는 현재 신뢰하는 TLK 집합을 저장하는 장치이며, 이 집합을 알기 때문에 두
가지를 검증한다.
하나는 피어 목록에 노드 키를 넣기 전에 하는 노드 키 서명 검증이고, 다른 하나는
신뢰 TLK 집합을 바꾸라는 요청을 처리하기 전에 하는 서명 검증이다.

TKA의 저장 방식은 암호학적 체인이고, 설정을 바꿀 때마다 한없이 커질 수 있다고
한다.
이 사실이 뒤의 키 교체 횟수 제한으로 이어진다.

### 가입 시나리오

켜진 상태에서 새 노드가 들어오는 흐름은 이렇다.
첫째, 새 노드의 공개 노드 키는 TLK의 서명이 있어야 한다.
둘째, 조정 서버는 서명된 공개 노드 키를 피어에게 나눠 준다.
셋째, 피어는 서명을 확인한 뒤에야 연결을 허용한다.
조정 서버가 서명 없는 노드를 끼워 넣어도 피어가 거부하므로 연결이 성립하지
않는다.

## 켜기

켜려면 tailnet의 Owner, Admin, IT admin 중 하나여야 한다.
기본값은 꺼짐이고, 잠글 노드는 Tailscale v1.46.1 이상이어야 한다.
켜는 명령은 `tailscale lock init`이며, 명령에 넣을 값은 관리 콘솔이 만들어 준다.

1. 관리 콘솔의 Device management 페이지를 열고 Enable Tailnet Lock을 고른다.
콘솔과 서명 노드의 클라이언트가 같은 tailnet에 로그인해 있어야 한다.
2. Add signing nodes에서 신뢰할 노드를 고른다. 최소 두 개를 골라야 한다.
3. 선택 사항으로, Tailscale 지원팀에 보낼 disablement secret을 하나 더 만들지
정한다.
4. 콘솔이 보여 주는 `tailscale lock init` 명령을 복사해 고른 서명 노드 중 한
곳에서 실행한다.

실행하면 disablement secret이 열 개 출력된다.
끄는 데는 하나만 있으면 된다.
이 값은 초기화할 때만 보이고, 잃어버렸는데 지원팀에도 주지 않았다면 tailnet을
복구할 수 없다고 문서는 경고한다.

```bash
# 서명 노드에서 실행한다. 값은 관리 콘솔이 만든 명령을 그대로 붙여 넣는다.
tailscale lock init <콘솔이 만든 인자>

# 켠 뒤에는 모든 노드에서 신뢰하는 서명 키 목록을 확인한다.
tailscale lock status
```

켠 직후에는 기존 노드가 모두 서명되고, 신뢰 TLK 집합이 기존 노드에 배포되며,
이후 새 노드 키는 모두 서명이 필요하다.
각 노드는 처음 받은 상태를 조정 서버에서 받으므로, 문서는 모든 노드에서
`tailscale lock status`를 실행해 서명 키 목록이 같은지, 지정한 서명 노드의 TLK와
일치하는지 확인하라고 한다.

## 끄기

끄는 것도 Owner, Admin, IT admin의 권한이 필요하다.
관리 콘솔에서는 Device management의 Disable Tailnet Lock에서 보관해 둔
disablement secret을 넣는다.
CLI에서는 `tailscale lock disable <disablement-secret>`를 쓴다.

한 번 쓴 disablement secret은 조정 서버가 모든 노드에 퍼뜨리므로 공개된 것으로
보아야 한다.
다시 켜면 새 disablement secret이 만들어진다.
secret을 못 찾아서 끌 수 없을 때의 마지막 수단은 각 노드에서
`tailscale lock local-disable`을 실행해 그 노드가 Tailnet Lock을 무시하게 하는
것이다.

## 노드 추가와 서명 노드 관리

### 새 노드 서명하기

잠긴 tailnet에 노드를 더하려면 새 노드의 노드 키에 서명해야 한다.
방법은 클라이언트 앱의 서명 링크와 `tailscale lock sign` 명령 둘이다.
서명 링크는 macOS, Windows, iOS에서만 되고 명령은 Linux, macOS, Windows에서만
된다.
두 방법 모두 노드 키 정보를 관리 콘솔의 Machines 페이지에서만 얻을 수 있어 콘솔
접근이 필요하다.

서명이 필요한 노드는 Machines 목록에서 Locked out 배지로 보이고,
`property:locked-out` 필터로 모아 볼 수 있다.

```bash
# 서명 노드에서 실행한다. nodekey는 추가할 노드의 노드 키이고,
# tlpub는 키 교체에 쓰는 선택 인자다.
tailscale lock sign nodekey:1abddef1 tlpub:abcdef12

# 추가할 노드에서 실행하면 위 명령을 만들어 준다.
tailscale lock status
```

서명된 노드 키가 만료되어도 다시 서명할 필요는 없다.
사용자가 다시 인증하면 노드가 자기 TLK로 새 노드 키에 서명해 서명이 자동으로
이어진다.

미리 서명한 인증 키(auth key)를 쓰면 노드를 추가한 뒤 서명하는 두 단계를 건너뛸
수 있다.

```bash
# 사전 승인된 auth key를 만든 뒤, 신뢰하는 TLK가 있는 노드에서 실행한다.
export AUTH_KEY="tskey-auth-<XXXXCTRL-NNNNNN>"
tailscale lock sign $AUTH_KEY
# 출력된 새 키로 tailnet의 기기를 사전 승인한다.
```

### 서명 노드 더하기와 빼기

서명 노드를 더하려면 먼저 그 노드의 TLK 공개 키를 알아야 한다.
형태는 `tlpub:abcdef12`이고, `nodekey:abcdef12` 형태의 노드 공개 키와 다르다.
`tailscale lock status`나 관리 콘솔의 Machine Details에서 Tailnet Lock key
항목으로 확인한다.
콘솔에 이 항목이 보이지 않으면 그 tailnet에서 Tailnet Lock이 꺼져 있다는 뜻이다.

```bash
# 신뢰하는 TLK가 있는 노드에서 실행한다.
tailscale lock add tlpub:trusted-key1 tlpub:trusted-key2
tailscale lock remove tlpub:trusted-key7 tlpub:trusted-key8
```

서명 노드 Node-B를 Node-A에서 `remove`하면 기본값으로 Node-B가 서명했던 노드가
모두 Node-A의 키로 다시 서명된다.
`--re-sign=false`를 주면 이 동작을 끈다.

### 침해된 서명 노드 폐기하기

서명 노드가 침해되면 `remove`가 아니라 `tailscale lock revoke-keys`로 키를
폐기한다.
폐기한 키는 다시 쓸 수 없고, 그 키가 서명했던 노드는 권한을 잃어 새 서명이
필요하다.
침해되지 않은 키를 빼는 것이라면 `remove`를 쓴다.

폐기는 여러 서명 노드가 공동 서명(co-sign)하는 여러 단계 절차다.

```bash
# 1. 침해되지 않은 서명 노드에서 시작한다.
tailscale lock revoke-keys tlpub:compromised-key1 tlpub:compromised-key2
# 출력에 --cosign 명령이 들어 있다.

# 2. 다른 신뢰 서명 노드에서 그 --cosign 명령을 실행한다.
#    출력에 새 --cosign 명령이 나오므로 그것을 다음 노드에서 실행한다.
#    --cosign을 쓴 횟수가 폐기하는 키 수를 넘을 때까지 반복한다.
#    (키 3개를 폐기하면 --cosign을 4번 실행한다.)

# 3. 마지막 --cosign 출력의 --cosign을 --finish로 바꿔 실행한다.
tailscale lock revoke-keys --finish <hex-data>
```

기본값으로 Tailscale이 Tailnet Lock 로그에서 갈라질 지점을 정하고, 어떤 키가
폐기 가능하다고 동의하는 서명 노드가 더 많으면 tailnet은 Tailscale이 신뢰할 수
있다고 판단한 갈래의 키를 쓴다.
서명 노드 대다수가 침해되면 Tailnet Lock을 끄고 다시 켠다.

## 값 정하기

문서가 숫자로 정한 것은 서명 노드 최소 2개, 최대 20개, 키 교체는 연 1회
이하다.
나머지는 문서의 사실에서 이 노트가 이끌어 낸 출발값이며, 문서가 권하는 값이
아니다.

| 항목               | 출발값                                                  | 근거                                                                    | 바꿀 때의 관찰                            |
| ------------------ | ------------------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------- |
| 서명 노드 수       | 3개 이상, 물리적으로 다른 장소                          | 2개가 최소이고 최대는 20개다. 폐기는 여러 노드의 공동 서명이 필요하다   | 폐기 절차를 연습했을 때 노드가 모자라는가 |
| 서명 노드의 종류   | Android가 아닌 기기                                     | Android는 서명 노드가 될 수 없다                                        | 서명용 기기를 실제로 켜 둘 수 있는가      |
| disablement secret | 열 개를 여러 곳에 나눠 보관하고 지원팀에 줄지 따로 정함 | 잃고 지원팀에도 없으면 복구 불가다. 지원팀이 가지면 지원팀이 끌 수 있다 | 보관 위치 접근 권한이 바뀌었는가          |
| 키 교체 주기       | 연 1회 이하                                             | TKA 체인이 한없이 커지지 않게 하려는 제한이다                           | `tailscale lock log`의 변경 빈도          |
| 상태 디렉터리      | 항상 지정                                               | 없으면 시작할 때마다 조정 서버에서 전체 상태를 받아야 한다              | 재시작 뒤 `lock status`가 바로 나오는가   |

## 트레이드오프

### 처음의 신뢰는 사라지지 않는다

켜는 순간 각 노드는 조정 서버가 보낸 초기 상태를 받는다.
그래서 조정 서버가 이미 침해된 상태에서 켜면 공격자가 보낸 서명 키 목록이 정착할
수 있다.
문서가 모든 노드에서 `tailscale lock status`를 비교하라고 하는 이유가 이것이다.
이 확인은 서명 노드가 아닌 노드에서도, 콘솔이 아니라 노드 자체에서 해야 의미가
있다.

켜기만 하면 되는 것이 아니라는 점이 어려운 부분이다.
비교할 기준(지정한 서명 노드의 TLK)을 조정 서버 바깥에서 얻어야 하고, 그 값은
`lock status`로 서명 노드에서 직접 읽을 수 있다.
이 방법은 문서에 적힌 절차이고, 기준 값을 어떻게 안전하게 전달할지는 문서가
다루지 않는다.

### 복구 가능성과 신뢰 범위가 맞바뀐다

disablement secret을 지원팀에 주면 secret을 모두 잃어도 tailnet을 되살릴 수
있다.
반대로 지원팀이 끌 수 있는 secret이 Tailscale 쪽에 있다는 뜻이기도 하다.
조정 서버가 침해된 상황에서 이 secret까지 새면 보호가 풀릴 수 있다는 것은 이
노트의 추론이고, 문서는 그런 시나리오를 다루지 않는다.
주지 않으면 신뢰 범위는 좁아지지만 secret을 잃는 순간 복구 수단이 사라진다.
열 개 중 하나만 있으면 되므로, 여러 곳에 나눠 두는 것으로 잃을 위험을 낮추고,
지원팀에 주는 것은 별개의 선택으로 다뤄야 한다.

### 서명 키는 기기에 있다

TLK는 기기에 저장되므로 기기가 침해되면 키를 얻을 수 있다고 문서가 인정한다.
서명 노드가 많을수록 침해될 기기가 늘고, 적을수록 폐기에 필요한 공동 서명자가
모자란다.
최소 2개와 최대 20개 사이에서 고르는 이유다.
문서는 폐기에 필요한 노드 수를 `--cosign` 횟수로 설명하지만, 같은 노드가 여러 번
공동 서명할 수 있는지는 적지 않았다.

### 다른 기능과의 충돌

device approval과는 함께 쓸 수 없다.
둘은 서로 배타적인 기능이라서, 기기 승인으로 쌓던 통제를 서명 절차로 옮겨야
한다.
링크로 공유한 노드는 잠긴 tailnet 안에서 서명을 받아야 접근할 수 있고, 공유받는
쪽은 초대를 수락하는 사용자의 노드가 잠긴 tailnet에서 서명되어 있어야 공유
노드에 접근할 수 있다.
Tailscale SSH Console은 서명된 노드에 대해 쓸 수 있고, 정책 파일이 네트워크
접근을, SSH 규칙이 SSH 접근을 허용해야 한다.

## 함정

상태 디렉터리가 없으면 Tailnet Lock 데이터가 메모리에만 있어 노드가 시작할
때마다 조정 서버에서 전체 상태를 다시 받는다.
문서는 이 시작 의존성을 없애려고 상태 디렉터리를 지정하라고 강하게 권한다.
macOS, Windows, iOS, Android, tvOS 클라이언트는 자동으로 정해지고,
`tailscaled`는 `--statedir`이나 `--state`로, Docker와 Kubernetes는
`TS_STATE_DIR` 환경 변수로 정한다.
컨테이너로 노드를 많이 띄운다면 가장 먼저 놓치기 쉬운 항목이다.

한 번 쓴 disablement secret은 공개된 것이므로 다시 쓰지 않는다.
disablement secret은 `init` 때만 출력되므로 화면 기록과 보관 절차를 같은
자리에서 끝내야 한다.
문서는 침해된 키에는 `revoke-keys`를, 침해되지 않은 키를 빼는 데는 `remove`를
쓰라고 구분한다.
`remove`는 기본값으로 그 키가 서명한 노드를 다시 서명하므로, 침해된 키를
`remove`로 빼면 그 키가 서명한 노드가 권한을 잃지 않고 남을 것으로 보인다.
이것은 문서의 두 설명을 이어 붙인 이 노트의 추론이다.
서명 노드가 Android뿐이면 서명을 할 수 없다.

## 확인하기

문서가 제안하는 확인은 노드마다 같은 명령을 실행하는 것이다.

```bash
# 모든 노드에서 실행해 신뢰 서명 키 목록이 같은지, 지정한 서명 노드의 TLK와
# 일치하는지 비교한다.
tailscale lock status

# 최근 Tailnet Lock 변경을 노드에서 직접 본다.
tailscale lock log
```

켜거나 끄거나 바꾸면 설정 감사 로그에도 이벤트가 남는다.
새 노드를 하나 띄워 Machines 목록에서 Locked out 배지가 붙는지, 서명하면
사라지는지 보는 것도 동작 확인이 된다.
이 노드는 서명 전에 피어와 연결되지 않아야 한다.

## 체크리스트

- 잠글 노드가 모두 v1.46.1 이상인가
- 서명 노드를 최소 2개, 서로 다른 장소에 고르는가
- disablement secret 열 개가 출력된 직후 보관을 마쳤는가
- 지원팀에 secret을 줄지 의식적으로 정했는가
- 모든 노드의 `lock status` 출력이 같은가
- 모든 노드에 상태 디렉터리가 지정되어 있는가
- device approval을 쓰고 있지 않은가
- 폐기 절차를 연습해 공동 서명할 노드가 충분한지 확인했는가

## 비평

### 문서는 켠 뒤의 조정 서버 가정을 숨긴다

문서는 TOFU 한 가지만 한계로 든다.
그러나 서명하지 않은 노드를 거부하는 것은 피어의 클라이언트 코드다.
문서는 그 클라이언트 소프트웨어를 누가 배포하는지, 배포물이 악의적일 가능성을
위협 모델에 넣는지 밝히지 않는다.
클라이언트를 Tailscale이 배포한다면 보호의 범위는 조정 서버가 악의적인 경우로
좁혀진다는 것이 이 노트의 추론이다.

### 복구 불가능성이 도입 문턱이다

모든 secret을 잃고 지원팀에도 없을 때 tailnet을 복구할 수 없다는 경고가 두 번
나온다.
보안 기능을 켜는 일이 한 번의 보관 실수로 되돌릴 수 없는 일이 되는 셈이다.
`local-disable`이 있지만 모든 노드를 하나씩 돌아야 하므로 노드가 많은 조직에서는
사실상 재구축에 가깝다.
문서는 이 비용을 경고로 적었을 뿐 줄여 주는 방법은 주지 않는다.

## 기억할 원칙

### 서명 권한은 조정 서버에서 분리된 곳에 둔다

Tailnet Lock이 하는 일은 새 노드를 들일지에 대한 결정권을 조정 서버에서 고객의
서명 노드로 옮기는 것이다.
옮긴 결정권이 잘 지켜지는지는 서명 노드의 수, 위치, 보관하는 secret에 달려 있다.

### 효과를 믿기 전에 비교한다

켜는 명령이 성공해도 신뢰가 확립된 것은 아니다.
모든 노드가 같은 서명 키 목록을 보고 있다는 사실을 직접 확인해야 처음의 신뢰가
검증으로 바뀐다.
