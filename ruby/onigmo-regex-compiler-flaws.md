# Ruby 정규식 엔진 Onigmo의 메모리 손상 문제 4건과 보안 업데이트

원문: [「Ruby」の正規表現エンジン「Onigmo」にリモートコード実行の問題、セキュリティ更新を実施 - 窓の杜](https://forest.watch.impress.co.jp/docs/news/2150800.html)

## 요약

일본 매체 窓の杜(마도노모리)가 2026년 10월 23일에 보도한 짧은 뉴스다.
Ruby 개발팀이 10월 23일(UTC) 보안 업데이트를 냈고, Ruby가 쓰는 정규식 엔진
Onigmo에서 여러 문제가 발견됐다는 내용이다.
미국 GitLab이 보고한 문제이고, GitLab 서버에서 원격 코드 실행에 악용될 수 있다고
기사는 전한다.
CVE 번호는 네 개가 붙었다.
CVE-2026-89078은 정규식 파서의 이중 해제(Double Free)다.
CVE-2026-93577은 정규식 컴파일러의 정수 오버플로이고, CVE-2026-97229는 CI/CD의
정규식 컴파일러에서 생기는 정수 오버플로다.
CVE-2026-110264도 정규식 컴파일러의 정수 오버플로다.

공격자가 조작한 정규식 패턴을 주면 Ruby가 정규식을 컴파일하는 과정에서 메모리가
손상되고, 최악의 경우 원격 코드 실행에 악용될 수 있다고 한다.
GitLab은 v19.4.1, 19.4.2, 19.5.1에 포함한 Ruby에 이미 패치를 적용해 대응했고,
이번에 Ruby의 각 계열에도 같은 수정이 들어갔다.
영향을 받는 것은 공격자가 제어할 수 있는 문자열로 정규식을 컴파일하는
애플리케이션이다.
`Regexp.new`, `Regexp.union`, `Regexp.compile`에 그런 문자열을 넘기거나,
`/#{input}/`처럼 정규식 리터럴에 끼워 넣는 경우가 해당한다.
개발자가 직접 쓴 정규식만 쓰는 애플리케이션은 영향이 없다.

권장 대책은 Ruby 4.0.9, 3.4.12, 3.3.13으로 올리는 것이다.
3.3.13에서는 취약점이 있던 표준 번들 라이브러리 `resolv`도 v0.3.2로 올라간다.
타임아웃을 두거나 패턴 길이를 제한하는 것은 확실한 대책이 되지 못한다고 개발팀이
밝혔다.
바로 업데이트할 수 없다면 신뢰할 수 없는 입력으로 정규식을 컴파일하지 않는 것이
핵심이다.
기사 끝의 설명에 따르면 Ruby 측은 이 문제들을 취약점으로 다룰지 아직 정하지
않았고 CVE 번호도 신청하지 않았다.
보안 스캐너로 추적할 때는 당분간 GitLab이 신청한 CVE 번호를 참고하라고 안내한다.

## 분석

### 영향 범위는 정규식을 만드는 출처로 정해진다

기사가 그은 경계선은 정규식 패턴의 출처다.
사용자 입력으로 패턴을 만드는 코드만 노출되고, 소스에 고정된 정규식은 안전하다.
검색 기능이나 필터 규칙, 설정 화면처럼 사용자가 패턴을 직접 적게 하는 기능이
전형적인 노출 지점이다.
이 문서는 그런 기능의 목록을 기사에서 확인하지 못했고, 위 예시는 기사가 든 호출
형태에서 이 문서가 연결해 본 것이다.

### 완화책이 통하지 않는다는 말의 무게

정규식 관련 보안 문제로 자주 떠올리는 것은 처리 시간이 폭주하는 문제이고, 이에는
타임아웃이나 길이 제한이 대응책이 된다.
이번 문제는 컴파일 단계의 메모리 손상이라 그런 완화책이 확실하지 않다고 개발팀이
밝혔다.
기사는 이유를 설명하지 않으며, 이 문서도 원인을 확인하지 못했다.
다만 처리 시간이 아니라 컴파일 시점의 문제라는 점이 완화책과 어긋난다는 해석은
기사의 서술과 맞는다.

### 분기 순서와 번호 체계

기사는 GitLab이 먼저 자기 번들에 패치했고 그다음 Ruby의 각 계열이 수정을
받아들였다고 전한다.
Ruby 측이 CVE를 신청하지 않은 상태라 스캐너는 GitLab의 번호를 따라야 한다.
같은 결함에 번호를 붙이는 주체와 수정을 내보내는 주체가 다른 상태이므로,
번호만으로 자기 환경이 영향권인지 판단하기 어렵다.

## 비평

### 기사는 4건의 심각도를 하나로 묶어 전한다

기사에는 네 CVE의 심각도 점수나 인증 필요 여부가 없다.
원격 코드 실행에 악용될 수 있다는 문장은 GitLab 서버를 가리키는데, 일반 Ruby
애플리케이션에서 얼마나 쉽게 악용되는지는 적혀 있지 않다.
같은 매체가 관련 기사로 CVSS 9.9의 GitLab 긴급 패치를 링크했을 뿐, 이 네 건의
점수는 나오지 않는다.
따라서 이 글만으로는 자기 서비스의 긴급도를 정하기 어렵다.

### 어느 CVE가 어느 Ruby 버전에 해당하는지가 빠져 있다

기사의 권장 버전은 4.0.9, 3.4.12, 3.3.13 세 개이고, 그보다 오래된 계열은 언급이
없다.
3.3 이하 계열이 지원 종료 상태인지, 영향을 받는지도 이 글에 없다.
Ruby 4.0.9가 모든 CVE를 고쳤는지도 기사는 한꺼번에 말할 뿐이다.
이 문서는 Ruby의 공식 공지를 열어 보지 못했으므로 이를 확인하지 않았다.

### 한 줄에 두 CVE를 묶은 서술은 오해를 부른다

기사 본문은 CVE-2026-93577과 CVE-2026-97229를 한 줄에 점으로 이어 적었다.
뒤의 것은 CI/CD의 정규식 컴파일러라는 별도 설명이 붙어 있어, 서로 다른
구성요소의 문제인지 같은 엔진 코드의 문제인지 독자가 가리기 어렵다.
기사가 두 번호를 구분하는 이유는 제시되지 않았다.

## 인사이트

### 입력으로 코드를 만드는 모든 곳이 공격 표면이다

정규식은 입력을 검사하는 도구로 여겨지지만, 사용자가 패턴을 쓰게 하는 순간
입력이 작은 프로그램의 소스가 된다.
이 사건은 컴파일러가 신뢰할 수 없는 입력을 받는 구조가 곧 취약점이 된다는 오래된
교훈의 사례다.
SQL, 템플릿, 정규식, 필터 표현식은 같은 부류이며, 이는 이 문서의 해석이다.

### 번호보다 호출 지점을 먼저 찾는다

CVE가 아직 Ruby 쪽에서 정리되지 않았으므로 스캐너 결과만 기다리면 놓칠 수 있다.
소스에서 `Regexp.new`, `Regexp.union`, `Regexp.compile`과 `/#{...}/`를 검색해
인자의 출처가 외부 입력인지 확인하는 것이 번호와 무관하게 할 수 있는 점검이다.
이 점검은 기사의 영향 조건을 검색 가능한 형태로 옮긴 것이다.

### 이 글을 읽는 방법

이 기사는 영향 조건과 대상 버전을 알리는 통지이며, 심각도 판단에는 Ruby와
GitLab의 공식 공지가 필요하다.
오늘 할 일은 사용 중인 Ruby 버전을 확인해 4.0.9, 3.4.12, 3.3.13 이상으로 올리고,
위의 호출 지점을 검색해 외부 입력이 닿는지 보는 것이다.
이 기사의 설명을 가를 관찰은 두 가지다.
Ruby 공식 공지가 이 문제들을 취약점으로 분류하고 자체 CVE를 내는지, 그리고 지원
종료된 Ruby 계열의 영향 여부가 밝혀지는지다.
둘 다 이 기사에는 없다.
