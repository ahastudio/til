## 요약

GitHub의 Karthik Raman과 Brian Celenza가 2026년 11월 5일에 쓴 글이다.
지난주 GitHub Universe에서 발표한 새 Git 스토리지 아키텍처를 설명하는 시리즈의
세 번째 글이며, 앞선 두 글은 두 원칙(조율 최소화, 저장소와 계산의 분리)과
저장소 대부분을 Azure로 옮기는 다리를 다뤘다고 한다.

글이 내세우는 성능은 내부 시험 결과다.
저장소 하나에 동시 에이전트 5,000개가 초당 7,200건의 푸시를 보내면서도 읽기
지연이 계속 낮게 유지되었다고 한다.
현재 GitHub.com에서 가장 바쁜 저장소도 1초에 많아야 수십 건의 쓰기를 받고
그것도 짧은 폭주로 온다고 글은 말한다.
글쓴이들은 에이전트가 늘면 이것이 지속적인 속도가 되리라 예상해
목표를 한 자릿수 증가가 아니라 두 자릿수(100배) 이상으로 잡았다.
한 저장소의 하루 요청이 3월부터 5월까지 약 4배가 된 사례도 든다.

설계의 출발점은 Git 객체가 내용으로 이름이 붙는 불변 데이터라는 관찰이다.
두 작성자가 합의 없이 동시에 저장해도 되므로,
합의가 필요한 것은 참조(브랜치 등) 갱신뿐이고 그것은 크기가 작다.
이를 바탕으로 2026년 5월에 시작한 설계가 Project Rubicon이다.

구성은 다음과 같다.
요청은 여전히 Spokes(라우팅, 부하 분산, 배치와 공정성 담당)로 들어오고
그 아래 데이터 평면이 새로 바뀌었다.

- 가상 복제본(virtual replica): 읽기와 쓰기를 처리하는 일회용 계산 노드다. 로컬 디스크는 언제든 다시 만들 수 있는 캐시다.
- Azure Blob Storage: 팩 파일과 읽기 가속 데이터를 내구성 있게 보관한다.
- Ref-CAS: 참조와 팩 목록(팩 매니페스트)을 담는 별도의 복제 로그 서비스다.
- 압축(compaction) 노드: 가상 복제본과 분리되어 블롭 저장소를 직접 상대로 팩을 합치고 도달할 수 없는 객체를 지운다.

쓰기는 가상 복제본이 팩을 색인해 Blob Storage에 올린 다음,
팩을 매니페스트에 올리고 참조를 갱신하는 트랜잭션 하나를 Ref-CAS에 커밋한다.
읽기는 복제본이 자신이 가진 참조 버전을 Ref-CAS에 물어 바뀌었을 때만 새 참조와
팩 위치를 받고, 필요한 팩을 캐시로 가져와 응답한다.

## 분석

### 불변 객체와 가변 참조를 다른 시스템에 맡긴다

글의 핵심 구분은 거의 모든 데이터가 한 번 쓰이고 바뀌지 않는다는 점이다.
팩과 색인, 읽기 가속 데이터는 서로 다른 키에 한 번만 쓰이므로 객체 저장소에
잘 맞는다.
참조는 반대로 작지만 많은 쓰기가 한꺼번에 경쟁하는 상태다.
같은 데이터를 한 종류의 저장소에 넣지 않고 접근 패턴으로 나누는 것이
이 아키텍처의 첫 결정이다.
글이 Ref-CAS를 작은 합의 그룹이라고 부르며 기존 구조에서 합의 그룹이 어딘가에
남아 있다고 앞선 글에서 말했다고 되새기는 것도 같은 맥락이다.

### 실패한 두 프로토타입이 설계를 정당화한다

글은 먼저 쓴 두 방식을 구체적으로 보여 준다.
첫 번째는 저장소의 모든 참조를 블롭 하나가 색인하는 쓰기 선행 로그였다.
조건부 쓰기는 한 번에 하나만 진행할 수 있어서
푸시를 묶어 보내도 한계가 블롭 하나의 왕복당 한 번의 쓰기였고,
실제로는 초당 수백 건 중반에 머물렀다고 한다.
두 번째는 참조를 해시로 여러 세그먼트 블롭에 나누는 방식이었다.
쓰기 한계는 올랐지만 읽기가 모든 세그먼트를 확인해야 해서
가장 느린 세그먼트에 묶였고, 읽기가 쓰기보다 자릿수로 많아서 손해였다고 한다.
이 대비 덕분에 Ref-CAS의 필요가 설명된다.
쓰기 확장과 읽기 단순성을 동시에 얻으려면 단일 버전 번호가 필요하고,
그것이 로그 순서 번호(LSN)다.

### 합의 범위를 참조 단위로 좁혀 병렬화한다

Ref-CAS의 갱신은 정족수가 커밋하는 비교 후 교환(compare-and-swap)이다.
트랜잭션은 자신이 건드리는 참조만 잠그므로,
각자 자기 브랜치에 푸시하는 에이전트 대부분은 서로 충돌하지 않고 병렬로
복제된다.
같은 참조를 두 푸시가 갱신할 때만 하나가 로그에 추가된다.
이 구조로 참조 상태만으로는 초당 수만 건의 연산을 처리했다고 글은 말한다.
읽기는 자기 버전이 최신이면 응답에 참조가 하나도 담기지 않아
변하지 않은 저장소의 비용이 비교 한 번이다.
Ref-CAS는 객체 데이터를 보관하거나 검증하지 않고 포인터만 담으며,
복제본이 팩을 먼저 올린 다음에 참조 트랜잭션을 커밋하므로
참조는 이미 내구성 있는 객체만 가리킨다.

## 비평

### 헤드라인 숫자의 시험 조건이 빠져 있다

5,000개 에이전트와 초당 7,200건 푸시는 내부 시험이고,
글은 그 시험이 어떤 워크로드였는지 설명하지 않는다.
글 스스로 에이전트 대부분이 자기 브랜치에 푸시해 충돌이 적다고 설명하는데,
시험의 푸시가 서로 다른 참조를 향했는지, 같은 브랜치에 몰렸는지에 따라
숫자의 의미가 크게 달라진다.
푸시 크기, 저장소 크기, 읽기 부하의 구성, 지연의 구체적 수치(분위수)도 없다.
한 저장소가 초당 7,200건을 받는 일이 현실에서 얼마나 자주 일어날지도
글은 가정으로만 말한다.
HN에서 crote는 저장소 하나에 초당 수천 건의 푸시가 들어오는 상황이 에이전트를
잘못 구성했다는 신호라고 비판했다.
GitHub은 완성된 작업을 올리는 곳이지 에이전트 사이의 실시간 채팅 채널이 아니며,
푸시가 그만큼이면 이슈, 풀 리퀘스트, 댓글, Actions 실행도 따라 늘어난다는
것이다.
그는 처리량을 늘리기보다 사용 한도로 행동을 유도하는 편이 낫지 않느냐고
물었다.[^crote]
글은 이 반론에 답하지 않는다.

### 합의 서비스의 실패 양상이 말해지지 않는다

HN에서 jiggawatts는 Git의 대부분이 내용으로 색인되는 불변 블롭과 이벤트 로그로
추상화되고, 앞은 본래 병렬이며 뒤는 저장소별로 나눌 수 있으므로
기성 시스템으로도 충분하지 않았느냐며 약간 과설계로 보인다고 썼다.[^jiggawatts]
이 지적은 글의 관찰, 곧 합의가 필요한 것은 참조 갱신뿐이라는 점과 같은 전제에
서 있다.
다른 점은 맞춤 서비스가 필요한 이유인데, 글은 두 블롭 방식의 한계를 보여 줄 뿐
기성 합의 시스템을 시험했는지는 말하지 않는다.
글은 계산 노드를 일회용으로 만들고 저장소를 블롭에 두는 것으로
가용성을 얻는다고 설명한다.
그러나 모든 쓰기가 반드시 지나가는 Ref-CAS가 느려지거나 정족수를 잃을 때
저장소가 읽기 전용이 되는지, 일부 저장소만 영향을 받는지에 대한 설명이 없다.
참조 단위로 합의 범위를 좁힌다고 했지만 그 합의 그룹을 어떻게 나누고
저장소를 어디에 배치하는지도 글에 나오지 않는다.
앞선 글이 다루었을 수 있으나 이 글만 읽은 독자에게는 가장 중요한 질문이 남는다.

### 가장 위험한 단계는 다음 글로 미뤄졌다

글은 압축은 모든 객체를 보존하지만 가비지 컬렉션은 아무도 참조하지 않는
객체를 지운다고 구분하고,
안전하게 데이터를 지우는 몇 가지 특별한 동작이 있어 별도의 논의가 필요하다고
말한다.
동시 푸시가 계속 들어오는 상태에서 객체가 정말 도달 불가능한지 판단하는 것은
이 설계에서 가장 틀리기 쉬운 부분이다.
압축 노드가 입력 팩과 출력 팩의 객체가 정확히 같은지 확인한다는 설명은 있지만,
삭제 쪽 안전 장치는 이 글에 없다.
따라서 이 글만으로는 데이터 손실 위험이 어떻게 막히는지 평가할 수 없다.

### 현재의 장애를 줄이는 글이 아니다

HN에서 yakkomajuri는 이 글이 단단한 미래 계획이지만 지금의 장애에는 도움이 되지
않는 것 같다고 읽었다.
글이 수평 확장 기법은 기존 구조에서 이어받고, 이 설계는 저장소 하나 안의 수직
확장을 위한 것이라고 밝히기 때문이다.
글은 지금 가장 바쁜 저장소도 쓰기가 초당 수십 건에 그친다고도 적는다.[^yakkomajuri]
usr1106은 기반이 Azure라는 점을 두고 신뢰성에 의문을 제기했는데,
이는 별도 기사를 인용한 한 댓글러의 우려이며 이 문서는 그 기사를 확인하지
못했다.[^usr1106]
글은 현재 시스템의 장애를 다루지 않고 가용성이 어떻게 달라지는지도 수치로
말하지 않는다.

## 인사이트

### 에이전트 트래픽은 쓰기보다 읽기 증폭을 키운다

글은 푸시 하나가 CI, 배포 시스템, 다른 에이전트의 읽기를 부르므로
읽기 증폭이 쓰기에 비례해 커진다고 설명한다.
그래서 설계의 많은 부분이 변하지 않은 저장소를 싸게 확인하는 데 쓰인다.
버전 하나의 비교로 응답이 끝나는 구조는 이 증폭을 흡수하기 위한 것이다.
에이전트가 사람보다 훨씬 자주 최신 상태를 확인하는 동작을 한다면,
앞으로의 병목은 쓰기가 아니라 최신인지 묻는 질문일 수 있다.
이 문서가 확인하지 못한 것은 에이전트의 폴링 빈도가 실제로 어느 정도인지다.

### Git은 그대로이고 서버는 Git이 아니게 된다

글은 개발자에게 Git은 Git으로 남고 푸시, 가져오기, 브랜치 방식과 보호 규칙도
같다고 말한다.
그러나 다음 단계로 든 항목은 클론 없이 서버에서 읽기, 한 번에 여러 파일을
커밋하는 원자적 커밋 API, 이벤트 스트림, 커밋 옆에 저장하는 에이전트 세션
맥락이다.
이들은 Git 프로토콜의 바깥에 있는 서비스 표면이다.
프로토콜은 호환성을 지키는 껍데기가 되고 에이전트는 더 효율적인 다른 입구를
쓰게 되는 구도다.
이 변화가 Git 자체를 바꾸려는 노력(가벼운 클론, 숨은 확장 비용 제거)과
어떤 관계에 놓일지는 글이 말하지 않으며, 지켜볼 일이다.

### 중앙 집중이 장점이 되는 지점이 있다

bob1029는 자율 에이전트 수천 개가 한 더미에서 협업한다면 Perforce가 더 나을
수 있다고 썼다.
테라바이트 규모를 기본으로 다루고, 파일 독점 잠금이 있고, 일부만 체크아웃할 수
있으며, 에이전트의 체크아웃은 즉시 버릴 수 있어서 분산이라는 Git의 장점이
필요 없다는 논리다.[^bob1029]
이는 한 사람의 의견이다.
그러나 조율 최소화라는 글의 원칙이 낙관적 병행(충돌하면 한쪽이 진다)에
기대고 있다는 점을 떠올리게 한다.
에이전트 수가 늘어 같은 파일을 만지는 일이 잦아지면, Git이 택한 비잠금 모델과
Ref-CAS의 비교 후 교환이 충돌을 사후 처리하는 방식이 한계에 닿을 수 있다.
글은 이 영역을 다루지 않는다.

분명히 적고 있다고 바로잡았다.[^masklinn]
이 논쟁은 모두 댓글러들의 서술이며 이 문서는 jj 문서를 열어 보지 않았다.
pksunkara는 Enroute가 Git 확장 문제를 이미 비슷하게 풀었다고 했는데,
이는 그 댓글러의 주장이며 이 문서는 확인하지 못했다.[^pksunkara]

### 같은 문제에 합의를 남기는 쪽과 지우는 쪽이 갈린다

이 저장소의 `git/git-at-any-scale.md`는 제목으로 보면 Git 호스팅에서 합의를
지우고 S3를 진실로 삼는 설계를 다룬다.
GitHub의 설계는 객체를 블롭에 두는 점이 같지만 참조를 위해 작은 합의 그룹을
남긴다.
두 갈래의 차이는 참조의 순서를 누가 책임지느냐에 있고,
이 글은 그 선택의 이유로 블롭 하나와 세그먼트 두 방식의 한계를 든다.
다른 쪽 설계가 같은 한계를 어떻게 피하는지는 이 문서가 비교하지 않았다.
두 설계의 차이가 실제로 갈리는 지점은 충돌 빈도가 높은 단일 브랜치에서
관찰될 것이다.
