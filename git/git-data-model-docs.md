# Git 공식 문서에 데이터 모델 문서를 넣기까지

원문: [A data model for Git (and other docs updates)](https://jvns.ca/blog/2026/01/08/a-data-model-for-git/)

HN 토론: <https://news.ycombinator.com/item?id=46547306> (8점, 1개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/a2clkv/data_model_for_git> (90점, 1개 댓글)

## 요약

Julia Evans가 2026년 1월 8일에 쓴 글이다.

**지난 가을에 Git 문서 작업에 시간을 쓰기로 했다**는 보고다.

동기가 이 글의 핵심이다.
오랫동안 오픈소스 문서 작업을 생각해 왔는데, **보통은 어떤 것의 문서가 개선될 수 있다고 생각하면 블로그 글이나 진을 쓴다**는 것이다.
그런데 이번에는 이렇게 생각했다고 한다. **대신 공식 문서를 몇 군데 개선할 수는 없을까?**

그래서 Marie와 함께 Git 문서를 몇 가지 바꿨다.

### 데이터 모델 문서

문서 작업을 하다가 알아챈 것이 있다.
Git 문서가 **“객체”, “참조”, “인덱스”라는 용어를 아주 많이 쓰는데, 그 용어들이 무엇을 뜻하는지, 그리고 “커밋”과 “브랜치” 같은 다른 핵심 개념과 어떻게 관계되는지에 대한 좋은 설명이 없다**는 것이다.

그래서 새 “데이터 모델” 문서를 썼다. **1,600 단어**짜리다.

왜 신났는지도 밝힌다.
**Git이 커밋과 브랜치 데이터를 어떻게 조직하는지 이해한 것이 여러 해 동안 Git이 어떻게 동작하는지 추론하는 데 정말 도움이 되었으며**, 그래서 데이터 모델의 짧고 정확한 판본이 있는 것이 중요하다고 생각한다는 것이다.

그런데 **“정확한” 부분이 그리 쉽지 않았다**고 적는다.
데이터 모델의 기본은 알고 있었는데 **검토 과정에서 새 세부를 배웠고 꽤 많이 고쳐야 했다**는 것이다.
예로 든 것이 **병합 충돌이 스테이징 영역에 어떻게 저장되는지**다.

### man 페이지 개선

핵심 man 페이지 몇 개의 도입부도 손봤다.

그런데 금방 깨달았다고 한다. **“내 판단으로 그냥 개선해 보자”는 통하지 않는다**는 것이다.
**왜 메인테이너들이 내 판본이 더 낫다고 믿어야 하는가**라는 것이다.

그리고 오픈소스 문서 변경을 논의할 때 자주 보는 문제를 짚는다.
**전문 사용자 두 명이 어떤 설명이 명확한지 아닌지를 두고 다투는 것**이다. “X가 좋은 설명 방식 같은데!” “아니, Y가 더 나을 것 같은데!”

이것이 생산적이지 않다고 보는데, 이유가 결정적이다.
**소프트웨어의 전문 사용자는 어떤 설명이 비전문가에게 명확할지 판단하는 데 악명 높게 서투르기 때문**이다.

그래서 man 페이지의 문제를 **좀 더 증거에 기반해** 찾아낼 방법이 필요했다는 것이다.

### 시험 독자를 모았다

방법이 단순하다.

Mastodon에서 시험 독자를 모집해 **현재 판본의 문서를 읽고 무엇이 헷갈리는지, 어떤 질문이 생기는지 말해 달라고 했다**.
**약 80명이 의견을 남겼고 정말 많이 배웠다**고 적는다.

받은 피드백의 종류가 넷이다.

**이해하지 못한 용어**(pathspec이 뭔가? “reference”가 무슨 뜻인가? Git에서 “upstream”에 특정한 의미가 있나?),
**구체적으로 헷갈리는 문장**,
**추가할 것에 대한 제안**(“나는 X를 늘 하는데 여기 들어가야 할 것 같다”),
**비일관성**(“여기서는 X가 기본값이라는 뜻인데 다른 데서는 Y가 기본값이라고 한다”)이다.

그리고 이 방법의 결정적 설계가 여기 있다.

**시험 독자 대부분이 Git을 최소 5~10년 써 온 사람들이었고 그것이 잘 통했다**는 것이다.
**5년 넘게 정기적으로 Git을 써 온 시험 독자 집단이 어떤 문장이나 용어를 이해할 수 없다고 하면, 문서를 더 명확하게 고쳐야 한다고 주장하기가 쉬워지기 때문**이다.

이 **“소프트웨어 사용자들에게 기존 문서에 대해 의견을 달게 하고 그들이 찾은 문제를 고친다”는 패턴이 정말 잘 통했다**고 평가하며, 앞으로 다시 시도해 볼 생각에 신난다고 적는다.

### 바뀐 man 페이지

네 개를 고쳤다. `git add`, `git checkout`, `git push`, `git pull`이다.

`git push`와 `git pull` 변경이 가장 흥미로웠다는데, 도입부 갱신에 더해 두 가지를 새로 썼기 때문이다.
**“upstream branch”라는 용어가 무엇을 뜻하는지 설명하는 절**(이전에는 제대로 설명되지 않았다)과 **“push refspec”이 무엇인지에 대한 정리된 설명**이다.

그리고 이 작업이 오픈소스 문서를 유지하는 일이 얼마나 많은 노동인지 알게 해 줬다고 적는다.
**명확하면서 동시에 참인 것을 쓰기가 쉽지 않고, 가끔은 타협해야 했다**는 것이다.

예로 든 문장이 구체적이다.
**“`git push`는 현재 브랜치에 upstream을 설정하지 않았으면 실패할 수 있는데, `push.default`가 무엇으로 설정되어 있느냐에 따라 다르다”**는 문장이 조금 모호한데, **“따라 다르다”가 정확히 무엇을 뜻하는지의 세부가 정말 복잡하고 그것을 풀어내는 것은 큰 프로젝트**이기 때문이다.

### Git에 기여하는 과정

Git 개발 과정을 이해하는 데 한참 걸렸다며 짧은 메모를 남긴다.

Git에 **“my first contribution” 채널이 있는 Discord 서버**가 있고 사람들이 매우 환대해 주었다는 것이다.

모든 기여를 **GitGitGadget**으로 했다. 자기가 편한 GitHub 풀 리퀘스트를 만들면 **GitGitGadget이 그것을 Git 개발자들이 쓰는 시스템(패치가 첨부된 이메일)으로 변환해 준다**는 것이다.
**Git으로 이메일 패치를 보내는 법을 배우지 않아도 되어서 아주 고마웠다**고 적는다.

그 밖에는 평소 이메일 클라이언트로 답장했고, **메일링 리스트 관례에 맞춰 80자로 줄바꿈**했다.
그리고 `lore.kernel.org`의 메일링 리스트 아카이브가 탐색하기 어려워서 **긴 스레드를 읽기 쉽게 자기 Git 리스트 뷰어를 뚝딱 만들었다**고 한다.

감사 명단에 Emily Shaffer, GitGitGadget 저자인 Johannes Schindelin, Patrick Steinhardt, Ben Knoble, 그리고 **Git 메인테이너인 Junio Hamano**가 들어 있다.

## 분석

### 이 글의 진짜 기여는 문서가 아니라 방법론이다

이 글에서 재사용 가능한 것이 데이터 모델 문서가 아니라 **시험 독자 방법**이다.

저자가 푼 문제를 정확히 보면 이렇다.

문서 개선 제안이 막히는 지점이 **“당신 설명이 더 낫다는 것을 어떻게 아는가”**다.
그리고 이 질문에 답할 방법이 없으면 논의가 취향 싸움이 된다. 저자가 “X가 좋다” “아니 Y가 낫다”의 교착이라고 표현한 그것이다.

시험 독자 방법이 그 질문을 **다른 질문으로 바꾼다**.

| 답할 수 없는 질문     | 답할 수 있는 질문                 |
| --------------------- | --------------------------------- |
| 내 설명이 더 명확한가 | 80명이 어느 문장에서 걸렸는가     |
| 이 용어가 어려운가    | 몇 명이 이 용어를 모른다고 했는가 |
| 이 내용이 필요한가    | 몇 명이 이것을 물었는가           |

전자는 의견이고 후자는 관찰이다.

그리고 관찰은 **반박이 아니라 해석의 대상**이 된다. 누군가 “그 사람들이 틀렸다”고 말할 수는 있지만, 그러면 왜 80명이 틀렸는지 설명해야 한다.

그래서 이 방법이 문서 논쟁의 성격을 바꾼다.
제안자가 자기 판단을 방어하는 구도에서, **양쪽이 같은 데이터를 보고 해석하는 구도**로 옮겨 간다.

### 초보자가 아니라 숙련자를 시험 독자로 쓴 것이 결정적이다

이 방법에서 가장 영리한 부분이 시험 독자의 구성이다.

직관적으로는 **문서가 명확한지 보려면 초보자에게 읽혀야 할 것 같다**. 대상 독자가 그들이니까.

그런데 저자는 **Git을 5~10년 이상 쓴 사람들**을 모았다.

이유가 명시되어 있다.
**5년 넘게 정기적으로 쓴 사람들이 어떤 문장을 이해할 수 없다고 하면 문서를 고쳐야 한다고 주장하기 쉬워지기 때문**이다.

이 선택이 왜 더 강력한가.

초보자가 못 알아들으면 **“아직 몰라서 그렇다”는 반박이 가능하다**. 문서가 전제 지식을 요구하는 것은 정당할 수 있기 때문이다.
10년차가 못 알아들으면 그 반박이 봉쇄된다. **전제 지식이 있는데도 못 알아들었다는 뜻**이기 때문이다.

즉 시험 독자의 숙련도를 올리면 **표본이 줄어드는 대신 증거의 힘이 세진다**.

그리고 이것이 앞선 [터미널 불만 설문](../cli/terminal-frustrations.md)의 구조와 같다.
그 설문에서도 응답자의 40%가 21년 이상 경력이었고, 저자가 **“완전한 초보자에게서 온 것이 아니다”**를 굵게 강조했다.

두 경우 모두 **숙련자의 혼란을 증거로 쓴다**.

그러므로 이 방법을 옮겨 쓸 때 기억할 규칙이 하나 나온다.
논쟁을 끝내는 것이 목적이면 반박당하기 어려운 표본을 고르고, 문서를 실제로 좋게 만드는 것이 목적이면 **대상 독자와 같은 표본을 고른다**.
저자가 전자를 택한 것은 상대가 Git 메인테이너였기 때문이다.

### 정확한 것을 쓰기가 명확하게 쓰기보다 어려웠다

저자가 데이터 모델 문서에 대해 **“정확한 부분이 그리 쉽지 않았다”**고 적고, 검토 과정에서 새 세부를 배워 꽤 많이 고쳤다고 밝힌다.

그 예가 **병합 충돌이 스테이징 영역에 어떻게 저장되는지**다.

이 대목이 이 글에서 가장 조용하면서 중요하다.

저자는 Git에 대한 책을 쓴 사람이다. “How Git Works”를 쓰면서 **Git이 어떻게 동작하는지 안다고 생각했고 실제로 맞았다**고 [터미널 진 글](../cli/secret-rules-of-the-terminal.md)에서 적었다.

그런데 공식 문서에 넣으려니 **틀린 데가 나왔다**.

차이가 무엇인가.

블로그와 진은 **유용하면 된다**. 단순화가 허용되고, 예외를 생략해도 되고, “대체로 이렇다”가 정당하다.
공식 문서는 **참이어야 한다**. 읽는 사람이 그것을 기준으로 삼기 때문이다.

그리고 이 차이가 검토 과정에서만 드러난다. 스스로는 자기가 단순화한 곳과 틀린 곳을 구분할 수 없다.

`git push` man 페이지의 타협 문장이 그 긴장의 표본이다.
**“`push.default`가 무엇으로 설정되어 있느냐에 따라 다르다”**가 모호한데, 정확히 쓰려면 별도 프로젝트가 되므로 모호한 채로 두었다.

즉 **명확함과 정확함이 충돌할 때 공식 문서는 정확함을 택하고 모호함을 감수한다**.
반대로 블로그는 명확함을 택하고 부정확함을 감수한다.

이 구분을 알면 두 종류의 글을 왜 둘 다 써야 하는지도 설명된다.

## 비평

### 90점에 댓글 1개라는 반응이 이 작업의 성격을 말해 준다

Lobste.rs에서 이 글이 **90점을 받았는데 댓글은 한 개**다.

그 한 개가 alper의 것이다.[^alper]
**세상에 나와 있는 가장 핵심적인 소프트웨어 인프라 중 하나에 대해, 아무도 문서화하려 들지 않았던 모든 것을 문서화하는 감사받지 못하는 일**이라는 것이다.
그리고 한 줄을 덧붙였다. **“이것 하나는 하자. 그 일이 그에게 그렇게까지 감사받지 못하는 일이 되지 않게 하자.”**

HN의 유일한 댓글도 같은 방향이다.

wscott가 적었다.[^wscott]
이런 작업이 정말 값지고 꼭 필요하다며, 오픈소스 프로젝트에 기여하는 데 **놀라울 정도로 마찰이 많다**는 점도 짚었다. 이 글이 그 어려움과 마찰을 잘 드러냈다는 것이다.
그리고 결정적인 한 줄을 붙였다. **공식 문서 개선이 헷갈리는 개념을 설명하는 독립 블로그 글보다 훨씬 낫다.**

이 반응 패턴 자체가 읽을 거리다.

90점은 “이것은 좋은 일이다”이고 **댓글 1개는 “덧붙일 말이 없다”**이다.

그리고 이것이 문서 작업의 구조적 위치를 보여 준다.
기술 논쟁 글은 반론을 부르고, 새 도구는 비교를 부르고, 성능 개선은 벤치마크 의심을 부른다.
문서 개선은 아무도 반대하지 않고 **아무도 말을 보태지 않는다**.

그 결과가 alper가 말한 “감사받지 못하는 일”이다. 반대가 없다는 것과 관심이 있다는 것이 다르기 때문이다.

그리고 이것이 왜 이 일이 미뤄져 왔는지도 설명한다.
칭찬은 받지만 논의를 만들지 않는 일은 **우선순위에서 밀린다**.

### wscott의 한 줄이 이 저장소에 대한 논평이기도 하다

**“공식 문서 개선이 헷갈리는 개념을 설명하는 독립 블로그 글보다 훨씬 낫다”**는 문장을 진지하게 받으면 불편한 함의가 있다.

저자 자신이 이 글 첫 문단에서 같은 것을 인정했다.
**보통은 문서가 개선될 수 있다고 생각하면 블로그 글이나 진을 쓴다**는 것, 그리고 이번에는 **대신** 공식 문서를 고쳐 보면 어떨까 생각했다는 것이다.

“대신”이 핵심이다. **블로그 글이 문서 개선의 대체재로 기능해 왔다**는 뜻이기 때문이다.

그리고 그 대체가 완전하지 않다.

[cherry-pick 3방향 병합 문서](cherry-pick-3way-merge.md)에서 arxanas가 정확히 그 공백을 지적했다.
**거의 모든 Git 학습 자료가 3방향 병합에 관한 결정적인 정보를 빠뜨리며, 대부분 DAG 수준에서만 다루는데 그래프 구조만으로는 Git이 실제로 어떻게 행동할지 예측할 수 없다**는 것이다.

그리고 저자 자신도 그 글에서 **Git 소스 코드 말고는 James Coglan의 “Building Git”이 `cherry-pick`이 3방향 병합을 쓴다고 설명하는 유일한 자료**였다고 적었다.

즉 상황이 이렇다.
설명이 잘된 블로그 글이 많은데, 그것들이 공식 문서의 공백을 메우지 못하고 오히려 **공백을 견딜 만하게 만든다**.

좋은 블로그 글이 있으면 검색으로 찾을 수 있고, 찾을 수 있으면 공식 문서를 고칠 압력이 줄어든다.

이 글의 데이터 모델 문서가 그 순환을 끊는 시도다. **1,600 단어를 블로그가 아니라 `git help` 안에 넣는 것**이다.

그리고 두 곳의 차이가 크다. 블로그는 검색해야 찾고 공식 문서는 **이미 설치되어 있다**.

### 방법론에 대한 검증이 아직 없다

저자가 시험 독자 방법이 **정말 잘 통했다**고 평가하고 다시 시도해 볼 생각에 신났다고 적는다.

그런데 이 글에는 그 평가를 뒷받침할 것이 없다.

무엇이 없는가.

**바뀐 문서가 실제로 더 나은지에 대한 측정**이 없다. 시험 독자들이 지적한 문장을 고쳤지만, 고친 판본을 다시 시험 독자에게 읽혔다는 언급이 없다.
그리고 **메인테이너들이 이 증거 때문에 설득되었는지**도 명시되지 않는다. 변경이 받아들여졌다는 사실만 있다.

전자가 특히 아쉽다.
**“80명이 이 문장에서 걸렸다”가 문제의 증거이지 해결의 증거는 아니기 때문**이다. 고친 문장이 다른 방식으로 걸릴 수도 있다.

방법론을 한 바퀴 더 돌리면 이렇게 된다.

```text
1. 현재 문서에 대한 시험 독자 피드백 수집
2. 지적된 지점 수정
3. 수정본에 대해 새 시험 독자 그룹에게 다시 읽힘   ← 이 단계가 없다
4. 걸리는 지점이 줄었는지 확인
```

3단계가 없으면 **수정이 개선이라는 것이 다시 판단의 문제**가 된다. 저자가 피하려 했던 바로 그 지점으로 돌아간다.

물론 자원 문제가 있다. 80명을 두 번 모으는 것이 쉽지 않고, 자원봉사 기반이면 더 그렇다.
다만 이 방법을 남이 쓰려 할 때 **가장 먼저 부딪히는 한계가 여기**라는 점은 짚어 둘 만하다.

### 기여 과정의 마찰이 부수적으로 기록되었다

이 글에서 의도치 않게 드러난 것이 **Git에 기여하는 것이 얼마나 번거로운가**다.

저자가 나열한 것을 보면 이렇다.
개발 과정을 이해하는 데 한참 걸렸고, GitGitGadget이 없었다면 **이메일로 패치 보내는 법을 배워야 했고**, 메일링 리스트 관례에 맞춰 80자 줄바꿈을 했고, 아카이브가 탐색하기 어려워 **자기 뷰어를 직접 만들었다**.

마지막 항목이 특히 시사적이다.

문서를 고치러 온 사람이 그 과정에서 **도구를 하나 만들어야 했다**.

wscott가 **오픈소스 프로젝트 기여에 놀라울 정도로 마찰이 많다**고 한 것이 이것을 가리킨다.

그리고 이 마찰이 문서 기여에 특히 불리하게 작용한다.

코드 기여자는 그 프로젝트의 코드를 이미 읽고 있으므로 개발 과정에 노출되어 있다.
**문서 기여자는 그렇지 않다.** 사용자로서 문서의 문제를 발견하고, 고치려면 개발자 도구 사슬 전체를 통과해야 한다.

즉 **문제를 발견할 위치와 고칠 권한이 있는 위치 사이의 거리가 문서에서 가장 멀다**.

Git에 “my first contribution” 채널이 있는 Discord가 있고 GitGitGadget이 있다는 사실이 그 거리를 줄이려는 노력이다. 그리고 저자가 그것들 덕분에 했다고 명시한다.

## 인사이트

### 전문가는 자기가 무엇을 아는지 모른다

저자가 방법론의 근거로 댄 한 문장이 이 글에서 가장 일반화할 만하다.

소프트웨어의 전문 사용자는 어떤 설명이 비전문가에게 명확할지 판단하는 데 **악명 높게 서투르다**.

이것이 왜 그런가.

전문가가 어떤 설명을 읽을 때, 그 설명이 빠뜨린 부분을 **자기 지식으로 자동으로 메운다**. 그리고 메웠다는 사실을 자각하지 못한다.
그러면 그 설명이 완전해 보인다.

Git 문서의 “pathspec”이 예다. 아는 사람에게는 정확한 용어이고 모르는 사람에게는 벽이다.
그런데 아는 사람은 **그것이 벽이라는 사실을 관찰할 수 없다**. 자기는 통과하기 때문이다.

이것이 문서뿐 아니라 코드 리뷰와 API 설계와 교육 전반에 적용된다.

**설명의 명확함은 설명하는 사람이 판단할 수 없는 속성이다.** 판단하려면 그 설명이 대상에게 어떻게 작동하는지 관찰해야 한다.

그래서 이 영역에서 의견 교환이 잘 안 된다.
두 전문가가 “내 설명이 더 명확하다”고 주장할 때, **둘 다 자기 설명만 자기에게 명확하다는 것을 확인하고 있다**.

저자의 해법이 그 구조를 정면으로 피해 간다. **판단하지 말고 관찰하라**는 것이다.

그리고 이 원칙을 실무에 옮기는 최소 형태가 있다.
문서를 쓰고 나서 **그 문서를 읽을 사람 중 한 명에게 소리 내어 읽으며 막히는 곳을 말해 달라고 하는 것**이다. 80명이 아니어도 한 명이 0명보다 압도적으로 낫다.

### 무료 대체재가 있으면 원본은 고쳐지지 않는다

이 글의 첫 문단과 wscott의 댓글이 함께 만드는 함의가 이 문서에서 가장 불편한 부분이다.

저자가 **보통은 블로그 글이나 진을 쓴다**고 적었고, wscott는 **공식 문서 개선이 그것보다 훨씬 낫다**고 적었다.

둘을 합치면 이렇게 된다.
좋은 비공식 설명이 존재하면 **공식 문서를 고칠 동기가 줄어든다**.

메커니즘이 명확하다.
사용자가 `git help push`에서 막히면 검색하고, 좋은 블로그 글을 찾고, 문제가 해결된다.
그러면 아무도 **`git help push`가 불충분하다고 보고하지 않는다**.

그리고 블로그 글을 쓴 사람도 만족한다. 자기 글이 읽히고 도움이 되기 때문이다.

이 균형이 안정적이라는 점이 문제다. 모두가 각자 만족하는데 **원본은 그대로다**.

같은 패턴이 여러 곳에 있다.
Stack Overflow 답변이 공식 문서를 대신하고, 사내 위키가 코드 주석을 대신하고, 잘 아는 동료가 온보딩 문서를 대신한다.

그리고 **대체재의 품질이 높을수록 균형이 더 안정적**이다.

깨는 방법은 하나뿐이다. **대체재를 만들던 사람이 원본으로 가는 것**이다.
그것이 이 글이 기록한 일이고, 저자가 “대신”이라는 단어로 스스로 표시한 전환이다.

여기서 나오는 실무 규칙이 있다.
어떤 주제에 대해 사내 문서를 세 번째로 쓰게 되었다면, **그 주제의 원본 문서를 고치는 것이 맞는지** 한 번 물어야 한다.
세 번 썼다는 것은 그 공백이 우연이 아니라는 증거이기 때문이다.

### 증거가 필요한 이유는 상대가 틀려서가 아니라 판단 근거가 없어서다

저자가 시험 독자를 모은 이유를 다시 보면, 메인테이너들을 **설득**하려는 것이 아니었다.

**“왜 메인테이너들이 내 판본이 더 낫다고 믿어야 하는가?”**라고 스스로 물었다.

이 질문의 방향이 중요하다. 상대를 이기려는 것이 아니라 **상대가 판단할 수단을 만들려는 것**이다.

Git 메인테이너 입장에서 생각하면 이 문제가 분명해진다.
문서 개선 제안이 들어올 때, 그것이 개선인지 취향인지 구분할 방법이 없다. 그리고 잘못 받아들이면 문서가 나빠진다.
그러니 보수적으로 굴 수밖에 없고, 그것이 문서 기여가 어려운 진짜 이유다.

시험 독자 데이터가 하는 일이 그 부담을 덜어 주는 것이다.
“내 말을 믿어 달라”가 아니라 “이 사람들이 여기서 막혔다”로 바뀌면, **메인테이너가 판단할 대상이 생긴다**.

이 구조가 문서에만 적용되는 것이 아니다.

코드 리뷰에서 “이게 더 읽기 쉽다”는 주장이 막히는 이유도 같고, 디자인 변경 제안이 취향 논쟁이 되는 이유도 같다.
공통점은 **제안자만 접근 가능한 판단을 근거로 들었다**는 것이다.

일반화하면, 주관적 품질에 대한 제안이 막힐 때 필요한 것은 더 나은 논증이 아니라 **상대도 볼 수 있는 관찰**이다.

그리고 그 관찰을 만드는 비용이 대개 제안자에게 있다. 저자가 80명을 모은 것이 그 비용이다.

제안이 거절당했을 때 물어야 할 것은 “왜 내 말을 안 믿지”가 아니라 **“내가 상대에게 무엇을 보여 줬지”**다.
