# Git 2.56: 해결한 충돌만 스테이징하고, 병합 기준점 탐색을 일찍 멈추다

원문: [Highlights from Git 2.56 - The GitHub Blog](https://github.blog/open-source/git/highlights-from-git-2-56/)

HN 토론: <https://news.ycombinator.com/item?id=49886850> (10점, 3개 댓글)

## 소개

GitHub의 Elijah Newren이 2026년 9월 28일 쓴 Git 2.56 하이라이트다.
Newren은 Git 2.34부터 기본 병합 전략인 merge-ort의 설계자이자 구현자이고, Git 프로젝트가 공식 권장하는 이력 재작성 도구 git-filter-repo의 저자다.
Git 2.56.0은 104명이 넘는 기여자의 기능과 버그 수정을 담았고, 그 가운데 39명이 새 기여자다.

글은 세 가지 주요 변경과 여러 작은 변경으로 되어 있다.
주요 변경은 해결한 충돌 경로만 골라 스테이징하는 `git add --resolved`, 더 이상 병합 기준점이 나올 수 없을 때 탐색을 멈추는 merge-base 최적화, 그리고 서버에서 path-walk 재팩을 쓸 수 있게 한 비트맵·델타 아일랜드 지원이다.
작은 변경으로는 `git history drop`, `git refs` 명령군, `git branch --delete-merged`, `git bisect run --reset-when-found`, `git replay --linearize`, 흔한 명령 실수 제안, 부분 클론의 큰 blob 버리기, `git log --follow`의 비선형 이력 추적, 그래프의 시각적 루트 들여쓰기, 여러 성능 절벽 제거가 있다.

이 노트는 사용자가 바로 쓸 수 있는 명령과, 그 명령들이 약속하는 것과 약속하지 않는 것을 중심으로 정리한다.
이 저장소에는 LWN이 릴리스 전에 쓴 전망을 다룬 `git-2-56-and-3-0.md`도 있는데, 그쪽은 SHA-256과 reftable과 Rust라는 3.0으로 가는 전환을 다루고, 이 노트는 2.56에 실제로 들어간 기능을 다룬다.

## 새 명령 쓰기

### 해결한 충돌만 스테이징하기

병합 충돌을 해결하는 일은 두 단계다.
작업 트리의 충돌 경로를 원하는 결과로 고친 뒤, 그 경로를 스테이징해 충돌이 해결되었다고 Git에 알린다.
두 번째 단계에서 흔히 쓰는 `git add -u`는 수정된 모든 추적 경로를 스테이징하므로, 병합과 무관한 로컬 변경까지 올리고, 충돌 표시를 하나 빠뜨린 파일도 그대로 올린다.

`git add --resolved`는 이 단계를 위해 만든 모드다.
색인에서 현재 병합되지 않은(unmerged) 경로만 고려하고, 스테이징하기 전에 병합되지 않은 일반 파일에서 남은 충돌 표시를 찾는다.
하나라도 남아 있으면 해당 경로를 알리고 색인을 바꾸지 않는다.

```bash
git add --resolved
# fatal: the following paths still have conflict markers:
#         recipe.txt

# recipe.txt 의 충돌 표시를 지운 뒤 다시
git add --resolved
git status --short
#  M notes.txt     ← 병합과 무관한 로컬 변경은 스테이징되지 않은 채 남는다
# M  recipe.txt    ← 해결한 충돌만 스테이징된다
```

경로 지정자(pathspec)로 대상 범위를 좁힐 수 있지만, 선택 범위 안에서는 전부 아니면 전무 규칙이 유지된다.
선택한 일반 파일 중 하나라도 충돌 표시가 남아 있으면 아무것도 스테이징하지 않는다.
해결된 삭제와 바이너리 충돌은 텍스트 표시가 없으므로 그대로 스테이징된다.
`-u`나 `-A`와 함께 쓸 수 없고, 충돌이 없었던 추적 파일은 무시한다.

### 병합된 로컬 브랜치 한꺼번에 지우기

```bash
# origin 아래 upstream을 가진 topic-* 브랜치 가운데 지울 수 있는 것만 보여 준다
git branch --delete-merged 'origin/*' 'topic-*' --dry-run

# 실제로 지운다
git branch --delete-merged 'origin/*' 'topic-*'

# 특정 브랜치를 일괄 정리에서 보호한다
git config branch.release-notes.deleteMerged false
```

첫 패턴은 upstream이 `origin` 아래에 있는 브랜치를, 둘째 패턴은 로컬 이름이 `topic-`으로 시작하는 브랜치를 고른다.
실제 삭제는 브랜치 끝이 해당 upstream에서 도달 가능한 경우에만 일어난다.
워크트리에서 체크아웃된 브랜치, upstream이 없는 브랜치, 모호한 push 설정을 가진 브랜치 몇 종류는 건너뛴다.

### 커밋 하나 빼기

실험적 명령 `git history`는 2.54의 `reword`와 `split`, 2.55의 `fixup`에 이어 2.56에서 `drop`을 얻었다.

```bash
git history drop <commit>
```

선택한 커밋을 지우고 그 후손을 커밋의 부모 위에 다시 재생한다.
`HEAD`가 움직이면 색인과 작업 트리를 갱신하되 무관한 로컬 변경은 보존한다.
후손을 재생하다 충돌하거나 로컬 변경을 덮어쓰게 되면 중단한다.
여전히 실험적이며, 병합 커밋이 있는 이력에서는 쓸 수 없고, 루트 커밋이나 병합 커밋은 지울 수 없다.

### 참조를 다루는 저수준 명령

흩어져 있던 참조 쓰기 명령이 `git refs` 아래로 모이고 있다.

```bash
git refs create refs/heads/topic <new-value>
git refs update refs/heads/topic <new-value> [<old-value>]   # old-value를 주면 비교 후 교체
git refs delete refs/heads/topic [<old-value>]
git refs rename refs/heads/old refs/heads/new
```

선택적인 이전 값은 갱신과 삭제에 비교 후 교체(compare-and-swap) 보호를 준다.
일부러 저수준으로 만든 명령이라, `git refs rename`은 참조와 reflog를 옮기지만 `git branch -m`이 하는 브랜치 설정 조정은 하지 않는다.

### 그 밖의 명령

`git bisect run`에 `--reset-when-found[=<where>]`가 생겼다.
기본값 `original`은 이분 탐색을 시작하기 전의 커밋으로 돌아가고, `found`는 이분 탐색 상태만 정리하고 원인 커밋에 머문다.
`--no-checkout`과는 함께 쓸 수 없다.

실험적 명령 `git replay`는 `--linearize`로 병합 구조를 평평하게 만들 수 있다.
커밋을 한 줄로 재생하고 병합 커밋을 버리며, 작업 트리를 쓰지 않고 `git rebase --no-rebase-merges`와 같은 구조를 만든다.
`--contained`나 여러 브랜치를 한 번에 재생하는 것과는 함께 쓸 수 없다.

부분 클론에서 필요할 때 가져온 blob은 지금까지 로컬에 영원히 남았다.
2.56은 크고 다시 가져올 수 있는 blob을 버리고 promisor 원격에 다시 기대게 할 수 있다.

```bash
git repack -a --filter=blob:limit=1m --drop-filtered --dry-run   # 후보만 보여 준다
git repack -a --filter=blob:limit=1m --drop-filtered              # 실제로 버린다
```

자동으로 크기가 제한되는 캐시가 아니라 수동 정리 도구이고, 현재는 `blob:limit` 필터만 지원한다.
promisor 원격이 있어야 하며, 현재 색인이 참조하는 객체를 버리는 것 같은 위험한 경우는 거부한다.
이 작업은 Siddharth Shrimali의 GSoC 프로젝트이며, Christian Couder와 Siddharth Asthana가 멘토로 기록되어 있다.

`git log --graph`는 여러 루트가 있는 그래프에서 무관한 커밋이 루트 바로 아래 같은 열에 놓여 이어진 것처럼 보이던 문제를, 필요할 때 시각적 루트를 들여써서 고쳤다.
기본으로 켜지며, 옛 렌더링은 `--no-graph-indent`로, 기본값은 `log.graphIndent`로 정한다.

`git push origin/main`처럼 치면 `git push origin main`을, `git branch --set-upstream-to origin main`처럼 치면 `--set-upstream-to=origin/main`을 제안한다.
제안하기 전에 그 수정이 그럴듯한지 확인해 무분별하게 추측하지 않는다.

## 동작 방식

### merge-base 탐색이 일찍 멈추는 이유

병합은 두 커밋의 가장 좋은 공통 조상을 출발점으로 쓰고, 세 점 diff는 토픽 브랜치의 작업이 어디서 시작하는지 정하는 데 쓴다.
저장소 호스트도 풀 리퀘스트 diff, 병합 가능성 검사, 리뷰 범위 계산에 같은 계산을 한다.
Git은 양쪽 끝에서 뒤로 걸어가며 한쪽에서 도달한 커밋을 파랑, 다른 쪽을 빨강으로 칠하고, 두 색이 모두 닿은 커밋을 후보로 삼는다.

후보 하나로는 끝나지 않는다.
교차 병합(criss-cross merge)은 서로의 조상이 아닌 병합 기준점을 여러 개 만들 수 있어서, Git은 모든 기준점을 찾을 때까지 계속 걸어야 한다.
옛 종료 규칙은 다른 기준점이 나올 수 없게 된 뒤에도 이미 공통인 오래된 이력을 한참 더 처리했다.

2.56은 대기열에 남은 커밋 가운데 한쪽 색만 칠해진 것이 몇 개인지 센다.
한쪽의 전용 커밋이 바닥나면 새 만남 지점이 생길 수 없으므로, 모든 기준점을 돌려주면서도 거기서 멈출 수 있다.
실제 모노레포 한 사례에서 탐색이 0.68초에서 0.01초로 줄었고, 두 대형 모노레포의 운영 평가에서 한쪽은 70배 안팎으로 빨라진 경우가 많았고 다른 쪽은 평균 20배쯤 빨라졌다.
Linux 커널의 오래된 성능 사례도 고쳐져, 기본 v2 커밋 그래프에서 `git merge-base --all v4.8 v4.9`가 167,441단계 0.29초에서 3,887단계 0.01초가 되었다.

### path-walk 재팩이 서버에서 막혀 있던 이유

재팩은 델타로 효율적으로 저장할 수 있는 비슷한 객체를 찾는다.
전통적인 탐색은 이름 해시로 후보를 묶고, path-walk 재팩은 트리의 위치를 따라 객체를 방문해 같은 경로의 버전들을 모아 훨씬 나은 델타 관계를 찾는다.
Fluent UI 저장소의 최근 클론으로 델타를 다시 계산하게 한 벤치마크에서, 일반 비트맵 재팩은 558.5MB 팩을, `--path-walk` 재팩은 164.4MB 팩을 만들어 약 71% 작았다.

그런데 저장소 호스트에는 작은 팩만으로는 부족하다.
객체 열거 질의에 빨리 답하려고 도달성 비트맵을 쓰고, 어떤 호스트는 한 참조 그룹의 객체가 다른 그룹에만 있는 객체에 의존하지 않게 하려고 델타 아일랜드를 쓴다.
path-walk 재팩은 둘 다와 호환되지 않았다.

2.56은 두 제약을 모두 없앴다.
path-walk 재팩이 새 비트맵에 넣을 커밋을 고를 수 있고, 이후의 `git pack-objects`는 기존 비트맵으로 답할 수 있으면 재사용하고 필요할 때만 path walk로 돌아간다.
델타 기준을 고르기 전에 커밋과 트리를 통해 아일랜드 소속을 전파하는 장부 작업도 한다.
다만 path-walk 재팩이 기본으로 켜지는 것은 아니며, 큰 호스트가 저장 공간 절감을 평가할 수 있게 도입 장벽 두 개를 없앤 것이다.

### 규모에서만 드러나던 절벽

평범한 작업에서 규모가 커질 때만 나타나던 성능 절벽도 여럿 고쳐졌다.
reftable 쓰기는 잠금을 잡은 뒤 불필요한 재로딩을 하지 않아, 파일 시스템 stat 호출이 참조 수에 선형이던 것이 상수가 되었다.
새 팩 파일을 로드할 때마다 기존 목록을 훑던 O(N²) 회귀가 사라져, 팩이 37,815개인 저장소에서 프롬프트 관련 명령이 4.5초 걸리던 문제가 없어졌다.
삭제 표시(tombstone)가 많은 reftable과 경로 제한 작업 트리 diff의 이차 탐색도 없앴고, 추적되지 않은 파일 수집은 이미 정렬된 입력에 기대지 않고 확실히 O(n log n)이 되었다.
reftable 삭제 표시 성능 테스트는 약 13초에서 0.2초로, 색인 항목이 약 50만 개인 Chromium 체크아웃의 어떤 `git diff`는 약 8분에서 0.07초로 줄었다.

`git log --follow`는 전역 “현재 경로” 하나를 유지하던 방식에서 부모마다 경로를 따로 기록하는 방식으로 바뀌었다.
부모마다 경로 이름을 다르게 바꿨을 때 먼저 방문한 쪽이 나머지 탐색을 정하던 문제가 사라져, 결과가 탐색 순서와 무관해지고 서브트리 병합 같은 경우가 고쳐졌다.

## 트레이드오프

### `--resolved`는 안전한 대신 한 번에 하나의 일만 한다

`git add --resolved`의 장점은 범위가 좁다는 것이다.
충돌 경로만 보고, 충돌 표시가 남았으면 아무것도 하지 않는다.
하지만 충돌을 해결하면서 다른 파일도 함께 고쳐야 하는 경우, 예컨대 병합 결과가 빌드되도록 충돌이 없었던 파일을 수정한 경우에는 그 파일을 따로 스테이징해야 한다.
`-u`나 `-A`와 섞을 수 없으므로, 명령 두 번이 필요하다.

전부 아니면 전무 규칙도 양면이 있다.
여러 파일의 충돌 가운데 일부만 해결하고 먼저 스테이징하고 싶다면, 경로 지정자로 해결한 파일만 골라야 한다.
그렇지 않으면 남은 파일 하나 때문에 아무것도 스테이징되지 않는다.
그리고 충돌 표시 검사는 일반 텍스트 파일에서만 의미가 있어서, 바이너리 충돌은 검사 없이 그대로 스테이징된다.
바이너리를 잘못 고른 채 해결했다고 표시하는 실수는 여전히 막지 못한다.

### `git history drop`과 대화형 재배치

`git history drop`은 커밋 하나를 빼는 일을 `git rebase -i`보다 단순하게 만든다.
작업 트리의 무관한 로컬 변경을 보존하고, 충돌하면 중단한다.
대신 병합 커밋이 있는 이력에서는 쓸 수 없고, 충돌이 나면 해결하며 이어 가는 대신 멈춘다.

그래서 이 명령은 선형 이력에서 깔끔하게 빠지는 커밋에 가장 잘 맞는다.
빼려는 커밋에 뒤 커밋이 기대고 있어 충돌이 난다면, 결국 `git rebase -i`로 돌아가 충돌을 직접 해결해야 한다.
실험적 명령이라 동작이 바뀔 수 있다는 점도 스크립트에 넣기 전에 고려해야 한다.

### 큰 blob 버리기는 공간을 되찾는 대신 네트워크 의존을 늘린다

`--drop-filtered`는 부분 클론이 시간이 지나며 불어나는 문제를 해결한다.
대신 버린 blob에 다시 접근하면 promisor 원격에서 다시 가져와야 하므로, 오프라인이거나 원격이 느리면 그 순간 작업이 막힌다.
자동으로 크기를 관리하는 캐시가 아니므로, 언제 무엇을 버릴지는 사용자가 정해야 한다.
먼저 `--dry-run`으로 후보를 보고, 자주 쓰는 큰 파일은 버리지 않도록 크기 기준을 정하는 편이 안전하다.

### path-walk 재팩은 저장 공간과 계산 사이의 선택이다

path-walk 재팩은 팩을 크게 줄이지만, 경로를 따라 객체를 방문하고 더 나은 델타를 찾는 데 계산이 든다.
2.56이 비트맵과 델타 아일랜드 호환을 더했지만 기본값으로 켜지 않은 것은, 호스트마다 저장 공간과 재팩 시간과 서빙 속도의 균형이 다르기 때문이다.
개인 저장소에서 71% 절감은 매력적이지만, 벤치마크는 델타를 강제로 다시 계산한 조건이었다.
평소의 증분 재팩에서도 같은 비율이 나오는지는 자기 저장소에서 재 봐야 한다.

## 함정

`git refs rename`은 `git branch -m`의 대체가 아니다.
참조와 reflog는 옮기지만 `branch.<name>.*` 설정, 곧 upstream이나 병합 설정은 옮기지 않는다.
브랜치 이름을 바꾸려는 목적이라면 여전히 `git branch -m`을 써야 하고, 저수준 스크립트에서 참조만 옮길 때 `git refs rename`을 쓴다.

`git branch --delete-merged`는 upstream에서 도달 가능한지로 판단하므로, 스쿼시 병합이나 리베이스 병합으로 합쳐진 브랜치는 병합된 것으로 보지 않는다.
GitHub의 스쿼시 병합을 쓰는 저장소에서는 실제로 합쳐진 브랜치가 목록에 나오지 않을 수 있다.
반대로 새 작업을 시작하려고 막 만든 브랜치처럼 아직 커밋이 없는 브랜치도 끝이 upstream에 포함되므로 지울 대상이 되니, `--dry-run`을 먼저 돌려 목록을 확인해야 한다.

`git log --graph`의 들여쓰기가 기본으로 켜지므로, 그래프 출력을 파싱하는 스크립트나 도구가 있다면 결과가 바뀔 수 있다.
옛 렌더링이 필요하면 `--no-graph-indent`나 `log.graphIndent`를 설정한다.

`git bisect run --reset-when-found`의 기본값은 원인 커밋이 아니라 시작 전 커밋으로 돌아가는 것이다.
원인 커밋을 조사하려고 했다면 `--reset-when-found=found`를 줘야 한다.

## 확인하기

`git add --resolved`의 동작을 빈 저장소에서 확인한다.
Git 2.56 이상이 필요하다.

```bash
#!/usr/bin/env bash
set -euo pipefail
git --version
dir=$(mktemp -d) && cd "$dir"
git init -q -b main && git config user.email t@example.com && git config user.name t

printf 'flour\n' > recipe.txt && printf 'n1\n' > notes.txt
git add . && git commit -qm base

git switch -qc other
printf 'sugar\n' > recipe.txt && git commit -qam other

git switch -q main
printf 'salt\n' > recipe.txt && git commit -qam main

printf 'n2\n' >> notes.txt                    # 병합과 무관한 로컬 변경
git merge other || true                       # recipe.txt 에서 충돌

git add --resolved || echo "→ 충돌 표시가 남아 있어 아무것도 스테이징되지 않음"
git status --short                             # UU recipe.txt,  M notes.txt

printf 'salt\nsugar\n' > recipe.txt           # 충돌 해결
git add --resolved
git status --short                             # M  recipe.txt,  M notes.txt
```

마지막 출력에서 `recipe.txt`는 스테이징되고 `notes.txt`는 스테이징되지 않은 채 남아야 한다.
같은 상황에서 `git add -u`를 쓰면 `notes.txt`까지 스테이징되는 것을 비교해 볼 수 있다.

merge-base 최적화는 오래된 브랜치가 많이 병합된 큰 저장소에서 차이가 드러난다.
Linux 커널 저장소가 있다면 원문과 같은 명령으로 확인할 수 있다.

```bash
time git merge-base --all v4.8 v4.9
```

## 체크리스트

- 충돌을 해결한 뒤 `git add -u` 대신 `git add --resolved`를 쓰는가?
- 충돌 해결과 함께 고친 다른 파일을 따로 스테이징했는가?
- 바이너리 충돌은 해결 결과를 직접 확인했는가?
- `git branch --delete-merged`를 실제로 돌리기 전에 `--dry-run`을 먼저 돌렸는가?
- 스쿼시 병합을 쓰는 저장소에서 `--delete-merged`가 합쳐진 브랜치를 못 찾는다는 것을 알고 있는가?
- 지우면 안 되는 브랜치에 `branch.<name>.deleteMerged = false`를 설정했는가?
- 브랜치 이름 변경에 `git refs rename`이 아니라 `git branch -m`을 쓰는가?
- 그래프 출력을 파싱하는 도구가 새 들여쓰기 기본값에 영향을 받지 않는가?
- `--drop-filtered`를 쓰기 전에 `--dry-run`으로 후보를 확인했는가?
- 실험적 명령(`git history`, `git replay`)을 자동화 스크립트에 넣지 않았는가?

## 기억할 원칙

### 좋은 명령은 할 수 있는 일보다 하지 않는 일로 정의된다

이번 릴리스의 새 명령들은 공통점이 있다.
`git add --resolved`는 충돌하지 않은 파일을 건드리지 않고, 충돌 표시가 남았으면 아무것도 하지 않는다.
`git branch --delete-merged`는 워크트리에서 체크아웃된 브랜치와 모호한 설정의 브랜치를 건너뛴다.
`git history drop`은 충돌하거나 로컬 변경을 덮어쓸 상황이면 중단한다.
`--drop-filtered`는 색인이 참조하는 객체는 버리지 않는다.

이 명령들은 기존 명령보다 더 많은 일을 하려고 만든 것이 아니다.
기존 명령이 너무 넓게 하던 일을, 필요한 범위로 좁히고 위험한 경우를 거부하도록 만든 것이다.
도구를 설계할 때 기능 목록보다 거부 목록이 사용자를 더 잘 보호한다.

다만 이런 안전 장치는 사람들이 그 명령을 알아야 쓸모가 있다.
HN의 tobwen은 AI로 코딩하는 사람에게는 최신 모델도 이런 새 기능을 모른다며, 변경 로그로 시험해 보니 Git처럼 흔한 도구는 큰 변화가 없었던 탓에 기능 지식의 기준 시점이 2023년이나 그 이전에 머물러 있었다고 적었다.[^tobwen]
pjmlp는 사람도 대부분 이런 기능을 모르고 끝없는 명령줄 옵션의 표면만 만지며, 망가진 로컬 저장소를 고치느니 새로 클론하는 것이 밈이 된 데는 이유가 있다고 답했다.[^pjmlp]
에이전트가 `git add -u`를 습관처럼 쓰는 한 `--resolved`의 보호는 닿지 않는다.
새 안전 명령을 들였다면, 팀 문서나 에이전트 지침 파일에 그 명령을 쓰라고 명시하는 것까지가 도입이다.

### 성능은 평균이 아니라 절벽에서 무너진다

이번 릴리스의 성능 개선은 대부분 평소에는 보이지 않다가 규모가 커질 때 드러나는 절벽이다.
팩 37,815개, 색인 항목 50만 개, 수천 개의 참조처럼 특정 조건에서만 선형이나 이차 비용이 폭발한다.
평범한 저장소에서는 이 차이를 느끼지 못하지만, 모노레포나 오래된 대형 저장소에서는 몇 분이 몇십 밀리초가 된다.

그래서 성능 문제를 찾을 때는 평균 저장소가 아니라 가장 큰 저장소, 가장 오래된 저장소, 가장 이상한 이력을 가진 저장소를 기준으로 봐야 한다.
Git의 이런 개선이 대부분 모노레포를 운영하는 회사들에서 나오는 것도, 절벽은 그 절벽에 부딪히는 사람만 찾을 수 있기 때문이다.
