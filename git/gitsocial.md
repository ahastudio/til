# GitSocial: 이슈와 PR을 Git 커밋으로 저장하고 S3 버킷을 포지로 쓴다

<https://gitsocial.org/>

## 소개

GitSocial은 자신을 “Git-native collaboration platform”이라고 소개하는 Go 바이너리 하나다.
CLI와 TUI로 동작하며, 이슈와 PR 등 협업 데이터를 Git 자체에 저장한다 — `gitmsg/*` 브랜치 위의
커밋으로, 구조화된 트레일러(structured trailers)를 담아서다.

핵심 동작은 하나의 멱등한 명령이다.
GitHub이나 다른 호스트에 있는 프로젝트를 자신이 소유한 S3 호환 버킷으로 미러링한다.

```bash
gitsocial mirror https://github.com/owner/repo s3://<endpoint>/<bucket>/<prefix>
```

그러면 그 버킷이 프로젝트의 완전한 정적 사이트를 제공한다 — 코드, 타임라인, 이슈, 릴리스까지.
동시에 그 버킷은 평범한 `git clone`의 소스로도 쓰인다.
`gitsocial.org` 자체가 이 방식으로 서비스되고 있고, 첫 화면에 브랜치 수와 최신 커밋 해시가
노출된다.

이 구조에서 나오는 주장이 “포지는 선택 사항이 된다(The forge becomes optional)”는 것이다.
이슈, PR, 릴리스, 포스트를 CLI나 TUI로 만들어 다른 커밋과 똑같이 푸시하고, 다른 저장소는
타임라인으로 팔로우한다.

## GitMsg 프로토콜과 확장

문서 구조가 이 프로젝트의 야심을 드러낸다.
개념 문서 다섯 개와 확장 사양 다섯 개로 나뉘어 있다.

| 개념 문서             | 내용                                     |
| --------------------- | ---------------------------------------- |
| GitMsg Protocol       | 핵심 메시지 형식, 헤더, 레퍼런스, 버저닝 |
| S3 Remote             | 버킷을 Git 원격으로 쓰는 방식, 정본 URL  |
| Static Site           | 버킷에서 제공되는 저장소 웹사이트        |
| Identity Verification | 탈중앙 신뢰 모델, 증명 출처, 캐싱        |
| Notifications         | 알림 종류, 범위, 트리거                  |

확장은 각각 별도의 사양 문서를 가진다.

| 확장    | 다루는 것                                         | 사양       |
| ------- | ------------------------------------------------- | ---------- |
| Social  | 포스트, 코멘트, 리스트, 타임라인, 팔로워          | GitSocial  |
| PM      | 이슈, 마일스톤, 스프린트, 라벨, 보드              | GitPM      |
| Review  | PR, 피드백, 포크, 버전 추적, 크로스 포지 시나리오 | GitReview  |
| Release | 릴리스, 아티팩트, 체크섬, 서명, SBOM              | GitRelease |
| Memo    | 지식을 커밋으로 다루는 계층형 메모                | —          |

클라이언트는 네 종류로 정리되어 있다 — Claude Code와 Cursor 등을 위한 Agent Skill, TUI, CLI,
그리고 stdio를 통한 JSON-RPC다.

## 설치와 사용법

설치 경로는 Homebrew, 설치 스크립트, Scoop, `go install`로 나뉜다.

```bash
brew install gitsocial-org/tap/gitsocial
```

기존 저장소를 터미널에서 탐색하려면 아무 호스트에서 클론한 뒤 프로젝트 디렉터리에서 두 명령을
실행한다.

```bash
gitsocial import     # 이슈, PR 등을 가져온다
gitsocial tui        # 터미널에서 탐색한다
```

자기 버킷에 저장소를 직접 호스팅하는 경로는 이렇다.

```bash
gitsocial config credentials set s3.example.com
gitsocial remote add s3://s3.example.com/mybucket/myrepo --default --site
gitsocial push
```

그러면 누구나 `gitsocial clone s3://...`으로 가져올 수 있고, 버킷의 공개 URL에서 평범한
`git clone`으로도 가져올 수 있다.
큰 저장소를 미러링할 때는 `-n 100`으로 먼저 시험해 보라고 안내한다.

## 자체 도구로만 협업한다

기여 안내가 이 프로젝트의 성격을 가장 잘 보여 준다.
모든 미러에서 플랫폼의 이슈와 PR이 비활성화되어 있으며, GitSocial은 협업에 자기 도구를 쓴다.

기여 절차는 아무 호스트(GitHub, GitLab, Codeberg, 자체 호스팅)에서 포크한 뒤 이렇게 진행한다.

```bash
git checkout -b feature/my-change

gitsocial review pr create \
  --base main \
  --head feature/my-change \
  "Short description of change"

git push origin feature/my-change
gitsocial push
```

그리고 첫 푸시 이후에 Matrix 방에서 포크 등록을 요청해야 한다 — 메인테이너가 그 PR과 이슈를
발견할 수 있게 하기 위해서다.

라이선스는 MIT다.

## 분석

### 트레일러를 데이터 모델로 삼은 것은 이 문제의 세 번째 답이다

포지의 락인이 코드가 아니라 코드를 둘러싼 데이터에 있다는 진단은 이미 합의에 가깝다.
이슈와 리뷰 코멘트는 `git clone`으로 따라오지 않고, 그래서 이동 비용이 생긴다.

이 문제에 대한 답이 지금 세 갈래로 갈렸다.
[Radicle](radicle.md)은 Collaborative Objects라는 별도의 Git 오브젝트 타입을 만들었고,
[Tangled](tangled.md)은 AT Protocol의 레코드로 옮겼다.
GitSocial의 답은 가장 보수적이다 — 새 오브젝트 타입도, 새 프로토콜도 만들지 않고 그냥 커밋 메시지의
트레일러를 쓴다.

이 선택의 미덕은 도구 의존이 없다는 것이다.
`Signed-off-by:`나 `Co-Authored-By:`가 그렇듯 트레일러는 Git이 이미 관례로 다루는 형식이고, 파싱에
특수한 라이브러리가 필요하지 않다.
`gitmsg/*` 브랜치에 있으므로 평범한 클론에 함께 따라오고, GitSocial 바이너리가 없어도 `git log`로
읽을 수 있다.

대가는 표현력이다.
트레일러는 키-값 한 줄이므로 중첩 구조나 대용량 본문을 담기 어렵고, 그래서 사양이 다섯 개로
갈라지게 된다 — GitMsg가 형식을 정하고 GitSocial, GitPM, GitReview, GitRelease가 각자의 키 집합을
정의하는 구조다.
Radicle이 COBs 하나로 처리한 것을 GitSocial은 규약 다섯 개로 처리한다.

### S3 버킷을 원격으로 쓴 것이 진짜 발명이다

기술적으로 가장 독특한 부분은 데이터 모델이 아니라 전송 계층이다.

버킷 하나가 세 가지 역할을 겸한다 — Git 원격, 정적 웹사이트, 그리고 평범한 `git clone` 소스다.
서버 프로세스가 없다.
Radicle은 노드를, [Forgejo](forgejo.md)는 웹 애플리케이션을, Tangled은 knot과 spindle을 요구하는데
GitSocial은 객체 스토리지만 요구한다.

이것이 자체 호스팅의 문턱을 다시 정의한다.
Radicle 스레드에서 xvilka가 요청한 것도, Forgejo가 자랑하는 것도 결국 “서버 운영이 얼마나 쉬운가”였다.
GitSocial의 답은 서버를 없애는 것이다 — 버킷을 만들고 공개 접근과 도메인을 프로바이더 대시보드에서
한 번 설정하면 끝이라고 안내한다.

그리고 `gitsocial.org` 자체가 그 방식으로 서비스된다는 것이 증명 방식이다.
첫 화면에 브랜치 수와 최신 커밋이 노출되는 것은 마케팅이 아니라 이 사이트가 정말 저장소의 정적
렌더링이라는 표시다.

### 미러링을 기본 명령으로 둔 것은 이주가 아니라 이중화를 파는 것이다

다른 대안 포지들의 첫 명령은 회원 가입이거나 인스턴스 설치다.
GitSocial의 첫 명령은 `mirror`다.

이 차이가 채택 전략의 차이다.
GitHub을 떠나라고 요구하지 않는다 — GitHub에 있는 그대로 두고 자기 버킷에 완전한 사본을 만들라고
한다.
그 사본이 코드뿐 아니라 이슈와 릴리스와 타임라인까지 포함하고, 정적 사이트로 열람 가능하며,
클론 소스로도 동작한다.

[GitHub에는 대안이 있지만 대체재는 없다](../github/github-alternatives-no-replacement.md)는 진단에
대한 우회로가 여기 있다.
대체재가 되려 하지 않고 보험이 되려 한다.
이주에는 결단이 필요하지만 미러에는 필요하지 않고, 명령이 멱등하다는 것은 그것을 cron에 걸 수 있다는
뜻이다.

## 비평

### 발견 가능성이 Matrix 방의 수동 등록에 걸려 있다

기여 안내의 마지막 문장이 이 설계의 급소를 그대로 노출한다 — 첫 푸시 후 Matrix 방에서 포크 등록을
요청해야 메인테이너가 당신의 PR과 이슈를 발견할 수 있다.

데이터 모델은 완전히 탈중앙이다.
그런데 “어느 포크에 내 PR이 와 있는지”를 아는 방법이 없다.
Git은 푸시를 통보하지 않으므로, 누군가 자기 버킷에 PR 메타데이터를 올려도 원본 저장소는 그것을
알 도리가 없다.

Radicle은 이 문제를 가십 프로토콜로 풀고, Tangled은 AT Protocol의 릴레이로 풀고, Forgejo는 4년째
못 풀고 있다.
GitSocial은 채팅방으로 푼다.
이것을 임시 조치라고 부르는 것도 관대한 표현이다 — 문서에 정식 절차로 적혀 있고, 대체 계획에 대한
언급이 없다.

그리고 이 결함은 프로젝트가 내세우는 미덕과 정확히 충돌한다.
“포지는 선택 사항이 된다”는 주장은 포지가 제공하던 기능 중 발견과 통보를 제외한 나머지에만
해당한다.
그런데 다수의 기여자를 받는 프로젝트에서 그 둘은 부차적 기능이 아니라 포지를 쓰는 이유다.

### 정적 사이트는 읽기를 해결하고 쓰기를 남긴다

버킷이 서버 없이 사이트를 제공한다는 것은 읽기 경로에서만 참이다.

이슈에 코멘트를 달려면 커밋을 만들어 어딘가에 푸시해야 하고, 그 어딘가는 자기 버킷이다.
즉 남의 프로젝트에 이슈를 열려면 먼저 자기 S3 버킷을 준비하고 자격 증명을 설정하고 도메인을
연결해야 한다.
GitHub에서 이슈를 여는 데 필요한 것은 계정 하나다.

이 비대칭이 기여자 층을 얇게 만든다.
코드를 쓰는 사람은 이미 도구를 갖췄으니 문턱이 낮지만, 버그를 신고하려는 사용자에게는 클라우드
스토리지 계정 설정이 요구된다.
오픈소스 프로젝트에 오는 이슈의 상당 부분이 개발자가 아닌 사용자로부터 온다는 점을 생각하면, 이
설계는 그 유입을 사실상 차단한다.

Matrix 방을 빠른 질문과 논의용으로 안내하는 것도 같은 사정의 반영으로 보인다 — 정식 경로가 무거우니
비공식 경로가 실제 창구가 된다.

### 사양을 다섯 개로 먼저 갈라 놓은 것은 순서가 뒤바뀐 선택이다

GitMsg, GitSocial, GitPM, GitReview, GitRelease.
사용자가 거의 없는 단계에서 사양 문서 다섯 개와 개념 문서 다섯 개가 먼저 존재한다.

사양을 쓰는 것은 다른 구현이 나올 것을 전제한 행위다.
그런데 이 프로젝트는 단일 Go 바이너리이고, 클라이언트 네 종류도 모두 같은 바이너리의 인터페이스다 —
CLI, TUI, JSON-RPC, 그리고 그 위에 올린 Agent Skill.
독립 구현이 없는 상태에서 사양은 문서화된 내부 구조에 가깝다.

여기에 조기 표준화의 위험이 있다.
사양을 공개하면 그것을 바꾸기 어려워지고, 사용 사례가 쌓이기 전에 정한 형식은 거의 항상 틀린다.
Radicle이 서명된 레퍼런스의 취약점을 공개적으로 처리해야 했던 것도, Forgejo가 ActivityPub 대응
논쟁의 늪에 빠진 것도 형식을 먼저 정하는 일의 난이도를 보여 준다.
사양 다섯 개를 유지하는 비용은 기여자 한 명이 아니라 조직이 감당하는 종류의 부담이다.

### 아무도 이야기하지 않는다는 것 자체가 데이터다

GitSocial은 Hacker News에 최소 세 번 올라왔고 각각 1점, 2점, 2점을 받았다.
Lobste.rs에는 스레드가 없다.

이 사실을 그냥 넘기면 안 된다.
[Radicle](radicle.md)은 같은 문제 영역에서 274점을, [Forgejo](forgejo.md)는 391점을,
[Tangled](tangled.md)은 332점을 받았다.
문제 의식이 인기 없는 것이 아니다.

기술적으로 GitSocial은 이 셋보다 급진적인 답을 갖고 있다 — 서버가 없고, 새 프로토콜도 없고,
기존 호스트를 버리라고 요구하지도 않는다.
그런데 그 급진성이 전달되지 않았다.
첫 화면이 저장소 렌더링이라 프로젝트 소개보다 커밋 로그가 먼저 보이고, “Git-native collaboration
platform”이라는 한 줄은 [Forgejo가 겪은 것과 같은](forgejo.md) 자기 순환적 설명이다.

여기에 순환이 있다.
자기 도구로만 협업하겠다는 선택이 기여자 유입을 좁히고, 기여자가 적으면 알려질 통로도 좁아지고,
알려지지 않으면 다른 구현이 나오지 않아 사양이 사양으로 기능하지 못한다.
도그푸딩은 신뢰의 증거이면서 성장의 제약이다.

## 인사이트

### 객체 스토리지를 원격으로 삼으면 스크래핑 비용 구조가 뒤바뀐다

2026년의 자체 호스팅 포지가 마주한 새 비용은 사람 트래픽이 아니라 크롤러다.
[Tangled](tangled.md)의 홈페이지에 걸린 최신 공지가 분산 봇 스크래핑 공격 대응이고,
[Forgejo](forgejo.md)와 관련해 HN에서 가장 많은 표를 받은 글 중 하나가 인스턴스를 AI 크롤러로부터
지키는 방법이다.

Git 저장소의 웹 인터페이스는 크롤러에게 사실상 무한한 페이지 공간이다.
커밋마다, 파일마다, diff마다 URL이 생기고 그 대부분은 요청 시점에 계산된다.
동적 렌더링이 전제된 구조에서 대규모 스크래핑은 곧 CPU 고갈이다.

GitSocial의 정적 사이트는 이 방정식을 바꾼다.
모든 페이지가 미리 생성되어 버킷에 놓여 있으므로 크롤러가 소비하는 것은 대역폭뿐이고, 대역폭은
CDN으로 흡수되며 계산 자원과 달리 예측 가능하게 과금된다.
포지를 방어하는 대신 포지를 방어할 필요가 없는 형태로 만든 것이다.

이 관점에서 보면 “서버 없음”은 편의 기능이 아니라 보안 속성이다.
공격면이 없는 것은 방화벽보다 강하고, 이는 개인 자체 호스팅이 다시 가능해지는 조건이기도 하다.
Forgejo 생태계의 무게 중심이 크롤러 방어의 규모의 경제 때문에 Codeberg 같은 공용 인스턴스로 쏠릴
수밖에 없는 것과 반대 방향의 힘이 여기 있다.

### 에이전트 클라이언트를 CLI와 나란히 둔 것은 포지의 표면이 바뀌고 있다는 신호다

GitSocial의 클라이언트 목록에서 첫 항목은 웹 UI가 아니다 — Claude Code와 Cursor 등을 위한 Agent
Skill이다.
그리고 그 아래에 TUI, CLI, stdio 기반 JSON-RPC가 온다.

이 순서와 구성이 시사하는 바가 있다.
웹 UI가 없는 포지를 설계할 수 있다는 것은, 협업 데이터에 접근하는 주된 방식이 브라우저가 아닐 수
있다는 판단이다.
stdio JSON-RPC는 정확히 에이전트가 도구를 붙이는 형태이고, Agent Skill은 그 위의 사용 규약이다.

[Radicle](radicle.md) 스레드에서 h1watt와 theptip이 각자 도달한 결론과 같은 방향이다 — 에이전트
워크플로에는 계정과 PAT로 짜인 웹 중심 포지보다 키와 CLI로 짜인 것이 맞는다는 것이다.
GitSocial은 그 판단을 제품 구조로 옮겼다.

여기서 나오는 예측은 이렇다.
포지의 경쟁이 UI 품질에서 API 표면과 로컬 도구 품질로 이동한다.
[Cursor Origin](../cursor/cursor-origin.md)이 MCP 확장성을 발표의 첫 항목으로 내세운 것도 같은
이동의 다른 쪽 끝이다.
차이는 Origin이 그 표면을 플랫폼이 소유한 서비스로 만들고, GitSocial은 로컬 바이너리로 만든다는
점이다 — 그리고 후자에는 감사 추적을 자산화할 방법이 없다.

### 미러는 이주보다 강한 전략이고, 그래서 채택을 측정할 수 없다

`mirror`를 첫 명령으로 둔 선택은 채택 곡선의 모양을 바꾼다.

이주는 배타적이다 — GitHub을 떠나면 GitHub에 없다.
미러는 배타적이지 않다 — 미러를 둔 프로젝트는 여전히 GitHub에 있다.
그래서 이주에는 결단과 조직 합의가 필요하지만 미러에는 한 사람의 cron 항목이면 된다.

이것이 다른 대안 포지들이 겪는 문제를 우회한다.
[Tangled](tangled.md)이 사회적 관성을 빌려 오는 방식으로, [Forgejo](forgejo.md)가 워크플로 호환성으로
문턱을 낮춘 것과 같은 계열의 전략이면서 더 급진적이다 — 문턱을 낮추는 것이 아니라 선택 자체를
없앤다.

그런데 여기에 역설이 있다.
미러는 배타적이지 않으므로 채택이 지표로 나타나지 않는다.
어떤 프로젝트가 GitSocial 미러를 두고 있는지는 그 버킷의 도메인을 아는 사람만 알고, 그 사실은
GitHub 쪽에 아무 표시도 남기지 않는다.
스타 수도, 인스턴스 수도, 사용자 수도 집계되지 않는다.

그래서 이 프로젝트의 성패는 관찰하기 어려운 형태로 진행될 것이다.
HN 점수 1점은 실패의 증거가 아니라 지표의 부재일 수도 있다 — 다만 그 부재는 자금 조달과 기여자
유입에서 그대로 불리하게 작용하고, 앞서 본 대로 사양 다섯 개를 유지할 조직을 만들기 어렵게 한다.
측정되지 않는 성장은 재투자로 순환되지 않는다.

### 세 번째 답이 나왔다는 사실이 답이 아직 없다는 뜻이다

같은 문제에 네 번째 진지한 시도가 나왔다는 것을 성숙의 신호로 읽을 수도 있고, 그 반대로 읽을 수도
있다.

[Radicle](radicle.md)은 프로토콜에, [Forgejo](forgejo.md)는 법인 형태에, [Tangled](tangled.md)은
사회적 관성에 걸었고, GitSocial은 인프라 형태에 걸었다 — 서버를 없애면 자체 호스팅이 보편화되고
그러면 포지가 선택 사항이 된다는 쪽이다.

그런데 네 프로젝트 모두 같은 지점에서 막혔다.
발견과 통보다.
Radicle은 가십 프로토콜을 만들었지만 사설 배포가 어려워 결국 공용 시드에 의존하고, Forgejo는 연합을
4년째 못 내놓았고, Tangled은 외부 프로토콜에서 그것을 빌려 오는 대가로 신원 주권을 내주었고,
GitSocial은 Matrix 방으로 대체했다.

그렇다면 포지의 본질은 저장도 렌더링도 아니라는 결론에 이른다.
포지는 “누가 무엇을 했는지 관련된 사람 모두에게 알리는 장치”이고, 그 기능만은 중앙 집중 없이
구현된 예가 아직 없다.
저장과 렌더링은 네 프로젝트가 각기 다른 방식으로 풀었고 다 잘 작동한다.
남은 하나가 GitHub이 실제로 판매하는 것이며, 그것을 대체하지 못하는 한 나머지가 얼마나 우아해도
보험 상품에 머문다.
