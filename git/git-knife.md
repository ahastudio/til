# git-knife: 커밋 메타데이터를 표처럼 고치는 GUI

<https://github.com/TheRealYT/git-knife>

HN 토론: <https://news.ycombinator.com/item?id=49259611> (163점, 101개 댓글)

## 소개

git-knife는 커밋의 메타데이터 — 메시지, 저자 이름과 이메일, 저자 날짜(author date),
커미터 날짜(committer date), 커미터 이름과 이메일 — 를 표를 편집하듯 고치는 데스크톱
GUI다.
Tauri v2 기반이며 프런트엔드는 TypeScript, 껍데기는 Rust다.
저장소는 2026년 8월 10일에 만들어졌고 v0.1.0이 같은 날, v0.2.0이 8월 12일에 나왔다.
공개 이틀 만에 스타 262개, 포크 7개를 모았다.

포지셔닝이 명확하다.
GitKraken, Sublime Merge, Fork, lazygit 같은 기존 GUI는 메시지 수정과 순서 변경은 잘
하지만 커밋 날짜를 사실상 불변으로 취급하고 임의 커밋의 커미터 날짜나 저자 신원을
노출하지 않는다.
반대로 그 메타데이터를 다시 쓸 수 있는 도구 — `git-filter-repo`, `git rebase`의 환경
변수 기법, `git commit-tree` — 에는 GUI가 없다.
git-knife는 그 빈칸을 채운다고 스스로 규정한다.

구현의 핵심은 git을 재구현하지 않는다는 것이다.
시스템 `git` CLI에 셸아웃하고 `git commit-tree`로 커밋을 다시 만드는데, 각 커밋의 원래
tree를 그대로 재사용하므로 파일 내용은 “증명 가능하게 절대 바뀌지 않는다”고 README가
적는다.

## 기능과 상태

MVP 기준으로 지원하는 것과 아직 없는 것이 README에 명시되어 있다.

| 구분   | 항목                                                                              |
| ------ | --------------------------------------------------------------------------------- |
| 지원   | 로컬 브랜치를 ref로 열어 편집 — 체크아웃하지 않으므로 작업 트리가 그대로 유지된다 |
| 지원   | 메시지, 저자·커미터 이름과 이메일, 저자 날짜, 커미터 날짜 편집                    |
| 지원   | 해당 텍스트 필드 전반의 대량 찾기·바꾸기(리터럴 또는 정규식)                      |
| 지원   | 적용 전 모든 변경 미리보기                                                        |
| 지원   | 재작성마다 백업 ref 자동 생성과 원클릭 복원                                       |
| 지원   | 이미 푸시된 히스토리를 건드리는 재작성이면 경고                                   |
| 지원   | 서명 커밋 인식 — 배지 표시, 서명이 제거된다는 경고, 자기 키로 재서명              |
| 제한   | 병합 커밋은 잠겨 있어 편집 불가                                                   |
| 미지원 | 순서 변경·스쿼시·삭제, 병합 재작성, 스테이징·브랜치·리모트 관리                   |

서명 커밋 관련 기능은 v0.2.0에서 들어왔고, 같은 릴리스에서 브랜치 선택기(체크아웃 없이
ref로 편집)도 추가됐다.

## 사용법

요구사항은 git 2.x, Node.js와 pnpm, 안정 버전 Rust이며 Linux에서는 Tauri v2용 시스템
의존성(`webkit2gtk-4.1`, `libgtk-3`, `libayatana-appindicator3`, `librsvg2`)이 필요하다.

```bash
pnpm install
pnpm tauri dev     # 개발 실행 (첫 cargo 빌드에 몇 분)
pnpm tauri build   # 번들 빌드
```

릴리스는 태그를 밀면 GitHub Actions의 `tauri-action`이 macOS·Linux·Windows 설치 파일을
만들어 초안 릴리스에 붙인다.
코드 서명은 설정되지 않아 macOS·Windows 빌드는 서명되지 않은 상태다.

편집 흐름은 다음과 같다.
저장소를 열고 드롭다운에서 브랜치를 고르면 git-knife가 체크아웃 없이 ref로 그 브랜치를
편집하므로 작업 트리와 현재 체크아웃은 그대로 남는다.
병합이 아닌 커밋을 클릭해 편집기를 펼치고 메시지나 이름·이메일·날짜를 바꾸면 그 행이
강조되며, 날짜 필드는 커밋의 원래 UTC 오프셋을 유지한다.
`Review & apply`로 이전 → 이후 미리보기를 확인하고 확정한다.
재작성은 로컬 브랜치에만 적용되고, 리모트에 접속하거나 대신 푸시하는 일은 없다 — 푸시는
항상 사용자의 명시적 단계다.

대량 찾기·바꾸기는 대상 필드(메시지, 저자·커미터 이름, 저자·커미터 이메일)를 조합해
고르고 찾기·바꾸기 문자열을 넣는 방식이다.
정규식을 켜면 `$1` 역참조를 쓸 수 있고 대소문자 구분은 기본으로 켜져 있으며, 패널이
일치하는 커밋 수와 교체 수를 실시간으로 센다.

## 분석

### 이 도구의 진짜 주장은 “커밋 날짜는 불변이 아니다”다

README의 비교표에서 git-knife가 유일하게 모두 채운 열은 저자 날짜와 커미터 날짜, 그리고
대량 정규식 치환이다.
나머지 축 — 메시지 수정, 순서 변경, 스쿼시 — 은 기존 GUI가 이미 잘하고 git-knife는 오히려
계획 상태다.
즉 이 프로젝트의 주장은 “더 나은 git GUI”가 아니라 “아무도 편집 대상으로 취급하지 않던
필드가 있다”는 관찰이다.

이 관찰은 도구 지형에 대한 정확한 진단에서 나왔다.
GUI들이 날짜를 불변으로 취급한 이유는 기술적 불가능이 아니라 그것을 고칠 이유가 협업
맥락에서 드물었기 때문이고, 그럴 이유가 있는 사람들은 CLI로 내려가 `git-filter-repo`나
환경 변수 기법을 썼다.
git-knife는 그 둘 사이의 사용자 — 날짜를 고쳐야 하지만 CLI 기법을 외우고 싶지 않은
사람 — 를 겨냥한다.

그런데 스레드에서 이 진단의 전제를 흔드는 정정이 나왔다.
`TiddoLangerak`은 순수 git에도 커밋에 연결된 날짜가 두 개 있다는 점을 짚었다 — 저자
날짜는 내용이 작성된 시점을 말하며 rebase로 바뀌지 않고, 바뀌는 것은 커밋 날짜뿐이다.
따라서 올바른 메타데이터는 이미 있고 오히려 더 정확하다는 것이다 — 언제 작성되었는지와
히스토리가 마지막으로 언제 바뀌었는지를 둘 다 알려 주기 때문이다[^TiddoLangerak].
이 지적이 맞다면 “rebase가 날짜를 망친다”는 불만의 상당 부분은 도구의 부재가 아니라
모델에 대한 오해에서 온다.

### 안전성 설계가 전부 “하지 않는 것”으로 구성되어 있다

이 도구가 다루는 작업 — 히스토리 재작성 — 은 잘못되면 되돌리기 어렵다.
그래서 설계의 대부분이 기능이 아니라 금지와 우회로 이뤄져 있다.

git을 재구현하지 않고 시스템 CLI에 셸아웃한다.
커밋을 다시 만들 때 원래 tree를 재사용해 파일 내용이 바뀔 경로 자체를 없앤다.
재작성 전에 백업 ref를 자동으로 만들고 원클릭 복원을 제공한다.
리모트에 접속하지 않으며 푸시하지 않는다.
브랜치를 체크아웃하지 않고 ref로 편집해 작업 트리를 건드리지 않는다.
병합 커밋은 잠가 둔다.

저자 본인이 그 의도를 밝혔다 — git에 셸아웃하고 원래 tree 객체를 재사용한 것은 의도적
결정이며, 자신이 다른 곳에서 실수하더라도 파일 내용은 바뀔 수 없게 하려는 것이라는
것이다[^YonathanTesfaye-tree].
이 목록이 곧 이 프로젝트의 신뢰 근거이며, 기능 목록보다 이쪽이 도입 판단에 쓰이는
정보다.

### HN 피드백이 하루 만에 릴리스로 반영된 궤적

v0.1.0이 2026년 8월 10일, Show HN 게시가 8월 11일, v0.2.0이 8월 12일이다.
그 사이에 스레드에서 가장 무거운 기술적 반론이 제기됐다.

`lrvick`은 이 도구가 여러 저자의 서명 커밋을 쓰는 저장소에서는 동작하지 않으며 동작할
수도 없다고 적었다.
서명된 git 히스토리는 불변이고 서명되지 않은 히스토리는 공급망 공격 벡터라는 것이며,
그러면서도 PR 전 정리 작업을 하는 단일 저자 WIP 브랜치에서는 유용해 보인다고
덧붙였다[^lrvick].
저자는 v0.2.0에서 이에 대한 경고를 추가했고 서명 커밋을 먼저 표시하며 다시 만든 커밋을
자기 키로 재서명할 수 있게 했다고 답했다[^YonathanTesfaye-signed].

이 속도는 이 프로젝트의 성격을 보여준다.
공개 이틀 만의 도구가 스레드에서 지적된 항목을 다음 날 릴리스에 넣는 것은 초기 프로젝트의
장점이지만, 동시에 사용자가 마주하는 문서와 기능이 며칠 단위로 달라진다는 뜻이기도 하다.
현재 README에 “서명 커밋 인식 ✅”가 적혀 있는 것은 이 궤적의 결과이며, HN 스레드를 읽고
저장소를 보는 사람은 두 상태를 동시에 보게 된다.

### 수요의 실체는 해시 보존을 포기해도 되는 히스토리다

스레드에서 나온 사용 사례들이 뚜렷한 공통점을 갖는다.

`Defletter`는 거의 10년간 주기적으로 이런 도구를 찾아 왔다며 자기 용도를 설명했다 —
모의 의회 프로젝트에서 법률을 git에 저장하고 커밋이 의회의 법률 그 자체를 나타내게 하는
것이며, 모든 커밋이 올바른 메타데이터를 갖는다는 보장이 필요하고 커밋 해시의 보존에는
전혀 관심이 없다는 것이다.
법률 하나를 빠뜨려 히스토리 중간에 interactive rebase로 넣어야 할 때 이후 커밋 날짜가
전부 리셋되어서는 안 된다는 요구도 함께 적었다[^Defletter].

`simonw`은 두 가지를 들었다.
하나는 스크래핑 프로젝트에서 커밋 날짜가 데이터가 실제로 바뀐 시점과 맞기를 원하는
경우이며, Internet Archive 같은 출처에서 그 시점을 재구성한다는 것이다.
다른 하나는 저장소를 둘로 나눌 때 파일의 저자와 날짜 히스토리를 보존하고 싶은
경우다[^simonw].
`xp84`는 실수로 잘못된 이메일 주소로 커밋해 온 경우를 들었고[^xp84], `f1shy`는 터미널이
잘못 설정되어 저자가 엉망이 된 경우와 사적·업무 프로젝트에서 서로 다른 저자를 쓰는
경우를 들었다[^f1shy].

이 사례들의 공통점은 히스토리를 협업 기록이 아니라 데이터셋으로 다룬다는 것이다.
해시가 바뀌어도 무관하고, 대신 메타데이터가 실제 사실과 맞아야 한다.
git-knife가 겨냥하는 자리는 이 용도이며, 그것이 “푸시 전 로컬 브랜치”라는 제약과
정확히 맞물린다.

## 비평

### 라이선스가 없는 상태로 262개의 스타를 받았다

저장소에 `LICENSE` 파일이 없다.
GitHub API도 라이선스를 인식하지 못하며, 저장소 루트 파일 목록에도 없다.
공개된 소스에 라이선스가 없다는 것은 법적으로 모든 권리가 유보된 상태라는 뜻이다 —
읽는 것은 되지만 사용, 수정, 재배포에 대한 허가가 주어지지 않았다.

이것이 이 프로젝트에서 특히 문제인 이유는 대상 사용자 때문이다.
이 도구는 회사 저장소의 히스토리를 다시 쓰는 데 쓰인다.
그런 도구를 업무에 도입하려면 법무 검토를 통과해야 하고, 라이선스가 없는 소프트웨어는
그 첫 관문에서 멈춘다.
스타 262개와 여러 사용 사례 보고가 붙은 시점에도 이 상태라는 것은, 초기 프로젝트에서
문서와 기능이 빠르게 움직이는 동안 가장 기본적인 위생 항목이 빠져 있었다는 뜻이다.

같은 맥락에서 배포 서명도 없다.
README가 macOS·Windows 빌드가 서명되지 않았고 초기 테스터에게는 괜찮다고 밝히는 것은
정직하지만, 조직 단말에서 서명되지 않은 설치 파일을 실행하는 것은 대체로 정책상 막혀
있다.
라이선스와 서명은 둘 다 “나중에 하면 되는 일”로 미뤄지기 쉬운데, 둘 다 없으면 이 도구를
실제로 필요로 하는 조직에는 도달하지 못한다.

### “증명 가능하게”라는 표현이 신뢰를 얻는 대신 의심을 불렀다

README는 원래 tree를 재사용하므로 파일 내용이 “증명 가능하게 절대 바뀌지 않는다”고
적는다.
스레드의 첫 반응이 이 문장을 향했다.

`NichoPaolucci`는 그 문장을 인용하며 LLM이 이것을 적어 둬서 다행이라고, git을 재구현
했을까 걱정했다고 적었다[^NichoPaolucci].
`rozab`은 이것을 일반화했다 — LLM의 가장 짜증나는 습성 중 하나가 지적을 받은 뒤 하지
않은 것을 크게 명시하는 것이며, 코드에서 멍청한 부분을 고치게 하면 그것을 하지 않는다고
자랑하는 주석을 남겨 미래의 독자에게는 시리얼 상자에 붙은 “석면 없음” 라벨처럼 읽힌다는
것이다[^rozab].

이 반응이 부당하지 않은 이유는 문장의 형태 때문이다.
“증명 가능하게”는 증명을 제시할 때만 값을 갖는 표현이고, 여기서 제시된 것은 메커니즘의
설명 한 줄이다.
저자의 답 — 원래 tree 객체를 재사용하므로 다른 곳에서 실수해도 파일 내용은 바뀔 수 없다
— 은 그 자체로 충분히 강한 논증이며, 사실 이 문장이 “증명 가능하게”보다 신뢰를 더 준다.
안전성을 주장하는 문서가 형용사를 줄이고 메커니즘을 늘릴 때 더 믿긴다는 것이 이 교환의
교훈이다.

### 서명 히스토리의 근본 문제는 v0.2.0으로 해결되지 않았다

`lrvick`의 지적은 두 부분으로 되어 있다.
하나는 서명이 제거된다는 경고의 부재이고, 다른 하나는 여러 저자의 서명 커밋이 있는
저장소에서는 원리적으로 불가능하다는 것이다.
v0.2.0은 앞의 것만 해결했다.

자기 키로 재서명하는 기능은 남의 커밋에 적용될 때 의미가 달라진다.
A가 서명한 커밋을 B가 다시 만들어 B의 키로 서명하면, 그 커밋은 더 이상 A가 그 내용을
보증했다는 증거가 아니다.
서명의 목적이 “이 사람이 이 내용을 승인했다”를 검증 가능하게 남기는 것이므로, 재서명은
복원이 아니라 대체다.
즉 다중 저자 서명 저장소에서 이 도구를 쓰면 히스토리의 서명 그래프가 한 사람으로
붕괴한다.

그런데 README의 상태 목록에는 “서명 커밋 인식 — 배지 표시, 서명 제거 경고, 자기 키로
재서명 가능”이 지원 항목의 체크 표시로 올라 있다.
이 표기는 문제가 다뤄졌다고 읽히지만, 실제로 다뤄진 것은 단일 저자 저장소의 경우다.
필요한 것은 기능이 아니라 범위 선언이다 — 이 도구는 단일 저자 브랜치의 푸시 전 정리를
위한 것이며 다중 저자 서명 히스토리에는 쓰지 말라는 문장이 상태 목록보다 앞에 있어야
한다.
`lrvick` 본인이 그 결론을 이미 적어 주었다는 점에서 더 그렇다.

### 비교표가 자기에게 유리한 축으로 짜여 있다

README의 도구 비교표는 여덟 개 도구를 일곱 개 축으로 평가한다.
그중 git-knife가 ✅를 받지 못한 축은 하나 — 순서 변경·스쿼시·삭제 — 이고 그것은 🚧
계획으로 표시된다.
문제는 그 하나가 실제 사용자가 히스토리 정리에서 가장 많이 쓰는 기능이라는 점이다.

이 구성에서 표는 “git-knife가 교집합”이라는 결론으로 자연스럽게 흐르는데, 그 결론은 아직
사실이 아니다.
현재 상태는 교집합이 아니라 다른 도구가 다루지 않는 축만 갖춘 보완 도구이며, 사용자는
여전히 순서 정리를 위해 `git rebase -i`나 기존 GUI로 돌아가야 한다.
`jauntywundrkind`가 `git rebase -i`를 스프레드시트에 비유하며 예전 스레드들을 링크하고
이 도구의 등장이 시의적절하다고 반응한 것도[^jauntywundrkind] 두 도구가 함께 쓰이는
관계임을 시사한다.

기존 대안이 표에서 빠진 것도 짚을 만하다.
`unqueued`는 이 도구가 git-notes를 쓰고 자기 네임스페이스에 백업 브랜치를 만드는 점을
평가하면서도 조금 더 가벼웠으면 좋겠다고 적고 `git-revise`를 확인해 보라고
권했다[^unqueued].
`git-revise`는 rebase보다 빠른 히스토리 편집을 겨냥한 CLI 도구이므로 이 표의 비교
대상이 되어야 할 후보다.
비교표는 포지셔닝의 근거로 제시된 만큼 누락 하나가 결론의 강도를 그대로 낮춘다.

## 인사이트

### 협업용 히스토리와 기록용 히스토리는 다른 도구를 요구한다

이 스레드의 사용 사례들을 모으면 git 히스토리에 두 가지 서로 다른 용도가 있다는 것이
드러난다.
하나는 협업 기록이다 — 여러 사람이 공유하고, 해시로 참조하고, 서명으로 보증하고, 따라서
불변이어야 한다.
다른 하나는 기록 그 자체다 — `simonw`의 아카이브 재구성이나 `Defletter`의 법률 저장소처럼
커밋이 외부 사실의 표현이고, 메타데이터가 부속 정보가 아니라 본문이며, 해시 안정성은
아무 값이 없다.

git은 전자를 위해 설계되었고, 그래서 후자의 사용자는 늘 우회로에서 살았다.
`git-filter-repo`와 환경 변수 기법과 `commit-tree`가 그 우회로이며, git-knife는 그것에
GUI를 붙인 것이다.
두 용도가 같은 도구를 쓰는 동안 안전 장치는 협업용 기준으로 설계되고, 기록용 사용자는
그 장치를 매번 우회하는 방법을 배워야 한다.

이 구분을 명시하면 도구 설계가 달라진다.
기록용 저장소는 애초에 해시 안정성을 포기한다고 선언할 수 있고, 그러면 재작성은 예외
작업이 아니라 정상 연산이 된다 — 백업 ref와 미리보기가 아니라 트랜잭션과 감사 로그가
필요해진다.
앞으로 이 범주를 정면으로 겨냥하는 도구가 나온다면 git-knife처럼 “위험하지만 유용한
칼”이 아니라 “이 저장소는 재구성 가능하다”를 전제하는 형태가 될 것이다.

### 고칠 수 있는 히스토리와 믿을 수 있는 히스토리는 동시에 성립하지 않는다

`lrvick`의 두 문장 — 서명된 히스토리는 불변이고 서명 없는 히스토리는 공급망 공격
벡터 — 은 이 도구의 한계를 넘어 일반 명제다.
히스토리를 사후에 고칠 수 있게 만드는 모든 장치는 그 히스토리가 증거로서 갖는 값을 깎고,
증거로서의 값을 지키는 모든 장치는 고치는 것을 막는다.

이 긴장은 해결되지 않고 관리된다.
관리의 단위는 도구가 아니라 경계선이며, 그 경계선은 대체로 푸시 시점이다.
푸시 전에는 히스토리가 초안이고 자유롭게 고칠 수 있으며, 푸시 후에는 기록이 되어 고칠 수
없다.
git-knife의 설계 — 로컬 브랜치만 편집, 리모트 접속 없음, 이미 푸시된 히스토리 경고 —
가 사실 이 규율을 코드로 옮긴 것이고, 그것이 이 도구에서 가장 잘 설계된 부분이다.

그래서 조직이 이런 도구를 도입할 때 정해야 하는 것은 도구의 사용 여부가 아니라 그
경계선의 위치다.
공유 브랜치를 강제 푸시로 고치는 것이 허용되는지, 서명 정책이 있는 저장소를 예외로 둘지,
초안 브랜치의 수명이 얼마인지가 실제 정책이며, 도구는 그 정책을 집행하는 수단일 뿐이다.
경계선이 없는 조직에서는 어떤 안전 장치가 붙은 도구를 써도 결국 공유 히스토리가 다시
쓰인다.

### 도구를 만들기 전에 기존 모델이 이미 답을 갖고 있는지 확인해야 한다

`TiddoLangerak`의 정정은 이 스레드에서 가장 값진 한 문단이다.
git은 이미 저자 날짜와 커미터 날짜를 구분하며, rebase는 후자만 바꾼다.
즉 “언제 작성되었는가”와 “히스토리가 마지막으로 언제 바뀌었는가”가 이미 따로 기록되어
있고, 이는 두 값을 하나로 합치는 것보다 정보량이 많다.

그렇다면 `Defletter`가 우려한 “rebase가 이후 커밋 날짜를 전부 리셋한다”는 문제의 일부는
문제가 아니다 — 저자 날짜는 유지되므로 법률이 언제 제정되었는지는 보존된다.
남는 진짜 수요는 저자 날짜 자체가 틀렸거나 아예 없어서 외부 출처로 재구성해야 하는
경우이며, 그것이 `simonw`의 아카이브 복원 사례다.
같은 도구가 두 요구를 함께 받고 있지만 후자만 도구가 필요하다.

이 패턴은 새 도구를 만들 때 반복된다.
불편이 관측되면 그 불편이 모델의 한계인지 모델에 대한 오해인지 먼저 갈라야 하는데, 후자일
때 만든 도구는 오해를 편리하게 만들어 오래 유지시킨다.
git의 이중 날짜는 20년 가까이 있던 기능이고 대부분의 GUI가 그것을 한 열로 뭉개 보여
왔다는 점에서, 여기서 부족했던 것은 편집 기능보다 표시 방식이었을 수 있다.

### 위험한 도구의 채택은 기능이 아니라 표면 신호로 결정된다

이 스레드에는 기술적 논의와 무관해 보이는 곁가지가 하나 있다.
`beart`는 스크린샷이 누군가의 모니터를 실제로 찍은 사진처럼 보인다며 왜 화면 캡처를 쓰지
않았는지 의아하고, 어째서인지 그 때문에 이 프로젝트를 만지고 싶지 않아진다고
적었다[^beart].
`skinfaxi`는 메타데이터를 확인하면 GNOME 스크린샷이라고 나온다며 `exiftool` 출력을 붙여
그 추측이 무의미하고 틀렸다고 반박했다[^skinfaxi].

이 교환이 사소해 보이지만 이 범주의 도구에서는 사소하지 않다.
히스토리를 다시 쓰는 도구는 잘못 동작할 때 복구 비용이 크므로, 사용자는 코드를 읽기 전에
표면 신호로 빠르게 걸러낸다 — 스크린샷의 품질, README의 문장, 커밋 메시지의 결, 라이선스의
유무.
`ffsm8`이 이것은 vibecoded이며 다른 하니스를 겨누면 한두 시간에 만들 수 있는 정도로
범위가 사소하다고 일축한 것도[^ffsm8] 같은 종류의 빠른 판정이다.

여기서 나오는 실무적 결론은 신뢰 확보의 순서다.
이 범주에서 기능을 추가하는 것은 신뢰에 거의 기여하지 않고, 검증 가능성을 노출하는 것이
기여한다 — 백업 ref, 적용 전 미리보기, 원본 tree 재사용 같은 메커니즘이 그것이며
git-knife는 이미 갖췄다.
남은 것은 기본 위생이다.
라이선스, 서명된 배포물, 그리고 “이 도구를 쓰면 안 되는 경우”를 앞에 적는 범위 선언이
`git rebase -i`를 대체하는 어떤 기능보다 채택에 크게 작용한다.
