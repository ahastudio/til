# Continuity: Git 호스팅에서 합의를 지우고 S3를 진실로 삼다

원문: [Git at any scale](https://cursor.com/blog/git-at-any-scale)

HN 토론: <https://news.ycombinator.com/item?id=49348141> (363점, 114개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/rwgwxv/git_at_any_scale>

## 요약

글은 Git이 리눅스 커널의 분산 작업 흐름을 위해 설계된 분산 시스템이라는 사실에서 시작한다.
그런데 20년이 지난 지금 대부분의 조직은 중앙 호스팅에 의존하고 있고,
그 호스팅을 잘 해내는 일이 대단히 어렵다는 것이 문제 서술이다.

Git 구조가 만드는 확장 난점은 두 가지로 정리된다.
하나는 팩파일이다.
Git은 압축된 데이터를 팩파일에 저장하는데,
이 형식은 로컬 기계에서 다루기 편한 단순한 이진 직렬화 형식이지만
서버에서 규모 있게 관리하기에는 이상적이지 않다.
객체가 델타로 저장되므로 물리적 읽기와 논리적 읽기가 많이 필요하다.
다른 하나는 DAG 순회다.
Git 저장소는 방향성 비순환 그래프이고,
그래프를 한 걸음씩 걸어야 하며,
앞의 포인터를 가져오기 전까지 다음 포인터의 값을 알 수 없다.
확장 접근법은 세 가지가 존재한다.
파일 시스템을 분산하거나, 팩파일을 분산하거나, Git 자체를 분산하는 것이다.

역사적 시도들이 차례로 소개된다.
Google의 Shawn Pearce는 JGit을 이용해 객체를 분산 해시 테이블에 저장하는 방식을 시도했다.
일반 작업에서는 동작했지만 Git 프로토콜의 한계 때문에
`git clone` 성능이 설계를 폐기할 만큼 나빴다.
GitHub는 2008년 이후 파일 시스템 쪽을 시도했다.
NFS 저장은 Git이 잠금과 찢김과 읽기와 동기화 같은
파일 시스템 의미론을 가정하기 때문에 실패했고,
GFS 배포는 단명했으며 DRBD 배포는 더 오래갔지만 둘 다 일상 운영이 끔찍했다.
근본 문제는 팩파일 전반에 걸친 무작위 읽기 패턴이
로컬 캐싱 없이는 네트워크 파일 시스템에서 동작하지 않는데,
규모가 커지면 그 캐싱이 불가능해진다는 것이다.

2013년부터 현재까지의 업계 표준은 Spokes다.
세 가지 선택으로 요약된다.
Git 자체를 분산하지 않고 팩파일 수준에서 동작하며,
저장소를 로컬 NVMe 디스크에 일반 Git으로 저장하고,
복제본 사이에 강한 일관성을 유지한다.
동기화 방식은 3단계 커밋이다.
Git 푸시는 새 객체를 담은 팩파일과
브랜치 포인터를 갱신해 커밋을 보이게 만드는 참조 트랜잭션으로 나뉜다.
팩파일은 동기화 없이 동시에 팬아웃하고,
더 작은 참조 트랜잭션에만 3단계 커밋을 적용한다.
Git 자체가 참조 트랜잭션 준비를 지원하기 때문에 가능한 구성이다.
참조에 잠금을 걸고 기존 값이 예상과 같은지 확인한 뒤
커밋이나 중단 명령이 올 때까지 잠금을 유지할 수 있다.

Spokes의 운영 난점이 이 글의 논거가 된다.
모든 단계의 지연이 클러스터에서 가장 느린 서버에 묶이므로,
복제본을 더할수록 푸시 처리량이 나빠진다.
꼬리 지연 문제다.
확장이 양방향으로 막히는 문제도 있다.
큰 모노레포는 복제본이 많이 필요해 세 개로 부족하고,
에이전트가 만든 아주 작은 저장소도 각각 세 개의 복제본을 요구해 자원을 낭비한다.
운영 복잡도 측면에서 저장소가 가축이 아니라 애완동물로 취급된다.
저장소를 기계에 대응시키는 라우팅 테이블이 필요하고,
끊임없는 체크섬과 검증이 필요하고,
손상을 빠르게 찾아 복구해야 하며,
정족수를 유지해야 한다.
사본 두 개가 손상되면 시스템이 실패한다.

Cursor의 Continuity는 S3 호환 객체 저장소에 둔 쓰기 선행 로그를 진실의 원천으로 삼고,
로컬 NVMe 저장소를 따뜻한 캐시로 쓴다.
핵심 원칙은 푸시가 완전히 영속화되기 전까지 확인 응답을 보내지 않는다는 것이다.
푸시 흐름은 다섯 단계다.
푸시를 별도 WAL 항목으로 S3에 저장하고,
팩파일을 로컬 디스크에 쓰면서 동시에 S3에 업로드하고,
로컬 저장소에 참조 트랜잭션을 준비하고,
WAL 항목을 가리키는 포인터를 S3에 있는 WAL 인덱스 파일에 기록한다.
이 구조가 모든 푸시를 선형화한다.
푸시마다 S3 오버헤드가 붙지 않도록 배치 처리를 하며,
그 덕분에 디스크가 허용하는 속도로 수용할 수 있다.

합의 알고리즘은 쓰지 않는다.
갱신이 S3에 대한 원자적 비교 후 교환을 사용하므로 어느 서버든 프라이머리가 될 수 있다.
글은 이 시스템이 열화됐을 때 항상 정확하고 건강할 때 항상 빠르도록 설계됐다고 표현한다.
라우팅은 랑데부 해싱으로 저장소 ID를 예상 노드에 대응시키고,
로컬 디스크에 저장소가 없으면 WAL에서 실체화한다.
복제는 낙관적이다.
가십 UDP 패킷으로 복제본에 갱신을 알리며,
패킷은 신뢰할 수 없지만 분산 시스템에서 신뢰할 수 있는 것은 없으므로 괜찮다는 논리다.
읽을 때 복제본은 예상 ETag를 넣어 S3에 조건부 GET을 보낸다.
본문 없는 304 응답이면 저장소가 최신이므로 즉시 응답하며,
이 작업은 평균 10밀리초 미만으로 거의 즉시다.
200 응답이면 새 WAL 인덱스를 받아 따라잡은 뒤 응답한다.
복제 UDP 패킷이 유실돼도 문제가 되지 않고,
모든 복제본의 모든 읽기가 진실의 원천에 대해 검증되므로 완전히 일관적이라는 것이다.

압축은 프라이머리만 수행한다.
복제본은 이미 압축된 팩을 S3에서 내려받아 CPU를 대역폭으로 교환한다.
여러 노드에서 압축이 동시에 발동해 Spokes를 괴롭히던 가용성 문제를 피하는 구성이다.
현대 Git이 다중 팩 인덱스와 증분 기하 압축을 지원하지만 재패킹은 여전히 CPU를 많이 쓴다.
확장 특성은 두 방향으로 제시된다.
읽기 처리량이 복제본 수에 선형으로 늘며,
복제본 100개까지 합성 스트레스 테스트를 돌려 읽기에서 일관된 선형 확장을 확인했다.
큰 모노레포는 수백 개 복제본에 배치하고,
에이전트가 만든 수백만 개의 작은 저장소는 각각 복제본 하나만 쓴다.
유휴 저장소는 가비지 컬렉션되고 필요할 때 실체화된다.

처리량 수치는 저장소 등급별로 나뉜다.
S3 Standard에서 초당 최대 120건의 푸시를 처리하며 압축과 복제를 포함한 값이다.
지연이 더 낮은 S3 Express One Zone에서는 초당 300건 이상이고,
병목은 Git이 디스크 데이터를 압축하는 속도다.
모든 푸시는 선형화되며 확인 응답 전에 외부 저장소에 영속화되고,
모든 클론은 완전히 일관적이다.
WAL 보장 덕분에 저장소의 모든 기본 연산이 추적되고,
모든 푸시와 재패킹에 대한 완전한 출처 데이터가 남으며,
어떤 복제본이든 되감고 앞으로 감을 수 있고,
상태를 위한 외부 데이터베이스 의존이 없다.
글은 마지막 절에서 Continuity 위에 만든 Git 호스팅 플랫폼 Origin을 소개한다.
에이전트가 소프트웨어 작업 방식을 근본적으로 바꿔
더 많은 코드와 더 많은 PR과 더 많은 CI 실행이 생겼다는 것이 배경이며,
실험적 기능보다 신뢰성과 성능과 고통 없는 이전을 강조한다.

## 분석

### 기술 설명의 형식을 취한 제품 출시 공지다

글의 구조가 목적을 드러낸다.
Git의 구조적 난점을 먼저 설명하고,
Google과 GitHub의 실패한 시도들을 연대순으로 배치하고,
현재 업계 표준인 Spokes의 운영 고통을 나열한 뒤,
자기 설계를 제시하고 마지막 절에서 Origin을 소개한다.
독자는 대안이 없다는 인식을 갖춘 상태에서 제품 이름에 도달한다.

이 구성은 설득력이 높고 동시에 검증을 어렵게 만든다.
앞부분의 역사 서술은 대부분 사실이고 반박할 여지가 적다.
NFS 위에서 Git이 잘 동작하지 않는다는 것은 알려진 사실이고,
3단계 커밋의 지연이 가장 느린 노드에 묶인다는 것도 구조적 사실이다.
그런데 그 사실들이 만든 신뢰가 뒤쪽의 검증되지 않은 주장으로 옮겨간다.
복제본 100개까지 선형 확장한다는 문장이
NFS 실패 서술과 같은 무게로 읽히게 되는 구조다.

게시 시점도 이 배치와 무관하지 않다.
GitHub가 8월 17일에 7시간 47분 장애를 겪고
회고를 게시한 것과 같은 주에 이 글이 올라왔다.
GitHub 대안을 묻는 토론이 크게 확산된 시점이기도 하다.
Spokes를 운영 고통의 대표 사례로 배치한 글이
그 주에 나온 것은 좋은 타이밍이며,
그 타이밍 자체가 글의 논지를 평가할 때 고려해야 할 맥락이다.

다만 저자의 위치가 이 판단을 복잡하게 만든다.
HN에서 `brasic`은 이 글 저자의 평판을 과장하기 어렵다며,
GitHub 내부 시스템에서 좋았던 모든 것에 그의 이름이 붙어 있는 것처럼 보였다고 적었다.
자신의 GitHub 재직 기간과 겹치지 않았지만
그가 Cursor에서 일한다는 사실만으로 Cursor 엔지니어링 조직에 대한 평가가
크게 올라간다는 것이다.[^brasic]
즉 Spokes의 운영 고통을 서술하는 사람이 그 시스템의 안쪽을 만든 사람이다.
경쟁사 설계를 깎아내리는 마케팅 문서라는 독법이 이 사실로 약해진다.
같은 사실이 다른 방향으로도 작동한다.
Spokes를 가장 잘 아는 사람의 서술이므로 정확할 가능성이 높은 동시에,
그 시스템에서 겪은 고통이 서술의 강도를 정할 수도 있다.

설계의 가장 중요한 선택을 `gritzko`가 짚었다.
그들이 변경되지 않은 Git 코드베이스를 구성 요소로 쓰기로 결정했다는 것이며,
리눅스 커널을 만든 사람들이 자기가 무엇을 하는지 알았을 것이라는 가정을 깔고 있다는 것이다.
그는 이 결정이 일반적 분산 데이터베이스 관점에서 기묘해 보이는 몇 가지 특징을 설명하며,
저자가 이 논쟁을 여러 번 해 본 것 같다고 봤다.
글에서 같은 주장이 몇 번 반복되고, 나머지는 거기서 따라 나온다는 것이다.[^gritzko]
이 관찰이 글의 구조를 다시 읽게 만든다.
객체를 분산 해시 테이블에 넣은 JGit 시도가 실패로 배치된 이유도 여기 있다.
Git을 다시 만들지 않기로 한 결정이 먼저이고,
그다음에 팩파일 수준에서 무엇을 할 수 있는지가 설계 공간이 된다.

### 합의를 지운 것이 아니라 S3에 위임한 것이다

글에서 가장 강한 주장은 합의 알고리즘이 필요하지 않다는 문장이다.
어느 서버든 프라이머리가 될 수 있고,
갱신이 S3의 원자적 비교 후 교환으로 이루어지기 때문이라는 것이다.
이 서술은 정확하면서 오해를 부른다.

정확한 부분은 Continuity의 코드베이스 안에 합의 구현이 없다는 것이다.
3단계 커밋도, Raft도, Paxos도 없다.
오해를 부르는 부분은 합의가 사라졌다는 인상이다.
조건부 쓰기가 성립하려면 어딘가에서 선형화 가능한 원자적 연산이 제공되어야 하고,
그 연산을 제공하는 것은 S3 내부의 합의 계층이다.
즉 합의는 옮겨졌을 뿐이며, 옮겨진 곳이 AWS의 운영 책임 아래다.

이 위임의 교환 조건이 글에 명시되지 않는다.
얻는 것은 코드 단순화와 운영 부담 감소다.
잃는 것은 통제와 가용성 결합이다.
Spokes 클러스터는 자기 NVMe 디스크와 자기 네트워크만 있으면 동작한다.
Continuity는 S3가 응답해야 동작한다.
이 차이는 정상 상황에서는 보이지 않고 S3 장애 때만 보인다.
그리고 글에는 그 상황에 대한 서술이 없다.

역사적으로 이 종류의 위임은 대체로 옳은 선택이었다.
스토리지와 컴퓨트를 분리하는 설계가 데이터베이스에서 표준이 된 것도 같은 논리다.
다만 그 선택을 “합의가 필요 없다”고 서술하는 것과
“합의를 객체 저장소에 위임했다”고 서술하는 것은 독자에게 다른 정보를 준다.
후자가 정확하고, 후자여야 독자가 자기 위험 모델에 대입할 수 있다.

HN에서 `wrs`가 이 서술 방식을 하나의 경향으로 지적했다.
어려운 문제를 상당 부분 S3로 밀어 넣고 S3가 그냥 동작한다고 가정한 뒤
S3가 어떻게 동작하는지는 설명하지 않으면서 인상적인 일을 해내는 흐름이 있다는 것이다.
그는 우리가 다른 기적적 해법에도 같은 일을 한다고 인정하면서
슈퍼스칼라 비순차 실행 프로세서가 그냥 동작한다고 가정하는 것을 예로 들었다.
그러나 이 경우에는 설명이 만족스럽지 않으며,
특히 S3가 알고리즘이 아니라 독점 제품이기 때문이라는 것이다.[^wrs]
마지막 문장이 핵심을 짚는다.
3단계 커밋은 논문으로 읽고 검증하고 다시 구현할 수 있는 알고리즘이다.
S3의 조건부 쓰기는 계약이며, 계약의 내부는 검증 대상이 아니다.
Spokes에서 Continuity로의 이동은 검증 가능한 것에서
신뢰해야 하는 것으로의 이동이기도 하다.

반대편 평가도 같은 스레드에 있다.
`biwills`는 이 대목이 S3가 얼마나 놀라운 엔지니어링 산물인지 다시 떠올리게 한다며
아홉이 열한 개인 내구성 수치를 인용했다.[^biwills]
이 두 반응이 함께 있는 것이 이 설계의 위치를 잘 보여 준다.
S3의 내구성은 어떤 자체 클러스터보다 높고,
동시에 그 내구성의 근거는 외부에서 확인할 수 없다.
자체 호스팅을 검토하는 조직에게는 이 교환이 결정적이다.
S3에 접근할 수 없는 환경에서는 이 설계의 핵심이 성립하지 않으며,
MinIO 같은 호환 구현으로 대체할 때
조건부 쓰기의 원자성이 같은 강도로 보장되는지 따로 확인해야 한다.

### 저장소를 애완동물에서 가축으로 바꾼 것이 실제 성과다

이 설계의 진짜 이득은 처리량 수치가 아니라 저장소의 지위 변화다.
Spokes에서 저장소는 특정 기계 세 대에 존재하는 상태이고,
그 대응 관계를 라우팅 테이블이 기억해야 하며,
손상되면 복구해야 하고 정족수를 유지해야 한다.
Continuity에서 저장소는 S3에 있는 WAL의 파생물이다.
랑데부 해싱으로 어느 노드가 담당할지 계산하고,
그 노드에 없으면 WAL에서 만들어 낸다.

이 변화가 만드는 능력이 두 가지다.
하나는 유휴 저장소의 가비지 컬렉션이다.
디스크에서 지워도 잃는 것이 없으므로 지울 수 있고,
필요할 때 다시 만든다.
다른 하나는 복제본 수의 자유다.
큰 모노레포는 수백 개, 작은 저장소는 하나로 둘 수 있다.
Spokes의 양방향 확장 문제가 여기서 해소된다.
저장소가 상태를 소유하지 않으면 복제본 수는 정책 변수가 된다.

이 성과가 왜 지금 중요한지는 글의 마지막 절이 밝힌다.
에이전트가 만든 저장소가 수백만 개라는 워크로드다.
사람이 만드는 저장소는 조직당 수천 개 규모이고 각각 오래 살아 있다.
에이전트가 실험을 위해 만드는 저장소는 수가 훨씬 많고 대부분 곧 버려진다.
저장소당 고정 비용이 세 개의 복제본이라면 이 워크로드가 성립하지 않는다.
설계의 출발점이 성능이 아니라 이 비용 구조였을 가능성이 크다.

### 압축을 프라이머리만 하는 결정이 읽기 확장을 만든다

읽기가 복제본 수에 선형으로 확장된다는 주장의 근거는 압축 정책에 있다.
Spokes에서 각 복제본은 자기 디스크의 데이터를 스스로 재패킹한다.
재패킹은 CPU를 많이 쓰므로 그 시간 동안 해당 복제본의 응답이 느려진다.
복제본이 많아지면 어느 순간에는 항상 누군가 압축 중이고,
그것이 글이 말하는 상시 가용성 문제다.

Continuity는 프라이머리만 압축하고 복제본은 결과물을 내려받는다.
CPU를 대역폭으로 교환한다는 표현이 이 결정을 정확히 요약한다.
복제본의 작업이 다운로드와 응답으로 단순화되므로,
복제본을 늘리는 것이 읽기 용량을 그대로 늘린다.
선형 확장은 알고리즘의 성질이 아니라 이 역할 분리의 결과다.

동시에 이 결정이 새 비용을 만든다.
압축된 팩을 모든 복제본이 내려받아야 하므로,
큰 모노레포에서 전체 재패킹이 일어나면 복제본 수에 비례한 대역폭이 소비된다.
복제본 수백 개에 수 기가바이트 팩을 배포하는 상황이 여기 해당한다.
글은 이 비용을 언급하지 않고 교환의 이득만 서술한다.
증분 기하 압축을 언급한 것이 부분적 답이지만,
전체 재패킹의 빈도와 그때의 대역폭 비용은 제시되지 않는다.

## 비평

### 처리량 수치가 비교 대상 없이 제시된다

초당 120건과 초당 300건 이상이라는 숫자가 이 글의 유일한 성능 근거다.
그런데 이 수치를 해석할 기준이 없다.
Spokes가 같은 조건에서 몇 건을 처리하는지 제시되지 않고,
GitHub의 실제 푸시 처리량과 비교되지도 않는다.
글의 논지가 Spokes보다 낫다는 것인데 비교 수치가 없다.

수치의 범위도 불분명하다.
초당 120건이 클러스터 전체의 값인지 저장소 하나에 대한 값인지 명시되지 않는다.
저장소 하나에 대한 값이라면 매우 좋은 숫자이고,
클러스터 전체 값이라면 GitHub 규모에서는 부족한 숫자다.
같은 글이 월 커밋 수십억 건 규모의 워크로드를 배경으로 언급하고 있으므로
이 구분이 결론을 바꾼다.

S3 Express One Zone을 써야 초당 300건이 나온다는 사실도 조건으로 다뤄지지 않는다.
Express One Zone은 이름 그대로 단일 가용 영역이다.
지연을 얻는 대가로 영역 장애에 대한 내구성을 포기하는 등급이며,
진실의 원천을 여기에 두는 구성은 다중 영역 내구성을 전제한 설계와 다른 물건이다.
글은 지연이 더 낮다는 서술만 하고 이 차이를 적지 않는다.
푸시가 확인 응답 전에 완전히 영속화된다는 원칙의 강도가
어느 저장소 등급을 쓰는지에 따라 달라지는데, 그 사실이 드러나지 않는다.

### 읽기 경로가 S3에 의존한다는 사실이 열화 서술에서 빠져 있다

이 설계에서 모든 읽기는 S3에 조건부 GET을 보낸다.
304 응답을 받으면 로컬 데이터를 그대로 제공하고, 그것이 10밀리초 미만이다.
이 구조가 완전한 일관성을 만들고, 그 점은 정확하다.
그런데 같은 구조가 읽기 경로를 외부 서비스에 결합시킨다.

Spokes와의 대조가 여기서 뒤집힌다.
Spokes 복제본은 로컬 디스크만으로 클론과 페치를 제공할 수 있다.
외부 저장소가 응답하지 않아도 읽기는 계속된다.
Continuity 복제본은 ETag 검증 없이는 데이터가 최신인지 모르므로,
S3가 응답하지 않을 때 두 선택 중 하나를 해야 한다.
일관성을 포기하고 오래된 데이터를 제공하거나, 읽기를 거부하는 것이다.

글은 이 시스템이 열화됐을 때 항상 정확하고 건강할 때 항상 빠르도록 설계됐다고 말한다.
문장은 좋은데 열화의 정의가 없다.
복제본 몇 대가 죽은 상태를 뜻하는지, S3가 느려진 상태를 뜻하는지,
S3가 응답하지 않는 상태를 뜻하는지 알 수 없다.
CI가 푸시 직후 클론하는 워크플로에서 이 차이는 즉시 체감되고,
글이 겨냥한 워크로드가 정확히 그 워크플로다.
열화 시 동작을 명시하지 않은 가용성 주장은 검증할 수 없는 주장이다.

### 복제본 100개 합성 테스트는 이 설계가 겨냥한 워크로드를 측정하지 않는다

선형 확장의 근거는 복제본 100개까지의 합성 스트레스 테스트다.
합성이라는 단어와 읽기라는 범위가 이 근거의 크기를 정한다.
측정된 것은 읽기 처리량이고, 측정되지 않은 것이 두 가지다.

하나는 같은 규모에서의 쓰기 처리량이다.
복제본이 100개일 때 푸시 처리량이 어떻게 되는지가 제시되지 않는다.
글의 논리대로라면 프라이머리만 압축하므로 푸시 쪽은 복제본 수와 무관해야 한다.
그러나 압축된 팩을 100개 복제본에 배포하는 대역폭이 있고,
가십 패킷과 조건부 GET의 총량도 있다.
Spokes의 문제를 꼬리 지연으로 규정한 글이
자기 설계의 꼬리 지연을 측정하지 않은 것은 논증의 공백이다.

다른 하나는 이 글이 문제로 제시한 워크로드 자체다.
큰 모노레포의 클론 시간과 페치 시간이 어디에도 없다.
`git clone` 성능이 나빠 JGit 설계가 폐기됐다는 서술로 글을 시작했는데,
Continuity에서 큰 저장소의 클론이 얼마나 걸리는지는 제시되지 않는다.
수백만 개의 작은 저장소를 실체화하는 데 걸리는 시간도 없다.
콜드 캐시에서 WAL로부터 저장소를 만들어 내는 지연이
이 설계에서 가장 새롭고 가장 위험한 경로인데 수치가 없다.

### 경쟁 설계를 실패의 역사로 배치하면서 규모의 차이를 지운다

글은 GitHub의 NFS와 GFS와 DRBD 시도를 실패로 서술하고
Spokes의 운영을 애완동물 돌보기로 서술한다.
전자는 2008년 무렵의 이야기이고 후자는 13년간 세계 최대 Git 호스팅을 돌린 시스템이다.
두 서술을 같은 흐름에 배치하면
Spokes가 초기 실패들의 연장선에 있는 미완성 설계처럼 읽힌다.

공정한 비교라면 규모 차이를 명시해야 한다.
Spokes가 겪는 운영 고통의 상당 부분은
그 시스템이 실제로 도달한 규모의 함수다.
라우팅 테이블과 체크섬과 정족수 관리가 필요해진 것은
수억 개 저장소와 수십억 건의 월 푸시를 처리하면서 발견된 문제들 때문이다.
Continuity는 아직 그 규모에서 검증되지 않았고,
그 규모에서 발견될 문제 목록도 아직 없다.

이 비대칭은 새 인프라 제품의 서술에서 반복되는 형태다.
기존 시스템의 알려진 문제 목록은 길고 구체적이며,
새 시스템의 문제 목록은 짧다.
후자가 짧은 이유는 설계가 더 좋아서일 수도 있고
아직 부딪히지 않아서일 수도 있는데,
두 경우를 구분할 정보가 글에 없다.
Spokes가 3단계 커밋을 고른 이유가 무엇이었는지,
그 선택이 어떤 실패 모드를 막았는지를 함께 서술했다면
Continuity가 그 실패 모드를 어떻게 다루는지도 검증할 수 있었을 것이다.

Spokes 서술 자체의 정확성도 지적됐다.
`eatonphil`은 팬아웃이 3단계 커밋으로 동기화되어
과반이 확인 응답할 때만 푸시가 수락된다는 문장을 인용하며,
3단계 커밋은 과반이 아니라 모든 노드의 동의를 요구하지 않는지 물었다.[^eatonphil]
이 질문에 답이 달리지 않았다.
경쟁 설계를 비교 대상으로 세운 글에서
그 설계의 합의 조건을 부정확하게 서술하면
꼬리 지연 논거의 크기도 함께 흔들린다.
모든 노드의 동의가 필요하다면 가장 느린 노드에 묶인다는 지적이 더 강해지고,
과반이면 약해진다.
어느 쪽인지에 따라 논증의 강도가 달라지는데 글은 한쪽으로 서술했다.

가장 실질적인 반박은 문제 정의 자체를 겨눈다.
`fmajid`는 GitHub의 확장 문제가
상대적으로 작은 저장소를 아주 많이 높은 동시성으로 다루는 것이라고 정리했다.
이것은 테라바이트 규모 모노레포를 가진 Google과 Microsoft와 Meta의 문제와 다르며,
그들은 모두 작업 중인 부분만 로컬 디스크에 올리는
가상 클론을 만드는 지연 로딩 해법을 갖고 있다는 것이다.
그리고 Microsoft Windows가 얼마 전 GitHub으로 옮겼는데
이 글이 너무 가볍게 기각한 파일 시스템 접근법을 그때 사용했다며
`microsoft/scalar`를 링크했다.[^fmajid]
이 지적이 글의 역사 서술에 구멍을 낸다.
NFS와 GFS와 DRBD의 실패를 근거로 파일 시스템 접근을 폐기된 경로로 배치했는데,
그 경로의 현대적 성공 사례가 존재하고
그 사례가 세계 최대 규모의 모노레포를 다루고 있다.
세 접근법 중 하나를 기각하는 논거가 2008년 사례에 근거한다는 것이
이 글에서 가장 약한 부분이다.

대안 설계에 대한 제안도 나왔다.
`luke5441`은 문제를 먼저 분리해야 한다고 봤다.
내용 주소 지정 객체 저장과 참조 저장은 별개 문제이고
libgit2에 이미 두 가지 백엔드가 있으므로,
각각에 적합한 분산 데이터베이스를 쓰면 된다는 것이다.
큰 규모에서 객체에는 가용성을 우선하는 Cassandra 계열,
참조에는 일관성을 우선하는 FoundationDB 계열을 쓰고,
성능을 위해 객체를 로컬에 캐시하고
요청을 그 객체가 캐시된 노드로 라우팅하는 구성이다.[^luke5441]
`zinodaur`는 반대 방향에서 더 단순한 결론을 냈다.
자신의 주된 소득은 Spokes가 쓰기 빈도가 그렇게 낮은 데이터베이스에
말도 안 되는 복제 프로토콜을 쓰고 있다는 점이며,
리더와 팔로워에 로그 시퀀스 번호 기반 바이너리 로그나 WAL을 쓰면 되고
그들의 분산 시스템 악몽 같은 조정 시스템은 필요 없다는 것이다.[^zinodaur]
이 두 반응이 이 글이 다루지 않은 설계 공간을 채운다.
Continuity는 팩파일 수준 유지와 객체 저장소 위임을 함께 선택했는데,
객체와 참조를 분리하는 선택지는 검토 대상으로 등장하지 않는다.
Git 코드베이스를 그대로 쓰기로 한 결정이 그 선택지를 미리 배제했기 때문이며,
그 결정의 비용이 여기서 드러난다.

## 인사이트

### 이 설계 전체가 객체 저장소의 조건부 쓰기 API 하나에 의존한다

Continuity에서 합의를 대체하는 유일한 원시 연산은 S3에 대한 원자적 비교 후 교환이다.
이 연산이 없으면 어느 서버든 프라이머리가 될 수 있다는 성질이 성립하지 않고,
설계 전체가 다시 합의 알고리즘을 요구한다.
그런데 이 기능은 객체 저장소에 오랫동안 없었다.
S3의 조건부 쓰기 지원은 비교적 최근에 추가된 기능이며,
그 이전에는 외부 잠금 서비스나 데이터베이스로 같은 일을 했다.

이 사실이 이 글을 읽는 방식을 바꾼다.
Continuity는 Git 호스팅에 대한 새로운 통찰의 결과가 아니라
플랫폼 원시 기능 하나가 추가되면서 가능해진 설계다.
글이 상태를 위한 외부 데이터베이스 의존이 없다는 점을 자랑하는데,
그것이 가능한 이유는 객체 저장소가 데이터베이스의 일부 기능을 흡수했기 때문이다.
의존이 사라진 것이 아니라 한 계층 아래로 접혀 들어갔다.

여기서 나오는 일반 규칙은 인프라 설계의 시점 의존성이다.
같은 문제에 대한 최적 설계가 클라우드 API의 기능 목록에 따라 바뀐다.
2013년의 Spokes 설계는 그 시점의 원시 기능 집합에서 합리적이었고,
2026년의 Continuity 설계는 다른 집합에서 합리적이다.
이것은 어느 팀이 더 똑똑했는지의 문제가 아니라 언제 설계했는지의 문제다.
그리고 다음 원시 기능이 추가되면 Continuity도 같은 방식으로 낡는다.
자체 호스팅 Git 서버를 고민하는 조직에게 이 관찰이 실용적 함의를 준다.
조건부 쓰기를 지원하는 객체 저장소가 있다면
이 설계의 핵심 아이디어를 훨씬 작은 규모로 재현할 수 있다.

`bilalq`가 같은 관찰을 다른 사례로 확인했다.
S3에 읽기 후 쓰기 일관성이 없던 것이 그리 오래전이 아니며,
그 변화 이후에 그 위에 만들어진 멋진 것들이 폭발적으로 늘어난 것을 보는 것이 놀랍다는 것이다.[^bilalq]
읽기 후 쓰기 일관성과 조건부 쓰기는 서로 다른 기능이지만
둘 다 같은 성격의 사건이다.
객체 저장소가 데이터베이스의 성질을 하나씩 획득하면서
그 위에 세울 수 있는 시스템의 종류가 계단식으로 늘어난다.
Continuity는 그 계단의 가장 최근 칸에 서 있는 설계다.

### 저장소가 값싼 임시 객체가 되면 코드 정체성의 단위가 흔들린다

이 설계가 가능하게 만드는 것은 수백만 개의 저장소를 값싸게 유지하는 것이다.
에이전트가 실험마다 저장소를 만들고 버리는 워크플로가 그 배경이다.
글은 이것을 용량 문제로 다루지만, 이차 효과는 개념 쪽에 있다.

저장소는 오랫동안 조직 단위의 정체성이었다.
접근 권한과 CI 설정과 이슈와 릴리스와 소유 팀이 저장소에 붙어 있다.
저장소가 하나 생기는 것이 조직적 사건이었고, 그래서 만드는 데 승인이 필요했다.
저장소가 값싼 임시 객체가 되면 이 결합이 유지되지 않는다.
수백만 개의 저장소에 각각 권한 정책과 CI 설정을 붙이는 것은 불가능하다.

그러면 정체성의 단위가 다른 곳으로 이동한다.
후보는 두 가지다.
하나는 저장소보다 큰 단위, 즉 워크스페이스나 프로젝트다.
권한과 정책을 그 층에 두고 저장소는 그 안의 파생물로 다룬다.
다른 하나는 저장소보다 작은 단위, 즉 변경 집합이다.
에이전트가 만든 브랜치와 그 브랜치의 테스트 결과가 추적 단위가 된다.
어느 쪽이든 저장소 단위로 값을 매기고 권한을 주던 관행은 유지되기 어렵다.

이 변화가 실무자에게 주는 함의는 도구 선택 기준이다.
Git 서버의 성능이 아니라 저장소 위의 층이 무엇을 제공하는지가 결정적이 된다.
수백만 개 저장소를 만들 수 있는 호스팅에서
그 저장소들을 조직 정책에 어떻게 묶을지에 대한 답이 없으면,
값싼 저장소는 관리되지 않는 표면으로 남는다.
같은 시기에 에이전트 작업 기록과 승인 이력을 다루는 도구들이 늘어나는 것도
이 공백을 시장이 인식하고 있다는 신호다.

HN에서 `bigcat12345678`이 이 논지를 더 멀리 밀었다.
에이전트는 Git 호스팅을 어렵게 만든 것에 그치지 않고
사람과 코드 사이에 새 계층을 요구하며,
그 계층에도 자기 버전 관리 산출물이 필요하다는 것이다.
그가 든 근거 중 세 번째가 특히 이 논의에 직접 걸린다.
중간 작업물이 폭증하고 지속적 산출물은 줄어들었으며,
에이전트는 스크래치 저장소와 추적 기록과 실패한 시도와 폐기된 구현을 남긴다.
사용자가 실제로 원한 것은 더 작고 더 가치 있어져
기능을 배포하는 것보다 의도를 충족시키는 것에 가까워졌는데,
우리는 제품에 쓰는 것과 같은 도구로 폐기물 더미를 버전 관리하고 있다는 것이다.
그는 기능 생산 시간이 자릿수 단위로 줄어든 반면
리뷰와 CI와 브랜치 워크플로는 사람의 작성 속도에 맞춰 조정되어 있어
관문이 빨라지지 않았다는 점도 함께 지적했다.[^bigcat12345678]

이 진단이 Continuity의 성과를 다르게 위치시킨다.
값싼 저장소를 수백만 개 만들 수 있게 하는 것은
폐기물 더미를 더 싸게 버전 관리하게 만드는 일이다.
그것 자체가 나쁜 일은 아니고 필요한 일이다.
다만 이 방향으로 인프라를 개선하면
제품 산출물과 폐기물이 같은 형식으로 같은 시스템에 쌓이는 상태가 고착된다.
구분이 필요해지는 시점은 저장 비용이 아니라 검색과 감사에서 온다.
어떤 브랜치가 실제로 배포된 결정이었고
어떤 브랜치가 버려진 시도였는지를 구분하는 표시가 없으면,
저장소가 값싸진 만큼 이력의 신호 대 잡음비가 나빠진다.

### 선형화 가능한 푸시가 에이전트 시대에 기능이 되는 이유

강한 일관성은 오랫동안 Git 호스팅의 판매 요소가 아니었다.
사람이 푸시하고 몇 초 뒤에 브라우저에서 확인하는 작업 흐름에서는
잠깐의 읽기 지연이 문제가 되지 않는다.
새로고침하면 되기 때문이다.

에이전트 작업 흐름에서는 그 여유가 사라진다.
푸시 직후 CI가 클론하고, 다른 에이전트가 같은 브랜치를 페치하고,
오케스트레이터가 참조 값을 읽어 다음 단계를 결정한다.
읽기가 오래된 값을 반환하면 자동화는 새로고침하지 않고 잘못된 결정을 내린다.
사람이 흡수하던 불일치를 흡수할 주체가 없다.
Continuity가 모든 클론이 완전히 일관적이라는 점을 앞세우는 이유가 여기 있다.

그런데 이 강점이 만드는 절충이 글에서 다뤄지지 않는다.
모든 푸시를 선형화한다는 것은 저장소 단위의 직렬화를 뜻하고,
직렬화는 병렬 푸시의 상한을 만든다.
에이전트 여러 대가 같은 저장소에 동시에 푸시하는 상황은
정확히 이 시스템이 겨냥한 워크로드인데,
그 상황에서 선형화가 처리량 제약으로 작동한다.
초당 120건이라는 숫자가 저장소 단위 값이라면 대체로 충분하고,
클러스터 단위 값이라면 병렬 에이전트 워크로드에서 곧 부딪힌다.
글이 이 구분을 밝히지 않은 것이 가장 아쉬운 지점이다.

더 근본적으로, 일관성과 처리량 중 무엇을 우선할지가 워크로드마다 다르다.
CI 트리거는 강한 일관성이 필요하다.
에이전트가 실험용 브랜치를 밀어 넣는 작업은 그렇지 않다.
같은 시스템이 두 종류를 구분하지 않고 모두 선형화하면
필요 없는 곳에서 비용을 지불한다.
작업별 일관성 등급이라는 개념이 다음 단계의 요구사항이 될 가능성이 높다.

### 더 좋은 Git 서버가 GitHub 대체재를 만들지는 않는다

이 글은 Git 호스팅의 어려운 부분이 Git 자체라고 전제한다.
팩파일과 DAG 순회와 복제와 압축이 문제이고,
그것을 잘 풀면 좋은 호스팅이 된다는 논리다.
Origin이 실험적 기능보다 신뢰성과 성능과 고통 없는 이전을 강조한다는 서술도 같은 전제에 서 있다.

실제 전환 비용의 위치는 다르다.
조직이 GitHub을 떠나지 못하는 이유는 `git push`가 느려서가 아니다.
Actions 워크플로, PR 리뷰 흐름, 웹훅으로 연결된 사내 시스템,
GitHub App으로 만든 자동화, OIDC 기반 클라우드 인증,
그리고 이슈와 논의에 쌓인 기록 때문이다.
Git 프로토콜 호환성은 이 목록에서 가장 쉬운 항목이며,
이미 여러 대안이 확보하고 있는 항목이다.

같은 주에 확산된 GitHub 대안 토론의 결론이 이 관찰과 겹친다.
대안은 있지만 대체재는 없다는 표현이 그것이다.
기능 목록을 비교하는 것보다
인증과 권한과 자동화 API와 백업과 조직 내 익숙함을 먼저 비교해야
실제 이전 비용을 판단할 수 있다.
고통 없는 이전이라는 약속은 저장소 데이터의 이전을 뜻할 뿐,
그 위에 얹힌 자동화의 이전을 뜻하지 않는다.

그렇다면 이 글의 가치는 제품 홍보가 아닌 곳에 있다.
Git 호스팅의 내부 구조를 이 정도 해상도로 공개한 문서가 드물고,
Spokes의 3단계 커밋 구조와 그 꼬리 지연 문제,
그리고 객체 저장소를 진실의 원천으로 삼는 대안 설계가 한 문서에 정리돼 있다.
자체 호스팅을 검토하는 팀이나 내부 Git 서버를 운영하는 팀에게
이 문서는 제품 소개보다 설계 참고자료로 더 유용하다.

Lobste.rs에서 `guillego`가 정확히 그 독법을 권했다.
그는 자신이 이 회사군의 새 버전관리 제품에 별 관심이 없다고 먼저 인정한 뒤,
그럼에도 이 글이 버전관리 시스템 호스팅의 난점에 대한
아주 좋은 기술 문서이며 저자의 GitHub 10년 경력에 근거하고 있다고 적었다.
사람들이 블로그에 이름을 올린 회사 때문에 숨기고 신고하는 것을 이해하지만,
파일 시스템과 버전관리에 관심 있는 사람에게는 한번 읽어 보라고 권했다.[^guillego-lobsters]
해당 스레드의 점수가 마이너스로 내려간 상태라는 사실이
이 권유의 배경을 설명한다.
회사에 대한 평가가 문서에 대한 평가를 덮는 상황이며,
설계 참고자료로서의 가치는 그 평가와 독립적이다.
그리고 그 용도로 읽을 때는 마지막 절의 제품 이름을 무시해도 손실이 없다.

HN에서 같은 진단이 더 직접적으로 나왔다.
`nikolay`는 Git의 성능이 문제가 아니라 GitHub Actions와 PR 같은 것이 문제이며,
Cursor가 유료 GitHub 고객을 가져가 같은 워크로드를 받는 순간
비슷한 문제를 겪기 시작할 것이라고 봤다.
GitHub은 소스 관리만이 아니고,
누구나 Gitolite를 설치해 훌륭하게 설정 가능하고 안전한 Git 환경을 만들 수 있지만
CODEOWNERS와 보호 브랜치와 태그가 하는 일은
자신이 십 년 전에 만든 것의 1%도 되지 못한다는 것이다.[^nikolay]
`speed_spread`는 역사 쪽에서 같은 지점을 짚었다.
GitHub의 핵심 혁신은 분산 SCM을 다시 중앙화한 것이었고,
좋은 웹 UI와 PR 같은 기능, 그리고 무료 호스팅 공간이 그 내용인데
그중 어느 것도 Git의 특이한 성질에 의존하지 않았다는 것이다.[^speed_spread]

`skybrian`은 여기에 수요 쪽 질문을 더했다.
이 글이 자기 Git 호스팅이 왜 더 확장 가능한지 훌륭하게 설명하지만,
GitHub이 계속 무료로 쓸 수 있고 가용성 문제를 고친다고 가정하면
대부분의 사람에게는 이것이 필요하지 않을 것 같다는 것이다.
그러면서 이런 아키텍처 개선 없이 무료 Git 호스팅이 계속 지속 가능할지 물었다.[^skybrian]
이 질문이 이 글과 같은 주의 GitHub 회고를 하나로 묶는다.
월 커밋이 넉 달 만에 두 배가 된 곡선에서
무료 호스팅의 단위 비용이 유지되려면 이런 종류의 설계 변경이 필요하다.
즉 Continuity의 실제 경쟁 상대는 GitHub의 기능 목록이 아니라
GitHub의 비용 구조일 수 있다.
그 축에서 이기면 기능 격차를 메울 시간을 벌고, 지면 기능 격차가 영구히 남는다.
