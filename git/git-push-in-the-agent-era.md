# git push는 그대로고 바뀌는 것은 그 앞과 뒤다: 에이전트 시대 Git의 세 층

GeekNews Article: [AI 시대, git push 앞뒤에서 바뀌는 것들](https://news.hada.io/article/git-push-in-the-agent-era)

## 요약

GeekNews가 직접 쓴 아티클로, 2026년 11월 12일에 올라왔다.
출발점은 두 회사의 상반된 선택이다.
Anthropic은 2026년 10월에 사내 모노레포에서 Git을 자체 버전 관리 시스템
Scion으로 교체했다.[^anthropic]
OpenAI는 11월에 병렬 에이전트 개발을 위한 새 Git 백엔드 Pando를
공개했다.[^gn-pando]
둘 다 여러 에이전트가 동시에 일하면서 저장소 부하가 커진 데서 나왔지만 바꾼
범위가 다르다.
Anthropic은 버전 관리 시스템 자체를 바꿨고 OpenAI는 서버 쪽을 바꿨으므로, OpenAI
개발자는 지금도 `git clone`으로 코드를 받고 `git push`로 변경을
올린다.[^gn-pando]

글은 “Git을 쓴다”고 부르는 일을 세 층으로 나눈다.
첫째는 클라이언트와 프로토콜로, 커밋을 만들고 `clone`이나 `push`로 주고받는
방식이다.
둘째는 서버와 저장소로, 코드를 보관하고 여러 작업에 전달하며 브랜치 갱신을
처리하는 방식이다.
셋째는 협업 흐름으로, 변경을 리뷰하고 CI로 검증하고 `main`에 합치는 방식이다.
이 틀로 GeekNews에 올라온 글 아홉 편을 이어서, 각 팀이 어디서 막혔고 어느 층까지
바꿨는지를 살핀다.

첫 질문은 에이전트가 늘면 Git의 어디가 바빠지느냐다.
한 컴퓨터에서는 `git worktree`로 작업 디렉터리를 나누면
Git 객체 저장소를 공유할 수 있다.
작업마다 클라우드 샌드박스를 새로 띄우면 환경마다 코드를 가져와야 하고, 푸시가
끝나면 CI가 같은 커밋을 여러 환경으로 다시 가져간다.
글은 Anthropic의 일일 병합이 2026년 5월 약 2,500건에서 9월 3만 건 이상으로 약
12배가 됐고, CI 체크아웃은 하루 약 2,500만 회였다고 전한다.[^anthropic]
하루 평균으로 환산하면 병합은 초당 약 0.35건, 체크아웃은 초당 약 290회다.
병합 한 건이 체크아웃 몇 번을 일으킨다는 뜻은 아니지만, 변경을 반영하는 횟수보다
그 코드를 가져가는 횟수가 훨씬 많을 수 있다는 점을 보여 준다고 글은 말한다.
GitHub의 4월 가용성 업데이트도 인용하는데, PR 하나가 Actions와 브랜치 보호,
검색, 알림 같은 기능을 함께 움직이므로 부하가 저장소에만 머물지 않는다는
설명이다.[^github-availability]

두 번째 층에서는 Git 명령을 그대로 두고 서버를 다시 설계한 사례를 모은다.
Pando는 서로 다른 브랜치의 푸시를 독립적으로 처리하고 같은 브랜치의 갱신 순서만
보장한다.
그래서 여러 브랜치를 함께 읽는 도구는 브랜치마다 다른 시점의 상태를 볼 수
있다.[^gn-pando]
읽기에서는 압축해 둔 팩파일(packfile)을 재사용하고 지역 캐시에서 내려 준다.
클라이언트가 이미 가진 객체를 일부 다시 받을 수 있지만, 서버가 같은 이력을
요청마다 새로 압축하는 일은 줄어든다.[^gn-pando]
글은 GitHub의 새 저장 구조(단일 저장소에서 초당 7,200회 푸시)와 Cursor의
Continuity(푸시를 S3의 변경 로그에 남기고 서버 디스크의 사본은 다시 만들 수 있는
캐시로 취급)도 같은 계열로 묶는다.[^gn-continuity]
구현과 일관성 보장은 다르지만, 코드를 보관하는 곳과 요청을 처리하는 서버를
분리하면서 기존 Git 사용법을 유지한다는 점이 공통이라고 정리한다.

읽기 요청만 나누는 방법도 있다.
Entire는 GitHub를 원본으로 두고 에이전트가 가까운 지역의 미러에서 `clone`과
`pull`을 하게 한다.[^entire-blog]
앞선 GitHub 글에서 미러는 장애가 났을 때 코드를 다시 가져올 수 있게 하는
사본이었지만, 글은 Entire의 미러를 평소에 여러 에이전트가 같은 코드를 가져갈 때
원본에 몰리는 요청을 줄이는 사본으로 구분한다.
GitLab의 차세대 SCM은 Git 프로토콜을 유지하면서 서버 구조를 바꾸고, 에이전트가
저장소 전체를 복제하지 않고 필요한 파일과 이력만 요청하는 인터페이스를 추가하고
있다고 한다.

Anthropic은 Scion으로 서버를 넘어 클라이언트와 프로토콜까지 바꿨다.
얕은 복제와 내부 미러로 한동안 대응했지만 병합과 체크아웃이 늘면서 미러를
운영하고 최신 상태로 유지하는 일이 복잡해졌다는 것이 글의 설명이다.
Scion은 대부분의 작업 환경이 온라인이라는 전제에서 시작해, 클라이언트가 필요한
데이터를 서버에서 받고 커밋과 리베이스와 병합도 서버에서 처리한다.[^anthropic]
로컬에 전체 이력을 두고 오프라인으로 일하는 Git의 장점 대신, 작업 환경마다
내려받아야 할 데이터를 줄이는 쪽을 택한 것이다.
기존 Git 클라이언트가 붙는 백엔드가 아니어서 Anthropic은 코드 리뷰와 검색과 권한
관리도 함께 만들었다.
글은 Git에서 Scion으로 데이터를 옮긴 과정은 소개돼 있지만 일반 Git 저장소로
내보내거나 미러링하는 방법은 발표 글에서 확인되지 않는다고 짚는다.
Anthropic도 대부분의 저장소에는 Git의 설계가 여전히 맞다고 설명한다고
덧붙인다.[^anthropic]

세 번째 층의 출발점은 푸시가 빨라져도 `main`에 합치는 일은 남는다는 구분이다.
에이전트 열 개가 각자 브랜치에 푸시하는 일과 그 열 개의 변경을 `main`에 반영하는
일은 다르다.
앞쪽은 서버가 변경을 받아들이는 속도이고, 뒤쪽은 변경을 어떤 순서로 합치고
검증할지의 문제다.
Pando의 설계를 독립적으로 구현한 오픈소스 Git 서버 Aspen이 이 차이를 보여 준다.
Aspen 팀은 `git.git` 저장소에서 브랜치 전용 URL을 쓴 자체 측정으로 5분간 초당
567회 푸시를 처리했고, `main`에 변경을 하나씩 순차 반영했을 때는 초당 약
4회였다.[^aspen-readme]
다음 변경이 직전 반영 결과에 의존하기 때문이고, 두 수치 모두 CI 실행은 포함하지
않는다.[^aspen-readme]

변경을 합칠 수 있다는 것과 합친 결과가 제대로 동작한다는 것도 다르다.
한 에이전트는 API 응답 형식을 바꾸고 다른 에이전트는 기존 응답 형식을 전제로
화면을 고쳤다면, 서로 다른 파일을 건드렸으므로 Git은 충돌 없이 합친다.
각 브랜치에서 테스트를 통과했더라도 두 변경을 함께 넣었을 때 화면이 동작하는지는
따로 확인해야 한다.
GitHub의 병합 큐(merge queue)는 최신 `main`에 큐에서 앞선 PR들의 변경과 이번
PR을 합친 상태를 만들어, 실제로 반영하기 전에 필수 검사를
돌린다.[^github-merge-queue]
검사를 통과한 여러 PR을 묶어 병합할 수도 있지만, 한 번에 병합할 PR 수를 늘린다고
각 PR에 예약된 CI 검사까지 하나로 합쳐지지는 않는다.[^github-merge-queue]
글은 Aspen에서 눈여겨볼 점을 PR을 묶을 수 있다는 사실이 아니라 서버가 `main`을
갱신하는 횟수로 본다.
Aspen은 각 PR을 별도 커밋으로 남기면서 여러 PR의 변경이 모두 들어간 결과로
`main`을 한 번만 갱신하며, 그래서 PR이 몰릴 때 같은 브랜치를 반복해서 갱신하는
비용을 줄일 수 있다고 한다.
GitLab이 소스 관리 다음의 병목으로 CI와 보안 검토와 배포를 짚은 이유도 여기에
있다고 글은 덧붙인다.

마지막으로 리뷰할 때 보는 기록이 달라지고 있다고 본다.
앞선 글에서 저장소를 옮겨도 PR에 쌓인 토론과 설계 판단은 따라오지 않는다고
했는데, 에이전트와 일할 때는 어떤 제약을 줬는지, 다른 방법을 시도했다가 왜
버렸는지 같은 기록이 PR을 열기 전부터 쌓인다.
Zed의 Delta는 동료를 나와 에이전트의 작업 스레드에 초대하고, 리뷰어는 코드와
대화를 함께 보면서 별도 작업 트리에서 수정을 시험한다.[^gn-delta]
Delta 팀은 자기 제품 저장소에서 PR을 끄고 이 방식으로 일했지만, 푸시와 빌드의
기준으로는 Git 커밋을 계속 썼다.[^gn-delta]
Delta는 대화와 편집 과정을 Git 커밋과 별도로 DeltaDB에 기록하므로, Git 저장소만
옮겨서는 그 기록이 따라오지 않는다.[^gn-delta]
Entire CLI의 체크포인트(checkpoint)는 Git 객체로 저장되지만 코드 브랜치와는
별도의 Git 참조(ref)를 쓰며, 글은 `main`만 푸시하면 세션 기록도 따라오는 것은
아니라고 적는다.

글은 사례를 표로 묶는다.
Git 명령이 유지되는지를 보면 Scion만 교체이고, Pando와 GitHub와 Cursor
Continuity와 Entire와 GitLab과 Aspen과 Zed Delta는 모두 유지다.
마무리는 열린 질문이다.
에이전트가 일을 시작할 때 무엇을 얼마나 받아올지, 사람이 결과를 넘겨받을 때
diff에 더해 작업 과정도 볼 수 있을지를 두고 실험이 이어지고 있고, 어느 쪽이 평소
쓰는 도구에 먼저 들어올지가 궁금하다고 한다.
몇 년 뒤에도 개발자는 같은 `git push`를 입력하겠지만, 그 앞에서 에이전트가
코드를 가져오는 방식과 그 뒤에서 팀이 변경을 검토하고 합치는 방식은 지금과 꽤
달라져 있을 수 있다는 것이 마지막 문장이다.

## 분석

### 세 층 모델은 서로 다른 발표를 같은 질문으로 읽게 한다

이 글은 새 실험을 하거나 새 수치를 내지 않는다.
아홉 편의 GeekNews 글은 각각 한 회사의 발표를 요약한 것이고, 이 글은 그 아홉
편에 같은 두 질문을 던진다.
어느 층을 바꿨는가, 그리고 Git 명령은 그대로인가다.
이 질문이 쓸모 있는 이유는 발표마다 자기 제품을 설명하는 어휘가 달라서 서로
비교되지 않기 때문이다.
Pando의 브랜치별 푸시, Continuity의 변경 로그, Entire의 미러, Scion의 서버 측
커밋은 이름만 보면 서로 다른 종류의 일처럼 읽힌다.
세 층에 놓으면 앞의 셋은 같은 층(서버와 저장소)의 서로 다른 선택이고 Scion만 한
층 위까지 올라갔다는 것이 보인다.

같은 방식이 앞선 글 [GitHub에 맡긴 것은 Git이
아니다](../github/github-is-not-just-git.md)에도 있었다.
그 글은 GitHub 의존을 코드, Issues와 Pull Request, Actions와 릴리스, 정체성의 네
층으로 나눠 GitHub이 멈추면 무엇이 멈추는지를 물었다.
이 글은 Git을 세 층으로 나눠 에이전트가 늘면 무엇이 바뀌는지를 묻는다.
두 분류는 겹친다.
이 글의 세 번째 층인 협업 흐름이 앞 글의 Issues와 Pull Request와 Actions를 모두
포함한다.
앞 글이 장애 때 멈추는 곳으로 짚은 층이 이 글에서는 에이전트 때문에 바뀌는
곳으로 다시 나온다.

이 글의 가장 강한 형태의 주장은 이렇다.
에이전트 시대에 Git에서 실제로 바뀌는 것은 `push` 명령이 아니라 그 앞의 읽기
분배와 그 뒤의 합치기와 기록이다.
근거는 아홉 개 사례와 몇 개의 수치다.
그 근거가 닿는 범위는 좁다.
대부분의 수치는 해당 회사나 프로젝트가 자기 조건에서 잰 결과이고, 독립된 측정은
글에도 없다.
Aspen은 스스로 검증 전 단계라고 밝히며,[^aspen-readme] Anthropic의 규모는 한
회사의 사례다.
결론이 바뀌려면 독립된 측정에서 실제 모노레포의 병목이
여전히 푸시 경로에 있다는 결과가 나오거나,
대부분의 팀이 겪는 문제가 읽기 분배가 아니라는 보고가 쌓여야 한다.

### 서버 쪽 해법은 “순서가 필요한 것은 참조 갱신뿐”이라는 원리로 모이고 Scion만 다르게 간다

Git 객체는 내용으로 이름이 붙는 불변 데이터여서 서로 다른 작성자가 합의 없이
동시에 저장해도 충돌하지 않는다.
그러므로 합의가 필요한 것은 어느 브랜치가 어느 커밋을 가리키는지, 곧 참조(ref)
갱신뿐이다.
[GitHub의 새 저장 구조를 다룬 문서](github-git-storage-rubicon.md)가 같은
관찰에서 출발한다.
이 원리를 사례마다 다르게 구현한다.
Pando는 참조 갱신을 브랜치별로 독립시켰다.[^gn-pando]
Aspen은 팩을 오브젝트 스토리지에 두고 브랜치 이력을 PostgreSQL에
둔다.[^aspen-readme]
Cursor의 Continuity는 푸시를 S3의 변경 로그(write-ahead log)에 직렬화해, 합의
프로토콜 없이도 저장소 전체에 대해 일관된 뷰를 얻는다.[^gn-continuity]
Aspen의 README는 이 차이를 직접 설명한다.
Aspen은 Pando처럼 같은 브랜치의 푸시만 순서대로 처리하므로 저장소 전체를 하나의
로그로 거치는 한도는 없지만, 모든 브랜치를 한 시점으로 보여 주는 스냅숏도 없다고
적는다.[^aspen-readme]
순서를 브랜치별로 쪼개는 쪽은 저장소 전체의 일관된 시점을 포기하고, 단일 로그를
두는 쪽은 직렬화 지점 하나를 대가로 일관된 시점을 지킨다.
같은 README는 Cursor의 수치(S3 Standard에서 초당 120회)와 자기 수치(초당
567회)를 한 표에 놓으면서도 두 설정이 달라 같은 조건의 비교가 아니라고
밝힌다.[^aspen-readme]

Scion은 같은 진단에서 다른 처방을 낸다.
Anthropic은 Scion의 개발 수명주기가 `main`이나 릴리스 브랜치 외의 참조를
권장하지 않는다고 설명하는데, 모든 서버가 합의해야 하는 전역 상태가 커지는 것이
확장의 문제이기 때문이다.[^anthropic]
참조 갱신을 독립 단위로 쪼개는 쪽(Pando, Aspen)과 참조의 수 자체를 줄이는
쪽(Scion)이 같은 진단에서 갈라진다.
이 갈림은 서버 설계에 머물지 않고 일하는 방식에 닿는다.
에이전트마다 브랜치를 하나씩 쓰는 흐름은 앞쪽을 전제하고, `main` 중심으로 짧게
합치는 흐름은 뒤쪽을 전제한다.
이것도 이 문서의 해석이며, 두 회사가 그렇게 설명한 것은 아니다.

### 읽기 쪽 부하가 설계를 정하고, 쓰기 쪽은 순서의 문제에 가깝다

글이 인용한 Anthropic 수치를 같은 단위로 놓으면 비대칭이 보인다.
병합이 초당 약 0.35건일 때 CI 체크아웃은 초당 약 290회여서 약 830배 차이가
난다.[^anthropic]
병합 한 건이 체크아웃을 몇 번 일으키는지를 뜻하는 비율은 아니라고 글이 단서를
달았듯 정확한 비교는 아니다.
그래도 한쪽이 세 자릿수 더 크다는 감각은 남는다.
Pando의 설명도 같은 구조다.
엔지니어 한 명이 여러 변경을 동시에 CI에 올리고, 푸시 하나가 같은 커밋을
가져오는 여러 작업을 실행할 수 있다.[^gn-pando]
Pando가 낸 성과 중 하나는 전송량의 99% 이상을 로컬 디스크 캐시에서 내보냈다는
것이다.[^gn-pando]

이 비대칭이 서버 쪽 해법들이 읽기에서 같은 종류의 도구를 쓰는 이유를 설명한다.
Pando는 만든 팩을 재사용하고, Entire는 지역 미러로 읽기를 나누고, GitLab은
필요한 파일과 이력만 요청하게 한다.
셋 모두 서버가 같은 일을 요청마다 다시 하지 않게 하려는 것이다.
쓰기에는 병렬화할 단위(브랜치)가 이미 있고 순서가 필요한 곳(같은 브랜치)이 좁다.
읽기에는 같은 요청이 반복되므로 재사용할 대상이 있다.
두 경우 모두 구조가 이미 해법의 모양을 정해 준다는 것이 이 절의 해석이다.

### 합치는 단계의 직렬 지점은 서버의 속도가 아니라 검증 시간이다

Aspen의 자체 측정에서 푸시는 초당 567회였지만 `main`에 하나씩 반영하는 속도는
초당 약 4회였고, 후자의 한도는 부하가 아니라 왕복 통신
지연이었다.[^aspen-readme]
반영 한 번에 약 0.25초가 드는 셈이다.
이 수치에 CI가 들어 있지 않다는 점이 핵심이다.
하루 3만 건 병합은 평균 약 2.9초에 한 건이다.
계산하면 86,400초를 30,000으로 나눈 값이다.
검증이 한 건에 몇 분 걸린다면 변경을 한 번에 하나씩 검증하는 방식으로는 이
속도를 따라갈 수 없다.

그러면 선택지는 세 가지로 좁혀진다.
여러 변경을 묶어 한 번에 검증하거나, 앞선 변경이 반영됐다고 가정하고 병렬로
검증하거나, 검증을 반영한 뒤로 옮기는 것이다.
GitHub 병합 큐는 앞의 두 가지를 제공한다.
앞선 PR이 포함된 병합 그룹(merge group) 단위로 검사하고, 동시에 돌릴 그룹
수(build concurrency)를 1에서 100 사이로 제한할 수 있다.[^github-merge-queue]
글이 다루는 것도 이 둘이다.

## 비평

### 규모의 기준으로 삼은 Anthropic이 병합 큐를 쓰지 않는다고 밝힌 대목이 빠져 있다

세 번째 층의 서술은 병합 큐와 서버 측 묶음 병합을 해법의 후보로 놓는다.
그런데 같은 글이 규모의 기준으로 가장 많이 인용하는 Anthropic은 그 후보를 택하지
않았다고 자기 글에 적었다.
Anthropic은 제대로 된 병합 큐가 에이전트 규모에서는 맞지 않는다고 본다.
수백에서 수천 개의 변경이 테스트가 도는 동안 병합될 수 있다면 CI가 무엇을
뜻하는지 불분명해진다는 이유다.
저장소 전역 잠금을 쓰는 업계 표준 병합 큐를 효과적으로 재현하지 못했으므로, 대신
병합 후와 배포 전의 자동 테스트에 투자했다고 한다.
동시에 들어온 변경이 충돌할 수 있지만 Claude가 대체로 사람이 알아채기도 전에
고친다는 설명이 이어진다.[^anthropic]

이 대목이 빠지면 세 번째 층의 경쟁이 도구 선택처럼 읽힌다.
실제로 갈리는 것은 정책이다.
반영하기 전에 검증해서 거부할 것인가, 반영한 뒤에 검증해서 고칠 것인가다.
글의 마지막 질문, 곧 어느 쪽이 평소 쓰는 도구에 먼저 들어올지는 이 구분 없이는
답할 수 없다.
병합 큐는 이미 있는 도구이고, 반영 후 복구는 에이전트가 충돌을 빠르게 고친다는
전제에 기대기 때문이다.
그 전제는 Anthropic의 환경에서 나온 것이고, 다른 팀에 그대로 옮겨진다는 근거는
Anthropic의 글에도 이 글에도 없다.

### Aspen의 묶음 병합이 글에서는 동작하는 기능처럼 쓰였지만 저장소는 기본값 꺼짐과 미측정이라고 적는다

글은 Aspen이 각 PR을 별도 커밋으로 남기면서 `main`을 한 번만 갱신하고 그래서
비용을 줄인다고 쓴다.
Aspen 저장소의 README는 같은 기능을 서버 측 병합 큐(`ASPEN_MERGE_QUEUE`)로
설명하는데, 기본값은 꺼져 있고 처리율은 아직 측정하지 않았다고
적는다.[^aspen-readme]
프로젝트 전체도 사전 알파(pre-alpha) 단계이고, 스스로 정한 출시 기준 가운데
24시간 무장애 시험과 퍼저 24시간 시험과 팀원이 문서만 보고 따라 하는 벤치마크
재현을 포함한 여러 항목이 아직 끝나지 않았다.[^aspen-readme]
두 가지 성능 수치도 한 대의 서버에서 한 번 돌린 결과여서 성능 주장이 아니라
참고용으로 보라고 README가 적는다.[^aspen-readme]

글은 567회와 약 4회를 소개하면서 조건(자체 측정, 브랜치 전용 URL, CI 제외)을
빠짐없이 밝혔다.
수치 자체는 정직하게 다룬 셈이다.
빠진 것은 이 서버의 지위다.
프로덕션이 아니라 검증 전 단계라는 점, 그리고 묶음 병합이 그 안에서도 꺼져 있는
기능이라는 점이다.
이 두 사실이 없으면 독자는 묶음 병합을 이미 측정된 방법으로 읽는다.

### 묶음 병합이 위험을 옮긴다는 증거가 글이 인용한 페이지에 이미 있다

글은 GitHub의 4월 가용성 업데이트를 PR 하나가 여러 서비스를 움직인다는 설명에만
인용한다.
같은 업데이트는 병합 큐의 사고도 다룬다.
4월 23일에 squash 방식의 병합 큐에서 병합 그룹에 PR이 둘 이상 들어가면 잘못된
병합 커밋이 만들어졌고, 이후 병합이 앞서 병합된 PR과 기존 커밋의 변경을
되돌렸다.
영향을 받은 것은 658개 저장소와 2,092개 PR이었다.[^github-availability]
GitHub는 데이터 손실은 없었다고 하면서도, 영향받은 기본 브랜치의 상태가 올바르지
않았고 모든 저장소를 자동으로 안전하게 복구하지는 못했다고
적었다.[^github-availability]

이 사고는 병합 큐를 쓰지 말라는 증거가 아니다.
영향은 병합 큐 밖에서 병합한 PR과 merge, rebase 방식에는
없었다.[^github-availability]
이 사고가 보여 주는 것은 묶음 병합이 구현하기 어려운 영역이라는 사실, 그리고
`main` 갱신 횟수를 줄이는 대신 갱신 한 번에 더 많은 변경이 걸린다는 사실이다.
글이 묶음 병합의 이점으로 든 것이 `main`을 갱신하는 횟수라면, 갱신 한 번이
틀렸을 때의 피해 범위도 함께 적어야 이점과 위험이 대칭을 이룬다.

### 표의 “유지” 열과 한 줄 요약은 약속의 조건을 지운다

표의 마지막 열은 Git 명령이 유지되는지를 유지와 교체 둘로 나눈다.
Scion만 교체이고 나머지는 모두 유지다.
그런데 같은 글의 본문이 Pando에서 여러 브랜치를 함께 읽는 도구는 브랜치마다 다른
시점의 상태를 볼 수 있다고 적는다.
명령은 그대로여도 저장소 전체의 일관된 시점이라는 보장은 사라진 것이다.
Aspen은 더 구체적이다.
일반 Git 클라이언트로 접속하지만, 강제 푸시와 브랜치 삭제에는 추가 옵션(`-o
force`)이나 lease, 브랜치 전용 URL이 필요하다.
일반 `--force-with-lease`가 동작하도록 OpenAI의 Git 포크가 넣은
확장(`explicit-haves`)도 구현하지 않는다.[^aspen-readme]
“명령을 유지한다”는 말은 철자가 같다는 뜻이지, 같은 명령이 같은 결과를 낸다는
뜻이 아니다.

표의 Entire 행도 같은 방식으로 줄어 있다.
표는 Entire를 서버와 저장소(읽기)로 분류하는데, 미러만 보면 맞는 분류다.
그러나 Entire의 발표는 GitHub가 뒷받침하는 브랜치에 푸시하면 GitHub가 허용하는
만큼만 빠르고, 더 많은 동시 푸시를 받으려면 Entire 고유 브랜치(Entire-native
branches)를 써야 한다고 적는다.[^entire-blog]
미러는 읽기를 나누지만 쓰기 쪽 한도는 원본을 떠나야 풀린다는 조건이 한 칸
요약에서 사라진다.

### 작업 기록의 이동 조건을 설명하면서 기본 동작과 접근 범위를 빠뜨린다

글은 Entire CLI의 체크포인트가 코드 브랜치와 별도의 Git 참조를 쓰므로 `main`만
푸시하면 세션 기록이 따라오지 않는다고 적는다.
Entire CLI의 README는 체크포인트가 기본적으로 별도의
참조(`refs/entire/checkpoints/…`)로 저장되고 코드와 함께 푸시된다고
적는다.[^entire-cli]
그러므로 글의 문장에는 조건이 필요하다.
기본 설정에서는 푸시와 함께 따라가고, 따라가지 않는 경우는 업로드를 끈
설정(`--skip-push-sessions`)을 쓰거나 이 참조를 옮기지 않는 방식으로 저장소를
옮길 때일 것이다.
뒤의 경우는 이 문서의 추정이다.

더 중요한 누락은 접근 범위다.
README는 세션 기록이 같은 Git 원격에 올라가므로 저장소가 공개 상태면 누구나 읽을
수 있고, 비밀 값을 가리는 처리(redaction)도 최선의 노력 수준이라고
경고한다.[^entire-cli]
기록을 별도 참조에 둔다는 구조 설명만으로는 그 기록이 코드와 같은 접근 권한
아래에 놓인다는 사실이 드러나지 않는다.
글이 기록 계층을 이주의 문제로 다루는 만큼, 이주와 함께 접근 권한이 어떻게
달라지는지도 같은 무게로 적혀야 한다.

## 인사이트

### Git 명령의 호환은 의미의 호환이 아니며, 포기한 보장의 목록이 새 계약이다

서버를 다시 설계하면서 `git push`를 그대로 두는 방식은 특정 보장을 포기하는
방식이기도 하다.
Pando는 저장소 전체의 일관된 시점을 포기했다.[^gn-pando]
Aspen은 Pando를 따라 같은 보장을 포기하고, 강제 푸시와 브랜치 삭제에도 추가
옵션을 요구한다.[^aspen-readme]
그러므로 이 서버들을 평가하는 질문은 Git 명령이 되느냐가 아니라 어떤 보장을
포기했고 우리 도구 중 무엇이 그 보장에 기대고 있느냐다.

이 구조는 처음이 아니다.
Cursor의 설명에 따르면 GitHub는 초기에 NFS와 GFS와 DRBD 같은 분산 파일시스템과
블록 복제로 저장소를 여러 서버에서 접근하게 하려 했지만, Git이 로컬 파일시스템의
잠금과 동기화 동작을 전제하고 있어서 네트워크 파일시스템에서는 느리고 오류가
많았다.[^gn-continuity]
GitHub는 결국 파일시스템을 공유하는 방식을 버리고 저장소 전용 서버에 RPC로
접근하는 구조로 옮겼다.[^gn-continuity]
이번에는 호환의 경계가 파일시스템에서 프로토콜로 올라왔을 뿐, 표면은 같고 의미가
약해졌다는 점이 같다.
프로토콜에도 명시되지 않은 의미가 있다.
여러 참조가 한 시점의 것이라는 가정이 그 예다.

둘째 효과는 실패가 조용하다는 점이다.
명령이 거부되지 않고 실행되므로, 예컨대 릴리스 자동화가 `main`과 릴리스 브랜치를
차례로 읽고 한쪽이 다른 쪽을 포함하는지 확인하는 단계가 서로 다른 시점의 상태를
보고 잘못 판단할 수 있다.
이 사례는 이 문서가 만든 가정이다.
의미 호환을 확인하는 방법은 표준 서버와 같은 연산열을 실행해 결과를 비교하는
차등 시험(differential testing)이다.
Aspen은 이 시험을 하고 있지만 목표로 삼은 100만 번의 무작위 연산 규모에는 아직
못 미쳤다고 스스로 적는다.[^aspen-readme]
도입을 검토한다면 여러 참조를 한꺼번에 읽는 도구와 강제 푸시의 의미에 기대는
스크립트의 목록부터 만들고, 후보 서버에 그것들을 돌려 보는 것이 호환 주장보다
믿을 만한 근거가 된다.

### `main`이 직렬 지점이 되면 팀이 고르는 것은 도구가 아니라 오류의 비용을 치르는 시점이다

병합 속도에 검증 시간을 곱하면 동시에 검증 중인 변경의 수가 나온다.
Anthropic의 평균 병합 속도 초당 약 0.35건에 검증이 10분(600초) 걸린다고
가정하면, 어느 순간이든 약 210건이 검증 중이다.
10분은 이 문서의 가정이다.
각 변경은 검증이 끝나기 전에 다른 변경이 먼저 들어와 전제가 바뀔 수 있다.
Anthropic이 병합 큐가 맞지 않는다고 본 이유도 이 지점이다.[^anthropic]

정책마다 비용을 치르는 쪽이 다르다.
반영 전 검증은 대기 시간과 거부된 PR로 치르고, 묶음 병합은 갱신 한 번이 틀렸을
때의 피해 범위로 치르며 GitHub의 4월 사고가 그 예다.[^github-availability]
반영 후 복구는 `main`이 깨져 있는 시간과 복구 능력으로 치른다.[^anthropic]
선택이 정책이라면 측정할 지표도 달라진다.
병합 성공률이 아니라 잘못 들어간 변경이 발견되고 복구되기까지 걸린 시간이 반영
후 복구의 핵심 지표가 될 것이다.
이는 이 문서의 추정이다.
수백 개의 에이전트가 `main`에서 갈라져 일하고 있다면 `main`이 깨진 시간은 그
에이전트 모두에게 번지기 때문이다.
GitHub의 사고에서 모든 저장소를 자동으로 안전하게 복구하지 못했다는 대목이 보여
주듯, 복구가 항상 자동으로 되는 것도 아니다.[^github-availability]

실무에서는 세 숫자를 곱해 보는 것으로 시작할 수 있다.
하루 병합 수를 초 단위로 바꾼 평균 간격, 검증에 걸리는 시간, 그리고 둘의 비다.
비가 1보다 훨씬 크면 한 번에 하나씩 검증하는 큐는 성립하지 않고, 위의 세 정책 중
하나를 의식적으로 골라야 한다.

### 작업 기록은 새로운 이주 대상이면서 새로운 접근 통제 대상이다

앞선 글은 GitHub 종속의 본체가 텍스트가 아니라 참조 그래프라고 정리했다.
세션 기록은 그 그래프에 새 종류의 간선을 더한다.
Entire는 커밋 메시지의 `Entire-Checkpoint` 트레일러로 커밋과 체크포인트를
잇는다.[^entire-cli]
Delta는 커밋 사이의 편집과 메시지를 Git과 별도인 DeltaDB에 기록한다.[^gn-delta]
기록이 같은 원격의 참조에 실리는 도구와 별도 저장소에 있는 도구가 공존하므로,
저장소를 옮길 때 확인할 목록이 PR과 Issues에서 세션 기록까지 늘어난다.

접근 통제에서는 더 눈여겨볼 점이 있다.
코드 저장소는 커밋한 것이
그 저장소의 독자에게 보여도 된다는 관행 아래 운영되어 왔다.
세션 기록은 그런 관행 밖에 있는 자유로운 대화다.
같은 원격에 올라가면 저장소 권한이 그 기록의 유일한 보호가 되고, 공개 저장소라면
누구나 읽을 수 있다.[^entire-cli]
이 도구에는 제어 수단이 있다.
README는 기록을 별도의 비공개 저장소로 보내는 설정(`--checkpoint-remote`),
업로드를 끄는 설정(`--skip-push-sessions`), 다음 푸시가 올릴 내용을 미리 보는
명령(`entire checkpoint list --outgoing`)을 안내한다.[^entire-cli]
결국 기록을 코드와 같은 경계에 둘지는 도입하는 팀이 명시적으로 정해야 하고,
기본값이 그 결정을 대신한다는 점을 알고 있어야 한다.

두 번째 효과는 비공개 저장소를 공개로 바꾸는 순간에 나타난다.
코드 이력은 공개 전에 점검하지만 별도 참조에 실린 세션 기록은 점검 목록에서
빠지기 쉽다.
공개 상태에서는 누구나 읽을 수 있다는 README의 경고가 이 시점에 현실이
된다.[^entire-cli]
이 시나리오는 이 문서의 추정이지만, 점검 목록에 세션 기록 참조를 넣는 비용은
거의 없다.
