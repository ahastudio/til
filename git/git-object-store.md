# Git이 두렵지 않으려면: `.git` 안의 객체 저장소를 직접 들여다보기

원문: [How Not to Be Afraid of Git Anymore | Neil Kakkar](https://neilkakkar.com/How-not-to-be-afraid-of-GIT-anymore.html)

## 소개

Neil Kakkar가 2018년 11월 13일에 쓴 글로, freeCodeCamp의 Medium 출판물에 먼저 실렸다.
그는 Git을 블랙박스로 보지 말고 열어 보라고 권한다.
Git이 어떻게 동작하는지 알면 다시는 명령이 안 먹혀서 저장소를 지우고 새로 받는 일을 하지 않게 된다는 약속이다.

글은 Git을 세 부분으로 나눈다.
객체 저장소(object store), 인덱스(index), 작업 디렉터리(working directory)다.
그리고 빈 저장소에서 파일 하나를 `add`하고, 커밋하고, 브랜치를 만들고, 다른 파일을 커밋하는 동안 `.git/` 디렉터리가 어떻게 바뀌는지 `tree`와 `git cat-file`로 따라간다.

글이 내리는 요약은 이렇다.
Git은 추적하라고 한 파일을 압축한 객체로 다루고, 각 객체는 내용에서 만든 해시를 ID로 갖는다.
파일을 `add`할 때마다 객체가 하나 생기고, 커밋할 때마다 트리 객체와 커밋 메타데이터 객체가 하나씩 생기며, 커밋은 부모를 가리켜 서로 이어진다.
브랜치는 `.git/refs/heads/` 아래에 있는, 커밋 객체를 가리키는 포인터일 뿐이다.

## 동작 방식

### 세 영역

| 영역          | 위치             | 담는 것                                         |
| ------------- | ---------------- | ----------------------------------------------- |
| 작업 디렉터리 | 저장소 폴더 자체 | 지금 편집하는 파일                              |
| 인덱스        | `.git/index`     | 다음 커밋에 들어갈 파일과 객체의 대응(스테이징) |
| 객체 저장소   | `.git/objects/`  | 내용 해시로 이름 붙은 압축된 객체               |

`git add`는 파일 내용으로 해시를 만들고, 내용을 압축해 그 해시 이름으로 객체 저장소에 넣고, 인덱스에 파일 이름과 객체를 적는다.
`git status`는 작업 디렉터리, 인덱스, 마지막 커밋을 비교해 무엇이 스테이징되었고 무엇이 추적되지 않는지 보여 준다.

### 객체 세 종류

- 블롭(blob): 파일 내용 하나. 파일 이름은 들어 있지 않다.
- 트리(tree): 디렉터리 하나. 이름, 모드, 그리고 블롭이나 하위 트리의 해시 목록이다.
- 커밋(commit): 루트 트리 하나의 해시, 부모 커밋의 해시, 작성자와 커미터, 메시지.

파일 하나를 추가한 첫 커밋은 객체 세 개를 남긴다.
`add`가 만든 블롭, 커밋이 만든 트리, 커밋 메타데이터다.
두 번째 파일을 추가해 커밋하면 다시 세 개가 늘어나고, 새 커밋에는 `parent` 줄이 생겨 이전 커밋을 가리킨다.

### 브랜치와 `HEAD`

`git branch the-ending`은 `.git/refs/heads/the-ending`이라는 파일을 만들고 거기에 현재 커밋의 해시를 적는다.
새 커밋이 없으니 `master`와 같은 해시다.
그 브랜치로 옮겨 커밋하면 `the-ending` 파일의 해시만 새 커밋으로 바뀌고, `master`는 그대로 첫 커밋을 가리킨다.

원문의 용어 설명은 `head`를 작업하던 최신 코드를 가리키는 포인터라고 쓴다.
정확히는 `.git/HEAD`가 지금 체크아웃된 브랜치를 가리키고(`ref: refs/heads/master`), 브랜치가 커밋을 가리킨다.
브랜치가 아니라 커밋을 직접 체크아웃하면 `HEAD`에 해시가 바로 적히는데, 이것이 분리된 HEAD(detached HEAD) 상태다.

## 확인하기

글의 실험을 그대로 따라 하면 `.git/` 안에서 무엇이 생기는지 직접 볼 수 있다.

### 블롭 하나 만들기

```bash
cd "$(mktemp -d)" && git init -q -b master
echo 'hello world!' > helloworld

git hash-object helloworld     # add 전에 해시를 미리 계산해 본다
git add helloworld
find .git/objects -type f      # 해시 앞 두 글자 디렉터리 아래에 객체가 생겼다
git cat-file -t "$(git hash-object helloworld)"   # blob
git cat-file -p "$(git hash-object helloworld)"   # hello world!
```

### 해시가 무엇으로 만들어지는지

```bash
# 블롭의 해시는 파일 내용만이 아니라 "blob <크기>\0" 머리말을 붙인 바이트의 SHA-1이다.
printf 'blob %d\0' "$(wc -c < helloworld)" | cat - helloworld | shasum
git hash-object helloworld     # 위와 같은 값
```

같은 내용의 파일은 이름이 달라도 같은 블롭 하나를 공유한다.
이름은 트리에 있고, 블롭에는 없기 때문이다.

### 커밋이 만드는 두 객체

```bash
git -c user.name=me -c user.email=me@example.com commit -q -m "Add helloworld"
git cat-file -p HEAD           # tree <해시>, author, committer, 메시지
git cat-file -p 'HEAD^{tree}'  # 100644 blob <해시> helloworld
cat .git/HEAD                  # ref: refs/heads/master
cat .git/refs/heads/master     # 첫 커밋의 해시
```

### 브랜치는 해시 한 줄짜리 파일이다

```bash
git branch the-ending
cat .git/refs/heads/the-ending # master와 같은 해시
git switch -q the-ending
echo 'Bye world!' > byeworld
git add byeworld
git -c user.name=me -c user.email=me@example.com commit -q -m "add byeworld"
git cat-file -p HEAD           # parent 줄이 첫 커밋을 가리킨다
cat .git/refs/heads/the-ending # 새 커밋 해시
cat .git/refs/heads/master     # 그대로 첫 커밋
```

## 트레이드오프

### 스냅숏 저장은 단순하지만 큰 파일에 약하다

원문의 요약은 Git이 변경마다 diff가 아니라 파일 전체를 저장하고, 그래서 아주 큰 파일을 잘 다루지 못한다고 쓴다.
절반은 맞다.
`add`가 만드는 느슨한 객체(loose object)는 파일 전체를 압축한 것이고, 커밋은 그 순간의 전체 트리를 가리킨다.
이 스냅숏 모델 덕분에 어떤 커밋이든 과거 파일을 다시 계산하지 않고 바로 꺼낼 수 있다.

하지만 저장 공간 쪽 이야기는 더 있다.
`git gc`나 `push` 때 느슨한 객체는 팩 파일(packfile)로 묶이고, 팩 안에서는 비슷한 객체 사이를 델타로 압축한다.
그래서 텍스트 파일의 작은 수정이 저장소를 파일 크기만큼 불리지는 않는다.
큰 파일이 문제인 진짜 이유는, 바이너리처럼 델타가 잘 안 되는 파일은 버전마다 거의 통째로 쌓이고, 저장소를 복제하는 모든 사람이 그 역사 전체를 받아야 한다는 데 있다.
Git LFS가 큰 파일을 저장소 밖에 두고 포인터만 커밋하는 이유가 이것이다.

### 연결 리스트라는 비유는 병합에서 깨진다

원문은 부모 포인터를 보고 커밋이 연결 리스트처럼 이어진다고 설명한다.
직선으로 쌓인 역사에서는 맞는 그림이다.
그러나 병합 커밋은 부모가 둘 이상이고, 그래서 Git의 역사는 리스트가 아니라 방향성 비순환 그래프(DAG)다.

이 차이는 명령을 이해하는 데 중요하다.
`HEAD^`와 `HEAD~`가 다른 이유, `git log --first-parent`가 필요한 이유, 리베이스가 병합 커밋을 어떻게 다루는지는 모두 부모가 여럿일 수 있다는 데서 나온다.
연결 리스트 그림으로 시작하되, 병합이 등장하는 순간 그래프로 바꿔 그려야 한다.

### 두 글자 디렉터리는 검색 속도보다 디렉터리 크기 때문이다

원문은 객체가 해시 앞 두 글자 디렉터리에 들어가는 이유를 검색이 빨라지기 때문이라고 쓴다.
더 정확한 이유는 한 디렉터리에 파일이 수십만 개 쌓이지 않게 256개로 나누는 것이다.
많은 파일 시스템은 한 디렉터리의 항목이 지나치게 많으면 느려지거나 다루기 어려워진다.

## 함정

### `add` 뒤에 파일을 고치면 커밋되는 것은 `add` 당시의 내용이다

인덱스는 파일 이름이 아니라 그 순간 내용의 블롭을 가리킨다.
`git add` 뒤에 파일을 더 고치면, 새 수정은 작업 디렉터리에만 있고 커밋에는 들어가지 않는다.
`git status`가 같은 파일을 스테이징된 변경과 스테이징되지 않은 변경에 동시에 보여 주는 것이 이 상태다.

### 커밋되지 않은 블롭도 객체 저장소에 남는다

`add`만 하고 커밋하지 않은 내용, 또는 `reset`으로 버린 커밋의 객체는 즉시 사라지지 않는다.
어떤 참조에도 닿지 않는 객체로 남았다가 가비지 컬렉션 때 정리된다.
실수로 비밀 값을 `add`했다가 되돌렸다면, 그 블롭은 `git fsck --lost-found`로 한동안 되살릴 수 있다는 뜻이기도 하다.

### 추적하지 않는 파일은 브랜치를 옮겨도 따라온다

원문의 `byeworld`처럼 추적하지 않는 파일은 어느 브랜치로 옮겨도 작업 디렉터리에 그대로 있다.
Git은 자기가 추적하는 파일만 브랜치에 맞게 바꾸기 때문이다.
그래서 브랜치를 옮긴 뒤 보이는 파일이 그 브랜치의 것이라고 가정하면 안 된다.

### 기본 브랜치 이름은 이제 `master`가 아닐 수 있다

글은 기본 브랜치를 `master`라고 설명하지만, 최근 Git과 대부분의 호스팅 서비스는 `init.defaultBranch` 설정에 따라 `main`을 기본으로 쓴다.
위의 실험에서 `git init -b master`로 이름을 고정한 것은 원문과 같은 경로를 보기 위해서다.

## 기억할 원칙

### 명령은 포인터와 객체를 옮기는 연산일 뿐이다

객체 저장소를 한 번 들여다보면 Git 명령 대부분이 두 가지 연산으로 보인다.
새 객체를 만드는 것과, 포인터가 가리키는 해시를 바꾸는 것이다.
`commit`은 객체를 만들고 현재 브랜치 포인터를 옮기고, `branch`는 포인터 파일을 하나 만들고, `reset`은 포인터를 다른 해시로 옮긴다.

이 그림을 가지고 있으면 명령이 무서운 이유가 줄어든다.
대부분의 명령은 객체를 지우지 않고 포인터만 옮기므로, 포인터가 어디 있었는지(`git reflog`)만 알면 거의 모든 실수를 되돌릴 수 있다.
저자가 약속한 두렵지 않음은, 결국 되돌릴 수 있다는 것을 아는 데서 온다.
