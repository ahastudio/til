# ERSC의 Git 이후: Git 프로토콜은 그대로 두고 저장소 밑을 갈아엎는다

원문: [What comes after git // ERSC](https://ersc.io/blog/what-comes-after-git)

HN 토론: <https://news.ycombinator.com/item?id=49652985> (77점, 31개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/ez6ivp/what_comes_after_git> (22점, 31개 댓글)

GN 토론: <https://news.hada.io/topic?id=36752>

## 요약

East River Source Control(ERSC)의 Steve Klabnik이 2026년 9월 10일에 쓴 글이다.
ERSC가 1년 넘게 만들어 온 것을 공식 발표하지는 않고,
버전 관리가 어디로 가는지에 대한 생각을 먼저 공유한다는 글이다.

글의 주장은 세 단계로 이어진다.
첫째, 에이전트 개발이 버전 관리 시스템에 특별한 부담을 준다고 한다.
코드가 더 빨리 더 많이 만들어져 저장소가 커지고, 활성 브랜치가 늘고,
병합 경합이 심해진다는 것이다.
에이전트는 더 많은 맥락을 쉽게 얻기 위해 모노레포와 잘 맞고,
개발 환경을 클라우드의 격리된 곳으로 옮기므로 빠른 클론이 필요하다고 한다.
큰 조직의 문제가 에이전트 때문에 나머지에게도 온다는 것이 글의 요지다.

둘째, Git은 미래를 위해 만들어지지 않았다고 말한다.
2005년의 제약 아래 리눅스 커널이라는 오픈소스 프로젝트를 위해 설계되었고,
코드를 공개하지 않는 조직에 유용한 기능이 빠져 있다는 것이다.
리눅스 7.2는 약 4,300만 줄이지만 큰 기업의 모노레포는 몇 년 전에 이미
수십억 줄이었다고 한다.
그럼에도 Git이 툴링 전반에 퍼져 있어 대안을 쓰기 어렵다는 점도 인정한다.

셋째, 그래서 ERSC는 Git 프로토콜은 그대로 말하되 저장소 계층을 바꾼다.
일반 Git 호스트는 Git 저장소를 디스크에 두고 그 앞에 서비스 계층을 두지만,
ERSC는 Git 저장소를 서버에 두지 않고 별도의 Git 이외 저장 엔진을 쓰며
그 앞에 Git 브리지를 둔다.
Git 저장소를 진실의 원천으로 쓰는 시스템과 달리 수평 확장이 가능하고,
다른 회사의 사용이 영향을 주지 않는 별도 배포라서 신뢰성과 통제를 준다고 한다.

넷째, 미래에 Jujutsu(jj)의 다른 백엔드를 서버에도 만드는 구상이다.
jj는 Git 백엔드로 로컬 Git 저장소와 일하지만 Google의 Piper 백엔드도 있어
개인이 동료가 Git을 써도 jj를 고를 수 있다.
ERSC는 서버에서 같은 전략을 쓰려 하고, 같은 저장 엔진 위에 Git 프로토콜
브리지와 향후의 네이티브 프로토콜 브리지를 나란히 두겠다고 한다.
글은 이 네이티브 프로토콜이 아직 없는 미래 작업이며, jj 상류에 그런 프로토콜이
지금 없고, 상류가 원하지 않을 수도 있다고 분명히 적는다.
코드 리뷰, CI, 이슈 추적 같은 나머지는 하나의 포지가 아니라 부품으로
제공하며, 저장소가 첫 번째 부품이라고 한다.

## 분석

### 호환성을 입구로, 교체를 출구로 삼는 구조다

글이 선택한 경로는 Git 클라이언트가 계속 동작하는 것이 전제인 교체다.
도입 저항이 가장 큰 곳은 모두가 쓰는 프로토콜이므로, 프로토콜은 지키고 그
아래만 바꾼다.
이는 다른 영역에서 반복된 방식이다.
인터페이스를 유지하면서 구현을 바꾸는 쪽이 사용자 전환 비용이 없기 때문이다.
글이 jj의 점진적 도입을 모델로 드는 것도 같다.
조직은 Git 클라이언트로 시작해 필요할 때 다른 클라이언트를 켠다.

### 저장소와 포지를 분리해 판다

글은 코드 리뷰와 CI 같은 부품을 따로 팔겠다고 말하며
전통적 포지의 통합 패키지와 선을 긋는다.
이는 스토리지만 먼저 내는 전략의 근거이기도 하다.
기존 도구와 섞어 쓸 수 있다고 하니 도입 부담이 줄고,
ERSC로서는 가장 어려운 부품부터 증명할 기회가 된다.
다만 글은 부품 사이의 인터페이스가 어떻게 정의되는지를 말하지 않는다.

### 수평 확장의 근거는 저장 엔진의 소유다

글이 말하는 확장성은 Git 저장소를 진실의 원천으로 삼지 않는다는 데서 나온다.
저장 형식을 바꾸면 Git 서버가 겪는 디스크와 복제 문제를 벗어날 수 있다는 논리다.
글은 어떤 형식인지, 합의를 어떻게 하는지, 어떤 일관성 모델인지 설명하지 않고
이 모두를 곧 발표할 것이라고 한다.
따라서 이 글에서 읽을 수 있는 것은 방향이고 설계가 아니다.

## 비평

### 글은 Git이 무엇을 못하는지 말하지 않는다

HN 반응의 대부분이 이 점을 지적했다.
sublinear는 글의 핵심이어야 할 대목이 빈약하며 Git의 무엇이 잘못인지 설명이
없다고 했고,[^sublinear]
Bayart는 비판이 Git의 데이터 표현과 저장에 대한 것인지, UX에 대한 것인지
알 수 없고 에이전트와 Git 사이의 오버헤드가 문제라면 버전 관리가 아니라 에이전트나
UI의 문제일 수 있다고 했다.[^bayart]
nrr는 Git 기술에 깊이 관여해 온 사람으로서 Jujutsu 이전 경로를 넘는 세부가 없어
실망했고 pack 프로토콜의 와이어 형식이 얼마나 골칫거리인지라도 짚어 주길
바랐다고 썼다.[^nrr]
fergie는 Git이 잘 못하는 것은 데이터와 데이터베이스의 버전 관리인데
글이 이를 다루지 않는다고 했다.[^fergie]
Lobste.rs에서도 sigmonsez가 글을 끝까지 읽었지만 구체적인 문제도 세부도 없다고
썼고,[^sigmonsez]
gspr는 Darcs나 Pijul 같은 다른 설계가 Git의 어느 면을 고칠지에 대한 비판을
기대했는데 AI 에이전트와 Git 저장소 이야기라서 실망했다고 했다.[^gspr]
글쓴이 steveklabnik은 이 글이 회사 전략과 버전 관리의 현재에 대한 믿음을 다룬
높은 수준의 글이고 기술 심층 글이 아니며,
기술 세부는 앞으로 다루겠다고 답했다.[^steveklabnik]
이 답은 글의 성격을 인정하지만, 글이 Git의 한계를 주장하는 근거를 제시하지
않았다는 점은 그대로 남는다.
이 문서도 같은 평가다.
글의 주장은 에이전트가 만드는 규모 문제와 Git의 한계를 같은 것으로 놓지만,
둘이 어디서 만나는지 구체적 사례나 수치가 없다.

### 오픈소스 설계라는 이유는 기업 규모의 이유가 되지 못한다

글은 Git이 오픈소스 프로젝트용이라 비공개 조직의 기능이 빠졌다고 말한다.
gonzalohm은 이 근거가 이상하다고 했고,
entrope는 글의 주장이 사실은 큰 기업은 모노레포를 쓰고 그것이 단일 프로젝트
저장소보다 크다는 것이며,
구글의 경험과는 맞지만 FreeBSD, OpenBSD, NetBSD 경험과는 어긋난다고 풀어
썼다.[^gonzalohm][^entrope]
어떤 기능이 빠졌는지는 글에 나오지 않으므로,
이 근거는 규모 주장에 기대고 규모 주장은 모노레포 사용에 한정된다.

### 발표가 아닌 발표다

글은 아무것도 발표하지 않는다고 시작해 곧 열겠다고 끝낸다.
EddieRingle은 글이 논증을 하지 않고 Git 경쟁자와 학회를 홍보한다고 느꼈고,
GraphQL이 왜 들어왔는지도 이해하지 못했다고 썼다.[^eddiering]
글에 GraphQL API가 그림에 없다고 한 줄 언급된 것이 전부다.
이 반응은 정보가 부족한 글이 신뢰를 얻지 못하는 방식의 한 예다.
Lobste.rs에서 algernon은 회사, 모노레포, 규모 이야기를 줄줄이 늘어놓는 글이라며
궁금한 것은 이 방향이 개인의 규모로 줄어들 수 있느냐이고
자신들은 대상이 아닌 것 같다고 썼다.[^algernon]
글은 큰 조직을 대상으로 말하며 개인과 소규모 팀에는 언급이 없다.

## 인사이트

### 호환성 전략은 가장 큰 리스크를 프로토콜 번역 계층에 모은다

Git 브리지는 Git 프로토콜의 모든 동작을 비Git 저장소 위에서 흉내 내야 한다.
rbsmith가 말한 대로 BitKeeper 팀에서 35년 가까이 이 분야에 있었다는 사람도
Git이 모두에게 충분하지는 않다고 하면서,
누군가에게는 그 고통을 없애는 데 돈을 낼 가치가 있다고 했다.[^rbsmith]
그 고통을 없애려면 브리지가 모든 경계 사례에서 Git과 같아야 하고,
한 번이라도 다르면 신뢰가 떨어진다.
글은 호환성 시험이나 지원 범위를 말하지 않는다.
브리지의 충실도가 이 접근의 성패를 가르며,
공개된 뒤 가장 먼저 확인할 것은 pack 프로토콜과 부분 클론 같은 까다로운
기능이 어디까지 동작하는지다.

### 에이전트가 만든 문제는 Git을 바꾸는 쪽과 서버를 바꾸는 쪽으로 갈린다

같은 시기에 GitHub은 Git을 유지하면서 서버 쪽 스토리지를 새로 짰다.
이 글의 ERSC는 서버 쪽 저장 엔진을 바꾸면서 클라이언트를 확장할 가능성을
열어 둔다.
둘 다 Git 프로토콜을 지키는 서버 교체라는 점에서 같은 방향이고,
글이 말한 jj의 네이티브 프로토콜이 다른 점이다.
프로토콜을 바꾸려면 클라이언트 생태계와 합의가 필요하다.
이 글은 상류가 원하지 않을 수도 있다고 인정했는데,
이는 정직하지만 이 전략의 약한 고리를 스스로 밝힌 것이다.
그 고리가 풀리지 않으면 결과는 빠른 Git 서버가 될 뿐이다.

### 이름 붙은 방향과 증명된 설계는 다르다

글의 제목은 Git 다음에 무엇이 오는지를 묻지만,
본문이 답하는 것은 ERSC가 무엇을 만들고 있다는 방향이다.
HN에서 같은 제목을 쓴 글이 이전에도 여러 번 올라왔다는 점은
이 질문이 반복되는 주제임을 보여 준다.
반복되는 질문에서 신뢰를 얻는 것은 질문의 새로움이 아니라 시험 가능한 설계다.
이 글 이후 ERSC가 설계와 수치를 공개하는지가, 이 문서가 다음에 확인할 일이다.
