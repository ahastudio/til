# Git으로 코드를 찾기: grep, 곡괭이, 그리고 줄 단위 이력

원문: [Git - Searching](https://git-scm.com/book/en/v2/Git-Tools-Searching)

## 소개

Pro Git 2판 7.5절이다.
어느 정도 규모가 있는 코드베이스라면 함수가 어디서 호출되고 정의되는지 찾거나 메서드의 이력을 봐야 할 일이 생기며, Git이 데이터베이스에 저장된 코드와 커밋을 빠르게 훑어보는 도구를 몇 가지 제공한다는 것이 이 절의 취지다.

세 가지 도구를 다룬다. 세 도구가 답하는 질문이 각각 다르다.

| 도구            | 답하는 질문                               |
| --------------- | ----------------------------------------- |
| `git grep`      | 이 문자열이 지금 어디에 있는가            |
| `git log -S/-G` | 이 문자열이 언제 들어오고 언제 사라졌는가 |
| `git log -L`    | 이 함수나 이 줄이 어떻게 변해 왔는가      |

이 구분이 이 절의 전부라고 해도 과언이 아니다.
같은 “찾기”라는 말로 부르지만, 위치를 찾는 것과 시점을 찾는 것과 변천을 따라가는 것은 다른 작업이고 도구도 다르다.

## git grep

`git grep`은 커밋된 어떤 트리든, 작업 디렉터리든, 인덱스든 문자열이나 정규식으로 검색한다.
기본 동작은 작업 디렉터리의 파일을 훑는 것이다.

`-n` 또는 `--line-number`로 줄 번호를 붙인다.

```bash
git grep -n gmtime_r
```

```text
compat/gmtime.c:3:#undef gmtime_r
compat/gmtime.c:8: return git_gmtime_r(timep, &result);
compat/gmtime.c:11:struct tm *git_gmtime_r(const time_t *timep, struct tm *result)
compat/mingw.c:826:struct tm *gmtime_r(const time_t *timep, struct tm *result)
date.c:482: if (gmtime_r(&now, &now_tm))
git-compat-util.h:1138:struct tm *git_gmtime_r(const time_t *, struct tm *);
```

매치를 전부 찍는 대신 어느 파일에 몇 번 나오는지만 보려면 `-c` 또는 `--count`를 쓴다.

```bash
git grep --count gmtime_r
```

```text
compat/gmtime.c:4
compat/mingw.c:1
compat/mingw.h:1
date.c:3
git-compat-util.h:2
```

검색 문자열이 어느 함수 안에 있는지가 궁금하면 `-p` 또는 `--show-function`을 붙인다.
이 옵션이 이 절에서 가장 저평가된 기능이다.

```bash
git grep -p gmtime_r *.c
```

```text
date.c=static int match_multi_number(timestamp_t num, char c, const char *date,
date.c: if (gmtime_r(&now, &now_tm))
date.c=static int match_digit(const char *date, struct tm *tm, int *offset, int *tm_gmt)
date.c: if (gmtime_r(&time, tm)) {
date.c=int parse_date_basic(const char *date, timestamp_t *timestamp, int *offset)
date.c: /* gmtime_r() in match_digit() may have clobbered it */
```

`gmtime_r`이 `date.c`의 `match_multi_number`와 `match_digit`에서 호출된다는 것이 바로 읽힌다.
세 번째 매치는 주석에 나온 문자열일 뿐이다.

여러 조건을 한 줄 안에서 동시에 만족시키려면 `--and`를 쓴다.
아래는 `LINK` 또는 `BUF_MAX`를 이름에 포함하는 상수 정의를, 현재 체크아웃이 아니라 `v1.8.0` 태그 시점에서 찾는 예다.

```bash
git grep --break --heading \
  -n -e '#define' --and \( -e LINK -e BUF_MAX \) v1.8.0
```

```text
v1.8.0:builtin/index-pack.c
62:#define FLAG_LINK (1u<<20)

v1.8.0:cache.h
73:#define S_IFGITLINK 0160000
74:#define S_ISGITLINK(m) (((m) & S_IFMT) == S_IFGITLINK)

v1.8.0:strbuf.c
326:#define STRBUF_MAXLINK (2*PATH_MAX)

v1.8.0:zlib.c
30:/* #define ZLIB_BUF_MAX ((uInt)-1) */
31:#define ZLIB_BUF_MAX ((uInt) 1024 * 1024 * 1024) /* 1GB */
```

`--break`와 `--heading`은 파일마다 빈 줄을 넣고 파일명을 머리글로 빼서 출력을 읽기 쉽게 만든다.

이 예에 이 명령의 두 가지 이점이 전부 들어 있다.
첫째는 빠르다는 것이고, 둘째는 작업 디렉터리만이 아니라 Git 안의 어떤 트리든 검색할 수 있다는 것이다.
마지막 인자로 `v1.8.0`을 준 것이 두 번째 이점이며, 이것이 `grep`이나 `ack`으로는 체크아웃 없이 할 수 없는 일이다.

## git log의 곡괭이

문자열이 지금 어디 있는지가 아니라 언제 존재했고 언제 들어왔는지를 알고 싶을 때가 있다.
`git log`에 커밋 메시지나 diff 내용으로 커밋을 찾는 옵션이 있다.

`-S`가 그것이고, 흔히 곡괭이(pickaxe) 옵션이라 불린다.
주어진 문자열의 출현 횟수를 바꾼 커밋만 보여 준다.

```bash
git log -S ZLIB_BUF_MAX --oneline
```

```text
e01503b zlib: allow feeding more than 4GB in one go
ef49a7a zlib: zlib can only process 4GB at a time
```

두 커밋의 diff를 보면 `ef49a7a`에서 상수가 도입되었고 `e01503b`에서 수정되었음을 알 수 있다.

“출현 횟수를 바꾼”이라는 조건이 핵심이다. 단순히 그 문자열이 diff에 등장하는 커밋이 아니다.
해당 문자열을 포함한 줄이 추가되고 동시에 같은 수만큼 삭제된 커밋은 걸리지 않는다.
그래서 도입 시점과 제거 시점만 정확히 뽑힌다.

더 구체적인 조건이 필요하면 `-G`에 정규식을 준다.

```bash
git log -G 'ZLIB_BUF_MAX|ZLIB_MAX' --oneline
```

`-G`는 diff의 추가·삭제 줄 중 정규식에 걸리는 것이 있는 모든 커밋을 보여 준다.
즉 출현 횟수가 그대로인 변경, 예를 들어 줄이 옮겨지거나 그 줄의 다른 부분이 바뀐 커밋까지 잡힌다.

## git log -L

줄 단위 이력 검색이다. 함수나 코드 한 줄의 변천을 패치 연속으로 보여 준다.

```bash
git log -L :git_deflate_bound:zlib.c
```

`:함수명:파일` 형태를 주면 Git이 그 함수의 경계를 추정한 뒤, 이력을 거슬러 올라가며 그 범위에 가해진 모든 변경을 패치로 내놓는다.
함수가 처음 생긴 시점까지 간다.

```text
commit ef49a7a0126d64359c974b4b3b71d7ad42ee3bca
Author: Junio C Hamano <gitster@pobox.com>
Date:   Fri Jun 10 11:52:15 2011 -0700

    zlib: zlib can only process 4GB at a time

diff --git a/zlib.c b/zlib.c
--- a/zlib.c
+++ b/zlib.c
@@ -85,5 +130,5 @@
-unsigned long git_deflate_bound(z_streamp strm, unsigned long size)
+unsigned long git_deflate_bound(git_zstream *strm, unsigned long size)
 {
-	return deflateBound(strm, size);
+	return deflateBound(&strm->z, size);
 }
```

줄 번호 범위로도 지정할 수 있다.

```bash
git log -L 100,120:zlib.c    # 100~120번째 줄의 이력
git log -L 100,+20:zlib.c    # 100번째 줄부터 20줄
```

## 어떤 도구를 쓸 것인가

찾는 대상이 아니라 질문의 형태로 고른다.

| 상황                                      | 명령                               |
| ----------------------------------------- | ---------------------------------- |
| 이 심볼이 지금 어디에 쓰이는가            | `git grep -n`                      |
| 어느 파일이 이 개념을 많이 다루는가       | `git grep --count`                 |
| 이 호출이 어느 함수 안에 있는가           | `git grep -p`                      |
| 예전 버전에는 이것이 어떻게 되어 있었는가 | `git grep <패턴> <태그 또는 커밋>` |
| 이 상수는 언제 생겼고 언제 없어졌는가     | `git log -S`                       |
| 이 패턴이 닿은 모든 변경을 보고 싶다      | `git log -G`                       |
| 이 함수는 어떻게 지금 모습이 되었는가     | `git log -L :함수:파일`            |
| 이 줄은 누가 마지막으로 바꿨는가          | `git blame`                        |

`git blame`과 `git log -L`의 관계를 헷갈리기 쉽다.
`blame`은 각 줄의 마지막 변경 하나만 보여 주고, `-L`은 그 줄의 모든 변경을 시간순으로 보여 준다.
`blame`으로 시작해 관심 있는 줄을 찾고 `-L`로 그 줄의 전체 역사를 보는 순서가 자연스럽다.

## 실전 조합

도입 시점을 찾은 뒤 그 커밋의 맥락을 보는 것이 가장 흔한 흐름이다.

```bash
# 1. 이 설정 키가 언제 생겼는지 찾는다
git log -S 'MAX_RETRY_COUNT' --oneline --reverse | head -1

# 2. 그 커밋 전체를 본다
git show $(git log -S 'MAX_RETRY_COUNT' --format=%H --reverse | head -1)

# 3. 그 커밋이 속한 병합과 PR 맥락을 본다
git log --merges --ancestry-path \
  $(git log -S 'MAX_RETRY_COUNT' --format=%H --reverse | head -1)..HEAD | tail -20
```

`--reverse`를 붙여 가장 오래된 것부터 보는 것이 1번의 요령이다.
`-S`는 도입과 제거를 모두 잡으므로, 정렬을 뒤집지 않으면 최신 변경이 먼저 나온다.

삭제된 코드를 되찾을 때도 같은 조합이 쓰인다.

```bash
# 삭제된 함수 이름으로 마지막 존재 시점을 찾는다
git log -S 'legacy_auth_handler' --oneline

# 삭제 커밋의 부모에서 파일을 꺼낸다
git show <삭제커밋>^:src/auth.c > /tmp/auth-before.c
```

특정 경로로 범위를 좁히면 큰 저장소에서 속도가 크게 달라진다.

```bash
git log -S 'MAX_RETRY_COUNT' -- src/ config/
git grep -n 'MAX_RETRY_COUNT' -- '*.go'
```

## 트레이드오프

### `-S`의 정확성은 이름이 유일할 때만 성립한다

곡괭이의 강점은 노이즈가 거의 없다는 것이다.
출현 횟수를 바꾼 커밋만 걸리므로, 결과가 두세 줄이면 그중 하나가 도입 커밋이라고 거의 확신할 수 있다.

그 정확성이 문자열의 유일성에 전적으로 의존한다.
`ZLIB_BUF_MAX` 같은 이름은 코드베이스 전체에서 하나의 개념을 가리키므로 곡괭이가 완벽히 작동한다.
`count`나 `handler`처럼 흔한 단어로는 수백 개 커밋이 나오고, 그 목록은 아무것도 말해 주지 않는다.

그리고 리팩터링이 이름을 바꾸면 곡괭이의 추적이 그 지점에서 끊긴다.
`MAX_RETRY`가 `MAX_RETRY_COUNT`로 바뀌었다면 두 이름을 각각 따로 쫓아야 하고, 그 사실 자체를 미리 알아야 한다.
즉 곡괭이는 답을 주지만, 질문이 이미 정확할 때만 그렇다.

이 한계를 우회하는 방법은 문자열이 아니라 구조를 검색하는 것이다.
`-G`에 정규식을 주어 `MAX_RETRY(_COUNT)?`처럼 변형을 함께 잡거나, 상수 이름 대신 그 값이나 주변 코드 형태를 검색하는 식이다.
그러나 어느 쪽이든 정확성과 재현율을 맞바꾸는 일이며, 공짜로 둘 다 얻을 수는 없다.

### `-L`은 편리한 대신 함수 경계 추정에 의존한다

`git log -L :함수:파일`이 놀라운 이유는 Git이 언어를 모르면서도 함수 경계를 잡아낸다는 점이다.
정규식 기반 휴리스틱이고, 언어별 규칙은 `.gitattributes`의 `diff` 속성으로 지정한다.

추정이 빗나가는 경우가 실제로 있다.
같은 이름의 함수가 오버로드되어 여러 개 있으면 어느 것을 잡을지 모호하고, 중첩 함수나 클로저는 경계가 엉킨다.
언어 설정이 없는 파일에서는 들여쓰기와 중괄호에 의존하므로, Python이나 Haskell처럼 중괄호가 없는 언어에서 특히 불안정하다.

더 근본적인 한계는 함수가 이동하거나 이름이 바뀌면 이력이 거기서 멈춘다는 것이다.
`-L`은 현재 이름과 현재 파일을 출발점으로 삼아 거슬러 올라가는데, 파일이 쪼개지거나 함수가 다른 파일로 옮겨 간 지점에서 추적이 끊긴다.
`--follow`처럼 파일 이름 변경을 따라가는 옵션과 조합할 수도 없다.

그래서 `-L`이 “함수가 처음 생긴 시점까지 간다”고 할 때의 “처음”은 실제 최초가 아니라 이 파일에서 이 이름으로 처음 나타난 시점이다.
이력이 짧게 끝났다면 그 지점의 커밋을 열어 함수가 어디서 왔는지 직접 확인해야 한다.

### `git grep`이 빠른 이유가 곧 한계의 이유다

`git grep`이 일반 `grep`보다 빠른 것은 인덱스를 알고 있기 때문이다.
`.gitignore` 대상과 추적되지 않는 파일을 아예 건드리지 않으므로, `node_modules`나 빌드 산출물이 자동으로 빠진다.

같은 성질이 한계이기도 하다. 추적되지 않는 파일은 검색되지 않는다.
방금 만들었지만 아직 `git add`하지 않은 파일은 `git grep`에 잡히지 않고, 그 사실을 알아채기 전까지는 “그 코드가 없다”고 잘못 결론 내리게 된다.
`--untracked` 옵션이 있지만 기본이 아니다.

그리고 커밋 트리를 검색할 때의 비용 구조가 다르다.
작업 디렉터리 검색은 파일을 그대로 읽지만, `v1.8.0` 같은 트리를 검색하려면 해당 시점의 블롭을 풀어야 한다.
태그 하나를 검색하는 것은 빠르지만, 여러 시점을 훑는 것은 체크아웃해서 `rg`를 돌리는 것보다 느릴 수 있다.

현대적 대안과의 관계도 정리해 둘 만하다.
`ripgrep`은 순수 텍스트 검색 속도에서 `git grep`보다 빠르고 `.gitignore`도 존중한다.
`git grep`이 남는 이유는 속도가 아니라 과거 트리를 검색할 수 있다는 점 하나다.

## 함정

`-S`에 정규식을 주면 안 된다. `-S`는 고정 문자열이고, 정규식이 필요하면 `-G`이거나 `-S`에 `--pickaxe-regex`를 함께 줘야 한다.

`-S`와 `-G`의 차이를 “-G가 더 강력하다”로만 기억하면 오해한다.
`-G`는 결과가 훨씬 많아지고, 도입 시점을 찾는 목적에는 오히려 나쁘다.
줄이 옮겨진 커밋까지 전부 걸리기 때문이다.

`git grep`의 패턴과 경로 사이에 `--`를 넣지 않으면, 패턴이 리비전으로 해석될 수 있다.
브랜치 이름과 같은 문자열을 검색할 때 실제로 겪는 문제다.

`git log -S`의 결과가 비어 있다고 해서 그 문자열이 존재한 적 없다는 뜻은 아니다.
경로 제한을 걸었거나, 얕은 복제(`--depth`)로 받은 저장소라면 이력 자체가 잘려 있다.
빈 결과를 보면 먼저 `git log --oneline | wc -l`로 이력이 온전한지 확인하는 편이 낫다.

서브모듈 안은 검색되지 않는다. `git grep --recurse-submodules`가 필요하다.

`--and`로 여러 조건을 걸 때 괄호를 셸이 먹지 않게 이스케이프해야 한다.
문서의 예에서 `\( ... \)`로 쓴 이유가 그것이다.

`-L`과 `-S`를 한 명령에 함께 쓸 수 없다. 두 옵션은 이력을 훑는 방식이 근본적으로 다르다.

## 확인하기

Git 저장소를 직접 복제해 문서의 예를 그대로 재현할 수 있다.

```bash
git clone https://github.com/git/git.git /tmp/git-src
cd /tmp/git-src

# 1. 함수 맥락과 함께 검색한다
git grep -p gmtime_r -- '*.c' | head -20

# 2. 과거 트리를 검색한다. 체크아웃하지 않는다는 점이 핵심이다
git grep -n ZLIB_BUF_MAX v1.8.0

# 3. 그 상수의 도입과 변경 커밋을 찾는다
git log -S ZLIB_BUF_MAX --oneline

# 4. -S 와 -G 의 결과 개수를 비교한다
git log -S ZLIB_BUF_MAX --oneline | wc -l
git log -G ZLIB_BUF_MAX --oneline | wc -l

# 5. 함수 하나의 전체 이력을 본다
git log -L :git_deflate_bound:zlib.c | head -60
```

4번이 두 옵션의 차이를 수치로 보여 주는 실험이다.
`-G` 쪽이 더 많이 나오며, 늘어난 커밋들이 출현 횟수를 바꾸지 않은 변경이다.

자기 저장소에서 `-L`의 한계를 확인하려면 이렇게 한다.

```bash
# 함수 이력이 예상보다 짧게 끝나는지 본다
git log -L :내함수:src/파일.c --oneline | tail -5

# 끝난 지점의 커밋을 열어 함수가 어디서 왔는지 확인한다
git show <가장오래된커밋> --stat
```

## 체크리스트

- 찾으려는 것이 위치인가, 시점인가, 변천인가를 먼저 정했는가
- 시점을 찾는데 `git grep`을 쓰고 있지는 않은가
- `-S`에 준 문자열이 코드베이스에서 충분히 유일한가
- `-S` 결과가 비었을 때 이력이 얕은 복제가 아닌지 확인했는가
- 그 심볼이 과거에 다른 이름이었을 가능성을 검토했는가
- 큰 저장소에서 경로 제한(`-- path`)을 걸었는가
- 추적되지 않는 파일이 검색 대상에서 빠진 것을 인지하고 있는가
- 서브모듈 안을 봐야 한다면 `--recurse-submodules`를 붙였는가

## 비평

### 이 절은 도구를 소개하지만 언제 쓸지는 말해 주지 않는다

세 도구의 사용법은 정확하고 예제도 실제 Git 저장소에서 재현 가능하다.
그런데 절 전체가 “이런 옵션이 있다”의 나열이고, 어떤 상황에서 어느 도구를 집어야 하는지에 대한 안내가 없다.

이것이 사소한 결함이 아닌 이유는 세 도구가 겉보기에 비슷하기 때문이다.
전부 문자열을 받아 결과를 출력하고, 전부 “검색”이라는 이름 아래 묶여 있다.
초보자가 `git log -S`를 써야 할 자리에 `git grep`을 쓰고 “없는데요”라고 결론 내리는 것은 흔한 실수이며, 이 절은 그 실수를 예방하지 않는다.

도입부의 문장이 힌트를 주기는 한다. 함수가 어디서 호출되고 정의되는지, 혹은 메서드의 이력을 봐야 할 때라고 두 경우를 나열한 부분이다.
그러나 그 구분이 이후 본문의 구조와 연결되지 않고, 각 도구를 소개할 때 “이럴 때는 이것”이라는 문장이 반복되지도 않는다.

### 곡괭이의 의미론을 한 문장으로 넘어간다

`-S`가 “그 문자열의 출현 횟수를 바꾼 커밋만” 보여 준다는 서술은 정확하다.
문제는 이 한 문장이 이 옵션을 이해하는 데 필요한 거의 전부인데, 그 함의가 설명되지 않는다는 점이다.

출현 횟수 기반이라는 사실에서 따라오는 결과가 여럿이다.
같은 줄을 옮기기만 한 커밋은 걸리지 않고, 추가와 삭제가 상쇄되는 리팩터링도 걸리지 않으며, 그래서 결과가 도입과 제거로 깔끔하게 좁혀진다.
이 성질이야말로 곡괭이가 유용한 이유인데, 문서는 그것을 `-G`와 대비해 설명하지 않는다.

`-G`에 대한 서술은 더 얇다. 더 구체적으로 하고 싶으면 정규식을 줄 수 있다는 한 문장이 전부다.
실제로 `-G`는 “더 구체적”인 것이 아니라 “더 넓은” 옵션이다. 정규식을 받는다는 점에서 표현력은 높지만, 매칭 조건 자체가 느슨해서 결과는 훨씬 많아진다.
“구체적”이라는 단어가 독자를 잘못된 방향으로 이끈다.

### 실패 모드를 다루지 않아 도구를 과신하게 만든다

이 절의 예제는 전부 성공한다. `gmtime_r`은 잘 찾아지고, `ZLIB_BUF_MAX`는 두 커밋으로 깔끔히 좁혀지며, `git_deflate_bound`의 이력은 함수가 생긴 시점까지 이어진다.

실제 저장소에서는 그렇지 않은 경우가 훨씬 많다.
`-L`이 함수 경계를 잘못 잡거나, 파일 분할 지점에서 이력이 끊기거나, `-S`가 흔한 단어 때문에 수백 개를 뱉거나, 얕은 복제라 아무것도 안 나오는 상황이 일상이다.

문서가 이런 경우를 언급조차 하지 않으면, 독자는 빈 결과나 짧은 이력을 도구의 한계가 아니라 사실로 받아들인다.
“이 함수는 2019년에 만들어졌다”는 결론이 실은 “이 파일에 이 이름으로 2019년에 나타났다”일 뿐인데도 그렇다.

Pro Git이 참조서가 아니라 입문서라는 점을 감안해도, 한 문단이면 될 경고가 빠져 있다.
특히 `-L`의 함수 경계 추정은 `.gitattributes`의 언어 설정에 의존하는데, 그 연결이 이 절 어디에도 없다.

## 기억할 원칙

### 이력을 검색 가능한 데이터로 보는 순간 커밋 단위가 달라진다

`git log -S`가 성립하려면 한 가지 전제가 필요하다. 하나의 변경이 하나의 커밋에 담겨 있어야 한다는 것이다.
상수를 도입한 커밋에 리포맷과 무관한 버그 수정이 섞여 있으면, 곡괭이가 그 커밋을 찾아 줘도 `git show`가 보여 주는 diff에서 관련 부분을 다시 골라내야 한다.

이 관계는 양방향이다.
커밋을 잘게 나누면 검색 도구가 잘 작동하고, 검색 도구를 자주 쓰면 커밋을 잘게 나눌 이유를 몸으로 알게 된다.
“나중에 곡괭이로 찾을 때 이 커밋이 답이 되는가”가 커밋 분할의 실용적 기준이 된다.

같은 논리가 커밋 메시지에도 적용된다.
`-S`로 커밋을 찾은 뒤 읽게 되는 것은 diff가 아니라 메시지이고, 거기에 왜 그렇게 했는지가 없으면 검색이 성공해도 알아낸 것이 없다.
검색 도구의 가치는 저장소가 검색할 만한 형태로 쓰였을 때만 실현된다는 뜻이다.

### 버전 관리 시스템은 백업이 아니라 질의 가능한 데이터베이스다

Git을 되돌리기 위한 안전망으로만 쓰는 사람과 질의 대상으로 쓰는 사람의 차이가 이 절에 압축되어 있다.
전자에게 이력은 필요할 때 꺼내는 보관소이고, 후자에게는 “이 결정이 언제 왜 내려졌는가”에 답하는 자료다.

후자의 관점이 실제로 바꾸는 것은 코드를 읽는 방식이다.
낯선 코드를 만났을 때 그 코드를 노려보는 대신 `git log -L`로 그것이 어떻게 지금 모양이 되었는지를 보면, 대개 각 줄이 어떤 문제에 대응해 추가되었는지가 드러난다.
주석이 없는 방어 코드의 이유가 이력에는 남아 있는 경우가 많다.

그리고 이 관점은 Git 바깥으로도 옮겨진다.
로그, 티켓 시스템, 설정 변경 기록이 전부 같은 성질을 갖는다. 보관만 하면 비용이고, 질의할 수 있으면 자산이다.
차이를 만드는 것은 저장 여부가 아니라 검색 가능한 형태로 저장했는가이며, Git이 `-S`와 `-L`을 제공할 수 있는 이유도 처음부터 이력을 스냅숏의 연속이라는 질의 가능한 구조로 설계했기 때문이다.
