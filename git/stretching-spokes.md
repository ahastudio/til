# GitHub이 지리적으로 떨어진 복제본까지 Git을 늘린 방법

원문: [Stretching Spokes](https://github.blog/engineering/infrastructure/stretching-spokes/)

HN 토론: <https://news.ycombinator.com/item?id=15468275> (92점, 1개 댓글)

## 요약

GitHub는 사용자 저장소를 여러 복제본으로 저장하고 동기화하는 시스템을
Spokes라고 부른다. Spokes는 거의 모든 경우 모든 복제본에, 최소한 언제나
과반수(quorum) 복제본에 업데이트가 안전하게 반영되도록 여러 전략을 쓰며,
복제를 파일시스템 블록 단위가 아니라 Git 애플리케이션 계층에서 수행한다는
점이 이전 시스템과 다르다. 이전에는 DRBD라는 파일시스템 블록 단위 복제를
썼는데 지연시간에 매우 민감해서 복제본들이 서로 가까이 있어야만 했고,
그 한계에서 벗어나려는 동기가 Spokes 개발의 출발점이었다.

복제본을 지리적으로 멀리 두는 데는 잘 알려진 이점이 있다. 넓은 지역에
걸친 재해가 발생해도 일부 복제본이 살아남을 확률이 높아지고, 여러 지역에
복제본이 있으면 Git 읽기 요청을 가장 가까운 복제본으로 보내 전송 시간을
줄일 수 있다는 것이다. 문제는 초기 버전의 Spokes가 프록시와 모든
복제본 사이의 저지연 통신을 요구해서 높은 업데이트 속도를 유지하려면
복제본들이 서로 가까이 있어야 했다는 점이다.

GitHub는 거의 7천만 개의 저장소를 호스팅하며, 사용자 하나가 풀 리퀘스트
브랜치에 푸시할 때마다 GitHub는 그 푸시 자체를 기록하고, 대상 저장소로
브랜치를 동기화해야 할 수도 있고, 테스트 병합과 테스트 리베이스를 계산해
각각의 참조(reference)를 만든다. master 브랜치에 푸시가 일어나면 master를
대상으로 하는 모든 활성 풀 리퀘스트에 대해 테스트 병합과 리베이스를
다시 계산하는데, 어떤 저장소에서는 이것이 백 개가 넘는 참조 업데이트를
유발할 수 있다. Spokes가 먼 거리의 복제본으로도 동작하려면 참조 업데이트가
높은 지연시간에서도 충분히 빨라야 하는데, 목표는 저장소 하나에서 초당
최소 몇 건의 업데이트를 지원하는 것, 즉 업데이트 한 건당 몇백 밀리초의
예산이다. 읽기는 쓰기보다 약 100배 많으므로 쓰기 최적화가 읽기를
느리게 만들어서는 안 된다는 제약도 따른다.

본문은 이 예산 안에서 어떻게 최적화했는지를 다섯 갈래로 설명한다.
대륙을 횡단하는 네트워크 왕복은 60~80밀리초가 걸리는데, GitHub는
3단계 커밋(three-phase commit) 프로토콜로 복제본을 갱신하고 복제본을
분산 락으로도 사용해 데이터베이스가 올바른 순서로 갱신되도록 하며, 이
전체 과정에 먼 복제본으로의 왕복 네 번이 든다. 이를 줄이기 위해
더 발전된 합의 알고리즘을 계획하고 있다고 밝힌다. 네트워크 대기 시간을
낭비하지 않도록, 한 복제본이 락을 얻는 동안 다른 복제본은 체크섬을
계산하고 코디네이터는 데이터베이스를 읽는 식으로 작업을 겹쳐 수행한다.
3단계 커밋을 구현하려면 각 복제본이 “이 참조 업데이트를 수행할 수
있는가”라는 질문에 답할 수 있어야 하는데, GitHub는 이를 위해 오픈소스
Git 프로젝트에 참조 업데이트 트랜잭션(`git update-ref --stdin`으로
노출됨)을 구현했고, 복제본 간에 트랜잭션 결과가 결정적이도록 상당한
작업을 들였다. Git은 우선 필요한 모든 로컬 참조 락을 획득한 뒤 기존
값이 예상과 같은지, 새 값이 타당한지 확인하고, 문제가 없으면 잠정
트랜잭션을 커밋하고 그렇지 않으면 전체를 롤백한다.

복제본의 상태를 요약하기 위해 GitHub는 모든 참조와 그 값의 목록에 대한
체크섬을 계산하는데 이를 “Spokes 체크섬”이라 부른다. 참조가 많은 바쁜
저장소에서는 체크섬을 처음부터 다시 계산하는 비용이 크므로, GitHub는
가능한 한 증분 방식으로 계산한다. 체크섬은 각 `(refname, value)` 쌍의
해시에 대한 배타적 논리합(XOR)으로 정의되며, 참조 하나가 갱신되면
`new_checksum = old_checksum XOR hash(refname, oldvalue) XOR
hash(refname, newvalue)`로 갱신할 수 있어 이전 체크섬만 알면 새 체크섬을
싸게 계산할 수 있다. 이런 최적화를 다 적용해도 참조 업데이트 한 건에는
여전히 약 3분의 1초가 걸리는데, master에 대한 업데이트가 백 개가
넘는 부기(bookkeeping) 참조 업데이트를 연쇄적으로 유발하면 저장소가
30초 가까이 바빠질 수 있어 사용자가 시작한 업데이트가 크게 지연되거나
타임아웃될 위험이 있다. GitHub는 일부 부기 업데이트를 더 적은 수의
트랜잭션으로 합치고, 시간에 덜 민감한 부기 업데이트보다 사용자가
시작한 업데이트에 우선순위를 주는 방식으로 이 문제를 해결했다.

결과적으로 Spokes는 GitHub.com에서 Git 읽기(페치와 클론)를 가장 가까운
최신 복제본으로 보내 전송 속도를 높이는 데 이미 쓰이고 있고, 시간이
지나며 더 많은 지역에 복제본이 추가되면 계속 개선될 것이라 밝힌다.
온프레미스 버전인 GitHub Enterprise도 같은 Spokes 기술을 이용한 지리
복제(Geo-replication)를 지원하게 됐으며, 이 복제본들은 투표권이 없는
(non-voting) 상태로 구성돼 있어 지리 복제된 호스트가 일시적으로
접속 불가능해져도 메인 GHE 호스트로의 Git 푸시는 계속 동작한다.

## 분석

### 이 글은 최적화 목록이 아니라 예산 제약 하나를 여러 층위에서 지키는 이야기다

본문은 다섯 개의 소절로 나뉘어 있지만 실제로는 하나의 제약 조건—
업데이트 한 건당 몇백 밀리초, 읽기는 절대 느려지지 않아야 함—이
네트워크 계층(왕복 횟수), 프로토콜 계층(트랜잭션 결정성), 상태 비교
계층(체크섬), 스케줄링 계층(우선순위)에서 각각 다른 형태로 나타난
것이다. 왕복 줄이기가 실패하면 체크섬 최적화로는 메울 수 없고,
체크섬이 느리면 우선순위 조정으로는 부족하다. 즉 이 시스템의 설계는
독립된 최적화들의 나열이 아니라, 하나의 지연시간 예산을 시스템의
모든 층위가 함께 지키도록 강제한 결과다.

### 부기 트래픽이라는 숨은 부하가 설계를 결정한다

master 브랜치 하나에 대한 푸시가 백 개 넘는 참조 업데이트를 유발할 수
있다는 사실이 이 글의 설계 전체를 사실상 좌우한다. 사용자가 인지하는
Git 작업은 “브랜치에 푸시했다”는 단순한 행위이지만, GitHub 내부에서는
그 하나의 행위가 모든 활성 풀 리퀘스트에 대한 재계산을 촉발하는
팬아웃(fan-out) 이벤트가 된다. 이 팬아웃이 사용자에게 보이지 않는
부기 작업이라는 점이 중요한데, 만약 GitHub가 이 부기 트래픽을
사용자 트래픽과 동일하게 취급했다면 우선순위 조정이나 트랜잭션 병합
같은 후속 최적화는 필요조차 없었을 것이다. 오히려 이 숨은 부하의
존재를 인식한 것 자체가 설계의 절반이다.

### 체크섬의 증분 계산은 분산 시스템의 일반 원칙을 구체화한다

XOR 기반 증분 체크섬은 “전체를 다시 계산하지 말고 변경분만 반영하라”는
분산 시스템의 오래된 원칙을 정확히 구현한 사례다. XOR을 고른 이유는
명시되지 않았지만, XOR이 결합적이고 자기 역원(self-inverse)이라는
성질—같은 값을 두 번 XOR하면 취소된다는 성질—덕분에 이전 값을 제거하고
새 값을 더하는 연산이 하나의 식으로 표현된다. 이는 체크섬이라는
좁은 문제를 풀기 위해 대수적 구조를 의도적으로 골랐다는 뜻이며,
바쁜 저장소에서 참조가 수천 개에 달해도 갱신 비용이 참조 하나의
해시 계산 두 번으로 고정된다는 실질적 이점을 낳는다.

## 비평

### 3단계 커밋의 왕복 네 번이라는 비용을 자세히 다루지 않는다

글은 3단계 커밋에 왕복 네 번이 든다고 명시하고 이를 “비싸지만 감당할
만하다”고만 서술할 뿐, 그 네 번의 왕복이 각각 무엇을 위한 것인지,
어느 지점에서 병렬화가 가능하고 어디서 불가능한지를 구체적으로
설명하지 않는다. 대륙 횡단 왕복이 60~80밀리초라면 네 번은 이미
240~320밀리초로, 글이 제시한 “몇백 밀리초” 예산 전체에 육박한다.
이 수치가 아슬아슬하게 예산에 맞아떨어진다는 사실 자체가 설계의
핵심 긴장인데, 글은 이를 “겹쳐서 처리한다”는 한 문장으로 넘기고
정확히 얼마나 겹쳐지는지, 실제 관측된 지연시간 분포가 어떤지는
제시하지 않는다.

### 더 발전된 합의 알고리즘 전환의 이유와 장애물을 설명하지 않는다

글은 왕복 횟수를 줄이기 위해 더 발전된 합의 알고리즘을 도입할 계획이
있다고만 언급하고, 왜 처음부터 그 알고리즘을 쓰지 않았는지, 3단계
커밋에서 무엇을 바꾸면 왕복이 줄어드는지, 전환에 어떤 장애물이 있는지는
다루지 않는다. Raft나 Paxos 계열 합의 알고리즘은 이미 널리 알려져
있고 GitHub 정도 규모의 회사가 그 존재를 몰랐을 리 없으므로, 3단계
커밋을 먼저 택한 이유—아마도 기존 Git 참조 업데이트 방식과의 호환성,
혹은 구현 복잡도—가 이 글에서 가장 궁금한 지점인데도 설명되지 않는다.

### 비투표 복제본의 장애 처리 세부사항이 없다

GitHub Enterprise의 지리 복제본이 “투표권이 없다”는 설계는 가용성과
일관성 사이의 트레이드오프를 함축하지만, 글은 이 복제본이 얼마나
뒤처질 수 있는지, 뒤처진 상태에서 읽기 요청이 그 복제본으로 라우팅되면
사용자가 오래된 데이터를 보게 되는지, 그리고 그 복제본이 다시 연결됐을
때 어떻게 따라잡는지를 설명하지 않는다. 비투표라는 결정이 쓰기 가용성을
지키기 위한 것이라는 점은 명확하지만, 그 대가로 읽기 일관성이 얼마나
희생되는지는 이 글만으로는 판단할 수 없다.

## 인사이트

### 부기 트래픽과 사용자 트래픽을 분리하는 패턴은 Git 밖에서도 반복된다

master에 대한 하나의 푸시가 백 개 넘는 파생 업데이트를 유발하고,
GitHub가 이를 우선순위로 분리해 처리한 방식은 이벤트 기반 시스템
전반에서 반복되는 패턴이다. 데이터베이스의 트리거가 만드는 연쇄
업데이트, 메시지 큐에서 하나의 이벤트가 여러 구독자에게 팬아웃되며
생기는 재시도 폭주, 캐시 무효화가 연쇄적으로 하위 캐시를 무효화하는
현상 모두 “사용자가 인지하는 행위 하나가 시스템 내부에서 훨씬 큰
작업량으로 증폭된다”는 같은 구조를 갖는다. 이 증폭을 사용자 경험과
분리해서 우선순위를 매기는 것이 해법이라는 점에서, Spokes의 설계는
Git 저장소 호스팅이라는 특수한 문제를 넘어 팬아웃이 있는 모든 시스템에
적용되는 일반 원칙을 보여 준다.

### 지연시간 예산은 물리 법칙에 의해 상한이 정해진 자원이다

이 글이 은연중에 드러내는 것은, 소프트웨어 최적화로는 절대 넘을 수
없는 물리적 하한선—빛의 속도로 정해지는 대륙 횡단 왕복 60~80밀리초—이
설계의 모든 선택을 제약한다는 사실이다. 왕복 횟수를 줄이고, 트랜잭션을
겹쳐 처리하고, 체크섬을 증분 계산하는 모든 최적화는 결국 “물리적으로
줄일 수 없는 왕복 시간 안에서 얼마나 많은 유용한 작업을 밀어 넣을
것인가”라는 하나의 질문에 대한 답이다. 이는 지리적으로 분산된 시스템을
설계하는 모든 엔지니어가 결국 마주치는 제약이며, CDN이 엣지 서버를
늘리는 이유나 데이터베이스가 리전별로 읽기 복제본을 두는 이유도 같은
물리적 한계에서 나온다.

### 결정론적 트랜잭션 결과가 감사 가능성이라는 부수 효과를 낳는다

복제본 간에 트랜잭션 결과가 결정적이도록 만들었다는 서술은 성능
최적화처럼 보이지만, 실제로는 그보다 더 중요한 부수 효과를 갖는다.
모든 복제본이 같은 입력에 대해 같은 결과를 내도록 보장하면, 두
복제본의 상태가 다를 때 그 차이가 “정당한 비동기 지연” 때문인지
“버그로 인한 진짜 불일치” 때문인지를 명확히 구분할 수 있게 된다.
이는 이 글의 체크섬 비교 메커니즘이 신뢰할 수 있는 근거가 되는
전제조건이기도 하다. 결정성이 없다면 체크섬이 달라도 그것이 오류인지
정상적인 지연인지 판단할 수 없고, 장애 복구나 감사 과정에서 근본
원인을 추적하는 일이 훨씬 어려워졌을 것이다.

### Git 저장소를 데이터베이스로 부르는 순간 요구되는 보증이 달라진다

발표 당시 이 시스템에 붙은 짧은 논평 하나가 이 글의 성격을 정확히
요약했다. 특화된 분산 비공개 데이터베이스를 만든 셈인데 그것이
Git을 말한다는 점이 흥미롭다는 것이었다[^reconbot].

한 줄짜리 반응이지만 분류를 바꿔놓는다는 점에서 값이 있다. Git
저장소를 파일 묶음으로 보면 이 글의 3단계 커밋과 체크섬 검증과
결정론적 트랜잭션은 과하게 정교한 장치로 보인다. 반면 저장소를
데이터베이스로 보면 같은 장치들이 최소 요건이 된다. 어떤 시스템이든
쓰기를 받고 복제하고 읽기를 서빙한다면 내구성과 일관성 보증을
명시해야 하고, 그 보증이 없는 저장소는 데이터베이스로 쓰일 수 없다.

이 재분류가 실무에서 갖는 함의는 기대치의 이동이다. Git을 파일
동기화로 이해하는 팀은 푸시가 성공했다는 것을 최종 상태로 받아들이고,
데이터베이스로 이해하는 팀은 어느 복제본까지 반영됐는지를 묻는다.
이 글이 다루는 문제는 전부 후자의 질문에서만 나오며,
GitHub이 지리적 확장을 위해 지불한 복잡도는 사실상 Git에 데이터베이스
수준의 보증을 소급 적용하는 비용이었다. 저장소를 데이터베이스처럼
쓰는 조직이 늘어날수록 같은 비용이 각자에게 청구된다.
