# kordoc: 한컴오피스 없이 HWP·HWPX·PDF를 Markdown으로 바꾸는 파서

<https://github.com/chrisryugj/kordoc>

Show GN: [kordoc - 한컴오피스 없이 HWP·HWPX·PDF를 마크다운으로 바꾸는 파서](https://news.hada.io/topic?id=35956)

## 소개

kordoc은 HWP 3.x·5.x, HWPX, HWPML, PDF, XLS·XLSX, DOCX, PPTX와 PNG·JPG·WebP
이미지를 Markdown과 구조화 데이터로 바꾸는 도구다.
라이브러리, CLI, MCP 서버 세 가지 방식으로 쓴다.
README는 광진구청에서 7년간 HWP 파일과 씨름한 지방공무원이 만들었고,
5개 공공 프로젝트에서 실제 관공서 문서 수천 건으로 검증했다고 소개한다.

GeekNews에 올린 글에서 만든 사람은 업무 문서가 거의 HWP라서 AI에 넣으려면 복사해
붙이거나 PDF로 바꿔야 했고, 표가 있으면 병합 칸이 모두 깨졌다고 설명한다.
그래서 HWP 파일 구조를 직접 읽는 파서를 만들었다고 한다.

문서는 한컴오피스 없이 파일을 직접 읽으며, 인터넷이 막힌 폐쇄망에서도 쓸 수
있다.
`KORDOC_OFFLINE=1`을 주면 외부 통신을 모두 막고, OCR도 API 키 없이 로컬 CPU에서
돈다.
라이선스는 MIT이고, Node.js 20 이상에서 macOS, Linux, Windows를 지원한다.
수집 시점의 최신 배포는 2026년 10월 25일의 4.24.5다.

## 사용법

### 설치와 CLI

```bash
npm install kordoc
```

CLI는 설치 없이 `npx kordoc`으로도 실행한다.
README의 예시는 다음과 같다.

```bash
npx kordoc 문서.hwpx -o 문서.md
npx kordoc *.pdf --jobs 4 -d ./결과
npx kordoc 문서.pdf --format json --pages 1-3
npx kordoc 스캔본.pdf --ocr -o 스캔본.md
npx kordoc generate 보고서.md --preset 보고서 -o 보고서.hwpx
npx kordoc fill --template gian -j 값.json -o 기안문.hwpx
npx kordoc lint 보고서.hwpx --gate --preset 보고서
```

`--jobs`는 파일 단위 병렬 변환이어서 메모리 사용도 함께 늘어난다.
RAG 색인에는 `--format chunks`를 쓰면 제목 경로를 붙인 구조 청크와 독립 표
청크가
나오고, 표를 HTML 없이 받으려면 `--table-format gfm`을 쓴다.

### 라이브러리

```typescript
import { parse, markdownToHwpx } from "kordoc"
import { writeFile } from "node:fs/promises"

const result = await parse("문서.hwpx")
if (result.success) {
  console.log(result.markdown)
  // result.blocks: 구조화 데이터, result.metadata: 문서 정보
}

const hwpx = await markdownToHwpx("# 추진계획\n\n본문", {
  gongmun: { preset: "보고서" },
})
await writeFile("보고서.hwpx", Buffer.from(hwpx))
```

Python과 Java에서는 상주 엔진 워커를 부르는 SDK가 따로 있다.

### AI 에이전트에 연결

```bash
npx -y kordoc setup
```

설치된 Claude Desktop, Claude Code, Cursor, Codex 같은 클라이언트에 MCP를
등록한다.
클라이언트를 다시 시작하면 파싱, 비교, 생성, 검수, 렌더 등 18개 도구를 쓸 수
있다.
공식 MCP 레지스트리에는 `io.github.chrisryugj/kordoc`으로 올라 있고,
Claude Code 플러그인으로도 설치할 수 있다.
MCP가 파일에 접근하는 범위는 `KORDOC_ROOT`로 정한다.

| --------- | ------------------------------------------------------------------------------------ |

| 보기·보안 | HWPX·HWP 미리보기와 영역 추출, 개인정보 마스킹                                       |

## 검증 결과

README는 버전 4.22.14를 2026년 10월 19일에 검증한 결과를 고정 코퍼스와 참조
기준으로
잰 수치로 싣는다.
렌더 배치는 4.24.4, PDF 글·표·OCR은 4.24.5 기준이다.

| 대상                 | 규모                   | 결과                                   |
| -------------------- | ---------------------- | -------------------------------------- |
| HWPX                 | 2,424문서, 표 10,342개 | 표 구조 일치 10,342/10,342, 100%       |
| HWP 5.x ↔ HWPX       | 1,130쌍, 표 4,315개    | 짝 문서의 표 구조 일치 100%            |
| PDF 글               | 744쌍                  | 글자 재현율 99.880%, 읽기 순서 99.302% |
| PDF 표               | 708쌍, 표 2,331개      | 표 탐지 99.83%, 구조 일치 98.20%       |
| OCR                  | 53문서, 102쪽, 표 67개 | 글자 오류율 0.0409, 표 구조 일치 24/67 |
| opendataloader-bench | PDF 200문서            | 종합 0.964(OCR 끔 0.939)               |

README는 표 구조 점수와 셀 내용, 화면 재현을 별도 지표로 구분하고,
중첩표 100%는 101개 표에 한정한 수치이며 전체 PDF와 조판의 완전 일치를 뜻하지
않는다고
적는다.
PDF 공개 벤치 종합 0.964는 공개 리더보드의 파서 12개보다 높은 점수라고 한다.

## 비평

### 모든 수치가 만든 사람의 코퍼스와 기준으로 잰 것이다

표 구조 100%는 원본 HWPX 2,424문서의 보이는 표를 기준으로 한 값이다.
이 코퍼스는 만든 사람이 일한 공공 프로젝트에서 모은 것이어서,
다른 기관이나 다른 시기의 문서에서도 같은 결과가 나오는지는 이 README만으로 알
수 없다.
참조 기준을 어떻게 만들었는지, 사람이 직접 확인했는지도 본문에는 나오지 않고
벤치마크 상세 문서로 넘어간다.
외부 사람이 같은 수치를 재현하려면 그 문서를 따로 읽어야 한다.

### 가장 약한 수치가 가장 덜 눈에 띄는 곳에 있다

표에서 눈에 띄는 숫자는 100%와 99%대다.
OCR 표 구조 일치는 67개 중 24개, 약 36%이고, 이 수치는 표의 한 줄에 있다.
스캔한 공문서는 현실에서 흔하므로, 이 비율이 실제 사용에서의 체감 품질을 크게
좌우할 수 있다.
4.24.5의 변경 이력이 이 수치를 21에서 24로 올렸다고 적는 점은,
이 부분이 진행 중인 영역이라는 뜻이다.

### 범위가 넓어질수록 읽기 도구의 신뢰 경계가 흐려진다

읽기에서 출발한 도구가 비교, 편집, 작성, 양식 채우기, 도장 날인, 검수까지 한다.
범위가 넓은 것은 장점이지만, 파일을 쓰는 기능은 읽는 기능과 위험이 다르다.
예산 산출근거 검산과 AI 문체 게이트 같은 검수 기능이 무엇을 기준으로 통과와
실패를
가르는지는 README에서 알 수 없다.
도구가 만든 서식 보존 패치에서 적용하지 못한 편집은 건너뛴 사유로 보고한다고
하지만,
공문서를 다루는 사용자가 그 보고를 읽고 판단한다는 전제가 필요하다.

## 인사이트

### HWP 장벽을 낮추는 일은 개발자가 아니라 사용자 쪽 문제를 푼다

README의 출발점은 파서의 정확도가 아니라 업무 문서가 거의 HWP라는 사실이다.
LLM에 넣으려면 사람이 복사해 붙이거나 PDF로 바꿔야 했다는 설명은,
형식 변환이 개발자의 일이 아니라 일하는 공무원의 일이었다는 뜻이다.
같은 사람이 도구를 만든 점이 이 도구의 방향, 곧 표의 병합 칸을 정확히 읽고
서식을 보존하는 쪽으로 힘을 쓰는 점을 설명한다.

이 구조는 특정 형식이 사실상 표준인 환경에서 반복된다.
해당 형식을 쓰는 사람이 직접 변환 도구를 만들고, 그 도구가 새로운 도구
생태계, 여기서는 MCP와 에이전트의 입구가 된다.
문서를 읽는 일이 해결되면 그다음 문제는 쓰는 일, 곧 서식에 맞게 작성하고
검수하는 일로 옮겨 간다는 점이 도구의 기능 순서에서 읽힌다.

### 문서를 읽는 일이 쉬워지면 개인정보를 다루는 지점이 늘어난다

공문서에는 개인정보가 많다.
이 도구는 개인정보 마스킹 기능과 폐쇄망 설치, 외부 통신 차단, 접근 범위 제한을
갖추고 있다.
그런데 MCP로 에이전트에 연결하는 순간 에이전트가 어떤 경로의 파일을 읽을 수
있는지가
설정에 달려 있다.
`KORDOC_ROOT`로 범위를 정하는 구조는 이 위험을 알고 있다는 신호지만,
기본값이 어디까지 열려 있는지는 README의 이 부분만으로 알 수 없다.

도구를 도입하는 쪽은 변환 품질 못지않게, 에이전트가 읽을 수 있는 폴더의 범위와
변환된 텍스트가 어디로 전송되는지를 먼저 확인해야 한다.
이 판단은 README의 서술에서 이끌어 낸 것이고, 실제 기본 설정은 확인하지 못했다.

### 이 글을 읽는 방법

이 README는 도구의 약속을 적은 문서다.
수치는 모두 만든 사람의 측정이고, 표현이 확신에 차 있는 만큼 범위 한정 문구도
함께 읽어야 한다.

내 문서에서도 쓸 만한지는 두 관찰로 가릴 수 있다.
첫째, 내가 실제로 다루는 문서 20개쯤을 골라 병합 칸이 있는 표를 변환하고,
원본과 나란히 놓고 셀 내용이 맞는지 눈으로 확인하는 것이다.
구조가 맞아도 내용이 틀린 셀이 있다면 README가 구분해 둔 두 지표의 차이가
내 문서에서 크다는 뜻이다.
둘째, 스캔한 문서가 많다면 OCR 결과의 표만 따로 골라 구조 일치 비율을 세는
것이다.
그 비율이 README의 24/67에 가깝다면, 스캔 문서에는 사람의 확인 절차가 필요하다.
