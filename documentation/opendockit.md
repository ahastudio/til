## 소개

OpenDocKit은 PDF, DOCX, PPTX, XLSX, HWP/HWPX, ODF, RTF, EPUB, HTML, 이메일,
이미지를 함수 하나로 읽어 Markdown으로 바꾸는 파이썬 라이브러리이다.
GeekNews에 글을 올린 hyeonsang010716이 저장소 소유자이다.
RAG나 에이전트에 문서를 넣다 보면 텍스트는 뽑히는데 구조가 깨진다는 문제에서
출발했다고 설명한다.
병합 셀이 풀리면서 값이 엉뚱한 행에 붙고, 2단 PDF에서 좌우 문단이 섞이고, HWP는
아예 열리지 않는 경우를 든다.

GitHub API로 읽은 저장소 정보는 다음과 같다(2026년 11월 20일 기준).

| 항목              | 값                                     |

| 라이선스          | MIT                                    |
| 언어              | Python                                 |
| 별과 포크         | 별 34개, 포크 2개                      |
| 열린 이슈         | 3개                                    |
| 저장소 생성       | 2026년 11월 11일                       |

저장소의 홈페이지 필드는 PyPI 프로젝트 주소이다.
이 페이지는 스크립트로 읽으면 내용이 거의 비어 있어서 PyPI의 JSON 메타데이터를
읽었고, 설명 문단은 저장소 README와 같은 내용이었다.

## 기능

README가 내세우는 특징은 다음과 같다.

- 구조 보존: 병합 셀, 다단 PDF, 테두리 없는 표, 중첩 목록, 각주, 발표자 노트를
옮긴다. 차트는 데이터 표로, SmartArt는 중첩 목록으로, Word, PowerPoint, 한글
수식은 LaTeX로 바꾼다.
- 한국 문서: HWP 5.x 파서를 처음부터 만들었고 HWPX, CP949 감지, NFC 정규화, 서식
위주의 표를 다룬다고 한다.
- 내용 기반 형식 판별: `.xls`로 저장된 HTML 표나 `.doc`라는 이름의 MHTML을 실제
형식대로 읽고 경고를 남긴다.
- 업로드 안전성: 압축 폭탄, 비정상적으로 많은 병합 셀, 재귀적 PDF 객체, 수
GB짜리 이미지에 상한이 있다. `IsolatedConverter`는 파일마다 메모리와 시간 제한이
걸린 일회용 작업 프로세스에서 변환한다.
- 이미지: 그림, 차트, 스캔 페이지를 추출해 걸러 내고, 비전 모델을 연결하면 원래
자리에 설명을 넣는다.
- 문자 예산: `max_chars`는 결과를 나중에 자르지 않고 그 지점에서 파싱을 멈춘다.
- 허용적 라이선스: 기본 설치의 의존성은 MIT, BSD, Apache 계열이고 PyMuPDF와
pyhwp를 쓰지 않는다. 복제 허용 조건이 강한(copyleft) 코드는 선택 설치인 `heic`
추가 기능 뒤에만 있다.

결과 객체는 Markdown 본문 `text`, 쪽, 슬라이드, 시트 단위의 `sections`,
건너뛰거나 근사한 내용을 평문으로 적은 `warnings`를 가진다.
`sections`는 청킹과 3쪽 같은 출처 표기에 쓰도록 만들었다.

지원 형식은 README의 표에 형식별로 정리되어 있다.
레거시 `.doc`와 `.ppt`는 LibreOffice가 설치되어 있으면 변환해서 읽고, 나머지는
라이브러리가 직접 읽는다.

## 사용법

설치는 `pip install opendockit`이며 변환만 하고 네트워크를 쓰지 않는다.
선택 추가 기능으로 비전 모델(`openai`), LangChain, LlamaIndex, MCP 서버, Open
WebUI, HEIC 이미지가 있다.

```python
from opendockit import convert_file

result = convert_file("quarterly-report.hwp")
print(result.text)
print(result.warnings)
```

서버에서는 `IsolatedConverter(workers=2)`로 파일마다 제한된 작업 프로세스에서
변환하며 기본 한도는 파일당 2GB와 2분이다.
명령줄은 `opendockit report.pdf`로 Markdown을 출력하고 `--json`, `--count`,
`--describe` 옵션이 있다.
`opendockit-mcp --root ~/Documents`는 Claude, Cursor 같은 에이전트가 문서를
Markdown으로 읽게 하는 MCP 서버이다.

통합 대상으로 LangChain 로더, LlamaIndex 리더, MCP 서버, Hermes Agent 플러그인
카탈로그, Claude Code 플러그인, Dify Marketplace, Open WebUI의 외부 추출 엔진을
든다.
GeekNews 글은 Dify와 Open WebUI가 HWP를 직접 읽지 못해서 그 빈자리를 채우는
용도로도 쓸 만하다고 쓴다.

## 분석

### 설계의 초점은 실제로 올라오는 파일이다

README의 첫 문장은 대부분의 변환기가 정상 경로만 처리한다는 점이고, OpenDocKit은
사람들이 실제로 올리는 파일을 위해 만들었다고 한다.
확장자가 틀린 파일, 병합 셀, 스캔본, 한국 사무 문서가 그 예이다.
기능 목록이 형식의 폭보다 실패하는 지점에 맞춰 짜여 있다는 것이 이 프로젝트의
특징이다.
이는 README를 이 문서가 정리한 것이다.

### 서버에 붙이는 것을 전제로 한 안전 장치가 들어 있다

작업 프로세스 격리, 입력 크기 상한, 문자 예산이 모두 서버에서 신뢰할 수 없는
업로드를 받을 때의 문제에 대응한다.
`max_chars`가 파싱을 도중에 멈춘다는 설계는 어차피 거절될 파일에 파싱 시간과
비전 모델 호출을 쓰지 않게 한다.
라이브러리 안에서 이 비용을 줄이는 것은 변환기를 서비스에 끼울 때 운영자가 따로
만들던 부분이다.

### 한국어 문서를 일급으로 다룬다

HWP 5.x 파서를 직접 만들었다는 점이 비교 대상과 갈리는 부분이다.
README의 비교 요약에서 이 라이브러리는 HWP와 HWPX를 읽는 유일한 도구로 나온다.
저장소 문서에는 PyMuPDF와 pyhwp를 쓰지 않아 라이선스 부담이 없다는 점도 같이
있어서, 한국 사무 환경에서 쓸 수 있는 조건을 의도적으로 맞춘 것으로 읽힌다.
이는 이 문서의 해석이다.

## 비평

### 비교 결과의 검사 항목을 만든 쪽이 비교의 주체이다

README는 구조 검사 49개를 모두 통과했고 다음은 Docling이 36개, MarkItDown 31개,
Kreuzberg 29개, Unstructured 12개라고 쓴다.
같은 글이 검사가 만든 쪽의 것이고 0.2.0이 그 검사를 알고 쓰였다고 스스로 밝힌다.
GeekNews 글도 검사 항목을 직접 만들었다는 점을 감안해 달라고 쓴다.
그래서 49 대 36은 이 프로젝트가 자신이 정한 기준에 맞는다는 뜻이며 다른 도구보다
일반적으로 낫다는 증거는 아니다.

### 약점이 분명히 적혀 있지만 크기는 다르게 읽힌다

README는 OCR이 없어서 스캔 문서와 이미지는 비전 모델로만 읽고, Kreuzberg가 약
30배 빠르며, 레거시 `.doc`와 `.ppt`는 LibreOffice를 거쳐 파일당 약 1초가 든다고
쓴다.
정직한 서술이지만 비전 모델을 쓰면 외부 호출 비용과 개인정보 문제가 따라온다.
기본 설치가 오프라인이라는 장점은 스캔 문서에는 적용되지 않는다는 뜻이다.
스캔 문서가 많은 환경에서 이 도구가 얼마나 쓸 만한지는 README로 판단하기 어렵다.

### 저장소가 아주 젊다

저장소는 2026년 11월 11일에 만들어졌고 별은 34개, 이슈는 3개이다.
저장소가 만들어진 지 9일 시점에 PyPI 최신 버전이 0.3.14이다.
버전이 빠르게 오르는 것은 활발하다는 신호일 수 있지만, 인터페이스가 아직
안정되지 않았을 가능성도 있다.
GeekNews 글의 작성자도 이상하게 변환되는 문서를 이슈로 알려 달라고 쓴다.

## 인사이트

### 문서 변환은 형식 지원보다 실패 방식의 설계 문제이다

변환기 비교에서 흔히 쓰는 기준은 지원하는 형식의 수이다.
OpenDocKit이 내세우는 것은 병합 셀이 어느 행에 붙는지, 읽지 못한 부분을 경고로
남기는지, 이상한 파일이 서버를 죽이지 않는지이다.
RAG 입력에서는 틀린 값이 조용히 들어가는 것이 변환 실패보다 해롭기 때문에
`warnings` 같은 장치가 의미가 있다.
이는 이 문서의 해석이다.

### 비교표를 읽을 때는 누가 검사를 만들었는지 먼저 본다

이 프로젝트의 README는 비교의 한계를 스스로 적었다.
같은 방식으로 다른 변환기의 비교표도 검사 항목의 출처를 먼저 확인하는 것이
필요하다.
스스로 한계를 적는 것은 신뢰를 높이지만, 그 한계 안에서도 숫자는 기준에
의존한다는 점이 남는다.

### 한국 환경에서 HWP 지원은 도구 연결의 빈칸을 메운다

Dify와 Open WebUI가 HWP를 직접 읽지 못한다는 설명은 AI 도구 연결 단계에서 한국
문서가 빠지는 현실을 보여 준다.
그 빈칸을 개별 라이브러리가 플러그인으로 메우는 방식은 빠르지만 각 플러그인의
유지 책임이 한 사람에게 쏠릴 수 있다.

### 확인할 관찰

이 문서의 해석을 가를 관찰은 세 가지이다.
실제 업로드 문서(HWP 포함)로 본 구조 보존의 정확도,
작성자가 만들지 않은 검사 항목으로 한 비교 결과,
릴리스가 이어질 때 인터페이스가 얼마나 바뀌는지이다.
