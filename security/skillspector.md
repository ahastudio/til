# SkillSpector: 설치 전에 에이전트 스킬을 검사하는 스캐너

<https://docs.nvidia.com/skills/scanning-agent-skills>

<https://github.com/NVIDIA/SkillSpector>

HN 토론: <https://news.ycombinator.com/item?id=48509844> (49점, 4개 댓글)

## 소개

NVIDIA가 공개한 AI 에이전트 스킬 보안 스캐너다.
Python 3.12 이상을 요구하며 Apache 2.0 라이선스로 배포된다.
2026년 3월 21일에 만들어졌고 확인 시점에 별 16,930개와 포크 1,442개를 기록하고
있다.

README는 문제 인식을 한 문장으로 요약한다.
Claude Code와 Codex CLI와 Gemini CLI 등이 쓰는 에이전트 스킬이 암묵적 신뢰 아래
최소한의 검증만 거쳐 실행된다는 것이다.
그래서 이 도구가 답하려는 질문은 이 스킬을 설치해도 안전한가다.

### 근거가 된 연구

수치는 Liu 등이 2026년에 발표한 「Agent Skills in the Wild: An Empirical Study
of
Security Vulnerabilities at Scale」에서 가져왔다고 밝힌다.

주요 마켓플레이스에서 수집한 42,447개 스킬이 데이터셋이며,
26.1퍼센트가 최소 하나의 취약점을 포함하고 5.2퍼센트는 악의적 의도를 보인다.
그리고
실행 가능한 스크립트를 포함한 스킬이 취약할 확률이 2.12배 높다는 것이 핵심
발견이다.

### NVIDIA Verified Skills 파이프라인의 일부

SkillSpector는 독립 도구가 아니라
NVIDIA Verified Skills 파이프라인의 구성 요소로
소개된다.
이 파이프라인은 스킬을 스캔하고 평가하고 서명한 뒤 공개하며, 통과한 스킬은
NVIDIA 스킬 카탈로그에 올라간다.

### 두 단계 파이프라인

1단계는 정적 분석이다.
11개 정적 분석기의 정규식 패턴 대조, 위험한 호출을 잡아내는 AST 기반 행위 분석,
의존성의 알려진 CVE를 OSV.dev에서 실시간으로 조회하는 것이다.
재현율이 높고 정밀도는 보통이라 오탐이 일부 나온다고 명시한다.

2단계는 선택적 LLM 의미 분석이다.
맥락과 의도를 평가하고 오탐을 걸러 내며 사람이 읽을 설명을 제공한다.
정밀도를 약 87퍼센트까지 올린다고 적는다.
LLM 프롬프트에는 악성 스킬이 분석 자체를 조작하지 못하게 하는 탈옥 방지 장치가
들어 있다고 밝힌다.

## 점수와 판정

점수 계산은 단순 가산이다.
CRITICAL은 50점, HIGH는 25점, MEDIUM은 10점, LOW는 5점을 더하고,
실행 가능한 스크립트가 있으면 1.3배를 곱한다.

| 점수 | 심각도 | 권고 |
| ------ | -------- | --------------- |
| 0–20 | LOW | SAFE |
| 21–50 | MEDIUM | CAUTION |
| 51–80 | HIGH | DO NOT INSTALL |
| 81–100 | CRITICAL | DO NOT INSTALL |

종료 코드는 셋이다.
점수 50 이하면 0, 50 초과면 1, 오류면 2다.
SAFE와 CAUTION이 같은 0으로 접히므로 둘을 구분하려면 종료 코드가 아니라 JSON의
`recommendation` 필드를 읽으라고 안내한다.

출력은 터미널과 JSON과 Markdown과 SARIF 2.1.0을 지원한다.

## 통합과 운영

### MCP 서버

`skillspector mcp`로 MCP 서버를 띄우면 MCP를 지원하는 에이전트가 스캔을 도구로
호출하고 그 결과로 스킬 설치를 차단할 수 있다.
별도의 감사 단계가 아니라 실행 시점의 방어막이 된다는 것이 이 모드의 취지다.

노출하는 도구는 `scan_skill` 하나이며 `risk_score`와 `severity`와
`recommendation`과 `safe_to_install`과 `findings`를 돌려준다.
정적 분석만 돌린 낮은 점수를 완전한 스캔의 깨끗한 결과로 오인하지 않도록
`llm_used`와 `scan_mode`도 함께 보고한다.

HTTP 전송 방식에는 인증이 없다고 명시한다.
포트에 닿을 수 있는 누구든 `scan_skill`을 호출할 수 있으므로,
라우팅 가능한 인터페이스에 바인딩한다면 인증하는 리버스 프록시 뒤에 두라고
권고한다.
HTTP에서는 로컬 경로와 `file://` URL이 자동으로 거부되어 인증되지 않은 호출자가
호스트 파일을 읽지 못하게 막는다.

### 입력 제한

원격 및 압축 입력에 두 가지 독립적인 상한을 건다.
수집 단계에서 `INGEST_MAX_BYTES`가 100 MiB이고
`INGEST_MAX_ZIP_MEMBERS`가 10,000개다.
분석 단계의 파일당 1 MB 상한(`MAX_FILE_BYTES`)은 별개의 하위 제한이다.
어느 쪽이든 넘으면 `IngestLimitExceededError`로 닫힌다.

### 기준선 억제

이미 확인하고
받아들인 발견을 기준선 파일에 담아 두면 재스캔에서 새 발견만 보고되고
점수에도 새 발견만 반영된다.
글롭 규칙 기반과 정확한 지문 기반을 모두 지원하며,
지문 기준선은 증거에 묶여 있어 스캔 대상이나 SkillSpector 버전이 바뀌면 해당
발견이 다시 살아난다.

### LLM 공급자

`SKILLSPECTOR_PROVIDER`로 고른다.
`openai`, `anthropic`, `anthropic_proxy`, `bedrock`, `nv_build`, `claude_cli`,
`codex_cli`를 지원하며 기본값은 `nv_build`다.
Ollama나 vLLM 같은 로컬 OpenAI 호환 서버도 쓸 수 있다.

CLI 공급자를 쓰면 API 키가 필요 없고 인증은 해당 CLI의 로그인 세션이 담당한다.
이때 하위 프로세스는 도구를 끄고 MCP를 막고 읽기 전용 샌드박스로 돌리며,
신뢰할 수 없는 스킬 내용은 표준 입력으로만 전달한다고 밝힌다.

### 신뢰 모델과 데이터 유출

README는 이 도구가 샌드박스가 아니라 다층 방어의 한 겹이라고 명시하고
경계를 네 줄로 정리한다.

스캔 대상 스킬을 결코 실행하지 않는다.
모든 분석이 정적이며 LLM 평가도 파일 내용에 대한 것이다.

LLM 분석을 켜면 분석 대상 파일 내용이 설정된 공급자 엔드포인트로 전송된다.
이것이 기본값이며, 내용을 로컬에 두려면 `--no-llm`을 써야 한다.

공급망 검사 SC4는 의존성 이름과 버전을 OSV.dev로 보낸다.
이것은 검사의 본질이므로 `--no-llm`으로도 동작하며, 파일 내용이 아니라
의존성 좌표만 보낸다.

호스트를 샌드박싱하지 않는다.
설치 전에 위험한 패턴을 표시할 뿐이며,
사용자가 그래도 설치하기로 한 스킬을 격리하지는 않는다.

### 명시된 한계

비영어 콘텐츠의 패턴을 놓칠 수 있고, 이미지 속 텍스트를 분석할 수 없으며,
컴파일되거나 암호화된 내용을 다루지 못하고, 정적 분석만 하므로
런타임 동작을 보지 못한다.
`api.osv.dev`에 접근할 수 없으면 SC4는 내장된 작은 대체 목록만 쓴다.

## 분석

### 이 도구의 실제 주장은 스킬이 패키지라는 것이다

SkillSpector의 설계는 한 가지 전제 위에 서 있다.
에이전트 스킬이 소프트웨어 패키지와 같은 종류의 공급망 대상이라는 것이다.

그 전제가 도구의 모든 선택을 설명한다.
CVE 조회, 타이포스쿼팅 탐지, 미고정 의존성 경고, SARIF 출력,
종료 코드 기반 CI 게이트,
기준선 억제가 전부 기존 소프트웨어 구성 분석 도구의 어휘를 그대로 옮겨 온
것이다.

이 이식이 자연스러운 이유가 있다.
스킬은 마크다운 파일 하나가 아니라 디렉터리이고, 그 안에 파이썬 스크립트와
`requirements.txt`가 들어 있을 수 있다.
HN에서 0gs가 그 점을 지적했다.
스킬은 하위 폴더에 무엇이든 하는 파이썬 파일을 포함할 수 있으며,
많은 사람이 그것을 얼마나 맹목적으로 가져다 쓰는지를 생각하면
실제로 꽤 아찔하다는 것이다.
그리고 자신도 몇 달 전에 거의 똑같은 것을 만들었다고 덧붙인다.[^0gs]

그런데 이 전제는 절반만 맞다.
스킬의 위험은 두 층에 나뉘어 있고, 아래층은 코드이며 위층은 프롬프트다.
아래층에는 기존 도구 체계가 그대로 통하고, 위층에는 통하지 않는다.
71개 패턴 중 AST와 오염 추적과 YARA와 공급망이 아래층을 보고, 프롬프트 인젝션과
거부 무력화와 메모리 오염과 트리거 남용이 위층을 본다.
그리고 위층의 탐지 방식은 여전히 정규식이다.

### 실행 가능한 스크립트 배수가 점수 공식에 그대로 들어간 것이 설계의 핵심이다

연구에서 가져온 수치 중 하나가 공식에 직접 반영돼 있다.
실행 가능한 스크립트가 있으면 점수에 1.3배를 곱한다는 것이며,
연구의 2.12배라는 수치가 그 근거다.

이 설계는 정직하면서 동시에 문제를 안고 있다.
정직한 이유는 경험적 기저율을 규칙에 명시적으로 넣었기 때문이다.
대부분의 보안 스캐너가 심각도 가중치를 근거 없이 정하는 것과 대비된다.

문제는 배수의 크기다.
연구가 말한 것은 취약할 확률이 2.12배라는 것이고,
도구가 적용한 것은 점수 1.3배다.
둘 사이의 변환 근거가 없다.
그리고 이 배수는 발견이 하나라도 있을 때만 작동한다.
발견이 0이면 0에 1.3을 곱해도 0이므로,
실행 스크립트가 있다는 사실 자체는 아무 점수도 만들지 않는다.

즉 기저율은 이미 탐지된 위험을 증폭하는 데만 쓰이고,
탐지되지 않은 위험의 사전 확률로는 쓰이지 않는다.
연구 결과를 인용하는 방식으로는 이상하다.
2.12배가 뜻하는 것은 실행 스크립트가 있는 스킬을 더 의심해야 한다는 것인데,
공식은 그 의심을 반영하지 않는다.

### 기본값 조합이 이 도구의 성격을 정한다

설정 가능한 항목이 많지만 기본값은 하나로 정해져 있다.
LLM 분석이 켜져 있고, 공급자는 `nv_build`이며, 그것은 build.nvidia.com이다.

따라서 아무 옵션 없이 `skillspector scan`을 실행하면
검사 대상 스킬의 파일 내용이
NVIDIA의 추론 엔드포인트로 전송된다.
README는 이 사실을 신뢰 모델 절에서 분명히 적어 두었고, 숨기지 않는다.

다만 기본값이라는 선택은 문서화와 다른 문제다.
보안 도구의 사용자 상당수는 사내 코드나 외부에서 받은 정체불명의 스킬을
검사하며,
전자는 유출 우려가 있고 후자는 제3자의 저작물이다.
기본 동작이 둘 다를 외부로 보내는 구조라면 `--no-llm`이 기본이어야 한다는 주장이
가능하다.

그리고 `--no-llm`을 써도 SC4가 의존성 이름과 버전을 OSV.dev로 보낸다.
파일 내용이 아니므로 위험은 훨씬 작지만,
완전한 오프라인 검사를 기대한 사용자에게는
예상 밖의 통신이다.
README가 이것을 명시한 것은 좋은 문서화이고,
동시에 완전 차단 모드가 없다는 사실의 고백이기도 하다.

## 비평

### 프롬프트를 정규식으로 검사한다는 것이 이 도구의 근본 한계다

71개 패턴의 상당수가 자연어를 대상으로 한다.
지시를 무시하라는 명령, 거부하지 말라는 지시,
면책 문구를 생략하라는 요구가 그 예다.

이 탐지는 표현이 고정돼 있을 때만 작동한다.
그리고 공격자는 README에 공개된 패턴 목록을 읽을 수 있다.
어떤 문구가 걸리는지 알면 걸리지 않는 문구를 쓰는 것이 어렵지 않으며,
자연어는 같은 의미를 표현하는 방법이 사실상 무한하다.

이 비대칭이 코드 취약점 탐지와의 결정적 차이다.
`eval()` 호출은 우회하려면 다른 실행 경로를 써야 하고 그 경로도 유한하다.
반면 거부하지 말라는 지시를 우회하는 데는 새로운 기술이 필요 없고
어휘만 바꾸면 된다.

2단계 LLM 분석이 이 문제를 푸는 장치로 배치돼 있다.
그런데 HN의 TZubiri가 그 구조의 순환을 짚었다.
LLM이 코드를 검토하거나 코드가 LLM을 검증하는 식이라면 다층 방어가 되지만,
LLM이 LLM을 검토하는 것은 중복으로 보인다는 것이다.
검토하는 LLM이 잡아낼 정도라면 실행하는 LLM도 거부했을 것이고,
프롬프트가 실행하는 LLM을 속인다면 검토하는 LLM도 속일 가능성이 크다는
논리다.[^TZubiri]

이 반론에 완전히 동의할 필요는 없다.
검토 시점의 LLM은 사용자 맥락 없이 파일 내용만 보고 판단하므로
실행 시점과 조건이 다르고,
탈옥 방지 프롬프트도 적용된다.
그러나 반론의 핵심 — 두 모델이 같은 종류의 실패를 공유한다는 것 — 은 남는다.
모델 계열이 같으면 실패 양식도 상관관계를 갖고,
기본 공급자가 하나로 고정된 구조에서는 그 상관이 높다.

### 87퍼센트라는 정밀도 수치에 측정 조건이 없다

README는 LLM 단계가 정밀도를 약 87퍼센트까지 개선한다고 적는다.
이 도구에서 유일한 성능 수치이며,
도입 여부를 판단하는 사람이 가장 먼저 볼 숫자다.

그런데 이 숫자를 해석할 정보가 하나도 없다.
어떤 데이터셋에서 쟀는지, 정답을 누가 정했는지,
어떤 모델과 어떤 공급자로 쟀는지,
정적 단계만 돌렸을 때의 정밀도는 얼마였는지가 전부 없다.

특히 재현율이 빠진 것이 크다.
정밀도만 제시된 보안 도구의 수치는 거의 의미가 없는데,
탐지를 보수적으로 할수록 정밀도가 올라가기 때문이다.
악성 스킬 절반을 놓치면서 정밀도 87퍼센트를 달성하는 것이 가능하고,
그 구성에서는 이 도구가 위험하다.
연구가 말한 5.2퍼센트라는 악의적 스킬 비율에 대해 이 도구가 몇 퍼센트를
잡아내는지가 실제로 알고 싶은 수치인데
제시되지 않는다.

이 공백이 HN의 첫 반응과 직결된다.
jacobgold는 이 접근이 특정 종류의 스킬을 검증하는 데는 유용해 보이지만
잘못된 안전감을 준다고 우려한다.
안티바이러스 소프트웨어와 비슷해서 없는 것보다는 낫겠지만
얼마나 나은지 알기 어렵다는 것이다.
스킬은 결국 프롬프트이고 에이전트는 거기 적힌 것에 따라 코드를 실행하므로,
스킬을 돌리는 에이전트가 코드를 쓰고 명령을 실행하고
인터넷에 닿을 수 있다면 신뢰할 수 있음을 증명하는 것은 사실상 불가능하다고 본다.
프로그램을 내려받을 때 우리는 만든 회사가 악성 코드를 넣지 않았으리라 믿으며,
악성 코드를 탐지할 방법이 일부 있지만
소프트웨어 배포는 여전히 대체로 신뢰 기반 체계라는 것이다.
그의 권고는 코드를 내려받아 실행할 만하지 않은 출처의 스킬은 돌리지 말라는
것이다.[^jacobgold]

얼마나 나은지 알기 어렵다는 지적이 바로 이 수치 공백을 가리킨다.
DonsDiscountGas가 공급망 공격은 실재하며 좋은 보안 계획에는 여러 겹이 필요하고
이것이 포함할 만한 한 겹으로 보인다고 반박했지만,[^DonsDiscountGas]
한 겹의 두께를 모르면 그 겹을 얼마나 신뢰할지도 정할 수 없다.

### 비영어 콘텐츠를 놓칠 수 있다는 한계가 한 줄로 처리된다

한계 목록의 첫 항목이 비영어 콘텐츠에서 패턴을 놓칠 수 있다는 것이다.
한 줄이고 설명이 없다.

이 한계의 실제 크기는 그 한 줄이 시사하는 것보다 훨씬 크다.
프롬프트 인젝션 계열 패턴이 전부 영어 문구 대조에 의존한다면,
한국어나 중국어나 일본어로 쓴
같은 지시는 전부 통과한다.
그리고 공격자에게 이것은 우회 기법이라고 부르기도 민망한 수준의 조작이다.

이 문제는 이 도구의 다른 부분과 충돌하기도 한다.
일괄 스캔 도구는 중국어와 일본어와 한국어 다국어 탐지를 지원한다고 적혀 있다.
그렇다면 핵심 스캐너가 왜 그렇지 않은지,
일괄 도구의 다국어 탐지가 무엇을 뜻하는지가 설명되지 않는다.
기여자가 만든 부속 도구와 본체의 기능 수준이 다르다는 뜻으로 읽히는데,
그 격차가 문서에 드러나지 않는다.

한국어 사용자에게 이것은 추상적 한계가 아니다.
국내에서 배포되는 스킬과 국내 조직이 검사할 스킬 상당수가 한국어를 포함하며,
그 부분에 대해 이 도구가 제공하는 보장은 사실상 없다.
LLM 단계가 다국어를 이해하므로 일부 보완되겠지만,
그것은 기본값으로 외부에 파일을 보내는 경로이기도 하다.
결국 한국어 스킬을 제대로 검사하려면 내용을 외부 공급자에 보내야 하는 구조이며,
이 맞바꿈이 문서에 정리돼 있지 않다.

### 이 도구가 NVIDIA 카탈로그의 관문이라는 사실이 평가에 반영되어야 한다

README는 SkillSpector가 NVIDIA Verified Skills 파이프라인의 일부이며,
통과한 스킬이 NVIDIA 스킬 카탈로그에 게시된다고 밝힌다.

이 배치가 도구의 성격을 바꾼다.
오픈소스 보안 스캐너이면서
동시에 특정 벤더가 운영하는 배포 채널의 입장 심사 기준이다.
무엇이 안전한지를 정의하는 규칙과 그 정의를 통과한 것을 유통하는 채널을 같은
조직이 갖는다.

이 구조 자체가 부정한 것은 아니다.
플랫폼 사업자가 심사 기준을 만들고 스토어를 운영하는 것은 익숙한 형태다.
다만 그 경우 기준의 투명성과 이의 제기 절차가 함께 요구되며,
여기서는 그 둘이 보이지 않는다.

구체적으로 답이 없는 질문이 있다.
경쟁 카탈로그에 올라온 스킬이 낮은 점수를 받으면 그것이 기술적 판정인지 상업적
판정인지
외부에서 구분할 방법이 있는가.
패턴 목록은 공개돼 있지만 가중치와 임계값은 이 저장소가 단독으로 정하며,
그 조정에 대한 거버넌스 서술이 없다.

그리고 앞서 다룬 점수 구간이 이 문제를 키운다.
HIGH 발견 두 개면 50점으로 CAUTION이고 세 개면 75점으로 설치 금지다.
이 경계가 한 발견의 심각도 분류에 따라 넘나들 수 있으며,
심각도 분류는 규칙 작성자가 정한다.
설치 금지라는 판정의 무게에 비해 그 판정에 이르는 산술이 지나치게 단순하다.

### 스킬 생태계는 패키지 저장소가 겪은 역사를 압축해서 반복하고 있다

이 도구가 이식해 온 어휘 — CVE 조회, 타이포스쿼팅, 미고정 의존성, 기준선 억제 —
는 패키지 생태계가 15년에 걸쳐 만든 것이다.
그 어휘가 만들어진 순서도 대체로 같았다.
먼저 공유 문화가 생기고, 규모가 커지고, 사고가 나고, 스캐너가 나오고,
서명과 카탈로그가 뒤따랐다.

스킬 생태계는 그 순서를 몇 년이 아니라 몇 달 단위로 지나가고 있다.
연구가 42,447개 스킬을 수집할 수 있었다는 사실 자체가 규모를 말해 주고,
26.1퍼센트라는 취약 비율은 초기 패키지 저장소의 상태와 크게 다르지 않다.

이 압축이 시사하는 바는 다음 단계도 예측 가능하다는 것이다.
패키지 생태계에서 스캐너 다음에 온 것은 서명과 출처 증명이었고,
그다음은 저장소 자체의 심사 정책이었으며,
그 정책이 가장 큰 저장소 운영자에게 집중됐다.
SkillSpector가 서명 파이프라인의 일부로 소개된다는 것은 이미 두 번째 단계에
들어섰다는 뜻이다.

여기서 나오는 실무 함의는 지금이 표준을 정할 시점이라는 것이다.
패키지 생태계에서 서명과 출처 증명의 표준이 벤더 중립적으로 자리 잡는 데 오래
걸렸고,
그 지연 동안 각 저장소가 자기 방식을 굳혔다.
스킬 쪽에서 같은 일이 벌어지면 에이전트 CLI마다 다른 검증 체계가 생기고,
스킬 작성자가 여러 관문을 각각 통과해야 하는 상태가 된다.

### 기저율이 26퍼센트인 대상에 이진 게이트를 걸면 게이트가 먼저 무너진다

연구가 말한 26.1퍼센트라는 수치는 이 도구의 존재 이유이면서
동시에 이 도구의 운영을 어렵게 만든다.
네 개 중 하나가 발견을 낸다면,
설치 금지를 기계적으로 적용하는 조직은 곧 예외 처리에 시달린다.

기준선 억제 기능이 그 사실을 이미 인정하고 있다.
알려진 발견을 받아들여 점수에서 제외하고 재스캔에서 새 발견만 보게 한다는 것은,
실무에서 점수가 0이 되지 않는다는 전제 위에 만들어진 기능이다.

이 구조는 정적 분석 도구가 반복해서 겪은 경로다.
린터와 정적 분석기가 도입될 때마다 같은 순서를 밟는다.
경고가 쏟아지고, 전부 고칠 수 없어 기준선을 만들고, 기준선이 사실상 영구화되고,
새 경고만 보게 되면서 기존 위험은 조용히 남는다.

보안 도구에서 이 경로는 더 위험하다.
린터의 기준선에 남는 것은 스타일 문제이지만,
보안 스캐너의 기준선에 남는 것은 실제 취약점이기 때문이다.
그리고
스킬은 외부에서 받아 오는 것이라 기준선을 만드는 사람과 취약점을 만든 사람이
다르다.
자기가 쓰지 않은 코드의 발견을 받아들이는 결정이 반복되면,
그 결정의 기준은 빠르게 느슨해진다.

그래서 이 도구를 도입하는 조직이 실제로 설계해야 하는 것은 임계값이 아니라
예외 승인 절차다.
누가 기준선에 항목을 추가할 수 있는지, 그 항목에 만료가 있는지,
재검토 주기가 있는지가
도구의 정밀도보다 결과를 더 크게 좌우한다.
지문 기준선이 스캔 대상이나 버전이 바뀌면 무효화된다는 설계는 그 방향의 좋은
기본값이며,
문서에서 가장 저평가된 부분이다.

### 설치 전 검사는 신뢰 결정을 미룰 뿐 없애지 못한다

jacobgold의 결론 — 코드를 내려받아 실행할 만하지 않은 출처의 스킬은 돌리지 말라
— 이
이 도구의 존재와 모순되지 않는다는 점이 중요하다.
스캐너는 신뢰 결정을 대신해 주지 않고 그 결정에 정보를 더할 뿐이다.

그런데 도구의 출력 형태가 그 구분을 흐린다.
`safe_to_install`이라는 필드명과 SAFE라는 권고 문구는 판정처럼 읽히고,
종료 코드 0은 자동화 파이프라인에서 통과로 처리된다.
정보를 제공하도록 설계된 것이 판정으로 소비되는 전형적 구조다.

이 문제를 이 도구가 부분적으로 인식하고 있다는 흔적이 있다.
MCP 도구가 `llm_used`와 `scan_mode`를 함께 돌려주는 이유가 정적 전용 스캔의 낮은
점수를
완전한 스캔의 깨끗한 결과로 오인하지 않게 하려는 것이라고 명시돼 있다.
같은 논리를 한 단계 더 밀면 SAFE라는 단어 자체가 문제가 된다.
정적 분석과 표본 기반 LLM 평가를 통과했다는 것과 안전하다는 것은 다른 진술이다.

여기서 나오는 일반 원칙은 보안 도구의 출력 어휘가 그 도구의 보증 범위를 넘어서면
안 된다는 것이다.
발견 없음과 안전함은 다르고,
전자를 후자의 언어로 표기하는 순간 사용자가 도구의 한계를 알아차릴 경로가
사라진다.
이 도구는 신뢰 모델 절에서 한계를 정직하게 적어 두었지만,
그 절을 읽는 사람은 소수이고 점수와 권고는 모두가 본다.

### 공격 표면이 문서가 아니라 실행 경로에 있다는 점이 다음 단계를 정한다

연구가 찾아낸 가장 실용적인 사실은 실행 가능한 스크립트를 포함한 스킬이 2.12배
더 위험하다는 것이다.
이 수치가 뜻하는 바는 위험이 스킬이라는 형식에서 오는 것이 아니라
그 안에 코드가 들어갈 수 있다는 사실에서 온다는 것이다.

그렇다면 가장 효과적인 대응은 더 나은 스캐너가 아니라 실행 경계다.
스킬이 프롬프트만 담고 코드를 담을 수 없다면 위험의 상당 부분이 사라지고,
코드를 담아야 한다면 그 코드가 어떤 권한으로 도는지가 검사보다 중요해진다.

에이전트 런타임 쪽에서 이 방향의 변화가 이미 진행 중이다.
스킬이 쓸 수 있는 도구를 선언하게 하고, 파일 접근 범위를 제한하고,
네트워크 접근을 승인 대상으로 만드는 설계가 그것이다.
SkillSpector의 MCP 최소 권한 범주가 선언된 권한과 실제 코드 능력의 불일치를 보는
것도 같은 방향의 인식이다.

여기서 이 도구의 장기적 위치가 정해진다.
실행 경계가 제대로 자리 잡으면 정적 스캐너의 역할은 줄어든다.
권한이 없으면 자격 증명을 유출하는 코드가 있어도 유출할 것이 없기 때문이다.
반대로 경계가 느슨한 상태가 지속되면 스캐너가 유일한 방어선으로 남고,
그것은 앞서 본 이유들로 충분하지 않다.

그래서 이 저장소가 앞으로 어떤 기능을 추가하는지보다,
에이전트 CLI들이 스킬에 어떤 권한 모델을 도입하는지를 보는 편이 이 문제의 향방을
더 잘 알려 준다.
그리고 지금 시점에서 개인 사용자가 할 수 있는 가장 효과적인 조치도 스캔이 아니라
격리다.
낯선 스킬은 별도 계정이나 컨테이너에서 먼저 돌려 보는 것이,
71개 패턴 중 하나에 걸리기를 바라는 것보다 확실하다.
