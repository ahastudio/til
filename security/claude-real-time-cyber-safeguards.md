# Claude Opus·Sonnet의 실시간 사이버 안전장치

원문: [Real-time cyber safeguards on Claude Opus and Sonnet](https://support.claude.com/en/articles/14604842-real-time-cyber-safeguards-on-claude)

## 요약

Anthropic이 Claude Opus와 Sonnet 계열 모델에 적용한 실시간 사이버
안전장치(real-time cyber safeguards)를 설명하는 공식 지원 문서다.
사용 정책(Usage Policy)에 근거해 금지되거나 고위험으로 판단되는
사이버보안 용도의 요청을 자동으로 탐지하고 차단하도록 설계되었다고
밝힌다.
문서는 이 안전장치가 Opus와 Sonnet 등급 모델에만 적용된다는 단서를
서두에 명시한다.

차단 대상은 두 범주로 나뉜다.
첫째는 금지된 사용(Prohibited use)으로, 대규모 데이터 유출(mass data
exfiltration)이나 랜섬웨어 코드 개발처럼 거의 항상 악의적으로 쓰이며
정당한 방어 목적이 거의 또는 전혀 없는 활동이다.
이 범주는 기본 차단되며 사이버 검증 프로그램을 통한 셀프서비스
신청으로 조정할 수 없다.
둘째는 고위험 이중용도(High Risk Dual use)로, 취약점 익스플로잇이나
공격형 보안 도구 개발처럼 정당한 방어적 활용이 존재하는 활동이다.
역시 기본 차단되지만, 방어 목적 사용자는 사이버 검증 프로그램을 통해
조정을 신청할 수 있다.

사이버 검증 프로그램(Cyber Verification Program, CVP)은 Opus와
Sonnet을 대상으로 한 무료 신청 기반 프로그램이다.
많은 보안 실무자가 이중용도 범주와 겹치는 정당한 업무를 수행한다는
점을 인정하면서, 그들이 중단을 최소화하며 안전하게 작업을 이어가도록
하는 것이 목적이라고 설명한다.
CVP는 데이터 보존(data retention)이 켜져 있어야 하며, API 조직이
제로 데이터 보존(Zero Data Retention, ZDR)을 쓰는 경우 데이터 보존이
켜진 별도 워크스페이스를 구성할 수 있다.
영업 관리형 Claude Enterprise나 Claude Teams 계정은 Anthropic 영업
담당자에게 문의해야 한다.

신청 경로는 Claude에 접근하는 방식에 따라 다르며, 심사 결과는 영업일
기준 2일 이내에 이메일로 통지하는 것을 목표로 한다.

| 접근 방식                                    | 신청 방법                                            |
| -------------------------------------------- | ---------------------------------------------------- |
| Anthropic 자사(Claude.ai, Claude Code, API)  | 검증 포털에서 신청(권한 있는 관리자만 옵션이 보임)   |
| Microsoft Foundry                            | Azure 테넌트 ID와 구독 ID로 Cyber Use Case Form 제출 |
| Amazon Bedrock                               | 현재 이용 불가                                       |
| Claude Platform on AWS                       | 검증 포털에서 AWS 계정을 연결해 신청                 |
| Google Vertex AI                             | 현재 이용 불가                                       |
| 서드파티 플랫폼                              | 해당 플랫폼에 직접 문의(모든 플랫폼이 참여하지 않음) |
| BYOK 고객                                    | Anthropic 자사 항목을 따름                           |

문서는 이의 제기 절차도 다룬다.
자격을 갖춘 신청을 잘못 거절하는 일이 이따금 발생하리라 예상하며,
승인된 사용자도 정당한 작업에서 여전히 차단을 겪을 수 있다고 인정하고
두 문제를 줄이려 노력 중이라고 밝힌다.
문제를 겪는 사용자에게는 두 가지 확인을 권한다.
하나는 올바른 조직에 로그인했는지로, CVP 승인은 특정 조직 ID에 묶여
있어 개인 워크스페이스처럼 다른 조직에서는 승인이 이어지지 않는다.
다른 하나는 해당 활동이 실제로 이중용도인지로, CVP 승인은 이중용도
활동의 차단만 해제하며 금지된 사용은 CVP 상태와 무관하게 계속
차단된다.
두 가지를 확인하고도 문제가 있다고 판단되면 신고 또는 이의 제기
양식을 제출할 수 있다.

## 분석

### 이중용도라는 범주를 제품 정책의 1급 개념으로 끌어올린 것

이 문서에서 구조적으로 가장 중요한 결정은 차단 대상을 하나의
목록이 아니라 두 범주로 쪼갠 것이다.
금지된 사용과 고위험 이중용도를 나누고, 후자에만 해제 경로를 여는
설계는 사이버보안 도구의 오래된 딜레마를 정책 언어로 옮긴 것이다.

이중용도라는 개념 자체는 새롭지 않다.
Metasploit, Burp Suite, Cobalt Strike 같은 도구는 모두 방어와 공격
양쪽에 쓰이며, 업계는 오랫동안 도구가 아니라 사용 맥락으로 정당성을
판정해 왔다.
문제는 LLM이 그 맥락을 판정할 위치에 있지 않다는 것이다.
같은 익스플로잇 코드 요청이 레드팀 훈련일 수도 침해 준비일 수도
있고, 요청 텍스트만으로는 구별되지 않는다.

Anthropic의 해법은 그 판정을 요청 시점이 아니라 계정 수준으로
옮기는 것이다.
개별 요청의 의도를 추론하는 대신, 조직이 사전에 자신을 검증받게
하고 그 검증 결과를 조직 ID에 결합한다.
이는 판정 불가능한 문제를 판정 가능한 문제로 치환한 것이며, 실질적으로
“이 요청이 악의적인가”를 “이 조직을 신뢰하는가”로 바꾼 셈이다.

### 데이터 보존을 필수 조건으로 건 것의 의미

CVP가 데이터 보존 활성화를 요구하고, ZDR 조직에는 별도 워크스페이스를
만들라고 안내하는 대목은 문서에서 가장 논쟁적인 부분이다.
표면적으로는 남용 조사를 위한 로그 확보로 읽히지만, 그 함의는
훨씬 넓다.

보안 업무는 성격상 민감 데이터를 다룬다.
침투 테스트 대상 시스템의 구조, 발견된 취약점, 고객사 인프라 정보가
프롬프트에 담기며, 이런 조직이 ZDR을 선택한 데는 계약상·규제상
이유가 있는 경우가 많다.
그런데 CVP는 정확히 그 조직들에게 데이터 보존을 켜라고 요구한다.

이 요구가 만드는 것은 교환 관계다.
고위험 기능을 쓰려면 감시 가능성을 제공해야 하고, 감시를 거부하면
기능을 잃는다.
이는 벤더가 위험을 관리하는 합리적 방식이지만, 동시에 보안 업무에서
가장 민감한 데이터가 벤더 측에 남게 되는 결과를 낳는다.
문서는 이 교환을 절차적 요구 사항으로만 서술하고, 그것이 왜
필요한지도 어떤 보호가 적용되는지도 설명하지 않는다.

### 플랫폼별 가용성 차이가 드러내는 통제 구조

신청 경로 표에서 가장 눈에 띄는 것은 Amazon Bedrock과 Google Vertex
AI에서 CVP를 쓸 수 없다는 항목이다.
같은 모델을 쓰더라도 어느 클라우드를 통해 접근하느냐에 따라 이중용도
작업의 가능 여부가 달라진다.

이 차이가 발생하는 이유는 CVP가 조직 신원 검증에 의존하기 때문이다.
Anthropic 자사 경로와 AWS의 Claude Platform에서는 Anthropic 계정을
만들어 클라우드 계정을 연결하는 방식으로 신원을 확인할 수 있지만,
Bedrock과 Vertex는 그 연결 고리가 없다.
Microsoft Foundry가 Azure 테넌트 ID와 구독 ID를 요구하는 것도 같은
맥락이다.

결과적으로 안전장치의 실효 범위가 모델이 아니라 유통 경로에 의해
결정된다.
같은 Opus 모델을 쓰는 두 조직이 클라우드 선택 하나로 전혀 다른
제약을 받게 되며, 이는 보안 도구를 만드는 조직에게 모델 선택보다
접근 경로 선택이 더 중요한 변수가 될 수 있음을 뜻한다.

### 실패를 미리 인정하는 서술 방식

이의 제기 항목에서 “자격을 갖춘 신청을 잘못 거절하는 일이 이따금
발생하리라 예상한다”고 밝히고, 승인된 사용자도 여전히 차단을 겪을 수
있다고 인정하는 대목은 정책 문서로서는 이례적으로 솔직하다.

이 서술은 두 가지 일을 동시에 한다.
하나는 기대치 관리다—오탐이 발생했을 때 그것이 시스템 결함이 아니라
예상된 범위 내 현상임을 미리 알림으로써 신뢰 손상을 줄인다.
다른 하나는 책임 분산이다—사용자에게 조직 ID 확인과 활동 범주 확인이라는
자가 진단 절차를 먼저 요구함으로써, 신고가 접수되기 전에 상당수
문의를 걸러낸다.

다만 이 솔직함에는 비대칭이 있다.
문서는 오탐(잘못된 차단)의 존재는 명시적으로 인정하지만, 미탐(차단해야
할 것을 놓치는)에 대해서는 아무 언급이 없다.
안전장치를 논하는 문서에서 탐지 실패의 다른 방향을 다루지 않는 것은,
이 문서의 독자가 차단당한 정당한 사용자로 상정되어 있음을 보여준다.

## 비평

### 탐지 방식에 대한 서술이 전무해 사용자가 대비할 근거가 없다

문서 전체에서 안전장치의 동작을 설명하는 문장은 “요청을 자동으로
탐지하고 차단하도록 설계되었다”가 사실상 전부다.
분류기가 무엇을 보는지, 요청 텍스트만 보는지 대화 이력 전체를 보는지,
코드를 실행 맥락과 함께 판정하는지, 신뢰도 임계값이 어떻게 설정되는지
아무것도 밝히지 않는다.

이 공백이 실무에서 문제가 되는 이유는 사용자가 회피 전략을 세울 수
없기 때문이 아니라, 정당한 작업을 어떻게 표현해야 통과하는지 알 수
없기 때문이다.
보안 연구자가 취약점 분석을 요청할 때 어떤 맥락을 덧붙이면 이중용도로
인정되는지, 어떤 표현이 금지 범주로 오인되는지에 대한 지침이 없으면
시행착오만 반복된다.
문서가 권하는 자가 진단—조직 ID 확인과 활동 범주 확인—은 이미
차단당한 뒤의 사후 절차이지, 사전에 작업을 설계하는 데는 도움이 되지
않는다.

비교 대상을 생각하면 이 공백은 더 두드러진다.
콘텐츠 필터를 제공하는 다른 API들은 대개 어떤 범주를 어떤 점수로
판정했는지를 응답에 포함하고, 사용자는 그 신호로 프롬프트를 조정한다.
여기서는 차단 여부만 통보되고 그 이유는 범주 이름 두 개로만
설명된다.
투명성을 낮추는 것이 회피를 어렵게 만드는 보안상 이점이 있다는 반론이
가능하지만, 문서는 그 절충을 언급조차 하지 않아 독자가 판단할 근거를
남기지 않는다.

### 조직 단위 승인은 개인 연구자를 구조적으로 배제한다

CVP 승인이 특정 조직 ID에 묶이고 개인 워크스페이스로는 이어지지
않는다는 규정은 운영상 합리적이지만, 그 결과 배제되는 집단이
분명하다.

보안 연구는 상당 부분 개인 단위로 이루어진다.
버그 바운티 헌터, 독립 취약점 연구자, 오픈소스 보안 도구 메인테이너,
학위 과정 중인 대학원생은 모두 조직 계정 없이 개인 자격으로 일한다.
이들이 하는 작업—익스플로잇 작성, 퍼징 하네스 개발, 공격 시나리오
재현—은 정확히 고위험 이중용도 범주에 해당한다.

문서의 신청 경로 표에는 개인 연구자를 위한 항목이 없다.
“권한 있는 관리자만 옵션이 보인다”는 단서는 조직 계정을 전제하며,
개인이 관리자인 1인 조직으로 신청 가능한지도 명시되지 않는다.
결과적으로 이 정책은 기업 보안팀에게는 신청 경로를 제공하고 개인
연구자에게는 사실상 사용 불가를 통보하는 셈이 되는데, 이 비대칭이
의도된 것인지 부작용인지 문서만으로는 알 수 없다.

이 배제가 장기적으로 문제인 이유는 보안 생태계에서 개인 연구자가
차지하는 비중 때문이다.
주요 취약점 상당수가 조직에 속하지 않은 개인에 의해 발견되어 왔고,
그들이 상용 AI 도구에서 밀려나면 그 격차는 규제받지 않는 모델이나
오픈 웨이트 모델로 이동해 메워질 것이다.
안전장치가 의도한 것은 위험한 능력의 통제이지만, 실제 효과는 그
능력의 사용자를 다른 곳으로 옮기는 것에 그칠 수 있다.

### 이중용도와 금지 사용의 경계가 정의되지 않은 채 결과만 통보된다

문서는 두 범주를 예시로만 구분한다.
금지 사용의 예로 대규모 데이터 유출과 랜섬웨어 코드 개발을, 이중용도의
예로 취약점 익스플로잇과 공격형 보안 도구 개발을 든다.
그런데 이 예시들 사이에는 넓은 회색지대가 있고, 문서는 그 지대를
어떻게 판정하는지 말하지 않는다.

구체적으로 생각해 보면 경계는 금방 흐려진다.
랜섬웨어의 암호화 루틴을 분석해 복호화 도구를 만드는 것은 어느
쪽인가.
침투 테스트 보고서를 위해 데이터 유출 시나리오를 시연하는 코드는
어떤가.
자동화된 대량 스캐닝 도구는 방어적 자산 관리인가 정찰인가.
이 질문들은 보안 업무에서 일상적으로 제기되며, 판정 기준 없이는
사용자가 자신의 작업이 어느 범주에 속하는지 예측할 수 없다.

이 불확실성은 이의 제기 절차에서 사용자에게 전가된다.
문서는 “해당 활동이 실제로 이중용도인지” 확인하라고 요구하지만,
그 판정 기준을 제공하지 않은 채 확인만 요구하는 것은 답을 알려주지
않고 정답을 맞히라는 것과 같다.
CVP 승인을 받은 조직조차 자신의 작업이 갑자기 금지 범주로 분류될
수 있다면, 그 승인이 제공하는 예측 가능성은 명목상에 그친다.

### 영업일 2일이라는 처리 기간은 사고 대응 시간과 맞지 않는다

CVP 심사 결과를 영업일 기준 2일 이내에 통지하는 것을 목표로 한다는
서술은 신규 신청에 대해서는 합리적이지만, 이 정책이 적용되는 업무의
성격을 고려하면 부족하다.

보안 업무의 상당 부분은 시간에 쫓긴다.
활성 침해 사고가 진행 중일 때 악성 코드를 분석하거나, 공개된
취약점의 익스플로잇 가능성을 긴급히 검증하거나, 제로데이 대응
과정에서 공격 경로를 재현해야 하는 상황이 그렇다.
이런 순간에 도구가 차단되고 해제까지 영업일 2일이 걸린다면, 그
도구는 사고 대응 워크플로에 편입될 수 없다.

문제는 이것이 사전 신청으로 해결되지 않는다는 점이다.
앞서 지적했듯 CVP 승인은 이중용도 활동만 해제하며, 승인된 조직도
“정당한 작업에서 여전히 차단을 겪을 수 있다”고 문서 스스로 밝힌다.
즉 미리 승인을 받아 두어도 결정적인 순간에 차단될 가능성이 남아
있고, 그 경우 의지할 수 있는 것은 다시 영업일 단위 이의 제기 절차다.

이 시간 구조가 시사하는 바는 명확하다.
현재 설계에서 Claude Opus·Sonnet은 계획된 보안 연구에는 쓸 수 있어도
실시간 사고 대응에는 신뢰할 수 없는 도구다.
문서가 “중단을 최소화한다(minimizing interruption)”를 CVP의 목적으로
내걸었지만, 최소화된 중단의 단위가 영업일이라면 그것은 일부 업무
유형에 대해서는 최소화가 아니다.

## 인사이트

### 이 정책의 실질은 능력 통제가 아니라 책임 이전이다

안전장치를 능력 통제 장치로 읽으면 이 정책은 실패하도록 설계되어
있다.
차단되는 활동은 모두 다른 수단으로 수행 가능하다—오픈 웨이트 모델,
경쟁 벤더, 기존 도구 체인이 모두 대안이며, 정말로 랜섬웨어를 만들려는
공격자가 Claude 차단에 막혀 포기할 가능성은 낮다.

그렇다면 이 정책이 실제로 하는 일은 무엇인가.
승인 절차를 거치고 데이터 보존에 동의한 조직에게 고위험 기능을
열어 주는 구조는, 그 기능이 오용되었을 때 “우리는 사용자를 검증했고
활동을 기록했다”고 말할 수 있는 위치를 만든다.
조직 ID에 승인을 결박하고 로그를 남기게 하는 것은 통제라기보다
추적 가능성 확보이며, 추적 가능성의 1차 수혜자는 사고가 났을 때
설명 책임을 져야 하는 벤더다.

이 해석은 문서의 여러 선택을 일관되게 설명한다.
데이터 보존을 필수로 건 것도, 승인을 조직 단위로 묶은 것도, 금지
범주는 CVP로도 해제하지 않는 것도 모두 능력 차단보다 책임 경계
설정에 부합한다.
GCC가 AI 생성 코드를 거부하는 정책이 실제로는 저작권 소송에서 선의를
입증할 서류를 만드는 것이었듯, 이 정책의 1차 수신자도 사용자가
아니라 미래의 규제 기관과 사고 조사관일 가능성이 높다.

이 관점이 실무에 주는 함의는 정책을 대하는 태도의 전환이다.
“어떻게 하면 차단을 피할까”가 아니라 “이 벤더가 어떤 위험을 자신의
장부에서 덜어내려 하는가”를 먼저 물으면, CVP 신청이 요구하는 것의
성격—무엇을 내주고 무엇을 얻는지—이 더 분명해진다.

### 이 구조는 암호화 수출 통제가 걸어간 길을 반복할 가능성이 높다

능력 자체는 중립적이지만 오용 가능성 때문에 접근을 제한하고, 정당한
사용자에게는 별도 승인 절차를 제공하는 구조는 1990년대 암호화 기술
수출 통제와 형태가 같다.
당시 미국은 강한 암호화를 군수품으로 분류해 수출을 제한했고,
정당한 사용자는 예외 승인을 받아야 했다.

그 정책이 어떻게 끝났는지는 알려져 있다.
암호화 알고리즘은 수학이었고 국경을 넘는 것을 막을 수 없었다.
PGP 소스 코드가 책으로 인쇄되어 수출되었고, 해외 구현체가 등장했으며,
결국 통제는 미국 기업의 경쟁력만 떨어뜨린 채 2000년 전후로 대폭
완화되었다.
Bernstein 판결은 소스 코드를 표현의 자유로 인정했다.

지금 상황과의 유비는 정확하지 않지만 구조는 겹친다.
모델 가중치는 알고리즘보다 통제하기 쉽지만, 오픈 웨이트 모델이
이미 존재하고 성능 격차가 줄고 있다.
차단이 강해질수록 수요는 규제 밖으로 이동하고, 그 이동은 되돌리기
어렵다.
암호화 통제에서 얻은 교훈이 반복된다면, 이 안전장치의 장기 균형점은
현재의 엄격함이 아니라 훨씬 완화된 형태이거나, 통제 지점이 모델
접근이 아니라 실행 환경으로 옮겨 간 형태일 것이다.

다만 한 가지 차이는 짚어야 한다.
암호화는 방어 기술이었고 확산이 사회적 이익이었지만, 공격형 보안
능력은 그렇게 단순하지 않다.
그럼에도 방어와 공격이 같은 지식에서 나온다는 점은 변하지 않으며,
통제가 방어 측 접근성을 더 크게 떨어뜨린다면—공격자는 규제를 무시하고
방어자는 준수하므로—순효과는 오히려 부정적일 수 있다.

### 조직 ID에 승인을 묶는 설계는 보안 컨설팅 업계의 작업 방식과 충돌한다

CVP 승인이 조직 ID에 결박된다는 규정은 단일 조직에서 일하는 사용자에게는
자연스럽지만, 보안 컨설팅 업계의 실제 작업 구조와는 잘 맞지 않는다.

침투 테스트와 보안 감사는 대개 고객사별로 격리된 환경에서 수행된다.
고객사 데이터를 섞지 않기 위해 프로젝트마다 별도 워크스페이스를 쓰고,
계약에 따라 고객사 테넌트에서 작업하기도 하며, 프리랜서는 여러
회사의 조직에 번갈아 소속된다.
이런 구조에서 승인이 하나의 조직 ID에만 붙으면, 컨설턴트는 프로젝트를
옮길 때마다 차단을 만나게 된다.

문서가 예시로 든 상황—“개인 워크스페이스 대신 팀 조직”—은 이 문제의
가장 단순한 형태일 뿐이다.
실제로는 데이터 격리를 위해 의도적으로 분리한 워크스페이스마다 별도
승인이 필요해지고, 각 승인은 영업일 2일이 걸린다.
데이터 격리라는 보안 모범 사례를 따를수록 CVP 사용이 불편해지는
역설이 생긴다.

이 마찰이 낳을 2차 효과는 예측 가능하다.
조직들은 승인받은 단일 워크스페이스에 여러 고객사 작업을 몰아넣으려는
유인을 갖게 되고, 이는 정확히 데이터 격리 원칙을 훼손하는 방향이다.
안전을 위해 설계된 정책이 다른 축의 안전 관행을 약화시키는 구조인데,
문서는 이 상충을 인식하지 않는다.
CVP가 조직 단위가 아니라 검증된 개인이나 자격 증명 단위로 작동했다면
피할 수 있었을 문제이며, 그 설계 선택의 근거는 문서에 제시되지 않는다.

### 모델 등급별 정책 분화는 안전과 성능을 교환하는 시장을 만들어낸다

이 문서가 서두에 명시하는 “Opus와 Sonnet 등급 모델에만 적용된다”는
단서는 지나치기 쉽지만 중요한 함의를 갖는다.
같은 벤더의 모델 사이에 정책 차이가 존재한다는 것은, 사용자가 능력과
제약을 저울질해 선택할 수 있다는 뜻이다.

이 구조가 만드는 것은 새로운 형태의 선택 압력이다.
고위험 작업을 하려는 사용자는 두 갈래 중 하나를 택하게 된다—더
강력한 모델을 쓰되 검증 절차와 데이터 보존을 감수하거나, 제약이
덜한 하위 등급 모델로 내려가되 성능을 포기하는 것이다.
이는 안전장치가 의도한 “위험한 작업을 막는다”가 아니라 “위험한
작업을 덜 유능한 모델로 밀어낸다”는 결과를 낳는다.

장기적으로 이 분화는 벤더에게 미묘한 문제를 안긴다.
안전장치를 최상위 모델에만 적용하는 것은 위험 관리 관점에서 합리적이지만,
그 결과 최상위 모델의 실사용 범위가 좁아지고 하위 모델이 오히려
넓은 용도로 쓰이게 된다.
성능 향상에 투입한 자원이 정책 제약 때문에 시장에서 온전히 회수되지
않는 구조이며, 이 긴장은 등급 간 성능 격차가 커질수록 심해진다.

여기서 파생되는 예측은 두 가지다.
하나는 안전장치가 결국 전 등급으로 확대되리라는 것—등급별 차이가
회피 경로로 쓰인다는 것이 드러나면 그 구멍을 막는 방향으로 갈
수밖에 없다.
다른 하나는 반대로 승인 절차가 경량화되리라는 것—검증을 거친
사용자에게 최상위 모델을 온전히 열어 주는 것이 상업적으로 더
합리적이기 때문이다.
어느 쪽이든 현재의 “최상위 모델만 제약, 승인은 영업일 2일”이라는
조합은 과도기적 형태로 보인다.
