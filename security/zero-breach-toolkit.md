# Zero Breach Toolkit: 알려진 mercenary spyware의 흔적을 오프라인으로 찾는 도구

<https://archivegenocide.com/scan/>

<https://github.com/interplains/Zero-Breach-Toolkit>

GN 토론: <https://news.hada.io/topic?id=36362>

## 소개

Zero Breach Toolkit은 컴퓨터, Android 폰,
iPhone 백업에서 알려진 스파이웨어의 흔적을 찾는 무료 오픈소스 도구이다.
대상은 Pegasus, Predator, Graphite, Candiru처럼 민간 업체가 판매하는
스파이웨어(mercenary spyware)이다.
제작자는 archivegenocide라는 이름을 쓰며,
이 저장소가 기존 프로젝트 Zero Breach 위에 만들어졌다고 밝힌다.
저장소는 2026-10-25에 만들어졌다.
README는 2버전부터 Windows, Mac, Linux에서 더블클릭으로 여는 프로그램이 되었고
27개 언어를 지원한다고 알린다.
릴리스 기록을 보면 v2.0.0은 2026-11-01 18:09 UTC에,
v2.0.1은 같은 날 18:36 UTC에 올라왔고, 그 앞의 v0.1.15는
2026-10-31이다.[^releases]
2026-11-02에 읽은 저장소 정보는 별 4,094개, 포크 431개, 열린 이슈 7개,
주 언어 Python, 라이선스 Apache-2.0이다.[^api]

제작자는 이 도구의 약속을 세 가지로 요약한다.
첫째, 읽기 전용이다.
원본 증거와 시스템 설정을 바꾸지 않고, 임시 데이터베이스 사본과 사용자가 요청한
보고서만 쓴다.
둘째, 검사 중에는 네트워크 요청을 하지 않는다.
스파이웨어 주소를 조회하지 않고 업로드 기능도 없으며,
Python의 네트워크 호출을 막고 우회 경로를 거부한다.
제작자는 이것이 운영체제 수준의 네트워크 샌드박스는 아니라고 스스로 적는다.
셋째, 한계를 보고서에 적는다.
무엇이 발견되었는지, 증거가 얼마나 강한지, 무엇을 검사하지 못했는지를 모두 쓰고,
깨끗한 결과를 안전의 증명으로 내놓지 않는다.

도구를 돌리기 전에 전문가의 도움을 먼저 받으라는 안내도 맨 앞에 있다.
지금 표적이 되고 있다고 생각하는 기자와 활동가는 Access Now의 디지털 보안
헬프라인이나 Amnesty International의 Security Lab에 연락하라고 한다.
이 도구를 먼저 돌릴 필요는 없다고도 적는다.

## 내려받는 프로그램으로 실행하기

README가 가장 쉬운 길로 내세우는 것은 Python도 명령도 필요 없는 프로그램이다.
릴리스 페이지에서 컴퓨터에 맞는 파일을 받아 두 번 누르면 창이 열린다.
검사 종류를 고르고 시작 버튼을 누른 뒤 결과를 읽고 보고서를 저장한다.
**Live connections** 탭은 지금 인터넷에 연결된 프로그램을 보여 주고,
스파이웨어 목록에 있는 주소를 표시한다.

| 컴퓨터            | 받을 파일                                     |
| ----------------- | --------------------------------------------- |
| Windows           | `zero-breach-toolkit-windows-x64.exe`         |
| Apple silicon Mac | `zero-breach-toolkit-macos-apple-silicon.dmg` |
| Intel Mac         | `zero-breach-toolkit-macos-intel.dmg`         |
| Linux             | `zero-breach-toolkit-linux-x64.tar.gz`        |

이 파일들은 Microsoft나 Apple의 서명이 없다.
그래서 처음 열 때 Windows는 PC를 보호했다는 경고를,
macOS는 한 번 차단하는 화면을
보여 주며, README는 각각 **More info**에서 **Run anyway**를 누르거나
**System Settings**의 **Open Anyway**를 누르라고 안내한다.
서명에는 실명 계정이 필요하다는 것이 제작자의 이유이다.
대신 GitHub가 공개된 소스로 빌드했는지는 `gh attestation verify <file> --repo
interplains/Zero-Breach-Toolkit`로 확인할 수 있다고 한다.

## 무엇을 검사하는가

검사 대상은 기기 종류에 따라 다르다.
아래 내용은 모두 제작자가 설명하는 검사 범위이며, 독립적으로 확인한 것이 아니다.

| 대상          | 읽는 것                                                                                                                                                                                                                                         | 한계로 적힌 점                                                                                                           |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Windows       | 브라우저(Chrome, Edge, Firefox 등 다수)의 기록과 쿠키와 다운로드, 다운로드 출처 표시(Mark of the Web), Win+R 입력 상자, 백신 상태와 Defender 기록, PowerShell 로그, shim cache와 Prefetch와 Amcache, DNS 캐시와 hosts 파일과 시작 프로그램 등록 | 관리자 권한이 필요 없다. 잠기거나 지원되지 않는 기록은 공백으로 보고한다. Amcache 일치는 실행을 증명하지 않는다          |
| macOS와 Linux | 같은 브라우저 계열(Snap과 Flatpak 포함), Safari 기록, 시작 설정(LaunchAgent와 systemd 등), 셸 시작 파일과 기록, hosts 파일, 읽을 수 있는 시스템 로그                                                                                            | Safari를 읽으려면 터미널에 전체 디스크 접근 권한이 필요하다. 저장된 설정을 읽을 뿐 작업이 켜졌는지나 실행됐는지는 모른다 |
| Android       | AndroidQF가 만든 수집본: 설치된 앱과 서명 인증서, 설치 이력, 로그, 복호화된 침입 로그, SMS 링크, 스토어 밖에서 설치한 앱의 권한, 수정된 폰의 징후(잠금 해제된 부트로더 등), Cellebrite 잠금 해제의 흔적                                         | 폰과 직접 통신하지 않는다. 수집본에 든 것만 본다. Cellebrite 기록은 폰이 제한된 시간만 보관한다                          |
| iPhone        | Finder, Apple Devices, iTunes의 로컬 백업(암호화 포함), 추출된 파일 시스템, sysdiagnose에서 메시지, Safari, 앱 기록, 구성 프로파일(원격 관리, 루트 인증서, VPN과 프록시와 DNS), 진단 로그                                                       | 지원하는 항목과 로컬 증거만 본다. 기기를 직접 수집하지 않는다. 일반 백업만으로는 Cellebrite 접근 여부를 알 수 없다       |

기본 파일 지문(해시) 검사는 `.dll`, `.exe`,
`.sys` 같은 확장자의 파일을 선택한 폴더에서
512 MiB까지 대상으로 한다고 README는 적는다.
컴퓨터 검사는 공개된 인프라나 파일 흔적을 찾을 수 있을 뿐,
폰이 감염되었는지는 알려 주지 못한다고 제작자는 적는다.

탐지가 아니라 예방을 위한 검사도 있다.
Windows와 macOS에서 Chrome, Firefox, Adobe Acrobat, Java, Office 같은 흔한
프로그램의 버전을 미국 CISA의 알려진 악용 취약점(Known Exploited
Vulnerabilities)
목록과 견준다.
공식 CVE 기록에 고쳐진 버전이 있고 설치된 버전이 그보다 낮을 때만 오래되었다고
부르며, 비교는 오프라인으로 한다.

비교 기준이 되는 지표(indicator)는 내려받는 출처 29곳과 내장 묶음 두 개에서 모은
약 13,300개이다.
출처에는 Amnesty International의 Security Lab,
Mobile Verification Toolkit(MVT) 프로젝트, Citizen Lab, Echap이 들어 있다.
Citizen Lab 보고서에서 손으로 가려 뽑은 Candiru와 Graphite 지표는 저장소에 들어
있어 오프라인에서도 쓰인다.
다른 내장 묶음에는 기자와 활동가와 소수자를 겨눈 스파이웨어의 파일
지문과 Android
패키지 이름 약 900개가 있고, README는 모든 줄에 출처를 달았다고 말한다.
나머지는 `--update` 명령이 정해진 공식 출처 목록에서 내려받는다.

## 실행하기

Python으로 소스에서 직접 돌리려면 3.8 이상만 있으면 된다.
관리자 권한도, 추가 패키지도 필요 없다.
암호화된 iPhone 백업을 읽을 때만 선택 패키지 `cryptography`가 필요하며,
자동으로 설치되지 않는다.

가장 짧은 경로는 다음과 같다.

```bash
git clone https://github.com/interplains/Zero-Breach-Toolkit.git
cd Zero-Breach-Toolkit
python3 -X utf8 scan/zero-breach-toolkit.py --update
python3 -X utf8 scan/zero-breach-toolkit.py
```

README는 `--update`가 검사 흐름에서 인터넷을 쓰는 단계라고 소개한다.
없으면 작은 내장 지표 묶음만 쓰이므로 제작자는 몇 주마다 반복하라고 권한다.
같은 README의 개인정보 절은 `--update`가 최신 릴리스 번호도 GitHub에 물어본다고
적는다(`--no-version-check`로 끈다).
`--collect-android`는 동의를 받은 뒤 고정된 수집기를 내려받고,
메뉴의 광고 차단 시험은 기본 브라우저로 시험 페이지를 연다.
Windows에서는 `scan\run-scan.cmd`를 두 번 눌러 실행할 수 있고,
메뉴에서 Enter만 누르면 표준 검사가 시작된다.
제작자는 표준 검사에 15분쯤 걸린다고 적는다.

자주 쓰는 옵션은 다음과 같다.

```bash
python3 -X utf8 scan/zero-breach-toolkit.py --quick
python3 -X utf8 scan/zero-breach-toolkit.py --phone "FOLDER"
python3 -X utf8 scan/zero-breach-toolkit.py --json report.json
python3 -X utf8 scan/zero-breach-toolkit.py --share-json summary.json
```

검사 범위는 `--scan-type`으로 고른다.

| 값         | 읽는 범위                                                   |
| ---------- | ----------------------------------------------------------- |
| `default`  | 플랫폼이 지원하는 컴퓨터 검사와 파일 후보                   |
| `full`     | 데스크톱 앱의 웹 캐시 원본과 모든 확장자의 파일까지         |
| `targeted` | `--target`으로 고른 파일, 폴더, 드라이브, 브라우저 프로필만 |
| `browser`  | 이 계정의 브라우저 프로필과 Chromium 내장 앱만              |

`--preview`는 검사 없이 제안된 범위만 보여 주고,
`--extended-windows`는 이미 있는 Sysmon과 보안 프로세스 이벤트를 추가로 읽는다.
스크립트와 AI 비서를 위해 `--describe`는 도구가 하는 모든 검사와 종료 코드와
결과를 전달하는 규칙을 JSON으로 출력한다.

### 폰 검사

Android는 먼저 폰에서 개발자 옵션과 USB 디버깅을 켜야 한다.
그다음 AndroidQF로 수집본을 만들고, 그 폴더를 `--phone`에 넘긴다.
AndroidQF가 묻는 질문에는 SMS 백업만 받고, 시스템이 아닌 패키지만 내려받고,
신뢰 인증서로 서명된 앱 사본은 지우지 않는 쪽으로 답하라고 한다.

iPhone은 컴퓨터에 암호화 로컬 백업을 만든 뒤 그 폴더를 검사한다.
암호화 백업에는 이 도구가 확인하는 기록이 더 많이 들어 있다고 제작자는 설명한다.
iPad도 같은 방식이며, 검사는 항상 컴퓨터에서 돌고 폰이나 태블릿 안에서는
돌지 않는다.

`--collect-android`는 실험 기능이다.
공식 AndroidQF v1.8.3을 내려받아 고정된 SHA-256과 대조한 뒤,
소유자의 동의를 받고 수집 질문을 대신 진행한다.
제작자는 이것이 도구가 자기가 배포하지 않은 프로그램을 실행하는 유일한
지점이라고 적는다.
고정된 해시는 게시자가 낸 파일 그대로인지 확인할 뿐,
수집기 자체를 감사한 것은 아니라고도 밝힌다.

### 연습용 예시

`--training`은 가짜 Android 폰을 가짜 지표로 검사해서,
실제 검사가 필요해지기 전에
보고서 읽는 법을 익히게 한다.
예시는 `spyware`, `worth-a-look`, `clean`, `cellebrite` 네 가지이고,
보고서는 `TRAINING EXAMPLE - NOT A REAL CHECK`로 시작한다.
컴퓨터나 실제 폰이나 내려받은 지표는 읽지 않으며,
공유용 요약과 증거 묶음은 만들 수 없다.

## 결과 읽기

보고서는 요약으로 시작한다.
무엇이 발견되었고, 그것이 무엇을 뜻하며, 무엇을 해야 하고,
무엇을 검사하지 못했는지를 먼저 보여 준다.

발견 항목에는 증거 등급이 붙는다.
알려진 스파이웨어 파일이 기기에 있다는 것은 강한 증거이다.
저장된 웹 페이지가 스파이웨어 주소를 언급한다는 것은 약한 증거이며,
대개 그 스파이웨어를 다룬 기사이다.
제작자는 일치 횟수가 아니라 등급이 행동을 정한다고 적는다.
도구가 스스로 판단하지 못하는 것(스토어 밖에서 설치한 앱, 코드를 내려받은 명령,
백신 예외)은 발견이 아니라 살펴볼 항목(Worth a look)으로 따로 모이며,
각각 흔한 무해한 설명이 붙는다.

“Something matched”는 감염되었다는 뜻이 아니라 더 살펴보라는 뜻이다.
이때 아무것도 지우지 말고, 보고서가 가리키는 주소를 방문하지도 말라고 안내한다.

스크립트가 쓸 종료 코드는 다음과 같다.

| 코드 | 뜻                                                 |
| ---- | -------------------------------------------------- |
| `0`  | 조치할 일치가 없고 기록된 검사 공백도 없다         |
| `1`  | 설정, 인자, 출력 오류                              |
| `2`  | 저장된 참조를 넘는 일치가 있다                     |
| `3`  | 조치할 일치는 없지만 검사나 지표 출처가 불완전했다 |
| `4`  | 검사 없이 시작 메뉴를 닫았다                       |

어떤 종료 코드도 기기가 안전하다는 증명이 아니라고 제작자는 분명히 적는다.
검사하지 못한 부분은 아무것도 확인해 주지 못했다는 뜻이므로 반드시 읽으라는 것이
보고서의 핵심 당부이다.

## 검증하기

제작자는 프로젝트가 익명이므로 말을 믿지 말고 재현할 수 있는 것만 믿으라고 쓴다.
소스에서 직접 실행하면 도구가 실행하는 모든 줄이 내려받은 복사본 안에 있고,
컴파일하거나 따로 가져오는 것이 없다.

릴리스에 붙은 단일 파일 `zero-breach-toolkit.py`는 같은 소스에서 생성된다.
릴리스 태그에서 다시 빌드해 해시를 비교하는 방법이 안내되어 있다.

```bash
git checkout v2.0.0
python build/bundle.py
python -c "import hashlib; print(hashlib.sha256(open('dist/zero-breach-toolkit.py','rb').read()).hexdigest())"
```

v2.0.1의 파일은 2,860,326바이트이고 SHA-256은
`0044b2773561711d74bbb432034d34b429a5cbe0d28d30d4747389487cbaabac`이다.
릴리스마다 공개된 크기와 해시가 기준이라고 README는 적는다.
빌드가 결정적(deterministic)이어서 해시가 같으면 공개된 파일에 그 소스만 들어
있다는 것이 제작자의 설명이다.

저장소의 `docs/VERIFYING.md`는 두 번째 방법으로 GPG 서명을 든다.
릴리스의 파일과 `SHA256SUMS.txt`에 ArchiveGenocide의 Ed25519 릴리스
서명 키로 만든
분리 서명이 붙어 있고, 키 지문은
`C24E C92B 12D6 670A 2516 065F 9B4D 5754 99AF A53C`라고 적혀 있다.
키를 믿기 전에 이 지문을 ArchiveGenocide의 검증 페이지나 이미 믿는 다른 기록과
견주라고 한다.

내려받는 프로그램은 다르게 검증한다.
GitHub Actions가 릴리스 태그에서 빌드하고 단일 파일 빌드와 대조한 뒤,
어떤 워크플로와 커밋과 러너가 만들었는지를 서명된 증명(attestation)으로 남긴다.
PyInstaller 결과는 바이트가 재현되지 않아서,
다시 빌드해 견주는 방법은 단일 파일에만
적용되고 프로그램은 증명이 검사 수단이다.
서명된 Windows 프로그램은 없고, 프로젝트가 익명인 동안은 만들 계획도
없다고 한다.
코드 서명 인증서에는 실명 법적 신원이 필요하기 때문이다.

지표 갱신은 별도의 신뢰 경로라고 VERIFYING.md는 적는다.
`--update`는 정해진 공식 출처에서 HTTPS로 목록을 받아 형식을 확인하고 파일마다
SHA-256을 기록하지만, 프로젝트가 그 목록에 서명하지는 않는다.
목록은 각 게시자의 저장소만큼만 믿을 수 있고, 릴리스 서명은 목록을 덮지 않는다.

## 한계

제작자가 적은 한계는 네 가지이다.
공개된 지표만 찾으므로 새롭거나 공개되지 않은 스파이웨어는 찾지 못한다.
스파이웨어는 표적마다 다시 만들어지는 일이 많고 흔적은 몇 주 안에 사라진다.
Android 검사는 수집본에 든 것만, iPhone 검사는 지원하는 항목만 본다.
전문가의 포렌식 조사를 대신하지 못한다.

개인정보 면에서는 전체 보고서에 사용자 이름, 파일 경로, 검색 기록,
SMS 발신자와 메시지 일부가 들어갈 수 있다고 경고한다.
`--share-json`은 개수, 범위 표시, 판정,
고정된 조언만 쓰고 지표 값과 날짜는 뺀다.
`--evidence-bundle`이 만드는 ZIP은 암호화되지 않으며, 원본 파일은 128개,
개당 64 MiB, 합계 256 MiB까지 담긴다.

저장소의 `dist/` 폴더에는 지표에 나온 광고와 추적 도메인의 차단 목록이 세 가지
형식(uBlock Origin용, hosts 파일, dnsmasq용)으로 들어 있다.
README는 차단이 감염을 탐지하지 못하는 임시방편이라고 적는다.

코드는 Apache License 2.0이고, 직접 고른 지표 파일은 CC0 1.0이다.
`--update`로 받은 지표 목록은 각 게시자의 조건을 따른다.

## 비평

### 쉬운 길과 검증된 길이 여전히 다른 바이트를 가리킨다

README에는 이제 길이 세 개 있다.
릴리스에서 프로그램을 받는 길, ZIP으로 main을 받아 Python으로 돌리는
단계별 안내,
태그를 체크아웃해 단일 파일을 재빌드하는 길이다.
비전문가용 단계별 안내는 여전히 Download ZIP을 눌러 `Zero-Breach-Toolkit-main`
폴더를 쓰라고 한다.
이 ZIP은 main 브랜치의 그 시점 코드이고, 저장소는 2026-10-25에 만들어졌으며
2026-11-01에도 코드가 푸시되었으므로 main은 며칠 단위로 움직이는 대상이다.[^api]
반면 해시로 재현할 수 있다고 제작자가 설명하는 것은 릴리스 태그의 단일 파일이다.

프로그램 쪽의 검증은 GitHub CLI를 설치해 `gh attestation verify`를
실행할 수 있는
사람에게 열려 있다.
README가 맨 앞에 내세운 독자인 기자와 활동가가 이 단계를 밟을지는 알 수 없다.
게다가 프로그램은 서명되지 않아서 처음 열 때 경고를 누르고
넘어가라고 안내받는다.
경고를 넘어가는 습관을 검증보다 먼저 가르치는 구조이다.
안내서의 쉬운 경로와 검증 경로가 서로 만나지 않는다는 점이 이 도구의 가장 큰
구조적 틈이다.

### 서명이 보증하는 것은 신원이 아니라 연속성이다

릴리스가 GPG로 서명된다는 설명은 안심을 주지만,
서명 키의 주인이 익명이라는 점은 그대로이다.
VERIFYING.md 스스로 서명은 누가 이 바이트를 냈는지를 증명할 뿐
버그가 없다는 뜻은
아니라고 적는다.
키 지문을 견주라고 안내한 검증 페이지는 같은 게시자의 도메인에 있는 것이므로,
독립적인 기록이 따로 없으면 지문을 확인하는 일이 순환한다.
이 도구는 사용자의 브라우저 기록과 메시지 일부까지 읽으므로,
제작자를 확인할 수 없다는 사실이 신뢰의 근거를 약하게 만드는 정도는 일반
도구보다 크다.

### 지표 갱신은 검증된 코드 밖에서 들어온다

도구 코드는 재빌드와 서명으로 확인할 수 있지만, 탐지의 내용물인 지표 목록은
`--update`가 받아 오는 외부 파일이고 프로젝트가 서명하지 않는다고 VERIFYING.md가
인정한다.
받은 목록은 형식이 맞는지와 SHA-256 기록으로만 보호된다.
출처 저장소가 오염되거나 목록이 바뀌면, 검증된 도구가 검증되지 않은 판정을 낼 수
있다.
이는 탐지 도구 전반의 문제이지만, 이 프로젝트가 검증 가능성을 가장 큰 장점으로
내세우기 때문에 그 범위가 코드까지라는 점을 분명히 읽어야 한다.

### 네트워크 차단의 보증 범위가 좁다

“검사 중에는 네트워크 요청이 없다”는 약속은 Python 호출을 막는 방식으로
지켜지며, 운영체제 수준의 차단이 아니라고 제작자 스스로 밝힌다.
그러면 이 약속이 지켜지는지는 결국 소스를 읽어 확인해야 하고,
사용자가 실제로 실행하는 것이 소스 그대로가 아닌 프로그램일 때는 확인이 더
어렵다.
검사하는 동안 방화벽으로 네트워크를 끊는 것은 사용자가 직접 할 수 있는 더 단단한
확인이지만, 안내서에는 그런 권고가 없다.
README 안에서도 `--update`가 유일한 인터넷 단계라는 설명과, 같은 단계가 릴리스
번호를 조회한다는 설명, 다른 명령이 수집기를 내려받는다는 설명이 나뉘어 있어서
어디까지가 검사 중인지를 한 문장으로 말하기 어렵다.

### 안내서 안의 숫자와 답이 서로 맞지 않는다

Android 수집 질문에 대한 답이 두 곳에서 다르다.
단계별 안내는 침입 로그(Intrusion Logs)를 “No”로 답하라고 하고,
상세 안내는 침입 로깅을 켜 두었다면 “No”가 아니라고 단서를 단다.
상세 안내는 파일 해시를 “Yes”로 하면 지문 검사가 늘지만 느리고 일부 폰에서는
수집이 멈출 수 있다고 덧붙이는데, 단계별 안내에는 이 설명이 없다.
쉬운 경로가 덜 철저한 경로가 되는 것은 의도된 선택일 수 있으나,
그 대가를 쉬운 경로 안에서는 알 수 없다.

파일 크기 한도도 README 안에서 맞지 않는다.
기본 검사는 512 MiB까지라고 하면서, 전체(`full`) 검사 설명에서는 120 MiB 한도가
그대로 남는다고 적는다.
어느 쪽이 지금 코드에 맞는지는 이 문서가 코드를 읽어 확인하지 않았다.

## 기억할 원칙

### 검사하지 못한 것을 결과의 일부로 만든다

이 도구의 설계에서 가장 옮겨 쓸 만한 것은 종료 코드 `3`이다.
일치가 없는 것과 아무것도 확인하지 못한 것을 한 가지 “깨끗함”으로 합치지 않고,
공백이 있으면 별도의 코드로 돌려준다.
부정적 결과를 내는 도구는 무엇을 보지 못했는지를 같은 비중으로 보고해야 한다.

### 인터넷을 쓰는 단계와 분석하는 단계를 분리한다

지표 내려받기는 `--update`에, 분석은 오프라인에 두고 둘을 한 명령에 섞지 않는다.
사용자는 네트워크가 열리는 순간을 스스로 고를 수 있고,
분석 코드는 네트워크 없이 검증할 수 있다.
민감한 데이터를 읽는 도구를 만들 때 먼저 옮겨 올 구조이다.

### 신뢰를 요구하는 안내와 검증하는 안내를 같은 경로에 둔다

쉬운 안내가 검증되지 않은 바이트를 가리키고 검증 안내가 다른 바이트를 가리키면,
대부분의 사용자는 검증되지 않은 쪽을 쓴다.
검증의 대상이 되는 파일과 안내서가 내려받으라고 하는 파일은 같아야 한다.
