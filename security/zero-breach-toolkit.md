# Zero Breach Toolkit: 알려진 mercenary spyware의 흔적을 오프라인으로 찾는 도구

<https://github.com/interplains/Zero-Breach-Toolkit>

GN 토론: <https://news.hada.io/topic?id=36362>

## 소개

Zero Breach Toolkit은 컴퓨터, Android 폰,
iPhone 백업에서 알려진 스파이웨어의 흔적을 찾는 무료 오픈소스 도구이다.
대상은 Pegasus, Predator, Graphite, Candiru처럼 민간 업체가 판매하는
스파이웨어(mercenary spyware)이다.
제작자는 archivegenocide라는 이름을 쓰며,
이 저장소가 기존 프로젝트 Zero Breach 위에 만들어졌다고 밝힌다.
저장소는 2026-10-25에 만들어졌고 2026-11-01 기준 별 4,043개,
포크 429개이다.[^repo-metadata]

제작자는 이 도구의 약속을 세 가지로 요약한다.
첫째, 읽기 전용이다.
원본 증거와 시스템 설정을 바꾸지 않고, 임시 데이터베이스 사본과 사용자가 요청한
보고서만 쓴다.
둘째, 검사 중에는 네트워크 요청을 하지 않는다.
스파이웨어 주소를 조회하지 않고 업로드 기능도 없으며,
Python의 네트워크 호출을 막는다.
제작자는 이것이 운영체제 수준의 네트워크 샌드박스는 아니라고 스스로 적는다.
셋째, 한계를 보고서에 적는다.
무엇이 발견되었는지, 증거가 얼마나 강한지, 무엇을 검사하지 못했는지를 모두 쓰고,
깨끗한 결과를 안전의 증명으로 내놓지 않는다.

도구를 돌리기 전에 전문가의 도움을 먼저 받으라는 안내도 맨 앞에 있다.
지금 표적이 되고 있다고 생각하는 기자와 활동가는 Access Now의 디지털 보안
헬프라인이나 Amnesty International의 Security Lab에 연락하라고 한다.
이 도구를 먼저 돌릴 필요는 없다고도 적는다.

## 무엇을 검사하는가

검사 대상은 기기 종류에 따라 다르다.
아래 내용은 모두 제작자가 설명하는 검사 범위이며, 독립적으로 확인한 것이 아니다.

| 대상          | 읽는 것                                                                                                                                           | 한계로 적힌 점                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Windows       | 브라우저 기록, 쿠키, 다운로드 출처 표시(Mark of the Web), PowerShell 로그, Defender 기록, Prefetch와 Amcache, DNS 캐시, hosts 파일, 시작 프로그램 | 관리자 권한이 필요 없다. 잠기거나 지원되지 않는 기록은 검사 공백으로 보고한다 |
| macOS와 Linux | 같은 브라우저 계열, Safari 기록, 시작 설정(LaunchAgent와 systemd 등), 셸 기록, 시스템 로그                                                        | Safari를 읽으려면 터미널에 전체 디스크 접근 권한이 필요하다                   |
| Android       | AndroidQF가 만든 수집본: 설치된 앱, 설치 이력, 로그, 복호화된 침입 로그, SMS 링크                                                                 | 폰과 직접 통신하지 않는다. 수집본에 든 것만 본다                              |
| iPhone        | Finder, Apple Devices, iTunes의 로컬 백업(암호화 포함), 추출된 파일 시스템, sysdiagnose                                                           | 지원하는 항목과 로컬 증거만 본다. 기기를 직접 수집하지 않는다                 |

파일 지문(해시) 검사는 `.dll`, `.exe`, `.sys` 같은 확장자의 파일을 120 MiB까지
대상으로 한다.
컴퓨터 검사는 공개된 인프라나 파일 흔적을 찾을 수 있을 뿐,
폰이 감염되었는지는 알려 주지 못한다고 제작자는 적는다.

비교 기준이 되는 지표(indicator)는 29개 출처에서 모은 약 12,400개이다.
출처에는 Amnesty International의 Security Lab,
Mobile Verification Toolkit(MVT) 프로젝트, Citizen Lab, Echap이 들어 있다.
Citizen Lab 보고서에서 손으로 가려 뽑은 Candiru와 Graphite 지표는 저장소에 들어
있어 오프라인에서도 쓰인다.
나머지는 `--update` 명령이 정해진 공식 출처 목록에서 내려받는다.

## 실행하기

필요한 것은 Python 3.8 이상뿐이다.
관리자 권한도, 추가 패키지도 필요 없다.
암호화된 iPhone 백업을 읽을 때만 선택 패키지 `cryptography`가 필요하며,
자동으로 설치되지 않는다.

가장 짧은 경로는 다음과 같다.

```bash
git clone https://github.com/interplains/Zero-Breach-Toolkit.git
cd Zero-Breach-Toolkit
python3 -X utf8 scan/zero-breach-toolkit.py --update
python3 -X utf8 scan/zero-breach-toolkit.py
```

`--update`는 검사 흐름에서 인터넷을 쓰는 유일한 단계이다.
없으면 작은 내장 지표 묶음만 쓰이므로 제작자는 몇 주마다 반복하라고 권한다.
Windows에서는 `scan\run-scan.cmd`를 두 번 눌러 실행할 수 있고,
메뉴에서 Enter만 누르면 표준 검사가 시작된다.
제작자는 표준 검사에 15분쯤 걸린다고 적는다.

자주 쓰는 옵션은 다음과 같다.

```bash
python3 -X utf8 scan/zero-breach-toolkit.py --quick
python3 -X utf8 scan/zero-breach-toolkit.py --phone "FOLDER"
python3 -X utf8 scan/zero-breach-toolkit.py --json report.json
python3 -X utf8 scan/zero-breach-toolkit.py --share-json summary.json
```

검사 범위는 `--scan-type`으로 고른다.

| 값         | 읽는 범위                                                   |
| ---------- | ----------------------------------------------------------- |
| `default`  | 플랫폼이 지원하는 컴퓨터 검사와 파일 후보                   |
| `full`     | 데스크톱 앱의 웹 캐시 원본과 모든 확장자의 파일까지         |
| `targeted` | `--target`으로 고른 파일, 폴더, 드라이브, 브라우저 프로필만 |
| `browser`  | 이 계정의 브라우저 프로필과 Chromium 내장 앱만              |

### 폰 검사

Android는 먼저 폰에서 개발자 옵션과 USB 디버깅을 켜야 한다.
그다음 AndroidQF로 수집본을 만들고, 그 폴더를 `--phone`에 넘긴다.
AndroidQF가 묻는 질문에는 SMS 백업만 받고, 시스템이 아닌 패키지만 내려받고,
신뢰 인증서로 서명된 앱 사본은 지우지 않는 쪽으로 답하라고 한다.

iPhone은 컴퓨터에 암호화 로컬 백업을 만든 뒤 그 폴더를 검사한다.
암호화 백업에는 이 도구가 확인하는 기록이 더 많이 들어 있다고 제작자는 설명한다.
iPad도 같은 방식이며, 검사는 항상 컴퓨터에서 돌고 폰이나 태블릿 안에서는
돌지 않는다.

`--collect-android`는 실험 기능이다.
공식 AndroidQF v1.8.3을 내려받아 고정된 SHA-256과 대조한 뒤,
소유자의 동의를 받고 수집 질문을 대신 진행한다.
제작자는 이것이 도구가 자기가 배포하지 않은 프로그램을 실행하는 유일한
지점이라고 적는다.
고정된 해시는 게시자가 낸 파일 그대로인지 확인할 뿐,
수집기 자체를 감사한 것은 아니라고도 밝힌다.

## 결과 읽기

보고서는 요약으로 시작한다.
무엇이 발견되었고, 그것이 무엇을 뜻하며, 무엇을 해야 하고,
무엇을 검사하지 못했는지를 먼저 보여 준다.

발견 항목에는 증거 등급이 붙는다.
알려진 스파이웨어 파일이 기기에 있다는 것은 강한 증거이다.
저장된 웹 페이지가 스파이웨어 주소를 언급한다는 것은 약한 증거이며,
대개 그 스파이웨어를 다룬 기사이다.
제작자는 일치 횟수가 아니라 등급이 행동을 정한다고 적는다.

“Something matched”는 감염되었다는 뜻이 아니라 더 살펴보라는 뜻이다.
이때 아무것도 지우지 말고, 보고서가 가리키는 주소를 방문하지도 말라고 안내한다.

스크립트가 쓸 종료 코드는 다음과 같다.

| 코드 | 뜻                                                 |
| ---- | -------------------------------------------------- |
| `0`  | 조치할 일치가 없고 기록된 검사 공백도 없다         |
| `1`  | 설정, 인자, 출력 오류                              |
| `2`  | 저장된 참조를 넘는 일치가 있다                     |
| `3`  | 조치할 일치는 없지만 검사나 지표 출처가 불완전했다 |
| `4`  | 검사 없이 시작 메뉴를 닫았다                       |

어떤 종료 코드도 기기가 안전하다는 증명이 아니라고 제작자는 분명히 적는다.
검사하지 못한 부분은 아무것도 확인해 주지 못했다는 뜻이므로 반드시 읽으라는 것이
보고서의 핵심 당부이다.

## 검증하기

제작자는 프로젝트가 익명이므로 말을 믿지 말고 재현할 수 있는 것만 믿으라고 쓴다.
소스에서 직접 실행하면 도구가 실행하는 모든 줄이 내려받은 복사본 안에 있고,
컴파일하거나 따로 가져오는 것이 없다.

릴리스에 붙은 단일 파일 `zero-breach-toolkit.py`는 같은 소스에서 생성된다.
릴리스 태그에서 다시 빌드해 해시를 비교하는 방법이 안내되어 있다.

```bash
git checkout v0.1.15
python build/bundle.py
python -c "import hashlib; print(hashlib.sha256(open('dist/zero-breach-toolkit.py','rb').read()).hexdigest())"
```

v0.1.15의 파일은 986,053바이트이고 SHA-256은
`4ebe1f3043e5efd056e201143bed8d4a44c3b937afde19f7b89e240cbf4a32f9`이다.
빌드가 결정적(deterministic)이어서 해시가 같으면 공개된 파일에 그 소스만 들어
있다는 것이 제작자의 설명이다.
릴리스는 GPG로 서명되지만, 서명된 Windows 실행 파일은 없고 프로젝트가 익명인
동안은 만들 계획도 없다고 한다.
코드 서명 인증서에는 실명 법적 신원이 필요하기 때문이다.

## 한계

제작자가 적은 한계는 네 가지이다.
공개된 지표만 찾으므로 새롭거나 공개되지 않은 스파이웨어는 찾지 못한다.
스파이웨어는 표적마다 다시 만들어지는 일이 많고 흔적은 몇 주 안에 사라진다.
Android 검사는 수집본에 든 것만, iPhone 검사는 지원하는 항목만 본다.
전문가의 포렌식 조사를 대신하지 못한다.

개인정보 면에서는 전체 보고서에 사용자 이름, 파일 경로, 검색 기록,
SMS 발신자와 메시지 일부가 들어갈 수 있다고 경고한다.
`--share-json`은 개수, 범위 표시, 판정,
고정된 조언만 쓰고 지표 값과 날짜는 뺀다.
`--evidence-bundle`이 만드는 ZIP은 암호화되지 않으며, 원본 파일은 128개,
개당 64 MiB, 합계 256 MiB까지 담긴다.

코드는 Apache License 2.0이고, 직접 고른 지표 파일은 CC0 1.0이다.
`--update`로 받은 지표 목록은 각 게시자의 조건을 따른다.

## 비평

### 안내서가 가리키는 코드와 검증이 보장하는 코드가 다르다

비전문가용 안내서는 GitHub의 Download ZIP을 눌러 `Zero-Breach-Toolkit-main`
폴더를 쓰라고 한다.
이 ZIP은 main 브랜치의 그 시점 코드이다.
반면 해시로 검증할 수 있다고 제작자가 설명하는 것은 릴리스 태그의 단일 파일이다.
저장소는 2026-10-25에 만들어졌고 2026-11-01에도 코드가 푸시되었으므로,
main은 며칠 단위로 움직이는 대상이다.[^repo-metadata]
따라서 안내서를 따라 하는 사용자는 재현 가능한 빌드가 보호해 주는 바이트가
아니라 그날의 main을 실행하게 된다.

익명 프로젝트가 “말을 믿지 말라”고 하는 태도는 옳다.
그러나 그 검증 경로는 git으로 태그를 체크아웃하고 빌드 스크립트를 돌릴 수 있는
사람에게 열려 있다.
제작자가 맨 앞에 내세운 독자인 기자와 활동가가 이 경로를 밟기는 어렵다.
안내서의 20분짜리 경로와 검증 경로가 서로 만나지 않는다는 점이 이 도구의 가장 큰
구조적 틈이다.

### 서명은 신원이 아니라 연속성만 보여 준다

릴리스가 GPG로 서명된다는 설명은 안심을 주지만,
서명 키의 주인이 익명이라는 점은 그대로이다.
이는 제작자의 글에 근거한 추정이다.
서명이 보여 줄 수 있는 것은 이전 릴리스와 같은 키가 서명했다는 연속성이고,
그 키를 가진 사람이 누구이며 믿을 만한지는 서명이 말해 주지 않는다.
이 도구는 사용자의 브라우저 기록과 메시지 일부까지 읽으므로,
제작자를 확인할 수 없다는 사실이 신뢰의 근거를 약하게 만드는 정도는 일반
도구보다 크다.

### 네트워크 차단의 보증 범위가 좁다

“검사 중에는 네트워크 요청이 없다”는 약속은 Python 호출을 막는 방식으로
지켜지며, 운영체제 수준의 차단이 아니라고 제작자 스스로 밝힌다.
그러면 이 약속이 지켜지는지는 결국 소스를 읽어 확인해야 하고,
그 소스는 앞의 비평에서 본 것처럼 사용자가 실제로 실행하는 코드와 일치한다고
보장되지 않는다.
검사하는 동안 방화벽으로 네트워크를 끊는 것은 사용자가 직접 할 수 있는 더 단단한
확인이지만, 안내서에는 그런 권고가 없다.

### 단계별 안내와 상세 안내가 서로 다르다

Android 수집 질문에 대한 답이 두 곳에서 조금 다르다.
단계별 안내는 침입 로그(Intrusion Logs)를 “No”로 답하라고 하고,
상세 안내는 침입 로깅을 켜 두었다면 “No”가 아니라고 단서를 단다.
상세 안내는 파일 해시를 “Yes”로 하면 지문 검사가 늘지만 느리고 일부 폰에서는
수집이 멈출 수 있다고 덧붙이는데, 단계별 안내에는 이 설명이 없다.
쉬운 경로가 덜 철저한 경로가 되는 것은 의도된 선택일 수 있으나,
그 대가를 쉬운 경로 안에서는 알 수 없다.

## 기억할 원칙

### 검사하지 못한 것을 결과의 일부로 만든다

이 도구의 설계에서 가장 옮겨 쓸 만한 것은 종료 코드 `3`이다.
일치가 없는 것과 아무것도 확인하지 못한 것을 한 가지 “깨끗함”으로 합치지 않고,
공백이 있으면 별도의 코드로 돌려준다.
부정적 결과를 내는 도구는 무엇을 보지 못했는지를 같은 비중으로 보고해야 한다.

### 인터넷을 쓰는 단계와 분석하는 단계를 분리한다

지표 내려받기는 `--update`에, 분석은 오프라인에 두고 둘을 한 명령에 섞지 않는다.
사용자는 네트워크가 열리는 순간을 스스로 고를 수 있고,
분석 코드는 네트워크 없이 검증할 수 있다.
민감한 데이터를 읽는 도구를 만들 때 먼저 옮겨 올 구조이다.

### 신뢰를 요구하는 안내와 검증하는 안내를 같은 경로에 둔다

쉬운 안내가 검증되지 않은 바이트를 가리키고 검증 안내가 다른 바이트를 가리키면,
대부분의 사용자는 검증되지 않은 쪽을 쓴다.
검증의 대상이 되는 파일과 안내서가 내려받으라고 하는 파일은 같아야 한다.
