# fail2ban: 로그를 읽어 방화벽 규칙을 넣는 데몬

<https://github.com/fail2ban/fail2ban>

HN 토론: <https://news.ycombinator.com/item?id=37795100> (160점, 128개 댓글)

## 소개

fail2ban은 `/var/log/auth.log` 같은 로그 파일을 읽어
인증 실패를 반복하는 IP를 찾아내고, 시스템 방화벽 규칙을 갱신해 그 IP의 새 연결을 일정 시간 동안 거부하는 데몬이다.
sshd와 Apache를 비롯한 표준 로그는 설치 직후 바로 읽을 수 있고,
원하는 로그와 원하는 오류 패턴을 직접 지정하는 것도 어렵지 않다.

2011년에 GitHub으로 옮겨 온 프로젝트이며 별 18,653개, 포크 1,499개, 미해결 이슈 275개를 기록하고 있다.
언어는 Python이고 라이선스는 GPL v2 이상이다.
0.10부터 IPv6 주소 매칭을 지원한다.

README가 스스로 그어 두는 경계선이 이 도구를 이해하는 출발점이다.
fail2ban은 잘못된 인증 시도의 비율을 낮출 수는 있지만 약한 인증이 만드는 위험 자체를 없애지는 못하며,
정말로 서비스를 보호하고 싶다면 2단계 인증이나 공개키 인증만 쓰도록 구성하라고 적혀 있다.
즉 이 도구가 파는 것은 보안이 아니라 소음 감소와 속도 제한이고, 저장소 자신이 그렇게 말한다.

실행 방식에도 규칙이 있다.
`fail2ban-server`를 직접 부르지 말고 항상 `fail2ban-client`를 쓰라고 README가 명시한다.

```bash
fail2ban-client -h        # 설치 확인
fail2ban-client version   # 버전 확인
fail2ban-client status    # 동작 중인 jail 목록
```

## 동작 방식

구성 요소는 셋이다.
로그에서 실패 줄을 찾아내는 필터(filter), 차단을 실행하는 액션(action),
그리고 이 둘을 로그 경로와 임계값에 묶는 jail이다.

한 번의 차단이 일어나는 과정을 시간 순으로 따라가면 이렇다.

1. 백엔드가 로그 파일이나 systemd 저널의 변경을 감지한다.
2. 필터의 정규식이 새로 들어온 줄에서 `<HOST>` 태그로 IP를 뽑아낸다.
3. 같은 IP의 실패가 `findtime` 안에 `maxretry`회 쌓이면 티켓이 만들어진다.
4. 액션이 실행되어 방화벽에 거부 규칙이 들어간다.
5. `bantime`이 지나면 규칙이 제거된다.

백엔드는 `pyinotify`, `polling`, `systemd`, `auto` 중에서 고른다.
`auto`는 `pyinotify`를 먼저 시도하고 없으면 `polling`으로 내려간다.
`systemd` 백엔드를 쓸 때는 `logpath` 대신 필터의 `journalmatch`가 어떤 저널 항목을 볼지 결정한다.

여기서 자주 놓치는 것은 fail2ban이 연결을 직접 막지 않는다는 점이다.
막는 주체는 언제나 방화벽이고 fail2ban은 그 규칙을 넣고 빼는 쪽이다.
따라서 방화벽 백엔드가 무엇인지, 규칙이 어느 체인에 들어가는지, 재부팅 후 규칙이 어떻게 되는지가 전부 운영의 문제로 남는다.

## 설정하기

`/etc/fail2ban/jail.conf`는 직접 고치지 않는 것이 원칙이다.
배포판 업데이트가 덮어쓰기 때문이며, 설정은 `jail.local`이나 `jail.d/` 아래의 `.local` 파일에 둔다.

```ini
# /etc/fail2ban/jail.local

[DEFAULT]
bantime  = 1h        # 첫 차단 길이. bantime.increment를 켜면 이 값이 기준이 된다
findtime = 10m       # 실패를 세는 창
maxretry = 5         # 이 횟수를 넘으면 차단
ignoreip = 127.0.0.1/8 ::1 203.0.113.0/24   # 내 사무실 대역을 반드시 넣는다

# 재범에게 점점 긴 차단을 주는 설정
bantime.increment   = true
bantime.multipliers = 1 5 30 60 300 720 1440 2880
bantime.maxtime     = 4w
bantime.rndtime     = 5m     # 해제 시각을 흩어 봇의 정확한 재시도 계산을 막는다

[sshd]
enabled = true
```

설정을 바꾼 뒤에는 재시작 대신 다시 읽기로 충분하다.

```bash
fail2ban-client reload          # 전체 설정 다시 읽기
fail2ban-client reload sshd     # 특정 jail만
fail2ban-client status sshd     # 현재 차단된 IP 확인
fail2ban-client set sshd unbanip 203.0.113.9   # 수동 해제
```

1.1.1부터 `ignoreip`에 파일을 지정할 수 있다.
파일 안의 항목은 쉼표나 공백이나 줄바꿈으로 구분하며 `#`나 `;` 뒤는 주석으로 무시된다.
파일은 첫 차단 시점에 지연 로딩되고 이후 갱신이 자동 반영되므로,
허용 대역이 자주 바뀌는 환경에서 설정 다시 읽기를 반복하지 않아도 된다.

```ini
[DEFAULT]
ignoreip = file:/etc/fail2ban/allowlist.txt
```

## 값 정하기

기본값은 보수적으로 잡혀 있다.
기본값을 그대로 쓰는 것이 나쁜 선택은 아니지만, 왜 그 값인지를 모르면 언제 바꿔야 할지도 알 수 없다.

| 항목         | 기본값            | 근거와 조정 기준                                                                     |
| ------------ | ----------------- | ------------------------------------------------------------------------------------ |
| `bantime`    | 10m               | 짧다. 자동 봇을 쫓아내는 데는 충분하지만 재범을 막지 못하므로 증가 설정과 함께 쓴다  |
| `findtime`   | 10m               | 이 창을 늘리면 느린 분산 공격을 잡지만 오탐도 함께 늘어난다                          |
| `maxretry`   | 5                 | 사람이 비밀번호를 잘못 치는 횟수보다 넉넉해야 한다. 공개키 전용이라면 더 낮춰도 된다 |
| `maxmatches` | `maxretry`와 동일 | 티켓에 보관할 매치 수이며 알림 액션에서 `<matches>` 태그로 쓰인다                    |
| `port`       | 0:65535           | `DEFAULT` 수준의 값이라 jail마다 덮어써야 한다                                       |
| `protocol`   | tcp               | UDP 서비스를 보호한다면 반드시 바꾼다                                                |

`bantime.increment`를 켜면 차단 시간이 재범 횟수에 따라 자라며,
기본 공식은 `ban.Time * (1<<(ban.Count if ban.Count<20 else 20)) * banFactor`로 1, 2, 4, 8, 16배로 늘어난다.
`bantime.multipliers`를 직접 주면 공식 대신 그 목록을 쓴다.
`bantime.overalljails`를 켜면 같은 IP를 모든 jail에 걸쳐 조회하므로,
한 서비스에서 걸린 상대가 다른 서비스에서도 긴 차단을 받는다.

측정해서 값을 고치는 기준은 둘이다.
차단 후에도 같은 IP가 계속 돌아온다면 `bantime`이 짧거나 증가 설정이 꺼져 있는 것이고,
정상 사용자가 걸린다면 `maxretry`가 낮거나 필터가 과하게 잡는 것이다.

## 1.1.1에서 달라진 것

1.0.2가 2022년 11월, 1.1.0이 2024년 4월, 1.1.1이 2026년 8월에 나왔다.
릴리스 간격이 2년 안팎인 프로젝트이므로 배포판 패키지와 상류 버전의 차이가 클 수 있다.

가장 크게 바뀐 것은 기본 차단 액션이다.
기본 차단 액션을 `jail.conf`가 아니라 `paths-*.conf`에서 지정하도록 바뀌었고,
표준 fail2ban이 `paths-debian.conf`를 포함하므로 기본 액션이 `nftables`가 되었다.
`iptables-multiport`를 전제로 만든 커스텀 액션이 있다면 이 변화를 확인해야 한다.
같은 릴리스에서 `action.d/iptables.conf`가 여러 체인을 지원하도록 다시 쓰였고,
그 과정에서 사용자가 파생시킨 액션이 호환되지 않을 수 있다고 ChangeLog가 명시한다.
`<chain>`을 `$chain`으로 바꾸는 식의 태그 교체가 필요하다.

sshd와 postfix의 기본 백엔드도 `systemd`로 바뀌었다.
`systemd` 백엔드에는 `rotated` 파라미터가 새로 생겼고 기본값은 `false`다.
회전된 저널 파일을 무시해 jail당 파일 디스크립터를 1~2개 수준으로 줄이며,
이는 저널 파일이 많을 때 발생하던 “too many open files” 문제를 막기 위한 조치다.

그 밖에 실무에서 바로 쓸 만한 추가가 둘 있다.
`skip_if_nologs`는 `logpath`에 해당하는 파일이 없을 때 그 jail만 건너뛰고 나머지를 계속 띄운다.
`fail2ban-regex`에 `-i`(`--invert`) 옵션이 생겨 매치되지 않은 줄을 출력할 수 있다.

## 확인하기

필터를 먼저 검증하지 않고 jail을 켜는 것이 가장 흔한 실수다.
`fail2ban-regex`는 실제 로그와 필터를 맞춰 보고 몇 줄이 잡혔는지 보여 준다.

```bash
# 실제 로그와 jail 설정을 맞춰 본다 (jail 이름을 주면 jail 설정을 먼저 쓴다)
fail2ban-regex /var/log/auth.log sshd

# 필터 파일 자체를 시험하려면 확장자를 붙인다
fail2ban-regex /var/log/auth.log sshd.conf

# 매치되지 않은 줄을 보고 빠뜨린 패턴을 찾는다 (1.1.1 이상)
fail2ban-regex -i -o /var/log/auth.log sshd.conf
```

방화벽 쪽 확인은 별개로 해야 한다.

```bash
# nftables 기본 액션을 쓰는 경우 실제로 규칙이 들어갔는지 본다
sudo nft list table inet f2b-table

# iptables 계열이라면
sudo iptables -L -n | grep -i f2b
```

`fail2ban-client status sshd`가 차단을 보고하는데 방화벽에 규칙이 없다면
액션이 실패하고 있는 것이며, 이 상태는 로그만 보면 정상처럼 보인다.

## 트레이드오프

### 차단 길이를 늘리면 자기 자신을 가둘 확률도 함께 늘어난다

긴 `bantime`은 재범을 줄이지만 오탐의 대가도 그만큼 길어진다.
HN 스레드에서 kevingadd는 잘못 설정한 fail2ban이 자기 IP를 막아 버려서
호스팅 업체의 긴급 셸로 들어가야 했다고 적었고,[^kevingadd]
eco는 그것이 우리 모두가 거치는 통과 의례라고 답했다.[^eco]

`ignoreip`에 관리 대역을 넣는 것이 표준 해법이지만 이것도 완전하지 않다.
집이나 이동 중의 IP는 미리 알 수 없고, 동적 IP라면 넣어 둔 값이 남의 주소가 되어 있을 수도 있다.
결국 긴 차단을 쓰려면 차단과 무관한 접근 경로를 하나 남겨 두어야 하며,
그것은 콘솔 접근이거나 별도 관리 네트워크다.
이 경로가 없다면 `bantime`을 늘리는 선택은 안전하지 않다.

### 로그를 읽는 방식은 유연하지만 지연과 취약점을 함께 가져온다

로그 파싱 방식의 장점은 명확하다.
로그를 남기는 모든 서비스를 별도의 연동 없이 보호할 수 있고,
필터를 한 줄 쓰면 새 서비스가 대상이 된다.

대가는 두 가지다.
첫째, 차단은 언제나 사후이며 로그가 기록되고 파싱된 다음에야 일어난다.
로그가 폭증하는 상황에서는 파싱 자체가 밀리면서 차단이 공격보다 늦게 도착하는 사례가 보고된다.
둘째, 정규식이 공격자가 부분적으로 통제하는 문자열을 처리한다는 사실이 그 자체로 공격면이 된다.
이 문제는 뒤의 비평에서 따로 다룬다.

방화벽 수준에서 같은 일을 하는 대안도 있다.
HN에서 computerfriend는 로그를 파싱하지 않고 iptables와 nftables만으로 비슷한 효과를 낼 수 있다고 지적했고,[^computerfriend]
chunk_waffle은 FreeBSD와 NetBSD의 `blocklistd`가 훨씬 단순한 접근이라면서
다만 지원을 원하는 데몬마다 작은 패치가 필요하다는 조건을 함께 밝혔다.[^chunk_waffle]
여기서의 교환은 명확하다.
커널 수준 접근은 빠르고 안전하지만 데몬이 협조해야 하고,
로그 파싱은 아무 데몬에나 붙지만 느리고 파서가 공격면이 된다.

### 속도 제한과 차단은 서로를 대체하지 못한다

nginx의 `limit_req`는 초과 요청을 버리기만 하고 그 이상은 하지 않는다.
HN에서 quibono는 이 둘을 엮는 구성을 설명했다.
fail2ban이 nginx 로그에서 한계 초과 기록을 찾아 Redis 집합에 IP를 넣고,
Lua 플러그인이 들어오는 요청의 주소가 그 집합에 있는지 확인해 연결을 끊는 방식이다.[^quibono]

이 조합이 필요한 이유는 각각이 다른 층에서 동작하기 때문이다.
속도 제한은 한 IP의 순간 속도를 억제하지만 그 IP가 계속 돌아오는 것을 막지 못하고,
차단은 재방문을 막지만 첫 폭주를 막지 못한다.
둘 중 하나만 두면 반드시 비는 구간이 생긴다.

## 비평

### 이 도구의 공격면은 정확히 공격자가 쓰는 문자열이다

fail2ban의 보안 권고 이력은 이 설계가 안고 있는 문제를 그대로 보여 준다.
1.1.1이 고친 GHSA-33wh-ccjc-p397은 `domino-smtp` 필터의 정규식에서 발생하는 ReDoS다.
공격자가 공백을 많이 넣은 SMTP 사용자명을 보내면 그 로그 줄 하나를 처리하는 데
수 초에서 수 시간이 걸릴 수 있고, 그동안 필터 스레드가 멈춰 다른 공격을 탐지하지 못한다.
같은 릴리스가 `dovecot` 필터의 같은 유형도 함께 고쳤다.
해당 jail이 기본으로 꺼져 있다는 점이 피해 범위를 줄이지만, 문제의 성격은 바뀌지 않는다.

더 오래된 사례인 CVE-2021-32749는 `mail-whois` 액션에서 원격 코드 실행이 가능했던 건이다.
mailutils의 `mail` 명령이 입력에 포함된 `\n~` 시퀀스를 이스케이프로 해석하는데,
whois 출력처럼 외부에서 오는 내용이 그대로 그 입력이 되었다.
즉 차단당한 쪽이 자기 whois 레코드에 심어 둔 문자열이 방어자의 서버에서 실행될 수 있었다.

두 사례의 공통점이 중요하다.
fail2ban은 공격자가 만든 문자열을 정규식으로 처리하고, 그 결과를 셸 명령의 인자로 넘긴다.
보안을 위해 설치한 프로세스가 공격자 입력을 가장 많이 다루는 프로세스가 되는 구조다.
HN에서 pandog는 이 프로젝트의 취약점 이력을 근거로,
fail2ban이 위험을 줄이지 못하면서 오히려 늘리기 때문에 보안 연극보다 나쁘다고까지 주장했다.[^pandog]

### 위협 모델 없이 설치되는 도구라는 비판

pandog의 주장은 여기서 한 걸음 더 나간다.
이 도구를 설치할 만큼 보안에 신경 쓰는 사람이라면 이미 강한 비밀번호나 공개키 인증으로
실제 위험을 제거했을 것이고, 그렇다면 남는 효과는 로그 소음 감소뿐이라는 것이다.
tptacek은 여기에 동의하면서, fail2ban이 위협 모델을 따지는 대신
보안 체크리스트를 따르는 사람들의 표식이 되었다고 적었다.[^tptacek]

이 비판은 README가 스스로 적어 둔 경계와 정확히 같은 곳을 가리킨다는 점에서 무겁다.
저장소는 약한 인증의 위험을 없애지 못한다고 밝히고 있고, 비판자는 그렇다면 무엇을 위한 도구냐고 묻는다.
공개키 전용 sshd에서 비밀번호 무차별 대입은 애초에 성공할 수 없으므로,
이 구성에서 fail2ban이 막는 것은 성공 가능성이 0인 시도다.

다만 이 논리에는 조건이 붙어 있다.
mullingitover는 상당한 규모의 봇넷을 가진 공격자라면 fail2ban으로 늦출 수조차 없다고 지적하면서도
그것이 무가치하다는 뜻은 아니며 만능 해법이 아닐 뿐이라고 정리했다.[^mullingitover]
실제로 보호 대상이 sshd 하나가 아니라 인증이 약할 수밖에 없는 웹 애플리케이션 로그인일 때,
그리고 그 앞에 CDN이나 WAF가 없을 때, 계산은 달라진다.
비판이 겨냥하는 것은 도구 자체보다 이 조건을 따지지 않는 설치 습관이다.

### 포트를 바꾸면 된다는 반론이 놓치는 것

소음이 문제라면 SSH 포트를 22가 아닌 곳으로 옮기면 된다는 주장이 스레드에서 여러 번 나왔다.
seanp2k2는 포트 변경만으로도 같은 효과를 얻는다고 적었다.[^seanp2k2]

throw0101c의 반박은 운영자의 시각에서 이 주장을 뒤집는다.
시스템 관리자로서 사용자들에게 다른 포트를 쓰라고 교육하고,
각자의 CLI 습관과 스크립트를 고치게 만들고 싶지 않다는 것이다.[^throw0101c]
그는 로그 소음을 더 줄이고 싶다면 IPv6 주소를 받아 IPv4를 버리라고 덧붙이면서,
`/64`를 스캔하려는 쪽에게는 행운을 빈다고 적었다.

이 대립은 보안 논쟁이 자주 빠지는 함정을 잘 보여 준다.
기술적으로 더 나은 해법이 조직적으로는 더 비싼 경우가 있고,
fail2ban처럼 사용자에게 아무것도 요구하지 않는 도구가 선택되는 이유가 대개 거기에 있다.
비판자들이 기술적으로 옳으면서도 설득에 실패하는 지점이기도 하다.

### 차단이 다른 팀의 정상 업무를 막을 수 있다

steelframe은 회사 네트워크에 데비안 서버를 붙여 두고 fail2ban을 돌렸더니
매일 아침 사내 스캐너가 포트를 두드릴 때마다 차단되었고,
차단이 만료되면 다음 날 같은 일이 반복되었으며 자신이 퇴사한 뒤에도 몇 주 혹은 몇 달간 그대로였다고 적었다.[^steelframe]

BrandoElFollito의 답글은 이 이야기를 다른 방향에서 읽는다.
기업의 스캐너는 재미로 도는 것이 아니라,
보안팀 모르게 서버를 붙여 놓고 결국 침해당하는 사람들을 찾아내기 위해 존재한다는 것이다.[^BrandoElFollito]
스캐너를 막는 행위는 이미 취약점 대응에 시달리는 팀의 일을 더 어렵게 만든다고 그는 적었다.

이 교환은 자동 차단 도구가 조직 안에서 갖는 성격을 드러낸다.
fail2ban은 어떤 트래픽이 악의적인지를 판단하지 않고 오직 실패 횟수만 센다.
같은 행동이 밖에서 오면 공격이고 안에서 오면 감사인데,
이 도구에는 그 차이를 표현할 수단이 `ignoreip` 목록밖에 없다.
운영 조직이 클수록 이 목록을 최신으로 유지하는 일이 도구 자체보다 어려워진다.

## 함정

정상 동작처럼 보이면서 실제로는 아무것도 막지 못하는 경우가 몇 가지 있다.

리버스 프록시 뒤에서 웹 로그를 볼 때, 로그에 남는 IP가 프록시의 IP라면
fail2ban은 매번 프록시를 차단한다.
`X-Forwarded-For`를 로그 포맷에 반영하고 필터가 그 필드를 보게 만들어야 하며,
동시에 그 헤더를 신뢰할 수 있는 출처에서만 받도록 프록시를 설정해야 한다.

로그 회전 직후 차단이 멈추는 경우도 있다.
1.1.1이 고친 버그 중 하나가 저널 회전 뒤 디스크립터가 사라지는 문제였고,
파일 백엔드에서도 회전 처리와 백엔드 선택이 어긋나면 새 파일을 읽지 않는 상태가 될 수 있다.

컨테이너 환경에서는 액션이 조용히 실패하기 쉽다.
컨테이너 안의 fail2ban이 호스트 네트워크 네임스페이스의 방화벽을 건드릴 권한이 없으면
상태 명령은 차단된 IP를 보고하지만 실제 규칙은 들어가지 않는다.
앞의 확인하기 절차가 이 상태를 잡아내기 위한 것이다.

기록되는 IP가 개인정보라는 점도 실무에서는 함정이 된다.
HN에서 Kiro는 IP가 개인정보인데 동의를 받을 수도 없으니 GDPR을 어떻게 지키느냐고 물었고,[^Kiro]
M2Ys4U는 GDPR이 미국 법률 용어인 PII가 아니라 개인정보 처리를 다루며,
동의는 여섯 개 합법 처리 근거 중 하나일 뿐이라고 답했다.[^M2Ys4U]
worksonmine은 데이터를 안전하게 지킬 의무가 있는 이상
무차별 대입 시도의 IP를 저장하는 것은 문제가 없고 오히려 요구에 가깝다고 덧붙였다.[^worksonmine]
실무적으로 남는 일은 차단 데이터베이스의 보존 기간을 정하고 그 근거를 적어 두는 것이다.

- 리버스 프록시 뒤라면 로그의 IP가 실제 클라이언트 주소인가?
- 1.1.1 이상으로 올린 뒤 기본 액션이 `nftables`로 바뀐 것을 커스텀 액션이 견디는가?
- 보호하려는 서비스의 인증이 약한가? 약하지 않다면 이 jail이 무엇을 막는지 설명할 수 있는가?
- 차단 기록의 보존 기간과 그 근거를 정해 두었는가?

## 기억할 원칙

### 방어 도구는 자신이 처리하는 입력의 출처를 먼저 물어야 한다

fail2ban의 두 보안 권고는 모두 공격자가 통제하는 문자열을 다루는 지점에서 나왔다.
로그 줄을 정규식에 넣는 곳과 whois 출력을 셸 명령에 넘기는 곳이다.
방어를 위해 추가한 구성 요소일수록 이 질문을 더 엄격하게 받아야 한다.
공격면을 줄이려고 넣은 프로세스가 가장 넓은 공격면을 갖게 되는 일이 실제로 일어나기 때문이다.

이 관점은 로그 기반 탐지 전반에 적용된다.
로그는 공격자가 내용을 부분적으로 정할 수 있는 데이터이며 신뢰할 수 있는 입력이 아니다.
파싱하는 쪽은 정규식의 최악 시간 복잡도와 출력의 이스케이프를 모두 자기 책임으로 다뤄야 한다.

### 무엇을 막는지 말할 수 없는 방어는 설정이 아니라 습관이다

이 저장소의 README와 가장 날 선 비판이 같은 문장을 향한다는 점은 우연이 아니다.
fail2ban은 약한 인증의 위험을 제거하지 않으며, 그 사실을 스스로 밝힌다.
그러므로 이 도구를 켤 때 답해야 할 질문은 설치 방법이 아니라
“지금 이 서비스의 인증은 어디가 약한가”이다.

답이 “약하지 않다”라면 fail2ban이 실제로 사는 것은 로그의 가독성과 대역폭이고,
그것도 가치가 있지만 보안 대책으로 계산해서는 안 된다.
답이 “웹 로그인이 비밀번호 하나다”라면 fail2ban은 의미 있는 완화책이며,
그때는 오탐과 자기 차단을 관리하는 비용을 감수할 이유도 분명해진다.
