# uBlock Origin 요소 선택기의 범용 XSS

원문: [Universal XSS in uBlock Origin from website-driven element picker](https://iter.ca/post/ubo-uxss/)

HN 토론: <https://news.ycombinator.com/item?id=50513160> (488점, 139개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/x0ykkw/universal_xss_ublock_origin_from_website> (21점, 0개 댓글)

## 요약

개인 블로그 iter.ca에 2026년 11월 15일 올라온 보안 글이다.
글이 가리키는 GitHub 보안 권고와 수정 커밋은 열지 않았고, 취약점을 재현하지도 않았다.
아래는 글의 주장을 구현 세부 없이 옮긴 것이다.

필자의 보고는 이렇다.
이번 달 초 uBlock Origin(Firefox용 MV2판)에서 한 번의 클릭으로 성립하는 범용 XSS를 발견했고, MV3판인 uBO Lite에도 덜 심각한 비슷한 문제가 있었다는 것이다.
악성 웹사이트가 확장 프로그램을 속여 임의의 신뢰된 필터를 추가하게 만들 수 있었다. 신뢰된 필터는 페이지에 자바스크립트를 주입할 수 있으므로, 공격자는 다른 사이트에 필터를 만들어 그 사이트의 맥락에서 임의의 코드를 실행할 수 있었다는 것이다. 지금은 수정되었다고 한다.
필자는 문제를 찾는 어려운 작업의 대부분을 GPT-5.6 Sol이 했고, 자신은 필터 주입에서 범용 XSS가 나올 수 있겠다고 생각해 살펴보라고 시켰으며 제시된 문제를 직접 확인했다고 쓴다. 글은 모두 직접 썼고 개념 증명 코드는 대부분 Claude가 썼다고 밝힌다.

글이 설명하는 구조는 네 단계이다.

- 배경: uBlock Origin의 요소 선택기는 페이지에서 우클릭해 불러오고, 확장 프로그램 안의 페이지를 iframe으로 주입해 구현한다. 이 페이지는 확장 프로그램의 배경 스크립트와 통신해 필터를 추가할 수 있다.
- 공격의 흐름: 선택기 주소를 알아내고, 투명한 iframe으로 선택기를 끼워 넣고, 원하는 필터가 들어가도록 선택기를 조종하고, 보이지 않는 생성 버튼을 사용자가 누르게 유도한다.
- 주소 알아내기: Firefox에서는 설치마다 무작위인 확장 프로그램 내부 식별자만 알면 되는데, 기본 필터 중 하나가 일으키는 동작 때문에 공격 페이지가 이를 알아낼 수 있었다고 한다. 필자는 이 식별자가 새는 길이 그 하나만은 아니라고 덧붙인다.
- 핵심 결함: 요소 선택기가 공격자의 메시지를 받으면 안 되는데 받았다. 선택기는 평소에 입력할 수 있는 필터를 제한하지만, 한 입력 필드의 처리 허점으로 제한을 우회할 수 있었다고 한다. 수정 중 하나는 진짜 선택기가 콘텐츠 스크립트에서 받은 비밀값을 첫 메시지에 실어 보내게 한 것이다. 클릭 유도는 필자가 구현하지 않았고, 그 부분은 투명 iframe을 겹쳐 두는 방식으로 가능하다고만 설명한다. 요소 선택기가 추가한 필터는 재컴파일 전까지 항상 신뢰되고, 사용자가 사용자 필터를 바꾸면 신뢰가 지워지지만 공격자가 곧바로 피해자 사이트를 열면 큰 도움이 되지 않는다고 쓴다.

## 분석

### 중심 주장은 신뢰 경계가 선택기 화면에서 뚫렸다는 것이다

글의 핵심 문장은 요소 선택기가 공격자의 메시지를 받으면 안 된다는 것이다.
확장 프로그램의 내부 화면이 웹 페이지에서 iframe으로 올릴 수 있고(웹에서 접근 가능한 자원으로 선언되어 있음) 메시지를 보낼 수 있다면, 확장 프로그램 권한을 가진 기능이 웹 페이지의 조종을 받는다.
수정이 출처 확인이 아니라 비밀값 교환이었다는 서술은 이 경계를 어떻게 복구했는지 보여 준다. 이는 글의 서술을 이 문서가 압축한 것이다.

### 설치마다 다른 식별자가 새면 추적에도 쓰일 수 있다

글은 확장 프로그램 식별자가 설치마다 무작위이고 이것이 알려지면 선택기 주소를 만들 수 있다고 쓴다.
필자는 새는 경로가 하나가 아니라고 하며, 이 식별자의 존재가 두 번째 문제(추적)를 낳는다는 것은 글이 직접 다루지 않는다. HN 독자가 이를 짚었다(비평 절).

### AI의 몫은 필자의 서술이다

필자는 발견의 어려운 부분을 AI가 했다고 쓴다.
이 서술은 독립적으로 확인할 수 없다.
다만 사람이 취약 가능성의 방향을 정하고 AI가 코드를 읽어 구체적 결함을 찾았고 사람이 검증했다는 분업이 명시되어 있다는 점이 눈에 띈다.

## 비평

### 글은 공격 조건과 영향 범위를 제한적으로 쓴다

공격에는 사용자의 클릭이 필요하고, 글은 클릭 유도 부분을 구현하지 않았다고 밝힌다.
수정된 상태라는 서술도 필자의 것이다.

### 독자들은 식별자 유출이 별개의 추적 문제라고 지적했다

HN의 한 댓글은 설치마다 무작위인 내부 식별자를 페이지가 알아낼 수 있다면 설치를 고유하게 추적하는 식별자가 되는 것 아니냐고 물었다.[^abcd_f]
다른 댓글은 얼마 전 어떤 Firefox 확장이 자기 식별자를 새게 할 수 있다는 것을 알았는데, 이제 어느 사이트든 uBO의 식별자를 얻을 수 있다는 것이 아이러니라고 했다.[^ethersteeds]
답글은 Chromium이 최근까지 웹 접근 자원에 고정 ID를 썼고 지금도 동적 ID는 선택 사항이며 이를 나열하는 페이지가 있다고 보탰다.[^tech234a]
글 자신은 이 문제를 추적 관점에서 다루지 않았다.

### 구조 비판은 확장 프로그램의 모델 전체로 번진다

한 댓글은 확장 프로그램이 페이지의 요소와 일하려면 웹사이트의 DOM에 인터페이스를 넣어야 하는 구조가 늘 마음에 들지 않았다고 했다. 비밀번호 관리자가 그렇게 하면 어떤 계정이 있는지 사이트에 새어 나갈 수 있다는 것이다.[^ByteOfWood]
이에 한 답글은 확장 프로그램용 오버레이 API가 Top Layer 기반으로 계획되었으나 추가되지 않았고 개발자 도구도 같은 이유로 별도 오버레이 페이지를 쓴다고 했다.[^esprehn]
다른 답글은 확장 프로그램의 버그가 웹사이트에 대량으로 영향을 줄 수 있다며 올해 1월 1Password가 모든 페이지에 라이브러리를 주입해 코드 블록이 최소 20일 깨진 일을 들었다.[^btown]
한 댓글은 uBlock Origin이 페이지를 검사하고 바꿀 광범위한 권한이 필요하므로 취약점이 더 악용되기 쉽다고 했고,[^SoftTalker]
다른 댓글은 확장 프로그램이라는 개념 자체가 위험하고 악성코드를 싣는 확장이 많다고 했다.[^negura]
DOM을 스냅샷으로 격리하자는 제안에는 성능이 반으로 줄고 보안 이득은 작으며 확장이 모든 네트워크 요청에 무제한 접근하는 더 큰 구멍이 있다는 반박이 달렸다.[^hackerbone][^jimmydorry]

### uBO Lite 쪽 공개가 덜 되어 있다는 관찰

한 댓글은 uBO Lite 저장소의 최신 커밋이 보안 정책 파일 생성이고, 큰 형제인 MV2 저장소와 달리 GitHub 페이지에 권고가 아직 없다고 지적했다.[^asimovDev]

### 반응은 있으나 방어의 방향이 갈린다

한 댓글은 서드파티 프레임을 기본으로 막는 차단 수준을 쓴다고 하며 해당 설정을 알렸고,[^user070223] 다른 댓글이 같은 우회책을 제안했다.[^ck2]

## 인사이트

### 가져갈 것은 확장 프로그램 내부 화면의 메시지 출처를 의심하는 습관이다

확장 프로그램이 자신의 화면을 웹 페이지에 올릴 수 있게 하는 순간, 그 화면이 받는 모든 메시지는 외부 입력이다.
글이 보고하는 수정은 메시지를 믿을 근거(비밀값)를 첫 단계에 넣는 방식이다.
같은 구조의 다른 확장이나 내부 화면을 쓰는 코드를 점검할 때 이 질문을 던질 수 있다. 이는 이 문서의 일반화이다.

### 사용자 입장에서는 업데이트 확인이 먼저이다

수정이 나왔다는 글의 서술에 따라, 사용 중인 확장 프로그램의 버전이 보안 권고의 수정 버전 이상인지 확인하는 것이 가장 직접적인 행동이다.

### 확인할 관찰

이 글의 서술을 가를 관찰은 세 가지이다.
GitHub 보안 권고가 말하는 영향 버전과 수정 버전이 글과 맞는지,
uBO Lite 쪽 문제가 어느 정도이고 언제 공개되는지,
확장 식별자 유출이 추적에 실제로 쓰이는 증거가 나오는지이다.
