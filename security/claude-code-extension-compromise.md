# Claude Code 확장 위조판이 Cursor 마켓플레이스에서 SSH 백도어를 심었다

원문: [Official Claude Code Extension Compromise: Security Advisory | Phorion](https://phorion.io/blog/offical-claude-code-vsx-compromise/)

HN 토론: <https://news.ycombinator.com/item?id=50300683> (884점, 522개 댓글)

## 요약

엔드포인트 보안 업체 Phorion의 Calum Hall이 2026-10-30에 올리고 10-31에 갱신한
보안 권고이다.
Cursor 마켓플레이스(marketplace)에 올라온 Claude Code for VS Code 확장 번들에
지속형 SSH 백도어가 들어 있었다고 보고한다.
영향 버전은 처음에 2.1.313만 적었다가, Cursor의 공지를 반영해 2.1.312와
2.1.313으로 고쳤다.
Cursor는 두 버전을 마켓플레이스에서 내렸고,
위조판이 올라 있던 시간은 2026-10-29 오전 2시 27분부터 오후 1시 35분까지(태평양
표준시)라고 밝혔다.[^cursor]

주입된 코드는 압축된(minified) `extension.js` 앞에 붙은 즉시 실행
함수(IIFE)이다.
Node가 파일을 읽는 순간 실행되므로 사용자가 확장을 쓰지 않아도,
확장의 `activate` 함수가 호출되기 전에 동작한다.
나머지 번들은 정상 확장과 같아 보인다고 한다.
동작은 네 단계로 나뉜다.

| 단계                           | 동작                                                                            | 남는 흔적                                        |
| ------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1. SSH 접근 준비               | 공격자의 Ed25519 공개키를 `~/.ssh/authorized_keys`에 추가                       | 주석 `svc-telemetry` 키                          |
| 2. 역방향 터널(reverse tunnel) | `134.209.82[.]225`의 22번 포트로 `ssh -R *:0:localhost:22` 연결                 | `/tmp/.stk_*` 임시 키, ssh 또는 autossh 프로세스 |
| 3. 지속성(persistence)         | macOS는 사용자 LaunchAgent, Linux는 crontab, Windows는 예약 작업 또는 시작 폴더 | `com.apple.sysmond.plist`, `~/.config/.smt`      |
| 4. 정찰(reconnaissance)        | 호스트 이름, 사용자, Git 이메일, 공인 IP, 환경 변수 이름을 8099번 포트로 전송   | `/beacon`으로 가는 평문 HTTP POST                |

역방향 터널의 포트 0은 공격자 서버가 임의의 포트를 열어 주게 한다.
운영자는 그 포트로 접속해 피해자 컴퓨터의 22번 포트에 도달하고,
1단계에서 심어 둔 키로 로그인한다.
그래서 JavaScript 안에 별도의 명령 수신 코드가 없어도 대화형 셸과 파일
전송이 가능하다.
터널은 60초 간격의 재시도 루프에 들어 있어서 IDE를 닫아도 유지된다.

정찰 단계의 비콘(beacon)은 `KEY`, `TOKEN`, `SECRET`, `PASS`, `AWS`,
`GCP`가 들어간 환경 변수의 이름을 최대 40개까지 보낸다.
값은 보내지 않는다.
글은 이를 어떤 호스트에 클라우드 자격 증명이 있는지 운영자가 가늠하는
목록이라고 해석한다.

저자가 가장 길게 다루는 대목은 macOS의 결함이다.
악성 코드는 `systemsetup -getremotelogin`을 관리자 권한 없이 실행하고,
출력에 `Off`가 있을 때만 SSH를 켜려 한다.
일반 사용자로 실행하면 이 명령은 `You need administrator access to run this
tool... exiting!`을 표준 출력으로 내고 종료 코드 0으로 끝난다.
그래서 `Off` 검사는 영원히 거짓이 되고 SSH를 켜는 단계는 건너뛰어진다.
Remote Login이 꺼진 Mac에서는 터널이 연결되어도 되돌아오는 트래픽이 닫힌 22번
포트에 막힌다.
저자는 Remote Login이 이미 켜져 있거나 나중에 켜지면 백도어가 그대로
쓰인다고 경고한다.

대응은 확장 삭제로 끝나지 않는다고 한다.
터널 프로세스를 끝내고, LaunchAgent와 `~/.config`의 파일을 지우고,
심어진 키와 `/tmp/.stk_*`를 지우고, Remote Login이 켜져 있지 않은지 확인하고,
해당 계정으로 닿던 자격 증명을 교체해야 한다.
글은 침해 지표(indicator of compromise)로 `extension.js`의 SHA-256,
두 키의 지문, 네트워크와 호스트 흔적의 목록을 싣는다.

## 분석

### 글의 전제는 사용자 권한만으로 충분하다는 것이다

악성 코드에는 권한 상승 익스플로잇이 없다.
저자도 이를 명시한다.
쓰는 것은 사용자 홈 디렉터리에 쓰기, 사용자 단위 LaunchAgent 등록,
외부로 나가는 SSH 연결뿐이다.
IDE 확장은 IDE를 실행한 사용자의 권한으로 돌기 때문에,
확장이 로드되는 순간 소스 코드와 개발 도구에 곧바로 닿는다는 것이 글의 전제이다.

이 전제 위에서 공격자가 고른 구성이 눈에 띈다.
받는 쪽에 명령 해석기를 두지 않고, 이미 있는 SSH 서버와 인증 키를 접근
수단으로 삼는다.
정찰 결과도 값이 아니라 이름만 보낸다.
탐지 쪽에서 보면 악성 JavaScript는 짧고 정적인 코드로 남고,
이후의 활동은 정상 SSH 로그인과 구분하기 어려워진다.
글이 말하듯 터널로 들어온 로그인은 서버 로그에 localhost에서 `svc-telemetry`
키로 인증한 것으로 찍힌다.

### 결함이 막은 것은 하나이고, 막지 못한 것은 나머지 전부이다

macOS 결함은 인바운드 경로 하나, 곧 Remote Login을 켜는 단계만 깬다.
키 추가, 터널 연결, 지속성 등록, 정찰 전송은 모두 관리자 권한이 필요하지 않아서
그대로 실행된다.
Cursor도 공지에서 SSH 서비스를 켜는 단계는 코드 오류 때문에 대체로 관리자 권한
없이는 실패한다고 쓴다.[^cursor]
두 문서는 같은 사실을 다르게 강조한다.
Cursor는 실패하는 부분을 앞세우고, Phorion은 실패하는 부분이 방어 수단이 될 수
없다는 점을 앞세운다.

Windows 쪽 결함도 같은 성격이다.
PowerShell 명령을 `/bin/sh`를 고정한 보조 함수로 넘기므로 일반 Windows에서는
진행되지 않을 것이라고 저자는 본다.
Linux에 대해서는 crontab 검사 결함이 반복 실행 때 사용자의 기존 cron 작업을 지울
수 있다고 표에 적지만, 상세는 글에서 찾을 수 없다.
이 점은 비평에서 다시 다룬다.

### 사건은 곧 누가 배포했는가의 논쟁이 되었다

Phorion의 제목은 공식(Official) 확장의 침해라고 말한다.
HN에서는 이 표현이 곧바로 논쟁이 되었다.
Anthropic 소속이라고 밝힌 felixrieseberg는 Anthropic의 시스템이나 직원 노트북이
침해된 것이 아니라고 썼다.
공격자가 Cursor 마켓플레이스에 접근해 변조된 사본을 올렸고,
Anthropic은 그것을 만들지도 올리지도 않았다는 설명이다.[^felixrieseberg]
같은 소속이라고 밝힌 ddworken은 VS Code 마켓플레이스와 OpenVSX의 공식 배포본은
영향이 없고 Cursor 사용자만 해당된다고 적었다.[^ddworken]
Cursor는 공지에서 해당 확장이 Anthropic이 개발한 것이 아니라고 밝혔다.[^cursor]

저자의 글은 이 경계를 직접 서술하지 않는다.
글이 확정하는 것은 Cursor 마켓플레이스에서 배포된 번들의 내용이고,
누가 어떤 경로로 올렸는지는 다루지 않는다.
그 공백을 HN 댓글이 추정으로 채웠다.
K0nserv는 2.1.313이 Anthropic 저장소의 변경 이력(CHANGELOG)과 태그에 없다는 점을
근거로 Anthropic 쪽 침해를 의심했다.[^K0nserv]
mirashii는 Claude Code 버전에는 평소에도 빠진 번호가 있다고 이의를 제기했다.[^mirashii]
번호가 비는 것이 침해의 증거가 되지 못한다는 뜻이다.

## 비평

### 제목의 공식이라는 단어가 책임 소재를 흐린다

글의 제목과 URL은 공식 확장의 침해를 말하고,
요약문은 Cursor 마켓플레이스의 번들이라고 적는다.
두 문장은 모순이 아니지만, 제목만 읽은 독자는 Anthropic이 배포한 확장이
오염되었다고 받아들이기 쉽다.
HN에는 그렇게 읽은 댓글이 있었다.
darkwi11ow는 OpenVSX의 릴리스 권한을 Anthropic 계정이 갖고 있다는 이유로
Anthropic 쪽 침해를 의심했다.[^darkwi11ow]

반대로 Anthropic의 설명만 받아들이면 책임이 Cursor에만 있다고 보게 되는데,
이것도 완결되지 않았다.
tzone은 Cursor의 확장 목록이 Anthropic 제작물로 표시되므로,
올릴 수 있는 쪽이 Anthropic 팀뿐이라는 가정이 깨진 것 자체가 Anthropic에게도
문제라고 썼다.
서명 키를 Anthropic이 갖도록 바꾸거나 아니면 Cursor 쪽 표시에서 이름을 빼야
한다는 주장이다.[^tzone]
IshKebab은 이를 억지라고 일축했다.[^IshKebab]
어느 쪽이 맞는지는 이 글만으로 판단할 수 없다.
다만 이 글의 제목이 이 논쟁에서 한쪽 해석을 전제로 삼는다는 점은 분명하다.

### 글이 약속하고 채우지 못한 것이 있다

Linux 행에는 crontab 결함이 아래에서 상세히 다뤄진다고 적혀 있지만,
본문 어디에도 그 설명이 없다.
기존 cron 작업을 지울 수 있다는 주장은 근거 없이 남는다.
또 로컬 호스트의 8099번 포트로 같은 보고서를 보내는 이유를 저자는 모른다고
인정하는데, 이 점은 정직하지만 악성 코드의 설계 의도를 읽는 데 빈칸이 남는다.

더 중요한 빈칸은 원인이다.
위조판이 어떻게 올라갔는지를 글은 다루지 않는다.
Cursor는 키를 교체하고 마켓플레이스를 다시 만들었다고 밝혔다.[^cursor]
이 조치는 마켓플레이스 쪽 침해를 시사하지만,
공지가 침투 경로를 설명하지는 않는다.
실제 피해에 대한 증거도 없다.
글은 운영자가 터널로 로그인했는지 확인하라고 권하지만,
로그인이 관찰되었다는 보고는 하지 않는다.

### 탐지 권고는 자사 제품으로 기울지만, 지표는 독립적으로 확인된다

글의 탐지 절은 ESF(Endpoint Security Framework) 텔레메트리(telemetry)에서 무엇을
볼지 구체적으로 알려 준다.
IDE 도우미 프로세스가 `authorized_keys`를 쓰는지,
비Apple 프로세스가 `com.apple.*` 라벨의 LaunchAgent를 만드는지를 보라는 식이다.
이 가운데 첫 항목은 실용적이다.
셸 명령 `echo`나 `tee`만 감시하는 규칙은 Node의 `fs.appendFileSync`를
놓치기 때문이다.
그러나 이 절 뒤에는 자사 탐지와 보호 기능 소개와 시연 신청이 이어지고,
같은 방향의 대안은 언급되지 않는다.

그래도 핵심 지표는 글 하나에 기대지 않는다.
Cursor의 공지는 같은 공격자 주소, 같은 키 지문,
같은 `extension.js` 해시 앞부분을 적고 있다.[^cursor]
따라서 지표 부분은 판매 문구와 별개로 신뢰할 수 있고,
판매 문구는 걸러 읽으면 된다.

## 인사이트

### 서명하는 쪽과 표시하는 쪽이 갈리면 이름이 신뢰의 근거를 대신한다

사용자가 보는 것은 확장 이름과 게시자 표기이다.
그 표기가 가리키는 주체와 실제로 파일을 올린 주체가 다를 수 있다는 것이 이번
사건에서 드러난 구조이다.
Anthropic은 자기 채널의 배포본은 그대로라고 말하고,
Cursor는 자기 마켓플레이스의 위조판을 지웠다고 말한다.
둘 다 사실일 수 있고, 그때 사용자는 두 설명 사이에 끼어 있다.

Linux 배포판의 미러가 비슷한 문제를 일찍 풀었다.
패키지는 배포판의 키로 서명되고, 미러는 파일을 나를 뿐 서명을 바꾸지 못한다.
미러가 침해되어도 클라이언트가 서명을 검증하면 변조가 드러난다.
마켓플레이스가 확장을 자체 키로 다시 서명하는 구조라면,
마켓플레이스의 침해는 클라이언트 쪽에서 게시자의 침해와 구별되지 않는다.
Cursor의 공지가 키 교체를 조치로 든 점은 이 구조를 의심하게 하지만,
서명이 실제로 어떻게 이뤄지는지는 이 자료로 확인되지 않는다.
이것은 필자의 추정이며, 확인하려면 Cursor의 서명 방식을 다룬 문서가 필요하다.

### 노출 시간이 11시간이었으므로 업데이트 지연 설정이 통했을 수 있다

Cursor가 밝힌 노출 시간은 약 11시간이다.[^cursor]
이 시간 동안 설치되거나 업데이트된 컴퓨터만 감염된다.
자동 업데이트에 지연(delay)을 두는 설정이 있다면, 이런 사건은 피해 가기 쉽다.
그런데 orlp는 VS Code 1.123 공지를 인용해, 이 지연이 Microsoft, GitHub,
OpenAI 같은 신뢰 게시자의 확장에는 적용되지 않고 사용자가 신뢰 목록을 고칠 수도
없다고 썼다.[^orlp]
필자는 이 공지를 직접 열어 보지 않았으므로 댓글의 보고로만 인용한다.

이 인용이 맞다면 업데이트 지연은 모든 확장을 지켜 주지 못한다.
지연이 가장 필요한 곳, 곧 유명 게시자의 확장이 가장 널리 퍼지는 곳에서 적용되지
않기 때문이다.
이번 사건은 Cursor의 마켓플레이스였고, 지연이 적용되는지는 편집기마다
다를 수 있다.
11시간짜리 노출은 하루만 지연해도 피할 수 있었다는 계산은,
지연이 해당 확장에 실제로 적용될 때만 성립한다.

### 확장을 지워도 사건은 끝나지 않고, 비용은 사용자에게 돌아간다

마켓플레이스에서 위조판이 내려가고 공격자 서버가 꺼졌다는 Cursor의 설명은 사건이
정리되었다는 인상을 준다.[^cursor]
그러나 같은 공지는 키와 지속성이 감염된 호스트에 남아 있으므로 조치가 필요하고,
호스트를 다시 만들어야 할 수도 있다고 적는다.[^cursor]
서버가 꺼졌다는 사실이 안심이 되지 않는 이유가 있다.
심어진 공개키는 여전히 공격자의 것이고,
터널이 아닌 다른 경로로 22번 포트에 닿을 수 있다면 그 키는 계속 쓸 수 있다.
이 경로가 노트북에서 흔한 것은 아니지만,
확장을 지운 뒤 우연히 Remote Login을 켜는 순간 조건이 바뀐다는 글의 경고와 같은
종류의 문제이다.

또 서버가 꺼지기 전에 비콘이 몇 대나 닿았는지는 두 문서 어디에도 서술이 없다.
운영자가 어떤 호스트가 준비되었는지 알았는지는 알 수 없고,
그래서 확인은 사용자의 몫으로 남는다.
사용자가 해야 할 확인은 구체적이다.
`~/.ssh/authorized_keys`에 심어진 키가 있는지 지문으로 대조하고,
`com.apple.sysmond.plist`와 `~/.config/.smt`가 있는지 보고,
이 파일들이 있다면 자격 증명을 교체한다.
키 주석 `svc-telemetry`는 글이 지적한 대로 쉽게 바뀔 수 있으므로 지문으로
확인하는 편이 안전하다.
