# 개발 환경에서 HTTPS를 쓰는 이유와 mkcert로 시작하는 법

원문: [Using HTTPS in Your Development Environment](https://auth0.com/blog/using-https-in-your-development-environment/)

GN 토론: <https://news.hada.io/topic?id=6144>

## 소개

Auth0의 Principal Developer Advocate인 Andrea Chiarelli가 2022년 3월 7일에 쓴 10분 분량의 안내 글이다.

HTTPS가 어떤 웹사이트나 웹 애플리케이션에도 필수이고 신뢰와 보안을 보장하며 브라우저 제공자들의 노력 덕에 널리 채택되었는데, **많은 개발자가 여전히 개발 환경에서 HTTP를 쓴다**는 관찰로 시작한다.

그리고 묻는다. 프로덕션 환경도 아닌데 왜 HTTPS로 바꿔야 하는가.

## HTTPS를 써야 하는 네 가지 이유

### 환경 동등성

첫 번째이자 가장 논리적인 이유가 개발 환경이 프로덕션 환경과 비슷해야 한다는 것이다.
**Twelve-Factor 방법론의 원칙 중 하나인 dev/prod parity**를 근거로 든다.
개발과 프로덕션 환경을 비슷하게 구성하면 개발에서 찾을 수 없는 문제를 프로덕션에서 겪을 위험이 줄어든다는 논리다.

구체적인 예가 따라온다.
HTTP 기반 CDN에서 JavaScript 라이브러리를 쓴다고 하면 로컬 개발 환경에서는 모든 것이 기대대로 동작한다.
그런데 HTTPS 기반 프로덕션 환경에서는 달라진다. 페이지에 **혼합 콘텐츠(mixed content)**가 생기기 때문이다.
브라우저가 HTTPS 페이지에서 HTTP 기반 리소스 로드를 거부할 수 있으며, 이것이 **HTTPS 다운그레이드 공격을 막기 위한 보안 조치**라고 설명한다.

### 강한 보안 정책

프로덕션에서 HTTPS를 켜는 것만으로는 충분하지 않다는 것이 두 번째다.

혼합 콘텐츠를 피하고 안전하지 않은 요청을 차단하도록 강제하려면 **콘텐츠 보안 정책(CSP)**을 써야 하는데, 이것이 의도치 않은 프로토콜 전환을 막아 준다.

그리고 결정적인 논리가 나온다.
CSP로 애플리케이션이 HTTPS에서 HTTP로 전환되는 것을 막으려면 **프로덕션과 개발 환경 양쪽에서 HTTPS를 써야 한다**는 것이다.
HTTP 기반 환경에서는 CSP 지시어가 동작하지 않기 때문이다.

즉 프로덕션 보안에 신경 쓴다면 개발 환경에서도 HTTPS를 쓸 수밖에 없다는 결론이다.

### 특정 브라우저 기능

현대 브라우저가 지원하는 고급 기능 일부는 로컬 개발 환경에서 HTTPS를 요구한다.
**서비스 워커, 보안 쿠키, 접두사 쿠키(prefixed cookies)**가 예로 제시된다.

일부 브라우저가 서비스 워커를 테스트할 때 호스트명을 `localhost`나 `127.0.0.1`로 명시하면 평문 HTTP를 허용하기는 한다.
그런데 이것이 앞서 말한 환경 동등성 원칙을 위반하며, **브라우저 제조사들이 강하게 권장하지 않는다**고 적는다.

### 커스텀 호스트명

보통 로컬 머신 이름으로 `localhost`를 쓰는데, 이것이 예약된 이름이고 `127.0.0.1`에 매핑되며 브라우저가 특히 보안 측면에서 특별하게 다룬다.

그런데 `myapplication`이나 `myhost.dev` 같은 커스텀 호스트명이 필요한 상황이 있다.
여러 개발 환경을 구분하기 위해 의미 있는 이름을 쓰고 싶은 경우이고, 머신의 hosts 파일을 편집해 할 수 있다.

경고가 붙는다. **hosts 파일 내용을 바꾸면 특정 인터넷 도메인 접근에 문제가 생길 수 있다**는 것이다.

이 경우 브라우저가 그것을 보안 사이트로 취급하지 않지만 HTTPS를 켜면 그렇게 된다.

### 나중에 바꾸면 된다는 생각에 대한 경고

HTTP로 새 프로젝트를 시작하고 프로젝트가 커지면 나중에 HTTPS로 바꾸자고 생각할 수 있다는 점을 짚는다.
이 접근이 **HTTP에서 HTTPS로 전환하는 것이 고통 없다는 흔한 생각**에 기반한다는 것이다.

그리고 Stack Overflow가 마이그레이션에서 겪은 문제들의 이야기를 읽어 보라고 권한다.

## HTTPS가 localhost에서 동작하는 방식

암호화 메커니즘의 세부를 전부 이해할 필요는 없지만 기본 용어는 필요하다며 개념을 정리한다.

클라이언트와 서버가 교환하는 데이터가 **공개키 암호(Public-Key Cryptography)**로 암호화되며, 이것이 개인키와 공개키 쌍에 기반한다.
서버는 **인증기관(CA)이 발급한 디지털 인증서**를 통해 클라이언트에게 공개키를 제공한다.

브라우저가 HTTPS 서버에 접속하면 서버의 디지털 인증서를 받고, 가장 먼저 하는 일이 **서버 도메인명이 인증서의 도메인명과 일치하는지 확인**하는 것이다.
이 검증이 공개키가 신뢰할 수 있는 출처에서 왔음을 보장한다.
브라우저는 인증서 만료일과 발급한 인증기관 같은 다른 것들도 확인한다.

프로덕션 환경에서는 실제 인증기관이 발급한 인증서가 필요하지만, **개발 환경에서는 더 느슨해도 되며 자체 서명 인증서를 직접 만들 수 있다**는 것이다.

## 설정하기

프레임워크마다 고유한 절차나 도구가 있을 수 있으므로 각자 문서를 확인하라고 안내하면서, 모든 프레임워크에서 동일한 것 하나를 짚는다.
**개인키와 공개키 쌍, 그리고 공개키를 담은 인증서가 필요하다는 것**이다.

### 인증서 만들기

가장 잘 알려지고 강력한 도구가 OpenSSL이지만 공개키 기반구조(PKI) 개념에 대한 좋은 지식을 요구한다고 적는다.
대부분의 경우 HTTPS 환경에 고급 요구사항이 없으므로 **mkcert 같은 단순한 도구가 훌륭한 선택**이라는 것이다.

```bash
# 처음 쓸 때 로컬 인증기관을 설치한다
mkcert -install
```

이때 나올 수 있는 경고를 미리 보여 준다.

```text
Warning: "certutil" is not available, so the CA can't be automatically installed in Firefox! ⚠️
Install "certutil" with "brew install nss" and re-run "mkcert -install" 👈
```

Firefox의 트러스트 스토어 지원과 관련된 것이며 Firefox를 쓰지 않으면 무시해도 된다고 설명한다.

로컬 CA를 설치하면 브라우저가 앞으로 만들 인증서를 신뢰하지 않는다고 불평하는 일이 없어진다.

```bash
# 프로젝트 폴더를 만들고 그 안에서 실행한다
mkcert localhost
```

두 파일이 생긴다.

| 파일                | 내용                 |
| ------------------- | -------------------- |
| `localhost-key.pem` | 개인키               |
| `localhost.pem`     | 공개키를 담은 인증서 |

이 인증서가 브라우저에게 받게 될 공개키가 `localhost`라는 이름의 서버에서 온 것임을 보장한다.
`localhost` 대신 다른 이름을 골라도 되는데, **그 이름을 hosts 파일에 커스텀 도메인으로 등록하는 것을 잊지 말라**고 덧붙인다.

### Node.js로 HTTPS 서버 만들기

키와 인증서 파일을 둔 같은 폴더에 `server.js`를 만든다.

```javascript
const https = require('https');
const fs = require('fs');

const options = {
  key: fs.readFileSync('localhost-key.pem'),   // mkcert가 만든 개인키
  cert: fs.readFileSync('localhost.pem')       // 공개키를 담은 인증서
};

https.createServer(options, function (req, res) {
  res.writeHead(200);
  res.end("I'm HTTPS-enabled!");
}).listen(8080);

console.log("The server is listening to port 8080 with HTTPS enabled.");
```

```bash
node server.js
```

그다음 `http://localhost:8080`으로 접속하면 서버가 평문 HTTP 통신을 시작하지 않는다는 화면이 나오고, `https://localhost:8080`으로 바꾸면 기대한 대로 응답한다고 설명한다.

## 실무에서 더 필요한 것들

이 글은 기본 설정까지만 다룬다. 실제로 쓰다 보면 부딪히는 문제들이 GN 스레드에서 구체적으로 나왔다.

### Windows에는 내장 명령이 있다

kunggom이 짚었다. Windows에도 PowerShell에 `New-SelfSignedCertificate`라는 명령어가 있어서 **별도의 외부 도구 설치 없이 자체 서명 인증서를 만들 수 있다**는 것이다.[^kunggom]

원문이 mkcert를 전제로 쓰였고 설치 안내도 그쪽뿐인데, Windows 환경에서는 이 경로가 더 짧다.

```powershell
# localhost용 자체 서명 인증서를 만들어 개인 인증서 저장소에 넣는다
New-SelfSignedCertificate -DnsName "localhost" -CertStoreLocation "cert:\LocalMachine\My"
```

다만 자체 서명 인증서를 만드는 것과 그것을 **신뢰하게 만드는 것**은 다른 작업이라는 점은 주의해야 한다.
mkcert의 `-install`이 하는 일이 후자이고, PowerShell 경로에서는 트러스트 스토어 등록을 따로 해야 한다.

### 인증서 관리 도구 선택

nicewook이 CFSSL은 어떠냐고 물었다. 자기도 그냥 OpenSSL을 써 왔는데 최근 읽는 책에서 CFSSL을 소개하더라며 장단점이나 비교가 궁금하다는 것이다.[^nicewook]

이 질문에 답이 달리지 않았지만 구분은 명확하다.

| 도구    | 성격                                      | 적합한 경우                           |
| ------- | ----------------------------------------- | ------------------------------------- |
| OpenSSL | 범용 저수준 도구                          | 세밀한 제어가 필요할 때               |
| mkcert  | 로컬 개발 전용. CA 생성·트러스트 설치까지 | 개인 개발 환경                        |
| CFSSL   | Cloudflare의 PKI 툴킷. API 서버 모드 지원 | 내부 CA를 운영하며 여러 서비스에 발급 |

즉 CFSSL은 이 글이 다루는 “개발자 한 명의 로컬 환경” 범위보다 한 단계 위의 도구다.

ngenius는 web.dev의 로컬 HTTPS 사용법 문서를 함께 소개했다.[^ngenius]

### 다른 기기에서 접속하는 문제

이 스레드에서 가장 실질적인 논의가 여기서 나왔다.

handohee가 문제를 제기했다.[^handohee]
로컬 서버에 스마트폰을 연결해 테스트할 때 HTTPS가 필수인 것 같은데, 자기 응용 분야는 **인터넷이 안 되는 로컬 네트워크인 경우가 많아 ngrok 류의 터널링을 쓸 수 없다**는 것이다.
위의 인증서 생성 방법은 되긴 하지만 관리가 편하지는 않았다며 다른 방법이 있는지 물었다.

ffdd270이 ngrok을 써 봤는데 굉장히 행복했다고 답했고,[^ffdd270] handohee가 다시 답했다.[^handohee-reply]
ngrok으로는 **인터넷도 안 되는 로컬 환경에서 안 되는 것**과 대역폭 한계로 테스트를 충분히 못 하는 문제가 있었다는 것이다.

galadbran이 Windows 환경의 우회법을 제시했다.[^galadbran]
개발 머신이 Windows 기반이라면 **Fiddler 같은 프록시를 띄우고 아이폰이나 안드로이드폰의 프록시 주소를 Fiddler 접속 주소로 설정하면 개발 머신의 hosts 파일 등이 적용**된다는 것이다.

이 교환이 원문이 다루지 않은 공백을 정확히 드러낸다.
원문은 `localhost` 인증서를 만드는 데서 끝나는데, `localhost`는 정의상 다른 기기에서 접근할 수 없는 이름이다.

그리고 이 질문에 대한 더 나은 답이 이후에 나왔다.
[localias](localias.md)가 **`.local` 도메인을 mDNS로 브로드캐스트**해 같은 네트워크의 휴대폰에서 개발 서버를 방문할 수 있게 한다.
인터넷 연결이 필요 없으므로 handohee가 말한 오프라인 로컬 네트워크 제약에 걸리지 않는다.

```bash
# 같은 와이파이의 다른 기기에서 접근 가능한 별칭
localias set frontend.local 8080
localias run
```

다만 이 경우에도 그 기기의 브라우저에서 인증서 경고가 뜬다. 로컬 루트 CA가 그 기기의 트러스트 스토어에 없기 때문이다.
localias 문서는 경고를 수락하고 진행해도 된다고 안내한다. 자기 로컬 개발 사이트이기 때문이다.

## 트레이드오프

### 자체 서명으로 충분한 범위가 정해져 있다

원문이 “개발 환경에서는 더 느슨해도 되며 자체 서명 인증서를 직접 만들 수 있다”고 정리하는데, 이 문장이 맞으면서도 경계를 흐린다.

정확히 말하면 mkcert가 만드는 것은 순수한 자체 서명 인증서가 아니다.
`mkcert -install`이 **로컬 CA를 만들어 트러스트 스토어에 넣고**, 그 CA가 서버 인증서에 서명한다.

이 차이가 실무에서 중요하다.

순수 자체 서명 인증서는 인증서마다 브라우저 경고를 수락해야 하고, 도구에 따라 `--insecure` 플래그를 붙여야 한다.
로컬 CA 방식은 한 번 신뢰를 설정하면 그 CA가 서명한 모든 인증서가 조용히 통과한다.

그래서 **편의가 크게 다르고 위험의 성격도 다르다**.

로컬 CA를 트러스트 스토어에 넣는다는 것은 그 CA의 개인키가 시스템의 TLS 신뢰를 좌우한다는 뜻이다.
[lcl.host 노트](lcl-host.md)에서 다룬 이름 제약 문제가 여기에도 그대로 적용된다. mkcert가 만드는 CA에는 이름 제약이 없다.

원문이 그 위험을 언급하지 않는다. `mkcert -install`을 한 줄로 안내하고 넘어간다.

### hosts 파일 편집에 붙은 경고가 충분하지 않다

커스텀 호스트명 절에서 “hosts 파일 내용을 바꾸면 특정 인터넷 도메인 접근에 문제가 생길 수 있다”는 경고를 넣은 것은 좋다.

그런데 그 문제가 무엇인지는 적지 않는다.

실제로 일어나는 일이 [localias 문서](localias.md)가 상세히 다루는 그것이다.

실제 도메인을 hosts에 매핑하면 **개발 쿠키가 프로덕션 요청에 섞이고**, 프로덕션이 HSTS를 쓰면 다른 개인키로 서빙하는 것을 브라우저가 명시적으로 금지하므로 무서운 오류가 난다.
그리고 HSTS 상태는 매핑을 지운 뒤에도 남는다.

원문이 `myhost.dev`를 커스텀 호스트명 예로 든 것도 아쉽다.
`.dev`는 **실제로 존재하는 TLD**이고 Google이 운영하며 **HSTS preload가 걸려 있다**. 즉 예시로 쓰기에 가장 나쁜 선택 중 하나다.

권장할 이름은 IETF가 예약해 둔 것들이다.

| TLD          | 성격                            |
| ------------ | ------------------------------- |
| `.test`      | 테스트 전용 예약. 가장 무난함   |
| `.example`   | 문서·예시 전용 예약             |
| `.invalid`   | 의도적으로 유효하지 않음을 표시 |
| `.localhost` | 루프백 전용 예약                |

### 이 방식은 한 사람의 기기를 넘어가지 않는다

원문의 절차가 개발자 한 명의 기기를 전제한다. mkcert로 CA를 만들고 그 기기의 트러스트 스토어에 넣는 것이다.

팀으로 확장하면 문제가 생긴다.

각자 자기 CA를 만들면 인증서가 서로 호환되지 않고, 하나의 CA를 공유하면 **개인키를 공유**해야 한다. 그것은 팀 전체의 TLS 신뢰를 파일 하나에 거는 일이다.

이 문제를 푸는 방향이 두 가지로 갈렸다.

[lcl.host](lcl-host.md)는 CA를 서비스로 옮겼다. 계정에 CA가 묶이므로 환경 사이를 옮겨 다닐 수 있고, 이름 제약으로 위험을 좁힌다.
[localias](localias.md)는 CA는 각자 만들되 **별칭 설정을 Git으로 공유**한다. 저장소 루트의 `.localias.yaml`이 그 역할이다.

원문은 2022년 글이고 이 문제를 다루지 않는다. 다만 독자가 이 절차를 팀에 도입하려 할 때 바로 부딪히는 지점이다.

## 함정

### 인증서 이름과 접속 이름이 어긋난다

브라우저가 가장 먼저 확인하는 것이 도메인명 일치라고 원문이 정확히 설명한다.

그런데 실무에서 이것이 자주 어긋난다.

`mkcert localhost`로 만든 인증서로 `https://127.0.0.1:8080`에 접속하면 실패한다. 이름이 다르기 때문이다.
컨테이너 안에서 서비스 이름으로 접속할 때도 마찬가지다.

mkcert는 여러 이름을 한 인증서에 담을 수 있다.

```bash
# 여러 이름과 IP를 한 인증서에 넣는다
mkcert localhost 127.0.0.1 ::1 myapp.test "*.myapp.test"
```

이렇게 만들면 파일명이 `localhost+4.pem` 형태가 되므로 서버 코드의 경로도 함께 고쳐야 한다.

### 인증서에 만료가 있다

원문이 브라우저가 만료일도 확인한다고 적지만, 개발 인증서의 만료를 관리하라는 말은 없다.

mkcert가 발급하는 인증서에도 유효 기간이 있고, 브라우저 정책이 강화되면서 그 기간이 짧아지는 추세다.
어느 날 갑자기 개발 환경이 인증서 오류를 내는 원인이 대체로 이것이다.

```bash
# 인증서 만료일 확인
openssl x509 -in localhost.pem -noout -dates
```

만료되면 같은 명령으로 다시 발급하면 된다. 로컬 CA는 그대로이므로 `mkcert -install`을 다시 할 필요는 없다.

이것이 [lcl.host](lcl-host.md)가 ACME 자동 갱신을 내세우는 이유이기도 하다.

### 서비스 워커는 HTTP localhost에서도 돌지만 그게 문제다

원문이 짚은 대로 일부 브라우저가 `localhost`와 `127.0.0.1`에서는 평문 HTTP로도 서비스 워커를 허용한다.

편해 보이지만 함정이다.

로컬에서 동작하던 것이 스테이징이나 프로덕션에서 동작하지 않을 수 있고, 그때 원인이 코드가 아니라 **프로토콜과 보안 컨텍스트**라는 것을 알아내기까지 시간이 걸린다.

같은 문제가 쿠키에서도 생긴다. `Secure` 속성이 붙은 쿠키는 HTTP에서 설정되지 않고, `__Host-` 접두사 쿠키는 더 엄격한 조건을 요구한다.
HTTP로 개발하면 이 코드 경로가 아예 실행되지 않으므로 테스트되지 않은 채 배포된다.

### 개발 인증서 파일을 저장소에 커밋하기 쉽다

`mkcert localhost`가 프로젝트 폴더에 `localhost-key.pem`을 만들고, 원문 예제가 그 폴더에 `server.js`를 두라고 안내한다.

그 폴더가 Git 저장소라면 개인키가 커밋될 수 있다.

로컬 개발용 키이므로 유출의 직접 피해는 제한적이지만, 두 가지 이유로 피해야 한다.
비밀 스캐너가 경고를 올리고, 팀원들이 같은 키를 쓰게 되어 앞서 말한 CA 공유 문제로 번진다.

```gitignore
*.pem
*-key.pem
```

## 체크리스트

- 개발 호스트명이 `.test`·`.example`·`.localhost` 중 하나인가? `.dev`나 실제 도메인을 쓰고 있지 않은가?
- 인증서에 실제로 접속할 모든 이름(호스트명, `127.0.0.1`, 컨테이너 이름)이 들어 있는가?
- `.pem` 파일이 `.gitignore`에 들어 있는가?
- Firefox를 쓴다면 `brew install nss` 후 `mkcert -install`을 다시 실행했는가?
- 프로덕션에서 CSP를 쓸 계획이라면 개발 환경에서도 같은 지시어를 적용해 보았는가?
- 다른 기기에서 테스트해야 하는가? 그렇다면 `localhost` 인증서로는 안 된다는 점을 알고 있는가?
- 개발 인증서의 만료일을 확인했는가?

## 기억할 원칙

### 개발 환경에서만 통과하는 코드 경로가 가장 위험하다

이 글의 논지가 환경 동등성인데, 그 원칙이 왜 중요한지를 가장 잘 보여 주는 것은 글이 든 혼합 콘텐츠 예가 아니라 **보안 기능들의 동작 조건**이다.

CSP 지시어, `Secure` 쿠키, `__Host-` 접두사 쿠키, 서비스 워커가 모두 같은 성질을 갖는다.
HTTPS에서만 의미가 있고 HTTP에서는 **조용히 무시되거나 다르게 동작한다**.

그래서 HTTP로 개발하면 이 코드들이 실행되지 않은 채로 배포된다. 테스트를 통과하는데 테스트한 적이 없는 상태다.

일반화하면 이렇다.
환경 차이가 오류를 일으키면 그나마 낫고, 조용히 다른 경로를 타면 **훨씬 나쁘다**.
전자는 개발 중에 드러나고 후자는 프로덕션에서 드러난다.

그리고 브라우저가 `localhost`를 특별 취급하는 것이 정확히 후자를 만든다.
편의를 위한 예외가 동등성을 깨는 지점이고, 원문이 그것을 “브라우저 제조사들이 강하게 권장하지 않는다”고 적은 이유다.

### 신뢰를 설치하는 것과 인증서를 만드는 것은 다른 작업이다

이 글에서 가장 자주 오해되는 부분이 `mkcert -install`과 `mkcert localhost`의 차이다.

앞의 것은 **로컬 CA를 만들어 시스템 트러스트 스토어에 넣는 일회성 작업**이고, 뒤의 것은 그 CA로 특정 이름의 인증서를 발급하는 반복 작업이다.

이 구분을 알면 여러 문제가 정리된다.

Firefox가 별도 트러스트 스토어를 쓰므로 `certutil`이 필요하다는 경고는 앞의 작업에 관한 것이다.
다른 기기에서 경고가 뜨는 것도 앞의 작업이 그 기기에서 이루어지지 않았기 때문이다.
인증서가 만료되면 뒤의 작업만 다시 하면 된다.

일반화하면, 로컬 TLS 문제를 만났을 때 먼저 물어야 할 것은 “인증서가 잘못되었나”가 아니라 **“누가 이 인증서를 신뢰해야 하는가”**다.

신뢰의 주체가 브라우저인지 명령줄 도구인지 다른 기기인지에 따라 확인할 트러스트 스토어가 달라지고, 그것이 [lcl.host](lcl-host.md)와 [localias](localias.md) 같은 도구가 자동화하려는 바로 그 작업이다.
