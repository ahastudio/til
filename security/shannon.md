# Shannon: 증명한 것만 보고하는 자율 침투 테스트 에이전트

<https://keygraph.io/>

<https://github.com/KeygraphHQ/shannon>

HN 토론: <https://news.ycombinator.com/item?id=46926419> (3점, 2개 댓글)

## 소개

Keygraph가 만든 웹 애플리케이션과 API용 자율 AI 침투 테스터다.
소스 코드를 분석해 공격 경로를 찾고,
실제 익스플로잇을 실행해 취약점이 프로덕션에 도달하기 전에 증명한다는 것이 한 줄 소개다.
저장소는 Shannon Open Source이며, 명령줄에서 직접 실행하는 전체 에이전트라고 밝힌다.
2026년 8월 24일 기준으로 별 47,153개, 포크 5,430개, 열린 이슈 30개, 워처 223명이다.
라이선스는 AGPL-3.0이고 주 언어는 TypeScript이며,
저장소는 2025년 9월 27일에 만들어졌고 마지막 푸시는 2026년 8월 21일이다.
릴리스는 2026년 8월 19일의 `v2.5.2`가 최신이고 같은 날 `v2.5.1`, 하루 전 `v2.5.0`이 나왔다.
README 맨 위에는 Shannon 2.0 정식 출시를 알리는 알림이 붙어 있고
Trendshift 배지도 함께 있다.

존재 이유를 밝힌 절의 논리가 이 도구의 프레이밍이다.
Claude Code와 Cursor 같은 도구 덕분에 팀은 끊임없이 코드를 출하하지만
침투 테스트는 1년에 한 번 일어난다는 것이다.
그래서 나머지 364일 동안 취약점을 모르는 채로 프로덕션에 내보내고 있을 수 있다.
Shannon은 모든 빌드나 릴리스마다 돌릴 수 있는
온디맨드 자동 침투 테스트를 제공해 그 공백을 메운다고 적는다.

실행은 두 명령이다.
`npx @keygraph/shannon setup`으로 대화형 마법사를 통해 자격증명을 설정하고,
`npx @keygraph/shannon start -u https://your-app.com -r /path/to/your-repo`로 실행한다.
Shannon은 Docker Hub에서 워커 이미지를 받아 필요한 로컬 인프라를 띄우고,
대상 저장소를 임시 워커 컨테이너 안에 읽기 전용으로 마운트한 뒤
결과를 로컬 워크스페이스에 쓴다.
사전 요구사항은 네 가지다.
워커 컨테이너를 위한 Docker,
권장 `npx` 워크플로를 위한 Node.js 18 이상,
AI 제공자 자격증명,
그리고 제공자와의 사이버 안전장치 확인이다.
마지막 항목은 Anthropic과 OpenAI가 사이버보안 워크로드에 실시간 안전장치를 적용하기 때문에
스캔이 실행 중간에 끊길 수 있으며,
첫 실행 전에 합법적 보안 테스터를 위한 안내 절차를 완료해야 한다는 내용이다.

주요 기능은 여덟 항목으로 정리된다.
추측성 경고 대신 재현 가능한 개념 증명 단계를 담은 익스플로잇 기반 리포트,
소스 코드 분석으로 동적 테스트를 유도하는 화이트박스 공격 계획,
정찰부터 취약점 분석과 익스플로잇과 리포트 생성까지 한 명령으로 실행하는 자율 실행,
로그인 흐름과 테스트 자격증명과 TOTP와 이메일 기반 로그인과 관심 영역과
교전 규칙을 설정 파일로 기술하는 인증된 테스트,
익스플로잇 가능한 Injection과 XSS와 SSRF와 인증 우회와 인가 우회를 겨냥하는 OWASP 중심 커버리지,
완료된 에이전트를 다시 실행하지 않고 중단된 실행을 이어가는 재개 가능한 워크스페이스,
구조화된 JSON과 설정으로 켤 수 있는 SARIF 2.1.0 출력,
그리고 자기 키를 쓰는 제공자 비종속 구성이다.
제공자는 Anthropic과 OpenAI와 xAI와 AWS Bedrock이 내장이고,
Anthropic Messages API나 OpenAI Chat Completions 또는 Responses API를 구현한
모든 엔드포인트를 커스텀 베이스 URL로 쓸 수 있다.
Ollama와 vLLM과 LM Studio로 서비스되는 자체 호스팅 모델과
OpenRouter와 LiteLLM 같은 게이트웨이도 기술적으로는 지원되지만 권장되지 않는다.
Shannon의 지시나 도구 사용 제약을 프런티어 모델만큼 안정적으로 따르지 못할 수 있기 때문이다.
Keygraph가 모델 트래픽을 중계하지 않는다는 점을 두 번 명시한다.

의도적으로 취약하게 만든 애플리케이션에 대한 샘플 리포트 세 건이 표로 제시된다.

| 대상             | 요약                                                             |
| ---------------- | ---------------------------------------------------------------- |
| OWASP Juice Shop | 인증 우회, SQL 인젝션, IDOR, SSRF를 포함한 20건 이상의 취약점    |
| c{api}tal API    | 명령 인젝션, 인증 우회, 대량 할당을 포함한 심각·높음 약 15건     |
| OWASP crAPI      | JWT, 인젝션, SSRF, API 인가 경로에 걸친 심각·높음 15건 이상      |

안전에 관한 경고는 여러 곳에 반복된다.
Shannon은 수동 스캐너가 아니라 실제로 익스플로잇을 실행하므로
사용자를 만들고 폼을 제출하고 애플리케이션 상태를 변경하고 외부 요청을 유발할 수 있다.
소유하거나 명시적 서면 승인을 받은 시스템에만 실행해야 하고
프로덕션에 실행하지 말라고 적는다.
샌드박스나 스테이징이나 로컬 개발 환경에서 폐기 가능한 데이터로 쓰라는 권고가 붙는다.
현재 외부 코드 기여는 받지 않으며 버그 리포트와 기능 요청 이슈만 환영한다고 밝힌다.
커뮤니티 오피스 아워가 목요일 미국·유럽 오전 10시 태평양시와 아시아 오후 2시 인도시에 열린다.

## 아키텍처

다단계 에이전트 워크플로가 아스키 도식으로 제시된다.
소스 코드 스캔인 사전 정찰에서 시작해 공격 표면 지도를 만드는 정찰로 넘어가고,
거기서 Injection과 XSS 등 취약점 유형별 에이전트로 병렬 분기한다.
각 취약점 에이전트 아래에 같은 유형의 익스플로잇 에이전트가 붙고,
모든 분기가 리포팅 단계로 합쳐진다.

각 단계의 역할은 다음과 같이 설명된다.
사전 정찰은 저장소에서 프레임워크와 진입점과 데이터 흐름과 유력한 공격 표면을 찾는다.
정찰은 실행 중인 애플리케이션을 탐색하고 런타임 동작을 코드 수준 맥락과 대응시킨다.
취약점 분석은 Injection과 XSS와 SSRF와 인증과 인가를 담당하는 전문 에이전트를 돌린다.
익스플로잇은 실제 개념 증명 공격을 시도하고 증명할 수 없는 가설을 버린다.
리포팅은 검증된 발견과 증거와 완화 지침을 최종 마크다운 리포트로 정리한다.
각 스캔은 격리된 워크스페이스와 호출별 오케스트레이션을 갖춘
임시 Docker 컨테이너 안에서 실행된다.

## 커버리지

`COVERAGE.md`는 OWASP 웹 보안 테스트 가이드 체크리스트를 그대로 옮겨 놓고
Shannon이 일관되고 안정적으로 처리하는 항목만 체크했다고 밝힌다.
동적 탐지가 다른 영역까지 확장되는 경우가 많지만
투명성을 위해 안정적으로 잡도록 설계된 것만 표시했다는 설명이 붙는다.
현재 겨냥하는 취약점 부류는 다섯 가지로 명시된다.
인증·인가 우회, SQL 인젝션, 명령 인젝션, XSS, SSRF다.
다루지 않는 것도 명시된다.
취약한 서드파티 라이브러리, 약한 암호 알고리즘, 안전하지 않은 설정처럼
능동적으로 익스플로잇할 수 없는 문제는 보고하지 않으며,
이 정적 분석 영역은 준비 중인 Keygraph Code Security(SAST) 제품이 담당한다.

체크리스트를 세어 보면 전체 109개 항목 중 52개가 체크되어 있다.
범주별 분포는 다음과 같다.

| 범주       | 항목                          | 체크  |
| ---------- | ----------------------------- | ----- |
| WSTG-INFO  | 정보 수집                     | 6/10  |
| WSTG-CONF  | 설정 및 배포 관리             | 2/14  |
| WSTG-IDNT  | 신원 관리                     | 5/5   |
| WSTG-ATHN  | 인증                          | 9/11  |
| WSTG-ATHZ  | 인가                          | 5/5   |
| WSTG-SESS  | 세션 관리                     | 7/11  |
| WSTG-INPV  | 입력 검증                     | 7/20  |
| WSTG-ERRH  | 오류 처리                     | 0/2   |
| WSTG-CRYP  | 암호                          | 2/4   |
| WSTG-BUSL  | 비즈니스 로직                 | 0/10  |
| WSTG-CLNT  | 클라이언트 측                 | 6/14  |
| WSTG-APIT  | API                           | 3/3   |

신원 관리와 인가와 API는 전 항목이 체크되어 있고,
인증도 11개 중 9개다.
반대로 비즈니스 로직 10개와 오류 처리 2개는 하나도 체크되지 않았고,
설정 관리는 14개 중 2개, 입력 검증은 20개 중 7개다.

## 에디션 구분

두 가지 형태로 제공된다는 서술이 README의 상당 부분을 차지한다.
Shannon Open Source는 직접 실행하는 단독 침투 테스터이고,
Keygraph 플랫폼은 Shannon을 지속적으로 돌리며
AppSec 생애주기 전체를 닫는 상용 제품이다.
플랫폼 쪽은 다섯 단계로 소개된다.
코드 속성 그래프 기반 SAST와 도달 가능성을 반영한 SCA와 비밀값과 IaC와 컨테이너 스캔인 분석,
후보 발견을 증명된 취약점으로 바꾸는 블랙박스·화이트박스 침투 테스트인 증명,
저장소별 취약점당 하나의 정본 레코드와 중복 제거와 소유자와 상태와 SLA와
양방향 Jira 동기화를 갖춘 관리,
패치를 자동 작성해 패치된 코드에 대해 재검증한 뒤 기존 리뷰 워크플로로 보내는 조치와 검증,
자체 호스팅과 에어갭 환경과 엄격한 BYOK 모델 접근인 배포다.

두 에디션을 비교한 표에서 가장 눈에 띄는 항목은 분석 단계다.
Shannon Open Source는 공격을 계획하기 위해
소스를 LLM에 넘기는 기본적인 통과 처리라고 적혀 있고,
Keygraph 플랫폼은 실제 코드베이스 파싱에 코드 속성 그래프와
SAST와 도달 가능성 SCA와 비밀값과 IaC와 컨테이너를 더한다고 적혀 있다.
발견 관리는 오픈소스가 로컬 마크다운 리포트이고,
조치는 리포트를 보고 수동으로 고친 뒤 전체 스캔을 다시 돌려 확인하는 방식이며,
플랫폼은 수정 PR을 열고 전체 재스캔 없이 지점 재검증으로 확인한다.
라이선스와 지원은 AGPL-3.0 커뮤니티 대 상용 지원으로 나뉜다.

## 분석

### 증명된 것만 보고한다는 규칙이 이 도구의 정체성이면서 커버리지의 정의다

README가 반복하는 문장은 하나다.
동작하는 개념 증명을 만들어 낸 경우에만 발견으로 보고하고,
증명할 수 없는 가설은 버린다는 것이다.
마지막 질의응답 항목에서 스캐너가 아니라 침투 테스터라고 못 눌러 두는 부분까지
같은 주장의 반복이다.

이 규칙이 왜 이 도구의 중심에 놓였는지는 AppSec의 실제 병목에서 나온다.
정적 분석 도구의 문제는 취약점을 찾지 못하는 것이 아니라 너무 많이 찾는 것이었다.
수천 건의 경고 중 실제로 위험한 것을 골라내는 작업이 사람의 시간을 소모하고,
그 비용이 임계를 넘으면 도구 전체가 무시된다.
익스플로잇 성공을 필터로 쓰면 그 문제가 사라진다.
증명이 곧 우선순위이고, 리포트에 남은 것은 전부 대응할 이유가 있는 것이다.

그런데 같은 규칙이 커버리지의 정의가 된다.
익스플로잇할 수 없는 것은 이 도구에 존재하지 않는다.
`COVERAGE.md`가 다루지 않는 것으로 나열한 항목들이 정확히 그 부류다.
취약한 서드파티 라이브러리는 그 자체로 익스플로잇 대상이 아니고,
약한 암호 알고리즘은 지금 당장 복호화되지 않고,
안전하지 않은 설정은 다른 조건이 겹칠 때 문제가 된다.
설계 결정으로서 일관되고, 문서에 명시되어 있어 정직하다.
동시에 그 결정이 무엇을 배제하는지는 도구 이름에서 드러나지 않는다.

### 에디션 비교표가 상품 설명보다 오픈소스 판의 한계를 정확히 밝힌다

기업이 오픈 코어 제품을 설명할 때 흔히 나오는 표는
상용 쪽에 기능을 더 나열하는 형태다.
이 표는 다르다.
분석 단계에서 오픈소스 판을 공격 계획을 위한 소스의 기본적인 LLM 통과 처리라고 적는다.
자기 제품의 핵심 기능을 이렇게 서술하는 것은 흔하지 않다.

이 문장이 알려 주는 것은 마케팅 포지션이 아니라 아키텍처다.
화이트박스라는 표현이 두 에디션에서 같은 의미가 아니라는 뜻이다.
오픈소스 판에서 소스 코드는 LLM 컨텍스트에 들어가는 텍스트이고,
플랫폼에서는 파싱되어 코드 속성 그래프가 된다.
전자는 모델의 독해력에 의존하고 후자는 정적 분석 자료구조에 의존한다.
큰 코드베이스에서 이 차이는 결정적이다.
컨텍스트에 넣을 수 있는 코드의 양이 상한이 되고,
그 상한을 넘으면 무엇을 넣을지 고르는 문제가 생기며,
그 선택 자체가 놓치는 공격 경로를 만든다.

이 정직함이 동시에 업셀 장치라는 점도 짚을 만하다.
표의 여섯 행 중 다섯 행에서 오픈소스 판의 칸이 최소 기능으로 적혀 있고,
그 옆 칸이 상용 제품의 기능 목록이다.
별 47,000개를 모은 도구가 자기 한계를 스스로 명시하는 구성은
신뢰를 만들면서 전환 경로를 함께 만든다.
그리고 이것이 이 저장소를 읽는 올바른 방식을 알려 준다.
무엇을 할 수 있는지가 아니라 어느 칸에 적혀 있는지를 보는 것이다.

### 사이버 안전장치가 사전 요구사항에 들어간 것은 정책 의존성의 등장이다

사전 요구사항 네 항목 중 세 개는 기술 의존성이다.
Docker와 Node.js와 API 키다.
네 번째는 다르다.
Anthropic과 OpenAI가 사이버보안 워크로드에 실시간 안전장치를 적용해
스캔이 중간에 끊길 수 있으므로,
첫 실행 전에 합법적 보안 테스터를 위한 안내 절차를 완료하라는 항목이다.

이 항목의 성질은 라이브러리 버전 요구사항과 완전히 다르다.
도구가 동작하려면 모델 제공자가 사용자를 정당한 보안 테스터로 인정해야 한다.
설치와 설정이 끝나고 대상에 대한 권한도 있는 상태에서,
실행 가능성이 제3자의 정책 판단에 걸린다.
그리고 그 판단이 실행 중간에 개입할 수 있다.
스캔이 한 시간을 넘기는 작업이므로 중간 차단은 재개 가능한 워크스페이스가
왜 기능 목록에 있는지에 대한 설명이 되기도 한다.

오픈소스 라이선스로 배포되는 도구가 이런 제약을 갖는 것은 새로운 구도다.
AGPL로 코드를 받아 자기 인프라에서 돌리는데,
그 실행의 성립 여부가 계정 정책에 달려 있다.
README가 제공자 비종속성을 두 번 강조하고
Keygraph가 모델 트래픽을 중계하지 않는다는 것을 두 번 적은 것이
이 제약에 대한 대응이다.
그런데 같은 문서가 로컬 모델은 권장되지 않는다고 적는다.
정책 제약을 피하는 경로가 있고, 그 경로의 대가가 결과 품질이다.

### 기여를 받지 않는 AGPL 저장소라는 조합

라이선스는 AGPL-3.0이고, 외부 코드 기여는 받지 않으며,
다른 조건이 필요한 조직을 위한 상용 라이선스 문의처가 안내된다.
포크는 5,430개다.

이 조합은 오픈 코어의 표준 형태이고 AGPL이 그 장치다.
네트워크를 통해 서비스로 제공하는 경우에도 소스 공개 의무가 생기므로,
이 코드를 기반으로 경쟁 서비스를 만드는 경로가 막힌다.
동시에 사용자가 직접 실행하는 것은 아무 제약이 없으므로
저장소의 용도인 로컬 CLI 실행에는 영향이 없다.
포크 비율이 별 대비 11퍼센트를 넘는 것도 이 용도와 맞는다.
읽기 위한 별과 쓰기 위한 포크의 비율이 라이브러리보다 높게 나오는 도구다.

기여를 받지 않는다는 결정은 그 자체로 판단할 일이 아니지만
커버리지와 함께 보면 의미가 생긴다.
체크되지 않은 57개 항목을 커뮤니티가 채울 수 있는 경로가 없다.
버그 리포트와 기능 요청은 열려 있고 코드는 닫혀 있으므로,
커버리지 확장 속도는 회사의 로드맵이 정한다.
오픈소스라는 단어가 여기서 의미하는 것은 열람과 실행의 자유이고
방향에 대한 참여는 포함되지 않는다.

## 비평

### 침투 테스터를 자처하지만 침투 테스터의 정의적 능력이 비어 있다

`COVERAGE.md`를 세어 보면 109개 항목 중 52개가 체크되어 있다.
절반에 조금 못 미친다.
그리고 비어 있는 쪽의 분포가 무작위가 아니다.
비즈니스 로직 10개 항목 전체가 비어 있다.

이것이 결정적인 이유는 이 도구가 스스로 정한 기준 때문이다.
스캐너가 아니라 침투 테스터라고 반복해 주장하며,
그 주장의 근거로 실제 익스플로잇 실행을 든다.
그런데 사람 침투 테스터를 자동 도구와 구별하는 능력은 익스플로잇 실행이 아니다.
익스플로잇 실행은 오래된 스캐너들도 한다.
사람이 하는 일 중 자동화되지 않은 부분이 바로 비즈니스 로직이다.
결제 흐름을 우회하고, 워크플로 순서를 뒤집고, 수량과 가격을 조작하고,
기능 사용 횟수 제한을 넘고, 승인 단계를 건너뛰는 종류의 공격이다.
체크리스트에서 비어 있는 열 개 항목이 정확히 그 목록이다.

빈 칸의 이유가 기술적으로 이해된다는 점이 비판을 약화시키지는 않는다.
비즈니스 로직 공격은 애플리케이션이 무엇을 하려는 것인지 알아야 성립하고,
그 의도는 코드에 명시되지 않는다.
그러므로 이 공백은 어려운 문제에 대한 정직한 미완이다.
문제는 프레이밍이다.
연 1회 침투 테스트와 364일의 공백이라는 서사는
이 도구가 그 침투 테스트를 대신할 수 있다는 전제 위에 있다.
실제 침투 테스트 리포트에서 가장 값어치 있는 발견이
비즈니스 로직 결함인 경우가 많다는 사실과 그 서사는 함께 성립하지 않는다.
전략적으로 초점을 맞췄다는 설명은 커버리지 문서에서는 맞는 말이지만,
연간 침투 테스트를 대체한다는 주장 옆에 놓이면 다른 이야기가 된다.

### 샘플 리포트가 모두 교육용 취약 앱이라 성능 신호가 되지 못한다

증거로 제시된 것은 세 건이다.
OWASP Juice Shop, c{api}tal API, OWASP crAPI.
셋 다 취약점을 찾는 연습을 위해 일부러 취약하게 만든 애플리케이션이다.

LLM 기반 도구를 이 대상으로 평가하는 것은 순환 논증에 가깝다.
이 앱들의 취약점은 문서화되어 있고, 워크스루가 공개되어 있고,
그 문서가 모델의 학습 데이터에 들어 있을 가능성이 매우 높다.
Juice Shop에서 SQL 인젝션을 찾았다는 결과가
소스 코드 분석 능력을 보여 주는지 사전 지식을 보여 주는지 구별할 방법이 없다.
실제 코드베이스에서 처음 보는 결함을 찾는 능력이 이 도구의 값어치인데,
제시된 증거는 그 능력을 측정하지 않는다.

측정 방식 자체도 정보를 담지 않는다.
20건 이상, 약 15건, 15건 이상이라는 표기가 전부다.
분모가 없다.
Juice Shop에 알려진 챌린지가 몇 개이고 그중 몇 개를 찾았는지가 재현율이며,
보고된 발견 중 몇 건이 실제였는지가 정밀도다.
둘 다 없다.
증명 기반이므로 오탐이 없다고 주장할 수는 있지만,
그 주장은 같은 README의 다른 문장과 충돌한다.
발견은 여전히 사람의 검토가 필요하며
LLM이 생성한 리포트에는 근거가 약하거나 틀린 내용이 있을 수 있다고 적혀 있다.
증명 여부를 판정하는 것도 LLM이라면
증명 기반이라는 필터의 강도는 그 판정의 정확도만큼이다.
그 정확도에 대한 수치가 없다.

### 프롬프트 인젝션이 한 줄로 처리되지만 이 도구의 위협 모델의 중심이다

한계 목록의 마지막 항목이 이렇다.
신뢰할 수 없거나 적대적인 코드베이스를 스캔하지 말라,
소스 코드를 읽는 AI 도구는 프롬프트 인젝션에 노출될 수 있다는 것이다.
정확한 경고이고, 그 자리에 놓일 만한 무게가 아니다.

이 도구의 구성을 보면 그 이유가 분명하다.
소스 코드를 읽고, 브라우저를 자동화하고, 명령줄 도구를 실행하는 에이전트다.
읽는 내용이 행동을 결정하고 그 행동에 셸이 포함된다.
컨테이너 격리는 호스트를 보호하지만 에이전트의 판단을 보호하지 않는다.
그리고 사용자 책임으로 넘기는 방식의 완화는
경계가 실무에서 성립할 때만 작동한다.
내 저장소라는 경계는 생각보다 약하다.
의존성 소스가 들어 있고, 테스트 픽스처가 있고,
외주나 인수로 들어온 코드가 있고, 사용자가 올린 템플릿이 있을 수 있다.

더 중요한 지점은 코드가 유일한 입력이 아니라는 것이다.
익스플로잇 단계에서 에이전트는 대상 애플리케이션이 반환한 내용을 읽고 다음 행동을 정한다.
HTTP 응답, 오류 메시지, 렌더링된 페이지, API 페이로드가 모두 컨텍스트로 들어간다.
침투 테스트의 대상은 정의상 신뢰할 수 없는 시스템이다.
스테이징 환경이라 해도 그 안의 데이터가 사용자 입력에서 온 것일 수 있고,
그 입력에 에이전트를 향한 지시가 들어 있을 수 있다.
즉 신뢰할 수 없는 코드베이스를 피하라는 조언을 완벽히 따라도
신뢰할 수 없는 입력을 읽는 구간이 남는다.
이 도구의 사용 방식 자체가 그 구간을 만든다.
README가 이 층위를 다루지 않는 것이 가장 큰 공백이다.

### 비용과 시간이 채택을 결정하는데 숫자가 없다

한계 목록에 시간은 있다.
전체 실행이 대략 1시간에서 1시간 30분 걸린다는 것이다.
비용은 없다.
모델 가격과 애플리케이션 복잡도에 따라 LLM API 비용이 발생할 수 있다고만 적혀 있다.

이 공백이 문제인 이유는 이 도구가 제안하는 사용 방식 때문이다.
모든 빌드나 릴리스마다 돌려 364일의 공백을 메우자는 것이 존재 이유의 요지다.
그런데 프런티어 모델로 다중 에이전트를 한 시간 반 돌리는 작업의 비용은
CI 파이프라인에 넣을 수 있는지를 결정하는 단일 변수다.
자릿수만 알아도 판단이 되는데 그 자릿수가 제시되지 않는다.
SARIF 2.1.0을 내보내 코드 스캐닝 서비스와 CI에 통합하라고 안내하면서,
그 통합이 경제적으로 가능한지에 대한 정보를 주지 않는다.

이 조합이 만드는 결과는 예측 가능하다.
독자는 우선 한 번 돌려 보고 청구서를 보고 나서 빈도를 정하게 된다.
그것은 평가 과정이 아니라 시행착오다.
샘플 리포트 세 건을 만들 때 각각 얼마가 들었는지를 적는 것만으로
이 문제가 해결된다.
이미 실행해서 리포트를 저장소에 넣어 두었으므로 그 숫자는 존재한다.
공개하지 않은 것은 정보가 없어서가 아니다.
대상 규모에 따른 대략적 비용 구간을 밝히는 것은
경쟁 정보를 노출하는 종류의 일이 아니라 도입 판단에 필요한 최소 정보다.

## 인사이트

### 증명 기반 필터는 신뢰를 사고 커버리지를 팔았으며 그 교환의 부호는 조직에 따라 다르다

이 도구의 설계 결정 하나가 나머지를 다 설명한다.
익스플로잇으로 증명된 것만 보고하겠다는 것이다.
그 결정은 정적 분석 도구의 실패사에 대한 반작용이다.
오탐이 쌓이면 사람이 무시하고, 무시되면 도구가 없는 것과 같아진다.
그 문제를 근본에서 없애는 방법이 증명을 통과 조건으로 삼는 것이다.

그런데 정밀도를 극단으로 올리면 재현율이 내려간다.
그리고 두 오류의 가시성이 다르다.
오탐은 리포트에 나타나므로 비용이 눈에 보이고,
미탐은 아무 곳에도 나타나지 않으므로 비용이 사고가 날 때까지 보이지 않는다.
증명 기반 도구가 신뢰를 얻는 이유가 여기 있고,
그 신뢰가 위험한 이유도 여기 있다.
깨끗한 리포트가 안전을 뜻하지 않는데, 깨끗한 리포트의 심리적 효과는 안전이다.

이차 효과는 보안 부채의 정의가 바뀌는 데서 나온다.
증명된 것만 관리 대상이 되면
지금 익스플로잇되지 않지만 위험한 것들이 목록에서 사라진다.
오래된 라이브러리, 약한 암호 파라미터, 지나치게 넓은 권한, 잘못된 설정이 그렇다.
이것들의 성질은 조건이 바뀌면 익스플로잇 가능해진다는 것이다.
새 엔드포인트가 하나 추가되면 도달할 수 없던 취약한 함수에 도달하게 되고,
그 순간에 부채가 사고로 바뀐다.
익스플로잇 가능성은 코드의 속성이 아니라 코드와 배포 형태의 함수이며,
증명 기반 접근은 그 함수의 현재 값만 본다.

그래서 이 도구를 어디에 두어야 하는지가 조직의 상태에 달린다.
트리아지할 사람이 없는 팀에는 정밀도가 가장 값어치 있는 속성이고,
이 도구가 곧바로 순이익이다.
이미 SAST를 운영하며 경고 목록을 관리하고 있는 팀에는
커버리지 공백이 더 비싼 문제이고,
이 도구의 올바른 자리는 SAST의 대체가 아니라 SAST 결과의 우선순위 판정기다.
어떤 정적 경고가 실제로 도달 가능한지를 익스플로잇으로 판정하는 용도다.
그리고 그것이 정확히 Keygraph 플랫폼이 구성한 파이프라인이다.
분석과 증명을 붙여 놓은 그 구조가 원래 필요한 형태이고,
오픈소스 판은 그중 증명 절반만 준다.
이 도구를 단독으로 쓰는 사람은 절반을 쓰고 있다는 사실을 알고 써야 한다.

### 모델 제공자의 안전장치가 이 범주의 새로운 단일 실패점이다

사전 요구사항에 들어간 사이버 안전장치 항목은 사소해 보이지만
보안 도구의 역사에서 처음 등장하는 종류의 제약이다.

과거에도 보안 도구는 차단당했다.
스캐너가 IDS에 걸리고 WAF에 막히고 레이트 리밋에 걸렸다.
그 차단의 주체는 방어자였고, 그것은 도구가 제대로 작동한다는 증거였다.
지금의 구도는 다르다.
차단의 주체가 도구의 동력원이다.
내가 소유한 시스템에 대해 서면 승인을 갖고 실행하는데,
모델 제공자가 이 워크로드를 어떻게 분류하는지에 따라 실행이 중단된다.

이차 효과는 사실상의 라이선스 체계가 생긴다는 것이다.
합법적 보안 테스터를 위한 안내 절차를 완료해야 한다는 요구는
심사와 승인의 절차이고, 그 승인의 발급자가 모델 제공자다.
보안 테스트를 할 자격을 판정하는 새 게이트키퍼가 등장한 것이며,
이 게이트는 국가나 인증기관이 아니라 사기업의 정책팀이 운영한다.
BYOK와 제공자 비종속 설계가 이에 대한 대응이지만 완전하지 않다.
게이트를 우회하는 경로인 로컬 모델을
README 자신이 권장하지 않는다고 두 번 적는다.
자유를 얻는 경로가 품질을 대가로 요구하는 구조다.

이 게이트가 왜 생겼는지는 이 도구에 대한 첫 반응들이 알려 준다.
저장소가 HN에 네 번 올라갔고 모두 한 자릿수 점수에 머물렀는데,
댓글이 달린 유일한 스레드에서 나온 질문이 오용 가능성이었다.
`jeremykalfus`는 이름이 영리하다고 적으면서
여기에 오용의 여지가 있어 보이는데 어떻게 완화하는지를 물었다.[^jeremykalfus]
`hendler`가 그에 대해 정리한 답이 이 범주의 구도를 그대로 담고 있다.
오픈소스이므로 화이트햇 도구이지만
동시에 스크립트 키디가 심각한 피해를 입힐 수 있게 만든다는 것,
그리고 이런 일이 모든 곳에서 동시에 벌어지고 있으므로
결국 하드웨어를 가장 많이 가진 쪽이 군비 경쟁에서 이기는 것 아니냐는 것이다.[^hendler]
저장소가 제시하는 완화 수단은 경고문과 라이선스뿐이며,
둘 다 실행을 막지 못한다.
서면 승인을 받은 대상에만 쓰라는 문장은 규범이고 강제가 아니다.
그렇다면 실제로 강제력을 갖는 지점은 하나 남는다.
모델 제공자의 안전장치다.
사전 요구사항에 들어간 그 항목이 불편한 절차로 보이지만,
`jeremykalfus`의 질문에 대해 이 생태계가 내놓은 유일한 구속력 있는 답이다.
그리고 그 답의 성질은 기술적 통제가 아니라 계정 심사다.

여기서 나오는 예측은 두 가지다.
첫째, 보안 도구가 모델을 고를 때 성능과 함께 정책 관용도를 고려하게 된다.
어느 제공자가 어떤 워크로드를 어디까지 허용하는지가
벤치마크 점수와 나란히 놓이는 선택 기준이 된다.
둘째, 이 심사 절차가 규모의 문제를 만든다.
기업 계정으로 심사를 통과할 수 있는 조직과
개인 계정으로 시작하는 연구자 사이에 접근 격차가 생긴다.
보안 연구가 역사적으로 개인의 호기심에서 나왔다는 점을 생각하면
이 격차가 장기적으로 무엇을 줄이는지는 분명하다.
자율 침투 테스터의 확산이 방어 능력을 민주화한다는 서사는
그 확산의 전제 조건이 심사 통과라는 사실과 함께 읽어야 한다.

### 이 도구의 실제 경쟁 상대는 사람 침투 테스터가 아니라 코드를 쓰는 에이전트다

존재 이유 절의 논리는 이렇다.
AI 코딩 도구로 출하 속도가 올라갔고 침투 테스트는 연 1회에 머물러 있으니
검증 속도를 출하 속도에 맞추자는 것이다.
비대칭을 정확히 지적한 프레이밍이다.
그런데 같은 비대칭에 다른 해법이 있고, 그 해법이 같은 기술에서 나온다.

생성 속도가 올라간 원인이 코드를 쓰는 에이전트라면
개입점은 두 곳이다.
쓰는 시점과 검증하는 시점이다.
Shannon은 검증 시점을 고르고, 그 시점의 특성은 사후이고 비싸다는 것이다.
실행에 한 시간 반이 걸리고 LLM 비용이 들고 대상이 실행 중이어야 한다.
쓰는 시점은 반대다.
PR 단위로 수십 초 안에 피드백이 오고 대상이 실행될 필요가 없다.
같은 모델 예산을 코드 리뷰 쪽에 쓰면 훨씬 잦은 개입을 얻는다.

역사적으로 이 경쟁의 결과는 한쪽으로 기울었다.
런타임에 버그를 찾는 것과 컴파일 시점에 버그를 막는 것 사이에서,
막는 쪽이 이겼다.
타입 시스템과 컴파일러 경고와 린터가
디버거보다 더 많은 결함을 실제로 제거했다.
이유는 정확도가 아니라 빈도다.
개발자가 코드를 쓰는 순간에 개입하는 도구는 하루에 수십 번 작동하고,
릴리스 전에 도는 도구는 주에 한 번 작동한다.

그러면 이 도구의 실제 자리는 README가 말하는 곳이 아닐 가능성이 높다.
모든 빌드마다가 아니라 릴리스 게이트나 분기별 감사다.
그리고 그 자리는 원래 사람 침투 테스트의 자리이므로,
이 도구가 실제로 바꾸는 것은 연 1회를 분기 1회나 월 1회로 만드는 것이다.
그것도 충분히 큰 개선이다.
다만 364일의 공백을 메운다는 서사와는 다른 주장이며,
1시간 30분이라는 실행 시간이 그 차이를 이미 말해 준다.
도구의 경제성이 프레이밍보다 정확한 지표다.

### 커버리지의 빈 칸은 기술적 난이도가 아니라 제품 경계로 결정된다

`COVERAGE.md`에서 다루지 않는 것으로 나열한 세 항목을 다시 읽어 보면
그것이 무엇인지 알 수 있다.
취약한 서드파티 라이브러리, 약한 암호 알고리즘, 안전하지 않은 설정이다.
그리고 바로 다음 문장이 이 영역을 Keygraph Code Security가 담당한다는 안내다.
즉 다루지 않는 것의 목록이 상용 제품의 기능 목록이다.

이 대응은 우연일 수도 있고 아닐 수도 있지만,
확인할 방법이 있다는 점이 중요하다.
에디션 비교표와 커버리지 문서를 겹쳐 보면 된다.
오픈소스 판이 최소 기능으로 적힌 칸과
체크되지 않은 WSTG 범주가 같은 영역을 가리킨다.
설정 관리가 14개 중 2개인 것과 IaC 스캔이 플랫폼 기능인 것,
취약한 의존성을 다루지 않는 것과 도달 가능성 SCA가 플랫폼 기능인 것이 짝을 이룬다.
기술적으로 어려워서 비어 있는 칸과
제품 경계 때문에 비어 있는 칸이 같은 문서에 섞여 있다.

이차 효과는 커뮤니티 기여를 받지 않는 결정과 결합할 때 나온다.
기여가 열려 있다면 비어 있는 칸 중 쉬운 것들은 채워진다.
설정 헤더 검사나 HTTP 메서드 테스트는 난이도가 높지 않다.
기여가 닫혀 있으면 그 칸들은 회사가 채울 때까지 비어 있고,
회사가 채울 유인은 그것이 상용 제품의 판매 영역인지에 달려 있다.
오픈소스 판의 커버리지가 기술 발전이 아니라 제품 전략의 함수가 된다는 뜻이다.

그래서 이 도구를 평가할 때 물어야 할 질문이 하나 바뀐다.
이 도구가 무엇을 못하는지가 아니라,
못하는 것 중 무엇이 상용 제품의 기능 목록에 들어 있는지다.
전자에 대한 답은 시간이 지나면 개선될 수 있고,
후자에 대한 답은 개선되지 않을 가능성이 크다.
같은 판단 틀이 이 범주의 다른 도구에도 적용된다.
자율 보안 에이전트를 오픈소스로 내놓는 회사들이 늘어나고 있고,
그 대부분이 같은 구조를 갖고 있다.
`security/strix.md`와 `security/pentagi.md`에 정리한 도구들도
공개 범위와 상용 범위의 경계가 능력의 경계처럼 제시되는 같은 형태다.
커버리지 문서를 공개한 것은 이 저장소의 장점이고,
그 문서를 제품 경계 지도로 읽는 것이 그 장점을 제대로 쓰는 방법이다.
