# Project Zero의 새 공개 정책

원문: [Policy and Disclosure: 2026 Edition](https://projectzero.google/2026/11/disclosure-policy.html)

HN 토론: <https://news.ycombinator.com/item?id=50496051> (261점, 130개 댓글)

GN 토론: <https://news.hada.io/topic?id=37190>

## 요약

Project Zero의 Natalie Silvanovich가 2026년 11월 13일에 올린 정책 발표이다.
이 문서는 글 전문을 읽었다.
글의 모든 서술은 Project Zero의 설명이다.

2021년부터 Project Zero는 벤더에게 취약점 수정에 최대 90일, 패치 배포를 위한 “소크 타임” 30일을 더 주는 “90 + 30” 정책을 써 왔다.
글은 AI 보조 취약점 발견과 악용이 위협 환경을 바꾸어 이 일정이 명백히 부족해졌다고 쓴다.
이유는 세 가지이다.

- LLM이 공격자가 취약점을 찾고 악용하는 속도를 높였고, 여러 당사자(악의적 당사자 포함)가 같은 버그를 발견할 위험도 키웠다. 오늘 보고된 취약점은 작년의 것보다 사용자에게 훨씬 큰 즉각적 위험이다.
- LLM이 패치를 보고 역공학해 악용하는 시간도 줄여서, 패치 후 악용까지 시간이 0이라는 모형이 불완전하지만 합리적이다. 그래서 패치 소크 타임은 더 이상 의미가 없고 거짓 비밀의 감각을 만들 뿐이다. 수정이 배포된 뒤 사용자가 설치하기까지의 “패치 격차(patch gap)”를 벤더가 줄이는 것도 똑같이 중요하다.
- LLM이 Project Zero가 보고하는 취약점 수도 늘렸다. 예전에 1년에 몇 건 찾던 대상에서 이제 일주일에 여러 건을 찾고, 벤더와의 협상이나 합의가 필요한 정책 요소(수정 여부 판단, 유예 적용 여부)는 관리하기 어려워지고 있다.

새 정책은 “Full X”이다. 취약점은 벤더에게 보고한 지 X일 뒤에 공개된다.
오늘부터 “Full 90”(90일), 2027년 2월 2일부터 “Full 60”(60일), 2028년 1월 3일부터 “Full 30”(30일)이다.
유예 기간과 변종 정책을 비롯해 대부분의 특례를 없앤다. 예외는 셋뿐이다.

- 이미 악용 중인 취약점: Google의 애플리케이션 보안 취약점 공개 정책에 따른다.
- 이미 공개된 취약점: 다른 곳에서 세부 내용이 공개되었으면 Project Zero도 재량으로 공개할 수 있다.
- 벤더의 요청: 보고받은 벤더가 요청하면 공개한다.

점진적으로 줄이는 이유는 이렇게 설명한다.
가장 많이 보고하는 벤더들에게 의견을 구했더니, 정책을 즉시 바꾸면 벤더가 수정 절차를 개선하는 동안 미수정 취약점이 공격자에게 노출되어 사용자가 해를 입을 수 있다는 우려가 있었다.
다른 우려로는 지나치게 공격적인 정책이 덜 심각한 버그를 우선 처리하게 만들 수 있다는 것, 벤더가 맞출 수 없는 정책을 즉시 시행하면 기한 안에 못 고친다고 받아들이고 시도조차 하지 않게 될 수 있다는 것이 있었다.
그래서 도전적이지만 현실적인 일정을 택했다고 한다.

심각도에 관해서는 Project Zero가 상당한 심각도와 입증된 보안 영향이 있는 취약점만 추적기에 올린다고 하면서도, 심각도는 공개 결정의 효과적인 기준이 아니라고 쓴다. 심각도는 공격자가 발견할 가능성에는 영향이 없고 사용자에게 미치는 영향에만 관계되기 때문이다.
하드웨어는 Spectre와 Meltdown처럼 드물게 예외를 허용했고 앞으로도 그럴 수 있다고 한다.
수정 여부를 확인하는 일은 계속 추적하고 수정되지 않았으면 알리겠지만 정책의 결정 지점은 아니다. 벤더에게 이진 판정의 결과를 지우지 않고 사용자가 어떻게 보호되는지 기술 세부를 공유하기 위해서라고 한다.

## 분석

### 중심 주장은 방어 일정의 가정이 바뀌었다는 것이다

글은 기존 정책의 두 구성(90일 수정, 30일 소크)이 각각 다른 가정에 기대었다고 본다.
수정 90일은 같은 버그를 다른 사람이 곧 찾지 않는다는 가정에, 소크 30일은 패치에서 악용까지 시간이 걸린다는 가정에 기댄다.
두 가정을 LLM이 약하게 만들었다는 것이 글의 논리이다.
이 논리는 Project Zero의 관찰(주당 여러 건)과 추정(패치 후 악용 시간 0)에 서 있고, 글은 수치나 측정을 제시하지 않는다.

### 자동화가 정책 설계의 목표로 들어갔다

글은 정책을 Project Zero와 벤더 양쪽이 자동화할 수 있게 한다는 목표를 명시한다.
“수정되었는가”를 협상하는 대신 달력이 결정한다. 그래서 유예와 변종 정책 같은 협상 요소가 사라졌다.
보고량이 늘어나는 상황에서 이 선택은 운영 부담을 줄이는 쪽으로 일관된다.

## 비평

### 30일이 근거에 비해 가혹하다는 반론

HN에서 가장 먼저 나온 반응은 일정에 대한 의문이었다.
한 댓글은 소크 타임을 없애는 근거는 설득력이 있었지만 전체를 30일로 줄이는 것은 가혹하고 글이 충분히 정당화하지 못했다고 했다.[^wowfunhappy]
다른 댓글은 훨씬 더 빠르게, 사실상 0일로 가야 한다고 했고,[^massroot]
또 다른 댓글은 보상금이 걸린 경우에는 기다릴 이유가 있지만 즉시 공개만이 벤더를 움직인다고 했다.[^glitchc]
글은 30일에 이르는 이유를 소크 타임 폐지와 별개로 설명하지 않고, 벤더 의견 수렴 때 일정이 “도전적이지만 현실적”이라고 판단했다고만 쓴다.

### 압력인지 공공 서비스인지를 둘러싼 논쟁

한 댓글은 이것이 협박의 한 형태 아니냐고 물었다. 거대 기업 Google이 보안을 명분으로 모두에게 작업 우선순위를 강제한다는 것이다.[^bmitc]
답글은 Project Zero가 취약점을 만들지 않고 찾는 것이며, 벤더는 무제한 시간을 원하고 사용자는 빨리 알기를 원하므로 긴장이 있고 그래서 기한이 필요하다고 했다.[^sethaurus]
다른 답글은 Google이 취약점을 만들지 않고 검증해 공개하는 것이어서 공공 서비스라고 했다.[^exoticpeartree]
글 자신은 벤더의 우려를 반영해 점진적으로 줄인다고 쓰므로 이 논쟁에 대한 직접 답은 없다.

### 벤더 생태계의 현실적 지연

한 댓글은 Android의 현재 패치와 공개 사이 긴 지연이 어떻게 맞춰질지 궁금해했고, 답글은 그 사슬 전체가 훨씬 빨라질 것이라고 했다.[^aissen][^fc417fc802]
다른 댓글은 AOSP가 패치를 6개월 늦추는 정책을 두고 있으며 이유가 “보안 개선”이었는데 지금은 빠른 패치와 느린 패치 중 무엇이 보안을 높이느냐고 비꼬았다.[^cookiengineer]
또 한 댓글은 Ubuntu가 훨씬 더 많은 시간이 필요할 것이라고 했고, 답글은 Ubuntu의 최근 취약점 대응 시간을 보고 Debian으로 옮겼다고 했다.[^wewewedxfgdf][^dannyw]
이는 개인 경험이고 글은 특정 벤더를 언급하지 않는다.

### AI 도구 접근을 벤더에게 주어야 한다는 제안

한 댓글은 버그를 찾는 회사들이 벤더나 오픈 소스 프로젝트가 패치할 수 있게 같은 도구 접근도 제공해야 한다고 했다. 아니면 벤더가 이를 자기 LLM을 쓰게 만드는 지렛대로 쓸 수 있다는 것이다.[^frost1x]
답글은 Project Zero가 GenAI 이전부터 있었고 이 버그를 찾는 “제품”은 그곳 사람들이라고 반박했다.[^sumeno]
이 논점은 글이 다루지 않는다. 글이 AI를 이야기하는 방식은 위협 환경이다.

## 인사이트

### 벤더가 준비할 일은 패치 격차를 줄이는 것이다

글에서 벤더에게 직접 요구하는 것은 두 가지이다.
수정을 더 빨리 내놓는 것, 그리고 패치가 나온 뒤 사용자가 받기까지의 시간(패치 격차)을 줄이는 것이다.
글은 후자를 “패치 롤아웃 시간을 줄이거나 수정이 진행되는 동안 사용자를 보호할 다른 전략”으로 풀 수 있다고 하고, 코드 경로를 일시적으로 끄는 것 같은 비패치 전략도 언급한다.
2027년 2월과 2028년 1월의 일정이 고정되어 있으므로 벤더는 지금부터 역산해 수정 절차를 맞춰야 한다.

### 공개 날짜가 예측 가능해졌다는 점이 방어자에게 유리하다

“보고일 + X일”은 협상 없이 계산되는 날짜이다.
벤더는 자기 쪽 달력을 이 날짜에 맞춰 수정과 배포, 완화책을 계획할 수 있다.
이는 글의 자동화 목표에서 이 문서가 끌어낸 해석이다.

### 확인할 관찰

이 정책의 효과를 가를 관찰은 세 가지이다.
벤더들의 실제 수정 시간이 60일과 30일 일정에 맞춰 줄어드는지,
기한 내 수정하지 못해 공개되는 사례에서 사용자 피해가 생기는지,
다른 취약점 공개 프로그램이 같은 방향으로 움직이는지이다.
셋 모두 이 문서가 확인하지 못했다.
