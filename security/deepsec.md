# DeepSec: 패턴 스캐너와 코딩 에이전트를 잇는 보안 리뷰 하네스

원문: [A deep dive into DeepSec, Vercel's AI security scanner](https://flaviocopes.com/deepsec/)

GN 토론: <https://news.hada.io/topic?id=34093>

## 소개

DeepSec은 Vercel이 내놓은 오픈소스 보안 스캐너이고 Apache 2.0 라이선스다.
빠른 패턴 스캐너와 Codex나 Claude 같은 코딩 에이전트를 한 파이프라인에 묶는다.
패턴 스캐너가 들여다볼 가치가 있는 코드를 찾아내면, 코딩 에이전트가 그 코드를 읽고
파일을 넘나들며 데이터를 따라가고 방어 장치가 있는지 확인한 다음 보안 발견 사항을 쓴다.

저장소 전체를 훑을 수도 있고 풀 리퀘스트에서 바뀐 파일만 볼 수도 있는데,
저자가 강조하는 것은 앞쪽이다.
대부분의 코드는 오늘날의 최고 모델에게 한 번도 검토받은 적이 없기 때문이다.
풀 리퀘스트 스캐너는 새 코드를 보지, 3년 전에 쓴 인증 코드나 출시 이후 바뀐 적 없는 웹훅을 자동으로 다시 보지 않는다.
DeepSec은 그 더 큰 일을 위해 만들어졌다는 것이다.

무엇이 아닌지를 먼저 정해 두는 것이 이 도구를 쓰는 데 더 중요하다.
저장소가 안전하다는 것을 증명해 주지 않으며, 제품을 이해하는 사람들이 쓴 위협 모델,
의존성과 비밀 정보 스캔, 보안 테스트, 런타임 모니터링, 민감한 코드의 수동 검토,
고위험 시스템의 침투 테스트 중 어느 것도 대체하지 않는다.
버그를 놓칠 수 있고 일부 발견 사항은 틀린다.
그리고 모든 처리를 내 기계에서 하지도 않는다.
로컬 실행 중에도 저장소는 내 기계에 있지만 선택한 모델 제공자는 관련 코드와 프롬프트를 받는다.
비공개 코드를 스캔하기 전에 제공자와 게이트웨이의 데이터 정책을 확인해야 한다.

마지막 경계가 가장 자주 잊힌다.
DeepSec은 신뢰할 수 있는 저장소를 위해 설계되었다.
프로젝트에 접근 권한을 가진 코딩 에이전트처럼 다루어야 하며,
신뢰할 수 없는 풀 리퀘스트를 로컬에서 겨냥해 놓고 그 코드가 내 기계에 닿을 수 없다고 가정하면 안 된다.

## 파이프라인

이 도구가 흥미로운 이유는 보안 검토를 상태가 저장되는 반복 가능한 공정으로 다룬다는 데 있다.

```text
저장소 → 인벤토리 → 패턴 스캔 → AI 조사 → 재검증 → 보고서
```

패턴 스캔이 탐색 범위를 좁히고 에이전트가 느린 추론을 맡는다.
두 번째 에이전트 단계가 결과를 재검증하며, 이 단계는 거짓 양성을 걷어 내고 심각도를 조정할 수 있다.

전통적인 정적 스캐너는 알려진 패턴을 찾는다.
문자열로 조립된 SQL 질의, 인증 래퍼가 눈에 띄지 않는 라우트, 사용자 입력을 다른 서버로 보내는 호출 같은 것이다.
빠르고 예측 가능하지만 맥락이 없다.
어떤 라우트가 사용자가 준 URL을 읽는다는 것은 패턴으로 알 수 있어도,
다른 함수가 그 URL을 검증하는지, 그 라우트가 공개인지, 그 요청이 사설 네트워크에 닿을 수 있는지는 알 수 없다.
코딩 에이전트는 그 질문들을 조사할 수 있다.

모든 단계는 `.deepsec/` 디렉터리 안에 저장되고, 나중 실행은 처음부터 다시 하는 대신 저장된 상태에서 이어 간다.
이것이 코딩 에이전트에게 저장소를 보안 관점에서 검토해 달라고 한 줄 프롬프트를 주는 것과의 핵심 차이다.
그 프롬프트도 쓸모가 있지만 커버리지 확인, 증분 상태, 재개 가능한 작업,
구조화된 발견 사항, 재검증, 안정된 보고서 형식을 주지 않는다.
DeepSec은 보안 검토를 둘러싼 하네스다.

## 첫 실행을 통제하기

필요한 것은 Node.js 22 이상, npm이나 pnpm이나 Yarn, Git 저장소, 지원되는 코딩 에이전트 모델 접근 권한, 그리고 코드를 스캔할 권한이다.
DeepSec은 `.deepsec/` 안에 자체 Node.js 작업 공간을 만들기 때문에 상위 프로젝트가 JavaScript일 필요는 없다.
TypeScript, Go, Python, Lua, Terraform을 비롯한 텍스트 기반 코드베이스를 검토할 수 있다.

무엇을 할지 먼저 보고 싶다면 저장소를 바꾸지 않고 계획만 출력할 수 있다.

```bash
npx deepsec init --plan --output json
```

작업 공간 뼈대만 만들고 멈출 수도 있다.

```bash
npx deepsec init --scaffold-only
```

이 명령은 패키지를 설치하지도, 로그인하지도, 모델을 고르지도, 저장소를 스캔하지도, 유료 처리를 시작하지도 않는다.
중요한 저장소라면 이 경로를 쓰고 새 디렉터리를 검토한 뒤 쓸 만한 설정 파일을 커밋하고 이어 가라는 것이 저자의 조언이다.

패턴 스캔은 로컬이고 무료이지만 AI 처리는 아니다.
큰 저장소에서 제한 없는 첫 실행을 시작하지 말고 비용과 시간 상한을 걸어야 한다.

```bash
npx deepsec init \
  --max-cost-usd 25 \
  --max-duration 30m
```

둘 중 하나에 도달하면 안전한 지점에서 멈추고, 같은 명령을 다시 실행하면 끝난 작업은 건너뛰고 이어 간다.
상한은 실행 단위로 적용되므로 재개한 실행을 합친 총액은 따로 세어야 한다.

더 작게 시작하려면 파일 수를 제한한다.
`.deepsec/` 안에서 실행한다.

```bash
pnpm deepsec process --limit 50
```

50개 파일이면 전부 처리하기 전에 비용과 속도와 발견 사항의 품질을 가늠할 수 있다.

인증 경로는 셋이다.
기본값은 Vercel AI Gateway이고, 필요하면 설정 과정에서 Vercel에 로그인해 작업 공간용 작은 프로젝트를 만든다.
이미 Codex나 Claude가 기계에 인증되어 있다면 그 세션을 쓸 수 있다.

```bash
npx deepsec init --model-auth local
```

이 방식에서는 게이트웨이 토큰이나 API 키를 설정하지 않지만, 선택한 하네스가 로그인되어 있어야 한다.
저자는 이 경로로 자기 사이트를 스캔했고 OpenAI API 키 없이 기존 ChatGPT 구독으로 돌렸다고 밝힌다.
다만 구독 한도가 큰 저장소의 전체 스캔에는 모자랄 수 있고, 로컬 자격 증명은 원격 샌드박스로 전달할 수 없다.

직접 키를 쓰려면 셸 기록에 남지 않도록 임시 변수에 먼저 넣는다.

```bash
read -s MY_OPENAI_KEY
export MY_OPENAI_KEY
```

그다음 설정에 변수 이름을 넘긴다.

```bash
npx deepsec init \
  --agent codex \
  --model-auth direct \
  --ai-provider openai \
  --ai-api-key-env MY_OPENAI_KEY
```

DeepSec은 값이 아니라 환경 변수 이름을 저장한다.
이후 실행 때마다 변수를 다시 제공하거나 `.deepsec/.env.local`에 넣고 그 파일을 Git 밖에 두어야 한다.
Anthropic이라면 `--agent claude --ai-provider anthropic`으로 바꾼다.

## 생성된 작업 공간과 INFO.md

설정이 끝나면 저장소에 `.deepsec/`가 생긴다.

```text
.deepsec/
  deepsec.config.ts
  generated-matchers.ts
  package.json
  AGENTS.md
  data/
    my-app/
      INFO.md
      SETUP.md
      project.json
      setup/
      files/
      runs/
      reports/
```

이 디렉터리는 상위 애플리케이션과 격리되어 자체 `package.json`과 의존성과 설정과 상태를 갖는다.
생성된 `.gitignore`는 자격 증명과 재현 가능한 스캔 상태를 저장소 밖에 두고,
`INFO.md`와 `SETUP.md`와 `deepsec.config.ts`와 `generated-matchers.ts`는 커밋할 수 있게 남긴다.
그 정책을 그대로 받아들이기 전에 검토해야 한다.
보안 보고서에는 민감한 코드 경로와 취약점 세부가 담길 수 있다.

`INFO.md`는 이 파이프라인에서 가장 값어치 있는 파일이다.
코딩 에이전트에게 이 저장소가 무엇을 하는지 알려 주는 문서이며, 모든 조사와 재검증과 분류 프롬프트에 포함된다.
설정이 자동으로 쓰지만 사람이 읽고 고쳐야 한다.
저자의 사이트에 대해 생성된 첫 판본은 이런 모양이었다.

```markdown
# flaviocopes.com

## What this codebase does

- Astro 7 site deployed as static output on Cloudflare Pages
- Public browser tools, mostly running in the browser
- Pages Functions for newsletters, sponsorships, course recovery, and purchases
- A scheduled Worker and several local operational scripts

## Auth shape

- There is no user account system or authenticated application area
- Paddle webhook signatures protect the purchase flow
- Public forms use Turnstile and IP-based rate limits
- Course URLs are possession-based credentials

## Known false positives

- Lessons and posts contain security examples that are not production code
- Public IDs and Turnstile site keys are not secrets
- Editor commands and MCP configuration are local tooling
```

세 번째 절이 특히 중요하다.
이 저장소에는 수업 자료로 일부러 안전하지 않게 쓴 코드가 들어 있는데, 그것은 학생에게 보여 주는 텍스트이지 운영 엔드포인트가 아니다.
그 사실을 미리 적어 두면 에이전트가 같은 발견을 반복해서 올리지 않는다.

`INFO.md`에 넣을 것은 짧고 사실적인 항목들이다.
제품이 무엇을 하는지, 신뢰할 수 없는 입력이 어디로 들어오는지, 사용자가 어떻게 인증하는지,
권한 검사가 어떻게 되는지, 어떤 데이터가 민감한지, 지켜져야 하는 불변식이 무엇인지,
그리고 안전하지 않아 보이지만 의도된 알려진 패턴이 무엇인지다.
비밀 정보는 넣지 않는다.

## 커버리지가 결과의 의미를 정한다

이 글에서 가장 중요한 개념이고, 대부분의 보안 스캐너 사용법에서 빠지는 부분이다.

설정 과정에서 DeepSec은 진입점의 구조화된 인벤토리를 만든다.
HTTP 라우트, RPC 핸들러, 큐 소비자, 크론 작업, 명령줄 명령, 웹훅, 에이전트 도구가 여기 들어가고
`data/<project>/setup/` 아래에 저장된다.
그리고 그 표면들을 자기 매처가 실제로 닿은 파일과 비교한다.

이유는 간단하다.
스캐너가 발견 사항 0건을 보고하는 경우는 두 가지다.
코드가 안전해서일 수도 있고, 올바른 파일을 한 번도 보지 않아서일 수도 있다.
두 결과는 화면에서 구별되지 않는다.
그래서 결과에 의미가 생기려면 커버리지를 먼저 확인해야 한다.

중요한 표면에 매처 커버리지가 없으면 설정이 프로젝트 전용 매처를 만들어 보고,
그래도 커버리지가 확보되지 않으면 유료 AI 단계에 들어가기 전에 멈춘다.
저자는 이것을 좋은 실패 방식이라고 부른다.
안심시키는 빈 보고서를 돌려주는 대신 사각지대를 보여 주기 때문이다.

## 매처 다루기

매처는 조사할 보안 민감 코드를 고르는 규칙이며, 대개 파일 경로와 정규식을 조합한다.
예를 들어 `src/rpc/` 안에서 RPC 핸들러를 등록하는 호출을 찾는 식이다.
매처가 취약점을 증명할 필요는 없다.
이 파일에 진입점이나 위험한 연산이 있으니 에이전트가 읽어야 한다고 말하는 것이 전부다.

잡음 수준은 셋이다.

| 수준      | 뜻                                     |
| --------- | -------------------------------------- |
| `precise` | 특정 버그를 강하게 시사하는 패턴       |
| `normal`  | 에이전트 조사가 필요한 유용한 후보     |
| `noisy`   | 모든 파일이 검토 가치가 있는 좁은 계열 |

매처가 넓을수록 비싼 AI 단계에 도달하는 파일이 많아진다.

설정이 받아들인 프로젝트 전용 규칙은 `.deepsec/generated-matchers.ts`에 저장된다.
이것들은 선언적 데이터이고, DeepSec은 쓰기 전에 경로와 정규식과 예시와 후보 수를 검증하며
이 단계에서 모델이 쓴 TypeScript를 실행하지 않는다.
그래도 사람이 읽어야 한다.
각 매처가 실제 소스 디렉터리를 가리키는지, 안정된 코드 패턴을 표현하는지, 생성된 파일을 포함하지 않는지,
주장하는 표면에 실제로 닿는지, 후보 수가 합리적인지를 확인한다.

하나만 골라 시험해 볼 수 있다.

```bash
pnpm deepsec scan --matchers internal-rpc-entrypoint
```

생성된 매처로 표현할 수 없는 규칙은 코드로 쓴다.
애플리케이션이 `registerRpc('users.get', getUser)` 같은 형태로 내부 핸들러를 등록한다고 하면
`.deepsec/matchers/internal-rpc.ts`를 이렇게 만든다.

```ts
import { regexMatcher, type MatcherPlugin } from 'deepsec/config'

export const internalRpc: MatcherPlugin = {
  slug: 'internal-rpc-entrypoint',
  description: 'Internal RPC entry points',
  noiseTier: 'normal',
  filePatterns: ['src/rpc/**/*.ts'],
  examples: ["registerRpc('users.get', getUser)"],
  match(content) {
    return regexMatcher(
      'internal-rpc-entrypoint',
      [{ regex: /registerRpc\s*\(/, label: 'RPC registration' }],
      content
    )
  },
}
```

설정에 등록할 때 생성된 플러그인을 지우지 않는 것이 중요하다.

```ts
import { defineConfig, type DeepsecPlugin } from 'deepsec/config'
import { generatedMatchersPlugin } from './generated-matchers.js'
import { internalRpc } from './matchers/internal-rpc.js'

const projectMatchers: DeepsecPlugin = {
  name: 'web-app-matchers',
  matchers: [internalRpc],
}

export default defineConfig({
  projects: [{ id: 'web-app', root: '..' }],
  plugins: [generatedMatchersPlugin, projectMatchers],
})
```

목표는 완전한 정적 분석기를 쓰는 것이 아니라 더 깊은 검토에 넘길 파일을 고르는 것이다.

## 일상 워크플로

초기화 이후에는 `.deepsec/` 안에서 작업한다.

```bash
pnpm deepsec status      # 현재 상태 확인
pnpm deepsec scan        # 로컬 매처 스캔, 모델 호출 없음
pnpm deepsec process     # 선택한 코딩 에이전트로 후보 처리
pnpm deepsec revalidate  # 발견 사항 재검증
pnpm deepsec report      # 요약 생성
pnpm deepsec export --format md-dir --out ./findings
```

`scan`은 저장소를 읽어 활성 매처를 적용하고 일치하는 파일에 후보 기록을 만든다.
모델을 호출하지 않으므로 자주 돌려도 된다.
여기서 지켜야 할 구분이 있다.
후보는 발견 사항이 아니다.
매처가 `dangerouslySetInnerHTML`을 보았다면 그 코드는 검토할 가치가 있지만,
값이 이미 살균되었을 수도 있고 신뢰된 정적 콘텐츠를 그릴 수도 있고 진짜 저장형 XSS일 수도 있다.
후보는 에이전트에게 출발점을 주는 것이다.

DeepSec은 Next.js, React, Express, Fastify, NestJS, Hono 같은 기술을 감지해
프레임워크별 매처를 켜고 조사 프롬프트에 관련 위협 힌트를 더할 수 있다.

`process`가 돈을 쓰기 시작하는 단계다.
대기 중인 후보 파일을 묶음으로 가져가 선택한 코딩 에이전트 백엔드에 넘기며,
에이전트는 소스 파일, 일치한 부분, `INFO.md`의 프로젝트 맥락,
파일을 넘나들며 코드를 따라갈 저장소 도구, 그리고 구조화된 출력 형식을 받는다.
호출자와 미들웨어와 검증과 권한 검사를 찾아본 뒤 발견 사항을 0건 이상 돌려준다.
각 발견 사항에는 심각도, 확신도, 해당 줄, 설명, 권장 수정이 담기고
모델과 에이전트와 시각과 가능하면 비용과 분석 이력이 함께 기록된다.
분석 이력은 덧붙이기만 하므로 나중에 다른 모델을 돌려도 앞선 분석이 지워지지 않는다.

## 결과를 처리하기: 재검증과 분류는 다른 질문이다

에이전트는 코드를 오해할 수 있다.
`revalidate`는 다른 에이전트 단계에게 그 발견 사항을 다시 보게 하며,
결과는 참 양성, 거짓 양성, 이미 수정됨, 불확실, 중복 중 하나가 된다.
결과가 많으면 심각도가 높은 것부터 시작한다.

```bash
pnpm deepsec revalidate --min-severity HIGH
```

재검증도 돈이 든다.
코드를 다시 읽고 Git 이력까지 살펴볼 수 있다.
그리고 문서 자체가 재검증 이후에도 눈에 띄는 거짓 양성 비율을 보고한다고 저자는 적는다.
제목만 보고 운영 사고를 열거나 위험한 패치를 적용하지 말라는 것이 그의 조언이다.

분류는 다른 질문에 답한다.

```bash
pnpm deepsec triage
```

심각도와 작업 우선순위는 관련은 있지만 같지 않다.
도달할 수 없는 내부 프로토타입의 높은 심각도 버그가 공개 결제 엔드포인트의 중간 발견보다 덜 급할 수 있다.
분류는 발견 사항의 텍스트를 읽어 P0, P1, P2, 건너뜀 같은 우선순위를 매기고 악용 가능성과 영향을 함께 고려한다.
소스를 다시 읽지 않는 더 싼 분류 단계이므로 재검증을 대체하지 않는다.
재검증은 이 발견이 진짜인가를 묻고, 분류는 언제 손대야 하는가를 묻는다.

쓸 만한 발견 사항은 시스템을 관통하는 경로를 서술한다.

```text
신뢰할 수 없는 입력 → 빠진 통제 → 민감한 연산 → 영향
```

구체적으로는 이런 모양이다.

```text
URL에서 온 청구서 ID
  → 테넌트 소유권 검사 없음
  → 청구서 ID로 데이터베이스 질의
  → 다른 테넌트의 청구서가 반환됨
```

코드를 고치기 전에 화살표 하나하나를 확인해야 한다.
공격자가 제어하는 입력이 그 연산에 실제로 닿는지, 다른 곳에 방어가 있는지를 본 다음 판단한다.
수정은 공유되는 가장 좁은 경계에 넣고, 실패해야 하는 경우에 대한 테스트를 더하고,
평소 테스트와 DeepSec을 다시 돌린다.
파일 해시가 소스가 바뀌었음을 알려 준다.
중요한 사안이라면 다른 에이전트 백엔드에게도 조사를 시키라고 저자는 권한다.
두 결과가 일치하는 것은 유용한 증거이지만 증명은 아니라는 단서가 붙는다.

## 사례: 504건이 몇 갈래의 작업이 되기까지

저자는 처음에 자기 사이트 전체를 스캔할 생각이 없었다.
대부분이 정적 콘텐츠이고 민감한 부분은 Cloudflare Pages Functions, 구매 웹훅,
강의 복구, 공개 도구, 운영 스크립트로 훨씬 작기 때문이다.
그런데도 전체 스캔을 돌렸고, 그것이 이 글에서 가장 쓸모 있는 교훈을 남겼다.
발견 사항의 수는 해야 할 변경의 수가 아니라는 것이다.

모델은 Codex의 `gpt-5.6-sol`에 추론 강도를 최고로 두었고 로컬 Codex 로그인으로 ChatGPT 구독을 통해 돌렸다.
설정은 저장소를 살펴 위협 모델을 쓰고 커버리지를 확인한 뒤 프로젝트 전용 매처 넷을 만들었다.
둘은 Astro 페이지 진입점을, 하나는 로컬 Node.js 운영 스크립트를, 나머지 하나는 Codex MCP 서버 등록을 찾았다.

결과는 이랬다.

| 항목             | 수치                       |
| ---------------- | -------------------------- |
| 조사한 파일      | 729개                      |
| 잠재적 발견 사항 | 504건                      |
| 심각도 분포      | 치명적 1, 높음 16, 중간 67 |
| 영향이 큰 버그   | 42건                       |
| 일반 버그        | 378건                      |
| 입력 토큰        | 약 1,440만                 |

화면에는 비용이 0달러로 표시되었는데 모델이 로컬 ChatGPT 구독으로 돌았기 때문이다.
별도 API 청구서가 없었을 뿐 구독 용량은 썼다는 점을 저자는 짚어 둔다.

504라는 숫자는 놀랍지만 화면의 표현은 잠재적 발견 사항이었고, 다음 지시는 재검증이었다.
첫 결과가 504항목짜리 할 일 목록이 되도록 의도된 적이 없다는 것이다.

저자는 저장소에서 Codex를 열어 DeepSec 결과를 분석하게 했다.
전부 고치라고 하지 않고 무엇이 중요하고 무엇이 기다려도 되고 무엇이 실제 운영 위험이 아닌지를 물었다.
쓴 프롬프트는 이런 모양이다.

```text
Analyze the findings saved by DeepSec in this repository.
Do not change any files.

Group related findings by root cause.
Separate remotely reachable production risks from local scripts,
content examples, and normal product bugs.

Tell me which issues need attention first and explain why.
```

이 두 번째 단계는 저장소와 DeepSec의 증거와 현재 구조를 모두 갖고 있었으므로
심각도 표가 답할 수 없는 질문에 답할 수 있었다.
이 코드가 인터넷에서 도달 가능한지, 공격자가 입력을 제어할 수 있는지,
다른 파일에 이미 방어가 있는지, 이것이 보안 문제인지 평범한 제품 버그인지,
같은 근본 원인이 여러 발견에 걸쳐 있는지, 실패했을 때의 실제 영향이 무엇인지다.

숫자는 빠르게 줄었다.
504건 중 462건이 `src/tools`와 `src/pages/tools`에서 나왔고, 그곳은 사이트에 올린 작은 브라우저 도구들이 모인 디렉터리다.
378건은 일반 버그로 분류되었고 잘못된 계산, 깨진 출력, 경계 조건, 사용자 인터페이스 문제 같은 것들이었다.
고칠 가치가 있을 수는 있어도 378건의 보안 비상은 아니다.
게다가 같은 문제가 도구 구현과 그 Astro 페이지 양쪽에 나타난 경우가 있어, 공유된 원인 하나를 고치면 여러 보고가 함께 닫혔다.

도달 가능성과 영향으로 묶고 나자 작업은 세 영역의 짧은 목록이 되었다.
서버 쪽 구매와 강의 복구와 공개 폼 흐름,
능동적 콘텐츠를 그리거나 명령과 코드를 생성하는 브라우저 도구,
그리고 신뢰할 수 없는 데이터가 셸이나 파일 시스템 연산에 닿을 수 있는 로컬 운영 스크립트다.
나머지는 평범한 제품 품질 백로그로 가거나 수동 확인을 기다리거나, 보고된 경로가 실재하지 않으면 버려졌다.

저자가 정리한 순서는 그대로 재사용할 만하다.
DeepSec에게 위협 모델과 인벤토리를 만들게 하고,
모델 호출에 돈이 든다면 범위를 제한한 표본을 먼저 돌리고,
첫 출력을 잠재적 발견 사항으로 다루고,
중요한 결과를 재검증하고,
코딩 에이전트에게 근본 원인과 도달 가능성으로 묶게 하고,
코드를 바꾸기 전에 중요한 경로를 확인한다.
그리고 실천 규칙 하나가 남는다.
신뢰할 수 없는 입력이 인증, 비공개 데이터, 돈, 인프라, 되돌릴 수 없는 작업과 만나는 지점에서 시작하라는 것이다.

## CI에 넣기

바뀐 파일만 검토하려면 기준 브랜치와 비교한다.

```bash
pnpm deepsec process --diff origin/main
pnpm deepsec process --diff-staged    # 스테이징된 변경
pnpm deepsec process --diff-working   # 커밋되지 않은 것과 추적되지 않은 파일
```

직접 모드는 세 가지를 한다.
바뀐 파일을 찾고, 그 파일에 로컬 매처를 돌리고,
매처가 걸리지 않은 파일이라도 바뀐 파일 전부를 에이전트에게 검토시킨다.

풀 리퀘스트용 요약을 만들 수도 있다.

```bash
pnpm deepsec process \
  --diff origin/main \
  --comment-out comment.md
```

파일은 새 발견 사항이 나올 때만 만들어진다.
종료 코드는 새로 찾은 것이 없으면 0, 하나 이상이면 1이고 그 밖의 값은 명령 실패를 뜻한다.
그래서 CI 관문으로 쓸 수 있는데, 저자는 자문 모드로 시작하라고 권한다.
보고서를 산출물로 저장해 품질을 검토한 뒤, 팀이 비용과 거짓 양성을 이해하게 되었을 때 차단 검사로 바꾸라는 것이다.

풀 리퀘스트 CI에서는 조심할 것이 하나 더 있다.
풀 리퀘스트는 애플리케이션 코드만 바꾸지 않는다.
`package.json`과 설치 스크립트와 DeepSec 설정처럼 CI에서 실행되는 파일도 바꿀 수 있다.
그래서 한 작업에 신뢰할 수 없는 풀 리퀘스트 코드와 강한 저장소 권한을 함께 주면 안 된다.
권한을 나눠야 한다.

```text
작업 1: 코드 읽기 + 검토 실행 + 산출물 쓰기
작업 2: 살균된 산출물 읽기 + PR 댓글 쓰기
```

첫 번째 작업은 저장소를 수정할 권한이 없어야 하고, 두 번째 작업은 풀 리퀘스트 코드를 실행하면 안 된다.
포크에서 온 풀 리퀘스트는 일반 `pull_request` 이벤트에서 저장소 비밀 정보를 받지 않으므로 건너뛰거나 격리된 환경으로 옮긴다.
그리고 검토 작업에는 모델 자격 증명이 존재하므로, 악의적인 변경은 그 작업에서 접근 가능한 어떤 비밀이든 훔치려 할 수 있다.
서드파티 GitHub Action은 전체 커밋 해시로 고정하고, 권한을 좁히고,
외부 기여에 비밀을 쥔 분석을 돌리기 전에 신뢰할 수 있는 승인을 요구해야 한다.

예약 실행은 신뢰된 기본 브랜치를 돌기 때문에 더 단순하다.

```yaml
name: deepsec scheduled scan

on:
  workflow_dispatch:
  schedule:
    - cron: '0 6 * * 1'

permissions:
  contents: read

jobs:
  scan:
    runs-on: ubuntu-latest
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile
        working-directory: .deepsec
      - run: pnpm deepsec scan
        working-directory: .deepsec
      - run: pnpm deepsec process
        working-directory: .deepsec
        env:
          AI_GATEWAY_API_KEY: ${{ secrets.AI_GATEWAY_API_KEY }}
      - run: pnpm deepsec revalidate --min-severity HIGH
        working-directory: .deepsec
        env:
          AI_GATEWAY_API_KEY: ${{ secrets.AI_GATEWAY_API_KEY }}
      - run: pnpm deepsec export --format md-dir --out ./findings
        working-directory: .deepsec
```

이 워크플로는 대기 중인 후보 전부를 깨끗한 CI 실행에서 처리한다.
켜기 전에 로컬에서 제한된 스캔을 먼저 돌려 봐야 한다.
그리고 생성된 상태는 보통 Git이 무시하므로, `--limit`으로 작업을 여러 예약 실행에 나눌 생각이라면
`.deepsec/data/`를 비공개 저장소에 보존해야 한다.
그러지 않으면 깨끗한 러너마다 같은 첫 묶음을 다시 처리한다.
취약점 보고서를 공개 빌드 로그에 내보내지 않도록 별도의 비공개 산출물 단계도 필요하다.

큰 저장소는 Vercel Sandbox 마이크로 VM으로 작업을 나눌 수 있다.

```bash
pnpm deepsec sandbox process \
  --project-id web-app \
  --sandboxes 10 \
  --concurrency 4
```

호스트가 실제 모델 자격 증명을 쥐고 모델 제공자로 가는 요청에만 붙이므로 샌드박스는 원본 자격 증명을 보지 않는다.
다만 샌드박스 팬아웃은 인프라와 인증과 업로드 시간과 비용을 더한다.
기계 열 대가 한 대보다 그럴듯해 보여서가 아니라 작업량이 그것을 요구할 때 쓰라는 것이 저자의 조언이다.

## 값 정하기

| 결정할 것             | 무엇에 따라 정하는가                                                     |
| --------------------- | ------------------------------------------------------------------------ |
| 첫 실행 비용 상한     | 표본 50개 파일의 실측 비용에 전체 후보 수를 곱한 값의 일부               |
| 표본 크기             | 발견 품질을 판단할 수 있는 최소치. 50개가 출발점                         |
| 매처 잡음 수준        | 표면이 얼마나 위험한가. 결제와 인증은 넓게, 표현 계층은 좁게             |
| 재검증 범위           | 심각도 기준. 처음에는 `HIGH` 이상, 신뢰가 쌓이면 확대                    |
| CI 관문 여부          | 팀이 거짓 양성 비율을 실측했는가. 실측 전에는 자문 모드                  |
| 샌드박스 팬아웃       | 로컬 실행이 예정된 창을 넘기는가. 넘기지 않으면 쓰지 않는다              |
| `.deepsec/` 커밋 범위 | 보고서에 민감한 코드 경로가 담기는가. 설정만 넣고 결과는 비공개 저장소로 |

## 함정

발견 사항의 수를 작업의 수로 읽는 것이 가장 비싼 실수다.
504건 중 462건이 한 디렉터리에서 나왔고 378건은 보안 문제가 아니었다.
첫 출력의 이름이 잠재적 발견 사항인 데는 이유가 있다.

발견 사항 0건을 안전의 증거로 읽는 것이 그다음이다.
커버리지 확인을 건너뛰면 아무것도 보지 않았다는 것과 볼 것이 없었다는 것을 구별할 수 없다.
DeepSec이 커버리지 실패 시 유료 단계 전에 멈추는 것은 이 혼동을 막기 위한 설계다.

같은 근본 원인이 여러 발견으로 쪼개져 올라온다.
도구 구현과 그것을 감싸는 페이지가 각각 보고되는 식이다.
근본 원인으로 묶지 않고 하나씩 처리하면 같은 수정을 여러 번 하게 되거나, 가장 좁은 공유 경계가 아닌 곳에 수정을 넣게 된다.

구독으로 돌리면 비용이 0달러로 표시된다.
청구서가 없을 뿐 구독 용량을 쓴 것이므로, 이 수치를 근거로 전체 스캔의 비용을 추정하면 안 된다.
실제로 DeepSec 저장소를 다룬 별도의 HN 글타래에서 한 이용자가
구독은 평가용으로는 쓸 만하지만 저장소 전체 스캔에는 여유가 부족하니 게이트웨이를 쓰라는 문서 문구를 인용하며 회의를 표한 적이 있다.[^nh43215rgb]
평가 단계와 운영 단계의 비용 구조가 다르다는 점은 도입 판단에서 먼저 확인해야 한다.

매처가 시끄러운 이유가 범위가 잘못된 것인데 무시 목록으로 결과를 감추는 것도 함정이다.
`ignorePaths`는 조사하면 안 되는 파일을 위한 것이고, 범위가 틀린 매처는 매처를 고쳐야 한다.

신뢰할 수 없는 저장소를 로컬에서 겨냥하는 것이 가장 위험한 실수다.
이것은 프로젝트 접근 권한을 가진 코딩 에이전트를 그 코드에 붙이는 일이다.

마지막으로 이 도구가 잘 맞지 않는 곳이 있다.
민감한 서버 코드가 없는 정적 사이트, 외부 입력이 없는 작은 스크립트,
프로젝트별 위협 맥락이 없는 라이브러리, 생성된 코드,
내 기계에서 신뢰할 수 없는 저장소, 그리고 발견 사항을 검토하고 고칠 사람이 없는 프로젝트다.
작은 수정마다 값싼 검사를 돌리는 것이 목적일 때도 맞지 않는다.
빠른 되먹임에는 평범한 린터와 테스트와 의존성 스캐너와 좁은 정적 규칙을 쓰고,
저장소 수준의 깊은 추론이 비용을 치를 가치가 있는 곳에 이 도구를 쓴다.

## 기억할 원칙

### 스캐너의 결과는 커버리지를 확인하기 전까지 아무 뜻도 없다

발견 사항 0건은 두 가지 세계에서 똑같이 나온다.
코드가 안전한 세계와, 스캐너가 그 코드를 한 번도 보지 않은 세계다.
화면만 보고 둘을 구별할 방법은 없다.

그래서 보안 도구를 도입할 때 가장 먼저 물어야 하는 것은 무엇을 찾았느냐가 아니라 무엇을 보았느냐다.
진입점 목록을 따로 만들고 도구가 실제로 읽은 파일과 대조해야 하며,
그 대조가 자동화되어 있지 않은 도구라면 사람이 해야 한다.
DeepSec이 커버리지가 확보되지 않을 때 유료 단계 전에 멈추는 설계를 좋은 실패 방식이라고 부르는 이유가 이것이다.
안심시키는 빈 보고서보다 사각지대를 보여 주는 중단이 낫다.

이 원칙은 보안에 국한되지 않는다.
테스트 커버리지, 로그 수집 범위, 모니터링 대상 목록 모두 같은 구조를 갖는다.
이상이 없다는 신호와 보고 있지 않다는 신호가 같은 모양으로 도착하는 곳에서는, 보고 있는 범위를 따로 재야 한다.

### 두 질문을 분리해야 우선순위가 생긴다

DeepSec이 재검증과 분류를 다른 명령으로 나눠 둔 것은 구현 편의가 아니라 판단의 구조다.
재검증은 이것이 진짜인가를 묻고 소스를 다시 읽는다.
분류는 언제 손대야 하는가를 묻고 텍스트만 읽는다.
두 질문은 비용도 다르고 필요한 정보도 다르다.

이 구분이 없으면 심각도 하나로 두 질문에 동시에 답하게 되고, 그 결과는 대개 잘못된 순서다.
도달할 수 없는 내부 프로토타입의 치명적 발견이 공개 결제 엔드포인트의 중간 발견보다 앞에 놓인다.
심각도는 문제가 얼마나 나쁜지를 말할 뿐 얼마나 급한지를 말하지 않으며,
급함은 도달 가능성과 영향에서 나온다.

같은 분리가 버그 트래커와 사고 대응과 기술 부채 목록에도 적용된다.
사실 확인과 우선순위 결정을 한 번에 하려 하면 둘 다 흐려진다.
먼저 진짜인 것만 남기고, 그다음에 남은 것들 사이의 순서를 정한다.
