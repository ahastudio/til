# OAuth 2.0 브라우저 앱: 토큰을 브라우저에 두지 않는 쪽이 권고안이다

원문: [RFC 10017: OAuth 2.0 for Browser-Based Applications | RFC Editor](https://www.rfc-editor.org/info/rfc10017/)

## 소개

RFC 10017은 2026년 8월에 나온 IETF Best Current Practice(BCP)다.
저자는 Aaron Parecki, Philippe De Ryck, David Waite이고,
브라우저에서 실행되는 자바스크립트 앱이 OAuth 2.0 클라이언트일 때
위협, 공격 결과, 보안 고려 사항, 모범 사례를 정리한다.
네이티브 앱용 RFC 8252(AppAuth)와 OAuth 2.0 보안 BCP인 RFC 9700을 토대로 하며,
RFC 9700의 권고를 브라우저 앱에 맞게 더 좁힌다.

이 RFC가 깔고 있는 전제는 하나다.
악성 자바스크립트는 정상 앱 코드와 같은 권한을 가진다(§5).
XSS를 막으려는 노력은 필요하지만 그것만으로는 충분하지 않으므로,
공격자가 이미 코드를 실행하고 있어도 피해를 제한하는 구조를 고르라는 것이다.

범위에는 한계가 있다.
프런트엔드와 API가 같은 도메인에 있어 OAuth 없이 쿠키 세션으로 충분한 앱은
OpenID Connect로 로그인만 위임하는 경우를 포함해 범위 밖이다(§1, §7.1).
헤더에는 `BCP: 212`가 적혀 있는데
본문의 참고 문헌은 RFC 8252에 같은 BCP 212를 붙인다.
이 불일치의 이유는 본문에서 확인하지 못했다.

## 위협 모델

RFC는 공격자가 악성 코드를 실행하게 된 뒤
할 수 있는 일을 네 시나리오로 나눈다(§5.1).

1. 1회 토큰 탈취: 저장소에서 토큰을 읽어 공격자 서버로 보낸다.
2. 지속 토큰 탈취: 10초 같은 간격으로 계속 훔쳐 최신 토큰을 항상 가진다.
3. 새 토큰 획득: 숨겨진 iframe에서 조용한 인가 코드 흐름을 새로 돌려 독립된 토큰을 받는다.
4. 요청 대행: 토큰 없이도 사용자 브라우저가 쿠키나 토큰을 붙여 주므로 리소스 서버에 직접 요청한다.

두 번째 시나리오는 흔한 방어를 무력화한다.
짧은 토큰 수명이나 리프레시 토큰 회전(rotation)은
최신 토큰을 늘 훔치는 상대에게 소용이 없다.
공격자는 훔친 뒤 앱의 토큰을 지우거나 사용자가 탭을 닫기를 기다리기만 하면 되고,
앱이 최신 리프레시 토큰을 쓰지 않으니 재사용 탐지도 일어나지 않는다(§5.1.2).

RFC는 세 번째 시나리오를 가장 위험하다고 본다.
공격자가 이미 앱의 출처 안에 있으므로 흐름이 정상 흐름과 구분되지 않고,
토큰을 어디에 어떻게 저장했는지가 무관해진다.
DPoP도 공격자가 자기 키 쌍으로 새 토큰에 DPoP를 설정하면 소용이 없다(§5.1.3).
사용자 동의를 매번 요구하면 막을 수 있지만
부트스트랩과 SSO를 깨뜨려 현실적이지 않다고 한다.

RFC는 네 번째 시나리오를 어떤 애플리케이션 수준 방어로도 막을 수 없다고
인정한다.
HttpOnly 세션 쿠키를 쓰는 서버 렌더링 앱도 마찬가지이고,
DPoP 명세도 이 시나리오를 범위 밖으로 둔다(§5.1.4).

## 구조 고르기

RFC는 세 가지 구조를 보안이 높은 순서대로 제시한다(§6).
다음 표는 RFC의 위협 분석을 이 문서에서
한 표로 다시 정리한 것이다(§6.1.4, §6.2.4, §6.3.4, §7.4.1).

| 구조                       | 1회 탈취         | 지속 탈취        | 새 토큰 획득 | 요청 대행 | RFC의 권고                            |
| -------------------------- | ---------------- | ---------------- | ------------ | --------- | ------------------------------------- |
| BFF                        | 막음             | 막음             | 막음         | 노출      | 업무용, 민감, 개인정보 앱에 강력 권고 |
| 토큰 중개 백엔드           | 액세스 토큰 노출 | 액세스 토큰 노출 | 막음         | 노출      | BFF가 불가능할 때만                   |
| 브라우저 전용 클라이언트   | 노출             | 노출             | 노출         | 노출      | 업무용, 민감, 개인정보 앱에 비권고    |
| Service Worker로 흐름 처리 | 막음             | 막음             | 노출         | 노출      | 비권고                                |

Service Worker가 새 토큰 획득을 막지 못하는 이유는 구체적이다.
악성 코드가 Service Worker를 등록 해제하면
새로 만든 프레임에는 Service Worker가 없으므로
그 프레임에서 새 인가 코드 흐름을 돌릴 수 있다(§7.4.1.1).

그 밖에 지켜야 할 금지 사항이 있다.
브라우저 클라이언트는 인가 코드 그랜트와 PKCE를 써야 하고,
Implicit 그랜트와
Resource Owner Password Credentials 그랜트는 쓰면 안 된다(§7.2, §7.3).
인가 서버는 인가 응답으로 액세스 토큰을 발급하면 안 되고,
SPA에 공유 비밀을 요구해서도 안 된다(§7.2, §6.3.3.1).

## 구현하기

BFF의 핵심 책임은 셋이다(§6.1).
인가 서버에 대해 기밀 클라이언트(confidential client)로 행동하고,
토큰을 쿠키 기반 세션에 묶어 브라우저에 노출하지 않으며,
모든 요청을 리소스 서버로 전달하면서 올바른 액세스 토큰을 붙인다.

다음은 로그인 이후의 BFF 요청 처리만 떼어 낸 최소 구현이다.
인가 코드 교환은 생략하고 세션에 시험용 토큰을 채워 둔다.
RFC의 요구 사항 중 쿠키 속성, CSRF 방어용 사용자 정의 헤더,
허용 목록 기반 전달을 코드로 보여 준다.

```javascript
import http from 'node:http';
import crypto from 'node:crypto';

// 세션 id -> { accessToken }. 실제 BFF는 인가 코드 교환(F) 뒤에 이 값을 채운다.
const sessions = new Map();

// 허용 목록: BFF 경로 -> 고정된 리소스 서버 주소 (§6.1.3.6)
const ROUTES = {
  '/bff/orders': 'http://127.0.0.1:9001/orders',
};
const COOKIE = '__Host-Http-sid';

// 로그인 흉내: 세션을 만들고 쿠키를 내려 준다 (G)
function login(res) {
  const sid = crypto.randomBytes(32).toString('base64url');
  sessions.set(sid, { accessToken: 'demo-access-token' });
  res.setHeader('Set-Cookie',
    `${COOKIE}=${sid}; Path=/; Secure; HttpOnly; SameSite=Strict`);
  res.end('ok');
}

const server = http.createServer(async (req, res) => {
  if (req.url === '/login') return login(res);

  // CSRF: 사용자 정의 헤더가 없으면 거절한다 (§6.1.3.3.2)
  if (req.headers['my-static-header'] !== '1') {
    res.statusCode = 403;
    return res.end('missing custom header');
  }
  const sid = /(?:^|;\s*)__Host-Http-sid=([^;]+)/.exec(req.headers.cookie ?? '')?.[1];
  const session = sessions.get(sid);
  if (!session) {
    res.statusCode = 401;
    return res.end('no session');
  }
  const target = ROUTES[req.url];
  if (!target) {            // 목록에 없는 목적지로는 절대 전달하지 않는다
    res.statusCode = 404;
    return res.end('unknown route');
  }
  // 쿠키는 떼고 액세스 토큰을 붙여 전달한다 (K)
  const upstream = await fetch(target, {
    method: req.method,
    headers: { authorization: `Bearer ${session.accessToken}` },
  });
  res.statusCode = upstream.status;
  res.end(await upstream.text());
});

server.listen(9000, '127.0.0.1');

// 시험용 리소스 서버: 받은 Authorization 헤더를 그대로 돌려준다
http.createServer((req, res) => res.end(`auth=${req.headers.authorization}`))
  .listen(9001, '127.0.0.1');
```

이 코드에는 로그인 이후만 있으므로 그대로 배포할 수 없다.
빠진 부분은 로그인 시작과 인가 코드 수신 엔드포인트,
토큰 교환, 리프레시, 로그아웃이다.
RFC는 이 엔드포인트들이 표준 OAuth 라이브러리에 이미 있다고 설명하므로
직접 구현하기보다 라이브러리를 쓰는 편이 낫다(§6.1.2.1).

## 값 정하기

BFF 쿠키 설정은 RFC가 항목별로 강도를 구분한다(§6.1.3.2).

| 항목                  | 수준       | 목적                                                      |
| --------------------- | ---------- | --------------------------------------------------------- |
| `Secure`              | MUST       | HTTPS에서만 전송한다                                      |
| `HttpOnly`            | MUST       | 자바스크립트가 세션을 읽지 못하게 한다                    |
| `SameSite=Strict`     | SHOULD     | 교차 사이트 요청에 쿠키를 싣지 않는다                     |
| 쿠키 `Path`는 `/`     | SHOULD     | 세션 쿠키를 앱 전체 경로에 적용한다                       |
| `Domain` 속성 없음    | SHOULD NOT | 하위 도메인과 쿠키를 공유하지 않는다                      |
| `__Host-Http-` 접두사 | SHOULD     | HTTP로 설정된 쿠키임을 표시하고 하위 도메인 공유를 막는다 |

SHOULD 항목을 MUST로 정하지 않은 이유는 기존
아키텍처가 규정을 지킬 수 있게 하기 위해서다.
새로 만드는 시스템이라면 전부 지키는 것이 쉽다고 RFC는 적는다.
이 기준에서 벗어나려면 배치 사정에 맞는 근거가 있어야 한다.

리프레시 토큰 수명은 RFC의 예시가 기준이 된다(§6.3.2.3).
액세스 토큰 10분, 리프레시 토큰 8시간으로 발급한 뒤
리프레시로 새 토큰을 받을 때마다 남은 수명이 줄어
처음 인가 시점에서 8시간이 지나면 요청이 실패한다.
회전된 새 리프레시 토큰이 처음 만료 시각을 넘기면 안 된다는 것이 핵심이다.
BFF에서는 쿠키 세션 수명을
리프레시 토큰 최대 수명과 같게 두는 것이 합리적이다(§6.1.2.2).

세션 방식은 두 갈래다.
서버 측 세션은 통제력이 크지만 확장성에 부담이 되어 소규모에만 권한다.
클라이언트 측 세션은 세션 자체의 취소가 어렵지만,
BFF에서는 쿠키가 토큰을 꺼내는 용도일 뿐이라서
액세스 토큰과 리프레시 토큰을 취소하면 접근이 끊긴다(§6.1.2.3).
클라이언트 측 세션에 토큰이 들어 있다면
쿠키 내용은 암호화하는 것이 좋다(§6.1.3.2).

## 트레이드오프

### BFF는 보안을 얻는 대신 서버 운영을 떠안는다

BFF는 OAuth 때문에 공격 표면을 늘리지 않는다.
남는 위험은 브라우저 안의 클라이언트 하이재킹뿐이며
이는 웹 앱 전반의 문제다(§6.1.4.3).
대가는 분명하다.
서버 측 구성 요소를 배치하고 운영해야 하고,
모든 상호작용을 BFF가 프록시하므로 서버 부하가 늘 수 있다.

여기에 어려움이 더 있다.
BFF가 모든 요청과 응답을 볼 수 있으므로
제3자가 호스팅하는 BFF는 프라이버시 영향이 크다(§6.1.3.4).
단일 인스턴스 BFF 뒤의 리소스 서버가 IP로 속도 제한을 걸면
많은 사용자의 요청이 하나의 IP에서 온 것처럼 보여 차단될 수 있다(§6.1.3.5).
BFF의 취약점은 앱 전체에 큰 영향을 주므로
BFF 자체가 핵심 공격 대상이 된다(§6.1.4.1).

### 토큰 중개 백엔드는 가볍지만 액세스 토큰이 노출된다

이 구조는 모든 요청을 프록시하지 않는다.
액세스 토큰만 브라우저에 내려 주고
리프레시 토큰과 클라이언트 자격 증명은 서버에 둔다.
그래서 장기 접근은 막지만 액세스 토큰 탈취와 그것으로
리소스 서버에 직접 접근하는 일은 막지 못한다(§6.2.4.4).

DPoP로 이를 보강하기도 어렵다.
토큰 교환은 백엔드가 하고 토큰 사용은 앱이 하므로
책임이 두 당사자로 나뉘는데, 이는 명세가 정의하지 않은 상황이다(§6.2.4.3.2).
캐시한 액세스 토큰의 범위가 요청 범위보다 넓으면 그대로 돌려주지 말고
리프레시 토큰으로 더 좁은 범위의 토큰을
새로 받아야 범위 상승 위험을 피한다(§6.2.2.3).

### 브라우저 전용 클라이언트는 방어를 겹쳐도 새 토큰 획득을 못 막는다

저장소를 Web Worker로 격리해 리프레시 토큰을 숨기는 방법이 있다.
이렇게 하면 앱의 리프레시 토큰은 유출되지 않지만
액세스 토큰은 여전히 노출된다(§8.3).
DPoP로 토큰을 브라우저의 추출 불가능한 키에
묶으면 탈취한 토큰을 바로 쓰지 못한다(§6.3.4.2.2).
그러나 격리 저장소를 쓰든 DPoP를 쓰든 공격자가 새
흐름을 돌려 자기 키로 새 토큰을 받는 것은 막지 못한다.

인가 서버 쪽에서 막는 방법도 RFC가 검토하고
모두 비권고로 정리한다(§6.3.4.2.3). iframe 안의 인가 요청을 막으면
공격자는 팝업이나 팝언더로 우회하고,
브라우저 전용 클라이언트의 부트스트랩도 깨진다.
매번 동의를 요구하면 사용자가 무심코 승인하는 동의 피로가 생겨
공격자가 시작한 흐름도 그대로 승인하게 된다.
결국 방어를 쌓아서는 이 시나리오를 해결할 수 없고 BFF처럼 구조를 바꿔야 한다.

### 같은 도메인이면 OAuth를 쓰지 않는 선택도 있다

RFC는 단순한 앱이 OAuth를 세션 관리 대용으로
쓰다가 복잡해지는 경우가 흔하다고 본다(§7.1).
같은 도메인의 프런트엔드와 API는 서버 측 쿠키 세션으로 충분할 수 있고,
OpenID Connect로 로그인만 위임하면 구조가 크게 단순해진다.
그래도 OAuth를 쓰면 얻는 이점이 있다고 RFC가 직접 든다.
나중에 도메인을 추가할 때 구조를 바꾸지 않아도 되고,
기존 라이브러리를 쓸 수 있으며, 로그인과 MFA,
계정 관리와 복구를 인가 서버에 모을 수 있고,
인증과 자원 제공의 책임을 나눌 수 있다.
이 경우에도 위의 세 패턴 중 하나로 구현하면 된다.

## 함정

- CORS만으로 CSRF를 막는다고 생각하면 안 된다.
  본문 없는 `POST`처럼 사전 요청(preflight)이 없는 요청은 CORS를 통과한다.
  BFF는 정적 사용자 정의 헤더를 요구하고 모든 요청에서 이를 검사해야 한다(§6.1.3.3.2).
- `SameSite=Strict`로는 부족한 경우가 있다.
  `a.example.com`과 `b.example.com`은 같은 사이트이므로
  하위 도메인 탈취로 BFF에 CSRF를 할 수 있다(§6.1.3.3.1).
- 자바스크립트 쿠키 API로 토큰을 저장하면 안 된다.
  쿠키가 앱 로드 같은 서버 요청에 함께 전송되는 부작용이 있어 비권고다(§8.1).
- 클로저에 토큰을 숨겨도 프로토타입 오염으로 클로저가 쓰는 함수를 바꿔치기하면
  인자를 통해 토큰이 노출될 수 있다(§8.4).
- Service Worker가 토큰을 영속 저장하려고 IndexedDB를 쓰면 메인 창과 공유되므로 격리가 깨진다(§8.2).
- BFF를 설정 가능한 프록시로 열어 두면 공격자가 임의 서버로 요청을 돌려 토큰을 빼낼 수 있다.
  목적지 호스트와 경로, 메서드를 허용 목록으로 제한해야 한다(§6.1.3.6).
- SPA 번들에 넣은 공유 비밀은 비밀이 아니다.
  인가 서버는 그것으로 클라이언트를 인증하면 안 되고 공개 클라이언트로 취급해야 한다(§6.3.3.1).
- 인가 서버의 토큰 엔드포인트뿐 아니라 디스커버리, JWKS, 취소, 인트로스펙션 같은
  엔드포인트도 앱이 부르면 CORS를 지원해야 한다(§6.3.3.4).
- 추출 불가능 키가 TPM이나 디스크 암호화로 보호된다는 보장은 Web Crypto API 명세에 없다.
  악성코드가 파일 시스템을 읽으면 세션 하이재킹과 같은 위험이 남는다(§9.2).

## 확인하기

위 예제 코드를 `bff.mjs`로 저장하고 `node bff.mjs`를 실행한 뒤
다른 터미널에서 다음을 순서대로 실행하면 BFF의 거절 규칙을 확인할 수 있다.
작성 시점에 직접 실행해 아래 결과를 확인했다.

```bash
# 1. 로그인: Set-Cookie에 Secure, HttpOnly, SameSite=Strict가 붙는지 본다
curl -si http://127.0.0.1:9000/login | sed -n 1,3p
SID=$(curl -si http://127.0.0.1:9000/login | grep -i set-cookie \
  | sed 's/.*sid=\([^;]*\);.*/\1/')

# 2. 사용자 정의 헤더가 없으면 403
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Cookie: __Host-Http-sid=$SID" http://127.0.0.1:9000/bff/orders

# 3. 세션 쿠키가 없으면 401
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "My-Static-Header: 1" http://127.0.0.1:9000/bff/orders

# 4. 정상 요청은 리소스 서버가 받은 Authorization 헤더를 돌려준다
curl -s -H "My-Static-Header: 1" -H "Cookie: __Host-Http-sid=$SID" \
  http://127.0.0.1:9000/bff/orders

# 5. 허용 목록에 없는 경로는 404
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "My-Static-Header: 1" -H "Cookie: __Host-Http-sid=$SID" \
  http://127.0.0.1:9000/bff/evil
```

기대 결과는 순서대로 상태 줄과 `Set-Cookie`와 `Date` 세 줄,
`403`, `401`, `auth=Bearer demo-access-token`, `404`다.
브라우저에서 확인하려면 개발자 도구의 Application 탭에서
세션 쿠키가 `HttpOnly`로 표시되는지,
콘솔에서 `document.cookie`에 보이지 않는지 본다.

## 체크리스트

- 같은 도메인에서 쿠키 세션으로 충분한데 OAuth를 쓰고 있지는 않은가.
- 업무용이나 개인정보를 다루는 앱이라면 BFF를 선택했는가.
- 토큰 중개 백엔드를 택했다면 BFF를 쓸 수 없는 이유를 설명할 수 있는가.
- BFF는 인가 서버에 기밀 클라이언트로 자격 증명을 등록했는가.
- 세션 쿠키에 `Secure`와 `HttpOnly`를 켰는가.
- 요청마다 정적 사용자 정의 헤더를 검사하는 CSRF 방어가 있는가.
- BFF가 전달할 수 있는 목적지, 경로, 메서드가 허용 목록으로 고정되어 있는가.
- 브라우저 전용 클라이언트라면 PKCE를 쓰고 정확히 일치하는 리디렉션 URI만 등록했는가.
- Implicit 그랜트와 비밀번호 그랜트를 모두 끄고 인가 응답으로 액세스 토큰을 발급하지 않는가.
- 리프레시 토큰은 회전하거나 발신자 제한이 걸려 있고 최대 수명이 있는가.
- 하나의 출처에 하나의 앱만 배치했는가.

## 기억할 원칙

### 방어는 새 토큰 획득 시나리오로 시험한다

악성 코드가 앱과 같은 권한을 가진다는 전제에서는
저장소를 어떻게 숨기든 공격자가 새 흐름을 돌려 토큰을 받는 것을 막지 못한다.
토큰 저장 방식, 짧은 수명, 회전, DPoP는 모두 이 시나리오 앞에서 한계가 있다.
그래서 브라우저 보안 설계를 평가할 때는
공격자가 숨겨진 iframe에서 새 인가 흐름을 돌렸을 때 무엇이 남는지를 먼저 묻는다.

### 막을 수 없는 것을 알고 있어야 한다

BFF를 쓰더라도 사용자 브라우저를 통한 요청 대행은 막을 수 없다고 RFC는 인정한다.
이 구조는 토큰이 새지 않고 공격자가 장기 접근을 얻지 못하게 보장할 뿐,
공격자가 앱 안에서 할 수 있는 일을 없애 주지는 않는다.
남는 위험은 XSS 예방과 CSP 같은 심층 방어,
그리고 BFF 쪽 이상 징후 탐지와 속도 제한으로 줄인다.
