# Lovable 앱에서 노출된 개인 데이터

원문: [Lovable: Many Apps Built on the Platform Expose Sensitive Data](https://www.crissyfield.de/research/lovable-en/)

HN 토론: <https://news.ycombinator.com/item?id=50499017> (765점, 303개 댓글)

## 요약

독일 보안 회사 Crissy Field GmbH가 Handelsblatt와 협력해 낸 연구 보고서이다.
2026년 11월 2일 Handelsblatt의 Lina Knees가 독일어로 조사 결과를 보도했고, 이 보고서는 그보다 최근 분석과 갱신된 수치를 담는다고 밝힌다.
이 문서는 보고서 전문을 읽었다.
Handelsblatt 기사와 보고서가 쓴 데이터셋은 읽지 못했다.

보고서의 배경은 이렇다.
Lovable은 스톡홀름에서 2023년 Anton Osika와 Fabian Hedin이 세운 스웨덴 AI 스타트업으로, 평문 설명을 웹 애플리케이션으로 바꿔 주고 프로그래밍 경험이 적은 사람도 쓰도록 설계되었다고 소개된다.
보고서는 Lovable의 마케팅이 기술 지식이 필요 없다고 반복해 말해 보안까지 맡아 준다는 인상을 줄 수 있지만, 이용 약관은 애플리케이션과 데이터 처리의 책임을 고객에게 둔다고 지적한다.

조사 방법과 결과는 이렇다.
연구진은 Supabase 데이터베이스 서비스에 집중했다. 연동 분석이 상대적으로 쉽고 Lovable 프로젝트 가운데 가장 널리 쓰인다고 믿기 때문이며, 2025년 말 도입된 Lovable 자체 데이터베이스 기능은 분석하지 않았다.
오픈 웹 보관소 Common Crawl 데이터로 2025년 12월부터 2026년 9월까지의 Lovable 프로젝트 159,041개를 찾아 분석했고, 그중 34,545개가 Supabase를 썼다.
24,664개 사이트는 로딩 즉시 로그인이나 다른 상호작용 없이 Supabase의 데이터베이스 레코드를 보냈다. 이것만으로는 보안 문제가 아니고 공개용 데이터일 수 있다.
그러나 추가 읽기 전용 요청으로 더 많은 내용을 가져올 수 있었고, 24,664개 사이트 중 7,403개(30%)의 표 10,560개에서 이메일 주소가 든 레코드를 찾았다.

보고서는 한계를 직접 적는다.
이메일 주소는 개인 정보 레코드를 가려내는 단서이지만 공개 연락처나 시험 데이터일 수도 있고, 이메일이 없는 개인 레코드는 놓친다. 두 효과가 어느 정도 상쇄하지만 정도는 확정하지 못했다.
그래서 30%는 확인된 유출률로 읽으면 안 되고, 더 자세히 본 24,664개 사이트에만 해당하며, Common Crawl 표본은 Lovable 전체를 대표하지 않는다고 한다.
데이터셋은 전체가 아니라 일부만 가져왔고, 접근 방법의 세부는 추가 접근을 쉽게 할 수 있어 공개하지 않는다고 밝힌다.

심각한 사례로 다음을 든다.
독일의 한 라이프스타일 포럼이 이름, 이메일, 생년월일, 성별이 든 프로필 8만 개 이상과 채팅 메시지 20만 건 이상을 노출했다.
여러 행사 주최자와 식당이 티켓과 음식 판매 관련 레코드 수만 건을 로그인 없이 노출했고, 이메일과 전화번호와 주소와 결제 정보와 티켓 코드가 있었다.
한 부동산 관리 회사는 세입자와 집주인과 거래 상대에 관한 민감한 내부 메일의 AI 요약을 노출했다.
한 서비스 제공자는 여권 번호와 만료일과 국적을 포함한 신분증 정보 레코드 1,000개 이상을 노출했다.
그 밖에 수만 건의 계약서와 청구서, 개인 사진 앨범, 내부 WhatsApp 대화, 고객에게 보낸 이메일 28만 통이 읽힐 수 있었다고 한다.
보고서는 이 정보가 악용되었는지는 확인하지 못했다고 쓰고, Handelsblatt가 조사 결과를 들고 Lovable에 연락했다고 한다.

## 분석

### 중심 주장은 쉬운 개발 도구가 접근 권한 검토의 필요를 없애지 않는다는 것이다

보고서는 접근 제어 실수가 사람이 쓴 앱에도 있지만, Lovable에서는 데이터베이스 연동이 반복되는 패턴을 따르므로 공격자가 많은 앱에서 비슷한 설정 오류를 찾기 쉽다고 본다.
또 비전문가는 이런 결함을 알아채고 막기가 더 어렵다고 한다.
권고는 실제 고객이나 사업 데이터를 다루기 전에 접근 권한, 인터페이스, 사용자 계정 간 분리를 점검하고 큰 변경마다 반복하라는 것이다.
자동 점검은 전문가 평가를 대신하지 못한다고 쓴다.

### 문제의 위치를 놓고 의견이 갈린다

보고서의 대상은 Lovable 앱이지만, HN에서는 책임이 Supabase에 있느냐는 질문이 나왔다.
한 댓글은 Supabase의 기본 설정이 오래전부터 문제였다고 짚으며 GitHub 토론을 가리켰고, 10월 30일에 고쳐졌다고 하지만 기존 프로젝트에는 예전 기본값이 그대로라는 보고가 돈다고 전했다.[^solar_fields]
다른 댓글은 놀랐다고 했다. 클라이언트 생성에 필요한 키가 기본적으로 데이터베이스 접근까지 준다는 것이다.[^yard2010]
다른 댓글은 문제의 위치가 Lovable의 구조인지 Supabase 연동인지 묻고, 후자라면 Supabase를 기본으로 쓰는 여러 AI 도구와 오픈 소스 프로젝트도 조사해야 한다고 했다.[^karakoram]
이 문서는 Supabase 쪽 주장을 확인하지 못했다.

## 비평

### Lovable의 반응과 반론

Lovable의 보안 책임자라고 밝힌 사용자는 스레드에서 원인이 행 수준 보안(Row-Level Security)의 부족이었고, 자사의 자동 점검이 바로 이것을 잡도록 만들어졌다고 했다.
모든 앱을 게시 전에 자동 점검하고 더 깊은 정적 분석을 무료로 제공하며, 발견 사항이 나오면 사용자가 “Fix”를 눌러 해결을 돕고, 자동 수정을 켜거나 심각한 발견이 있으면 게시를 막을 수 있다고 한다.[^igorandri]
이에 한 답글은 영향받은 사람이 발견 사항을 처리하지 않은 최종 이용자라는 반응을 인용하며, 사이트 운영자 7,500곳이 처리하지 않았다면 구조적 실패이니 더 책임을 지고, 사용자 데이터가 새는 것을 아는 앱의 게시를 막으라고 했다.[^varenc]
다른 답글은 유출된 데이터가 어디로 갔는지 목록을 만들었는지, 사본을 받은 모든 당사자가 파기했다고 확인했는지를 물었다.[^jacquesm]
또 다른 답글은 이용자가 덜 기술적이라면 보안을 해치는 선택을 허용하는 것이 무책임하고, 취약점이 있으면 고치거나 앱을 내리는 두 가지 선택만 주어야 한다고 했다.[^shepherdjerred]
이 문서는 Lovable의 점검 기능이 이번 앱들에 실제로 어떻게 작동했는지 확인하지 못했다.

### 이것이 유출(breach)인지에 대한 정의 논쟁

한 댓글은 보고서가 읽기 전용 키로 공개된 데이터를 읽은 것이라면, 공개한 것이 유출이고 읽은 것은 유출이 아니라고 물었다.[^nospi]
답글은 URL의 식별자를 바꾸는 것만으로 무단 접근 혐의를 받은 사례가 있고, 기술적으로 접근 가능하다는 것이 누구나 접근하도록 의도되었다는 뜻은 아니라고 했다.[^ahtihn]
다른 답글은 정확한 용어가 “의도하지 않은 공개(inadvertent disclosure)”라며 NIST 용어집을 가리켰다.[^jacquesm2]
다른 댓글은 기술적으로 맞더라도 민감 정보를 새게 만들 수 있는 도구의 민주화에는 더 강한 안전장치가 필요하다고 했다.[^hmokiguess]
연구자는 이 사안을 데이터 보호 변호사의 도움을 받아 분석했고, 데이터셋을 Lovable에 공유해 고객에게 연락하게 했으며 당국에는 신고하지 않았다고 답했다.[^neathack2]

### 수치의 해석에는 주의가 필요하다

보고서의 30%는 이메일 레코드를 가진 사이트의 비율이고 유출률이 아니라고 보고서가 직접 적는다.
HN의 한 댓글은 전체 분석 사이트 중 얼마가 개인 정보를 유출했느냐고 물었고, 저자가 스레드에서 2.5%라고 답했다고 전했다.[^lysace]
이 문서는 저자의 해당 답글과 2.5%의 산정 방식을 확인하지 못했고, 보고서 본문에는 이 수치가 없다.
그래서 이 문서는 30%와 2.5%를 서로 다른 정의의 수치로 보고 어느 쪽도 유출률로 쓰지 않는다.

### 책임을 보는 틀이 다르다

한 댓글은 AI를 탓하지만 인증 없이 저장된 민감 데이터는 새로운 0-day가 아니었고 해결책은 강한 법적 책임이라고 했다.[^hn_throwaway_99]
저자는 AI가 문제의 핵심이 아닐 수 있고, 문제는 “누구나 기술 지식 없이 만들 수 있다”고 반복하면서 약관에서 책임을 떠넘기는 마케팅이라고 답했다.[^neathack]
다른 답글은 EU 시민이 소송할 수 있고 GDPR에 따라 유출 당사자가 조치할 의무가 있으며 벌금이 매출에 비례할 수 있다고 설명했다.[^berkes]
한 댓글은 인증과 인가를 구분했다. 이 사례는 자체 인증 코드가 아니라 인가 실수나 인가 부재이고, 인가는 어떤 식으로든 직접 써야 한다는 것이다.[^fabian2k]

## 인사이트

### 기본값이 안전하지 않은 도구는 사용자에게 책임을 이전한다

보고서와 스레드를 합치면 구조가 보인다.
플랫폼은 접근 제어가 없는 기본 구성을 만들 수 있고, 점검 도구를 따로 제공하며, 약관에서 책임을 고객에게 둔다.
비전문가 고객은 점검 결과의 의미를 모를 수 있다.
한 댓글은 플랫폼이 기본 거부 데이터베이스와 최소 권한 API와 자동 인증 시험을 기본으로 갖춰 안전하지 않은 배포를 어렵게 해야 한다고 했다.[^liquid_thyme]
다른 댓글은 사후 점검을 만든 사람이 할 것이라는 가정이 이런 사고를 일상으로 만든다고 했다.[^trestacos]
이 문서는 이 구조 해석을 두 댓글의 방향과 맞춘 것이고, 실제 기본값은 확인하지 못했다.

### 앱을 만드는 쪽의 점검 순서

보고서의 권고를 점검 순서로 줄이면 이렇다.
실제 데이터를 받기 전에 비로그인 상태에서 어떤 표가 읽히는지 확인하고,
사용자 계정 간 데이터 분리를 시험하며,
큰 변경 뒤 이를 되풀이하고,
전문 지식이 없으면 검토를 맡기는 것이다.
이 문서는 접근 방법의 구체적 절차를 쓰지 않는다. 보고서도 같은 이유로 세부를 공개하지 않았다.

### 확인할 관찰

이 사안의 결론을 가를 관찰은 세 가지이다.
영향받은 사이트가 수정되었는지와 Lovable이 기본 설정이나 게시 차단 정책을 바꾸는지,
Supabase의 기본값 변경이 기존 프로젝트에도 적용되는지,
유럽 데이터 보호 당국이 이 사안을 조사하는지이다.
셋 모두 이 문서가 확인하지 못했다.
