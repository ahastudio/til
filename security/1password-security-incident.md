# 1Password 백엔드 보안 사고

트윗: [We’re sharing an update about a recent security incident involving some of 1Password’s backend systems.](https://twitter.com/1password/status/2125642686443258030)

HN 토론: <https://news.ycombinator.com/item?id=50644817> (1404점, 593개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/aulbi2/update_on_security_incident_involving> (39점, 3개 댓글)

GN 토론: <https://news.hada.io/topic?id=37847>

## 요약

1Password 공식 계정이 2026년 11월 26일 2시 28분에 올린 트윗이다.
읽은 시점의 조회수는 220만이었다.
1Password의 백엔드 시스템 일부와 관련된 최근 보안 사고에 관한 소식이다.

트윗의 요지는 다섯 가지다.

- 고객 볼트 내용(비밀, 비밀번호, 그 밖의 볼트 항목)과 이를 보호하는 키는 접근도 침해도 없었다고 확인했다.
- 공격자가 일부 백엔드 시스템에 접근해 일부 고객의 이름과 이메일 주소를 가져갔다.
- 서비스는 정상 운영 중이고 고객이 할 조치는 없으며 피싱을 경계하라고 한다.
- 독립 보안 전문가를 투입해 봉쇄와 복구 노력을 검증하게 했다.
- 볼트의 비밀은 사용자만 가진 키로 암호화되어 1Password도 접근할 수 없다.

트윗은 자세한 내용을 블로그 글로 안내한다.

블로그 글은 2026년 11월 25일자이고 트윗보다 훨씬 자세하다.[^blog]
글에 따르면 1Password는 11월 19일에 직원의 회사 GitHub 계정이 침해된
징후를 조사하기 시작했다.[^blog]
공격자는 그 계정으로 소스 코드에 접근하고 백엔드 서비스에 악성 코드를
올렸으며, 그 코드가 고객의 관리용 데이터를 내려받았다고 한다.[^blog]

| 구분             | 블로그 글이 밝힌 내용                                                     |
| ---------------- | ------------------------------------------------------------------------- |
| 영향받은 정보    | 이름과 이메일, 계정·사용자 식별자, 계정 생성과 마지막 로그인 시각         |
| 영향받은 정보    | 공개 키, SRP(Secure Remote Password) 매개변수                             |
| 영향받은 정보    | 초대, 프로비저닝, 계정 복구 이메일 링크에 든 토큰                         |
| 영향받은 정보    | 내부 구조와 관련된 비밀이 아닌 메타데이터                                 |
| 영향받지 않은 것 | 볼트와 항목, 볼트 보호 키, 계정 비밀번호와 Secret Key, 복구 키, 앱과 확장 |
| 함께 일어난 일   | 비공개 저장소의 소스 코드 복사, CI/CD 시스템 접근                         |

글이 꼽은 대응은 다음과 같다.[^blog]
침해된 GitHub 계정을 비활성화하고 탈취된 토큰을 폐기했다.
노출 가능성이 있던 내부 자격 증명을 모두 교체했다.
초대와 복구 이메일의 코드를 숫자 6자리에서 영숫자 10자로 늘렸다.
내부 GitHub, CI/CD, 엔드포인트 통제를 강화했다.
노출된 프로비저닝 토큰으로 계정을 탈취한 내부 증거는 확인하지 못했다고 한다.
영향받은 서비스는 깨끗한 버전으로 복원했다.

## 분석

### 침입 경로는 개발자 계정에서 시작했다

트윗은 백엔드 시스템이라고만 쓰지만 블로그 글은 경로를 더 구체적으로 적는다.
직원의 GitHub 계정이 열리고, 소스 코드에 접근하고,
백엔드 서비스에 악성 코드가 올라가고, 그 코드가 데이터를 내려받는 순서다.[^blog]
글에 적힌 대응도 GitHub 계정 비활성화, 토큰 폐기, CI/CD 통제 강화에 모여 있다.[^blog]
이 사고에서 방어선이 무너진 곳은 암호화가 아니라 개발 도구의 계정이었다는
뜻이다.
고객 데이터를 지키는 설계와 회사 내부 도구를 지키는 보안은
서로 다른 층이다.

### 볼트와 계정 정보를 다르게 다루는 설계

트윗은 볼트 보호를 앞세우고 이름과 이메일을 뒤에 둔다.
이 순서는 제품의 zero-knowledge 설계와 맞는다.
볼트 내용은 사용자만 가진 키로 암호화되므로 서버가 침해되어도
꺼낼 수 없다는 것이 1Password의 설명이다.
이 구조는 [1Password의 Zero-Knowledge 아키텍처](1password-zero-knowledge-architecture.md)에
정리되어 있다.
반면 이름, 이메일, 식별자, 로그인 시각 같은 계정 정보는 서버가 평문으로
다루는 정보이므로 서버 침해가 곧 노출이 된다.
설계가 지키는 범위와 지키지 않는 범위가 이번 사고의 영향 목록에 그대로 나타난다.

### 초대·복구 토큰과 코드 길이 변경

가장 기술적인 대목은 이메일 링크의 토큰이다.
글에 따르면 토큰은 초대나 복구를 끝내는 데 쓰이지만,
SSO 로그인이나 사용자의 등록 이메일로 간 6자리 숫자 코드와 함께일 때만 동작하고
토큰만으로는 계정에 접근할 수 없다.[^blog]
공격자가 토큰을 가졌다면 남는 방어는 6자리 코드다.
숫자 6자리는 조합이 100만 가지이므로, 1Password는 코드를 영숫자 10자로 늘려
무차별 대입을 사실상 불가능하게 했다고 설명한다.[^blog]
글이 문자 집합을 밝히지 않아 정확한 조합 수는 알 수 없다.
숫자만이어도 10의 10제곱으로 1만 배, 소문자와 숫자라면 36의 10제곱이다.
이는 이 문서의 계산이다.
이 변경은 토큰이 노출된 것을 전제한 방어라는 점이 중요하다.

### 트윗과 블로그의 역할 분담

트윗은 안심 메시지와 링크를 담은 입구이고, 상세 목록은 블로그에 있다.
220만 조회의 짧은 글에는 이름과 이메일만 적혀 있지만
블로그에는 토큰, 식별자, 소스 코드, CI/CD 접근이 있다.
이 차이는 은폐라기보다 매체의 성격이다.
다만 트윗만 읽은 사람은 사고의 폭을 좁게 이해할 수 있다.

## 비평

### 규모를 말하는 수치가 없다

트윗은 일부 고객과 제한된 정보라고 쓰고,
블로그는 일부 사용자의 계정 기록이라고 쓴다.[^blog]
영향받은 계정 수, 전체 고객 가운데 비율, 토큰 상태에 있던 사용자 수는
둘 다 적지 않았다.
프로비저닝이나 복구 단계에 있던 소수 사용자에게는 개별 통지가 갔다고 하지만
소수가 몇 명인지는 알 수 없다.[^blog]
내 계정이 포함되었는지 판단할 근거가 공지에 없다.
HN의 brandon272는 일부라는 표현이 0.01%인지 75%인지 알려 주지 않는다고
지적했고,[^brandon272]
고객에게 중요한 것은 비율보다 내가 그 일부에 들었는지라는 답이 달렸다.

### 조치가 필요 없다는 말과 대응 목록의 간격

트윗은 고객이 할 조치가 없다고 쓴다.
블로그도 계정에서 바꿀 것은 없다고 하면서 피싱을 경계하라고 권한다.[^blog]
그런데 회사는 같은 글에서 초대와 복구 코드의 길이를 늘리는 방어를 새로 넣었다.
고객이 할 일이 없다는 말은 고객 계정 설정 기준에서는 맞을 수 있다.
다만 이름과 이메일이 함께 유출되었으므로 피싱의 정확도는 높아질 수 있다.
고객 쪽 위험이 피싱이라면 그에 맞춘 구체적 안내가 글에 더 있어야 한다.
HN의 qixxiq는 1Password 도메인이 아닌 곳에서 자기 정보가 일부 들어간
정교한 피싱 메일을 받았다고 썼다.[^qixxiq]
이 메일이 이번 유출 데이터에서 나왔는지는 확인된 바 없고 작성자의 추정이다.
같은 스레드에서 몇 달 전부터 비슷한 메일을 받았다는 답도 있어서
유출과의 연관은 단정할 수 없다.

### 계정 탈취가 없었다는 확인의 근거

글은 노출된 프로비저닝 토큰으로 계정이 탈취된 내부 증거를 확인하지 못했다고
쓴다.[^blog]
이는 내부 로그에서 증거가 없었다는 뜻이며, 없었음의 증명은 아니다.
독립 전문가를 투입했다는 설명은 있지만 그 검증의 결과나 범위는 공개되지 않았다.
회사가 글을 갱신하겠다고 밝혔으므로 이후 보고를 기다려야 한다.[^blog]

### 시간선과 침입 원인이 비어 있다

글에는 조사 시작일(11월 19일)과 게시일(11월 25일)만 있다.
공격자가 언제 처음 접근했는지, 얼마 동안 머물렀는지,
직원 GitHub 계정이 어떻게 열렸는지는 적혀 있지 않다.
악성 코드가 백엔드에 올라간 기간도 알 수 없다.
원인이 없으면 같은 경로가 막혔는지 외부에서 판단하기 어렵다.

### 악성 코드가 배포된 통제가 설명되지 않았다

블로그 글은 계정이 침해되어 악성 코드가 백엔드에 올라갔다고만 쓰고,
어떤 배포 통제가 있었고 왜 막지 못했는지는 쓰지 않는다.
HN의 ctidd는 main 브랜치로의 직접 푸시를 막지 않았는지, 보호 규칙이 없었는지
우회되었는지가 대응 목록에 없다고 지적했다.[^ctidd]
답글들은 개인 액세스 토큰이 쓰였는지, 계정이 어떻게 열렸는지 같은 가능성을
나열했지만 모두 추정이다.
공지에 이 설명이 없어서 독자는 같은 경로가 막혔는지 판단할 수 없다.

### 볼트가 안전한 이유의 두 설명

HN의 xucheng는 볼트가 안전한 이유가 공격자가 암호화된 볼트 데이터를 얻지
못해서인지, 얻었어도 종단간 암호화 때문에 읽을 수 없어서인지
공지에서는 분명하지 않다고 물었다.[^xucheng]
두 경우는 결과가 같아도 같은 상황이 아니고,
암호화된 데이터가 새어 나갔다면 피싱으로 비밀번호와 Secret Key를 얻는 길이
열릴 수 있다는 것이 질문의 요지다.[^xucheng]
공지는 볼트 내용에 접근한 적이 없다고 쓰지만,
이 구분을 직접 짚은 문장이 없다는 지적은 공지의 빈틈을 정확히 가리킨다.

### 설계상 안전하다는 말의 신뢰

Lobste.rs의 altano는 LastPass도 설계상 볼트 내용이 안전하다고 하다가 크게
뚫렸다고 상기시키며 확신이 크지 않다고 썼다.[^altano]
1Password의 사례와 LastPass의 사례는 침해 경로가 다르므로 같은 결론을 낼 수는
없다.
다만 설계가 약속하는 범위를 독자가 외부에서 검증하기 어렵다는 점은 같다.

### 소스 코드 복사의 파급

글은 소스 코드가 고객 데이터가 아니며 사용자 비밀을 담고 있지 않다고 쓴다.[^blog]
이 말은 데이터 측면에서는 이해할 수 있다.
그러나 소스 코드가 공격자에게 넘어가면 이후 취약점을 찾기 쉬워진다는 점은
글에서 다루지 않는다.
앱과 브라우저 확장이 영향받지 않았다는 서술이 있지만,
그 확인 방법은 적혀 있지 않다.

## 인사이트

### 암호화 설계는 범위를 정해 준다

이번 사고는 zero-knowledge 설계가 약속하는 것과 약속하지 않는 것을
구분해서 보여 준다.
볼트 내용은 서버에서 복호화할 수 없어 보호되지만
계정 정보와 토큰은 서버가 아는 정보라서 노출되었다.
서비스를 고를 때 서버가 모르는 것과 서버가 아는 것의 목록을 따로 보는 습관이
도움이 된다.
SRP 같은 인증 프로토콜의 성격은
[1Password/srp 패키지 문서](1password-srp-go-package.md)에 있다.

### 개발자 계정과 CI/CD가 공급망이다

고객이 쓰는 제품이 안전해도 그것을 만드는 계정이 열리면 백엔드가 바뀐다.
직원의 GitHub 계정에서 악성 코드가 백엔드로 갔다는 경로는
자기 조직의 개발 도구에도 같은 질문을 던진다.
토큰 수명, 개인 계정 강제 인증, CI/CD 비밀의 범위가 그 점검 항목이다.
비슷한 형식의 사고 공지는 [Northflank 침해](northflank-breach.md)와
[Trigger.dev 보안 사고](trigger-dev-security-incident.md) 문서에도 있다.

### 서버가 모르는 키만으로는 배포 경로가 해결되지 않는다

HN의 anotherhue는 키를 저장하지 않는다는 점이 안전의 근거가 되는지 물었다.
GitHub 계정이 열릴 수 있다면 비밀을 외부로 보내는 나쁜 릴리스가 나갈 수도 있고,
사용자는 한 번의 암호화가 아니라 수천 번의 릴리스에서 안전한 소프트웨어가
계속 배달되기를 믿는 것이라는 주장이다.[^anotherhue]
이 주장은 이번 사고에서 앱 변조가 확인되었다는 뜻이 아니다.
블로그 글은 앱과 확장이 영향받지 않았다고 쓴다.
다만 암호화 설계가 지키는 범위의 바깥에 배포 신뢰가 있다는 점은 짚어 둘 만하다.
Lobste.rs의 smoores도 앱 배포 체계가 CI/CD 접근만으로 악성 앱 번들을 올릴 수 없게
되어 있는지 알고 싶다고 썼다.[^smoores]
그런 일이 생기면 볼트 내용에 닿을 수 있어 매우 나쁘다는 것이다.[^smoores]
공지는 이 부분에 답하지 않는다.

### 변경의 출처를 사람이 승인하는 방식

HN의 tptacek는 SaaS 기업에서 직원 노트북이 뚫려 GitHub에 코드를 올리고
그 코드가 배포되는 것이 가장 중요한 공격 경로라고 썼다.[^tptacek]
그는 PR이 쏟아지는 속도에서는 모든 줄을 사람이 읽기 어렵다고 보고,
현실적으로 확인할 것은 변경의 출처, 곧 사람 개발자의 서명 같은 것이라고 했다.
다만 공격 기간에는 공격자가 이메일도 갖고 있어서 어려운 문제라고 덧붙였다.[^tptacek]
simonw가 계정이 이미 뚫린 뒤의 방어를 묻자 보호 브랜치, 별도 승인자,
정적 자격 증명 배제를 권하는 답이 달렸다.[^simonw][^madeofpalk]
관련해서 줄 단위 리뷰가 현실적인지에 대한 논쟁은
[Diff를 읽지 않는 PR 머지 사례](../code-review/pr-without-reading-diff.md)와도 이어진다.

### 사고 공지는 목록과 요약을 따로 읽는다

요약 트윗은 가장 좋은 소식을 앞에 두고, 본 글은 영향받은 항목을 줄줄이 적는다.
공지를 읽을 때 요약의 어조와 본문의 목록을 대조하면
빠진 정보와 강조의 차이가 보인다.
이 사고에서는 토큰과 식별자가 요약에는 없고 본문에만 있었다.

### 확인할 것

블로그 글의 갱신 내용, 곧 영향받은 계정 수, 최초 접근 시점,
직원 계정이 열린 경로, 독립 전문가의 검증 결과를 확인해야 한다.
1Password가 보낸 개별 통지의 대상 기준도 확인이 필요하다.
이 문서는 블로그 글을 읽은 11월 26일 기준으로 쓴 것이다.
