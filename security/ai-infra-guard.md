# AI-Infra-Guard: AI 인프라, 에이전트, 스킬, 모델 API를 한 곳에서 점검하는 레드팀 플랫폼

<https://tencent.github.io/AI-Infra-Guard/>

<https://github.com/Tencent/AI-Infra-Guard>

GN 토론: <https://news.hada.io/topic?id=34645>

## 소개

A.I.G(AI-Infra-Guard)는 Tencent Zhuque Lab이 만든 오픈소스 AI 레드팀 플랫폼이다.
저장소 설명은 Agent Scan, Skills Scan, MCP Scan, AI Infra Scan, LLM
탈옥(jailbreak) 평가로 AI 생태계를 지키는 풀스택 플랫폼이라고 적는다.
README의 표현으로는 AI 보안 위험을 스스로 점검하는 가장 포괄적이고 지능적이며
쓰기 쉬운 해법을 목표로 한다.
라이선스는 Apache-2.0이고 주 언어는 Python이다.
GitHub API로 확인한 시점의 별은 6,666개,
포크는 626개이며 2024년 12월 25일에 만들어져 최신 푸시는 2026년 10월 1일이다.
README의 최근 소식에 따르면 가장 최근 릴리스는 2026년 9월 17일의 v4.6.2다.

운영 주체는 Tencent 보안 플랫폼 부서 소속의 Zhuque Lab이다.
README는 이 팀이 NVIDIA, Google, Microsoft 같은 업체와 OpenClaw, Linux,
Hugging Face 같은 오픈소스 커뮤니티의 고위험 취약점 수정을 도왔다고 적고,
Black Hat, DEF CON, ICLR, CVPR, NeurIPS, ACL에서 연구를 발표했다고 소개한다.
이 내용은 모두 README의 자기 소개이며 이 글에서 별도로 확인하지 않았다.

## 기능

### 검사 영역

README의 기능 표는 검사 영역을 여섯 갈래로 나눈다.

| 영역                           | README의 설명                                                                                                 |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| ClawScan(OpenClaw 보안 점검)   | OpenClaw의 안전하지 않은 설정, Skill 위험, CVE 취약점, 개인정보 유출을 한 번에 평가                           |
| Agent Scan                     | 독립적인 다중 에이전트 자동 스캔 프레임워크로 AI 에이전트 워크플로의 보안을 평가하며 Dify와 Coze 지원         |
| MCP Server & Agent Skills scan | MCP 서버와 에이전트 스킬 모두에서 14개 대분류의 보안 위험을 탐지하며 소스 코드나 원격 URL로 스캔              |
| AI infra 취약점 스캔           | 100개 이상의 AI 프레임워크 구성요소와 2,000개 이상의 알려진 CVE를 식별하며 Ollama, ComfyUI, vLLM, n8n 등 지원 |
| 탈옥 평가                      | 선별한 데이터셋과 여러 공격 방식으로 프롬프트 보안 위험을 평가하고 모델 간 비교 제공                          |
| 모델·API 중계 점검기           | 모델 지문 확인, Claude 서명 검증, 중계 블랙박스 감사, PAMELA, Ventor QTest                                    |

릴리스 노트가 보여 주는 속도도 눈에 띈다.
v4.6.0은 LLM API 오염 탐지(모델 바꿔치기와 백도어 위험에 대한 다중
프로브 블랙박스 감사)를 추가하고 취약점 라이브러리를 146개 AI 구성요소와 2,000개
이상의 CVE 규칙으로 늘렸다.
v4.6.1은 모델 지문 범위(Gemini 2.5/3.1,
Gemma 2/3/4, GLM-5.3)를 넓혔고, v4.6.2는 LangFlow, n8n, vLLM, llama-cpp,
MLflow 등 40개 이상의 구성요소에 CVE 규칙 155개를 더했다.

### Skill 스캔과 SkillTrustBench

독립 도구인 `aig-skill-scan`은 `pip install aig-skill-scan`으로 설치해
`LLM_API_KEY` 환경 변수와 모델 이름을 지정해 돌린다.
위험 분류는 SkillTrustBench의 T01~T09를 따르며, A 명령·기억(지시 가로채기, 기억
오염), B 코드 실행(원격 페이로드 실행, 내장 악성 코드), C 시스템 권한(권한 상승,
지속성), D 도구 체인·의존성(도구 가로채기·위장, 안전하지 않은 의존성), E 코드
품질(안전하지 않은 코딩 관행)의 다섯 계층으로 묶인다.

README의 성능 표는 SkillTrustBench에서 모델별 결과를 보여 준다.
F1 기준으로 Claude Opus 4.6이 0.9848, GLM 5.1이 0.9836,
Gemini 3.5 Flash가 0.9792, Kimi 2.6이 0.9780, DeepSeek v4 Flash가 0.9740이다.
오탐률(FPR)은 Opus 4.6이 0.0663, Gemini 3.5 Flash가 0.0120으로 서로 다르다.

## 설치와 사용

### 배포

Docker 20.10 이상, 메모리 4GB 이상, 디스크 10GB 이상이 필요하다.
저장소를 복제하고 `docker-compose -f docker-compose.images.yml up -d`를 실행하면
`http://localhost:8088`에서 웹 UI가 뜬다.
다른 방법으로 `docker.sh` 스크립트를 내려받아 실행하는 한 줄 설치(README가
“권장”으로 표시)와 소스 빌드가 있다.
OpenClaw 채팅에서는 `clawhub install aig-scanner`로 호출할 수 있고,
이때 `AIG_BASE_URL`을 실행 중인 A.I.G 서비스로 지정한다.

### 검사 흐름

AI 인프라 취약점 스캔의 대상은 GitHub 주소가 아니라 실행 중인 AI
서비스의 네트워크 주소다.
로컬 vLLM(`http://127.0.0.1:8000`)이나 LAN의 Ollama 서버, 내부에 노출된 ComfyUI,
CIDR이나 범위로 지정한 여러 호스트가 예로 나온다.
A.I.G가 서비스에 접속해 지문으로 구성요소와 버전을 식별하고 2,000개 이상의 CVE와
맞춰 본 뒤 구성요소 버전, 일치한 취약점, 심각도, 조치 링크가 담긴 보고서를 낸다.
MCP 서버와 에이전트 스킬은 원격 URL이나 업로드한 소스 아카이브로 검사하며 실행
중인 인스턴스가 필요 없다.
탈옥 평가는 설정에서 대상 LLM의 API 엔드포인트와 키를 넣고
데이터셋을 골라 시작한다.

### 확장

규칙은 파일로 추가한다.
서비스 식별 규칙은 `data/fingerprints/`,
취약점 규칙은 `data/vuln/`, MCP 규칙은 `data/mcp/`,
탈옥 평가 데이터셋은 `data/eval`에 YAML 등으로 넣고 풀 리퀘스트로 보낸다.
API 문서는 서비스를 띄운 뒤
`http://localhost:8088/docs/index.html`에서 볼 수 있다.

## 운영 시 주의

README는 이 프로젝트가 기업이나 개인의 내부 사용을 위한 AI 레드팀 플랫폼이며
인증 기능이 없으므로 공개 네트워크에 배포하면 안 된다고 명시한다.
점검 대상 서비스의 주소와 대상 모델의 API 키를 입력받는 구조라서, 이 서비스
자체가 내부망에서 민감한 정보를 다루는 지점이 된다.
온라인 Pro 버전(`aigsec.ai`)은 초대 코드가 필요하며, 이슈나 풀 리퀘스트,
토론으로 기여한 사람이나 커뮤니티를 키우는 데 도움을 준 사람이
우선이라고 적혀 있다.

## 분석

### 하나의 플랫폼이 AI 보안의 서로 다른 층을 한꺼번에 덮으려 한다

A.I.G의 범위는 층이 서로 다르다.
인프라 취약점 스캔은 전통적인 버전 지문과 CVE 대조이고,
MCP·스킬 스캔은 코드와 공급망 점검이며, 탈옥 평가는 모델의 행동 시험이고,
중계 점검기는 API 공급자의 신뢰성 감사다.
이들을 묶는 공통점은 AI를 제품에 넣는 팀이 점검해야 하는 대상이 모델 하나가
아니라 모델을 둘러싼 구성요소 전체라는 인식이다.

이 구성은 프로젝트의 이력에서도 보인다.
README의 팀 소개에 따르면 보안 플랫폼 부서장이 AI 에이전트 통제 상실 위험의 자동
평가를 제안했고, 그 뒤 플랫폼이 AI 인프라 취약점 스캔에서 에이전트 실행 위험,
도구 오용, 권한 경계 평가로 확장됐다고 적는다.
이름의 Infra에서 출발해 범위가 에이전트와 스킬로 넓어진 이력이
현재의 “풀스택”이다.

### 규칙과 데이터를 파일로 둔 확장 모델

기여 안내에서 핵심은 코드가 아니라 데이터 디렉터리다.
지문, 취약점, MCP 규칙, 탈옥 데이터셋이 각각 파일로 분리돼 있어, 새 CVE가
나왔을 때 스캐너의 코드를 고치지 않고 규칙만 추가하면 된다.
팀 소개에서 Zhuque Lab 책임자가 취약점 업데이트와 벤치마크 정렬을 자동화하는
장치를 제안했다고 쓴 것도 이 구조와 맞는다.
2,000개 이상의 규칙과 146개 구성요소라는 규모를 유지하려면 규칙 쪽의
유지보수가 지속돼야 한다.

### 벤치마크와 연구를 같은 곳에서 만든다

README는 자신이 쓰는 벤치마크(SkillTrustBench)와 연구 결과(FORGE-Bench,
RogueHandoff-20, SkillJack)를 같은 도메인과 저장소 아래 둔다.
FORGE-Bench는 16개 영역,
1,800개 궤적에서 에이전트의 통제 상실을 평가하는 결정론적 벤치마크이고,
RogueHandoff-20은 다른 에이전트의 위험한 전략에 노출된 뒤의 취약성을 측정한다.
도구, 분류 체계, 벤치마크, 논문이 한 팀 안에서 순환하는 구조다.

## 비평

### 성능 수치의 출처가 도구를 만든 쪽이다

성능 표의 평가 기준인 SkillTrustBench는 `matrix.tencent.com`에 있고,
README가 Zhuque Lab의 홈페이지로 거는 주소도 같은 도메인이다.
도구를 만든 쪽이 만든 벤치마크에서 도구의 성능을 보이는 것은 흔하지만,
독립적인 재현이나 외부 데이터셋에서의 결과는 README에 없다.
표 안의 수치도 해석에 주의가 필요하다.
가장 높은 F1(0.9848)을 낸 Opus
4.6은 오탐률이 0.0663이어서 정상 스킬의 약 6.6%를 위험하다고 판정하고,
오탐률이 가장 낮은 Gemini 3.5 Flash(0.0120)는 재현율이 0.9641로 더 낮다.
이는 선택의 문제이지만, 한 지표(F1)로 순위를 매기는 표에서는 이 균형이 가려진다.

README의 소식에 “근거 없는 오탐(evidence-free false positives) 감소”가 개선
사항으로 올라 있는 것도 오탐이 실제 문제였음을 시사한다.
또한 이 스캐너가 LLM을 호출해 판정하므로 결과는 쓰는 모델과 프롬프트에 의존하며,
같은 스킬이라도 모델을 바꾸면 판정이 달라질 수 있다.

### 자기 소개로 쌓은 신뢰는 검증되지 않는다

README는 NVIDIA, Google, Microsoft의 취약점 수정을 도왔다는 주장과 수많은
기업·대학 로고를 사용자 감사 항목에 싣는다.
이런 내용은 README 안에서 검증할 수 없다.
별을 눌러 달라는 문구와, 사용자 설문에 성의 있게 답하면 Tencent 기념품을
주겠다는 안내도 같은 지면에 있다.
프로젝트가 활발하다는 사실(자주 이어지는 릴리스,
6,666개의 별)과 점검 결과를 믿어도 된다는 사실은 별개다.

### 스캐너 자체가 공격 표면이다

이 플랫폼은 점검 대상의 주소와 대상 모델의 API 키를 받고,
인증이 없으며, 한 줄 설치 스크립트를 권장 방식으로 내놓는다.
README는 공개 네트워크 배포를 금지하는 것으로 위험을 정리하지만,
내부망 안에서도 접근 통제가 없는 서비스에 키가 모이는 구조는 남는다.
릴리스 노트에는 v4.5.2에 “동적 모드에서 도구 화이트리스트로 RCE를 막는다”는
항목이 있는데, 이는 MCP 서버를 실제로 실행해 점검하는 경로가 있었고 그 경로에
위험이 있었음을 시사한다.
믿을 수 없는 코드를 다루는 도구의 격리 방식이 README에서는 설명되지
않는다(필자는 README와 릴리스 노트만 읽었고 코드는 확인하지 않았다).

### CVE 일치는 취약하다는 증거가 아니다

AI 인프라 스캔의 방식은 서비스를 지문으로 식별하고 버전에 맞는
CVE를 나열하는 것이다.
버전이 같다는 사실이 해당 배포에서 악용할 수 있다는 뜻은 아니다.
배포판이 패치를 되돌려 적용했거나 문제가 되는 기능이 꺼져 있을 수 있다(이 한계는
일반적인 버전 기반 스캐너에 대한 필자의 배경 지식이다).
README의 사용 안내는 “버전을 자동으로 감지한다”고 설명할 뿐 이
한계를 다루지 않는다.
보고서가 취약점을 나열하는 것과 위험을 판단하는 것 사이에는
사람의 검토가 필요하다.

## 인사이트

### AI 보안의 점검 대상은 모델이 아니라 모델을 둘러싼 배관이다

A.I.G의 여섯 기능 가운데 모델의 출력 안전성을 직접 보는 것은 탈옥 평가 하나다.
나머지는 서비스 서버(Ollama, vLLM, ComfyUI, n8n), 에이전트 워크플로, MCP 서버,
스킬, API 중계라는 배관이다.
AI 기능을 제품에 넣는 팀이 늘수록 공격 표면은 모델 가중치가 아니라
모델을 서빙하고 도구에 연결하는 주변 소프트웨어에서 생긴다는 이 프로젝트의
구성이 암시하는 바다.

여기서 나오는 2차 효과는 목록(인벤토리) 문제다.
LAN의 어딘가에서 누군가 Ollama를 띄워 두는 일은 흔하고,
스캔은 대상 주소를 알아야 시작된다.
README가 CIDR와 범위 입력을 예시로 드는 것은 이 문제를 인식했다는 신호지만,
점검 이전에 어떤 AI 서비스가 있는지를 먼저 파악해야 한다는 선행 과제는
도구가 풀어 주지 않는다.

### 스킬과 MCP는 패키지 관리자의 공급망 문제를 다시 겪는다

SkillTrustBench의 분류(원격 페이로드 다운로드와 실행, 도구 가로채기와 위장,
안전하지 않은 의존성)는 패키지 저장소에서 익숙한 공급망 위협과
닮았다(필자의 비교다).
여기에 에이전트에만 있는 범주, 곧 지시 가로채기와 기억 오염이 얹힌다.
코드가 아니라 자연어 지시가 실행의 일부가 되기 때문이다.

릴리스 노트의 v4.5.2는 `.pyc` 바이트코드 우회 탐지와 문자셋 밀수(charset
smuggling) 방어를 추가했다고 적는다.
공격자가 스캐너의 가정을 피해 가는 방법을 찾고, 스캐너가 규칙을 덧붙이는 반복은
백신과 악성코드의 오랜 숨바꼭질과 같은 모양이다(필자의 해석이다).
스킬 마켓이 커질수록 점검은 일회성 감사가 아니라 지속적인 서비스가 돼야 한다.

### LLM이 LLM을 속이는 문서를 판정하는 구조의 순환

`aig-skill-scan`은 LLM을 호출해 스킬을 판정한다.
그런데 스킬이 노리는 대상 중에는 LLM을 조작하는 지시문이 있다.
점검 대상 안에 스캐너 자신을 향한 지시가 들어 있을 수 있다는 점에서,
스캐너도 간접 프롬프트 주입의 표적이 될 수 있다(이는 구조에서 나온 필자의
추론이며 이 프로젝트에서 확인된 사례는 아니다).

README의 연구 목록은 이런 방향의 연구와 겹친다.
DeepSeek Harness의 간접 프롬프트 주입 평가(14,560회 실행)와 SkillJack(자기 진화
에이전트의 스킬 체계에 지속적 백도어를 심는 오염된 궤적)이 그것이다.
방어 도구가 공격 연구와 같은 팀에서 나오는 것은 장점이지만,
스캐너의 판정 모델을 어떻게 보호하는지는 별개의 질문으로 남는다.

### 모델 정체를 검증하는 일이 하나의 제품 영역이 된다

중계 점검기는 호출한 API가 약속한 모델인지,
중간에서 바꿔치기되거나 백도어가 있지 않은지를 여러 번의 질의로 판단한다.
모델 지문 범위가 릴리스마다 넓어지는 것(Gemini, Gemma,
GLM)도 이 영역의 움직임이다.
같은 이름의 엔드포인트가 같은 모델이라는 보장이 사라진 시장에서,
사용자는 받은 것을 확인할 수단이 필요하다.

이 기능이 필요하다는 사실이 시장의 구조를 말해 준다.
API를 재판매하는 중계 사업자가 있고 구매자는 가격과 품질을 직접 비교할 수 없다.
그러면 정체 검증은 결국 경제적 신뢰 문제이며, 점검기가 쓰는 질의가 알려지면 중계
쪽이 그 질의에만 맞춰 응답하게 만들 유인이 생긴다(필자의 추론이다).
공개 오픈소스 점검기가 이 숨바꼭질에서 어떻게 앞서 나갈지는
README만으로는 알 수 없다.
