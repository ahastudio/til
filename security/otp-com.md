# otp.com: 채널을 고르지 않고 수신자만 넘기는 OTP 인증 API

<https://otp.com/>

## 소개

otp.com은 SMS, WhatsApp, Telegram, 이메일로 일회용 인증 코드(OTP)를 보내고
확인하는 API 서비스다.
홈페이지는 Verify Your Users. One API. Multichannel이라는 문구를 내걸고,
영업 상담도 설치비도 없이 셀프서비스로 10분이면 첫 OTP를 보낼 수 있다고 말한다.
`llms.txt`는 범용 메시징이나 마케팅 플랫폼이 아니라
인증에만 집중한다고 스스로 선을 긋는다.

운영 주체는 이용약관에 나온다.
약관의 계약 상대방은 튀르키예 법인 Verifykit Yazılım A.Ş.이고,
등록 주소는 이스탄불 사르예르의 Maslak 지구다.
개인정보처리방침도 같은 회사를 데이터 컨트롤러로 적는다.
같은 이름의 verifykit.com은 WhatsApp OTP, 인바운드 SMS,
플래시콜 같은 인증 상품을 따로 팔고 있다.
약관에 실린 과금 대상에 음성 OTP, 사일런트 인증, 번호 조회가 들어가 있고
개인정보처리방침이 Viber와 플래시콜 제공자를 열거하는 것도,
otp.com이 공개한 네 채널보다 넓은 기존 사업의 문서를 가져다 쓴 흔적으로 읽힌다.
이는 문서 문구에서 나온 해석이며 회사가 밝힌 내용은 아니다.

도메인 자체에도 이력이 있다.
2025년 1월 Hacker News의 한 댓글은 GoDaddy 경매에 나온 세 글자 도메인 예시로
otp.com을 최소 제시가 10만 달러에 올려 두었다.[^soheil]
그 뒤 어떤 경로로 지금 운영사에 넘어갔는지는 공개된 자료에서 확인하지 못했다.

변경 이력으로 본 출시 과정은 짧다.

`@otp.com/mcp`가 37회다.
공개한 지 두 달이 안 된 서비스라는 점을 감안하고 읽어야 한다.

## 동작 방식

### 보내고 확인하는 두 번의 호출

기본 흐름은 `POST /otp/send`로 코드를 보내고 `POST /otp/verify`로 사용자가
입력한 값을 확인하는 것이다.
기본 URL은 `https://api.otp.com/api/v1`이고, API 키를 Bearer 토큰으로 보낸다.
`recipient`에는 E.164 형식 전화번호나 이메일 주소를 넣는다.
요청에 채널 필드는 없다.
응답에는 `otp_id`, `status`, 실제로 쓰인 `channel`,
가린 수신자 `masked_recipient`,
WhatsApp 링크 `action_url`, 마무리 방식 `completion`이 담긴다.

코드 자체는 어떤 응답에도 들어 있지 않다.
서버는 코드를 만들어 보내기만 하고, 확인은 `otp_id`와 사용자가 입력한 코드를
다시 보내는 방식으로만 한다.
틀린 코드를 넣어도 바로 실패하지 않고,
시도 횟수가 남아 있는 동안 `pending`에 머문다.
시도가 바닥나면 `failed`, 수명이 지나면 시도가 남아 있어도 `expired`가 된다.
정확한 시도 횟수와 코드 수명은 문서에 숫자로 나오지 않는다.

`GET /otp/{otp_id}`는 언제든 상태를 읽는 풀(pull) 방식 조회이고,
웹훅은 `otp.approved`, `otp.failed`, `delivery.delivered`,
`delivery.failed` 네 가지 이벤트를 보낸다.
웹훅 요청에는 `{timestamp}.{rawBody}`를 서명 비밀로 HMAC-SHA256한
`X-Webhook-Signature`와 `X-Webhook-Timestamp`가 붙는다.
재시도로 같은 이벤트가 다시 올 수 있으므로 이벤트 `id`로 중복을 걸러야 한다.

### 라우팅과 폴백

채널은 계정의 라우팅 설정이 정한다.
이메일 주소면 이메일로 보내고, 전화번호면 앱마다 정한 채널 순서를 따르며,
국가별로 순서를 덮어쓸 수 있다.
문서는 그래서 응답의 `channel`로 분기하지 말고 `completion`을 보라고 권한다.

폴백은 서버가 알아서 다음 채널로 넘기는 것이 아니라
클라이언트가 `POST /otp/resend`를 호출할 때 일어난다.
`resend`는 같은 OTP를 순서상 다음 채널로 옮기고,
`{"channel":"sms"}`처럼 채널을 지정하면 그 채널로 옮긴다.
SMS, 이메일, Telegram에서는 새 코드를 만들지 않고 같은 코드를 다시 보낸다.
재전송 사이에는 쿨다운이 있어 너무 빨리 부르면 `429 ResendCooldownError`가 오고,
보낼 수 있는 횟수를 다 쓰면 `409 ResendNotAllowedError`가 온다.

일부 국가는 SMS 펌핑과 요금 사기 때문에 플랫폼 전체에서 막혀 있고,
그런 곳으로 보내면 `403 GeoBlockedError`가 난다.
정당한 사유가 있으면 대시보드에서 계정 단위로 열어 달라고 신청할 수 있다.
SMS 펌핑이 어떤 구조로 돈을 빼 가는지는
[`security/ait-fraud.md`](ait-fraud.md)에 정리되어 있다.

### `client_ip`가 하는 일

`send` 요청의 `client_ip`는 선택 필드지만 문서는 첫날부터 넣으라고 거듭 말한다.
이 값은 서버 주소가 아니라 OTP를 요청한 최종 사용자의 IP다.
값이 없으면 훨씬 빡빡한 앱 단위 공용 속도 제한에 묶이고,
값이 있으면 VPN, 프록시, Tor, 데이터센터 IP는 속도를 늦추고 알려진 악성 IP는
`403 IpReputationBlockedError`로 거절한다.
사설 주소나 예약 주소는 없는 것으로 친다.
`resend`는 원래 `send`에 실린 IP로 평가한다.

### WhatsApp의 세 가지 방식

WhatsApp만 흐름이 여러 갈래다.
계정은 아래 셋 중 하나로 동작하고, 기본값은 Code back이다.
방식을 바꾸려면 `info@otp.com`에 메일을 보내야 한다.

| 방식            | `action_url` | `completion` | 클라이언트가 할 일                                        |
| --------------- | ------------ | ------------ | --------------------------------------------------------- |
| Code back       | `wa.me` 링크 | `"code"`     | 링크를 보여 주고, 사용자가 받은 코드를 받아 `verify` 호출 |
| Inbound approve | `wa.me` 링크 | `"inbound"`  | 링크를 보여 주고, 상태를 3~5초마다 조회하거나 웹훅 대기   |
| Template        | `null`       | `"code"`     | SMS와 똑같이 코드를 받아 `verify` 호출                    |

두 링크 방식에서는 `send` 시점에 아무것도 발송되지 않는다.
사용자가 링크를 열어 미리 채워진 메시지를 otp.com 업무용 번호로 보내야 비로소
흐름이 시작된다.
이 사용자 발신(MO) 구조는
[`security/octomo-mo-sms-auth.md`](octomo-mo-sms-auth.md)가 다룬
역방향 SMS 인증과 같은 발상이고, Inbound approve는 코드 없이 메시지 자체가 승인
신호가 된다는 점에서 그쪽에 더 가깝다.

링크 방식에서는 WhatsApp이 채널 순서의 맨 앞에서만 동작한다.
링크를 보여 주는 일은 앱만 할 수 있기 때문에,
일반 `resend`는 순서 중간의 WhatsApp을 건너뛴다.
이미 링크 상태인 OTP에 일반 `resend`를 부르면 같은 링크를 다시 돌려줄 뿐이라,
WhatsApp이 없는 사용자를 SMS로 옮기려면
반드시 `{"channel":"sms"}`를 지정해야 한다.
`completion`은 OTP가 만들어질 때 고정되므로 계정 방식을 바꿔도 진행 중인
인증에는 영향이 없다.

### WhatsApp 코드는 자동 입력되지 않는다고 보고 설계한다

otp.com 문서에는 WhatsApp으로 받은 코드를 앱이나 브라우저가 자동으로 채워 준다는
설명이 없다.
WhatsApp 채널 페이지는 사용자가 링크를 열어 대화를 시작하면
코드가 그 대화로 돌아온다고만 적는다.
그리고 이 채널이 사용자에게 동작을 하나 더 요구하므로,
버튼을 보여 줄 수 있는 흐름에 맞는다고 덧붙인다.
WhatsApp 인증 문서도 Code back에서는 사용자가 받은 코드를 앱 화면에 직접
입력하고, Template에서는 SMS처럼 사용자가 코드를 입력한다고 적는다.
otp.com이 채널을 비교한 글도 WhatsApp의 약점을 코드를 받으려면 한 번 더 눌러야
하고 앱이 있어야 한다는 점으로 꼽고,
흐름을 링크로 코드를 받은 뒤 다시 입력하는 것으로 설명한다.

otp.com이 자동 입력을 다루는 곳은 OTP 입력 화면 설계 가이드 하나이고,
그 경로는 모두 SMS 기준이다.
웹에서는 `autocomplete="one-time-code"` 입력란에 iOS Safari가 수신한 SMS의 코드를
제안하고, 네이티브에서는 Android의 SMS Retriever API와 자동 완성,
iOS의 AutoFill 프레임워크를 쓴다는 설명이다.
가이드는 이 장치들이 메시지 형식에 달려 있다고 하는데,
WhatsApp 메시지에 대해서는 같은 이야기를 하지 않는다.
모바일 SDK 문서도 SDK가 화면을 띄우고 사용자의 입력을 받는다고만 하고,
자동 입력은 언급하지 않는다.

WhatsApp 자체에는 인증 템플릿의 원탭·제로탭 자동 입력이 있다.
다만 이것은 otp.com 문서가 아니라 Meta의 WhatsApp Business 기능이고(해석),
Android 앱의 패키지 이름과 서명 해시를 템플릿에 등록해야 동작한다.
otp.com의 `send` 요청에는 이런 값을 넘기는 필드가 없고,
Template 방식이 어떤 WhatsApp 템플릿으로 보내는지도 문서에 없다.
따라서 이 기능이 otp.com에서 동작한다고 기대할 근거는 없다.

정리하면 Code back과 Template에서는 사용자가 WhatsApp에서 코드를 보고
앱으로 돌아와 직접 입력하거나 붙여 넣는다고 가정해야 한다.
입력 자체를 없애는 방식은 Inbound approve뿐이다.
사용자가 미리 채워진 메시지를 보내면 그것이 승인이 되므로 코드 입력란이 필요 없다.
대신 사용자는 WhatsApp에서 보내기를 누르고 앱으로 돌아와야 하고,
앱은 상태를 조회하거나 웹훅을 기다려야 한다.
SMS 자동 입력이 주는 한 번 탭 경험을 원한다면
채널 순서에서 SMS를 WhatsApp보다 앞에 두는 수밖에 없다.
그때도 otp.com이 보내는 SMS 형식이 OS의 자동 입력 조건에 맞는지는
실제 기기에서 확인해야 한다.

### 모바일 SDK와 토큰 교환

키는 두 종류다.
서버 키(`otp_live_…`, `otp_test_…`)는 모든 동작을 할 수 있어 백엔드에만 둔다.
공개 키(`otp_pk_live_…`, `otp_pk_test_…`)는 앱 바이너리에 넣어 배포하는 키로,
인증을 시작하고 답하는 일만 할 수 있고 누가 인증됐는지는 읽지 못한다.

모바일 SDK는 화면을 띄우고 코드를 보내고 입력을 받은 뒤 짧게 사는
`verification_token`만 돌려준다.
백엔드가 서버 키로 `POST /verifications/exchange`를 불러야 어떤 수신자가
인증됐는지 알 수 있다.
문서는 기기에서 본 성공 여부는 UI용 힌트일 뿐이고,
변조된 빌드는 어떤 결과든 주장할 수 있다고 분명히 적는다.
토큰이 없거나 만료됐거나 이미 교환됐거나 남의 것이면
모두 같은 `404`를 돌려주는데,
이를 구분해 주면 API 키를 가진 누구나 토큰 존재 여부를 떠볼 수 있기
때문이라고 설명한다.

공개 키를 빼내 다른 곳에서 쓰는 것은 기기 증명으로 막는다.
SDK는 처음 쓸 때 iOS에서는 App Attest, Android에서는 Keystore 증명으로 하드웨어
키를 등록하고 모든 발송에 서명한다.
Android 최소 버전이 흔한 API 24가 아니라 26인 이유도
하드웨어 증명이 8.0부터 보장되기 때문이라고 밝힌다.
모바일 SDK는 상용 라이선스 바이너리로 배포되고 소스가 없으며,
서버 SDK와 MCP 서버는 MIT 라이선스로 소스가 공개되어 있다.

## 연동하기

### REST로 보내고 확인하기

아래는 문서의 샌드박스 예시를 그대로 옮긴 것이다.
테스트 키에서는 실제 메시지가 나가지 않고 과금도 없으며,
맞는 코드는 항상 `123456`이다.
이 문서를 쓰면서 직접 실행해 보지는 않았다.

```bash
# 1. 코드 보내기: 채널은 넘기지 않는다. client_ip는 최종 사용자의 IP다.
curl -X POST https://api.otp.com/api/v1/otp/send \
  -H "Authorization: Bearer otp_test_•••" \
  -H "Content-Type: application/json" \
  -H "idempotency-key: signup:8f21c4" \
  -d '{"recipient":"+14155552671","locale":"en","client_ip":"81.2.69.142"}'

# 2. 사용자가 입력한 코드 확인
curl -X POST https://api.otp.com/api/v1/otp/verify \
  -H "Authorization: Bearer otp_test_•••" \
  -H "Content-Type: application/json" \
  -d '{"otp_id":"9f3c1b2a-…","code":"123456"}'

# 3. 도착하지 않았으면 다음 채널로, 또는 채널을 지정해서
curl -X POST https://api.otp.com/api/v1/otp/resend \
  -H "Authorization: Bearer otp_test_•••" \
  -H "Content-Type: application/json" \
  -d '{"otp_id":"9f3c1b2a-…","channel":"sms"}'
```

`idempotency-key` 헤더를 붙이면 같은 호출을 반복해도 두 번째 코드를 보내지 않고
첫 응답을 다시 돌려준다.
네트워크 타임아웃, 큐 재전달, 버튼 두 번 누르기에 대비하는 장치다.
키는 회사 단위로 묶이고 키만으로 대조하므로,
수신자가 다른데 같은 키를 쓰면 첫 수신자의 OTP가 돌아온다.
`signup:<user_id>`처럼 인증 대상마다 다른 키를 써야 한다.
키 길이는 128자까지다.

### SDK와 MCP 서버

서버 SDK는 공개 OpenAPI 명세에서 생성되며 Node.js, Python, Go, PHP를 지원한다.
Python 패키지는 아직 PyPI에 없어 GitHub에서 설치한다.
1.2.0부터는 토큰 교환을 위한 `VerificationsApi`가 별도 클라이언트로 들어 있다.

MCP 서버 `@otp.com/mcp`는 stdio로 동작하는 얇은 클라이언트이고,
`send_otp`, `verify_otp`, `resend_otp`, `get_otp_status` 네 도구를 노출한다.
환경 변수 `OTP_API_KEY`가 유일한 자격 증명이다.
문서는 `claude mcp add`나 `codex mcp add` 같은 한 줄 설치가 키를 설정 파일과 셸
기록에 평문으로 남긴다고 경고하고,
공유 기기나 라이브 키라면 설정 파일을 직접 고치라고 권한다.
도구 설명에도 에이전트가 IP를 지어내거나 서버 자신의 주소를 넣지 말라는 문장이
들어 있다.

홈페이지는 이 모든 것을 한 번의 프롬프트로 연동한다고 내세운다.
API 문서 주소와 호출 예시가 담긴 프롬프트를 복사해 AI 도구에 붙여 넣으면
에이전트가 API 문서를 읽고 연동 코드를 쓰고 테스트까지 한다는 설명이다.

## 가격

과금 단위는 보낸 인증 한 건이다.
선불 크레딧을 충전해 두면 건마다 공개된 국가별 요율로 차감되고,
설치비, 월 최소 금액, 구독료는 없다.
새 계정에는 신용카드 없이 무료 크레딧 3달러가 들어온다.

| 국가     | SMS     | WhatsApp |
| -------- | ------- | -------- |
| 미국     | $0.0132 | $0.0041  |
| 한국     | $0.0084 | $0.0093  |
| 독일     | $0.0480 | $0.0660  |
| 인도     | $0.0384 | $0.0017  |
| 튀르키예 | $0.0012 | $0.0011  |
| 콜롬비아 | $0.0009 | $0.0010  |
| 코모로   | $0.4238 | $0.0093  |

Telegram은 어느 나라든 $0.0120, 이메일은 $0.0012로 고정이다.
가격표에는 199개국이 올라 있고, SMS는 콜롬비아 $0.0009부터 코모로 $0.4238까지,
WhatsApp은 콜롬비아 $0.0010부터 독일 $0.0660까지 벌어진다.
가격 페이지 계산기에 미국 SMS 월 1만 건을 넣으면 132달러가 나온다.
SMS와 WhatsApp 요율은 전달 가능한 경로 중 가장 싼 값이라 출발점일 뿐이며,
실제 비용은 메시지를 받는 통신사와 폴백 경로에 따라 달라진다고 적혀 있다.

무엇에 돈을 내는지는 분명하게 정리되어 있다.
코드를 보낼 때 한 번 과금되고, 사용자가 코드를 받든 못 받든,
결과가 승인이든 실패든 만료든 같다.
확인 호출은 몇 번을 하든 무료다.
`resend`는 새 인증으로 쳐서 옮겨 간 채널의 요율로 다시 과금된다.
아무것도 나가기 전에 거절된 발송과 샌드박스 발송은 무료다.
WhatsApp 링크 방식처럼 코드 하나에 메시지 두 통이 오가도 한 건으로 센다.

## 약관이 정하는 것

약관은 홈페이지의 가벼운 인상과 결이 다르다.
서명한 주문서가 없으면 전달, 지연, 경로 안정성, 국가 범위,
인증 성공 어느 것도 보장하지 않는다.
구매는 크레딧이 충전되는 순간 확정되어 환불되지 않고,
사용자가 받지 못했거나 필터링, 경로 폐쇄,
계정 정지가 일어나도 환불 사유가 되지 않는다.
구매 정책은 한 푼도 쓰지 않은 충전분에 한해
환불을 요청할 수 있다고 따로 적어 두었다.
일반 크레딧은 자동으로 만료되지 않지만, 체험이나 프로모션 크레딧은 언제든
줄이거나 없앨 수 있다.

SMS 펌핑의 책임은 고객 쪽으로 넘어온다.
금지 행위 목록에 SMS 펌핑, 트래픽 자극, 인증 남용, 가짜 계정 생성이 들어 있고,
의심만으로도 계정과 경로를 막을 수 있으며 그로 인한 차감은 환불하지 않는다.
면책 조항은 고객 계정과 연관된 SMS 펌핑과 인위적 트래픽으로 생긴 청구까지
고객이 배상하게 한다.
otp.com의 총 책임 한도는 50달러다.
분쟁은 ICC 규칙에 따른 중재로 풀며, 중재지는 런던,
준거법은 잉글랜드와 웨일스 법이다.
결제는 Zotlo(Z3P LLP) 같은 판매 대행(Merchant of Record)이 처리할 수 있다.
약관은 사업자 전용이며 소비자로서의 이용은 받지 않는다.

## 트레이드오프

### 채널을 고르지 않는 API는 분기를 없애지 못하고 옮길 뿐이다

요청에서 채널을 뺀 설계의 이점은 분명하다.
국가별로 더 잘 들어가는 채널을 대시보드에서 바꿔도 코드를 고칠 필요가 없다.
하지만 WhatsApp 링크 방식이 들어오면서 클라이언트는 다시 분기해야 한다.
`action_url`이 있으면 버튼을 보여 주고, `completion`이 `"inbound"`면 코드 입력란
대신 폴링이나 웹훅을 기다려야 한다.
문서 스스로 Inbound approve를 요청하기 전에 배포된 모든 클라이언트가
`completion`을 읽는지 확인하라고 경고한다.
채널 이름 대신 두 필드로 분기하게 바꿨을 뿐,
클라이언트가 흐름의 모양을 알아야 한다는 사실은 그대로다.

더 까다로운 문제는 이 분기가 계정 설정에 달려 있다는 점이다.
코드는 그대로인데 운영자가 메일 한 통으로 WhatsApp 방식을 바꾸면,
이미 앱스토어에 나간 구버전 클라이언트가
코드가 오지 않는 OTP에 입력란을 띄울 수 있다.
`completion`을 OTP 생성 시점에 고정하는 것은 진행 중인 인증만 지켜 줄 뿐,
다음 인증부터는 지켜 주지 않는다.

### 발송 기준 과금은 폴백 비용을 고객에게 넘긴다

결과와 상관없이 발송마다 과금하는 방식은 단순하고 예측하기 쉽다.
대신 전달 실패의 비용을 고객이 진다.
SMS가 안 들어가 `resend`로 WhatsApp에 넘기면 두 건 값을 내고,
가격 페이지도 폴백이 잦다면 두 번째 시도 비용을 따로 잡으라고 권한다.
홈페이지가 말하는 99% 넘는 전달률이 이 폴백 체인을 전제로 한 숫자라면,
그 전달률에는 두 번째, 세 번째 발송 비용이 이미 들어 있는 셈이다.

인증에 성공한 건만 과금하는 모델을 가정해 비교하면 차이가 드러난다.
그런 모델이라면 펌핑으로 생긴 가짜 발송 비용 상당 부분을 제공자가 떠안겠지만,
발송 기준 과금에서는 그 비용이 고스란히 고객 잔액에서 빠진다.
otp.com은 국가 차단과 IP 평판으로 이 위험을 줄이려 하지만,
남는 위험은 약관이 고객에게 배정한다.

### 같은 코드를 다른 채널로 다시 보내는 설계

SMS, 이메일, Telegram 사이의 `resend`는
새 코드를 만들지 않고 같은 코드를 다시 보낸다.
사용자 입장에서는 먼저 온 메시지와 나중 온 메시지 중 무엇을 넣어도 맞으니
혼란이 적다.
반면 같은 비밀이 여러 전달 경로에 동시에 놓이므로,
노출 면적은 채널 수만큼 넓어진다.
이메일 계정이나 SIM 중 한 곳만 탈취되어도 그 코드가 유효하다는 뜻이고,
코드가 하나의 수명과 시도 횟수를 공유한다는 점만이 이를 묶어 둔다.

## 함정

### 홈페이지와 문서가 서로 다른 말을 한다

홈페이지의 기능 설명은 폴백이 추가 코드도 설정도 필요 없이
자동으로 일어난다고 쓴다.
문서상으로는 클라이언트가 `resend`를 불러야만 다음 채널로 넘어가고,
WhatsApp 링크 방식에서는 채널을 직접 지정해야 빠져나온다.
폴백 버튼과 타이머는 결국 연동하는 쪽이 만들어야 한다.

채널 순서가 끝났을 때의 동작도 문서마다 다르다.
`resend` 레퍼런스와 라우팅 문서는 마지막으로 쓸 수 있는 채널을 반복한다고 하고,
FAQ는 더 쓸 채널이 없다고 알려 준다고 하며,
수명 주기 문서는 남은 채널이 없으면 `409`를 준다고 한다.
재시도 로직을 짤 때는 문서를 믿기보다
샌드박스에서 끝까지 `resend`를 불러 실제 응답을 확인해야 한다.

작은 불일치도 있다.
홈페이지는 Telegram 사용자를 WhatsApp과 똑같이 20억 명 이상이라고 적고,
180개국 이상이라는 홈페이지 문구와 달리 가격표에는 199개국이 있다.
채널 페이지는 SMS가 국가별로 값이 다른 유일한 채널이라면서
바로 옆에 WhatsApp도 국가별 요율을 붙여 두었고,
SMS 가격이 1센트 미만에서 몇 센트 사이라고 하지만
같은 페이지의 상한은 42센트가 넘는다.

### 에이전트용 연동 자료가 가장 늦게 고쳐진다

AI 도구에 붙여 넣으라는 홈페이지 프롬프트의 Node.js 예시는
`api.sendOtp({ sendOtpRequest: … })`와 `verifyOtpRequest`를 쓴다.
SDK 문서와 `sdk-node` 저장소의 생성 코드는
`sendRequest`와 `verifyRequest`를 받는다.
에이전트가 이 프롬프트를 그대로 따르면 타입 검사에서 걸리거나,
JavaScript라면 필수 인자 누락으로 런타임에 실패한다.

MCP 서버도 10월 7일의 WhatsApp 방식 변경을 따라가지 못했다.
GitHub 저장소의 마지막 푸시는 8월 18일이고, `get_otp_status` 도구 설명은
WhatsApp OTP가 스스로 승인되기를 기다리며 폴링하지 말라고,
모든 채널에서 `verify_otp`를 불러야만 `pending`을 벗어난다고 적고 있다.
Inbound approve 계정에서는 정반대로 상태 조회가 유일한 마무리 방법이다.
`send_otp` 설명도 WhatsApp이면 항상 `action_url`이 있다고 하지만
Template 방식에서는 `null`이다.
에이전트는 도구 설명을 그대로 믿으므로,
이런 계정 설정에서는 에이전트가 잘못된 흐름을 고를 수 있다.

### 샌드박스가 보여 주지 않는 것

샌드박스의 정답 코드는 계정의 코드 길이에 맞춰 숫자를 세어 올린 값이라,
기본 6자리에서 바꾼 계정은 `123456`이 아니라 `1234`처럼 된다.
샌드박스에서는 `completion`이 항상 `"code"`라
Inbound approve 흐름은 라이브 키로만 시험할 수 있다.
iOS에서는 Xcode로 설치한 빌드가 개발용 App Attest 환경으로 증명하는데,
라이브 키는 운영 환경만 받으므로
샌드박스 키로 잘 되던 앱이 같은 기기에서 라이브 키로 바꾸는 순간 `403`을 받는다.
문서는 라이브 키는 TestFlight 빌드로 시험하라고 안내한다.

### `client_ip`를 빼먹으면 장애처럼 보인다

`client_ip` 없이 보내면 앱 전체가 하나의 좁은 속도 제한을 나눠 쓴다.
개발 중에는 문제가 없다가
트래픽이 늘면 `Rate limit exceeded: client_ip`가 쏟아진다.
로드 밸런서 뒤에서 `req.ip`가 프록시 주소를 돌려주면
모든 사용자가 같은 IP로 보이므로,
신뢰할 프록시 설정을 먼저 맞춰야 이 값이 의미를 가진다.

## 체크리스트

- 서버 키(`otp_live_…`)가 브라우저나 앱 바이너리 어디에도 들어가지 않는가?
- 모바일 인증 결과를 기기의 `matched`가 아니라 `POST /verifications/exchange` 응답으로 판단하는가?
- `send`마다 최종 사용자의 실제 IP를 `client_ip`로 넘기는가?
- `idempotency-key`를 인증 대상마다 다르게 만드는가?
- 클라이언트가 `channel`이 아니라 `action_url`과 `completion`으로 화면을 고르는가?
- WhatsApp 링크 방식에서 SMS로 빠지는 버튼이 `{"channel":"sms"}`를 지정해 `resend`를 부르는가?
- 폴백까지 포함한 발송 건수로 월 비용을 계산했는가?
- 웹훅 서명을 원본 본문으로 다시 계산해 상수 시간으로 비교하고, 오래된 타임스탬프를 거절하는가?
- 웹훅 이벤트를 `id`로 중복 제거하는가?
- 펌핑 방어를 otp.com의 국가 차단에만 맡기지 않고 가입 경로에 자체 속도 제한을 두었는가?

## 기억할 원칙

### 기기가 말한 결과는 증거가 아니다

otp.com 문서에서 가장 단단한 부분은 모바일 흐름이다.
앱에 들어가는 키는 누구나 꺼낼 수 있고
앱이 보고하는 성공은 누구나 위조할 수 있으니,
기기에는 의미 없는 토큰만 주고 서버 대 서버 교환에서만 사실을 확정한다.
이 원칙은 OTP에 국한되지 않는다.
결제, 구독 영수증, 게임 점수처럼 클라이언트가 결과를 보고하는 모든 흐름에서,
신뢰할 수 있는 답은 내가 통제하는 서버가 직접 확인한 것뿐이다.

### 인증 API의 비용 모델이 보안 책임의 경계를 정한다

발송 기준 과금, 환불 불가, 펌핑 책임의 고객 전가는
따로 떨어진 조항이 아니라 한 묶음이다.
돈이 발송 시점에 나가면 가짜 발송을 막을 동기도 발송하는 쪽에 있어야 하고,
약관은 정확히 그 방향으로 책임을 배정한다.
인증 제공자를 고를 때 요율표보다 먼저 볼 것은,
공격자가 내 가입 폼으로 문자를 수만 통 보냈을 때
그 비용이 누구 잔액에서 빠지는지다.
