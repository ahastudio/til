# CSS만으로 웹메일의 비밀번호와 토큰을 훔치는 법

원문: [CSS: the bomb inside your inbox](https://portswigger.net/research/css-the-bomb-inside-your-inbox)

## 요약

PortSwigger Research의 Gareth Heyes가 2026년 8월 6일에 공개한 연구
글이며 Black Hat USA 2026 발표와 함께 나왔다.
출발점은 한 문장이다.
웹메일 클라이언트는 흔히 신뢰할 수 없는 CSS를 신뢰된 UI 안에서
렌더링하며, 이를 안전하게 만들기 위해 CSS 살균(sanitization)에
의존하지만 그 경계를 무너뜨릴 수 있다는 것이다.
연구는 Outlook, Gmail, Fastmail, ProtonMail, Yahoo Mail, AOL Mail,
OpenAI Atlas, Cowork를 대상으로 실제 우회를 시연한다.

첫째 범주는 허용된 HTML/CSS 자체의 오용이다.
`<label>` 요소로 UI 동작을 가로채는 라벨 하이재킹은 Outlook에서
핀 고정이나 리본 컨트롤 조작에 쓰였다.
`:before`/`:after` 의사 요소로 LLM에게는 감춰진 텍스트를 보여 주고
사용자에게는 다른 텍스트를 보여 주는 간접 프롬프트 주입은 OpenAI
Atlas를 겨냥했다.
초안 작성 중 HTML을 붙여 넣는 순간 발생하는 경쟁 조건을 이용한
클립보드 토큰 유출은 AOL과 Yahoo와 Firefox에서 성립했다.

둘째 범주는 CSS 속성 선택자 공격이다.
Medium의 12자리 16진수 이메일 로그인 토큰 같은 값을 중첩된 속성
선택자로 훔친다.
중첩 선택자로 CSS 크기를 줄이면서 토큰의 앞뒤 조각을 무차별
대입하고, 겹치는 16진수 조각으로 가운데 문자를 계산해 낸다.

셋째 범주는 CSP를 우회하는 토큰 유출이다.
외부 리소스가 CSP로 막혀 있어도, 글꼴 높이 오라클과 CSS 애니메이션을
써서 숫자 토큰을 훔칠 수 있다는 것이다.
`unicode-range`와 `descent-override`를 쓴 커스텀 `@font-face` 규칙,
애니메이션을 통한 높이 계산, 그리고 `inset` 속성으로 토큰의 등장
빈도에 따라 링크를 보이거나 숨기는 방식을 조합한다.

넷째 범주는 살균기 우회다.
이미지 프록시 우회로는 Fastmail에서 이스케이프된 백슬래시
(`/\5c/user.fm/`)로 base64 인코딩을 우회하는 방법, ProtonMail에서
URL 함수 안에 주석을 중첩하는 방법, Gmail에서 정의되지 않은 변수를
쓴 `image-set(var(--x,'//02.rs'))`가 제시된다.
CSS 변이(mutation) 공격으로는 Chrome이 CSSOM으로 변환할 때 키프레임
이름과 미디어 쿼리 안의 16진수 이스케이프를 해독한다는 점을
이용한다.
예를 들어 `@keyframes foo\7d\2a`가 `@keyframes foo }*`로 바뀌어
Fastmail의 CSS 스코프를 벗어난다.
Outlook의 살균기는 CSS 주석을 곁들인 미디어 쿼리로 임의 선택자를
주입해 우회한다.

### 착취 기법

CSS 핫와이어링은 UI 동작 위에 보이지 않는 `:before`/`:after` 의사
요소를 겹쳐 페이지의 모든 클릭을 가로채고, 이메일을 스팸으로
표시하는 것 같은 의도하지 않은 동작을 강제한다.

비밀번호 탈취는 여러 기법을 조합한다.
DOMPurify가 허용 목록에 올린 커스텀 데이터 속성에 라이브러리가
위험한 CSS를 덧붙이는 CSS 가젯, 키 입력을 가리기 위해
`-webkit-text-security:disc`를 쓴 `<select>` 요소 위장, 키 입력을
감지하는 인접 형제 결합자(`option+option:checked`), 실시간
키로깅을 가능하게 하는 Firefox의 select 타이머 재설정 특이 동작,
이메일 경계를 벗어나기 위한 `position:fixed` 가젯이 그것이다.

Slack 토큰 유출은 Gmail의 이미지 프록시 우회와, Cowork의 AI 이메일
비서를 겨냥한 간접 프롬프트 주입을 결합해 이메일에서 토큰을
빼낸다.

방어 권고로는 이메일을 샌드박스 iframe으로 격리할 것, 이미지
요청과 `data:` URL을 차단할 것, CSS 키워드에 엄격한 허용 문자
목록을 적용할 것, `:has()`와 `:checked`와 `:focus`와 `:not()` 같은
위험한 선택자를 금지할 것, 허용된 속성이 만들어 내는 CSS 가젯을
감사할 것, 이미지 프록시를 항상 쓸 것을 든다.
앞으로의 공격으로는 지연 로드 이미지를 쓴 제안 중인
`<selectedcontent>` 요소를 이용한 HTML 전용 키로거와, interest
invoker와 popover 속성을 이용한 Chrome 실시간 키로거를 제시한다.
전체 소스 코드는 GitHub에 공개되어 있다.

## 분석

### 이 연구의 축은 “살균”이 아니라 “신뢰 경계의 위치”다

CSS 살균은 위험한 값을 걸러 내는 문제로 다뤄지는 경우가 많지만, 이
연구가 실제로 겨냥하는 것은 다른 층위다.
살균기가 무엇을 걸러 낼지 정확히 알더라도, CSS 자체가 튜링
완전에 가까운 표현력을 가진 선언형 언어이기 때문에 “허용된 것들의
조합”이 예상하지 못한 능력을 만들어 낸다.
CSS 가젯이라는 개념이 이를 정확히 짚는다.
DOMPurify가 안전하다고 판단해 허용한 커스텀 데이터 속성이, 다른
라이브러리가 그 속성에 CSS를 덧붙이는 순간 위험한 조합이 된다.

이 구조는 살균기 하나를 아무리 개선해도 해소되지 않는다.
살균기는 자신이 허용한 값의 목록을 알지만, 그 값이 페이지의 다른
컴포넌트와 만났을 때 생기는 창발적 능력까지는 알 수 없기 때문이다.
곧 CSS 살균의 근본적 난점은 필터링 규칙의 정교함이 아니라, 신뢰
경계를 컴포넌트 단위가 아니라 전체 렌더링 파이프라인 단위로 그어야
한다는 요구에 있다.

### 파서 차이가 살균기와 렌더러 사이의 틈을 만든다

Chrome의 CSSOM 변이 공격이 이 연구에서 가장 시사적인 사례다.
살균기는 원본 CSS 텍스트를 검사해 위험한 패턴이 없다고 판단하지만,
브라우저는 그 CSS를 파싱해 내부 객체 모델로 변환하는 과정에서
16진수 이스케이프를 해독한다.
`foo\7d\2a`라는, 살균기가 볼 때는 안전한 식별자가 브라우저 내부에서
`foo }*`로 바뀌면서 CSS 스코프를 이탈한다.

이것은 파서 차등 공격(parser differential attack)의 CSS 판본이다.
같은 입력을 두 시스템이 서로 다르게 해석할 때, 검사하는 시스템의
해석과 실행하는 시스템의 해석 사이의 틈이 공격 표면이 된다는
패턴은 HTTP 요청 밀수(request smuggling)나 XML 파서 차이 공격에서
이미 반복적으로 나타났다.
PortSwigger 자신이 HTTP 요청 밀수 연구로 유명한 조직이라는 점을
생각하면, 이번 CSS 연구는 같은 방법론을 새 프로토콜 계층에 옮겨
적용한 결과로 읽을 수 있다.

### AI 비서의 등장이 오래된 취약점에 새 파괴력을 준다

간접 프롬프트 주입 사례들 — OpenAI Atlas를 겨냥한 의사 요소 은닉
텍스트, Cowork의 AI 이메일 비서를 겨냥한 Slack 토큰 유출 —
이 연구에서 가장 새로운 부분이다.
그런데 그 기반 기술인 CSS 의사 요소로 사람 눈에는 안 보이는 텍스트를
숨기는 기법 자체는 전혀 새롭지 않다.
스팸 필터를 속이려고 흰 배경에 흰 텍스트를 쓰는 것과 같은 계열의
오래된 수법이다.

달라진 것은 그 숨겨진 텍스트를 읽는 주체다.
사람은 안 보이는 텍스트를 무시하지만, 이메일을 요약하고 답장을
초안하는 AI 비서는 렌더링된 화면이 아니라 DOM이나 텍스트
콘텐츠에 접근할 가능성이 높고, 그 경우 숨겨진 텍스트가 사람에게는
안 보이면서 AI에게는 명령으로 읽힌다.
곧 이 연구는 새 취약점을 발견했다기보다, 오래된 취약점의 피해자가
사람에서 AI 에이전트로 넓어지는 순간을 포착한 것에 가깝다.

## 비평

### “CSS 살균으로 안전하게 만들려 한다”는 전제가 방어 산업 전체를 겨눈다

이 연구는 특정 벤더 하나의 실수가 아니라 Outlook, Gmail, Fastmail,
ProtonMail, Yahoo, AOL을 모두 동시에 무너뜨린다.
이렇게 광범위한 벤더가 같은 종류의 공격에 취약하다는 것은 개별
구현 실수가 아니라 업계가 공유하는 방어 모델 자체의 결함을
시사한다.

그런데 연구는 그 결함이 무엇인지를 명시적으로 정리하지 않는다.
방어 권고 목록은 “이미지 프록시를 항상 쓸 것”, “위험한 선택자를
금지할 것”처럼 개별 우회에 대한 패치를 나열하는 데 그친다.
살균 기반 접근 자체가 구조적으로 지속 가능하지 않다면, 필요한
것은 우회 목록을 계속 늘리는 것이 아니라 방어 모델을 통째로
바꾸는 것이다.
연구가 권고 목록 맨 위에 “샌드박스 iframe으로 격리”를 두면서도
그것을 예외가 아니라 원칙으로 제시하지 않은 것은 아쉬운 지점이다.

### 실제 공격 난이도에 대한 서술이 없다

이 연구가 보여 주는 각 기법은 정교하다.
16진수 조각을 겹쳐 중간 문자를 계산하는 토큰 추출, 글꼴 높이
오라클로 숫자를 읽어 내는 CSP 우회, Firefox의 select 타이머 재설정
특이 동작을 이용한 실시간 키로깅 — 이들은 모두 상당한 CSS 전문
지식과 시행착오를 요구하는 기법이다.

그런데 원문은 각 기법이 요구하는 페이로드 크기나 실행 시간, 실제
공격자가 이를 실전에서 재현하는 데 필요한 사전 조건(대상 서비스의
특정 버전, 특정 브라우저 조합 등)을 체계적으로 정리하지 않는다.
연구의 목적이 개념 증명이라는 점을 감안해도, 방어자가 우선순위를
정하려면 “이론적으로 가능하다”와 “낮은 노력으로 대량 공격이
가능하다” 사이의 구분이 필요한데 이 구분이 흐릿하다.
Medium의 로그인 토큰을 훔치는 공격처럼 구체적 피해가 명확한
사례가 있는가 하면, 미래의 제안 중인 HTML 요소를 이용한 공격처럼
아직 존재하지 않는 표준을 겨냥한 사례도 같은 목록에 나란히
놓여 있어 위험도의 층위가 섞인다.

### 벤더별 대응 상태가 빠져 있다

연구가 여러 벤더의 구체적인 우회를 공개했다면, 각 벤더가 이를
언제 통보받았고 언제 패치했는지, 아직 패치되지 않은 것이 있는지가
독자에게 중요한 정보다.
책임 있는 공개(responsible disclosure) 관행을 따랐다면 이 정보가
자연스럽게 따라와야 하는데, 공개된 요약에는 이 타임라인이
빠져 있다.

이 공백은 독자의 행동을 바꾼다.
지금 이 순간에도 살아 있는 공격인지, 이미 막힌 과거의 사례인지에
따라 웹메일 사용자와 보안 담당자가 취해야 할 조치가 완전히
달라지기 때문이다.

## 인사이트

### CSS는 계속 능력을 얻어 왔지만 위협 모델은 그 속도를 따라가지 못했다

CSS는 원래 문서를 꾸미는 선언형 스타일 언어로 설계됐다.
그런데 지난 십수 년 동안 애니메이션, 변수, 컨테이너 쿼리, `:has()`
같은 관계형 선택자가 차례로 추가되면서 CSS는 조건부 로직과 상태
읽기 능력을 갖춘 준(準) 프로그래밍 언어로 진화했다.
이 연구에 나온 기법들 — 애니메이션으로 값을 측정하는 오라클,
선택자로 존재 여부를 검사하는 로직 — 은 모두 이 진화의 산물이다.

문제는 각 기능이 추가될 때마다 그 기능이 CSS 살균이라는 오래된
방어 모델에 어떤 영향을 주는지가 별도로 검토되지 않았다는 점이다.
새 CSS 기능은 웹 표준 위원회에서 접근성과 개발 편의성을 기준으로
논의되고, 그 기능이 신뢰 경계를 넘나드는 정보 유출 채널이 될
가능성은 보안 연구자가 사후에 발견한다.
이 패턴은 CSS에 국한되지 않는다.
브라우저에 새 API가 추가될 때마다 반복되는 구조이며, 기능
추가와 위협 모델 갱신 사이의 시차가 공격 연구자들의 주된 사냥터가
되어 왔다.

### 신뢰 경계를 격리가 아니라 필터링으로 지키려는 시도는 결국 무너진다

이 연구가 무너뜨린 것은 개별 벤더의 구현이 아니라 “위험한 입력을
걸러내면 신뢰 경계를 지킬 수 있다”는 접근법 자체다.
같은 패턴이 웹 보안의 역사에서 여러 차례 반복됐다.
XSS 방어에서 블랙리스트 기반 필터링이 화이트리스트와 콘텐츠 보안
정책(CSP)에 자리를 내준 것, SQL 인젝션 방어에서 이스케이핑이
매개변수화된 쿼리에 자리를 내준 것이 그 사례다.
공통점은 필터링이 “무엇이 위험한지 안다”는 전제 위에 서 있는데,
공격자는 항상 방어자가 아직 모르는 위험한 조합을 찾아낸다는
것이다.

CSS 살균도 같은 궤적을 걷고 있는 것으로 보인다.
이 연구가 제시한 방어 권고의 첫 항목이 “샌드박스 iframe으로
격리”인 것은 우연이 아니라, 업계가 이미 필터링에서 격리로
넘어가야 한다는 결론에 가까이 와 있다는 신호로 읽을 수 있다.
다만 격리로의 전환은 이메일 클라이언트의 UI 통합성 — 답장 버튼과
같은 화면에 이메일 본문이 매끄럽게 녹아드는 경험 — 을 희생해야
하므로, 벤더들이 이 전환을 미루는 유인이 계속 존재한다.

### AI 에이전트가 웹의 신뢰 모델을 다시 쓰게 만드는 것은 새 취약점이 아니라 낡은 취약점의 재평가다

이 연구가 보여 준 간접 프롬프트 주입 사례들의 진짜 함의는 새로운
공격 기법의 발견이 아니라, 기존 취약점의 심각도 재평가다.
사람 눈에 안 보이는 텍스트를 CSS로 숨기는 기법은 스팸 필터
회피만큼 오래됐고 그동안 크게 위험하다고 여겨지지 않았다.
그 텍스트를 읽는 대상이 필터링 알고리즘이었을 때는 최악의 결과가
스팸 메일 통과 정도였기 때문이다.

이제 그 텍스트를 읽는 대상이 사용자의 계정 권한으로 도구를 호출할
수 있는 AI 비서로 바뀌면서, 같은 기법의 최악의 결과가 계정
탈취나 토큰 유출로 뛰어올랐다.
이것은 웹 보안 커뮤니티가 시급히 재검토해야 할 목록이 있다는
뜻이다.
“사람에게는 안 보이지만 기계는 읽을 수 있는 콘텐츠”를 만드는 모든
오래된 기법 — 흰 배경 흰 글씨, 화면 밖 배치, 매우 작은 글꼴, 이
연구의 의사 요소 은닉 — 이 AI 에이전트가 웹 콘텐츠를 소비하는
주체로 등장한 순간 전부 재평가 대상이 된다.
위협 모델링 관점에서 이는 새 위협을 찾는 문제가 아니라, “낮음”으로
분류해 두었던 옛 발견 항목들의 서랍을 다시 여는 문제에 가깝다.
