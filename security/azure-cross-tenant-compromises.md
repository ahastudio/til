# Azure API Connections: 검증으로 막은 테넌트 경계는 계속 뚫렸다

원문: [Azure's Weakest Link - Five Full Cross-Tenant Compromises](https://www.binarysecurity.no/posts/2026/10/one-root-case)

HN 토론: <https://news.ycombinator.com/item?id=50301854> (337점, 61개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/gttasf/azure_s_weakest_link_five_full_cross> (2점, 0개 댓글)

GN 토론: <https://news.hada.io/topic?id=36296>

## 요약

Haakon Wik Gulbrandsrud는 Azure Logic Apps의 API Connections에서
다른 테넌트의 연결을 사용해 백엔드에 접근할 수 있는
치명적 권한 상승 취약점 다섯 건을 보고했다.
그는 이 취약점들로 총 20만 달러의 포상금을 받았고,
모두 합리적인 기간 안에 수정됐다고 밝혔다.

API Connections는 공유 Azure API Management(APIM)를 통해
백엔드 서비스에 요청을 보낸다.
APIM은 커넥터의 OpenAPI 정의를 확인한 뒤,
연결에 저장된 자격 증명으로 백엔드를 호출한다.
공격자가 요청 경로 또는 호출 URL을 바꿔
다른 연결을 선택하게 하면 그 연결의 권한이 사용된다.

저자는 먼저 ARM의 `DynamicInvoke` 경로 순회로
다른 테넌트의 Key Vault 비밀을 읽었다.
해당 경로를 차단한 뒤에는 별도 함수 `DynamicList`로
피해자의 SQL 데이터베이스에 쓰는 데 성공했다.
이후 Logic App의 `host.api.RuntimeUrl`을 이용해
검증한 연결과 다른 연결로 요청을 보내는 방법을 찾았다.

Microsoft가 URL 검증을 추가한 뒤에도 경로 정규화 전 검사를 우회했고,
그 문제를 고치는 과정에서 기존 검증이 사라져
앞서 막은 공격이 다시 가능해졌다.
저자는 이 사례들을 통해 입력값을 하나씩 막는 대응으로는
최종 호출 대상과 권한의 일치를 보장하기 어렵다고 주장한다.
다만 실제 백엔드에서 가능한 작업은 연결 자격 증명의 권한에 달리며,
저자는 보고한 취약점이 모두 수정됐다고 글을 끝맺는다.

## 분석

### 공유 APIM이 연결 자격 증명을 대신 사용한다

원문에 따르면 Logic App은 공유 APIM 인스턴스에 요청을 보낸다.
APIM은 커넥터 유형의 OpenAPI 정의를 확인해 작업의 유효성을 검사하고,
입력 토큰이나 키를 연결에 설정된 백엔드 자격 증명으로 바꾼다.
그 뒤 APIM은 그 자격 증명을 사용해 백엔드에 요청한다.

따라서 요청자의 권한과 실제로 사용되는 권한은 분리될 수 있다.
요청자는 자기 연결을 호출하는 것처럼 보이더라도,
요청 경로나 URL이 다른 연결을 가리키면
서비스는 그 연결의 자격 증명으로 동작할 수 있다.
저자가 말하는 테넌트 간 침해는 이 불일치에서 비롯된다.

Microsoft 문서의 구성도에는 자격 증명과 메타데이터 저장소,
APIM, 직접 호출되는 REST API, 변환 처리를 맡는
Azure App Service Environment의 커넥터 웹앱이 나타난다.
저자는 여기에 ARM의 `DynamicInvoke`와 `/extensions/proxy/`를 통한
직접 호출 경로를 추가해야 전체 구조가 드러난다고 지적한다.

저자는 연결에 저장된 토큰이나 키를 최소 권한으로 설정할 수 있다고
인정한다.
OAuth 연결은 처음 연결을 만든 사람의 토큰을 사용한다고 설명하며,
권한을 실제로 최소화하는 경우가 드물 것이라는 견해도 밝힌다.
후자는 저자의 추정이고, 공격 뒤 가능한 작업은
각 연결 자격 증명의 실제 권한에 달려 있다.

### 첫 번째 취약점은 DynamicInvoke 경로 순회였다

첫 번째 사례는 저자가 앞선 글에서 이미 공개한 공격의 재설명이다.
공격자는 자신의 API Connection에 대한 ARM `DynamicInvoke` 요청에서
`request.method`를 `get`으로 지정하고,
`request.path`에 인코딩된 상위 경로 이동을 넣었다.
이 경로는 APIM에서 피해자의 Key Vault 연결을 가리키도록 구성됐다.

원문에 실린 응답은 `HTTP/2 200 OK`였고,
`victimsecret`의 값 `dontreadme`를 반환했다.
이는 공격자가 피해자의 자격 증명을 알아낸 결과가 아니다.
자기 연결에서 시작한 요청이 APIM에서 다른 연결로 향했고,
APIM이 그 연결의 자격 증명으로 Key Vault를 조회한 결과다.

신고 몇 주 뒤 Microsoft는 해당 요청을 차단했다.
재시도 때 `InvalidApiConnectionDynamicInvokeRequest` 오류가 반환됐다.
저자는 오류 내용과 추출한 코드를 바탕으로,
수정이 경로 제한에 집중됐다고 판단하고 다른 호출 함수를 조사했다.

### 두 번째 취약점은 같은 경로 제한이 DynamicList에는 없다는 점이었다

저자는 Standard Logic App의 전용 호스트에서 관련 코드를 추출했다.
화면에 나온 검증 코드는 요청 경로를 URL 디코딩한 뒤
`../`가 들어 있는지 검사한다.
저자는 이 코드가 실제 호스트에서 실행되는지,
배포 산출물에만 포함된 것인지는 확인하지 못했다고 밝혔다.

코드에는 `DynamicInvoke` 외에 `DynamicList`, `DynamicTree`,
`DynamicSchema` 함수도 정의돼 있었다.
저자는 이 함수들이 문서화되지는 않았지만
같은 경로에서 호출 가능했다고 설명한다.
다른 함수에도 같은 검증이 있는지 확인했고,
`DynamicList` 요청에서는 경로 매개변수를 각각 지정할 수 있었다.

원문의 `DynamicList` 예시는 처음 두 경로 매개변수에 `..`를 넣고,
SQL 커넥터와 피해 연결, 데이터베이스, 쿼리 작업을 지정한다.
그 결과 피해자의 SQL 데이터베이스에서
`MySecrets` 테이블에 값을 삽입하는 요청이 성립했다.
이는 읽기뿐 아니라 쓰기 작업도 가능했음을 보이는 사례다.

저자는 `DynamicList`만 먼저 신고했다.
Microsoft는 나머지 관련 엔드포인트도 차단했다.
저자는 별도의 완화 조치가 보이지 않았다고 했으며,
엔드포인트가 다시 열리면 취약할 것이라는 말은 자신의 예상으로 제시했다.
`DynamicTree`와 `DynamicSchema` 각각의 공격 성공 사례는
원문에 나오지 않는다.

### 세 번째 취약점은 Logic App의 RuntimeUrl 대체였다

ARM의 동적 호출 경로가 차단되자 저자는 Logic App 실행 흐름을 살폈다.
그는 Consumption Logic App이 Version 1 연결을,
Standard Logic App이 Version 2 연결을 만든다는 차이에 주목했다.
원문에 실린 흐름도에서 Standard는 연결 생성 후
특정 Logic App의 관리 ID에 접근을 허용한다.
Consumption 흐름에는 같은 개별 승인 단계가 없다.

저자는 이 차이에서 Consumption이 Version 1 연결을 사용할 수 있고,
입력 검증이 그 접근을 제한할 것이라는 가설을 세웠다.
피해자 연결을 `host.connection`에 직접 넣는 방식은
런타임의 소유권 검사에 막혔다.
하지만 워크플로 Code 보기에서는 입력을 더 세밀하게 바꿀 수 있었고,
저자는 `host.api.RuntimeUrl` 속성을 찾아냈다.

이 속성을 지정하면 `host.connection`의 소유권을 검사한 뒤에도
실제 호출 URL을 다른 값으로 바꿀 수 있었다.
저자에 따르면 호스트명이 `azure-apihub.net`으로 끝나면
필요한 `Authorization` 헤더도 요청에 포함됐다.
그는 자기 연결 참조는 유지하면서 URL을 피해자의 Key Vault 연결로 바꿨고,
워크플로 실행 결과 피해자의 비밀 항목을 확인했다.

### 네 번째 취약점은 URL 정규화 전에 실행된 검증이었다

Microsoft는 `RuntimeUrl` 경로가 참조 연결의 예상 API 엔드포인트와
일치하는지 검사하도록 수정했다.
오류 메시지는 `host.api`를 생략하거나
연결에 맞는 URL을 사용하라고 안내했다.
저자는 이 수정이 적절해 보인다고 평가했다.

그러나 검증은 경로 정규화보다 먼저 실행됐다.
저자는 자기 연결을 가리키는 경로 뒤에 `/1/../../`와
다른 연결 식별자를 이어 붙였다.
런타임 검증은 정규화 전 경로를 보고 자기 연결이라고 판단했지만,
APIM이 경로를 해석한 뒤에는 피해자의 연결을 가리켰다.
저자는 같은 결과를 다시 얻어 네 번째 취약점으로 신고했다.

이 사례에서 검사 자체는 있었지만 검사한 문자열과
실제로 실행된 경로가 달랐다.
문자열이 승인된 연결처럼 보이는지 확인하는 것만으로는
정규화 이후의 최종 대상을 보장하지 못했다.

### 다섯 번째 취약점은 수정 과정에서 기존 검증이 사라진 회귀였다

네 번째 경로 순회 문제를 수정한 뒤,
원래 `RuntimeUrl` 경로 검증이 더 이상 수행되지 않았다.
그 결과 세 번째 취약점에서 사용한 URL 대체 공격이 다시 가능해졌다.
이는 새로운 우회 기법이 아니라,
이미 막았던 공격이 후속 수정에서 되살아난 회귀였다.

저자는 이 사례까지 포함해 치명적 권한 상승 취약점 다섯 건을 보고했다.
마지막에는 모두 합리적인 기간 안에 수정됐으며,
MSRC와 일부 이견이 있었지만 전체 결과에는 만족한다고 밝혔다.
원문은 수정 완료를 보고하지만,
현재 이 공격 경로들이 열려 있다는 후속 확인을 제시하지 않는다.

### 반복된 우회는 검증 입력보다 최종 권한 대상을 보게 한다

다섯 사례의 세부 입력은 서로 다르다.
첫 두 사례는 ARM 동적 호출의 경로 구성에서 시작했고,
세 번째는 Logic App의 별도 URL 속성을 이용했다.
네 번째는 정규화 순서 차이였으며,
다섯 번째는 기존 검증이 사라진 회귀였다.

이 사례들을 연결하는 공통점은 요청 형식의 유사성이 아니다.
검증된 요청자가 실제로 어느 연결을 실행하게 했는지,
그리고 그 연결의 자격 증명이 어떤 권한으로 사용됐는지다.
따라서 각 입력을 차단하는 검증과 함께
최종 선택된 연결이 승인된 대상인지 확인하는 경계가 필요하다는
설계 결론을 도출할 수 있다.
이는 원문 사례에 근거한 해석이지,
Microsoft 내부 구현에 이미 적용된 사실은 아니다.

## 비평

### 광범위한 영향 주장은 실증된 연결 권한과 구분해 읽어야 한다

저자는 누구나 전 세계 다른 연결을 장악해
연결된 백엔드에 접근할 수 있다고 강하게 요약한다.
본문은 Key Vault 비밀 읽기와 SQL 쓰기를 실증하므로
테넌트 경계를 넘는 권한 사용은 구체적으로 뒷받침된다.

그러나 백엔드에서 가능한 작업은 피해 연결에 저장된
토큰이나 키가 가진 권한에 달려 있다.
읽기 전용 자격 증명이라면 SQL 쓰기 사례와 같은 결과가
자동으로 따라오지는 않는다.
저자도 자격 증명을 최소 권한으로 설정할 수 있다고 명시하므로,
“다른 연결을 사용할 수 있다”와
“모든 백엔드를 완전히 장악한다”는 범위를 나눠야 한다.

글에는 여러 종류의 백엔드가 영향 범위로 언급되지만,
모든 커넥터와 권한 조합을 시험한 결과는 없다.
독자가 자기 환경의 노출을 판단하려면
연결 버전, 인증 방식, 커넥터, 자격 증명 권한별 조건이 더 필요하다.
이 정보가 없다고 실증이 약해지는 것은 아니지만,
보편적인 피해 범위를 계산하기는 어렵다.

### Consumption 권한 설명은 실증 결과와 추론을 나눠야 한다

Version 1과 Version 2의 연결 생성 흐름은
저자가 RuntimeUrl 공격을 찾게 된 배경이다.
흐름도에서 Version 2에는 특정 Logic App의 관리 ID에
접근을 허용하는 단계가 있고, Version 1에는 그 단계가 없다.

저자는 여기서 Consumption이 Version 1 연결 전반에
암묵적으로 접근할 것이라고 추론했다.
그 뒤 RuntimeUrl을 사용한 실제 공격 성공을 보여주지만,
Version 1 연결 전체의 내부 권한 규칙을
독립적으로 입증한 것과는 구분해야 한다.
요금제 전체의 보안 속성을 단정하려면
연결별 검사와 실행 시 권한 부여 방식에 관한 추가 자료가 필요하다.

이 구분을 지키면 글의 기여를 정확히 평가할 수 있다.
저자는 구체적 경로를 통해 다른 연결의 자격 증명을 사용했고,
그 과정에서 수정 우회와 회귀를 찾아냈다.
반면 모든 Consumption 환경과 연결이 같은 조건에 놓인다는 결론은
본문의 시연 범위를 넘어선다.

### 수정 완료만으로 노출 기간과 실제 침해 여부를 알 수 없다

저자는 다섯 취약점이 모두 합리적인 기간 안에 수정됐다고 보고한다.
동시에 수정 과정에서 우회와 회귀가 반복됐다고 설명한다.
두 사실을 함께 보면 개별 수정의 성공뿐 아니라
이전 공격 경로가 계속 차단되는지 확인하는 일이 중요하다.

원문에는 취약점별 신고일, 수정 적용일, 재발견일이 정리돼 있지 않다.
실제 공격자가 이를 악용했는지, 고객이 어떤 로그를 확인해야 하는지도
다루지 않는다.
따라서 이 글만으로 각 고객의 노출 기간이나 침해 여부를 판단할 수 없다.
수정이 완료됐다는 보고는 현재의 위험 상태를 점검할 자료와 별개다.

### 수정이 두 번 실패했다는 요약은 원문 사례와 맞춰 읽어야 한다

이번에는 고치다가 이전 수정을 망가뜨려 다시 취약해졌다고 정리했다.[^outworlder]

다섯 번째는 그 수정 뒤에 기존 검증이 사라진 회귀였다.
첫 두 사례는 사정이 다르다.
수정이 틀렸다기보다 같은 경로 제한이 `DynamicList`에는 적용되지 않았다.
따라서 계속 잘못 고쳤다는 평가는 다섯 건 전체가 아니라
뒤의 두 건에 가장 정확히 들어맞는다.

## 인사이트

### 회귀 검사에는 이전 공격 사례와 권한 조건을 함께 남겨야 한다

다섯 번째 취약점은 새 경로를 고치는 과정에서
기존 `RuntimeUrl` 검증이 사라져 발생했다.
따라서 최신 취약점의 재현 절차만 검사하면
이전에 막은 공격이 되살아났는지 놓칠 수 있다.
세 번째 URL 대체와 네 번째 정규화 우회는
별도의 재현 사례로 유지할 필요가 있다.

이 사례에서 더 일반적인 검사 조건도 도출할 수 있다.
자기 연결을 호출하도록 승인된 요청이
다른 테넌트 연결의 자격 증명으로 실행되지 않아야 한다.
`DynamicInvoke`, `DynamicList`, 워크플로 실행 경로가 달라도
최종 연결과 사용 권한의 관계를 확인해야 한다.
이는 원문을 바탕으로 한 제안이다.

### 관리 경로와 워크플로 경로는 함께 검토해야 한다

처음 두 공격은 ARM에서 시작했고,
세 번째 공격은 Logic App의 워크플로 실행에서 시작했다.
진입점은 달라도 저장된 연결 자격 증명을 쓰는 APIM으로 이어졌다.
따라서 관리 API 하나를 차단하거나 검증했다고 해서
실행 경로의 동일한 권한 문제가 해결됐다고 볼 수 없다.

연결형 자동화 서비스에서는 연결을 만들고 관리하는 기능뿐 아니라,
런타임 입력이 그 연결을 실제로 어떻게 사용하는지도 검토해야 한다.
연결 소유권 검사, URL 검증, 경로 정규화가
실행 대상 확정 전후에 어떤 순서로 적용되는지 확인해야 한다.
최종적으로 승인된 연결의 권한만 쓰이는지를
전체 호출 경로에서 검사하는 것이 실무 기준이 된다.

### 연결 권한 축소는 테넌트 경계 검증과 별도로 필요하다

Hacker News의 magicalhippo는 자국 내 데이터센터와
고객 선호가 Azure 선택 이유였다고 설명했다.[^magicalhippo]
traceroute66은 기존 Microsoft 제품과 공급업체 관리의 편의를
선택 이유로 들었다.[^traceroute66]
이 댓글들은 취약점의 원인을 입증하지는 않지만,
고객이 보안 문제를 발견한 뒤 공급자를 곧바로 바꾸기 어려운
운영 배경을 보여준다.

공급자를 유지하는 상황에서도 연결 자격 증명의 권한과
그 자격 증명을 사용하는 워크플로를 점검할 수 있다.
권한을 줄이면 연결 악용 뒤 가능한 작업의 범위를 낮출 수 있다.
다만 고객의 최소 권한 설정은 공급자가 테넌트 경계를 지켜야 할
책임을 대신하지 않는다.
두 통제는 각기 다른 실패를 막으므로 함께 필요하다.

### 별개 보고: 관리자 동의 콜백의 위조 가능성

unddoch는 Microsoft 보안 담당자가 스레드를 본다면
`login.microsoftonline.com/XXX/v2.0/adminconsent`를 살펴 달라고 썼다.[^unddoch]
관리자 동의 절차의 끝에서 사용자를 되돌려 보내는 콜백이,
다른 고객의 Azure 테넌트 ID를 아는 공격자에게 위조될 수 있다는 주장이다.
문서가 `tenant` 매개변수의 값으로 사용자를 인증하거나 인가하지
말라고 경고하지만,
실제로 인증할 방법이 있어야 그 경고가 도움이 된다는 것이 그의 요지다.
이는 원문의 다섯 건과 다른 문제이며, 원문은 이를 다루지 않는다.

Microsoft 보안 담당자라고 밝힌 wibartle는 `redirect_uri`가 앱 등록과 대조해
검사된다고 답했다.[^wibartle]
임의의 링크로 악성 사이트에 보내는 문제는 업계 전체가 잘 풀지 못한 OAuth의
일반 문제이고,
Microsoft도 블로그에서 다뤘다고 했다.
관리자 동의를 보여 주는 대부분의 포털은 그 요청 직전이나 직후에
OpenID Connect로 사용자를 인증한다는 설명도 덧붙였다.
unddoch의 요지는 이해하지 못했으니 MSRC 사례나 이메일로 알려 달라고 요청했다.

unddoch는 이어서 서비스 제공자가 이를 어떻게 막아야 하는지
물었다.[^unddoch-followup]
고객 A가 서비스에 자신의 Azure 환경을 연결한 뒤,
공격자가 같은 서비스에 다른 테넌트를 만들어 연동 절차를 거치고,
A의 테넌트에 관리자 동의가 설정됐다는 요청을 콜백에 보내는 시나리오다.
흐름을 시작한 사용자가 같은 테넌트에 속하는지 검증해도 권한 없는
사용자일 수 있고,
한 고객이 여러 테넌트를 둘 수도 있다는 난점도 적었다.
확인 시점에 이 질문에 달린 답글은 없었다.
따라서 스레드에서 확인되는 것은 답이 아니라 열린 질문이다.
콜백이 가리키는 테넌트가 아니라, 서비스가 시작한 흐름과
로그인한 사용자의 권한에 요청을 묶었는지가 점검 항목이 될 수 있다.
이는 이 문서의 해석이다.
