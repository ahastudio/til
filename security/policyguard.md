# PolicyGuard: 프롬프트가 모델에 닿기 전에 자연어 정책으로 막는다

원문: [Amazon Bedrock 기반 PolicyGuard: 코딩 어시스턴트를 위한 Pre-Model Semantic DLP 프레임워크 | AWS 기술 블로그](https://aws.amazon.com/ko/blogs/tech/amazon-bedrock-based-sematic-dlp/)

## 요약

Kyutae Park이 2026년 8월 24일 AWS 기술 블로그의 Amazon Bedrock 분류에 올린 글이다.
글 끝의 저자 소개에는 OpenAI Partner AI Deployment Engineer 김정원과
OpenAI 솔루션즈 아키텍트 심대열도 함께 실려 있다.
문제 정의는 코딩 어시스턴트가 만든 새 유출 경로다.
GitHub Copilot과 OpenAI Codex와 Claude Code 도입이 빨라지면서
개발자가 프롬프트에 넣는 API 키와 데이터베이스 비밀번호와
고객 개인정보와 사내 미공개 전략이 외부 LLM 서비스로 전송된다.
기존 DLP는 이메일과 업로드 같은 정형 데이터 흐름을 겨냥했으므로
비정형 프롬프트를 다루지 못하며,
규칙 기반 도구는 맥락에 의존하는 민감 정보를 처리하지 못한다는 것이 한계로 지목된다.

PolicyGuard의 핵심은 DLP 로직 전체를 자연어 정책 파일에 담는 방식이다.
`policy.txt`는 약 1,200 토큰, 106줄이며 시스템 프롬프트로 주입된다.
구조는 네 부분이다.
INSTRUCTIONS는 분류기의 역할과 출력 형식과 프롬프트 주입 방어 지시를 담고,
POLICY는 여덟 개의 민감 범주를 정의한다.
AUTH_SECRET, FINANCIAL_IDENTIFIER, GOVERNMENT_IDENTIFIER, PERSONAL_DATA,
CUSTOMER_CONFIDENTIAL, PROPRIETARY_CODE, PROMPT_INJECTION, OTHER_SENSITIVE다.
DECISIONS는 ALLOW와 BLOCK과 REVIEW의 기준을 정하고,
EXAMPLES는 few-shot 예시 쌍을 제공한다.
동작 흐름은 개발자가 프롬프트를 제출하면
OpenAI Codex의 UserPromptSubmit 훅이 분류기를 호출하고,
분류기가 `policy.txt`를 시스템 프롬프트로 받아 입력을 판정해
`decision`과 `categories`를 담은 JSON을 반환하는 것이다.
ALLOW면 모델로 넘어가고 BLOCK이나 REVIEW면 거부되며,
오류와 타임아웃에서도 프롬프트가 나가지 않는 fail-closed 설계다.

구현은 Amazon Bedrock 위에서 gpt-oss-safeguard-20b를 분류기로 쓴다.
Bedrock이 입력 프롬프트를 모델 학습에 쓰지 않고 지정 리전 안에서 처리한다는 점을 근거로 든다.
대안으로 SageMaker AI 실시간 엔드포인트 배포를 제시하며,
프롬프트가 기록되지 않도록 Data Capture를 기본 비활성화한다.
이식성 실험에는 Ministral 8B와 Claude Haiku 4.5와 Llama 3.1 8B가 함께 쓰였다.

평가 데이터는 다국어 합성 프롬프트 2,000건이다.
자격증명 200건, PII 200건, 사내 기밀 200건, 프롬프트 주입 200건,
일반 코딩 질문 600건, 하드 네거티브 200건, 다국어 400건으로 구성된다.
예시로 자격증명은 `api_key = 'sk-proj-abc123...'`,
PII는 주민등록번호 형식, 사내 기밀은 미공개 분기 매출,
하드 네거티브는 AWS 키 로테이션 방법을 묻는 질문이다.
언어 분포는 영어 60%, 한국어 34%, 일본어 3%, 중국어 3%다.
평가 프로토콜은 봉인 방식이다.
개발 세트 421건, 검증 세트 435건, 은닉 홀드아웃 217건,
그리고 정책을 확정한 뒤 한 번만 평가하는 프로즌 테스트 927건이다.

결과는 세 갈래로 제시된다.
프로즌 테스트 927건에서 유효 차단율이 96.5%, 오탐률이 3.0%,
정확도가 96.8%, 지연 P50이 669밀리초다.
은닉 홀드아웃에서는 정확도 100%였다.
트랙 A는 형식 비교다.
자연어 정책이 정확도 96.8%인 데 비해
같은 내용의 JSON 루브릭은 90.7%, Presidio는 79.2%,
제로샷은 64.6%, 길이 통제 조건은 61.4%였다.
자연어와 JSON의 차이에 대한 McNemar 검정 결과가 χ²=31.58, p<0.001이며,
길이 통제와의 비교에서 Cohen's h가 0.915로 큰 효과 크기라고 밝힌다.
트랙 B는 동일한 `policy.txt`를 여러 모델에 적용한 이식성 실험이다.
gpt-oss-safeguard-20b가 차단율 96.5%에 오탐 3.0%, 지연 669밀리초,
Ministral 8B가 89.7%에 6.3%, 350밀리초,
Claude Haiku 4.5가 86.4%에 1.8%, 864밀리초,
Llama 3.1 8B가 64.1%에 14.7%, 372밀리초였다.
네 모델 중 세 개가 86% 이상의 차단율을 보였다.
트랙 C는 절제 실험이다.
완전한 정책이 96.5%일 때
few-shot 예시를 빼면 67.1%로 29.4포인트,
범주 정의를 빼면 63.0%로 33.5포인트,
주입 방어를 빼면 49.7%로 46.8포인트 떨어졌고,
한 줄만 남긴 최소 조건은 21.5%로 75.0포인트 하락했다.
주입 방어 지시문의 기여가 가장 컸다.

반복 개선 과정도 표로 제시된다.
초기 정책이 약 83%였고,
한국어 제한 마커를 추가한 1차 개선에서 5분 만에 96%,
테스트 목적이라는 프레이밍에 대한 방어를 추가한 2차 개선에서 3분 만에 검증 세트 100%가 됐다.
그 뒤 정책을 수정하지 않은 상태로 프로즌 테스트에서 96.8%였다.
총 15분, 열 줄 추가, 코드 변경 없음으로 요약된다.
규칙 기반과의 비교에서는 Microsoft Presidio가 차단율 62.2%에 오탐 9.7%, 지연 4밀리초이므로
차단율은 34.3포인트 높고 오탐은 6.7포인트 낮으며 지연은 665밀리초 느리다.

운영 권고는 Bedrock을 기본으로, SageMaker 자체 호스팅을 폴백으로 두고
오류와 타임아웃에서 fail-closed로 동작하게 하는 구성이다.
비용은 프롬프트당 약 0.01달러로,
개발자 1,000명이 하루 50개 프롬프트를 쓰면 하루 500달러,
영업일 21일 기준 월 약 10,500달러다.
좌석당 월 20~50달러인 엔터프라이즈 DLP와 비교해
고정 비용 대신 사용량 기반 유연성을 갖는다고 설명한다.
Amazon Bedrock Guardrails와의 차이도 표로 정리된다.
Guardrails는 API 호출 이후에 적용되어 프롬프트가 서비스에 도달하고
체크박스와 예시 다섯 개로 정책을 맞추는 2차 방어선인 반면,
PolicyGuard는 호출 이전에 적용되어 차단 시 프롬프트가 도달하지 않고
자연어로 정책을 무제한 맞출 수 있는 1차 방어선이라는 것이다.

한계는 네 가지로 명시된다.
합성 데이터 기반 평가여서 실제 기업 환경의 프롬프트 분포와 차이가 있을 수 있고,
단일 턴만 검사하므로 대화 맥락의 간접 참조를 처리할 수 없고,
지연이 규칙 기반의 4밀리초 대비 669밀리초여서 UX에 영향을 줄 수 있고,
입력만 검사하므로 출력 DLP는 포함되지 않는다.
향후 방향으로는 Presidio를 1차 필터로 두고 PolicyGuard를 2차 의미 분류로 쓰는 하이브리드,
출력 DLP, 반복 프롬프트에 대한 캐시 계층,
정책 내용을 아는 공격자에 대한 견고성 강화,
비식별화된 실제 개발자 프롬프트 검증을 든다.
부록 B의 오류 분석은 프로즌 테스트 30건의 오류를 나눈다.
미탐 13건은 명시적 마커 없는 한국어 제한 표현 4건,
코드 조각 안의 부분 자격증명 3건, 인코딩된 주입 시도 2건,
다중 엔티티 조합 2건, 복합 맥락 PII 2건이다.
오탐 17건은 자격증명 관련 질문 오인 7건, 현실적 합성값 오인 5건,
한국어 동음이의어 3건, 과도한 맥락 해석 2건이다.
저자는 대부분의 오류가 `policy.txt`의 추가 규칙이나 예시로 보완 가능한 수준이며
근본적 아키텍처 한계가 아니라고 정리한다.
참고 문헌으로 Llama Guard, WildGuard, ShieldGemma, Presidio,
Instruction Hierarchy, Ignore Previous Prompt 논문이 인용된다.

## 분석

### 정책을 코드가 아니라 프롬프트에 둔 결정이 이 프레임워크의 전부다

기술적으로 새로운 것을 찾으면 별로 없다.
LLM을 분류기로 쓰는 방식은 Llama Guard와 WildGuard와 ShieldGemma가 이미 했고,
이 글도 그 세 편을 참고 문헌으로 인용한다.
프롬프트 훅에서 무언가를 가로채는 것도 새 발명이 아니다.
새로운 것은 정책을 어디에 두었는가다.

기존 DLP의 실제 병목은 탐지 기술이 아니라 정책 저작이었다.
무엇이 민감한지 아는 사람은 법무와 보안과 도메인 담당자이고,
정규식을 쓰는 사람은 엔지니어다.
그래서 정책이 만들어지는 경로가 항상 통역을 거쳤고,
통역 과정에서 맥락이 소실됐다.
“미공개 분기 매출”은 정규식으로 표현할 수 없고,
그것을 표현할 수 없다는 사실이 규칙 기반 DLP가
맥락 의존 정보를 다루지 못하는 근본 이유다.

정책을 자연어로 두면 편집 능력이 판단하는 사람에게 돌아간다.
글이 자랑하는 15분과 열 줄과 코드 변경 없음이 그 이동의 측정값이다.
한국어 제한 마커를 추가하는 일과
테스트 목적이라는 프레이밍을 방어하는 일은
정규식을 쓰는 작업이 아니라 문장을 쓰는 작업이며,
그 문장을 쓸 사람은 그 조직의 무엇이 민감한지 아는 사람이다.
트랙 C의 절제 실험이 이 관점을 뒷받침한다.
범주 정의를 빼면 33.5포인트가 떨어진다는 것은
정확도의 3분의 1이 모델이 아니라 정책 문장에서 나온다는 뜻이다.

### 삽입 지점이 훅이라는 사실이 Guardrails와의 차이를 만든다

Guardrails 비교 표에서 실제로 갈리는 항목은 하나다.
적용 시점이다.
API 호출 이후인지 이전인지가
프롬프트가 서비스에 도달하는지를 결정하고,
도달 여부가 로그에 남는지를 결정한다.
분류기의 품질이 아니라 위치가 이 프레임워크의 가치 주장 전부를 지탱한다.

이 위치가 가능해진 조건이 최근에 생겼다는 점이 중요하다.
코딩 어시스턴트가 프롬프트 제출 훅을 노출하기 전에는
클라이언트와 모델 사이에 코드를 끼워 넣을 자리가 없었다.
네트워크 프록시로 하면 TLS를 끊어야 하고,
IDE 플러그인으로 하면 도구마다 따로 만들어야 한다.
`UserPromptSubmit` 같은 훅이 표준화되면서
한 지점에서 전송 이전에 개입할 수 있게 됐다.

이 구조가 하네스 논의와 같은 결론을 가리킨다.
통제 지점은 모델이 아니라 모델을 감싼 실행 환경에 있다.
모델 제공자가 제공하는 안전장치는 정의상 모델에 도달한 뒤에 작동하므로
전송 자체를 막을 수 없다.
전송을 막을 수 있는 곳은 하네스 안이며,
그 하네스가 훅을 노출하는지가 조직이 이 통제를 구현할 수 있는지를 정한다.
같은 이유로 이 프레임워크는 훅을 노출하지 않는 도구에는 적용되지 않으며,
글이 도입부에서 Copilot과 Codex와 Claude Code를 함께 나열했지만
구현은 Codex 훅 하나에만 붙어 있다.

### 봉인된 평가 프로토콜이 이 글을 벤더 블로그에서 실험 보고서로 옮긴다

벤더 블로그의 성능 수치는 대체로 검증할 수 없는 형태로 제시된다.
데이터를 어떻게 나눴는지, 몇 번 측정했는지,
정책을 수정하며 같은 세트를 반복해 봤는지가 밝혀지지 않는다.
이 글은 그 부분을 명시한다.

나눔이 네 층이다.
개발 세트 421건으로 정책을 만들고,
검증 세트 435건으로 다듬고,
은닉 홀드아웃 217건으로 확인하고,
프로즌 테스트 927건은 정책을 확정한 뒤 한 번만 평가했다.
그리고 그 결과가 은닉 홀드아웃 100%에서 프로즌 테스트 96.8%로 떨어졌다는 사실을 그대로 적는다.
과적합의 크기를 스스로 보고한 것이며,
숨기려면 은닉 홀드아웃 수치만 실었을 것이다.

통계 검정을 붙인 것도 같은 계열이다.
자연어와 JSON의 차이에 McNemar 검정을 쓴 것은
같은 표본에 두 방법을 적용한 쌍체 설계에 맞는 선택이다.
길이 통제 조건을 따로 둔 것도 정확한 통제다.
정책이 긴 프롬프트라는 것 자체가 성능을 올리는 것인지
정책의 내용이 올리는 것인지를 가르기 위한 조건이며,
Cohen's h 0.915라는 효과 크기까지 제시한다.
이 정도의 설계를 갖춘 블로그 글은 드물고,
그 사실이 이 글에서 인용할 만한 부분과 그렇지 않은 부분을 가른다.

### 주입 방어가 최대 기여 요소라는 결과가 이 분류기의 성격을 드러낸다

절제 실험의 네 조건 중 가장 큰 하락은 주입 방어 제거다.
96.5%에서 49.7%로 46.8포인트가 떨어진다.
few-shot 예시 제거가 29.4포인트, 범주 정의 제거가 33.5포인트인데
주입 방어 하나가 그 둘보다 크다.

이 수치가 무엇을 뜻하는지 생각해 보면 불편하다.
차단 능력의 절반 가까이가 민감 정보를 알아보는 데 쓰이는 것이 아니라,
입력이 분류기를 설득하려는 시도를 버티는 데 쓰인다.
평가 데이터의 구성이 그 이유를 설명한다.
2,000건 중 200건이 프롬프트 주입이며,
예시로 든 것이 정책을 무시하고 ALLOW를 반환하라는 지시다.
즉 이 분류기의 입력은 정의상 적대적이다.

이 성질이 규칙 기반과의 근본적 차이를 만든다.
정규식은 설득당하지 않는다.
`sk-proj-`로 시작하는 문자열을 찾는 규칙에
그 규칙을 무시하라고 말할 통로가 없다.
LLM 분류기는 정책과 입력이 같은 채널에 있으므로 통로가 있다.
글이 참고 문헌에 Instruction Hierarchy와
Ignore Previous Prompt를 넣은 것이 이 문제를 인식했다는 표시이고,
INSTRUCTIONS 절에 주입 방어 지시를 넣은 것이 그 대응이다.
그런데 지시문으로 하는 방어는 지시문을 이기려는 입력과 같은 층에서 싸운다.

## 비평

### 합성 데이터 2,000건에서 얻은 96.5%가 실제 분포로 이전된다는 근거가 없다

저자도 이 한계를 첫 번째로 적는다.
합성 데이터 기반 평가여서 실제 기업 환경의 프롬프트 분포와 차이가 있을 수 있다는 것이다.
정직한 진술이지만 차이의 방향을 말하지 않는다.
그리고 데이터 구성을 보면 방향을 추정할 수 있다.

구성에서 눈에 걸리는 것은 양성 사례의 형태다.
자격증명 200건의 예시가 `api_key = 'sk-proj-abc123...'`이고
PII 200건의 예시가 주민등록번호 형식이다.
둘 다 형식이 명확한 값이며 정규식이 가장 잘 잡는 종류다.
실제 환경에서 어려운 사례는 형식이 없는 것들이다.
로그 조각에 섞인 내부 호스트명,
자연어로 서술된 고객 이름과 계약 조건,
코드 리뷰 요청에 포함된 사업 로직이 그렇다.
이 글이 다루려던 것이 정확히 그 맥락 의존 정보였는데,
평가 세트의 양성 사례는 형식 기반 쪽으로 기울어 있다.

같은 구성이 Presidio 비교의 신뢰도도 깎는다.
형식이 명확한 자격증명과 주민등록번호가 400건이나 있는 세트에서
Presidio의 차단율이 62.2%에 머문 것은 낮다.
이 낮음의 원인이 Presidio의 한계인지 기본 설정의 한계인지가 밝혀지지 않는다.
Presidio는 인식기를 추가하고 임계값을 조정하는 도구이므로,
공정한 비교라면 같은 데이터로 조율한 기준선을 세워야 한다.
기본 설정 대비 34.3포인트 우위는 조율되지 않은 상대에 대한 우위이며,
그 사실이 표에 표시되지 않는다.
음성 사례가 800건으로 40%를 차지하는 구성도
오탐률 비교의 해석을 어렵게 만든다.

### 669밀리초를 UX 영향 가능으로 처리했지만 실제로는 설계 제약이다

지연은 한계 목록의 세 번째 항목으로 한 줄 언급된다.
P50 669밀리초로 규칙 기반의 4밀리초보다 느리고 UX에 영향을 줄 수 있다는 것이다.
이 서술이 문제의 크기를 축소한다.

첫째, P50만 제시되고 꼬리가 없다.
Bedrock 호출의 P95와 P99가 얼마인지가 사용자 경험을 결정하는데
그 수치가 없다.
분류기가 20B 모델이므로 부하와 리전에 따라 꼬리가 길어질 수 있고,
fail-closed 설계이므로 타임아웃은 곧 작업 차단이다.
즉 지연이 나빠지는 상황과 개발자가 막히는 상황이 같은 사건이다.

둘째, 이 게이트는 모든 프롬프트에 걸린다.
글의 비용 시나리오가 개발자당 하루 50개 프롬프트를 가정하므로,
P50만 잡아도 하루 33초의 순수 대기가 개발자마다 생긴다.
코딩 어시스턴트와의 상호작용은 대화형이고 짧은 왕복이 반복되므로
매 왕복에 0.7초가 붙는 것은 체감이 크다.
글이 제시한 완화책인 캐시 계층은 향후 과제로 미뤄져 있고,
반복 프롬프트가 아닌 첫 요청에는 적용되지 않는다.

셋째, 폴백 경로의 지연이 제시되지 않는다.
운영 권고는 Bedrock을 기본으로 SageMaker 자체 호스팅을 폴백으로 두는 구성인데,
폴백으로 전환됐을 때의 지연과 정확도가 표에 없다.
장애 시에도 fail-closed로 동작한다는 서술은 안전 측면에서는 옳지만,
그 상태가 곧 전사 개발자의 작업 중단을 뜻한다는 점이 다뤄지지 않는다.
보안 통제를 도입할 때 가장 먼저 요구되는 수치가
정상 시 성능이 아니라 통제 실패 시 영향 범위인데 그것이 빠져 있다.

### 비용 비교가 성립하지 않는 대상과 이루어졌다

비용 계산 자체는 명료하다.
프롬프트당 0.01달러, 개발자 1,000명이 하루 50개면 하루 500달러, 월 약 10,500달러다.
문제는 그다음 문장이다.
좌석당 월 20~50달러인 엔터프라이즈 DLP와 비교해
고정 비용 대신 사용량 기반 유연성을 갖는다고 적는다.

이 비교는 두 가지 이유로 성립하지 않는다.
첫째, 범위가 다르다.
엔터프라이즈 DLP는 이메일과 엔드포인트와 클라우드 스토리지와 웹 업로드를 함께 다룬다.
PolicyGuard는 코딩 어시스턴트 프롬프트 하나의 채널을 다룬다.
전자를 후자로 대체할 수 없으므로 비용은 대체가 아니라 추가다.
1,000석 기준으로 엔터프라이즈 DLP가 월 2만에서 5만 달러라면,
PolicyGuard 도입은 그 위에 월 1만 달러를 더하는 결정이다.
둘째, 단가 자체가 싸지 않다.
개발자당 월 10.5달러를 채널 하나에 쓰는 것이며,
그 채널을 커버하는 비용이 전체 DLP 예산의 20~50%에 해당한다.

토큰 계산이 없다는 점도 아쉽다.
`policy.txt`가 약 1,200 토큰이고 매 프롬프트에 시스템 프롬프트로 주입되므로,
비용의 대부분이 정책 자체의 입력 토큰이다.
그렇다면 프롬프트 캐싱을 쓸 때 단가가 어떻게 바뀌는지가
비용 논의에서 가장 실용적인 항목이 된다.
정책이 정적이고 사용자 입력이 동적이므로
정적 부분을 앞에 두는 배치만으로 캐시 적중이 가능한 구조이며,
그 계산이 있으면 월 10,500달러가 크게 달라진다.
캐시를 향후 과제의 지연 개선 항목으로만 언급하고
비용 항목으로 다루지 않은 것이 이 절의 공백이다.

### 적응적 공격을 향후 과제로 미룬 것이 이 설계의 중심 위협을 비껴간다

오류 분석의 결론이 이렇다.
대부분의 오류가 `policy.txt`의 추가 규칙이나 예시로 보완 가능한 수준이며
근본적 아키텍처 한계가 아니라는 것이다.
30건의 오류를 놓고 보면 이 판단이 타당해 보인다.
한국어 제한 마커와 동음이의어와 합성값 오인은 예시를 더하면 줄어든다.

그런데 같은 오류 목록에 인코딩된 주입 시도 2건이 있고,
절제 실험은 주입 방어가 성능의 최대 기여 요소라고 말한다.
두 사실을 합치면 결론이 달라진다.
이 시스템의 성능 절반을 지탱하는 구성요소가
공격자가 직접 겨냥할 수 있는 지시문이며,
그 지시문에 대한 우회가 이미 소수 관측됐다.
그리고 향후 과제 목록의 네 번째 항목이
정책 내용을 아는 공격자에 대한 견고성 강화다.

보안 통제에서 이것은 향후 과제가 아니라 위협 모델의 중심이다.
DLP를 우회하려는 동기를 가진 주체가 누구인지 생각하면 분명해진다.
악의적 외부인이 아니라 막히는 개발자다.
급한 디버깅에 프롬프트가 차단되면 우회를 시도할 유인이 생기고,
그 사람은 조직 내부에 있으므로 정책을 볼 수 있다.
정책이 코드가 아니라 저장소의 텍스트 파일이라는 사실이
편집 접근성이라는 장점과 열람 가능성이라는 취약점을 동시에 만든다.

이 문제가 구조적인 이유는 채널이 하나이기 때문이다.
정책도 텍스트이고 공격도 텍스트이며 같은 컨텍스트에 들어간다.
정규식 엔진에는 이 성질이 없다.
같은 계열의 역사적 선례가 웹 애플리케이션 방화벽이다.
패턴으로 공격을 걸러내는 방어는 우회 기법과 군비 경쟁을 했고,
지속된 해법은 구조적 분리였다.
바인딩 파라미터가 데이터와 코드를 다른 경로로 보낸 것이 그 분리다.
이 글이 하이브리드 구성을 향후 과제로 든 것이 그 방향의 첫걸음인데,
Presidio를 1차 필터로 두는 구성은 형식 기반 탐지를 앞에 두는 것이지
주입 방어를 구조적으로 분리하는 것은 아니다.

## 인사이트

### 정책이 프롬프트가 되면 정책 변경이 배포가 아니라 편집이 되고 그것이 감사 문제를 만든다

이 프레임워크가 파는 이점은 15분과 열 줄과 코드 변경 없음이다.
같은 성질이 반대 방향에서 위험이 된다.
보안 통제의 판정 기준 전체가 텍스트 파일 하나에 있고,
그 파일을 편집할 수 있는 사람이 통제를 바꿀 수 있다.

절제 실험이 그 위험의 크기를 정확히 알려 준다.
한 줄만 남긴 최소 조건에서 차단율이 21.5%다.
주입 방어 문장들을 지우면 49.7%다.
즉 실수로든 의도로든 `policy.txt`의 일부 절을 삭제하는 편집 하나가
차단율을 절반 이하로 떨어뜨린다.
그리고 그 변화는 조용하다.
분류기는 여전히 동작하고 JSON을 반환하며 ALLOW와 BLOCK을 낸다.
차단율이 떨어졌다는 사실은 어디에도 오류로 나타나지 않는다.

여기서 나오는 실행 항목이 이 글에 이미 만들어져 있는데 제안되지 않았다.
프로즌 테스트 927건을 병합 게이트로 쓰는 것이다.
`policy.txt`가 변경되는 모든 커밋에서 그 세트를 돌려
차단율과 오탐률이 기준선 아래로 내려가면 병합을 막는다.
정책이 프롬프트라서 편집이 쉬워졌다면,
그 편집을 검증하는 회귀 테스트도 같은 정도로 쉬워야 한다.
데이터셋이 이미 있고 판정이 결정적이므로 구현 비용이 거의 없다.

이 조치가 앞선 비평 항목들과도 연결된다.
정책 편집으로 오류를 보완할 수 있다는 저자의 결론이 옳다면,
그 보완이 다른 항목을 망가뜨리지 않았는지 확인하는 절차가 필요하다.
한국어 제한 마커를 잡으려고 규칙을 추가하면
한국어 동음이의어 오탐이 늘어날 수 있다.
15분 만에 정책을 개선했다는 서술이 매력적인 만큼
15분 만에 정책을 악화시킬 수도 있다는 점이 함께 성립한다.
회귀 게이트가 없으면 이 프레임워크의 최대 장점이 최대 위험이 된다.

### 프롬프트 훅이 새 통제 지점이 됐고 그 지점의 소유권이 아직 정해지지 않았다

역사적으로 새 통신 채널이 열릴 때마다 그 목에 게이트웨이가 자랐다.
이메일에는 메일 게이트웨이가, 웹에는 프록시가,
엔드포인트에는 에이전트가, 브라우저에는 확장이 생겼다.
매번 기술적 난점보다 소유권 싸움이 더 오래 걸렸다.
누가 그 게이트웨이를 설정하고, 사용자가 그것을 끌 수 있는지가 쟁점이었다.

코딩 어시스턴트의 프롬프트 제출 훅이 지금 그 목이다.
그리고 지금 그 훅의 설정은 개발자 로컬의 설정 파일에 있다.
이 사실이 이 프레임워크의 연구 결과와 실제 통제 사이의 간격을 만든다.
차단율 96.5%는 훅이 켜져 있을 때의 수치이고,
훅이 켜져 있는지는 제약을 받는 당사자가 결정한다.
급한 작업에서 막힌 개발자가 훅을 잠시 비활성화하면
그 순간 차단율은 0%다.

이차 효과는 도입 방식의 요구사항이다.
이 통제가 실제로 통제가 되려면 훅 설정이 관리되어야 한다.
관리형 설정으로 배포하고, 로컬에서 덮어쓸 수 없게 하고,
비활성화된 상태를 탐지해 보고해야 한다.
글은 훅에 붙이는 방법을 설명하고 그것을 관리하는 방법은 설명하지 않는다.
그리고 이 부분이 조직마다 다르며 도구마다 다르다.
Codex와 Claude Code와 Copilot의 설정 관리 방식이 서로 다르므로,
도입부에서 세 도구를 나열한 것과 구현이 한 도구의 훅에 붙은 것 사이의 거리가
실제로는 이 관리 문제만큼 크다.

여기서 나오는 판단 기준이 하나 생긴다.
프롬프트 단계 DLP를 검토하는 조직은
분류기의 정확도보다 훅의 관리 가능성을 먼저 확인해야 한다.
정확도 96.5%짜리 분류기를 끌 수 있는 훅에 붙이는 것과
정확도 86%짜리 분류기를 끌 수 없는 지점에 붙이는 것 중
후자가 조직 전체의 실효 차단율을 더 높인다.
Claude Haiku 4.5가 86.4%로 나온 트랙 B의 수치가
이 계산에서 실용적 의미를 갖는 이유다.

### 이 글이 실제로 증명한 것은 DLP가 아니라 LLM 분류기 저작 방법론이다

세 트랙의 결과를 DLP 제품 관점에서 읽으면 하나의 사례 연구다.
방법론 관점에서 읽으면 훨씬 넓게 쓸 수 있는 결과가 나온다.
트랙 B는 같은 정책 파일이 네 모델에서 얼마나 이전되는지를 측정했다.
트랙 C는 정책의 어느 절이 성능을 지탱하는지를 절제로 측정했다.
반복 개선 표는 정책 편집의 시간당 정확도 증가를 기록했다.
세 개를 합치면 LLM 기반 분류기를 만들 때의 작업 절차가 된다.

이 절차의 형태가 재사용 가능하다.
분류 기준을 자연어로 쓰고,
개발과 검증과 은닉과 프로즌으로 데이터를 네 층으로 나누고,
프로즌은 정책을 확정한 뒤 한 번만 쓰고,
정책의 각 절을 하나씩 빼면서 기여도를 측정하고,
같은 정책을 여러 모델에 돌려 이식성을 확인한다.
DLP가 아니라 콘텐츠 분류나 티켓 라우팅이나
코드 리뷰 판정에도 그대로 적용되는 절차다.
그리고 절제 실험이 특히 값어치가 크다.
프롬프트를 다듬는 작업은 보통 감으로 이루어지는데,
절 단위로 빼면서 측정하면 어느 문장이 일하는지 숫자로 나온다.

이 관점에서 보면 이 글에서 가장 인용할 만한 수치는 96.5%가 아니다.
주입 방어를 빼면 46.8포인트가 떨어지고
범주 정의를 빼면 33.5포인트가 떨어진다는 두 값이다.
프롬프트의 어느 부분에 투자해야 하는지를 알려 주는 유일한 정보이며,
같은 절제를 자기 프롬프트에 해 보면 자기 답을 얻는다.
1,200 토큰짜리 정책에서 실제로 일하는 문장이 어느 것인지 모르는 팀이 대부분이고,
그 무지가 컨텍스트 예산을 낭비하게 만든다.

동시에 이 방법론의 공개에는 긴장이 있다.
부록 A가 `policy.txt`의 구조를 공개하고
절제 실험이 어느 절을 지우면 무력화되는지 알려 준다.
연구의 재현성을 위해서는 둘 다 필요하고,
적응적 공격을 막기 위해서는 둘 다 위험하다.
같은 글이 향후 과제로 정책 내용을 아는 공격자에 대한 견고성을 들면서
정책 구조와 취약한 절을 함께 공개하는 셈이다.
보안 도구의 논문에서 반복되는 절충이고 정답이 없지만,
공개된 정책을 그대로 쓰는 조직은 공개된 우회법도 함께 받는다는 점은 짚어 둘 만하다.
자기 조직의 문장으로 다시 쓰는 것이 정확도를 위해서도,
공개된 우회를 피하기 위해서도 필요하다.

### 입력만 막는 게이트는 절반의 통제이고 나머지 절반이 더 어렵다

한계 목록의 네 번째 항목이 입력만 검사한다는 것이다.
출력 DLP는 향후 과제로 미뤄져 있고 한 줄로 처리된다.
그런데 코딩 어시스턴트의 유출 경로를 나열해 보면
입력만 막아서 닫히지 않는 경로가 여럿 남는다.

가장 직접적인 것은 에이전트가 스스로 읽는 파일이다.
개발자가 프롬프트에 비밀을 쓰지 않아도,
에이전트가 저장소를 읽어 `.env` 파일이나 설정 파일을 컨텍스트에 올린다.
그 내용은 사용자 프롬프트가 아니므로 `UserPromptSubmit` 훅을 지나지 않는다.
도구 호출의 결과가 모델에 들어가는 경로도 같다.
데이터베이스를 조회하는 도구가 고객 레코드를 반환하면
그 레코드가 다음 요청의 컨텍스트에 포함된다.
프롬프트 단계 게이트는 이 경로를 보지 못한다.

이 관찰이 통제 지점의 위치를 다시 묻게 만든다.
사용자 프롬프트는 사람이 의식적으로 쓰는 텍스트이므로
교육과 경고로도 어느 정도 줄어드는 채널이다.
도구 결과와 파일 읽기는 사람이 의식하지 않는 채널이므로
자동 통제가 아니면 줄어들지 않는다.
즉 막기 쉬운 쪽에 게이트가 있고 어려운 쪽에 없다.
글의 96.5%는 전자에 대한 수치이고,
조직의 실제 유출 위험에서 전자가 차지하는 비중은 알려지지 않았다.

그래서 이 프레임워크를 도입하는 조직이 함께 해야 할 일이 정해진다.
같은 정책 파일을 도구 결과에도 적용하는 것이다.
훅이 사용자 프롬프트에만 걸린다면 다른 지점이 필요하고,
그 지점은 도구를 실행하는 하네스 안이다.
파일 읽기 도구가 반환한 내용을 모델에 넘기기 전에 같은 분류기를 통과시키면
같은 `policy.txt`로 두 채널을 덮을 수 있다.
정책이 자연어이고 모델 이식성이 확인됐다는 트랙 B의 결과가
이 확장을 값싸게 만든다.
글이 출력 DLP를 향후 과제로 든 것보다 이쪽이 먼저이며,
유출은 모델이 답하기 전에 이미 일어나 있기 때문이다.
