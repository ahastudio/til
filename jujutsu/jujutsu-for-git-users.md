# Jujutsu(jj): Git 저장소 위에서 커밋을 계속 고쳐 쓰는 버전 관리 도구

영상: [Git 사용자를 위한 Jujutsu Workshop | vim.kr](https://www.youtube.com/live/DczKGei6igY)

GN 토론: <https://news.hada.io/topic?id=36374>

## 소개

2026년 10월 31일 토요일 14시부터 18시까지 서울 성동구의 튜링의사과에서 vim.kr이
연 워크숍의 현장 라이브다.
영상 설명에 따르면 발표자는 Tangled 개발자 boltless이고, 내용은 Git 내부 구조에서 시작해 Jujutsu(jj)의 데이터 모델과 기본 명령, edit와 squash 워크플로, 머지와 rebase, 일급 객체(first-class)인 conflict, 메가 머지 워크플로, 그리고 마지막 시간의 Tangled와 AT Protocol 소개다.
영상은 3시간 17분이고, 영상 설명의 챕터는 24개다.

발표자는 jj를 쓴 지 1년이 조금 넘었다고 말하고(0:25),
참석자는 Git을 이미 아는 사람으로 전제한다.
이 문서는 한국어 자동 자막을 처음부터 끝까지 읽고 썼다.
자동 자막은 jj를 “주즈츠”로, vim.kr을 “빔케이”로 적는 식으로 고유명사를 자주
틀려서, 명령 이름은 영상 설명의 챕터와 jj 문서로 맞췄다.
이 문서를 쓴 환경에는 jj가 설치되어 있지 않아서 아래 명령은 직접 실행해
보지 않았다.

## Git과 jj는 같은 객체 위에서 다른 것을 더한다

발표자는 Git을 blob, tree, commit, tag 네 종류의 객체로 설명한다(0:10).
객체는 해시로 식별되어 불변이고, 브랜치와 태그 같은 ref는 가리키는 곳을
옮길 수 있다.
작업 트리와 객체 저장소 사이에는 인덱스가 있어서 `git add`와 `git commit`의 두
단계가 생긴다.

jj는 blob, tree, commit을 그대로 쓰고, 저장소 엔진으로는 지금 Git만
쓴다고 한다(0:17).
그래서 Git 저장소에서 만든 커밋을 jj로 열어도 같은 커밋이 보인다.
발표자가 꼽은 차이는 다음과 같다.

| 항목          | Git                                  | jj                                                            |
| ------------- | ------------------------------------ | ------------------------------------------------------------- |
| 현재 상태     | 인덱스와 작업 트리가 따로 있다       | 작업 트리 전체가 커밋 하나이고 인덱스와 stash가 없다          |
| 브랜치        | 쪼개져 나간 지점이고 HEAD를 따라온다 | 북마크(bookmark)는 Git 태그에 가깝고 자동으로 따라오지 않는다 |
| 식별자        | 커밋 해시                            | 커밋 해시와 변경(change) ID 두 가지                           |
| 기록          | reflog가 ref 이동을 남긴다           | 연산 로그(operation log)가 jj 명령마다 남는다                 |
| 저장소 만들기 | `git init`                           | `jj git init`(`jj init`은 없다)                               |

작업 트리와 객체 저장소는 jj 명령을 칠 때마다 그 자리에서 동기화된다(0:20).
그래서 파일을 고친 뒤 `jj status`나 `jj log`를 치는 순간 그 내용이 현재 커밋에
반영되고, 커밋 해시는 계속 바뀐다.
변경 ID는 그동안 그대로다(0:38).

변경 ID는 jj가 커밋에 넣는 무작위 문자열이고 결정적으로 정해지지 않는다(2:12).
발표자는 이 ID를 커밋 메타데이터에 넣기 시작한 지 1년이 안 되었고,
그 전에는 로컬에만 있었다고 말한다.
Git 저장소를 처음 jj로 열면 변경 ID가 자동으로 붙는다고 한다(2:11).
같은 변경 ID를 가진 커밋이 한 로그에 둘 이상 나오면 jj가 이를 `divergent`로 눈에
띄게 표시한다(0:23).
발표자는 Gerrit이 커밋 메시지 끝에 붙이는 자체 변경 ID(`Change-Id` 트레일러)는
jj의 것과 호환되지 않지만, Gerrit이 Git Merge 2026에서 jj 방식의 변경 ID를 공식
지원하기 시작했다고 설명했다고 전한다(0:24).
이 문서는 그 지원 여부를 확인하지 않았다.

## 기본 흐름: 먼저 설명을 쓰고 파일을 고친다

발표자는 jj와 Git의 마인드셋이 가장 크게 다른 곳이 순서라고 말한다(0:29).
Git은 파일을 고친 뒤 커밋으로 포장하고,
jj는 무엇을 바꿀지 커밋 메시지로 먼저 쓴 뒤 파일을 만든다.
Git에서도 빈 커밋을 만들고 `git commit --amend`로 쌓는 식으로 할 수 있고,
발표자는 그 방식을 반년 써 봤다고 한다.

```bash
jj git init
jj describe -m "add hello"
echo "hello" > hello.txt
jj new
jj log
```

`jj describe`는 현재 커밋의 메시지를 쓴다.
`jj new`는 현재 커밋을 부모로 하는 새 빈 커밋을 만들고 거기로 옮겨 간다.
`jj commit`은 `describe`와 `new`를 한꺼번에 하는 명령으로,
Git의 `commit`과 가장 비슷하게 동작한다(0:49).
`jj squash`는 현재 커밋의 변경을 부모로 합치고,
`jj squash -i`는 합칠 변경을 대화형으로 고른다.[^cli]

`jj git init`을 치면 빈 커밋과 그 아래의 루트 커밋이 함께 있다.
루트 커밋의 ID는 항상 같고(0:45), jj에서는 모든 변경이 최소 부모 하나를 가진다.
발표자는 인자 없이 `jj`를 치면 `jj status`가 실행된다고 말했는데,
jj 문서의 기본값은 `log`다.[^config]

## 이미 만든 커밋 고치기: edit 워크플로와 squash 워크플로

발표자가 jj에서 가장 좋은 부분으로 꼽는 것은 지나간 커밋을 쉽게 고치는
일이다(0:55).
방법은 두 가지다.

edit 워크플로는 `jj edit <변경 ID>`로 고칠 커밋으로 옮겨 가서 그 자리에서 파일을
고치는 방식이다(0:53).
고치는 즉시 그 커밋의 해시가 바뀌고, 그 위의 자손이 모두 다시 쌓인다.
`jj file show`는 특정 리비전의 특정 파일 내용을 보여 주므로,
옮겨 가지 않고도 다른 커밋의 파일을 볼 수 있다.

squash 워크플로는 현재 커밋 위에 `jj new <변경 ID>`로 새 커밋을 만들어 거기서
고친 뒤, `jj squash`로 아래 커밋에 합치는 방식이다(1:28).
`jj edit`으로 옮겨 가서 파일을 고치면 그 위 자손이 모두 다시 쌓이므로,
squash 워크플로에서는 `jj edit` 대신 `jj new <ID>`를 쓴다고 발표자는
설명한다(1:29).
`jj new <ID>`는 그 커밋을 부모로 하는 커밋을 만드는 동작이라 Git에서 브랜치를
만드는 것과 같지만 레퍼런스를 만드는 것은 아니라고 발표자는 말한다(1:30).
다른 커밋의 메시지를 고칠 때는 `jj describe -r <ID>`를 쓴다(0:57).

## 되돌리기

`jj evolog -r <ID>`는 한 변경이 지금까지 어떻게 바뀌어 왔는지의 기록을
보여 준다(1:15).
`jj undo`는 직전 연산을 취소하고, 한 번 더 치면 그 이전 연산을 취소한다(1:21).
발표자는 되돌리기의 되돌리기에 관한 질문에 “`jj redo`는 없을 것 같다”고 했다가
있었을 수도 있다며 정정했는데, jj의 CLI 문서에는 `jj redo`가 가장 최근에 취소한
연산을 다시 실행한다고 적혀 있다.[^cli]

`jj op log`는 스냅샷을 찍은 모든 jj 명령을 기록하고,
`jj op restore <연산 ID>`는 그 시점으로 저장소를 되돌린다(1:23).
복원과 `undo`도 연산 로그에 남기 때문에, 되돌린 뒤에 다시 되돌릴 수 있다(1:25).
발표자는 이것이 reflog와 다르다고 설명한다(1:24).
reflog는 ref를 옮긴 기록을 따로 남기는 것이라,
reflog를 거치지 않고 ref를 만지면 기록되지 않는다.
jj는 스냅샷을 찍을 때 연산 로그가 만들어지므로 그 단계를 건너뛰는 방법을
발표자는 모른다고 했다.

## 머지와 rebase

jj에서 머지 커밋은 부모가 둘 이상인 커밋일 뿐이다.
`jj new a b c`처럼 리비전 여러 개를 주면 셋을 모두 부모로 하는 커밋이
만들어진다(1:37).
Git의 `--ours`와 `--theirs` 같은 구별이 없고 부모 사이에 우열이 없다고 발표자는
말한다(1:34).
Git에서도 옥토퍼스 머지로 가능하지만 jj는 두 개 머지와 세 개 이상의 머지를
구별하지 않는다는 것이 차이다.

rebase는 옮길 대상과 갈 곳을 모두 명시하는 방식이다(1:49).
Git처럼 체크아웃을 먼저 해서 어느 쪽에 서 있는지 정할 필요가 없다.
옮길 대상을 정하는 옵션은 세 가지다.[^cli]

| 옵션 | 옮기는 범위                                           |
| ---- | ----------------------------------------------------- |
| `-b` | 가지(branch) 전체. 옵션이 없으면 `-b @`가 기본이다    |
| `-s` | 지정한 리비전과 그 자손                               |
| `-r` | 지정한 리비전 하나만. 자손은 그 부모 쪽으로 옮겨 간다 |

`-A`(`--insert-after`)와 `-B`(`--insert-before`)는 지정한 리비전의 뒤나 앞에
끼워 넣는다.[^cli]
참석자가 옵션 이름이 예전과 달리 `insert-after` 계열로 바뀐 것 같다고 짚자
발표자는 그렇다고 확인했다(2:09).
같은 리비전의 앞과 뒤에 동시에 끼워 넣으라고 하면 순환이 생기므로 안 된다고
발표자는 말한다(1:49).
리비전을 가리키는 표현식은 `M::L`처럼 두 리비전 사이를 범위로 쓰는 문법이 있고,
거의 모든 jj 명령이 같은 문법을 공유한다고 한다(1:45).
리비전을 가리키는 이 문법은 별칭(alias)과 함수를 정의해 늘릴 수 있다(3:04).

## 충돌을 커밋에 담아 두고 작업을 이어가기

발표자는 jj가 머지 충돌을 일급 객체로 지원한다고 말한다(1:50).
Git은 충돌이 나면 충돌 모드로 들어가 해결하거나 전부 되돌리기 전에는 다른 일을
못 하지만, jj는 충돌이 난 커밋이 그대로 하나의 커밋으로 남는다(1:52).
충돌 표시는 파일 안에 적히고, 표시를 지우고 `jj status`를 치면 충돌이
사라진다(1:53).
충돌 표시가 있는지로 판단한다고 발표자는 알고 있다고 했다(1:54).

충돌이 난 커밋 위로 가지 않으면 그 충돌은 작업에 영향을 주지 않는다(1:55).
Git에서 stash나 worktree가 필요했던 이유 중 많은 것이 충돌이 난 상태에서는 그
자리를 못 쓰기 때문이었는데, jj에서는 충돌을 그대로 두고 옆으로 옮겨 다른 일을
이어 갈 수 있다(1:56).
충돌 난 커밋 위 가지에서 해결한 내용은 `jj squash`로 충돌이 난 커밋에
보낸다(1:59).
이때 `jj diff -r`로 머지 커밋을 보면 jj가 부모 트리들을 메모리에서 임시로 머지한
뒤 현재 트리와 비교해 보여 준다고 한다(2:00).

## 메가 머지 워크플로

`jj new`에 리비전을 여러 개 줘서 아직 머지되지 않은 기능 가지 여러 개를 모두
부모로 하는 커밋 하나를 만들고, 그 위에서 작업하는 방식이다(2:02).
발표자는 jj 사용자에게 가장 좋았던 점을 물으면 순위가 높게 나오는
워크플로라고 말한다.
Git worktree가 기능마다 디렉터리를 하나씩 만드는 것과 달리,
모든 기능을 임시로 병합한 한 트리에서 작업한다.

작업하다가 변경이 기능 A에 속한다고 판단되면 `jj rebase -r <변경> -B <머지
커밋>`처럼 그 커밋을 머지의 한 부모 쪽으로 보낸다(2:03).
새 기능이라고 판단되면 머지 커밋의 부모에 새 줄기를 하나 더 만든다.
`jj abandon`으로 머지 커밋을 없앨 수 있다(2:09).
발표자는 모노레포에서는 기능 가지끼리 충돌이 잘 나지 않아 특히 효율적이라고
말한다(2:04).
발표자는 안 지운 가지가 많아서 보통은 부모로 삼을 가지를 직접 고르지만,
리비전 표현식의 별칭으로 가지를 한꺼번에 모을 수도 있다고 한다(2:05).

## Tangled와 AT Protocol

3부는 jj로 원격 저장소를 쓰는 법을 보이기 전에 발표자가 일하는 Tangled를
소개하는 것으로 시작한다(2:28).
발표자에 따르면 Tangled는 2025년에 회사가 세워졌고 발표자도 그해에 들어갔으며,
Git Merge 2026에서 대표가 데모를 보였고 NixCon에서는 Nix를 지원하는 CI 엔진을
소개했다(2:29, 2:30).
자동 자막은 행사 이름과 서비스 이름을 자주 틀리게 적어서, 아래의 고유명사는
발표 흐름과 영상 설명으로 맞췄고 확정하지 못한 것은 그렇게 적었다.

발표자는 Tangled의 기본 철학을 원격 저장소를 사용자가 원하는 대로 바꿀 수
있어야 한다는 것으로 설명한다(2:31).
이를 위해 데이터가 모두 열려 있어야 하고 사용자가 자기 데이터를 갖고 있어야
한다고 한다.
Google이 데이터를 쥐고 있어서 YouTube 클라이언트를 만들기 어려운 상황을
반례로 들고,
Tangled의 가치가 변하더라도 커뮤니티와 네트워크가 망가지지 않는 것이 목표라고
한다(2:32).

이 구조를 가능하게 하는 것이 AT Protocol이다.
발표자는 이 프로토콜이 2022년 Twitter 내부에서 Twitter를 탈중앙화하려는 시도로
시작되었고, 그래서 Twitter 규모의 사용량을 감당하도록 설계되었다고
설명한다(2:32).
참석자가 Bluesky가 아니라 원래 Twitter에서 시작한 것이라고 짚자 발표자는
그렇다고
확인하고, 그 내용을 Bluesky가 이어받았으며 지금은 일부를 IETF에서 표준화하고
있다고 덧붙였다(2:33).
표준화 대상은 프로토콜 전체가 아니라 식별자와 URI 같은 일부이고, IETF 안에
따로 개발 작업 그룹이 있다고 한다(2:34).
이 문서는 표준화의 진행 상황을 확인하지 않았다.

발표자는 구조를 마이크로서비스 아키텍처에 빗대어 설명한다(2:35).
각 사용자의 계정은 실제 도메인으로 처리되고, 그 도메인이 가리키는 분산
식별자(DID)가
계정이 현재 어디에서 호스팅되는지를 알려 준다(2:36).
그래서 사람이 읽는 핸들과 데이터 호스트를 모두 식별자를 유지한 채 바꿀 수 있다.
ActivityPub과 비교하면, ActivityPub은 서비스끼리 메시지를 주고받는 쪽이고
AT Protocol은 마이크로서비스 구조를 그대로 열어 일부 데이터를 사용자가 직접
호스팅하게 한 쪽이라고 한다(2:37).
이 차이 때문에 비공개 데이터는 ActivityPub이 다루기 쉽고, 이벤트 스트리밍을 쓰는
AT Protocol에서는 어렵다고 발표자는 말한다.

발표자가 Bluesky를 예로 든 구성은 세 층이다(2:38).
사용자 데이터는 개인 데이터 서버(PDS)에 저장된다.
색인 서버가 PDS들을 크롤링해 클라이언트에 제공하는데, 발표자는 이를
Google이 웹을
크롤링해 검색 결과를 주지만 데이터를 소유하지는 않는 것에 견준다.
색인 서버가 분산된 데이터베이스를 직접 크롤링하면 병목이 생기므로, 이벤트
스트리밍 서비스인 릴레이(relay)를 따로 둔다.

Tangled는 이 구성을 그대로 따른다고 한다(2:39).
색인 서버와 웹 클라이언트가 있고, 사용자 데이터는 사용자의 PDS에 저장된다.
Bluesky와 다른 점은 Git 저장소를 별도의 저장소 서버에 둔다는 것이다.
이 서버는 PDS와 같은 규격을 지원해서 AT Protocol SDK로 직접 읽을 수 있고,
내부 저장은 Git 저장소이며 바깥과는 AT Protocol로 말한다고 한다.
자막은 이 서버의 이름을 확정할 수 있게 적히지 않았다.
CI 엔진도 이벤트 처리 서비스라서 사용자가 직접 호스팅할 수 있고,
클라이언트는 각 사용자의 CI 엔진에서 파이프라인 내역과 로그를 가져온다(2:40).
Tangled가 제공하는 부분은 색인 서버부터 사용자 클라이언트까지이고,
저장소 서버와 PDS 같은 데이터 저장소는 사용자가 소유하게 되어 있다고 한다.

발표자는 이것을 해킹 가능한 포지(hackable forge)라고 부른다(2:40).
데이터를 사용자가 서비스하므로 크롤링해서 색인하고 보여 줄 수 있으면 서드파티
클라이언트가 될 수 있다는 것이다.
릴리스한 지 며칠 안 되어 누군가 TestFlight으로 iOS 앱을 올렸고,
다른 사람이 Tangled처럼 보이는 또 다른 클라이언트를 만들어 호스팅하고 있다고
소개한다(2:41).
저장소 쪽에서는 Cloudflare가 최근 발표한 Git 저장소 저장 서비스에 올린
저장소를 Tangled에서 볼 수 있고 Git Merge 26에서 이를 시연했다고 한다(2:42).
자막이 서비스 이름을 정확히 적지 않아서 어떤 제품인지는 확인하지 못했다.
CI도 Tangled의 워크플로 파일을 따를 필요가 없어서, 로컬에서 GitHub Actions를
돌리는 도구로 CI 엔진을 만들면 이론상 로그를 그대로 보여 줄 수 있다고 한다.
발표자는 한 친구가 특정 CI를 지원하지 않으면 넘어오지 않겠다고 해서 에이전트로
연결해 보였고, 그 시험 저장소에는 해당 CI의 디렉터리만 있고 Tangled 관련
파일은 없다고 설명한다(2:42, 2:43).
이 문서는 이 시연의 결과를 확인하지 않았다.

## 원격 저장소와 협업

jj는 Git 프로토콜로 원격에 올리므로 관련 명령이 `jj git` 아래에 있다.
`jj git remote add origin <URL>`로 원격을 더하고,
`jj bookmark set`으로 북마크를 만들고, `jj git push`로 올린다(2:46).
`jj git push -b <북마크>`는 지정한 북마크만 올린다.
`jj git push -c <리비전>`은 북마크를 만들어서 올리고,
이름은 기본으로 `push-` 뒤에 변경 ID 앞부분이 붙는다.[^cli]
`jj git push --named 이름=리비전`은 이름을 직접 정해 올린다.[^cli]
발표자가 이름을 안 지어도 되는 `-c`를 많이 쓰면 지우지 않은 `push-...` 북마크가
쌓인다는 점도 짚는다(1:12).
북마크를 만든 것을 감지해 지울 방법이 없어서 자동으로 지워지지 않는다고 한다.

`jj git fetch`는 있지만 pull은 없다(2:58).
`jj git push`는 기본이 강제 푸시(force push)라고 발표자는 말한다(2:51).
같은 변경을 계속 다시 쓰기 때문에, 이미 올린 가지의 커밋 해시가 바뀐 채로
올라가는 것이 정상 흐름이다.

공유된 가지를 건드리지 않도록 jj는 불변 커밋(immutable commit)이라는
개념을 둔다(3:01).
기본값에서 `trunk()`와 태그와 추적하지 않는 원격 북마크가 불변이라고 jj 문서가
설명하고, 불변 커밋도 `--ignore-immutable` 플래그로 고칠 수 있다.[^config]
발표자는 자기 커밋은 공유된 가지에서도 계속 고치고 싶어서 `immutable_heads()`를
자기 방식으로 정의해 쓴다고 한다(3:04).

발표자가 일하는 Tangled의 풀 리퀘스트(pull request) 화면은 커밋 범위의 diff,
전체 diff, 그리고 다시 제출한(resubmission) 두 버전 사이의 interdiff를 보여
준다고 발표자는 말한다(2:20).
마지막 것이 jj의 `interdiff`와 같은 개념이다.
커밋을 다시 올리면 해시가 바뀌고 부모가 달라질 수 있어서 `jj diff`로 두 버전을
비교하면 부모가 바뀐 변경까지 섞여 보인다.
`jj interdiff`는 이전 버전을 새 버전의 부모 위로 임시로 rebase한 뒤 두 트리를
비교해서, 그 변경 자체가 어떻게 바뀌었는지만 보여 준다(2:56).
변경 ID 같은 식별자가 있어야 가능한 기능이라 이를 보여 주는 포지는
Tangled뿐이라고 발표자는 알고 있다고 한다(2:18).

## 질의응답에서 나온 한계

- Git LFS와 `.gitattributes`는 지원되지 않는다고 발표자는 말한다(3:12). jj가 실제 Git CLI를 쓰는 것은 fetch와 push뿐이고 나머지는 Rust로 만든 Git 라이브러리로 처리해서, 그 라이브러리의 미지원 기능에 막힌다는 설명이다(3:13).
- 저장소 엔진은 Git 하나뿐이다. 발표자는 jj를 만든 쪽에서 자체 엔진을 만들 계획을 밝힌 적이 있다고 하지만 실제로 동작하는 다른 엔진은 본 적이 없다고 말한다(0:27).
- Git 저장소 하나를 협업자 몇 명은 jj로, 몇 명은 Git으로 쓸 수 있다. 같은 커밋의 변경 ID가 사람마다 다를 수 있지만 발표자는 상관없다고 한다(2:12).
- `jj workspace`는 `git worktree`에 대응하고, 발표자는 0.46.0에서 Git과 완전 호환된다고 말한다. Nix build는 상대 경로를 지원하지 않아 안 된다고 한다(3:10).
- 여러 커밋의 메시지를 한 텍스트 파일에서 한꺼번에 고치는 기능은 발표자가 알기로 없다(3:06).
- 설명이 없는 커밋은 기본값에서 푸시가 막힌다(3:06).

## 비평

### 라이브 실습은 발표자의 기억에 기대는 곳이 많다

영상은 발표자가 직접 명령을 쳐 보이는 실습이라, 막히면 그 자리에서 기억으로 답한다.
기본 명령이 `status`라고 했다가 `log`를 보여 준 것,
`redo`가 없을 것 같다고 했다가 정정한 것은 위에서 문서와 대조해 확인했다.
이 밖에도 Watchman 백엔드가 연산 로그에 어떻게 남는지(1:26),
삭제된 북마크를 지우는 옵션(1:13), `jj undo`의 예전 동작(1:22)은 발표자가 스스로
기억이 확실하지 않다고 밝힌 곳이다.
그래서 영상의 설명은 개념을 이해하는 데는 쓸 수 있지만,
명령의 정확한 옵션은 jj 문서로 다시 확인해야 한다.

### “더 쉽다”의 근거는 한 사람의 경험이다

발표자는 같은 데이터 모델을 쓰는 Git이 왜 이렇게 만들어져 있지 않은지 의문이 들
정도로 jj가 맞다는 느낌이 들 것이라고 말한다(0:08).
근거는 자신이 군대에서 jj를 알게 된 뒤 Git 흐름을 jj로 재현하려다 jj로 넘어온
경험과 1년 사용이다.
학습 비용이나 사고 비율을 Git과 견준 자료는 영상에 없다.
Git으로 충분히 하고 있는 사람이 옮길 때 잃는 것(LFS, `.gitattributes`,
엔진의 다양성)은 질의응답에서 나왔고, 이는 위의 한계 절에 정리했다.

### 마지막 시간은 발표자 소속의 제품 소개를 겸한다

발표자는 Tangled에서 1년째 일하고 있고(0:02),
3부(2:28)는 Tangled와 AT Protocol 소개로 시작한다.
`jj interdiff`를 보여 주는 포지가 Tangled뿐이라는 말(2:18)과 jj를 가장 잘
지원하는 포지라는 인상은 모두 발표자의 말이다.
다른 포지를 두루 비교해서 한 말은 아니고,
영상에서는 Gerrit과 다른 포지 한두 곳이 언급되었을 뿐 지원 범위는
확인되지 않았다.
이 문서도 그 주장을 확인하지 않았다.

### 기본 강제 푸시는 협업의 위험을 사용자에게 옮긴다

발표자는 `jj git push`가 기본으로 강제 푸시라고 말하고(2:51),
이는 변경을 계속 다시 쓰는 jj의 흐름에서 자연스럽다.
막아 주는 것은 불변 커밋 설정뿐이다.
`immutable_heads()`를 자기 커밋까지 고칠 수 있게 넓혀 쓰는 발표자의 설정(3:04)은
그 보호를 스스로 줄인 것이다.
공유 가지에 올릴 때 누가 그 위에 이미 일했는지는 jj가 알려 주지 않으므로,
팀에서는 불변으로 둘 범위를 먼저 정해야 한다.
이 문서는 jj의 푸시 안전 검사가 어떻게 동작하는지는 확인하지 않았다.

## 체크리스트

- [ ] `jj --version`이 영상이 말한 0.46.0 근처 이상인가(워크스페이스의 Git 호환이 이 버전부터라고 발표자가 말했다)
- [ ] 쓰려는 저장소가 Git LFS나 `.gitattributes`에 기대지 않는가
- [ ] 임시 클론에서 `jj git init`과 `jj describe`, `jj new`, `jj squash`를 한 번씩 돌려 봤는가
- [ ] `jj undo`와 `jj op restore`로 실수를 되돌려 봤는가
- [ ] 협업하는 가지의 `immutable_heads()`를 어디까지로 할지 팀에서 정했는가
- [ ] `jj git push -c`로 생긴 `push-...` 북마크를 정리할 방법이 있는가
- [ ] 쓰는 포지가 변경 ID나 `interdiff`를 보여 주는지 확인했는가
