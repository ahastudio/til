# Docker와 V8 메모리 제한 설정

원문: [Set memory limits using both Docker and v8](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/docker/memory-limit.md)

## 요약

Node.js 모범 사례 저장소의 도커 절에 있는 한 항목이다. 저장소 페이지의 캡처에 따르면 저장소는 이슈 57개와 풀 리퀘스트 83개가 열려 있다.
항목의 제목은 Docker와 V8을 모두 써서 메모리 제한을 두라는 것이다.

본문(「한 단락 설명」)의 내용은 다음과 같다.

- 메모리 제한은 프로세스나 컨테이너가 쓸 수 있는 메모리의 상한이다. 넘으면 프로세스가 OOMKill로 죽는다. 제한은 한 워크로드가 다른 워크로드의 자원을 모두 쓰는 일을 막는다.
- 제한은 런타임이 컨테이너를 메모리가 충분한 호스트에 배치하는 데도 쓰인다. 예로 500MB를 쓰는 컨테이너가 여유 메모리가 300MB인 인스턴스에서 실패하는 경우를 든다.
- 설정 지점은 두 곳이다. V8 플래그(`--max-old-space-size`)와 Docker 런타임 제한이며 둘 다 필요하다고 한다.
- Docker 제한은 런타임에 확장과 배치 결정을 위한 넓은 시야를 준다. 호스트에 여유가 있으면 짧은 메모리 급증은 견딜 수 있고, 운영팀은 메모리 스왑 같은 프로덕션 옵션도 정할 수 있다.
- `--max-old-space-size`가 없으면 V8이 제한 가까이에서 공격적으로 가비지 컬렉션을 하지 않아 호스트 메모리의 50에서 60% 정도만 쓰고도 죽을 수 있다. 권고는 V8 제한을 Docker 제한의 75에서 100%로 두는 것이다.

예제는 두 가지이다. Docker에서는 `docker run --memory 512m my-node-app`이고, Kubernetes에서는 요청 400Mi, 제한 500Mi에 `--max-old-space-size=350`을 주는 파드 정의이다.

```yml
apiVersion: v1
kind: Pod
metadata:
  name: my-node-app
spec:
  containers:
  - name: my-node-app
    image: my-node-app
    resources:
      requests:
        memory: "400Mi"
      limits:
        memory: "500Mi"
    command: ["node index.js --max-old-space-size=350"]
```

항목은 세 문서를 인용한다. Kubernetes 문서는 메모리 제한이 없는 컨테이너가 노드의 모든 메모리를 쓸 수 있어 OOM Killer가 작동할 수 있고 OOM 상황에서 죽을 가능성이 더 높다고 한다.
Docker 문서는 리눅스에서 커널이 중요한 시스템 기능에 쓸 메모리가 부족하면 OOME를 던지고 프로세스를 죽여 메모리를 확보한다고 한다.
Node.js 문서는 `--max-old-space-size`가 V8 올드 세대 메모리의 최대 크기를 정하고, 사용량이 한도에 가까워지면 V8이 가비지 컬렉션에 더 많은 시간을 쓴다고 하며 예로 2GB 기계에서 1536MB를 든다.

## 비평

### 수치의 근거가 항목에 없다

호스트 메모리의 50에서 60%에서 죽는다는 서술과 75에서 100%라는 권고는 출처나 측정이 항목에 없다.
같은 저장소의 예제도 Docker 제한 500Mi에 V8 350(70%)이라서 권고 범위(75에서 100%)와 일치하지 않는다. 이 문서는 이 불일치를 저장소에서 확인하지 못했다.

### 예제의 명령 형식이 의심스럽다

Kubernetes 예제의 `command`가 한 문자열 안에 `node`와 플래그를 모두 담은 배열 한 칸이다. 쿠버네티스에서 `command`의 각 칸은 실행 파일 인자로 쪼개지지 않으므로 이 형태는 그대로 실행되지 않을 수 있다. 이 문서는 직접 시험하지 못했다.
단위도 다르다. `--max-old-space-size`는 메가바이트이고 `Mi`는 메비바이트이다. 항목은 이 차이를 말하지 않는다.

### 힙 밖 메모리를 다루지 않는다

V8 올드 세대 제한은 힙만 제한한다. 버퍼, 네이티브 애드온, 스레드 스택 등 힙 밖 메모리와 사이드카의 메모리는 컨테이너 한도에 계산된다.
이 때문에 힙 한도를 컨테이너 한도의 100%로 두라는 권고는 위험할 수 있다. 같은 문제가 다음에 정리한 Next.js 토론에서 사이드카가 150Mi를 쓰는 사례로 나온다. 이는 이 문서의 해석이다.

### 외부 반응

HN에는 이 파일 주소로 올라온 글이 없었다. 저장소 전체 글은 여러 건이고 댓글은 없었다.

## 기억할 원칙

- Docker 제한과 V8 제한을 둘 다 둔다. 컨테이너 제한만 두면 V8이 한도를 모르고 늦게 정리하다 죽는다.
- V8 힙 한도는 컨테이너 한도보다 충분히 낮게 둔다. 힙 밖 메모리와 사이드카를 뺀 값에서 정한다.
- 단위(MB와 MiB)와 `command` 배열의 형식은 예제를 그대로 옮기지 말고 확인한다.
