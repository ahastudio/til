# 모던 Node.js 패턴 2025: 웹 표준을 품고 의존성을 걷어내다

원문: [Modern Node.js Patterns for 2025](https://kashw1n.com/blog/nodejs-2025/)

HN 토론: <https://news.ycombinator.com/item?id=44778936> (869점, 428개 댓글)

GN 토론: <https://news.hada.io/topic?id=22326>

## 요약

kashw1n.com에 2025년 5월 15일 실린 글이다.
콜백과 CommonJS가 지배하던 초기 Node.js에서
오늘날 표준 기반의 개발 경험으로의 전환을 정리한다.
모던 Node.js가 웹 표준을 받아들이고, 외부 의존성을 줄이며,
더 직관적인 개발자 경험을 제공한다는 것이 핵심 주장이다.

모듈 시스템에서 ESM이 표준이 되었고,
내장 모듈에 `node:` 접두사를 붙여 npm 패키지와 명확히 구별한다.
최상위 await(top-level await)로 초기화 코드를 감싸던
즉시 실행 async 함수(IIFE)가 사라진다.
내장 웹 API가 외부 의존성을 대체한다.
`fetch`가 axios와 node-fetch를 대신하고,
`AbortSignal.timeout()`으로 타임아웃을,
`AbortController`로 취소를 표준 방식으로 다룬다.

내장 테스트 러너(`node --test`)가 Jest·Mocha를 대체하고,
`--watch`가 nodemon을, `--env-file`이 dotenv를 대체한다.
비동기 패턴에서는 `Promise.all` 병렬 실행과 구조화된 오류 처리,
AsyncIterator를 통한 이벤트 스트림 처리가 성숙했다.
스트림은 `pipeline`으로 자동 정리와 오류 처리를 제공하고,
`Readable.fromWeb`/`toWeb`으로 웹 스트림과 상호 운용한다.
워커 스레드가 CPU 집약 작업에 진짜 병렬성을 준다.

그 밖에 실험적 권한 모델(`--experimental-permission`),
`perf_hooks` 기반 성능 모니터링,
단일 실행 파일(SEA), 구조화된 오류 클래스,
`diagnostics_channel`, `#` 접두사 임포트 맵,
동적 임포트를 통한 조건부 로딩을 다룬다.
결론은 웹 표준을 받아들이고, 내장 도구를 활용하며,
모던 비동기 패턴으로 사고하라는 것이다.
이 패턴들은 점진적으로 도입할 수 있고 기존 코드와 함께 동작한다.

## 분석

### 이 글의 핵심 주장은 Node.js가 런타임에서 플랫폼으로 진화했다는 것이다

글 전체를 관통하는 서사는 의존성의 내재화다.
과거에 npm 패키지로 채우던 것들,
곧 HTTP 클라이언트, 테스트 러너, 파일 감시, 환경 변수 로딩이
이제 Node.js 자체에 내장되었다.
Node.js가 단순한 JavaScript 런타임에서
포괄적 개발 플랫폼으로 진화했다는 것이다.

이 진화가 중요한 이유는 의존성이 곧 비용이기 때문이다.
HN에서 farkin88이 정확히 짚었다.
진짜 killer 업그레이드는 ESM이 아니라
fetch와 AbortController가 코어에 들어온 것이며,
axios와 node-fetch를 제거해 Lambda 번들 크기를 줄이고
콜드 스타트 지연을 약 100ms 단축했다는 것이다.[^farkin88]
의존성을 걷어내는 것은 코드 정리가 아니라
번들 크기, 시작 시간, 보안 표면의 실질적 개선이다.

vinnymac의 보충이 이 내재화의 범위를 넓힌다.
chalk나 picocolors도 더 이상 필요 없이
`node:util`의 `styleText`로 텍스트를 직접 꾸밀 수 있다는 것이다.[^vinnymac]
tyleo는 내장 테스트로 jest를, 내장 watch로 nodemon을
버릴 수 있다고 반겼다.[^tyleo]
작은 유틸리티부터 큰 프레임워크까지,
npm 생태계가 채우던 자리를 런타임이 하나씩 흡수한다.

### 웹 표준 채택이 여러 실행 환경 간 호환성을 겨냥한다

이 글이 반복 강조하는 것은 웹 표준과의 정렬이다.
`fetch`, `AbortController`, Web Streams는 모두
브라우저 개발자가 이미 아는 API다.
Node.js가 이것들을 채택한 것은 단순한 편의가 아니라,
서버·브라우저·엣지 런타임 사이의 코드 공유를 겨냥한 전략이다.

이 정렬이 중요한 이유는 런타임 파편화에 대한 대응이기 때문이다.
Cloudflare Workers, Deno, Bun 같은 대안 런타임이
웹 표준 API를 전면에 내세우며 등장했다.
Node.js가 같은 표준을 채택하면,
코드가 특정 런타임에 묶이지 않고 여러 환경에서 동작한다.
`Readable.fromWeb`/`toWeb`으로 웹 스트림과 Node 스트림을 오가는 것은
이 상호 운용을 구체화한다.
opentelemetry가 관측을 표준화해 벤더 종속을 끊었듯,
웹 표준 API는 런타임 종속을 끊는다.

GN에서 sanori의 관찰이 이 경쟁의 동학을 드러낸다.
Deno로 프로젝트를 시작하며 이런 것도 되네 했는데
node.js도 비슷하게 변하고 있다는 것이다.[^sanori]
이것은 정확한 통찰이다.
Deno가 웹 표준과 내장 도구를 전면에 내세워 등장하자,
Node.js가 그 방향으로 따라 진화했다.
경쟁 런타임이 Node.js의 현대화를 촉발한 것이다.

## 비평

### 이 글이 AI로 작성된 듯한 과장을 담고 있다

이 글의 가장 날카로운 비평은 그 문체 자체를 겨냥한다.
HN에서 refulgentis는 이 글이 LLM으로 작성된 듯
과장되게 들린다고 지적했다.
`node:` 접두사가 단순한 관례 이상이며,
개발자와 도구 모두에게 Node.js 내장을 임포트한다는
명확한 신호이고 잠재적 충돌을 막는다는 서술을 인용하며,
LLM이 이것을 지나치게 서사시처럼 만들었다는 것이다.[^refulgentis]

이 비평이 중요한 이유는 기술 글쓰기의 신뢰성 문제를 건드리기 때문이다.
`node:` 접두사는 유용한 관례이지만,
그것을 game-changing이나 crystal clear 같은 과장으로 포장하면
독자는 실제 이득의 크기를 가늠하기 어렵다.
generation-vs-distribution-freedom에서 본 AI의 후광효과처럼,
AI로 매끄럽게 다듬어진 글은 내용의 실제 무게보다
더 권위 있게 읽힐 수 있다.
모든 패턴을 한결같이 혁명적으로 묘사하면,
정작 중요한 fetch 내장과 사소한 `node:` 접두사가 같은 무게로 읽힌다.

이것은 influential-blog-posts에서 본,
기억하기 좋은 형식이 영향력의 대리 지표가 되는 문제와 이어진다.
매끄럽고 균일하게 열광적인 문체는 읽기 쉽지만,
비판적 판단을 흐린다.
좋은 기술 글은 무엇이 크고 무엇이 작은지를 구별해 주어야 하는데,
모든 것을 똑같이 현대적이라 칭송하면 그 구별이 사라진다.

### 내장 기능의 성능과 한계를 충분히 다루지 않는다

이 글은 내장 기능의 이점만 나열하고 그 한계는 거의 다루지 않는다.
HN에서 azangru가 중요한 반례를 들었다.
Matteo Collina에 따르면 Node의 fetch는 내부적으로 undici 클라이언트의 fetch인데,
WHATWG 웹 스트림을 생성해야 하므로
대안인 undici request보다 본질적으로 느리다는 것이다.[^azangru]
곧 내장 fetch가 편의를 주지만 성능에서는 대가가 있다.

이 누락이 중요한 이유는 채택 결정을 왜곡하기 때문이다.
글은 axios를 버리고 fetch를 쓰라고 권하지만,
고성능이 필요한 경로에서는 fetch가 최선이 아닐 수 있다.
farkin88의 콜드 스타트 개선과 azangru의 처리량 우려는 상충하지 않는다.
번들 크기와 시작 시간에서는 내장 fetch가 이득이고,
높은 처리량에서는 undici request가 나을 수 있다.
이 트레이드오프를 명시하지 않으면,
독자는 모든 상황에서 fetch가 최선이라 오해한다.

단일 실행 파일(SEA)에 대한 서술도 같은 문제를 안는다.
fleebee가 실제로 시도해 보니
제공된 명령이 만든 `.blob`은 여전히 Node 런타임을 요구했고,
진짜 실행 파일을 만들려면 추가 단계가 필요했다고 했다.[^fleebee]
ios-wallet-library-card에서 본,
테스트 없이 공유된 방법의 문제가 여기서도 나타난다.
글이 SEA를 자기 완결적 실행 파일 배포로 소개했지만,
실제 동작은 그 인상과 달랐다.

### 실험적 기능을 안정 기능과 뒤섞어 제시한다

이 글은 안정화된 기능과 실험적 기능을 명확히 구분하지 않는다.
권한 모델은 `--experimental-permission`이고,
SEA도 실험적이며, 글 자체가 네트워크 제한 기능이
아직 릴리스되지 않았다고 코드 주석에 적어 두었다.
그럼에도 이것들이 모던 패턴으로 나란히 제시된다.

이 혼재가 중요한 이유는 프로덕션 도입 가능성을 흐리기 때문이다.
내장 fetch나 테스트 러너는 프로덕션에서 바로 쓸 수 있지만,
실험적 권한 모델은 API가 바뀔 수 있고 신뢰성이 검증되지 않았다.
독자가 이 둘을 같은 준비도로 여기고 도입하면,
안정 기능은 잘 동작하되 실험 기능에서 예기치 못한 문제를 만난다.
simonw가 권한 모델을 처음 알았다며 반긴 것은[^simonw]
그 기능의 매력을 보여 주지만,
동시에 그것이 아직 실험적임을 독자가 인지해야 함을 상기시킨다.

성숙도의 스펙트럼을 평평하게 제시하는 것은
kafka exactly-once에서 본,
강한 이름이 조건을 가리는 문제와 같다.
모던 Node.js라는 우산 아래
안정된 것과 실험적인 것이 함께 담기면,
독자는 각 기능의 실제 준비도를 스스로 조사해야 한다.
좋은 안내라면 무엇을 지금 믿고 쓸 수 있고
무엇을 아직 조심해야 하는지를 표시해야 한다.

## 인사이트

### 런타임의 기능 흡수가 npm 생태계의 역할을 재편한다

이 글이 드러내는 가장 이전 가능한 통찰은
Node.js가 흔한 기능을 흡수하면서
npm 생태계의 역할이 근본적으로 재편된다는 점이다.
fetch, 테스트 러너, watch, 환경 변수 로딩, 텍스트 스타일링이
모두 런타임에 내장되면서,
그것들을 제공하던 axios, jest, nodemon, dotenv, chalk의 자리가 줄어든다.

이 재편이 중요한 이유는 오픈소스 유지보수의 경제를 바꾸기 때문이다.
수많은 개발자가 의존하던 유틸리티 패키지들이
런타임에 흡수되면, 그 패키지 메인테이너의 노력은 가치를 잃는다.
좌파패드(left-pad) 사건이 보여 준,
작은 패키지에 대한 과도한 의존의 위험이
런타임 내재화로 완화되지만,
동시에 그 패키지들을 유지하던 생태계의 노동이 무의미해진다.
smile-nestjs-sqs에서 본 재발명의 순환처럼,
런타임의 흡수는 생태계의 특정 층을 통째로 대체한다.

두 번째 차수의 효과는 이것이 의존성 문화를 바꾼다는 점이다.
farkin88이 습관적으로 npm i axios를 하는 사람에게
이제 그만둘 때라고 한 것은,
단순한 도구 교체가 아니라 사고방식의 전환을 요구한다.
무언가가 필요하면 먼저 패키지를 찾던 습관에서,
먼저 런타임에 내장되어 있는지 확인하는 습관으로 옮겨야 한다.
GN의 dnltmdwhd가 이제 axios 안 쓰고 fetch로 바로 되네라고 한 것이[^dnltmdwhd]
이 전환의 개인적 순간을 보여 준다.

### 경쟁 런타임이 Node.js의 현대화를 강제했다

sanori가 Deno에서 본 것을 Node.js가 따라 한다고 관찰한 것은
이 모든 변화의 숨은 동력을 드러낸다.
Node.js의 현대화는 자발적 진화가 아니라
Deno, Bun, Cloudflare Workers 같은 경쟁 런타임의 압력에 대한 대응이다.
경쟁자가 웹 표준과 내장 도구를 전면에 내세우자,
Node.js가 그 방향으로 움직일 수밖에 없었다.

이 통찰이 새로운 프레임을 주는 이유는
지배적 플랫폼의 혁신 동학을 설명하기 때문이다.
Node.js는 오랫동안 지배적이었기에 변화가 느렸다.
CommonJS와 콜백에 안주할 수 있었다.
Deno가 Node.js 창시자 Ryan Dahl의 후회에서 나와
웹 표준과 보안과 TypeScript를 기본으로 내세우자,
Node.js는 자기 관성을 깨고 따라잡아야 했다.
지배자는 스스로 혁신하기보다 도전자에 반응해 혁신한다.

세 번째 차수의 함의는 경쟁이 사용자에게 이득이라는 점이다.
Deno와 Bun이 없었다면 Node.js가 이토록 빠르게
fetch, 테스트 러너, 권한 모델을 내장했을지 의심스럽다.
homebrew-7.0에서 본, 대기업 기능의 신뢰 공백을 오픈소스가 메우듯,
런타임 시장에서도 도전자가 지배자의 정체를 깨운다.
사용자가 얻는 현대적 Node.js는
경쟁이 만든 산물이며,
그 경쟁이 식으면 Node.js의 혁신 속도도 다시 느려질 수 있다.

### 네이티브 TypeScript 지원이 다음 큰 전환을 예고한다

gabrielpoca118이 네이티브 TypeScript 트랜스파일러를 잊지 말라고 한
것은[^gabrielpoca118]
이 글이 충분히 다루지 않은 다음 큰 전환을 가리킨다.
Node.js가 TypeScript를 직접 실행할 수 있게 되면,
ts-node나 별도 빌드 단계 같은 또 다른 의존성 층이 사라진다.
웹 표준 API 내장이 axios를 지웠듯,
네이티브 TS는 TypeScript 툴체인의 상당 부분을 지운다.

이 통찰이 중요한 이유는 내재화의 논리적 종착점을 보여 주기 때문이다.
Node.js의 진화 방향은 일관되게 외부 도구의 흡수다.
HTTP 클라이언트, 테스트, 감시, 환경 변수에 이어
이제 타입 검사와 트랜스파일까지 런타임으로 들어온다.
이 궤적이 계속되면,
프로젝트를 시작할 때 설치해야 할 도구의 목록이 계속 줄어든다.
설정의 복잡성이 런타임으로 옮겨 가며,
개발자는 더 적은 조립으로 더 빨리 시작한다.

이 통찰의 함의는 개발 경험의 경쟁 축이 이동한다는 것이다.
과거의 경쟁은 어느 프레임워크가 더 많은 기능을 주느냐였다.
이제는 어느 런타임이 더 적은 설정으로 더 많은 것을 내장하느냐다.
Deno와 Bun이 이 축에서 앞서 나가자 Node.js가 따라온다.
네이티브 TypeScript는 이 경쟁의 다음 전장이며,
그것이 안정화되면 TypeScript 프로젝트의 시작 방식이 근본적으로 바뀐다.
런타임이 더 많이 품을수록,
개발자는 도구를 조립하는 대신 코드를 쓰는 데 집중하게 된다.
