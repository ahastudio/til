# Mac.apk: 에뮬레이터 없이 Android 앱을 Apple Silicon Mac의 일반 프로세스로 돌리는 호환 계층

<https://projects.voltare.us/macapk.html>

<https://github.com/kksimp/Mac.apk>

HN 토론: <https://news.ycombinator.com/item?id=50154624> (272점, 144개 댓글)

GN 토론: <https://news.hada.io/topic?id=35659>

## 소개

Mac.apk는 Apple Silicon Mac에서
Android 앱을 에뮬레이터나 가상 머신이나 Linux 커널 없이 직접 실행한다고
소개하는 프로젝트다.
앱은 평범한 macOS 프로세스로 시작해 Mac의 GPU로 그리고 CPU에서
네이티브 속도로 실행되며, Dock에 나타나고
신호등 단추 옆에 뒤로 가기 단추가 있는 자기 창을 가지며,
크기를 바꾸고 회전할 수 있고 Mac의 라이트와 다크 모드를 따라간다.
위키는 이것이 Wine이나 Proton이나 WSL과 같은 호환 계층이라고 설명한다.
한 운영체제용으로 쓰인 소프트웨어를 다른 운영체제에서 돌리는 것이고,
Android 앱 환경을 macOS 위에 직접 제공한다는 뜻이다.

## 동작 방식

위키는 앱의 세 부분을 각각 이렇게 처리한다고 설명한다.

Java와 Kotlin 코드는 Android 고유의 바이트코드인 DEX로 배포된다.
앱을 처음 실행할 때 Mac.apk가 DEX를 표준 Java 바이트코드로 바꿔 결과를
보관하므로 다음부터는 이 일을 건너뛰며,
첫 실행이 느린 이유의 대부분이 이 변환이다.
변환기는 따로 공개된 dex2jvm이고
변환된 코드는 Mac.apk에 들어 있는 OpenJDK로 만든 Java 런타임에서 돈다.

Android 자체는 Mac.apk가 AOSP의 동작에 맞춰 다시 구현한다.
액티비티와 뷰와 레이아웃과 리소스와 입력과 알림과 저장소가 그렇다.
Android가 휴대폰 하드웨어나 시스템 서비스에 말을 걸 곳에서는 macOS에 말을 걸어,
창은 Mac의 창이고 클립보드는 Mac의 클립보드이며 위치는 위치 서비스에서,
소리는 macOS를 통해, 컨트롤러는 macOS의 게임 컨트롤러 지원을 통해 온다.

네이티브 코드는 64비트 ARM이면 그대로 돌고
32비트 ARM은 실행 전에 한 번 64비트 ARM으로 다시 컴파일해 보관한다.
앱에 둘 다 있으면 64비트를 쓰고
Android의 C 라이브러리와 시스템 라이브러리는 macOS 위에 쌓은 Mac.apk가 제공한다.
리눅스 시스템 호출을 번역하는 것은 아니고 라이브러리 수준에서 이루어진다.

그래픽은 OpenGL ES를 ANGLE로,
Vulkan을 MoltenVK로 돌려 둘 다 Apple의 Metal에 도달한다.
설치한 앱은 저마다 하나의 Mac 앱이 되고
APK와 라이브러리와 변환된 코드와 저장 데이터가 앱 안에 들어간다.
Google Play Services는 대부분의 앱이 쓰는 부분을 Mac.apk가 자체로 구현하고
자신을 Mac.apk 기기로 소개한다.

## 설치하기

릴리스 페이지의 디스크 이미지를 받아 Mac.apk를 응용 프로그램으로 끌어다 놓는다.
Apple이 서명하고 공증했으므로 평소처럼 열린다.
Mac.apk를 열어 왼쪽 위의 Runtime 옆 Install을 누르고 설정의 File types에서
Make Default를 눌러 macOS 안내를 승인한 뒤,
`.apk` 파일을 두 번 누르거나 Mac.apk 창에 끌어다 놓는다.

README는 어떤 앱이든 첫 실행이 느리며 큰 앱은 최대 1분까지 걸린다고 적는다.
그동안 Mac.apk가 앱을 준비하기 때문이고 이후 실행은 빠르다.
앱 하나는 APK 크기의 대략 1.5배에서 3배의 디스크를 쓴다.

버그를 보고할 때는 Mac.apk 버전과 macOS 버전과 앱과 얻은 곳,
일어난 일, `~/Library/Logs/macapk/`의 앱 로그를 보내라고 한다.
로그는 공개로 올리기 전에 직접 훑어보라는 당부가 있다.

## 설계 결정

### 고치는 곳은 앱이 아니라 Mac.apk다

위키의 설계 결정 문서는 Mac.apk가 앱을 패치하거나 크랙하지 않는다고 밝힌다.
앱이 이상하게 동작하면 Mac.apk의 Android 구현의 빈틈으로 보고
거기서 고친다는 것이다.
고침이 플랫폼에 있으므로 같은 일을 하는 모든 앱에 도움이 되고
그래서 하나의 릴리스가 여러 앱을 한꺼번에 살리는 일이 흔하다고 한다.

### 정체를 속이지 않는다

Mac.apk는 앱에게 자신이 Mac.apk 기기라고 말한다.
공인된 Android 휴대폰인 척하지 않고,
기기를 증명하려는 어떤 것도 위조하지 않는다.
라이선스 검사는 사용자의 계정으로 Google에 가고
Google의 서명된 응답이 손대지 않은 채 앱에 닿으며,
Play Integrity와 비슷한 하드웨어 증명은 진실하게 통과할 수 없어서
제공하지 않는다.
Epic의 안티 치트 같은 것을 우회하지 않고,
광고를 속이거나 결제를 허용하지도 않는다.
이 때문에 일부 로그인 버튼과 몇몇 게임의 호환성을 잃는다고
인정하며 그것이 맞는 거래라고 쓴다.

### 샌드박스가 아니다

Android 앱은 사용자의 macOS 계정 권한으로 돌고 다른 Mac 앱과 같다.
Mac.apk가 앱의 Java 코드에 Android의 권한 규칙을 적용하지만
그것은 보안 경계가 아니라고 스스로 밝히고 믿는 APK만 설치하라고 한다.
면책 문구는 앱을 잘못 고른 데서
오는 데이터 손실과 악성코드와 보안 사고에 책임지지 않는다고 적는다.

## 트레이드오프

### 호환성을 정직함과 바꿨다

설계 결정이 인정하는 대로 Play Integrity를 제공하지 않고
안티 치트를 우회하지 않으므로 일부 앱은 영영 돌지 않는다.
알려진 문제에는 Fortnite가 Epic의 안티 치트에서
멈추고 Mac.apk가 우회하지 않을 것이라는 항목이 있다.
Duolingo는 새 계정을 만들거나 로그인할 수 없다고 호환 목록이 적는다.
그래서
호환성의 상한은 앱이 요구하는 증명을 얼마나
진실하게 통과할 수 있느냐로 정해진다.

### 첫 실행의 변환 비용을 지불하고 이후를 빠르게 한다

DEX를 Java 바이트코드로 바꾸고
32비트 ARM을 64비트로 다시 컴파일하는 일을 첫 실행에 몰아 하고 결과를 보관한다.
그 대가로 첫 실행은 최대 1분이 걸리고 앱마다 디스크를 늘 차지한다.
Asphalt Legends는 macOS가 그래픽 캐시를 지운 뒤 처음 시작할 때 로고에서
30초쯤 멈추는데,
얼어붙은 것이 아니라 셰이더를 준비하는 중이라고 알려진 문제에 적혀 있다.

### 최신 macOS만 지원하는 이유가 안정성이다

macOS 26.4 이상이 필요한 이유를 위키는 이렇게 설명한다.
네이티브 Android 코드가 macOS 26.4부터 있는 플랫폼 기능에 기대는데,
그것 없이는 앱이 깔끔히 실패하지 않고
가끔 충돌하거나 자기 데이터를 망가뜨리거나
앱의 버그처럼 보이는 이상한 일을 한다.
그래서 이상하게 돌기보다 거부하는 쪽을 택했고 시작할 때 기능을 확인해 없으면
네이티브 코드를 실행하지 않는다. macOS 27에서는
v1.0.1702 이상을 써야 하며 이전 버전은 Unity 게임이 빈 창에서 멈춘다.

## 함정

앱의 저장 데이터가 앱 자신의 `.app` 안에 있으므로
앱을 휴지통으로 끌어다 놓으면 저장 데이터가 지워진다.
README는 Mac.apk의 제어판에서 지우라고 경고한다.

앱이 사용자의 실제 사진과 다운로드와 문서 폴더를 쓰며 샌드박스가 없으므로,
믿지 않는 APK를 설치하면 파일을 읽고
쓰는 일이 다른 Mac 앱과 같은 권한으로 이루어진다.

Hill Climb Racing 1.71.1은 시작할 때 충돌하고
1.68.1은 작동한다고 알려진 문제가 적는다.
앱 버전마다 결과가 다르므로 호환 목록의 버전 열을 확인해야 한다.

Among Us는 컨트롤 메뉴에서 방향키를 D-패드로 켜야 키보드로 움직인다.

## HN에서 나온 논점

### Google Play Services 의존이 실사용 가치를 가른다

bilalq는 실제로는 Google Play Services 의존과 구글의 폐쇄적인 시도가 이것의
쓸모를 줄일 것이라고 했고,[^bilalq] Doohickey-d는 커스텀 롬에서
쓰는 것처럼 구글 서비스를 돌릴 수도 있으며
이미 Aurora Store를 해법으로 올려 놓았으니
조작하는 사람들을 위한 것이라고 했다.[^Doohickey-d]
이 문서가 읽은 위키는 Play Services를 자체 구현한다고 밝히고
호환 목록의 앱 가운데 Duolingo와 Thunderbird 같은 곳에서 로그인 문제가 보인다.
Google 서비스에 기대는 앱의 수치는 호환 목록의 66개 앱이 대표하는지에 달려 있다.

### 누가 쓰는가라는 질문에 답이 갈린다

MBCook은 이것이 누구에게 의미 있게 유용하냐고 물으며 해커다운 업적이지만
Apple Silicon Mac에서 iOS 앱도 개발자가 허용하면 돌릴 수 있고
자신은 실제로 필요한 적이 없다고
했다.[^MBCook] bilalq는 iOS와 Android 앱을 개발하는 사람으로서 iOS는 스토어에서
설치한 프로덕션 변형을 Mac에서 늘 돌리며 Android도 그럴 수 있다면 좋겠다고
했고,[^bilalq-dev] hex4def6는 권한을 의심스러울 만큼 많이 요구하고
두 단계 낮은 Android 버전을 요구하는 고양이 급식기 앱 같은 경우를
들었다.[^hex4def6] f17428d27584는 Minecraft 플레이어에게 쓸모가 있다며,
콘솔과 모바일 플레이어가 모두 베드록 버전이라 Android 버전을 Mac에서
돌리면 베드록 렐름에 들어갈 수 있다고 했다.[^f17428d27584]

### 기술적 정체성에 대한 오해가 이어진다

andsoitis는 Android 앱이 대개 Kotlin이나 Java로 쓰이니 JVM에 의존하지 않느냐고
물었고, quasarj는 README를 4초만 보면 Java 코드를 JVM에서 돌린다고 되어 있다고
답했다.[^andsoitis][^quasarj] chuckadams는 Android는 JVM을 쓴 적이 없고
DEX를 Dalvik VM 형식으로 번역해 실행했으며
지금은 앱이 미리 네이티브 코드로 컴파일되지만 APK에서는
중간 표현으로 DEX를 쓴다고 정리했다.[^chuckadams]
이 문서가 읽은 위키는 변환된 코드가 OpenJDK로 만든 Java 런타임에서 돈다고
밝히므로,
가상 머신이 없다는 표현은 Android 시스템을 부팅하는 가상 머신이 없다는
뜻으로 읽어야 하고 Java 코드가 런타임에서 실행되는 것까지 부정하지는 않는다.

## 확인하기

이 문서는 Mac.apk를 직접 설치해 실행하지 않았고
README와 위키와 호환 목록의 설명을 읽고 정리했다.
직접 확인하려면 Apple Silicon Mac에서
macOS 26.4 이상을 쓰는지 확인한 뒤 릴리스에서
디스크 이미지를 받아 Runtime을 설치하고, 호환 목록에서
작동으로 표시된 가벼운 앱(예: 계산기)을 `.apk`로
열어 첫 실행 시간과 이후 실행 시간을 비교한다.
앱을 지울 때는 Mac.apk 제어판에서 지워 저장 데이터가 어떻게 되는지도 확인한다.

## 체크리스트

- macOS 26.4 이상의 Apple Silicon Mac인가.
- 설치할 APK의 출처를 믿는가, 샌드박스가 없음을 알고 있는가.
- 앱 버전이 호환 목록에서 작동으로 표시된 버전인가.
- Google 로그인이나 Play Integrity나 안티 치트에 기대는 앱이 아닌가.
- 앱을 지울 때 휴지통이 아니라 Mac.apk 제어판을 쓰는가.
- 버그를 보고할 때 로그를 공개 전에 훑어보는가.

## 기억할 원칙

### 호환 계층의 가치는 속이지 않는 선 안에서 얼마나 많은 앱이 도느냐에 달려 있다

Mac.apk는 자신이 Mac.apk 기기라고 밝히고 증명을 위조하지 않는다.
이 선택은 일부 앱을 포기하게 하지만 반대로 Google의 서명된 답을 손대지 않고
전달하므로 라이선스 검사 같은 부분의 신뢰를 보존한다.
이 문서의 읽기로는 이 계층이 오래 쓰일지는 속임수로 호환성을 늘리지 않는
이 원칙 아래에서 호환 목록의 앱 수가 얼마나 늘어나는지에 달려 있다.
