# grounded-expert: 전문가 역할극 대신 전문가의 절차를 강제하는 에이전트 skill

<https://github.com/pko89403/grounded-expert>

Show GN: [grounded-expert - AI 코딩 에이전트가 기억 대신 공식 문서를 찾아 인용하며 답하게 하는 skill](https://news.hada.io/topic?id=36651)

## 소개

grounded-expert는 도메인 질문에 답할 때 subagent를 띄워 공식 스펙, 문서,
논문 같은 1차 자료(primary sources)를 실시간으로 찾아 열고,
자기 주장을 그 자료와 대조하게 하는 에이전트 skill이다.
저장소는 MIT 라이선스이고, 플러그인 매니페스트(manifest)의 작성자 이름은
skiiwoo이며, 저장소 소유 계정은 pko89403이다.
README는 Claude Code용 플러그인이 기준이고 Codex와 Antigravity 지원은 실험
단계라고 밝힌다.
GeekNews의 Show GN 글은 2026년 11월 5일 pko89403 계정이 올렸다.[^gn-topic]

제작자가 말하는 문제는 이렇다.
“너는 HTTP 전문가야” 같은 persona 프롬프트를 주면 모델이 기억(parametric
memory)으로 답하면서 역할을 연기하고, 틀린 사실도 맞는 사실만큼 자신 있게
말한다는 것이다.[^gn-topic]
제작자는 실제 전문가와 다른 점이 말투가 아니라 찾아보고, 근거를 대고,
틀리면 고치는 절차라고 보고, persona 대신 그 절차를 강제하는 skill을 만들었다고
설명한다.[^gn-topic]

이 문서는 GeekNews 글과 저장소의 README, `plugin/SKILL.md`, `CHANGELOG.md`,
`CONTRIBUTING.md`, `docs/openai-evaluation.md`,
`plugin/agents/grounded-researcher.md`를 읽고 정리했다.
skill을 설치해 실행해 보지는 못했다.
동작과 효과에 관한 서술은 모두 제작자가 저장소에 적은 내용이며,
직접 확인한 결과가 아니다.

## 동작 방식

### 질문 하나가 plan card를 거쳐 subagent 조사로 이어진다

`plugin/SKILL.md`가 정한 순서는 다음과 같다.
먼저 도메인, 정확한 질문, 수준(level)을 정한다.
다음으로 그 분야의 실제 전문가가 근거로 인용할 자료 유형을 2~4개 찾아 적는다.
이 단계는 검색 전에 한다.
그런 다음 사용자에게 plan card를 보여 주고 질문 하나를 한다.

plan card에는 질문, 가정한 도메인, 자료 유형, 1차 자료로 인정할 호스트,
수준과 상대 비용, 토큰과 시간 추정, 답변 언어가 들어간다.
사용자가 `go`라고 답하면 조사가 시작되고, 한 줄을 고쳐서 답할 수도 있으며,
`go and don't ask again`을 답하면 그 대화에서는 묻지 않는다.
헤드리스나 CI에서는
`Pre-approved: run the subagent now; do not ask for confirmation.` 문장이
프롬프트에 없으면 카드에서 멈춘다고 README가 적는다.

### 수준은 세 가지이고 비용이 다르다

| 수준(level)    | 동작                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| quick          | 자료 1개, 반대 근거 검색 없음, 점검 1회                                                                   |
| standard(기본) | 독립 자료 2개 이상, EXTRACTED와 INFERRED 표시, 반대 근거 검색 1회를 포함한 점검 최대 2회                  |
| thorough       | standard에 더해 후보 자료 유형마다 subagent를 병렬로 추가하고 교차 확인, 안전과 법률과 금전이 걸린 질문용 |

SKILL.md는 “대충”, “빨리”는 quick, “꼼꼼히”,
“전부 확인해서”는 thorough로 읽는다고 적는다.
plan card의 추정은 quick이 약 1만 토큰에 1분 미만,
standard가 약 1만~11만 토큰에 1~10분이고,
thorough는 아직 측정하지 않았다고 되어 있다.

### 답변은 주장마다 인용과 URL이 붙은 표다

SKILL.md의 출력 규약(output contract)은 답변의 형식을 정한다.
결론으로 시작해 수준과 도메인 줄, 그리고 `#`, `Claim`, `Tag`, `Quote`, `Source`,
`URL` 열을 가진 표가 온다.
표 뒤에는 남은 불확실성, `Disconfirming search:` 줄,
마지막으로 사용자가 지금 할 일을 적는 `Next step:` 줄이 온다.

각 행에는 태그가 하나씩 붙는다.

| 태그          | 의미                                                                   |
| ------------- | ---------------------------------------------------------------------- |
| EXTRACTED     | 1차 자료 호스트 페이지의 연속된 한 구절을 글자 그대로 따옴표 안에 옮김 |
| INFERRED      | 1차 자료가 아닌 호스트의 요약이거나, 여러 구절을 엮은 추론             |
| REUSED        | 7일 이내에 확인한 기존 행을 다시 조회 없이 사용                        |
| not confirmed | 열어 본 페이지에 근거가 없음                                           |

`INFERRED` 아래에는 호스트를 밝히는 `(via <host>)`,
원본의 복사본임을 밝히는 `(copy via <host>)`,
그림에서 읽었음을 밝히는 `(figure N)` 변형이 있다.
`Disconfirming search:` 줄은 반대 근거를 찾았는지(`found`),
찾았지만 없었는지(`ran`), quick이라 하지 않았는지(`not run (quick)`) 셋 가운데
하나만 쓴다.

### subagent는 검색과 조회 도구만 가진다

Claude Code 플러그인으로 설치하면 `grounded-expert:grounded-researcher`라는
agent를 부르고, 이 agent의 도구는 WebSearch와 WebFetch로 제한된다.
다른 환경에서는 `general-purpose`로 대신하고,
그 경우 도구 제한은 강제가 아니라 프롬프트의 규칙이라고 SKILL.md가 적는다.
조사 결과는 사용자에게 그대로 전달하며,
표의 행을 산문으로 바꿔 쓰지 말라고 규정한다.
subagent의 호출이 실패하면 그 사실을 말하고
`direct answer — no independent subagent`라는 라벨을 붙이도록 한다.

### 확인한 주장을 7일 동안 다시 쓴다

프로젝트의 `.claude/grounded-expert/claims.md`에 `fetched_at`, `Claim`, `Quote`,
`URL` 열의 표를 두고, 7일 이내의 행을 후보(Verified candidates)로
subagent에 넘긴다.
EXTRACTED 행만 이 파일에 저장되고, thorough 수준에서는 캐시를 쓰지 않는다.
0.9.0 릴리스가 이 기능을 넣었고 0.9.1이 캐시를 프로젝트당 파일 하나로 고쳤다고
`CHANGELOG.md`가 적는다.

## 설치

Claude Code에서는 다음 명령으로 설치한다.

```bash
/plugin install grounded-expert --marketplace pko89403/grounded-expert
```

README는 Claude Code 2.1.275 이상에서 이 명령이 저장소를
마켓플레이스(marketplace)로 추가하고 확인과 설치 범위 선택 단계를
거친다고 적는다.
셸 형태인 `claude plugin install`은 2.1.292 이상이 필요하다고 한다.
이후 `/grounded-expert <질문>`으로 직접 부르거나,
도메인 사실의 정확성이 필요한 질문에서 skill이 자동으로 뜨도록 되어 있다.

## 분석

### 전문가의 차이를 말투가 아니라 절차로 정의하고 그 절차를 형식으로 고정한다

저장소의 주장은 한 문장으로 요약된다.
persona는 말투를 바꿀 뿐 사실 확인 절차를 바꾸지 않는다는 것이다.
그래서 이 skill은 역할을 주는 대신 자료 유형 선정, 자료 수 하한, 반대 근거 검색,
인용 형식을 규칙으로 둔다.

특히 출력 형식이 절차의 일부다.
표의 각 행은 주장, 태그, 인용, URL을 한 줄에 묶으므로,
읽는 사람은 문장 하나를 URL의 페이지에서 글자 그대로 찾아 대조할 수 있다.
확인하지 못한 주장은 `not confirmed` 행으로 따로 표시하게 하므로,
모르는 것을 아는 것과 같은 문장 안에 섞지 않게 만든다.

### 조사 비용을 세 층으로 나눠 사용자에게 보여 준다

수준 세 가지와 plan card는 같은 목적을 가진다.
조사가 비용을 쓰기 전에 무엇을 얼마나 할지 사용자가 먼저 보고 고칠 수 있게
하는 것이다.
README는 승인한 호출마다 실제 subagent가 실시간 검색을 하므로 이것이 캐시된
조회가 아니라 실제 API 사용량이라고 적고,
thorough는 병렬 subagent가 더해진다고 밝힌다.

7일 캐시는 같은 대화나 같은 프로젝트에서 반복되는 질문의 비용을 줄이려는 장치다.
캐시에 EXTRACTED 행만 저장하는 선택은, 따옴표와 URL로 검증 가능한 행만
재사용하겠다는 뜻으로 읽힌다.

### 이식성보다 실패 기록을 먼저 공개한다

README는 Claude Code 패키지를 기준으로 삼고,
Antigravity 지원은 Claude Code의 평가(eval) 묶음에 포함되지 않으며 `self`
subagent가 웹 검색과 URL 조회 도구를 받는지 아직 확인하지 않았다고 적는다.
Codex용 패키지는 공개 Plugins Directory에 제출하지 않았다고 한다.
`docs/openai-evaluation.md`는 더 나아가 행동 면의 출시 기준(behavioral release
gate)을 통과하지 못했다고 적고 설치된 패키지를 돌린 여덟 번의 실행 결과를
표로 남긴다.

그 표에서 반복되는 판정은 답이나 조사 자체는 인정되지만,
독립 subagent가 실제로 생성되었다는 흔적이 기록에 없다는 것이다.
문서는 수신자가 비어 있는 대기 이벤트를 subagent 생성의 증거로 세지 않는다고
명시한다.
기능의 한계를 제작자가 저장소 안에 자세히 적는 점은 이 프로젝트가 자기 주장을
검증하려는 태도를 보여 준다.

## 비평

### 효과가 측정되지 않았다는 점이 제작자 설명에 이미 있다

GeekNews 글은 모델이 이미 아는 질문에서는 정답률 차이가 작고,
차이는 근거를 검증할 수 있다는 점이라고 적는다.[^gn-topic]
모델이 틀리는 질문에서 효과를 측정하는 작업은 진행 중이라고도 적는다.[^gn-topic]
내가 읽은 저장소 파일에서는 이 skill을 쓴 답과 쓰지 않은 답의 정확도를 비교한
결과를 찾지 못했다.

저장소에는 평가 사례 열 개가 있고 이름만 보면 HTTP 리다이렉트, GDPR 가명화,
Python 딕셔너리 순서, SQLite 외래 키 등이다.
`CONTRIBUTING.md`는 `claude plugin eval`로 전체 묶음을 돌려 이전 기준과
비교하라고 요구한다.
그러나 그 점수 기록은 저장소에서 보이지 않으며,
평가 사례의 채점 기준 파일을 내가 열어 읽지도 않았다.
따라서 이 skill의 가치 주장은 절차가 올바르다는 설계상의 논거에 기대고 있고,
정답률이 올랐다는 측정에 기대고 있지 않다.

### EXTRACTED 태그는 글자 그대로의 인용을 약속하지만 예시가 그 약속의 한계를 보여 준다

출력 규약에서 EXTRACTED는 1차 자료 페이지의 한 구절을 글자 그대로 옮긴
것이어야 한다.
그런데 README의 예시 답변은 두 RFC의 301 항목 본문이 요약 기능이 있는 조회
도구를 거쳐 들어왔으므로 인용문은 도구가 재현한 것이고 RFC 원문 텍스트는 읽지
않았다고 스스로 적는다.
같은 예시의 표에서 그 행들은 EXTRACTED로 표시되어 있다.

이는 태그가 보장하는 것이 페이지의 글자와 일치한다는 사실이 아니라,
조회 도구가 돌려준 글과 일치한다는 사실임을 뜻한다.
제작자가 이 사실을 답변의 첫 문단에 밝힌 것은 정직한 처리이지만,
표만 읽는 사람은 이 단서를 놓칠 수 있다.
저장소의 `tools/check_quotes.py`는 답변 파일과 선택적 fixtures 디렉터리를 받아
규약 준수를 검사하고 종료 코드에서 INVALID와 UNVERIFIED를 구분한다고 사용법에
적혀 있다.
나는 이 스크립트 본문을 끝까지 읽지 않았으므로,
실제 조회된 페이지와 인용을 대조하는지는 확인하지 못했다.

### 1차 자료의 기준이 목록 밖에서는 에이전트의 선언에 달려 있다

규약에는 도메인 다섯 개(http, law-eu, ml-paper, javascript,
python)의 1차 자료 호스트가 고정되어 있다.
그 밖의 질문은 `Domain: other`와 함께 `Primary hosts (declared):` 줄에 호스트를
선언해야 한다.
선언하는 쪽은 자료 유형을 정한 에이전트 자신이므로,
어떤 호스트든 선언하면 1차 자료가 된다는 구조다.

다만 plan card가 이 호스트 목록을 조사 전에 사용자에게 보여 주고 고칠 기회를
주므로, 오류를 잡는 책임은 사용자에게 넘어간다.
클라우드 제공자 문서처럼 목록에 없는 도메인에서는 이 카드의 검토가 사실상 유일한
점검 수단이다.
`go and don't ask again`을 답한 대화에서는 카드는 출력되지만 사용자의 답을
기다리지 않으므로, 고칠 기회가 사실상 사라진다.

### 지시만으로는 보장되지 않는다는 점을 저장소가 스스로 문서화했다

`docs/openai-evaluation.md`는 이 문서의 규칙들이 지시이며 강제된 런타임 보장이
아니라고 반복해서 적는다.
Codex 실행에서는 독립 subagent를 썼다고 보고하면서 기록에는 성공한 생성이
없었다는 사례가 여럿이었고, 문서는 프롬프트 지시만으로는 이런 근거 없는 서술이
안정적으로 사라지지 않았다고 말한다.
Claude Code 쪽에는 같은 방식의 실행 기록이 저장소에 없으며,
SKILL.md는 subagent가 한 일은 그 답변이 보여 줄 때만 subagent의 일로 서술하라고
규정할 뿐이다.
Claude Code에서 같은 문제가 없는지는 이 저장소만으로는 알 수 없다.

## 인사이트

### 근거 표는 검증의 비용을 낮추지만 검증이 일어나게 하지는 않는다

표의 한 행은 URL을 열어 인용을 찾아보면 확인되므로 사람이 검증하는 비용이 작다.
그러나 비용이 작아진 것과 사람이 실제로 확인하는 것은 별개다.
인용과 URL이 붙은 답변은 그 자체로 검증된 것처럼 읽히는 효과를 낼 수 있고,
이는 학술 글의 각주가 내용과 맞는지 확인하지 않아도 신뢰를 주는 현상과
같은 구조다.

이 효과에 대한 대응은 두 가지다.
하나는 앞의 비평에서 본 검사 스크립트처럼 기계가 인용을 대조하는 것이고,
다른 하나는 `not confirmed` 행과 단서를 표의 앞쪽에 두어 읽는 사람이 먼저 보게
하는 것이다.
이 skill이 표 뒤에 남은 불확실성을 두는 현재 배치는 두 번째에 약하다는 것이 내
판단이다.

### 프롬프트로 정한 계약은 바깥의 검사가 있어야 계약이 된다

저장소는 SKILL.md의 지시, 검사 스크립트, 평가 묶음,
그리고 기여 절차의 규칙을 함께 둔다.
`CONTRIBUTING.md`가 `claude plugin validate --strict`를 통과했다고 동작이
안전하다는 뜻은 아니라고 적은 것은 이 점을 안다는 표시다.
타입 주석은 타입 검사기가 없으면 설명일 뿐인 것처럼,
프롬프트의 규칙은 바깥의 검사가 있어야 보장이 된다.

이 구조에서 제품의 품질은 SKILL.md의 문장이 아니라 평가 묶음이 얼마나 넓고
엄격한지에 달린다.
평가 사례가 열 개인 지금은 어느 사례가 깨지면 변경을 막을 수 있는 정도이고,
질문 유형 전체에 대한 정답률을 말하기에는 이르다.
측정이 진행 중이라는 제작자의 말이 이 지점을 가리킨다.

### 7일 캐시의 신선도 한도는 이 도구가 가장 필요한 질문과 어긋날 수 있다

GeekNews 글에서 제작자가 받고 싶은 피드백은 모델이 자주 틀리는 질문 사례로,
최근 버전 변경이나 개정된 스펙을 예로 든다.[^gn-topic]
이런 질문은 공식 문서가 바뀐 직후에 답이 달라지는 유형이다.
7일 이내의 EXTRACTED 행을 다시 쓰는 캐시는 문서가 그 사이에 개정되었다면 낡은
인용을 새 조회 없이 내놓을 수 있다.

SKILL.md는 thorough에서 캐시를 끄고, 후보를 데이터로만 취급하라고 지시한다.
그러나 standard 수준의 일상 사용에서 어느 질문이 빠르게 바뀌는 문서에
해당하는지는 사용자가 알아서 판단해야 한다.
버전과 개정이 핵심인 질문에는 thorough를 쓰거나 캐시 파일을 비우는 것이
안전하다는 것이 내 추론이다.

### 도입 판단은 직접 만든 소규모 시험으로 할 수 있다

이 skill은 공개된 텍스트 자료(RFC, 공식 문서,
논문)가 웹에 있고 틀린 답의 비용이 큰 질문에 맞는 도구다.
사내 코드나 비공개 문서에 대한 질문은 이 skill의 조회 도구가 닿지 않는다.
시험은 모델이 자주 틀리는 질문 열 개를 모아 skill을 쓴 답과 쓰지 않은 답을
비교하고, EXTRACTED 행의 인용이 실제 페이지에 글자 그대로 있는지 직접
대조하는 것이다.

이 시험에서 인용 대조가 대부분 실패하거나 정답률 차이가 없다면,
이 skill의 가치는 답을 고치는 것이 아니라 답의 출처를 남기는 것에 그친다고 보는
것이 맞다.
반대로 모델이 틀리는 질문에서 차이가 뚜렷하다면 plan card의 마찰과 비용을 감수할
이유가 된다.
이 판단 기준은 내가 세운 것이며 저장소가 제시한 것이 아니다.
