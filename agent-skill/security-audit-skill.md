## 소개

Cloudflare가 공개한 코딩 에이전트용 스킬이다.
에이전트를 보안 감사자로 바꾼다는 것이 내건 문구이고,
여섯 단계로 구성된 다단계 보안 감사를 지휘한다.
MIT 라이선스다.

설치는 Skills CLI를 쓴다.

```bash
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit
```

사용자 수준에 설치하려면 `--global`을 붙인다.

호출은 코딩 에이전트에게 보안 감사를 요청하는 평범한 문장으로 한다.

```text
security audit this codebase
find security vulnerabilities in ./src
do a security review, output to ~/audits/my-project
```

전체 감사 모드와 안내(guidance) 모드를 지원하며,
출력 디렉터리를 지정하지 않으면
결과가 `~/security-audit-skill/<repo-name>/run-<N>`에 쌓인다.
README에 따르면
코드베이스를 직접 감사하거나 모의침투해 달라는 요청은 전체 감사 모드이고,
보안 질문이나 특정 취약점 조사는 보고서 산출물을 요청하지 않는 한 안내 모드다.
경로에 실행 회차가 들어간다는 점이 이 도구의 전제를 드러낸다. 한 번 돌리고
끝나는 것이 아니라 여러 번 돌리도록 설계되어 있다.

저장소는 마크다운 한 장이 아니다.
`skills/security-audit/` 아래에 정찰, 탐색,
검증 단계의 프롬프트와 공격 유형별 문서를 합쳐
마크다운이 15개(합계 약 180KB)이고,
JSON 스키마 하나, 의존성 없는 Node.js 검증기 두 개와 그 테스트 두 개가 있다.
공격 유형 문서는 메모리 안전, LLM 대상,
웹 프로토콜과 인증, 클라이언트 쪽, 공급망,
클라우드 배포, RPC와 메시징, 자원 고갈,
데이터 격리, 데스크톱과 모바일 등으로 나뉜다.
HN의 acedTrex는 마크다운 파일 하나에 글과 저장소를 바친다며
이 분야의 몰락이 빠르다고 비꼬았다.[^acedTrex]
vntok은 저장소를 열어 보라며 하위 폴더에 파일이 이십여 개, 텍스트가 300KB쯤 있고
프롬프트의 작은 수정을 시간에 따라 추적하는 데 Git이 적합하다고 답했다.[^vntok]
acedTrex는 프롬프트는 추적할 필요가 없다고 맞받았다.[^acedTrex-reply]

## 이 스킬이 나온 곳

README는 이 스킬이 Cloudflare의 취약점 발견 하네스의 씨앗이었다고 밝힌다.
하네스는 여러 단계로 자라 저장소 전체에 도는 시스템이 되었고,
이 스킬은 저장소 하나에서 시작하는 출발점이라는 설명이다.
하네스를 설명한 Cloudflare 블로그 글에 따르면 처음 스킬은 약 450줄이었고
한 세션에서 7단계 감사를 돌렸으며,
이 저장소의 README는 같은 흐름을 여섯 단계로 적는다.
블로그의 7단계에는 결과를 수집 API에 제출하는 단계가 들어 있고,
공개본이 단계를 어떻게 다시 나누었는지는 두 글만으로는 알 수 없다.[^blog]

스킬을 돌려 보니 벽이 셋 나왔다고 한다.
컨텍스트가 차면 모델이 자기 기억을 잃어 찾은 버그를 잊고,
실행 중간에 죽으면 처음부터 다시 해야 하며,
한 저장소 안에서는 그것을 쓰는 다른 저장소와의 관계가 보이지 않는다.
또 한 번 돌리면 여러 번 돌려 얻는 버그의 절반쯤만 찾고
찾은 것도 단순하고 덜 미묘한 쪽으로 치우친다고 적었다.[^blog]
README의 설계 원칙에 있는 같은 취지의 문장은 자체 시험 실행에서 나온 관찰이다.

하네스는 이 벽들을 상태를 데이터베이스로 빼내고
단계마다 에이전트를 두는 식으로 풀었다.
블로그는 저장소 128개를 덮는 스캐너가 되기까지 여섯 주쯤 걸렸고,
발견하는 쪽과 검증하는 쪽에 서로 다른 모델을 쓴다고 설명한다.[^blog]
이 저장소에는 그 하네스가 들어 있지 않고 스킬만 있다.
블로그도 하네스는 나중에 공개되기를 바란다고만 적는다.[^blog]

## 여섯 단계가 하는 일

| 단계 | 이름           | 하는 일                                                          |
| ---- | -------------- | ---------------------------------------------------------------- |
| 1    | 정찰           | 아키텍처, 신뢰 경계, 입력 표면을 파악하고 커버리지 원장을 만든다 |
| 2    | 커버리지 탐색  | 원장의 단위마다 격리된 헌터를 배정하고, 비평가가 빈틈을 찾는다   |
| 3    | 후보 검증      | 고유한 후보마다 새 검증자가 반증을 시도한다                      |
| 4    | 구조화 출력    | 확인됨, 검증 필요, 기각으로 분류해 스키마로 검증한다             |
| 5    | 독립 검증      | 새 에이전트가 근거로 인용된 소스가 실제로 그런지 확인한다        |
| 6    | 대상 중립 보고 | 검증된 데이터만으로 상세 보고서를 만든다                         |

이 배열에서 새 후보를 만드는 것은 1단계와 2단계이고,
3단계와 5단계는 앞 단계의 출력을 의심하는 데 쓰이며,
4단계와 6단계는 기록을 기계가 검사할 수 있는 형태로 만들고 보고서로 옮긴다.
발견보다 반증과 검증에 더 많은 단계를 쓰는 구조이며,
이것이 이 스킬의 핵심 설계 판단이다.

1단계의 산출물은 `architecture.md`와 `coverage-ledger.json`이다.
원장은 감사 범위를 안정적인 단위로 쪼갠 목록이고,
2단계의 헌터는 이 단위에서 배정된다.[^skill]
단위의 상태에는 계획됨, 후보, 막힘, 보류, 범위 밖 등이 있고,
감사가 끝난 뒤의 커버리지 진술은 이 원장에서 나온다.[^valid]

두 종류의 격리가 들어 있다.
2단계의 헌터는 서로 격리되어 각자 맡은 영역만 본다. 한
헌터가 다른 헌터의 결론에 오염되지 않게 하려는 것이다.
3단계와 5단계의 검증자는 발견자와 다른 에이전트다. 자기가 찾은
것을 자기가 검증하면 확증 편향이 그대로 통과하기 때문이다.

5단계가 따로 있는 이유도 짚어 둘 만하다.
3단계는 취약점이 진짜인지를 묻고,
5단계는 그 근거로 제시된 코드 인용이 실제로 그 파일 그 줄에 있는지를 묻는다.
실질적으로 내용이 바뀌는 교체가 일어나면
그것에도 다른 독립 검증자가 한 명 더 붙는다.
에이전트가 그럴듯한 코드 조각을 지어내는 실패 양식을 겨냥한 단계이며,
논리의 검증과 사실의 검증을 분리한 것이다.

## 실행 프로파일과 쓰기 격리

전체 감사에는 프로파일이 셋 있다.
`quick`은 헌터 한 차례와 마지막 비평가 한 번으로 끝나는 제한된 한 번의 훑기이고,
`standard`가 기본이며
`deep`은 위험이 크거나 큰 대상을 위해 단위를
하위 시스템과 수명주기 단계별로 쪼개고
비평가를 빈틈이 없을 때까지 돌린다.
지정한 범위(경로, 하위 시스템,
두 소스 참조 사이의 차이)만 보는 감사도 있으며,
범위 밖은 덮은 것이 아니라 `out_of_scope`로 기록하고
부분 감사임을 보고서가 밝힌다.
프로파일은 범위와 중복의 크기를 바꿀 뿐 증거 기준은 바꾸지 않는다.[^skill]

공유 파일(`run-metadata.json`, `architecture.md`,
`coverage-ledger.json`, `findings.json`과 보고서 셋)은
부모 에이전트만 쓴다.
헌터와 검증자는 `agents/<agent-id>/` 아래 자기 `scratch/`에만 쓰고,
보존되는 `artifacts/`로의 승격은 신뢰할 수
있는 부모 쪽 코드가 허용 목록에 있는 파일만
디스크립터 기반의 경쟁 조건에 안전한 절차로 복사한다.
심볼릭 링크, 하드 링크, FIFO, 소켓, 디렉터리,
크기 한도를 넘는 파일은 승격하지 않는다.[^skill]
대상 코드가 쓸 수 있는 곳에서 보존 영역으로 넘어오는 길을 좁게 만든 설계다.

## 판정 기준

이 스킬이 명시한 원칙들이 실제 결과물의 성격을 결정한다.

확립된 경계 실패만 확인으로 올린다.
즉 “이 입력이 여기까지 도달해 이런 일이 벌어진다”를 보일 수 있어야 하고,
보일 수 없으면 확인이 아니다.
소스에 근거가 있지만 막힌 단서는
정확히 풀리지 않은 사실과 함께 `needs_validation`으로 남긴다.

심각도는 입증된 영향을 요구한다.
영향을 시연하지 못하면
심각도를 높게 매기지 않는다. 이론적으로 위험해 보인다는 것만으로는 부족하다.

심층 방어의 공백은 취약점이 아니다.
계층 A가 공격을 막는다면
계층 B가 없다는 사실은 취약점이 아니라 강화 노트(hardening note)다.
보고서에서도 확인된 취약점 표와 분리된 항목으로 나온다.[^valid]

검증은 적대적이어야 한다.
검증자의 과제는 발견을 확인하는 것이 아니라 반증하는 것이고,
반증에 실패했을 때만 확인으로 남는다.

여러 번 돌리면 커버리지가 좋아진다.
한 번의 실행이 전수 검사가 아니라 표본 추출에 가깝다는 것을 전제로 하며,
README는 자체 시험 실행에서
한 번이 반복 실행 전체가 찾은 취약점의 절반쯤을 찾았다고 적는다.

세 판정은 다음처럼 구분된다.
`confirmed`는 소스 추적이 완전하고 관찰된 결과의 범위가 정해진 것이고,
`needs_validation`은 풀리지 않은 사실 하나가 정확히 적혀 있고
심각도가 없는 것이며,
`rejected`는 반증된 후보의 기록이다.
`confirmed`만 심각도를 받는다.[^skill]

| 심각도        | 기준(스킬의 정의)                                                              |
| ------------- | ------------------------------------------------------------------------------ |
| critical      | 인증 없는 행위자가 코드 실행, 데이터 저장소 전체 접근, 임의 계정 탈취를 얻는다 |
| high          | 명시된 보안 통제를 완전히 무력화한다. 인증 우회, 테넌트 간 읽기·쓰기 등        |
| medium        | 실제 경계 위반이지만 영향 범위나 전제 조건이 좁다                              |
| low           | 비밀이 아닌 내부 정보 노출이나, 이득에 비해 지속적인 노력이 드는 효과          |
| informational | 확인은 됐지만 영향이 최소인 관찰. 큰 발견의 전제 조건으로 쓰인다               |

high와 medium을 가르는 질문은 입증된 결과가 실제 결과를 낳는
행위에 대한 명시적 통제를 완전히 무력화하는지, 약화시키는지다.
구체적인 피해를 말할 수 없다면
심각도는 느낌보다 낮다는 것이 스킬의 규칙이다.[^skill]

## 트레이드오프

### 오탐을 줄이는 대가로 미탐을 늘린다

이 스킬이 겨냥한 문제는 분명하다.
에이전트에게 보안 감사를 시키면 그럴듯한 취약점 목록이 길게 나오고,
그것을 사람이 하나씩 확인하는 비용이 감사 자체보다 크다.
여섯 단계 중 3단계, 4단계, 5단계를 검증에 쓴 것은
이 비용을 자동화 안으로 흡수하겠다는 선택이다.

대가는 기준을 통과하지 못한 것들이 확인된 취약점 표에서 빠진다는 것이다.
심층 방어 공백을 취약점으로 치지 않고 입증된 영향을 요구하면,
실제 보안 팀이 관심을 가질 만한 항목
상당수가 강화 노트나 검증 필요 쪽으로 밀린다.
만료 없는 토큰, 과도한 권한 범위,
로깅되지 않는 민감 동작은 전부 그 자체로는 경계 실패가 아니지만
사고의 전제 조건이 되는 것들이다.
강화 노트는 보고서에 별도로 실리므로 사라지지는 않지만,
우선순위 표에는 들어오지 않는다.

여기서 흔한 기대가 통하지 않는다.
“기준을 낮추면 되지 않나”는 생각이 자연스럽지만,
기준을 낮추는 순간 이 도구가 해결하려던 원래 문제가 그대로 돌아온다.
확인과 기각 사이에 “검증 필요” 범주를 둔 것이 그 절충이며,
이 범주를 실제로 읽을 사람이 있느냐가 도구의 실효를 가른다.
읽지 않는다면 이 구조는 오탐을 줄인 것이 아니라 오탐을 다른 파일로 옮긴 것이다.

### 여러 번 돌리라는 권고가 비결정성을 인정한다

같은 코드베이스에 같은 스킬을 돌려도 결과가 달라진다는 것이 이 권고의 전제다.
출력 경로에 실행 회차를 넣은 것도 여러 실행을 나란히 두고 보라는 뜻이다.
그러나 이 스킬은 되풀이를 맹목적인 재시도로 두지 않는다.
이전 실행의 원장과 결과를 읽어 비어 있는 곳을 겨냥하고,
소스가 바뀐 곳은 다시 검증하며,
이미 확인된 항목은 소스와 조건이 그대로일 때만 이어받는다.
이어받은 확인도 현재 실행의 독립 검증을 거치고,
이전 실행에서 낡았거나 풀리지 않은 작업은 덮인 것으로 치지 않는다.[^skill]
그러니 실행들은 독립된 표본이라기보다 원장을 공유하며 쌓이는 누적이다.

이 구조는 한 가지를 얻는다.
감사 끝의 커버리지 진술이 이 실행에서 무엇을 덮었고
무엇을 보류하고 무엇을 범위 밖으로 뒀는지를 말한다.
README는 한 번의 실행이 대상을 소진했다고 암시하지 말라는 규칙도 둔다.[^skill]

남는 질문은 그래도 몇 번 돌려야 충분한가이다.
원장은 무엇을 훑었는지를 세어 주지만 훑은 곳에서 못 찾은 것은 세지 못한다.
Cloudflare 블로그도 자기 시스템의 누락률을 주장하지 않는다.
모든 실제 버그를 표시한 정답 집합이 없으므로 재현율 수치는 추측일 수밖에 없고,
재실행이 새 버그를 계속 찾는지와 커버리지가 계속 늘어나는지를 대리 지표로 본다고
적었다.[^blog]
따라서 아무것도 안 나왔다는 결과와 안전하다는 결론 사이에는 여전히 다리가 없다.

그래서 이 도구를 릴리스 게이트로 쓰기는 어렵다.
쓸 수 있는 자리는 게이트가 아니라 탐색이다. 사람이 볼 곳을 좁혀 주는 용도이고,
그 이상으로 해석하면 실제로는 보장이 없는데 보장이 있다고 믿게 된다.

### 격리가 만드는 사각지대

헌터를 서로 격리해 각자 영역만 보게 하는 것은 오염을 막지만
동시에 무언가를 놓치게 만든다.
실제 취약점 상당수가 두 영역의 접점에 있기 때문이다.
인증은 A 모듈이 하고 권한 검사는 B 모듈이 하는데 그 사이 호출 경로에서
컨텍스트가 유실되는 종류의 결함은, 각각을 따로 본 헌터 누구에게도 보이지 않는다.

스킬은 이 문제를 알고 있고 헌터 사이를 잇는 장치를 둔다.
헌터 한 차례가 끝날 때마다 새 비평가가 원장을 읽고,
연결되지 않은 진입점, 확인되지 않은 병렬 경로, 빠진 수명주기 단계,
근거 없는 제외를 찾아 새 단위로 제안한다.[^hunt]
1단계의 정찰이 신뢰 경계를 파악하는 것도 이 문제에 대한 부분적 대응이다.
경계를 먼저 그려 두면 헌터 배정이 그 경계를 따라가고,
경계를 가로지르는 흐름이 누군가의 영역에 들어간다.
다만 이 방식은 1단계가 경계를 제대로 그렸을 때만 작동하며,
1단계가 놓친 경계는 이후 단계 전체에서 존재하지 않는 것이 된다.

이 문제는 설계로 완전히 해소되지 않는다.
격리를 풀면 오염이 돌아오고, 유지하면 접점이 사라진다.
현실적인 보완은 정찰 결과를 사람이 한 번 읽는 것이다. 여섯 단계 중 사람이
개입할 가치가 가장 큰 지점이 마지막 보고서가 아니라 첫 단계의 경계 목록이다.

### 토큰 비용이 도입을 가른다

HN에서 가장 먼저 나온 반응은 비용이다.
drchaim은 중간 규모의 코드베이스에 100만 토큰을 들이고
아무것도 얻지 못했다고 적었다.[^drchaim]
jesse_dot_id는 비교적 작은 FastAPI 프로젝트에서 최소 15만 토큰을 썼고
세션 한도에 걸려 몇 시간 뒤에 이어 가야 했다고 했다.[^jesse_dot_id]
chrisweekly는 15만 토큰이 모델의 주의가 흐려지고
지시를 불규칙하게 따르기 시작하는 구간이라고 지적했다.[^chrisweekly]
SkyPuncher는 이런 도구가 PR 같은 특정 부분에 집중할 때 가장 잘 돈다고
했다.[^SkyPuncher]
모두 개인의 경험이고, 코드 크기와 모델과 설정이 달라 서로 비교할 수 없다.

스킬은 이 문제를 이미 알고 있다.
앞서 본 예산은 최대 에이전트 호출 수로 설정하고,
범위를 좁힌 실행과 `quick` 프로파일도 있다.
다만 기본값인 `standard`의 비용 구조가 README에 수치로 나오지 않아서,
처음 돌리는 사람은 작은 범위의 `quick`부터 시작해 비용을 가늠하는 편이 안전하다.
이는 이 문서의 권고다.

하네스 쪽 토론에서는 규모가 더 커진 같은 걱정이 나왔다.
jerf는 여러 모델로 코드베이스를 계속 훑고
교차 검증을 교차 검증하는 과정이 토큰을 수억 단위로 먹는다고 불평하며,
블로그의 비용 절에 금액이 보이지 않는다고 짚었다.[^jerf]
elevation은 책임 있는 기업이라면
공격자의 비용을 기대 이익보다 높이는 것이 목표이고,
공격이 너무 비싸서 감수하던 위험은 이 도구가 바꾼다고 답했다.[^elevation]
joshka는 대규모로 돌린다면
캐시된 입력 토큰으로 10대 1, 배치 토큰으로 2대 1의 비용 이점이 있고
자체 하네스를 만드는 이유가 이런 것을 직접 설계하는 데 있다고 했다.[^joshka]
이 수치는 댓글이 든 것이며 이 문서가 확인하지 않았다.

### 대상 중립 보고가 뜻하는 것

6단계의 대상 중립(target-neutral) 보고는
재현을 대상의 고유 인터페이스로 서술한다는 뜻이다.
스킬의 정의에서 `confirmed` 기록의 `execution`은 API 또는 HTTP 입력,
CLI 호출, 라이브러리 호출,
메시지, 파일 고정물, 브라우저 동작, 렌더링된 정책,
로컬 하네스 중 해당하는 것으로 쓴다.
보고서에 라이브 대상을 겨냥한 절차는 담지 않는다.[^valid][^skill]

이 선택에는 실질적인 이유가 있다.
감사 결과물은 유출되면 그 자체로 위험하고,
특히 에이전트가 만든 파일이 저장소에
커밋되거나 이슈에 붙는 일이 실제로 벌어진다.
재현 절차가 상세할수록 유용하지만 유출 시 손해도 그만큼 커진다.

대상 중립이 재현 정보를 덜어 낸다는 뜻은 아니다.
`medium` 이상의 확인된 기록은 `FINDINGS-DETAIL.md`에 소스 경로 전체와
대상 중립 로컬 재현을 복사해 넣게 되어 있다.[^valid]
그러니
수정한 사람이 재현을 처음부터 구성해야 하는
상황은 낮은 심각도나 검증 필요 항목에서 생긴다.
보고서를 어디에 두고 누가 볼 수 있는지를 먼저 정한 다음,
그 환경에서 얼마나 구체적으로 적을지를 정하는 것이 순서다.

### 모델이 같으면 독립 검증이 약해진다

스킬은 발견자와 검증자가 다른 에이전트라고 요구하지만,
다른 모델이어야 한다고 요구하지는 않는다. README와 SKILL.md,
정찰·탐색·검증 문서에서 그런 조항을 찾지 못했다.
블로그가 하네스에서 강조하는 것은 반대 방향이다.
발견에 쓴 모델과 검증에 쓴 모델을 완전히 다르게 해서
서로 다른 논리로 교차 검증하고,
같은 모델은 같은 렌즈로 코드 경로를 본다는 점을 한계로 든다.[^blog]

이 차이는 중요하다.
스킬을 한 모델 위에서 돌리면 새 에이전트라도
같은 훈련에서 나온 같은 편향을 공유한다.
새 컨텍스트가 막아 주는 것은 발견자의 추론 과정에 끌려가는 오염이지,
모델 자체의 체계적 맹점은 아니다.
스킬을 쓰는 사람이 검증 단계의 모델을 따로 고를 수 있다면
그것이 가장 싼 개선일 수 있다.
이 문서는 그 효과를 측정한 자료를 찾지 못했으므로 가설로 둔다.

## 함정

기본 출력 경로가 홈 디렉터리 아래다.
`~/security-audit-skill/<repo-name>/run-<N>`에 감사 결과가 쌓이며,
여기에는 취약점 후보와 코드 인용이 들어간다.
백업 대상이나 동기화 폴더에 포함되어 있는지 확인하지 않으면
감사 결과가 의도치 않은 곳으로 흘러간다.

“확인됨”만 읽고 끝내면 이 도구를 절반만 쓰는 것이다.
기준이 엄격하므로 확인 범주는 짧고,
실제 판단이 필요한 것들은 “검증 필요”에 모인다.
그 범주를 읽을 사람과 시간을 정해 두지 않으면
도구를 도입한 효과가 나오지 않는다.

한 번 실행하고 깨끗하다고 결론짓는 것이 가장 흔한 오용이다.
스킬 자신이 여러 번 돌리라고 밝히고 있으며,
이것은 성능 권고가 아니라 단일 실행의 커버리지가 불완전하다는 고백이다.

샌드박스를 강제할 수 없으면 스킬은 대상 코드를 실행하지 않는다.
요구 조건은 외부 네트워크 차단, 허용 목록으로 채운 빈 환경,
읽기 전용 대상과 도구 및 scratch 전용 쓰기, 낮은 자원과 시간 한도 네 가지다.
하나라도 지킬 수 없으면 그 단서는
실행 증명 없이 `needs_validation`으로 남는다.[^skill]
기본 환경에서 이것이 갖춰지지 않으면 확인 범주가 작아지는 것이 설계된 동작이다.
HN의 9el은 요구 사항에 OS 수준 샌드박스가 왜 들어 있는지 물었다.[^9el]
스킬 본문의 답은 빌드와 테스트와 퍼저를 돌리는 동안 대상 코드가
호스트와 보존 출력과 인증 정보에 닿지 못하게 하려는 것이다.[^skill]

보안 감사라는 표현 자체가 모델의 거부를 부르기도 한다.
wslh는 보안 연구라는 틀을 명시한 스킬이 상위 모델에서 거부를 일으킬 때가 있어서
보안 틀 없이 버그 유형별로 나눈 스킬들과 그 결과를
합쳐 보안 버그를 가리는 스킬을 쓴다고 했다.[^wslh]
viraptor는 보안 전문가라면 제공자의 검증 절차를 거치면
그런 거부가 줄어든다고 답했지만,
xur17은 회사와 개인으로 모두 거쳤는데
몇 주째 응답이 없다고 반박했다.[^viraptor][^xur17]
스킬을 돌리는 모델이 이 요청을 받아 주는지는 도입 전에 확인할 사항이다.

예산이 부족하면 감사가 불완전하게 끝난다.
스킬은 최대 에이전트 호출 수를 예산으로 받고,
정찰과 비평가와 검증자의 몫을 먼저 확보한 뒤에야 헌터를 배정한다.
검증 예산이 바닥나면 검증하지 못한 후보를 발견으로 올리지 않고
실행을 불완전으로 기록한다.[^skill]
`quick`이나 범위를 좁힌 실행은 부분 감사라고 보고서가 밝혀야 하므로,
이런 보고서를 전체 감사로 읽으면 안 된다.

에이전트가 코드베이스 전체를 읽는다는 사실도 전제해야 한다.
감사 대상이 민감한 코드라면 어떤 모델이 어디에서
도는지가 감사 자체보다 먼저 결정할 문제다.

## 확인하기

도입 판단은 이미 알고 있는 결함으로 하는 것이 가장 정확하다.
과거에 실제로 고쳤던 취약점이 있는 커밋으로 되돌린 브랜치를 만들고
그 위에서 감사를 돌려, 그것을 찾아내는지 본다.

```bash
# 알려진 결함이 있던 시점으로 되돌린 브랜치에서 실행
git switch -c audit-baseline <취약점이-있던-커밋>
# 에이전트에게: security audit this codebase, output to ./audit-baseline
```

확인할 것은 세 가지다.
그 결함을 찾았는가, 찾았다면 확인 범주에 넣었는가 아니면 검증 필요에 넣었는가,
그리고 같은 브랜치에 세 번 돌렸을 때 결과가 얼마나 흔들리는가.
세 번째가 가장 중요하다. 흔들림의 폭이 이
도구를 신뢰할 수 있는 범위를 정하기 때문이다.

반대 방향의 시험도 값이 있다.
이미 고친 브랜치에 돌려 그 결함을 다시 보고하는지 보는 것이다. 고쳐진
코드에 대해 취약하다고 보고한다면 그것이 이 도구의 오탐률을 직접 보여 준다.

## 체크리스트

- 출력 디렉터리를 정했고, 그 경로가 백업이나 동기화 대상이 아닌지 확인했는가
- 이미 알고 있는 결함으로 기준선 시험을 돌려 보았는가
- 같은 대상에 여러 번 돌려 결과의 흔들림을 측정했는가
- “검증 필요” 범주를 읽을 사람과 시점을 정했는가
- 1단계가 파악한 신뢰 경계 목록을 사람이 읽고 빠진 것이 없는지 확인했는가
- 감사 대상 코드가 외부 모델에 넘어가도 되는지 확인했는가
- 이 도구의 결과를 게이트로 쓰는지 탐색으로 쓰는지 명시했는가
- OS 수준 샌드박스의 네 가지 통제를 모두 강제할 수 있는지 확인했는가
- 첫 실행을 `quick`이나 좁힌 범위로 돌려 토큰 비용을 가늠했는가
- 스킬을 돌릴 모델이 보안 감사 요청을 거부하지 않는지 확인했는가

## 기억할 원칙

### 적대적 검증은 발견자와 검증자가 다를 때만 검증이다

이 스킬에서 가장 옮겨 쓸 만한 설계는 검증을 다른 에이전트에게 맡긴 것이다.
같은 컨텍스트 안에서 “이게 맞는지 다시 확인해 봐”라고 시키면
에이전트는 대체로 자기 결론을 다시 정당화하며, 그것은 검증이 아니라 반복이다.
새 에이전트에게 반증을 과제로 주면 인센티브의 방향이 바뀐다.

이 원리는 보안 감사 밖에서도 그대로 쓰인다.
코드 리뷰, 사실 확인, 테스트 작성이 전부 같은 형태이며, 공통 조건은 두 가지다.
검증자가 발견자의 추론 과정을 보지 않을 것,
그리고 검증자의 성공 조건이 확인이 아니라 반증일 것.

그리고 이 스킬이 5단계를 따로 둔 이유도 함께 기억할 만하다.
논리가 맞는지와 인용한 사실이 실재하는지는 다른 질문이고,
앞의 것만 검증하면 실재하지 않는 코드 위에 정교한 논증이 서 있는 결과가 나온다.
에이전트 산출물을 검증할 때 이 두 층을 분리하는 것이,
산출물의 길이가 늘어날수록 더 중요해진다.

### 기계가 검사할 수 있는 것은 기계에게 맡기고, 의미는 다른 에이전트에게 맡긴다

이 스킬은 두 종류의 검증자를 구분해서 쓴다.
`findings.json`과 원장은 의존성 없는
Node.js 검증기가 스키마와 일관성을 검사하고,
인용한 소스가 실제 그런지는 새 에이전트가 읽어 확인한다.
블로그는 이 구분을 더 분명히 적는다.
`findings.json`의 기계 검사는 스키마를
지켰는지를 보는 것이지 맞는지를 보는 것이 아니고,
파일 경로와 줄 번호가 실재하는지는 모델이
아니라 평범한 코드가 먼저 확인한다.[^blog]

에이전트가 자기 익스플로잇이 통하도록 소스를 고쳐 놓고
그렇게 만든 버그를 보고하는 일이 있다고 블로그는 경고한다.
그래서 하네스에서는 확인된 발견마다 소스를 건드리지 않은 원본에서
도는 테스트를 PoC로 달아야 한다고 한다.[^blog]
이 저장소의 스킬은 수정안을 서술할 뿐 대상 소스를 고치지 않으며,
검증 단계에서도 대상과 도구를 읽기 전용으로 두고
쓰기를 scratch로 제한해 같은 위험을 줄인다.[^skill]
검증에서 중요한 것은 검증자를 늘리는 일이 아니라
각 층이 어떤 종류의 오류를 잡는지 정해 두는 일이다.
