## 소개

Archify는 에이전트 스킬이다.
저장소 설명은 아키텍처, 워크플로, 시퀀스, 데이터 흐름, 생명 주기 다이어그램을 아름답고 검증 가능하게, 움직임과 선명한 내보내기를 갖춘 독립 HTML로 만든다는 것이다.
README 첫머리는 범위를 더 넓게 잡아, 이해하거나 계획하거나 공유하고 싶은 무엇이든 인터랙티브한 시각 자료로 바꾼다고 적는다.
아이디어나 질문이나 계획을 에이전트에게 설명하면 탐색하고 고치고 공유할 수 있는 HTML이 나오며, 여행 일정과 학습 지도부터 복잡한 시스템까지 다룬다는 것이다.
MIT 라이선스이고, 2026년 4월 15일에 저장소가 만들어져 9월 25일 기준 스타 71,328개, 포크 4,797개이며, 현재 개발 버전은 `v2.17.0-dev.1`이다.

Cursor, Claude Code, Codex CLI, OpenCode에서 동작하고, Claude.ai에는 `archify.zip`을 스킬로 올려 쓸 수 있으며, DeepSeek Harness용 커뮤니티 플러그인도 있다.
README는 제작자가 9월 1일 공개한 스크린숏을 근거로 GitHub Trending 주간 전 언어 저장소 1위에 올랐다고 밝히고, QbitAI의 소개와 인터뷰를 든다.
Kimi Work, Supercode, EverMind의 Raven이 후원사로 올라 있다.

## 동작 방식

### 다섯 가지 다이어그램

| 종류         | 알맞은 대상                            | 프롬프트에 넣을 것               |
| ------------ | -------------------------------------- | -------------------------------- |
| Architecture | 구성 요소, 서비스, 저장소, 경계        | 범위, 핵심 구성 요소, 주 경로    |
| Workflow     | CI/CD, 승인, 도구 호출, 런북           | 참여자, 순서, 분기, 예외         |
| Sequence     | API 호출, 캐시 폴백, 인증, 비동기 추적 | 호출자, 피호출자, 반환, 시점     |
| Data Flow    | 파이프라인, 계보, 개인정보, 소비자     | 원천, 변환, 저장소, 경계         |
| Lifecycle    | 상태, 재시도, 대기, 종료 결과          | 상태, 이벤트, 재시도와 취소 경로 |

### 생성에서 전달까지

작업은 다섯 단계로 흐른다.
에이전트가 설명에서 타입이 있는 JSON 중간 표현(IR)을 만들고, 번들된 검증기와 레이아웃 규칙이 그 원본을 검사한다.
실패하면 정확히 어디를 고쳐야 하는지를 기계가 읽을 수 있는 JSON으로 돌려준다.
선택적인 미리 보기는 루프백 전용 데스크톱 세션으로 원본 하나를 지켜보며 검증을 통과한 개정판만 다시 불러오고, 실패하면 마지막으로 통과한 결과를 계속 보여 준다.
전달 단계에서는 같은 디렉터리에 후보를 렌더링해 검사하고, 통과한 결과만 대상 파일을 원자적으로 바꾼다.
이후 요청에서는 에이전트가 원본을 고치되 관계없는 구조는 그대로 둔다.

README가 밝히는 엔지니어링 원칙은 이렇다.
범용 자동 배치 대신 에이전트가 위계와 간격과 경로와 강조를 정하고, 공유되는 자동 연결점은 화살표가 한 점에 몰리지 않도록 결정적으로 퍼진다.
렌더러가 있는 모든 모드는 스키마와 재현 가능한 원본을 가진다.
쇼케이스 결과물이 마지막 정상본을 대체하려면 스키마, 레이아웃, HTML과 SVG, 경로, 레이블과 경로 사이 간격 검사를 모두 통과해야 한다.
실패하면 Node 스택 추적이나 막연한 재시도 대신, 안정된 규칙 코드와 정확한 대상과 측정된 근거와 지원되는 수정 방법만 담은 “수리 영수증”을 돌려준다.
스킬은 두 번의 수정 라운드 안에서 각 진단 대상의 `supportedFixes`만 적용하라고 에이전트에게 지시하며, 시각적 검토는 따로 한다.

### 사실에 충실한 상호작용

결과물 HTML에서는 노드를 찾아 초점을 맞추고, 상류와 하류의 도달 범위를 따라가고, 두 노드 사이의 경로를 탐색하고, 역할을 비교하고, 장별로 이야기를 재생할 수 있다.
README는 이 상호작용이 작성된 노드와 관계만 재사용하며, 위상을 새로 지어내거나 런타임 영향을 주장하지 않는다고 적는다.
소스 근거는 요청할 때만 붙는다.
근거가 있는 Architecture 노드는 `SRC n`으로 표시되고, 하나의 공개 커밋에 고정된 Git 검증 파일과 줄 범위를 연다.
README는 공개 저장소 `mco-org/mco`의 커밋 `9f1a1cf`를 추적해 만든 실행 구조 지도를 예로 든다.

PR 리뷰용으로는 Architecture Delta가 검증된 이전, 변화, 이후 스냅숏을 기계 영수증과 함께 비교한다.
README는 이것이 영향이나 위험이나 병합 안전성을 추론하지 않는다고 명시한다.
Architecture의 선택적 `deployment-ownership` 프로필은 작성된 소유자, 지역 배치, 사설 데이터베이스 범위, 이름 붙은 경계 넘기가 빠지면 실패로 닫히며, 실제 인프라를 살펴보지는 않는다.

## 사용법

설치는 한 줄이다.

```bash
npx skills add tt-a1i/archify -g
```

저장소 없이 설명만으로 시작할 수 있다.

```text
Use Archify to draw: Browser -> API -> Redis cache -> PostgreSQL fallback.
```

저장소를 근거로 그리려면 저장소를 열고 이렇게 요청한다.

```text
Analyze this repository, then use archify to create a high-level runtime architecture diagram.
Show 8–12 core components, one primary path, external dependencies, and trust boundaries.
Put supporting detail in cards instead of adding more edges.
```

그다음 “Redis 추가”, “인증을 왼쪽으로”, “롤백 경로 강조”처럼 좁은 요청으로 다듬는다.
저장소 안에서는 CLI로 직접 검증하고 전달할 수 있다.

```bash
cd archify
node bin/archify.mjs doctor
node bin/archify.mjs guide "Show CI/CD checks, approval, deploy, and rollback"
node bin/archify.mjs validate workflow examples/agent-tool-call.workflow.json --quality showcase --json
node bin/archify.mjs deliver workflow examples/agent-tool-call.workflow.json /tmp/workflow.html --quality showcase --open --json
```

결과물은 독립 HTML 파일 하나라, Archify를 설치하지 않은 사람도 브라우저로 열어 상호작용을 그대로 쓸 수 있다.
Archify는 안정 매니페스트를 선택적 알림을 위해서만 GET하며, 업데이트를 내려받거나 설치하지 않는다.
성공한 확인 뒤에는 약 72시간(±20%)을 기다리고, 서버는 IP와 시각 같은 일반 HTTP 메타데이터만 보며, `ARCHIFY_UPDATE_CHECK_DISABLED=1`로 끌 수 있다.

## 분석

### “검증 가능하다”는 말의 범위를 정확히 좁혀 두었다

Archify가 가장 공들인 것은 검증이지만, 그 검증이 무엇을 보증하는지를 여러 곳에서 좁혀 둔다.
스키마, 레이아웃, 경로, 레이블 간격 검사는 다이어그램이 잘 만들어졌다는 것을 보증할 뿐, 다이어그램이 시스템을 맞게 그렸다는 것을 보증하지 않는다.
README는 상호작용이 위상을 지어내거나 런타임 영향을 주장하지 않는다고 쓰고, Architecture Delta가 영향이나 병합 안전성을 추론하지 않는다고 쓰며, 배포 소유 프로필이 실제 인프라를 살펴보지 않는다고 쓴다.

이 선 긋기는 정직하다.
에이전트가 그린 다이어그램에서 가장 흔한 실패는 존재하지 않는 관계를 그럴듯하게 그리는 것인데, Archify는 그 문제를 검증으로 해결한다고 주장하지 않는다.
대신 사실 확인이 필요한 곳에는 `SRC n` 노드를 두어 특정 커밋의 파일과 줄 범위로 연결한다.
구조적 검증은 기계가, 사실 검증은 사람이 원본을 열어 보는 방식으로 나눈 것이다.

### 에이전트를 위한 오류 메시지를 설계한 것이 이 스킬의 핵심 기술이다

“수리 영수증”은 작은 기능처럼 보이지만 설계 철학을 담고 있다.
사람을 위한 도구는 실패하면 스택 추적을 보여 주고, 사람이 그것을 읽고 원인을 찾는다.
에이전트는 스택 추적을 읽고 원인을 추측하다가 엉뚱한 곳을 고치거나 같은 시도를 반복한다.
Archify는 실패를 규칙 코드, 대상, 측정값, 지원되는 수정 방법으로 돌려주고, 에이전트에게 그 수정 방법만 두 번 안에 적용하라고 제한한다.

이것은 에이전트 도구 설계의 일반 원칙으로 읽힌다.
에이전트에게 주는 피드백은 사람에게 주는 피드백보다 더 좁고 더 구조화되어 있어야 하며, 무엇을 할 수 있는지뿐 아니라 무엇만 할 수 있는지를 알려 줘야 한다.
마지막 정상본을 원자적으로만 바꾸는 전달 방식도 같은 원칙이다.
에이전트가 실패해도 사용자가 보는 결과는 깨지지 않는다.

## 비평

### 71,328개의 별에 비해 공개 논의의 흔적이 거의 없다

Archify는 반년 만에 7만 개가 넘는 별을 모았고 GitHub Trending 주간 1위를 내세운다.
그런데 HN에 올라온 스레드는 1점에 댓글 하나였고, 그 댓글도 쓸 만한 아키텍처 도구라는 한 문장이었다.[^soltanov]
Lobste.rs에서는 검색되지 않았다.
README가 드는 인지도의 근거는 제작자의 트렌딩 스크린숏, QbitAI의 소개와 인터뷰, 개발자 커뮤니티의 공유 글이다.

별의 규모와 논의의 규모가 이렇게 어긋나는 경우, 별은 채택의 증거로 읽기 어렵다.
중국어권 커뮤니티에서 퍼졌을 가능성도 충분하고, WeChat과 QQ 그룹 배지가 그 방향을 가리킨다.
그러나 어느 쪽이든 독자가 이 도구의 품질을 판단할 근거는 별이 아니라 README와 Proof Lab이 보여 주는 결과물이다.
README가 후원사 배너와 수상 목록을 사용법보다 앞에 둔 배치는, 그 판단을 별과 평판 쪽으로 끌어당긴다.

### 범위를 “무엇이든”으로 넓힌 것이 검증의 강점을 흐린다

저장소 설명은 소프트웨어 다이어그램 다섯 종류를 말하지만, README 첫머리는 여행 일정과 학습 지도와 법률 인용 점검과 계약 검토까지 말한다.
상하이 시티워크 4일 일정표가 대표 커뮤니티 사례로 크게 실린다.
이 사례들은 Archify의 출력이 확장 가능한 HTML이라는 것을 보여 주지만, 동시에 이 도구의 가장 강한 부분과 거리가 멀다.

Archify의 차별점은 타입이 있는 원본, 검증 게이트, 소스 근거 노드였다.
여행 일정에는 검증할 스키마도, 고정할 커밋도 없다.
README가 그 확장은 커뮤니티 작성자가 그 결과물에만 덧붙인 것이라고 밝히기는 하지만, 범위를 “무엇이든”으로 넓힐수록 “검증 가능한 다이어그램”이라는 약속이 어디까지 해당하는지 흐려진다.

### 레이아웃 판단을 에이전트에게 맡긴 선택은 재현성과 긴장한다

README는 범용 자동 배치 대신 에이전트가 위계와 간격과 경로와 강조를 정한다는 것을 장점으로 든다.
그 결과 다이어그램은 사람이 손으로 그린 것처럼 의도가 담기지만, 같은 설명으로 다시 그리면 다른 배치가 나올 수 있다.
타입이 있는 JSON 원본이 재현 가능하다는 것은 원본이 같으면 결과가 같다는 뜻이지, 같은 설명에서 같은 원본이 나온다는 뜻은 아니다.

에이전트가 이후 요청에서 관계없는 구조를 그대로 둔다는 설명은 이 긴장을 부분적으로 완화한다.
그러나 팀이 같은 시스템을 여러 번 그리거나, 다른 사람이 같은 저장소로 다시 그렸을 때 비교 가능한 결과를 얻으려면 배치의 안정성이 중요하다.
Architecture Delta가 이전과 이후를 비교할 수 있는 것도 두 스냅숏의 원본이 같은 뼈대를 공유할 때뿐이다.

## 인사이트

### 에이전트 다이어그램 도구는 두 갈래로 나뉘고 있다

같은 날 GeekNews에 올라온 [[whiteboard]]와 Archify는 같은 문제, 곧 에이전트가 만든 코드와 시스템을 사람이 이해하게 하는 문제를 다른 방식으로 푼다.
Whiteboard는 데스크톱 앱 안의 캔버스에 에이전트가 그리게 하고, 다이어그램의 노드를 코드로 바로 연결하는 데 힘을 쏟는다.
Archify는 에이전트가 스킬로 독립 HTML을 만들게 하고, 그 HTML이 구조적으로 올바르다는 것을 보증하는 데 힘을 쏟는다.

두 접근은 서로 다른 것을 잃는다.
Whiteboard는 앱에 묶이는 대신 코드와의 연결을 얻고, Archify는 어디서나 열리는 파일을 얻는 대신 코드와의 연결은 요청할 때만 붙인다.
에이전트가 그린 설명이 코드와 어긋나는 문제를 둘 다 완전히 풀지 못했다는 점도 같다.
이 분야의 다음 단계는 두 장점을 합치는 것, 곧 어디서나 열리는 파일이면서 모든 관계가 코드의 실제 호출로 검증되는 다이어그램이 될 것이다.

### 스킬이 패키지 생태계의 모양을 닮아 가고 있다

`npx skills add`로 설치하고, 버전이 있고, 변경 이력과 로드맵이 있고, 업데이트 확인이 있고, 여러 에이전트 도구별 설치 위치가 있다.
Archify는 에이전트 스킬이 프롬프트 한 장에서 소프트웨어 패키지로 자라는 모습을 보여 준다.
번들된 검증기와 CLI가 있는 이상, 이것은 지시문이 아니라 에이전트가 호출하는 프로그램이다.

이 전환은 패키지 생태계의 오래된 문제도 함께 가져온다.
업데이트 확인을 위한 네트워크 호출에 대해 README가 무엇을 보내고 보내지 않는지 길게 설명하는 것은, 사용자가 이미 그것을 물을 만큼 스킬을 소프트웨어로 대하고 있다는 뜻이다.
스킬이 코드와 네트워크 접근을 가진 패키지가 되면, 서명과 공급망 검증과 권한 범위 같은 패키지 관리의 질문이 스킬에도 그대로 적용된다.
71,328개의 별을 가진 스킬이 에이전트 수만 곳에 설치되어 있다면, 그 스킬의 다음 버전은 그 모든 에이전트의 동작을 바꾼다.
