# sprite-gen: 게임용 스프라이트 생성 도구

<https://github.com/aldegad/sprite-gen>

## 소개

sprite-gen은 그림 한 장에서 게임 엔진에 넣을 수 있는 스프라이트를 뽑는
Codex/Claude 스킬이자 파이썬 CLI다.
README의 첫 문장은 한 장의 그림에서 아틀라스 또는 투명한 모션 루프가 나온다는
것이다.

README가 풀려는 문제는 이미지 모델에 스프라이트 시트를 그려 달라고 했을 때
생기는 일이다.
프레임마다 얼굴이 달라지고, 배경이 지워지지 않고,
포즈가 겹치거나 격자에서 벗어나서 게임 엔진이 쓸 수 없는 PNG가 나온다는
설명이다.
sprite-gen은 베이스 이미지 한 장을 받아 행 단위로 생성을 돌리고,
크로마 키 배경을 진짜 알파로 바꾸고,
포즈마다 투명 프레임을 뽑고,
`manifest.json.frame_layout`이 붙은 런타임 아틀라스를 만든다.
같은 그림을 영상 모델에 넘겨 상태마다 끊김 없는 투명 루프를 받는 길도 있다.
생성이 끝내 맞추지 못하는 마지막 10%는 큐레이션 웹뷰에서 사람이 비교하고
거르고 옮기고 재생해 본 뒤 굽는다.

2026년 11월 25일 기준 GitHub API가 알려 준 값은 다음과 같다.
라이선스는 Apache-2.0이고 언어는 Python이다.
저장소는 2026년 5월 12일에 만들어졌고 마지막 갱신은 2026년 11월 21일이다.
별은 4,249개, 포크는 449개, 열린 이슈는 2개다.
패키지 버전은 4.3.0이다.
토픽은 `2d-game`, `ai-tools`, `claude-code`, `codex`, `game-dev`, `gamedev`,
`pixel-art`, `sprite-generation`, `sprite-sheet`이다.

저장소에 홈페이지가 등록되어 있지 않다.
API의 `homepage` 값이 비어 있고, `pyproject.toml`의 URL도 저장소 하나뿐이며,
소유자 프로필의 `blog`도 비어 있다.
README가 가리키는 Steam 페이지는 제작자가 만드는 게임의 위시리스트 안내이고
도구의 사이트가 아니다.
이 문서는 그 페이지를 열어 보지 않았다.
README는 여섯 개 언어판(영어, 한국어, 일본어, 중국어 간체,
스페인어, 프랑스어)이 있고
GitHub 후원 링크를 둔다.

이 문서는 README, `SKILL.md`, `docs/` 일부, `CONTRIBUTORS.md`, `SECURITY.md`,
`pyproject.toml`과 파이썬 소스를 읽어 정리했다.
소스는 영역을 나누어 읽었다.
`gen/`, `frames/`와 `spec/`와 `compose/`, `video/`, `curate/`와 `serve/`와
`effects/`다.
읽은 범위가 좁았던 곳은 본문에 그렇게 적었다.
어떤 코드도 실행하지 않았고 시험도 돌리지 않았으며 이미지나 영상을 생성해 보지
않았다.
따라서 아래의 동작은 코드와 문서를 읽고 얻은 것이고, 산출물의 품질은 확인하지
않았다.
코드 주석에 적힌 실측 수치는 저장소의 자기 보고이며 재현하지 않았다.

## 설치와 시작

설치는 가상환경에서 패키지를 편집 모드로 깐다.
README는 이 가상환경이 지원하는 유일한 인터프리터라고 적는다.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e .
sprite-gen --help
```

스킬로는 Codex의 스킬 설치 스크립트를 쓴다.

```bash
python3 ~/.codex/skills/.system/skill-installer/scripts/install-skill-from-github.py \
  --repo aldegad/sprite-gen --path . --name sprite-gen
```

파이썬은 3.11 이상이고 필수 패키지는 Pillow(`>=13.0.0,<14`)와
NumPy(`>=2.2.6,<3`) 둘이다.
RIFE의 PyTorch 백엔드를 쓸 때만 `torch` 선택 의존성이 필요하다.
외부 바이너리는 `SKILL.md`가 적는다.
`codex`(이미지 생성), `ffmpeg`, `img2webp`, `node`(얼굴 굽기),
`rife-ncnn-vulkan`(루프 보정)이다.
RIFE는 `sprite-gen rife install`로 설치하고 내려받는 zip이 830MB, 남기는 것이
45MB라고 한다.
RIFE가 없으면 걷기와 달리기 루프는 촬영된 그대로 잘리고 경고가 나온다.

자격 증명은 구독 로그인을 먼저 쓰고 API 키는 로그인이 없을 때만 쓴다.
README의 표를 정리하면 다음과 같다.

| 호출                            | 먼저 쓰는 것                 | 로그인이 없을 때                 |
| ------------------------------- | ---------------------------- | -------------------------------- |
| `gen --provider codex`          | `codex`의 ChatGPT 로그인     | (API 키 로그인이면 그 키로 과금) |
| `gen --provider grok`, `video*` | `grok` CLI 로그인            | `XAI_API_KEY`                    |
| `pixel-draw`                    | `claude`(Claude Code) 로그인 | `ANTHROPIC_API_KEY`              |
| `gen --provider openai`         | 없음                         | `OPENAI_API_KEY`                 |

키로 나가는 호출은 호출당 과금이며 요청이 나가기 전에 표준 오류에 그렇게
적는다고 README는 밝힌다.
`openai` 제공자는 서버나 SaaS를 위한 길이고 기본값이 되지 않는다.

## 파이프라인과 도구

README는 `sprite-gen --help`가 같은 지도를 출력한다고 설명한다.
두 개의 스프라이트 파이프라인은 순서가 있는 생성 흐름이고,
도구 묶음은 서로 독립인 명령이며,
장면 만들기는 끝난 자산을 받는 선택 작업이다.

| 구분              | 들어가는 것 → 나오는 것                                                          |
| ----------------- | -------------------------------------------------------------------------------- |
| A · 아틀라스 행   | 그림 한 장과 상태 목록 → `sprite-sheet-alpha.png`와 `manifest.json.frame_layout` |
| B · 영상에서 루프 | 그림 한 장 → 상태마다 끊김 없는 투명 GIF, WebP, 스트립                           |
| C · 유틸리티      | 가져온 이미지나 격자 시트 → 투명 컷, 끝난 아틀라스 → 큐레이션용 런               |
| D · 후처리        | 끝난 시트 → 결정적 색 변형, Aseprite, Phaser, Flame 내보내기                     |
| E · 자산 도구     | 반복 타일, 투영 그림자, 모션과 접지 측정                                         |
| S · 장면          | 기존 자산과 배치, 카메라, 조명 → PNG 프레임, MP4, GIF                            |

파이프라인 A는 다섯 명령이다.

```bash
sprite-gen prepare --out-dir <run> --character-id <id> --base-image base.png
sprite-gen gen-set --run-dir <run> --provider codex
sprite-gen extract --run-dir <run>
sprite-gen compose-atlas --run-dir <run>
sprite-gen curation --run-dir <run>
```

파이프라인 B는 `video-set` 한 명령으로 돌리고,
각 항목에서 `video-canvas`, `video`, `video-frames`, `video-loop` 순서로
진행한다.
영상 MCP를 가진 에이전트가 직접 클립을 만드는 길도 있고,
그때는 `video-prompt`가 프롬프트를 출력하고 `video-frames`와 `video-loop`가
mp4를 받는다.
README는 이 길이 ZCRE의 Grok Imagine 1.5에 끝 프레임이 없어
걷기, 달리기, 점프에만 맞는다고 적는다.
`SKILL.md`는 이 경우 sprite-gen이 MCP를 직접 부르지 않는다고 적는다.

README는 이 밖에 몇 가지 기능을 따로 소개한다.
그림 속 아이템이 몸의 한쪽에 있을 때 뒤집으면 반대편으로 가는 문제를 위한
`--handed`와 `handed-check`가 있다.
제목 로고를 글자 단위로 다시 그려 투명하게 뽑고 철자가 틀리면 거절하는 `logo`가
있다.
Pillow와 NumPy만으로 도는 결정적 색 변형 `recolor`가 있다.
이 문서는 그 기능들의 산출물을 평가하지 않았다.

## 동작 방식

### 모듈 구성

`sprite_gen/`의 파이썬은 142개 파일 64,568줄이고 `tests/`는 280개 파일
79,200줄이다.
두 합계는 이 문서가 직접 다시 세었고 합해서 143,768줄이다.
도메인은 13개이며 `sprite_gen/_modules.py`의 표 하나가 모듈과 도메인의 짝을
정한다.
CLI 동사는 `cli.py`의 `COMMANDS` 딕셔너리에 57개가 등록되고,
각 동사의 도메인은 손으로 적지 않고 `run` 함수가 속한 모듈에서 유도한다.
표에 없는 모듈은 `KeyError`로 실패하므로 동사를 추가하면서 도메인을 빠뜨릴 수
없다.

| 도메인    | 역할                                                 | 줄 수  |
| --------- | ---------------------------------------------------- | ------ |
| `video`   | 캔버스, 프레임, 루프, 세트, 보정, RIFE               | 29,516 |
| `gen`     | prepare, 제공자 셋, gen-set, 영상 호출, pixel-draw   | 10,331 |
| `frames`  | 크로마 제거, 추출, cutout, slice-sheet, unpack-atlas | 8,099  |
| `effects` | breathe, 해부 분석, recolor, shadow, 보간            | 3,852  |
| `qa`      | 점검, 점수, 모션, 같은 프레임 검출, 보정 루프        | 2,515  |
| `serve`   | 큐레이션 웹뷰와 구성 캔버스의 서버                   | 2,351  |
| `spec`    | 실행 폴더 입출력, 자산 어댑터, 레이아웃              | 1,945  |
| `compose` | 아틀라스, 사이클, GIF, Aseprite와 PNG 내보내기       | 1,124  |

`frames`, `spec`, `compose`의 합 11,168줄은 노트의 값이고 나머지 도메인 줄 수도
같은 출처다.
가장 큰 파일은 `frames/extract.py`가 3,983줄이다.
`video/sway.py`가 3,928줄이고 `video/loop.py`가 3,889줄이다.
`sprite_gen/video/`는 `.py`가 49개이며 이 중 `.mjs`가 별도로 2개다.

진입점은 `pyproject.toml`의 콘솔 스크립트 `sprite-gen =
“sprite_gen.cli:main”`이고
`python -m sprite_gen.cli`도 같은 `main`이다.
`main`은 UTF-8 출력 설정, 파서 생성, 인자 해석, 옛 이름 확인, `run(**kwargs)`
호출 순서다.
옛 동사 이름 `video-follow`와 `video-follow-inspect`는 별칭으로 남아
각각 `video-sway`와 `video-sway-inspect`로 간다.
`scripts/`의 파이썬 파일은 같은 동사를 부르는 얇은 호환 래퍼로 남아 있다고
`pyproject.toml` 주석이 적는다.

종료 코드는 동사마다 다르다.
`workflow` 동사는 준비되면 0, 아니면 2다.
`gen-set`은 실패한 항목이 있으면 1이다.
codex를 쓸 수 없을 때 “묻는다”를 고른 호출은 75로 끝난다.
`SystemExit("메시지")` 형태의 오류는 표준 파이썬 동작상 1이다.

### 제공자와 호출 방식

이미지 제공자는 codex, grok, openai 셋이고 호출 방식이 모두 다르다.

codex는 서브프로세스다.
`codex exec --json --sandbox workspace-write --skip-git-repo-check --color
never`에
`--add-dir`로 생성 이미지 폴더를 더해 부르며, 인자는 리스트로 넘기고 프롬프트는
표준 입력으로 보낸다.
결과 PNG는 모델이 알려 준 경로에서 읽지 않는다.
codex 세션의 rollout jsonl에 들어 있는 인라인 base64를 풀어서 얻는다.
rollout 파일이 둘 이상이면 수정 시각으로 고르지 않고 실패한다.
기본 동작은 쓴 rollout 파일을 지우고 `--keep-session`일 때만 남긴다.
이 코드는 키나 토큰을 읽지 않는다.
`codex login status`를 15초 제한으로 실행해 종료 코드 0이면 로그인으로 보고,
출력에 `chatgpt`가 있으면 구독, 없으면 API 키 로그인으로 판정한다.

grok과 openai는 SDK 없이 `urllib`로 보내는 HTTP 호출이다.
grok은 `https://api.x.ai/v1`의 `/images/generations`와 `/images/edits`를 부르고
기본 모델 문자열은 `grok-imagine-image-2.0`이다.
grok 로그인 파일 `~/.grok/auth.json`이 있으면 그 파일의 `key`를 토큰으로 쓰고,
파일이 아예 없을 때만 `XAI_API_KEY`를 쓴다.
파일이 있는데 깨졌거나 만료되었으면 키로 넘어가지 않고 실패하며,
만료된 토큰을 이 도구가 갱신하지 않는다.
openai는 `/images/generations`(JSON)와 참조 이미지가 있을 때
`/images/edits`(multipart)를 부르고
키는 `OPENAI_API_KEY` 하나뿐이다.
openai는 기본 제공자가 될 수 없어서 `SPRITE_GEN_DEFAULT_PROVIDER=openai`는
거부된다.

세 제공자 모두 키를 명령줄 인자에 싣지 않고 HTTP 헤더에만 싣는다.
오류 본문은 보여 주되 `sk-`와 `xai-`로 시작하는 긴 문자열과 `Bearer` 토큰, URL
질의 문자열을 가리고,
요청에 쓴 자격 증명이 8자 이상이면 그 값 자체도 가린다.

과금 알림은 코드에 있다.
`announce_api_billing`이 요청을 보내기 전에 호출당 과금이라는 문구를 표준 오류로
한 줄 출력한다.
openai, 키 경로의 grok, API 키로 로그인된 codex, 키 경로의 pixel-draw가 이를
호출한다.
알리기만 하고 사용자 확인을 받지는 않는다.
확인을 요구하는 쪽은 안내 동사 `workflow`의 `--confirm-api-billing`이다.

codex를 쓸 수 없을 때의 흐름도 코드에 있다.
`--provider`를 주지 않은 호출이 codex를 못 쓰면 `sprite-gen ask
codex-unavailable:` 뒤에
JSON 한 줄(`cause`, `reason`, `question`, `choices`)을 표준 오류에 쓰고 종료
코드 75로 끝난다.
이때 아무것도 생성하지 않는다.
`SKILL.md`는 에이전트가 이 질문에 스스로 답하거나 제공자를 바꾸지 말고
사용자에게 물으라고 지시한다.
선택은 환경 변수 `SPRITE_GEN_CODEX_UNAVAILABLE`, 저장된 설정, 기본값 `ask`의
순서로 읽는다.
저장은 `defaults save --codex-unavailable <값>`이며
README 표기와 달리 `--expected-revision`을 함께 줘야 한다.
설정 파일은 `~/.config/sprite-gen/preferences.json`이고
쓰기는 잠금과 revision 비교 뒤 원자적 교체로 이루어진다.

### 프롬프트 조립과 키 색

`prepare`는 출력 폴더가 비어 있지 않으면 `--force` 없이는 거부한다.
`sprite-request.json`, 상태별 `prompts/<상태>.txt`와
`references/layout-guides/<상태>.png`, 빈 `raw/`와 `frames/`를 만든다.
기본 상태는 idle, attack, jump, wave이고 모두 4프레임이며 fps는 4, 8, 8, 6이다.
셀 기본은 256이고 안전 여백 비율 기본은 0.094다.

행 프롬프트는 f-string 템플릿이 조립한다.
캐릭터 설명, 스타일 계약, 앵커 잠금, 상태별 요구, 투명과 아티팩트 금지 규칙,
정확히 N프레임, 레이아웃 가이드 설명, 평면 순색 키 배경, 안전 여백이 들어간다.
레이아웃 가이드 이미지는 PIL로 그린다.
`gen/prompt_parts.py`의 `Prompt` 클래스는 호출자의 텍스트를 고치지 않고
방향, 손잡이, 키 배경 같은 엔진 문장 조각을 뒤에 덧붙인다.
호출자 텍스트가 옵션과 반대로 말하면 `notes`로 경고하고 그대로 보낸다.

키 색은 `prepare --chroma-key auto`가 정한다.
후보는 자홍 `#FF00FF`, 초록 `#00FF00`, 청록 `#00FFFF`, 파랑 `#004DFF` 넷이다.
베이스 이미지의 피사체 픽셀과 각 후보의 색 거리를 재고,
거리를 정렬해 하위 1 퍼센타일 값으로 순위를 매긴다.
모든 피사체 픽셀이 96.0보다 먼 후보가 있으면 그중 최고를 고르고,
없으면 순위로만 고른 뒤 경고한다.
동점이면 목록의 앞쪽, 곧 자홍이 이긴다.
`gen`의 `--chroma-key`는 자홍과 초록 중 하나이고 자동 선택 코드가 없다.

`gen-set`은 상태 행마다 자식 프로세스 `python -m sprite_gen.cli gen`을
`ThreadPoolExecutor`로 돌린다.
병렬 수의 기본값은 `DEFAULT_CONCURRENCY = 6`이다.
코드 주석은 2026년 8월에 6개 동시 요청에서 제공자의 제한이 없었다고 적는다.
행의 완성 기준은 보고서다.
읽히는 보고서와 디코딩되는 이미지가 둘 다 있어야 기존 행을 재사용하고,
실패하면 이미지와 보고서를 지워 다음 실행이 다시 만들게 한다.
방향 계약이면 앵커 단계를 먼저 돌리고 하나라도 실패하면 행 단계를 시작하지
않는다.

### 크로마 키 제거

README는 추출기가 배경을 벗기지(peel) 않고 언믹스(unmix)한다고 주장한다.
코드는 이 주장과 맞는다.
`frames/extract.py`에는 `peel`이라는 함수가 없고 그 단어는 인자 도움말 하나에만
남아 있다고 노트는 적는다.
기본 경로는 RGB 공간의 `remove_chroma_background`이고 단계는 다음과 같다.

1. 하드 컷. 선언된 키 색까지의 유클리드 거리가 문턱 이하이거나 알파가 0인 픽셀을
지운다.
   문턱 기본값은 `DEFAULT_KEY_THRESHOLD = 96.0`이다.
2. 칠해진 배경색 보정. 생성기가 `#00FF00`을 어둡게 칠하는 일이 있어서
   모서리와 테두리 표본에서 키 계열 픽셀의 가장 흔한 색을 찾고,
   표본의 12% 이상일 때만 선언된 키 대신 채택한다.
3. 부분 알파 언믹스. 혼합 모델은 `관측 = (1-k)*피사체 + k*키`이다.
   키 틴트 점수는 키 채널 평균에서 비키 채널 평균을 뺀 값이고,
   픽셀을 지워진 것, 피사체, 대역 안 혼합, 대역 밖 혼합 네 부류로 나눈다.
   경계 문턱 기본값은 `--fringe-key-threshold 180.0`, `--fringe-delta 18.0`이다.
4. 번짐 제거. 언믹스 뒤에도 남은 틴트 픽셀을 8-연결 군집으로 묶고,
   군집이 `max(32, 피사체 수 × 비율)` 이하이고 최대 틴트가 40.0을 넘으면
   알파는 두고 색만 보정한다.

선택적 다섯째 단계인 `decontam.py`는 가장자리 픽셀을
`관측 = 알파 × 팔레트 색 + (1 - 알파) × 국소 배경`으로 설명한다.
팔레트는 피사체 안쪽에서 학습한 32색이고 5비트 양자화 히스토그램 위의 k-means를
10회 돈다.
시드는 가중 최원점 탐욕법이라 무작위가 없다.
채도가 높은 피사체(빨간 머리카락과 초록 키)의 경계를 올리브나 주황으로 잘못
복원하는 문제를
막으려는 것이라고 모듈 설명이 적는다.
기본은 꺼짐이고 `video-frames`와 `video-set`에서는 자동으로 켜진다고 문서가
말한다.
YCbCr 경로는 옵트인이다.

`cutout`은 모서리 색으로 길을 고른다.
흰색이나 밝은 무채색이면 위치 기반 매트, 자홍과 초록이면 위 크로마 엔진을 그대로
재사용,
그 밖의 단색이면 `measured_matte`다.
`--white-check`라는 이름은 오해를 부른다.
`cutout`의 이 옵션은 흰 판이 아니라 청록, 자홍, 노랑 세 판에 합성한 PNG를 쓴다.
사람이 눈으로 보는 용도이고 자동 합격 판정이 아니며,
자동 검사는 따로 알파 0인데 RGB가 0이 아닌 픽셀이 있으면 멈추는 코드가 맡는다.
진짜 흰 판에 합성하는 쓰기는 `gen/chroma.py`에 있다.

### 프레임 추출과 정렬

행의 프레임 분할은 기본이 연결 성분이다.
알파가 16을 넘는 픽셀을 4-연결로 묶고,
가장 큰 성분 면적의 20%(최소 120)를 시드 문턱으로 삼는다.
프레임 수를 못 채우면 그 행은 막히고,
슬롯을 균등 분할하는 대체는 `--allow-slot-fallback`을 줄 때만 켜진다.
포즈가 서로 붙은 경우의 분리는 `segment.py`가 맡고 요청에서 `projection`을
골랐을 때만 켜진다.
열별 알파 질량을 평활해 포즈 런을 찾고 동적 계획법으로 절단선을 고른다.

정렬 기본값은 `align_x = foot-centroid`, `align_y = bottom`이다.
`align_y`가 `bottom`이면 프레임마다 바닥 기준선에 접지한다.
행 전체에는 단일 축척 하나를 적용해서 소품이 뻗은 포즈 하나만 줄어드는 일을
막는다.
프레임 사이 정합은 상체 65%의 알파 겹침을 최대화하는 정수 이동을
가로 8, 세로 3 안에서 완전 탐색한다.

픽셀 아트용 격자 감지는 `detect_pixel_pitch`가 후보 피치 2부터 48까지에서
색 경계가 격자선 근처에 모이는 정도에서 우연 기대치를 뺀 점수를 비교한다.
최고점이 0.2 미만이면 스냅하지 않는다.
README의 Backbone Lattice는 이 행 전체의 합의 격자를 가리키며,
소스 전체에서 `backbone`이라는 단어는 `frames/extract.py`에 한 번 나온다고
노트는 적는다.
정의는 `docs/pixel-unfake.md`에 있다.
`gen/pixel_grid.py`는 이것이 아니라 pixel-draw가 모델의 답을 해석하는 격자
파서다.

추출은 실행 폴더 쓰기 잠금을 잡고 `frames/`와 `extract-failure.json`을
하나의 `publish_guard` 아래에서 한 번에 교체하며,
예외가 나면 둘 다 이전 상태로 되돌린다.
프레임은 원본과 요청과 엔진의 파생 캐시이고 캐시 키는 `engine_revision()`이다.
이는 `extract.py`, `spec/layout.py`, `frames/decontam.py` 세 파일의 SHA-256 앞
12자다.
엔진이 바뀌면 `heal_run`이 낡은 행을 원본에서 다시 만든다.

### 아틀라스와 manifest

`compose-atlas`는 낡은 프레임을 복구하고, 잠금을 잡고, 프레임 목록이 정상일 때만
진행한다.
아틀라스의 가로는 `columns × cell_width`이고 세로는 `상태 수 × cell_height`이며
`columns`는 각 상태의 고유 인스턴스 수의 최댓값이다.
같은 원본 프레임, 변형, 픽셀 편집, 호흡 위상으로 구워지는 인스턴스는 셀 하나를
공유한다.
`frame_layout`은 `sheetWidth`, `sheetHeight`, `cellWidth`, `cellHeight`,
`rows`를 가지며
`rows.<상태>`는 재생 순서의 절대 사각형 `{x, y, w, h}` 목록이다.
`animation` 쪽에는 상태마다 `row`, `frames`, `fps`, `durations_ms`, `loop`,
`frame_variant`가 있다.
엔진은 격자를 추측하지 않고 이 사각형을 읽으면 된다.
`export_aseprite`는 `loop`을 내보내지 않는다고 노트는 적는다.

### 실행 폴더 계약과 잠금

`sprite-request.json`이 숫자의 단일 출처이고 `curation.json`은 사람이 고른 것을
담는 사이드카다.
쓰는 단계는 `.sprite-gen.lock`을 잡는다.
README와 `docs/architecture.md`는 한 폴더에 작업자 하나라는 규칙을 이 잠금으로
강제한다고 설명한다.
노트의 코드 읽기에 따르면 잠금은 기다리지 않고 즉시 실패하고, 낡은 잠금의 기준은
900초이며,
읽기와 게시를 나누는 rwlock에는 시간 제한이 없다.
Windows 쪽은 `LockFileEx` 백엔드가 있다.
`curation.json`은 이 잠금 밖에서 원자적으로 쓰이고,
다시 가져오기(`--force`) 게시와는 별도의 rwlock으로 직렬화된다.
큐레이션 저장 요청이 되돌려 보낸 실행 세대(`runRevision`)가 다르면 거절되므로,
낡은 자동 저장이 새로 가져온 런의 프레임에 옛 선택을 적용하지 못한다.

### 영상 파이프라인

`video-canvas`는 상태마다 캔버스 모양을 `STATE_CANVAS` 표 하나에서 정한다.
점프는 3:4의 세로 캔버스에 위쪽 여유 0.34다.
공격은 16:9 가로 캔버스에 위 0.20, 앞 0.28, 뒤 0.2를 비운다.
걷기, 달리기, idle은 정사각형이고, 옆모습 걷기와 달리기는 실루엣의 여유를 읽어
모자라면 가로를 부족분만큼 넓힌다.
네 모서리 색이 한 색이 아니면(채널 편차 24 초과) 입력을 거부한다.
코드 주석은 Grok Imagine이 이미지-영상 요청에서 `aspect_ratio`를 무시하고
입력 이미지의 틀을 유지한다고 적는다.

영상 호출은 grok CLI가 아니라 `api.x.ai/v1`에 대한 직접 HTTP다.
`POST /videos/generations`(그리고 `/videos/extensions`, `/videos/edits`)로
제출하고
`GET /videos/{request_id}`로 4초 간격 폴링하며 전체 마감은 기본 600초다.
기본 모델은 `grok-imagine-video-1.5`, 길이는 1에서 15초, 해상도는 480p, 720p,
1080p이고
요청 본문에 fps가 없으며 끝 프레임(`last_frame`)을 지원한다.
`video-set`은 기본 3초, 공격은 2초로 만든다.
이미 수락된 요청을 새로 제출하면 중복 과금이므로 폴링이 실패해도 같은
`request_id`로 다시 묻는다.
받은 바이트의 4번째부터 8번째가 `ftyp`인지로 mp4를 확인하고 API 상태 문자열은
믿지 않는다.

루프 지점은 클립 자체의 주기로 찾는다.
각 프레임을 96×96으로 줄이고 알파를 곱한 RGBA를 펼쳐
프레임 쌍의 평균 절대차 행렬 `D[i][j]`를 만든다.
주기 프로파일은 `prof[L] = mean(D[j, j+L])`(2칸 간격 표본)이고
후보 L은 양옆보다 작은 지역 최소다.
가장 깊은 최소의 1.15배 이내에서 가장 작은 L을 주기로 고른다.
주기성 점수 `(프로파일 평균 - prof[주기]) / 프로파일 평균`이 0.15 미만이면
주기가 없다며 거부한다.
이음새는 주기 L-1, L, L+1과 시작점마다 `|log(이음새 거리 / 안쪽 거리)|`가 가장
작은 곳이다.
거리 대신 로그 비율을 쓰는 이유를 주석은 같은 포즈가 반복되는 정지를 보상하지
않기 위해서라고 적는다.
걷기의 후보 범위는 프레임 비율이 아니라 초 단위(0.5에서 1.6초)로 정한다.
주석은 걸음 주기가 몸의 사실이지 클립 길이의 함수가 아니기 때문이라고 설명한다.
주기가 한 걸음 길이로 보이면 두 배 부근의 반복을 찾고,
없으면 반걸음이라며 다시 만들라고 거부한다.

`period.py`는 주기의 2분의 1, 3분의 1이 같은 모션 경로로 돌아오는지 재어
의심으로 기록만 하고 자르지는 않는다.
RIFE는 점프 프레임 수리, 같은 그림이 반복되는 셀의 채우기, 방향이 여럿인 세트의
주기 맞춤
(`video-cycle-align`)에 쓰인다.
`rife_install.py`는 zip의 SHA-256을 코드에 고정해 압축을 풀기 전에 검증하고
압축 멤버의 경로를 걸러낸다고 노트는 적는다.
`loop.py`의 스트립 상한은 64셀, 폭 32,000px, 높이 520px이다.

### Breathe

Breathe는 한 프레임을 자르거나 붙이지 않고 스프라이트 전체에 연속 변형장 하나를
건다.
강도는 목 아래에서 0으로 줄어들어 강체 구간은 항등이라 프레임 사이에 비트 단위로
같다.
파형은 `0.86*sin(2πt) + 0.14*sin(4πt)`이고 세로는 행의 정수 복제와 삭제,
가로는 밀도의 적분(`np.cumsum`)에서 만든 단조 사상이다.
격자를 벗어나는 연산이 없어서 같은 입력이면 같은 출력이라는 것이 모듈의
주장이다.
변형 결과가 셀 밖으로 나가면 조용히 자르지 않고 멈춘다.
해부(목, 얼굴, 부속)는 프레임마다 재지 않고 기준 프레임 하나로 줄 전체의 한 벌을
확정한다.
파이썬 구현과 같은 결과를 큐레이터 JS가 내야 해서
`tests/effects/test_breathe_js_mirror.py`가 미러를 지킨다.

### 큐레이션 서버

`serve_curation.py`는 표준 라이브러리의 `ThreadingHTTPServer`이고
기본 `--host`는 `127.0.0.1`, `--port`는 0(빈 포트)이며 기본으로 브라우저를 연다.
`/api` 경로는 GET이 `run`, `op-progress`, `anchor`, `breathe-anatomy`,
`base-grid`, `progress`와 다운로드이고
POST가 `curation`, `compare-gif`, `compose`, `base-edit`, `state-fps`,
`interpolate`, `reroll`, `export`, `export-gif`다.
경로 이탈은 `_safe_path`가 `resolve()` 뒤 `relative_to`로 막아 403으로 답한다.
프런트엔드는 번들러 없이 클래식 `<script>`를 의존 순서로 나열한다.
큐레이터 JS가 28개, 구성 캔버스 JS가 8개이고 외부 CDN 호출은 없다.
이 서버의 보안 표면은 비평에서 다룬다.

### 오류 처리와 재시도

재시도 규칙은 `gen/retry.py` 한 곳에 있다.
POST는 제공자가 요청을 받지 않았다고 문서화한 응답에서만 다시 보낸다.
Anthropic은 429, 500, 529, OpenAI는 429와 503, xAI는 429다.
돈을 더 내야 하는 응답(예를 들어 `insufficient_quota`)은 다시 보내지 않는다.
대기는 `retry-after`(120초 이하일 때만) 또는 `min(4.0 × 2^실패 수, 60.0)`이며
`ASKS_AGAIN = 2`라서 한 호출은 최대 세 번 전송된다.
연결이 끊겨 답이 없는 요청은 서버가 받았을 수 있다고 보고 다시 보내지 않는다.
이미지 호출의 시간 제한은 기본 180초이고 코드 주석은 정상 최장 129초 실측에서
정했다고 적는다.

### 의존성과 시험

`SECURITY.md`는 런타임 의존성이 Pillow와 NumPy 둘이며
둘 다 직접 선언해야 하고 전이 의존에 기대면 안 된다고 적는다.
NumPy의 순수 파이썬 대체 구현은 금지한다.
추출 경로가 바이트 동일성 계약을 가지며 이는 NumPy 2.0의 NEP 50 승격 규칙에
의존하기 때문이라고
`pyproject.toml` 주석이 설명한다.
`_deps.py`는 NumPy를 가져오는 유일한 모듈이고 없으면 설치 명령을 담은 오류로
일찍 멈춘다.

시험은 `tests/` 아래 280개 파일, 79,200줄이다.
영역별 규모는 `tests/video` 116개 파일 35,796줄, `tests/gen` 41개 13,809줄,
`tests/frames` 30개 6,377줄, `tests/spec` 8개 2,312줄,
`tests/packaging` 12개 3,014줄이다.
시험이 지키는 것은 기능만이 아니라 계약과 문서이기도 하다.
`test_cli_taxonomy.py`는 모든 동사가 정확히 한 도메인에 속하고 `--help`에 한
번씩 나오는지,
`test_floor_python_grammar.py`는 하한 파이썬(3.11)이 패키지의 모든 파일을
읽는지,
`test_text_encoding.py`는 인코딩을 이름 짓지 않은 텍스트 입출력이 없는지,
`test_project_metadata.py`는 README의 파이썬 문구와 `requires-python`과 리눅스
레인의 고정 버전이 맞는지를 본다.
`test_codex_unavailable.py`는 codex를 못 쓸 때 종료 코드 75가 나오고
표준 출력이 비어 있고 출력 파일이 없는지까지 확인한다.
이 문서는 시험을 하나도 실행하지 않았으므로 통과 여부는 모른다.

### 저장소 운영

`.github`에는 `FUNDING.yml`만 있고 워크플로가 없다.
`docs/release.md`는 변경을 올릴 때마다 도는 CI가 없다고 직접 적는다.
시험 게이트와 wheel, sdist 빌드는 `scripts/linux_lane.sh`가 하고,
메인테이너가 시험할 버전을 지정해 손으로 시작하는 워크플로가
별도 저장소 `aldegad/sprite-gen-lane`의 GitHub 호스트 러너(ubuntu x86-64)에서
돌린다.
RIFE의 PyTorch 백엔드용 CUDA 게이트는 메인테이너의 NVIDIA 호스트에서
`scripts/cuda_lane.py`로 돈다.
`CHANGELOG.md`는 822KB이고 버전 제목이 95개다.
`CONTRIBUTORS.md`는 외부 기여를 사람별로 적고, 병합되지 않은 제안도
그 벤치마크가 실제 파이프라인 비교를 이끌어 기본값 96을 확인했다는 식으로
기록한다.
`SECURITY.md`는 의존성 추가 전에 `safedeps check`로 어드바이저리를 조회하고
저장소의 비밀 스캔 훅을 쓰라고 안내한다.
취약점 신고 창구는 이 파일에 없다.

## 분석

### 에이전트가 한 단계만 맡는 파이프라인

설계의 중심은 생성 모델을 한 단계에 가두는 것이다.
README와 아키텍처 문서는 `gen`과 `gen-set`이 유일한 AI 단계라고 설명하고,
키 제거, 프레임 분할, 정렬, 아틀라스 합성, 루프 선택은 모두 측정으로 정해진다.
코드에서도 이 구분이 보인다.
키 제거의 문턱은 96.0, 경계 문턱은 180.0 같은 상수이고,
정렬은 상체 65%의 겹침을 정수 이동으로 탐색하며,
루프 지점은 프레임 쌍 거리 행렬의 지역 최소와 주기성 0.15로 정해진다.
모델의 출력이 불안정해도 후단이 같은 입력에 같은 바이트를 내는 것이 목표이고,
NumPy를 직접 선언하고 순수 파이썬 대체를 금지한 이유도 이 바이트 동일성
계약이다.

### 아틀라스 길과 영상 길

두 길은 같은 그림을 다른 가정으로 다룬다.
아틀라스 길은 모델에게 한 행을 정해진 프레임 수로 그리게 하고 그 프레임을
뽑는다.
영상 길은 모델이 만든 움직임의 주기를 거리 행렬로 측정해 자른다.
앞의 길은 프레임이 닮지 않을 위험이 있고 뒤의 길은 주기가 흐릴 위험이 있다.
영상 길의 코드는 그 위험에 대한 방어로 가득하다.
반걸음 거부, 의심 주기 기록, 이음새 문턱, 같은 그림 반복 채우기가 그렇다.
README가 영상 길을 `video-set` 한 명령으로 감싸면서도
`docs/video-pipeline.md`가 197KB, `docs/loop-repair.md`가 377KB에 이르는 이유가
여기에 있다고 본다.

### 에이전트를 사용자로 가정한 인터페이스

CLI는 사람이 아니라 에이전트가 부를 것을 전제로 짜여 있다.
`workflow`는 읽기 전용으로 상태(`ready`, `needs-input`, `blocked`)와 질문을
JSON으로 내놓고,
`capabilities`는 모든 동사와 인자와 과금 제공자를 한 줄 JSON으로 낸다.
codex를 못 쓸 때는 종료 코드 75와 구조화된 질문 한 줄로 멈추고 에이전트가
사용자에게 묻게 한다.
`SKILL.md`는 질문 문구와 “스스로 답하지 말 것”이라는 지시를 함께 적는다.
돈이 드는 선택을 에이전트가 대신하지 못하게 하는 장치가 프로토콜 수준으로
구현되어 있다.

## 비평

### README와 코드가 어긋나는 곳이 있다

README와 문서의 주장을 코드와 대조한 결과 대부분은 맞았지만 세 건이 어긋났다.
첫째로 README는 `gen-set`이 한 번에 4행씩 돈다고 적는데(`README.md`의 주석과
한국어판)
코드의 기본값은 `DEFAULT_CONCURRENCY = 6`이고 `docs/gen.md`도 6이다.
이 문서가 직접 `gen_set.py`와 README를 다시 읽어 확인했다.
4가 어디서 온 숫자인지는 확인하지 못했다.
둘째로 `SECURITY.md`는 NumPy의 하한이 CPython 3.10 호환을 위해서라고 적지만
`pyproject.toml`은 `requires-python = ">=3.11"`이고 그 주석은 더 오래된 파이썬을
버려도
NumPy를 올릴 필요가 없다고 달리 적는다.
셋째로 `docs/pixel-unfake.md`는 `align_y`의 기본값을 `center`라고 적지만
코드 기본값은 `bottom`이다(`extract.py`에서 확인).
셋 모두 사용자가 문서를 믿고 따랐을 때 틀린 값이 되는 종류다.
`test_project_metadata.py`가 README의 파이썬 문구를 시험으로 묶어 둔 것과
대비되는데,
같은 방식으로 병렬 수와 정렬 기본값도 시험에 묶을 수 있다.

### 로컬 도구로서의 보안 표면

노트의 코드 읽기에서 위협 모델이 신뢰된 로컬 환경이라는 해석이 필요한 부분이
있다.
이 문서는 서버를 실행하지 않았으므로 아래는 코드 읽기에서 보이는 사실이고 악용
가능성은 추론이다.

- 큐레이션 서버와 구성 캔버스 서버에는 토큰, `Origin`, `Host` 검사와 CORS 헤더가
없다.
기본 바인딩은 `127.0.0.1`과 임의 포트이지만 `--host`를 막거나 경고하는 코드는
찾지 못했다.
POST 본문의 크기 상한도 없고 개수 제한은 `compare-gif`의 프레임 1에서 200개와
fps 1에서 30뿐이다.
- 구성 캔버스의 `POST /api/mount`는 클라이언트가 준 임의 디렉터리를 연다.
  이후의 탐색은 마운트 뿌리 안으로 가두지만 첫 마운트 자체에는 제한이 없다.
- `SPRITE_GEN_{OPENAI,XAI,ANTHROPIC}_BASE_URL`을 설정하면 해당 제공자의 키와
grok 로그인 토큰이
  그 주소로 가고 `http://`도 허용된다.
  `docs/gen.md`가 이 점을 직접 경고한다.
- 영상 클립 다운로드는 먼저 토큰 없이 받고, 401이나 403이면 같은 URL에
`Authorization: Bearer`를 붙여 다시 받는다.
  제공자가 준 URL의 호스트를 검사하는 코드를 읽은 범위에서 찾지 못했다.
- `SPRITE_GEN_RIFE_EXECUTOR`는 `module:attr` 문자열을 `importlib`로 가져온다.
  환경 변수를 제어하는 쪽이 코드를 실행시킬 수 있다는 뜻이다.
- codex 자식 프로세스는 부모에 설정된 다른 제공자의 키 환경 변수를 그대로
상속한다.
- `unpack_atlas` 매니페스트의 아틀라스 이름, `layout.py`의 상태 이름, 자산
서술자 파일명에는
  경로 포함 검사가 보이지 않는다.
  픽셀 수 상한은 `MAX_SOURCE_PIXELS = 67,108,864` 하나다.

반대로 잘 처리된 곳도 있다.
모든 서브프로세스 호출은 리스트 인자이고 `shell=True`가 없다.
키는 명령줄에 실리지 않고 오류 출력에서 가려진다.
RIFE 설치는 zip의 해시를 코드에 고정한다.

### 수치와 주장의 상당수가 저장소의 자기 보고다

코드 주석에는 날짜가 붙은 실측이 많다.
6개 동시 요청에서 제한이 없었다는 것, 참조 이미지가 있을 때 투명 생성의 native가
1/6, chroma가 6/6이었다는 것,
Grok이 `aspect_ratio`를 무시한다는 것, 옆모습 걷기가 주기 28 대신 39를 골랐다는
것이 그 예다.
이런 주석은 결정의 이유를 남기는 좋은 습관이지만 외부 시점에서는 확인할 수 없는
주장이다.
README의 hero GIF 설명도 같다.
이 문서는 산출물을 생성해 보지 않았고,
README가 말하는 캐릭터들이 한 장의 그림에서 나왔다는 설명도 확인하지 못했다.

### 문서의 양과 외부 모델 의존

`CHANGELOG.md`가 822KB, `docs/loop-repair.md`가 377KB다.
한 항목의 길이가 매우 길어서(맨 위 항목은 업그레이드 주의만 한 문단이다)
README만 읽는 사용자가 알아야 할 제한이 그 안에 묻히기 쉽다.
또 모델 이름과 서비스 동작(`grok-imagine-video-1.5`, `gpt-image-2.5-flare`,
제공자별 오류 코드 표)이
코드에 상수로 들어 있어서 제공자가 바꾸면 도구가 깨진다.
CI가 없는 구조라 그 깨짐은 메인테이너가 손으로 레인을 돌릴 때 드러난다.

## 인사이트

### 모델 앞에 질문을 세우는 종료 코드

종료 코드 75는 실패가 아니라 질문이라는 약속이다.
에이전트가 자기 판단으로 제공자를 바꾸면 과금이 달라지므로,
코드가 생성 전에 멈추고 구조화된 질문을 내보내며 `SKILL.md`가 답하는 쪽은
사용자라고 적는다.
같은 패턴은 돈이 드는 모든 도구에 일반화된다.
되돌릴 수 없는 비용 앞에서 에이전트가 선택하지 못하게 하려면 지시문이 아니라
프로세스의 종료 상태로 막는 것이 안정적이다.
다만 이 방어는 에이전트가 종료 코드를 읽는다는 전제 위에 있다.

### 결정적 후단이 만드는 시험 가능성

생성 단계를 가두면 나머지가 같은 입력에 같은 출력을 내는 순수 함수에 가까워진다.
그래서 79,200줄의 시험이 골든 파일과 바이트 동일성, 파이썬과 JS 미러의 일치를
지킬 수 있다.
이는 AI가 낀 파이프라인을 유지보수하는 현실적인 방법이다.
모델이 바뀌면 입력이 달라지지만 후단은 그대로이므로,
어느 쪽이 변했는지를 가를 기준이 남는다.
한편 키 제거의 문턱 96.0이 외부 기여자의 벤치마크에서 80을 제안받고도 실제
파이프라인 비교로 유지되었다는
기록은, 오프라인 합성 벤치마크가 실제 생성물 분포를 대표하지 못할 수 있다는
교훈이다.

### 주석에 남은 측정이 도구의 지식이 된다

이 저장소는 일화적 실패를 날짜가 붙은 실측과 함께 상수 옆 주석에 남긴다.
반걸음 문제, 3초 클립의 걷기 판정, 투명 생성의 성공률이 그렇다.
이는 모델 서비스처럼 동작이 문서화되지 않은 대상 위에서 도구를 만들 때
조사한 지식을 코드가 가지게 하는 방식이다.
위험은 서비스가 바뀌면 주석이 낡은 사실로 남는다는 점이다.
날짜가 붙어 있어 낡았음을 알아볼 수 있다는 것이 그나마의 안전장치다.

### 자기 문서를 시험으로 묶는 범위

`test_project_metadata.py`는 문서의 한 문장을 코드의 값에 묶는다.
이 방식이 병렬 수 4와 6, `align_y`의 center와 bottom 같은 불일치를 막았을
것이다.
문서의 모든 수치를 묶는 것은 비현실적이지만,
사용자가 그대로 따라 하는 기본값과 종료 코드와 명령 형식에는 같은 처리를 할
값어치가 있다.
