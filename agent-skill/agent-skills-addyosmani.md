# Agent Skills - Addy Osmani의 프로덕션급 AI 코딩 에이전트 스킬 모음

<https://github.com/addyosmani/agent-skills>

HN 토론: <https://news.ycombinator.com/item?id=48015397> (376점, 212개 댓글)

GN 토론: <https://news.hada.io/topic?id=28294>

## 요약

Google Cloud AI 디렉터 Addy Osmani가 공개한 오픈소스 프로젝트로, AI 코딩 에이전트가
스펙·테스트·보안 리뷰를 건너뛰는 문제를 해결하기 위해 엔지니어링 스킬을
제공한다. 개발 사이클 6단계(정의 → 계획 → 구축 → 검증 → 검토 → 배포)에 걸쳐
9개의 슬래시 명령어(`/spec`, `/plan`, `/build`, `/test`, `/constraints`,
`/review`, `/webperf`, `/code-simplify`, `/ship`)로 자동화된 워크플로우를 구성한다.
`/build auto`는 계획 수립과 구현을 한 번에 자동으로 처리한다.

프로젝트는 25개 스킬(메타 1, 정의 4, 계획 1, 빌드 7, 검증 2, 리뷰 4, 배포 6)로
구성되며, 여기에 4개의 에이전트 페르소나(코드 리뷰어, 테스트 엔지니어, 보안
감사자, 웹 성능 감사자)와 7개의 참고 체크리스트(완료 정의, 테스트 패턴, 보안
체크리스트, 성능 체크리스트, 접근성 체크리스트, 관측 가능성 체크리스트, 오케스트레이션
패턴)가 더해진다. 설치는 `npx skills add addyosmani/agent-skills` 같은 범용
skills CLI(70개 이상 에이전트 지원)부터 Claude Code 플러그인, Cursor, Gemini
CLI, Codex, Windsurf, GitHub Copilot, Kiro 등 플랫폼별 방식까지 폭넓게
지원한다. MIT 라이선스로 공개돼 있으며, 창시자 Addy Osmani 외에 Federico
Bartoli와 Joan León이 협력자로 이름을 올리고 있다.

## 분석

설계 철학의 핵심은 “검증은 협상 불가”다. 모든 단계가 실제 증거(테스트 통과, 빌드
출력, 런타임 데이터)로 완료 기준을 정의한다. 에이전트가 “완료했다”고 선언하는 것이
아니라 관찰 가능한 결과물로 완료를 증명하게 만든다.

Google 엔지니어링 원칙들이 스킬에 직접 내장되어 있다.

- **Hyrum's Law**: 모든 공개 인터페이스는 결국 의존된다 — 변경 시 영향 범위를 검토하라
- **Beyoncé Rule**: “좋으면 테스트를 달았어야지” — 검증 없이 배포하지 말라
- **Chesterton's Fence**: 이유를 모르면 제거하지 말라

각 스킬에는 “나중에 테스트 추가하겠다” 같은 흔한 합리화와 반박 논거를 담은
안티-합리화 표도 포함된다. 에이전트의 지름길 유혹을 명시적으로 차단하는 구조다.

다만 HN에서 wg0은 이 설계 전제 자체에 의문을 제기한다.
LLM은 `AGENTS.md`나 개별 스킬 파일에 명시된 규칙 하나쯤은 언제든 슬롯머신처럼
누락시킬 수 있다는 것이다[^wg0].
이 지적은 하네스 설계가 “LLM은 규칙을 엄밀하게 따르는 존재이고 문제는 규칙을
충분히 명확하게 명시하지 못한 것뿐”이라고 전제한다면, 그 전제 자체가 LLM의
작동 방식에 대한 근본적 오해라고 본다.
`stellalo`도 비슷한 지점을 짚는다. 스킬 정의는 “상황이 요구하면 주입된다”고
말하지만, 그 상황 판단 자체를 다시 LLM이 내린다는 점에서 강제가 아니라
LLM이 “따르기로 결정할 수도 있는” 절차에 불과하다는 것이다[^stellalo].

Claude Code뿐 아니라 Cursor, Gemini CLI, Windsurf, GitHub Copilot 등 다양한
플랫폼을 지원하며, 모든 스킬은 마크다운 파일로 시스템 프롬프트에 주입된다.

### 페르소나와 체크리스트는 스킬과 다른 층위의 강제 장치다

25개 스킬이 “무엇을 언제 하라”는 절차라면, 4개의 에이전트 페르소나는 “누구의
관점에서 판단하라”는 역할을 지정한다. 코드 리뷰어 페르소나는 시니어 스태프
엔지니어의 5축 리뷰 기준을, 보안 감사자 페르소나는 OWASP Top 10 기반 위협
모델링 관점을 에이전트에 부여한다. 참고 체크리스트(`definition-of-done.md`,
`security-checklist.md` 등)는 다시 그 아래 층위에서 페르소나의 판단이 근거해야
할 구체적 항목을 제공한다. 스킬이 워크플로우, 페르소나가 관점, 체크리스트가
근거라는 삼중 구조로 “에이전트가 무엇을 지켜야 하는가”를 여러 각도에서
중복으로 강제하는 설계다.

## 비평

GeekNews의 xguru는 핵심을 짚었다. “마크다운 파일이라 전부 도입할 필요는 없고,
토큰 소모량을 고려해 필요한 것만 선별해야 한다.”[^gn-xguru] 25개 스킬을 전부
활성화하면 컨텍스트 창을 상당히 소비하고 에이전트의 반응 속도와 유연성이
떨어질 수 있다.

또한 댓글에서는 “자신만의 하네스를 만들어가는 것이 효율적”이라는 의견이 지배적이었다.
남이 만든 스킬 모음을 그대로 쓰기보다는, 이 저장소를 출발점으로 팀 혹은 개인의
맥락에 맞게 커스터마이징하는 전략이 더 현실적이다.
HN의 `dmix`도 같은 결론에 도달한다. 대규모 스킬 세트를 실제로 써본 경험상
“너무 많은 일을 한다”는 인상만 남았고, Vim 플러그인처럼 커뮤니티 전체를
일괄 설치하기보다 골라 쓰는 편이 낫다는 것이다[^dmix].
`zmmmmm`은 이 문제를 구체적 수치로 보완한다. 스킬 하나하나가 표와 체크리스트,
코드 예시로 몇 페이지씩 이어질 만큼 길어서, 몇 개만 동시에 활성화해도 컨텍스트
창을 상당히 잠식할 수 있다고 지적한다[^zmmmmm].

### 자신을 “표준 SDLC의 재포장”이라 주장하는 근거가 빈약하다는 지적

프로젝트 설명은 이 스킬 모음이 새로운 것을 발명한 게 아니라 아마존의
“working-backwards memo”나 “bar raiser” 같은, 이미 검증된 조직의 소프트웨어
개발 생명주기를 어휘만 바꿔 재현한 것이라고 주장한다. `senko`는 이 비유가
“끔찍하게 틀렸다”고 정면으로 반박하며, 이런 주장이 LLM이 그럴듯하게 지어낸
서술을 검증 없이 그대로 받아들인 결과가 아닌지 의심한다[^senko].
`codemog`는 더 근본적인 공백을 짚는다. 이런 하네스 프로젝트들은 하나같이
“이 스킬을 적용했을 때와 안 했을 때”를 비교하는 벤치마크나 코드 생성 샘플 같은
“지루하지만 실제로 중요한” 검증 자료를 건너뛴다는 것이다. 그는 이 글의 문체
자체가 벤치마크 대신 확신에 찬 서술로 채워져 있다고 꼬집는다[^codemog].

Addy Osmani가 Chrome 팀 리드에서 Google Cloud AI 디렉터로 이직한 직후 발표된
프로젝트라는 점도 맥락으로 읽힌다. 이 프로젝트는 기술적 기여이자 새 역할에서의
포지셔닝이기도 하다.

### 규모의 폭발적 증가는 xguru의 우려를 되레 입증한다

이 저장소는 19개 스킬로 시작해 짧은 기간 안에 25개 스킬, 4개 페르소나, 7개
체크리스트로 불어났고 별표도 9만 개를 넘어섰다. 인기가 늘어난 만큼 저장소가
다루는 범위도 함께 늘어났다는 사실은, “전부 도입하지 말고 필요한 것만
선별하라”는 xguru의 경고가 시간이 지날수록 더 유효해지고 있다는 뜻이다.
프로젝트가 성장할수록 신규 채택자가 마주하는 선택지는 더 많아지고, 그만큼
“일단 전부 설치하고 본다”는 지름길의 유혹도 커진다. 저장소 자체가 제공하는
`docs/adoption-guide.md`와 `docs/comparison.md`가 뒤늦게 추가된 것도, 커진
규모를 어떻게 걸러 쓸지에 대한 안내가 필요해졌다는 신호로 읽을 수 있다.

## 인사이트

### 에이전트의 지름길 본능

AI 코딩 에이전트가 테스트, 스펙, 보안 리뷰를 건너뛰는
이유는 훈련 데이터에 “일단 동작하는 코드”가 과잉 대표되기 때문이다. 이 스킬 모음이
해결하려는 문제는 에이전트의 기술적 한계가 아니라 인센티브 구조의 문제다. 명시적으로
“건너뛰지 말라”는 규칙을 주입하지 않으면 에이전트는 최단 경로를 택한다.

### 코딩 문화의 외재화

Hyrum's Law, Beyoncé Rule, Chesterton's Fence 같은
구글의 엔지니어링 문화 원칙이 에이전트의 행동 지침으로 변환된다는 점은 의미심장하다.
수십 년에 걸쳐 조직 내에서 구전되던 엔지니어링 지혜가 마크다운 파일 몇 줄로
누구나 에이전트에 주입할 수 있는 형태가 됐다. 문화가 코드가 되는 전환이다.

### 스킬 생태계의 파편화 위험

Claude Code, Cursor, Gemini CLI 각각을 위한 스킬
형식이 다르면서도 이 프로젝트는 통합 지원을 주장한다. 실제로는 플랫폼마다 스킬이
동작하는 방식이 달라 “한 번 작성, 어디서나 실행”이 허상일 가능성이 높다. 에이전트
스킬 표준화가 생태계의 다음 과제로 부상하고 있다.
같은 문제의식은 HN에서도 반복된다. `CharlesW`는 검색 노출(SEO/LLMO) 관점에서
이 저장소가 `obra/superpowers` 같은 경쟁 스킬 세트와 어떻게 구별되는지 묻고[^charlesw],
`cortesoft`는 GitHub의 `spec-kit`과 철학이 겹치는데 서로 통합될 수 있는지,
아니면 그저 중복 투자인지 되묻는다[^cortesoft]. 짧은 기간에 여러 조직이 각자
독립적으로 비슷한 스킬 세트를 내놓고 있다는 사실 자체가, 표준화 이전 단계에서
벌어지는 경쟁적 포지셔닝에 가깝다는 것을 시사한다.

### 시니어 엔지니어 지식의 증류

이 프로젝트의 가장 큰 가치는 기술 스택이 아니라
시니어 엔지니어들이 코드 리뷰에서 반복적으로 지적하는 패턴들을 명시화했다는 점이다.
“나중에 테스트 추가하겠다”는 말이 왜 거짓말인지를 에이전트에게 가르치는 것은,
주니어 개발자에게 같은 내용을 가르치는 것과 구조적으로 동일한 문제다.

### 좋은 스킬이 곧 좋은 결과물을 보장하지 않는다는 반증 사례

GN에서 `blacksocks`는 회사 지시로 바이브 코딩만으로 개발해 보라는 과제를
받아 이런 스킬 세트를 여러 개 직접 적용해 본 경험을 전한다. 결과는 뛰어난
스킬 구성 자체가 높은 품질을 보장하지 않았다는 것이었다. 오히려 AI가 만든
코드를 읽고 판단하는 능력이 핵심이었고, 도구가 정교해질수록 “읽고 판단하는
힘”이 상대적으로 더 중요해지는 역설을 겪었다고 말한다[^gn-blacksocks].
이 증언은 앞서 다룬 “시니어 엔지니어 지식의 증류”라는 가치와 정면으로
긴장 관계에 있다. 시니어의 판단 기준을 스킬 파일로 옮겨 적을 수는 있어도,
그 판단 기준을 실제로 적용해 코드를 읽고 검증하는 능력 자체는 스킬 파일이
대신 길러주지 못한다.
