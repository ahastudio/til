# Paperthin: 더하지 않고 덜어내는 에이전트 스킬 모음

<https://paperthin.ai/>

<https://github.com/LilMGenius/paperthin>

## 소개

Paperthin은 “저수준 에이전트형 설계 패턴(low-level agentic design patterns)”을
표방하는 스킬 모음이다.
README는 이 저장소를 재귀적 자기 개선(RSI, recursive self-improvement)을 위한
“스킬북”이라고 소개한다.
NVIDIA의 최신 증명을 오래된 엔지니어링 지혜로 풀어냈고, OpenAI 하네스 엔지니어링
해커톤 우승자의 무개입(zero-touch) 방식에서 추출했다는 것이다.
Codex, Claude Code, OpenCode, Cursor, Grok Build, Pi 같은 어느 에이전트에서나 쓸
수 있다고 내세운다.

저장소는 2026년 6월 19일에 만들어졌고 마지막 푸시는 11월 10일이며, 라이선스는
MIT, 주 언어는 JavaScript다.
GitHub API로 확인한 2026년 11월 12일 기준 별은 1,426개, 포크는 123개다.
이 문서의 이전 판은 7월 22일 시점의 스킬 28개를 다뤘지만, 지금은 45개이고 이전
판이 다룬 일부 이름(`readchk`, `feynman`, `prism`, `reorder`)은 현재 색인에
없다.
README는 만든 사람 Bran Lee의 이력(OpenAI 해커톤 1위, Claude Code 공식 밋업 초청
연사 두 번, Google DeepMind 해커톤 심사위원, 2014년 정보올림피아드 은상 등)을
본문 첫머리에 싣는다.
이 이력은 저자 본인의 서술이며 이 문서는 확인하지 못했다.

### 설치

README는 에이전트마다 경로를 하나만 고르라고 한다.
두 경로를 함께 설치하면 모든 스킬이 두 번 로드되기 때문이다.

| 대상         | 명령                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------- |
| Codex        | `codex plugin marketplace add LilMGenius/paperthin && codex plugin add paperthin@paperthin`       |
| Claude Code  | `claude plugin marketplace add LilMGenius/paperthin && claude plugin install paperthin@paperthin` |
| 그 밖의 전체 | `npx skills@latest add LilMGenius/paperthin --global --agent '*'`에 이어 매일 갱신하는 일정 등록  |

Claude Code는 설치 뒤 `/plugin`의 Marketplaces에서 자동 갱신을 한 번 켜야 한다.
사용은 `/paperthin` 뒤에 하고 싶은 일을 적는 것이 전부이고, 원리가 궁금하면
`/re0-tutorial`을 쓴다.
이미 설치한 사람은 새 세션에서 `/re0-upgrade`를 한 번 돌리면 된다.
설치 안내의 마지막 항목은 “별 하나가 수수료”라는 요청이다.
README는 영어 외에 열 개 언어 번역을 링크하고, 웹 채팅에는 `llms-full.txt`를
건네라고 안내한다.

## 구성: 2×2 지도와 스킬 색인

Paperthin은 스킬을 “아티팩트가 몇 개인가 × 시간이 얼마나 걸리는가”라는 2×2
지도로 나눈다.

| 영역       | 범위                   | 묻는 것                          | 스킬 수 |
| ---------- | ---------------------- | -------------------------------- | ------- |
| `depth/`   | 아티팩트 하나, 지금    | 이 하나가 깨끗하고 참인가        | 28      |
| `breadth/` | 여러 아티팩트, 지금    | 하나의 진실이 어디서나 일관된가  | 5       |
| `coil/`    | 한 프로젝트, 여러 회차 | 각 회차가 다음 회차를 가르쳤는가 | 11      |
| `mesh/`    | 여러 관점, 여러 회차   | 여럿이 진실로 수렴하는가         | 1       |

색인은 스킬마다 “무엇을 하는가 / 호출 주체(model·user) / 읽기 전용 여부”를 표로
적는다.
전체 45개 중 사용자가 호출하는 스킬은 17개, 모델이 스스로 부르는 스킬은
28개이고, 읽기 전용 표시가 붙은 것은 15개다.

`depth/`가 가장 두껍다.
- 다시 쓰기와 줄이기: 누더기가 된 문서를 패치하지 않고 깨끗한 첫 판으로 다시
  쓰는 `re0`, 규칙과 동작을 잃지 않고 군더더기를 줄이는 `debloat`, 목록을 한
  가지 기준으로 재정렬하되 문구는 건드리지 않는 `re0-order`, 오래갈 문서의
  브랜드와 도구 이름을 실제 기능으로 바꾸는 `detool`, 프로젝트 자신의 스타일에
  코드를 맞추는 `re0-style`.
- 문장 부호 정리: 에이전트가 흩뿌리는 긴 줄표를 걷어내는 `dedash`, 한국어
  가운뎃점을 쉼표나 연결어로 제안하는 읽기 전용 `dedot`.
- 요청과 결정 점검: 일을 시작하기 전에 요청을 이해했는지 확인하고 두 해석이 정말
  다를 때만 묻는 `readback`, 건네받은 파일에서 의도를 제안하는 `aim`, 가장 싼
  충분한 모델 티어와 추론 강도를 권하는 `modelchk`, 습관 때문에 남은 요구를
  덜어내자고 제안하는 `elon`, 새 조각이 대상의 문서화된 범위에 속하는지 보는
  `scopechk`.
- 비판과 사고: 계획을 무너뜨릴 단 하나의 반론과 가장 싼 검증을 내놓는 `hate`,
  같은 질문을 여러 새 머리에 던져 의견이 갈리는 곳을 먼저 보여 주는
  `macrothink`, 서로 무관한 다섯 분야에서 아이디어를 빌려 오는 `crossthink`,
  결정 재료를 점검표로 바꾸되 대신 고르지 않는 `re0-decide`, 방금 내린 결정을
  설명할 수 있을 때까지 캐묻는 `whychk`.
- 실행 안전과 검증: 위험한 범위를 먼저 도려내고 나머지를 전속력으로 돌리는
  `autobahn`, 변경 직후 이 저장소의 검사를 산출물에 돌리는 `sip`, 배경 없는
  독자에게 넘겨 보는 `shower`, 주장을 양방향으로 검증하는 `factchk`, 시험이나
  지표가 스스로를 채점하는지 보는 `mandela`, 거짓 성공 보고를 만드는 가짜와
  조용한 대체 경로를 찾는 `demock`, 공유 파일에서 개인과 회사 정보를 역할로
  바꾸는 `deid`.
- 커밋과 배포: 커밋 메시지를 다시 쓰는 `re0-git`, 릴리스 점검표를 돌리는
  `re0-release`, 남의 기여를 병합하는 `re0-merge`, 저장소를 서명된 커밋 하나로
  다시 공개하는 `re0-squash`.

나머지 영역은 상대적으로 얇다.
- `breadth/`: 여러 곳에 복사된 사실에 하나의 집을 주는 `ssotize`와 중복 파일을
  하나의 실체로 합치는 `ssotize-local`, README와 AGENTS.md의 줄을 읽는 사람에
  맞게 나누는 `re0-readme`, 건네받은 자료를 지식 베이스의 규칙대로 정리하는
  `re0-import`, 카탈로그를 한 번에 최신으로 올리는 `re0-upgrade`.
- `coil/`: 기억할 단 하나의 명령 `paperthin`, 목표에 맞는 스킬 순서를 정해 보여
  주고 실행하는 `re0-workflow`, 끝난 회차에서 교훈을 뽑는 `re0-memo`, 교정이
  가르친 것을 문서와 규칙에 되먹이는 `backprop`, 교훈만 남기고 처음부터 다시
  시작하는 `re0-work`, 자리를 비운 뒤 상황을 알려 주는 `catchup`, 다음 최선의
  행동 하나를 돌려주는 `nba`, 새 회차의 폴더를 여는 `re0-plan`, 만들고 시험하고
  배우고 다시 시작하는 순환을 돌리는 `re0-loop`, 장시간 작업의 정체를 감시하는
  `re0-watch`, 한 스킬을 세 단계로 가르치는 `re0-tutorial`.
- `mesh/`: 여러 독립된 의견을 개수가 아니라 근거로 가중하는 `multithink`
  하나뿐이다.

## 문제 진단과 근거

README의 문제 진술은 직설적이다.
“대부분의 에이전트 스킬은 슬롭이다.”
에이전트에게 목표를 주면 더한다.
파일을 더, 옵션을 더, “도움이 되는” 보일러플레이트를 더.
더하기는 진척처럼 보이고, 무엇도 그것을 되돌아가 지우게 만들지 않는다.
이것이 프로젝트 전체에 반복되면 거의 중복인 스킬, 죽은 설정, 같은 말을 세 번
하는 마크다운이 생긴다.
Paperthin의 베팅은 반대 방향이다.
이 스킬들은 하나도 빠짐없이 무언가를 덜어내고, 무엇을 덜어내는지는 색인이 말해
준다고 한다.
README가 요약하는 제품은 한 문장이다.
어려운 부분은 기능이 아니라 절제이고, 개선할 것을 찾지 못한 패스는 아무것도
바꾸지 않으며, 그 절제가 곧 제품이다.

이 문서의 이전 판은 각 Fix에 접힌 `[PROOF]` 블록(Setup·Result·So)이 붙어 있다고
적었다.
현재 README에는 그 블록이 없고 `llms-full.txt`에도 나타나지 않는다.
대신 “The Proof”라는 절이 하나 있다.
이 절은 NVIDIA 연구진이 낸 논문 「You don't need long context」에서 가져온
수치를 표로 보여 준다.[^arxiv]
README가 인용한 값은 다음과 같다.

| 측정 항목                           | 긴 컨텍스트 | 짧은 노트        |
| ----------------------------------- | ----------- | ---------------- |
| SWE-bench Verified, Claude Opus 4.5 | 70.0        | 70.2             |
| 실행에 필요했던 최대 컨텍스트       | 200K 토큰   | 16K 토큰         |
| 오픈 웨이트 모델 서빙 처리량(H100)  | 256K 윈도우 | 16K에서 최대 7배 |

논문의 초록은 뒤쪽 토큰이 앞쪽보다 생성 비용이 크고 그 격차가 최대 7배에 이르며,
잦은 압축(compaction)으로 짧은 컨텍스트를 유지해도 정확도 손실이 거의 없다는
것을 보였다고 요약한다.
이 문서가 논문 본문(arXiv HTML)에서 확인한 값은 README의 표와 일치한다.
Opus 4.5의 SWE-bench Verified 기준선은 70.0, 한 컨텍스트에 행동 하나만 두는
압축(SAC)은 70.2였고, 최대 컨텍스트는 200K에서 16K로 줄었다.
처리량 배수는 GLM 5.2가 3.6배, Kimi K2.6이 5.6배, Qwen 3 Coder Next가 7배였다.

README는 이어서 논문의 발견을 스킬에 대응시키는 표를 둔다.
긴 작업이 긴 컨텍스트를 요구하지 않는다는 발견은 `re0-work`(검증된 교훈만 가지고
처음부터 다시 시작)와 `re0-git`(다음 세션을 위한 인계를 커밋 기록에 남김)에
대응된다.
좋은 노트가 원래 요청 문구를 가깝게 지킨다는 발견은 `re0-loop`에, 하고 있는 일과
이유와 다음 단계를 담는다는 발견은 `re0-memo`와 `nba`에 대응된다.
계획과 완료 조건을 담는다는 발견은 `re0-plan`과 `re0-workflow`에, 이력 없이
노트만으로 이해되는지 보는 것은 `shower`에, 작은 윈도우가 더 빠르다는 발견은
`elon`, `debloat`, `re0`에 대응된다.
이 대응은 README 저자가 한 연결이며 논문이 Paperthin을 언급하는 것이 아니다.

## 분석

### 이 프로젝트의 핵심 주장은 “스킬의 기본 동작이 더하기라서 슬롭이 쌓인다”이다

Paperthin의 진단은 개별 스킬의 품질이 아니라 스킬이라는 형식의 기본값을
겨냥한다.
에이전트에게 목표를 주면 더하는 쪽으로 기울고, 더한 것을 되돌아가 지우게 하는
힘이 어디에도 없다는 것이다.

이 진단이 날카로운 이유는 인센티브의 비대칭을 짚기 때문이다.
파일을 만들고 옵션을 늘리는 것은 눈에 보이는 산출이라 “일했다”는 증거가 되지만,
지우는 것은 산출이 줄어드는 것처럼 보여 아무도 하지 않는다.
그래서 결과물은 “그럴듯하고 분주하며 조용히 유지 불가능한” 상태로 수렴한다.
이것은 이 저장소의 다른 문서가 다룬 “생성이 싸지면 복잡도가 임계점으로
밀려간다”는 관찰과[^ref-debt] 같은 구조이며, Paperthin은 그 관찰을 도구 계층에서
반복한다.

이 진단이 처방의 형태를 결정한다.
모든 스킬이 덜어낸다는 공통 규칙은 취향이 아니라, 더하기가 기본값인 시스템에
반대 방향의 편향을 의도적으로 심는 것이다.
`debloat`는 규칙과 동작을 잃지 않는 범위로, `re0-order`는 항목만 옮기고 문구는
바꾸지 않는 범위로 권한을 좁게 묶는다.
이 한정이 덜어내기가 파괴로 번지지 않게 하는 설계다.

### 새로 들어온 근거는 스킬의 “한 번에 하나, 노트로 이어 가기”와 맞물린다

현재 README의 중심 근거는 긴 대화 이력 대신 짧은 상태 노트로 이어 가도 성능이
유지된다는 논문이다.
이 근거는 Paperthin의 coil 영역(회차마다 교훈을 남기고 처음부터 다시 시작)이
가정하는 작동 방식과 직접 닿는다.
`re0-work`가 검증된 교훈만 남기고 v0에서 다시 시작하는 것, `re0-git`이 다음
세션의 인계를 커밋 기록에 남기는 것, `shower`가 노트만 넘겨 이해되는지 보는 것은
모두 “상태는 노트에, 이력은 버린다”는 같은 원리다.
이 원리가 맞다면 스킬이 하는 일은 새 기능을 붙이는 것이 아니라 에이전트가 이력
없이도 이어 갈 수 있게 정리하는 것이다.
다만 논문의 SAC는 한 컨텍스트에 행동 하나만 두는 설정으로 측정한 것이고, 스킬이
실제로 같은 설정을 만든다는 근거는 README에 없다.

### 호출 주체와 읽기 전용 표시가 권한 설계를 드러낸다

색인 표에서 가장 실용적인 열은 호출 주체(model·user)와 읽기 전용 여부다.
`hate`(계획을 죽일 반론), `macrothink`(신선한 독해 팬아웃), `whychk`(결정
캐묻기), `multithink`(독립 의견의 근거 가중)는 모두 사용자 호출이다.
판단을 흔드는 스킬이라 사람이 겨눠야 한다는 설계로 읽힌다.
반면 `re0`, `readback`, `sip` 같은 정리와 점검 스킬은 모델이 스스로 부른다.

`macrothink`의 규칙은 이 설계를 구체적으로 보여 준다.
현재 SKILL.md는 다수결이나 평균을 내지 말고, 같은 모델의 수렴을 “검증되었다”고
말하지 말며, 수렴은 안심이지 증명이 아니라고 적는다.
이는 이 저장소의 다른 문서가 다룬 “같은 모델 다수는 상관된 오류를
증폭한다”는[^ref-graph] 위험을 스킬 규칙으로 방어한 것이다.

## 비평

### 근거 표가 유리한 한 줄을 골랐다

README의 “The Proof” 표는 Opus 4.5의 SWE-bench Verified 한 행만 싣는다.
같은 논문의 같은 표에서 GPT 5.6 Sol은 SAC가 SWE-bench Verified 82.4%로 자기
기준선보다 2.0%포인트, Terminal-Bench 84.3%로 3.3%포인트 낮았다.
Opus 4.5의 Terminal-Bench는 기준선 47.2에서 SAC 51.8로 올랐다.
압축 시점을 가장 잘 조정한 경우(Best EoCC)는 SWE-bench 74.8, Terminal-Bench
52.8로 SAC보다 높았다.
논문의 요지는 “정확도를 거의 잃지 않는다”이고, README의 문구 “점수를 유지한다”는
이 요지에 맞지만 모델과 벤치마크에 따라 증감이 갈린다는 사실을 표만으로는 알 수
없다.
이 비평은 이 문서가 논문 본문에서 확인한 값에 기댄 것이며, 논문 전체를
재검토하지는 않았다.

또 하나의 간극은 논문의 대상이다.
논문은 대화 이력의 압축이 모델 정확도와 서빙 비용에 미치는 영향을 측정했고,
Paperthin의 스킬 대부분(`dedash`, `deid`, `re0-merge` 등)은 문서와 코드,
저장소를 다루는 작업이다.
README의 대응표가 연결하는 것은 `re0-work`, `re0-memo` 같은 일부 스킬이고, 28개
`depth/` 스킬 가운데 이 논문과 직접 닿는 것은 소수다.

### “모든 스킬이 덜어낸다”는 규칙이 카탈로그의 크기와 충돌한다

Paperthin의 선언은 “이 스킬들은 하나도 빠짐없이 덜어낸다”이지만, 그 선언을 담은
것은 45개 스킬과 열한 개 언어의 README, 지도 이미지를 가진 저장소다.
이전 판이 지적한 긴장은 오히려 커졌다.
스킬은 28개에서 45개로 늘었다.

README는 슬롭을 거의 중복인 스킬, 죽은 설정, 같은 말을 세 번 하는 마크다운으로
규정한다.
그런데 `re0` 접두사를 공유하는 스킬이 열여덟 개(`depth/` 여덟, `breadth/` 셋,
`coil/` 일곱)이고, `dedash`와 `dedot`은 모두 문장 부호를 다루며, `debloat`와
`elon`과 `re0`는 모두 “덜어내는” 계열이다.
각각의 범위가 표에서 구별된다는 README의 설명은 맞다.
다만 “거의 중복인 스킬”이라는 자기 진단의 기준을 이 카탈로그에 적용하면 이
카탈로그도 혐의에서 자유롭지 않다.

이 긴장은 사용자 경험으로 돌아온다.
45개 가운데 언제 무엇을 부를지 아는 것 자체가 학습 부담이고, `nba`, `catchup`,
`re0-workflow` 같은 메타 스킬이 필요한 것은 카탈로그가 한눈에 잡히지 않는다는
신호다.
README가 “기억할 명령은 `/paperthin` 하나”라고 하는 것은 이 부담을 인정하고
입구를 하나로 좁히는 해법이다.

### 중립성과 시의성의 긴장이 모습만 바꿔 남아 있다

`modelchk`는 벤더 중립을 엄격히 지킨다.
능력 티어 `fast`, `standard`, `frontier`와 추론 강도만 권고하고, 구체 모델이나
경로를 고르거나 바꾸거나 고정하는 권한을 갖지 않는다고 SKILL.md가 적는다.
`detool`은 오래갈 문서의 브랜드, 모델, 도구 이름을 그것이 뜻하는 메커니즘으로
바꾼다.
그런데 README의 첫 줄부터 NVIDIA, OpenAI, Claude Code, 특정 모델명(Opus 4.5, GLM
5.2, Kimi K2.6, Qwen 3 Coder Next)이 근거로 쓰인다.
이는 README가 홍보 문서라는 성격 때문일 수 있지만, 이 이름들이 `detool`의 대상이
되는 “오래가야 하는 문서”는 아니라는 구별이 README에는 없다.
이전 판이 짚은 저장소 토픽의 모델 이름 문제는 현재 토픽 목록(`nvidia`,
`claude-code`, `grok` 등)에 `fable`이 빠지고 다른 이름이 들어가는 식으로 모습만
바뀌었다.

### 홍보 요소가 설계 철학과 어긋나 보인다

README는 저자의 수상 이력을 본문 첫머리에 놓고, “Paid in stars”라는 항목으로 별
하나를 수수료로 요청하며, 일론 머스크의 “Best part is no part”를 인용한다.
README의 각주는 그 말이 SpaceX 부스터의 그리드 핀 하나를 없앤 데 관한 것이고
Paperthin에 관한 말이 아니라고 스스로 밝힌다.
이 점은 정직한 처리이지만, 절제를 내세우는 문서가 이력과 인용으로 권위를 쌓는
모습은 제품 철학과 결이 다르다.
이는 문체에 대한 평가이고 스킬의 품질과는 별개다.

## 인사이트

### 에이전트 도구의 진짜 경쟁은 기능이 아니라 “아무것도 하지 않을 줄 아는 능력”으로 이동한다

Paperthin의 가장 값진 주장은 스킬 목록이 아니라 한 문장에 있다.
개선할 것을 찾지 못한 패스는 아무것도 바꾸지 않는다는 것이다.
이 기준은 에이전트 도구를 고르는 시금석이 된다.

이 기준이 근본적인 이유는 생성 비용이 0에 가까워졌기 때문이다.
무언가를 만드는 능력이 흔해지면 차별화는 만들지 않을 때를 아는 것으로 옮겨 간다.
매번 무언가를 바꾸는 도구는 진척의 착시를 주지만 저장소를 부풀리고, 아무것도
바꾸지 않을 수 있는 도구만이 반복 적용에 안전하다.
이 저장소의 다른 문서가 다룬 “생성이 싸지면 값은 판단으로 옮겨
간다”는[^ref-fund] 관찰이 도구의 설계 원칙으로 내려온 것이 이 절제 기준이다.

이 통찰의 2차 효과는 도구 평가 방법의 변화다.
지금 대부분의 스킬은 “무엇을 할 수 있는가”로 소개되지만, 진짜 물어야 할 것은
“깨끗한 입력에 돌렸을 때 무엇을 하는가”다.
멱등성에 가까운 이 성질은 자동 호출되는 스킬의 필수 조건이며, 그렇지 않은 도구는
자동화될수록 해롭다.

### “오래된 지혜의 자동화”라는 프레임은 검증된 원칙을 검증되지 않은 실행으로 바꾼다

Paperthin은 각 스킬을 에고 없는 프로그래밍이나 보이스카우트 규칙 같은 검증된
원칙의 자동화로 소개했고, 지금 README는 이를 NVIDIA 논문의 증명으로 바꿔 부른다.
그러나 원칙이나 논문의 권위가 자동화된 실행의 권위로 이전되지는 않는다.
원칙이 유효한 것은 판단하는 사람이 맥락을 이해하고, 이해관계가 없고, 틀렸을 때
책임을 지기 때문이다.
그 판단을 모델에 넘기면 이름은 남지만 그 요소는 함께 넘어가지 않는다.
이 저장소의 다른 문서가 다룬 “AI는 책임을 지지 않는다”는[^ref-leadership] 지적이
여기 그대로 적용된다.

그러므로 이런 스킬은 원칙을 대신 지켜 주는 장치가 아니라 원칙을 떠올리게 하는
알람에 가깝다.
사용자 호출 스킬이 판단을 흔드는 것들에 몰려 있는 것은 저자도 이 점을 안다는
신호로 읽히며, 이 구분을 지키는 것이 도구를 대체물이 아닌 촉매로 쓰는
경계선이다.

### 스킬 카탈로그의 다음 병목은 개수가 아니라 조합과 순서다

`nba`, `catchup`, `re0-workflow`, 그리고 `/paperthin` 하나로 입구를 모으는
설계는 카탈로그가 커질 때의 진짜 문제를 드러낸다.
스킬이 충분히 많아지면 병목은 “무엇이 있는가”가 아니라 “지금 어느 것을 어떤
순서로 쓰는가”가 된다.
`re0-workflow`가 목표에 맞는 스킬과 순서를 정해 보여 주고, 사용자가 해야 할
곳에서 멈추는 것은 이 병목에 대한 직접적인 답이다.

이 이동이 구조적인 이유는 조합의 수가 개수보다 빨리 늘기 때문이다.
이 저장소의 다른 문서가 다룬 “개별 루프에서 루프들의
오케스트레이션으로”라는[^ref-graph] 이동이 스킬 층에서도 반복된다.
그 조율이 잘 되면 사용자는 스킬 이름을 외울 필요가 없어지므로, 역설적으로
카탈로그의 가시성은 성숙의 지표가 아니라 미성숙의 흔적이다.

### 결론을 바꿀 관찰

- 같은 작업을 스킬 없이 돌린 경우와 Paperthin의 `re0-work`, `re0-loop`를 쓴
  경우를 독립된 평가로 비교해 성과 차이가 나타난다면, 논문 근거를 스킬의 효과로
  읽는 것이 정당해진다.
- GPT 5.6 Sol처럼 SAC에서 점수가 내려간 모델에서 Paperthin의 노트 중심 흐름이
  같은 하락을 보인다면, README가 한 행만 보여 준 선택성이 실제 한계로 확인된다.
- 카탈로그가 더 늘지 않고 오히려 줄어든다면(스킬을 합치거나 폐기한다면),
  “덜어낸다”는 선언이 카탈로그 자체에도 적용된다는 증거가 된다.
