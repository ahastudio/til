# pixel-making: 초안 5~10개를 렌더해 비교하며 픽셀아트 영상·게임·슬라이드를 코드로 만드는 Claude Code 스킬

<https://github.com/revfactory/pixel-making>

## 소개

pixel-making은 픽셀아트 애니메이션과 효과(VFX), 장면을 코드로 그려 영상(MP4,
GIF, 루프 영상),
브라우저 게임, 스프라이트 애니메이션(시트, GIF, APNG), 발표 슬라이드로 내보내는
Claude Code 스킬입니다.
저장소는 2026년 11월 1일에 올라왔고 커밋은 하나, 별은 0개, 포크는 1개입니다.
언어는 TypeScript와 JavaScript(`.mjs`)이고, 파일은 52개입니다.
이 문서는 README와 `SKILL.md`, 파일 목록, `vfx/LICENSE`를 읽어 정리한 것이고,
스킬을 설치해 렌더해 본 결과가 아닙니다.

설치는 저장소를 `~/.claude/skills/pixel-making`으로 복제하는 것이 전부입니다.
Node 22.18 이상을 권하고(`.ts` 효과를 바로 실행하기 위해서),
장면과 렌더러만 쓰면 Node 18 이상이면 됩니다.
MP4와 GIF 출력에는 ffmpeg가 필요하고, 없어도 컨택트시트와 스틸과 PNG 시퀀스와
스프라이트 시트는 만들어진다고 README가 적습니다.

```bash
node scripts/new.mjs my-project --kind video --vfx explosion
node scripts/render.mjs my-project/scenes/title.mjs --stills 0.9,1.5 --out my-project/records/title
node scripts/render.mjs vfx/explosion.ts --fx --opts '{"size":1.2}' --seconds 2
```

## 작업 방식

`SKILL.md`는 이 스킬이 Sprite Fusion의 Hugo Duprez가 Claude와 Codex로 픽셀 VFX를
만들며 정리한 방식을 따른다고 밝히고, 원문으로 `spritefusion.com`의 블로그
글을 듭니다.
이 문서는 그 글을 열어 보지 않았으므로,
아래는 `SKILL.md`가 옮겨 적은 내용입니다.

여섯 가지 원칙이 있습니다.

- 효과는 스프라이트 이미지가 아니라 코드로 그립니다. 숫자 하나로 크기와 색과 속도를 바꿀 수 있기 때문입니다.
- 초안을 5~10개 만들어 짧은 영상으로 렌더하고 비교해 하나를 고릅니다.
- 품질 기준은 눈으로 정하고, 첫 버전에서 멈추지 않습니다.
- 사용자가 말한 게임이나 영화를 판단 기준(레퍼런스)으로 삼습니다.
- 움직임은 애매하면 더 과장합니다. 늘어남과 눌림, 준비 동작, 가감속, 호, 따라오는 움직임, 과장의 여섯 원칙이 `references/motion.md`에 있습니다.
- 수정은 한 번에 하나씩 하고, 고칠 때마다 다시 렌더해 확인합니다.

진행 순서는 환경 확인, 요청 읽기, 프로젝트 만들기, brief(아트 디렉션) 작성,
초안 렌더와 비교, 선택한 초안 다듬기, 매체별 내보내기,
납품 보고의 여덟 단계입니다.
매체마다 기본값이 정해져 있습니다.
영상은 320×180을 6배 해서 1920×1080으로 만들고 4~10초이며,
게임은 60Hz 고정 간격이고, 스프라이트는 16·32·64px 크기를 씁니다.

## 픽셀 규칙

`SKILL.md`가 요약한 규칙은 다음과 같습니다.

- 저해상도 버퍼에 그리고 정수배로, 최근접 샘플링으로만 키웁니다. MP4는 짝수 배율이 좋다고 합니다(yuv420p의 색 번짐을 피하려고).
- 반투명은 섞지 않고 4×4 Bayer 디더로 찍습니다. 실제 알파는 안개처럼 중간색이 눈에 띄지 않는 곳에만 쓰고, 이는 색 수를 100색 이상으로 늘린다고 합니다.
- 색은 램프에서 단계로 고르고 중간색을 새로 만들지 않습니다. 부드러운 빛은 가산 합성하는 `light` 버퍼에만 둡니다.
- 움직이는 것의 앞쪽을 밝게, 꼬리를 어둡게 그리고, 깊이는 속도와 길이와 밝기로 나눕니다.
- 결정적으로 만듭니다. `Math.random()`과 `Date.now()`를 쓰지 않고 시드 난수와 경과 시각만 써서, 같은 입력이 같은 영상이 되게 합니다.
- 한글 제목은 갈무리 BDF 픽셀 폰트를 정수배로 키워 외곽선 하나만 두릅니다. 획이 1픽셀인 글꼴에 외곽선과 그림자를 함께 두르면 글자가 뭉개진다고 합니다.

## 분석

### 영상을 볼 수 없다는 제약을 도구 설계로 풀었다

`SKILL.md`는 Claude가 영상을 재생해서 볼 수 없다고 분명히 적습니다.
그래서 렌더러가 영상과 함께 컨택트시트(시간순 프레임 격자)와 지정 시각의 확대
스틸을 PNG로 만들고,
Claude는 렌더할 때마다 이 PNG를 열어 판단합니다.
효과의 컨택트시트는 그려진 영역만 잘라 확대하고,
장면의 컨택트시트는 화면 전체를 1배로 붙여 구성과 흐름만 보게 하며 세부는
스틸로 봅니다.
이 구조는 시간 축의 판단을 정지 프레임 여러 장의 판단으로 바꾼 것입니다.

그 한계도 스킬이 알고 있습니다.
타이밍은 `--slow 0.25`로 4배 느리게 렌더해 확인하고,
사용자에게는 MP4 경로를 알려 움직임을 직접 확인하게 합니다.
결국 움직임의 최종 판단은 사람이 합니다.

### 결정적 렌더러가 초안 비교를 성립시킨다

초안을 5~10개 뽑아 비교하는 방식은 같은 입력이 항상 같은 영상일 때만 의미가
있습니다.
무작위가 끼면 두 초안의 차이가 구성의 차이인지 우연인지 알 수 없기 때문입니다.
그래서 시드와 경과 시각만 쓰는 규칙이 있고,
`--variants`(옵션이 다른 초안)와 `--seeds`(같은 초안의 시드 변형)를 구분합니다.
`SKILL.md`는 시드만 바꾼 변형은 같은 초안의 우연한 차이일 뿐이어서
구성, 색, 타이밍, 형태가 다른 초안을 만들라고 따로 적습니다.

### 측정 가능한 것은 수치로 정해 두었다

눈으로 판단하라는 원칙 옆에 숫자가 붙어 있습니다.
장면은 16~48색, 효과 램프는 흰색에서 시작하는 7~10단계, 배경 램프는 3~6단계이고,
렌더러가 변형마다 프레임당 색 수를 출력해 brief의 범위 안인지 확인하게 합니다.
루프 영상은 `--loop-check`가 0픽셀이어야 통과합니다.
미감은 눈에, 규칙은 숫자에 맡기는 분업입니다.

## 비평

### 효과 25종은 만든 사람도 실행해 보지 않았다고 적혀 있다

`SKILL.md`는 이 스킬을 만들 때 25종 원본 코드를 실행하지 않았다고 직접 적습니다.
코드를 읽고 카탈로그를 썼으므로, 처음 렌더할 때는 컨택트시트를 열어
카드의 설명과
같은 모습인지 확인하고 다르면 사용자에게 알리라는 지시가 붙어 있습니다.
솔직한 서술이지만, 이 스킬의 효과 카탈로그가 검증되지 않은 상태로 배포되었다는
뜻입니다.
저장소에는 렌더 결과 샘플(영상이나 시트 이미지)도 들어 있지 않아서,
품질은 설치해 돌려 봐야만 알 수 있습니다.

### 시각 판단을 모델에 맡기는 것이 검증되지 않았다

컨택트시트를 읽고 “첫 1~3프레임에 사건이 한눈에 보이는가”,
“실루엣이 읽히는가” 같은 항목을
점검하는 주체는 모델입니다.
점검표는 구체적이지만, 모델이 픽셀아트의 좋고 나쁨을 사람과 같은 방향으로
가린다는
근거는 저장소에 없습니다.
초안 중 하나를 고르는 일도 사용자가 맡기면 스킬이 스스로 하도록 되어 있어,
그 선택의 질은 모델의 시각 판단에 걸려 있습니다.

### 저장소 자체의 라이선스가 적혀 있지 않다

`vfx/`의 25종은 Hugo Duprez(Sprite Fusion)의 MIT 코드라고
`vfx/LICENSE`가 밝히고,
갈무리 폰트는 SIL OFL 1.1이며 저장소에 포함되지 않는다고 README가 적습니다.
그런데 스킬 본체(`scripts/`, `references/`, 템플릿)에 대한 라이선스는 README에도
최상위에도 보이지 않고, GitHub의 라이선스 항목도 비어 있습니다.
다른 프로젝트에 가져다 쓰려는 사람에게는 본체의 사용 조건이 불명확합니다.

### 처음 쓸 때 네트워크로 폰트를 받는다

한글 제목에 쓰는 갈무리 폰트는 처음 쓸 때 jsDelivr에서 받아
`~/.cache/pixel-making/fonts`에 둡니다.
네트워크가 막힌 환경에서는 폰트 파일을 그 폴더에 직접 넣거나 내장 3×5 글꼴만
써야 하고,
내장 글꼴로는 한글을 찍을 수 없다고 읽힙니다.
받은 폰트 파일의 무결성을 확인하는 단계는 문서에 없습니다.

## 인사이트

### 1. 영상을 못 보는 에이전트에게는 프레임 격자와 확대 스틸을 만들어 준다

이 스킬에서 가장 옮겨 쓸 만한 것은 결과물을 에이전트가 읽을 수 있는 형태로 같이
내보내는 습관입니다.
시간 축이 있는 결과(영상, 애니메이션, 로그)는 시간순 프레임 격자 하나와 핵심
순간의 확대 이미지로
바꿔 주면 에이전트가 렌더할 때마다 스스로 점검할 수 있습니다.
최종 판단은 사람이 하도록 파일 경로를 알려 주는 단계를 남겨 두는 것도 함께
가져갈 점입니다.

### 2. 비교를 쓰려면 먼저 결정적으로 만든다

초안을 여러 개 뽑아 고르는 방식은 재현 가능한 출력이 전제입니다.
시드를 고정하고, 시드만 다른 변형과 구성이 다른 초안을 구분해 부르는 것만으로도
고르는 일이 의미를 갖습니다.

### 3. 쓰기 전에 할 일

한 가지 효과를 `--fx` 모드로 렌더해 컨택트시트가 카탈로그 카드의 설명과 같은지
확인합니다.
다른 프로젝트에 코드를 가져갈 계획이라면 본체의 라이선스를 저장소 주인에게 먼저
묻습니다.
네트워크가 제한된 환경이라면 폰트를 미리 받아 둡니다.

### 4. 이 스킬에 대한 판단을 바꿀 관찰

같은 brief로 이 스킬을 쓴 경우와 한 줄 요청을 한 경우의 결과를 사람이 눈으로
비교한 사례가
공개되면 초안 비교 방식의 가치가 드러납니다.
25종 효과 가운데 카탈로그 카드와 렌더 결과가 다른 항목이 몇 개나 나오는지도
이 스킬의 완성도를 가늠하는 관찰입니다.
