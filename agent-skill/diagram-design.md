# Diagram Design: 에이전트가 만드는 다이어그램에 편집 디자인 규칙을 입히는 스킬

<https://cathrynlavery.github.io/diagram-design/>

<https://github.com/cathrynlavery/diagram-design>

GN 토론: <https://news.hada.io/topic?id=33664>

## 소개

Diagram Design은 Claude Code, Codex, GitHub Copilot, Factory Droid, Pi를 비롯한
Agent Skills 호환 호스트에서 쓰는 다이어그램 생성 스킬이다.
저장소 설명이 표방하는 바가 분명하다.
39가지 편집 다이어그램 유형을 제공하고, 결과물은 자기 완결적인 HTML과 SVG이며,
그림자도 없고 Mermaid 슬롭도 없다는 것이다.
MIT 라이선스이고 2026년 4월에 만들어졌으며 별은 약 3만 9천 개다.

이 문장들은 처음 문서를 쓸 때의 수치이고, 그사이 숫자가 달라졌다.
2026년 10월 11일 기준 저장소 설명은 유형 수를 44가지로 적고,
지원 호스트 목록 맨 앞쪽에 Cursor를 새로 넣어
Claude Code, Codex, GitHub Copilot, Cursor, Factory Droid, Pi를 나열한다.
같은 날 GitHub API 기준 별은 49,188개, 포크는 3,112개이고,
이날 GitHub Trending 4위에 올라 있었다.
2026년 4월 16일에 저장소가 만들어졌다.
README가 가장 먼저 내미는 설치 경로도
호스트별 마켓플레이스에서 `npx skills add cathrynlavery/diagram-design`
한 줄로 바뀌었다.
프로젝트 홈페이지는 diagramdesign.dev로 따로 생겼고(#273),
문서 상단의 `cathrynlavery.github.io/diagram-design` 주소는
이제 유형별 예제를 넘겨 보는 갤러리 역할을 한다.

만든 이유를 설명하는 대목에도 한 문장이 더해졌다.
모델은 내용을 이미 이해하고 있었고 빠진 것은 취향이었으므로
그 취향을 글로 적어 두었다는 것이다.
적어 둔 취향은 강조색 하나를 한두 곳에만 쓰기, 1px 헤어라인, 그림자 없음,
모든 좌표를 4px 격자에 맞추기다.
diagramdesign.dev는 같은 생각을 일반적인 도구는 이 상자를 어디에 둘지 묻지만
이 도구는 이 상자가 존재할 자격이 있는지 묻는다는 말로 요약한다.

만든 이유는 직접 밝혀 두었다.
littlemight.com에 글을 쓰고 BestSelf.co를 운영하는데,
아키텍처 스케치나 순서도나 중요도 피라미드가 필요할 때마다 Claude에게 물으면
사이트의 나머지와 전혀 어울리지 않는 일반적인 둥근 상자 그림이 돌아왔다는
것이다.
그러면 Figma와 30분을 씨름하거나 다이어그램을 그냥 포기하게 되어,
39가지 시각 유형을 갖추고 웹사이트를 읽어 60초 만에 브랜드에 맞추는 스킬을
만들었다고
설명한다.
인용구로 내건 원칙도 있다.
가장 품질을 높이는 조치는 대개 삭제이고, 모든 노드가 자기 자리를 얻어야 하며,
강조색은 독자가 가장 먼저 봐야 할 한두 가지에만 쓰고,
목표 밀도는 10분의 4라는 것이다.

## 제공하는 것

39개 시각 유형은 모두 세 가지 정적 변형으로 제공된다.
미니멀 라이트, 미니멀 다크, 풀 에디토리얼이며 브라우저에서 바로 열 수 있고
빌드 단계도 JavaScript도 외부 이미지 의존도 없다.
유형 목록에는 아키텍처, IT 현행 상태, 순서도, 시퀀스, 상태 기계, ER/데이터 모델,
타임라인, 스윔레인, 사분면, 레이더, 루프/플라이휠, 중첩, 트리, 조직도,
레이어 스택,
벤 다이어그램, 피라미드/퍼널, 막대·선·산점도·트리맵·간트,
메달리온, 데이터 흐름, DP 통합, DP 보안 매트릭스,
그리고 2.5.10에서 추가된 Sankey, 피시본, Wardley 맵, 칸반, 사용자 여정, 배포,
의존성 그래프, UML 클래스, 스토리 맵, 데이터베이스 스키마,
극좌표 차트, 폭포 차트가 포함된다.

이 중 추가 시점은 CHANGELOG와 대조하면 바로잡을 부분이 있다.
CHANGELOG는 2.5를 2.5.0부터 2.5.20까지 묶어 기록하는데,
그 묶음에서 한꺼번에 추가된 열 개 유형은
Sankey부터 데이터베이스 스키마까지다(#118).
극좌표 차트(#134)와 폭포 차트(#191)는 2.6 묶음에서 추가되었다.
2.6(2.6.0~2.6.74, 2026년 8월 20일~10월 10일)에서는
히트맵(#164), 아키텍처 델타(#241), 분해 액소노메트릭(#268),
액소노메트릭 평면도(#270)도 더해져 유형이 44개가 되었다.
아키텍처 델타는 이전·변경·이후 세 패널과 추가, 삭제, 변경, 이동, 재연결을 적는
변경 대장으로 두 시점의 구조 차이를 보여 주는 유형이다.
분해 액소노메트릭은 한 물체의 부품을 2:1 다이메트릭 투영에서 같은 간격으로
떼어 놓는 그림이고, 액소노메트릭 평면도는 같은 투영으로
층 하나나 부지 하나를 위에서 비스듬히 보여 준다.
유형 수를 늘리지 않는 변형도 있다.
선 차트는 슬로프그래프, 릿지라인, 스트림그래프, 범프 차트를,
산점도는 버블과 비스웜을, 트리맵은 마리메코를 같은 참조 문서로 다룬다.
갤러리는 유형마다 01부터 44까지 번호 하나를 주고,
변형과 예제에는 같은 번호에 알파벳을 붙인다.

2.3부터는 의미 패턴(semantic patterns)이 도입되었다.
동작이 중요할 때는 의미 패턴을 먼저 고르고 시각 유형을 나중에 고른다는 구조이며,
팬인 큐와 병목, 반복되는 단계 슬롯, 비정형 입력 변환, 짝지어진 정책 추적,
보안이 확보된 표준 경로, 거버넌스 카탈로그, 보완적 보안 계층,
추적 가능한 블록 분해라는 여덟 가지가 라우팅된다.
CHANGELOG 기준으로 2.3에서 처음 도입된 패턴은 일곱 가지였고,
추적 가능한 블록 분해(#169)와 생애주기 단계 지도(#228)가 2.6에서 더해졌다.
그래서 2026년 10월 11일 기준 README가 라우팅하는 패턴은 아홉 가지이며,
생애주기 단계 지도는 상태 기계 유형으로 보낸다.
추적 가능한 블록 분해를 쓴 다이어그램은 내보낼 때 `--registry`를 붙이면
블록마다 달린 `data-block-*` 메타데이터를 `.registry.json` 파일로 따로 낸다.
이 설계의 목적은 유형 수를 늘리지 않고도 큐나 정책 추적이나 신뢰 경계를
가장 가까운 기존 유형으로 표현하게 하는 것이다.
움직임은 선택 사항이고 별도의 시각 유형을 만들지 않으며,
`none`·`reveal`·`step`·`loop` 모드가 완전한 정적 첫 프레임과 결정론적 타이밍을
갖는다.
동작 축소 설정에서는 완전한 정적 프레임을 보여 주고 재생 컨트롤을 숨긴다.
기본값은 `none`이며 일반 출력은 정적이고 스크립트가 없다.
움직임이 있는 HTML을 이미지로 뽑을 때는 `?motion=static`으로 열고
글꼴 로딩이 끝난 뒤 정적 프레임임을 확인하고 찍으라고 안내한다.

## 브랜드 온보딩

이 스킬의 차별점으로 제시되는 것이 온보딩이다.
기본 팔레트는 제트 블랙과 아토믹 탠저린 조합이지만,
사이트 주소를 주면 홈페이지를 가져와 주요 팔레트와 글꼴 스택을 추출하고
그것을 `paper`, `ink`, `muted`, `accent`, `link` 같은 의미 역할에 매핑한 뒤
제안 차이를 보여 주고 승인을 받아 `references/style-guide.md`에 기록한다.
`<body>` 배경이 `paper`가 되고, 본문 색이 `ink`,
가장 많이 쓰인 브랜드 색(CTA나 링크나 제목)이 `accent`,
`<h1>` 글꼴이 제목 글꼴, `<body>` 글꼴이 노드 이름 글꼴이 되는 식이다.
README의 추출 표에는 보조 글자색이 `muted`, 카드나 컨테이너 배경이 `paper-2`,
`<code>`나 `<pre>` 글꼴이 보조 라벨 글꼴이 되는 항목도 있다.
가져온 홈페이지 HTML은 신뢰할 수 없는 데이터로 다루며,
이 규칙은 문서 동기화 테스트로 강제된다(#160).

기본 팔레트도 2026년 10월에 조정되었다.
CHANGELOG의 미출시 항목에 따르면 밝은 스킨의 강조색을 `#bf4520`으로 어둡게 바꿔
강조색 글자가 바탕 위에서 4.71:1 대비를 내게 했다(#161).
같은 묶음에서 CI에 WCAG 대비 검사가 들어가,
글자 역할은 4.5:1, 꼭 보여야 하는 표식은 3:1을 밝은 바탕과 어두운 바탕 모두에서
넘어야 한다.
기본 글꼴은 Instrument Serif, Geist, Geist Mono를 Google Fonts에서 불러오며
README는 이것이 다이어그램이 하는 유일한 네트워크 요청이라고 적는다.
시스템 글꼴을 요청하거나 스타일 가이드의 글꼴 출처를 `system`으로 두면
네트워크 요청이 전혀 없는 파일이 나온다.

검증 장치도 명시되어 있다.
토큰을 쓰기 전에 `paper` 위의 `ink`가 WCAG AA 대비를 만족하는지 확인하고,
9~12px 크기에서 실패하면 조정값을 제안하며 이유를 설명한다.
브랜드 매칭은 충실도 영수증을 함께 내놓는데,
표본으로 삼은 URL, 정확한 색 역할, 글꼴 계열과 굵기, 글꼴 출처 URL,
그리고 사용된 대체 항목이 기록된다.
모든 템플릿은 인라인 SVG에 접근 가능한 이름과 설명을 부여하고
`role="img"`와 해석되는 `aria-labelledby`, `<title>`과 `<desc>` 슬롯을 갖추며,
ID는 다이어그램과 변형별로 접두사를 붙여 한 페이지에 여러 SVG를 인라인해도
접근성 이름 ID가 충돌하지 않게 한다.
새 프로젝트에서 처음 쓸 때는 스타일 가이드가 기본값인지 확인하고,
기본값이면 온보딩을 돌릴지 토큰을 직접 붙여 넣을지 기본값으로 진행할지 묻는
첫 실행 게이트가 있다.
여러 고객사를 다룰 때는 브랜드를 프로필로 저장하고
프로젝트에 `.diagram-design` 마커를 두어 병렬 작업 공간이 서로 다른 브랜드를
쓰게 할 수
있다.
프로필 라이브러리는 `~/.diagram-design/profiles/`에 있고
Claude Code, Codex, Factory Droid, Pi가 함께 쓴다(2.4, #61).
패키지 갱신이 설치된 `style-guide.md`를 덮어쓸 수 있으므로,
스타일 가이드를 직접 고칠 사람은 저장소를 클론해 로컬 경로로 설치하라고 권한다.

## 가져오기와 출력 조절

기존 다이어그램을 다시 그리는 기능도 있다.
draw.io와 Mermaid와 Excalidraw 소스를 가리키면 같은 내용을 이 디자인 시스템으로
다시 그린다.
draw.io는 `.drawio`, `.drawio.xml`, 다이어그램이 내장된 `.drawio.png`,
`.drawio.svg`를
읽고 압축된 페이로드도 처리하며,
Mermaid는 `.mmd`와 `.mermaid`와 마크다운 안의 펜스 블록을 받고,
Excalidraw는 `.excalidraw`와 `.excalidraw.json` 장면 파일을 받되
텍스트만 파싱하고 렌더링이나 JavaScript 실행, 브라우저, 네트워크는 쓰지 않는다.
가져오기는 2.1의 draw.io(#22), 2.2의 Mermaid(#24), 2.6의 Excalidraw(#192)
순으로 늘었다.
2.6에서는 Mermaid 문장 길이를 4,096자로 제한하고,
draw.io의 중복 셀 ID와 순환하거나 유한하지 않은 좌표를 거부하는 등
입력 파서에 보안 제한도 더해졌다(#258, #281, #283).

핵심은 변환이 아니라 목적지에 맞추는 것이라고 밝히며 네 개의 다이얼을 제시한다.
형식은 `html`·`svg`·`png`·`html+png`이고,
크기는 `doc-inline`부터 `slide-16x9`, `social-og`, `print-a4-landscape`까지이며
`viewBox`뿐 아니라 글자 크기 램프까지 바꾼다.
투사되는 슬라이드에서는 노드 이름이 12px가 아니라 16px가 된다는 설명이 붙는다.
나머지 두 다이얼은 세부 수준과 독자다.
세부 수준은 `faithful`(노드 24개 이하), `balanced`(12개 이하),
`simplified`(7개 이하)이고,
장식, 중복, 말단 묶음, 인프라 순으로 덜어 내는 고정된 사다리를 따른다.
독자는 `engineer`·`mixed`·`executive`이며 노드 수가 아니라 문구를 바꾼다.
예를 들어 `Auth Service / JWT · RS256 · :8443`이
`Auth Service / token check`를 거쳐 `Sign-in`이 된다.
크기 프리셋에는 `doc-wide`, `slide-4x3`, `social-square`,
`print-a3-landscape`(2.6, #248), `print-letter-landscape`, `fit`도 있다.
가져오기가 끝나면 무엇을 합치고 접고 버렸는지 적은 충실도 장부를 내놓으며,
원본의 좌표, 팔레트, 글꼴, 자동 레이아웃은 넘어오지 않고
구성 요소, 관계, 묶음, 방향만 넘어온다.
내보내기는 SVG와 PNG를 지원하며,
PNG는 Playwright로 기본 2배 해상도로 래스터화한다.

설치 경로는 호스트별로 안내되어 있고,
Claude Code는 플러그인 마켓플레이스,
Codex와 Copilot과 Factory Droid는 각자의 CLI,
Pi는 Git 설치, Kiro는 저장소 하위 디렉터리 URL 가져오기,
OpenCode는 디렉터리 복사나 심볼릭 링크를 쓴다.
2026년 10월 11일 기준 README에는 여기에 `npx skills add` 경로가 더해졌다(#199).
이 교차 에이전트 CLI는 Cursor, Cline, Gemini CLI, Windsurf, Amp, Zed, Warp,
Roo, Kilo 같은 Agent Skills 호스트에 스킬 전체를 설치하고,
여러 호스트 루트를 고르면 심볼릭 링크 방식을 권해
한 번의 갱신이 모두에 닿게 한다.
다만 이 설치는 마켓플레이스 갱신을 따라가지 않고 `npx skills update`로 직접
갱신해야 하며,
`/export-diagram`, `/import-mermaid`, `/profile`, `/doctor` 같은 명령은
네이티브 패키지에만 들어 있다.
README는 공식 빌드가 이 저장소에서만 나오고,
플러그인 디렉터리 등재는 Cathryn Lavery의 회사인 LittleMight가 하므로
다른 이름의 등재는 비공식 사본이라고 밝힌다.
스킬이 네트워크로 보내는 것은 `PRIVACY.md`에 정리되어 있다.

## 분석

### 이 스킬이 파는 것은 기능이 아니라 기본값이다

39개 유형이라는 숫자가 눈에 띄지만 경쟁 요소는 유형 수가 아니다.
Mermaid도 대부분의 유형을 지원하고 draw.io는 더 많은 것을 그릴 수 있다.
이 저장소가 실제로 파는 것은 아무 지시 없이 나오는 결과물의 품질,
즉 기본값이다.

저장소 설명의 표현이 그 점을 분명히 한다.
그림자 없음, Mermaid 슬롭 없음, Figma 없음, 일반적인 둥근 상자 없음,
30분짜리 색 고르기 없음.
전부 하지 않는 것의 목록이며, 만들 수 있는 것의 목록이 아니다.
목표 밀도 4/10과 강조색을 한두 곳에만 쓴다는 원칙도 같은 성격의 제약이다.

이 구성은 에이전트 시대의 도구 설계에서 반복되는 패턴이다.
생성 능력 자체는 모델이 이미 갖고 있으므로,
도구의 값어치는 무엇을 만들 수 있는가가 아니라
요청하지 않아도 지켜지는 규칙이 무엇인가에서 나온다.
스킬이라는 형식이 이 역할에 잘 맞는 이유이기도 하다.

### 브랜드 온보딩이 이 프로젝트의 실질적 차별점이다

다이어그램 생성 도구는 많지만 결과물이 특정 사이트의 시각 언어와 맞아떨어지게
만드는 도구는 드물다.
이 스킬은 웹사이트에서 색과 글꼴을 추출해 의미 역할에 매핑하고,
그 토큰을 39개 유형 전체가 공유하게 한다.
`accent`라는 이름으로 참조하고 `#eb6c36` 같은 값으로 참조하지 않는다는 설계가
이 공유를 가능하게 한다.
이 원칙은 그사이 저장소 내부에도 적용되었다.
유형별 참조 문서가 기본 스킨의 16진수 값을 직접 적어 두어
사용자 지정 바탕에서 영역 라벨 불투명도가 깨진다는 이슈가 있었고(#65),
이후 참조 문서가 스킨의 역할 토큰을 쓰도록 바뀌었다.
유형이 44개로 늘어난 2026년 10월 기준으로도 공유 구조는 같다.

이 방식은 디자인 시스템의 토큰 개념을 그대로 가져온 것이다.
값이 아니라 역할로 참조하면 브랜드 교체가 토큰 교체로 끝나고,
프로필 저장과 프로젝트별 마커로 여러 브랜드를 병렬 운용할 수 있다.
사람이 쓰는 디자인 시스템에서는 당연한 구조인데,
에이전트가 생성하는 산출물에 같은 구조를 적용한 사례는 아직 많지 않다.

충실도 영수증이라는 장치는 여기서 한 걸음 더 간다.
어떤 URL을 표본으로 삼았고 어떤 색을 어떤 역할에 매핑했으며
글꼴을 어디서 가져왔고 무엇으로 대체했는지를 기록한다는 것은,
자동 추출의 결과를 사람이 검증할 수 있게 만든다는 뜻이다.
생성 결과를 믿으라고 요구하는 대신 근거를 제출하는 설계이며,
에이전트 도구가 갖추어야 할 기본 태도에 가깝다.

### 접근성과 검증을 기본 경로에 넣은 점이 눈에 띈다

WCAG AA 대비 검사를 토큰 기록 전에 수행하고 실패 시 조정값을 제안한다는 것,
모든 SVG에 `role="img"`와 `aria-labelledby`와 `<title>`·`<desc>`를 넣는다는 것,
ID를 다이어그램과 변형별로 접두사 처리해 중복을 막는다는 것은
접근성을 선택 기능이 아니라 출력 경로의 일부로 둔 설계다.

이 선택이 중요한 이유는 다이어그램이 접근성에서 가장 취약한 산출물이기 때문이다.
이미지로 내보낸 다이어그램은 대체 텍스트가 없으면 스크린 리더 사용자에게
존재하지
않는 것과 같고, 실무에서 대체 텍스트는 거의 작성되지 않는다.
생성 단계에서 접근 가능한 이름을 강제하면 그 공백이 기본적으로 메워진다.

움직임 처리도 같은 태도를 보인다.
기본값이 정적이고, 움직임을 쓰더라도 완전한 정적 첫 프레임을 갖추며,
동작 축소 설정에서는 정적 프레임만 보여 준다는 규칙이다.
그리고 움직임 HTML은 검토된 컨트롤러만 쓰고
임의의 인라인 스크립트와 원격 자산과 실행 가능한 HTML 속성은 거부한다고
명시한다.
생성 산출물이 실행 가능한 코드를 담을 때 생기는 위험을 인식한 설계다.

## 비평

### 규칙을 코드가 아니라 문서로 강제하므로 준수 여부가 보장되지 않는다

이 스킬의 핵심 자산은 스타일 규칙과 의미 패턴과 금지 목록이다.
그런데 그것들은 전부 마크다운 참조 문서로 존재하고,
실제 준수는 모델이 그 문서를 읽고 따르느냐에 달려 있다.
그림자를 쓰지 말라는 규칙이 지켜지는지 검사하는 장치는 명시되어 있지 않다.

이 구조는 스킬이라는 형식 자체의 한계이기도 하다.
문서로 된 제약은 모델의 문맥 관리와 지시 준수 능력에 의존하며,
긴 세션이나 복잡한 요청에서 가장 먼저 잊히는 것이 그런 제약이다.
39개 유형과 8개 의미 패턴과 4개 다이얼을 동시에 다루는 상황에서
목표 밀도 4/10 같은 미세한 규칙이 끝까지 유지된다고 보장할 근거는 없다.
2026년 10월 11일 기준으로 이 숫자는 44개 유형과 9개 의미 패턴으로 늘었다.

해결책은 검증기다.
생성된 HTML을 파싱해 그림자 속성이 있는지, 강조색이 몇 번 쓰였는지,
노드 수가 밀도 기준을 넘는지, `aria-labelledby`가 실제로 해석되는지 검사하는
`doctor` 계열 도구가 그 역할을 할 수 있고 저장소에도 그런 명령이 언급된다.
다만 그것이 필수 경로인지 선택 점검인지는 문서에서 분명하지 않으며,
규칙 기반 도구에서 이 구분은 품질의 핵심이다.

다시 확인해 보니 검증 장치는 이 문단이 처음 쓰일 때 읽은 것보다 많고,
그 범위는 두 층으로 나뉜다.
첫째, `SKILL.md`의 마무리 체크리스트는 설치된 스킬 안의
`scripts/self_check.py`를 생성 파일에 돌려 통과했는지 확인하라고 한다.
하지만 이 스크립트가 보는 것은 접근 가능한 SVG 계약, 단일 파일 안전성,
움직임의 기본 조건이고, 그림자나 강조색 횟수나 밀도는 보지 않는다.
체크리스트의 나머지 항목인 4px 격자, 연결선 규칙, 범례 위치는
모델이 스스로 답하는 질문 형태로 남아 있다.
둘째, `lint-skin.py`, `lint-render.py`, `verify-geometry.py`,
WCAG 대비 검사 같은 CI 게이트는 저장소의 템플릿과 예제에 대해 풀 리퀘스트마다
Linux, Windows, macOS에서 돈다.
README의 비교 표가 말하는 겹침과 잘림 CI 검사도 이 층이다.
이것은 사용자가 받은 다이어그램이 아니라 스킬이 본보기로 싣는 파일의 품질을
지키는 장치다.
따라서 이 비평의 요지는 그대로 유효하되,
사용자 산출물에 대한 강제 검증은 접근성과 안전성 범위로 한정되어 있다고
정정해 두는 편이 정확하다.

### 편집 품질이라는 기준이 주관적이라 검증되지 않는다

이 프로젝트는 편집 품질을 표방하고 Mermaid 슬롭과 대비한다.
그런데 편집 품질이 무엇인지에 대한 정의는
밀도 4/10과 강조색 한두 곳이라는 두 개의 수치 외에는 제시되지 않는다.
나머지는 스크린숏으로 보여 주는 방식이다.

이 대목은 README를 다시 읽고 바로잡아야 한다.
README의 디자인 시스템 요약에는 수치로 된 규칙이 더 있다.
초점 요소는 다이어그램마다 한두 개, 글꼴은 세 계열,
테두리는 1px 헤어라인, 그림자 없음, 모서리 반경은 최대 10px,
모든 좌표와 너비와 간격은 4로 나누어떨어져야 한다는 것이다.
저자는 4px 규칙을 타협 불가라고 하며
다이어그램이 AI가 만든 것처럼 느껴지지 않게 하는 장치로 설명한다.
그래서 편집 품질의 정의가 두 수치뿐이라는 앞의 서술은 틀렸다.
다만 이 규칙들 역시 대부분 검사가 아니라 지시로 존재한다는 점에서
첫 번째 비평과 이어진다.

이 구성의 문제는 비교 기준의 부재다.
Mermaid 출력이 못생겼다는 데 많은 사람이 동의하겠지만,
그 못생김이 Mermaid의 기본 테마 때문인지 자동 레이아웃 알고리즘 때문인지,
아니면 사용자가 노드를 너무 많이 넣기 때문인지는 구분되지 않는다.
후자가 주된 원인이라면 이 스킬의 밀도 규칙이 진짜 기여이고
나머지 시각 처리는 부차적이 된다.

더 실질적인 문제는 레이아웃이다.
다이어그램 품질의 상당 부분은 배치 알고리즘에서 오고,
교차하는 간선을 줄이고 계층을 정렬하는 일은 오랜 연구가 쌓인 영역이다.
이 스킬은 HTML과 SVG를 직접 생성하므로
배치를 모델의 판단에 맡기는 구조인데,
노드가 수십 개로 늘었을 때 그 판단이 얼마나 버티는지에 대한 자료는 없다.
공개된 예시가 대체로 정돈된 소규모 다이어그램이라는 점이 이 의문을 키운다.

2026년 10월에 재구성된 README는 이 한계를 스스로 인정한다.
새로 들어간 비교 표는 Mermaid와 PlantUML의 배치를 자동,
draw.io와 Excalidraw를 수동, 이 스킬을 에이전트가 4px 격자에 놓는 방식으로
구분하고, 단점이 실재한다고 적는다.
출력 품질은 함께 돌리는 모델에 달려 있고,
같은 프롬프트도 두 번 돌리면 배치가 달라질 수 있으며,
결과물은 편집 가능한 원본 형식이 아니어서
풀 리퀘스트에서 비교할 텍스트도 상자를 끌어 옮길 캔버스도 없다는 것이다.
Git에 살면서 스프린트마다 바뀌는 문서에는 여전히 Mermaid가 낫고,
이 스킬은 발행할 다이어그램을 위한 것이라고 선을 긋는다.
가져오기의 세부 수준 다이얼이 노드를 24개, 12개, 7개 이하로 묶는 것도
배치 판단을 모델이 감당할 수 있는 규모로 제한하는 장치로 읽힌다.
이것은 원문에 없는 해석이다.

### 호스트 다변화가 유지보수 표면을 빠르게 넓힌다

README에 열거된 설치 대상만 Claude Code, Codex, GitHub Copilot, Factory Droid,
Claude Cowork, Pi, Kiro, OpenCode에 이른다.
각 호스트마다 설치 명령과 갱신 방식과 스킬 탐색 경로가 다르고,
문서는 그 차이를 상세히 적어 준다.
사용자에게는 친절하지만 유지보수 관점에서는 부담이 큰 구성이다.

호스트별 플러그인 체계는 아직 표준화되지 않았고 각자 빠르게 바뀐다.
Claude Code가 서드파티 마켓플레이스의 자동 갱신을 기본으로 끈다는 점,
Factory Droid가 매니페스트 버전이 아니라 커밋으로 Git 플러그인을 추적한다는 점,
Cowork 조직 마켓플레이스가 비공개 저장소를 요구해 미러링이 필요하다는 점,
Pi에는 자동 패키지 갱신이 없다는 점이 전부 문서에 적혀 있는데,
이 항목들은 전부 상대 쪽 변경으로 무효가 될 수 있는 정보다.

이 부담은 스킬 생태계 전반의 문제이기도 하다.
스킬은 본질적으로 텍스트 파일 묶음이라 이식이 쉽지만,
배포와 갱신 경로는 호스트마다 다르므로 이식성이 배포성으로 이어지지 않는다.
결과적으로 인기 있는 스킬일수록 문서의 상당 부분이 설치 안내에 소모되고,
그 안내가 낡는 속도는 스킬 본체가 낡는 속도보다 빠르다.

그 뒤의 변화가 이 진단을 뒷받침한다.
2026년 10월 11일 기준 README는 Cursor, Cline, Gemini CLI, Windsurf, Amp, Zed,
Warp, Roo, Kilo까지 `npx skills add`로 묶어 안내하면서,
이 독립 설치가 마켓플레이스 갱신을 따라가지 않는다는 점과
기존 독립 설치를 지우고 Codex 마켓플레이스로 옮기는 일회성 이전 절차를
따로 적어야 했다.
Cowork 조직 마켓플레이스의 자동 동기화는 미러의 기본 브랜치에
플러그인 버전을 올린 풀 리퀘스트가 병합될 때만 돌고
직접 푸시는 웹훅을 일으키지 않는다는 설명도 추가되었다.
CHANGELOG에는 Cowork 설명 길이 제한에 맞춰 플러그인 설명을 줄인 기록(#216)과
OpenAI 플러그인 디렉터리용 Codex 매니페스트 준비(#264)도 있다.
반면 diagramdesign.dev 첫 화면은 같은 날 5개 에이전트라고 적고 있어,
문서끼리도 지원 범위를 같은 숫자로 말하지 못한다.

### 별 3만 9천 개라는 숫자가 실사용을 보증하지는 않는다

2026년 4월에 만들어져 다섯 달 만에 별 3만 9천 개는 대단히 빠른 성장이다.
그러나 이 숫자를 도구의 성숙도로 읽기는 어렵다.
스킬과 프롬프트 모음 저장소는 설치가 가볍고 공유가 쉬워
별이 실사용보다 훨씬 빠르게 붙는 범주이기 때문이다.

실제로 확인 가능한 신호는 다른 곳에 있다.
버전 이력을 보면 2.0에서 루프가, 2.3에서 의미 패턴과 선택적 움직임이,
2.5.10에서 열 개 유형이 추가되는 등 갱신은 활발하다.
반면 이슈와 풀 리퀘스트의 성격, 기여자 수, 외부에서 만든 사례,
그리고 생성된 다이어그램이 실제 블로그와 문서에 얼마나 실렸는지는
저장소 정보만으로 알 수 없다.

2026년 10월 11일에 다시 보면 숫자는 더 커졌고 신호도 조금 더 보인다.
별은 49,188개로 늘었고,
diagramdesign.dev는 같은 날에도 별 17k+와 GitHub Trending 1위 기록을 내걸고 있어
홈페이지 수치가 저장소보다 한참 뒤처져 있다.
버전은 병합마다 자동으로 올라가 2.6 묶음만 2.6.0에서 2.6.74까지 이어졌다(#172).
열린 풀 리퀘스트는 63개, 열린 이슈는 20개다(GitHub 검색 API 기준).
외부 기여는 실제로 들어오고 있다.
히트맵(#164), 폭포 차트(#191), 스트림그래프(#140) 같은 유형과 변형이
외부 기여로 들어왔고,
draw.io와 Excalidraw 파서의 보안 제한도 외부 기여자의 풀 리퀘스트로 병합되었다.
최근에는 관리자가 여러 풀 리퀘스트의 수정을 한 번에 묶어 반영하는 커밋이 늘었다.
예를 들어 #350은 아홉 개 풀 리퀘스트의 차트 검증기 수정을 모았다.
그리고 `CONTRIBUTING.md`는 쓰기 권한이 없는 기여자가 동시에 열 수 있는
풀 리퀘스트를 다섯 개로 제한한다.
기여가 검토 능력을 앞지르기 시작했다는 신호로 읽히며, 이것은 해석이다.
PlantUML 가져오기(#358), 서비스 블루프린트 유형(#360),
RTL과 아랍어 라벨 지원(#353) 같은 제안이 열린 채로 대기 중이다.

GeekNews 반응도 아직 기대 표명 단계에 가깝다.
toida는 발표 자료 만들 때 쓰면 좋겠다고 적었고[^toida],
다른 반응도 짧은 호응이다.[^tapioca]
그 뒤에 달린 daumkakao의 댓글도 엄청나다는 감탄 한 줄이어서[^daumkakao]
2026년 10월 11일 기준으로도 실사용 보고는 없다.
Hacker News에는 두 건의 제출이 있었지만 각각 2점과 1점에 댓글이 없어
실사용 보고를 찾기 어렵다.
2026년 10월 11일에 다시 확인해도 두 제출 모두 살아 있는 댓글이 없다.
도입을 검토한다면 별 수보다 자기 프로젝트의 실제 다이어그램 서너 개를
이 스킬로 다시 그려 보는 쪽이 훨씬 빠른 판정이 된다.

## 인사이트

### 스킬의 값어치는 능력이 아니라 거절 목록에서 나온다

이 저장소의 설명문에서 가장 많은 자리를 차지하는 것은 하지 않는 것들이다.
그림자 없음, Mermaid 슬롭 없음, 일반적인 둥근 상자 없음,
빌드 단계 없음, JavaScript 없음, 외부 이미지 의존 없음.
기능 목록이 아니라 금지 목록이 제품 설명의 중심에 있다.

이 구성이 합리적인 이유는 생성 모델의 성질에 있다.
모델은 요청받은 것을 대체로 만들어 내지만, 요청받지 않은 것도 만들어 낸다.
그림자와 그러데이션과 과도한 색은 아무도 요청하지 않았는데 나타나고,
그것들이 결과물을 아마추어처럼 보이게 한다.
따라서 품질을 올리는 가장 값싼 개입은 능력을 더하는 것이 아니라
기본 산출물에서 무엇을 빼는지를 정하는 것이다.

이 관찰은 스킬을 직접 만드는 사람에게 실용적인 지침이 된다.
스킬 문서에 무엇을 할 수 있는지 나열하는 것보다,
이 영역에서 반복적으로 나타나는 나쁜 기본값이 무엇인지 목록화하고
그것을 금지하는 편이 산출물의 평균 품질을 더 올린다.
사내 스킬이라면 우리 조직에서 자주 반려되는 산출물의 특징을 모으는 것이
그 목록의 출발점이다.

### 브랜드 토큰 추출은 디자인 시스템 없는 조직에 자동 디자인 시스템을 만든다

이 스킬의 온보딩은 사이트에서 색과 글꼴을 뽑아 의미 역할에 매핑한다.
디자인 시스템이 있는 조직에서는 당연히 이미 존재하는 매핑이지만,
디자인 시스템이 없는 조직에서는 이 추출이 사실상 최초의 토큰 정의가 된다.

여기서 흥미로운 2차 효과가 생긴다.
토큰이 다이어그램을 위해 정의되었더라도,
일단 `paper`·`ink`·`muted`·`accent`라는 역할 이름과 값의 쌍이 파일로 존재하면
그것은 다른 산출물에도 재사용될 수 있는 자산이 된다.
발표 자료, 사내 문서 템플릿, README 배지, 생성 이미지의 색 지정이
같은 토큰을 참조할 수 있다.

이 경로는 전통적인 디자인 시스템 도입 경로와 방향이 반대다.
보통은 디자인 팀이 시스템을 정의하고 도구가 그것을 따르는데,
여기서는 도구가 필요해서 만든 추출물이 시스템의 씨앗이 된다.
디자인 인력이 없는 소규모 팀에서 일관성을 확보하는 현실적인 경로이며,
같은 방식이 슬라이드나 문서 생성 스킬에도 적용될 수 있다.

다만 주의할 점이 있다.
자동 추출은 현재 사이트의 상태를 그대로 옮기므로,
사이트 자체가 일관되지 않으면 그 비일관성이 토큰에 고정된다.
충실도 영수증이 표본 URL을 기록하는 이유가 여기에 있고,
추출 결과를 사람이 한 번 검토하는 단계가 빠지면
잘못된 기준이 전 산출물로 퍼진다.

### 그림 생성의 병목은 그리기가 아니라 언제 그리지 않을지 정하는 일이다

저자가 인용구로 내건 원칙은 가장 품질을 높이는 조치가 대개 삭제라는 것이다.
그리고 목표 밀도를 10분의 4로 정해 두었다.
생성 비용이 0에 가까워진 환경에서 이 제약이 갖는 의미는 크다.

다이어그램을 손으로 그리던 시절에는 비용 자체가 절제를 강제했다.
노드 하나를 더하는 데 시간이 들었으므로 자연히 꼭 필요한 것만 남았다.
생성이 즉시 이루어지면 그 자연적 제동이 사라지고,
모든 관계를 다 그려 넣은 읽을 수 없는 그림이 기본값이 된다.
Mermaid 슬롭이라는 표현이 가리키는 것도 대체로 이 현상이다.

그래서 이 영역의 진짜 과제는 더 많은 유형을 지원하는 것이 아니라
언제 다이어그램을 그리지 않을지, 무엇을 그리지 않을지 판단하는 것이다.
표로 충분한 것, 문장 두 줄로 충분한 것, 그리고 아예 설명이 필요 없는 것을
구분하는 판단은 아직 사람의 몫이다.
스킬이 밀도 목표를 숫자로 명시한 것은 그 판단의 일부를 자동화하려는 시도이고,
이런 종류의 수치 제약이 생성 도구 설계에서 앞으로 더 흔해질 것이다.

문서 작성 전반에 같은 원리가 적용된다.
생성이 싸질수록 편집자의 역할이 커지고,
편집자의 핵심 기술은 무엇을 넣을지가 아니라 무엇을 뺄지를 정하는 것이다.
도구가 그 역할의 일부를 기본값으로 가져가면,
사람은 더 상위의 판단, 즉 이 설명에 그림이 필요한가에 집중할 수 있다.

### 자기 완결 HTML을 산출물로 택한 선택이 장기 보존성을 결정한다

이 스킬은 결과를 자기 완결적인 HTML과 인라인 SVG로 낸다.
빌드 단계도 JavaScript도 외부 이미지 의존도 없다는 조건이 붙는다.
사소해 보이지만 산출물의 수명을 결정하는 선택이다.

다이어그램은 문서 중에서 가장 잘 썩는 자산이다.
Figma 링크는 계정과 권한에 묶이고,
이미지 파일은 원본과 분리되어 수정이 불가능해지며,
Mermaid 블록은 렌더러 버전에 따라 모양이 바뀌고,
draw.io 파일은 전용 편집기가 있어야 열린다.
반면 인라인 SVG가 든 단일 HTML 파일은 브라우저만 있으면 열리고,
텍스트이므로 버전 관리에서 차이를 볼 수 있으며, 부분 수정이 가능하다.

이 특성은 에이전트가 산출물을 다시 다루는 시나리오에서 특히 값이 커진다.
다음에 같은 다이어그램을 수정해 달라고 요청할 때,
에이전트가 읽고 고칠 수 있는 형태로 남아 있느냐가 재작업 비용을 가른다.
이미지로만 남은 다이어그램은 매번 처음부터 다시 만들어야 하고,
그 과정에서 이전 결정이 소실된다.

그래서 생성 도구를 고를 때 물어야 할 질문이 하나 추가된다.
이 도구의 산출물을 6개월 뒤에 사람이 열 수 있는가,
그리고 에이전트가 읽고 부분 수정할 수 있는가.
이 질문은 다이어그램만이 아니라
슬라이드와 보고서와 대시보드에도 똑같이 적용되며,
생성이 값싸질수록 산출물의 형식이 더 중요해지는 역설을 만든다.
