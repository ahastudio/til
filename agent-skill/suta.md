## 소개

suta는 Claude Code나 Codex가 UI를 만들 때 읽는 에이전트 스킬이다.
레이아웃·색·모션 기준과 UI 패턴 56종의 코드를 한 스킬에 담았다.
README는 AI로 UI를 만들 때마다 비슷한 카드와 과한 색상, 불필요한 장식이
반복되는 게 불편해서 만들었다고 동기를 밝힌다.
저자 Guksu(GeekNews 아이디 yung3152)는 이를 디자인의 AI slop이라 부르고,
그것을 줄이는 것을 목표로 삼는다.
이름은 수타(手打)에서 왔고, 기계로 찍어낸 면이 아니라 손으로 친 면처럼
손으로 다듬은 UI를 지향한다는 뜻이다.

저장소는 2026년 8월 19일에 만들어졌고, 2026년 10월 11일에 0.10.0 릴리스가
나왔다.
라이선스는 MIT이며, 패턴 코드는 TypeScript와 React로 쓰여 있다.
README 배지에는 테스트 633개 통과가 적혀 있다.
스킬 본문과 패턴 설명서는 한국어로 쓰여 있고,
README는 영어 요청으로 시험했을 때 영어 UI 문구와 영어 답변이 나왔다고
한 차례 기록을 덧붙인다.
홈페이지는 GitHub Pages에 올린 패턴 데모 사이트로,
패턴마다 실제로 움직이는 화면을 만져 볼 수 있다.

GeekNews 글이 함께 보면 좋은 글로 묶은 다이어그램 스킬은
`agent-skill/diagram-design.md`에 정리되어 있다.
다이어그램이 아니라 화면 UI를 다룬다는 점에서 suta와는 대상이 다르다.
같은 문제의식을 다른 방식으로 푸는 스킬로는
`agent-skill/taste-skill.md`(다이얼로 실험성을 조절하는 방식),
`agent-skill/hallmark.md`(Build·Audit·Redesign·Study 명령 방식),
`agent-skill/emilkowalski-skills.md`(애니메이션 판단 기준)가 있다.

## 구성

### 스킬 하나에 패턴 56종

설치되는 것은 `skills/suta/` 폴더 하나다.
에이전트는 시작할 때 `SKILL.md`의 설명문만 읽어 두고,
UI 요청이 오면 본문을 열어 필요한 패턴만 그때그때 읽는다.
안내 문서는 이 구조 덕분에 다른 스킬과 함께 설치해도 에이전트의 스킬 목록을
차지하지 않는다고 설명한다.

| 경로                         | 내용                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| `SKILL.md`                   | 작업 절차, AI 슬롭 금지선, 레이아웃·모션 값, 패턴 카탈로그 |
| `patterns/{패턴}/PATTERN.md` | 언제 쓰는가, 왜 이 기술인가, 파일 표, 사용법, 주의사항     |
| `patterns/{패턴}/assets/`    | 의존성 없는 코어(`.ts`), React 래퍼(`.tsx`), CSS           |
| `scripts/audit.mjs`          | 레이아웃·모션 규칙을 한 번에 돌리는 통합 검사              |
| `scripts/post-edit-hook.mjs` | 파일을 고칠 때마다 같은 검사를 돌리는 훅                   |

패턴은 등장과 전환(11종), 로딩과 진행(7종), 피드백(6종), 내비게이션(7종),
제스처(8종), 컨트롤(12종), 표면과 스타일(1종), 원칙과 검토(4종)로 나뉜다.
모달·바텀시트·토스트·드롭다운·캐러셀 같은 컴포넌트와 함께,
`layout-principles`·`motion-principles` 같은 기준 문서와
`layout-audit`·`motion-audit` 같은 검사 도구도 패턴의 한 종류로 들어 있다.

여러 패턴이 함께 쓰는 로직은 패턴마다 같은 파일로 복사되어 있다.
그런 파일의 첫 줄에는 `@shared-core` 헤더가 붙고,
저장소의 `validateSkills.mjs`가 원본과 내용이 같은지 확인한다.
패턴 하나만 떼어 가도 import 경로가 끊기지 않게 하려는 설계다.

### 바텀시트 패턴을 예로 보면

`bottom-sheet`는 드래그 추적과 닫기 판정을 맡는 `createSheetDrag.ts`,
시트·백드롭·이동을 정의하는 `bottom-sheet.css`,
드래그와 백드롭·Esc·스크롤 잠금을 묶은 `BottomSheet.tsx`로 이루어진다.
설명서는 라이브러리 대신 포인터 이벤트와 CSS transition을 쓴 이유를
드래그 중에는 transition을 끄고 손가락을 따라가고,
놓으면 CSS가 스냅백이나 닫힘을 처리하는 분업으로 설명한다.
React가 아닌 프로젝트는 코어와 CSS만 가져가 `data-open`을 토글하면 된다.

## 동작 방식

### 에이전트가 따르는 12단계

`SKILL.md`의 작업 절차는 코드 작성보다 덜어내기와 순서 정하기를 앞에 둔다.

1. 프로젝트의 프레임워크, TypeScript 여부, 스타일 방식, 기존 토큰을 읽는다.
2. 기존 화면을 고칠 때는 값보다 중복을 먼저 없앤다.
같은 정보가 두 곳에 있거나, 같은 행동의 입구가 둘 이상이거나,
위아래 고정 줄이 여럿이면 하나로 줄인다.
3. 화면 요소를 적고 순위를 매긴다. 1순위는 하나이고,
넣을 이유를 한 문장으로 말할 수 없는 요소는 뺀다.
4. 톤을 정한다. UI의 유채색은 강조색 하나와 오류 빨강까지다.
5. 금지선을 확인한다.
6. 요청을 화면 요소로 쪼개 카탈로그에서 패턴을 고른다.
7. 고른 패턴의 `PATTERN.md`를 끝까지 읽는다.
8. `assets/`를 프로젝트에 복사해 맞춘다.
9. 값을 토큰에 연결한다.
10. `audit.mjs`를 돌려 error가 0이 될 때까지 고친다.
11. 마무리 체크리스트를 확인한다.
12. 어떤 패턴을 왜 썼는지 1~2줄로 보고한다.

6단계의 예시는 구체적이다.
국수집 주문 화면이면 `quantity-stepper`, `bottom-sheet`, `loading-button`,
`toast-stack`을 고르고, 증권 사이트면 `search-suggest`,
`segmented-control`, `tab-indicator`, `modal-dialog`, `toast-stack`을 고른다.
맞는 패턴이 없으면 금지선만 지켜 구현한다.

### 금지선은 AI가 흔히 하는 것과 대신할 것의 짝이다

금지선은 레이아웃, 글자·색·면, 모션, 상호작용·피드백, 접근성, CSS 구조의
여섯 표로 나뉜다.
각 행은 AI가 흔히 하는 것, 대신할 것, 근거 패턴의 세 칸이다.

| AI가 흔히 하는 것                                  | 대신                                                   |
| -------------------------------------------------- | ------------------------------------------------------ |
| 어떤 화면이든 히어로 → 카드 3장 → 버튼             | 화면 유형의 뼈대에서 시작한다                          |
| 모든 섹션을 카드로 감싸고 카드 안에 상자를 또 넣음 | 간격·얇은 선·옅은 바탕으로 묶고, 카드는 한 겹만        |
| 강조색으로 프레임워크 기본 파랑·남색·보라          | 서비스 성격에서 하나를 고르고 이유를 한 줄 남긴다      |
| 상태마다 주황·초록·파랑·노랑 알약                  | 무채색 + 강조색 하나 + 오류 빨강                       |
| 이모지를 아이콘·사진 대신 사용                     | 24 격자·선 1.75의 선 아이콘 한 벌                      |
| `transition: all`                                  | 움직일 속성을 이름으로 나열                            |
| `height`·`top` 애니메이션                          | `transform`·`opacity`만, 높이는 grid 기법, 위치는 FLIP |
| `div`에 `onClick`                                  | `button`·`a`·`input`·`dialog` 같은 기본 요소           |
| 동작 줄이기 설정 무시                              | 모든 CSS에 `prefers-reduced-motion` 블록               |
| 한국어 문구가 단어 중간에서 줄바꿈                 | `word-break: keep-all`                                 |

강조색 기본값은 거의 검정이다.
요청에 브랜드나 업종 같은 근거가 없으면 거의 검정을 쓰라는 규칙인데,
`tone.md`는 근거 없이 고른 색은 파랑이든 청록이든 AI가 늘 고르는 색이
된다고 이유를 단다.
기본값을 그대로 두면 모든 서비스가 같은 무채색이 된다는 경고도
`layout-principles`에 함께 적혀 있다.

### 기준값의 출처는 국내 앱 화면이다

레이아웃과 톤의 숫자는 국내 앱 31곳의 화면 1,104장과 웹사이트 19곳을 재서
뽑았다고 밝힌다.
모은 화면은 1,116장이지만 앱 화면이 아닌 12장을 빼고 집계했기 때문에
문서에 두 숫자가 함께 나온다.
예를 들어 31곳 중 25곳(81%)이 UI 체계 색을 2종 이하로 쓰고,
잘 만든 앱 화면의 87%에는 옅은 색 면이 없으며,
65%는 채운 버튼이 0개라는 수치가 금지선의 근거로 붙어 있다.

| 무엇        | 값                                                                    |
| ----------- | --------------------------------------------------------------------- |
| 간격 척도   | 4·8·12·16·24·32·48·64px, 묶음 안 8, 묶음 사이 24, 구역 사이 32        |
| 글자 크기   | 12(하한)·14(모바일 본문 하한)·16(본문)·20·24·32·40px, 한 화면에 4~5종 |
| 글자 색     | 주 `#1b1e24`, 보조 `#4b5260`, 옅은 `#646b77`, 모두 4.5:1 이상         |
| 면          | 흰 면 `#fff` + 옅은 바탕 `#f2f3f5`, 카드는 테두리·그림자 없이         |
| 상태 색     | 오류·할인 `#c8341f`, 완료 `#13795b`, 주의·정보는 색을 두지 않는다     |
| 등락 색     | 상승 `#d0262d`, 하락 `#1b64da`(국내 관례), 늘 부호나 ▲▼와 함께        |
| 굵기·반경   | 굵기 400·600·700, 반경 8·12·24px                                      |
| 누르는 영역 | 44px, 입력칸·주 버튼 높이 48px                                        |

증권 화면의 상승·하락 색은 상태 색이 아니라 시장의 약속으로 따로 센다.
흔히 쓰는 밝은 빨강·파랑(`#e62c28`, `#2272eb` 등)은 흰 면에서 4.3~4.7:1이라
작은 글자에서 4.5:1을 넘기 어렵고,
일반 Claude가 만든 증권 화면의 axe 색 대비 위반 대부분이 이 색이었다고 한다.
그래서 토큰 값은 대비를 맞춘 짙은 색으로 정해 두었다.

### 모션은 크기에 따라 시간이 정해진다

| 무엇이 움직이는가                 | 시간      | 이징                                          |
| --------------------------------- | --------- | --------------------------------------------- |
| 색·불투명도 상태 변화             | 100ms     | ease-out `cubic-bezier(0.22, 1, 0.36, 1)`     |
| 작은 요소 등장·퇴장(툴팁·토글)    | 150ms     | ease-out                                      |
| 컴포넌트 전환(탭·아코디언·토스트) | 250ms     | ease-out                                      |
| 화면 크기의 이동(시트·모달)       | 350ms     | drawer `cubic-bezier(0.32, 0.72, 0, 1)`       |
| 화면 전환·카드 확장               | 420ms     | drawer                                        |
| 살짝 넘쳤다 돌아옴(좋아요 팝)     | 150~250ms | overshoot `cubic-bezier(0.34, 1.56, 0.64, 1)` |

퇴장은 진입의 3/4이고 퇴장에도 ease-out을 쓴다.
목록은 30ms 간격으로 처음 10개까지만 차례로 등장시킨다.
하루에 100번 보는 것은 움직이지 않는다는 규칙도 있다.
reduced-motion에서는 시간을 1ms·80ms·120ms로 줄이는데,
0ms로 두면 `transitionend`가 오지 않기 때문이라고 이유를 적어 두었다.

## 검사

### 통합 검사와 편집 후 훅

`audit.mjs`는 레이아웃 규칙 16개와 모션 규칙 9개를 한 번에 돌리고
결과를 `file:line`으로 낸다.
Node 22.18 이상이 필요하며, 그보다 낮으면 `--experimental-strip-types`를
붙여 실행한다.

```bash
node skills/suta/scripts/audit.mjs src/                # 폴더 재귀
node skills/suta/scripts/audit.mjs src/ --json         # 기계가 읽을 JSON
node skills/suta/scripts/audit.mjs src/ --warn-only    # 기존 코드에 단계적으로 적용
node skills/suta/scripts/audit.mjs src/ --errors-only  # CI 로그를 짧게
```

error로 막는 것은 확실한 결함뿐이다.
11px 미만 글자, `width`·`height`·`top` 같은 레이아웃 속성 애니메이션,
`transition: all`, 움직임이 있는데 reduced-motion 블록이 없는 파일이 그렇다.
카드 안 카드, 효과 남발, 4px 격자 밖 간격, 옅은 색 면, 유채색 3계열 이상,
이모지 아이콘, `100vh`, 16px 미만 입력칸 글자 같은 것은 warn으로 남기고
판단은 원칙에 맡긴다.
의도한 예외는 이유를 적은 주석으로 선언한다.

```css
.axis-tick {
  /* layout-audit-ignore: tiny-text — 차트 축 눈금, 값은 툴팁으로도 읽힌다 */
  font-size: 10px;
}
```

플러그인으로 설치하면 `PostToolUse` 훅이 같은 검사를 편집 직후에 돌린다.
Claude Code에서는 `Write|Edit|MultiEdit`, Codex에서는 `apply_patch`가 대상이다.
훅은 이번 편집이 바꾼 줄만 보고, 그 줄에 error가 있으면 종료 코드 2와 함께
고치는 법을 에이전트에게 돌려보낸다.
warn은 최대 5줄로 알리기만 하고, 문제가 없으면 아무것도 출력하지 않는다.
바꾼 줄만 보는 이유는 기존 CSS의 상관없는 줄 때문에 편집마다 되돌아오고
에이전트가 범위 밖 코드를 고치게 되는 것을 막기 위해서라고 `hookCore.ts`가
설명한다.
`SUTA_HOOK=off`로 끌 수 있고, 훅이 실패해도 편집을 막지는 않는다.

| 대상                         | 방법                                          | 편집 후 검사   |
| ---------------------------- | --------------------------------------------- | -------------- |
| Claude Code                  | 대화창에서 마켓플레이스 추가 후 플러그인 설치 | 설치 즉시 켜짐 |
| Codex                        | 터미널에서 플러그인 추가 후 `/hooks`에서 승인 | 승인해야 돎    |
| Cursor·Gemini CLI·Copilot 등 | `npx skills add` 또는 설치 스크립트           | 없음           |

```text
/plugin marketplace add Guksu/suta
/plugin install suta@suta
```

```bash
# Codex
codex plugin marketplace add Guksu/suta
codex plugin add suta@suta

# 스킬만 설치 (편집 후 검사 없음)
npx skills add Guksu/suta --skill suta
```

설치 스크립트는 `.agents/skills/suta`에 복사하고 git만 있으면 된다.
`--dest .cursor/skills`처럼 다른 폴더를 줄 수 있고,
같은 명령을 다시 실행하면 `suta` 폴더만 교체해 업데이트한다.
직접 부르려면 Claude Code에서 `/suta:suta`, Codex에서 `$suta`를 쓴다.
안내 문서는 모든 UI 작업에 반드시 쓰게 하려면 프로젝트의 `AGENTS.md`나
`CLAUDE.md`에 UI 작업에는 suta 스킬을 따른다는 한 줄을 넣으라고 권한다.

예전 이름 fe-skills를 쓰던 사람은 옛 마켓플레이스와 `fe-system` 플러그인,
패턴마다 따로 설치된 스킬 폴더를 먼저 지워야 한다.
옛 폴더들이 suta와 같은 요청에 겹쳐 걸리기 때문이다.

README가 권하는 첫 요청은 다음과 같다.

```text
suta를 사용해서 이메일, 비밀번호, 로그인 버튼, 비밀번호 찾기 링크가 있는
로그인 화면을 만들어줘. 간단하게 구성하고 키보드로도 사용할 수 있게 해줘.
```

이 문서는 suta를 직접 설치해 실행해 보지 않았고,
저장소의 스킬 파일과 문서를 읽어 정리했다.

## 저자가 공개한 실험 결과

### 화면 비교

같은 요청·모델·설정으로 suta 설치 여부만 바꿔 Claude Code에 화면을 만들게 했다.
모바일 웹뷰 이커머스 실험은 suta 없이 1회, suta 0.8로 4회 실행했다.
suta 쪽은 주황을 곳곳에 쓰던 화면이 갈색 강조색 하나와 할인율 빨강으로,
이모지 아이콘이 선 아이콘으로, BEST·NEW 배지가 할인율·가격·별점으로 바뀌었다.
axe 접근성 검사의 색 대비 위반은 6개 화면에서 111곳이 0곳이 되었다.
대신 생성 시간은 2.3분에서 5~7분으로,
비용은 0.39달러에서 1.35~1.55달러로 늘었다.

데스크톱 증권 웹사이트 실험은 suta 없이 4회, suta 0.10으로 2회 실행했다.
axe 위반은 63~277곳에서 0곳이 되었고,
첫 화면 안에 주문 버튼이 있는 경우는 4번 중 2번에서 2번 모두가 되었다.
생성 시간은 3~4.4분에서 7.4~14.5분, 비용은 0.54~0.75달러에서
1.51~1.72달러로 늘었다.
설치 여부를 가린 14쌍을 모델 두 개에 순서를 바꿔 두 번씩 보였더니,
모델별로 28회 중 23회와 24회 suta 쪽을 골랐다.

### 벤치마크

상세·로그인·설정·대시보드·랜딩·장바구니·검색 결과·바텀시트의 8가지 요청을
조건마다 두 번씩 실행해 화면 16개를 브라우저에서 쟀다.

| 지표 (16개 화면)                | suta 없이 | suta 0.6.0 |
| ------------------------------- | --------- | ---------- |
| 접근성 위반(axe, 합계)          | 87        | 13         |
| 상자 안 상자(합계)              | 41        | 1          |
| 그라데이션·흐림·큰 그림자(합계) | 47        | 0          |
| 24px 미만 터치 영역(합계)       | 27        | 0          |
| 주 버튼이 파랑·남색·보라인 화면 | 10        | 0          |

결함 지표는 크게 줄었지만 판정은 엇갈렸다.
두 판정 모델에게 설치 여부를 가린 화면을 비교시켰을 때,
기본 판정 모델은 32회 중 11회, 다른 판정 모델은 19회 suta를 골랐다.
1차 판정에서 suta 쪽은 깔끔하지만 밋밋하다는 평을 들었고,
저자는 이 평을 받고 글자·색·면 기준을 다시 분석해 0.6.0을 만들었다.
화면 하나의 생성 시간 중앙값은 61초에서 103초로 늘었고,
입력 토큰은 일반의 4.4배였다.

저자는 한계를 스스로 적어 두었다.
실행 횟수가 조건당 1~4회뿐이고, 규칙의 값은 국내 서비스에서 뽑아
다른 나라 관례와 다를 수 있으며, 화면 생성에는 Claude Code의 기본 모델
하나만 썼다.
판정 모델 하나는 화면을 만든 모델과 같아서,
적은 표본의 모델 평가를 일반적인 품질 차이로 해석하기 어렵다고도 밝힌다.

## 트레이드오프

### 결함을 줄이는 것과 좋아 보이는 것은 다른 문제다

suta가 확실히 줄이는 것은 측정 가능한 결함이다.
색 대비 위반, 상자 안 상자, 작은 터치 영역, 넘친 화면은 0에 가까워졌다.
그러나 같은 벤치마크에서 기본 판정 모델은 여전히 suta 없는 쪽을
21 대 11로 더 많이 골랐다.
결함을 걷어 낸 화면이 곧 매력적인 화면은 아니라는 뜻이다.

저자도 이 차이를 알고 있다.
1차의 밋밋하다는 평에 답한 것이 면을 두 단계로 나누고
강조색을 선택 상태와 링크에 이어 쓰라는 규칙이다.
금지선은 빼는 방향으로만 작동하기 쉬워서, 무엇을 더해야 하는지를 따로
적어 두지 않으면 흰 바탕에 선만 남는 화면이 나온다.
suta의 금지선 표에 장식을 걷어 낸 뒤에도 남는 AI 티라는 별도 표가 있는
이유가 이것이다.

### 국내 앱의 관례를 기본값으로 삼는다

기준값은 국내 앱 31곳에서 왔다.
하단 탭 바를 어느 화면에 둘지, 소셜 로그인 버튼에 카카오 노랑을 쓰라는 것,
상승 빨강·하락 파랑 같은 규칙은 국내 서비스에서는 그대로 맞지만
해외 서비스에는 바꿔야 한다.
등락 색처럼 해외 관례를 따로 적어 둔 항목도 있지만,
모든 규칙에 그런 분기가 있지는 않다.
국내 모바일 웹뷰를 만드는 팀에게는 강점이고,
다른 시장의 데스크톱 SaaS를 만드는 팀에게는 걸러 들어야 할 부분이다.

### 품질 대신 시간과 비용을 낸다

공개된 모든 실험에서 생성 시간과 비용이 두세 배 늘었다.
에이전트가 `SKILL.md`, 화면 유형 문서, 패턴 설명서를 읽고
검사를 돌리고 고치는 과정이 그대로 비용이 된다.
`screen-conventions.md`만 41KB이고 `principles.md`가 26KB라서,
화면 하나를 만들 때 읽는 양이 적지 않다.
한 화면을 빨리 그려 보는 프로토타입 단계보다는,
남길 화면을 만드는 단계에서 비용 대비 효과가 크다.

### 정적 검사는 코드의 값만 본다

검사는 소스 텍스트를 읽는 휴리스틱이다.
CSS 파서가 아니라서 SCSS의 깊은 중첩, 런타임에 조합하는 클래스,
CSS 모듈의 클래스 이름은 정확히 읽지 못한다.
글자 대비, 누르는 영역, 좁은 폭 넘침, 클릭되지 않는 버튼은 브라우저에서
확인해야 한다고 README와 `SKILL.md`가 함께 밝힌다.
`SKILL.md`는 error 0·warn 0이어도 정보·행동이 겹치거나 화면 유형의 뼈대와
다르면 끝난 것이 아니라고 적어, 검사 통과를 완료로 착각하지 말라고 경고한다.

## 함정

- 편집 후 훅은 파일 편집 도구(Write·Edit)로 고칠 때만 돈다. 에이전트가 셸 heredoc으로 파일을 쓰면 검사가 돌지 않는다. `SKILL.md`도 이를 명시하고 끝에 통합 검사를 직접 돌리라고 한다.
- 스킬만 설치(`npx skills add`)하면 훅이 없다. 검사는 에이전트가 절차를 지켜 직접 돌릴 때만 일어난다.
- Codex는 `/hooks`에서 승인해야 훅이 돈다. 마켓플레이스만 갱신하고 설치된 플러그인까지 바뀌었다고 판단하지 말라고 안내 문서가 따로 적는다.
- Node 22.18 미만이면 훅은 조용히 종료 0으로 지나간다. 검사가 돌지 않았는데 문제가 없는 것처럼 보일 수 있다.
- 글자 크기 기준이 문서마다 조금 다르다. `SKILL.md`는 12px 이상을 요구하지만, 검사의 error 기준은 11px 미만이고 11px대는 warn이다.
- `no-reduced-motion`은 파일 단위다. 전역 CSS 한 곳에만 reduced-motion 블록을 두는 구조면 컴포넌트 파일마다 error가 난다.
- 벤치마크 문서는 지금 버전을 0.8.0이라고 적고 있지만 플러그인 매니페스트는 0.10.0이다. 공개된 수치가 최신 버전의 결과는 아니다.
- fe-skills 시절의 패턴별 스킬 폴더가 남아 있으면 같은 요청에 겹쳐 걸린다.
- 체크리스트는 예시 데이터에 대화나 git 설정에 보이는 실제 이름·이메일·전화번호를 넣지 말라고 요구한다. 에이전트가 맥락에서 개인 정보를 끌어다 화면을 채우는 일이 실제로 있다는 뜻이다.

## 체크리스트

- 1순위 요소가 하나이고, 채운 주 버튼이 하나인가?
- 같은 정보와 같은 행동이 한 곳에만 있는가?
- UI의 유채색이 강조색 하나와 오류 빨강을 넘지 않는가?
- 강조색을 고른 이유가 한 줄로 남아 있는가?
- 면이 흰 면과 옅은 바탕 두 단계이고, 카드에 테두리와 그림자를 함께 쓰지 않았는가?
- 간격·글자 크기·반경을 토큰에서만 골랐는가?
- 움직이는 속성이 `transform`과 `opacity`뿐인가?
- 새로 쓴 CSS마다 reduced-motion 블록이 있는가?
- 클릭할 수 있는 것이 모두 키보드로 닿고 포커스가 보이는가?
- 모달·시트·메뉴가 Esc로 닫히고 포커스가 돌아오는가?
- `audit.mjs`의 error가 0인가?
- 가장 긴 값, 빈 값, 320px 폭에서 브라우저로 직접 확인했는가?

## 기억할 원칙

### 취향은 측정 가능한 금지선으로 바꿀 수 있는 만큼만 전달된다

AI가 만든 티가 난다는 말은 막연하지만,
suta는 그것을 `transition: all`, 기본 파랑, 상자 안 상자, 이모지 아이콘처럼
코드에서 찾을 수 있는 항목으로 쪼갰다.
그리고 각 항목에 잘 만든 앱에서 잰 비율을 근거로 붙였다.
덕분에 에이전트는 규칙을 따를 수 있고, 검사 스크립트는 위반을 잡을 수 있다.

그러나 벤치마크가 보여 주듯 금지선을 다 지킨 화면도 판정에서 질 수 있다.
측정할 수 있는 것은 결함이고, 좋은 화면은 그 위에서 무엇을 먼저 보이고
무엇을 뺄지 정하는 판단에서 나온다.
suta가 작업 절차의 앞쪽에 순서 정하기와 덜어내기를 두고,
검사를 통과해도 끝이 아니라고 적은 것은 이 경계를 인정한 것이다.
에이전트에게 디자인을 맡길 때 자동화할 수 있는 것은 하한선이고,
상한선은 여전히 사람이 화면을 보고 정해야 한다.
