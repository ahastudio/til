# Impeccable: AI가 만든 프런트엔드의 상투성을 잡는 디자인 스킬

<https://impeccable.style/>

<https://github.com/pbakaus/impeccable>

HN 토론: <https://news.ycombinator.com/item?id=46587284> (103점, 64개 댓글)

GN 토론: <https://news.hada.io/topic?id=27750>

## 소개

Impeccable은 AI 코딩 에이전트에게 디자인 지침을 주는 스킬 패키지다.
저장소 설명은 AI 하네스가 디자인을 더 잘하게 하는 디자인 언어라고 하고, README는
스킬 1개, 명령 24개, 라이브 브라우저 반복, 그리고 AI가 만든 프런트엔드 디자인을
겨냥한 결정론적 탐지 규칙 62개로 요약한다.
Paul Bakaus가 만들었고 라이선스는 Apache 2.0이다.
Anthropic의 `frontend-design` 스킬에서 출발했다고 README가 밝힌다.

문제 설정은 모든 모델이 같은 SaaS 템플릿으로 학습되어 지침이 없으면 같은 흔적이
반복된다는 것이다.
README가 드는 예는 모든 곳에 쓰는 Inter 글꼴, 보라에서 파랑으로 가는 그라디언트,
카드 속의 카드, 색 배경 위의 회색 글씨, 제목마다 붙는 둥근 사각형 아이콘이다.

## 구성

### 하나의 스킬과 24개 명령

모든 명령은 `/impeccable <command> <target>` 한 형태로 호출한다.
프로젝트를 시작할 때는 `/impeccable init`을 먼저 돌려 대상 독자, 목적, 운영
맥락, 제약, 어조 같은 변하지 않는 제품 사실을 `PRODUCT.md`에 기록한다.
화면별 시각 방향은 나중에 정하고, 기존 또는 새로 만든 시각 체계는 `DESIGN.md`에
따로 기록한다.

명령은 용도로 묶인다.

| 묶음        | 명령                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------- |
| 계획과 구축 | `craft`, `shape`, `document`, `extract`                                                                    |
| 검토        | `critique`, `audit`, `polish`                                                                              |
| 강도 조절   | `bolder`, `quieter`, `distill`, `overdrive`                                                                |
| 세부 개선   | `harden`, `onboard`, `animate`, `colorize`, `typeset`, `layout`, `delight`, `clarify`, `adapt`, `optimize` |
| 브라우저    | `live`, `generate`                                                                                         |

`/impeccable pin audit`처럼 명령을 단독 단축 명령(`/audit`)으로 고정할 수 있다.
README의 안티 패턴 목록은 흔한 글꼴 쓰지 않기, 색 배경 위 회색 글씨 금지, 순수한
검정과 회색 대신 색조 넣기, 카드 중첩 금지, 바운스와 탄성 이징 금지다.

### 설치

권장 경로는 프로젝트 루트에서 `npx impeccable install`을 실행하는 것이다.
설치기는 감지한 하네스 폴더를 보여 주고 프로젝트 또는 전역 설치를 묻는다.
Cursor, Claude Code, Gemini CLI, Codex CLI, Grok Build, Hermes Agent, Veto 등
여러 도구를 지원하며, 갱신은 `npx impeccable update`다.
Git 서브모듈, VS Code 확장, Claude Code
플러그인(`/plugin marketplace add pbakaus/impeccable`), 웹사이트 ZIP, 저장소에서
직접 복사하는 방법도 있다.
스킬 자체는 런타임이 필요 없고, 각 사본에 든 작은 실행기가 엔진 바이너리를
쓰거나 처음 실행할 때 `~/.impeccable/bin/`에 내려받는다.

### 탐지기 CLI

AI 하네스 없이 안티 패턴을 찾는 독립 CLI가 있다.

```bash
npx impeccable detect src/                 # 디렉터리 검사
npx impeccable detect https://example.com  # URL 검사, 설치된 Chrome 계열 브라우저 사용
npx impeccable detect --json .             # CI용 JSON 출력
npx impeccable detect --github src/        # GitHub Actions 주석 출력
npx impeccable detect --list-rules         # 규칙 목록
```

종료 코드는 0이 문제 없음, 2가 주요 발견 있음, 1이 검사하지 못한 대상이
있음이다.
README는 깨끗한 탐지 결과가 증거일 뿐 시각이나 접근성 품질의 증명이 아니라고
명시한다.
규칙은 AI 상투성(옆면 띠 테두리, 보라 그라디언트, 바운스 이징, 어두운 글로우)과
일반 디자인 품질(줄 길이, 좁은 패딩, 작은 터치 영역, 건너뛴 제목 수준)을 다룬다.

### 디자인 훅

Claude Code, GitHub Copilot, Codex, Cursor, Grok Build에서는 설치가 공급자
고유의 훅 매니페스트를 함께 설치한다.
훅은 UI 파일을 직접 편집할 때 탐지기를 실행해 발견 사항을 에이전트 흐름으로
돌려준다.
Claude Code에서는 `.claude/settings.local.json`에 들어가 머신 로컬로 유지된다.
설치된 명령 훅은 모델의 도구 승인과 별개로 실행되므로, 첫 편집이나 종료
이벤트에서 엔진이 내려받아질 수 있다는 점을 README가 직접 경고한다.

### 빌드 경로와 텔레메트리

새 화면을 디자인할 때 먼저 완성도 높은 시안을 만들고 그에 맞춰 구현하는
방식(`comp`)과, 코드에서 바로 만들되 개발 전용 방향 계약을 두고 마지막에
확인하는 방식(`code`)을 고를 수 있다.
선택은 `.impeccable/config.json`의 `buildPath`에 기록된다.

새 디자인을 시작할 때 스킬은 impeccable.style의 roll API에 시각 세계 묶음을
요청한다.
옵트아웃하지 않으면 어떤 묶음이 보였고 어떤 카드가 선택됐는지에 대한 익명 기록도
함께 보낸다.
프로젝트 이름, 파일, 코드, `PRODUCT.md`는 보내지 않는다고 README가 밝힌다.
끄는 방법은 `npx impeccable telemetry off`, 환경 변수 `DO_NOT_TRACK=1`,
`IMPECCABLE_NO_TELEMETRY=1`, 또는 프로젝트 설정의 `"telemetry": false`다.

## 분석

### 지침 파일과 검사기를 한 쌍으로 묶은 구조다

Impeccable의 핵심 설계는 프롬프트 쪽의 스킬과 코드 쪽의 결정론적 탐지기를 한
패키지로 묶은 것이다.
스킬은 에이전트가 처음부터 상투를 피하도록 방향을 주고, 탐지기와 훅은 결과물이
그 방향을 지켰는지 LLM 없이 확인한다.
탐지기가 API 키 없이 돌고 CI 출력과 종료 코드를 제공하는 것은 이 도구가 에이전트
밖의 품질 게이트로도 쓰이도록 설계됐음을 보여 준다.
이는 이 문서의 해석이다.

### 문서화된 맥락이 일관성의 원천이 된다

`init`이 변하지 않는 제품 사실을 `PRODUCT.md`에 쓰고 시각 체계를 `DESIGN.md`에
따로 쓰게 한 것은 두 종류의 지식을 분리하는 선택이다.
독자와 목적은 오래 가고 시각 방향은 화면마다 바뀐다는 가정이다.
이 분리가 명령 24개가 서로 다른 시점에서 같은 사실을 읽게 하는 접착제다.

### 이 도구는 모델의 평균으로 수렴하는 경향을 어휘로 풀려고 한다

HN에서 turnsout은 LLM에게는 올바른 용어를 언급하는 것만으로도 모델이 그 방향으로
기운다고 썼다.[^turnsout]
행간이나 글꼴 조합을 말하면 모델이 타이포그래피에 더 주의를 기울인다는 설명이며,
전문가가 아니어도 이 현상을 쓸 수 있다는 것이 그의 요지다.
Impeccable의 24개 명령은 이 어휘를 명령 이름으로 고정한 것으로 읽힌다.
이는 이 문서의 해석이다.

## 비평

### 가장 중요한 증거였던 사례 비교가 설득력이 없었다

HN 스레드가 열린 시점의 랜딩 페이지에는 전후 비교 사례가 있었고 반응이 거의 한
방향이었다.
wackget은 전 사례가 후 사례보다 훨씬 낫다고 썼고, fxtentacle는 랜딩 페이지
예시가 사용량 수치, 가동 시간, 평점 같은 장점을 잃고 글자 대비가 더 나빠졌으며
대시보드가 더 정돈되어 보인 것은 유용한 정보가 사라졌기 때문이라고
지적했다.[^wackget][^fxtentacle]
저자 paulbakaus는 사례가 부실했고 급히 출시했으며 실제로는 아직 공개되지 않은
프로덕션 프로젝트에 이 명령들을 효과적으로 써서 오픈소스로 냈지만 그 화면을
스크린샷으로 쓸 수 없었다고 답하고 사례를 내렸다.[^paulbakaus]
도구의 가치를 보이는 가장 직접적인 증거가 공개된 상태로는 없어졌다는 뜻이다.

### 어휘가 디자인 능력을 대신하지 못한다는 반론에 구조적 답이 없다

Antibabelic은 좋은 디자인 프롬프트에 디자인 어휘가 필요하다는 소개 문구에 대해
어휘는 표면이고 그 아래에는 쓰기 쉽고 접근 가능하며 특정 인상을 주는 물건을
만드는 이해가 있다고 반박했다.[^antibabelic]
저자는 어휘가 도움은 되지만 사용자나 LLM을 훌륭한 디자이너로 만들지는 않는다고
인정하고 랜딩 페이지의 과장된 어조를 낮췄다.[^paulbakaus-vocab]
인정은 있었지만, 어휘가 어디까지 방향을 잡고 어디서부터 판단이 필요한지의 경계는
README에 없다.

### 탐지 규칙은 취향을 규칙으로 고정한다

README의 안티 패턴에는 순수한 검정과 흰색을 쓰지 말라는 항목이 있다.
HN에서 raylad는 회색 글씨가 디자이너들의 애호이지만 대비가 부족해 읽기 어렵다고
불평했다.[^raylad]
같은 규칙이 접근성 도구이면서 취향의 강요가 될 수 있다는 점을 README의 `ignores`
설정과 파일 단위 인라인 면제 주석이 인정하고 있다.
규칙 62개 중 어느 것이 접근성 근거를 갖고 어느 것이 취향인지 구분해서 보여
주지는 않는다.

### 훅은 승인 모델 밖에서 실행된다

README는 설치된 훅이 모델의 도구 승인과 독립적으로 실행되며 첫 편집이나 종료
이벤트에서 엔진이 다운로드되어 캐시될 수 있다고 직접 적는다.
무인 실행 전에 설치된 훅을 검토하라는 권고까지 쓰는 점은 투명하지만, 이는
기본값이 승인 없는 외부 바이너리 다운로드를 포함한다는 뜻이기도 하다.
라이브 모드가 `package.json`의 `impeccable:manual-edit-validate` 스크립트를
셸에서 사용자 권한으로 실행한다는 경고도 같은 범주다.

## 인사이트

### 스킬 배포가 소프트웨어 배포의 공급망 문제를 그대로 상속한다

설치기가 훅, 실행기, 내려받는 바이너리를 함께 놓는 순간 이 스킬은 문서가 아니라
실행 가능한 의존성이 된다.
README가 Hermes에서 프로젝트 로컬 스킬을 저장소별 신뢰 결정 뒤에 두는 이유를
프롬프트 주입 경로가 될 수 있기 때문이라고 설명하는 대목이 이 문제를 정확히
가리킨다.
스킬 마켓이 생긴다면 서명, 버전 고정, 훅 권한 표기가 패키지 관리와 같은 수준으로
필요해진다.
이는 이 문서의 해석이다.

### 디자인 지식의 상품화는 검증 가능한 부분에서 먼저 일어난다

HN에서 redfloatplane은 에이전트 스킬을 파는 사람들이 나타나는 것이 흥미롭고
전문가가 생성형 AI로 잃을 수입을 일부 만회하는 길이 될지
궁금해했다.[^redfloatplane]
Impeccable에서 실제로 기계적으로 검증되는 부분은 탐지기의 62개 규칙뿐이고, 그
위의 명령 어휘는 효과가 취향에 좌우된다.
돈을 받고 팔 수 있는 지식은 검증 가능한 규칙 쪽으로 몰리고, 판단이 필요한 쪽은
여전히 사람의 몫으로 남는다.
이는 이 문서의 해석이다.

### 상투를 피하는 규칙이 새로운 상투가 된다

모든 모델이 같은 SaaS 템플릿에서 학습한다는 진단은 같은 스킬을 쓰는 모든
프로젝트가 같은 반 상투를 갖게 될 위험을 낳는다.
Inter를 쓰지 말라는 규칙을 따른 다음 선택이 모두 같은 대안 글꼴로 모이면 다음
세대의 상투가 생긴다.
README가 시각 세계 묶음을 카탈로그에서 뽑아 보여 주는 롤 방식과 텔레메트리로
선택을 되먹이는 것은 이 위험을 의식한 설계로 읽히지만, 카탈로그가 얼마나
다양한지는 이 문서가 확인하지 못했다.
이는 이 문서의 해석이다.

### 이 글을 읽는 방법

이 문서는 저장소 README와 HN 스레드(2026년 초 랜딩 페이지 시점)의 댓글을 읽었고
impeccable.style 사이트, 명령별 상세 문서, 탐지 규칙 62개의 목록은 직접 열지
않았다.
GeekNews 토픽에는 읽을 수 있는 댓글이 없었다.
Lobste.rs에서는 2026년 9월 1일 이후 427개 이야기를 훑었으나 이 프로젝트의 스레드를 찾지 못했다.

주장을 가를 관찰은 두 가지다.
하나는 같은 화면을 Impeccable 없이 만든 결과와 `craft` 또는 `polish`를 쓴 결과를
접근성 검사와 실제 사용자 과제 성공률로 비교한 결과다.
다른 하나는 이 스킬을 쓴 여러 프로젝트가 같은 글꼴, 색, 레이아웃으로
수렴하는지를 센 결과다.
앞의 것이 있으면 효과의 크기를, 뒤의 것이 있으면 새로운 상투가 생기는지를 알 수
있다.
