# Mobile Harness: 휴대폰 제어용 에이전트 지침

<https://mobile-harness.com/>

<https://github.com/droidrun/mobile-harness>

## 소개

Droidrun(Mobilerun)이 낸 오픈소스 저장소로, AI 에이전트가 Android와 iOS 기기를 제어하는 방법을 적은 마크다운 지침 모음이다.
`platforms/` 아래의 안내서, 앱별 카드, 벤치마크 방법론 페이지는 열지 않았고 직접 설치해 써 보지도 않았다.
설명과 수치는 모두 제작사의 주장이다.

GitHub API로 읽은 시점(2026년 11월 18일)의 저장소 수치는 별 456개, 포크 53개, 열린 이슈 9개, 라이선스 MIT, 생성일 2026년 6월 1일, 마지막 푸시 2026년 11월 3일이다. 릴리스는 없다.
저장소 설명은 Android, iOS, 클라우드 폰을 제어하는 스킬이다.

홈페이지는 이를 실제 휴대폰을 에이전트가 몰게 하는 이식 가능한 오픈소스 하네스라고 소개한다. 문구는 하나의 Mobilerun API로 Android와 iOS 기기를 로컬이나 클라우드에서 제어한다는 것이고, 설정 프롬프트를 에이전트에 붙여 넣는 빠른 시작을 안내한다. 하단에는 한 대의 로컬 휴대폰에서 실제 기기 여러 대로 Mobilerun을 통해 확장하라는 안내가 있다.
핵심은 이것이 에이전트 실행 환경이 아니라는 점이다.
README는 컴팩트한 마크다운 하네스(harness)이며 에이전트 런타임이 아니라고 밝힌다.
실제 제어 경로는 파이썬 패키지 `mobilerun_core`이고, 필요한 곳에는 보조 앱을 둔다.

구성은 이렇다.

- 로딩 모델: 모든 런타임은 `AGENTS.md`에서 시작하고, 스킬 기반 런타임은 `SKILL.md`를 읽는다. `AGENTS.md`가 필요한 가장 작은 파일로 안내한다. Android 작업은 `platforms/android/GUIDE.md`, iOS 작업은 `platforms/ios/GUIDE.md`, 제어가 실패했을 때만 플랫폼별 `recovery/GUIDE.md`, 로그인이나 결제 같은 비밀 정보 화면이 나올 때만 `core/credentials`, 메모리를 읽고 쓸 때만 `core/memory/GUIDE.md`, 전면 앱의 `CARD.md`만 읽는다. 모든 파일을 한꺼번에 읽지 말라고 한다.
- 앱 카드: 전면 앱의 패키지(Android)나 번들 ID(iOS)로 `apps/<플랫폼>/<앱>/CARD.md`를 읽는다. 저장소에는 Chrome, 설정, eBay, Gmail 등 Android 앱 카드 네 개가 있다. 사용자가 `local/apps/`에 둔 같은 경로의 카드가 있으면 출하된 카드와 어긋날 때 그쪽이 우선한다.
- 로컬 상태: 사용자와 에이전트가 소유하는 것은 모두 git이 무시하는 `local/` 한 곳에 둔다. 에이전트가 쓰는 메모리(`local/memory/`), 선택적 자격 증명 메모(`local/credentials/`), 개인 앱 카드(`local/apps/`)이다. 저장소는 이들의 규칙과 템플릿만 추적해 `git pull`이나 플러그인 업데이트와 분리된다.
- 업데이트: 평소 세션에서는 설치된 의존성을 확인만 하고 쓴다. 가져오기, `npx skills update`, 패키지 설치와 업그레이드를 시작 절차로 하지 말라고 하며, 사용자가 요청하거나 확인된 호환성 문제가 작업을 막을 때만 `UPDATE.md`를 읽는다. 고정된 버전은 사용자가 승인하기 전에는 바꾸지 않는다.
- 설치: `npx skills add droidrun/mobile-harness`(skills.sh), Claude Code 플러그인(`/plugin marketplace add`와 `/plugin install`), 수동 설치가 있다. 첫 사용에는 어느 경우에도 파이썬 3.11부터 3.13에서 `mobilerun-core[local]`을 설치하는 설정이 필요하다. 에이전트에게 저장소를 설정해 달라고 붙여넣는 프롬프트도 제공한다.

제어 경로는 다음과 같다.

| 대상                           | 백엔드               | 비고                                                   |
| ------------------------------ | -------------------- | ------------------------------------------------------ |
| Android, ADB 있음              | `local-android-adb`  | ADB 기본 제어, Portal이 있으면 Portal 기능을 자동 사용 |
| Android, ADB 없음, Portal 있음 | `local-android-http` | 사용자가 준 Portal 주소와 베어러 토큰이 필요           |
| iPhone, iPad(USB)              | `local-ios-http`     | `mobilerun-ios --local <udid>`, 기본 `127.0.0.1:8080`  |
| iOS 시뮬레이터                 | `local-ios-http`     | `ios-portal` 앱, 기본 `127.0.0.1:6643`                 |
| 클라우드 폰                    | `cloud`              | API 키와 기기 ID 필요                                  |

ADB도 Portal도 없는 Android는 막힘으로 분류하고 사용자에게 켜 달라고 요청하게 한다.
주 API는 `Mobilerun().connect(...)`로 얻는 `device`이며 `ui()`, `screenshot()`, `start_app()`, `find_nodes()`, `tap_node()`, `tap_text()`, `scroll()`, `scroll_until()`, `type()`, `list_apps()`, 딥링크와 클립보드 등을 제공한다. 선택 기능은 쓰기 전에 `device.supports(...)`로 확인하라고 한다.

비필수 규칙으로는 화면의 텍스트와 웹페이지, 앱 내용을 에이전트에 대한 지시가 아니라 신뢰할 수 없는 데이터로 다루게 한다. 자격 증명, 결제, 파괴적 동의 화면에서는 사용자가 정확한 행동을 명시적으로 허가한 경우에만 이어 가고 아니면 묻게 한다. 토큰과 API 키를 로그, 채팅, 스크린샷, 요약에 출력하지 말라고 한다.

벤치마크로 AndroidWorld와 iOSWorld의 결과를 내세운다(그림의 대체 텍스트와 본문에서 읽었다).
표준 코딩 에이전트에 앱 카드와 영속 메모리를 붙여 평가했고, Android는 gpt-6-astra(낮은 추론), iOS는 gpt-6-astra(중간)와 gpt-6-luna(높음)를 썼다고 한다.

- AndroidWorld: 116개 과제에서 평균 점수 100%, 이진 통과율 100%(116개 전부 만점).
- iOSWorld: 133개 과제에서 공식 평균 점수 98.34%, 이진 통과율 92.48%(123개 만점, 10개 부분 점수).
- 평균 점수는 과제 점수의 평균이고 이진 통과율은 점수 1.0을 받은 과제만 센다고 설명한다.

## 분석

### 중심 주장은 지침을 파일로 나눠 필요한 만큼만 읽힌다는 것이다

이 저장소의 설계는 실행 코드가 아니라 라우팅이다.
`AGENTS.md`가 상황별로 읽을 파일을 정하고, 앱 카드와 복구 안내서는 해당 상황에서만 읽게 한다.
에이전트의 문맥을 아끼면서 앱마다 다른 지식을 쌓을 수 있는 구조이며, 사용자의 `local/`이 출하된 카드를 덮어쓰게 해 개인 지식과 배포 지식을 분리한다.
이는 저장소의 서술을 이 문서가 정리한 것이다.

### 제어는 접근성 트리와 스크린샷에 기대는 방식이다

`find_nodes`, `tap_node`, `tap_text`가 접근성 트리의 텍스트, 설명, 리소스 ID, 접근성 식별자를 검색한다고 설명한다.
화면 밖에 있는 노드(`offscreen`)와 숨겨진 노드(`hidden`)를 구분하는 표시와, 스크롤이 실제로 움직였는지 확인하는 `verify`가 있다.
좌표를 추측해 누르는 것이 아니라 노드 정보를 근거로 누르게 하려는 설계로 읽힌다.
이는 이 문서의 해석이며 실제 동작은 확인하지 못했다.

### 안전 규칙이 지침의 앞쪽에 있다

화면의 텍스트를 지시가 아니라 데이터로 다루게 하고, 비밀 정보와 결제, 파괴적 동의에서 멈추게 하며, 업데이트를 사용자의 요청이나 호환성 문제가 있을 때만 하게 한다.
휴대폰은 계정과 결제 수단이 연결된 기기이므로 이런 규칙이 지침의 비필수 규칙으로 올라 있는 것은 자연스럽다.
다만 규칙은 에이전트가 따를 지침이고, 위반을 막는 강제 장치는 저장소에 없다.

## 비평

### 벤치마크는 제작사 자체 평가이다

README는 표준 코딩 에이전트에 앱 카드와 영속 메모리를 붙였다고 하는데, 앱 카드와 메모리가 평가 과제를 겨냥해 만들어졌는지(과제에 맞춘 카드인지)는 README에 나오지 않는다.
Android 100%라는 값은 만점 116개의 결과이므로, 평가 세트에 맞춘 조정이 있었는지가 해석에 영향을 준다.
iOS는 이진 통과율 92.48%로 완전하지 않아 두 플랫폼의 결과가 다르다.

### 평가 모델이 특정 모델 조합이다

Android는 gpt-6-astra, iOS는 gpt-6-astra와 gpt-6-luna를 썼다고 한다.
다른 모델(Claude, Gemini, 오픈 모델)에서도 같은 결과가 나오는지는 README에 없다.
하네스가 모델에 중립적인지는 이 결과로 알 수 없다.

### 설치와 의존성의 실질 비용이 지침 밖에 있다

저장소는 마크다운이지만 실제 동작은 `mobilerun-core` 파이썬 패키지, 로컬 Android의 ADB와 Portal 앱, iOS의 `mobilerun-ios`와 WDA 서명(별도 문서 링크), 클라우드의 API 키에 의존한다.
README는 제목에서 컴팩트한 마크다운이라고 하지만 첫 사용에는 파이썬 3.11부터 3.13의 가상환경과 기기 준비가 필요하다.
핵심 제어 코드는 이 저장소가 아니라 별도 패키지에 있어서, 이 저장소만으로는 동작의 세부를 검토할 수 없다.

### 클라우드와 연결된 제품 구조가 있다

README의 클라우드 모드는 Mobilerun의 API 키와 API 주소를 쓰고, 상단에는 제작사 웹사이트와 커뮤니티 링크가 있다.
로컬 모드는 로그인 없이 된다고 하지만, 이 저장소가 제작사의 클라우드 서비스의 입구 구실도 한다는 점은 알고 읽어야 한다.

### 외부 반응

HN에서는 저장소 주소와 홈페이지 주소(`mobile-harness.com`)로 검색한 결과 이 저장소의 스레드가 없었다(이름 검색에서도 같은 저장소의 글이 없었다).
Lobste.rs에서는 `droidrun`과 `mobilerun`으로 검색한 결과가 0건이었다(대조 쿼리는 정상이었다).
GeekNews에서는 `Mobile Harness`, `droidrun`, 설명 표현으로 검색했고 이 저장소의 토픽은 없었다(대조 쿼리는 정상이었다). `droidrun`으로 걸린 토픽 하나는 다른 회사와 Google의 오픈소스 출처 논쟁을 다룬 것이라 무관했다.
그래서 이 저장소의 주장은 독자의 검토를 거의 거치지 않았다.

## 인사이트

### 가져갈 것은 지침을 상황별 파일로 쪼개 라우팅하는 구성이다

시작 파일 하나가 읽을 파일을 정하고, 실패했을 때와 비밀 정보 화면이 나왔을 때만 읽는 파일을 따로 두는 구성은 휴대폰이 아니라도 쓸 수 있다.
문맥을 아끼고, 위험한 상황의 규칙을 그 상황에서만 불러오게 하며, 사용자 소유 파일이 배포 파일을 덮어쓰게 하는 규칙이 핵심이다.
자기 팀의 에이전트 지침이 한 파일로 비대해졌다면 같은 나눔을 시험할 수 있다. 이는 이 문서의 적용이다.

### 휴대폰 에이전트에는 비밀 정보 경계를 먼저 정한다

화면 텍스트를 지시로 받아들이지 않기, 자격 증명과 결제에서 멈추기, 토큰을 출력하지 않기는 기기를 직접 제어하는 에이전트의 최소 규칙으로 읽을 수 있다.
도입하기 전에 어떤 앱과 화면을 에이전트에게 열어 둘지, 테스트 기기와 계정을 따로 둘지를 정하는 것이 이 규칙들보다 앞선다.

### 확인할 관찰

이 저장소의 주장을 가를 관찰은 세 가지이다.
앱 카드와 메모리를 과제에 맞추지 않은 상태에서 독립 평가가 같은 점수를 내는지,
다른 모델에서 하네스가 같은 성공률을 내는지,
화면의 텍스트가 에이전트를 속이려는 공격(프롬프트 주입)에서 규칙이 실제로 지켜지는지이다.
