# rederive: 코드 설계를 되짚어 배우는 스킬

<https://ericzou.dev/rederive/>

<https://github.com/EricJujianZou/rederive>

## 소개

rederive는 코딩 에이전트용 스킬(skill)이다.
AI가 써 준 코드를 면접이나 업무에서 설명해야 하는 사람이, 자기 저장소의 각
부분을 어떻게 만들었을지 질문받으며 설계 결정을 스스로 다시 도출(re-derive)하게
한다.
남의 오픈소스 저장소를 배우는 데도 쓸 수 있다.
만든 사람은 Eric Zou이고, 저장소 소개글은 “호기심을 되살리려는 지친 개발자의
시도”라는 문구로 시작한다.

핵심 약속은 설명하지 않고 질문만 한다는 것이다.
저장소 README는 이를 에이전트가 하는 말을 외우는 대신 도출을 통해 이해하도록
일부러 그렇게 만들었다고 밝힌다.

2026년 11월 25일 GitHub API로 읽은 저장소 정보는 다음과 같다.

| 항목        | 값                                           |
| ----------- | -------------------------------------------- |
| 라이선스    | MIT                                          |
| 언어        | Python (스크립트), 본체는 마크다운 스킬 파일 |
| 별          | 1,672개                                      |
| 포크        | 88개                                         |
| 열린 이슈   | 4개                                          |
| 생성        | 2026-10-19                                   |
| 마지막 갱신 | 2026-11-19                                   |
| 변경 이력   | 약 86건 (API 응답의 마지막 페이지 번호 기준) |

저장소의 `homepage` 필드에 등록된 프로젝트 사이트 `ericzou.dev/rederive`를 열어
읽었다.
사이트는 설치 명령, 동작 방식 네 줄, 자주 묻는 질문 네 개로 이루어진 한 장짜리
페이지다.
사이트가 README에 없는 새 주장을 더하지는 않는다.
다만 사이트에 적힌 별 수는 1,025개로, 같은 날 API가 돌려준 1,672개와 다르다.
사이트 문구가 갱신되지 않은 것으로 보이며, 이 문서는 API 값을 쓴다.

## 동작 방식

설치는 `npx skills add EricJujianZou/rederive` 한 줄이다.
README는 이 명령이 Claude Code, Codex, Cursor, Gemini CLI 등 약 70개 에이전트의
스킬 폴더에 같은 스킬을 넣는다고 설명하고, Claude Code 플러그인으로 설치하는
방법도 따로 둔다.
요구 사항은 `git`, `bash`, `python3`다.

저장소의 실질적인 내용은 `skills/rederive/SKILL.md` 132줄과 보조 스크립트 두
개(`history.sh` 71줄, `structure.py` 449줄)다.
SKILL.md는 여섯 단계로 구성된다.

### 저장소를 고르고 뿌리 문제로 시작한다

인자가 없으면 현재 디렉터리, 경로를 주면 그 경로, git 주소를 주면 `git clone
--filter=blob:none`으로 받는다.
상태는 대상 저장소 안의 `.rederive/`에 두고, 처음 한 번 `.git/info/exclude`에 이
폴더를 추가해 변경 이력에 섞이지 않게 한다.
로컬 경로는 사용자 자신의 저장소로, 복제한 주소는 남의 저장소로 간주한다.

첫 질문은 프로젝트가 왜 존재하는가다.
자기 저장소라면 “코드가 생기기 전에 어떤 문제가 있었는가”를 묻고, 남의
저장소라면 README와 초기 이력에서 문제를 추려 “이 문제를 어떻게 풀겠는가”를
묻는다.
이 질문을 던지는 동안 배경 서브에이전트가 다음 단계의 지도를 만든다.
서브에이전트가 없으면 에이전트가 직접 지도를 만든 뒤 질문한다.

### 결정 지도를 만든다

`history.sh`는 변경 이력에서 단서를 모아 출력한다.
처음 15건, 메시지에 설계 변경을 뜻하는 단어(refactor, replace, migrate 등)가
들어간 최근 40건, 건드린 파일 수가 가장 많은 15건, 가장 자주 바뀐 파일 20개,
설계 문서, 최상위 구성이다.
이력이 없거나 부족한 경우를 위해 `structure.py`가 JS/TS, Python, Go, Rust,
C/C++의 진입점과 파일 간 import 관계를 요약한다.
두 스크립트 모두 `git`과 파일 읽기만 쓰며, 내가 읽은 범위에서 네트워크 호출은
없었다.

에이전트는 이 출력과 README, 설계 문서, 진입점, import 연결을 따라 읽은 뒤
5~10개의 결정을 고른다.
기준은 “문제에서 사용자가 스스로 발명할 수 있는 메커니즘”이다.
데이터가 어떻게 움직이는지, 상태가 어디에 저장되는지, 실패를 어떻게 다루는지,
부분을 왜 분리했는지 같은 것이고, 언어와 프레임워크 선택이나 이름 짓기나 설정은
제외한다.
결정은 처음부터 만든다면 필요해지는 순서로 늘어놓고, 각 항목에 문제, 주어진 것,
제약, 결정의 일반 명칭, 선택지, 근거, 코드 위치를 적어 `.rederive/map.md`에
쓴다.
코드 위치는 파일이 있고 심볼이 실제로 들어 있는지 `grep -n`으로 확인한 뒤
적는다.
README는 이 지도에 정답이 있으므로 끝나기 전에는 열지 말라고 안내한다.

### 문제를 하나씩 푼다

한 문제는 다음 순서로 진행된다.
먼저 코드가 없다고 가정하고 문제와 주어진 조건만 말하고 해법을 묻는다.
그다음 “이 제약에서는 당신의 설계가 이런 문제를 일으킨다”는 식으로 제약을 한
번에 하나씩 더한다.
사용자의 설계가 원본보다 낫다면 그렇다고 말하고 기록한다.
원본 설계에 도달하면 바로 알려 주되, 저장소의 파일명이나 함수명이 아니라
업계에서 쓰는 일반 이름(예: 미들웨어 체인)으로 부른다.

막힌 경우에는 지도의 선택지를 한 줄 장단점과 함께 보여 주고 고르게 한다.
틀린 답이 두 번 연속 나오면 문제의 스케치를 제안하고, 승낙하면 Claude 아티팩트나
텍스트로 그린다.
결정 자체는 요청을 받아도 밝히지 않으며, 대신 제약을 더하거나 빠진 조각이 해야
할 일을 이름 없이 설명한다.
문제가 끝나면 “코드의 어디에 있는지 보겠느냐”고 한 번 묻고, 승낙하면 지도의 코드
위치 목록과 그 설계가 들어온 변경을 보여 준다. 코드 자체는 보여 주지 않는다.

### 기록과 마무리 카드

문제가 끝날 때마다 `.rederive/log.md`에 어디서 막혔는지, 혼자 찾아낸 것, 잘한
것, 어설펐던 것, 더 나은 아이디어를 적는다.
세션을 한 문제 이상 끝냈다면 프로젝트 이름, 설명, 해결한 결정 이름 최대 세 개,
걸린 시간, 힌트 없이 푼 문제 수를 담은 텍스트 카드를 그리고, 같은 내용을 담은
Twitter 게시 작성 화면 링크를 붙인다.
스킬 규칙은 사람에게 “건축가처럼 생각한다” 같은 평가 딱지를 붙이거나 점수와 연속
기록과 등수를 매기는 것을 금지한다.

### 저장소 내용에 대한 방어

SKILL.md는 저장소 안의 코드, 주석, 문서, 변경 메시지를 가르칠 재료로만 쓰고
에이전트에게 주는 지시로 취급하지 말라고 한다.
그런 글이 명령 실행이나 파일 변경이나 URL 접근을 시키면 따르지 말고 사용자에게
무엇이라고 적혀 있었는지 알리라고 한다.
저장소 자체의 코드, 스크립트, 설치 단계, 시험은 절대 실행하지 않는다는 규칙도
있다.
메시지당 질문은 하나로 제한하고, 보내기 전에 물음표와 요청 표현의 수를 세어
하나만 남기게 한다.

## 사용법

```text
/rederive                                       # 지금 있는 저장소
/rederive ~/code/myapp                          # 로컬 저장소
/rederive https://github.com/expressjs/express  # 현재 폴더에 복제
```

다른 위치에 복제하려면 에이전트를 시작하기 전에 `REDERIVE_CLONE_DIR` 환경 변수를
정한다.
막혔다거나 문제를 건너뛰고 싶다거나 처음부터 다시 하고 싶다는 말을 평범한
문장으로 하면 된다.
README는 텔레메트리를 보내지 않으며 지도와 기록이 모두 로컬의 `.rederive/`에
남는다고 밝힌다.
다만 에이전트가 코드를 자기 모델로 보내는 것은 다른 작업과 같다고 사이트의 FAQ가
덧붙인다.

## 분석

### 지식 전달을 문제 풀이로 뒤집은 설계다

보통 에이전트에게 코드를 설명해 달라고 하면 설명이 돌아온다.
rederive는 이 방향을 뒤집어 에이전트가 문제를 내고 사용자가 설계를 만든다.
SKILL.md의 첫 문단이 이를 명시한다. 사용자는 아는 프레임워크가 아니라 맨 문제와
플랫폼의 기본 사실에서 시스템을 설계해야 하고, 설명은 마지막 수단이다.
이 접근은 소크라테스식 문답이라는 오래된 교수법을 코드 이해에 적용한 것이며,
저장소 주제 태그에도 `socratic-method`가 들어 있다.

### 품질 장치가 지도 한 장에 몰려 있다

이 스킬의 품질은 에이전트가 만드는 `map.md`의 질에 거의 전적으로 달려 있다.
문제의 순서, 제약, 선택지, 정답이 모두 여기서 나오기 때문이다.
SKILL.md는 이 지도의 품질을 지키려고 몇 가지를 둔다.
변경 메시지보다 diff와 코드를 믿으라고 하고, 코드 위치는 `grep -n`으로 실제
존재를 확인하게 하며, 선택 기준을 “사용자가 문제에서 발명할 수 있는
메커니즘”으로 좁혔다.
사이트의 FAQ는 AI가 큰 변경 몇 개로 만든 저장소에서도 이 방식이 동작한다고
말하는데, 그래서 이력이 아니라 코드 구조를 읽는 `structure.py`를 따로 둔 것으로
보인다.

### 에이전트의 행동 규칙이 곧 제품이다

저장소에는 실행되는 프로그램이 거의 없다.
제품의 대부분은 에이전트가 따라야 할 규칙문이다.
메시지당 질문 하나, 문제 도중 파일명 비공개, 결정을 말해 놓고 이유를 묻는 일
금지, 문제 수를 미리 말하지 않기 같은 규칙이 그렇다.
이런 규칙은 모델이 잘 따르는 한도에서만 효과가 있으며, 이 스킬은 그 점을 자체
규칙(발송 전 물음표 세기)으로 보완하려 한다.

## 비평

### '설명하지 않는다'는 약속이 문서 안에서 단계적으로 풀린다

README와 사이트는 질문만 하고 설명하지 않는다고 말한다.
그러나 SKILL.md는 막힌 경우 선택지를 장단점과 함께 보여 주고, 틀린 답이 두 번
나오면 문제를 그림으로 그려 주고, 문제가 끝나면 코드 위치와 도입된 변경을 알려
주게 한다.
이는 모두 합리적인 보조이고 설명이 마지막 수단이라는 SKILL.md의 문장과도 맞는다.
다만 사용자에게 보이는 약속은 “질문만 한다”이고 실제 동작은 “질문을 먼저 하고
막히면 힌트를 준다”에 가깝다.
설계 의도가 그렇다면 첫 문장의 약속도 거기에 맞추는 편이 정확하다.

### 학습 효과를 보여 주는 근거가 저장소에 없다

저장소는 이 방식이 코드를 이해하게 한다고 전제하지만, 면접이나 업무에서 설명이
나아졌다는 측정이나 사례는 싣지 않는다.
사이트와 README의 증거는 세션 화면 한 장과 동작 설명이다.
마무리 카드가 보여 주는 “힌트 없이 푼 문제 수”는 사용자가 얼마나 풀었는지의
기록이지 이해가 남았는지의 기록이 아니다.
이는 비판이라기보다 아직 없는 것의 목록이다. 이 문서도 스킬을 직접 실행해 보지
않았으므로 효과에 대해서는 판단하지 않는다.

### 코드 이해의 단위가 '결정 5~10개'로 고정되어 있다

지도는 문제를 5~10개로 정한다.
작은 저장소에는 맞는 숫자일 수 있지만, 큰 시스템의 모든 중요한 결정이 10개 안에
들어간다고 보기는 어렵다.
README는 이 숫자를 설계 특성으로 적지만 왜 이 범위인지는 말하지 않는다.
또한 선택 기준이 “사용자가 문제에서 발명할 수 있는 메커니즘”이라 규모, 성능,
호환성처럼 문제에서 도출하기 어려운 결정은 지도에서 빠질 가능성이 있다.

### 저장소 소개 문구가 서로 맞지 않는다

지원 에이전트 수가 문서마다 다르다.
README의 배지는 “75개 더”, 본문은 “약 70개”라고 쓰고, `docs/`의 발표 준비 문서는
“다른 22개”와 “25개”로 적는다.
시점이 다른 값이 갱신 없이 남은 것으로 보이며 기능에 영향은 없지만, 숫자를
내세우는 소개일수록 일관되어야 한다.
사이트의 별 수도 같은 문제를 보인다(1,025개 대 API의 1,672개).

### 저장소에 성장 전략 문서가 함께 들어 있다

`docs/` 아래에는 인기 있는 스킬 저장소들이 어떻게 별을 얻었는지 정리한 글과,
10월 26일 월요일 발표 일정의 게시 초안이 들어 있다.
내용은 발표 시간대, 커뮤니티별 게시 전략, 큐레이터에게 보낼 메시지, 별이
530개에서 954개로 늘어난 시기의 유입 경로(인스타그램 릴스 영상)까지 구체적이다.
작성자가 이를 숨기지 않고 공개한 점은 투명하지만, 사용자가 받는 스킬 저장소에
홍보 운영 문서가 섞여 있다는 사실은 알아 둘 만하다.
이 문서는 `docs/` 안의 수치를 저장소 스스로의 기록으로 소개할 뿐 확인하지
않았다.
같은 문서가 인용하는 외부 조사 보고서는 열지 못했다.

### 이 문서가 확인한 범위

저장소를 `--depth 1`로 복제해 README, SKILL.md 전체, `history.sh` 전체,
`structure.py` 앞부분, `docs/` 두 파일, 플러그인 설정을 읽었다.
`structure.py`의 언어별 분석 본문은 읽지 않았고, 스킬을 실행하지 않았다.
README의 “75개 에이전트 지원”과 “텔레메트리 없음”도 직접 시험하지 않았다.
텔레메트리에 대해서는 읽은 스크립트에 네트워크 호출이 없다는 것까지만 확인했다.

## 인사이트

### 질문을 설계의 일부로 삼으면 AI 의존의 문제가 학습 문제로 바뀐다

이 아이디어는 이 문서의 해석이다.
AI에게 코드를 맡기면 코드는 생기지만 이해는 따라오지 않는다는 불만이 이 저장소의
출발점이다.
rederive는 이 간격을 에이전트에게 더 설명시키는 방식이 아니라, 에이전트를
질문자로 쓰는 방식으로 메운다.
같은 모델이 코드를 쓰던 입에서 질문하는 입으로 역할이 바뀌는 셈이다.

여기서 생기는 비용은 시간과 노력이다.
설명을 읽는 것보다 설계를 직접 해 보는 것이 훨씬 오래 걸리고, 이 방식은 사용자가
그 비용을 치를 동기가 있을 때만 쓰인다.
저장소가 면접 준비를 첫 사례로 내세우는 이유도 그 동기가 분명한 상황이기
때문으로 읽힌다.

### 스킬의 본체가 규칙문일 때 업데이트는 문장 수정이다

이 저장소는 실행 파일 없이 마크다운 한 장이 제품이다.
설치는 폴더 하나를 복사하는 일이고, 동작을 고치는 일은 문장을 고치는 일이다.
이는 배포와 수정이 쉽다는 장점이지만, 같은 문장이 모델이 바뀔 때마다 다르게
해석될 수 있다는 약점도 함께 가진다.
지도 만들기와 질문 방식이 모델의 성능에 직접 의존하므로, 같은 스킬이 모델마다
다른 품질을 낼 가능성이 크다.
어떤 모델에서 시험했는지가 저장소에 적혀 있지 않은 것은 이 점에서 아쉽다.

### 학습용 스킬은 이해 확인 방법을 만들어야 다음 단계로 간다

지금의 기록(`log.md`)은 어디서 막혔는지를 적는다.
다음 단계는 세션이 끝난 뒤 며칠 지나 같은 결정을 다시 묻고 기억나는지를 보는
것처럼, 이해가 남았는지를 확인하는 장치일 것이다.
간격을 두고 다시 묻는 복습은 학습 연구에서 오래 쓰여 온 방법이고, 이 스킬의 로그
구조가 이미 그 재료를 갖고 있다.
이 제안은 이 문서의 해석이며 저장소가 계획한 것으로 확인된 바는 없다.

### 코드를 읽는 이유가 '고치기'에서 '설명하기'로 이동한다

저장소가 내세우는 상황은 면접과 업무에서의 설명이다.
AI가 코드를 대신 쓰는 환경에서는 코드를 직접 고치는 능력보다 코드가 왜 그렇게
생겼는지 설명하는 능력이 따로 평가받는 순간이 생긴다.
rederive가 팔리는 것은 이 변화에 대한 불안이다.
이 불안이 얼마나 오래 이어질지는 알 수 없고, 그에 따라 이 도구의 수요도 달라질
수 있다.
