# ECC: 별 25만 개짜리 스킬 모음이 측정에서는 평균 이하였다

<https://ecc.tools/>

<https://github.com/affaan-m/ECC>

## 소개

ECC는 자신을 “에이전트 하네스 성능 최적화 시스템”으로 규정하는 대규모 스킬 모음이다.
저장소 설명은 “스킬, 본능, 메모리, 보안, 그리고
Claude Code, Codex, Opencode, Cursor 등을 위한 연구 우선 개발”이다.
MIT 라이선스이고 2026년 1월 18일에 만들어졌으며,
확인 시점 기준 별 255,248개, 포크 38,230개다.
주 언어는 JavaScript로 표시되지만
README의 배지는 Shell, TypeScript, Python, Go, Java, Perl, Markdown을 함께 나열한다.

README는 13개 언어로 번역돼 있고
(영어, 포르투갈어, 중국어 간체·번체, 일본어, 한국어, 튀르키예어,
러시아어, 베트남어, 태국어, 독일어, 스페인어, 우크라이나어),
Discord, 웹사이트 `ecc.tools`, GitHub App,
npm 패키지 `ecc-universal`과 `ecc-agentshield` 배지가 상단에 배열된다.
star-history의 “오늘의 트렌딩 저장소” 배지와 전역 순위 배지도 있다.

ECC는 “Everything Claude Code”의 약자이며,
GeekNews에 소개된 바에 따르면
2025년 9월 Anthropic과 Forum Ventures가 연 해커톤에서 우승한 작품이다.[^gn-jamkris]

### 구성 요소

README가 제시하는 구성은 다섯 종류다 —
에이전트 68개(계획, 리뷰, 빌드 수리, 보안, 아키텍처, 도메인 작업),
스킬 286개(TDD, 연구, 보안, 문서, 프런트엔드, 데이터, ML, 운영 등),
명령 94개(“ECC가 스킬 우선 표면으로 이동하는 동안의 편의 진입점”),
훅과 메모리(강제, 세션 요약, 지속 학습, 본능, 컨텍스트 제어),
규칙(언어나 프로젝트별로 선택하는 상시 적재 표준),
그리고 AgentShield(프롬프트, 훅, MCP 설정, 권한, 비밀, 에이전트 파일 스캔)다.

설치는 `npx ecc-universal setup`이 정식 경로이며
Node.js 18 이상, Git, Claude Code 2.1 이상을 요구한다.
Codex 앱과 CLI, 그 밖의 에이전트와 에디터를 위한 경로가 따로 문서화돼 있고,
“저컨텍스트·훅 없음 경로”라는 별도 설치 옵션도 있다.
자체 호스팅 모델과 커스텀 엔드포인트 절에는
ECC와 Itô compute로 Kimi를 자체 호스팅하는 방법이 포함된다.

README 상단에는 경고 상자가 있다 —
검증된 채널에서만 설치하라는 것이며,
GitHub 저장소, 두 npm 패키지, GitHub App,
플러그인 슬러그 `ecc@ecc`, 웹사이트를 열거하고
“서드파티 재업로드와 비공식 미러는 프로젝트가 유지·검토하지 않으며
멀웨어를 포함할 수 있다”고 적는다.

### 판매 논거

“왜 ECC를 선택하는가” 절은 대조표로 제시된다.
시스템이 없으면 계획이 채팅 기록으로 사라지지만
ECC에서는 구현이 시작되기 전에 편집 가능한 산출물이 된다.
“TDD를 써 주세요”는 모델이 잊을 수 있는 지시이지만
ECC에서는 증거를 동반한 RED → GREEN → REFACTOR 게이트 워크플로가 된다.
같은 컨텍스트가 코드를 쓰고 리뷰하는 대신
새 컨텍스트의 리뷰어가 회귀와 맹점을 찾는다.
메모리가 거대한 대화록을 저장하는 것을 뜻하는 대신
세션이 요약과 본능과 재사용 가능한 스킬로 증류된다.
품질 검사가 상기에 의존하는 대신 훅이 결정론적으로 강제할 수 있다.

버전 이력이 README 안에 길게 실려 있다.
2026년 2월에 v1.2.0(통합 명령과 스킬)부터 v1.6.0(Codex CLI, AgentShield, 마켓플레이스)까지,
3월에 v1.8.0(하네스 성능 시스템)과 v1.9.0(선택적 설치와 언어 확장),
4월에 v2.0.0-rc.1, 6월에 v2.0.0(“에이전트 하네스 운영체제”),
그리고 현재 2.1과 개발 중인 통합 메모리 볼트다.
스타 히스토리 그래프의 설명은
“2026년 1월 18일부터 2월 7일까지 첫 4만 개 별”이다.

### rust-testing 스킬

`skills/rust-testing/SKILL.md`는 11,798자다.
프런트매터의 설명은
“단위 테스트, 통합 테스트, 비동기 테스트, 속성 기반 테스트,
모킹, 커버리지를 포함한 Rust 테스트 패턴. TDD 방법론을 따름”이며,
`metadata: origin: ECC`가 붙는다.

“작동 방식”은 일곱 단계다 —
대상 코드 식별, 테스트 작성(`#[test]`,
매개변수화에는 rstest, 속성 기반에는 proptest),
mockall로 의존성 모킹, 테스트 실행(RED),
구현(GREEN), 리팩터링, 그리고 cargo-llvm-cov로 커버리지 확인하되 80% 이상을 목표로 하는 것이다.

TDD 워크플로 절이 이 스킬의 중심이다.
RED-GREEN-REFACTOR 순환이 도식으로 제시되고,
`todo!()`를 자리표시자로 두고 테스트를 먼저 쓴 뒤
최소 구현으로 통과시키는 예제가 코드로 나온다.

나머지는 항목별 패턴 카탈로그다 —
모듈 수준 테스트 조직, 어서션 매크로,
`Result` 반환과 패닉 테스트, 통합 테스트 파일 구조,
Tokio 비동기 테스트, rstest 매개변수화, 테스트 헬퍼,
proptest 기본 속성 테스트와 커스텀 전략, mockall 트레이트 모킹,
독 테스트, Criterion 벤치마킹, 커버리지 실행과 목표,
테스트 명령 모음, 모범 사례, CI 통합이다.

커버리지 목표는 표로 제시된다 —
핵심 비즈니스 로직 100%, 공개 API 90% 이상,
일반 코드 80% 이상, 생성·FFI 바인딩은 제외다.

모범 사례는 DO와 DON'T 목록이다.
할 것으로는 테스트를 먼저 쓸 것(TDD),
`#[cfg(test)]` 모듈 사용, 구현이 아니라 동작 테스트,
시나리오를 설명하는 서술적 테스트 이름,
`assert!`보다 `assert_eq!` 선호,
`Result`를 반환하는 테스트에서 `?` 사용,
테스트 독립 유지가 열거된다.
하지 말 것으로는 `Result::is_err()`로 테스트할 수 있을 때 `#[should_panic]` 쓰기,
모든 것을 모킹하기, 불안정한 테스트 무시하기,
테스트에서 `sleep()` 쓰기, 오류 경로 테스트 건너뛰기가 있다.
문서는 “테스트는 문서다”라는 문장으로 끝난다.

## 분석

### danluu의 측정에서 이 스킬이 받은 판정은 총점과 실제 효과가 정반대였다

Dan Luu가 26개 조건과 4개 스킬로 에이전트 테스트 기법을 평가했을 때
ECC Rust 테스트 스킬은 총점으로는 Default에 거의 근접했다.
그런데 그가 실행을 분해하자 다른 그림이 나왔다.

160회 중 153회가 스킬을 읽었고 그것이 테스트를 더 만들게 했는데,
언제 읽었는지(이르게·늦게·아예 안 읽음)로 나누자
노출에 따른 기울기가 관찰됐다 —
일찍 읽을수록 행동이 더 바뀌었고 정확도는 더 나빴다.
총점이 괜찮아 보인 이유는
스킬을 읽지 않은 7회가 100% 정확도를 냈고
늦게 봐서 거의 영향받지 않은 9회도 100%였기 때문이다.
실제로 영향을 받은 경우만 보면
ECC는 평균 이하이며 Rust 내장 프레임워크와 Creusot 사이에 놓인다.

그가 지목한 원인은 이 저장소에서 그대로 확인된다 —
“스킬이 에이전트에게 red-green TDD를 쓰라고 지시한다”는 것이다.
`SKILL.md`의 세 번째 절 제목이 “TDD Workflow for Rust”이고,
“작동 방식” 일곱 단계 중 세 단계가 RED-GREEN-REFACTOR이며,
모범 사례 DO 목록의 첫 항목이 “테스트를 먼저 쓸 것(TDD)”이다.
danluu의 별도 조건에서 TDD 프롬프트는 예측대로 저조했고,
그 이유는 에이전트가 어려운 경우를 다루지 않는 테스트를 더 많이 쓰기 때문이었다.

즉 이 스킬의 문제는 부정확한 정보가 아니라 정확한 나쁜 지시다.
문서에 적힌 Rust 테스트 패턴은 대체로 옳고,
`assert_eq!` 선호나 `sleep()` 금지 같은 항목은 통상적인 조언이다.
결과를 나쁘게 만든 것은 그 조언들이 아니라
“먼저 실패하는 테스트를 쓰라”는 워크플로 지시이며,
그것이 에이전트에게 작고 의미 없는 테스트를 대량 생산하게 만든다.

### 별 25만 개와 측정된 효과 사이의 간극이 이 사례의 핵심이다

이 저장소는 확인 시점 기준 별 255,248개, 포크 38,230개다.
GitHub 전체에서 상위권에 드는 숫자이며,
README에 트렌딩 배지와 전역 순위 배지가 붙어 있다.
스타 히스토리 설명에 따르면 2026년 1월 18일 생성 후
2월 7일까지 3주 만에 4만 개를 모았다.

danluu가 이 사례에서 끌어낸 결론이 바로 그 간극이다.
그는 “우리는 스킬을 160회 돌렸는데
이것은 어느 합리적인 사람이 하는 것보다 많은 횟수”라면서도,
“겉으로 총점만 보면 ECC가 괜찮아 보인다”고 적는다.
그리고 사람들이 몇 번의 작은 실행으로
스킬이 유용하다고 오해하는 일이 흔하며,
공개 LLM 벤치마크에 대해서도
통계적으로 무의미한 총점이 그대로 돌아다니는 것을 자주 본다고 덧붙인다.

별의 수가 측정된 효과와 무관하다는 것은 놀랍지 않다.
별은 문서를 읽고 인상이 좋을 때 눌리고,
효과는 에이전트 행동이 바뀔 때 발생하며,
둘 사이에 체계적 연결이 없기 때문이다.
문제는 그 무관함이 신호를 끊는다는 데 있다 —
설치 결정이 별을 근거로 내려지고
별은 효과를 반영하지 않으면 생태계가 학습하지 못한다.

이 저장소의 README가 그 순환을 보여준다.
상단에 별·포크·기여자·설치 수 배지가 여섯 개 있고,
스타 히스토리 그래프가 두 번 나오며,
“트렌딩 저장소”와 “전역 순위” 배지가 나란히 있다.
반면 어떤 과제에서 무엇이 얼마나 개선됐는지에 대한 수치는 없다.

### 286개 스킬과 68개 에이전트라는 규모가 그 자체로 설계 결정이다

이 저장소가 제시하는 숫자 — 에이전트 68개, 스킬 286개, 명령 94개 — 는
어떤 작업을 하든 관련된 무언가가 있다는 것을 약속한다.
그리고 그 약속이 채택의 이유이기도 하다.
하나씩 고르는 대신 한 번에 설치하면 된다는 것이다.

그런데 스킬이 확률적으로 발동한다는 사실과 이 규모가 만나면 문제가 생긴다.
danluu의 측정에서 Hegel 스킬은 160회 중 157회 발동했고
ECC 스킬은 153회 발동했다.
스킬이 하나일 때는 그 발동률이 성능을 결정하지만,
286개가 함께 설치돼 있으면
어느 스킬이 언제 발동하는지가 사용자 통제를 벗어난다.
그리고 각 스킬의 효과가 독립적이지 않으므로
개별 스킬을 평가한 결과가 조합에 그대로 적용되지 않는다.

README가 “저컨텍스트·훅 없음 경로”와
“먼저 올바른 구성 요소를 찾으라”는 절을 따로 두고 있다는 것이
이 문제를 저자도 인식하고 있음을 보여준다.
선택적 설치가 v1.9.0의 기능으로 등재돼 있고
규칙이 “언어나 프로젝트별로 선택하는” 것으로 서술된다.
그러나 정식 설치 경로는 여전히 `npx ecc-universal setup`이며
기본값이 전체 설치인지 선택 설치인지는 README에서 분명하지 않다.

### 이 프로젝트의 실제 형태는 스킬 모음이 아니라 플랫폼이다

README를 끝까지 읽으면 이것이 스킬 저장소가 아니라는 것이 분명해진다.
npm 패키지 두 개, GitHub App, 웹사이트, Discord, 마켓플레이스 슬러그가 있고,
`api.ecc.tools`가 배지 엔드포인트를 제공하며,
자체 호스팅 모델과 Itô compute CLI 브리지 절이 있고,
AgentShield라는 별도 보안 스캐너가 포함된다.
크로스 툴 능력 지도, 토큰 최적화, 보안, 문제 해결 절이 각각 길다.

이 구조에서 개별 스킬의 품질은 제품의 일부일 뿐이다.
`rust-testing/SKILL.md` 하나가 11,798자인데
286개 스킬이 있다면 스킬 텍스트만 수백만 자 규모다.
그 전부를 같은 밀도로 검증하는 것은 사실상 불가능하며,
danluu가 평가한 것은 그중 하나였다.

여기서 이 저장소를 평가할 때의 난점이 나온다.
하나의 스킬이 나쁘다는 것이 전체가 나쁘다는 뜻은 아니고,
전체가 좋다는 것을 보이려면
286개를 각각 측정해야 하는데 아무도 하지 않는다.
그리고 그 사실이 별 25만 개를 설명한다 —
검증 불가능한 규모는 검증되지 않은 채로 신뢰를 얻는다.

### 생태계 이식본이 나올 만큼 커졌고 그 과정에서 보안 버그가 발견됐다

이 저장소의 규모가 만든 이차 현상이 GeekNews에 기록돼 있다.
Gemini를 주로 쓰는 개발자 jamkris가
ECC의 스킬 183개를 Gemini CLI와 Antigravity 생태계로 통째로 이식해
Everything-Gemini-Code라는 프로젝트를 만들었다는 것이다.[^gn-jamkris]
그는 ECC의 생태계 포트임을 명시하고,
ECC에 새 커밋이 머지되면 주간 cron이 드리프트를 측정해
GitHub 이슈로 가시화하는 구조를 뒀다고 밝힌다.

여기서 주목할 것은 그가 덧붙인 한 문장이다 —
마이그레이션하면서 ECC의 보안 버그를 찾아내 PR을 올렸고
그것이 ECC에 병합됐다는 것이다(PR #1843, #1853).
그리고 ECC Discussions에 자기 프로젝트를 소개했더니
원작자가 피드백을 남겼다고 전한다.

이 사실이 앞 절의 검증 문제에 대한 부분적 답이 된다.
286개 스킬을 아무도 전부 검증하지 않는다고 했지만,
다른 생태계로 이식하려는 사람은 전부를 읽어야 하고
그 과정에서 문제를 발견한다.
즉 이식이 의도치 않은 감사 역할을 한 셈이다.
동시에 그 감사가 우연에 의존한다는 점도 드러난다 —
Gemini 사용자 한 명이 이식을 시도하지 않았다면
그 보안 버그는 발견되지 않았을 것이다.

## 비평

### 자체 측정 결과가 어디에도 없다

이 저장소는 “에이전트 하네스 성능 최적화 시스템”을 표방한다.
성능 최적화를 표방하는 시스템에는
최적화 전후를 비교한 수치가 있어야 하는데 README에 없다.

있는 것은 정성적 대조표다 —
“계획이 채팅 기록으로 사라진다” 대 “계획이 편집 가능한 산출물이 된다”,
“TDD를 써 달라는 것은 모델이 잊을 수 있는 지시” 대
“증거를 동반한 게이트 워크플로”.
이 대조는 무엇이 달라지는지를 서술하지만
그것이 결과를 개선하는지는 말하지 않는다.
그리고 danluu의 측정에서는 정확히 그 TDD 게이트 워크플로가
결과를 나쁘게 만든 원인으로 지목됐다.

“토큰 최적화”라는 절이 README에 따로 있다는 점이 이 문제를 키운다.
토큰은 측정하기 가장 쉬운 지표이고,
스킬이 컨텍스트를 차지한다는 것은 자명하므로
“우리 스킬을 켠 실행과 끈 실행의 토큰 차이”는
저자가 하루면 낼 수 있는 수치다.
그 수치가 없는 상태에서 “성능 최적화 시스템”이라는 규정은
검증되지 않은 자기 서술로 남는다.

### 규모를 자랑하는 지표만 있고 효과를 나타내는 지표는 하나도 없다

README 상단에 배지가 열네 개 있다.
Discord, 웹사이트, GitHub App, 라이선스,
별, 포크, 기여자, 설치 수, npm 주간 다운로드 두 개,
그리고 언어 배지 일곱 개다.
여기에 트렌딩 배지와 전역 순위 배지가 별도로 있고
스타 히스토리 그래프가 본문에 삽입된다.

이 배지들이 공통으로 재는 것은 채택이다.
얼마나 많은 사람이 별을 눌렀고, 설치했고, 내려받았는지다.
소프트웨어 저장소에서 흔히 함께 붙는
빌드 상태, 테스트 커버리지, 벤치마크 결과 배지는 없다.
`## Running Tests` 절이 README 뒤쪽에 있으므로
테스트 자체는 존재하는데 그 결과가 상단에 노출되지 않는다.

이 선택이 우연이 아닌 이유는
채택 지표가 자기 강화적이기 때문이다.
별이 많으면 트렌딩에 오르고,
트렌딩 배지가 README에 붙으면 더 많은 별을 모으며,
그 순환에 효과에 대한 정보는 들어가지 않는다.
star-history 링크가 세 곳에 걸려 있다는 것이
이 순환을 의식적으로 운용하고 있음을 보여준다.

### 보안 경고문이 이 프로젝트가 처한 상황을 드러내는데 그 원인은 다루지 않는다

README 첫 화면에 굵은 경고 상자가 있다.
공식 채널에서만 설치하라는 것이며,
서드파티 재업로드와 비공식 미러가
유지·검토되지 않고 멀웨어를 포함할 수 있다고 경고한다.

이 경고가 필요했다는 것은 실제로 그런 미러가 존재한다는 뜻이다.
그리고 그것은 이 프로젝트의 성공이 만든 결과다 —
25만 별짜리 스킬 모음은 공급망 공격의 매력적인 표적이며,
사용자가 스킬을 설치한다는 것은
에이전트에게 임의의 지시를 주입할 권한을 주는 것이기 때문이다.

그런데 경고는 “우리 채널을 쓰라”로 끝난다.
공식 채널에서 받은 스킬이 안전하다는 것을 사용자가 어떻게 확인하는지,
286개 스킬의 변경이 어떻게 검토되는지,
서명이나 체크섬 같은 검증 수단이 있는지는 나오지 않는다.
AgentShield가 “프롬프트, 훅, MCP 설정, 권한, 비밀, 에이전트 파일”을 스캔한다고 하는데
그것이 자기 자신의 스킬도 스캔하는지는 불분명하다.
자기 프로젝트의 보안을 스캔하는 도구를 자기 프로젝트가 포함한다면
그 구조 자체를 설명해야 하는데 README는 그 층위를 다루지 않는다.

### rust-testing 스킬의 조언 다수가 Rust 기본 문서와 겹친다

이 스킬의 내용을 항목별로 보면
`#[cfg(test)]` 모듈 사용, `assert_eq!`와 `assert!`의 차이,
통합 테스트를 `tests/` 디렉터리에 두는 것,
`cargo test` 플래그 목록, 독 테스트 —
대부분이 Rust 공식 책과 cargo 문서에 있는 내용이다.

이것이 문제인 이유는 대상이 사람이 아니라 모델이기 때문이다.
Rust 공식 문서는 훈련 데이터에 대량으로 들어 있으므로
모델이 이미 아는 내용을 다시 적재하는 것은
컨텍스트를 소비하되 행동을 바꾸지 않는다.
danluu가 스킬 설계에 대해 “이미 주제를 아는 모델을 상대할 때는
기본 행동을 수정하는 진술을 주어야지
모르는 사람이 그 행동을 할 수 있게 하는 설명서를 쓰는 것이 아니다”라고 적은 것이 이 지점이다.

그리고 실제로 행동을 바꾼 부분은
모델이 이미 알던 것이 아니라 TDD 지시였고,
그것이 결과를 나쁘게 만들었다.
즉 이 스킬은 무해한 부분으로 컨텍스트를 채우고
유해한 부분으로 행동을 바꾼 셈이다.
danluu가 ECC에서 “대부분의 지시가 무시됐고
영향력 있었던 TDD 지시는 결과를 나쁘게 만들었다”고 관찰한 것이 정확히 그 구조다.

## 인사이트

### 스킬 모음의 규모는 검증 불가능성을 통해 신뢰를 만든다

286개 스킬, 68개 에이전트, 94개 명령이라는 숫자는
“무엇을 하든 쓸 것이 있다”는 약속으로 읽힌다.
그런데 같은 숫자가 다른 것을 뜻하기도 한다 —
아무도 전체를 검증할 수 없다는 것이다.

검증 가능한 작은 도구는 검증당한다.
누군가 써 보고 안 되면 이슈를 열고,
그 이슈가 쌓이면 평판이 정해진다.
286개짜리 모음에서는 어느 스킬이 발동했는지조차 추적하기 어렵고,
결과가 나빠도 원인을 특정할 수 없으며,
사용자는 “내가 잘못 썼나” 쪽으로 귀인하게 된다.

이 구조는 다른 분야에도 있다.
기능이 수백 개인 엔터프라이즈 소프트웨어,
성분이 수십 개인 건강기능식품,
지표가 백 개인 컨설팅 보고서가 같은 성질을 갖는다.
공통점은 개별 요소의 효과를 분리할 수 없어
전체에 대한 인상만 남는다는 것이며,
그 인상은 대개 규모 자체가 만든다.

danluu의 노출-반응 분석이 이 구조를 깨는 유일한 방법을 보여준다 —
스킬을 읽은 실행과 읽지 않은 실행을 나누는 것이다.
이 분해는 286개 전부에 대해 할 수 있고,
발동률과 노출별 성능만 있으면 되므로 비싸지도 않다.
그런 데이터를 요구하는 관행이 없다는 것이
이 생태계의 현재 상태이며,
25만 별과 평균 이하 성능이 공존하는 이유다.

### 정확한 정보로 채운 스킬이 나쁜 워크플로 하나로 무너질 수 있다

이 스킬의 내용은 대부분 옳다.
`sleep()` 대신 채널이나 `tokio::time::pause()`를 쓰라는 것,
불안정한 테스트를 무시하지 말라는 것,
`#[should_panic]`보다 `Result::is_err()`를 쓰라는 것은
Rust 커뮤니티의 통상적 합의다.

그런데 측정된 효과는 음수였고,
그 원인이 목록 어디에도 없는 절 —
RED-GREEN-REFACTOR 워크플로 — 이었다.
정보의 정확성과 워크플로의 효과가 독립 변수이며,
후자가 전자를 압도한다는 뜻이다.

이 비대칭에는 이유가 있다.
정확한 정보는 모델이 이미 알 확률이 높으므로 한계 효과가 작고,
워크플로 지시는 행동 순서를 바꾸므로 효과가 크다.
그리고 행동 순서를 바꾸는 것은
그 순서가 옳을 때만 좋은 일이다.
사람에게 좋은 워크플로가 에이전트에게도 좋을 것이라는 가정이
이 스킬의 유일한 검증되지 않은 전제이며,
danluu의 TDD 조건이 그 전제를 반증한다.

실무적 함의는 스킬을 검토하는 순서다.
사실 오류를 찾는 것은 쉽고 대체로 무해한 반면,
행동 순서를 바꾸는 문장을 찾는 것이 어렵고 중요하다.
“이 스킬에서 에이전트가 하는 일의 순서를 바꾸는 문장이 무엇인가”를
먼저 묻고, 그 문장만 실측하면
286개 스킬 중 검증이 필요한 것이 훨씬 줄어든다.

### 스킬 배포가 공급망이 되면 서명 없는 배포는 지속될 수 없다

README 첫 화면의 보안 경고는
이 프로젝트가 이미 공급망 표적이 됐음을 보여준다.
그리고 스킬 공급망은 코드 공급망보다 검증이 어렵다.

코드는 실행 전에 정적 분석을 할 수 있고,
악성 동작이 대체로 코드 형태로 존재하므로 패턴을 찾을 수 있다.
스킬은 자연어 지시이며 악성 지시와 정상 지시의 구문적 차이가 없다.
“테스트가 실패하면 테스트를 수정하라”는 문장은
정상적인 조언일 수도 있고 품질을 무너뜨리는 지시일 수도 있으며,
그 판별에는 맥락 이해가 필요하다.
AgentShield가 프롬프트를 스캔한다고 해도
이 판별을 자동화하기는 원리적으로 어렵다.

그리고 스킬의 권한 모델이 이 문제를 키운다.
설치된 스킬은 에이전트의 컨텍스트에 들어가고,
에이전트는 파일 시스템과 셸과 네트워크에 접근한다.
즉 스킬 설치는 임의 코드 실행 권한을 주는 것과 실질적으로 같은데,
npm 패키지와 달리 잠금 파일도 무결성 해시도 관례가 되어 있지 않다.

역사적으로 같은 단계를 거친 생태계들이 있다.
npm은 초기에 서명이 없었고 typosquatting 사고를 겪은 뒤
잠금 파일과 무결성 해시와 프로비넌스를 도입했다.
브라우저 확장은 사이드로딩이 자유롭던 시기를 지나
스토어 심사와 서명으로 옮겨 갔다.
스킬 생태계는 지금 그 이전 단계에 있으며,
이 저장소의 경고문이 그 단계의 전형적 대응 —
“우리 채널만 쓰세요” — 이다.
그 대응이 충분했던 전례는 없다.

### 채택 지표만 노출하는 관행이 이 분야의 정보 환경을 만든다

이 저장소의 README에는 배지가 열네 개 있고
그중 효과를 재는 것은 하나도 없다.
이것을 이 프로젝트의 선택으로만 보면 비판이 되지만,
관행으로 보면 다른 이야기가 된다 —
붙일 수 있는 효과 배지가 존재하지 않는다.

소프트웨어에는 CI 통과 배지, 커버리지 배지, 다운로드 배지가 있고
그중 앞의 둘은 품질에 관한 것이다.
스킬에는 대응물이 없다.
“이 스킬은 X 벤치마크에서 무조건 대비 Y% 개선”이라는 배지를 만들려면
표준 벤치마크와 표준 측정 절차가 있어야 하는데 둘 다 없다.
그래서 붙일 수 있는 것이 별과 포크와 설치 수뿐이고,
모든 스킬 저장소가 같은 배지를 단다.

이 공백을 메우는 데 필요한 것은 대단한 인프라가 아니다.
danluu가 이 실험 전체를 하며 쓴 것은
Zstd RFC 하나와 숨겨진 테스트 스위트,
그리고 조건당 160회 실행이다.
표준 과제 몇 개와 발동률·노출별 성능 보고 형식만 합의되면
스킬 저장소가 자기 수치를 붙일 수 있고,
붙이지 않은 저장소가 눈에 띄게 된다.

그리고 그 관행이 생기면 지금의 순환이 끊긴다.
현재는 문서가 좋아 보이면 별을 받고
별이 많으면 설치되며 효과는 측정되지 않는다.
효과 배지가 있으면 문서 품질과 별개의 축이 생기고,
이 저장소처럼 규모가 큰 프로젝트일수록
그 축에서 불리해질 수 있다는 것이
이 관행이 자발적으로 생기지 않는 이유이기도 하다.
