# AI 위임 루프: 에이전트를 늘리지 말고 일마다 매뉴얼 폴더를 키워라

원문: [AI 위임 루프: 에이전트 대신 매뉴얼으로 일 넘기기 | 낭만빌더 김스듴](https://sdk-kim-builds.com/guides/ai-delegation-loop-playbook/)

## 소개

낭만빌더 김스듴이 2026년 9월 18일에 올린 실무 가이드다.
주장은 첫 문단에 다 들어 있다.
일마다 에이전트를 새로 만들지 말고, 일 하나에 매뉴얼 폴더 하나를 만들어
범용 AI에게 넘기라는 것이다.
가이드는 그 폴더를 세 레이어(프로세스, 툴박스, 증명)로 나누고,
각 레이어를 세팅하는 붙여넣기 프롬프트 네 개와
실패한 결과를 폴더로 되돌리는 루프를 제공한다.
첫 매뉴얼 하나에 30분 정도를 잡으라고 한다.

가이드가 약속하는 것은 쓸수록 나아지는 위임이다.
수정이 채팅이 아니라 폴더에 쌓이므로
같은 실수를 다시 타이핑할 일이 줄어든다는 것이다.
약속하지 않는 것도 있다.
매뉴얼이 지켜지는지를 확인하는 장치는 결국 같은 AI가 돌리는 검증 항목이고,
그 검증을 바깥에서 강제하는 방법은 다루지 않는다.

이 문서는 가이드의 구조를 정리하고,
각 결정에 무엇이 걸려 있는지, 실제로 어디서 깨지는지,
그리고 검증을 AI의 말이 아니라 실행으로 확인하는 방법을 다룬다.
같은 생각을 Anthropic 쪽에서 먼저 말한 발표는
`agent-skill/dont-build-agents-build-skills-instead.md`에 정리되어 있다.

## 동작 방식

### 왜 에이전트가 죽는다고 보나

가이드의 진단은 배선이다.
이메일용, 콘텐츠용, 리드용 에이전트를 따로 만들면
각자 프롬프트와 도구와 연결을 갖게 되고,
일이 조금만 바뀌어도 어딘가가 끊어지며 그걸 발견하는 사람은 사용자라는 것이다.
가이드는 이것을 데모에서는 잘 돌던 에이전트가 2주 안에 죽는 이유라고 부른다.

대안은 범용 에이전트 하나에 일별 폴더를 주는 것이다.
가이드는 처음부터 부족했던 것은 지능이 아니라
글로 적힌 사용자의 업무 지식이었다고 정리한다.

### 매뉴얼 폴더의 세 레이어

| 레이어   | 담는 것                                             | 없으면 생기는 일                         |
| -------- | --------------------------------------------------- | ---------------------------------------- |
| 프로세스 | 판단을 실제로 쓰는 순서, 결정 규칙, 예외 사례       | 결과물이 사용자답지 않다                 |
| 툴박스   | 스크립트, 템플릿, 참조 데이터, 좋은 예시, 규칙 파일 | 매번 같은 것을 새로 짓고 결과가 흔들린다 |
| 증명     | 실패할 수 있는 완료의 정의                          | 90%만 된 결과를 사용자가 검수하게 된다   |

프로세스 레이어는 `SKILL.md` 하나다.
가이드는 좋은 `SKILL.md`에 일곱 가지가 들어간다고 한다.
한 줄 목적, 언제 쓰는지(실제로 입에 담을 말로), 입력과 그 위치,
번호 붙은 순서, 결정마다 근거가 되는 규칙, 완료의 정의,
예전에 사고가 났던 예외 사례다.

툴박스는 `files/` 아래에 두고 `SKILL.md`가 이름으로 가리킨다.
넣을 것은 기계적 단계를 하는 스크립트, 대괄호 자리표시자가 든 템플릿,
고객 이름 표기나 가격 같은 참조 데이터, 만족했던 완성 예시, 규칙 파일,
자주 쓰는 하위 단계 프롬프트다.
넣지 말 것은 일회성 산출물, 비밀번호나 키가 담긴 것, 반쯤 된 초안이다.
가이드의 기준은 첫날 새 직원에게 주지 않을 것이면 폴더에도 넣지 말라는 것이다.

증명 레이어는 완료의 정의를 검증 항목으로 적은 것이다.
가이드가 가장 힘주어 말하는 레이어이고,
AI가 자기 초안을 읽고 괜찮아 보인다고 하는 것은 아무 가치가 없다고 한다.
증거로 인정되는 것은 원본 파일까지 추적되는 숫자, 열리는 링크,
렌더링 스크린샷, 실제로 도는 테스트, 인용문과 대조한 주장, 개수,
참조 파일과 대조한 표기다.
가이드는 실패할 수 없는 검증은 검증이 아니라고 정리한다.

### 다 만들어진 폴더

```text
[job-name]/
  SKILL.md              목적, 언제 쓰는지, 입력, 순서, 결정, 완료의 정의, 예외 사례
  files/
    INDEX.md            저장된 파일마다 한 줄: 이름, 용도, 날짜
    numbers-pull.py     기계적 단계를 수행하는 스크립트
    update-template.md  [자리표시자]가 든 템플릿
    tone-rules.md       사용자의 표준
  examples/
    2026-09-08-good.md  만족했던 완성 작업
  notes.md              수정 기록, 최신이 위로
```

일 하나에 폴더 하나다.
두 일이 자꾸 섞이면 원인은 각 `SKILL.md`의 언제 쓰는지 섹션이고,
그 일을 시키고 싶을 때 실제로 칠 말 그대로 적으라고 한다.

### 파일을 누가 쓰느냐에 따라 두 가지로 돌아간다

AI가 로컬 파일을 읽고 쓸 수 있는 환경,
즉 Claude Code나 파일 접근이 되는 에이전트에서는
`~/playbooks/weekly-client-update` 같은 실제 폴더를 두고
AI가 `SKILL.md`를 직접 고친다.
가이드는 이쪽을 복리로 쌓이는 형태라고 부른다.

브라우저나 데스크톱 앱의 Claude, ChatGPT에서 Project를 쓰는 경우는 다르다.
Project에 올린 파일을 AI가 다시 쓸 수 없으므로,
AI가 새 버전을 출력하면 사용자가 실제 폴더에 저장하고
올린 복사본을 교체해야 한다.
예전 파일을 지우지 않고 새 파일을 추가하면 같은 파일의 두 버전이 생기고,
AI는 몇 주 전에 폐기한 지시를 따르기 시작한다.
Dropbox나 Drive에서 올려도 링크가 아니라 복사본이 들어가므로,
마스터는 하나이고 업로드는 마스터를 고치는 순간 낡는 스냅샷이라는 것이
가이드의 원칙이다.

### 루프: 채팅이 아니라 매뉴얼을 고친다

틀린 결과가 나오면 먼저 어느 레이어가 실패했는지 진단한다.

| 증상                                          | 실패한 레이어 |
| --------------------------------------------- | ------------- |
| 단계가 빠졌거나 순서가 틀렸거나 규칙이 없음   | 프로세스      |
| 이미 있는 것을 다시 지었거나 저장 파일이 낡음 | 툴박스        |
| 이 실수를 잡았을 검증이 없음                  | 증명          |

그 레이어에 가장 작은 내구성 있는 수정을 하고,
같은 실수가 두 번째라면 부드러운 리마인더가 아니라 명시적 규칙을 넣는다.
수정마다 `notes.md`에 날짜, 무엇이 틀렸는지, 무엇을 바꿨는지를 한 줄로 남기고,
같은 작업을 처음부터 다시 돌려 전후를 비교한다.
`notes.md`는 한 달에 한 번 읽고,
같은 레이어에 기록이 반복되는 일은 정말 어려운 일이므로
다음에 제대로 자동화할 후보라고 본다.

## 세팅하기

가이드는 각 단계에 붙여넣을 프롬프트를 전문으로 제공한다.
여기서는 그대로 옮기지 않고, 각 프롬프트가 AI에게 강제하는 조건을 정리한다.
네 프롬프트 모두 끝에 같은 조항이 붙는다.
파일을 직접 쓸 수 없으면 쓴 척하지 말고
전체 내용과 정확한 파일명, 위치를 출력하고,
업로드된 예전 복사본을 교체하라고 상기시키라는 것이다.

### 프롬프트 1: 인터뷰로 `SKILL.md` 만들기

- 한 번에 질문 하나만 하고 답을 기다린다.
- 최소 여덟 개를 묻고, 사용자가 끝났다고 하기 전에는 파일을 쓰지 않는다.
- 계기와 빈도, 입력과 위치, 실제 순서, 결정과 규칙, 완료 전 확인 사항,
  예외 사례, 톤과 기준, 나쁜 버전의 모습을 모두 다룬다.
- 다 쓰면 파일 전체를 보여 주고,
  무엇을 잘못 뽑았는지와 사용자가 말하지 않은 것이 무엇인지를 묻는다.

답할 때는 완전한 문장과 실제 예시로 답하라고 한다.
짜증 나는 질문이 대개 진짜 중요한 질문이고,
첫 버전은 80% 정도 맞을 것이며, 고치는 것은 채팅이 아니라 파일에서 하라고 한다.

### 프롬프트 2: 통과한 산출물을 도구로 저장하기

- `files/`에 날짜나 버전 번호 없이 설명적인 이름으로 저장한다.
- 상황에 특화된 부분은 대괄호 자리표시자로 바꾸고 채워진 예시 하나를 아래에 남긴다.
- `SKILL.md`의 해당 단계가 파일을 이름으로 가리키게 하고, 언제 쓰고 언제 쓰지 않는지 적는다.
- `files/INDEX.md`에 파일명, 용도, 날짜를 한 줄 추가한다.
- 그런 다음 일을 처음부터 다시 돌려, 어떤 저장 파일을 썼고 무엇을 새로 지었는지 보고한다.

마지막 조건이 툴박스를 채우는 장치다.
가이드는 두 번째 실행에서 무엇이 다시 지어졌는지가 보이고,
그것이 모두 툴박스 후보라고 말한다.

### 프롬프트 3: 실패할 수 있는 검증 항목 만들기

- 일에 특화된 검증 항목을 5~10개 쓴다.
- 모든 항목은 AI 자신의 의견 바깥의 증거로 확인할 수 있어야 하고,
  명확한, 전문적인, 고품질 같은 애매한 단어는 쓰지 않는다.
- 일을 마칠 때마다 사용자에게 보여 주기 전에 전 항목을 돌리고, 실패를 고치고, 다시 돌린다.
- 항목마다 근거와 함께 통과/실패를 한 줄로 내고,
  확인할 수 없는 것은 통과로 가정하지 말고 이유와 함께 밝힌다.
- 첫 패스에서 두 개보다 많이 실패하면 결과물을 땜질하지 말고 멈춰,
  어느 프로세스 단계가 원인인지 보고한다.

### 프롬프트 4: 레이어 진단으로 고치기

틀린 이유를 정확히 적어 넘기면,
AI가 실패한 레이어를 두 문장으로 진단하고 그 레이어에 가장 작은 수정을 한다.
매뉴얼 전체를 다시 쓰지 말라는 조건이 붙고,
`notes.md`에 기록한 뒤 같은 작업을 다시 돌려 전후를 보여 주게 한다.

### 첫 30분

가장 자주 하는 일을 고르고, 프롬프트 1을 돌려 인터뷰에 답한다(15분쯤).
일을 한 번 돌려 제대로 나온 것을 프롬프트 2로 저장하고,
프롬프트 3으로 검증 항목을 넣은 뒤 두 번째로 돌린다.
가이드는 두 번째 실행에서 설명이 얼마나 줄었는지 보라고 하며
한 번으로 멈추지 말라고 한다.

## 값 정하기

| 값                   | 가이드의 출발점                                               | 근거와 바꿀 때                                                                     |
| -------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 첫 일감              | 주 1회 이상, 나쁜 버전을 한눈에 알아봄, 설명이 20분 안에 끝남 | 반복이 잦아야 루프가 돌고, 나쁜 버전이 보여야 검증 항목을 쓸 수 있다               |
| 인터뷰 질문 수       | 최소 8개                                                      | 순서, 결정, 예외를 모두 꺼내려면 필요하다. 예외가 많은 일이면 더 늘린다            |
| 검증 항목 수         | 5~10개                                                        | 적으면 구멍이 생기고 많으면 돌리는 비용이 커진다. 실패 기록이 쌓이는 쪽으로 늘린다 |
| 첫 패스 실패 허용    | 2개까지, 넘으면 멈춤                                          | 실패가 많으면 결과물이 아니라 프로세스가 틀렸다는 신호다                           |
| 폴더 검토 주기       | 매달                                                          | 거의 같은 파일이 두 개면 AI가 잘못된 쪽을 고른다                                   |
| `notes.md` 검토 주기 | 매달                                                          | 같은 레이어의 반복 기록이 다음 자동화 후보를 알려 준다                             |
| 같은 실수의 처리     | 두 번째부터 명시적 규칙                                       | 한 번은 우연일 수 있지만 두 번이면 매뉴얼의 빈칸이다                               |

이 값들은 가이드가 근거를 수치로 제시하지 않은 출발점이다.
바꿀 근거는 `notes.md`에서 얻는다.
같은 검증이 몇 주째 한 번도 실패하지 않으면 그 항목은 줄여도 되는 후보이고,
검증을 통과했는데 사용자가 고친 결과가 반복되면 항목이 모자란 것이다.

## 트레이드오프

### 에이전트 여럿 대신 매뉴얼 하나: 배선은 줄지만 경계는 사용자에게 온다

일별 에이전트를 없애면 에이전트마다 따로 있던 프롬프트와 도구 연결이 사라진다.
대신 어느 매뉴얼을 쓸지 고르는 일이 범용 에이전트의 판단으로 넘어간다.
가이드가 언제 쓰는지 섹션을 실제로 칠 말로 적으라고
거듭 강조하는 이유가 이것이다.
에이전트 사이의 배선이 끊어지던 문제는,
매뉴얼 사이의 경계가 흐려지는 문제로 모양을 바꿔 남는다.

배선이 없어지는 것도 아니다.
툴박스의 `numbers-pull.py`는 광고 대시보드에 접근해야 하고,
그 접근 경로와 인증은 여전히 어딘가에 설정되어 있어야 한다.
가이드는 비밀번호와 키를 폴더에 넣지 말라고만 할 뿐,
그러면 스크립트가 자격 증명을 어디서 얻는지는 다루지 않는다.
데이터 원천이 바뀌면 깨지는 것은 여전히 스크립트이고,
발견하는 사람도 여전히 사용자다.

### 자기 검증은 비용을 줄이지만 같은 눈으로 본다

증명 레이어는 사용자에게 오기 전에 AI가 자기 작업을 검증하게 한다.
이것으로 사용자가 보는 결과물의 품질은 분명히 올라가고, 검수 시간도 줄어든다.
그러나 검증 항목을 돌리고 통과/실패를 보고하는 주체가 결과물을 만든 AI 자신이다.
가이드가 증거의 예로 든 숫자 추적, 링크 확인, 테스트 실행은
도구로 실제 실행될 때만 증거가 되고,
실행 없이 쓴 통과 보고는 괜찮아 보인다는 말과 다르지 않다.

가이드도 이 위험을 알고 있어서
확인할 수 없는 것을 통과로 가정하지 말라는 조건을 넣었다.
그러나 이 조건도 같은 AI가 지키는 것이다.
결국 검증 비용을 줄이는 만큼, 검증이 실제로 돌았는지 확인하는 일이 새로 생긴다.
이 일은 검증 항목 일부를 AI 바깥의 스크립트로 옮겨야 줄어든다.
아래 확인하기 섹션의 스크립트가 그 예다.

### 인터뷰는 암묵지를 꺼내지만 사용자의 시간을 가장 많이 쓴다

가이드는 순서를 직접 적지 말고 인터뷰를 받으라고 한다.
스스로 적지 않을 부분이 결과물을 사용자답게 만드는 부분이기 때문이라는 것이다.
주간 고객 업데이트 예제에서 항상 가장 크게 움직인 숫자로 시작한다는 규칙은
어떤 SOP에도 없었지만 인터뷰에서 나왔다.

비용은 사용자 쪽에 몰린다.
한 번에 질문 하나씩 최소 여덟 개를 완전한 문장으로 답해야 하고,
그것이 일마다 반복된다.
인터뷰가 꺼낼 수 있는 것은 사용자가 말로 설명할 수 있는 판단까지다.
숙련자가 이유를 대지 못하는 판단은 질문으로 나오지 않고,
틀린 결과가 나온 뒤 루프에서 하나씩 드러난다.
그래서 첫 버전이 80% 정도라는 가이드의 기대치는 낙관이 아니라 구조적인 한계다.

## 함정

### 검증 항목이 결과물의 숫자를 원본과 대조하지 못하면 4주차의 실수가 다시 난다

가이드의 실전 예제는 4주차에 AI가 데이터에 없는 숫자를 지어낸 사례를 든다.
증명 실패로 진단하고 모든 수치가 뽑힌 파일에 존재해야 한다는 검증을 추가했더니
그 뒤로 한 번도 일어나지 않았다고 한다.
이 검증이 AI의 보고로만 돌아간다면,
같은 AI가 숫자를 지어내고 그 숫자가 파일에 있다고 보고할 수 있다.
이런 항목은 스크립트로 만들어 툴박스에 넣고,
`SKILL.md`가 그 스크립트의 출력을 증거로 붙이게 해야 한다.

### `examples/`의 날짜 파일명과 `files/`의 날짜 금지가 섞인다

프롬프트 2는 `files/`에 저장할 때 이름에 날짜나 버전을 넣지 말라고 하지만,
폴더 예시의 `examples/`는 `2026-09-08-good.md`처럼 날짜로 이름을 붙인다.
도구는 하나만 있어야 하고 예시는 여러 개가 쌓여도 된다는 구분으로 보이지만,
가이드는 이 구분을 따로 설명하지 않는다.
AI가 이 규칙을 반대로 적용하면 `files/`에 날짜가 붙은 템플릿이 쌓이고,
가이드가 경고한 거의 같은 파일 두 개 문제가 생긴다.
`SKILL.md`에 두 폴더의 이름 규칙을 따로 적어 두는 편이 낫다.

### 툴박스 스크립트는 실행되는 코드다

AI가 통과한 산출물을 스스로 스크립트로 저장하고 다음 실행 때 그 스크립트를 쓴다.
사용자가 그 코드를 읽지 않으면,
매뉴얼은 아무도 검토하지 않은 코드를 매주 돌리는 장치가 된다.
특히 파일 이름 바꾸기나 포맷 변환처럼 파일을 고치는 스크립트는
잘못되면 원본을 덮어쓴다.
저장 시점에 사람이 한 번 읽고, Git 같은 버전 관리 아래에 두는 것이 최소한이다.
이 부분은 가이드에 없는 이 문서의 권고다.

### Project 복사본은 언제나 낡아 있다

채팅 전용 도구에서는 실제 폴더와 Project 업로드가 따로 존재한다.
AI가 출력한 새 `SKILL.md`를 실제 폴더에만 저장하고 업로드를 잊으면,
다음 채팅은 예전 지시로 돌아간다.
반대로 업로드만 하고 실제 폴더에 저장하지 않으면 마스터가 업로드보다 낡는다.
가이드의 원칙대로 마스터 하나를 정하고,
교체할 때는 지우고 올리는 순서를 지켜야 같은 파일의 두 버전이 생기지 않는다.

### `notes.md`는 읽지 않으면 쌓이기만 한다

수정 기록은 루프의 연료지만, 최신이 위로 쌓이는 한 줄 기록은 몇 달이면 길어진다.
가이드는 한 달에 한 번 읽으라고 하는데,
그 결과로 무엇을 하는지는 다음 자동화 후보를 찾는다는 것 외에는 없다.
읽은 뒤 `SKILL.md`나 검증 항목으로 옮긴 기록은 정리하고,
반영되지 않은 기록만 남겨야 노트가 다음 판단에 쓰인다.

## 비평

### 근거로 든 사례가 출처 없이 결론만 옮겨졌다

가이드는 Vercel이 데이터 팀에 전문가 에이전트 체인을 줬다가
직원들 반응이 형편없었고,
범용 AI 하나에 파일 폴더와 평범한 도구 몇 개를 줬더니
내부 점수가 대략 두 배가 됐다고 쓴다.
그러나 이 이야기에는 링크도 출처도 없다.
공개적으로 확인할 수 있는 Vercel의 글은 2025년 12월의
「We removed 80% of our agent's tools」인데,
여기서 text-to-SQL 에이전트 d0는 에이전트 체인이 아니라 전문 도구를 줄이고
파일 시스템과 bash를 준 사례이고 수치는 성공률 80%에서 100%다.
가이드가 인용한 형편없다는 반응과 두 배라는 점수는 이 문서에서 찾지 못했다.

더 곤란한 것은 방향이다.
Vercel은 2026년 10월에도 d0 같은 전문 에이전트를 조율하는
사내 오케스트레이터 V를 소개하는 세션을 열고 있다.
Vercel의 공개 자료가 보여 주는 것은 전문 에이전트를 버렸다는 이야기가 아니라,
에이전트 하나의 도구는 줄이고 여러 에이전트의 조율은 키운다는 이야기에 가깝다.
일마다 에이전트를 만들지 말라는 가이드의 결론은
개인 실무자에게는 맞을 수 있지만,
그 근거로 Vercel을 드는 것은 사례가 말하는 것보다 많이 말하는 셈이다.

Anthropic 엔지니어들이 일별 에이전트를 멈췄다는 서술과
슬라이드 스타일링 스크립트 일화도 같은 문제를 갖는다.
같은 주장을 하는 발표(Barry Zhang과 Mahesh Murag의
「Don't Build Agents, Build Skills Instead」)가 있지만,
가이드는 그것을 가리키지 않는다.
결과는 독자가 주장을 확인할 수 없다는 것이다.
검증할 수 없는 완료 보고를 받아들이지 말라는 가이드가
자기 근거는 검증할 수 없게 적었다.

### 증명 레이어의 이름에 걸맞은 강제 장치가 없다

가이드는 실패할 수 없는 검증은 검증이 아니라고 말한다.
이 원칙은 옳고, 검증 항목의 예시도 구체적이다.
그러나 검증을 실행하는 주체, 결과를 판정하는 주체, 그 결과를 보고하는 주체가
모두 결과물을 만든 같은 AI다.
프롬프트 3이 요구하는 근거와 함께 쓴 한 줄짜리 통과/실패도
실제 실행 로그가 아니라 AI가 쓴 문장이다.

이 구조에서 증명 레이어가 실제로 하는 일은 AI에게 확인할 목록을 주는 것이다.
그것만으로도 결과는 좋아지지만,
가이드가 말하는 증거, 즉 AI의 의견 바깥에 있는 것은
실행 가능한 스크립트와 그 출력이 있을 때만 생긴다.
가이드는 툴박스에 스크립트를 넣으라고 하면서도,
검증 항목 자체를 스크립트로 만들라는 연결은 하지 않는다.
툴박스와 증명을 잇는 이 한 걸음이 빠져서,
가장 중요하다고 말한 레이어가 가장 약한 레이어로 남는다.

### 실전 예제는 성공 하나만 보여 준다

주간 고객 업데이트 예제는 4주차에 숫자를 지어낸 실수가 검증 추가로 사라지고
6주차에는 읽고 보내기만 한다는 이야기로 끝난다.
일 하나, 실수 하나, 수정 하나로 루프가 수렴하는 장면이다.
가이드가 네 직무의 툴박스와 검증 예시를 들었지만
실행 경과를 보여 준 것은 이것뿐이고,
같은 레이어에서 실패가 반복되는 경우는 다음 자동화 후보라고만 정리한다.

루프가 수렴하지 않는 경우는 다루지 않는다.
검증을 늘릴수록 AI가 검증을 통과하는 쪽으로 결과를 맞추는 경우나,
데이터 원천이 바뀌어 툴박스가 통째로 낡는 경우가 그렇다.
쓸수록 좋아진다는 약속은
실패가 레이어 하나의 작은 수정으로 고쳐질 때만 성립하고,
그 조건이 얼마나 자주 성립하는지는 이 예제 하나로 알 수 없다.

## 확인하기

숫자를 지어내는 실수는 AI의 보고가 아니라 스크립트로 막을 수 있다.
아래 스크립트는 결과물에 나온 모든 숫자가 원본 데이터 파일에 있는지를 확인한다.
툴박스의 `files/check-numbers.py`로 두고,
`SKILL.md`의 완료의 정의에서 이 스크립트의 출력 전체를 붙이게 하면 된다.

```python
#!/usr/bin/env python3
"""결과물의 모든 숫자가 원본 데이터 파일에 있는지 확인한다.

사용법: python3 check-numbers.py output.md data.csv [data2.csv ...]
하나라도 없으면 종료 코드 1을 돌려준다.
"""
import re
import sys

# 쉼표 자리 구분과 소수점을 허용하고, 퍼센트 기호는 떼어 낸다.
NUMBER = re.compile(r"\d{1,3}(?:,\d{3})+(?:\.\d+)?|\d+(?:\.\d+)?")


def normalize(token: str) -> str:
    # 1,234.50과 1234.5를 같은 값으로 본다.
    value = float(token.replace(",", ""))
    return f"{value:g}"


def numbers_in(text: str) -> set[str]:
    return {normalize(m) for m in NUMBER.findall(text)}


def main() -> int:
    if len(sys.argv) < 3:
        print(__doc__)
        return 2
    output = open(sys.argv[1], encoding="utf-8").read()
    source = "".join(open(p, encoding="utf-8").read() for p in sys.argv[2:])
    allowed = numbers_in(source)
    missing = sorted(numbers_in(output) - allowed, key=float)
    if missing:
        print("FAIL: 원본에 없는 숫자:", ", ".join(missing))
        return 1
    print("PASS: 결과물의 숫자", len(numbers_in(output)), "개가 모두 원본에 있음")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

이 스크립트는 단순한 대조라서 한계가 분명하다.
원본에 없지만 정당한 숫자,
즉 날짜, 주차, 원본 숫자로 계산한 증감률도 실패로 잡힌다.
쉼표로 구분한 CSV에서는 `1,234`가 두 칸인지 천 단위 숫자인지 구분하지 못하므로,
원본은 쉼표 구분 없이 숫자를 적은 형식으로 뽑아 두는 편이 안전하다.
그런 숫자가 많은 일이라면 허용 목록을 따로 두거나,
계산한 값을 먼저 데이터 파일에 써 두고
결과물은 그 파일만 인용하게 하는 편이 낫다.
후자가 모든 수치가 뽑힌 파일로 추적되어야 한다는
가이드의 원칙에 더 가깝다.

200단어 이하나 금지 단어 없음 같은 항목도 같은 방식으로 스크립트로 옮길 수 있다.
옮길 수 없는 항목, 예를 들어 톤이 단계에 맞는지는
AI의 판정으로 남기되, 판정이라는 사실을 보고에 표시하게 한다.

## 기억할 원칙

### 고친 것은 채팅이 아니라 파일에 남아야 한다

가이드에서 가장 오래 쓸 수 있는 원칙은 루프 자체다.
채팅에서 고친 것은 채팅이 닫히면 사라지고,
파일에서 고친 것은 다음 실행이 물려받는다.
이 원칙은 AI 위임에만 해당하지 않는다.
사람에게 일을 넘길 때도 구두로 고쳐 준 것은 남지 않고 문서로 고친 것만 남는다.
가이드가 매뉴얼을 새 직원에 빗대는 것도 이 때문이다.

### 증거는 만든 쪽이 아닌 곳에서 나와야 한다

결과물을 만든 쪽이 그 결과물이 맞다고 말하는 것은,
그것이 사람이든 AI든 증거가 되지 못한다.
증거는 원본 파일, 실행 로그, 테스트 결과처럼 만든 쪽 바깥에 있어야 한다.
가이드는 이 원칙을 말로는 정확히 세웠지만,
지키게 하는 장치는 스크립트로 만들어 툴박스에 넣을 때에만 생긴다.
