# ub-mode: 동작하게 만들고, 바르게 만들고, 실천으로 남기는 코딩 에이전트 스킬

<https://github.com/unclebob/ub-mode>

## 소개

`ub-mode`는 에이전트가 코드를 새로 쓰거나 고칠 때 따르는 소프트웨어 공학 원칙을
한 파일에 담은 스킬이다.
저장소에는 `README.md`(2,195바이트)와 `SKILL.md`(3,958바이트) 두 파일뿐이다.
README는 이 스킬이 @poteto의 규칙(`poteto-mode`와 `pstack`)의 일부를 바탕으로
줄인 것이고, 결정적(deterministic) 품질 게이트 도구와 짝을 이룬다고 밝힌다.

이 스킬은 Uncle Bob Martin이 만들었다.
그는 2026년 10월 26일 트윗에서 이 스킬을 직접 작성해 꽤 좋은 결과를 얻었고,
자신의 grokbots가 코드를 쓸 때 이 스킬을 쓴다고 소개했다.[^tweet]
저장소는 그 하루 전인 10월 25일에 만들어졌고,
GitHub API로 2026년 10월 29일에 읽은 별은 3,408개, 포크는 168개다.
저장소에는 라이선스 파일이 없다.

호출은 `/ub-mode`이고, 스킬 설명문은 `/ub-mode`를 실행하거나 줄인 원칙(reduced
principles)을 요청할 때 쓴다고 적는다.
본문 첫머리는 변경을 요청받을 때마다 세 단계를 따르라고 한다.
먼저 동작하게 만들고(First Make it Work),
그다음 바르게 만들고(Then Make it Right),
마지막으로 실천 항목을 지킨다(Follow Practice).

## 스킬의 구성

`SKILL.md`는 세 단계 아래에 항목 스무 개 남짓을 두고,
각 항목은 한두 줄에서 네 줄 사이의 불릿으로 끝난다.
원칙의 설명은 거의 없고 행동 지시만 있다.

### 1단계: First Make it Work

여기에는 동작하는 해법에 이르는 태도 여덟 가지와 아키텍처 다섯 가지가 있다.

| 항목                           | 지시의 내용                                                                                                                 |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Laziness Protocol              | 결정은 한 곳에만 두고, 문제를 푸는 가장 작은 수정만 낸다                                                                    |
| Foundational Thinking          | 로직 전에 데이터 형태를 맞추고, 동시 쓰기가 문제가 되면 상태를 공유하지 않는다                                              |
| TDD                            | 코드를 바꾸기 전에 실패하는 테스트를 쓰고, 예상한 이유로 실패하는지 본다                                                    |
| Redesign From First Principles | 새 요구를 옛 설계에 덧붙이지 않고, 처음부터 있었다면 어떻게 만들었을지 생각해 조각으로 낸다                                 |
| Attack the Premise             | 같은 전제를 공유하는 두 수정이 같은 게이트에서 실패하면 그 전제를 한 문장으로 쓰고 불균형을 쥔 행위자를 센 뒤 할당을 없앤다 |
| Subtract Before You Add        | 무엇을 더하기 전에 복잡도를 먼저 덜어 낸다                                                                                  |
| Outcome-Oriented Execution     | 확인할 수 있는 최종 상태를 겨냥하고, 계획하고 되돌릴 수 있다면 중간에 깨져도 된다                                           |
| Build the Lever                | 한눈에 명백하지 않은 일은 그 일을 하는 도구를 만든다. 한 단위를 손으로 한 뒤 도구를 그 단위에 맞춘다                        |

아키텍처 항목은 다섯 개다.
Model the Domain은 불가능해야 할 상태가 구조상 표현되지 않게 하고 용어집을
유지하되, 코드가 이미 명확하고 지역적이면 손대지 않는다.
Boundary Discipline은 데이터를 들어오는 곳에서 검사하고 안쪽에서는 믿으며
비즈니스 로직을 순수 함수에 둔다.
Type System Discipline은 잘못된 값을 쓸 수 없게 만들고,
바깥 데이터를 들어오는 곳에서 한 번만 파싱하고, 컴파일러를 침묵시키지 않는다.
Make Operations Idempotent는 두 번 실행하거나 중간에 죽은 뒤 다시 실행해도 같은
상태에 이르게 한다.
Separate Before Serializing Shared State는 같은 가변 상태가 필요 없으면 각자
따로 갖게 하고, 필요하면 쓰는 쪽을 하나로 하되 이를 구조로 강제한다.

### 2단계: Then Make it Right

이 단계는 원인 수정과 검증, 그리고 세 가지 도구 게이트로 이루어진다.
Fix Root Causes는 재현하고 원인을 고치며,
충돌만 가리는 방어 코드는 수정이 아니라고 한다.
Sequence work into verifiable units는 작은 단위 하나를 끝내고 확인한 뒤
다음으로 간다.
Test Behavior, Not Implementation은 사용자가 코드를 부르는 방식으로 호출해
사용자가 볼 결과를 확인하라고 하고, 모든 함수가 아무것도 돌려주지 않아도 통과할
테스트는 버리라고 한다.
Refactoring은 코드가 하는 일을 고정하고, 구조를 바꾸고,
동작이 바뀌지 않았음을 증명한다.

세 게이트의 지시는 구체적인 수치를 가진다.
Crapper는 함수마다 CRAP 점수를 10 아래로 낮추며,
함수를 쪼개거나 테스트하거나 둘 다 한다.
이때 case 문을 줄일 가치가 있는지는 따져 보라고 한다.
Dryer는 순위 0.8 이상의 중복을 없앤다.
Mutator는 커버되지 않은 부분을 덮고, 살아남은 변이를 죽이고, 죽은 코드를 지운다.

### 3단계: Practice

네 항목이다.
Keep a Log는 취한 모든 행동과 그 이유를 기록하고 끝나면 보고한다.
Guard the Context Window는 메인 스레드를 작게 유지하고 부피가 큰 일은 다른
곳으로 보내 요약만 남긴다.
Worktree Cleanup은 지워도 되는 것을 찾고,
쓰이는 것이 의존하지 않는지 확인한 뒤 디스크를 회수하며,
커밋하지 않은 작업은 결정을 기다린다.
Commit and Push는 자주, 작고 순서 있는 커밋으로 하고, 각 커밋에 이유, 변경 내용,
증명 방법을 적고, 끝에 메인 라인으로 푸시한다.

## 동반 도구

README는 이 스킬이 구조, 복잡도, 중복, 테스트의 철저함을 강제하기 위해 결정적
도구에 기댄다고 적고 네 저장소를 소개한다.

| 도구       | 하는 일                                                                  | 라이선스(GitHub API) |
| ---------- | ------------------------------------------------------------------------ | -------------------- |
| crapper    | 함수별 순환 복잡도, 테스트 커버리지, CRAP 점수를 계산한다[^crapper]      | 0BSD                 |
| dryer      | 구조적 코드 중복을 찾는다[^dryer]                                        | 0BSD                 |
| mutator    | 변이 테스트로 커버되지 않은 코드와 살아남은 변이를 드러낸다[^mutator]    | 0BSD                 |
| uml-viewer | 컴포넌트, 커버리지, CRAP, 변이 점수, 의존 방향을 시각화한다[^uml-viewer] | 표시 없음            |

crapper와 mutator의 저장소 설명문은 Clojure, Java, Go, TypeScript, Rust,
Python을 지원하고 uml-viewer가 읽는 스냅숏 형식으로 결과를 낸다고
적는다.[^crapper][^mutator]
이 문서는 네 도구를 설치하거나 실행하지 못했다.

## 설치와 사용

`SKILL.md`를 에이전트의 skills 디렉터리에 `ub-mode/SKILL.md`로 복사하고
`/ub-mode`를 실행한다.
README는 Grok, Claude, Cursor 세 도구의 skills 디렉터리를 예로 든다.
스킬은 도구 없이도 읽히지만, Crapper, Dryer,
Mutator 항목은 해당 도구가 설치되어 있어야 의미가 있다.

## 분석

### 이 스킬은 원칙을 가르치는 문서가 아니라 점검표다

스킬의 모든 항목은 설명 없이 명령형 불릿이다.
Laziness Protocol의 첫 줄인 결정은 한 곳에만 둔다는 문장은 DRY를 풀어 쓴
것이지만 DRY라는 이름도 이유도 적지 않는다.
이 압축은 독자가 사람이 아니라 에이전트이기 때문에 가능하다.
에이전트는 원칙의 이름만으로 배경 지식을 끌어올 수 있으므로,
이유를 적는 데 쓸 토큰을 지시의 수에 쓴다.
같은 이유로 문장이 짧고 단정적이며, 이 짧음이 컨텍스트 비용을 낮춘다.
이 문서의 해석으로는 이 스킬의 설계 방침은 인간용 설명서를 에이전트용 점검표로
줄이는 데 있다.

### 가장 눈에 띄는 선택은 판단을 숫자 게이트로 바꾼 것이다

세 단계 가운데 2단계만 임계값이 있다.
CRAP 10 미만, 중복 순위 0.8 미만, 변이 생존 0이다.
앞의 두 임계값은 에이전트의 자기 평가를 거치지 않고 도구가 판정한다.
에이전트에게 코드가 깔끔한지 묻는 대신 도구를 돌리게 하는 이 구조는,
같은 모델이 쓰고 같은 모델이 검토하면 맹점이 같다는 문제를 우회한다.
반대로 1단계의 원칙들은 도구가 검사하지 않는다.
Attack the Premise나 Redesign From First Principles를 지켰는지는 에이전트가
스스로 말하는 수밖에 없다.
스킬은 판정 가능한 쪽에는 도구를, 판정할 수 없는 쪽에는 말을 둔 셈이다.

### 1단계의 몇 항목은 일반 원칙이 아니라 특정 실패에 대한 처방이다

Attack the Premise는 같은 전제를 공유하는 두 수정이 같은 게이트에서 실패했을
때만 발동하는 매우 좁은 규칙이다.
Build the Lever는 일을 한 번 손으로 한 뒤 그 단위에 맞춰 도구를 만들라고 하며,
이는 반복 작업에서 에이전트가 같은 일을 계속 손으로 하는 습관을 겨냥한다.
Worktree Cleanup은 디스크 회수까지 적는다.
이런 항목은 책의 목차에서 나오지 않고 에이전트를 오래 부려 본 경험에서 나온다.
저자가 grokbots를 직접 써 보고 정리했다는 트윗의 설명과 맞는다.[^tweet]

## 비평

### 효과를 보여 주는 증거는 저자의 한 문장뿐이다

이 스킬이 좋은 결과를 낸다는 근거는 저자가 꽤 좋은 결과를 얻었다고 쓴 트윗이
전부다.[^tweet]
같은 과제를 이 스킬 없이 돌렸을 때와 비교한 결과,
어느 모델에서 얼마나 달랐는지는 저장소에 없다.
저자의 grokbots와 저자의 코드 취향이 이미 스킬의 원칙과 맞물려 있을 가능성도
배제되지 않는다.
별 3,408개는 관심의 크기이지 효과의 증거가 아니다.

### 임계값의 근거가 없다

CRAP 10과 중복 0.8이 왜 그 값인지는 적혀 있지 않다.
함수를 CRAP 10 아래로 쪼개라는 지시는 함수 수를 늘리고,
쪼갠 함수를 읽는 비용을 키울 수 있다.
스킬은 case 문을 줄일 가치가 있는지 따져 보라는 한 줄로 이 부작용을 인정하지만,
어떤 기준으로 따지는지는 말하지 않는다.
숫자 게이트가 에이전트의 손에 들어가면 코드가 좋아지는 것이 아니라 숫자가
좋아지는 방향으로 움직일 수 있다.
mutator의 살아남은 변이를 죽이는 일도 마찬가지로,
의미 없는 단언을 늘려 점수만 올릴 수 있다.
스킬의 Test Behavior 항목이 모든 함수가 아무것도 돌려주지 않아도 통과할 테스트는
버리라고 하는 것은 이 위험을 아는 대목이지만,
게이트 자체가 이 위험을 막는지는 확인되지 않는다.

### 도구가 있어야 반쪽이 아닌 스킬이 된다

2단계의 세 게이트는 crapper, dryer, mutator가 설치되어 있다고 가정한다.
SKILL.md는 도구를 어디서 받고 어떻게 쓰는지 적지 않고,
도구의 위치는 README에만 있다.
도구가 없으면 에이전트는 이 항목을 건너뛰거나 도구를 흉내 내어 점수를
어림잡을 수 있다.
스킬 파일 하나를 복사해서 쓰라는 설치 안내와,
네 저장소가 필요하다는 의존 사이에 간극이 있다.
dryer의 중복 순위 0.8이 무엇의 비율인지도 스킬에는 없다.

### Commit and Push 항목은 환경에 따라 충돌한다

마지막 항목은 작은 커밋을 자주 하고 끝에 메인 라인으로 푸시하라고 한다.
에이전트에게 푸시를 금지한 저장소나 리뷰를 거쳐야 하는 팀에서는 이 지시가 그
규칙과 정면으로 부딪친다.
이 스킬은 개인이 직접 쓰는 저장소를 전제하며, 이 전제는 스킬에 적혀 있지 않다.

## 인사이트

### 게이트를 도구에 맡기는 구조는 에이전트의 자기 보고를 믿지 않는 설계다

Keep a Log는 취한 모든 행동과 이유를 기록해 끝에 보고하라고 한다.
이 지시와 도구 게이트를 함께 놓으면 스킬이 신뢰하는 것과 의심하는 것이 드러난다.
행동의 이유는 에이전트의 말을 받아들이고, 코드의 상태는 도구의 숫자로 확인한다.
이 구분은 사람이 코드 리뷰에서 하는 일과 같다.
설명은 듣되 테스트 결과와 커버리지 리포트는 직접 본다.
따라서 이 스킬에서 일반화할 수 있는 부분은 CRAP 10이라는 값이 아니라,
에이전트가 쓴 코드를 에이전트가 판정하지 않게 하는 배치다.
이 가설을 뒤집는 관측은 도구 게이트를 켠 에이전트와 끈 에이전트의 결함률이
같은 경우다.

### 스킬은 짧을수록 지켜질 가능성이 높지만 지켜졌는지는 더 알기 어렵다

스킬은 4KB도 안 되는 한 파일이어서 에이전트 컨텍스트에 부담을 주지 않는다.
앞서 서소영의 글이 다룬 스킬 크기 문제와 반대 극단이며,
130개 스킬을 관리하는 조직과 한 파일로 모든 코드 작업을 덮는 개인은 같은 문제를
반대 방향에서 푼다.
다만 항목이 많은 짧은 점검표는 에이전트가 얼마나 지켰는지 판정하기 어렵다.
TDD 항목의 예상한 이유로 실패하는지 본다는 지시는 로그에는 남을 수 있어도 실제로
그랬는지는 로그만으로 증명되지 않는다.
스킬이 늘 켜져 있는 규칙 모음이라면 준수 여부를 재는 별도 점검이 필요하다.
이 문서가 권하는 방법은 같은 작업에 `/ub-mode`를 쓴 경우와 쓰지 않은 경우를 각각
돌려 로그의 항목 이행 횟수와 게이트 통과 횟수를 비교하는 것이다.

### 이 스킬은 코드 품질의 합의를 에이전트의 조작 가능한 값으로 바꾼다

CRAP, 중복, 변이 생존은 오래전부터 사람이 쓰던 지표이고,
사람 팀에서는 임계값을 넘겨도 리뷰어의 판단이 끼어든다.
에이전트에게는 임계값이 곧 종료 조건이 된다.
종료 조건이 숫자이면 에이전트는 숫자를 만족시키는 가장 쉬운 길을 찾는다.
이때 지표는 코드의 질을 재는 눈금에서 에이전트의 목표 함수로 바뀌고,
지표가 목표가 되면 좋은 지표가 아니게 된다는 오래된 경고가 다시 해당된다.
스킬이 Subtract Before You Add와 죽은 코드 삭제를 숫자 게이트와 함께 두는 것은
이 위험을 일부 상쇄한다.
그러나 어느 쪽이 이기는지는 도구와 모델의 조합에 달려 있어서,
이 문서는 이를 확인하지 못했다.
