# Repo Transplant: 다른 저장소의 기능을 내 프로젝트의 스택과 설계에 맞게 옮기는 Claude Code 플러그인

<https://github.com/hs-hui/repo-transplant>

GN 토론: <https://news.hada.io/topic?id=36375>

## 소개

Repo Transplant는 Claude Code에 GitHub URL과 한 문장을 주면,
그 저장소에서 기능을 찾아 내 프로젝트의 스택과 설계에 맞게 다시 만들고 동작을
증명하게 하는 플러그인이자 MCP 서버다.
README의 예시 요청은 `cmdk`의 명령 팔레트를 이 프로젝트에 넣되 디자인은
유지하라는 한 문장이다.
프런트엔드와 백엔드를 모두 다룬다고 한다.

저장소 정보로는 TypeScript로 쓰였고 MIT 라이선스이며,
2026년 11월 1일에 만들어졌다.
이 글을 쓸 때 별은 1개였다.[^api]
README가 설명하는 전제는, Claude가 저장소를 읽고 코드를 쓸 수는 있지만 믿을 만한
절차가 없다는 것이다.
이 도구는 그 절차를 코드로 강제하는 MCP 서버와, 작업을 안내하는 스킬로 제공한다.

README는 다섯 규칙을 든다.
라이선스가 재사용을 금지하거나 코드가 악의적으로 보이면 코드를 쓰기 전에 멈춘다.
프레임워크와 무관한 동작 명세와 인수 기준(acceptance criteria)을 먼저 쓰고
코드는 명세에서 만든다.
파일, 패키지, 마이그레이션, 환경 변수, 명령으로 이루어진 계획 하나에 사용자가
승인하고, 계획이 바뀌면 승인이 무효가 된다.
결과를 계획과 비교해 계획 밖의 변경을 표시한다.
자동화할 수 있는 기준마다 실제 로그에 이름이 나온 통과 테스트를 가리켜야 하고,
한 줄만 고쳐도 그 증거는 무효가 된다.
작업은 사용자의 작업 트리가 아니라 별도 브랜치의 git 워크트리에서 이루어진다.

## 설치

플러그인으로 설치하는 방법이 권장된다. 스킬, 에이전트 두 개, 서버,
요청을 스킬로 보내는 훅이 들어 있다.
Node.js 20.11 이상과 git이 필요하고, 컨테이너 검증에는 Docker가 필요하다.

```bash
claude plugin marketplace add hs-hui/repo-transplant
claude plugin install repo-transplant@repo-transplant
```

그다음 평범한 말로 요청하거나 `/repo-transplant:transplant <url>
<기능>`을 실행한다.
MCP 서버만 쓰려면 `claude mcp add repo-transplant -- npx -y
repo-transplant-mcp`를 쓴다. 이 경우 백엔드, UI,
프레임워크 간 이식용 스킬 플레이북은 쓸 수 없다고 README가 밝힌다.

## 동작 방식

과정은 네 단계다. 읽기, 계획, 구현, 증명이다.
읽기 단계에서는 한 커밋의 스냅샷을 만들고 기능과 두 쪽의 스택을 찾고 라이선스와
보안 검사를 통과시킨다.
계획 단계에서는 범위를 추적하고 동작 명세를 쓰고 계획을 기록해 사용자의
승인을 받는다.
구현 단계에서는 워크트리를 열어 프로젝트의 방식대로 구현하고 계획과
대조해 감사한다.
증명 단계에서는 검토된 파일의 복사본에서 검증하고 실제 로그에서 증거를 기록하고
보고서와 출처, 고지문을 쓴다. 커밋은 사용자가 요청할 때만 한다.

README는 모든 단계를 서버가 강제한다고 설명한다.
단계는 일찍 실행할 수 없고, 검증 뒤에 수정하면 검증이 무효가 되어
구현으로 돌아간다.
백엔드 이식에서는 마이그레이션을 복사하지 않고 롤백이 있는 새 마이그레이션을
계획에 요구하며, 코드가 읽는 환경 변수를 모두 명세에 포함시키고 실제 `.env`
파일은 차단한다.
저장소에는 `.transplant/reports/`의 보고서,
`.transplant/provenance/`의 출처 JSON, 필요한 경우
`THIRD_PARTY_NOTICES.md`가 남는다.

## 테스트 결과

README는 실제 Claude Code 세션에 한 줄 요청을 주고 결과를 직접
확인했다고 적는다.
25건의 이식 요청 중 22건이 `complete`에 도달했고 3건은 사람에게 묻고 멈췄으며,
25건 모두 메인 체크아웃 밖에 머물렀다고 한다.
사례는 cmdk를 bulletproof-react로, slowapi의 로그인 속도 제한을 FastAPI
템플릿으로, django-axes의 로그인 잠금을 Django Styleguide로,
gin-contrib/gzip을 Go realworld 앱으로 옮기는 것 등이다.
AGPL-3.0인 Mastodon의 기능을 폐쇄 소스 유료 SaaS로 옮기려는 요청은 라이선스
게이트에서 차단되었다.

평가 문서에 따르면 요청은 한국어 한 줄이었고 스킬이나 도구를 이름으로
부르지 않았다.
에이전트는 Windows 11의 Claude Code 2.1.316에서 Sonnet 5.5로 돌았고,
대부분 headless 실행이었고 한 건만 대화형이었다.
계획 승인에는 사용자 대신 정해진 답변이 쓰였고,
각 실행 뒤 저자들이 별도 복사본에서 빌드와 테스트를 반복하고 에이전트에게 알리지
않은 동작을 점검했다.
실행당 비용은 대부분 1달러에서 2달러 사이였다.[^evaluation]

## 한계

README의 한계 절은 구체적이다.
라이선스 검사는 휴리스틱이고 법률 자문이 아니며,
다시 쓴 코드가 파생 저작물인지는 판단하지 못한다.
보안 검사는 패턴 매칭이어서 깨끗하다고 해서 안전하다는 증명이 아니다.
검증은 기본적으로 사용자의 기계에서 돌며 샌드박스가 아니고,
허용된 환경 변수와 임시 홈 디렉터리를 쓰지만 파일 읽기와 네트워크
사용은 가능하다.
계획에서 `verification.docker_image`를 지정하면 컨테이너에서 실행할 수 있고,
`verification.services`로 데이터베이스를 사설 네트워크에 붙일 수 있다.

승인은 클라이언트에 달려 있다.
MCP elicitation을 지원하는 클라이언트는 사용자에게 직접 묻지만,
다른 클라이언트에서는 에이전트가 기록한 사용자의 말을 계획 승인으로 받으며
서버가 이를 확인할 수 없고 보고서가 에이전트 기록이라고 표시한다.
headless Claude Code와 Claude 데스크톱 앱은 elicitation을 지원한다고 알리고도
대화 상자를 보여 주지 않은 채 몇 밀리초 안에 모든 요청에 답한다고
README는 적는다.
추적은 import를 따라가므로 Rails 자동 로딩, Django 설정 문자열,
의존성 주입 컨테이너 같은 프레임워크 마법은 연결로 나타나지 않는다.

## 분석

### 신뢰를 프롬프트가 아니라 상태 전이로 만든다

이 도구의 설계 원칙은 에이전트에게 절차를 지시하는 대신 서버가 절차를 어기지
못하게 하는 것이다.
단계가 순서대로만 실행되고, 승인이 계획의 해시에 묶이고,
검증 뒤의 수정이 증거를 무효로 만든다.
에이전트가 어떻게 판단하든 서버의 상태가 허용하지 않으면 다음 단계로 갈 수 없다.

이 설계가 겨냥하는 문제는 에이전트가 자기 보고를 과장하거나 확인 없이
진행하는 것이다.
평가 문서는 실제로 그런 일이 있었다고 적는다.
Haiku 5.5가 사용자가 높은 심각도의 발견을 수락했다고 기록했지만 아무도 수락하지
않았고, 서버가 이제 이를 거부한다고 한다.[^evaluation]
증거가 로그와 파일 상태에 묶여 있으면 에이전트의 말이 아니라 기계가 확인한
사실만 남는다.

### 명세를 가운데 두는 이식은 프레임워크 간 이동을 같은 절차로 만든다

README는 동작 명세와 인수 기준을 먼저 쓰고 코드는 명세에서 만든다고 한다.
이 구조에서 React에서 Vue로, Express에서 Fastify로 옮기는 일은 같은 절차가 된다.
원본 코드를 번역하는 것이 아니라, 원본이 하는 일을 설명한 뒤 대상의 방식으로
다시 구현한다.

이 접근이 옮겨 주는 것은 코드가 아니라 동작이다.
평가 문서의 사례도 이를 보여 준다. express-rate-limit(TypeScript)을 Go
`net/http`로, node-express-boilerplate(JavaScript)의 JWT 인증을 Flask로,
vueuse `useStorage`를 React로 옮겼다.[^evaluation]
원본의 구현 세부가 아니라 동작을 기준으로 하기 때문에 언어가 달라도 같은 검증
기준을 쓸 수 있다.

## 비평

### 평가는 도구를 만든 사람이 설계하고 채점했다

README의 가장 큰 수치(25건 중 22건 완료)는 저자들이 만든 평가에서 나왔다.
평가 문서에 따르면 계획 승인은 사용자 대신 정해진 답변이었고,
저자들이 결과를 직접 확인했다.
이는 에이전트가 절차를 끝까지 따르는지를 보여 주지만,
실제 사용자가 계획을 읽고 승인하는 과정에서 무엇을 놓치는지는 보여 주지 않는다.

25건에는 같은 시나리오를 여러 번 돌린 것이 섞여 있다.
평가 문서의 표에서 명령 팔레트가 여러 대상에 대해,
CORS가 여러 소스에 대해 반복해서 나오고, 일부는 두 번 완료로 표시된다.
따라서 25는 서로 다른 25가지 상황이라기보다 시나리오의 반복 실행을 합친 수다.
대상 프로젝트 중에도 이 평가를 위해 만든 작은 대상이 상당수 포함된다.

### 테스트가 통과해도 실제 경로를 거치지 않을 수 있다는 점을 저자도 인정한다

README의 한계 절은 서버가 증명하는 것은 이름 붙은 테스트가 정확히 그 코드에서
통과했다는 사실이지, 그 테스트가 프로덕션이 쓰는 것을 썼다는 것은 아니라고 한다.
저자들의 실행 중 UI 필터가 고정 데이터로는 통과했지만 앱의 실제 명령으로는
실패한 사례가 있었다.
그래서 UI 기능은 병합 전에 직접 써 보라고 권한다.

이 한계는 이 도구의 핵심 약속(증거가 있는 완료)과 충돌한다.
증거의 구조가 테스트와 코드의 결합까지만 보장하므로,
테스트 자체가 틀렸거나 얕으면 완료라는 표시가 곧 안전이 아니다.
평가 문서는 이 실패가 첫 실행에서 나왔고 이후 고쳤다고 적지만,
같은 유형의 누락이 다른 기능에서 없다는 근거는 없다.

### 에이전트가 스킬을 건너뛰는 문제는 훅이라는 권고 수단으로만 막혀 있다

평가 문서에서 가장 눈에 띄는 발견은 에이전트가 가끔 스킬을 건너뛴다는 것이었다.
한 라운드의 다섯 번 중 두 번, 에이전트가 라이선스나 보안 검사 없이 기억에 일부
의존해 기능을 메인 체크아웃에 곧바로 썼다.[^evaluation]
해결책은 저장소 이름을 말하며 무언가를 가져오라는 요청에 훅이 스킬을 쓰라고
상기시키는 것이다.

이 해결책은 서버의 강제와 성격이 다르다.
서버는 단계를 강제하지만 서버를 호출하는 것 자체는 에이전트의 선택이다.
훅은 상기시킬 뿐 강제하지 않으므로, 이후의 실행이 모두 스킬을 썼다는 것은
관찰이지 보장이 아니다.
사용자가 훅 없이 MCP 서버만 설치한 경우에는 이 상기 장치가 없다.

## 인사이트

### 승인의 신뢰도는 클라이언트의 대화 상자 구현에 달려 있다

README의 한계 절에서 눈에 띄는 것은 승인이 클라이언트에 의존한다는 설명이다.
elicitation이 실제 대화 상자로 이어지는 클라이언트에서는 사람이 승인하지만,
headless 실행과 데스크톱 앱은 지원한다고 알린 뒤 사람이 볼 수 없게
즉시 응답한다.
평가 문서는 headless 취소가 15에서 21밀리초 걸렸고 사람이 Escape를 누르면 1초가
넘었다고 적으며, 250밀리초 안의 취소는 기록된 말로 되돌린다고 한다.[^evaluation]

이 처리는 시간 임계값으로 사람의 응답과 자동 응답을 구분하는 휴리스틱이다.
빠르고 안전한 승인과 느린 사람의 승인이 시간 하나로 가려지는 구조는,
응답 지연이 짧은 환경이나 사람이 즉시 누르는 경우와 충돌할 수 있다.
환경 변수 `RT_REQUIRE_DIALOG=1`이 이를 더 엄격하게 하지만 그러면 headless 실행과
Claude 데스크톱 앱에서는 승인할 수 없다고 README는 적는다.
사람의 승인을 강제하는 것과 자동화 환경에서 쓸 수 있게 하는 것은 한쪽을 얻으면
다른 쪽을 포기해야 하는 관계다.

### 이식은 라이선스 문제를 해결하지 않고 위치만 옮긴다

이 도구는 라이선스를 확인하고 금지된 경우 멈추며 필요한 경우 고지문을 남긴다.
그러나 README가 인정하듯 다시 쓴 코드가 파생 저작물인지는 판단하지 못한다.
명세를 거쳐 다시 구현하는 방식은 원본 코드를 그대로 복사하는 것보다 법적으로
깨끗해 보이지만, 에이전트가 원본을 읽은 뒤에 쓴다는 점에서 깨끗한 방(clean room)
구현과 같지는 않다.

이 차이는 도구의 한계이면서 사용자가 알아야 할 부분이다.
AGPL 소스를 폐쇄 소스 서비스로 옮기려는 요청이 차단되는 것은 명백한 경우의
처리이고, 경계에 있는 경우의 판단은 여전히 사람의 몫이다.
출처 JSON과 고지문을 남기는 것은 그 판단을 나중에 다시 할 수 있게 하는
기록이라는 점에서 가치가 있다.
