# ffmpeg-skill: 코딩 에이전트에게 로컬 FFmpeg 편집 도구 42개와 검증 절차를 주는 스킬

<https://github.com/kajisho5/ffmpeg-skill>

## 소개

ffmpeg-skill은 Claude Code, Cursor, Codex처럼 `SKILL.md`를 읽는 에이전트가 로컬
FFmpeg로 영상과 오디오를 편집하게 만드는 Agent Skill이다.
저자는 kajisho5이고 라이선스는 MIT이다.
저장소는 2026-09-03에 만들어졌고, 이 글을 쓴 2026-10-30에 별 약 4,000개, 포크
316개, 커밋 443개, 버전 2.21.1이다.

구성 요소는 세 가지이다.
첫째는 에이전트가 읽는 `SKILL.md`(216줄)로, 작업 순서와 요청별 도구 표, 보고
형식을 담는다.
둘째는 `scripts/` 아래의 Python 표준 라이브러리 스크립트이다.
`_`로 시작하는 보조 파일 3개를 빼면 45개 중 42개가 도구이고, 각 도구는
`ffmpeg`와 `ffprobe`만 호출한다.
셋째는 도구 이름, 입력 스키마, 필요한 FFmpeg 구성 요소를 기계가 읽을 수 있게
내놓는 계약(contract)과 이를 MCP로 노출하는 서버(`mcp/server.py`)이다.

저자가 정한 작업 순서는 probe, 편집, check, look이다.
먼저 `probe.py`가 길이, 프레임 레이트, 해상도, HDR 여부를 재고, 편집 도구가
파일을 만들고, `check.py`가 플랫폼 규격에 맞는지 판정한다.
화면이 바뀌었으면 마지막에 `look.py`가 만든 컨택트 시트(contact sheet) PNG를
에이전트가 직접 본다.
보고서는 `Look:` 줄에 그 PNG를 적어야 끝난다.

도구는 여섯 묶음이다.

| 묶음           | 도구 수 | 예                                                     |
| -------------- | ------- | ------------------------------------------------------ |
| 분석           | 3       | `probe`, `scenes`, `look`                              |
| 편집           | 24      | `cut`, `join`, `silence`, `fit`, `stabilize`, `redact` |
| 오디오         | 3       | `audio`, `sync`, `loudness`                            |
| 화면           | 4       | `caption`, `overlay`, `graphics`, `color`              |
| 전달           | 4       | `export`, `check`, `proxy`, `report`                   |
| 오케스트레이션 | 4       | `render`, `batch`, `multicam`, `verify`                |

## 설치와 사용

설치는 FFmpeg를 먼저 깔고 `npx ffmpeg-skill`을 실행하는 것이 전부이다.
`--cursor`, `--codex`, `--all`로 대상을 고르고, Claude Code 플러그인으로도
설치할 수 있다.
macOS에서는 Homebrew의 기본 `ffmpeg`에 `subtitles`, `drawtext`, `zscale` 필터가
없어서 `ffmpeg-full`이 필요하다.
이 패키지는 keg-only라서 PATH에 직접 올려야 하지만, 기본 `ffmpeg`가 PATH에
있으면 스킬이 같은 prefix의 `ffmpeg-full`을 알아서 쓴다고 README는 적는다.

```bash
npx ffmpeg-skill            # Claude Code용으로 설치
npx ffmpeg-skill doctor     # ffmpeg 구성 요소 점검
npx ffmpeg-skill contract --json | head -40
```

모든 도구가 같은 공통 플래그를 받는다.
`--dry-run`은 실행할 ffmpeg 명령만 출력하고, `--json`은 결과와 출력 파일의
probe를 구조화해서 돌려준다.
`--plan FILE`은 드라이런을 입력 파일 지문(fingerprint)과 함께 저장해 두었다가
`render.py FILE`로 나중에 실행하게 하고, 그 사이 입력이 바뀌었으면 거부한다.
`--timeout`의 기본값은 1,800초이다.

README가 직접 측정해 둔 한계도 있다.
4 vCPU 서버에서 60분짜리 1080p 파일 전체를 `export.py --preset youtube`로
재인코딩하면 기본 타임아웃에 걸려 1,802초에 중단되고, 아무것도 쓰이지 않는다.
10분 구간은 514초(실시간의 약 1.2배)가 걸렸다.
긴 원본은 `--timeout 0`이나 `--fast`를 써야 한다.

## 분석

### 입력 스키마는 코드에서 만들어지고, 나머지 계약은 손으로 쓴다

저자가 SPEC이라고 부르는 패턴의 핵심은 도구의 `input_schema`를 따로 쓰지 않고
스크립트의 `argparse` 파서에서 뽑는다는 것이다.
`scripts/_contract.py`의 `_capture_parser()`는
`argparse.ArgumentParser.parse_args`를 잠시 바꿔치기하고, 각 스크립트를 import한
뒤 `main()`을 부른다.
`main()`이 `parse_args()`에 닿는 순간 가짜 함수가 예외로 파서 객체를 넘겨주고,
이 객체에서 플래그, 타입, 선택지, 기본값, 상호 배타 그룹을 읽는다.
MCP 서버는 자체 도구 표 없이 이 결과를 그대로 변환하므로, 스크립트에 플래그를
추가하면 CLI와 MCP 정의가 한 번에 바뀐다.

범위는 정확히 입력 스키마까지이다.
`role`, `capabilities`, `outputs`, `output_schema`는 손으로 쓴 `TOOL_META`
표에서 오고, 이 표의 키는 42개이다.
README도 이 구분을 직접 밝힌다.
그래서 이 설계가 막는 것은 플래그 이름과 타입이 어긋나는 종류의
드리프트(drift)이고, 도구가 무엇을 보증하는지에 관한 설명이 코드와 어긋나는
문제는 `tests/test_contract.py`가 CI에서 잡도록 남겨 두었다.

### 에이전트에게 셸도 필터 그래프도 주지 않는다

이 스킬이 에이전트에게 거는 가장 눈에 띄는 제한은 자유 입력의 차단이다.
호출자가 `-vf` 문자열이나 `filter_complex`를 넘길 수 없고, 도구는 자기
`argparse` 플래그만 받는다.
저장소의 `scripts`, `mcp`, `bin`에서 `shell=True`를 검색했을 때 일치하는 줄이
없었고, MCP 서버는 구조화된 인자를 argv 리스트로 바꿔 스크립트를 실행한다.
MCP는 원시 `argv` 형식도 받지만, 그것도 해당 스크립트의 CLI 플래그 목록일 뿐
ffmpeg 명령줄이 아니다.

`SKILL.md`는 여기에 규칙을 하나 더 얹는다.
42개 스크립트가 제공하지 않는 기능이 필요하면 가장 가까운 내장 옵션을 안내하고,
`scripts/*.py` 밖에서 raw ffmpeg 호출을 추측해서 만들지 말라고 한다.
이유는 README의 FAQ에 있다.
`color.py`의 HDR에서 SDR 변환 체인은 색 태그가 틀려도 종료 코드 0으로 끝나
화면이 바랜 파일을 만들기 때문에,
손으로 쓴 ffmpeg 호출의 실패는 조용하다는 설명이다.
이 설계는 에이전트가 할 수 있는 일을 줄이는 대신,
틀렸을 때 알 수 있는 일을 늘린다.

### 상품은 실행이 아니라 거부와 검증이다

도구들이 공통으로 가진 성질은 기본 동작이 거부라는 점이다.
`scripts/_common/runner.py`는 출력 경로가 이미 있으면 `--overwrite` 없이는
`output_exists`로 거부하고, 이 거부는 ffmpeg가 시작되기 전에 일어난다.
실패한 JSON에는 `kind`와 `reason` 코드가 붙어서, 에이전트가 문장을 해석하지 않고
분기할 수 있다.

측정이 되지 않는 상황도 통과로 처리하지 않는다.
`doctor`는 ffmpeg 필터 목록을 읽을 수 없으면 해당 구성 요소를 `missing`이 아니라
`unknown`으로 보고한다.
README에 따르면 FFmpeg 8에서 `-filters` 출력의 플래그 열이 짧아졌을 때, 열 폭에
맞춘 파서가 아무것도 못 찾고 모든 필터를 없는 것으로 보고한 사고(0.9.0)가 이
규칙의 출발점이다.
`SKILL.md`의 보고 형식도 같은 태도이다.
라벨은 `Done:`과 `Failed:` 두 가지이고, 일부만 성공했으면 `Done:` 아래
`Notes:`에 부족분을 적는다.

## 비평

### 헤드라인 숫자는 통과한 항목이 아니라 실행한 프롬프트 수에 가깝다

README의 `Tested on real footage` 표에는 `100 / 100`, `108 / 108`, `90 / 90`
같은 굵은 숫자가 줄지어 있다.
그런데 같은 행의 본문을 읽으면 이 숫자가 한 가지 지표가 아니다.
1.17.0 행의 헤드라인은 `100 / 100`이지만, 본문은 라우팅 95%, 정직한 거부와 실패
22/25, 보고 형식 98/100, 그리고 `--fit-size`가 템플릿 경로에서 도달 불가능했다는
결함을 적고 있다.
분모가 프롬프트 수이고 분자는 실행이 끝난 수에 가까워 보이며, 항목별 결과가
본문에 따로 있다.

평가 방식에도 한계가 있다.
에이전트는 Sonnet이고, 채점은 정규식과 Opus 채점기가 맡으며, 프롬프트 집합과
채점기를 저자가 같이 키웠다.
저자는 이 약점을 숨기지 않고 오히려 많이 적는다.
평가 21(1.18.0)에서는 12개 중 4개가 스크립트를 찾지 못했다고 쓰고, 1.17.2
평가에서도 사용자 자막을 고쳐 쓰는 문제가 네 번째 반복까지 남았다고 쓴다.
그러므로 이 표는 광고 숫자로 읽기보다 저자의 수정 일지로 읽는 편이 맞다.
다만 독립된 제3자 평가는 README에 없고, 실제 Windows 기기에서 전체 코퍼스를 돌린
기록도 없다(이슈 #143이 추적 중이다).

### 도구가 42개인데 찾는 일은 에이전트의 몫이다

MCP의 `tools/list`는 기본으로 12개만 보여 주고, 나머지 30개는 이름을 알아야
`tools/call`로 부를 수 있다.
저자는 이 선택을 컨텍스트 절약으로 설명한다.
그러나 에이전트가 존재를 모르는 도구는 쓰이지 않는다.
평가 21의 결과가 정확히 이 문제이다.
새로 추가한 플래그 다섯 개가 `SKILL.md`에 이름조차 없자 12개 프롬프트 중 8개만
라우팅됐고, 1.18.1이 요청 표에 행을 추가한 뒤 평가 22에서 8개 중 7개가 되었다.

이 구조에서 `SKILL.md`의 요청 표가 사실상 도구 발견의 유일한 경로가 된다.
표는 손으로 쓰고, 도구가 늘수록 길어지며, 에이전트는 매 세션 그 표를 읽는다.
입력 스키마는 코드에서 자동으로 만들어지는데 발견 경로는 수동이라서, 자동화된
쪽과 수동인 쪽의 속도 차이가 곧 라우팅 실패율이 된다.
“42개가 과한가”라는 FAQ의 답은 도구마다 약속하는 검증이 다르다는 논리인데, 그
논리가 맞더라도 이름을 기억해야 하는 비용은 줄지 않는다.

### 마지막 검증은 호출한 에이전트의 눈에 달려 있다

작업 순서의 8단계는 화면이 바뀐 모든 작업 뒤에 `look.py` PNG를 에이전트가
보게 한다.
이 단계가 자막이 얼굴을 가리거나 색이 바랬는지를 잡는 유일한 장치이다.
그런데 README는 이 검사가 이 스킬의 기능이 아니라 호출한 에이전트의 시각이라고
분명히 밝힌다.
얼굴, 제품, 중요한 장면을 감지하는 코드는 저장소에 없고, 크롭 위치는 기본이
중앙이다.

시각 능력이 없는 호출자를 위한 규칙은
`Look: PATH (pixels not inspected; agent has no image view)`라고 적는 것이다.
이것은 정직한 처리이지만, 그 경우 이 스킬의 핵심 약속인 verify-last가 절반만
지켜진다.
기계가 확인하는 항목(길이, 해상도, 라우드니스, 규격)과 사람이나 비전 모델이
확인하는 항목(구도, 가림, 색감)이 보고서에서 구분되기는 하지만, 후자를 강제할
수단은 문서뿐이다.

## 인사이트

### 스키마 드리프트를 없애면 남는 제약은 문서 쪽에서 드러난다

입력 스키마를 파서에서 파생시킨 효과는 이중이다.
플래그와 MCP 정의가 어긋나는 오류가 구조적으로 사라진다.
동시에, 에이전트 성능을 좌우하는 변수가 스키마가 아니라 에이전트가 읽는 자연어
라우팅 표라는 사실이 평가 결과에서 선명해진다.
평가 21에서 정답은 맞았지만 스크립트를 못 찾은 사례가 4건이나 된 것은 스키마가
맞아도 발견이 안 되면 소용없다는 증거이다.

이 구조는 API 문서 생성 도구가 겪은 경로와 같다.
OpenAPI 스키마를 코드에서 뽑으면 필드 정의는 정확해지지만, 어떤 엔드포인트를
언제 쓰는지의 서술은 여전히 사람이 쓰므로 그쪽이 오래된다.
이 스킬에서 같은 일이 일어나지 않게 하려면 요청 표를 계약의 `role`과 같은
방식으로 파생시키거나, 적어도 새 플래그가 표에 없으면 CI가 실패하게 만드는
테스트가 필요하다.
저장소가 이미 문서와 코드의 일치를 테스트로 강제하는 문화를 가졌으므로, 다음
단계는 그 테스트를 라우팅 표까지 넓히는 것이다.

### 거부 가능성은 에이전트용 도구의 설계 항목이다

`--plan`은 입력의 크기와 앞뒤 8MiB의 sha256을 지문으로 저장하고, 실행 시점에
입력이 바뀌었으면 거부한다.
계획과 실행을 나누고 그 사이의 변경을 감지하는 구조는 Terraform의 `plan`과
`apply`, 그리고 데이터베이스 마이그레이션 도구의 dry-run과 같은 계열이다.
사람이 쓰는 도구에서 이런 장치는 선택 사항이지만, 에이전트가 쓰는 도구에서는
필수에 가깝다.
에이전트는 방금 본 상태가 아직 유효하다고 가정하고 긴 작업을 이어 가는 경향이
있기 때문이다.

또 하나의 이점은 실패가 구조화되어 있다는 점이다.
`kind`와 `reason` 코드는 사람이 읽는 오류 문장을 파싱하지 않고 재시도 여부를
정하게 해 준다.
이 방식을 따르는 도구는 성공했다는 말보다 정확히 무엇을 확인했는지를 먼저
돌려주게 된다.
에이전트용 도구를 평가할 때 성공률보다 먼저 볼 항목은 거짓 성공의 수인데, 저자는
이 수를 모든 평가 행에 별도로 적는다(대부분 0).

### 도구 수를 정하는 문제는 컨텍스트 예산 문제이고, 이 스킬은 그것을 두 층으로 풀었다

12개를 기본으로 노출하고 30개를 숨기는 구조는 도구 수가 늘어날 때 모든 에이전트
스킬이 맞닥뜨릴 선택이다.
전부 보여 주면 스키마 자체가 컨텍스트를 먹고, 숨기면 발견이 느려진다.
이 저장소는 `SKILL.md`를 두 층으로 나눠 상시 읽는 파일에는 작업 순서와 요청 표만
두고 긴 설명은 `references/`로 보냈다.
README는 평가에서 에이전트 한 번 실행에 약 72,000 토큰이 들고 그중 약 64,000이
호스트 자체의 고정 비용이라고 적는다.
스킬이 줄일 수 있는 몫은 그 바깥의 일부이고, 그래서 도구를 몇 개 보여 줄지보다
어떤 12개를 고르는지가 중요해진다.

채택 측면에서는 저자 한 명이 만든 열 개가 넘는 저장소 생태계라는 점도
따져야 한다.
이 저장소는 다른 저장소를 호출하지 않고 다른 저장소가 이 저장소의 계약을 읽는,
한 방향 의존으로 설계되어 있다.
2.x에서는 도구 이름과 CLI 인자, JSON 키, 종료 코드를 유지한다고 약속하고, 이를
인자 이름 스냅샷 테스트로 강제한다.
반면 3.0은 Python 3.9와 FFmpeg 5.x를 버리고, 2.0은 `--crf`를 `--quality`로
바꾸고 기존 출력 파일을 거부하도록 바꿨다.
두 달 만에 2.21.1에 이르렀으므로 의존하려면 README의 권고대로 태그나 npm 버전을
고정하는 편이 안전하다.
