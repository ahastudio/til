# Anime Series Maker: 캐릭터 시트 두 장과 한 줄 줄거리로 애니 에피소드를 연재하는 스킬

<https://github.com/Mayzmei/anime-series-maker>

## 소개

Anime Series Maker는 Claude Code와 Codex 같은 에이전트에 넣어 쓰는
Agent Skill이다.
README는 캐릭터 시트 두 장과 한 줄짜리 줄거리를 완성된 애니메이션 에피소드로
바꾸고, 같은 출연진으로 다음 편을 이어 만드는 워크플로라고 소개한다.
훅 기획, 컷별 대본, 목소리가 들어간 클립 생성, 클립 검수, 편집,
Instagram용 커버와 캡션까지 에이전트가 맡는다.

영상 생성은 Renoise라는 서비스의 MCP 서버로 수행한다.
`SKILL.md`의 설명은 Seedance 계열 영상 모델을 Renoise MCP로 쓴다고 적는다.
라이선스는 MIT이고, 저장소는 2026년 10월 26일에 만들어졌다.
GitHub API로 읽은 시점의 별은 100개, 포크는 12개, 주 언어는 Python이다.

README 첫머리에는 작성자가 2주 동안 고정 출연진으로 Instagram에 애니메이션
에피소드 40편을 올렸고, 상위 세 편이 조회수 651K, 546K,
346K를 기록했다고 적혀 있다.
저장소는 그 과정 전체를 하나의 스킬로 묶었고,
크레딧을 날린 실수도 모두 담았다고 한다.
이 수치는 작성자의 자기 보고이며, 이 문서는 검증하지 않았다.

## 동작 방식

### 전체 파이프라인

`SKILL.md`가 정의한 흐름은 열한 단계다.
0단계는 Renoise MCP, ffmpeg, Python 환경 점검이다.
1단계는 시리즈당 한 번 만드는 series bible이고, 2단계는 훅, 3단계는 대본이다.
4단계는 프롬프트 조립과 검증, 5단계는 비용 견적과 승인과 첫 클립 생성이다.
6단계는 클립 검수, 7단계는 편집, 8단계는 커버, 9단계는 캡션, 10단계는 기록이다.

작업 폴더는 사용자가 정하며 기본값은 `./my-series/`다.
시리즈 전체의 설정은 `series.json`에, 에피소드 기록은 `episodes.json`에,
편마다 대본은 `episode.json`에 둔다.
조립한 프롬프트는 `prompts/clip01.txt`처럼,
내려받은 결과는 `clips/clip01.mp4`처럼 저장한다.

### series bible: 일관성을 파일로 고정한다

`series.json`에는 출연진, 화풍, 목소리 설정, 배경, 반복 개그가 들어간다.
README는 이 파일 덕분에 30화가 1화와 같은 모습이 된다고 설명한다.
`SKILL.md`는 각 캐릭터의 `look` 필드에 머리 길이·색·가르마, 눈, 교복 요소, 신발,
소품까지 눈에 보이는 디자인을 모두 적으라고 요구한다.
모델이 클립마다 이 필드를 다시 읽으므로 모호하게 적으면 모습이
흔들린다는 이유다.
시트가 없으면 먼저 이미지 모델로 시트를 만들고,
시트가 일관성에 가장 큰 영향을 준다고 적는다.

### 훅을 먼저 정한다

대본보다 전제(premise)를 먼저 정한다.
에이전트는 한 줄짜리 전제를 세 개 내놓고 하나를 추천한다.
`references/hooks.md`에는 작성자의 Instagram 조회수 순위가 표로 있다.
1위가 651K를 얻은 “3초 만에 실패하는 속임수”, 2위가 546K와 187K의 “변신”,
3위가 346K의 “같은 대사를 세 번 반복하며 악화시키기”다.
그 아래로 “원하지만 인정하지 못함”, “구출”, “작은 규칙이나 의식”이 이어진다.
같은 문서는 14~30초짜리 단일 개그 에피소드가 60~100초짜리 줄거리 에피소드를 거의
항상 이긴다고 적는다.

### 프롬프트를 스크립트로 조립하고 검증한다

`scripts/build_prompt.py`는 `series.json`과 `episode.json`으로 클립별
프롬프트를 조립한다.
`references/prompt-framework.md`가 설명하는 순서는 오프닝 지시, 참조 시트 매핑,
캐릭터 일관성, 화풍, 목소리와 오디오, 배경, 초점, 표정 변화, 컷 목록,
마지막 장면, 텍스트 금지 문구의 열한 블록이다.
컷 목록은 `[0s – 3s] SHOT 1` 형식으로 동작, 대사, 효과음,
카메라를 컷마다 적는다.

검증 코드는 직접 읽어 확인했다.
시트 ID가 `material:<숫자>` 꼴이 아니면 실패한다.
`look`이 120자보다 짧으면 실패한다.
클립 길이가 1초 미만이거나 `max_clip_seconds`(기본 15초)를 넘으면 실패한다.
컷에 `action`, `sfx`, `camera`, `dialogue` 중 하나가 없거나,
컷 시간이 앞 컷의 끝과 이어지지 않거나,
마지막 컷의 끝이 클립 길이와 다르면 실패한다.
완성된 프롬프트가 1,500자보다 짧거나 `TODO`, `TBD`,
`{{ }}` 같은 자리표시자가 남아 있어도 실패한다.
실패하면 파일을 쓰지 않고 종료 코드 1로 끝난다.

### 비용 게이트와 첫 클립 확인

`SKILL.md`는 생성 전에 `estimate_cost`로 클립 수, 총 초, 크레딧,
잔액을 보여 주고 사용자의 명시적인 승인을 채팅에서 받으라고 한다.
승인 뒤에는 클립 1개만 먼저 만들어 보여 주고,
캐릭터·목소리·화풍이 맞는지 물은 다음에야 나머지를 한 번에 제출한다.
제출 때는 `ep07-clip02` 같은 `idempotencyKey`를 붙인다.
`build_prompt.py`는 그 키와 클립당 참조 시트 목록을 담은 `tasks.json`도
함께 만든다.

### 검수와 편집

클립마다 캐릭터가 시트와 같은지, 자막이나 말풍선이 구워 넣어지지 않았는지,
목소리의 언어와 성별이 맞는지, 이야기 논리가 서는지,
화풍이 2D로 유지됐는지 확인한다.
실패한 클립은 일부만 이어 붙이지 않고 통째로 다시 만든다.

`scripts/assemble.py`는 클립의 fps, 픽셀 형식, 색 범위,
SAR을 맞추고 `libx264`로 한 번만 인코딩한다.
README와 스크립트 머리말은 `-c copy`로 이으면 Instagram이 구간을
떨어뜨린다고 적는다.
출력은 1080p, 라우드니스는 −14 LUFS이며,
편집점마다 앞뒤 프레임을 모은 `*_joins.jpg`를 만든다.

## 설치와 사용

```bash
git clone https://github.com/Mayzmei/anime-series-maker.git
cp -R anime-series-maker/skills/anime-series-maker <에이전트의 skills 디렉터리>/
brew install ffmpeg
python3 -m pip install pillow
```

위는 README가 안내하는 설치 순서이며, 복사 위치는 에이전트마다 다르다.
Claude Code와 Codex는 각자의 skills 디렉터리에 복사하고,
다른 에이전트는 `skills/anime-series-maker` 폴더나 그 zip을 Skills
페이지에서 가져온다.
Pillow는 커버 검사에만 필요하다.

Renoise 계정이 따로 필요하다.
README는 브라우저 로그인이라 API 키를 붙여 넣을 필요가 없다고 적고,
에이전트별 연결 방법을 표로 준다.
Codex는 `codex mcp add renoise --url https://renoise.ai/api/public/mcp`로
연결하고, 다른 MCP 클라이언트도 같은 URL을 원격 서버로 추가한다.
사용은 평문으로 한다.
README의 예시는 캐릭터 설명과 목소리 언어, 화풍을 한 문장으로 말하고,
다음 편은 “고양이로 변하는 이야기” 정도로 요청하는 것이다.

## 저장소 구조

`skills/anime-series-maker/` 아래에 워크플로 본문 `SKILL.md`, 참조 문서 네 개,
예시 JSON 두 개, 스크립트 세 개가 있다.
참조 문서는 프롬프트 구조, 화풍 프리셋, 훅 공식, 함정 목록이다.
예시는 `templates/series.json`과 `templates/episode.json`이고,
스크립트는 `build_prompt.py`, `assemble.py`, `cover_check.py`다.
README는 영어 판과 중국어 판이 있다.

## 분석

### 에이전트가 운영하는 제작 파이프라인이다

이 스킬의 핵심은 모델 호출이 아니라 호출 앞뒤의 규율이다.
`SKILL.md`는 에이전트가 무엇을 언제 멈추고 사용자에게 물어야 하는지를
단계마다 정해 둔다.
견적 뒤에는 반드시 승인을 기다리고, 대본은 표로 보여 주고 승인을 받고,
편집본은 커버를 만들기 전에 보여 준다.
이 문서의 해석으로는 이것이 하네스 설계에 가깝다.
`agentic-coding/harness-engineering-seven-jobs.md`가 다룬 틀로 읽으면 계약(대본
JSON), 센서(검수 체크리스트와 `analyze_media`),
권한 게이트(비용 승인)가 모두 들어 있다.

### 일관성을 프롬프트가 아니라 데이터에 맡긴다

캐릭터가 흔들리는 문제를 이 저장소는 두 겹으로 다룬다.
하나는 모든 클립에 등장 캐릭터의 시트를 모두 첨부하는 것이고,
다른 하나는 `look` 텍스트를 매 클립 프롬프트에 다시 쓰는 것이다.
`pitfalls.md`는 시트가 하나 빠지거나 `look`이 모호할 때 3번째 클립쯤에서 머리가
짧아지고 옷이 바뀐다고 적는다.
일관성을 모델의 기억이 아니라 파일과 조립 스크립트에 둔 점이 재사용
가능한 설계다.

### 경험칙이 조건문과 문서로 굳어 있다

`pitfalls.md`의 표는 증상, 원인, 처방의 세 열로 되어 있고 모든 행이 한 번
크레딧을 잃은 실수에서 나왔다고 한다.
그 가운데 일부는 코드가 되었다.
`-c copy` 금지는 `assemble.py`의 단일 인코딩이 되었고,
빈 프롬프트 일괄 제출 사고는 `build_prompt.py`의 검증과 종료 코드가 되었다.
`SKILL.md`도 방금 만들고 검증한 파일이 아니면 `create_tasks`에 넘기지
말라고 쓴다.
지침과 기계적 검사를 쌍으로 둔 구조다.

## 비평

### 상위 조회수는 한 계정의 관측이며 훅 공식은 그 위에 서 있다

`hooks.md`의 순위표는 조회수 표본이 작성자의 40편, 한 시리즈, 한 계정,
두 주라는 점에서 일반 공식이라 부르기 어렵다.
1위 651K 하나가 순위를 이끌고, 같은 공식이 다른 출연진과 다른 계정에서도
통하는지는 저장소 안에서 확인할 수 없다.
표의 마지막 줄에 있는 “짧은 단일 개그가 긴 이야기를 거의 항상 이긴다”는 문장도
같은 계정의 비교다.
게다가 알고리즘 노출, 업로드 시점, 팔로워 수 같은 변수가 조회수에 섞여 있다.
이 구조는 스킬이 에피소드를 기록하고 조회수를 입력받아 다음 전제를 순위화한다는
`episodes.json` 설계로 부분적으로 보완된다.
그러나 그 보완도 사용자 한 명의 소표본이라는 한계를 그대로 가진다.

### 품질 검수는 에이전트의 눈에 의존한다

`build_prompt.py`는 형식 검증을 코드로 하지만, 검수 단계는 체크리스트다.
캐릭터가 시트와 같은가, 목소리 성별이 맞는가 같은 항목은 `analyze_media`와 네
곳의 프레임 캡처를 에이전트가 보고 판단한다.
모델이 만든 결과를 모델이 확인하는 구조이므로,
틀린 판정이 나와도 이 저장소에는 그것을 잡는 장치가 없다.
`SKILL.md`가 클립 1을 사용자에게 보이고,
편집본도 커버 전에 보이라고 한 것은 사람 확인을 최종 센서로 둔 설계다.
그러므로 일관성 검수가 자동이라는 인상은 정확하지 않다.

### 비용은 실패할 때마다 선형으로 쌓이고 상한이 없다

실패한 클립은 통째로 다시 만들며, `SKILL.md`는 재시도 비용을 사용자에게 알린 뒤
다시 제출하라고 한다.
하지만 재시도 횟수의 상한이나 에피소드당 예산 상한은 코드에도 문서에도 없다.
`pitfalls.md`는 실행 중인 작업을 취소할 수 없다고 적는다.
견적과 승인은 최초 계획 비용에만 걸리고, 재시도는 건별 승인에 기댄다.
클립 수가 늘고 검수가 까다로워질수록 크레딧이 어디서 새는지 사용자가 직접
챙겨야 한다.

### 외부 서비스에 묶여 있고 저작권 위험은 문장으로만 관리한다

영상 생성은 전부 Renoise에 의존한다.
검증과 편집 스크립트는 독립적이지만, 생성 단계와 모델 선택 규칙은 Renoise MCP의
도구 이름(`get_account`, `list_models`, `create_tasks` 등)에 묶여 있다.
이 문서는 Renoise 쪽을 열어 확인하지 않았고,
요금과 모델 목록은 서비스의 현재 상태에 따라 달라질 수 있다.

저작권은 README가 사용할 권리가 있는 캐릭터만 쓰라고 안내하고 프롬프트에
프랜차이즈 이름을 넣지 말라고 한다.
그러나 제목에 “fan anime”과 “同人动画”를 트리거로 두고,
외형만 묘사하는 방식은 심의를 통과하기 위한 우회로도 읽힌다.
`pitfalls.md`가 이름을 넣으면 거절된다는 이유로 외형 묘사를 권한다는 점도 이
읽기를 뒷받침한다.
규칙은 문서의 문장이고 코드가 확인하는 항목은 아니다.

## 인사이트

### 연재물에서 값을 갖는 것은 한 편의 품질이 아니라 편 사이의 일관성이다

생성형 영상은 한 편만 만들 때는 모델 성능이 거의 전부이지만,
연재물이 되면 재현성이 문제가 된다.
이 저장소는 그 문제를 시트, `look` 필드,
매 클립 재서술이라는 데이터 구조로 풀었다.
이 문서의 추론으로는 같은 설계가 영상 밖에도 옮겨 갈 수 있다.
연재 만화, 브랜드 캐릭터, 시리즈 사진처럼 시간에 걸쳐 같은 대상이 나와야 하는
모든 생성 작업은 설정 파일을 단일 진실 원천으로 두고 프롬프트를 파생 산출물로
취급하는 편이 안전하다.
시험해 볼 방법은 `series.json`을 바꾸지 않은 채 열 편을 만들어 `look` 항목별
이탈 횟수를 세어 보는 것이다.

### 이 방식에서 병목은 생성 비용에서 판단의 비용으로 옮겨 간다

클립 하나는 15초이고 한 편은 클립 한두 개에서 여섯 개다.
생성이 쉬워지면 대본 승인, 첫 클립 확인, 클립 검수, 편집본 확인,
커버 확인에 드는 사람의 시간이 단위 비용을 정한다.
작성자는 2주에 40편을 만들었다고 하니 하루 세 편 가까이이고,
이 속도에서는 매 편의 사람 확인이 반복 노동이 된다.
그렇다면 사람이 반복 확인하는 항목 가운데 기계가 판정할 수 있는 것부터 코드로
옮기는 것이 다음 단계다.
예를 들어 자막이 구워 넣어졌는지는 프레임에서 문자 인식으로 대략
걸러 볼 수 있다.
반대로 목소리 성별과 이야기 논리는 사람이 계속 봐야 할 가능성이 크다.
이 구분은 이 문서의 추측이며, 실제로 어느 항목에서 재시도가 가장 자주 나는지
기록을 모아야 판단할 수 있다.

### 조회수로 전제를 순위화하는 루프는 취향을 데이터로 바꾸면서 같은 것만 반복하게 만든다

`hooks.md`는 조회수가 높았던 하위 시리즈를 반복하라고 권하고,
다음 전제를 실제 조회수로 순위화하라고 한다.
이는 성과가 확인된 공식에 집중하는 착취 전략이다.
단기적으로는 합리적이지만, 같은 공식을 반복할수록 시청자가 익숙해져 한계 효과가
떨어질 수 있다.
탐색과 착취의 균형을 설계에 넣지 않은 점이 이 루프의 약점이다.
다만 이는 가설이다.
이 가설을 뒤집는 관측은 같은 공식을 연속 투입한 에피소드의 조회수가 줄지 않고
유지되는 경우이고, 확인하려면 순위표 갱신 이력과 업로드 순서를 모은
기록이 필요하다.
