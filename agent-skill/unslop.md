# unslop: 바이브 코딩이 만든 AI 티 나는 UI를 디자이너의 교정 순서로 고치게 하는 스킬

<https://github.com/heydamir/unslop>

## 소개

unslop은 Claude Code, Codex, Google Antigravity에서 쓰는 스킬이다.
저장소 설명은 이 스킬을 “바이브 코딩으로 만든, AI처럼 보이는 UI를 고유한 성격을
가진 인터페이스로 바꾸는 Claude 스킬”이라고 소개한다.
만든 사람은 Damir Sokolovsky(Twitter 계정 @heydamir)이고, README는 그가
Twitter에서 “Unslopping” 연재를 시작했다고 밝힌다.
2026년 10월 29일에 저장소가 만들어졌고 마지막 푸시는 11월 8일이다.
이 문서를 쓴 시점에 별은 14,374개, 포크는 798개이며 라이선스는 CC BY 4.0이다.

README가 말하는 동작은 이렇다.
먼저 보라색 그라데이션, 빛 번짐(glow), 이모지 라벨, 소리치는 문구, 들쭉날쭉한
여백 같은 “슬롭(slop)”을 찾아낸다.
그다음 제품 자체에서 디자인 방향을 정하고, 디자이너가 빨간 펜으로 교정하듯
화면을 단계별로 고친다.
Next.js, React, Vue, Svelte, Tailwind, 순수 HTML과 CSS에서 쓸 수 있고, 코드가
없고 링크만 있는 라이브 사이트도 다룬다고 한다.

### 구성

| 경로                        | 내용                                                                          |
| --------------------------- | ----------------------------------------------------------------------------- |
| `skills/unslop/SKILL.md`    | 약 31KB의 본문. 실행 순서, 아홉 단계, 점검표                                  |
| `skills/unslop/references/` | `signs.md`(슬롭 목록), `tokens.md`(값), `visuals.md`, `effects.md`, `refs.md` |
| `skills/unslop/scripts/`    | `snapshot.mjs`(라이브 사이트 저장), `story.mjs`(영상 렌더)                    |
| `examples/`                 | 바이브 코딩 화면 둘(`dashboard.html`, `hero.html`)                            |
| `test/`                     | 두 스크립트의 테스트                                                          |

설치는 스킬 폴더를 `~/.claude/skills/`나 프로젝트의 `.claude/skills/`에 복사하는
것이다.
라이브 사이트 저장과 영상 만들기에는 Playwright와 Chromium이, 영상에는 ffmpeg도
필요하다.
사용은 `/unslop this dashboard`처럼 호출하거나 일상 문장으로 요청하는 것이다.

### 실행 순서

`SKILL.md`가 정한 순서는 일곱 단계다.
화면을 보고(가능하면 렌더해 스크린샷을 본다), 슬롭을 목록으로 만들고, 얼마나
고칠지 정하고, 방향을 다섯 줄로 쓴 뒤 사용자 답을 기다리고, 아홉 단계로 고치고,
점검표로 확인하고, 보고한다.
고칠 정도는 세 가지로 나뉜다. 슬롭이 많으면 전체 과정을, 약간이면 목록에 나온
것만 고치는 다듬기 모드를, 없으면 “없다”고 말하고 작은 개선 두세 가지만
제안한다.

방향은 다섯 줄이다.

| 항목      | 내용                                                                       |
| --------- | -------------------------------------------------------------------------- |
| Product   | 무엇을 누구에게 해 주는지 한 문장                                          |
| Character | 구체적인 단어 두세 개. clean, modern, sleek, minimal, premium은 쓸 수 없다 |
| World     | 제품이 속한 장소나 재료. 중립색의 색조, 강조색, 시각 자료를 정한다         |
| Moments   | 색과 질감을 몰아줄 한두 군데                                               |
| Signature | 이 제품만 가질 작은 디테일 하나                                            |

아홉 단계는 간격, 색, 아이콘, 문구, 서체, 레이아웃, 디테일, 시각 자료, 모션
순서다.
간격이 먼저인 이유는 리듬이 맞아야 나머지가 달라 보이기 때문이고, 문구가 서체와
레이아웃보다 앞서는 이유는 제목의 길이가 크기와 위치를 정하기 때문이라고 본문이
설명한다.
시각 자료와 모션은 화면이 그것들 없이도 동작한 뒤에 맞춘다.

### 단계별 규칙의 예

- 간격은 4px 격자 위에 둔다. 같은 것은 같은 크기로 하고, 그룹 안 간격은 그룹
  사이보다 작게 한다.
- 색은 하나의 중립 램프를 제품의 세계 쪽으로 약하게 물들여 쓰고, 강조색은 하나를
  드물게 쓴다. 색조 그라데이션, 그라데이션 글자, 색이 있는 빛 번짐은 없앤다.
- 이모지는 한 세트의 선 아이콘으로 바꾼다. 크기는 16 또는 18px, 선 굵기는 1.5로
  통일한다.
- 문구는 느낌표와 “Welcome back, Damir! 👋” 같은 인사 제목을 없애고, 변화량에는
  비교 대상을 붙인다(`+12% vs last month`). 확인할 수 없는 문구(`Loved by
  10,000+ teams`)는 사용자에게 사실인지 묻고, 아니면 지운다.
- 서체는 400과 500 두 굵기를 중심으로 하고, 라벨은 대문자 넓은 자간 대신 문장형
  대소문자로 쓰며, 숫자는 `tabular-nums`로 한 형식을 쓴다.
- 앱과 대시보드의 배경과 표면은 회색에 가깝게 유지한다. 주황, 갈색, 파랑,
  초록으로 읽히는 배경은 “너무 나간 것”이라고 적는다. 세계의 색은 강조색, 차트,
  중심 장면에만 쓴다.
- 랜딩 페이지는 한 장의 장면 이미지를 가장 강한 히어로로 꼽는다. 이미지 생성
  도구가 있으면 장면을 만들고, 없으면 제품 미리보기를 코드로 만들고 프롬프트를
  적어 빈 자리를 남긴다.
- 모션은 이유 없이 반복되는 것(`animate-pulse` 등)과 `transition-all`을 없애고,
  한 가지 이징 곡선과 몇 개의 지속 시간만 쓴다.

### 하지 말 것과 영상

금지 목록은 제품 이름을 바꾸지 않기, 제품이 무엇인지 바꾸지 않기, 없앤 장식을 새
장식으로 채우지 않기(유리, 질감, 네온, 벤토 격자로 유행을 바꾸는 것 포함),
기능과 주장과 데이터를 지어내지 않기, 모든 제품에 같은 모양을 쓰지 않기다.

선택 기능인 스토리 영상은 화면이 스스로를 고치는 과정을 보여 주는 10초 안팎의
정사각 영상이다.
한 페이지에서 CSS 값만 바꿔 간격, 색, 모서리가 제자리에서 변하게 하고, 슬롭에는
빨간 선택 상자와 치수선을 그린다.
`SKILL.md`는 이 영상이 화제가 되었다고 적는데, 이는 저자의 서술이며 이 문서는
확인하지 못했다.
모든 영상에는 “unslop by @heydamir” 표기가 들어가야 한다.

README 끝에는 “Hire the unslopper”가 있다. 디자이너가 대신 해 주기를 바라면 핵심
화면 하나를 3일 안에 사용자의 스택으로 고쳐 준다는 안내이고, 저자의 사이트로
연결된다.
라이선스는 상업적 사용을 포함해 자유롭게 쓰되 저자를 밝히고 이 저장소로 링크를
걸 것을 요구한다.

## 분석

### 이 스킬이 담은 것은 스타일이 아니라 교정의 순서다

비슷한 목적의 스킬은 이 저장소에도 여럿 있다. `agent-skill/impeccable.md`,
`agent-skill/hallmark.md`, `agent-skill/frontend-design.md`가 그것이다.
unslop을 구별하는 것은 금지 목록의 내용보다 작업 순서를 고정한 점이다.
간격에서 시작해 문구를 서체보다 앞에 두고 시각 자료와 모션을 마지막에 두며, 단계
하나를 화면 전체에 끝낸 뒤 다음으로 넘어가라고 한다.
이 순서에는 이유가 적혀 있다. 간격이 맞아야 나머지가 다르게 읽히고, 제목 길이가
서체 크기를 정한다는 것이다.
이유가 적힌 순서는 에이전트가 단계를 건너뛰고 한꺼번에 그럴듯하게 만드는 경향을
막는 장치로 읽힌다. 이는 이 문서의 해석이다.

### 방향을 먼저 쓰고 멈추게 한다

`SKILL.md`는 방향 다섯 줄을 쓴 뒤 사용자에게 보여 주고 답을 기다리라고 하며,
사용자가 “그냥 해라”라고 한 경우에만 건너뛴다.
방향을 나중에 바꾸면 모든 단계를 다시 해야 하기 때문이다.
또 “깨끗하지만 어느 제품에도 어울리는 화면은 다음 템플릿”이라고 경계하고, 마지막
점검에 제품 이름을 다른 제품으로 바꿔도 화면이 맞으면 더 밀어붙이라는 항목을
둔다.
슬롭을 지우는 일을 절반으로 보고, 나머지 절반을 “이 제품만 가질 수 있는
화면”으로 정의한 것이다.

### 규칙은 수치와 비교 대상으로 쓰여 있다

간격은 4의 배수이고, 이모지 대신 한 세트의 아이콘을 쓰며, 바깥 반경에서 패딩을
뺀 값을 안쪽 반경으로 쓰고, 강조색 위 글자는 4.5 대 1 대비를 지킨다.
“깔끔하게”라는 말 대신 확인할 수 있는 값을 주었기 때문에 결과를 점검표로 다시 볼
수 있다.
`references/tokens.md`는 이 값을 시작점이라고 부르며, 프로젝트에 이미 좋은
체계가 있으면 값은 그대로 두고 쓰임만 고치라고 한다.

## 비평

### 스킬이 나아졌다는 증거는 저자가 고른 예시뿐이다

저장소가 보여 주는 근거는 저자 본인이 만든 예시 화면 둘과 전후 이미지, 그리고
화제가 되었다는 영상이다.
같은 입력을 스킬 없이 고친 결과와 나란히 놓는 비교, 여러 모델과 여러 화면에서의
반복 결과, 사용자가 결과를 더 좋게 평가했다는 자료는 저장소에 없다.
`test/`의 테스트도 스크립트의 인자 검증, 저장 파일 생성, 영상 메타 태그 처리를
확인할 뿐 디자인 결과의 품질은 건드리지 않는다.
별 14,374개는 주목도를 보여 주지만 효과의 증거는 아니다. 저장소를 만든 지 2주
남짓 만에 모인 수치라서 더욱 그렇다.

### 금지 목록은 한 가지 취향을 보편 규칙처럼 쓴다

회색에 가까운 배경, 400과 500 두 굵기, 대문자 라벨 금지, 키캡과 고정폭 숫자 같은
선택은 이 저자가 선호하는 미감이다.
스킬도 이 문제를 안다. “템플릿 룩” 항목에서 정리된 화면이 아무도 결정하지 않았을
때 돌아가는 모양(`#161616`, Inter, 흰 글자)을 경고하고, 유행을 다른 유행으로
바꾸지 말라고 한다.
그러나 같은 문서가 배경은 회색이어야 하고 주황이나 파랑으로 읽히면 너무 나간
것이라고 단정한다. 이 규칙을 그대로 따르는 수많은 앱이 같은 모양으로 수렴할
위험은 스킬의 방향 단계가 막아야 하는데, 그 단계가 실제로 막는지는 근거가 없다.
이 위험은 이 문서의 추론이다.

### 슬롭의 정의가 시점에 묶여 있다

`signs.md`의 목록은 보라색 그라데이션, 이모지, 빛 번짐 같은 현재 모델이 자주
내놓는 기본값을 겨냥한다.
모델이 달라지거나 이 목록 자체가 학습되어 같은 증상이 사라지면 목록의 대부분이
가리킬 대상을 잃고, 목록이 담지 못하는 새로운 상투성이 생긴다.
방향을 제품에서 도출하라는 부분은 시간이 지나도 남지만, 그 품질은 에이전트가
제품을 얼마나 잘 읽는지에 달려 있고 스킬은 그것을 점검할 방법을 주지 않는다.

### 저장소가 서비스 영업을 겸한다

README 끝의 “Hire the unslopper” 안내와 영상의 필수 표기는 스킬이 저자의 영업
통로이기도 함을 보여 준다.
이는 숨겨져 있지 않고 저작자 표시를 요구하는 라이선스와도 일관된다.
다만 스킬이 방향과 결과를 사용자에게 먼저 보여 주고 판단하게 하는 구조는 “사람이
더 잘한다”는 서비스 안내와 긴장 관계에 있다. 도구가 충분하면 서비스가 필요 없고,
부족하면 스킬의 가치가 줄기 때문이다.
이는 이 문서의 해석이며 저자의 의도는 확인하지 못했다.

## 인사이트

### 디자인 취향은 점검 가능한 프로세스로 옮길 수 있는 부분과 없는 부분이 갈린다

이 스킬에서 옮겨진 것은 값(격자, 대비, 굵기)과 순서(간격에서 모션까지)와
금지(그라데이션 글자)다.
옮겨지지 않는 것은 방향 다섯 줄을 쓰는 판단이다. 이 부분은 에이전트가 제품
설명에서 “world”와 “signature”를 끌어내는 능력에 맡겨져 있다.
값과 순서는 반복해서 같은 결과를 내는 데 유리하고, 판단은 입력에 따라 달라진다.
따라서 같은 스킬이라도 방향을 사용자가 직접 정하는 경우와 에이전트에 맡기는
경우의 결과 차이가 가장 큰 변수일 것이다. 이는 이 문서의 가설이다.

### 슬롭을 지우는 스킬이 널리 쓰이면 지운 뒤의 모양이 새 기본값이 된다

수많은 사용자가 같은 스킬을 쓰면 “정리된 화면”의 모양이 서로 가까워진다.
스킬이 스스로 템플릿 점검을 넣은 것은 이 위험을 안다는 뜻이지만, 점검의 통과
기준은 에이전트의 자기 평가다.
이 구조는 인간의 편집 기준이 시간이 지나 관행이 되는 경과와 닮았다. 규칙이
유행이 되면 규칙을 어기는 쪽이 새로 눈에 띄는 쪽이 된다.
그러면 이 스킬의 효과는 도입 초기에 가장 크고, 널리 퍼진 뒤에는 방향 단계의
품질에 좌우될 것이다. 이는 이 문서의 추론이다.

### 쓰는 법: 목록 대신 순서와 멈춤 지점을 가져온다

이 스킬을 쓰지 않는 사람도 가져갈 것이 있다.
UI를 에이전트에게 맡길 때 한 번에 “예쁘게 해 줘”라고 하는 대신 감사, 방향 확인,
단계별 수정, 점검으로 나누고, 방향 확인에서 사람이 멈추게 하는 것이다.
특정 색이나 굵기 규칙은 제품의 브랜드와 충돌하면 버려야 하지만, 순서와 멈춤
지점은 어느 제품에도 적용된다.
비슷한 스킬과 비교할 때 먼저 볼 것은 금지 목록의 겹침이 아니라 이런 절차의
차이다.

### 결론을 바꿀 관찰

- 같은 화면을 스킬 없이, 그리고 스킬로 고친 결과를 여러 모델에서 가려 놓고
  평가한 결과가 나오면, 효과에 대한 근거 부족 비평은 근거를 얻거나 사라진다.
- 이 스킬로 고친 여러 제품의 화면이 서로 닮아 보인다는 사례가 쌓이면, 취향
  수렴에 대한 비평이 강해진다.
- 모델이 기본값으로 보라색 그라데이션과 이모지를 더 내놓지 않게 된 뒤에도 이
  스킬이 효과를 낸다면, 효과는 금지 목록이 아니라 절차와 방향 단계에서 온 것으로
  읽는 해석이 맞다.
