# SQLite에서 배운 신뢰성의 교훈

YouTube: [Reliability Lessons From SQLite - Richard Hipp | SSW 2026](https://www.youtube.com/watch?v=V_qzqY1bb7I)

## 요약

Software Should Work 2026 컨퍼런스에서 SQLite 개발자 Richard Hipp이 한 54분짜리 발표다.
2026년 8월 3일에 공개되었고, 슬라이드는 <https://sqlite.org/u/ssw6>에 있다.
초록은 SQLite가 26년 역사 동안 그냥 동작한다는 평판을 얻었으며 이 발표가 — 적어도 리드 개발자의 견해로는 — 그 평판을 만든 설계 선택과 개발 관행을 다룬다고 밝힌다.

### SQLite가 존재하는 이유

발표는 SQLite가 존재하는 이유부터 시작한다 — Informix가 동작하지 않았기 때문이다.
클라이언트들이 Informix 서버를 통해 디스크의 데이터베이스 파일에 접근하는 구조에서 서버가 죽으면 모든 클라이언트가 데이터베이스에 연결할 수 없습니다라는 오류창을 보게 된다.
SQLite는 서버를 없애고 각 클라이언트가 라이브러리를 링크해 디스크 파일에 직접 접근하게 만든 구조다.

SQLite는 전력 손실에도 안전한 ACID 트랜잭션을 갖춘 완전한 SQL을 제공하며, 애플리케이션에 링크되는 C 라이브러리이지 서버도 시스템도 아니다.
데이터베이스는 고정되고 잘 정의된 파일 형식을 가진 단일 파일이고, API는 안정적이고 하위 호환되며, 퍼블릭 도메인이다.
배포는 `sqlite3.c`라는 하나의 큰 C 파일로 이루어지는데 269K 줄(코드 170K)이고 100개가 넘는 작은 C 파일에서 조립되며 일부는 기계 생성이다 — 에이전트가 작성한 코드는 없다.
현재 커미터는 3명이다.

프로젝트 설계 수명은 2000-05-29부터 2050-05-29까지로 잡혀 있다.
사용 규모는 모든 휴대전화와 웹 브라우저, 대부분의 컴퓨터·TV·자동차·기타 기기에 들어가 있고, 수십억 명이 매일 의존하며, 사용 중인 데이터베이스 인스턴스가 1조 개를 넘고, 휴대전화 파일시스템 I/O의 약 50%를 담당한다.
그렇게 많이 쓰이는 이유로 유용함, 배포 용이성, 오픈소스, 낮은 의존성, 낮은 자원 사용, 죽지 않음을 들고, 이를 만드는 문제보다 푸는 문제가 더 많다와 그냥 동작한다로 묶는다.

### 테스트되지 않은 것은 동작하지 않는다

발표의 중심은 항공 소프트웨어 인증 표준인 DO-178B(1992, 84쪽)에서 가져온 세 축이다 — 요구사항 분석과 추적, 형상 및 생애주기 관리, 테스트.
형상 관리 쪽에서는 Hipp 본인이 만든 Fossil을 든다.

테스트의 목표는 100% MC/DC(Modified Condition/Decision Coverage)다.
모든 기계어 분기 명령이 최소 한 번씩 참으로 가고 거짓으로도 가야 하며, 비트마스크 검사의 모든 비트가 결과를 바꿔야 한다.
`if( a==5 && (b==7 || c==11) )`에 대해 100% 분기 커버리지는 네 가지 경우를 요구하고, `if( (x & 7)==0 )`에 대한 100% MC/DC는 일곱 가지 경우를 요구한다.
측정은 `gcc -fprofile-arcs -ftest-coverage`와 `gcov -b`로 하는데, 32만 줄이 넘는 15.5MB짜리 출력이 나온다.
비트마스크 검사처럼 gcov가 잡지 못하는 부분은 `testcase()` 매크로로 보완한다 — `SQLITE_COVERAGE`가 정의되었을 때만 `if(X){ noop(); }`가 되고 그 외에는 아무것도 아니다.
경계값 테스트도 같은 매크로로 표시한다.

테스트는 세 종류로 나뉜다.
① 테스트 케이스 검증 — 모든 요구사항이 충족되었는가, 100% MC/DC인가.
② 소스 코드 검증 — UBSAN, MSAN, ASAN, TSAN과 정적 분석.
③ 오브젝트 코드 검증 — 테스트한 것을 비행시키고, 비행시킬 것을 테스트하라.

### 결함 주입을 가능하게 하는 구조

테스트 프로그램은 애플리케이션 자리에 들어가 `sqlite3.c`를 호출하는데, 여기에 세 개의 주입 지점이 있다.
애플리케이션 정의 인터페이스(SQL 함수, 콜레이션 함수, 가상 테이블, 메모리 할당자, 페이지 캐시) 쪽에서 `malloc()` 실패를 시뮬레이션하고, VFS 쪽에서 I/O 오류와 전력 손실과 OS 크래시를 시뮬레이션하며 불변식을 검사한다.
OS 인터페이스는 함수 포인터 호출로 되어 있다 — `unix_syscall` 구조체 배열이 시스템 콜 이름과 현재 값과 기본값을 갖고 `#define osOpen`이 그 포인터를 거친다.
이 인터페이스는 공개되어 있지만 눈에 잘 띄지 않으며, 싱글턴이고 스레드 안전하지 않으며 테스트 전용이다.

OOM 테스트는 대체 메모리 할당자를 쓰게 한 뒤 N번째 할당에서 한 번만 실패하게 만들어 N=1,2,3…으로 반복하고, 다시 N번째부터 모든 할당이 실패하게 만들어 반복한다 — 더 이상 실패가 발생하지 않을 때까지다.
I/O 오류 테스트는 N번째 시스템 콜에서 I/O 오류를 주는 방식으로 같은 형태다.
크래시 테스트는 가상 파일시스템을 구현한 대체 OS 인터페이스를 써서, N번째 시스템 콜에서 상태 스냅숏을 만들고 전력 손실 후 실제 파일시스템에서 예상되는 전형적인 무작위 변경을 가한 뒤, 손상된 스냅숏 위에서 SQLite를 재시작해 올바르게 복구하는지 확인하며, 각 N에 대해 이를 여러 번 반복한다.

`sqlite3_test_control()`은 모든 빌드에 포함된다 — 테스트한 것을 비행시킨다는 원칙 때문이다.
질의 최적화를 켜고 끄고, 질의 계획기 상수를 조정하고, `sqlite3FaultSim()`을 제어하고, PRNG를 알려진 값으로 시드하고, 서브모듈 단위 테스트를 돌린다.
`sqlite3FaultSim(int eCode)`는 기본적으로 0을 반환하고 `sqlite3_test_control()`로 0이 아닌 값을 반환하게 만들 수 있으며 선택적으로 N번째 호출에서만 그렇게 할 수 있다 — 2026-07-02 기준 24개 지점에 있다.
예를 들어 `pthread_create()` 실패 경로를 이것으로 만든다.

### 테스트 자산의 규모

테스트는 두 갈래다.
TCL 테스트는 원조로 26년 이상의 역사와 2만 개 케이스, 1450만 번의 테스트를 담고 있으며 SQLite 자체보다 6.5배 크고 소스 트리의 일부다 — 다만 커스텀 빌드를 쓰므로 비행시킬 것을 테스트하지는 못한다.
TCL은 1988년경 John Ousterhout이 만든 C 문법을 가진 Lisp이며, Hipp은 SQLite를 야생으로 탈출한 TCL 확장이라고 부른다.

Test Harness #3(TH3)는 2008-09-25에 첫 코드가 들어갔고 303일과 385번의 체크인 뒤인 2009-07-25에 코어에 대해 100% MC/DC를 달성했다.
2026-06-24 기준 6,716번의 체크인(연평균 353회), 2,419개 파일, 662,731줄이며, 코어와 유닉스 OS 인터페이스와 RTREE와 STAT4에 대해 100% MC/DC다.

코드 주석에 대한 지침도 나온다 — 모든 함수의 목적을 서술하고, 모든 변수가 무엇을 나타내는지 서술하며, 간결하게 쓰고 상투구를 넣지 않는다.
아직 태어나지 않은 사람도 코드를 이해할 수 있도록, 그리고 인간 언어와 형식 언어가 서로 다른 뇌 경로를 쓰기 때문이다.

`assert(X)`는 불변식이다 — X가 거짓이면 프로그램에 버그가 있고, 내장된 테스트이며, 프로그램에 대한 어떤 진실을 서술하는 실행 가능한 주석이다.
SQLite에는 약 7,500개(정확히는 7,442개, 코드의 4%)의 `assert()`가 있고 `assert()`가 무연산일 때 4배 빠르게 돌기 때문에 기본적으로 꺼져 있으며 `-DSQLITE_DEBUG`로 켠다.
`NEVER()`와 `ALWAYS()`는 388개 인스턴스로 테스트되지 않은 분기를 식별한다 — 커버리지 빌드에서는 각각 0과 1을 반환하고, 디버그 빌드에서는 반대 값이 나오면 `assert(0)`으로 죽으며, 배포 빌드에서는 그냥 X다.
`testcase()`는 1,202개 인스턴스다.

### 변이 테스트와 그 한계

변이 테스트는 소스 코드나 오브젝트 코드에 작은 변경을 가하고 — 분기를 무조건 점프로 바꾸거나, 명령을 무연산으로 바꾸거나, 한 줄을 주석 처리하고 — 테스트 절차가 그 오류를 잡아내는지 확인하는 것이다.
이는 테스트 케이스의 검증이지 코드의 오류를 찾는 것이 아니며, 부족한 테스트를 찾는 데만 쓴다.

두 가지 어려움이 제시된다.
`strHash()`에서 `while( (c = (unsigned char)*z++)!=0 )`의 분기를 무조건 점프로 바꾸면 해시 함수가 항상 0을 반환하고 해시 테이블이 연결 리스트로 퇴화하지만 답은 여전히 항상 맞다.
`if( shortCutWorks() ){ FastShortCutCase() }else{ SlowerGeneralCase() }` 구조에서는 `SlowerGeneralCase()`가 항상 동작하므로 `shortCutWorks()`의 거짓 음성을 탐지하기 어렵다.

이 외에 플랫폼 다양성(MSVC·GCC·LLVM, Linux·Mac·OpenBSD·Windows, x64·x86·ARM·PPC, 32비트와 64비트, 빅엔디언과 리틀엔디언, 부호 있는 char와 없는 char), 최적화 비활성화 테스트(같은 SQL을 최적화를 끄고 다시 돌려 같은 답이 나오는지 확인), 성능 테스트, 멀티스레드 테스트, 크로스 플랫폼 테스트, SQLite를 쓰는 애플리케이션 재빌드 및 테스트, 정적 분석이 있으며 체크리스트가 전체를 관리하는 데 도움이 된다고 말한다.

### 퍼징과 AI 버그

테스트의 예상 밖 이득으로는 소수의 커미터만으로 유지보수 가능하다는 점, 무언가를 깨뜨릴 두려움 없이 리팩터링하거나 개선할 자유, 버그를 더 쉽게 찾고 고칠 수 있다는 점, 더 빠른 코드가 꼽힌다.
마지막 항목은 그래프로 뒷받침된다 — `speedtest1`을 완료하는 데 필요한 x64 CPU 사이클이 2009년 약 34억에서 2024년 약 10억 이하로 내려간다.

소스 코드와 테스트 스위트가 서로 구별된다는 무언의 가정이 있지만, SQLite에서는 배포되는 소스 코드의 약 15%가 실은 테스트 스위트의 일부이고 오브젝트 코드에서 그 비율은 더 작지만 여전히 0이 아니다.
그리고 실제 비율에 가깝게 그리면 소스 코드 원이 테스트 스위트 원보다 훨씬 작다.

프로젝트 연표에는 2005년경 3.0.0, 2010년경 100% MC/DC, 2013년경 프로파일 유도 퍼징, 2020년경 질의 퍼징, 2025년경 AI 버그가 표시된다.
프로파일 유도 퍼징은 2013년 Michał Zalewski(lcamtuf)의 AFL과 LLVM의 libFuzzer가 기반이고, SQLite의 `dbsqlfuzz`는 libFuzzer 기반으로 데이터베이스 파일과 SQL 입력을 동시에 퍼징하며 SQLite 데이터베이스와 SQL 텍스트에 특화된 커스텀 변이기를 쓰고 수십 개 코어에서 24시간 내내 돌아간다 — 롤업 데이터베이스는 77,645개 케이스, 20.8MB다.

질의 퍼징은 Manuel Rigger가 2019년경 발명한 기법이다 — `SELECT a, b, c FROM ...`이 `(1, 2, 3)`을 반환한다면 `SELECT * FROM (<원래 질의>) WHERE b=2;`도 같은 튜플을 반환해야 한다는 불변식으로 질의 결과의 불일치를 찾는다.

AI 버그의 예로는 `median(X)` 구현이 나온다 — 모든 X 입력을 배열에 모아 퀵소트한 뒤 가운데 값을 취하는데, 병적인 100만 항목 입력이 퀵소트가 CPU 스택을 넘치게 만든다.
AI가 제안한 수정은 `quicksort()`에 depth 파라미터를 추가해 너무 깊어지면 다른 알고리즘을 쓰라는 것이었고, 실제 수정은 더 작은 파티션에 대해서만 재귀하는 것이었다(Robert Sedgewick).

마지막 정리는 일곱 줄이다 — 테스트 가능성은 설계 목표여야 한다, 100% MC/DC 테스트는 효과가 있다, 테스트 케이스의 크기는 코드의 10배 이상이어야 한다, 코드의 약 10~20%는 테스트에만 쓰인다, 명확하고 간결한 문서, 시간의 대부분을 테스트에 쓸 것을 예상하라, 좋은 버전 관리는 상황 인식을 준다.

## 분석

### 이 발표는 테스트 방법론이 아니라 아키텍처 이야기다

표면적으로 이 발표는 커버리지 지표와 퍼저 목록이다.
그런데 실제로 반복해서 등장하는 것은 어떻게 테스트했는가가 아니라 무엇이 테스트를 가능하게 했는가다.

OS 인터페이스를 함수 포인터로 호출하는 구조가 없으면 I/O 오류 주입이 불가능하다.
메모리 할당자를 교체 가능하게 만들지 않았으면 OOM 테스트를 짤 수 없다.
VFS 계층이 없으면 전력 손실 시뮬레이션이 성립하지 않는다.
이 세 가지는 모두 설계 결정이지 테스트 기법이 아니며, 발표의 마지막 슬라이드 첫 줄이 테스트 가능성은 설계 목표여야 한다인 이유가 여기에 있다.

이 순서는 대부분의 조직이 하는 것과 반대다.
보통은 기능을 만들고 나중에 테스트를 붙이며, 그때 발견하는 것은 이 코드는 테스트하기 어렵다는 사실이다.
SQLite의 답은 테스트하기 어려운 코드를 어떻게든 테스트하는 방법이 아니라, 애초에 주입 지점을 아키텍처에 넣어두는 것이다.
그리고 그 지점들이 공개 API로 존재하되 눈에 잘 띄지 않게(published, but obscure) 배치되어 있다는 점이 이 설계의 세밀함을 보여준다 — 테스트를 위해 캡슐화를 깨되, 그것을 일반 사용자가 밟지 않도록 한 것이다.

### 100% MC/DC는 지표가 아니라 강제 장치다

100% MC/DC를 목표로 잡으면 커버리지 도구가 잡지 못하는 곳이 드러난다.
비트마스크 검사의 각 비트가 결과를 바꾸는지는 gcov가 알려주지 않으므로 `testcase()` 매크로를 소스에 넣어야 하고, 도달 불가능해 보이는 방어 코드는 `NEVER()`/`ALWAYS()`로 표시해야 한다.
즉 커버리지 100%를 진짜로 달성하려 하면 소스 코드의 형태가 바뀐다.

이것이 이 발표에서 가장 이식성 있는 아이디어다.
커버리지를 지표로 쓰면 숫자를 올리기 위한 무의미한 테스트가 늘어나지만, 커버리지를 강제 장치로 쓰면 코드의 어느 부분이 검증 불가능한지가 명시적으로 표시된다.
388개의 `NEVER()`/`ALWAYS()`는 이 코드는 테스트되지 않았고 우리는 그것을 안다는 선언의 목록이다.

`assert()` 7,442개에 대한 설명도 같은 성격이다 — 불변식이자 내장 테스트이자 실행 가능한 주석이라는 세 정의를 나란히 놓는다.
주석은 낡고 테스트는 별도 파일에 살지만, `assert()`는 코드 옆에 있으면서 실행된다.
디버그 빌드에서 4배 느려지는 대가를 치르고 그것을 기본에서 끄되 개발 중에는 항상 켜 둔다는 배치는, 검증 자산이 배포물의 성능을 인질로 잡지 않게 하는 방법이다.

### 테스트한 것을 비행시킨다는 원칙이 TCL 테스트를 2급으로 만든다

발표는 26년 역사의 TCL 테스트를 원조라고 부르면서도 커스텀 빌드를 쓰기 때문에 비행시킬 것을 테스트하지 못한다고 명시한다.
같은 이유로 `sqlite3_test_control()`은 모든 빌드에 들어간다.

이 구분은 항공 소프트웨어 문화에서 온 것이고 소프트웨어 업계 일반의 관행과 충돌한다.
대부분의 프로젝트는 테스트 빌드와 배포 빌드를 다르게 만들고, 그 차이를 문제로 여기지 않는다.
디버그 심볼, 어서션, 모킹된 의존성, 테스트 전용 플래그가 배포본에는 없는 것이 정상으로 통한다.

SQLite는 그 차이를 결함으로 본다.
테스트 통과가 배포본에 대해 아무것도 말해주지 않을 수 있기 때문이다.
그래서 TH3라는 두 번째 하네스를 66만 줄 규모로 별도로 만들었고, 그것이 TCL 테스트를 대체하지 않고 병존한다.
비용을 보면 이 원칙이 얼마나 비싼지 드러난다 — 같은 목적의 테스트 자산을 두 벌 유지하는 것이다.

## 비평

### 발표는 이 방식의 비용을 숫자로 제시하면서도 그 비용의 성격을 흐린다

테스트 케이스가 코드의 10배 이상이어야 한다는 결론은 명확하고 정직하다.
TH3 66만 줄, TCL 테스트가 SQLite의 6.5배, 배포 소스의 15%가 실은 테스트 코드라는 수치도 모두 제시된다.

문제는 이 비용이 어디에서 나왔는지다.
SQLite는 API가 안정적이고 하위 호환되며, 파일 형식이 고정되어 있고, 요구사항이 26년 동안 근본적으로 바뀌지 않았다.
SQL 표준은 천천히 움직이고 데이터베이스가 해야 할 일은 명확하다.
이 조건에서 테스트 자산은 자산으로 축적되지만, 요구사항이 분기마다 바뀌는 제품에서는 같은 자산이 부채가 된다.

발표는 이 조건을 언급하지 않는다.
프로젝트 설계 수명이 2050년까지라는 슬라이드가 사실상 그 답이지만, 그것이 전제라는 점을 명시하지 않으므로 청중은 10배 규칙을 보편 규칙으로 가져가기 쉽다.
50년 수명을 가정하지 않는 프로젝트에서 코드의 10배짜리 테스트를 만드는 것은 합리적이지 않을 수 있고, 그 판단 기준은 발표에 없다.

### 커버리지 100%를 달성한 뒤에도 버그가 나온다는 사실이 충분히 다뤄지지 않는다

2009년에 코어에 대해 100% MC/DC를 달성했다.
그런데 연표는 그 뒤로 2013년 프로파일 유도 퍼징, 2020년 질의 퍼징, 2025년 AI 버그를 계속 추가한다.
즉 100% MC/DC는 충분하지 않았고, 그 사실이 연표 자체로 증명되어 있다.

이것은 커버리지 지표의 근본적 한계다 — 모든 분기를 실행했다는 것은 모든 입력 조합을 실행했다는 뜻이 아니다.
발표가 든 `median(X)` 버그가 정확히 그 예다.
퀵소트 코드의 모든 분기는 이미 커버되어 있었을 것이고, 문제는 100만 항목의 병적인 배열이라는 입력 특성이었다.
질의 퍼징이 찾는 결과 불일치도 마찬가지로, 코드 경로가 아니라 의미론의 문제다.

발표는 이 층위 차이를 명시적으로 정리하지 않는다.
100% MC/DC 테스팅은 효과가 있다가 결론에 그대로 남고, 그것이 무엇에 대해 효과가 있고 무엇에 대해 없는지는 청중이 연표에서 스스로 읽어내야 한다.
실무자에게 필요한 것은 커버리지가 잡는 결함 부류와 퍼징이 잡는 결함 부류와 불변식 검사가 잡는 결함 부류의 구분인데, 발표는 세 가지를 시간 순으로 나열할 뿐 어느 것이 무엇을 대체하지 못하는지 말하지 않는다.

### 변이 테스트의 어려움 두 가지는 방법론의 실패가 아니라 코드 설계의 신호다

발표는 변이 테스트가 어려운 사례로 두 가지를 든다.
해시 함수를 망가뜨려도 답은 맞다는 것과, 빠른 지름길이 실패해도 느린 일반 경로가 받아주므로 지름길의 거짓 음성을 탐지할 수 없다는 것이다.

이 둘은 변이 테스트의 한계로 제시되지만, 다르게 읽을 수 있다.
두 사례 모두 정확성에는 영향이 없고 성능에만 영향이 있는 코드다.
즉 변이 테스트가 실패한 것이 아니라, 정확성 오라클로 성능 회귀를 잡으려 한 것이다.
성능 회귀를 잡는 도구는 따로 있고, 발표에도 `speedtest1`이라는 성능 테스트가 등장한다.

더 흥미로운 것은 두 번째 사례가 드러내는 설계 패턴이다.
지름길과 일반 경로를 나란히 두고 지름길이 실패하면 조용히 일반 경로로 떨어지는 구조는 견고하지만 관측 불가능하다.
같은 구조가 데이터베이스 질의 계획기, 캐시 계층, 프로토콜 협상 어디에나 있고, 어디서나 같은 문제를 만든다 — 지름길이 언제부터 동작하지 않았는지 아무도 모른다.
해법은 변이 테스트를 개선하는 것이 아니라 지름길의 적중률을 계측해 노출하는 것인데, 발표는 이 방향을 언급하지 않는다.

## 인사이트

### 테스트 자산이 클수록 사람이 적게 필요해진다는 역설

이 발표에서 가장 반직관적인 수치는 커미터가 3명이라는 것이다.
전 세계 1조 개 인스턴스, 휴대전화 I/O의 절반을 담당하는 소프트웨어를 세 사람이 유지한다.

보통 우리는 테스트를 비용으로 계산한다 — 테스트를 쓰는 시간만큼 기능 개발이 늦어진다는 것이다.
SQLite의 배치는 반대 방향을 가리킨다.
테스트 자산이 충분히 크면 사람 수를 늘리지 않고도 변경을 감당할 수 있고, 사람 수가 적으면 조율 비용이 사라지며, 조율 비용이 사라지면 다시 변경 속도가 빨라진다.
예상 밖 이득 슬라이드의 첫 줄이 소수의 커미터만으로 유지보수 가능이고 두 번째 줄이 두려움 없이 리팩터링할 자유인 것은 우연이 아니다.

이 관점은 조직 규모에 대한 통상적 계산을 뒤집는다.
코드베이스가 커져서 사람을 더 뽑는다는 결정은, 실은 검증 자산이 부족해서 각 변경마다 사람의 주의가 필요하다는 상태를 인력으로 메우는 것일 수 있다.
그리고 사람을 더 뽑으면 검증 자산을 만들 시간이 아니라 조율에 시간이 들어가므로, 이 상태는 스스로를 강화한다.
SQLite가 보여주는 것은 그 순환에서 빠져나오는 데 15년이 걸렸다는 사실이기도 하다 — 2000년에 시작해 2009년에 100% MC/DC에 도달했고 그 뒤로도 계속 하네스를 추가했다.

### 테스트에서 나온 성능 향상이 이 발표의 가장 저평가된 발견이다

`speedtest1` 그래프는 2009년 34억 사이클에서 2024년 10억 이하로 내려간다.
같은 소프트웨어가 15년 동안 3배 이상 빨라졌고, 발표는 이를 테스트의 예상 밖 이득으로 분류한다.

인과는 단순하다 — 회귀를 즉시 잡아주는 테스트가 있으면 위험한 최적화를 시도할 수 있다.
데이터 구조를 바꾸고, 알고리즘을 교체하고, 코드 경로를 재배치하는 변경은 미묘한 정확성 문제를 낳기 쉬우며, 그 문제를 잡을 수단이 없으면 아무도 시도하지 않는다.
성능은 대개 한 번의 큰 개선이 아니라 수백 번의 작은 개선으로 만들어지고, 각 개선의 기대값이 위험보다 크려면 위험이 충분히 낮아야 한다.

이 인과는 성능뿐 아니라 모든 종류의 개선에 적용된다.
API를 정리하는 일, 의존성을 줄이는 일, 오래된 추상을 걷어내는 일이 모두 같은 구조를 갖는다 — 기대 이득은 작고 위험은 크며, 검증 비용이 위험을 낮춘다.
그래서 검증 자산이 부족한 조직에서는 코드가 나빠지는 것이 아니라 코드가 굳는다.
버그가 늘어나는 것보다 개선이 멈추는 쪽이 먼저 온다는 점은, 테스트 투자를 정당화할 때 대개 언급되지 않는 논거다.

### AI 수정 제안 사례는 이 발표의 결론과 정확히 대칭을 이룬다

`median(X)`의 스택 오버플로에 대해 AI는 퀵소트에 깊이 파라미터를 넣고 너무 깊어지면 다른 알고리즘으로 전환하라고 제안했고, 실제 수정은 더 작은 파티션에 대해서만 재귀하는 것이었다.
전자는 증상에 대한 방어이고 후자는 Sedgewick이 정리한 표준 기법이다.

이 대비가 흥미로운 이유는 AI 제안도 문제를 고치기 때문이다.
깊이 파라미터를 넣으면 스택 오버플로는 실제로 사라지고, 테스트도 통과할 것이다.
차이는 결과가 아니라 코드가 남기는 것에 있다 — 전자는 새 분기와 새 알고리즘과 새 임계값을 남기고, 후자는 재귀 조건 한 줄을 바꾼다.
100% MC/DC를 목표로 하는 프로젝트에서 새 분기는 새 테스트 케이스를 의미하고, 새 임계값은 그 값 주변의 경계값 테스트를 의미한다.

여기서 발표의 다른 슬라이드가 다시 읽힌다 — SQLite는 에이전트가 작성한 코드를 받지 않는다는 문장이다.
이유를 라이선스나 품질로만 읽으면 부분적이다.
검증 비용이 코드 줄 수가 아니라 분기 수에 비례하는 프로젝트에서, 동작하는 가장 쉬운 수정을 내놓는 생성기는 그 자체로 비용 구조를 악화시킨다.
그리고 그 비용은 수정을 받은 시점이 아니라 이후 26년간 매 릴리스마다 발생한다.

### 사용 규모와 유지 규모의 불균형이 이 사례의 재현 가능성을 제한한다

1조 개 인스턴스, 휴대전화 I/O의 절반, 커미터 3명.
발표는 xkcd 2347을 인용해 이 상황을 스스로 농담으로 만든다 — 네브래스카의 누군가가 2003년부터 고맙다는 말도 못 듣고 유지해 온 프로젝트 위에 모든 현대 디지털 인프라가 얹혀 있다는 그림이다.

그런데 이 그림에는 대개 언급되지 않는 조건이 있다.
SQLite가 이 부담을 감당할 수 있는 이유는 요구사항이 안정적이고, 사용자가 API 변경을 요구하지 않으며, 기능 추가 압력이 낮기 때문이다.
같은 규모로 쓰이면서 요구사항이 계속 바뀌는 소프트웨어는 세 사람으로 유지될 수 없다.
즉 이 사례가 증명하는 것은 좋은 테스트가 있으면 적은 인원으로 큰 소프트웨어를 유지할 수 있다가 아니라, 요구사항을 동결할 수 있고 좋은 테스트가 있으면 그렇다는 조건부 명제다.

이 조건을 분리해 보면 실무에 옮길 수 있는 것이 남는다.
시스템 전체의 요구사항을 동결할 수는 없어도, 특정 계층의 요구사항은 동결할 수 있다.
파일 형식, 프로토콜, 코어 자료구조처럼 오래 살아야 하는 층을 골라 그 층에만 SQLite식 검증을 적용하고, 요구사항이 자주 바뀌는 층은 다른 전략으로 다루는 분리다.
발표가 소스 코드와 테스트 스위트의 원 크기를 실제 비율로 다시 그린 슬라이드는 인상적이지만, 모든 코드에 그 비율을 적용하라는 뜻으로 읽으면 대부분의 조직에서 실행 불가능한 조언이 된다.
어느 층에 적용할지를 고르는 판단이 이 발표에서 청중이 스스로 채워야 하는 빈칸이다.
