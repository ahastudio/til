# RFC 9457: API마다 오류 형식을 새로 만들지 말라는 표준

원문: [RFC 9457 - Problem Details for HTTP APIs](https://datatracker.ietf.org/doc/html/rfc9457)

HN 토론: <https://news.ycombinator.com/item?id=37138744> (13점, 4개 댓글)

전작 RFC 7807 HN 토론: <https://news.ycombinator.com/item?id=35364224> (176점, 48개 댓글)

전작 RFC 7807 Lobste.rs 토론: <https://lobste.rs/s/lailai/rfc_7807_problem_details_for_http_apis> (12점, 1개 댓글)

## 요약

RFC 9457은 Mark Nottingham, Erik Wilde, Sanjay Dalal이 쓴 2023년 7월 표준화 트랙(Standards
Track) 문서로, 2016년의 RFC 7807을 대체한다.
목적은 한 문장으로 정리된다 — HTTP 응답 본문에 오류의 기계 판독 가능한 상세 정보를 담는
“문제 상세(problem detail)”를 정의해, HTTP API마다 새 오류 응답 형식을 정의할 필요를 없애는
것이다.

명세는 문제의 종류를 URI로 식별한다.
API는 자기가 통제하는 URI로 자기만의 문제를 식별할 수도 있고, 상호운용성과 공통 의미를 얻으려고
기존 URI를 재사용할 수도 있다.
데이터 모델은 JSON 객체이며 직렬화하면 `application/problem+json` 미디어 타입을 쓴다.
부록 B가 동등한 XML 형식을 `application/problem+xml`로 정의한다.

명세가 스스로 그린 경계선이 뚜렷하다.
문제 상세는 어떤 상태 코드와도 쓸 수 있지만 4xx·5xx의 의미에 가장 자연스럽게 맞으며, HTTP에서
문제를 전달하는 유일한 방법도 아니다.
응답이 여전히 어떤 리소스의 표현이라면 그 애플리케이션의 형식으로 상세를 서술하는 편이 나은
경우가 많고, 이미 정의된 HTTP 상태 코드만으로 추가 설명 없이 충분한 상황도 많다.
명세의 목표는 형식이 필요한 애플리케이션에 공통 오류 형식을 주어, 각자 만들거나 더 나쁘게는 기존
HTTP 상태 코드의 의미를 재정의하려는 유혹에 빠지지 않게 하는 것이다.

전작에서 바뀐 것은 부록 D에 세 항목으로 정리돼 있다 — 공통 문제 타입 URI의 레지스트리를 도입한
것(4.2절), 여러 문제가 동시에 발생했을 때의 처리를 명확히 한 것(3절), 역참조할 수 없는 타입
URI에 대한 지침을 준 것(3.1.1절)이다.
감사의 말에는 Subbu Allamaraju, Mike Amundsen, Roy Fielding, Julian Reschke 등이 이름을 올렸다.

## 명세

### 다섯 멤버

문제 상세 객체는 다섯 멤버를 가질 수 있다.
멤버 값의 타입이 명세와 맞지 않으면 소비자는 그 멤버를 반드시 무시해야 하며(MUST), 처리는 그
멤버가 없었던 것처럼 계속된다.

| 멤버       | 타입          | 의미와 제약                                                                 |
| ---------- | ------------- | --------------------------------------------------------------------------- |
| `type`     | URI 참조 문자열 | 문제 타입의 1차 식별자. 없으면 값은 `about:blank`로 간주된다                |
| `status`   | JSON 숫자     | 원 서버가 생성한 HTTP 상태 코드. 있어도 참고용(advisory)일 뿐이다           |
| `title`    | 문자열        | 문제 타입의 짧은 사람 읽기용 요약. 발생마다 달라지지 않아야 한다(SHOULD NOT) |
| `detail`   | 문자열        | 이번 발생에 특정한 사람 읽기용 설명                                         |
| `instance` | URI 참조 문자열 | 문제의 특정 발생을 식별한다                                                 |

`type`은 소비자가 문제 타입의 1차 식별자로 반드시 써야 한다(MUST).
타입 URI가 로케이터라면(`http`·`https` 스킴 등) 역참조 시 사람이 읽을 문서를 제공해야 하지만
(SHOULD), 소비자는 개발자에게 정보를 줄 때(디버깅 도구를 쓸 때 등)를 빼면 타입 URI를 자동으로
역참조하지 않아야 한다(SHOULD NOT).
상대 URI는 혼란을 부를 수 있어 가능하면 절대 URI를 권장한다 — 명세는 `https://api.example.org/foo/bar/123`과
`https://api.example.org/widget/456`이 같은 `example-problem`을 반환하면 서로 다른 리소스로
해소된다는 예를 든다.
역참조할 수 없는 URI도 허용되며 `tag:example@example.org,2021-09-17:OutOfLuck` 같은 tag URI
스킴을 예로 들지만, 나중에 URI를 해소하고 싶어질 수 있어 해소 가능한 URI를 권장한다.

`status`의 위치가 미묘하다.
생성자는 실제 HTTP 응답에 같은 상태 코드를 반드시 써야 하며(MUST), 이 형식을 이해하지 못하는
일반 HTTP 소프트웨어도 올바르게 동작하게 보장해야 한다.
그러면 이 멤버는 언제 쓰이는가 — 중개자나 캐시가 상태 코드를 바꿨을 때, 그리고 메시지 본문이
HTTP 정보 없이 저장됐을 때 원래 코드가 무엇이었는지 알아내는 용도다.

`title`은 타입 URI의 의미를 모르고 알아낼 수도 없는 사용자(오프라인 로그 분석 등)를 위한
참고용이다.
`detail`은 디버깅 정보를 주기보다 클라이언트가 문제를 고치도록 돕는 데 집중해야 하며, 소비자는
`detail`을 파싱해 정보를 얻으려 하지 않아야 한다(SHOULD NOT) — 그런 용도로는 확장이 더 적절하고
오류가 덜 난다.

### 두 예제

명세의 첫 예제는 잔액 부족이다.
`POST /purchase`에 대해 403 Forbidden과 함께 `application/problem+json`을 돌려주며, 확장 멤버
`balance`와 `accounts`를 더한다.

```http
HTTP/1.1 403 Forbidden
Content-Type: application/problem+json
Content-Language: en

{
 "type": "https://example.com/probs/out-of-credit",
 "title": "You do not have enough credit.",
 "detail": "Your current balance is 30, but that costs 50.",
 "instance": "/account/12345/msgs/abc",
 "balance": 30,
 "accounts": ["/account/12345",
              "/account/67890"]
}
```

둘째 예제는 같은 타입의 문제가 여러 건 발생한 경우다.
422 Unprocessable Content와 함께 `errors` 확장 배열을 쓰고, 각 원소는 `detail`로 문제를 서술하고
`pointer`로 요청 본문 안의 위치를 JSON Pointer로 지목한다.

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
Content-Language: en

{
 "type": "https://example.net/validation-error",
 "title": "Your request is not valid.",
 "errors": [
             {
               "detail": "must be a positive integer",
               "pointer": "#/age"
             },
             {
               "detail": "must be 'green', 'red' or 'blue'",
               "pointer": "#/profile/color"
             }
          ]
}
```

타입이 서로 다른 여러 문제를 만났을 때는 가장 관련 있거나 급한 문제 하나를 응답에 담기를
권장한다(RECOMMENDED).
여러 이질적 타입을 담는 일반 “배치” 문제 타입을 만들 수는 있지만 HTTP 의미에 잘 맞지 않는다는
것이 명세의 판단이다.
두 예제 모두 클라이언트가 `Accept`에 `application/problem+json`을 넣지 않았는데도 서버가 그
타입으로 응답하는데, 명세는 이것이 HTTP가 허용하는 바라고 밝힌다.

### 확장과 새 타입 정의

문제 타입 정의는 그 타입에 특정한 멤버를 더할 수 있다(MAY).
클라이언트는 알아보지 못하는 확장을 반드시 무시해야 하며(MUST), 그래야 문제 타입이 진화하며
정보를 더할 수 있다.
확장 이름은 문자로 시작하고 문자·숫자·`_`로 구성하고 세 글자 이상이기를 권장하며(SHOULD),
XML 형식에서 쓰려면 XML의 Name 규칙에 맞아야 한다.

새 문제 타입 정의가 반드시 문서화해야 하는 것은 셋이다(MUST) — 타입 URI(보통 `http`·`https`
스킴), 짧게 잘 서술한 제목, 함께 쓸 HTTP 상태 코드다.
`Retry-After` 응답 헤더의 사용을 명시할 수 있고(MAY), 타입 URI는 문제 해결법을 설명하는 HTML
문서로 해소되기를 권장한다(SHOULD).

명세는 새 타입을 만들기 전에 멈춰 생각하라고 요구한다.
문제 상세는 하부 구현의 디버깅 도구가 아니라 HTTP 인터페이스 자체에 대해 더 자세히 알리는
수단이며, 웹의 어느 리소스에나 적용될 만큼 정말 일반적인 문제는 보통 그냥 상태 코드로 표현하는
편이 낫다 — “쓰기 접근 불허” 문제 타입은 PUT에 대한 403 Forbidden이 자기 설명적이므로 아마
불필요하다는 것이 예로 나온다.
이미 오류를 실어 보낼 더 적절한 자체 형식이 있다면 그것을 쓰는 편이 낫다 — 문제 상세는 새
“fault”·“error” 문서 형식을 만들 필요를 없애려는 것이고, 기존 도메인 특화 형식을 대체하려는
것이 아니다.

### 레지스트리와 about:blank

RFC 9457이 전작에 더한 가장 큰 것은 “HTTP Problem Types” 레지스트리다.
정책은 RFC 8126 4.6절의 Specification Required이며, 지정 전문가는 커뮤니티 피드백과 문제 타입의
정의 수준, 이 명세의 요구사항을 함께 고려한다.
결정적 제한이 하나 있다 — 벤더 특화, 애플리케이션 특화, 배치 특화 값은 등록할 수 없다.
등록 시 `https://iana.org/assignments/http-problem-types#` 접두사를 타입 URI로 쓸 수 있지만
(MAY), 명세는 그 URI가 해소되지 않을 수 있다고 덧붙인다.

이 명세가 실제로 등록한 문제 타입은 하나다.

```text
Type URI:  about:blank
Title:  See HTTP Status Code
Recommended HTTP status code:  N/A
Reference:  RFC 9457
```

`about:blank`는 그 문제가 HTTP 상태 코드 이상의 의미를 갖지 않음을 뜻한다.
이때 `title`은 해당 코드의 권장 HTTP 상태 문구와 같기를 권장하며(404면 “Not Found”), 클라이언트
선호에 맞춰 지역화할 수 있다(MAY).
그리고 `type` 멤버의 정의상 `about:blank`가 기본값이므로, `type`을 명시하지 않은 모든 문제 상세
객체는 암묵적으로 이 URI를 쓴다.

### 보안 고려와 부록

보안 절이 짚는 위험은 두 갈래다.
하나는 정보 누출로, 생성자는 스택 덤프 같은 구현 세부를 HTTP 인터페이스로 노출하지 않도록
권장된다 — 서버 구현과 데이터의 민감한 세부가 드러날 수 있기 때문이다.
다른 하나는 `status` 멤버가 HTTP 상태 코드의 정보를 중복해 둘이 어긋날 가능성을 만든다는 것이며,
명세는 어느 쪽이 우선하는지 분명하지 않다고 스스로 적는다.
프록시·로드 밸런서·방화벽·바이러스 스캐너 같은 일반 HTTP 소프트웨어가 이 멤버에 담긴 상태
코드를 알거나 존중할 가능성은 낮다.

부록 A는 비규범적(non-normative) JSON Schema를 준다.
부록 B는 XML 형식을 RELAX NG 스키마로 정의하며, 확장 배열은 `i`라는 이름의 자식 요소들만 담은
요소로 직렬화한다.
XML에 XSLT를 가리키는 처리 명령을 넣어 클라이언트가 (X)HTML로 변환해 사람이 읽기 좋게 표시하게
할 수 있으며, 이 방법을 쓸 때는 변환을 수행할 수 있는 클라이언트 수를 최대화하려고 XSLT 1.0을
쓰는 편이 좋다고 조언한다.
부록 C는 다른 형식에 문제 상세를 넣는 방법을 다루는데, HTML에서 `application/problem+json` 타입의
`script` 태그로 JSON을 감싸는 예와 RDFa 매핑을 언급하되 구체적 권고는 하지 않는다.

## 분석

### 이 명세의 진짜 주장은 “형식을 정의하지 말라”이다

RFC 9457을 오류 형식 명세로 읽으면 절반만 읽은 것이다.
명세가 반복해서 말하는 것은 형식을 쓰라는 것이 아니라 형식을 새로 만들지 말라는 것이며, 그 논거는
상호운용성보다 훨씬 구체적인 위험을 향한다 — 각자 만들거나 “더 나쁘게는 기존 HTTP 상태 코드의
의미를 재정의하려는 유혹”이다.

이 위험 진단이 명세의 모든 설계 결정을 설명한다.
`status` 멤버를 두고도 생성자가 실제 응답에 같은 코드를 쓰도록 MUST로 묶은 것, 정말 일반적인
문제는 그냥 상태 코드로 표현하라고 한 것, PUT에 대한 403이 자기 설명적이므로 “쓰기 접근 불허”
타입은 불필요하다고 명시한 것은 모두 하나의 목표를 향한다 — HTTP의 기존 의미 체계를 API가
잠식하지 못하게 막는 것이다.
표준은 오류 형식을 주는 대신 오류 형식을 만들려는 충동을 흡수하는 배수구 역할을 자임한다.

이 독해가 명세의 자기 제한도 설명한다.
“이 형식으로 오류를 전달하지 않기로 한 애플리케이션이라도 이 설계를 검토하면 기존 형식으로 오류를
전달할 때 마주칠 설계 결정에 도움이 될 수 있다”는 문장은 표준 문서로서는 이례적으로 약한
주장이다.
자기 형식의 채택률보다 자기가 막으려는 실패의 감소를 중시하는 태도이며, 이는 Nottingham이
HTTP 명세 작업에서 일관되게 취해 온 자세다.

이 배수구 기능이 실무에서 어떻게 소비되는지를 Lobste.rs의 한 증언이 잘 보여 준다.
dvogel은 여러 API 프로젝트에 이것을 구현했는데 주된 동기가 HTTP 코드를 둘러싼(대부분 자전거
색깔 논쟁인) 다툼에서 벗어나기 위해서였다고 밝힌다 — 단순한 진실은 일부 HTTP 코드를 과적하거나
빠른 디버깅을 위한 추가 메타데이터가 필요하다는 것이며, 그 목적에서 이 명세는 권위에 호소할
좋은 인용처였다는 것이다[^dvogel].
표준의 실제 효용이 기술적 우수성이 아니라 논쟁 종결 도구라는 이 관찰은 명세의 자기 규정과
정확히 맞아떨어진다.
다만 dvogel은 같은 문단에서 이 명세가 새로운 자전거 색깔 논쟁의 가능성도 많이 열어 준다고
덧붙이는데, 이 유보는 뒤의 비평에서 다룰 문제들 — 무엇을 확장에 넣을지, 표준 멤버와 이름이
충돌할 때 무엇을 양보할지 — 을 미리 가리킨다.

### JSON에 하이퍼미디어가 없다는 문제의 잔여물

`type`을 URI로 만든 결정은 취향이 아니라 계보의 산물이다.
2007년 《RESTful Web Services》가 XML을 전제로 썼고 2013년 《RESTful Web APIs》가 JSON에
링크와 폼이 없다는 문제를 정면으로 다뤄야 했던 흐름[^ref-rwa] 속에서, 오류 본문도 같은 문제를
겪는다 — JSON에는 “이 오류가 무엇인지”를 가리킬 표준 수단이 없다.

URI를 식별자로 쓰는 것은 그 빈틈을 메우는 가장 웹다운 답이다.
전역 유일성을 중앙 등록 없이 얻고, 원하면 그 주소가 문서를 내놓게 만들 수 있다.
HN에서 eyelidlessness가 `type`이 XML 네임스페이스 URI를 강하게 연상시킨다고 관찰한 것은[^eyelidlessness]
정확한 계보 인식이며, 실제로 부록 B의 XML 형식은 `urn:ietf:rfc:7807` 네임스페이스를 쓴다.

그런데 이 결정은 식별자와 문서 주소를 같은 문자열로 합친다.
명세는 이 합침이 만드는 긴장을 알고 있어서 소비자가 자동 역참조를 하지 않아야 한다고(SHOULD NOT)
제한하고, 동시에 그 URI가 HTML 문서로 해소되기를 권장한다(SHOULD).
즉 기계는 방문하지 말고 사람만 방문하는 URL이 된다 — 이 어색한 지위가 뒤에서 다룰 문제의
뿌리다.

### 레지스트리 도입은 전작이 실패한 지점에 대한 답이다

전작 RFC 7807이 2016년에 나온 뒤 7년간 무엇이 부족했는지를 부록 D의 세 항목이 알려 준다.
가장 앞에 놓인 것이 레지스트리이며, 이것은 “각자 URI를 만들라”는 전작의 태도가 상호운용을
만들어내지 못했다는 인정이다.

문제는 이렇게 정리된다 — 모든 API가 자기 도메인의 URI로 “인증 실패”를 식별하면, 형식은
통일됐지만 의미는 하나도 통일되지 않는다.
클라이언트는 여전히 API마다 타입 URI 목록을 따로 익혀야 하고, 표준이 준 것은 파서 하나를
재사용할 수 있다는 것뿐이다.
레지스트리는 널리 쓰이는 타입 URI를 공통 자산으로 만들어 “공통 의미를 활용”하게 하려는
시도다.

같은 맥락에서 3.1.1절이 역참조 불가 URI 지침을 새로 넣은 것도 읽힌다.
tag URI로도 식별할 수 있다고 허용하면서도 해소 가능한 URI를 권장하는 이유를 명세가 직접
설명하는데, 그 논거가 흥미롭다 — 나중에 타입 URI를 해소해 오류 정보를 알아내는 도구를 도입하면,
그 능력을 쓰려면 해소 가능한 URI로 갈아타야 하고 그것은 문제 타입에 새 정체성을 부여하는 것이므로
호환성을 깨는 변경이 된다.
표준이 아직 존재하지 않는 도구를 위해 지금의 명명 방식을 제한하고 있는 것이다.

## 비평

### 레지스트리는 사람들이 실제로 필요한 오류를 담을 수 없다

4.2절이 새 레지스트리의 핵심 성과로 제시되지만, 같은 절이 그 레지스트리의 유용성을 스스로
봉쇄한다 — 벤더 특화, 애플리케이션 특화, 배치 특화 값은 등록할 수 없다.

이것이 치명적인 이유는 실무 API 오류의 압도적 다수가 정확히 그 세 범주에 속하기 때문이다.
“잔액이 부족하다”, “이 결제 수단은 이 국가에서 지원되지 않는다”, “이 필드가 스키마와 맞지
않는다” 같은 오류는 애플리케이션 특화다.
반대로 애플리케이션에 특화되지 않은 정말 일반적인 문제는 명세 자신이 4절에서 “보통 그냥 상태
코드로 표현하는 편이 낫다”고 배제해 버렸다.
그래서 레지스트리에 들어갈 수 있는 것은 애플리케이션 특화도 아니고 상태 코드로 충분하지도 않은
좁은 틈새뿐이며, 명세 발행 시점에 그 틈새에 등록된 것은 `about:blank` 하나다.

`about:blank`가 등록된 유일한 항목이라는 사실은 상징 이상이다.
그것은 “이 문제에는 HTTP 상태 코드 이상의 의미가 없다”는 타입, 즉 문제 타입의 부재를 뜻하는
타입이다.
전작이 상호운용을 못 만들었다는 진단에 대한 답으로 레지스트리를 도입했지만, 그 레지스트리가
담을 수 있는 것은 “추가 의미 없음”이었다.
HN에서 sublinear가 이 구조를 정확히 찔렀다 — 오류를 제대로 처리하려면 오류 종류의 망라적 열거가
있어야 하는데 이 RFC는 그것을 완전히 우회하며, 앱 개발자가 결국 자기 열거 체계를 만들어 확장에
넣어야 한다면 이미 쓰던 JSON을 그냥 응답하는 것보다 나을 게 없다는 것이다[^sublinear].
tl은 `type`이 전역 유일하므로 서버가 옛 클라이언트에 새 오류를 보낼 수 있고, 표준에 넣으면
라이브러리 개발자가 오류 처리를 아예 하기라도 할 확률이 오른다고 반박했지만[^tl] — 이 반박은
형식의 가치를 옹호하는 것이지 레지스트리의 가치를 옹호하는 것이 아니다.

### 명세는 자기가 대체한 문서의 식별자를 그대로 안고 있다

RFC 9457은 RFC 7807을 대체(Obsoletes)한다고 첫 페이지에 선언한다.
그런데 명세 본문의 규범적 요소 상당수가 여전히 7807을 가리킨다.

부록 B의 RELAX NG 스키마는 `default namespace ns = “urn:ietf:rfc:7807”`로 시작하고, XML 예제의
루트 요소도 `<problem xmlns=“urn:ietf:rfc:7807”>`이다.
부록 A의 JSON Schema는 `“title”: “An RFC 7807 problem object”`를 그대로 달고 있다.
XML 네임스페이스가 안정 식별자여야 하므로 바꾸지 않은 것은 기술적으로 옳은 선택이며 실제로
바꿨다면 호환성을 깼을 것이다 — 그러나 명세가 그 이유를 한 줄도 설명하지 않는다는 것은 별개
문제다.
`about:blank` 등록이나 상대 URI 위험처럼 사소한 사항까지 이유를 붙여 설명하는 문서가, 자기
네임스페이스가 대체된 RFC 번호를 가리키는 이유는 침묵으로 넘긴다.

이 침묵의 비용은 구현자가 치른다.
7807을 읽은 적 없는 개발자가 9457만 보고 XML 형식을 구현하려면 왜 네임스페이스가 문서 번호와
다른지 스스로 추측해야 하고, 이 추측은 “문서가 낡았나”라는 잘못된 결론으로 쉽게 간다.
부록 A의 JSON Schema 제목은 더 나쁘다 — 그것은 안정 식별자가 아니라 그냥 갱신을 빠뜨린 문자열
이며, 비규범적 부록이라는 사실이 오류를 정당화하지는 않는다.
문서가 자기 개정 이력을 부록 D에 세 항목으로 정리하면서 자기 본문의 옛 번호 세 곳은 정리하지
않은 것은, 명세를 “대체”한다는 선언이 문서 헤더에서만 참이라는 뜻이다.

### `status` 멤버는 명세 스스로 무용함을 입증하고도 남았다

`status`에 대한 명세의 서술은 이례적으로 방어적이다.
있어도 참고용일 뿐이고(advisory), 생성자는 실제 응답에 같은 코드를 반드시 써야 하며(MUST),
보안 절은 이 멤버가 정보를 중복해 어긋날 가능성을 만들고 어느 쪽이 우선하는지 분명하지 않으며
일반 HTTP 소프트웨어가 이 멤버를 알거나 존중할 가능성은 낮다고 적는다.

이만큼의 경고를 붙였다면 그 멤버를 유지할 근거가 강해야 한다.
명세가 제시하는 용례는 둘이다 — 중개자나 캐시가 상태 코드를 바꿨을 때 원래 코드를 알아내는 것,
그리고 메시지 본문이 HTTP 정보 없이 저장됐을 때다.
첫째 용례는 사실상 성립하지 않는다.
중개자가 상태 코드를 바꾸는 상황에서 클라이언트가 본문의 `status`를 믿고 원래 코드를 복원한다면,
그것은 중개자의 변경을 무시하는 것이며 명세가 MUST로 보장하려던 “형식을 이해하지 못하는 일반
HTTP 소프트웨어도 올바르게 동작한다”는 성질과 정면으로 충돌한다.
둘째 용례 — 로그에 본문만 남는 경우 — 는 실재하지만, 그것은 로깅 시스템이 상태 코드를 같이
기록하지 않는다는 로깅의 결함이며 와이어 형식이 감당할 문제가 아니다.

결과적으로 이 멤버는 좁은 편의 하나를 얻는 대가로 영구적인 불일치 표면을 만든다.
두 곳에 같은 값을 쓰는 필드가 있으면 언젠가 달라지고, 명세가 우선순위를 정하지 않았으므로 그때
클라이언트의 동작은 구현마다 갈린다.
차라리 `status`를 아예 빼고 필요한 곳에서 확장으로 넣게 하는 편이 명세의 다른 원칙 — 표준
멤버는 최소로, 나머지는 확장으로 — 과 일관됐을 것이다.

### 확장 이름 규칙은 거의 아무도 쓰지 않는 형식을 위해 JSON 사용자에게 세금을 매긴다

4절은 확장 멤버 이름이 문자로 시작하고 문자·숫자·`_`로 구성되고 세 글자 이상이기를 권장한다
(SHOULD).
3.2절은 그 이유를 밝힌다 — XML 형식에서 쓰려면 XML의 Name 규칙에 맞아야 한다는 것이다.

이 제약의 분배가 불공평하다.
`application/problem+json`을 쓰는 압도적 다수의 구현이 XML 직렬화를 할 일이 없는데도, 하이픈이
들어간 이름이나 두 글자 이름(`id`처럼 이미 관행이 된 이름)을 피하라는 지침을 받는다.
명세가 “JSON 이외의 형식으로 직렬화될 수 있도록”이라고 적은 이유는 정직하지만, 그 가능성의
현실적 무게를 명세는 검토하지 않는다.
HN 스레드에서 XML 형식의 존재 자체가 반복해서 화제가 됐다는 사실이 그 무게를 짐작하게 한다 —
hcarvalhoalves가 JSON 본문 기반이면 HTTP 얘기가 아니지 않냐고 물었을 때 mholt가 “HTTP API를
위한 것이고 XML도 있다”고 답했고[^mholt-xml], eyelidlessness는 XML 형식이 XML로서는 놀랄 만큼
제약적이고 특이하다고 관찰했다[^eyelidlessness-xml].

더 근본적인 문제는 이 규칙이 잘못된 층에 놓였다는 것이다.
JSON 표현과 XML 표현의 매핑 제약이라면 부록 B의 문제여야 하는데, 4절의 새 문제 타입 정의 규칙에
들어가 있다.
그 결과 XML을 전혀 고려하지 않는 문제 타입 저자도 이 규칙을 읽고 따를 것을 권고받으며, 확장
이름을 짓는 흔한 실무 결정이 쓰지 않는 직렬화 형식의 문법에 묶인다.

### 표준 멤버와 확장이 같은 층에 섞이는 설계는 충돌을 예약한다

문제 상세 객체는 `type`·`status`·`title`·`detail`·`instance`와 확장 멤버를 같은 평면에 놓는다.
이 결정이 파싱을 단순하게 만드는 대신 이름 충돌을 구조적으로 보장한다.

HN에서 WirelessGigabit이 정확히 이 점을 문제 삼아, 표준 필드를 자유 형식의 단일 속성으로 옮겼다면
파싱이 더 쉬웠을 것이라고 지적했다[^WirelessGigabit].
no_circuit은 더 구체적인 비교를 들었다 — 다른 RPC 명세들처럼 사용자 정의 필드를 하위 객체에
넣지 않은 것이 아쉽고, 사람 읽기용 메시지는 `detail`이 아니라 `message`여야 했으며 불투명한
타입을 담는 `details` 필드가 따로 있어야 했다는 것이다.
그러면서 실질적 문제를 짚었다 — 이미 오류 타입을 가진 시스템은 `type`·`title`·`status`·`detail`·`instance`와
필드 이름이 충돌할 수 있고, 그러면 실제 오류를 정의상 표준이 아닌 확장 멤버에 넣게 된다[^no_circuit].

이 비판이 무게를 갖는 이유는 명세가 그 충돌을 해결할 도구를 주지 않기 때문이다.
값 타입이 맞지 않으면 멤버를 무시한다는 규칙(3.1절)은 타입 불일치만 다루고, 의미 충돌 —
애플리케이션의 `status`가 HTTP 상태 코드가 아닌 도메인 상태를 뜻하는 흔한 경우 — 은 다루지
않는다.
기존 오류 형식을 문제 상세로 옮기려는 팀은 자기 필드 이름을 바꾸거나, 자기 데이터 전체를 하나의
확장 객체 안으로 밀어 넣어 명세의 평면 설계를 우회하는 수밖에 없다.
후자를 택하면 남는 것은 `application/problem+json`이라는 미디어 타입 이름뿐이며, 그때 이 표준의
실질적 기여는 오류 본문에 미디어 타입을 붙였다는 것으로 축소된다.

## 인사이트

### 이 표준이 표준화한 것은 오류의 의미가 아니라 오류를 담는 봉투다

RFC 9457을 채택한 프레임워크는 많다.
HN에서 radicalriddler는 ASP.NET이 .NET 6에 통합했고 서버가 어떤 오류를 돌려줄지 생각하기가 훨씬
단순해졌다고 했고[^radicalriddler], techdragon은 ASP.NET 6 실험에서 쓰면서 이것에 RFC가 있다는
사실조차 몰랐고 그냥 오류 메시지가 좋아서 쓰고 있었다고 했다[^techdragon].
mholt는 ACME(RFC 8555)가 이것을 쓰기 때문에 클라이언트 측을 구현했다고 밝혔다[^mholt].
이 저장소의 Spring 노트도 `ResponseStatusException`이 RFC 9457 지원을 위해 계층을 바꿨다는 사실을
기록한다[^ref-spring].

그런데 이 채택이 만들어내는 것은 봉투의 통일이지 의미의 통일이 아니다.
클라이언트가 어느 API에서든 `title`·`detail`을 꺼내 보여줄 수 있게 된 것은 진짜 이득이지만 —
treve가 자기 REST 클라이언트에서 정확히 그 일을 한다고 했듯이[^treve] — 그것은 오류를 사람에게
전달하는 문제를 푼 것이고, 프로그램이 오류에 따라 다르게 행동하는 문제는 그대로 남는다.
후자는 `type` URI를 API별로 익혀야 하며, 앞서 본 대로 레지스트리는 그 URI를 공통화하지 못한다.

2차 효과가 여기서 나온다.
프레임워크가 기본으로 `application/problem+json`을 내보내기 시작하면, 그 API는 “표준 오류를
쓴다”고 말할 자격을 얻는다.
techdragon이 RFC의 존재조차 모르고 썼다는 것은 이 효과의 순한 형태이지만, 험한 형태는 API 문서에
“RFC 9457 준수”라고 적힌 것을 본 클라이언트 개발자가 오류 처리 코드를 재사용할 수 있다고 믿는
것이다.
실제로 재사용 가능한 것은 파서이고, 분기 로직은 매번 새로 써야 한다.
표준 준수 표기가 상호운용의 증거로 읽히는 순간, 표준은 상호운용을 만드는 대신 상호운용을
확인하는 일을 방해한다.

### 이 명세는 REST 진영이 SOAP Fault를 20년 걸려 다시 발명한 결과다

문제 상세의 구조 — 문제 종류의 식별자, 짧은 사람 읽기용 문구, 발생별 상세, 확장 영역 — 는
1999년 SOAP 1.1의 Fault와 거의 같은 뼈대다.
`faultcode`가 종류를, `faultstring`이 사람 읽기용 요약을, `detail`이 애플리케이션 특화 정보를
담았고, `faultcode`는 QName이었으므로 XML 네임스페이스 URI로 전역 유일성을 얻었다 — RFC 9457의
`type`이 URI인 것과 같은 발상이다.

《RESTful Web Services》가 SOAP·WS-\* 스택을 웹에 맞선 무거운 아키텍처로 규정하고 한 장을 들여
비판한 것이[^ref-soap] 2007년이다.
그 비판의 핵심은 오류 봉투가 나쁘다는 것이 아니라, 웹이 이미 제공하는 것(상태 코드, 콘텐츠 협상,
URI)을 재발명하거나 무시한다는 것이었다.
RFC 9457이 SOAP Fault와 다른 지점은 정확히 거기다 — 상태 코드를 대체하지 않고 그 위에 얹으며,
콘텐츠 협상으로 형식을 고르고, 정말 일반적인 문제는 상태 코드에 맡기라고 스스로 물러선다.

그러나 이 우회로가 무엇을 잃었는지도 정직하게 봐야 한다.
SOAP은 WSDL이라는 기계 판독 가능한 계약이 있었고, 그 계약 안에 어떤 fault가 발생할 수 있는지
열거돼 있었다.
RFC 9457에는 그런 열거가 없다 — sublinear가 지적한 “망라적 열거의 부재”는 이 명세의 누락이라기보다
REST 진영이 계약 언어를 버리면서 함께 버린 능력이다.
20년의 우회로 끝에 얻은 것은 더 가볍고 웹과 싸우지 않는 오류 봉투이고, 잃은 것은 “이 API가 어떤
오류를 낼 수 있는가”를 기계가 미리 아는 능력이다.
OpenAPI가 그 능력을 부분적으로 되찾아 오려 하지만, 오류 타입 열거를 OpenAPI 문서에 적는 일은
RFC 9457이 요구하지도 검증하지도 않는 별개의 규율이다.

### 타입 URI를 식별자와 문서 주소로 겸용하게 만든 결정은 시간이 지날수록 비용을 청구한다

명세는 `type`을 1차 식별자로 반드시 쓰라고 하고(MUST), 해소 가능한 URI를 권장하고, 그 URI가
문제 해결법을 담은 HTML로 해소되기를 권장하며, 동시에 소비자가 자동 역참조하지 않아야 한다고
한다(SHOULD NOT).
네 규칙을 합치면 하나의 문자열이 두 역할을 겸한다 — 영구 식별자이면서 문서의 현재 주소다.

이 겸용의 문제는 두 역할의 수명이 다르다는 것이다.
식별자는 절대 변하면 안 되고, 문서 주소는 회사 도메인이 바뀌고 문서 사이트가 개편되고 제품이
매각되면 반드시 변한다.
명세도 이 긴장을 감지해 타입 URI가 “자기 통제 아래 있고 시간이 지나도 안정적이어야 한다”고
당부하지만, 당부는 도메인 만료를 막지 못한다.
아이러니는 명세 자신의 예시에서 드러난다 — 레지스트리 접두사로 `https://iana.org/assignments/http-problem-types#`를
쓸 수 있다고 하면서 “그 URI들은 해소되지 못할 수 있다”고 곧바로 덧붙인다.
표준 문서가 자기가 권장하는 접두사조차 해소를 보장하지 못한다고 적는 것이다.

이 저장소의 다른 문서에서 본 사례가 이 위험이 가설이 아님을 보여 준다.
《RESTful Web APIs》의 Maze+XML 명세는 저자가 공개한 원 사이트가 사라져 지금은 예제 코드의 실제
출력과 제3자 구현으로 역추적해야 확인할 수 있다[^ref-maze].
같은 일이 문제 타입 URI에서 일어나면 결과는 더 조용하고 더 나쁘다 — 클라이언트는 여전히 그
문자열로 정확히 분기하고 코드는 잘 돌아가는데, 그 문자열이 무엇을 뜻하는지 설명하는 문서만
사라진다.
식별자로서는 살아 있고 문서로서는 죽은 URL이 축적되는 것이며, 이때 남는 것은 `title` 필드에
담긴 한 줄뿐이다.
명세가 `title`을 “타입 URI의 의미를 모르고 알아낼 수도 없는 사용자를 위한 참고용”이라고 규정한
것은 이 미래를 이미 내다본 문장으로 읽힌다.

### 기계 판독성이라는 이 명세의 전제는 소비자가 사람에서 에이전트로 바뀌면서 비로소 시험대에 오른다

RFC 9457의 설계는 사람과 기계의 역할을 뚜렷이 나눈다.
`title`과 `detail`은 사람 읽기용이고 소비자는 `detail`을 파싱하지 않아야 하며(SHOULD NOT), 기계가
쓸 정보는 `type`과 확장에 넣어야 한다.
타입 URI의 문서는 사람이 읽고, 기계는 그 URL을 방문하지 않아야 한다.

이 분업은 클라이언트가 사람이 작성한 프로그램이라는 전제 위에 서 있다.
사람이 문서를 읽고 분기 코드를 쓰므로, 기계용 정보는 최소한의 식별자로 충분하고 나머지 설명은
사람의 언어로 두면 된다는 것이다.
LLM 기반 에이전트가 API 클라이언트가 되면 이 전제가 무너진다 — 에이전트에게는 `detail`의 산문이
가장 유용한 신호이고, 파싱하지 말라는 권고는 의미를 잃으며, 타입 URI를 역참조해 문서를 읽는 것이
정확히 하고 싶은 일이 된다.
명세가 자동 역참조를 금하다시피 한 이유(SHOULD NOT)는 무한 요청 증폭과 부하 우려였는데, 그
우려는 정당하지만 대안을 제시하지 않는다.

여기서 이 표준의 가치가 뜻밖의 방향으로 재평가된다.
에이전트에게 필요한 것은 구조화된 오류가 아니라 자기 서술적(self-describing) 오류이며, RFC 9457은
사람용으로 남겨 둔 `title`·`detail` 때문에 오히려 그 요구에 잘 맞는다.
반대로 이 명세가 기계용으로 설계한 부분 — URI 식별자, 확장 멤버 — 은 에이전트에게는 상대적으로
덜 중요하다.
설계 의도와 실제 효용이 어긋난 것이며, 이 어긋남은 명세를 개선해서 좁힐 문제가 아니라 소비자가
바뀌면 같은 명세의 어느 부분이 값진지도 바뀐다는 사실로 받아들여야 한다.
그리고 이 관점에서 보면 `about:blank`가 유일한 등록 타입이라는 앞서의 빈약함이 다르게 읽힌다 —
타입 URI가 상호운용을 만들지 못한 자리를, 사람용으로 쓰인 산문이 대신 메우게 될 수 있다.
