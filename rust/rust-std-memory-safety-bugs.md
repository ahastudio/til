# Rust 표준 라이브러리의 메모리 안전성 버그

원문: [Memory Safety Bugs in Rust Standard Library](https://forge-blog.github.io/posts/rust-std-memory-safety/)

HN 토론: <https://news.ycombinator.com/item?id=50478701> (158점, 119개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/plreds/memory_safety_bugs_rust_standard_library> (2점, 0개 댓글)

## 요약

Microsoft FORGE Lab의 Yechan Bae가 2026년 11월 9일에 올린 글이다.
이 문서는 글 전문을 읽었다.
글이 링크한 Rust 이슈와 수정 변경은 열지 않았다.
이 문서는 버그를 재현하는 코드를 옮기지 않고, 글이 분류한 원인과 교훈 중심으로 요약한다.

글의 요지는 이렇다.
FORGE Lab이 Rust 표준 라이브러리(std와 core)에서 여러 메모리 안전 문제를 찾았고, 완전히 안전한 Rust 코드만으로 정의되지 않은 동작(undefined behavior)을 일으키는 경우도 있었다.
연구는 Hyenas(코드명 MDASH의 연구용 선행 판)라는 AI 기반 취약점 스캔 시스템의 도움을 받았고, 연구자가 근본 코드를 조사하고 버그를 재현하고 보안 영향을 평가했으며 Rust 관리자와 함께 보고하고 고쳤다고 한다.
글은 컴파일러 자체의 오류(잘못된 컴파일, 타입 시스템의 구멍)는 다루지 않고 표준 라이브러리의 unsafe 코드가 만드는 건전성(soundness) 버그만 다룬다.
게시 시점에 연구팀이 보고한 이슈 중 둘이 열려 있다고 밝힌다.

배경 설명은 이렇다.
Rust의 안전 API는 소규모 unsafe 조각 위에 만들어지고(Vec과 String 포함), 그 API는 안전한 코드가 어떻게 쓰든 정의되지 않은 동작을 일으킬 수 없어야 건전하다.
글은 이 약속을 지키기가 보기보다 어렵다는 예를 든다. 호출자가 고르는 타입의 `AsRef` 구현이 첫 호출과 둘째 호출에서 다른 슬라이스를 돌려주면, 두 호출이 같은 값을 준다고 믿은 unsafe 코드가 범위 밖을 읽을 수 있다.
버그는 세 가지 잘못된 신뢰로 나뉜다.

- 패턴 1, 코드가 패닉하지 않는다는 신뢰: unsafe 코드는 불변식을 잠깐 깨고 나중에 복구하는 경우가 많은데, 그 사이에 패닉이 나면 되감기(unwinding)가 소멸자를 실행하며 깨진 불변식을 노출한다(패닉 안전성 버그). 예로 nightly API `Iterator::map_windows`의 버퍼 복제 중 사용자 `clone`이 패닉하면 초기화되지 않은 값을 버리게 되는 문제를 든다. 수정은 새 버퍼를 다 쓸 때까지 `ManuallyDrop`에 담아 되감기 때 누수로 처리하는 것이다. 새로 안정화된 Allocator API는 할당자가 되감기를 하면 표준 라이브러리 곳곳이 건전하지 않게 되는 문제가 있어, 개별 수정 대신 구현자가 되감기를 하지 않아야 한다는 규칙과 함께 Rust 1.100(11월 12일)에서 안정화된다고 한다.
- 패턴 2, 사용자 구현이 올바르다는 신뢰: unsafe 코드가 호출자가 준 비교자나 트레이트 구현을 부른다. 그것은 안전한 코드이지만 올바르다는 뜻은 아니다. C++에서는 `std::sort`가 엄격 약순서를 요구하고 어기면 정의되지 않은 동작인데, Rust의 `sort_by`는 같은 비교자에서도 논리 오류일 뿐 정의되지 않은 동작은 아니어야 한다. 책임이 unsafe 코드 쪽에 있다는 것이다. 예로 nightly `Pattern` 트레이트의 `as_utf8_pattern`을 믿고 한 바이트 치환 빠른 경로를 탄 `str::replace`가 UTF-8이 아닌 `String`을 만들 수 있었다. 수정은 `StringPattern`이 `&[u8]` 대신 `&str`을 갖게 해 타입이 UTF-8을 보장하게 한 것이다. 더 일반적 교훈은 호출 결과를 한 번만 받아 보관하거나 검증하거나 위조할 수 없는 타입에 담고, 안 되면 트레이트를 unsafe로 만들어 구현자가 약속하게 하는 것이다. `join`은 2020년에 한 번 고쳐졌지만(CVE-2020-36323) 2026년 4월에 다른 경로가 다시 고쳐져야 했다.
- 패턴 3, 하부 시스템에 대한 신뢰: 운영체제와 C 라이브러리의 프로세스 전역 상태(신호 스택, 메모리 매핑, 환경 변수)를 믿는 경계이다. 정적 분석이 이 모든 주변 동작을 모델링해야 해서 찾기 어려웠는데, 글은 AI 에이전트가 실행 환경을 충분히 알아 이 영역을 탐색할 만하게 만든다고 쓴다. 예로 자식 스레드가 `process::exit`를 부르면 실행 중인 메인 스레드의 대체 신호 스택 매핑이 해제되는 문제(2015년부터 있었고 스택 오버플로 시 안내 메시지 대신 단순한 분할 오류로 죽는다)와, `CommandExt::exec`가 읽기 잠금만 잡고 프로세스 전역 `environ`을 쓰는 문제를 든다. 글은 전자의 악용 가능성을 따져 보았고 실제 조건이 매우 까다로워 실질적 악용은 가능성이 낮다고 평가했으며, 이 평가가 다른 이슈에 자동으로 적용되지는 않는다고 밝힌다. 다른 사람이 보고한 `process::exit`와 스레드 로컬 소멸자의 이중 해제 문제도 소개한다.

결론은 이렇다.
Rust의 기준(안전한 API는 어떻게 써도 정의되지 않은 동작을 일으키면 안 된다)은 C와 C++보다 엄격하여 일대일 비교가 어렵고, 표준 라이브러리의 건전성 버그가 곧 이를 쓰는 프로그램의 취약점은 아니다. 각 버그는 정확한 순간의 패닉이나 의도적으로 잘못된 구현이나 자식 스레드의 `process::exit` 같은 특이한 조건이 필요하다고 쓴다.
글은 nightly 과정이 동작한다고 평가한다. 많은 보고가 불안정 API 단계에서 잡혀 안정화 전에 설계가 바뀌었다는 것이다. 동시에 안정판에 이른 버그와 불완전한 수정이 있었다고 한다.
마지막으로 FORGE Lab이 이 연구를 MDASH와 Microsoft Defender, Perception이라는 자사 보안 제품과 연결한다고 밝힌다.

## 분석

### 중심 주장은 건전성의 책임이 항상 unsafe 코드 쪽에 있다는 것이다

세 패턴의 공통점은 unsafe 코드가 주변 코드에 대한 가정을 문서화하지 않고 믿었다는 것이다.
패턴 2의 비교가 이를 선명하게 보여 준다. 같은 잘못된 비교자에서 C++은 정의되지 않은 동작이고 Rust는 논리 오류에 그쳐야 한다.
HN의 한 댓글도 같은 점을 짚었다. 신뢰하는 사용자 코드가 악의적이라는 반박에, 안전 Rust의 목표는 안전한 트레이트의 (잘못된) 구현에서도 정의되지 않은 동작이 없는 것이라는 답이다.[^mswphd]
다른 답글은 충분히 위장된 악의는 무능과 구별되지 않으므로 악의적이어서 안 센다고 할 수 없다고 했다.[^pwdisswordfishq]

### 새 영역은 정적 분석이 아니라 환경 지식이다

패턴 3의 버그가 오래 살아남은 이유를 글은 Rust 타입 시스템 밖의 지식(커널 호출, C 라이브러리 상태)이 필요하기 때문이라고 설명한다.
그리고 언어 모델이 이 경계를 검사하기에 적합하다는 가설을 내놓는다.
이 가설은 글 한 편의 두세 사례에서 나온 것이고, 도구의 발견율이나 거짓 양성은 제시되지 않는다.

## 비평

### 이 발견이 Rust의 안전성에 대해 무엇을 말하는지의 해석이 갈린다

한 댓글은 이런 발견이 이상하거나 스캔들이 아니라고 했다. Rust 프로젝트에 건전성 문제 표시가 붙은 이슈가 178개 열려 있고 상당수는 nightly에만 있지만 출시 전에 못 잡히는 경우도 있다는 것이다.[^simonask]
답글은 이것이 Rust가 메모리 안전하지 않다는 증거라고 했고,[^cowlevel]
이에 구현이 완전히 무결해야만 메모리 안전한 것이냐는 반문이 나왔다.[^hmry]
이 문서는 178개라는 수를 확인하지 못했다.
글은 같은 주제에 대해 조심스럽다. 표준 라이브러리의 건전성 버그가 곧 프로그램의 취약점은 아니라고 쓴다.

### 패닉 되감기가 문제의 뿌리라는 의견

한 댓글은 패닉 안전성을 쫓는 일이 C++의 예외 안전성과 같은 저주이고 이해를 넘는 복잡성을 낳는다고 했다.[^codeflo]
답글들은 되감기가 있는 패닉이 Rust의 가장 큰 죄이며 숨은 반환 경로를 만든다고 했고,[^mindspunk]
기본을 즉시 프로세스 종료로 하자는 의견도 있었다.[^panzerschrek]
반론은 그렇게 하면 테스트 하니스나 플러그인 시스템처럼 패닉 뒤에도 계속 돌려야 하는 용도에 맞지 않는다는 것이었고,[^xirdus]
다른 답글은 되감기 없는 Rust는 10년 전의 복잡도 예산에는 맞지 않았지만 지금은 고려할 만하다고 했다.[^masklinn]
한 댓글은 패닉 중단 외에는 쓰지 말라고도 했다.[^ozgrakkurt]
글은 패닉 처리 방식 자체의 변경을 제안하지 않고, 불변식을 깨는 동안 호출하는 코드를 조심하는 규율을 권한다.

### 인덱싱 패닉 같은 설계 논의는 주제를 벗어났다

한 댓글은 벡터 인덱싱이 범위를 벗어나면 `Some`이 아니라 패닉하는 것이 Rust답지 않다고 했고,[^hingler36]
답글들은 이는 메모리 안전 버그가 아니며 `get`이 이미 있다고 했다.[^chai-t-rex][^namjh]
글의 범위(건전성 버그)와 관련이 없는 논의이다.

### 도구 홍보와 AI 언급에 대한 반응

한 댓글은 이를 AI의 좋은 쓰임이라고 했고,[^not_a_bot_4sho]
다른 댓글은 AI 이슈가 프로젝트에서 막힌 이유라고 했다. 이는 이 글과 직접 관련이 있는 서술이 아니다.[^ozgrakkurt]
글은 도구가 어떤 발견에 얼마나 기여했는지를 구분하지 않는다. 연구자가 근본 코드를 조사하고 재현하고 보안 영향을 평가했다고만 쓴다.
이 문서는 Hyenas와 MDASH의 성능에 대한 독립적 자료를 찾지 못했다.

## 인사이트

### unsafe 코드를 쓰는 사람이 가져갈 세 가지 규율

글의 교훈을 규율로 줄이면 이렇다.
호출하는 모든 코드(`clone`, `drop`, 비교, 클로저, 반복자 메서드)를 조기 종료 가능성으로 보고, 불변식을 깨기 전에 패닉할 수 있는 작업을 끝내거나 깨진 상태를 되감기에 안전하게 만든다.
사용자 구현의 성질에 기대야 하면 한 번만 부르고 결과를 보관하거나 검증하거나 타입에 담고, 안 되면 트레이트를 unsafe로 만든다.
프로세스 전역 상태(환경, 신호 스택)에는 다른 스레드와 C 라이브러리가 언제든 접근할 수 있다고 가정한다.

### 불완전한 수정이 반복되는 패턴을 점검하라

`join`이 2020년에 한 번 고쳐지고 2026년에 다른 경로가 또 고쳐진 사례는, 한 경로의 수정이 같은 함수의 다른 경로를 덮지 못한다는 것을 보여 준다.
`Pattern`의 다른 문제 두 개가 아직 열려 있다는 서술도 같은 맥락이다.
같은 부류의 버그를 고칠 때는 그 부류의 불변식을 문서로 명시하는 것이 개별 수정보다 효과적이라는 읽기가 가능하다. 이는 이 문서의 해석이다.

### 확인할 관찰

이 글의 평가를 가를 관찰은 세 가지이다.
열려 있는 이슈(`Pattern` 관련 둘 등)가 어떻게 해결되는지,
`exec`와 `environ`의 안정판 버그 수정이 병합되는지,
같은 방법이 다른 기반 라이브러리에서도 비슷한 수의 건전성 버그를 찾는지이다.
셋 모두 이 문서가 확인하지 못했다.
