# curl Rust 재작성 사례

원문: [Actual curl rewrites in rust](https://daniel.haxx.se/blog/2026/11/17/actual-curl-rewrites-in-rust/)

HN 토론: <https://news.ycombinator.com/item?id=50525713> (32점, 7개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/1dj9w1/actual_curl_rewrites_rust> (117점, 68개 댓글)

GN 토론: <https://news.hada.io/topic?id=37377>

## 요약

curl 유지보수자 Daniel Stenberg가 2026년 11월 17일 블로그에 쓴 글이다.
curl과 libcurl을 Rust로 다시 쓴 프로젝트가 올가을 둘 나타난 일을
그가 어떻게 보는지 밝힌다.
하나는 몇 달 전에 보인 urlx이고, 다른 하나는 11월에 나온
“curl, rewritten in Rust”다.
뒤쪽은 이름도 curl을 그대로 쓰며, 만드는 데 8,600달러를 썼다고 주장한다.

글의 중심 주장은 코드를 한 번 쓰는 일은 문제였던 적이 없다는 것이다.
에이전트 여럿이 몇 주 만에 해낸 일이 놀랍기는 하지만,
curl은 문서가 잘 되어 있고,
이 API를 쓰는 오픈 소스 응용이 수백 개이며,
구현을 검증할 시험이 수천 개이고,
세상의 AI가 curl 코드를 오래 학습했기 때문에 가능했다고 그는 본다.
C 코드가 있으니 AI는 Rust로 옮기고
시험이 통과할 때까지 다듬으면 된다는 설명이다.

curl은 수많은 결정과 시간, 사용자, 되먹임이 쌓인 결과이므로
어느 한순간의 curl을 따라 만드는 일은 완벽한 명세가 있어 할 만하다고 쓴다.
다만 그 뒤로 이어지는 수정과 개선이 프로젝트를 살아 있게 한다고 말한다.
글이 든 수치는 다음과 같다.

| 항목                        | 글이 적은 내용                                           |
| --------------------------- | -------------------------------------------------------- |
| 재작성 비용                 | 8,600달러(재작성 쪽의 주장)                              |
| 줄 수                       | C 185,000줄이 Rust 340,000줄로(필자가 직접 센 값)        |
| 같은 기간 curl 본가         | 3주 남짓 동안 커밋 300개 이상, 버그 수정 200개 남짓      |
| 커밋 속도                   | 하루 평균 약 11개                                        |
| 2026년에 확인된 취약점      | 81건 중 14건(17.3%)이 메모리 안전 언어였다면 피했을 실수 |
| Rust 구현에도 남았을 취약점 | 67건                                                     |

Stenberg는 경쟁 대안을 만들기 어려운 주된 이유가 언어가 아니라
개발 속도와 개발 팀, 주변 공동체라고 쓴다.
수십 년간 이어 온 ABI와 API 안정성은 curl만 보여 줄 수 있고,
오늘 나온 대안이 그럴 수 있는지는 수십 년 뒤에야 안다고 한다.
그는 어떤 언어로든 재작성을 믿지 않으며
끝없이 다듬고 반복하고 리팩터링하는 쪽을 믿는다고 밝힌다.

글쓴이는 두 프로젝트의 제작자와 연락한 적이 없고
저장소 링크를 사람들이 붙여 넣어 주어서 알게 되었다고 한다.
이 프로젝트들이 개념 증명 이상인지는 앞으로 알게 되리라고 보고,
하루 평균 11개쯤 쌓이는 본가 커밋을 따라가며 Rust로 바꿀 수도 있다고 덧붙인다.
자신의 기분은 재미있고 조금 어리둥절하며 흥미롭다고 쓰고,
행운을 빈다는 말로 맺는다.

### 글이 가리킨 두 저장소

이 문서는 글이 링크한 두 저장소와, 8,600달러 주장이 걸린 Claude 아티팩트를
열어 보았다.
저장소 수치는 2026-11-26에 GitHub API로 읽은 값이다.
이 문서는 코드를 빌드하거나 시험을 돌려 보지 않았다.

| 항목        | kov/curl                           | urlx                      |
| ----------- | ---------------------------------- | ------------------------- |
| 시작        | 2026-10-20                         | 2026-03-08                |
| 마지막 갱신 | 2026-11-24                         | 2026-10-06                |
| 성격        | curl/curl 저장소의 포크            | 새 저장소                 |
| 라이선스    | 저장소 표시는 NOASSERTION          | MIT                       |
| 별 / 포크   | 7 / 1                              | 27 / 3                    |
| TLS         | 여러 백엔드(OpenSSL이 기본)        | rustls                    |
| 시험 주장   | C가 통과하는 시험을 둘만 빼고 통과 | 1,300개 통과, 92개 건너뜀 |

kov/curl의 README는 이 재작성을 Anthropic의 Claude가 Claude Code에서
저장소 유지보수자의 지휘와 검토를 받으며 썼다고 적는다.
시작한 2026년 10월 20일 이후 커밋이 약 2,300개이고,
시험을 포함한 Rust 코드가 약 43만 줄이며 C의 `lib/`와 `src/`는 20만 줄이라고
한다.[^kov]
C 코드를 줄 단위로 옮긴 것이 아니라 C 트리에서 옵션, 상수, 구조체 배치, 시험을
뽑아 만든 목록(inventory)을 기준으로 지었고, curl의 시험 모음을 판정 기준으로
썼다고 한다.[^kov]
`libcurl.so.4`를 그대로 바꿔 끼울 수 있는 라이브러리와 명령줄 도구,
그리고 Rust API(`curl-core`)를 만들며 Rust API가 제품이라고 밝힌다.[^kov]
C와 다르게 동작하도록 의도한 곳은
`DIVERGENCE.md`에 시험과 함께 적었다고 한다.[^kov]
성능은 릴리스 빌드에서 C 속도의 0.81배에서 1.11배 사이로 보고하며
NTLM과 quictls는 만들지 않았다고 한다.[^kov]

urlx의 README는 curl과 libcurl의 메모리 안전한 처음부터의 재구현이라고 소개한다.
curl 시험 1~1400번 가운데 1,300개가 통과하고 92개는 건너뛰었으며
25개는 영구 제외했다고 적는다.[^urlx]
지원 표에서 HTTP/3은 검증되지 않았다고 표시한다.[^urlx]

8,600달러 주장이 걸린 아티팩트 “Rewriting curl in Rust”는
작성자를 적지 않고 `kov/curl`의 `rust-rewrite` 브랜치를 가리키며,
기간을 2026년 10월 20일부터 11월 15일까지로 잡는다.[^artifact]
요약 표는 27일, 커밋 2,750개, Rust 430,224줄, 에이전트 326개,
API 비용 약 8.6천 달러, C가 통과하고 Rust가 실패하는 시험 0개다.[^artifact]
비용은 정가 기준 약 8,650달러이며, 구독 플랜으로 돌렸다면
API에서 들었을 값이지 실제로 청구된 금액이 아니라고 페이지가 밝힌다.[^artifact]

페이지는 11월 11일에 2000년부터 2026년 10월까지 공개된
curl 취약점 239건을 재작성의 설계와 맞춰 보았다고 한다.[^artifact]
약 3분의 1은 재작성에서 일어날 수 없다는 분류이고,
메모리 안전 버그 41건과 타입이나 소유권으로 막힌 43건이 여기에 든다.[^artifact]
논리 결함이 133건, 재작성에 없는 코드에 관한 것이 22건이다.[^artifact]
옛 버그 여덟 개가 재작성에서 되살아난 것을 찾아
같은 날 고쳤다고 한다.[^artifact]
프로덕션 코드의 `unsafe` 사용은 3,711곳이고
그 가운데 1,326곳이 C ABI 계층에 속한다고 적는다.[^artifact]
이 수치는 제작 쪽의 자체 보고이며 이 문서가 따로 검증하지는 않았다.

## 분석

### 코드를 쓰는 비용과 프로젝트를 유지하는 비용을 나누는 주장

Stenberg의 글은 한 문장으로 줄이면, 쓰는 일은 싸졌지만 유지하는 일은 그대로라는
주장이다.
저장소의 숫자가 이를 뒷받침하는 쪽과 흔드는 쪽을 함께 보여 준다.
27일에 정가 환산 약 8.6천 달러라는 값은 재작성 하나가 몇 주와 한 사람의 지휘로
가능했다는 점에서 글의 첫 문단과 맞는다.
반면 유지에 필요한 것으로 글이 꼽는 수정과 개선의 흐름은,
재작성 쪽이 같은 에이전트 작업으로 이어 갈 수 있는지가 아직 열려 있다.

### 시험 모음과 C 코드가 명세 역할을 한다는 설명

글은 AI가 할 일이 C 코드를 옮기고 시험이 통과할 때까지 다듬는 것이라고 쓴다.
kov/curl의 README가 서술하는 제작 방식은 이 설명과 큰 틀에서 같다.
C 트리가 무엇을 만들지 정하고 curl의 시험 모음이 판정한다는 것이다.[^kov]
다른 점은 줄 단위 번역이 아니라
C 트리에서 목록을 뽑아 따로 지었다고 밝히는 것이다.
따라서 Stenberg가 든 이유 중 문서, 사용 사례, 시험은 README와 겹치고,
AI가 curl 코드를 학습했다는 이유는 README나 이 문서가 확인할 수 없다.

### 재작성이 쫓아야 하는 본가의 움직임

글의 수치로 계산하면 3주 남짓 동안 커밋 300개는 하루 약 11개에 가깝다.
같은 기간에 재작성은 줄 수가 185,000에서 340,000으로 늘었다고 한다.
글은 이를 본가가 재작성이 갖지 못한 200여 개의 수정을 더했다는 뜻으로 읽는다.
kov/curl은 curl 저장소의 포크이고 C 트리를 함께 두고 있어서
본가의 변경을 가져올 길이 구조상 열려 있지만,
이 문서는 그 길이 실제로 쓰였는지 확인하지 못했다.

### 17.3%라는 수치가 세는 것

14를 81로 나누면 17.3%이고 81에서 14를 빼면 67이다.
계산은 맞고, 글은 이를 반복하는 주장이라고 스스로 밝힌다.
이 수치는 Stenberg가 각 취약점을 메모리 안전 언어였다면 피했을 가능성이 큰지로
분류한 결과다.
분류 기준은 글에 적혀 있지 않다.
같은 해 curl.se의 취약점 목록 파일에는 2026년에 공개된 항목이 69건 있어
글의 81건과 센 기준이 다른 것으로 보이지만 차이의 이유는 확인하지 못했다.[^vuln]
Stenberg가 2021년 3월에 쓴 글은 당시 공개된 98건 가운데 51건(52%)을
C의 실수 때문이라고 셌다.[^half2021]
이번 글의 14건 대 81건은 2026년에 확인된 것만의 비율이고
앞의 값은 누적 건수여서, 둘을 한 추세로 잇기는 어렵다.
Lobste.rs에서 ohrv는 이전에는 절반이었는데 이번에는 17%라고 짚었다.[^ohrv]

## 비평

### 두 재작성을 직접 확인하지 않은 채 없는 것을 말한다

글은 200여 개의 수정을 재작성들이 갖지 못했다고 쓴다.
글쓴이는 제작자와 연락한 적이 없고 저장소를 시험했다는 서술도 없다.
kov/curl은 curl 저장소의 포크라서 시작 시점의 C 트리를 담고 있고,
그 뒤 본가 수정이 들어갔는지는 확인된 바가 없다.
따라서 갖지 못했다는 문장은 가능성의 서술이지 확인된 사실이 아니다.
이 문서도 두 저장소의 수정 반영 여부를 열어 보지 않았다.

### 메모리 안전만 센 수치와 새 코드의 결함

17.3%는 Rust 구현이 없앨 수 있는 취약점의 비율을 메모리 안전 하나로 센 값이다.
kov/curl의 README는 재작성의 이유를 메모리 안전 버그에 더해
정수 값이 서로 바뀌는 문제와 설명하던 대상보다 오래 남은 상태까지 든다.
정수마다 타입을 따로 주고 연결과 전송의 상태를 서로 다른 타입으로 만들었다고
한다.[^kov]
이것이 글이 센 14건 밖의 취약점을 줄이는지는 이 문서가 판단할 수 없다.
반대로 43만 줄의 새 코드가 새 논리 결함을 만들 가능성은
글도 README도 수치로 다루지 않는다.
아티팩트는 이 점을 일부 다룬다.
239건의 점검에서 옛 버그 여덟 개가 재작성에 되살아났다고 적고,
메모리 안전 41건 외에
타입이나 소유권으로 막힌 것이 43건이라고 분류한다.[^artifact]
같은 점검에서 논리 결함 133건은 재작성이 고쳐진 C를 따라 하기 때문에만
막힌다고 스스로 밝힌다.[^artifact]
HN에서 viraptor는 남은 67건 가운데에도
더 표현력 있는 언어가 막았을 수 있는 것이 있다고 짚었다.[^viraptor]
C에서 문자열을 직접 파싱하고 비교하기 어려워 내려진 결정이
Rust의 열거형과 `Eq` 트레이트였다면 달라졌을지 묻는 것이며,
이는 댓글 작성자의 추정이다.[^viraptor]
Lobste.rs에서 gendx는 이 문장이 Rust의 이점을 메모리 오류 방지로만 읽게 한다고
비판했다.[^gendx]
상태 기계를 전수 패턴 매칭으로 표현하는 타입 시스템과
성공 코드를 0과 1로 뒤바꾸는 오류를 줄이는 오류 처리,
린트를 이점으로 든다.[^gendx]
또 비교 기준은 새 재작성이 아니라 reqwest 같은 기존 Rust HTTP 라이브러리여야
한다고 했다.[^gendx]
RustSec에 reqwest의 보고 취약점은 없지만 전이 의존성인 rustls에는
올해 낮음·중간 5건이 있어 비교가 결론에 이르지 못한다고 본다.[^gendx]
그가 바라는 것은 올해의 curl 취약점 10~20건을 골라
Rust 컴파일러가 막았을지 따져 보는 분석이다.[^gendx]

### 경쟁으로 보는 틀과 제작자가 밝힌 목표의 차이

글은 이 프로젝트들을 curl과 경쟁하는 대안으로 읽고
개발 속도와 공동체가 그 경쟁을 어렵게 한다고 쓴다.
kov/curl의 README는 `libcurl.so.4`를 그대로 바꿔 끼울 수 있다고 하면서도
Rust API가 제품이고 C ABI는 그 위의 변환 계층이라고 밝힌다.[^kov]
제작자는 HN에서 이 작업이 본가 유지보수자가 어렵다고 말한 일을
직접 해 본 실험이라고 설명했다.[^kov-hn]
본업을 하는 사이의 부수 프로젝트였고 자기 시스템의 libcurl을 이것으로
바꿔 쓰고 있다고도 썼다.[^kov-hn]
이 작업이 10년 뒤에도 유지되겠느냐는 댓글에는
아마 그렇지 않을 것이라고 답하면서,
본가 유지보수자가 쓴다면 이점이 크다는 것이
실험의 요점이라고 했다.[^darkamaul][^kov-reply]
목표가 증명과 대체의 사이에 있어서, 글의 경쟁 틀이 모든 경우에 맞지는 않는다.
kornel은 Rust에는 이미 자체 HTTP 생태계가 있어
curl 재작성이 살아남기 어렵다고 썼다.[^kornel]
pert는 재작성보다 기존 Rust HTTP 라이브러리 위에
같은 명령줄 모양을 가진 별도 구현을 보고 싶다고 했다.[^pert]
ohrv는 줄 단위 번역이 2년 전에는 어렵고 지금은 가능하다는 점이 달라졌다고 하며,
안전한 libcurl이 필요한 중요 인프라가 있다면 글의 논거가 반론이 되지 못한다고
보았다.[^ohrv]

### 줄 수 비교의 기준이 다르다

글이 센 값은 C 185,000줄에서 Rust 340,000줄이고,
README는 시험을 포함해 Rust 약 43만 줄, C 20만 줄을 적는다.[^kov]
글은 세는 시점과 범위를 밝히지 않았고 README의 값은 시험 포함이다.
두 값은 서로 다른 시점이나 범위에서 센 것이라 한쪽이 틀렸다고 볼 수 없으나,
둘을 이어 한 흐름으로 읽을 수도 없다.
ahartmetz는 더 높은 수준의 언어로 옮기며
줄 수가 거의 두 배가 된 점을 짚었다.[^ahartmetz]
글의 값으로 나누면 약 1.84배다.

### 8,600달러는 정가 환산값이다

글은 8,600달러를 재작성 쪽의 주장으로 전한다.
아티팩트는 같은 값을 정가 기준 약 8,650달러로 적고,
실제 청구액이 아니라 API에서 들었을 환산값이라고 밝힌다.[^artifact]
viraptor는 이런 작업에는 API 요금이 아니라 구독을 쓰므로
실제 지출은 훨씬 적었을 것이라고 썼고,[^viraptor]
페이지의 설명은 이 추정과 어긋나지 않는다.
글의 문장은 제작자가 8,600달러를 썼다는 주장으로 읽히지만
페이지가 말하는 것은 환산값이므로 같은 뜻이 아니다.
실제 지출액은 이 문서가 확인하지 못했다.

### 글이 다루지 않는 재작성의 이유

글은 취약점과 프로젝트의 지속성을 중심으로 재작성을 논한다.
fschuett는 Rust가 WASM까지 어디서든 빌드되고 여러 라이브러리를 엮기 쉬우며
취약점이 약 20% 줄어도 그것은 줄어드는 것이라고 썼다.[^fschuett]
cozzyd는 libcurl을 쓰기는 이미 쉽고 배포판에 설치되어 있다고 답했다.[^cozzyd]
pjmlp는 CMake와 conan이 있고, GCC 프런트엔드 프로젝트가 있는 이유가
LLVM 기반 컴파일러로는
C 컴파일러가 있는 모든 곳을 덮지 못해서라고 응수했다.[^pjmlp-reply]
Lobste.rs에서는 이식성이 같은 논쟁으로 이어졌다.
johnklos는 Rust가 C만큼 이식성이 좋지 않아
재작성 요구가 곧 많은 플랫폼의 지원 중단 요구라고 썼다.[^johnklos]
kornel은 Haiku, QNX, 68k, AVR까지 Rust가 지원하고,
빠진 플랫폼은 유지보수자 둘과 CI를
갖추지 못한 극소수라고 답했다.[^kornel-platform]
sunshowers는 Rust의 이식성이 C와 다를 뿐이라며,
Tokio 덕에 illumos에서 cargo-nextest를
코드 수정 없이 빌드한 경험을 들었다.[^sunshowers]
이 논쟁은 글의 틀 밖에 있으며 이 문서는 양쪽 주장을 확인하지 못했다.

## 인사이트

### 쓰는 비용이 내려가면 신뢰를 쌓는 시간이 남는다

Bun의 Zig에서 Rust로의 이식은 11일에 API 비용 약 165,000달러가 들었다고
[Bun Rust 이식 문서](rewriting-bun-in-rust.md)에 정리되어 있다.
curl의 재작성은 27일에 정가 환산 약 8.6천 달러로,
두 작업은 대상과 방식이 달라 직접 견줄 수 없다.
그래도 둘 다 짧은 시간과 금액으로 수십만 줄이 나왔다는 점은 같다.
이럴 때 남는 희소한 자원은 코드가 아니라 그 코드가 오래 옳다는 증거이고,
Stenberg가 ABI와 API 안정성을 수십 년 단위로 말하는 것도 같은 지점이다.

### 공개된 시험 모음은 명세이자 복제의 지름길이다

curl의 시험은 수천 개이고 공개되어 있다.
이 시험이 구현의 품질을 지키는 장치이면서 동시에 다른 구현이 겨냥할 판정 기준이
된다는 점이 두 재작성에서 드러난다.
kov/curl의 README는 C가 통과하는 시험을 둘만 빼고 모두 통과한다고 쓴다.[^kov]
시험이 곧 명세인 프로젝트는
이 공개가 만드는 이점과 복제 비용 하락을 함께 안게 된다.
[Mythos 문서](../security/mythos-curl-vulnerability.md)가 다룬 것처럼
curl은 이미 AI 분석의 대상이 된 프로젝트이기도 하다.

### 재작성 열풍이 언어 공동체에 남기는 인상

pjmlp는 Rust 재작성의 유행이 언어에 해가 된다고 보았다.[^pjmlp]
C를 C++로 다시 쓰던 시절의 열풍처럼
언어 이름만 봐도 거리를 두는 사람을 만들고,
배우려 했을 수도 있는 사람까지 멀어지게 한다는 것이다.[^pjmlp]
이는 한 댓글 작성자의 경험에 근거한 의견이다.
Stenberg는 언어가 아니라 재작성 자체에 회의적이어서 두 논점은 서로 다르다.

### 확인할 것

kov/curl이 본가의 최근 수정을 실제로 가져오는지,
`DIVERGENCE.md`에 적힌 차이와 시험 현황이 본가의 최신 상태에서도 유지되는지
확인이 필요하다.
Stenberg가 센 81건과 14건의 분류 기준, curl.se 목록과의 차이도 확인할 부분이다.
아티팩트의 수치는 제작 쪽 보고이며,
239건 분류의 개별 판정은 따로 확인하지 못했다.
urlx의 현재 상태는 마지막 갱신이 2026-10-06이라는 사실까지만 확인했다.
