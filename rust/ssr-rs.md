# ssr_rs: Rust 서버 안에 V8을 심어 JavaScript 번들을 렌더링하는 크레이트

<https://github.com/Valerioageno/ssr-rs>

<https://docs.rs/ssr_rs/latest/ssr_rs/>

## 소개

`ssr_rs`는 Rust 서버에서 서버 사이드 렌더링을 가능한 한 단순하고 가볍게 할 수 있게 하는 것을 목표로 하는 크레이트다.
V8 자바스크립트 엔진의 내장 버전인 `rusty_v8`을 써서 번들된 파일을 파싱하고 평가한 뒤 렌더링된 HTML 문자열을 돌려준다.
저장소는 2021년 4월 23일에 만들어졌고, 이 문서 작성 시점 기준 GitHub 스타 251개, 포크 22개, 열린 이슈 3개다.
crates.io 기준 누적 다운로드 46,284회에 최근 다운로드 4,316회이며, 24개 버전이 나왔고 최신은 2025년 5월 9일의 0.8.3이다.

README는 이 프로젝트가 SSR을 내장한 풀스택 리액트 프레임워크인 tuono의 중추(backbone)라고 밝힌다.
현재 Vite, Webpack, Rspack과 React 18, Svelte 5, SolidJS에서 동작한다고 적고 `examples/` 폴더를 참조하라고 안내한다.
docs.rs에 게시된 0.8.3 문서에는 같은 문장이 React 18과 Svelte 4까지만 나열되어 있다.

공개 API는 좁다.
docs.rs가 노출하는 최상위 항목은 `v8` 모듈과 `Ssr` 구조체와 `SsrError` 열거형 셋뿐이다.
사용 흐름은 `Ssr::create_platform()`으로 V8 플랫폼을 초기화하고, 번들 파일을 문자열로 읽고, `Ssr` 인스턴스를 만든 뒤 `render_to_string`을 호출하는 네 단계다.

```rust
use ssr_rs::Ssr;
use std::fs::read_to_string;

fn main() {
    Ssr::create_platform();

    let source = read_to_string("./path/to/build.js").unwrap();

    let mut js = Ssr::new(&source, "entryPoint").unwrap();

    let html = js.render_to_string(None).unwrap();

    assert_eq!(html, "<!doctype html><html>...</html>".to_string());
}
```

`entryPoint`가 이 크레이트에서 가장 많은 설명을 차지하는 개념이다.
그것은 하나 이상의 속성이 함수이고 호출하면 렌더링 결과를 반환하는 객체를 돌려주는 함수이거나, 그런 객체 자체다.
번들된 JS가 즉시 실행 함수 표현식(IIFE)이거나 평범한 객체인 경우 `entryPoint`는 빈 문자열이고, `var SSR = (() => ({...}))()`처럼 변수에 담긴 경우 `SSR`이 진입점이 된다.
문서는 내보내기 결과가 번들러에 의해 직접 관리된다고 덧붙인다.
초기 props는 `render_to_string`에 JSON 문자열로 넘기며, README 예시는 `"hello"`, `"ciao"`, `"こんにちは"`를 담은 배열로 비ASCII 문자열 전달을 함께 보여 준다.

스레드 모델에 대한 설명이 별도로 붙어 있다.
V8 엔진 자체는 서로 다른 스레드에서 같은 아이솔레이트에 접근하는 것을 허용하지만 이 크레이트는 그것을 두 가지 이유로 금지한다.
첫째, `rusty_v8` 라이브러리가 아직 V8 Locker API를 구현하지 않아 다른 스레드에서 `Ssr` 구조체에 접근하면 V8 엔진이 패닉을 일으킨다.
둘째, HTML을 렌더링하는 데는 스레드 간 공유 상태가 필요하지 않다.
그래서 병렬 계산이 더 나은 선택이라며 actix-web 설정을 제시하는데, `thread_local!`로 워커 스레드마다 `RefCell<Ssr>`을 하나씩 두고 요청마다 `borrow_mut()`으로 빌려 쓰는 형태다.

```rust
thread_local! {
    static SSR: RefCell<Ssr<'static, 'static>> = RefCell::new(
            Ssr::from(
                read_to_string("./client/dist/ssr/index.js").unwrap(),
                "SSR"
                ).unwrap()
            )
}
```

`benches/README.md`는 크레이트의 주된 목표가 나머지 Rust 생태계처럼 “엄청나게 빠른” 것이라며 wrk로 측정한 결과를 싣는다.
같은 애플리케이션을 `actix-rs + ssr_rs`로 빌드해 돌린 것과 `node`에 fastify 서버를 얹어 돌린 것을 비교한다.
12스레드 400커넥션 30초 조건에서 전자는 초당 266,177.68 요청에 평균 지연 2.26ms였고, 후자는 초당 31,740.30 요청에 평균 지연 24.04ms이며 타임아웃 소켓 오류 48건이 났다.
측정 환경은 Intel Core i5 13600KF에 DDR5 32GB이고 Ubuntu가 설치된 WSL 머신이라고 밝힌다.
같은 문서의 두 번째 줄에는 이 측정이 `ssr_rs` v0.3.0을 대상으로 한 것이라는 단서가 붙어 있다.

기여 안내의 알려진 할 일 목록은 다섯 가지다.
다른 Rust 백엔드 프레임워크 예제 추가, Vue와 Qwik 같은 다른 프런트엔드 프레임워크 예제 추가, Deno와 Bun을 상대로 시험할 벤치마크 구성 추가, V8 스냅숏 지원 탐색, 그리고 javy 같은 것을 이용한 JS의 WASM 컴파일 탐색이다.
라이선스는 README가 MIT와 Apache 이중 라이선스라고 밝히지만 GitHub API가 보고하는 값은 Apache-2.0 단일이다.

## 분석

### `entryPoint`는 설정값이 아니라 번들러의 출력 형태가 Rust API로 새어 나온 것이다

이 크레이트의 문서에서 가장 긴 설명을 받는 것은 렌더링도 성능도 아닌 `entryPoint`다.
네 가지 JavaScript 코드 형태를 예시로 보여 주면서 각각 무엇을 진입점 문자열로 넘겨야 하는지 알려 준다.
빈 문자열이 정답인 경우가 둘, 변수 이름이 정답인 경우가 둘이다.

이 설명이 필요한 이유는 이 크레이트가 모듈 시스템을 다루지 않기 때문이다.
V8 아이솔레이트에서 소스를 평가한 뒤 전역 객체에서 이름을 찾아 함수를 호출하는 방식이며, 그래서 번들러가 최종 산출물을 IIFE로 감쌌는지 변수에 할당했는지가 그대로 Rust 쪽 인자로 올라온다.
문서가 “내보내기 결과는 번들러가 직접 관리한다”고 적은 문장이 이 구조를 정확히 요약한다.
크레이트는 번들러의 출력 규약을 알지 못하고, 사용자가 그 차이를 문자열 하나로 메워 주어야 한다.

이 설계는 단순함의 대가다.
ES 모듈 로딩이나 CommonJS 해석을 지원했다면 이 인자는 사라졌겠지만 크레이트가 훨씬 커졌을 것이다.
`Ssr`, `SsrError`, `v8` 세 심볼만 노출하는 최소 표면이 유지되는 것은 이 결정 덕분이다.
동시에 이것이 이 크레이트를 쓰는 사람이 겪는 첫 번째 실패 지점이기도 하다.
번들 설정을 바꾸면 Rust 코드의 문자열 상수가 조용히 틀리게 되고, 그 오류는 컴파일 타임이 아니라 런타임에 드러난다.

### 스레드 공유를 금지한 결정이 배포 아키텍처 전체를 정한다

README가 제시하는 두 가지 금지 이유는 성격이 다르다.
첫 번째인 Locker API 미구현은 시간이 지나면 해소될 수 있는 상류 라이브러리의 상태다.
두 번째인 “HTML 렌더링에는 공유 상태가 필요 없다”는 것은 설계 판단이며, 상류가 바뀌어도 유지될 수 있는 입장이다.

두 이유를 합쳐 나온 것이 워커 스레드마다 아이솔레이트를 하나씩 두는 구조다.
이 모델은 락도 없고 경합도 없어 요청 처리 경로가 단순하다.
`RefCell`을 쓰는 것도 같은 스레드 안에서만 빌리므로 안전하며, 동기화 비용이 0이다.
Node.js가 단일 스레드 이벤트 루프로 같은 문제를 회피하는 것과 비교하면, 이쪽은 스레드 수만큼 런타임을 복제해 문제를 회피한다.

대가는 메모리다.
V8 아이솔레이트는 각각 자기 힙과 자기 컴파일된 코드 캐시를 갖는다.
워커가 12개면 번들이 12번 파싱되고 평가되며 12벌의 힙이 유지된다.
문서는 이 비용을 언급하지 않고, 아이솔레이트 하나의 상주 메모리가 얼마인지도 알려 주지 않는다.
할 일 목록에 V8 스냅숏 지원 탐색이 올라 있는 것이 이 문제를 인식하고 있다는 신호인데, 스냅숏은 초기화 시간을 줄이지 메모리 복제를 없애지는 않는다.

### 이 크레이트의 실제 사용자는 개인 개발자가 아니라 tuono다

README와 docs.rs가 모두 이 프로젝트를 tuono의 중추라고 소개한다.
이 관계가 크레이트의 성격을 이해하는 데 중요하다.
누적 4만 6천 다운로드에 최근 4천 다운로드라는 수치는 라이브러리로서 널리 쓰인다고 보기 어려운 규모이지만, 하나의 프레임워크가 안정적으로 의존한다면 이야기가 다르다.

실제로 그렇다.
tuono는 저장소가 `Valerioageno/tuono`에서 `tuono-labs/tuono`로 옮겨 갔고 스타 1,135개를 모았으며, `tuono_lib`의 `Cargo.toml`은 여전히 `ssr_rs = "0.8.3"`을 고정하고 있다.
다만 tuono 쪽도 마지막 릴리스가 2025년 5월 25일이고 기본 브랜치의 마지막 사람 커밋이 2025년 7월 20일이라 함께 조용해진 상태다.
즉 `ssr_rs`는 자기보다 큰 프로젝트의 하부 계층으로 실제로 쓰이고 있다.

이 관계가 API 설계에도 반영되어 있다고 보아야 한다.
`entryPoint` 문자열, 프로퍼티 이름으로 렌더 함수를 고르는 방식, props를 JSON 문자열로 넘기는 인터페이스는 모두 상위 프레임워크가 번들러를 통제할 때 가장 쓰기 좋은 형태다.
번들 출력 형태를 프레임워크가 직접 정한다면 `entryPoint`는 하드코딩할 수 있는 상수가 되고, 앞 절에서 지적한 실패 지점이 사라진다.
직접 쓰는 사람에게 거칠게 느껴지는 인터페이스가 하부 계층으로서는 적절할 수 있다는 뜻이며, 이 크레이트를 평가할 때 두 관점을 섞으면 판단이 흐려진다.

## 비평

### 대표 벤치마크가 다섯 단계 전 버전의 것이고 변수가 통제되지 않았다

`benches/README.md`는 이 크레이트의 성능 주장을 뒷받침하는 유일한 문서이고, README 본문이 그것을 링크한다.
그런데 그 문서의 두 번째 줄이 측정 대상이 v0.3.0이라고 밝힌다.
현재 최신은 0.8.3이므로 0.4, 0.5, 0.6, 0.7, 0.8 다섯 개의 마이너 버전을 건너뛴 숫자다.
그 사이에 V8 버전도 올라갔고 API도 `from`에서 `new`로 바뀌었는데, 성능이 좋아졌는지 나빠졌는지에 대한 정보가 없다.

숫자 자체도 곧이곧대로 읽기 어렵다.
초당 266,177 요청은 i5-13600KF 한 대에서 나온 값인데, 이것이 React 컴포넌트 트리를 실제로 렌더링한 결과라면 요청당 3.8마이크로초 안에 렌더링이 끝났다는 뜻이다.
`renderToString`이 그 시간 안에 끝나는 컴포넌트라면 그것은 사실상 문자열 상수에 가깝고, 그런 대상으로 잰 처리량은 렌더링 성능이 아니라 HTTP 스택 성능을 잰 것에 가깝다.
비교 대상인 fastify 쪽이 초당 31,740 요청이라는 것도 같은 의심을 키운다.
두 값의 비율 8.4배가 렌더링 엔진의 차이인지 액틱스와 fastify의 HTTP 처리 차이인지 이 측정으로는 분리되지 않는다.

측정 조건에도 문제가 있다.
문서 자신이 밝히듯 Ubuntu가 설치된 WSL 머신에서 돌렸고, 부하 생성기 wrk와 서버가 같은 기계에 있다.
Node 쪽 결과에는 타임아웃 소켓 오류 48건이 기록되어 있는데 액틱스 쪽에는 없으므로, 두 실행이 같은 조건에서 이루어졌다고 보기 어렵다.
클라이언트가 서버와 CPU를 나눠 쓰는 상황에서 한쪽만 소켓 타임아웃을 낸다는 것은 부하 생성기가 포화되었을 가능성을 시사한다.

이 지적이 사소하지 않은 이유는 이 크레이트의 존재 이유가 성능이기 때문이다.
“나머지 Rust 생태계처럼 엄청나게 빠른 것이 주된 목표”라고 문서가 명시하는데, 그 목표의 유일한 증거가 다섯 버전 전의 통제되지 않은 측정이다.
할 일 목록에 “Deno와 Bun을 상대로 시험할 벤치마크 구성 추가”가 올라 있다는 사실은 저자도 현재 벤치마크가 부족하다는 것을 알고 있음을 보여 주지만, 그 항목은 여전히 미완료 상태다.

### 문서 세 곳이 서로 다른 API와 서로 다른 지원 목록을 말한다

같은 크레이트를 설명하는 문서가 셋인데 내용이 갈린다.
docs.rs에 게시된 0.8.3 문서는 기본 예제에서 `Ssr::from(source, "entryPoint")`를 쓰고 지원 대상으로 React 18과 Svelte 4를 든다.
GitHub README는 같은 예제에서 `Ssr::new(&source, "entryPoint")`를 쓰고 지원 대상으로 React 18과 Svelte 5와 SolidJS를 든다.
`from`은 소유권을 가져가고 `new`는 참조를 받으므로 호출 형태가 다르다.

더 나쁜 것은 README 자신이 일관되지 않다는 점이다.
본문 첫 예제는 `Ssr::new(&source, ...)`인데 actix-web 예제는 `Ssr::from(read_to_string(...).unwrap(), "SSR")`이다.
같은 문서 안에서 두 생성자를 섞어 쓰면서 어느 것이 권장인지, 둘이 어떻게 다른지에 대한 설명이 없다.
크레이트를 처음 쓰는 사람이 README를 위에서 아래로 읽으면 예제를 복사할 때마다 다른 API를 쓰게 된다.

이 어긋남은 문서 갱신 순서에서 나왔을 가능성이 높다.
crates.io에 마지막으로 발행된 0.8.3은 2025년 5월 9일이고 저장소의 마지막 푸시는 2025년 10월 1일이므로, 그 다섯 달 사이의 변경이 README에만 반영되었다.
Svelte 5와 SolidJS 지원도 그 기간에 추가된 것으로 보인다.
문제는 사용자가 `cargo add ssr_rs`로 설치하는 것이 0.8.3이라는 점이다.
README를 보고 SolidJS 예제를 기대한 사람이 받는 것은 그 지원이 들어가기 전 버전이다.

같은 계열의 방치가 링크에도 있다.
README가 “이 프로젝트는 tuono의 중추”라며 거는 링크는 `Valerioageno/tuono`인데, 그 저장소는 지금 존재하지 않는다.
tuono는 `tuono-labs/tuono`로 옮겨 갔으나 그쪽도 2025년 7월 이후 사람 커밋이 없다.
자기 존재 이유로 내세우는 프로젝트의 링크가 죽어 있는 상태이며, 라이선스 표기도 README는 이중 라이선스라고 하는데 GitHub은 Apache-2.0으로 인식하고 있다.

### V8을 크레이트에 묶은 대가가 어디에도 문서화되어 있지 않다

`ssr_rs`의 유일한 정식 의존성은 `v8 ^135.1.0`이다.
이 한 줄이 이 크레이트를 쓰는 데 따르는 가장 큰 비용을 담고 있는데 문서는 그것을 다루지 않는다.

가장 눈에 띄는 것은 크기다.
crates.io가 보고하는 압축 크레이트 크기가 0.8.2에서 41,631바이트였다가 0.8.3에서 4,621,851바이트가 되었다.
111배 증가이며 크레이트 자체 코드가 그만큼 늘었다고 보기는 어렵다.
무엇이 들어갔는지 릴리스 노트나 README 어디에도 설명이 없고, 이 크기는 빌드 시간과 CI 캐시와 컨테이너 이미지 크기에 직접 영향을 준다.
`rusty_v8`은 사전 빌드된 V8 정적 라이브러리를 내려받거나 소스에서 빌드하는데, 후자는 수십 분이 걸리는 것으로 알려져 있다.
“가능한 한 단순하고 가볍게”를 표방하는 크레이트의 실제 빌드 경험이 어떤지가 문서화되어야 할 지점이다.

두 번째는 보안 갱신 주기다.
V8은 브라우저에서 가장 공격받는 코드베이스 중 하나이고 정기적으로 취약점이 보고된다.
`v8 ^135.1.0`으로 고정하면 V8 메이저 버전이 크레이트 저자의 갱신 속도에 묶이며, 저장소가 열 달째 조용한 상태에서는 그 속도가 사실상 0이다.
서버에서 신뢰할 수 없는 JavaScript를 평가하는 용도라면 이것이 결정적이지만, 자기가 빌드한 번들만 평가하는 이 크레이트의 용도에서는 위험이 훨씬 낮다.
문제는 문서가 그 구분을 해 주지 않아 사용자가 스스로 판단해야 한다는 것이다.

세 번째는 이식성이다.
현재 열린 이슈 중 하나가 정확히 이 문제인데, 2025년 10월 23일에 올라온 WASM(wasip2) 컴파일 불가 문의이며 `rusty_v8`을 다른 것으로 대체할 수 있느냐고 묻는다.
V8을 정적으로 링크하는 크레이트는 V8이 지원하는 타깃에서만 동작하므로 WASM 타깃이나 일부 임베디드 환경에서 쓸 수 없다.
README의 할 일 목록에 javy를 이용한 JS의 WASM 컴파일 탐색이 올라 있는 것이 같은 문제를 겨냥한 것으로 보이지만, 이슈는 답 없이 열려 있다.

## 인사이트

### 조용한 저장소가 곧 방치는 아니며, 이 크레이트는 완성에 가까운 상태로 읽어야 한다

표면 지표만 보면 이 프로젝트는 시들해 보인다.
마지막 릴리스가 2025년 5월, 마지막 푸시가 2025년 10월, 열린 이슈 세 개, 스타 251개다.
보통 이런 지표 조합은 채택을 재고할 이유가 된다.

그러나 두 가지 사실이 그 판단을 뒤집는다.
첫째, 상위 프로젝트인 tuono가 2026년 8월까지 활발히 개발되면서 `ssr_rs = "0.8.3"`을 그대로 쓰고 있다.
의존하는 쪽이 매일 커밋하면서도 버전을 올릴 필요를 느끼지 않는다는 것은 이 크레이트가 자기 일을 하고 있다는 뜻이다.
둘째, 공개 API가 `Ssr`과 `SsrError`와 `v8` 모듈 셋뿐이다.
표면이 이만큼 좁으면 바꿀 것이 별로 없다.

이 조합이 만드는 상태를 “완성”이라고 부를 수 있다.
[Rails가 완성되었다는 주장을 다룬 노트](../rails/amiko.md)에서 같은 구분이 쟁점이었는데, 거기서 Rails 코어 메인테이너가 사용자 관점의 완성과 유지보수자 관점의 미완성을 갈랐다.
`ssr_rs`는 그 구분이 훨씬 단순하게 적용되는 사례다.
사용자가 마주하는 표면은 안정적이고, 유지보수 부담의 대부분은 상류인 V8 갱신에서 온다.
그래서 이 크레이트를 평가할 때 물어야 할 것은 커밋 빈도가 아니라 V8 갱신이 필요해질 때 누가 그 일을 하느냐다.

여기서 나오는 실천적 결론은 하부 라이브러리의 활동 지표를 상위 소비자와 함께 보라는 것이다.
얇은 어댑터 계층은 정상 상태에서 조용한 것이 맞고, 활동이 많다면 오히려 인터페이스가 아직 정해지지 않았다는 신호일 수 있다.
반대로 이 크레이트가 위험해지는 시점은 커밋이 멈추는 때가 아니라 tuono가 다른 방식으로 갈아타는 때다.

### 이 크레이트의 진짜 이득은 처리량이 아니라 프로세스 경계의 제거다

벤치마크가 측정하려 한 것과 이 크레이트가 실제로 주는 것이 어긋나 있다.
문서는 액틱스와 fastify의 초당 요청 수를 나란히 놓고 8.4배라는 숫자를 만든다.
그러나 앞서 짚었듯 그 숫자는 렌더링 성능을 분리해 내지 못하며, 설령 정확하더라도 실무에서 SSR 처리량이 병목인 서비스는 흔하지 않다.

같은 애플리케이션을 Rust 서버와 Node 렌더링 서비스로 나누어 운영해 본 사람 입장에서 실제 이득은 다른 데 있다.
Node 사이드카가 사라진다는 것이다.
프로세스가 하나면 배포 단위가 하나이고, 컨테이너가 하나이고, 헬스 체크가 하나이고, 두 프로세스 사이의 HTTP 왕복과 그 왕복에서 생기는 타임아웃 설정과 커넥션 풀과 재시도 정책이 전부 사라진다.
Rust 핸들러가 데이터를 가져와 곧바로 같은 프로세스 안에서 렌더 함수를 호출하므로 직렬화 경계도 props JSON 하나로 줄어든다.

이 관점에서 보면 이 크레이트의 경쟁 상대는 fastify가 아니다.
Node 렌더링 서비스를 별도로 띄우는 운영 방식이고, 비교해야 할 지표는 처리량이 아니라 배포 복잡도와 장애 지점 수와 지연의 꼬리 분포다.
특히 꼬리 지연이 그렇다.
프로세스 간 HTTP 왕복이 있으면 네트워크 지터와 커넥션 재수립이 p99를 만드는데, 같은 프로세스 안의 함수 호출에는 그 항이 없다.

그래서 이 크레이트가 스스로를 파는 방식이 자기에게 불리하다.
“엄청나게 빠르다”는 주장은 검증 대상이 되고 앞 절에서 본 대로 검증에서 약해진다.
“Node 프로세스를 없앤다”는 주장은 검증할 필요가 거의 없고 반박하기도 어렵다.
`benches/README.md`가 다섯 버전째 갱신되지 않은 것도 어쩌면 저자 자신이 그 숫자에 큰 의미를 두지 않기 때문일 수 있다.

### 아이솔레이트를 스레드마다 두는 모델은 메모리로 동시성을 사는 것이며 상한이 있다

`thread_local!` 패턴은 코드로 보면 우아하다.
락이 없고, 경합이 없고, `RefCell`의 런타임 검사조차 같은 스레드 안이라 사실상 공짜다.
그러나 이 우아함은 자원 배분 결정을 배포 시점으로 미룬 결과다.

액틱스는 기본적으로 CPU 코어 수만큼 워커를 띄우므로, 16코어 서버에서는 V8 아이솔레이트가 16개 만들어지고 번들이 16번 파싱된다.
번들 크기가 커질수록 이 비용이 선형으로 늘고, 리액트 애플리케이션 번들은 대개 작지 않다.
동시성을 늘리려면 워커를 늘려야 하는데 워커를 늘리면 메모리가 늘고, 메모리 상한에 걸리면 동시성 상한에 걸린다.
Node가 단일 프로세스에서 이벤트 루프로 많은 요청을 처리하다가 CPU 바운드인 렌더링에서 막히는 것과 정확히 대칭인 실패 양상이다.

이 절충이 잘 맞는 구간이 분명히 있다.
번들이 작고 코어가 넉넉한 컨테이너에서는 메모리 몇백 메가바이트를 더 쓰고 락 없는 병렬성을 얻는 것이 좋은 거래다.
반대로 메모리가 빡빡한 소형 인스턴스에 배포하거나 코어가 많은 기계 한 대에 밀어 넣으려는 경우에는 정확히 반대가 된다.
문서가 이 절충을 명시하지 않아서 사용자는 배포 후에야 이 사실을 알게 된다.

할 일 목록의 V8 스냅숏 항목이 이 문제를 절반만 겨냥한다는 점도 짚어 둘 만하다.
스냅숏은 파싱과 초기 평가를 건너뛰어 아이솔레이트 생성 시간을 줄이지만, 각 아이솔레이트가 자기 힙을 갖는다는 사실은 바꾸지 못한다.
메모리를 실제로 줄이려면 아이솔레이트 간 코드 캐시 공유나 Locker API를 통한 아이솔레이트 공유가 필요한데, 후자는 README가 명시적으로 배제한 방향이다.
곧 이 크레이트의 확장 한계는 상류 라이브러리가 아니라 자기 설계 결정에서 온다.

### 이 계층이 사라지는 방향은 이미 저장소 안에 적혀 있다

README의 마지막 할 일 항목은 javy를 이용한 JavaScript의 WASM 컴파일 탐색이다.
열린 이슈 하나는 wasip2 타깃으로 컴파일할 수 없으니 `rusty_v8`을 대체할 수 있느냐고 묻는다.
두 항목이 같은 미래를 가리킨다.

그 미래에서 이 크레이트의 구조는 통째로 바뀐다.
JavaScript 번들을 미리 WebAssembly로 컴파일해 둘 수 있다면 서버는 V8 대신 훨씬 작은 WASM 런타임만 있으면 되고, 그러면 4.6MB 크레이트도 V8 버전 고정도 타깃 제약도 사라진다.
아이솔레이트마다 힙을 복제하는 문제도 WASM 인스턴스의 훨씬 가벼운 메모리 모델로 옮겨 간다.
실행 속도는 아마 V8보다 느리겠지만, 앞서 정리했듯 이 계층에서 중요한 것은 최고 처리량이 아니라 프로세스 경계의 제거이므로 그 손실이 결정적이지 않을 수 있다.

다만 이 전환에는 아직 큰 장애물이 있다.
javy 같은 도구는 JavaScript 인터프리터를 WASM으로 컴파일해 그 안에서 스크립트를 돌리는 방식이라 리액트의 서버 렌더링처럼 무거운 작업에서 성능 손실이 크고, 최신 언어 기능 지원도 V8에 미치지 못한다.
동시에 이 접근을 진지하게 추구하는 곳은 대개 엣지 런타임 벤더이고, 그들의 목표는 라이브러리가 아니라 자기 플랫폼이다.

그래서 이 저장소가 남긴 두 줄이 흥미로운 위치에 있다.
크레이트 저자가 자기 크레이트의 핵심 의존성을 언젠가 걷어내고 싶어 한다는 것을 문서로 남긴 셈이며, 그것이 이 계층의 성격을 말해 준다.
`ssr_rs`가 하는 일은 본질적으로 두 런타임 사이의 임시 다리이고, 다리는 양쪽 땅이 붙으면 필요 없어진다.
이 크레이트를 채택할 때 물어야 할 마지막 질문은 그 다리를 얼마나 오래 쓸 계획인가이며, tuono처럼 프레임워크 내부에 감춰 두면 나중에 갈아 끼우기 쉽고 애플리케이션 코드에서 직접 호출하면 그만큼 어려워진다.
