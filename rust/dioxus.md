# Dioxus: 하나의 Rust 코드베이스로 웹과 데스크톱과 모바일을 겨냥하는 프레임워크

<https://dioxuslabs.com/>

<https://github.com/dioxuslabs/dioxus>

## 소개

Dioxus는 웹과 데스크톱과 모바일을 하나의 코드베이스로 만드는 Rust 풀스택 앱 프레임워크다.
설정이 필요 없는 초기화, 통합된 핫 리로딩, 시그널 기반 상태 관리를 내세우며, 서버 함수로 백엔드 기능을 더하고 자체 CLI로 번들링한다고 README가 요약한다.
저장소는 2021년 1월 15일에 만들어졌고, 이 문서 작성 시점 기준 스타 38,596개, 포크 1,835개, 열린 이슈 732개이며 라이선스는 MIT 또는 Apache-2.0 이중이다.
crates.io 기준 누적 다운로드는 224만 6천여 회이고 최근 다운로드가 76만 2천여 회이며, 안정 최신은 2026년 7월 30일의 0.7.10, 최신은 하루 뒤 나온 0.8.0-alpha.1이다.

예제 코드는 여섯 줄이다.
`use_signal(|| 0)`으로 시그널을 만들고 `rsx!` 매크로 안에서 `h1`과 두 개의 `button`을 선언하며, `onclick`에 `move |_| count += 1`을 넘긴다.
React의 훅과 JSX에 대응하는 형태이되 상태 갱신이 `count += 1`처럼 직접 대입으로 표현된다는 점이 다르다.

내세우는 고유 기능은 여섯 가지다.
세 줄로 만드는 크로스플랫폼 앱, React와 Solid와 Svelte의 장점을 결합했다는 상태 관리, 내장된 타입 안전 풀스택 웹 프레임워크, 웹과 macOS와 리눅스와 윈도우 배포를 위한 통합 번들러, 서브초 단위 Rust 핫 패칭과 에셋 핫 리로딩이다.
`dx serve` 한 명령으로 앱이 돌고 마크업과 스타일을 고치면 밀리초 단위로 반영되며, 실험적인 `dx serve --hotpatch`는 Rust 코드를 실시간으로 갱신한다고 설명한다.

풀스택 기능은 axum과 깊이 통합되어 있다.
웹소켓, SSE, 스트리밍, 파일 업로드와 다운로드, 서버 사이드 렌더링, 폼, 미들웨어, 핫 리로드 같은 내장 기능 중에서 고르거나 완전히 직접 구성해 기존 axum 백엔드를 통합할 수 있다고 밝힌다.

렌더러가 여러 개라는 점이 이 프로젝트의 구조적 특징이다.
web-sys, 웹뷰, 서버 사이드 렌더링, 라이브뷰로 렌더링할 수 있고 실험적인 WGPU 기반 렌더러도 있으며, Bevy나 WGPU 안에 Dioxus를 넣거나 임베디드 리눅스에서 돌릴 수도 있다고 적는다.
데스크톱은 웹뷰 외에 실험적으로 WGPU나 Skia 기반 Freya로 렌더링할 수 있고, 모바일도 같은 선택지를 갖는다.
shadcn/ui와 Radix Primitives를 본뜬 일급 기본 컴포넌트 모음도 제공한다고 밝힌다.

크기 주장이 구체적이다.
웹에서는 `.avif` 생성과 `.wasm` 압축과 최소화를 활용해 50kb 미만 웹앱을 만들 수 있고 데스크톱과 모바일 앱은 5mb 미만이라고 하며, 지원 플랫폼 표에서는 단순한 “hello world”가 약 50kb로 React에 견줄 만하고 데스크톱 바이너리는 3mb 미만이라고 적는다.
모바일은 `dx serve --platform android`로 몇 초 만에 에뮬레이터나 실기기에서 돌고 Java와 Objective-C를 최소 오버헤드로 직접 호출한다고 밝힌다.
서버 사이드 렌더링 항목에는 서스펜스와 하이드레이션, 서버 함수, 추출자와 미들웨어와 라우팅 통합, 정적 사이트 생성과 증분 재생성이 나열되어 있다.

프로젝트 운영에 대한 서술도 README에 있다.
Dioxus가 사이드 프로젝트에서 전임 엔지니어 소규모 팀으로 성장했으며 FutureWei와 Satellite.im과 GitHub Accelerator 프로그램의 후한 지원 덕분에 전임으로 일할 수 있다고 밝힌다.
장기 목표는 고품질 유료 엔터프라이즈 도구를 제공해 Dioxus가 자립하는 것이며, 채택에 관심 있는 회사는 연락해 달라고 적는다.
기여자는 100명 이상이 집계되고 상위는 `jkelleyrtp` 3,135건, `ealmloff` 2,242건, `mrxiaozhuox` 343건 순이며, 최근 커밋은 2026년 8월 10일까지 여러 사람 이름으로 이어진다.
README는 한국어를 포함해 다섯 개 언어 번역본을 링크한다.

## 분석

### 이 프로젝트의 진짜 주장은 크로스플랫폼이 아니라 렌더러 교체 가능성이다

“세 줄로 만드는 크로스플랫폼 앱”이라는 표제 문구는 이 프로젝트를 Flutter나 React Native와 같은 칸에 놓는다.
그러나 README를 끝까지 읽으면 더 특이한 구조가 드러난다.
같은 컴포넌트 트리를 web-sys로 DOM에 쓰거나, 웹뷰에 띄우거나, 서버에서 문자열로 렌더링하거나, 라이브뷰로 웹소켓 너머에 그리거나, WGPU로 GPU에 직접 그릴 수 있다.
Bevy 안에 넣거나 임베디드 리눅스에서 돌릴 수도 있다고 적는다.

이 목록은 크로스플랫폼과 다른 이야기다.
크로스플랫폼은 하나의 소스가 여러 운영체제에서 도는 것을 뜻하지만, 여기서는 하나의 소스가 여러 렌더링 백엔드에서 돈다.
Flutter는 렌더러가 하나(Skia 계열)이고 React Native는 플랫폼 위젯 하나이며, 그 단일성이 각 프레임워크의 일관성과 한계를 동시에 만든다.
Dioxus는 그 자리를 비워 두고 갈아 끼우게 했다.

이 설계가 별도 프로젝트들을 낳았다.
CSS 레이아웃 엔진 Taffy와 HTML/CSS 렌더러 Blitz가 같은 조직에 있고 README와 홈페이지 모두 그것들을 나란히 링크한다.
`jkelleyrtp`가 HN에서 Tauri와의 관계를 정리하며 “우리는 오랫동안 blitz라는 네이티브 HTML/CSS 라이브러리를 만들어 왔고 곧 안정화된다”고 밝힌 것[^jkelleyrtp-blitz]이 그 방향을 보여 준다.
즉 장기 계획은 웹뷰를 벗어나 자체 렌더링 스택을 갖는 것이며, 크로스플랫폼은 그 스택이 완성되었을 때의 결과이지 현재의 성취가 아니다.

### React Native와 같은 아키텍처라는 자기 규정이 논쟁의 절반을 정리한다

HN 스레드에서 반복된 첫 번째 혼란은 Tauri와의 관계였다.
`datadeft`가 Tauri와 Dioxus가 비슷한 프로젝트냐고 물었고[^datadeft], `jasonjmcghee`는 Electron과 React/React Native의 비교에 가깝다며 Tauri가 웹 앱을 창에 담아 Rust 코드와 연결하는 방식이고 Dioxus는 순수 Rust로 웹 앱을 쓰는 방식이라고 답했다.[^jasonjmcghee]
`resoluteteeth`는 문서를 보고 Dioxus가 데스크톱 렌더러로 Tauri를 쓰는 것 같다고 적었다가 나중에 그 서술이 부정확했다고 스스로 정정했다.[^resoluteteeth]

`jkelleyrtp`의 답변이 그 오해를 풀었다.
Tauri를 반드시 쓰는 것이 아니라 Tauri가 유지하는 `wry`라는 라이브러리를 쓰는 것이며, 그것은 사실상 Rust web-view 라이브러리의 더 잘 유지되는 포크라는 설명이다.
Tauri와 좋은 친구 사이지만 그들이 유지하는 라이브러리 하나를 쓴다는 이유로 사람들이 자기들 아키텍처와 철학을 오해하는 것 같다고 덧붙였다.[^jkelleyrtp-blitz]

더 유용한 정리는 `echelon`이 던진 질문 묶음에 대한 답에 있다.
데스크톱과 모바일에서 네이티브 앱으로 도는지, egui 같은 즉시 모드인지, 웹에서는 캔버스에 그리는지 DOM에 쓰는지, 웹 워커로 멀티스레딩이 되는지, 다른 웹 앱과 섞을 수 있는지를 한꺼번에 물었다.[^echelon]
`jkelleyrtp`는 Dioxus가 현대 React Native와 아키텍처가 비슷하며 Rust 코드가 네이티브로 돌고 VM 없이 JNI와 Objective-C를 자유롭게 호출할 수 있다고 답했다.
유지 모드(retained mode)이고 React/Svelte 앱의 아키텍처에 가깝게 머물며, 웹에서는 DOM과 직접 대화하고 SSR과 하이드레이션과 스트리밍 HTML과 Next.js 같은 풀스택 프레임워크를 웹어셈블리로 제공한다는 것이다.
상태 관리가 멀티스레드이고 많은 사용자가 웹 워커와 PWA를 쓰고 있으며, 다중 프레임워크 공존에는 덜 집중했지만 React를 Dioxus에 넣고 Dioxus를 React에 넣는 것이 확실히 가능하다고 했다.[^jkelleyrtp-arch]

이 한 답변이 앞선 여러 추측을 정리한다는 사실 자체가 문서의 문제를 시사한다.
아키텍처를 한 문단으로 설명하는 자리가 README에 없고, 그래서 같은 질문이 스레드마다 반복된다.

### 전임 코어 팀이라는 사실이 이 프로젝트를 Rust GUI 생태계에서 예외로 만든다

Rust UI 프로젝트는 대개 개인이나 소수의 여가 시간으로 유지된다.
README가 별도 절을 두어 사이드 프로젝트에서 전임 엔지니어 소규모 팀으로 성장했고 FutureWei와 Satellite.im과 GitHub Accelerator의 지원 덕분에 전임으로 일한다고 밝히는 것은 그 예외성을 알고 있다는 표시다.
기여자 통계도 이를 뒷받침해서 상위 두 명이 3,135건과 2,242건으로 압도적이고, 그 아래로 수십 명이 이어진다.

이 차이가 커뮤니티에서 어떻게 읽히는지가 흥미롭다.
`weinzierl`은 Leptos를 사랑한다며 그들이 최소한의 예산으로 만든 것을 최소 50만 달러의 벤처 자본을 조달한 Dioxus와 비교해 보라고 적었고[^weinzierl], `chromatin`은 Leptos가 한 개인의 창작물이고 그 개인이 성공회 사제라고 알고 있는 반면 Dioxus는 벤처 투자를 받았다는 대조가 흥미롭다고 했다.[^chromatin]
`klabb3`는 더 날카롭게 “VC 투자를 받은 기본적인 기능의 UI 라이브러리”라는 표현을 썼다.[^klabb3]

정작 비교 대상이 된 쪽의 반응이 이 대조를 정리했다.
Leptos의 Greg 본인이 스레드에 나와, 자신은 오픈소스에 시간을 조금 쓸 수 있는 행복한 처지이지만 전업으로 할 수도 없고 원하지도 않으며 스타트업을 세울 생각도 없고 약간의 GitHub 후원금이 커피값을 대는 정도이며 Leptos는 상업적 벤처가 아니고 앞으로도 아닐 것이라고 밝혔다.
그리고 동시에 Dioxus가 자금을 조달해 Jon이 전임으로 일하고 다른 사람들을 전임으로 데려올 수 있게 된 것이 정말 기쁘며 이것은 밀물이 모든 배를 띄우는 상황이고 자본이 이런 것들로 흘러가는 편이 100% 낫다고 했다.[^gbjma]

이 답변이 중요한 이유는 자금 조달이 프로젝트 품질의 대리 지표가 아니라는 점을 당사자가 확인해 주기 때문이다.
동시에 그것이 무엇의 지표인지는 남는다.
전임 팀은 릴리스 주기와 문서 품질과 이슈 응답을 만들고, 그것들이 채택 결정에 실제로 영향을 준다.
0.7.10 안정판과 0.8.0-alpha가 하루 차이로 나오고 최근 커밋이 여러 사람 이름으로 매일 이어지는 상태는 여가 프로젝트가 만들기 어려운 종류의 것이다.

### 0.7 문서와 0.6 문서가 공존하는 상태가 개발 속도의 표시다

README의 링크들은 `learn/0.7/`을 가리킨다.
그런데 홈페이지의 내비게이션 항목 대부분은 `learn/0.6/guide`, `learn/0.6/guides/desktop/`, `learn/0.6/guides/fullstack/`처럼 0.6을 가리키고, 0.7 링크는 하나뿐이다.
저장소 예제 안내도 메인 브랜치의 예제가 git 버전을 대상으로 하니 최신 안정 릴리스용 예제는 v0.6 브랜치를 보라고 안내한다.

세 곳이 서로 다른 버전을 가리키는 상태는 문서 관리 실패로 읽히기 쉽지만, 이 프로젝트에서는 다른 원인일 가능성이 크다.
0.5가 2024년 3월, 0.6이 2024년 12월, 0.7이 2025년 11월에 나왔고 그 사이사이에 패치가 촘촘히 들어갔으며 지금은 0.8 알파가 진행 중이다.
메이저 릴리스마다 API가 상당히 바뀌는 0.x 단계에서 문서를 버전별로 통째로 유지하면 갱신 지점이 여러 곳으로 흩어진다.

이 상태가 사용자에게 만드는 비용은 실질적이다.
검색으로 도착한 문서가 어느 버전인지 확인해야 하고, 예제를 복사하기 전에 브랜치를 확인해야 한다.
README가 그 위험을 알고 예제 절 맨 앞에 경고를 둔 것은 좋은 처리이지만, 홈페이지 내비게이션이 0.6을 가리키는 것은 그 경고가 닿지 않는 자리다.

## 비평

### 웹에서의 가치 제안이 가장 약한데 표제는 웹을 앞세운다

README의 지원 플랫폼 표에서 웹이 맨 위에 있고, 홈페이지 표제도 “풀스택 웹, 데스크톱, 모바일”의 순서다.
그런데 스레드에서 가장 근본적인 반론이 정확히 웹을 겨냥했다.

`klabb3`는 표준화되고 성숙하고 효과적인 것을 왜 VC 투자를 받은 기본적인 기능의 UI 라이브러리로 대체하려 하는지 이해할 수 없다고 적었다.
Rust를 정말로 좋아한다면 가설적 매력은 알겠지만, 웹을 버리려는 욕망은 이해할 수 없으며 웹은 세계 8대 불가사의 같은 것이고, DOM과 접근성과 렌더링과 JIT과 샌드박싱을 처음부터 다시 만드는 것은 새 운영체제를 만드는 일에 가깝다는 것이다.[^klabb3]

`jkelleyrtp`의 반박은 오해를 정정하는 형태였다.
dioxus-web은 기본적으로 React나 SolidJS나 Svelte 같은 것이며 다른 웹 프레임워크와 똑같이 DOM에 쓰고 DOM 이벤트를 처리한다는 것이다.
Dioxus가 다른 지점은 네이티브 플랫폼이며 거기서 웹 같은 API를 네이티브 위젯에 제공하려 하고, 브라우저 전체가 아니라 3.5mb에 들어가는 렌더링 엔진만 배포하는 일렉트론 같은 것이라고 설명했다.
네이티브 플랫폼 사용자들이 중간 매개 없이 시스템 API에 접근하는 것을 좋아하며 스레드를 띄우고 유닉스 소켓과 대화하고 FFI를 호출할 수 있고, 일렉트론 같은 것은 무겁고 느리며 UI와 시스템 사이에 IPC 경계를 둔다는 것이다.[^jkelleyrtp-web]

이 반박은 정확하지만 동시에 웹에서의 차별점이 없다는 것을 인정한다.
DOM에 쓰고 DOM 이벤트를 처리하는 것이 React와 같다면, 웹에서 Dioxus를 고를 이유는 Rust를 쓰고 싶다는 것뿐이다.
그리고 그 이유는 비용이 따른다.
README가 “hello world”가 약 50kb로 React에 견줄 만하다고 적은 것은 사실 방어적인 문장이다.
같은 크기라는 것은 웹어셈블리 런타임과 Rust 표준 라이브러리를 실어 보내고도 겨우 비긴다는 뜻이며, 애플리케이션이 커질수록 그 기준선이 어떻게 움직이는지는 나와 있지 않다.

`cardanome`이 이 계산을 다르게 표현했다.
가비지 컬렉션 언어로 쓸 수 없는 사용 사례가 보이지 않으며, Rust는 명령줄 앱과 도구와 시스템 프로그래밍에 훌륭하지만 UI는 할 수는 있어도 Rust의 강점을 살리지 못하고, Tauri는 최소한 사람들이 자기 JS 지식을 쓰게 해 주므로 훨씬 팔기 쉽다는 것이다.
Rust를 쓰는 것이 즐겁다면 그것으로 충분하지만 대부분에게 사업적으로 말이 되지는 않는다고 덧붙였다.[^cardanome]

### “세 줄로 크로스플랫폼”이라는 문구가 감추는 것

README의 첫 번째 고유 기능은 세 줄의 코드로 만드는 크로스플랫폼 앱이다.
이 문구는 빌드 대상을 늘리는 것이 세 줄이라는 뜻이지 앱이 세 줄로 완성된다는 뜻은 아니지만, 읽는 사람에게 남는 인상은 후자에 가깝다.

`risyachka`가 이 인상을 정면으로 반박했다.
모바일과 데스크톱과 웹을 모두라는 말은 실제로 멀티플랫폼 앱을 만들어 보기 전까지만 좋게 들리며, 99% 경우에 그 셋이 공통점이 거의 없다는 것을 알게 된다는 것이다.
UI는 보통 플랫폼마다 완전히 다시 디자인해야 하고 각각이 다른 곳에는 없고 앞으로도 없을 고유 기능을 가지며, `if os=='desktop'` 같은 분기가 잔뜩 필요해지거나 안드로이드처럼 더 세분화된 분기가 필요해진다는 것이다.
앱이 작지 않다면 각 플랫폼의 전문 프레임워크로 UI를 다시 만드는 편이 오히려 단순하고, 요즘은 기존 프레임워크가 아주 성숙해서 이것이 아주 단순한 문제라고 덧붙였다.[^risyachka]

이 지적이 Dioxus에 특히 아픈 이유는 렌더링 전략이 플랫폼마다 다르기 때문이다.
웹에서는 DOM에 쓰고, 데스크톱과 모바일에서는 웹뷰나 WGPU나 Skia로 그린다.
같은 `rsx!` 코드가 세 곳에서 돈다는 것과 세 곳에서 같게 보인다는 것은 다른 이야기이며, 웹뷰와 WGPU 렌더러 사이에도 차이가 있다.
README는 이 차이를 다루지 않고 지원 플랫폼 표에 렌더링 방식만 나열한다.

`highwaylights`가 같은 지점을 다른 각도에서 짚었다.
아주 인기를 얻을 수도 있겠지만 “마법 같은”과 “엄청나게 빠른” 같은 단어가 즉시 프레임워크 피로를 유발하며, 성공하면 다른 모든 프레임워크를 낡게 만들 수 있다는 말은 대단히 대담한 주장이고, .NET이 이미 여러 해에 걸쳐 여러 번 그렇게 했지만 다른 프레임워크들이 여전히 존재하는 이유는 모든 문제에 망치가 필요하지는 않기 때문이며 해결하려는 사용 사례가 늘수록 만능선수 문제를 겪는다는 것이다.[^highwaylights]

`jkelleyrtp`의 답이 이 대목에서 가장 정직하다.
자기들 핫 리로딩이 Rust 생태계에서는 “마법”이며 그 글의 원래 의도된 독자가 Rust 진영이었고, 형식 문자열과 간단한 Rust 코드를 핫 리로딩하는 것은 Rust 세계에서 사실상 마법이라는 것이다.
“엄청나게 빠른”은 농담조로 쓴다면서도 Dioxus가 정말 빠르며 Rust와 DOM 사이를 아주 빠르게 만드는 데 많은 연구 개발을 했고 sledgehammer 바인딩 계층이 JS 프레임워크 벤치마크에서 SolidJS보다 빠르다고 덧붙였다.[^jkelleyrtp-magic]
곧 마케팅 문구의 기준점이 웹 프레임워크 생태계가 아니라 Rust 생태계라는 자백이며, 그것이 이 프로젝트를 웹 프레임워크로 읽는 독자와 어긋나는 이유다.

### 컴파일 시간이 핫 리로드 서사와 정면으로 충돌한다

README는 밀리초 단위 반영과 서브초 Rust 핫 패칭을 앞세운다.
실제 사용자 보고는 다르다.

`bobajeff`는 Dioxus를 시험해 볼 때 컴파일 시간이 문제였으며 핫 리로드가 눈에 띄게 그리 뜨겁지 않았고 Node.js 세계에서 익숙한 것과 극명한 대조를 이뤘다고 적었다.[^bobajeff]
`davidatbu`는 Leptos를 쓰면서 컴파일 시간을 문제로 들었고 그것이 Leptos 문제가 아니라 Rust 문제라고 단서를 달았다.[^davidatbu]
`marcyb5st`는 비슷한 문제를 겪었지만 프로젝트를 카고 워크스페이스 안의 여러 크레이트로 쪼개 리로드 시간을 10~15초에서 약 4초로 줄였다고 우회법을 공유했다.[^marcyb5st]

이 격차가 문서화되지 않았다는 점이 비판의 요지다.
핫 리로딩에는 두 종류가 있는데, 마크업과 스타일 변경은 재컴파일 없이 반영되므로 실제로 밀리초 단위일 수 있고, Rust 로직 변경은 재컴파일이 필요하므로 프로젝트 크기에 비례한다.
README는 이 구분을 “마크업과 스타일을 고치면 밀리초 단위”와 “실험적인 `--hotpatch`는 Rust 코드를 실시간 갱신”이라는 두 문장으로 스치듯 표현하지만, 실험적이라는 단어의 무게와 재컴파일이 필요한 경우의 실제 대기 시간은 알려 주지 않는다.

`marcyb5st`의 우회법이 필요했다는 사실이 이 문제의 성격을 말해 준다.
프로젝트를 크레이트로 쪼개는 것은 프레임워크가 아니라 사용자가 해야 하는 작업이고, 그것을 알려 주는 것은 README가 아니라 남의 블로그 글이다.
“설정이 필요 없는 초기화”를 내세우는 프레임워크에서 좋은 개발 경험을 얻으려면 워크스페이스 구조를 스스로 설계해야 한다면, 그 설정은 사라진 것이 아니라 문서 바깥으로 밀려난 것이다.

### 수익 모델이 4년째 문장 하나와 대기자 명단으로 남아 있다

README는 장기 목표가 고품질 유료 엔터프라이즈 도구를 제공해 자립하는 것이라고 밝힌다.
그 계획의 현재 상태를 확인할 수 있는 곳은 홈페이지의 `/deploy` 페이지다.
그 페이지의 제목은 “Dioxus Deploy”이고 바로 아래 문구는 “Coming soon!”이며 행동 유도 버튼은 “Join the Waitlist”다.
빌드와 배포와 확장 세 범주에 자동 미리보기, 실시간 협업, 푸시 투 디플로이, 앱스토어 배포, 호스팅 LiteFS와 SQLite, 추적 로그 시각화, 크래시 분석, 스케일 투 제로, A/B 테스트 같은 항목이 나열되어 있지만 전부 예고다.
`/pricing`과 `/enterprise`는 404를 반환한다.

같은 페이지 하단에 “© 2024 Dioxus Labs”가 적혀 있고, 헤더의 GitHub 스타 표시는 24.5k인데 실제 저장소는 38,596개다.
2026년 8월에 확인한 홈페이지가 2024년 저작권 표시와 1만 4천 개 뒤처진 스타 수를 달고 있다는 것은 이 사이트가 오래 손대지 않았다는 뜻이며, 하루 단위로 커밋이 들어오는 저장소와 대조된다.

이 상태가 문제가 되는 이유는 프레임워크 채택 결정에서 지속 가능성이 기능만큼 중요하기 때문이다.
README가 스스로 이 프로젝트가 후원에 의존한다고 밝히고 자립 계획을 제시했으므로, 그 계획의 진척이 곧 프로젝트의 미래에 대한 정보다.
`klabb3`가 “VC 투자를 받은 UI 라이브러리”라는 표현을 쓴 것[^klabb3]과 `weinzierl`이 자금 규모를 언급한 것[^weinzierl]은 그 정보를 요구하는 방식이었고, 답은 여전히 대기자 명단이다.

오해를 피하기 위해 덧붙이면 이것은 프로젝트가 위태롭다는 뜻이 아니다.
릴리스 주기와 커밋 활동과 기여자 분포는 건강하다.
다만 자립 계획이 실행되지 않은 채로 남아 있는 동안 이 프로젝트의 지속성은 세 후원자의 의사에 달려 있으며, 그 사실이 문서에 명시되어 있으면서도 그 다음 문장이 4년째 업데이트되지 않았다는 점이 채택자가 스스로 계산해야 할 항목이다.

## 인사이트

### 렌더러를 갈아 끼울 수 있다는 설계가 이 프로젝트의 진짜 자산이자 최대 위험이다

`klabb3`가 DOM과 접근성과 렌더링과 JIT과 샌드박싱을 처음부터 다시 만드는 것이 새 운영체제를 만드는 일에 가깝다고 한 것[^klabb3]은 비판으로 쓰였지만 사실은 이 프로젝트가 하고 있는 일에 대한 정확한 서술이다.
Taffy가 CSS 레이아웃을 다시 구현하고, Blitz가 HTML/CSS 렌더링을 다시 구현하고, WGPU 렌더러가 그리기를 다시 구현한다.
이것들이 전부 같은 조직 아래 있고 README와 홈페이지가 나란히 링크한다.

이 방향이 왜 자산인지는 배포 형태를 보면 보인다.
브라우저 전체가 아니라 렌더링 엔진만 3.5mb로 실어 보낼 수 있다면, 그것은 일렉트론이 해결하지 못한 문제를 해결한 것이다.
일렉트론 앱이 100mb를 넘고 시작이 느린 이유는 크로미움 전체를 담기 때문이고, Tauri가 시스템 웹뷰를 쓰는 이유는 그것을 피하려는 것이지만 그 대가로 플랫폼마다 다른 렌더링 엔진을 상대해야 한다.
자체 렌더러는 두 문제를 동시에 푼다.

동시에 이것이 최대 위험이다.
브라우저 엔진을 다시 만드는 일이 얼마나 큰지는 Servo와 Ladybird가 보여 주고 있고, 그 프로젝트들이 전임 인력을 갖고도 수년째 진행 중이다.
Blitz는 그보다 좁은 목표를 갖지만, 앱 개발자가 CSS의 어느 부분까지 쓸 수 있는지가 실질적 제약이 된다.
README가 WGPU 렌더러를 실험적이라고 부르고 `jkelleyrtp`가 GPU 관련 작업이 초기 단계지만 능력이 있으며 최종 비전은 React Native Skia처럼 인터페이스 대부분을 GPU에 그리고 상호작용은 네이티브 시스템 API로 처리하는 것이라고 밝힌 것[^jkelleyrtp-magic]이 현재 위치를 말해 준다.

그러므로 이 프로젝트를 평가할 때 물어야 할 것은 오늘의 기능이 아니라 이 계층이 완성될 가능성이다.
웹뷰 기반으로만 쓴다면 Tauri와의 차이는 언어와 컴포넌트 모델뿐이고, 자체 렌더러가 완성되면 완전히 다른 제품이 된다.
두 미래 사이의 거리가 이 프로젝트에 대한 판단의 폭을 정한다.

### 자본이 오픈소스 프레임워크에 들어오면 비교 축이 기능에서 지속성으로 옮겨 간다

Leptos와 Dioxus를 비교하는 대화가 기능 비교로 시작해 자금 조달 비교로 끝나는 패턴이 스레드에 그대로 남아 있다.
`ewuhic`이 Dioxus의 생태계가 크게 부족하고 컴포넌트 라이브러리가 하나도 없다며 자기는 경쟁자인 Leptos를 추적하고 쓴다고 적은 것[^ewuhic]에서 시작해, `weinzierl`의 예산 대조[^weinzierl]와 `chromatin`의 개인 대 벤처 대조[^chromatin]로 이어진다.

이 이동이 일어나는 이유가 있다.
0.x 단계의 프레임워크에서 오늘의 기능 차이는 몇 달이면 뒤집힐 수 있지만, 누가 몇 년간 이것을 유지할 것인가는 뒤집기 어렵다.
그래서 사용자는 기능 목록 대신 자금과 인력을 읽으려 하고, 그 읽기가 종종 서투르다.
`feznyng`이 Leptos는 웹 전용이고 Dioxus는 웹과 모바일과 데스크톱이니 사과와 오렌지 비교 아니냐고 지적한 것[^feznyng]이 그 서투름을 교정하는 시도였다.

Leptos 저자 본인의 답변이 이 비교의 올바른 형태를 보여 준다.
자기는 전업으로 할 수도 없고 원하지도 않으며 Leptos는 상업적 벤처가 아니고 앞으로도 아닐 것이라고 자기 프로젝트의 성격을 규정한 뒤, Dioxus의 자금 조달을 밀물이 모든 배를 띄우는 상황으로 환영했다.[^gbjma]
곧 두 프로젝트는 경쟁 관계가 아니라 다른 종류의 프로젝트이며, 사용자가 골라야 할 것은 “더 나은 프레임워크”가 아니라 “내 프로젝트의 수명에 맞는 유지 모델”이다.

여기서 나오는 실천적 규칙은 자금 조달을 품질 신호로 읽지 말고 위험의 형태를 바꾸는 요인으로 읽으라는 것이다.
후원받는 프로젝트는 빠르게 움직이지만 후원이 끊기면 급격히 멈추고, 개인 프로젝트는 느리게 움직이지만 저자가 계속 쓰는 한 계속 존재한다.
Dioxus의 README가 세 후원자 이름을 밝히고 자립 목표를 적은 것은 그 위험을 공개한 것이며, 앞 절에서 본 대로 그 계획의 진척이 멈춰 있다는 사실이 그 공개를 계속 유효하게 만든다.

### 크로스플랫폼 프레임워크의 성패는 렌더링이 아니라 컴포넌트 생태계에서 갈린다

`ewuhic`의 지적, 곧 컴포넌트 라이브러리가 하나도 없다는 것[^ewuhic]에 대해 `diablozzq`는 컴포넌트 라이브러리가 시급한 핵심 기능이며 시작은 했지만 개발이 본격화되지 않았고 우선순위가 밀렸다며, 기본 개발자에게 직접 만들기는 힘든 일이라고 덧붙였다.[^diablozzq]
코어 개발자 `Evan-Almloff`가 좋은 커뮤니티 컴포넌트 라이브러리가 여럿 있다며 0.6을 지원하는 `daisy_rsx`를 예로 들었지만[^evan], 그 답변이 커뮤니티 라이브러리를 가리켰다는 사실 자체가 당시 일급 제공물이 없었음을 확인한다.

현재 README에는 그 답이 들어가 있다.
shadcn/ui와 Radix Primitives를 본뜬 일급 기본 컴포넌트 모음을 제공한다는 절이 생겼고 스크린샷도 붙어 있다.
2024년 12월의 지적이 그 뒤 릴리스에 반영된 것이며, 이 프로젝트가 커뮤니티 피드백에 반응한다는 증거다.

그런데 이 선택 자체가 앞서 본 긴장을 키운다.
shadcn/ui와 Radix는 웹 접근성 패턴을 HTML과 ARIA 위에 구현한 것이고, 그 모델을 웹뷰가 아닌 WGPU 렌더러로 옮기려면 접근성 트리를 직접 만들어야 한다.
`klabb3`가 나열한 항목 중 접근성이 있었던 것[^klabb3]이 우연이 아니며, 이것은 렌더러를 바꾸면 따라오는 비용 중 가장 자주 잊히는 항목이다.

역사적 유비가 있다.
React Native가 초기에 겪은 가장 큰 마찰은 렌더링 성능이 아니라 컴포넌트였다.
플랫폼마다 다른 네이티브 위젯을 하나의 API로 묶으려니 최소 공통분모가 되었고, 그래서 실무에서는 결국 플랫폼별 분기와 네이티브 모듈이 쌓였다.
`risyachka`가 예언한 `if os=='desktop'` 분기의 증식[^risyachka]이 정확히 그 역사의 반복이며, Dioxus가 웹 표준 컴포넌트 모델을 모든 렌더러에 강제하는 방식으로 그것을 피하려 한다는 점이 이번 시도의 차별점이다.
성공한다면 최소 공통분모가 위젯이 아니라 HTML과 CSS가 되며, 그것이 이 프로젝트가 걸고 있는 판돈이다.

### Rust로 UI를 쓰는 비용을 정당화하는 것은 성능이 아니라 배포 형태다

`cardanome`의 반론, 곧 UI는 가비지 컬렉션 언어로 쓸 수 있고 Rust의 강점을 살리지 못한다는 지적[^cardanome]은 성능 축에서 보면 반박하기 어렵다.
버튼을 누르고 목록을 그리는 일에 소유권과 수명이 필요하지 않고, `jkelleyrtp`가 자랑한 sledgehammer 바인딩의 SolidJS 대비 우위[^jkelleyrtp-magic]도 실사용에서 체감되는 종류의 차이는 아니다.

그런데 그가 제시한 대안인 Tauri와 비교하면 다른 축이 보인다.
`jkelleyrtp`가 네이티브 플랫폼 사용자들이 좋아하는 것으로 든 것은 속도가 아니었다.
중간 매개 없이 시스템 API에 접근하고, 스레드를 띄우고, 유닉스 소켓과 대화하고, FFI를 호출하는 것이며, 일렉트론 같은 것이 UI와 시스템 사이에 IPC 경계를 둔다는 점을 문제로 지목했다.[^jkelleyrtp-web]
README도 같은 것을 강조해서 데스크톱 항목에 “IPC 없는 완전한 네이티브 시스템 접근”이 있고 모바일 항목에 “최소 오버헤드로 Java와 Objective-C를 직접 호출”이 있다.

이것은 성능 논거가 아니라 구조 논거다.
Tauri에서는 UI가 JavaScript이고 시스템 작업이 Rust이므로 둘 사이에 직렬화된 메시지 경계가 있고, 그 경계가 타입 안전성과 디버깅과 지연을 모두 건드린다.
Dioxus에서는 UI 코드와 시스템 코드가 같은 언어이고 같은 프로세스이며 같은 타입을 공유하므로 그 경계가 없다.
이것이 [ssr_rs 노트](ssr-rs.md)와 [Tuono 노트](tuono.md)에서 반복해서 확인한 것과 같은 종류의 이득이다.
프로세스나 언어 경계를 없애는 것이 처리량보다 훨씬 자주 실질적인 이유가 된다.

그러므로 이 프레임워크를 채택할지 판단하는 기준은 “Rust가 UI에 적합한가”가 아니라 “이 앱이 시스템과 얼마나 자주 대화하는가”여야 한다.
파일 시스템과 하드웨어와 네이티브 SDK를 자주 건드리는 데스크톱·모바일 앱이라면 경계 제거의 값어치가 크고, 폼과 목록으로 이루어진 웹 앱이라면 그 값어치가 0에 가깝다.
공교롭게도 README가 웹을 지원 플랫폼 표 맨 위에 두고 홈페이지 표제도 웹을 먼저 부르는데, 이 프레임워크의 논거가 가장 강한 자리는 그 목록의 반대쪽 끝이다.
