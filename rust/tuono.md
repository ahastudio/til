# Tuono: JS 런타임 없이 Rust 서버가 React를 렌더링하는 Next.js 대안

<https://tuono.dev/>

<https://github.com/tuono-labs/tuono>

## 소개

Tuono는 Rust를 백엔드로 써서 React 애플리케이션을 만드는 풀스택 웹 프레임워크이며, 사용성과 성능에 강하게 초점을 둔다고 밝힌다.
이름은 천둥을 뜻하는 이탈리아어이고 발음은 “2 Oh No”이며, 왜 Tuono냐는 물음에 문서는 그냥 멋진 이름이라서라고 답한다.
Next.js 경험이 있으면 여기서 편안할 것이라는 문장이 README와 문서 첫머리에 함께 놓여 있다.
저장소는 2024년 4월 28일에 만들어졌고, 이 문서 작성 시점 기준 스타 1,135개, 포크 62개, 열린 이슈 45개이며 라이선스는 MIT다.

문서는 이 프레임워크가 두 가지 한계를 겨냥한다고 명시한다.
JS 런타임(Node, Deno)을 쓰지 않고 React 서버 사이드 렌더링 프로젝트를 가능하게 하는 것, 그리고 Rust처럼 대체로 어려운 언어로 하는 웹 개발을 쉽게 만드는 것이다.
그리고 두 개의 수사적 질문으로 그것을 반복한다.
Node와 Deno와 Bun만이 React 앱을 서버 사이드 렌더링할 수 있는 유일한 런타임이냐는 물음에 아니라고 답하며, Tuono가 서버 쪽을 Rust로 쓴 최초의 풀스택 React 프레임워크이고 그 근거로 `ssr-rs` 크레이트를 든다.
Rust가 어려우니 서버 코드 작성도 어렵지 않겠느냐는 물음에도 아니라고 답하며, 각 서버 쪽 라우트가 React 라우트 옆의 별도 파일에서 관리되고 라우팅은 `./src/routes` 디렉터리 안의 파일 정의를 바탕으로 Tuono가 처리한다고 설명한다.

내세우는 기능은 다섯 가지다.
네이티브 TypeScript, Next.js 같은 라우팅, CSS/SCSS 모듈, 서버 사이드 렌더링, 핫 모듈 리로드다.
설치는 `cargo install tuono`이고 macOS와 리눅스와 윈도우에서 쓸 수 있다.
CLI는 `dev`, `build`, `new`, `help` 네 개의 하위 명령을 가지며, `tuono new [NAME]`으로 프로젝트를 만들고 선택적으로 `--template` 플래그로 예제 폴더의 템플릿에서 시작할 수 있다.
그 뒤 원하는 JS 패키지 매니저로 의존성을 설치하고 `tuono dev`로 개발 환경을 띄운다.

서버 사이드 렌더링은 파일 쌍으로 표현된다.
어떤 페이지에 SSR을 켜려면 같은 이름의 `.rs` 파일을 만들면 되며, `src/routes/about.tsx` 옆에 `src/routes/about.rs`를 두고 그 안에 `#[tuono_lib::handler]`를 붙인 함수를 정의한다.
그 함수가 HTML을 렌더링하기 전에 매 요청마다 호출되고, 반환한 `Response::Props(Props::new(data))`가 라우트의 `data` 프롭으로 전달된다.
TypeScript 쪽에서는 `TuonoRouteProps` 타입으로 프롭 구조를 기술하는데, 이 타입은 데이터가 아직 로딩 중인 상태와 성공적으로 가져와 쓸 준비가 된 상태를 구분하기 쉽게 설계되었다고 문서가 밝힌다.

API 라우트는 별도 규칙을 따른다.
`src/routes/api` 폴더 안의 파일은 `/api/*` 경로로 대응되며 React 라우트가 아니라 API 엔드포인트로 취급된다.
Tuono 서버는 내부적으로 axum이 관리하고 대부분의 axum 문법을 그대로 쓸 수 있게 `tuono_lib::axum::*`를 재수출한다.
차이는 두 가지로, 함수 위에 `tuono_lib::api(method)` 매크로 속성이 있어야 하고 첫 인자가 언제나 `tuono_lib::Request`여야 한다.
React 라우트와 달리 API는 `tuono_lib::Response`를 반환해서는 안 되며, 한 파일에 여러 HTTP 메서드를 담을 수 있다.

정적 사이트 생성은 실험 단계로 표시되어 있다.
문서는 이 기능이 실험적이고 아직 몇몇 시나리오를 놓치고 있으며 곧 안정화될 것이라는 경고를 맨 앞에 둔다.
`tuono build --static`으로 모든 JS와 CSS 에셋을 빌드하고 각 페이지를 개별 `index.html`로 사전 렌더링하며, `#[tuono_lib::handler]`로 원격 데이터를 불러올 수는 있지만 빌드 시점에만 로드된다.
그리고 현재 개발 단계에서는 앱 전체가 SSG나 SSR 중 하나를 골라야 하고 렌더링 전략을 섞을 수 없다고 명시한다.

성능 주장은 별도 저장소인 `tuono-labs/tuono-benchmarks`가 뒷받침한다.
그 저장소는 각 비교를 가능한 한 공정하게 만들기 위해 각 프레임워크가 백엔드 서비스에서 데이터를 요구하는 서버 사이드 렌더링 페이지 하나만 담아야 하고, 반환 데이터는 0에서 10 사이 난수를 담은 JSON이어야 한다고 규정한다.
자기 하드웨어로 시도해 보고 결과가 크게 다르면 이슈를 열어 달라는 요청도 함께 적혀 있다.
마지막으로 측정된 버전은 v0.17.0이며, wrk를 12스레드 400커넥션 30초로 돌린 결과 Tuono가 초당 41,341.09 요청에 평균 지연 10.10ms, Next.js Pages 라우터가 초당 10,358.80 요청에 평균 지연 40.86ms, Next.js App 라우터가 초당 10,170.10 요청에 평균 지연 39.96ms였다.

배포 현황은 crates.io와 npm 양쪽에 있다.
crates.io의 `tuono`는 누적 다운로드 86,630회에 최근 다운로드 467회이고 98개 버전이 나왔으며 최신은 2025년 5월 25일의 0.19.7이다.
npm의 `tuono`도 최신이 0.19.7이고 최근 한 달 다운로드가 539회다.
기여자는 19명으로 집계되며 `Valerioageno`가 440건, `renovate[bot]`이 171건, `marcalexiei`가 117건, `jacobhq`가 27건 순이다.

## 분석

### 이 프레임워크의 논지는 성능이 아니라 프로세스 위상의 변경이다

문서가 세운 두 한계 중 첫 번째가 이 프로젝트의 정체성이다.
JS 런타임 없이 React SSR을 하겠다는 것인데, 여기서 “없이”가 무엇을 뜻하는지 정확히 볼 필요가 있다.
JavaScript가 실행되지 않는다는 뜻이 아니다.
Tuono는 `ssr-rs`를 통해 V8을 프로세스 안에 임베드하므로 React의 `renderToString`은 여전히 JavaScript로 실행된다.

사라지는 것은 언어도 엔진도 아니고 별도 프로세스다.
전통적인 구성에서 Rust 백엔드와 React SSR을 함께 쓰려면 Node 프로세스를 따로 띄우고 두 프로세스 사이에 HTTP를 놓아야 한다.
그러면 배포 단위가 둘이고, 헬스 체크가 둘이고, 그 사이에 타임아웃과 커넥션 풀과 재시도 정책이 생긴다.
Tuono는 그 전부를 한 바이너리 안의 함수 호출로 접는다.

이 관점이 문서의 수사적 질문을 다시 읽게 만든다.
“Node와 Deno와 Bun만이 React를 SSR할 수 있는 유일한 런타임이냐”는 물음의 정확한 답은 “V8을 임베드하면 어떤 프로세스든 할 수 있다”이며, 그것은 새로운 발견이 아니라 오래된 사실이다.
새로운 것은 그 사실을 프레임워크 수준으로 포장해 Next.js와 같은 개발 경험을 얹었다는 점이다.
[`ssr_rs` 노트](ssr-rs.md)에서 정리했듯 그 하부 계층의 실제 이득도 처리량이 아니라 프로세스 경계 제거였고, Tuono는 같은 이득을 사용자가 직접 조립하지 않아도 되게 만든 상위 포장이다.

### Next.js API를 그대로 따른 결정이 채택 비용과 평가 기준을 동시에 정한다

“Next.js 경험이 있으면 편안할 것”이라는 문장이 README와 문서 양쪽 첫머리에 있다.
파일 시스템 라우팅, `src/routes` 디렉터리, 동적 라우트, `Link` 컴포넌트, `useRouter` 훅, API 라우트가 전부 Next.js의 대응물과 이름과 형태를 공유한다.
문서 자신도 Tuono API가 Next.js의 것에 가능한 한 붙어 있으려 하며 적어도 거기서 큰 영감을 받았고, 주된 차이는 백엔드 시스템이라고 명시한다.

이 결정의 이득은 분명하다.
기존 Next.js 사용자가 배워야 할 새 개념이 사실상 서버 쪽 핸들러 하나뿐이며, 나머지는 이미 아는 것이다.
1인 주도 프로젝트가 API를 처음부터 설계하는 대신 검증된 것을 빌려 오는 것은 자원 배분으로도 합리적이다.

대가는 평가 기준까지 함께 가져온다는 점이다.
Next.js를 표준으로 삼겠다고 선언하는 순간 사용자는 Next.js가 가진 것 전부를 기대하게 된다.
증분 정적 재생성, 미들웨어, 이미지 최적화, 서버 컴포넌트, 스트리밍, 국제화 라우팅이 전부 비교 항목이 되고, 없는 것은 미완성으로 읽힌다.
직접 만든 API였다면 “우리는 다르게 한다”고 말할 수 있었을 자리에서 “아직 없다”고 말해야 하는 구조다.
바로 다음 절에서 볼 SSG의 실험 표시가 그 구조 안에서 어떻게 읽히는지가 이 결정의 실제 비용이다.

### 파일 쌍이 이 프레임워크의 실제 인터페이스다

Tuono가 서버와 클라이언트의 경계를 표현하는 방식은 지시어도 매크로 접두사도 아니고 파일 이름이다.
`about.tsx` 옆에 `about.rs`를 두면 그 라우트에 SSR이 켜지고, 두지 않으면 켜지지 않는다.
경계가 파일 시스템에 있다는 것은 별도 문법을 배울 필요가 없다는 뜻이며, `#[tuono_lib::handler]` 하나만 알면 된다.

이 설계가 데이터 흐름도 정한다.
Rust 핸들러가 `Props`를 만들고 그것이 React 컴포넌트의 `data` 프롭으로 들어가는 단방향이며, 그 사이의 직렬화는 프레임워크가 처리한다.
TypeScript 쪽 `TuonoRouteProps`가 `isLoading`과 `data`를 함께 노출하는 것은 이 프롭이 서버 렌더링 시점과 클라이언트 전환 시점에 다른 상태를 가질 수 있음을 타입으로 드러낸 것이다.
React Server Components가 같은 경계를 컴파일러와 지시어로 처리하고 Topcoat 같은 Rust 프레임워크가 `$(...)` 표현식으로 처리하는 것과 비교하면, Tuono의 방식은 가장 덜 영리하고 가장 이해하기 쉽다.

다만 이 단순함에는 표현력의 상한이 있다.
경계가 라우트 단위이므로 한 페이지 안의 일부만 서버에서 가져오거나 컴포넌트가 자기 데이터를 스스로 가져오는 구성이 어렵다.
모든 서버 데이터가 라우트 최상단에서 한 번에 결정되어 프롭으로 내려가야 하며, 이것은 Next.js의 `getServerSideProps` 시절 모델이지 서버 컴포넌트 이후의 모델이 아니다.
문서가 Next.js를 표준으로 삼으면서도 어느 시점의 Next.js인지는 말하지 않는다.

### 벤치마크 저장소가 이 프로젝트에서 가장 잘 관리된 문서다

성능을 내세우는 프로젝트의 벤치마크는 대개 자기에게 유리한 조건에서 한 번 재고 방치된다.
`tuono-benchmarks`는 그 패턴에서 눈에 띄게 벗어나 있다.
비교를 가능한 한 공정하게 만들기 위해 각 프레임워크가 백엔드에서 데이터를 요구하는 SSR 페이지 하나만 담아야 한다는 규칙을 명시하고, 반환 데이터의 형태까지 `{"data": 0}`으로 고정한다.
각 프레임워크의 고유한 성능 개선을 살려 비교를 공정하게 하는 것이 목표라고 적고, 자기 하드웨어로 돌려 보고 결과가 크게 다르면 이슈를 열어 달라고 요청한다.

숫자도 겸손하다.
Tuono 41,341 req/s 대 Next.js 10,359 req/s로 약 4배이며, 지연은 10.10ms 대 40.86ms다.
같은 저자가 만든 하부 크레이트의 벤치마크가 초당 266,177 요청이라는 비현실적 값을 내세운 것과 대조된다.
그쪽 수치는 요청당 3.8마이크로초 안에 React 렌더링이 끝났다는 뜻이라 사실상 렌더링을 재지 않은 것인데, 이쪽은 10ms라는 값이 실제로 컴포넌트를 렌더링하고 데이터를 가져온 시간처럼 읽힌다.

Next.js 쪽 실행 방식을 `pm2`로 띄운 것도 눈여겨볼 만하다.
프로덕션 구성에 가깝게 맞추려는 시도이며, 단순히 `next start`를 한 번 돌린 것보다 공정하다.
다만 pm2의 인스턴스 수가 명시되지 않아 Node 쪽이 여러 코어를 썼는지 하나만 썼는지 알 수 없고, 12스레드로 부하를 거는 조건에서 이 차이는 결과를 크게 바꾼다.
공정성을 목표로 선언한 문서에서 이 항목이 빠진 것은 아쉬운 대목이다.

## 비평

### 저장소는 살아 있어 보이지만 `main`은 2025년 7월에 멈춰 있다

GitHub API가 보고하는 `pushed_at`은 2026년 8월 10일이다.
어제까지 무언가가 푸시되었다는 뜻이고, 스타 1,135개와 함께 보면 활발한 프로젝트로 읽힌다.
그런데 기본 브랜치의 HEAD는 2025년 7월 23일이며 그 커밋의 내용은 `fix(deps): update dependency vite to v6.3.5`, 곧 의존성 봇의 자동 갱신이다.
사람이 만든 마지막 커밋은 2025년 7월 20일 `Valerioageno`의 의존성 중복 제거이며, 그 앞의 열 몇 개 커밋도 전부 `renovate[bot]`이다.

`pushed_at`이 최신인 이유는 브랜치 목록이 설명한다.
12개 브랜치 중 9개가 `renovate/`로 시작하고 그중 다섯 개는 `npm-babel-core-vulnerability`, `npm-happy-dom-vulnerability`, `npm-turbo-vulnerability`, `npm-vite-vulnerability`, `npm-vitest-vulnerability`처럼 취약점 이름을 달고 있다.
곧 어제의 푸시는 개발이 아니라 봇이 새 브랜치를 만든 것이다.

배포 기록이 같은 이야기를 한다.
GitHub 릴리스의 최신은 2025년 5월 25일의 v0.19.7이고, crates.io와 npm의 최신 버전도 같은 날짜의 0.19.7이다.
이 문서를 쓰는 시점 기준으로 약 15개월 동안 릴리스가 없었고 13개월 동안 사람 커밋이 없었다.
문서 사이트가 여전히 “가장 빠른 풀스택 웹 프레임워크”라고 선언하고 README가 기여를 환영한다고 적는 상태에서, 이 정보를 얻으려면 브랜치 목록과 릴리스 페이지를 직접 확인해야 한다.

이 관찰이 중요한 이유는 프레임워크가 라이브러리와 다르기 때문이다.
라이브러리는 표면이 좁고 하는 일이 정해져 있으면 갱신이 멈춰도 오래 쓸 수 있다.
프레임워크는 그 아래에 React와 Vite와 TypeScript와 axum이 놓여 있고 그것들이 계속 움직이므로, 멈춘 프레임워크는 시간이 지날수록 아래층과 어긋난다.
Next.js를 표준으로 삼겠다고 선언한 프로젝트라면 특히 그렇다.

### 보안 표시가 붙은 의존성 갱신이 병합되지 않고 쌓여 있다

열린 풀 리퀘스트를 최근 갱신순으로 보면 상위 여덟 개가 전부 `renovate[bot]`이고, 그중 다섯 개의 제목에 `[security]`가 붙어 있다.
`vite`를 v6.4.3으로, `@babel/core`를 v7.29.6으로, `happy-dom`을 v20으로, `vitest`를 v3.2.6으로, `turbo`를 v2.9.14로 올리는 것들이며 각각 2026년 6월 말부터 8월 초 사이에 열렸다.
가장 오래된 것은 두 달 가까이 열려 있다.

이 목록이 드러내는 것은 단순한 방치 이상이다.
Rust 백엔드를 내세우는 프레임워크의 미해결 보안 갱신이 전부 JavaScript 쪽이라는 사실이다.
`vite`, `babel`, `vitest`, `turbo`, `happy-dom`은 모두 빌드와 테스트 도구이고, Tuono가 Node 런타임을 서버에서 없앴다고 해서 개발 시점의 JS 공급망이 없어지지는 않는다.
사용자가 `tuono dev`를 돌릴 때 이 도구들이 로컬에서 실행되며, 그것이 바로 이 갱신들이 보안 표시를 단 이유다.

여기에 판단의 어려움이 있다.
개발 의존성의 취약점은 프로덕션 서버의 취약점과 성격이 다르고, 대부분은 실제 위험이 낮다.
그러나 그 판단을 누군가 해야 하는데 병합도 종료도 되지 않은 채 열려 있다는 것은 아무도 보고 있지 않다는 뜻이다.
비어 있는 이슈 트래커가 그 인상을 강화한다.
풀 리퀘스트를 제외한 열린 이슈는 2025년 11월 27일의 서브패스 호스팅 기능 요청 하나뿐이며, 그것도 여덟 달 넘게 답이 없다.

### SSG의 실험 표시와 렌더링 전략 혼합 불가가 Next.js 대안이라는 주장을 좁힌다

문서는 정적 사이트 생성 페이지 맨 위에 이 기능이 실험적이고 아직 몇몇 시나리오를 놓치고 있다는 경고를 둔다.
그 자체는 정직한 표시다.
문제는 바로 아래 문장이다.
현재 개발 단계에서는 앱 전체가 SSG나 SSR 중 하나를 골라야 하며 혼합 렌더링 전략은 아직 쓸 수 없다는 것이다.

이 제약이 Next.js를 표준으로 삼은 결정과 정면으로 부딪친다.
Next.js에서 페이지마다 렌더링 방식을 다르게 고르는 것은 부가 기능이 아니라 핵심 설계이며, 마케팅 페이지는 정적으로 굽고 대시보드는 요청마다 렌더링하는 구성이 가장 흔한 사용 형태다.
그것을 앱 전체 단위로만 고를 수 있다면 실질적으로 두 개의 서로 다른 프레임워크를 골라 쓰는 것에 가깝다.

같은 페이지의 다른 문장도 이 제약을 키운다.
SSG 모드에서 `#[tuono_lib::handler]`로 원격 데이터를 불러올 수는 있지만 빌드 시점에만 로드된다는 서술인데, 재검증 기제에 대한 언급이 없다.
Next.js의 증분 정적 재생성에 해당하는 것이 없다면 정적으로 구운 페이지의 데이터를 갱신하는 유일한 방법은 재빌드와 재배포다.
문서가 이 사실을 부정적으로 서술하지 않고 그냥 적어 두었을 뿐이라 독자가 스스로 함의를 계산해야 한다.

그리고 이 제약을 해소할 주체가 앞 절에서 본 상태에 있다.
“곧 안정화될 것”이라는 문장은 2025년 중반 기준의 약속이고, 그 이후 릴리스가 없다.
실험 표시는 시간이 지날수록 정보량이 줄어드는 종류의 표시이며, 마지막 릴리스로부터 15개월이 지난 지금은 사실상 “이대로 굳었다”로 읽어야 한다.

### 벤치마크가 재는 것은 프레임워크가 아니라 런타임 조합이다

앞서 이 프로젝트의 벤치마크가 잘 관리되어 있다고 평가했는데, 그 평가는 방법론의 정직함에 대한 것이지 결론의 유효성에 대한 것은 아니다.
측정된 마지막 버전이 v0.17.0이고 현재 최신이 0.19.7이라는 시차가 첫 번째 문제다.
릴리스가 멈춘 지금은 그 시차가 더 늘지 않는다는 점이 역설적인 위안이지만, 두 마이너 버전 사이에 SSR 경로가 어떻게 달라졌는지에 대한 정보는 없다.

더 근본적인 문제는 4배라는 숫자가 무엇의 차이인지다.
Tuono 쪽은 axum이 HTTP를 받고 V8이 렌더링하며, Next.js 쪽은 Node가 HTTP를 받고 V8이 렌더링한다.
렌더링 엔진이 양쪽 다 V8이므로 차이는 렌더링이 아니라 그 바깥, 곧 HTTP 처리와 요청 파이프라인과 스레드 모델에서 온다.
그렇다면 이 벤치마크가 보여 주는 것은 “Rust가 JavaScript보다 빠르다”가 아니라 “axum의 요청 처리가 Node의 그것보다 가볍다”이며, 그 결론은 React와 무관하게 이미 알려진 사실이다.

이 구분이 실무 판단에 영향을 준다.
페이지 렌더링 자체가 무거운 애플리케이션, 곧 컴포넌트 트리가 크고 데이터 변환이 많은 경우에는 병목이 V8 안에 있으므로 두 구성의 차이가 4배보다 훨씬 작아진다.
반대로 렌더링이 가볍고 요청 수가 많은 경우에는 차이가 벌어진다.
벤치마크가 규정한 시나리오, 곧 난수 하나를 담은 JSON을 받아 렌더링하는 페이지는 후자에 가깝다.
공정성을 위해 단순한 시나리오를 고른 것이 결과적으로 이 프레임워크에 유리한 구간을 고른 셈이며, 저장소가 이 편향을 언급하지 않는다.

## 인사이트

### 유지되지 않는 프레임워크의 진짜 비용은 빠진 기능이 아니라 의존성 표면이다

멈춘 오픈소스 프로젝트를 평가할 때 보통 묻는 것은 “필요한 기능이 다 있는가”다.
Tuono에 대해 그렇게 물으면 답은 나쁘지 않다.
파일 기반 라우팅과 SSR과 API 라우트와 CSS 모듈과 핫 리로드가 있고, 없는 것은 혼합 렌더링과 증분 재생성 정도다.
작은 프로젝트라면 그 상태로도 쓸 만해 보인다.

그러나 프레임워크의 유지보수 부담은 자기 코드가 아니라 자기가 붙들고 있는 다른 사람들의 코드에서 온다.
열린 풀 리퀘스트 목록이 그 사실을 그대로 보여 준다.
`vite`, `@babel/core`, `happy-dom`, `vitest`, `turbo`, `typescript`, `oxc-transform`, `@vitejs/plugin-react-swc`가 전부 이 프로젝트의 관리 대상이고, 그중 다수가 몇 주 단위로 새 버전을 낸다.
Rust 쪽도 `axum`과 `tokio-tungstenite`와 `ssr_rs`가 있다.

여기서 나오는 관찰은 Rust 백엔드를 쓴다고 해서 JavaScript 공급망 부담이 줄지 않는다는 것이다.
오히려 늘어난다.
순수한 Next.js 프로젝트라면 관리할 툴체인이 하나인데, Tuono는 Rust 툴체인과 JS 툴체인을 모두 붙들고 그 둘을 잇는 접착 코드까지 유지해야 한다.
1인이 주도하고 두 번째 기여자가 117건인 프로젝트에서 이 표면이 감당 가능한지가 진짜 질문이었고, 커밋 기록이 답을 준 셈이다.

그러므로 이런 프로젝트를 채택할 때 세어야 할 것은 기능 목록이 아니라 의존성 목록이다.
프레임워크가 멈추면 사용자가 그 의존성들을 스스로 올려야 하는데, 그것은 포크해서 빌드 파이프라인을 직접 유지한다는 뜻이다.
`ssr_rs`처럼 심볼 셋뿐인 라이브러리라면 그 부담이 작지만, 빌드 도구와 개발 서버와 번들러를 품은 프레임워크에서는 그 부담이 사실상 프로젝트 하나를 인수하는 것과 같다.

### JS 런타임을 없앤다는 약속은 JavaScript 생태계를 없애지 못한다

문서의 첫 번째 한계 진술은 “JS 런타임(Node, Deno)을 쓰지 않고” React SSR을 가능하게 하는 것이다.
이 문장이 정확히 무엇을 약속하는지 따져 보면 약속의 범위가 생각보다 좁다.

프로덕션 서버에서 Node 프로세스가 사라지는 것은 사실이다.
그러나 V8은 그대로 있고, React는 그대로 JavaScript이고, 번들은 Vite가 만들고, 타입은 TypeScript가 검사하고, 테스트는 Vitest가 돌린다.
`tuono new` 다음에 사용자가 하는 일이 “좋아하는 JS 패키지 매니저로 의존성을 설치”하는 것이라는 사실이 이 구조를 요약한다.
`node_modules`는 그대로 있고 `package.json`도 그대로 있다.

즉 없어진 것은 런타임 프로세스이지 런타임 생태계가 아니며, 이 둘을 구분하지 않으면 잘못된 기대를 갖게 된다.
Node 보안 공지에서 자유로워지는 것은 맞지만 npm 공급망 공격에서 자유로워지지는 않는다.
서버 메모리에서 Node의 오버헤드가 사라지는 것은 맞지만 V8 힙은 그대로 있고, [`ssr_rs` 노트](ssr-rs.md)에서 정리했듯 워커 스레드마다 아이솔레이트가 복제되므로 오히려 늘어날 수도 있다.

이 구분을 명확히 하면 이 프레임워크가 실제로 파는 것이 보인다.
그것은 “JavaScript 없는 웹 개발”이 아니라 “서버 프로세스 하나로 끝나는 배포”이며, 이미 Rust 백엔드를 운영하는 조직이 React 프런트엔드를 같은 바이너리에 넣고 싶을 때 값어치가 가장 크다.
문서가 두 번째 한계로 “Rust처럼 어려운 언어로 하는 웹 개발을 쉽게” 만드는 것을 든 것도 같은 청중을 가리킨다.
그렇다면 첫 문장의 수사적 질문보다 이 청중을 직접 부르는 편이 이 프로젝트에 유리했을 것이다.

### 1인 프로젝트가 조직 이름을 얻는 순간 신뢰 신호가 실체보다 앞선다

이 프로젝트는 `Valerioageno/tuono`에서 `tuono-labs/tuono`로 옮겨 갔다.
개인 계정에서 조직 계정으로의 이동은 흔한 절차이고 그 자체로 문제될 것이 없다.
다만 그 이동이 만드는 인상은 실체와 다를 수 있다.

기여자 통계가 실체를 보여 준다.
`Valerioageno` 440건, `renovate[bot]` 171건, `marcalexiei` 117건, `jacobhq` 27건이고 나머지 15명은 한 자릿수다.
봇을 빼면 사실상 한 명이 주도하고 한 명이 상당히 돕는 구조이며, “labs”라는 이름이 시사하는 조직은 없다.
문서 사이트 하단이 “Valerio Ageno와 이 멋진 사람들이 만들었다”로 끝나는 것이 더 정직한 서술이다.

같은 종류의 신호 부풀림을 다른 곳에서도 본 적이 있다.
[Topcoat 노트](topcoat.md)에서 정리했듯 그 프로젝트가 `tokio-rs` 조직 아래 있는 이유는 전략이 아니라 CI 사용량 할당이었고, 창시자 본인이 분리해 나갈 가능성이 높다고 밝혔다.
독자들은 조직 이름에서 지속성과 인력 규모를 읽어 내는데, 두 사례 모두 그 읽기가 근거 없는 것이었다.

여기서 나오는 실천적 규칙은 조직 계정을 신뢰 신호로 세지 말고 기여자 분포와 릴리스 주기를 대신 보라는 것이다.
Tuono의 경우 그 두 지표를 먼저 봤다면 채택 판단이 달라졌을 사람이 있을 것이다.
스타 1,135개와 `tuono-labs`라는 이름과 잘 만들어진 문서 사이트가 함께 만드는 인상은 crates.io 최근 다운로드 467회와 npm 월 539회라는 실제 사용량과 두 자릿수 배율로 벌어져 있다.

### 같은 사람이 쌓은 두 층에서 아래층이 위층보다 오래 버티는 이유

이 프로젝트를 그 하부 크레이트와 나란히 놓으면 흥미로운 대비가 나온다.
`ssr_rs`는 마지막 릴리스가 2025년 5월, 마지막 푸시가 2025년 10월로 조용하다.
Tuono도 마지막 릴리스가 2025년 5월, 마지막 사람 커밋이 2025년 7월로 조용하다.
표면적으로 같은 상태인데 위험도가 다르다.

`ssr_rs`는 공개 심볼이 셋뿐이고 하는 일이 V8을 감싸는 것 하나다.
표면이 좁으니 바꿀 일이 적고, 실제로 Tuono가 `0.8.3`을 고정한 채 쓰고 있었다.
그 크레이트를 두고 조용한 것이 곧 방치는 아니라고 판단했던 근거가 그것이었다.

Tuono는 정반대다.
사용자가 마주하는 표면이 CLI와 라우팅 규약과 매크로와 프롭 타입과 빌드 파이프라인까지 넓고, 그 아래에 계속 움직이는 JS 툴체인 전체가 있다.
표면이 넓으면 상류의 변화가 닿는 지점도 많아지고, 멈춘 상태에서 어긋남이 누적되는 속도가 빠르다.
Vite의 메이저 버전이 올라가거나 React가 API를 바꾸면 `ssr_rs`는 영향을 받지 않지만 Tuono는 받는다.

여기서 일반화할 만한 판단 기준이 나온다.
조용한 저장소를 만났을 때 물어야 할 것은 마지막 커밋 날짜가 아니라 그 프로젝트가 붙들고 있는 움직이는 부품의 수다.
부품이 적으면 조용함은 완성의 신호일 수 있고, 부품이 많으면 조용함은 부채가 쌓이는 소리다.
공교롭게도 이 두 프로젝트는 같은 사람이 아래위로 쌓은 것이라 이 대비가 한 사람의 관리 역량 문제가 아니라 계층의 성질 문제임을 보여 준다.
프레임워크를 만드는 일이 라이브러리를 만드는 일보다 어려운 이유는 처음 만들 때가 아니라 그 다음에 있다.
