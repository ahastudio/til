# Rust 1.100은 never 타입과 allocator API를 10년 만에 안정화하며 오래 끌어온 프로젝트 목표를 한꺼번에 마무리한 릴리스이다

원문: [Announcing Rust 1.100.0](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/)

HN 토론: <https://news.ycombinator.com/item?id=50472038> (431점, 174개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/81hnjw/announcing_rust_1_100_0>

## 요약

Rust 릴리스 팀이 2026년 11월 12일에 낸 Rust 1.100.0 공지이다.
`rustup update stable`로 올릴 수 있고, 지난 릴리스(1.99.0)는 2026년 10월 1일,
1.99.1은 10월 15일이었다.[^releases]
글은 일곱 가지를 이번 릴리스의 내용으로 꼽는다.
never 타입, allocator API, DropGuard API, 크기가 0인 타입을 만드는 `conjure_zst`,
Cargo의 미사용 의존성 보고, Cargo 캐시 충돌 감소, Cargo의 `min-publish-age`이다.

### never 타입

글은 10년 동안 다섯 번의 안정화 시도가 실패한 끝에 never 타입(`!`)이 마침내 안정화되었고
이것으로 이 작업의 프로젝트 목표가 완료된다고 쓴다.
`!`는 값을 낼 수 없는 발산 연산의 타입이다.
`return`, `break`, `std::process::exit` 같은 표현식이 이 타입을 갖고,
`!`는 다른 모든 타입으로 강제 변환(never-to-any coercion)된다.
그래서 `match`의 한 가지가 값을 돌려주지 않아도 타입 검사를 통과한다.
이번 릴리스는 `!`를 어디에나 이름으로 쓸 수 있게 한다.
`Result<T, !>`처럼 쓰는 것이 전에는 불가능했다.
또 `Infallible`을 `!`의 별칭으로 바꾼다.
이 변경 때문에 호환성을 깨는 변화가 하나 들어갔다.
2024 에디션 이전(2015, 2018, 2021)의 never 타입 폴백(fallback)이 `()`에서 `!`로 바뀌었다.
이는 2024 에디션에서 이미 한 변경이고, 일부 드문 경우(예: 제네릭 매개변수를 돌려주는 함수의
결과를 무시할 때)에 영향을 주며 컴파일러가 더 많은 코드를 도달 불가로 판단할 수 있다고
글은 말한다.
글은 미래 호환성 경고를 아주 일찍부터 내보냈고 깨진 공개 크레이트에 수정을 배포했다고
적는다.

### allocator API

`allocator_api`의 핵심이 안정화되어 라이브러리가 `Vec`과 `Box`에 쓸 수 있는 사용자 정의
할당기를 정의할 수 있다.
새로 안정화된 `Allocator` 트레이트를 통해서이다.
글은 이것이 Allocators 1.0 프로젝트 목표의 기반이고, 더 많은 컬렉션과 포인터 타입에 대한
안정화가 뒤따를 것이라고 한다.

### DropGuard와 conjure_zst

`core::mem::DropGuard`는 값과 클로저를 받아, 가드가 드롭될 때 클로저를 실행하고 값을
소비한다.
`Deref`와 `DerefMut`를 구현해서 값을 그대로 쓸 수 있고, `dismiss`로 클로저를 실행하지
않고 값을 꺼낼 수도 있다.
글의 예는 문자열 여러 개를 파싱해 벡터에 넣다가 하나라도 실패하면 벡터를 원래 길이로
되돌리는 `parse_all`이다.
`std::mem::conjure_zst`는 크기가 0인 타입의 값을 만드는 전용 함수이다.
`()`를 `transmute`하거나 `MaybeUninit::uninit().assume_init()`을 쓰는 여러 편법을 대체한다.
많은 API가 그런 타입을 만들 수 없다는 점에 안전성을 기대하므로 이 함수는 `unsafe`이다.
글은 PyO3의 `Python<'py>`(GIL을 잡고 있다는 표식 토큰)를 예로 든다.

### Cargo

미사용 의존성 보고는 `cargo::unused_dependencies` 린트로 나오고 기본이 경고이다.
rustc의 `unused_crate_dependencies`는 한 패키지의 여러 빌드 대상이 의존성을 공유하므로
오탐이 있었다.
글은 한계도 적는다.
의존성을 쓸 수 있는 모든 빌드 대상을 빌드할 때만 경고가 나오고,
`cargo check --bin foo`처럼 일부만 빌드하면 경고가 없으며,
`dev-dependencies`는 모든 개발용 대상이 빌드되었는지 보장할 수 없어서 경고를 내지
않는다.
이 린트는 `[lints.cargo]` 테이블로 제어하는 Cargo 자체의 린트 체계의 일부이다.

캐시 충돌 감소는 빌드 디렉터리의 배치 변경이다.
이전에는 빌드 설정 해시가 플랫폼 제약 때문에 모든 곳에 붙지 않아서 불필요한 재빌드,
놓친 재빌드, 어떤 바이너리가 쓰이는지에 대한 혼란이 있었고 git worktree 사이에 빌드
디렉터리를 공유하면 더 심했다.
이제 파일 종류가 아니라 빌드 단계를 기준으로 디렉터리를 나누고 해시를 파일 이름에서 부모
디렉터리로 옮겨 모든 내용에 일관되게 적용한다.
내부 변경이지만 이 레이아웃의 빈틈을 우회하던 빌드 절차와 테스트가 깨질 수 있다고 글은
경고한다.

`min-publish-age`(의존성 쿨다운)는 새로 게시된 버전을 일정 기간 건너뛰고 의존성을 고르게
한다.
악성 버전은 게시 후 몇 시간이나 며칠 안에 자동 스캐너나 커뮤니티에 걸러지는 경우가 많다는
전제이다.
`.cargo/config.toml`의 `[registry]`에 `global-min-publish-age = "3 days"`를 적어 켠다.
`cargo update`는 더 최근 버전을 선택하지 않고 무엇을 보류했는지 알려 준다.
급히 새 버전이 필요하면 `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow`로 한 번만 확인을
넘길 수 있고 그 버전은 `Cargo.lock`에 남는다.
주의 사항은 세 가지이다.
레지스트리가 각 버전의 게시 시각(`pubtime`)을 기록해야 하고 없으면 보류되지 않는다.
`cargo install`은 최소 게시 연령을 무시한다.
쿨다운은 일부 공급망 공격의 위험만 줄일 뿐 완전한 방어가 아니다.
글은 crates.io의 공급망 강화 프로젝트(격리 지원과 의심스러운 릴리스의 자동 탐지)가
계획되어 있다고 덧붙인다.

### 안정화된 API와 그 밖의 변경

안정화 API 목록에는 `Allocator`, `Global`, `System`, `Box::new_in`, `Vec::new_in`,
`DropGuard`, `conjure_zst` 외에도 `bool::toggle`, `Box::map`, `Rc::map`, `Arc::map`,
`Box::take`, `str::trim_prefix`, `str::trim_suffix`, `Path::trim_prefix`,
`Vec::from_fn`, `UnsafeCell::replace` 등이 있다.
상세 릴리스 노트에는 더 많은 항목이 있다.
`extern "custom"`과 `-Cprofile-sample-use`가 안정화되었고, `wasm32-wasip3`가 Tier 2로
올랐으며, `i686-pc-windows-gnu`는 호스트 도구가 없는 Tier 2가 되었고, 새 Tier 3로
`powerpc64-sony-ps3`가 추가되었다.[^relnotes]
호환성 주의 항목에는 `if let`에서 클로저가 변수를 더 정밀하게 캡처해 새 오류가 날 수 있는 것,
`box` 패턴이 문법적으로 금지된 것, 일부 `Box` 구현이 임의의 할당기로 일반화되어 새 타입
추론 오류가 날 수 있는 것, `cargo install`이 기본으로 `.crate`의 락파일을 쓰게 되어
`--locked`가 아무 일도 하지 않게 된 것, 표준 라이브러리가 Unicode 18.0.0을 쓰는 것이
있다.[^relnotes]

## 분석

### 이번 릴리스의 성격은 오래된 프로젝트 목표의 완료이다

가장 강하게 말하면 1.100은 새 기능 모음이 아니라 여러 해에 걸친 작업의 결산이다.
글이 스스로 목표라는 말을 거듭 쓴다.
never 타입은 프로젝트 목표의 완료이고, allocator API는 Allocators 1.0의 기반이고,
Cargo 린트는 한 프로젝트 목표의 완료이고, 빌드 디렉터리 배치는 2025년 목표에서 시작해 새
목표로 가는 이정표이다.
Cargo의 `min-publish-age`도 RFC 3923(작성 시작 2026년 2월 23일)에서 안정화 PR(2026년 8월
28일 병합)까지 약 여섯 달이 걸렸다.[^rfc3923][^cargo-17335]
HN에서 steveklabnik은 오래 걸린 기능이 마침내 들어오는 기념비적 릴리스라고 했고,
nirinor도 이번 릴리스에서 가장 기대되는 안정화로 never 타입, 사용자 정의 할당기,
의존성 쿨다운을 꼽았다.[^steveklabnik][^nirinor]

### 호환성의 비용을 미래 호환성 경고와 크레이터 조사로 치렀다

never 타입 안정화의 가장 어려운 부분은 `Infallible`을 `!`의 별칭으로 바꾸면서 폴백을
모든 에디션에서 바꾸는 호환성 파괴였다.
안정화 PR의 크레이터(crater, 크레이트 대량 빌드 시험) 분석에 따르면 모든 깨짐이 이 폴백
변경에서 왔다.
직접 깨진 크레이트는 7개뿐이고, 약 3천 개의 크레이터 실패는 거의 전부 이미 수정된 새 버전이
있는 오래된 라이브러리 버전에 의존하는 크레이트에서 나왔다.
대부분의 원인은 `?` 연산자가 제네릭 반환 타입을 `()` 대신 `!`로 추론하게 만드는
패턴이었다.[^pr-155499]
미래 호환성 경고는 PR 125289 이후부터 내보냈고 의존성에서의 경고는 PR 141937 이후부터
내보냈다고 한다.[^pr-155499]
이 분석은 PR 작성자의 것이고 이 문서가 크레이터 결과를 직접 확인한 것은 아니다.
눈에 띄는 것은 에디션이 이 변경을 막아 주지 못했다는 점이다.
호환성 주의 항목은 폴백이 모든 에디션에서 `!`로 바뀌었다고 적는다.[^relnotes]
HN에서 wpollock은 호환성을 깨는 변경이 있으니 semver상 주 버전을 올려야 하지 않느냐고
물었다.[^wpollock]
이 문서는 이 물음에 대한 답을 스레드에서 찾지 못했다.
theelx도 Lobste.rs에서 `Infallible` 별칭 때문에 2015까지 모든 에디션에 호환성 파괴가
들어간 것이 유감이라고 했다.[^theelx]

### allocator는 최소 기능으로 안정화했고 건전성 문제를 비켜 갔다

안정화 PR의 보고서는 안정화한 범위를 `Allocator` 트레이트와 `Box`, `Vec`의 최소 기능으로
한정한다.
`allocator_api`의 나머지는 `allocator_ext`로 이름을 바꿔 불안정 상태로 남긴다.
보고서는 건전성 문제도 적는다.
`Allocator`가 `Clone`일 때의 안전 요건은 불안정한 마커 하위 트레이트로 옮겼고,
메서드와 드롭에서 언와인드하지 않을 것을 구현자에게 요구하며, `Allocator`는 `dyn` 호환이
되도록 결정했다.
`Box::into_pin`은 `Box`가 할당기에 대해 공변인 것과 수동 `Clone` 구현이 상호작용하는
건전성 버그 때문에 사용자 정의 할당기와는 아직 쓸 수 없고, 이를 위해 불안정한
`StaticAllocator` 마커 트레이트를 둔다.[^pr-156882]
블로그의 핵심 부분 안정화라는 표현은 이 제한들을 압축한 것이다.
이 PR 보고서는 작성자 자신의 의견이며 libs 팀 전체의 입장이 아니라고 스스로 밝힌다.

### 공급망 방어는 선택 기능으로 들어왔다

`min-publish-age`는 기본이 꺼져 있고 사용자가 설정 파일에 적어야 한다.
RFC는 이 기능이 완전한 방어가 아니며 보안만을 위해 의존해서는 안 된다고 적고,
동기에 점진적 롤아웃도 든다.
새 버전이 한꺼번에 퍼지면 문제도 한꺼번에 발견되므로, 위험을 회피하는 쪽은 얼마나 기다릴지
고르고 일부는 카나리(canary)로 최신 버전을 쓴다는 것이다.[^rfc3923]
RFC의 예는 로컬에서는 14일 쿨다운을 쓰고, CI에는 최신 버전을 시험하는 별도 작업을 두는
것이다.[^rfc3923]

## 비평

### 블로그는 호환성 변경의 무게를 낮춰 말하고 상세는 다른 곳에 있다

블로그는 never 타입 폴백 변경을 거의 눈에 띄지 않을 것이고 드문 경우에 영향이 있다고
설명한다.
그러나 상세 릴리스 노트의 호환성 주의 항목은 스무 개쯤이고, 그중 몇 가지는 일반 코드에
닿는다.
`if let` 안에서의 클로저 캡처 변경, `box` 패턴 제거, `Box`의 일반화로 인한 추론 오류, 일부
`Iterator::min`과 `max`가 쓰는 `Ord` 메서드 변경, x86의 “Rust” ABI가 SSE 레지스터를 쓰게
된 것이다.[^relnotes]
이 항목들이 블로그 본문에는 없고 다른 변경 링크 뒤에 있다.
이 목록 가운데 어느 것이 실제 프로젝트를 깰지는 이 문서가 확인하지 못했다.

### 쿨다운에는 빈틈이 있고 효과의 증거가 아직 없다

블로그가 밝힌 한계 외에 HN 질문이 빈틈을 짚었다.
mkl은 `cargo install`이 쿨다운을 무시하면 효과가 크게 줄지 않느냐고 물었고,
Cargo 개발자 epage는 사용성과 일관성 때문이라고 답했다.
MSRV를 인식하는 리졸버가 `cargo install`에 영향을 주지 않게 한 것과 비슷하게, 낡은 버전을
눈치채지 못한 채 받는 것을 피하려는 것이다.[^mkl][^epage-install]
GolDDranks는 `cargo install`이 이제 락파일을 기본으로 써서 이 점이 완화된다고 보았다.[^goldd]
uncivilized는 왜 게시 시각이 인덱스에 없을 수 있느냐고 물었고 epage는 레지스트리 명세에 몇
릴리스 전에야 추가되어 레지스트리가 갱신했는지 보장할 수 없다고 답했다.[^uncivilized][^epage-pubtime]
SOLAR_FIELDS는 쿨다운이 올해 급격히 평가가 바뀌었다고 했다.
처음에는 공급망 공격 때문에 모두가 옹호했는데 이제는 제로데이를 놓칠 수 있다는 우려가 나온다는
것이다.[^solar-fields]
이 기능이 공급망 사고를 실제로 줄이는지는 아직 측정된 바가 없다.

### 빌드 디렉터리 변경은 한 번 되돌린 뒤의 재안정화이다

블로그는 이 작업이 2025년 목표에서 시작했다고 쓰지만, 안정화 PR은 이것이 재안정화라고
밝힌다.
이전 안정화(PR 16807)가 나이틀리에서 발견된 성능과 확장성 문제로 롤백되었고,
세 개의 PR로 완화한 뒤 나이틀리에서 약 2주 동안 보고된 문제 없이 돌았다는 것이다.[^cargo-17354]
블로그 본문은 이 롤백을 언급하지 않는다.
HN의 jadbox는 컴파일이 오래 걸리고 임시 파일이 90GB에 이른다고 했고, epage는 빠른 컴파일과
작은 빌드 디렉터리가 서로 상충할 수 있다고 답했다.[^jadbox][^epage-speed]
이 변경이 기존 도구를 깰 수 있다는 블로그의 경고는 정직하지만 어떤 도구가 영향을 받는지는
cargo#17287로 미룬다.

### 이름과 접근성의 문제도 남았다

HN의 ustad는 never 타입이 무슨 뜻인지 모르겠다고 했고, Xirdus는 타입을 값의 집합으로 보면
never는 빈 집합이라고 설명했다.[^ustad][^xirdus]
mond는 자주 쓰지 않는 타입에 `!`라는 기호는 과하다고 했다.[^mond]
이 반응은 안정화가 끝난 이름과 표기를 바꿀 수 없다는 점에서 의견일 뿐이다.

### LLM 시대에 언어의 안정성과 기능이 무슨 의미인지에 대한 질문

Sol-은 LLM 검증 루프를 낫게 하지 않는 한 언어 기능이 아직 의미 있느냐고 물었고,
yodsanklai는 직장에서 Rust를 주로 쓰지만 코드를 거의 읽지 않고 함수와 타입 정의를 훑는다고
답했다.[^sol][^yodsanklai]
KolmogorovComp는 코딩 에이전트 시대에는 호환성을 완화해 언어가 더 빨리 움직이게 해야 한다고
했고, raphlinus는 강하게 반대하며 LLM 문화가 모든 것을 일시적으로 보는 것과 달리 내구성이
중요하다고 했다.[^kolmogorov][^raphlinus]
이 논의는 릴리스 자체와는 거리가 있지만 이번 릴리스의 가장 큰 쟁점인 호환성 파괴를 어떻게
볼지와 닿아 있다.

## 인사이트

### 올리기 전에 의존성의 폴백 경고를 확인한다

이 릴리스의 가장 큰 위험은 폴백 변경이다.
이 문서의 제안은 1.99에서 먼저 의존성이 이전 버전 폴백에 의존하는지(미래 호환성 경고)를 보고,
1.100에서 전체 테스트를 돌린 뒤 `Cargo.lock`의 오래된 의존성을 갱신하는 것이다.
PR 분석이 말하는 대로 거의 모든 깨진 크레이트에 이미 수정된 새 버전이 있다.[^pr-155499]
빌드 디렉터리를 직접 읽는 도구는 Cargo의 JSON 메시지로 산출물 위치를 찾도록 바꾸고,
빌드 캐시를 디렉터리 배치에 맞춰 둔 CI는 키를 다시 점검한다.[^relnotes]
이 점검 목록은 이 문서의 제안이다.

### 쿨다운은 짧게 시작하고 카나리 작업을 함께 둔다

블로그의 예는 3일, 안정화 PR의 예는 7일, RFC의 예는 14일이다.[^cargo-17335][^rfc3923]
기준이 하나로 정해져 있지 않다는 뜻이다.
이 문서의 제안은 3일쯤으로 시작해 의존성 갱신 PR의 분포를 보며 조정하고,
CI에는 RFC의 예처럼 `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow`로 최신 버전을 시험하는
별도 작업을 두는 것이다.[^rfc3923]
`cargo install`로 설치하는 도구는 쿨다운이 적용되지 않으므로 `cargo install foo@1.2.3`처럼
버전을 고정한다.
급한 보안 수정은 환경 변수로 한 번만 허용하고, 허용한 사실이 `Cargo.lock`에 남는다는 점을
리뷰에서 확인한다.
이 운영 방식은 이 문서의 제안이다.

### DropGuard는 되돌리기 가능한 변경에 쓴다

`DropGuard`는 변경을 하다가 실패하면 되돌리는 패턴(성공하면 `dismiss`)에 맞는다.
HN에서 levkk는 Go의 `defer`와 비슷하다고 했고, Groxx는 건너뛸 수 있는 `defer`라서 안전을
위해 성공하지 않으면 되돌리는 Go 코드를 정리해 줄 것이라고 했다.
aw1621107은 Go의 `defer`가 함수 범위인 것과 달리 블록 범위라는 차이를 짚었다.[^levkk][^groxx][^aw1621107]
이 문서의 제안은 여러 단계로 상태를 바꾸는 함수(벡터에 여러 값 추가, 파일 여러 개 쓰기)
에서 성공 경로 끝에 `dismiss`를 두는 방식으로 롤백을 한 곳에 모으는 것이다.

### allocator를 쓰려는 코드는 allocator-api2에서 옮겨 올 수 있다

lukax는 Bumpalo가 드롭을 호출하지 않아서 아레나 누수를 고치던 중 `allocator-api2` 크레이트로
`Vec::new_in`을 쓰고 있었는데 이제 안정판에서 쓸 수 있다고 했다.[^lukax]
nrposner와 pert는 이미 있는 아레나 할당기를 더 쉽게 끼워 넣을 수 있을 것이라며 앞으로
`Vec`과 `Box` 외의 타입도 이 트레이트를 받으면 좋겠다고 했다.[^nrposner][^pert]
이 문서의 제안은 자기 코드가 `allocator-api2`에 기대고 있다면 `Box::into_pin`이 아직 사용자
정의 할당기와 쓸 수 없다는 제한과 `HashMap` 같은 컬렉션이 아직 안정 API에 없다는 점을
먼저 확인하는 것이다.
이 제한은 안정화 PR의 보고서와 안정화 API 목록에서 읽은 것이다.[^pr-156882]

### 이 릴리스의 주장을 확인할 관찰

호환성 파괴가 정말 작았는지는 업데이트 후 몇 주 동안의 이슈 트래커와 크레이트 릴리스에서
알 수 있다.
폴백 관련 이슈가 PR 분석의 예측대로 이미 수정된 의존성 업데이트로 해소되면 비용이 작았다는
뜻이고, 새 버전이 없는 의존성이 반복해서 보고되면 비용이 더 컸다는 뜻이다.
쿨다운의 효과는 설정을 켠 프로젝트에서 악성 버전이 락파일에 들어오기 전에 걸러진 사례가
쌓여야 판단할 수 있다.
이 관찰은 이 문서의 제안이다.
