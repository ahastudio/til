# Microsoft에서 Rust가 Tier-1 언어가 됐다: rustc_codegen_utc가 그 증거다

원문: [Guest Post: Rust Is Tier-1 Language at Microsoft](https://rustfoundation.org/media/guest-post-rust-is-tier-1-language-at-microsoft/)

HN 토론: <https://news.ycombinator.com/item?id=49643546> (615점, 353개 댓글)

Lobste.rs 토론: <https://lobste.rs/s/eerwba/rust_is_tier_1_language_at_microsoft>

## 요약

Victor Ciura가 2026년 9월 10일 Rust Foundation 블로그에 올린 게스트 포스트다.
저자는 Microsoft DevDiv/CoreAI의 Rust 툴링 팀 수석 엔지니어로,
조직과 오픈소스 커뮤니티 전반의 oxidation 작업에 필요한 컴파일러 툴체인과
라이브러리를 만든다.
25년간 C++로 시스템 프로그래밍을 해 왔고 Visual C++(DevDiv), Advanced
Installer, Clang Power Tools 같은 팀을 거쳤다.

글은 Rust가 Microsoft에 전략적으로 중요하다는 것이 더는 놀랍지
않다는 문장으로 시작한다.
Azure CTO Mark Russinovich가 네이티브 코드에 대한 미래 전략을 밝힌 것부터
이후 몇 년간 Rust 프로젝트 지원에 투입한 수백만 달러까지가 그 근거로
제시된다.

핵심 선언은 이것이다.
오늘날 Rust는 C++, C#, TypeScript와 나란히 Microsoft 내부 개발에서
가장 잘 지원되는 언어 중 하나다.
그리고 이 “Tier-1 언어” 엔지니어링 지위가 뜻하는 바를 구체적으로 정의한다.
내부 팀에게 로컬 개발부터 프로덕션까지 포장된 길(paved path)을 제공하는
것이며, 여기에는 보안 툴체인 빌드, 생산적인 개발자 도구, 품질 워크플로,
깊은 플랫폼 통합, 그리고 Microsoft 소프트웨어가 충족해야 하는 SDL 요구사항
준수가 포함된다.

### rustc_codegen_utc

Windows 플랫폼과 MSVC는 수십 년간 함께 진화해 왔고 C와 C++가 개발
플랫폼의 구성 요소였다.
MSVC와 Windows가 혁신할 때 그 기능이 C++와 Rust 양쪽에서 가능해야 하고
둘 사이의 상호운용이 매끄러워야 한다는 것이 문제 설정이다.
MSVC는 Windows의 네이티브 플랫폼 컴파일러이며,
펌웨어와 드라이버, 커널과 하이퍼바이저, 마이크로서비스와 앱에 이르기까지
Microsoft 전반에서 Rust 사용이 늘어나면서 Rust가 그 생태계에 온전히
참여해야 한다.
하이브리드 Rust/C++ 프로젝트에서 특히 중요하다.

그 목표를 향한 가장 중요한 투자가 `rustc_codegen_utc`다.
이것은 rustc의 대체 코드 생성 백엔드이며 `rustc_codegen_llvm`,
`rustc_codegen_gcc`, `rustc_codegen_cranelift`와 같은 아키텍처 계열이다.
같은 백엔드 인터페이스에 연결되어 rustc의 공유 컴파일러 기계 장치를
MSVC 백엔드(일명 “UTC”)에 잇는다.

지원하려는 것은 여섯 가지다.
Windows 툴링 생태계와 ABI와의 높은 호환성, 바이너리 하드닝과 코드 보안
기능, 링크 후 컴플라이언스·분석·서비싱(Hotpatch 포함), 하이브리드
프로젝트를 위한 매끄러운 Rust/C++ 상호운용, 교차 언어 인라이닝과
최적화와 SPGO(Sample Profile Guided Optimization), 디버깅과 크래시 덤프
분석, 그리고 프로파일링과 진단과 커버리지다.

이 능력과 워크플로는 MSVC 기술 스택 위에서 여러 해에 걸쳐 만들어졌다.
rustc를 그 백엔드에 연결하면 Windows 고유 기능을 하나하나 병렬로 다시
구현하는 대신 같은 플랫폼 투자 위에서 기본적으로 완전한 호환성을
얻는다는 것이다.
결과는 Windows에서 Rust와 C++를 위한 통합 코드 생성 플랫폼이다.

### 통합 백엔드의 전략적 의미

Microsoft의 프로덕션 소프트웨어는 광범위한 보안·품질 워크플로를 거친다.
Rust가 Tier-1 언어가 됐지만 수십 년의 개발을 거친 C++가 여전히
지배적이며, 통합 코드 생성 플랫폼을 쓰면 유지보수와 진화 비용을 모두
최소화할 수 있다.
MSVC와 Windows는 계속 혁신하고 새 코드 생성 능력과 보안 기능과 진단과
서비싱 기술이 늘 추가되는데, `rustc_codegen_utc`가 있으면 그 투자가
C++와 Rust 공통의 토대에 안착한다.
저자는 이것이 운영상 중복 엔지니어링을 줄인다는 점에서도 중요하지만
전략적으로도 중요하다고 적는다.
Rust가 Microsoft의 Windows 네이티브 엔지니어링 생태계에 직접
참여하게 된다는 것이다.

상호운용에 대해서는 다른 플랫폼과의 대비를 든다.
다른 플랫폼에서 하이브리드 Rust/C++ 프로젝트가 C++를 Clang으로 빌드하면
두 언어가 이미 같은 LLVM 코드 생성 플랫폼에 닿는다.
`rustc_codegen_utc`는 MSVC가 네이티브 플랫폼 컴파일러인 Windows 네이티브
C++ 프로젝트에 같은 공유 백엔드 기회를 만든다.
다만 저자는 코드젠과 플랫폼 특이사항과 ABI와 예외 처리와 링크 후 툴링이
상호운용 과제의 절반일 뿐이라고 단서를 단다.
고품질의 언어 수준 상호운용, FFI 계약, 바인딩, 언어 의미론의 차이,
빌드 시스템이 사내와 업계 전반에서 작업 중인 문제이며, Rust Foundation의
Interoperability Initiative를 참조하라고 안내한다.

### 배포 현황

`rustc_codegen_utc`는 Microsoft DevDiv의 전담 팀이 진행한 주요 투자이며
2026년 초부터 프로덕션 준비 상태였다.
Rust 1.90부터 자체 호스팅(self-hosted)되고 있고, rustc와 표준 라이브러리와
관련 도구의 보안 공급망 빌드, 로컬 개발과 프로덕션 파이프라인과의 통합,
엔지니어링 시스템의 공통 품질·컴플라이언스 워크플로를 포함하는 더 넓은
내부 Rust 플랫폼의 일부다.

오늘 기준 100개가 넘는 Microsoft 프로젝트 저장소가 이것으로 빌드하며,
매주 더 많은 저장소가 채택하면서 롤아웃이 계속된다.
저자는 이것을 Rust의 전체 엔지니어링 수명 주기 — 획득, 툴링, 품질, 보안,
플랫폼 통합, 프로덕션 배포, 장기 지원 — 에 대한 지속적 투자의 일부로
규정한다.
질문이나 피드백은 Rust 프로젝트 Zulip의 전용 토픽에 남기라고
안내하며 글이 끝난다.

## 분석

### “Tier-1”이라는 단어가 Rust 프로젝트의 용법과 다르게 쓰였다

Rust 커뮤니티에서 tier 1은 정해진 뜻이 있다.
rustc의 플랫폼 지원 등급이며 tier 1은 CI에서 전체 테스트가 돌고
공식 바이너리가 배포되는 대상을 가리킨다.
이 글의 “Tier-1 언어”는 그것이 아니라 Microsoft 내부의 언어 지원 등급이다.
같은 용어를 다른 체계에서 쓴 것이며, Rust Foundation 블로그에
실린 글이라는 점에서 혼동의 여지가 있다.

그런데 이 선택이 우연은 아닐 것이다.
저자는 Tier-1 지위를 “paved path”로 정의하고 그 내용을 여섯 항목으로
열거하는데, 이것은 플랫폼 지원 등급의 정의 방식과 형식이 같다.
즉 언어를 플랫폼처럼 다루는 어휘를 의도적으로 가져온 것이며,
사내 언어 정책을 공학적 등급 체계로 서술하려는 시도로 읽힌다.

HN에서 Havoc이 물은 것 — Microsoft가 다른 어떤 언어를 tier 1로 보고
tier 2에는 무엇이 있느냐 — 이 이 어휘의 공백을 짚는다.[^Havoc]
글은 C++, C#, TypeScript, Rust 넷을 들지만 등급 체계의 나머지는
밝히지 않으며, 무엇이 tier 1이 아닌지가 없으면 tier 1이라는 표현의
정보량이 줄어든다.

### 이 발표의 실질은 언어 정책이 아니라 컴파일러 백엔드다

제목과 첫 문단은 언어 지위에 관한 것이지만 본문의 대부분은
`rustc_codegen_utc`에 할애된다.
HN의 pornel이 이 점을 한 줄로 요약했다.
여기서 큰 뉴스는 LLVM을 MSVC 백엔드로 대체했다는 것이다.[^pornel]

이 구분이 중요한 이유는 검증 가능성 때문이다.
“Rust가 전략적으로 중요하다”는 선언은 여러 해 반복돼 왔고 그
자체로는 새롭지 않다.
전담 팀이 대체 코드젠 백엔드를 만들어 100개 넘는 저장소에서 프로덕션으로
돌린다는 것은 자원 투입의 증거이며, 선언과 달리 되돌리기 어렵다.

pjmlp가 HN에서 짚은 것도 그 층위다.
C와 C++ 언어 툴링에서 역할을 하는 모든 주요 OS 벤더가 이제 시스템
프로그래밍 언어 선택지를 다변화했으며, MSVC 통합 소문에 대한 공개
소식을 마침내 얻었다는 것이다.[^pjmlp]
즉 이 발표의 뉴스 가치는 방향 전환이 아니라 소문의 확인에 있다.

### LLVM 우회가 Rust 생태계에 제기하는 물음

`rustc_codegen_utc`는 `rustc_codegen_gcc`와 `rustc_codegen_cranelift`에
이은 세 번째 계열 대안이지만 성격이 다르다.
앞의 둘은 커뮤니티 프로젝트이고 이것은 한 기업이 자사 플랫폼을 위해 만든 것이다.

이 차이가 만드는 물음을 HN의 swiftcoder가 직접 던졌다.
Microsoft 바깥에서도 쓸 수 있게 열 것인가.[^swiftcoder]
글은 답하지 않는다.
오픈소스 여부도, 라이선스도, 외부 배포 계획도 언급되지 않는다.

성능에 대한 정보는 오히려 Zulip 스레드에서 나왔다.
e4m2가 인용한 바로는 rustc perf suite를 포함한 여러 워크로드를 돌린 결과
런타임 성능이 대체로 LLVM과 동등하며, 본인도 예상하지 못한 결과라고
적었다.[^e4m2]
LLVM의 최적화 성숙도를 감안하면 이것은 상당한 성취인데, 보도문 성격의
이 글에는 성능 수치가 한 줄도 없다.

## 비평

### Tier-1이라는 지위와 실제 사용 규모 사이의 간극이 서술되지 않는다

글은 “100개가 넘는 저장소가 이것으로 빌드한다”를 롤아웃의 근거로 제시한다.
Microsoft의 저장소 총수를 생각하면 100개는 작은 숫자이며, 글은 그
분모를 밝히지 않는다.

현장 증언이 이 간극을 보여 준다.
Lobste.rs에서 Azure Storage에서 매일 C++를 쓴다는 ahelwer는 자기가 본
바로는 Rust가 Microsoft에서 아직 널리 쓰이지 않으며 그것이 바뀌기를
바란다고 적었다.
그 거대한 C++ 프로젝트에 Rust를 도입하면 좋겠지만 지난번 시도에서
FFI가 꽤 복잡했고 특히 COM 같은 오래된 Microsoft 기술과 연동하기가
까다로웠다는 것이다.[^ahelwer]
같은 사람이 덧붙이길, 자기 조직에는 Rust를 아는 현업 개발자가 매우
적으며 Russinovich 같은 윗선의 지침을 가리키는 것이 도움이 될 수는
있다고 했다.[^ahelwer2]

이 증언과 글의 서술이 모순되지는 않는다.
Tier-1은 지원 수준이지 채택률이 아니기 때문이다.
문제는 글이 그 구분을 명시하지 않아 독자가 채택 규모를 실제보다
크게 추정하게 된다는 점이다.
“Rust가 Tier-1이 됐다”는 헤드라인과 “아직 널리 쓰이지 않는다”는
현장 관찰이 둘 다 참일 수 있으며, 그 사실이 글에 없다.

### 상호운용의 어려운 절반을 인정하면서 진척도는 말하지 않는다

저자는 코드젠과 ABI와 링크 후 툴링이 상호운용 과제의 절반일 뿐이며
언어 수준 상호운용과 FFI 계약과 바인딩과 의미론 차이와 빌드 시스템이
남아 있다고 정직하게 적는다.
그런데 그 나머지 절반에 대해서는 Rust Foundation의 Interop
Initiative 링크를 제시하는 데 그친다.

이 공백이 실무적으로 결정적이다.
HN의 abbefaria27이 정확히 이 지점을 물었다.
요즘 Rust와 C++ 상호운용은 어떤 상태인지, 그것이 채택을 막는
요인이며, 자기가 아는 대부분의 C++ 개발자는 Rust라는 발상을 좋아하지만
아무도 30년 된 작동하는 코드를 다시 쓰지 않을 것이고 점진적으로
통합할 수 있어야 한다는 것이다.[^abbefaria27]

이 물음에 대한 가장 구체적인 답은 글이 아니라 Lobste.rs 댓글에서 나왔다.
Microsoft의 Rust 권고 기술 전략 문서 공동 저자였던 david_chisnall에
따르면, 그 권고의 일부가 C++와의 긴밀한 통합이 필요한 경우에만 C++를
쓰되 그 제약을 없애는 데 투자하라는 것이었고, 이후 Microsoft가 Rust의
COM 지원을 포함한 Rust/C++ 상호운용 개선에 1,000만 달러를 투자했다는
것이다.
다만 본인이 회사를 떠날 때까지 그 작업이 크게 진척되지는
않았다고 덧붙인다.[^david_chisnall]

즉 투자 규모는 공개돼 있는데 결과는 공개돼 있지 않다.
백엔드 통합의 진척도는 저장소 수로 제시하면서 상호운용의 진척도는
이니셔티브 링크로 대신하는 비대칭이 이 글의 가장 큰 정보 공백이다.

### 도구 지원의 핵심 항목이 빠져 있다

Tier-1 정의에 “생산적인 개발자 도구”가 들어 있는데, 본문은
컴파일러 백엔드만 다룬다.
HN에서 같은 질문이 두 번 나왔다.
petilon은 Tier-1이라면 왜 Visual Studio에서 지원되지 않느냐고
물었고,[^petilon] ComputerGuru는 언제 Visual Studio에서 Tier-1 디버깅
지원을 받게 되느냐고 물었다.[^ComputerGuru]

이 물음이 정당한 이유는 글 자신이 디버깅과 크래시 덤프 분석을
`rustc_codegen_utc`의 목표 중 하나로 열거했기 때문이다.
MSVC 백엔드에 연결하면 PDB와 기존 디버깅 인프라를 그대로 쓸 수 있다는
함의가 있는데, 그것이 실제로 Visual Studio 사용자 경험으로 이어졌는지는
언급되지 않는다.

이 공백은 대상 독자의 문제이기도 하다.
Rust Foundation 블로그의 독자는 Rust 개발자이고 그들 다수는
Visual Studio를 쓰지 않는다.
반면 이 글이 설득해야 할 Microsoft 내부 C++ 개발자는 Visual Studio를
쓴다.
게재 지면과 설득 대상이 어긋나 있으며, 그 결과 글은 두 청중 중
어느 쪽에도 필요한 정보를 다 주지 못한다.

### 내부 정치에 대한 회의를 다루지 않는다

글은 Rust가 C++, C#, TypeScript와 “나란히” 있다고 서술한다.
Lobste.rs와 HN 양쪽에서 이 수평 관계에 대한 회의가 나왔다.

VC++와 .NET 팀에 있었다는 splicebot의 증언이 가장 직접적이다.
자기 재직 시절 Microsoft에 1등급 언어는 하나뿐이었으며 그것은
Windows가 원하는 무엇이든 되기 위해 존재하는 VC++였고, 자기가 떠난
지 10년 됐지만 달라졌다는 말을 듣지 못했으며 이 블로그가 사실상 그
인상을 확인해 준다는 것이다.
그리고 Rust 팀에게 밀려날 테니 되받아 미는 데 능하기를 바란다는
조언을 남겼다.[^splicebot]

이 관점에서 보면 통합 백엔드는 대등한 참여가 아니라 종속의 형태다.
Rust가 MSVC 백엔드에 연결되면 Windows 플랫폼 투자를 함께 받지만,
동시에 MSVC의 일정과 우선순위에 묶인다.
글은 이 관계를 “Rust가 생태계에 온전히 참여한다”는 긍정형으로만
서술하며, 참여의 대가는 한 줄도 다루지 않는다.

HN에서 js8과 zapzupnz가 반농담으로 던진 embrace·extend·extinguish
언급도[^js8] 근거 있는 분석은 아니지만 이 불편함의 표현이다.

## 인사이트

### 언어 채택의 마지막 관문은 문법이 아니라 사후 처리 도구다

`rustc_codegen_utc`가 지원하려는 목록을 보면 컴파일 자체는 일부에 불과하다.
링크 후 컴플라이언스와 분석과 서비싱, Hotpatch, 크래시 덤프 분석,
SPGO, 커버리지가 함께 있다.
이것들은 코드를 만드는 도구가 아니라 이미 배포된 코드를 다루는 도구다.

대규모 조직에서 언어 채택이 막히는 지점이 대체로 여기다.
새 언어로 코드를 쓰는 것은 개인이 결정할 수 있지만, 그 코드가 배포된
뒤 보안 패치를 어떻게 적용하고 크래시 덤프를 어떻게 읽고 프로파일을
어떻게 뜨는지는 조직 차원의 인프라 문제다.
그 인프라가 없으면 언어를 좋아하는 팀도 프로덕션에 올릴 수 없고,
그래서 채택이 실험 단계에서 멈춘다.

Hotpatch가 목록에 들어 있는 것이 특히 시사적이다.
재부팅 없이 커널과 서비스를 패치하는 기술은 Windows Server 운영의
핵심이며, Rust로 쓴 코드가 그 절차에 참여하지 못하면 그 영역에는
들어갈 수 없다.
즉 이 백엔드 투자가 실제로 여는 것은 새 애플리케이션이 아니라
기존 운영 체계 안의 자리다.

여기서 나오는 일반 원리는 언어 전환의 비용 구조에 관한 것이다.
재작성 비용은 눈에 보이고 자주 논의되지만, 실제로 전환을 막는 것은
배포 이후의 도구 체인 전체를 복제하는 비용이며 그것은 재작성보다
크고 덜 논의된다.
Microsoft가 병렬 구현 대신 기존 백엔드 연결을 택한 이유도 그 비용
계산이며, 다른 조직에 주는 교훈은 언어 전환 계획에서 컴파일러가
아니라 운영 도구 목록부터 세어 보라는 것이다.

### 메모리 안전 언어로의 전환이 언어 논쟁에서 코드 생성 인프라 논쟁으로 내려왔다

지난 몇 년의 Rust 담론은 “다시 쓸 것인가”였다.
HN의 bryanlarsen이 관찰한 대로 올해 RustConf의 초점 상당 부분은
C++ 상호운용과 Python 상호운용과 JavaScript 상호운용이었고, 더는
rewrite it in Rust가 아니라 생태계의 일부가 되는 것이라는 것이다.
[^bryanlarsen]

이 이동은 논쟁의 층위가 내려갔다는 뜻이다.
언어 선택은 팀이 하고 상호운용은 조직이 하며 코드 생성 백엔드는
플랫폼 벤더가 한다.
논쟁이 아래로 내려갈수록 참여자가 줄고 결정이 되돌리기 어려워지며,
그래서 지금 벌어지는 일이 앞으로 십 년의 기본값을 정한다.

역사적 유비로는 C++가 플랫폼 언어가 된 과정이 있다.
C++가 Windows의 기본이 된 것은 언어 논쟁에서 이겨서가 아니라 MFC와
COM과 Visual Studio와 PDB가 C++를 전제로 만들어졌기 때문이며, 그
전제가 쌓인 뒤에는 다른 선택이 사실상 불가능해졌다.
`rustc_codegen_utc`는 그 전제의 층에 Rust를 넣는 작업이며, 성공하면
십 년 뒤 Rust를 쓰지 않을 이유가 줄어든다.

동시에 이 층위의 통합에는 비대칭이 있다.
Rust는 MSVC 생태계에 들어가지만 MSVC는 Rust 생태계에 들어가지
않는다.
cargo와 crates.io와 rustdoc은 여전히 Rust 쪽에 있다.
그래서 장기적으로 두 개의 중력이 생긴다.
Windows 프로덕션 요구가 끄는 쪽과 Rust 커뮤니티 도구가 끄는 쪽이며,
Microsoft 내부 Rust와 바깥 Rust의 실무 경험이 갈릴 가능성이 있다.

### 시스템 언어로 애플리케이션을 쓰는 관행이 이 전환의 숨은 쟁점이다

이 글에서 가장 논쟁적인 반응은 언어 지위가 아니라 용도에 관한 것이었다.
Microsoft 기술 전략 문서 공동 저자 david_chisnall이 권고의 마지막
항목으로 적은 것이 그것이다.
저수준 기능이 필요 없는 신규 프로젝트라면 제발 시스템 프로그래밍
언어를 쓰지 말라는 것이며, C#과 TypeScript가 바로 거기 있고 좋으며
생산적으로 만들어 준다는 것이다.
그리고 자기가 정말 원했던 것은 사람들이 시스템 프로그래밍 언어로
고수준 애플리케이션 코드를 쓰는 것을 멈추게 하는 것이었으며, 그렇게
하는 것은 진짜 남자가 되는 것이 아니라 못을 치는 데 드라이버를 쓰는
사람이 되는 것이라고 적었다.[^david_chisnall]

이 권고가 흥미로운 이유는 Rust 채택 확대와 방향이 다르기 때문이다.
Tier-1 지위와 paved path는 Rust를 쓰기 쉽게 만드는 장치이고, 쓰기
쉬워지면 저수준 기능이 필요 없는 곳에도 쓰이게 된다.
즉 이 글이 알리는 성취가 전략 문서가 막으려 한 결과를 촉진할 수 있다.

Lobste.rs에서 이 권고에 대한 반박도 곧바로 나왔다.
hjvt는 완전한 패턴 매칭, 자립 실행 파일 생산, Rust에 근접한 툴링,
그리고 괜찮은 다형성을 모두 갖춘 “애플리케이션 프로그래밍 언어”를
대 달라고 물었다.[^hjvt]
natkr는 시스템 프로그래밍을 마초주의로 보는 것도 싫지만 그 반작용
또한 상당 부분 C에서 온 것이라며, 순수한 프로그래머 만족도 관점에서
Rust와 경쟁할 만한 고수준 언어를 모르겠다고 적었다.[^natkr]

이 대립이 드러내는 것은 언어 선택이 기술 요구가 아니라 개발자
경험으로 결정되는 국면에 들어섰다는 점이다.
GC가 있어도 되는 곳에 GC 없는 언어를 쓰는 이유가 성능이 아니라 타입
시스템과 도구와 오류 메시지라면, 조직의 언어 정책은 “필요한가”가
아니라 “사람들이 원하는가”를 상대해야 한다.
그리고 Tier-1 지원은 그 원함을 실행 가능하게 만들어 주는 장치이므로,
정책과 인프라가 서로 반대 방향으로 작동하는 구조가 남는다.

### 백엔드 다변화는 Rust 언어 명세에 부담을 옮긴다

`rustc_codegen_utc`가 성공적으로 자리 잡으면 Rust는 프로덕션급
백엔드를 둘 갖게 된다.
지금까지 Rust의 사실상 명세는 rustc와 LLVM의 조합이 하는 일이었고,
정의되지 않은 구석은 LLVM의 동작이 답이었다.

백엔드가 둘이 되면 그 답이 갈릴 수 있다.
부동소수점 세부 동작, 정의되지 않은 동작의 실제 귀결, 인라이닝과
최적화가 관측 가능한 동작에 미치는 영향, 그리고 특히 `unsafe` 코드가
의존해 온 암묵적 가정들이 백엔드마다 다르게 나타날 수 있다.
C와 C++가 여러 컴파일러를 가지면서 겪은 것이 정확히 이 문제이며,
그 대응으로 나온 것이 엄밀한 표준 문서와 정의되지 않은 동작
목록이었다.

Rust에는 아직 그런 의미의 공식 표준이 없다.
Ferrocene의 명세 작업과 Rust Project의 MIR 의미론 정리가 진행
중이지만 완결되지 않았다.
백엔드 다변화가 그 작업의 우선순위를 올릴 것이며, 이것이 이 발표의
가장 덜 논의된 파급 효과다.

역설적인 것은 이 부담이 Rust 생태계 전체에 걸린다는 점이다.
`rustc_codegen_utc`가 Microsoft 내부용으로 남더라도, 그 백엔드에서만
드러나는 의미론 문제가 보고되면 Rust 프로젝트가 답해야 한다.
백엔드는 사유일 수 있지만 그것이 제기하는 명세 질문은 공유되며,
그 비용은 커뮤니티가 진다.
swiftcoder의 물음 — 외부에 열 것인가 — 이 중요한 실무적 이유도
여기에 있다.
열려 있으면 검증이 분산되고, 닫혀 있으면 문제 보고만 들어오고
재현은 불가능해진다.
