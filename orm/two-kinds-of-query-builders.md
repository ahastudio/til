# 같은 모양, 다른 원리: SQL 쿼리 빌더는 데이터 지향과 구문 지향 두 종류로 갈린다

원문: [Two Kinds of SQL Query Builders · FunSQL.jl](https://mechanicalrabbit.github.io/FunSQL.jl/stable/two-kinds-of-sql-query-builders/)

Lobste.rs 토론: <https://lobste.rs/s/zknqct/two_kinds_sql_query_builders> (26점, 16개 댓글)

GN 토론: <https://news.hada.io/topic?id=34562>

## 요약

Julia용 SQL 쿼리 빌더 FunSQL.jl 문서에 실린 글이다.
글은 SQL의 역설로 시작한다.
SQL은 사람이 쓰도록 설계되었지만, 오늘날 대부분의 SQL은 컴퓨터가 생성한다.
그런데 SEQUEL, 즉 Structured English Query Language라는 원래 이름처럼 유사 영어 문법이 복잡해서 생성하기 어렵고, 그래서 쿼리 빌더 라이브러리가 쓰인다.
FunSQL은 SQL의 질의 능력 전체를 지원하면서, 그것을 조합 가능한 데이터 지향 인터페이스로 노출한다는 두 목표를 내세운다.

글은 OMOP CDM 데이터베이스에서 가장 나이 많은 남성 환자 100명을 찾는 질의를 다섯 라이브러리로 쓴다.
FunSQL, Ruby의 Active Record, PHP의 Laravel, C#의 EF/LINQ, R의 dbplyr 모두 필터, 정렬, 제한, 선택을 차례로 잇는 같은 모양의 파이프라인이다.
독립된 부품을 차례로 이어 질의를 만든다는 점에서 모두 조합 가능한 인터페이스다.

차이는 파이프라인 순서를 바꿀 때 드러난다.
정렬과 제한을 필터 앞으로 옮기면, FunSQL과 EF/LINQ와 dbplyr에서는 결과가 가장 나이 많은 남성 환자 100명에서 가장 나이 많은 환자 100명 중 남성으로 바뀐다.
Active Record와 Laravel에서는 결과가 바뀌지 않는다.
앞의 셋은 노드 순서에 민감하고, 뒤의 둘은 그렇지 않다.

글은 이 차이를 각 노드가 처리하는 정보의 종류로 설명한다.
데이터 지향 빌더에서 파이프라인은 질의의 기대 출력을 명세한다.
노드가 데이터를 직접 처리한다고 가정했을 때의 결과와 생성된 SQL의 결과가 같아야 한다.
SQL은 `FROM`, `JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT`, 그리고 맨 위에 쓰지만 마지막에 실행되는 `SELECT`라는 고정된 절 순서를 가지므로, 이 순서에 맞지 않는 파이프라인은 SQL-92가 도입한 중첩 질의, 즉 `FROM` 안의 하위 질의로 쪼개 변환한다.
반면 구문 지향 빌더는 `select`, `from`, `where`, `orderby`, `limit` 같은 칸을 가진 SQL 구문 트리를 빌더 패턴으로 채운다.
칸의 내용만 같으면 채우는 순서는 상관이 없으므로 순서에 둔감하다.

어느 쪽이 나은지에 대해 글은 양쪽을 평가한다.
구문 지향 빌더는 구현이 쉽고 SQL 기능 전체를 지원할 수 있지만, SQL 문법의 결함을 그대로 물려받아 복잡한 파이프라인을 조립하기 어렵다.
데이터 지향 빌더는 파이프라인 조립이 쉽지만, 필요한 노드를 빌더가 제공해야 한다.
EF/LINQ와 dbplyr은 범용 질의 프레임워크인 LINQ와 dplyr을 SQL로 옮기는 SQL pushdown 방식으로 만들어졌는데, 원래 프레임워크가 SQL을 염두에 두지 않았으므로 일부 파이프라인은 SQL로 바꿀 수 없고, 반대로 유용한 SQL 상당수는 대응하는 파이프라인이 없다.
글은 SQL-86의 상관 하위 질의, SQL-92의 조인 유형과 중첩, SQL:1999의 재귀 질의와 데이터 큐브, SQL:2003의 윈도 함수를 열거하며, SQL을 일관성 없는 기업형 괴물이라 부르면서도 그 능력의 폭은 어떤 프레임워크도 따라오지 못했다고 쓴다.
FunSQL은 기존 프레임워크를 옮기지 않고 처음부터 SQL의 능력에 맞춰 설계해 `Bind`로 상관 하위 질의와 lateral join을, `Group`과 `Partition`으로 집계와 윈도 함수를, `Iterate`로 재귀 질의를 지원하며, 모든 노드가 데이터 처리 의미론을 가지므로 원리상 SQL을 대체할 질의 언어로 발전할 수도 있다고 끝맺는다.

## 분석

### 같은 인터페이스가 서로 다른 계약을 숨긴다

글의 가장 중요한 관찰은 표기법이 의미를 보장하지 않는다는 점이다.
다섯 라이브러리의 코드는 거의 같아 보이지만, 메서드 체인의 각 단계가 데이터를 변환하는지, 구문 트리의 칸을 채우는지는 코드만으로 알 수 없다.
이 차이는 순서를 바꿔 보기 전까지 드러나지 않는다.

이 관찰이 실무에서 중요한 이유는 조건부로 질의를 조립할 때 순서가 자주 바뀌기 때문이다.
권한에 따라 필터를 더하고, 페이지네이션을 위해 제한을 더하는 코드에서, 구문 지향 빌더는 어디에 무엇을 붙였든 같은 SQL을 만든다.
데이터 지향 빌더는 붙인 순서대로 의미가 쌓인다.
같은 코드 모양을 보고 다른 라이브러리의 직관을 가져오면, 오류 없이 다른 결과가 나온다.

### 구문 지향은 SQL의 결함을 상속하고, 데이터 지향은 SQL의 결함을 숨긴다

글은 SQL 문법의 결함으로 고정된 절 순서, 질의 중첩, 실행 흐름과 어긋나는 `SELECT`의 위치를 든다.
구문 지향 빌더는 이 결함을 그대로 노출한다.
데이터 지향 빌더는 파이프라인을 SQL 순서에 맞게 쪼개고 중첩해서 결함을 사용자에게서 가린다.

Lobste.rs에서 lalitm은 글이 BigQuery의 파이프 구문을 끝까지 다루지 않은 것이 놀랍다며, 데이터베이스가 파이프 SQL을 지원하면 이 글과 일반적인 SQL 비판의 상당수가 풀린다고 썼다[^lalitm].
quad는 2024년 논문 SQL Has Problems. We Can Fix Them: Pipe Syntax In SQL을 인용하며, 파이프 구문이 SQL에 내장된 데이터 지향 쿼리 빌더라고 정리했다[^quad].
Google에서 일한다는 willhbr은 파이프 구문 덕분에 테스트용으로 `LIMIT`이나 `WHERE`를 줄 단위로 주석 처리했다 풀었다 할 수 있다고 했다[^willhbr].
글이 쿼리 빌더 계층에서 풀려는 문제를, 데이터베이스가 언어 차원에서 직접 풀기 시작했다는 것이다.

### SQL pushdown의 한계는 의미론의 불일치에서 온다

EF/LINQ와 dbplyr에 대한 글의 비판은 구현이 아니라 출발점을 향한다.
LINQ와 dplyr은 메모리 위의 컬렉션과 데이터프레임을 위해 설계되었고, SQL은 그 의미론을 따라 만든 대상이 아니다.
그래서 SQL로 옮길 수 없는 연산이 생기고, SQL에만 있는 연산은 표현할 수 없다.

이는 번역 계층의 일반적인 운명이다.
두 언어의 의미론이 일치하지 않으면, 번역기는 교집합만 안전하게 다룰 수 있다.
FunSQL이 SQL의 능력에 맞춰 노드를 처음부터 설계했다는 주장은, 교집합 대신 SQL 쪽의 합집합을 목표로 삼았다는 뜻이다.

## 비평

### 유일하다는 주장은 비교 대상을 좁게 잡아 얻은 결론이다

글은 FunSQL만이 SQL 기능 전체와 데이터 지향 인터페이스를 함께 갖춘 유일한 빌더라고 말한다.
그러나 비교 대상은 다섯 라이브러리뿐이고, 그중 데이터 지향은 SQL pushdown으로 만든 두 개다.
SQL로 컴파일되는 파이프라인 언어처럼, SQL을 염두에 두고 처음부터 설계된 다른 시도는 다루지 않는다.

Lobste.rs의 viraptor는 PRQL을 예로 들며, 일반 키워드가 필요에 따라 하위 질의, CTE, 조인으로 번역되고 필터가 `WHERE`나 `HAVING`으로 알아서 바뀌는 파이프 구문을 소개했다[^viraptor].
BigQuery 파이프 구문도 같은 범주다.
유일함을 주장하려면 이런 시도와의 차이를 보여야 하는데, 글은 그 비교를 하지 않는다.
FunSQL의 실제 차별점은 Julia 안에서 노드를 일급 값으로 다루는 라이브러리라는 점일 텐데, 글은 그것을 범주 전체에 대한 우위로 확장한다.

### 쿼리 빌더가 왜 필요한지라는 질문을 건너뛴다

글은 쿼리 빌더가 필요하다는 전제에서 출발해, 어떤 빌더가 나은지를 묻는다.
Lobste.rs의 noteflakes는 예시들이 결국 평범한 SQL과 너무 닮았다며, SQL을 알아야 쓸 수 있으면서 CTE, 윈도 함수, `RETURNING` 같은 고급 기능은 막는 DSL의 가치가 `SELECT`를 끝에 쓰게 해 주는 것 말고 무엇이냐고 물었다[^noteflakes].
thiht는 몇 년째 SQL을 직접 쓰며, 동적 조건도 정적 질의로 쓰면 되고 덕분에 SQL 실력이 늘고 최종 질의에 놀랄 일이 없다고 했다[^thiht].

반대편의 답도 있었다.
yorickpeterse는 여러 데이터베이스에 같은 질의를 쓸 수 있고, 조건에 따라 질의를 문자열 연결 없이 조립할 수 있고, SQL 주입이 어려워지고, 정적 타입 언어에서는 어느 정도 타입 안정성을 얻는다고 정리했다[^yorickpeterse].
koala는 쿼리 빌더와 ORM을 혼동하기 쉽다며, 쿼리 빌더가 데이터베이스의 모든 SQL 기능을 지원하지 못할 이유는 없다고 덧붙였다[^koala].
이 논쟁은 글이 다뤘어야 할 앞 단계다.
쿼리 빌더의 목적이 동적 조립과 안전성이라면, 데이터 지향이냐 구문 지향이냐보다 그 목적에 어느 쪽이 맞는지가 먼저다.

### 쓰기 쉬움을 읽기 쉬움보다 앞세운다

글은 실행 순서대로 노드를 쓸 수 있다는 점을 데이터 지향 빌더의 장점으로 든다.
Lobste.rs의 neilmadden은 이것이 읽기 쉬움보다 쓰기 쉬움과 코드 완성을 앞세우는 것 아니냐며, 무엇이 반환되는지 알려고 질의 전체를 읽고 싶지는 않다고 했다[^neilmadden].
`SELECT`가 맨 위에 있는 SQL은 실행 흐름과 어긋나지만, 결과의 모양을 첫 줄에 보여 준다.

순서 민감성도 양날이다.
데이터 지향 빌더에서는 필터 하나를 어디에 붙이느냐에 따라 결과가 바뀌므로, 조건부 조립 코드를 읽는 사람은 실행 경로마다 노드의 순서를 추적해야 한다.
구문 지향 빌더의 순서 둔감성은 글이 결함으로 다루지만, 질의를 여러 함수에 나눠 조립하는 코드에서는 오히려 안전장치가 된다.
어느 쪽이 나은지는 질의가 분석용 파이프라인이냐, 애플리케이션의 조건부 조회냐에 따라 달라진다.

## 인사이트

### 순서에 민감한 빌더에서 조건부 조립은 새로운 버그의 근원이 된다

웹 애플리케이션은 흔히 기본 질의를 만든 뒤, 요청 파라미터에 따라 필터와 정렬과 페이지네이션을 덧붙인다.
구문 지향 빌더에서는 이 덧붙이기가 순서와 무관하게 같은 의미를 갖는다.
데이터 지향 빌더에서는 페이지네이션을 위한 제한이 권한 필터보다 먼저 붙으면, 먼저 100개를 자른 뒤 그중 권한 있는 것만 남기는 질의가 된다.
결과는 조용히 적어지고, 오류는 나지 않는다.

그래서 데이터 지향 빌더를 애플리케이션에 쓸 때는 조립 순서를 규약으로 정해야 한다.
예를 들어 권한 필터는 항상 원천 바로 뒤에, 제한은 항상 맨 끝에 붙이는 함수 구조를 강제하는 식이다.
글이 장점으로 든 자유로운 노드 배치는 분석가에게는 표현력이지만, 여러 사람이 함수 단위로 질의를 나눠 조립하는 팀에게는 순서 계약을 문서화해야 하는 비용이다.
Lobste.rs의 willhbr이 말한 것처럼 각 단계가 한 스키마에서 다른 스키마로의 변환이라면 조합이 쉬워지지만[^willhbr-compose], 그 변환의 순서가 곧 의미라는 사실도 함께 받아들여야 한다.

### 추상화 계층의 가치는 성능을 해치지 않는 재사용에서 나온다

Lobste.rs의 yumaikas는 쿼리 빌더의 가장 큰 이점이 문법 차이가 아니라, 여러 SQL 방언에서 성능상 어색해지기 쉬운 공통 로직을 추상화할 수 있다는 점이라고 했다[^yumaikas].
T-SQL 환경에서 큰 질의를 뷰와 프로시저로 나눴다가 성능이 크게 떨어진 경험도 덧붙였다.
k749gtnc9l3w도 모델 정의에서 조인을 생성하는 도우미나 자주 쓰는 필터 조각을 추상화하는 용도를 들었다[^k749gtnc9l3w].

이 관점에서 데이터 지향 빌더의 진짜 경쟁 상대는 구문 지향 빌더가 아니라 데이터베이스의 뷰와 CTE다.
뷰는 데이터베이스 안에서 재사용 단위를 만들지만, 최적화기가 뷰 경계를 넘어 최적화하지 못하면 성능을 잃는다.
쿼리 빌더는 애플리케이션 쪽에서 조각을 조합해 하나의 질의로 펼치므로, 최적화기는 펼쳐진 전체를 본다.
FunSQL 같은 빌더의 가치는 재사용 가능한 조각을 만들면서도 데이터베이스에는 하나의 평평한 질의를 넘겨줄 수 있다는 데 있고, 글은 이 점을 거의 말하지 않는다.

### SQL 위에 새 언어를 얹는 시도는 결국 데이터베이스가 흡수한다

FunSQL의 마지막 문장은 언젠가 SQL을 대체할 질의 언어로 발전할 수 있다는 기대다.
역사를 보면 SQL을 대체하려는 시도는 대체보다 흡수로 끝나는 경우가 많았다.
객체 데이터베이스와 NoSQL 운동은 SQL을 버리자고 했지만, 결국 많은 시스템이 SQL 인터페이스를 다시 더했고, SQL 쪽은 JSON 타입과 윈도 함수로 그 요구를 받아들였다.

파이프 구문도 같은 길을 걷고 있다.
Lobste.rs 댓글이 짚었듯, 쿼리 빌더가 풀던 절 순서와 중첩 문제를 BigQuery 같은 데이터베이스가 SQL 문법 안에서 직접 풀기 시작했다[^lalitm][^quad].
데이터베이스가 파이프 구문을 표준처럼 지원하게 되면, 데이터 지향 빌더의 차별점은 문법이 아니라 호스트 언어와의 통합, 즉 타입 검사와 재사용과 테스트 쪽으로 옮겨 간다.
simonw가 Django ORM에서 바꾸고 싶은 한 가지로 타입 힌트와 맞지 않는 이중 밑줄 표기를 꼽은 것처럼[^simonw], 그 경쟁은 이미 호스트 언어의 도구 체계 위에서 벌어지고 있다.
