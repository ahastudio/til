# react-native-glass-effect-view — iOS 26 리퀴드 글래스를 React Native에 이식하기

<https://github.com/tschoffelen/react-native-glass-effect-view>

## 소개

react-native-glass-effect-view는 Apple의 네이티브 리퀴드 글래스(liquid glass) 시각 효과를
React Native 컴포넌트로 감싼 패키지다.
iOS 26 이상에서는 Apple의 네이티브 글래스 효과 구현을 그대로 쓰고,
그보다 낮은 iOS 버전과 Android에서는 CSS 스타일의 그림자와 배경 블러로 대체(폴백)한다.
별 47개, 포크 6개, MIT 라이선스이며 커밋 30개 규모의 활성 저장소다.
저장소에는 구현 지원을 위한 전문 컨설팅 서비스 제공 안내도 있다.

## 설치와 사용법

npm으로 설치한다.

```bash
npm install react-native-glass-effect-view
```

iOS 빌드에는 Xcode 26 이상이 필요하다.

기본 사용법은 다음과 같다.

```javascript
import { GlassEffectView } from "react-native-glass-effect-view";

<GlassEffectView>
  <Text>Hello world!</Text>
</GlassEffectView>
```

## 설정 프로퍼티

컴포넌트는 `appearance`(“light”/“dark”/“default”), `useNative`(불리언),
`tintColor`(문자열), `style`(ViewStyle), 표준 `ViewProps`를 받는다.

## 플랫폼 지원

iOS 26 이상에서는 네이티브 구현이 쓰이고,
iOS 26 미만과 Android에서는 폴백 블러 구현이 쓰인다.

## 분석

### “네이티브 우선, 폴백 보장”이라는 구조가 크로스플랫폼 라이브러리의 표준 해법이 됐다

이 라이브러리의 설계는 특정 문제 하나를 겨냥한다.
Apple이 플랫폼 고유의 새 시각 효과를 내놓을 때마다
크로스플랫폼 개발자는 그 신기능을 쓸지, 아니면 모든 플랫폼에서 동작하는
낮은 공통분모로 타협할지 선택해야 했다.
이 패키지는 그 선택을 없앤다.
`useNative` 플래그와 자동 버전 감지로 지원되는 곳에서는 진짜 네이티브 효과를,
지원되지 않는 곳에서는 근사한 대체 효과를 자동으로 골라 쓴다.

이 패턴 자체는 새롭지 않다.
`react-native-blur`, `expo-blur`처럼 OS 고유 시각 효과를
크로스플랫폼으로 감싸는 라이브러리들이 이미 오랫동안 이 구조를 써 왔다.
이 프로젝트가 흥미로운 지점은 그 표준 해법을 아주 짧은 시간 안에,
Apple의 발표 이후 Xcode 26이 나오자마자 리퀴드 글래스라는
가장 최신의 시각 언어에 적용했다는 속도다.
크로스플랫폼 생태계가 플랫폼 벤더의 신기능에 반응하는 주기가
과거보다 훨씬 짧아졌다는 것을 보여주는 사례로 읽을 수 있다.

### 폴백이 “비슷해 보이는 것”과 “진짜인 것”의 간극을 어떻게 처리하는지가 이 라이브러리의 진짜 가치다

README는 폴백을 “CSS 스타일의 그림자와 배경 블러”로 간단히 설명하지만,
실제로 리퀴드 글래스는 단순한 블러 이상의 효과다.
Apple의 원본 구현은 배경의 색상과 밝기에 따라 유리 표면이 굴절하듯 반응하고,
스크롤이나 상호작용에 따라 표면이 동적으로 일렁이는 애니메이션을 포함한다.
CSS 그림자와 정적 블러로는 이 동적 반응성을 재현할 수 없다.

이 간극을 어떻게 처리하느냐가 이런 종류의 “네이티브 흉내” 라이브러리의
실질적 품질을 가른다.
폴백이 원본과 시각적으로 너무 다르면 개발자는 두 플랫폼에서
전혀 다른 느낌의 앱을 배포하게 되고, 이는 크로스플랫폼 개발의
근본 목적(일관된 경험)을 훼손한다.
반대로 폴백을 원본에 최대한 가깝게 만들려고 애쓰면
그 자체로 상당한 구현 복잡도를 떠안게 된다.
이 라이브러리가 이 트레이드오프를 어느 지점에서 타협했는지가
README만으로는 충분히 드러나지 않는다.

## 비평

### “네이티브”라는 표현이 실제 채택 가능성을 과장한다

README는 “iOS 26+에서 네이티브 구현을 쓴다”는 점을 핵심 기능으로 내세운다.
그런데 iOS 26이 나온 지 얼마 되지 않은 시점에서, 실제 사용자 기기의
상당수는 여전히 iOS 26 미만을 쓰고 있을 가능성이 크다.
새 OS 버전이 나온 뒤 사용자 기반이 그 버전으로 넘어가는 데는
통상 1~2년이 걸리는 것이 iOS 생태계의 일반적인 패턴이다.

이 말은 이 라이브러리를 도입하는 개발자 대다수가 실제로는
대부분의 사용자에게 폴백 구현을 보여 주게 된다는 뜻이다.
“네이티브 리퀴드 글래스”라는 헤드라인 기능이 실제로 작동하는 비율은
지금 시점에서는 상당히 낮을 수 있다.
README가 이 채택 곡선의 현실을 언급하지 않고
네이티브 지원을 마치 지금 당장 대다수 사용자에게 적용되는 기능처럼
서술하는 것은, 실제 배포 시나리오를 과장되게 그린다.

### Android 지원이 “명목상 지원”에 머무를 위험이 있다

플랫폼 지원표를 보면 Android는 항상 폴백 구현만 쓰도록 돼 있다.
이것은 기술적으로는 정직한 설계지만, 크로스플랫폼 라이브러리라는
이름표가 함의하는 것(양쪽 플랫폼에서 동등한 가치를 제공한다는 기대)과는
거리가 있다.
Android 개발자 입장에서 이 라이브러리를 선택할 이유는
“iOS의 최신 효과를 흉내 낸 블러”뿐이고, Android 고유의 대응 효과
(예: Material You의 다이나믹 컬러나 Android 자체의 블러 API)와
통합될 계획은 README에서 언급되지 않는다.

이는 이 라이브러리가 본질적으로 “iOS 우선, Android는 구색 맞추기”
구조라는 것을 시사한다.
저장소 이름과 설명이 “React Native”라는 크로스플랫폼 프레임워크를
전면에 내세우지만, 실질적인 설계 목표는 iOS의 신기능을
React Native 생태계에 이식하는 것에 가깝다.
이것이 나쁜 선택은 아니지만, 프로젝트 설명에서 이 비대칭을
더 명확히 밝혔다면 Android 중심 프로젝트를 찾는 개발자들이
시간을 낭비하지 않았을 것이다.

### “전문 컨설팅 서비스” 안내가 오픈소스 프로젝트의 유지보수 동기를 불투명하게 만든다

저장소에 컨설팅 서비스 안내가 붙어 있다는 것은
이 프로젝트가 순수한 커뮤니티 기여작이 아니라
상업적 서비스의 포트폴리오 또는 리드 제너레이션 수단으로도 기능한다는 뜻이다.
이 자체가 문제는 아니다.
많은 성공적인 오픈소스 프로젝트가 이런 방식으로 유지보수 자금을 조달한다.

그러나 이 구조는 프로젝트의 우선순위에 대한 질문을 남긴다.
버그 수정과 신규 기능 추가가 커뮤니티의 요청에 따라 이뤄지는지,
아니면 컨설팅 고객의 요구에 맞춰 우선순위가 정해지는지가
외부에서는 확인하기 어렵다.
별 47개, 커밋 30개라는 아직 이른 단계의 프로젝트에서
이런 상업적 요소가 이미 노출돼 있다는 것은,
장기적으로 이 프로젝트가 열린 커뮤니티 프로젝트로 성장할지
아니면 컨설팅 사업의 홍보 도구로 남을지가 아직 불확실하다는 뜻이기도 하다.

## 인사이트

### 플랫폼 벤더의 신기능은 이제 서드파티 생태계의 반응 속도로 그 채택 곡선이 결정된다

이 라이브러리의 존재 자체가 하나의 구조적 패턴을 보여준다.
Apple 같은 플랫폼 벤더가 새로운 시각 언어를 발표하면,
그 기능이 실제로 널리 쓰이는 데 걸리는 시간은
Apple의 네이티브 API 품질만이 아니라
서드파티 크로스플랫폼 생태계가 얼마나 빨리 그것을 감싸는가에도 좌우된다.

React Native나 Flutter 같은 크로스플랫폼 프레임워크가 지배적인 시장에서
개발자 대다수는 네이티브 API를 직접 다루지 않는다.
따라서 이런 프레임워크의 커뮤니티가 새 네이티브 기능을
얼마나 빨리, 얼마나 매끄럽게 감싸느냐가
그 기능의 실질적 시장 침투 속도를 사실상 좌우한다.
이 역학은 벤더에게도 함의가 있다.
Apple이 신기능의 채택을 가속하고 싶다면,
공식 API의 품질뿐 아니라 서드파티 크로스플랫폼 생태계가
그것을 감쌀 수 있도록 초기 문서와 도구를 얼마나 잘 지원하느냐가
중요한 변수가 된다.

### 폴백 전략은 결국 “무엇을 진짜로 재현할 가치가 있는가”를 판단하는 디자인 작업이다

CSS 그림자와 블러로 리퀴드 글래스를 흉내 내는 결정은
단순한 기술적 타협이 아니라 실질적인 디자인 판단이다.
리퀴드 글래스의 모든 속성(동적 굴절, 색상 반응, 상호작용 애니메이션)을
전부 재현하는 것은 비현실적이므로,
라이브러리 제작자는 반드시 “이 효과의 본질이 무엇인가”를 먼저 판단해야 한다.

이 판단이 왜 중요한가.
사용자가 리퀴드 글래스를 “그 재질감” 때문에 알아보는지,
아니면 “그 반응성” 때문에 알아보는지에 따라
폴백이 성공적으로 보일지 실패해 보일지가 갈린다.
만약 재질감(반투명함, 은은한 그림자)이 핵심이라면 정적 블러로도
충분히 비슷한 인상을 줄 수 있지만,
반응성(스크롤에 따른 굴절 변화)이 핵심이라면 정적 블러는
그 효과의 본질을 놓친 것이 된다.
이런 종류의 “네이티브 흉내” 라이브러리를 평가할 때는
표면적인 기능 목록보다 “이 제작자가 원본 효과의 어떤 속성을
핵심으로 판단했는가”를 살펴보는 것이 실제 품질을 가늠하는 데
더 유용한 질문이다.

### 신기능 전용 이름이 붙은 라이브러리는 다음 플랫폼 업데이트에서 이름 자체가 부채가 될 위험을 안는다

“glass-effect-view”라는 이름은 지금은 Apple의 최신 시각 언어를
정확히 가리키지만, Apple이 몇 년 뒤 또 다른 시각 언어(예: 리퀴드 글래스의
다음 세대 디자인)를 내놓으면 이 이름은 낡은 트렌드를 가리키는 명칭이 된다.
`react-native-blur`처럼 효과의 일반적 성격(블러)을 이름에 담은 라이브러리와
`glass-effect-view`처럼 특정 시즌의 디자인 트렌드를 이름에 담은 라이브러리는
장기적인 유지보수 궤적이 다를 수 있다.

전자는 다음 세대 디자인이 나와도 “우리가 그 효과도 지원한다”고
자연스럽게 기능을 확장할 수 있지만,
후자는 이름 자체가 특정 시대의 스냅숏이 되어
다음 트렌드를 흡수하려면 이름 변경이나 새 프로젝트 시작이라는
더 무거운 결정을 마주하게 된다.
플랫폼 벤더의 최신 트렌드를 빠르게 따라잡는 전략(이 프로젝트가 보여준 강점)과
그 트렌드가 지나간 뒤에도 유지보수 가능한 이름·구조를 유지하는 전략은
서로 다른 종류의 준비를 요구하며, 이 프로젝트가 앞으로 몇 년간
이 긴장을 어떻게 다루는지가 오픈소스 라이브러리로서
지속 가능성을 가늠하는 시금석이 될 것이다.
