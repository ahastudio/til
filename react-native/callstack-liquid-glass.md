# React Native Liquid Glass

<https://github.com/callstack/liquid-glass>

## 소개

`@callstack/liquid-glass`는 iOS 26의 liquid glass 시각 효과를 React
Native 앱에서 그대로 쓸 수 있게 해 주는 라이브러리다.
Apple의 최신 디자인 언어를 네이티브 코드를 직접 작성하지 않고도
React Native 애플리케이션에 적용할 수 있도록 만든 것이 이 프로젝트의
목적이다.
설치는 `npm install @callstack/liquid-glass` 또는
`yarn add @callstack/liquid-glass`로 하며, Xcode 26 이상과
React Native 0.80 이상을 요구한다.

핵심 컴포넌트는 `LiquidGlassView`다.
`interactive`(터치 반응 여부), `effect`(`'clear'` | `'regular'` |
`'none'`), `animated`(효과 전환 애니메이션 여부), `tintColor`(색조),
`colorScheme`(`'light'` | `'dark'` | `'system'`) 같은 prop을 받는다.
여러 유리 요소를 하나로 묶어 병합 효과를 내는
`LiquidGlassContainerView`도 제공되며, `spacing` prop으로 병합
임계 거리를 조절한다.
기기의 지원 여부는 `isLiquidGlassSupported`라는 불리언 상수로 확인할
수 있다.

지원 플랫폼은 iOS 26 이상이며, 지원되지 않는 버전에서는 일반 `View`로
자동 대체된다.
Expo Go 환경에서는 지원되지 않는다.
문서에 명시된 주의사항으로는 `interactive` prop을 마운트 이후
동적으로 바꿀 수 없다는 점, 그리고 배경색에 따라 텍스트 색을 자동
조정하는 기능이 유리 요소의 높이가 65px 미만일 때만 정상 동작한다는
제약이 있다.

## 분석

### 동일한 문제를 서드파티가 먼저 풀어야 했던 이유

Apple이 iOS 26에서 liquid glass를 시스템 디자인 언어로 채택했다면,
React Native 진영이 이를 쓰려면 결국 누군가 `UIVisualEffectView` 같은
네이티브 API를 브리지로 감싸야 한다.
Callstack은 React Native 생태계에서 네이티브 모듈 컨설팅과 오픈소스
기여로 자리 잡은 회사이고, 이 저장소는 그 포지셔닝의 연장선에
있다.
공식 프레임워크(Expo)가 아니라 서드파티가 별도로 이런 라이브러리를
내놓았다는 사실 자체가, 네이티브 디자인 트렌드와 크로스플랫폼
프레임워크의 공식 지원 사이에는 항상 시차가 있고 그 공백을 커뮤니티가
메운다는 패턴을 보여준다.

### `effect`와 `interactive`를 분리한 설계

`effect`(`'clear'` | `'regular'` | `'none'`)와 `interactive`(터치
반응)를 별개의 축으로 분리해 둔 설계는, Apple이 실제 iOS 26 UI에서
유리 효과를 정적 장식과 동적 인터랙션 두 가지 용도로 쓰고 있다는 점을
반영한 것으로 보인다.
탭 바나 다이얼로그처럼 사용자 입력에 반응해 빛과 굴절이 바뀌는
요소와, 배경 장식처럼 정적인 유리 표면은 렌더링 비용과 구현 복잡도가
다르기 때문에 이를 분리해 노출하는 편이 API 설계상 합리적이다.

### `interactive`를 마운트 후 변경할 수 없다는 제약의 함의

`interactive` prop이 마운트 이후에는 바뀌지 않는다는 제약은, 이 값이
단순한 렌더링 스타일이 아니라 네이티브 뷰 초기화 시점에 결정되는
구조적 속성임을 시사한다.
`UIVisualEffectView` 계열 API는 터치 제스처 인식기를 등록하는 시점에
따라 성능이나 이벤트 처리 방식이 달라질 수 있는데, 이런 네이티브
제약을 React의 선언적 prop 모델 위에 그대로 노출하면 이번처럼
“일부 prop은 동적으로 바뀌지 않는다”는 예외가 생긴다.
이는 네이티브 뷰를 감싸는 브리지 라이브러리 전반에서 반복되는
구조적 긴장이다.

### 텍스트 색 자동 조정의 높이 제약이 알려주는 구현 한계

배경에 따라 텍스트 색을 자동으로 바꾸는 기능이 유리 높이 65px 미만일
때만 동작한다는 제약은, 이 기능이 배경 전체를 실시간으로 분석하는
것이 아니라 특정 크기 이하의 영역에서만 색상 샘플링 알고리즘이
안정적으로 동작하도록 최적화되어 있음을 보여준다.
작은 배지나 버튼 같은 UI 요소에 최적화된 기능을 큰 카드나 패널에
그대로 적용하면 실패한다는 뜻이며, 이는 라이브러리가 특정 사용
사례(작은 인터랙티브 요소)를 염두에 두고 설계되었음을 드러낸다.

## 비평

### iOS 26과 Xcode 26이라는 이중 최신 버전 요구가 채택 장벽을 만든다

이 라이브러리는 iOS 26 이상뿐 아니라 Xcode 26 이상까지 요구한다.
런타임 버전 제약은 사용자 기기 보급률의 문제이지만, 빌드 도구
버전 제약은 개발팀 전체의 개발 환경을 강제로 끌어올려야 한다는
뜻이다.
Xcode 메이저 버전 업그레이드는 종종 다른 네이티브 의존성이나 CI
파이프라인에 파급 효과를 낳는데, README는 이 도입 비용에 대해 전혀
언급하지 않는다.
결과적으로 팀 전체가 아직 이전 Xcode 버전에 머물러 있다면, 이
라이브러리 하나를 쓰기 위해 관련 없는 다른 도구 체인까지 전부
갱신해야 하는 부담을 지게 된다.

### “Expo Go 미지원”이라는 한 줄이 실제 개발 워크플로 단절을 가린다

README는 Expo Go에서 지원되지 않는다고 간단히 언급하지만, 이는 Expo
생태계에서 흔히 쓰이는 빠른 미리보기 워크플로 자체를 포기해야 한다는
뜻이다.
Expo Go로 QR코드를 스캔해 즉시 확인하던 개발자는 이제 매번 네이티브
빌드(development build)를 새로 만들어야 하고, 이는 반복 개발
주기를 몇 분에서 훨씬 길게 늘린다.
한 줄짜리 caveat 뒤에 숨어 있는 이 개발 경험 저하는 라이브러리
도입을 검토하는 팀이 미리 계산에 넣기 어려운 비용이다.

### 컴포넌트 병합(merging) 동작의 예측 가능성이 검증되지 않았다

`LiquidGlassContainerView`의 `spacing`으로 여러 유리 요소를
병합한다는 기능 설명은 있지만, 병합이 일어나는 정확한 조건이나
병합된 상태에서 개별 요소의 상호작용(터치 이벤트, 애니메이션)이
어떻게 처리되는지에 대한 설명이 README에 없다.
디자인 시스템에서 여러 유리 카드를 나란히 배치하다가 사용자가
스크롤하며 카드 간격이 좁아지는 상황을 만들면, 병합 발생 여부를
개발자가 직접 실험해서 알아내야 한다.
공개된 API 명세만으로는 이 동작이 프로덕션에서 예측 가능하게
재현되는지 검증할 방법이 없다.

### 65px 제약이 임의적인지 근본적인지 알 수 없다

텍스트 색 자동 조정이 65px 미만에서만 동작한다는 수치는 매우
구체적이지만, 이 숫자가 알고리즘의 근본적 한계인지 아니면 현재
구현의 미완성 상태를 가리는 임시 값인지 README만으로는 판단할 수
없다.
만약 이후 버전에서 이 제약이 완화된다면 기존에 이를 우회하려고 다른
방식으로 구현해 둔 코드가 오히려 중복되거나 충돌할 수 있는데, 이런
제약이 로드맵 상에서 개선될 예정인지에 대한 언급이 전혀 없다.

## 인사이트

### 서드파티 라이브러리가 공식 프레임워크보다 먼저 최신 트렌드를 흡수하는 구조

Callstack 같은 컨설팅 기반 오픈소스 조직이 Apple의 최신 디자인
언어를 React Native에 가장 먼저 이식하는 역할을 맡는다는 사실은,
크로스플랫폼 생태계의 혁신 속도가 공식 메인테이너의 릴리스 주기가
아니라 커뮤니티 컨설팅 회사의 대응 속도에 좌우된다는 점을 보여준다.
이는 장기적으로 두 가지 함의를 가진다.
하나는 이런 라이브러리가 나중에 공식 프레임워크에 흡수되거나
대체될 때 API가 바뀌는 마이그레이션 비용이 생긴다는 것이고, 다른
하나는 특정 회사의 유지보수 의지에 프로덕션 앱의 디자인 언어가
종속된다는 것이다.
과거 React Native의 여러 네비게이션이나 제스처 라이브러리가 이런
경로를 거쳤고, 결국 공식 지원으로 흡수되거나 유지보수가 끊기는 두
갈래 중 하나로 수렴해 왔다.

### 이중 최신 버전 요구가 만드는 생태계 파편화

iOS 26과 Xcode 26을 동시에 요구하는 라이브러리가 늘어나면, React
Native 앱 하나가 서로 다른 최신 요구사항을 가진 여러 서드파티
패키지를 조합해야 하는 상황에서 버전 충돌이 구조적으로 늘어난다.
지금은 liquid glass 하나의 문제처럼 보이지만, iOS가 매년 새로운
시각적 패러다임을 내놓고 그때마다 서드파티가 즉시 대응하는 패턴이
반복되면, 몇 년 뒤에는 하나의 React Native 프로젝트가 지원해야 할
최소 Xcode 버전이 여러 라이브러리의 요구사항 중 가장 높은 값으로
수렴하게 된다.
이는 오래된 기기를 지원해야 하는 앱일수록 최신 네이티브 트렌드
라이브러리를 채택하기 어려워지는 구조적 격차를 만든다.

### 65px 같은 구현 세부사항이 디자인 시스템 문서에 새어 들어오는 현상

원래대로라면 “텍스트 색이 배경에 맞춰 자동으로 바뀐다”는 것은 UI
디자인 문서에서 다룰 추상적 동작이어야 하는데, 여기서는 65px이라는
구현 디테일이 API 계약의 일부로 노출되어 있다.
이는 네이티브 브리지 라이브러리가 늘어날수록, 원래는 네이티브 계층에
숨어 있어야 할 알고리즘의 한계가 그대로 JavaScript API 사용자에게
전가되는 경향을 보여주는 사례다.
디자인 시스템 팀이 컴포넌트 크기 가이드라인을 정할 때 이런 서드파티
라이브러리의 구현 제약까지 고려해야 한다면, 추상화 계층이 오히려
디자인 결정의 자유도를 제한하는 역설적 결과를 낳는다.
