# Expo GlassEffect

<https://docs.expo.dev/versions/latest/sdk/glass-effect/>

## 소개

`expo-glass-effect`는 iOS의 네이티브 `UIVisualEffectView`를 활용해
“liquid glass” 효과를 렌더링하는 React 컴포넌트 모음이다. iOS, tvOS, Expo Go
환경을 지원하며, `expo install expo-glass-effect` 명령으로 npm, yarn, pnpm,
bun 어느 패키지 매니저에서든 설치할 수 있다. Bare React Native 프로젝트에서는
Expo 모듈이 사전에 설정되어 있어야 한다.

핵심 제약은 이 유리 효과가 iOS 26 이상에서만 동작한다는 점이다. 그보다 낮은
버전에서는 일반 `View`로 자동 대체(fallback)된다. 또 하나 주의할 점은
`GlassView`나 그 부모 뷰의 `opacity`를 0으로 설정하면 렌더링 자체가
비활성화된다는 것이다. 애니메이션을 만들 때 흔히 쓰는 opacity 트릭이 이
컴포넌트에는 통하지 않는다는 뜻이다.

## 명세

### GlassView

단일 요소에 네이티브 유리 효과를 적용하는 컴포넌트다. 주요 prop은 다음과
같다.

- `glassEffectStyle`: `'clear'`, `'regular'`, `'none'` 같은 문자열 값이나
  `animate`, `animationDuration`을 포함한 설정 객체를 받는다.
- `colorScheme`: 기본값은 `'auto'`이며 `'light'`, `'dark'`로 강제할 수 있다.
- `isInteractive`: 인터랙티브 유리 효과 여부를 지정하는 불리언 값이다.
- `tintColor`: 유리 효과에 색조를 입힌다.

### GlassContainer

여러 개의 `GlassView`를 하나의 컨테이너로 묶는 컴포넌트다. `spacing` prop으로
개별 유리 요소가 서로 얼마나 가까워지면 하나로 병합되는지를 제어한다.

### 유틸리티 함수

- `isLiquidGlassAvailable()`: 시스템 버전, 컴파일러 버전, Info.plist 설정을
  종합적으로 검사해 유리 효과 사용 가능 여부를 반환한다.
- `isGlassEffectAPIAvailable()`: 런타임에 API 사용 가능 여부를 확인한다.
  iOS 26 베타처럼 API 지원이 유동적인 환경과의 호환성을 확인할 때 특히
  중요하다.

문서는 Reanimated와 연동해 opacity 기반 우회 없이 네이티브 애니메이션을
적용하는 예제, 그리고 `GlassContainer`의 `spacing`이 여러 유리 요소의 병합
동작에 미치는 영향을 보여주는 예제를 함께 제공한다.

## 분석

### 두 개의 가용성 체크 함수가 나뉜 이유

`isLiquidGlassAvailable()`과 `isGlassEffectAPIAvailable()`이 별도로 존재하는
것은 우연이 아니다. 전자는 “이 기기와 빌드 환경이 애초에 유리 효과를 지원할
자격이 있는가”를 정적으로 판단하고, 후자는 “지금 이 런타임에서 실제로 API를
호출해도 되는가”를 동적으로 판단한다. iOS 메이저 버전이 올라가는 시점에는
베타 OS와 정식 OS 사이에서 API 시그니처나 동작이 바뀔 수 있고, Apple의 새
UI 프레임워크는 늘 그런 식으로 릴리스 사이클 중간에 조용히 변경되어 왔다.
Expo가 이 두 체크를 분리해 노출한 것은, 라이브러리 개발자가 겪을 실패
지점을 미리 예상하고 API 계약에 반영한 결과로 볼 수 있다.

### opacity 제약이 알려주는 구현 방식

`opacity: 0`이 렌더링을 완전히 끄는 현상은 단순한 버그가 아니라 구현 방식이
드러나는 단서다. `UIVisualEffectView`는 배경을 실시간으로 샘플링해 블러와
굴절을 계산하는 방식으로 동작하는데, 이 계산 자체가 상당한 GPU 비용을
수반한다. Apple이 opacity 0인 요소의 이펙트 계산을 건너뛰도록 최적화해
두었을 가능성이 높고, Expo는 이를 그대로 노출하는 대신 문서에만 명시했다.
결과적으로 개발자는 “왜 페이드 아웃이 안 되지”라는 질문에 부딪히기 전에
문서를 읽어야 하는 부담을 진다.

### iOS 전용 기능을 크로스플랫폼 프레임워크에 편입시키는 패턴

Expo SDK는 원래 “한 번 작성해서 여러 플랫폼에 배포”를 지향하는
프레임워크다. 그런데 `expo-glass-effect`는 iOS 26 이상에서만 실질적으로
동작하고 나머지 플랫폼에서는 평범한 `View`로 대체된다. 이는 Expo가 최근
몇 년간 반복해 온 전략, 즉 플랫폼별 최신 네이티브 기능을 우선 흡수하고
안드로이드나 웹에는 graceful degradation으로 대응하는 방식의 연장선이다.
크로스플랫폼 추상화의 완전성보다 “iOS에서 최신 디자인 언어를 빠르게
따라가는 것”을 우선순위에 둔 선택이라 할 수 있다.

### Info.plist 검사가 시사하는 배포 복잡도

`isLiquidGlassAvailable()`이 Info.plist 설정까지 검사 대상에 포함한다는
점은, 이 기능이 단순히 OS 버전만으로 켜고 끌 수 있는 것이 아니라 빌드
설정 차원의 사전 조건을 요구한다는 뜻이다. Apple의 새로운 UI 프레임워크가
종종 Info.plist의 특정 키나 entitlement를 요구해 온 전례를 고려하면, 이
함수는 개발자가 겪을 수 있는 “코드는 맞는데 빌드 설정이 틀려서 안 되는”
문제를 미리 걸러주는 역할을 한다.

## 비평

### “iOS 26 이상”이라는 조건이 실질 적용 시점을 가린다

문서는 iOS 26 이상에서만 유리 효과가 동작한다고 명시하지만, 실제 앱에서
이 기능을 의미 있게 사용하려면 사용자 기반의 상당수가 iOS 26 이상으로
업그레이드해야 한다. Apple 생태계의 통상적인 메이저 버전 채택 곡선을
감안하면, 신규 OS 배포 이후 1년 가까이는 fallback 뷰가 실제로 대다수
사용자에게 노출되는 경험이 된다. 문서는 이 fallback이 “일반 View”라고만
설명할 뿐, 디자인 시스템 차원에서 두 가지 시각적 경험을 어떻게 조율해야
하는지에 대한 지침을 전혀 제공하지 않는다. 결과적으로 개발자는 유리
효과가 적용된 화면과 적용되지 않은 화면을 별도로 디자인해야 하는 부담을
문서 밖에서 스스로 해결해야 한다.

### 가용성 체크 API의 사용 시점이 모호하다

`isLiquidGlassAvailable()`과 `isGlassEffectAPIAvailable()`이라는 두 함수를
제공하는 것 자체는 합리적이지만, 문서 요약만 보면 어느 시점에 어느
함수를 호출해야 하는지가 명확하지 않다. 앱 시작 시 한 번 체크해 전역
상태로 캐싱해야 하는지, 아니면 매 렌더링마다 재확인해야 하는지에 대한
권장 패턴이 빠져 있다. 두 함수의 이름이 미묘하게 비슷해 개발자가 둘 중
하나만 호출하고 넘어갈 위험도 있는데, 이는 잘못된 가용성 판단으로 이어져
런타임 크래시나 스타일이 깨진 화면을 낳을 수 있다.

### spacing 값의 의미가 수치로 설명되지 않는다

`GlassContainer`의 `spacing` prop은 “요소들이 얼마나 가까워지면 병합되는가”를
결정하는 핵심 값인데, 요약된 문서에는 이 값이 어떤 단위인지, 기본값이
무엇인지, 병합이 일어나는 임계 거리를 계산하는 공식이 있는지에 대한 정보가
없다. 디자인 시스템에서 여러 유리 요소를 배치할 때 병합 여부는 순전히
시각적 실험으로 알아내야 하는 값이 되어버리는데, 이는 선언적 API가
지향해야 할 예측 가능성과 배치된다.

### Reanimated 연동이 “네이티브 애니메이션”의 범위를 흐릿하게 만든다

문서는 opacity 기반 우회 없이 네이티브 애니메이션을 쓸 수 있다고
강조하면서 동시에 Reanimated 연동 예제를 제공한다. 그런데 애니메이션이
`glassEffectStyle`의 `animate` 설정을 통한 네이티브 트랜지션인지,
아니면 Reanimated가 별도 레이어에서 구동하는 애니메이션인지 경계가
분명치 않다. 두 방식이 섞여 있는 애니메이션 파이프라인에서는 프레임
동기화 문제나 우선순위 충돌이 발생하기 쉬운데, 문서 요약 수준에서는 이
지점에 대한 언급이 전혀 없다.

## 인사이트

### 유리 효과는 디자인 시스템의 버전 분기를 강제한다

`expo-glass-effect`를 도입한다는 것은 단순히 새 컴포넌트를 하나 추가하는
일이 아니라, 사실상 iOS 26 이상과 그 이하를 위한 두 개의 디자인 시스템을
유지하겠다는 결정이다. Apple이 과거 다크 모드나 Dynamic Island를 도입할
때도 비슷한 패턴이 있었지만, 이번에는 “표면 재질 자체”가 바뀌는 것이라
시각적 격차가 훨씬 크다. 앱이 두 갈래 경험을 몇 년에 걸쳐 유지보수해야
하는 비용은 초기 도입 결정 단계에서 거의 논의되지 않는 부분이며, 이는
프레임워크 업데이트 공지가 “새 기능이 추가되었다”는 프레임으로만
소비되는 것과 대비된다.

### GPU 비용 문제가 나중에 성능 이슈로 되돌아올 가능성

블러와 굴절 계산을 실시간으로 수행하는 `UIVisualEffectView` 기반 컴포넌트를
리스트나 스크롤 뷰 안에 여러 개 배치하면, 초기 프로토타입에서는 드러나지
않던 프레임 드랍 문제가 실제 사용자 기기, 특히 구형 기기에서 나타날
가능성이 높다. Apple 자체 UI에서도 유리 효과가 적용된 요소는 화면 전체가
아니라 국소적인 영역에 한정해 사용되는 경향이 있는데, 이는 서드파티
개발자들이 이 컴포넌트를 화면 전반에 남용했을 때 겪을 성능 저하를 Apple이
이미 알고 있었다는 방증이기도 하다. `expo-glass-effect` 문서는 이 성능
경계에 대한 가이드를 전혀 제공하지 않으므로, 실제 채택 이후 몇 달 안에
“유리 효과를 어디까지 써도 되는가”를 둘러싼 커뮤니티 차원의 경험칙이
따로 형성될 가능성이 크다.

### 크로스플랫폼 프레임워크가 플랫폼별 최신 기능을 흡수하는 방식의 전례

React Native 진영에서 특정 플랫폼의 최신 네이티브 기능을 먼저 흡수하고
나머지 플랫폼에는 fallback으로 대응하는 패턴은 이번이 처음이 아니다.
Dynamic Island 대응 컴포넌트나 iOS 위젯 지원이 유사한 경로를 거쳤다.
이 패턴이 반복된다는 것은, 크로스플랫폼 프레임워크의 실제 경쟁력이
“완전한 추상화”가 아니라 “각 플랫폼의 최신 트렌드를 얼마나 빨리 따라
잡느냐”로 재정의되고 있다는 신호로 읽을 수 있다. 이는 장기적으로
안드로이드나 웹에서의 개발 경험이 iOS에 비해 구조적으로 뒤처지는 결과로
이어질 수 있으며, Expo 생태계 안에서 플랫폼 간 기능 격차가 문서화된
형태로 누적되어 간다는 뜻이기도 하다.
