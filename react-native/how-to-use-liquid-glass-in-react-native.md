# How to Use Liquid Glass in React Native

원문: [How To Use Liquid Glass in React Native](https://www.callstack.com/blog/how-to-use-liquid-glass-in-react-native)

## 요약

Callstack의 Mike Grabowski와 Oskar Kwaśniewski가 작성한 이 글은
`@callstack/liquid-glass` 라이브러리의 사용법과 모범 사례를 소개한다.
Liquid Glass는 Apple이 iOS 26부터 도입한 새로운 디자인 재질로, UI
요소에 주변을 실시간으로 반사·굴절하는 반투명한 유리 외관을 부여한다.
위젯이나 탭 바 같은 요소에 주로 쓰이며, 목적은 밑에 있는 콘텐츠를
가리지 않으면서도 전경과 배경의 구분을 유지하는 것이다.
글은 이를 iOS 7에서 처음 등장한 블러 효과의 발전된 형태로 설명한다.

글은 먼저 Apple의 Human Interface Guidelines를 인용하며 사용상 모범
사례를 강조한다.
Apple은 커스텀 컨트롤에 Liquid Glass를 과도하게 적용하지 말라고
경고하는데, 이는 이 재질이 원래 콘텐츠에 주의를 끌기 위한 것이므로
여러 컨트롤에 남용하면 오히려 사용자 경험을 해칠 수 있기 때문이다.
저자들은 헤더, 내비게이션 바, 카드, 액션 버튼처럼 핵심적인 UI
요소에만 이 효과를 한정해서 쓰라고 권장하며, 전체 화면을 투명하게
만들지 말 것, `colorScheme`과 `tintColor`로 가독성과 대비를
확보할 것, GPU 가속 블러의 성능 비용을 고려해 요소를 과도하게 쌓거나
애니메이션시키지 말 것, 그리고 iOS 26 미만이나 Android에서는 자동으로
불투명한 `View`로 대체되므로 그 상태에서도 디자인이 무리 없이 보이게
반투명 배경색을 대체 값으로 지정할 것을 제안한다.

API 설명 부분에서는 두 가지 핵심 컴포넌트를 다룬다.
`LiquidGlassView`는 개별 요소를 감싸는 “유리 패널” 컴포넌트로,
`interactive`(기본값 `false`, 터치 시 미세한 인터랙션 효과),
`effect`(`'clear'` | `'regular'`, 기본값 `'regular'`),
`tintColor`, `colorScheme`(기본값 `'system'`) 같은 prop을 제공한다.
`isLiquidGlassSupported`를 가져와 기기가 iOS 26 이상인지 확인하고
대체 스타일을 적용할 수 있다.
`LiquidGlassContainerView`는 여러 개의 `LiquidGlassView`를 감싸는
부모 컴포넌트로, 두 유리 요소가 가까워지면 하나로 병합되는 효과를
구현한다.
예시 코드에서는 `spacing={20}`으로 두 원형 요소가 20포인트 이내로
가까워지면 서로 병합되는 모습을 보여준다.

글은 이 라이브러리가 순정 React Native와 Expo 양쪽에서 동작하며
지원되지 않는 플랫폼에서는 우아하게 대체된다는 점을 강조하고,
오픈소스로 공개된 GitHub 저장소를 확인해 볼 것을 권하며 마무리된다.

## 분석

### 모범 사례를 API 설명보다 앞세운 구성의 의도

이 글은 API 레퍼런스보다 먼저 “모범 사례” 섹션을 배치한다.
이는 단순한 구성상의 선택이 아니라, Liquid Glass가 기술적으로는
간단히 적용할 수 있지만 오남용의 위험이 큰 기능이라는 저자들의
판단을 반영한다.
Apple의 HIG를 직접 인용하는 방식은 이 라이브러리 제작자들이 단순히
API를 이식하는 데서 그치지 않고, Apple이 의도한 디자인 철학까지
함께 전달하려 한다는 것을 보여준다.
컨설팅 회사가 작성한 기술 블로그가 이런 구성을 택했다는 것은,
독자가 이 라이브러리를 도입할 때 API 오용보다 디자인 오용으로 인한
실패를 더 우려했다는 뜻이기도 하다.

### “Graceful fallback”이 라이브러리 설계 철학의 핵심으로 명시된다

글은 iOS 26 미만이나 Android에서 자동으로 일반 `View`로 대체된다는
점을 단순한 제약 사항이 아니라 모범 사례 항목 중 하나로 서술한다.
개발자에게 “대체 상태에서도 디자인이 무리 없이 보이도록 반투명
배경색을 지정하라”고 구체적으로 권고하는 것은, 이 라이브러리가
플랫폼 분기 처리를 개발자의 몫으로 남겨두면서도 그 처리가 최소한의
품질을 갖추도록 유도하는 설계 철학을 보여준다.
이는 서드파티 라이브러리가 네이티브 최신 기능을 이식할 때 흔히
겪는 “지원 플랫폼과 미지원 플랫폼 사이의 시각적 격차”라는 문제를
문서 차원에서 정면으로 다루는 드문 사례다.

### 성능 경고가 구체적 수치 없이 원칙 수준에 머무른다

글은 “GPU 가속 실시간 블러이므로 소수의 요소에는 효율적이지만,
많은 수의 반투명 뷰를 쌓거나 과도하게 애니메이션시키는 것은
피하라”고 조언한다.
이는 앞서 살펴본 `expo-glass-effect` 문서에서도 드러났던 동일한
근본 제약, 즉 `UIVisualEffectView` 계열 API의 실시간 렌더링 비용
문제를 그대로 반영한 것이다.
다만 이 글은 “몇 개까지가 소수인지”, “어느 정도의 애니메이션이
과도한지”에 대한 구체적 기준을 제시하지 않고 원칙적 경고에 머무는데,
이는 실제 성능 임계값이 기기 세대와 화면 복잡도에 따라 달라 일반화된
수치를 제시하기 어렵다는 현실적 한계를 반영한 것으로 보인다.

## 비평

### 모범 사례 권고가 강제할 수 없는 개발자 재량에 전적으로 의존한다

글은 “커스텀 컨트롤에는 아껴서 사용하라”, “전체 화면을 투명하게
만들지 말라”고 권고하지만, 이 라이브러리의 API 자체는 개발자가
`LiquidGlassView`를 화면 전체에 몇 개든 배치하는 것을 막을 어떤
장치도 제공하지 않는다.
Apple의 HIG를 인용해 원칙을 전달하는 것과, 실제로 그 원칙을 어기기
어렵게 만드는 API 설계는 전혀 다른 수준의 보장이다.
결과적으로 이 글이 제시하는 모범 사례는 순전히 문서를 읽은 개발자의
자율적 준수에 의존하며, 프로젝트에 새로 합류한 개발자나 빠르게
기능을 추가해야 하는 상황에서는 이 권고가 쉽게 무시될 수 있는
구조다.

### `effect`의 두 옵션만으로 실제 Apple UI의 다양성을 다 담지 못한다

라이브러리는 `effect`로 `'clear'`와 `'regular'` 두 가지만
제공하지만, 실제 iOS 26의 Liquid Glass는 문맥에 따라 훨씬 다양한
강도와 색조의 변형을 보여준다.
글은 이 두 옵션이 Apple의 네이티브 디자인 언어를 충분히 대표한다고
암묵적으로 전제하지만, 두 값으로 단순화된 API가 Apple이 실제
시스템 UI에서 구현한 미묘한 변주(다이얼로그, 탭 바, 위젯마다 다른
블러 강도와 반사율)를 얼마나 정확히 재현하는지에 대한 검증이나
비교는 전혀 제시되지 않는다.
이는 “네이티브와 동일하게 동작한다”는 암묵적 주장을 뒷받침할 근거가
부족하다는 뜻이다.

### 병합(merging) 효과의 조건이 원 모양 예시로만 시연되어 일반화 근거가 약하다

`LiquidGlassContainerView`의 병합 예시는 두 개의 동일한 크기의
원형 요소로만 시연된다.
그러나 실제 UI에서는 서로 다른 크기와 모양(둥근 사각형, 비정형
카드)을 가진 요소들이 섞여 있는 경우가 훨씬 흔한데, 글은 이런
비대칭적인 상황에서도 병합이 매끄럽게 일어나는지에 대해 전혀 다루지
않는다.
`spacing` 값이 20이라는 단일 예시만 제공되고, 이 값이 요소 크기에
비례해서 조정되어야 하는지, 아니면 절대적인 포인트 단위로 고정된
개념인지에 대한 설명도 없어, 독자는 이 API를 실제 프로덕션 레이아웃에
적용하기 전에 스스로 여러 조합을 실험해야 한다.

## 인사이트

### 컨설팅 회사가 작성한 기술 블로그는 라이브러리 채택을 유도하는 마케팅과 기술 문서의 이중 기능을 수행한다

이 글의 마지막 부분은 라이브러리 사용법 설명에서 자연스럽게
Callstack의 iOS 개발 컨설팅 서비스 홍보로 이어진다.
이는 우연이 아니라, 오픈소스 라이브러리를 무료로 배포하면서 그
사용법을 설명하는 기술 블로그를 통해 잠재 고객을 컨설팅
서비스로 유도하는 전형적인 개발자 마케팅 전략이다.
이 구조에서 “모범 사례”로 제시된 내용이 실제로 얼마나 엄밀하게
검증된 권고인지, 아니면 라이브러리를 신뢰할 만하게 보이도록
포장하는 수사인지 구분하기 어려워진다.
독자는 기술 문서를 읽는 동시에 컨설팅 회사의 역량을 홍보하는 콘텐츠를
읽고 있다는 점을 인식하고, 성능이나 안정성에 대한 주장은 별도의
독립적인 검증을 거쳐야 한다.

### “과도한 사용을 피하라”는 경고가 실제로는 채택 이후에나 발견되는 문제를 예방하지 못한다

Apple의 HIG를 인용한 절제 권고는 라이브러리를 처음 도입하는
시점의 개발자에게는 설득력 있게 들리지만, 실제 남용은 대개
프로젝트 초기가 아니라 여러 개발자가 참여하고 디자인 요구사항이
누적되는 후반부에 발생한다.
새로운 기능 요청마다 “이 카드에도 유리 효과를 넣어달라”는 디자이너의
요청이 하나씩 쌓이다 보면, 어느 순간 화면 전체가 반투명 요소로
뒤덮이는 상태에 도달하게 되는데, 이 과정은 각각의 개별 결정
시점에서는 합리적으로 보인다.
이런 점진적 남용은 문서에 담긴 원칙적 경고로는 막을 수 없고, 오히려
디자인 시스템 차원에서 유리 효과를 적용할 수 있는 컴포넌트 목록을
사전에 제한하는 거버넌스가 필요하다는 결론으로 이어진다.
이는 글이 명시적으로 다루지 않는, 조직적 차원의 대응 방안이다.

### GPU 성능 경고가 반복되는 것은 이 세대 모바일 디자인 트렌드의 공통된 취약점을 드러낸다

동일한 GPU 가속 블러 비용에 대한 경고가 Expo의 `expo-glass-effect`
문서와 이 글 모두에서 반복된다는 사실은, Liquid Glass라는 디자인
트렌드 자체가 태생적으로 성능과 심미성 사이의 긴장을 안고 있다는
것을 보여준다.
과거 뉴모피즘이 그림자 연산 비용 때문에 리스트 뷰에서 프레임 드랍을
일으켰던 것처럼, 실시간 배경 샘플링에 의존하는 모든 디자인
트렌드는 결국 “이 효과를 화면에 몇 개까지 배치할 수 있는가”라는
동일한 질문에 부딪힌다.
이 반복되는 경고는 개별 라이브러리의 결함이 아니라, Apple이
디자인 언어를 실시간 GPU 렌더링에 의존하는 방향으로 설계할 때마다
서드파티 생태계 전체가 같은 성능 제약을 상속받는다는 구조적
패턴을 시사한다.
결과적으로 다음 세대의 디자인 트렌드가 등장할 때도 이와 유사한
성능 경고 문서가 반복해서 작성될 가능성이 높다.
