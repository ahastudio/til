# Cloudflare Containers 공개 베타: Kubernetes 오퍼레이터 대신 JavaScript로 컨테이너를 제어한다

원문: [Containers are available in public beta for simple, global, and programmable compute](https://blog.cloudflare.com/containers-are-available-in-public-beta-for-simple-global-and-programmable/)

HN 토론: <https://news.ycombinator.com/item?id=44367693> (80점, 21개 댓글)

## 요약

Gabi Villalonga Simón, Ivan Chernetsky, Josh Seba, Nafeez Nazer, Thomas Lefebvre가 2025년 6월 24일에 쓴 발표문이다.
Cloudflare Containers가 **유료 플랜 사용자 전원에게** 베타로 열렸다는 내용이다.

Workers 옆에서 새로운 종류의 애플리케이션을 돌릴 수 있게 되었다고 적는다.
엣지에서의 미디어·데이터 처리, 어떤 언어로든 만든 백엔드 서비스, 배치 워크로드의 CLI 도구가 예로 제시된다.

네 가지를 내세운다.

**워크플로가 단순하다**: 몇 줄로 Container를 정의하고 `wrangler deploy`를 실행하면 된다. Worker와 똑같다.

**전역이다**: Workers처럼 Region:Earth에 배포한다. 전역 앱을 위해 5개 리전에 설정을 관리할 필요가 없다.

**적재적소에 쓸 수 있다**: Workers와 Containers 사이의 요청 라우팅이 쉽다. 초경량이고 확장 가능해야 하면 Worker를, 더 많은 성능과 유연성이 필요하면 Container를 쓴다.

**프로그래밍 가능하다**: 컨테이너 인스턴스가 필요할 때 생성되고 Workers 코드가 제어한다.
커스텀 로직이 필요하면 API 호출을 엮거나 **Kubernetes 오퍼레이터를 작성하는 대신 JavaScript를 조금 쓰면 된다**는 것이다.

### 사용 방식

발표문이 코드 샌드박싱을 예시로 든다.
사용자가 만들었거나 AI가 만든 코드를 플랫폼의 일부로 실행하려 하고, 각 사용자에게 격리된 컨테이너가 필요하며, 사용자가 전 세계에 분산되어 있고, 기다리지 않도록 빠르게 시작해야 하는 상황이다.

Worker에서 `Container` 클래스와 `wrangler.jsonc`로 설정한다.

```javascript
export class MyContainer extends Container {
  defaultPort = 8080;   // 컨테이너가 listen할 기본 포트
  sleepAfter = '5m';    // 이 시간 동안 요청이 없으면 컨테이너를 잠재운다
}

export default {
  async fetch(request, env) {
    const pathname = new URL(request.url).pathname;

    // 온디맨드 컨테이너 인스턴스로 요청을 처리한다
    if (pathname.startsWith('/sandbox/')) {
      const sessionId = pathname.split("/")[2]
      const containerInstance = getContainer(env.CONTAINER_SANDBOX, sessionId)
      return await containerInstance.fetch(request);
    }

    // 그 외에는 Worker 코드로 처리한다
    return myWorkerRequestHandler(request);
  },
};
```

바인딩에 전달되는 **고유 ID마다 새 컨테이너 인스턴스**가 생성되고 요청이 그리로 라우팅된다.
새 인스턴스가 요청되면 Cloudflare가 전역 네트워크에서 미리 프로비저닝해 둔 준비된 컨테이너 중 가장 좋은 위치를 고른다.
그래서 사용자가 어디 있든 가까운 곳에 컨테이너를 배포할 수 있고, 초기 시작이 **몇 초**밖에 걸리지 않는다는 것이다.

이미지 설정은 URL이나 로컬 Dockerfile 경로로 한다.

```json
"containers": [
  {
    "class_name": "ContainerSandbox",
    "image": "./Dockerfile",
    "max_instances": 80,
    "instance_type": "basic"
  }
]
```

`wrangler dev`를 실행하면 컨테이너 이미지가 자동으로 빌드되어 로컬 Worker를 통해 라우팅된다.
이미지를 다시 빌드하려면 터미널에서 **`R` 키**를 누르면 컨테이너가 재빌드되고 재시작된다.

배포는 `wrangler deploy` 하나다. wrangler가 이미지를 계정에 푸시하고 전역 네트워크 여러 위치에 프로비저닝한다.
“아티팩트 관리”나 배포나 인증을 걱정할 필요가 없고 컨테이너를 Workers와 통합하려고 애쓸 필요가 없다고 적는다.

관측성은 내장이다. 대시보드에서 인스턴스별 상태와 자원 사용량을 지표로 추적하고, 로그는 Cloudflare UI에 **7일간 보관**되거나 외부 싱크로 푸시된다.

### 인스턴스와 가격

선택 가능한 인스턴스가 셋이며, 더 큰 것을 추가할 계획이라고 적는다.

| 이름     | 메모리  | CPU       | 디스크 |
| -------- | ------- | --------- | ------ |
| dev      | 256 MiB | 1/16 vCPU | 2 GB   |
| basic    | 1 GiB   | 1/4 vCPU  | 4 GB   |
| standard | 4 GiB   | 1/2 vCPU  | 4 GB   |

과금은 쓴 만큼만이다.
컨테이너에 요청이 전송되거나 수동으로 시작될 때 과금이 시작되고, 인스턴스가 잠들면 멈춘다.
잠드는 것은 타임아웃으로 자동으로 일어날 수 있으므로 **0으로 축소하기가 쉽고** 버스트 트래픽에서도 높은 활용률을 얻는다는 것이다.

실제로 실행 중인 **10ms마다** 과금되며, Workers Standard에 월간 포함량이 있다.

| 항목   | 단가                | 포함량      |
| ------ | ------------------- | ----------- |
| 메모리 | GiB-초당 $0.0000025 | 25 GiB-시간 |
| CPU    | vCPU-초당 $0.000020 | 375 vCPU-분 |
| 디스크 | GB-초당 $0.00000007 | 200 GB-시간 |

이그레스는 지역별로 다르다.

| 지역                    | 단가        | 포함량 |
| ----------------------- | ----------- | ------ |
| 북미와 유럽             | GB당 $0.025 | 1 TB   |
| 호주·뉴질랜드·대만·한국 | GB당 $0.050 | 500 GB |
| 그 외 전 지역           | GB당 $0.040 | 500 GB |

### 다음에 올 것

발표문이 로드맵 네 가지를 미리 공개한다.

**더 높은 한도와 더 큰 인스턴스**: 현재 동시 인스턴스를 총 **40 GiB 메모리와 총 40 vCPU**로 제한한다.
일부 워크로드에는 충분하지만 많은 사용자가 훨씬 더 높기를 원할 것이며, 선별된 고객들은 이미 수천 개의 동시 컨테이너로 확장하고 있다고 적는다.

**전역 오토스케일링과 지연 인식 라우팅**: 현재는 ID로 주소를 지정해 온디맨드로 시작한다.
많은 사용에서는 전역에 배포된 다수의 무상태 컨테이너 중 하나로 라우팅하고 살아 있는 인스턴스를 자동 확장하길 원한다는 것이다.

```javascript
class MyBackend extends Container {
  defaultPort = 8080;
  autoscale = true;  // 메모리나 CPU 사용률이 높으면 새 인스턴스가 생성된다
}

// 가장 가까운 준비된 컨테이너로 라우팅하고 전역으로 부하를 분산한다
async fetch(request, env) {
  return getContainer(env.MY_BACKEND).fetch(request);
}
```

**Containers와 Workers 사이의 더 많은 통신 수단**: 인스턴스에서 셸 명령을 실행하는 `exec`와 컨테이너에서 Workers로 오는 HTTP 요청 핸들러를 추가한다.

```javascript
class MyContainer extends Container {
  // 컨테이너에서 Worker로 오는 요청을 호스트명별로 받는다
  handlers = {
    "example.cf": "handleRequestFromContainer"
  };

  handleRequestFromContainer(req) {
    return new Response("You are responding from Workers to a Container request to a specific hostname")
  }

  // exec으로 컨테이너 안에서 명령을 실행한다
  async cloneRepo(repoUrl) {
    let command = this.exec(`git clone ${repoUrl}`)
    await command.print()
  }
}
```

**개발자 플랫폼과의 추가 통합**: R2 버킷 마운트, Hyperdrive 접근, KV 접근을 아주 간단하게 만들겠다는 것이다.

### 제시된 활용 사례

Workers에서 돌릴 수 없던 라이브러리를 이제 돌릴 수 있다며 FFmpeg으로 비디오를 GIF로 변환하는 Worker를 예로 든다.
크론 작업의 일부로 컨테이너를 돌리거나, 정적 프런트엔드와 컨테이너화된 백엔드를 배포하거나, **Cloudflare Agent가 Container에서 Claude Code를 대신 실행**하게 할 수도 있다고 적는다.

상태 관리에 Durable Objects를, 복잡한 동작 구성에 Workflows·Queues·Agents를, 컨테이너 데이터와 미디어 저장에 R2를 쓰라고 덧붙인다.

## 분석

### 진짜 제품은 컨테이너가 아니라 Workers의 탈출구다

발표문에서 이 제품의 존재 이유를 가장 정확히 말하는 문장이 활용 사례 절에 있다.

수년간 많은 사용자가 **“컨테이너에서 돌려야 하는 이 한 조각만 배포할 수 있다면 전체 애플리케이션을 Cloudflare에서 돌리고 싶다”**고 말해 왔다는 것이다.

이 문장이 제품의 성격을 규정한다.
Cloudflare가 컨테이너 호스팅 시장에 진입하는 것이 아니라, **Workers 런타임의 제약 때문에 이탈하던 워크로드를 붙잡는 것**이다.

그래서 제시되는 예가 전부 “Workers에서는 안 되던 것”이다.
FFmpeg은 네이티브 바이너리라 V8 아이솔레이트에서 돌지 않고, CLI 도구도 마찬가지이며, 임의 언어의 백엔드도 그렇다.

이 관점에서 보면 발표문이 컨테이너 플랫폼으로서의 경쟁력을 거의 논하지 않는 이유가 설명된다.
Fly.io도 Modal도 Railway도 언급되지 않고, 비교 대상이 오직 **Workers 자신**이다.

그리고 이것이 설계에도 반영되어 있다.
모든 트래픽이 Workers를 통해 프록시되며, 컨테이너는 Worker 코드가 `getContainer()`로 호출하는 대상이다.
독립적으로 주소를 갖는 서비스가 아니라 **Worker의 확장 자원**이다.

HN에서 NathanFlurry가 그 제약의 구체적 결과를 짚었다.[^NathanFlurry-udp]
라이브스트림에서 TCP를 고려 중이라고 했지만 Workers 자체가 UDP를 지원하지 않으므로 UDP는 곧 오지 않을 것 같으며, Cloudflare Containers로 가는 모든 트래픽이 Workers 플랫폼을 통해 프록시되어야 하기 때문이라는 것이다.

Zerpiez가 물었던 것이 dnsdist 같은 서비스를 돌릴 수 있느냐였는데,[^Zerpiez] 답은 구조적으로 아니다.

### 프로그래밍 가능성이 실제 차별점인데 논의에서 밀렸다

네 가지 주장 중 셋은 다른 플랫폼도 어느 정도 한다.
단순한 배포도, 전역 배치도, 경량 런타임과 컨테이너의 조합도 새롭지 않다.

새로운 것은 네 번째다. **컨테이너 생명주기를 JavaScript로 제어하는 것**이다.

발표문의 표현이 정확하다. 커스텀 로직이 필요하면 API 호출을 엮거나 Kubernetes 오퍼레이터를 작성하는 대신 JavaScript를 조금 쓰면 된다는 것이다.

이것이 실제로 다른 층위의 주장이다.
보통 컨테이너 오케스트레이션의 제어 평면은 선언적 설정(YAML)과 컨트롤러로 이루어지는데, 여기서는 **요청을 처리하는 코드가 곧 제어 평면**이다.

코드 샌드박싱 예제가 그 힘을 보여 준다.
세션 ID를 URL에서 꺼내 `getContainer(env.CONTAINER_SANDBOX, sessionId)`로 넘기면 그 ID마다 인스턴스가 생긴다.
“사용자마다 격리된 컨테이너”라는 요구가 코드 두 줄이 된다.

Kubernetes로 같은 것을 하려면 사용자별 Pod을 만드는 오퍼레이터를 쓰거나 API 서버를 호출하는 서비스를 별도로 두어야 한다.
그리고 그 서비스가 인증과 정리와 가비지 컬렉션을 스스로 처리해야 한다. 여기서는 `sleepAfter`가 그 일을 한다.

로드맵의 `exec`와 컨테이너→Worker 핸들러가 이 방향을 더 밀고 나간다.
`this.exec('git clone ...')`을 Worker 클래스의 메서드로 쓴다는 것은 컨테이너를 **객체처럼 다루겠다**는 선언이다.

그런데 HN 스레드는 이 부분을 거의 다루지 않았다.
21개 댓글 중 절반 이상이 가격 이야기이고, 프로그래밍 모델에 대한 논의는 없다.

이것이 발표 자체의 구성 탓이기도 하다.
프로그래밍 가능성이 네 가지 주장 중 마지막에 한 문단으로 놓이고, 가격표는 별도 절로 표와 함께 제시된다.

### 온디맨드와 잠자기가 가격 논쟁의 실제 쟁점이다

HN에서 가장 먼저 그리고 가장 많이 나온 반응이 가격이었다.

develatio가 계산을 내놓았다.[^develatio]
계산이 틀리지 않았다면 `standard` 컨테이너 하나를 한 달 내내 쉬지 않고 돌리면 약 $55가 되며, 단순한 데모나 장난감 프로젝트가 아닌 무엇에든 극히 비싸 보인다는 것이다.
무거운 서비스에 다른 무엇 대신 이것을 쓸 이유를 생각할 수 없으며 자기가 사용 사례를 못 보는 것이냐고 물었다.

rochoa의 답이 이 논쟁의 핵심을 짚었다.[^rochoa]
`standard` 인스턴스에 대해 계산은 틀리지 않았으며, 이것은 **온디맨드 부분을 쓰고 남용하는 것에 관한 이야기**라는 것이다.
그리고 시작 가이드의 첫 예제가 `sleepAfter = '10s'`로 되어 있다는 점을 지적했다.

이 교환이 제품 설계와 가격표의 관계를 드러낸다.

이 가격 구조는 **상시 가동 워크로드를 위해 만들어지지 않았다**.
10ms 단위 과금, 자동 잠자기, ID별 인스턴스 생성이 전부 짧게 켜졌다 꺼지는 사용을 전제한다.

발표문도 그렇게 적는다. 0으로 축소하기 쉽고 버스트 트래픽에서도 높은 활용률을 얻는다는 것이다.

그래서 develatio의 계산과 rochoa의 반박이 서로 틀리지 않았다.
상시 가동으로 쓰면 비싸다는 것이 맞고, 그렇게 쓰라고 만든 것이 아니라는 것도 맞다.

문제는 발표문이 그 경계를 명시하지 않는다는 점이다.
“어떤 언어로든 만든 백엔드 서비스”를 첫 문단의 사용 사례로 들면서, 그런 백엔드가 대체로 상시 가동이라는 사실을 다루지 않는다.

## 비평

### 경쟁 제품과의 비교가 발표문에 전혀 없고 댓글에서 대신 이루어졌다

발표문은 자기 플랫폼 안에서만 이야기한다. Worker와 Container를 언제 쓰는지는 설명하지만, 다른 컨테이너 서비스와 어떻게 다른지는 한 줄도 없다.

그 비교를 HN에서 경쟁사 직원이 했다.

NathanFlurry가 Cloudflare Containers와 Fly Machines와 Rivet Containers를 비교한 글을 발행했다고 알리며 자기가 Rivet에서 일한다고 밝혔다.[^NathanFlurry-compare]
그리고 구체적 수치를 댓글로 제시했다.[^NathanFlurry-price]

1 CPU와 2 GB 램과 50 GB 임시 저장소 기준으로 Cloudflare Containers가 **$74.90**이고, Fly Machines에서 같은 구성이 지역에 따라 다르지만 `performance-1x`로 **$31.00**이며 Fly Machines에도 Cloudflare와 같은 잠자기 기능이 있다는 것이다.
Rivet Containers는 **$29.40**으로 비슷한 가격대이지만 잠자기에 다른 접근을 취해 스냅샷 대신 콜드스타트 최적화와 오토스케일링을 택했다고 덧붙였다.

blixt가 Modal도 Cloudflare Containers와 비슷한 기능 집합을 가졌다고 알고 있는데 가격 면에서 상당히 유리하게 나온다고 보탰다.[^blixt]

이 상황에 두 가지를 구분해야 한다.

먼저 이해관계다. 두 숫자 모두 경쟁사 직원이 제시한 것이고, 비교 조건(50 GB 임시 저장소, 지역, 잠자기 동작의 차이)이 각 플랫폼에서 동일하게 성립하는지 검증되지 않았다.
NathanFlurry가 소속을 두 번 다 밝힌 것은 정직한 처신이지만, 그 정직함이 수치의 정확성을 보증하지는 않는다.

그럼에도 남는 문제가 있다. **발표문이 그 비교를 전혀 제공하지 않았기 때문에 경쟁사의 수치가 유일한 비교 자료가 되었다**는 점이다.

Cloudflare가 자사 제품의 가격 우위를 강조하는 회사라는 점에서 이 침묵이 눈에 띈다.
R2의 이그레스 0 정책은 AWS S3와의 직접 비교를 전면에 내세워 만들어진 서사였다.

여기서는 그 비교가 없고, 대신 “투명한 가격”이라는 표현만 있다.
가격표를 공개하는 것과 그 가격이 경쟁력 있음을 보이는 것은 다른 일이다.

### 이그레스 과금이 Cloudflare 자신의 서사와 충돌한다

dinvlad가 짧게 적었다. 이그레스가 다른 제품들과 달리 TB당 $25이며 됐다는 것이다.[^dinvlad]

이 반응이 짧지만 무게가 있다.

Cloudflare의 개발자 플랫폼 서사에서 가장 강력한 한 줄이 **이그레스 요금 0**이었다.
R2가 그것으로 만들어졌고, 이 발표문 안에서도 Pages 계열 서사가 그 위에 서 있다.

그런데 Containers에는 지역별 이그레스 요금이 붙는다. 북미·유럽 GB당 $0.025, 호주·뉴질랜드·대만·한국 GB당 $0.050, 그 외 GB당 $0.040이다.

한국이 가장 비싼 구간에 속한다는 점은 국내 사용자에게 실질적이다.
북미의 두 배이고, 포함량도 1 TB가 아니라 500 GB다.

발표문은 이 차이를 설명하지 않는다.
이그레스 표를 제시할 뿐, 왜 다른 제품과 다른지 혹은 앞으로 어떻게 될 것인지에 대한 언급이 없다.

Havoc이 실무적 우려를 제기했다. bunny가 제공하는 것과 비슷해 보이며, Cloudflare가 레이트 리밋을 걸게 해 주지 않느냐고 물으면서 그 이그레스 요율이면 어떤 형태로든 그것이 필요해 보인다는 것이다.[^Havoc]

이 지적이 정확하다.
컨테이너가 프로그래밍 가능하다는 것은 코드 실수 하나로 대량 트래픽을 만들 수 있다는 뜻이고, 이그레스에 요금이 붙으면 그것이 곧 청구서가 된다.

발표문에 지출 상한이나 경보에 대한 언급이 없다.

### 40 GiB·40 vCPU 상한이 로드맵 절에 묻혀 있다

이 발표에서 가장 중요한 제약이 “다음에 올 것” 절 안에 놓여 있다.

현재 동시 인스턴스를 총 40 GiB 메모리와 총 40 vCPU로 제한한다는 것이다.

이 숫자를 인스턴스 표와 대조하면 규모가 보인다.
`standard`가 4 GiB에 1/2 vCPU이므로 메모리 기준으로 동시 10개, vCPU 기준으로는 80개다. 메모리가 먼저 걸린다.
`basic`이면 메모리 기준 40개다.

그리고 설정 예제의 `max_instances`가 80으로 되어 있다.
`basic` 인스턴스 80개는 80 GiB이므로 계정 상한의 두 배다. 예제 설정이 상한을 넘는 값을 보여 주고 있는 셈이다.

이 제약이 문제인 이유는 발표문이 내세운 대표 사용 사례와 정면으로 부딪히기 때문이다.

코드 샌드박싱은 **사용자마다 인스턴스를 만드는** 패턴이다.
동시 사용자가 수십 명을 넘는 순간 상한에 닿는다.

발표문 자신이 그 부족함을 인정한다.
일부 워크로드에는 충분하지만 많은 사용자가 훨씬 더 높기를 원할 것이라는 문장이다.

그런데 그 인정이 로드맵 절에 있고, 제품 소개와 가격표를 지난 뒤에 나온다.
읽는 순서상 독자가 “내 사용 사례에 맞는가”를 판단하는 시점보다 뒤다.

선별된 고객들이 이미 수천 개의 동시 컨테이너로 확장하고 있다는 문장도 이 대비를 키운다.
그 역량이 존재하지만 일반 사용자에게는 40 GiB가 주어진다는 뜻이기 때문이다.

### “전체 애플리케이션을 Cloudflare에서”라는 프레임을 Cloudflare 사람이 정정했다

ttoinou가 물었다. 이제 Cloudflare Workers와 Containers로 전체 웹사이트를 모든 지역에 분산해 엣지에서 호스팅할 수 있느냐는 것이다.[^ttoinou]

kentonv가 답했다. **수년 전부터 Workers만으로 가능했으며 저장소로 Durable Objects를 쓰면 된다**는 것이다.[^kentonv]

이 교환이 발표문의 프레이밍 문제를 드러낸다.

발표문의 서사는 “이제 전체 애플리케이션을 Cloudflare에서 돌릴 수 있다”에 가깝게 읽힌다.
그런데 Workers 런타임의 핵심 개발자가 그것은 이미 되던 일이라고 정정한다.

Containers가 실제로 더해 주는 것은 웹 애플리케이션 호스팅이 아니라 **Workers 런타임에서 실행 불가능한 코드를 돌리는 능력**이다.
FFmpeg 같은 네이티브 바이너리, 임의 언어 런타임, CLI 도구다.

이 구분이 사소하지 않다.
“이제 전부 돌릴 수 있다”로 읽은 독자는 일반 웹 백엔드를 Container로 옮기려 할 것이고, 그것이 정확히 상시 가동 워크로드이며 가격 구조가 맞지 않는 사용이다.

즉 develatio의 가격 불만과 이 프레이밍 문제가 같은 뿌리에서 나온다.
**발표문이 Container를 Worker의 예외 처리 장치가 아니라 일반 컴퓨트 제품처럼 소개했기 때문**이다.

## 인사이트

### 잠자기 타임아웃이 아키텍처 결정이 된다

`sleepAfter`가 설정 한 줄로 보이지만 실제로는 이 플랫폼에서 가장 중요한 값이다.

이 값 하나가 세 가지를 동시에 정한다. **비용, 지연, 상태 유지**다.

짧게 잡으면 비용이 줄지만 다음 요청이 콜드 스타트를 겪는다. 발표문은 초기 시작이 몇 초라고 적으므로 그 몇 초를 사용자가 기다린다.
길게 잡으면 응답은 빠르지만 유휴 시간에도 과금된다. 10ms 단위 과금은 켜져 있는 동안 계속 돈다.

그리고 컨테이너가 잠들면 프로세스 내부 상태가 사라진다.
발표문이 상태 관리에 Durable Objects를 쓰라고 권하는 이유가 여기 있다.

이 구조가 실무에 남기는 요구가 명확하다.
**컨테이너 안에 보존해야 할 상태를 두지 않는 설계**가 전제되어야 한다. 그렇지 않으면 `sleepAfter`를 길게 잡을 수밖에 없고, 그러면 가격 이점이 사라진다.

시작 가이드가 `sleepAfter = '10s'`를 쓰고 발표문 예제가 `'5m'`을 쓴다는 차이도 그래서 의미가 있다.
10초는 샌드박스처럼 한 번 쓰고 버리는 용도이고, 5분은 세션이 이어지는 용도다.

값을 정하는 기준은 이렇게 잡을 수 있다.

| 상황                          | 시작값 | 근거                                    |
| ----------------------------- | ------ | --------------------------------------- |
| 일회성 코드 실행·배치 변환    | 10s    | 다음 요청이 없을 가능성이 높다          |
| 사용자 세션 기반 샌드박스     | 1~5m   | 연속 요청 간격이 대체로 분 단위다       |
| 대화형 도구(에이전트 실행 등) | 5~15m  | 콜드 스타트가 사용자 체감을 크게 해친다 |
| 상시 가동이 필요한 백엔드     | —      | 이 플랫폼의 가격 구조에 맞지 않는다     |

마지막 줄이 중요하다. 상시 가동이 필요하면 `sleepAfter`를 조정하는 것이 아니라 **다른 제품을 골라야 한다**.

### 제어 평면을 애플리케이션 언어로 내리는 흐름의 사례다

이 발표의 기술적 주장 중 오래갈 것이 “Kubernetes 오퍼레이터 대신 JavaScript”다.

이것이 개별 제품의 편의 기능이 아니라 더 큰 흐름의 한 사례다.

인프라 제어가 전통적으로 **선언적 설정과 별도 컨트롤러**로 이루어졌다.
YAML로 원하는 상태를 적고, 컨트롤러가 현재 상태를 그리로 수렴시키는 구조다.
이 모델의 장점은 명확하다. 상태가 검사 가능하고, 컨트롤러가 장애를 복구하며, 설정이 코드와 분리된다.

단점도 명확하다. **동적 결정을 표현하기 어렵다**.
“이 사용자에게는 인스턴스를 하나 주고, 이 요청은 기존 인스턴스로 보내고, 10초 뒤 정리한다”는 로직을 선언적으로 쓰려면 별도의 컨트롤러를 작성해야 한다.

Cloudflare의 선택은 그 결정을 요청 처리 코드 안으로 옮기는 것이다.
`getContainer(binding, id)`가 곧 스케줄링이고, `sleepAfter`가 곧 가비지 컬렉션 정책이다.

같은 방향의 사례가 여럿 있다.
Durable Objects가 상태 파티셔닝을 객체 주소로 표현한 것, 서버리스 함수가 프로비저닝을 호출로 표현한 것이 같은 계열이다.

그리고 대가도 같은 계열이다.
제어 로직이 애플리케이션 코드에 섞이면 **인프라와 독립적으로 검사하거나 대체하기 어려워진다**.

Kubernetes 매니페스트는 다른 클러스터에 적용할 수 있지만, `Container` 클래스를 상속한 Worker 코드는 Cloudflare 밖에서 의미가 없다.
이식성을 잃는 대신 표현력을 얻는 거래이고, 이 거래가 유리한지는 워크로드의 수명에 달려 있다.

### AI 에이전트 실행이 이 제품의 숨은 주 대상일 수 있다

발표문이 활용 사례를 나열하면서 하나를 조용히 끼워 넣는다.
**Cloudflare Agent가 Container에서 Claude Code를 대신 실행**하게 할 수 있다는 것이다.

이 한 줄이 제품의 대표 예시인 코드 샌드박싱과 이어진다.
사용자가 만들었거나 **AI가 만든** 코드를 실행하는 플랫폼을 만드는 상황이 첫 예시의 설정이었다.

이 조합이 왜 잘 맞는지는 요구사항을 늘어놓으면 보인다.

에이전트 실행에는 격리가 필요하다. 생성된 코드를 신뢰할 수 없기 때문이다.
세션마다 별도 환경이 필요하다. 한 작업의 파일 변경이 다른 작업에 새면 안 된다.
수명이 짧고 불규칙하다. 에이전트가 몇 분 일하고 멈춘다.
임의의 도구가 필요하다. `git`, 패키지 관리자, 컴파일러가 컨테이너 안에 있어야 한다.

이 넷이 정확히 Containers의 설계 지점이다. ID별 인스턴스, 자동 잠자기, 10ms 과금, 임의 이미지다.

그리고 로드맵의 `exec`가 이 해석을 강화한다.
`this.exec('git clone ...')`을 Worker 메서드로 노출하는 것은 **에이전트 하네스가 필요로 하는 바로 그 인터페이스**다.

여기서 나오는 예측이 있다.
Containers의 가격 구조가 일반 백엔드 호스팅 관점에서 비싸 보이는 것이 설계 실패가 아니라 **대상 워크로드가 다르기 때문**일 가능성이 높다.
에이전트 실행은 본질적으로 버스트이고, 상시 가동 서비스와 비용 구조가 다르다.

그렇다면 develatio의 질문 — 무거운 서비스에 이것을 쓸 이유를 모르겠다는 것 — 에 대한 답은 “그런 용도가 아니다”이고, 발표문이 그 답을 명확히 하지 않은 것이 소통의 문제다.

그리고 이 해석이 맞다면 경쟁 구도도 달라진다.
비교 대상이 Fly.io나 Railway 같은 범용 컨테이너 호스팅이 아니라, 에이전트 샌드박스를 제공하는 쪽이 된다.
그 시장에서는 전역 배치와 Workers 통합과 프로그래밍 가능한 생명주기가 실질적 우위이고, GB-초 단가 비교는 부차적이다.
