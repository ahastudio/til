# cf: 에이전트를 첫 번째 사용자로 설계한 Cloudflare 전체 API CLI

원문: [Introducing cf: the agentic CLI for the entire Cloudflare API | Cloudflare Blog](https://blog.cloudflare.com/cloudflare-cf-cli-launch/)

HN 토론: <https://news.ycombinator.com/item?id=49879577> (169점, 86개 댓글)

GN 토론: <https://news.hada.io/topic?id=34473>

## 요약

Cloudflare의 Matt “TK” Taylor와 Samuel Macleod가 2026년 9월 28일 Birthday Week에 발표한 글이다.
출발점은 숫자다.
Wrangler 사용 중 에이전트의 비율은 1년 전 한 자릿수에서 2026년 3월 4분의 1이 되었고, 발표 전주에는 48%에 이르렀다.
에이전트는 하루에 서로 다른 명령을 거의 두 배 많이 쓰고, 여섯 개 이상의 명령을 쓸 확률이 거의 네 배 높다.
그런데 Wrangler가 다루는 작업은 약 280개이고 Cloudflare API는 수천 개다.

새 CLI `cf`는 이 차이를 메우려고 만들었다.
Wrangler는 제품 팀마다 따로 손으로 만든 탓에 `d1 info`, `hyperdrive get`, `workflows describe`처럼 용어가 제각각이었고, 수천 줄짜리 맞춤 기능이 거의 쓰이지 않기도 했다.
`cf`는 Cloudflare의 통합 API 생성 파이프라인 Forge가 API 문서와 SDK를 만드는 OpenAPI 스키마에 약간의 주석을 더해 명령을 생성하므로, 3,000개가 넘는 API 작업 전체를 덮는다.
에이전트에게 `cf` 하나를 주고 Worker를 만들고 배포하고 관측하고 Access로 보호하고 도메인을 사고 WAF를 앞에 두라고 시킬 수 있다는 것이 글의 그림이다.

에이전트를 위한 설계는 세 가지다.
첫째, JSON이 기본 출력이다.
에이전트는 Wrangler 명령마다 `--json`을 붙이고 `jq`로 걸렀는데, 많은 명령이 사람용 유니코드 표만 내놓았다.
`cf`는 사람에게는 보기 좋게, 에이전트에게는 압축해서 JSON을 내고, 도메인 구매처럼 사람의 입력이 필요한 작업에는 검증된 입력 폼을 띄운다.
둘째, `cf cli search`로 자연어 질문에 맞는 명령을 작은 검색 색인에서 찾는다.
에이전트가 `--help`를 처음 실행할 때 이 명령의 존재를 알려 준다.
셋째, 설정 파일이 TOML이나 JSONC 대신 TypeScript로 된 `cloudflare.config.ts`다.
타입이 있으니 Claude Code나 Codex처럼 LSP 플러그인을 쓰는 에이전트가 형식을 추론해 더 정확하게 고친다.
Cloudflare 내부의 5,000줄 넘는 Wrangler 설정 일부는, 복사한 `env` 블록 대신 같은 기반에서 환경을 프로그램으로 만드는 방식으로 40% 줄었다.

개발 환경은 Vite가 기본이 된다.
Wrangler가 처음 나왔을 때는 Vite가 없어 esbuild와 자체 개발 서버를 썼지만, 이제 Cloudflare Vite Plugin과 Vitest 플러그인이 권장 경로다.
esbuild에 의존하는 JavaScript Worker와 Rust, Python Worker는 `cf`가 계속 Wrangler에 위임한다.
`cf migrate`로 옮기고, 공개 베타가 끝나면 Wrangler의 마지막 메이저 버전이 `cf`를 쓰라고 안내하며, 그 뒤 18개월 동안 유지보수를 지원한다.
설치는 `npm i -g cf`이고 오픈소스다.

글에는 에이전트에게 붙여 넣을 프롬프트도 있다.
이 프롬프트는 에이전트에게 저장소의 `AGENTS.md`나 `CLAUDE.md`가 아니라 모든 프로젝트에 적용되는 사용자 수준 지시 파일에 `cf` 사용 지침을 추가하라고 한다.
지침은 `cf`를 Wrangler보다 우선하고, Wrangler 설정 파일이 있는 프로젝트에서만 Wrangler를 쓰고, 명령을 추측하지 말고 `cf cli search`로 찾으라는 내용이다.

## 분석

### 사용자의 절반이 에이전트가 되면 CLI의 기본값이 뒤집힌다

글의 논리는 48%라는 숫자 하나에 기대고 있다.
사용자의 절반이 에이전트라면, 사람을 위한 기본값과 에이전트를 위한 옵션이라는 기존 구조가 거꾸로 되어야 한다는 것이다.
JSON 기본 출력은 그 뒤집기를 가장 선명하게 보여 준다.
사람은 이 CLI의 고객이지만 실제로는 한 단계 떨어져 있고, 에이전트가 걸러 준 결과를 원하는 형식으로 받는 편이 표를 읽는 것보다 낫다는 문장이 그 논리를 요약한다.

이 전환은 Unix 도구 전통과도 이어진다.
사람이 읽기 좋은 출력과 기계가 파싱하기 좋은 출력의 긴장은 오래된 문제이고, `git`의 porcelain과 plumbing 구분이 그 절충이었다.
`cf`는 기본을 plumbing 쪽에 두고, 사람에게는 보기 좋은 출력과 폼이라는 별도 통로를 준다.

### 발견 가능성이 문서에서 도구 안으로 들어온다

명령이 280개에서 3,000개로 늘면 발견 문제가 생긴다.
사람이라면 문서를 검색하지만, 에이전트에게 3,000개 명령의 도움말을 컨텍스트에 넣을 수는 없다.
`cf cli search`는 발견을 도구 자체의 기능으로 만든다.

HN에서 recroad는 REST 문서만 주면 에이전트가 Cloudflare 작업을 다 알아서 했다며 CLI가 API의 부분집합이냐고 물었다[^recroad].
artdigital은 Cloudflare 문서를 참조하는 `AGENTS.md`와 변경 기록 규칙을 둔 별도 폴더에서 에이전트에게 작업을 맡긴다며, `cf`는 API를 탐색하기 쉬운 CLI로 감싼 것이라고 추측했다[^artdigital].
두 사람의 경험은 `cf`의 핵심이 새 기능이 아니라 탐색 비용 절감이라는 점을 보여 준다.
bhouston은 여기서 한 걸음 더 나가, 예제까지 포함해 완전히 발견 가능하도록 공개 CLI 명세 형식을 지원하라고 제안했다[^bhouston].

### 생성된 CLI는 일관성을 조직 구조에서 떼어 낸다

Wrangler의 비일관성은 코드 문제라기보다 조직 문제였다.
제품 팀마다 자기 방식으로 명령을 만들었으니 `info`, `get`, `describe`가 섞였다.
콘웨이의 법칙이 CLI 표면에 그대로 드러난 셈이다.

Forge로 스키마에서 명령을 생성하면 명령 이름의 일관성은 팀의 규율이 아니라 생성기의 규칙이 된다.
이는 AWS CLI가 서비스 API 정의에서 명령을 생성하고, Google Cloud가 discovery 문서로 클라이언트를 만드는 것과 같은 방향이다.
에이전트 시대에 이 선택이 더 중요해지는 이유는, 에이전트가 한 제품에서 배운 패턴을 다른 제품에 그대로 적용하기 때문이다.
사람에게 사소한 동사 차이가 에이전트에게는 틀린 추측의 원인이 된다.

### 학습된 습관과 싸우지 않으려고 이름을 바꾼다

글에서 가장 흥미로운 논증은 왜 Wrangler를 고치지 않고 새 CLI를 만들었는가다.
Wrangler는 수년 치 문서와 블로그가 LLM 학습에 들어가 있다는 장점이 있지만, 바로 그 때문에 크게 바꾸면 학습된 행동과 충돌한다.
에이전트에게 익숙한 도구의 두 버전 차이를 이해시키는 것보다, 처음 보는 도구와 지침 파일을 주는 편이 덜 헷갈린다는 것이다.

이 판단은 API 버저닝의 오래된 원칙이 에이전트 시대에 새 형태로 나타난 것이다.
하위 호환을 깨는 변경은 같은 이름 아래 두지 말라는 원칙이, 이제 사람의 기억이 아니라 모델의 가중치를 상대로 적용된다.

## 비평

### TypeScript로 쓴 CLI는 에이전트 우선이라는 원칙과 어긋난다

HN에서 가장 많은 답글을 받은 slowin의 댓글은 이 CLI를 왜 TypeScript로 썼는지 모르겠다며, 사용자에게 CLI의 의존성 관리를 떠넘기지 말고 컴파일 언어로 쓰라고 했다[^slowin].
geodel은 자사 인프라에서 돌 때는 Rust로 최적화하고, 사용자 컴퓨터에서 돌 때는 JS가 최선이라고 결론 내리는 것이 요즘 기술 기업의 방식이라고 꼬집었다[^geodel].
반대편에서 kelchm은 기존 Cloudflare 도구 생태계 안에서는 합리적인 선택이라고 봤고[^kelchm], wannabe44는 에이전트가 쓰는 코드의 유지보수성을 이유로 Rust와 Go를 검토하고도 논쟁을 피하려고 밝히지 않았을 수 있다고 추측했다[^wannabe44].

이 논쟁을 글의 논리 안에 놓으면 문제가 더 선명해진다.
글은 에이전트가 첫 번째 사용자라고 말한다.
에이전트는 샌드박스, CI 컨테이너, 새로 만든 가상 머신에서 CLI를 실행하는 일이 많고, 그때마다 Node 런타임과 `npm i -g`가 전제 조건이 된다.
단일 바이너리였다면 설치가 한 단계로 끝났을 것이다.
시작 시간도 문제다.
amluto는 새로 설치한 gcloud가 캐시가 따뜻한 상태에서도 도움말 하나 띄우는 데 1.2초가 걸린다며, 원격 LLM조차 지루해할 만큼 느리고 에이전트용 CLI라면 더 빨라야 한다고 썼다[^amluto].
도구 호출마다 CLI를 새로 띄우는 에이전트에게는 처리량이 아니라 호출당 지연이 비용이고, 런타임을 띄우는 언어는 그 지연을 매번 더한다.
설정 파일을 TypeScript로 만든 결정은 타입 검사라는 분명한 이유가 있지만, CLI 본체까지 TypeScript여야 하는 이유는 글에 없다.

### 에이전트에게 전역 지시 파일을 고치게 하는 프롬프트는 경계를 넘는다

글이 제공하는 복사용 프롬프트는 에이전트에게 저장소가 아니라 사용자 수준 지시 파일을 고치라고 한다.
그 파일은 사용자가 모든 프로젝트에 적용하려고 직접 관리하는 곳이다.
한 벤더의 지침이 그 파일에 들어가면, Cloudflare와 무관한 프로젝트에서도 에이전트가 그 지침을 읽는다.

프롬프트는 기존 내용을 보존하고 충돌하는 Wrangler 지침만 바꾸라고 조심스럽게 쓰여 있다.
하지만 원리 자체가 문제다.
사용자가 붙여 넣은 텍스트가 에이전트의 전역 설정을 바꾸게 하는 패턴이 정상화되면, 같은 모양의 텍스트가 웹 페이지나 README에 숨어 있을 때 구별하기 어려워진다.
프롬프트 인젝션 방어의 기본은 에이전트가 설정 파일을 고치기 전에 사람이 그 변경을 확인하는 것이고, 벤더가 공식적으로 그 반대를 권하면 사용자에게 나쁜 습관을 가르친다.

### 3,000개 명령을 에이전트에게 주면서 권한 이야기는 없다

글은 에이전트가 Worker를 배포하고 도메인을 사고 WAF를 설정하는 그림을 그린다.
그런데 그 모든 작업이 같은 API 토큰 하나로 이루어진다면, 에이전트의 실수 하나가 DNS나 방화벽 규칙까지 닿는다.
hackernud3s는 이 CLI가 권한을 줄 토큰을 만드는 일만 빼고 다 할 수 있고, 그 토큰 화면은 웹사이트에서 매주 자리를 옮긴다고 꼬집었다[^hackernud3s].

verdverm은 에이전트가 CLI를 직접 쓰기보다 스크립트를 쓰게 하고 스크립트를 에이전트 밖에서 실행하면, 에이전트 프로세스에서 자격 증명을 완전히 뺄 수 있다고 했다[^verdverm].
그리고 이런 CLI는 읽기 전용 디버깅 세션에는 좋지만, 클라우드 인프라를 바꿀 때는 IaC를 계속 쓰라고 조언했다.
creatonez는 더 강하게, 프로덕션 인프라 설정에 무작위 단어 생성기를 쓰는 사용자를 막아야지 왜 돕느냐고 반발했다[^creatonez].
글이 넓힌 표면만큼 권한을 좁히는 방법, 예를 들어 명령 그룹별 토큰 범위나 읽기 전용 모드를 다루지 않은 것이 가장 큰 공백이다.

### 출시 시점과 상태가 글의 어조와 맞지 않는다

esafak은 1.0이 실제로 나오지 않았고 CI가 빨간색이라며, 사전 릴리스를 잘 쓰고 있지만 글은 며칠 기다렸어도 됐다고 지적했다[^esafak].
글은 공개 베타라고 밝히지만, 에이전트의 전역 지침에 Wrangler보다 `cf`를 우선하라고 적게 하는 프롬프트는 베타 도구에 대한 요구로는 과하다.
`cf` 명령이 실패해도 보고를 제안하지 않고는 Wrangler로 돌아가지 말라는 지침은, 베타의 피드백 수집을 사용자의 작업 흐름 한가운데에 끼워 넣는다.

## 인사이트

### 에이전트 사용 비율은 CLI 설계의 새 KPI가 된다

Cloudflare가 48%라는 숫자를 공개할 수 있었다는 것 자체가 신호다.
CLI가 호출 주체가 사람인지 에이전트인지 구분해 측정하고 있다는 뜻이고, 이 측정이 제품 결정을 이끌었다.
다른 벤더도 곧 같은 숫자를 추적할 것이다.

이 지표가 퍼지면 CLI 설계 논의의 기준이 바뀐다.
출력 형식, 오류 메시지, 도움말 구조가 사람의 가독성이 아니라 에이전트의 토큰 비용과 성공률로 평가된다.
오류 메시지가 다음에 실행할 명령을 제안하는지, 도움말이 검색 가능한지가 품질의 척도가 된다.
사람을 위한 CLI가 나쁜 에이전트용 CLI인 것은 아니지만, 둘 사이에서 기본값을 고를 때 이제 근거가 숫자로 존재한다.

### 학습 데이터가 부채가 되는 순간이 온다

Wrangler 사례는 LLM 시대의 새로운 기술 부채를 보여 준다.
수년 동안 쌓인 문서와 블로그는 도구의 자산이었지만, 도구를 크게 바꾸려는 순간 모델 속의 오래된 지식이 새 버전과 충돌하는 부채가 된다.
Cloudflare는 이름을 바꾸는 방식으로 이 부채를 떼어 냈다.

이 패턴은 앞으로 반복될 것이다.
널리 쓰인 도구일수록 모델이 더 깊이 학습했고, 그래서 호환을 깨는 변경이 더 어렵다.
결과적으로 큰 변경은 버전 번호가 아니라 새 이름과 새 도구로 나타날 가능성이 높다.
그리고 새 도구는 모델이 모르는 상태에서 시작하므로, 지침 파일과 도구 안의 검색 기능이 학습 데이터의 공백을 메우는 역할을 떠맡는다.
`cf`가 `--help`에서 `cf cli search`를 알려 주는 것도, 전역 지침 파일에 들어가려는 것도 이 공백을 메우려는 시도다.

### 설정 파일이 코드가 되면 IaC와 CLI의 경계가 다시 그어진다

`cloudflare.config.ts`는 Worker 설정에서 시작하지만, 글은 곧 정책, 존, DNS까지 이 파일로 관리하겠다고 한다.
그렇게 되면 이 파일은 사실상 Cloudflare 전용 IaC가 된다.
smithclay가 Forge 기반이니 Terraform을 네이티브로 내보내는 기능도 나오길 바란다고 한 것은 이 방향을 정확히 읽은 것이다[^smithclay].

여기서 긴장이 생긴다.
Terraform은 상태 파일과 plan 단계로 변경을 미리 보여 주고, 여러 벤더를 한 언어로 묶는다.
TypeScript 설정은 타입 검사와 프로그래밍 가능성을 주지만, 벤더 하나에 묶인다.
에이전트가 쓰기 쉬운 벤더 전용 설정과, 사람이 검토하기 쉬운 벤더 중립 plan 중 무엇이 기본이 될지는 아직 정해지지 않았다.
에이전트가 인프라를 바꾸는 비율이 늘수록, 변경을 미리 보여 주는 plan 단계의 가치는 오히려 커진다.

### 에이전트용 도구는 사람이 해야 할 일을 명시적으로 남겨야 한다

`cf`의 도메인 구매 폼은 작은 기능이지만 중요한 원칙을 담고 있다.
어떤 작업은 사람이 직접 입력하는 편이 낫다는 것을 도구가 인정한다.
verdverm이 소개한, 사람만 할 수 있거나 사람이 해야 하는 일을 에이전트가 대화형 스크립트로 만들어 넘기게 하는 스킬도 같은 방향이다[^verdverm].

에이전트 우선 도구가 성숙하려면 이 목록이 더 길고 명시적이어야 한다.
토큰 발급, 결제, DNS 변경, 방화벽 규칙처럼 되돌리기 어렵거나 권한을 넓히는 작업을 도구가 스스로 사람에게 넘기는 구조가 필요하다.
3,000개 명령을 모두 에이전트에게 여는 것보다, 그중 어느 것을 사람 몫으로 남길지 정하는 것이 더 어려운 설계 문제다.
