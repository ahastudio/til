# Durable Objects: 상태를 애플리케이션의 논리 단위로 쪼개는 서버리스

원문: [Workers Durable Objects Beta: A New Approach to Stateful Serverless](https://blog.cloudflare.com/introducing-workers-durable-objects/)

HN 토론: <https://news.ycombinator.com/item?id=24616169> (209점, 91개 댓글)

GN 토론: <https://news.hada.io/topic?id=2930>

## 요약

Kenton Varda가 2020년 9월 28일 Birthday Week에 쓴 17분 분량의 발표문이다. Durable Objects 비공개 베타 시작을 알린다.

배경 설명이 먼저 온다.
2017년 Workers를 내놓으면서 엣지에서 도는 코드가 성능만이 아니라 배포 편의와 비용에서도 나을 수 있다는 생각을 세웠고, 아이솔레이트 기술 덕에 다른 제공자를 붙잡는 긴 콜드 스타트 없이 서버리스를 더 싸게 제공할 수 있었다는 것이다.
Workers KV로 쉽게 쓰는 최종 일관성 엣지 저장소도 더했다.

그런데 지금까지 **강한 일관성으로 상태를 관리하거나 여러 클라이언트 사이를 실시간으로 조율하는 일을 엣지에서만 할 수는 없었다**.
그래서 애플리케이션의 그 부분은 다른 곳에 호스팅해야 했다.

Durable Objects가 그 빠진 조각이며, 중앙 “오리진” 서버 없이 애플리케이션 전체가 엣지에서 돌게 만드는 것이라고 적는다.

### 이름의 세 부분

저자가 이름 짓기가 어려웠다고 솔직히 밝힌다. 오늘날 널리 쓰이는 다른 클라우드 기술과 꼭 같지 않기 때문이라는 것이다.
결국 “Unique Durable Objects”, 줄여서 Durable Objects로 정했다며 세 단어를 나눠 설명한다.

**Objects**: 객체 지향 프로그래밍에서 말하는 객체다. Durable Object는 클래스의 인스턴스이며, 말 그대로 JavaScript(또는 선택한 언어)로 작성한 클래스 정의다.
클래스에 공개 인터페이스를 정의하는 메서드가 있고, 객체는 코드와 비공개 상태를 결합한 그 클래스의 인스턴스다.

**Unique**: 각 객체가 전역 고유 식별자를 갖는다. 그 객체는 한 시점에 **전 세계에서 단 한 곳**에만 존재한다.
객체 ID를 아는 전 세계 어느 Worker든 그 객체에 메시지를 보낼 수 있고, 모든 메시지가 같은 곳에 도달한다.

**Durable**: 보통의 JavaScript 객체와 달리 디스크에 지속 상태를 저장할 수 있다.
각 객체의 지속 상태는 그 객체에만 비공개이므로 저장소 접근이 빠를 뿐 아니라, 객체가 메모리에 일관된 사본을 안전하게 유지하며 **지연 없이** 다룰 수 있다.
메모리의 객체는 유휴 상태가 되면 종료되고 나중에 필요할 때 다시 만들어진다.

### 두 가지 능력

**저장소**: 각 객체에 지속 저장소가 붙어 있다. 그 저장소가 특정 객체에만 비공개이므로 언제나 객체와 같은 위치에 있다.
그래서 저장소가 매우 빠르면서 강한 트랜잭션 일관성을 제공한다.
전통적인 거대 단일 데이터베이스를 **많은 작은 논리 단위로 쪼개는 것**이며, 그럼으로써 서버리스에서 기대하는 이점 — 유지보수 부담 없는 손쉬운 확장 — 을 얻는다는 것이다.

**조율**: 지금까지 Workers에서는 각 요청이 무작위로 Worker 인스턴스에 부하 분산되었다.
어느 인스턴스가 요청을 받을지 제어할 수 없었으므로 두 클라이언트가 같은 Worker와 대화하게 만들 수 없었고, 따라서 클라이언트들이 Workers를 통해 조율할 방법이 없었다.
Durable Objects는 같은 주제에 관한 요청을 같은 객체로 보내며, 그 객체가 **저장소를 건드릴 필요 없이** 사이를 조율한다.
실시간 채팅, 협업 편집, 화상 회의, pub/sub 메시지 큐, 게임 세션이 예로 제시된다.

조율 사례 다수가 WebSocket을 필요로 하므로, 이 베타와 함께 **Workers에 WebSocket 지원도 추가**했다고 밝힌다.

### Region: Earth

Durable Objects를 쓰면 Cloudflare가 각 객체가 살 데이터센터를 자동으로 정하고 필요에 따라 객체를 **투명하게 이전**한다.

전통적인 데이터베이스와 상태 저장 인프라는 데이터를 쓰이는 곳 가까이 두기 위해 지리적 “리전”을 생각하게 만드는데, 그것이 본질적으로 지리적이지 않은 애플리케이션에는 부자연스러운 부담이라는 것이다.

대신 저장 모델을 **애플리케이션의 논리 데이터 모델에 맞춰** 설계한다.
문서 편집기라면 문서마다 객체를 두고, 채팅 앱이라면 채팅방마다 객체를 둔다.
각 객체의 오버헤드가 최소이므로 수백만 또는 수십억 개를 만들어도 문제가 없다고 적는다.

### 실시간 협업 편집이라는 핵심 사례

표준 웹 애플리케이션 스택에서 이것이 어려운 문제인 이유를 설명한다.
전통적인 데이터베이스는 애초에 실시간용으로 설계되지 않았고, 키 입력을 데이터베이스에 저장한 뒤 사용자가 반복해서 폴링하게 하면 잘해야 지연이 나쁘고 최악에는 지구 반대편 사용자들이 같은 내용을 두고 다투며 트랜잭션이 반복 실패한다는 것이다.

해법의 비밀은 **살아 있는 조율 지점**이다.
Alice와 Bob이 보통 WebSocket으로 같은 조율자에 연결하고, 조율자가 저장 계층을 거치지 않고 서로의 키 입력을 전달한다.
같은 내용을 동시에 편집하면 조율자가 충돌을 즉시 해소하고, 메모리에 문서 사본을 유지하므로 저장소 기록은 비동기로 할 수 있다.

이름난 실시간 협업 편집기가 전부 이렇게 동작하지만, 표준 서버리스 인프라는 이런 조율 지점을 지정하고 사용자를 같은 서버 인스턴스로 보내는 일을 쉽게 만들어 주지 않는다는 것이다.

### 원자적 카운터 예제

```javascript
export class Counter {
  constructor(controller, env) {
    // controller.storage가 객체의 디스크 지속 저장소 인터페이스다
    this.storage = controller.storage
  }

  async initialize() {
    let stored = await this.storage.get("value");
    this.value = stored || 0;
  }

  async fetch(request) {
    // 저장소에서 완전히 초기화되었는지 확인한다
    if (!this.initializePromise) {
      this.initializePromise = this.initialize();
    }
    await this.initializePromise;

    let url = new URL(request.url);
    switch (url.pathname) {
      case "/increment":
        ++this.value;
        await this.storage.put("value", this.value);
        break;
      case "/decrement":
        --this.value;
        await this.storage.put("value", this.value);
        break;
      case "/":
        // 현재 값만 반환한다. 저장소 호출이 필요 없다
        break;
      default:
        return new Response("Not found", {status: 404});
    }

    return new Response(this.value);
  }
}
```

호출 쪽은 이렇다.

```javascript
// "my-counter"라는 이름의 카운터 객체 ID를 파생한다.
// 이 이름은 전 세계에서 정확히 하나의 인스턴스에 대응한다.
let id = COUNTER_NAMESPACE.idFromName("my-counter");

let response = await COUNTER_NAMESPACE.get(id).fetch(request);
```

여러 클라이언트가 동시에 요청해도 증감이 유실되지 않으며, 읽기는 디스크 접근 없이 전부 메모리에서 처리된다는 설명이다.

### 채팅 데모가 드러내는 두 가지 쓰임

오픈소스 채팅 앱 데모를 함께 공개했다.
채팅방마다 Durable Object가 제어하고, 사용자는 WebSocket으로 객체에 연결하며, 한 사용자의 메시지가 다른 사용자들에게 브로드캐스트된다.
채팅 이력도 지속 저장소에 저장되지만 **그것은 이력용일 뿐이고, 실시간 메시지는 저장 계층을 거치지 않고 직접 중계**된다.

두 번째 쓰임이 더 흥미롭다. IP별 메시지 속도 제한이다.
각 IP에 최근 요청 빈도를 추적하는 Durable Object를 배정해, 너무 많이 보내는 사용자를 여러 채팅방에 걸쳐 일시 차단할 수 있다.

그리고 결정적인 한 문장이 붙는다.
이 객체들은 **실제로 아무 지속 상태도 저장하지 않는다**. 아주 최근 이력만 신경 쓰고 속도 제한기가 가끔 초기화되어도 큰일이 아니기 때문이다.
그래서 이 속도 제한 객체들은 **저장소 없는 순수 조율 객체**의 예라는 것이다.

앱 전체가 몇백 줄이고 배포 설정은 몇 줄이며, 채팅방 수는 Cloudflare 가용 자원까지 매끄럽게 확장된다.
다만 **각 객체가 단일 스레드이므로 개별 채팅방의 확장에는 한계가 있다**고 명시한다. 사람 참가자가 따라갈 수 있는 수준을 훨씬 넘는 한계라고 덧붙인다.

### 아직 데이터베이스는 아니다

Durable Objects를 분산 시스템을 만드는 **저수준 프리미티브**로 본다고 적는다.

그리고 한계를 명확히 한다. 오늘의 Durable Objects는 완전한 데이터베이스 해법이 아니며, **각 객체가 자기 데이터만 볼 수 있다**.
여러 객체에 걸친 질의나 트랜잭션을 하려면 애플리케이션이 추가 작업을 해야 한다.

그럼에도 전망을 제시한다.
모든 큰 분산 데이터베이스가 낮은 수준에서는 데이터 일부를 저장하는 “청크”나 “샤드”로 구성되며 분산 데이터베이스의 일은 청크 사이를 조율하는 것이라는 관찰이다.
그래서 각 청크를 Durable Object로 저장하는 엣지 데이터베이스의 미래가 보인다며, 그것을 Cloudflare가 만들 필요도 없고 누구나 그 위에 만들 수 있다고 적는다.

### Q&A에서 밝힌 것들

**KV와의 차이**: KV는 최종 일관성이며 “마지막 쓰기 승리” 의미론이라 자주 바뀌거나 전 세계에 즉시 보여야 하는 상태에는 부적합하다.
Durable Objects는 저장 스펙트럼의 반대편이며 트랜잭션 보장과 즉시 일관성이 필요한 작업에 매우 잘 맞는다.
다만 트랜잭션은 본질적으로 한 곳에서 조율되어야 하므로 지구 반대편 클라이언트는 광속의 한계 때문에 중간 정도의 지연을 겪으며, 자동 이전으로 그 문제에 대응한다는 것이다.

그리고 **앞으로 Workers KV 구현 자체에 Durable Objects를 활용할 계획**이라고 밝힌다.

**왜 CRDT가 아닌가**: CRDT 기반 저장소를 Durable Objects 위에 만들 수 있지만 Durable Objects가 CRDT를 요구하지는 않는다는 것이다.
CRDT가 강력하지만 올바르게 적용하기 어렵고, 데이터 손실 없이 자동 충돌 해소가 가능한 자료 구조는 일부뿐이라고 적는다.
git에 익숙한 개발자라면 문제가 보인다며, 임의의 충돌 해소는 어렵고 어떤 자동 알고리즘이든 가끔 틀릴 것이며 임의 순서의 병합을 처리하면서 같은 답을 내야 한다면 더 어렵다는 것이다.

결론이 단호하다. 대부분의 애플리케이션에서 **CRDT는 지나치게 복잡하고 들이는 노력만큼의 값을 하지 못한다**고 느끼며, 문서마다 단일 권위 조율 지점을 배정하는 편이 대체로 훨씬 쉽다는 것이다. 그것이 정확히 Durable Objects가 하는 일이다.

### 마지막 논지

상태가 “서버리스”라는 것이 무엇을 뜻하는지로 글을 맺는다.

서버리스가 성공한 이유가 **의미적 정렬** 때문이라는 것이다.
아무도 자기 비즈니스 로직을 “서버”나 “컨테이너”나 “프로세스” 단위로 생각하지 않고 이벤트 단위로 생각하는데, 서버리스가 연산의 논리 단위를 이벤트로 잡았기 때문에 부담을 옮기는 데 성공했다는 논리다.

같은 철학을 상태에 적용하면, 상태를 애플리케이션의 논리 단위에 대응하는 잘게 쪼갠 조각으로 나누는 것이 된다.
애플리케이션에서 상태의 논리 단위는 “테이블”이나 “컬렉션”이나 “그래프”가 아니다.
채팅 앱에서는 **채팅방**이고, 온라인 스프레드시트 편집기에서는 **스프레드시트**이며, 온라인 상점에서는 **장바구니**다.

저장 계층이 제공하는 물리적 저장 단위를 애플리케이션에 내재한 논리적 상태 단위와 일치시킴으로써, 확장성과 리전 문제를 포함해 그동안 개발자에게 떨어지던 여러 부담을 저장 제공자가 가져갈 수 있다는 것이다.

Scala 쪽이 액터 모델에 열심이고 Lightbend가 “Stateful Serverless”라는 용어를 한동안 써 왔으며 Erlang과 Elixir 쪽도 그렇다고 덧붙였다.
핵심은 “널리 쓰이는”에 있는 것 같다고 정리하면서, 자기 말이 의도보다 오만하게 들린다고 사과하고 튜플 공간 연구자들이 80~90년대에 크게 애썼는데 산업에 대체로 무시당한 것이 안타깝다고 적었다.

vyrotek은 Azure Durable Functions와 비슷하냐고 물으며, 이 기능들이 서버리스 액터 모델을 구현하는 좋은 방법으로 이해되는데 Cloudflare 페이지에 액터 모델에 대한 언급이 전혀 없어 놀랐다고 적었다.[^vyrotek]

이 교환들이 이 글의 실제 주장을 정확한 크기로 만든다.
**새로운 것은 개념이 아니라 그 개념이 웹 인프라의 기본 제품으로 제공된다는 사실**이다.
글이 “널리 쓰이는 다른 클라우드 기술과 꼭 같지 않다”고 쓴 것이 그 뜻이었고, kentonv의 답이 그것을 확인한다.

### 단일 스레드 객체가 이 설계의 전부다

이 제품이 강한 일관성을 싸게 제공하는 비결이 하나다. **객체마다 한 번에 한 곳에만 존재하고 단일 스레드로 돈다는 것**이다.

합의 프로토콜이 필요 없다. 쓰기를 조율할 상대가 없기 때문이다.
분산 트랜잭션이 필요 없다. 트랜잭션 범위가 객체 하나이기 때문이다.
락이 필요 없다. 동시 실행이 없기 때문이다.

dividuum이 이 지점을 정확히 파고들었다.[^dividuum]
예제 Counter 객체가 전역에 인스턴스 하나만 있고 get과 put 사이에 추가로 `await`하는 호출이 없으므로 원자성이 보장되는 것이냐고 물었고, 그러면 그 객체가 다른 Worker에서 인스턴스화되는 것이 막히느냐고 물었다.

kentonv의 답이 이 모델의 정확한 규칙을 준다.[^kentonv-eorder]
각 객체가 본질적으로 액터 모델 의미의 액터이며 다른 객체와 일반 Worker에 메시지를 보낼 수 있고, **들어오는 요청은 이전 이벤트가 끝나기를 기다리며 막히지 않는다**는 것이다.
따라서 **블록은 `await` 문이 없을 때만 원자적**이다.

그리고 카운터 예제에서 초기화 이후 `await`하는 것이 저장소 `put()`뿐이므로 기술적으로는 `put()`들이 잘못된 순서로 수행될 수 있다고 상상할 수 있지만, `put()`이 async 메서드임에도 실제 쓰기는 `put()`이 호출된 순서로 일어나도록 보장할 수 있다고 밝혔다.
이것이 Cap'n Proto RPC가 구현하는 **E-order** 덕분이라는 설명이다.

이 답이 발표문 본문에 없는 핵심 정보다.
“await가 없으면 원자적”이라는 규칙은 이 플랫폼에서 코드를 쓰는 사람이 반드시 알아야 하는데, 글은 “동시 요청에도 일관적”이라고만 적는다.

그리고 대가도 명확하다. 단일 스레드가 곧 객체당 처리량 상한이다.
proppy가 단일 Durable Object가 처리할 수 있는 최대 qps를 물었고,[^proppy] kentonv는 객체가 한 스레드로 제한되며 그것이 몇 qps인지는 앱이 요청 핸들러에서 임의의 코드를 돌릴 수 있으므로 전적으로 앱에 달렸다고 답했다.[^kentonv-qps]

### 속도 제한기 예제가 이 제품의 성격을 가장 잘 설명한다

채팅 데모에서 두 번째 쓰임이 본문에서 짧게 지나가지만 개념적으로 가장 중요하다.

IP별 속도 제한 객체가 **아무 지속 상태도 저장하지 않는다**는 것이다.

이것이 왜 결정적인가 하면, “Durable”이라는 이름이 가리키는 것이 이 제품의 주된 쓰임이 아님을 보여 주기 때문이다.

글 자신이 Q&A에서 그렇게 적는다. Durable Objects가 주로 저장 제품이 전혀 아니며 그것을 쓰는 많은 사례가 실제로 지속 저장소를 활용하지 않는다는 것이다.

그렇다면 이 제품이 파는 것은 저장소가 아니라 **주소 지정 가능한 단일 실행 지점**이다.
같은 ID로 보낸 요청이 같은 곳에 도달한다는 보장 하나가 제품의 핵심이고, 저장소는 거기 딸려 오는 것이다.

이 관점에서 보면 Workers의 기존 한계 서술이 다시 읽힌다.
“어느 인스턴스가 요청을 받을지 제어할 수 없었으므로 클라이언트들이 조율할 방법이 없었다”는 문장이 문제 정의이고, 고유 ID가 답이다.

pier25가 이 점을 농담으로 정리했다. 제대로 이해한 것이라면 본질적으로 Worker를 위한 즉시 일관적 분산 상태이며 그냥 “Workers State”라고 불러도 됐겠다는 것이다.[^pier25]

GN에서 xguru도 같은 층위를 짚었다.[^xguru]
서버리스가 대부분 무상태인 것들에 주로 적용되어 왔는데 **조율이 필요한 부분까지 포함하도록 더 확장하는 것**이며, 요즘 Cloudflare의 행보가 무척 흥미롭다는 관찰이다.

## 비평

### 운영 수치를 하나도 제시하지 못한 채 발표했다

이 글이 17분 분량인데, 실제로 이 제품을 도입할지 판단하는 데 필요한 숫자가 하나도 없다.

HN 독자들이 그 질문을 차례로 던졌다.

jopsen이 Durable Object의 크기 한도와 초당 읽기·쓰기 한도를 물으며, 그것이 대체로 자기 클라우드 프리미티브에 대해 가장 먼저 알고 싶은 것들이라고 적었다.[^jopsen]
그리고 일관성에 대해서는 적어도 명확히 밝혔다는 점에 대해서는 점수를 줬다.

kentonv의 답이 솔직하지만 공백을 확인해 준다.[^kentonv-throughput]
개별 Worker 인스턴스의 처리량을 묻는 것과 비슷해서 시스템이 필요한 만큼 자동으로 띄우므로 전체 처리량은 사실상 무제한이며, 애플리케이션은 객체를 합리적으로 가능한 한 잘게 만들어 한 객체의 한도가 문제 되지 않게 해야 한다는 것이다.
그리고 **아직 이런 질문들에 대한 수치가 없으며 초기 베타이고 아직 손볼 최적화가 많이 남았다**고 밝혔다.

toddh는 더 긴 목록을 냈다. 보안이 어떻게 동작하는지, 메시지 발신자에 백프레셔가 있는지, 순서 보장이 있는지, 활성화된 객체가 상태를 재구성할 수 있게 메시지가 큐에 쌓이는지, 패시베이션 온도를 제어할 수 있는지, 객체가 다중 스레드를 지원할 수 있는지, 객체가 이동할 수 있는지, 장애 조치는 어떤지다.[^toddh]

kentonv가 상세히 답했다.[^kentonv-security]
메시지는 다른 Worker에서만 Durable Objects로 보낼 수 있고, 보내려면 발신 Worker에 “Durable Object Namespace Binding”을 설정해야 하며, 현재는 같은 계정의 Worker만 네임스페이스에 바인딩할 수 있다는 것이다.
백프레셔에 대해서는 현재 유일한 메시지 형식이 HTTP(WebSocket 포함)이며 요청·응답 본문과 WebSocket 스트림에 백프레셔가 실제로 있고, 그것이 Cap'n Proto에 스트리밍 흐름 제어를 추가한 이유라고 밝혔다.

이 답변들의 질이 높다는 점은 인정해야 한다. 발표 당일 저자가 직접 기술 질문에 상세히 답한 것이다.

문제는 **그 정보가 블로그 글이 아니라 HN 댓글에만 있다**는 점이다.
발표문을 읽고 판단하려는 독자는 바인딩 기반 접근 제어도, await 원자성 규칙도, 백프레셔 존재도 알 수 없다.

### 강한 일관성을 내세우면서 검증 계획이 없다

이 제품의 모든 차별점이 “강한 트랜잭션 일관성”에서 나온다. KV와의 비교도 그 축으로 이루어진다.

skybrian이 장애 시 내구성 보장이 어떻게 되는지 물으며, 지속 저장소를 복제하면 지연이 늘 것 같다고 짚고 **Jepsen 테스트가 있을 예정인지** 물었다.[^skybrian]

a-robinson의 답이 두 가지를 밝힌다.[^a-robinson]
저장소가 인근 여러 사이트에 복제되고 쓰기에 약간의 지연을 더하지만 하드웨어나 네트워크 장애로 객체가 오프라인이 되거나 유실되는 것보다는 낫다는 것이다.
그리고 **현재로서는 Jepsen 테스트 계획이 없으며 나중에 말이 되는지 보겠다**고 답했다.

이 답이 문제적이다.

Jepsen은 분산 시스템의 일관성 주장을 외부에서 검증하는 사실상의 표준이고, 여러 데이터베이스가 그 검증에서 문서화된 보장과 실제 동작의 차이를 드러냈다.

일관성을 핵심 가치로 파는 제품이 그 검증을 계획에 두지 않았다는 것은, 사용자가 그 보장을 **믿는 것 외에 확인할 방법이 없다**는 뜻이다.

특히 이 제품은 검증이 더 어려운 구조다.
객체가 자동으로 이전되고, 유휴 시 종료되었다가 재생성되며, 복제 구성이 공개되지 않는다.
이전 중에 쓰기가 들어오면 어떻게 되는지, 재생성 시점에 메모리 상태와 디스크 상태가 어긋나는 창이 있는지가 글에 없다.

kentonv가 다른 답에서 저장을 다루는 것이 가볍게 여기지 않는 큰 책임이며 제대로 하는 것이 결정적으로 중요해서 신중히 하고 있다고 적었지만,[^kentonv-throughput] 그 신중함이 외부 검증으로 이어지지는 않았다.

### CRDT를 물리치는 논증이 실제 쟁점을 비껴간다

Q&A의 CRDT 절이 글에서 가장 단호한 부분이면서 가장 약한 논증이다.

주장은 세 가지다. CRDT를 올바르게 적용하기 어렵고, 자동 충돌 해소가 가능한 자료 구조가 제한적이며, 대부분의 애플리케이션에서 지나치게 복잡하고 값을 하지 못한다는 것이다.

앞의 둘은 사실이다. 세 번째는 판단이고, 그 판단의 근거가 제시되지 않는다.

더 중요한 것은 **비교 축이 어긋나 있다**는 점이다.

CRDT를 쓰는 주된 이유가 “충돌 해소가 자동이라 편해서”가 아니다. **네트워크 분단과 오프라인 동작을 견디기 위해서**다.
클라이언트가 서버에 닿지 못하는 동안에도 로컬에서 편집하고 나중에 병합할 수 있다는 것이 핵심 가치다.

Durable Objects의 단일 권위 조율 지점은 그 성질을 원리적으로 가질 수 없다.
객체가 한 곳에만 존재하므로 그 객체에 닿지 못하면 쓰기가 불가능하다.

글은 이 차이를 다루지 않는다. 복잡도만 비교하고 가용성 모델은 비교하지 않는다.

그리고 글 자신이 제시한 사례들이 이 공백을 드러낸다.
모바일 기기에서 쓰는 문서 편집기, IoT 기기 조율, 게임 세션이 전부 연결이 끊기는 상황을 상정해야 하는 것들이다.

글이 CRDT를 Durable Objects 위에 올릴 수 있다고 덧붙이며 객체를 지역별로 여러 개로 복제해 CRDT로 동기화하는 그림을 제시하지만, 그것을 “최적화로서 필요하다고 판단되면 구현할 만한 것”이라고 부른다.
오프라인 지원이 최적화가 아니라 요구사항인 애플리케이션에게는 다른 이야기가 된다.

### 가격을 모른 채 설계하라고 권하는 셈이 된다

phn이 가격에 대한 언급을 찾을 수 없다며 일반 Workers $5/월 플랜에 포함되는지 물었다.[^phn]

kentonv는 베타 참가자에게 현재 무료이며 출시 후 가격이 어떻게 될지 아직 정하는 중이고, 사람들이 실제로 어떻게 쓰는지 보고 피드백을 받아야 올바른 가격 구조를 정할 수 있다는 것을 깨달았으며 그것이 베타의 목적이라고 답했다.[^kentonv-pricing]

Durable Objects PM인 greg-m이 더 구체적으로 답했다.[^greg-m-pricing]
비공개 베타의 일부로 크든 작든 모든 애플리케이션이 접근할 수 있도록 가격을 어떻게 매기는 것이 최선인지 피드백을 받고 있으며, 베타 동안 저장소 접근이 무료이지만 **베타를 벗어나면 기본 $5/월 플랜에 포함되지 않을 것**이라는 예상이다.
연산 요소와 저장 요소가 모두 있으므로 장기 가격 모델이 둘을 투명하고 경쟁력 있게 엮기를 원한다고 적었다.
그리고 베타를 벗어날 때 저장 비용이 AWS DynamoDB나 Google Cloud Firestore 같은 기존 서비스보다 쌀 것으로 예상해도 된다고 덧붙였다.

이 답변이 성실하지만 문제를 해소하지는 않는다.

이 제품이 요구하는 것은 **저장 모델의 재설계**다. 테이블을 객체로 쪼개고 논리 단위를 다시 잡으라는 것이다.
그런 변경은 되돌리기 비싸다.

그런데 가격이 정해지지 않은 상태다. 특히 객체 수가 비용에 어떻게 반영되는지가 미지수인데, 글은 수백만에서 수십억 개를 만들어도 문제없다고 권한다.
객체당 고정 비용이 있느냐 없느냐에 따라 “잘게 쪼개라”는 권고의 경제성이 정반대가 된다.

## 인사이트

### 저장 단위를 논리 단위에 맞추는 것이 일관성 문제를 설계 단계에서 없앤다

이 글의 마지막 논지가 기술 주장이 아니라 **설계 방법론**이고, 그것이 가장 오래갈 부분이다.

핵심은 이렇다. 분산 데이터베이스의 어려움 대부분이 **한 트랜잭션이 여러 물리 노드에 걸치기 때문**에 생긴다.
2단계 커밋도, 합의 프로토콜도, 격리 수준의 미묘함도 전부 그 문제에서 나온다.

그런데 애플리케이션의 논리 단위를 보면 한 트랜잭션이 여러 단위에 걸치는 경우가 생각보다 적다.
장바구니에 항목을 넣는 것은 그 장바구니 안의 일이고, 채팅 메시지를 보내는 것은 그 방 안의 일이며, 문서를 편집하는 것은 그 문서 안의 일이다.

그래서 **물리 저장 단위를 논리 단위와 일치시키면 분산 트랜잭션이 필요한 경우가 대부분 사라진다**.

이것이 샤딩과 다른 점이 중요하다.
asim이 이것이 샤딩 아니냐고 물었는데,[^asim] 부분적으로 맞다. 다만 샤딩은 보통 **용량 때문에** 나중에 도입하는 대응이고, 여기서는 **도메인 모델이 처음부터 경계를 정한다**.

샤딩 키를 정할 때 흔한 실패가 부하 분산과 트랜잭션 경계 중 하나를 골라야 하는 상황인데, 논리 단위로 쪼개면 그 둘이 대체로 일치한다. 인기 있는 채팅방은 부하도 크고 트랜잭션 경계도 그 방이다.

한계도 같은 자리에서 나온다. **여러 단위에 걸친 질의가 필요해지는 순간 이 모델이 답을 주지 않는다.**
agotterer가 객체를 가로질러 질의할 수 있는지, 예를 들어 특정 문자열이 쓰인 모든 객체 인스턴스를 찾을 수 있는지 물었는데[^agotterer] 글 자신이 각 객체가 자기 데이터만 볼 수 있다고 인정한다.

그래서 이 모델이 잘 맞는 애플리케이션의 조건이 분명해진다.
**쓰기가 단위 안에서 닫히고, 읽기 중 단위를 가로지르는 것은 별도 인덱스로 감당 가능한 경우**다.
그렇지 않으면 객체 위에 질의 계층을 직접 만들어야 하고, 그것이 글이 말한 “엣지 데이터베이스”를 스스로 만드는 일이다.

### 이식 불가능한 프리미티브가 생태계의 반작용을 만든다

이 모델의 매력이 곧 종속의 크기다.

kovek이 발표 당일 그 점을 물었다. 이것을 쓰려면 Cloudflare를 써야 한다는 뜻이냐며, 앞으로 이것이 더 표준적이 되어 자기 인프라에서 비슷한 것을 할 수 있을지 궁금하고 이미 어딘가 오픈소스로 그런 해법이 있을지 물었다.[^kovek]

발표 시점에는 답이 없었다. 그리고 이후 몇 년이 그 답을 만들었다.

[Rivet Kit이 Durable Objects의 오픈소스 대안](https://news.hada.io/topic?id=22459)으로 나왔고, [celld는 컨트롤 플레인도 합의도 없이 버킷만으로 조율하는 자가호스팅 Durable Objects](../distributed-system/celld.md)를 표방한다.

이 반작용의 패턴이 익숙하다.
독점 프리미티브가 충분히 유용하면 그것을 재구현하는 오픈소스가 따라오고, 그 재구현이 개념을 표준에 가깝게 만든다.

그런데 이 경우 재구현이 특히 어렵다. **Durable Objects의 보장이 Cloudflare 네트워크의 성질에 기대고 있기 때문**이다.
“전 세계에서 한 곳에만 존재한다”는 보장을 지키려면 전역 라우팅과 이전 메커니즘이 필요하고, 그것은 애플리케이션 계층에서 재현하기 어렵다.

그래서 대안들이 대체로 보장을 조금씩 바꾼다. celld가 합의 없이 버킷으로 조율한다는 것이 그런 조정이다.

여기서 나오는 판단 기준이 있다.
이 프리미티브에 의존해 설계할 때는 “어느 보장에 기대고 있는가”를 **명시해 두어야 한다**.
단일성에 기대는지, 지연 없는 메모리 상태에 기대는지, 트랜잭션 일관성에 기대는지에 따라 이전 가능한 대안이 달라진다.

### 자기 제품으로 자기 제품을 다시 만들겠다는 선언이 가장 강한 신호였다

Q&A에 한 문장이 조용히 들어 있다. 앞으로 Workers KV 구현 자체에 Durable Objects를 활용해 더 나은 성능을 제공할 계획이라는 것이다.

이 문장이 발표문에서 가장 자신 있는 부분이다.

새 프리미티브를 내놓으면서 **기존 자사 제품을 그 위에 다시 올리겠다**고 말하는 것은 두 가지를 동시에 주장한다.
그 프리미티브가 충분히 일반적이라는 것과, 자기들이 그것에 운영 부담을 걸 만큼 신뢰한다는 것이다.

그리고 6년이 지난 지금 이 예측을 채점할 수 있다.

D1이 Durable Objects의 트랜잭션 저장소 API 위에 만들어졌다.
글이 그린 “각 청크를 Durable Object로 저장하는 엣지 데이터베이스”가 외부 개발자가 아니라 **Cloudflare 자신에 의해** 먼저 실현된 셈이다.

[Containers 발표문](containers.md)도 상태 관리에 Durable Objects를 쓰라고 권하고, [Pages 풀스택 발표문](pages-goes-full-stack.md)의 바인딩 목록에도 Durable Object 네임스페이스가 들어 있다.

즉 이 제품은 사용자용 기능인 동시에 **플랫폼의 내부 기반**이 되었다.

여기서 일반화할 만한 관찰이 있다.
플랫폼이 내놓는 프리미티브의 수명은 **그 플랫폼이 그것을 내부적으로 쓰는지**로 상당 부분 예측된다.
내부에서 쓰이면 성능 개선과 버그 수정의 동기가 사용자 요구와 무관하게 유지되고, 쓰이지 않으면 사용자가 줄 때 함께 방치된다.

발표 시점에 이 신호를 읽을 수 있었다는 점이 흥미롭다.
“KV를 DO로 다시 구현하겠다”는 한 문장이 가격표도 성능 수치도 없던 그 시점에 이 제품의 지속성에 대한 가장 강한 근거였다.

### 조율 지점을 만드는 비용이 0에 가까워지면 아키텍처 선택이 바뀐다

발표문이 실시간 협업을 핵심 사례로 들면서 한 문장을 덧붙인다.
Durable Objects가 장벽을 낮추어 **실시간 협업이 웹 전반의 표준이 되기를 바라며, 이제 사용자에게 갱신을 위해 새로고침하게 만들 이유가 없다**는 것이다.

이 희망이 기술 주장이 아니라 경제 주장이다.

지금까지 실시간 협업이 큰 제품의 전유물이었던 이유가 어렵기 때문만은 아니다.
조율 서버를 상시 운영해야 하고, 그것이 상태를 가지므로 배포와 확장과 장애 조치를 직접 다뤄야 하며, 사용자가 적은 시간에도 비용이 든다.

Durable Objects는 그 셋을 모두 없앤다. 유휴 시 종료되고 필요할 때 재생성되며 위치가 자동으로 정해진다.

그래서 이 발표의 이차 효과는 “실시간 기능을 잘 만들 수 있게 되었다”가 아니라 **“실시간 기능을 만들지 않을 이유가 줄었다”**에 가깝다.

글이 든 예 중 가장 작은 것이 이 변화를 잘 보여 준다.
정적 콘텐츠 사이트가 개별 기사마다 별도 Durable Object로 조율해 댓글 위젯이나 라이브 채팅 위젯을 붙일 수 있다는 것이다.

이것이 이전에는 성립하지 않던 규모다. 기사 하나를 위해 조율 서버를 두는 것은 비용이 맞지 않았다.

그리고 이 변화가 사용자 기대를 바꾼다.
한 영역에서 실시간이 기본이 되면 인접 영역에서 새로고침이 결함으로 보이기 시작한다.

다만 이 낙관에 붙는 단서가 있다. **조율 지점을 만드는 비용이 낮아져도 협업 기능의 어려운 부분은 남는다**는 것이다.
충돌 해소, 실행 취소 의미론, 권한 모델, 오프라인 처리가 그것이고, 글이 CRDT를 물리치며 정리한 문제들이 바로 거기 있다.
인프라 장벽이 사라지면 그다음 장벽이 드러나는 것이지 사라지는 것이 아니다.
