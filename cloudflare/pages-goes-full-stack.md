# Cloudflare Pages가 풀스택이 된 날: 디렉터리 규약 하나로 Workers를 끌어들이다

원문: [Cloudflare Pages Goes Full Stack](https://blog.cloudflare.com/cloudflare-pages-goes-full-stack/)

HN 토론: <https://news.ycombinator.com/item?id=29253032> (350점, 123개 댓글)

## 요약

Nevi Shah, Glen Maddern, Cina Saffary가 2021년 11월 17일 “Full Stack Week”에 맞춰 쓴 발표문이다.

[2020년 12월 Pages 출시 발표](pages.md)의 마지막 약속 — 앞으로 몇 달에 걸쳐 Workers와 Pages를 매끄러운 경험으로 통합하겠다는 것 — 이 실제로 구현된 결과물이다.

글이 그 연속성을 첫 문단에서 명시한다.
4월에 Pages를 정식 출시하며 이제 시작일 뿐이라고 약속했고, 플랫폼의 여정이 리다이렉트와 커스텀 헤더 설정 같은 작은 동적 기능을 가진 정적 사이트 지원에서 시작했다는 것이다.

그리고 그린 미래가 이렇다.
**프런트엔드, API, 스토리지, 데이터를 포함한 애플리케이션 전체가 커밋 하나로 배포되고, 스테이징에서 쉽게 테스트되며, 병합 한 번으로 프로덕션에 배포되는 것**이다.

### 동작 방식

기존 워크플로가 그대로 유지된다는 점을 강조한다.
코드를 쓰고 Git 제공자에 푸시하면(이제 GitLab도 지원한다고 함께 발표) 사이트 전체를 배포해 주는데, 다른 점은 프런트엔드만이 아니라 백엔드도 Cloudflare Workers로 서버리스 함수를 배포한다는 것이다.

메커니즘이 단순하다. **저장소의 파일시스템 규약**과 **함수 핸들러 익스포트**다.

프로젝트 루트에 `./functions` 디렉터리를 만들고, 그 안의 JavaScript나 TypeScript 파일에서 함수 핸들러를 익스포트한다.

```javascript
// /filename으로 오는 GET 요청은 "Hello, world!"를 반환한다
export const onRequestGet = () => {
  return new Response("Hello, world!")
}

// JSON 본문을 가진 POST 요청은 "Hello, <name>!"을 반환한다
export const onRequestPost = async ({ request }) => {
  const { name } = await request.json()
  return new Response(`Hello, ${name}!`)
}
```

커밋하면 새 Pages 빌드가 촉발되어 동적 사이트가 배포된다.
빌드 파이프라인에서 Pages가 디렉터리를 순회하며 파일명을 저장소 구조에 상대적인 URL로 매핑한다.

내부적으로는 Pages가 소스의 라우팅과 기능을 전부 포함하는 Workers를 생성한다.
깊이 중첩된 라우트, 와일드카드 매칭, 인증과 오류 처리 같은 것을 위한 미들웨어를 지원한다고 적는다.

### 바인딩

풀스택 애플리케이션을 만드는 큰 부분이 바인딩이라며, 기존 Workers에서 쓰던 바인딩을 Pages로 가져온다고 밝힌다.

| 바인딩                      | 내용                                                                          |
| --------------------------- | ----------------------------------------------------------------------------- |
| KV 네임스페이스             | 서버리스 전역 키-값 저장소. Workers 대시보드에서 설정한 것을 연결             |
| Durable Object 네임스페이스 | 강한 일관성 조율 프리미티브. WebSocket 연결, 상태 처리, 전체 앱 구축용        |
| R2 (곧 제공)                | S3 호환 객체 스토리지. 이그레스 요금을 0으로 내리는 중                        |
| 환경 변수                   | 평문으로 저장되어 함수에서 접근 가능. 프로덕션·프리뷰 양쪽에 빌드·런타임 설정 |
| 시크릿 (곧 제공)            | 암호화된 환경 변수. wrangler나 대시보드에서 볼 수 없음                        |

R2와 시크릿이 “곧 제공”으로 표시되어 있다는 점이 이 발표의 시점을 말해 준다.

### 프리뷰와 로컬 개발

정적 사이트에서 제공하던 협업·테스트 경험이 백엔드에도 적용된다.
프로덕션 배포 전에 프리뷰 환경에 배포해 변경을 스테이징할 수 있고, 커밋마다 고유 URL을 가진 버전 이력이 유지되며, 최신 변경에 대한 일관된 URL과 함께 무한 스테이징 권한이 그대로 주어진다.

다만 작은 변경마다 빌드하고 배포하는 것이 번거로울 수 있다는 점을 인정하고, wrangler CLI 최신 릴리스로 풀스택 Pages 애플리케이션을 로컬에서 개발할 수 있게 했다고 밝힌다.

Miniflare가 그 기반이며, 모의 시크릿·환경 변수·KV를 지원하는 상태로 애플리케이션 전체를 로컬에서 돌릴 수 있다. Durable Objects 지원은 “곧”이다.

```bash
# wrangler v2 베타 설치
npm install wrangler@beta

# 정적 자산 폴더를 서빙
npx wrangler pages dev ./dist

# 또는 기존 도구를 자동으로 프록시
npx wrangler pages dev -- npx react-scripts start
```

### 할 수 있게 된 것들

**오늘날 HTTP Workers로 할 수 있는 모든 것**이라고 적는다.
함수를 가진 Pages 애플리케이션을 배포할 때 Pages가 사용자를 대신해 1급 Workers를 컴파일하고 배포하므로, Pages 애플리케이션 안에 Worker를 배포할 때 기능 손실이 전혀 없다는 것이다.

**SvelteKit 기본 지원**이 프레임워크 쪽 첫 사례다.
SvelteKit 프로젝트가 `@sveltejs/adapter-cloudflare` 패키지를 붙여 설정하면 Pages에 추가해 바로 배포할 수 있으며, API 엔드포인트와 완전한 서버 사이드 렌더링을 함께 배포한다.
API 엔드포인트를 포함한 프로젝트 전체가 프리뷰 배포의 혜택을 받는다는 점도 짚는다.

**서버 사이드 렌더링**의 이점을 구체적 예로 설명한다.
상품 페이지를 가진 애플리케이션이 `product/[id].js` 파일 하나를 정의해 `id` 파라미터를 받고, Workers KV 바인딩에서 상품 정보를 가져와 그 페이지의 HTML 응답을 생성할 수 있다.
정적 사이트 생성기 방식과 비교하면 더 간결하고 유지보수가 쉬운데, **빌드 시점에 상품마다 정적 HTML 페이지를 만들지 않아도 되기 때문**이라는 것이다. 수만에서 수십만 페이지가 될 수 있다.

**이미 Worker가 있는 경우**를 위한 탈출구도 제공한다.
빌드가 프로젝트 출력 디렉터리에 `_worker.js`라는 ES 모듈 Worker를 생성하게 하고 커밋하면 나머지는 알아서 처리한다는 것이다.
프레임워크 작성자이거나 제공된 파일 구조를 따르지 않는 복잡한 사용 사례에 유리하다고 적는다.

### 가격과 로드맵

오픈 베타로 출시하며 Cloudflare 요금제에 추가 비용 없이 누구나 써 볼 수 있게 한다고 밝힌다.
제한은 여전히 있지만, 이 오픈 베타 기간을 팀들이 Pages 프로젝트에서 함수를 어떻게 배포하는지 배우는 데 쓰겠다는 것이다.
당분간 청구 걱정 없이 창의성에 기대라고 권한다.

그리고 **몇 달 뒤 정식 출시를 발표할 때 청구가 Workers Bundled 요금제를 반영할 것**이라고 미리 알린다. 결국 내부적으로는 그냥 Workers이기 때문이라는 것이다.

앞으로의 계획도 나열한다.
통합 로깅과 배포된 함수에 대한 더 많은 분석을 더해 개발자 경험을 개선하겠다는 것이다.

프레임워크 쪽 로드맵이 특히 구체적이다.
SvelteKit에서 보였듯 정적 코드와 동적 코드를 함께 매끄럽게 배포하는 Pages의 능력이 최종 사용자 성능과 개발자 편의를 동시에 준다며, **NextJS, NuxtJS, React Server Components, Remix, Hydrogen** 같은 프레임워크와 기술의 팬들에게 계속 지켜보라고 적는다.
NextJS, NuxtJS, React Server Components, Shopify Hydrogen 등이 매끄럽게 통합되도록 작업이 진행 중이라는 것이다.

마지막으로 빌드 시간을 줄이는 작업을 하고 있다고 덧붙인다.

## 분석

### 파일시스템 규약을 고른 것이 이 발표의 실질적 결정이다

기술적으로 새로운 것은 없다. Workers는 이미 있었고 Pages도 이미 있었으며, 글 자체가 이전에도 Wrangler를 설치해 Worker를 수동 배포하면 둘을 연결할 수 있었다고 인정한다.

바뀐 것은 **연결 방식**이다.
“가능했다”에서 “두 번 생각하지 않아도 되는 것”으로 만들고 싶었다는 문장이 그 의도를 정확히 적는다.

그리고 그 수단으로 고른 것이 `./functions` 디렉터리 규약이다.

이 선택이 중요한 이유가 있다.
설정 파일이 아니라 디렉터리 구조를 계약으로 삼으면 **배포 대상이 저장소를 보는 것만으로 결정된다**. 별도의 선언이 필요 없고, 코드 위치가 곧 라우트가 된다.

Next.js의 `pages/` 디렉터리가 이미 검증한 패턴이고, 이 발표가 그것을 서버리스 함수로 옮긴 것이다.

다만 규약 기반 설계에는 대가가 있다.
HN에서 locusofself가 그 대목을 짚었다.[^locusofself]
저장소의 파일시스템 규약을 사용하고 함수 핸들러를 하나 이상 익스포트하면 Pages가 Workers를 활용해 서버리스 함수를 배포해 준다는 문장이, 필요 이상으로 훨씬 혼란스럽다는 것이다.

규약은 알고 나면 단순하지만 처음 읽는 사람에게는 설명하기 어렵다.
글이 그 설명을 한 문장에 압축하려다 실패한 것이고, 바로 다음에 나오는 코드 예제가 그 문장보다 훨씬 잘 설명한다.

### `_worker.js` 탈출구가 규약의 한계를 인정한 설계다

발표문에서 눈에 덜 띄지만 구조적으로 중요한 것이 `_worker.js`다.

`./functions` 규약이 라우팅을 파일 구조에 위임하는데, 그 구조가 맞지 않는 경우가 있다.
프레임워크가 자체 라우터를 갖고 있거나, 빌드 산출물의 모양을 프레임워크가 정하는 경우다.

그래서 출력 디렉터리에 ES 모듈 Worker 하나를 놓으면 그것을 통째로 쓰게 했다.
글이 이 기능의 대상을 명시한다. **프레임워크 작성자와 제공된 파일 구조를 따르지 않는 복잡한 사용 사례**다.

이 두 경로의 공존이 플랫폼 설계의 한 패턴을 보여 준다.
**규약은 다수의 편의를 위해 두고, 규약을 벗어나야 하는 소수를 위해 한 단계 낮은 인터페이스를 노출하는 것**이다.

그리고 실제로 후자가 프레임워크 어댑터 생태계의 토대가 되었다.
SvelteKit 어댑터가 하는 일이 결국 SvelteKit의 빌드 산출물을 Pages가 이해하는 형태로 내놓는 것이기 때문이다.

### 발표 타이밍이 경쟁 구도를 드러낸다

이 발표가 놓인 하루가 흥미롭다.

HN에서 redm이 그날 첫 페이지 목록을 옮겼다.[^redm]
Netlify가 1억 500만 달러를 유치했다는 소식, Netlify가 OneGraph를 인수했다는 소식, 그리고 Cloudflare Pages가 풀스택이 되었다는 소식이 같은 날 올라와 있었다는 것이다.
뉴스 사이클이 어떻게 흘러가는지 흥미롭고 이게 어떻게 전개될지 보는 것도 흥미롭겠다고 적었다.

같은 날 두 회사가 정반대 전략을 발표한 셈이다. 한쪽은 자본을 모으고 인수했고, 다른 쪽은 기존 자산을 결합했다.

destitude가 구조적 우위를 짚었다.[^destitude]
Cloudflare가 CDN과 곧 나올 이그레스 요금 “없는” 내장 객체 스토리지 때문에 우위에 있을 것 같으며, 그것과 경쟁하기는 어려울 것이라는 예상이다.

Thorentis는 인수를 예측했다. 이 제품이 Netlify와 상당히 가깝거나 완전히 직접 경쟁하는 지점에 왔으므로 Cloudflare가 가까운 미래에 Netlify 인수를 시도할 것 같다는 것이다.[^Thorentis]

neom이 반박했다.[^neom]
Netlify가 너무 크고 많은 돈을 모았으며 상장사가 되면 조직 부채를 다루는 것만으로도 충분히 어렵다는 것이다.
그리고 흥미로운 사실을 덧붙였다. Netlify가 Linc라는 작은 스타트업을 인수했고 그들의 CTO인 Glen Maddern이 **이 블로그 글의 엔지니어**라는 것이다.
Cloudflare가 그 두 스타트업의 밸류에이션을 자기 시가총액에 유기적으로 더하려 하는 편이 더 말이 된다고 봤다.

youngtaff도 같은 결론을 냈다. Cloudflare가 이미 더 나은 방문자 경험을 제공하는 더 나은 기술 스택을 갖고 있으며, Netlify는 Apache Traffic Server에 이것저것 감싼 것이고 이렇다 할 CDN이 없으며 기능도 제한적이라는 것이다.[^youngtaff]

결과적으로 이 예측들이 맞았다. Cloudflare는 Netlify를 인수하지 않았고 자체 제품군을 확장했다.

### SvelteKit을 첫 프레임워크로 고른 것이 전략적이었다

발표문이 SvelteKit만 실제 지원으로 내놓고 나머지는 로드맵에 올렸다.

seeekr가 이 선택에 반응했다.[^seeekr]
Svelte(Kit)를 직접 지원하는 첫 프레임워크로 삼은 것을 보는 게 꽤 멋지며, 최근 Vercel에 새 애플리케이션을 배포했지만 Cloudflare가 동등하거나 더 매력적인 선택지가 될 때를 매우 기대한다는 것이다.

camgunz는 반대 방향의 효과를 봤다. SvelteKit 기본 지원이 Svelte에게 엄청난 일이며 채택 급증의 문턱에 있는지 궁금하다는 것이다.[^camgunz]

그런데 같은 주에 반대되는 사건이 있었다.
jadbox가 그것을 짚었다. Svelte 창시자 Rich Harris가 그 주에 **Vercel에 합류했다**는 것이다.[^jadbox]

yumraj가 농담으로 정리했다. Cloudflare가 Vercel 대신 Rich Harris를 고용했어야 한다는 것이다.[^yumraj]

이 타이밍이 플랫폼-프레임워크 관계의 성격을 보여 준다.
플랫폼이 프레임워크를 지원하는 것과 프레임워크를 후원하는 것이 다르고, 후자가 더 강한 결합을 만든다.

Cloudflare는 어댑터를 지원했고 Vercel은 메인테이너를 고용했다.
그리고 이후 Next.js–Vercel, SvelteKit–Vercel 관계가 이 구도의 연장선에서 전개되었다.

한편 이 발표의 프레임워크 로드맵을 지금 돌아보면 성적이 엇갈린다.
NextJS, NuxtJS, React Server Components, Remix, Hydrogen을 모두 약속했는데, 그중 Next.js 지원이 가장 오래 그리고 가장 어렵게 진행되었다.
`@cloudflare/next-on-pages` 같은 별도 어댑터가 필요했고, Node.js 런타임 기능과 Workers 런타임의 간극이 반복해서 문제가 되었다.

이 어려움의 원인이 이 발표문 자체에 암시되어 있다.
“오늘날 HTTP Workers로 할 수 있는 모든 것”이라는 문장이 능력의 상한을 정하는데, Next.js가 기대하는 것은 Node.js 환경이지 Workers 런타임이 아니다.

technobabbler가 발표 당일 정확히 그 요구를 제기했다.[^technobabbler]
Next.js에 대한 드롭인 지원 계획이 있느냐고 물으며, 정적 빌드만이 아니라 Vercel처럼 백엔드 서버와 서버리스 함수까지 어쩌면 특정 API를 Workers에 매핑하는 식으로 지원할 수 있겠느냐는 것이다.
그리고 이유를 밝혔다. Next 같은 프레임워크가 “서버리스라는 아이디어는 좋지만 백엔드 전체를 처음부터 다시 만들고 싶지는 않다”는 문제를 푼다는 것이며, 라우팅·캐싱·무효화·빌드체인·이미지 변환 같은 문제를 프레임워크가 추상화해 주는 게 좋다는 것이다.
Cloudflare Pages와 Workers가 거의 같은 것을 할 수 있지만 더 많은 코딩과 설정을 요구한다는 것이 유일한 차이라고 적었다.

## 비평

### “몇 달 뒤 Workers 요금제”라는 예고가 무엇을 뜻하는지 흐리게 적혔다

가격 절이 이 발표문에서 가장 조심스럽게 쓰인 부분이다.

오픈 베타 동안 추가 비용이 없고 청구 걱정 없이 만들라고 권하면서, 몇 달 뒤 정식 출시 때 청구가 Workers Bundled 요금제를 반영할 것이라고 적는다.

문제는 그 전환이 기존 Pages 사용자에게 무엇을 의미하는지가 설명되지 않는다는 점이다.
Pages의 정적 호스팅은 무제한 대역폭이 핵심 매력이었는데, 함수를 쓰기 시작하면 요청 단위 과금이 붙는다.

발표문은 두 모델이 어떻게 공존하는지, 정적 요청과 함수 요청이 어떻게 구분되는지, 미들웨어를 전역으로 걸면 모든 요청이 함수 요청이 되는지를 다루지 않는다.

마지막 쟁점이 특히 실질적이다.
글이 인증과 오류 처리를 위한 미들웨어를 지원한다고 자랑하는데, 미들웨어를 루트에 걸면 정적 자산 요청도 Worker를 거치게 된다.
그러면 “무제한 대역폭 정적 호스팅”의 경제성이 통째로 바뀐다.

getcrunk가 관련 질문을 남겼지만 답을 얻지 못했다. 무제한 대역폭은 어떻게 되는 것이며 10~100TB 넘게 밀어 넣는 사람이 있느냐는 것이다.[^getcrunk]

이 공백이 무료 베타 기간에는 문제가 되지 않지만, 베타 기간이 바로 아키텍처 결정이 내려지는 시기라는 점이 문제다.
글 자신이 창의성에 기대라고 권하는데, 가격 모델을 모르는 채 내린 구조 결정은 나중에 비싸게 청구된다.

### Git 푸시 외의 배포 경로가 없다

이 발표의 워크플로가 전적으로 Git 제공자에 묶여 있다.

zapita가 그 제약을 물었다.[^zapita]
GitHub이나 GitLab에서 끌어오게 하는 대신 Pages에 콘텐츠를 직접 푸시할 방법이 있느냐는 것이며, 많은 팀이 기존 Git 통합을 갖춘 자체 배포 도구를 갖고 있어 거기에 Pages 타깃을 추가하는 편을 선호한다는 것이다.
Netlify는 GitHub 풀 기능을 우회하게 해 주는데 Cloudflare도 그러느냐고 물었다.

`888666`이 짧게 답했다. **그렇지 않다**는 것이다.[^888666]

lucasyvas가 이 문제의 일반적 형태를 정리했다.[^lucasyvas-deploy]
개인적으로 원한다면 별도의 배포 명령이 있는 쪽을 선호하는데, 외부 CI 시스템을 더 쉽게 쓸 수 있게 해 주기 때문이며, Git으로만 동작해서 아예 제외한 앱 플랫폼이 여럿 있다는 것이다.

dvasdekis는 같은 문제를 인프라 관리 쪽에서 제기했다.[^dvasdekis]
Terraform 제공자에서 Pages 지원을 보고 싶으며 4월부터 열려 있는 이슈라는 것이고, 자기 조직이 모든 클라우드 구성 요소를 Terraform으로 완전히 옮겼기 때문에 Cloudflare Pages에 Terraform 지원이 없는 것은 도입 불가 사유라는 것이다.
데이터 웨어하우스 팀까지 완전히 Terraform으로 옮겼는데 정적 사이트 호스팅처럼 “웹스러운” 것이 간단한 사용 사례여야 한다고 적었다.

이 지적들이 [Pages 출시 발표 노트](pages.md)에서 다룬 GitLab 미지원 불만과 같은 계보에 있다.
1년 뒤 GitLab이 추가되었지만 **Git 없는 배포 경로**는 여전히 없었다.

그리고 이것이 단순한 기능 누락이 아니라 제품 철학의 결과다.
커밋 하나로 전체 애플리케이션을 배포한다는 서사가 Git을 진실 공급원으로 전제하기 때문이다.
그 서사가 강력한 만큼, 이미 다른 배포 파이프라인을 가진 조직을 배제한다.

### “기능 손실이 전혀 없다”는 주장이 검증되지 않은 채 제시된다

발표문이 강한 진술을 한다. Pages 애플리케이션 안에 Worker를 배포할 때 기능 손실이 전혀 없으며 새로 얻는 이점만 있다는 것이다.

그런데 같은 글에 그 진술과 충돌하는 단서가 여럿 있다.
R2와 시크릿이 “곧 제공”이고, 로컬 개발에서 Durable Objects 지원이 “곧”이며, 통합 로깅과 분석이 향후 계획이다.

즉 배포된 Worker의 런타임 기능은 같을지 몰라도 **운영 도구는 같지 않다**.

holonomically가 이 간극을 실무 관점에서 물었다.[^holonomically]
Cloudflare Pages와 Workers로 실제 프로덕션 워크로드를 돌리는 사람이 있는지 궁금하다며, 서버리스 제품을 시도할 때마다 성능과 디버깅 경험에 늘 실망했기 때문이라는 것이다.

newsbinator가 구체적 경험을 보고했다.[^newsbinator]
CORS와 전혀 무관한 로직 오류 때문에 Worker가 던지던 CORS 오류를 디버깅하느라 온종일 쓴 뒤 Cloudflare Workers를 포기했다는 것이다.
CORS 헤더를 이유 없이 조정하고 다시 테스트하는 데 쓸 수 있는 시간은 한정되어 있으며, Pages는 나을지 모르지만 Pages의 백엔드에서 Workers를 더는 건드리고 싶지 않다고 적었다.

이 보고가 발표문의 공백을 정확히 겨눈다.
런타임 기능 동등성은 주장되었지만 **오류가 났을 때 무엇을 볼 수 있는지**는 향후 계획으로 미뤄졌고, 서버리스 채택의 실제 장벽이 대체로 후자에 있다.

WORMS_EAT_WORMS이 holonomically에게 그런 댓글이라면 세부를 밝혀야 한다고 요구한 것도 타당하다.[^WORMS_EAT_WORMS]
다만 요구의 방향이 반대여야 했다. 기능 손실이 전혀 없다고 주장하는 쪽이 로깅과 디버깅 경로를 함께 제시했어야 한다.

### 데이터 계층의 공백이 발표문에서 다뤄지지 않는다

바인딩 목록이 KV, Durable Objects, R2, 환경 변수, 시크릿이다.

관계형 데이터베이스가 없다.

lucasyvas가 이 점을 짚었다.[^lucasyvas]
이 분야에서 큰 경쟁자가 되는 길에 잘 올라섰으며, 자기가 정말 기대하는 것은 이것과 맞물리는 사내의 더 전통적인 데이터 저장소 옵션이 나오는 것이라는 것이다.
이 모든 서비스로 구성된 풀스택 프리뷰 환경을 만들 수 있다면 대단할 것이며, 기본적으로 전역 가용하다는 점이 우위라고 적었다.

0xy도 같은 경계를 그렸다.[^0xy]
DevOps, 모니터링, 서버리스 백엔드, 파일 스토리지, 데이터 저장소, 프런트엔드 자산 서빙의 원스톱 상점에 정말 가까워졌으며, 사이드 프로젝트 하나를 옮기는 것이 이제 손에 닿는데 **Redis와 Postgres만은 당분간 AWS에 남겨야 한다**는 것이다.
데이터베이스나 pub/sub 같은 솔루션도 언젠가 올 거라고 예상했다.

rtcoms이 우회로를 제시했다. Postgres는 Supabase로 호스팅할 수 있고 Redis도 클라우드 서비스가 있다는 것이다.[^rtcoms]

이 교환이 당시 플랫폼의 실제 경계를 보여 준다.
“애플리케이션 전체를 커밋 하나로 배포한다”는 서사에서 **데이터가 빠져 있었다**.

발표문이 프런트엔드·API·스토리지·데이터를 함께 배포하는 미래를 첫 문단에서 그리는데, 정작 그 글이 제공하는 데이터 계층은 키-값과 객체 스토리지다.
관계형 데이터를 쓰는 대부분의 애플리케이션에게 이것은 완결된 스택이 아니다.

발표문이 이 공백을 인정하고 로드맵에 올렸다면 더 정직했을 것이다. 프레임워크 로드맵은 상세히 적으면서 데이터 계층은 언급하지 않는다.

## 인사이트

### 컴파일 타깃을 바꾸지 않고 진입 경로만 바꾼 것이 이 발표의 본질이다

이 발표에서 새로 만들어진 런타임이 없다.

Pages가 하는 일은 저장소를 읽어 Workers를 **생성**하는 것이고, 글이 그것을 명시한다. 내부적으로 라우팅과 기능을 전부 포함하는 Workers를 생성하며, 1급 Workers를 컴파일해 배포한다는 것이다.

즉 Pages Functions는 새 제품이 아니라 **Workers에 대한 컴파일러**다.

이 구조가 왜 영리한지는 유지 비용에서 드러난다.
새 실행 환경을 만들면 그것을 영원히 유지해야 하지만, 기존 런타임으로 컴파일하면 런타임 개선이 자동으로 상속된다.

그리고 이 구조가 이후 전개를 예고한다.
[Pages 출시 노트](pages.md)가 정리했듯 결국 Workers가 그릇이 되고 정적 자산이 그 기능 중 하나가 되었는데, 그 역전이 가능했던 이유가 처음부터 Pages의 산출물이 Workers였기 때문이다.

여기서 일반화할 만한 원칙이 나온다.
**새 사용자 경험을 만들 때 새 런타임을 만들지 말고 기존 런타임에 대한 컴파일 경로를 만들라는 것**이다.
그러면 나중에 둘을 합칠 때 데이터 이전이나 재구현 없이 진입점만 정리하면 된다.

이 관점에서 보면 `./functions` 규약과 `_worker.js` 탈출구가 같은 것의 두 표현이다. 둘 다 결국 같은 산출물을 만드는 서로 다른 소스 형식이다.

### 빌드 타임 생성에서 요청 시점 생성으로 옮겨 가는 전환점이었다

서버 사이드 렌더링 절에 있는 예시가 이 시기 웹 개발의 방향 전환을 압축한다.

상품 페이지 수만~수십만 개를 빌드 시점에 정적 HTML로 만들지 않고, `product/[id].js` 하나가 KV에서 데이터를 가져와 응답을 만든다는 것이다.

이것이 JAMstack 서사에 대한 실질적 수정이다.
Pages가 출시될 때 내건 깃발이 JAMstack이었고 그 핵심이 빌드 시점 사전 생성이었는데, 1년 만에 같은 제품이 요청 시점 생성을 권하고 있다.

빌드 시간 문제가 그 전환의 직접적 동인이다.
페이지가 수만 개면 빌드가 몇십 분이 되고, 상품 하나가 바뀌어도 전체를 다시 만들어야 한다.
발표문이 마지막에 빌드 시간을 줄이는 작업을 하고 있다고 적은 것이 같은 압력의 다른 표현이다.

그리고 엣지 컴퓨팅이 이 전환을 가능하게 한 조건이다.
요청 시점 생성이 중앙 서버에서 일어나면 지연이 문제인데, 사용자 근처 엣지에서 일어나면 정적 파일과 지연 차이가 크지 않다.

lewisjoe가 이 경제성 변화를 개인 개발자 관점에서 적었다.[^lewisjoe]
인디 소프트웨어 제작자로서 앱을 돌릴 괜찮은 클라우드 서버 구성에 50달러를 내야 하는 것이 답답하며, 5달러짜리 공유 VM이 있지만 부하를 감당할 괜찮은 램과 코어를 원하는데 4GB 램에 4코어가 50달러여서는 안 된다는 것이다.
WASM이 나왔을 때 이것이 저렴한 비용으로 쓸 수 있는 컴퓨팅 파워의 새 차원을 열 것이라고 알았지만 방법은 확실하지 않았는데 이제 알겠다며, Cloudflare가 Workers를 내놓고 그것을 활용해 다른 엣지에 저비용 컴퓨팅을 가져오는 놀라운 일을 하고 있다고 적었다.
운이 좋다면 클라우드 인프라가 아마존·마이크로소프트 같은 거대 기업의 손에 양극화되지 않고 예전처럼 저렴하게 유지되는 시대에 들어갈지도 모른다는 기대다.

5년 뒤 시점에서 이 기대의 성적은 엇갈린다.
엣지 컴퓨팅의 단가는 실제로 낮아졌지만, 그 공급자가 소수로 집중되었다는 점에서 양극화 우려는 해소되지 않았다.

### 한 제품의 확장이 인접 시장 전체의 압력이 된다

이 발표에 대한 반응에서 가장 많이 언급된 회사가 Cloudflare가 아니었다.

cloverich가 Heroku를 꺼냈다.[^cloverich]
Heroku가 가만히 앉아 모두가 자기를 지나쳐 가게 두는 것이 놀랍다는 것이며, Heroku가 여전히 확장 가능한 노력 0의 풀스택 애플리케이션을 위한 훌륭한 플랫폼인데 CDN 호스팅 정적 사이트가 필요해지는 순간 플랫폼 밖을 봐야 한다는 것이다.
둘이 서로의 자연스러운 연장이므로 미친 일이라고 적었다.

brundolf도 짧게 같은 말을 했다. 드디어 Heroku에서 옮길 때가 된 것 같다는 것이다.[^brundolf]

bloodyplonker22는 더 일반적인 패턴으로 정리했다.[^bloodyplonker22]
이런 회사들이 훌륭한 원트릭 포니이며, 훌륭한 제품 하나를 내놓고 그것이 거의 스스로 팔리다가 성장을 늘릴 새 보조 제품을 내놓지 못하는 지점에 이른다는 것이다.
그 시점에 외부 CEO를 앉히거나 대기업에 인수되며 똑똑한 사람들은 현금화하고 떠나고, Cloudflare 같은 더 작고 민첩한 회사가 결국 더 나아질 제품으로 시장 점유율을 완전히 가져간다는 것이다.
PagerDuty를 다른 예로 들었다.

dopeboy가 Heroku 쪽에 동의를 보탰다. Salesforce가 정말 방치했으며 Render 같은 직접 경쟁자에게서 더 나은 제품이 나오는 것을 보고 있다는 것이다.[^dopeboy]

이 반응들이 보여 주는 것이 있다.
Cloudflare가 발표한 것은 자사 두 제품의 통합인데, 독자들이 읽은 것은 **여러 인접 시장에 대한 동시 압력**이다.

정적 호스팅(Netlify), PaaS(Heroku), 프레임워크 호스팅(Vercel)이 각각 다른 시장인데, 하나의 플랫폼이 세 곳에 동시에 걸치면 각 시장의 전문 업체가 “여기만 잘하는 곳”이 된다.

여기서 나오는 구조적 관찰이 있다.
통합 플랫폼의 위협은 각 영역에서 최고가 되는 것이 아니라, **경계를 넘나드는 비용을 0으로 만드는 것**이다.
cloverich의 불만이 정확히 그것이다. Heroku가 풀스택을 잘하지만 CDN 정적 사이트를 붙이려면 플랫폼을 나가야 한다는 것.

haliskerbas가 반대편에서 같은 이점을 증언했다. 작은 프로젝트라면 HTML 파일 하나를 만들어 몇 분 만에 커스텀 도메인에 꽂는 것이 너무 쉽고 유연성도 크다는 것이다.[^haliskerbas]

그리고 그가 남긴 바람 — 무료 티어가 지금처럼 좋게 유지되기를 바란다는 것 — 이 이 모델의 지속 가능성 질문을 요약한다.
경계를 넘나드는 비용을 0으로 만드는 전략은 각 경계에서 수익을 포기하는 것을 전제하는데, 그 포기가 언제까지 가능한지가 정해져 있지 않다.

### 서버리스 회의론이 5년째 같은 형태로 반복된다

EGreg가 이 스레드에서 가장 근본적인 반론을 냈다.[^EGreg]

이들이 부르는 “서버리스”의 요점을 모르겠으며 그것이 실제로는 서버이자 중앙화된 클라우드이고, 기껏해야 API 표면적을 제한하는 공통 컴파일 타깃을 갖는 정도의 의미라는 것이다.
문자 그대로 스택에 대해 훨씬 더 많은 것을 통제하면서 MySQL이든 외부 API든 원하는 것을 할 수 있고 자기 서버를 CDN의 오리진 서버로 쓸 수 있다는 것이다.
평범한 PHP 사이트를 가져와 “세션 의존적” 부분을 별도 서비스로 분리하면 나머지는 캐시 가능한 정적 리소스라고 적었다.

이 반론의 구조가 흥미롭다. **서버리스가 제공하는 것이 새 능력이 아니라 제약**이라는 지적이기 때문이다.

그리고 그 지적이 부분적으로 옳다.
이 발표문이 자랑하는 것 중 순수하게 새로운 능력은 거의 없다. SSR도, 라우팅도, 미들웨어도 기존 서버에서 다 하던 것이다.

새로운 것은 **운영 부담의 위치**다.
서버를 프로비저닝하고 스케일링하고 패치하는 일이 사라지고, 대신 런타임의 제약을 받아들여야 한다.

그래서 이 논쟁이 결론에 이르지 못하는 이유도 분명하다.
운영 부담이 큰 조직에게는 제약이 값싼 대가이고, 운영 역량이 이미 있는 조직에게는 제약이 순손실이다.

주목할 점은 이 반론이 2021년에 나왔고 지금도 같은 형태로 반복된다는 것이다.
그동안 바뀐 것은 제약의 내용이다. 당시 Workers 런타임이 Node.js API를 거의 지원하지 않았고, 이후 호환성 계층이 계속 넓어졌다.

즉 서버리스 논쟁의 실제 전선은 “서버리스가 좋은가”가 아니라 **“제약이 얼마나 빨리 줄어드는가”**다.
그리고 그 속도를 결정하는 것이 이 발표문이 약속한 것과 같은 종류의 통합 작업이다.
