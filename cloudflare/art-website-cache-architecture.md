# Kshitij Lauria의 예술 웹사이트 구조

원문: [I'm quite pleased by the tech architecture of my art website](https://klauria.tech/klauria-art/)

HN 토론: <https://news.ycombinator.com/item?id=50577991> (185점, 38개 댓글)

GN 토론: <https://news.hada.io/topic?id=37607>

## 요약

소프트웨어 개발자 Kshitij Lauria가 자기 그림과 스케치북 쪽을 올린 웹사이트의
기술 구조를 설명한 글이다.
글 안에 그 사이트의 지도, 타임라인, 작품 페이지가 대화형 위젯으로 끼워져 있다.
글은 LLM 사용 공개로 마무리하며 시스템 설계는 자신의 것이고
사이트 코드는 LLM으로 썼다고 밝힌다.

글의 흐름은 다음과 같다.

- 문제: 올해 그림 일부를 온라인에 올리려 했다.
  친구와 가족에게 단체 채팅방으로 스캔본을 보내 왔는데 정리되지 않았고,
  어디서 그렸는지 묻는 사람이 있었다. 동생이 작품마다 표식이 있는 지도를 제안했다.
- 두 마음: 쓰는 도구를 가장 가까운 것으로 때우자는 실용의 늑대와,
  내용이 거의 바뀌지 않으니 정적 사이트여야 한다는 미학의 늑대가 있다.
  하루에 많아야 네 점, 평균 0.3점 미만을 올리므로 미학의 늑대가 이겼다.
- 새 문제: 정적 사이트는 글마다 파일을 추가하고 빌드와 배포를 해야 한다.
  태그와 위치를 정하는 화면은 웹 UI가 가장 좋은데 그러면 정적이지 않게 된다.
  그래서 남에게는 정적이고 자기에게는 동적인 사이트를 원했다.
- 해법: 모든 HTML 페이지를 서버에서 그리되 Cloudflare가 응답을 30일 동안 캐시하도록
  헤더를 붙인다. 작품 업로드나 태그 변경 같은 쓰기 요청이 오면
  요청 처리기가 캐시된 모든 페이지를 무효화한다.
- 이미지: 업로드할 때 작은 크기를 세 가지로 만든다.
  업로더가 자신뿐이므로 이 일을 자기 브라우저에서 하고,
  원본과 함께 Cloudflare의 S3 호환 저장소 R2에 올린다.
  Cloudflare의 이미지 서비스는 처음 요청할 때 크기를 바꾸지만,
  필요한 크기를 이미 알아서 미리 계산했다고 한다.
- 메타데이터: 모든 작품의 정보를 R2의 JSON 파일 하나에 둔다.
  동적 HTML 페이지를 요청하면 Cloudflare Worker가 이 JSON을 읽어 HTML을 만들고
  다음 무효화까지 캐시된다.
- 대화형 요소: 지도와 타임라인은 클라이언트에서 도는 자바스크립트로,
  그 JSON 하나를 읽어 초기화하고 서버에 아무것도 쓰지 않아 데이터베이스가 없다.
- 전체 무효화: 편집이 영향을 주는 페이지만 무효화하는 최적화가 가능하지만,
  의존 관계가 어디에도 적혀 있지 않아 틀리면 절반만 갱신된 사이트라는
  정확성 버그가 생기므로 전부 무효화하기로 했다.
- 비용: 계산과 대역폭은 무료이고 저장소는 현재 무료이며 10GB 무료 구간을 넘으면
  한 달 몇 센트를 낸다. 프레임워크는 Cloudflare가 인수한 Astro인데
  꼭 필요하지는 않고 핵심은 캐시 관리라고 한다.

## 분석

### 정적과 동적 사이의 선택

글의 핵심은 새 기술이 아니라 두 속성을 분리한 것이다.
읽는 사람에게는 캐시된 응답(정적처럼 빠르고 저렴)을 주고,
쓰는 사람에게는 웹 UI(동적)를 준다.
이 방식의 비용은 쓰기가 일어날 때마다 모든 페이지가 다시 만들어진다는 것이며,
글은 올리는 빈도가 낮다는 사실로 이를 정당화한다.
적용 조건은 글이 직접 쓴 것처럼 쓰기가 드물고 읽기가 많은 사이트이다.

### 전체 무효화의 판단

글은 최적화를 하지 않은 이유를 올바름의 위험으로 든다.
빌드 시스템은 의존을 명시해 필요한 것만 다시 만들지만
이 사이트는 의존이 코드에 숨어 있다.
잘못된 의존 선언의 결과가 구식 페이지가 섞이는 것이라는 점을 감안하면
쓰기 빈도가 낮은 곳에서 단순한 규칙을 고른 판단이다.

## 비평

### 정적 사이트인가

HN의 cowlevel은 이것이 정적이 아니라 서버 사이드 렌더링(SSR)이라고 짚었다.
필자는 페이지가 처음 방문할 때 서버에서 그려지고 다음 변경까지 거의 영원히 캐시되므로
정적 사이트의 비용과 성능 특성을 가진다고 답했다.[^cowlevel][^articulatepang]
killingtime74는 이미 여러 프레임워크가 지원하는 서버 렌더링 페이지를 발견한 것이라고 했다.[^killingtime74]
글은 새로움을 주장하지 않고 자신에게 효율적인 해법이라고 쓰며,
이 비판은 글의 주장과 충돌하지 않는다.

### 새로운 방식인가

jrm4는 20년쯤 정적 사이트를 써 왔고 이것이 왜 표준이 되지 않았는지 의아하다고 했다.[^jrm4]
chrisweekly는 Jamstack, 정적 사이트 생성기가 이미 표준이라고 반박했다.[^chrisweekly]
mikeryan은 1999년에 만든 CMS 사례를 들었다. URL 끝에 내용 ID, 템플릿 ID,
캐시 우회 표시가 있고 정적 페이지를 먼저 찾아 없으면 조립해 캐시하는 방식이었다.[^mikeryan]
이 오래된 패턴과 글의 방식이 어디까지 같은지는 이 문서가 확인하지 못했다.

### 비슷한 요구와 대안

nicbou는 Cloudflare Pages의 정적 사이트에 트윗처럼 쉽게 짧은 글을 올리고 싶고,
서버에 POST를 커밋으로 바꾸는 도구를 두는 방법이 복잡하다고 했다.[^nicbou]
이 문제는 글의 접근과 같은 계열이다.
ricardobeat는 bunny.net이 CDN, 이미지 크기 변환, 엣지 함수, CLI를 갖추었고
월 평균 0.22달러가 든다고 했다.[^ricardobeat]
이는 댓글의 경험이며 이 문서는 확인하지 못했다.

### 접근성

zelphirkalt는 스크립트를 막은 상태에서도 방문해 결함이 없었다고 했다.[^zelphirkalt]
이는 글이 서버에서 HTML을 그리는 구조의 효과이다.

### LLM 사용의 의미

zzzeek은 이 글이 실제 물리 매체로 작업하는 시각 예술가가
LLM으로 웹사이트 구조를 만든 사례로 보여 놀랐다고 했고,[^zzzeek]
필자는 자신이 전문 시각 예술가가 아니라 소프트웨어 개발자이며
그림은 취미로 그린다고 정정했다.[^articulatepang-artist]
글은 설계는 자기 것이고 코드는 LLM이 썼다고 밝혔고, 코드의 품질은 이 문서가 확인하지 못했다.

## 인사이트

### 글에서 가져갈 것

읽는 쪽의 비용과 쓰는 쪽의 편의를 따로 최적화할 수 있다는 점이 가장 쓸모가 있다.
캐시 헤더와 전체 무효화라는 두 장치만으로 서버를 두면서도 정적 사이트의 비용 구조를 얻는다.
단, 쓰기 빈도가 높거나 페이지 수가 커서 전체를 다시 그리는 비용이 커지면
글이 의도적으로 건너뛴 부분 무효화가 필요해진다.

### 확인할 관찰

1. 작품 수가 늘어 전체 무효화 후 첫 요청의 지연이 체감되는지.
2. 무료 구간(저장소 10GB)을 넘기는 시점과 이후 비용.
3. 글이 밝힌 의존 선언 없는 구조가 갱신 누락을 일으킨 적이 있는지.

위 셋 모두 이 문서가 확인하지 못했다.
