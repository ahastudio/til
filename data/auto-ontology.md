# NVIDIA Auto Ontology: 데이터의 의미를 먼저 정의해 에이전트의 틀린 숫자를 막으려는 계층

<https://github.com/NVIDIA/auto-ontology>

HN 토론: <https://news.ycombinator.com/item?id=50348962> (288점, 138개 댓글)

GN 토론: <https://news.hada.io/topic?id=36528>

## 소개

NVIDIA는 Auto Ontology를 기업 메타데이터로 컨텍스트 계층(context layer)을 만들어
주는 오픈 라이브러리라고 소개한다.
이 계층은 에이전트에게 데이터가 어디에 있고 무엇을 뜻하는지, 써도 되는지,
어떻게 쓰는지,
어디서 왔는지, 무엇과 비슷한지를 알려 주는 역할이다.
NVIDIA가 내세우는 문제의식은 에이전트의 신뢰성이 에이전트 기반 분석을
가로막는다는 것이다.
매출 지표에 빨리 답해도 숫자가 틀리면 가치가 없다는 설명이다.
GitHub 저장소 설명문은 이 프로젝트를 데이터 위에 의미 기반의 그래프형 추론
계층을 만드는 Python 프레임워크라고 부르고,
결정적인(deterministic) 질의 생성과 더 나은 컨텍스트 검색을 약속한다.
라이선스는 Apache-2.0이고, 내가 GitHub API로 확인한 2026년 11월 5일 기준으로
2026년 4월 27일에 만들어졌고 별이 6,378개이며 기본 브랜치의 가장 최근 커밋은
11월 4일이다.
NVIDIA는 외부 풀 리퀘스트는 받지 않고 통합 요청과 버그 보고만 이슈로
받는다고 밝힌다.

### 다섯 가지 역할

NVIDIA는 이 도구가 개발자에게 다섯 가지를 가능하게 한다고 적는다.

| 역할     | NVIDIA의 설명                                                                 |
| -------- | ----------------------------------------------------------------------------- |
| Discover | 메타데이터에서 기업 온톨로지를 만들고 기존 온톨로지와 시맨틱 모델을 연결한다  |
| Ground   | 지표, 엔티티, 관계에 신뢰할 수 있는 업무 의미를 주고 시스템 간 정의를 맞춘다  |
| Validate | 생성된 질의를 인증된 정의와 계보(lineage)에 견주어 확인하고 출처를 함께 준다  |
| Expose   | MCP, CLI, API로 어떤 에이전트 harness에도 컨텍스트를 제공한다                 |
| Learn    | 인증된 수정과 사용 기록을 온톨로지에 되먹여 질문마다 공유 컨텍스트를 개선한다 |

NVIDIA는 이 도구가 고객이 이미 가진 시맨틱 모델을 대체하지 않고 보완한다고
설명한다.
Apache Ossie와의 호환도 제공한다.
Ossie의 NVIDIA용 변환기를 통해 모델 정의를 Ossie YAML로 가져오고 내보낼 수 있다.
Ossie 자체는 [Apache Ossie 문서](apache-ossie.md)에서 다룬다.

### 온톨로지가 담는 것과 작동 순서

온톨로지는 세 종류의 정의로 이루어진다.
용어(term)는 Customer나 Invoice Line 같은 업무 개념으로,
설명과 동의어를 갖고 그것을 담은 열(column)에 대응한다.
SQL 속성(SQL attribute)은 마진이나 누적 합계처럼 검토를 거친 SQL 식으로,
에이전트가 재사용하므로 같은 지표는 항상 같은 방식으로 계산된다.
관계(relationship)는 브리지 테이블을 포함해 테이블이 조인되는 방식이며 키와
데이터에서 추론한다.

작동은 생성, 인증, 답변 세 단계다.
생성 단계에서 수집 서비스는 소스 데이터베이스의 스키마를 읽고 열을 프로파일링해
값을 샘플링한 뒤,
테이블마다 용어를 뽑아 열에 대응시키고,
테이블 사이의 조인과 브리지 테이블을 추론하며,
쿼리 기록에서 SQL 속성을 제안한다.
결과는 Postgres에 저장되고 검색용 임베딩은 pgvector에 들어간다.
NVIDIA는 Wide World Importers 예제 데이터베이스를 한 번 컴파일하면 용어 31개가
나온다고 보여 준다.

인증 단계에서는 사람이 실제 질문으로 초안을 시험하고,
UI나 API로 용어와 설명과 SQL 속성을 고친 뒤,
올바르다고 판단한 이름, 설명, SQL 속성을 인증(certify)한다.
답변 단계에서 에이전트는 질문의 의도를 분류하고 엔티티를 추출하며,
임베딩 검색으로 후보 용어, 열, SQL 속성을 찾아 SQL을 쓴다.
그다음 필터 값과 질의를 데이터베이스에 대해 확인하고 검사가 실패하면
SQL을 고치며,
실행한 뒤 답과 함께 SQL과 거친 단계를 돌려준다.
후보가 질의를 뒷받침하지 못하면 이 데이터로는 답할 수 없다고 알린다.
예측성 질문은 KumoRFM이 설정되어 있을 때 그쪽으로 보낸다.
KumoRFM은 호스팅 서비스이고, 답하려면 연결된 테이블을 업로드한다.
업로드는 `KUMO_MAX_TABLES`(기본 20)로 제한되며 `KUMO_MAX_ROWS_PER_TABLE`은
정하지 않으면 제한이 없다.

### 구성 요소와 모델

| 구성 요소           | 기술                             | 역할                                        | 포트 |
| ------------------- | -------------------------------- | ------------------------------------------- | ---- |
| Frontend            | Next.js, Better Auth, Prisma     | 웹 UI, 인증, 공개 API 게이트웨이            | 3000 |
| Backend             | FastAPI(Python 3.12+), LangChain | 텍스트-SQL 에이전트, 카탈로그, 온톨로지 API | 3001 |
| Ingestion service   | FastAPI(Python 3.12+)            | 수집과 시맨틱 컴파일                        | 3002 |
| MCP server          | FastMCP                          | 공개 API 위의 읽기 전용 에이전트 도구       | 3003 |
| Postgres + pgvector | PostgreSQL 17                    | 카탈로그, 온톨로지, 앱 데이터, 벡터 저장소  | 5432 |
| HashiCorp Vault     | 선택 사항                        | 연결 자격 증명 저장                         | 없음 |

연결할 수 있는 데이터베이스 엔진은 PostgreSQL, MySQL, Databricks, Snowflake,
ClickHouse, Trino, Apache Kyuubi, HeavyDB, DuckDB, SQLite 열 가지다.
모델은 네 가지 역할로 나뉜다.
`nvapi-` 키를 쓰면 기본값은 `REASONING`과 `NON_REASONING`이
`nvidia/nemotron-3.5-lightning-30b-a3b`,
`EMBED`가 `nvidia/nemotron-3.5-embed-1b`,
`RERANK`가 `nvidia/nemotron-3.5-rerank-8b`다.
`REASONING` 모델은 온톨로지를 만들고 답의 SQL과 설명을 쓰며 답변 가능성을
채점하고,
`NON_REASONING` 모델은 질문 의도 분류, 엔티티 추출, 후보 선택,
SQL 검사와 수리를 맡는다.
Nemotron 3.5 Lightning 자체는 [별도
문서](../llm/nemotron-3.5-lightning.md)에서 다룬다.
자체 호스팅 NIM이나 OpenAI 호환 엔드포인트도 쓸 수 있고,
임베딩 모델은 수집할 때와 질의할 때 같아야 한다고 NVIDIA는 명시한다.

### 에이전트에 연결하기

MCP 서버는 어떤 MCP 클라이언트에도 온톨로지에 대한 읽기 전용 도구를 준다.
사용자는 Auto Ontology로 로그인하고 모든 호출은 그 사용자의 권한으로 실행된다.
도구는 아홉 개다.

| 용도        | 도구                                                                                                             |
| ----------- | ---------------------------------------------------------------------------------------------------------------- |
| 준비 상태   | `check_readiness`: 이 배포가 무엇이든 답할 수 있는 상태인지                                                      |
| 용어        | `search_terms`, `get_term`, `get_term_columns`, `get_term_sql_attributes`, `get_sql_attribute`, `describe_table` |
| 답변 가능성 | `check_answerable`: 온톨로지가 이 질문을 다루는지                                                                |
| 질문        | `ask_question`: 답, SQL, 행                                                                                      |

`ask_question`은 웹 UI가 쓰는 `POST /api/chat/completions`를 호출하고,
모델 호출이 여러 번 이어지므로 보통 수십 초가 걸리며,
결과는 100행으로 제한되고 `row_count`와 `truncated`가 잘린 사실을 알린다.
NVIDIA는 데이터베이스, 스키마, 원시 열을 탐색하는 도구를 일부러 두지 않았다고
설명한다.
소비자는 시맨틱 계층을 통해 데이터에 닿아야 하고,
카탈로그 탐색기는 에이전트가 원시 테이블로 추론하도록 부추긴다는 이유다.
API 명세는 87개 연산을 공개하지만 MCP에는 선별한 도구만 올렸다.
REST로는 API 토큰을 발급해 같은 엔드포인트에 질문을 보낼 수 있고,
응답은 서버가 보내는 이벤트(SSE) 스트림이다.
저장소에는 설치, 온톨로지 관리, 질의를 각각 안내하는 에이전트용 스킬 세 개도
들어 있다.

### 배포할 때 알아 둘 점

NVIDIA는 3001번과 3002번 포트를 사설 네트워크에 두라고 경고한다.
FastAPI가 프런트엔드가 전달하는 `x-auto-ontology-user-id` 헤더의 사용자 신원을
그대로 믿고,
수집 서비스의 엔드포인트(수집, 삭제, 초기화,
컴파일)에는 자체 인증이 없기 때문이다.
빠른 시작은 Docker Compose v2, uv, NVIDIA API 키가 필요하고,
예제 데이터베이스를 넣는 스크립트는 별도 저장소의 것을 쓴다.
예제에서 에이전트는 2015년 6월 펜실베이니아의 특정 상품 매출을 질문받고
용어 Invoice Line(revenue), Stock Item,
State Province를 찾아 조인 경로를 따라 SQL을 만든 뒤
588.80달러(송장 줄 3개)라는 답과 SQL을 돌려준다.
광고 데이터가 없는 이 데이터베이스에 광고 수익률을 묻는 두 번째 예에서는
`check_answerable`이 커버리지 0.5를 보고하고 어느 용어도 광고비를 다루지
않는다고 알린 뒤 사용자에게 되묻는다.

## 분석

### 핵심 주장은 질의 생성의 정확도가 아니라 정의의 소유다

NVIDIA가 문제로 삼는 것은 SQL이 문법적으로 맞느냐가 아니라 숫자가 맞느냐다.
숫자가 틀리는 흔한 경로는 에이전트가 revenue라는 열을 찾았지만 환불을
포함하는지, 어느 데이터 집합을 써야 하는지 모르는 경우다.
Auto Ontology의 해법은 이 판단을 질문마다 모델에 맡기지 않고 한 번 정의해 인증해
두는 것이다.
인증 단계가 파이프라인 한가운데 있다는 점이 이를 드러낸다.
모델은 초안을 만들고, 사람이 바로잡아 인증하며,
에이전트는 인증된 정의 위에서 답한다.

Hacker News의 IanCal은 이 구조를 두 단계로 읽었다.
모델이 여러 문서와 출처에서 용어의 뜻과 질의 방법을 매번 알아내는 방식 대신,
한 번 구조화한 기계 판독 가능한 온톨로지 위에서 질의하도록 일을 둘로
쪼갠다는 것이다.
첫 단계의 변환은 오류를 낼 수 있지만, 한 번만 실행되고 수정을 쌓을 수 있으며
같은 문서를 매번 다르게 해석하는 오류가 사라진다고 그는 보았다.[^IanCal-split]
또 IanCal은 고객이 구매한 사람인지 구매할 가능성이 있는 사람인지,
시스템마다 정의가 같은지가 기업에서 흔한 쟁점이라는 예를 들었다.[^IanCal]
matthieu_bl은 온톨로지가 코드베이스에 없는 지식,
예컨대 고객을 셀 때 테스트 계정을 빼는 분석가의 습관을 문서화하게 하고,
매출의 뜻이 영업과 재무에서 다를 때 하나를 고르게 하며,
사람이 읽을 수 있는 단일 기준으로서 거버넌스 도구가 된다고
정리했다.[^matthieu_bl]
theptip은 데이터 엔지니어와 데이터 과학자의 일이 이해관계자와 일회성 질의를
다루는 것에서 온톨로지를 검토하는 것으로 바뀐다고 풀었다.[^theptip]
이 세 댓글은 모두 독자가 문서를 읽고 구성한 해석이고,
NVIDIA의 설명과 정확히 같은 것은 아니다.

### 에이전트가 원시 스키마를 보지 못하게 한 것은 의도된 제한이다

MCP 도구 목록에 원시 스키마 탐색이 없다는 점은 설계 결정이다.
NVIDIA의 설명은 카탈로그 탐색기가 있으면 에이전트가 원시 테이블을 직접 추론하려
들기 때문에,
`describe_table`처럼 그 테이블에 연결된 용어와 SQL 속성만 돌려주는 도구만
둔다는 것이다.
이는 표면적으로 에이전트의 능력을 줄이는 선택이다.
대신 시맨틱 계층이 다루지 않는 질문은 `check_answerable`이 커버리지로 알려 주고
되묻게 만든다.
따라서 이 제품은 답할 수 있는 질문에 더 정확히 답하는 것과 함께,
답하지 못할 질문을 가려내는 것을 기능으로 내세운다.

### 검증의 책임은 제품과 소비하는 에이전트가 나눠 진다

제품 안에서 이루어지는 검증은 답변 단계의 4단계다.
필터 값과 질의를 데이터베이스에 대해 확인하고 실패하면 SQL을 고친다.
저장소의 `sql_value_validation.py`는 이 값 검증을 생성된 SQL의 리터럴을 읽기
전용 질의로 확인하는 에이전트로 구현하며,
이 검증 에이전트의 도구 호출 상한을 20으로 정해 둔다.

반면 질의 스킬의 검증 문서는 소비하는 에이전트에게 더 많은 일을 요구한다.
성공적으로 실행된 SQL이 의도한 질문에 답했다는 증거가 아니라고 먼저 말하고,
SQL이 필요한 제약을 모두 보존했는지, 일대다 조인으로 이미 집계된 지표를 다시
합산하지 않았는지,
행의 단위와 시간 범위와 분모가 맞는지를 에이전트가 따로 확인하라고 한다.
잘린 결과는 전체 목록이나 총합을 증명하지 못하므로 주장을 좁히라고도 한다.
근거가 부족하면 조용히 일부를 자르거나 가장 최근 행을 고르지 말고 실패로
처리하라고 한다.
이는 내 해석이지만, 제품이 마지막 검증의 상당 부분을 소비자 쪽 절차에
넘겼다는 뜻이다.
README의 Validate 항목이 말하는 인증된 정의와 계보에 대한 확인이 제품 안에서
어디까지 자동인지는 문서에서 구분되지 않는다.

NVIDIA가 내세운 문제는 틀린 숫자인데, 저장소 README에는 이 도구가 정확도를
얼마나 올리는지 보여 주는 수치가 없다.
README의 벤치마크 절은 BIRD 같은 텍스트-SQL 벤치마크를 돌리려면 별도 저장소를
보라고 안내한다.
그 저장소(Auto-Ontology Eval)는 같은 모델에 스키마만 준 대조군과 Auto Ontology가
컨텍스트를 찾는 처리군을 비교해 정확도 차이를 낸다고 설명한다.
채점은 각 벤치마크의 공식 규칙(BIRD는 실행 정확도)을 쓰는 결정적 검증기이고,
LLM 심판은 쓰지 않는다.[^eval]
설계 자체는 합리적이지만, 내가 읽은 이 저장소의 README에는 결과 수치가 없다.
안내 링크가 가리키는 저장소 이름이 `ontology-sql-eval`에서
`auto-ontology-eval`로 바뀌어 있다는 점도 눈에 띈다.

저장소에 정확도처럼 보이는 숫자가 있기는 하다.
질의 스킬의 BENCHMARK.md는 이 스킬을 쓴 에이전트의 점수를 보고하는데,
이는 에이전트가 스킬의 지침을 따르는지를 13개 과제에서 과제당 한 번씩
평가한 것이다.
Claude Code에서 정확성(correctness) 점수가 47.7%에서 100.0%로,
Codex에서 50.8%에서 70.8%로 올랐다고 하지만,
이는 텍스트-SQL의 정확도가 아니라 스킬 지침의 효과이므로 같은 문제를
답하지 않는다.

Hacker News의 smithclay는 여러 출처를 질의해야 하는 데이터 에이전트를 평가하는
UC Berkeley의 DataAgentBench 순위표에서 NVIDIA의 접근이 어디에 놓이는지 보고
싶다고 적었다.[^smithclay]
gavinray는 이 벤치마크가 자신의 직장과 그 대학의 협업이라고
밝혔다.[^gavinray-dab]
DataAgentBench의 공저자가 나온 대담은 [데이터 에이전트 벤치마크
문서](data-agent-benchmark.md)에 있다.

### 인증 비용과 의미 틈의 문제를 문서가 다루지 않는다

이 구조의 신뢰는 사람이 인증한 정의의 품질에 달려 있다.
그러나 NVIDIA의 설명에서 인증은 한 줄이고,
인증에 드는 시간과 인력이나 초안의 채택률은 나오지 않는다.
예로 든 용어는 예제 데이터베이스 하나에서 31개다.
실제 기업의 수천 개 테이블에서 몇 개의 용어가 나오고 그중 몇 개를 사람이 고쳐야
하는지는 보고되지 않았다.

Hacker News의 ewild는 열 이름이 저장된 데이터를 제대로 설명하지 못하고 의미가
데이터 과학자들의 암묵지에만 있을 때,
윗선이 틀린 답이나 법적으로 쓸 수 없는 데이터를 답으로 믿게 될까
걱정했다.[^ewild]
adolph는 이를 의미 틈(semantic gap)이라 부르며 예를 들었다.
환자 키가 앱과 API에서는 SI 단위로 단위 표기와 함께 있지만 데이터 웨어하우스에는
단위 표기 없이 미국 관용 단위로 저장되어 있다.
그는 LLM 온톨로지의 기대가 애플리케이션 코드를 읽어 열의 맥락을 알아내는 것이며
이 도구는 그렇지 않다고 보았다.[^adolph]
NVIDIA가 설명하는 수집 입력은 스키마, 열 프로파일, 샘플 값,
쿼리 기록이므로 애플리케이션 코드는 들어 있지 않다.
shostack은 이것이 사람이 집행하는 거버넌스를 위한 도구와 라벨링 계층이지 사람
문제를 마법처럼 풀지는 않는다고 평했다.[^shostack]

### 저장소가 약속하는 결정적 질의 생성과 설명된 작동 방식이 맞지 않는다

저장소 설명문은 결정적인 질의 생성을 약속한다.
그러나 NVIDIA가 설명하는 답변 단계에서 SQL을 쓰는 것은 후보를 받은 모델이고,
`REASONING` 모델이 각 답의 SQL과 설명을 쓰며 검사에 실패하면 모델이 다시 고친다.
결정적인 부분은 인증된 용어와 SQL 속성을 후보로 쓰는 범위에 있을
가능성이 있지만,
같은 질문에 같은 SQL이 나온다는 보장은 문서에 없다.
이는 약속과 설명의 차이를 지적하는 것이고,
코드에서 실제 보장이 있는지는 내가 확인하지 못했다.

온톨로지라는 이름에도 의문이 따랐다.
fnordpiglet은 OWL, RDF, SPARQL 같은 표준 대신 이 도구를 쓸 이유가 무엇이냐고
물었고,[^fnordpiglet]
andriy_koval은 RDF 엔진이 Postgres보다 품질과 성능과 기능이 낮고 LLM에게는 표준
SQL이 더 쉽다고 답했다.[^andriy_koval]
antonvs는 이 도구가 철학이나 학술의 온톨로지가 아니라 소프트웨어에서 시스템
엔티티의 이름, 속성, 관계를 기계가 읽게 정의한 것을 만든다고 풀었다.[^antonvs]
NVIDIA는 온톨로지를 Postgres의 카탈로그 옆에 저장한다고 밝히고 있어 실제 구조는
antonvs의 설명에 가깝다.
표준과의 관계는 Ossie 변환기 한 줄 외에는 설명되지 않는다.

### README는 독자가 제품을 같은 뜻으로 이해하게 만들지 못한다

Hacker News에서 가장 긴 하위 논의(하위 댓글 40개)는 README의 첫 문장이 무슨
뜻인지 알기 어렵다는 반응에서 나왔다.[^dstu]
데이터와 온톨로지 일로 경력을 보낸 barrrrald도 README를 이해하지 못했고 그림은
더 혼란스럽게 했다고 적었다.[^barrrrald]
gavinray는 README를 읽고 직접 쓴 설명에서 중앙 가상 데이터베이스에 여러
데이터베이스의 모델을 모으고 여러 데이터 출처의 결과를 메모리에서 합친다고
요약했다.[^gavinray-explainer]
내가 읽은 NVIDIA의 설명에는 여러 데이터베이스의 결과를 메모리에서 합친다는
말이 없고,
질문을 SQL로 바꿔 연결된 데이터베이스에 실행한다고만 되어 있다.
독자마다 제품을 다르게 이해했다는 것이다.

내용 면에서도 두 곳이 어긋난다.
README 앞부분의 모델 설명은 임베딩 모델을 `nvidia/nemotron-3-embed-1b`,
재순위 모델을 `nvidia/llama-nemotron-rerank-vl-1b-v2`로 적고,
뒤쪽 표와 `.env.example`은 `nvidia/nemotron-3.5-embed-1b`와
`nvidia/nemotron-3.5-rerank-8b`를 쓴다.
같은 설명이 구성 요소 표를 두 번 싣고, 열이 다르다.
Learn 항목은 목록 기호 없이 적혀 있고, 작동 순서를 설명하는 절은 생성, 인증,
답변 세 단계만 다루어 Learn 단계의 작동은 설명이 없다.
수집과 질의에서 임베딩 모델이 같아야 한다는 조건이 있으므로,
첫 번째 목록을 보고 설정한 사람은 기본값과 다른 모델을 고르게 될 수 있다.

## 인사이트

### 인증된 정의는 오류를 없애지 않고 오류가 생기는 단계를 옮긴다

Hacker News의 grey-area는 신뢰할 수 없는 에이전트를 더 붙여 신뢰성을 고치려는
것이라고 비판했다.[^grey-area]
IanCal은 불완전한 시스템도 조합 방식에 따라 오류율이 내려갈 수 있다고
답했다.[^IanCal-combine]
두 주장은 모두 맞을 수 있고, 어느 쪽인지는 오류가 어디서 생기는가에 달려 있다.

Auto Ontology는 오류를 세 단계로 나눈다.
초안을 만드는 단계의 오류, 사람이 인증하는 단계의 오류,
인증된 정의로 SQL을 쓰는 단계의 오류다.
첫 번째는 사람이 걸러낸다고 가정한다.
세 번째는 필터 값 검증과 소비자 쪽 검증이 줄인다.
남는 것은 두 번째, 곧 인증된 정의 자체가 틀렸거나 낡았을 때다.
이때 인증이라는 표시는 신뢰를 높이므로,
틀린 지표가 모든 답에 일관되게 재사용될 수 있다.
이는 내 추론이고, 근거는 인증된 정의가 모든 질의의 기준이 된다는 NVIDIA의
설명이다.

원본 데이터의 열 의미가 바뀌었을 때 인증된 용어가 어떻게 처리되는지는 README에
설명이 없다.
저장소에 카탈로그 비교(diff)와 증분 수집을 이름에 가진 파일이 있으나 나는 그
동작을 읽지 않았다.
이를 가를 시험은 예제 데이터베이스에서 인증을 마친 뒤 한 열의 의미나
단위를 바꾸고,
인증된 용어가 표시를 잃거나 경고를 내는지,
아니면 이전 정의로 계속 답하는지 보는 것이다.

### 이 제품의 가장 독특한 행동은 정확도 지표로 점수가 매겨지지 않는다

예제에서 광고 수익률 질문에 에이전트는 답하지 않고 되물었다.
이 행동은 NVIDIA가 보여 주는 장점 중 가장 차별되는 것이다.
그런데 평가 저장소가 쓰는 방식은 에이전트의 SQL을 정답 SQL과 같은
데이터베이스에서 실행해 결과를 비교하는 것이다.
정답 SQL이 없는 질문, 곧 데이터로 답할 수 없는 질문은 이 방식으로 점수를 줄
수 없다.
내 추론이지만, 올바른 거절은 실행 정확도 위에서는 보상도 손실도 받지 않는다.

그래서 거절을 측정하려면 답할 수 없는 질문 집합이 따로 필요하다.
거짓 답변률(답이 없는데 숫자를 낸 비율)과 거짓 거절률(답이 있는데 거절한 비율)을
함께 보고해야 한다.
`check_answerable`의 커버리지가 0.5였던 예처럼 점수가 중간인 구간에서 어디를
경계로 삼는지도 드러난다.
DataAgentBench처럼 여러 출처의 질의를 다루는 벤치마크가 이런 질문을 포함하는지는
내가 확인하지 못했다.

### 정의를 쓰는 비용은 줄고 정의를 검토하는 비용은 남는다

데이터 카탈로그나 메타데이터 프로젝트가 오래 겪어 온 어려움은 정의를 쓰고 갱신할
사람이 없다는 점이었다고 나는 본다.
이 판단에는 이 문서가 근거로 든 출처가 없다.
Auto Ontology는 쓰는 일을 모델에 넘긴다.
그러나 theptip이 말한 대로 사람의 일은 쓰기에서 검토로 옮겨 갈 뿐이다.[^theptip]
검토할 항목의 수는 모델이 초안을 쏟아 낼수록 늘 수 있다.
예제 데이터베이스에서는 용어가 31개였지만 규모가 커진 환경에서는 같은 비율로 늘
것이라는 보장이 없고 줄 것이라는 보장도 없다.

가장 어려운 항목은 어차피 사람에게만 있는 지식이다.
Hacker News에서 ewild가 적은 것처럼 의미가 데이터 과학자들의 머릿속에만 있다면,
모델은 그럴듯한 초안을 쓸 수 있어도 맞는지 판단할 근거가 없다.
따라서 이 도구의 효과는 초안의 품질보다 검토하는 사람이 얼마나 빨리 바로잡는지에
달렸을 것이다.
이를 확인하는 관측은 용어 하나를 인증하는 데 걸리는 시간,
초안이 수정 없이 인증되는 비율, 수정 후에도 틀린 채 인증되는 비율이다.
이 세 수치가 나오면 정의를 쓰는 비용이 줄었다는 주장도,
검토 비용이 남는다는 이 문서의 주장도 확인하거나 깰 수 있다.
