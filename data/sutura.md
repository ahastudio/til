# sutura: 인증된 지표 정의로만 질문을 받고 호출자의 신원으로 실행하는 시맨틱 데이터 런타임

<https://telekom.github.io/sutura/>

<https://github.com/telekom/sutura>

GN 토론: <https://news.hada.io/topic?id=36620>

## 소개

sutura는 Rust로 쓴 시맨틱 데이터 런타임(semantic data runtime)이다.
쿼리를 HTTP와 MCP로 서비스하고,
기본적으로 인증된(certified) 지표 정의를 써서 답한다.
메타데이터와 데이터 소스는 어댑터로 연결하고,
한 질문이 여러 소스의 데이터를 합칠 수 있다.
저장소는 GitHub 조직 `telekom`에 있고 라이선스는 Apache-2.0이다.

저장소 설명은 데이터와 시맨틱을 끼워 넣을 수 있는 안전한 멀티플레이어 채팅형
데이터 경험이라는 뜻이고, README는 이를 시맨틱 데이터 런타임이라고 다시
정의한다.
README는 DataFusion(로컬 쿼리 실행), Arrow(결과 배치),
ADBC(데이터 시스템 연결), polyglot-sql(방언별 SQL 생성)을 기술 기반으로 들고,
Wren과 Spice를 시맨틱 모델과 쿼리 연합의 설계 참고로 든다.

이 문서는 저장소의 README와 `docs/`의 아키텍처, 개념, 시작하기, 통합, Q&A,
신원 증명 문서, `CHANGELOG.md`를 읽고 썼다.
코드는 읽지 않았고 직접 설치하거나 실행하지 않았다.

## 해결하려는 문제와 네 가지 속성

문서는 에이전트가 데이터베이스에 직접 연결해 SQL을 쓰는 방식에서 두 가지 문제가
생긴다고 말한다.
첫째, 에이전트가 정의까지 만들어 내므로 에이전트가 말한 “매출”이 재무팀의 정의와
같은지 아무도 말할 수 없다.
둘째, 행이 호출자가 아니라 서비스 계정이 읽을 수 있는 만큼 돌아와서 행 수준
보안(row-level security)이 아무 효과가 없다.

sutura의 설계는 이 둘을 막는 네 가지 속성으로 정리된다.

| 속성                               | 메커니즘                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------- |
| SQL을 실행하게 시킬 수 없다        | 질문 타입에 SQL, 테이블, 필터 필드가 없다. 모르는 필드는 거부되고 모든 값은 바인드 매개변수가 된다    |
| 정의는 카탈로그에서 온다           | 정의는 고정된 해시 스냅샷으로 도착하고, sutura는 고치지 않으며, 서비스 시작 전에 앵커를 다시 실행한다 |
| 거부(refusal)는 오류가 아닌 답이다 | 이유가 붙은 결과이고, 모든 결과는 반환 전에 감사 싱크(audit sink)에 기록된다                          |
| 모든 쿼리가 호출자 권한으로 돈다   | 호출자로 실행할 수 없는 단계는 거부된다. 다만 데이터 시스템에 따라 다르다(아래 신원 절)               |

## 질문의 모양

질문은 지표(metric), 차원(dimension), 단위 기간(grain),
한정된 시간 범위로 이뤄진다.
문서는 이것이 어휘의 전부이며,
이 틀을 벗어난 질문은 거부되는 것이 아니라 표현할 수 없다고 말한다.

- 지표: 누군가 인증한 측정값(매출, 활성 구독자, 이탈 등)이고 시맨틱 계층에서 온다.
- 차원: 지표가 선언한 분해 기준(지역, 상품, 요금제 등)이다. 선언하지 않은 차원은 거부 사유와 함께 돌아온다.
- 차원 값은 고정된 번들의 허용 목록으로 검사하고, 쿼리에 문자열로 붙이지 않는다.
- 단위 기간: 지표가 지원하는 시간 해상도다.
- 시간 범위: 양 끝이 있어야 하고, 10년을 넘는 범위는 `TimeRangeTooLong`으로 거부된다.

질문 파일의 예는 YAML이다.
저장소의 `examples/single-player/questions/recurring-revenue-by-region.yaml`이
예이고, 지표 이름, 단위 기간, 날짜 범위, 차원, 필터를 적는다.

거부의 사유는 문장이 아니라 타입이다.
`DimensionValueNotAllowed` 같은 변형은 어떤 차원이 문제인지만 말하고,
호출자가 보낸 값을 되풀이하지 않는다.
이는 호출자의 글이 로그나 UI나 에이전트의 맥락으로 반사되는 것을 막기 위해서라고
한다.
CLI는 거부도 결과이므로 종료 코드를 `0`으로 낸다.

## 정의는 고정된 스냅샷이고 편집할 수 없다

정의(definition)는 지표가 계산하는 측정, 읽는 모델, 지원하는 단위 기간,
분해 가능한 차원, 의미에 포함되는 필터로 이뤄진다.
이 의미는 표현식 언어가 아니라 닫힌 어휘이고,
측정은 두 가지 모양(`simple` 하나, `ratio` 둘)이며 필수 필터는 네 가지 연산자다.
sutura가 이 정의로 쿼리 전체를 생성하므로,
호출자가 쓴 SQL도 카탈로그가 쓴 SQL도 경로에 없다.

정의는 버전과 해시(digest)를 가진 스냅샷으로 도착한다.
카탈로그 편집은 질문의 의미를 호출 사이에 바꿀 수 없고,
바뀌면 해시가 바뀌며 해시가 답에 따라간다.
카탈로그를 읽는 경로는 요청 맥락을 받지 않으므로 한 호출자에게 다른 정의를 줄 수
없다.
앵커(anchor)는 지표의 알려진 결과이고,
앵커를 선언한 지표를 모두 다시 실행해 일치할 때만 번들이 검증된 것으로 통과한다.

문서는 “찾을 수 없는 것”을 표로 정리한다.

| 없는 것                              | 이유                                                                    |
| ------------------------------------ | ----------------------------------------------------------------------- |
| SQL, 테이블 이름, 필터 표현식, 행 ID | 도구 표면에 필드가 없다                                                 |
| 캐시된 결과                          | 행 수준 보안 아래에서 질문을 키로 한 캐시는 사용자 간 유출이다          |
| 정의 편집                            | 편집은 정의를 그것이 인증하는 숫자에서 떼어 낸다. 정의는 상위에서 쓴다  |
| 서비스 신원으로의 쿼리               | 호출자로 실행할 수 없는 단계는 낮춰 실행하지 않고 거부한다              |
| 한정되지 않은 시간 범위              | 범위가 한정되어야 해석된다                                              |
| 정의에 속한 필터의 제거나 이름 변경  | 필수 필터는 모든 계획에 컴파일되고 호출자에게 그것을 가리킬 필드가 없다 |

## 카탈로그와 데이터 시스템

sutura는 두 포트를 분리한다.
카탈로그(catalog)는 정의를 공급하고,
데이터 시스템(data system)은 데이터를 갖고 쿼리를 실행한다.

| 카탈로그      | `kind`         | 공급하는 것                 |
| ------------- | -------------- | --------------------------- |
| 마크다운      | `markdown`     | 모델, 조인, 지표, 지식 전부 |
| DataHub       | `datahub`      | 모델, 설명, 조인, 지표      |
| OKF           | `okf`          | 테이블과 설명               |
| Data Contract | `datacontract` | 테이블, 타입, 설명, 조인    |
| OpenMetadata  | `openmetadata` | 테이블, 타입, 설명, 조인    |
| RDBMS 사전    | `rdbms`        | 테이블, 타입, 설명          |
| Cube          | `cube`         | 모델, 타입, 설명            |
| Wren          | 가져오기 명령  | 검토할 마크다운 카탈로그    |

지표가 없는 카탈로그는 인증된 질문에 답하지 못한다.
한 배포는 한 종류의 카탈로그를 쓴다.

| 데이터 시스템 | `kind`       | 쿼리의 신원                                                       |
| ------------- | ------------ | ----------------------------------------------------------------- |
| DataFusion    | `files`      | sutura를 실행하는 운영체제 사용자                                 |
| DuckDB        | `duckdb`     | sutura를 실행하는 운영체제 사용자                                 |
| BigQuery      | `bigquery`   | 서비스 계정 하나, 또는 호출자 본인의 계정                         |
| PostgreSQL    | `postgres`   | 선언된 역할 하나                                                  |
| ClickHouse    | `clickhouse` | 선언된 사용자 하나, 또는 호출자마다 선언된 사용자                 |
| Oracle        | `oracle`     | 선언된 사용자 하나. 호출자 토큰 경로는 만들었으나 검증되지 않았다 |
| Cube          | `cube`       | Cube가 토큰 하나 또는 호출자마다의 토큰을 받는다                  |

한 질문이 여러 데이터 시스템을 읽을 수 있다.
sutura가 계획을 사실(fact) 단계와 조회(lookup) 단계로 나눠 각 소스에서 실행하고
결과를 조인한다.
조회 단계가 `governance.lookup_leg_ceiling`(기본 3)을 넘으면
`PlanNeedsTooManyLookupLegs`, 소스 수가 `governance.source_ceiling`(기본 4)을
넘으면 `PlanSpansTooManySources`로 거부된다.
Cube 소스는 연합 질문의 한 단계를 실행하지 못한다.

## 신원은 두 갈래다

sutura는 신원을 두 갈래로 나눈다.

- 1갈래: sutura가 누가 묻는지 안다. 호출자의 토큰을 답하기 전에 HTTP와 MCP에서 검증한다(`security.inbound`).
- 2갈래: 데이터 시스템이 호출자 권한으로 쿼리를 실행한다. BigQuery와 ClickHouse가 이렇게 하고, 나머지는 운영자가 소스마다 선언한 신원 하나로 실행한다(`shared-service-user`).

문서는 공유 신원을 쓰는 소스의 결과가 갈릴 수 있다고 말한다.
합산한 결과에는 한쪽 신원이 볼 수 있고 다른 쪽 신원은 볼 수 없는 행이 섞일 수
있다.
그래서 다중 사용자(`multi-user`) 배포에서는 `shared-service-user` 소스마다
운영자가 `acknowledged_because`로 이유를 적어야 하고,
적지 않으면 배포가 시작되지 않는다.

권한, 행 정책, 마스킹은 데이터 시스템에 남는다.
sutura는 누가 무엇을 볼 수 있는지의 사본을 갖지 않고, 결과 캐시도 두지 않는다.
공유 베어러 토큰만 쓰는 배포는 호출자별 신원이 없어,
감사 기록의 주체가 배포 자체다.

## 시작하기

저장소의 `getting-started.md`가 안내하는 길은 세 가지다.

- Docker Compose: `examples/single-player/compose.yaml`로 서버를 띄우고 `sutura doctor`와 `/health`로 확인한다. macOS와 Windows의 Docker Desktop은 호스트 네트워킹을 켜야 한다.
- Linux 바이너리: 릴리스마다 자산 네 개(x86_64와 aarch64의 musl과 glibc)가 있고, `sha256sum -c`와 `gh attestation verify`로 검증한다.
- Nix: 소스에서 빌드하며 첫 빌드가 오래 걸린다.

macOS와 Windows용 바이너리는 없고 Docker Compose나 Nix를 써야 한다.

```bash
sutura catalog examples/single-player/catalog
sutura query examples/single-player/catalog \
  examples/single-player/questions/recurring-revenue-by-region.yaml \
  examples/single-player/data
sutura compile examples/single-player/catalog \
  examples/single-player/questions/recurring-revenue-by-region.yaml
```

문서의 예제 결과는 지역별 반복 매출이다.
central 51,739, east 32,598, north 42,157, south 21,203, west 49,425,
null 4,999이고, 합계는 202,121이다.
`null` 행은 고객 테이블(`dim_customer.csv`)에 없는 고객의 구독 하나이며,
그 매출은 합계에 남는다.
첫 줄에 카탈로그 버전과 정의 해시가 나온다.

### 자기 카탈로그 쓰기

카탈로그는 YAML 머리말이 붙은 마크다운 파일의 디렉터리다.
모델은 테이블, 소스, 열을 적고, 지표는 모델, 측정, 단위 기간, 차원을 적는다.
문서의 지표 예는 `recurring_revenue`이고,
`status`가 `active`인 구독의 `mrr_cents` 합계다.
필수 필터는 호출자가 보거나 제거할 수 없고,
차원의 `values`는 필터가 쓸 수 있는 값이며 `values`가 없는 차원은 그룹화에만
쓴다.

소스는 `conf/base.yaml`에 선언하고 `SUTURA_CONFIG_DIR=conf`로 지정한다.

```yaml
security:
  identity: single-user
  single_user_because: "one analyst, one laptop, the files they already have"
sources:
  local:
    kind: files
    data_dir: "/absolute/path/to/data"
    posture: shared-service-user
```

모든 설정 키에는 환경 변수가 있고,
`SUTURA__`에 키 경로를 대문자로 `__`로 이어 쓴다.
예를 들어 `sources.local.data_dir`은 `SUTURA__SOURCES__LOCAL__DATA_DIR`이다.

## 도입 전에 정할 것

| 결정                        | 선택지                                | 판단 근거                                                                                      |
| --------------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 호출자별 행 권한이 필요한가 | BigQuery나 ClickHouse / 그 밖의 소스  | 문서가 호출자 권한 실행을 말하는 곳은 이 둘이고 나머지는 선언된 신원 하나로 실행한다           |
| 카탈로그                    | 마크다운 / DataHub / 그 밖            | 지표가 있는 카탈로그만 인증된 질문에 답한다                                                    |
| 지표 서빙 계층              | Cube를 둠 / 두지 않음                 | BI 도구나 REST 클라이언트가 같은 지표를 쓰면 Cube를 권하고, 결과 캐시는 Cube 쪽에서만 가능하다 |
| 설치                        | Docker Compose / Linux 바이너리 / Nix | macOS와 Windows 바이너리는 없다                                                                |
| 신원 검증                   | `security.inbound`를 켬 / 공유 토큰만 | 공유 토큰만 쓰면 감사 기록의 주체가 배포 자체다                                                |

## 비평

### 핵심 속성의 근거가 아직 일부만 실행되었다

네 번째 속성인 모든 쿼리가 호출자 권한으로 돈다는 말은 저장소 자신의 문서에서
한정된다.
소개 표 자체가 BigQuery와 ClickHouse를 제외한 모든 데이터 시스템이 선언된 신원
하나로 실행된다고 적는다.
Oracle은 호출자 토큰으로 세션을 여는 경로를 만들었지만 실행해서 확인된 적이
없다고 한다.
PostgreSQL 어댑터는 호출자를 위한 자리가 없다는 능력(`NoPlaceForASubject`)을
선언해, 호출자 신원 실행을 요청한 배포는 시작하지 않는다.

신원 증명 문서(`where-identity-is-proven.md`)는 이 한정을 더 깊게 쓴다.
이 문서는 주장마다 어떤 시험 환경(venue)이 정직하게 답할 수 있는지를 표로
정리하고, 초록색 실행이 실제보다 많은 것을 증명한 것으로 읽히는 일이 가장 비싼
실패라고 말한다.
표에서 BigQuery가 `domain_delegation` 작업을 위임된 주소로 기록하는지는
의도적으로 무시된 시험이고, 도메인 전체 위임이 제공될 때까지 통과한 실행이
없다고 적는다.
서로 다른 두 주체가 ADBC 경로에서 서로 다른 두 BigQuery 주체로 해석되는지는
시험을 통과했지만, 어서션이 테스트 픽스처이며 사람의 로그인이 아니라고 적는다.
서비스되는 바이너리 위에서 검증된 사람 호출자가 묻는 경우를 다루는 시험 환경에
대해 문서는 어디에서도 실행되지 않고 상시 시험 칸이 없으며 통과한 실행도
관찰되지 않았다고 적는다.
저장소가 스스로 이렇게 구분해 적는다는 점은 신뢰할 만하지만,
이는 헤드라인 속성이 아직 끝까지 실행된 증거가 없다는 뜻이기도 하다.

### 닫힌 어휘는 표현할 수 있는 지표를 제한한다

측정은 `simple`과 `ratio`이고 항(term)은 열 집계와 `count_if`뿐이다.
윈도 함수, 백분위수, 두 열에 걸친 식은 이 어휘로 말할 수 없다.
문서는 이를 위해 `authored_sql:`을 두지만,
현재 어떤 어댑터도 이를 실행하지 않으며 그것을 가진 번들은 서비스 시작 때 지표
이름과 함께 거부된다고 적는다.
따라서 이런 지표는 지금 서비스할 수 없다.
다른 길로 `run_sql` 도구가 있고 기본으로 꺼져 있다고 문서가
적는다(`examples/raw-sql`).
안전과 표현력 사이의 이 교환은 의도된 것이다.
이 방식이 맞는지는 도입하려는 조직의 지표 중 닫힌 어휘로 표현되지 않는 것이 몇
개인지로 가려진다.

### 결과 캐시가 없어 모든 질문이 소스까지 간다

호출자마다 보는 행이 다를 수 있으므로 질문을 키로 한 캐시는 한 호출자의 행을
다른 호출자에게 보낸다는 이유로 sutura는 결과 캐시를 두지 않는다.
이 판단은 보안상 합리적이다.
그 대가는 같은 질문의 반복이 매번 데이터 시스템의 비용과 지연을 낳는다는 점이고,
문서가 말하는 완화책은 Cube 같은 서빙 계층의 캐시다.
이 문서가 읽은 범위에서 질의 경로의 지연이나 처리량을 측정한 수치는 없었다.
문서에 나온 벤치마크는 musl 할당자를 mimalloc으로 바꾼 것(48코어에서 92초 대
4초)이다.

### 성숙도 지표가 빠른 변화를 가리킨다

저장소는 2026-08-24에 만들어졌고 이 문서를 쓴 2026-11-05에도 푸시가 있었다.
그 사이 릴리스가 15개(최신 v0.11.0,
2026-10-27)이고 커밋이 약 1,234개이며 기여자가 4명이고 별이 20개다.
73일 동안 1,234개면 하루 약 17개의 커밋이다.
v0.11.0의 변경 기록에는 호환성을 깨는 변경이 13개 있다.
저장소 루트에 `AGENTS.md`, `CLAUDE.md`, `.claude`, `.codex`,
`.opencode`가 있는 것으로 보아 코딩 에이전트를 많이 쓰는 개발로 짐작되지만,
이 문서는 그 내용을 읽지 않았다.
이 수치는 활발한 개발을 보여 주는 동시에,
설정과 API가 아직 안정되지 않았다는 신호다.

## 확인하기

도입을 판단하기 전에 직접 해 볼 수 있는 확인이다.

- Docker Compose로 단일 사용자 예제를 띄우고 `sutura doctor`로 빌드된 프로필과 연결된 데이터 시스템을 본다.
- 위의 `query` 결과의 여섯 행을 더해 합계가 202,121인지, `null` 행이 합계에 남아 있는지 확인한다.
- `sutura compile`로 생성된 SQL을 보고, 카탈로그 없이 질문을 바꿔 보며 어떤 거부가 나오는지 본다(`questions/refused-*.yaml`).
- 자신의 데이터 시스템이 호출자 권한 실행을 지원하는 BigQuery나 ClickHouse인지 확인하고, 지원한다면 신원 증명 문서의 해당 표에서 자신의 구성에 해당하는 칸이 `yes`인지 읽는다.
- 다중 사용자 배포에서 공유 신원 소스에 `acknowledged_because`를 적지 않으면 배포가 시작되지 않는지 확인한다.

## 체크리스트

- 호출자별 행 권한이 필요하다면 소스가 BigQuery나 ClickHouse이고 해당 구성이 증명된 칸에 속하는가.
- 서비스할 지표가 모두 `simple`과 `ratio`와 네 가지 필수 필터 연산자로 표현되는가.
- 같은 질문의 반복 비용을 데이터 시스템이나 서빙 계층의 캐시로 감당할 수 있는가.
- `security.inbound`를 켜서 감사 기록에 호출자가 남게 했는가.
- 호환성을 깨는 변경이 잦은 0.x 버전에 맞춰 버전을 고정하고 변경 기록을 읽는 절차가 있는가.
