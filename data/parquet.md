## 소개

Python In Production 채널이 2026년 10월 5일에 올린 13분 분량의 영상이다.
“Data Engineering for ML and AI” 시리즈의 1장이며, 다음 장은 Iceberg가 수천 개의 Parquet 파일을 하나의 테이블로 묶는 방식이다.
영상은 뉴욕 택시 운행 기록 1천만 건으로 모든 수치를 잰다.

시작은 실험 하나다.
1천만 건의 운행 요금 평균을 계산하는 함수가 거의 1GB짜리 CSV 파일을 0.2초 안에 읽는다.
읽는 파일을 같은 운행의 Parquet 파일로 바꾸면 파일 크기는 6분의 1이 되고, 같은 함수가 7밀리초에 끝난다.
읽기가 27배 빨라진 것이다.
영상의 요지는 이렇다.
언어 모델이 이런 함수를 쉽게 써 주지만, 데이터를 어떻게 저장할지는 사람이 고르므로 그 선택을 이해해야 한다.
이 문서는 영상의 수치와 설명을, 선택에 쓸 수 있는 순서로 정리한다.

## 동작 방식

### 행 단위 저장과 열 단위 저장

파일 형식은 표를 두 방식 중 하나로 저장한다.
CSV, JSON Lines, Avro는 행 단위(row storage)이고 Parquet, ORC, Feather는 열 단위(columnar storage)다.
CSV는 한 줄에 운행 하나가 있고 쉼표가 값 19개를 나눈다.
값마다 길이가 달라 요금의 위치가 줄마다 다르므로, 읽는 쪽은 모든 줄의 모든 글자를 읽으며 쉼표를 세어 요금을 찾는다.
Parquet은 같은 열의 값을 붙여 저장하므로 요금만 읽고 나머지 열은 건너뛴다.
집계, 필터, 학습 작업은 대부분 많은 행에서 몇 개의 열만 읽기 때문에 이 구조가 맞는다.

이 속도 차이는 도구에 상관없이 나타난다.
영상이 시험한 세 도구에서 CSV는 Polars가 가장 빨랐고, DuckDB는 3배 넘게, pandas는 10배 넘게 걸렸다.
그런데 pandas로 Parquet에서 요금을 읽는 것이 Polars로 CSV에서 읽는 것보다 7배 빨랐다.
속도의 원인이 도구가 아니라 파일 형식이라는 뜻이다.

### 파일 안의 형식: 타입과 푸터

CSV는 모든 값을 텍스트로 저장한다.
17.70달러는 글자 네 개이고, 이를 숫자로 되돌리는 파싱을 읽을 때마다 모든 요금에 대해 한다.
CSV는 열의 타입도 저장하지 않아서 읽는 쪽이 처음 몇 줄을 보고 타입을 추측한다(타입 추론).
영상은 이 추측이 틀리는 예를 든다.
PyArrow가 수수료 1달러를 소수점 없이 숫자 1로 쓰면, Polars는 처음 100행에서 정수만 보고 정수 열로 취급한다.
약 8만 행 뒤에 30센트가 나오면 읽기가 실패한다.
Parquet은 각 열의 타입을 파일에 저장하므로 이 문제가 없다.

Parquet 파일은 `PAR1` 네 바이트로 시작하고, 열의 데이터가 이어지고, 그 뒤에 푸터(footer)가 붙는다.
파일의 끝은 푸터의 길이와 다시 `PAR1`이다.
푸터에는 모든 열의 이름, 타입, 그리고 각 열의 데이터가 파일의 어디서 시작하는지가 적혀 있다.
쓰는 쪽은 데이터를 쓴 뒤에야 각 열의 시작 위치를 알기 때문에 푸터를 마지막에 쓴다.
읽는 쪽은 마지막 8바이트를 먼저 읽고, 그다음에 푸터를 읽는다.
영상의 파일에서 푸터는 158MB 중 26KB다.
푸터는 Thrift라는 간결한 이진 형식이어서, 값을 텍스트 파싱 없이 바이트에서 바로 읽는다.

### 인코딩으로 줄이는 크기

Parquet이 CSV보다 6배 작은 이유는 같은 종류의 값이 열 안에 나란히 있어 반복이 많기 때문이다.
값을 정확히 되돌릴 수 있는 더 작은 형태로 쓰는 것을 인코딩이라고 한다.
영상의 파일은 세 가지를 쓴다.
결제 유형 열에는 서로 다른 값이 5개뿐이다.

- 사전 인코딩(dictionary encoding): 5개의 값을 목록에 한 번씩 쓰고, 각 행에는 그 목록에서의 위치만 저장한다.
- 런 렝스 인코딩(run-length encoding): 같은 위치가 연속으로 반복되면 한 번만 쓰고 반복 횟수를 적는다.
- 비트 패킹(bit-packing): 서로 다른 위치 값 5개는 64비트가 아니라 3비트에 들어가므로, 필요한 비트 수만큼만 채워 넣는다.

결제 유형을 64비트 숫자로 그냥 저장하면 76MB이지만, 세 인코딩을 거치면 2.2MB가 된다.
사전만으로는 절약이 없다.
위치가 차지하는 바이트가 원래 값과 같기 때문이다.
결제 유형이 32비트였더라도 세 인코딩은 94%를 줄인다.

### 페이지와 압축

Parquet은 각 열을 페이지로 나눈다.
영상의 예시 열에서 한 그룹은 결제 유형 약 100만 개를 담고, 첫 페이지에는 5개 값의 목록이 있고 이어지는 53개 페이지에 위치가 들어간다.
PyArrow는 기본으로 한 페이지에 최대 2만 개의 위치를 넣는다.
각 페이지의 머리에는 인코딩 방식과 바이트 수가 적힌다.
2만 개의 결제 유형이 모두 같다면 한 페이지가 런 하나로 끝나고, 압축 전 데이터가 13바이트다.

압축은 인코딩과 별개의 단계다.
각 페이지를 독립적으로 압축하므로 읽는 쪽은 다른 페이지 없이 한 페이지만 풀 수 있다.
Zstandard는 결제 유형을 2.2MB에서 1.2MB로 더 줄인다.

### 행 그룹과 조건 밀어넣기

Parquet은 행을 행 그룹(row group)으로 나누고, 각 그룹 안에 열을 차례로 저장한다.
영상의 파일은 행 그룹이 10개다.
PyArrow는 각 행 그룹의 각 열에 대해 최솟값과 최댓값을 푸터에 쓴다.
2월 15일의 평균 요금을 구한다면 행 그룹마다 승차 시각의 최소와 최대를 보고, 2월 15일이 범위 밖이면 그 행 그룹을 읽지 않고 건너뛴다.
날짜 조건을 읽는 쪽에 넘기는 것을 조건 밀어넣기(predicate pushdown)라고 부른다.

운행이 승차 시각순으로 정렬되어 있으면 2월 15일은 행 그룹 하나의 범위에만 들고, 읽는 쪽은 10개 중 1개를 읽는다.
섞여 있으면 모든 행 그룹에 모든 날이 들어 있어 10개를 다 읽는다.
영상의 측정으로는 20배 많은 바이트를 읽고, 시간은 거의 두 배가 걸린다.

## 값 정하기

영상이 보여 주는 설정과 그 영향을 표로 모았다.
시작 값의 근거는 영상의 측정이며, 자기 데이터에서는 다시 재야 한다.

| 설정                    | 기본값(영상 기준)                               | 영향                                                                                   |
| ----------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------- |
| 압축 방식               | Polars는 Zstandard, PyArrow와 DuckDB는 Snappy   | Zstandard는 Snappy와 거의 같은 속도로 쓰면서 파일이 5분의 1 작다                       |
| 행 정렬                 | 원본 순서                                       | 승차 시각순 정렬은 144MB, 섞으면 213MB. 필터 열로 정렬하면 건너뛰는 행 그룹이 늘어난다 |
| 행 그룹 크기            | PyArrow 약 100만 행, DuckDB와 Polars 약 12만 행 | 작으면 정밀하게 건너뛰지만 푸터가 커진다. 크면 푸터는 작지만 덜 건너뛴다               |
| 페이지 크기(PyArrow)    | 위치 최대 2만 개                                | 페이지 단위로 독립 압축된다                                                            |
| 형식 버전과 페이지 버전 | 형식 2.6, 페이지는 버전 1(PyArrow 기본)         | 형식 버전은 담을 수 있는 타입을, 페이지 버전은 페이지 배치를 정한다                    |

행 그룹 크기의 극단을 영상은 이렇게 잰다.
1만 행짜리 행 그룹으로 쓰면 정렬된 파일에 행 그룹이 956개이고 푸터가 26KB에서 2.2MB로 커진다.
행 그룹 하나에 모든 운행을 넣으면 하루치를 찾으려고 27MB를 읽고 55밀리초가 걸린다.
영상은 대부분의 경우 인기 있는 쓰기 도구의 기본값이 잘 맞는다고 한다.

## 트레이드오프

### 압축 방식은 네트워크 속도에 따라 답이 달라진다

Gzip과 Brotli는 파일을 더 작게 만들 수 있지만 대가가 있다.
PyArrow 기본 설정에서 Gzip은 Zstandard보다 쓰기에 30배 가까이 걸리고, Brotli는 읽기에 2.5배 걸린다.
Zstandard는 파일이 메모리에 있을 때 모든 열을 읽는 데 압축하지 않은 파일보다 약 24밀리초 더 걸린다.
그러나 파일이 약 25Gbps보다 느린 네트워크로 오면, 압축으로 아낀 91MB가 도착하는 시간이 Zstandard가 푸는 시간보다 길다.
영상은 그래서 압축이 네트워크로 읽는 경우에는 읽기도 빠르게 한다고 한다.
읽기 속도, 쓰기 속도, 저장 크기의 균형을 애플리케이션에 맞춰 골라야 한다.

### CSV를 압축하는 방법으로는 같은 이득을 얻지 못한다

Python 3.14는 표준 라이브러리에 Zstandard를 포함한다.
CSV를 압축하면 188MB가 되고 Parquet은 158MB다.
그러나 요금을 읽으려면 여전히 모든 줄을 풀고 파싱해야 한다.
압축된 CSV에서 요금을 읽는 시간은 압축하지 않은 CSV의 5배다.
같은 열을 Parquet에서 읽는 시간은 7밀리초다.
크기 차이보다 읽는 방식의 차이가 더 크다.

### 열 단위 저장이 항상 낫지는 않다

영상은 행 단위의 SQLite와 열 단위의 DuckDB를 같은 데이터로 비교한다.
운행 하나를 번호로 찾는 데 SQLite는 약 6마이크로초가 걸리고 DuckDB는 29배 오래 걸린다.
운행 하나를 추가하는 일도 SQLite는 약 0.2밀리초에 저장하지만, PyArrow, Polars, DuckDB는 끝난 Parquet 파일에 행을 추가하지 못한다.
Parquet에 한 건을 더하려면 파일 전체를 다시 써야 하고, 쓰는 데 거의 2초가 걸린다.
반대로 월별 평균 요금은 DuckDB가 필요한 열 두 개만 읽어 SQLite보다 49배 빠르다.
DuckDB가 프로세서의 모든 코어를 쓰는 점도 있는데, 코어 하나끼리 비교해도 DuckDB가 9배 빠르다.
따라서 한 행씩 읽고 쓰는 앱에는 행 저장이, 많은 행을 한꺼번에 읽는 분석과 학습에는 열 저장이 맞다.

### 끝나지 않은 문제: 파일이 많아지는 경우

영상은 장 끝에서 이 구조의 한계를 예고한다.
Parquet이 퍼지면서 S3 같은 객체 저장소에 정리되지 않은 Parquet 파일이 많이 쌓인다는 것이다.
다음 장에서 Iceberg가 수천 개의 Parquet 파일을 하나의 테이블로 묶는 방식을 다룬다고 한다.

## 함정

- 필터에 쓰는 열로 정렬하지 않으면 최솟값과 최댓값 범위가 모든 행 그룹에 걸쳐 조건 밀어넣기가 효과를 잃는다.
- 몇 개의 잘못된 값이 행 그룹 하나를 건너뛰지 못하게 만든다.
  영상의 데이터에는 승차 시각이 2002년, 2008년, 2009년인 운행이 9건 있었고, 그중 두 건이 3월 운행의 행 그룹에 들어 있었다.
  그 행 그룹의 푸터 범위가 2002년 12월부터 2024년 3월까지가 되어, 2월의 하루를 찾으려고 3월 행 그룹 전체를 읽는다.
  데이터를 정리하는 일이 엔지니어링의 문제이기도 하다는 사례다.
- 푸터는 읽는 쪽이 가장 먼저 읽는다.
  행 그룹을 너무 작게 나누면 푸터가 커져 읽기가 느려진다.
- Parquet “버전 2”는 두 가지를 뜻할 수 있다.
  형식 버전(담을 수 있는 타입)과 페이지 버전(페이지 배치)이 따로 있으므로, 어느 쪽인지 확인하고 말해야 한다.
- 끝난 Parquet 파일에 행을 추가하는 도구는 영상이 시험한 PyArrow, Polars, DuckDB에는 없다.
  행 단위 추가가 필요한 용도에는 맞지 않는다.

## 확인하기

내가 가진 Parquet 파일이 영상의 구조를 따르는지 확인하는 방법을 두 가지 적는다.
이 환경에는 PyArrow가 설치되어 있지 않아서 두 번째 방법은 실행해 보지 못했다.
첫 번째는 표준 라이브러리만으로 영상이 설명한 파일 끝의 구조를 확인하는 스크립트다.

```python
import struct
import sys


def inspect(path: str) -> None:
    with open(path, "rb") as f:
        head = f.read(4)
        f.seek(-8, 2)  # 마지막 8바이트: 푸터 길이(4바이트) + PAR1
        tail = f.read(8)
    footer_len = struct.unpack("<I", tail[:4])[0]
    print("시작 4바이트:", head)
    print("끝 4바이트  :", tail[4:])
    print("푸터 길이   :", footer_len, "바이트")
    assert head == b"PAR1" and tail[4:] == b"PAR1", "Parquet 파일이 아닙니다"


inspect(sys.argv[1])
```

푸터 길이를 리틀 엔디언 4바이트 정수로 읽은 것은 이 문서가 덧붙인 가정이며, 영상은 이 부분을 말하지 않는다.
이 스크립트는 `PAR1`로 시작하고 끝나는 가짜 파일과 그렇지 않은 파일로 동작을 확인했고, 실제 Parquet 파일로는 돌려 보지 못했다.

두 번째는 PyArrow로 행 그룹과 통계를 확인하는 실험이다.

```python
import pyarrow.parquet as pq

meta = pq.ParquetFile("trips.parquet").metadata
print("행 그룹 수:", meta.num_row_groups)
for i in range(meta.num_row_groups):
    col = meta.row_group(i).column(0).statistics  # 첫 번째 열의 최솟값, 최댓값
    print(i, col.min, col.max)
```

정렬한 파일과 섞은 파일에서 최솟값과 최댓값의 범위가 얼마나 겹치는지 비교하면, 영상이 말한 건너뛰기 효과를 직접 볼 수 있다.

## 체크리스트

- 이 데이터를 주로 읽는 방식이 많은 행의 몇 개 열인지, 한 행 전체인지 적어 두었는가.
- 쿼리가 자주 거는 필터 열이 무엇인지 알고, 그 열로 정렬해 쓰는가.
- 필터 열에 범위를 크게 벗어나는 이상한 값이 없는지 확인했는가.
- 행 그룹 크기를 기본값으로 둘지, 바꾼다면 푸터 크기와 건너뛰기 정밀도를 재 보았는가.
- 압축 방식을 읽기 속도, 쓰기 속도, 저장 크기, 읽는 네트워크 속도를 보고 골랐는가.
- 한 행씩 추가하거나 고쳐야 하는 용도에 Parquet을 쓰고 있지 않은가.

## 기억할 원칙

### 속도는 도구가 아니라 저장 방식에서 온다

영상의 가장 반복되는 결과는 도구를 바꿔도 CSV와 Parquet의 순위가 바뀌지 않는다는 것이다.
읽는 도구를 고르기 전에 파일이 읽는 쪽에게 무엇을 건너뛰게 해 주는지부터 본다.
열 단위 저장은 열을, 행 그룹 통계는 행 그룹을, 페이지 단위 압축은 페이지를 건너뛰게 해 준다.

### 데이터의 질서가 곧 성능이다

정렬 순서와 이상한 값 몇 개가 읽는 바이트를 20배 바꿨다.
저장 형식의 이점은 데이터가 그 형식이 기대하는 모양일 때 나온다.
쓰는 쪽에서 정렬하고 정리하는 비용은 읽는 쪽이 매번 나눠 갚는다.
