# 쿼리 엔진은 읽고 계산하고 옮기는 양을 줄이는 프로그램이고, 고르는 기준은 데이터의 위치와 반복 여부다

영상: [쿼리 엔진은 어떻게 동작할까? Trino와 DuckDB 이해하기 | 최신 데이터 인프라 이해하기 시즌2 EP04](https://news.hada.io/geekcast/data-infra-s2-ep04)

## 소개

GeekNews의 GeekCast가 2026년 11월 5일에 올린 10분 57초짜리 영상이다.
진행은 GeekNews의 xguru 권정혁이 맡고,
데이터 인프라 이해하기 시즌2의 네 번째 편이다.
앞 편([파일에서 테이블로](data-lakehouse.md))은 레이크의 파일을 테이블로
관리하고
이름으로 찾아가는 연결까지 다뤘다.
이번 편은 그 데이터를 실제로 읽고 계산하는 쪽이다.
영상의 질문은 레이크에 저장한 파일에서 SQL 한 줄이 어떻게 분석 결과가
되느냐이다.

예제는 앞 편과 같은 키보드 광고 분석이다.
지난 6개월간 광고를 보고 들어온 고객이 결국 어떤 상품을 주문했는지 알아본다.
방문과 클릭 기록, 주문 내역은 이미 모아 두었다.
그러나 파일이 쌓여 있다고 답이 나오지는 않는다.
광고로 들어온 고객을 찾고, 그 고객의 주문을 연결하고, 상품별로 묶어야 한다.
이 계산을 실행하는 프로그램이 쿼리 엔진(query engine)이라고 영상은 설명한다.

영상은 데이터 인프라 지도에서 저장소의 오른쪽을 Historical과
Predictive로 나눈다.
Historical은 기록된 데이터에서 무슨 일이 있었는지 살펴보는 쪽이다.
Predictive는 그 기록에서 패턴을 배워 아직 모르는 결과를 예측하는 쪽이다.
오늘 다루는 것은 이 중 필요할 때 SQL로 질문하는 Ad Hoc Query Engine이다.
실시간 분석은 6편에서, 머신러닝 라이브러리와 플랫폼은 9편에서 다룬다고 한다.
다음 편은 새 주문과 취소를 분석 쪽에 반영하는 수집과 변환이다.

이 문서는 영상의 수동 한국어 자막과 설명란의 챕터를 읽고 썼다.
화면의 그림은 보지 못했다.
영상의 설명 중 Presto와 Trino의 갈라짐에 관한 이야기는 발표자의 말이며
이 문서가 따로 확인하지 않았다.
「확인하기」의 실험은 이 문서가 DuckDB 2.0.0에서 직접 실행한 것이다.

## 동작 방식

### SQL은 원하는 답을 적는 것이고 실행 계획은 엔진이 세운다

영상은 SQL이 어떤 답을 원하는지 적는 것이라고 설명한다.
엔진은 그 답을 만들려고 실행 계획(execution plan)을 세운다.
어떤 데이터를 먼저 읽고, 어디서 조건을 걸고, 어떻게 연결하고 집계할지를 정한다.
지난 편의 카탈로그와 테이블 정보는 읽을 데이터를 찾는 데 쓰인다.
거기서 찾은 파일을 읽고 실제 계산을 하는 것은 엔진이다.
Parquet나 Iceberg에 넣었다고 알아서 광고 분석을 해 주는 것은 아니다.

카탈로그와 엔진의 역할이 이렇게 갈린다.
카탈로그는 파일과 테이블을 찾는 일을 돕고,
엔진은 계산을 실행한다.
영상은 마지막에 이 구분을 다시 한 번 짚는다.

### 일의 크기는 읽는 양과 계산하는 양과 옮기는 양이다

영상이 엔진을 이해하는 가장 중요한 틀로 내놓는 것은 이 세 양이다.
6개월을 분석하는데 다른 기간의 기록까지 전부 읽을 필요는 없다.
고객과 상품만 필요하므로 배송 주소를 읽을 필요도 없다.
필요한 부분만 읽을 수 있으면 그만큼 할 일이 줄어든다.

방문 기록을 주문과 연결할 때는 같은 고객의 데이터를 만나게 해야 한다.
데이터가 여러 서버에 나뉘어 있으면 그 과정에서 일부를 옮겨야 할 수 있다.
결국 얼마나 읽고, 얼마나 계산하고, 얼마나 옮기는지가 중요하다.
영상은 서버를 더 붙이는 것도 이 일을 줄이거나 나누기 위한 선택이라고 설명한다.

### Trino는 데이터를 옮기지 않고 여러 저장소를 하나의 SQL로 묻는다

Trino는 여러 서버가 나누어 계산하는 SQL 쿼리 엔진이다.
방문 기록과 주문 이력은 레이크에 있고 상품 분류는 회사의 다른 DB에 있다고
해 보자.
광고 유입 고객이 개발자 굿즈 중 어느 종류를 주문했는지 보려면 이 정보가 함께
필요하다.
Trino는 커넥터(connector)로 각 저장소에 접근하고,
하나의 SQL에서 레이크의 데이터와 다른 DB의 상품 정보를 연결한다.
이것을 서로 다른 곳의 데이터를 함께 조회하는 연합 쿼리(federated
query)라고 한다.

Trino를 쓰려고 모든 데이터를 Trino 전용 저장소에 다시 넣을 필요는 없다.
데이터를 그대로 두고 커넥터로 데이터가 있는 곳에 연결해서 묻는다.
질문을 받은 코디네이터(coordinator)가 일을 나누고,
워커(worker)들이 데이터를 읽고 계산해 중간 결과를 주고받으며 최종 결과를 만든다.
연결한 시스템이 처리할 수 있는 계산은 그쪽에 맡기기도 한다.

데이터 인프라 지도에는 Presto라고 적혀 있다.
영상에 따르면 Presto는 Meta가 만들어 공개한 오픈 소스인데,
운영 권한을 둘러싼 갈등으로 초기 개발자들이 나와 독립시킨 프로젝트가
PrestoSQL이다.
이후 상표권 문제로 이름이 Trino로 바뀌었고,
Meta에 남은 쪽은 PrestoDB로 이어져 서로 갈라졌다.
영상은 새로 시스템을 구성한다면 그냥 Trino를 고르면 된다고 말하며
이유로 오픈 소스 커뮤니티의 지지와 풍부한 커넥터 생태계를 든다.

### Dremio는 팀이 같은 뷰를 쓰게 하고 자주 보는 집계를 미리 준비한다

Trino가 여러 저장소를 연결해 묻는 방법이라면,
Dremio는 그 데이터를 회사 사람들이 반복해서 분석하기 편하게 만드는
기능을 더한다.
방문 기록과 주문을 연결하는 SQL을 담당자마다 새로 쓰면 번거롭다.
Dremio에서는 이 연결을 뷰(view)로 만들어 두고 분석가들이 같은 데이터를
함께 쓴다.
Power BI나 Tableau 같은 도구를 붙여 대시보드로 볼 수도 있다.

핵심 기능은 Reflections다.
광고별 주문 수처럼 자주 계산하는 내용을 집계 데이터로 미리 준비해 두는 것이다.
엔진이 조회에 맞는 가속 데이터를 쓰면 매번 방대한 방문 기록부터 다시 계산하는
부담이 준다.
영상은 레이크의 데이터를 편하게 조회하고 대시보드에서 빠르게 쓰게 하는 것을
Dremio의 강점이라고 정리한다.

### Drill과 Impala는 각자 다른 상황을 위한 엔진이다

원래 지도에는 Dremio와 Drill이 슬래시로 함께 적혀 있지만 둘은 서로 다른
프로젝트라고 영상은 짚는다.
Apache Drill은 JSON처럼 구조가 다양한 데이터나 파일을 SQL로 조회할 때
떠올리면 된다.
방문 이벤트 파일을 열어 고객과 캠페인 값을 확인하는 식이고,
테이블을 미리 정의하지 않아도 JSON 파일을 그대로 읽는다는 것이 장점이다.

Apache Impala는 Hadoop 환경에 저장된 데이터를 대화형 SQL로 빠르게 조회하는 데
강점이 있다.
여러 서버가 데이터를 나눠 읽고 동시에 계산하는 MPP(massively parallel
processing) 구조를 쓴다.
Hive Metastore에 있는 테이블 정보를 이용하므로
분석가가 SQL을 바꿔 가며 빠르게 결과를 볼 수 있다.

### DuckDB는 내 프로그램 안에서 파일을 바로 분석한다

DuckDB는 분석용 SQL을 실행하는 DB인데 내 프로그램 안에서 함께 실행할 수 있다.
별도의 DB 서버를 먼저 마련하지 않아도 된다는 것이 매력이다.
광고 캠페인 하나의 방문 기록과 주문 파일을 받았다면
노트북에서 Parquet 파일을 바로 읽어 고객을 연결하고 어떤 상품을 주문했는지
확인한다.
파일을 다른 서버에 올리고 테이블을 만들고 다시 데이터를 넣는 준비를
줄이는 것이다.
Python에서 계산한 결과를 받아 그래프를 그리는 일도 자연스럽게 이어진다.
영상은 성능 좋은 멀티 코어 CPU를 잘 활용해 로컬에서도 자유롭게 분석할 수
있다고 말한다.

지난 편의 DuckLake도 여기서 이어진다.
DuckLake가 파일 목록과 테이블 상태를 관리하면 DuckDB가 그 정보로 데이터를 읽고
계산한다.
파일을 직접 분석하는 데서 관리되는 테이블을 분석하는 쪽으로 넓히는 셈이다.

### 같은 Iceberg 테이블을 여러 엔진이 읽는다

영상의 마지막 예는 레이크에 저장한 테이블을 웨어하우스에서도 분석하는 것이다.
Spark로 정리한 Iceberg 주문 테이블을 Trino로 조회하고 Snowflake에서도 분석한다.
같은 데이터를 도구마다 따로 옮기는 부담을 줄일 수 있다고 영상은 말한다.

| 엔진   | 영상이 말하는 강점                                         | 어울리는 상황                             |
| ------ | ---------------------------------------------------------- | ----------------------------------------- |
| Trino  | 커넥터로 여러 저장소를 하나의 SQL로 조회하는 연합 쿼리     | 방문과 주문은 레이크에, 상품은 다른 DB에  |
| Dremio | 공유 뷰와 Reflections로 반복 분석과 대시보드 가속          | 담당자마다 같은 연결 SQL을 다시 쓰는 팀   |
| Drill  | 테이블 정의 없이 JSON 같은 구조가 다양한 파일을 SQL로 조회 | 방문 이벤트 파일을 바로 열어 보는 일      |
| Impala | Hadoop 데이터를 MPP 병렬 처리로 대화형 조회                | 이미 Hadoop을 쓰는 회사의 SQL 탐색        |
| DuckDB | 내 프로그램 안에서 Parquet를 서버 없이 분석                | 노트북에서 받은 파일을 Python과 함께 분석 |

## 엔진을 고르는 기준

영상의 정리는 제품 이름을 외우기보다 모두 SQL로 데이터를 읽고 계산한다는 점을
기억하라는 것이다.
이 도구들이 같은 칸에 있는 이유는 파일이나 외부 저장소에 있는 데이터를 SQL로
분석하게 해 주기 때문이다.
다만 연결하는 저장소, 테이블 정보를 다루는 방식,
조회를 빠르게 하는 구조는 서로 다르다.

고르는 기준은 세 가지로 요약된다.
첫째, 데이터가 내 컴퓨터에 있는지 여러 저장소에 흩어져 있는지 본다.
캠페인의 Parquet 파일을 받아 내 프로그램에서 바로 분석한다면 DuckDB가 가장 쉽고
빠른 선택이다.
여러 저장소의 방문 기록과 주문과 상품 정보를 SQL로 함께 조회한다면 Trino 같은
연합 조회 엔진을 놓을 수 있다.
둘째, 회사가 이미 Hadoop 같은 시스템을 쓰고 있는지 본다.
셋째, 같은 분석을 자주 반복하는지 본다.
반복한다면 미리 준비한 집계 결과로 조회를 빠르게 하는 기능이 중요해진다.

## 트레이드오프

### 데이터를 복사하지 않는 편리함에는 이동과 부담이 남는다

Trino는 미리 복사하지 않아도 되지만 데이터 이동까지 없어지는 것은 아니라고
영상은 분명히 말한다.
연결하고 집계하는 동안 네트워크를 쓰고 원본 DB에 부담을 줄 수도 있다.
여러 곳을 연결하는 편리함과 그 조회의 비용을 함께 봐야 한다.

반대로 DuckDB처럼 파일을 내 쪽으로 가져와 분석하면 이동은 처음 한 번의
복사로 끝난다.
대신 팀이 같은 기준으로 계산하는 일은 개인의 파일 단위에서는 어렵다.
이 대비는 영상이 직접 말한 것이 아니라 두 설명을 겹쳐 본 이 문서의 해석이다.

### 미리 준비한 집계는 빠르지만 원본이 바뀌면 다시 맞춰야 한다

Dremio의 Reflections는 광고별 주문 수 같은 자주 쓰는 집계를 미리 계산해 둔다.
영상은 이로써 매번 방대한 방문 기록부터 다시 계산하는 부담이 준다고만 말한다.
미리 계산한 값은 원본에 새 주문과 취소가 들어오면 다시 맞춰야 한다.
영상은 이 비용을 말하지 않고, 이 문장은 이 문서의 추론이다.
다음 편이 새 주문과 취소를 분석 쪽에 반영하는 수집과 변환을 다루므로
그쪽에서 답이 나올 수 있다.

## 함정

### 제품 이름이 아니라 같은 일을 하는 공통점부터 본다

영상은 Trino, Dremio, Drill, Impala, DuckDB가 모두 SQL로 데이터를 읽고
계산한다는 점을 먼저 기억하라고 한다.
제품 이름을 외우면 각 제품이 서로 대체재인지 보완재인지 헷갈린다.
지도의 Dremio와 Drill이 슬래시로 묶여 있다고 같은 제품은 아니다.

### Presto, PrestoDB, PrestoSQL, Trino를 같은 이름으로 읽는다

영상의 설명대로라면 Presto라는 이름은 지금 Trino와 PrestoDB로 갈라져 있다.
PrestoSQL은 이름을 바꾸기 전의 Trino이다.
자료를 찾을 때 이름이 섞이면 서로 다른 프로젝트의 문서를 같은 제품의 것으로 읽을
수 있다.

### 파일 형식에 넣었으니 분석이 된다고 기대한다

영상은 Parquet나 Iceberg에 넣었다고 알아서 광고 분석을 해 주는 것은 아니라고 말하고,
읽고 계산하는 일은 엔진이 한다고 설명한다.
파일 형식과 테이블 형식은 저장하는 방법이고,
분석은 엔진이 실행하는 계획에서 나온다.

### 연합 조회가 원본의 부담도 없앤다고 기대한다

Trino가 미리 복사하지 않는다는 말을 원본이 한가하다는 말로 읽으면 안 된다.
조회가 몰리면 원본 DB가 먼저 부담을 받는다.
영상이 이를 직접 경고하고 있다.

## 비평

### 선택 기준이 조건이고 측정이 아니라서 경계가 흐리다

영상의 기준은 데이터의 위치, 기존 Hadoop 환경, 반복 여부라는 세 조건이다.
이 조건은 어떤 엔진을 먼저 후보에 올릴지 정하는 데는 도움이 된다.
그러나 데이터가 얼마나 커지면 노트북의 DuckDB에서 Trino로 옮겨야 하는지,
몇 개의 동시 사용자부터 공유 엔진이 필요한지는 말하지 않는다.
벤치마크나 비용 숫자도 영상에 없다.

따라서 영상의 기준은 출발점이지 결정 규칙이 아니다.
자기 데이터와 쿼리로 같은 질문을 두 엔진에 돌려 보는 일이 남는다.

### 새로 구성한다면 그냥 Trino라는 권고는 조건 없이 단정한다

영상은 새로 이런 조회 시스템을 구성한다면 그냥 Trino를 고르면 된다고 말한다.
근거로 든 것은 오픈 소스 커뮤니티의 지지와 커넥터 생태계다.
이 권고는 앞서 말한 세 조건과 어떻게 맞물리는지 설명하지 않는다.
이미 Hadoop을 쓰는 회사나 분석가 몇 명이 파일을 받아 보는 팀에게도
같은 권고가 맞는지는 영상만으로 알 수 없다.
이 권고는 연합 조회가 필요한 상황을 전제한 말로 읽는 것이 안전하다.

### 갈라진 이유에 대한 설명은 발표자의 요약이다

Presto가 Trino와 PrestoDB로 갈라진 경위는 운영 권한을 둘러싼 갈등과 상표권
문제라고
영상이 두 문장으로 말한다.
이 설명은 영상이 출처를 밝히지 않는 요약이며, 이 문서가 확인하지 않았다.
이 경위가 중요한 것은 이름이 갈라진 사실이지 누구의 잘못인지가 아니다.
영상도 새 시스템에는 Trino를 고르라는 결론으로 바로 넘어간다.

## 확인하기

영상의 핵심은 필요한 부분만 읽고, 조건을 먼저 걸고,
연결해서 집계한다는 흐름이다.
아래 실험은 이 흐름이 DuckDB의 실행 계획에 어떻게 나타나는지 직접 본다.
DuckDB 2.0.0에서 실행했고,
설치는 `pip install duckdb`로 한다.

```python
import duckdb

con = duckdb.connect()

# 방문 기록 20만 건(캠페인과 사용자 에이전트 열 포함)을 Parquet로 만든다.
con.execute("""
COPY (
  SELECT
    DATE '2026-01-01' + CAST(i % 308 AS INTEGER) AS visit_date,
    i % 50000 AS customer_id,
    CASE WHEN i % 5 = 0 THEN 'keyboard_ad'
         WHEN i % 5 = 1 THEN 'mouse_ad' ELSE 'organic' END AS campaign,
    'Mozilla/5.0 (long user agent string number ' || (i % 97) || ')' AS user_agent
  FROM range(200000) t(i)
) TO 'visits.parquet' (FORMAT parquet, ROW_GROUP_SIZE 20000)
""")

# 주문 5만 건(배송 주소 열 포함)을 Parquet로 만든다.
con.execute("""
COPY (
  SELECT
    i AS order_id,
    i % 50000 AS customer_id,
    ['keyboard','mouse','monitor','cable'][1 + (i % 4)] AS product,
    DATE '2026-02-01' + CAST(i % 270 AS INTEGER) AS order_date,
    'Seoul, street ' || (i % 9973) || ', building ' || (i % 313) AS shipping_address
  FROM range(50000) t(i)
) TO 'orders.parquet' (FORMAT parquet, ROW_GROUP_SIZE 10000)
""")

# 광고 유입 고객의 주문을 상품별로 센다(영상의 예제와 같은 질문).
query = """
SELECT o.product, count(*) AS orders
FROM 'visits.parquet' v
JOIN 'orders.parquet' o USING (customer_id)
WHERE v.campaign = 'keyboard_ad'
  AND v.visit_date >= DATE '2026-05-05'
GROUP BY o.product
ORDER BY orders DESC
"""
for _, plan in con.execute("EXPLAIN " + query).fetchall():
    print(plan)
```

실행 결과의 실행 계획에서 Parquet 스캔 두 곳을 보면 이렇다.

```text
Parquet Scan (orders)           Parquet Scan (visits)
  Projections: customer_id,       Projections: customer_id
               product            Filters: campaign = 'keyboard_ad',
                                           visit_date >= '2026-05-05'
```

주문 파일은 다섯 열이 있는데 계획이 읽는 열은 `customer_id`와 `product`
둘뿐이다.
`order_id`, `order_date`, `shipping_address`는 계획에 나타나지 않는다.
방문 파일은 `customer_id` 하나만 읽고,
`campaign`과 `visit_date` 조건이 스캔 단계(Filters)에 붙어 있다.
영상이 말한 6개월 밖의 기록과 배송 주소를 건너뛴다는 설명이 이 계획에 대응한다.
조인은 `customer_id`로 이뤄지고 그 뒤에 상품별 집계와 정렬이 이어진다.

이 실험은 한 대의 컴퓨터에서 파일 두 개를 읽는 가장 작은 경우다.
여러 서버로 나눠 계산하거나 다른 DB를 연결하는 Trino의 동작은 이 문서가 직접
실행해 보지 못했다.

## 체크리스트

- 분석할 데이터가 내 컴퓨터에 있는 파일인지 여러 저장소에 흩어져 있는지 적었다.
- 회사가 이미 Hadoop 같은 시스템을 쓰고 있는지 확인했다.
- 같은 분석을 반복하는지 정했고, 반복한다면 미리 계산할 집계가 무엇인지 적었다.
- 쿼리의 실행 계획에서 읽는 열과 조건이 필요한 만큼만 나오는지 보았다.
- 여러 저장소를 연결해 조회한다면 원본 DB가 받을 부담을 확인했다.
- 자료에서 Presto, PrestoDB, PrestoSQL, Trino 중 어느 프로젝트를 말하는지 구분했다.
- 같은 테이블을 여러 엔진이 읽는다면 어떤 엔진이 만들고 어떤 엔진이 읽는지 적었다.

## 기억할 원칙

### 카탈로그는 찾고 엔진은 계산한다

지난 편은 이름에서 파일까지 찾아가는 길이었고,
이번 편은 그 파일을 읽어 계산하는 길이다.
영상은 광고 유입 고객의 방문 기록을 읽고, 주문을 고객 번호로 연결하고,
상품별 주문 수를 집계하는 흐름으로 이를 요약한다.
테이블 형식과 카탈로그를 정했다고 분석이 끝난 것이 아니라
그 위에서 실행할 엔진을 따로 정해야 한다.

### 엔진은 읽는 양, 계산하는 양, 옮기는 양을 줄이는 방식으로 이해한다

제품마다 이름과 기능이 다르지만 영상이 쓰는 틀은 하나다.
필요한 부분만 읽고, 계산을 나누거나 미리 해 두고, 옮기는 데이터를 줄인다.
새 엔진을 만나면 어떤 양을 어떻게 줄이는 제품인지를 먼저 묻는다.
이 질문에 답할 수 있으면 제품 이름을 외우지 않아도 된다.
