# 파일에서 테이블로: 데이터 레이크의 파일 형식, 테이블 형식, 카탈로그를 나눠 보기

## 소개

GeekNews의 GeekCast가 2026년 10월 29일에 올린 13분 13초짜리 영상이다.
데이터 인프라 이해하기 시즌2의 세 번째 편이고,
앞 편은 데이터 웨어하우스와 데이터
레이크를 다뤘다.
이번 편은 레이크 쪽을 더 들여다본다.
DB에서는 주문 테이블을 조회하면 되는데,
레이크에는 주문 파일이 여러 개 쌓여 있다.
그 파일 안에 데이터를 어떻게 담고, 여러 파일을 어떻게 하나의 주문 테이블처럼
조회하느냐가
영상의 질문이다.

영상의 답은 세 가지 역할이다.
파일 안에 데이터를 담는 파일 형식, 여러 파일을 테이블로 관리하는 테이블 형식,
이름으로 테이블을 찾는 카탈로그이다.
실제로 파일을 읽고 계산하는 엔진은 다음 편(Trino와 DuckDB)에서 다룬다고 영상이
말한다.

예제는 지난 6개월간 집행한 키보드 광고 캠페인의 효과 분석이다.
광고를 타고 방문한 고객이 어떤 상품을 둘러보고 장바구니에 무엇을 담고 무엇을
주문했는지 본다.
방문, 클릭, 장바구니 같은 행동은 JSON 이벤트로 기록되고 실제 주문은
서비스의 DB에
저장된다.
하루에 100만 건의 행동 이벤트가 쌓이면 6개월(180일)에 약 1억 8천만 건이다.
주문 내용만으로는 고객이 어떤 경로로 샀는지 알 수 없으므로,
레이크에 모은 행동 기록과 주문 내역을 연결해야 광고에서 구매까지의
흐름이 보인다.

이 문서는 영상의 자막(자동 생성)과 설명란의 챕터를 읽고 썼다.
화면의 그림은 보지 못했고 아래 확인하기의 명령은 이 문서가 실행해 보지
못한 것이다.
자동 자막은 이름을 자주 틀리게 적는다(「아이스버그」, 「파케이」 등).
이 문서는 표준 이름으로 적었다.

## 동작 방식

### 분석가의 SQL이 파일에 닿는 길

분석가는 SQL에 주문 테이블 이름을 쓴다.
엔진은 카탈로그에서 그 이름에 해당하는 테이블 정보를 찾고,
그 정보를 따라 저장소의 데이터 파일을 읽는다.
영상은 이 순서를 세 역할이 연결되는 길로 보여 준다.

| 역할        | 하는 일                                        | 영상이 든 이름                                            |
| ----------- | ---------------------------------------------- | --------------------------------------------------------- |
| 파일 형식   | 파일 안에 데이터를 어떤 방식으로 담을지 정한다 | Parquet, ORC, Avro                                        |
| 테이블 형식 | 여러 파일을 하나의 테이블로 관리한다           | Apache Iceberg, Delta Lake                                |
| 카탈로그    | 테이블 이름에서 필요한 정보를 찾게 해 준다     | Hive Metastore, AWS Glue Data Catalog, REST 방식 카탈로그 |
| 엔진        | 실제로 데이터를 읽고 계산한다                  | 다음 편(Trino, DuckDB)                                    |

### 파일 형식은 값을 담는 방식이다

파일을 보관하는 곳은 객체 저장소이다.
Amazon S3, Google Cloud Storage, Azure Blob이 그 예이고 S3에서는
보관함을 버킷이라고
부른다.
버킷 안에 주문 파일이 놓이고, Parquet는 그 파일 안에 데이터를 담는 방식이다.

Apache Parquet는 분석용 컬럼 기반 파일 형식이다.
데이터를 컬럼별로 모아 둔다.
상품별 주문 금액을 더하려면 상품과 금액 컬럼만 필요하고 배송
주소까지 읽을 필요가
없다.
비슷한 값을 모아 압축할 수 있다는 점도 분석에 유리하다.
그래서 CSV나 JSON으로 받은 주문 내역을 반복해서 분석할 때는 Parquet로
바꿔 저장하기도
한다.
영상은 파일 형식을 고르는 일이 데이터를 어떤 방식으로 담고 읽을지
고르는 일이라고
말한다.

Apache ORC도 컬럼 기반 파일 형식이고 Hive와 함께 많이 쓰인다.
Apache Avro는 목적이 조금 다르다.
주문 번호와 상품, 금액을 가진 레코드를 정해진 구조로 저장하거나 전달하는 직렬화
형식이다.
항목과 자료형을 정하는 스키마를 써서 보내는 쪽과 받는 쪽이 같은
규칙으로 데이터를
해석하게 한다.
나중에 쿠폰 코드 항목이 추가돼도 호환 규칙을 지키면 구조를 넓힐 수 있고,
쿠폰 코드의 기본값을 정해 두면 쿠폰 코드가 없던 예전 주문도 읽을 수 있다.
여러 서비스가 이벤트를 주고받을 때 유용하며 이벤트 전달과의 연결은
6편에서 다룬다고
한다.
영상의 기억법은 Parquet와 ORC는 컬럼을 골라 읽는 분석 장면, Avro는 구조가 정해진
레코드를 주고받는 장면이다.
각 형식이 그 용도로만 쓰인다는 뜻은 아니라고 단서를 단다.

### 테이블 형식은 파일의 변경을 관리하는 규칙이다

파일 안의 데이터 형식을 정했다고 주문 테이블의 변경이 관리되는 것은 아니다.
A-1001 주문이 취소되어 분석용 주문 내역에 반영되는 상황을 보자.
읽는 쪽은 어떤 파일이 최신 상태에 속하는지 알아야 하고,
변경 중에 조회하더라도 완성되지 않은 상태를 읽으면 안 된다.
이때 필요한 것이 테이블 형식이다.
테이블을 이루는 파일, 컬럼 구조, 확정된 상태를 관리하는 규칙이고,
이 정보를 메타데이터라고 한다.

대표 이름은 Apache Iceberg와 Delta Lake이다.
Parquet 대신 하나를 고르는 관계가 아니다.
Parquet 파일을 Iceberg나 Delta Lake 테이블로 관리할 수 있다.
Iceberg는 스냅샷으로 테이블의 확정된 상태를 표현한다.
어느 파일들이 그 상태에 속하는지를 연결해 둔 것이고 전체 데이터를
매번 복사하지는
않는다.
Delta Lake는 파일의 추가와 제외 같은 변경을 트랜잭션 로그로 기록하고 그
기록으로 테이블
상태를 구성한다.
여기서 로그는 고객의 취소 사유를 적는 업무 기록이 아니라 테이블을 관리하는 변경
기록이다.
구조는 다르지만 둘 다 데이터 파일을 쓰고,
조회가 확정된 테이블 상태를 읽도록 한다.
영상은 스냅샷과 로그의 세부 구조보다 두 이름이 테이블 관리라는 같은
자리에 있다는
점을 먼저 보라고 한다.
실제로 파일을 읽고 변경을 실행하는 것은 엔진이고,
Iceberg가 혼자 주문을 가져오거나
집계하는 프로그램은 아니다.

Hive ACID도 이 문제와 연결된다.
Hive 테이블에 데이터를 추가하고 수정하고 삭제할 때 트랜잭션을 지원하는 기능이고,
완전한 ACID 테이블에는 ORC를 쓴다.
ACID는 원자성, 일관성, 격리성, 지속성이다.
변경을 전부 반영하거나 전혀 반영하지 않고, 규칙을 지키고, 다른 작업과의 충돌을
다루고, 확정한 결과를 보존한다는 성질이다.
영상은 Iceberg가 테이블의 변경을 관리하는 것은 같지만 특정 엔진에
종속되지 않는 열린
테이블 형식이라는 점에 초점이 있고, Spark나 Trino 같은 여러 엔진이
같은 형식을 함께
쓴다고 설명한다.

### 카탈로그는 이름에서 테이블 정보로 가는 연결이다

SQL에 파일 주소를 하나씩 적는 대신 주문 테이블 이름을 쓰고 싶다.
엔진은 그 이름이 어떤 테이블을 가리키는지 알아야 하고 이 연결을 관리하는 것이
카탈로그이다.
Iceberg를 예로 들면 엔진이 카탈로그에서 주문 테이블의 메타데이터 위치를 찾고,
그 정보를 따라 스냅샷과 데이터 파일로 간다.
주문 취소가 반영되어 파일 구성이 바뀌어도 분석가는 같은 테이블 이름을 쓰면 된다.
카탈로그에 주문 데이터가 들어 있는 것은 아니고,
테이블을 찾아가는 데 필요한 정보를
관리한다.

시즌1에서 본 Hive Metastore가 이 역할과 연결된다.
Iceberg에서는 Hive Metastore, AWS Glue Data Catalog,
REST 방식 카탈로그 등을 쓸 수 있고,
지원하는 구성과 연결 방식은 도구마다 다르다.
회사 전체의 데이터를 검색하고 담당자와 업무 의미까지 확인하는 이야기는 8편에서
넓힌다고 한다.

### DuckLake는 이 구성을 단순하게 만드는 접근이다

DuckLake는 DuckDB 팀이 최근에 낸 오픈소스이다.
주문 데이터는 Parquet 파일에 두고, 테이블 이름과 파일 목록과 변경
이력은 SQL DB에서
함께 관리한다.
테이블 관리와 카탈로그 정보를 한 곳에 모으는 구성이다.
장점은 노트북 한 대에서도 가볍게 시작할 수 있다는 것이다.
DuckDB와 로컬 파일, Parquet 파일이 든 폴더만으로 데이터를 테이블로
관리하는 구성을
만들 수 있고, 별도의 카탈로그 서버를 띄우지 않고 파일 기반
레이크하우스를 써 볼 수
있다.
여러 사람이 공유해야 하면 카탈로그를 PostgreSQL 같은 DB에 두는 구성으로 넓힌다.
계산은 각자의 엔진이 하고 테이블 상태는 공유하는 방식이다.
역할은 같고 이를 구현하는 방법이 달라진다는 것이 영상의 요점이다.

### 파일을 테이블로 관리하면 얻는 것

영상은 네 가지를 든다.

| 기능        | 해결하는 문제                                                   | 영상의 단서                                                           |
| ----------- | --------------------------------------------------------------- | --------------------------------------------------------------------- |
| 타임 트래블 | 어제 보고서가 읽던 테이블 상태를 지정해 당시 결과를 다시 읽는다 | 주문 취소를 되돌리는 것이 아니고, 당시 기록과 파일이 남아 있어야 한다 |
| 스키마 변경 | 해외 배송을 시작해 배송 국가 컬럼을 추가한다                    | 예전 주문의 값을 저절로 채워 주지는 않는다                            |
| 파티셔닝    | 날짜별로 나눠 배치해 필요한 날짜만 찾아 읽는다                  | 배치 기준을 바꾸는 것과 기존 파일을 다시 정리하는 작업은 구분한다     |
| 컴팩션      | 작은 파일을 적절한 크기로 합쳐 읽기 부담을 줄인다               | 주문 내용과 금액은 그대로이다                                         |

타임 트래블은 주문 날짜로 어제 주문만 고르는 것과 다르다.
그것은 데이터의 내용으로 거르는 일이고,
타임 트래블은 분석에 썼던 테이블의 과거 상태를
다시 읽는 일이다.
영상은 구체적인 지원과 동작이 테이블 형식과 엔진에 따라 달라진다고 단서를 단다.

### 레이크하우스는 같은 테이블을 여러 작업이 쓰는 구조이다

담당자는 주문 테이블을 SQL로 집계해 보고서를 만들고,
개발자는 키보드를 산 고객이 티셔츠도 사는지 분석해 상품 추천에 쓴다.
저장소의 파일을 테이블로 관리하면 두 작업이 같은 주문 테이블을 쓸 수 있고,
작업마다 데이터를 따로 옮겨 놓고 맞추는 부담이 줄어든다.
파일 기반 레이크에 이런 테이블 관리와 분석 기능을 결합하는 접근이
레이크하우스이다.

게임 회사의 예도 같은 모양이다.
플레이어가 어느 스테이지에서 실패하고 언제 종료하는지를 기획자는 보고서로 보고,
데이터 사이언티스트는 다음 주에도 플레이할 사용자를 예측하는 모델을 만든다.
각 팀이 기록을 따로 복사해 관리하면 늦게 들어온 기록과 수정 사항을 각각
반영해야 하고
어느 데이터를 기준으로 계산했는지도 맞춰야 한다.
레이크하우스에서는 플레이 기록을 하나의 테이블로 관리하고 목적에 맞는
가공만 각 작업이
따로 한다.
이 접근을 발전시킨 대표 플랫폼으로 영상은 Databricks를 들며, Delta Lake를 쓰고
Apache Iceberg도 지원한다고 한다.
어떤 주문을 매출이나 추천 학습에 포함할지,
취소와 환불의 집계 날짜 기준은 각 작업에서
정하며 이는 7편에서 다룬다고 한다.

## 트레이드오프

### 타임 트래블은 과거를 남겨 두는 비용을 요구한다

영상이 직접 말한 조건은 당시 기록과 데이터 파일이 남아 있어야 한다는 것이다.
이 문서의 해석으로는 이 조건이 비용이다.
과거를 다시 읽을 수 있으려면 이전 상태에 속한 파일을 지우지 않아야
하므로 보관하는
저장 용량이 늘고, 어디까지 남길지의 기준이 필요하다.
영상은 이 보관 기간과 정리 방법을 말하지 않는다.
보고서를 다시 만들어야 하는 기간(예: 한 달 전 결산)에 맞춰 보관 기간을
정해야 한다.

### 열린 형식은 엔진의 선택권을 주고 조합의 책임을 남긴다

Iceberg가 특정 엔진에 종속되지 않는 열린 형식이라는 점은 Spark와 Trino 같은 여러
엔진이 같은 테이블을 쓰게 한다.
대신 영상이 단서로 반복하듯 지원하는 구성과 연결 방식은 도구마다 다르다.
엔진과 카탈로그와 테이블 형식의 조합이 모두 서로를 지원해야 하므로,
형식이 열려 있다는 것이 모든 조합이 된다는 뜻은 아니다.
이 호환의 확인은 고르는 쪽의 몫이다.

### 가볍게 시작하는 구성과 공유하는 구성은 운영 부담이 다르다

DuckLake는 노트북 한 대에서 시작하고 공유가 필요하면 PostgreSQL 같은
DB로 카탈로그를
옮긴다.
시작 비용은 낮지만 공유하는 순간 DB가 새 운영 대상이 된다.
영상은 이 단계에서 쓰는 쪽이 늘 때의 동시성이나 접근 통제를 다루지 않는다.

## 함정

### 파일 형식과 테이블 형식을 둘 중 하나로 고르려 한다

영상이 직접 짚는 오해이다.
Parquet는 값을 담는 방식이고 Iceberg는 변경을 관리하는 방식이어서 서로
대체하지 않는다.
Parquet 파일을 Iceberg 테이블로 관리한다.
S3와 Parquet와 Iceberg가 함께 나오는 것은 같은 일을 하는 제품 셋이 아니라 저장과
파일 형식과 테이블 관리를 각각 맡기 때문이다.

### 카탈로그에 데이터가 들어 있다고 생각한다

카탈로그는 주문 데이터가 아니라 위치와 구조 정보를 보관한다.
카탈로그가 사라져도 파일은 저장소에 남지만,
이름에서 파일로 가는 연결을 잃는다는 점이
영상의 구분에서 따라 나오는 결과이다.
이 문서는 이 결과를 실제 도구에서 확인하지 못했다.

### 스키마 변경과 파티션 변경이 과거 데이터까지 고친다고 기대한다

영상은 두 가지를 분명히 구분한다.
새 컬럼을 추가해도 예전 주문의 배송 국가가 저절로 채워지지 않는다.
파티션 기준을 바꾸는 것(월별에서 일별로)과 기존 파일을 새 기준으로 다시 정리하는
작업은 다른 일이다.
관리 기능이 구조의 변경을 기록하는 것과 데이터를 다시 쓰는 것은 별개이다.

### 타임 트래블을 날짜 필터로 착각한다

주문 날짜로 어제 주문만 고르는 것은 데이터의 값으로 거르는 일이고,
타임 트래블은 테이블의 상태를 고르는 일이다.
취소가 반영되기 전의 상태를 읽고 싶다면 날짜 필터로는 안 된다.

## 확인하기

아래는 영상의 구분을 로컬에서 시험하는 DuckDB 예이다.
이 문서가 DuckDB를 설치하지 못해 실행해 보지 못한 명령이고,
DuckLake의 확장 이름과 시간 여행 문법은 DuckDB 버전에 따라 다를 수
있으니 공식 문서를
먼저 확인한다.

### Parquet가 필요한 컬럼만 읽는지 본다

```sql
-- 주문 표본 100만 행을 CSV로 만든 뒤 Parquet로 바꿔 저장한다
COPY (
  SELECT
    'A-' || i AS order_id,
    'keyboard' AS product,
    (i % 100) * 1000 AS amount,
    DATE '2026-05-01' + (i % 180)::INT AS order_date,
    'paid' AS status,
    repeat('x', 100) AS shipping_address
  FROM range(1, 1000001) t(i)
) TO 'orders.csv' (HEADER, DELIMITER ',');

COPY (SELECT * FROM 'orders.csv') TO 'orders.parquet' (FORMAT parquet);

-- 파일 크기를 비교하고, 컬럼 두 개만 읽는 집계와 전체를 읽는 조회의 시간을 비교한다
SELECT product, sum(amount) FROM 'orders.parquet' GROUP BY product;
SELECT * FROM 'orders.parquet' LIMIT 10;
SELECT * FROM parquet_metadata('orders.parquet') LIMIT 5;
```

CSV와 Parquet의 파일 크기 차이, 컬럼 두 개만 읽는 집계의 시간을
`shipping_address`까지
읽는 조회와 비교해 본다.

### 테이블 형식이 만드는 상태를 본다

```sql
INSTALL ducklake;
LOAD ducklake;

-- 메타데이터는 로컬 DB 파일에, 데이터는 lake_files 폴더의 Parquet에 둔다
ATTACH 'ducklake:meta.ducklake' AS lake (DATA_PATH 'lake_files/');

CREATE TABLE lake.orders AS SELECT * FROM 'orders.parquet';
UPDATE lake.orders SET status = 'canceled' WHERE order_id = 'A-1001';

-- 스냅샷 목록을 보고, 취소 전 상태를 지정해 읽는다 (문법은 버전에 따라 확인)
SELECT * FROM ducklake_snapshots('lake');
SELECT * FROM lake.orders AT (VERSION => 1) WHERE order_id = 'A-1001';
SELECT * FROM lake.orders WHERE order_id = 'A-1001';
```

마지막 두 조회가 취소 전과 후의 다른 상태를 돌려주는지 보고,
`lake_files` 폴더에 어떤 Parquet 파일이 새로 생겼는지 목록으로 확인한다.

## 체크리스트

- 파일 형식, 테이블 형식, 카탈로그, 엔진을 서로 다른 선택으로 구분하고 있는가?
- 반복해서 분석하는 데이터를 CSV나 JSON 그대로 두지 않고 컬럼 기반 형식으로 바꿨는가?
- 취소나 수정이 일어날 때 조회가 완성되지 않은 상태를 읽지 않도록 테이블 형식을 쓰는가?
- 쓰려는 엔진과 카탈로그와 테이블 형식의 조합이 서로를 지원하는지 확인했는가?
- 타임 트래블이 필요한 기간을 정하고 그 기간 동안 파일을 남기는 설정을 했는가?
- 새 컬럼을 추가한 뒤 예전 데이터의 기본값을 어떻게 다룰지 정했는가?
- 작은 파일이 쌓이는 테이블에 컴팩션 주기를 정했는가?
- 여러 팀이 같은 테이블을 쓴다면 취소와 환불의 집계 기준을 팀별로 따로 정하는가?

## 기억할 원칙

### 이름과 파일 사이를 세 칸으로 나눠 본다

분석가가 쓰는 테이블 이름에서 실제 값까지는 카탈로그가 위치를 찾고,
테이블 형식이 어떤
파일들이 현재 상태인지 알려 주고, 파일 형식이 값을 읽는 방식을 정한다.
문제가 생기면 어느 칸의 문제인지 먼저 가른다.
테이블을 못 찾으면 카탈로그, 취소가 반영되지 않았으면 테이블 형식,
쿼리가 느리면 파일 형식과 파일의 크기와 배치를 의심한다.
이 분류는 영상의 구분을 문제 진단의 순서로 바꿔 읽은 이 문서의 해석이다.

### 같은 바탕 데이터를 함께 쓰고 가공만 따로 한다

영상의 마지막 예(쇼핑몰의 주문, 게임의 플레이 기록)가 모두 같은 구조이다.
바탕이 되는 기록은 한 테이블로 함께 관리하고,
보고서나 학습 데이터 같은 목적에 맞는
가공은 각 작업이 한다.
팀마다 사본을 만들면 늦게 들어온 기록과 수정 사항을 각각 반영해야
하고 계산 기준도
어긋난다.
이 원칙은 도구 선택보다 앞서는 것이고, 어떤 도구를 쓰든 사본을 줄이는
방향이 이 영상의
핵심이다.
