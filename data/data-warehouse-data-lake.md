## 소개

GeekNews의 GeekCast에서 2026년 10월 22일에 올린 15분 남짓한 영상이다.
진행자는 xguru이고, 시즌2 두 번째 편으로 데이터 웨어하우스와 데이터 레이크를 다룬다.
주문을 처리하는 데이터베이스가 이미 있는데 분석용 저장소를 따로 두는 이유를 가상의 온라인 쇼핑몰 주문으로 풀어 간다.
영상은 다음 편에서 이어 갈 Parquet, Iceberg, 카탈로그 이야기로 끝난다.

영상의 약속은 하나다.
웨어하우스는 정리된 표, 레이크는 원본 파일이라는 단순한 구분을 믿지 말고,
데이터를 담는 곳, 데이터의 구조를 관리하는 방식, 읽고 계산하는 엔진을 나눠서 보라는 것이다.
이 문서는 그 구분을 실제 선택에 쓸 수 있도록 정리한다.

## 동작 방식

### 운영과 분석은 데이터를 읽는 방식이 다르다

고객이 주문 내역 화면을 열면 그 고객의 주문 몇 건을 빨리 찾아 보여 줘야 한다.
결제할 때는 해당 주문의 결제 상태를 바꾸고 재고를 정확히 처리해야 한다.
서비스 데이터베이스는 이런 일, 곧 지금 들어오는 주문을 받아 서비스가 제대로 돌아가게 하는 일을 맡는다.

지난달 매출을 분석하는 일은 성격이 다르다.
지난달 주문을 쭉 읽고, 취소와 환불을 반영하고, 상품별로 묶어 금액을 더해야 한다.
광고비와 비교하려면 광고 시스템의 데이터도 필요하다.
영상은 앞의 작업을 트랜잭션 처리(OLTP), 뒤의 작업을 분석 처리(OLAP)라고 부른다.

서비스 데이터베이스에서도 SQL로 매출을 계산할 수 있고, 데이터가 작고 질문이 단순하면 그것으로 충분하다.
문제는 분석이 늘어날 때 생긴다.
주문을 받아야 하는 데이터베이스에서 큰 집계를 계속 돌리면 서로 자원을 두고 다투어 서비스에 영향을 줄 수 있다.
다른 시스템의 데이터를 합쳐야 하고 예전 상태도 남겨야 한다.
서비스는 현재 고객 정보만 보여 주면 되지만, 분석은 주문 당시 고객이 어느 지역에 있었는지를 알아야 할 수 있다.
이래서 서비스가 쓰는 데이터와 분석에 쓸 데이터를 분리해서 관리하기 시작한다.

### 데이터 웨어하우스가 하는 일

영상은 웨어하우스를 파일을 넣어 두는 창고로 보면 역할이 안 보인다고 말한다.
여러 시스템의 데이터를 모아 분석할 수 있는 테이블로 관리하고, SQL로 읽고 계산할 수 있게 하는 기반이다.
주문, 결제, 환불, 광고비가 서로 다른 시스템에서 와도 주문 번호나 날짜 같은 기준으로 연결하면,
상품별 매출과 광고비를 비교하거나 첫 구매 고객이 다음 달에 다시 샀는지를 볼 수 있다.

데이터가 웨어하우스에 들어갔다고 저절로 정리되지는 않는다.
영상이 드는 예가 하나 있다.
한 주문에 상품이 세 개 들어 있는데 주문 금액을 상품 행마다 더하면 매출이 세 배로 부풀려진다.
그래서 주문 한 건을 한 줄로 볼지, 주문 안의 상품 하나를 한 줄로 볼지부터 정해야 한다.
영상은 시즌1에서 소개한 스타 스키마가 분석 모델의 대표적인 방식 하나일 뿐, 모든 웨어하우스가 그 모양일 필요는 없다고 덧붙인다.
분석용 테이블에는 개별 주문 수준의 상세 데이터를 둘 수도 있고, 날짜별 매출처럼 미리 집계한 결과를 둘 수도 있다.

### 컬럼 기반 저장

분석 시스템에서 자주 나오는 기술이 컬럼 기반 저장(columnar storage)이다.
주문 테이블에 주문 번호, 고객 번호, 날짜, 상품, 금액, 배송 주소가 있다고 하자.
주문 한 건을 보여 줄 때는 그 주문의 여러 항목을 함께 읽는 것이 자연스럽다.
날짜별 매출을 계산할 때는 많은 주문에서 날짜와 금액만 읽으면 되고 배송 주소는 필요 없다.
행 기반 저장은 한 주문의 항목들을 모아 두고, 컬럼 기반 저장은 여러 주문의 날짜끼리, 금액끼리 모아 둔다.
같은 종류의 값이 모여 있어 압축에도 유리할 수 있다.
영상은 컬럼 기반이라고 모든 쿼리가 빨라지는 것은 아니라고 분명히 한다.
읽는 데이터의 양, 나눠 둔 방식, 계산의 종류도 영향을 준다고 한다.

### 데이터 레이크와 객체 저장소

데이터 레이크는 모양과 용도가 다른 데이터를 파일 형태로 넓게 모아 두고 필요한 작업에서 읽어 쓰는 구조다.
표 형태의 주문뿐 아니라 상품 조회 기록, 서버 로그, 상담 문서가 대상이다.
영상의 예는 이렇다.
고객이 상품을 볼 때마다 이벤트를 기록해 날짜별 파일로 모은다.
주문은 계속 서비스 데이터베이스에서 관리하고, 분석용 사본을 따로 내보내 함께 모은다.
주문을 받는 시스템 자체를 파일로 바꾸는 이야기가 아니다.

처음에는 날짜별 방문 수만 세다가 나중에 구매까지의 과정을 분석하거나 추천 모델을 학습할 수 있다.
처음에 합계만 남겼다면 새 질문이 생겨도 원래 어떤 행동이 있었는지 다시 볼 수 없다.
다만 영상은 모든 데이터를 영원히 모으자는 뜻은 아니라고 한다.
목적과 보관 기간, 개인정보 처리 방식을 정해야 한다.
레이크에는 처음 받은 원본뿐 아니라 오류를 정리한 데이터와 분석하기 좋게 가공한 데이터를 구분해 둘 수도 있다.

Amazon S3, Google Cloud Storage, Azure Blob Storage 같은 객체 저장소는 데이터를 객체 단위로 보관하는 서비스다.
S3에서는 버킷이라는 저장 공간 안에 객체를 넣는다.
영상은 여기서 중요한 구분을 한다.
파일을 올렸다고 분석 시스템이 완성되지는 않는다.
어떤 파일에 어떤 데이터가 있는지 알아야 하고, 읽어 계산하는 도구가 필요하며, 누가 접근하는지 관리하고, 새 데이터가 제대로 들어왔는지 확인해야 한다.
객체 저장소는 데이터를 담는 기반이고, 데이터 레이크는 그 위에 데이터를 모아 관리하고 활용하는 구조다.

## 세 제품을 고르는 기준

영상은 Snowflake, Google BigQuery, Amazon Redshift를 대표 제품으로 소개한다.
세 제품 모두 데이터를 모아 SQL로 분석한다는 역할은 같고, 차이는 다음에서 난다.

| 제품      | 영상이 말하는 강점                                                                                                                   | 자연스러운 선택 조건                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| Snowflake | 저장과 계산의 분리. 업무별로 다른 컴퓨트 자원을 붙이고 필요할 때 키우거나 멈출 수 있다. AWS, Azure, Google Cloud를 지원한다          | 업무별로 성능과 비용을 나눠 조절해야 할 때                         |
| BigQuery  | 서버리스. 서버와 클러스터 운영은 Google이 맡고, Google Analytics 4 이벤트를 내보내 주문 데이터와 연결할 수 있다                      | Google Cloud 안에서 여러 데이터를 모아 분석할 때                   |
| Redshift  | 컬럼 기반 저장과 여러 노드의 병렬 처리. S3의 파일을 Spectrum으로 읽어 함께 분석할 수 있다. 클러스터 방식과 서버리스 방식 중 선택한다 | AWS에 서비스와 데이터가 이미 있고 보고서와 대시보드로 잇고 싶을 때 |

영상은 비교의 기준을 세 가지로 정리한다.
데이터가 어느 클라우드에 있는지, 업무별 계산 자원을 어떻게 나눌지, 비용과 운영을 어떻게 관리할지다.

## 트레이드오프

### 웨어하우스와 레이크의 경계는 흐려지고 있다

웨어하우스는 정리된 표, 레이크는 원본 파일이라는 구분은 실제로 딱 맞지 않는다.
웨어하우스에도 처음 가져온 데이터를 넣고 안에서 정리하는 경우가 있다.
시즌1의 ELT, 곧 먼저 적재하고 그 안에서 변환하는 방식과 이어진다.
요즘 웨어하우스는 JSON처럼 모양이 유연한 데이터도 다룬다.
반대로 레이크에도 잘 정리된 표 데이터를 둘 수 있고, 여러 파일을 하나의 테이블처럼 관리할 수 있다.

레이크는 저장만 하고 웨어하우스는 계산도 한다는 구분도 조심해야 한다.
레이크 위에 파일을 읽는 쿼리 엔진을 붙이면 SQL 분석이 가능하다.
그래서 영상은 데이터를 담는 곳, 데이터의 구조를 관리하는 방식, 읽고 계산하는 엔진으로 나눠 보라고 권한다.
실제 제품은 이 역할들을 묶어 제공하기도 하고, 바깥에 있는 데이터를 읽기도 한다.
이 경계가 가까워지며 나온 것이 레이크하우스이고, 영상은 다음 편에서 다루겠다고 한다.

### 비용은 저장 단가만으로 판단할 수 없다

영상은 레이크는 싸고 웨어하우스는 비싸다고 단정하기 어렵다고 말한다.
파일을 보관하는 비용뿐 아니라 읽고 계산하는 비용과 운영하는 사람의 시간이 들기 때문이다.
데이터가 얼마나 빨리 들어와야 하는지, 얼마나 자주 읽는지, 누가 쓰는지도 함께 봐야 한다.

### 파일이 모여 있는 것만으로는 답이 안 나오는 질문이 있다

영상의 마지막 질문이 이 편에서 남기는 숙제다.
레이크에 어제 파일과 오늘 파일이 있는데 어제 저장한 주문이 오늘 취소됐다면 예전 데이터는 어떻게 고칠까.
고치는 동안 다른 사람이 읽으면 어떤 상태를 보게 될까.
이 질문에는 어떤 파일들을 한 테이블로 볼지, 변경된 상태를 어떻게 관리할지가 필요하다.
영상은 Parquet 같은 파일 형식, Iceberg 같은 테이블 형식, 카탈로그의 위치를 다음 편에서 다룬다고 한다.

## 함정

영상에서 직접 나오거나 영상의 설명에서 이어지는 함정을 정리한다.

- 웨어하우스에 넣었다고 데이터가 정리되지 않는다.
  한 줄이 무엇을 뜻하는지, 곧 단위를 먼저 정하지 않으면 금액이 부풀려진다.
- 처음부터 합계만 저장하면 나중의 새 질문에 답할 수 없다.
  반대로 모든 것을 영원히 보관하는 것도 답이 아니다.
  목적, 보관 기간, 개인정보를 정해야 한다.
- 객체 저장소에 파일을 올리는 일과 데이터 레이크를 만드는 일은 다르다.
  찾기, 계산, 접근 권한, 갱신 확인이 따로 필요하다.
- 컬럼 기반 저장이 모든 쿼리를 빠르게 하지는 않는다.
  어떤 데이터를 얼마나 읽는지가 더 큰 변수일 수 있다.
- 작은 팀이 두 가지를 모두 처음부터 만들 필요는 없다.
  영상은 지금 풀어야 하는 질문의 범위에서 시작하고, 역할을 나눌 필요가 생기면 넓히라고 한다.

## 확인하기

영상이 말하는 컬럼 기반 저장의 이점을 가장 작은 규모로 확인해 보는 예제다.
같은 주문 데이터를 행 단위와 컬럼 단위로 배치해 두고, 날짜별 매출을 계산할 때 건드리는 값의 수를 센다.
외부 라이브러리 없이 Python만으로 돌아간다.
시간은 Python 리스트에서의 측정이라 의미가 크지 않으니, 건드리는 값의 수가 줄어드는 것만 본다.

```python
import random
import time
from collections import defaultdict

random.seed(7)
N = 300_000
FIELDS = ["order_id", "customer_id", "order_date", "product", "amount", "address"]

# 행 기반: 주문 한 건의 모든 항목이 한 덩어리로 붙어 있다
rows = [
    (i, random.randrange(50_000), f"2026-10-{1 + i % 28:02d}",
     f"item-{i % 900}", random.randrange(5, 200), "x" * 40 + str(i))
    for i in range(N)
]

# 컬럼 기반: 같은 항목끼리 모여 있다 (같은 데이터를 세로로 다시 배치)
cols = {name: [r[k] for r in rows] for k, name in enumerate(FIELDS)}


def revenue_row_store():
    touched = 0
    out = defaultdict(int)
    for r in rows:
        touched += len(r)            # 행을 꺼내면 6개 항목이 따라온다
        out[r[2]] += r[4]
    return out, touched


def revenue_column_store():
    touched = 0
    out = defaultdict(int)
    dates, amounts = cols["order_date"], cols["amount"]
    touched += len(dates) + len(amounts)   # 필요한 두 컬럼만 읽는다
    for d, a in zip(dates, amounts):
        out[d] += a
    return out, touched


for name, fn in [("row", revenue_row_store), ("column", revenue_column_store)]:
    t0 = time.perf_counter()
    result, touched = fn()
    print(f"{name:6s} touched={touched:>9,} values  time={time.perf_counter()-t0:.3f}s")

assert revenue_row_store()[0] == revenue_column_store()[0]
print("same result: True")
```

이 문서를 쓰는 환경에서 실행한 결과는 다음과 같다.
행 방식은 1,800,000개, 컬럼 방식은 600,000개의 값을 건드렸고 결과는 같았다.
건드리는 값이 세 배 차이가 나는 것은 항목 6개 가운데 2개만 읽기 때문이다.
실제 분석 시스템은 여기에 압축과 디스크 단위 읽기가 더해지므로, 이 예제는 원리를 보는 용도일 뿐 성능 측정이 아니다.

## 체크리스트

- 지금 답하려는 질문이 매일 보는 주문 수와 매출인지, 여러 시스템을 연결한 분석인지, 상세 로그를 오래 보관해 다시 처리하는 일인지 적어 두었는가.
- 분석용 테이블의 한 줄이 무엇을 뜻하는지(주문 한 건인지 주문 안의 상품 하나인지) 정했는가.
- 서비스 데이터베이스에서 큰 집계를 돌려 주문 처리에 영향을 주고 있지 않은가.
- 데이터가 어느 클라우드에 있는지 확인하고, 그 클라우드에서 자연스러운 웨어하우스를 후보로 정했는가.
- 객체 저장소에 쌓는 파일에 대해 찾는 방법, 읽는 도구, 접근 권한, 갱신 확인이 정해져 있는가.
- 상세 기록을 보관한다면 목적, 보관 기간, 개인정보 처리 방식을 정했는가.

## 기억할 원칙

### 웨어하우스와 레이크를 제품이 아니라 역할로 나눠 본다

담는 곳, 구조를 관리하는 방식, 읽고 계산하는 엔진은 서로 다른 역할이다.
한 제품이 이 역할을 묶어 제공할 수도 있고, 다른 제품의 데이터를 바깥에서 읽을 수도 있다.
제품 이름으로 웨어하우스인지 레이크인지 묻는 질문은 곧 의미가 흐려진다.
어떤 역할을 어디에 둘지 묻는 편이 선택에 쓸모가 있다.

### 필요한 범위에서 시작하고 역할이 갈릴 때 넓힌다

작은 데이터는 기존 데이터베이스나 읽기용 환경, 심지어 노트북의 파일 몇 개로 시작할 수 있다.
여러 사람이 같은 데이터를 반복해서 분석하고 대시보드를 운영해야 하면 관리형 웨어하우스가 편하다.
다양한 상세 기록을 보관해 여러 방식으로 처리해야 하면 레이크를 함께 고려한다.
구조는 질문이 요구할 때 넓힌다.
