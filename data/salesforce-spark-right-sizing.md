# 성공한 Spark 작업에서 낭비를 찾는 법: Salesforce의 하루 800만 실행 사례

원문: [Apache Spark Resource Optimization: Lessons From Eight Million Jobs a Day](https://engineering.salesforce.com/apache-spark-resource-optimization-lessons-from-eight-million-jobs-a-day/)

GN 토론: <https://news.hada.io/topic?id=35502>

## 소개

Salesforce의 Siddharth Sharma, Suvhrajit Basak, Kusum Dhalia, Nabeel Qaiser는
2026년 10월 8일, Data 360에서 하루 약 800만 번 실행되는 Apache Spark 작업의
자원을 줄인 과정을 공개했다.
작업은 짧은 실행부터 몇 시간에 걸쳐 테라바이트를 처리하는 것까지 다양했다.

글의 출발점은 단순하다.
작업이 성공했다는 것은 설정이 동작한다는 증거일 뿐,
할당한 용량이 얼마나 필요했는지는 말해 주지 않는다.
근거 없이 CPU, 메모리, 실행기(executor)를 줄이면
절감 대신 느린 실행, 비싼 재시도, 운영 장애를 얻을 수 있다.
그래서 팀은 쓰지 않은 용량과 메모리 압박, 셔플 병목을 구분하고,
애플리케이션 코드를 바꾸지 않고 근거를 모으는 방법을 찾았다.

## 동작 방식

### 성공 속에 숨은 낭비

팀이 마주친 한 작업은 시작할 때 실행기 40개를 요청했지만,
대부분은 처음에 아무 일도 하지 않았다.
작업은 실패하지 않았으므로 성공 여부만 보면 낭비가 보이지 않는다.
그러나 그 할당은 파드와 노드의 잦은 생성과 삭제(churn),
그리고 쓰지 않는 용량을 만들었다.
고정 자원 프로필도, 테넌트와 데이터 양으로 추정하는 방식도
제출 전에 할당을 정하는 데는 도움이 되지만,
그 할당이 실행 중에 어떻게 쓰였는지는 알려 주지 않는다.

### 코드 변경 없이 원격 측정을 모은다

애플리케이션 코드는 각 팀이 가지고 있다.
모든 팀에 계측 코드를 넣어 달라고 하면 조사 전에 통합 프로젝트가 생긴다.
팀은 관리형 Spark 제출이 모두 지나가는 공통 관문인
Data Processing Controller(DPC)를 계측 지점으로 삼았다.

1. DPC가 제출을 만들 때 오픈소스 DataFlint Spark 플러그인을 확장해 주입한다.
2. Spark 리스너 훅이 애플리케이션 코드와 독립적으로 실행을 관찰한다.
3. 각 드라이버에서 모은 원격 측정을 Kafka로 내보낸다.
4. 중앙 Iceberg 레이크하우스에 쌓는다.

수집은 안전해야 했다.
리스너는 전용 리스너 버스 큐를 쓰고,
계측을 설정하거나 초기화하지 못해도 제출은 계속된다.
내보내기 실패와 원격 측정 공백은 경보로 감시한다.

### 지표가 거짓말하지 않게 정의한다

쿼리가 그럴듯한 최적화 후보를 내놓아도,
불완전한 실행, 빠진 기록, 잘못 센 재시도가 결과를 왜곡할 수 있다.
글은 세 가지 함정을 든다.

- 불완전한 실행은 완전한 실행에 무엇이 필요한지 말해 주지 못한다.
  전체 평균도 특정 작업의 요구를 말해 주지 못한다.
- 재시도한 스테이지는 비용이 드는 추가 작업이지만,
  모든 시도를 별개의 논리 작업으로 세면 성공한 실행의 분석이 왜곡된다.
- 메모리 스필과 디스크 스필은 같은 압박을 다른 형태로 기록한 것이라,
  둘을 더하면 잘못된 총량이 나온다.

팀은 이 의미를 Silver라는 정제된 분석 계층에 담았다.
애플리케이션, 잡, 스테이지 시도, 실행기를 연결하는 모델이다.
자원 크기 결정에는 정의된 작업과 환경 범위 안의 완전한 실행만 쓰고,
신뢰성 조사에서는 실패와 재시도도 본다.
비용은 Spark 애플리케이션마다 드라이버 파드와 모든 실행기 파드의 비용을 더해,
같은 작업의 변경 전후를 비교할 수 있게 했다.

### 낮은 활용률은 낭비일 수도, 병목일 수도 있다

팀은 “어떤 비싼 작업이 작업을 하나도 처리하지 않는 실행기를 반복해서
할당하는가”라는
구체적인 질문으로 시작했다.
서비스 비용, CPU 유휴 시간, 작업 0개 실행기로 Data 360 상위 10개 작업을 골랐다.
Silver는 Trino로 노출했고,
자연어 질문에서 SQL을 만들어 주는 에이전트 프로파일링 스킬도 만들었다.
그 답에는 SQL, 공식, 가정이 함께 나와 엔지니어가 근거를 검토할 수 있다.

증상에 따라 개입이 달라진다.

| 증상                               | 뜻하는 것                       | 다음 행동              |
| ---------------------------------- | ------------------------------- | ---------------------- |
| 작업 0개를 처리한 실행기           | 시작 할당이 과했을 가능성       | 더 작은 초기 할당 실험 |
| 작업을 받은 실행기의 높은 CPU 유휴 | 할당된 CPU 상당량이 쓰이지 않음 | 최대 실행기 수 등 실험 |
| 셔플이 많은 작업의 fetch 실패      | 신뢰성 문제                     | 별도 신뢰성 조사       |

낮은 CPU 활용률만으로 용량을 줄여도 된다고 할 수 없고,
작업 0개 실행기가 정확히 몇 개로 줄여야 하는지를 알려 주지도 않는다.
자원 크기 실험을 할지 실행 동작을 조사할지 먼저 정하고 나서 개입을 고른다.

## 구현하기

실행기 40개로 시작하던 작업에는 동적 할당을 유지한 채
`initialExecutors`를 4로 낮췄다.
필요할 때 용량이 늘어날 수 있게 두고 시작 할당만 줄인 것이다.

```bash
spark-submit \
  --conf spark.dynamicAllocation.enabled=true \
  --conf spark.dynamicAllocation.initialExecutors=4 \
  --conf spark.dynamicAllocation.maxExecutors=<기존 값 유지> \
  ...
```

한 달 넘게 운영한 결과 실행 시간, 재시도,
실패의 수용 불가한 악화 없이 낭비가 사라졌다.
실행기 유휴 시간이 90%를 넘던 다른 작업 묶음에서는
나머지 프로필은 그대로 두고 최대 실행기 수를 약 20% 줄였고,
역시 한 달 넘게 실행 시간, 스필, 재시도, 실패를 관찰해 수용 가능함을 확인했다.
글은 두 변경 모두 해당 작업에서만 검증된 것이며
보편적인 Spark 설정이 아니라고 강조한다.

## 값 정하기

| 결정           | 이 사례의 값     | 근거                                      |
| -------------- | ---------------- | ----------------------------------------- |
| 초기 실행기 수 | 40에서 4로       | 시작 시 대부분의 실행기가 작업 0개        |
| 최대 실행기 수 | 약 20% 감소      | 실행기 유휴 시간 90% 이상                 |
| 관찰 기간      | 한 달 이상       | 실행 시간, 스필, 재시도, 실패의 변화 확인 |
| 비교 창        | 변경 전후 각 4주 | 주간 컴퓨팅 비용 비교                     |

이 값을 다른 작업에 그대로 옮기면 안 된다.
옮길 것은 값이 아니라 값을 정한 근거,
즉 작업 0개 실행기와 유휴 시간이라는 신호와
한 달 이상의 관찰이다.

## 트레이드오프

### 줄일수록 애플리케이션만이 아니라 플랫폼도 봐야 한다

팀은 단계별로 낮은 환경에서 운영으로 변경을 넓히며,
p95 실행 시간, 재시도, OOM, 스필과 함께
파드 churn, 노드 churn, IP 프리픽스 소비, etcd 압력을 확인했다.
변경은 애플리케이션과 실행 플랫폼 양쪽에서 수용 가능해야 했다.
실행기를 너무 많이 할당하면 낭비지만, 동적 할당이 실행기를 자주 늘리고 줄이면
쿠버네티스 제어 평면에 다른 압력이 생긴다.

### 성과는 통제 실험이 아니다

대상 작업 전체의 주간 컴퓨팅 비용은 변경 전후 4주씩 비교해 31% 줄었다.
같은 기간 같은 환경에서 DPC 작업 시작 수는 7% 넘게 늘었다.
글은 이것이 통제 실험이 아니라 전후 비교라서
같은 기간의 다른 변화도 영향을 주었을 수 있다고 스스로 밝힌다.
절감 효과를 다른 작업으로 일반화하려면 같은 방식으로 다시 측정해야 한다.

## 함정

- 성공한 작업만 보면 낭비가 보이지 않는다.
  성공은 설정이 동작한다는 증거이지 효율적이라는 증거가 아니다.
- 불완전한 실행과 부분 측정이 섞인 집계는 낭비를 과장하거나 숨긴다.
- 재시도를 별개 작업으로 세면 성공한 실행의 자원 요구가 부풀려진다.
- 메모리 스필과 디스크 스필을 더하면 압박이 두 배로 보인다.
- 낮은 CPU 활용률을 보고 바로 줄이면 셔플 병목이나 메모리 압박을
  악화시킬 수 있다.
- 계측이 실패할 때 제출이 막히면, 관찰 도구가 새 장애 원인이 된다.

## 확인하기

글은 내일 바로 할 수 있는 일로 다음을 권한다.

1. 비싸고 반복되는 작업 하나를 고른다.
2. 완전하고 비교 가능한 실행들에서 요청한 용량과 실제 유용한 작업을 비교한다.
3. 유휴의 원인을 조사한다.
4. 목표를 좁힌 변경 하나를 시험한다.
5. 롤아웃을 넓히기 전에 컴퓨팅 비용을 실행 시간, 스필, 재시도,
실패와 함께 평가한다.

하루 800만 번의 실행이 없어도 이 방법은 쓸 수 있다는 것이 글의 결론이다.

## 체크리스트

- 분석에 완전한 실행만 포함했는가?
- 재시도와 스필을 이중으로 세지 않았는가?
- 비용 경계(드라이버와 모든 실행기 파드)가 변경 전후로 같은가?
- 낮은 활용률이 낭비인지 병목인지 구분했는가?
- 변경 하나만 바꾸고 나머지 프로필은 고정했는가?
- 한 달 이상 실행 시간, 스필, 재시도, 실패, OOM을 관찰했는가?
- 파드와 노드 churn, etcd 압력 같은 플랫폼 지표도 확인했는가?
- 계측이 실패해도 작업 제출이 계속되는가?

## 기억할 원칙

### 자원 추정은 가설이고, 다음 실행이 판정한다

글은 자원 추정을 가설로 다루고,
실행 근거로 변경을 고르고,
이후 실행으로 효과를 판정하라고 말한다.
이 원칙이 Spark 자원 최적화를 일회성 정리 작업이 아니라
반복 가능한 공학 실무로 만든다.
팀이 다음 단계로 DPC가 검증된 권고를 자동으로 적용하는 방안을 검토하는 것도
관찰, 진단, 최적화를 하나의 고리로 묶으려는 같은 원칙의 연장이다.
