# 1장 웹 서핑: 이미 아는 RESTful 시스템으로 용어 익히기

《RESTful Web APIs》(Leonard Richardson, Mike Amundsen, O'Reilly 2013) 1장 정리.

## 개요

저자의 공식 설명에 따르면 1장은 “이미 익숙한 RESTful 시스템, 즉 웹사이트를 예로 기본 용어를 설명한다”.
이 정리는 저자의 공식 장별 설명과 해당 장이 다루는 공개 표준을 근거로 하며, 책 본문을 옮긴 것이 아니다.

이 장의 전략은 새 개념을 새 어휘로 가르치지 않는 것이다.
REST를 아키텍처 이론에서 시작하면 추상적인 제약 조건의 목록이 되지만, 브라우저로 웹사이트를 쓰는 경험에서 시작하면 같은 개념이 이미 매일 하는 동작으로 설명된다.
독자는 리소스가 무엇인지 배우기 전에 이미 URL을 주소창에 넣어 봤고, 하이퍼미디어를 정의하기 전에 이미 링크를 눌러 봤다.
1장이 하는 일은 그 익숙한 동작에 정확한 이름을 붙이는 것이다.

이 접근은 전작 《RESTful Web Services》가 “모든 웹 사이트는 이미 서비스다”라는 명제에서 출발한 것과 같은 뿌리를 가진다.[^ref-rws]
다만 전작이 그 명제를 서버 설계의 출발점으로 썼다면, 이 장은 그것을 용어 학습의 교보재로 쓴다.

## 리소스와 URL

리소스는 서버가 이름을 붙여 다룰 수 있는 모든 것이다.
블로그 글 하나, 사용자 프로필, 검색 결과 목록, 어제자 판매 보고서가 모두 리소스다.
물리적 실체가 있을 필요는 없고, 서버가 “이것에 대해 이야기할 수 있다”고 정하면 리소스가 된다.

URL은 그 리소스의 이름이다.
정확히는 URI의 한 종류로, 이름을 붙이는 동시에 어떻게 접근하는지도 알려 준다.

```text
https://www.example.com/blog/2013/restful-web-apis
```

이 문자열 하나가 웹 아키텍처에서 감당하는 역할이 크다.
어떤 리소스인지 식별하고, 어느 서버에 물어봐야 하는지 알려 주고, 어떤 프로토콜을 쓸지 정한다.
브라우저 주소창에 넣거나, 남에게 메신저로 보내거나, 북마크에 저장하는 것이 모두 같은 문자열로 되는 것이 웹의 힘이다.
이 성질을 전작에서는 주소 지정 가능성(addressability)이라 불렀다.

## 표현: 리소스 자체는 결코 전달되지 않는다

브라우저가 받아 오는 것은 리소스가 아니라 리소스의 표현(representation)이다.
“오늘의 날씨”라는 리소스를 GET하면 서버는 날씨 그 자체를 보내지 않고, 그것을 서술한 문서를 보낸다.
그 문서가 HTML일 수도 있고 JSON일 수도 있으며, 한국어일 수도 영어일 수도 있다.

이 구별이 사소해 보이지만 REST라는 이름의 절반을 차지한다.
Representational State Transfer라는 이름 자체가 “표현을 통한 상태 전이”이며, 클라이언트와 서버가 실제로 주고받는 유일한 것이 표현이다.
서버 안의 데이터베이스 행이나 객체는 클라이언트에게 절대 노출되지 않고, 클라이언트는 오직 표현만 보고 세계를 이해한다.

이 장에서 표현을 다루는 방식은 3장의 예고이기도 하다.
1장은 “브라우저 화면에 보이는 것이 표현이다”라는 직관을 심어 두고, 3장에서 그것을 리소스와의 관계로 정식화한다.

## 링크와 폼: 웹사이트가 알려 주는 다음 행동

웹사이트를 쓸 때 사용자는 다음에 어떤 URL로 가야 하는지 미리 알지 않는다.
현재 페이지가 알려 준다.

```html
<a href="/blog/2013/restful-web-apis">RESTful Web APIs 소개</a>
```

링크는 “여기를 누르면 이 URL을 GET한다”는 뜻이다.
사용자는 URL의 구조를 몰라도 되고, 서버가 URL 체계를 바꿔도 링크만 따라가면 계속 동작한다.

폼은 링크보다 한 단계 더 나아간다.

```html
<form action="/messages" method="POST">
  <input type="text" name="text">
  <input type="submit" value="보내기">
</form>
```

이 마크업은 세 가지를 한꺼번에 알려 준다.
어느 URL로 보낼지(`/messages`), 어떤 HTTP 메서드를 쓸지(`POST`), 그리고 어떤 데이터를 채워야 하는지(`text`라는 이름의 값)다.
사용자는 API 문서를 읽지 않고도 새 메시지를 만들 수 있다 — 만드는 방법이 페이지 안에 함께 실려 있기 때문이다.

이 두 가지, 링크와 폼이 다음 절에서 다룰 하이퍼미디어의 실체다.

## 하이퍼미디어: 서버가 클라이언트를 이끄는 방식

하이퍼미디어는 표현 안에 “다음에 할 수 있는 요청”이 함께 들어 있는 구조를 가리킨다.
HTML은 태어날 때부터 하이퍼미디어 형식이었고, 그래서 웹사이트를 쓰는 사람은 하이퍼미디어를 의식할 일이 없었다.

이 구조가 만들어 내는 결과가 웹의 유연성이다.
사이트가 새 기능을 추가하면 페이지에 새 링크와 새 폼이 생기고, 사용자는 그것을 눌러 보면 된다.
브라우저를 업그레이드할 필요도, 사용법을 다시 배울 필요도 없다.
브라우저가 아는 것은 “링크는 누르면 GET, 폼은 제출하면 지정된 메서드”라는 규칙뿐이고, 그 규칙은 어느 사이트에서나 같다.

REST 논의에서 이 성질을 흔히 HATEOAS(Hypermedia as the Engine of Application State)라 부른다.
애플리케이션의 상태가 어디로 갈 수 있는지를 클라이언트에 하드코딩하지 않고, 서버가 보낸 표현이 결정한다는 뜻이다.
1장이 이 개념을 웹사이트로 설명하는 이유는, 그것이 이미 성공적으로 작동하는 유일한 대규모 사례이기 때문이다.

## HTTP 메서드: 통일 인터페이스

브라우저가 어떤 사이트에 대해서도 같은 방식으로 동작할 수 있는 이유는, 할 수 있는 동작의 종류가 미리 정해져 있기 때문이다.
RFC 9110이 정의하는 표준 메서드는 다음과 같다.

| 메서드    | 뜻                                       |
| --------- | ---------------------------------------- |
| `GET`     | 리소스의 표현을 가져온다                 |
| `HEAD`    | 표현 없이 헤더만 가져온다                |
| `POST`    | 리소스에 데이터를 보내 처리를 맡긴다     |
| `PUT`     | 리소스의 상태를 보낸 표현으로 바꾼다     |
| `DELETE`  | 리소스를 삭제한다                        |
| `OPTIONS` | 리소스에 쓸 수 있는 통신 옵션을 물어본다 |
| `PATCH`   | 리소스를 부분적으로 수정한다 (RFC 5789)  |

이 목록이 짧다는 것이 핵심이다.
사이트마다 `getUser`, `createOrder`, `deleteComment` 같은 동사를 새로 정의하는 대신, 모든 사이트가 같은 소수의 동사를 쓰고 차이는 URL로 표현한다.
전작에서 통일 인터페이스(uniform interface)라 부른 것이 바로 이것이다.[^ref-rws]

브라우저가 실제로 쓰는 것은 대체로 GET과 POST 둘뿐인데, 그럼에도 웹이 돌아간다는 사실이 이 인터페이스가 얼마나 적은 어휘로 충분한지를 보인다.

## 안전성과 멱등성

메서드마다 “이 요청을 보내면 무슨 일이 벌어지는가”에 대한 약속이 다르다.
RFC 9110은 이를 안전(safe)과 멱등(idempotent)이라는 두 성질로 정리한다.

안전한 메서드는 리소스의 상태를 바꾸지 않는 읽기 전용 요청이다.
GET, HEAD, OPTIONS가 여기 속한다.
브라우저가 링크를 미리 가져오거나 프록시가 응답을 캐시할 수 있는 것은 GET이 안전하다는 약속 덕분이다.
“삭제하기”를 GET 링크로 만들면 안 되는 이유도 여기에 있다 — 검색 엔진 크롤러가 그 링크를 따라가는 순간 데이터가 사라진다.

멱등한 메서드는 같은 요청을 여러 번 보내도 결과 상태가 한 번 보낸 것과 같은 요청이다.
PUT과 DELETE가 여기 속하고, 안전한 메서드는 자동으로 멱등이다.
네트워크가 끊겨 응답을 못 받았을 때 클라이언트가 안심하고 재시도할 수 있는 근거가 멱등성이다.

POST는 안전하지도 멱등하지도 않다.
브라우저가 폼을 다시 제출할 때 “이 양식을 다시 보내시겠습니까?”라고 묻는 것이 이 사실의 사용자 인터페이스 버전이다.

```text
안전  ⊂  멱등  ⊂  전체 메서드
GET, HEAD, OPTIONS  ⊂  + PUT, DELETE  ⊂  + POST, PATCH
```

## 상태 코드: 무슨 일이 일어났는지 알리는 규약

응답의 첫 줄에 담기는 세 자리 숫자가 요청의 결과를 알린다.
백 자리로 큰 분류가 정해진다.

```http
HTTP/1.1 200 OK
HTTP/1.1 303 See Other
HTTP/1.1 404 Not Found
HTTP/1.1 405 Method Not Allowed
HTTP/1.1 500 Internal Server Error
```

2xx는 성공, 3xx는 추가 동작 필요(주로 리다이렉트), 4xx는 클라이언트 잘못, 5xx는 서버 잘못이다.
이 분류가 유용한 이유는 클라이언트가 모르는 코드를 만나도 백 자리만 보고 대략의 대응을 정할 수 있기 때문이다.
처음 보는 451을 받은 클라이언트도 “4로 시작하니 내 요청에 문제가 있다”까지는 알 수 있다.

웹사이트에서 이 코드들이 어떻게 쓰이는지가 1장의 설명 방식과 잘 맞는다.
폼을 제출한 뒤 브라우저 주소가 바뀌는 것은 서버가 303 See Other를 보내며 `Location` 헤더로 새 URL을 알려 줬기 때문이고, 잘못된 주소를 넣었을 때 나오는 오류 페이지가 404다.
사용자에게는 화면의 문구로 보이지만 프로그램에게는 숫자가 계약이다.

## 미디어 타입: 이 바이트를 어떻게 읽어야 하는가

서버가 보낸 표현이 어떤 형식인지는 `Content-Type` 헤더가 알린다.

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
```

미디어 타입은 “이 바이트 뭉치를 어떤 규칙으로 해석하라”는 지시다.
브라우저가 `text/html`을 보면 HTML 파서를 돌려 화면을 그리고, `image/png`를 보면 이미지로 표시하며, `application/pdf`를 보면 PDF 뷰어를 띄운다.
같은 바이트라도 미디어 타입이 다르면 완전히 다른 것이 된다.

미디어 타입이 알려 주는 것은 문법만이 아니다.
`text/html`이라는 타입은 “이 문서 안에 `<a>`와 `<form>`이 있을 수 있고 그것들이 하이퍼미디어 제어를 뜻한다”는 것까지 규정한다.
브라우저가 어떤 사이트의 링크든 똑같이 처리할 수 있는 것은 미디어 타입 명세가 그 의미를 공통으로 고정해 두었기 때문이다.
2장에서 JSON API가 겪는 문제의 뿌리가 정확히 여기에 있다 — `application/json`은 문법만 정의하고 링크의 의미는 정의하지 않는다.

미디어 타입의 등록과 이름 규칙은 RFC 6838이 정한다.
`text/html`처럼 IANA에 등록된 표준 타입도 있고, `application/vnd.amundsen.maze+xml`처럼 특정 벤더가 정의한 타입도 있다.

## 핵심 정리

1장이 웹사이트에서 끌어내는 용어는 다음과 같이 정리된다.

- 리소스는 서버가 이름 붙여 다루는 대상이고, URL이 그 이름이다.
- 클라이언트가 받는 것은 리소스가 아니라 표현이며, REST라는 이름의 절반이 여기서 나온다.
- 링크와 폼은 “다음에 할 수 있는 요청”을 표현 안에 함께 실어 보내는 장치이고, 이것이 하이퍼미디어다.
- HTTP 메서드는 소수로 고정된 통일 인터페이스이며, 차이는 동사가 아니라 URL로 낸다.
- 안전성은 캐시와 크롤링을, 멱등성은 재시도를 가능하게 하는 약속이다.
- 상태 코드는 백 자리 분류 덕분에 모르는 코드에도 대응할 수 있게 한다.
- 미디어 타입은 문법뿐 아니라 하이퍼미디어 제어의 의미까지 규정하며, 이 점이 2장의 문제 제기로 이어진다.

이 장의 진짜 논지는 목록 자체가 아니라 순서다.
REST를 배우기 위해 새로 익혀야 할 것은 거의 없고, 이미 매일 쓰는 시스템에 정확한 이름을 붙이는 일이 남았을 뿐이라는 것이 1장의 주장이다.
