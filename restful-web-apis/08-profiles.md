# 8장 프로파일: 데이터 형식과 실제 API 사이의 틈 메우기

《RESTful Web APIs》(Leonard Richardson, Mike Amundsen, O'Reilly 2013) 8장 정리.

## 개요

저자의 공식 설명에 따르면 이 장의 주제는 한 문장으로 요약된다.
“프로파일은 (여러 API가 쓸 수 있는) 데이터 형식과 특정 API 구현 사이의 틈을 메운다.
내가 권하는 프로파일 형식은 ALPS이지만 XMDP와 JSON-LD도 다룬다.”
저자는 이 장부터 자기 조언이 집필 당시의 최신 기술을 앞서가기 시작한다고 밝혔고, 이 책을 쓰기 위해 ALPS 형식을 직접 개발해야 했다고 했다.

이 정리는 저자의 공식 장별 설명과 해당 장이 다루는 공개 표준을 근거로 하며, 책 본문을 옮긴 것이 아니다.

따라서 아래 내용은 두 층으로 나뉜다.
프로파일이라는 개념의 위치와 저자의 의도는 공식 설명과 이 저장소의 [whats-new.md](whats-new.md)에 근거하고, 형식의 구체적 문법과 규칙은 ALPS 인터넷 드래프트, RFC 6906, JSON-LD 권고안, XMDP 명세를 직접 확인한 것이다.

## 프로파일이 겨냥하는 문제: 하이퍼미디어가 못 푸는 절반

프로파일을 이해하려면 먼저 하이퍼미디어가 무엇을 풀고 무엇을 못 푸는지를 갈라야 한다.
저자는 이 구별을 두 책의 차이를 설명하는 글에서 명시했고, 이 저장소에는 [RESTful Web Services에서 RESTful Web APIs로: 세 가지 큰 변화](whats-new.md)에 정리돼 있다.

하이퍼미디어는 “클라이언트가 다음에 어떤 HTTP 요청을 할 수 있는가”를 잘 푼다.
링크와 폼이 가능한 상태 전이를 표현 안에 실어 주므로, 클라이언트는 URL 구조를 사전에 알 필요 없이 서버가 준 것만 따라가면 된다.

그러나 하이퍼미디어는 “그 요청이 실세계에서 무엇을 뜻하는가”는 못 푼다.
링크 관계 `cancel`은 클라이언트에게 “이 요청을 할 수 있다”를 알려 주지만, 그것이 “주문을 취소한다”는 의미를 전달하지는 않는다.
이 저장소의 [example-code.md](example-code.md)에 정리한 `the-boaster` 클라이언트가 정확히 이 틈을 보여 준다 — 이 클라이언트는 올바른 `Accept` 헤더를 보내고 링크 관계를 정확히 해석하며 서버가 준 하이퍼미디어를 흠 없이 따라가지만, “미로를 통과한다”는 실세계 의미는 전혀 수행하지 않는다.
프로토콜 준수와 의미 수행은 별개라는 것이다.

8장 이전까지 이 틈을 메우는 방법은 둘뿐이었다.
하나는 사람이 읽는 API 문서를 따로 쓰는 것인데, 기계가 읽을 수 없고 구현과 어긋나기 쉽다.
다른 하나는 5장의 Maze+XML처럼 도메인 특화 미디어 타입을 새로 정의하는 것인데, 도메인마다 새 미디어 타입을 만들어 등록해야 하고 그 타입을 아는 클라이언트만 쓸 수 있다.
프로파일은 새 미디어 타입을 만들지 않고도 도메인 특화 설계의 이점 일부를 얻으려는 제3의 길이다.

## RFC 6906: `profile` 링크 관계가 정의한 프로파일의 규칙

프로파일이라는 개념 자체는 Erik Wilde가 쓴 RFC 6906(2013년 3월)이 `profile` 링크 관계 타입으로 등록했다.
공교롭게도 이 책과 같은 해에 나온 문서이며, ALPS 드래프트는 이 RFC를 규범적으로 참조한다.

RFC 6906은 프로파일을 “제약, 관례, 확장, 또는 기본 미디어 타입 의미를 바꾸지 않는 그 밖의 측면처럼, 리소스 표현을 처리하는 데 쓸 수 있는 추가 의미”로 기술한다.
여기서 결정적인 규칙이 하나 있다.
프로파일은 프로파일 지식 없이 처리될 때 리소스 표현의 의미를 바꾸어서는 안 된다(MUST NOT).
그래야 프로파일을 아는 클라이언트와 모르는 클라이언트가 같은 표현을 안전하게 쓸 수 있다.

이 규칙이 프로파일과 새 미디어 타입의 경계를 긋는다.
RFC 6906은 XHTML을 XML의 프로파일이 아니라 새 미디어 타입으로 분류한다 — XHTML은 밑에 깔린 XML 구조에 대한 완전히 새로운 관점을 도입하기 때문이다.
반면 hCard는 (X)HTML의 프로파일이다 — (X)HTML 자체의 처리 규칙과 의미를 전혀 바꾸지 않으면서 추가 의미를 뽑아낼 처리 규칙만 더하기 때문이다.

프로파일은 URI로 식별되지만, 그 URI는 XML 네임스페이스 URI처럼 식별자로만 기능한다.
클라이언트는 프로파일 URI를 링크가 아니라 식별자로 다뤄야 하며(SHOULD), 특정 URI가 있다는 사실만으로 표현이 그 프로파일을 따른다고 단정할 수 있어야 한다.
다만 클라이언트가 모르는 프로파일 URI를 만날 수 있는 환경이라면, 프로파일 관리자는 URI를 역참조 가능하게 만들고 그 자리에 유용한 문서를 두는 것을 고려해야 한다(SHOULD).

하나의 표현은 프로파일 0개 또는 여러 개를 동시에 따를 수 있다.
클라이언트가 지원하는 프로파일 집합에 따라 같은 표현이 서로 다른 처리 규칙 집합으로 처리될 수 있다는 뜻이다.

RFC 6906은 프로파일과 함께 쓰일 새 미디어 타입이라면 `profile`이라는 미디어 타입 파라미터를 정의해야 한다고 권한다(SHOULD).
그러면 클라이언트가 `Accept` 헤더에서 특정 프로파일을 요청할 수 있다.
파라미터를 쓰더라도 표현 안에 `profile` 링크 관계로 같은 값을 넣는 편이 좋은데(SHOULD), 표현이 대화 맥락 밖으로 나가면 미디어 타입 레이블은 쉽게 사라지기 때문이다.
파라미터를 정의하는 미디어 타입은 그것을 공백으로 구분된 프로파일 URI 목록으로 정의해야 한다(SHOULD).

## ALPS: 저자가 이 책을 위해 만든 프로파일 형식

ALPS(Application-Level Profile Semantics)는 Mike Amundsen, Leonard Richardson, Mark W. Foster가 쓴 IETF 인터넷 드래프트다.
저자가 이 책을 위해 직접 개발해야 했다고 밝힌 형식이며, 이 글을 쓰는 시점에 확인 가능한 최신 드래프트는 draft-04(2020년 10월)로 여전히 RFC가 아니다.
책이 2013년에 권한 형식이 7년 뒤에도 드래프트에 머물러 있었다는 사실 자체가 “저자의 조언이 당시 최신 기술을 앞서갔다”는 자기 고백을 뒷받침한다.

### ALPS가 정의하는 것

ALPS 드래프트의 초록은 이 형식을 “HTML 마이크로포맷과 비슷한 복잡도의, 애플리케이션 수준 의미에 대한 간단한 설명을 정의하는 데이터 형식”으로 규정한다.
ALPS 문서는 애플리케이션 비의존적 미디어 타입(HTML, HAL, Collection+JSON, Siren 등)으로 된 문서의 애플리케이션 의미를 설명하는 프로파일로 쓰인다.
이렇게 하면 프로파일 문서를 여러 미디어 타입에 걸쳐 재사용할 수 있다.

드래프트의 동기 절은 문제를 이렇게 정식화한다.
범용 미디어 타입으로 하이퍼미디어 애플리케이션을 구현할 때, 클라이언트와 서버는 데이터 요소 이름, 링크 관계 값, 상태 전이 파라미터 같은 도메인 특화 정보에 대한 이해를 공유해야 한다.
그런데 이 정보는 표현에 쓰인 미디어 타입이 아니라 구현되는 애플리케이션(회계, 연락처 관리 등)에 속한다.
`application/accounting` 같은 미디어 타입을 새로 만들어 등록하는 대신, 대상 도메인의 프로파일을 기술하는 ALPS 문서를 만들면 그것을 다양한 미디어 타입에 일관되게 적용할 수 있다는 것이 ALPS의 제안이다.

드래프트는 두 미디어 타입을 IANA에 등록한다 — `application/alps+xml`과 `application/alps+json`이다.

### ALPS 문서의 구조

ALPS 문서의 중심에는 `descriptor` 하나가 있다.
`descriptor`는 데이터 요소이거나 상태 전이이며, 어느 쪽인지는 `type` 속성이 정한다.

`type` 값은 네 가지다.

| 값           | 의미                                                             |
| ------------ | ---------------------------------------------------------------- |
| `semantic`   | 데이터 요소(기본값)                                              |
| `safe`       | 안전하고 멱등인 상태 전이를 촉발하는 하이퍼미디어 컨트롤         |
| `idempotent` | 안전하지 않지만 멱등인 상태 전이(예: HTTP PUT, DELETE)           |
| `unsafe`     | 안전하지도 멱등이지도 않은 상태 전이(예: HTTP POST)              |

이 네 값이 곧 HTTP 균일 인터페이스를 프로토콜 이름 없이 추상화한 것이다.
ALPS는 특정 전송 프로토콜에 묶이지 않으므로 “GET”이 아니라 “safe”라고 말한다.

문서 요소는 `alps`(루트), `doc`(사람이 읽는 설명), `descriptor`, `ext`(확장), `link`(관련 문서 링크)다.
속성으로는 `format`, `href`, `id`, `name`, `rel`, `rt`, `title`, `type`, `value`, `version`이 정의돼 있다.
이 가운데 `rt`는 상태 전이의 반환 타입(return type)을 가리키는 속성으로, 그 전이를 실행하면 어떤 `descriptor`가 돌아오는지를 명시한다.

드래프트의 연락처 관리 예제는 XML 표현으로 이렇게 생겼다.

```xml
<alps version="1.0">
  <doc format="text">A contact list.</doc>
  <link rel="help" href="http://example.org/help/contacts.html" />

  <descriptor id="collection" type="safe" rt="contact">
    <doc>
      A simple link/form for getting a list of contacts.
    </doc>
    <descriptor id="nameSearch" type="semantic">
      <doc>Input for a search form.</doc>
    </descriptor>
  </descriptor>

  <descriptor id="contact" type="semantic">
    <descriptor id="item" type="safe">
      <doc>A link to an individual contact.</doc>
    </descriptor>
    <descriptor id="fullName" type="semantic" />
    <descriptor id="email"    type="semantic" />
    <descriptor id="phone"    type="semantic" />
  </descriptor>
</alps>
```

여기에는 URL이 하나도 없다는 점이 중요하다.
드래프트의 FAQ는 “ALPS에는 왜 URL이 없는가”를 따로 항목으로 두고 답한다.
ALPS는 어떤 URL이 어떤 의미를 갖는지를 말하는 것이 아니라, 의미 자체를 이름으로 정의하는 어휘집이기 때문이다.
URL은 런타임에 서버가 표현 안에서 알려 준다.

FAQ에는 “왜 워크플로 구성 요소가 없는가”, “왜 의미 서술자에 범위를 지정하는 방법이 없는가”도 있다.
ALPS가 의도적으로 작게 유지된 형식임을 드러내는 대목이다.

### 같은 프로파일이 여러 미디어 타입에 붙는다

ALPS의 실질적 가치는 하나의 프로파일 문서가 서로 다른 미디어 타입의 표현에 그대로 적용된다는 데 있다.
드래프트는 위 연락처 프로파일을 HTML, HAL, Collection+JSON 세 가지 표현에 적용한 예를 나란히 보인다.

HTML에서는 대부분의 ALPS 요소가 `class` 속성으로 구현된다.
`collection`이라는 `id`는 폼의 CSS 클래스가 되고, `contact`는 테이블 행(`tr`)의 클래스가 되며, 하위 서술자 `fullName`, `email`, `phone`은 각 행의 `td`가 된다.

HAL에서는 모든 상태 전이(`collection`, `item`)가 링크 관계로 표현되고, 모든 데이터 서술자는 서술자 이름을 딴 태그가 된다.

Collection+JSON에서는 `links` 배열에 `profile` 관계로 프로파일을 걸고, `queries` 배열의 항목이 `rel`과 `rt`를 갖는다.

```json
{
  "collection": {
    "version": "1.0",
    "href": "http://example.org/contacts/",
    "links": [
      { "rel": "profile", "href": "http://alps.io/profiles/contacts" },
      { "rel": "help", "href": "http://example.org/help/contacts.html" }
    ]
  }
}
```

같은 의미를 세 형식이 각자의 관용구로 담아내는 이 구조가 ALPS의 설계 목표다.
드래프트의 표현대로, 애플리케이션 수준 의미를 전송 프로토콜과 미디어 타입에서 독립적으로 정의하면 애플리케이션 비의존적 미디어 타입으로 애플리케이션 특화 표현을 낼 수 있게 된다.

다만 드래프트는 한계도 명시한다.
모든 미디어 타입이 모든 ALPS 서술자를 충실히 표현할 수 있는 것은 아니다.
예를 들어 순수 `application/json`에는 하이퍼링크를 표현하는 표준적 방법이 없으므로, 그런 미디어 타입에 ALPS를 적용하면 프로파일의 일부 측면은 표현할 수 없다.

### 표현에서 ALPS 문서로 링크하는 법

ALPS 드래프트는 표현과 프로파일을 잇는 방법을 RFC 6906에 맡긴다.
표현 문서는 ALPS 문서로 링크되어야 하며(SHOULD), 그 링크에는 `profile` 링크 관계를 반드시 써야 한다(MUST).
표현의 미디어 타입에 링크 능력이 없거나 링크 관계를 표현할 수 없다면 HTTP `Link` 헤더를 쓸 수 있다(MAY).
미디어 타입이 프로파일 연결용 파라미터를 정의한다면 그것을 쓸 수도 있다(MAY).

```http
HTTP/1.1 200 OK
Content-Type: application/json
Link: <http://alps.io/profiles/contacts>; rel="profile"
```

하나의 표현이 여러 ALPS 프로파일로 기술될 수 있고, 두 프로파일이 같은 요소에 충돌하는 의미를 준다면 표현에서 더 먼저 링크된 문서가 우선한다(SHOULD).
우선순위는 미디어 타입 파라미터, `Link` 헤더, 표현 내부 링크 순이다.

### 클라이언트에게 프로파일이 주는 것

드래프트가 밝히는 클라이언트 측 이득이 이 장의 요점을 압축한다.
문서의 ALPS 프로파일을 손에 쥔 클라이언트는 서술자의 `id`나 `name` 값을 문서 안의 해당 요소와 연결할 수 있다.
그러면 클라이언트는 응답 레이아웃의 세세한 변경, 심지어 미디어 타입 자체의 전면 교체에도 더 잘 적응한다.
드래프트는 이것을 “프로파일에 대고 코딩한다(code for the profile)”고 표현한다.

이것이 URL에 대고 코딩하는 방식(하이퍼미디어가 없앤 결합)과 미디어 타입 구조에 대고 코딩하는 방식(프로파일이 없애려는 결합)을 차례로 걷어낸 자리다.

## XMDP: HTML4가 남긴 프로파일 자리를 채운 형식

XMDP(XHTML Meta Data Profiles)는 Tantek Çelik이 만든, XHTML 기반의 간단한 메타데이터 프로파일 정의 형식이다.
ALPS보다 훨씬 이르고 범위도 좁지만, 프로파일이라는 발상의 계보를 보여 주므로 이 장에 함께 놓인다.

출발점은 HTML4의 빈칸이다.
HTML4는 `<meta>` 요소의 `name` 속성에 대해 “이 명세는 이 속성의 유효한 값을 나열하지 않는다”고 명시했고, 대신 `<head>` 요소의 `profile` 속성으로 속성과 값을 정의하는 메타데이터 프로파일을 가리키게 했다.
그러면서 프로파일의 형식은 정의하지 않는다고 다시 분명히 했다.
XMDP는 그 정의되지 않은 자리를 채우려는 제안이다.

XMDP의 설계 원칙은 단순함, 재사용, 최소주의 세 가지다.
형식은 사람이 손으로 쓰기 쉬워야 하고, 이미 확립된 형식의 요소를 최대한 재사용하며 새 용어를 만들지 않아야 하고, HTML4가 함의하는 필요를 만족시키되 그 이상은 하지 않아야 한다.
그 결과 형식 자체가 XHTML의 부분집합이 됐고, 따라서 형식 자신도 하나의 프로파일이다.

XMDP가 ALPS와 공유하는 것은 “새 형식을 발명하지 않고 기존 형식 위에 의미 층을 얹는다”는 태도다.
차이는 범위다 — XMDP는 HTML 메타데이터 속성의 어휘를 정의하는 데 그치지만, ALPS는 데이터 요소와 상태 전이를 함께 정의해 하이퍼미디어 API의 의미를 겨냥한다.
RFC 6906이 프로파일의 선례로 HTML4의 `profile` 속성을 들면서 “HTML5는 이 메커니즘을 통째로 버릴 것 같다”고 적은 것은, XMDP 계열의 접근이 링크 관계 기반 접근으로 대체된 경위를 요약한다.

## JSON-LD: `@context`로 이름에 IRI를 붙이는 길

JSON-LD는 프로파일 문제에 전혀 다른 계보에서 접근한다.
시맨틱 웹과 Linked Data 진영의 산물이며, 이 책에서는 8장에서 프로파일의 한 선택지로 소개된 뒤 12장에서 Linked Data를 다룰 때 본격적으로 등장한다.

JSON-LD 1.0은 2014년 1월 W3C 권고안이 됐고, 1.1은 2020년 권고안이 됐다.
명세는 이 형식을 “Linked Data를 직렬화하기 위한 JSON 기반 형식”으로 규정하며, 이미 JSON을 쓰는 시스템에 쉽게 통합되고 JSON에서 JSON-LD로 매끄럽게 올라갈 경로를 제공하도록 설계됐다고 밝힌다.

핵심 장치는 `@context`다.
JSON 문서의 키는 그 자체로는 그저 문자열이지만, `@context`는 각 키를 IRI에 대응시켜 전역적으로 유일한 식별자를 부여한다.
`@id`는 노드 식별자를, `@type`은 노드의 타입을 지정한다.

```json
{
  "@context": {
    "name": "http://schema.org/name",
    "email": "http://schema.org/email"
  },
  "@id": "http://example.org/contacts/1",
  "name": "Ann Arbuckle",
  "email": "aa@example.org"
}
```

프로파일 관점에서 보면 JSON-LD의 `@context`는 ALPS의 서술자 어휘와 같은 일을 한다 — 표현에 등장하는 이름이 무엇을 뜻하는지를 밖에서 정의하고 표현이 그것을 가리키게 한다.
차이는 두 가지다.

첫째, JSON-LD의 의미 단위는 IRI로 식별되는 전역 어휘(schema.org 같은)이고, ALPS의 의미 단위는 프로파일 문서 안에서 `id`로 식별되는 지역 서술자다.
둘째, JSON-LD 자체에는 상태 전이 개념이 없다 — 데이터의 의미는 주지만 “이 요청을 하면 무슨 일이 일어나는가”는 말하지 않는다.
그 빈칸을 채우려는 것이 JSON-LD 위에 얹힌 Hydra 어휘이며, 10장의 하이퍼미디어 지형도에서 다시 만난다.

## 프로파일이라는 베팅의 성격

저자가 8장 서두에서 “이 장부터 내 조언이 최신 기술을 앞서간다”고 밝힌 것은 기술적 겸양이 아니라 정확한 상태 보고다.
프로파일은 2013년 시점에 문제 정식화가 막 끝난 영역이었고, 저자가 권하는 형식은 저자 자신이 이 책을 위해 만들어야 했던 것이었다.

이 정직함이 8장의 논지를 오히려 강하게 만든다.
저자가 다른 글에서 밝혔듯, 프로파일이 정답이 아닐 수도 있지만 이 문제는 어떻게든 풀어야 하고 전작은 이 문제를 정식화조차 하지 못했다.
8장이 남긴 것은 특정 형식의 승리가 아니라 문제의 정식화다 — 데이터 형식은 여러 API가 공유하고 API 구현은 저마다 다른데, 그 사이의 도메인 의미를 기계가 읽을 수 있게 어디에 어떻게 두어야 하는가.

## 핵심 정리

프로파일은 여러 API가 공유하는 데이터 형식과 특정 API 구현 사이의 틈을 메운다.
그 틈이란 하이퍼미디어가 못 푸는 절반, 곧 “이 요청이 실세계에서 무엇을 뜻하는가”라는 의미의 문제다.

RFC 6906은 `profile` 링크 관계를 등록하며 프로파일의 규칙을 정했다.
프로파일은 기본 미디어 타입 의미를 바꿔서는 안 되고, 프로파일을 모르는 클라이언트도 같은 표현을 안전하게 쓸 수 있어야 하며, 프로파일 URI는 링크가 아니라 식별자로 다뤄야 한다.

ALPS는 저자가 이 책을 위해 만든 프로파일 형식이며 `application/alps+xml`과 `application/alps+json`을 등록한다.
문서의 중심은 `descriptor`이고, `type` 값 `semantic`, `safe`, `idempotent`, `unsafe`가 데이터 요소와 세 종류의 상태 전이를 구분한다.
ALPS 문서에는 URL이 없다 — 어휘만 정의하고 URL은 런타임에 서버가 표현으로 알려 준다.

같은 ALPS 프로파일이 HTML, HAL, Collection+JSON 등 여러 미디어 타입의 표현에 그대로 적용된다.
그래서 클라이언트는 미디어 타입 구조가 아니라 프로파일에 대고 코딩할 수 있고, 응답 레이아웃 변경이나 미디어 타입 교체에도 견딘다.

XMDP는 HTML4가 형식을 정의하지 않고 남긴 `profile` 속성의 자리를 XHTML 부분집합으로 채운 초기 시도다.
JSON-LD는 Linked Data 계보에서 `@context`로 JSON 키에 IRI를 붙여 같은 문제에 접근하지만, 그 자체에는 상태 전이 개념이 없다.

이 장은 저자 스스로 최신 기술을 앞서간다고 밝힌 지점이며, 권장 형식 ALPS는 2020년 draft-04 시점에도 RFC가 되지 못했다.
8장이 남긴 지속적 가치는 특정 형식이 아니라 문제의 정식화 자체다.
