# RESTful Web APIs와 RESTful Web Services는 무엇이 다른가

원문: [What's New in RESTful Web APIs?](https://www.crummy.com/2013/10/21/0)

## 요약

Leonard Richardson가 2013년에 발표한 이 글은 자신의 저서 두 권,
2007년의 _RESTful Web Services_와 2013년의 후속작 _RESTful Web APIs_가
어떻게 다른지를 설명한다. 그는 먼저 옛 책이 이제는 시대에 뒤떨어졌으며
무료로 온라인에 공개되어 있으니 굳이 구매할 필요가 없다고 분명히 한다.

이 글은 2013년 10월 21일, 트위터에서 두 책 사이에 무엇이 바뀌었느냐는 질문을 받고 쓴 답이다.
저자는 O'Reilly가 옛 책을 절판 중이니 실수로라도 사지 말라고 당부하고, 샀다면 반품하라고까지 말한다.
그렇지 않으면 자기 로열티에서 차감된다는 이유다.

두 판 사이의 핵심적인 차이는 세 가지다. 첫째, 새 책은 JSON과 호환되는
하이퍼미디어 문서를 설계하는 문제를 정면으로 다룬다. 2007년 당시에는
JSON이 아직 API의 지배적인 포맷이 아니었기 때문에 이 문제 자체가
존재하지 않았고, 새 책은 2장부터 본격적으로 이 주제를 다룬다.
저자는 이 문제를 다루지 않는 책은 망가진 현상 유지를 떠받치는 것이라고 단언하며, 새 책은 2장부터 이 문제를 두드리기 시작해 끝까지 멈추지 않는다고 말한다.

둘째, 2007년 이후 Collection+JSON, Siren, HAL, JSON-LD 등 다양한
하이퍼미디어 기술이 새로 등장했다. 새 책은 원저에는 없었던 이러한
기술들을 포괄적으로 다룬다.

셋째, 새 판은 프로필(profile)이라는 개념을 도입한다. 이는 API 상호작용
안에서 실세계의 의미를 전달하는 최신 접근법으로, 2007년에는 상상할 수도
없었던 개념이라고 저자는 말한다.

Richardson는 두 책 사이에 근본적인 관점 전환이 있었다고 짚는다.
_Services_가 서버 측 리소스(resource)를 강조했다면, _RESTful Web APIs_는
클라이언트와 서버가 주고받는 문서인 표현(representation)을 우선한다.
새 책은 하이퍼미디어가 클라이언트를 유효한 HTTP 요청으로 이끄는
역할을 일관되게 강조한다. 저자는 또한 “컬렉션 패턴(collection
pattern)”을 현대 API 설계의 핵심으로 꼽으며, 이는 Atom Publishing
Protocol에서 처음 도입된 접근법으로 REST API의 약 80%가 이 패턴을
따른다고 밝힌다.

옛 책의 도입부 이야기, 즉 웹 API는 웹과 같은 원리로 작동하고 HTTP는 이렇게 돌아가며 Fielding의 제약은 이런 일을 한다는 설명은 새 책에도 남았다.
다만 클라이언트와 서버가 표현을 주고받으며 서로의 상태를 바꾸는 상호작용에 늘 초점을 두도록 다시 쓰였다.

컬렉션 패턴은 Atom Publishing Protocol이 개척한 CRUD에 가까운 설계다.
어떤 리소스는 GET, PUT, DELETE에 응답하는 아이템이고, 어떤 리소스는 아이템을 담으며 POST로 새 아이템을 추가받는 컬렉션이다.
저자는 이른바 REST API의 약 80%가 이 패턴에 들어가지만 REST는 그보다 크며, 이 패턴에 이름을 붙이고 정의해야 비로소 그 너머를 볼 수 있다고 말한다.

프로필은 하이퍼미디어가 풀지 못하는 문제를 겨냥한다.
하이퍼미디어는 클라이언트가 다음에 어떤 HTTP 요청을 할 수 있는지는 잘 알려 주지만, 그 요청이 실세계에서 무엇을 뜻하는지는 알려 주지 못한다.
8장 이전에 쓰이던 해법은 두 가지였다.
사람이 읽는 문서로 미리 설명하거나, Maze+XML처럼 도메인 특화 미디어 타입을 새로 정의하는 것이고, 저자는 둘 다 큰 문제가 있다고 본다.
8장의 프로필은 새 미디어 타입을 만들지 않고도 그 이점의 일부를 얻게 해 준다.
저자는 이 책을 위해 ALPS 형식을 직접 개발해야 했다고 밝히며, 프로필이 정답이 아닐 수도 있지만 이 문제는 어떻게든 풀어야 하고 옛 책은 이 문제를 정식화조차 못 했다고 덧붙인다.

## 분석

### 왜 관점이 리소스에서 표현으로 옮겨갔는가

2007년의 _RESTful Web Services_는 REST를 URI로 식별되는 리소스의
집합으로 설명하는 전통적인 프레이밍을 따랐다. 이는 Fielding의 논문이
제시한 아키텍처 스타일을 충실히 따르는 접근이지만, 실무자에게는
“어떤 리소스를 어떤 URI에 둘 것인가”라는 설계 질문에 매몰되기 쉬운
프레임이었다. 반면 2013년 판이 표현을 중심에 두는 것은, REST API를
실제로 사용하는 개발자의 경험이 리소스 자체가 아니라 요청과 응답으로
오가는 JSON/XML 문서라는 사실을 반영한다. 클라이언트는 서버의 리소스
모델에 접근할 수 없고, 오직 표현만을 주고받으며 다음 행동을 결정한다.
이 전환은 단순한 용어 변경이 아니라, REST API 설계를 아키텍처
다이어그램의 문제에서 문서 포맷과 하이퍼미디어 제어의 문제로
재정의하는 작업이다.

이 재배치는 REST라는 이름과도 맞아떨어진다.
Representational State Transfer라는 이름 자체가 표현을 중심에 두는데, 옛 책은 역설적으로 리소스에 초점을 맞춰 그 이름의 절반을 덜 강조했다.
이 저장소의 RESTful Web Services 정리에서 본 “ROA는 리소스·URI·표현·링크의 네 개념”이라는 틀에서[^ref-rws], 강조점이 표현과 그것을 잇는 하이퍼미디어로 옮겨 간 것이다.
표현에 초점을 맞추면 한 표현이 다음에 가능한 표현과 요청을 어떻게 알려 주느냐가 중심 질문이 되고, 그 답이 하이퍼미디어다.
옛 책이 리소스를 서버 구현의 관점에서 봤다면 새 책은 표현을 클라이언트가 따라가는 상태 기계의 관점에서 보며, 이 전환이 나머지 두 변화의 토대가 된다.

### JSON의 부상이 만든 새로운 문제

2007년 시점에 JSON은 REST API의 지배적 포맷이 아니었다. 당시 REST 논의는
XML 기반 하이퍼미디어(Atom, XHTML)를 전제로 이루어졌고, XML은 임의의
문서 구조에 링크와 폼을 자연스럽게 끼워 넣을 수 있는 성숙한 도구였다.
그런데 JSON이 API 포맷의 사실상 표준이 되면서, “JSON 문서 안에 어떻게
하이퍼미디어 제어(링크, 폼)를 표준적인 방식으로 넣을 것인가”라는
문제가 새로 생겨났다. JSON 자체에는 링크나 관계를 표현하는 내장 문법이
없기 때문이다. Collection+JSON, HAL, Siren 같은 포맷들은 모두 이
공백을 메우기 위한 경쟁적 시도였고, 새 책이 이들을 폭넓게 다루는 것은
업계가 아직 단일한 답에 수렴하지 못했다는 사실 자체를 반영한다.

### 프로필 개념이 노리는 것

프로필은 표현의 미디어 타입만으로는 전달할 수 없는 도메인 의미론을
보완하기 위한 장치다. 예컨대 HAL이나 Siren 같은 범용 하이퍼미디어
포맷은 “이것이 링크다”, “이것이 컬렉션이다”라는 구조적 정보는
전달하지만, “이 링크가 가리키는 것이 주문(order)인지 고객(customer)인지”
같은 의미는 별도로 정의해야 한다. 프로필은 이 간극을 메우는 시도이며,
동시에 REST 커뮤니티가 “완전히 범용적인 하이퍼미디어 포맷 하나로 모든
도메인을 다 표현할 수 있다”는 초기의 이상에서 한발 물러났다는 신호이기도
하다.

### 컬렉션 패턴에 이름을 붙인 것이 이 글의 개념적 진전이다

저자가 컬렉션 패턴에 이름을 붙여야 그 너머를 볼 수 있다고 한 대목은 이 글에서 가장 통찰력 있는 부분이다.
현상에 이름을 주는 일은 그것을 상대화하고 넘어설 도구를 만든다.
컬렉션 패턴은 REST API의 80%를 차지할 만큼 흔하지만, 너무 흔해서 그것이 여러 선택지 중 하나라는 사실이 보이지 않았다.

옛 책도 AtomPub을 다뤘지만 그것을 패턴으로 부르지 않았고, 그 사이 6년 동안 같은 구조가 수없이 다시 발명됐다.
새 책은 Collection+JSON과 OData가 이 패턴을 명시적으로 담고 Siren과 Hydra가 더 미묘하게 담는다고 관찰하는데, 새 형식들조차 대체로 이 패턴의 변주라는 뜻이다.
디자인 패턴이 소프트웨어 공학에서 한 일과 같다.
반복되는 해법에 이름을 주면 그것을 의식적으로 고르거나 거부할 수 있게 되고, REST가 곧 컬렉션 패턴이라는 암묵적 등식이 깨진다.

### 닮은 두 질문을 가른 것이 프로필 논의의 토대다

저자는 하이퍼미디어가 푸는 질문과 풀지 못하는 질문을 분명히 나눈다.
`<a href="/orders/5/cancel">` 같은 링크는 클라이언트에게 이 요청을 보낼 수 있다는 사실은 알려 주지만, 그것이 주문을 취소한다는 실세계의 의미는 링크만으로 전달되지 않는다.
이 구분은 하이퍼미디어의 한계를 정직하게 인정하는 일이고, 동시에 프로필이 들어설 자리를 만든다.

ALPS 같은 프로필은 여러 API가 공유하는 데이터 형식과 특정 API 구현 사이의 틈, 곧 이 링크가 실세계에서 무엇을 하느냐는 의미를 메우려는 시도다.
저자가 이 책을 위해 ALPS를 직접 개발해야 했다는 사실은, 2013년 당시 기존 도구로는 이 문제가 풀리지 않았다는 뜻이다.
이것이 이 글의 미해결 최전선이면서, 아래 비평이 겨냥하는 검증되지 않은 베팅의 지점이기도 하다.

## 비평

### “80%가 컬렉션 패턴을 쓴다”는 근거가 제시되지 않는다

Richardson는 REST API의 약 80%가 컬렉션 패턴을 사용한다고 단언하지만,
이 수치의 출처나 조사 방법은 이 글에서 전혀 드러나지 않는다. 이는
저자 자신의 경험적 관찰일 수도 있고, 특정 API 디렉토리를 조사한
결과일 수도 있지만, 글만 보아서는 구분할 수 없다. 이런 정량적 주장은
독자가 “정말 그런가?”를 검증할 방법이 없는 상태로 제시될 때 설득력이
아니라 권위에 기대는 수사가 된다. 컬렉션 패턴이 흔하다는 주장 자체는
합리적이지만, 구체적 수치를 붙이는 순간 그 수치를 뒷받침할 근거도
함께 제시해야 한다.

### 옛 책을 “구매하지 말라”는 조언은 과도하게 단순하다

저자는 _RESTful Web Services_가 시대에 뒤떨어졌으니 사지 말라고
권하지만, 이는 두 책의 관계를 지나치게 단순화한다. 옛 책이 다루는
Fielding의 REST 제약 조건, URI 설계, HTTP 메서드의 의미론 같은 기초는
2013년 시점에도 여전히 유효했을 내용이다. 실제로 바뀐 것은 하이퍼미디어
포맷의 생태계와 JSON의 위상이지, REST의 근본 원리가 아니다. “옛 책은
낡았다”는 프레이밍은 두 책이 실제로 공유하는 기초를 지워버리고,
독자가 무엇이 정말 바뀌었는지 판단할 기회를 빼앗는다.

이 서사는 저자의 이해관계와도 얽혀 있다.
저자는 두 책의 저자이자 로열티 수령자이고, 옛 책을 샀다면 반품하라는 말까지 한다.
정직한 공개이지만, 글의 목적이 순수한 기술 비교만이 아니라 구매 유도이기도 하다는 사실을 드러낸다.
옛 책이 망가진 현상 유지를 떠받친다는 강한 표현은 기술적 판단이면서 신간을 돋보이게 하는 대비 수사이고, 그 우위의 근거가 된 하이퍼미디어 형식과 프로필이 실무에서 얼마나 검증됐는지는 이 글이 답하지 않는다.

저자 자신도 이 긴장을 무심코 드러낸다.
옛 책을 HTTP 레퍼런스로만 썼다면 새 책은 필요 없고, 2007년 이후 추가된 Link 헤더나 PATCH 형식만 보충하면 된다고 인정하기 때문이다.
옛 책의 기초가 여전히 유효하다면, 낡은 것은 책 전체가 아니라 그 위에 얹힌 최신 형식들이다.

### 하이퍼미디어 전면화라는 베팅은 실무에서 대체로 빗나갔다

이 글의 가장 근본적인 약점은 시간이 드러냈다.
저자는 2013년에 JSON과 하이퍼미디어의 결합이 미래라고 걸었지만, 2026년 시점에서 그 예측은 주류 API 설계에서 대체로 실현되지 않았다.
HAL, Siren, Collection+JSON은 틈새로 남았고, JSON-LD와 Hydra는 시맨틱 웹 진영 밖으로 거의 퍼지지 않았으며, 저자가 직접 만든 ALPS도 널리 채택되지 않았다.
현실의 REST API는 여전히 저자가 현상 유지라 부른 것, 곧 하이퍼미디어 없는 컬렉션 패턴 JSON이고, 오히려 GraphQL, gRPC, tRPC 같은 비하이퍼미디어 접근이 부상했다.

이 빗나감은 80% 관찰과 아이러니하게 맞물린다.
저자는 REST API의 80%가 컬렉션 패턴이고 REST는 그보다 크다며, 나머지 20%를 향해 책의 대부분을 썼다.
실무는 반대로 갔다.
그 80%가 오히려 더 늘었고, 저자가 조명한 정교한 하이퍼미디어 기법은 소수 애호가의 영역으로 남았다.
패턴에 이름을 붙여 그 너머를 보게 했다는 기여는 개념적으로 옳지만, 실무가 그 너머로 가지 않았다면 책의 무게 중심은 현실과 어긋난 것이다.

### 프로필의 실효성에 대한 의문을 저자 스스로 회피한다

글은 프로필을 “혁신적인 최신 개념”으로 소개하지만, 프로필이 실제로
클라이언트 개발자의 작업을 얼마나 줄여주는지, 혹은 프로필을 정의하고
유지하는 비용이 얼마나 되는지는 다루지 않는다. 새로운 표준을
도입한다는 것은 그 표준을 채택하고 유지하는 비용이 새로 발생한다는
뜻이다. 이 글이 쓰인 시점에서 프로필이 아직 검증되지 않은 개념이었다는
점을 고려하면, “혁신적”이라는 수식어보다 “아직 실효성이 입증되지 않은
시도”라는 신중한 평가가 더 정확했을 것이다.

저자는 프로필이 정답이 아닐 수도 있고 이 조언이 집필 당시의 최신 기술을 앞서간다고 인정한다.
지적으로 정직한 태도이지만, 독자가 8장에서 무엇을 확신하고 가져가야 할지는 흐려진다.
어떻게든 풀어야 한다는 당위는 문제의 중요성을 강조할 뿐, 그 해법이 살아남을 근거는 주지 않는다.
결국 책의 가장 야심 찬 부분이 가장 검증되지 않은 부분이고, 독자에게 남는 것은 이 문제가 중요하다는 인식이지 이렇게 풀린다는 해법이 아니다.

## 인사이트

### 하이퍼미디어 포맷의 난립은 표준화 실패의 신호였다

2007년부터 2013년 사이에 Collection+JSON, HAL, Siren, JSON-LD 등
여러 하이퍼미디어 포맷이 동시다발적으로 등장했다는 사실은, 이 글이
암시하는 것처럼 “생태계가 풍성해졌다”는 신호가 아니라 업계가 단일
표준에 수렴하는 데 실패했다는 신호로 읽는 편이 더 정확하다. 실제로
2020년대 현재까지도 이들 포맷 중 어느 것도 JSON 하이퍼미디어의
사실상 표준 지위를 차지하지 못했고, 대다수 실무 API는 하이퍼미디어
제어 없이 단순한 JSON과 별도의 문서화(OpenAPI 등)로 대체하는 방향으로
갔다. 이는 HATEOAS(Hypermedia as the Engine of Application State)라는
REST의 핵심 제약이 실무에서 채택 장벽이 매우 높았다는 것을 보여주는
사례이며, 여러 경쟁 포맷의 존재 자체가 그 채택 실패의 증상이었다고
볼 수 있다.

### REST 진영의 자기 정의는 계속 후퇴해 왔다

Fielding의 원 논문부터 Richardson의 2007년 책, 그리고 이 2013년 글까지
이어지는 궤적을 보면, “진짜 REST”의 정의가 점점 더 관대해지는 방향으로
움직여 왔음을 알 수 있다. 리소스 중심에서 표현 중심으로, 범용
하이퍼미디어 포맷에서 프로필로 보완되는 하이퍼미디어 포맷으로 옮겨가는
과정은 이론이 실무의 저항에 부딪힐 때마다 정의를 넓혀 그 저항을
흡수하는 패턴이다. 이는 REST만의 특수한 현상이 아니라, 애자일이나
마이크로서비스 같은 다른 아키텍처/방법론 용어들도 겪은 공통된
궤적이다. 처음에는 엄격한 제약의 집합으로 출발했다가, 실무자들이
그 제약을 온전히 지키지 못하면 용어 자체가 느슨해지며 결국 “REST API”라는
말이 “HTTP와 JSON을 쓰는 API”와 거의 동의어가 되어버리는 결말로
수렴한다.

### 프로필이라는 아이디어는 시맨틱 웹의 축소판 재도전이다

프로필 개념이 시도하는 것 — 범용 포맷 위에 도메인 특화 의미론을
얹는 것 — 은 사실 2000년대 초 시맨틱 웹(Semantic Web)이 온톨로지와
RDF를 통해 시도했던 것의 축소판이다. 시맨틱 웹은 지나치게 야심 찬
전 지구적 의미론 체계를 구축하려다 실무 채택에 실패했다는 평가를
받는데, 프로필은 그 교훈을 받아들여 범위를 개별 API의 문서 단위로
축소한 재도전으로 볼 수 있다. 이 글은 프로필을 완전히 새로운 개념처럼
소개하지만, 실제로는 “의미론을 기계가 읽을 수 있게 별도로 명시한다”는
오래된 아이디어가 스케일을 낮춰 돌아온 것에 가깝다. 이런 계보를
파악하면, 프로필이 채택되려면 시맨틱 웹이 실패한 지점 — 즉 의미론을
정의하고 유지하는 비용을 실무자가 감당할 만큼 낮추는 것 — 을
해결해야 한다는 예측을 세울 수 있다.

### 하이퍼미디어와 프로필의 진짜 사용자는 AI 에이전트였다

저자가 2013년에 정식화한 두 질문, 곧 클라이언트가 다음에 어떤 요청을 할 수 있느냐와 그 요청이 실세계에서 무엇을 뜻하느냐는 사람이 짜는 클라이언트에게는 대체로 필요 없었다.
그러나 2026년의 AI 에이전트에게는 정확히 핵심 문제가 됐다.
이 책의 비전은 시대를 잘못 만난 것이 아니라 사용자를 잘못 예측한 것이다.

사람이 API 클라이언트를 짤 때는 문서를 읽고 URL을 하드코딩하면 되므로, 서버가 런타임에 가능한 요청을 알려 주는 하이퍼미디어는 과잉이었다.
이것이 하이퍼미디어가 실무에서 빗나간 이유다.
LLM 에이전트는 문서를 미리 읽고 코드를 짜는 대신 런타임에 지금 무엇을 할 수 있는지 알아야 하고, 그것이 바로 하이퍼미디어가 푸는 문제다.
서버가 다음 HTTP 요청을 알려 주는 최선의 방법이 하이퍼미디어라는 저자의 문장은, 13년 뒤 MCP의 도구 목록(`tools/list`)과 에이전트가 런타임에 능력을 발견하는 구조에서 되살아난다[^ref-mcp].

프로필 문제도 같은 방식으로 재발견된다.
하이퍼미디어로는 풀 수 없다던 실세계 의미의 문제는, 정확히 MCP 도구의 자연어 설명이 LLM에게 풀어 주려는 문제다.
에이전트에게 `POST /orders/5/cancel`이 주문을 취소한다는 뜻임을 알려 주는 일, 저자가 프로필과 ALPS로 시도한 그 일이 이제 도구 설명과 스키마로 구현된다.
모델이 무엇을 할 수 있고 그것이 무슨 뜻인지를 런타임에 공급받는 아키텍처가[^ref-knowledge] 저자가 그린 하이퍼미디어와 프로필 비전의 실현인 셈이다.

### 이름 붙이기가 개념적 진보의 핵심 행위다

저자가 컬렉션 패턴에 이름을 붙인 일은 개별 기여를 넘어, 지식이 어떻게 진보하는지에 대한 일반 원리를 보여 준다.
이름이 없는 것은 대상화되지 않는다.
컬렉션 패턴이 이름 없이 REST API의 80%를 차지할 때 그것은 REST가 원래 그런 것처럼 보였고 대안이 보이지 않았다.
이름을 얻자 이것은 하나의 패턴이고 REST는 그보다 크다는 인식이 열렸다.

디자인 패턴 운동이 Singleton과 Observer에 이름을 붙여 그것을 의식적으로 고르거나 거부하게 한 것과 같은 일이다.
옛 책이 AtomPub이라는 개별 표준을 다뤘다면, 새 책은 그것을 컬렉션 패턴으로 추상화해 Collection+JSON, OData, Siren이 모두 그 변주임을 드러냈다.
이 추상화가 없으면 새 형식이 나올 때마다 또 하나의 표준처럼 보이지만, 패턴으로 보면 같은 패턴의 다른 구현으로 정리된다.
좋은 기술서가 개별 도구가 아니라 그 도구들의 문법을 가르치는 이유가 여기 있다.

### 기초는 남고 최신은 낡는다는 것이 기술서의 역설이다

이 글에서 가장 오래 남는 교훈은 저자가 무심코 인정한 대목, 곧 HTTP는 그리 많이 바뀌지 않았다는 말에 있다.
책의 최신 부분인 하이퍼미디어 형식과 프로필은 빠르게 낡았지만, 옛 책과 공유하는 기초인 HTTP와 Fielding 제약은 지금도 유효하다.
기술의 층위마다 수명이 다르기 때문이다.
이 저장소의 RESTful Web Services 정리에서 본, REST와 ROA의 개념은 유효하지만 특정 프레임워크와 포맷은 시대의 흔적이라는 관찰이[^ref-rws] 저자 자신의 입으로 확인된다.

빠르게 바뀌는 층인 형식, 도구, 표준을 다루는 책은 빠르게 낡고, 느리게 바뀌는 층인 프로토콜, 원리, 제약을 다루는 부분은 오래 남는다.
새 책의 하이퍼미디어 동물원(10장)은 2026년엔 대부분 역사적 유물이 됐지만, 그 책이 옛 책과 공유하는 HTTP, 리소스, 표현의 기초는 여전히 API 설계의 토대다.
저자는 새 책이 미래를 다룬다고 팔았지만, 역설적으로 그 책에서 가장 오래 살아남은 것은 옛 책과 공유하는 과거였다.
