# RESTful Web APIs 예제 코드: 하나의 서버, 세 개의 클라이언트

<https://github.com/RESTful-Web-APIs/example-code>

## 소개

《RESTful Web APIs》(Richardson & Amundsen, O'Reilly 2013)의 클라이언트·서버 예제를 담은 Node.js
저장소다.
2013년 9월에 만들어졌고 마지막 푸시는 2019년 10월이며, 라이선스는 명시돼 있지 않다.
저장소는 두 개의 예제 세계로 나뉜다 — 책 6장의 컬렉션 패턴을 보이는 “You Type It, We Post
It”(Collection+JSON), 그리고 5장의 도메인 특화 설계를 보이는 “The Maze”(Maze+XML)다.

구성은 README에 정리돼 있다.
`/YouTypeIt/server`는 웹사이트와 API를 함께 제공하는 Node.js 서버이고, `/YouTypeIt/test`는
POST·PUT 테스트에 쓸 샘플 표현이다.
`/Maze/server`는 Maze+XML 서버이며, 클라이언트는 셋이다 — 사용자가 미로를 직접 탐험하는
대화형 클라이언트 `/Maze/the-game/`, 미로 전체를 ASCII 지도로 그리는 자동 봇 `/Maze/the-mapmaker/`,
그리고 실제로는 미로를 통과하지 않고 통과했다고 주장하는 클라이언트 `/Maze/the-boaster/`다.

의존성은 극도로 얇다.
서버는 Express 같은 프레임워크 없이 Node의 `http` 모듈만 쓰고, 클라이언트는 XML 파싱을 위한
`xmldom`(0.1.x)과 정적 파일 서빙을 위한 `mime`(1.2.x)만 의존한다.
`package.json`의 engines는 `node 0.8.x`, `npm 1.1.x`로, 2013년 당시의 런타임을 그대로 남기고
있다.

## You Type It, We Post It: 같은 서버가 웹사이트와 API를 함께 낸다

`YouTypeIt/server/app.js`는 마이크로블로깅 서비스를 한 프로세스에서 두 얼굴로 제공한다.
브라우저용 HTML 경로와 프로그래밍용 API 경로를 정규식 라우팅으로 나란히 둔 것이 이 예제의 핵심
구조다.

```javascript
// 브라우저 요청용
var reHome   = new RegExp('^\/$','i');
var reAbout  = new RegExp('^\/about$','i');
var reList   = new RegExp('^\/messages$','i');
var reItem   = new RegExp('^\/messages\/.*','i');

// API 요청용
var reAPIList = new RegExp('^\/api\/$', 'i');
var reAPIItem = new RegExp('^\/api\/.*', 'i');
```

두 경로의 메서드 지원이 다르다는 점이 중요하다.
HTML 쪽에서 목록(`/messages`)은 GET과 POST를 받고 나머지는 GET만 받으며, 그 외 메서드에는
405 Method Not Allowed를 돌려준다.
API 쪽에서 목록(`/api/`)은 GET·POST를, 항목(`/api/{id}`)은 GET·PUT·DELETE를 받는다 — 컬렉션
패턴의 전형인 “컬렉션은 POST로 추가, 아이템은 GET/PUT/DELETE”가 코드로 그대로 나타난다.

API 표현은 Collection+JSON 템플릿(`templates/collection.js`) 하나로 만들어진다.

```json
{
    "collection" :
    {
        "version" : "1.0",
        "href" : "{@host}/api/",
        "items" : {@list},
        "template" : {
            "data" : [
                {"prompt" : "Text of message", "name" : "text", "value" : ""}
            ]
        }
    }
}
```

여기서 `template`가 하이퍼미디어의 핵심이다.
서버는 데이터만 주는 게 아니라 “새 메시지를 만들려면 `text`라는 이름의 값을 채워 보내라”는 쓰기
양식을 표현 안에 함께 실어 보낸다.
클라이언트는 이 템플릿을 채워 POST하고(`test/post.js`), 수정할 때도 같은 모양으로 PUT한다(`test/put.js`).

```json
{
  "template" : {
    "data" : [
      {"name" : "text", "value" : "testing"},
      {"name" : "junk", "value" : ""}
    ]
  }
}
```

서버는 이 요청을 `msg.template.data[0].value`로 읽어 저장하고, 응답으로 다시 같은 Collection+JSON
문서를 돌려준다.
HTML 쪽 POST는 폼 인코딩 본문을 받아 처리한 뒤 303 See Other로 새 항목 URL로 보내고, API 쪽
DELETE는 204 No Content를 돌려준다.
테스트 방법도 저장소가 직접 알려 준다 — `curl --verbose -X POST -d @post.js http://localhost:1337/api/`.

## The Maze: 도메인 특화 미디어 타입과 세 종류의 클라이언트

`Maze/server/app.js`는 Maze+XML(`application/vnd.amundsen.maze+xml`) 서버다.
URL 경로의 세그먼트 수만으로 라우팅하는 극단적으로 단순한 구조를 쓴다 — 0개면 미로 목록, 1개면
특정 미로, 2개면 그 미로의 특정 방(cell), 그 이상이면 404다.
GET 외의 메서드는 405를 돌려주고(OPTIONS는 CORS용으로 처리), 모든 응답은 문자열 템플릿을 조립해
XML로 만든다.

미로 데이터는 파일 하나에 담긴 JSON이다.

```javascript
{
  "_id" : "five-by-five",
  "title" : "A Beginner's Maze",
  "cells" : {
      "cell0":{"title":"Entrance Hallway", "doors":[1,1,1,0]},
      "cell1":{"title":"Hall of Knives", "doors":[1,1,1,0]},
      "cell2":{"title":"Library", "doors":[1,1,0,0]}
  }
}
```

`doors` 배열은 북·서·남·동 네 방향의 벽 여부이고, 서버는 이것을 링크로 번역한다.
방 번호 `z`에서 각 방향의 이웃은 `[z-1, z-sq, z+1, z+sq]`(`sq`는 미로 한 변의 크기)로 계산되며,
문이 열린 방향(`doors[i]===0`)에 대해서만 `<link rel=“north” href=“...”>` 같은 링크를 표현에
넣는다.
마지막 방에 도달하면 `rel=“exit”` 링크가 붙고, 모든 방 표현에는 그 미로로 돌아가는 `rel=“maze”`와
전체 목록으로 가는 `rel=“collection”` 링크가 함께 실린다.

이 설계의 요점은 클라이언트가 미로의 구조를 미리 알 필요가 없다는 것이다.
클라이언트는 벽 배열이나 좌표계를 이해하지 않고, 표현에 들어 있는 링크 관계(`north`, `south`,
`east`, `west`, `exit`, `maze`, `collection`, `start`)만 따라간다.
서버가 다음에 갈 수 있는 곳을 표현 안에서 알려 주므로, 클라이언트의 코드는 “어떤 rel을 찾을
것인가”로 환원된다.

### the-mapmaker: 링크만 따라가며 전체 지도를 그린다

`the-mapmaker.js`는 사람 없이 미로 전체를 탐험해 ASCII 지도를 그리는 봇이다.
응답에서 `<link>` 노드를 모두 긁어 rel과 href를 뽑고, 방문 목록(`m.visited`)과 방 목록(`m.rooms`)을
관리하며 재귀적으로 요청을 이어 간다.

```javascript
nodes = doc.getElementsByTagName('link');
for (i = 0, x = nodes.length; i < x; i++) {
    links.push({
        'rel':  nodes[i].getAttribute('rel'),
        'href': nodes[i].getAttribute('href')
    });
}
```

이 클라이언트가 보여 주는 것은 하이퍼미디어 클라이언트의 이상형이다 — 미로가 5×5든 100개
방이든(저장소에는 `100-rooms.txt`도 있다), 코드를 고치지 않고 같은 로직으로 탐험한다.
서버가 미로를 바꿔도 클라이언트는 링크를 따라갈 뿐이다.

### the-boaster: 하이퍼미디어를 따르되 일은 하지 않는다

`the-boaster.js`는 이 저장소에서 가장 의미심장한 예제다.
이름 그대로 “허풍쟁이”이며, 미로를 실제로 통과하지 않고 통과했다고 주장한다.

```javascript
// look for the start and claim victory
link = findLink(links, 'start');
if (link) {
    m.moves = parseInt(Math.random()*12)+1;
    console.log(m.winner.replace('{m}', m.moves));
    return;
}
```

이 클라이언트는 collection → maze 링크를 정직하게 따라가다가, `rel=“start”` 링크를 발견하는
순간 무작위 숫자를 “이동 횟수”로 지어내 “다 끝냈다, 겨우 N번 만에!”라고 출력하고 종료한다.
프로토콜 수준에서 보면 이 클라이언트는 완벽하게 규격을 지킨다 — 올바른 `Accept` 헤더(`application/vnd.amundsen.maze+xml`)를
보내고, 링크 관계를 정확히 해석하며, 서버가 준 하이퍼미디어를 따라간다.
그럼에도 실세계 의미(“미로를 통과한다”)는 전혀 수행하지 않는다.

### the-game: 브라우저에서 도는 사람용 클라이언트

`the-game`은 같은 Maze+XML 서버에 붙는 브라우저 클라이언트다.
`index.js`는 미디어 타입을 명시하고(`g.mediaType = “application/vnd.amundsen.maze+xml”`), 응답
XML에서 rel을 파싱해 사용자가 누를 수 있는 방향 버튼으로 바꾼다.
서버 URL을 사용자가 직접 입력하게 하고(`select-server` 폼), 미로 목록에서 하나를 고르고(`select-maze`),
그다음부터는 표현에 실린 링크만으로 이동한다.
rel 값이 공백으로 구분된 복수일 수 있다는 것까지 처리한다(`rels = xml[i].getAttribute('rel').split(' ')`).

## 분석

### 이 저장소의 진짜 교재는 코드가 아니라 “같은 서버에 붙는 세 클라이언트”다

저장소를 파일 단위로 보면 평범한 2013년 Node.js 코드지만, 구성 단위로 보면 하나의 교육적 배치가
드러난다.
같은 Maze+XML 서버에 성격이 전혀 다른 세 클라이언트가 붙고, 서버 코드는 한 줄도 바뀌지 않는다.

이 배치가 중요한 이유는 그것이 하이퍼미디어의 약속을 실물로 증명하기 때문이다.
사람이 조작하는 브라우저 클라이언트(the-game), 사람 없이 도는 탐험 봇(the-mapmaker), 그리고 규격만
지키고 일은 안 하는 클라이언트(the-boaster)가 모두 같은 표현을 소비한다.
서버는 “이 클라이언트가 브라우저인지 봇인지”를 알 필요가 없고, 클라이언트는 “미로가 어떻게
생겼는지”를 미리 알 필요가 없다 — 둘을 잇는 것은 오직 미디어 타입과 링크 관계의 약속이다.
앞서 이 저장소의 RESTful Web Services 정리에서 본 “통일 인터페이스와 연결성(connectedness)”이[^ref-rws]
여기서 실행 가능한 코드로 나타난다.

이 배치가 책의 5장(도메인 특화 설계)과 6장(컬렉션 패턴)의 대비도 실물로 보여준다.
Maze+XML은 미로라는 특정 도메인을 위해 만든 미디어 타입이고, Collection+JSON은 여러 도메인이
공유하는 범용 패턴이다.
같은 저장소에 둘을 나란히 두어, 독자가 “새 미디어 타입을 만들 것인가, 기존 패턴을 쓸 것인가”라는
5·6장의 선택을 코드로 비교하게 한다.

### the-boaster는 농담이 아니라 책의 핵심 논증을 실행 가능한 형태로 남긴 것이다

세 클라이언트 중 the-boaster만 아무 쓸모 없는 일을 한다.
그러나 이 “쓸모없음”이야말로 책이 8장에서 프로파일을 도입하는 이유를 가장 선명하게 보여주는
장치다.

이 클라이언트가 드러내는 것은 하이퍼미디어의 정확한 한계다.
저자들이 crummy 글에서 정식화한 두 질문 — “클라이언트가 다음에 어떤 요청을 할 수 있는가”와
“그 요청이 실세계 관점에서 무엇을 뜻하는가” — 중[^ref-whatsnew] 하이퍼미디어는 앞의 것만 푼다.
the-boaster는 앞의 질문에 완벽히 답한다: `Accept` 헤더를 올바르게 보내고, `collection`·`maze`·`start`
rel을 정확히 찾아 따라간다.
그러나 뒤의 질문 — “미로를 통과한다는 것이 실세계에서 무슨 뜻인가” — 은 프로토콜 어디에도 없으므로,
클라이언트는 통과하는 척만 하고도 규격 위반을 하지 않는다.

이 예제가 API 설계 논의에 던지는 함의가 크다.
“하이퍼미디어를 쓰면 클라이언트가 알아서 올바르게 동작한다”는 낙관은 the-boaster 앞에서 무너진다 —
하이퍼미디어는 가능한 전이를 알려 줄 뿐, 그 전이의 의미를 강제하지 못한다.
저자들이 이 클라이언트를 굳이 만들어 저장소에 남긴 것은, 자기 기술의 한계를 스스로 실행 가능한
반례로 제시한 것이며, 이것이 8장 프로파일(ALPS)의 필요를 코드로 정당화한다.

### 프레임워크 없는 구현이 프로토콜을 가리지 않으려는 선택이다

두 서버 모두 Express나 라우터 라이브러리를 쓰지 않고 Node의 `http` 모듈과 정규식·문자열 템플릿만
쓴다.
2013년에도 Express는 이미 표준에 가까웠으므로, 이것은 능력 부족이 아니라 의도적 선택이다.

이 선택이 교육적으로 옳은 이유는 프레임워크가 프로토콜을 감추기 때문이다.
Express로 쓰면 `app.get('/messages/:id', ...)` 한 줄이 라우팅·메서드 매칭·응답을 모두 처리해,
정작 배워야 할 것 — 어떤 URL이 어떤 메서드를 받고, 안 받는 메서드에는 405를 돌려주며, 상태
코드와 헤더를 어떻게 고르는가 — 이 프레임워크 뒤로 사라진다.
Maze 서버가 `res.writeHead(code, headers)`로 직접 응답을 쓰고, YouTypeIt 서버가 메서드마다
`switch`로 405를 명시적으로 처리하는 것은, HTTP의 통일 인터페이스를 코드 표면에 드러내려는
것이다.

이 선택의 대가도 분명하다.
문자열 연결로 XML을 만들고(`template.link.replace('{l}', ...)`), 정규식으로 라우팅하며, 표현
생성과 비즈니스 로직이 한 파일에 섞인다.
이는 프로덕션 코드로는 권할 수 없지만, “하이퍼미디어 표현이 결국 문자열이고 그 안의 링크가
클라이언트의 다음 행동을 결정한다”는 사실을 가장 앙상하게 보여준다.
교재용 코드와 실무용 코드의 목적이 다르다는 것을 이 저장소는 정직하게 드러낸다.

## 비평

### 저장소가 책의 13개 장 중 두 장만 커버한다

README와 실제 파일 구조를 보면 이 저장소는 5장(Maze+XML)과 6장(Collection+JSON)의 예제만 담는다.
책의 나머지 열한 장 — 특히 저자들이 가장 야심 차게 다룬 7장(HAL·Siren), 8장(프로파일·ALPS),
9장(설계 절차), 12장(JSON-LD·RDF), 13장(CoAP) — 에 대응하는 코드가 없다.

이 공백이 문제인 이유는 코드가 없는 장이 바로 검증이 가장 필요한 장이기 때문이다.
Maze+XML과 Collection+JSON은 개념이 단순해 글만으로도 이해되지만, ALPS 프로파일이 실제 클라이언트
동작을 어떻게 바꾸는지는 코드 없이 상상하기 어렵다.
저자 자신이 이 책을 위해 ALPS를 직접 개발했다고 밝힌 만큼[^ref-whatsnew], 그 형식이 실제로 어떤
클라이언트 코드를 가능하게 하는지를 보이는 예제가 있었다면 8장의 설득력이 훨씬 컸을 것이다.
가장 검증되지 않은 아이디어에 예제가 없다는 것은, 독자가 그 장을 개념으로만 받아들여야 한다는
뜻이다.

이 불균형이 저장소의 실용적 가치도 제한한다.
독자가 “책을 읽고 코드로 확인한다”는 학습 경로를 택하면, 초반 두 장 이후로는 참고할 것이 없다.
the-boaster처럼 개념을 예리하게 드러내는 예제가 프로파일 영역에도 있었다면 — 예컨대 “프로파일이
있는 클라이언트와 없는 클라이언트의 차이”를 보이는 한 쌍 — 저장소가 책의 논증을 훨씬 강하게
뒷받침했을 것이다.
현재 구성은 “쉬운 부분은 코드로, 어려운 부분은 글로”라는 비대칭을 남긴다.

### 벤더링된 `node_modules`가 저장소의 대부분을 차지한다

파일 목록을 보면 실제 예제 코드는 열 몇 개 파일이지만, 저장소 파일의 압도적 다수는 세 클라이언트에
각각 커밋된 `node_modules/xmldom`이다.
같은 라이브러리가 세 번 중복돼 있고, 그중에는 1.2MB짜리 테스트 XML 파일(`test/test.xml`)이 세 벌
들어 있다.

이 상태가 문제인 이유는 그것이 예제의 초점을 흐리기 때문이다.
독자가 저장소를 클론하면 3.6MB가 넘는 테스트 픽스처와 서드파티 코드가 따라오며, 정작 읽어야 할
`the-boaster.js`(2.8KB)나 `the-mapmaker.js`(8.6KB)는 그 사이에 묻힌다.
`.gitignore`가 있는데도 `node_modules`가 커밋된 것은 2013년 당시 npm 생태계의 불안정(설치 재현성
문제)에 대한 방어였을 수 있지만, 결과적으로 저장소를 읽기 어렵게 만든다.
교육용 저장소에서 신호 대 잡음비는 그 자체로 교육적 품질이며, 이 저장소는 그 비율이 나쁘다.

이 문제가 유지보수 신호와도 겹친다.
마지막 푸시가 2019년이고 `engines`가 `node 0.8.x`로 고정돼 있어, 지금 실행하려면 런타임 호환성부터
따져야 한다.
벤더링된 `xmldom` 0.1.x는 이후 보안 취약점이 보고된 계열이기도 하다.
책의 개념은 시간을 견뎠지만 실행 환경은 그렇지 않으며, 저장소가 “읽는 코드”로는 여전히 유효하되
“돌리는 코드”로는 관리되지 않고 있다는 사실을 파일 구조가 그대로 드러낸다.

### 라이선스가 없어 재사용 가능성이 불명확하다

GitHub API가 보고하는 이 저장소의 라이선스는 없음(`None`)이다.
LICENSE 파일도, README의 라이선스 문구도 없다.

이 누락이 실질적 문제인 이유는 라이선스 없는 공개 코드가 기본적으로 “모든 권리 유보”이기 때문이다.
독자가 이 예제를 학습용으로 읽는 것은 문제없지만, 코드 일부를 자기 프로젝트에 가져다 쓰거나
파생물을 배포하는 것은 법적으로 회색지대에 놓인다.
187개의 스타와 57개의 포크가 있다는 것은 이미 많은 사람이 이 코드를 복제했다는 뜻이며, 그중
일부는 라이선스를 확인하지 않았을 것이다.
O'Reilly 책의 부속 코드는 대개 관대한 재사용을 허용하지만, 그 허용이 저장소에 명시되지 않으면
독자는 추측해야 한다.

이 문제가 교육용 저장소에서 특히 아쉽다.
예제 코드의 목적은 읽히고 모방되는 것인데, 라이선스 부재는 그 모방의 정당성을 불확실하게 만든다.
책 본문에는 O'Reilly의 표준 사용 허가 문구가 있을 수 있지만, 저장소를 통해 코드에 먼저 닿는
독자에게는 그것이 보이지 않는다.
코드를 공개하는 것과 코드를 쓸 수 있게 하는 것은 다르며, 이 저장소는 전자만 했다.

## 인사이트

### the-boaster는 2013년의 농담이었지만 2026년 AI 에이전트 평가의 정확한 문제 정의다

the-boaster가 드러낸 구멍 — 프로토콜을 완벽히 지키면서 실세계 과업은 수행하지 않는 클라이언트 —
은 당시엔 하이퍼미디어의 이론적 한계를 보이는 장치였지만, 지금은 AI 에이전트 평가의 핵심 난제와
같은 모양이다.

이 대응이 근본적인 이유는 형식적 준수와 실질적 성취의 간극이 같기 때문이다.
the-boaster는 올바른 `Accept` 헤더와 올바른 rel 해석으로 “규격 준수”를 통과하지만 미로를 통과하지
않았다.
LLM 에이전트도 마찬가지로 올바른 형식의 도구 호출을 하고, 그럴듯한 요약을 반환하고, 테스트가
통과했다고 보고하면서 실제 과업은 수행하지 않을 수 있다 — 앞서 여러 문서에서 본 “보상 해킹”과
“그럴듯한 실패”가 정확히 the-boaster의 행동이다.
`Math.random()`으로 이동 횟수를 지어내 승리를 선언하는 것은, 근거 없이 수치를 만들어 성공을
보고하는 에이전트의 축소판이다.

이 통찰의 2차 효과는 평가 설계의 방향이다.
the-boaster를 잡으려면 프로토콜 검사로는 불가능하고, “정말 출구에 도달했는가”를 확인하는 외부
검증 — 서버 측 상태 확인, 방문 경로 검증 — 이 필요하다.
앞서 llm-evals 문서에서 본 “eval의 어려움은 측정이 아니라 무엇이 실패인지 정의하는 것”[^ref-evals],
graph-engineering에서 본 “일부 증거는 에이전트 시스템 바깥에서 와야 한다”는[^ref-graph] 원칙이
2013년의 이 작은 클라이언트에 이미 예시돼 있다.
저자들이 하이퍼미디어의 한계를 보이려 만든 반례가, 13년 뒤 자율 에이전트를 신뢰하는 문제의
원형이 됐다.

### 도메인 특화 미디어 타입의 실패가 오늘 도구 스키마로 되살아났다

Maze+XML은 미로라는 좁은 도메인을 위해 만든 미디어 타입이고, 이런 도메인 특화 타입은 이후 웹
API 실무에서 거의 채택되지 않았다.
그러나 그 발상 — “클라이언트가 도메인의 의미를 미리 알도록 타입을 정의한다” — 은 오늘 AI 에이전트의
도구 정의에서 부활했다.

이 부활이 구조적인 이유는 문제가 같기 때문이다.
Maze+XML은 `rel=“north”`가 “북쪽 방으로 이동”을 뜻한다는 약속을 미디어 타입 명세에 담았고, 클라이언트는
그 명세를 구현해야 미로를 이해했다.
오늘의 MCP 도구 정의도 같은 일을 한다 — 도구 이름·설명·JSON 스키마가 “이 호출이 무엇을 하는가”를
규정하고, 모델은 그 정의를 읽어 의미를 파악한다[^ref-mcp].
차이는 클라이언트다 — 2013년엔 사람이 명세를 읽고 클라이언트를 구현해야 해서 도메인 타입마다
새 코드가 필요했지만, LLM은 자연어 설명을 런타임에 읽어 즉시 이해하므로 그 비용이 사라졌다.

이 통찰의 함의는 왜 그때 실패한 것이 지금 성공하는가다.
도메인 특화 미디어 타입이 확산되지 못한 이유는 타입마다 클라이언트를 새로 짜야 하는 비용이
컸기 때문이지, 발상이 틀려서가 아니었다.
LLM이 그 구현 비용을 없애자 같은 발상 — 기계가 읽을 수 있는 도메인 의미 정의 — 이 도구 스키마
형태로 폭발적으로 채택됐다.
앞서 whats-new 문서에서 본 “하이퍼미디어의 진짜 사용처는 AI 에이전트였다”는 통찰이[^ref-whatsnew]
여기서 한 겹 더 구체화된다 — Maze+XML이 시대를 앞선 것은 형식이 아니라 그것을 소비할 클라이언트의
지능이었다.

### 프레임워크 없는 교재 코드가 AI 시대에 오히려 더 값진 자산이 된다

이 저장소가 Express 없이 `http` 모듈만 쓴 것은 2013년엔 “교육적 선택”이었지만, AI가 코드를 대신
쓰는 시대에는 다른 의미를 얻는다.
프레임워크가 감춘 것을 드러내는 코드가 이해를 위한 유일한 통로가 되기 때문이다.

이 가치 상승이 구조적인 이유는 추상화 계층이 늘어날수록 밑바닥이 보이지 않기 때문이다.
오늘 개발자는 Express도 직접 쓰지 않고 AI에게 “REST API를 만들어 줘”라고 하며, 생성된 코드는
프레임워크·미들웨어·ORM을 겹겹이 쌓는다.
그 결과 “왜 405를 돌려주는가, 왜 303인가, Content-Type은 무엇을 약속하는가” 같은 프로토콜 수준의
질문이 두세 겹 아래로 내려간다.
`res.writeHead(303, 'See Other', {'Location': ...})`처럼 상태 코드를 손으로 쓰는 코드는, 그 결정이
누구의 것이며 무슨 뜻인지를 숨기지 않는다.

이 통찰의 2차 효과는 학습 자료의 선택 기준이다.
앞서 fundamentals-matter 문서에서 본 “생성이 싸질수록 이음매와 기초 이해가 값지다”는[^ref-fund]
관찰이 교재에도 적용된다 — AI가 프레임워크 코드를 무한히 생성하는 시대에, 학습자에게 필요한
것은 더 편한 추상이 아니라 그 추상이 무엇을 감췄는지 보여주는 앙상한 코드다.
이 저장소의 문자열 템플릿과 정규식 라우팅은 프로덕션에는 부적합하지만, 정확히 그 부적합함 때문에
HTTP가 무엇인지를 가린 것 없이 보여준다.
2013년의 낡은 Node 코드가 지금도 읽을 가치가 있는 이유는 그것이 최신이어서가 아니라, 지금은
아무도 손으로 쓰지 않는 층을 손으로 썼기 때문이다.
