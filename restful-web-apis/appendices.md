# 부록: 상태 코드, 헤더, 그리고 Fielding 학위논문

《RESTful Web APIs》(Leonard Richardson, Mike Amundsen, O'Reilly 2013) 부록 A/B/C 정리.

## 개요

세 부록은 본문에서 다 담지 못한 참조 자료를 모은 것이다.
부록 A The Status Codex는 저자의 설명대로 11장의 확장이며, HTTP 명세가 정의하는 41개의 표준 상태 코드와 확장으로 정의된 몇몇 유용한 코드를 깊이 들여다본다.
부록 B The Header Codex는 부록 A와 비슷한 성격으로, HTTP 명세가 정의하는 46개의 요청·응답 헤더와 몇몇 확장을 상세히 개관한다.
부록 C An API Designer's Guide to the Fielding Dissertation은 REST의 토대 문서를 API 설계에 무엇을 뜻하는지의 관점에서 깊이 논의한다.
이 정리는 저자의 공식 장별 설명과 해당 장이 다루는 공개 표준을 근거로 하며, 책 본문을 옮긴 것이 아니다.

숫자에 대해 한 가지 짚어 둔다.
41개와 46개는 저자가 밝힌 수치이며, 2013년 당시 HTTP/1.1의 규범 문서였던 RFC 2616(1999)을 기준으로 한 것이다.
RFC 2616의 상태 코드를 세어 보면 1xx 두 개, 2xx 일곱 개, 3xx 여덟 개, 4xx 열여덟 개, 5xx 여섯 개로 정확히 41개가 된다.
아래 목록은 현행 규범인 RFC 9110 HTTP Semantics(2022년 6월)를 기준으로 정리했으므로 RFC 2616과 항목이 조금 다르다.

## 부록 A: 상태 코드 개관

### 코드 클래스의 뜻

RFC 9110은 상태 코드를 세 자리 정수로 정의하고, 첫 자리가 응답의 클래스를 정한다.
클라이언트는 개별 코드를 몰라도 첫 자리만으로 응답을 다룰 수 있어야 한다 — 이것이 확장 가능성의 근거다.

| 클래스 | 이름          | 뜻                                        |
| ------ | ------------- | ----------------------------------------- |
| 1xx    | Informational | 요청을 받았고 처리가 계속된다             |
| 2xx    | Successful    | 요청을 성공적으로 받고 이해하고 수용했다  |
| 3xx    | Redirection   | 요청을 완료하려면 추가 행동이 필요하다    |
| 4xx    | Client Error  | 요청에 문제가 있어 보인다                 |
| 5xx    | Server Error  | 서버가 유효한 요청을 처리하는 데 실패했다 |

### 1xx Informational

| 코드 | 이름                | 절     | 요지                                         |
| ---- | ------------------- | ------ | -------------------------------------------- |
| 100  | Continue            | 15.2.1 | `Expect: 100-continue`에 대한 계속 진행 신호 |
| 101  | Switching Protocols | 15.2.2 | `Upgrade` 요청을 수용해 프로토콜을 바꾼다    |

| ---- | ----------------------------- | ------ | ----------------------------------------------- |

| 201  | Created                       | 15.3.2 | 새 리소스가 만들어졌다. `Location`으로 가리킨다 |
| 202  | Accepted                      | 15.3.3 | 처리를 수락했으나 아직 완료되지 않았다          |
| 203  | Non-Authoritative Information | 15.3.4 | 중간자가 표현을 변형해 전달했다                 |
| 204  | No Content                    | 15.3.5 | 성공했고 보낼 본문이 없다                       |
| 205  | Reset Content                 | 15.3.6 | 성공했으니 문서 뷰를 초기화하라                 |
| 206  | Partial Content               | 15.3.7 | 범위 요청에 대한 부분 표현이다                  |

### 3xx Redirection

| 코드 | 이름               | 절     | 요지                                 |
| ---- | ------------------ | ------ | ------------------------------------ |
| 300  | Multiple Choices   | 15.4.1 | 표현이 여럿이니 골라라               |
| 301  | Moved Permanently  | 15.4.2 | 영구 이전. 이후 요청은 새 URI로 하라 |
| 302  | Found              | 15.4.3 | 일시 이전                            |
| 303  | See Other          | 15.4.4 | 결과를 다른 URI에서 GET으로 받아라   |
| 304  | Not Modified       | 15.4.5 | 조건부 GET에서 표현이 그대로다       |
| 305  | Use Proxy          | 15.4.6 | 폐기됨(deprecated)                   |
| 306  | (Unused)           | 15.4.7 | 쓰이지 않음                          |
| 307  | Temporary Redirect | 15.4.8 | 일시 이전. 메서드를 바꾸지 말 것     |
| 308  | Permanent Redirect | 15.4.9 | 영구 이전. 메서드를 바꾸지 말 것     |

302와 307, 301과 308의 차이가 API에서 특히 중요하다.
301/302는 역사적으로 클라이언트가 POST를 GET으로 바꿔 재요청하는 관행이 굳었고, 307/308은 메서드와 본문을 그대로 유지하도록 명시한다.

### 확장 상태 코드

저자가 “몇몇 유용한 확장 코드”라 부른 것들은 RFC 9110 바깥에서 정의된 코드다.

| 코드 | 이름                            | 출처     | 요지                                    |
| ---- | ------------------------------- | -------- | --------------------------------------- |
| 428  | Precondition Required           | RFC 6585 | 조건부 요청을 요구해 갱신 유실을 막는다 |
| 429  | Too Many Requests               | RFC 6585 | 요청 빈도 제한에 걸렸다                 |
| 431  | Request Header Fields Too Large | RFC 6585 | 헤더가 너무 크다                        |
| 511  | Network Authentication Required | RFC 6585 | 네트워크 접근을 위한 인증이 필요하다    |
| 451  | Unavailable For Legal Reasons   | RFC 7725 | 법적 사유로 제공할 수 없다              |

이 중 428은 API 설계에 직접 쓸모가 있다.
서버가 무조건부 PUT을 거부하고 `If-Match`를 요구함으로써, 11장에서 본 낙관적 동시성 제어를 프로토콜 차원에서 강제할 수 있다.

오류 본문의 형식도 확장 영역이다.
RFC 9457 Problem Details for HTTP APIs(2023, RFC 7807을 대체)가 `application/problem+json`으로 오류를 서술하는 표준 형식을 제공한다.

## 부록 B: 헤더 개관

### 헤더에서 필드로

부록 B의 대상은 요청 헤더와 응답 헤더다.
RFC 9110은 용어를 바꿔 “헤더 필드”와 “트레일러 필드”를 묶어 필드(field)라 부르고, IANA에 HTTP Field Name Registry라는 별도 레지스트리를 새로 만들었다.

RFC 9110 자신이 그 레지스트리에 등록한 필드는 아래와 같다.
저자가 말한 46개와 정확히 겹치지는 않는데, RFC 2616 이후 일부 필드가 다른 문서로 옮겨 가고(`Cache-Control`, `Expires`, `Age` 등은 RFC 9111로) 일부가 폐기됐기 때문이다(`Content-MD5`).

## 부록 C: Fielding 학위논문 읽기

### 문서의 성격

부록 C는 Roy Fielding의 2000년 UC Irvine 박사 학위논문 Architectural Styles and the Design of Network-based Software Architectures를 API 설계자의 관점에서 읽는다.
REST가 정의된 곳은 이 논문의 5장이며, 그 5.1절이 제약을 하나씩 더해 가며 REST를 유도(derive)한다.

읽는 방식이 중요하다.
5.1절은 널 스타일(null style) — 아무 제약도 없는 상태 — 에서 시작해 제약을 하나씩 추가하고, 매번 그 제약이 어떤 아키텍처 속성을 얻게 하고 어떤 것을 잃게 하는지를 함께 적는다.
즉 REST는 규칙 목록이 아니라 트레이드오프의 누적 기록이다.
API 설계자가 이 논문에서 가져갈 것은 “이렇게 하라”가 아니라 “이 제약을 택하면 무엇을 얻고 무엇을 잃는가”라는 계산법이다.

### 여섯 제약

논문 5.1절이 순서대로 더해 가는 제약은 여섯 개다.

#### 클라이언트-서버 (5.1.2)

관심사를 분리하는 제약이다.
사용자 인터페이스 관심사와 데이터 저장 관심사를 나누어, 양쪽이 독립적으로 진화할 수 있게 한다.

#### 무상태 (5.1.3)

클라이언트-서버 상호작용이 무상태여야 한다는 제약이다.
논문의 규정대로, 클라이언트에서 서버로 가는 각 요청은 그 요청을 이해하는 데 필요한 모든 정보를 담아야 하며 서버에 저장된 어떤 맥락도 활용할 수 없다.
따라서 세션 상태는 전적으로 클라이언트에 유지된다.

이 제약이 유도하는 속성은 가시성, 신뢰성, 확장성이다.
가시성은 모니터링 시스템이 요청 하나만 보고도 요청의 성격 전부를 알 수 있어서 좋아지고, 신뢰성은 부분 실패로부터의 복구가 쉬워져서 좋아지며, 확장성은 서버가 요청 사이에 상태를 저장하지 않아 자원을 빨리 놓아줄 수 있어서 좋아진다.

대가도 논문이 명시한다.
같은 데이터를 요청마다 반복해 보내야 하므로 네트워크 성능이 나빠질 수 있고, 애플리케이션 상태를 클라이언트에 두면 서버가 일관된 애플리케이션 동작을 통제할 힘을 잃는다 — 여러 클라이언트 버전이 의미론을 올바로 구현하느냐에 애플리케이션이 의존하게 되기 때문이다.

#### 캐시 (5.1.4)

네트워크 효율을 높이기 위한 제약이다.
요청에 대한 응답 안의 데이터가 캐시 가능한지 아닌지를 암묵적으로든 명시적으로든 표시해야 한다.
응답이 캐시 가능하면 클라이언트 캐시는 그 응답 데이터를 이후의 동등한 요청에 재사용할 권리를 얻는다.

이 제약은 일부 상호작용을 부분적으로 또는 완전히 없애 효율성·확장성·체감 성능을 높인다.
대가는 신뢰성 저하다 — 캐시 안의 낡은 데이터가 서버에 직접 요청했을 때 얻었을 데이터와 크게 다르면 문제가 된다.

#### 통일 인터페이스 (5.1.5)

논문이 REST를 다른 네트워크 기반 스타일과 구별하는 중심 특징으로 꼽는 제약이다.
컴포넌트 인터페이스에 일반성이라는 소프트웨어 공학 원칙을 적용해 전체 아키텍처를 단순화하고 상호작용의 가시성을 높인다.
구현이 그것이 제공하는 서비스로부터 분리되어 독립적 진화가 장려된다.

대가가 분명하게 적혀 있다.
통일 인터페이스는 효율을 떨어뜨린다 — 정보가 애플리케이션의 필요에 특화된 형태가 아니라 표준화된 형태로 전달되기 때문이다.
REST 인터페이스는 큰 단위의 하이퍼미디어 데이터 전송에 효율적이도록 설계돼 웹의 일반적 경우에 최적화됐으나, 다른 형태의 아키텍처적 상호작용에는 최적이 아니다.

통일 인터페이스를 얻으려면 여러 제약이 더 필요하다.
논문은 REST가 네 개의 인터페이스 제약으로 정의된다고 명시한다.

```text
identification of resources                     리소스의 식별
manipulation of resources through representations  표현을 통한 리소스 조작
self-descriptive messages                       자기 서술적 메시지
hypermedia as the engine of application state   애플리케이션 상태 엔진으로서의 하이퍼미디어
```

이 네 개가 이 책 전체의 뼈대와 정확히 겹친다.
리소스 식별은 URI, 표현을 통한 조작은 이 책이 전작과 달리 무게를 옮긴 지점, 자기 서술적 메시지는 미디어 타입과 프로파일, 그리고 마지막 것이 4장 이후 책 전체에 퍼진 하이퍼미디어다.

#### 계층 시스템 (5.1.6)

인터넷 규모의 요구를 위해 더해지는 제약이다.
각 컴포넌트가 자신이 직접 상호작용하는 바로 그 계층 너머를 볼 수 없도록 동작을 제약해, 아키텍처가 계층적으로 구성될 수 있게 한다.
시스템에 대한 지식을 한 계층으로 한정함으로써 전체 복잡도에 상한을 두고 하부 독립성을 촉진한다.

계층은 레거시 서비스를 감싸거나 새 서비스를 낡은 클라이언트로부터 보호하는 데 쓰이고, 중간자는 여러 네트워크와 프로세서에 걸친 부하 분산으로 확장성을 높인다.
주된 단점은 데이터 처리에 오버헤드와 지연을 더해 체감 성능을 떨어뜨린다는 것이며, 캐시 제약을 지원하는 시스템에서는 중간자의 공유 캐시가 이를 상쇄할 수 있다.

논문은 계층 시스템과 통일 인터페이스가 결합하면 균일한 파이프-필터 스타일과 비슷한 성질이 유도된다고 적는다.
메시지가 자기 서술적이고 그 의미론이 중간자에게 보이기 때문에, 중간자가 메시지 내용을 능동적으로 변형할 수 있다.

#### 코드 온 디맨드 (5.1.7)

마지막으로 더해지는 제약이며, 유일하게 선택적(optional)이다.
REST는 애플릿이나 스크립트 형태의 코드를 내려받아 실행함으로써 클라이언트 기능을 확장하는 것을 허용한다.
미리 구현해 둬야 할 기능의 수가 줄어 클라이언트가 단순해지고, 배포 후 기능을 내려받을 수 있어 확장성이 좋아진다.
그러나 가시성이 떨어지므로 REST 안에서 선택적 제약일 뿐이다.

논문은 “선택적 제약”이라는 말이 형용모순처럼 들릴 수 있음을 스스로 짚고 그 쓸모를 설명한다.
여러 조직 경계를 아우르는 시스템의 아키텍처 설계에서, 선택적 제약은 그것이 시스템의 어떤 영역에서 유효하다고 알려진 경우에만 아키텍처가 그 이점(과 단점)을 얻는다는 뜻이다.
논문의 예시대로, 조직 내 모든 클라이언트가 자바 애플릿을 지원한다고 알려져 있으면 그 조직 안의 서비스는 내려받는 자바 클래스로 기능을 확장하는 이점을 누릴 수 있다.
동시에 그 조직의 방화벽이 외부로부터의 애플릿 전송을 막으면, 웹의 나머지 부분에는 그 클라이언트들이 코드 온 디맨드를 지원하지 않는 것처럼 보인다.

### API 설계자가 가져갈 것

이 부록을 API 설계 관점에서 읽으면 몇 가지가 분명해진다.

제약은 규칙이 아니라 계산이다.
논문은 어느 제약에서도 대가를 감춘 적이 없다.
“REST를 지킨다”가 목적이 되는 순간 이 논문의 방법론 자체를 배반하는 것이며, 물어야 할 것은 언제나 “이 제약으로 무엇을 얻고 무엇을 잃는가”다.

여섯 제약 중 다섯은 필수이고 하나는 선택이다.
코드 온 디맨드가 선택적이라는 사실은, 아키텍처 스타일이 부분적으로만 적용될 수 있고 그 범위를 설계자가 정할 수 있음을 뜻한다.

가장 자주 빠지는 것은 통일 인터페이스의 네 번째 제약이다.
대부분의 “REST API”는 리소스 식별과 표현을 통한 조작까지는 하지만 하이퍼미디어를 애플리케이션 상태 엔진으로 쓰지 않는다.
이 책 전체가 겨냥한 지점이 정확히 여기이며, 부록 C가 마지막에 놓인 이유이기도 하다.

## 핵심 정리

부록 A는 11장의 확장으로, 저자가 41개라 밝힌 HTTP 표준 상태 코드와 몇몇 확장 코드를 훑는다.
41이라는 수는 RFC 2616 기준이며(1xx 2개, 2xx 7개, 3xx 8개, 4xx 18개, 5xx 6개), 현행 RFC 9110은 항목이 조금 다르다.
클래스의 뜻 — 1xx 정보, 2xx 성공, 3xx 리다이렉션, 4xx 클라이언트 오류, 5xx 서버 오류 — 을 알면 개별 코드를 몰라도 응답을 다룰 수 있다는 것이 확장성의 근거다.
API 설계에서 특히 갈라 써야 할 짝은 301/308과 302/307(메서드 보존 여부), 401과 403(인증과 인가), 409와 412(상태 충돌과 전제 실패)다.
확장 코드 중에는 428 Precondition Required와 429 Too Many Requests(RFC 6585), 451(RFC 7725)이 실무에서 쓸모가 크고, 오류 본문은 RFC 9457 Problem Details로 표준화할 수 있다.

부록 B는 저자가 46개라 밝힌 요청·응답 헤더를 다룬다.
RFC 9110은 이들을 필드(field)라 부르고 IANA HTTP Field Name Registry로 정리했으며, 캐싱 관련 필드는 RFC 9111로 분리됐다.
요청 쪽은 협상(`Accept` 계열), 인증(`Authorization`), 조건부(`If-*`), 범위(`Range`)로 묶이고, 응답 쪽은 위치(`Location`), 검증자(`ETag`, `Last-Modified`), 인증 챌린지(`WWW-Authenticate`), 협상 정보(`Vary`)로 묶인다.
표현을 서술하는 `Content-*` 계열은 요청과 응답 양쪽에 나타난다.

부록 C는 Fielding 학위논문 5장을 API 설계의 관점에서 읽는다.
REST는 널 스타일에서 시작해 여섯 제약을 차례로 더해 유도된다 — 클라이언트-서버, 무상태, 캐시, 통일 인터페이스, 계층 시스템, 그리고 선택적인 코드 온 디맨드다.
논문은 매 제약마다 얻는 속성과 치르는 대가를 함께 적으며, 통일 인터페이스가 효율을 떨어뜨린다는 것까지 명시한다.
통일 인터페이스는 다시 네 개의 인터페이스 제약으로 정의된다 — 리소스의 식별, 표현을 통한 리소스 조작, 자기 서술적 메시지, 애플리케이션 상태 엔진으로서의 하이퍼미디어다.
이 마지막 하나가 대부분의 “REST API”에 빠져 있고, 그 빈자리를 겨냥한 것이 이 책 전체다.
