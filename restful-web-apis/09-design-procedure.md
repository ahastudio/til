# 9장 설계 절차: RESTful API를 단계별로 설계하기

《RESTful Web APIs》(Leonard Richardson, Mike Amundsen, O'Reilly 2013) 9장 정리.

## 개요

저자의 공식 설명은 이 장을 한 문장으로 요약한다.
“이 장은 지금까지 책에서 논의한 모든 것을 한데 모아, RESTful API를 설계하는 단계별 안내를 준다.”
즉 9장은 새 개념을 도입하는 장이 아니라, 1~8장에서 쌓은 재료를 실제 설계 순서로 배열하는 장이다.

이 정리는 저자의 공식 장별 설명과 해당 장이 다루는 공개 표준을 근거로 하며, 책 본문을 옮긴 것이 아니다.

이 장은 특히 조심해서 다뤄야 한다.
공식 설명이 한 문장뿐이라 절차의 구체적 단계 목록을 본문에서 확인할 방법이 없기 때문이다.
그래서 아래에서는 확인 가능한 것과 추론인 것을 명확히 갈라 둔다 — 전작 《RESTful Web Services》의 9단계 절차는 이 저장소에 원문 근거로 정리돼 있으므로 그대로 인용하고, 《RESTful Web APIs》가 그 절차를 어떻게 재배치했을지는 저자가 직접 밝힌 두 책의 차이와 5~8장의 공식 설명에서 따라 나오는 범위 안에서만 이야기한다.

## 전작이 남긴 9단계 절차

《RESTful Web Services》(2007)는 문제 공간을 RESTful 리소스로 나누는 범용 절차를 제시했다.
이 저장소에는 [읽기 전용 서비스 설계](../restful-web-services/05-read-only-services.md)와 [베스트 프랙티스](../restful-web-services/08-best-practices.md) 두 문서에 같은 절차가 정리돼 있다.

절차는 아홉 단계다.

1. 데이터 집합(data set)을 파악한다.
2. 데이터 집합을 리소스로 나눈다. 이후 3~9단계는 리소스의 각 종류에 대해 반복한다.
3. URI로 리소스에 이름을 붙인다.
4. 균일 인터페이스의 부분집합을 노출한다.
5. 클라이언트로부터 받을 표현을 설계한다.
6. 클라이언트에 제공할 표현을 설계한다.
7. 하이퍼미디어 링크와 폼을 사용해 이 리소스를 기존 리소스에 통합한다.
8. 전형적인 진행 흐름을 고려한다. 무엇이 일어나야 하는가.
9. 오류 상황을 고려한다. 무엇이 잘못될 수 있는가.

전작은 이 절차가 Joe Gregorio의 “How to create a REST Protocol”과 많은 공통점이 있다고 밝혔고, 각 리소스마다 절차를 반복하기보다 모든 리소스를 한꺼번에 설계해 나가는 방식으로 서술했다.
또한 이 절차는 REST와 ROA의 제약만 고려하며, 사용하는 프레임워크가 추가 제약을 걸 수 있다고 단서를 달았다.

절차의 형태를 보면 무게중심이 어디에 있는지가 드러난다.
아홉 단계 가운데 앞의 넷(데이터 집합, 리소스 분할, URI, 균일 인터페이스)이 리소스를 정의하는 데 쓰이고, 표현은 5~6단계에서, 하이퍼미디어는 7단계에서 뒤늦게 등장한다.
설계자가 먼저 하는 일은 “무엇이 리소스인가”를 정하고 URI를 붙이는 것이다.

## 무게중심이 표현으로 옮겨간다

저자 Leonard Richardson이 두 책의 차이를 직접 정리한 글의 요지는 이 저장소의 [whats-new.md](whats-new.md)에 정리돼 있고, 9장을 이해하는 열쇠도 거기 있다.

저자에 따르면 《Services》는 HTTP의 리소스 개념에 무겁게 초점을 맞춰 사실상 서버 측을 강조했다.
반면 《APIs》는 표현 — 클라이언트와 서버가 주고받는 문서 — 에 초점을 맞추며, REST가 사는 곳이 바로 그 표현이라고 본다.
저자는 옛 책의 도입 이야기는 남았지만, 클라이언트와 서버가 표현을 주고받으며 서로의 상태를 조작하는 상호작용에 늘 초점을 두도록 다시 썼다고 밝혔다.

이 초점 이동이 설계 절차에 갖는 함의는 분명하다.
전작 절차에서 5~7단계에 놓였던 표현과 하이퍼미디어가 더 이상 리소스 정의 뒤에 오는 후속 작업이 아니게 된다.
“클라이언트가 이 문서를 받아 무엇을 할 수 있는가”가 먼저 오고, 리소스와 URI는 그 흐름을 뒷받침하는 구현 세부로 내려간다.

여기서 한 가지는 분명히 해 두어야 한다.
《APIs》 9장이 전작의 아홉 단계를 정확히 어떤 순서로 재배열했는지는 본문 없이 단정할 수 없다.
확인 가능한 것은 저자가 밝힌 초점 이동의 방향과, 5~8장이 제공하는 설계 재료가 무엇인지까지다.

## 9장이 모아 오는 재료들

공식 장별 설명을 보면, 9장이 “한데 모으는” 앞 장들의 결과물이 무엇인지가 드러난다.
설계 절차가 각 단계에서 꺼내 쓸 수 있는 도구가 이미 갖춰져 있는 셈이다.

### 1~4장이 준 것: 개념 틀

1장은 이미 익숙한 RESTful 시스템인 웹사이트를 예로 기본 용어를 설명하고, 2장은 같은 기능을 프로그래밍 가능한 API로 옮긴다.
3장은 리소스가 HTTP의 근본 개념이고 표현이 REST의 근본 개념임을 밝히며 둘의 관계를 정리한다.
4장은 하이퍼미디어를 “표현들을 하나의 일관된 API로 묶는 빠진 재료”로 규정한다.

설계 절차의 관점에서 이 네 장은 “무엇을 설계 대상으로 삼을 것인가”를 정한다.
전작이 리소스를 대상으로 삼았다면, 여기서는 표현과 그 사이의 전이가 대상이다.

### 5~7장이 준 것: 형식 선택의 세 갈래

5~7장은 표현 형식을 정하는 세 가지 전략을 순서대로 제시한다.
9장 절차에서 “어떤 미디어 타입을 쓸 것인가”를 결정할 때 고르는 선택지가 바로 이 셋이다.

| 전략           | 장 | 성격                                                              |
| -------------- | -- | ----------------------------------------------------------------- |
| 도메인 특화 설계 | 5장 | 자기 문제에 정확히 맞는 새 표준을 만든다. 예: Maze+XML              |
| 컬렉션 패턴     | 6장 | 반복해서 나타나는 컬렉션 구조를 쓴다. 예: Collection+JSON, AtomPub |
| 순수 하이퍼미디어 | 7장 | 범용 형식으로 원하는 표현을 전달한다. 예: HTML, HAL, Siren        |

이 순서 자체가 저자의 판단을 담고 있다.
5장은 새 표준을 설계하는 전략을 “뻔한(obvious) 전략”이라 부르고, 7장은 컬렉션 패턴이 안 맞을 때 범용 형식으로 가라고 안내한다.
저자가 다른 글에서 “REST API의 약 80%가 컬렉션 패턴에 포섭되지만 REST는 그보다 크다”고 한 것을 함께 놓으면, 실무 절차에서의 기본값은 컬렉션 패턴을 먼저 검토하고 맞지 않을 때 순수 하이퍼미디어로 가는 쪽임을 알 수 있다.

### 8장이 준 것: 의미를 붙이는 층

[8장](08-profiles.md)의 프로파일은 형식 선택 뒤에 남는 문제를 처리한다.
범용 형식을 골랐다면 그 형식은 여러 API가 공유하므로, “이 API에서 이 필드와 이 링크가 실세계에서 무엇을 뜻하는가”를 따로 말해야 한다.
ALPS 같은 프로파일 형식이 그 자리를 채우고, `profile` 링크 관계(RFC 6906)가 표현과 프로파일을 잇는다.

설계 절차에 이 단계가 들어간다는 것은, 전작에는 아예 없던 단계가 하나 늘었다는 뜻이다.
전작의 아홉 단계 어디에도 “도메인 의미를 기계가 읽을 수 있는 문서로 따로 기술한다”는 단계는 없다.

## 절차의 각 단계가 어떻게 달라지는가

전작의 아홉 단계를 표현 중심 관점에서 다시 읽으면, 각 단계가 그대로 남되 의미가 바뀐다.
아래는 저자가 밝힌 초점 이동에서 따라 나오는 해석이며, 9장 본문의 단계 목록을 옮긴 것이 아니다.

데이터 집합 파악은 그대로 첫 단계로 남는다.
어떤 접근을 택하든 무엇을 다루는 서비스인지부터 정해야 한다.

리소스 분할과 URI 명명은 지위가 내려간다.
하이퍼미디어를 제대로 쓰면 클라이언트는 URI 구조를 알 필요가 없고 서버가 준 링크만 따라가므로, URI 설계는 클라이언트와의 계약이 아니라 서버 내부의 편의가 된다.
이 저장소의 [example-code.md](example-code.md)에 정리한 Maze+XML 클라이언트들이 그 증거다 — `the-mapmaker`는 미로가 5×5든 100개 방이든 코드를 고치지 않고 링크만 따라가며 전체 지도를 그린다.

균일 인터페이스 노출은 표현이 담는 하이퍼미디어 컨트롤의 문제로 바뀐다.
전작에서는 “이 리소스가 GET, PUT, DELETE 중 무엇에 응답하는가”를 정하는 단계였다면, 표현 중심 관점에서는 “이 표현이 어떤 링크와 폼을 싣는가”가 같은 일을 한다.
ALPS가 상태 전이를 `safe`, `idempotent`, `unsafe`로 추상화한 것도 같은 발상이다 — 메서드 이름이 아니라 전이의 성질이 설계 단위다.

표현 설계는 절차의 중심으로 올라온다.
그리고 이 단계는 이제 “JSON 스키마를 정한다”가 아니라 “어떤 하이퍼미디어 형식을 쓸 것인가”라는 질문이 된다.
저자가 전작의 가장 큰 결함으로 “유효한 JSON이면서 동시에 하이퍼미디어인 문서를 어떻게 설계하는가”를 다루지 않은 점을 꼽은 것이 정확히 이 지점이다.

하이퍼미디어 통합은 별도 단계라기보다 표현 설계에 이미 포함된다.
링크와 폼이 표현의 일부이지 표현을 다 만든 뒤에 붙이는 장식이 아니기 때문이다.

정상 흐름과 오류 조건 고려는 그대로 남는다.
다만 하이퍼미디어 API에서 정상 흐름은 “클라이언트가 어떤 링크를 따라 어떤 순서로 이동하는가”라는 상태 기계의 문제가 되고, 오류 조건은 오류 표현 역시 하이퍼미디어여야 한다는 요구를 낳는다.

여기에 프로파일 작성이라는 새 단계가 붙는다.
범용 형식을 골랐다면 도메인 의미를 어딘가에 기술해야 하고, 그 자리가 프로파일이다.

## 이 장의 위치

9장은 책의 3부(실무 주제)를 여는 장이며, 뒤로 11장의 HTTP 실무, 12장의 Linked Data, 13장의 CoAP이 이어진다.
즉 9장은 “이론을 다 봤으니 이제 만들어 보자”의 전환점이다.

절차를 제시하는 책이 흔히 빠지는 함정을 이 장이 어떻게 피했는지는 본문 없이 알 수 없다.
다만 저자가 전작에서 이미 “이 절차는 REST와 ROA의 제약만 고려하며 프레임워크가 추가 제약을 걸 수 있다”고 단서를 달았고, “각 리소스마다 절차를 반복하는 대신 모든 리소스를 한꺼번에 설계해 나간다”고 실무적 조정을 밝힌 전례가 있다.
절차를 기계적 체크리스트가 아니라 판단이 개입하는 지침으로 다뤄 온 저자의 태도는 두 책에 걸쳐 일관돼 보인다.

## 핵심 정리

9장은 새 개념을 도입하지 않고, 1~8장의 재료를 RESTful API 설계의 단계별 안내로 재배열하는 장이다.
공식 설명이 한 문장뿐이므로, 절차의 구체적 단계 목록은 본문 없이 단정할 수 없다.

전작 《RESTful Web Services》는 아홉 단계 절차를 제시했다.
데이터 집합 파악, 리소스 분할, URI 명명, 균일 인터페이스 노출, 수신 표현 설계, 송신 표현 설계, 하이퍼미디어 통합, 정상 흐름, 오류 조건이다.
이 절차에서는 앞의 네 단계가 리소스 정의에 쓰이고 표현과 하이퍼미디어는 뒤에 온다.

저자가 밝힌 두 책의 차이는 무게중심이 리소스에서 표현으로 옮겨갔다는 것이다.
그 결과 URI 설계는 클라이언트와의 계약이 아니라 서버 내부의 편의로 내려가고, 표현 형식 선택이 절차의 중심으로 올라온다.

9장이 모아 오는 재료는 세 층이다.
1~4장의 개념 틀, 5~7장의 형식 선택 세 갈래(도메인 특화, 컬렉션 패턴, 순수 하이퍼미디어), 8장의 프로파일이다.
프로파일 작성은 전작의 아홉 단계에 없던 새 단계다.
