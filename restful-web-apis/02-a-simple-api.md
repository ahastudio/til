# 2장 단순한 API: 웹사이트의 교훈을 프로그래밍 가능한 API로

《RESTful Web APIs》(Leonard Richardson, Mike Amundsen, O'Reilly 2013) 2장 정리.

## 개요

저자의 공식 설명에 따르면 2장은 “1장에서 다룬 웹사이트와 동일한 기능을 하는 프로그래밍 가능한 API로 웹의 교훈을 옮긴다”.
이 정리는 저자의 공식 장별 설명과 해당 장이 다루는 공개 표준을 근거로 하며, 책 본문을 옮긴 것이 아니다.

이 장의 구성이 영리한 이유는 변수를 하나만 바꾸기 때문이다.
기능은 1장의 웹사이트와 똑같이 두고, 소비자만 사람에서 프로그램으로 바꾼다.
그러면 무엇이 그대로 넘어가고 무엇이 깨지는지가 선명하게 드러난다 — URL, 메서드, 상태 코드는 그대로 넘어가지만, 링크와 폼은 넘어가지 못한다.
그 깨진 자리에서 이 책 전체의 문제의식이 나온다.

## 그대로 옮겨지는 것

1장에서 정리한 용어 중 상당수는 API로 옮겨도 아무것도 바뀌지 않는다.

리소스와 URL은 그대로다.
`/messages`가 메시지 목록이고 `/messages/21818525`가 그중 하나라는 구조는, 그것을 브라우저가 읽든 스크립트가 읽든 같다.

HTTP 메서드도 그대로다.
목록을 읽을 때 GET, 새 항목을 만들 때 POST, 기존 항목을 바꿀 때 PUT, 지울 때 DELETE를 쓴다.
안전성과 멱등성의 약속도 그대로 유효하며, 오히려 프로그램 클라이언트에게 더 중요하다 — 사람은 재시도할지 스스로 판단하지만, 프로그램은 멱등성 보장에 기대어 자동으로 재시도한다.

상태 코드도 그대로다.
사람에게 404가 “페이지 없음” 안내문으로 보였다면, 프로그램에게는 분기 조건이 된다.
지원하지 않는 메서드에 405 Method Not Allowed를 돌려주는 규칙도 동일하다.

이 저장소의 예제 코드 분석에서 본 You Type It, We Post It 서버가 이 대응 관계를 한 파일 안에서 보여 준다.[^ref-example]
같은 프로세스가 브라우저용 HTML 경로와 프로그램용 API 경로를 나란히 제공하고, 두 경로의 라우팅과 상태 코드 처리가 거의 대칭을 이룬다.

## 옮겨지지 않는 것: JSON에는 링크도 폼도 없다

문제는 표현을 바꾸는 순간 시작된다.
API의 표현 형식으로 대부분 JSON을 고르는데, JSON은 하이퍼미디어 형식이 아니다.

같은 리소스를 HTML로 내면 이렇게 된다.

```html
<ul>
  <li><a href="/messages/21818525">첫 번째 메시지</a></li>
  <li><a href="/messages/3689823">두 번째 메시지</a></li>
</ul>
<form action="/messages" method="POST">
  <input type="text" name="text">
  <input type="submit" value="보내기">
</form>
```

같은 것을 평범한 JSON으로 내면 이렇게 된다.

```json
{
  "messages": [
    {"id": "21818525", "text": "첫 번째 메시지"},
    {"id": "3689823", "text": "두 번째 메시지"}
  ]
}
```

두 문서가 담은 데이터는 같지만, 담지 못한 것이 다르다.
HTML 쪽에는 “이 항목을 보려면 이 URL을 GET하라”와 “새 메시지를 만들려면 이 URL로 `text`를 POST하라”가 문서 안에 들어 있다.
JSON 쪽에는 `id`라는 문자열만 있을 뿐, 그것으로 URL을 어떻게 만드는지, 새 항목을 어디로 어떻게 보내는지가 어디에도 없다.

이 차이의 뿌리는 미디어 타입 명세다.
`text/html`은 `<a href>`가 링크이고 `<form>`이 쓰기 양식이라는 것을 규정한다.
`application/json`은 객체와 배열과 문자열의 문법만 규정하고, 어떤 키가 링크인지는 아무 말도 하지 않는다.
`{“href”: “/messages/21818525”}`를 링크로 읽어야 한다는 것은 JSON 명세 어디에도 없고, 그 API의 관행일 뿐이다.

## 빠진 정보는 사람이 읽는 문서로 새어 나간다

링크와 폼이 표현에서 사라지면 그 정보가 없어지는 것이 아니라 자리를 옮긴다.
개발자 문서 사이트로 옮겨 간다.

```text
POST /messages
Content-Type: application/x-www-form-urlencoded

파라미터:
  text (필수) - 메시지 본문, 최대 140자

응답: 201 Created, Location 헤더에 새 메시지 URL
```

이 문서는 사람이 읽으라고 쓴 것이다.
사람이 읽고, 이해하고, 클라이언트 코드에 URL 패턴과 파라미터 이름을 손으로 넣는다.
그 결과 API에 대한 지식이 두 곳에 나뉘어 존재하게 된다 — 서버의 구현과, 클라이언트 개발자의 머리를 거쳐 클라이언트 코드에 고정된 사본이다.

이 이중화가 비용을 만드는 지점이 변경이다.
웹사이트는 서버가 URL 체계를 바꿔도 링크만 새로 내보내면 브라우저가 따라간다.
API는 서버가 URL 체계를 바꾸면 모든 클라이언트가 깨지고, 각 클라이언트의 개발자가 문서를 다시 읽고 코드를 고쳐야 한다.
그래서 API는 버전을 나누고, 낡은 버전을 몇 년씩 유지하고, 폐기 일정을 공지하는 관례가 생긴다.

저자들이 이 책을 쓴 동기가 여기에 있다.
1장에서 본 웹의 유연성은 하이퍼미디어에서 나왔는데, API 세계는 표현 형식을 JSON으로 바꾸면서 그 유연성만 빠뜨린 채 나머지를 가져왔다.
README에 정리한 대로 이 책의 문제의식은 “아키텍처의 이점을 대부분 담지 못한 거의 RESTful한 API의 폭증”이며, 그 결핍의 구체적인 이름이 하이퍼미디어의 부재다.

## 해법의 방향: 기계가 읽을 수 있는 표현

그래서 필요한 것은 문서를 더 잘 쓰는 일이 아니라, 문서에만 있던 정보를 표현 안으로 되돌리는 일이다.
사람이 읽는 산문 대신 기계가 파싱할 수 있는 구조로 옮기면, 클라이언트는 링크와 양식을 실행 시점에 발견하게 된다.

이 방향을 실제 형식으로 구현한 것이 Collection+JSON, HAL, Siren, JSON-LD 같은 하이퍼미디어 JSON 형식이며, 책은 5장부터 8장까지 이것들을 다룬다.
2장은 그 형식들을 자세히 설명하기 전에, 왜 그런 것이 필요한지를 가장 단순한 예제로 확정한다.

## Collection+JSON으로 본 실제 해법

이 저장소의 예제 코드 분석에 나오는 You Type It, We Post It 서버가 이 해법의 최소 사례다.[^ref-example]
1장의 웹사이트와 2장의 API가 같은 프로세스에서 같은 데이터를 서비스하되, API 쪽 표현은 평범한 JSON이 아니라 Collection+JSON이다.

```json
{
    "collection" :
    {
        "version" : "1.0",
        "href" : "{@host}/api/",
        "items" : {@list},
        "template" : {
            "data" : [
                {"prompt" : "Text of message", "name" : "text", "value" : ""}
            ]
        }
    }
}
```

여기서 `template`가 HTML의 `<form>`에 대응한다.
서버는 데이터만 주지 않고 “새 메시지를 만들려면 `text`라는 이름의 값을 채워 보내라”는 쓰기 양식을 표현에 함께 실어 보낸다.
`prompt`는 사람이 읽을 라벨이고 `name`은 기계가 쓸 키이므로, 하나의 구조가 사람용 UI 생성과 기계용 요청 조립을 동시에 감당한다.

클라이언트는 이 템플릿을 채워 그대로 되돌려 보낸다.

```json
{
  "template" : {
    "data" : [
      {"name" : "text", "value" : "testing"}
    ]
  }
}
```

POST로 보내면 생성이고 PUT으로 보내면 수정이며, 요청 본문의 모양은 같다.
클라이언트 코드에 URL 패턴이나 파라미터 이름을 고정할 필요가 사라지고, 대신 “표현에서 `template`를 찾아 채운다”는 규칙 하나만 남는다.

이 구조가 2장의 논지를 완성한다.
JSON을 버릴 필요는 없고, JSON 위에 링크와 폼의 의미를 규정하는 미디어 타입을 얹으면 된다.
서버는 응답의 `Content-Type`으로 그 약속을 알리고, 클라이언트는 `Accept`로 그 약속을 요구한다 — 이것이 3장에서 다룰 콘텐츠 협상과 이어진다.

## 핵심 정리

2장이 확정하는 것은 다음과 같다.

- URL, HTTP 메서드, 상태 코드, 안전성과 멱등성은 웹사이트에서 API로 그대로 옮겨진다.
- 옮겨지지 않는 것은 링크와 폼이며, 이유는 `application/json`이 문법만 정의하고 하이퍼미디어 제어의 의미를 정의하지 않기 때문이다.
- 빠진 정보는 사라지지 않고 사람이 읽는 개발자 문서로 자리를 옮기며, 거기서 클라이언트 코드로 손으로 옮겨진다.
- 그 결과 API 지식이 서버와 클라이언트 양쪽에 이중으로 존재하게 되고, 서버가 바뀔 때마다 모든 클라이언트가 깨지는 구조가 만들어진다.
- 해법의 방향은 문서를 잘 쓰는 것이 아니라, 링크와 양식을 기계가 읽을 수 있는 형태로 표현 안에 되돌리는 것이다.
- Collection+JSON의 `template`가 그 최소 구현이며, HTML의 `<form>`이 하던 일을 JSON 위에서 그대로 한다.

이 장의 결론은 문제 제기의 형태로 남는다 — 웹은 하이퍼미디어로 유연성을 얻었는데 API는 왜 그것을 버렸는가.
책의 나머지가 이 질문에 대한 답이다.
