# 4장 하이퍼미디어: 표현들을 하나의 API로 묶는 빠진 재료

《RESTful Web APIs》(Leonard Richardson, Mike Amundsen, O'Reilly 2013) 4장 정리.

## 개요

저자는 이 장을 이렇게 소개한다 — 하이퍼미디어는 표현들을 하나의 일관된 API로 묶어 주는 빠진 재료이며,
이 장은 이미 우리에게 익숙한 하이퍼미디어 데이터 형식인 HTML을 주로 써서 하이퍼미디어가 무엇을 할 수 있는지
보인다.

이 정리는 저자의 공식 장별 설명과 해당 장이 다루는 공개 표준을 근거로 하며, 책 본문을 옮긴 것이 아니다.

3장까지가 리소스와 표현, 즉 “무엇을 주고받는가”를 다뤘다면 4장은 “그다음에 무엇을 할 수 있는가”를 다룬다.
표현이 아무리 잘 설계돼도 그것들이 서로 떨어져 있으면 API가 아니라 문서 더미에 지나지 않는다.
그 문서들을 하나의 애플리케이션으로 잇는 것이 하이퍼미디어이며, 이 장의 전략은 새로운 것을 발명해 설명하는
대신 이미 30년 가까이 그 일을 해 온 HTML을 해부하는 것이다.

## 하이퍼미디어의 정의: 서버가 다음 요청을 알려 준다

하이퍼미디어를 가장 짧게 정의하면 “서버가 클라이언트에게 지금 할 수 있는 다음 HTTP 요청이 무엇인지
표현 안에서 알려 주는 방법”이다.
이 저장소의 색인 문서도 4장을 그렇게 요약한다 — 하이퍼미디어는 서버가 클라이언트에게 다음에 할 수 있는
HTTP 요청을 알려 주는 최선의 방법이다.[^ref-readme]

여기서 핵심은 그 정보가 어디에 있느냐다.
문서 바깥에 있으면 클라이언트 개발자가 사람이 읽는 문서를 보고 URL 조립 규칙을 코드에 고정해야 하고,
그 순간 서버는 URL 구조를 바꿀 수 없게 된다.
문서 안에 있으면 클라이언트는 실행 시점에 서버가 준 것만 따라가면 되고, 서버는 URL을 바꿔도 클라이언트를
깨뜨리지 않는다.
하이퍼미디어가 결합도를 낮춘다는 말의 실체가 이것이다 — 하이퍼미디어는 URL을 클라이언트의 코드에서
서버의 표현으로 옮긴다.

이 장이 HTML을 교재로 삼는 이유도 여기 있다.
브라우저는 세상에서 가장 널리 쓰이는 하이퍼미디어 클라이언트인데, 그 브라우저 안에는 어떤 사이트의 URL도
하드코딩돼 있지 않다.
브라우저가 아는 것은 오직 HTML이라는 미디어 타입의 규칙뿐이며, 나머지는 전부 서버가 보내 준 문서에서
읽는다.
API가 이 성질을 갖지 못할 이유는 없다는 것이 이 장의 논지다.

## HTML의 두 장치: 링크와 폼

HTML은 하이퍼미디어 제어를 두 종류로 나눈다 — 상태를 바꾸지 않는 이동과 상태를 바꾸는 제출이다.

링크는 안전한 이동을 나타낸다.

```html
<a href="/messages/42" rel="item">42번 메시지 보기</a>
```

이 요소가 클라이언트에게 알려 주는 것은 세 가지다 — 어떤 URL로(`href`), 어떤 메서드로(GET, 명시되지
않지만 HTML의 규칙상 고정), 그리고 그 요청이 현재 문서와 어떤 관계인지(`rel`)다.
메서드가 GET으로 고정돼 있다는 사실이 중요하다.
클라이언트는 이 링크를 따라가도 아무것도 망가지지 않는다는 것을 미디어 타입의 규칙만으로 알 수 있고,
그래서 검색 엔진 크롤러가 남의 사이트 링크를 마음대로 따라다녀도 문제가 생기지 않는다.

폼은 그보다 훨씬 많은 것을 알려 준다.

```html
<form action="/messages" method="post">
  <input type="text" name="text" value="">
  <input type="submit" value="Post">
</form>
```

폼은 URL과 메서드에 더해 “요청 본문에 무엇을 어떤 이름으로 담아야 하는가”까지 표현 안에 담는다.
링크가 “여기로 갈 수 있다”라면 폼은 “여기에 이런 모양의 데이터를 보낼 수 있다”이며, 이 차이가
하이퍼미디어를 읽기 전용 탐색에서 쓰기 가능한 애플리케이션으로 끌어올린다.
`method=“get”`인 폼은 입력값을 질의 문자열로 붙인 URL을 만들어 내므로, 사실상 클라이언트가 실행 시점에
URL을 조립하는 안전한 방법이 된다 — 검색 상자가 그 예다.

HTML 폼의 한계도 정직하게 봐야 한다.
HTML 명세가 폼에 허용하는 메서드는 GET과 POST뿐이며, PUT과 DELETE는 폼으로 표현할 수 없다.
그래서 웹 프레임워크들이 숨은 `_method` 필드 같은 우회를 만들어 냈고, 이 결핍은 이후 장에서 다루는
전용 하이퍼미디어 형식들이 자기 나름의 쓰기 제어(예컨대 Collection+JSON의 `template`)를 새로 정의하는
동기가 된다.[^ref-example]

## 링크 관계: 전이에 이름을 붙이는 일

`href`는 어디로 가는지 알려 주지만 왜 가는지는 알려 주지 않는다.
그 자리를 채우는 것이 링크 관계, 즉 `rel` 속성이다.

`rel`은 링크의 목적지가 현재 문서와 어떤 관계인지를 짧은 문자열로 표시한다.
`<link rel=“stylesheet”>`가 “이건 이 문서의 스타일시트다”를 뜻하고 `<a rel=“next”>`가 “이건 이 시리즈의
다음 문서다”를 뜻하는 식이다.
클라이언트 코드가 실제로 하는 일은 대부분 이 문자열을 찾는 것으로 환원된다 — 이 저장소의 예제 코드
분석에서 본 지도 그리기 봇도 결국 응답에서 `<link>` 노드를 긁어 `rel`과 `href`만 뽑아 쓴다.[^ref-example]

이 문자열이 아무나 마음대로 지어도 되는 것이었다면 상호운용성은 없었을 것이다.
그래서 IANA가 링크 관계 레지스트리를 운영한다.
실제로 레지스트리를 확인해 보면 API 설계에 그대로 쓸 수 있는 관계들이 이미 등록돼 있다.

```text
self         Conveys an identifier for the link's context.            (RFC 4287)
collection   The target IRI points to a resource which represents
             the collection resource for the context IRI.             (RFC 6573)
item         The target IRI points to a resource that is a member
             of the collection represented by the context IRI.        (RFC 6573)
next / prev  시리즈의 다음/이전 문서                                   (HTML)
first / last 시리즈의 처음/마지막 문서                                 (RFC 8288)
edit         Refers to a resource that can be used to edit
             the link's context.                                      (RFC 5023)
create-form  The target IRI points to a resource where a submission
             form can be obtained.                                    (RFC 6861)
search       링크 문맥을 검색하는 데 쓸 수 있는 리소스                  (OpenSearch)
describedby  링크 문맥에 대한 정보를 제공하는 리소스                    (POWDER)
profile      표현이 특정 프로파일을 따름을 표시                        (RFC 6906)
```

이 목록에서 읽어야 할 것은 개별 항목이 아니라 그 존재 방식이다.
`collection`과 `item`은 특정 회사의 API가 아니라 RFC 6573이라는 표준이 정의했고, 그 덕에 서로 모르는
서버와 클라이언트가 같은 뜻으로 그 단어를 쓴다.
레지스트리에 없는 관계가 필요하면 짧은 이름 대신 URL을 관계 이름으로 쓰는 확장 방식이 준비돼 있다 —
이 규칙과 `Link` 헤더의 문법은 현재 RFC 8288이 정의하며, 책이 쓰이던 2013년에는 그 전신인 RFC 5988이
현행이었다.

링크 관계는 헤더로도 보낼 수 있다는 점이 API 설계에서 특히 유용하다.

```http
HTTP/1.1 200 OK
Content-Type: application/json
Link: <https://example.com/messages?page=2>; rel="next"
Link: <https://example.com/profiles/message>; rel="profile"
```

본문 형식이 하이퍼미디어를 지원하지 않는 순수 JSON이어도, `Link` 헤더는 전이를 실어 나를 수 있다.
JSON에 하이퍼미디어가 없다는 문제를 부분적으로 우회하는 이 방법은 이 책이 전작과 갈라지는 지점 중
하나와 맞닿아 있다.[^ref-whatsnew]

## HATEOAS의 실제 뜻

HATEOAS(Hypermedia as the Engine of Application State)는 REST 논의에서 가장 자주 인용되면서 가장 자주
오해되는 약어다.
풀어 쓰면 “애플리케이션 상태의 엔진은 하이퍼미디어다”인데, 여기서 결정적인 단어는 “엔진”이다.

이 말이 뜻하는 것은 클라이언트가 지금 어떤 상태에 있고 다음에 어떤 상태로 갈 수 있는지를 결정하는 주체가
클라이언트 코드가 아니라 서버가 보낸 문서라는 것이다.
클라이언트가 자기 안에 상태 기계를 갖고 “로그인 다음엔 장바구니, 장바구니 다음엔 결제”라는 순서를 알고
있다면 그것은 HATEOAS가 아니다.
서버가 매 응답마다 지금 가능한 전이를 링크와 폼으로 실어 보내고 클라이언트가 그중에서 고르는 것이 HATEOAS다.

브라우저를 쓰는 사람의 경험이 정확히 이렇다.
장바구니 페이지에 결제 버튼이 없으면 사람은 결제할 수 없고, 있으면 누른다.
사람은 그 사이트의 상태 전이도를 외운 적이 없으며, 매 순간 화면에 있는 것 중에서 고를 뿐이다.
HATEOAS는 그 경험을 프로그램 클라이언트에게도 주자는 요구다.

그래서 HATEOAS의 실제 판정 기준은 “응답에 링크가 있는가”가 아니라 “클라이언트가 URL을 몰라도 되는가”다.
응답에 링크를 잔뜩 담아 놓고도 클라이언트가 그 링크를 무시한 채 자기가 조립한 URL로 요청한다면 그 API는
하이퍼미디어를 쓰는 것이 아니라 하이퍼미디어를 장식으로 붙인 것이다.
저자들이 “거의 RESTful한” API가 폭증했다고 지적하는 대목이 겨냥하는 것이 이 상태다.[^ref-readme]

## 하이퍼미디어가 풀지 못하는 문제

이 장의 가장 중요한 부분은 하이퍼미디어가 할 수 있는 일이 아니라 할 수 없는 일이며, 그것이 8장으로
이어지는 다리가 된다.

저자들이 정식화한 두 질문으로 나누면 경계가 선명해진다 — 첫째, 클라이언트가 다음에 어떤 요청을 할 수
있는가.
둘째, 그 요청이 실세계 관점에서 무엇을 뜻하는가.[^ref-whatsnew]
하이퍼미디어는 첫 번째 질문만 푼다.

폼 하나를 놓고 보면 분명하다.
서버가 `POST /messages`로 `text` 필드를 보내라는 폼을 주면 클라이언트는 그 요청을 정확히 만들어 낼 수
있다.
그러나 그 요청이 “메시지를 게시한다”는 뜻인지 “주문을 취소한다”는 뜻인지는 폼 어디에도 없다.
사람은 버튼에 적힌 “Post”라는 글자를 읽고 알지만, 그 글자는 사람이 읽는 자연어일 뿐 기계가 해석하도록
정의된 것이 아니다.

이 간극이 이론적 흠집이 아니라 실제 결함이라는 것을 이 책의 예제 코드가 스스로 증명한다.
저자들이 만든 the-boaster 클라이언트는 올바른 `Accept` 헤더를 보내고 링크 관계를 정확히 해석하며 서버가
준 하이퍼미디어를 완벽하게 따라가면서도, 미로를 실제로 통과하지 않고 통과했다고 주장한다.[^ref-example]
프로토콜 수준에서 이 클라이언트는 아무 잘못이 없다 — 하이퍼미디어가 강제하는 것은 전이의 가능성이지
전이의 의미가 아니기 때문이다.

두 번째 질문에 답하려면 별도의 장치가 필요하며, 그것이 8장의 프로파일이다.
`rel=“profile”`이 IANA 레지스트리에 RFC 6906으로 등록돼 있다는 사실 자체가 이 다리의 존재를 보여 준다 —
하이퍼미디어의 어휘 안에, 하이퍼미디어가 못 하는 일을 다른 문서에 위임하는 관계가 이미 마련돼 있다.
저자가 이 책을 위해 ALPS를 직접 개발한 것도 이 위임을 받을 문서 형식이 아직 없었기 때문이다.[^ref-whatsnew]

## 핵심 정리

하이퍼미디어는 서버가 클라이언트에게 다음에 가능한 요청을 표현 안에서 알려 주는 장치이며, 그 효과는
URL 지식을 클라이언트 코드에서 서버의 문서로 옮기는 것이다.

HTML은 그 장치를 두 가지로 나눠 갖는다 — 링크(`<a href>`)는 안전한 GET 이동을, 폼(`<form>`)은 메서드와
요청 본문의 모양까지 포함한 제출을 알려 준다.
HTML 폼이 GET과 POST만 지원한다는 제약은 이후 장의 전용 하이퍼미디어 형식들이 자기 쓰기 제어를 새로
정의하게 만든 원인이다.

링크 관계(`rel`)는 전이에 이름을 붙여 의미의 일부를 공급하고, IANA 링크 관계 레지스트리가 그 이름들을
공용 어휘로 관리한다.
`self`, `collection`, `item`, `next`, `edit`, `create-form`, `profile` 같은 관계는 이미 표준이 정의해
두었으므로 API 설계자가 새로 지어낼 이유가 없다.

HATEOAS는 응답에 링크가 있느냐가 아니라 클라이언트가 URL을 모르고도 동작하느냐로 판정된다.
클라이언트가 자기 안에 상태 전이 순서를 갖고 있다면 링크가 아무리 많아도 하이퍼미디어 API가 아니다.

하이퍼미디어는 “다음에 무엇을 할 수 있는가”만 답하고 “그것이 실세계에서 무슨 뜻인가”는 답하지 않는다.
이 한계는 저자들 스스로 the-boaster라는 반례로 코드에 남겨 두었으며, 8장의 프로파일이 그 빈자리를 겨냥한다.
