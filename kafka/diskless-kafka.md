# Diskless Kafka: 브로커가 로그를 내려놓으면 합의는 메타데이터로 옮겨 간다

원문: [Diskless Kafka: What Happens When Brokers Stop Owning the Data?](https://softwaremill.com/diskless-kafka-object-storage-kip-1150-and-kafkas-future/)

GN 토론: <https://news.hada.io/topic?id=34454>

## 요약

SoftwareMill의 Michał Matłoka가 2026년 9월 9일에 쓰고 Adam Warski가 검토한 글이다.
Kafka는 순차 I/O를 잘 쓰도록 설계되었다.
프로듀서가 레코드를 배치로 묶고, 브로커가 그 배치를 순서 있는 로그 세그먼트에 덧붙이고, 컨슈머가 순차 구간을 읽으며, 운영체제 페이지 캐시와 `sendfile` 같은 제로 카피를 활용한다.
글은 클라우드에서 객체 저장소를 활성 로그로 쓰면 브로커가 데이터를 옮기지 않고도 확장할 수 있지 않을까라는 질문에서 출발한다.
그것이 diskless Kafka, 즉 Kafka 클라이언트 API는 유지하면서 영속 데이터를 브로커가 소유한 파티션 로그에서 떼어 내는 아이디어다.

동기는 비용과 탄력성이다.
세 가용 영역에 걸친 클러스터에서 리더가 받은 레코드를 다른 영역의 팔로워에게 복제하면 영역 간 트래픽이 크게 나온다.
KIP-1150은 이것을 AWS와 Google Cloud에서 주요 비용 요인으로 꼽는다.
브로커마다 파티션만큼의 저장 공간이 필요하고, 용량을 늘리거나 잃은 복제본을 대체할 때 데이터를 복사해야 하므로 저장 공간이 계산 자원의 변화 속도를 묶는다.
기존 Tiered Storage는 완료된 세그먼트만 원격으로 옮기므로 활성 세그먼트와 팔로워 복제는 그대로이고, diskless는 활성 쓰기 경로까지 바꾼다.
이름과 달리 디스크가 없다는 뜻이 아니라, 브로커 로컬 디스크가 사용자 데이터의 1차 진실의 원천이 아니라는 뜻이며, KIP-1150은 이를 serverless가 서버 없음과 맺는 관계에 비유한다.

S3는 Kafka 로그가 아니다.
객체 저장소는 적고 큰 객체를 원하고, Kafka는 많고 독립적이며 순서가 있는 파티션을 원한다.
그래서 대부분의 구현은 여러 파티션의 데이터를 한 객체에 묶는다.
WarpStream Agent는 기본 250ms 배치 타임아웃이나 크기 기준으로 플러시하는데, 글은 이 값이 영속 쓰기 지연이 아니라 배치를 기다리는 최대 시간이며, 프로듀서 확인 응답은 업로드와 메타데이터 커밋까지 기다린다고 짚는다.
파티션이 섞인 객체는 물리적 파티션 로그를 없애므로, 순서와 오프셋과 커밋 상태는 강한 일관성을 가진 메타데이터가 정한다.
글의 표현으로는 Kafka 프로토콜을 입은 분산 데이터베이스다.
diskless Kafka는 페이로드 복제를 S3에 맡길 수 있지만 Kafka의 의미론은 S3에 맡길 수 없으므로, 합의를 없애는 것이 아니라 옮긴다.

구현은 여섯 가지로 비교된다.

| 시스템                 | 영속 페이로드 경로                  | 순서와 메타데이터                           |
| ---------------------- | ----------------------------------- | ------------------------------------------- |
| WarpStream             | 객체 저장소에 직접                  | 별도의 강한 일관성 메타데이터 저장소        |
| AutoMQ                 | WAL을 거쳐 객체 저장소              | S3Stream과 Kafka 메타데이터(KRaft)          |
| Redpanda Cloud Topics  | 객체 저장소                         | 파티션별 Raft 자리 표시자와 공유 메타스토어 |
| Confluent Freight      | 객체 저장소에 직접                  | Kora 내부                                   |
| Aiven Diskless         | 객체 저장소                         | PostgreSQL 기반 Batch Coordinator           |
| Apache Kafka(KIP-1163) | 객체 저장소 WAL 세그먼트, 이후 병합 | 제안된 Diskless Coordinator                 |

AutoMQ는 WAL을 복제하지 않고 EBS 볼륨의 복제나 S3에 맡긴 채 브로커가 죽으면 다른 브로커가 이어받는다.
Redpanda는 L0 객체가 영속된 뒤 파티션 Raft 로그에 자리 표시자를 쓰고 응답하므로 브로커가 여전히 Raft 그룹 상태를 갖는다.
Confluent Freight는 100ms 미만 지연 대신 1~2초까지 걸릴 수 있는 쓰기 경로를 받아들인다.
Aiven은 트랜잭션, 압축 토픽, Kafka Streams 상태 저장소를 지원하지 않고, classic에서 diskless로의 전환만 가능하다.

Apache Kafka는 2026년 3월 2일 KIP-1150을 채택했지만, 이는 방향 결정이지 출시된 기능이 아니다.
8월 25일 기준 KIP-1163과 KIP-1164는 논의 중이고, KIP-1165는 폐기되었다가 7월에 다시 열렸다.
KIP-1164는 내부 토픽 `__diskless_metadata`를 진실의 원천으로 두고, 수백 MB에서 GB까지 커질 수 있는 상태를 로컬 SQLite로 구체화한다.
이 메타데이터 토픽 자체는 classic 토픽이라, 동기화된 복제본을 너무 많이 잃으면 diskless 쓰기가 멈춘다.

읽기 경로는 쓰기 최적화의 대가를 치른다.
파티션이 섞인 L0 객체에서 P7 하나를 재생하려면 여러 객체를 범위 읽기해야 하므로, Redpanda의 Reconciler나 WarpStream의 압축처럼 파티션과 오프셋 기준으로 재배치하는 배경 작업이 필요하다.
글은 이것을 LSM 트리 패턴으로 본다.
지연 시간은 배치 창과 객체 저장소 요청 비용의 교환이라 설정으로 없앨 수 없고, 운영의 복잡성은 사라지는 것이 아니라 배치, 메타데이터 순서, 압축, 가비지 수집, 캐시로 옮겨 간다.
S3가 싸다는 말로 비용 모델이 끝나지 않으며, 90% 저렴하다는 벤더 주장에는 맥락이 필요하다.
글의 결론은 모든 토픽이 아니라 처리량이 크고 보존 기간이 길며 지연을 견디는 워크로드에서, 그리고 토픽 단위로 선택하는 다중 모드 Kafka라는 방향이다.

## 분석

### 비용 절감의 정체는 복제의 단위를 바꾸는 것이다

글에서 가장 중요한 문단은 메타데이터 계층이 결국 원래의 복제 문제 아니냐는 반론에 답하는 부분이다.
메타데이터 저장소도 복제되는 강한 일관성 시스템이고 배치마다 커밋을 처리하므로, 조정 작업의 수는 줄지 않는다.
달라지는 것은 각 작업이 싣는 양이다.
페이로드 대신 객체와 오프셋 범위를 가리키는 포인터 크기의 레코드만 복제된다.

이 설명이 설득력을 갖는 것은 클라우드의 요금 단위 때문이다.
영역 간 트래픽은 작업 수가 아니라 바이트로 과금된다.
그러니 복제되는 단위를 메가바이트짜리 레코드에서 메타데이터 항목으로 줄이면 절감이 생기고, 파티션 간 배치는 커밋 빈도를 레코드 수가 아니라 배치 수에 비례하게 만든다.
diskless Kafka는 복제를 피하는 것이 아니라, 작고 합의가 꼭 필요한 데이터에만 복제를 남긴다.

### 모든 구현이 같은 문제를 다른 층에서 다시 푼다

여섯 구현을 나란히 놓으면 공통점이 보인다.
모두 페이로드를 객체 저장소로 보내고, 모두 순서를 정하는 강한 일관성 계층을 어딘가에 둔다.
차이는 그 계층을 어디에 두느냐와 브로커에 얼마나 상태를 남기느냐다.
WarpStream은 메타데이터를 별도 서비스로 빼서 Agent를 완전히 교체 가능하게 만들고, Redpanda는 기존 Raft 기계를 재사용하려고 브로커에 작은 상태를 남긴다.

그리고 없앤 줄 알았던 최적화가 다른 층에서 다시 나타난다.
AutoMQ의 WAL은 여러 파티션의 쓰기를 모아 고정 크기 순환 구조에 순차로 쓰고 그룹 커밋한다.
글의 표현대로 객체 저장소는 영속 데이터가 사는 곳을 바꿀 뿐, 순차 I/O의 가치를 폐지하지 않는다.
KIP-1164가 메타데이터를 로컬 SQLite로 구체화하는 것도 같은 흐름이다.
인덱스가 필요한 상태는 결국 로컬의 빠른 저장 구조로 돌아온다.

### Kafka의 프로토콜이 Kafka의 저장 구조보다 오래 살아남는다

글의 마지막 논점은 Kafka API가 Kafka의 원래 저장 설계보다 커졌다는 것이다.
애플리케이션은 토픽, 파티션, 오프셋, 컨슈머 그룹, 트랜잭션을 이해하지만, 그 아래가 ext4인지 S3인지는 신경 쓰지 않는다.
그래서 WarpStream, AutoMQ, Redpanda가 프로토콜 경계 아래에서 과감하게 실험할 수 있었고, 이제 Apache Kafka 자신이 같은 방향으로 움직인다.

이 구조는 S3 API가 걸은 길과 닮았다.
S3 API는 Amazon의 구현보다 오래 살아남아 MinIO, Cloudflare R2, Ceph의 공통 인터페이스가 되었다.
Kafka 프로토콜도 사실상의 스트리밍 표준이 되면서, 원조 구현은 여러 구현 중 하나가 되어 간다.

## 비평

### 비용 논의에 숫자가 하나도 없다

글은 영역 간 복제가 주요 비용 요인이라는 KIP-1150의 주장을 인용하고, 객체 저장소가 블록 저장소보다 바이트당 대체로 훨씬 싸다고 말한다.
그러면서 90% 저렴하다는 벤더 주장에는 맥락이 필요하다고 경고한다.
그런데 정작 그 맥락을 채울 숫자, 예를 들어 초당 몇 MB의 워크로드에서 영역 간 트래픽이 얼마이고, 같은 워크로드의 PUT과 GET 요청 비용이 얼마인지는 하나도 제시하지 않는다.

이 공백은 결론의 힘을 약하게 만든다.
글은 처리량이 크고 보존이 길고 지연을 견디는 워크로드에 적합하다고 말하지만, 처리량이 얼마 이상이어야 이 교환이 이득인지는 독자가 추정해야 한다.
작은 객체의 경제학이 핵심 제약이라고 스스로 강조한 글이라면, 배치 창과 파티션 수와 요청 비용의 관계를 간단한 계산이라도 보여 줬어야 한다.
벤더 주장에 맥락이 필요하다고 말하는 것과 그 맥락을 제공하는 것은 다른 일이다.

### 실패 모드가 구현 설명 속에 흩어져 있다

글은 각 구현의 장애 처리를 한두 문장씩 언급한다.
AutoMQ는 죽은 브로커의 볼륨을 다른 브로커에 붙이고, KIP-1164는 메타데이터 토픽이 동기화된 복제본을 너무 많이 잃으면 diskless 쓰기가 멈춘다.
하지만 diskless 구조 전체의 새 실패 모드, 즉 객체 저장소의 지역 장애, 메타데이터 계층과 객체 저장소 사이의 불일치, 가비지 수집이 아직 참조되는 객체를 지우는 경우는 정리하지 않는다.

classic Kafka의 실패 모드는 수년의 운영으로 잘 알려져 있다.
diskless Kafka는 복잡성을 메타데이터와 압축과 가비지 수집으로 옮긴다고 글 스스로 말했는데, 옮겨 간 곳에서 무엇이 어떻게 깨지는지는 말하지 않는다.
업그레이드를 검토하는 독자에게는 지연 시간이나 비용보다 이쪽이 더 중요한 질문일 수 있다.

### 이미 쓰고 있는 기능이 막히는 문제가 뒤로 밀린다

Aiven의 제한 목록은 가볍지 않다.
트랜잭션, 압축 토픽, Kafka Streams 상태 저장소가 지원되지 않고, diskless에서 classic으로 되돌릴 수 없다.
글은 이것을 Aiven 설명 안에서 한 번, 다중 모드 논의에서 한 번 언급하지만, 이것이 적합한 워크로드의 경계를 얼마나 좁히는지는 따로 다루지 않는다.

CDC는 글이 적합한 워크로드로 꼽은 예인데, 많은 CDC 파이프라인은 키별 최신 상태를 유지하려고 압축 토픽을 쓴다.
정확히 한 번 처리를 위해 트랜잭션을 쓰는 스트림 처리도 흔하다.
토픽 단위로 모드를 고를 수 있다는 결론은 맞지만, 그 선택이 되돌릴 수 없고 기능을 잃는다면 선택의 비용은 지연 시간보다 훨씬 크다.

## 인사이트

### 객체 저장소 위의 시스템들은 합의를 어디에 둘지로 갈린다

GN에서 click은 S3 위에서 도는 이런 서비스들이 신기하다며, 비슷한 사례로 Cursor의 Git 저장 시스템 Continuity를 떠올렸다[^gn-click].
두 시스템을 나란히 보면 흥미로운 대조가 생긴다.
`git/git-at-any-scale.md`가 정리한 Continuity는 S3의 조건부 쓰기와 ETag를 이용한 비교 후 교환으로, 별도의 합의 계층 없이 S3 자체를 진실의 원천으로 삼는다.
diskless Kafka는 반대로, S3에 바이트를 두되 순서와 오프셋은 별도의 강한 일관성 계층에서 정한다.

차이를 만드는 것은 쓰기의 동시성이다.
Git 저장소의 참조 갱신은 저장소 하나당 드물고, 한 번의 조건부 쓰기로 충분하다.
Kafka는 수만 개 파티션에 초당 수많은 배치가 들어오고, 각 배치에 전역 순서를 매겨야 한다.
객체 저장소의 원자적 연산만으로 감당할 수 있는 쓰기 빈도와, 별도 합의 계층이 필요한 쓰기 빈도 사이의 경계가 이 계열 시스템의 설계를 가르는 첫 질문이 된다.

### Kafka는 데이터베이스가 걸어온 길을 뒤따른다

글이 도달한 그림, 즉 거의 상태 없는 계산, 공유 객체 저장소, 강한 일관성 메타데이터, 캐시, 배경 압축은 클라우드 데이터 웨어하우스의 구조와 같다.
Snowflake가 저장과 계산을 분리하고, Neon이 PostgreSQL의 저장 계층을 페이지 서버와 객체 저장소로 떼어 낸 것이 먼저 간 길이다.
Kafka는 로그라는 가장 단순한 저장 모델로 시작했기 때문에 이 전환이 늦었을 뿐이다.

이 계보에서 보면 다음 단계도 예측할 수 있다.
데이터베이스가 저장을 분리한 뒤에 벌어진 일은 저장 계층을 여러 엔진이 공유하는 것이었다.
Iceberg 같은 테이블 형식이 여러 쿼리 엔진의 공통 저장이 된 것처럼, diskless Kafka의 객체가 스트리밍과 분석이 함께 읽는 형식이 되면 Kafka 토픽과 데이터 레이크의 경계가 흐려진다.
글이 적합한 워크로드로 데이터 레이크 수집을 꼽은 것은, 그 경계가 이미 움직이고 있다는 신호다.

### 다중 모드는 선택지를 늘리는 대신 판단을 토픽 소유자에게 넘긴다

토픽 단위로 classic, tiered, diskless를 고르게 하는 것은 합리적인 결론이다.
하지만 그 결정은 플랫폼 팀이 아니라 토픽을 만드는 각 팀에게 내려간다.
지연 시간 예산, 필요한 기능, 보존 기간, 비용을 이해하고 모드를 골라야 하는데, 대부분의 팀은 기본값을 쓴다.

그래서 다중 모드 Kafka의 실제 성패는 기본값에 달려 있다.
기본값이 classic이면 절감은 일부 팀의 적극적인 선택에 머물고, 기본값이 diskless면 지연에 민감한 팀이 뒤늦게 문제를 발견하는데, 적어도 Aiven에서는 되돌릴 수 없다.
기술적으로는 토픽 단위 선택이 유연함이지만, 조직적으로는 새로운 설정 부채가 된다.
플랫폼 팀이 워크로드 특성을 보고 모드를 추천하거나 강제하는 정책 계층이 diskless Kafka 도입의 숨은 필수 조건이 될 것이다.
