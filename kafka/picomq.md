## 소개

PicoMQ는 HTTP와 Kafka 프로토콜로 읽고 쓰는 내구성 있는 실시간 스트림 서버다.
Rust로 작성되었고 Apache-2.0 라이선스이며, 저장소는 2026년 8월에 만들어졌다.
클라이언트는 이름 붙은 스트림을 만들고 레코드를 덧붙인 뒤 다시 읽는다.
레코드는 S3 호환 오브젝트 스토리지에 저장되고,
클러스터 조정은 SQL 데이터베이스를 거친다.
문서는 노드를 백업할 만한 로컬 상태가 없는 단일 바이너리라고 설명한다.

저장소는 두 부분으로 나뉜다.
스트림 엔진은 별도 저장소인 `s3stream`이고,
`picomq/`는 메타데이터 계층, 서버, 프로토콜 프런트엔드, 클라이언트,
`pico` CLI를 담는 호스트다.
HN의 Show HN 글에서 작성자 adesh_nalpet은 S3Stream이 AutoMQ에서 쓰이는 스트림
저장 기본 요소를 Rust 라이브러리로 내놓은 것이라고 소개했다.

문서가 내세우는 관점은 스트림을 작고 버리기 쉬운 단위로 보는 것이다.
스트림 이름은 URL 경로처럼 생겼고 요청 하나로 만들어지며,
쉬고 있는 동안에는 비용이 들지 않는다고 한다.
한 배포가 스트림을 열 개 가질 수도, 주문마다, 세션마다,
기기마다, 작업마다 하나씩 수백만 개를 가질 수도 있다는 것이다.
나는 이 서버를 직접 실행하지 않았다.
아래의 동작 방식과 수치는 README와 저장소의 `website/pages/docs/` 문서,
HN 스레드의 작성자 답글에서 가져왔다.

## Kafka와 무엇이 다른가

문서의 FAQ인 Why not Kafka는 로그 작업을 두 종류로 나눈다.
깔때기형(funneling)은 많은 생산자가 적은 수의 공유 로그에 쓰고 소비자가
로그 전체를 읽는 경우로, 텔레메트리나 클릭스트림 수집, 웨어하우스 적재가 예다.
라우팅형(routing)은 엔티티마다 순서 있는 로그가 따로 있고 소비자가 이름으로
개별 로그를 읽는 경우로, 메시징, 피드, 엔티티별 상태, 에이전트 세션이 예다.
문서는 Kafka가 깔때기형만 지원하고 PicoMQ는 둘 다 지원한다고 주장한다.

근거는 읽기 증폭이다.
Kafka에서는 엔티티마다 파티션을 줄 수 없어 여러 엔티티가 파티션 하나에 섞이고,
한 키의 레코드만 돌려주는 읽기 경로가 없다.
그래서 사용자 한 명의 기록을 재구성하려면 파티션 전체를 훑어야 하고,
읽기 증폭은 파티션 크기를 요청한 레코드 크기로 나눈 값이 된다.
오프셋이 파티션 단위라 나쁜 레코드 하나가 뒤의 모든 엔티티를 막고,
파티션 수를 바꾸면 데이터가 움직이며,
뜨거운 키는 제자리에서 나눌 수 없는 뜨거운 파티션이 된다는 지적도 함께 있다.

PicoMQ는 엔티티별 로그를 일급 객체로 만든다.
생산자는 이름 붙은 스트림에 쓰므로 파티셔너가 없고,
엔티티 하나를 읽는 일은 스트림 하나를 따라가는 일이 된다.
집계 읽기는 접두사(prefix) 아래 스트림을 나열해 합쳐 읽는 방식이다.
깔때기형도 같은 모델로 표현되어,
파티션이 N개인 토픽은 한 접두사 아래의 스트림 N개가 된다.
키를 LSM 트리에 `(key, sequence)`로 넣는 신생 시스템들이 읽기 증폭은 고치지만
로그를 따로 나열하거나 지우지 못하고 계속 컴팩션해야 한다는 비교도 문서에 있다.

## 동작 방식

### 세 구성 요소

배포는 노드, 오브젝트 스토어, SQL 데이터베이스로 이뤄진다.

| 구성 요소        | 담는 것                     | 선택지                                                 |
| ---------------- | --------------------------- | ------------------------------------------------------ |
| 노드             | 캐시                        | `pico serve` 프로세스 또는 Postgres 안 백그라운드 작업 |
| 오브젝트 스토어  | 데이터 객체, 기본값의 WAL   | S3와 호환 스토어, 로컬 파일 시스템                     |
| SQL 데이터베이스 | 메타데이터 로그, 선택적 WAL | Postgres, 단일 노드는 SQLite                           |

노드 안에는 프로토콜 리스너, 관리 리스너, 소유권 라우터, 스트림 서비스,
`s3stream` 엔진이 쌓여 있다.
Postgres 확장으로 노드를 Postgres의 백그라운드 워커로 띄우면
메타데이터 로그와 WAL이 같은 데이터베이스에 들어간다.

### 합의 프로토콜 대신 SQL 명령 로그

노드 등록, 스트림 생성과 열기, 객체 커밋, 소유권 이전 같은 클러스터 상태
변화는 모두 명령이다.
노드가 명령을 SQL 데이터베이스에 제안하면 순서 있는 로그 테이블이 위치를
매기고, 모든 노드가 그 테이블을 따라 읽으며 메모리 상태에 적용한다.
합의 프로토콜이 줄 순서를 데이터베이스가 대신 주는 구조다.
명령 적용은 결정적이라 로그를 재생하면 항상 같은 상태가 나오고,
적용한 명령 1024개마다 스냅숏 행을 써서 시작 시 재생을 짧게 유지한다.
작성자는 HN에서 처음에는 OpenRaft로 썼다가 운영 복잡도를 줄이고 노드를
무상태로 두려고,
RisingWave에서 영감을 받은 SQL 명령 로그로 바꿨다고 밝혔다.[^adesh_nalpet]

### 쓰기와 WAL

덧붙이기는 레코드가 WAL에 들어가면 확인 응답을 받는다.
WAL은 오브젝트 스토어나 Postgres에 있고, 노드 로컬 디스크는 쓰기 경로에 없다.
들어온 레코드는 묶음(bulk)으로 모여 하나의 `PUT`이나 한 번의 `INSERT` 커밋이
된다.
쓰기는 파이프라인으로 여러 개가 동시에 날아가지만 확인 응답은 제출 순서대로
나간다.
이전 쓰기가 진행되는 동안 도착한 레코드가 다음 쓰기에 모두 실리는 그룹
커밋 덕분에 동시성이 높을수록 레코드당 비용이 줄어든다.

WAL은 장기 저장 형태가 아니라 대기 구역이다.
백그라운드 업로드 작업이 WAL 내용을 읽기에 맞춘 객체로 다시 묶고,
메타데이터 로그에 명령 하나로 커밋한다.
이 명령은 객체 등록과 관련된 모든 스트림의 끝 오프셋 전진을 원자적으로 하므로,
읽는 쪽은 커밋 전체를 보거나 전혀 보지 않는다.
커밋이 적용되면 그 범위의 WAL 객체는 지워진다.

### 읽기

읽기는 스트림의 소유 노드가 가장 빠른 계층에서 답한다.
최근 레코드를 담는 테일 캐시, 아직 객체로 올라가지 않은 레코드를 담는 로그
캐시, 커밋된 객체의 페이지를 LRU로 담는 블록 캐시 순서다.
모든 읽기는 WAL 업로드가 끝난 가장 높은 오프셋인 확인 오프셋(confirm
offset)까지로 제한된다.
그래서 레코드는 내구성을 얻는 순간 읽을 수 있게 되고,
충돌로 사라질 수 있는 데이터를 읽는 쪽이 보는 일은 없다.

끝까지 읽은 소비자는 롱 폴링이나 SSE로 기다린다.
롱 폴링은 기본 25초, SSE 연결은 55초마다 다시 맺는데,
둘 다 흔한 프록시의 유휴 타임아웃보다 짧게 잡은 값이다.
쓰기 경로가 WAL 업로드 완료 시점에 대기자를 깨우므로,
전달 지연은 내구성 지연과 같다.

### 소유권과 펜싱

각 스트림은 한 번에 한 노드만 서비스한다.
어떤 노드든 요청을 받고, 다른 노드가 소유한 스트림이면 `307`로 소유자 주소를
돌려준다.
배치는 슬롯 대비 할당 스트림 비율이 가장 낮은 노드로 가는 결정적 함수라
모든 노드가 같은 답을 계산한다.
노드는 시작할 때마다 밀리초 벽시계로 새 에포크를 받고,
스트림은 열릴 때마다 에포크가 오른다.
이전 에포크를 쥔 쓰기는 거부되므로, 오래된 라우팅 정보는 리다이렉트를 한 번
낭비할 뿐 스트림을 둘로 쪼개지 못한다는 것이 문서의 설명이다.

## 사용법

README 기준 설치와 단일 노드 실행은 다음과 같다.
단일 노드는 SQLite 메타데이터 로그와 로컬 파일 오브젝트 스토리지를 쓴다.

```bash
cargo install --path picomq/pico-cli

pico serve \
    --meta-url sqlite:./data/meta.db \
    --storage=-2@file://./objects
```

모든 플래그는 `PICO_*` 환경 변수로도 줄 수 있다.
`/health`와 `/ready`는 기본값 `127.0.0.1:9090`인 `--admin-listen`에 있다.
인증은 기본으로 꺼져 있고, 루프백이 아닌 주소에 바인딩하려면
`--auth required`나 `--insecure-allow-remote`가 필요하다.

스트림 조작과 벤치마크는 같은 `pico` 바이너리로 한다.

```bash
pico create /streams/orders --content-type text/plain
seq 1 1000 | pico append /streams/orders --batch 100
pico read /streams/orders
pico tail /streams/orders -f
pico close /streams/orders && pico delete /streams/orders

pico --http2 bench -b 1024 -w 512 --connections 4 --streams 4 -d 60
```

HTTP API는 스트림이 곧 URL이라는 모델이다.
`PUT`이 만들고 `POST`가 덧붙이고 `GET`이 읽고 `DELETE`가 지운다.
읽기 위치는 `GET /{stream}?seq=0`처럼 쿼리로 주고,
`live=long-poll`이나 `live=sse`로 대기 방식을 고른다.
위치 상태는 응답 헤더로만 오가고 서버는 소비자에 대해 아무것도 기억하지 않아,
일주일 뒤에 마지막 오프셋을 들고 와도 이어서 읽을 수 있다고 문서는 설명한다.
정확히 한 번 덧붙이기는 `Pico-Producer-Id`, `Pico-Producer-Epoch`,
`Pico-Producer-Seq` 헤더로 생산자를 식별해 처리한다.

Docker Compose로는 `harness/aio`에서 Postgres와 RustFS를 붙인 1노드,
2노드 클러스터, SQLite만 쓰는 경량 구성을 띄울 수 있다.

### Kafka 클라이언트로 붙이기

노드는 `--no-kafka`를 주지 않는 한 `--kafka-listen`에서 Kafka 와이어
프로토콜을 서비스한다.
HTTP로 만든 `/orders/eu` 스트림은 이름이 허용되고 비어 있으면 Kafka 토픽
`orders.eu`가 되고, Kafka 클라이언트가 만든 토픽은 HTTP에서 스트림으로 보인다.
지원 범위에는 분명한 경계가 있다.

| 영역        | 지원 여부                                                           |
| ----------- | ------------------------------------------------------------------- |
| Produce     | `acks` 0, 1, all이 같은 동작이며, 확인된 레코드는 내구적으로 저장됨 |
| 멱등 생산자 | 에포크 펜싱, 시퀀스 검사, 중복 재생을 포함해 지원                   |
| 소비자 그룹 | 클래식 그룹 프로토콜 지원                                           |
| 파티션      | 토픽당 하나만 지원, 그 이상 요청은 거부                             |
| 미지원      | 트랜잭션과 컨트롤 배치, KIP-848 소비자 프로토콜, SASL               |

Kafka 리스너에는 자체 인증이 없다.
그래서 `--auth required`를 켜도 루프백 밖에 바인딩하려면 항상
`--insecure-allow-remote`가 필요하고,
문서는 이를 네트워크 경계 안의 서비스로 다루라고 권한다.

## 값 정하기

튜닝 문서의 기준은 덧붙이기 지연의 하한이 WAL 쓰기 한 번이고,
오브젝트 스토어 비용이 대략 `PUT` 횟수에 비례한다는 것이다.
조용한 스트림에서는 묶음 간격(batch interval)이 지연을 지배한다.

| WAL             | 묶음 간격 기본값 | 크기 상한 | 쓰기 비용                   |
| --------------- | ---------------- | --------- | --------------------------- |
| 오브젝트 스토어 | `250` ms         | `8` MiB   | `PUT` 한 번, S3에서 수십 ms |
| Postgres        | `1` ms           | `1` MiB   | 커밋 한 번, 한 자릿수 ms    |

오브젝트 스토어 WAL에서 간격을 `5` ms로 줄이면 하한에 가까운 지연을 얻는 대신
플러시마다 `PUT`을 한 번씩 낸다.
붐비는 스트림은 크기 상한이 먼저 묶음을 닫으므로 이 값에 둔감하다.
엔진 메모리는 `--wal-cache-size` 기본 200 MiB, `--block-cache-size` 기본
100 MiB, `--wal-upload-threshold` 기본 100 MiB다.
업로드 임계값을 키우면 객체가 크고 적어지지만 WAL이 길어져 충돌 뒤 복구가
느려진다.
트래픽이 적은 노드에서는 `--wal-upload-interval-ms`를 켜 WAL을 짧게 유지하라고
문서는 권한다.

## 트레이드오프

### 내구성 확인의 지연이 가장 큰 비용이다

로컬 디스크를 쓰기 경로에서 뺀 대가로,
모든 확인 응답은 원격 저장소에 쓰기 한 번을 기다린다.
HN에서 KaiserPro가 S3 기반이면 쓰기 성능이 나쁘지 않냐고 묻자,
작성자는 스트림 사이에 공유하는 WAL, 서버 쪽 묶음,
HTTP/2를 쓴 클라이언트 쪽 파이프라이닝으로
스트림당 최대 100 MiB/s를 낼 수 있다고 답했다.[^adesh_nalpet-throughput]
다만 내구성 확인 지연은 약 250 ms이고 S3 Express에서는 더 낮다고 인정했다.
Shakahs는 S3 Express One Zone의 쓰기 지연이 10 ms 미만이라 WAL에 쓰고,
일반 S3의 100~150 ms도 작업에 따라 괜찮을 수 있다고 보탰다.[^Shakahs]

문서의 쓰기 설명은 S3에서 수십 밀리초라고 쓰지만,
튜닝 표의 오브젝트 스토어 묶음 간격 기본값은 250 ms다.
조용한 스트림의 레코드 하나는 이 간격까지 기다릴 수 있으므로,
기본 설정의 체감 지연은 작성자가 말한 250 ms 쪽에 가깝다고 보는 편이 안전하다.
이것은 두 수치를 맞춰 본 내 해석이다.
한 자릿수 밀리초가 필요하면 Postgres WAL로 옮기거나 S3 Express 계열을 써야
하고, 작성자는 디스크나 EBS에 먼저 쓰는 WAL을 선택적 기능으로 준비 중이라고
했다.

### SQL 로그는 운영을 덜지만 의존을 옮긴다

Raft를 걷어내면 노드는 무상태가 되고 노드를 잃어도 몇 초의 재라우팅으로
끝난다.
그 대신 클러스터의 순서와 펜싱 전부가 Postgres 하나에 걸린다.
WAL까지 Postgres에 두면 복제 설정이 곧 데이터 내구성이 된다.
문서는 동기 스탠바이가 없을 때 주 호스트를 잃으면 마지막 복제 커밋 이후의
레코드가 사라지고, `fsync = off`면 시작을 거부한다고 표로 밝힌다.
쉽게 말해 PicoMQ의 내구성은 오브젝트 스토어나 Postgres 운영 수준을 넘지 못한다.

### Kafka 호환은 표면만 맞춘다

Kafka 클라이언트가 그대로 붙는다는 점은 이식 비용을 낮추지만,
파티션이 하나뿐이고 트랜잭션이 없다는 제약 때문에 기존 Kafka 파이프라인을
그대로 옮기는 용도는 아니다.
jdcasale은 Kafka를 써 본 두 번 모두 초당 GB 단위였고 진짜 실시간 시스템은
수십 마이크로초 왕복을 위해 따로 만들었다며,
모든 것을 다 한다고 주장하기보다 어떤 영역을 잘하는지 인정하는 편이 더 나은
설득이라고 짚었다.[^jdcasale]
작성자는 이에 동의하며 FAQ에 Kafka의 대체재가 아니라는 내용을 넣겠다고 답했다.
jdcasale은 이어서 Kafka API의 함정을 들며 Kafka 와이어 프로토콜에 강하게
묶이지 않은 결정을 지지했다.[^jdcasale-api]

## 함정

### 리다이렉트를 따라갈 때 인증 헤더가 빠진다

API 문서에 따르면 표준 HTTP 클라이언트는 교차 출처 리다이렉트에서
`Authorization`을 떨어뜨리는데, 소유권 리다이렉트는 출처를 넘나든다.
그래서 인증을 켠 클러스터에서는 클라이언트가 `307`을 직접 따라가며 자격 증명을
다시 붙여야 한다.
`picomq-client`와 CLI는 이렇게 하지만 직접 만든 HTTP 클라이언트는 놓치기 쉽다.

### 비용은 바이트가 아니라 요청 수로 쌓인다

대부분의 오브젝트 스토어 요금은 요청 수가 지배한다고 튜닝 문서는 말한다.
묶음 간격을 줄여 지연을 낮추면 `PUT`이 늘고,
업로드 임계값을 낮춰 복구를 빠르게 하면 재작성이 늘어난다.
soleveloper가 Discord 같은 채팅을 만들면 얼마냐고 묻자 작성자는 하루 100만
메시지, 메시지당 200바이트, 월 약 6GB 기준으로 모두 포함해 월 30~150달러라고
어림했다.[^adesh_nalpet-pricing]
soleveloper는 읽는 쪽 트래픽이 메시지 수의 10~100배일 수 있다고
되물었다.[^soleveloper]
작성자는 이 금액이 주로 컴퓨팅, 네트워크, S3 쓰기 비용이고 비용을 분리한 공개
벤치마크를 준비 중이라고 답했다.[^adesh_nalpet-cost]
즉 이 숫자는 측정값이 아니라 어림이다.

### 소유권이 옮겨 간 직후에는 캐시가 비어 있다

스트림이 다른 노드로 옮겨 가면 오프셋은 그대로지만 새 소유자의 캐시는 차갑다.
이전 직후의 읽기는 테일이 다시 데워질 때까지 오브젝트 스토어 지연을 낸다.
Farrynet은 Fly.io 같은 환경에서 노드를 0으로 줄였다 다시 늘릴 때 WAL 복구가
소비자의 콜드 스타트 지연을 키우지 않느냐고 물었는데,
스레드에서 답은 달리지 않았다.[^Farrynet]
문서에 따르면 복구 시간은 WAL 길이에 비례하므로,
업로드 임계값과 간격이 이 질문의 실질적인 답이 된다.

### 원 프로토콜의 미래가 흔들린다

PicoMQ는 자체 Pico 프로토콜 외에 ElectricSQL이 만든 Durable Streams 공개
프로토콜을 구현한다.
Jonovono는 Electric이 인수되어 Durable Streams 프로젝트의 앞날이 불확실하다고
적었고,[^Jonovono]
alasano는 Electric Cloud의 Durable Streams가 인수 뒤 정리되고 있다고
전했다.[^alasano]
이 프로토콜을 기준으로 클라이언트를 만든다면 명세를 누가 관리할지부터 확인해야
한다.

## 기억할 원칙

### 스트림의 단위는 저장 구조가 아니라 읽는 방식이 정한다

PicoMQ의 주장은 결국 하나다.
엔티티 하나를 읽는 일이 잦다면 엔티티마다 로그를 주고,
전체를 훑는 일이 잦다면 넓은 로그를 쓰라는 것이다.
Kafka의 파티션 모델이 나쁜 것이 아니라 라우팅형 읽기에 맞지 않을 뿐이며,
반대로 PicoMQ도 초당 GB 단위 깔때기나 마이크로초 지연에는 맞지 않는다.
도입 판단은 처리량보다 먼저 어떤 단위로 읽는지에서 시작해야 한다.

### 무상태 노드는 상태를 없애지 않고 다른 곳에 맡긴다

노드에 디스크가 없다는 말은 운영을 단순하게 하지만,
그 상태는 오브젝트 스토어와 SQL 데이터베이스로 옮겨 갔을 뿐이다.
지연은 오브젝트 스토어의 쓰기 왕복이, 순서와 펜싱은 데이터베이스의 가용성이
정한다.
그 두 시스템을 이미 잘 운영하고 있다면 PicoMQ의 운영 부담은 작고,
그렇지 않다면 부담이 사라지는 것이 아니라 그쪽으로 옮겨 갈 뿐이다.
