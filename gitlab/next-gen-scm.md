# GitLab의 차세대 SCM: Git 호환은 지키고 백엔드와 에이전트 인터페이스를 새로 만든다

원문: [Scaling Git for the agentic software factory | GitLab](https://about.gitlab.com/blog/scaling-git-for-the-agentic-software-factory/)

GN 토론: <https://news.hada.io/topic?id=36758>

## 요약

GitLab의 Bill Staples가 2026년 10월 13일에 쓴 글이다.
GitLab이 에이전트 수천 개가 큰 저장소를 동시에 다루는 환경을 위한 차세대 소스
코드 관리(SCM)를 만들고 있다는 소개다.
6월 GitLab Transcend에서 처음 발표했고 8월에 아키텍처와 초기 성능 결과를 더
공유했으며, 지금은 비공개 베타라고 한다.

글은 Anthropic의 사례를 근거로 든다.
Anthropic 모노레포의 하루 병합이 5월 약 2,500건에서 9월 3만 건 이상으로 늘었고,
엔지니어들이 전용 소스 관리 시스템 Scion을 만들었다고 한다.
글은 Scion이 항상 온라인인 에이전트가 클라이언트 대부분인 거대한 모노레포를
위한 것이고, Anthropic 스스로 Git의 범용 대체가 아니며 코드 리뷰, 검색, CI도
따로 필요하다고 인정했다고 쓴다.
GitLab은 이와 달리 더 넓은 기업 시장을 겨냥해 Git 호환성, 인프라 선택,
소프트웨어 개발 수명 주기와의 통합을 지키며 에이전트 규모 성능을 낸다고 한다.
글에는 Anthropic 소스 컨트롤 팀의 Nick G.의 말이 인용되어 있고,
Git 서버가 Git 모델에서 벗어나지 않고도 할 수 있는 일을 넓힐 여지가 있다는
내용이다.

설계의 요지는 두 가지다.
첫째, 전통적인 Git 작업은 에이전트가 일부만 필요해도 저장소 데이터를 많이
내려받게 하고, 에이전트 호출 하나가 5~10GB 전송과 30초 이상의 준비를 요구할
수 있다고 한다.
둘째, 그래서 Git 프로토콜은 유지하되 공유 객체 저장소 위에서 상태 없는 계산이
수평 확장되고, 에이전트가 저장소 전체를 매번 클론하지 않고 필요한 파일과 이력을
요청하는 에이전트 전용 인터페이스를 둔다고 한다.
내부 초기 시험에서 작업이 최대 50배 빨랐고 토큰은 최대 2배 적게, 네트워크
트래픽은 최대 1,000배 적게 썼다고 하며, 글은 이것이 특정 조건의 최고치이고
지속적인 동시 부하 아래의 검증은 계속 진행 중이라고 밝힌다.
같은 구조를 GitLab.com과 고객이 통제하는 S3 호환 저장소에서, 에어갭 데이터
센터를 포함해 돌릴 수 있게 설계했다고 한다.

글은 소스 컨트롤만 빨라져서는 병목이 하류로 옮겨 갈 뿐이라고 덧붙인다.
GitLab.com에서 지난 1년 고객의 CI/CD 파이프라인이 40%, 코드 푸시가 50% 늘었다고
한다.
에이전트별로 격리된 세션에서 실패한 실험을 버리고 성공한 변경만 기존 머지
리퀘스트, 파이프라인, 보안 검사, 거버넌스로 흘려 보낸다는 구상과,
소프트웨어 수명 주기 전체의 컨텍스트 그래프인 GitLab Orbit,
단계 간 에이전트 작업을 조율하는 GitLab Duo Agent Platform을 연결한다.
글 끝에는 미래 전망 진술에 관한 법적 고지가 붙어 있다.

## 분석

### Git을 지키는 것이 이 글의 포지션이다

글은 Anthropic의 Scion을 에이전트 규모 문제의 증거로 쓰면서 곧바로 선을 긋는다.
Scion은 특정 환경에 맞춘 것이고, GitLab은 범용 기업 시장을 위해 Git 호환을
유지한다는 것이다.
같은 문제 진단에서 반대 결론을 이끄는 구조다.
Anthropic 쪽 글은 이 저장소의 `version-control/scion.md`가 다루지만,
이 문서는 그 내용을 이 글의 인용과 대조하지 않았다.
차이는 고객의 이전 가능성이라는 상업적 논거에서 나온다.
글도 대부분의 기업이 소스 컨트롤을 새 인프라로 옮길 수 없다고 말한다.

### 병목을 소스 컨트롤에서 CI와 거버넌스로 확장한다

글의 후반은 소스 컨트롤은 첫 병목일 뿐이라고 말하며
CI, 보안 검토, 배포, 에이전트 책임 추적으로 논점을 넓힌다.
이는 기술적 서술이면서 제품 전략이다.
저장소 계층의 성능은 다른 업체도 낼 수 있지만,
CI와 보안과 거버넌스를 한 플랫폼에 묶은 것은 GitLab이 가진 차별점이라고
글이 직접 말한다.
성능 이야기가 통합 플랫폼의 가치를 말하는 도입부로 쓰이는 구성이다.

### 에이전트 인터페이스가 Git의 바깥에 놓인다

글은 Git 프로토콜을 유지한다고 하면서 에이전트 전용 인터페이스를 따로 둔다.
에이전트는 클론 없이 필요한 파일과 이력만 요청한다.
이는 Git 호환이 클라이언트 쪽에서 지켜지고 에이전트는 다른 문으로 들어온다는
뜻이다.
같은 시기 GitHub도 클론 없는 읽기와 원자적 커밋 API를 계획에 넣었다.
글은 이 인터페이스가 어떤 형태인지 말하지 않는다.

## 비평

### 가장 눈에 띄는 숫자에는 조건이 없다

50배, 2배, 1,000배는 모두 최대치이고 글도 특정 조건의 최고 개선이라고 밝힌다.
그러나 어떤 저장소, 어떤 작업, 어떤 기준 흐름과 비교했는지 글에 없다.
에이전트 호출 하나가 5~10GB를 내려받는다는 수치도 어떤 저장소에서 나온
것인지 말하지 않는다.
비공개 베타이므로 독자는 이 수치를 검증할 수 없다.
글은 고객이 자기 저장소로 시험해 보라고 권하는데,
이 권유가 검증을 고객에게 넘기는 구조라는 점도 짚어 둘 만하다.

### 경쟁 사례를 자기 방향의 증거로 쓰는 것은 주의해서 읽어야 한다

글은 Anthropic의 경험이 GitLab이 추구한 아키텍처 방향을 강화한다고 말한다.
그러나 같은 글이 Scion은 범용 대체가 아니라고도 쓴다.
Scion은 Git을 떠나 새 시스템을 만들었고 GitLab은 Git을 남기는 쪽이므로,
Anthropic의 선택은 GitLab의 선택을 직접 뒷받침한다고 보기 어렵다.
뒷받침하는 것은 문제가 실재한다는 점뿐이다.
인용된 Nick G.의 발언이 Git 서버를 확장할 여지에 대한 것이긴 하지만,
이는 Anthropic이 GitLab의 제품을 택한다는 뜻이 아니다.

### 데이터 주권 주장은 제품이 없는 상태의 약속이다

글은 에어갭 데이터 센터와 고객 통제 S3 호환 저장소에서 같은 구조가 돈다고
말한다.
그러나 제품은 비공개 베타이고, 동시 부하 검증은 진행 중이라고 글이 밝혔다.
자체 호스팅 환경에서 상태 없는 계산과 공유 객체 저장소가 얼마나 운영하기 쉬운지,
객체 저장소의 일관성 보장이 환경마다 다른 점을 어떻게 다루는지는 글에 없다.
이 약속은 설계 의도이고 검증된 기능이 아니다.

## 인사이트

### 같은 진단이 세 가지 제품 전략으로 갈린다

에이전트가 저장소에 거는 부하가 인프라를 바꾼다는 진단은 Anthropic, GitHub,
GitLab, ERSC가 공유한다.
이 문서가 읽은 글들에서 출발점은 같고 처방은 다르다.
Anthropic은 GitLab 글의 설명대로라면 자체 시스템을 만들었고,
GitHub은 서버 스토리지를 새로 짜면서 Git을 유지했고,
ERSC는 Git 브리지 아래에 비Git 저장 엔진을 두는 구상을 밝혔고,
GitLab은 Git 호환 백엔드에 에이전트 인터페이스와 거버넌스를 묶는다.
선택의 차이는 기술보다 각자가 이미 가진 고객과 플랫폼이 무엇이냐에서 나온다.
어느 설계가 맞는지는 이 글들로 정해지지 않고,
공개 뒤 실제 대규모 저장소에서 나오는 수치로 가려질 것이다.

### 병목이 이동한다는 논리는 도구 판매의 논리이기도 하다

글은 소스 컨트롤이 빨라지면 병목이 CI와 검증으로 옮겨 간다고 말한다.
이는 합리적인 관찰이다.
그러나 같은 논리는 소스 컨트롤을 파는 곳이 CI와 보안과 거버넌스까지 같이 팔
이유가 된다.
병목 이동은 사실이어도 그 해법이 한 플랫폼이어야 한다는 결론은 따로 입증해야
한다.
푸시 50% 증가와 파이프라인 40% 증가라는 수치는 에이전트 때문인지, 일반적인
성장인지 글이 구분하지 않는다.

### 에이전트 책임 추적이 새 경쟁 축이 된다

글의 마지막 줄기 중 하나는 에이전트 행동의 귀속과 권한 부여, 변경 뒤의 지시와
결정을 보존하는 것, 리뷰어에게 맥락을 주는 것이다.
저장소 성능이 상품화되면 누가 무엇을 했는지 증명하는 기능이 차별점이 된다.
이것이 기능으로 구현될 때 가장 어려운 부분은 에이전트가 만든 변경의 근거를
얼마나 믿을 수 있게 남기느냐이며, 글은 방법을 말하지 않는다.
이 문서가 다음에 확인할 것은 이 기능이 제품에 실제로 들어가는지와 그 형식이다.
