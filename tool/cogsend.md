# CogSend: 내 Cloudflare 계정에서 돌리는 소셜 미디어 예약 발행 도구

<https://cogsend.com/>

<https://github.com/deepakness/cogsend>

HN 토론: <https://news.ycombinator.com/item?id=49810515> (2점, 0개 댓글)

GN 토론: <https://news.hada.io/topic?id=34739>

## 소개

CogSend는 Mastodon, Bluesky, LinkedIn, Threads, Twitter에 올릴 글을 한 번 쓰고
플랫폼별로 다듬은 뒤 바로 발행하거나 예약하는 셀프 호스팅 도구다.
저장소는 deepakness가 2026년 9월 22일에 만들었고, MIT 라이선스이며 주
언어는 TypeScript다.
GitHub API 기준으로 별 177개, 포크 25개다.

README가 내세우는 이유는 비용과 데이터 소유다.
호스팅형 예약 도구는 보통 채널마다 요금을 받고 글과 토큰을 자기 서버에 둔다.
CogSend는 사용자의 Cloudflare
계정에서 돌아가므로 데이터는 사용자의 D1 데이터베이스와 R2 버킷에 남고,
글은 사용자의 API 자격 증명으로 나가며, 구독료가 없다.
나는 이 도구를 직접 설치하거나 실행하지 않았고,
아래 내용은 홈페이지와 README, `docs/` 문서에서 가져온 것이다.

주요 기능은 다음과 같다.

- 스레드 편집기: 게시물마다 카드 하나, 대체 텍스트가 있는 이미지 최대 네 장, 플랫폼별 탭
- 자동 분할: 긴 초안을 붙이면 고른 플랫폼 중 가장 빡빡한 곳에 맞춰, 플랫폼마다의 글자 수 계산 방식대로 스레드를 나눈다
- 발행과 예약: 계정별 결과를 보고 취소, 재예약, 재시도한다
- 자동 재시도: 일시적 실패는 최대 다섯 번까지 스스로 다시 시도한다
- 인사이트: 7일, 30일, 90일 동안의 성공과 실패, 실패 이유
- 링크 미리보기 카드
- AES-256-GCM으로 암호화해 저장하는 플랫폼 토큰과 관리자 계정의 2단계 인증
- 설정 화면의 실행 중인 버전, 틱 도착 여부, 새 릴리스 알림
- MCP 서버와 개인 API 키

스택은 Cloudflare Workers 위의 SvelteKit 2와 Svelte 5이고,
Drizzle로 쓰는 D1(SQLite)과 미디어용 R2를 쓴다.

홈페이지는 인사이트 화면을 보여 주기 위한 차트가 아니라 무엇이 고장 났는지
알려 주는 통계라고 설명한다.
발행 성공과 실패를 사용자의 시간대 기준 날짜로 묶고 직전
같은 기간과 나란히 보여 준다.
실패는 API 오류를 늘어놓지 않고 이유별로 묶으므로,
플랫폼 전체의 장애와 글 하나의 문제가 다르게 보인다.
마지막 발행 시각을 함께 띄워 한 주 동안 아무것도 나가지 않은 상황을 바로
알아챌 수 있게 했다.

## 동작 방식

### 예약은 틱이 처리한다

예약된 글은 D1에 저장되고 틱이 발행한다.
틱은 Worker 자체의 cron 트리거이거나, 틱 엔드포인트에 POST를 보낼 수 있는
무엇이든 될 수 있다.
cron 트리거는 `wrangler.jsonc`에 켜진 상태로 들어 있고 1분마다 돈다.

틱은 언제나 가장 오래된 예약 글 하나를 발행하고,
그다음 글은 예상 호출 수가 요청의 Cloudflare 예산에 들어갈 때만 시작한다.
이 예산은 D1 문장, R2 읽기,
플랫폼 호출을 모두 세며 Workers 무료 플랜에서 50이다.
예산에 들어가지 않는 글은 다음 틱으로 넘어가므로 무료 플랜에서는 밀린 글이
1분에 한두 개씩 빠진다.
문서는 이 설계가 플랫폼이 이미 받아들인 글을 처리하는 도중에 요청이 예산을 다
써서 같은 글이 두 번 나가는 일을 막는다고 설명한다.
유료 플랜에서는 `SUBREQUEST_LIMIT`을 설정하면 한 틱이 예약된 글을 모두 발행한다.
틱은 멱등이라 중복되거나 늦은 호출이 와도 해가 없다.

### 중복 발행을 막는 장치는 플랫폼마다 다르다

같은 초안과 계정으로 두 번 발행하면 기존 행을 재사용하고,
이미 발행된 계정은 `skipped: true`로 돌아온다.
재시도한 스레드 조각은 처음 시도와 같은 플랫폼 쪽 id를 쓰므로 중간에 실패한
스레드가 이미 나간 부분을 다시 올리지 않는다.
Mastodon은 이 id를 한 시간 동안 기억하고 Bluesky는 레코드 덮어쓰기를 거부한다.
Twitter, LinkedIn, Threads는 이런 id를 받지 않는다.
그래서 이 세 플랫폼에서 글 생성 요청을 보냈지만 응답이 오지 않으면 발행되었을 수
있다는 오류로 실패 처리하고 자동으로 재시도하지 않는다.
사용자가 플랫폼을 먼저 확인한 뒤 재시도해야 한다.

## 설치하기

Node 22.13 이상, 24, 또는 26 이상이 필요하고 25 같은 홀수
릴리스는 지원하지 않는다.
홈페이지는 Node 22.12 이상이라고 적어 README와 부 버전 하나가 다르므로,
22 계열을 쓴다면 22.13 이상으로 맞추는 편이 안전하다.
Workers, D1, R2를 쓸 수 있는 Cloudflare 계정도 필요하다.

```sh
git clone --depth 1 https://github.com/deepakness/cogsend.git cogsend
cd cogsend && npm install && npm run setup
```

`setup`은 Cloudflare 리소스, 관리자 계정,
시크릿을 만들고 배포한 뒤 URL을 출력한다.
그 주소로 로그인해 인증 앱으로 QR을 찍고 백업 코드를 저장한다.
다시 실행해도 안전하다고 README는 적는다.
설치가 제대로 되었는지는 `npm run doctor`로 확인한다.
이 명령은 읽기 전용이며 Cloudflare 계정, 데이터베이스, 버킷, 시크릿,
배포를 차례로 점검하고, 실패한 항목마다 고치는 명령을 함께 출력한다.
`-- --app-url <url>`을 붙이면 배포된 앱에도 직접 물어본다.
Mastodon과 Bluesky는 바로 연결되고, LinkedIn, Threads,
Twitter는 먼저 OAuth 앱을 만들거나 Zernio를 거쳐 연결한다.
Zernio는 README에 후원사로 표시된 서비스로,
자체 개발자 앱 없이 이 플랫폼들을 연결하게 해 준다.

업데이트는 다음 한 줄이다.

```sh
git pull && npm ci && npm run deploy:release
```

`deploy:release`는 테스트, 마이그레이션, 빌드, 배포를 차례로 실행한다.
데이터는 체크아웃이 아니라 D1과 R2에 있으므로 pull이 데이터를 건드리지 않는다.

### 외부에서 틱 호출하기

Workers 무료 플랜은 계정당 cron 트리거를 다섯 개만 허용하고, 이 개수는 계정의
모든 Worker가 나눠 쓴다.
남은 트리거가 없으면 `npm run deploy`가 그 사실을 알리고 트리거 없이 앱을
배포하며, 예약 글은 누군가 틱 엔드포인트를 호출할 때까지 기다린다.
그때는 cron-job.org, 라즈베리 파이, systemd 타이머,
번들된 GitHub Actions 워크플로 등에서 다음처럼 호출한다.

```sh
curl -X POST "$APP_URL/api/internal/tick" \
  -H "Authorization: Bearer $SCHEDULER_SECRET" \
  -H "Content-Type: application/json"
```

`Content-Type: application/json`은 생략하면 안 된다.
SvelteKit의 CSRF 방어가 폼 콘텐츠 유형으로
들어오고 `Origin`이 맞지 않는 POST를 앱 코드에 닿기 전에 403으로 막는데,
많은 cron 서비스가 기본으로 폼 유형을 보낸다.
번들된 GitHub 워크플로는 5분 간격으로 설정되어 있지만 GitHub이 대략 두 시간에 한
번꼴로 줄인다고 문서는 경고하므로 주된 틱이 아니라 예비로 쓰는 편이 맞다.

## 에이전트와 스크립트에서 쓰기

스크립트, 단축어, cron, MCP 클라이언트는 쿠키 대신 개인 API 키를 쓴다.
키는 읽기 전용과 읽기·쓰기 중 하나로 만들고,
원본 키는 한 번만 보여 주고 해시만 저장한다.
키는 계정 연결과 해제, 키 생성과 회전과 폐기에는 쓸 수 없고 이 작업은
브라우저 세션에만 남는다.

`<인스턴스>/api/mcp`가 MCP 서버이며 POST로 받는 상태 없는 Streamable HTTP다.
Claude Code에서는 `.mcp.json`에 다음을 넣고
`COGSEND_API_KEY`를 환경 변수로 둔다.

```json
{
  "mcpServers": {
    "cogsend": {
      "type": "http",
      "url": "https://cogsend.example.com/api/mcp",
      "headers": { "Authorization": "Bearer ${COGSEND_API_KEY}" }
    }
  }
}
```

읽기 전용 키로는 `list_connections`, `list_drafts`, `get_draft`, `list_queue`,
`validate_post`를 쓸 수 있다.
초안 생성과 수정, 예약, 발행, 재시도 같은 나머지 도구는 읽기·쓰기 키가 필요하다.
`publish_draft`와 `retry_delivery`는 실제 계정에 글을 올린다.
문서는 쓰기나 발행을 하는 도구 앞에서 묻도록 클라이언트를 설정하라고 권하고,
CogSend가 그런 도구를 표시하지만 멈추고 물어볼 수 있는 것은
클라이언트뿐이라고 적는다.
미디어, 설정, 인사이트, 계정 관리는 MCP로 노출하지 않는다.

## 트레이드오프

### 구독료 대신 운영 책임을 진다

무료 플랜 안에서 돌릴 수 있다는 것이 README의 핵심 약속이다.
그러나 R2는 결제 수단 등록이 필요하고, 무료 플랜의 요청당 예산 50
때문에 밀린 글은 1분에 한두 개씩만 나간다.
cron 트리거가 다른 Worker와 다섯 개를 나눠 쓴다는 제약도 있다.
홈페이지는 나머지 한도도 적어 둔다.
R2는 처음 10GB까지 무료이고 외부로 나가는 트래픽은 늘 무료다.
D1은 하루에 쓴 행이 10만 개를 넘으면 그날은 멈췄다가 UTC 자정에 다시 돌고,
그 사이 데이터는 잃지 않는다.
Twitter는 API가 사용량 과금이라 연결하기 전에 잔액을 미리 충전해 두어야 한다.
개발자 앱 등록을 피하려고 Zernio를 거쳐도 무료 플랜은 있지만 Twitter 연결에는 카드가 필요하다.
결국 구독료가 없다는 말은 개인 인스턴스 기준이며,
Twitter를 쓰는 순간 플랫폼 쪽 비용은 피할 수 없다.
호스팅형 도구가 받는 채널 요금은 사라지지만, 그 대가로 사용자는 트리거 개수,
플랫폼 OAuth 앱, 시크릿 회전, 백업을 직접 챙긴다.

### 재시도의 안전성은 플랫폼이 정한다

자동 재시도는 일시적 실패에 다섯 번까지 돌지만,
중복을 막는 장치는 플랫폼이 멱등 키를 받는지에 달려 있다.
Mastodon과 Bluesky에서는 안전하게 재시도하지만 Twitter, LinkedIn,
Threads에서 응답을 못 받은 요청은 사람이 확인해야 한다.
여러 계정에 같은 글을 뿌리는 도구에서 가장 신경 쓰이는 실패가 중복 게시인데,
그것을 완전히 막을 수 없는 플랫폼이 셋이라는 뜻이다.
문서가 이 경계를 숨기지 않고 오류 메시지까지 정해 둔 점은 좋은 설계로 보인다.

### 에이전트에게 발행 권한을 줄지 정해야 한다

MCP 서버 덕분에 Claude Code나 Codex가 초안을 쓰고 예약하고 발행까지 할 수 있다.
읽기 전용 키와 읽기·쓰기 키의 구분은 있지만 발행만 따로 막는 범위는
문서에 나오지 않는다.
초안 작성만 맡기고 싶어도 읽기·쓰기 키에는 `publish_draft`가 함께 따라온다.
그래서 실제 계정으로 글이 나가는 것을 막는 마지막 장치는 클라이언트의 확인
설정이고, CogSend 문서도 그 점을 인정한다.

## 함정

- 새로 설치한 직후 몇 분 동안 설정 화면이 아직 틱이 없다고 보여도 정상이다. Cloudflare가 여유 있는 머신에서 cron을 돌리기 때문이며, 한 시간 뒤에도 그대로면 `npm run doctor -- --app-url <url>`로 원인을 확인한다.
- 여러 계정 id를 한 요청으로 발행하면 예산에 들어가지 못한 계정은 `deferred: true`로 돌아온다. 이 계정들은 이미 예약된 상태이므로 다시 보내면 안 된다.
- 반대로 요청이 도중에 멈춰 `stopped: true`가 오면 마지막 결과 뒤의 계정은 완료되지 않은 것이므로 다시 보내야 한다. 두 응답을 헷갈리면 중복 발행이나 누락이 생긴다.
- 예약 API가 HTTP 200을 돌려도 예약되었다고 단정하지 말고 `error`, `alreadyPublished`, `inFlight`를 확인한다.
- API가 받아들인 본문도 발행 시점에 각 플랫폼의 글자 수와 미디어 제한을 다시 검사하므로 플랫폼이 거부할 수 있다.

## 기억할 원칙

### 셀프 호스팅 도구의 품질은 실패 경로의 문서에서 드러난다

CogSend의 README는 기능 목록이 짧고, 문서의 많은 분량이 틱 예산, 중복 발행,
지연된 트리거, 응답을 잃은 요청처럼 일이 잘못되는 경우에 쓰여 있다.
여러 플랫폼에 글을 보내는 도구에서 사용자가 실제로 다치는 지점은 기능 부족이
아니라 두 번 나간 글이나 조용히 빠진 글이다.
셀프 호스팅을 고를 때는 기능표보다 이런 실패 경로를 얼마나 구체적으로 적어
두었는지를 먼저 보는 것이 낫다.
