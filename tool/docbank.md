# Docbank: 문서의 권위를 경로가 아니라 안정적 ID에 두는 로컬 우선 기록 시스템

<https://docbank.ai/>

<https://github.com/kenn-io/docbank>

## 소개

한 줄 표어가 범위를 정한다 — “Your documents. Your agents. One system.”이다.
저장소 설명은 사람과 에이전트를 위한 문서(PDF, 이미지, 텍스트 등)의
로컬 우선 기록 시스템이라고 적는다.

README 맨 위에 경고가 있다.
알파 소프트웨어이므로 대체 불가능한 자료는 독립적인 사본을 따로 두고
백업을 검증한 뒤에 의존하라는 것이다.

스스로 규정하는 정체성은 자기주권형(self-sovereign) 문서 시스템이다.
익숙한 가상 트리에 안정적 문서 ID, 불변 콘텐츠 버전, 색인 기반 검색,
복구 가능한 삭제, 검증된 백업, 그리고 선택적 영구 감사 이력을 결합했다고 설명한다.
금고(vault) 카탈로그가 사업자 계정 안이 아니라 사용자 통제 아래 남는다는 문장이 뒤따른다.

문제 정의는 두 문장으로 압축되어 있다.
경로는 파일을 찾기에는 쓸 만한 자리이지만 장기 식별자로는 빈약하다는 것,
그리고 클라우드 드라이브는 계정 접근과 사업자 정책까지 내 아카이브의 권위 일부로 만든다는 것이다.

경계도 명시한다 — 동기화·공유 서비스가 아니라 아카이브이자 기록 시스템이며,
작업 폴더를 기기 간에 미러링하지 않고 공개 공유 링크도 만들지 않는다.

## 무엇을 할 수 있는가

README가 필요와 기능을 표로 대응시킨다.

| 필요             | 제공 기능                                                                             |
| ---------------- | ------------------------------------------------------------------------------------- |
| 기록 정리와 검색 | 재귀 임포트, 검증된 업로드, 가상 폴더, 태그, 이름·추출 텍스트 순위 검색               |
| 변경 중 동일성   | 안정적 노드 ID, 불변 버전 UUID, 검증된 교체, 되돌리기, 명시적 버전 정리               |
| 에이전트 안전    | 인증된 HTTP와 OpenAPI, 제한된 목록, 구조화된 오류, 리비전 사전조건, 다이제스트 영수증 |
| 실수 복구        | 복구 가능한 휴지통, 리비전 기반 복원, 명시적 GC와 리팩, 금고 전체 검증                |
| 복구 증명        | 인크리멘탈 스냅숏 저장소, 완전한 콘텐츠 검증, 토폴로지 독립 복원                      |
| 영구 기록 보존   | 미리보기 우선 감사 범위, 고정 보존, 독립적으로 재생되는 증거                          |
| 물리 용량 관리   | 루스·팩 저장, 자동 제한 패킹, 다중 스토어 배치와 수리·구제·이전                       |

핵심 구분을 다섯 항목으로 다시 정리해 둔다 —
안정적 노드 ID는 이동과 이름 변경 후에도 문서를 계속 식별하고,
모든 콘텐츠 버전은 불변이며 검증 가능한 SHA-256 다이제스트로 이름 붙고,
리비전이 낡은 자동화를 조용한 덮어쓰기 대신 명시적 충돌로 바꾸고,
휴지통과 영구 삭제와 가비지 컬렉션과 팩 회수가 각각 별개의 결정이며,
인크리멘탈 백업은 복원 결과를 공표하기 전에 검증된다.

물리 콘텐츠는 울타리를 친 파일시스템이나 S3 호환 스토어에 둘 수 있지만,
그 스토어가 문서 카탈로그가 되지는 않는다고 명시한다.

## 사용법

초기화 의식이 없다 — 첫 데이터 명령이 금고를 만들고 데몬을 띄운다.

```bash
docbank add ~/Documents --dest /archive
docbank tree /archive
docbank search "tax return"
docbank web
```

파일을 받고 같은 문서를 이전 내용을 다시 쓰지 않고 변경하는 흐름이다.

```bash
docbank get /archive/Documents/receipt.pdf ./receipt.pdf
docbank versions list /archive/Documents/receipt.pdf
docbank put revised-receipt.pdf /archive/Documents/receipt.pdf
docbank mv /archive/Documents/receipt.pdf /archive/Documents/receipt-2026.pdf
docbank verify
```

복구 지점을 만들고 증명하는 흐름은 네 단계다.

```bash
docbank backup init --repo ~/Backups/docbank
docbank backup create --repo ~/Backups/docbank --tag first-import
docbank backup verify --repo ~/Backups/docbank
docbank backup restore --repo ~/Backups/docbank --target ~/Restores/docbank-test
```

설치는 `docbank.ai`의 스크립트를 파이프하는 방식인데,
설치 프로그램이 릴리스의 `SHA256SUMS`와 다이제스트가 일치하지 않으면 설치를 거부한다고 적는다.
소스 빌드에는 Go 1.26+와 CGO, C 컴파일러, Node 24+, npm이 필요하다.

## 에이전트 계약

별도 문서가 에이전트용 설계를 다룬다.
첫 문장이 자세를 정한다 — Docbank는 에이전트가 직접 열어야 하는 데이터베이스가 아니라
에이전트 대응 인터페이스를 가진 문서 기록 시스템이라는 것이다.
데몬 하나가 금고를 소유하고, CLI와 에이전트와 스크립트와 외부 애플리케이션이
모두 그 인증된 HTTP 계약을 통과하므로 검증과 동시성과 무결성과 유지보수 규칙을 공유한다.

계약이 에이전트에게 주는 것은 네 가지로 정리된다 —
이름 변경과 이동을 견디는 안정적 동일성,
`If-Match`로 낡은 읽기·수정·쓰기를 HTTP 412 충돌로 바꾸는 충돌 증거,
업로드가 해시와 크기를 선언하고 다운로드가 다이제스트 증거를 실어 오는 바이트 증거,
그리고 페이지네이션과 검색 상한과 구조화된 문제 코드와 드라이런과 NDJSON 진행 표시로
사람용 출력을 긁지 않게 하는 제한된 자동화다.

면(surface)은 네 가지이고 용도가 갈린다.

| 인터페이스    | 용도                              | 계약                                          |
| ------------- | --------------------------------- | --------------------------------------------- |
| CLI           | 사람이 지시하는 작업, 셸 스크립트 | 읽기 좋은 출력, 문서화된 기계 모드            |
| HTTP API      | 독립 애플리케이션, 장기 워크플로  | 인증 JSON, 리비전, 페이지네이션, 구조화 오류  |
| OpenAPI       | 클라이언트 생성과 기능 발견       | `docbank openapi --json`, `/openapi.json`     |
| 마크다운 문서 | HTML 긁기 없는 컨텍스트 조회      | 모든 공개 `/foo/` 페이지가 `/foo.md`로도 발행 |

정신 모델은 네 줄이다 —
데몬이 권위이므로 `docbank.db`를 직접 열거나 팩 파일을 고쳐 쓰거나
파일시스템 배치에서 살아 있는 내용을 추론하지 말 것,
ID가 노드를 식별하고 경로는 현재 배치를 서술할 뿐이라는 것,
콘텐츠 동일성은 불변이므로 `put`은 검증된 바이트를 추가하고
`revert`는 저장된 이력을 제자리에서 고치는 대신 이전 버전에서 새 헤드를 만든다는 것,
그리고 스트림은 끝나기 전까지 검증되지 않았으므로
성공적인 EOF까지 읽고 다이제스트 증거를 확인한 뒤에 내려받은 바이트를 공표하라는 것이다.

## 배포와 신뢰 경계

배치 형태는 두 가지다.
스탠드얼론에서는 데몬 하나가 금고를 소유하고 모든 CLI와 브라우저와 TUI와 스크립트와
외부 에이전트가 루프백 인증 API를 지난다.
임베드에서는 Go 애플리케이션 하나가 독립적으로 뿌리내린 금고를 인프로세스로 소유하며
CGO와 순수 Go SQLite를 고를 수 있다.

보조 스토리지에 관한 문장이 하나 따로 있다.
Docbank는 설정된 파일시스템과 S3 호환 스토어의 콘텐츠를 검증하지만 암호화하지는 않으므로,
그 네임스페이스는 소유자 접근 제어와 운영자에 맞는 저장 암호화로 보호하라는 것이다.

백업에 관한 조건도 명시된다.
로컬 데이터베이스와 주 블롭 디렉터리를 멈춘 상태로 복사한 것은
보존된 모든 블롭이 여전히 주 권위를 갖고 있을 때에만 완전하며,
`docbank backup create`는 원격 전용 배치에서도 완전하게 남아 선호되는 이식 가능한 복구 경로라고 적는다.

## 분석

### 경로 대신 ID를 권위로 삼는 결정이 이 제품의 전부다

README의 문제 정의는 한 문장에 담겨 있다 —
경로는 파일을 찾기에는 좋지만 장기 식별자로는 빈약하다는 것이다.
그 관찰 위에 나머지 기능이 전부 얹힌다.

이 구분은 새로운 것이 아니고, 새로 적용된 자리가 새롭다.
이름과 내용을 분리해 내용에 해시로 이름을 붙이는 방식은
Git의 오브젝트 저장소와 Plan 9의 Venti와 IPFS가 이미 같은 형태로 쓴다.
Docbank가 한 일은 그 구조를 개인 문서 계층으로 가져오면서
사람이 보는 트리는 그대로 두는 것이다 — 노드 ID가 동일성을 지고,
경로는 현재 배치를 서술하는 라벨로 내려간다.

그리고 이 분리가 클라우드 드라이브 비판과 이어진다.
Dropbox나 Google Drive에서 문서의 동일성은 사업자 계정 안의 레코드에 있고,
계정이 정지되거나 정책이 바뀌면 아카이브의 권위가 함께 흔들린다.
Docbank는 카탈로그를 로컬 데몬에 두고 물리 바이트만 외부 스토어에 배치할 수 있게 해서
그 두 층을 갈라 놓는다 — 스토어를 문서 카탈로그로 만들지 않는다는 문장이 그 선언이다.

### 에이전트 인터페이스를 UI의 부속이 아니라 계약으로 설계했다

대부분의 개인 문서 도구에서 자동화는 나중에 붙는다 —
UI를 먼저 만들고, 스크립트용 CLI를 추가하고, 요청이 오면 API를 낸다.
Docbank는 순서를 뒤집었다.
데몬 하나가 금고를 소유하고 CLI와 웹과 TUI와 에이전트가 모두 같은 인증 계약을 통과하므로,
사람이 쓰는 경로와 기계가 쓰는 경로가 같은 검증과 동시성 규칙을 공유한다.

계약의 구체적인 내용이 이 설계의 진지함을 보여 준다.
`If-Match`와 리비전으로 낡은 읽기·수정·쓰기를 HTTP 412로 만드는 것은
데이터베이스의 낙관적 잠금과 HTTP의 ETag가 오래 쓴 방식이고,
개인 문서 계층에 그것이 필요해진 이유는 이제 그 계층에 동시 기록자가 생겼기 때문이다.
다이제스트 영수증과 “스트림은 끝나기 전까지 검증되지 않았다”는 규칙도 같은 성격이다 —
에이전트가 부분 다운로드를 완성된 파일로 취급하는 사고를 계약 수준에서 막는다.

가장 눈에 걸리는 항목은 문서 인터페이스다.
모든 공개 페이지를 `/foo.md`로도 발행하는 이유를 HTML 긁기 없는 컨텍스트 조회라고 적는다.
문서를 사람용 표면이 아니라 조회 대상으로 취급한 것이며,
`docbank openapi --json`으로 기능 목록을 기계가 받아 갈 수 있게 한 것과 짝을 이룬다.

그리고 금지 항목이 허용 항목보다 많은 말을 한다.
`docbank.db`를 열지 말라, 팩 파일을 고쳐 쓰지 말라,
파일시스템 배치에서 내용을 추론하지 말라는 세 문장은
에이전트가 지름길을 찾을 것을 전제하고 그 지름길을 미리 닫아 둔 것이다.

### 삭제를 네 개의 결정으로 쪼갠 것이 이 시스템의 성격을 말한다

휴지통과 영구 삭제와 가비지 컬렉션과 팩 회수를 각각 별개의 결정으로 분리했다는 문장은
기능 목록의 한 줄로 보이지만 제품의 분류를 정한다.

소비자 저장 서비스는 이 넷을 하나로 합친다.
삭제를 누르면 휴지통에 들어가고 30일 뒤에 알아서 사라지며,
공간 회수는 사용자가 알 필요 없는 내부 동작이다.
편의로는 옳은 선택인데, 그 결과 “지웠다”가 무엇을 뜻하는지 사용자가 통제하지 못한다.

아카이브의 일은 반대다 — 파괴를 의도적으로 만드는 것이다.
넷으로 쪼개면 각 단계에서 멈출 수 있고,
어느 단계까지 진행됐는지가 상태로 남으며, 회수는 명시적 명령이 된다.
같은 본능이 “인크리멘탈 백업은 복원 결과를 공표하기 전에 검증된다”에도 있다 —
검증되지 않은 복구 지점을 복구 지점으로 부르지 않겠다는 것이다.

이 성격 때문에 이 제품의 비교 대상이 정해진다.
Dropbox가 아니라 보존 시스템과 WORM 저장소와 문서 관리 시스템 쪽이고,
그래서 “선택적 영구 감사 이력”과 “고정 보존” 같은 어휘가 개인용 도구에 들어와 있다.

### Hubble.md가 답하지 않은 질문에 이 프로젝트가 답한다

같은 범주의 앞선 사례가 있다.
[사람과 에이전트가 같은 노트를 함께 쓰는 앱 Hubble.md](hubble.md)는
공유 데이터를 전제로 노트 앱을 만들었고, 그 문서의 비평 중 하나가
에이전트가 사용자의 노트를 편집하는 위험을 다루지 않는다는 것이었다.

Docbank는 그 질문에서 시작한 것처럼 보인다.
리비전 사전조건이 조용한 덮어쓰기를 명시적 충돌로 바꾸고,
휴지통이 복구 가능하고, 모든 버전이 불변으로 남고,
바이트마다 다이제스트 영수증이 붙는다.
에이전트가 실수할 것을 전제하고 실수의 결과를 되돌릴 수 있게 만든 설계다.

두 프로젝트의 강조점이 갈리는 지점도 분명하다.
Hubble.md는 저작(authoring)을 최적화한다 — 쓰고 고치고 에이전트에게 맡기는 흐름이다.
Docbank는 보관(custody)을 최적화한다 — 넣고 증명하고 되돌리는 흐름이며,
편집기가 없고 애초에 그것을 목표로 하지 않는다.
같은 문제 인식에서 출발해 한쪽은 작업 공간을, 다른 쪽은 금고를 만들었다.

## 비평

### 스스로 정한 비목표가 대부분의 사용자가 실제로 원하는 기능이다

경계 선언이 명확하다 — 동기화·공유 서비스가 아니고,
작업 폴더를 기기 간에 미러링하지 않고, 공개 공유 링크도 만들지 않는다.
원칙으로서는 존중할 만하고 범위를 지키는 태도이기도 하다.

그런데 그 셋이 사람들이 문서 도구에 지불하는 이유의 대부분이다.
노트북과 휴대폰에서 같은 파일을 보는 것, 링크 하나로 남에게 보내는 것이
Dropbox와 Google Drive의 사용 시간을 채우는 동작이다.
그것을 하지 않겠다고 하면 Docbank는 기존 도구의 대체재가 아니라 추가 시스템이 된다.

그래서 “Your documents. Your agents. One system.”이라는 표어와 어긋난다.
하나의 시스템이라고 말하지만 실제로는 두 개를 운영해야 한다 —
동기화가 필요한 작업 문서는 여전히 클라우드 드라이브에 있고,
보존이 필요한 기록은 Docbank에 있다.
그리고 무엇을 어느 쪽에 둘지 결정하는 일에 대한 도움이 제품 안에 없다.

경계를 그은 것이 잘못이라는 뜻은 아니다.
동기화는 어렵고, 아카이브와 동기화를 함께 하려던 제품들이 대체로 둘 다 못했다.
다만 표어가 그 선택을 감춘다 —
“One system”이 아니라 “기록용 한 시스템”이 실제 약속이고,
그 차이가 첫 화면에 있어야 한다.

### 자기주권을 표방하면서 암호화하지 않고, 그 사실이 하위 절에만 있다

첫 화면의 정체성은 자기주권형 문서 시스템이고,
클라우드 드라이브가 계정 접근과 사업자 정책을 아카이브의 권위로 만든다는 비판이 그 근거다.
그 비판은 정당하다.

그런데 배포와 신뢰 경계 절에 문장 하나가 있다 —
설정된 파일시스템과 S3 호환 스토어의 콘텐츠를 검증하지만 암호화하지는 않으며,
그 네임스페이스는 소유자 접근 제어와 운영자에 맞는 저장 암호화로 보호하라는 것이다.
즉 물리 바이트를 외부 스토어에 두면 그 운영자가 내용을 읽을 수 있고,
그 문제는 사용자가 다른 수단으로 해결해야 한다.

이 조합에서 자기주권의 범위가 좁아진다.
주권이 미치는 것은 카탈로그이고 — 문서 ID와 버전과 이력은 로컬에 있다 —
바이트에는 미치지 않는다.
클라우드 드라이브 비판의 핵심 중 하나가 사업자가 내용을 본다는 것이었으므로,
같은 축에서 이 제품이 개선한 것은 정책 의존성이지 기밀성이 아니다.

배치도 문제다.
암호화하지 않는다는 사실은 제품 선택에 직접 영향을 주는 정보인데
소개나 기능 표가 아니라 신뢰 경계 절에 있다.
반대로 “검증”이라는 단어는 기능 표의 일곱 행 중 네 행에 나온다.
검증과 암호화는 다른 보장이며, 전자가 반복되고 후자가 한 번 언급되면
읽는 사람은 둘 다 있다고 짐작하게 된다.

### 알파 경고와 제품의 핵심 약속이 서로를 상쇄한다

README 최상단의 경고는 두 가지를 요구한다 —
대체 불가능한 자료는 독립적인 사본을 따로 두고, 백업을 검증한 뒤에 의존하라는 것이다.
정직한 문장이고 알파 소프트웨어에 적절한 태도다.

그런데 이 제품이 파는 것이 바로 그 둘이다.
기능 표의 “복구 증명” 행이 인크리멘탈 스냅숏과 완전한 콘텐츠 검증과 토폴로지 독립 복원이고,
`docbank backup verify`가 CLI의 네 단계 중 하나다.
검증된 백업을 제공하는 시스템이 사용자에게 시스템 밖에서 백업을 검증하라고 요구하면,
현재 버전은 대체 불가능한 자료의 기록 시스템일 수 없다.
표어가 약속한 일을 아직 못 한다는 뜻이며, 그 사실이 경고문 안에 들어 있다.

릴리스 속도가 이 판단을 뒷받침한다.
한 달 사이에 v0.9.0에서 v0.13.0까지 다섯 번 올라갔고,
저장소는 6주 전에 만들어졌다.
빠르게 움직이는 것 자체는 좋은 신호인데, 보존을 파는 제품에서는 양면이다 —
저장 형식과 백업 형식이 아직 굳지 않았을 가능성이 함께 커진다.
그리고 그 위험을 판정할 정보, 즉 형식 안정성에 대한 언급이 README에 없다.

정직함을 유지하면서 이 긴장을 줄일 방법이 있다.
어느 기능이 알파이고 어느 기능이 굳었는지를 나누어 표시하는 것이며,
특히 백업 저장소 형식의 하위 호환 정책을 한 줄로 적어 두는 것이다.
“대체 불가능한 자료는 아직 맡기지 말라”와 “복구를 증명한다”가
같은 문서에 아무 구분 없이 함께 있는 지금이 가장 읽기 어려운 상태다.

### 기능 어휘가 이미 모델을 가진 사람에게만 통한다

이 프로젝트의 문서 밀도는 규모에 비해 매우 높다.
README가 링크하는 문서가 열네 개이고, 모든 공개 페이지가 마크다운으로도 발행되며,
OpenAPI 스펙과 아키텍처 개요와 CLI 참조가 따로 있다.
6주 된 저장소의 상태로는 이례적이고, 그 자체는 강점이다.

문제는 표현이다.
기능 표의 한 행이 “미리보기 우선 감사 범위, 고정 보존, 독립적으로 재생되는 증거”이고
다른 행이 “다중 스토어 배치와 수리·구제·이전”이다.
“토폴로지 독립 복원”도 같은 성격이다.
전부 정확한 표현으로 보이지만, 그 정확성이 작동하려면 독자가 이미
이 시스템의 개념 모델을 갖고 있어야 한다.

이 문제가 실제 손해를 만드는 지점은 채택 결정이다.
처음 온 사람이 답해야 하는 질문은 “내 어떤 문제가 이걸로 풀리는가”인데,
README에는 그 문제를 가진 구체적인 사람이 나오지 않는다.
경로가 장기 식별자로 빈약하다는 관찰이 있지만,
그 빈약함이 실제로 무엇을 망가뜨렸는지에 대한 장면이 없다 —
이름을 바꿨더니 무엇이 끊어졌고, 그때 무엇을 잃었는지가 없다.

비교 대상이 가까이 있다.
[Hubble.md](hubble.md)는 만든 사람의 동기를 먼저 말하고 그것으로 설계를 설명했다.
Docbank는 설계를 먼저 말하고 동기를 생략했다.
`msgvault`와 함께 개인 데이터 도구 가족을 만들고 있다는 마지막 문단이
그 동기에 가장 가까운데, 그 문단이 라이선스 바로 위에 있다.

## 인사이트

### 에이전트 시대의 파일 문제는 저장이 아니라 참조 안정성이다

에이전트에게 파일을 다루게 하는 도구는 대체로 경로를 건넨다.
그 경로는 한 턴 안에서는 잘 작동하고, 세션을 넘기면 무너진다 —
사람이 폴더를 정리하거나 이름을 바꾸는 순간 에이전트가 들고 있던 참조가 다른 것을 가리키거나
아무것도 가리키지 않게 된다.

이 문제가 지금 드러나는 이유는 개인 문서 계층에 동시 기록자가 처음 생겼기 때문이다.
그전까지 내 문서 폴더의 기록자는 나 한 명이었고,
경로 기반 참조로 충분했던 것은 정리와 편집을 같은 사람이 순차적으로 했기 때문이다.
에이전트가 들어오면 그 전제가 깨지고, 데이터베이스가 수십 년 전에 마주한 문제가
파일 계층에서 다시 나타난다.

Docbank가 낸 답 — 안정적 노드 ID와 `If-Match` 리비전 — 은 그래서 새 발명이 아니다.
HTTP의 ETag와 관계형 데이터베이스의 낙관적 잠금이 같은 형태이고,
새로운 것은 그것이 개인 문서 도구의 필수 요소가 되었다는 사실이다.

여기서 예측이 하나 나온다.
파일을 다루는 MCP 서버와 에이전트 도구가 리비전 사전조건 없이 쓰기를 허용하는 동안,
가장 발견하기 어려운 부류의 버그가 계속 생긴다 —
문서가 조용히 이전 상태로 되돌아가고 아무도 그것을 오류로 보지 않는 종류다.
로그에는 성공만 남고, 사용자는 몇 주 뒤에 내용이 사라진 것을 발견한다.
그 계층에 사전조건을 넣는 것이 곧 기본 요구사항이 될 것으로 보인다.

### 로컬 우선 도구의 진짜 경쟁자는 클라우드가 아니라 폴더 하나다

이 범주의 제품들은 대체로 클라우드에 져서 사라진 것이 아니다.
평범한 디렉터리에 졌다.
Evernote와 DEVONthink와 여러 문서 관리 도구가 같은 자리에서 밀렸고,
이유는 폴더의 도입 비용이 0이고 탈출 비용도 0이기 때문이다.

Docbank의 답은 자기 금고가 폴더가 아니라는 것이다 —
데몬이 권위이고, `docbank.db`를 열지 말라고 명시하고,
파일시스템 배치에서 내용을 추론하지 말라고 요구한다.
그 요구가 이 시스템의 보장을 가능하게 하는 조건이고,
동시에 탈출 비용을 만드는 조건이다.

살아남은 도구들이 어떻게 했는지를 보면 갈림길이 보인다.
Git은 오브젝트가 해시로 이름 붙은 파일이고 최악의 경우 손으로도 읽을 수 있다.
Obsidian은 저장소가 그냥 마크다운 디렉터리다.
반면 자체 데이터베이스만이 해석할 수 있는 저장 형식을 요구한 도구들은
그 데이터베이스와 함께 사라졌다.

Docbank는 두 성질을 함께 갖고 있다 — SHA-256으로 이름 붙은 블롭과 팩은 Git의 모양이고,
카탈로그는 SQLite 데이터베이스다.
그래서 남는 질문이 구체적이다.
10년 뒤에 블롭 디렉터리만 남은 사람이 카탈로그를 재구성할 수 있는가.
README의 백업 절이 이 질문에 조건부로 답한다 —
데이터베이스와 주 블롭 디렉터리의 정지 사본은
보존된 모든 블롭이 여전히 주 권위를 가질 때에만 완전하다는 것이다.
조건이 붙은 완전성은 보장이 아니며, 그 조건을 없애는 것이
이 제품의 장기 신뢰에서 가장 값이 나가는 작업으로 보인다.

### 감사 이력을 선택 기능으로 둔 것이 이 제품의 시장을 갈라 놓는다

기능 표에서 가장 어려운 어휘가 몰린 행이 영구 기록 보존이다 —
미리보기 우선 감사 범위, 고정 보존, 독립적으로 재생되는 증거다.
그리고 소개는 이것을 “선택적” 영구 감사 이력이라고 부른다.

선택적이라는 단어가 두 종류의 사용자를 동시에 겨냥한다는 뜻이다.
개인은 감사 이력이 필요 없고, 규제 산업의 조직은 그것 없이는 쓸 수 없다.
그래서 이 기능은 조직 쪽을 향한 설계이며, 설계 난도가 가장 높은 부분이 그쪽에 배치되어 있다.

그런데 조직은 지금 이것을 살 수 없다.
알파 소프트웨어이고, 보조 스토어를 암호화하지 않으며,
백업을 시스템 밖에서 검증하라고 안내한다 —
규제 대응 조직의 조달 요건에서 셋 다 통과하지 못한다.
반대로 오늘 채택할 수 있는 사용자, 즉 에이전트를 쓰는 개인에게 필요한 것은
안정적 ID와 버전과 휴지통 정도이며 감사 범위는 쓰지 않는다.

이 배분이 로드맵 위험이다.
가장 어려운 기능이 아직 오지 못하는 구매자를 향해 있고,
올 수 있는 구매자를 붙잡는 기능은 상대적으로 단순하다.
그리고 `msgvault`와 함께 개인 데이터 도구 가족을 만든다는 마지막 문단은
실제 계획이 개인 쪽 베팅임을 시사한다 — 두 신호가 서로 다른 방향을 가리킨다.
어느 쪽인지 정하면 문서의 어휘부터 달라질 수 있다.

### 문서를 기계 판독 채널로 함께 발행하는 것이 새 경쟁 지점이 된다

모든 공개 페이지를 `/foo.md`로도 내는 결정과
`docbank openapi --json`으로 기능 목록을 노출하는 결정은 사소한 편의로 보인다.
그런데 이 둘이 향하는 독자가 사람이 아니다 —
문서 인터페이스 표의 용도 칸에 “HTML 긁기 없는 컨텍스트 조회”라고 적혀 있다.

이 선택의 값은 도구를 고르는 과정이 바뀌는 데서 나온다.
어떤 문서 시스템을 쓸지 사람이 비교 글을 읽고 정하는 대신
에이전트가 후보들의 기능 목록을 받아 와 요구사항과 맞춰 보는 방식이 늘어나면,
읽기 쉬운 기계 채널을 가진 쪽이 후보에 남는다.
문서가 마케팅 표면에서 API로 성격이 바뀌는 것이며,
그 전환에서 잃을 것이 거의 없다는 점이 이 결정을 값싸게 만든다.

같은 축의 반대편 선택이 최근에 있었다.
[Danzly는 약관에 봇과 스크립트와 API 접근을 금지하고 AI 학습을 서면 허가 사항으로 두었다](danzly.md) —
자기 데이터가 자산이므로 기계 채널을 닫는 판단이다.
[별 13,235개를 받은 노트 저장소는 그 채널을 열어 둘 근거를 적지 않아
스킬로 만들려는 사람을 멈춰 세웠다](../architecture/system-design-notes.md).
Docbank는 세 번째 자리에 있다 — 기계 채널을 의도적으로, 조건과 함께 열었다.

그리고 조건이 있다는 점이 핵심이다.
문서와 OpenAPI는 열어 두면서 `docbank.db` 직접 접근은 금지하고,
접근 경로를 인증된 데몬 계약 하나로 모았다.
기계에게 문을 열되 어느 문인지 지정한 것이며,
이 조합 — 발견은 쉽게, 접근은 좁게 — 이
에이전트를 상대하는 제품의 기본 자세가 될 것으로 보인다.
