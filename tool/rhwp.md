# rhwp: Rust와 WebAssembly로 만든 오픈소스 HWP 뷰어와 에디터

<https://github.com/edwardkim/rhwp>

GN 토론: <https://news.hada.io/topic?id=28473>

GN 토론: <https://news.hada.io/topic?id=28906>

## 소개

rhwp는 HWP와 HWPX 파일을 어디서든 열고 고치게 하려는 오픈소스 프로젝트다.
Rust와 WebAssembly로 작성했고 라이선스는 MIT다.
2026년 3월 27일에 저장소가 만들어졌고, 저장소 설명은 Rust와 wasm으로 만든
아래한글 viewer와 editor다.
README는 알(R), 모두의 한글이라는 이름 뜻과 All HWP, Open for Everyone이라는
문구로 목표를 내세운다.

README의 로드맵에 따르면 현재는 v0.8.7을 거쳐 v1.0 조판 엔진 체계화를 중심으로
작업하고 있고, 40명이 넘는 외부 기여자와 공동 유지보수자 두 명이 v2.0 협업
기반을 함께 키우고 있다.
배포 형태는 Chrome, Edge, Firefox 확장, VS Code 확장, 온라인 데모, npm 패키지,
CLI와 MCP 서버를 갖춘 릴리스 바이너리다.
고지 문구는 한글과컴퓨터의 공개 문서를 참고해 개발했으며 한글과컴퓨터와 제휴나
후원 관계가 없다는 점을 밝힌다.

## 기능

### 파싱과 렌더링

파서는 HWP 5.0 바이너리(OLE2 복합 파일), HWPX, 제한 지원하는 HML(HWPML
2.9/2.91)을 읽는다.
구역, 문단, 표, 글상자, 이미지, 수식, 차트, 머리말과 꼬리말, 바탕쪽, 각주와
미주를 다룬다.
렌더링은 문단 배치와 표 셀 병합, 다단, 문단 번호, 세로쓰기, 개체 배치를
지원하고, 수식은 분수, 행렬, 적분 같은 큰 연산자와 100개가 넘는 수학 기호를
포함한다.
README는 HML이 실제 corpus로 확인된 구조만 제한 지원하며, 보존할 수 없는 요소가
있으면 경고하고 손실 저장을 차단한다고 적는다.

### 출력과 렌더러

출력은 SVG, PNG(`native-skia` 빌드), PDF이고, 웹에서는 Canvas로 그린다.
저장은 HWP 편집 저장, HWPX와 HML의 의미 보존 저장, HWPX에서 HWP로의 변환 경로를
갖는다.
공통 중간 표현(`PageRenderTree`에서 `PageLayerTree`)을 두고 SVG, Canvas2D,
CanvasKit, native Skia를 백엔드로 연결한다.
기본 요청은 호환 경로인 Canvas2D이고, `?renderer=auto`일 때만 문서 사전 검사를
통과한 문서를 CanvasKit으로 고정한다.

### 웹 에디터와 hwpctl 호환 레이어

웹 에디터는 텍스트 편집, 서식 대화상자, 표 생성과 행과 열 편집, 셀 수식을
지원한다.
한컴 웹기안기 호환을 위한 hwpctl API 계층이 있고 30개 액션과 필드 API를
제공한다.

## 사용하기

### 웹에 임베드

```bash
npm install @rhwp/editor   # 완전한 에디터 UI (iframe)
npm install @rhwp/core     # WASM 파서/렌더러 API
```

```html
<div id="editor" style="width:100%; height:100vh;"></div>
<script type="module">
  import { createEditor } from '@rhwp/editor';
  const editor = await createEditor('#editor');
</script>
```

`@rhwp/core`를 직접 쓸 때는 글자 폭을 재는 `measureTextWidth` 함수를 호스트가
제공해야 한다.

### CLI

```bash
rhwp export-svg sample.hwp -o out/            # SVG 내보내기
rhwp export-pdf sample.hwp -o out.pdf         # PDF (바이트 재현 가능)
rhwp dump sample.hwp -s 2 -p 45               # 구역 2의 문단 45 중간 표현
rhwp info sample.hwp                          # 크기, 버전, 구역, 글꼴
rhwp capabilities                             # 전 명령의 기계 판독 계약
```

릴리스에는 linux x86_64, macOS(x86_64/aarch64), windows x86_64 바이너리와 무결성
검증용 `SHA256SUMS.txt`가 붙는다.

### MCP 서버

```json
{ "mcpServers": { "rhwp": { "command": "rhwp", "args": ["mcp-serve"] } } }
```

`hwp_info`로 문서 규모를 파악하고 `hwp_search`로 위치를 찾고 `hwp_fill_fields`로
누름틀을 채운다.
큰 문서는 `hwp_open`과 `hwp_doc_*` 세션 도구로 다시 파싱하지 않고 반복 조회하고
편집한다.

## 개발 방식

README는 이 프로젝트가 Claude Code를 페어 프로그래머로 쓰지만 바이브 코딩이
아니라고 선언한다.
사람인 작업지시자가 방향과 아키텍처 결정을 소유하고, 계획서를 쓰고 승인한 다음
구현하며, 3,400개 이상의 테스트와 Clippy, CI, 코드 리뷰를 품질 관문으로 둔다.
`mydocs/` 디렉터리에 일일 작업 기록, 구현 계획서, 리뷰 피드백, 기술 문서가 1만
개가 넘는 파일로 쌓여 있다고 하고, 이를 Hyper-Waterfall 방법론이라 부른다.
작업은 GitHub Issue 번호를 브랜치 이름(`local/task{N}`)과 커밋
메시지(`Task #1: 내용`)에 쓰고, 기여 PR의 대상은 `main`이 아니라 `devel`이다.

## 분석

### 닫힌 포맷에 대한 역공학이 지속 가능한 형태가 된 사례다

HWP는 한 회사가 사실상 독점해 온 문서 포맷이고, rhwp의 가치는 뷰어 하나가 아니라
파서, 조판, 저장, 호환 API를 같은 엔진에서 제공하는 데 있다.
README는 한컴 PDF가 정답지가 아니라고 분명히 적는다.
한컴 도구와 버전, 출력 경로에 따라 PDF 결과가 다르므로 어느 출력이 기준인지가
환경 의존적이라는 설명이다.
이 문장은 조판 충실도를 어떻게 검증해야 하는지가 이 프로젝트에서 가장 어려운
문제임을 보여 준다.
이는 이 문서의 해석이다.

### 하나의 엔진이 여러 배포 형태로 퍼지는 구조다

같은 Rust 코어가 WASM으로 컴파일되어 브라우저 확장, VS Code 확장, 임베드용 npm
패키지, CLI와 MCP 서버로 나간다.
GeekNews에는 이 엔진을 쓰는 다른 프로젝트들(HOP, Slack 연동, 안드로이드 앱 등)이
별도 토픽으로 올라와 있다.
이 중 HOP은 이 저장소의 `tool/hop.md`에서 다루는 별개의 프로젝트다.
엔진을 라이브러리처럼 떼어 쓰게 만든 것이 확산의 조건이었다고 읽힌다.
이는 이 문서의 해석이다.

### 개발 과정 자체를 공개 자산으로 내놓는다

`mydocs/`를 코드가 아니라 AI로 소프트웨어를 만드는 방법에 대한 문서라고
자리매김한 것은 이 저장소가 제품이면서 방법론의 증거물이라는 뜻이다.
README의 비교표는 바이브 코딩과 이 프로젝트를 사람의 역할, 계획, 품질 관문,
디버깅, 아키텍처, 문서로 나누어 대비한다.

## 비평

### 이 프로젝트가 한컴 문서와 얼마나 같은지의 척도가 README에 없다

README는 수치로 3,400개 테스트, 40명 이상의 기여자, 450K 이상 라인, 1만 개
이상의 문서를 제시한다.
그러나 실제 한컴 문서 묶음에서 렌더링이 몇 퍼센트나 일치하는지, 어떤 문서가
깨지는지는 보이지 않는다.
테스트 수는 신뢰의 간접 지표일 뿐 충실도의 직접 지표가 아니다.
시각 회귀 CI가 있다고 하지만 기준 이미지를 무엇으로 삼는지가 README에서 확인되지
않는다.

### 바이브 코딩이 아니라는 선언은 증명이 아니라 주장이다

사람이 생각을 멈추지 않는다는 문장은 프로세스의 의도를 설명할 뿐이다.
450K 이상 라인 가운데 사람이 직접 읽고 이해한 비율이나 AI가 쓴 비율은 README에
없다.
문서와 계획서의 양이 많다는 사실은 프로세스가 있다는 증거이지, 각 결정이
옳았다는 증거는 아니다.

### 상표와 포맷 사양의 법적 경계는 사용자가 가늠해야 한다

README는 공개 문서를 참고했고 상표는 한컴의 것이며 제휴가 없다고 밝히지만, Legal
FAQ는 위키로 넘긴다.
공공기관이 이 도구를 업무 표준으로 쓸 때의 위험이나 한컴 쪽 정책 변화의 영향은
README에서 다루지 않는다.
이 문서는 위키를 열지 않았다.

### 에이전트 쓰기 권한이 큰 도구를 한 줄 설정으로 건넨다

`hwp_fill_fields` 같은 쓰기 도구가 MCP로 노출되고, 설정은 한 줄이다.
에이전트가 서식을 채우고 저장하는 동작에 대한 승인과 되돌리기의 방침은 README에
보이지 않는다.
HML 저장에서 손실을 차단한다는 설계와 달리 에이전트 호출에 대한 방침은 별도로
확인해야 한다.

## 인사이트

### 문서 포맷의 개방은 뷰어가 아니라 에이전트가 읽을 수 있느냐로 평가받는다

HWP를 읽고 채우는 MCP 서버를 처음부터 내장했다는 것은 이 프로젝트가 사람용
뷰어와 에이전트용 도구를 같은 엔진의 두 얼굴로 본다는 뜻이다.
행정과 공공 문서가 HWP 중심인 환경에서는 에이전트가 쓸 수 있는 도구가 없으면
자동화가 막힌다.
이는 이 문서의 해석이다.

### 조판 충실도는 끝이 없는 문제여서 기준 설정이 제품의 핵심이 된다

기준이 한컴의 어느 출력인지 정할 수 없다는 점이 이 프로젝트의 장기 과제다.
기여자가 늘수록 서로 다른 환경의 샘플이 들어오고, 그 샘플이 사실상의 사양서를
만든다.
이는 이 문서의 해석이다.

### 방법론 문서가 쌓이는 속도는 코드가 쌓이는 속도와 같은 숙제를 만든다

1만 개 이상의 문서가 쌓이면 문서 자체가 탐색해야 하는 코드베이스가 된다.
README가 capability 카탈로그와 에이전트 실패 사전을 따로 만든 것은 이 문제를
의식한 대응으로 읽힌다.
이는 이 문서의 해석이다.

### 이 글을 읽는 방법

이 문서는 README와 GeekNews의 두 토픽 및 댓글을 읽었고 `mydocs/`, 위키, 로드맵
문서, 실제 렌더링 결과는 열지 않았다.
HN에는 이 저장소 주소의 스레드가 없었고, Lobste.rs에서는 2026년 6월 12일 이후
430개 이야기를 훑었으나 스레드를 찾지 못했다.
GeekNews 28473의 댓글 세 개는 모두 짧은 호평이어서 별도 사실로 쓸 만한 정보는
없었다.

주장을 가를 관찰은 두 가지다.
하나는 실제 업무용 HWP 문서 묶음을 한컴 도구와 rhwp로 각각 렌더링해 쪽 수와 줄
바꿈 위치가 일치하는 비율이다.
다른 하나는 코드 변경 가운데 사람이 직접 작성하거나 수정한 비율이다.
앞의 것이 있으면 조판 충실도를, 뒤의 것이 있으면 개발 방식 주장의 크기를 알 수
있다.
