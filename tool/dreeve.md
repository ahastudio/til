# Dreeve: 스포츠·피트니스 데이터를 위한 자체 호스팅 대시보드

<https://github.com/dreeveapp/dreeve>

HN 토론: <https://news.ycombinator.com/item?id=49101030> (18점, 3개 댓글)

## 소개

Dreeve는 스포츠·피트니스 데이터를 위한 자체 호스팅 오픈소스 대시보드다.
이전 이름은 Statistics for Strava였다.
PHP(Symfony)로 작성되었고 AGPL-3.0 라이선스이며 별 2.1천 개를 받았다.
이름 Dreeve는 서플랑드르 방언에서 왔는데,
양옆으로 나무가 늘어선 시골길을 뜻하며
자전거를 타거나 달리는 사람이 선호하는 길을 가리킨다.

핵심 기능은 활동 데이터의 수집과 시각화다.
FIT/TCX/GPX 파일이나 Strava 연동으로 활동을 가져오고,
브라우저 기반 관리 패널에서 활동과 장비를 관리한다.
통계와 차트가 담긴 대시보드를 보고,
장비 추적과 통근 플래그를 위한 자동화 규칙을 설정한다.

상세 기능으로는 상세 활동 목록과 월별 통계 열람,
장비 사용량과 정비 추적, 구간(segment) 이력과 기록 조회,
활동 위치의 히트맵 생성, 업적 타임라인과 Strava 챌린지 진행 조회,
활동 사진 아카이브 접근이 있다.
AI 기반 운동 추천, 공유 가능한 사용자 배지 생성,
프로그레시브 웹 앱(PWA) 기능도 제공한다.

배포는 Docker 구성을 포함하며,
Symfony 프레임워크 구성 요소, webpack 번들링,
PHPUnit과 codecov 통합을 통한 테스트 인프라를 갖추고 있다.

## 분석

### 이 프로젝트의 핵심은 데이터 소유권의 회복이다

Dreeve의 존재 이유는 Strava가 보여 주는 것을 대체하는 것이 아니라,
사용자가 자기 운동 데이터를 자기 서버에 두게 하는 것이다.
Strava 같은 상용 서비스는 데이터를 자기 클라우드에 가두고
고급 통계를 유료 구독 뒤에 둔다.
Dreeve는 같은 데이터를 로컬에서 소유하며
통계·히트맵·구간 분석을 무료로 제공한다.

이 지향이 중요한 이유는 피트니스 데이터의 민감성 때문이다.
운동 기록은 사용자의 위치 이력, 생활 패턴, 건강 상태를 담는다.
히트맵 하나가 집과 직장의 위치, 주로 다니는 경로를 드러낸다.
이 데이터를 상용 서비스에 맡기는 것은
그 정보를 제3자의 서버와 정책에 위임하는 것이다.
Dreeve의 자체 호스팅은 이 위임을 되돌린다.

FIT/TCX/GPX라는 표준 포맷을 직접 가져오게 한 설계가 이 지향을 뒷받침한다.
Strava 연동에만 의존하지 않고 원시 파일을 수집할 수 있으므로,
사용자는 특정 플랫폼에 묶이지 않고
여러 기기와 서비스의 데이터를 한곳에 모을 수 있다.
HN에서 ashenke가 Garmin Connect 데이터도 가져오는지,
모든 운동 데이터를 로컬에 보관하고 싶다고 물은 것은[^ashenke]
바로 이 데이터 소유권 욕구가 실제 사용자에게 있음을 보여 준다.

### 이름을 바꾼 결정이 프로젝트의 방향을 드러낸다

Statistics for Strava에서 Dreeve로의 개명은 단순한 브랜딩이 아니다.
원래 이름은 Strava에 종속된 부가 도구임을 드러냈다.
새 이름은 Strava를 지우고 독립적 정체성을 취한다.
이것은 프로젝트가 Strava의 보완재에서
독립적 피트니스 데이터 플랫폼으로 자기를 재정의하려는 신호다.

이 재정의가 중요한 이유는 지속 가능성과 직결되기 때문이다.
특정 상용 API에 이름과 정체성을 건 프로젝트는
그 API가 정책을 바꾸면 존립이 흔들린다.
Strava는 실제로 서드파티 API 접근을 여러 차례 제한해 왔다.
Dreeve가 이름에서 Strava를 떼고
FIT/TCX/GPX 직접 수집을 전면에 둔 것은
단일 플랫폼 의존의 위험을 줄이려는 방어적 선택이다.

AGPL-3.0을 택한 것도 같은 맥락에서 읽힌다.
AGPL은 네트워크 서비스로 배포할 때도 소스 공개를 요구하는 강한 카피레프트다.
이는 누군가 Dreeve를 상용 SaaS로 포장해
오픈소스 기여를 되돌리지 않고 가져가는 것을 막는다.
데이터 소유권을 지향하는 프로젝트가
코드 소유권 구조에서도 일관된 선택을 한 것이다.

## 비평

### AI 운동 추천은 이 프로젝트의 정체성과 어긋난다

기능 목록에 포함된 AI 기반 운동 추천은
Dreeve의 자체 호스팅·데이터 소유권 지향과 긴장을 일으킨다.
AI 추천이 로컬 모델로 동작하는지,
아니면 외부 API에 데이터를 보내는지가 명시되지 않았다.
후자라면, 데이터를 로컬에 두려고 자체 호스팅을 택한 사용자가
가장 민감한 운동 데이터를 다시 외부 AI 서비스에 흘리게 된다.

이 모순이 중요한 이유는 프로젝트의 핵심 약속을 침식하기 때문이다.
사용자가 Strava를 떠나 Dreeve로 온 이유가 데이터 통제라면,
AI 추천이 그 데이터를 외부로 보내는 순간
Strava에 맡기던 것과 무엇이 다른지 불분명해진다.
자체 호스팅 프로젝트가 AI 기능을 넣을 때는
데이터 흐름을 명시적으로 밝히는 것이 신뢰의 조건인데,
README는 이를 다루지 않는다.

이것은 많은 오픈소스 프로젝트가 AI 기능을 급히 붙이며 빠지는 함정이다.
기능 목록에 AI를 추가하면 매력적으로 보이지만,
그 프로젝트가 지키려는 가치와 AI의 데이터 요구가 충돌하는지는
따로 검토되지 않는다.
Dreeve처럼 데이터 소유권이 존재 이유인 프로젝트에서
이 검토의 부재는 단순한 기능 문제가 아니라 정체성 문제다.

### PHP·Symfony 선택은 자체 호스팅 장벽을 낮추지만 한계도 있다

Dreeve가 PHP와 Symfony를 택한 것은
자체 호스팅 도구로서 합리적 선택이다.
PHP는 공유 호스팅과 저사양 서버에서 널리 돌아가고,
Docker 구성까지 제공하므로 설치 장벽이 낮다.
이것은 일반 사용자가 자기 서버에 올리기 쉽게 하려는 배려다.

그러나 이 선택에는 명시되지 않은 대가가 있다.
FIT/GPX 같은 대용량 시계열 데이터의 처리,
히트맵과 구간 분석 같은 지리 연산은
PHP 웹 스택에서 성능 부담이 될 수 있다.
활동이 수천 건 쌓인 장기 사용자에게
대시보드 응답성이 어떻게 유지되는지는 README가 말하지 않는다.
HN에서 chriscyber가 훌륭하고 유용하다고 짧게 호평했지만,[^chriscyber]
대규모 데이터에서의 성능은 별점이나 짧은 호평으로 검증되지 않는다.

자체 호스팅 도구의 진짜 시험은 초기 인상이 아니라
데이터가 쌓인 뒤의 유지 부담이다.
장비 정비 추적, 구간 이력, 사진 아카이브까지 기능이 넓은 만큼,
그 모두를 사용자가 자기 서버에서 관리·백업·업그레이드해야 한다.
기능의 풍부함은 장점이지만,
자체 호스팅에서는 그만큼 운영 표면이 넓어진다는 뜻이기도 하다.

## 인사이트

### 자체 호스팅 대시보드는 플랫폼 데이터 락인에 대한 개인의 대응이다

Dreeve가 드러내는 가장 이전 가능한 통찰은
자체 호스팅 도구의 부상이
플랫폼 데이터 락인에 대한 개인 차원의 저항이라는 점이다.
Strava, Garmin, Apple 같은 플랫폼은
사용자 데이터를 자기 생태계에 가두고
그 위에서 구독을 판다.
Dreeve 같은 프로젝트는 그 데이터를 개인의 서버로 되찾아 온다.

이 흐름이 중요한 이유는 소프트웨어 소유 모델의 진자를 보여 주기 때문이다.
지난 10년은 로컬 앱에서 클라우드 SaaS로의 이동이었다.
그러나 구독 피로와 데이터 주권 의식이 커지면서
일부 사용자는 다시 자기 인프라로 돌아온다.
tool 디렉터리의 여러 자체 호스팅 앱 문서가 보여 주듯,
이것은 Dreeve만의 현상이 아니라
개인 데이터를 다루는 도구 전반에서 나타나는 반작용이다.

두 번째 차수의 효과는 이것이 플랫폼의 API 정책을 압박한다는 점이다.
자체 호스팅 대안이 많아질수록,
Strava 같은 플랫폼이 서드파티 접근을 조이면
사용자 이탈의 출구가 열려 있게 된다.
Dreeve가 Strava 연동과 파일 직접 수집을 병행하는 것은
그 출구를 항상 열어 두는 설계이며,
이것이 역으로 플랫폼이 데이터를 완전히 가두기 어렵게 만든다.

### 데이터를 소유하면 그 데이터를 지킬 책임도 함께 온다

Dreeve의 약속, 곧 데이터를 로컬에 두라는 것에는
글이 강조하지 않는 뒷면이 있다.
데이터를 소유하는 순간 그 데이터의 백업·보안·유지가 온전히 개인의 몫이 된다.
Strava가 대신 해 주던 서버 관리, 데이터 이중화, 보안 패치를
이제 사용자가 자기 서버에서 감당해야 한다.

이 이전이 중요한 이유는 데이터 주권의 진짜 비용을 드러내기 때문이다.
운동 데이터는 위치 이력을 담으므로,
자체 호스팅 서버가 잘못 노출되면
그 히트맵과 경로가 그대로 유출된다.
security 디렉터리의 여러 데이터 유출 문서가 보여 주듯,
관리되지 않은 자체 호스팅 인스턴스는
상용 서비스보다 오히려 취약할 수 있다.
데이터를 소유한다는 것은 그것을 지킬 전문성도 요구한다.

이 긴장의 함의는 자체 호스팅이 만능이 아니라 트레이드오프라는 점이다.
데이터 통제를 얻는 대신 운영 책임을 진다.
Dreeve가 Docker 구성으로 설치를 쉽게 한 것은 이 부담을 낮추려는 것이지만,
설치의 용이함과 안전한 장기 운영은 다른 문제다.
자체 호스팅 도구가 진짜 대중화되려면
설치뿐 아니라 백업·보안·업그레이드까지
비전문가가 감당할 수 있게 자동화되어야 하며,
그 지점이 아직 이 분야 전체의 미해결 과제로 남아 있다.

### 니치 오픈소스의 지속성은 창작자의 개인적 필요에 달려 있다

Dreeve는 개발자 자신이 달리거나 자전거를 타는 사람일 때
가장 잘 만들어지는 종류의 도구다.
이름을 서플랑드르 방언의 나무 길에서 따온 것,
통근 플래그와 장비 정비 추적 같은 세밀한 기능은
실제로 이 활동을 하는 사람만이 필요를 아는 것들이다.

이 관찰이 새로운 프레임을 주는 이유는
니치 오픈소스의 지속성을 설명하기 때문이다.
상용 서비스는 시장이 충분히 크지 않으면 그 니치를 방치하거나 철수한다.
그러나 개발자 자신이 사용자인 오픈소스는
시장 규모와 무관하게 창작자의 개인적 필요가 유지되는 한 지속된다.
Statistics for Strava에서 Dreeve로 여러 해에 걸쳐 진화하며
별 2.1천 개를 모은 것은 이 스크래치-유어-온-이치 동력의 증거다.

세 번째 차수의 효과는 이런 도구가 상용 서비스의 사각지대를 메운다는 점이다.
Strava가 모든 사용자를 위한 평균적 기능에 집중하는 동안,
Dreeve는 데이터에 집착하는 소수를 위한 깊은 기능을 판다.
플랫폼이 넓고 얕게 가면,
개인 오픈소스는 좁고 깊게 간다.
이 분업은 니치 사용자에게는 축복이지만,
동시에 그 도구의 운명이 한 창작자의 지속적 관심에 묶여 있다는
취약성도 함께 안고 있다.
