# 알한글(Alhangeul)은 rhwp 엔진을 수정하지 않고 Tauri로 감싼 Windows·Linux용 HWP/HWPX 편집기이다

<https://github.com/postmelee/alhangeul-tauri>

<https://postmelee.github.io/alhangeul-tauri/>

## 소개

알한글(Alhangeul)은 Windows와 Linux에서 HWP와 HWPX 문서를 열고 편집하고 저장하는
오픈소스 데스크톱 앱이다.
저장소 이름은 `alhangeul-tauri`이고 MIT 라이선스이다.
2026년 7월 19일에 만들어졌고, 이 문서가 읽은 2026년 11월 12일에는 별 3개와
포크 0개였다.
릴리스는 2026년 9월 30일의 v0.1.0부터 2026년 11월 11일의 v0.1.3까지
네 번 나왔다.

공식 사이트는 한글 파일이 더는 낯선 문서가 아니라는 문구로 시작하고,
문서를 열고 편집하고 저장하며 탐색기에서 첫 페이지를 미리 볼 수 있다고 소개한다.
첫 화면에는 최신 버전 v0.1.3과 Windows, Linux 탭이 있다.
Windows 탭은 NSIS를 일반 설치로 권장하고, MSI는 조직과 관리 배포용으로 안내한다.
두 형식 모두 앱 안 업데이트를 지원한다고 표시한다.
설치 안내와 변경 내용, 문의와 제보 페이지가 따로 있고,
macOS 사용자를 위한 알한글 for macOS 링크도 있다.[^updates]

기능은 다섯 가지로 요약된다.
HWP와 HWPX 열기, 편집, 저장, 다른 이름으로 저장, 두 형식 사이의 변환 저장이 첫째이다.
편집한 문서를 PDF로 저장하거나 시스템 인쇄로 내보내는 것이 둘째이다.
설치된 글꼴을 감지해 문서에 적용하는 로컬 글꼴이 셋째이다.
파일 연결, 드래그 앤 드롭, 여러 창에서 문서 열기가 넷째이다.
Windows 탐색기와 Linux 파일 관리자에서 문서의 첫 페이지를 썸네일로 보여 주는 것이
다섯째이다.

문서를 읽고 그리는 엔진은 edwardkim/rhwp이다.
알한글은 Tauri 데스크톱 셸과, 파일, 창, 글꼴, 인쇄, 운영체제 통합을 맡는다.
현재 포함된 rhwp는 v0.9.0이다.
같은 소유자의 macOS용 저장소(alhangeul-macos)가 따로 있고, 이 저장소는 로고를
거기서 가져왔다.[^provenance]
이 문서는 앱을 설치하거나 실행하지 않았고, 저장소의 README와 문서만 읽고 썼다.

### 설치 형식

| 운영체제    | 형식        | 안내                                     |
| ----------- | ----------- | ---------------------------------------- |
| Windows x64 | NSIS (.exe) | 일반 설치 권장                           |
| Windows x64 | MSI (.msi)  | 조직·관리 배포, NSIS 썸네일 문제 시 대안 |
| Linux x64   | AppImage    | 실행 권한 부여, 자동 업데이트 지원       |
| Linux x64   | DEB / RPM   | 배포판 패키지, 파일 관리자 썸네일 지원   |
| Linux arm64 | DEB         | 수동 패키지 설치와 업데이트              |

Windows 설치 파일에는 코드 서명(Authenticode)이 없어 보안 경고가 나올 수 있다.
앱 안의 업데이트 확인은 Windows NSIS와 MSI, Linux x64 AppImage에서 쓸 수 있고,
DEB, RPM, arm64는 새 패키지를 받아 수동으로 설치한다.
업데이트가 있어도 자동으로 설치하지 않고, 사용자가 다운로드와 설치를 선택해야 진행한다.
저장하지 않은 문서가 있으면 설치를 막고 먼저 저장하도록 안내한다.[^updates]
Windows에는 WebView2 Runtime이 필요하고, AppImage에는 실행 권한과 파일 및 상위
폴더의 쓰기 권한이 필요하다.[^notes-013]
자동 업데이트에는 Minisign 서명을 쓰며, 이것은 Windows의 Authenticode 코드 서명과
별개라고 릴리스 노트가 밝힌다.[^notes-013]

### 버전별 변경

릴리스 노트는 각 버전을 rhwp에서 온 변화와 앱 자체의 변화로 나누어 적는다.[^notes-013]

v0.1.1(2026년 10월 4일)은 rhwp v0.8.6을 그대로 쓰고 로컬 글꼴 사용 시의 속도를
개선했다.
글꼴 이름과 한글 별칭을 찾을 때 같은 목록을 반복 조회하던 비용을 줄였다.
고정된 Windows VM에서 Canvas2D와 로컬 글꼴을 켠 10쪽 HWPX 문서를 다시 여는 시간의
중앙값이 18.255초에서 0.516초로, 같은 조건의 Linux VM에서는 2.504초에서 0.636초로
줄었다.
공개 문서와 같은 화면 크기로 5회씩 비교한 결과이고, 모든 PC와 문서에서 같은 속도를
보장하지는 않는다고 적는다.[^notes-011]

v0.1.2(2026년 10월 9일)는 rhwp v0.8.7을 반영했다.
문단 안 연속 표의 너비와 줄바꿈, 중첩 표와 행 병합 표의 쪽 분할을 보정했고,
빈 머리말과 꼬리말이 있는 HWP 저장본, 반복 표 제목과 쪽 경계 설정의 저장을 보정했다.
영어 UI, 웹 하이퍼링크 편집, 덮어쓰기 모드, 찾기 결과 개수 표시가 추가되었다.
앱 쪽에서는 새 upstream의 글꼴 공급 API와 기존 로컬 글꼴 선택을 연결하고,
창 제목과 접근성 이름이 제품명을 유지하게 했다.
CanvasKit 표시 모드에서 로컬 글꼴 파일을 지운 뒤 다시 감지하면 쪽이 비어 보이던
문제도 고쳤다.[^notes-012]

v0.1.3(2026년 11월 11일)은 rhwp v0.9.0을 반영했다.
중첩 표가 다음 쪽으로 이어질 때 셀 여백과 줄 배치를 처리하는 방식을 개선했고,
HWP와 HWPX를 저장하고 다시 열 때 표 앞뒤의 본문과 머리말과 꼬리말이 보존되도록
보정했다.
PDF 가져오기에서는 쪽 범위를 정하고 원본 배치와 편집하기 쉬운 배치 중에서 고를 수
있다.
스캔한 글자를 인식하는 OCR은 지원하지 않는다.
앱 쪽에서는 글꼴을 찾을 때 이름과 스타일을 함께 확인하게 했고,
PDF 가져오기와 문서 편집이 같은 엔진 버전을 쓰게 맞췄으며,
컴퓨터에서 글꼴을 지운 뒤 다시 감지해도 남아 있던 문제를 고쳤다.[^notes-013]
세 버전 모두 변경의 대부분이 rhwp에서 온 것이고 앱 자체의 변경은 글꼴, 창 제목,
가져오기 연결 같은 통합 쪽에 모여 있다.
이 관찰은 앞의 구조 설명(엔진은 수정하지 않는다)과 맞는다.

### 저장소가 직접 밝히는 한계

한컴에서 보이는 배치와 달라질 수 있고, 모든 문서와 글꼴과 프린터의 조합을
검증하지는 않았다.
직접 공급하는 로컬 글꼴은 지원하는 정적 TTF와 OTF로 한정되며,
일부 글꼴은 대체 글꼴로 보이고 한컴 전용 글꼴은 제품에 포함하지 않는다.
Windows NSIS 설치에서는 환경에 따라 썸네일이 보이지 않는 문제가 있다.
데스크톱용 별도의 자동 복구 저장소는 없으므로 작업 중에는 자주 저장하라고 안내한다.

### 릴리스 노트가 적은 알려진 한계

v0.1.3 노트는 한계를 여섯 가지로 적는다.
Windows 설치 파일은 Authenticode 서명이 없다.
일부 Windows NSIS 환경에서 탐색기 썸네일이 나오지 않으며, 썸네일이 필요하면 MSI를
쓸 수 있다.
강제 MSI 재설치에서 3010(재부팅 요구)을 관측했고 재부팅 뒤의 동작은 검증하지
않았다.
외부 글꼴이 막히거나 필요한 글꼴이 없으면 다른 글꼴로 보이거나 문서 모양이 달라질 수
있다.
Microsoft Print to PDF로 출력하면 눈으로 보이는 내용은 확인했지만 검색 가능한
텍스트가 없고, 앱의 직접 PDF 내보내기는 한글 검색을 확인했다.
PDF 가져오기의 모든 형식과 배치 옵션, 모든 Wayland와 GPU와 글꼴과 배포판과 물리
프린터 조합은 검증하지 않았고, 암호가 걸린 PDF를 암호로 가져와도 새 문서에 원본
암호가 자동으로 적용되지는 않는다.[^notes-013]
v0.1.2 노트는 이전 버전의 성능 수치를 새 엔진 고정 버전의 측정 결과로 승계하지
않는다고 적는다.[^notes-012]

## 구조

### 엔진은 수정하지 않고 경계만 소유한다

저장소는 세 층으로 나뉜다.
`apps/desktop`은 Tauri 2 셸이고, 파일 시스템, 문서 세션, 저장과 내보내기, 인쇄 창,
파일 연결, 패키징을 맡는다.
`apps/studio-host`는 rhwp의 편집기 UI인 rhwp-studio를 그대로 쓰는 Vite 호스트이고,
Tauri와 이어 주는 어댑터를 둔다.
`third_party/rhwp`는 읽기 전용 submodule이며 알한글 기능을 위해 직접 고치지 않는다.[^upstream]
TypeScript UI는 분명한 bridge API를 호출하고, 파일과 문서 세션과 저장과 인쇄와
운영체제 통합은 Rust가 소유한다는 것이 에이전트 운영 문서의 규칙이다.[^agents]

rhwp 버전은 Stable 릴리스 태그와 그 태그가 가리키는 커밋을 함께 입력해야만
갱신된다.
submodule, 네 개의 native Cargo lock, 같은 커밋에서 새로 만든 번들 WASM,
출처와 산출물의 SHA-256을 기록하는 `rhwp-core.lock`을 한꺼번에 맞춘다.
브랜치나 태그 없는 커밋은 갱신 입력으로 받지 않는다.[^upstream]
`rhwp-core.lock`에는 번들 WASM의 크기(약 26.8MB)와 해시도 적혀 있다.[^lock]

편집기 UI도 복제하지 않는다.
Vite의 실제 루트와 진입점은 `third_party/rhwp/rhwp-studio` 아래이고,
자체 `index.html`, `main.ts`, 툴바, 캔버스, 눈금자, 렌더러 복제본은 허용하지 않는다.
upstream import를 대체하는 별칭은 데스크톱 호스트, 글꼴 정책, 제품 정보에 필요한
12개 leaf 어댑터로 제한된다.
이 경계는 테스트가 지킨다.
별칭이 12개인지, `legacy-upstream-copy`가 0개인지, 금지된 진입점이 없는지,
어댑터가 300줄 상한 안인지를 검사한다.[^upstream]
엔진이나 렌더러의 버그는 먼저 upstream에서 해결하고,
데스크톱 통합 차이만 이 경계 안의 어댑터에 둔다.[^upstream]

이렇게 하는 이유가 문서에 한 가지 구체적으로 나온다.
upstream이 시작할 때 자동으로 만드는 빈 문서는 WASM 안에서만 존재해서 native 저장
세션이 없고, 그래서 저장할 수 없다.
알한글은 Tauri에서 이 자동 생성만 건너뛰고, 파일 메뉴의 새로 만들기가 Rust 세션을
먼저 만들게 했다.[^upstream]

### 썸네일은 셸 프로세스 밖에서 만든다

Windows 탐색기가 `.hwp`와 `.hwpx`의 첫 페이지를 요청하면 작은 COM handler DLL이
응답한다.
문서 파싱과 래스터화는 Shell 프로세스 안에서 실행하지 않는다.
handler는 제한된 스트림에서 문서 바이트를 읽고, 익명 파이프와 Job Object로
별도 worker를 띄운 뒤, 검증한 첫 페이지 BGRA 비트맵을 Shell에 돌려준다.[^win-thumb]
handler DLL에는 렌더 기능이 없고 프로토콜과 한도, process 격리와 비트맵 반환만 있다.
엔진을 DLL에 직접 링크하지 않는다는 뜻이다.[^upstream]

Linux 쪽도 같은 원칙이다.
`apps/linux-thumbnailer`는 Freedesktop의 `%i %o %s` 규약을 따르는 CLI이고,
자식 프로세스 감독, 제한 시간, `RLIMIT_AS`, PNG 게시를 맡는다.
영구 캐시와 무효화는 Nautilus와 Thunar·Tumbler가 소유한다.[^upstream]

### 글꼴은 세 단계 순서로 해석한다

글꼴은 시스템에 설치된 것, 지원하는 파일 기반 글꼴, 알한글이 번들한 대체 글꼴
순서로 찾는다.
번들 글꼴은 오픈 라이선스 대체 글꼴뿐이고, 지원하는 파일 기반 글꼴은 저장소나
배포물에 넣지 않는다.[^fonts]
추가 스캔은 알한글이 정한 제한된 폴더만 허용한다.
Linux는 `~/.local/share/fonts`와 `~/.fonts`이고, Windows는 사용자별 글꼴 폴더이다.
한컴 오피스의 공유 글꼴 폴더는 의도적으로 스캔하지 않는다.[^fonts]
사용 여부 선택은 앱 데이터의 `local-font-preferences.json`에 버전 1 형식으로
선택만 저장하고, 글꼴 목록이나 경로나 바이트는 저장하지 않는다.[^fonts]

PDF 내보내기는 같은 스캔 폴더를 공유하고 마지막 fallback으로 Noto Sans KR과
Noto Serif KR을 쓴다.
텍스트를 PDF에 넣는 변환이 실패하면 같은 SVG를 글자 모양 그대로 변환하는 방식으로
다시 시도하고, 결과에 `outlined-fallback` 표시와 경고를 붙인다.
변환 중에 글자가 사라지거나 `.notdef` 글리프가 남으면 파일을 쓰지 않고 실패한다.[^fonts]

### 릴리스는 기록으로 판정한다

버전별 공개 상태는 GitHub 릴리스와 웹, 업데이트 feed를 실제로 읽어 보고 정한다.
가장 높은 파일 이름이나 현재 소스 버전을 최신 공개 버전으로 취급하지 않는다.
일부 게시가 성공했다는 사실이나 같은 버전에서 업데이트가 없다는 확인만으로
전체 공개와 업그레이드 완료를 선언하지 않는다.[^releases]
릴리스 노트의 사용자 문구는 `v<version>.notes.json` 한 곳이 원문이고,
GitHub 본문과 웹 안내 페이지가 거기서 생성된다.[^releases]
README는 v0.1.0에서 v0.1.1, v0.1.1에서 v0.1.2, v0.1.2에서 v0.1.3으로의 실제
업데이트와 설정 유지, 문서 재열기를 검증했다고 적는다.

### 에이전트가 따르는 하이퍼-워터폴

`AGENTS.md`는 코딩 에이전트(Codex, Claude Code 등)가 따를 하이퍼-워터폴 방법론을
적는다.
새 기능, 버그 수정, 구조 변경은 이슈, 브랜치, 오늘 할 일, 계획서, 구현, 검증,
최종 보고서, PR의 순서를 생략하지 않는다.
소스를 고치기 전에 작업지시자의 승인을 받고,
각 단계가 끝난 뒤에도 승인 없이 다음 단계로 가지 않는다.
이슈 close는 승인 뒤나 PR merge 확인 뒤에만 한다.
파일은 300줄, 함수는 50줄, 매개변수는 5개, 순환 복잡도는 10을 권장 상한으로 둔다.[^agents]
`CLAUDE.md`는 `AGENTS.md`를 그대로 불러오는 한 줄짜리 파일이다.
외부 기여자에게는 이 내부 계획서와 단계 보고서를 요구하지 않는다.[^contributing]

## 개발하기

필요한 것은 Node.js 24, Corepack과 pnpm 10.33.0, Rust stable, 대상 운영체제의
Tauri 2 prerequisites이다.
처음에는 `git submodule update --init --recursive`와 `pnpm install --frozen-lockfile`을
실행하고, 개발 모드는 `pnpm tauri dev`이다.[^development]
어느 호스트에서도 돌릴 수 있는 기본 검증은 `check:product-boundary`,
`check:rhwp-pin`, `check:committed-rhwp`, `test:upstream`, `test:studio`,
`build:studio` 등이다.
Rust 데스크톱 검증과 Tauri 빌드는 Windows와 Linux에서만 한다.[^development]
버그 수정에는 재현을 잡는 검증을 포함하고, PR은 `devel` 브랜치로 연다.
문서 파싱과 배치 문제는 upstream rhwp와 관련될 수 있으므로,
공개해도 되는 문서라면 rhwp 데모와 비교한 결과를 덧붙일 수 있다.[^contributing]

## 분석

### 이 프로젝트의 중심 설계는 엔진이 아니라 경계를 소유하는 것이다

가장 강하게 말하면 알한글은 문서 엔진을 만들지 않고 엔진과 운영체제 사이의
접착면만 소유하는 제품이다.
엔진의 버그는 upstream에서 고치고, 알한글이 고치는 것은 저장 세션, 파일 연결,
글꼴 공급, 인쇄, 썸네일 같은 데스크톱 쪽 차이뿐이다.
이 선택은 문서 파서를 직접 쓰는 비용을 피하는 대신 upstream의 방향에 제품이
묶이는 비용을 받아들인다.
눈에 띄는 것은 이 경계를 선언에 그치지 않고 테스트로 고정한 점이다.
별칭 수, 복제본의 부재, 어댑터 크기가 테스트로 검사되고,
엔진 갱신은 태그와 커밋과 해시 lock을 함께 요구한다.
경계가 문서가 아니라 CI에서 깨지도록 만든 설계이다.

### 운영체제 통합의 위험을 프로세스와 한도로 가둔다

탐색기와 파일 관리자의 썸네일은 사용자가 열지 않은 문서를 셸이 대신 파싱하게
만든다.
알한글은 이 파싱을 셸 프로세스 밖의 별도 worker로 내보내고,
Windows에서는 Job Object와 파이프를, Linux에서는 제한 시간과 `RLIMIT_AS`를 쓴다.
정상 문서는 문제가 없어도 깨진 문서가 셸이나 파일 관리자를 끌고 내려가는 일을
막으려는 설계로 읽힌다.
이것은 문서의 설계 의도를 이 문서가 해석한 것이고, 의도대로 막아 주는지를 실행해서
확인하지는 않았다.

### 검증 기록이 성공과 미검증을 구분한다

릴리스 기록은 부분 성공을 전체 성공으로 쓰지 않는다는 규칙을 반복한다.
Windows 썸네일 문서는 등록 성공이 실제 썸네일 성공을 보장하지 않는다고 적고,
전체 CI가 성공한 것은 제한을 보존하는 검사 계약을 통과했기 때문이지 NSIS 문제가
해결됐기 때문이 아니라고 밝힌다.[^win-thumb]
문제가 풀리지 않은 채로 기록되어 있다는 점이 이 문서들을 신뢰할 근거로 읽힌다.

## 비평

### 첫 화면의 약속인 썸네일이 Windows NSIS 설치에서 아직 되지 않는다

README는 파일 탐색기에서 첫 페이지를 미리 볼 수 있다고 소개하지만,
같은 README가 NSIS 설치에서 환경에 따라 썸네일이 나오지 않는다고 인정한다.
아키텍처 문서에 따르면 격리 검사에서 NSIS의 연결 조회, 직접 COM 생성, JPG
썸네일은 성공했지만 HWP와 HWPX의 Shell과 강제 추출은 `0x80040154`로 실패했고,
MSI 설치는 통과했다.[^win-thumb]
문서는 UAC 값이나 한컴 버전만으로 원인을 단정하지 않고,
MSI 설치를 일괄 권유하지도 않는다고 적는다.
이 검사는 실제 한컴 설치 대신 합성한 등록값을 쓴 CI이므로 일반 Windows 10과 11
탐색기의 보장이 아니라고도 한다.[^win-thumb]
원인이 확정되지 않은 채 저장소가 일반 설치로 권장하는 NSIS가 영향을 받는다는 점이
사용자에게 가장 직접적인 한계이다.

### 편집기인데 데스크톱의 자동 복구가 없다

README는 별도의 데스크톱 자동 복구 저장소가 없으니 자주 저장하라고 안내한다.
개발 문서는 upstream Studio의 브라우저 자동 저장과 복구를 상속하지만
네이티브 복구 저장소는 없다고 적는다.
네이티브 저장에는 외부에서 원본이 바뀌었는지 감지하고 덮어쓰기를 확인하는 기능이
구현되어 있다고도 한다.[^development]
문서 편집기에서 충돌이나 정전 뒤에 작업을 되찾는 기능이 없다는 것은,
사용자가 신뢰하는 서식 문서를 맡기기 전에 알아야 할 위험이다.
이 문서는 상속받은 브라우저 복구가 데스크톱 앱에서 실제로 동작하는지 확인하지
못했다.

### 엔진과 편집기 UI 양쪽이 한 upstream에 기대고 있다

제품의 문서 처리와 편집 화면 둘 다 rhwp와 rhwp-studio를 그대로 쓰므로,
upstream이 멈추거나 방향을 바꾸면 알한글이 대응할 수 있는 폭이 좁다.
엔진을 갱신할 때마다 Windows와 Linux에서 네이티브 테스트, 썸네일 산출물,
설치와 롤백, 탐색기와 파일 관리자의 실제 확인을 반복해야 한다고 문서가 직접
적는다.[^upstream]
이 비용을 소규모 저장소가 계속 감당할 수 있는지가 문제이다.
이 문서는 유지 인원을 확인하지 못했다.
저장소가 3주 정도 된 신생 프로젝트라는 점은 이 비용이 아직 여러 번의 갱신으로
검증되지 않았음을 뜻한다.

### 한컴과 얼마나 같게 보이는지는 수치로 공개되지 않았다

README는 배치가 한컴과 달라질 수 있다고 말하지만, 어느 정도의 문서가 같게
나오는지는 이 문서가 읽은 README와 문서에서 찾지 못했다.
한글 문서는 관공서와 학교의 제출 서식으로 쓰이는 경우가 많아서 배치 차이가 곧
제출 가능 여부로 이어질 수 있다.
저장소의 기준은 수용 환경별 검증 기록이지 사례 모음에 대한 호환 통계가 아니다.
이 지적은 이 문서가 읽은 범위에 한정되고, 다른 곳에 호환 자료가 있을 수 있다.

### 홈페이지가 앞세우는 기능과 권장하는 설치 형식이 어긋난다

공식 사이트의 첫 문구는 탐색기에서 첫 페이지를 미리 볼 수 있다고 약속하고,
같은 화면에서 NSIS를 일반 설치로 권장한다.
그런데 릴리스 노트는 일부 Windows NSIS 환경에서 탐색기 썸네일이 나오지 않으며
썸네일이 필요하면 MSI를 쓰라고 적는다.[^notes-013]
권장 설치 형식과 앞세운 기능이 같은 사이트 안에서 서로 걸리는 셈이다.
설치 안내와 변경 내용 링크를 따라가야 한계를 알 수 있다.
이 어긋남은 이 문서가 읽은 두 페이지의 문구를 비교한 것이다.

### 속도 개선 수치는 새 기능의 이득이 아니라 앞선 느림을 줄인 것이다

v0.1.1의 18.255초에서 0.516초로 줄었다는 수치는 눈에 띄지만,
그 조건이 로컬 글꼴을 켠 Canvas2D의 10쪽 HWPX를 고정된 VM에서 5회씩 잰 중앙값이라는
점을 함께 읽어야 한다.[^notes-011]
설명은 같은 글꼴 목록을 반복 조회하던 비용을 줄였다는 것이므로,
직전 버전이 그 조건에서 그만큼 느렸다는 뜻이기도 하다.
5회라는 표본과 하나의 문서로는 일반화할 수 없고, 노트도 모든 PC와 문서에서의 같은
속도를 보장하지 않는다고 적는다.
이 문서는 이 수치를 재현하지 않았다.

## 인사이트

### 내 문서로 먼저 시험한다

이 앱이 내 업무에 맞는지는 저장소의 안내를 그대로 따라 내 문서로 확인할 수 있다.
README도 중요한 문서는 원본을 보관하고 저장한 결과를 다시 열어 확인하라고 권한다.
이 문서의 제안은 자주 쓰는 서식 열 개쯤을 골라 열기, 편집, 저장, 다시 열기,
PDF 내보내기를 해 보고 쪽 수와 글꼴 대체 여부를 원본과 비교하는 것이다.
한 번이라도 쪽 수나 표가 틀어지면 제출용으로는 한컴에서 최종 확인하는 절차를
남겨 둔다.
이 시험 방법은 이 문서의 제안이고 저장소가 정한 절차가 아니다.

### 설치 형식은 썸네일이 필요한지로 고른다

릴리스 노트의 문구를 그대로 따르면 탐색기 썸네일이 필요한 Windows 사용자는 NSIS보다
MSI를 먼저 시험해 볼 이유가 있다.[^notes-013]
이 문서의 제안은 설치 뒤에 탐색기에서 HWP 파일의 첫 페이지가 보이는지를 한 번
확인하고, 안 보이면 MSI로 바꿔 다시 확인하는 것이다.
MSI 강제 재설치에서 재부팅을 요구한 관측이 있으므로 업무 PC라면 재부팅 시점도
미리 정해 둔다.
이 순서는 이 문서의 제안이다.

### 래퍼 앱을 만든다면 이 경계 설계를 가져올 수 있다

남의 엔진을 감싼 앱을 만든다면 이 저장소에서 세 가지를 가져올 수 있다.
엔진을 읽기 전용 vendor로 두고 태그와 커밋과 해시를 lock 파일에 함께 고정하는 것,
복제본이 생기지 않도록 별칭 수와 어댑터 크기를 테스트로 검사하는 것,
셸이 호출하는 파싱을 별도 프로세스와 자원 한도 안에서 돌리는 것이다.
이 선택은 이 문서의 정리이다.

### 도입 판단을 바꿀 관찰

Windows 사용자는 NSIS 썸네일 문제의 원인이 확정되는지, 그리고 이후 릴리스에서
해결로 기록되는지를 볼 만하다.
rhwp 갱신 뒤의 회귀 기록이 반복해서 깨끗하게 남는지도 함께 본다.
해결되지 않거나 갱신마다 새 회귀가 기록되면 이 앱은 아직 업무용이 아니라
시험용이라는 뜻이다.
자동 복구가 없는 점은 이 앱에서 서식을 오래 편집하는 쓰임을 막는 조건이 될 수 있다.
이 판단 기준도 이 문서의 제안이다.
