# ztd-charts: 한 카드에 한 가지만 말하게 만들고 AI 에이전트가 JSON으로 쓰게 한 React 차트 라이브러리

<https://github.com/Junhan2/ztd-charts>

## 소개

ztd-charts는 React용 애니메이션 차트 36종을 순수 SVG로 그리는 오픈소스
라이브러리다.
저장소는 2026년 11월 5일에 만들어졌고 MIT 라이선스이며,
11월 9일 현재 별은 95개다.
README는 이 라이브러리를 “보고서처럼 읽히는” 차트라고 소개하고,
차트마다 JSON 스펙(spec)이 있어 AI 에이전트가 쓸 수 있다고 설명한다.
npm에는 라이브러리 `ztd-charts`, 명령줄 도구 `ztd-charts-cli`,
MCP 서버 `ztd-charts-mcp` 세 패키지가 0.5.0으로 올라 있다.[^npm]

### 차트 묶음

README가 나누는 일곱 묶음은 다음과 같다.
비율(파이, 도넛, 와플, 마리메코, 분할 막대), 계층(트리맵, 선버스트), 흐름(퍼널,
생키, 코드), 비교(막대, 폭포, 파레토, 레이더, 슬로프, 덤벨, 롤리팝)이다.
추이에는 라인(범위 띠 포함), 영역, 스트림, 스파크라인, 캘린더 히트맵, 범프,
캔들스틱, 스카이라인이 있고, 분포에는 박스(바이올린 포함), 비스웜, 릿지라인,
히스토그램이 있다.
관계(히트맵, 버블, 산점도, 평행 좌표)와 KPI(게이지, 불릿,
방사형 막대)까지 합치면 36종이다.
차트 정의 레지스트리의 항목 수도 이 숫자와 맞는다.

### 내세우는 특징

README의 “왜 ztd charts인가” 절은 여섯 가지를 든다.
카드마다 한 가지만 말하게 하고(강조색은 한 항목에만, 나머지는 무채색,
차트 아래에 굵은 한 줄 요약), 스크롤로 보일 때 그려지고 데이터가 바뀌면
지금 모양에서 이어서 움직이며, 구간을 끌면 그 구간의 변화와 고점,
저점을 읽어 준다.
키보드 조작, 모든 차트의 스크린리더 설명과 데이터 표, 모션 줄이기,
모든 글자의 WCAG AA 대비를 기본으로 제공한다고 한다.
React만 피어 의존성(peer dependency)이고
공통 코어를 쓴 차트 하나가 Brotli로 약 12~24 kB이며, 아주 큰 데이터는 알아서
캔버스로 바꾼다고 한다.
`locale="ko-KR"`로 숫자 표기(1.2만, 3.4억)와 차트 글을 한국어로 바꿀 수 있다.

### AI 에이전트용 기능

차트 하나가 곧 JSON 스펙이라, 같은 차트를 컴포넌트로도 쓰고
`{ type, data, encoding, options }` 형태의 스펙으로도 쓸 수 있다.
스펙에는 공개 JSON Schema가 있고, CLI(`ztd-charts-cli`)는 스펙의 검증,
PNG·SVG·HTML 렌더링, 프로젝트 시작, CSV에서의 차트 추천을 한다.
MCP 서버는 도구 다섯 개를 제공한다.
`list_charts`, `get_chart_schema`, `validate_spec`, `render_chart`,
`suggest_chart`다.
저장소에는 에이전트가 차트 고르기부터 검증된 미리보기까지 따라가는
스킬(`skills/ztd-charts/SKILL.md`)과 라이브러리 전체를 한 파일에 담은
`llms.txt`도 있다.

### MCP 서버의 주소 가져오기 방어

`render_chart`는 데이터를 `{ url }`로 받으면 서버가 그 주소를 가져온다.
이 경로에는 `guard.ts`가 있다.
내부망, 이 컴퓨터, 클라우드 메타데이터에 해당하는 IPv4 대역(10.0.0.0/8,
127.0.0.0/8, 169.254.0.0/16 등)과 IPv6 대역을 막고, IPv4를 품은 IPv6 형태(NAT64,
6to4)도 안에 든 주소로 판단한다.
검사는 연결하는 순간의 주소에 하므로 확인한 뒤 DNS가 다른 주소를 주는
우회(리바인딩)도 막고, 리디렉트는 20번까지 따라가며 매번 같은 검사를 한다.
`ZTD_CHARTS_ALLOW_PRIVATE_URLS=1`을 켜면 이 차단이 풀린다.

### 게시와 사용 규모

npm 레지스트리에서 세 패키지는 모두 11월 5일에 처음 게시되었고
버전이 일곱 개씩이며 최신은 0.5.0이다.[^npm]
11월 2일부터 8일까지 주간 내려받기는 `ztd-charts` 1,377건, CLI 1,122건,
MCP 1,026건이다.[^npm-downloads]
이 수치에는 자동화된 설치와 미러가 포함될 수 있어 실제 사용자 수와 같지 않다.

## 분석

### 설계 규칙이 API에 들어 있다

이 라이브러리의 설계 규칙은 “강조는 한 항목, 나머지는 중립,
아래에 한 줄 요약”이다.
스킬 문서가 이를 한 문장으로 적고,
API에서는 차트의 `highlight` 옵션과 카드의 `takeaway` 필드로 나타난다.
그리기 도구가 보통 맡기지 않는 “무엇을 말할 것인가”가 입력의 일부가 된다는
뜻이다.
작성자가 요약 문구와 강조한 항목이 어긋난 예시 세 곳을 평가 문서에서
직접 고친 것도 이 규칙을 기준으로 한 일이다.

### 에이전트가 쓰는 쪽을 기본 사용자로 놓았다

스킬 문서의 절차는 데이터 보기, 차트 고르기, 스펙 쓰기, 검증, 미리보기,
코드로 옮기기 순서다.
각 단계에 대응하는 도구가 MCP 서버에 있고,
`validate_spec`은 모르는 차트 종류에 대한 “혹시 …인가요” 제안과 누락된 채널,
데이터에 없는 필드, 숫자가 아닌 값 필드를 JSON 경로와 함께 돌려준다.
오류 메시지가 사람이 읽는 문장이면서
에이전트가 다음 수정에 쓰는 입력이 되는 구조다.
`render_chart`가 PNG를 이미지로 돌려주는 것도,
에이전트가 결과를 눈으로 확인하게 하려는 설계다.

### 의존성 없이 직접 만든 비용을 번들 예산으로 관리한다

스케일, 축, 레이아웃, 애니메이션을 직접 구현해 외부 차트 라이브러리를 쓰지
않으므로, 코드가 커지면 번들도 커진다.
평가 문서는 공통 부품의 결함을 고치자 모든 차트가 약 0.49 kB 커졌고
라인과 영역은 구간 선택 기능으로 2.5 kB 더 커졌다고 기록한다.
이 변화를 차트별 `size-limit` 한도(예: 파이 13.5 kB)와 대조해 한도를 올릴 때
사유를 적는 방식으로 관리한다.

## 비평

### 성능과 접근성 수치는 작성자의 자체 측정이다

README와 평가 문서가 내세우는 60fps, 대비 4.6:1 이상,
axe 위반 0건은 작성자가 직접 만든 QA 도구를 헤드리스 Chromium에서
돌려 얻은 값이다.
옛 최종 보고서는 스스로 한계를 적는다.
실기기, Safari, Firefox는 재지 않았고 숫자는 헤드리스 Chromium 기준이며,
4배 느린 CPU에서 1만 점 다시 재생이 60fps에 못 미치는 곳(버블 55.7fps,
비스웜 52.6fps)이 남아 있다고 한다.
평가 문서가 나중에 이 값을 58.1fps와 55.7fps로 갱신했다.
이 한계 표시는 정직하지만, README의 접근성 문구는 외부 감사나 지원 기술을 쓰는
사용자의 확인 없이 자체 검사만 근거로 한다.
스크린리더 설명과 데이터 표가 실제 스크린리더에서
쓸 만한지는 이 저장소만으로는 알 수 없다.

### 5일 사이에 0.5.0까지 왔다는 점이 안정성과 충돌한다

저장소는 11월 5일에 만들어졌고 0.5.0이 11월 9일이며
세 패키지가 각각 일곱 버전이다.[^npm]
스펙의 JSON 구조가 공개 계약이고 에이전트가 그 계약대로 스펙을 쓰므로, 0.x에서
필드나 차트 종류가 바뀌면 이전에 만든 스펙이 깨진다.
`@junhanlee/chart-kit`에서 이름을 바꾸었다고 문서가 밝히고, CLI도 0.2.0에서
이름과 환경 변수가 바뀌었다고 적는다.
스펙 스키마를 호환성 있게 유지하겠다는 약속이나 버전 정책은 이번에 읽은 문서에서
찾지 못했다.

### 주소를 가져오는 도구는 안으로의 접근은 막지만 밖으로의 전송은 막지 않는다

`guard.ts`는 내부망을 읽는 요청을 꼼꼼히 막는다.
그러나 `render_chart`는 에이전트가 넘긴 공개 주소를 그대로 가져오고,
도구 주석은 이 도구가 바깥 세계와 상호작용한다(`openWorldHint`)고 표시한다.
프롬프트에 심긴 지시로 에이전트가 대화 안의 정보를 주소의 쿼리 문자열에 실어
공개 주소로 요청하면, 이 차단은 그 전송을 막지 못한다.
이 위험은 내부망 접근 방어와 다른 종류이며,
이 저장소의 문서는 이 경우를 다루지 않는다.

### 문서가 코드보다 먼저 낡는다

옛 최종 보고서는 31종과 “npm에 배포하지 않았어요”라고 적지만 지금은 36종이고
npm에 올라 있다.
보고서 첫머리가 옛 기록이라고 밝히므로 오해를 막으려는 표시는 있다.
README는 React만 피어 의존성이라고 적는데
패키지 매니페스트는 `react`와 `react-dom`을 모두 피어로 둔다.
“런타임 의존성 0” 배지는 `ztd-charts` 패키지에만 해당하고,
PNG를 그리는 CLI와 MCP 쪽은 `@resvg/resvg-js` 같은 의존성을 가진다.

## 인사이트

### 차트 라이브러리의 문서가 스키마와 오류 메시지로 옮겨 간다

사람이 쓰는 라이브러리는 문서와 예제로 배우지만,
에이전트가 쓰는 라이브러리는 스키마, 검증 오류, 예시 스펙으로 배운다.
`validate_spec`의 “혹시 …인가요” 제안은 문서
페이지가 아니라 에이전트의 다음 입력이 된다.
이 변화의 이차 효과는 오류 문구와 스키마가 사실상 공개 API가 된다는 점이다.
문구 한 줄을 바꾸면 에이전트의 수정 경로가 달라지므로,
오류 메시지에도 회귀 시험이 필요하다.
이 저장소의 시험 중 `spec.test.ts`와 `mcp.test.ts`가 그 방향에 있는지는 시험
내용을 읽어야 알 수 있고, 이번에는 읽지 않았다.

### 의견이 강한 기본값이 모델 사이의 편차를 줄인다

같은 데이터로 모델마다 다른 차트를 그리게 두면 결과가 들쭉날쭉하다.
이 라이브러리는 강조 한 항목, 한 줄 요약, 차트 종류 선택표(질문에서
첫 선택으로)를 스킬에 고정해 편차를 줄인다.
JSON으로 선언해서 그리는 방식은 Vega-Lite 같은 문법 기반 도구와 닮았지만, 여기서
스펙은 36개의 이름 붙은 차트 종류를 고르는 쪽이라 조합의 자유는 적고
결과의 예측 가능성은 높다.
에이전트에게는 자유도가 낮은 도구가 더 안정적이라는 점이 이 선택의 근거이고,
그 대가는 표에 없는 차트를 만들 수 없다는 것이다.

### 시각 확인을 모델의 눈에만 맡기면 이 순환이 닫히지 않는다

스킬은 미리보기 이미지에서 강조가 올바른 항목에 갔는지,
글이 잘리지 않았는지 에이전트가 확인하라고 한다.
그런데 저장소의 QA 도구는 이미 잘림, 겹침, 대비를 숫자로 검사한다(카드 522장에서
잘림과 겹침 0건, 글자 11,024개 중 최소 대비 4.6:1이라고 평가 문서는 적는다).
MCP의 `render_chart`가 돌려주는 것은 PNG와 검증 경고뿐이고,
이런 레이아웃 검사 결과는 도구 응답에 들어 있지 않다.
모델이 이미지를 읽는 능력에 기대는 대신 같은 검사를 도구가 에이전트에게
돌려주면, 확인 단계가 판단에서 측정으로 바뀐다.
