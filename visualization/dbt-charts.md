# 차트를 채팅에 맞춰 다시 짜기 — dbt Charts의 선언형 접근

원문: [Charts Built for Chat](https://dbtcharts.com/blog/charts-built-for-chat/)

HN 토론: <https://news.ycombinator.com/item?id=49704246> (295점, 89개 댓글)

## 요약

Dave Fowler는 dbt Labs가 dbt Charts를 오픈소스로 공개한다고 밝힌다.
AI 에이전트가 만드는 시각화를 통제하기 위한, 대시보드용 선언형 언어다.
글은 문제를 이렇게 짚는다.
에이전트는 코드, SQL, Git에는 능숙하지만 남이 만든 UI 안에서는 서툴다.
에이전트가 리포트를 생성하면 여러 언어와 프레임워크에 걸쳐 파일이 흩어지는 마찰이 생기는데,
dbt Charts는 이를 감사 가능한 코드로 옮겨 해결하려 한다.

dbt Charts는 자신을 코드의 지저분한 자유와 BI 도구의 좁은 통제 사이의 제3의 선택지로 규정한다.
기존 BI 인터페이스에 AI를 끼워 넣는 대신, 차트 생성을 코드로,
구체적으로는 구조화된 YAML 언어로 옮긴다.
하나의 대시보드가 단일 YAML 파일 안에 살며,
SQL은 어떤 데이터를 볼지(WHAT)를, YAML은 어떻게 볼지(HOW)를 선언하고,
문서화를 위한 Markdown과 변수·매크로를 위한 Jinja가 함께 들어간다.
글의 표현으로는, SQL이 무엇을 볼지 선언하는 언어로 남고 그것을 YAML로 감싸 어떻게 볼지를 선언한다.

언어는 열여섯 가지 차트 유형과 합성 차트를 지원하며,
보드 수준과 테마 수준 설정에서 상속되는 계단식(cascading) 스타일을 제공한다.
dbt 프로젝트와 깊이 통합되어 차트가 모델과 같은 Git 저장소에 나란히 살고,
모델과 시각화의 변경이 통합 CI/CD로 함께 배포된다.
엄격한 YAML·SQL 검증에 더해, 렌더링 전에
`WARN-BAR-BAND-WIDTH-TOO-NARROW` 같은 시각화 점검 경고를 띄운다.

오픈소스 언어는 Apache 2.0 라이선스로 `uv tool install dbt-charts`로 설치한다.
이와 함께 dbt Labs는 호스팅 플랫폼 dbtCharts.com을 내놓았다.
대화형 분석, 시각적 편집, 버전 이력, 권한 기반 공유를 제공하며,
오픈소스 언어와 호환되어 보드가 로컬, CI, 플랫폼에서 동일하게 렌더링된다고 한다.

## 분석

### 문제를 UI가 아니라 매체의 불일치로 규정한다

글의 핵심 진단은 에이전트가 코드에는 능숙하고 UI에는 서툴다는 한 문장에 압축된다.
이 진단이 dbt Charts의 모든 설계 결정을 끌어낸다.
문제를 에이전트의 능력 부족이 아니라 매체의 불일치로 보면,
해법은 에이전트를 UI에 적응시키는 것이 아니라 시각화를 코드로 옮기는 것이 된다.
기존 BI 도구에 AI를 끼워 넣는 접근을 명시적으로 거부하는 이유가 여기 있다.

이 프레이밍은 논쟁의 축을 바꾼다.
AI 분석 도구 경쟁은 대개 BI 인터페이스에 얼마나 똑똑한 챗봇을 붙이느냐로 흘러왔다.
dbt Charts는 그 축 자체를 거부하고,
에이전트가 이미 잘 다루는 매체인 코드와 Git으로 시각화를 끌어내린다.
문제를 어디에 두느냐가 해법의 형태를 결정하며,
매체 불일치라는 진단은 코드로의 이동을 필연처럼 보이게 만든다.

### SQL과 YAML의 분업으로 관심사를 가른다

dbt Charts의 언어 설계는 WHAT과 HOW의 분리를 중심에 둔다.
SQL이 어떤 데이터를 볼지를 선언하고, YAML이 어떻게 볼지를 선언한다.
이 분업은 새로운 발명이 아니라 dbt가 이미 확립한 철학의 연장이다.
dbt는 변환 로직을 SQL로 선언하고 그 위에 구성을 YAML로 얹는 방식으로 성공했고,
dbt Charts는 같은 문법을 시각화 계층으로 확장한 것이다.

이 연속성이 통합의 근거가 된다.
차트가 모델과 같은 저장소에 살고 같은 CI/CD로 배포된다는 것은,
dbt 사용자에게 완전히 새로운 워크플로를 배우게 하는 대신
이미 익숙한 Git 기반 워크플로 안으로 시각화를 편입시킨다는 뜻이다.
Markdown과 Jinja까지 한 파일에 담는 것도 같은 논리다.
분석가가 이미 쓰는 도구들을 하나의 감사 가능한 파일로 모으는 것이,
여러 언어에 흩어진 에이전트 산출물이라는 문제의 직접적 대칭이 된다.

### 검증을 언어의 일부로 만들어 에이전트를 통제한다

`WARN-BAR-BAND-WIDTH-TOO-NARROW` 같은 시각화 점검은 사소해 보이지만
설계 철학의 핵심을 드러낸다.
에이전트가 만든 차트를 통제하려면, 통제가 사람의 검토가 아니라
언어 자체의 검증으로 들어와야 한다는 것이다.
YAML·SQL 문법 검증에 더해 시각화 규칙까지 렌더링 전에 강제하면,
에이전트의 산출물이 사람의 눈을 거치기 전에 일차적으로 걸러진다.

이것이 거버넌스라는 단어의 실제 내용이다.
코드로 옮기는 것만으로는 통제가 되지 않는다.
코드도 에이전트가 마구 생성하면 지저분한 자유로 돌아간다.
검증 규칙을 언어에 내장해야, 흩어진 파일 대신
규칙을 통과한 단일 파일이라는 통제된 산출물이 보장된다.
dbt Charts가 자신을 코드와 BI 도구 사이의 제3항으로 부를 수 있는 근거는
자유(코드)에 규칙(검증)을 더했다는 이 조합에 있다.

## 비평

### 제3의 선택지라는 규정이 트레이드오프를 감춘다

코드의 지저분한 자유와 BI 도구의 좁은 통제 사이라는 프레이밍은 매력적이지만,
두 극단의 단점만 모아 대비시키는 수사적 구도다.
BI 도구의 좁은 통제는 동시에 비개발자도 쓸 수 있는 접근성이고,
코드의 지저분한 자유는 동시에 무한한 표현력이다.
dbt Charts는 이 둘의 장점 사이가 아니라,
YAML이라는 특정 지점을 선택한 것이며 그 선택에는 고유한 비용이 따른다.

YAML은 코드보다 제약이 많고 BI 도구보다 진입 장벽이 높다.
열여섯 가지 차트 유형이라는 명시는 표현력의 상한을 드러낸다.
BI 도구의 좁음을 비판하면서 스스로도 유형의 목록으로 한계를 긋는 것이다.
분석가가 YAML 문법과 계단식 스타일 상속, Jinja 매크로를 배워야 한다면,
BI 도구의 접근성을 포기한 대가가 분명히 존재한다.
제3의 선택지라는 표현은 이 대가를 두 극단의 단점 뒤로 숨긴다.

HN에서 carterschonwald는 이 YAML 선택을 신랄하게 비판했다.
YAML은 프로그래밍 언어가 아니며,
조건문과 변수 바인딩이 YAML에 들어오면 끔찍한 참사가 된다는 것이다.
LLM이 있는데 언어라는 단어를 쓰려면 진짜 계산 언어를 만들어야지
YAML에 머무는 것이 실망스럽다고 했다.[^carterschonwald]
dgudkov는 다른 각도에서 혁신성을 의심했다.
BI는 이미 분리되어 사람들이 AI로 Excel과 Power BI 리포트를 생성하고 있으며,
YAML이든 XML이든 JSON이든 AI가 시키는 대로 만들 뿐이라
블로그가 주장하는 만큼 혁신적이지는 않다는 것이다.[^dgudkov]
두 지적 모두 YAML이라는 특정 선택이 자명한 최적점이 아님을 드러낸다.

### 에이전트를 위한 도구라면서 인간의 학습을 전제한다

글의 논리에는 긴장이 있다.
문제는 에이전트가 UI에 서툴다는 것인데,
해법은 인간이 YAML 언어를 배워 감사하는 것이다.
에이전트가 코드에 능숙하니 YAML을 생성하는 것은 자연스럽지만,
그 산출물을 검토하고 규칙을 정하고 스타일을 상속 구조로 설계하는 것은 인간의 몫이다.
즉 이 도구는 에이전트의 생성을 인간의 거버넌스로 감싸는 구조다.

이 구조가 나쁜 것은 아니지만, 마케팅과 실제 노동 분배가 어긋난다.
채팅에 맞춘 차트라는 제목은 대화만으로 차트가 나오는 인상을 주지만,
실제로 거버넌스가 작동하려면 누군가 YAML 스키마, 검증 규칙,
테마 계층을 설계하고 유지해야 한다.
에이전트가 마찰을 없애는 것이 아니라,
마찰을 UI 다루기에서 코드 리뷰하기로 옮기는 것이다.
이 이전이 순이득인지는 팀이 YAML 거버넌스를 유지할 역량이 있느냐에 달렸다.

### dbt 생태계 밖에서는 논거가 약해진다

dbt Charts의 가장 강한 논거는 dbt 프로젝트와의 통합이다.
차트가 모델과 같은 저장소에 살고 함께 배포된다는 이점은,
이미 dbt를 쓰며 Git 기반 워크플로에 투자한 팀에게만 온전히 성립한다.
글은 이 전제를 명시하지 않은 채 일반적인 AI 분석 문제의 해법처럼 제시한다.

dbt를 쓰지 않는 팀에게 이 도구는 제3의 선택지가 아니라,
새로운 언어와 새로운 저장소 규율을 통째로 도입하는 큰 결정이 된다.
BI 도구의 좁은 통제를 감수하는 팀 상당수는
그 접근성 때문에 그 선택을 한 것이지 무지 때문이 아니다.
dbt Charts의 논리가 설득력을 갖는 범위는
이미 코드-우선 데이터 문화를 가진 조직으로 좁게 한정되며,
그 밖에서는 코드로 옮기라는 처방이 해법이 아니라 새로운 부담이 된다.

BI 팀을 오래 이끈 HN의 RobGoretsky는 이 한계를 더 근본적으로 짚었다.
시각화는 BI 도구 가치의 작은 조각일 뿐이며,
거버넌스, 접근 제어, 상호작용, 시맨틱 계층과의 연결이 핵심이라는 것이다.
예시가 원시 SQL을 보여주지만 실제로는 차원과 측정값의 이름 같은
더 추상적인 것을 원하게 된다고 했다.[^RobGoretsky]
chupchap 역시 차트를 클릭해 데이터로 파고들어 필터링할 수 있느냐고 물으며,
시각화는 BI 도구가 하는 일의 빙산의 일각일 뿐이라고 지적했다.[^chupchap]
dbt Charts가 대체하려는 BI 도구의 좁은 통제가
사실은 상호작용과 거버넌스라는 두꺼운 가치층을 포함한다는 것을,
이 비판들이 드러낸다.

## 인사이트

### 거버넌스의 단위가 검토에서 언어로 이동한다

dbt Charts가 드러내는 깊은 전환은 AI 산출물을 통제하는 방식에 있다.
에이전트가 대량으로 생성하는 시대에는 사람이 하나씩 검토하는 거버넌스가 무너진다.
dbt Charts의 응답은 통제를 사후 검토에서 사전 언어 제약으로 옮기는 것이다.
`WARN-BAR-BAND-WIDTH-TOO-NARROW` 같은 규칙을 언어에 내장하면,
사람이 보기 전에 규칙이 먼저 걸러낸다.

이 이동은 시각화를 넘어 AI 산출물 전반에 적용되는 패턴이다.
에이전트가 코드를 생성하는 세계에서 코드 리뷰가 병목이 되듯,
에이전트가 차트를 생성하는 세계에서는 차트 검토가 병목이 된다.
해법은 검토자를 늘리는 것이 아니라,
검토의 상당 부분을 기계가 강제하는 규칙으로 코드화하는 것이다.
dbt Charts는 이 원리를 시각화에 구현한 사례이며,
AI 시대의 거버넌스가 사람의 눈이 아니라 언어의 제약으로 이동함을 보여준다.

### 선언형 언어는 에이전트 산출물의 표준 형식이 되어간다

dbt Charts가 자연어나 임의 코드가 아니라 선언형 YAML을 택한 것은 우연이 아니다.
에이전트는 자유 형식 코드를 잘 생성하지만, 자유 형식은 검증하기 어렵다.
선언형 언어는 표현력을 제한하는 대신 기계 검증과 감사를 가능하게 한다.
이는 인프라(Terraform), 빌드(YAML CI), 데이터 변환(dbt)에서 반복된 패턴이며,
시각화가 같은 경로를 따르는 것이다.

이 패턴의 함의는 에이전트 시대의 인터페이스 설계 원칙이다.
에이전트가 산출물을 만드는 영역마다,
자유 형식과 완전 통제 사이의 선언형 중간층이 표준이 되어간다.
선언형 층은 에이전트가 생성하기 쉽고, 기계가 검증하기 쉽고, 사람이 감사하기 쉽다.
dbt Charts의 진짜 베팅은 시각화라는 특정 영역이 아니라,
에이전트가 만드는 모든 것이 결국 선언형 스키마로 수렴한다는 방향성이다.
이 베팅이 맞다면, 앞으로의 도구 경쟁은 더 똑똑한 챗봇이 아니라
에이전트가 생성하고 기계가 검증할 수 있는 더 나은 선언형 언어를 두고 벌어진다.

다만 이 방향성에는 유력한 반론이 있다.
HN의 mritchie712는 이미 너무 늦었을 수 있다고 보았다.
사람들이 에이전트로부터 정확히 원하는 것을 얻는 데 익숙해졌고,
자신들의 에이전트는 사용자가 원하는 대로 React 앱을 직접 작성해 준다는 것이다.[^mritchie712]
rcarmo 역시 에이전트가 라이브러리 없이 SVG 차트를 직접 생성하게 하는 스킬을 만들어,
타임라인과 막대 차트의 80%를 놀랄 만큼 잘 처리한다고 했다.[^rcarmo]
이 반론들은 선언형 중간층이 표준이 되기 전에
에이전트의 자유 형식 생성이 그 자리를 차지할 수 있음을 시사한다.
선언형과 자유 형식 중 무엇이 이길지는,
검증 가능성의 이점이 즉시성의 이점을 넘어서느냐에 달렸다.

### 매체를 사람에서 에이전트로 옮기면 접근성의 정의가 바뀐다

가장 멀리 가는 함의는 접근성 개념의 재정의다.
BI 도구는 비개발자의 접근성을 위해 UI를 제공했다.
dbt Charts는 그 UI가 에이전트에게는 오히려 장벽이라고 본다.
사람에게 쉬운 것과 에이전트에게 쉬운 것이 갈라지는 순간,
접근성이라는 단어가 누구를 위한 것인지 되물어야 한다.

이 전환은 도구 설계의 청중을 바꾼다.
지금까지 도구는 인간 사용자의 편의를 최적화했지만,
에이전트가 주된 생성자가 되면 최적화 대상이 에이전트의 생성 용이성으로 옮겨간다.
YAML은 사람에게 UI보다 불편하지만 에이전트에게는 UI보다 편하다.
이 재정렬이 진행되면, 인간은 생성자에서 감사자로 물러나고
도구의 표면은 인간의 눈이 아니라 에이전트의 문법에 맞춰 다시 설계된다.
채팅에 맞춘 차트라는 제목의 진짜 의미는,
차트의 매체가 사람의 손에서 에이전트의 언어로 넘어간다는 선언이다.
