# Claude Code가 좋은 이유는 단순함이라는 주장: 로그로 뜯어본 2025년의 에이전트 설계

원문: [Minusx | What makes Claude Code so damn good (and how to recreate that magic in your agent)!?](https://minusx.ai/blog/decoding-claude-code/)

HN 토론: <https://news.ycombinator.com/item?id=44998295> (469점, 304개 댓글)

GN 토론: <https://news.hada.io/topic?id=22696>

## 요약

MinusX의 vivek이 2025년 8월 21일, Claude Code가 왜 그렇게 쓰기 좋은지와 그 경험을 자기 에이전트에서 어떻게 재현할 수 있는지를 정리했다.
글은 Claude Code가 지금까지 써 본 에이전트 가운데 가장 즐거웠으며, 같은 모델을 써도 Cursor나 GitHub Copilot 에이전트보다 덜 짜증 난다는 경험에서 출발한다.
MinusX의 Sreejith가 Claude Code의 모든 네트워크 요청을 가로채 기록하는 로거를 만들었고, 글은 그 로그를 몇 달 동안 분석한 결과다.
저자는 아키텍처를 그대로 옮긴 글이 아니라, 즐거운 LLM 에이전트를 만드는 안내서라고 밝힌다.

핵심 메시지는 “단순하게 하라”다.
LLM은 디버깅하고 평가하기가 이미 충분히 어렵고, 멀티 에이전트, 에이전트 간 인계, 복잡한 RAG 검색 같은 복잡성은 디버깅을 열 배 어렵게 만들 뿐이라는 것이다.
글은 교훈을 네 갈래로 정리한다.

첫째는 제어 루프다.
Claude Code는 메인 스레드가 하나이고 메시지 기록도 평평한 목록 하나다.
복잡한 작업이 있으면 자기 자신을 하위 에이전트로 띄우지만, 그 하위 에이전트는 다시 하위 에이전트를 띄울 수 없어 분기는 최대 하나이며, 그 결과는 도구 응답으로 메인 기록에 붙는다.
중요한 LLM 호출의 50% 이상이 claude-3-5-haiku로 가며, 큰 파일 읽기, 웹 페이지 해석, git 기록 처리, 긴 대화 요약, 심지어 키 입력마다 바뀌는 한 단어짜리 처리 상태 표시까지 작은 모델이 맡는다.

둘째는 프롬프트다.
시스템 프롬프트는 약 2,800 토큰, 도구 설명은 무려 9,400 토큰이고, 사용자 프롬프트에는 늘 `claude.md`가 1,000~2,000 토큰 붙는다.
`claude.md` 같은 컨텍스트 파일이 있을 때와 없을 때의 성능 차이는 밤과 낮이라고 저자는 말한다.
`<system-reminder>`, `<good-example>`, `<bad-example>` 같은 XML 태그와 “Tone and style”, “Proactiveness”, “Task Management” 같은 Markdown 제목으로 프롬프트를 구조화한다.

셋째는 도구다.
Claude Code는 RAG를 거부하고, ripgrep과 jq와 find로 사람처럼 코드베이스를 검색한다.
저자는 RAG가 유사도 함수, 재순위기, 청킹, 큰 JSON과 로그 파일 처리 같은 숨은 실패 지점을 만든다며, LLM 검색은 강화학습으로 배울 수 있는 방식이고 이것이 LLM 시대의 “카메라 대 라이다”라고 반쯤 농담한다.
도구는 Bash, Read, Write 같은 저수준, Edit, Grep, Glob 같은 중간 수준, Task, WebFetch, ExitPlanMode 같은 고수준이 섞여 있으며, 자주 쓰는 동작은 Bash로 할 수 있어도 별도 도구로 만든다.
할 일 목록은 모델이 스스로 관리하는데, 긴 작업에서 길을 잃는 “컨텍스트 부패”를 막으면서도 도중에 계획을 고칠 유연성을 준다.

넷째는 조종 가능성이다.
어조와 스타일 섹션이 Claude Code를 “취향 있게” 느끼게 하며, 저자는 이 부분을 그대로 복사해 쓰라고 권한다.
IMPORTANT, VERY IMPORTANT, NEVER, ALWAYS 같은 강조가 여전히 모델을 지뢰에서 떼어 놓는 최선의 방법이라며 “유감스럽게도 여전히 최신 기술”이라고 적는다.
가장 중요한 작업은 알고리즘, 곧 판단 지점과 휴리스틱과 예시를 명시적으로 적어 주고, 서로 충돌하는 해야 할 일과 하지 말아야 할 일의 뒤죽박죽은 피하라고 조언한다.

## 분석

### 2025년 여름의 반(反) 멀티 에이전트 선언이다

이 글이 나온 2025년 8월은 멀티 에이전트 시스템이 유행하던 때다.
기획자 에이전트가 요구 사항을 쓰고, 구현 에이전트가 코드를 쓰고, QA 에이전트가 검증하는 인계 구조가 여러 프레임워크의 기본 예제였다.
저자는 그 흐름을 정면으로 거슬러, 여러분의 앱에 멀티 에이전트 시스템이 필요할 가능성은 매우 낮다고 말한다.

근거는 두 가지다.
하나는 디버깅이다.
추상화 층을 하나 더할 때마다 시스템은 디버깅하기 어려워지고, 그렇게 복잡한 시스템이 어쩌다 작동해도 나중에 크게 바꾸기가 두려워진다.
다른 하나는 모델 발전의 방향이다.
복잡한 발판을 쌓을수록 일반 모델이 나아지는 경로에서 벗어나게 되며, 저자는 이것을 “쓴 교훈”과 자율주행에 빗댄다.

Hacker News에서 ahmedhawas123은 모두가 멀티 에이전트로 달려가는 시점에, LLM을 우선하는 조직이 어떻게 접근하는지 보여 줘서 도움이 됐다고 적었다.[^ahmedhawas123]
nojs는 Claude Code의 맞춤 하위 에이전트가 Opus를 쓰게 하고 프롬프트를 극단적으로 다듬어도 메인 에이전트보다 눈에 띄게 못한 경우가 많다며, 이것이 “평평하게 유지하라”는 논리와 맞아떨어진다고 적었다.[^nojs]

### 모델이 잘하는 일은 모델에 맡기고, 못하는 일은 프롬프트와 도구로 가린다

글의 첫 판단, 곧 Claude Code가 LLM이 무엇을 잘하고 무엇을 못하는지에 대한 근본적인 이해 위에서 만들어졌다는 말은 이후 모든 교훈을 관통한다.
RAG를 버리고 grep을 쓰게 한 것은 모델이 코드를 잘 읽고 정규식을 잘 쓴다는 믿음에서 나오고, 할 일 목록을 모델이 관리하게 한 것은 모델이 긴 작업에서 길을 잃는다는 약점을 인정한 데서 나온다.
작은 모델을 적극적으로 쓰는 것도 같은 판단이다.
긴 파일 읽기와 요약처럼 판단이 덜 필요한 일은 싼 모델에 맡긴다.

Hacker News에서 whazor는 Claude Code 성공의 열쇠가 Unix라고 적었다.[^whazor]
Claude가 명령을 실행해 코드를 검색하고, 컴파일을 시험하고, 여러 작업을 할 수 있는데, Unix 명령은 문서화가 잘돼 있고 학습 데이터에 예시가 넘쳐 난다는 것이다.
LLM 검색이 RAG보다 낫다는 저자의 주장은, 사실 모델이 이미 학습한 도구 생태계에 기대는 편이 새 검색 장치를 끼워 넣는 것보다 낫다는 주장으로 읽힌다.

### 프롬프트 공학은 여전히 “대문자로 외치기”에 기대고 있다

글에서 가장 솔직한 대목은 4.2절이다.
Claude Code조차 모델에게 무엇을 하지 말라고 할 때 IMPORTANT와 NEVER를 대문자로 반복하며, 저자는 이것이 추하지만 지금은 따라 하라고 권한다.
그는 미래의 모델은 더 조종하기 쉬워져 이런 추함을 피할 수 있을 것이라고 기대한다.

Hacker News에서 AceJohnny2는 대문자나 별표가 토큰화 과정을 거쳐서도 의미를 갖느냐고 물었고,[^AceJohnny2] Danborg는 IMPORTANT와 NEVER 태그에 기대는 것이 현재 모델의 한계를 보여 주는 필요악이라고 적었다.[^Danborg]
athrowaway3z는 “하지 말아야 할 것 대신 해야 할 것을 말하라”는 조언, 곧 모델이 무언가에 손을 뻗을 때 그 대안이 컨텍스트에 있게 하라는 조언을 본 뒤로 같은 문제가 사라졌다고 전했다.[^athrowaway3z]
이 교환은 강조어가 효과가 있다는 관찰과, 그것이 가장 좋은 방법은 아니라는 반론이 함께 존재함을 보여 준다.

## 비평

### “좋은 이유”를 하네스에서만 찾고 모델의 몫을 가볍게 다룬다

글은 제목에서 Claude Code가 왜 그렇게 좋은지를 묻고, 답을 루프, 프롬프트, 도구, 조종 가능성에서 찾는다.
저자도 무거운 일의 대부분은 새 Claude 4 모델, 특히 사고 사이사이에 도구를 부르는 능력이 한다고 인정하지만, 그 인정은 한 문장에 그친다.
Hacker News에서 OtherShrezzing은 기본 모델이 벤치마크의 코딩 과제가 아니라 현실의 코딩 과제를 잘하기 때문이라며, 자체 시스템 프롬프트를 가진 GitHub Copilot에서 모델을 바꿔 보면 Claude가 OpenAI와 Google 모델을 크게 앞서 다른 모델들은 사실상 쓸모없을 정도라고 적었다.[^OtherShrezzing]

이 반론이 맞다면, 글이 말하는 교훈의 상당 부분은 “좋은 모델을 방해하지 않는 법”이지 “좋은 에이전트를 만드는 법”이 아니다.
저자 스스로 같은 모델로도 Claude Code가 Cursor나 Copilot보다 덜 짜증 난다고 했으니 하네스의 몫이 있는 것은 분명하다.
그러나 글은 그 몫이 얼마인지, 곧 다른 모델을 Claude Code의 프롬프트와 도구로 돌리면 어떻게 되는지를 보이지 않는다.
MinusX가 이 교훈을 자기 제품에 넣었다고 말하면서도 그 전후를 비교하지 않은 것도 같은 빈자리다.

### 공개 문서를 다시 쓴 것 이상인지가 불분명하다

Hacker News에서 brokegrammer는 제목이 Claude Code가 다른 도구보다 왜 나은지를 보여 줄 것처럼 말하지만, 실제로는 Claude Code 문서를 다른 말로 반복할 뿐이라며, 자신이 무언가를 놓친 것인지 아니면 Anthropic 홍보인지 물었다.[^brokegrammer]
the_mitsuhiko는 Claude Code가 오픈소스가 아니지만 동작을 파악할 도구가 있다며, 세션에서 쓰인 모든 도구와 프롬프트를 JSON과 보기 좋은 HTML로 뽑아 주는 Claude Trace를 추천했다.[^the_mitsuhiko]

이 반응은 글의 가치가 어디에 있는지를 가른다.
프롬프트와 도구 목록 자체는 로그를 보면 누구나 확인할 수 있다.
글이 더하는 것은 해석, 곧 왜 그런 선택이 좋은지에 대한 저자의 판단인데, 그 판단은 대부분 “나는 이렇게 느꼈다”와 “우리는 MinusX에 넣었다” 수준의 근거에 기대고 있다.
50% 넘는 호출이 Haiku로 간다는 로그 통계처럼 가로챈 데이터만이 줄 수 있는 관찰이 더 많았다면, 글은 문서의 재서술과 확실히 구별됐을 것이다.

### “단순함”은 그 뒤의 Claude Code 자신이 지키지 않았다

이 글은 2025년 여름의 Claude Code를 기준으로 쓰였다.
그 뒤 Claude Code는 도구와 기능이 계속 늘었고, 2026년 9월의 [[harness-tax]]는 일곱 모델 모두에서 Claude Code의 첫 호출 초기 컨텍스트가 도구 네 개짜리 최소 하네스 Pi의 10배를 넘으며, 비슷한 성공률에 두 배 가까운 비용을 쓴다고 보고했다.
같은 연구에서 가장 단순한 하네스가 파레토 경계선에 올랐다.

이것은 글의 교훈이 틀렸다는 뜻이 아니라, 글이 말한 단순함이 상대적이었다는 뜻이다.
2,800 토큰의 시스템 프롬프트와 9,400 토큰의 도구 설명은 2025년의 멀티 에이전트 프레임워크에 비하면 단순했지만, 절대적으로 가벼운 구성은 아니었다.
저자는 시스템 프롬프트의 길이를 강조하면서도 그 길이의 비용을 계산하지 않았고, “그대로 복사하라”는 권유는 그 비용까지 복사하게 만든다.

## 인사이트

### 하네스의 교훈은 모델이 바뀌면 유통기한이 지난다

글이 권한 강조어, 곧 IMPORTANT와 NEVER는 2025년 모델의 약점에 맞춘 처방이었다.
저자 스스로 모델이 더 조종하기 쉬워지면 이런 추함을 피할 수 있을 것이라고 적었다.
1년 뒤 모델이 달라지면, 대문자로 외치는 지시는 불필요할 뿐 아니라 해로울 수 있다.
지나치게 강조된 금지는 모델을 필요 이상으로 조심스럽게 만들고, 서로 충돌하는 강조는 저자가 경계한 “해야 할 일과 하지 말아야 할 일의 뒤죽박죽”을 만든다.

그래서 이 글에서 오래 남는 교훈은 구체적 처방보다 원칙 쪽이다.
디버깅할 수 있게 루프를 평평하게 유지하라, 모델이 잘하는 일은 모델에 맡겨라, 가장 중요한 작업의 판단 지점을 명시하라는 원칙은 모델이 바뀌어도 유효하다.
반면 “이 섹션을 그대로 복사하라”는 조언은 복사한 시점의 모델에 묶인다.

### 다른 에이전트 안에 Claude Code를 통째로 넣는 흐름을 예고했다

Hacker News에서 _1tem은 Claude Code가 너무 좋아서 자기 에이전트 루프 안에서 그 에이전트 루프를 쓰고 싶다며, 특수한 작업을 위한 브라우저 에이전트를 Claude Code와 헤드리스 브라우저와 Playwright MCP 서버를 묶은 Docker 이미지로 만들 계획이라고 적었다.[^_1tem]
글은 Claude Code의 설계를 자기 에이전트에 재현하는 법을 말했지만, 이 댓글은 재현하지 않고 그대로 내장하는 길을 가리킨다.

이후의 흐름은 두 번째 길 쪽으로 기울었다.
Claude Agent SDK처럼 에이전트 루프 자체가 부품으로 제공되면서, 많은 제품이 하네스를 다시 만드는 대신 가져다 쓰게 됐다.
[[unreal-agent]]가 CLI 중심 SDK가 로컬 세션과 하위 프로세스에 대한 가정 때문에 운영 환경에 잘 옮겨지지 않는다고 비판한 것은, 바로 이 “가져다 쓰기”가 부딪힌 벽이다.
단순한 하네스를 배워 직접 만드느냐, 잘 만든 하네스를 통째로 빌리느냐의 선택은 지금도 이어지는 긴장이다.

### 에이전트가 시스템 전체에 접근한다는 문제는 단순함으로 풀리지 않는다

글은 Claude Code의 설계를 즐거움과 효율의 관점에서만 다루고 보안은 거의 다루지 않는다.
Hacker News에서 noduerme는 혼자 일하는 개발자로서 노트북 한 대에 모든 저장소와 API 키와 SSH 키가 있는데, 시스템 전체와 CLI에 대한 접근을 무언가에 주는 것이 너무 무섭다고 적었다.[^noduerme]
무엇을 읽고 올리고 실행할지 알 수 없다는 것이다.

Bash 하나로 무엇이든 할 수 있게 하는 설계는 단순함의 정점이지만, 동시에 에이전트의 행동 범위를 가장 넓게 여는 설계이기도 하다.
글이 칭찬한 “사람처럼 grep하는” 에이전트는 사람처럼 `~/.ssh`도 읽을 수 있다.
그 뒤 에이전트 보안 사고가 늘면서 샌드박스와 권한 모델이 하네스 설계의 중심으로 올라온 것은, 단순한 루프가 풀지 못한 문제가 무엇이었는지를 보여 준다.
