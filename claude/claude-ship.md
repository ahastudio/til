# Claude Ship 출시

원문: [Introducing Claude Ship](https://claude.com/ko/resources/articles/introducing-claude-ship)

HN 토론: <https://news.ycombinator.com/item?id=50618513> (88점, 34개 댓글)

## 요약

Anthropic이 2026년 11월 23일 Claude Ship을 베타로 공개했다.
PR을 연 개발자가 다음 일로 넘어가도,
리뷰 결과 확인, 수정, 승인 요청이 이어지며 흐름이 끊긴다는 문제에서 출발한다.
사람이 모든 변경을 승인하는 방식은 사람이 한 줄씩 쓰던 시절에는 따라갈 만했지만,
에이전트로 개발하는 팀이 늘면서
PR 이후의 속도가 코드 작성 속도를 따라가지 못한다는 것이다.
Claude Code 팀은 코드 대부분을 Claude가 쓰는 팀이라고 밝힌다.

Claude Ship은 PR을 리뷰하고, 고치고, 팀이 정한 정책에 따라 병합해도 되는지
결정하는 묶음이다.
어디서 돌릴지와 어떤 변경에 사람이 필요한지는 팀이 정한다.
Claude Enterprise 조직은 최소 1만 달러의 Claude Ship 크레딧을 받을 수 있다.
받은 날부터 30일 안에 써야 하고, 2027년 1월 15일까지 신청하며 약관이 붙는다.

### 구성 요소

세 부분으로 이루어져 있고, 각 부분의 상태와 역할은 다음과 같다.

| 구성 요소        | 상태      | 하는 일                                         | 원문이 밝힌 조건                                           |
| ---------------- | --------- | ----------------------------------------------- | ---------------------------------------------------------- |
| Code Review      | 정식 출시 | 여러 관점으로 PR을 읽고 결과를 검증해 PR에 올림 | 저장소마다 Quick, Standard, Deep 중 선택                   |
| PR Steward       | 베타      | 실패한 CI, 병합 충돌, 리뷰 의견에 대응해 수정   | 승인과 병합을 하지 않도록 설계                             |
| Claude Approvals | 베타      | 저장소의 정책 파일에 따라 승인 여부를 결정      | 기본 브랜치에 정책 파일이 있어야 시작, 관리자가 끌 수 있음 |

Code Review는 코드베이스를 기준으로 PR을 여러 관점에서 깊이 읽는다.
결과를 모으고, 적대적으로 검증하고, 분류해서 PR에 올린다.
저장소마다 Quick, Standard, Deep 세 단계의 리뷰 수준을 고른다.
Claude Code 팀에서는 Claude의 리뷰가 더 넓은 절차의 한 층이며,
병합된 PR이 6월부터 9월 사이에 두 배 넘게 늘고
되돌려진 비율은 40% 넘게 줄었다고 한다.

PR Steward는 CI 실패, 병합 충돌, Code Review와 다른 리뷰 도구와 팀원의
리뷰 의견이 나오면 끼어든다.
푸시할 때마다 무엇을 바꿨고 어떻게 되돌리는지를 댓글로 남긴다.
개발자는 `@claude`와 지시를 달아 방향을 잡고, `@claude stop`으로 멈춘다.

Claude Approvals는 팀이 저장소에 파일로 쓴 승인 정책을 적용한다.
정책이 허용하면 일상적인 변경을 스스로 승인하고,
특정 상황에서는 더 깊은 사람의 서명을 요구할 수 있다.
원문은 이것을 더 똑똑한 CODEOWNERS 파일처럼 동작한다고 비유한다.
판단 근거로는 Code Review의 발견 사항이나 자연어로 쓴 분류기(classifier)를
쓸 수 있다.
대부분의 고객에게는 처음에 관찰 전용 모드로 켜 신뢰를 쌓은 뒤,
브랜치 보호에서 Claude Approvals의 통과를 필수로 두라고 권한다.

### 시작하는 두 가지 길

개발자는 Claude Code의 새 `/ship` 명령으로 자기 PR에서 써 볼 수 있다.
변경이 준비되면 `/ship`을 실행하고, Claude가 푸시하고 PR을 열고 리뷰하고
피드백과 실패한 검사를 처리해 병합 직전 상태로 만든다.
병합 가능 여부는 개발자의 권한과 저장소의 브랜치 규칙이 정한다.
이 명령은 Claude Code와 데스크톱 앱에 이날부터 순차적으로 배포된다.

관리자는 저장소 단위로 켠다.
Code Review와 PR Steward는 저장소마다 관리자가 켜고,
Claude Approvals는 연결된 저장소의 기본 브랜치에 정책 파일이 있으면 시작하며
관리자가 끌 수 있다.
관리자는 리뷰 수준, 리뷰가 도는 시점, 지출 한도를 저장소별로 정한다.
기존 브랜치 보호와 필수 검사는 그대로 쓴다.
저장소 하나로 시작해 월 지출 한도를 걸고,
승인 정책은 믿을 때까지 관찰 모드로 돌리는 것이 원문이 그리는 도입 경로다.

### 사례와 고객 의견

Claude Code 팀은 자기 PR 상당수에 Claude Ship을 쓴다고 한다.
가장 큰 변화는 누가 고객 피드백에 행동할 수 있는가이다.
제품 관리자(PM)가 피드백을 읽고 Claude Tag와 방향을 이야기해 PR을 열게 한 뒤
다음 일로 넘어가면, Claude Ship이 리뷰와 수정과 승인 판단까지 맡는다.
Analytics API 문서가 Admin 키로 Pro와 Team의 사용량을 가져올 수 있는 것처럼
읽혀 고객이 혼란을 겪은 건이 예로 나온다.
PM이 Claude Tag에게 수정이 진행 중인지 묻자 Claude Tag가 PR을 열었고,
Code Review는 막을 만한 것을 찾지 못했고 문서 리뷰어가 서명했으며
Claude Approvals가 통과해 그날 저녁에 병합되었다.

두 고객의 의견이 실려 있다.
Vatsal Bhatt는 Claude Code Review가 사람 리뷰어보다 먼저 실제 문제를 잡은
사례가 여러 번 있었고, 사람은 계속 관여하되 사람의 시간이 손이 필요한
변경에 쓰인다고 말한다.
Alex Devkar는 시범 팀들이 리뷰 의견 처리에 쓰는 시간이 줄었고
제안 방식과 의견 정리 방식을 팀 절차에 맞출 수 있다고 말한다.

### 제공 범위와 비용

Claude Team과 Enterprise 요금제의 GitHub 저장소에서 쓸 수 있다.
Code Review는 정식 출시이고 PR Steward와 Claude Approvals는 베타다.
사용량은 토큰 기준으로 청구되며, 비용은 PR의 수와 크기,
리뷰 수준, 리뷰가 도는 빈도, PR Steward의 작업량에 따라 달라진다.
관리자는 Code Review와 PR Steward에 지출 한도를 둘 수 있다.
Claude Approvals에는 기본 요금이 없지만,
정책 안의 분류기는 쓴 토큰만큼 청구되고
Claude의 리뷰를 쓰는 정책은 관찰 모드에서도 Code Review 요금이 붙는다.
`/ship` 실행은 일반 Claude Code 사용량으로 센다.
데이터 무보존(Zero Data Retention), HIPAA 구성, 고객 관리 암호화 키를 쓰는
조직은 쓸 수 없다.

## 분석

### 병목이 리뷰에서 PR 이후 전체로 옮겨 갔다는 진단

원문의 출발점은 쓰기가 빨라진 만큼 쓰기 이후가 느려 보인다는 관찰이다.
3월에 Anthropic이 낸 Code Review 발표는 같은 병목을 코드 산출량 증가와
리뷰 부담으로 설명했고,
이 저장소의 [Claude Code Review](claude-code-review.md) 문서가
그 내용을 정리했다.
그때는 리뷰어 한 층을 만들었고, 이번에는 그 뒤에 이어지는 수정과 승인까지
같은 시스템으로 묶었다.
병목이 한 단계씩 뒤로 밀리면서 그때마다 새 에이전트가 붙는 구조다.

이 진단이 맞다면 PR 이후의 모든 단계가 자동화의 후보가 된다.
원문이 든 순서(리뷰, 수정, 승인)는 개발자가 PR을 연 뒤 겪는 대기의 순서와
그대로 겹친다.
세 단계를 한 제품 이름으로 묶은 것은 단계 사이의 전달 비용을 없애겠다는
뜻으로 읽힌다.

### 승인의 자동화는 경계를 허무는 대신 정책으로 옮긴다

3월의 Code Review 발표는 Code Review가 PR을 승인하지 않고 승인은 여전히
사람의 판단이라고 분명히 했다.
이번 Claude Ship에서 승인은 Claude Approvals라는 별도 부분이 맡는다.
다만 PR Steward는 승인과 병합을 하지 않도록 설계되었다고 따로 적어,
수정하는 쪽과 승인하는 쪽을 분리해 놓았다.

승인의 기준은 저장소에 파일로 들어간다.
CODEOWNERS 파일이 누가 어떤 경로를 승인하는지를 적는 것과 같은 자리에,
어떤 변경은 에이전트가 승인해도 되는지를 적는 셈이다.
정책이 파일이므로 버전 관리와 리뷰의 대상이 되고,
저장소마다 다르게 둘 수 있다.
관찰 전용 모드와 브랜치 보호 연결이라는 두 단계의 도입 경로는
승인 권한을 한 번에 넘기지 않으려는 설계다.

Hacker News의 fwlr는 이 흐름을 위임의 사다리로 풀었다.
Claude가 쓰고 사람이 읽고 동료가 리뷰하고 팀장이 병합하던 단계에서,
Claude가 읽고, 리뷰하고, 마지막에는 병합까지 하는 단계로
한 칸씩 올라간다는 것이다.[^fwlr]
이 농담은 Claude Ship이 사다리의 어느 칸에 놓이는지를 되묻게 한다.
PR Steward가 승인과 병합을 하지 않도록 설계되었다는 서술은
마지막 칸을 사람이 쥐게 하는 위치를 지킨다.
다만 브랜치 보호에서 Claude Approvals의 통과를 필수로 두면,
병합 조건 하나를 에이전트가 맡게 된다.

### 비용 구조가 도입 절차를 결정한다

비용 서술이 구체적이다.
Claude Approvals에는 기본 요금이 없지만 정책이 Claude의 리뷰를 쓰면
관찰 모드에서도 Code Review가 돌고 청구된다.
따라서 승인 정책을 시험하는 단계에서도 리뷰 비용은 발생한다.
지출 한도는 Code Review와 PR Steward에만 설정할 수 있다고 적혀 있어,
분류기 비용을 한도로 막을 수 있는지는 원문에 없다.

## 비평

### 효과 수치는 비교 기준이 없다

병합된 PR이 6월부터 9월 사이에 두 배 넘게 늘고 되돌려진 비율이 40% 넘게
줄었다는 수치는 Claude Code 팀 한 곳의 것이다.
같은 기간에 Claude가 쓰는 코드의 양과 팀의 구성이 어떻게 바뀌었는지,
Code Review 외에 무엇이 바뀌었는지가 함께 나오지 않는다.
원문도 Claude의 리뷰는 더 넓은 절차의 한 층이라고 단서를 단다.
병합 수의 증가는 PR이 작아졌거나 많아져서도 생길 수 있고,
되돌림 비율은 품질을 재는 지표 가운데 하나일 뿐이다.
수치는 이 제품이 맞게 작동하는지를 보여 주기보다
이 팀에서 어떤 변화가 있었는지를 알려 준다.
기간이 9월에서 끝나는 점도 이번 출시와 어떤 관계인지 설명되지 않는다.

### 하나뿐인 사례는 가장 위험이 낮은 변경이다

본문의 사례는 API 문서의 설명을 고친 PR이다.
코드 동작이 아닌 문서 변경이고, 막을 만한 것이 없다는 판정이 나왔으며,
문서 리뷰어의 서명도 있었다.
Claude Approvals가 승인 판단을 맡는다는 주장을 뒷받침하기에 이 사례는
가장 쉬운 부류에 속한다.
승인 정책이 어려워지는 지점은 동작을 바꾸는 코드, 권한이나 결제 경로,
정책이 놓친 변경이다.
원문은 이런 변경에서 Claude Approvals가 어떻게 행동했는지,
거짓 승인이나 거짓 거부가 얼마나 있었는지를 싣지 않는다.

### 정책 파일을 누가 바꾸는지는 쓰여 있지 않다

승인 정책이 저장소의 파일이라면 정책 파일을 바꾸는 PR도 PR이다.
그 PR을 누가 어떤 기준으로 승인하는지, Claude Approvals가 자신의 정책을
바꾸는 변경을 승인할 수 있는지는 원문에 나오지 않는다.
기본 브랜치에 정책 파일이 있어야 시작한다는 서술만 있고,
정책 변경의 처리는 문서 밖의 설정에 달려 있을 수 있기 때문이다.
확인하려면 정책 파일을 바꾸는 PR에 어떤 규칙이 적용되는지를
설명서에서 찾아야 한다.

### 판매 조건이 평가와 섞여 있다

본문 한가운데에 1만 달러 이상의 크레딧과 신청 기한이 들어 있다.
이 페이지는 Anthropic이 자기 제품을 소개하는 글이고,
인용된 두 고객도 시범 팀이거나 이미 쓰고 있는 사용자다.
이들의 의견은 리뷰와 수정이 도움이 되었다는 경험을 알려 주지만,
승인 자동화가 위험을 늘리지 않았다는 증거는 아니다.
고객 의견 두 건이 모두 Code Review와 PR Steward에 관한 것이고
Claude Approvals에 대한 구체적 의견은 없다는 점도 같은 방향이다.

운영 묶음이어서, 반론은 그 묶음에 값을 매길 수 있는지를 묻는 것으로 읽힌다.
이 문서는 어느 쪽이 맞는지 가릴 근거가 없다.

### 도입할 때 부딪히는 현실적 조건

원문이 밝힌 제외 대상과 청구 방식은 도입 전에 걸리는 조건이다.
unstatusthequo는 데이터 무보존 조직이 제외된다는 문구를 보고
아쉬움을 적었다.[^unstatusthequo]
Sol-는 이것이 웹판 Claude Code로 PR을 Anthropic 인프라에서 열어 보는 구조인지,
Code Review처럼 API 사용량으로 청구되는지 물었다.[^Sol-]
원문은 토큰 기준 청구라고 적을 뿐 실행되는 인프라는 설명하지 않는다.
sambucini는 새 `/ship` 명령이 자기 팀의 `/ship` 스킬을 덮어쓰며,
번들 스킬을 모두 끄거나 이름을 바꾸는 수밖에 없어 보인다고 적었다.[^sambucini]

## 인사이트

### 승인 기준이 사람의 관행에서 쓰이는 정책으로 바뀐다

CODEOWNERS가 쓰는 규칙은 사람이 누구인지에 관한 것이었다.
Claude Approvals의 정책은 변경이 어떤 성격인지에 관한 것으로,
자연어 분류기가 판단의 재료가 될 수 있다.
이 문서의 해석으로는, 이 방식을 쓰는 팀은 암묵적이던 승인 관행을
처음으로 글로 적어야 한다.
어떤 변경이 일상적인지를 글로 적다 보면
팀마다 서로 다르게 이해하던 위험의 기준이 드러난다.
정책을 쓰는 작업은 도입 비용이면서 팀의 위험 감각을 점검하는 계기가 된다.

### 관찰 모드는 신뢰를 재는 도구이고, 그 측정에도 비용이 든다

관찰 전용 모드를 거치라는 권고는 에이전트의 판단과 사람의 판단을
나란히 비교해 보라는 뜻으로 읽힌다.
이 문서의 해석으로는 이 모드가 남기는 기록, 곧 사람은 승인했는데
에이전트는 아니라고 한 건과 그 반대의 건이 도입 여부를 정하는
가장 좋은 자료다.
그런데 정책이 Claude의 리뷰를 쓰면 관찰 모드에서도 Code Review가 돌고
청구된다.
신뢰를 재는 단계가 이미 비용을 낳으므로,
한도 없이 넓게 켜면 측정이 먼저 예산을 쓴다.
저장소 하나로 시작하라는 원문의 권고는 안전과 함께 비용을 가두는 역할도 한다.

### 쓰는 쪽, 고치는 쪽, 승인하는 쪽이 같은 계열이 된다

Claude가 코드를 쓰고 Claude Code Review가 검토하고 PR Steward가 고치고
Claude Approvals가 승인하는 흐름에서, 사람이 개입하는 자리는 정책을 정하는
일과 예외를 처리하는 일로 줄어든다.
이 설계는 단계를 분리해(PR Steward는 승인하지 않는다) 서로 견제하게 만들었지만,
모두 같은 모델 계열의 판단이라는 점은 그대로다.
같은 계열의 모델이 같은 종류의 실수를 할 가능성은
이 저장소의 [Claude Code Review](claude-code-review.md) 문서가
이미 짚었던 문제와 이어진다.
정책이 막아 주지 못하는 실수는 정책을 쓴 사람이 예상하지 못한 종류다.

Hacker News에서는 계열을 섞는 쪽이 낫다는 현장 경험이 올라왔다.
springtimesun은 직접 쌓은 리뷰 절차가 이 구성과 닮았다면서
모델 계열을 겹쳐 쓰고,
Claude 외의 모델도 리뷰어로 많이 잡아낸다고 적었다.[^springtimesun]
bob1029은 코드 작성에 OpenAI 모델을 많이 쓰는 팀에서
다른 제공자의 모델로 리뷰하는 것이 책임 분리로 좋아 보인다고 했고,[^bob1029]
marssaxman은 Claude와 Codex를 적대적 루프로 돌려
한쪽이 리뷰하고 다른 쪽이 통과할 때까지 고친다고 답했다.[^marssaxman]
igor47은 한 모델만 쓰는 것보다 정말 낫다는 평가가 있는지 물었고,[^igor47]
이 스레드에는 그 평가가 올라오지 않았다.
같은 계열의 한계를 이미 다른 방식으로 피하는 사용자가 있다는 뜻이지만,
효과의 근거는 아직 보이지 않는다.

### 도입 순서는 기능의 의존이 아니라 신뢰의 순서이다

원문이 제시하는 길은 `/ship`을 개인이 써 보는 것에서 시작해,
저장소 하나에 Code Review와 PR Steward를 켜고,
마지막에 승인 정책을 관찰 모드로 돌리다가 브랜치 보호에 연결한다.
권한이 낮은 단계에서 높은 단계로 올라가며
각 단계에서 사람이 결과를 보고 되돌릴 수 있는 장치(푸시마다 남는 되돌리기 안내,
`@claude stop`, 관찰 모드)가 하나씩 있다.
같은 자동화라도 되돌릴 수 있는 일을 먼저 맡기고
되돌리기 어려운 일을 나중에 맡기는 순서이며,
이 순서는 이 제품만이 아니라 에이전트에게 권한을 넘기는 다른 일에도 적용된다.
