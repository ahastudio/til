# 한 컴퓨터에서 여러 Claude 계정을 쓰고, 다른 계정에 일을 맡기는 법

## 소개

한 컴퓨터에서 Claude Code를 계정마다 따로 로그인해 두고 번갈아 쓰는 방법은 `CLAUDE_CONFIG_DIR`로 해결된다.
이 노트는 거기서 한 걸음 더 나아가, 메인 계정의 세션에서 `claude -p`로 다른 계정을 불러 일을 맡기면 메인 계정의 토큰을 아낄 수 있는지를 따진다.

결론부터 적으면, 기술적으로는 된다.
다른 계정이 한 일은 그 계정의 사용량으로 잡히고, 메인 세션에는 돌아온 결과 텍스트만 들어온다.
다만 이 방법이 값어치를 내는 일의 범위는 좁고, 약관과 데이터 문제는 이 노트가 확인하지 못했다.
그래서 이 노트의 구성은 먼저 되는 이유와 설정을 적고, 맡겨도 되는 일과 안 되는 일을 가른 뒤, 막히는 지점을 하나씩 적는다.

한 가지 먼저 밝혀 둔다.
이 노트의 명령 중 `claude auth status`와 빈 설정 폴더의 동작, 래퍼 스크립트의 환경 변수 처리는 직접 실행해 확인했다.
두 번째 계정으로 실제 모델을 호출하는 부분은 로그인한 두 번째 계정이 없어 실행하지 못했다.
그 부분은 공식 문서를 읽고 쓴 것이다.

## 동작 방식

### 설정 폴더가 계정을 가른다

`CLAUDE_CONFIG_DIR`을 정하고 실행하면 설정, 세션 기록, claude.ai 로그인이나 API 키가 그 폴더에 따로 쌓인다.[^auth]
macOS에서는 자격 증명이 키체인에 들어가는데, 이 항목도 설정 폴더에 묶여 있어서 `CLAUDE_CONFIG_DIR`이 다른 세션은 다른 항목을 읽는다.[^auth]
Linux와 Windows에서는 `.credentials.json` 파일이 설정 폴더 아래에 생긴다.[^auth]
이 변수는 프로젝트 설정과 로컬 설정에서는 지정할 수 없고, 셸이나 사용자 설정에서만 정한다.[^env]

빈 설정 폴더로 `claude auth status`를 돌리면 로그인이 안 된 상태가 JSON으로 나온다.
직접 돌려 보니 `loggedIn`이 `false`이고 `authMethod`가 `none`이었다.
이 명령은 `--json`과 `--text` 출력을 모두 지원한다.

### 자격은 환경 변수가 로그인보다 앞선다

여러 자격이 함께 있으면 Claude Code는 정해진 순서로 하나를 고른다.
클라우드 공급자 변수, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `apiKeyHelper`, `CLAUDE_CODE_OAUTH_TOKEN`이 모두 `/login`으로 저장한 구독 로그인보다 앞선다.[^auth]
비대화형 `-p`에서는 `ANTHROPIC_API_KEY`가 있으면 항상 그 키를 쓴다.[^auth]

이 순서가 다중 계정에서 가장 위험한 지점이다.
메인 세션이 환경 변수로 인증되어 있으면, `CLAUDE_CONFIG_DIR`을 바꿔 자식 세션을 띄워도 그 변수가 그대로 상속되어 같은 계정이 선택될 수 있다.
이 상속은 문서의 우선순위 규칙에서 읽어 낸 것이고, 실제 모델 호출로 재현하지는 않았다.

### `claude -p`는 결과만 돌려준다

`claude -p "<프롬프트>"`는 비대화형으로 실행되어 응답을 출력하고 끝난다.[^headless]
`--output-format json`을 주면 결과가 `result` 필드에 담기고, 세션 ID와 `total_cost_usd` 같은 메타데이터가 함께 나온다.[^headless]
비용 수치는 클라이언트 쪽 추정이어서 실제 청구액과 다를 수 있다고 문서가 밝힌다.[^headless]

메인 세션이 Bash 도구로 이 명령을 실행하면, 메인 컨텍스트에 들어오는 것은 명령의 출력 텍스트뿐이다.
위임받은 세션이 읽은 파일과 거친 추론은 그 세션 안에 남고, 메인 계정의 사용량으로는 잡히지 않는다는 것이 절약의 원리다.
이 구조는 서브에이전트가 자기 컨텍스트에서 일하고 요약만 돌려준다는 공식 설명과 모양이 같지만, 청구 대상이 다른 계정이라는 점이 다르다.

## 설정하기

### 폴더와 래퍼

계정마다 폴더를 하나씩 만들고, 계정 이름을 받는 래퍼 스크립트를 `PATH`에 둔다.
공식 문서의 예시는 `.zshrc`의 alias인데, alias는 대화형 셸에서만 펼쳐진다.
직접 확인한 결과 `zsh -c`로 띄운 비대화형 셸은 같은 `.zshrc`가 있어도 `command not found`를 냈고, `zsh -ic`로 띄운 대화형 셸에서만 alias가 동작했다.
Claude Code의 Bash 도구가 `claude-dev` 같은 alias를 쓰려는 상황이 바로 비대화형 셸이므로, 위임에는 alias 대신 실행 파일을 쓴다.

```bash
#!/usr/bin/env bash
# claude-acct: 계정 이름으로 설정 폴더를 고르고 claude를 실행한다
# 사용법: claude-acct <계정이름> [claude 인자...]
set -euo pipefail
name="${1:?usage: claude-acct <name> [claude args...]}"; shift
dir="$HOME/.claude-$name"
[ -d "$dir" ] || { echo "no config dir: $dir" >&2; exit 2; }
# 환경에 남은 자격이 /login보다 앞서므로 지운다 (계정이 섞이는 것을 막는다)
exec env -u ANTHROPIC_API_KEY -u ANTHROPIC_AUTH_TOKEN -u CLAUDE_CODE_OAUTH_TOKEN \
  -u ANTHROPIC_PROFILE CLAUDE_CONFIG_DIR="$dir" claude "$@"
```

`$HOME/.claude-dev` 폴더를 만들고 `claude-acct dev`를 처음 실행하면 그 폴더에서 로그인과 초기 설정이 시작된다.[^auth]
기본 계정은 `claude`를 그대로 쓰면 된다.

### 위임용 래퍼

`-p` 호출에는 권한 모드와 허용 도구를 반드시 정해야 한다.
수동 모드의 `-p` 실행에서는 승인이 필요한 호출이 승인 수단이 없으면 거부된다.[^headless]
아래 래퍼는 기본값을 읽기 전용 도구로 두고, 쓰는 일은 환경 변수로 열게 한다.

```bash
#!/usr/bin/env bash
# claude-delegate: 다른 계정에 일을 맡기고 결과 텍스트만 돌려받는다
# 사용법: claude-delegate <계정> "<프롬프트>"
# PERM(권한 모드), TOOLS(허용 도구)로 바꿀 수 있다
set -euo pipefail
acct="${1:?usage: claude-delegate <account> <prompt>}"; prompt="${2:?prompt}"
claude-acct "$acct" -p "$prompt" \
  --permission-mode "${PERM:-dontAsk}" \
  --allowedTools "${TOOLS:-Read,Grep,Glob}" \
  --output-format json | jq -r '.result'
```

`dontAsk`는 승인이 필요했을 호출을 모두 거부하는 모드이고, `--allowedTools`에 적힌 도구와 승인이 필요 없는 읽기는 그대로 실행된다.[^headless]
이 래퍼를 가짜 `claude`로 시험해, 설정 폴더가 계정별로 바뀌고 인자가 순서대로 전달되며 `PERM`과 `TOOLS`가 반영되는 것을 확인했다.

### 공통 설정을 나눌지 정한다

폴더가 다르면 `settings.json`, 스킬, 메모리, 권한 허용 목록이 공유되지 않는다.
같은 설정을 쓰려면 파일을 복사하거나 링크로 잇는데, 이 노트는 링크한 파일을 Claude Code가 어떻게 읽는지 시험하지 않았다.
저장소 안의 `CLAUDE.md`와 `.claude/`는 어느 계정에서 실행하든 똑같이 적용된다.

## 값 정하기

맡길지 말지는 일의 모양으로 정한다.

| 일의 모양                             | 위임          | 이유                                                |
| ------------------------------------- | ------------- | --------------------------------------------------- |
| 큰 코드베이스를 읽고 한 문단으로 요약 | 맡긴다        | 읽는 토큰이 크고 돌아오는 결과가 작다               |
| 로그나 문서 한 덩이의 분류와 추출     | 맡긴다        | 입력과 출력이 분명하고 서로 의존하지 않는다         |
| 독립된 검토(주장 확인, 코드 리뷰)     | 맡긴다        | 메인의 편향과 컨텍스트 없이 보는 것이 이점이다      |
| 메인이 이미 파일을 읽어 둔 일의 후속  | 맡기지 않는다 | 위임받은 쪽이 같은 파일을 처음부터 다시 읽는다      |
| 여러 번 주고받으며 방향을 잡는 일     | 맡기지 않는다 | 한 번의 호출이 하나의 대화여서 끼어들 수 없다       |
| 쓰기와 되돌리기가 얽힌 일             | 맡기지 않는다 | 권한을 넓게 열어야 하고 결과를 메인이 검증해야 한다 |

기준은 돌아오는 결과가 맡긴 일의 크기보다 훨씬 작은가이다.
읽는 양이 크고 결과가 작을수록 메인 계정에서 아끼는 몫이 커진다.

## 트레이드오프

### 아끼는 것은 메인의 컨텍스트이고 총 토큰은 늘어난다

위임받은 세션은 자기 시스템 프롬프트와 도구 정의를 처음부터 싣고 시작한다.
프롬프트 캐시는 계정을 가로질러 공유되지 않으므로, 두 계정을 오가면 같은 접두부를 두 번 처리한다.
이 마지막 줄은 캐시가 계정 단위라는 추정에서 나온 것이고 이 노트가 확인하지 못했다.
어느 쪽이든 두 계정의 사용량을 합하면 한 계정에서 직접 일할 때보다 많아질 수 있다.
그래서 이 방법은 총 토큰을 줄이는 방법이 아니라, 메인 계정의 한도를 쓰는 속도를 늦추는 방법이다.

### 맡긴 일은 자기 완결적이어야 한다

위임받은 세션은 메인의 대화와 읽은 파일을 보지 못한다.
프롬프트에 목적, 대상 경로, 돌려받을 형식을 모두 적어야 하고, 이것을 적는 일이 일 자체보다 오래 걸리면 위임은 손해다.
돌려받는 형식을 JSON 스키마로 고정하면 메인이 후처리하기 쉬워진다.[^headless]

### 권한을 넓게 열수록 감시가 어려워진다

`-p`는 신뢰 대화상자를 띄우지 않고, `--bare`를 쓰지 않으면 프로젝트의 훅과 MCP 서버를 그대로 불러온다.[^headless]
다른 계정에 맡긴 일이 무인으로 도는 동안 낯선 저장소의 훅이 실행될 수 있다는 뜻이다.
읽기 전용 도구와 `dontAsk`로 시작해서, 쓰기가 필요한 일에만 `acceptEdits`를 열고 되돌릴 수 있는 브랜치에서 돌린다.

### 약관과 데이터의 문제는 이 노트가 판단하지 못한다

두 계정이 모두 본인 소유인 구독이라 해도, 한도를 피하려고 일을 나누는 사용이 약관과 사용 정책에 어긋나는지는 이 노트가 확인하지 못했다.
검색에서 나온 2025년 보도는 계정 공유와 재판매가 정책 위반이라는 Anthropic의 설명을 전하지만, 이 노트는 약관 본문을 읽지 않았다.
업무용 계정을 개인 일에 쓰거나 그 반대로 쓰는 것은 한도와 별개로 조직의 규정과 데이터 처리 설정이 다를 수 있다.
계정마다 모델 학습에 쓰이는 데이터 설정과 보존 기간이 다를 수 있다는 점도 위임하는 프롬프트에 무엇을 담을지에 영향을 준다.
실제로 쓰기 전에 현재의 Consumer Terms, Usage Policy, 조직의 규정을 직접 읽어야 한다.

### 한도가 문제라면 구독 계정이 아닌 길도 있다

같은 계정 안에서는 서브에이전트에 더 가벼운 모델을 지정하는 방법이 있다.
계정을 늘리지 않고 한도를 쓰는 속도를 줄이는 방법이라 약관 문제가 없다.
별도 청구를 원하면 Claude Console의 API 키를 `ANTHROPIC_API_KEY`로 주는 방법이 있다.
`-p`에서는 이 키가 있으면 항상 쓰이고, `--bare`는 구독 로그인을 읽지 않고 이 키를 쓰도록 만들어졌다.[^headless]
이 경우 비용은 사용량만큼 청구되고, 구독 한도와는 별개다.

## 함정

### `--bare`는 구독 로그인을 읽지 않는다

`--bare`는 시작이 빠르고 호스트의 설정에 영향받지 않아 스크립트에 권장되지만, OAuth 자격과 키체인을 읽지 않는다.[^headless]
`CLAUDE_CODE_OAUTH_TOKEN`도 읽지 않는다.[^auth]
그래서 두 번째 구독 계정으로 위임할 때 `--bare`를 붙이면 인증이 실패한다.
구독 계정으로는 `--bare`를 빼고, 대신 훅과 MCP, `CLAUDE.md`가 로드되는 것을 감수해야 한다.

### 환경 변수 자격이 조용히 계정을 바꾼다

메인 세션을 `CLAUDE_CODE_OAUTH_TOKEN`이나 `ANTHROPIC_API_KEY`로 띄웠다면, 래퍼가 그 변수를 지우지 않는 한 자식 세션도 같은 자격을 쓸 수 있다.
위의 `claude-acct`가 `env -u`로 이 변수들을 지우는 이유다.
가짜 `claude`로 시험해, 부모에 `ANTHROPIC_API_KEY`와 `CLAUDE_CODE_OAUTH_TOKEN`이 있어도 자식에게는 전달되지 않는 것을 확인했다.

### 장기 토큰은 구독 로그인의 대체가 아니다

`claude setup-token`이 만드는 토큰은 1년짜리이고 모델 요청만 할 수 있다.[^auth]
원격 제어 세션을 만들거나 claude.ai 커넥터를 가져오지 못한다.[^auth]
위임 용도로는 충분하지만, 이 토큰을 환경 변수로 걸어 두면 다른 계정의 로그인보다 앞서므로 계정별로 따로 두어야 한다.

### 로그인이 만료되면 위임이 조용히 실패한다

저장된 로그인이 만료되면 모델 요청이 `Login expired` 오류로 실패한다.[^auth]
`-p`에서는 인증 실패가 결과로 출력되고 종료 코드가 0이 아닐 수 있으므로, 래퍼는 종료 코드와 `result`를 확인해야 한다.
위의 `claude-delegate`는 `jq`로 `result`만 뽑을 뿐 오류를 구분하지 않으므로, 쓰는 사람이 직접 점검 단계를 더해야 한다.

### Console 로그인은 설정 폴더로 갈리지 않는다

문서는 API 키 없이 Console 계정으로 로그인한 경우를 설정 폴더로 나눌 수 없다고 적는다.[^auth]
그 로그인은 설정 폴더 밖에 저장되기 때문이다.
Console 계정을 둘 이상 쓸 때는 이 방법이 통하지 않는다.

## 확인하기

계정마다 로그인이 따로 유지되는지 한 번에 본다.

```bash
# 각 설정 폴더가 서로 다른 로그인을 가졌는지 확인한다
for name in dev work; do
  echo "== $name"
  claude-acct "$name" auth status --text
done
```

두 출력의 계정 정보가 달라야 한다.
같은 계정이 두 번 나오면 환경 변수 자격이 걸려 있는 것이니 `env | grep -E 'ANTHROPIC|CLAUDE_CODE_OAUTH'`로 찾는다.

위임이 실제로 다른 계정으로 가는지는 두 계정의 사용량 표시를 비교해 본다.
같은 작은 요청을 보내고 어느 계정의 사용량이 늘었는지 보는 방법이고, 이 노트는 이 실험을 하지 못했다.
`--output-format json`의 `total_cost_usd`는 추정치라서 계정 구분의 근거로 쓰지 않는다.

## 체크리스트

- 계정마다 설정 폴더가 따로 있고 `claude auth status`가 서로 다른 계정을 보여 주는가.
- 위임 호출이 alias가 아니라 `PATH`의 실행 파일을 쓰는가.
- 래퍼가 `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`을 지우는가.
- 구독 계정으로 위임하는 호출에 `--bare`가 붙어 있지 않은가.
- `--permission-mode`와 `--allowedTools`를 정했고 기본값이 읽기 전용인가.
- 맡기는 프롬프트에 목적, 경로, 돌려받을 형식이 모두 들어 있는가.
- 돌아오는 결과가 맡긴 일의 크기보다 충분히 작은가.
- 쓰기를 맡길 때 되돌릴 수 있는 브랜치에서 돌리는가.
- 위임 호출의 종료 코드와 `result`를 확인하는가.
- 약관, 사용 정책, 조직 규정, 계정별 데이터 설정을 직접 읽어 확인했는가.

## 기억할 원칙

### 아끼는 것이 무엇인지 먼저 적는다

위임이 줄이는 것은 메인 계정의 컨텍스트와 사용량이고, 전체 토큰이 아니다.
이것을 적어 두지 않으면 절약이라는 이름 아래 두 계정의 합계가 늘어도 알아채지 못한다.
위임할 일의 기준은 읽는 양은 크고 돌아오는 결과는 작은 일이다.

### 계정을 나누는 일은 기술 문제 앞에 정책 문제다

설정 폴더로 계정을 가르는 방법은 공식 문서가 직접 권하는 사용법이다.
그 위에 한도를 피하려고 일을 나누는 흐름을 얹는 것은 다른 문제이고, 그 답은 설정 파일이 아니라 약관과 조직의 규정에 있다.
기술적으로 되는 것과 해도 되는 것을 따로 확인한다.
