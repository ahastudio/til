# patent-harness: 청구항을 쓰는 에이전트와 거절하는 에이전트를 나눈 특허 출원 준비 하네스

<https://github.com/revfactory/patent-harness>

## 소개

patent-harness는 아이디어 메모나 선행기술 조사 보고서를 넣으면 Claude Code
에이전트 15개가
특허 출원 준비 서류 8종을 만든다고 설명하는 하네스입니다.
서류는 검토 보고서, 발명신고서, 청구범위, 명세서 초안, SVG 개략도,
시험 계획, 출원 전략과 일정표, 검증 원장입니다.
저장소는 2026년 10월 25일에 만들어졌고 별은 23개,
포크는 16개이며 커밋은 두 개입니다.
이 문서는 README와 오케스트레이터 스킬, 기한표, 청구항 검사 스크립트,
모의 심사관
정의를 읽어 정리한 것입니다.
하네스를 직접 실행해 서류를 만들어 본 결과가 아니고,
법률 내용의 정확성도 확인하지
않았습니다.

구성은 에이전트 15개, 스킬 11개, 스크립트 4개이며 파일 목록과 일치했습니다.
모델은 일의 종류로 나뉩니다.
법리와 기술을 함께 따지거나 긴 법률 문서를 쓰는 일곱 개는 opus,
원문 대조와 수집과 편집처럼 절차가 정해진 일곱 개는 sonnet,
막연한 아이디어에서 과제와 변형례를 스스로 정해야 하는 발명 발굴가 하나는
fable입니다.
README는 쓸 수 없는 모델이면 각 정의 파일의 `model:` 값만 바꾸면 된다고
적습니다.

## 과제 유형과 단계

과제 유형은 세 가지이고, 오케스트레이터 스킬이 요청을 읽어 유형과 실행 단계를
정합니다.

| 유형          | 쓰는 경우                               | 실행 단계                              |
| ------------- | --------------------------------------- | -------------------------------------- |
| R 보고서 검토 | 외부 기관의 선행조사 보고서를 받았을 때 | 0 → 1R → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9 |
| D 신규 발굴   | 메모나 회의록에서 출원할 발명을 찾을 때 | 0 → 1D → 2 → 3 → 후보 선택 → 4 → 9     |
| F 출원 준비   | 발명신고서가 확정됐을 때                | 0 → 4 → 5 → 6 → 7 → 8 → 9              |

D 유형에서 후보를 고르는 일에는 사업 판단이 들어가므로 사용자에게 묻고,
원하면 이어서 F 유형을 실행합니다.

단계마다 실행 방식이 다릅니다.

| 단계 | 하는 일                                             | 실행 방식                  |
| ---- | --------------------------------------------------- | -------------------------- |
| 1    | 특허 번호 추출, 본문 변환, 보고서 주장 분류         | 리더가 직접, 스크립트      |
| 2    | 서지 대조, 불일치 재확인, 보충 검색, 시장 주장 확인 | Workflow(문헌 묶음별 병렬) |
| 3    | 신규성·진보성, 자유실시 위험, 공백 영역 분석        | 서브에이전트 3개 병렬      |
| 4    | 발명신고서, 발명자 질문, 시험 계획                  | 서브에이전트 2개 병렬      |
| 5    | 청구항 작성과 모의 심사(최대 2회)                   | 지속형 에이전트 협업       |
| 6    | 도면 부호표와 SVG 개략도, 명세서                    | 지속형 에이전트 협업       |
| 7    | 형식 검사, 작성자 수정, 재검사 1회                  | 단발 검사와 지속형 수정    |
| 8    | 권리 형태, 출원 경로, 기한 일정표                   | 단발                       |
| 9    | 보고서 편집과 리더의 최종 검토                      | 단발과 리더 검토           |

5·6단계에 지속형 에이전트를 쓰는 이유로 README는 청구범위 작성가가 지적받은 항만
고치려면 이전 버전의 맥락을 기억해야 한다는 점을 듭니다.
모의 심사관은 작성가에게 직접 수정을 요구하지 않고,
의견서와 수정 요청은 리더가 전달하며 반복 횟수도 리더가 셉니다.

## 에이전트가 맡는 확인

README는 LLM 하나에게 청구항을 쓰게 하면 청구항 문체의 문장이 나올 뿐이고,
그 문장이 선행문헌을 피하는지는 따로 확인해야 알 수 있다고 말하며
확인을 맡을 에이전트를 따로 두었다고 설명합니다.

| 확인할 것                                      | 맡는 쪽                                                                                               |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 보고서의 특허 번호, 출원인, 법적 상태          | 서지 검증가가 Google Patents 원문과 항목별로 대조하고, `일치`가 아닌 판정은 다른 검증가가 다시 확인   |
| 요약이 청구 범위를 실제보다 넓게 적었는가      | 청구항 1과 초록 기준으로 대조해 `불일치(범위 과장)`로 표시                                            |
| 청구항이 어떤 이유로 거절될 수 있는가          | 모의 심사관이 의견제출통지서 형식으로 거절 이유를 쓰고, 판정이 애매하면 출원인에게 불리한 쪽으로 정함 |
| 보정안이 거절 이유를 해소했는가                | 이유마다 `해소`, `일부 해소`, `미해소`. 청구항 문언만 보고 판정                                       |
| '상기 X'의 X가 앞에 있는가, 도면 부호가 맞는가 | `check_claims.py`와 `check_spec.py`가 의심 목록을 만들고 형식 검사관이 정독해 오탐을 제외             |
| 제품이 남의 특허를 침해하는가                  | 자유실시 분석가가 존속 특허 독립항과 제품 구성을 구성요소 완비 원칙으로 대비하고 회피 설계를 냄       |

## 출원 전 공개를 막는 규칙

특허는 출원 전에 발명 내용이 공개되면 신규성을 잃을 수 있다고 README가 적고,
15개 에이전트 정의 파일 모두에 같은 규칙을 넣었다고 합니다.
산출물과 발명 내용을 Artifact, 문서 커넥터, 외부 공유 서비스에 올리지 않고,
결과는 프로젝트 폴더의 `_workspace/{case}/`와 `outputs/{case}/`에만 쓰며,
사용자 홈 폴더와 세션 메모리 디렉터리에는 쓰지 않고,
패키지를 설치할 때 캐시가 홈 폴더에 남지 않게 한다는 것입니다.
모의 심사관 정의 파일에서 이 규칙이 작업 원칙의 맨 앞에 들어 있는 것을
확인했습니다.

## 분석

### 쓰는 쪽과 거절하는 쪽을 분리하고 거절하는 쪽에 편향을 주었다

이 하네스에서 가장 분명한 설계는 청구범위 작성가와 모의 심사관을 따로 둔
것입니다.
모의 심사관 정의는 출원인 편을 들지 않는다고 적고,
판정 기준이 애매하면 출원인에게 불리한 쪽으로 판정하며 그 이유를 쓰라고 합니다.
모의 심사의 목적이 실제 거절 가능성을 미리 드러내는 것이라는 이유입니다.
또 판정은 청구항 문언으로만 하게 합니다.
같은 파일에는 실제 사건에서 메모에는 시험 조건을 적었다고 했으나 문언에는
시간 기준만
있었다는 사례가 근거로 붙어 있습니다.

### 단계마다 실행 모드를 이유와 함께 골랐다

오케스트레이터 스킬은 단계마다 실행 모드와 그 이유를 표로 적습니다.
문헌 목록을 미리 확정해 묶음별로 나눌 수 있고 판정을 스키마로 받아 코드로
합칠 수 있는
2단계는 Workflow, 서로 독립인 3·4단계는 서브에이전트 병렬,
이전 버전 맥락이 필요한 5·6단계는 지속형 협업입니다.
같은 저자의 [Harness](harness.md)가 말하는 세 가지 실행 모드를 한 파이프라인
안에서 단계별로
섞어 쓴 사례입니다.

### 사실은 스크립트로, 판단은 에이전트로 나누었다

특허 번호 추출, 원문 가져오기, 청구항 형식 검사,
명세서 검사는 스크립트가 맡습니다.
`check_claims.py`는 번호 누락, 종속 관계, `상기 X`의 선행 근거, 불명확 표현(약,
대략, 바람직하게,
등), 한 항에 문장이 둘 이상인 경우를 찾고,
결과가 의심 목록이며 오탐을 걸러 내는 일은
검사관이 한다고 파일 머리말에 적습니다.
같은 결과가 나와야 하는 일은 코드로, 읽고 판단해야 하는 일은 에이전트로 나눈
것입니다.

### 단계를 넘길 때 파일을 고정한다

청구항 확정본을 넘길 때 `shasum`으로 해시(`freeze_04.sha`)를 남기고,
보고서를 쓰기 직전에 `shasum -c`로 바뀌지 않았는지 확인합니다.
고정한 뒤 고칠 내용은 새 버전 파일로 씁니다.
단계 사이에서 산출물이 조용히 바뀌는 일을 값싸게 막는 장치입니다.

### 실패를 규칙으로 바꾼 기록이 남아 있다

README는 실제 사건 하나를 0단계부터 9단계까지 실행하며 문제가 나올 때마다
정의 파일과
스크립트를 고쳤다고 하고, 그중 여덟 건을 표로 보여 줍니다.
예를 들어 Google이 표시한 상태만 보고 내린 판정 세 건이 재확인에서 뒤집혀서
법적 이벤트 표를 함께 가져오도록 스크립트를 고쳤고,
동시 요청 때문에 503 차단을 세 번 받아 요청 간격을 2초로 늘렸고,
에이전트가 사용자 홈 폴더의 메모리 디렉터리에 기록을 남긴 일이 있어 홈 폴더
쓰기를 금지했습니다.

## 비평

### 근거가 된 실행 사례를 확인할 수 없다

규칙이 실제 사건 실행에서 나왔다는 설명이 이 저장소의 신뢰 근거인데,
README는 공개 전에 정의 파일과 스킬의 사건 유래 예시를 가상 사례(등산화 밑창)와
형식 예시로 바꿨다고 밝힙니다.
저장소에는 만들어진 서류 샘플(청구항, 모의 의견서,
보고서)이 없고 소개 GIF만 있습니다.
그래서 8종 서류의 품질도, 표에 적힌 고친 규칙의 실제 효과도 독자가 확인할 방법이
없습니다.

### 법적 판단의 정확도를 잰 자료가 없다

신규성·진보성 판단, 자유실시 위험 등급,
모의 거절 이유는 모두 모델이 내는 판단입니다.
README는 산출물이 초안이고 출원 전에 변리사 검토를 받아야 한다고 적으며,
이 판단들이 변리사나 실제 심사 결과와 얼마나 일치하는지는 보여 주지 않습니다.
모의 심사관과 청구범위 작성가가 같은 계열의 모델이므로 같은 맹점을 공유할 수
있다는 점은
이 문서의 추정이고, 저장소가 이를 다루지는 않습니다.

### 외부 검색 도구가 공개 통제의 빈틈이 될 수 있다

공개 통제 규칙은 Artifact, 문서 커넥터, 외부 공유 서비스,
홈 폴더 쓰기를 막습니다.
그런데 확인한 모의 심사관 정의의 도구 목록에는 `WebFetch`와 `WebSearch`가 들어
있습니다.
검색 질의에 발명의 핵심 용어가 담길 수 있는데 그 경로를 다루는 규칙은 읽은
범위에 없었고,
이는 이 문서의 추정입니다.
README는 발명 내용이 Claude API로 전송된다는 점을 인정하며 미공개 발명을 다뤄도
되는지는
소속 기관의 보안 정책을 먼저 확인하라고 적습니다.

### 데이터 출처가 막히기 쉽고 값이 추정이다

서지 검증은 Google Patents 페이지를 스크립트로 가져오는 데 기댑니다.
README는 Google의 법적 상태와 만료 예정일이 추정값이어서 각국 특허청 원부로
확인해야 하고,
KIPRIS와 J-PlatPat은 자동 접근이 막히는 경우가 많아 그때는 대체 데이터베이스
결과를 쓰고
“원부 확인 필요” 목록에 올린다고 적습니다.
자동 수집이 이용 약관과 어떤 관계인지는 README에 없고,
이 문서도 확인하지 않았습니다.
판단 기준은 한국 특허법과 심사기준뿐이며 상표는 범위 밖입니다.

### 가져다 쓸 때의 조건이 적혀 있지 않다

README는 다른 프로젝트에서 쓰려면 `.claude/` 폴더를 복사하라고 안내하지만,
저장소 파일 목록에 라이선스 파일이 없고 GitHub의 라이선스 항목도 비어 있습니다.
복사와 수정이 허용되는지가 명시되지 않았습니다.
또 2단계는 문헌 묶음마다 검증가를 띄워 에이전트를 열 개 가까이 쓰고
README가 토큰 사용량이 많다고 경고하지만, 얼마나 드는지는 적지 않습니다.

## 인사이트

### 1. 고위험 문서는 쓰는 에이전트와 반박하는 에이전트를 나눈다

반박하는 쪽에는 쓰는 쪽 편을 들지 않는 지시, 애매하면 불리하게 판정하는 규칙,
작성자의 메모가 아니라 결과물의 문언만 보고 판정하는 규칙을 함께 준다는 점이
이 설계에서 옮겨 쓸 만한 구체적인 부분입니다.
법률 문서가 아니어도 계약서, 보안 보고서,
설계 문서처럼 틀리면 비싼 글에 같은 구조를 쓸 수 있습니다.

### 2. 같은 결과가 나와야 하는 확인은 코드로 만든다

형식 검사는 스크립트가 의심 목록을 만들고 에이전트가 정독해 오탐을 제외하는
두 단계로
하는 편이 한 단계로 하는 것보다 안정적이라고 이 저장소는 보여 줍니다.
스크립트를 쓰면 같은 입력의 결과가 같고, 에이전트는 오탐 판단에만 쓰입니다.

### 3. 단계를 넘길 때 해시로 고정한다

`shasum`으로 확정본의 해시를 남기고 다음 단계 직전에 확인하는 방식은 어떤 다단계
파이프라인에도 붙일 수 있는 값싼 장치입니다.

### 4. 도입 전에 결과를 아는 사건으로 시험한다

라이선스는 저장소 주인에게 묻습니다.
