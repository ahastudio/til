# 컴퓨터 사용이 정식 출시되고 좌표 대신 요소 참조로 웹을 다루는 도구가 붙었다

원문: [Build production agents with computer use, the Skills API, and the Files API](https://claude.com/blog/computer-use-skills-api-files-api)

GN 토론: <https://news.hada.io/topic?id=32754>

## 요약

Anthropic이 2026년 8월 20일에 올린 제품 발표이며,
컴퓨터 사용과 Skills API와 Files API가
Claude 플랫폼에서 정식 출시됐다는 내용이다.
읽는 시간이 5분으로 표시된 짧은 글이다.

세 기능의 역할을 각각 정리한다.
컴퓨터 사용은 에이전트가 보이는 소프트웨어를 조작하게 하는 것이며,
스크린숏이 주어지면 사람이 키보드 앞에서 하듯
클릭하고 타이핑하고 스크롤한다.
그래서 자동화를 염두에 두지 않고 만들어진 애플리케이션에서도 작동한다.
Skills API는 지시와 스크립트와 템플릿이 담긴 폴더를
작업이 요구할 때만 Claude가 불러오게 하는 것이며,
자기 스킬을 올리고 버전을 관리해 아무 요청에나 붙일 수 있고
Claude의 코드 실행 샌드박스에서 돌므로 직접 호스팅할 것이 없다.
Files API는 에이전트가 읽고 쓰는 문서의 저장소이며,
PDF나 스프레드시트를 한 번 올려 두고
이후 요청에서 다시 보내는 대신 ID로 참조하고
에이전트가 만든 파일을 내려받는다.

새로 추가된 것이 브라우저 사용 도구다.
컴퓨터 사용을 웹으로 확장한 것이며,
스크린숏과 함께 페이지의 구조를 읽어
화면상의 위치가 아니라 특정 필드나 버튼에 대해 행동한다.

정식 출시로 달라진 점을 네 항목으로 든다.
컴퓨터 사용 도구가 모델 호출마다 한 동작이 아니라
한 턴에 여러 동작을 하게 되어 더 적은 호출과 시간으로 작업이 끝나며,
BAA 아래 HIPAA 규제 워크로드에도 쓸 수 있게 됐다.
브라우저 사용 도구는 같은 다중 동작 턴을 쓰면서 페이지 구조를 더하므로
픽셀만으로 할 때보다 웹 요소를 더 안정적으로 겨냥한다.
Skills API는 자기 스킬을 올리고 버전을 관리하는 더 단순한 API가 됐고,
Files API는 자동 파일 만료와 5배 높은 요청 한도와
조직당 1 TB 저장 공간을 얻었다.

사용 예로 보험금 청구 에이전트를 든다.
Files API에서 접수 문서를 읽고,
팀의 접수 절차가 담긴 스킬을 따르고,
브라우저 사용 도구로 보험사 웹 포털에서 제출을 완료하고,
확인서를 파일로 저장한다는 흐름이다.
이미 정식 출시된 코드 실행과 웹 검색이 같은 루프에 들어간다고 덧붙인다.

고객 인용이 둘이다.
Asteroid의 연구 엔지니어는
API가 없는 의료·보험 시스템 안에서 에이전트가 일하며,
새 컴퓨터 사용 도구에서 가장 긴 청구 워크플로가
32분에서 13분으로 줄고,
시험한 모든 워크플로에서 작업당 비용이 약 30% 떨어지고,
완료율이 100%에 도달했으며
프롬프트는 하나도 바꾸지 않았다고 말한다.
Box의 뱅킹 총괄은 Skills API가
Box Agent에 특화된 문서 생성을 넣는 직관적인 방법이었다고 말하며,
은행의 경우 스킬 하나가 그 회사의 신용 방법론과
승인된 메모 형식을 담고,
Box Agent가 그것을 이미 Box에 있는 재무제표와 거래 문서에 적용해
분석가 검토용 신용 메모를 만든다고 설명한다.

Skills API와 Files API는 Microsoft Foundry를 통해서도 쓸 수 있고,
갱신된 컴퓨터 사용과 브라우저 사용 도구는
Google Cloud의 Vertex AI에 곧 온다고 밝힌다.
기존 베타 연동은 이행 기간 동안 계속 작동한다.

## 브라우저 사용 도구의 실제 규격

발표문이 짧으므로 플랫폼 문서를 함께 읽어야 실제 모양이 보인다.

이 도구는 클라이언트 도구 모음이다.
`tools` 배열에 `browser_toolset_20260801` 한 항목을 넣으면
기본으로 27개의 멤버 도구가 생기며,
`navigate`와 `read_page`와 `left_click`과 `screenshot` 같은 것들이다.
선택적으로 켤 수 있는 네 개가 더 있다 —
`javascript_exec`, `file_upload`, `read_console`, `read_network`다.
그리고 결정적인 문장이 하나 있다 —
모든 호출은 사용자의 애플리케이션이 자기 브라우저 자동화에 대해 실행하며
Anthropic 쪽에서는 아무것도 돌지 않는다.

컴퓨터 사용과의 차이가 명시된다.
컴퓨터 사용은 스크린숏과 좌표만으로 데스크톱 전체를 다루고,
브라우저 사용은 구조 — 접근성 트리, 요소, 폼, 탭 — 와
픽셀 — 스크린숏과 뷰포트 좌표 — 을 함께 쓴다.
작업이 웹페이지 안에 머문다면 후자를 고르라고 안내하며,
읽기만 필요하면 웹 페치와 웹 검색이 더 가볍다고 덧붙인다 —
그쪽은 서버 도구라 API가 대신 실행하므로 운영할 브라우저가 없다.

요소 참조가 이 도구의 핵심 장치다.
`read_page`의 결과가 요소마다 참조를 달아 돌아온다 —
`link "Documentation" [ref_1]`, `textbox "Search docs" [ref_3]` 같은 형태다.
그러면 다음 턴에서 `ref_2`를 클릭할 수 있으므로
스크린숏에서 링크를 찾는 단계가 사라진다.
위치를 받는 멤버는 `target` 객체를 받는데
뷰포트 픽셀 좌표(`CoordinateTarget`)이거나
요소 참조(`RefTarget`)다.

일괄 동작의 규칙이 엄격하다.
한 턴에 여러 멤버 호출이 오면 나온 순서대로 실행하고,
첫 실패에서 멈추고,
이후의 모든 호출에 `is_error: true`와 함께
정확히 `Not executed: an earlier action in this turn failed.`라는 문장을 답해야 한다.
병렬 도구 사용과 응답 모양이 같은데
동시 실행이 아니라 순차 실행이라는 점이 다르다.
실행기가 왕복마다 한 호출만 처리할 수 있으면
`tool_choice`에 `disable_parallel_tool_use`를 켜면 된다.

좌표 처리에 함정이 있다.
도구 모음이 화면 크기를 선언하지 않으므로
Claude가 돌려받은 스크린숏에서 뷰포트 크기를 추론하며,
따라서 스크린숏 크기를 일관되게 유지해야 한다.
그리고 API가 도구 모음 이미지를 축소해 주지 않는다 —
모델의 이미지 크기 한도를 넘으면,
또는 요청에 이미지가 20개를 넘으면 적용되는 더 엄격한 한도를 넘으면
요청이 거부된다.
그래서 돌려주기 전에 크기를 줄이고
Claude가 내놓는 좌표를 그 배율의 역수로 되돌려야 한다.

## 비용과 한계

문서의 가격 절에 발표문에 없는 수치가 있다.

`browser_toolset_20260801`을 기본 멤버로 선언하는 것만으로
요청에 약 6,600 입력 토큰이 붙는다.
Fable 5와 Mythos 5와 Opus 5와 Opus 4.8에서 약 6,610이고
Sonnet 5에서 약 6,670이며,
멤버 도구 정의와 도구 사용 시스템 프롬프트를 덮는 값이다.
선택적 멤버 네 개를 모두 켜면 약 880 토큰이 더 붙고,
`configs`로 멤버를 끄면 줄어든다.
그 위에 스크린숏과 확대 이미지가 이미지 입력으로 과금되고,
접근성 트리와 페이지 텍스트와 콘솔·네트워크 항목 같은
텍스트 결과도 과금된다.

한계 목록이 다섯 항목이다.
브라우저 사용은 Claude API에서만 쓸 수 있고,
스트리밍할 때 각 멤버의 `input`이
하나의 완전한 `input_json_delta`로 도착하며,
요소 참조가 최선 노력이라는 것이다 —
가상화된 목록과 캔버스로 렌더링되는 인터페이스와
스크롤할 때 다시 렌더링되는 페이지는
안정적인 참조를 노출하지 못할 수 있고
그런 곳에서는 Claude가 스크린숏과 좌표 클릭으로 되돌아간다.
`read_console`과 `read_network`는
사용자의 브라우저 자동화가 잡을 수 있는 것만,
그것도 탭에 붙은 시점 이후만 보고한다.
그리고 지연과 시각 인식 정확도와
프롬프트 인젝션 위험이 컴퓨터 사용에서 그대로 이어진다.

데이터 처리의 경계도 명시된다.
브라우저 세션과 내려받은 파일과 올린 파일은 사용자 환경에 남고,
사용자가 돌려주는 스크린숏과 페이지 텍스트와 탭 상태는
API 요청 내용의 일부가 되어 표준 보존 정책을 따른다.
브라우저 사용 도구는 ZDR 대상이다.

## Skills API와 Files API의 실제 규격

같은 발표에 함께 실린 나머지 둘도 문서를 열면 조건이 붙는다.

Skills의 컨텍스트 비용이 세 단계로 공개되어 있다.

| 단계 | 적재 시점  | 토큰 비용        | 내용                        |
| ---- | ---------- | ---------------- | --------------------------- |
| 1    | 항상(시작) | 스킬당 약 100    | 프론트매터의 이름과 설명    |
| 2    | 발동될 때  | 5,000 미만       | `SKILL.md` 본문의 지시      |
| 3+   | 필요할 때  | 접근 전까지 없음 | 번들 파일과 스크립트의 출력 |

1단계가 항상 적재된다는 점이 중요하다.
스킬 하나당 약 100 토큰이므로
스킬 50개를 붙이면 요청마다 5,000 토큰이 고정으로 붙는다.
3단계에는 실용적 상한이 없다고 명시하는데,
접근하지 않은 번들 내용은 컨텍스트를 쓰지 않기 때문이다.
스크립트는 bash로 실행되고 출력만 컨텍스트에 들어가며
스크립트 코드 자체는 들어가지 않는다.

동작 방식이 파일 시스템 위에서 이루어진다.
스킬이 발동되면 Claude가 bash로 `SKILL.md`를 읽고,
그 지시가 다른 파일을 참조하면 추가 bash 호출로 그것도 읽는다.
그래서 Skills를 API에서 쓰려면 코드 실행 도구가 전제 조건이며,
스킬이 도는 컨테이너가 그 도구의 컨테이너다.
`container` 매개변수에 `skill_id`를 지정하는 방식이고,
미리 만들어진 것으로 `pptx`와 `xlsx`와 `docx`와 `pdf`가 있다.

API에서 스킬이 도는 환경에 제약이 셋 있다.
네트워크 접근이 없어서 외부 API 호출과 인터넷 접근이 불가능하고,
실행 중 패키지 설치가 불가능하며,
미리 설치된 패키지만 쓸 수 있다.
Claude Code에서는 반대로 전체 네트워크 접근이 있으며 —
사용자 컴퓨터의 다른 프로그램과 같은 수준이다 —
전역 패키지 설치는 권장되지 않는다고 적는다.

공유 범위가 표면마다 다르다.
claude.ai는 사용자 개인 단위이고
팀 구성원이 각자 올려야 하며,
중앙 관리자 관리나 조직 단위 배포를 지원하지 않는다.
Claude API는 워크스페이스 전체이므로
워크스페이스 구성원 전원이 올려진 스킬에 접근한다.
Claude Code는 개인 또는 프로젝트 기반이다.
그리고 표면 사이에 동기화되지 않는다 —
claude.ai에 올린 것은 API에 따로 올려야 하고,
API에 올린 것은 claude.ai에서 쓸 수 없다.

Files API의 규격에 발표문과 다른 무게의 항목이 있다.
파일당 최대 500 MB이고,
`expires_in_seconds`를 업로드 시 넣으면 자동 만료가 걸리는데
3,600초(1시간)에서 7,776,000초(90일) 사이의 정수이며
업로드 시 한 번 정해지고 이후 바꿀 수 없다.
만료되면 내용 다운로드가 404가 되고,
메타데이터는 최대 30일간 계속 읽히며
그 기간에는 목록 응답에도 계속 나타난다.
그리고 올린 파일은 내려받을 수 없다 —
내려받을 수 있는 것은 스킬이나 코드 실행 도구가 만든 파일이다.

가장 중요한 항목이 접근 범위다.
문서가 굵은 글씨로 적는다 —
업로드된 파일은 워크스페이스 전체에서 접근 가능하며
최종 사용자나 대화나 세션 단위로 제한되지 않는다는 것이다.
같은 워크스페이스의 어떤 API 키든 거기 업로드된 어떤 파일에도 접근하며,
별도 워크스페이스에 배정하지 않으면
모든 키가 조직의 기본 워크스페이스를 공유한다.
그래서 최종 사용자나 신뢰할 수 없는 출처에서
`file_id` 값을 받지 말라고 경고한다 —
사용자가 준 파일 ID는
한 사용자가 다른 사용자가 올린 내용을 읽게 만들기 때문이다.
파일 ID를 서버 측 참조로 취급하고
사용자와 파일의 대응을 애플리케이션이 관리하라고 적는다.

## 분석

### 실행이 클라이언트에 남는다는 설계가 이 도구의 성격을 정한다

문서의 한 문장이 이 도구의 위치를 결정한다.
모든 호출을 사용자의 애플리케이션이 자기 브라우저 자동화에 대해 실행하며
Anthropic 쪽에서는 아무것도 돌지 않는다는 것이다.

이 설계가 발표문의 표현과 대비된다.
발표문은 “에이전트가 보이는 소프트웨어를 조작하게 한다”고 적어
기능이 제공되는 것처럼 읽히는데,
실제로 제공되는 것은 27개 멤버의 이름과 스키마와
그것을 부르는 모델의 판단이다.
브라우저를 띄우고 클릭을 실행하고 스크린숏을 찍는 일은 전부 사용자 쪽이며,
Skills API가 코드 실행 샌드박스에서 돌아
호스팅할 것이 없다고 명시한 것과 정반대다.

그러면 이 도구가 만드는 작업량도 정해진다.
멤버 27개에 대응하는 실행기를 구현해야 하고,
일괄 동작의 순차 실행과 중단 규칙을 지켜야 하고,
`browser_state` 블록의 형식 규칙을 지켜야 하고,
스크린숏 크기를 한도 안으로 줄이고 좌표를 역산해야 한다.
문서의 오류 표가 그 부담의 크기를 보여 준다 —
API가 대화 안의 모든 멤버 `tool_use`와 `tool_result` 블록을 검증하고
형식이 잘못되면 Claude가 돌기 전에 `invalid_request_error`를 낸다.

이 구조에 이점도 있다.
브라우저가 사용자 환경에 있으므로
로그인 세션과 쿠키와 사내망 접근이 그대로 쓰이고,
문서가 밝힌 대로 세션과 파일이 그 환경을 벗어나지 않는다.
API가 없는 시스템을 다루는 것이 이 도구의 용도이므로 —
Asteroid의 인용이 정확히 그 경우다 —
그 시스템에 이미 접근 가능한 쪽에서 실행하는 것이 유일한 방법이기도 하다.

### 요소 참조가 컴퓨터 사용의 가장 큰 약점을 겨냥한다

이 릴리스에서 기술적으로 새로운 것이 하나다.
좌표 대신 참조로 요소를 지목하는 것이다.

컴퓨터 사용의 실패 양상이 대부분 좌표에서 나왔다.
스크린숏을 보고 픽셀 위치를 추정하므로
해상도가 바뀌거나 요소가 조금 움직이면 다른 곳을 클릭하고,
그 실패가 조용해서 —
클릭은 성공했고 대상만 틀렸으므로 —
루프가 잘못된 상태에서 계속 진행한다.
`read_page`가 `[ref_1]` 형태의 참조를 돌려주면
그 추정 단계가 없어지므로 이 실패 모드가 사라진다.

발표문의 표현이 이 차이를 정확히 담았다 —
화면상의 위치가 아니라 특정 필드나 버튼에 대해 행동한다는 것이다.
그리고 문서가 대안 경로도 남겼다.
참조가 최선 노력이므로
가상화된 목록과 캔버스 렌더링과
스크롤 시 재렌더링되는 페이지에서는
안정적 참조가 나오지 않고 좌표 클릭으로 되돌아간다는 것이다.
두 경로를 함께 두는 것이 현실적인 설계다.

그런데 이 이점이 브라우저 밖으로 확장되지 않는다.
접근성 트리가 있어야 참조가 만들어지므로
데스크톱 애플리케이션에는 같은 장치를 쓸 수 없고,
컴퓨터 사용은 여전히 스크린숏과 좌표뿐이다.
그러면 이 릴리스가 실제로 개선한 범위가
“웹 안에 머무는 작업”이며,
Asteroid의 인용이 웹 포털 작업이라는 점이 그 범위를 확인한다.

### 6,600 토큰이라는 고정비가 이 도구의 적용 범위를 좁힌다

문서의 가격 절에 있는 수치가
발표문에서 가장 크게 빠진 정보다.

도구 모음을 선언하는 것만으로 요청마다 약 6,600 입력 토큰이 붙는다.
멤버 정의 27개와 도구 사용 시스템 프롬프트의 비용이며,
선택적 멤버를 다 켜면 약 7,500이 된다.
에이전트 루프는 매 턴 요청을 다시 보내므로
이 값이 턴마다 반복되고,
프롬프트 캐싱이 걸리면 캐시 단가로 내려가지만
캐시 쓰기 비용이 먼저 든다.

이 고정비가 짧은 작업에 불리하게 작동한다.
페이지 하나를 열어 값 하나를 읽는 작업이라면
실제 내용보다 도구 정의가 큰 요청이 되며,
문서가 그 경우의 대안을 먼저 제시한다 —
읽기만 필요하면 웹 페치와 웹 검색이 더 가볍고
서버 도구라 브라우저를 운영할 필요가 없다는 것이다.
즉 이 도구의 손익분기가 존재하고,
그 계산이 문서에 있고 발표문에 없다.

같은 구조가 Skills에도 있다.
스킬 메타데이터가 시작 시 항상 적재되어 스킬당 약 100 토큰이므로,
붙여 둔 스킬의 수가 곧 고정비다.
브라우저 도구 모음의 6,600과 스킬 50개의 5,000을 더하면
아무 일도 하지 않은 요청이 1만 토큰을 넘는다.
두 값의 성격이 같다 —
할 수 있는 일의 목록을 모델에게 알리는 비용이며,
목록이 길어질수록 매 턴 반복된다.

`configs`로 멤버를 끄면 줄어든다는 안내가
이 비용을 다루는 실무 방법이다.
27개 중 자기 작업에 필요한 것만 남기면
정의 토큰이 줄고 모델이 고를 후보도 줄어드므로,
비용과 정확도가 같은 방향으로 개선된다.
그런데 어느 멤버를 끄면 얼마가 줄어드는지는
개별 수치로 제시되지 않고
토큰 계산 엔드포인트로 직접 재라고 안내한다.

### 고객 인용의 수치가 이 발표에서 가장 강한 근거다

발표문에서 검증 가능한 형태의 주장이 하나 있다.
Asteroid의 인용이며 세 수치를 담는다.

가장 긴 청구 워크플로가 32분에서 13분으로 줄고,
시험한 모든 워크플로에서 작업당 비용이 약 30% 떨어지고,
완료율이 100%에 도달했으며
프롬프트는 하나도 바꾸지 않았다는 것이다.
마지막 조건이 이 인용을 강하게 만든다 —
프롬프트를 바꾸지 않았다면
개선의 원인이 도구 쪽 변경으로 좁혀지기 때문이다.

그리고 그 원인이 발표문의 다른 항목과 맞물린다.
컴퓨터 사용이 모델 호출마다 한 동작이 아니라
한 턴에 여러 동작을 하게 됐다는 것이며,
왕복 횟수가 줄면 시간과 비용이 함께 준다.
32분에서 13분은 2.5배이고
비용은 30% 감소이므로 두 수치의 비율이 다른데,
그 차이도 설명된다 —
왕복이 줄어도 이미지와 텍스트 결과의 총량은 크게 줄지 않으므로
지연이 비용보다 더 개선된다.

동시에 이 인용의 한계도 분명하다.
Asteroid는 이 기능을 쓰는 회사이므로 이해가 걸려 있고,
“시험한 모든 워크플로”의 개수와 종류가 밝혀지지 않았고,
완료율 100%의 표본 크기도 없다.
그렇다고 값이 없는 것은 아니다 —
API가 없는 의료·보험 시스템이라는 조건이 구체적이므로
같은 조건의 독자가 자기 경우에 대입할 수 있다.

## 비평

### 5분짜리 발표문과 실제 계약의 복잡도 차이가 너무 크다

이 발표문의 서술이 세 문장으로 요약된다.
컴퓨터 사용은 보이는 소프트웨어를 조작하고,
Skills API는 전문성을 주고,
Files API는 문서를 준다는 것이다.
그리고 셋을 합치면 프로덕션 에이전트를 만들 수 있다고 맺는다.

문서를 열면 다른 문서가 나온다.
멤버 도구 27개와 선택적 멤버 4개,
`CoordinateTarget`과 `RefTarget` 두 형태,
일괄 동작의 순차 실행과 정확한 중단 문구,
`browser_state` 블록의 형식 규칙,
스크린숏 크기 한도와 좌표 역산,
그리고 열 줄이 넘는 요청 오류 표다.
발표문이 이 규격을 요약하려 하지 않고
문서 링크로 넘긴다.

이 간격이 문제인 이유는 판단의 시점 때문이다.
발표문을 읽고 도입을 결정하는 쪽은
구현 부담을 모른 채 결정하며,
그 부담이 실제로는 브라우저 자동화 실행기 하나를 만드는 일이다.
발표문에 “이 도구는 브라우저 자동화를 직접 운영해야 한다”는
한 문장이 있으면 그 오해가 없어지는데,
지금은 “Anthropic 쪽에서 아무것도 돌지 않는다”는 문장이
플랫폼 문서에만 있다.

그리고 이 간격이 같은 발표문 안에서 불균형을 만든다.
Skills API에 대해서는 코드 실행 샌드박스에서 돌므로
호스팅할 것이 없다고 명시했는데,
브라우저 사용에 대해서는 같은 층위의 정보를 주지 않는다.
두 기능이 이 점에서 정반대이므로
그 대비가 발표문에서 가장 필요한 정보였다.

### 프롬프트 인젝션 위험을 문서 링크 하나로 넘긴다

브라우저 사용 도구는 신뢰할 수 없는 입력을 다루는 도구다.
문서가 그것을 명확히 적는다 —
Claude가 살아 있는 웹페이지를 읽고 행동하므로
페이지가 제공하는 모든 것이 신뢰할 수 없는 입력이고
Claude가 취하는 행동은 실제 효과를 낼 수 있다는 것이다.

그런데 그 위험의 처리가 얇다.
한계 목록의 마지막 항목에서
프롬프트 인젝션 위험이 컴퓨터 사용에서 그대로 이어진다고 적고
그쪽 문서를 링크한다.
브라우저 사용에 고유한 위험 —
페이지 내용이 접근성 트리를 통해 텍스트로 들어오고,
그 텍스트가 요소 이름을 담고 있으며,
그 이름을 모델이 행동의 근거로 쓴다는 것 — 은 별도로 다뤄지지 않는다.

이 고유성이 중요한 이유가 있다.
좌표 클릭에서는 모델이 픽셀을 보고 판단하므로
페이지가 모델에게 문장을 건네기 어려운데,
요소 참조에서는 요소의 접근성 이름이 그대로 모델의 컨텍스트에 들어간다.
그러면 버튼 이름에 지시문을 넣는 공격이 성립하며,
이 릴리스의 핵심 개선이 동시에 새 표면이다.
문서가 그 교환을 언급하지 않는다.

발표문에는 이 주제가 아예 없다.
대신 HIPAA 규제 워크로드에 쓸 수 있게 됐다는 항목이 있으며,
그것은 규제 준수의 이야기이고 인젝션 방어의 이야기가 아니다.
의료·보험 포털에서 에이전트가 제출을 완료한다는 예시를 든 발표문이라면,
그 포털이 악의적일 필요도 없이 —
광고나 서드파티 위젯 하나로 — 텍스트가 주입될 수 있다는 점이
같은 지면에 있어야 했다.

### 다운로드 URL 처리 지침이 문서 깊숙한 곳에 있다

문서에서 가장 구체적인 보안 지침 하나가
다운로드 보고 절의 마지막 항목에 있다.

내용이 이렇다.
`url`은 원격 서버에서 오며
리다이렉트를 거친 뒤 서명된 질의 문자열 자격 증명을 자주 담으므로,
Claude의 컨텍스트에 넣고 싶지 않은 질의 매개변수를 제거하고
보고하거나 파일 시스템 경로에 쓰기 전에 정제하라는 것이다.

이 지침이 두 가지를 동시에 말한다.
하나는 자격 증명 유출이다 —
서명된 URL을 그대로 보고하면
그 토큰이 API 요청 내용에 들어가고 보존 정책의 대상이 된다.
다른 하나는 경로 주입이다 —
원격 서버가 준 문자열을 파일 시스템 경로로 쓰면
디렉터리 탈출이 가능해진다.
둘 다 실제로 일어나는 종류이고,
둘 다 구현자가 놓치기 쉽다.

문제는 위치다.
이 지침이 `state_changes` 필드의 형식 규칙들 사이에 있으며,
`size_bytes`가 음이 아닌 정수라는 서술과 같은 목록에 있다.
형식 규칙과 보안 요구가 같은 층위로 나열되면
구현자가 전자를 만족시키고 후자를 지나칠 수 있다.
보안 고려 절이 따로 있는 문서이므로
이 항목이 그쪽에도 있어야 한다.

같은 문제가 스크린숏 처리에도 있다.
API가 도구 모음 이미지를 축소해 주지 않으므로
한도를 넘으면 요청이 거부되고,
좌표를 배율의 역수로 되돌려야 한다는 것이다.
이것은 보안이 아니라 정확성 문제인데
놓치면 클릭이 조용히 엉뚱한 곳으로 간다.
치명적 결과를 내는 항목들이
형식 규칙 목록에 섞여 있는 것이 이 문서의 구조적 약점이다.

### Files API의 격리 책임이 전부 개발자에게 있는데 발표문은 편의만 말한다

발표문의 Files API 설명이 세 동작이다.
PDF나 스프레드시트를 한 번 올려 두고,
이후 요청에서 다시 보내는 대신 ID로 참조하고,
에이전트가 만든 파일을 내려받는다는 것이다.
전부 편의에 관한 서술이다.

문서가 굵은 글씨로 적은 사실이 그 편의의 조건을 바꾼다.
업로드된 파일이 워크스페이스 전체에서 접근 가능하고
최종 사용자나 대화나 세션 단위로 제한되지 않으며,
별도 워크스페이스를 배정하지 않으면
모든 API 키가 조직의 기본 워크스페이스를 공유한다.
그래서 사용자에게서 `file_id`를 받지 말라는 경고가 따라붙는다 —
사용자가 준 파일 ID가
다른 사용자의 파일을 읽게 만들기 때문이다.

이것이 다중 사용자 제품을 만드는 쪽에게 결정적이다.
파일 저장소가 사용자별 격리를 제공하지 않으므로,
그 격리를 애플리케이션이 직접 구현해야 한다 —
사용자와 파일 ID의 대응 표를 자기 데이터베이스에 두고
요청마다 소유권을 검사해야 한다.
그것을 하지 않으면
파일 ID를 추측하거나 전달받은 쪽이 남의 문서를 읽는다.

그러면 “한 번 올리고 ID로 참조한다”는 편의의 성격이 달라진다.
같은 ID가 워크스페이스 전체의 공용 핸들이므로
편의와 위험이 같은 성질에서 나온다.
발표문이 든 예시가 보험금 청구 에이전트이고
접수 문서를 Files API에서 읽는 흐름인데,
그 문서가 개인의 의료 정보라면
격리 실패의 결과가 가장 무거운 경우다.
HIPAA 적격이 같은 발표문에 있으므로 더욱 그렇다.

### 스킬이 표면마다 따로 관리되고 claude.ai는 중앙 관리가 안 된다

발표문은 Skills API를 “자기 스킬을 올리고 버전을 관리하는 더 단순한 API”로 소개한다.
문서를 열면 관리 단위가 표면마다 다르다.

세 표면의 공유 모델이 서로 다르다.
claude.ai는 사용자 개인 단위이고 각자 올려야 하며,
문서가 명시적으로 중앙 관리자 관리와
조직 단위 배포를 지원하지 않는다고 적는다.
Claude API는 워크스페이스 전체이므로
구성원 전원이 접근한다.
Claude Code는 파일 시스템 기반의 개인 또는 프로젝트다.
그리고 셋 사이에 동기화가 없다.

이 구성이 조직에 두 문제를 동시에 만든다.
하나는 배포다 —
같은 스킬을 쓰게 하려면 세 곳에 각각 올려야 하고,
claude.ai에서는 구성원마다 올려야 한다.
스킬이 절차 지식이라면 그 절차가 바뀔 때마다
같은 수의 갱신이 필요하다.
다른 하나는 통제다.
claude.ai에서 관리자가 스킬을 중앙에서 관리할 수 없으므로,
개인이 올린 스킬의 내용을 조직이 확인할 방법이 없다.

같은 문서가 스킬의 위험을 분명히 적기 때문에 이 공백이 커진다.
번들된 모든 파일 —
`SKILL.md`와 스크립트와 이미지와 자원 — 을 검토하고
예상치 못한 네트워크 호출이나 파일 접근 패턴,
스킬의 명시된 목적과 맞지 않는 동작 같은
비정상 패턴을 찾으라고 안내하며,
악의적 스킬이 파일 조작과 bash와 코드 실행을
해로운 방식으로 부를 수 있다고 적는다.
검토가 필요하다고 말하면서
검토를 강제할 지점을 claude.ai에는 두지 않은 것이다.

그리고 API 쪽의 워크스페이스 전체 공유도 같은 축의 문제다.
한 사람이 올린 스킬이 워크스페이스 구성원 전원에게 보이므로
배포는 쉬운데 검토 절차가 문서에 없다.
[스킬을 홈 디렉터리에 복사하라는 설치 안내가
신뢰 검토를 건너뛴다는 문제](../agentic-coding/solo-skills.md)와 같은 층이며,
여기서는 그 복사가 조직 단위로 일어난다.

### 세 기능을 함께 발표한 구성이 각각의 성숙도를 가린다

이 발표문이 세 기능의 정식 출시를 하나로 묶는다.
그런데 셋의 상태가 같지 않다.

Files API의 변경이 운영 지표다 —
자동 파일 만료, 5배 높은 요청 한도, 조직당 1 TB다.
Skills API의 변경은 “더 단순한 API”라는 서술 하나이며,
무엇이 어떻게 단순해졌는지가 없다.
컴퓨터 사용의 변경은 실질적이다 —
턴당 다중 동작과 HIPAA 적격이다.
브라우저 사용은 변경이 아니라 신규이며,
문서에 따르면 Claude API에서만 쓸 수 있고
Claude Managed Agents에서는 아직 쓸 수 없다.

이 차이가 하나로 묶이면서 지워진다.
“정식 출시”라는 한 단어가 넷에 다 붙으므로
브라우저 사용이 다른 셋과 같은 성숙도로 읽히는데,
실제로는 오늘 새로 나온 것이고
플랫폼 가용성이 가장 좁다.
발표문이 “브라우저 사용 도구: 오늘 컴퓨터 사용에 신규”라고 적어
그 사실을 밝히기는 하지만,
같은 목록의 다른 항목들과 같은 무게로 놓인다.

그리고 이 구성이 이행 안내도 흐린다.
기존 베타 연동이 이행 기간 동안 계속 작동한다고만 적고,
그 기간이 얼마인지,
베타에서 정식으로 옮길 때 무엇이 바뀌는지가 없다.
`browser_toolset_20260801`이라는 날짜 붙은 식별자가 있으므로
버전 관리 체계는 있는데,
이전 베타 식별자와의 대응이 발표문에 제시되지 않는다.

## 인사이트

### 접근성 트리가 자동화 인터페이스로 재발견되고 있다

이 릴리스의 핵심 장치가 접근성 트리이고,
그 사실이 이 기술의 궤적에서 흥미로운 지점이다.

접근성 트리는 화면 낭독기를 위해 만들어졌다.
시각에 의존하지 않고 페이지를 조작할 수 있도록
요소의 역할과 이름과 상태를 구조로 노출하는 것이며,
그 목적이 지금 에이전트의 요구와 정확히 겹친다 —
에이전트도 픽셀 대신 구조로 페이지를 다루려 한다.
`read_page`가 돌려주는 `link "Documentation" [ref_1]` 형태가
낭독기가 읽어 주는 내용과 같은 정보다.

이 겹침이 실용적 결론을 만든다.
접근성을 잘 구현한 페이지가 에이전트에게도 잘 동작하며,
`aria` 속성이 없고 `div`로 만든 버튼만 있는 페이지는
참조가 나오지 않아 좌표 클릭으로 떨어진다.
문서가 든 실패 조건 — 가상화된 목록,
캔버스 렌더링, 스크롤 시 재렌더링 — 이
전부 접근성이 약한 패턴이라는 점이 그것을 확인한다.

그러면 접근성 작업의 유인이 바뀐다.
지금까지 그 작업의 근거는 규제와 윤리였고
효과를 측정하기 어려웠는데,
에이전트가 페이지를 조작하는 비중이 늘면
같은 작업이 자동화 성공률로 측정된다.
접근성이 나쁜 페이지에서 에이전트 작업이 실패하면
그것이 사업 지표에 나타나며,
그 경로가 규제보다 강한 유인일 수 있다.

동시에 반대 방향의 위험도 생긴다.
접근성 트리가 자동화의 입구가 되면
그것을 막으려는 사이트가 나올 수 있고,
그 결과는 낭독기 사용자에게 그대로 돌아간다.
봇 차단이 접근성 저하로 이어지는 이 구조가
이미 CAPTCHA에서 일어난 일이며,
같은 일이 페이지 구조 층에서 반복될 수 있다.

### 도구 정의의 고정비가 에이전트 설계의 새 제약이 된다

약 6,600 토큰이라는 수치가
개별 제품의 가격 정보를 넘어서는 함의를 갖는다.

도구를 늘리면 모델이 할 수 있는 일이 늘어나는데
그 대가가 매 요청의 고정비다.
27개 멤버가 6,600 토큰이면 멤버당 약 245 토큰이고,
여기에 도구 모음을 여럿 붙이면 —
컴퓨터 사용과 배시와 텍스트 편집기와 자기 도구들 —
정의만으로 컨텍스트의 상당 부분이 찬다.
문서가 그것들 각각 자기 토큰 비용이 있다고 명시한다.

이 제약이 에이전트 설계를 두 방향으로 밀어낸다.
하나는 선별이다 —
`configs`로 필요한 멤버만 켜고
작업 종류마다 다른 도구 집합을 쓰는 것이다.
다른 하나는 지연 로딩이며,
문서에 `defer_loading` 옵션이 나오는 것이 그 장치다.
둘 다 “가능한 도구를 다 붙인다”는 초기 관행의 반대 방향이다.

그리고 이 제약이 하위 에이전트 구조의 근거가 된다.
도구가 많으면 하나의 에이전트에 다 붙이는 대신
작업별 하위 에이전트에 나누는 것이 싸지며,
그 분할의 기준이 능력이 아니라 토큰 예산이다.
[에이전트 하네스에서 컨텍스트 구성과 도구 정의가
성능 차이를 만든다는 관찰](../ai-tool/vomit.md)이
이 층에서 비용으로도 나타난다.

여기서 도구 제공자 쪽의 유인도 정해진다.
정의 토큰을 줄이는 것이 곧 채택 유인이므로,
멤버를 27개로 펼치는 대신
하나의 도구에 `action` 매개변수를 두는 설계가 다시 유리해진다.
브라우저 사용이 전자를 골랐고
그 이유가 정확도 — 모델이 이름으로 도구를 고르는 것이
매개변수 값으로 고르는 것보다 안정적이다 — 이므로,
정확도와 토큰 비용의 교환이 이 층의 설계 문제로 남는다.

### 네트워크가 없는 샌드박스가 스킬의 실제 용도를 좁힌다

API에서 스킬이 도는 환경의 제약이
이 기능의 적용 범위를 발표문보다 훨씬 좁게 만든다.

세 제약이 함께 걸린다.
네트워크 접근이 없어 외부 API를 부를 수 없고,
실행 중 패키지 설치가 불가능하며,
미리 설치된 패키지만 쓸 수 있다.
그러면 스킬이 할 수 있는 일이
주어진 파일을 변환하고 계산하고 문서를 만드는 쪽으로 제한된다.
미리 만들어진 스킬 넷이 `pptx`와 `xlsx`와 `docx`와 `pdf`인 것이
그 범위를 정확히 보여 준다.

이 제약이 안전 장치이기도 하다.
스킬은 남이 만든 코드를 실행하는 기능이므로
네트워크가 없으면 데이터 유출 경로가 크게 줄고,
패키지 설치가 없으면 공급망 공격 표면이 사라진다.
문서의 보안 절이 악의적 스킬의 위험을 경고하는데,
그 위험의 상당 부분을 런타임 제약이 이미 막는다.

그런데 발표문의 예시가 이 제약을 넘어선다.
보험금 청구 에이전트가 팀의 접수 절차 스킬을 따라
보험사 웹 포털에서 제출을 완료한다는 흐름인데,
포털 조작은 브라우저 사용 도구가 하고
스킬은 절차를 지시하는 역할이다.
즉 스킬이 직접 외부와 통신하지 않고
지시만 하고 실행은 다른 도구가 하는 구조이며,
그 분업이 문서의 제약과 정합한다.
발표문이 그 분업을 설명하지 않아
스킬이 무엇을 할 수 있는지 오해하기 쉽다.

그러면 스킬을 설계할 때의 원칙도 정해진다.
외부 호출이 필요한 부분은 스킬 밖의 도구로 빼고
스킬에는 판단과 형식만 남기는 것이며,
문서가 “이 제약 안에서 동작하도록 스킬을 계획하라”고 맺는 것이 그 뜻이다.
Claude Code에서는 전체 네트워크 접근이 있으므로
같은 스킬이 표면마다 다르게 동작할 수 있고,
그 차이가 스킬을 옮길 때 조용한 실패를 만든다.

### 클라이언트에서 실행되는 도구는 규제 준수의 경계를 바꾼다

컴퓨터 사용이 BAA 아래 HIPAA 워크로드에 적격이 됐다는 항목이
발표문에서 가장 조용하게 중요한 부분이다.

이 적격성이 성립하는 조건이 실행 위치와 맞물린다.
브라우저 세션과 파일이 사용자 환경에 남고
API로 가는 것은 사용자가 돌려주는 스크린숏과 페이지 텍스트와 탭 상태다.
그러면 보호 대상 정보가 어디로 가는지가
사용자의 코드에 달려 있으며,
스크린숏에 환자 정보가 찍히면 그것이 요청 내용이 된다.

이 구조가 책임의 위치를 옮긴다.
서버 도구라면 제공자가 데이터 처리 경로를 통제하는데,
클라이언트 도구는 무엇을 보낼지 사용자가 정한다.
그래서 규제 적격이 “이 도구를 쓰면 준수된다”가 아니라
“이 도구로 준수하게 만들 수 있다”는 뜻이며,
그 차이가 감사에서 드러난다.
문서가 ZDR 대상이라고 밝힌 것도 같은 층위다 —
선택할 수 있는 옵션이고 기본 상태가 아니다.

그러면 규제 산업에서 이 도구를 쓸 때의 실제 작업이 정해진다.
스크린숏에서 불필요한 영역을 가리고,
접근성 트리에서 식별 정보를 걸러 내고,
다운로드 URL의 서명 매개변수를 제거하는 것이며,
셋 다 사용자 코드에서 해야 한다.
문서가 마지막 항목만 명시적으로 안내하고
앞의 둘은 언급하지 않는다.

이 상황이 이 시기 도구 도입의 일반적 형태로 보인다.
[규제가 엄격한 핀테크에서 에이전트를 쓰는 방법이
도구를 신뢰하는 것이 아니라
도구의 네트워크 트래픽을 감시하는 층을 따로 만드는 것](../startup/garry-tan-founder-rules.md)이었던
사례와 같은 방향이며,
공통 처방은 무엇이 밖으로 나가는지를
자기 코드에서 결정하고 기록하는 것이다.
