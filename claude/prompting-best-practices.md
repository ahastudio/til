# Claude 프롬프트 모범 사례: 명확하게, 이유와 함께, 모델별로 다시 시험하며

원문: [Prompting best practices - Claude Platform Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

## 소개

Anthropic이 현재 Claude 모델용 프롬프트 엔지니어링을 모아 둔 참조 문서다.
Claude Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5.5, Opus 5, Opus 4.8,
4.7, 4.6, Sonnet 5.5, 5, 4.6, Haiku 5.5, 4.5를 대상으로 한다.
세 부분으로 나뉜다.
앞에 모델별 안내가 있어 한 모델이 다르게 행동하는 지점과 프롬프트에서 무엇을
바꿔야 하는지를 모델별 페이지로 안내한다.
이어 모든 현재 모델에 쓰는 기법(일반 원칙, 출력과 형식, 도구 사용, 사고,
에이전트 시스템)이 나오고, 마지막에 이전 세대 프롬프트의 이전 고려 사항이 있다.
문서는 기법이 특정 모델을 거명하면 그 모델에서 측정한 것으로 보고 다른 모델에
쓰기 전에 자신의 eval로 다시 확인하라고 강조한다.
모델별 페이지는 이 저장소의 [Fable 5.1 프롬프팅](prompting-fable-5-1.md) 문서와
[Opus 5.5 프롬프팅](prompting-opus-5-5.md) 문서가 다룬다.

이 문서는 실제로 쓰는 순서대로 정리한다.
먼저 모든 모델에 통하는 원칙을, 이어 출력과 도구와 사고와 에이전트 장기 작업을,
마지막으로 이전 시 주의할 변경을 다룬다.

## 일반 원칙

### 명확하고 직접적으로 쓴다

Claude는 명확하고 명시적인 지시에 잘 반응한다.
작업이 엄밀히 요구하는 것보다 더 해 주기를 바란다면 모델이 모호한 프롬프트에서
짐작하기를 기대하지 말고 명시적으로 요청해야 한다.
문서는 Claude를 뛰어나지만 규범과 업무 방식에 맥락이 없는 새 직원처럼 생각하라고
하고, 핵심 시험을 제시한다.
작업 맥락이 거의 없는 동료에게 프롬프트를 보여 주고 따라 해 보라고 했을 때
동료가 혼란스러워한다면 Claude도 그렇다는 것이다.
출력 형식과 제약을 구체적으로 쓰고, 순서나 완결성이 중요하면 번호 목록이나
글머리표로 순차 단계를 준다.
예컨대 분석 대시보드를 만들어 달라는 요청은 가능한 한 많은 관련 기능과
상호작용을 넣고 기본을 넘어 완전한 구현을 만들라는 문장을 덧붙일 때 더
효과적이다.

### 지시의 이유를 붙인다

지시 뒤의 맥락이나 동기를 설명하면 Claude가 목표를 더 잘 알고 더 목표에 맞는
답을 낸다.
말줄임표를 쓰지 말라고만 하는 것보다 응답을 텍스트 음성 변환 엔진이 읽으므로
엔진이 발음하지 못하는 말줄임표를 쓰지 말라고 쓰는 편이 낫다.
Claude가 설명에서 일반화하기 때문이다.

### 예시를 쓴다

예시는 출력의 형식, 어조, 구조를 이끄는 가장 믿을 만한 수단 가운데 하나다.
예시는 실제 사용을 닮은 관련성, 의도하지 않은 패턴을 배우지 않도록 엣지
케이스까지 다룬 다양성, 지시와 구분되도록 `<example>` 태그로 감싼 구조를 갖춰야
한다.
3~5개가 가장 좋고, Claude에게 예시의 관련성과 다양성을 평가하거나 추가 예시를
만들게 할 수도 있다.

### XML 태그로 구조를 세우고 역할을 준다

지시, 맥락, 예시, 변수 입력이 섞인 복잡한 프롬프트는 각 내용을 자기
태그(`<instructions>`, `<context>`, `<input>`)로 감싸면 오해가 준다.
태그 이름은 일관되고 서술적으로 쓰고, 계층이 있으면 중첩한다(`<documents>` 안에
`<document index="n">`).
시스템 프롬프트에 역할을 한 문장만 줘도 행동과 어조가 초점을 얻는다.

### 긴 문서는 위에, 질문은 끝에 둔다

2만 토큰 이상의 큰 문서나 데이터가 많은 입력은 긴 데이터를 프롬프트 위쪽에,
질의와 지시와 예시는 그 아래에 둔다.
질의를 끝에 두면 복잡한 다문서 입력에서 응답 품질이 최대 30% 좋아졌다고 문서는
쓴다.
각 문서를 `<document>`로 감싸고 `<source>`와 `<document_content>` 하위 태그를
쓰고, 긴 문서 작업에서는 작업 전에 관련 부분을 먼저 인용하게 하면 관련 내용에
집중하고 나머지를 무시한다.

## 출력과 형식

최신 모델은 이전 모델보다 간결하고 자연스럽게 말하고, 자축하는 갱신 대신 사실에
기반한 진행 보고를 한다.
도구 호출 뒤에 요약을 건너뛰고 곧바로 다음 행동으로 갈 수 있으므로, 작업이 끝난
뒤 한 일을 짧게 요약해 달라고 요청하면 가시성이 늘어난다.
Opus 5는 기본 응답이 더 길고 노력 수준을 바꿔도 길이가 안정적으로 바뀌지
않으므로 간결함을 명시적으로 요구해야 하고, Fable 5.1은 에이전트 작업 중 도구
호출 사이의 갱신이 적으므로 진행 텍스트를 명시적으로 청해야 한다.

형식은 네 가지로 조종한다.
하지 말라는 것보다 하라는 것을 말한다(마크다운을 쓰지 말라는 대신 매끄럽게
이어지는 산문 단락으로 구성하라).
XML 형식 지시자를 쓴다.
프롬프트의 스타일을 원하는 출력 스타일에 맞춘다(프롬프트에서 마크다운을 빼면
출력의 마크다운이 준다).
특정 형식 선호에는 상세한 프롬프트를 쓴다.
Fable 5.1은 이미 이전 모델보다 형식을 덜 쓰므로 마크다운 억제 블록이 필요한
구조까지 억누를 수 있어 그 블록을 빼거나 더 짧은 규칙으로 바꾸라고 한다.
수식은 최신 모델이 LaTeX를 기본으로 쓰므로 일반 텍스트를 원하면 LaTeX와 MathJax
표기를 쓰지 말라고 지시한다.

### 프리필(prefill) 이전

Claude 4.6 모델과 Mythos Preview부터 마지막 assistant 턴의 프리필(Claude가 이어
쓸 부분 응답)은 지원되지 않고 프리필이 든 요청은 400 오류를 낸다.
형식 강제는 구조화된 출력이나 enum 필드가 있는 도구로, 서두 제거는 시스템
프롬프트의 직접 지시(여기 있습니다, 같은 말로 시작하지 말 것)나 XML 태그
출력으로 바꾼다.
불필요한 거절 회피에는 프리필 없이 사용자 메시지 안의 명확한 프롬프트로
충분하고, 이어 쓰기는 중단된 응답의 끝 문장을 사용자 메시지에 넣어 이어서 쓰라고
한다.
오래된 대화의 맥락 주입은 이전에 프리필한 assistant 알림을 사용자 턴에 넣거나
도구와 컨텍스트 압축 시점으로 옮긴다.

## 도구 사용

최신 모델은 정밀한 지시 이행으로 훈련되어 특정 도구를 쓰라는 명시적 방향에서
이득을 본다.
이 함수를 개선할 수 있는 변경을 제안해 줄 수 있어요라고 하면 Claude가 구현 대신
제안만 할 수 있으므로, 이 함수를 성능이 좋아지게 바꿔라처럼 행동을 요구해야
한다.
기본적으로 더 적극적으로 행동하게 하려면 시스템 프롬프트에 `<default_to_action>`
블록(변경을 제안만 하지 말고 구현하고, 의도가 불분명하면 가장 유용한 행동을
추론해 도구로 빠진 정보를 찾는다)을 넣고, 반대로 더 주저하게 하려면
`<do_not_act_before_instructions>` 블록을 넣는다.
Opus 4.5와 4.6은 시스템 프롬프트에 더 민감해서 도구가 덜 호출되는 것을 막으려고
쓴 강한 언어가 이제 과호출을 부를 수 있고, 반드시 쓰라는 대문자 지시는 이 도구를
쓸 때처럼 보통의 문장으로 낮추라고 한다.

독립적인 도구 호출은 병렬로 실행된다.
프롬프트 없이도 성공률이 높지만 `<use_parallel_tool_calls>` 블록으로 거의
100%까지 높일 수 있고, 반대로 단계 사이에 잠깐 쉬며 순차로 실행하라고 해서 낮출
수 있다.
Fable 5.1의 긴 에이전트 루프에서는 병렬 호출 지시를 도구 결과 한 라운드가 끝날
때마다 턴 범위 시스템 메시지로 보낸다.

## 사고와 추론

Opus 4.6은 이전 모델보다 사전 탐색을 더 많이 하고 특히 높은 노력 수준에서
그렇다.
이전에 더 철저히 하라고 권하던 프롬프트는 조정해야 한다.
일괄 기본값(도구를 기본으로 쓰라) 대신 표적 지시(문제 이해에 도움이 될 때
쓰라)를 쓰고, 과한 프롬프트(확신이 없으면 도구를 써라)를 빼며, 그래도 과하면
노력 수준(effort)을 낮추는 것을 대비책으로 쓴다.
사고가 너무 많으면 접근 하나를 골라 끝까지 가고 새 정보가 직접 모순될 때만
결정을 재검토하라는 지시를 줄 수 있다.
`budget_tokens`로 사고 비용을 제한하는 방식은 Opus 4.6과 Sonnet 4.6에서 아직
동작하지만 폐기 예정이고, Claude 4.7 이후 모델에서는 `budget_tokens`를 설정하면
400 오류가 난다.

Claude 4.6 이후 모델은 적응형 사고(`thinking: {type: "adaptive"}`)를 쓴다.
Claude가 언제 얼마나 생각할지 스스로 정하고, 노력 수준과 질의 복잡도 두 요인으로
보정한다.
Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5.5에서는 사고가 항상 켜져 있고
적응형이 유일한 모드다.
내부 평가에서 적응형 사고가 확장 사고보다 안정적으로 성능이 좋았다고 문서는
말한다.

```python
# 이전: 수동 예산의 확장 사고(구형 모델)
client.messages.create(
    model="claude-sonnet-4-5-20250929",
    max_tokens=16000,
    thinking={"type": "enabled", "budget_tokens": 10000},
    messages=[{"role": "user", "content": "..."}],
)

# 이후: 적응형 사고와 노력 수준
client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    messages=[{"role": "user", "content": "..."}],
)
```

`thinking`을 생략했을 때의 기본 동작은 모델마다 다르다.
Opus 4.6에서 4.8과 Sonnet 4.6은 사고가 꺼지고, Opus 5, Sonnet 5.5, Sonnet 5,
Haiku 5.5는 사고가 켜져 응답이 사고 블록으로 시작할 수 있다.
그래서 위치가 아니라 종류로 콘텐츠 블록을 고르고, `max_tokens`에 사고 몫을
남겨야 한다.
문서는 몇 가지 지침을 덧붙인다.
처방적 단계보다 일반적 지시(철저히 생각하라)가 더 나은 추론을 낳는 경우가 많다.
사고와 함께 쓰는 다중 예시도 효과가 있어 문제, 적용할 방법, 기대 답으로
제시한다.
사고가 꺼졌을 때의 수동 연쇄 사고(CoT)는 대비책이고, Fable 5.1, Fable 5, Opus
5.5, Opus 5, Sonnet 5.5에서는 추론을 글로 쓰라는 프롬프트가 거부될 수 있으므로
사고에 맡긴다.
끝내기 전에 검증 기준으로 자기 답을 확인하라고 덧붙이면 코딩과 수학의 오류를
안정적으로 잡지만, Opus 5는 지시 없이도 스스로 잘 검증하므로 이전 모델용 검증
지시가 과검증으로 토큰과 지연을 늘린다.

## 에이전트 시스템

최신 모델은 장기 추론과 상태 추적이 강하고, 한 번에 모든 것을 시도하지 않고 몇
가지를 꾸준히 진행하며, 여러 컨텍스트 윈도우를 넘나드는 작업에서 상태를 저장하고
새 윈도우에서 이어 간다.
Sonnet 5, 4.6, Haiku 4.5는 남은 컨텍스트 윈도우를 추적하는 컨텍스트 인식을
가졌고, 컨텍스트를 압축하거나 외부 파일에 저장하는 하네스(예를 들어 Claude
Code)를 쓴다면 이를 프롬프트에 알려야 한다.
알리지 않으면 컨텍스트 한도에 다가갈 때 작업을 일찍 마무리하려 할 수 있다.
문서의 견본은 컨텍스트가 자동 압축되므로 토큰 예산 걱정으로 일찍 멈추지 말고,
한도에 가까워지면 진행과 상태를 메모리에 저장하라고 지시한다.

여러 컨텍스트 윈도우에 걸치는 작업을 위한 지침은 다음과 같다.
첫 윈도우에는 틀(테스트 작성, 설정 스크립트)을 세우는 다른 프롬프트를 쓰고 이후
윈도우에서 할 일 목록을 반복한다.
작업 전에 테스트를 구조화된 형식(`tests.json`)으로 만들게 하고, 테스트를
지우거나 고치는 것은 용납할 수 없다고 상기시킨다.
서버와 테스트와 린터를 시작하는 `init.sh` 같은 편의 도구를 만들게 한다.
컨텍스트를 비울 때는 압축보다 새 윈도우를 고려한다. 최신 모델은 로컬 파일
시스템에서 상태를 찾는 데 뛰어나므로 `pwd`를 부르고, `progress.txt`와
`tests.json`과 git 로그를 보고, 새 기능 전에 기본 통합 테스트를 직접 돌리라고
구체적으로 시작을 지시한다.
자율 작업이 길수록 사람의 피드백 없이 정확성을 검증할 도구(컴퓨터 사용 도구,
브라우저 자동화 MCP)가 필요하다.

상태 관리는 구조화된 상태(테스트 결과, 작업 상태)는 JSON으로, 진행 메모는 자유
텍스트로, 변경 기록과 복원 지점은 git으로 하며, 점진적 진행을 명시적으로
요구한다.
자율과 안전의 균형을 위해 Opus 4.6은 파일 삭제, 강제 푸시, 외부 서비스 게시처럼
되돌리기 어려운 행동을 할 수 있으므로, 로컬에서 되돌릴 수 있는 행동은 하되
되돌리기 어렵거나 공유 시스템에 영향을 주거나 파괴적인 행동은 먼저 물으라는
프롬프트를 쓴다.
장애물을 만났을 때 `--no-verify`로 안전 검사를 우회하거나 낯선 파일을 버리는
식의 파괴적 지름길을 쓰지 말라는 문장도 있다.

하위 에이전트는 최신 모델이 스스로 위임하지만, Opus 4.6은 간단한 grep으로 충분한
곳에도 하위 에이전트를 띄우는 과사용 경향이 있고 Opus 5도 이전 모델보다 쉽게
위임한다.
하위 에이전트가 병렬로 돌 수 있거나 격리된 컨텍스트가 필요하거나 상태를 공유하지
않는 독립 작업일 때만 쓰고, 단순 작업과 단일 파일 수정에는 직접 하라는 지침을
준다.
복잡한 프롬프트의 명시적 연쇄(초안, 기준에 따른 검토, 개선)는 중간 산출물을
검사하거나 파이프라인 구조를 강제할 때 여전히 유용하다.

코딩 에이전트에는 네 가지 지침이 있다.
테스트와 반복을 위해 만든 임시 파일은 끝에 지우라고 한다.
Opus 4.5와 4.6의 과잉 엔지니어링(불필요한 파일, 추상화, 요청하지 않은
유연성)에는 범위, 문서화, 방어적 코딩, 추상화를 최소로 하라는 지침을 준다.
테스트 통과에만 집중해 하드코딩하는 경향에는 모든 유효한 입력에 맞는 일반 해법을
쓰고, 과제가 비현실적이거나 테스트가 틀렸다면 우회하지 말고 알리라고 한다.
환각을 줄이려면 `<investigate_before_answering>` 블록으로 열어 보지 않은 코드에
대해 추측하지 말고 먼저 파일을 읽으라고 한다.

## 기능별 팁

비전은 Opus 4.5와 4.6에서 좋아졌고, 이미지의 관련 영역을 확대하게 하는 자르기
도구나 스킬을 주면 이미지 평가에서 일관된 향상이 있었다고 한다.
프런트엔드 디자인은 지침이 없으면 모델이 일반적인 패턴으로 수렴해 AI 슬롭 미학이
되므로, 글꼴, 색과 테마, 모션, 배경에 대한 `<frontend_aesthetics>` 시스템
프롬프트 조각을 제공한다.
이 조각은 Inter, Roboto, Arial 같은 흔한 글꼴과 흰 바탕의 보라색 그라데이션을
피하라고 하고, 그래도 Space Grotesk 같은 선택으로 수렴하니 틀 밖에서 생각하라고
덧붙인다.
약 복용량 질문이 올 수 있는 앱에는 모델마다 문서가 준 `<medical_guidance>`
블록을 그대로 시스템 프롬프트에 넣으라고 한다.
이 블록은 어린이의 복용량을 기억이 아니라 제품 라벨(웹 검색이 있으면 DailyMed
같은 공식 사본으로 확인)에서만 알려 주고, 라벨이 없으면 약사나 의사에게 가라고
안내하게 한다.

## 이전하기

이전 세대에서 옮길 때의 고려 사항은 다음과 같다.
원하는 행동을 구체적으로 쓴다.
품질과 상세함을 높이는 수식어를 붙인다.
애니메이션과 상호작용 요소는 원하면 명시적으로 요청한다.
사고 설정을 적응형으로 바꾸고 `budget_tokens` 대신 `effort`로 깊이를 조절한다.
프리필 응답에서 벗어난다.
게으름 방지 프롬프트를 낮춘다. 이전 모델에서 필요했던 지시에 4.6 모델은 과반응할
수 있다.
사고 블록을 변경 없이 되돌려 보내고 기록을 추가 전용으로 유지한다.
Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5에서는 사고 블록 앞의 대화를
수정하면(앞선 메시지 편집, 시스템이나 도구 재구성, 오래된 턴의 제자리 요약) 이후
모든 사고 블록이 무효가 되어 오류가 나거나 블록이 버려진다.
이런 변경은 대화 중간의 시스템 메시지나 서버 쪽 컨텍스트 관리로 옮겨야 한다.

## 트레이드오프

### 지시를 강하게 쓸수록 모델이 정밀해지고 과반응도 한다

최신 모델은 시스템 프롬프트에 더 민감하다.
도구가 덜 호출되던 이전 모델용으로 반드시 쓰라는 강한 언어를 쓰면 이제 과호출이
되고, 더 철저히 하라는 지시는 과탐색과 과사고로 이어진다.
문서의 처방은 강한 언어를 보통의 언어로 낮추고, 일괄 기본값을 표적 지시로
바꾸고, 노력 수준을 대비책으로 쓰는 것이다.
이 처방의 어려움은 같은 프롬프트가 모델 세대에 따라 반대 방향으로 오작동한다는
것이어서, 프롬프트를 한 번 쓰고 끝낼 수 없다.

### 지시의 구체성과 자유도 사이에서 고른다

명시적 지시가 정밀한 이행을 낳지만 처방적 단계는 모델의 추론을 제약한다.
문서는 처방적 계획보다 일반적 지시가 더 나은 추론을 낳는 경우가 많고 Claude의
추론이 사람이 규정하는 것을 자주 넘어선다고 말한다.
반대로 형식과 제약은 구체적으로 쓰라고 한다.
무엇을 구체적으로 쓰고 무엇을 열어 둘지가 판단이다. 이 문서는 출력의 형식과
제약, 행동의 허용 범위는 구체적으로, 추론의 방법은 일반적으로 쓰는 것으로
읽는다.
이는 이 문서의 해석이다.

### 모델별 안내가 많아 일반 원칙과의 경계가 흐려진다

같은 문서에 여러 모델의 예외가 겹쳐 있다.
Opus 5의 과검증과 Opus 4.6의 하위 에이전트 과사용과 Fable 5.1의 갱신 부족이 서로
다른 조정을 요구한다.
어떤 지침이 자기 모델에 해당하는지를 가려내는 일이 사용자의 몫이고, 문서는
모델별 페이지를 먼저 읽으라고 안내하지만 지침 사이의 충돌을 해결하지는 않는다.

## 함정

- 프리필이 든 요청은 Claude 4.6 모델부터 400 오류가 난다. 코드에 프리필이 남아
있는지 먼저 찾는다.
- `budget_tokens`는 4.7 이후 모델에서 400 오류다. 이전 모델용 설정을 그대로
옮기면 깨진다.
- 사고가 기본으로 켜진 모델에서는 응답이 사고 블록으로 시작하므로 첫 블록을
텍스트라고 가정한 코드는 깨진다.
- 마크다운 억제 블록을 형식이 적은 모델(Fable 5.1)에 그대로 쓰면 필요한 구조까지
억누른다.
- 검증 지시를 Opus 5에 그대로 쓰면 과검증으로 토큰과 지연이 는다.
- 사고 블록 앞의 대화를 요약하거나 고치면 이후 사고 블록이 무효가 된다. 기록은
추가 전용으로 둔다.
- 약 복용량 블록은 문서가 준 모델별 문구를 그대로 쓰라고 한다. 고쳐 쓴 블록은
검증되지 않았다.

## 확인하기

문서 자신이 권하는 방법은 기법이 특정 모델에서 측정된 것이므로 다른 모델에 쓰기
전에 자신의 eval로 확인하는 것이다.
이 문서는 실행하지 못했지만, 가장 작은 확인은 같은 요청을 지시를 바꾼 두
프롬프트(예를 들어 하지 말라는 문장과 하라는 문장)로 같은 모델에서 여러 번 돌려
출력 형식이 어떻게 달라지는지 세어 보는 것이다.
프롬프트를 모델 세대 사이에 옮길 때는 같은 eval 묶음을 두 모델에 돌려 과호출,
과사고, 과검증의 증상이 나타나는지 본다.

## 체크리스트

- 맥락이 없는 동료에게 프롬프트를 보여 주고 혼란스러워하지 않는지 확인했는가.
- 지시에 이유를 붙였는가.
- 예시는 3~5개이고 `<example>` 태그로 감쌌는가.
- 긴 문서는 위에, 질의는 끝에 있는가.
- 형식은 하지 말라는 문장이 아니라 하라는 문장으로 썼는가.
- 프리필과 `budget_tokens`를 쓰는 코드가 남아 있지 않은가.
- 사고가 기본으로 켜진 모델에서 콘텐츠 블록을 위치가 아니라 종류로 고르는가.
- 되돌리기 어려운 행동은 먼저 묻도록 지시했는가.
- 여러 컨텍스트 윈도우 작업에 `tests.json`과 `progress.txt`와 git 같은 상태
저장을 갖췄는가.
- 모델별 페이지를 먼저 읽고 자신의 eval로 확인했는가.

## 기억할 원칙

### 프롬프트는 모델의 성격에 대한 가설이고 모델이 바뀌면 다시 시험한다

문서가 모델마다 조정을 달리 요구하는 것은 프롬프트가 영구적인 최적해가 아니라
특정 모델의 경향에 대한 보정이라는 뜻이다.
과호출이 필요했던 시절의 강한 언어는 과호출 모델에서는 해가 되고, 검증을
요구하던 지시는 스스로 검증하는 모델에서는 낭비다.
따라서 프롬프트에 가정한 모델의 경향을 주석으로 남기고, 모델을 바꿀 때 그 가정을
다시 시험하는 것이 오래 쓰는 방법이다.
