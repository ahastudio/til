# Claude Fable 5.2 프롬프팅: 관찰한 증상마다 처방이 다르고, 처방마다 토큰과 부작용이 따르므로 하나씩 넣고 재야 한다

원문: [Prompting Claude Fable 5.2](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2)

HN 토론: <https://news.ycombinator.com/item?id=50453513> (12점, 0개 댓글)

## 소개

Anthropic이 Claude Platform 문서에 올린 Claude Fable 5.2 전용 프롬프팅 가이드다.
모델의 기능과 API 변경은 별도 문서(What’s new, 마이그레이션 가이드)가, 모든 최신
모델에 공통인 기법은 Prompting best practices 문서가 다룬다.
이 가이드는 그 둘에 없는 것, 곧 Fable 5.2가 이전 모델과 다르게 행동하는 대목과
그에 맞춘 시스템 프롬프트와 하니스(harness) 조정만 다룬다.
페이지 설명은 이 내용이 Claude Mythos 5.2에도 해당한다고 적는다.

가이드의 구성은 관찰한 증상에서 시작한다.
처음에 아홉 개의 증상 목록을 놓고 각각 해당 절로 보낸다.
그래서 처음부터 읽는 문서가 아니라, 내 에이전트가 보이는 행동에 맞는 절을 찾아
읽는 문서다.
이 문서는 같은 증상 순서가 아니라 동작, 값, 대가, 함정의 순서로 다시 정리했다.

이 문서가 읽은 범위는 가이드 본문 전체와, 가이드가 근거로 연결한 Preserved
thinking 문서와 Mid-conversation system messages 문서의 해당 대목이다.
가이드의 수치는 모두 Anthropic이 자체 테스트에서 낸 값이며 이 문서가 Fable 5.2를
호출해 재현하지는 않았다.
가이드의 프롬프트 문구는 그대로 옮기지 않고 내용만 풀어 썼다.
「확인하기」의 스크립트는 이 문서가 직접 실행한 것이고 모델을 호출하지 않는다.

## 동작 방식

### 가이드는 관찰한 증상에서 처방을 찾게 만든다

| 관찰한 증상                                                         | 해당 절                         |
| ------------------------------------------------------------------- | ------------------------------- |
| 어떤 effort를 써야 할지 모르겠거나 쉬운 요청이 느리게 시작한다      | effort 정하기                   |
| 작업이 끝나기 전에 턴이 끝난다                                      | 작업을 끝까지 하게 하기         |
| 코딩 에이전트가 기존 코드를 복사하거나 문제를 보고만 하고 둔다      | 코드의 소유자 밝히기            |
| 긴 에이전트 턴이 조용해 보인다                                      | 긴 턴 동안 사용자에게 알리기    |
| 작업에 필요한 것보다 서브에이전트를 많이 시작한다                   | 서브에이전트에 대한 기대 정하기 |
| 에이전트가 불필요한 승인을 요청하거나 일상 작업을 보류한다          | 쌓이는 주의 문구 줄이기         |
| 시스템 프롬프트, 스킬, 하니스가 Fable 5.1이나 Opus 5.5용으로 쓰였다 | 이전 모델용 지침 점검하기       |
| 사용자가 긴 작업 뒤의 최종 보고서를 읽는다                          | 보고서 읽기 쉽게 하기           |
| 요청이 `stop_reason: "refusal"`을 돌려준다                          | 거절 다루기                     |

### effort가 생각의 양과 도구 호출 수와 토큰을 정한다

가이드는 effort가 모델이 얼마나 생각하는지, 도구를 몇 번 호출하는지, 턴이 얼마나
걸리는지, 토큰을 얼마나 쓰는지를 정한다고 설명한다.
Claude API에서 Fable 5.2의 기본값은 `high`다.
같은 effort 단계는 모델이 달라도 같은 순서지만 단계별 생각의 양은 다를 수
있어서, Fable 5.1이나 Opus 5.5에서 맞춘 값을 가져오지 말고 effort 비교
시험(sweep)을 다시 하라고 한다.

`high` 이상에서는 인사에 답할 때도 거의 모든 응답 전에 생각한다.
Anthropic의 테스트에서 직접 답하라는 지시는 `medium` 이상에서 생각을
멈추지 못했다.
그러므로 기본 요청이 느리거나 비싸면 문구를 고칠 것이 아니라 그 턴의 effort를
낮춰야 한다.
effort는 응답 길이에는 영향이 적어서 길이와 어조는 프롬프트로 바꾼다.

한 작업 안에서 단계를 섞을 수도 있다.
`medium`으로 계획을 세운 뒤 길고 사람이 지켜보지 않는 구간만 올리는 식이다.
프롬프트 캐시(prompt cache)를 유지하면서 대화 도중 effort를 바꾸려면 메시지별
effort(베타)를 쓰고, 쓸 수 없으면 다음 요청에 새 최상위 `effort` 값을 주되
그러면 캐시가 다시 시작된다.

### 모델이 턴을 일찍 끝내는 방식은 세 가지다

긴 다단계 작업에서 Fable 5.2는 일이 끝나기 전에 턴을 끝낼 때가 있다.
남은 일을 나열하며 끝내거나, 계속할지 묻고 끝내거나, 시간 초과 같은 평범한
장애에서 멈춘다.
`low`와 `medium`에서 더 자주 일어난다.

가이드가 권하는 시스템 프롬프트의 취지는 둘로 나뉜다.
오류, 시간 초과, 잠긴 파일, 빈 결과, 실패한 도구 같은 평범한 장애는 먼저
진단하고, 진짜 막힌 것이 아니면 재시도나 다른 도구로 돌파하게 한다.
반대로 누군가가 분명히 막아 둔 것(건드리지 말라고 표시된 파일, 일부러 막은 접근,
안전 장치)은 건드리지 않고 무엇을 발견했는지 말한 뒤 다른 안전한 길을 찾게 한다.
그리고 사용자의 답이 필요 없는 일은 멈추지 않고 이어 가게 한다.

Anthropic은 에이전트형 코딩 제품의 녹화 세션을 `medium`에서 다시 돌려 이 문구의
한 버전을 시험했다.
미완료로 끝난 세션이 대략 절반으로 줄었고, 허락을 묻거나 계속할지 제안하는
종료는 대부분 사라졌다.
남은 일을 나열하고 멈추는 종료는 줄지 않았고, 출력 토큰은 약 30% 늘었다.
모델이 덜 묻게 되므로 위험하거나 되돌릴 수 없는 작업의 확인 단계는 하니스에
그대로 두라고 한다.

승인은 구체적으로 줘야 한다.
단순한 계속(continue)이나 엄지 이모지 대신 어떤 작업을 허락하는지(예: 스테이징
데이터베이스에서 마이그레이션을 실행하라) 적는다.
승인이 필요한 단계를 시스템 프롬프트에 쓸 때도 대상을 좁혀야 한다.
Anthropic의 모의 테스트에서 “이 대화 밖의 사람에게 메시지를 보내는 일”을 승인
대상에 넣었더니 동료와 다른 팀에 보내는 일상 요청의 약 절반을 모델이 보류했다.

### 코드의 소유자를 밝히면 구조를 고치려는 성향이 켜진다

Fable 5.2는 코드가 누구 것인지에 민감하다.
작은 코딩 과제에서 프롬프트가 소유에 대해 아무 말도 하지 않거나 남의
코드베이스로 소개하면, 중복이 생기더라도 기존 구조에 더하는 경향이 있었다.
코드베이스가 모델 자신의 것이라고 하면 중복 코드를 합치고, 시키지 않은 관련
수정도 가끔 했다.

처방은 모델이 이 코드베이스의 소유자이자 장기 유지보수자이며 설계가 자기에게
달려 있다고 말하는 한 문장이다.
이 문장으로 중복 코드를 공통 함수로 합친 실행이 10% 미만에서 약 75%로 늘었다.
대가는 크다.
출력 토큰이 약 70~80% 늘었고, 시키지 않은 변경(특히 새 테스트와 문서)이 생겼고,
일부 실행에서는 기존 기능의 동작이 바뀌었다.
PR 요약이 작은 변경을 빼먹는 경우도 많아서 요약과 실제 diff를 함께 봐야 한다.
사용자가 코드를 가졌고 변경을 최소로 원하면 이 문장을 빼라고 한다.
“겸사겸사 하는 리팩터링과 이름 변경을 하지 말라”는 범위 제한 규칙을 앞에 넣어도
이 문장을 취소하지 못했고, 그 경우에도 절반이 넘는 실행에서 중복을 합쳤다.

### 진행 상황은 thinking 블록으로 오고, 기본값에서는 비어 있다

긴 도구 호출 구간에서 사용자에게 보이는 글이 적거나 첫 도구 호출 전에 무엇을
할지 말하지 않을 수 있다.
가이드가 먼저 점검하라는 것은 클라이언트다.
Fable 5.2에서 도구 호출 사이에 모델이 쓰는 갱신은 진행 갱신(progress-update)
`thinking` 블록으로 온다.
기본 `thinking.display` 값은 `"omitted"`이고 이때 블록의 text는 비어 있다.
그래서 `text` 블록만 그리는 클라이언트는 긴 턴 동안 조용해 보인다.
`display`를 `"updates"`(베타, `thinking-display-updates-2026-08-18` 헤더)로
바꾸면 갱신 요약을, `"summarized"`로 바꾸면 갱신과 추론 요약을 함께 받는다.
받은 뒤 도구 호출 사이에 text가 있는 `thinking` 블록을 그려야 한다.

대화형 환경에서 갱신을 더 늘리려면 세 가지 방법이 있다.

첫째, 하니스에서 연속 침묵을 센다.
`text`도 text가 있는 `thinking`도 없는 도구 호출 단계가 몇 번 이어지는지 센다.
`display`가 `"updates"`나 `"summarized"`일 때만 센다.
여러 번 이어지면 최신 도구 결과 뒤에 알림을 붙이는데,
사용자가 한동안 소식을 못 들었으니 지금 하는 일을 몇 마디로 말하고
계속하라는 취지다.
이 알림은 턴 범위 시스템 메시지(turn-scoped system message)로 붙이며
`clear_at: "next_user_message"`와 베타 헤더
`mid-conversation-system-clear-at-2026-08-21`을 쓴다.[^mid-conversation]
Anthropic의 다단계 코딩 테스트에서 이 알림은 가장 긴 침묵 구간을 대략 절반으로
줄였고 토큰이나 시간은 눈에 띄게 늘지 않았다.

둘째, 시작 줄과 마무리 요약을 요청한다.
첫 도구 호출 전에 한 줄로 할 일을 말하고, 중간에 짧은 갱신을 하고,
끝에 그 메시지만 읽어도 전체를 알 수 있는 요약을 쓰게 하는 시스템
프롬프트 문구다.
코딩 과제의 모든 실행에서 첫 도구 호출 전에 메시지를 썼고 과제당 출력 토큰이
약 20% 늘었다.

셋째, 시스템 프롬프트에 한 문장을 넣는다.
도구를 몇 번 호출할 때마다 현재 상황을 한 줄로 알리라는 문장이다.
워크플로 자동화 과제에서 긴 침묵 대부분이 사라졌다.

알림을 하니스에서 넣었다면 이후 요청에서도 `messages`에 그대로 남겨야 한다.
지우거나 고쳐 쓰는 것은 앞 턴을 편집하는 일이어서 그 뒤의 thinking 블록이
무효가 된다.
Mid-conversation system messages 문서도 이미 지워진(cleared) 턴 범위 메시지를
그대로 다시 보내야 하고 현재 상태로 다시 만들어 보내면 앞 메시지를 편집하는
것이라고 설명한다.[^mid-conversation]
가이드는 이 모델이 사람이 자주 갱신을 기다리지 않는 긴 비동기 작업에 잘 맞아서
그런 작업에 추천한다고 덧붙인다.

### 서브에이전트는 하니스가 부르는 만큼 시작한다

위임을 얼마나 하는지는 하니스와 과제에 달렸다.
짧은 과제와 최소한의 서브에이전트 도구에서는 거의 시작하지 않았고, 위임을 권하는
프롬프트를 가진 코딩 제품에서는 적극적으로 위임했다.
`xhigh`와 `max`에서는 자기 작업을 검토하려고 서브에이전트를 썼는데 Fable 5.1은
같은 과제에서 그러지 않았다.
초기 테스터는 Fable 5.2를 다른 모델의 계획자와 조정자로 쓰는 데 좋은
결과를 얻었다.

서브에이전트가 한 세션 비용의 큰 부분을 차지할 수 있으므로 서브에이전트가
기본으로 쓰는 모델을 확인해야 한다.
도구 설명은 필요한 것보다 많이 시작할 때만 바꾼다.
새 설명에는 서브에이전트가 세션 비용에 얼마를 더하는지, 위임이 값어치 있는 때와
아닌 때, 서브에이전트에게 일을 어떻게 설명해 보낼지를 쓴다.
`high`에서 이런 비용 중심의 긴 설명이 짧은 설명보다 서브에이전트 수를 대략
절반으로 줄였다.

### 쌓인 주의 문구는 모델이 그대로 따른다

기억(memory)과 노트와 지침 파일에는 지난 세션의 주의 문구가 쌓이고, Fable 5.2는
이를 가까이 따라서 불필요한 승인을 요청한다.
초기 테스트에서는 여러 에이전트가 함께 일할 때 주로 보였다.
가이드의 처방은 네 가지다.

1. 더 필요 없는 노트를 지운다.
   기억 속의 “다시 시도하지 말라” 같은 옛 지침을 모델이 계속 따른다.
2. 승인이 필요 없는 단계를 이름으로 적는다.
   더 자유롭게 행동하라는 말은 모호하다.
3. 검증 단계를 점검한다.
   “첫 오류에서 멈추고 검토하라” 같은 조건이 자율 작업을 막을 수 있다.
4. 예외를 분명히 한다.
   모델은 “never”가 든 지침을 절대적인 것으로 받아들인다.
책임을 모델에게 두고 싶으면 파일을 절대 지우지 말라는 말 대신 파일을 지우기 전에
   승인을 요청하라고 쓴다.

### 접두사 검사가 이전 사고 블록의 유효성을 정한다

가이드는 프롬프트 문구를 더하거나 빼는 작업을 새 대화에서만 하라고 경고한다.
Fable 5.2는 보존된 사고(preserved thinking)를 쓰고, API가 모든 계정에 접두사
검사(prefix check)를 강제하기 때문이다.
Preserved thinking 문서에 따르면 블록의 접두사는 그 앞의 최상위 `system`
프롬프트와 `tools`와 `messages`이고, 접두사가 그 블록을 만들 때 보낸 것과 다르면
그 블록과 뒤의 사고 블록이 모두 검사에 실패한다.[^preserved-thinking]
Fable 5.2는 계정이 언제 만들어졌든 설정이 비어 있을 때 400 오류를
돌려준다.[^preserved-thinking]
`effort`, `max_tokens`, `output_config`, `tool_choice`, `metadata`와
`cache_control` 표시는 접두사에 들지 않는다.[^preserved-thinking]

옛 사고 블록은 접두사에 들지 않지만 각 블록은 앞 블록을 기록한다.
가장 오래된 블록이나 가장 새 블록이나 전부는 제거할 수 있지만, 가운데를 빼면 그
뒤가 무효가 된다.[^preserved-thinking]
`thinking.block_binding.prefix_mismatch_behavior`를 `"drop_block"`으로
두면(베타, `thinking-binding-controls-2026-08-01` 헤더) 실패한 블록을 버리고
요청이 성공한다.
문서는 이것이 근본 해결이 아니라 임시방편이며, 모델이 이전 턴의 추론을 읽지
못하면 다시 만들어 내서 출력 토큰이 늘 수 있다고 경고한다.[^preserved-thinking]
가이드의 안내는 같다.
압축과 컨텍스트 편집을 빼면 기록을 추가만 하는(append-only) 상태로
유지하라는 것이다.
그러면 캐시 적중률이 높게 유지되고 버려지는 사고도 없다.

### 이전 모델용으로 쓴 지침 가운데 비용이 들거나 효과가 없는 것이 있다

가이드는 Fable 5.2로 옮길 때 다음 습관을 다시 보라고 한다.

- 위임을 지시하는 줄이 시스템 프롬프트, 스킬, 에이전트 파일에 있으면 과하게
  위임할 때 지운다.
- 모델에게 작업의 토큰 예산을 보여 주는 하니스가 있으면, `high`와 `xhigh`의 코딩
  과제에서 큰 예산을 없애도 성능이 같고 비용이 줄었다.
이 결과는 프롬프트 속 문장에 대한 것이고 API의 작업 예산(task budgets, 베타)
  기능은 시험하지 않았다.
- 앞 턴을 편집하는 하니스 코드는 접두사 검사에 걸린다.
- Opus 5.5 가이드가 채팅용으로 제안한 “앞 답변은 끝난 것으로 보라”는 두 문장은,
  `high`에서 후속 질문에 대한 Fable 5.2의 생각을 줄였고 앞 답변의 실수를 짚는
  일도 크게 줄였다.
- “숙고하지 말고 바로 답하라”는 지시는 Fable 5.1에서는 대체로 따랐지만 Fable
  5.2는 `medium` 이상에서 생각을 멈추지 않는다.
지시를 지우고 effort를 낮춘다.
- “한 문장에 한 지시, 20단어 이하” 같은 글쓰기 규칙은 엄격히 따라서 문장이 끊겨
  보일 수 있다.
- 쌓인 규칙과 노트와 기억은 이유가 사라진 것을 지우고, 절대 규칙은 범위와 이유를
  붙여 다시 쓴다.
이미 막힌 시스템은 기억과 노트를 줄여 다시 시작하는 것도 생각해 볼 만하다.

### 최종 보고서는 처음 보는 사람을 기준으로 쓰게 한다

초기 테스터는 Fable 5.2의 글을 Fable 5.1보다 높게, 명확성은 Opus 5.5와 비슷하게
평가했다.
그러나 긴 에이전트 작업 뒤 보고서를 읽는 사람은 도구 호출과 파일을 보지
못했으므로 보고서가 혼자서 이해되어야 한다.
가이드가 주는 시스템 프롬프트는 맥락이 적은 독자를 상정하고, 핵심을 첫 몇 문장에
두고, 정의되지 않은 참조를 앞줄에 쓰지 않고, 작업 중 만든 용어를 쓰지 않고, 쉬운
단어와 짧은 문장(ASD-STE100 단순 기술 영어 스타일)으로 쓰라는 내용이다.
에이전트 과제에서 이 문구는 보고서의 밀도를 낮추고 세미콜론을 줄였고, 워크플로
자동화 과제에서는 문장을 짧게 했다.
길이나 세부 항목은 사용 목적에 맞춰 더 지시할 수 있다.

### 거절은 범주와 함께 돌아오고, 추론을 본문에 쓰게 하면 걸린다

Fable 5.2는 안전 분류기를 돌리며 거절된 요청은 `stop_reason: "refusal"`과
`stop_details.category`를 돌려준다.
범주는 `cyber`, `bio`, `frontier_llm`(경쟁 AI 모델 개발을 도울 수 있는 요청),
`reasoning_extraction`(내부 추론을 응답 본문에 재현하라는 요청),
`general_harms`, `null`이다.
정당한 보안과 생명과학 업무도 `cyber`와 `bio` 분류기에 걸릴 수 있어서
Anthropic의 검증 프로그램(Cyber Verification, Life Sciences Verification)을
안내하고, Mythos 5.2는 그 프로그램으로 검증된 조직에만 같은 기능을
제공한다고 한다.
프롬프트나 스킬이나 도구 설명이 추론을 응답에 써 달라고 요청한다면 지운다.
모델이 어떻게 추론했는지는 `display: "summarized"`로 두고 thinking
블록에서 읽는다.

`high` 위의 이득은 과제마다 고르지 않으므로 내 평가에서 이득이 확인된
곳에만 올린다.

## 트레이드오프

### 덜 멈추는 모델은 덜 묻는 모델이다

일찍 멈추는 증상에 처방을 넣으면 허락 요청과 계속 제안이 줄어든다.
같은 효과가 모델이 위험한 작업에서도 덜 묻게 만든다.
가이드가 확인 단계를 하니스에 남기라고 하는 이유가 이것이다.
얻는 것은 사람이 지켜보지 않는 긴 실행의 완주율이고, 치르는 것은 출력 토큰
약 30%와 모델에게 맡기던 안전 확인을 하니스로 옮기는 일이다.
얻을 수 없는 것도 있다.
남은 일을 나열하고 멈추는 종료는 이 처방으로 줄지 않았다고 가이드가 밝힌다.

### 구조 개선을 시키면 변경의 범위를 통제하기 어렵다

소유자 문장은 중복 통합을 10% 미만에서 약 75%로 올린다.
같은 문장이 요청하지 않은 테스트와 문서를 만들고 일부 기능의 동작까지 바꾼다.
범위 제한 규칙을 앞에 넣어도 절반이 넘는 실행에서 통합이 일어났다는 시험 결과는
“이 정도만 고치라”는 제한이 이 문장의 효과를 온전히 막지 못한다는 뜻이다.
구조 개선이 목적인 정리 작업에는 맞지만, 기능 수정 작업에는 이 문장을 빼고 검토
단계에서 diff를 읽는 쪽이 안전하다.
요약이 변경을 빼먹는 경향도 있어서 요약만 믿고 병합할 수 없다.

### 진행 알림은 클라이언트와 하니스를 바꿔야 얻는다

모델에게 한 문장을 더하는 방법이 가장 싸고, 하니스의 알림이 가장 효과가
크다(가장 긴 침묵을 대략 절반으로, 토큰은 그대로).
그러나 하니스 방법은 `display` 값 변경, 베타 헤더 두 개, 턴 범위 메시지 지원,
이후 요청에 알림 유지까지 요구한다.
클라이언트가 `thinking` 블록을 그리지 않으면 어느 쪽도 사용자에게 닿지 않는다.
가이드도 문장만 넣었을 때 여러 도구 호출이 갱신 없이 이어지는 것은 남는다고
인정한다.

## 함정

### 저장된 대화에 새 문구를 넣으면 400 오류가 날 수 있다

이 가이드에서 가장 실무적인 경고다.
시스템 프롬프트에 문구를 더하거나 도구 설명을 바꾸는 처방은 새 대화에서만
하라고 한다.
사고 블록을 보낸 대화에서 `system`이나 `tools`나 앞 메시지를 바꾸면 접두사
검사에 걸린다.
이미 진행 중인 대화에서 지침을 바꾸려면 새 턴에 넣거나 대화 중간 시스템 메시지로
덧붙인다.
처방을 적용했다는 것과 기존 세션이 계속 동작한다는 것은 별개의 일이다.

### 범위 제한 규칙이 소유자 문장을 이기지 못한다

소유자 문장 앞에 범위 제한 규칙이 있어도 절반이 넘는 실행에서 중복이 통합됐다.
위임을 지시하는 줄이 남아 있으면 서브에이전트 설명을 바꿔도 과다 위임이 이어질
수 있다는 것은 이 문서의 추정이다.
가이드가 위임 줄을 먼저 읽고 지우라고 한 순서는 이 추정과 맞는다.
어느 쪽이든 처방을 넣기 전에 옛 지침을 지우는 순서가 필요하다.

### 앞 답변을 끝난 것으로 보라는 문장이 자기 오류 지적을 없앤다

Opus 5.5 시절의 지침이 Fable 5.2에서 후속 질문의 생각을 줄이고 앞 답변의 실수를
짚는 일을 크게 줄였다.
비용을 줄이려는 문장이 품질 안전 장치를 함께 없앤 사례다.
쓰려면 모델이 자기 실수를 여전히 짚는지 먼저 확인한다.

### 침묵을 세면서 display를 omitted로 둔다

`"omitted"`에서는 모든 `thinking` 블록이 비어 있어 모든 단계가 조용해 보인다.
연속 침묵을 세는 하니스는 `"updates"`나 `"summarized"`일 때만 의미가 있다.

### 절대 규칙은 문자 그대로 받아들여진다

“never”가 든 지침을 모델은 절대적인 것으로 받아들인다.
정말 절대적이지 않다면 승인을 요청하라는 식으로 예외를 쓴다.

## 비평

### 처방이 막는 중단은 세 가지 중 둘뿐이다

가이드는 일찍 끝나는 방식을 셋으로 나눈다.
남은 일을 나열하고 끝내기, 계속할지 묻고 끝내기, 평범한 장애에서 멈추기다.
처방의 효과를 보고하는 단락은 허락을 묻거나 계속을 제안하는 종료가 대부분
사라졌다고 하고, 남은 일을 나열하고 멈추는 종료는 줄지 않았다고 덧붙인다.
그렇다면 처방은 세 가지 중 둘만 다루고, 가이드가 가장 먼저 든 형태는 이 가이드
안에 해법이 없다.
가이드가 이 한계를 숨기지는 않았다.
다만 증상 목록은 작업이 끝나기 전에 턴이 끝난다는 증상을 이 절 하나로 보내서,
독자는 세 형태가 모두 다뤄진다고 기대하기 쉽다.
하니스에서 남은 항목을 확인하고 이어 가게 하는 장치가 따로 필요한지는 이
가이드에서 알 수 없다.

### 수치는 조건이 좁고 표본이 공개되지 않았다

가이드의 수치 거의 전부는 Anthropic이 자체 테스트에서 낸 값이고 조건이 한 줄로
제시된다.
녹화 세션을 `medium`에서 재생한 한 제품, 작은 코딩 과제, 다단계 코딩 과제,
`high`에서의 한 코딩 제품, 워크플로 자동화 과제 같은 식이다.
과제의 수, 반복 횟수, 신뢰 구간은 없다.
“대략 절반”이라는 표현은 방향은 알려 주지만 내 하니스에서 같은 폭이 나올
근거는 아니다.
가이드도 마지막 단계에서 효과와 토큰 비용을 내 과제에서 재라고 말한다.
그러므로 표의 수치는 기대치가 아니라 무엇을 재야 하는지의 목록으로 읽어야 한다.

### 처방끼리의 상호작용은 측정하지 않았다

각 처방의 효과는 따로 측정됐다.
그러나 같은 가이드가 소유자 문장과 범위 제한 규칙이 충돌하면 문장이 이기는 것을
보여 준다.
이는 지침이 단순히 더해지지 않는다는 증거다.
작업 완주 문구, 소유자 문장, 진행 알림 문구, 보고서 문구를 모두 넣으면 어떻게
되는지, 특히 출력 토큰의 증가 폭(30%, 70~80%, 20%)이 합쳐지는지는 가이드에 없다.
마지막 단계가 처방을 하나씩 넣고 효과를 재라고 한 것은 이 간극에 대한
대답이지만, 그 말은 가이드가 제안한 문구 묶음을 한꺼번에 복사해 쓰는 것이
위험하다는 뜻이기도 하다.

## 확인하기

가이드의 두 가지 하니스 처방은 모델을 호출하지 않고 점검할 수 있다.
하나는 사용자가 읽을 것이 없는 연속 도구 호출 단계 수를 세는 것이고, 다른 하나는
요청 사이에 `system`, `tools`, 앞 `messages`가 바뀌었는지 보는 것이다.
아래 스크립트는 파이썬 표준 라이브러리만 쓰고 이 문서가 실행했다.
Fable 5.2가 실제로 어떻게 행동하는지는 이 실험이 보여 주지 않는다.
점검 로직이 가이드의 설명대로 동작하는지만 모형 데이터로 보인다.

```python
import json


def longest_silent_run(assistant_turns):
    """사용자가 읽을 것이 없는 연속 도구 호출 단계의 최댓값을 센다.

    단계마다 text 블록이나 내용이 있는 thinking 블록이 있으면 그 단계는 조용하지 않다.
    display가 "omitted"이면 모든 thinking 블록의 text가 비어 있으므로 조용한 단계로 센다.
    """
    longest = current = 0
    for blocks in assistant_turns:
        if not any(b["type"] == "tool_use" for b in blocks):
            current = 0  # 도구 호출이 없는 응답은 연속을 끊는다
            continue
        readable = any(
            (b["type"] == "text" and b.get("text", "").strip())
            or (b["type"] == "thinking" and b.get("thinking", "").strip())
            for b in blocks
        )
        current = 0 if readable else current + 1
        longest = max(longest, current)
    return longest


def prefix_edits(requests):
    """각 요청이 앞 요청의 system, tools, messages 앞부분을 그대로 유지했는지 본다."""
    problems = []
    for i in range(1, len(requests)):
        prev, cur = requests[i - 1], requests[i]
        if prev["system"] != cur["system"]:
            problems.append((i, "system이 바뀌었다"))
        if prev["tools"] != cur["tools"]:
            problems.append((i, "tools가 바뀌었다"))
        n = len(prev["messages"])
        for j in range(min(n, len(cur["messages"]))):
            if prev["messages"][j] != cur["messages"][j]:
                problems.append((i, f"messages[{j}]가 바뀌었다"))
                break
        else:
            if len(cur["messages"]) < n:
                problems.append((i, "messages가 줄었다"))
    return problems


# 1) 조용한 단계 세기
tool = {"type": "tool_use", "name": "read_file"}
turns = [
    [{"type": "thinking", "thinking": ""}, tool],                          # 조용함
    [{"type": "thinking", "thinking": ""}, tool],                          # 조용함
    [{"type": "thinking", "thinking": ""}, tool],                          # 조용함
    [{"type": "text", "text": "설정 파일을 읽었고 이제 테스트를 돌린다."}, tool],  # 읽을 것이 있음
    [{"type": "thinking", "thinking": ""}, tool],                          # 조용함
]
print("조용한 연속 단계의 최댓값:", longest_silent_run(turns))
turns[0][0]["thinking"] = "먼저 설정 파일 위치를 찾는다."
turns[1][0]["thinking"] = "찾은 파일을 읽는다."
print("display를 updates로 바꾼 뒤:", longest_silent_run(turns))

# 2) 앞부분 변경 감지
base = {"system": "규칙 v1", "tools": [{"name": "read_file"}],
        "messages": [{"role": "user", "content": "버그를 고쳐 줘"}]}
r1 = json.loads(json.dumps(base))
r2 = json.loads(json.dumps(base)); r2["messages"].append({"role": "assistant", "content": "확인한다"})
r3 = json.loads(json.dumps(r2)); r3["system"] = "규칙 v1 (오늘 날짜 추가)"
r4 = json.loads(json.dumps(r3)); r4["messages"][0]["content"] = "버그를 고쳐 줘 (수정됨)"
r5 = json.loads(json.dumps(r4)); r5["messages"].append({"role": "user", "content": "계속"})
for i, why in prefix_edits([r1, r2, r3, r4, r5]):
    print(f"요청 {i}: {why}")
print("검사한 요청 수:", 5)
```

실행 결과는 이렇다.

```text
조용한 연속 단계의 최댓값: 3
display를 updates로 바꾼 뒤: 1
요청 2: system이 바뀌었다
요청 3: messages[0]가 바뀌었다
검사한 요청 수: 5
```

읽는 방법은 이렇다.
`thinking` 블록이 모두 비어 있을 때(기본 `"omitted"`에 해당) 조용한 단계가
연속 3번이다.
앞의 두 단계에 text를 넣자(`"updates"`에 해당) 최댓값이 1로 줄어든다.
요청 번호는 0부터 센다.
요청 2는 `system`에 날짜 문구를 더했고, 요청 3은 첫 사용자 메시지를 고쳤으므로
둘 다 접두사 변경으로 잡힌다.
요청 0에서 요청 1로 `messages`에 한 줄을 추가한 것은 잡히지 않는데, 추가만 하는
방식이 허용되기 때문이다.
요청 3에서 4로 사용자 메시지를 하나 더한 것도 마찬가지다.
이 스크립트는 `system`과 `tools`와 `messages`를 문자 그대로 비교할 뿐이며,
Preserved thinking 문서가 편집으로 치는 모든 경우(예: URL로 보낸 이미지의
바이트가 바뀌는 경우)를 잡지는 못한다.

## 체크리스트

- Fable 5.2의 `effort`를 `high`로 명시했고 `medium`과 `xhigh`도 돌려 보았다.
- 시스템 프롬프트, 스킬, 에이전트 파일, 기억 파일에서 이전 모델용 지침(위임
  지시, 생각을 줄이라는 지시, 글쓰기 규칙, 쌓인 절대 규칙)을 읽고 지우거나
  시험했다.
- 가장 긴 에이전트 작업을 돌려 일찍 멈춤, 불필요한 승인, 침묵, 과다 위임, 기존
  코드에 더하기가 있는지 기록했다.
- 처방은 한 번에 하나씩 넣었고 그때마다 효과와 출력 토큰 비용을 내
과제에서   쟀다.
- 클라이언트가 `thinking` 블록을 그리고 `display`가 `"updates"`나
  `"summarized"`인지 확인했다.
- 하니스가 `system`과 `tools`를 대화 내내 같게 두고 `messages`는 추가만 하는지
  확인했다.
- 저장된 대화에 새 문구를 넣지 않았고, 바꿔야 하면 새 턴에 넣었다.
- 위험하거나 되돌릴 수 없는 작업의 확인 단계를 하니스에 남겼다.
- 소유자 문장을 쓴다면 요약이 아니라 실제 diff를 검토한다.
- 프롬프트나 도구 설명이 모델에게 추론을 응답에 써 달라고 요청하지 않는다.

## 기억할 원칙

### 처방은 증상을 관찰한 뒤에 넣고 비용을 같이 잰다

가이드의 모든 처방에는 토큰이나 부작용이 붙어 있다.
관찰하지 않은 증상에 미리 처방을 넣으면 얻는 것 없이 비용만 치른다.
증상이 보이는 지점에서 한 번에 하나만 넣고, 효과와 출력 토큰을 함께 기록하는
것이 이 가이드의 마지막 단계가 말하는 방법이다.

### 지침은 모델이 따르는 코드이므로 이전 모델용 지침은 부채다

Fable 5.2는 지침을 가까이 따른다.
그래서 이전 모델에서 필요했던 지침, 쌓인 주의 문구, 한 번 넣고 잊은 규칙이
비용과 부작용을 만든다.
새 모델로 옮길 때는 문구를 더하기 전에 있는 것을 읽고 지우는 일이 먼저다.
그 확인을 쉽게 하려면 지침마다 이유를 적어 두는 것이 도움이 된다.
이 마지막 제안은 이 문서의 것이며 가이드가 말한 것은 아니다.
