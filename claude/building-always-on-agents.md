# 상시 가동 에이전트의 구성 요소

원문: [Building always-on agents](https://claude.com/ko/resources/articles/building-always-on-agents)

GN 토론: <https://news.hada.io/topic?id=37550>

## 소개

Anthropic의 William Hu가 2026년 11월 13일에 Claude 리소스 사이트에 올린 안내서이다.
분류는 모범 사례(Best practices)이고 제품은 Claude Platform으로 표시되어 있다.
상시 가동 에이전트(always-on agent)는 여러 세션에 걸쳐 언제 어떻게 행동할지
스스로 정하며 계속 실행되는 에이전트이다.
글은 이런 에이전트를 만드는 핵심 구성 요소와 그것들이 맞물리는 방식을 설명한다.

글에 따르면 상시 가동 에이전트는 상태를 유지하고 먼저 행동한다.
세션 사이에 맥락을 관리하고 직접 감독 없이 행동을 취한다는 뜻이다.
밑바닥에서는 다른 에이전트와 같은 핵심 루프(core loop)로 돌아가고,
차이는 에이전트가 언제 깨어나는지, 실행 사이에 무엇이 이어지는지,
작업 결과가 사용자에게 어떻게 닿는지를 정하는 주변 구조에 있다.

글은 최근 이런 에이전트가 다시 늘어난 이유를 두 가지로 든다.
첫째, 최신 모델은 사용자의 의도를 파악하고 언제 물어봐야 하는지 아는 판단이 낫다.
둘째, 지능이 싸지고 있고 장기 과제에서 특히 그렇다.
한 장기 코딩 벤치마크에서 Opus 5.5는 해결한 과제당 비용이 Opus 5보다 78% 낮았고,
일반 작업에서는 40% 낮았다고 한다.
이 수치는 Anthropic이 자사 모델에 대해 보고한 값이다.

## 동작 주기

상시 가동 에이전트는 실제로 계속 켜져 있지 않다.
대부분의 시간은 잠들어 있고 주기적으로 깨어나 일한다.
한 번 일하는 구간을 실행(run)이라 부른다.
실행에서 에이전트는 이벤트를 받고, 작업을 끝내고, 무슨 일이 있었는지 저장한다.
실행은 세션(session) 안에서 일어나며 세션은 메시지와 도구 호출의 기록이다.
실행이 끝나면 다시 잠들고 이 주기가 계속 반복된다.
글은 이것을 사용자가 느끼는 경험을 가리키는 말로 본다.

## 다섯 가지 구성 요소

글이 꼽는 구성 요소는 이벤트 인박스, 타이머, 메모리, 권한, 아웃박스이다.

### 이벤트 인박스(event inbox)

사용자 메시지만 기다리는 일반 에이전트와 달리 상시 가동 에이전트는
웹훅, 예약 작업, 백그라운드 작업 같은 여러 종류의 이벤트로 깨어난다.
이벤트 출처가 에이전트를 직접 부르는 방식은 두 이벤트가 동시에 와서
실행이 경쟁하거나, 충돌로 이벤트가 사라지는 문제가 있다.
그래서 모든 출처는 인박스에 이벤트를 쓰고 워커(worker)가 거기서 가져간다.

가장 단순한 구성은 세 부분이다.

1. 이벤트의 내구성 있는 목록. 보통 데이터베이스 테이블이다.
2. 이벤트를 목록에 쓰는 핸들러. 보통 HTTP 엔드포인트이다.
3. 목록을 읽는 워커. 보통 백그라운드 서비스이다.

인박스는 이벤트마다 상태를 기록하고 출처의 고유 식별자로 중복을 제거할 수 있다.
글은 관계형 데이터베이스에 이벤트를 행으로 추가하는 방식을 권하고,
사용자마다 인박스 하나로 시작하라고 한다.
사용자의 답장처럼 이전 작업을 잇는 이벤트는 기존 세션을 재개하고
나머지는 새 세션을 시작한다.

구현에서 글이 드는 모범 사례는 네 가지이다.

- 핸들러는 이벤트를 빨리 수신 확인(acknowledge)한다.
  웹훅 제공자는 느린 응답을 실패로 보기 때문이다.
  프롬프트 인젝션 검사 같은 깊은 검증은 실행 중에 한다.
- 인박스가 진실의 원천이다.
  워커가 실행 중에 죽어도 새 워커가 같은 이벤트를 집어 재시도할 수 있다.
- 인박스에는 활성 워커가 한 번에 하나만 있다.
  실행 중에 새 이벤트가 오면 다음 실행으로 미루거나, 현재 실행에 합치거나,
  중단하고 다시 시작할 수 있다.
- 워커는 쌓인 이벤트를 묶어 처리한다.
  사용자가 메시지를 연달아 보내면 한 번의 실행으로 합쳐 답장을 한 번만 한다.

### 타이머(timer)

타이머는 이벤트 인박스와 함께 에이전트가 먼저 행동하게 한다.
종류는 두 가지이다.
후속 확인(follow-up)은 답장을 확인하는 것처럼 에이전트가 스스로 정하는 마감이고,
스케줄(schedule)은 일간 뉴스레터처럼 정해진 주기로 반복되는 작업이다.

타이머는 인박스와 분리된 자기만의 내구성 저장소에 둔다.
인박스에는 지금 처리할 준비가 된 이벤트만 있어야 하기 때문이다.
타이머가 직접 실행을 시작하지는 않는다.
스케줄러가 정해진 간격으로 저장소를 훑어 기한이 된 것을 찾는다.
후속 확인은 완료로 표시하고, 스케줄은 다음 발생 시각으로 기한을 갱신한다.
그리고 인박스에 이벤트를 추가해 워커를 깨운다.
스케줄러는 직접 만들거나 내구성 실행 엔진(durable execution engine)을 쓸 수 있다.

### 메모리(memory)

에이전트는 서로 끊어진 여러 실행에 걸쳐 일하므로 연속성을 메모리에 의존한다.
메모리도 자기만의 저장소를 둔다.
Anthropic 제품에서는 Claude Code의 자동 메모리와 Messages API의 메모리 도구가
파일 디렉터리로 구현되어 있다.
상시 가동 에이전트에서는 이 디렉터리를 데이터베이스나 오브젝트 스토어 같은
내구성 저장소에 대응시켜 워커보다 오래 살아남게 한다.

기준은 다시 조회할 수 없는 것만 담는 것이다.
이슈 트래커처럼 다른 시스템에 이미 있는 것은 포인터만 저장한다.
글이 나누는 메모리 종류는 넷이다.

- 사용자 지시: 에이전트 동작에 대한 지시. 별도 파일에 두고 매 실행 시작에 읽는다.
- 사용자 노트: 역할, 선호, 받은 교정 같은 사용자에 대해 알게 된 것.
  파일 하나로 시작해 커지면 작은 파일 여러 개로 나누고,
  실행 시작에는 색인만 읽고 필요할 때 개별 파일을 맥락에 불러온다.
- 지난 메시지: 이미 사용자에게 한 말을 기록해 반복을 피한다.
- 작업 진행: 진행 중인 작업마다 한 일과 남은 일을 적은 파일.
  새 실행이 이 파일을 읽고 이전 실행이 멈춘 곳에서 이어간다.

실행 중에 저장하는 것 외에 드리밍(dreaming)을 더할 수도 있다.
드리밍은 지난 세션을 검토해 메모리를 다듬는 일로, 낡은 항목을 바꾸고
여러 실행에 걸쳐서만 보이는 패턴을 찾는다.

맥락 창의 관점에서는 시스템 프롬프트, 도구 정의, 메모리 파일이
모든 실행에 포함되는 고정 비용이다.
글은 이를 짧게 유지하고 프롬프트 캐싱(prompt caching)으로 비용을 줄이라고 한다.
세션이 너무 길어지면 오래된 메시지를 압축하거나 새 세션을 시작한다.
두 방법 모두 세부 내용을 잃으므로 남겨야 할 것은 진행하면서 메모리에 저장해야 한다.

### 권한(permissions)

글은 권한을 상시 가동 에이전트의 위험이 가장 큰 곳으로 본다.
실행이 사용자의 접근 권한을 쥔 채 정의상 감독 없이 돌기 때문이다.
도구 호출마다 에이전트는 스스로 진행할지, 막을지, 승인을 기다릴지 정해야 한다.
구성 요소는 다른 에이전트와 같다.

- 자격 증명 저장소: 에이전트 환경 밖의 프록시가 나가는 요청에 자격 증명을 붙인다.
  에이전트는 자격 증명 없이 요청을 보내고 프록시가 실제 값을 주입해 전달한다.
- 자동 모드(auto mode): 분류기가 위험이 높은 행동을 검토해 위험하다고 본 것을 막는다.
  가장 중요한 결정에는 여전히 사용자 검토가 필요하다.
- 보류된 도구 호출(deferred tool call): 훅이 도구 호출을 보류하고 사용자 입력을 기다린다.
  보류되면 실행이 끝나고 세션은 호출 도중에 저장된다.
  요청은 사용자에게 보이고, 답은 인박스의 이벤트로 돌아와 새 실행이 세션을 재개한다.
  기다리는 동안 워커는 다른 이벤트를 처리하므로 에이전트가 막히지 않는다.

### 아웃박스(outbox)

일반 에이전트는 응답이 생성되는 대로 사용자에게 스트리밍한다.
상시 가동 에이전트는 대부분 백그라운드에서 일하므로
사용자는 단계별 과정이 아니라 결과와 몇 가지 세부 사항만 받는다.
실행은 세 가지 방식으로 끝난다.
메시지를 아웃박스로 보내거나, 보낼 것이 없다고 판단하거나,
보류된 도구 호출로 권한이나 추가 입력을 요청한다.

대부분은 사용자에게 바로 전달하는 send 도구로 충분하다.
메시지 속도를 조절하거나 오류에서 복구하고 싶을 때만 공식 아웃박스가 필요하다.
아웃박스는 인박스와 대응하는 별도 테이블이고, 디스패처(dispatcher)가
대기 중인 메시지를 읽어 무엇을 전달할지 정한다.
메시지 양은 조절해야 한다.
너무 많이 보내면 시끄럽고 너무 적게 보내면 사용자가 알아야 할 것을 놓친다.
글은 평가(eval)를 만들어 균형을 찾으라고 하며,
조용하게 시작해 사용자의 주의를 점차 얻는 편이 낫다고 한다.

## 전체가 맞물리는 방식

모든 실행은 인박스의 이벤트로 시작한다.
사용자 메시지, 웹훅, 타이머 중 무엇이든 마찬가지이다.
워커가 이벤트를 집으면 새 세션이나 기존 세션에서 에이전트를 깨운다.
에이전트는 메모리를 읽어 기준선을 잡고, 권한 안에서 행동하고,
배운 것을 메모리에 갱신한다.
실행이 끝나면 아웃박스에 행을 쓰고 디스패처가 사용자에게 전달한다.
실행이 타이머를 설정해 나중에 에이전트를 다시 깨울 수 있고,
사용자의 답장은 이벤트로 인박스에 돌아온다.
각 실행은 짧지만 순환이 이어지기 때문에 항상 켜져 있는 것처럼 느껴진다.

## 비평

### 안내서의 범위

글은 구성 요소의 설계를 설명하지만 이 설계가 실제로 운영되는 사례의 수치는 싣지 않는다.
비용 수치 하나가 모델 비교로 나올 뿐이고, 인박스를 사용자마다 하나로 시작하라는
권고나 조용하게 시작하라는 권고의 근거는 제시되지 않는다.
이 문서는 그 권고들을 시험하지 못했다.

### 제품과 겹치는 설명

메모리의 디렉터리 구조, 자동 모드, 보류된 도구 호출은 글이 Anthropic 제품의 기능에서
가져온 패턴이다.
같은 구조가 다른 모델이나 프레임워크에서도 같은 수준으로 성립하는지는 글이 다루지 않는다.

### 빠진 부분

글은 권한을 위험이 가장 큰 곳이라고 하면서도 구체적 실패 사례를 들지 않는다.
프롬프트 인젝션 검사를 실행 중에 한다는 한 문장 외에는
이벤트 출처가 외부일 때의 신뢰 경계를 설명하지 않는다.
인박스에 들어오는 웹훅 내용이 모델 입력이 되므로 이 부분은 독자가 따로 설계해야 한다.

## 기억할 원칙

- 에이전트는 켜져 있지 않고 이벤트가 깨운다. 깨우는 경로는 인박스 하나로 모은다.
- 인박스, 타이머, 메모리, 아웃박스는 각자 내구성 저장소를 가지며 워커보다 오래 산다.
- 메모리에는 다시 조회할 수 없는 것만 두고, 나머지는 포인터로 남긴다.
- 보낼 메시지의 양은 평가로 조절하고 조용하게 시작한다.
