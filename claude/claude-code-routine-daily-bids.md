# Claude Code 루틴으로 입찰공고를 매일 모으려면 절차는 저장소 문서에 두고 키는 전용 환경에 분리한다

원문: [Claude Code로 매일 입찰공고 자동 수집하기: 루틴 설정과 실행 방법 - Modern IT Insights](https://axonn.wikidocs.net/blog/33528)

GN 토론: <https://news.hada.io/topic?id=36633>

## 소개

WikiDocs의 블로그 Modern IT Insights가 2026년 10월 15일에 올린 글이다.
Claude Code의 루틴(Routine) 기능으로 공공데이터포털의 조달청 나라장터 입찰공고를
매일 가져와 요약 노트로 저장하게 만드는 방법을 단계별로 설명한다.
출근해서 노트 한 장만 읽으면 밤사이 올라온 공고가 정리되어 있게 하는
것이 목표다.

글은 루틴을 할 일(프롬프트), 작업할 GitHub 저장소, 연결할 외부 서비스를
한 묶음으로 저장한 설정이라고 설명한다.
조건이 맞으면 Anthropic의 클라우드가 Claude Code를 새로 띄워 그 일을
처음부터 끝까지
맡기므로 내 PC가 꺼져 있어도 돈다고 한다.
실제로 할 일은 저장소의 `CLAUDE.md`에 적고, 루틴의 프롬프트는 그 문서를 따르라는
한 줄로 두는 것이 글의 핵심 요령이다.

이 문서는 글을 읽은 뒤 글이 참고 자료로 든 공식 문서와 대조해 썼다.
대조한 공식 문서는 「Automate work with scheduled tasks」와 「Use Claude
Code in the
cloud」이다.[^docs-sched][^docs-web]
공식 문서는 이 기능을 이제 예약 작업(scheduled tasks)이라 부르며
이전 이름이 루틴이라고 밝힌다.[^docs-sched]
이 문서는 루틴을 직접 만들어 실행해 보지는 못했다.

## 동작 방식

### 루틴은 세 가지 조건에서 시작된다

| 트리거        | 언제 실행되는가                                   |
| ------------- | ------------------------------------------------- |
| 일정          | 매시간, 매일, 평일, 매주 또는 지정한 시각에 한 번 |
| API           | 외부 프로그램이 루틴 전용 주소로 요청을 보낼 때   |
| GitHub 이벤트 | 저장소에 PR이 열리거나 릴리스가 나올 때           |

글은 루틴이 Pro, Max, Team, Enterprise 요금제에서 쓸 수 있고
2026년 10월 현재 리서치 프리뷰라고 쓴다.
공식 문서는 같은 요금제에 Ultra를 더해 적고 리서치 프리뷰라는 점도
확인한다.[^docs-sched]
공식 문서에 따르면 한 작업에 트리거를 여러 개 붙일 수 있고,
API 트리거는 작업 전용 주소로 보내는 HTTP POST와 베어러 토큰으로
시작한다.[^docs-sched]

### 실행 중에는 사람에게 묻지 않고 스스로 판단한다

글은 루틴이 작업 중간에 대화 형태로 질문할 수 없어서 스스로 짐작해
일한다고 쓴다.
그래서 애매한 부분을 미리 문서로 정해 두는 것이 가장 중요하다는 것이 글의
결론이다.
공식 문서도 예약 작업이 완전한 Claude Code 클라우드 세션으로 자율 실행되며
만들 때 권한 모드를 고르지 않는다고 설명한다.[^docs-sched]
다만 공식 문서는 실행이 자동 모드(auto mode)에서 시작하고,
거부 규칙에 걸리거나 차단이 반복되면 실행이 멈춰 답을 기다릴 수 있다고
덧붙인다.[^docs-sched]
이 차이는 아래 함정에서 다시 다룬다.

## 구현하기

글은 준비, 절차 문서, 루틴 등록, 시험 실행의 네 단계로 나눈다.

### 1단계: 준비

- 인증키를 받는다. 공공데이터포털에 가입해 「나라장터 입찰공고」 Open API에
  활용 신청을 하면 승인 뒤 마이페이지에서 키를 볼 수 있다.
- 요약 노트를 기록할 GitHub 저장소를 만든다. 비공개여도 된다.
- 터미널에서 `claude`를 실행해 `/web-setup`을 입력하면 GitHub 계정이 Claude 계정에
  연결된다. 저장소에 Claude GitHub App을 설치하는 방법도 있다.
- `claude.ai/code`에서 전용 클라우드 환경을 만든다. 메시지 입력창 위의 구름
  아이콘으로 새 환경을 추가하고, 네트워크 접근을 Custom으로 바꿔 허용 도메인에
  `apis.data.go.kr`을 넣는다. 「Also include default list of common package
  managers」도 함께 체크한다. 환경 변수에는
`DATA_GO_KR_API_KEY=<인증키>`를 넣는다.

글은 기본 환경을 쓰지 않고 전용 환경을 만드는 이유를 이렇게 설명한다.
환경 변수는 그 환경을 쓰는 모든 세션에서 보이므로,
기본 환경에 인증키를 넣으면 다른 작업에도 키가 노출된다는 것이다.

### 2단계: 절차 문서 쓰기

저장소 최상위에 `CLAUDE.md`를 만들고 할 일을 구체적으로 적어 커밋한다.
아래는 글의 예시 절차를 바탕으로 이 문서가 몇 가지를 고친 것이다.
날짜 기준을 한국 시간으로 명시하고, 실패하면 한 번 다시 시도하고,
키를 출력하지 않고, 노트 외의 파일은 고치지 않는다는 항목은 글에 없고 이
문서가 더했다.

```markdown
## 입찰공고 정리 절차

1. 날짜 기준은 한국 시간(KST)이다. 어제 0시부터 24시 사이에 올라온
   입찰공고를 공공데이터포털 API로 조회한다.
   인증키는 환경 변수 `DATA_GO_KR_API_KEY`로 읽고, 노트와 로그에 출력하지 않는다.
2. 공고명에 "AI", "클라우드", "보안"이 들어간 공고만 남긴다.
3. 공고명, 발주기관, 예산, 마감일을 표로 정리해 `notes/YYYY-MM-DD.md`에 저장한다.
4. API 호출이 실패하면 한 번 다시 시도한다.
   그래도 실패하면 노트 맨 위에 실패 사실과 오류 메시지를 적는다.
5. `notes/` 아래의 새 노트만 커밋하고 `main` 브랜치에 push한다.
   이 파일을 포함해 다른 파일은 고치지 않는다.
```

글은 이렇게 해 두면 검색 키워드를 바꿀 때 루틴 설정은 그대로 두고 이 파일만
고치면 된다고 말한다.

### 3단계: 루틴 등록

`claude.ai/code/routines`에서 New routine을 눌러 차례로 채운다.

| 항목     | 입력                                                             |
| -------- | ---------------------------------------------------------------- |
| 이름     | 「입찰공고 매일 요약 정리」처럼 알아보기 쉬운 이름               |
| 프롬프트 | 저장소의 `CLAUDE.md`를 읽고 절차를 처음부터 끝까지 따르라는 지시 |
| 모델     | 입력창 옆의 모델 선택에서 고른다                                 |
| 저장소   | 1단계에서 만든 저장소                                            |
| 환경     | 1단계에서 만든 전용 환경                                         |
| 트리거   | Schedule, 평일, 오전 8시 7분                                     |
| 커넥터   | 이 루틴은 외부 서비스를 쓰지 않으므로 모두 해제                  |

프롬프트의 지시문은 두 줄이다.
`CLAUDE.md`의 「입찰공고 정리 절차」를 따르라는 것과,
결과는 `main`에 push하고 pull request는 만들지 않는다는 것이다.
터미널에서는 `/schedule`을 입력하고 「평일 오전 8시 7분에 입찰공고 매일 요약
정리」처럼
말로 설명해도 되며, 이때는 claude.ai 구독 계정으로 로그인되어 있어야 한다.

### 4단계: 시험 실행과 확인

1. 루틴 상세 화면에서 Run now를 눌러 한 번 실행한다.
2. 실행 목록에 생긴 항목을 열어 Claude가 한 일을 처음부터 끝까지 본다.
3. 저장소에 `notes/` 폴더와 오늘 날짜의 노트가 생겼는지 확인한다.
4. 결과가 마음에 들지 않으면 루틴 설정이 아니라 `CLAUDE.md`를 고치고 다시
실행한다.

## 값 정하기

| 값            | 글의 선택                | 근거와 확인                                                                                                                  |
| ------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 실행 시각     | 평일 오전 8시 7분        | 정각에 맞춘 일정은 몇 분 늦게 시작할 수 있다. 공식 문서도 같은 이유로 정각을 피하라고 한다.[^docs-sched]                     |
| 실행 간격     | 하루에 한 번             | 글은 최소 1시간이라고 한다. 공식 문서는 1시간보다 잦은 cron 표현이 거부된다고 확인한다.[^docs-sched]                         |
| 시간대        | 로컬 시간으로 입력       | 공식 문서에 따르면 프리셋은 로컬 시간이고, 5개 필드뿐인 cron 표현은 UTC로 읽는다.[^docs-sched]                               |
| 푸시할 브랜치 | `main`, PR 없음          | 기본은 `claude/` 접두사 브랜치다. 다른 브랜치로 보내려면 프롬프트에 적어야 한다.[^docs-sched]                                |
| 커넥터        | 모두 해제                | 필요 없는 서비스에 접근을 열어 두지 않는다.                                                                                  |
| 네트워크      | `apis.data.go.kr`만 추가 | 기본 허용 목록 밖의 호스트는 403으로 막힌다는 것이 공식 문서의 설명이고, 글은 이 도메인을 직접 추가하라고 한다.[^docs-sched] |

## 트레이드오프

### 절차를 문서에 두면 이력이 남지만 루틴이 읽는 문서가 곧 지시문이다

절차를 프롬프트가 아니라 저장소 문서에 두면 언제 무엇을 바꿨는지 git에
기록이 남고,
키워드를 바꿀 때 루틴 설정을 건드리지 않아도 된다.
대신 루틴이 읽는 지시문이 저장소의 일반 파일이 된다.
루틴이 같은 저장소의 `main`에 push할 수 있다면 `CLAUDE.md`도 고칠 수 있다.
위 예시에서 이 파일을 고치지 말라는 항목을 넣은 이유가 이것이다.
이 위험은 이 문서의 추론이며 글은 다루지 않는다.

### 전용 환경은 노출 범위를 줄이지만 키가 환경 변수라는 점은 남는다

전용 환경을 만들면 다른 작업이 같은 키를 보는 일은 막을 수 있다.
그러나 공식 문서는 환경 변수가 환경을 쓰는 누구에게나 보이므로
Anthropic이 호스팅하는 환경에서는 API 키를 네트워크 시크릿(network secret)으로
저장하라고 권한다.[^docs-sched]
네트워크 시크릿은 키가 샌드박스 밖에 있고 조건에 맞는 요청이 세션을 떠난 뒤에
키가 붙는 방식이라고 공식 문서는 설명한다.[^docs-web]
글의 환경 변수 방식은 동작하지만 공식 문서의 권고와 다르다.
네트워크 시크릿을 만드는 구체적 절차는 이 문서가 확인하지 못했다.

## 함정

### 환경 변수에 넣은 키는 환경을 쓰는 모든 세션이 본다

글이 기본 환경에 키를 넣지 말라고 한 이유가 이것이고,
공식 문서도 같은 사실을 적는다.[^docs-sched]
전용 환경을 만들어도 그 환경을 쓰는 다른 루틴이나 세션에는 키가 보인다.
키를 쓰는 작업만 그 환경을 쓰게 하거나 네트워크 시크릿으로 옮겨야 한다.

### 정각에 일정을 잡으면 늦게 시작한다

정각에 맞춘 일정이 몰려 몇 분 늦게 시작할 수 있다는 것이 글과 공식 문서의 공통된
설명이다.[^docs-sched]
아침 8시에 노트를 읽는다면 8시 7분처럼 약간 늦춰 잡고,
읽는 시각은 그보다 충분히 뒤로 둔다.

### 서버의 시계와 cron 표현의 시간대가 로컬 시간이 아닐 수 있다

글은 클라우드 서버의 시계가 로컬 타임존이 아닐 수 있으므로
어제 공고가 언제부터 언제까지인지 문서에 명시하라고 말한다.
공식 문서에 따르면 cron 표현은 시간대 접두사가 없으면 UTC로 읽는다.[^docs-sched]
프리셋 대신 cron 표현을 쓸 때는 이 차이를 잊기 쉽다.

### 실행 목록의 녹색 표시는 성공을 뜻하지 않는다

글은 녹색이 세션에서 동작이 오류 없이 끝났다는 뜻일 뿐이라고 경고한다.
실제로 무엇을 했는지는 실행 기록이나 결과 노트에서 확인해야 한다.
공식 문서의 설명대로 실행이 권한 질문에서 멈춰 답을 기다릴 수 있다면,
녹색도 완료도 아닌 상태가 생길 수 있다는 점도 확인 대상이다.[^docs-sched]

### GitHub 연결이 끊기면 실행이 건너뛰어지다가 꺼진다

공식 문서에 따르면 GitHub 연결이 없거나 만료되면 예약 작업은 최대 72시간
동안 실행을
건너뛰다가, 72시간이 지나면 꺼지고 다시 연결한 뒤 직접 켜야 한다.[^docs-sched]
글은 이 점을 언급하지 않는다.
매일 도는 작업이라면 노트가 며칠째 없을 때 이 연결부터 확인한다.

### 이름이 두 가지로 보인다

글은 루틴이라고 쓰고 공식 문서는 예약 작업이라고 쓴다.
공식 문서는 웹 주소(`claude.ai/code/routines`)와 명령 별칭(`/routines`)에
이전 이름이 남아 있다고 밝힌다.[^docs-sched]
자료를 찾을 때는 두 이름을 모두 검색해야 한다.

## 비평

### 인증키 보관은 공식 권고보다 한 단계 약하다

글은 인증키를 환경 변수에 넣고 전용 환경으로 노출을 줄이라고 안내한다.
공식 문서의 권고는 네트워크 시크릿이다.[^docs-sched]
글의 안내가 틀렸다고 하기는 어렵다.
환경 변수가 그 환경 안에서만 보인다는 설명 자체는 맞기 때문이다.
그러나 글은 더 강한 방법이 있다는 점을 말하지 않고,
이 방법은 키가 샌드박스 안의 세션에서 읽힌다는 점을 남긴다.
공공데이터포털 키처럼 노출 피해가 작은 키에는 충분할 수 있지만,
같은 방식을 결제나 쓰기 권한이 있는 키에 쓰면 위험이 커진다.

### 실행 중에 허락을 구하지 않는다는 서술은 단순화다

글은 루틴이 실행 중에 허락을 구하지 않는다고 쓴다.
공식 문서에 따르면 실행은 자동 모드로 시작하고,
거부 규칙에 걸리거나 차단이 반복되면 실행이 멈춰 답을 기다린다.[^docs-sched]
이 차이는 이 튜토리얼에서 실제로 문제가 되기 어렵다.
입찰공고 조회와 노트 저장은 위험이 낮은 작업이기 때문이다.
그래도 같은 방법을 파일 삭제나 외부 전송이 있는 작업에 쓰면
실행이 조용히 멈출 수 있다.

### 필터와 날짜 기준이 단순해서 누락을 점검할 수단이 없다

예시의 필터는 공고명에 AI, 클라우드, 보안이 들어간 공고만 남기는 것이다.
공고명에 이 단어가 없는 관련 공고는 빠지고,
이 단어가 있어도 관련 없는 공고가 들어올 수 있다.
글은 필터의 누락이나 오탐을 점검하는 방법을 제시하지 않는다.
API가 하루치를 한 번에 주는지, 페이지를 나눠 주는지도 글에서 다루지 않는다.
노트가 정확한지 확인하려면 일정 기간 사람이 직접 검색한 결과와 비교해 봐야 한다.

### 비용과 한도에 대한 설명이 없다

공식 문서는 예약 작업이 대화형 세션과 같은 방식으로 구독 사용량을 쓰고,
트리거 종류별로 시간당 한도가 있다고 밝힌다.[^docs-sched]
글에는 매일 도는 작업이 사용량을 얼마나 쓰는지,
한도에 걸리면 어떻게 되는지가 없다.
평일에 하루 한 번 도는 작업이라 한도에 걸릴 가능성은 낮지만,
같은 계정에 루틴이 여러 개 쌓이면 사용량이 늘어난다.

## 확인하기

시험 실행 뒤에 확인할 것은 노트가 생겼는지가 아니라 노트의 내용이 맞는지다.

1. Run now로 만든 실행 기록을 열어 Claude가 어떤 API를 어떤 날짜 범위로
불렀는지 본다.
2. 같은 날짜 범위를 공공데이터포털에서 직접 조회해 공고 수를 비교한다.
3. 노트에 키 값이 출력되지 않았는지 본다.
4. `CLAUDE.md`와 다른 파일이 바뀌지 않았는지 커밋 기록에서 본다.
5. 일부러 잘못된 키를 넣어 실행하고 노트 맨 위에 실패 사실이 적히는지 본다.
6. 며칠 뒤 실행 목록에서 모든 날짜의 노트가 있는지, 빠진 날이 없는지 본다.

## 체크리스트

- 인증키를 이 루틴만 쓰는 전용 환경에 두었고, 네트워크 시크릿으로 옮길 수 있는지 확인했다.
- 허용 도메인에 데이터 API 도메인만 추가했다.
- 필요 없는 커넥터를 모두 해제했다.
- 절차 문서에 날짜 기준과 시간대, 실패 처리, 쓸 파일의 범위를 적었다.
- 실행 시각을 정각에서 몇 분 늦춰 잡았다.
- 푸시할 브랜치를 프롬프트에 적었고, 필요하면 브랜치 보호 규칙을 걸었다.
- GitHub 연결이 만료되지 않았는지 정기적으로 확인한다.
- 노트가 빠진 날이 없는지 확인하는 방법을 정했다.

## 기억할 원칙

### 사람이 대신 판단하지 못하는 일은 문서로 먼저 정해 둔다

루틴은 실행 중에 사람에게 물을 수 없으므로 애매한 부분을 스스로 짐작한다.
날짜 기준, 실패했을 때의 처리, 쓸 수 있는 파일의 범위처럼
사람이 옆에 있었다면 물어봤을 것들을 문서에 먼저 적는다.
글의 모든 요령이 이 원칙에서 나오고, 이 문서가 더한 항목도 같은 이유에서
더한 것이다.

### 루틴의 권한은 필요한 일에만 열고 키는 더 좁게 둔다

네트워크는 필요한 도메인만, 커넥터는 쓰는 것만, 푸시는 정한 브랜치에만 연다.
키는 환경 변수에서 시작해 네트워크 시크릿으로 옮기는 쪽으로 좁힌다.
자동으로 도는 작업일수록 한 번의 실수가 누구의 눈에도 띄지 않고 반복되므로,
처음에 열어 둔 범위가 곧 사고의 최대 크기가 된다.
