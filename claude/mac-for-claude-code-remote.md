# 여분의 Mac을 Claude Code 전용 실행 호스트로 구성하기

원문: <https://ykdojo.github.io/claude-controls-mac/>

HN 토론: <https://news.ycombinator.com/item?id=48959392> (251점, 150개 댓글)

## 요약

여분의 Mac을 Claude Code가 컴퓨터 사용까지 포함해 완전히 제어하는 항상 켜진 기기로 만드는 16단계 가이드다.
휴대폰에서 Claude 앱으로, 또는 메인 Mac에서 SSH로 그 기기에 말을 걸 수 있게 된다.
저자는 자기 기기에서 돌리고 싶지 않은 종류의 조사 작업과 개발 작업을 위임할 별도 환경을 원했다고 밝힌다.

`--dangerously-skip-permissions` 플래그를 켠 Claude Code는 메인 기기에서 돌릴 때 본질적 위험을 안는데,
필요한 접근 권한을 모두 갖춘 별도 환경을 여분의 Mac에 만들면 그 위험을 없애거나 줄일 수 있다는 것이 출발점이다.
덤으로 언제 어디서나 휴대폰에서 Claude Code에 말을 걸 수 있게 되며,
저자는 모바일 앱의 일반 Claude보다 Claude Code가 대체로 더 유능해서 개인적으로 유용했다고 적는다.

### 컨테이너와 OpenClaw를 쓰지 않은 이유

저자는 자신이 컨테이너 실행의 열렬한 지지자이고 그것을 편하게 하는 환경까지 만들었다고 밝히면서도 두 가지 한계를 든다.
첫째, 컨테이너는 여전히 메인 기기에서 돌기 때문에 완전히 분리되지 않는다 — 예를 들어 컨테이너가 보내는 네트워크 요청은 여전히 메인 기기를 통과한다.
둘째, 컨테이너의 역량에 제한이 있다 — 게임 개발을 위해 에이전트가 Unity를 돌리게 하고 싶었는데 컨테이너에서는 쉬운 방법이 없고,
Mac에서만 쓸 수 있는 다른 앱들도 마찬가지이며 컴퓨터 사용으로 그 앱들을 클릭하고 드래그하게 하려면 특히 그렇다.

OpenClaw 같은 것을 쓰지 않은 이유로는 Claude Code의 최신 기능 전부에 접근하고 싶고,
Claude 앱에서 제어할 수 있는 것이 편하며, Claude 구독 사용량을 쓸 수 있다는 점을 든다.
결국 넓은 권한으로 에이전트를 돌리는 것은 잃을 것이 없는 기기에서 더 안전하되, 컨테이너 대신 완전한 Mac을 쓰는 이득을 얻는다는 정리다.
접근법은 세 줄로 요약된다 — 메인이 아닌 낡거나 여분인 Mac을 쓸 것,
개인 데이터가 없고 Apple ID를 로그인하지 않은 새 로컬 계정을 만들어 에이전트가 닿을 민감한 것이 없게 할 것,
로컬 네트워크의 메인 Mac에서 SSH로 몰고 휴대폰에서 제어할 것.

### 기본 설정 (1~10단계)

대상 Mac은 먼저 지운다 — 에이전트에게 이 기기의 모든 것에 접근할 권한을 주게 되므로,
지원 기종은 시스템 설정에서 모든 콘텐츠 및 설정 지우기를, 구형 Intel Mac은 복구 모드에서 디스크 유틸리티로 지운 뒤 macOS를 재설치한다.
새 로컬 사용자 계정을 만들고 Apple ID 로그인은 건너뛰기를 권하며, `sudo`가 동작하려면 계정에 관리자 권한이 필요하다.

SSH는 `sudo systemsetup -setremotelogin on`으로 켜는데, 전체 디스크 접근 권한이 필요하다는 오류가 나면
터미널 앱에 그 권한을 먼저 준 뒤 재실행한다.
패스워드 없는 `sudo`는 `/etc/sudoers.d/` 아래 규칙 파일을 만들어 설정한다 —
파일을 쓰고, `chmod 440`으로 읽기 전용으로 만들고(그렇지 않으면 `sudo`가 무시한다),
`sudo visudo -cf`로 문법을 검증한다.
sudoers 파일의 오타는 `sudo` 자체를 못 쓰게 만들 수 있으므로 반드시 `parsed OK`가 출력되어야 한다는 경고가 붙는다.

주소는 IP보다 호스트명을 권한다 — IP는 바뀌지만 호스트명은 그대로이기 때문이다.
`scutil --get LocalHostName`으로 확인하고 `.local`을 붙여 쓰며,
네트워크 안에서 `.local` 이름이 유일해야 하고 두 기기가 같은 이름이면 주소가 엉뚱한 Mac을 가리킬 수 있으므로 필요하면 `sudo scutil --set LocalHostName`으로 바꾼다.
패스워드 없는 SSH는 `ssh-keygen -t ed25519`와 `ssh-copy-id`로 설정한다.

항상 켜두기 위해 세 가지 전원 설정을 건다 — 충전 중 시스템 절전 안 함, 덮개를 닫아도 절전 안 함, 디스플레이도 계속 켜기다.
화면 보호기가 켜지면 화면이 잠길 수 있으므로 `defaults -currentHost write com.apple.screensaver idleTime 0`으로 아예 시작하지 않게 한다.

클립보드 동기화는 macOS 기본 도구인 `pbcopy`와 `pbpaste`를 SSH로 파이프해 만든다 —
암호화된 P2P 방식이며 Apple ID도 서드파티 서비스도 필요 없다.
`clip.sh`가 이를 하나의 명령으로 감싸고 텍스트만 되는 원래 도구에 이미지 지원을 더하며, `IC_BOX` 환경 변수로 대상 호스트를 가리킨다.
`clip send`는 내 클립보드를 대상으로, `clip get`은 반대로 보낸다.

Claude Code 설치는 SSH로 설치 스크립트를 실행하고, `~/.local/bin`이 PATH에 없다는 경고가 나오면
`~/.zshrc`가 아니라 `~/.zshenv`에 추가한다 — 비대화형을 포함한 모든 zsh가 읽는 파일이기 때문이다.
선택 단계로 셸 별칭, DX 플러그인, `settings.json` 조정, GitHub CLI, 그리고 옵트인인 Playwright MCP와 `yt-dlp`를 적용하는 스크립트가 제공되며 재실행해도 안전하다.
Claude와 GitHub 로그인은 대화형이라 SSH로 접속해서 한다.
저자는 GitHub에 대해 메인 계정이 아닌 별도 계정을 쓰기를 강력히 권한다.

### SSH를 통한 컴퓨터 사용 (11단계)

이 단계는 대상 기기의 대화형 `claude` 세션이 자기 데스크톱을 보고(스크린샷) 제어(마우스·키보드)하게 하되 그것을 SSH로 몬다.
그냥은 안 되는데, SSH와 macOS의 권한 모델이 가로막기 때문이다.

우회가 필요한 이유가 명시되어 있다 — macOS는 화면 캡처와 입력을 GUI 로그인 세션에 묶인 화면 기록·손쉬운 사용 권한 뒤에 두므로 SSH 프로세스는 디스플레이에 닿을 수 없다.
해법은 LaunchAgent가 GUI 세션 안에서 고정 소켓 위의 tmux 서버를 계속 살려 두는 것이다.
거기서 만들어지는 모든 `claude` 세션은 그 서버에 붙어 GUI 세션을 물려받으므로 디스플레이에 닿을 수 있고, 사용자는 SSH로 접속(attach)한다.
설치 스크립트가 LaunchAgent(앵커 세션 `cc`를 가진 지속 tmux 서버)를 설치하고 `~/.claude.json`에서 내장 컴퓨터 사용 도구를 켜며, tmux와 Claude Pro 또는 Max 플랜이 필요하다.

메인 Mac에는 `ic.sh`(ic는 isolated claude)를 설치한다.
각 `ic` 실행은 대상 기기에 자기만의 `claude` 세션을 만들고 접속하며 여러 개를 동시에 돌릴 수 있다.
플래그는 `claude`를 그대로 따르고 하위 명령이 추가된다 —
`ic sh`는 claude 없이 셸만, `ic vnc`는 화면 공유, `ic rc`는 휴대폰에서 몰기,
`ic history`는 저장된 대화, `ic ls`는 살아 있는 세션 목록, `ic attach`/`ic kill`/`ic kill-all`/`ic kill-except`가 있다.
모든 `ic` 세션은 `--dangerously-skip-permissions`로 돌고 `ic rc`는 `--permission-mode bypassPermissions`를 쓴다.

텍스트를 밖으로 복사하는 데는 제약이 있다 — 세션이 tmux에서 돌고 Terminal.app이 `claude`가 내보내는 OSC52 클립보드 이스케이프 시퀀스를 받지 못하므로
마우스로 선택해도 Mac 클립보드에 확실히 들어가지 않으며, 빠른 우회는 `Cmd-A` 후 `Cmd-C`로 보이는 화면 전체를 복사하는 것이다.

모든 `ic` 세션이 고정 소켓의 tmux 서버에 살기 때문에 메인 Mac의 Claude Code 세션이 SSH로 그중 하나에 직접 프롬프트를 넣을 수 있다 — 에이전트가 에이전트에게 일을 위임하고 확인하는 것이다.
`tmux send-keys`로 프롬프트를 입력한 뒤 두 번째 Enter로 확정해야 하는데,
긴 프롬프트에서는 텍스트와 같은 버스트로 보낸 Enter가 제출로 인식되지 않아 입력창에 남기 때문이라는 설명이 붙는다.
답을 읽을 때는 `capture-pane`을 스피너가 사라질 때까지 반복 호출한다.

한 번은 사람이 직접 해야 하는 것이 있다.
화면 기록과 손쉬운 사용 권한은 GUI에서만 부여할 수 있고 사람이 기기 앞에서(또는 화면 공유로) 해야 하는데, macOS가 이 프롬프트에 대한 합성 클릭을 막기 때문이다.
그리고 이 권한은 `claude`가 아니라 **tmux에 부여**해야 한다 —
macOS가 캡처와 제어를 사슬에서 책임 있는 프로세스에 귀속시키는데 여기서는 tmux 서버가 그것이고 `claude`는 그 자식으로 돌기 때문이다.
화면 기록은 스크린샷을, 손쉬운 사용은 마우스·키보드 제어를 담당하며, 실행 중인 프로세스는 시작 시점의 권한 상태를 캐시하므로 부여 후 tmux 서버를 재시작해야 반영된다.
tmux에 전체 디스크 접근을 주면 최신 macOS에서 앱마다 뜨는 다른 앱의 데이터에 접근하려 한다는 프롬프트가 사라진다.

### 나머지 기능 (12~16단계)

VPN 설치는 대상 기기의 Claude에게 시키면 되지만 세 가지는 사람이 해야 한다 —
무료 등급이라도 필요한 로그인 자격 증명 입력(`clip send`로 비밀번호를 안전하게 보내 붙여넣는다),
첫 연결 시 뜨는 VPN·네트워크 구성 허용 시스템 프롬프트, 그리고 GUI 전용 앱을 모는 데 필요한 11단계 설정이다.
이 흐름은 VPN뿐 아니라 사실상 다른 어떤 애플리케이션에도 통한다고 밝힌다.

휴대폰 제어는 두 가지다 — 기존 세션 안에서 `/remote-control`(`/rc`)을 실행해 그 세션을 휴대폰에서 몰거나,
`claude remote-control`로 서버를 띄워 휴대폰에서 새 세션까지 시작하는 것이다.

Claude in Chrome은 별도 단계인데, 11단계의 컴퓨터 사용이 브라우저를 **의도적으로 제어하지 않기** 때문이다 —
브라우저는 Claude가 화면을 볼 수는 있지만 클릭하거나 입력할 수는 없는 제한 등급을 받는다.
확장이 그 공백을 채워 이동·클릭·폼 입력·콘솔 로그와 네트워크 요청 읽기를 제공하며,
Playwright MCP와 달리 평소 쓰는 Chrome 프로필을 몰기 때문에 대상 기기에 만들어 둔 로그인 상태를 그대로 쓸 수 있다.
알려진 문제 두 가지가 명시된다 — 메인 Mac의 Chrome에도 같은 계정으로 확장이 있으면 Claude Code가 어느 브라우저에 붙을지 물어보는데 로컬 기기 판별이 틀릴 수 있고(#74667),
휴대폰에서 띄운 세션은 현재 브라우저 도구를 받지 못한다(#74671).

화면 공유는 macOS 12.1부터 명령줄로 켤 수 없어 기기 앞에서 GUI로 켜야 하며, 원격 관리가 켜져 있으면 토글이 숨겨질 수 있다.
Tailscale은 `.local` 이름이 LAN에서만 해석되는 제약을 푼다 —
P2P 종단간 암호화 WireGuard 터널로 기기들을 잇고, 공개 인터넷에 아무것도 노출하지 않으면서 어느 망에서든 SSH·`ic`·`clip`·화면 공유가 동작한다.
네트워크 가입은 도달 가능성만 줄 뿐 SSH와 화면 공유는 여전히 키나 비밀번호를 요구한다는 점을 강조한다.
관리 콘솔에서 두 가지를 권한다 — 탈취된 Tailscale 로그인만으로 기기를 추가하지 못하게 하는 기기 승인,
그리고 약 180일 뒤 키 만료로 대상 기기가 네트워크에서 빠지지 않도록 키 만료 비활성화다.

## 분석

### 에이전트 인프라로서의 개인 하드웨어

이 가이드가 등장한 배경은 Claude Code에 `--dangerously-skip-permissions` 플래그를 붙여
장시간 에이전트 작업을 돌리는 수요가 커졌다는 것이다.
이 플래그는 파일 시스템 접근, 명령 실행, 브라우저 제어를 포함한 넓은 권한을 에이전트에 준다.
메인 개발 기기에서 이것을 허용하는 것은 프로덕션 서버에 루트 접근을 주는 것과 비슷한 위험이다.

컨테이너 접근 방식은 이 문제의 절반만 해결한다.
컨테이너가 메인 기기에서 돌아가면 컨테이너 탈출 취약점이나 호스트 파일시스템 마운트를 통해
결국 같은 위험이 남는다.
물리적 분리는 공격 표면 자체를 기기 단위로 제한한다는 점에서 근본적으로 다른 접근이다.

주목할 것은 저자가 컨테이너를 반대하는 논거가 보안이 아니라는 점이다.
스스로를 컨테이너 실행의 열렬한 지지자라고 밝히고 그 환경까지 만들었다면서,
컨테이너를 떠난 이유로 Unity 같은 Mac 전용 앱을 컴퓨터 사용으로 몰 수 없다는 역량 문제를 든다.
즉 이 설정의 진짜 동기는 격리 강화가 아니라 GUI 자동화이고, 격리는 그 결정에 따라오는 요구사항이다.
네트워크 요청이 메인 기기를 통과한다는 두 번째 이유도 보안이라기보다 트래픽 분리에 가까우며,
12단계에서 VPN을 설치해 대상 기기 트래픽이 자기 IP와 별도로 나가게 한다는 대목이 그 의도를 확인해 준다.

### 원격 에이전트 인프라의 실제 필요

장시간 백그라운드 에이전트 작업은 로컬 개발 환경과 다른 요구사항을 가진다.
항상 켜져 있어야 하고, 절전 상태가 없어야 하고, 모바일에서 접근 가능해야 한다.
이 요구사항은 개인 노트북보다 서버에 가깝다.

Tailscale을 통한 외부 접속 지원은 이 설정이 단순히 집에 두고 쓰는 기기를 넘어
어디서든 접근 가능한 개인 에이전트 서버 역할을 한다는 뜻이다.
흥미로운 점은 클라우드 VM 대신 개인 하드웨어를 쓴다는 선택이다.
비용 없이 항상 켜진 에이전트 호스트를 운영할 수 있는 방법이다.

TekMol은 왜 굳이 맥이어야 하는가, 클라우드 VM에 CLI 인터페이스면 충분하지 않은가라는 직접적인 의문을 제기했다.[^TekMol]
smetannik도 같은 맥락에서 왜 여분의 기기가 Mac이어야 하는가, iMessage 때문인가라고 물었다.[^smetannik]
이 질문들이 핵심을 찌른다.
Claude in Chrome을 통한 브라우저 자동화, macOS 전용 앱과의 통합, GUI 기반 작업은
CLI만으로 처리할 수 없는 영역이다.
Mac이어야 하는 이유는 macOS 에코시스템 내의 GUI 자동화 수요에서 온다.

Havoc은 반대 방향에서 같은 것을 짚는다 — 대부분의 시간을 유휴로 보내거나 가벼운 HTTP 요청을 처리하는 용도에 Mac을 쓰는 것이 이상하다는 것이다.
사실상 영광스러운 API 게이트웨이이고 어지간한 감자에서도 돌 텐데,
한 세대가 MacBook을 코더의 당연한 선택으로 여기며 자라서 그 담장 밖의 하드웨어를 상상하지 못하는 것 같다는 지적이다.[^Havoc]
이 비판이 정확한 지점과 빗나가는 지점이 함께 있다 — GUI 자동화가 목적이면 macOS가 필요하지만,
가이드에 나오는 작업 상당수(조사, 저장소 작업, 원격 세션)는 실제로 감자에서도 돈다.

### tmux를 권한 경계로 삼는 설계

11단계의 우회 방법은 이 가이드에서 기술적으로 가장 흥미로운 부분이고, macOS 보안 모델의 성질을 그대로 드러낸다.

macOS는 화면 캡처와 입력 합성을 GUI 로그인 세션에 묶고, 권한을 프로세스가 아니라 책임 있는 프로세스에 귀속시킨다.
그래서 SSH로 들어온 프로세스는 디스플레이에 닿을 수 없고, 우회하려면 GUI 세션 안에 살아 있는 무언가에 붙어야 한다.
LaunchAgent가 띄워 둔 tmux 서버가 그 무언가이고, 이후 모든 `claude` 세션이 그 서버의 자식으로 태어나 GUI 세션을 물려받는다.

이 구조에서 권한을 `claude`가 아니라 tmux에 준다는 사실이 결정적이다.
그 순간 tmux 서버가 이 기기의 실질적 권한 경계가 되고, 그 아래에서 도는 모든 것이 화면 기록·손쉬운 사용·전체 디스크 접근을 물려받는다.
가이드는 이를 macOS의 귀속 규칙에 대한 설명으로 담담하게 서술하지만, 보안 관점에서 이것은 권한을 프로세스 하나에서 세션 관리자 전체로 넓힌 것이다.
`ic`로 띄우는 세션이 여러 개든, 나중에 사람이 같은 소켓에 붙어 무엇을 하든 같은 권한을 갖는다.

같은 성질이 편의를 만들기도 한다.
고정 소켓 덕분에 메인 Mac의 Claude가 SSH로 대상 기기의 Claude에게 프롬프트를 넣을 수 있다는 마지막 보너스가 그것이다.
에이전트가 에이전트에게 일을 시키고 `capture-pane`으로 결과를 읽는 이 패턴은 별도의 프로토콜 없이 tmux만으로 구현된 다중 에이전트 오케스트레이션이며,
두 번째 Enter를 따로 보내야 한다는 실무적 주의사항까지 붙어 있다는 점에서 실제로 써 본 사람의 기록이다.

## 비평

### 잃을 것이 없는 기기라는 전제가 가이드 자신의 단계들에 의해 무너진다

이 설정의 보안 논거는 하나다 — 개인 데이터도 Apple ID도 없는 기기라서 에이전트가 닿을 민감한 것이 없다는 것이다.
그런데 가이드를 끝까지 따라가면 그 기기에는 다음이 쌓인다.
Anthropic 계정 로그인(10단계), GitHub 계정 로그인(10단계), VPN 서비스 자격 증명(12단계),
Chrome 확장에 로그인된 Claude 계정과 평소 로그인 상태를 갖춘 Chrome 프로필(14단계), Tailscale 네트워크 멤버십(16단계)이다.

저자도 이 문제를 부분적으로 인식한다 — GitHub는 메인 계정이 아닌 별도 계정을 강력히 권한다.
그런데 같은 논리를 Anthropic 계정이나 Chrome 프로필에는 적용하지 않는다.
오히려 14단계는 평소 쓰는 Chrome 프로필을 몰기 때문에 만들어 둔 로그인 상태를 그대로 쓸 수 있다는 점을 장점으로 내세우는데,
로그인 상태를 쌓아 두라는 권유는 잃을 것이 없는 기기라는 전제와 정면으로 충돌한다.

결국 이 설정이 실제로 달성하는 것은 잃을 것이 없는 상태가 아니라 잃을 것이 적은 상태이며,
그 적음은 시간이 지나며 줄어든다.
에이전트를 유용하게 만드는 모든 조치가 그 기기에 자격 증명을 하나씩 더하기 때문이고,
이 방향성은 가이드가 자기 논거를 갱신하지 않은 채 기능을 늘려간 결과다.
정직한 서술은 이 기기가 위험을 없애는 것이 아니라 폭발 반경을 메인 기기에서 이 기기로 옮긴다는 것이고,
그 반경 안에 무엇이 들어가는지는 사용자가 단계마다 결정해야 한다.

### 보안 격리가 네트워크 층에서 멈춘다

잃을 것이 없는 기기라는 원칙은 좋지만, 에이전트 호스트가 네트워크와 연결되는 순간
그 기기 자체가 공격 지점이 된다.
Tailscale로 외부에서 접근 가능하고, SSH가 열려 있고, 패스워드 없는 sudo가 설정되면
에이전트 호스트에 무단 접근이 이뤄질 경우 그 기기가 네트워크 침투 발판이 된다.

spikk는 파일 격리만으로는 부족하다며 에이전트 호스트를 별도 VLAN으로 분리해야 한다고 제안했다.[^spikk]
nunez도 같은 결론에 도달한다 — 편집증적인 말이지만 Claude가 자기 마음대로 움직일 것을 생각하면
네트워크 탈출에 대비해 그 기기를 자체 VLAN이나 전면 차단 방화벽 규칙 뒤에 두겠다는 것이다.[^nunez]
같은 로컬 네트워크에 있는 기기에 대한 횡적 이동(lateral movement) 위험을 막으려면
네트워크 수준의 격리가 추가돼야 한다는 것이다.

가이드에는 이 층이 전혀 없다.
16단계가 Tailscale의 보안 성질(가입해도 SSH 키는 여전히 필요하다, 기기 승인을 켜라)을 설명하긴 하지만,
그것은 외부에서 이 기기로 들어오는 경로에 대한 것이고 이 기기에서 내 LAN의 다른 기기로 나가는 경로는 다루지 않는다.
에이전트가 임의 명령을 실행하는 기기가 내 NAS와 라우터와 프린터와 같은 서브넷에 있다는 사실이 이 설정의 가장 큰 미논의 위험이다.

패스워드 없는 sudo에 대해서도 반론이 있다.
drnick1은 에이전트에게 sudo 권한을 주는 것이 무모해 보인다며,
자기는 컨테이너나 VM은 쓰지 않지만 Claude에게 권한 없는 UNIX 계정 하나만 준다고 적는다.[^drnick1]
이 지적이 특히 아픈 이유는 가이드가 패스워드 없는 sudo를 왜 필요로 하는지 설명하지 않기 때문이다 —
프롬프트 없이 관리 작업을 하기 위해서라고만 되어 있고, 어떤 작업이 그것을 요구하는지는 나오지 않는다.
sudoers 파일 오타로 잠길 수 있다는 경고를 세심하게 붙이면서 그 권한이 정말 필요한지는 묻지 않는 것이 이 가이드의 성격을 보여준다.

### VM이나 다른 하드웨어로 같은 격리를 더 싸게 달성할 수 있다

esaym은 여분의 Mac 없이도 libvirt 스크립트로 격리된 그래픽 데스크톱 환경을 제공한다고 밝혔다.[^esaym]
망가지면 몇 초 만에 덤프하고 재설치할 수 있다는 복구 편의성도 강점으로 꼽았다.
somewhatrandom9도 UTM으로 Mac에서 macOS VM을 실행하고 그 안에 Claude Code를 설치하는 방법을 제시했다.[^somewhatrandom9]
물리적 기기가 없어도 동등한 격리를 달성할 수 있다는 현실적인 대안이다.

복구 편의성은 특히 중요한 차이다.
VM은 스냅숏에서 되돌릴 수 있지만 물리 Mac은 그럴 수 없고, 이 가이드에는 대상 기기가 오염되었을 때 무엇을 하라는 안내가 없다.
1단계에서 기기를 지우고 시작하라고 했으니 논리적으로는 다시 지우는 것이 답인데,
16단계까지 따라온 설정을 재구축하는 비용은 스냅숏 복원과 비교가 되지 않는다.
잃을 것이 없는 기기라는 설계는 오염을 감수하겠다는 뜻인데, 정작 오염 후 복구 절차가 없다는 점이 설계의 미완성을 드러낸다.

여분의 Mac이 있다는 전제 자체도 검토 대상이다.
arxari가 여분의 Mac을 설정한다는 문구에 마치 다들 하나쯤 있다는 듯이라고 짧게 붙인 것이 그 정서다.[^arxari]
rootsudo는 낡은 M2로 하고 있으며 로컬 모델을 돌리기에는 부족해도 OpenClaw와 Claude에는 완벽했고,
M1/M2 MacBook이 이제 Mac mini보다 싸서 놀랐다고 전한다.[^rootsudo]
guluarte는 훨씬 가벼운 조합을 쓴다 — terminus와 WireGuard와 tmux면 충분하고 운동하면서 휴대폰으로 Claude와 Codex를 몬다는 것이다.[^guluarte]
이 설정들과 비교하면 16단계 가이드의 상당 부분은 GUI 자동화를 위한 것이고, 그것이 필요 없는 사용자에게는 과잉이다.

### 24시간 에이전트의 용례가 가이드 안에 없다

이 가이드는 어떻게에 대해 매우 상세하지만 무엇을 위해에 대해서는 거의 말하지 않는다.
저자가 밝힌 동기는 자기 기기에서 돌리고 싶지 않은 종류의 조사 작업과 개발 작업이라는 두 단어뿐이다.

deadbabe는 이 사람들이 24/7 에이전트를 돌리면서 대체 무엇을 하는 건가, 할 일 목록을 관리하는 건가라고 비꼬았다.[^deadbabe]
catoc은 더 솔직하다 — AI가 정말 24시간 자기를 돕는 좋은 용례를 도무지 떠올릴 수 없으며, 이것이 필요해지고 싶다고 적는다.[^catoc]
이 반응들은 냉소가 아니라 정보 요청이고, 가이드가 답하지 않은 질문이다.

반대편에 구체적 용례가 없는 것은 아니다.
languagehacker는 HomeBridge와 연동해 집 자동화 시스템을 Claude가 제어하게 한다고 밝혔고,[^languagehacker]
schainks는 방향을 뒤집어 Claude가 홈랩에 SSH로 세션을 띄워 Mac이 필요 없는 작업을 처리하게 했다고 전한다.[^schainks]
그런데 이 용례들은 모두 댓글에 있고 가이드에는 없다.
16단계를 다 따라간 뒤 무엇을 하게 되는지가 없으면 이 문서는 설정 매뉴얼이지 설계 문서가 아니며,
독자는 자기에게 필요한 단계가 어디까지인지 판단할 근거를 얻지 못한다.

## 인사이트

### 개인 에이전트 인프라가 등장하고 있다

이 가이드가 HN에서 주목받았다는 사실은 에이전트 작업을 위한 전용 인프라 수요가
실제로 존재한다는 것을 보여준다.
클라우드 AI 서비스로 간단히 해결되지 않는 이유는 컴퓨터 사용이 로컬 기기의 GUI와
직접 상호작용해야 하기 때문이다.
브라우저, 앱, 파일 시스템을 실제로 조작하는 작업은
클라우드 API 호출만으로 처리할 수 없다.

이 인프라 패턴이 확산되면 개인 개발자도 에이전트 전용 기기를 갖추는 것이
표준적인 개발 환경 구성이 될 수 있다.
에이전트 호스트, 메인 개발 기기, 클라우드 API가 협력하는 개인 에이전트 아키텍처다.

여기에 경제적 변수가 하나 붙는다.
weard_beard는 이 글을 읽고 Claude를 배워볼까 하다가 Anthropic 가격 체계를 찾아보고 물러섰다고 적는다 —
클라우드 서비스 관리보다 100배 복잡하고, AI 사용료로 파산하지 않는 법을 알아내는 것 자체가 풀타임 직업이자 별도 기술이라는 것이다.[^weard_beard]
항상 켜진 에이전트 호스트의 비용은 전기가 아니라 토큰이고, 그 비용이 예측 불가능하면 24시간 운영이라는 전제 자체가 흔들린다.
가이드가 Claude Pro 또는 Max 플랜을 요구한다고 명시한 것은 그 비용을 정액으로 고정하는 선택이며,
개인 하드웨어를 쓰는 이유가 클라우드 VM 비용 절감이라면 정작 더 큰 비용은 구독 쪽에 있다.

### macOS의 권한 모델이 에이전트 시대에 맞지 않는다는 것이 이 가이드로 증명된다

11단계 전체가 하나의 우회다.
macOS는 화면 캡처와 입력 합성을 GUI 로그인 세션과 사람의 클릭에 묶어 두었고, 그 설계는 명확한 위협 모델 위에 있다 —
원격에서 몰래 화면을 보거나 키를 누르는 것을 막겠다는 것이다.

문제는 에이전트가 정확히 그 시나리오와 구별되지 않는다는 점이다.
사용자가 원해서 원격에서 화면을 보고 키를 누르는 프로그램과, 공격자가 몰래 그렇게 하는 프로그램을 OS가 구분할 방법이 없다.
그래서 macOS의 답은 사람이 기기 앞에서 직접 허용하게 하는 것이고, 그 결과 이 가이드에는 스크립트로 할 수 없는 일이라는 문장이 반복해서 등장한다 —
권한 부여, 화면 공유 활성화, VPN 네트워크 구성 승인, Chrome 확장 설치가 모두 그렇다.

여기서 드러나는 구조적 긴장은 자동화의 마지막 한 걸음이 언제나 사람에게 남는다는 것이다.
그리고 그 한 걸음이 남는 지점은 대체로 권한 부여다.
tmux에 화면 기록과 손쉬운 사용과 전체 디스크 접근을 준 뒤로는 그 아래 모든 것이 자동화되므로,
실제로 일어나는 일은 자동화의 제거가 아니라 사람의 승인 한 번을 영구적 권한으로 바꾸는 것이다.

이 패턴은 OS 벤더에게 숙제를 남긴다.
지금은 권한 부여가 이진법이고 프로세스 단위이며 시간 제한이 없다 —
tmux에 준 권한은 tmux가 다시 시작될 때까지 유지되고, 그 아래 무엇이 도는지는 묻지 않는다.
에이전트를 상정한 권한 모델이라면 범위(이 앱만), 기간(이번 세션만), 감사(무엇을 캡처했는지)를 함께 다뤄야 하는데
그런 모델은 아직 어느 데스크톱 OS에도 없다.

### 브라우저를 컴퓨터 사용에서 의도적으로 제외한 것이 이 생태계의 신뢰 경계를 보여준다

14단계에 흥미로운 문장이 있다 — 11단계의 컴퓨터 사용은 브라우저를 의도적으로 제어하지 않으며,
브라우저는 Claude가 화면을 볼 수는 있지만 클릭하거나 입력할 수는 없는 제한 등급을 받는다는 것이다.

이 구분은 우연이 아니다.
브라우저는 사용자의 로그인 세션을 모두 담고 있는 곳이고, 은행과 이메일과 사내 시스템이 거기 있다.
그래서 화면 전체를 클릭할 수 있는 권한을 준 뒤에도 브라우저만은 별도 등급으로 다루는 것이며,
브라우저를 제어하려면 별도 확장을 설치하고 별도로 로그인하고 별도 플랜을 요구하는 경로를 거치게 한다.

그런데 이 경계는 결국 사용자가 스스로 허무는 방식으로 설계되어 있다.
확장을 설치하면 브라우저 제어가 열리고, 그때 확장이 모는 것은 평소 쓰는 Chrome 프로필이다 —
가이드가 장점으로 내세운 그 성질이 바로 신뢰 경계를 통과하는 지점이다.
즉 플랫폼은 기본값을 안전하게 두고 우회 경로를 문서화했으며, 사용자는 편의를 위해 그 경로를 밟는다.

같은 구조가 이 문서 전체에 반복된다 — `--dangerously-skip-permissions`, 패스워드 없는 sudo, tmux에 준 전체 디스크 접근, 브라우저 확장이 모두 같은 형태다.
각 안전장치는 이유가 있어 존재하고, 각 우회는 편의를 위해 정당화되며, 우회의 총합이 이 기기의 실제 보안 자세를 정한다.
이 가이드의 가장 큰 기여는 그 총합을 한곳에 모아 보여준다는 점이고,
가장 큰 위험은 열여섯 단계를 순서대로 따라가는 동안 그 총합이 얼마나 커지는지 보이지 않는다는 점이다.

### 에이전트가 에이전트를 모는 패턴이 프로토콜 없이 tmux로 먼저 나타났다

가이드의 보너스 항목 — 메인 Mac의 Claude가 SSH로 대상 기기의 Claude에게 프롬프트를 넣는 것 — 은
분량으로는 짧지만 이 문서에서 가장 앞선 부분이다.

이 패턴이 성립하는 이유는 tmux 세션이 주소 지정 가능하기 때문이다.
고정 소켓과 세션 ID가 있으면 외부에서 그 세션에 입력을 보내고 화면을 읽을 수 있으며, 그것으로 충분하다.
MCP도 A2A도 필요 없고, 에이전트가 서로를 발견하는 표준도 필요 없다 — SSH와 tmux라는 40년 된 도구 조합이 그 일을 한다.

여기서 배울 것은 다중 에이전트 오케스트레이션의 최소 요구사항이 생각보다 낮다는 점이다.
필요한 것은 세 가지뿐이다 — 대상 에이전트를 지목하는 주소, 입력을 넣는 경로, 출력을 읽는 경로.
지금 논의되는 에이전트 간 프로토콜들이 더하는 것은 이 위의 신원과 인가와 발견이고, 그것들이 필요해지는 시점은 신뢰하지 않는 상대와 통신할 때다.
자기 기기 두 대 사이에서는 그 층이 전부 불필요하다.

동시에 이 방식의 조악함이 그 층이 왜 필요한지도 보여준다.
프롬프트를 넣은 뒤 두 번째 Enter를 따로 보내야 하고, 응답이 끝났는지는 스피너가 사라졌는지를 화면에서 눈으로 확인해야 하며,
`capture-pane`의 마지막 30줄을 잘라 읽는다.
구조화된 응답도, 완료 신호도, 오류 전파도 없다 — 터미널 화면을 파싱하는 것은 스크린 스크래핑이고 그 취약함을 그대로 물려받는다.
그래서 이 패턴의 올바른 위치는 프로토타이핑이며, 같은 일을 오래 반복하게 되는 순간 구조화된 인터페이스로 옮겨야 한다는 신호로 읽는 것이 맞다.
