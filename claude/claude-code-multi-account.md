## 한눈에 보기

한 컴퓨터에서 Claude Code를 계정 둘 이상으로 쓰는 방법은 이제 공식
문서에 실려 있다.
계정마다 설정 폴더를 따로 두고, 실행할 때 `CLAUDE_CONFIG_DIR` 환경 변수로 폴더를
고르는 방식이다.[^auth]
폴더마다 설정, 세션 기록, claude.ai 로그인이나 API 키가 따로 쌓인다.[^auth]
개인 계정과 회사 계정을 번갈아 쓰는 사람,
고객사마다 계정이 다른 프리랜서에게 필요한 기능이다.

이 글은 세 겹으로 나뉜다.
첫째는 계정을 가르는 법이다.
공식 방법과 한 블로그의 변형, 앱이 대신 관리해 주는 방법을 견준다.
둘째는 계정이 섞이지 않게 하는 법이다.
환경 변수 자격이 로그인보다 앞서는 규칙과 회사 정책이 걸리는 지점이 여기에 있다.
셋째는 메인 계정의 세션에서 `claude -p`로 다른 계정에 일을 맡기는 법이다.
되기는 하지만 값어치를 내는 일의 범위가 좁고,
약관과 데이터의 문제는 기술이 정하지 않는다.

상황별로 어느 절을 읽으면 되는지는 아래 표와 같다.

| 상황                                          | 쓸 방법                               | 읽을 곳                    |
| --------------------------------------------- | ------------------------------------- | -------------------------- |
| 개인과 회사 계정을 번갈아 쓰고 싶다           | 설정 폴더와 alias                     | 계정을 가르는 법           |
| alias가 안 먹는 스크립트나 도구에서 쓰고 싶다 | `PATH`의 실행 파일 래퍼               | 계정을 가르는 법           |
| 한도 경고와 대화 이어 가기까지 원한다         | 계정 관리 앱(예: Offrun)              | 계정을 가르는 법           |
| 계정이 조용히 섞이는 일을 막고 싶다           | 환경 변수 자격 제거, 로그인 상태 점검 | 계정이 섞이지 않게 하는 법 |
| 큰 읽기 작업을 다른 계정에 맡기고 싶다        | `claude -p` 위임 래퍼                 | 다른 계정에 일을 맡기는 법 |
| 한도를 피하려는 목적이 섞여 있다              | 먼저 약관과 조직 규정을 읽는다        | 약관과 정책                |

확인 범위를 먼저 밝힌다.
`claude auth status`가 빈 설정 폴더에서 어떻게 동작하는지,
alias가 비대화형 셸에서 펼쳐지지 않는 것,
아래 래퍼 스크립트의 환경 변수 처리는 직접 실행해 확인했다.
두 번째 계정으로 실제 모델을 호출하는 부분은 로그인한 두 번째 계정이 없어
실행하지 못했고 공식 문서를 읽고 썼다.
약관은 본문을 읽었지만 법률 자문이 아니다.

## 계정을 가르는 법

### 공식 방법은 설정 폴더 하나에 계정 하나다

공식 문서의 절차는 짧다.
계정마다 설정 폴더를 만들고, `claude`를 시작할 때 `CLAUDE_CONFIG_DIR`을 그
폴더로 지정한다.[^auth]
문서의 예시는 `.bashrc`나 `.zshrc`에 alias를 넣어 `claude-work`는 회사 계정을,
그냥 `claude`는 개인 계정을 쓰게 하는 것이다.[^auth]

```bash
alias claude-work='CLAUDE_CONFIG_DIR=~/.claude-work claude'
```

새 터미널에서 `claude-work`를 처음 실행하면 새 폴더에 대한 로그인과 초기 설정이
시작된다.[^auth]
폴더가 계정을 가르는 방식은 저장 위치에서 갈린다.
macOS에서는 자격 증명이 키체인에 들어가는데 이 항목도 설정 폴더에 묶여 있어서,
`CLAUDE_CONFIG_DIR`이 다른 세션은 다른 항목을 읽는다.[^auth]
Linux와 Windows, 그리고 키체인에 쓰지 못하는 상황의 macOS에서는
`.credentials.json` 파일이 그 설정 폴더 아래에 생긴다.[^auth]

한 가지 예외가 있다.
API 키 없이 Claude Console 계정으로 로그인한 경우는 설정 폴더로 나눌 수
없다.[^auth]
Claude Code가 그 로그인을 설정 폴더 바깥에 저장하기 때문이다.[^auth]
Console 계정을 둘 이상 오가야 한다면 이 방법은 통하지 않는다.

이 변수는 셸이나 사용자 설정에서만 정할 수 있고,
프로젝트 설정과 로컬 설정은 무시한다.[^env]
이 패턴은 AWS CLI의 `AWS_PROFILE`, Kubernetes의 `KUBECONFIG`,
Docker의 `DOCKER_CONFIG`처럼 환경 변수 하나로 설정 위치를 가르는 오래된 관행과
같은 모양이다.
이 문서의 해석으로는 환경 변수가 프로세스 생성 때 부모에서 자식으로 상속되고
자식의 변경이 부모에 전파되지 않는다는 성질 덕분에,
터미널 탭마다 다른 계정을 쓰는 격리가 별도의 가상화 없이 성립한다.
설정 파일의 `env` 블록에 넣을 때는 절대 경로를 써야 하며,
`~`나 `$HOME`은 셸이 풀어 주지 않아서 적은 그대로 남는다.[^env]

### 블로그의 변형은 바이너리 경로와 알림 alias를 더한다

2026년 3월 13일에 Buwaneka Sumanasekara가 Medium에 올린 글은 같은 방식을 다섯
단계로 풀어 쓴다.[^medium]
설정 폴더 둘을 만들고, `type -a claude`로 바이너리의 실제 경로를 찾고,
셸 설정에 계정별 alias를 넣고, 각 계정으로 `/login`을 하고,
`/status`로 확인한다.[^medium]
공식 방법과 다른 점은 alias가 `claude` 대신 바이너리의 전체 경로를 부른다는
것이다.[^medium]
그 이유는 글의 세 번째 alias에 있다.
기본 `claude` 명령을 “계정별 명령을 쓰라”는 안내 문구를 찍는 alias로 덮어써서,
계정 문맥 없이 실수로 실행하는 일을 막는다.[^medium]
이 문서의 해석으로는, 기본 명령을 덮어쓰는 alias가 원래 명령을 다시 부를 수
없으므로 바이너리 경로가 필요해진 것이다.

이 아이디어는 공식 문서에 없는 실용적인 보강이다.
다만 대가가 둘 있다.
Node 버전 관리자(NVM)를 쓰면 바이너리 경로에 Node 버전이 들어가므로 Node를 올릴
때 alias를 고쳐야 한다는 점을 글이 직접 경고한다.[^medium]
경로를 하드코딩한 alias는 Claude Code를 다른 방식으로 설치하거나 옮기면 같은
문제를 겪는다.
기본 명령을 덮어쓴다는 것은 `claude`를 부르는 모든 스크립트가 안내 문구를
받는다는 뜻이기도 하다.

글의 마지막 팁은 프로젝트 루트의 `.env` 파일에 `CLAUDE_CONFIG_DIR`을 적어
프로젝트별 기본 계정으로 삼으라는 것이다.[^medium]
이 팁은 확인하지 못했다.
공식 환경 변수 문서는 `.env` 파일을 읽는다고 적지 않고,
프로젝트 설정으로는 이 변수를 정할 수 없다고 한다.[^env]
`.env`를 읽어 환경 변수로 올려 주는 도구가 셸에 없다면 이 파일은 효력이
없을 수 있다.
디렉터리에 들어갈 때 환경 변수를 자동으로 설정하는 direnv 같은 도구의 `.envrc`가
대안이 될 수 있다는 것이 이 글의 제안이며, 시험하지는 못했다.

### alias 대신 실행 파일을 쓸 때는 래퍼가 필요하다

alias는 대화형 셸에서만 펼쳐진다.
직접 확인한 결과 `zsh -c`로 띄운 비대화형 셸은 같은 `.zshrc`가 있어도 `command
not found`를 냈고, `zsh -ic`로 띄운 대화형 셸에서만 alias가 동작했다.
스크립트나 Claude Code의 Bash 도구가 `claude-work`를 부르는 상황이 바로 비대화형
셸이므로, 이럴 때는 alias 대신 `PATH`에 둔 실행 파일을 쓴다.

```bash
#!/usr/bin/env bash
# claude-acct: 계정 이름으로 설정 폴더를 고르고 claude를 실행한다
# 사용법: claude-acct <계정이름> [claude 인자...]
set -euo pipefail
name="${1:?usage: claude-acct <name> [claude args...]}"; shift
dir="$HOME/.claude-$name"
[ -d "$dir" ] || { echo "no config dir: $dir" >&2; exit 2; }
# 환경에 남은 자격이 /login보다 앞서므로 지운다 (계정이 섞이는 것을 막는다)
exec env -u ANTHROPIC_API_KEY -u ANTHROPIC_AUTH_TOKEN -u CLAUDE_CODE_OAUTH_TOKEN \
  -u ANTHROPIC_PROFILE CLAUDE_CONFIG_DIR="$dir" claude "$@"
```

`$HOME/.claude-dev` 폴더를 만들고 `claude-acct dev`를 처음 실행하면 그 폴더에서
로그인이 시작된다.
가짜 `claude`로 시험해, 설정 폴더가 계정별로 바뀌고 인자가 순서대로 전달되며,
부모 환경에 있던 `ANTHROPIC_API_KEY`와 `CLAUDE_CODE_OAUTH_TOKEN`과
`ANTHROPIC_PROFILE`이 자식에게 전달되지 않는 것을 확인했다.
폴더가 없으면 오류를 내고 종료 코드 2로 끝난다.

### 앱이 대신 관리해 주는 길도 있다

Offrun은 이 일을 앱으로 푼다.
Offrun의 가이드는 수동 방식의 빈틈 둘을 짚는다.
폴더마다 기록이 따로라서 한 계정의 대화를 다른 계정에서 이어 갈 수 없고,
한도에 가까워져도 경고가 없어서 멈춘 뒤에야 알게 된다는 것이다.[^offrun]
Offrun은 같은 폴더 방식을 쓰되 계정 추가와 폴더 생성을 대신하고,
로그인마다 사용량과 리셋 시각을 보여 주며,
한 로그인이 한도에 닿으면 채팅을 같은 에이전트의 다음 로그인으로 옮긴다고
한다.[^offrun]
토큰은 읽거나 복사하거나 저장하지 않고 CLI에 폴더 위치만 넘긴다는 것이 가이드의
설명이다.[^offrun]
이 앱의 구조와 한계는 `agentic-coding/offrun.md`에 따로 정리했다.

수동 방식과 앱의 차이는 경고와 이어 가기다.
수동 방식은 가볍고 설정이 투명하지만 한도 경고와 대화 이어 가기가 없다.
앱은 이를 채우는 대신 새 의존성과 신뢰의 대상이 하나 늘어난다.
어느 쪽이든 계정마다 따로 쌓이는 로그인이라는 원리는 같다.

## 계정이 섞이지 않게 하는 법

### 자격 우선순위를 알아야 한다

여러 자격이 함께 있으면 Claude Code는 정해진 순서로 하나를 고른다.[^auth]
순서는 클라우드 공급자 변수, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`,
`apiKeyHelper`, `CLAUDE_CODE_OAUTH_TOKEN`, Anthropic 프로필과 연동 자격,
마지막이 `/login`으로 저장한 구독 로그인이다.[^auth]
구독 로그인이 가장 뒤라는 점이 핵심이다.
대화형 모드에서는 `ANTHROPIC_API_KEY`를 한 번 승인하면 그 키를 쓰고,
비대화형 `-p`에서는 키가 있으면 항상 그 키를 쓴다.[^auth]
`CLAUDE_CODE_OAUTH_TOKEN`은 `/login`을 실행하면 그 세션에서만 새 로그인으로
바뀌고, 변수를 지우지 않으면 새 세션마다 다시 읽힌다.[^auth]

이 순서가 다중 계정에서 가장 위험한 지점이다.
메인 세션이 환경 변수로 인증되어 있으면 `CLAUDE_CONFIG_DIR`을 바꿔 자식 세션을
띄워도 그 변수가 상속되어 같은 계정이 선택될 수 있다.
이 상속은 문서의 우선순위 규칙에서 읽어 낸 것이고,
실제 모델 호출로 재현하지는 않았다.
앞의 `claude-acct`가 `env -u`로 변수를 지우는 이유다.

Anthropic 프로필도 같은 종류의 구멍이다.
프로필은 Claude Code 설정 폴더와 별개인 Anthropic 설정 디렉터리에 저장되고,
`ANTHROPIC_PROFILE`로 이름을 지정하면 `/login`보다 앞선다.[^auth]
Console 계정에 키 없이 로그인하면 이 프로필이 만들어지는데,
그 저장 위치가 설정 폴더 밖이라는 앞의 예외와 같은 이야기다.[^auth]
`claude-acct`가 `ANTHROPIC_PROFILE`도 지우지만,
이미 활성 프로필 파일이 있는 경우는 변수로 막을 수 없다.
어떤 자격이 실제로 쓰이는지는 `/status`로 확인한다.
로그인과 API 키가 함께 설정되어 있으면 `/status`가 쓰이지 않는 쪽을
표시한다.[^auth]

### 어느 계정으로 로그인되어 있는지 점검한다

계정마다 로그인이 따로 유지되는지는 한 번에 볼 수 있다.

```bash
# 각 설정 폴더가 서로 다른 로그인을 가졌는지 확인한다
for name in dev work; do
  echo "== $name"
  claude-acct "$name" auth status --text
done
```

두 출력의 계정 정보가 달라야 한다.
같은 계정이 두 번 나오면 환경 변수 자격이 걸려 있는 것이니 `env | grep -E
'ANTHROPIC|CLAUDE_CODE_OAUTH'`로 찾는다.
빈 설정 폴더로 `claude auth status`를 돌리면 로그인이 안 된 상태가
JSON으로 나온다.
이 글을 쓰며 돌려 보니 `loggedIn`이 `false`이고 `authMethod`가 `none`이었다.
이 명령은 `--json`과 `--text` 출력을 모두 지원한다.
대화형 세션 안에서는 `/status`가 같은 정보를 보여 준다.

### 회사 정책이 개인 계정 로그인을 막을 수 있다

회사 컴퓨터에서 개인 계정을 쓰려는 경우에는 기술 이전에 정책이 걸린다.
관리자가 관리형 설정에 `forceLoginMethod`와 `forceLoginOrgUUID`를 두면 Claude
Code는 다른 조직의 claude.ai 로그인에 오류를 내고,
시작할 때 쓰는 자격이 목록에 없는 조직에 속하면 종료한다.[^auth]
같은 정책은 `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`,
`apiKeyHelper` 같은 환경 자격도 시작 단계에서 막는다.[^auth]
그러니 설정 폴더로 개인 계정을 따로 로그인해 두는 방법이 회사 관리형 설정이 걸린
기기에서는 통하지 않을 수 있다.
이 문서는 그런 기기에서 시험하지 못했고 문서의 서술을 옮긴 것이다.

또 약관의 한 조항은 회사 이메일로 만든 계정이 그 회사의 Anthropic 기업 계정에
연동될 수 있고 관리자가 이를 모니터링할 수 있다고 밝힌다.[^terms]
계정을 나누는 일은 어느 데이터가 어느 조직의 규정을 따르는지를 나누는
일이기도 하다.

### 로그인 만료는 조용히 작업을 멈춘다

저장된 로그인이 만료되면 모델 요청이 `Login expired` 오류로 실패한다.[^auth]
만료 3일 전부터 시작할 때 경고가 나오지만,
이 경고는 정보일 뿐 요청을 막지 않는다.[^auth]
`/status`의 `Login` 행이 `Expired — log in again`을 보여 주고,
만료 전에 미리 확인할 수 있다.[^auth]
장시간 도는 백그라운드 세션이나 원격 제어 세션은 로그인이 만료되면 다시
로그인하기 전까지 진행하지 못한다.[^auth]
계정을 여럿 두면 이 만료도 계정 수만큼 따로 관리해야 한다.

## 다른 계정에 일을 맡기는 법

### 원리는 결과 텍스트만 돌아오는 비대화형 실행이다

`claude -p "<프롬프트>"`는 비대화형으로 실행되어 응답을 출력하고
끝난다.[^headless]
`--output-format json`을 주면 결과가 `result` 필드에 담기고,
세션 ID와 `total_cost_usd` 같은 메타데이터가 함께 나온다.[^headless]
비용 수치는 클라이언트 쪽 추정이어서 실제 청구액과 다를 수 있다고 문서가
밝힌다.[^headless]
실행이 성공하면 종료 코드 0, 실패하면 0이 아닌 코드로 끝나고,
인증이 없는 것 같은 실행 중 실패는 결과로 표준 출력에 찍힌다.[^headless]

메인 세션이 Bash 도구로 이 명령을 실행하면 메인 컨텍스트에 들어오는 것은 명령의
출력 텍스트뿐이다.
위임받은 세션이 읽은 파일과 거친 추론은 그 세션 안에 남고,
다른 계정의 사용량으로 잡힌다는 것이 절약의 원리다.
이는 서브에이전트가 자기 컨텍스트에서 일하고 요약만 돌려주는 구조와 모양이
같지만, 청구 대상이 다른 계정이라는 점이 다르다.
이 청구 귀속은 공식 문서에서 읽은 구조에서 나온 추정이며,
두 계정의 사용량 표시를 비교한 실험은 하지 못했다.

### 맡길 일과 맡기지 않을 일은 결과의 크기로 가른다

| 일의 모양                             | 위임          | 이유                                                |
| ------------------------------------- | ------------- | --------------------------------------------------- |
| 큰 코드베이스를 읽고 한 문단으로 요약 | 맡긴다        | 읽는 토큰이 크고 돌아오는 결과가 작다               |
| 로그나 문서 한 덩이의 분류와 추출     | 맡긴다        | 입력과 출력이 분명하고 서로 의존하지 않는다         |
| 독립된 검토(주장 확인, 코드 리뷰)     | 맡긴다        | 메인의 편향과 컨텍스트 없이 보는 것이 이점이다      |
| 메인이 이미 파일을 읽어 둔 일의 후속  | 맡기지 않는다 | 위임받은 쪽이 같은 파일을 처음부터 다시 읽는다      |
| 여러 번 주고받으며 방향을 잡는 일     | 맡기지 않는다 | 한 번의 호출이 하나의 대화여서 끼어들 수 없다       |
| 쓰기와 되돌리기가 얽힌 일             | 맡기지 않는다 | 권한을 넓게 열어야 하고 결과를 메인이 검증해야 한다 |

기준은 돌아오는 결과가 맡긴 일의 크기보다 훨씬 작은가이다.
읽는 양이 크고 결과가 작을수록 메인 계정에서 아끼는 몫이 커진다.
이 표는 이 글의 판단이며 측정한 값이 아니다.

### 위임용 래퍼는 권한을 읽기 전용으로 시작한다

`-p` 호출에는 권한 모드와 허용 도구를 정해야 한다.
승인이 필요한 호출은 Manual 모드의 `-p` 실행에서 승인할 수단이 없으면 거부되고,
Claude Code v2.1.302부터는 권한 모드를 정하지 않은 `-p` 실행이 Manual 모드로
시작한다.[^headless]
아래 래퍼는 기본값을 읽기 전용 도구로 두고 쓰는 일은 환경 변수로 열게 한다.

```bash
#!/usr/bin/env bash
# claude-delegate: 다른 계정에 일을 맡기고 결과 텍스트만 돌려받는다
# 사용법: claude-delegate <계정> "<프롬프트>"
# PERM(권한 모드), TOOLS(허용 도구)로 바꿀 수 있다
set -euo pipefail
acct="${1:?usage: claude-delegate <account> <prompt>}"; prompt="${2:?prompt}"
claude-acct "$acct" -p "$prompt" \
  --permission-mode "${PERM:-dontAsk}" \
  --allowedTools "${TOOLS:-Read,Grep,Glob}" \
  --output-format json | jq -r '.result'
```

`dontAsk`는 승인이 필요했을 호출을 모두 거부하는 모드이고,
`--allowedTools`에 적힌 도구와 승인이 필요 없는 읽기는 그대로
실행된다.[^headless]
이 래퍼를 가짜 `claude`로 시험해, 설정 폴더가 계정별로 바뀌고 인자가 순서대로
전달되며 `PERM`과 `TOOLS`가 반영되는 것을 확인했다.
`set -o pipefail`이 켜져 있어서 `claude`가 실패하면 파이프라인도 실패로 끝난다.
다만 `jq`는 `result`만 뽑을 뿐 오류의 종류를 구분하지 않으므로,
쓰는 사람이 종료 코드와 결과를 확인하는 단계를 더해야 한다.

### 함정 다섯 가지

첫째, `--bare`는 구독 로그인을 읽지 않는다.
`--bare`는 시작이 빠르고 호스트의 설정에 영향받지 않아 스크립트에 권장되지만,
OAuth 자격과 키체인을 읽지 않는다.[^headless]
`CLAUDE_CODE_OAUTH_TOKEN`도 읽지 않는다.[^auth]
그래서 구독 계정으로 위임할 때 `--bare`를 붙이면 인증이 실패한다.
문서는 `--bare`가 앞으로 `-p`의 기본값이 될 것이라고 적는다.[^headless]
그날이 오면 구독 로그인으로 위임하는 래퍼는 동작이 바뀔 수 있으므로,
Claude Code를 올릴 때마다 이 부분을 다시 시험해야 한다.

둘째, `-p`는 신뢰 대화상자를 띄우지 않는다.
`--bare`를 쓰지 않으면 프로젝트의 훅과 MCP 서버를 그대로 불러온다.[^headless]
다른 계정에 맡긴 일이 무인으로 도는 동안 낯선 저장소의 훅이 실행될 수
있다는 뜻이다.
읽기 전용 도구와 `dontAsk`로 시작해서, 쓰기가 필요한 일에만 `acceptEdits`를 열고
되돌릴 수 있는 브랜치에서 돌린다.

셋째, `claude setup-token`이 만드는 장기 토큰은 구독 로그인의 대체가 아니다.
이 토큰은 1년짜리이고 모델 요청만 할 수 있어서 원격 제어 세션을 만들거나
claude.ai 커넥터를 가져오지 못한다.[^auth]
위임 용도로는 충분하지만, 환경 변수로 걸어 두면 다른 계정의 로그인보다 앞서므로
계정별로 따로 두어야 한다.

넷째, `-p` 안에서는 `/login` 같은 터미널 전용 명령을 쓸 수 없다.[^headless]
로그인이 만료된 계정으로 위임하면 실행이 실패하므로 미리 `claude-acct <계정>
auth status`로 점검한다.

다섯째, 인증 실패는 조용하다.
위임 결과가 오류 문구인지 진짜 결과인지 구분하지 않고 이어 쓰면 오류가
결과처럼 흘러간다.
종료 코드를 확인하고 결과의 형식을 JSON 스키마로 고정하는 방법이
있다.[^headless]

## 맡기면 무엇을 아끼고 무엇이 늘어나는가

### 아끼는 것은 메인의 컨텍스트이고 총 토큰은 늘어난다

위임받은 세션은 자기 시스템 프롬프트와 도구 정의를 처음부터 싣고 시작한다.
프롬프트 캐시는 계정을 가로질러 공유되지 않을 것이라는 추정이 있지만 이 글이
확인하지 못했다.
어느 쪽이든 두 계정의 사용량을 합하면 한 계정에서 직접 일할 때보다
많아질 수 있다.
그래서 이 방법은 총 토큰을 줄이는 방법이 아니라 메인 계정의 한도를 쓰는 속도를
늦추는 방법이다.

### 맡긴 일은 자기 완결적이어야 한다

위임받은 세션은 메인의 대화와 읽은 파일을 보지 못한다.
프롬프트에 목적, 대상 경로, 돌려받을 형식을 모두 적어야 한다.
이것을 적는 일이 일 자체보다 오래 걸리면 위임은 손해다.

### 한도가 문제라면 계정을 늘리지 않는 길이 먼저다

같은 계정 안에서는 서브에이전트에 더 가벼운 모델을 지정하는 방법이 있다.
계정을 늘리지 않고 한도를 쓰는 속도를 줄이는 방법이라 약관 문제가 생기지 않는다.
별도 청구를 원하면 Claude Console의 API 키를 `ANTHROPIC_API_KEY`로 주는 방법이
있고, `-p`에서는 이 키가 있으면 항상 쓰인다.[^auth]
이 경우 비용은 사용량만큼 청구되고 구독 한도와는 별개다.

## 약관과 정책은 기술이 답하지 않는다

설정 폴더로 개인과 회사 계정을 나누는 일은 공식 문서가 직접 안내하는
사용법이다.[^auth]
그 위에 한도를 피하려고 일을 나누는 흐름을 얹는 것은 다른 문제다.
이 글이 읽은 Anthropic의 소비자 이용약관(2025년 10월 8일 시행)에서 관련된 대목은
다음과 같다.[^terms]

- 2조: 로그인 정보, API 키, 계정 자격을 다른 사람과 공유하거나 계정을 넘기는 것을 금지한다. 본인이 소유한 계정을 여러 개 두는 것을 다루는 조항은 이 글이 읽은 범위에 없다.
- 3조: 서비스를 남용하는 행위, 특히 시스템이나 보호 조치를 우회하는 방식을 금지한다.
- 3조의 자동화 조항: API 키로 접속하거나 Anthropic이 명시적으로 허용한 경우를 제외하고 봇이나 스크립트를 통한 자동화된 접속을 금지한다.
- 12조: Anthropic이 용량 제한을 늘리거나 줄일 수 있다.

이 조항들이 이 글의 사용에 어떻게 적용되는지는 이 글이 판단하지 못한다.
`claude -p`는 공식 문서가 소개하는 Claude Code의 기능이라는 점,
그러나 한도를 피할 목적으로 계정 사이에서 일을 나누는 것이 우회에 해당하는지는
약관 본문만으로 알 수 없다는 점을 구분해야 한다.
API 키와 Console은 별도의 상용 약관을 따른다고 약관 페이지가 밝힌다.[^terms]
Anthropic이 서드파티 도구에서의 구독 사용을 막았다는 공지는
`claude/third-party-subscription-block.md`가 다룬다.

반대편의 도구도 있다.
여러 구독 계정을 라운드로빈으로 돌려 한도를 넓히는 프록시와 로드
밸런서(`ai-tool/cliproxyapi.md`, `codex/codex-lb.md`,
`web-api/sub2api.md`)는 이 글이 다루는 폴더 분리와는 목적이 다르다.
각 문서가 그 도구들의 약관 충돌 가능성을 따로 논한다.
폴더로 계정을 가르는 일과 계정 풀로 한도를 넓히는 일을 같은 선 위에 놓지 않는
것이 이 글의 입장이다.
업무용 계정을 개인 일에 쓰거나 반대로 쓰는 일은 한도와 별개로 조직의 규정과
데이터 처리 설정이 다를 수 있다.
실제로 쓰기 전에 현재의 약관, 사용 정책, 조직의 규정을 직접 읽어야 한다.

## 체크리스트

- 계정마다 설정 폴더가 따로 있고 `claude auth status`가 서로 다른 계정을 보여 주는가.
- 위임 호출이 alias가 아니라 `PATH`의 실행 파일을 쓰는가.
- 래퍼가 `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_PROFILE`을 지우는가.
- Console 계정을 둘 이상 쓰지 않는가(설정 폴더로 나뉘지 않는다).
- 회사 기기의 관리형 설정이 개인 계정 로그인을 막지 않는가.
- 구독 계정으로 위임하는 호출에 `--bare`가 붙어 있지 않은가.
- `--permission-mode`와 `--allowedTools`를 정했고 기본값이 읽기 전용인가.
- 맡기는 프롬프트에 목적, 경로, 돌려받을 형식이 모두 들어 있는가.
- 돌아오는 결과가 맡긴 일의 크기보다 충분히 작은가.
- 위임 호출의 종료 코드와 `result`를 확인하는가.
- 로그인 만료 시점을 `/status`로 확인하는가.
- 약관, 사용 정책, 조직 규정, 계정별 데이터 설정을 직접 읽어 확인했는가.

## 기억할 원칙

### 계정을 가르는 일과 한도를 넓히는 일은 다른 문제다

설정 폴더는 로그인을 가르는 도구이고, 그것으로 어떤 목적을 이루는지는 약관과
조직 규정이 정한다.
폴더 분리는 문서화된 사용법이고 위임으로 한도를 늘리는 일은 문서화되지 않은
응용이라는 차이를 적어 둔다.

### 환경 변수의 우선순위를 믿고 계정이 섞이지 않는다고 가정하지 않는다

자격은 환경 변수가 로그인보다 앞선다.
계정을 나눴다고 믿는 순간에도 상속된 변수 하나가 계정을 바꿀 수 있다.
래퍼가 변수를 지우고 `auth status`로 점검하는 습관이 가장 싼 방어다.

### 아끼는 것이 무엇인지 먼저 적는다

위임이 줄이는 것은 메인 계정의 컨텍스트와 사용량이고 전체 토큰이 아니다.
이것을 적어 두지 않으면 절약이라는 이름 아래 두 계정의 합계가 늘어도
알아채지 못한다.
