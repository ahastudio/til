# Harness — Claude Code 에이전트 팀 & 스킬 아키텍트

<https://github.com/revfactory/harness>

GN 토론: <https://news.hada.io/topic?id=27969>

## 소개

Harness는 “하네스 구성해줘” 같은 한 문장으로 도메인 설명을 에이전트 팀과
그 팀이 쓰는 스킬로 바꿔 주는 Claude Code 플러그인입니다.
README는 이를 Claude Code용 팀 설계 공장(team-architecture factory)이라고
부릅니다.
저장소는 2026년 3월 26일에 만들어졌고 라이선스는 Apache-2.0이며,
별 9,326개, 포크 1,341개, 열린 이슈 3개입니다.
마지막 푸시는 9월 28일이고 README의 버전 배지는 2.1.0입니다.
이 문서는 README를 읽어 정리한 것이고, 플러그인을 직접 설치해 돌려 본 결과가
아닙니다.

GeekNews에는 3월 29일에 소개글이 올라왔습니다.
소개글은 실행 모드를 에이전트 팀(`TeamCreate`, `SendMessage`, `TaskCreate`)과
서브 에이전트 두 가지로 설명합니다.[^gn]
GeekNews 운영자 xguru는 첫 댓글에서 저자가 카카오 AI Native 전략 팀 리더라고
소개했습니다.[^xguru]
현재 README는 `TeamCreate` 기반의 v1이 더는 없는 실험용 API에 기대고 있었다고
적으므로, 그 소개글은 v1 기준의 설명입니다.

## v2에서 달라진 것

README는 v2를 현재 Claude Code의 다중 에이전트 런타임에 맞춘 전면 재작성이라고
설명합니다.
달라진 점은 다음과 같습니다.

- 실행 모드가 셋이 되었습니다. 워크플로 오케스트레이션(`pipeline()`, `parallel()`, 스키마, 예산을 쓰는 결정적 스크립트), 지속형 에이전트 협업(이름 있는 에이전트와 `SendMessage`와 공유 작업 목록), 서브 에이전트 위임(한 번 보내고 끝내는 병렬 호출)입니다.
- 실험용 플래그 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 의존이 사라졌습니다.
- v1은 모든 에이전트에 `model: "opus"`를 고정했지만, v2는 작업의 복잡도와 지속 시간과 자율성과 지연 요구에 따라 에이전트마다 모델 등급을 고르고 근거 없는 일괄 고정을 금지합니다.
- 적대적 검증, 심사단, 더 나올 게 없을 때까지 반복, 완결성 비평 같은 품질 패턴이 워크플로 기반으로 정리되었습니다.
- 문서에만 있던 진화 기능이 `/harness:evolve` 스킬로 실제 제공됩니다. 초기 하네스와 현재 하네스의 차이를 잡아 피드백을 일반화하고 에이전트와 스킬과 오케스트레이터에 되먹입니다.
- v1 산출물(`TeamCreate`, `TeamDelete`, 실험 플래그)을 감지해 기계적으로 옮기는 경로가 들어 있습니다.

## 설계 방식

여섯 가지 아키텍처 패턴이 있고 각각 가장 알맞은 v2 실행 모드에 대응됩니다.
파이프라인, 팬아웃/팬인, 전문가 풀, 생산자/리뷰어, 감독자, 계층적 위임입니다.
실행 모드는 팀 크기가 아니라 제어 흐름의 모양으로 고르고,
단계마다 모드를 섞을 수도 있다고 합니다.

| 모드                    | 사용하는 수단                            | 알맞은 경우                                                                   |
| ----------------------- | ---------------------------------------- | ----------------------------------------------------------------------------- |
| 워크플로 오케스트레이션 | `Workflow` 스크립트                      | 제어 흐름이 결정적일 때: 나열 가능한 팬아웃, 검증 루프, 대규모, 구조화된 출력 |
| 지속형 에이전트         | `Agent(name:)`, `SendMessage`, 작업 목록 | 문맥을 유지하는 장기 전문가, 반복 피드백과 협상                               |
| 서브 에이전트 위임      | 한 번짜리 `Agent` 호출                   | 결과만 필요한 병렬 작업                                                       |

워크플로는 8단계입니다.
0단계는 기존 하네스 점검(신규, 확장, 유지보수, v1 산출물 감지)이고,
이어서 도메인 분석, 실행 모드와 팀 구조 설계,
에이전트 정의 생성(`.claude/agents/`),
스킬 생성(`.claude/skills/`), 오케스트레이션과 `CLAUDE.md` 포인터,
검증과 시험, `/harness:evolve`를 통한 유지보수가 뒤따릅니다.
스킬은 점진적 공개(Progressive Disclosure)로 문맥을 아끼도록 만든다고 합니다.
검증 단계는 트리거 평가, 시험 실행, 스킬이 있을 때와 없을 때의 A/B 비교를
포함합니다.

생성 결과는 프로젝트 안의 `.claude/agents/`(누가), `.claude/skills/`(어떻게와
오케스트레이터), 그리고 트리거 규칙과 변경 이력만 담은 최소한의
`CLAUDE.md`입니다.

## 설치와 사용

```shell
/plugin marketplace add revfactory/harness
/plugin install harness@harness-marketplace
```

마켓플레이스 대신 스킬 폴더를 전역 스킬로 복사하는 방법도 있고,
환경 변수와 실험 플래그는 필요 없다고 합니다.
사용은 `하네스 구성해줘`, `build a harness for this project`,
`design an agent team for <domain>` 같은 요청으로 시작하고,
쓴 뒤에는 `하네스 회고해줘`나 `evolve the harness with this feedback`로
진화 단계를 돌립니다.

## 분석

### 에이전트 팀은 책임 분리를 에이전트 층에 적용한 것이다

단일 에이전트가 모든 작업을 맡으면 문맥이 오염되고 역할이 섞여 품질이 떨어질 수
있습니다.
팀 구조는 각 에이전트를 자기 전문 영역에 집중시키는 방식으로 이를 막으려는
설계이고, 소프트웨어의 책임 분리(Separation of Concerns)와 같은 발상입니다.

### 스킬 재사용이 팀 운영 비용을 줄이는 쪽으로 설계되어 있다

매번 프롬프트를 새로 쓰지 않고 검증된 스킬을 재사용하면 새 팀을 꾸리는 비용이
줄어듭니다.
README가 스킬 생성에 점진적 공개를 쓰고, 오케스트레이터와 보강 스킬을 분리하고,
`/harness:evolve`로 사용 피드백을 스킬에 되먹이는 것은 모두 이 방향입니다.

### v2의 핵심 변화는 런타임이 바뀌어 설계를 다시 쓴 것이다

실험용 API가 사라지자 실행 모드와 품질 패턴과 모델 정책까지 다시 쓴 것이
v2입니다.
하네스는 프롬프트 모음이 아니라 에이전트 생성과 메시징과 동시성 같은 런타임
기능 위에 선 구조물이라는 점을 이 이력이 보여 줍니다.
같은 저자의 `revfactory/codex-harness`가 이 하네스를 Codex로 옮기면서 계층적
위임을 의존성 그래프로 바꾼 것도 같은 현상입니다. 이 저장소의 [codex-harness
문서](../agentic-coding/codex-harness.md)가 그 이식을 다룹니다.

## 비평

### 효과를 보여 주는 수치는 저자가 직접 잰 v1 결과 하나뿐이다

README가 근거로 드는 것은 소프트웨어 공학 작업 15개에서 구조화된 사전 설정이
코드 에이전트의 출력 품질에 미치는 영향을 잰 시험입니다.
평균 품질이 49.5에서 79.3으로(+60%), 15개 모두 개선, 출력 분산 -32%라고 하며,
README 스스로 저자가 직접 수행한 n=15의 v1 결과이니 도입 판단 전에 자체 파일럿을
돌리라고 적습니다.
v2의 실행 모드와 품질 패턴이 이 수치를 유지하는지는 README에 없습니다.

GeekNews 댓글에서도 같은 질문이 나왔습니다.
wang3281은 하네스를 만드는 입장에서 오픈소스 하네스의 효과를 어떤 시험으로
보여 주는지, 공식적이고 정량화된 벤치마크가 있는지 궁금하다고 물었고,
체감이 아닌 효과성 검증을 다들 어떻게 하는지 되물었습니다.[^wang3281]
이 질문에 대한 답은 같은 스레드에 달리지 않았습니다.

### 토큰 비용은 README에 없고 사용자 보고에만 있다

README는 비용을 다루지 않습니다.
neocode24는 Max 100 구독으로 시작하자마자 토큰 한도에 닿았다고
적었고,[^neocode-limit]
namojo는 Claude Max 200과 Opus로도 한두 시간이면 일일 한도에 이를 것이라고
추정했습니다.[^namojo]
namojo는 같은 글에서 결과물의 수준이 준전문가급이고,
컨텍스트를 열어 보면 하네스가 최대한의 효율로 쓰이는 것을 알 수 있다고도
썼습니다.[^namojo]
여러 에이전트를 병렬로 돌리는 구조이므로 모델 호출이 늘어나는 것은 설계의
귀결이고, 이득과 비용을 같은 작업으로 맞비교한 자료는 어디에도 없습니다.

### 모드를 섞으면 감독자가 엉뚱한 곳에 일을 맡길 수 있다

edunga1은 이미 에이전트 팀을 쓰고 있다면 특별할 것은 없지만,
팀 구성 정보를 새 세션에서도 잇도록 에이전트와 스킬로 기반을 만들어 주는 점은
편리했다고 평가했습니다.
다만 하네스가 서브 에이전트와 에이전트 팀을 모두 고려하다 보니,
감독자 패턴에서 팀이 이미 만들어져 있는데도 감독자가 서브 에이전트에 일을
맡기는 엉뚱한 상황이 종종 생겼다고 보고했습니다.[^edunga1]
v2는 실행 모드를 제어 흐름 모양으로 고르도록 바꿨지만,
이 보고가 v1 시절의 것이어서 v2에서 해소되었는지는 확인되지 않았습니다.

## 인사이트

### 1. 단일 에이전트의 한계를 팀 구조로 돌파한다

하나의 에이전트가 모든 작업을 담당하면 문맥이 오염되고,
역할 혼선으로 품질이 떨어집니다.
코드 리뷰 에이전트는 리뷰만 하고 문서 에이전트는 문서만 보게 하면
책임 분리를 에이전트 층에 적용한 구조가 됩니다.

### 2. 도입 전에 자기 작업으로 비교 시험을 한다

저자가 잰 +60%는 자기 환경의 v1 결과이고 비용은 측정되지 않았습니다.
자기 저장소의 실제 작업 대여섯 개를 골라 하네스를 쓴 경우와 한 줄 요청으로
시킨 경우를 같은 모델로 돌려 품질과 토큰 사용량을 함께 기록하면
README의 어떤 수치보다 빠르게 도입 여부를 알려 줍니다.

### 3. 에이전트 조직화는 소프트웨어 아키텍처 문제다

에이전트 수가 늘수록 의존성, 인터페이스, 상태 공유 문제가 생깁니다.
역할 경계를 명확히 하고, 에이전트 간 통신 방식을 정하고,
한 에이전트의 실패가 다른 에이전트로 번지지 않게 설계해야 합니다.
v2가 실행 모드를 제어 흐름의 모양으로 고르게 한 것은 이 설계 문제를 도구가
대신 판단해 주려는 시도입니다.

### 4. 이 판단을 바꿀 관찰

v2의 실행 모드별로 같은 작업의 품질과 비용을 공개한 시험이 나오면 효과 주장은
강해지거나 약해집니다.
모드를 섞는 구성에서 감독자의 잘못된 위임이 줄었다는 재현 사례가 나와도
비평의 한 항목이 사라집니다.
