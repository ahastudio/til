# Claude Tag 관리자 설정: 권한 상속, 지출 한도, 감사 경로

원문: [What is Claude Tag?](https://support.claude.com/en/articles/15594475-what-is-claude-tag)

HN 토론: <https://news.ycombinator.com/item?id=48649418> (3점, 1개 댓글)

## 소개

Claude Tag의 지원 문서이며 2026년 8월 21일자다.
관리자가 실제로 설정해야 하는 항목을 다루므로, 제품 발표문보다 운영에 필요한 정보가 훨씬 많다.

이 문서가 먼저 알리는 것은 이행이 이미 끝났다는 사실이다.
Claude in Slack은 2026년 8월 3일에 새 Claude Tag 경험으로 전환되었고,
Claude와 Slack을 연동하려면 이제 Claude Tag를 쓰라고 안내한다.
Claude Tag는 Team과 Enterprise 요금제에서 베타로 제공되며 현재 Slack에서 동작한다.

제품이 약속하는 것은 세 가지다.
대화에 @Claude를 태그하면 조직의 도구와 주변의 공유 맥락을 써서 실제 작업을 맡고,
자기 정체성으로 동작하며, 자기가 있는 채널에서 관련 정보를 기억해 맥락을 쌓고, 스스로 후속 조치를 할 수 있다.
FAQ는 이것을 기존 경험의 다음 세대라고 규정하고,
며칠에 걸쳐 맥락을 기억하고, 스스로 후속 작업을 예약하고, 먼저 확인하러 오고,
자기 정체성으로 행동한다는 점을 달라진 부분으로 꼽는다.

약속하지 않는 것도 분명하다.
Slack 바깥의 표면은 이 문서의 범위가 아니며, 설정 권한은 특정 역할에만 열려 있고,
기억은 채널과 워크스페이스 경계를 따른다.

## 동작 방식

### 세 개의 표면과 두 개의 청구 주체

Slack 안에서 Claude를 만나는 경로가 셋인데, 그중 하나만 조직 계정으로 청구된다.
이 구분이 이 제품에서 가장 먼저 이해해야 할 부분이다.

| 표면               | 사용 방법                                                            | 쓰는 권한                                                | 청구 대상        |
| ------------------ | -------------------------------------------------------------------- | -------------------------------------------------------- | ---------------- |
| 채널 태그          | 아무 채널에서나 `@Claude`를 태그하고 스레드에서 작업을 지켜봄        | 관리자가 그 채널에 설정한 조직 정체성의 도구와 접근 권한 | 조직             |
| 다이렉트 메시지    | `@Claude`와 비공개 대화 시작                                         | 사용자가 자기 Claude 계정에서 켜 둔 기능과 연결한 도구   | 개인 Claude 계정 |
| AI 어시스턴트 패널 | Slack의 AI 어시스턴트 헤더에서 Claude 아이콘을 눌러 오른쪽 패널을 염 | 다이렉트 메시지와 동일                                   | 개인 Claude 계정 |

채널에서 태그하면 작업 전체가 채널의 모든 사람에게 보이는 상태로 진행된다.
같은 채널의 모두가 같은 Claude를 상대하므로 누구나 방향을 돌리거나 이어받을 수 있다.
작업이 끝나면 스스로 글을 올리고, 스레드가 멈추면 사람을 태그해 확인을 요청하기도 한다.

### 권한은 세 층으로 상속된다

접근 권한과 기억은 상위 층에서 하위 층으로 내려온다.
각 층은 바로 위 층의 권한과 기억을 물려받는다.

| 층           | 적용 범위                                | 상속                                                     |
| ------------ | ---------------------------------------- | -------------------------------------------------------- |
| 조직 전체    | Claude Tag가 설치된 모든 곳              | 없음, 최상위                                             |
| 워크스페이스 | 해당 Slack 워크스페이스의 모든 공개 채널 | 조직 전체의 권한과 기억                                  |
| 비공개 채널  | 그 채널 하나                             | 워크스페이스가 이미 준 것 위에 자격 증명과 저장소를 추가 |

문서가 드는 예가 이 구조의 용도를 잘 보여 준다.
법무 업무용으로 만든 채널은 도구와 기억을 엔지니어링 채널과 분리해 유지한다.
민감한 연결을 좁은 집단에 묶어 두려면 비공개 채널을 쓰라는 권고다.

여기서 읽어야 할 것은 분리의 방향이다.
비공개 채널은 상위 권한을 물려받은 위에 더하는 자리이므로, 아래로 좁히는 장치가 아니라 위에 얹는 장치다.
조직 전체 층에 무언가를 붙이면 그것은 모든 채널에 내려간다.

### 게스트가 있는 채널은 별도 스위치를 탄다

Slack 게스트가 포함된 채널에는 게스트 응답 허용이라는 설정이 따로 있고, 세 가지 중 하나를 고른다.

| 값           | 동작                                                                 |
| ------------ | -------------------------------------------------------------------- |
| Restrict     | 기본값이며 Claude가 그 채널에 아예 들어가지 않는다                   |
| Channel only | Claude가 답하되 게스트가 있는 동안에는 채널 한정 접근으로만 동작한다 |
| Allow        | 다른 채널과 마찬가지로 설정된 전체 접근 권한을 쓰며 답한다           |

기본값이 차단이라는 점이 중요하다.
외부 협력사나 계약자가 들어와 있는 채널은 관리자가 명시적으로 열기 전까지 Claude가 동작하지 않는다.

## 설정하기

Claude 앱이 설치된 뒤의 설정은 Primary Owner 또는 Owner만 할 수 있다.
문서가 별도로 강조하는 부분이며, Admin 역할로는 불가능하다.

설정 순서는 셋이다.
Claude의 정체성을 프로비저닝하고, 조직의 도구와 저장소를 연결하고, Claude Tag가 동작할 채널을 고른다.
채널 하나가 준비되면 팀원은 개별적으로 설정할 것이 없다.

사용 권한은 조직 설정의 Claude Tag 항목에서 Member Access로 정하며 세 가지 모드가 있다.

| 모드                        | 대상                               |
| --------------------------- | ---------------------------------- |
| Slack 워크스페이스의 누구나 | 워크스페이스 구성원 전체           |
| Claude 조직의 구성원        | Claude 조직에 속한 사람만          |
| 역할이 허용한 구성원만      | 커스텀 역할에 권한을 부여한 사람만 |

세 번째가 역할 기반 접근이고 Claude Enterprise 요금제에서만 쓸 수 있다.
역할로 제한하려면 Member Access를 세 번째 값으로 두고
커스텀 역할에 Slack에서의 Claude Tag 권한을 부여한다.
이 설정은 채널 멘션과 다이렉트 메시지 양쪽에 함께 적용된다.

## 값 정하기

지출은 사람 수가 아니라 사용량 기반이므로, 한도 설정이 도입 시점의 실질적인 결정이 된다.

| 항목           | 내용                                                     | 정할 때 볼 것                                                     |
| -------------- | -------------------------------------------------------- | ----------------------------------------------------------------- |
| 조직 전체 한도 | 모든 채널을 합친 총액의 하드 캡이며 이 값을 넘길 수 없다 | 도입 크레딧이 소진된 뒤의 월 예산, 넘겼을 때 업무가 멈춰도 되는지 |
| 채널별 한도    | 조직 한도 위에 개별 채널마다 따로 건다                   | 채널의 작업 성격, 상시 동작 여부, 참여 인원                       |
| 새 채널 기본값 | 새로 만들어지는 채널이 물려받는 한도                     | 채널이 얼마나 자주 새로 생기는지, 방치될 가능성                   |
| 임계 알림      | 어떤 한도든 75%와 95%에서 관리자에게 통지된다            | 알림을 받을 관리자가 실제로 대응할 수 있는지                      |
| 사용량 분석    | 같은 화면에서 채널별 지출 내역을 본다                    | 어느 채널이 비용을 만드는지 주기적으로 검토할 담당                |

한도에 걸렸을 때의 동작이 명시되어 있고, 이 부분이 값을 정하는 방식을 바꾼다.
한도를 넘길 작업은 거절되며 조용히 잘리지 않는다.
막힌 사용자는 Slack을 떠나지 않고 관리자에게 증액을 요청할 수 있고,
알림에는 한도 때문인지 잔액 때문인지가 적힌다.

거절이 기본 동작이므로 한도를 낮게 시작해도 위험이 적다.
절반쯤 진행된 작업이 잘려 부분 결과가 남는 상황이 생기지 않기 때문이며,
증액 요청 경로가 제품 안에 있으므로 낮게 잡고 올리는 방향이 합리적이다.
반대로 높게 잡아 두면 75% 알림이 울릴 때 이미 큰 금액이다.

## 기억과 감사

Claude Tag는 채널 단위와 워크스페이스 단위로 맥락을 유지한다.
관리자는 그 기억을 열람하고 편집하고 삭제할 수 있다.

감사는 조직 설정의 Claude Tag 하위 Audit 화면에 모인다.
조직 전체의 예약 작업과 일회성 작업이 전부 나열되고,
Agent Identity로 이루어진 모든 네트워크 호출도 함께 기록된다.

행위별 추적 경로도 각 도구 쪽에 남는다.
Slack 게시물은 Claude 앱에서 온 것으로 표시되고,
커밋과 풀 리퀘스트는 Claude GitHub App이 작성자로 나타나며
그 작업을 시작한 Slack 스레드로 돌아가는 링크가 붙는다.

상시 동작을 확인하는 방법은 채널 안에서 직접 묻는 것이다.

```text
@Claude what triggers do you have set up here?
```

이 질문으로 그 채널에 걸려 있는 standing work를 보고 끌 수 있다.

## 데이터가 남는 자리

문서가 구분하는 것은 Slack 쪽 기록과 Claude 쪽 기록이다.

| 항목          | 내용                                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------------------- |
| 저장 분리     | Slack에서의 Claude 대화는 Claude 이력과 별도로 유지된다                                                         |
| 가시성        | Slack에서 시작한 대화는 Claude 채팅 이력에 보이지 않고, Claude 웹앱에서 시작한 대화는 Slack에서 접근되지 않는다 |
| 삭제          | 연동을 해제하거나 앱을 삭제하면 30일 안에 Claude에서 자동 삭제된다                                              |
| Slack 측 보존 | Slack 안의 대화는 조직의 Slack 보존 정책을 따른다                                                               |
| 기억 보존     | 채널과 워크스페이스 기억은 작업이 끝나도 유지되며, 채널 경계를 지킨다                                           |
| 귀속          | 채널 작업은 조직의 Claude 정체성에, 다이렉트 메시지 작업은 개인 계정에 귀속된다                                 |

## 트레이드오프

### 상속 구조는 설정을 단순하게 만들고 실수의 범위를 넓힌다

조직 전체에서 워크스페이스로, 다시 비공개 채널로 내려가는 상속은 관리 부담을 크게 줄인다.
채널마다 자격 증명을 다시 붙이지 않아도 되고, 새 채널이 생겨도 기본 권한이 따라온다.

대가는 실수의 폭발 반경이다.
조직 전체 층에 저장소 하나를 연결하면 그것은 모든 워크스페이스의 모든 공개 채널로 내려간다.
권한을 줄이는 방향의 조작이 구조에 들어 있지 않다는 점이 특히 그렇다.
문서가 설명하는 비공개 채널은 위에 더하는 자리이고, 상위 권한을 빼는 자리가 아니다.

그래서 남는 어려움이 있다.
조직 전체 층을 최소로 유지하면 채널마다 설정을 반복해야 하고,
편의를 위해 상위 층을 채우면 열람 범위가 조용히 넓어진다.
중간값이 없는 것은 아니지만, 어느 쪽이든 정기적으로 상위 층에 무엇이 붙어 있는지 확인하는 절차가 필요하며
그 절차는 제품이 제공하지 않는다.

### 개인 청구와 조직 청구가 같은 자리에 섞여 있다

다이렉트 메시지는 개인 Claude 계정으로 청구되고 개인이 켜 둔 도구를 쓰며,
채널 태그는 조직으로 청구되고 관리자가 설정한 도구를 쓴다.
경계는 명확하지만 그 경계가 사용자 눈에 보이지 않는다.

같은 Slack 창에서 같은 `@Claude`를 부르는데,
어디서 불렀느냐에 따라 누가 돈을 내는지와 무엇에 접근할 수 있는지가 바뀐다.
채널에서 되던 일이 다이렉트 메시지에서 안 되거나 그 반대인 상황이 생기고,
원인이 권한 설정이라는 사실이 사용자에게 즉시 드러나지 않는다.

조직 관점에서는 반대 방향의 문제가 있다.
조직 한도를 빡빡하게 걸면 사람들이 다이렉트 메시지로 옮겨 가고,
그것은 개인 계정으로 청구되면서 조직의 감사 화면에는 잡히지 않는다.
비용은 줄지만 가시성도 함께 줄어드는 교환이며, 한도를 정할 때 이 이동을 함께 고려해야 한다.

### 기억이 일을 잘하게 만들면서 지우기 어려운 자산이 된다

기억은 이 제품의 핵심 기능이다.
며칠에 걸쳐 맥락을 유지하기 때문에 같은 설명을 반복하지 않아도 되고,
문서 표현대로 작업이 끝나도 폐기되지 않고 남는다.

그 유지가 관리 대상을 하나 늘린다.
관리자는 기억을 보고 고치고 지울 수 있지만, 무엇을 지워야 하는지는 알려 주지 않는다.
채널에서 오간 말 중 철회된 결정, 잘못된 수치, 퇴사자가 남긴 판단이 섞여 있고,
그중 무엇이 기억으로 굳었는지는 목록을 직접 훑어야 알 수 있다.

기억이 상속된다는 점이 여기에 겹친다.
워크스페이스 층의 기억은 그 아래 모든 공개 채널로 내려가므로,
한 채널의 맥락이 다른 채널의 답변 근거가 될 수 있는 경로가 구조적으로 존재한다.
채널 경계를 지킨다는 문장과 상위 층 기억을 상속한다는 문장이 같은 문서에 있고,
둘이 만나는 지점에서 실제 범위가 정해지는데 그 지점이 명시되어 있지 않다.

### 감사 로그가 행위는 남기고 근거는 남기지 않는다

감사 화면은 꽤 충실하다.
조직 전체의 예약 작업과 일회성 작업이 모이고, Agent Identity로 나간 네트워크 호출까지 기록되며,
커밋과 풀 리퀘스트에서 Slack 스레드로 돌아가는 링크가 붙는다.
사고가 났을 때 무엇이 일어났는지 되짚기에 충분한 구성이다.

빠진 축은 왜다.
어떤 작업이 어떤 기억과 어떤 채널 맥락을 근거로 그 판단에 이르렀는지는 기록되지 않는다.
Claude가 잘못된 값을 쓴 경우, 그 값이 어느 스레드에서 왔는지 알아야 같은 실수를 막을 수 있는데
감사 화면은 행위의 목록이지 근거의 목록이 아니다.

두 축을 다 갖는 것이 쉬운 일은 아니다.
근거까지 남기려면 모델이 참조한 기억 조각을 매번 기록해야 하고, 그 자체가 새로운 민감 데이터 저장소가 된다.
현재 구성에서 실무적으로 가능한 보완은 기억 열람 화면과 감사 화면을 함께 보는 습관이며,
그 둘을 잇는 것은 제품이 아니라 운영하는 사람이다.

## 함정

### 이행이 이미 일어났고 문서가 그 사실만 알린다

Claude in Slack은 2026년 8월 3일에 전환되었다.
이 문서는 8월 21일자이며 전환을 안내가 아니라 완료된 사실로 적는다.
아직 옮기지 않았다면 이행 안내 문서로 가라는 링크만 있다.

실무적으로 확인할 것은 전환 이후 무엇이 달라졌느냐다.
새 제품은 자기 정체성으로 동작하고, 기억을 유지하고, 스스로 후속 작업을 예약한다.
이전 앱에는 없던 성질이므로, 같은 채널에 같은 방식으로 두면 동작 범위가 넓어진 상태로 계속 돌아간다.
전환이 자동으로 이루어진 조직이라면 기존 채널 목록과 권한을 다시 훑어야 한다.

### 설정 권한이 Admin에게 없다

문서가 별도 경고로 적어 둔 항목이다.
Claude Tag의 접근과 채널을 설정할 수 있는 것은 Primary Owner와 Owner뿐이고 Admin 역할은 할 수 없다.

큰 조직에서 이것이 병목이 된다.
Slack의 Owner는 대개 소수이고 일상 운영에서 멀리 있는 경우가 많은데,
채널을 추가하거나 도구 연결을 바꾸는 일이 전부 그 소수를 거쳐야 한다.
도입 전에 누가 Owner인지 확인하고, 그 사람이 설정 변경 요청을 처리할 수 있는지 정해 두지 않으면
설정이 필요한 시점마다 대기가 생긴다.

### 역할 기반 접근이 Enterprise 전용이다

Member Access의 세 번째 모드, 즉 역할이 허용한 구성원만 쓰게 하는 설정은 Claude Enterprise 요금제에서만 제공된다.

Team 요금제에서는 선택지가 둘뿐이다.
Slack 워크스페이스의 누구나, 또는 Claude 조직의 구성원 전체다.
두 값 모두 사실상 전원 허용에 가까우므로, Team 요금제에서는 사용자 단위 제한이 없다고 보는 편이 정확하다.
제한이 필요하면 사용자 축이 아니라 채널 축으로 걸어야 하며, 그것이 이 요금제에서 쓸 수 있는 유일한 경계다.

### 게스트 설정을 열면 되돌릴 때 이미 늦다

게스트 채널 설정의 기본값은 차단이고, 그것이 안전한 기본이다.
문제는 Allow로 바꾼 뒤다.
Claude가 그 채널에서 전체 접근 권한으로 동작하면서 쌓은 기억은 설정을 되돌려도 남는다.
문서는 관리자가 기억을 삭제할 수 있다고 적지만, 무엇이 언제 들어갔는지는 별도로 추적해야 한다.

Channel only라는 중간값이 있는 이유가 여기에 있다.
게스트가 있는 동안에는 채널 한정 접근으로 낮춰 동작하므로,
외부인이 드나드는 채널에서는 Allow보다 이쪽이 기본 선택이 되어야 한다.

## 체크리스트

- Primary Owner 또는 Owner가 누구인지 확인했고, 그 사람이 설정 변경 요청을 처리할 수 있는가
- 조직 전체 층에 붙인 자격 증명과 저장소 목록을 적어 두었고, 그것이 모든 공개 채널로 내려간다는 점을 검토했는가
- 조직 전체 지출 한도를 정했고, 그 값을 넘겼을 때 업무가 멈춰도 되는지 합의했는가
- 새 채널이 물려받는 기본 한도를 확인했는가
- 75%와 95% 알림을 받을 관리자가 지정되어 있고 그 사람이 대응할 수 있는가
- 게스트가 포함된 채널의 설정이 Restrict 또는 Channel only인가
- Team 요금제라면 사용자 단위 제한이 불가능하다는 점을 전제로 채널 범위를 정했는가
- 채널별 기억을 주기적으로 검토할 담당과 주기를 정했는가
- 감사 화면을 확인하는 주기를 정했고, 예약 작업 목록을 점검하는 절차가 있는가
- 각 채널에서 `@Claude` 에게 걸려 있는 트리거를 물어 standing work를 확인했는가
- 다이렉트 메시지 사용이 조직 감사에 잡히지 않는다는 점을 관련자에게 알렸는가

## 기억할 원칙

### 상속되는 권한 모델에서는 최상위 층이 실질적인 정책이다

조직 전체에서 워크스페이스로, 워크스페이스에서 비공개 채널로 내려오는 구조에서
실제 접근 범위를 정하는 것은 가장 위에 무엇이 붙어 있느냐다.
아래 층은 더할 수만 있고 뺄 수 없으므로, 위에 붙인 것은 어디서든 쓸 수 있다고 보아야 한다.

이 성질은 이 제품에만 있는 것이 아니다.
디렉터리 서비스의 그룹 상속, 클라우드의 조직 단위 정책, 저장소의 조직 수준 시크릿이 모두 같은 모양이고,
같은 실수가 반복된다.
편의를 위해 상위에 붙인 자격 증명이 몇 달 뒤 아무도 기억하지 못하는 채널에서 쓰이는 것이다.

그래서 실천은 단순하다.
상위 층은 비워 두는 것을 기본으로 삼고, 무언가를 올릴 때마다 그것이 모든 하위에 내려간다는 사실을 문장으로 적어 남긴다.
그리고 그 목록을 정기 점검 항목에 넣는다.
권한을 뺄 수 없는 구조에서는 붙이는 순간의 판단이 유일한 통제 지점이다.

### 사용량 기반 과금에서는 거절이 잘림보다 안전하다

이 제품이 한도 초과 시 작업을 거절하고 조용히 자르지 않는다고 명시한 것은 작은 문장이지만 운영 방식을 바꾼다.
부분 결과가 남지 않으므로 한도를 낮게 잡는 비용이 거의 없고, 증액 경로가 제품 안에 있으므로 되돌리기도 쉽다.

반대 설계를 떠올리면 차이가 분명하다.
한도에 걸렸을 때 진행 중이던 작업이 중간에 끊기면, 반쯤 만들어진 결과물이 어디까지 믿을 수 있는지 판단해야 하고
그 판단 비용이 절약한 금액보다 클 때가 많다.
그래서 사용량 기반 도구를 도입할 때 확인해야 할 항목이 정해진다.
한도에 도달하면 무엇이 일어나는지, 그리고 그 동작이 거절인지 중단인지다.

거절이 기본인 도구에서는 낮게 시작해 올리는 것이 옳고,
중단이 기본인 도구에서는 여유 있게 잡고 알림으로 관리하는 것이 옳다.
같은 예산 관리라도 실패 동작에 따라 정반대의 전략이 나온다.
