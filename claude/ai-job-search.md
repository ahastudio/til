# AI Job Search: Claude Code로 돌리는 공고 평가부터 면접 준비까지의 구직 파이프라인

<https://github.com/MadsLorentzen/ai-job-search>

Show HN: [AI-powered job application framework built on Claude Code](https://news.ycombinator.com/item?id=48847930) (2점, 0개 댓글)

## 소개

AI Job Search는 Claude Code 위에 만든 구직 지원 프레임워크다.
저장소 설명은 내 컴퓨터에서 돌아가는 구직이라는 문구로 시작하고, 채용 공고 평가,
이력서 맞춤화, 커버레터 작성, 면접 준비를 한데 묶었다고 소개한다.
사용자는 저장소를 내려받아 프로필을 채우고,
Claude Code 안에서 슬래시 명령으로 공고를 찾고 평가하고 지원서를 만든다.
MIT 라이선스이고 주 언어는 Python이며, 2026년 3월 18일에 만들어졌다.
2026년 10월 11일 기준으로 별 45,853개, 포크 15,871개를 받았고,
마지막 push는 10월 8일이다.

저자 Mads Lorentzen은 README에서 자신을 지구물리학자로 소개한다.
2025년 말 자리가 없어지자 자기 구직을 위해 이 프레임워크를 만들었고,
저장소에 있는 `/scrape`, `/apply`, `/interview` 흐름을 매주 직접 썼다고 적는다.
맞춤 지원서 69건, 1차 면접 20건, 계약 1건을 거쳐
2026년 6월 AI 엔지니어로 입사했다는 것이 README가 내세우는 근거다.
저자는 만나는 모든 고용주에게 이 도구를 쓴다고 미리 밝혔고,
그것이 불리하게 작용하기보다 대개 기술적인 대화로 이어졌다고 쓴다.
이 수치는 README의 자기 보고이며,
더 긴 지원 깔때기는 LinkedIn 글에 있다고 안내한다.

README 첫머리에는 Anthropic과 관계없는 독립 프로젝트라는 고지와 함께,
이 프로젝트와 연결된 암호화폐나 토큰,
유료 후원 프로그램은 없으니 그런 주장은 사기로 보라는 경고가 붙어 있다.
후원 경로는 Ko-fi 링크와 GitHub 기여뿐이라고 밝힌다.
별이 수만 개로 불어난 저장소를 사칭하는 시도가 있었음을 짐작하게 하는 대목이다.

## 동작 방식

### 전체 흐름

핵심은 세 명령이다.
`/setup`으로 프로필을 채우고, `/scrape`로 채용 포털을 검색하고,
`/apply <url>`로 한 공고에 대한 평가와 지원서를 만든다.
여기에 `/rank`, `/interview`, `/outcome`, `/expand`, `/upskill`, `/html-report`,
`/notion-sync`, `/gmail-sync`, `/add-template`, `/add-portal`,
`/reset`이 붙는다.
`CONTRIBUTING.md`는 `/setup` → `/scrape` → `/rank` → `/apply` → `/interview` →
`/outcome` → 다시 `/setup`의 보정으로 이어지는 생애 주기가 기능적으로
완성되었다고 선언하고, 새 명령에는 높은 기준을 적용한다고 밝힌다.

코드보다 마크다운이 본체라는 점이 특징이다.
명령은 `.claude/commands/*.md`,
지원서 작성 지식은 `.claude/skills/job-application-assistant/` 아래 `01`부터
`09`까지의 문서, 검색 조율은 `.claude/skills/job-scraper/SKILL.md`에 들어 있다.
`CONTRIBUTING.md`는 마크다운 명세가 곧 구현이라고 적는다.
Python과 TypeScript 코드는 포털 CLI, PDF 검증, 중복 제거 키 계산,
`robots.txt` 판정처럼 결정적으로 처리해야 하는 부분만 맡는다.

프로필은 여러 파일에 나뉜다.
루트 `CLAUDE.md`에 이름, 연락처, 학력, 경력, 기술, 행동 성향, 목표 업종,
절대 조건(deal-breaker)이 들어가고,
`01-candidate-profile.md`에 구조화한 이력서 데이터,
`02-behavioral-profile.md`에 PI나 DISC 같은 행동 평가 결과,
`07-interview-prep.md`에 STAR 사례가 들어간다.
`AGENTS.md`는 Codex, Antigravity,
Gemini CLI 같은 다른 에이전트가 같은 파일을 읽도록 가리키는 얇은
포인터 역할만 한다.

### `/scrape`와 포털 스킬

`/scrape`는 `.agents/skills/*/SKILL.md`를 모두 읽어 설치된 포털 CLI를 찾는다.
각 포털 스킬은 `search`와 `detail` 명령, `--format json|table|plain` 출력,
`enabled:` 플래그를 갖춘 독립 폴더이며,
이 계약만 지키면 등록 없이 자동으로 쓰인다.
기본으로 상위 세 개 검색 범주를 돌리고, 최근 14일로 범위를 좁히며,
호출당 약 20건으로 결과를 자른다.
`bun`이 없거나 CLI가 실패하면 WebSearch로 대체하고,
어떤 포털이 대체 경로로 돌았는지 결과 요약에 따로 적는다.

결과는 `tools/job_key.py`가 계산한 정규 키로 `seen_jobs.json`에 기록하고,
지원 추적용 `job_search_tracker.csv`와 대조해 이미 본 공고와 이미
지원한 공고를 뺀다.
같은 내용의 공고가 도시만 바꿔 여러 번 올라오면 한 줄로 합치고 대량 게시 신호로
표시하되, 고용주를 사기로 단정하지 말라는 규칙이 붙어 있다.
적합도가 높거나 중간인 공고에는 LinkedIn 사람 검색 링크 두 개를 만들어 주는데,
검색 결과 페이지를 자동으로 긁지는 않고 링크만 건넨다.

포털 파서는 조용히 망가진다는 전제로 건강 검사도 한다.
회사명이 모두 비었거나 HTML 조각이 제목에 섞이면 반쯤 망가진 것으로,
이전에는 결과를 내던 포털이 0건을 내면 의심 대상으로 본다.
의심 포털에는 탐침 검색을 한 번, 재시도를 한 번만 하며,
429나 차단 페이지는 고장의 증거로 치지 않는다.

### `/apply`의 작성자와 검토자

`/apply`는 작성자 에이전트와 검토자 에이전트를 나눈다.
흐름은 다음과 같다.

1. 공고를 가져온다. WebFetch가 403을 받으면 `robots.txt` 확인 뒤 브라우저 헤더로
   재시도하고, 그래도 안 되면 고용주의 자체 채용 페이지를 찾는다.
2. 공고 URL의 호스트를 설치된 포털, Greenhouse나 Lever 같은 여섯 개 ATS 도메인,
   미확인 호스트 중 하나로 분류한다.
3. `04-job-evaluation.md`의 틀로 적합도를 평가한 뒤, 계속할지 사용자에게 묻는다.
4. 승인하면 LaTeX로 이력서와 커버레터 초안을 쓴다.
5. 새 문맥의 검토자 에이전트를 띄워 회사를 조사하고 초안을 비평하게 한다.
6. 검토 의견을 반영하고, PDF를 컴파일해 눈으로 확인하며 다듬는다.
7. 이력서 PDF의 텍스트 층을 추출해 ATS가 읽는 모습을 확인한다.
8. 검증 체크리스트와 함께 결과를 보여 주고, 추적 CSV에 `drafted`로 기록한다.

평가는 두 관문과 다섯 차원으로 이루어진다.
자격 관문은 시민권이나 영주권 요구를 공고 문구 그대로 확인해 실패하면 점수도
매기지 않고 초안도 쓰지 않는다.
언어 관문은 프로필의 언어 표에 아예 없는 언어를 요구하면 탈락시키고,
선언한 언어라도 요구 수준이 더 높아 보이면 탈락 대신 표시만 해서 판단을
사용자에게 넘긴다.
점수는 기술 일치, 경력 일치, 행동과 문화 적합, 위치와 이동 조건,
경력 방향과 동기의 다섯 차원으로 매긴다.

검토자에게는 초안을 파일 경로가 아니라 프롬프트 안에 그대로 넘긴다.
README는 이것을 토큰 절약 장치로 설명하면서,
컴파일과 확인 단계가 그 절약분 일부를 다시 쓴다고 인정한다.
검토자는 수정안을 `old_string`과 `new_string`을 가진 JSON 배열로 돌려주고,
작성자는 이것을 다시 읽지 않고 바로 적용한다.

사실 검증은 세 출처의 합집합에 기댄다.
`01-candidate-profile.md`, 마스터 이력서 `cv/main_example.tex`,
`CLAUDE.md`의 프로필 절 중 어디에도 근거가 없는 날짜, 직함, 수치는 지운다.
그래서 `/apply`는 사용자가 대화 중에 새 사실을 말하면 같은 턴에
`01-candidate-profile.md`에 써 넣으라고 지시한다.
대화에만 남은 사실은 다음 세션에서 근거 없는 주장으로 취급되어 이력서에서 조용히
사라지기 때문이다.

### PDF와 ATS 검증

이력서는 moderncv의 banking 스타일을 `lualatex`로,
커버레터는 `fontspec`이 필요한 자체 `cover.cls`를 `xelatex`로 컴파일한다.
이력서는 정확히 2쪽, 커버레터는 정확히 1쪽이어야 한다.
`tools/verify_pdf.py`가 쪽수를 재고,
`tools/verify_layout.py`가 100pt가 넘는 빈칸, 일찍 끝난 페이지,
쪽 끝에 홀로 남은 항목 제목을 잡는다.
moderncv의 `\cventry`는 표로 그려져 쪼개지지 않으므로,
공간이 모자라면 항목 전체가 다음 쪽으로 넘어가며 구멍을 남긴다는 설명도 있다.
2쪽을 넘으면 오래된 항목부터 자르지 않고, 공고 관련성, 문서 안의 고유성,
커버레터가 의존하는지를 합친 점수가 가장 낮은 줄부터 자른다.

ATS 검사는 렌더링된 페이지가 아니라 PDF에 들어 있는 텍스트 층을 본다.
pypdf나 Poppler `pdftotext`로 텍스트를 뽑아 `(cid:NNN)` 표식이나 깨진 문자가
없는지, 이메일과 전화번호가 아이콘이 아닌 글자로 남았는지,
읽는 순서가 맞는지 확인한다.
`--ascii-dates`는 연도에 붙은 유니코드 대시를 찾는데,
LaTeX가 `--`로 만든 en-dash 때문에 Workday 가져오기에서 날짜가 통째로 빠진
사례가 근거로 적혀 있다.
그다음 공고의 키워드를 포함, 동의어만 있음, 빠졌지만 실제로 가진 기술,
진짜 공백으로 나누고, 진짜 공백은 채워 넣지 않는다.

### 지원 이후

`/outcome`은 면접 단계, 합격, 불합격, 무응답을 기록하고 제출한 이력서, 커버레터,
공고 원문을 `documents/applications/<company>_<role>/`에 보관한다.
10일 넘게 소식이 없는 지원에는 후속 메일 초안을 쓰지만 보내지는 않으며,
지원 한 건에 두 번까지로 제한한다.
`/gmail-sync`는 Gmail 커넥터로 면접 초대나 불합격 메일을 읽어 변경을 제안하고,
사용자가 승인한 뒤에만 추적 파일에 쓴다.
`/notion-sync`는 Notion 데이터베이스로 한 방향 읽기 전용 보기를 내보내며,
문서는 파일 이름만 보낸다.
`/interview`는 실제로 제출한 이력서와 공고,
이전 면접의 피드백으로 단계별 준비 자료를 만들고,
경험이 없는 부분은 지어내지 말고 정직한 연결 답변을 쓰라고 한다.

## 설정하기

아래 명령은 README와 `SETUP.md`에 적힌 순서이며,
이 글을 쓰면서 직접 실행해 보지는 않았다.
필요한 것은 Claude Code, Python 3.10 이상, 포털 CLI용 Bun,
`lualatex`와 `xelatex`가 들어 있는 LaTeX 배포판이다.
README는 Claude Code에 무료 요금제가 없으므로 Pro, Max,
Team 구독이나 API 크레딧이 필요하고,
가끔 쓰면 API 종량제가 대개 더 싸다고 적는다.
ATS 검사를 기계적으로 하려면 `pip install pypdf`를 더한다.

README의 첫 단계는 `gh repo fork --clone`이지만,
바로 아래에 공개 저장소의 포크는 항상 공개이고 `/setup`이 개인정보를 추적되는
파일에 쓴다는 경고가 붙어 있다.
자기 구직용이라면 포크 대신 비공개 저장소를 만들고 원본을 `upstream`으로 두라는
것이 문서의 권고다.

```bash
# 원본을 받아 비공개 원격으로 옮기는 흐름 (SETUP.md 8절의 권고를 따른 예)
git clone https://github.com/MadsLorentzen/ai-job-search.git
cd ai-job-search
git remote rename origin upstream          # 업데이트는 원본에서 받는다
git remote add origin git@github.com:<me>/ai-job-search-private.git  # 비공개 저장소

# 포털 CLI 의존성 설치
for tool in jobbank-search jobdanmark-search jobindex-search jobnet-search linkedin-search freehire-search; do
  (cd .agents/skills/$tool/cli && bun install)
done

claude    # Claude Code 실행 뒤 /setup
```

`/setup`은 세 경로를 고른다.
`documents/` 폴더에 이력서 PDF, LinkedIn 내보내기, 학위증, 추천서,
과거 지원서를 넣어 두면 그것을 읽고,
이력서 하나를 대화창에 붙여 넣으면 그것을 가져오며,
둘 다 없으면 인터뷰로 채운다.
검색 설정만 다시 하려면 `/setup --section search`를 쓴다.
그다음 `/scrape`로 검색하고, 결과가 많으면 `/rank`로 일괄 채점한 뒤,
고른 공고에 `/apply <url>`을 실행한다.
URL을 가져올 수 없으면 공고 본문을 그대로 붙여 넣어도 된다.

덴마크 밖에서 쓴다면 `/add-portal`에 지역 채용 사이트 URL을 주어 포털
스킬을 생성한다.
이 명령은 검색 URL 패턴과 결과 구조,
`robots.txt`와 약관을 조사해 같은 계약의 CLI를 만들고,
실제 검색을 한 번 돌려 본 뒤 등록한다.
로그인이 필요한 포털은 거절하고,
약관이 자동 접근을 막는 포털에는 개인 용도 한정 경고를 넣는다.

## 트레이드오프

### 내 컴퓨터에서 돌지만 오프라인은 아니다

저장소의 표어는 내 컴퓨터에서 돌아가는 구직이고,
`SECURITY.md`는 문서가 설계상 기기를 떠나지 않는다고 적는다.
이 말은 저장소가 따로 서버를 두지 않고 문서 내용을 다른 서비스에 올리지 않는다는
뜻으로 읽어야 한다.
Claude Code는 읽은 파일 내용을 모델에 보내 처리하므로, 이력서, 행동 평가 결과,
연봉 기대치, 지원 이력은 작업할 때마다 모델 API를 거친다.
이 부분은 Claude Code의 작동 방식에서 나온 해석이며,
저장소 문서가 직접 다루지는 않는다.
`/gmail-sync`는 받은 편지함을,
`/notion-sync`는 파이프라인 목록을 각 커넥터로 오가게 하고,
동봉된 `gemini-research-expert` 에이전트는 Gemini CLI에 조사 프롬프트를 넘긴다.

로컬 파일 쪽에도 경계선이 있다.
`.gitignore`는 추적 CSV, 연봉 데이터, `documents/` 하위 내용, 지원서 결과물,
회사 조사 캐시, 사진, `.env`를 제외한다.
그러나 `/setup`이 채우는 `CLAUDE.md`와 `01-candidate-profile.md` 같은 프로필
파일은 추적 대상이다.
업스트림 업데이트를 3방향 병합으로 받으려면 이 파일들이 git 안에
있어야 하기 때문이다.
결국 프로필을 git에 두는 편리함과 프로필이 원격에 올라갈 위험을 맞바꾼 구조이며,
안전은 사용자가 포크 대신 비공개 저장소를 쓰느냐에 달려 있다.

### 덴마크에서 출발한 포털 구성

README는 평가와 작성 흐름은 언어와 나라에 묶이지 않지만,
포털 검색 스킬은 덴마크 시장용이라고 밝힌다.
Jobindex, Jobnet, Akademikernes Jobbank, Jobdanmark의 네 CLI가 그 예다.
다만 현재 이 네 포털은 `enabled: false`로 나오고,
`/setup`이 시장을 덴마크로 고를 때만 켠다.
기본으로 켜진 것은 LinkedIn의 비로그인 `jobs-guest` 엔드포인트를 쓰는
`linkedin-search`와, freehire.me의 공개 REST API를 쓰는 `freehire-search`다.

그래서 덴마크 밖의 사용자는 처음부터 LinkedIn 의존도가 높다.
지역 포털을 원하면 `/add-portal`로 직접 만들거나 커뮤니티 포크에서
폴더를 복사해야 한다.
`CONTRIBUTING.md`는 인도, 프랑스, 중국 포털 PR을 거절한 사례를 들며,
한 나라의 포털을 받으면 모든 나라의 포털을 받아야 하므로 시장별 스킬은 포크에
둔다고 설명한다.
GeekNews에는 사람인, 원티드, 점핏을 수집하면서
이런 해외 도구에 없는 한국 포털 지원을 내세운 별도 프로젝트가 Show GN으로
올라온 적이 있다.
업스트림이 지역 포털을 받지 않는 정책이 이런 갈래를 낳는 것으로 보인다.

포크의 포털 스킬을 복사해 쓰는 일은 공급망 문제이기도 하다.
`.claude/settings.json`은 포털 CLI 실행을 매번 묻지 않도록 허용 목록에 올려
두므로, 복사한 CLI는 사용자의 경력 데이터가 있는 디렉터리에서 확인 없이 돈다.
README가 코드를 전부 읽고,
`package.json`에 의존성과 `postinstall` 같은 생명 주기 스크립트가 없는지 보고,
네트워크 없이 테스트를 돌려 보라고 요구하는 이유다.
자동 설치 도구를 일부러 만들지 않았다는 설명도 같은 맥락이다.

### 스크레이핑과 포털 약관

LinkedIn 스킬의 `SKILL.md`는 자동 접근이 LinkedIn 서비스 약관에 어긋난다고
분명히 적고, 개인 용도로만 적은 양을 쓰라고 경고한다.
즉 기본으로 켜진 포털 하나가 약관 위반을 전제로 동작한다.
프레임워크는 이것을 숨기지 않고 사용자 책임으로 넘기는 쪽을 택했다.

대신 접근 예절은 꼼꼼하게 정해 두었다.
포털 CLI는 `Mozilla/5.0 (compatible; jobindex-cli/1.0)`처럼 도구 이름을 밝힌
User-Agent를 쓰고 브라우저를 흉내 내지 않는다.
429와 5xx에는 지수 백오프로 물러나고, CI는 실제 포털에 요청을 보내지 않는다.
브라우저 헤더로 재시도하는 경로는 `tools/robots_check.py`를 먼저 통과해야
하는데, 이 도구는 `*`이나 `Claude-User`에 대한 Disallow가 있으면 재시도를 막고,
`robots.txt`를 읽지 못하면 허락이 확인되지 않은 것으로 본다.
Python 표준 `urllib.robotparser`가 빈 줄에서 규칙 묶음을 끝내 Barclays 같은 실제
파일을 전부 허용으로 읽는다는 이유로 직접 구현했다는 설명도 붙어 있다.

남는 문제는 `robots.txt`와 약관이 다르다는 점이다.
`robots.txt`가 허용해도 약관은 자동 수집을 금지할 수 있고,
검사 도구는 앞의 것만 기계적으로 판정한다.
`/add-portal`은 약관 제한을 사용자에게 알리고 판단을 넘기지만,
그 판단이 맞는지는 결국 사람이 약관을 읽어야 안다.

### 채용 측 AI 필터와의 관계

이 프레임워크는 지원자 쪽 자동화가 채용 쪽 자동화를 상대하는 구도 위에 서 있다.
ATS 텍스트 층 검사와 키워드 범위 표는 기계가 읽는 이력서를 전제로 하고,
공고의 정확한 용어를 섹션 제목에까지 쓰라는 지시도 있다.
문체 지침이 em-dash를 금지하고 상투적인 표현 목록을 지우게 하는 것도,
AI가 쓴 글의 흔한 표지를 없애는 효과를 낸다.
이것은 해석이며, 저장소는 em-dash 금지의 이유를 AI 탐지와 연결하지 않는다.

반대 방향의 제동도 있다.
진짜 공백인 키워드는 채우지 않고,
면접에서 말을 바꿔야 할 정도의 각색은 사용자에게 다시 묻게 한다.
69건 지원에 1차 면접 20건이라는 저자의 수치는 이 정직성 규칙이 서류 통과율을
크게 떨어뜨리지 않았다는 한 사례로 읽을 수 있지만,
비교 대상이 없는 한 사람의 기록이다.
지원자 모두가 같은 도구로 맞춤 지원서를 대량으로 만들면 맞춤화 자체의 신호
가치가 줄어든다는 점은 저장소가 다루지 않는 2차 효과다.

### 도구 사용을 밝히는 태도

저자는 모든 고용주에게 이 도구를 쓴다고 밝혔다고 말한다.
프로필 템플릿 `CLAUDE.md`에도 이력서나 커버레터에서 에이전트형 코딩이나 AI
도구를 언급할 때는 Claude Code를 이름으로 밝히라는 규칙이 있다.
저자에게 이 공개는 약점을 숨기지 않는 것이 아니라 AI 엔지니어 직무에
맞는 포트폴리오였다.
지구물리학자에서 AI 엔지니어로 옮긴 경로에서는 도구 자체가 실력의
증거가 된 셈이다.

이 태도가 모든 직군에 옮겨지는지는 따로 따져야 한다.
AI 활용이 직무와 무관하거나 채용 측이 AI 작성 지원서를 감점하는 곳이라면,
같은 공개가 대화의 계기가 아니라 감점 사유가 될 수 있다.
저자의 경험은 AI 직무로 옮겨 간 한 사람의 사례로 보는 편이 안전하다.

## 함정

### 포크와 `gh` 기본 저장소

포크는 비공개로 바꿀 수 없으므로, 프로필 커밋을 포크에 push하면 누구나 본다.
1.7.0 변경 기록에는 더 미묘한 사고가 적혀 있다.
`gh repo fork --clone`은 업스트림 저장소를 `gh`의 기본 저장소로 지정하므로,
지원 건마다 추적 이슈를 만드는 사용자 자동화가 개인 구직 데이터를 업스트림의
공개 이슈 트래커에 올렸다.
일주일에 두 사용자에게서 네 건이 나왔고, 사용자는 그 이슈를 지울 수 없었다.
지금 `SETUP.md`는 `gh repo set-default`를 포크 명령 바로 옆에 둔다.
`CONTRIBUTING.md`는 개인화된 포크의 PR이 기본 대상인 업스트림으로 실수로 들어온
사례도 한 주에 세 건 있었다고 적는다.

### 문서 사이의 어긋남

`SECURITY.md`는 채워진 프로필이 gitignore 대상이라고 적지만,
`.gitignore`와 `SETUP.md`를 보면 `CLAUDE.md`와 프로필 스킬 파일은 추적된다.
gitignore 대상은 추적 CSV, 연봉 데이터, `documents/`, 지원서 보관본 쪽이다.
보안 정책 문서만 읽고 프로필 파일이 안전하다고 믿으면 안 된다.

### 지시 수준의 방어는 샌드박스가 아니다

공고는 신뢰할 수 없는 입력으로 다룬다.
공고 안의 지시를 따르지 않고, 공고 본문에 있는 URL을 가져오지 않으며,
회사 조사는 공고 링크가 아니라 회사 이름 검색에서 시작한다.
`SECURITY.md` 스스로 이 방어는 지시 수준이라 샌드박스가 아니라고 밝히고,
허용 목록은 Bash 명령만 다스릴 뿐 WebFetch와 WebSearch에는 미치지
않는다고 적는다.
숨은 텍스트로 지원서 내용을 조작하려는 공고가 있다면 마지막 방어선은 제출 전에
사람이 읽는 것이다.

### 대화에서 말한 사실은 사라진다

세 출처 대조는 지어낸 경력을 막지만,
사용자가 지난주 대화에서 말한 진짜 성과와 지어낸 것을 구별하지 못한다.
`01-candidate-profile.md`에 기록되지 않은 사실은 다음 실행에서 근거 없는
주장으로 지워진다.
프로필 파일을 갱신하지 않고 대화로만 보완하면 이력서가 점점 얇아진다.

### 오래된 공고와 유령 공고

LinkedIn의 만료 공고 URL은 비슷한 다른 공고로 넘겨 주므로,
저장해 둔 링크가 어느새 다른 일자리를 가리킬 수 있다.
`detail`의 `isActive: false`가 이것을 잡지만,
`true`는 마감 배너가 없다는 뜻일 뿐 열려 있다는 보장이 아니다.
게시일을 저장하지 않던 시기에는 2024년 5월 13일자 freehire 공고가 133건 중 1위로
채점된 적이 있어, 지금은 `posted_date`를 따로 남긴다.

### 오래된 권한 파일

예전 버전은 `Bash(curl:*)`, `Bash(python:*)`,
`Bash(bun:*)`를 허용하는 `.claude/settings.local.json`을 커밋했다.
그 전에 받은 사본에는 이 파일이 남아 지금의 좁은 허용 목록 위에 계속 적용되므로,
`SETUP.md`는 지우거나 개인 설정만 남기라고 안내한다.

## 확인하기

아래는 저장소가 제공하는 검사 경로이며, 이 글을 쓰면서 실행하지는 않았다.

```bash
# CI와 같은 정적 검사 (네트워크 없이 돈다)
python3 tools/lint_skills.py
python3 tools/security_guards.py      # 허용 목록 확대, 생명 주기 스크립트, gitignore 약화 검사
python3 -m unittest discover -s tests

# 포털 CLI 하나의 오프라인 테스트와 실제 검색
(cd .agents/skills/linkedin-search/cli && bun run typecheck && bun test)
bun run .agents/skills/linkedin-search/cli/src/cli.ts search -q "data engineer" -l "Berlin, Germany" --jobage 7 --format table

# 특정 사이트에 브라우저 헤더 재시도가 허용되는지
python3 tools/robots_check.py 'https://example.com/careers/job/123'   # 0이면 허용, 1이면 금지

# 컴파일한 이력서의 쪽수와 텍스트 층
python tools/verify_pdf.py cv/main_<company>_<role>.pdf --pages 2 --ascii-dates --dump-text /tmp/cv.txt
python tools/verify_layout.py cv/main_<company>_<role>.pdf
```

개인정보 경계는 `git status`와 `git check-ignore -v <파일>`로 직접
확인하는 편이 확실하다.
`/setup` 뒤에 어떤 파일이 수정됨으로 잡히는지 보고,
원격이 포크인지 비공개 저장소인지는
`git remote -v`와 `gh repo set-default --view`로 확인한다.
CI는 LaTeX 예제 두 개를
TeX Live 최신판과 Debian bookworm 두 환경에서 컴파일하고,
템플릿 파일에 `[PLACEHOLDER]` 토큰이 남아 있는지 검사해 개인정보가 업스트림에
들어오는 것을 막는다.

## 기억할 원칙

### 에이전트 워크플로의 본체는 명세와 검증 도구다

이 저장소에서 모델이 하는 일은 마크다운 명세가 정하고,
모델이 틀리기 쉬운 부분은 Python 도구가 숫자로 판정한다.
쪽수, 빈칸 크기, 날짜의 대시 문자, 중복 제거 키,
`robots.txt` 판정처럼 결과가 하나로 정해져야 하는 일은 모델에 맡기지 않는다.
변경 기록의 상당 부분이 명세와 도구가 서로 어긋난 지점을 고치고,
그 어긋남을 다시 잡는 테스트를 더하는 내용이라는 점도 같은 방향을 가리킨다.

### 초안까지는 자동, 보내는 것은 사람

`/apply`는 초안을 쓰지만 제출하지 않고,
`/outcome`은 후속 메일을 쓰지만 보내지 않으며,
`/gmail-sync`는 변경을 제안하지만 승인 없이는 쓰지 않는다.
업스트림 감시 워크플로도 보고만 하고 병합하지 않는다.
돌이키기 어려운 행동, 곧 지원서 제출, 메일 발송, 기록 변경,
병합 앞에는 항상 사람의 확인이 있다.
구직처럼 실수의 비용을 지원자 혼자 지는 일에서 이 경계는 기능이 아니라 전제다.
