# Harness 100: 열 분야 100개의 에이전트 팀을 복사해 쓰도록 모아 둔 Claude Code 템플릿 모음

<https://github.com/revfactory/harness-100>

## 소개

Harness 100은 Claude Code용 에이전트 팀 100개를 분야별로 모아 둔 저장소입니다.
하네스 하나는 전문가 에이전트 4~5명과 팀을 지휘하는 오케스트레이터 스킬 1개,
에이전트의 지식을 보강하는 스킬 2~3개로 이루어진다고 README가 설명합니다.
한국어판(`ko/`)과 영어판(`en/`)이 같은 구성으로 따로 있고,
라이선스는 Apache-2.0입니다.
저장소는 2026년 3월 22일에 만들어졌고 별은 1,320개, 포크는 459개입니다.
이 문서는 README와 저장소 파일 일부(유튜브 제작, 보안 감사, 계약 분석,
식단 계획 하네스)를 읽어 정리한 것이고, 하네스를 실제로 실행해 본 결과가
아닙니다.

README의 집계는 저장소 파일 트리와 맞았습니다.
영어판 기준으로 에이전트 정의 파일이 489개, 스킬 파일이 315개,
하네스별 `CLAUDE.md`가 100개였습니다.
에이전트가 5명인 하네스가 89개, 4명인 하네스가 11개입니다.
스킬 315개에서 오케스트레이터 100개를 빼면 보강 스킬이 215개이므로
하네스당 평균 2.15개이고, README의 2~3개는 이 평균보다 넉넉한 표현입니다.

## 하네스 하나의 내부

각 하네스는 `.claude/` 폴더 하나로 완결됩니다.
`CLAUDE.md`가 개요를, `agents/`가 전문가 에이전트를, `skills/`가
오케스트레이터와 보강 스킬을 담습니다.
사용법은 폴더를 자기 프로젝트의 `.claude/`로 복사하는 것이 전부입니다.

```bash
cp -r en/01-youtube-production/.claude/ /path/to/my-project/.claude/
```

01번 유튜브 제작 하네스는 에이전트 다섯 명으로 팀을 짭니다.
콘텐츠 전략가, 대본 작가, 썸네일 디자이너, SEO 최적화 담당, 제작 검토자입니다.
오케스트레이터 스킬의 흐름은 세 단계입니다.
1단계는 오케스트레이터가 직접 입력을 정리해 `_workspace/00_input.md`에
저장합니다.
2단계는 전략을 먼저 만든 뒤 대본과 썸네일을 병렬로 진행하고,
그 결과로 SEO 패키지를 만들고, 마지막에 검토자가 교차 검증합니다.
3단계는 검토 보고서의 필수 수정 항목이 반영됐는지 확인하고 사용자에게
보고합니다.

오케스트레이터 스킬에는 모든 하네스에 공통인 절이 있습니다.
실행 모드, 에이전트 구성표, 요청 범위별 모드, 데이터 전달 방식, 오류 처리,
보강 스킬 목록, 시험 시나리오입니다.
요청 범위별 모드는 이미 있는 대본을 주면 전략과 작성 단계를 건너뛰고
SEO와 썸네일 담당만 투입하는 식입니다.
오류 처리는 에이전트가 실패하면 한 번 재시도하고, 그래도 실패하면 그 산출물
없이 진행하면서 검토 보고서에 빠졌다고 적는 방식입니다.
에이전트끼리는 `SendMessage`로 직접 소통하고, 산출물은 `_workspace/` 폴더의
번호가 붙은 파일로 주고받습니다.
검토자의 지적은 최대 두 번까지 수정을 요청하고 다시 검증합니다.

README는 모든 하네스가 지키는 품질 기준 여덟 가지를 나열합니다.
팀 모드와 교차 검증, 분야 지식(OWASP, 블룸의 교육목표 분류, 포터의 5 Forces 등),
구조화된 산출물, 의존성 그래프, 오류 처리, 규모별 모드, 시험 시나리오 세 종류,
스킬이 켜질 조건과 켜지지 않을 조건의 명시입니다.

## 분석

### 이 저장소가 파는 것은 팀 설계의 틀이다

100개의 분야는 달라도 오케스트레이터의 뼈대는 같습니다.
보안 감사, 계약 분석, 식단 계획 하네스의 오케스트레이터 절 제목을 읽어 보면
같은 순서로 같은 절이 반복됩니다.
이 반복은 결함이 아니라 설계입니다.
전문가 에이전트 몇 명, 의존성 순서, 병렬 구간, 검토자, 오류 처리, 범위별 축소
모드라는 틀을 고정하고 분야 지식만 갈아 끼우는 구조이기 때문입니다.

그래서 이 저장소의 쓰임새는 완성된 제품을 받는 것보다 출발 틀을 받는 데
가깝습니다.
같은 저자의 `revfactory/harness`가 도메인 설명으로 에이전트 팀을 새로 만들어
주는 메타 스킬이라면,[^harness] 이 저장소는 그 결과물 100개를 미리 만들어 둔
목록으로
읽힙니다. 두 저장소의 관계를 저장소가 직접 밝히지는 않으므로 이는 이 문서의
해석입니다.

### 검토자 에이전트는 모든 팀에 들어 있는 품질 장치다

에이전트가 5명인 하네스 89개에서 다섯 번째는 검토자나 QA입니다.
유튜브 하네스의 검토자는 전략과 대본과 썸네일과 SEO가 서로 일관된지 확인하고,
문제를 중요도로 나눠 담당 에이전트에게 수정을 요청합니다.
다른 에이전트의 산출물을 읽고 반박하는 역할을 팀마다 하나씩 따로 둔 점이
이 설계의 가장 일관된 선택입니다.

## 비평

### 영어판 일부는 읽을 수 없는 상태로 배포되어 있다

영어판 27~30번 하네스의 번역이 깨져 있다는 풀 리퀘스트가 2026년 6월 19일에
올라왔고 아직 열려 있습니다.[^pr4]
확인해 보니 영어판 28번 보안 감사 오케스트레이터는 지금도 제목이
`inthisbefore setup`이고 설명문도 단어가 붙고 일부가 빠진 상태입니다.
`ko/`와 `en/`이 같은 구성이라는 README의 첫 문장이 이 네 하네스에서는 영어판에
해당하지 않습니다.
저장소의 커밋은 API로 조회하면 하나뿐이고 마지막 푸시가 만든 날과 같은 3월
22일이어서,
이후 들어온 수정 제안 여섯 건 중 하나만 닫혔고 나머지 다섯 건은 열려 있습니다.
열린 건 가운데에는 하네스를 플러그인 마켓플레이스로 배포해 필요한 것만 설치하게
하자는 제안도 있습니다.[^pr5]
유지보수가 이어지는 저장소가 아니라 한 번 공개된 자료 모음으로 보는 편이
정확합니다.

### 시험 시나리오는 실행 결과가 아니라 기대치다

README는 모든 하네스가 시험 시나리오를 갖춘다고 적습니다.
유튜브 하네스의 시나리오는 정상 흐름, 기존 파일이 있는 흐름,
오류 흐름 세 가지이고,
각각 입력과 기대 결과를 문장으로 적어 둔 것입니다.
이 시나리오를 실제로 돌려 통과했다는 기록은 저장소에서 확인하지 못했습니다.
품질 기준 여덟 가지가 모든 하네스에 적용된다는 말은 문서의 구성 요소가
들어 있다는 뜻으로만 확인됩니다.

### 분야 지식의 정확도는 검증되지 않았다

법률, 세금, 건강, 규제 같은 분야의 하네스가 들어 있습니다.
README는 GDPR, BMR/TDEE, 특허 청구항 작성 패턴 같은 틀이 들어 있다고
적지만, 그 내용이 맞는지 점검했다는 설명은 없습니다.
이 문서도 그 내용의 정확성은 확인하지 않았습니다.
이런 분야에서는 에이전트 팀의 교차 검증이 같은 모델이 같은 지식으로 서로를
검토하는 구조이므로, 틀린 전제는 팀 전체가 공유합니다.

### 현재 실행 환경과 맞는지는 확인되지 않았다

오케스트레이터가 쓰는 도구는 `SendMessage`와 `TaskCreate`, `TaskUpdate`입니다.
같은 저자의 `revfactory/harness` README는 v1이 지금은 없는 실험용 `TeamCreate`
API에 기대고 있었고, v2에서 실행 모드를 다시 짰다고 설명합니다.[^harness]
Harness 100은 3월 22일 이후 바뀌지 않았으므로, 지금의 Claude Code에서 100개가
그대로 동작하는지는 이 문서가 시험하지 않았습니다.
스킬 파일 이름도 소문자 `skill.md`이고,
`revfactory/harness`의 README는 `SKILL.md`를 씁니다.[^harness]
소문자 파일명이 스킬로 인식되는지도 확인하지 않았습니다.

### 복사 한 줄이 기존 프로젝트의 설정과 겹친다

설치는 하네스의 `.claude/`를 프로젝트의 `.claude/`로 복사하는 한 줄입니다.
각 하네스는 자기 `CLAUDE.md`를 들고 있으므로,
이미 `CLAUDE.md`나 같은 이름의 에이전트가
있는 프로젝트에 복사하면 파일이 겹칩니다.
README는 기존 설정과 합치는 방법을 설명하지 않습니다.

## 인사이트

### 1. 가져다 쓰기 전에 하네스 하나를 읽고 줄인다

100개를 그대로 설치하기보다, 일하는 분야에서 하나를 골라 오케스트레이터와
에이전트 정의를 직접 읽고 자기 업무에 맞게 줄이는 것이 이 저장소를 쓰는
현실적인 방법입니다.
읽을 때 볼 곳은 의존성 표(누가 누구를 기다리는가), 병렬 구간,
검토자가 확인하는 항목, 오류 시 건너뛰는 규칙입니다.
이 네 가지가 팀 설계의 핵심이고 분야 지식은 그 위에 얹힌 내용입니다.

### 2. 검토자 에이전트를 자기 파이프라인의 최소 단위로 가져간다

하네스 전체를 쓰지 않더라도 이 구조에서 옮겨 쓸 만한 것은 마지막에 산출물끼리의
일관성을 점검하는 전담 에이전트입니다.
점검 항목을 표로 미리 적어 두고, 지적을 필수와 권장으로 나누며,
수정 요청은 두 번까지로 제한하는 세 가지가 구체적인 설계입니다.

### 3. 이 저장소에 대한 판단을 바꿀 관찰

시험 시나리오를 돌려 통과한 기록이나, 하네스를 쓴 경우와 쓰지 않은 경우의 산출물
비교가 공개되면 이 저장소는 템플릿 모음에서 검증된 자료로 올라섭니다.
깨진 영어판이 수정되어 합쳐지거나 현재 런타임에서의 동작 확인이 나와도 판단이
달라집니다.
반대로 같은 분야에서 한 줄짜리 요청이 100개 중 하나의 하네스를 쓴 결과보다
못하지 않다는 비교가 나오면 이 구조의 가치는 줄어듭니다.
