# Claude Code 모범 사례: 모델이 모르는 것을 알려 주고, 검사를 붙이고, 예외 없는 규칙은 강제한다

원문: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

HN 토론: <https://news.ycombinator.com/item?id=46714987> (4점, 1개 댓글)

## 소개

이 문서는 Claude Code의 공식 모범 사례 문서가 말하는 바를 정리한 것이다.
문서의 출발점은 새 세션에서 평범한 첫 프롬프트를 써도 대개 설정 없이 알맞게
동작한다는 선언이다.
터미널과 VS Code 세션은 위험한 동작을 분류기가 검토하는 자동(auto) 모드로
시작하고, 독립된 일은 하위 에이전트(subagent)에 넘기며,
대화가 길어지면 컨텍스트가 차기 전에 자동으로 압축된다고 한다.

그래서 이 문서가 다루는 것은 기본값으로 부족한 경우이다.
프로젝트에는 코드만 봐서는 알 수 없는 지식, 규칙, 제약이 있다.
누군가의 머릿속에만 있는 배포 절차, 절대 읽으면 안 되는 파일,
통과해야 끝으로 인정되는 검사, 넘으면 안 되는 예산이 그런 예이다.

문서는 세션이 기대와 다르게 흘러갈 때의 원인을 넷으로 나눈다.
첫째, 저장소에서 읽을 수 없는 정보가 빠져서 엉뚱한 것을 만들거나 매 세션 같은
사실을 다시 찾는다.
둘째, 자기 작업을 확인할 수단이 없어서 끝났다고 말하고 실제로는 아니다.
셋째, 절대 일어나면 안 되는 일이 일어나거나 항상 해야 하는 단계가 빠진다.
프롬프트만으로는 이를 보장할 수 없다.
넷째, 결과는 맞는데 일의 가치에 비해 시간, 토큰, 권한 확인이 너무 많이 들었다.
각각이 이 문서의 한 절에 대응하고, 무인 실행과 더는 필요 없는 조언이
뒤에 붙는다.

## 동작 방식

### 모든 지시는 결정적이거나 비결정적이다

문서의 뼈대는 지시를 둘로 가르는 것이다.
비결정적 지시는 사람이 쓰고 모델이 읽는 것으로, 프롬프트, `CLAUDE.md`,
스킬이 여기에 속한다.
모델이 따르는 편이지만 따른다는 보장은 없고,
하지 않기로 하거나 다른 것을 할 수도 있다.
결정적 지시는 사람이 설정하고 하네스(Claude Code)가 실행하는 것으로, 훅(hook),
거부(deny) 규칙, 관리형 설정이 여기에 속한다.
모델이 무엇을 결정했든 매번 적용된다.

| 영역             | 비결정적(모델이 결정)                            | 결정적(하네스가 강제)                               |
| ---------------- | ------------------------------------------------ | --------------------------------------------------- |
| 무엇을 할지      | 프롬프트, `CLAUDE.md`, 모델이 스스로 고르는 스킬 | 훅, 사람만 시작할 수 있는 스킬                      |
| 무엇을 건드릴지  | 자동 모드의 분류기                               | 거부 규칙, 엄격 모드의 샌드박스, 관리형 설정        |
| 언제 끝인지      | 증거 요청, `/goal`, `/code-review`               | 테스트, 타입 검사, `Stop` 훅, CI                    |
| 얼마나 쓸지      | 노력(effort) 수준, 모델의 속도                   | `--max-turns`, `--max-budget-usd`, 설정한 지출 한도 |
| 마지막 말은 누가 | 모델이 한 일의 요약                              | 브랜치 보호, 병합을 승인하는 사람                   |

문서는 대부분은 모델이 결정하게 두는 쪽이 낫다고 말한다.
거의 모든 지침에는 예외가 있고, 모델은 눈앞의 코드를 보고 지침이 맞는지 판단하는
데 능숙하기 때문이다.
결정적 지시는 무슨 일이 있어도 항상 일어나거나 절대 일어나면 안 되는 일을 위한
것이며, 흔히 그 프로젝트에 특화된 것이다.
“생성된 클라이언트 `src/gen/`은 절대 고치지 말 것”이나 “파일을 만들면 항상
라이선스 헤더 스크립트를 돌릴 것”이 그 예로 나온다.

문서의 실용 규칙은 둘이다.
`CLAUDE.md`의 한 줄에 강조를 계속 더하는데도 모델이 놓친다면 그 줄은
훅에 속한다.
반대로 단순한 선호에 훅을 걸어 두었다면 지우고 모델이 결정하게 해야 한다.

## 설정하기

### 보이지 않는 것만 적는다

모델은 작업을 시작할 때 코드를 읽고 파일 구조, 관례, 테스트 프레임워크,
기존 컴포넌트의 작성 방식을 대개 사람이 설명하는 것보다 빨리 찾는다.
그래서 적을 것은 저장소에 없던 정보뿐이다.
회의에서 내린 결정, 한 사람의 머릿속에 있는 배포 절차,
통합 테스트에 필요한 환경 변수가 그런 것이다.
저장소에 있지만 찾는 데 몇 분이 걸려 매 세션 되풀이되는 탐색도 여기에 든다.

적기 전의 시험은 두 질문이다.
코드를 읽어서 찾을 수 있는가, 실제로 찾으러 갈 것인가.
둘 다 그렇다면 적지 않는다.

### 구체적으로 요청한다

구체적인 프롬프트도 같은 이유로 효과가 있다.
파일 이름, 증상, “고쳐졌다”의 모습을 처음에 말하면 한 차례의 수정 왕복을 아낀다.
문서는 “로그인 버그를 고쳐”보다 증상, 볼 곳,
실패하는 테스트를 먼저 쓰게 하는 요청을 예로 든다.
이미 가진 것은 설명하지 말고 넘기라고 한다.
파일은 `@`와 경로로, 이미지는 붙여 넣기로, 명령 출력은 파이프로 넘긴다.

“차근차근 생각해”나 “철저히 해” 같은 문구는 키워드가 아니라 평범한 프롬프트
글이라고 문서는 말한다.
생각의 깊이를 정하는 주된 수단은 노력 수준이다.
다만 `be ambitious`는 아직 효과가 있다고 한다.
모델은 요청을 보수적으로 읽어 요건을 겨우 채우는 가장 작은 것을 만들기 쉬운데,
얼마나 큰 결과를 원하는지는 사용자만 알기 때문이다.
이것은 생각의 깊이가 아니라 범위를 알려 주는 말이다.

무엇을 원하는지 아직 모를 때는 모델에게 인터뷰를 시키라고 한다.
스펙을 쓸 수 있을 때까지 질문하게 하고 `SPEC.md`에 쓰게 한 뒤,
새 세션에서 그 파일로 만들기 시작한다.
깨끗한 컨텍스트와 글로 적힌 완료 기준이 생기고,
나중에 리뷰어에게 줄 파일도 된다.

### `CLAUDE.md`는 짧게 둔다

`CLAUDE.md`는 모든 세션에 로드되므로 모든 줄이 모든 작업에서 모델의 주의를
조금씩 쓴다.
문서가 권하는 내용은 네 가지이다.
저장소에서 작업을 확인하는 방법(테스트, 타입 검사,
린트 명령과 파일 하나만 돌리는 법), 코드가 오해를 부르는 곳(곳곳에 있지만 새
코드가 따라 하면 안 되는 옛 패턴), 저장소에 없는 결정, 두 번 고쳐 준 것이다.
문서는 `CLAUDE.md`가 짧게 유지되는 예로 명령, 관례,
주의점 세 묶음의 열 줄 안팎 파일을 보여 준다.

타입 검사 줄에는 명령만 적는다고 문서는 강조한다.
모델이 작업하면서 스스로 확인하려면 명령을 알아야 하기 때문이다.
통과를 강제하고 싶다면 그것은 `Stop` 훅의 일이고,
“끝내기 전에 항상 타입 검사”라는 줄은 대개는 통하지만 매번은 아니다.

시작은 `/init`이 만들어 준 초안에서 줄을 지우는 일이 대부분이고,
메모리 안내서는 200줄 아래를 권한다고 한다.
`/doctor`는 코드에서 알 수 있는 내용의 삭제를 제안하고,
`/doctor prompt-audit`은 옛 모델을 위해 쓴 지시, 없는 파일을 가리키는 지시,
서로 모순되는 지시를 표시한다.
개인 선호는 `CLAUDE.local.md`에 두고 `.gitignore`에 넣는다.

### 규칙은 해당 구역에만 적용한다

한 구역에서만 필요한 규칙은 `.claude/rules/`에 `paths:` 필터와 함께 둔다.
그러면 모델이 그 구역에서 일할 때만 로드된다.
문서의 예는 `src/api/**/*.ts`에 대해 요청 본문 검증 방식과 `openapi.yaml` 등록을
요구하는 규칙이다.

### 팀의 절차는 스킬에 둔다

더 유능한 모델도 이 팀이 릴리스를 어떻게 하는지,
장애 대응 절차가 무엇인지는 모른다.
그런 지식은 `.claude/skills/<이름>/SKILL.md`의 스킬에 둔다.
스킬은 모델이 스스로 시작할 수 있는 경우 이름과 설명만 매 세션 보이고 전체는
필요할 때 읽으므로 `CLAUDE.md`보다 컨텍스트가 가볍다.
`CLAUDE.md`의 원칙인 “찾을 수 없는 것만 적는다”는 스킬에도 적용된다.

부작용이 있는 절차는 `disable-model-invocation: true`를 붙여 모델이 스스로
시작하지 못하고 사람이 `/release`를 입력할 때만 돌게 한다.
문서의 예 스킬은 main과 깨끗한 작업 트리를 확인하고, 변경 로그를 쓰고,
태그를 붙이고, CI가 배포하게 하며 로컬에서는 절대 게시하지 않는다.

### 필요한 도구를 연결한다

다른 시스템에 있는 정보는 그 시스템의 CLI가 있으면 가장 쉽게 연결된다.
CLI가 없으면 MCP를 쓴다.
연결된 서버는 쓰지 않을 때도 도구 이름과 지시를 컨텍스트에 더하므로,
필요 없는 서버는 `/mcp`에서 끄라고 한다.
타입이 있는 언어라면 코드 인텔리전스 플러그인이 정의로 바로 건너뛰게 해 준다.

## 검사 붙이기

모델은 작업이 끝나 보이면 멈춘다.
끝났는지 알려 주는 실행 수단이 없으면 “끝나 보임”이 판단의 전부이고,
그러면 사람이 테스트 스위트가 되어 모든 실수가 눈치챌 때까지 남는다.
통과 또는 실패로 돌아오는 것을 주면 모델은 스스로 고치고 다시 돌리는
고리를 닫는다.

검사는 테스트 파일, 빌드의 종료 코드, 린터, 고정 출력과의 비교 스크립트,
목업 옆에 둔 브라우저 스크린샷처럼 모델이 결과를 읽을 수 있으면 무엇이든 된다.
엄격함은 모델이 스스로 판단하는 것에서 하네스가 강제하는 것까지 네 단계로
정할 수 있다.

| 단계                | 방법                                                                      | 누가 강제하는가               |
| ------------------- | ------------------------------------------------------------------------- | ----------------------------- |
| 프롬프트            | “인증 테스트를 돌리고 통과할 때까지 계속해”                               | 모델이 스스로 만족을 판단한다 |
| 목표                | `/goal`로 조건을 정하면 별도 모델이 매 턴 뒤 대화를 보고 확인한다         | 별도 모델                     |
| Stop 훅             | 모델이 턴을 끝내려 할 때 스크립트를 돌리고 종료 코드 2면 다시 일하게 한다 | 하네스                        |
| 코드를 쓰지 않은 쪽 | `/code-review`가 대화를 보지 못한 새 하위 에이전트로 diff를 본다          | 독립된 검토자                 |

어느 쪽이든 증거를 요구하라고 문서는 말한다.
실행한 명령과 출력, 또는 스크린샷이다.
“모든 테스트 통과”라는 말만으로는 알 수 있는 것이 거의 없고,
지켜보지 않은 세션에서는 증거가 유일한 단서이다.
끝났다고 한 뒤 `/verify`를 쓰면 앱을 빌드해 실행하고 결과를 보게 해서 테스트와
타입 검사가 놓치는 문제를 잡는다.

### 스펙으로 리뷰한다

일반적인 버그 사냥이 아니라 계획과 대조하는 리뷰를 원하면 리뷰
프롬프트를 직접 쓴다.
요구사항이 모두 구현되었고 나열한 경계 사례에 테스트가 있는지 보고,
정확성에 영향을 주는 빈틈만 알리고 스타일은 건너뛰게 한다.
`스타일은 건너뛰라`는 부분을 빼지 말라고 문서는 당부한다.
문제를 찾으라고 요청받은 리뷰어는 언제나 무언가를 찾고,
모든 지적을 고치면 불필요한 추상 계층과 일어날 수 없는 사례의 테스트가
쌓이기 때문이다.

### Stop 훅으로 강제한다

타입 검사 규칙을 `.claude/settings.json`에 몇 줄로 옮긴 것이 `Stop` 훅이다.

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" }
        ]
      }
    ]
  }
}
```

종료 코드 2가 멈춤을 막고, 표준 오류로 나온 내용이 아직 끝낼 수 없는 이유로
모델에게 돌아간다.
그래서 컴파일러 출력을 표준 오류로 돌린다.
훅이 도구 호출 없이 연속 여덟 번 막으면 Claude Code가 다음 막기를 무시하고 턴을
끝내며, 이 상한은 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`으로 올릴 수 있다고 한다.

## 강제하기

문서의 요점은 매번 일어나야 하는 일은 훅, 거부 규칙,
관리형 설정으로 만들라는 것이다.
`CLAUDE.md`는 지침을 위한 것이고, 모델은 지침이 해당하지 않는다고
판단할 수 있다.
“`.env`를 읽지 마라”, “편집 뒤 항상 포매터를 돌려라”,
“마이그레이션 폴더는 건드리지 마라” 같은 규칙은 모델이 거의 항상 따르지만,
“거의”로 부족하면 하네스가 적용하는 설정으로 옮긴다.

### 훅으로 단계를 강제한다

훅은 도구 호출 전후, 모델이 멈추려 할 때,
세션이 시작될 때 같은 고정된 지점에서 사용자의 것을 실행한다.
셸 명령(가장 흔함), HTTP 엔드포인트로의 POST, MCP 서버의 도구 호출,
모델이 판단하게 하는 `prompt` 또는 `agent` 훅이 있다.
`prompt`나 `agent` 훅은 다른 모델이 결정하므로 결정적이지 않고,
진짜 강제에는 `command`나 `http` 훅을 써야 한다.
훅 자체가 죽거나 시간 초과일 때도 행동을 막아야 한다면 `onFailure:
“block”`을 더한다.
커밋에서 비밀 값을 검사하는 훅이라면 검사기가 죽었을 때 검사 없이 통과시키느니
커밋을 막는 편이 낫기 때문이다.

포매터 규칙은 `PostToolUse` 훅이 된다.
`Edit`이나 `Write` 뒤마다 돌므로 모델이 규칙을 기억하는지는 상관없다.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "npx prettier --write --ignore-unknown \"$(jq -r '.tool_input.file_path')\"" }
        ]
      }
    ]
  }
}
```

마이그레이션 규칙은 `migrations/` 아래 경로에 종료 코드 2를 내는
`PreToolUse` 훅이 된다.
훅은 예외가 전혀 없는 규칙을 위한 것이며,
“named export를 선호한다”처럼 예외가 많은 것은 `CLAUDE.md`에 남긴다.

### 권한 규칙과 샌드박스로 접근을 제한한다

`deny` 규칙은 자동과 `bypassPermissions`를 포함한 모든 권한 모드에서 유지되므로
`.env` 규칙이 속할 곳이다.

```json
{
  "permissions": {
    "allow": ["Bash(pnpm tsc --noEmit)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.local)", "Read(./secrets/**)"]
  }
}
```

규칙은 의도가 아니라 도구 호출에 일치하므로 경계를 알아야 한다고 문서는 말한다.
`Read` 규칙은 `cat .env`를 잡는데, Claude Code가 흔한 파일 읽기 명령을
알아보기 때문이다.
파일을 여는 스크립트는 잡지 못한다.
도메인에 대한 `WebFetch` 거부 규칙은 샌드박스가 꺼져 있으면 같은 도메인으로의
`curl`을 막지 못한다.
운영체제 수준의 제한은 `/sandbox`로 켜며,
기본적으로는 모델이 차단된 명령을 샌드박스 밖에서 다시 시도해도 되느냐고 물을 수
있고 엄격 모드가 그 재시도를 끈다.

자동 모드는 하드 규칙이 아니라 각 행동을 판단하는 분류기 모델이므로,
“절대 안 된다”는 규칙은 거부 규칙이나 훅에 두라고 문서는 경고한다.

### 규칙이 적용되는 범위를 고른다

규칙이 어디에 있는지가 누구에게 적용되는지를 정한다.
`.claude/settings.local.json`과 `~/.claude/settings.json`은 본인만의 것이다.
`.claude/settings.json`과 그 안의 훅은 저장소의 것이어서 커밋하면 모두에게
적용되고, 거부 규칙은 곧바로 적용되지만 허용 규칙은 각자가 신뢰 대화상자를
수락할 때까지 기다린다.
관리형 설정은 조직의 것이며 개인 설정이 덮어쓸 수 없어서 보안 팀의 정책이 들어갈
유일한 곳이다.
강제 규칙은 적게 유지하라고 문서는 덧붙인다.
훅과 거부 규칙은 모두 가끔 잘못 작동하고 누군가 관리해야 하므로,
마흔 개에 이르면 대부분은 모델이 스스로 저울질할 수 있었던 선호일 것이다.

## 기본값 바꾸기

기본값은 작업이 시간, 토큰, 중단에서 너무 많이 들 때까지 두라고 한다.
그때는 `/usage`로 어디에 썼는지 본다.
새 세션은 자동 모드로 시작하고, 대부분의 요금제에서 Claude Opus 5.5를 medium
노력으로 쓰고, 필요하면 하위 에이전트에 위임하고, 대화가 늘면 압축한다.

### 권한 모드

수동 모드는 안전하지만 열 번째 질문부터 읽지 않고 승인하게 되고 자리를 비우면
아무것도 움직이지 않는다.
`bypassPermissions`는 거부와 확인 규칙이 다루지 않는 모든 것을 승인하므로 쓰고
버리는 컨테이너에서만 말이 된다.
자동 모드는 그 사이이고, 별도의 분류기가 정해진 순서로 행동을 검토한다.
`curl | bash`, 운영 배포와 마이그레이션, 남의 작업 위로의 강제 푸시,
외부로 가는 민감 데이터, 모델이 읽은 내용이 시킨 것처럼 보이는 행동을 막는
데 집중한다.
세 번 연속(또는 총 스무 번) 막으면 자동 모드가 멈추고 다시 묻는다.

이것이 결정적 통제를 대체하지는 않는다.
거부와 확인 규칙, `PreToolUse` 훅이 분류기보다 먼저 적용되기 때문이다.
자동 모드가 일상적인 것을 반복해서 막으면 `autoMode.allow`나 신뢰하는 인프라에
대한 설명을 일반 문장으로 더한다.
문서는 모든 목록에 `"$defaults"`를 남기라고 경고한다.
없으면 기본 규칙을 더하는 것이 아니라 대체해서,
`soft_deny`에서는 강제 푸시와 운영 배포에 대한 기본 차단이 사라진다.
또 `autoMode` 블록은 분류기가 프로젝트 설정의 `autoMode`를 무시하므로
`~/.claude/settings.json`에 있어야 한다.

### 모델과 노력

노력(effort)은 모델이 얼마나 오래 생각하는지를 정하는 주된 수단이며 예전에
프롬프트 문구로 하던 일의 대부분을 대체한다.
Opus 5.5, Sonnet 5.5, Haiku 5.5의 기본값은 `medium`이고 범위가 분명한 일상적인
기능 작업에 충분하다.
빠뜨리기 쉬운 경우에 중요하면 `/effort high`나 `xhigh`로 올린다.
남이 쓴 코드의 버그, 불안정한 테스트, 옛 구조를 읽는 모든 곳을 찾아야 하는
스키마 변경이 그런 예이다.
빠르게 오가며 결과마다 직접 검토할 때는 `low`로 내린다.
`max`는 보안 취약점 사냥처럼 혼자 풀게 두고 싶은 어려운 문제에만 쓰고,
보통 작업에서는 과하게 생각해서 `high`보다 낫지 않은 답에 더 치르기 쉽다.
다음 메시지 하나에만 필요하면 설정을 바꾸지 않고 그 프롬프트에
`ultrathink`를 넣는다.

### 하위 에이전트의 비용

하위 에이전트는 병렬 작업, 긴 출력을 메인 대화 밖에 두기,
대화를 보지 못한 리뷰어, 더 적은 도구를 가진 과제에서 값어치를 한다.
비용은 대부분 토큰이다.
각 하위 에이전트가 자기 요청을 보내고 같은 사용량에 잡히기 때문이다.
새 하위 에이전트는 대화가 이미 가진 맥락을 먼저 모아야 해서 시간도 더
걸릴 수 있다.
기본적으로 같은 모델이거나 더 작은 모델이 같은 일을 하므로 병렬성이나 새로운
눈을 얻을 뿐 더 똑똑한 답을 얻지는 못한다.

줄이는 방법은 네 가지이다.
단순한 일을 하는 하위 에이전트 정의에는 `model: haiku`를 둔다.
짧은 요약을 돌려 달라고 한다.
`/usage`로 하위 에이전트 종류별 몫을 본다.
`.claude/agents/`의 사용자 정의 하위 에이전트에는 `tools: Read, Grep,
Glob`만 주어서 고칠 수 없는 리뷰어로 만든다.
이 제한은 프롬프트로 부탁한 것이 아니라 Claude Code가 강제한다.

### 비용과 컨텍스트

대부분의 현재 모델은 100만 토큰 창이 있고 압축이 그 위쪽에서 일어나므로
컨텍스트가 부족해지는 일은 드물다.
그래도 필요 없는 컨텍스트에 값을 치를 수는 있다.
요청마다 대화 전체가 전송되어서 관련 없는 세 작업이 쌓인 세션은 네 번째 작업의
매 턴마다 세 작업을 다시 읽는다.
이것은 캐시가 따뜻한 동안은 할인되고 만료되면 전액이다.

관련 없는 작업 사이에는 `/clear`를 쓰고, `/compact`는 초점을 주어 쓰고,
`/loop`와 목표 확인, 하위 에이전트 같은 백그라운드 작업을 주시한다.
프롬프트 캐시는 구독에서 약 한 시간, API 키와 클라우드 제공자와 사용
크레딧에서 5분이다.
하위 에이전트는 바꾸지 않으면 5분이다.

## 세션 조종하기

처음 1분을 지켜보고, 모델이 벗어나는 즉시 `Esc`를 누르고,
두 번 고쳐 주고도 틀리면 세 번째 수정 대신 `/clear`로 더 나은 프롬프트를 쓰라는
것이 요약이다.
`Esc`는 지금까지의 결과를 유지한 채 멈춘다.
`/rewind`(또는 빈 프롬프트에서 `Esc` 두 번)는 코드와 대화 중 하나 또는 둘 다를
이전 프롬프트로 되돌려서, 과감한 접근을 먼저 시도하고 안 되면 되감는 것을 덜
위험하게 만든다.
`/clear`는 새로 시작한다.
같은 것을 두 번 고쳤는데도 틀렸다면 세 번째 수정은 이미 두 번의 실패를 담은
대화에 더하는 것일 뿐이기 때문이다.

체크포인트는 메인 대화에서 모델이 자기 파일 도구로 고친 파일만 다루므로 Bash
명령으로만 건드린 파일은 복원되지 않는다.
git을 대체하지 않고 함께 쓴다.

## 무인 실행

자리를 비우고 실행을 맡기기 전에 그 작업에 맞춰 다섯 질문을 확인하라고
문서는 말한다.

1. 끝이 어떤 모습인지 아는가? 목표 조건, 스펙 파일, 초록으로 바꿀 실패하는 테스트.
2. 자기 작업을 확인할 수 있는가? 테스트 스위트, `Stop` 훅, 리뷰 단계.
3. 무엇을 건드려도 되는가? 권한 규칙, `dontAsk`, 샌드박스, 작업 트리, 푸시해도 되는 브랜치 하나.
4. 무엇이 멈추게 하는가? `--max-turns`, `--max-budget-usd`, 지출 한도.
5. 결과가 어디로 가고 누가 승인하는가? PR, 댓글, 요약, 그리고 병합이나 배포를 승인하는 사람.

한 번 시작하면 긴 작업은 모델이 끌고 가고, 사람에게 남는 것은 시작,
이번 “끝”의 정의, 마지막 병합 승인이다.

### 스크립트에서 실행하기

`claude -p "프롬프트"`는 한 번 실행하고 종료하며 CI, git 훅,
셸 반복문에서 쓰인다.
스크립트에서는 대개 몇 가지 플래그를 더한다.
`--bare`는 훅, 스킬, 플러그인, MCP 서버,
저장소와 머신의 `CLAUDE.md`를 건너뛰어 어디서 돌려도 같은 일을 하게 하고,
claude.ai 로그인도 쓰지 않는다.
`--append-system-prompt`, `--mcp-config`,
`--settings`는 실행이 필요로 하는 것을 명시적으로 넘기고,
`--allowedTools`는 도구를 미리 승인하며,
`--permission-mode dontAsk`는 그 밖에 물었을 것을 거부한다.
`--output-format json`은 파싱할 결과 객체 하나를 준다.

```bash
for file in $(cat files.txt); do
  claude --bare -p "Migrate $file to the new logger API and commit. Reply OK or FAIL." \
    --allowedTools "Read,Edit,Bash(git add *),Bash(git commit *)" \
    --permission-mode dontAsk \
    --max-turns 20
done
```

세 파일로 먼저 돌려 무엇이 잘못되는지 보고 프롬프트를 고친 뒤 나머지를
돌리라고 한다.
자동 모드도 `-p`와 함께 `--permission-mode auto`로 쓸 수 있지만,
비대화형 실행에서는 분류기가 막으면 그 행동만 거부하고 계속하며 터미널처럼
멈추지 않는다.

### 일정이나 사건으로 시작한다

모델이 스스로 할 수 없는 한 가지는 시작을 결정하는 일이어서, 사람, 타이머,
또는 CI 실패나 새 PR 같은 사건이 시작해야 한다.
열린 세션 안에서는 `/loop`가 프롬프트를 일정 간격으로 반복한다.
노트북이 닫혀 있어도 돌아야 하는 일에는 `/schedule`로 클라우드 예약
작업을 만든다.
클라우드 예약 작업을 켜 두기 전에는 작업이 우회할 수 없는 GitHub 브랜치 규칙으로
`main`을 보호하라고 경고한다.

### 세션을 병렬로 돌린다

별개의 작업은 각자 체크아웃을 주어 편집이 충돌하지 않게 한다.
`claude -w feature-auth`가 새 작업 트리에서 세션을 시작한다.
작업 트리는 새 체크아웃이므로 `.env` 같은 gitignore된 파일이 없고 의존성도
설치되어 있지 않다.
필요한 파일은 저장소 루트의 `.worktreeinclude`에 `.gitignore` 문법으로
적으면 복사된다.
링크가 아니라 복사하므로 작은 파일만 넣어야 하고,
`node_modules` 같은 큰 디렉터리는 `worktree.symlinkDirectories` 설정이나
`CLAUDE.md`의 설치 명령으로 다룬다.
`claude -p --worktree`로 만든 작업 트리는 질문 없이 끝나므로 직접 지워야 한다.

한 세션이 코드를 쓰고 다른 세션이 그 과정을 보지 못한 채 리뷰하는 구성이 가장
쉬운 독립 리뷰어라고 문서는 말한다.

## 더는 필요 없는 조언

문서는 한때 좋은 조언이었지만 대부분 모델이 못 하던 일의 우회책이었고 이제는
모델이 따라잡았다고 하며 일곱 가지를 든다.

| 옛 조언                                           | 문서가 말하는 이유                                                                                                                                                              |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 컨텍스트 창이 주된 제약이니 공격적으로 관리하라   | 대부분의 모델이 100만 토큰 창이 있고 압축이 자동이라 소진은 드물다. 작업 사이의 `/clear`는 초점 있는 컨텍스트가 더 나은 답과 낮은 비용을 주므로 여전히 가치가 있다              |
| 놓치는 지시에 IMPORTANT나 대문자를 붙여라         | 옛 모델에는 필요했지만 현재 모델은 평이하게 쓴 줄을 따르고 강조를 쌓으면 규칙을 과하게 적용한다. 예외 없는 규칙이면 훅이나 거부 규칙으로, 긴 파일에서 줄이 묻히면 파일을 줄인다 |

## 확인하기

이 문서가 직접 확인한 것은 세 가지이다.
첫째, 위의 세 JSON 예제(`Stop` 훅, `PostToolUse` 훅,
권한 규칙)는 파서가 읽는 유효한 JSON이다.
둘째, `Stop` 훅의 명령 `pnpm tsc --noEmit 1>&2 || exit 2`의 논리는 실패하는
검사를 `false`로 대신했을 때 종료 코드 2로,
통과하는 검사를 `true`로 대신했을 때 0으로 끝난다.
셋째, 이 저장소에 설치된 Claude Code 2.1.308의 도움말에 `--bare`,
`--max-budget-usd`, `--allowedTools`, `--append-system-prompt`, `--mcp-config`,
`--settings`, `--output-format`, `-w`가 있고 `--permission-mode`의 선택지는
`acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`이다.

```bash
sh -c 'false 1>&2 || exit 2'; echo "failing check: $?"
sh -c 'true 1>&2 || exit 2'; echo "passing check: $?"
claude --help | grep -E -e '--bare|--max-budget-usd|--permission-mode'
```

실제 훅이 세션에서 모델을 막는지, 자동 모드의 분류기가 문서가 나열한 것을
막는지는 시험하지 않았다.

## 비평

### 모델의 행동에 대한 주장이 근거 없이 서술된다

문서는 현재 모델이 평이하게 쓴 줄을 따르고 강조는 규칙을 과하게 적용하게
만든다고 말하지만, 어떤 실험이나 측정에서 나온 말인지 적지 않는다.
“더는 필요 없는 조언” 표의 일곱 항목이 모두 같은 형식이다.
옛 조언이 우회책이었고 모델이 따라잡았다는 서술은 설득력 있지만 제조사의
관찰이며 독립된 확인이 아니다.
이 표의 항목은 모델 버전에 묶여 있어서,
모델이 바뀌면 같은 문서의 같은 표가 반대 방향으로 고쳐질 수 있다.
HN의 이 문서 스레드에 달린 유일한 댓글은 검증 기준을 주고,
프롬프트마다 범위를 좁히고, 구체적인 작업을 시키고,
`/clear`를 자주 쓰는 것을 유용했다고 적는다.[^aanet]
다만 이 스레드는 2026년 1월 22일의 것이어서 당시 문서가 지금과 같았는지는
확인하지 못했다.

### “결정적”이라는 말은 도구 호출의 일치 범위까지만 결정적이다

문서의 표는 거부 규칙과 훅을 결정적이라고 하지만, 같은 문서가 그 경계를 적는다.
규칙은 의도가 아니라 도구 호출에 일치하고,
`Read` 규칙은 `cat .env`는 잡지만 파일을 여는 스크립트는 잡지 못하며,
도메인 거부 규칙은 샌드박스 없이는 `curl`을 막지 못한다.
따라서 강제가 결정적인 것은 규칙이 일치하는 범위 안에서이고,
범위 밖은 모델의 판단에 남는다.
문서는 보안에는 거부 규칙과 샌드박스를 함께 쓰라고 하는데,
이는 하나의 결정적 수단으로는 부족하다는 고백이기도 하다.

### 결정적 수단은 하나의 하네스에 묶여 있다

문서가 권하는 강제 수단(훅, 거부 규칙, 관리형 설정,
`Stop` 훅)은 모두 Claude Code의 기능이다.
이 저장소처럼 여러 에이전트에서 같은 지침을 쓰려는 곳에서는 같은 훅이 다른
에이전트에 없을 수 있다.
그러면 규칙을 `AGENTS.md`에 적는 것(비결정적)과 각 하네스의 설정으로 강제하는
것(결정적)이 따로 관리된다.
문서는 팀 설정을 별도 문서에 맡기고 이 문제를 다루지 않는다.

### 기본값은 사용량을 늘리는 쪽이다

문서가 기본값으로 소개하는 것은 자동 위임, 백그라운드로 도는 하위 에이전트,
포크, medium 노력이고, 모두 요청과 토큰을 늘릴 수 있다.
문서는 이 비용을 숨기지 않고 `/usage`로 보라고 하며,
하위 에이전트가 같은 모델에서 더 똑똑한 답을 주지 않는다고도 쓴다.
그래도 기본값이 사용자의 비용을 줄이는 쪽이 아니라 쓰는 쪽이라는 구조는 문서가
짚지 않는다.

## 기억할 원칙

### 반드시 일어나야 하는 일은 글이 아니라 설정으로 만든다

문서가 가장 분명히 말하는 것은 지시의 신뢰도가 표현의 세기에서 오지 않고 집행의
주체에서 온다는 점이다.
아무리 강하게 써도 따를지는 모델이 정하고,
하네스가 집행하면 모델의 기억과 판단에 달리지 않는다.
강조를 더하는 것이 효과가 없다는 신호이고,
그 신호가 나타나면 줄을 고치지 말고 집행 위치를 바꾼다.

### 끝의 정의는 모델이 읽을 수 있는 통과·실패이다

“끝나 보임”만 가진 모델은 사람을 테스트 스위트로 만든다.
통과 또는 실패로 돌아오는 검사 하나와 그 실행 증거를 요구하는 것이 무인
실행의 전제이다.
검사의 엄격함은 모델이 스스로 판단하는 것부터 하네스가 강제하는 것까지 정할 수
있고, 일의 위험에 맞춰 고른다.
