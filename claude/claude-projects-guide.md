# Claude Projects 소개와 활용 가이드

트윗: [Claude Projects 소개와 활용 가이드: 실전 워크플로우와 세팅 팁](https://twitter.com/yulmu_coffee/status/2122602823464649018)

## 소개

율무커피(@yulmu_coffee)가 2026년 11월 17일 Twitter에 올린 7분 분량의 긴 글(Twitter Article)이다. 조회수 1만 2천 회로 표시되어 있다.
이 문서는 글 전문을 읽었다. 글이 인용하는 Claude Code 문서, 출시 공지, 해외 사용자 글은 열지 않았고, 새 Claude Projects를 직접 써 보지도 않았다. 제품의 동작과 한도, 가격은 모두 글의 서술이다. 같은 필자의 다른 글(`llm/understanding-llms.md`)은 별개 출처이다.

글의 주장은 이렇다.
Claude Code 세션을 서너 개 동시에 띄우면 어느 세션에 무슨 일을 줬는지, 같은 배경을 또 붙여 넣었는지, 어디서 내 답을 기다리는지 챙기는 중간 관리자가 되는데, 2026년 9월 17일 공개된 Claude Projects가 이 일을 Claude에게 넘긴다는 것이다.

## 동작 방식

글이 설명하는 구조는 다음과 같다.

- 프로젝트 하나는 Claude와 나누는 긴 대화(조율자, 오케스트레이터, Projects에서는 코디네이터라 부름) 하나이다. 여기에 할 일을 던지면 Claude가 작업을 쪼개 여러 스레드(Thread)에 나눈다.
- 스레드는 보통 클라우드에서 도는 독립 Claude Code 세션이어서 여러 개가 동시에 움직이고 노트북을 덮어도 멈추지 않는다. 내 컴퓨터 환경이 필요한 작업만 골라 로컬에서 돌릴 수도 있다.
- 제공 범위: Pro, Max, Ultra(구 Max 20x) 플랜의 공개 베타이고, claude.ai/code와 데스크톱 앱의 Code 탭, 모바일 앱에서 쓴다. 베타 초기에는 대기자 명단 승인이 필요했고 최근에는 하루 안팎으로 빨라졌다고 한다.
- 기존 프로젝트와의 차이: 기존 프로젝트가 참고 파일과 맞춤 지침을 묶어 둔 폴더였다면 새 프로젝트는 그 자체가 지속 대화이다(출시 공지의 제목이 폴더에서 대화로). 기존 프로젝트는 대화마다 사용자가 직접 요청하고 결과가 대화 속 답변인 반면, 새 프로젝트는 Claude가 작업을 스레드로 나눠 병렬로 실행하고 결과가 브랜치와 PR, Library에 쌓이는 파일로 남는다. 새 프로젝트는 공유가 안 되고 만든 사람만 쓴다. 베타 초기에 기존 프로젝트가 있는 계정은 새로 만들기 대신 시작하기가 떠서 생성이 막히곤 했고, 기존 프로젝트를 보관(Archive)하면 풀린다고 한다.
- 서브에이전트와의 차이: 일반 세션의 서브에이전트는 결과 요약만 남기고 사라지는 단발성 일꾼이고 요약이 메인 컨텍스트를 채운다. Projects의 스레드는 끝나도 꺼지지 않는 영속적인 독립 세션으로, 자기 컨텍스트 윈도우와 브랜치를 갖고 PR을 연 뒤에도 CI 실패 수정과 리뷰 코멘트 반영을 계속 지켜보며 사용자가 스레드 방에 들어가 대화를 이어 갈 수도 있다.
- 코디네이터의 일: 가벼운 질문은 바로 답하고 새 작업은 새 스레드로 보내거나 관련 영역을 맡은 기존 스레드에 넘긴다. 한 메시지에 무관한 작업이 섞이면 각각 별도 스레드를 연다. 스레드의 세부 과정을 감시하지 않고 최종 보고만 읽는다.
- 결과물: 코드는 GitHub 브랜치와 PR, 문서와 리서치는 Overview 패널의 Library 탭에 파일로 쌓인다. 스레드는 검토 준비 완료, 내 답변 대기, 진행 중, 유휴, 해결됨으로 묶여 보이며 해결됨은 직접 표시하거나 마지막 단계를 끝내거나 7일간 활동이 없으면 자동 이동한다.

## 활용 패턴

글이 소개하는 해외 사용 사례 넷이다.

1. 백로그 덤프(Boris Cherny): 개별 세션을 일일이 관리하지 않고 아이디어와 버그 수정거리를 그때그때 프로젝트 대화에 던져 둔다. 코디네이터와 스레드가 프로젝트 메모리를 공유해 맥락을 잃지 않고 처리한다.
2. 공유 계약 선행: API, 웹, 모바일 세 저장소를 동시에 고칠 때 무작정 나누면 필드명과 기본값을 다르게 가정해 합칠 때 계약이 깨진다. 먼저 타입과 기본값과 에러 규격 같은 인터페이스 계약을 문서나 메모리에 확정하고 그것을 전제로 각 서비스 스레드를 병렬로 돌린다. 병렬화의 병목은 코드 작성이 아니라 병합 충돌이라는 서술이다.
3. 비코딩 콘텐츠 파이프라인(Wyndo): 저장소 없이 폴더만 올려도 돈다. 뉴스레터 폴더 구조(작업별 참조 규칙을 적은 CLAUDE.md, 독자와 문체와 금지어를 적은 about, 채널별 포맷 가이드, 문체 기준 글을 모은 examples, 초안과 파생 글이 저장되는 output)를 예로 들고, 자료 조사와 과거 글 중복 확인은 의존성이 없어 병렬로, 초안과 채널별 파생 글은 순차로 묶는다. 폴더 업로드는 최대 100개 파일, 200MB의 복사본이라 로컬에서 고치면 Library에서 교체해야 반영된다.
4. 개인(클라우드)과 업무(로컬) 혼합: 사이드 프로젝트는 GitHub 커넥터로 클라우드 스레드가 24시간 돌고, 사내 보안과 로컬 DB와 VPN이 얽힌 업무는 같은 프로젝트에서 Remote Control로 내 컴퓨터에 붙은 로컬 스레드로 돌린다.

## 설정하기

글의 설정 조언은 세 묶음이다.

- 지침을 세 층으로 나눈다: 프로젝트 지침(최대 16,000자, 코디네이터와 모든 스레드가 읽음, 분배 방식과 대상 브랜치와 자체 검증과 승인 필수 사항 같은 공통 운영 규칙만 짧게), 저장소 CLAUDE.md(그 저장소를 다루는 스레드가 읽음, 빌드·테스트 명령과 컨벤션), 프로젝트 메모리 MEMORY.md(클라우드 스레드가 쌓는 함정과 결정 노트, 잘못된 추측과 민감 정보가 들어갈 수 있어 처음 몇 번 돌린 뒤 직접 읽고 다듬는 편이 안전). 프로젝트 지침 5요소 템플릿은 프로젝트의 목적, 브랜치와 PR 규칙, 완료 전 테스트와 린트와 결과 요약, 접근할 수 없는 자원이 있으면 멈추고 목으로 때우지 않는다는 규칙, 병합과 강제 푸시와 CI 설정 변경 금지이다. 글은 네 번째(접근 불가 시 멈춤)가 없으면 스레드가 권한 없는 API를 목으로 대체해 그럴듯하지만 틀린 PR을 연다고 강조한다.
- 사용량: 별도 과금 없이 기존 플랜 한도를 공유하고, 스레드마다 온전한 세션이며 PR을 감시하는 스레드도 CI 실패나 리뷰 코멘트마다 깨어나 토큰을 쓴다. Pro 플랜은 점심 전에 하루치 한도가 닳기 쉬워 사실상 Max 플랜에서만 온전히 쓴다고 한다. 설정에서 스레드 모델과 노력 수준을 낮추고(새 프로젝트 기본값이 Opus 높은 노력), 한도 초기화 시 자동으로 이어 달리는 옵션을 끄는 것을 검토하고, 1시간 넘게 쉰 스레드는 깨우지 않는다. 캐시 수명이 약 1시간이라 지나면 이전 대화를 다시 읽기 때문이다.
- 클라우드와 로컬의 연결: 코드는 GitHub에 있어야 하고(GHES, GitLab, Bitbucket 미지원), 해당 저장소에 Claude GitHub 앱이 설치되어야 한다. 클라우드 스레드는 저장소의 루트 CLAUDE.md와 `.claude/CLAUDE.md`, `.claude/rules/`만 가져가고 `.claude/skills/`와 `.mcp.json`과 `.claude/settings.json`(훅, 권한, 환경 변수)은 읽지 않는다. 스킬은 계정 설정에서 켜고, 플러그인은 프로젝트 설정에서 추가하고, MCP는 claude.ai 커넥터로 연결하고, 패키지와 비밀과 네트워크는 클라우드 환경의 설정 스크립트와 환경 변수로 지정한다. 로컬 스레드에는 프로젝트 메모리가 로드되지 않으므로 꼭 알아야 할 내용을 지침이나 작업 프롬프트에 직접 적어야 하고, 데스크톱 앱(Claude Code v2.1.280 이상)에서 Remote Control을 켜고 같은 폴더를 두 스레드가 덮어쓰지 않도록 Worktree 옵션을 켠다.

## 함정

- 캐시가 식은 스레드에 말을 걸면 비용이 크게 늘어난다. 글은 Opus 5.5의 15만 토큰 스레드 기준으로 캐시가 살아 있으면 0.03달러, 만료되면 1.20달러로 40배라고 쓴다. 쉬는 스레드는 인계 파일을 남긴다.
- 살아 있는 스레드의 모델을 중간에 바꾸면 캐시와 상관없이 전체를 다시 쓴다.
- 코디네이터와 스레드의 권한이 다르다. claude.ai 커넥터와 Computer Use는 스레드에만 있고 코디네이터에는 없으므로, 메일이나 문서를 읽는 일은 스레드에서 직접 한다.
- 스레드가 권한 승인을 기다리며 멈췄거나 잘못된 방향으로 갈 때는 코디네이터를 통하지 않고 해당 스레드 방에 직접 들어가 답하거나 멈춰야 한다.
- 클라우드 샌드박스는 턴 사이에 복구하지 못하면 저장소를 새로 복제해 커밋하지 않은 변경이 사라지므로 중간 커밋을 지시한다. 승인 없이 병합하지 말라는 지침은 강제력이 없으므로 반드시 막을 동작은 GitHub 브랜치 보호 규칙으로 잠근다.
- 단일 세션으로 끝날 작업은 일반 세션이, 대화 없이 주기적으로 돌릴 리포트는 예약 작업이, 여러 팀원이 조율하는 일은 Slack용 Claude Tag가 더 가볍고 싸다. 하루 최대 새 스레드 수는 200개라고 글은 쓴다.

글은 마지막에 비용 절감과 성공률을 위한 열 가지 추천을 표로 정리한다(식은 스레드에 말 걸지 않기, 쉬기 전에 인계 파일, PR을 병합 스레드에 넘기면 원래 스레드는 구독을 끊고 닫기, CLAUDE.md를 짧게, 검증을 훅으로 강제, PR 전 새 맥락 리뷰, 스레드의 모델 바꾸지 않기 등). 복붙용 초기 설정 프롬프트도 제시하는데, 프로젝트 파악과 설정(지침, 작업 환경 분리, 모델과 노력 수준, 레포 CLAUDE.md, 프로젝트 메모리)과 기본 규칙(동시 스레드 3~4개, 병합은 전담 스레드 하나가, 되돌릴 수 없는 일은 승인 후, 마이그레이션은 병합 뒤에, 결과부터 짧게 보고)을 담는다.

## 비평

### 제품의 동작은 필자의 서술이고 확인되지 않았다

한도와 캐시 비용(0.03달러와 1.20달러), 지원하는 저장소 호스트, 로드되는 설정 파일의 범위는 모두 글의 서술이다. 이 문서는 글이 인용하는 공식 문서를 열지 않았다.
베타 기능이라 이 내용은 빠르게 바뀔 수 있다. 글도 개별 수치를 최신 문서에서 확인하라는 식의 단서는 달지 않는다.

### 사용 사례의 출처가 간접적이다

백로그 덤프와 비코딩 파이프라인은 해외 사용자의 방식을 소개한 것이고, 필자 자신이 몇 주 돌려 본 결과(소요, 비용, 실패)는 글에 없다.
따라서 이 패턴들이 효과적이라는 증거는 소개된 사람들의 말뿐이다.

### 비용 서술이 한쪽으로 기운다

글은 마지막에 중간 관리 비용을 Claude에게 위임하고 그 대가로 플랜 사용량을 지불하는 거래라고 정리하지만, 실제 사용량 대비 절감한 시간의 비교는 없다.
Pro 플랜에서는 사실상 쓰기 어렵다는 서술(점심 전에 한도 소진)이 있어, 이 기능의 접근성이 플랜에 크게 좌우된다는 점이 드러난다.

### 안전 장치의 설명이 지침에 의존한다

승인 없이 병합하지 말라는 같은 지침이 강제되지 않는다고 글이 스스로 지적하며 브랜치 보호 규칙을 권한다. 지침 템플릿의 대부분이 이런 비강제 규칙이다.
접근 불가 시 멈춘다는 규칙이 실제로 지켜지는지도 글이 확인하지 않는다.

### 외부 반응

HN과 GeekNews에서 이 트윗의 스레드는 검색되지 않았다(GeekNews의 Claude Projects 관련 토픽은 이전 기능에 대한 것이다). Lobste.rs의 twitter.com 도메인 최근 글 75개에도 없었다.
그래서 이 글의 서술은 독자의 검토를 거치지 않았다.

## 인사이트

### 가져갈 것은 지침의 계층을 나누는 설계이다

공통 운영 규칙은 프로젝트 지침에, 저장소별 명령과 컨벤션은 저장소 CLAUDE.md에, 스레드가 쌓는 함정은 메모리에 두면 읽는 범위와 비용이 나뉜다.
이 구조는 Projects가 아닌 다른 에이전트 환경에서도 쓸 수 있다. 읽는 쪽이 무엇을 읽는지가 다른 도구에서도 지침의 위치를 정하는 기준이다. 이는 이 문서의 정리이다.

### 강제할 것과 부탁할 것을 구분한다

병합 금지처럼 지침으로는 지킬 수 없는 것은 브랜치 보호 규칙 같은 시스템 설정으로 막고, 지침에는 보고 방식과 작업 순서처럼 부탁해도 되는 것만 적는다.

### 확인할 관찰

이 글의 서술을 가를 관찰은 세 가지이다.
공식 문서가 글의 한도와 캐시 비용과 설정 로드 범위를 확인해 주는지,
이 기능으로 실제 작업을 돌렸을 때의 사용량과 절감한 시간이 어느 정도인지,
베타가 끝난 뒤 공유와 플랜 제한이 어떻게 바뀌는지이다.
셋 모두 이 문서가 확인하지 못했다.
