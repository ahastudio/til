# Claude 모델 고르기: Opus 5.5에서 시작해 토큰 단가가 아니라 작업 하나의 비용으로 위아래를 판단하라는 가이드

HN 토론: <https://news.ycombinator.com/item?id=50435447> (3점, 1개 댓글)

HN 토론: <https://news.ycombinator.com/item?id=50441841> (3점, 0개 댓글)

## 소개

Addy Osmani가 2026년 11월 9일에 claude.dev 블로그의 Playbooks 분류로 올린 15분
분량의 가이드다.
Claude Platform이나 Claude Code에서 일상적인 작업에 어느 모델을 쓸지,
그 선택이 어떤 맞교환(trade-off)을 뜻하는지 설명한다.
기준이 되는 계열은 일반 제공 모델 넷, 곧 Claude Haiku 5.5, Sonnet 5.5, Opus 5.5,
Fable 5.2다.
Claude Mythos 5.2는 사이버보안과 생명과학 연구에 가장 강한 모델이며
검증 프로그램을 통해서만 쓸 수 있다고 한다.

가이드가 주는 것은 시작점이다.
대부분의 일은 기본 노력 수준(effort)이 중간인 Opus 5.5에서
시작하라는 것이 첫 문장의 답이다.
그 모델은 Claude Code의 기본 모델이고 토큰당 가격이 Fable 5.2의 절반이다.
거기서 범위가 명확한 일상 작업은 Sonnet 5.5로, 분류와 라우팅과 추출처럼 단순하고
물량이 많은 일은 Haiku 5.5로 내려가고,
가장 어려운 기술 과제나 Opus 5.5를 높은 노력 수준으로 돌려도 모자란 일이나 감독
없이 오래 도는 일은 Fable 5.2로 올라간다.
모델을 옮기기 전에 노력 수준을 먼저 조절해 보라고도 한다.

가이드가 주지 않는 것도 분명하다.
어느 모델이 더 낫다는 판정이 아니라 자기 작업에서
재어 보는 절차를 마지막에 요구한다.
모델별 벤치마크 수치는 다른 글(Fable 5.2 페이지, 출시 글)에 맡기고
여기서는 비용과 노력의 예시로만 쓴다.

## 모델 고르기

가이드의 작업별 표를 이 문서의 말로 줄이면 다음과 같다.
시작 모델과 시작 노력 수준이며, 모두 출발점이지 정답이 아니다.

| 작업                                                    | 시작 모델                 | 시작 노력 수준               |
| ------------------------------------------------------- | ------------------------- | ---------------------------- |
| 일상 엔지니어링과 디버깅, 여러 풀 리퀘스트의 기능       | Opus 5.5                  | 중간(기본), 이어서 높음      |
| 분류, 라우팅, 태깅, 대량 추출                           | Haiku 5.5                 | 중간(기본)                   |
| 파일 검색, 로그 읽기, 요약을 맡는 하위 에이전트         | Haiku 5.5 또는 Sonnet 5.5 | 모델의 기본값                |
| 채팅과 대화형 세션                                      | Sonnet 5.5                | 낮음 또는 중간               |
| 범위가 정해진 코딩(버그 수정, 명세 기반 기능)           | Sonnet 5.5                | 중간, 어려우면 높음          |
| 일상적인 문서, 슬라이드, 스프레드시트                   | Sonnet 5.5                | 높음(Claude Code에서는 중간) |
| 반복 실행하는 조사, 검토, 초안 작성                     | Sonnet 5.5                | 중간                         |
| 컴퓨터 사용과 이미지가 많은 흐름                        | Opus 5.5                  | 중간                         |
| 대규모 리팩터링, 마이그레이션, 설계, 하위 에이전트 지휘 | Fable 5.2                 | 중간, 이어서 높음            |
| 심층 조사와 과학, 정량 분석                             | Fable 5.2                 | 중간, 이어서 높음            |
| 아직 모르겠음                                           | Opus 5.5                  | 중간(기본)                   |

가이드는 이 표의 경계를 흐리게 둔다.
명세가 분명하다고 Sonnet을 쓰라는 뜻은 아니라는 것이다.
마이그레이션이나 성능 최적화는 명세가 분명해도 어려워서 Opus 5.5가 필요하고,
큰 작업이면 Fable 5.2가 필요할 수 있다고 적는다.
복잡한 재무 모델이나 자료 더미에서 만드는 문서도 Sonnet이 아니라 Opus 5.5에서
시작하라고 한다.

## 값 정하기

### 가격과 한도

가이드가 제시한 Claude API 정가는 다음과 같다.
캐시 읽기는 같은 프롬프트를 다시 읽을 때의 값이다.

| 항목                    | Haiku 5.5                                    | Sonnet 5.5                   | Opus 5.5 | Fable 5.2                    |
| ----------------------- | -------------------------------------------- | ---------------------------- | -------- | ---------------------------- |
| 입력(100만 토큰당)      | 0.10달러, 10만 토큰 초과 프롬프트는 0.50달러 | 2달러                        | 4달러    | 8달러                        |
| 출력(100만 토큰당)      | 0.50달러, 10만 토큰 초과 프롬프트는 2.50달러 | 10달러                       | 20달러   | 40달러                       |
| 캐시 읽기(100만 토큰당) | 0.01달러, 10만 토큰 초과는 0.05달러          | 0.10달러                     | 0.20달러 | 0.20달러                     |
| 상대 지연               | 가장 빠름                                    | 빠름                         | 보통     | 보통                         |
| API 기본 노력 수준      | 중간                                         | 높음(Claude Code에서는 중간) | 중간     | 높음(Claude Code에서는 중간) |
| 빠른 모드(fast mode)    | 없음                                         | 없음                         | 있음     | 있음                         |

네 모델의 컨텍스트 창은 모두 100만 토큰, 최대 출력은 12만 8천 토큰이다.
Haiku 5.5만 프롬프트 길이에 따라 토큰 값이 달라진다.

### 작업 하나의 비용을 재는 코드

가이드는 비용을 작업 단위로 재라고 하면서 응답의 usage 필드에서
완료된 작업의 비용을 기록하라고 말한다.
그 계산을 가이드의 정가로 옮긴 코드다.
캐시 쓰기 가격은 가이드에 없으므로 넣지 않았고, 필요하면 직접 더해야 한다.

```python
# 가격은 가이드에 실린 Claude API 정가다(100만 토큰당 달러).
PRICES = {
    "haiku-5.5": {"in": 0.10, "out": 0.50, "cache_read": 0.01},
    "haiku-5.5-long": {"in": 0.50, "out": 2.50, "cache_read": 0.05},
 # 프롬프트 10만 토큰 초과
    "sonnet-5.5": {"in": 2.00, "out": 10.00, "cache_read": 0.10},
    "opus-5.5": {"in": 4.00, "out": 20.00, "cache_read": 0.20},
    "fable-5.2": {"in": 8.00, "out": 40.00, "cache_read": 0.20},
}


def call_cost(model, usage):
    """응답 한 번의 비용. usage는 응답의 usage 필드와 같은 이름의 키를 쓴다."""
    if model == "haiku-5.5":
        prompt = usage.get("input_tokens",
0) + usage.get("cache_read_input_tokens", 0)
        if prompt > 100_000:  # Haiku만 프롬프트 길이로 구간이 갈린다
            model = "haiku-5.5-long"
    p = PRICES[model]
    return (
        usage.get("input_tokens", 0) * p["in"]
        + usage.get("output_tokens", 0) * p["out"]
        + usage.get("cache_read_input_tokens", 0) * p["cache_read"]
    ) / 1_000_000  # 캐시 쓰기 가격은 가이드에 없으므로 포함하지 않는다


def task_cost(model, usages):
    """한 작업이 끝날 때까지 쓴 모든 호출의 합."""
    return sum(call_cost(model, u) for u in usages)
```

입력 5,000토큰, 출력 2,000토큰,
캐시 읽기 15만 토큰인 호출은 이 계산으로 Sonnet 5.5가 0.045달러,
Opus 5.5가 0.09달러, Fable 5.2가 0.15달러다.
같은 숫자를 직접 돌려 확인한 값이다.
Haiku 5.5는 입력 5,000토큰, 출력 500토큰의 짧은 호출에서
약 0.00075달러로 Sonnet 5.5의 0.015달러의 20분의 1이다.
프롬프트가 12만 토큰이 되면 Haiku 5.5는 0.06125달러,
Sonnet 5.5는 0.245달러로 격차가 4배로 줄어든다.

## 트레이드오프

### 토큰 단가가 높아도 작업당 비용은 낮을 수 있다

가이드의 첫 번째 맞교환은 능력과 작업당 비용이다.
큰 모델이 대체로 더 비싸고 더 유능하지만
작업 단위에서는 이것이 성립하지 않을 수 있다고 한다.
Anthropic이 돌린 Terminal-Bench 3.0에서
이전 모델 Fable 5.1은 최대 노력으로 58.0%, Opus 5.5는 높음으로 58.9%를 받았고
후자는 토큰을 절반만 썼다고 한다.
FrontierCode 2.0에서는 Fable 5.2가 높음으로 45.3%, Opus 5.5가 최대로 45.5%였고
Fable 5.2의 작업당 비용이 약 절반이었다고 한다.

이 두 번째 예에서 이 문서의 계산을 해 보면 의미가 보인다.
Fable 5.2의 토큰 단가가 Opus 5.5의 두 배인데 작업당 비용이 절반이라면,
두 모델이 비슷한 입력과 출력 비율을 쓴다고
가정할 때 Fable 5.2는 토큰을 약 4분의 1만 쓴 셈이다.
이 계산은 비율 가정에 기댄 근사다.
가이드의 결론은 어려운 작업에서
Opus 5.5의 노력을 높음 위로 올리기 전에 Fable 5.2를 시험하라는 것이다.
일상 작업은 여전히 Opus 5.5의 중간에서 시작한다.

소형 모델에 대해서는 반대 방향의 한계를 적는다.
Haiku 5.5 같은 모델은 결과를 확인할 수 있는 대량 작업에는 잘 맞지만
긴 에이전트 반복에는 덜 맞는다고 한다.
가장 어려운 작업이 비용의 대부분을 차지하므로 비교할 때는 전형적인 작업만이
아니라 가장 어려운 작업의 값도 매기라고 한다.
20문제짜리 검색 벤치마크에서 두 문제가 지출의 43%를 차지한 예가 나온다.

### 빠른 설정은 더 일찍 끝나고 더 많이 틀린다

둘째 맞교환은 지연과 정확도다.
사람이 기다리는 응답이면 Sonnet 5.5를 낮음이나 중간으로 시작하라고 한다.
Fable 5.2는 Fable 5.1보다 출력이 최대 30% 빠르고,
Sonnet 5.5는 Sonnet 5보다 30% 빠르다고 한다.

노력 수준은 지연과 대체로 비례하며,
SWE-bench Pro의 Opus 5.5 수치가 구체적인 사다리를 준다.

| 노력 수준        | 점수 변화(높음 대비) | 비용(높음 대비) |
| ---------------- | -------------------- | --------------- |
| 낮음             | 약 8점 낮음          | 약 3분의 1      |
| 중간             | 약 2.5점 낮음        | 약 70%          |
| 매우 높음(xhigh) | 약 1.4점 높음        | 2.5배           |

점수를 조금 더 얻으려는 비용이 위로 갈수록 급격히 커지는 모양이다.
이 표는 이 문서가 가이드의 문장을 정리한 것이다.

모델이나 노력을 올리기 전에 자기 검증 수단을 주는 편이 비용 효율적이고
지연도 덜 늘린다고 가이드는 말한다.
모델이 작업에 충분하지 않을 때의 순서는 이렇다.
먼저 모델이 테스트, 빌드, 엔드포인트를 부르는 스크립트로 자기 결과를 검증할 수
있게 하고, 그다음 노력을 한 단계 올리고, 그래도 안 되면
위 모델로 가되 더 낮은 노력에서 시작한다.
결과를 자동으로 확인할 수 있다면 전부 낮은 수준으로 돌리고
실패한 것만 높은 수준으로 다시 돌리는 방법도 있다.
같은 SWE-bench Pro 부분집합에서 Opus 5.5를 낮음으로 돌리고
실패한 것만 높음으로 다시 돌렸더니 약 97%가 통과했고 작업당 약 0.17달러였다.
모든 작업을 높음으로 돌린 경우는 95.3%에 0.29달러였다.
이 문서의 계산으로 비용은 약 41% 적다.

### 컨텍스트는 매 턴마다 다시 보내는 비용이다

넷째 맞교환은 컨텍스트와 비용이다.
모든 현재 세대 모델이 100만 토큰 창을 갖지만
큰 컨텍스트는 매 턴마다 다시 전송되어 비용이 든다.
다만 긴 실행에서는 입력의 대부분이 캐시 읽기로 청구된다.
Opus 5.5의 캐시 읽기는 100만 토큰에 0.20달러여서 15만 토큰의 컨텍스트에서
한 턴의 캐시 읽기는 약 0.03달러, 2만 토큰에서는 약 0.004달러다.

그래서 큰 모델일수록 주 컨텍스트를 간결하게 유지하는 것이 더 중요하다.
비싼 모델의 컨텍스트는 결정에 쓰고,
장황한 읽기는 더 싼 하위 에이전트에 맡기라는 것이 가이드의 요지다.
Fable 5.2와 Opus 5.5는 캐시 읽기 값이 같아서
캐시가 많은 긴 실행에서는 둘의 차이가 캐시되지 않은 입력과 출력에 몰리고,
거기서는 Fable이 토큰당 두 배다.

## 섞어 쓰기

### 모델을 바꾸는 시점은 자연스러운 끊김에서다

프롬프트 캐시는 그것을 쓴 모델에 속한다.
새 모델로 넘어간 첫 턴은 대화 전체에 캐시 쓰기 가격을 낸다.
Claude Code에서는 `/compact`를 먼저 실행하거나 짧은 계획서를 쓴 새 세션으로
시작하고, API에서는 전체 기록 대신 지금까지 한 일의 요약으로 새 대화를 열라고
한다.

각 사고(thinking) 블록은 그것을 만든 모델을 기록하고,
모델마다 읽을 수 있는 다른 모델의 블록이 정해져 있다.
Claude API 기준으로 Opus 5.5는 Sonnet 5.5와 Haiku 5.5의 블록을,
Sonnet 5.5는 Haiku 5.5의 블록을, Fable 5.2는 세 모델의 블록을 읽는다.
그래서 한 단계 아래로 옮기면 이전의 추론을 잃고,
읽을 수 없는 블록은 API가 버려서 요청은 성공하지만
새 모델은 그 추론 없이 일한다.

### 하위 에이전트는 실수가 싸게 드러나는 일에만 작은 모델을 쓴다

하위 에이전트는 자기 컨텍스트 창에서 일하고 요약을 돌려주며,
토큰은 그것이 도는 모델의 값으로 청구된다.
Claude Code에서는 하위 에이전트 정의에 `model: haiku`나 `model: sonnet`을 쓰고,
기본값은 `CLAUDE_CODE_SUBAGENT_MODEL` 환경 변수로 정한다.
가이드의 예는 다음과 같다.

```markdown
---
name: log-reader
description: Reads test output and logs,
and reports each failing case. Use after a test run.
tools: Read, Grep, Glob, Bash
model: haiku
---
Read the logs you're given. For each failure, report the file,
the test name and the first error line. Don't edit any files.
```

이 파일은 `.claude/agents/log-reader.md`에 저장한다.
가이드의 규칙은 파일 찾기, 테스트 실행,
로그 읽기처럼 실수가 쉽게 드러나는 일만 작은 모델에 맡기고,
코드 수정과 판단은 주 모델에 두는 것이다.
작은 모델이 검색 결과를 잘못 읽으면
주 모델이 엉뚱한 파일을 열어 토큰을 쓰기 때문이다.

Claude Code 안에서는 `opusplan` 별칭이 계획은 Opus로, 실행은 Sonnet으로 한다.
가이드는 이것이 자기 조언과 반대라고 짚는다.
코드 수정을 Sonnet에 넘기게 되므로 기본으로 삼기 전에 자기 작업에서 재어 보라고
한다.

### 어드바이저와 대량 위임은 비용을 줄이지만 조건이 좁다

어드바이저 도구(베타)는 빠르고 싼 실행 모델과 더 강한 조언 모델을 짝짓는다.
실행 모델이 작업 중에 조언을 구할 때만 조언 모델이 개입하고,
토큰 대부분은 실행 모델의 값으로 청구된다.
가이드는 이것에 신중하다.
플랫폼의 비용 안내서가 비교한 네 가지 짝 가운데
실행 모델 단독보다 분명히 나은 것이 없었고,
한 사례는 Opus 5.5(높음) 실행 모델에 Fable 5.1 어드바이저를 붙여 내부 코딩
벤치마크에서 90.1%, 시도당 2.92달러였다.
이는 Opus 5.5 단독(높음)보다 1.7점 높지만 비용은 약 2.1배이고,
그 차이는 실행 간 잡음의 경계에 있어 노력을 올려서 얻을 정도와 비슷하다고 한다.

한 컨텍스트 창을 넘는 큰 일에는 상위 모델이 쪼개고
여러 싼 작업자에게 병렬로 맡겨 합치는 방식이 있다.
약 2,200만 토큰 분량의 소스에서 결함을 찾는 내부 벤치마크에서
Opus 5.5 지휘자와 최대 25개의 Sonnet 5.5 작업자는 Opus 5.5 단독(기본 노력)보다
비용이 약 3분의 1 낮고 점수는 비슷했다.
의존 관계가 있는 한 줄기 단계이거나 한 컨텍스트 창에 들어가는 일에는 쓰지 말라고
한다.
계획과 병합 비용이 아끼는 비용보다 크기 때문이다.

## 함정

모델 이름만 바꾸면 되는 줄 알았다가 깨지는 지점을 가이드가 모아 두었다.

- Fable 5.2는 보존된 사고(preserved thinking)를 모든 API 계정으로 넓혔다.
Fable 5.2의 사고 블록 앞의 내용(시스템 프롬프트, 도구, 이전 메시지)이 바뀌면
API가 400 오류를 돌려준다.
기록을 직접 편집하는 코드는 추가만 하도록 만들어야 한다.
- Opus 5.5와 Fable 5.2는 항상 생각하며, 생각을 끈 요청은 오류를 낸다.
Sonnet 5.5는 기본으로 생각하고
`between_tools`로 도구 호출 사이로 제한할 수 있다.
Haiku 5.5는 높음 이하에서 끌 수 있다.
- 도구 사용 강제(`tool_choice`가 `any`나 `tool`)는 Sonnet 5.5, Opus 5.5,
Fable 5.2에서 400 오류다.
`auto`로 보내고 도구에 `strict: true`를 표시하며 프롬프트에 언제 쓸지 적는다.
- Haiku 4.5에서 5.5로 옮길 때는 `budget_tokens`를 노력 수준으로 바꾸고,
기본이 아닌 `temperature`, `top_p`, `top_k`를 빼며,
마지막을 사용자 턴으로 끝내야 한다.
- Anthropic API에서 `haiku` 별칭은 이제 Haiku 5.5로 풀리고
Claude Code v2.1.293 이상이 필요하다.
Amazon Bedrock, Google Cloud, Microsoft Foundry,
Claude Platform on AWS에서는 아직 Haiku 4.5로 풀린다.
같은 설정이 제공자에 따라 다른 모델이 된다는 뜻이므로 모델 식별자를 고정하는
편이 안전하다.
- Claude Code의 내장 Explore 하위 에이전트는
이제 항상 Haiku가 아니라 세션 모델로 돈다.
탐색을 싸게 하려면 `model: haiku`를 지정한 Explore 이름의 하위 에이전트를 직접
정의한다.
- Opus 5.5, Sonnet 5.5,
Fable 5.2의 안전 분류기는 사이버보안과 생물학 내용을 가장 자주 표시한다.
Claude Code에서는 표시된 요청이 이전 모델로 다시 돌 수 있고,
표시된 사이버보안 요청은 Opus 4.8로, 생물학 요청은 Opus 5로 내려간다.

한 시스템이 여러 모델을 쓴다면 가장 엄격한 모델에 맞춰 요청을 만들라고 한다.
기록은 추가만 하고, `tool_choice`는 `auto`와 strict 도구로 보내며,
콘텐츠 블록을 종류별로 읽고, 프롬프트와 도구 설명은 가장 문자 그대로 받아들이는
모델에 맞춰 정확히 쓴다.
그러면 코드를 바꾸지 않고 단계가 위아래로 움직일 수 있다.
라우팅 규칙이 단순하다면(단계 유형별로 한 모델) 모델에게 모델을 고르게 하지 말고
코드가 고르게 하라고 덧붙인다.

## 확인하기

공개된 수치는 시작 모델을 줄 뿐이고, 가이드는 후보를 자기 작업에서
시험한 뒤에 정하라고 한다.
절차는 다섯 단계다.

1. 실제 작업의 표본을 뽑고 각 작업에 결과 검사(통과하는 테스트, 닫힌 티켓,
맞는 행 수)를 쓴다.
2. 후보 모델을 노력 수준 두세 개로 각각 돌린다.
캐시를 공유하지 않도록 실행마다 세션을 따로 쓴다.
완료된 작업의 비용은 각 응답의 usage 필드에서 기록한다.
3. 점수와 지출의 산점도를 그린다.
다중 모델 구성은 모든 단일 모델의 점을 이길 때만 남긴다.
4. 이긴 구성은 실제 트래픽 일부에서 그림자(shadow)로 돌려 보고 전환한다.
5. Claude Code에서 빠르게 보려면 백로그의 작업 하나를 `/model`로 두 모델에서
돌려 `/usage`가 알려 주는 값을 비교한다.

위의 비용 계산 코드는 2단계의 기록을 합치는 데 쓸 수 있다.

## 비평

### 가이드가 내세우는 근거는 대부분 Anthropic 내부 실행이다

글의 비용 사례는 Terminal-Bench 3.0, FrontierCode 2.0, SWE-bench Pro 부분집합,
내부 코딩 벤치마크, 내부 결함 탐색 벤치마크에서 나온다.
이 가운데 Terminal-Bench 3.0은 Anthropic의 실행이라고 명시되고,
몇은 내부 벤치마크라고 적힌다.
독자가 같은 설정으로 재현할 수 있는지는 글에 없다.

추천이 판매자의 기본 상품과 겹친다는 점도 알아 둘 만하다.
첫 답이 Claude Code의 기본 모델인 Opus 5.5이고,
가이드가 말하는 “아직 모르겠음”의 답도 같다.
이는 가이드가 틀렸다는 뜻이 아니라,
기본값이 추천과 일치하는 구조에서는 추천의 독립성이 확인되지 않는다는 뜻이다.
가이드가 스스로 독자에게 자기 작업에서 재라고 하는 것이 이 한계를 보완한다.

### 두 벤치마크의 차이는 잡음과 구별되지 않는다

Terminal-Bench 3.0에서 58.0%와 58.9%, FrontierCode 2.0에서
45.3%와 45.5%는 각각 1점과 0.2점 차이다.
가이드는 이를 거의 같은 점수라고 읽지만,
같은 글이 어드바이저 사례의 1.7점 차이는 실행 간 잡음의 경계라고 평가한다.
같은 기준을 적용하면 앞의 두 차이도 구별되지 않는다.
이 경우 결론은 “토큰을 더 쓴 쪽이 더 낫다”가 아니라 “이 점수 구간에서
더 쓴 토큰이 점수를 거의 올리지 못했다”이며, 가이드의 결론과 같은 방향이다.
다만 단일 실행의 점수에 반복 횟수와 분산이 없다는 점은 남는다.

### 모델 이름과 제공자 차이가 설정의 이식성을 깬다

가이드는 `haiku` 별칭이 Anthropic API에서는 Haiku 5.5,
다른 클라우드에서는 Haiku 4.5로 풀린다고 적는다.
이 한 줄이 가이드의 단순한 표보다 실무에서 더 위험하다.
같은 하위 에이전트 정의가 환경에 따라 다른 세대의 모델과 다른 요청 규칙(400
오류가 나는 매개변수)을 만나기 때문이다.
가이드의 표는 모델 이름만 나열하고 이 경계는 뒤쪽 한 문단에만 둔다.

## 체크리스트

- 이 작업의 결과를 자동으로 검사하는 수단이 있는가.
- 모델을 올리기 전에 모델이 스스로 검증할 수 있는 테스트, 빌드,
스크립트를 주었는가.
- 모델을 올리기 전에 노력 수준을 한 단계 올려 보았는가.
- 비교에 전형적인 작업만이 아니라 가장 어려운 작업을 넣었는가.
- 모델 후보의 비용을 토큰 단가가 아니라 완료된 작업 하나의 비용으로 재었는가.
- 노력 수준을 두세 개로 나누고 실행마다 세션을 분리해 캐시가 섞이지 않았는가.
- 하위 에이전트에 맡긴 일이 실수가 싸게 드러나는 일인가.
- 모델을 바꾸는 시점이 작업의 자연스러운 끊김인가,
그 전에 요약이나 `/compact`를 했는가.
- 제공자별로 모델 별칭이 같은 모델로 풀리는지 확인했는가.
- 요청의 기록이 추가만 되고, `tool_choice`가 `auto`이며,
콘텐츠 블록을 종류별로 읽는가.
- 선택한 구성이 모든 단일 모델의 점을 이기는지 산점도로 확인했는가.

## 기억할 원칙

### 모델은 단가가 아니라 완료된 작업 하나의 값으로 비교한다

토큰 단가가 두 배인 모델이 작업당 비용으로는 절반일 수 있고,
가장 싼 모델도 프롬프트가 길어지면 격차가 20배에서 4배로 줄어든다.
비교의 단위는 단가표가 아니라 결과를 통과한 작업 하나이고,
그 값은 가장 어려운 작업이 좌우한다.
이 원칙은 모델이 바뀌어도 유지되므로 가이드의 구체적인 가격이나 점수보다 오래
남는다.

### 올리는 순서는 검증, 노력, 모델이다

가장 싼 개선은 모델이 자기 결과를 검증하게 하는 것이고, 그다음이 노력 한 단계,
마지막이 위 모델이다.
위로 갈수록 점수당 비용이 급격히 커지며, 위 모델로 갈 때는 낮은 노력에서
시작해 두 선택을 비교한다.
결과를 자동으로 검사할 수 있다면 낮은 수준으로 전부 돌리고
실패만 다시 돌리는 방식이 가장 먼저 시험할 만하다.
