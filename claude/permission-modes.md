# 권한 모드: 무엇을 허용할지가 아니라 누가 승인할지를 고르는 설정

원문: [Choose a permission mode - Claude Code Docs](https://code.claude.com/docs/en/permission-modes)

## 요약

권한 모드는 세션에서 Claude가 먼저 묻지 않고 할 수 있는 행동의 범위를 정한다.
Manual 모드에서는 파일을 편집하거나 셸 명령을 실행하거나 네트워크에 닿는 대부분의 행동 전에 멈추고 묻는다.
auto 모드에서는 사용자 대신 두 번째 모델인 분류기가 행동을 검토한다.
Pro와 Max와 Team 플랜에서는 기본 시작 모드가 auto다.
전환은 CLI의 `Shift+Tab`, VS Code의 모드 표시기, 데스크톱의 모드 선택기로 하며
실행 중인 세션의 모드도 언제든 바꿀 수 있다.

모드는 여섯 개다.

| 모드                | 묻지 않고 실행되는 것                                              | 적합한 상황                        |
| ------------------- | ------------------------------------------------------------------ | ---------------------------------- |
| `default`           | 읽기만                                                             | 모든 행동을 직접 검토, 민감한 작업 |
| `acceptEdits`       | 읽기, 파일 편집, 흔한 파일시스템 명령                              | 검토하며 코드를 반복 수정할 때     |
| `plan`              | 읽기, auto 모드가 가능하면 분류기가 승인한 명령                    | 바꾸기 전에 코드베이스를 탐색할 때 |
| `auto`              | 전부, 배경 안전 검사와 함께                                        | 긴 작업, 프롬프트 피로 줄이기      |
| `dontAsk`           | 미리 승인된 도구만                                                 | 잠긴 CI와 스크립트                 |
| `bypassPermissions` | 전부                                                               | 격리된 컨테이너와 VM에서만         |

모든 행동을 검토하는 모드는 CLI와 `claude --help`와 VS Code·JetBrains 확장과
데스크톱 앱에서 Manual로 표시되지만 설정 값은 `default`이며,
훅과 SDK 통합이 쓰는 값도 `default`다.
CLI는 `manual`을 별칭으로 받으며 이 표시와 별칭은 v2.1.200 이상이 필요하다.
어떤 모드에서도 자동 승인되지 않는 행동도 따로 정해져 있다.
명시적 ask 규칙에 걸린 도구,
조직이 `ask`로 설정한 커넥터 도구,
`AskUserQuestion`처럼 사용자 상호작용이 필요한 도구와
`requiresUserInteraction`으로 표시된 MCP 도구,
임계 경로를 대상으로 하는 `rm`과 `rmdir`,
그리고 세션 간 메시징 안전장치다.

시작 모드는 여러 층에서 결정된다.
터미널 세션은 `--permission-mode` 플래그나 `--dangerously-skip-permissions`,
그다음 설정 파일의 `permissions.defaultMode`, 그다음 내장 기본값 순서로 정해진다.
`.claude/settings.json`이나 `.claude/settings.local.json`에 넣은 `auto` 값은 적용되지 않으며,
그 경우 `~/.claude/settings.json`의 값 대신 내장 기본값이 쓰인다.
내장 기본값은 실행 방식과 플랜과 기능 플래그 수신 여부에 따라 갈린다.
어떤 설정 파일이든 `disableAutoMode`를 `"disable"`로 두었거나,
기능 플래그 수신이 꺼져 있거나 설치·업그레이드 직후 첫 세션이거나,
`claude -p`나 Agent SDK이거나,
Amazon Bedrock과 Google Cloud의 Agent Platform과 Microsoft Foundry 등이거나,
Enterprise 플랜이나 Console API 키이면 `default`로 시작한다.
Pro와 Max와 Team 플랜이 터미널이나 VS Code 확장에서 실행될 때만 `auto`다.
`auto` 내장 기본값은 macOS와 Linux와 WSL에서 v2.1.228,
네이티브 Windows에서 v2.1.233 이상이 필요하다.
VS Code 확장은 자체 우선순위 목록을 따르며
프로젝트의 `.claude/settings.json`을 시작 모드 결정에 읽지 않는다.

auto 모드의 분류기는 요청 범위를 넘어서는 확대,
인식되지 않은 인프라를 대상으로 하는 행동,
Claude가 읽은 적대적 내용에 이끌린 것으로 보이는 행동을 차단한다.
`SendMessage`로 다른 에이전트에게 보내는 메시지도 전달 전에 검토하고,
임계 경로를 대상으로 하는 `rm`과 `rmdir`도 검토해 승인하거나 차단한다.
사용 조건은 플랜은 전부 가능하고,
Team과 Enterprise에서는 기본 제공이되 관리자가 `permissions.disableAutoMode`로 끌 수 있으며,
모델은 Anthropic API와 Claude Platform on AWS에서 Opus 4.6 이상,
Sonnet 4.6 이상, Fable 5이고,
Bedrock과 Agent Platform과 Foundry와 Claude apps gateway에서는
Sonnet 5와 Opus 4.7 이상과 Fable 5만 지원된다.
문서는 경고 상자로 auto 모드가 프롬프트를 줄이지만 안전을 보장하지는 않으며
민감한 작업의 검토를 대체하는 용도가 아니라고 적는다.

기본 차단 목록은 길고 버전별로 계속 늘어난다.
`curl | bash` 같은 코드 내려받아 실행하기, 민감 데이터를 외부로 보내기,
프로덕션 배포와 마이그레이션, 클라우드 스토리지 대량 삭제,
IAM이나 저장소 권한 부여, 공유 인프라 수정,
세션 이전부터 있던 파일의 비가역적 파괴, 강제 푸시가 기본에 있다.
`git reset --hard`와 `git checkout -- .`과 `git clean -fd`와 `git stash drop` 계열,
이번 세션에서 만들지 않았거나 이미 푸시된 커밋에 대한 `git commit --amend`,
`terraform destroy` 계열도 포함된다.
v2.1.195 이후로는 비밀 관리자 쓰기와 DNS·TLS 변경,
사람이 승인하지 않은 PR 병합과 CI 검사 비활성화,
`atlantis apply` 같은 자동화 명령을 댓글로 남기기,
프로덕션 기능 플래그 조작, 클러스터 노드 드레인,
DaemonSet이나 어드미션 웹훅 생성,
살아 있는 자격증명을 트랜스크립트나 파일에 출력하기 등이 추가됐다.
v2.1.198에는 `/tmp`나 공유 스크래치 디렉터리를 와일드카드로 지우는 것과
자기 tmux 페인에 키 입력을 보내 자기 인터페이스를 조작하는 것이 들어왔고,
v2.1.200에는 보안 동작을 지키는 테스트를 주석 처리하거나 강제 통과시키는 것과
`git remote set-url`로 푸시 대상을 바꾸는 것이,
v2.1.203에는 민감한 로컬 저장소의 내용이 커밋이나 PR이나 gist로 들어가는 것이,
v2.1.205에는 세션 트랜스크립트 파일에 쓰는 것과
대화에서 값이 확인되지 않는 셸 변수를 대상으로 하는 재귀 강제 삭제가 추가됐다.
기본 허용 목록에는 작업 디렉터리 안의 로컬 파일 작업,
잠금 파일이나 매니페스트에 선언된 의존성 설치,
`.env`를 읽어 해당 API에 자격증명을 보내기, 읽기 전용 HTTP 요청,
그리고 작업 중인 저장소의 어느 브랜치로든 푸시하기가 있다.
`claude auto-mode defaults`로 전체 규칙을 JSON으로 출력할 수 있다.

분류기의 판정 순서는 네 단계이며 먼저 걸리는 단계가 이긴다.
allow·ask·deny 규칙에 걸리는 행동이 즉시 결정되고,
읽기 전용 행동과 작업 디렉터리 안의 파일 편집이 자동 승인되고,
나머지가 분류기로 가고,
분류기가 차단하면 Claude가 사유를 받아 다른 방법을 시도한다.
다만 보호 경로 쓰기는 allow 규칙이 있어도 분류기로 가고,
조직이 `ask`로 설정한 커넥터 도구와 `requiresUserInteraction` MCP 도구는
allow 규칙이 있어도 사용자에게 직접 묻는다.
auto 모드에 진입하면 임의 코드 실행을 부여하는 광범위 allow 규칙이 해제된다.
`Bash(*)`나 `PowerShell(*)`, `Bash(python*)` 같은 와일드카드 인터프리터,
패키지 관리자 실행 명령, `Agent` 규칙, `Monitor` 규칙이 그 대상이며
`Bash(npm test)` 같은 좁은 규칙은 유지되고 모드를 벗어나면 복원된다.
분류기는 사용자 메시지와 읽기 전용이 아닌 도구 호출과 CLAUDE.md 내용을 보며,
도구 결과는 제거되므로 파일이나 웹페이지의 적대적 내용이 직접 조작할 수 없다.
하위 에이전트는 시작 전 작업 설명, 실행 중 각 행동, 종료 시 전체 행동 이력의
세 지점에서 검토되며 하위 에이전트 frontmatter의 `permissionMode`는 무시된다.
분류기는 기본적으로 Claude Sonnet 5에서 돌고 세션 모델 선택을 따르지 않으며,
Enterprise 플랜과 API·Bedrock·Agent Platform·Foundry 계정에서는
분류기 호출이 토큰 사용량에 계산된다.
차단이 연속 3회 또는 누적 20회에 이르면 auto 모드가 멈추고 다시 프롬프트가 뜨며
이 임계값은 설정할 수 없다.

대화에서 진술한 경계도 차단 신호가 된다.
푸시하지 말라거나 검토할 때까지 기다리라고 말하면
기본 규칙이 허용하는 행동도 분류기가 차단하며,
나중에 해제할 때까지 유지되고 Claude 자신의 판단으로는 해제되지 않는다.
다만 이 경계는 규칙으로 저장되지 않고 매 검사마다 트랜스크립트에서 다시 읽히므로
컨텍스트 압축이 그 메시지를 지우면 사라질 수 있으며,
문서는 하드 보증이 필요하면 deny 규칙을 쓰라고 안내한다.
나머지 모드도 각각 정리되어 있다.
`dontAsk`는 프롬프트가 뜰 모든 호출을 자동 거부해
allow 규칙과 읽기 전용 Bash 명령과 `PreToolUse` 훅이 승인한 것만 실행한다.
`bypassPermissions`는 보호 경로 쓰기를 포함해 검사를 건너뛰지만
어떤 모드에서도 자동 승인되지 않는 행동은 여전히 묻고,
Linux와 macOS에서 root나 `sudo`로는 시작을 거부하며,
Claude Code on the web은 설정 파일의 이 값과 `dontAsk`를 무시한다.
보호 경로는 `.git`과 `.vscode`와 `.claude` 등의 디렉터리와
셸 초기화 파일과 패키지 관리자 설정 파일 등이며
`.claude/worktrees`만 예외다.
설정 파일의 allow 규칙은 보호 경로 쓰기를 미리 승인하지 못한다.
임계 경로는 파일시스템 루트와 최상위 디렉터리, 홈 디렉터리,
Windows 드라이브 루트, 작업 디렉터리와 그 상위 등이며,
allow 규칙이나 `PreToolUse` 훅의 `"allow"`로도 승인되지 않는다.

## 분석

### 모드 목록은 편의성의 스펙트럼이 아니라 승인 주체의 목록이다

여섯 개 모드를 표로 보면 묻는 횟수 순으로 늘어선 것처럼 읽힌다.
`default`에서 `bypassPermissions`로 갈수록 프롬프트가 줄어든다는 배치다.
그런데 문서의 첫 두 문단이 다른 축을 제시한다.
Manual에서는 사용자가 묻고,
auto에서는 두 번째 모델인 분류기가 사용자 대신 행동을 검토한다는 것이다.

이 축으로 다시 세우면 모드가 세 무리로 갈린다.
사람이 승인하는 것이 `default`와 `acceptEdits`,
모델이 승인하는 것이 `auto`와 조건부의 `plan`,
아무도 승인하지 않는 것이 `dontAsk`와 `bypassPermissions`다.
마지막 두 개가 같은 무리라는 점이 특히 그렇다.
하나는 사전 목록에 없으면 전부 거부하고 다른 하나는 전부 허용하지만,
둘 다 실행 시점에 판단하는 주체가 없다는 점에서 같다.
프롬프트 횟수로 정렬하면 이 둘이 양 끝에 놓이는데,
승인 주체로 정렬하면 나란히 놓인다.

이 재정렬이 중요한 이유는 기본값 때문이다.
Pro와 Max와 Team 플랜의 내장 시작 모드가 `auto`라는 서술은
도입부 두 번째 문단에 한 줄로 놓여 있다.
그 한 줄의 내용은 대부분의 개인 사용자에게
승인 주체가 이미 사람에서 모델로 넘어갔다는 것이다.
문서는 그 사실을 강조하지도 정당화하지도 않고 사실로 배치한다.
정당화는 별도의 발표 글이 맡았고
`claude/auto-mode.md`에 그 논증을 정리해 두었는데,
이 문서는 그 결정이 이미 내려진 뒤의 참조 문서로서
무엇이 어떻게 동작하는지만 서술한다.

### 차단 목록의 축적 방식이 위협 모델의 출처를 드러낸다

기본 차단 목록은 한 번에 설계된 것처럼 읽히지 않는다.
v2.1.195 이후 추가, v2.1.198 이후 추가, v2.1.200 이후 추가,
v2.1.203 이후 추가, v2.1.205 이후 추가라는 소제목이 차례로 붙어 있고
각 묶음이 앞의 묶음을 세분화하거나 빈틈을 메운다.

그 세분화의 방향을 보면 무엇이 문제였는지 짐작된다.
처음에는 프로덕션 배포나 IAM 권한 부여처럼 범주가 넓었다.
뒤로 갈수록 좁고 구체적이다.
와일드카드나 기간 필터로 `/tmp`를 지우는 것,
보안 동작을 지키는 테스트만 골라 주석 처리하는 것,
`.env.example` 같은 예시 파일에서 API 기본 URL을 제3자 호스트로 돌리는 것,
값이 대화에 나타나지 않는 셸 변수를 대상으로 재귀 강제 삭제를 하는 것이다.
이 정도로 구체적인 규칙은 위협 모델링에서 연역되기 어렵다.
관측된 행동에서 귀납되는 쪽에 가깝다.

두 항목이 특히 눈에 띈다.
v2.1.205의 세션 트랜스크립트 쓰기 금지와
v2.1.198의 자기 tmux 페인에 키 입력 보내기 금지다.
전자는 에이전트가 자기 기록을 고치는 것을 막고,
후자는 문서 표현대로 자기 권한이나 감독을 바꾸는 행위로 분류된다.
둘 다 외부 공격자를 상정한 규칙이 아니다.
차단 목록에 도구 자신이 들어와 있다는 뜻이며,
이것은 목록의 다른 항목들과 성질이 다르다.

### 사용자의 사전 허가보다 런타임 판단을 위에 두는 설계다

판정 순서 네 단계는 통상적인 권한 시스템과 비슷해 보인다.
명시적 규칙이 먼저이고 그다음이 기본 허용이고 나머지가 검토 대상이다.
그런데 그 순서에 붙은 예외들이 방향을 뒤집는다.

보호 경로 쓰기는 allow 규칙이 있어도 분류기로 간다.
문서는 설정 파일의 allow 규칙이 보호 경로 쓰기를 미리 승인하지 못하며,
안전 검사가 allow 규칙 평가보다 먼저 실행되므로
`Edit(.claude/**)` 같은 항목을 넣어도 결과가 달라지지 않는다고 명시한다.
임계 경로 삭제도 allow 규칙이나 `PreToolUse` 훅의 `"allow"`로 승인되지 않는다.
그리고 auto 모드에 진입하면
`Bash(*)`나 와일드카드 인터프리터나 `Agent`나 `Monitor` 같은
광범위 allow 규칙이 아예 해제된다.

세 장치가 같은 원칙을 구현한다.
사용자가 명시적으로 허용한 것이라도
임의 코드 실행이나 감독 장치 변경에 해당하면 시스템이 그 허가를 무시한다.
보통의 권한 시스템에서는 명시적 허가가 최종 결정이고
시스템은 그것을 집행하는 쪽이다.
여기서는 명시적 허가가 입력의 하나이고 최종 결정은 런타임에 내려진다.
`Monitor` 규칙이 v2.1.236 이전에는 해제 대상이 아니어서
전체 도구를 매칭하는 규칙이 분류기 검토 없이 명령을 승인했다는 서술이
이 원칙이 사후에 확장되고 있음을 보여 준다.

### 보호 경로와 임계 경로는 모드 밖에 있는 별도의 층이다

문서 구조에서 이 두 절은 모드 설명이 모두 끝난 뒤에 온다.
그리고 각각 모드별로 어떻게 되는지를 표로 다시 제시한다.
즉 모드에 종속된 설정이 아니라 모드와 직교하는 층이다.

임계 경로 절의 첫 문장이 그 성격을 밝힌다.
allow 규칙이나 `"allow"`를 반환하는 훅이
임계 경로 삭제를 승인하지 못하게 하는 것이
모델 오류에 대비한 회로 차단기라는 것이다.
보호 대상이 사용자의 실수가 아니라 모델의 실수라고 명시한 셈이다.
그래서 이 층은 사용자가 무엇을 허가했는지와 무관하게 작동해야 하고,
실제로 그렇게 설계되어 있다.

보호 경로 목록의 구성도 같은 관점에서 읽힌다.
`.git`과 셸 초기화 파일과 패키지 관리자 설정 파일은
한 번 오염되면 이후의 모든 실행에 영향을 주는 자리다.
`.npmrc`나 `.pre-commit-config.yaml`이나 `.envrc`가 목록에 있는 이유가 그것이고,
`.claude` 자신이 목록에 있는 이유도 같다.
`.claude/worktrees`만 예외로 빠진 것은
Claude가 자기 git 워크트리를 그 아래 두기 때문이라고 문서가 밝힌다.
도구가 자기 설정 디렉터리를 보호 대상으로 지정하고
자기가 써야 하는 하위 경로만 예외로 뚫어 둔 구조다.

## 비평

### 선택을 돕는 문서가 변경 이력의 지층이 되어 원래 기능을 잃고 있다

제목은 권한 모드를 고르라는 것이고 첫 절은 모드 비교 표다.
그런데 본문의 상당 부분은 어느 버전에서 무엇이 달라졌는지에 대한 서술이다.
차단 목록의 개별 항목마다 단서가 붙는다.
v2.1.211 이전에는 기본 브랜치로 범위가 좁혀져 있었다,
v2.1.198부터는 대화에서 내부 레지스트리를 언급한 경우에도 적용된다,
PR과 이슈와 커밋 메시지 범위 지정은 v2.1.200 이상이 필요하다,
그 검사는 v2.1.203 이상이 필요하다 같은 식이다.

이 구성의 비용은 독자가 자기 상태를 확인할 수 없다는 것이다.
지금 내 버전에서 무엇이 차단되는지 알려면
항목 수십 개마다 붙은 버전 조건을 하나씩 대조해야 한다.
그리고 그 대조는 사람이 하기에 적합한 작업이 아니다.
문서가 제공하는 대안이 하나 있다.
`claude auto-mode defaults`로 전체 규칙을 JSON으로 출력하는 것이다.
그 명령이 존재한다는 사실은 이 문제를 이미 인지하고 있다는 뜻인데,
그렇다면 본문의 목록은 현재 동작만 담고
버전 조건은 별도 표나 하위 페이지로 분리하는 편이 낫다.

선택 문서와 변경 이력이 한 페이지에 섞이면 둘 다 제대로 기능하지 않는다.
모드를 고르려는 사람은 자기와 무관한 과거 동작을 읽어야 하고,
업그레이드 영향을 확인하려는 사람은
버전별로 정리되지 않은 서술에서 항목을 주워 모아야 한다.
같은 문서 안에 두 종류의 독자가 있는데
어느 쪽도 자기 경로를 갖지 못한다.

### 시작 모드 규칙이 표 하나로 정리되지 않는다는 사실 자체가 설계 신호다

시작 모드를 알아내려면 몇 개의 목록을 겹쳐 읽어야 한다.
터미널 세션의 우선순위 세 단계,
그 세 번째 단계인 내장 기본값을 정하는 여섯 행짜리 표,
VS Code 확장의 별도 네 단계 목록,
데스크톱의 폴더별 기억과 그것이 `defaultMode`를 이기는 규칙,
웹과 모바일에서 클라우드 세션이냐 원격 제어 세션이냐에 따라 갈리는 목록이다.

여기에 예외가 겹친다.
`auto` 값은 프로젝트 설정 파일에서 적용되지 않는다는 서술이
문서 안에서 최소 세 곳에 반복된다.
시작 모드 절, 다른 모드로 시작하기 절의 표,
그리고 auto 모드 절의 문제 해결 문단이다.
VS Code 확장은 프로젝트 설정을 시작 모드에 읽지 않는다는 서술도 여러 번 나오고,
`claudeCode.claudeProcessWrapper`가 설정되면
3번과 4번 항목이 적용되지 않는다는 조건이 또 붙는다.

같은 예외를 세 번 적어야 한다는 것은 문서의 문제가 아니라 규칙의 문제다.
그 증거가 auto 모드 절의 한 문단에 있다.
`defaultMode: "auto"`를 설정했는데 터미널 세션이 오류 없이 Manual로 시작하면
그 설정이 아마 프로젝트 설정 파일에 있을 것이며
`~/.claude/settings.json`으로 옮기라는 안내다.
사용자가 실제로 겪는 혼란을 문서가 미리 알고 해설로 대응하는 형태인데,
설정한 대로 되지 않고 오류도 나지 않는 동작을
문서로 보완하는 것은 가장 비싼 해법이다.
값이 무시될 때 경고를 띄우는 것이 같은 문제에 대한 더 싼 답이고,
그 경고가 없다는 사실이 이 절을 길게 만들었다.

### 안전을 보장하지 않는다고 적은 장치에 최종 판정을 맡긴다

auto 모드 절의 경고 상자는 분명하다.
프롬프트를 줄이지만 안전을 보장하지 않으며
민감한 작업의 검토를 대체하는 용도가 아니라는 것이다.
그런데 같은 문서가 분류기를 여러 곳에서 최종 판정자로 배치한다.

임계 경로 표를 보면 그 구성이 선명하다.
`default`와 `acceptEdits`에서는 사용자에게 묻고,
`auto`에서는 분류기로 보내고,
`bypassPermissions`에서는 사용자에게 묻는다.
가장 위험한 삭제에 대해
가장 느슨한 모드가 사람에게 묻고 중간 모드가 모델에게 묻는다.
설계 의도는 이해된다.
`bypassPermissions`는 분류기가 아예 없는 모드이므로
회로 차단기가 프롬프트 말고는 기댈 곳이 없다.
그러나 결과적으로 모드의 위험 순서와 검토 강도의 순서가 어긋난다.
`rm -rf /`에 대해 auto 모드 사용자는 모델의 판정을 받고
bypass 모드 사용자는 자기 눈으로 확인한다.

같은 구조가 하위 에이전트 검토에도 있다.
종료 시점의 검토에서 분류기 요청 자체가 별도 안전 검사에 거부되면
Claude Code는 결과를 그대로 반환하되
검토되지 않았으니 신뢰할 수 없는 것으로 다루라는 경고를 앞에 붙인다.
안전한 처리이지만 그 경고를 받는 주체가 Claude 자신이라는 점이 남는다.
검토받지 않은 작업물을 신뢰하지 말라는 지시를
검토 대상과 같은 종류의 모델이 읽고 판단한다.
이 층을 사람이 보는 경로는 문서에 서술되지 않는다.

### 대화로 세운 경계가 조용히 사라진다는 사실이 한 문장으로 처리된다

경계 절의 내용은 두 부분이다.
푸시하지 말라고 말하면 분류기가 기본 허용 행동도 차단하며
나중에 해제할 때까지 유지된다는 것,
그리고 그 경계가 규칙으로 저장되지 않고
매번 트랜스크립트에서 다시 읽히므로
컨텍스트 압축이 그 메시지를 지우면 사라질 수 있다는 것이다.
문서는 하드 보증이 필요하면 deny 규칙을 쓰라는 한 문장으로 넘어간다.

이 실패 방식은 이 문서에 나오는 다른 어떤 실패보다 다루기 어렵다.
차단은 알림이 뜨고 `/permissions`의 최근 거부 탭에 기록된다.
반복 차단은 임계에 도달하면 auto 모드를 멈춘다.
분류기 요청 실패는 오류 문서로 연결된다.
경계 유실만 아무 신호가 없다.
사용자는 말했고, 시스템은 한동안 지켰고,
어느 시점에 지키지 않기 시작하는데 그 전환이 보이지 않는다.

더 나쁜 것은 이 실패가 사용자의 신뢰를 근거로 삼는다는 점이다.
경계가 처음에 잘 작동했다는 경험이
나중에 확인하지 않을 이유가 된다.
푸시하지 말라고 했더니 실제로 안 했다는 관찰이 쌓인 뒤에
압축이 일어나면, 그때가 확인을 가장 안 할 시점이다.
deny 규칙을 쓰라는 안내는 옳지만
문제를 인지한 사용자에게만 닿는다.
압축 시 경계 진술을 보존하는지,
경계가 유실됐을 때 사용자에게 알리는지,
현재 유효한 경계 목록을 조회할 수 있는지에 대한 서술이 없고,
셋 중 어느 것도 없다면 이 기능은 신뢰할 수 있는 상태로 제시되기 어렵다.

## 인사이트

### 승인이 자동화되면서 승인 사유의 설명 가능성이 함께 사라졌다

판정 순서의 네 번째 단계에 짧은 서술이 하나 있다.
분류기가 차단하면 Claude가 사유를 받아 다른 방법을 시도하는데,
대부분의 세션에서 그 사유는 서술된 설명이 아니라
`Blocked by classifier`라는 고정 텍스트이며 v2.1.208 이후 그렇다는 것이다.
기능 서술로는 한 줄이지만 함의는 크다.

사람이 승인하던 시절에는 판단의 기록이 사람에게 있었다.
왜 허용했는지 왜 막았는지를 승인한 사람이 설명할 수 있고,
설명하지 못하더라도 책임의 소재는 분명했다.
분류기가 승인하면 두 가지가 함께 바뀐다.
판단의 주체가 모델이 되고, 판단의 근거가 텍스트로 남지 않는다.
고정 문구로 바꾼 이유는 짐작할 수 있다.
서술된 사유가 Claude의 다음 시도를 유도해
우회 경로를 찾게 만들 수 있기 때문이다.
차단 사유를 알려 주면 그 사유를 피하는 방법도 알려 주는 셈이다.

같은 구도를 먼저 지나간 분야가 있다.
신용 심사와 사기 탐지가 규칙 기반에서 모델 기반으로 옮겨 갔을 때
정확도는 올라가고 설명은 사라졌다.
그리고 규제가 설명 요구를 다시 붙였다.
왜 거절됐는지 말할 수 없는 자동 판정은
정확하더라도 제도적으로 수용되지 않았기 때문이다.
에이전트 도구가 조직에 들어갈수록 같은 압력이 생긴다.
차이는 여기서 설명을 요구하는 쪽이 규제 기관이 아니라
사고 조사를 해야 하는 내부 팀이라는 점이다.

그래서 예측은 감사 기록 쪽으로 향한다.
지금 제공되는 것은 `/permissions`의 최근 거부 탭과
재시도 단축키이며 세션 안에서만 유효하다.
기업 도입이 진행되면 필요한 것은
세션 밖에서 조회 가능하고 시점이 기록된 결정 로그다.
무엇이 차단됐는지만이 아니라 무엇이 허용됐는지가 특히 그렇다.
차단은 사용자가 알아차리지만 허용은 알아차리지 못하고,
사후에 문제가 되는 것은 허용된 쪽이기 때문이다.
지금 당장 할 수 있는 대비는 두 가지다.
`claude auto-mode defaults`로 규칙 전문을 뽑아 버전과 함께 보관해 두는 것,
그리고 `PostToolUse` 훅의 `classifierContext`로
조직의 판단 맥락을 신뢰된 경로로 주입해 두는 것이다.

### 차단 목록은 위협 모델이 아니라 사고 이력이고, 그렇게 읽어야 쓸모가 있다

버전별 추가 항목을 시간순으로 늘어놓으면 목록의 성격이 바뀐다.
추상적인 위험 범주의 나열이 아니라
관측된 실패의 목록으로 읽히기 시작한다.
`/tmp`를 와일드카드로 지우는 것,
보안 테스트만 골라 주석 처리하는 것,
`.env.example`의 엔드포인트를 제3자로 돌리는 것,
값이 확인되지 않는 셸 변수를 재귀 삭제 대상으로 넘기는 것은
누군가 실제로 겪지 않으면 규칙으로 만들 이유가 없는 구체성이다.

그중 한 항목은 아키텍처의 한계에서 직접 나온다.
셸 변수 대상 재귀 삭제가 차단되는 이유를 문서가 설명한다.
변수 값이 이전 명령 출력에서만 왔고
분류기는 도구 결과를 받지 않으므로
삭제 대상을 다른 삭제 규칙과 대조할 수 없다는 것이다.
그리고 해제 방법도 명시된다.
정확한 경로를 사용자가 말하거나
Claude가 해결된 리터럴 경로를 명령에 써서 다시 실행하는 것이다.
즉 이 규칙은 위험 그 자체가 아니라
분류기가 볼 수 없다는 사실을 차단 사유로 삼는다.
안전 장치가 자기 시야의 경계를 규칙으로 표현한 사례다.

이 목록이 공개되어 있다는 점도 짚을 만하다.
차단 규칙을 공개하면 우회 경로의 지도가 되고,
공개하지 않으면 사용자가 왜 막혔는지 알 수 없다.
보안 도구가 오래 겪은 딜레마이며 이 문서는 공개 쪽을 택했다.
`claude auto-mode defaults`로 전체를 JSON으로 뽑을 수 있게 한 것은
그 선택을 한 걸음 더 밀어붙인 것이다.
대신 차단 사유는 고정 문구로 감췄다.
규칙은 공개하고 특정 판정의 근거는 감추는 조합이며,
설계로서 일관된다.

실무적으로는 이 목록을 자기 조직의 양식으로 삼을 수 있다.
우리 환경에서 실제로 문제가 됐던 행동을
이 목록과 같은 구체성으로 적어 보면
`autoMode.environment`에 넣을 항목의 후보가 그대로 나온다.
그리고 그 작업은 분류기 설정이 아니라
자기 조직의 위험 목록을 처음으로 문서화하는 일이 된다.
대부분의 팀에는 그런 목록이 없고,
있다면 그것이 도구 설정보다 오래 남는 자산이다.

### 도구가 자기 자신을 위협 모델 안에 넣기 시작했다

문서 곳곳에 흩어진 항목 다섯 개가 하나의 원칙을 가리킨다.
`.claude`가 보호 디렉터리라는 것,
세션 트랜스크립트 파일에 쓰는 것이 차단된다는 것,
자기 tmux 페인에 키 입력을 보내는 것이
자기 권한이나 감독을 바꾸는 행위로 분류된다는 것,
auto 모드 진입 시 광범위 allow 규칙이 해제된다는 것,
그리고 하위 에이전트 frontmatter의 `permissionMode`가 무시된다는 것이다.

이 다섯 개는 각각 다른 절에 있고 서로 참조하지 않는다.
그런데 모두 같은 문장으로 요약된다.
감독 장치를 감독 대상이 바꿀 수 없다는 것이다.
설정을 못 바꾸고, 기록을 못 고치고, 인터페이스를 조작하지 못하고,
자기에게 유리한 권한 규칙을 상속시키지 못한다.
트랜스크립트에 대해 쓰기는 막고 읽기는 허용한다는 세부까지
이 원칙과 일관된다.

같은 원칙이 먼저 자리 잡은 곳이 있다.
감사 로그를 추가만 가능하게 만들고 관리자도 지우지 못하게 하는 설계,
그리고 커널이 자기 메모리 영역을 사용자 프로세스로부터 분리하는 설계다.
공통점은 시스템의 일부를 나머지로부터 보호한다는 것이고,
그 구분선이 그어지는 시점은
나머지 부분을 완전히 신뢰할 수 없다고 판단한 시점이다.
에이전트 도구에서 그 판단이 내려졌다는 것이
이 문서의 조용한 내용이다.

여기서 나오는 예측은 다음 단계에 관한 것이다.
불변 기록의 역사에서 다음에 오는 것은 언제나 검증이다.
지우지 못하게 하는 것으로 시작해
서명하고 외부에 보관하고 대조하는 데까지 간다.
세션 트랜스크립트가 쓰기 금지 대상이 됐다면
그다음 질문은 그 파일이 변조되지 않았음을 어떻게 확인하는가다.
지금은 규칙이 그것을 막는다는 것뿐이고,
막힌 것과 확인된 것은 다르다.
그리고 그 단계에 이르면 보호 경로 목록은
보호 대상 목록이 아니라 신뢰 앵커 목록으로 이름이 바뀐다.

### 분류기가 도구 결과를 보지 못한다는 하나의 결정이 안전성과 오탐을 동시에 정한다

판정 절의 한 문장이 이 시스템 전체의 성격을 정한다.
분류기는 사용자 메시지와 읽기 전용이 아닌 도구 호출과 CLAUDE.md를 보고,
도구 결과는 제거되므로
파일이나 웹페이지의 적대적 내용이 분류기를 직접 조작할 수 없다는 것이다.

프롬프트 주입 방어로 보면 정확한 설계다.
분류기가 판정 대상과 같은 입력을 읽으면
그 입력에 심어진 지시가 판정자까지 오염시킬 수 있다.
판정자를 오염원에서 격리하는 것이 이 구조의 핵심이고,
서버 측 탐침이 들어오는 도구 결과를 따로 검사한다는 서술도 같은 계열이다.
방어의 층을 나누고 각 층이 보는 것을 다르게 만든 것이다.

그런데 같은 결정이 오탐의 구조적 원인이 된다.
셸 변수 항목이 그 증거이고, 그 항목만이 아니다.
분류기가 도구 결과를 보지 못한다는 것은
지금까지 무슨 일이 일어났는지를 부분적으로만 안다는 뜻이며,
맥락이 필요한 판정일수록 보수적으로 기울게 된다.
그리고 그 보수성이 반복 차단 임계와 만난다.
연속 3회 또는 누적 20회에 이르면 auto 모드가 스스로 멈춘다.
즉 분류기가 모르는 것이 많을수록
auto 모드가 자기를 끄는 빈도가 올라간다.

여기에 조정 손잡이가 두 개 있고 둘 다 같은 성질이다.
`PostToolUse` 훅의 `classifierContext`와
`environment` 설정의 신뢰 인프라 목록이다.
전자는 도구 결과에 애플리케이션이 붙인 주석이고
후자는 관리자가 미리 등록한 목록이다.
둘 다 모델이 읽은 내용이 아니라 시스템이 제공한 내용이다.
해법의 방향이 더 많이 보여 주기가 아니라
신뢰된 경로로만 보여 주기라는 점이 여기서 분명해진다.

그래서 실무 결론이 하나 나온다.
auto 모드에서 반복 차단이 잦을 때
먼저 손댈 곳은 프롬프트 표현이 아니다.
차단된 행동이 어떤 맥락을 필요로 하는지 확인하고,
그 맥락이 대화 본문이 아니라
훅이나 환경 설정 같은 신뢰된 경로로 들어가고 있는지를 보는 것이다.
대화에 설명을 더 쓰는 방식은 두 가지 이유로 약하다.
분류기가 그 설명을 읽더라도 압축으로 사라질 수 있고,
같은 경로로 적대적 내용도 들어올 수 있어
설계가 애초에 그 경로의 무게를 낮춰 두었기 때문이다.
