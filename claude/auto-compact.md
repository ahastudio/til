# Claude Code 자동 압축은 요약이지만 967K까지 기다리면 매 메시지가 비싸진다

트윗: [Just to avoid some confusion: auto-compact does summarize.](https://twitter.com/lydiahallie/status/2108624109538291901)

## 소개

Lydia Hallie(`@lydiahallie`)가 2026년 10월 10일에 올린 트윗이며,
조회수는 58만 5천 회다.
앞서 Twitter 사용자 `@wholyv`가 10월 9일에 올린 글이 있었고,
이 트윗은 그 오해를 바로잡는 답이다.
`@wholyv`는 자동 압축이 기본값에서 최근 100만 토큰을 컨텍스트에 불러오는 줄
알았고, 요약해서 부하를 줄이는 줄 알았다고 적었다.
그는 그래서 사람들이 세션을 압축하는 것만으로 5시간 한도의 2~15%를
쓴다고 보았다.

트윗이 하는 말은 세 가지다.
자동 압축은 요약하며, 실행되면 대화 전체가 짧은 요약으로 바뀌고 마지막 100만
토큰을 남겨 두지 않는다.
약 967K라는 수치는 100만 토큰 모델에서 압축이 실행되는 시점일 뿐이다.
압축 자체는 바로 앞서 보낸 메시지와 비슷한 양의 토큰을 읽는 요청 하나이고,
캐시가 아직 따뜻하면 대부분 캐시 읽기다.
트윗은 `@rohit3a`가 찾아낸 점을 인용하는데, 967K까지 기다리면 그 시점 이전의 모든 메시지가 그때까지의 대화 전체를 매번 포함하므로 토큰을 많이 쓴다는 것이다.
대부분은 캐시에서 읽혀 훨씬 싸지만, 그래도 사용량에 잡히고 대화가 길어질수록
쌓인다고 한다.
해법으로 제시된 것은 `/autocompact 400k`이며,
400K에서 요약하게 해서 메시지가 그만큼 커지지 않게 한다.

트윗에는 영상이 한 개 붙어 있고, 이 문서는 영상 내용을 읽지 못했다.
`@rohit3a`의 원래 글도 열어 보지 않았다.
이 문서는 트윗의 주장을 Claude Code 공식 문서와 대조해서,
맞는 부분과 문서만으로는 확인되지 않는 부분을 나눠 적는다.
`claude/claude-code-how-it-works.md`가 Claude Code의 전반적인 동작을 다루고,
이 문서는 그중 자동 압축과 캐시 비용이라는 좁은 주제를 다룬다.

## 동작 방식

### 자동 압축 창은 컨텍스트가 얼마나 차면 압축하느냐다

공식 문서는 자동 압축 창(auto-compact window)을 컨텍스트 창이 얼마나 차면 대화를
압축하는지의 기준이라고 정의한다.[^model-config]
문서는 Sonnet 5 이후, Haiku 5.5, Opus 4.7 이후,
Fable 5.1과 Fable 5가 기본으로 100만 토큰 창에서 돈다고 적는다.[^model-config]
같은 문서는 세션이 기본값에서 약 967K 토큰에서 자동 압축되며,
더 일찍 압축하려면 모델별 자동 압축 창을 줄이라고 한다.[^model-config]
따라서 트윗의 967K는 문서의 기본값과 일치하고,
100만 토큰 모델에서만 해당한다는 말도 이 문서가 확인한 범위에서는 맞다.
다만 이 문장이 문서에서 Haiku 5.5 항목에 적혀 있어서,
이 문서는 967K가 열거된 모든 모델에 같다는 점까지는 확인하지 못했다.

### 압축 요청은 큰 요청이지만 캐시가 따뜻하면 싸다

문서에 따르면 압축은 메시지 기록을 요약으로 바꾸며,
설계상 대화 층의 캐시를 무효화한다.[^caching]
요약을 만들기 위해 Claude Code는 별도의 요청을 보내고,
이 요청은 대화의 시스템 프롬프트와 도구,
요약할 기록을 반복한 뒤 요약 지시로 끝난다.[^caching]
캐시가 따뜻하면 그 요청은 접두부를 캐시에서 읽어서,
중간 세션의 `/compact`는 컨텍스트 크기가 암시하는 비용의 일부만 든다고 문서는
말한다.[^caching]
이는 트윗의 압축이 요청 하나이고 대부분 캐시 읽기라는 설명과 맞는다.
압축 다음 턴은 훨씬 짧은 요약만 캐시에 다시 쓰므로 느린 쪽이 아니라고 문서는
덧붙인다.[^caching]

### 압축을 기다리는 동안의 비용은 매 요청마다 쌓인다

문서는 Claude Code가 모든 요청마다 대화 전체를 보내고,
캐시 덕분에 그 기록을 캐시 토큰 요율로 다시 읽는다고 설명한다.[^costs]
그래서 하루 열려 있던 세션에서 한 줄 질문을 해도 대화 전체에 해당하는 사용량이
든다고 한다.[^costs]
이것이 `@rohit3a`의 지적과 겹치는 부분이다.
캐시 읽기는 싸지만 공짜가 아니므로, 컨텍스트가 커질수록 모든 메시지의 읽기
비용이 같이 커진다.

## 설정하기

공식 문서가 적는 설정 방법은 다음과 같다.
현재 모델에 대해서는 `/autocompact`를 값과 함께 실행하고(`/autocompact 500k`
같은 형태), `/autocompact auto`는 모델에 맞춰 조정된 창으로
되돌린다.[^model-config]
모든 모델에는 설정 파일의 `autoCompactWindow`를 쓰고,
한 번의 실행에는 `--autocompact` 플래그를 쓴다.[^model-config]
스크립트와 클라우드 환경에서는 환경 변수 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`에
토큰 수를 넣으며, 이 변수가 명령, 플래그, 설정보다 우선한다.[^model-config]

```bash
# 한 번만: 이 실행만 400K에서 압축한다
claude --autocompact 400k

# 세션 안에서: 현재 모델에 저장된다
# /autocompact 400k
# /autocompact auto    # 모델에 맞춰 조정된 기본값으로 복귀

# 스크립트와 CI: 명령, 플래그, 설정보다 우선한다
export CLAUDE_CODE_AUTO_COMPACT_WINDOW=400000
```

허용되는 값은 10만에서 100만 토큰이며, `200000` 같은 숫자,
`500k`나 `1M` 같은 접미사, 100에서 1000 사이의 맨숫자(천 단위)를 쓸 수
있다.[^model-config]
문서는 어떤 방식으로 정하든 창이 모델의 컨텍스트 창을 넘지 못한다고
한다.[^model-config]
모델별로 저장하는 동작은 v2.1.288부터이고,
그 전에는 모든 모델에 하나의 창이 저장되었다.[^model-config]
환경 변수에 `k`와 `M` 접미사를 쓰려면 v2.1.304 이상이어야 한다.[^model-config]
문서는 상태 줄의 사용 비율이 모델의 전체 컨텍스트 창을 기준으로 하므로,
환경 변수가 설정된 동안은 그 비율이 압축 시점을 알려 주지 않는다고
경고한다.[^model-config]

## 값 정하기

트윗이 든 400K와 문서의 예시 값들은 시작점일 뿐이며, 적정값은 작업 방식에 달려 있다.
아래는 이 문서가 제안하는 출발점이고, 각 값의 근거는 비용 구조다.

| 상황                           | 시작값           | 근거와 조정 신호                                                              |
| ------------------------------ | ---------------- | ----------------------------------------------------------------------------- |
| 긴 세션이 많고 사용량이 걱정됨 | 400K (트윗의 값) | 메시지마다 읽는 기록이 줄어든다. 압축이 너무 잦으면 값을 올린다               |
| 한 작업이 컨텍스트를 크게 채움 | 500K 안팎        | 압축으로 요약되면 세부가 사라지므로, 작업 단위가 큰 경우에는 창을 넉넉히 둔다 |
| 쉬었다 돌아오는 일이 잦음      | 값보다 TTL 확인  | 캐시가 식은 뒤의 첫 요청과 압축은 접두부를 새로 처리한다                      |
| 기본값(약 967K)을 유지         | `auto`           | 컨텍스트가 필요하고 사용량이 문제 되지 않으면 기본값이 맞다                   |

측정할 것은 `/usage`의 세션 블록에 나오는 캐시 통계다.
문서에 따르면 v2.1.251 이상에서 `Prompt cache (main)` 줄이 요청 수,
캐시에서 온 입력 토큰 비율, 미스 수, 캐시가 지금 따뜻한지를 보여 준다.[^costs]
창을 바꾼 뒤 같은 종류의 작업에서 이 비율과 한도 소모 속도를 비교하면 값을 근거
있게 고칠 수 있다.

## 트레이드오프

### 일찍 압축하면 비용이 줄지만 세부가 사라진다

400K에서 압축하면 메시지마다 읽는 기록이 줄어 사용량이 낮아진다.
압축은 대화를 요약으로 바꾸므로, 압축 전에 있던 파일 내용과 중간 결정이 요약에
남는지는 요약의 품질에 달린다.
문서는 압축이 버리는 것이 더는 필요 없는 내용일 때 유리하다고 하며,
작업 사이의 자연스러운 경계에서 `/compact`를 직접 실행하라고 권한다.[^caching]
버리고 싶은 경로에 들어갔다면 `/rewind`가 낫다고 하는데,
되감기는 이미 캐시된 접두부로 잘라 내기 때문이다.[^caching]
얻는 것은 낮은 사용량이고, 잃는 것은 요약에 담기지 않은 세부이며,
끝까지 남는 어려움은 무엇이 요약에 살아남을지를 미리 알 수 없다는 점이다.

### 캐시가 식으면 압축이 가장 비싸다

문서는 캐시 수명보다 길게 쉰 뒤에는 읽을 캐시가 없어서 요약 요청이 기록을
캐시되지 않은 입력으로 다시 처리한다고 한다.[^caching]
그래서 오래된 세션을 다시 열 때 `/compact`의 비용이 가장 크다.[^caching]
구독에서 주 대화의 기본 TTL은 한 시간이고, 사용 크레딧, API 키,
클라우드 제공자에서는 5분이다.[^caching]
트윗의 압축은 대부분 캐시 읽기라는 말은 캐시가 따뜻하다는 조건에서만 성립하며, 트윗도 이 조건을 단서로 붙였다.

## 함정

### 사용량이 높은 원인을 압축 하나로 돌린다

문서는 세션이 오래 열려 있을 때 사용량이 늘어나는 이유로 긴 컨텍스트와 캐시 미스
외에도 예약 작업, 다른 세션의 메시지, 목표 점검,
하위 에이전트와 워크플로를 든다.[^costs]
자동 압축 창을 줄여도 이런 요인이 그대로면 사용량이 기대만큼 줄지 않는다.
`/usage`의 분해 화면이 10% 이상을 차지하는 행동에 대해 권고를 낸다고 문서가
설명하므로, 그 화면에서 비중이 큰 항목을 먼저 확인해야 한다.[^costs]

### 창을 줄이면서 상태 줄 비율을 믿는다

환경 변수로 창을 정하면 상태 줄의 사용 비율이 압축 시점을 가리키지
않는다.[^model-config]
비율이 낮게 보여도 설정한 창에 가까워졌을 수 있으므로,
압축이 일어나는 시점은 비율이 아니라 설정한 토큰 수로 가늠해야 한다.

### 유휴 압축을 모른다

문서는 한 시간 TTL 상태로 긴 대화를 놀려 두면 Claude Code가 그 대화를 압축할 수
있고, `idleCompaction`을 `false`로 하면 끌 수 있다고 한다.[^caching]
이 설정은 v2.1.290 이상에서 요구된다.[^caching]
사용자가 직접 정한 창과 별개로 압축이 일어나므로,
압축 빈도를 추적할 때 이 동작도 확인해야 한다.

## 확인하기

사용 중인 버전에서 직접 시험할 수 있다.
먼저 `claude --version`으로 v2.1.288 이상인지 본다.
세션에서 `/autocompact 400k`를 실행하고,
같은 작업을 기본값(`/autocompact auto`)과 400K로 각각 진행해서 `/usage`의 한도
막대와 `Prompt cache (main)` 줄을 비교한다.
`CLAUDE_CODE_AUTO_COMPACT_WINDOW`를 설정한 세션에서는 `/usage`가 환경 변수의
값으로 덮였다는 것을 알려 주는지 확인한다.[^model-config]
캐시가 식은 상태의 압축 비용은 10분 이상 쉰 뒤 `/compact` 직전과 직후의 사용량
변화로 볼 수 있다.

## 비평

### 트윗은 수치를 주지 않고 그럴듯한 설명만 준다

트윗은 압축이 바로 앞 메시지와 비슷한 양을 읽는 요청 하나라고 하지만, 실제 토큰 수나 사용량 비율을 보여 주지 않는다.
`@wholyv`가 말한 2~15%라는 한도 소모와 400K에서 줄어드는 폭이 어느
정도인지도 없다.
공식 문서는 압축이 요청이라는 구조와 캐시가 따뜻할 때 싸다는 점을 확인해 주지만,
한도 소모의 정량적 크기는 문서에도 없다.
따라서 `/autocompact 400k`의 효과는 구조상 그럴듯하다는 수준이고,
사용자별 절감량은 직접 재야 알 수 있다.

### 따뜻한 캐시라는 전제가 결론의 크기를 정한다

트윗은 대부분 괜찮다는 결론을 캐시가 따뜻하다는 조건에 걸어 두었다.
그런데 문서에 따르면 캐시는 구독에서 한 시간, 그 밖에는 5분 안에 식고,
식은 뒤의 첫 요청은 접두부 전체를 새로 처리한다.[^caching]
자주 쉬는 사람, API 키 사용자, 사용 크레딧으로 넘어간 구독자는 따뜻한 캐시라는
전제가 맞지 않을 수 있다.
트윗은 이 경우의 비용을 말하지 않으며, 이 조건이 깨지는 사용자에게는 400K 권고의 이득이 더 커질 수도, 압축 자체가 더 비싸질 수도 있다.

### 기본값이 왜 967K인지는 말하지 않는다

트윗은 기본 창이 크다는 사실과 줄이는 법만 말한다.
왜 기본값이 그렇게 높은지, 높게 둔 이익이 무엇인지는 설명하지 않는다.
컨텍스트가 클수록 요약에서 사라지는 정보가 줄어든다는 것이 기본값의 합리적인
근거일 수 있지만, 이 문서는 문서에서 그 설명을 찾지 못했다.
그래서 기본값이 사용자에게 불리하다고 단정하기는 어렵고,
비용과 정보 보존의 교환이라고 보는 것이 맞다.

## 체크리스트

- 사용하는 모델이 100만 토큰 창에서 도는지 확인했는가.
- `claude --version`이 v2.1.288 이상인가.
- `/autocompact`로 정한 값이 `/status`나 `/usage`에서 의도한 값으로 보이는가.
- 환경 변수 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`가 설정되어 있어서 다른 설정을 덮고 있지 않은가.
- 창 값이 10만에서 100만 토큰 사이인가.
- 상태 줄의 사용 비율을 압축 시점의 신호로 읽고 있지 않은가.
- `/usage`의 `Prompt cache (main)` 줄로 캐시가 따뜻한지와 미스 수를 확인했는가.
- 오래 쉰 세션을 다시 열기 전에 `/compact` 비용이 큼을 알고 있는가.
- 사용량이 높은 원인이 압축이 아니라 예약 작업이나 하위 에이전트일 가능성을 `/usage` 분해로 확인했는가.
- 창을 바꾼 뒤 같은 작업에서 한도 소모 속도를 비교했는가.

## 기억할 원칙

### 컨텍스트의 크기는 한 번의 비용이 아니라 모든 요청의 비용이다

압축 시점을 늦추면 압축은 덜 하지만, 그만큼 모든 요청이 더 큰 기록을
다시 읽는다.
캐시 읽기가 싸다는 사실은 이 비용을 줄이지만 없애지는 않는다.
창을 정할 때는 압축 한 번의 비용이 아니라 압축 사이에 보낼 요청 수를 곱해서
생각해야 한다.

### 오해를 바로잡는 글도 측정으로 확인한다

트윗은 오해를 풀어 주지만, 효과의 크기는 사용자마다 달라서 글에서 읽을 수 없다.
구조에 대한 설명은 공식 문서로 대조할 수 있고,
절감량은 `/usage`로 직접 잴 수 있다.
둘을 나누어 확인하면 트윗의 권고를 근거 있게 쓸 수 있다.
