# Claude.dev: Anthropic이 개발자용 글과 영상을 한곳에 모은 새 홈

트윗: [Claude.dev is our new home for developers building with Claude.](https://twitter.com/ClaudeDevs/status/2105391694741119047)

## 요약

ClaudeDevs 계정이 2026년 10월 1일 오전 5시 17분(화면 표시 기준)에 올린 트윗이다.
본문은 두 문장이다.
Claude.dev가 Claude로 개발하는 사람들을 위한 새로운 홈이며,
엔지니어링 심층 글, Claude Code와 API 가이드, Claude를 만드는 팀의 팁,
그리고 몇 가지 재미있는 이스터 에그가 있다는 내용이다.
영상이 하나 붙어 있고, 조회수 150만에 답글 280, 리포스트 781, 좋아요 12K,
북마크 5.5K로 표시됐다(수치는 필자가 페이지를 연 시점 기준이다).

트윗이 가리키는 `claude.dev`를 열어 보면 제목은 “claude.dev Blog / technical
writing for people building with Claude”이고 소개문은 Anthropic의 개발자들이
나누는 팁과 요령과 관점이라고 한다.
글 분류 탭은 전체, 에이전트, 엔지니어링, 플레이북, 스킬, 튜토리얼이다.
추천 글 열 개는 Getting started with Claude Code mods(9월 28일, Addy Osmani,
튜토리얼, 11분), Automating eval design and hillclimbing with Claude(9월 28일,
12분), Building with Claude Sonnet 5.5(9월 25일, 9분),
Using Claude Code: Spending your effort(9월 25일, 8분), What a task costs on
Opus 5.5(9월 23일, 21분), How we made claude.ai 3x faster in two weeks(9월 22일,
15분), Getting the most out of Opus 5.5 in Claude and Claude Code(7월 24일,
9분), The new rules of context engineering for Claude 5 generation models(6월
3일, 7분), Lessons from building Claude Code: How we use skills(6월 2일,
11분), A harness for every task: dynamic workflows in Claude Code(11분)다.
추천 영상 다섯 편은 How founders build on Claude Managed Agents(9월 8일,
34분 42초), How the Claude Code team uses Claude Code(9월 2일,
22분 23초), How Ramp engineers work with AI agents at every step(8월 6일,
21분 59초), DoorDash gave every employee Claude Code(7월 7일,
25분 11초), The future of work with Claude(7월 2일,
11분 26초)이고 “YouTube에서 더 보기” 링크가 붙는다.

화면에 불러온 답글 세 개는 짧다.
Alex는 이런 출시 영상의 애니메이션을 만드는 사람이 급여 인상을 받아야
한다고 했고, Emanuele Di Pietro는 “clawdbot spotted”라고 썼으며,
Dave Kiss는 “keep hunting”이라고 남겼다.
이스터 에그를 찾는 놀이가 이 짧은 답글들에서 이미 시작된 것으로 보인다.

## 분석

### “새 홈”은 이미 있던 블로그에 이름과 입구를 준 것이다

트윗은 새 홈이라고 말하지만, claude.dev의 글은 출시 트윗보다 먼저 나왔다.
HN에는 9월 22일과 23일에 `claude.dev/blog/...` 글이 올라와 있었다.
`how-we-made-claude-ai-faster`(200점이 넘는 글),
`getting-the-most-out-of-opus-5-5`,
그리고 9월 27일의 `spending-your-effort`가 그 예이며, 이 저장소에도 이 블로그를
원문으로 인용한 노트가 있다.
그러니 10월 1일의 사건은 콘텐츠의 신설이 아니라 흩어져 있던 개발자용 글을 한
이름 아래 모으고 계정(ClaudeDevs)과 연결해 알리는 일로 읽힌다(블로그의 공식
개설일은 확인하지 못했다).

### 콘텐츠의 종류가 제품 사용 방식 자체를 향해 있다

추천 글의 제목을 보면 모델 소개나 제품 발표가 아니다.
Spending your effort, What a task costs on Opus 5.5, Getting the
most out of Opus 5.5, 컨텍스트 엔지니어링의 새 규칙, 스킬 사용법, 동적 워크플로,
평가 자동화와 hillclimbing은 모두 모델과 도구를 어떻게 쓸지에 대한 글이다.
분류 탭인 에이전트, 플레이북, 스킬, 튜토리얼도 같은 방향이다.

모델이 바뀔 때마다 좋은 사용법이 바뀐다는 사실이 이 콘텐츠를 필요하게 만든다.
이 저장소의 Opus 5.5 프롬프팅 가이드 노트가 보여 주듯,
모델 세대가 바뀌면 effort 기본값, 썸킹 가능 여부, 진행 보고 방식이 달라진다.
사용법이 모델과 함께 낡는다면 개발자 사이트는 한 번 쓰는 문서가 아니라 모델
출시에 맞춰 갱신되는 연속 게재물이 된다.

### 사이트는 글, 영상, 외부 사례를 한 표면에 놓는다

추천 영상은 Ramp, DoorDash 같은 고객 사례와 Claude Code 팀 내부의 사용법,
창업자들의 Managed Agents 사용기로 구성된다.
글이 만드는 사람의 관점이라면 영상은 쓰는 조직의 관점이다.
둘을 한 사이트에 두면 개발자가 “공식 팀은 이렇게 쓴다”와 “다른 회사는 이렇게
쓴다”를 같은 자리에서 비교할 수 있다.

추천 글의 필자 표시에도 눈에 띄는 점이 있다.
첫 카드에 Addy Osmani의 이름이 올라 있는데, 이 저장소의 다른 노트에 따르면
그는 9월 초 Anthropic에 합류해 Claude Code를 맡았다.
새 홈의 첫 번째 글을 최근 합류한 인물의 튜토리얼이 맡은 것은 사이트가 제품
책임자의 목소리를 전면에 두려는 신호로 읽을 수 있다(필자의 해석이다).

## 비평

### 트윗은 사이트를 설명하지만 주장의 근거는 영상에 있다

트윗 본문은 두 문장의 목록이다.
무엇이 있는지는 말하지만 이전의 어디와 무엇이 다른지는 말하지 않는다.
필자는 첨부된 영상을 볼 수 없어서(텍스트 추출로 읽었다) 영상이 무엇을
보였는지 확인하지 못했다.
답글의 단서(애니메이션, 이스터 에그)로 영상이 연출에 공을 들였다는 짐작은
가능하지만 내용은 알 수 없다.

그래서 이 트윗만으로는 “새 홈”이 이전의 문서, 블로그,
쿡북과 어떤 관계인지 알 수 없다.
Claude의 개발자용 문서는 `platform.claude.com`에 있고 제품
소식은 `anthropic.com`에 있는데(필자가 읽은 Claude 문서와 발표문의 주소에 근거한
것이다), 이 셋의 역할 분담은 트윗이 설명하지 않는다.

### 목록의 균형은 날짜가 말해 준다

추천 글 열 개 가운데 여섯 개가 9월 22일부터 28일 사이의 글이고,
나머지는 7월 24일, 6월 3일, 6월 2일과 날짜 없는 하나다.
최근 일주일의 비중이 큰 목록은 글이 활발히 올라온다는 인상을 주지만,
이는 추천 목록의 선택이며 전체 발행 빈도는 아니다.
“더 불러오기” 뒤에 몇 개의 글이 있는지는 확인하지 못했다.

또 트윗은 “Claude Code와 API 가이드”를 약속하는데 사이트의 분류 탭에는 API
항목이 보이지 않는다.
API 가이드가 에이전트나 엔지니어링 같은 다른 분류에 들어 있는 것인지,
문서 사이트로 연결되는 것인지는 이 화면만으로는 알 수 없다.

### 참여 수치는 관심의 크기이지 콘텐츠의 품질이 아니다

조회수 150만과 좋아요 12K는 개발자 커뮤니티가 이 계정을 얼마나
주시하는지를 보여 준다.
그러나 필자가 불러온 답글 세 개는 영상의 애니메이션에 대한 칭찬과 이스터 에그
이야기였고, 핵심 약속인 심층 글과 가이드의 품질에 대한 반응은 그 안에 없었다.
품질은 개별 글에 대한 반응이 보여 주며,
예컨대 HN에서 claude.ai 성능 글이 200점이 넘는 점수를 받은 것이 그런 신호다.

## 인사이트

### 개발자 플랫폼의 전쟁터는 문서에서 사용법 콘텐츠로 옮겨 간다

API 문서는 기능이 무엇인지를 말하고, 이 사이트의 글은 그것을
어떻게 쓸지를 말한다.
모델의 행동이 세대마다 바뀌는 시장에서는 후자가 채택의 병목이다.
같은 모델을 쓰면서도 effort 설정과 하네스 구성과 프롬프트 지시의
차이로 결과와 비용이 크게 달라지기 때문이다(Opus 5.5 글 두 편의 제목이 비용과
활용을 주제로 한다).

그러면 사용법 콘텐츠가 제품의 일부가 된다.
경쟁 모델도 능력이 비슷해질수록 개발자가 모델을 고르는 이유는 그 모델을 잘 쓰는
방법이 얼마나 쉽게 얻어지는가로 옮겨 갈 수 있다(필자의 전망이다).
claude.dev는 그 경쟁을 겨냥한 별도 매체로 보인다.

### 이스터 에그는 콘텐츠 소비를 참여로 바꾸는 장치다

트윗이 이스터 에그를 약속하고 답글에서 “찾는 중”이라는 놀이가 바로
시작된 것은 우연이 아니다.
사이트를 구석구석 뒤지게 만들면 방문이 한 번 읽고 나가는 소비에서 오래
머무는 탐색으로 바뀐다.
이는 게임과 개발자 문화에서 오래 쓰인 방식이다(필자의 일반론이다).

이 방식에는 대가가 있다.
탐험하는 사이트는 재미있지만 급할 때 정보를 찾는 사이트로서는 거슬릴 수 있다.
개발자용 사이트의 일차 사용자는 문제를 빨리 해결하려는 사람이므로,
놀이 요소가 검색과 읽기 경로를 방해하지 않는지가 사이트의 성패를 가를 것이다.
사이트의 검색 단축키(`S`)와 분류 탭이 그 균형의 장치로 보이지만 실제
사용성은 확인하지 못했다.

### 공식 목소리가 여러 채널로 쪼개질수록 한 곳에 모으는 가치가 커진다

개발자가 Claude에 대해 듣는 경로는 계정(ClaudeDevs), 문서 사이트, 제품 블로그,
영상, 팀원 개인 트윗(이 저장소에서 `spending-your-effort`의 원 트윗은 개인
계정이다)으로 흩어져 있다.
이 경로들이 서로 다른 속도로 갱신되면 같은 주제에 대한 지침이 어긋날 수 있다.
한 사이트에 모으고 그곳을 단일한 입구로 알리는 것은 이 불일치를 줄이는 방법이다.

반대로 한 사이트가 입구가 되면 책임도 한곳에 모인다.
어떤 글이 낡았는지, 어떤 권고가 철회됐는지를 알리는 일이 필요해진다.
모델이 빠르게 바뀌는 환경에서 글의 유통기한을 표시하는 방식(작성일
표시는 있지만 어느 모델 버전에 유효한지는 카드에서 보이지 않는다)이 이
사이트의 신뢰를 정할 것이다.
