# TeamClaude: 한 사람이 가진 여러 구독 계정을 묶어 한도에 닿으면 자동으로 옮겨 가는 로컬 프록시

<https://github.com/KarpelesLab/teamclaude>

## 소개

TeamClaude는 Claude Code와 Codex를 위한 다중 계정 프록시다.
저장소 설명은 Claude Max, ChatGPT와 Codex, API 키, 서드파티 백엔드 계정을
한 풀로 묶고 한도에 닿으면 계정을 돌린다고 한다.
코딩 에이전트와 공급자의 API 사이에 놓여서 여러 계정을 들고 있다가,
현재 계정이 세션 한도나 주간 한도에 가까워지면 다음 계정으로 옮겨 가므로
세션이 429 오류로 멈추지 않는다고 설명한다.
Claude 계정은 Claude Code를, Codex 계정은 Codex CLI를 맡고
두 풀이 프록시 하나를 공유한다.

2026년 11월 6일에 읽은 GitHub 정보는 다음과 같다.
MIT 라이선스, JavaScript, 스타 475개, 포크 149개, 열린 이슈 24개다.
2026년 3월 24일에 만들어졌고 최신 릴리스는 2026년 10월 31일의 `v1.1.27`이다.
npm 패키지는 `@karpeleslab/teamclaude`이고 Node.js 20 이상이 필요하며,
런타임 의존성이 없고 Node 내장 모듈만 쓴다고 한다.
컨테이너 이미지는 GHCR에 있고 Nix 플레이크도 저장소에 있다.

README가 가장 먼저 밝히는 것은 이 도구가 한 사람을 위해 만들어졌다는 점이다.
이름의 팀은 사람이 아니라 에이전트이고,
에이전트 세션을 열 개나 쉰 개씩 동시에 돌리는 사람은 구독 하나로 모자라
계정이 찰 때마다 손으로 갈아타는 일을 이 도구가 대신한다는 것이다.
풀의 모든 계정은 본인 것이고 클라이언트는 공급자의 공식 CLI이며,
사람 사이에 계정을 공유하거나 다른 클라이언트가 구독 자격으로 접속하게
하는 길이 아니라고 적는다.

README는 이름이 TeamRouter로 바뀔 예정이라고 한다.
Codex와 서드파티 계정까지 묶으므로 이름이 이를 말해야 한다는 이유다.
여러 릴리스에 걸쳐 진행되며, 지금은 새 이름이 모든 곳에서 받아들여지고
옛 이름이 기준으로 남아 있다.
`teamrouter` 명령이 같은 CLI를 실행하고,
`TEAMCLAUDE_*` 환경 변수를 `TEAMROUTER_*`로도 읽고,
`~/.config/teamrouter.json`이 있으면 그것을 쓴다.

## 시작하기

```bash
npm install -g @karpeleslab/teamclaude

teamclaude login     # 계정마다 한 번, 브라우저 OAuth
teamclaude server    # 프록시를 시작하고 TUI를 보여 준다
teamclaude run       # 다른 터미널에서: 프록시를 거치는 Claude Code
```

이미 Claude Code에 로그인해 있다면 `teamclaude import`가 그 자격을 가져온다.
자주 쓰는 명령은 다음과 같다.

| 명령                           | 용도                                           |
| ------------------------------ | ---------------------------------------------- |
| `teamclaude accounts`          | 계정과 등급, 토큰 상태 목록                    |
| `teamclaude status`            | 실행 중인 프록시의 상태, 서버가 떠 있어야 한다 |
| `teamclaude disable <name>`    | 계정을 지우지 않고 잠시 멈춘다                 |
| `teamclaude priority <name> 1` | 회전 순서, 숫자가 낮을수록 우선                |
| `teamclaude alias --install`   | 평범한 `claude`가 프록시를 거치게 한다         |

설정은 `~/.config/teamclaude.json`에 있고 손으로 고치도록 만들어졌다.
관찰한 한도는 옆의 `teamclaude.state.json`에 따로 저장하고,
지워도 트래픽에서 다시 학습한다고 한다.

## 동작 방식

README가 설명하는 요청의 흐름은 다섯 단계다.
Claude Code가 `api.anthropic.com` 대신 로컬 프록시와 통신한다.
프록시가 자격이 있는 계정을 고르고 그 계정의 실제 토큰을 넣고,
요청 본문의 `account_uuid`를 그 계정에 맞게 고쳐 쓴다.
응답의 `anthropic-ratelimit-unified-*` 헤더가 5시간 세션과 7일 주간 한도 정보를
채우고 재시작 뒤에도 남는다.
기준값(기본 98%)에 닿으면 회전하고,
한도 때문에 429가 나면 다른 계정으로 요청을 다시 보내 클라이언트가 한도를 보지
않게 한다.
만료되는 토큰, 일시적인 네트워크 오류, 클라이언트의 토큰 갱신은
프록시가 안에서 처리한다.

README가 나열한 기능 중 눈에 띄는 것은 다음과 같다.

- 주간 한도가 가장 빨리 초기화되는 계정을 우선해서 고른다.
- 모델별 주간 한도를 따로 추적해서, 한 모델의 한도를 다 쓴 계정도
  다른 모델의 요청은 계속 받는다.
- 소진된 한도 구간과 분당 요청 제한을 구분해서 앞의 것에서만 회전한다.
  분당 제한에서 회전하면 부하를 다음 계정으로 옮길 뿐 따뜻한 캐시만 버리기
  때문에 같은 계정에 속도를 맞춘다고 한다.
- 방금 바뀐 계정에 요청을 일정 속도로 흘려서, 에이전트 떼가 같은 순간에
  넘어가 그 계정을 다시 막는 연쇄를 막는다.
- 모든 계정이 소진되면 429를 돌려주지 않고 한도가 초기화될 때까지 요청을 붙들고
  있는 옵션(`holdSeconds`)이 있고 기본은 꺼져 있다.
- 모든 계정의 무료 한도가 끝났을 때 Anthropic의 유료 추가 사용량 계정을 쓰는
  옵션(`allowExtraUsage`)이 있고, 실제 돈이 청구되며 기본은 꺼져 있다.
- OAuth 토큰이 만료되기 전에 갱신해서 설정에 되쓴다.
- DeepSeek과 GLM 같은 Anthropic 호환 API를 낮은 우선순위의 대체로 쓸 수 있다.
- 계정마다 자기 HTTP 또는 SOCKS 프록시로 트래픽을 보낼 수 있고,
  그 프록시가 죽으면 다음 계정으로 넘어간다.
- 선택적으로 켜는 MCP 엔드포인트로, 에이전트가 세션 안에서 풀의 한도를 읽거나
  계정을 바꾼다.
- TUI에 한도 막대와 초기화까지 남은 시간, 활동 로그가 있고
  실행 중에 설정을 바꿀 수 있다.

## 프록시 모드

`teamclaude run`의 기본은 MITM 프록시 모드다.
일부 Claude Code 기능(예를 들어 Claude Design MCP)은
`ANTHROPIC_BASE_URL`을 무시하고 `https://api.anthropic.com`을 코드에
직접 적어 쓰므로, 평범한 리버스 프록시로는 이를 잡을 수 없기 때문이라고 한다.
이 모드는 claude를 HTTPS 포워드 프록시(`HTTPS_PROXY`) 뒤에서 띄우고,
로컬에서 만든 CA를 `NODE_EXTRA_CA_CERTS`로 신뢰하게 한다.
가로챈 호스트에서는 터널을 끝내고 요청마다 재시도하는 클라이언트로 다시
보낸다.
각 요청에서 활성 계정의 실제 자격을 넣고, 클라이언트의 `x-api-key`는 버리고,
`metadata.user_id` 안의 `account_uuid`를 고쳐 쓴다.

신뢰 모델에 대해 문서는 CA를 로컬에서 만들어 설정 디렉터리에 두고,
`teamclaude run`으로 띄운 claude 프로세스만 신뢰하며
시스템 신뢰 저장소에는 넣지 않는다고 한다.
CA 개인 키는 디스크에 쓰지 않고 잎 인증서 키는 `0600`이며,
상류 쪽에서는 진짜 Anthropic 인증서를 그대로 검증한다고 한다.
클라이언트의 토큰 갱신, Remote Control, claude.ai 첨부 파일 전송처럼
짝지어진 신원에 묶인 요청은 회전된 토큰으로는 실패하므로
클라이언트 자신의 자격으로 통과시킨다.

회사처럼 외부로 직접 나갈 수 없는 환경을 위한 상류 프록시 설정(`upstreamProxy`)도
있다.
`teamclaude env`가 `HTTPS_PROXY`를 TeamClaude 자신으로 내보내므로,
그 셸에서 시작한 서버가 자기 자신을 상류 프록시로 물려받지 않도록
자기 주소인 값은 버린다고 한다.

## 서비스 약관에 대한 저장소의 입장

`docs/compliance.md`는 메인테이너의 선의의 이해일 뿐 법률 자문이 아니라고 먼저
밝힌다.
사람 사이의 계정 공유, 재판매, 호스팅 서비스, 공급자 공식 클라이언트가 아닌
하네스에 구독 자격을 주는 일은 이 도구의 용도가 아니라고 한다.
`CONTRIBUTING.md`도 이 범위를 벗어나는 변경은 잘 만들었어도 병합하지 않는다고
적는다.
다중 구독 회전에 대해서는 Claude Code의 `/extra-usage` 흐름이 이미 한도에 닿으면
다른 계정으로 로그인하라고 안내한다는 점을 들어,
자동화된 풀링을 Anthropic이 명시적으로 허락한 것은 아니므로 현재의 약관을 직접 읽고
판단하라고 한다.
문서는 의도한 방식(진짜 Claude Code CLI, 본인 구독)의 사용이 Claude Code 약관과
일치한다고 메인테이너가 알고 있다고 쓰고,
OpenAI와 백엔드 공급자의 약관에 대한 같은 정리는 아직 없다고 인정한다.
기본값은 보수적이어서 클라이언트가 요청하지 않은 호출을 하는 기능
(keep-warm, 한도 탐침, 자동 초기화권 사용)은 꺼져 있다.

## 가짜 포크에 대한 경고

`SECURITY.md`와 README는 TeamClaude를 사칭한 악성 소프트 포크가 있다고 경고한다.
원래의 커밋 이력과 패키지 이름까지 유지한 채 저장소에 숨긴 바이너리와
이를 실행하는 설치 단계로 악성 코드를 심는다고 한다.
정식 출처는 이 저장소와 npm 패키지 `@karpeleslab/teamclaude`뿐이고,
바이너리 압축 파일로는 절대 배포하지 않으므로
압축 파일을 풀어 실행하라는 안내는 의심하라고 한다.

## 비평

### 한 사람을 위한 도구라는 선언과 기능 목록이 항상 맞물리지는 않는다

저장소는 사람 사이의 공유를 위한 것이 아니라고 반복해서 밝히면서도,
`proxy.clientKeys`, 루프백이 아닌 `proxy.host`, callback.net 토큰 동기화를
넣었다.
compliance 문서는 이 기능들이 자신의 기계와 에이전트가 자신의 프록시에
닿게 하려는 것이지 풀을 남에게 넘기는 방법이 아니라고 설명한다.
그러나 같은 기능은 기술적으로 다른 사람에게도 쓸 수 있고,
그 구분은 코드가 아니라 사용자의 의도에 달려 있다.
이 문서는 이 구분이 실제로 지켜지는지 확인할 수 없다.
저장소가 이를 스스로 인식한다는 것은 CONTRIBUTING이 사용자나 공유 프록시를
말하는 변경에 누구를 위한 것인지 묻겠다고 적은 데서 읽힌다.

### 약관 판단은 메인테이너의 이해에 기댄다

compliance 문서의 결론은 의도한 사용이 Claude Code 약관과 일치한다고
메인테이너가 알고 있다는 것이고,
Anthropic이 자동화된 풀링을 명시적으로 허락하지 않았다는 점도 같은 문서가
인정한다.
이 문서는 약관 본문을 읽지 않았고,
공급자가 이런 도구를 어떻게 볼지도 알 수 없다.
OpenAI 쪽은 저장소 스스로 아직 정리가 없다고 쓴다.
계정 정지 같은 결과의 책임은 사용자에게 있고,
또 이 도구가 요청 본문의 `account_uuid`를 고쳐 쓴다는 점은 동작 방식에서 본 대로다.
이 동작이 약관의 관점에서 어떻게 읽힐지는 문서가 다루지 않는다.

### 트래픽 우회 기능이 한도의 의도를 다르게 읽게 한다

프록시 모드 문서는 일부 429가 계정이 아니라 프록시의 나가는 IP에 걸리므로
계정을 돌려도 소용없다고 설명하고,
sx.org의 주거용 프록시로 다른 나가는 IP를 쓰는 옵션을 제공한다.
기본은 꺼져 있고 `always`와 `on 429 only` 모드가 있으며,
문서는 대역폭에 따라 실제 비용이 든다고 밝힌다.
같은 절에 TeamClaude 개발을 지원한다는 추천 링크가 들어 있다.
이 문서는 이 옵션이 공급자의 제한 장치를 피하는 용도로 쓰일 수 있다는 점과
저장소에 제3자 서비스의 추천 링크가 있다는 점을 사실로 적어 둔다.
이 옵션의 사용이 약관에 맞는지는 compliance 문서가 따로 다루지 않았다.

### 가로채기는 신뢰를 요구한다

MITM 모드는 로컬 CA를 만들어 한 프로세스에만 신뢰시키고
시스템 저장소에는 넣지 않는다고 한다.
이 설계는 위험을 줄이지만, 이 도구를 쓰는 순간 모든 계정의 실제 토큰과
요청 본문이 한 로컬 프로세스를 지난다는 사실은 남는다.
`src/` 디렉터리의 `server.js`는 약 297KB, `index.js`는 약 167KB로 작지 않다.
의존성이 없다는 장점이 있지만 직접 읽어 검증하기 어렵다는 부담도 함께 있다.
이 문서는 코드를 읽거나 실행하지 않았다.
저장소가 직접 경고하는 사칭 포크 사례는 이 신뢰가 실제 공격 표면임을 보여 준다.

## 인사이트

### 한도는 계정의 속성이 아니라 여러 겹의 신호라서 라우터가 복잡해진다

README의 기능 목록은 한도를 5시간 세션, 7일 주간, 모델별 주간으로 나누고,
소진된 구간과 분당 제한을 구분하고,
IP에 걸리는 429와 계정에 걸리는 429를 구분한다.
각각 다른 대응을 요구한다는 것이 이 프로젝트의 문서가 여러 쪽에 걸친 이유로
읽힌다.
이 문서의 해석으로는 이는 공급자의 한도 모델이 외부에서 헤더로만 추정할 수
있는 불투명한 규칙이라서,
라우터가 그 추정을 계속 보정해야 한다는 뜻이다.
공급자가 한도 모델을 바꾸면 라우터의 가정이 깨질 수 있고,
내려받은 릴리스 목록에서 10월에만 다섯 번(`v1.1.23`부터 `v1.1.27`까지)의 릴리스가
확인되는 것이 이 보정 작업의 빈도를 보여 준다.

### 에이전트가 늘수록 구독이 아니라 용량을 사게 된다

저장소의 출발점은 동시에 열 개나 쉰 개의 에이전트 세션을 돌리는 사람이 구독
하나로는 모자란다는 것이다.
구독이 사람 한 명의 속도에 맞춰 설계되었다는 가정은
에이전트가 그 속도를 깨는 순간 흔들린다.
같은 압력을 다른 쪽에서 보면 [codex-lb](../codex/codex-lb.md)는
Codex 계정을 로드 밸런서로 묶고,
[Claude Code 다중 계정](./claude-code-multi-account.md)은
공식 설정 폴더로 계정을 가르는 길을 설명한다.
세 문서는 같은 요구가 도구마다 다른 수준(분리, 풀링, 자동 회전)으로 나타난다는
점을 보여 준다.
다만 어느 수준이 공급자의 약관에 맞는지는 각 도구의 문서가 아니라
공급자가 정할 일이다.

### 한도를 숨기는 도구는 한도를 가르치는 도구가 된다

프록시가 429를 가려 주면 사용자는 어느 계정이 얼마나 쓰였는지 보지 않게
된다.
그래서 이 도구는 TUI에 한도 막대와 초기화 카운트다운을 크게 보여 주고,
MCP 엔드포인트로 에이전트에게 풀의 한도를 읽게 한다.
이 문서의 해석으로는 가리는 기능과 보여 주는 기능이 한 도구 안에서 같이
커지는 것은 우연이 아니다.
가리면 가릴수록 한도가 어디서 터질지를 운영자가 알아야 하기 때문이다.

### 결론을 바꿀 관찰

공급자가 자동 풀링을 명시적으로 허락하거나 금지한다는 공식 입장을 내면
이 도구의 법적 위치가 정해진다.
`src/`의 코드를 독립적으로 감사한 결과가 공개되면
토큰을 다루는 한 프로세스를 신뢰할 수 있는지 가려진다.
공급자가 한도 헤더의 형식이나 계정 신원 검증을 바꿨을 때
이 도구가 얼마나 빨리 따라가는지가 유지 가능성의 지표가 된다.
