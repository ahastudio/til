# cc-explorer: 흩어진 Claude Code 세션을 한곳에서 찾는 로컬 뷰어

<https://github.com/Noaarhk/cc-explorer>

Show GN: <https://news.hada.io/topic?id=32060>

## 소개

skarb8277이 GeekNews에 Show GN으로 올린 도구다.
로컬에 쌓인 Claude Code 세션 기록(`~/.claude/projects/**/*.jsonl`)을 디렉터리 위계로 탐색하고
대화 타임라인을 다시 읽고 검색하고 정리하는 로컬 웹앱이며, 저장소 설명은 읽기 전용 웹 뷰어라고 밝힌다.
저장소는 2026년 7월 3일에 만들어졌고 주 언어는 HTML이며 라이선스는 명시되어 있지 않다.
GeekNews 글은 8점에 댓글 3개를 받았다.

만들게 된 계기가 글 첫머리에 있다.
여러 프로젝트를 오가다 보니 세션이 디렉터리별로 흩어졌고, 예전 대화에서 필요한 내용을 찾지 못해
같은 것을 다시 묻거나 이미 했던 논의를 반복하는 일이 잦아졌다는 것이다.
`claude --resume`의 인터랙티브 피커로 세션을 고를 수는 있지만 탐색 범위가 현재 디렉터리와
`/add-dir`로 추가한 디렉터리로 한정되며, 디렉터리 구조와 세션이 어디에 흩어져 있는지를 기억해내는 것은
CLI로는 무리라고 느꼈다고 적는다.

설계 원칙은 네 가지로 정리되어 있다 — 파이썬 표준 라이브러리만 쓰므로 설치할 패키지가 없고,
`127.0.0.1`에만 바인드하며 외부 네트워크 호출이 없고,
대화 기록 내용은 수정하지 않으며 쓰기는 삭제 연장과 삭제와 설정 편집뿐이고,
macOS·Linux·Windows에서 동작한다.
GeekNews 글은 `server.py`와 `index.html` 두 파일이 전부이고 외부 패키지도 빌드 단계도 없다고 강조한다.

## 주요 기능

### 탐색과 검색

디렉터리 트리는 `~/.claude/projects`의 인코딩된 폴더명이 아니라 세션이 실제로 실행된 `cwd`로 위계를 만든다 —
평소 쓰던 디렉터리 구조 그대로 탐색된다는 뜻이다.
세션 목록은 최근 활동순이며 git 브랜치별로 묶이고, 제목·시각·메시지 수·모델·삭제 D-N 배지를 보여준다.

분기 위계가 이 도구의 특징적인 부분이다.
`/branch`로 갈라진 세션이 목록에 평평하게 나열되면 어느 세션에서 나온 갈래인지 알기 어려우므로,
분기 세션을 부모 밑에 들여쓰기로 붙이고 분기 태그를 달아 계보가 한눈에 보이게 했다.
부모가 다른 브랜치나 폴더에 있으면 태그에 마우스를 올려 원본 세션 제목을 확인한다.

대화 타임라인은 세션 ID·기간·토큰·사용 도구 요약과 함께 대화를 그대로 다시 보여준다.
검색은 두 층이다 — 모든 세션 본문을 훑어 매칭 세션과 스니펫을 보여주는 전체 검색과,
현재 세션 안에서 매칭을 하이라이트하고 `Enter`/`Shift+Enter`로 이동하는 세션 내 검색이다.
resume 버튼은 `cd '<cwd>' && claude -r '<세션ID>'`를 클립보드에 복사해 그 세션을 이어가게 한다.

### 필터

기간 필터는 전체·오늘·최근 7일·최근 30일·직접 입력 중에서 고르며 마지막 활동 기준이고,
목록과 검색 결과와 트리의 세션 수에 함께 적용된다.
표시 필터는 타임라인에 그릴 유형을 고르게 한다 — User, Assistant, 도구 결과, 주입 컨텍스트, thinking, 도구 호출 여섯 가지다.
도구 호출과 사고 과정이 너무 많이 섞여 읽기 어려웠기 때문에 내가 한 질문과 에이전트의 답변만 남기고 걷어낼 수 있게 한 것이다.

### 자동 삭제 관리와 설정

Claude Code는 시작할 때 `cleanupPeriodDays`(기본 30일)보다 오래된 세션 파일을 지운다.
따로 알려주지 않으므로 남은 기간을 삭제 D-N 배지로 띄우고(3일 이하 빨강, 7일 이하 노랑) 두 가지 방법으로 막는다.
연장은 그 세션의 시계만 리셋하며 내용은 그대로 두는데, 구현은 파일 `mtime`을 현재로 갱신하는 방식이다.
설정에서 `cleanupPeriodDays` 자체를 늘리면(예: 30 → 180) 모든 세션에 적용되고 배지도 즉시 새 기준으로 다시 계산된다.

정리도 같은 화면에서 한다.
체크해서 삭제하면 확인 모달을 거쳐 영구 삭제되며 복구할 수 없고,
세션 `.jsonl`과 함께 사이드카 디렉터리(`<session>/subagents/`, `<session>/tool-results/`)도 같이 지운다.
설정 드로어에서는 `showThinkingSummaries` 같은 boolean과 `effortLevel`도 편집할 수 있으며, 저장 전 `settings.json.bak` 백업을 남긴다.

## 설치

```bash
git clone https://github.com/Noaarhk/cc-explorer.git
cd cc-explorer
python3 install.py
cc-explorer
```

`http://127.0.0.1:8765/`가 브라우저에서 자동으로 열리고 포트가 쓰이고 있으면 자동으로 증가한다.
`--no-open`으로 자동 열기를 끄고 `Ctrl+C`로 종료한다.
설치 없이 `python3 server.py`로 바로 띄울 수도 있으며 요구사항은 Python 3.8 이상과 브라우저뿐이다.
저장소를 다른 경로로 옮기면 링크가 깨지므로 `install.py`를 다시 실행해야 하고, 제거는 `install.py --uninstall`이다.

## 분석

### 이 도구가 실제로 채우는 공백은 검색이 아니라 위치 기억이다

세션 검색 도구는 이미 여럿 있고, 대화 기록을 텍스트로 뒤지는 일 자체는 `grep`으로도 된다.
이 도구가 겨냥한 지점은 다르다 — 세션이 어디 있는지 모른다는 문제다.

Claude Code는 세션을 `~/.claude/projects` 아래 인코딩된 폴더명으로 저장한다.
사용자가 기억하는 것은 그 인코딩된 이름이 아니라 자기가 일하던 디렉터리이므로,
저장 구조와 기억 구조가 어긋난다.
이 도구가 가장 먼저 한 일이 트리를 실제 `cwd` 기준으로 다시 세운 것이고, 그것이 나머지 기능의 전제가 된다.

`claude --resume`이 현재 디렉터리로 범위가 한정된다는 제약도 같은 곳에서 나온다.
CLI는 현재 위치라는 맥락 위에서 동작하도록 설계되었는데, 세션 기록은 그 맥락을 가로질러 찾아야 하는 자산이다.
도구의 형태가 CLI가 아니라 웹앱인 이유도 여기에 있다 — 전역 목록을 한 화면에 펼치고 트리로 좁혀 들어가는 일은
터미널 인터랙션보다 브라우저 쪽이 잘 맞는다.

### 자동 삭제 관리는 기능이 아니라 위험 알림이다

세 번째 기능인 삭제 D-N 배지는 다른 두 기능과 성격이 다르다.
탐색과 필터는 편의를 개선하지만, 이 배지는 사용자가 몰랐던 사실을 알려준다 —
Claude Code가 30일이 지난 세션 파일을 시작할 때 조용히 지운다는 것이다.

README가 따로 알려주지 않으므로라고 적은 대목이 이 기능의 정당성이다.
공식 문서에 있는 동작이지만 사용자는 대체로 모르고, 알게 되는 시점은 대개 필요한 세션이 사라진 뒤다.
그래서 이 도구가 제공하는 실질은 조회 기능이 아니라 만료 임박이라는 상태를 가시화한 것이며,
그 위에 연장과 기준 기간 변경이라는 두 가지 대응 수단을 붙였다.

연장의 구현이 파일 `mtime` 갱신이라는 점을 README가 밝힌 것도 눈여겨볼 만하다.
이는 우아한 해법이 아니라 외부 도구가 쓸 수 있는 유일한 지렛대다 —
Claude Code가 만료를 파일 수정 시각으로 판단하므로, 그 판단 근거를 건드리는 것 말고는 방법이 없다.
읽기 전용을 표방하는 도구가 쓰기를 하는 세 지점(연장·삭제·설정 편집)이 모두 이 제약에서 나온 것이고,
그 예외를 README가 먼저 열거한 것은 정직한 설계 서술이다.

### 세션 기록이 자산으로 취급되기 시작했다는 신호

이 도구의 존재 자체가 코딩 에이전트 사용의 한 단계 변화를 가리킨다.
세션 기록을 로그로 보면 지워져도 상관없지만, 자산으로 보면 지워지면 안 된다.

만든 사람의 동기가 그 전환을 그대로 서술한다 — 예전 대화에서 필요한 내용을 찾지 못해
같은 것을 다시 묻거나 이미 했던 논의를 반복하게 되었다는 것이다.
즉 세션은 작업의 부산물이 아니라 그 프로젝트에 대한 축적된 맥락이며,
그 맥락을 잃으면 같은 비용을 다시 치른다.

이 관점에서 보면 분기 위계 기능의 의미도 달라진다.
`/branch`로 갈라진 세션들의 계보를 보여주는 것은 편의가 아니라 이력 관리다 —
어떤 시도가 어디서 갈라져 나왔는지가 곧 그 프로젝트에서 무엇을 탐색했는지의 기록이기 때문이다.
버전 관리가 코드에 대해 하는 일을 세션에 대해 하려는 시도로 읽을 수 있고, 아직 그 초기 단계에 있다.

## 비평

### 읽기 전용이라는 표방과 실제 쓰기 권한 사이의 간격

README는 대화 기록 내용은 수정하지 않는다고 굵게 강조하고 저장소 설명도 읽기 전용 웹 뷰어라고 적는다.
그런데 같은 문서가 쓰기는 삭제 연장·삭제·설정 편집뿐이라고 이어 붙인다.

이 세 가지는 결코 가볍지 않다.
삭제는 확인 모달을 거치지만 영구적이고 복구할 수 없으며, 세션 `.jsonl`뿐 아니라 사이드카 디렉터리까지 함께 지운다.
설정 편집은 `settings.json`을 건드리는데, 이 파일은 Claude Code 자체의 동작을 규정한다.
`effortLevel`이나 `showThinkingSummaries`를 바꾸는 것은 뷰어가 할 일의 범위를 명백히 넘어선다.

읽기 전용이라는 표현이 정확하려면 그 대상이 무엇인지 한정되어야 한다 — 대화 기록 내용은 읽기 전용이지 도구 전체가 그렇지는 않다.
이 구분이 중요한 이유는 사용자가 신뢰 수준을 결정하는 근거이기 때문이다.
읽기 전용 뷰어라고 이해하고 실행한 사용자는 이 도구가 자기 `settings.json`을 쓸 수 있다는 사실을 예상하지 않는다.
백업 파일을 남긴다는 점은 좋은 처리이지만, 그 처리가 필요하다는 사실 자체가 표방과 실제가 어긋난다는 증거다.

### 라이선스가 없다는 것은 쓰지 말라는 뜻에 가깝다

저장소에 라이선스가 명시되어 있지 않다.
GitHub에 공개되어 있고 `git clone`을 안내하지만, 라이선스가 없는 코드는 기본적으로 저작권자가 모든 권리를 보유한다.

Show GN에 올려 사람들에게 써보라고 권하는 도구에서 이것은 실질적인 문제다.
개인이 자기 컴퓨터에서 돌려보는 것까지는 대체로 문제가 되지 않지만,
회사에서 쓰거나 포크해서 고치거나 사내 도구에 통합하는 순간 법적 근거가 없어진다.
이 도구의 성격상 개발팀 단위로 쓰고 싶어지는 종류라는 점을 생각하면 더 그렇다.

같은 지적이 이 저장소만의 문제는 아니다.
개인이 만든 도구를 빠르게 공개하는 흐름에서 라이선스는 가장 자주 빠지는 항목이고,
빠졌다는 사실이 의도적 유보가 아니라 단순 누락인 경우가 대부분이다.
그래서 실질적 조언은 저자에게 향한다 — 파일 하나를 추가하는 비용으로 이 도구의 사용 가능 범위가 크게 달라진다.

### 세션 파일 포맷에 대한 의존이 어디까지인지 드러나지 않는다

이 도구는 `~/.claude/projects/**/*.jsonl`을 직접 읽고, 인코딩된 폴더명에서 `cwd`를 복원하고,
사이드카 디렉터리 구조(`subagents/`, `tool-results/`)를 알고 있으며, `settings.json`의 특정 키를 편집한다.
이 중 어느 것도 공개된 안정적 인터페이스가 아니다.

Claude Code는 빠르게 바뀌는 도구이고, 세션 저장 형식과 디렉터리 구조는 언제든 달라질 수 있다.
그때 이 도구는 조용히 잘못된 결과를 보여주거나 동작을 멈춘다.
후자는 낫다 — 전자가 위험한데, 예를 들어 새 형식의 메시지 유형을 인식하지 못하면 타임라인에서 일부가 사라지고
사용자는 그 대화가 원래 그랬다고 생각하게 된다.

README에는 이 위험에 대한 언급이 없고, 어떤 Claude Code 버전에서 검증했는지도 적혀 있지 않다.
비공식 포맷에 의존하는 도구가 반드시 밝혀야 할 것은 두 가지다 —
어느 버전에서 동작을 확인했는지, 그리고 형식을 인식하지 못했을 때 무엇을 하는지다.
읽기 전용을 강조한 도구일수록 후자가 중요한데, 읽기만 한다는 약속이 정확하게 읽는다는 뜻은 아니기 때문이다.

### GN 반응이 도구의 검증으로 읽히기에는 얇다

Show GN 글은 8점에 댓글 3개를 받았고, 그중 하나는 작성자 본인의 감사 인사다.
나머지 둘은 이전 작업 내역을 찾는 데 도움이 된다는 소감과 좋다는 짧은 반응이다.

이것은 이 도구가 나쁘다는 뜻이 아니라 아직 검증되지 않았다는 뜻이다.
스타 20개와 포크 3개도 같은 크기를 가리킨다.
Show GN이라는 형식이 자기 도구를 알리는 자리라는 점을 생각하면 자연스러운 반응 규모이지만,
읽는 쪽에서는 이 수치를 품질 신호로 오해하지 않아야 한다.

특히 이 도구는 세션 삭제 기능을 갖고 있고 그 삭제는 복구할 수 없다.
검증이 얇은 상태에서 복구 불가능한 동작을 제공하는 도구는 사용 순서를 정해두는 편이 안전하다 —
먼저 읽기 기능만 써보고, 삭제 기능은 세션 디렉터리를 따로 백업한 뒤에 쓰는 식이다.
README에는 그런 안내가 없다.

## 인사이트

### 에이전트 도구의 다음 격전지는 대화 기록의 소유와 검색이다

코딩 에이전트를 쓰는 시간이 길어질수록 축적되는 것은 코드가 아니라 대화다.
어떤 결정을 왜 내렸는지, 어떤 접근을 시도했다가 왜 버렸는지, 어떤 제약을 발견했는지가 모두 세션 안에 있고,
그 정보의 상당 부분은 커밋 메시지에도 코드 주석에도 남지 않는다.

지금 이 기록은 각 도구의 로컬 디렉터리에 도구별 형식으로 흩어져 있다.
Claude Code는 `~/.claude/projects`에, 다른 도구는 다른 곳에 저장하며 형식도 다르다.
그래서 도구를 바꾸면 축적된 맥락을 잃고, 여러 도구를 함께 쓰면 어느 대화가 어디 있는지 모르게 된다.
cc-explorer가 푸는 문제는 이 중 하나의 도구 안에서의 흩어짐이고, 도구 사이의 흩어짐은 아직 아무도 풀지 않았다.

여기서 예상되는 전개는 두 갈래다.
하나는 각 벤더가 자기 기록을 클라우드로 옮기고 검색을 기본 제공하는 방향인데,
그러면 편해지는 대신 기록이 로컬을 떠나고 이탈 비용이 커진다.
다른 하나는 공통 형식이 생겨 여러 도구의 기록을 한 곳에서 다루는 방향인데,
그러려면 벤더들이 자기 기록을 표준 형식으로 내보내야 할 유인이 있어야 한다.
전자가 벤더에게 유리하고 후자가 사용자에게 유리하므로, 기본값은 전자로 흐를 가능성이 높다.

그래서 cc-explorer 같은 로컬 도구의 의미는 기능 이상이다 —
기록이 로컬에 있고 사용자가 직접 다룰 수 있다는 상태를 유지하는 쪽에 서 있는 도구이고,
그 상태가 유지되는 동안에만 이런 도구가 존재할 수 있다.

### 조용한 데이터 삭제 정책은 사용자가 발견할 수 없는 종류의 손실을 만든다

`cleanupPeriodDays` 기본값 30일은 문서에 있는 정상 동작이다.
그런데 이 정책이 만드는 손실에는 특이한 성질이 있다 — 사용자가 손실을 인지하는 시점이 손실 시점보다 훨씬 늦다.

파일이 지워질 때 알림은 없고, 지워진 뒤에도 아무 증상이 없다.
증상이 나타나는 것은 몇 달 뒤 그 세션을 찾을 때이고, 그때 사용자가 내리는 결론은 대체로 내가 못 찾는 것이다.
없어졌다는 사실 자체를 확인할 방법이 없으므로 이 손실은 통계에도 잡히지 않는다.

이 구조는 캐시 정책의 얼굴을 하고 있지만 실제로는 보존 정책이다.
캐시는 지워져도 재생성되지만 대화 기록은 재생성되지 않는다.
기본값 30일이 선택된 근거가 디스크 사용량이라면, 그것은 저장 비용과 정보 가치를 비교한 결정인데
그 비교를 벤더가 사용자 대신 하고 있고 기본값이 삭제 쪽에 있다.

일반화하면 이렇다 — 사용자가 만든 데이터에 대한 기본 정책이 삭제일 때는 그 사실이 눈에 보여야 한다.
브라우저 방문 기록, 메신저 대화, 클라우드 휴지통이 모두 만료 정책을 갖지만 대체로 남은 기간이나 복구 경로를 노출한다.
cc-explorer의 D-N 배지가 하는 일이 정확히 그 노출이고, 그것을 서드파티 도구가 해야 했다는 점이
이 영역의 제품 성숙도가 아직 낮다는 것을 보여준다.

### 표준 라이브러리만 쓰고 두 파일로 끝낸 선택이 이 도구의 신뢰 근거다

파이썬 표준 라이브러리만 쓰고, 설치할 패키지가 없고, `127.0.0.1`에만 바인드하며, 외부 호출이 없다.
GeekNews 글은 `server.py`와 `index.html` 두 파일이 전부라고 밝힌다.

이 선택들은 기능이 아니라 감사 가능성에 대한 것이다.
이 도구는 사용자의 모든 Claude Code 대화를 읽는다 — 코드, 자격 증명이 스쳐간 로그, 사내 논의가 그 안에 있다.
그런 도구를 신뢰하려면 무엇을 하는지 확인할 수 있어야 하고, 파일 두 개와 표준 라이브러리는 실제로 확인 가능한 규모다.
의존성 트리가 수십 개인 도구였다면 같은 확인이 불가능했을 것이다.

이 관점은 개인용 도구 일반에 적용된다.
민감한 로컬 데이터를 다루는 도구에서 의존성 없음은 편의(설치가 쉽다)가 아니라 보안 속성(공급망이 없다)이며,
바이너리 배포가 아니라 소스 그대로 실행되는 형태도 같은 성질을 갖는다.
반대로 말하면, 이런 도구가 편의를 위해 프레임워크를 도입하는 순간 신뢰의 근거가 사라진다.

다만 이 신뢰는 검증하는 사람이 있을 때만 성립한다.
읽을 수 있다는 것과 읽었다는 것은 다르고, 스타 20개짜리 저장소의 `server.py`를 실제로 읽어본 사람은 많지 않을 것이다.
확인 가능성은 필요조건이지 충분조건이 아니며, 이 도구를 팀에 도입하려는 사람이 해야 할 일은
표준 라이브러리만 쓴다는 문장을 믿는 것이 아니라 그 파일을 한 번 열어보는 것이다.
