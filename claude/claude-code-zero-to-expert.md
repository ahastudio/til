# Claude Code 0에서 전문가까지: 컨텍스트, 계획, 검증을 가르치는 스페인어 가이드

트윗: [CLAUDE CODE de 0 a experto: La guía completa.](https://twitter.com/n0tisma/status/2114335960053821538)

## 소개

ismael(@n0tisma)이 2026년 10월 25일에 올린 스페인어 장문 글이다.
페이지에는 11분 분량이고 조회수 892.7K로 표시된다.
Claude Code를 처음 쓰는 사람이 팀 단위의 병렬 에이전트 운용까지 가는 길을
부(Parte)로 나눠 설명한다.
글은 스스로 10부라고 쓰지만 부 번호는 0부터 10까지여서 실제로는 열한 개다.
글머리는 ClaudeDevs가 Claude Code 코드의 약 90%를 Claude가 쓴다고 밝힌 트윗을
인용하며 시작한다.
이 가이드는 그 격차가 프로그래밍 실력이 아니라 도구가 안에서 어떻게 일하는지
알고 필요한 것을 주는 데서 난다고 주장한다.

글에는 Anthropic 쪽 트윗 아홉 개가 인용돼 있고, 도해 이미지가 열 장 붙어 있다.
열 장은 표지 한 장, 부별 도해 여덟 장, 마지막 치트시트 한 장이다.
이 문서는 본문 전체와 이미지 열 장을 모두 읽고 썼으며,
인용된 트윗은 열어 보지 않았다.
명령어와 설정은 Claude Code 공식 문서에서 확인했고, 확인한 쪽에는 각주를 달았다.

## 동작 방식

### 컨텍스트 창은 책상이고, 가장 중요한 부분이다

가이드는 한 가지만 가져가라면 Part 2를 가져가라고 한다.
Claude는 모든 것을 기억하는 것이 아니라 크기가 제한된 책상(mesa de trabajo)
위에서 일한다는 설명이다.[^mesa]
책상 위에는 영구 지침인 CLAUDE.md, 연결된 도구(커넥터와 MCP), 열어 본 파일,
지금까지의 대화, 명령 실행 결과가 올라간다.

Part 2의 도해는 이 구성을 한 줄 막대로 그린다.
왼쪽부터 CLAUDE.md, 도구, 열린 파일, 대화(메시지와 명령 결과), 남은 공간 순서다.
막대 아래에는 이 비율이 설명용이라는 작은 글씨(Proporciones
ilustrativas)가 있다.
실제 사용량을 보여 주는 그림이 아니라는 뜻이다.

책상을 정리하는 명령은 세 개다.

| 명령       | 가이드의 설명                                   | 공식 문서의 설명                                                           |
| ---------- | ----------------------------------------------- | -------------------------------------------------------------------------- |
| `/clear`   | 책상 전체를 비운다. 작업이 바뀔 때마다 쓴다     | 빈 컨텍스트로 새 대화를 시작한다[^commands]                                |
| `/compact` | 대화를 요약해 공간을 비운다. 보존할 내용을 지정 | 지금까지의 대화를 요약해 컨텍스트를 비운다. 요약 초점 지정 가능[^commands] |
| `/context` | 무엇이 책상을 차지하는지 보여 준다              | 컨텍스트 사용량을 격자로 시각화하고 최적화 제안을 보여 준다[^commands]     |

도해 맨 아래의 황금 규칙(Regla de oro)은 한 과제에 한 대화이고,
새 과제는 `/clear`로 시작하라는 것이다.
가이드는 한 대화에서 서로 다른 일 다섯 개를 하는 것을 초보자의 첫 번째
실수로 꼽는다.

### CLAUDE.md는 짧고 확인 가능한 규칙만 담는다

CLAUDE.md는 Claude가 대화를 시작할 때마다 자동으로 읽는 텍스트 파일이다.
프로젝트에서 `/init`을 실행하면 초안이 만들어지고, 그 뒤에 사람이 고친다.
공식 문서도 `/init`이 `CLAUDE.md` 가이드를 만든다고 설명한다.[^commands]

Part 3의 도해는 12줄짜리 예시 파일을 보여 준다.
Marta의 온라인 가게라는 가정(Tienda online de Marta)이고,
실행 명령 두 개(`npm run dev`, `npm test`)와 규칙 네 개로 이뤄진다.
규칙은 끝내기 전에 테스트를 돌려 결과를 보여 줄 것,
결제 폴더를 묻지 않고 건드리지 않을 것,
고객용 문구는 친근하게 너라고 부르는 말투(tuteo)로 쓰고 기술 용어를 피할 것,
내 승인 없이 커밋하지 않을 것이다.
오른쪽 네 칸은 넣을 것 둘과 뺄 것 둘이다.

| 구분 | 내용                                                      | 이유                                |
| ---- | --------------------------------------------------------- | ----------------------------------- |
| 넣음 | 추측할 수 없는 것: 테스트 방법, 건드리면 안 되는 곳, 취향 | 코드를 봐도 알 수 없다              |
| 넣음 | 확인 가능한 규칙: “테스트를 실행하라”                     | “좋은 코드를 써라”는 검증할 수 없다 |
| 뺌   | 긴 문서                                                   | 대화마다 책상을 차지한다            |
| 뺌   | 코드에 이미 있는 것                                       | Claude가 코드에서 직접 본다         |

가이드는 같은 실수를 두 번 하면 CLAUDE.md에 한 줄을 더하라고 권한다.
한 화면을 넘기지 말라는 기준도 같이 준다.
위치는 두 곳으로 나뉜다.
프로젝트 안의 파일은 해당 프로젝트의 규칙이고,
사용자 폴더의 `~/.claude/CLAUDE.md`는 모든 프로젝트에 적용되는 개인 선호다.

### 다섯 단계가 가끔 되는 것과 항상 되는 것을 가른다

Part 4는 요청 한 줄과 기다림을 방법으로 대체한다.

| 단계 | 하는 일                                    | 도해의 예시 문장                                                |
| ---- | ------------------------------------------ | --------------------------------------------------------------- |
| 1    | 탐색: 건드리기 전에 이해하게 한다          | “사용자 등록이 어떻게 동작하는지 읽어라. 아무것도 바꾸지 마라.” |
| 2    | 계획: 파일을 바꾸지 않고 계획을 제안받는다 | `Shift+Tab`이 계획 모드를 켠다                                  |
| 3    | 구현: 계획이 납득될 때만 진행을 허락한다   | “계획대로 진행해라.”                                            |
| 4    | 검증: 테스트, 웹 열기, 결과 확인           | “동작함을 보여 줘.”                                             |
| 5    | 저장: 변경을 검토하고 git에 저장한다       | “명확한 메시지로 커밋해라.”                                     |

도해의 맨 아랫줄에는 중단 키 두 개가 있다.
`Esc`는 Claude를 즉시 멈추게 하고, `Esc` 두 번(Esc Esc)은 시간 기계(máquina del
tiempo)처럼 이전 시점으로 돌아가 변경을 되돌린다.
공식 문서에서도 `Esc`는 현재 응답이나 도구 호출을 중간에 멈추고 그때까지의
작업은 남긴다고 한다.[^interactive-mode]
입력창이 비어 있을 때 `Esc` 두 번은 되감기 메뉴를 연다.[^interactive-mode]
`/rewind`는 대화와 코드를 이전 시점으로 되돌리는 명령이다.[^commands]

큰 작업에는 파일 두 개를 더한다.
`PLAN.md`는 단계별 계획이고 각 단계에 바뀌는 것과 확인 방법이 들어간다.
`PROGRESS.md`는 한 일, 통과한 테스트, 남은 일이다.
다음 날 새 대화를 열어도 Claude가 이 파일을 읽고 이어 간다.

### 모델은 역할로 나눠 쓴다

Part 5의 도해는 세 모델을 설계자, 구현자, 속도형으로 부른다.
막대 평가는 능력, 속도, 비용 세 줄이고 하단에 방향 평가(Valoración
orientativa)라는 단서가 붙는다.

| 모델       | 역할   | 능력 | 속도 | 비용 | 추천 용도                                   |
| ---------- | ------ | ---- | ---- | ---- | ------------------------------------------- |
| Opus 5.5   | 설계자 | 5/5  | 2/5  | 5/5  | 큰 계획, 어려운 결정, 남의 작업 검토        |
| Sonnet 5.5 | 구현자 | 4/5  | 4/5  | 3/5  | 일상 작업, 작성과 수정, 계획 구현           |
| Haiku 5.5  | 속도형 | 3/5  | 5/5  | 1/5  | 검색과 정렬, 기계적 작업, 검색 서브에이전트 |

막대 수는 이미지를 읽은 값이며, 가이드가 정한 방향 평가일 뿐 측정값이 아니다.
도해의 마지막 줄은 많이 쓰는 조합을 Opus가 계획하고, Sonnet이 만들고,
Haiku가 찾는 순서로 적는다.
글 본문은 Haiku 5.5가 이전 버전보다 약 75% 싸다는 Anthropic 트윗을 인용해 반복
작업의 자동화 문턱이 내려갔다고 말한다.

### 도구 상자는 다섯 가지이고, 요청과 규칙을 구분한다

Part 6의 도해는 다섯 가지 구성 요소를 카드로 보여 준다.

| 구성 요소              | 비유(원문)           | 하는 일                                   | 도해가 든 예와 진입점                         |
| ---------------------- | -------------------- | ----------------------------------------- | --------------------------------------------- |
| 스킬(skills)           | 레시피(las recetas)  | 반복 작업의 지침을 저장, 필요할 때만 연다 | 글 게시 체크리스트, `SKILL.md`                |
| 서브에이전트(subagent) | 인턴(los becarios)   | 자기 책상에서 일하고 요약만 돌려준다      | Haiku로 프로젝트를 읽는 검색기, `/agents`     |
| 훅(hooks)              | 알람(las alarmas)    | 특정 순간에 항상 자동 실행된다            | 편집 뒤 자동 포맷, `/hooks`                   |
| MCP                    | 콘센트(los enchufes) | Claude를 GitHub, Notion, Slack 등에 연결  | GitHub나 Notion의 작업 읽기, `claude mcp add` |
| 플러그인(plugins)      | 묶음(los packs)      | 위의 것을 한 번에 설치                    | 코드 리뷰 묶음, `/plugin`                     |

Part 6의 두 번째 도해는 CLAUDE.md 지침과 훅의 차이를 그린다.
CLAUDE.md 지침은 요청(una petición)이고, 훅은 규칙(una regla)이다.
파일 편집 열 번을 나란히 그려, 지침 쪽은 열 번 중 한 번이 물음표로 비어 있고 훅
쪽은 열 번 모두 체크가 된 모습이다.
이 그림은 설명용 예시(Ejemplo ilustrativo)이며 측정한 비율이 아니다.
도해의 결론은 절대 실패하면 안 되는 일은 훅에 넣으라는 것이다.

### 병렬 작업은 세션을 나누고 작업 복사본을 쓴다

Part 7에는 이미지가 없다.
가이드는 여러 대화가 동시에 일하게 하고,
서로 덮어쓰지 않도록 세션마다 프로젝트의 자기 복사본(git에서는 worktree)을 쓰게
하라고 한다.
딸린 기능으로 세 가지를 든다.

- `/btw`: 본 작업과 무관한 질문을 따로 열어 책상을 어지럽히지 않는다. 공식 문서도 대화에 더하지 않는 곁질문이라고 설명한다.[^commands]
- `/loop`: 세션이 열려 있는 동안 일정 간격으로 작업을 반복한다. 공식 문서의 설명과 같다.[^commands]
- `/schedule`: 컴퓨터가 꺼져 있어도 클라우드에서 도는 정기 작업을 만든다. 공식 문서는 이 기능을 클라우드 예약 작업(과거 이름 routines)으로 설명한다.[^commands]

### 보안은 모든 단계를 손으로 승인하는 방식의 한계에서 시작한다

Part 8의 도해는 제목이 직접 말한다.
모든 것을 손으로 승인하는 것이 더 안전하지 않다는 것이다.
막대는 Anthropic 테스트에서 위험한 명령을 잡아낸 비율로,
자동 모드 89%와 수동 승인 14%다.
도해 아래 단서는 모든 단계를 승인해야 하면 읽지 않고 예를 누르게 된다는 설명과,
다음 주부터 웹, 데스크톱, 모바일에서도 자동 모드가 기본이 된다는 안내다.
도해 출처 줄에는 `@ClaudeDevs, 7 ago 2026`과 `@claudeai,
22 oct 2026`이 적혀 있다.

가이드가 권하는 다섯 규칙은 다음과 같다.

1. 권한을 정의한다. `.claude/settings.json`이나 `/permissions`로 묻지 않고 할 일과 절대 하지 않을 일을 가른다.
2. 개인 정보를 보호한다. 전역 CLAUDE.md에 이름과 이메일을 외부 요청에 넣지 말고 웹 문서의 지시는 정보로만 다루라고 적는다.
3. 외부 콘텐츠를 불신한다. 웹과 PDF와 메일에 숨은 지시(프롬프트 인젝션)가 있을 수 있다.
4. 비밀 값은 `.env`에 두고 git에 올리지 않는다. Claude가 읽지 못하게 막는 훅까지 권한다.
5. 저장하기 전에 검토한다. `/code-review`와 `/security-review`를 쓴다.

`/security-review`는 공식 문서에서 현재 브랜치가 원격 기본 브랜치와 다른 변경을
분석해 주입, 인증, 데이터 노출 같은 위험을 찾는 명령으로 설명된다.[^commands]
자동 모드는 공식 문서상 Claude Code v2.1.283 이후 터미널과 VS Code 세션의 기본
시작 모드이고, 그 이전 버전에서는 Pro, Max,
Team 요금제에서만 그렇다.[^permission-modes]
Shift+Tab은 권한 모드를 순환시키는 키이며,[^interactive-mode] 계획 모드로
직행하는 키가 아니다.[^permission-modes]

### 치트시트는 본문에 없는 명령도 담고 있다

Part 10의 이미지는 2026년 10월 표기가 붙은 한 장짜리 표로,
본문에 없는 명령도 포함한다.
이미지 글씨가 작아 읽은 값이며, 본문에 이미 나온 것은 괄호로 표시한다.

| 묶음(원문 제목)                 | 항목                                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| 시작(EMPEZAR)                   | `/init`(본문), `@archivo`(파일을 대화에 넣기), `!comando`(터미널 명령 실행), `/help`         |
| 책상 정리(ORDENAR LA MESA)      | `/clear`, `/compact`, `/context`, `/btw`(모두 본문)                                          |
| 제어(CONTROLAR)                 | `Shift + Tab`(모드 전환), `Esc`, `Esc Esc`와 `/rewind`, `/model`                             |
| 재개(RETOMAR)                   | `claude --continue`(마지막 대화 이어서), `claude --resume`(고르기), `PLAN.md`, `PROGRESS.md` |
| 팀 꾸리기(MONTAR TU EQUIPO)     | `/agents`, `SKILL.md`, `/hooks`, `/plugin`                                                   |
| 연결(CONECTAR)                  | `claude mcp add`, `/mcp`(연결 확인과 관리), `claude -p "…"`(대화 없이 스크립트에서 실행)     |
| 자동화(AUTOMATIZAR)             | `/loop`, `/schedule`, `worktrees`(세션이 서로 덮어쓰지 않게)                                 |
| 검토와 보호(REVISAR Y PROTEGER) | `/code-review`, `/security-review`, `/permissions`                                           |

맨 아래 규칙 네 개는 한 과제에 한 대화, 건드리기 전에 계획, “동작함을 보여 줘”,
반복하는 것은 스킬이다.
`@archivo`는 파일 경로 자동완성을 여는 `@` 입력이고,
`!`로 시작하는 입력은 셸 모드로 명령을 실행해 그 출력을 세션에
더한다.[^interactive-mode]
`claude --continue`는 현재 디렉터리의 가장 최근 대화를 불러온다는 점에서
가이드의 설명과 같다.
CLI 참조의 해당 표에서 `--continue`와 `--resume` 항목은 확인했지만 `claude -p`의
항목은 이 문서가 열어 보지 않았다.

## 비평

### 공식 문서와 어긋나는 문장이 이미 있다

가이드의 명령 설명 대부분은 공식 문서와 맞지만, 세 군데는 현재 문서와 다르다.

첫째는 `/agents`다.
가이드는 서브에이전트를 `/agents`로 만들고 `.claude/agents/`에
저장한다고 적는다.
공식 문서에서 `/agents`는 서브에이전트 생성이나 관리를 Claude에게 요청하거나
`.claude/agents/`를 직접 고치라는 안내를 출력하는 명령이다.
v2.1.197 이하에서만 대화형 화면이 열린다.[^commands]
둘째는 `/hooks`다.
가이드는 훅이 `/hooks`로 설정된다고 하지만,
공식 문서는 `/hooks`를 훅 설정을 보는 명령으로 설명한다.[^commands]
셋째는 Shift+Tab이다.
도해는 `Shift+Tab`이 계획 모드를 켠다고 쓰지만, 공식 문서에서 이 키는 `default`,
`acceptEdits`, `plan` 등을 순환하며 자동 모드가 켜져 있으면 첫 입력이
`default`로 돌아간다.[^interactive-mode]
처음 쓰는 사람이 키를 한 번 누르고 계획 모드에 들어갔다고 믿으면 틀릴 수 있다.

가이드는 Claude Code가 몇 주마다 바뀌어 글을 계속 고치겠다고 밝힌다.
위 세 군데는 그 갱신이 아직 반영되지 않은 부분이거나 작성 시점 이후 바뀐 부분일
수 있고, 어느 쪽인지는 이 문서가 가를 수 없다.

### 모델 이름은 사용 환경에 따라 달라진다

Part 5는 Opus 5.5, Sonnet 5.5, Haiku 5.5를 세 칸에 고정해 보여 준다.
공식 문서의 모델 설정 표에서 Anthropic API에서는 세 별칭이 이 셋으로 풀리지만,
Amazon Bedrock과 Google Cloud의 에이전트 플랫폼에서는 Sonnet 4.5와 Haiku 4.5,
AWS의 Claude Platform에서는 Sonnet 4.6과 Haiku 4.5다.[^model-config]
같은 문서는 Sonnet 5.5가 Claude Code v2.1.284 이상,
Opus 5.5가 v2.1.280 이상을 요구한다고 적는다.[^model-config]
도해의 능력, 속도, 비용 막대는 이 환경 차이를 다루지 않는다.
가이드의 설치 안내는 Pro, Max, Team, Enterprise나 API 크레딧이 필요하다고 하며,
이는 공식 설치 문서와 맞다.[^setup]

### 89%와 14%는 한 번의 테스트이고 도해의 결론은 그보다 크다

Part 8의 도해 제목은 모든 것을 손으로 승인하는 것이 더 안전하지 않다는
일반 명제다.
근거는 Anthropic이 말한 테스트 한 번의 수치이며,
글이 인용한 트윗은 테스트에서 위험한 명령을 89% 잡았고 수동 승인은
14%였다고만 적는다.
무엇을 위험한 명령으로 셌는지, 사람이 실제로 얼마나 읽지 않고 승인하는지는 이
문서가 확인하지 못했다.
도해의 출처 줄 날짜도 본문에 인용된 트윗 날짜와 하루씩 어긋난다.
도해는 `7 ago`와 `22 oct`이고 본문에 인용된 트윗 표기는 Aug 8과 Oct 23이다.
시간대 차이일 수 있으며 이 문서가 가릴 수 없다.

수치의 해석도 갈린다.
매번 승인하다 보면 읽지 않고 누르게 되므로 자동 모드가 낫다는 읽기는 합리적이다.
다만 자동 모드의 분류기가 놓치는 11%가 어떤 종류인지,
그 11%가 되돌릴 수 없는 명령인지는 이 수치에서 알 수 없다.
그래서 이 글의 5개 보안 규칙 중 권한 정의와 비밀 값 보호가 자동 모드와
별개로 남는다.

### 가이드는 중간 규모 작업의 실패를 다루지 않는다

가이드의 방법은 계획과 검증이 있는 일에는 잘 작동하지만,
실패 대응은 `Esc`와 되감기 둘뿐이다.
테스트가 없는 코드베이스에서 “동작함을 보여 줘”가 무엇을 뜻하는지,
계획이 틀렸을 때 어디서부터 다시 하는지는 나오지 않는다.
이 문서가 확인한 범위에서 가이드는 이 질문에 답하지 않는다.

## 확인하기

글의 설명을 직접 확인하려면 작은 프로젝트에서 다음 순서로 해 본다.

1. `/context`를 실행해 연결한 도구가 책상을 얼마나 쓰는지 본다.
2. `Shift+Tab`을 눌러 상태 표시줄이 `plan mode on`을 보여 줄 때까지 몇 번 눌러야 하는지 센다. 횟수는 현재 모드에 따라 달라진다.
3. `/hooks`를 실행해 설정 편집 화면이 열리는지 설정 보기만 되는지 확인한다.
4. `/agents`를 실행해 대화형 화면이 열리는지 안내만 나오는지 확인한다.
5. 도구 호출이 끝난 뒤 입력창이 비어 있는 상태에서 `Esc`를 두 번 눌러 되감기 메뉴가 열리는지 본다.

## 체크리스트

- 작업이 바뀔 때 `/clear`로 새 대화를 시작했는가.
- CLAUDE.md가 한 화면 안에 들어가고 확인 가능한 규칙만 담고 있는가.
- 10분 넘게 걸릴 작업은 계획을 먼저 받았는가.
- 끝낸 작업에 대해 테스트 실행 같은 확인 방법을 요구했는가.
- 반드시 실행해야 하는 일을 CLAUDE.md의 지침이 아니라 훅에 넣었는가.
- 사용하는 환경(Anthropic API인지 클라우드 제공자인지)에서 가이드가 말한 모델 이름이 실제로 선택되는가.
- 가이드의 명령 설명을 쓰기 전에 현재 버전의 공식 명령 목록과 맞는지 확인했는가.

## 기억할 원칙

### 반복해서 틀리는 것은 규칙으로, 반드시 지킬 것은 훅으로 옮긴다

이 가이드에서 가장 오래 남는 구분은 요청과 규칙이다.
CLAUDE.md의 한 줄은 Claude가 대화가 길어지면 잊을 수 있는 요청이고,
훅은 매번 실행되는 규칙이다.
도해가 보여 준 열 번 중 한 번의 빈칸이 그 차이다.
무엇을 훅으로 올릴지 정하는 기준은 한 번 실패해도 괜찮은지 여부다.
