# 팀을 위한 클로드 코드 완벽 가이드 예제 저장소: 장마다 완주 시점의 스냅샷을 담고 일부러 깨진 상태로 시작하는 실습 재료

<https://github.com/wikibook/claude-code-teams>

<https://wikibook.co.kr/claude-code-teams/>

## 소개

이 저장소는 위키북스에서 나온 『팀을 위한 클로드 코드 완벽 가이드』의
예제 코드다.
저장소 설명은 책의 예제 코드라고만 적는다.
2026년 11월 6일에 읽은 GitHub 정보는 다음과 같다.
스타 0개, 포크 0개, 열린 이슈 0개이고 2026년 10월 2일에 만들어져
10월 18일에 마지막으로 푸시되었다.
기본 브랜치는 `main`이고, 라이선스는 GitHub이 인식한 것이 없다.

책 소개 페이지는 지은이를 윤대희로, 출간일을 2026년 10월 29일로,
분량을 752쪽으로, 정가를 38,000원으로 적는다.
지은이는 카카오스타일의 데이터 사이언스 팀 리더라고 소개한다.
책의 주제는 클로드 코드를 개인의 도구에서 팀의 인프라로 옮기는 과정이다.
소개 페이지는 개인에게 도입된 에이전트가 팀 단위에서는 결합 시점의 충돌,
공유되지 않는 노하우, 사용 비용의 편차를 낳는다고 진단하고,
파일럿 설계부터 팀 공통 환경, 병렬 작업, 리뷰 파이프라인, 비용 거버넌스,
보안, 에이전트 팀과 무인 자동화, 성과 측정까지를 순서대로 다룬다고 한다.

## 저장소의 구성

README는 본문에 실린 설정 파일과 스크립트가 모두 이 저장소의 실제 파일이라고
한다.
저장소는 장별 디렉터리로 나뉘고 각 장 폴더는 그 장을 완주한 시점의
스냅샷이다.
같은 프로젝트라도 장이 진행되면서 파일이 늘어나므로
실습은 반드시 해당 장의 폴더에서 시작하라고 안내한다.
각 장 폴더의 `README.md`에 사용하는 파일과 실행 방법이 있고,
본문의 사용자 입력은 장 폴더의 `prompts/`에 `장-순번_요지.txt`라는 이름의
텍스트 파일로 한 건씩 들어 있다.

예제 프로젝트는 다섯 개이고 모두 가상의 서비스다.

| 프로젝트   | 사용 장        | 설명                                               |
| ---------- | -------------- | -------------------------------------------------- |
| hello-todo | 2장            | 브라우저 할 일 목록 앱, 첫 실습용 최소 프로젝트    |
| moneylog   | 3장            | 지출 가계부 웹앱, 시작 상태에 실습용 버그 포함     |
| paylog     | 4~6장          | 결제 서비스 모노레포                               |
| notihub    | 7·8장, 13~17장 | 사내 알림 서비스 조직, 표준·거버넌스·자동화 실습용 |
| minishop   | 9~12장         | 주문·쿠폰·환불을 다루는 쇼핑몰 백엔드              |

1장과 17장은 본문 서술 중심이라 폴더가 없고,
15장 폴더에는 사용자 입력 파일 하나만 있다.
실습 환경은 Python 3.11 이상과 Node.js 22 이상이고
일부 예제는 `jq`와 `gh` CLI가 필요하다.
셸 스크립트는 POSIX 셸 기준이며 Windows에서는 Git Bash나 WSL을 쓰라고 한다.

폴더별 파일 수는 장마다 다르다.
이 문서가 파일 목록에서 센 값으로, 가장 큰 폴더는 12장(46개)과 10장(44개)이고
가장 작은 폴더는 6장(3개)과 15장(1개)이다.
`보조자료/`에는 15개 파일이 있다.

## 장마다 들어 있는 실습

이 문서가 장 README에서 읽은 내용을 장별로 정리한다.

- **9장 작업 결합의 공학**: 결합 오류를 재현하는 스크립트가 회사 손실
  1,200원을 출력하면 재현에 성공한 것이다.
  이어서 금액 계산 인터페이스 계약 문서, 계약 테스트, 파일 오너십
  (`CODEOWNERS`), 의존성 방향 검사 스크립트, 가정을 드러내는 PR 템플릿,
  병합 게이트 워크플로가 있다.
- **10장 Git 전략과 병렬 작업**: `claude --worktree`로 워크트리 두 개를 띄워
  병렬로 작업한다.
  README는 저장소 전체를 클론한 채 실행하면 저장소 전체가 워크트리로 복사되고
  `.worktreeinclude`도 적용되지 않으므로 minishop 폴더를 밖으로 복사해
  독립 저장소로 만든 뒤 진행하라고 안내한다.
- **11장 코드 리뷰 파이프라인**: PR 자동 리뷰 워크플로와 리뷰어
  서브에이전트 세 종류(계약, 보안, 컨벤션)가 있다.
  포크 PR에는 시크릿이 전달되지 않고 무료 비공개 저장소에서는 룰셋이
  강제되지 않으므로 공개 저장소를 권한다.
  트리거에서 `synchronize`를 빼면 푸시마다 다시 리뷰하지 않아 사용량을
  줄일 수 있다고 설명한다.
- **13장 비용 거버넌스**: 관리 설정으로 OpenTelemetry 텔레메트리를 켜는
  파일과 주간 비용 리포트를 만드는 Python 스크립트, 지출 데이터 샘플이 있다.
  README는 스크립트 출력이 본문의 출력 결과와 문자 단위로 일치한다고 한다.
- **15장 에이전트 팀과 멀티에이전트**: 지시문 하나가 전부다.
  예약 알림의 간헐적 중복 발송 버그(이슈 #482)에 대해 가설마다 팀원을 하나씩
  만들어 조사시키고, 서로의 발견으로 다른 가설을 반박하거나 지지하게 하며,
  코드는 고치지 않고 결론과 근거 로그를 태스크에 남기게 한다.
- **16장 파이프라인 통합과 헤드리스 자동화**: 헤드리스 스크립트, SDK 기반
  템플릿 검수기, 이슈 분류와 CI 실패 자동 수정 GitHub Actions 워크플로,
  야간 이관 배치 러너가 있다.
  README는 이 저장소의 스크립트가 모두 `--bare`로 실행되는데
  `--bare`는 장기 토큰 변수를 읽지 않으므로 콘솔 API 키를
  `ANTHROPIC_API_KEY`에 넣어 실행하라고 한다.
  GitHub Actions 예제는 로컬 실행이 불가능해 시험용 저장소가 필요하다.

## 보안 설정 예제

14장 폴더의 `payments-api/.claude/settings.json`은 결제 서비스용
권한 프로파일이다.
`.env*`와 `~/.aws`, `~/.ssh` 읽기, `aws`와 `kubectl` 실행,
`WebFetch` 전체를 거부하고,
`git push`와 `npm publish`는 매번 묻고,
`npm test`와 `npm run lint`, 특정 문서 도메인에 대한 `WebFetch`만 허용한다.
샌드박스는 켜 두고 `~/.aws`, `~/.ssh`, `~/.kube`, `~/.claude`의 읽기를 막고,
네트워크는 `registry.npmjs.org`와 문서 도메인만 허용하며
샌드박스 밖 실행은 허용하지 않는다.

같은 폴더의 `ops/managed-settings.d/10-security.json`은 조직 공통 정책이다.
`rm -rf /*`를 포함한 거부 목록과
우회 모드 비활성화(`disableBypassPermissionsMode`),
로그인 방식 고정, 관리 훅만 허용하는 설정이 들어 있다.
README는 우회 모드 차단이 관리 설정으로 배포되었을 때만 강제되므로
드롭인 파일을 운영체제별 시스템 경로에 두고 확인하라고 한다.
샌드박스는 macOS, 리눅스, WSL2에서만 동작한다고 밝힌다.

## 보조자료

`보조자료/`는 책의 결정을 조직에 옮기는 도구로 구성되었다고 README가 소개한다.
파일럿 기준 문서, 보안 검토 답변, 에이전트 팀 실행 예외 신청서,
팀 공통 `CLAUDE.md`, 권한 정책, PR 템플릿, 온보딩 문서의 양식과 예시,
6주 더하기 심화 2회의 스터디 가이드, 자가진단이 있다.
권하는 순서는 자가진단 A로 시작하는 것이다.
기반 관행 다섯 문항에 아니오가 셋 이상이면 도구보다 표준이 먼저이므로
6~8장의 내용과 관련 양식을 먼저 다루라고 한다.

## 비평

### 저장소만으로는 실습의 이유가 보이지 않는다

각 폴더의 README는 어느 파일이 본문의 어느 예제 번호에 대응하는지와
실행 명령을 알려 준다.
왜 그 설정을 그렇게 두었는지는 책 본문에 있고 저장소에는 없다.
이 문서는 책을 읽지 않았으므로 본문이 이 파일들을 어떻게 설명하는지,
예제가 책의 주장을 실제로 뒷받침하는지는 판단하지 못했다.
위의 내용은 저장소의 README와 몇 개의 파일, 책 소개 페이지를 읽은 결과다.

### 스냅샷 방식은 같은 프로젝트를 여러 벌 만든다

장마다 완주 시점의 스냅샷을 두는 방식은 실습의 출발 상태를 확실히 정해 주지만,
minishop이 9장부터 12장까지 네 번, paylog가 4장부터 6장까지 나오는 식으로
같은 프로젝트가 장마다 따로 있다.
README도 이전 상태는 앞 장의 폴더를 쓰라고 안내한다.
이 구조에서는 한 곳의 결함을 고쳐도 다른 폴더에 반영되지 않는다.
의도적으로 결함을 넣은 폴더가 있으므로 이는 설계로 보이지만,
수정과 유지보수는 장 수만큼 늘어난다.

### 라이선스가 없고 사용 범위가 적혀 있지 않다

GitHub API는 이 저장소의 라이선스를 인식하지 못했고,
읽은 README에도 라이선스 문구가 없다.
독자가 실습에 쓰는 것은 의도된 사용이지만,
파일을 자기 조직의 표준 문서로 가져가는 것은 책이 권하는 사용 방식이다.
그 재사용이 어디까지 허용되는지는 저장소에서 확인할 수 없다.

### 설정 키가 현재 클로드 코드와 맞는지 확인하지 못했다

README는 클로드 코드의 최신 버전이 필요하다고만 하고 버전을 적지 않는다.
`disableBypassPermissionsMode`, `allowManagedHooksOnly`, `--bare`,
`--worktree` 같은 설정과 옵션은 이 문서가 공식 문서와 대조하지 못했다.
실습이 버전에 의존하는 만큼 따라 하다 막히면 먼저 설치한 버전을 의심해야 한다.
이 문서는 예제를 실행하거나 빌드하지 않았다.

## 인사이트

### 일부러 깨진 상태로 시작하는 저장소는 사용자가 시험으로 읽게 만든다

3장 moneylog에는 실습용 버그가 들어 있고,
9장의 결합 실패 재현 코드는 수정되지 않은 상태이며,
16장의 `src/sum.js`에는 의도적으로 `a - b`가 들어 있어
CI가 실패해야 자동 수정 워크플로가 트리거된다.
훅이 있는 폴더에서는 `.env` 수정 같은 동작이 정책상 막히는데
README는 이것이 정상이라고 적는다.
이 문서의 해석으로는 이 저장소가 동작하는 예제의 모음이 아니라
실패를 재현하는 실험 키트다.
그래서 이 저장소를 그대로 자기 저장소에 넣어 CI를 돌리면 빨간 불이 나는 것이
정상이고,
독자는 통과하는 것이 아니라 어디서 왜 막히는지를 보도록 설계되었다고 읽힌다.

### 권한의 층위가 파일 위치로 나뉘어 있다

14장은 같은 거부 규칙을 프로젝트 설정과 관리 설정에 모두 둔다.
프로젝트 설정은 서비스 하나의 규제 등급을 정하고,
관리 설정은 조직 전체가 우회 모드를 끄거나 관리 훅만 허용하게 한다.
우회 모드 차단이 관리 설정으로 배포되었을 때만 강제된다는 README의 주의는
개발자가 자기 저장소의 파일을 고쳐서 풀 수 있는 규칙과
조직이 배포해서 풀 수 없는 규칙이 다른 층위라는 뜻이다.
이 구분을 이해하지 못하면 프로젝트 설정만 믿고 안전하다고 생각하기 쉽다.

### 도입은 코드가 아니라 문서 양식의 묶음으로도 설계된다

보조자료의 열 개 파일 중 대부분은 코드가 아니라 양식이다.
파일럿 기준, 보안 검토 답변, 예외 신청서, 권한 정책, PR 템플릿, 온보딩 문서가
그렇다.
자가진단에서 기반 관행에 아니오가 많으면 도구가 아니라 표준을 먼저 다루라는
순서가 이를 보여 준다.
이 문서의 해석으로는 이 책이 클로드 코드의 기능이 아니라
팀이 합의하고 기록하고 점검하는 절차를 제품으로 본다.
다만 이 양식이 실제 조직에서 도입 성과를 내는지는 이 문서가 확인할 수 없다.

### 결론을 바꿀 관찰

저장소에 라이선스와 버전 표기가 추가되면 재사용과 최신성의 두 가지 불확실성이
줄어든다.
책 본문이 이 파일들의 설정 이유를 설명하는 방식을 읽으면
위 해석이 설계 의도와 맞는지 가려진다.
장 폴더를 실제로 실행한 독자의 이슈나 후기가 쌓이면
실습 재료로서 얼마나 막힘 없이 동작하는지 알 수 있다.
